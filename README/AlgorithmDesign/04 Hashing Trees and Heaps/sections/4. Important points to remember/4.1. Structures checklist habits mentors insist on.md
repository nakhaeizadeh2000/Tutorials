## 4.1. Structures checklist (habits mentors insist on)

### 1) **Average with distribution, worst with intent**

**Definition** — every average claim in this domain travels with its distribution (hashing `O(1)` over non-adversarial keys — leaf 1.1's verified 10-chain; quickselect-adjacent expectations over random orders), and every worst case travels with its intent model (adversarial keys? sorted inserts? crafted collisions? — leaves 1.1/2.1's threat shapes). "Average" without distribution is a rumor; "worst" without intent is paranoia — the checklist demands both halves stated before code ships.

- **What problem it solves**: distribution-free averages and intent-free worsts produce the two classic misbudgets — HashDoS-shaped outages (average assumed, adversary delivered) and over-engineered defenses (red-black imported where input order is provably random — complexity without a customer). Stating both converts performance discussion from adjectives ("fast", "safe") into contracts ("`O(1)` average uniform, `O(n)` worst adversarial — budgeted for uniform, monitored for crafted").
- **Modern guidance** — write the pair per structure-use ("hash: average/uniform + worst/adversarial-budgeted" vs "hash: average/uniform, adversary impossible here because keys are internal IDs" — the second sentence is the analysis doing its job). Revisit intent when exposure changes (internal tool → public API: adversary model flips, worst-case budgeting activates). Test the honest cases (uniform benchmarks *and* degenerate probes — verified pairs from leaves 1.1/2.1 as the template).

```javascript
// GOOD: both halves stated — the contract travels with the structure
// user-session map: O(1) avg (uniform IDs) / O(n) worst (crafted keys) -> seeded engine hashing + monitoring.
// internal enum map: O(1) avg, adversary impossible (closed key set) -> average budgeted, no defense needed.
// BAD: "hash maps are O(1)" as the whole analysis —
// half a contract; the unbargained half bills under adversarial load
```

### 2) **Invariants before operations**

**Definition** — BST order (left < node ≤ right — leaf 2.1), heap property (parent ≤ children — leaf 3.1), trie prefix-sharing (common paths common nodes — leaf 3.2), traversal visit-orders (pre/in/post/level meanings — leaf 2.2): structure truths precede the code that maintains them. Operations *derive* from invariants (descent from order, sift from heap property, autocomplete from prefix sharing) — code written invariant-first is verifiable line by line; code written operation-first is hope with syntax.

- **Why it matters (correctness)**: invariant violations corrupt structurally (broken BST order returns wrong search results — silent, not crashing; violated heap property serves non-extremes — priority inverted without error; desynced tries miss completions). Each failure is silent-value (answers, not errors) and input-dependent (small tests preserve invariants accidentally). Invariant-first development plus invariant-asserting tests (verify heap property after every op in debug builds — pennies per check, total coverage) converts the class from incidents into caught bugs.
- **Modern guidance** — state the invariant as a comment above every structure implementation (one line — the contract future readers verify against). Assert invariants in debug/test builds (property checks after mutation ops — BST order, heap shape, trie counts). Test invariant edges explicitly (duplicates for BST policy, equals for heap stability-of-shape, empty/single for traversals — the verified matrices across leaves 2.1–3.2). When an invariant can't be stated crisply, the structure is wrong for the problem — back up to requirements.

```javascript
// GOOD: invariant as comment + debug assertion (structure truth, then code)
// BST: left < node <= right (duplicates right). Assert: inorder ascending after every mutation (debug).
// heap: parent <= children. Assert: loop verify after sift in tests (property, not order).
// BAD: structure code with no stated invariant ("it works on tests") —
// passing tests preserve invariants accidentally; production inputs violate them deliberately
```

### 3) **Bounds on every cache and table**

**Definition** — eviction at birth (Domain 01 §2.2's discipline, restated for this domain's structures): memo tables capped, frequency maps scoped to input lifetime, caches with LRU/TTL/weak-key policies, priority queues drained per use, trie suggestions display-bounded (leaf 3.2's collect-10 rule). Unbounded growth is a memory incident scheduled — cardinality-open structures (user keys, request IDs, stream vocabularies) grow until the heap gives, and the heap gives at 3 AM.

- **Why it hurts when missing (correctness, maintainability)**: unbounded-structure OOMs are the top application memory-incident shape (session maps, memo caches, frequency tables over streams — each grows with input cardinality, none shrinks without policy). The failure arrives as process death (no graceful degradation — heap exhaustion kills), diagnosed as "memory leak" when it's actually "memory policy absent." Eviction-at-birth converts death into bounded behavior (LRU evicts, TTLs expire, weak keys collect — memory becomes a budget, not a hope).
- **Modern guidance** — attach the bound or eviction policy in the same commit as the structure's creation (size cap, TTL, weak references — unbounded is a bug filed against the future). Prefer weak keys for derived caches (GC collects unreachable entries — policy without code), LRU caps for hot caches (recency approximates value), TTLs for time-sensitive data (staleness is correctness, not just memory). Audit growth in production (heap snapshots per deploy — tables that grow across deploys without bound get policies before the page fires).

```bash
# GOOD: bounds at birth, per structure (policy travels with creation)
#  memo table:   cap 100k entries + FIFO evict (leaf: Domain 01 §2.2 pattern)
#  session map:  TTL 30min + LRU 10k (staleness is correctness here)
#  frequency:    scoped to input lifetime (freed with the pass, never global)
#  suggestions:  collect-10 cutoff (leaf 3.2 — compute what displays)
# BAD: unbounded Maps "for performance" with no eviction anywhere —
# cardinality-open growth scheduled; heap exhaustion unscheduled
```

### 4) **Common confusion**

- "Checklists replace structure fluency" — checklists *trigger* the right analysis at the right moment (distribution? invariant? bound?). Fluency executes; checklists route. Both, in that order.
- "Average-case analysis is optional for interviews" — "over what distribution?" is the question separating analyzers from reciters (leaf 1.1's HashDoS shape as the canonical follow-up). Optional is how fails happen.
- "Invariants slow down shipping" — invariants speed *correct* shipping (one comment preventing silent-value incidents beats ten debugging hours). Slow is debugging corruption without a stated truth to check against.

### 5) **Performance note**

The checklist costs minutes per structure-use (distribution stated, invariant commented, bound attached) against silent-value incidents (wrong search results, inverted priorities, missed completions — hours of debugging answers that aren't errors) and OOM deaths (unbounded growth — process loss, not slowdown). Highest-leverage item is bounds-at-birth (prevents the death-shaped failure); second is invariant comments (converts incidents to caught bugs). Minutes preventing outages — structures' best attention rate.

### 6) **Mentor note**

Convert this leaf into the domain's application runbook: distribution + intent per average, invariants per structure, bounds per table — every use, every time. Quiz juniors on routing ("which question fires for user-keyed maps? for sorted feeds into BSTs? for streaming top-k?") until answers are environmental. Watch for checklist decay (analysis performed for a sprint, abandoned under deadline — fix with "requires:" comments and property asserts as review-blocking) and average-only quoters ("`O(1)`, done" — fix with "over what distribution, against whom?" reflexively). Review check: distributions stated, invariants commented and asserted, tables bounded — and the mentor's own structures modeling all three visibly.
