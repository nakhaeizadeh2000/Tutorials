## 5.1. Common interview QA: hashing, trees, and heaps

### 1) **Design a hash map**

**Definition** — the machinery screen: buckets + hash function, collision strategy (chaining vs open addressing — trade stated: chaining degrades gracefully, probing caches better), load factor + doubling resize (amortized `O(1)` — Domain 01 §2.1's method, fourth domain appearance), and honest bounds (average `O(1)` uniform, worst `O(n)` adversarial — leaf 1.1's verified 10 vs 10,000 chains as the receipt). Graded on *mechanics plus honesty*: candidates who derive resize-amortization and state the threat model pass; candidates who recite "`O(1)`" fail the follow-up.

- **What a good answer sounds like**: structure narrated with numbers — "array of buckets, Fibonacci-multiplied hash mod capacity; chaining on collision (verified max-10 at 10k/1024 uniform); resize at 0.75 doubling with rehash (amortized constant — same doubling economics as dynamic arrays); worst case all-one-bucket `O(n)` (verified 10,000 degenerate — HashDoS shape, seeded engine hashing defends)." Then the use close (complements/groups/caches — leaf 1.1's relation modeling) and the JS note (`Map` borrowed in production, hand-rolled for the interview).
- **Modern guidance** — interviewers listen for *resize reasoning* plus *adversarial honesty*: candidates who amortize doubling live and name HashDoS unprompted demonstrate depth; candidates who stop at "hash, bucket, done" demonstrate API memory. Red flags: open addressing without deletion-tombstone handling (deleted slots break probe chains — the classic implementation bug), load factor never mentioned (resizing unconsidered), "no worst case" claims (distribution-free averages — Domain 01 §1.2 violated live).

```javascript
// The design, sketched (leaf 1.1's verified machinery as interview response)
// buckets: Array(16) of chains; h(k): Fibonacci-mix mod capacity; load > 0.75 -> double + rehash.
// get/set/delete: O(1) avg (uniform — verified flat ns/op), O(chain) worst (verified 10 vs 10000).
// production: borrow Map (seeded, tuned); interview: hand-roll chaining + doubling + tombstone-free deletes.
```

### 2) **Validate a BST, iteratively**

**Definition** — the invariant screen: "is this binary tree a valid BST?" with the iterative constraint (no recursion — depth risk from leaf 2.2, made explicit). Expected answer threads bounds (each node carries `(low, high)`; left tightens high, right tightens low; violation fails fast) over an explicit stack — `O(n)` time, `O(h)` heap space. Verified-adjacent: inorder-ascending check is the alternative (sort-check via traversal — simpler, but `O(n)` aux for the output or threading mastery; bounds-threading is single-pass with `O(h)`).

- **What a good answer sounds like**: invariant first ("left < node ≤ right,_duplicates right — stated before code"), bounds derived ("root gets (−∞,+∞); descending left sets high=node.v, right sets low=node.v"), iteration justified ("explicit stack — degenerate trees threaten ~13,920-frame ceiling, Domain 01 §2.2"), edges covered (empty → valid; single → valid; equal-adjacent → policy applied). Then the complexity close (`O(n)` visits once each, `O(h)` stack — same envelope as traversal, different question).
- **Modern guidance** — grade derivation over recall: candidates who re-derive bounds-threading from the invariant pass even with shaky syntax; candidates who inorder-collect-and-check-sorted pass functionally but miss the `O(h)`-space point (ask "without storing the traversal?" as the follow-up that separates). Instant fail: comparing only parent-child pairs (grandparent violations pass — the classic wrong validator: checks local order, misses global invariant).

```javascript
// The answer derived, not recalled (leaf 2.1's invariant + leaf 2.2's iterative discipline)
function isValidBST(root) {
  const st = root ? [[root, -Infinity, Infinity]] : [];  // bounds travel with nodes
  while (st.length) {
    const [n, lo, hi] = st.pop();
    if (n.v <= lo || n.v > hi) return false;             // invariant violated: fail fast
    if (n.l) st.push([n.l, lo, n.v]);                    // left tightens high
    if (n.r) st.push([n.r, n.v, hi]);                    // right tightens low
  }
  return true;
} // O(n) time, O(h) heap space. Parent-only comparison ("check neighbors") FAILS grandparents — bounds or nothing.
```

### 3) **Top-k streaming numbers**

**Definition** — the heap screen: "k largest from an unbounded stream" — size-`k` min-heap keeps the k biggest (root = smallest-of-kept = admission threshold; arrivals above threshold evict-and-insert, below pass by). Verified: top-3 of 10,000 shuffled → `[9999,9998,9997]`, `O(n log k)` time, `O(k)` memory (independent of stream length — the property that makes it streaming). Against sort-and-slice (`n log n` per query) and full-sort-once (`n log n` + `O(n)` storage of history — fine for bounded re-query, wrong for streams).

- **What a good answer sounds like**: inversion stated ("min-heap for largest-k — the heap holds the *threshold*, arrivals audition against it"), economics compared ("`n log k` streaming vs `n log n` sort-per-query — gap structural for `k ≪ n`; sort-once wins only for bounded re-queryable data"), memory bounded ("`O(k)` regardless of stream — unbounded streams demand bounded state, Domain 01 §2.2's discipline restated"), edges covered (`k > n` → all elements; `k = 1` → running max; duplicates → threshold admits equals consistently).
- **Modern guidance** — listen for the *inversion* (min-for-max stated deliberately, not stumbled into) plus *streaming economics* (memory independent of input length — the sentence separating stream algorithms from batch ones). Red flags: max-heap of everything + pop-k ("works" at `O(n)` memory + `n log n` build — streaming violated, batch smuggled in), sort-per-query on streams (re-sort per arrival — quadratic-ish total, the pattern unrecognized), no `k > n` handling (edges unconsidered).

### 4) **Common confusion**

- Candidates who design hash maps without resize ("fixed buckets suffice") — load factor degrades silently; doubling is the analysis, not an optimization.
- "BST validation via inorder-sortedness is cheating" — it's a valid alternative (`O(n)` time), trading `O(n)` output space for conceptual simplicity; bounds-threading is the `O(h)`-space refinement. Know both, state the trade.
- Treating top-k as "sort, take k" under streaming constraints — batch answers to stream questions reveal pattern blindness; the heap inversion is the screened knowledge.

### 5) **Performance note**

Interview answers here should be compact: hash-map design (three minutes — buckets, collisions, resize-amortization, honest bounds, production note), BST validation (two minutes — invariant, bounds-threading, iterative justification, grandparent-trap named), top-k streaming (two minutes — inversion, economics, edges). Candidates who narrate mechanisms with receipts take the same time as silent coders and prove triple — structure is speed, in interviews as in analysis.

### 6) **Mentor note**

Use Q1 as the machinery screen (resize derived live, HashDoS named unprompted), Q2 as the invariant screen (bounds threaded from contract, grandparent-trap avoided), Q3 as the economics screen (inversion stated, streaming memory bounded). Rubric: junior — correct structures with counting shown; mid — invariants stated, edges covered (duplicates, empty, `k>n`), amortization mechanized; senior — threat models (adversarial keys named), tightness awareness, borrow-vs-build discipline ("ship Map, hand-roll for understanding") without prompting. Keep the verified numbers ready (10 vs 10,000 chains; depth 10 vs 4; `[9999,9998,9997]`) — receipts separate narrators from memorizers. Red-flag fails: resize-free maps, parent-only validators, sort-per-query streaming, distribution-free averages.
