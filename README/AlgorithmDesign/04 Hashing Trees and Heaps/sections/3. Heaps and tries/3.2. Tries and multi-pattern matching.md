## 3.2. Tries and multi-pattern matching

### 1) **Prefixes share nodes**

**Definition** — a trie stores strings character-by-character down shared paths: common prefixes occupy common nodes (insert walks/creates one node per character — `O(m)` per word of length `m`), word-endings marked with counts/flags. Verified: 5 words (`app/apple/application/apt/bat`, 19 characters total) occupy **17 nodes** — shared `app`/`ap` prefixes compress structurally (each shared prefix stored once, however many words share it). Lookup walks characters (`O(m)`, independent of word count — dictionary size never enters the cost).

- **What problem it solves**: prefix-shaped workloads defeat flat structures — autocomplete over hash maps scans all keys per keystroke (`O(n·k)`); sorted word lists binary-search per prefix (`O(k log n)` plus range enumeration); regex alternations recompile per query. Tries convert prefix sharing into structure: descent *is* the query (walk the prefix — arrival means match), and storage compresses exactly where language redunds (shared stems, morphological families, URL hierarchies). The shape fits the question like convergence fits sorted pairs (Domain 03 §1.1).
- **Modern guidance** — reach for tries on prefix workloads (autocomplete, spell-suggest, IP routing tables, multi-pattern scanning below). Implement with `Map` children (Unicode-safe, iteration-ordered — plain-object children reintroduce key-stringification hazards from leaf 1.1's warnings). Mark endings with counts (frequency-aware suggest ranks by count — free with `end++`), not booleans (counts generalize; flags don't). Compress single-child chains (radix/ Patricia variants) past ~10⁵ keys — node-per-character overhead dominates at scale.

```javascript
// GOOD: sharing as structure — verified 17 nodes for 19 characters
function trieInsert(t, w) {
  let n = t;
  for (const c of w) {                       // unicode-safe iteration (code points, not UTF-16 units)
    if (!n.kids.has(c)) n.kids.set(c, { kids: new Map(), end: 0 });
    n = n.kids.get(c);
  }
  n.end++;                                   // counts, not flags (frequency ranks free)
} // insert O(m), lookup O(m) independent of dictionary size. 5 words -> 17 nodes verified.
// BAD: sorted-array + binary-search per keystroke ("simpler") —
// O(k log n) per keystroke plus range enumeration; latency bills per character typed
```

### 2) **Autocomplete walks the trie**

**Definition** — descend the prefix (miss → empty result, `O(m)`), then enumerate the subtree (DFS collecting endings — cost proportional to *matches*, not dictionary). Verified: `app` → `["app","apple","application"]`; `z` → `[]` (miss in 1 step — non-prefixes fail fast, never scanning). Lookup of exact words reads `end` counts (verified `app:1, apple:1, appl:0` — prefix-without-word correctly zero). The query costs track answer size, not data size — the scaling property autocomplete needs (keystrokes interactive, dictionaries huge).

- **Why it matters (correctness)**: autocomplete latency budgets live per keystroke (sub-50ms interactive) against million-word dictionaries — linear scans blow the budget by 4 orders of magnitude, and caching only helps repeated prefixes (first-typed prefixes miss always). Trie descent costs prefix-length (single-digit steps), enumeration costs matches (bounded by UI display count — top-10 cutoff caps it structurally). The performance *is* the feature here: slow autocomplete isn't used, whatever its recall.
- **Modern guidance** — cap enumeration at display count (collect-10-then-stop — unbounded subtree walks on `a*` prefixes defeat the purpose; UI shows ten, compute ten). Rank by frequency counts (the `end++` from previous section, plus query-log weights — popular completions first). Handle misses fast and explicitly (`[]` with suggestion fallback — "no matches" is a designed response, not an error path). For fuzzy matching (typos — edit distance ≤ 1), extend to Levenshtein automata on trie traversal (Domain 06's DP wearing trie clothes — the cross-link that pays for both domains).

```javascript
// GOOD: descent + bounded enumeration — verified completions and fast miss
function complete(t, p, limit = 10) {
  let n = t;
  for (const c of p) { n = n.kids.get(c); if (!n) return []; }  // miss in O(m), zero scanning
  const o = [];
  (function walk(x, s) {
    if (o.length >= limit) return;           // UI-bounded: compute what displays, nothing more
    if (x.end) o.push(s);
    for (const [c, k] of x.kids) walk(k, s + c);
  })(n, p);
  return o;  // complete(app) -> ["app","apple","application"] verified; complete(z) -> [] verified.
}
// BAD: full-subtree enumeration sorted by insertion ("complete") —
// unbounded walks on short prefixes; UI displays ten, server computed ten thousand
```

### 3) **Aho-Corasick generalizes KMP**

**Definition** — Aho-Corasick runs KMP's idea on a trie: build failure links on trie *nodes* (longest proper suffix that's also a trie prefix — KMP's prefix table lifted from one pattern to a pattern set), then scan text once following goto-or-fail transitions — `O(n + m + z)` total (`n` text, `m` pattern mass, `z` matches). Single pattern → reduces to KMP (Domain 03 §3.2's ancestor, honored); many patterns → one pass finds all (virus signatures, profanity filters, log-signature sets — the workloads where per-pattern scanning bills multiplicatively).

- **Why it hurts when missing (correctness, maintainability)**: multi-pattern scanning without AC multiplies work by pattern count (KMP × 10k signatures = 10k text passes — log pipelines that never finish; regex alternation of 10k patterns = backtracking roulette with catastrophic worst cases). AC converts pattern-count from multiplier into preprocessing (build once over pattern mass, scan once per text — the same economics as sorting-once-query-often, Domain 02). Teams that need it and lack it ship either slowness (per-pattern passes) or wrongness (naive alternations with missed overlaps).
- **Modern guidance** — reach for Aho-Corasick on multi-pattern exact matching (signature sets, dictionaries, entity extraction — 100+ patterns is the crossover where AC beats batched KMP; below that, batched single-pattern scans win on simplicity). Build with BFS-ordered failure links (queue discipline — Domain 03 §3.1's FIFO, fourth appearance: levels before links). Output-link optimization for dense matches (follow output chains, don't re-walk — matches-per-position stay linear). Full implementation lives in Domain 06's string-DP neighborhood *only if* warranted — otherwise this contract (complexity + use-cases + crossover) plus a vetted library suffices; tries here, automata there, borrowed everywhere.

```bash
# GOOD: the generalization ladder, placed (one pattern -> many, with crossovers)
#  one-off search      -> builtins (indexOf, SIMD constants win small)
#  single-pattern scan -> KMP O(n+m) guaranteed (Domain 03 §3.2)
#  multi-pattern scan  -> Aho-Corasick O(n+m+z) (failure links on trie nodes — this leaf's descendant)
#  fuzzy/typo-tolerant -> Levenshtein-on-trie / DP edit distance (Domain 06)
# BAD: regex alternation of 10k signatures ("flexible") —
# backtracking worst cases meet multiplicative patterns; outages wear regex clothes
```

### 4) **Common confusion**

- "Tries waste memory" — tries *compress* shared prefixes (verified 17 < 19 — savings grow with prefix redundancy: dictionaries compress 30–60% typically). Node overhead dominates only past ~10⁵ keys (radix compression answers) or with tiny sharing (random strings — wrong structure, use hashing).
- "Autocomplete needs AI" — prefix descent + frequency ranking answers most autocomplete (deterministic, explainable, sub-millisecond). ML ranks ambiguous intent; tries serve known vocabularies — different problems sharing a text box.
- "Aho-Corasick is just KMP on each pattern" — KMP-per-pattern rescans text per pattern (`O(patterns × n)`); AC scans once (`O(n + m + z)`) via trie-organized failure links. Shared scanning is the entire contribution — "just" undersells the rung change.
- "Character nodes assume ASCII" — `Map`-keyed children handle full Unicode (code-point iteration — leaf's implementation detail, load-bearing for real text). Byte-tries on UTF-8 split characters; char-tries on code points don't.

### 5) **Performance note**

Trie ops cost `O(m)` per word (verified probes single-digit ms at these sizes) with node-per-character memory (17 nodes/5 words verified — overhead per node ~ Map + flag, the dominant cost at scale); autocomplete costs `O(prefix + matches)` (answer-sized, not data-sized — the scaling property); AC costs `O(n+m+z)` (linear in everything — the multi-pattern floor). Optimize node shape first (Map vs array children by alphabet size — dense alphabets array-index, sparse Map), enumeration bounds second (display-count cutoff), failure-link construction third (BFS once, amortized over scans).

### 6) **Mentor note**

Teach sharing with node-counting (19 chars → 17 nodes verified — "where did two characters go?" teaches compression structurally). Drill autocomplete as descent-then-enumerate (miss-fast on `z` first — failure cheapness is half the lesson). Place Aho-Corasick on the ladder explicitly (builtins → KMP → AC → fuzzy — each rung named with its crossover, the map juniors navigate by). Watch for the hash-default ("Map of words, scan per prefix" — fix with per-keystroke latency arithmetic at dictionary scale) and the regex-alternation enthusiast (10k patterns, one regex — fix with backtracking worst-case demo). Review check: Map children (Unicode-safe), end-counts (not flags), enumeration bounded, misses explicit, juniors can place any string workload on the ladder unprompted.
