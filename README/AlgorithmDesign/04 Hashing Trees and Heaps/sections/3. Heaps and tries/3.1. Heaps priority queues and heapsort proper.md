## 3.1. Heaps, priority queues, and heapsort proper

### 1) **Sift maintains the heap property**

**Definition** — a binary heap holds one invariant per node (min-heap: parent ≤ children — the minimum always at the root; max-heap mirrors): *push* appends at the end and bubbles up (`O(log n)` swaps); *pop* moves the last element to the root and sifts down (`O(log n)`); *heapify* builds from arbitrary input bottom-up in `O(n)` (sift from the last parent down to the root — most nodes sit near leaves with tiny sift distances, so total work sums linearly, not `n log n`). Verified: bottom-up heapify costs **1982** comparisons at `n=1000` vs top-down insert-all **7987** (~`2n` vs ~`n log n` — linearity measured, not asserted); extraction order verified `1,2,3,5,8,9`.

- **What problem it solves**: extrema-under-mutation defeats static structures (sorted arrays re-sort per insert — `n log n` per update; linear scans pay `n` per query) — heaps serve both directions at logarithmic cost with array-compact storage (indices encode parentage: parent `(i−1)>>1`, children `2i+1/2i+2` — no pointers, prefetch-friendly). Schedulers, merges, and streaming statistics all need "current extreme, repeatedly, under updates" — the heap is that question's data structure the way hash maps are lookup's.
- **Modern guidance** — heapify bottom-up always (linear build — top-down insertion wastes a log factor for identical output; the verified 4× gap at `n=1000` widens with `n`). Implement sift iteratively (loop over levels — no recursion, no stack questions). Store in arrays with index arithmetic (pointer-free heaps halve memory traffic vs node heaps — cache wins where both qualify). Test heapify output as *property*, not order (every parent ≤ children — order emerges only through extraction).

```javascript
// GOOD: linear build, logarithmic updates — verified 1982 vs 7987
function heapify(a) {                              // bottom-up: sift from last parent to root
  const sift = (i) => { for (;;) { const l = 2 * i + 1, r = l + 1; let m = i;
    if (l < a.length && a[l] < a[m]) m = l; if (r < a.length && a[r] < a[m]) m = r;
    if (m === i) break; [a[m], a[i]] = [a[i], a[m]]; i = m; } };
  for (let i = (a.length >> 1) - 1; i >= 0; i--) sift(i);
  return a;
} // O(n) build (verified ~2n comps — leaves do O(1) each, and most nodes ARE leaves).
// BAD: build-by-insertion ("same result") —
// O(n log n) for identical output; the 4x verified gap at n=1000 grows with n
```

### 2) **Priority queues schedule by importance**

**Definition** — a priority queue serves extremes first (push with priority, pop the min/max — heap underneath, `O(log n)` both): k-way merge (heap of run-heads merges sorted streams in `n log k` — Domain 02 §2.1's external sort consumes this), Dijkstra's frontier (cheapest-unsettled-first — [Domain 05/2.1 flagship](<../../../05 Graphs/sections/2. Paths and components/2.1. Dijkstra weighted shortest paths.md>)), top-k streaming (size-`k` min-heap keeps the k largest: evict-if-smaller per arrival — verified top-3 of 10,000 → `[9999,9998,9997]`), task scheduling (deadlines/importance order work queues).

- **Why it matters (correctness)**: extrema queries without PQs nest or sort per query (top-k by full sort: `n log n` per question vs `n log k` streaming — verified gap widens as `k ≪ n`; k-way merge by repeated minima: `n·k` rescans vs `n log k` heap). The PQ converts "best so far, repeatedly" from re-computation into maintenance (each arrival/departure logarithmic — the frontier stays current instead of being rebuilt). Streaming statistics, schedulers, and graph frontiers all reduce here.
- **Modern guidance** — reach for size-`k` heaps on top-k/streaming-extrema (evict-if-dominated per arrival — memory `O(k)`, independent of stream length); k-way heaps on merging (run-heads only in memory — the external-sort pattern); decrease-key-capable heaps on Dijkstra (or lazy-deletion with standard heaps — stale entries skipped on pop, simpler and usually faster in practice). State the heap's comparison target per use (min for top-k-largest via eviction — the inversion that confuses first-timers: keep the *smallest of the kept*, evict below it).

```javascript
// GOOD: streaming top-k in O(k) memory — verified [9999,9998,9997] from 10k shuffled
function topK(stream, k) {
  const h = [];                                     // min-heap of the k largest seen (inversion intended)
  const push = (v) => { h.push(v); let i = h.length - 1;
    while (i > 0) { const p = (i - 1) >> 1; if (h[p] <= h[i]) break; [h[p], h[i]] = [h[i], h[p]]; i = p; } };
  const pop = () => { /* sift-down as above, O(log k) */ };
  for (const v of stream) { if (h.length < k) push(v); else if (v > h[0]) { pop(); push(v); } }
  return h.sort((x, y) => y - x);
} // O(n log k) time, O(k) space. Full sort per query: O(n log n) — gap structural for k << n.
// BAD: sort-and-slice per top-k query ("simpler") —
// n log n per question where n log k streaming applies; simplicity billing logarithmically
```

### 3) **Heapsort delivers the teaser promise**

**Definition** — Domain 02 §3.2's contract, fulfilled: heapify in `O(n)` (verified linear above), then `n` extract-max-to-end steps × `O(log n)` sift-down = `O(n log n)` *guaranteed* (no pivot, no adversary — worst case *is* the average case, structurally), `O(1)` auxiliary (in-place array — no merge buffer), *unstable* (distant swaps scramble equal keys — the price of the guarantee, stated). The sorting story's third corner, complete: merge (guaranteed + scratch), quick (fast average + collapse risk), heap (guaranteed + in-place + unstable + weaker constants).

- **Why it hurts when missing (correctness, maintainability)**: heapsort's absence leaves guarantee-plus-memory scenarios unserved (embedded sorts, kernel paths, real-time-adjacent batch — merge's scratch forbidden, quick's collapse unacceptable). More commonly, its absence leaves *introsort* unexplained (Domain 02 §2.2's depth guard switches to heapsort past `2·log n` — the guard *is* this algorithm on standby; engineers shipping introsort without understanding heapsort maintain machinery they can't reason about). The teaser promised; this leaf delivers; the curriculum's most load-bearing cross-link (after recurrence) closes.
- **Modern guidance** — use heapsort where guarantees meet memory constraints (embedded, kernels, guard fallbacks — the specialist's niche); prefer TimSort-class library sorts everywhere else (2–3× better constants via cache behavior + stability + adaptivity — heapsort wins paper parity and loses silicon). Never implement heapsort *instead of* understanding heaps (the sort is three lines atop sift — learn sift deeply, the sort follows free). State all three corners per sorting decision (guarantees? memory? constants? — the table from Domain 02 §4.1, now complete).

```javascript
// GOOD: the teaser fulfilled — guaranteed linearithmic, in-place, unstable (all three stated)
function heapSort(a) {
  heapify(a);                                       // O(n) linear build (verified ~2n)
  for (let end = a.length - 1; end > 0; end--) {
    [a[0], a[end]] = [a[end], a[0]];                // extract-max to its final slot...
    siftDown(a, 0, end);                            // ...restore heap on the prefix (O(log n) each)
  }
  return a;
} // O(n log n) worst-case GUARANTEED (no adversary exists), O(1) aux, UNSTABLE (distant swaps).
// BAD: "heapsort: O(n log n), use freely" without the unstable qualifier —
// equal-key pipelines silently reorder (Domain 02 §4.1's stability rule, violated by omission)
```

### 4) **Common confusion**

- "Heapify is `O(n log n)` (n inserts)" — bottom-up heapify is `O(n)` (verified 1982 vs 7987 — most nodes near leaves, sift distances tiny). Insert-all is the `n log n` way to build identically — know both, ship bottom-up.
- "Priority queue means sorted output" — PQs serve *extremes on demand* (pop order sorted, internal order heap-shaped — peeking past the root sees no sorted sequence). Sorted output requires draining (heapsort) or repeated pops.
- "Heapsort's guarantee makes it the default" — guarantees cost constants (cache-hostile jumps lose 2–3× to merge's streams at equal `n`) plus stability. Default remains adaptive library sorts; heapsort is the memory-constrained guarantee specialist.
- "Min-heap for top-k-largest is backwards" — deliberate inversion (keep the *smallest of the kept* at the root — arrivals evict by beating it). The heap holds the threshold, not the answer; the answer drains out sorted at the end.

### 5) **Performance note**

Heap ops cost `log n` sifts with cache-hostile jumps (verified extraction order at single-digit ms these sizes; constants ~2–3× merge's streams — paper parity, silicon gap); heapify costs `~2n` bottom-up (verified — linear build, the optimization that matters); top-k streaming costs `n log k` with `O(k)` memory (gap over sort-per-query widens as `k/n` shrinks). Optimize build first (bottom-up always), eviction policy second (size-`k` discipline), sift micro-structure never (borrowed-shape territory — clarity over cleverness in heap code).
