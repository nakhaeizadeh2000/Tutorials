## 2.2. Traversals: inorder, pre, post, and level

### 1) **Depth-first spells three ways**

**Definition** — one recursion, three readings by *when* the node is visited: preorder (node → left → right — structure-preserving: copy/serialize trees), inorder (left → node → right — emits BST content sorted), postorder (left → right → node — children before parents: evaluate expressions, free subtrees, compute heights). Verified on the fixed 7-node tree: pre `4,2,1,3,6,5,7`; in `1,2,3,4,5,6,7`; post `1,3,2,5,7,6,4` — same walk, three projections; inorder sorted *because* the tree is a BST (leaf 2.1's invariant read out), not because traversal sorts.

- **What problem it solves**: tree questions reduce to visit-order choice — serialize (preorder + null markers reconstructs exactly), evaluate (postorder computes children first — expression trees, directory sizes, DP-on-trees in Domain 06), audit sortedness (inorder must emit ascending — the one-line BST validator for honest trees). Wrong order gives wrong answers structurally (preorder "sorted" output isn't; postorder deletion frees parents first — use-after-free wearing traversal clothes). Order selection *is* the algorithm here; the walk is incidental.
- **Modern guidance** — choose by consumer (serialize → pre; evaluate/bottom-up → post; sorted-emit → in on BSTs), state the choice with the reason ("postorder: sizes need children first"), and test on the fixed 7-node tree (memorize the three verified strings — any implementation must reproduce all three). For serialization, include null markers (bare preorder values don't reconstruct uniquely — two trees, one preorder; markers disambiguate).

```javascript
// GOOD: one walk, three projections — verified strings as test oracle
function walk(n, pre = [], ino = [], post = []) {
  if (!n) return;
  pre.push(n.v); walk(n.l, pre, ino, post); ino.push(n.v); walk(n.r, pre, ino, post); post.push(n.v);
} // pre 4,2,1,3,6,5,7 | in 1,2,3,4,5,6,7 | post 1,3,2,5,7,6,4 (verified — oracle for any reimplementation).
// BAD: "traverse and collect" without order semantics ("DFS output") —
// which DFS? Three exist; the consumer decides, and unstated order is a latent bug
```

### 2) **Breadth-first needs a queue**

**Definition** — level order visits by depth (root, then its children, then theirs — verified `4,2,6,1,3,5,7`): the only traversal a stack can't produce, because depth-first machinery dives where breadth waits. Implementation is Domain 03 §3.1's FIFO discipline applied to nodes (enqueue children, dequeue current — the queue *is* the waiting room of each level). Cost: `O(n)` time, `O(w)` space where `w` is max width (the frontier held simultaneously — up to `n/2` on full trees, the space price of level thinking).

- **Why it matters (correctness)**: shortest-path-on-unweighted-graphs *is* BFS ([Domain 05/1.1](<../../../05 Graphs/sections/1. Traversal/1.1. BFS levels with shortest-hop guarantees.md>) — first visit is shortest by level construction), level-averages/zigzag/right-side-views are BFS-shaped interviews, and serialization-by-level powers heap array layouts (next leaf — heap indices *are* level order). DFS-substituted "level" code (depth tracking + bucketing) works but wastes the queue's natural fit — and depth-keyed buckets misorder where FIFO can't. Structure matches algorithm (Domain 03 §3.1's design rule, restated for trees because BFS is its flagship).
- **Modern guidance** — reach for level order on depth-shaped questions (levels, views, shortest-hops, completeness checks — complete-binary-tree validation is a BFS with null-accounting). Size the queue honesty (`O(w)` — full-tree width halves memory assumptions; streaming levels via length-snapshots keeps per-level processing clean). Never recurse "by depth" for true BFS (depth-parameter DFS visits depth-first regardless of parameter name — the call stack is LIFO, and LIFO can't wait).

```javascript
// GOOD: FIFO levels — verified 4,2,6,1,3,5,7
function levelOrder(root) {
  if (!root) return [];
  const out = [], q = [root];               // queue: the waiting room of each level (Domain 03 §3.1)
  while (q.length) {
    const lvl = [];
    for (let i = q.length; i > 0; i--) {    // snapshot: exactly this level, no more
      const n = q.shift();
      lvl.push(n.v);
      if (n.l) q.push(n.l); if (n.r) q.push(n.r);
    }
    out.push(lvl);
  }
  return out;
} // O(n) time, O(w) space (frontier width). Length-snapshot per level — no depth parameter anywhere.
// BAD: DFS-with-depth pushing into level buckets "as BFS" —
// visits depth-first (order wrong for streaming/shortest uses); buckets hide the mismatch until it matters
```

### 3) **Iterative twins bound the stack**

**Definition** — every recursive traversal has an explicit-stack twin trading call-stack depth for heap-managed state: iterative inorder (push-left spine, pop-visit-go-right — verified identical `1,2,3,4,5,6,7`), iterative pre/post (push-based with visit-markers or reversed tricks), Morris traversal (`O(1)` space via temporary threading — expert territory, mutates-then-restores). The trade: recursion reads as structure (code mirrors tree — reviewable), iteration survives depth (no `RangeError` past ~13,920 frames — Domain 01 §2.2's ceiling binds degenerate trees exactly).

- **Why it hurts when missing (correctness, maintainability)**: recursive traversals on degenerate trees crash (depth-`n` descent — leaf 2.1's sorted-10 chain is harmless, sorted-100k is a `RangeError` in production), and the crash arrives on the largest inputs (where depth is deepest — testing never reaches). Iterative twins cost modest complexity (spine management, visit markers) for structural immunity (heap grows to gigabytes; call stack doesn't). Depth is the input nobody controls (user-fed insertion orders — leaf 1.1's threat model again).
- **Modern guidance** — recurse for clarity where depth is bounded (balanced trees, small inputs, interviews screening recursion); iterate where depth is open (user-ordered inserts, degenerate-capable structures, production traversals). Implement iterative inorder fluently (the spine loop above — five lines, the price of admission); know Morris exists without defaulting to it (threading mutates during traversal — `O(1)` space bought with reentrancy hazards; borrow, don't invent). State the choice per traversal ("recursive: depth ≤ 60 by balancing guarantee" — the bound that justifies clarity).

```javascript
// GOOD: spine-managed inorder — verified identical output, zero call-stack risk
function inorderIter(root) {
  const out = [], st = []; let c = root;
  while (c || st.length) {
    while (c) { st.push(c); c = c.l; }  // descend the left spine (heap-held, not call-held)
    c = st.pop(); out.push(c.v); c = c.r;
  }
  return out;  // 1,2,3,4,5,6,7 verified — same as recursive, immune to depth.
} // O(n) time, O(h) heap space (spine, visible) vs O(h) call stack (invisible, finite).
// BAD: "recursion is fine, trees are balanced" as an unstated assumption —
// balance hoped (leaf 2.1), depth unbounded, RangeError scheduled by input order
```

### 4) **Common confusion**

- "Inorder sorts" — inorder *emits BST order* (verified sorted because the tree holds the invariant — leaf 2.1); on arbitrary binary trees inorder emits whatever arrangement exists. Traversal reads structure; it doesn't create order.
- "BFS and DFS differ only in order" — they differ in *guarantees* (BFS first-visit-is-shortest on unweighted graphs — [Domain 05/1.1](<../../../05 Graphs/sections/1. Traversal/1.1. BFS levels with shortest-hop guarantees.md>); DFS reaches deep fast with `O(h)` space). Order is the visible difference; guarantees are the load-bearing one.
- "Iterative is always better" — iterative bounds stack risk at clarity cost (spine loops, visit markers). Better *where depth is open*; worse where bounded depth makes recursion the clearer proof. Match to depth risk, not dogma.
- "Morris traversal is the optimal answer" — optimal *space* (`O(1)`), with mutation-during-traversal hazards (threading/unthreading races under concurrency, reentrancy). Optimality in one axis, liability in others — state the trade, don't chant the name.

### 5) **Performance note**

Traversals cost `n` visits each (verified strings cost microseconds at 7 nodes — linear scaling, constant ~pointer-hops) with space by flavor (recursive `O(h)` call stack; iterative `O(h)` heap spine; BFS `O(w)` frontier; Morris `O(1)` threaded). Double-traversal patterns (validate-then-process) cost `2n` — fine; traversal-per-query patterns (repeated full walks for point questions) cost `n` × queries — augment the structure instead (parent pointers, subtree sizes — Domains [05](<../../../05 Graphs/README.md>)/06 contexts). Optimize visit-count first (one pass, both answers — collect pre+in+post together as the verified probe does), stack-vs-heap second (depth risk decides).

### 6) **Mentor note**

Memorize-via-derivation: one recursion, visit-position determines flavor (node-left-right permutations of three slots — pre/in/post fall out of slot order, no separate memorization). Drill the fixed-tree oracle (three verified strings — implementations prove themselves against it). Teach BFS as FIFO-applied (Domain 03 §3.1 deja vu deliberately invoked — "same discipline, new citizens"). Convert recursion-to-iteration live once (spine loop written beside the recursive twin — the five-line gap demystifies). Watch for the order-blind ("DFS output" — fix with "which of the three, and what consumes it?") and the depth-hopeful ("balanced, surely" — fix with degenerate-depth probe on the spot). Review check: traversal chosen by consumer, oracle strings green, depth risk stated (recursive bound or iterative twin), juniors can emit all three orders from one walk.
