## 2.1. Binary search trees: ordered maps with a shadow

### 1) **Invariant orders everything**

**Definition** — a BST holds one invariant at every node: left subtree `< node ≤` right subtree (duplicates policy stated: right, counted, or rejected — pick one, document it). Search/insert/delete all *descend* comparing once per level: `O(h)` where `h` is height — logarithmic on balanced trees, linear on degenerate ones (next section). Inorder traversal emits sorted order — verified: shuffled insert of 1–10 reads back `1,2,…,10` exactly. The invariant is the structure; everything else is descent with different endings.

- **What problem it solves**: ordered maps need *both* key lookup and order statistics (predecessor/successor, range queries, sorted iteration, k-th smallest) — hash maps answer lookup in `O(1)` average but know nothing of order (leaf 1.1's boundary: unordered power). BSTs trade constant lookup for logarithmic order: min/max in `O(h)`, successor without full scans, ranges by bounded traversal. Sorted arrays answer order statically; BSTs answer it *dynamically* (inserts/deletes interleaved with queries — the workload arrays can't serve).
- **Modern guidance** — reach for BST-shaped structures on dynamic ordered workloads (leaderboards with rank queries, interval sets, sweep-line status structures — Domain 06's geometry). In JavaScript, borrow ordering (sorted arrays + binary search for static data — Domain 02 §3.1; `Map` + explicit sort keys where dynamics are light). Implement BSTs for interviews and understanding (descent logic is the transferable skill); ship library balanced trees (next section's deferral — hand-rolled rebalancing is a bug farm with a rotating schedule).

```javascript
// GOOD: descent with an invariant — verified inorder 1..10 from shuffled insert
function bstInsert(nd, v) {
  if (!nd) return { v, l: null, r: null };
  if (v < nd.v) nd.l = bstInsert(nd.l, v);   // left: strictly smaller (invariant, left half)
  else nd.r = bstInsert(nd.r, v);            // right: greater-or-equal (duplicates policy: right)
  return nd;
} // O(h) per op: O(log n) balanced, O(n) degenerate (next section prices the shadow).
// BAD: BST without a stated duplicate policy ("goes right, I think") —
// search/delete/inorder assume possibly different policies; unstated invariants diverge by author
```

### 2) **Degenerate input builds a list**

**Definition** — sorted insertion defeats the invariant's purpose without violating it: each new maximum descends to the deepest right leaf — height `n`, every operation `O(n)`. Verified: sorted 1–10 → depth **10** (a linked list wearing tree syntax) vs shuffled → depth **4** (logarithmic-ish). Same code, same invariant, two rungs apart — input order decides, and sorted input is the *common* case (timestamps, IDs, logs arrive ordered) plus the *adversarial* case (complexity-DoS via sorted feeds — leaf 1.1's threat model, wearing bark).

- **Why it matters (correctness)**: degenerate BSTs fail exactly like quicksort's pivot collapse (Domain 02 §2.2 — same shape, different structure: no splitting vs no branching), and for the same reason (ordered input meets position-naive choices). The failure compounds: `O(n)` descent per op × `n` ops = `O(n²)` workloads, plus recursion depth `n` threatening the stack (Domain 01 §2.2's ~13,920 ceiling — degenerate trees reach it around 14k sorted inserts, a Tuesday-sized feed). Unbalanced BSTs are linked lists with extra steps and extra risk.
- **Modern guidance** — never ship unbalanced BSTs on untrusted-order input (shuffle first, or balance structurally — next section). Test with sorted input always (the degenerate probe: depth must stay logarithmic — verified 4, not 10). Prefer iterative descent in production hand-rolls (loop over levels — no stack liability at any depth). Treat "BST" in design docs as meaning *balanced* BST unless degenerate is explicitly accepted (and priced) — the unqualified name oversells the naive structure.

```javascript
// GOOD: deletion by successor-splice — verified order preserved (2,3,4,6,7,8,9,10 after removing 5,1)
function bstDelete(nd, v) {
  if (!nd) return null;
  if (v < nd.v) nd.l = bstDelete(nd.l, v);
  else if (v > nd.v) nd.r = bstDelete(nd.r, v);
  else {  // found: three cases, one idea (preserve invariant with surviving subtree)
    if (!nd.l) return nd.r; if (!nd.r) return nd.l;   // 0-1 children: splice survivor up
    let s = nd.r; while (s.l) s = s.l;                // two children: inorder successor...
    nd.v = s.v; nd.r = bstDelete(nd.r, s.v);          // ...copies up, original spliced out
  }
  return nd;
}
// BAD: deletion by "rebuild the subtree" or value-blanking (tombstones in BSTs) —
// rebuilds bill O(subtree) per delete; tombstones rot the invariant queries depend on
```

### 3) **Balance is a separate structure**

**Definition** — self-balancing trees (AVL: height-difference ≤ 1, rotations on violation; red-black: color invariants bounding longest path ≤ 2× shortest — height `O(log n)` guaranteed) convert the degenerate hope into a structural promise: *every* operation `O(log n)` worst-case, on *every* input order. The mechanics (rotations, recoloring, deletion fixups — dozens of cases) are famously intricate: correct implementations take experts weeks, and the bug surface (rotation direction, double-rotation order, delete-fixup cases) punishes part-time implementers.

- **Why it hurts when missing (correctness, maintainability)**: hand-rolled "balanced" trees fail partially — rotations correct on insertion paths but broken on deletion fixups (the rarer, harder cases), passing tests for months before corrupting on the untested case (silent invariant violation: queries return wrong answers, not errors — the worst failure shape). Meanwhile library balanced trees (one import, decades of verification, measured constants) sit unused beside the custom code. The build-vs-borrow calculus here is the most lopsided in data structures: borrow, always, in production.
- **Modern guidance** — state the guarantee, borrow the code ("ordered map, `O(log n)` worst-case via red-black library" — the design-doc sentence; the import beside it). Implement AVL/red-black *once*, for learning (rotations understood beats rotations memorized — draw, don't recite), then never again in production. In JavaScript specifically: no stdlib ordered map exists — use sorted-array + binary search (static/small), `Map` + lazy sort (light dynamics), or a vetted library (functional red-black packages — pinned, tested) for serious ordered dynamics. Document which, with the input-order reasoning that chose it.

```bash
# GOOD: guarantee stated, code borrowed (design-doc discipline)
#  "Leaderboard ranks: ordered map, O(log n) worst-case (red-black lib X vPinned).
#   Degenerate risk: none (structural guarantee, not input hope). Verified: depth 4-shape on shuffled 10."
# BAD: hand-rolled AVL in production ("no dependency") —
# deletion fixups untested, rotations half-remembered; the dependency saved is dwarfed by the corruption risk
```

### 4) **Common confusion**

- "BSTs are `O(log n)`" — *balanced* BSTs are `O(log n)`; naive BSTs are `O(h)` with `h` ranging `log n` (lucky) to `n` (sorted — verified 10). The qualifier is the analysis (same honesty leaf 1.1 demands for hashing).
- "Inorder traversal sorts" — inorder *emits BST content* in sorted order (verified 1..10); the sort already happened at insertion (each descent placed the key). Traversal reads order, it doesn't create it.
- "Duplicates break BSTs" — duplicates break *unstated policies* (search finds one, delete removes which?, inorder shows runs — all fine once the policy `≤`-right-or-count is declared). Policy first, code second.
- "Balanced trees are overkill; inputs are random" — inputs are *timestamped* (sorted), *user-fed* (adversarial-capable), and *growing* (today's random is tomorrow's pattern). Randomness is not a structural guarantee — rotations are.

### 5) **Performance note**

BST ops cost `h` comparisons (verified depth 10 degenerate vs 4 shuffled at `n=10` — order-of-magnitude divergence at toy sizes, widening with `n`); deletion costs one descent + successor walk (same `O(h)` envelope — no hidden factors); inorder costs `n` visits + `O(h)` stack (recursive) or `O(1)` aux iterative with threading/trade-offs (next leaf). Balanced variants add rotation overhead per update (constant small — a few pointer writes amortized across descents). Optimize structure choice first (balanced-vs-naive decides the rung), duplicate policy second (search/delete semantics), rotation tuning never (borrowed code territory).

### 6) **Mentor note**

Demonstrate degeneracy live (sorted-10 → depth-10 chain drawn beside shuffled-10 → depth-4 tree — "same code, same invariant, two rungs" converts input-order from footnote to design input). Drill deletion's three cases by hand (0/1/2 children — successor-splice traced on paper before coded). Teach balance as borrow-discipline ("implement once to learn, import forever to ship" — the rare topic where learning and shipping diverge openly). Watch for the rung-quoter ("BSTs are log n" — fix with sorted-input depth probe on the spot) and the hand-roller ("no dependency" AVL — fix with deletion-fixup quiz: "state all four cases"). Review check: duplicate policy declared, degenerate tested (sorted input in the matrix), balance borrowed (library named, pinned), juniors can trace descent/inorder/deletion aloud.
