## 1.2. Prefix sums and frequency patterns

### 1) **Prefix maps answer range queries**

**Definition** — prefix sums turn range questions into key lookups: store running totals (`prefix[i]` = sum of `a[0..i)`), then any range sum is a subtraction (`sum(l..r) = prefix[r+1] − prefix[l]`, `O(1)` per query after `O(n)` preprocessing). For *counting* subarrays with sum K: store prefix *frequencies* — each new prefix `s` asks "how many earlier prefixes equal `s−K`?" (each such prefix starts a valid subarray ending here). Verified: `[3,4,−7,1,3,3,1,−4]`, K=7 → **4** subarrays — one pass, no enumeration, including negatives where sliding windows can't go (Domain 03 §2.2's admission rule, routed here).

- **What problem it solves**: range/subarray questions without prefix thinking nest (all `O(n²)` ranges enumerated) or window where windows don't apply (negatives break monotonicity — the silent-wrong-answer trap from Domain 03 §2.2). Prefix maps convert the range into a *lookup*: past running totals remembered, present total queried — the map-first reflex (leaf 1.1) specialized to cumulative state. One pass builds, `O(1)` reads, negatives welcome.
- **Modern guidance** — reach for prefix maps on subarray-sum/count/shortest-with-sum questions (exact-K counting, zero-sum detection — `s−K = s` means `K = 0` falls out free, divisible-by-K via remainders). Seed `prefix[0] = 1` (empty prefix counts — subarrays *starting* at index 0 exist; unseeded maps undercount by exactly those). Distinguish sums (prefix arithmetic) from extrema (prefix *minima* for max-subarray variants — Kadane's territory, the greedy cousin in [Domain 06/3.1](<../../../06 Dynamic Programming Greedy and Backtracking/sections/3. Greedy and backtracking/3.1. Greedy choices and exchange arguments.md>)). State which: sum-lookup vs min-tracking — different maps, different questions.

```javascript
// GOOD: ranges as lookups — verified count 4 (negatives included, windows excluded)
function countSubarraysSumK(a, k) {
  const pref = new Map([[0, 1]]);   // seed: empty prefix (subarrays starting at 0 count!)
  let s = 0, n = 0;
  for (const x of a) {
    s += x;
    n += pref.get(s - k) || 0;      // earlier prefixes starting a valid subarray ending here
    pref.set(s, (pref.get(s) || 0) + 1);
  }
  return n;
} // countSubarraysSumK([3,4,-7,1,3,3,1,-4], 7) = 4 verified. O(n) time average, O(n) space.
// BAD: sliding windows on exact-sum-with-negatives ("O(n) either way") —
// windows assume monotonic sums (Domain 03 §2.2 admission); prefix maps assume nothing
```

### 2) **Frequency tables classify**

**Definition** — counting *is* a technique: build key→count once (`O(n)`), answer classification questions in follow-up passes — anagrams (sorted-word keys group: verified `[eat,tea,ate]/[tan,nat]/[bat]`), first-unique (count pass + order pass — verified indices 0 and 2), top-k-frequent (count + bucket-by-frequency: `O(n)` without sorting), duplicates/majority (Boyer-Moore voting for strict-majority in `O(1)` space — the count that cancels itself). Two passes max, zero nesting — the nested alternative (`O(n²)` pairwise comparison) is the tax ignorance pays.

- **Why it matters (correctness)**: classification without counting re-derives per query (is-anagram by sorting both strings per pair — `O(k log k)` × pairs; first-unique by `indexOf`/`lastIndexOf` per character — quadratic wearing helpers). Frequency tables separate *measurement* (one counting pass) from *judgment* (read the table): each question becomes table arithmetic. The pattern generalizes to streaming (approximate counters — Count-Min sketches trade exactness for memory where streams never end).
- **Modern guidance** — count first on classification questions (anagram? unique? majority? top-k? — the table answers all four from one pass). Choose key wisely (sorted-word for anagrams — `O(k log k)` per word once; char-count tuples where alphabet is tiny and words long). For top-k, bucket by frequency (`O(n)` — index by count, collect from the top) instead of sorting entries (`n log n` — paying order where rank suffices). State space honestly (`O(alphabet)` or `O(distinct)` — bounded by input diversity, not input size).

```javascript
// GOOD: measure once (count), judge often (read the table) — verified groupings + indices
function groupAnagrams(ws) {
  const m = new Map();
  for (const w of ws) { const k = [...w].sort().join("");
    if (!m.has(k)) m.set(k, []); m.get(k).push(w); }
  return [...m.values()];
} // [["eat","tea","ate"],["tan","nat"],["bat"]] verified. O(N*K log K) time, O(N*K) space.
// firstUnique("leetcode") = 0, ("loveleetcode") = 2 verified (count pass + order pass).
// BAD: pairwise anagram checks ("no extra space") —
// O(words^2) comparisons to save one table; classification without counting is enumeration
```

### 3) **Hashing trades space for passes**

**Definition** — the transaction restated for this leaf's patterns (Domain 01 §2.2's trade, specialized): prefix maps spend `O(n)` table to collapse `O(n²)` enumeration into one pass; frequency tables spend `O(distinct)` to collapse repeated classification into lookups; complement maps (leaf 1.1's two-sum) spend `O(n)` to collapse pairing into streaming. Deliberate when the table is bounded (prefixes ≤ `n`, frequencies ≤ alphabet-or-distinct — priced up front); dangerous when cardinality is open (user-keyed caches without eviction — Domain 01 §2.2's incident shape, restated because it recurs).

- **Why it hurts when missing (correctness, maintainability)**: unbudgeted tables are the top memory-incident shape in application code (session caches keyed by user, memo maps keyed by request, frequency tables over unbounded streams — each grows with input cardinality until the heap gives). The fix is never "less hashing" (the passes saved are real) — it's *bounded* hashing (eviction at birth: LRU caps, TTLs, weak keys — the policy travels with the table's creation commit). Time-bought-with-memory without a memory budget is the loan from Domain 01 §2.2 restated for maps.
- **Modern guidance** — write the space bound beside every table (`O(n)` prefixes, `O(distinct)` frequencies — stated, reviewed). Cap tables over open cardinality at creation (size bound, TTL, or weak references — unbounded is a bug filed against the future). Revisit at 10× input growth (the table that fit at 10⁴ rows OOMs at 10⁷ — trades expire with scale, Domain 01 §2.2's expiry clause). The expert habit, repeated until reflexive: every `new Map()` used as storage gets its bound or eviction in the same commit.

```bash
# GOOD: the trade budgeted per pattern (space beside time, bounds beside creation)
#  prefix-sum-K: O(n) table  x O(n) single pass  (enumeration O(n^2) avoided; table bounded by n)
#  frequencies:  O(distinct) x O(n) two passes    (nesting O(n^2) avoided; bounded by alphabet/distinct)
#  complements:  O(n) seen    x O(n) streaming    (pairing O(n^2) avoided; dropped when pass ends)
# BAD: unbounded frequency tables over streams ("just counting") —
# cardinality-open counting is a memory incident with a head start; bound at birth
```

### 4) **Common confusion**

- "Prefix sums need extra arrays" — the *map* replaces the array where lookups are by value (sum-K counting); plain prefix *arrays* serve positional range-sum queries. Structure follows question (value-lookup → map; position-lookup → array).
- "Frequency counting is `O(n)` space always" — `O(distinct)`: alphabet-bounded for chars (constant-ish), input-bounded for arbitrary keys. The bound that matters is diversity, not length.
- "Two-sum needs sorting first" — sorted two-sum converges (Domain 03 §1.1); *unsorted* two-sum hashes (leaf 1.1) — sorting an unsorted instance to converge costs `n log n` where hashing costs `n`. Structure present decides; structure absent gets built cheapest.
- "Hashing removes all nesting" — hashing removes *enumerative* nesting (pairs, ranges, groups); recursive/structural nesting (trees, DP) answers to other techniques (Domains 04–06). Maps collapse lookups, not all complexity.

### 5) **Performance note**

Prefix passes cost `n` inserts + `n` lookups (verified count-4 probe runs single-digit ms at these sizes) with `O(n)` table (prefixes distinct up to `n` — worst-case memory equals input size, the honest price). Frequency passes cost `2n` map ops with `O(distinct)` table (alphabet-capped for chars — constant-ish in practice). Enumeration alternatives cost `n²` ranges (the gap widens with `n` — tables win *more* where naivety costs most). Optimize table choice first (Map vs object vs typed array by key shape), eviction second (open cardinality), hash quality third (engine default suffices — leaf 1.1).

### 6) **Mentor note**

Teach prefix maps as "windows where windows can't go" (negatives welcome — the admission contrast with Domain 03 §2.2 teaches both techniques at once). Drill frequency-first on classification ("count, then judge" — anagrams/first-unique/top-k from one table). Demand space bounds beside every table ("bounded by what?" — unbounded answers get eviction policies before merge). Watch for the enumerator ("thorough" `O(n²)` ranges — fix with the count-4 probe as evidence) and the unbounded-counter ("just counting" streams — fix with cardinality arithmetic on their own inputs). Review check: seed lines present (`[0,1]`), validity/edge cases covered (empty, impossible, negatives), tables bounded, juniors can derive sum-K from scratch given only "remember past totals."
