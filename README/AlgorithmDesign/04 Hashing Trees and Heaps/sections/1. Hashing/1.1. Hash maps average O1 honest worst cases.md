## 1.1. Hash maps: average `O(1)`, honest worst cases

### 1) **Hash, probe, resize**

**Definition** — a hash map spreads keys across buckets by hash (`bucket = h(key) mod capacity`), resolves collisions by chaining (linked overflow per bucket) or open addressing (probe for the next free slot), and *resizes* (doubles capacity, rehashes everything) when load factor (`n / capacity`) passes ~0.7–0.75. Resizing is the amortization story from Domain 01 §2.1 wearing structure clothes: occasional `O(n)` rehash prepaid by many `O(1)` inserts — verified shape identical to dynamic-array doubling (copies per insert bounded by a constant).

- **What problem it solves**: keyed lookup without hashing is a ladder demotion — linear scan (`O(n)` per query), tree descent (`O(log n)`), or pre-sorting (`n log n` admission per dataset). Hashing buys *average* constant lookup/insert/delete with zero ordering requirements: complements, groupings, caches, indexes — the highest-leverage `O(1)` in working code. The "average" qualifier is load-bearing (next section); the machinery is what earns it on honest inputs.
- **Modern guidance** — default to `Map` for keyed work in JavaScript (preserves insertion order, any key type — [JavaScript 09 mechanics](<../../../../JavaScript/09 Collections Map Set and Weak References/README.md>), linked never re-taught); plain objects only for string-keyed records (prototype chain and key-stringification are footguns wearing convenience). Size initial capacity when known (`new Map(iterable)` in one shot beats incremental growth past resize thresholds). Never implement production hashing by hand (collision discipline + resize tuning + hash quality — borrowed from engines, not reinvented).

```javascript
// GOOD: keyed work at average-constant cost — the workhorse pattern
function twoSumUnsorted(a, t) {
  const seen = new Map();                        // complements remembered: value -> index
  for (let i = 0; i < a.length; i++) {
    if (seen.has(t - a[i])) return [seen.get(t - a[i]), i];
    seen.set(a[i], i);
  }
  return null;
} // twoSumUnsorted([11, 2, 15, 7, 4], 15) -> [0,4] verified (11 + 4). O(n) time average, O(n) space.
// BAD: nested loops "to avoid the extra space" on keyed lookups —
// O(n^2) time to save O(n) space is the trade backwards (Domain 01 §2.2: budget both sides)
```

### 2) **Collisions degrade adversarially**

**Definition** — all keys landing in one bucket turns the map into a linked list: lookup degrades to `O(n)` chain-walking. Verified with a bucket model (10,000 keys, 1024 buckets): uniform Fibonacci hashing → max chain **10** (average ~9.8 — Poisson-tight, lookups effectively constant); degenerate constant hash → max chain **10,000** (every key in bucket 7 — lookup is a full scan). Same structure, same API, different hash behavior: two complexity rungs apart. Real engines mitigate (V8 transitions collision-heavy objects, Java treeifies chains past 8) — mitigations bound the damage, they don't restore `O(1)`.

- **Why it matters (correctness)**: adversarial hashing is a *security* boundary, not a theory footnote — HashDoS (crafted keys colliding under weak hashes) turns every hash-dependent endpoint quadratic (2003 Perl, 2011‑12 web frameworks — outages from colliding POST keys). The threat model decides the rung: trusted integer keys → average holds, budget `O(1)`; user-controlled strings undermultirow naive hashing → budget the worst case or harden (randomized seeds per process — SipHash in modern runtimes — make crafted collisions unplannable). Average-case analysis *is* a threat model wearing mathematics (Domain 01 §1.2).
- **Modern guidance** — state the distribution with every average claim ("`O(1)` average over non-adversarial keys" — falsifiable, reviewable). Rely on engine hashing for strings (seeded, hardened — don't reimplement). For untrusted keys at scale, verify empirically (benchmark with adversarial-ish inputs, not just uniform — Domain 01 §3.1's workload honesty). Never build security decisions on average-case hashing ("attacker can't find collisions" — they read the same papers; randomized seeds are the defense, assumptions aren't).

```javascript
// GOOD: the two rungs, measured on one model (10k keys, 1024 buckets — verified)
// uniform hash  -> max chain 10  (lookups ~constant: the engineered case)
// constant hash -> max chain 10000 (lookups scan: the adversarial case, HashDoS shape)
// Same Map API both times — the rung lives in the hash behavior, not the interface.
// BAD: "`O(1)` lookup" quoted without distribution —
// against crafted keys the average is whatever the adversary bills you (Domain 01 §1.2, applied)
```

### 3) **Maps model relationships**

**Definition** — beyond lookup, maps *relate*: complements (two-sum — seen-pairs), groupings (anagrams by sorted-key, users by cohort), frequency tables (next leaf's counting), memo caches (Domain 01 §2.2's fib table — keys are subproblem identities), and indexes (id → record — the database inside your process). The unifying shape: one pass builds the relation (`O(n)` inserts), subsequent queries read it (`O(1)` average each) — preprocessing amortized over queries, same economics as sorting-once-query-often (Domain 02) with better constants and no ordering requirement.

- **Why it hurts when missing (correctness, maintainability)**: relation-shaped problems solved without maps nest instead — group-by via nested scan (`O(n²)` grouping), dedup via `includes` loops (leaf: Domain 03 §1.1's warning, repeated at structure level), complement search via pairs (verified `n²/2` triangle, Domain 01 §2.1). Each passes small tests (constants forgive) and bills at production sizes. The map-first reflex ("can a single pass with remembered state answer this?") converts an entire interview/problem family from nested to linear.
- **Modern guidance** — ask "what would I remember per element?" for every multi-pass-looking problem (complements, groups, counts, seen-sets — the remembered state *is* the map's content). Prefer `Map` over objects for non-string keys and iteration order (insertion-ordered entries compose with pipelines; object key-stringification corrupts). Bound map growth at creation where cardinality is unbounded (eviction policy in the same commit — Domain 01 §2.2's cache discipline, restated because unbounded maps remain the top memory incident shape).

```bash
# GOOD: the map-first reflex — one pass builds, O(1) reads (amortize over queries)
#  two-sum / group-anagrams / first-unique / subarray-sum-K (next leaf) / memo tables
#  pattern: build relation in one pass (O(n) inserts), query per element (O(1) avg each).
# BAD: nested scans on relation-shaped problems ("no extra space") —
# O(n^2) time to save O(n) space, backwards (Domain 01 §2.2) on every axis that bills
```

### 4) **Common confusion**

- "Hash maps are `O(1)`" — *average* `O(1)` over non-adversarial keys; worst `O(n)` per operation. The qualifier is the analysis (verified 10 vs 10,000 chains on one model).
- "Objects and Maps are interchangeable" — objects stringify keys (`{1:'a'}` collides conceptually with `{'1':'a'}`), inherit prototypes (`__proto__` hazards — JavaScript 06 documents), and unordered-iterate integers first. Maps take any key, order by insertion, stay clean. Different structures sharing a nickname.
- "Resizing makes inserts `O(n)`" — resizing amortizes (Domain 01 §2.1, fourth appearance): total rehash work across `n` inserts bounded linearly → `O(1)` amortized per insert, hard guarantee, no distribution assumed.
- "Collisions don't matter with good hashes" — good hashes matter for *honest* inputs; *adversarial* inputs need seeded hashing (engine-provided) plus worst-case budgeting. Hash quality and threat model are separate dials.

### 5) **Performance note**

Map ops cost tens of nanoseconds flat across sizes at honest loads (verified: single-to-tens of ns at `n=10³` and `n=10⁵` — no growth trend; absolute numbers are machine-specific noise, flatness is the signal). Degenerate chains cost `O(chain)` pointer hops per op (verified 10,000-deep worst — cache-hostile linked walking, the expensive shape). Resize events cost `O(n)` rehash each, geometrically spaced (amortized constant — the verified doubling economics from Domain 01 §2.1, restated for buckets). Optimize hash quality first (engine default, seeded), load factor second (resize earlier under adversarial suspicion), structure choice third (trees where ordering needed — next section).

### 6) **Mentor note**

Demonstrate both rungs live (uniform max-10 vs degenerate 10,000 on one model — "same API, two universes" lands harder than any definition), then name the threat model explicitly (trusted vs user-controlled keys — the sentence that converts analysis into security thinking). Drill map-first reflex with relation-shaped problems (complements/groups/counts — "what would you remember per element?"). Watch for the average-quoter ("`O(1)`, done" — fix with "over what distribution? against whom?") and the nester ("no extra space" — fix with time/space trade arithmetic on their own sizes). Review check: distribution stated per average claim, maps bounded where cardinality is open, objects-vs-Maps chosen deliberately, juniors can name both rungs with the verified numbers.
