## 1.1. Memoization vs tabulation

### 1) **Overlapping subproblems invite memo tables**

**Definition** — dynamic programming applies when subproblems *overlap* (same subproblem solved many times in the recursion tree) and exhibit *optimal substructure* (optimal answers built from optimal subanswers): memoization stores each distinct answer on first computation, turning exponential recomputation into polynomial distinct work. Verified: naive `fib(25)` makes **242,785** calls (the recursion tree re-solves `fib(3)` thousands of times); memoized makes **49** calls filling **24** table entries — same answers, five orders apart, identical code shape plus a cache.

- **What problem it solves**: naive recursion on overlapping subproblems bills exponentially for polynomially-many distinct answers (fib(100) needs 100 distinct values; naive demands ~10²¹ calls — heat death first). Memoization converts the tree into a DAG evaluation (each distinct subproblem computed once, reused everywhere): the recursion *structure* stays (top-down, ask-driven), the *complexity* collapses to distinct-states × transition-cost. Five orders of magnitude from one Map — the highest-leverage cache in algorithms.
- **Modern guidance** — reach for memoization when the recurrence is clear but the evaluation order isn't (tree-shaped thinking: state the relation, cache the function — order emerges from demand). Key the table by subproblem identity (arguments tuple — `Map` with composite keys or nested maps; key design *is* the implementation). Size the table honesty (24 entries for fib(25) — `O(states)` space stated beside the time win, Domain 01 §2.2's trade restated for DP).

```javascript
// GOOD: tree-shaped thinking, DAG-priced execution — verified 242785 -> 49 calls
function fibMemo(n, memo = new Map()) {
  if (n <= 1) return n;
  if (!memo.has(n)) memo.set(n, fibMemo(n - 1, memo) + fibMemo(n - 2, memo));  // compute once...
  return memo.get(n);                                                          // ...reuse everywhere
} // fibMemo(25) = 75025, 49 calls, 24 entries verified. O(n) time, O(n) space + O(n) stack.
// BAD: naive recursion "for clarity" past n = 40 ("still fast on tests") —
// exponential bills at production sizes; clarity without memoization is energy waste with syntax
```

### 2) **Top-down asks, bottom-up builds**

**Definition** — two control flows, same complexity: *memoization* (top-down: recurse on demand, cache answers — evaluates only reachable states, pays recursion stack); *tabulation* (bottom-up: iterate states in dependency order, fill the table — evaluates all states up to target, `O(1)` stack, enables space compression). Same `O(states × transition)` time, different constants and space shapes: memoization skips unreachable states (sparse win) but risks stack depth (Domain 01 §2.2's ceiling); tabulation touches everything (dense cost) but rolls space (previous-row-only → `O(1)`–`O(n)`).

- **Why it matters (correctness)**: control flow decides failure modes — deep recursion overflows where tabulation iterates (fib(20000) memoized dies on stack, tabulated survives); sparse state spaces waste tabulation (reachable fraction tiny — table fills states nobody asks); dependency cycles break tabulation ordering (topological order required — memoization with cycle detection degrades gracefully where tables deadlock). The recurrence is shared; the evaluation strategy is engineered per workload.
- **Modern guidance** — default to memoization for clarity (recurrence transcribed directly — reviewable against the math) and sparse states (reachable ≪ total — demand-driven wins). Convert to tabulation when depth threatens (linear chains past ~10⁴ — stack ceiling binds), space compresses (rolling rows cut tables to `O(1)`/`O(n)`), or hot loops demand it (iteration beats call overhead measurably — Domain 01 §3.1 verifies). State the choice per implementation ("memoized: sparse states" / "tabulated: depth + compression") — the sentence that prevents cargo-cult conversion.

```javascript
// GOOD: same recurrence, engineered control flow (tabulated twin — no stack, rolling space)
function fibTab(n) {
  if (n <= 1) return n;
  let a = 0, b = 1;                       // rolling pair: O(1) space (table compressed away)
  for (let i = 2; i <= n; i++) { const c = a + b; a = b; b = c; }
  return b;
} // O(n) time, O(1) space, O(1) stack. Memo twin: O(n) space + O(n) stack, sparse-friendly.
// BAD: memoization on 10^5-deep chains ("same complexity") —
// same TIME complexity; stack depth differs — RangeError is not a complexity class
```

### 3) **State defines the table**

**Definition** — DP design starts from *state*: parameters identifying a subproblem (index `i`, position `(i,j)`, remaining capacity, bitmask subset — dimensions = parameter count, table size = state count). Transitions move between states (recurrence), base cases anchor them, evaluation order respects dependencies (topological — reverse edges of the dependency DAG, Domain 05 §1.2's order enabling DP). Complexity reads off the design: `O(states × transition-cost)` time, `O(states)` space (compressible when dependencies are local).

- **Why it hurts when missing (correctness, maintainability)**: stateless DP attempts enumerate instead (brute force wearing memo-table clothes — caching full inputs instead of subproblem identities, or recursing without overlapping structure — memoization with zero hits bills recursion overhead for nothing). Bloated states explode tables (3D where 2D suffices — dimension discipline is the analysis), and unordered evaluation reads garbage (tabulation before dependencies computed — silent wrong answers, the ordering bug tests miss when small tables accidentally align). State-transition-base-order *before code* — the four slots from the checklist leaf, previewed.
- **Modern guidance** — fill four slots on paper first (state? transition? base? order? — thirty seconds that prevent every structural DP bug). Minimize dimensions aggressively (rolling arrays, bitmask compression, coordinate squeezing — each dimension removed divides memory). Verify overlap exists (distinct-states ≪ naive-calls — the verified 24-vs-242785 ratio is the pattern; memoization without overlap is overhead without payoff). Name the table after the state ("`dp[i]` = best up to `i`" — the definition reviewers check transitions against).

```bash
# GOOD: four slots before code (design discipline)
#  state:      dp[i] = optimal answer for prefix ending at i (1D, O(n) states)
#  transition: dp[i] = best over valid predecessors (O(choices) each)
#  base:       dp[0..k] seeded from problem edges (stated, tested)
#  order:      increasing i (dependencies: smaller prefixes — topological by construction)
# BAD: "DP with memo" and no statable state ("cache results as we go") —
# caching without subproblem identity is overhead; recurrence without order is wrong answers
```

### 4) **Common confusion**

- "DP means recursion + memo" — DP means *optimal substructure + overlapping subproblems, exploited via stored answers* (tabulation qualifies fully — no recursion required). Memoization is one evaluation strategy, not the paradigm.
- "Memoization fixes any exponential" — memoization fixes *overlapping* exponentials (fib: 24 distinct states); non-overlapping exponentials (permutations: `n!` distinct states — every state unique, cache never hits) stay exponential. Overlap is the admission ticket (leaf: Domain 06 §4.1).
- "Tabulation is always faster" — tabulation wins depth-safety and space compression; memoization wins sparse states (computes reachable-only) and clarity (recurrence transcribed). Same complexity class, different engineering envelopes.
- "Greedy is just DP with small tables" — greedy commits without reconsideration (no table — leaf 3.1's exchange proofs replace stored subanswers); DP explores options via stored optima. One decision vs many remembered — different paradigms sharing optimization goals.

### 5) **Performance note**

Memoization costs distinct-states × transition (verified 49 calls for 24 states — near-1:1, the ideal ratio) plus `O(states)` table + `O(depth)` stack; tabulation costs the same time with `O(states)` table (compressible to `O(1)`–`O(row)`) and `O(1)` stack. Naive baseline costs exponential calls (verified 242,785 at `n=25` — doubling every ~2 increments of `n`). Optimize overlap-exploitation first (table vs tree — five orders), control flow second (depth/space/sparsity decide memo-vs-tab), micro-structure never (cache design dominates constants).

### 6) **Mentor note**

Demonstrate the collapse live (242,785 vs 49 — "same answers, five orders apart" converts memoization from technique to reflex), then convert top-down to bottom-up together (same recurrence, rolling space — the two envelopes side by side). Demand four-slot designs before DP code ("state? transition? base? order?" — thirty seconds preventing structural bugs). Watch for the naive-optimist ("fast on tests" exponentials — fix with `n=100` arithmetic on the spot) and the memo-everything reflex (caching without overlap — fix with "how many distinct states?" as the admission question). Review check: overlap proven (distinct ≪ naive), state named with table size, control flow justified (depth/space/sparsity), juniors can derive memo-from-recurrence aloud.
