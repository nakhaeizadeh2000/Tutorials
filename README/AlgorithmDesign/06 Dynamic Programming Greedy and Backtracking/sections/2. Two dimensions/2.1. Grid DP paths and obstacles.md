## 2.1. Grid DP: paths and obstacles

### 1) **Paths sum from top and left**

**Definition** — right/down paths to each cell = paths from above + paths from left (`dp[i][j] = dp[i−1][j] + dp[i][j−1]`, first row/column seeded with 1s): `O(mn)` time, `O(mn)` table (compressible to one row — next sections). Verified: 3×7 grid → **28** paths. The recurrence *is* the combinatorics (each path's last step comes from exactly one predecessor — counting without enumerating, the DP signature move from leaf 1.2's stairs generalized to two dimensions).

- **What problem it solves**: path enumeration explodes combinatorially (3×7 has 28 paths — enumerable; 20×20 has ~35 billion — not), while closed forms (binomial coefficients — valid only obstacle-free) collapse on real inputs. Grid DP counts *through* the recurrence (each cell's answer from two neighbors — linear in cells, exact with obstacles, costs, and constraints layered on). The table answers every sub-rectangle simultaneously (prefix-of-paths property — queries answered, not just the corner).
- **Modern guidance** — seed edges explicitly (first row/column = 1 — reachable by exactly one monotone route; the base cases novices fumble). Fill row-major (dependencies above+left computed — order respects DAG, Domain 05 §1.2's principle wearing table clothes). Test the combinatorics on small grids (3×7→28 verified — closed-form cross-check where obstacles absent). Generalize moves carefully (diagonal allowed → third predecessor; k-step jumps → window sums, Domain 03 §2.1's exchange recurring).

```javascript
// GOOD: counting through recurrence — verified 28
function gridPaths(m, n) {
  const dp = Array.from({ length: m }, () => new Array(n).fill(1));  // edges seeded (one route each)
  for (let i = 1; i < m; i++)
    for (let j = 1; j < n; j++)
      dp[i][j] = dp[i - 1][j] + dp[i][j - 1];   // last step from above OR left (exhaustive, disjoint)
  return dp[m - 1][n - 1];
} // gridPaths(3, 7) = 28 verified. O(mn) time, O(mn) space (rolling next section).
// BAD: DFS enumeration with memo "for clarity" on grids ("same complexity") —
// same class, worse constants (call overhead × cells) plus stack depth m+n; tables suit tables
```

### 2) **Obstacles zero out cells**

**Definition** — blocked cells contribute nothing (`dp = 0` — unreachable, absorbing): propagation flows *around* them automatically (neighbors sum the surviving routes — no special-case branching in the recurrence, just zeroed seeds). Verified: 3×3 middle-blocked → **2** paths (the two perimeter routes — center's 6 would-be paths vanish); blocked start → **0** (correct: no journey begins). Obstacles *constrain*, never complicate — the recurrence shape is identical, the seeds carry the information.

- **Why it matters (correctness)**: obstacle handling branches wrong in naive implementations (skip-if-blocked with uninitialized neighbors — `undefined` arithmetic → `NaN` propagation; or obstacle-aware recurrence variants that double-count around corners). Zero-seeding unifies: blocked cells are just cells with zero ways-through (the recurrence sums zeros honestly — no branches, no `NaN`, no double-count). Start-blocked and end-blocked fall out free (0 propagates correctly — edge cases handled by structure, not conditionals).
- **Modern guidance** — encode obstacles as zeros at seed/fill time (never as recurrence branches — uniformity is correctness). Test the obstacle matrix explicitly (middle-blocked 2, start-blocked 0, end-blocked 0, wall-bisected 0 — verified pair plus two implied; walls spanning full rows/columns sever all routes — connectivity reasoning from Domain 05 §1.2, restated). Distinguish blocked (zero ways) from zero-cost (next section's min-path — passable with no price — different zeros, different semantics).

```javascript
// GOOD: obstacles as zeros — recurrence unchanged, edges covered structurally
function pathsObs(g) {
  const R = g.length, C = g[0].length;
  const d = Array.from({ length: R }, () => new Array(C).fill(0));
  for (let i = 0; i < R; i++) for (let j = 0; j < C; j++) {
    if (g[i][j] === 1) { d[i][j] = 0; continue; }   // blocked: zero ways (absorbing, no branch needed)
    if (i === 0 && j === 0) d[i][j] = 1;            // start free: one empty route
    else d[i][j] = (i ? d[i - 1][j] : 0) + (j ? d[i][j - 1] : 0);
  }
  return d[R - 1][C - 1];
} // middle-blocked 3x3 -> 2 verified; blocked start -> 0 verified (no journey begins).
// BAD: obstacle-skipping branches inside the recurrence ("optimized") —
// uninitialized-neighbor NaN + corner double-counts; zeros unify, branches fracture
```

### 3) **Compress to one row**

**Definition** — grid recurrences read only the previous row (paths: above + left — left is current-row-earlier, above is previous-row-same-column): one array updated left-to-right suffices — `O(n)` space (columns) instead of `O(mn)`. Verified shape: min-path `[[1,3,1],[1,5,1],[4,2,1]]` → **7** via single rolling row (`1→3→1→1→1` path — right, right, down, down). The compression generalizes (rolling arrays wherever dependencies are local — leaf 1.1's fib pair, Domain 01 §2.2's principle, third appearance).

- **Why it hurts when missing (correctness, maintainability)**: full tables on large grids waste memory proportionally (10⁴×10⁴ grid → 10⁸ cells ≈ 800MB for a one-row recurrence — OOM where `O(n)` fits in L3), and tables invite index bugs the rolling form prevents (row/column transpositions, stale-row reads — fewer indices, fewer mistakes). Compression isn't premature optimization (memory *is* the constraint at grid scale); it's the recurrence's honest space bound. Full tables persist only where backtracking needs history (path *reconstruction* reads the table backwards — store parents or recompute, decided explicitly).
- **Modern guidance** — roll by default (one row for top-left dependencies; two rows where diagonal reads need previous-row stability — update direction matters: left-to-right preserves above-reads). Keep full tables only for reconstruction (path recovery walks history — store it deliberately, priced). State space beside time per grid DP ("`O(mn)` time, `O(n)` space rolled" — the sentence reviewers check). Test rolling against full-table oracles on small grids (identical answers — compression proven, not hoped).

```javascript
// GOOD: one row, left-to-right (above-reads stable) — verified 7
function minPath(g) {
  const R = g.length, C = g[0].length, prev = new Array(C).fill(0);
  for (let i = 0; i < R; i++) for (let j = 0; j < C; j++) {
    if (i === 0 && j === 0) prev[j] = g[i][j];
    else prev[j] = g[i][j] + Math.min(i ? prev[j] : Infinity, j ? prev[j - 1] : Infinity);
  }                                               // prev[j]: above (stable, this column); prev[j-1]: left (fresh)
  return prev[C - 1];
} // O(mn) time, O(n) space. Right-to-left would corrupt above-reads — direction is correctness.
// BAD: full m x n tables "for clarity" at grid scale —
// 800MB for one-row recurrences; clarity that OOMs is not clarity
```

### 4) **Common confusion**

- "Grid DP needs the full table" — needs it only for *reconstruction* (path recovery); counting/optimizing need rolling rows. Table size follows *use* (answers vs paths), not habit.
- "Obstacles need special recurrences" — obstacles need zeroed seeds (verified 2 and 0); the recurrence never changes. Special-casing multiplies bug surface for zero expressive gain.
- "Update direction doesn't matter" — rolling left-to-right preserves above-reads; right-to-left (or top-to-bottom in column-major) corrupts them. Direction *is* the dependency order (Domain 05 §1.2, wearing indices).
- "Combinatorics replaces grid DP" — binomial coefficients answer obstacle-free counts only (verified 28 either way); obstacles/costs/constraints need the table. Closed forms are special cases, DP the general method.

### 5) **Performance note**

Grid DP costs `mn` cells × `O(1)` transitions (verified probes single-digit ms) with `O(n)` rolled space (vs `O(mn)` full — 800MB-vs-KB at 10⁴ scale); obstacle handling adds zero asymptotic cost (zero-seeds ride the same loops); min-path adds `min` per cell (constant — same envelope as counting). Optimize space shape first (roll by default), recurrence sharing second (count + min in one pass where both needed), micro-loop third (typed arrays past 10⁷ cells — cache wins where tables fit L3).

### 6) **Mentor note**

Teach counting through recurrence with the verified 28 (combinatorics without enumeration — the DP signature move), obstacles as zeros (2 and 0 probes — structure over branching), compression live (full table → one row, same answers — "store what's reread"). Drill update direction ("which reads must stay stable?" — direction derived, not memorized). Watch for the enumerator ("thorough" DFS counting — fix with 20×20 ≈ 35-billion arithmetic) and the table-hoarder (full grids where rolling suffices — fix with predecessor analysis: "which rows does the transition read?"). Review check: edges seeded, obstacles zeroed (never branched), space rolled (reconstruction justified where kept), juniors can derive paths/min/obstacle variants from one recurrence.
