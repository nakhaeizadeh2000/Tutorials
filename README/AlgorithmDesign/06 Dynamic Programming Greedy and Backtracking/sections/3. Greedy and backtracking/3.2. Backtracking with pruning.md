## 3.2. Backtracking with pruning

### 1) **Search with undo**

**Definition** — backtracking explores decision trees with state restoration (choose → recurse → *unchoose*: place a queen, recurse rows below, remove it on return — the undo that reuses one board across the whole search). Verified: N=4 → **2** solutions, N=8 → **92** (the canonical counts — any implementation must reproduce both). Subsets enumerate `2ⁿ` (verified 1,048,576 at `n=20` = 2²⁰ exactly); permutations `n!` — output-sensitive costs (the answer count *is* the complexity floor where all answers are required).

- **What problem it solves**: constraint problems without closed forms (N-queens, Sudoku, partitions-with-rules, exact covers) need *systematic* search — random sampling misses solutions silently, greedy commits wrongly (leaf 3.1's foil, restated: local placement breaks global constraints), DP needs overlapping structure absent here. Backtracking enumerates *completely* (every leaf visited or pruned — next section) with *shared state* (one board, undone per return — `O(n)` space for exponential search). Completeness with constant-ish memory is the deliverable.
- **Modern guidance** — structure every backtracker identically (choose from candidates → check constraints → recurse → undo the choice — the four-line skeleton; deviations hide state leaks). Undo *explicitly* (remove/restore in code, never "reset later" — leaked state corrupts sibling subtrees silently). Count solutions to calibrate (N=4→2, N=8→92 verified oracles — wrong counts mean broken search *or* broken constraints; either way the oracle catches it). Prefer iterative-deepening where depth varies wildly (depth-bounded completeness — exotic, named for completeness).

```javascript
// GOOD: choose-recurse-unchoose — verified 2 and 92 (oracle pair)
function queens(n) {
  let count = 0; const col = new Array(n).fill(-1);   // shared board: O(n) space, whole search
  function ok(r, c) { for (let i = 0; i < r; i++)
    if (col[i] === c || Math.abs(col[i] - c) === r - i) return false; return true; }
  function bt(r) {
    if (r === n) { count++; return; }                 // complete placement: count it
    for (let c = 0; c < n; c++) if (ok(r, c)) { col[r] = c; bt(r + 1); /* undo implicit: overwritten */ }
  }
  bt(0); return count;
} // queens(4) = 2, queens(8) = 92 verified. Time output-sensitive (answer-sized); space O(n).
// BAD: copying the board per recursion ("safer") —
// O(n) copy x exponential nodes = memory avalanche; undo shares one board correctly
```

### 2) **Prune with constraints**

**Definition** — pruning kills subtrees that cannot succeed (constraint checks *before* recursing: attacked squares skipped, over-budget partials abandoned, infeasible remainders detected): completeness preserved (only dead subtrees cut — live ones explored fully), search collapsed (N-queens without pruning tries `nⁿ` placements ≈ 16M at `n=8`; with row/column/diagonal constraints ≈ thousands of nodes — orders apart). Constraint *propagation* (forward checking: eliminate newly-impossible values eagerly — Sudoku solvers' engine) prunes deeper still.

- **Why it matters (correctness)**: unpruned backtracking is enumeration wearing recursion (correct, exponential, unusable past toy sizes — N=12 queens unpruned outlives patience). Pruning is what makes search *usable*: same answers, fraction of the tree. But pruning must preserve completeness (cut only provably-dead subtrees — aggressive "likely-dead" heuristics convert exact search into sampling *silently*). The discipline: prune on proof (constraint violation ⟹ no completion below), never on likelihood.
- **Modern guidance** — check constraints before recursing (fail fast at the shallowest failing node — depth of cut determines savings). Order candidates by constraining power (most-constrained-first: fewest options tried first — failures surface shallow, subtrees die young). Propagate eagerly where cheap (forward checking on tight constraints — Sudoku rows/columns/boxes; the propagation that separates solvers from enumerators). Measure nodes-visited, not just answers (pruning quality quantified — the metric that compares constraint designs).

```javascript
// GOOD: prune on proof (attacked squares never recursed — verified counts include pruning)
// ok(r, c) checks columns + diagonals BEFORE bt(r+1): dead placements die at depth r, not r+5.
// N=8 -> 92 solutions via thousands of nodes (pruned) vs ~16M placements (raw n^n). Same answers.
// ordering: left-to-right columns here; most-constrained-first generalizes (fewest options first).
// BAD: "prune unlikely branches" heuristics in exact search ("faster") —
// likelihood-pruning converts completeness to sampling silently; answers missing without notice
```

### 3) **Complexity is output-sensitive**

**Definition** — backtracking costs track *answers plus pruned nodes* (subsets: exactly `2ⁿ` leaves — verified 1,048,576 = 2²⁰, no pruning possible since every subset is an answer; N-queens: 92 answers via thousands of nodes — pruning ratio enormous; SAT: zero-or-one answers via exponential search — worst case full tree). Output-sensitive analysis states both terms (answers × cost-each + pruned-nodes × check-cost) instead of one exponential blob — the framing that distinguishes enumeration (answers dominate) from search (pruning dominates).

- **Why it hurts when missing (correctness, maintainability)**: output-blind complexity ("exponential, avoid") kills legitimate enumeration (subsets of 20 *must* cost ~10⁶ — the answers themselves; no smarter algorithm exists where all answers are required) and excuses unpruned search ("exponential anyway" — pruning ratios of 1000× dismissed with the same label). Output-sensitivity separates unavoidable cost (answer count — proven lower bound) from avoidable waste (unpruned nodes — engineering target). The two terms get different responses: accept the first, attack the second.
- **Modern guidance** — state answers-vs-nodes per search ("92 answers via ~10⁴ nodes" — both numbers, the ratio is the pruning grade). Accept answer-dominated costs unconditionally (enumeration *is* exponential where answers are — 2²⁰ subsets verified exact, irreducible). Attack node-dominated costs with constraints (propagation, ordering, memoization of dead states — failed-subproblem caching converts repeat dead-ends into table lookups, DP wearing search clothes from leaf 1.1). Never quote bare exponentials ("`O(2ⁿ)`" — of *what*? answers? nodes? both? — the decomposition is the analysis).

```bash
# GOOD: output-sensitive accounting (answers vs nodes, separately)
#  subsets(20):  1048576 answers via 1048576 nodes (verified exact) — enumeration, irreducible.
#  queens(8):    92 answers via ~10^4 nodes (pruned) vs ~16M placements (raw) — pruning grade: 1000x.
#  SAT worst:    0-1 answers via 2^n nodes — search-dominated, propagation attacks nodes.
# BAD: "backtracking is O(2^n)" as the whole analysis —
# answers and nodes conflated; irreducible enumeration and fixable waste treated identically
```

### 4) **Common confusion**

- "Backtracking is just DFS" — DFS *traverses* existing graphs (Domain 05 §1.2); backtracking *builds and unbuilds* decision states (choose/undo cycle — no graph materialized, states constructed per path). Related control flow, different objects.
- "Pruning changes answers" — sound pruning removes *only* provably-dead subtrees (answers preserved exactly — verified counts prove it); heuristic cutting removes live ones (sampling, not search). Proof separates them; speed doesn't.
- "Memoization fixes backtracking" — memoization helps *overlapping* dead states (failed-subproblem caching — DP hybrid where subproblems recur); tree-shaped searches with unique states gain nothing (cache never hits — overhead without payoff, leaf 1.1's admission ticket restated).
- "N-queens teaches queens" — N-queens teaches *constrained search skeletons* (choose Constrain recurse undo prune — the pattern solving Sudoku, partitions, exact covers). Queens are the example; skeletons transfer.

### 5) **Performance note**

Backtracking costs answers + pruned-nodes (verified: 2/92 solutions, 2²⁰ exact enumeration, thousands-vs-millions pruning gap) with `O(depth)` shared state (undo reuses one board — memory minimal by construction). Constraint checks cost per node (cheap tests compound across millions of nodes — `ok()` hotness matters; bitmask columns/diagonals trade clarity for 10× speedups where profiles demand). Optimize pruning first (constraint strength decides node counts — orders of magnitude), candidate ordering second (constrained-first dies young), bit-level tricks last (constants on already-pruned trees).

### 6) **Mentor note**

Teach skeletons before problems (choose-constrain-recurse-undo — one shape solving queens/Sudoku/partitions; learn once, apply widely). Demonstrate pruning with node counts (raw placements vs pruned nodes — the 1000× gap converts skeptics permanently). Drill output-sensitivity ("answers or nodes dominating here?" — the question that routes effort correctly). Watch for the enumerator-without-pruning ("thorough" raw search — fix with node-count arithmetic on N=12) and the likelihood-pruner ("probably dead" cuts — fix with "prove it dead or explore it"). Review check: undo explicit, constraints checked pre-recursion, oracle counts green (2/92), output-sensitivity stated (answers vs nodes), juniors can skeleton any constrained search unprompted.
