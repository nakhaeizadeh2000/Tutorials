## 4.1. Paradigm checklist (habits mentors insist on)

### 1) **Optimal substructure first**

**Definition** — the DP admission ticket: optimal answers built from optimal subanswers (stairs from predecessors, robbery from constrained bests, grids from top/left, alignments from prefix triples — leaves 1.2–2.2). Without it, tables store optima nobody can compose (greedy-shaped problems forced into DP tables that prove nothing — structure without substructure). State it per problem ("optimal X contains optimal Y because...") — the sentence that admits DP or routes elsewhere (greedy with exchange, backtracking with pruning).

- **What problem it solves**: paradigm-first selection memorizes shapes without preconditions (DP "for optimization problems" applied where substructure fails — tables filled with locally-optimal values that don't compose globally; the silent-wrong-answer class DP produces when misadmitted). Substructure-first inverts the flow: prove composability, then tabulate — and the proof attempt itself routes correctly (exchange sketch emerges → greedy; overlapping states emerge → DP; neither → backtracking with pruning).
- **Modern guidance** — write the substructure sentence before any table ("optimal path to (i,j) extends an optimal path to a predecessor — because any subpath of an optimal path is optimal for its endpoints"). Attempt the exchange sketch in parallel (greedy candidate + swap argument — five minutes that either certify streaming or confirm tables). When neither holds, say so explicitly (brute force honestly priced, or approximation with stated ratios — no paradigm masquerading).

```javascript
// GOOD: admission proven, then tabulated (substructure sentence first)
// stairs: ways(n) = ways(n-1) + ways(n-2) — last step partitions all compositions (disjoint, exhaustive).
// robbery: best(i) = max(best(i-1), best(i-2)+a[i]) — optimal either skips i or takes it constrained.
// grids: paths(i,j) = paths(above) + paths(left) — last step partitions all routes.
// BAD: "looks like DP, build a table" without substructure ("intuitive") —
// tables without composability store numbers that don't combine; answers wrong with DP formatting
```

### 2) **Greedy proven or DP'd**

**Definition** — the fork every optimization problem faces: greedy with exchange proof (streaming, no table — leaf 3.1's certification) or DP with tables (exploration, stored optima — leaves 1.1–2.2). Hope is not a paradigm (uncertified greed fails on verified counterexamples — 3-vs-2 coins; unproven DP wastes tables where streaming sufficed — engineering excess). The checklist demands one or the other *evidenced*: exchange sketch attached, or differential test green, or table justified by failed exchange.

- **Why it matters (correctness)**: paradigm errors are the most expensive category (wrong answers at scale, not slow ones — uncertified greed ships overcharges; unnecessary DP ships late with memory incidents; backtracking where DP applied bills exponentially). Each stems from skipping the fork decision (defaulting to familiarity — "I know DP" tables everything; "greedy is elegant" hopes everywhere). The fork *is* the analysis: two minutes choosing correctly saves quarters of wrong-shaped code.
- **Modern guidance** — run the fork explicitly (exchange sketch attempted → success ships greedy, failure ships DP; differential test on randomized inputs as arbiter — agreement maps validity, disagreement locates boundaries). Prefer DP as the safe default (tables explore what greed assumes — correct superset; optimize to greedy only with proof). Prefer greedy where certified *and* hot (streaming constants matter at scale — certified greed is the fastest correct code, not a shortcut). Document the fork outcome ("exchange holds — greedy certified" vs "no exchange found — DP tables").

```bash
# GOOD: the fork decided with evidence (per optimization problem)
#  exchange sketch succeeds? -> greedy (streaming, proven). e.g. activity selection (verified trio).
#  exchange fails/unclear?   -> DP tables (exploration, safe). e.g. arbitrary coins (verified 3-vs-2).
#  differential green?       -> greedy where agreed, DP where diverged (boundary mapped, both shipped rightly).
# BAD: paradigm by familiarity ("I do DP for these") or elegance ("greedy reads cleaner") —
# familiarity misadmits, elegance hopes; evidence decides
```

### 3) **State, transition, base, order**

**Definition** — the four DP slots filled before code (leaf 1.1's design discipline, restated as checklist): *state* (subproblem identity — dimensions = parameters, size = count), *transition* (recurrence over predecessors — exhaustive and disjoint), *base* (edge seeds — empty compositions count, blocked cells zero), *order* (evaluation sequence respecting dependencies — increasing indices, topo order, rolling direction). Unfilled slots produce the four classic DP bugs respectively (wrong table shape, missing cases, off-by-one seeds, garbage-from-uncomputed reads).

- **Why it hurts when missing (correctness, maintainability)**: slot-skipping bugs are silent-value (tables fill with plausible wrong numbers — no errors, just incorrect optima that pass small tests where brute force agrees by coincidence). Each missing slot has a signature failure (no state → exponential re-solve; partial transition → missed optima; unseeded base → off-by-one cascades; wrong order → reads of uncomputed cells). The four-slot check converts debugging from archaeology into slot-audit (which slot is wrong? — asked first, answered fast).
- **Modern guidance** — write the four slots as comments above every DP implementation (state/transition/base/order — reviewable design, not just code). Verify slots independently (state count vs table size — match; transition exhaustiveness — cases partition; base values — oracle-tested; order — dependencies precede uses). Reuse slot patterns across problems (1D take-skip, 2D grid-sum, DAG-relax, split-enumerate — the family shapes from leaves 1.2–2.2, recognized not reinvented). Newcomers fill slots on paper first (thirty seconds preventing structural bugs).

```javascript
// GOOD: four slots as comments (design reviewable before code runs)
// state:      dp[i] = max loot through house i (1D, O(n) states)
// transition: dp[i] = max(dp[i-1], dp[i-2] + a[i]) (skip/take — exhaustive, disjoint)
// base:       dp[-1] = 0, dp[0] = a[0] (empty earns nothing; first stands alone)
// order:      increasing i (dependencies: smaller prefixes first)
// BAD: recurrence coded directly from intuition ("dp[i] = ... something with max") —
// unslotted recurrences hide missing cases, unseeded bases, and unordered reads simultaneously
```

### 4) **Common confusion**

- "Checklists replace paradigm fluency" — checklists *route* to the right paradigm with the right evidence; fluency implements recurrences. Routing first (substructure? exchange? slots?), execution second.
- "Small DP problems don't need four slots" — small problems need slots *most* (tests pass without them — structural bugs surface at scale, far from the code). Slots are cheapest when tables are smallest.
- "Greedy-vs-DP is a style choice" — it's an *evidence* choice (exchange proof or differential agreement vs table exploration). Style doesn't decide correctness; proofs and tables do.

### 5) **Performance note**

The checklist costs minutes per optimization problem (substructure sentence, fork decision, four slots) against wrong-paradigm incidents (uncertified greed overcharges; unneeded tables OOM; exponential backtracking where DP applied — hours of debugging answers that aren't errors, plus rewrites). Highest-leverage item is the fork decision (selects paradigm correctly); second is four-slot design (prevents structural DP bugs); third is exchange sketching (certifies streaming where valid). Minutes preventing rewrites — paradigms' best attention rate.

### 6) **Mentor note**

Convert this leaf into the domain's selection runbook: substructure → fork (greedy-proven vs DP-tabled) → four slots → implement. Quiz juniors on routing ("which question fires for arbitrary coins? for canonical? for N-queens?") until answers are environmental. Watch for checklist decay (paradigms chosen by familiarity under deadline — fix with fork-evidence as review-blocking) and slot-skipping ("intuitive recurrences" — fix with four-slot demands before code review). Review check: substructure stated, fork evidenced, slots filled — and the mentor's own optimization code modeling all three visibly.
