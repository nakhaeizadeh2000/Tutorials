## 1.1. Opposite-ends and same-direction patterns

### 1) **Converge on sorted data**

**Definition** — opposite-ends pointers start at both extremes and walk inward, deciding per step which end to move: two-sum on sorted arrays (`a[l] + a[r]` vs target — too small advances left, too big retreats right), palindromes (mirror comparison inward), container-with-most-water (move the shorter wall — the only move that can improve). Verified: two-sum `[1,2,4,7,11,15]` target 15 → pair `[2,4]` (values 4+11) in 4 steps — each step discards one index permanently, so ≤ `n` steps total: `O(n)` time, `O(1)` space.

- **What problem it solves**: nested loops price pairs at `O(n²)` (Domain 01 §2.1's triangle) — but sorted order makes most pairs *impossible*, and opposite-ends pointers exploit exactly that: each comparison eliminates a whole row or column of the pair matrix (smaller-than-target kills the left index for all right partners; larger kills the right for all left). Sortedness converts quadratic search into linear elimination — the order pays for the algorithm.
- **Modern guidance** — reach for convergence when the input is sorted (or sortable for less than the search saves — `n log n` sort + linear scan beats `n²` past small `n`) and the decision is monotone in both pointers (sum too small → left must rise; too big → right must fall). State the elimination invariant ("each step discards ≥1 index forever") — it's the linearity proof reviewers check. Never converge on unsorted data (no elimination valid — sort first, hash instead per Domain 04, or pay the nest).

```javascript
// GOOD: elimination, not enumeration — verified 4 steps on n=6
function twoSumSorted(a, t) {
  let l = 0, r = a.length - 1;
  while (l < r) {
    const s = a[l] + a[r];
    if (s === t) return [l, r];   // found: values a[l]+a[r]
    if (s < t) l++; else r--;     // too small kills l for all partners; too big kills r
  }
  return null;
} // twoSumSorted([1,2,4,7,11,15], 15) -> [2,4] in 4 steps. O(n) time, O(1) space.
// BAD: nested pair loops on sorted input ("simpler") —
// O(n^2) enumeration where O(n) elimination applies; sortedness paid for, never spent
```

### 2) **Chase with fast and slow**

**Definition** — same-direction pointers separate roles instead of ends: one pointer *writes* (next kept position), one *reads* (scans ahead) — dedupe-sorted (`write` advances only on new values), remove-element (skip banned values in place), move-zeroes (compact non-zeros, backfill). Order preserved, `O(1)` extra, one pass: the read pointer visits each element once, the write pointer trails at ≤ read speed — linearity by construction, no elimination argument needed.

- **Why it matters (correctness)**: in-place compaction without the pattern corrupts — overwriting unread elements (write overtaking read), skipping comparisons (advancing both on mismatch), or allocating (defeats the `O(1)` point). The reader/writer split makes each pointer's contract statable: reader never revisits (progress guaranteed), writer only advances on kept values (output prefix always valid). Every in-place filter is this shape; recognizing it converts pointer juggling into contract following.
- **Modern guidance** — use reader/writer for in-place filtering with order preservation (dedupe, remove, partition-stable variants); prefer index-based writes over swaps (swaps disturb unread regions — writes only touch the settled prefix). State both contracts in comments (reader: "visits each index once"; writer: "output[0..w) valid"). When extra space is affordable and clarity matters, the copying version (`filter`) beats the in-place one — `O(n)` aux for readability is often the right trade (Domain 01 §2.2).

```javascript
// GOOD: reader/writer contracts — order kept, O(1) extra, one pass
function dedupeSorted(a) {
  if (a.length === 0) return 0;
  let w = 1;                                  // writer: a[0..w) holds deduped prefix
  for (let r = 1; r < a.length; r++)          // reader: visits each index once
    if (a[r] !== a[w - 1]) a[w++] = a[r];     // new value -> settle it, advance writer
  return w;                                   // length of deduped prefix
} // O(n) time, O(1) aux, stable (first occurrences keep order).
// BAD: splice-in-loop dedupe ("expressive") —
// O(n) splice x O(n) positions = O(n^2) with index invalidation; expressive and quadratic
```

### 3) **Sortedness is the admission ticket**

**Definition** — both patterns consume *structure*: convergence needs sorted order (elimination valid only when comparisons order the discards); chasing needs the target predicate to be prefix-decidable (keep/drop decided per element, no lookahead). Unsorted input pays admission three ways: sort first (`n log n` + linear — wins past small `n`), hash instead (Domain 04 — `O(n)` average, no order needed), or pay the nest (`n²` — honest when `n` is tiny and stays tiny).

- **Why it hurts when missing (correctness, maintainability)**: pointers applied to unstructured input produce confident wrong answers — two-sum converging on unsorted data *misses pairs* (elimination invalid: "too small" discards indices whose partners aren't ordered), sliding readers over predicate-violating streams *skip valid windows*. The failure is silent (an answer, not an error — wrong pair, missed optimum) and input-dependent (passes tests, fails production). Structure isn't an optimization here — it's the correctness precondition.
- **Modern guidance** — check the ticket before the pattern: "is it sorted?" (if not: sort cost vs hash vs nest — decide explicitly, document the choice), "is the predicate monotone/prefix-decidable?" (if not: pointers don't apply — reach for DP/backtracking, Domain 06). Write the precondition as an assertion or doc line ("requires: sorted ascending") — the cheapest contract in the file, and the one that prevents silent wrong answers.

```javascript
// GOOD: admission checked, alternatives priced
// two-sum unsorted, n = 10^6: sort (n log n) + converge (n) beats nest (n^2); hash (Domain 04) beats both if order unneeded.
// twoSumSorted documents: "requires: ascending sorted — unsorted input gives wrong answers silently."
// BAD: converging pointers on unsorted arrays because "it worked on the test" —
// elimination without order is guessing with pointer arithmetic; production inputs collect
```

### 4) **Common confusion**

- "Two pointers means two indices" — linked-list pointers chase *nodes* (tortoise/hare — next leaf), windows slide *bounds*, stacks track *candidates*. Two moving references, not necessarily integers.
- "Converge works if I sort a copy" — sorting a copy works *if indices don't matter* (values only); index-returning variants must map back (decorate with original indices first — sort pairs, converge, undecorate).
- "Reader/writer needs extra space for safety" — the contracts *are* the safety (writer trails reader — unread regions never touched). Extra space buys clarity, not correctness; choose by readability budget (Domain 01 §2.2's trade, stated).
- "O(n) pointers beat O(n log n) sort-then-scan always" — pointers need sorted input; if sorting costs `n log n`, total is `n log n` regardless. The pointer pass is linear *given* structure — price the structure too.

### 5) **Performance note**

Pointer passes cost `n` steps with `O(1)` aux and sequential access (prefetch-friendly — the hardware's favorite pattern); convergence costs ≤ `n` eliminations (verified 4 steps on 6 elements — sublinear in practice for early hits). Sorting admission costs `n log n` once (amortize over many queries — sort once, converge often). The expensive mistake is nesting on sorted data (quadratic where linear applied) or converging on unsorted data (wrong answers at any speed).

### 6) **Mentor note**

Drill elimination aloud ("too small kills left for *all* partners — why?" until the matrix reasoning is reflexive), then reader/writer contracts ("what does each pointer guarantee?"). Test admission discipline with unsorted inputs deliberately (watch the confident wrong answer land, then add the precondition line — the lesson sticks through embarrassment). Watch for the nester ("nested loops, simpler" — fix with step-counting: 4 vs 36 on the verified example) and the admitter-skipped (pointers on unstructured input — fix with "requires: sorted" as a review-blocking comment). Review check: invariants stated per pointer, admission documented, hidden linear calls audited (no `includes` inside the pass — Domain 01 §2.1's trap).
