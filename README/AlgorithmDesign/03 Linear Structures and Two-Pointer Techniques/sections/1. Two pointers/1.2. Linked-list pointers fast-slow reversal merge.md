## 1.2. Linked-list pointers: fast-slow, reversal, merge

### 1) **Tortoise and hare find cycles**

**Definition** — Floyd's algorithm: slow advances one node, fast two — on a cycle they *must* meet (fast laps the loop, gaining one node per round — relative speed guarantees rendezvous within one loop length); on acyclic lists fast hits `null` first. Verified: cyclic list → `true`, entrance `2`; acyclic → `false`. Entrance needs a second phase (restart one pointer at head, advance both singly — they meet at the loop start: distance head→start equals meeting→start mod loop length). `O(n)` time, `O(1)` space — no visited-set, no marking.

- **What problem it solves**: cycle detection without the pattern costs memory (visited-sets: `O(n)` aux for the question "have I been here?") or mutation (flag fields corrupting shared structures). Fast-slow spends *speed difference* instead: two pointers, three cases (meet → cycle; null → clean; plus entrance on demand). The technique generalizes anywhere rates differ — middle-finding (fast reaches end when slow halves), k-th-from-end (fast leads by k), palindrome checks on reversed halves.
- **Modern guidance** — reach for fast-slow on linked structures for cycle/middle/k-th questions (the pattern *is* the answer in interviews — state "tortoise and hare" by name). Guard the fast pointer doubly (`f && f.next` — single guards segfault on even lengths; the most common implementation bug). Derive entrance when asked (phase two from the meeting point — know the modular-distance argument, not just the code). Never mark nodes to detect cycles in shared structures (mutation leaks across owners — `O(1)`-space fast-slow exists precisely to avoid it).

```javascript
// GOOD: rendezvous guaranteed by relative speed — verified true/2/false
function hasCycle(h) {
  let s = h, f = h;
  while (f && f.next) {          // double guard: even-length lists need both
    s = s.next; f = f.next.next; // fast gains exactly one node per round -> must meet in a loop
    if (s === f) return true;
  }
  return false;                  // fast hit null: acyclic, slow never mattered
} // O(n) time (<= one loop length + prefix), O(1) space. Entrance: restart s at head, single-step both.
// BAD: visited-Set cycle detection on shared lists ("simpler") —
// O(n) aux for a question answerable in O(1), plus allocation pressure per query
```

### 2) **Reverse and merge in place**

**Definition** — reversal rewires `next` pointers with three references (prev/current/next — verified `1,2,3` → `3,2,1`); sorted merge splices two lists through a dummy head (compare heads, attach smaller, advance — verified `1,3` + `2,4` → `1,2,3,4`). Both `O(n)` time, `O(1)` auxiliary (a few pointers beside the nodes — the nodes themselves are input, Domain 01 §2.2's accounting). The dummy head eliminates the empty-result special case (merge code without branches for "first element" — uniformity as correctness).

- **Why it matters (correctness)**: pointer surgery corrupts silently — one lost `next` reference orphans the tail (unrecoverable without the reflog-like safety nets Git enjoys; here there are none), and the corruption manifests far from the rewiring (downstream traversals hit `null` early or loop forever). The disciplines that prevent it: save-before-overwrite (`n = c.next` *first* — the line whose absence eats lists), dummy heads (uniform attach logic, no first-element branching), and single-pass verification (walk the result immediately — length and order asserted, not assumed).
- **Modern guidance** — save-then-rewire as an inviolable two-line idiom (`const n = c.next; c.next = p;` — never reversed); dummy heads for every construction loop (merge, partition, copy — the branch it removes is the bug it prevents); recursive reversal only for short lists (depth `n` stack — Domain 01 §2.2's ~13,920 frame ceiling binds here exactly). Test surgery with length assertions (result length == input lengths — orphan detection in one number) plus order checks.

```javascript
// GOOD: save-before-overwrite + dummy head — verified 3,2,1 and 1,2,3,4
function rev(h) { let p = null, c = h;
  while (c) { const n = c.next; c.next = p; p = c; c = n; }  // save FIRST, rewire second
  return p; }
function merge(l1, l2) { const d = {v: 0, next: null}; let t = d;  // dummy: no first-element branch
  while (l1 && l2) { if (l1.v < l2.v) { t.next = l1; l1 = l1.next; } else { t.next = l2; l2 = l2.next; } t = t.next; }
  t.next = l1 || l2; return d.next; }  // O(n+m) time, O(1) aux.
// BAD: rewiring without saving (c.next = p before reading c.next) —
// tail orphaned in one statement; manifests as truncation three functions later
```

### 3) **Lists trade access for splicing**

**Definition** — the structure trade, stated once: linked lists splice/insert/delete in `O(1)` *at a known node* (rewire local pointers — no shifting) but index in `O(n)` (walk from head — no random access); arrays index in `O(1)` but insert/delete mid-structure in `O(n)` (shift the tail). Pick by operation mix: splice-heavy with local context (merge pipelines, adjacency in graphs — [Domain 05/3.1](<../../../05 Graphs/sections/3. Graph modeling/3.1. Representations and modeling recipes.md>)) → lists; index-heavy or scan-heavy (binary search, pointer arithmetic) → arrays. Cache behavior sharpens the trade (arrays prefetch; lists chase — constants favor arrays where both qualify).

- **Why it hurts when missing (correctness, maintainability)**: structure mismatch bills twice — lists used as arrays (index-walking in loops: `O(n)` per access × `n` accesses = accidental quadratic, the silent twin of Domain 01 §2.1's nesting) and arrays used as splice buffers (`splice()` in loops: `O(n)` shifts × `n` splices — leaf 1.1's warning, repeated at structure level). Both pass tests (small `n` forgives) and fail at scale (constants stop forgiving). The operation mix decides; familiarity doesn't vote.
- **Modern guidance** — default to arrays in JavaScript (cache-friendly, indexable, method-rich — the engine optimizes them relentlessly); reach for linked structures where splicing dominates *and* nodes are already in hand (LRU lists ([Domain 04/1.1 caches](<../../../04 Hashing Trees and Heaps/sections/1. Hashing/1.1. Hash maps average O1 honest worst cases.md>)), adjacency ([Domain 05/3.1](<../../../05 Graphs/sections/3. Graph modeling/3.1. Representations and modeling recipes.md>)), merge steps). In interviews, implement list surgery fluently (reversal/merge/cycle are the price of admission) but recommend arrays in design discussions unless the mix justifies otherwise. Document the mix beside non-default choices ("list: 10⁶ splices/day, zero indexing" — the justification travels with the structure).

```javascript
// GOOD: structure follows operation mix
// splice-heavy, node-local (merge steps, LRU): linked nodes, O(1) rewire, no shifting.
// index-heavy, scan-heavy (search, windows): arrays, O(1) access, prefetch-friendly.
// BAD: linked list with index-walking loops ("we might need inserts later") —
// O(n) per access x O(n) loop = quadratic speculation tax; arrays until the mix proves otherwise
```

### 4) **Common confusion**

- "Fast-slow only detects cycles" — rates-differencing generalizes (middle, k-th-from-end, palindrome halves, intersection by length-aligning). Cycle detection is the flagship, not the fleet.
- "Entrance needs extra memory" — phase two (head-restart, single-step both) finds the entrance in `O(1)` space via the modular-distance argument. Memory never enters the picture.
- "Recursive reversal is cleaner" — cleaner syntax, linear stack (Domain 01 §2.2's ceiling binds: ~13,920 frames). Iterative three-pointer is the production shape; recursion is the whiteboard shape.
- "Dummy heads waste a node" — one allocation buys branchless uniformity (no first-element special case — the branch it removes is the most bug-dense line in list code). Cheapest node you'll ever allocate.

### 5) **Performance note**

List passes cost `n` pointer hops with `O(1)` aux (cache-hostile hops vs array strides — 3–10× constant gap typical, widening with size); reversal/merge add zero allocation (surgery reuses nodes — GC-neutral, the quiet virtue). Fast-slow costs ≤ `n` + loop-length steps (linear with small constants — two pointers, no allocation). Optimize structure choice first (arrays where both qualify — cache wins), surgery discipline second (save-first/dummy-head prevent the corruption incidents that dwarf micro-costs).

### 6) **Mentor note**

Drill surgery by hand-tracing (three boxes, arrows rewired per statement — juniors who draw never orphan), then verify live (length assertions + order checks on every result). Teach fast-slow as rates ("what else can speed differences find?" — middle, k-th, entrance generalize from one idea). Quiz structure choice by operation mix ("splice-heavy or index-heavy?" — arrays until proven otherwise). Watch for the unsaver (rewire before save — fix with the two-line idiom as inviolable order) and the list-romantic (linked everything — fix with index-cost arithmetic on their own loops). Review check: save-first ordering, dummy heads on constructions, cycle guards doubled, structure justified by mix.
