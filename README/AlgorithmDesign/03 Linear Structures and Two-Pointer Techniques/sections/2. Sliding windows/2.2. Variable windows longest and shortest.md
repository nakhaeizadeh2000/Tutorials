## 2.2. Variable windows: longest and shortest

### 1) **Expand right, shrink left**

**Definition** — the variable-window loop: extend right one step, then shrink left *while the window is valid* (or invalid, by problem shape) — each pointer monotonic, total moves ≤ `2n`. Longest-substring-without-repeats: track last-seen indices, jump left past duplicates, record the max — verified `abcabcbb → 3`, `bbb → 1`, empty → 0. The shrink condition is the algorithm: "while duplicate inside, advance left" — validity restored minimally, maximality preserved automatically.

- **What problem it solves**: optimal subarrays with *unknown size* defeat fixed windows (which size? trying all sizes nests to quadratic) and brute force enumerates `O(n²)` ranges. Variable windows find the optimum in one pass by exploiting monotonic validity: extending right can only gain (for longest-valid) or break (for shortest-containing) — and shrinking left restores the property minimally. One pass, both directions monotone, optimum recorded en route — no enumeration, no re-scanning.
- **Modern guidance** — template the loop (expand → update state → shrink-while → record) and vary only validity + recording: longest-valid (shrink while *invalid*, record max), shortest-containing (shrink while *valid*, record min — next section's probe). State validity as a boolean of window state ("no duplicates" via last-seen map; "contains all" via missing-count) — the shrink condition *is* the algorithm, and unstated validity is where window bugs live.

```javascript
// GOOD: expand-shrink-record — verified 3/1/0
function longestNoRepeat(s) {
  const last = new Map(); let st = 0, best = 0;   // validity: s[st..i] all distinct
  for (let i = 0; i < s.length; i++) {
    if (last.has(s[i]) && last.get(s[i]) >= st) st = last.get(s[i]) + 1;  // shrink past duplicate
    last.set(s[i], i);
    if (i - st + 1 > best) best = i - st + 1;     // record en route
  }
  return best;
} // O(n) time (each index visited twice max), O(min(n, alphabet)) space.
// BAD: all-starting-positions enumeration ("thorough") —
// O(n^2) ranges where one monotone pass suffices; thoroughness that bills quadratically
```

### 2) **Count valid, then contract**

**Definition** — the shortest-containing variant (minimum window substring): expand right counting coverage (`missing` tracks unsatisfied demand), and *while coverage holds*, contract left recording each valid window (the last valid before breaking is the minimal for that right edge). Verified: `ADOBECODEBANC`/`ABC` → `BANC`, single `a`/`a` → `a`, impossible `a`/`aa` → `""`. The `missing` counter (demand minus supply, negatives allowed for surplus) makes validity `O(1)`-testable per step — no map-scanning inside the loop.

- **Why it matters (correctness)**: shortest-containing inverts the longest-valid loop (shrink-while-*valid* vs shrink-while-*invalid*), and the inversion confuses memorized templates — candidates shrink the wrong direction, record at the wrong moment, or test validity by rescanning (`O(n)` check inside `O(n)` loop → silent quadratic). The `missing` counter is the discipline: validity as arithmetic (zero means covered), contraction as the recording loop (every valid window examined, minima kept). Correctness flows from the counter, not from loop-shape memory.
- **Modern guidance** — implement coverage as counters (`missing` for demand, frequency maps for supply — negatives encode surplus, never separate branches). Record *inside* the contract loop (every valid window is a candidate — the minimum hides among them, not at loop end). Handle impossibility explicitly (`""` — verified — not `null`, not exception: the honest empty answer). Test the inversion pair together (longest + shortest on the same session — the contrast teaches more than either alone).

```javascript
// GOOD: validity as arithmetic — verified BANC/a/""
function minWindow(s, t) {
  const need = new Map(); for (const c of t) need.set(c, (need.get(c) || 0) + 1);
  let missing = t.length, l = 0, best = null;   // validity: missing === 0
  for (let r = 0; r < s.length; r++) {
    if (need.has(s[r])) { if (need.get(s[r]) > 0) missing--; need.set(s[r], need.get(s[r]) - 1); }
    while (missing === 0) {                      // contract while valid, recording each
      if (!best || r - l < best[1] - best[0]) best = [l, r];
      const c = s[l]; if (need.has(c)) { need.set(c, need.get(c) + 1); if (need.get(c) > 0) missing++; } l++;
    }
  }
  return best ? s.slice(best[0], best[1] + 1) : "";
} // O(n+m) time, O(alphabet) space. Surplus via negatives — no special cases.
// BAD: validity by full-map scan per step ("clearer") —
// O(alphabet) check x O(n) steps = O(n*alphabet); arithmetic validity is O(1) and clearer once learned
```

### 3) **Monotonicity is the admission ticket**

**Definition** — windows apply iff validity decides *monotonically* as the window grows: for longest-valid problems, extending right preserves invalidity (once invalid, larger stays invalid — shrinking is the only repair); for shortest-containing, extending right preserves validity (once covered, larger stays covered — contracting is safe). If growing the window can *flip validity either way* (e.g., "subarray with sum exactly K" admitting negatives — extending may fix or break arbitrarily), the shrink loop has no sound direction — windows don't apply, and prefix-sums/hashmaps ([Domain 04/1.2](<../../../04 Hashing Trees and Heaps/sections/1. Hashing/1.2. Prefix sums and frequency patterns.md>) do.

- **Why it hurts when missing (correctness, maintainability)**: misapplied windows produce confident wrong answers on exactly the inputs tests skip — negative numbers in "exact sum" windows (shrinking assumes monotonic sums; negatives break the assumption silently), non-monotone predicates with shrink loops (validity flips unpredictably; the recorded "optimum" is whatever the loop happened to keep). The failure is silent-value (an answer, not an error) and distribution-dependent (passes positives-only tests). Admission criteria aren't pedantry — they're the soundness proof.
- **Modern guidance** — check monotonicity before windowing ("does growing preserve the relevant validity direction?"): nonnegatives for sum-windows (yes), distinctness for longest-unique (yes — duplicates only accumulate), exact-sum with negatives (no — prefix-map instead), at-most-K distinct (yes — counts only grow). Write the monotonicity as a comment ("growing preserves invalidity → shrink-only repair sound") — the one line that separates applicable from misapplied. When in doubt, counterexample-hunt with negatives and zeros before coding.

```javascript
// GOOD: admission checked — monotonicity stated, alternatives routed
// longest-unique: duplicates accumulate with growth -> shrinking repairs soundly. WINDOW APPLIES.
// exact-sum-K with negatives: growth may fix OR break -> no sound shrink direction -> PREFIX-MAP (Domain 04 leaf 1.2, live link below).
// at-most-K-distinct: distinct count grows monotonically -> shrink-while-over sound. WINDOW APPLIES.
// BAD: sliding windows on exact-sum-with-negatives because "windows are O(n)" —
// O(n) wrong answers; the admission ticket was checked never
```

### 4) **Common confusion**

- "Variable windows are `O(n²)` (nested loops)" — left monotonicity bounds total moves at `2n` (leaf 2.1's aggregate proof, reused). Nesting without monotonicity analysis miscounts every window.
- "Longest and shortest use the same loop" — inverted shrink conditions (while-invalid vs while-valid) and inverted recording (max vs min). Same skeleton, opposite decisions — memorize the skeleton, derive the decisions from validity.
- "Windows beat prefix sums generally" — windows win streaming single-pass scenarios; prefix sums win arbitrary offline range queries. Pick by query pattern (leaf 2.1), not by familiarity.
- "Empty/impossible inputs are edge trivia" — verified `""` and `0` probes catch seeding and validity bugs the happy path hides. Impossible-input behavior is specified, not improvised.

### 5) **Performance note**

Variable windows cost ≤ `2n` pointer moves + `O(1)` validity arithmetic per step (verified probes run in single-digit milliseconds at these sizes) with `O(alphabet)` auxiliary (frequency structures — bounded by charset, not input). Naive enumeration costs `O(n²)` ranges × `O(n)` validity checks (cubic worst with naive validity — the gap windows close is *two* rungs, not one). Optimize validity arithmetic first (`missing` counters over map scans), pointer discipline second (monotonicity is structural — no tuning available, none needed).

### 6) **Mentor note**

Teach the inversion pair together (longest/shortest side by side — same skeleton, opposite shrink/record; the contrast teaches validity-driven derivation over template memory). Demand validity booleans before code ("what makes a window valid here? how is it tested in O(1)?"). Admission-hunt with negatives as a group exercise ("which of these five problems admit windows?" — exact-sum-with-negatives must fail loudly). Watch for the template-memorizer (loops recalled, validity unstated — fix with "state validity first, code second") and the enumerator ("thorough" `O(n²)` ranges — fix with `2n`-movement arithmetic on their own sizes). Review check: validity boolean + `O(1)` test, shrink direction derived (not recalled), impossible inputs specified, monotonicity admission argued where non-obvious.
