## 2.1. Fixed windows: sums in one pass

### 1) **Add one, drop one**

**Definition** — a fixed-size window slides by admitting the newcomer and evicting the exilee: `window += a[i] − a[i−k]` — each element enters once and exits once, so `n` elements cost `O(n)` additions instead of `k` per position (`O(n·k)` naive). Verified: max-sum-of-3 in `[2,1,5,1,3,2]` → 9 (window `5,1,3`) and all-negatives `[-4,-1,-5]` → −5 (initialization to first window, not zero — the bug the negative test catches).

- **What problem it solves**: recomputation prices overlap repeatedly — naive k-sums redo `k−1` shared additions per position (the overlapping work grows with `k`, so larger windows cost *more* per step under naivety). Sliding reuses the overlap structurally: consecutive windows differ by exactly two elements (one in, one out), so each position costs `O(1)` update. The technique converts repeated subarray queries from multiplicative to additive — windows as running state, not recomputed ranges.
- **Modern guidance** — reach for fixed windows on contiguous-subarray-of-size-k questions (sums, averages, extrema with deques — leaf 3.1, character counts with frequency maps). Initialize from the first window (never zero — negatives expose the bug instantly, as the verified probe shows). State the window meaning before code ("window = sum of `a[i−k+1..i]`") — the invariant that makes add-one-drop-one obviously correct.

```javascript
// GOOD: overlap reused structurally — verified 9 and -5
function maxSumK(a, k) {
  let w = 0;
  for (let i = 0; i < k; i++) w += a[i];   // first window: the seed (initializing to 0 breaks negatives)
  let best = w;
  for (let i = k; i < a.length; i++) {     // window = sum of a[i-k+1..i], always
    w += a[i] - a[i - k];                  // admit newcomer, evict exilee: O(1) per position
    if (w > best) best = w;
  }
  return best;
} // O(n) time (2n additions), O(1) space. Naive recompute: O(n*k).
// BAD: slice-and-reduce per position ("readable") —
// k additions x n positions = O(n*k); readability that bills multiplicatively
```

### 2) **Windows amortize to linear**

**Definition** — both window pointers move monotonically (right advances `n` steps; left advances ≤ `n` steps — never retreats), so total pointer movement is ≤ `2n` regardless of per-step behavior: `O(n)` by aggregate analysis (Domain 01 §2.1's method wearing work clothes). Fixed windows move both in lockstep (exactly `n` each); variable windows (next leaf) move left at most as often as right advances — the same ≤ `2n` bound covers both. Amortization here needs no banking argument — monotonicity *is* the proof.

- **Why it matters (correctness)**: per-step analysis misprices windows ("inner while loop → nested → quadratic?" — the Domain 01 §2.1 eyeballing trap in new clothes). The inner shrink loop *looks* nested but left never retreats — total left-moves across the run bounded by right-moves. Engineers who count nesting without monotonicity "optimize" linear windows into complexity; engineers who see monotonicity prove linearity in one sentence. The aggregate view (total movement ÷ positions) is the analysis; the nested view is the illusion.
- **Modern guidance** — prove linearity by monotonicity ("each index enters once, exits once — `2n` moves total"), never by staring at nesting depth. State the movement bound in review ("left advances ≤ right advances — total `O(n)`"). When pointers *can* retreat (non-monotone variants — expanding search, backtracking), the bound breaks — name the retreat explicitly and re-analyze (those belong to [Domain 06's backtracking](<../../../06 Dynamic Programming Greedy and Backtracking/sections/3. Greedy and backtracking/3.2. Backtracking with pruning.md>), where retreat is the technique).

```javascript
// GOOD: monotonicity as the linearity proof (stated, not hoped)
// right: 0 -> n (n advances). left: 0 -> <=n (never retreats). Total moves <= 2n -> O(n).
// The inner while (next leaf's shrinker) runs O(n) TOTAL across the run, not per position.
// BAD: "nested loop, must be O(n^2)" from shape alone —
// nesting without monotonicity analysis miscounts every window ever written
```

### 3) **Fixed size, fixed discipline**

**Definition** — fixed windows carry three disciplines: seed from the first window (zero-initialization corrupts negatives — verified), update by exchange (admit + evict atomically — partial updates desync the window silently), and size-guard the edges (`k > n` → defined behavior: whole-array answer or explicit error, never undefined indexing). The window invariant ("window ≡ aggregate of current range") holds at every step or the technique is just arithmetic with confidence issues.

- **Why it hurts when missing (correctness, maintainability)**: window bugs are silent-value bugs (wrong sum, not crashes — off-by-one admission windows include `k+1` elements; zero-seeding poisons negatives; edge `k > n` reads `undefined` → `NaN` propagation). Each passes positive-case tests and fails the cases tests forgot. The disciplines convert testing luck into structural guarantees: seed-right (negatives safe), exchange-atomic (sync guaranteed), edge-defined (no undefined behavior, literally).
- **Modern guidance** — write the invariant as a comment (`// window = sum(a[i-k+1..i])`), seed explicitly from data (first window, never constants), exchange in one statement where the language allows (`w += a[i] − a[i−k]` — admission and eviction visibly paired), and decide `k > n` up front (return whole-array aggregate or throw — documented, tested). Test the discipline matrix: negatives, `k = 1`, `k = n`, `k > n`, empty — five cases, all the classic bugs.

```javascript
// GOOD: disciplines visible — invariant, seed, exchange, edges
function avgK(a, k) {
  if (k <= 0) throw new RangeError("k must be positive");
  if (k >= a.length) return a.reduce((s, x) => s + x, 0) / a.length; // edge defined, tested
  // ... seed-first-window + atomic exchange as above ...
}
// BAD: zero-seeded, unguarded, invariant-unstated windows —
// correct on positive tests, NaN on negatives, undefined on edges: three silent failures, one function
```

### 4) **Common confusion**

- "Windows need extra space for the elements" — fixed windows keep the *aggregate* (sum/count), not the elements: `O(1)` space. Storing the window contents is the beginner implementation (and the `O(k)` space the analysis should have flagged).
- "Sliding beats prefix sums" — prefix sums answer *arbitrary* range queries in `O(1)` after `O(n)` preprocessing (overlapping/non-uniform windows, offline queries); sliding wins *streaming* single-pass scenarios. Different tools: preprocessed random access vs online running state.
- "Variable windows are just flexible fixed windows" — variable windows add the shrink-while-valid loop and its monotonicity proof (next leaf) — a second mechanism, not a parameter change. Fixed first, variable second, in learning and in derivation.
- "Amortized means average here" — monotonicity gives a *worst-case* `2n` bound (Domain 01 §2.1's aggregate method), not a distributional average. Stronger claim, same proof shape.

### 5) **Performance note**

Fixed windows cost `2n` arithmetic ops with `O(1)` space and perfect stride-1 access (prefetch-optimal — the hardware's favorite loop shape after raw scans). Naive recomputation costs `n·k` (the gap widens with `k` — windows win *more* where naivety costs most). Prefix sums cost `n` preprocessing + `O(1)`/query (better for many arbitrary queries; worse for single streaming passes — pick by query pattern, not habit).

### 6) **Mentor note**

Teach exchange with the overlap drawn (two consecutive windows, shared middle shaded — "what *actually* changes?" → two elements, always). Drill the negative test first (seed bugs die on first contact with negatives — the probe `[−4,−1,−5] → −5` converts skeptics). Demand the invariant comment before accepting window code ("window ≡ ?" — unstated invariants are where silent-value bugs breed). Watch for the recomputer ("slice+reduce per position, readable" — fix with `n·k` arithmetic on their own sizes) and the nester-counter ("nested loop → quadratic" — fix with monotonicity proof on the spot). Review check: invariant stated, seed from data, exchange atomic, edges defined and tested, monotonicity argued for linearity.
