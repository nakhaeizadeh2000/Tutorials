## 4.1. Linear-techniques checklist (habits mentors insist on)

### 1) **Structure first, pointers second**

**Definition** — the pattern follows the structure's guarantees: sorted → converge (elimination valid); prefix-decidable → chase (reader/writer contracts); monotone validity → windows (shrink direction sound); nested/dominance queries → monotone stacks; repetitive text → KMP/Rabin-Karp. Choosing pointers before confirming structure produces confident wrong answers (leaf 1.1's unsorted-convergence silence, leaf 2.2's non-monotone windows). Structure is the admission ticket; pointers are the vehicle.

- **What problem it solves**: pattern-first selection memorizes shapes without preconditions — two pointers "for pair problems" applied to unsorted data, windows "for subarrays" applied to non-monotone predicates, stacks "for next-greater" without equal-policy. Each misfires silently (answers, not errors). Structure-first inverts the flow: name the guarantee (sorted? monotone? nested?), then the pattern follows by derivation — and code review checks the guarantee instead of the shape.
- **Modern guidance** — ask "what structure does this input promise?" before "which pattern do I use?" (sortedness, monotonicity, nesting, repetitiveness — the four admissions of this domain). Document the answer beside the pattern ("sorted ascending — convergence sound" — one line that prevents unsorted reuse). When no structure promises anything, say so explicitly (brute force honestly priced, or hash/DP alternatives from Domains 04/06 — no pattern masquerading).

```javascript
// GOOD: guarantee named, pattern derived
// input sorted ascending (verified precondition) -> converge (elimination sound).
// longest-unique: duplicates accumulate monotonically -> variable window (shrink sound).
// single-pattern stream, guarantees needed -> KMP (no-rescan sound).
// BAD: "two pointers for pair problems" as the whole decision procedure —
// shapes without preconditions misfire silently on unstructured input
```

### 2) **State the invariant before the loop**

**Definition** — every technique in this domain carries an invariant (window ≡ aggregate of current range; stack decreasing awaiting answers; answer in `[lo,hi)`; tortoise-hare distance relationship) — stated as a comment before the loop, verified against every update. Bugs live where invariants go unstated: desynced windows, violated monotonicity, lost tortoise leads. The invariant is the contract the code proves line by line; unstated contracts get broken lines.

- **Why it matters (correctness)**: invariant-first converts debugging from archaeology into checking (which update broke the stated truth?) and review from reading into verification (does each branch preserve it?). Teams that state invariants catch desyncs in review; teams that don't catch them in production value-errors. The cost is one comment per loop; the payoff is every silent-value bug class this domain documents.
- **Modern guidance** — write the invariant before the loop (comment first, code second — the order that forces derivation over improvisation). Check each branch against it during review ("does this advance preserve window-meaning?"). Test invariant edges explicitly (empty windows, single elements, all-equal runs, impossible inputs — the verified matrices across leaves 2.1–3.2). When an invariant can't be stated crisply, the technique is wrong for the problem — back up to structure-first.

```javascript
// GOOD: contract before code — the invariant reviewers verify
// window = sum of a[i-k+1..i], always. (leaf 2.1)
// stack decreasing; top is nearest unresolved smaller-or-equal. (leaf 3.1)
// answer (first >= t) in [lo, hi); a[0..lo) < t. (Domain 02 §3.1)
// BAD: pointer code with no stated meaning ("l and r move toward each other") —
// movement described, meaning absent; correctness uncheckable by construction
```

### 3) **Amortize explicitly**

**Definition** — linearity proofs stated per technique (each index enters/exits once: windows ≤ `2n` moves; each element pushed/popped once: stacks ≤ `2n` ops; text pointer monotone: KMP ≤ `2n` steps; convergence discards ≥1 index/step: ≤ `n` steps). "Amortized" named with its mechanism (monotonicity, geometric prepayment, elimination) — never as a bare adjective. Reviewers check the mechanism; the word alone proves nothing (Domain 01 §2.1's discipline, applied four times across this domain).

- **Why it hurts when missing (correctness, maintainability)**: unproven "linear" claims hide quadratics (nested loops without monotonicity — the eyeballing trap, Domain 01 §2.1; `shift()`-based deques billing `O(n)` per slide — leaf 3.1's tax; validity rescans inside window loops — leaf 2.2's arithmetic lesson). Each passes small tests (constants hide scaling) and bills at production sizes. Explicit amortization (mechanism + bound) catches all three in review — the proof is the performance test that runs before code ships.
- **Modern guidance** — state mechanism + bound for every linearity claim ("left never retreats → ≤ `2n` moves → `O(n)`" — one sentence, checkable). Audit hidden linear factors inside "linear" loops (`includes`/`indexOf`/`shift`/full scans — Domain 01 §2.1's trap, recurring). Re-verify at 10× growth (monotonicity holds structurally — the proof scales; constants don't — re-measure per Domain 01 §3.1). The expert habit: every `O(n)` claim in review gets "by what mechanism?" — answered in one sentence or sent back.

```bash
# GOOD: mechanism + bound, per technique (review-ready one-liners)
#  windows:  monotonic pointers -> <= 2n moves -> O(n).
#  stacks:   push+pop once each  -> <= 2n ops  -> O(n).
#  KMP:      monotone text ptr   -> <= 2n steps -> O(n+m).
#  converge: >= 1 index/step discarded -> <= n steps -> O(n).
# BAD: "it's O(n), trust me" without mechanism —
# unmechanized linearity is where hidden quadratics (shift, rescan, retreat) hide
```

### 4) **Common confusion**

- "Checklists replace technique fluency" — checklists *trigger* the right technique at the right moment (structure? invariant? amortization?). Fluency executes; checklists route. Both, in that order.
- "Small inputs don't need invariants" — small inputs need invariants *most* (tests pass without them — the bugs they hide surface at scale, far from the code). Invariants are cheapest when the loop is smallest.
- "Amortization analysis is overkill for interviews" — "each element moves at most twice" is a one-sentence answer that separates analyzers from memorizers. Underkill is the risk, not overkill.

### 5) **Performance note**

The checklist costs a minute per technique-use (structure named, invariant stated, mechanism argued) against silent-value incidents (wrong pairs, missed optima, desynced windows — hours of debugging answers that aren't errors). The highest-leverage item is invariant-first (converts debugging to checking); the second is admission-first (prevents silent wrongness entirely). Minutes preventing incidents — linear techniques' best attention rate.

### 6) **Mentor note**

Convert this leaf into the domain's application runbook: structure → invariant → amortization, in that order, every time. Quiz juniors on routing ("which question fires for nested queries? for repetitive text? for rank queries?") until answers are environmental. Watch for checklist decay (patterns applied without preconditions under deadline — fix with "requires:" comments as review-blocking) and mechanism-free linearity claims ("O(n), trust me" — fix with "by what mechanism?" as the reflexive follow-up). Review check: structure documented, invariants stated, amortization mechanized — and the mentor's own code modeling all three visibly.
