## 3.2. String matching without the naive scan

### 1) **Naive matching is quadratic**

**Definition** — slide the pattern along the text, comparing forward from each position, restarting at the next position on mismatch: `O(n·m)` worst-case (`n` positions × `m` comparisons — repetitive text forces near-full compares per position). Verified: 25 A's + B searched for 10 A's + B costs **176 comparisons** — each alignment matches 10 A's then fails on B, rescanning the same A's seventeen times. Correct, simple, and quadratic exactly where text repeats (logs, DNA, generated content — the inputs that matter).

- **What problem it solves**: nothing — naive matching is the *baseline*, and baselines exist to be beaten with understanding. Its value is pedagogical (the failure shape teaches what "never re-scan" must mean) and practical-at-small (short patterns on short texts: constants beat machinery below hundreds of characters — know when to stop optimizing). Every serious matcher is best understood as "naive, minus the rescanning" — the baseline frames all three successors.
- **Modern guidance** — ship naive below ~100 characters of text (clarity wins; `String.prototype.includes`/`indexOf` are engine-optimized C++ doing exactly this with SIMD assist — verified-fast without your help). Reach past it when repetitive text meets long patterns (the verified 176-comparison shape at toy sizes extrapolates to millions of wasted compares in logs). Never hand-roll "optimized naive" (skip tables without theory — that's Boyer-Moore done badly; either commit to a real algorithm or stay naive-and-honest).

```javascript
// GOOD: the baseline, honestly priced — verified 176 comps on 26-char text
function naiveSearch(t, p) {
  const out = [];
  for (let i = 0; i <= t.length - p.length; i++) {
    let j = 0;
    while (j < p.length && t[i + j] === p[j]) j++;
    if (j === p.length) out.push(i);   // 17 alignments x ~10 compares on A*25+B (verified 176)
  }
  return out;
} // O(n*m) worst, O(n+m) best (early mismatch). Correct; rescans relentlessly.
// BAD: "optimized" naive with ad-hoc skips ("jump 2 on mismatch") —
// unsound skips miss matches silently; sound skips ARE KMP/Boyer-Moore (below), done properly
```

### 2) **KMP prefixes never re-scan**

**Definition** — Knuth-Morris-Pratt preprocesses the *pattern* into a prefix table (longest proper prefix that's also a suffix, per position — verified `[0,0,1,2,3,0,1]` for the probe pattern): on mismatch, the table says how far the pattern can slide *without rechecking text* (matched prefix's border reattaches — text pointer never retreats). Verified search: classic text finds the pattern at index **10** in **23 comparisons** (vs naive's 176-shape on far smaller input) — `O(n+m)` guaranteed: table `O(m)`, scan `O(n)`, text pointer monotone (leaves 2.1–2.2's method, fourth appearance).

- **Why it matters (correctness)**: KMP's guarantee is input-independent (no bad cases — repetitive text, the naive killer, is KMP's comfort zone: borders are longest exactly there). The table *is* the algorithm's memory of partial matches — failure links encode "given what matched so far, what's the longest prefix still viable?" Once built, scanning never reconsiders a text character (each advances or triggers a table jump — total `2n` operations, the familiar amortization). Predictability, not just speed, is the deliverable.
- **Modern guidance** — reach for KMP on single-pattern streaming search (logs, network inspection — `O(m)` table fits anywhere, text passes once, guaranteed ceiling). Build the table with the standard loop (verified values as test oracle: `[0,0,1,2,3,0,1]` — any implementation must reproduce it). Prefer engine builtins for one-off searches (`indexOf` — SIMD-assisted naive beats KMP constants below large sizes); prefer KMP where guarantees matter (real-time inspection, adversarial inputs, worst-case SLAs). Multi-pattern needs Aho-Corasick (tries + failure links — Domain 04's trie leaf owns it; KMP is its single-pattern ancestor).

```javascript
// GOOD: memory of partial matches — verified table + 23-comparison search
function kmpTable(p) {
  const t = [0];
  for (let i = 1, j = 0; i < p.length; i++) {
    while (j > 0 && p[i] !== p[j]) j = t[j - 1];  // follow failure links (never rescan text later)
    if (p[i] === p[j]) j++;
    t[i] = j;
  }
  return t;  // probe pattern -> [0,0,1,2,3,0,1] verified. O(m) time, O(m) space.
}
// search: text pointer monotone, mismatches jump via table -> match at 10 in 23 comps (verified).
// BAD: rebuilding the table per search call ("stateless design") —
// O(m) preprocessing amortizes over the scan; rebuilding per call bills it every time
```

### 3) **Rabin-Karp hashes the window**

**Definition** — rolling hash turns window compares into arithmetic: hash the pattern once, hash the first text window, then *roll* (`new = ((old − out·B^(m−1))·B + in) mod M` — `O(1)` per slide, verified recurrence in the probe). Equal hashes → verify by direct compare (collisions possible — the hash proposes, the characters dispose); unequal → skip without comparing. Verified: finds the match at **[10]** identically to KMP. Average `O(n+m)` (hash rolls + rare verifications); worst `O(n·m)` adversarial (crafted collisions force verification everywhere — hash DoS, the security footnote).

- **Why it hurts when missing (correctness, maintainability)**: teams needing *multi-pattern* or *plagiarism-scale* search reinvent per-pattern scanning (KMP × patterns — linear in pattern count) where rolling hash shines (one text pass, many pattern hashes — average-case scaling with the pattern set, not against it). Conversely, single-pattern users adopt Rabin-Karp for its fame and inherit collision handling + modulus bugs for gains KMP delivers deterministically. The algorithm follows the workload: one pattern → KMP (guaranteed); many patterns → Rabin-Karp/Aho-Corasick (amortized); one-off → builtins.
- **Modern guidance** — use Rabin-Karp for multi-pattern average-case search (document plagiarism, log-signature scanning — many hashes, one pass). Choose large moduli (2⁶⁴ natural overflow or 10⁹+7 — collision rarity is load-bearing; toy moduli collide in demos). Always verify hits by compare (hash equality ≠ match — the verification line is correctness, not paranoia). Treat adversarial-collision risk explicitly (secret seed or KMP fallback where attackers craft inputs — average-case algorithms need threat models, Domain 01 §1.2's distribution honesty applied).

```javascript
// GOOD: arithmetic sliding, verified hits, compare-on-match — verified [10]
// rolling: hw = ((hw - out*P + M) * B + in) % M  (O(1) per slide; M = 1000000007, B = 257)
// equal hash -> t.slice(i, i+m) === p (verify!); unequal -> skip (no character touched).
// Average O(n+m); worst O(n*m) adversarial (forced verifications) — threat-model the input.
// BAD: hash-match returned as found ("collisions are rare") —
// rare is not never; the compare line is one statement — skip it and ship probabilistic correctness
```

### 4) **Common confusion**

- "KMP is always faster than naive" — faster *asymptotically*; engine builtins (SIMD naive) win small (constants dominate below hundreds of chars). Guarantees vs speed: KMP promises the ceiling, builtins win the sprint.
- "The prefix table is wasted preprocessing" — `O(m)` table amortizes over the `O(n)` scan (and over *repeated* scans with table reuse — preprocess once, search many texts). Preprocessing is investment with guaranteed returns, not overhead.
- "Rolling hashes never collide in practice" — collisions are rare per compare but *certain* across billions of windows at weak moduli (birthday math doesn't negotiate). Verify-on-hit is the entire correctness story.
- "String matching needs no analysis" — `n·m` vs `n+m` decides log pipelines (verified 176 vs 23 at toy sizes — extrapolate to 10GB). Matching is where ladder budgeting (Domain 01 §1.1) meets production volume most directly.

### 5) **Performance note**

Naive bills `n·m` worst (verified 176 on 26 chars — scales to billions on logs); KMP bills `n+m` always (verified 23 — table `m` once, scan `n` monotone); Rabin-Karp bills `n+m` average (rolls + rare verifies) with modulus-sized constants. Builtin `indexOf` beats all three below ~100 chars (SIMD constants) — crossover measured per engine, not derived. Optimize selection first (workload → algorithm: one-off/streaming/multi-pattern), constants second (moduli, table reuse, builtin thresholds).

### 6) **Mentor note**

Teach rescanning pain first (run the verified 176 vs 23 side by side — "same answer, 8× the work at 26 characters" extrapolates itself). Build the prefix table by hand on the board (borders discovered, not received — `[0,0,1,2,3,0,1]` as class exercise with the probe as oracle). Derive rolling recurrence together (window overlap arithmetic — same exchange idea as leaf 2.1's add-drop, now multiplicative). Watch for the premature-KMP ("always KMP" — fix with builtin-crossover measurement) and the unverified-hasher (hash-equals-found — fix with one crafted collision demo). Review check: algorithm matched to workload (one-off/streaming/multi), table values tested against oracle, hits verified by compare, moduli justified, crossover acknowledged.
