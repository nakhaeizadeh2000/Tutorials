## 3.1. Monotonic stacks and queue discipline

### 1) **Next-greater in one pass**

**Definition** — a *monotonic* stack keeps candidates in sorted order (decreasing for next-greater): each new element pops all smaller stack-tops (their answer is *now* — the current element), then pushes itself. Verified: `[4,1,2,5,3]` → `[5,2,5,−1,−1]` — each element pushed once, popped once: `O(n)` total stack operations (amortization by monotonicity, leaves 2.1–2.2's method again). The naive nested scan (`O(n²)` forward looks per element) never sees that each comparison resolves *two* elements (the popper's answer pending, the popped's answer found).

- **What problem it solves**: "next X to the right satisfying P" appears everywhere (greater/smaller/warmer-days/stock-spans/histogram rectangles) and naive forward scanning re-walks the same elements per query — quadratic on monotone inputs (decreasing array: every element scans to the end finding nothing). The monotonic stack converts repeated scanning into single-pass resolution: elements wait on the stack in the order future queries need, and each arrival resolves exactly those it dominates. Waiting structured beats searching repeated.
- **Modern guidance** — reach for monotone stacks on next/previous greater/smaller queries (direction × comparison = four variants, one pattern — flip traversal and comparator, never re-derive). Maintain the invariant explicitly ("stack decreasing — top is the nearest unresolved smaller-or-equal") and pop-while-violated before pushing (the pop loop *is* the resolution step). Equal-element policy decided up front (pop on `≤` vs `<` — determines first-vs-last occurrence semantics; state it, test duplicates).

```javascript
// GOOD: resolution by arrival — verified [5,2,5,-1,-1]
function nextGreater(a) {
  const r = new Array(a.length).fill(-1), st = [];  // invariant: st decreasing, awaiting answers
  for (let i = 0; i < a.length; i++) {
    while (st.length && a[i] > a[st[st.length - 1]]) r[st.pop()] = a[i];  // arrival resolves all dominated
    st.push(i);
  }
  return r;
} // O(n) time (push+pop once each), O(n) space (stack). Naive nested: O(n^2) on decreasing input.
// BAD: forward scan per element ("direct") —
// re-walks unresolved suffixes per query; quadratic exactly where the stack is linear
```

### 2) **Queues order, deques slide**

**Definition** — queues (FIFO) order processing (BFS preview — Domain 05 traverses level by level through a queue); double-ended queues (push/pop both ends) slide extrema: sliding-window maximum keeps *candidate indices* in decreasing value order, evicting out-of-window fronts and dominated backs — verified `[1,3,−1,−3,5,3,6,7],k=3` → `[3,3,5,5,6,7]`. Each index enters/exits once: `O(n)` total (monotonicity amortization, third appearance — the method generalizes). Heaps also answer window extrema (`O(n log k)`) — deques win by exploiting the slide (expiry ordered by position, dominance by value — two orders, one structure).

- **Why it matters (correctness)**: window extrema without deques cost a heap per window (`n log k` — fine) or a rescan per window (`n·k` — the naive trap, quadratic in disguise). The deque's double-endedness encodes both eviction rules (front: too old; back: never maximal while the newcomer stands) in `O(1)` amortized operations — the rare structure whose API *is* the algorithm. Misuse (plain queue for extrema — rescans; heap where slide suffices — log factor donated) is the performance bug that passes every test and bills at scale.
- **Modern guidance** — use deques for sliding-window extrema/minima (both ends working: front expires, back dominates); heaps for *global* top-k and merging (Domain 04 — no positional expiry); plain queues for ordering (BFS, task pipelines — FIFO semantics, never extrema). State both eviction rules in comments (age + dominance — the two invariants reviewers verify). JS has no stdlib deque — index-managed arrays serve (`head` pointer over `push`/`shift`... note `shift()` is `O(n)`: maintain head indices or accept small-`n` costs explicitly).

```javascript
// GOOD: both ends working — verified [3,3,5,5,6,7]
function slidingMax(a, k) {
  const dq = [], out = [];                       // dq: indices, values decreasing, in-window
  for (let i = 0; i < a.length; i++) {
    while (dq.length && a[dq[dq.length - 1]] <= a[i]) dq.pop();  // dominated: never maximal again
    dq.push(i);
    if (dq[0] <= i - k) dq.shift();              // expired: left the window (head-index in production)
    if (i >= k - 1) out.push(a[dq[0]]);          // front is the window maximum, always
  }
  return out;
} // O(n) total (each index pushed/popped once), O(k) space.
// BAD: heap per window ("general") — O(n log k) where O(n) applies;
// or rescan per window ("simple") — O(n*k), the naive trap in work clothes
```

### 3) **LIFO/FIFO as design tools**

**Definition** — stacks (LIFO) model nesting and reversal (parentheses matching — verified `()[]{}` true, `([)]` false, empty true, lone `(` false; call-stack simulation; undo histories; DFS preview), queues (FIFO) model fairness and ordering (BFS, pipelines, rate limiters). Choosing by *temporal semantics* (most-recent vs earliest) rather than by API familiarity converts structure selection from habit into design: nesting → stack, fairness → queue, both-ends → deque (previous section).

- **Why it hurts when missing (correctness, maintainability)**: structure mismatch corrupts order-sensitive logic silently — queue where stack belonged reverses nesting (mismatched closers accepted), stack where queue belonged starves early arrivals (BFS becomes DFS — traversal *order* wrong, results subtly reordered). The failure passes small tests (orders coincide on tiny inputs) and diverges at scale. Temporal semantics stated up front ("most-recent-first because nesting") prevent the entire class.
- **Modern guidance** — name the temporal need before the structure ("LIFO: closers match recent openers" → stack; "FIFO: levels complete before depth" → queue). Validate parentheses-style with the pop-compare one-liner (map closers to openers — mismatch or empty-stack-pop fails fast). Simulate recursion with explicit stacks past depth limits (Domain 01 §2.2's ~13,920 ceiling — the explicit stack trades hidden `RangeError` for visible heap). Document the choice per use ("stack: nesting semantics" — one line that prevents queue-substitution refactors).

```javascript
// GOOD: temporal semantics select the structure — verified true/false/true/false
function validParens(s) {
  const match = { ")": "(", "]": "[", "}": "{" }, st = [];
  for (const c of s) {
    if ("([{".includes(c)) st.push(c);              // LIFO: closers match RECENT openers (nesting)
    else if (st.pop() !== match[c]) return false;   // empty-pop (undefined) fails safely
  }
  return st.length === 0;
}
// BAD: counting openers vs closers ("balanced counts") —
// counts accept "([)]" (balanced, misnested); order needs a stack, not arithmetic
```

### 4) **Common confusion**

- "Monotonic stacks sort" — stacks *filter by dominance* (resolving queries), never reorder input. Sorting arranges; monotone stacks answer-while-scanning. Different operations sharing only the word "order."
- "`shift()` makes array-deques fine" — `shift()` is `O(n)` (reindexes the array — the deque that bills linearly per slide). Fine below thousands of ops; past that, head-index management or linked chunks. Know the tax before paying it at scale.
- "Stacks/queues are trivial, skip to graphs" — BFS/DFS *are* queue/stack disciplines on graphs (Domain 05); parentheses/call-simulation carry the same invariants. Trivial here means load-bearing there — the deja vu is the point.
- "Equal elements don't matter in monotone stacks" — the `≤` vs `<` pop policy decides first-vs-last occurrence semantics (verified probes use strict `>` — equals stay stacked). Undecided policy = unspecified answers on duplicates.

### 5) **Performance note**

Monotone passes cost `2n` stack ops (push+pop once each — linear with tiny constants, sequential-ish access); deque slides cost `2n` end-ops with `O(k)` space (indices, not values — half the memory of value-storing variants); parentheses validation costs `n` pushes/pops worst-case (`O(n)` stack on all-openers — bounded by input, freed on close). The `shift()` tax (`O(n)` per slide — array-deque honesty) dominates naive implementations past ~10⁴ slides: head indices or it didn't happen.

### 6) **Mentor note**

Teach dominance with the arrival narrative ("each newcomer resolves everyone it dominates — who waits, who falls?") and have juniors hand-run the verified example ([4,1,2,5,3] → pops traced). Teach deque duality by naming both evictions per line ("too old? too small?" — two questions, two ends). Drill parentheses as the LIFO acid test (counts-vs-stack on `([)]` converts counters permanently). Watch for the rescanner ("simple nested loops" — fix with `2n`-operation arithmetic) and the heap-default ("general" `n log k` where linear applies — fix with "what does the slide give you that the heap can't use?"). Review check: monotone invariant stated, equal-policy decided, eviction rules commented, `shift()` tax acknowledged or engineered away.
