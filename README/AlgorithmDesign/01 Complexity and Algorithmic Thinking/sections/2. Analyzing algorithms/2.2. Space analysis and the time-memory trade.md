## 2.2. Space analysis and the time-memory trade

### 1) **Auxiliary vs total space**

**Definition** — *total* space counts everything (input included); *auxiliary* space counts only the extra your algorithm allocates — and auxiliary is the quoted bound, because input size isn't your design choice. In-place algorithms use `O(1)` auxiliary (a few scalars beside the input); copying algorithms use `O(n)` (a second array, a table, a buffer). Stating which one you mean is half the analysis: "`O(n)` space" for an algorithm handed an `n`-element input says nothing unless auxiliary-vs-total is explicit.

- **What problem it solves**: space discussions without the distinction mislead twice — copying algorithms look free ("it's just one more array" — doubling memory on a 10GB dataset is not "just"), and in-place algorithms look cramped (their constant-scratch discipline reads as stinginess rather than the scalability feature it is). Naming auxiliary space makes memory a design input like time: budgeted, traded, and reviewed — instead of discovered via OOM at 3 AM.
- **Modern guidance** — quote auxiliary always ("`O(1)` auxiliary, `O(n)` total" — both numbers, no ambiguity). Prefer in-place for large inputs on constrained runtimes (embedded, edge, giant batch jobs); prefer clarity-copies for small inputs where memory is cheap and mutation bugs are expensive. The trade is contextual — the *statement* of both bounds is not.

```javascript
// GOOD: both bounds stated — the trade visible in the signature line
function reverseInPlace(xs) {  // O(1) auxiliary: two indices beside the input
  for (let i = 0, j = xs.length - 1; i < j; i++, j--) [xs[i], xs[j]] = [xs[j], xs[i]];
  return xs;
}
const reversedCopy = (xs) => [...xs].reverse();  // O(n) auxiliary: a second array (clarity for mutation-freedom)
// BAD: "reverse is O(n) space" — which reverse? auxiliary or total? (state both, always)
```

### 2) **Call stacks are space**

**Definition** — every live call frame occupies memory: recursion of depth `d` with frame size `f` costs `O(d·f)` auxiliary space — the elegant one-liner ships a hidden stack bill. Verified on Node v20.20.2 (V8, engine-dependent): unbounded self-recursion throws `RangeError` at depth ~13,920 — the stack is finite, and deep recursion finds its end. Naive Fibonacci recurses to depth `n` (`O(n)` stack) while recomputing exponentially (`O(2ⁿ)` time — leaf 2.1's ladder rung); memoized Fibonacci keeps depth `n` but adds a table of `n−1` entries (verified sizes: `n=10` → 9, `n=20` → 19, `n=30` → 29 — linear table, exactly).

- **Why it matters (correctness)**: stack bills arrive as crashes, not slowdowns — `RangeError: Maximum call stack size exceeded` in production on the input 10× larger than tests (depth scales with `n` exactly where testing stopped). And default recursion is the wrong tool past thousands of depth in JS (no tail-call optimization in V8 — the elegant recursive walk dies where the boring loop survives). Space analysis of recursion isn't academic: it's the difference between "works" and "RangeErrors on customer data."
- **Modern guidance** — price every recursion as depth × frame before shipping (log-depth divide-and-conquer: fine; linear-depth list/tree walks: convert past ~10⁴ expected depth or prove the bound). Prefer iteration for linear-depth traversals in JS (explicit stacks trade hidden `RangeError` risk for visible `O(n)` heap the GC manages). When recursion is the clearest expression (trees, backtracking — Domains 04/06), state the depth bound in the leaf and guard callers with input limits.

```javascript
// GOOD: depth priced, table counted — verified numbers
function fibMemo(n, memo = new Map()) {  // depth n (O(n) stack) + table n-1 entries (O(n) aux)
  if (n <= 1) return n;
  if (!memo.has(n)) memo.set(n, fibMemo(n - 1, memo) + fibMemo(n - 2, memo));
  return memo.get(n);
} // O(n) time (each subproblem once), O(n) aux (table n-1 verified: 9/19/29 for n=10/20/30).
// Depth ~13920 kills V8 (verified RangeError) — fibMemo(20000) dies on stack, not on table.
// BAD: naive fib recursion ("elegant") — O(2^n) time AND O(n) stack: worst of both axes, no memo table
```

### 3) **Trade deliberately, never accidentally**

**Definition** — memoization (tables trading memory for time), indexing (structures trading memory for queries), and streaming (recomputing trading time for memory) are the same transaction in different clothes: `O(memory)` buys `O(time)` or vice versa. Deliberate trading budgets both sides up front ("`O(n)` table buys `O(2ⁿ)→O(n)` time — worth it to `n=10⁵`" — the verified memo table above); accidental trading discovers one side in production (the "cache" that grows unbounded — a memory leak wearing an optimization costume).

- **Why it hurts when missing (correctness, maintainability)**: unbudgeted memoization is the classic memory incident — keys accumulate (user IDs, query strings, unbounded cardinality), the table outgrows the heap, and the "optimization" OOMs the service it was speeding up. Every cache needs an eviction story (LRU bound, TTL, weak references — Domain 04 owns the structures) *before* it needs entries. Time-bought-with-memory without a memory budget is a loan from the heap at predatory rates.
- **Modern guidance** — write the trade as an equation in the design note ("table `O(n)` entries × entry size vs recompute `O(2ⁿ)` — breakeven immediate, cap at …"). Bound every memo structure at creation (size cap, TTL, or weak keys — unbounded caches are bugs filed against the future). Revisit the trade when inputs grow 10× (the table that fit at 10⁴ rows OOMs at 10⁷ — trades expire with scale). The expert habit: every `Map` used as a cache gets its eviction policy in the same commit as its creation.

```javascript
// GOOD: the trade budgeted — table cost beside time saved, cap beside creation
const memo = new Map();                       // O(entries) aux — capped below, not "later"
function fibCapped(n) {
  if (n <= 1) return n;
  if (!memo.has(n)) {
    memo.set(n, fibCapped(n - 1) + fibCapped(n - 2));
    if (memo.size > 100000) { const k = memo.keys().next().value; memo.delete(k); } // eviction at birth
  }
  return memo.get(n);
}
// BAD: unbounded memo ("it only caches") —
// keys accumulate with input cardinality; the optimization OOMs the service it was speeding
```

### 4) **Common confusion**

- "Auxiliary space includes the input" — by definition it excludes it. Total includes; auxiliary is extra. Conflating them makes every algorithm "`O(n)` space" and the analysis content-free.
- "In-place means no extra memory" — in-place means `O(1)` *auxiliary* (a few scalars, indices, temps). Zero-scratch algorithms are vanishingly rare; constant-scratch is the actual standard.
- "Recursion depth doesn't matter in JS" — ~13,920 frames kills V8 (verified). Depth matters more in JS than in languages with TCO or segmented stacks — the elegant recursion is the riskiest one here.
- "Caches only help" — caches trade memory for time *and* add invalidation, staleness, and eviction obligations. Unbudgeted caches are memory incidents with good intentions.

### 5) **Performance note**

Space costs real money (heap per instance × fleet size) and real latency (GC pressure scales with allocation rate — the copying algorithm pays twice: memory *and* collector time). The verified table (29 entries for `n=30`) is bytes; the same shape at `n=10⁷` is hundreds of MB per call — multiply by concurrency and the trade needs re-pricing. Measure heap (`process.memoryUsage()`) alongside time (leaf 3.1's harness extends naturally) — time-only profiling approves memory incidents.

### 6) **Mentor note**

Teach the stack bill with the crash: run the depth probe live (~13,920 → `RangeError` lands harder than any warning), then convert one linear recursion to iteration together (visible heap replacing invisible stack). Teach memoization with the table sizes (9/19/29 — "who paid, in what currency?" is the question that makes trades deliberate). Watch for the stack-blind (recursion for everything — fix with mandatory depth bounds in review) and the unbounded-cacher (Map without eviction — fix with "eviction policy in the same commit"). Review check: every recursion states depth, every cache states its bound, every non-trivial function states auxiliary space beside time.
