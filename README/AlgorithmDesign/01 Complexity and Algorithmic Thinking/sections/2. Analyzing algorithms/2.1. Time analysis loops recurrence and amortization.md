## 2.1. Time analysis: loops, recurrence, and amortization

### 1) **Count the dominant operation**

**Definition** — time analysis counts repetitions of the dominant operation as a function of `n`: sequential blocks add, nested loops multiply, early exits and skips need case thinking (leaf 1.2). The triangular pair-loop runs `n(n−1)/2` inner iterations — verified exactly (`n=100` → 4950 = `100·99/2`) — which is `O(n²)`: the `/2` is a constant, scale erases it. Methodology: find what repeats most, express its count in `n`, dominate-and-name (leaf 1.1).

- **What problem it solves**: "looks linear" is how quadratics ship — the inner loop hides behind a helper call, a callback, or a innocuous `.includes()` inside a `.filter()` (two linear passes nested → `n²`, wearing linear clothes). Counting forces the structure visible: every nesting level is a multiplication, every hidden linear call inside a loop is a second factor. The engineers who count find the `n²` in review; the engineers who eyeball find it in the incident.
- **Modern guidance** — expand one level past comfort: inline the helper's cost, count the callback's complexity, price the "free" method (`indexOf`/`includes`/`splice` inside a loop each smuggle a factor of `n` — JavaScript 08 owns the method mechanics, this track prices their composition). State counts as formulas first (`n(n−1)/2`), bounds second (`O(n²)`) — the formula checks the bound, and reviewers can verify formulas.

```javascript
// GOOD: count, formula, bound — verified exact
function hasDuplicate(xs) {
  for (let i = 0; i < xs.length; i++)
    for (let j = i + 1; j < xs.length; j++)
      if (xs[i] === xs[j]) return true;   // inner runs n(n-1)/2 times worst-case (n=100 -> 4950)
  return false;
} // O(n^2) time, O(1) space. The early return helps the best case only (leaf 1.2).
// BAD: xs.filter(x => xs.includes(x)) "looks linear" —
// includes() is O(n) inside filter()'s O(n): n^2 in linear clothing (count the callback!)
```

### 2) **Recurrences describe divide-and-conquer**

**Definition** — recursive algorithms get recurrence relations: divide into `a` subproblems of size `n/b`, pay `f(n)` to combine → `T(n) = aT(n/b) + f(n)`. The canonical `T(n) = 2T(n/2) + O(n)` (halve twice, linear combine — merge sort's shape) unrolls level by level: each of the `log₂n` levels costs `n` → `O(n log n)`. Verified by direct evaluation: `T(1024) = 11264 = 1024·10 + 1024` exactly (`n·log₂n + n`). Unrolling once by hand (levels × cost-per-level) beats memorizing the Master theorem for every analysis you'll actually perform.

- **Why it matters (correctness)**: divide-and-conquer hides its cost in the recursion tree — the code shows one innocent recursive call (times two) plus a "linear" merge, and intuition prices it near-linear. The tree tells the truth: `log n` levels each doing `n` work is linearithmic, not linear, and that gap decides feasibility at 10⁷ inputs (leaf 1.1's ladder). Recursion also bills space (leaf 2.2): depth `log n` here, depth `n` for degenerate quicksort pivots — the same tree, the other axis.
- **Modern guidance** — draw the tree (levels × width × per-node cost) before reaching for theorems; unroll two levels on paper and the pattern generalizes. Learn the three shapes by recognition: halve-and-combine-linear → `n log n` (merge sort); halve-and-combine-constant → `log n` (binary search — Domain 02); shrink-by-one-and-combine-linear → `n²` (naive quicksort worst case, selection-style recursion — the degenerate the tree warns about). When the recurrence resists (uneven splits, floors), bound between friendly neighbors rather than solving exactly — bounds are the product, closed forms the luxury.

```javascript
// GOOD: the recurrence visible in code, the tree on paper
function mergeSort(xs) {
  if (xs.length <= 1) return xs;              // T(1) = O(1)
  const m = xs.length >> 1;
  const L = mergeSort(xs.slice(0, m));        // T(n/2)
  const R = mergeSort(xs.slice(m));           // T(n/2)
  return merge(L, R);                         // O(n) combine
} // T(n) = 2T(n/2) + O(n) -> O(n log n) time. (Space: O(n) aux + O(log n) stack -> leaf 2.2.)
// T(1024) = 11264 = n*log2(n) + n, verified by evaluation — levels (10) x cost-per-level (1024).
// BAD: "recursive, so O(log n)" —
// recursion depth is not the cost; levels x work-per-level is (depth log n with n work is n log n)
```

### 3) **Amortization averages over sequences**

**Definition** — amortized analysis bounds the *average cost per operation over a worst-case sequence*: occasional expensive operations spread across many cheap ones, with a hard guarantee (no distribution assumed — unlike average-case, leaf 1.2). The canonical dynamic-array push: mostly `O(1)`, but every doubling copies all `size` elements (`O(n)` that one time). Verified accounting: 1,000 pushes → 1,023 copies total (~1.02/push); 100,000 pushes → 131,071 copies (~1.31/push) — total copying stays under `2n`, so push is `O(1)` amortized: the expensive pushes are prepaid by the cheap ones geometrically (each doubling doubles the runway).

- **Why it hurts when missing (correctness, maintainability)**: per-operation worst-casing misprices resizable structures (`Array.push` "sometimes `O(n)`" → treated as linear → redesigns that fix nothing), while naive averaging *without* the guarantee misprices adversarial sequences (leaf 1.2's distribution trap in new clothes). Amortization threads the needle: a worst-case statement (holds for every sequence) about an average (per operation). The aggregate method (total over sequence ÷ length — the verified computation above) proves it in one division; the banker's method (each cheap op deposits credit for future copies) makes it intuitive.
- **Modern guidance** — reach for amortization when costs spike periodically by design (doubling arrays, hash table resizes, splay-style restructuring — Domain 04's hash story). Prove by aggregates (total copies `< 2n` → `O(1)` each — the verified numbers are the proof sketch) and explain by banking (each push pays 1 for itself + 1 toward the next doubling). Never quote amortized bounds where per-operation latency matters (real-time frames, request deadlines — the occasional `O(n)` spike *is* the incident there; amortized analysis answers throughput questions, not tail-latency ones).

```javascript
// GOOD: spikes prepaid geometrically — verified totals
// push costs: 1 each, plus full-copy at sizes 1,2,4,8,...: total copies for n pushes < 2n
// n=1000 -> 1023 copies (1.02/push); n=100000 -> 131071 (1.31/push). O(1) amortized, hard guarantee.
// Each cheap push "banks" credit covering its share of the next doubling (banker's view).
// BAD: "push is O(n) because resize copies everything" (worst-cases the operation, ignores the sequence)
//   or "push averages O(1)" (right number, no guarantee — amortization is the guarantee, not the average)
```

### 4) **Common confusion**

- "Recurrence solving needs the Master theorem" — unrolling (levels × cost) solves every recurrence you'll meet in practice; the theorem is a shortcut for exams, the tree is understanding for engineers.
- "Amortized `O(1)` means every op is fast" — most ops are fast; the guarantee is on the *sequence average*. Tail-latency budgets need per-op worst cases — different question, different bound.
- "Early `return` changes complexity" — early exits improve best/average cases only (leaf 1.2); worst-case analysis assumes the exit never fires. Price the input that runs the full loops.
- "Counting is obsolete — profilers exist" — profilers measure constants on fixed inputs (leaf 3.1); counting predicts scaling on future inputs. Complementary, not competing — count first, profile second.

### 5) **Performance note**

Analysis costs minutes and predicts across machines; profiling costs runs and predicts one machine. The verified probes above (pair counts, copy totals, recurrence evaluation) each ran in milliseconds — and their value is portable (formulas and ratios), unlike timings. Budget analysis time proportional to blast radius: hot-path and scale-critical code gets full trees and aggregates; glue code gets a rung estimate (leaf 1.1) and moves on.

### 6) **Mentor note**

Teach counting with hidden costs first: `filter`+`includes`, `splice`-in-loop, string concat in loops (quadratic via immutability — JavaScript 11 owns the string model, this track prices it). Then the tree: have juniors unroll `2T(n/2)+n` to three levels on paper before showing the closed form — the pattern discovered beats the theorem received. Then amortization via the verified copy totals (1.02/push, 1.31/push — "who paid for the copies?" is the question that teaches banking). Watch for the eyeballer ("looks linear" — fix with mandatory counting in review) and the theorem-reacher (Master theorem before tree — fix with "draw it first"). Review check: every non-trivial function carries time + space bounds with the dominant operation named; recurrences show the tree, amortized claims show the aggregate.
