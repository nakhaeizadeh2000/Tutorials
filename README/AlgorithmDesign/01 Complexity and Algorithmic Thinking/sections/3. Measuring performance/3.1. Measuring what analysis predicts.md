## 3.1. Measuring what analysis predicts

### 1) **Time with harnesses, not vibes**

**Definition** — a measurement harness separates signal from noise: warm up the JIT (untimed runs first — cold code measures the compiler, not the algorithm), repeat and average (per-op means over hundreds of runs), and isolate the operation (measure the loop, not the setup). One run is anecdote; a thousand runs is data. The harness below is the template every later domain reuses: `measure(fn, n, reps)` returns mean-ms-per-op, warmed and averaged.

- **What problem it solves**: naive timing lies fluently — cold-start JIT compilation dwarfs the algorithm (first run 10× slower), background GC pauses contaminate single runs, and tiny inputs measure timer granularity instead of work (the leaf 1.1 probe showed 4000 elements timing *faster* than 2000 — pure noise). Decisions made on vibes optimize the noise: "optimization" that warmed the cache, "regressions" that were GC pauses. Harnesses convert timing from storytelling into instrumentation.
- **Modern guidance** — warm up (5+ untimed runs — V8 optimizes hot code, and you want the optimized version timed), repeat (100+ reps for micro-ops, fewer for slow ones — total wall time ~seconds keeps the suite runnable), report per-op means with the harness attached (numbers without methodology are vibes with decimals). Keep benchmarks in the repo beside the algorithm (regression-detecting, CI-runnable — measurement that isn't repeated rots into folklore).

```javascript
// GOOD: warmed, averaged, per-op — the reusable harness (verified on Node v20.20.2)
function measure(fn, n, reps = 100) {
  for (let w = 0; w < 5; w++) fn(n);      // warmup: JIT compiles before timing starts
  const t0 = performance.now();
  for (let r = 0; r < reps; r++) fn(n);
  return (performance.now() - t0) / reps; // mean ms/op — noise averaged out
}
// BAD: console.time around one cold call on 500 elements —
// measures compilation + noise + timer granularity, attributes all three to the algorithm
```

### 2) **Confirm the curve, not the constant**

**Definition** — the doubling experiment: time at `n` and `2n` with the harness, and read the *ratio* — `~2×` means linear, `~4×` quadratic, `~2×+` linearithmic, `~1×` constant — regardless of absolute milliseconds. Verified textbook results: linear sum at 30k→60k ratio **2.01**; pairwise sum at 1200→2400 ratio **4.06**. The ratios confirm the rung; the milliseconds (machine-specific, expiring) confirm nothing portable. Analysis predicts the ratio; measurement checks it — the scientific loop in one division.

- **Why it matters (correctness)**: constants mislead in both directions — a fast machine makes quadratics look linear (until inputs double twice more), a slow machine makes linears look broken (until someone profiles the constant instead of the curve). Ratio thinking is scale-invariant: it asks "what happens when reality grows?" rather than "how fast is it here?" The engineer who confirms curves ships algorithms that survive growth; the engineer who records milliseconds ships surprises scheduled by input size.
- **Modern guidance** — run the doubling experiment for every complexity claim that matters (one script, two sizes, one ratio — minutes of work that audit the analysis). Expect approximate ratios (2.01 not 2.00, 4.06 not 4.00 — caches, GC, and turbo frequencies perturb; 3× where 4× predicted still confirms quadratic, 1.2× where 2× predicted refutes linear). When ratios disagree with analysis, trust neither blindly: re-derive (hidden factor?) and re-measure (methodology flaw?) — the disagreement is the most informative outcome the loop produces.

```javascript
// GOOD: one division audits the analysis — verified ratios
function ratio(fn, n, reps) { return measure(fn, 2 * n, reps) / measure(fn, n, reps); }
// linear sum:  ratio(lin, 30000, 100) = 2.01 (predict O(n) -> confirmed)
// pairwise:   ratio(qd, 1200, 10)    = 4.06 (predict O(n^2) -> confirmed)
// BAD: "linear sum takes 0.028ms" recorded as the performance fact —
// portable to no other machine, predictive of no other input size, expiring with this hardware
```

### 3) **Constants strike back in production**

**Definition** — the regimes where analysis underdetermines reality: small-`n` crossovers (insertion sort's `O(n²)` beats merge sort's `O(n log n)` below ~10–50 elements — less overhead per element, cache-friendly), hardware effects (cache lines, branch prediction, SIMD — constant-factor swings of 10–100× invisible to Big-O), and JIT realities (monomorphic shapes fast, megamorphic slow — same complexity, different machine code). Analysis ranks candidates; measurement picks winners *at your `n`, on your hardware*.

- **Why it hurts when missing (correctness, maintainability)**: curve-only thinking produces its own incidents — the `O(n log n)` library sort force-fitted where insertion's quadratic wins small (slower *and* more code), the "optimal" structure with pointer-chasing constants that loses to arrays at every real size (B-trees beat BSTs on disk for constants, not curves), the theoretically-linear algorithm with a 10MB-per-element constant. Production bills constants in latency and money; Big-O doesn't itemize them. The mature stance holds both: curves for scaling, constants for shipping.
- **Modern guidance** — hybridize at crossovers (merge sort → insertion below ~32 elements — every standard library does this; the leaf 1.1 ladder picks candidates, measurement sets the threshold), profile at production sizes (benchmark `n` you ship, not `n` that's convenient — convenient sizes hide constant dominance), and re-measure per platform (V8 vs JSC, server vs phone — constants move, curves don't). State both in performance notes: "linearithmic scaling, insertion below 32 (measured crossover on V8)" — the sentence future maintainers need.

```javascript
// GOOD: curves for scaling, constants for shipping — hybridize at measured crossovers
function sortSmall(xs) {
  return xs.length < 32 ? insertionSort(xs) : mergeSort(xs); // O(n^2) wins small (measured), O(n log n) wins large
} // threshold 32 measured on V8 (leaf: Domain 02) — re-measure per engine, state per note.
// BAD: "O(n log n) everywhere, theory says so" —
/// theory ranks growth; shipping pays constants — the crossover is empirical, not derivable
```

### 4) **Common confusion**

- "Benchmarks replace analysis" — benchmarks measure one machine at fixed sizes; analysis predicts all machines at all sizes. Replace analysis with benchmarks and every hardware refresh invalidates your performance knowledge.
- "Noisy benchmarks mean broken code" — noise means broken *methodology* (no warmup, single run, tiny input). Fix the harness (warm, repeat, scale up) before suspecting the algorithm — the leaf 1.1 inversion (4000 faster than 2000) was methodology, exonerated by warmup.
- "Ratio near-misses refute the analysis" — 3× where 4× predicted confirms quadratic (caches help large-n relatively); 2.5× where 2× predicted demands investigation (hidden factor or methodology). Read ratios with hardware literacy, not calculator literalism.
- "Microbenchmarks predict production" — microbenchmarks confirm *curves*; production adds I/O, contention, and GC pressure the harness excludes. Confirm scaling in micro, validate latency in situ.

### 5) **Performance note**

Harness cost is seconds per experiment (warmup + reps tuned to ~1–5s wall time — cheap enough to run per claim, expensive enough to average noise out). Doubling experiments double that. The cost that matters is *unmeasured* shipping: algorithms whose curves were never confirmed accumulate as scaling debt, payable with interest at input-growth time. Two minutes of harness per complexity claim is the cheapest insurance in performance engineering.

### 6) **Mentor note**

Run the doubling experiment live (2.01 and 4.06 landing in front of juniors converts ratio-thinking from slogan to reflex), then break it on purpose (cold single-run timings that invert — "4000 faster than 2000, explain?" — methodology debugging as a taught skill). Make harness-plus-ratio the review requirement for every performance claim ("show me the doubling" beats "show me the milliseconds"). Watch for the stopwatch-reporter (absolute timings as facts — fix with "what's the ratio?") and the analysis-purist ("theory says, no need to measure" — fix with one crossover surprise, insertion beating merge small). Review check: every complexity claim ships with a doubling ratio, every constant-sensitive choice ships with a measured threshold, benchmarks live beside the code they justify.
