## 6.1. Boundaries: what is covered elsewhere

### 1) **Language mechanics**

**Definition** — loops, closures, Array methods, string handling, Map/Set operations — the *how* of writing code — belong to the [JavaScript track](<../../../../JavaScript/README.md>) (Domains 02, 05, 08, 09, 11); this track prices their composition (the *how much*). When a leaf here says "`includes()` inside `filter()` costs `O(n²)`," the *mechanics* of those methods are a link (notably [JavaScript 08/4.1](<../../../../JavaScript/08 Arrays/sections/4. Searching slicing and joining/4.1. Searching and testing indexOf lastIndexOf includes find findLast every some.md>)), and only the *counting* is new.

- **Why the boundary matters**: analysis questions ("what does this cost?") and mechanics questions ("how does this method work?") share code but different models — counting vs operating. Re-teaching method semantics inside analysis leaves produces the longest, least re-readable pages in algorithms pedagogy: half API reference, half mathematics, fully skimmable. Keep them split: operate in JavaScript, price here.
- **Modern guidance** — if a passage here needs more than one sentence of language mechanics, stop and link instead. The one-sentence versions: loops nest into products (JS 02), callbacks carry the complexity of their bodies (JS 05), methods cost what their domain states (JS 08/09/11). Everything else here is *counting* (repetitions as functions of `n`).

```javascript
// GOOD: one line here, depth behind the link
xs.filter((x) => seen.has(x)); // O(n) expected — Set.has is O(1) average (JS 09 mechanics + [Domain 04 proof](<../../../04 Hashing Trees and Heaps/sections/1. Hashing/1.1. Hash maps average O1 honest worst cases.md>))
// BAD: re-explaining how filter/has/sort work inside analysis leaves
```

### 2) **Concrete algorithms and structures**

**Definition** — sorting algorithms, search structures, hash tables, trees, graphs, dynamic programming — the *things analyzed* — belong to Domains 02–06 of this track, not here. This domain owns the measuring tape (notation, cases, analysis, measurement); they own the objects measured. When [Domain 02](<../../../02 Sorting and Searching/README.md>) says "merge sort is `O(n log n)`," the *recurrence* is a link back here (leaf 2.1), and only the *algorithm* is new.

- **Why the boundary matters**: every analysis concept duplicated per algorithm rots independently — six definitions of Big-O drifting across six domains, six amortized explanations diverging. Single source of truth (PROMPT §5): the concept gets its full treatment once (here), everywhere else one line plus a link. This leaf is the map that keeps those lines short for the whole track.
- **Modern guidance** — memorize the forward map used here and defer the rest: sorting/searching → [Domain 02](<../../../02 Sorting and Searching/README.md>); linear techniques → 03; hashing/trees/heaps → 04; graphs → 05; DP/greedy/backtracking → 06; production problem-solving → 07. When algorithm curiosity strikes mid-analysis ("but how does quicksort actually partition?"), follow the forward link — [Domain 02 answers with code and proofs, not prose](<../../../02 Sorting and Searching/README.md>).


### 3) **Vocabulary naming**

**Definition** — what "Big-O", "technical interview", or "optimization" *means in a meeting* — the naming level — belongs to [IT Vocabulary](<../../../../ITVocabulary/README.md>); this track never re-teaches definitions those leaves own. Map-style stop-list: model → JavaScript track, composition → here (analysis), algorithms → Domains 02–06, mastery → 07, words → IT Vocabulary.

- **Why the boundary matters**: every boundary crossed here is duplication that rots — glossaries copied into analysis leaves go stale when industry usage shifts, while the words-track stays current. The concept gets its full treatment once, everywhere else one line plus a link.
- **Modern guidance** — when writing or reviewing Domain 01 content, ask "does a sibling domain or track own this sentence?" If yes, compress to a link. The domain stops at: notation, cases, time analysis, space analysis, measurement — everything about *how the language works*, *which algorithm to use*, or *what the words mean* lives elsewhere.

### 4) **Common confusion**

- "Analysis is where advanced algorithms live" — analysis is *measurement*; the advanced mechanics distribute across Domains 02–06. This domain is the ruler, not the territory.
- "Boundaries leaves are filler" — they are the DRY contract made visible: each states what its domain deliberately does *not* teach so the repo can teach it once.

### 5) **Performance note**

No runtime cost to boundaries — the performance is editorial: one-line links instead of copied sections keep every leaf short, searchable, and single-sourced. When JavaScript 08 changes a method's documented cost, one domain updates instead of seven.

### 6) **Mentor note**

Use this leaf as the "where do I look?" map for juniors arriving with analysis-adjacent questions: mechanics → JavaScript track, algorithms → Domains 02–06, words → IT Vocabulary. Quiz: "where does quicksort live?" (02), "where does `includes` cost live?" (JS 08 + this track's counting). Correct answers mean the track's architecture landed — the most valuable thing a boundaries leaf can teach.
