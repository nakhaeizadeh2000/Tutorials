## 5.1. Common interview QA: complexity and analysis

### 1) **What's the complexity of this loop?**

**Definition** — the reading exercise that opens most algorithm interviews: a loop (or nest, or recursion) on the whiteboard, and the candidate prices it live. The grading isn't the answer — it's the *procedure*: identify the dominant operation, count repetitions as a function of `n`, dominate-and-name, state the case (worst by default). Strong candidates narrate ("inner runs `n−i` times, sums to `n²/2`, so `O(n²)` worst-case") while writing; weak candidates guess the rung from shape ("two loops, uh, quadratic?").

- **What a good answer sounds like**: counting aloud with formulas before bounds — "`j` runs `n−i−1` times per `i`, total `n(n−1)/2` (verified 4950 at `n=100` in our leaves), so `O(n²)` time, `O(1)` auxiliary." Then the adversarial follow-up unprompted: "worst case — full scan, no early exit; best case `O(1)` if the first pair matches, which we don't budget." Then the trap-check: hidden costs named (`includes` inside `filter`? method costs from the language track?).
- **Modern guidance** — interviewers listen for *dominant-operation thinking* plus *case discipline*, not rung recall: candidates who ask "what counts as the operation?" and state "worst-case" unprompted demonstrate analysis; candidates who answer "`O(n²)`" silently demonstrate memory. Red flags: counting syntax tokens instead of repetitions, quoting best cases as budgets, missing the nested linear call (the `includes`-in-`filter` trap catches most juniors).

```javascript
// The exercise, exactly as it presents (leaf 2.1's verified shape)
function hasDuplicate(xs) {
  for (let i = 0; i < xs.length; i++)
    for (let j = i + 1; j < xs.length; j++)
      if (xs[i] === xs[j]) return true;
  return false;
}
// Full-marks narration: "inner runs n-i-1 per i -> n(n-1)/2 total (4950 at n=100) -> O(n^2)
// worst-case (exits never fire); O(1) auxiliary; best O(1) unbudgeted."
```

### 2) **When is `O(n²)` acceptable?**

**Definition** — the judgment question separating ladder-reciters from engineers: quadratic is fine when `n` is small (≤10⁴ — leaf 1.1's budget), when simplicity beats scaling (code that runs on hundreds of rows forever — the pairwise loop is *clearer* than the clever linear one), and when constants dominate favorably at shipped sizes (measured crossover — leaf 3.1: insertion below ~32 beats merge). Acceptability is a function of `(n, growth outlook, clarity value, measured constants)` — never of the rung alone.

- **What a good answer sounds like**: budgets with conditions — "Quadratic is fine below ~10⁴ inputs with no growth ahead — that's 10⁸ ops, seconds. It's *preferable* when the linear alternative costs significant complexity for inputs that never grow (small fixed-size problems, prototypes, one-off migrations). And I'd verify with a doubling experiment rather than assume — 4× ratio confirms we're paying what we think." Seniors add the expiry clause: "revisit when `n` grows 10× — trades expire with scale (leaf 2.2)."
- **Modern guidance** — grade the *conditional structure* (budgets, growth outlook, measurement), not the threshold number: candidates who say "depends on `n` and growth, here's how I'd decide" pass; candidates who say "never" (dogma) or "always fine" (oblivion) fail. Instant fail: choosing quadratic for unbounded user-scale input ("it's simpler") — simplicity doesn't survive 10⁶ rows. Follow-up separating senior: "your `O(n²)` choice now faces 100× growth — walk me through the migration" (re-budget, re-derive, re-measure — the checklist firing in order).

```bash
# The judgment, structured (leaf 1.1 budgets + leaf 3.1 verification)
#  n <= 10^4, no growth  -> O(n^2) acceptable, often clearer — verify with one doubling run
#  n unbounded/user-scale -> linearithmic or better required — simplicity doesn't survive 10^6 rows
#  crossover regimes      -> hybridize at measured thresholds (insertion <32, merge above)
```

### 3) **Derive `O(n log n)` for halving work**

**Definition** — the recurrence answer: for `T(n) = 2T(n/2) + O(n)` (merge sort's shape), unroll the tree — `log₂n` levels, each doing `n` combine work → `O(n log n)`. Verified evaluation: `T(1024) = 11264 = 1024·10 + 1024` exactly. The derivation candidates must perform live: write the recurrence from the code (two halves + linear merge), draw two levels, generalize to `log n` levels × `n` work. Pattern discovered beats theorem recited — interviewers who hear "by the Master theorem, case 2" follow up with "show me why" anyway.

- **What a good answer sounds like**: code-to-recurrence-to-tree in three breaths — "two recursive halves plus linear merge gives `T(n) = 2T(n/2) + n`; level 0 does `n`, level 1 two halves of `n/2` = `n`, every level `n`; depth `log₂n`; total `n log n`." Then the contrast unprompted: "halve-and-combine-*constant* (binary search) is `log n` — one half kept, not two; shrink-by-one-and-combine-linear is `n²` — the degenerate the tree warns about." The tree drawn (even ASCII) signals understanding no theorem citation can fake.
- **Modern guidance** — listen for *levels × work-per-level* as the organizing idea: candidates who structure every recurrence answer that way generalize to unseen recurrences; candidates who pattern-match ("halving means log") collapse on `2T(n/2)+n` vs `T(n/2)+O(1)` vs `T(n−1)+n` distinctions. Red flags: "recursive so logarithmic" (depth ≠ cost), memorized Master cases without tree intuition, ignoring the combine cost (the `+n` is where linearithmic lives — drop it and the answer is wrong by a factor of `n`).

```javascript
// The derivation target (leaf 2.1's verified recurrence)
function mergeSort(xs) {
  if (xs.length <= 1) return xs;      // T(1) = O(1)
  const m = xs.length >> 1;
  return merge(mergeSort(xs.slice(0, m)), mergeSort(xs.slice(m)));  // 2T(n/2) + O(n)
} // levels: log2(n) x work-per-level: n -> O(n log n). T(1024) = 11264 verified.
```

### 4) **Common confusion**

- Candidates who answer complexity questions with timings ("it runs in 3ms") — curves, not clocks (leaf 1.1); ask for the doubling prediction to recalibrate.
- "Amortized means average" in Q&A — the classic trap answer; amortized is sequence-guaranteed (leaf 2.1), average is distribution-assumed (leaf 1.2). Candidates who separate them unprompted signal senior depth.
- Treating space as an afterthought ("oh, and space?") — time and space ship together (leaf 2.2); interviewers note who states both unprompted.

### 5) **Performance note**

Interview answers cost nothing to compute but everything to structure: loop pricing (60 seconds — count, formula, bound, case), quadratic acceptability (90 seconds — budgets, conditions, expiry), recurrence derivation (two minutes — code, tree, contrast). Candidates who narrate procedures without models take longer and prove less — structure is speed, in interviews as in analysis.

### 6) **Mentor note**

Use Q1 as the reading screen (every hire must count dominant operations with formulas), Q2 as the judgment screen (every hire must budget conditionally, never dogmatically), Q3 as the derivation screen (every hire must unroll a tree live). Rubric: junior — correct rungs with counting shown; mid — cases stated (worst default, distributions named), space quoted beside time; senior — crossovers, expiry clauses, and distribution honesty ("over what inputs?") without prompting. Keep the verified numbers ready (4950, 1/5001/10000, 11264, 2.01/4.06) — candidates who anchor to measured evidence stand out; interviewers who demand it hire better. Red-flag fails: best-case budgets, timing-as-analysis, "recursive so logarithmic," unbounded-input quadratics.
