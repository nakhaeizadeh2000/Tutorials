## 4.1. Complexity checklist (habits mentors insist on)

### 1) **Name time and space before coding**

**Definition** — the design conversation starts from numbers, not code: before implementing, state the target bounds ("`O(n)` time, `O(1)` auxiliary") with the cost model named ("comparisons", "extra structures"). The bounds are the *requirement* the implementation must meet — reviewers check code against numbers, not vibes. Functions without stated bounds get them assigned in review (by reading the loops) instead of by design (by choosing the approach).

- **What problem it solves**: code-first analysis produces rationalization ("the implementation is pairwise, so `O(n²)` it is") instead of design ("we need linear — which approach gives it?"). Stating bounds first inverts the flow: the bound selects the approach (ladder budgeting — leaf 1.1), the approach produces the code, review verifies the match. Mismatches surface as design discussions ("pairwise can't meet linear — rethink") rather than post-ship incidents.
- **Modern guidance** — write bounds in the PR description or design doc beside inputs ("`n` = daily events, ~2M — linearithmic or better required"). Name the dominant operation with the bound ("`O(n)` hash insertions" — checkable in review). When bounds are unknown (novel problem), state the question explicitly ("complexity TBD — spike first") rather than shipping unbounded.

```javascript
// GOOD: numbers before code — the bound selects the approach
// "dedupe 2M IDs: O(n) time, O(n) aux via Set (hash insertions dominate). Pairwise O(n^2) rejected: ~4T ops."
function dedupe(ids) { return [...new Set(ids)]; }
// BAD: code first, bounds never —
// review discovers the rung, production discovers the incident
```

### 2) **Worst-case first, distribution second**

**Definition** — guarantee the hardest input, then optimize the common one: budget capacity on worst-case bounds (leaf 1.2's contract), then spend measured effort where profiles point (hot paths, real distributions — leaf 3.1's workload timing). The order is load-bearing — reversed, "typical" performance gets engineered while adversarial inputs hold the pager. Both matter; worst-case is first among equals because only it composes into guarantees.

- **Why it matters (correctness)**: average-first engineering ships the classics — quicksort without pivot discipline (sorted inputs degrade), hash maps without collision thinking (crafted keys degrade), caches without miss-storm analysis (cold starts cascade). Each performed beautifully on typical data and failed on merely-unlucky data, let alone adversarial. Worst-case-first doesn't forbid averages — it *bounds* them: optimize the common case inside a contract the worst case can't break.
- **Modern guidance** — ask "what input makes this slowest?" for every algorithm under review (the adversarial reflex — leaf 1.2), then "what does ours look like?" (measured distribution — leaf 3.1). Where adversaries exist (user input, network data), worst-case *is* the budget — no distribution talk allowed. Document both where they differ ("worst `O(n²)` adversarial, average `O(n log n)` uniform, measured `1.8×` on traces" — the expert sentence travels with the code).

```javascript
// GOOD: contract first, profile second
// quickSelect: worst O(n^2) (adversarial pivots) -> median-of-medians or shuffle for guarantees;
// measured traces: 1.8x over sort-based select -> ship with shuffle, budget the worst. (Domain 02 preview.)
// BAD: "average O(n log n), ship it" with user-controlled input ordering —
// the adversary reads your analysis too
```

### 3) **Verify the curve empirically**

**Definition** — one doubling experiment per claim that matters: harness, two sizes, one ratio (leaf 3.1's loop). Analysis predicts, measurement confirms — and disagreements get investigated, not filed. The verified ratios from this domain (2.01 linear, 4.06 quadratic) are the template: predicted rung → measured ratio → match or mystery. Unverified bounds are hypotheses wearing theorems' clothes.

- **Why it hurts when missing (correctness, maintainability)**: paper analysis errs in the details that matter — hidden linear factors (the "constant" method call that's actually a scan), JIT shape effects (megamorphic sites 10× slower at identical complexity), hardware regimes (cache cliffs between measured and shipped sizes). Each produces code that's correct on paper and wrong in production — right rung claimed, wrong curve shipped. The doubling experiment catches all three in minutes, because it measures *scaling* (what analysis claims) rather than speed (what analysis never claimed).
- **Modern guidance** — require doubling ratios for scale-critical claims (hot paths, data-plane code, anything with 10× growth ahead); accept analysis-only for glue code (rung estimate + move on — proportionality, not paranoia). When ratio and analysis disagree, run the disagreement down (re-derive for hidden factors, re-measure for methodology flaws) — the resolution always teaches something (a hidden scan, a shape change, a cache effect) worth more than either input alone. Benchmarks live beside the code (CI-runnable, re-run on performance PRs).

```bash
# GOOD: the loop closed — predict, measure, match (leaf 3.1 harness, verified ratios)
#  claim O(n)      -> ratio(lin, 30000) = 2.01  -> confirmed, ship
#  claim O(n^2)    -> ratio(qd, 1200)   = 4.06  -> confirmed, budget accordingly
#  mismatch?       -> re-derive + re-measure -> the most informative outcome, investigate fully
# BAD: paper bounds merged without measurement on scale-critical paths —
# scaling debt, payable with interest at input-growth time
```

### 4) **Common confusion**

- "Checklists replace analysis" — checklists *trigger* analysis at the right moments (before coding, before shipping, before scaling). The thinking stays human; the timing becomes systematic.
- "Small functions don't need bounds" — small functions compose into big systems (leaf 2.1's nesting math). Unbounded helpers are how `O(n)` pipelines silently become `O(n²)` — one innocent scan per stage.
- "Verification is only for performance-critical code" — verification is proportional: doubling experiments for hot paths, rung estimates for glue. Skipping both isn't pragmatism, it's the incident pipeline.

### 5) **Performance note**

The checklist costs minutes per feature (bounds stated, worst-case asked, one doubling run) against incident costs in hours and scaling rewrites in weeks. The highest-leverage item is bounds-before-code (selects approaches, prevents rationalization); the second is the doubling experiment (audits claims, catches hidden factors). Minutes that prevent rewrites — the track's best rate of return on attention.

### 6) **Mentor note**

Convert this leaf into the team's analysis runbook: bounds-with-models before code, worst-case-first in review, doubling ratios for scale-critical claims. Quiz juniors on placement ("which checklist item fires here?") until the three habits trigger unprompted. Watch for checklist decay (analysis performed for a sprint, abandoned under deadline — fix by requiring bounds in PR templates, so the checklist has mechanical teeth) and analysis theater (bounds stated, never verified, wrong anyway — fix with "show me the doubling"). Review check: bounds stated with models, worst cases asked, curves verified where scale demands — and the mentor's own designs modeling all three visibly.
