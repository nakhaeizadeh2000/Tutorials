## 1.2. Best, worst, and average cases

### 1) **Worst case is the contract**

**Definition** — the worst-case bound holds for *every* input of size `n`: "linear search is `O(n)`" means no input of length `n` costs more than linear — guaranteed, no distribution assumed. Verified with comparison counts on 10,000 elements: target first → 1 comparison; target at index 5000 → 5001; target absent → 10,000 (every element examined). The `O(n)` label prices the hardest input; easier ones come free.

- **What problem it solves**: guarantees compose — SLAs, capacity plans, and nesting analyses ("this `O(n)` scan runs inside an `O(n)` loop" — leaf 2.1) all need bounds that hold unconditionally. Best-case and average-case bounds come with asterisks (which input? which distribution?) that void them exactly when relied upon most — under adversarial or merely unlucky load. The worst case is the only bound you can budget against without fine print.
- **Modern guidance** — quote worst-case by default, always ("`O(n)` worst-case" — two extra words that convert a claim into a contract). Design nested structures against worst cases (a hash map inside a hot loop is an `O(n)`-per-op liability wearing `O(1)` average clothing — leaf 2.2's collision story). Reserve other cases for the sections below — explicitly labeled, never implied.

```javascript
// GOOD: the contract priced on the hardest input — verified counts
function linSearch(xs, t) {
  for (let i = 0; i < xs.length; i++) if (xs[i] === t) return i; // 1 .. n comparisons
  return -1;
}
// n=10000: first -> 1, middle -> 5001, absent -> 10000. O(n) worst-case: no input exceeds linear.
// BAD: "O(1) — usually the item is near the front" —
// "usually" is not a bound; provision on it and the adversary (or theMonday import) collects
```

### 2) **Best case rarely matters**

**Definition** — the best-case bound prices the *easiest* input (linear search finds it first: `O(1)`): true, useless for planning. Best cases describe luck, and systems aren't provisioned on luck — nobody sizes servers for the request pattern that flatters, prices SLAs on the input that cooperates, or chooses algorithms by their finest hour. The one honest use: proving a lower bound exists ("even the best input costs *this* much" — optimality arguments, Domain 02's sort lower bound).

- **Why it matters (correctness)**: best-case quoting is the performance equivalent of survivorship bias — the demo runs on warm caches with tiny inputs, the numbers look heroic, production disagrees. Interviews test exactly this: "binary search is `O(1)` best-case" is a true statement that reveals a candidate who optimizes for applause. Correctness thinking demands the adversarial question as reflex: "what input makes this slowest?" — asked before "how fast is it typically?"
- **Modern guidance** — mention best case only to dismiss it ("`O(1)` best, `O(n)` worst — we budget the worst") or in optimality proofs ("any correct algorithm needs `Ω(n)` here, and ours meets it" — lower-bound matching, the expert move). Never let a best-case number travel without its worst-case sibling — orphaned optimism is how `O(n)` systems get provisioned as `O(1)`.

```javascript
// GOOD: best case stated, then correctly discarded
// linSearch: best O(1) (target first), worst O(n) (target absent) -> budget O(n). Done.
// The O(1) travels only inside optimality talk: "finding an arbitrary element needs Omega(1) trivially."
// BAD: benchmarking the first-element hit and reporting "search runs in constant time" —
// measured luck, published as analysis
```

### 3) **Average needs a distribution**

**Definition** — average-case analysis prices the *expected* cost over an input distribution: linear search over uniformly random targets averages `n/2` comparisons → `O(n)` (same rung, halved constant — the bound rarely changes, the bill does). The load-bearing phrase is "over *what* distribution?": uniform random, real workload traces, adversarial — each yields different averages, and the analysis is only as honest as the distribution is realistic. Quicksort's `O(n log n)` average assumes no adversary picks pivots' nightmares; hash maps' `O(1)` average assumes non-pathological hashing (leaf 2.2).

- **Why it hurts when missing (correctness, maintainability)**: distribution-free "average" talk smuggles uniformity in — real workloads skew (hot keys, sorted-already inputs, duplicate-heavy streams), and skewed inputs hit the cases uniform analysis priced at epsilon. The classics: quicksort degrading on sorted data (pivot nightmare — Domain 02), hash maps degrading under collision attacks (key nightmare — Domain 04), "average `O(1)`" caches with 100% miss storms. Each incident retro reads "assumed uniform, received reality."
- **Modern guidance** — state the distribution with the average ("`O(n log n)` average over random permutations" — falsifiable, reviewable). Prefer measured workload profiles over assumed uniformity (leaf 3.1: time *your* inputs, not random ones). When adversaries exist (user-controlled keys, network inputs), budget the worst case regardless of the average — security thinking *is* worst-case thinking with intent. The expert sentence covers all three: "worst `O(n²)`, average `O(n log n)` uniform, measured `1.8×` on our traces."

```javascript
// GOOD: average with its distribution named — verified middle case
// linSearch, uniform random target in n=10000: expected comparisons ~5000 (measured mid: 5001)
// -> O(n) average (uniform). Same rung as worst here; the constant halved, the budget didn't move.
// Quicksort: O(n log n) average (random permutations) vs O(n^2) worst (sorted + naive pivot) -> Domain 02.
// BAD: "average O(n log n)" with no distribution —
// against adversarial input the average is whatever the adversary bills you
```

### 4) **Common confusion**

- "Average of best and worst" — no: average weights *all* inputs by probability, not two endpoints. (Best + worst)/2 is a formula for nothing.
- "Amortized means average" — amortized averages over a *sequence of operations* with a worst-case guarantee per sequence (leaf 2.1); average-case averages over *inputs* with a distribution assumption. Different mathematics, different guarantees — amortized is stronger.
- "Worst case is pessimistic" — worst case is *contractual*: the bound holds for all inputs, which is what composition and provisioning need. Pessimism is a mood; contracts are engineering.
- "`O(n)` average equals `O(n)` worst, so the distinction never matters" — here the rungs coincide; for quicksort (`n log n` vs `n²`) and hashing (`1` vs `n`) the distinction *is* the design conversation.

### 5) **Performance note**

Case analysis costs nothing at design time (three questions per algorithm: hardest? easiest? typical-over-what?) and prices everything downstream: worst cases size capacity, averages size expectations, best cases size nothing. The verified counts above (1 / 5001 / 10000) took one scratch script — and their value is the *ratio pattern* (luck vs typical vs adversarial), portable to every search you'll ever analyze.

### 6) **Mentor note**

Drill the adversarial reflex first: for every algorithm a junior meets, ask "what input makes this slowest?" before "how fast is it?" — until worst-case-first is involuntary. Then demand distributions with every average ("over what inputs?" — accept no average without one). The calibration exercise: linear search counts live (1 / 5001 / 10000 — luck, typical, contract in three numbers). Watch for the best-case quoter (optimizes for applause — fix with adversarial inputs on the spot) and the distribution-free averager ("usually fast" — fix with one skewed workload measured live). Review check: every bound states its case (worst by default, others labeled with distributions); no orphaned `O(1)` best-cases traveling as budgets.
