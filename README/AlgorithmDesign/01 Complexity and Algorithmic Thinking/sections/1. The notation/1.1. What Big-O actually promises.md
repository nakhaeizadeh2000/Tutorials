## 1.1. What Big-O actually promises

### 1) **Upper bounds on growth, not stopwatches**

**Definition** — Big-O names an *upper bound on how cost grows* as input size `n` grows: `O(n)` means "cost grows at most linearly" — double the input, at most double the work (beyond some size, modulo constants). It never promises seconds, comparisons, or superiority on any particular input. Two `O(n)` algorithms can differ 100× in wall time; an `O(n²)` algorithm beats an `O(n log n)` one on every input you'll ever feed it if `n` stays tiny. The notation compares *curves*, never *clocks*.

- **What problem it solves**: without growth analysis, performance discussion degenerates into benchmarking anecdotes — "my laptop runs it in 2s" (your laptop, your input, today). Hardware changes, inputs grow, and the anecdote expires. Big-O survives both: it names the property of the *algorithm* (how work scales), which outlives every machine it runs on. When input grows 10× and the system falls over, the engineer who read the curve saw it coming; the engineer who read the stopwatch is surprised.
- **Modern guidance** — state the bound with its cost model ("`O(n)` comparisons", "`O(n)` extra space") — a bare `O(n)` without naming *what* is counted invites the classic confusion below. Analyze first for the curve, measure second for the constant (leaf 3.1 owns the measurement half). Never quote Big-O as a performance prediction in milliseconds — quote it as a scaling contract, then verify scaling empirically.

```javascript
// GOOD: same curve, different clocks — Big-O sees one thing, stopwatches another
function sumA(xs) { let s = 0; for (const x of xs) s += x; return s; }       // O(n) additions
function sumB(xs) { return xs.reduce((s, x) => s + x, 0); }                  // O(n) additions too
// Both O(n). Either may win a given race (JIT, callback overhead) — the notation
// promises only this: double xs, both do ~2x the additions. Verified below in leaf 3.1 style.
// BAD INSTINCT: "both O(n) so performance is identical" —
// growth identical, constants differ; Big-O never promised otherwise
```

### 2) **Drop constants, keep the dominant term**

**Definition** — asymptotic analysis keeps the fastest-growing term and discards the rest: `3n² + 10n + 5` → `O(n²)`, `n + log n` → `O(n)`, `2n` → `O(n)`. Rationale, not laziness: as `n → ∞`, the dominant term dwarfs the others (`3n²` vs `10n` at `n = 10⁶` differs by 5 orders of magnitude — the `10n` is a rounding error on the curve). Constants (`3×`) and lower terms vanish from the notation *because scale erases them*, not because they're small today.

- **Why it matters (correctness)**: beginners either track every operation (analysis paralysis — counting `+1`s that scale erases) or drop the wrong term (keeping the `O(n)` setup loop while ignoring the `O(n²)` core — the bound then lies about the algorithm). The discipline is mechanical: expand nested costs into a sum, identify the fastest grower, name it. One term, honestly chosen, beats five terms precisely wrong.
- **Modern guidance** — simplify aggressively but *state the dropped context once* ("`O(n²)` time from the pairwise loop; the `O(n)` preprocessing is dominated"). Keep constants alive in a separate sentence when they matter operationally ("`O(n)` with a large constant — hashes 10KB records" warns differently than bare `O(n)`). The notation drops them; engineering judgment keeps the important ones visible beside it.

```javascript
// GOOD: expand, dominate, name — one term, honestly chosen
function pairSums(xs) {
  let total = 0;                       // O(1)
  for (let i = 0; i < xs.length; i++)  // outer n ...
    for (let j = 0; j < xs.length; j++)// ... x inner n = n^2 additions
      total += xs[i] + xs[j];
  return total;                        // total: n^2 + O(1) -> O(n^2) time, O(1) space
}
// BAD: "O(n) because there's one return statement" or "O(n^3) counting every + as a loop" —
// count repetitions of the dominant operation, not syntax tokens
```

### 3) **The ladder you must feel**

**Definition** — the growth ladder, each rung a different universe of feasible inputs: `O(1)` constant (hash lookup — billions OK), `O(log n)` logarithmic (binary search — halving devours billions in ~30 steps), `O(n)` linear (one pass — bounded by I/O), `O(n log n)` linearithmic (good sorts — the price of order), `O(n²)` quadratic (pairwise — dead past ~10⁴–10⁵), `O(2ⁿ)` exponential (subsets — dead past ~30–40). Feeling means *input budgeting*: given a rung, name the largest `n` that finishes today.

| Class | Doubling the input… | Feasible `n` (≈1s budget) |
|---|---|---|
| `O(1)`, `O(log n)` | cost barely moves | effectively unbounded |
| `O(n)` | cost ~2× | ~10⁸ simple ops |
| `O(n log n)` | cost ~2×+ | ~10⁷ |
| `O(n²)` | cost ~4× | ~10⁴ |
| `O(2ⁿ)` | cost *squares* | ~30 |

- **Why it hurts when missing (correctness, maintainability)**: engineers without the ladder pick algorithms by familiarity — nested loops for everything, recursion for fit — and discover the rung in production (the `O(n²)` dedup that handled test data and chokes on the customer import; the exponential partition search that never returns). The ladder converts "slow" (vague, arguable) into "quadratic on 10⁶ rows" (specific, falsifiable, plannable). Every performance incident retro in this track starts with naming the rung nobody named up front.
- **Modern guidance** — memorize the ladder as *budgets*, not definitions: before coding, ask "what's `n` here, and which rungs survive it?" (`n ≤ 20` → anything; `n ≤ 10⁴` → quadratic OK; `n ≥ 10⁶` → linearithmic or better, with constants checked). Verified doubling behavior on Node v20.20.2 (warmed-up, per-op means): linear sum 20k→40k measured 0.013→0.028ms (~2.1× ✓); pairwise sum 800→1600 measured 0.900→2.722ms (~3×, approaching 4× with cache effects — honest hardware, predicted curve). The ratios confirm the rung; the milliseconds confirm nothing portable.

```javascript
// GOOD: budget before code — the ladder as a design input
// "dedupe 2M event IDs" -> O(n^2) pairwise needs ~4T ops (dead) -> O(n) Set pass (leaf: [Domain 04/1.1](<../../../04 Hashing Trees and Heaps/sections/1. Hashing/1.1. Hash maps average O1 honest worst cases.md>))
// "all partitions of 40 items" -> O(2^n) ~ 1T subsets (dead) -> rethink the requirement ([Domain 06/3.2](<../../../06 Dynamic Programming Greedy and Backtracking/sections/3. Greedy and backtracking/3.2. Backtracking with pruning.md>))
// BAD: coding first and discovering the rung from the incident report —
// the ladder is a design tool, not a postmortem vocabulary
```

### 4) **Common confusion**

- "Big-O is the exact speed" — it bounds *growth shape* from above. Exactness was never on offer; portability across machines was the actual prize.
- "Lower Big-O always wins" — asymptotically, eventually; in production, constants, cache, `n`, and implementation quality vote too. The ladder picks candidates; measurement (leaf 3.1) picks winners.
- "`O(1)` means instant" — constant means *input-independent*: a 10ms hash lookup and a 1ns array index are both `O(1)` with very different clocks. Flat curve, possibly high floor.
- "Log bases matter" — `log₂ n` vs `log₁₀ n` differ by a constant factor (change of base) — scale erases it. All logs live on one rung.

### 5) **Performance note**

Analysis itself is free (paper, minutes); its payoff is avoiding the expensive experiments (implementing the quadratic, deploying it, profiling the incident). The verified numbers above cost one scratch script — and their value isn't the milliseconds (machine-specific, expiring) but the ratios (curve-specific, portable). Measure ratios, publish curves, distrust absolute timings older than your current hardware.

### 6) **Mentor note**

Make juniors *feel* each rung before formalizing: run the doubling script for linear vs quadratic live (0.013→0.028 vs 0.900→2.722 lands harder than any definition), then ask for input budgets ("which rung survives 10⁷ rows?"). Drill ladder placement as a reflex — every code review gets "state the rung" until bounds appear unprompted. Watch for the two failure postures: the counter (tracks every `+1`, never names the curve — fix with "dominant term only") and the stopwatch-reader ("but it runs fast on my machine" — fix with 10× input on the spot). Review check: every non-trivial function states time + space bounds (leaf 2.2) with the cost model named; no bare `O(n)` without "of what."
