## 1.2. Constraints-first design

### 1) **Read limits as specifications**

**Definition** — constraint translation table (Domain 01 §1.1's ladder, applied as specification): `n ≤ 20` → enumeration honest (`2ⁿ` feasible — backtracking/sudoku shapes); `n ≤ 500` → `O(n³)` tolerable (Floyd, cubic DP — hundreds-cubed fits seconds); `n ≤ 10⁵` → `O(n log n)` ceiling (sort+scan, heaps, balanced structures); `n ≤ 10⁷` → `O(n)` small constants (I/O dominates — milliseconds per element verified: 200k scan 3.99ms scales the estimate); memory caps → table/streaming mandates (256MB forbids `10⁸`-cell tables — rolling or streaming required).

- **What problem it solves**: limit-blind design ships the classics — exponential on `10⁵` (heat death scheduled by optimism), quadratic on `10⁶` rows (10¹² ops ≈ hours, not seconds), full tables under caps (OOM on hidden larger tests — samples fit, judges don't). Each passes samples (tiny by design) and fails scale (the actual specification). Translation converts "which algorithm?" from taste into arithmetic — falsifiable in seconds, before any code exists.
- **Modern guidance** — translate both caps (time *and* memory — 256MB tables cap states at ~3·10⁷ integers; time caps rung via ladder). Budget constants explicitly (verified 3.99ms/200k → ~20ms/M → 10⁷ ≈ 200ms linear headroom — arithmetic, not vibes). Re-check on approach selection (chosen constants × limits — hash overhead 3× still linear; recursion depth vs stack — Domain 01 §2.2). State the translation with the approach ("`n=2·10⁵` → linearithmic ceiling → sort+scan" — the sentence preventing exponential detours).

```bash
# GOOD: limits translated before approaches discussed (specifications, not hints)
#  n <= 20:    enumerate (2^n feasible — backtracking honest, Domain 06 §3.2)
#  n <= 500:   O(n^3) tolerable (Floyd-shaped budgets, seconds)
#  n <= 10^5:  O(n log n) ceiling (sort+scan, heaps, balanced structures)
#  n <= 10^7:  O(n) small constants (200k scan 3.99ms verified — scale the estimate)
#  256MB cap:  tables <= ~3*10^7 ints (rolling/streaming mandated past it)
# BAD: "should pass" without limit arithmetic — hope wearing complexity notation
```

### 2) **200k-scan sanity checks**

**Definition** — production-size estimation probes: time a linear pass at shipped scale *before* optimizing (verified 200k scan: 3.99ms — linear arithmetic extrapolates: 10⁷ ≈ 200ms, 10⁸ ≈ 2s ≈ budget edge). Sanity checks calibrate intuition (is linear fast *enough*? — usually yes with 10–100× headroom; is quadratic *possible*? — 10⁵² is never yes). One probe per performance question — seconds of measurement replacing quarters of debate.

- **Why it matters (correctness)**: unestimated performance ships two failure shapes — over-engineering (log-structured merge for 10⁴ rows that fit RAM scan — complexity without customers) and under-budgeting (quadratic "probably fine" on 10⁶ rows — 10¹² ops ≈ hours, discovered in production). The sanity probe rightsizes both (linear measured at scale → headroom computed → approach selected with margins). Estimation is design input, not post-ship forensics.
- **Modern guidance** — probe at shipped sizes (200k+ elements — timer granularity washes out, JIT warms up — Domain 01 §3.1's harness discipline, applied). Extrapolate linearly for linear code (verified 3.99ms → 10⁷ ≈ 200ms — arithmetic, stated with the hardware caveat). Compare against budgets explicitly (200ms vs 1s budget → 5× headroom, ship; vs 100ms budget → optimize or parallelize). Re-probe per platform (V8 vs JSC vs phones — constants move 2–5×; the probe travels, assumptions don't).

```javascript
// GOOD: estimate before optimizing (one probe, arithmetic headroom)
// 200k scan: 3.99ms verified -> 10^7 ≈ 200ms (linear extrapolation) -> vs 1s budget: 5x headroom, SHIP.
// vs 100ms budget: optimize (parallelize, SIMD, better constants) or renegotiate — decided by numbers.
// BAD: "linear, so fast enough" without measurement ("theory") or
//      "too slow, optimize" without measurement ("instinct") — both skip the 4ms probe that decides
```

### 3) **Two-solution strategy**

**Definition** — brute force first (obviously-right, exponential-or-quadratic welcome — correctness banked in minutes), optimized second (paradigm-selected per constraints — performance engineered against the oracle). The brute force *becomes* the stress oracle (leaf 2.1: 500/500 agreement methodology) — first solution pays twice (submission fallback + verification truth). Time-box the brute force (15 minutes — then optimize regardless; perfect brute force is still brute force).

- **Why it hurts when missing (correctness, maintainability)**: optimized-first development debugs two unknowns simultaneously (is the approach right? is the code right? — failures ambiguous, fixes speculative). Brute-first separates them (oracle trusted → optimized diffs are *the* bug signal; stress disagreements locate precisely). Skipped oracles also forfeit partial credit (contests score subtasks — brute force banks small-input points while optimization targets large; interviews credit working baselines over broken brilliance).
- **Modern guidance** — time-box brute force ruthlessly (correct > clever in the first third of the clock — bank truth early). Keep the oracle beside the optimized (stress harness from leaf 2.1 runs both — agreement monitored, not assumed). Optimize against disagreements (failing cases are *the* specification gaps — shrink, diagnose, fix per leaf 2.2's verdict classes). Submit brute force when optimization stalls (banked points beat perfect attempts — contests and interviews both reward working over brilliant-but-broken).

```bash
# GOOD: truth banked early, performance engineered against it (two-solution discipline)
#  0:00-0:15 brute force (correct, slow) -> oracle banked, fallback secured.
#  0:15-0:40 optimized (paradigm-selected) + stress vs oracle (500/500 methodology).
#  stuck? -> submit brute (partial credit banked) — working beats brilliant-but-broken.
# BAD: optimized-first with no oracle ("confident") —
# failures ambiguous (approach? code?), no fallback, no partial credit — confidence billing triple
```

### 4) **Common confusion**

- "Constraints limit creativity" — constraints *direct* creativity (rung ceilings eliminate wrong families instantly — design space shrinks to feasible approaches, where creativity actually pays). Unlimited design wanders; constrained design converges.
- "Sanity probes are premature optimization" — probes *prevent* premature optimization (measured headroom kills speculative tuning) and premature pessimism (measured slack kills unnecessary complexity). Measurement before both.
- "Two solutions waste time" — brute force pays twice (fallback + oracle) in a third of the clock; optimized-first pays ambiguity tax on every failure. Waste is debugging without truth, not banking it early.

### 5) **Performance note**

Method costs minutes (translation, probe, brute force) against wrong-approach rewrites (tens of minutes) and truthless debugging (ambiguous failures per verdict). Highest-leverage item is constraints-first (selects paradigm correctly); second is oracle banking (disambiguates all future failures); third is sanity probes (rightsizes effort). Minutes preventing rewrites — method's best attention rate.

### 6) **Mentor note**

Enforce translation before approaches ("n-bound → rung → shortlist" until instantaneous — no algorithm talk before numbers). Demand sanity probes on performance claims ("show me the 200k number" — measured headroom or it didn't happen). Require brute-force oracles on non-trivial solutions ("where's the truth version?" — agreement monitored). Watch for the taste-selector ("I like DP for these" — fix with constraint arithmetic on their own limits) and the confidence-skipper ("no oracle needed" — fix with one ambiguous failure autopsied live). Review check: limits translated, probe run, oracle banked — and the mentor's own problem-solving modeling all three visibly.
