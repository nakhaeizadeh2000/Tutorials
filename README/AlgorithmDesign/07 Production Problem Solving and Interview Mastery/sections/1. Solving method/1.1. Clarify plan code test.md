## 1.1. Clarify, plan, code, test

### 1) **Examples before algorithms**

**Definition** — hand-run samples before selecting techniques: work 2–3 input/output pairs by hand (trace the transformation physically — what moves where, what stays), and the problem's structure surfaces (sortedness, monotonicity, overlapping subproblems, graph hiding in grid clothes). Examples are requirements executable by hand; algorithms chosen after examples fit observed structure instead of imagined generality.

- **What problem it solves**: statement-first coding misreads systematically (constraints skimmed, edge semantics assumed, "sorted" unnoticed — the implementation answers a nearby problem correctly). Hand-running forces contact with specifics (duplicates in the sample behave how? empty input means what? the third example breaks which assumption?). Misreading caught at minute two costs a question; caught at minute forty costs the interview.
- **Modern guidance** — run samples by hand before discussing approaches (pen-and-paper traces, narrated — interviewers score the habit visibly). Invent the missing examples (statement gives two — construct the empty, the single, the duplicate, the extreme; the matrix from Domain 07's own checklist, previewed). Restate the problem in own words with examples attached ("given X, produce Y — e.g. [example] → [output] because [trace]") — restatement errors surface before code exists.

```javascript
// GOOD: examples as executable requirements (traced before techniques chosen)
// "two-sum sorted [1,2,4,7,11,15], 15 -> [2,4]: 4+11, converge inward (Domain 03 §1.1)."
// "empty -> null; single -> null (no pair); duplicates -> first valid (documented)."
// Structure observed (sorted!) picks the technique — examples did the analysis.
// BAD: coding from the title ("two sum — hash map, go") —
// title-driven selection skips structure (sortedness unnoticed — O(n) space donated needlessly)
```

### 2) **Constraints pick the paradigm**

**Definition** — limits are specifications wearing numbers: `n ≤ 20` enumerates (`2ⁿ` feasible — backtracking honest), `n ≤ 500` tolerates `O(n³)` (Floyd-shaped budgets), `n ≤ 10⁵` demands linearithmic or better (Domain 01 §1.1's ladder, applied), `n ≤ 10⁷` demands linear with small constants (I/O dominates — budget milliseconds per element), memory caps forbid tables (streaming/rolling mandated). Reading constraints *is* paradigm selection — the numbers name the rung before any algorithm is discussed.

- **Why it matters (correctness)**: constraint-blind selection ships the classics — exponential on `n=10⁵` (heat death scheduled), quadratic on `10⁶` rows (timeout at 10¹² ops), full tables under 256MB caps (OOM on the judge's larger hidden tests). Each passes samples (tiny by design) and fails hidden scale (the actual test). Constraints-first converts "which algorithm?" from taste into arithmetic (ladder rung vs limit — falsifiable in seconds).
- **Modern guidance** — translate limits immediately (n-bound → rung ceiling → paradigm shortlist: enumerate/`n²`/linearithmic/linear). Check time *and* memory caps (256MB forbids `10⁸`-cell tables — space ladder beside time ladder, Domain 01 §2.2). Re-check mid-solution (chosen approach's constants × limits — verified 200k-scan 3.99ms scales the estimate: is there 100× headroom?). State the budget with the approach ("`n=2·10⁵` → linearithmic ceiling → sort+scan selected" — the sentence that prevents exponential detours).

```bash
# GOOD: limits translated before approaches discussed (ladder applied to budgets)
#  n <= 20,   any time   -> enumerate (2^n feasible — backtracking honest, leaf: Domain 06 §3.2)
#  n <= 500,  1s         -> O(n^3) tolerable (Floyd-shaped budgets)
#  n <= 10^5, 1s         -> O(n log n) ceiling (sort+scan territory)
#  n <= 10^7, 256MB      -> O(n) small constants, rolling space (tables forbidden by cap)
# BAD: "O(n^2) should pass" without limit arithmetic —
# should-pass without numbers is hope; ladder-vs-limit is engineering
```

### 3) **Edges enumerated, not discovered**

**Definition** — the edge matrix written before code (empty, single-element, all-equal, duplicates, extremes, impossible — per problem shape): each cell gets expected behavior (return value, exception, sentinel — specified, not improvised). Edges enumerated up front convert wrong-answer verdicts from mysteries into checklist items (which matrix cell failed? — diagnosis by elimination instead of archaeology).

- **Why it hurts when missing (correctness, maintainability)**: undiscovered edges are the top WA source (empty input crashes indexing, single-element skips loops entirely, all-equal breaks distinctness assumptions, impossible inputs return garbage instead of specified sentinels). Each passes happy-path tests by construction (tests cover the middle, edges live at the borders). The matrix costs a minute to write and catches the verdict class responsible for most failed submissions — enumerated edges are tested edges; tested edges don't surprise.
- **Modern guidance** — write the matrix with the examples (input shape × expected behavior — empty→?, single→?, duplicates→?, max→?, impossible→?). Encode edges as unit tests first (failing tests before implementation — TDD's actual value proposition, restated for problem solving). Revisit the matrix after coding (each cell traced through the implementation — the review that catches off-by-ones before judges do). Keep impossibility specified (`""`, `-1`, `null`, exception — chosen per API, documented per edge).

```javascript
// GOOD: edges specified before implementation (matrix first, code second)
// longestNoRepeat: "" -> 0, "b" -> 1, "bbbb" -> 1, "abcabcbb" -> 3 (verified Domain 03 §2.2).
// minWindow: impossible -> "" (specified sentinel, verified); single-match -> itself.
// BAD: "works on samples" submitted without edge enumeration —
// hidden tests live at the borders; unenumerated edges are undiscovered verdicts
```

### 4) **Common confusion**

- "Clarifying wastes interview time" — clarifying *invests* two minutes to prevent twenty lost to wrong-problem code. Misread problems cost the whole session; questions cost seconds.
- "Constraints are hints, not specs" — constraints *are* the paradigm specification (rung ceilings, memory caps — the numbers that select algorithms). Hints suggest; specs decide.
- "Edge cases are bonus" — edges are the *majority* of hidden tests (borders, empties, extremes — judges test boundaries systematically). Bonus thinking ships WA verdicts.

### 5) **Performance note**

Method costs minutes (examples traced, constraints translated, matrix written) against wrong-problem rewrites (tens of minutes) and WA-debugging cycles (edge archaeology per verdict). Highest-leverage item is constraints-first (selects paradigm correctly); second is edge matrices (converts mysteries to checklist items). Minutes preventing rewrites — method's best attention rate.

### 6) **Mentor note**

Enforce hand-traces before approaches ("show me two examples worked by hand" — no technique discussion until structure observed). Drill constraint translation ("n-bound → rung → shortlist" until instantaneous). Demand edge matrices with examples (written together, tested together). Watch for the title-coder ("two sum — hash map, go" — fix with "work the examples first") and the sample-only tester ("works on samples" — fix with matrix enumeration as submission gate). Review check: examples traced, constraints translated, edges specified — and the mentor's own problem-solving modeling all three visibly.
