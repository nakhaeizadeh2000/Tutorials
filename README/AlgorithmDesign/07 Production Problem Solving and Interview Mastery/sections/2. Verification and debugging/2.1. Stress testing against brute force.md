## 2.1. Stress testing against brute force

### 1) **Oracles decide truth**

**Definition** — stress testing pits a slow-but-obviously-right implementation (brute force: exhaustive, simple, trusted by inspection) against the fast candidate on hundreds of randomized small inputs: any disagreement *is* a bug in the candidate (or, rarely, the oracle — both get inspected, but smart money backs simplicity). Verified methodology: Kadane vs brute-force max-subarray agree **500/500** on randomized length-≤12 arrays with values in [−10,10]. Agreement doesn't prove correctness (shared blind spots possible — different algorithms, same misreading), but disagreement proves *incorrectness* mechanically.

- **What problem it solves**: hand-picked tests verify examples, not logic (authors test what they thought of — bugs live in what they didn't: negative-only arrays, single elements, ties, overflow-adjacent values). Randomized oracles explore the unthought systematically (500 tiny cases cover shapes no human enumerates — empties, singletons, all-negative runs, alternating signs). The brute force is *also* the fallback submission (leaf 1.2's two-solution strategy — truth banked twice: verification now, partial credit later).
- **Modern guidance** — write the brute force first (obviously-right beats cleverly-fast for truth duty — nested loops welcome, no optimization allowed in oracles). Generate small random inputs (tiny sizes hit edges densely — length ≤ 12 covers empties-to-patterns; value ranges crossing zero/sign boundaries). Compare exactly (deep equality on outputs — mismatches print both inputs *and* both outputs for diagnosis). Keep oracles beside solutions (test files, not scratch — rerun on every refactor; truth that isn't repeated rots).

```javascript
// GOOD: truth automated — verified 500/500 agreement methodology
function stress(fast, brute, trials = 500) {
  for (let t = 0; t < trials; t++) {
    const n = 1 + Math.floor(Math.random() * 12);      // tiny: edges dense (empties via n=0 variant)
    const a = Array.from({ length: n }, () => Math.floor(Math.random() * 21) - 10);
    const f = fast(a), b = brute(a);
    if (f !== b) return { fail: a, fast: f, brute: b }; // disagreement IS the bug report
  }
  return { agree: trials };  // Kadane vs brute: 500/500 verified (agreement, not proof — see below).
}
// BAD: "tested on samples" as verification ("confident") —
// samples cover thoughts; oracles cover shapes — bugs live unthought
```

### 2) **Randomized agreement at scale**

**Definition** — hundreds of tiny randomized trials (not dozens of medium ones): small inputs maximize *shape* coverage per trial (empties, singletons, extremes, ties — dense in tiny spaces, sparse in large), while trial count maximizes *confidence* (500 agreements bound the bug rate tighter than 50 — each clean trial halves the remaining suspicion, roughly). Verified shape: 500 trials × ≤12 elements × [−10,10] values — full agreement in single-digit seconds. Scale trials to runtime budget (seconds of testing per solution — cheap enough to run per refactor, strong enough to catch most logic slips).

- **Why it matters (correctness)**: medium-input hand tests cover *values*, tiny randomized tests cover *shapes* (the structural edge cases — empty/single/duplicate/extreme — that hand tests forget and judges remember). Agreement across 500 shapes means the candidate handles everything small correctly — and most logic bugs are size-independent (wrong recurrence, missed edge, off-by-one — all visible at n ≤ 12). Large-input bugs (overflow, performance cliffs) need separate probes (leaf 1.2's sanity scans, Domain 01 §3.1's doubling) — stress covers logic, not scale.
- **Modern guidance** — bias generation toward edges (include empties, singletons, all-equal, extremes with extra probability — uniform random under-samples borders; edge-weighted generation oversamples where bugs live). Vary seeds per run (fixed seed reproduces, fresh seeds explore — CI uses fixed for determinism, developers use fresh for coverage). Count agreements as confidence, not proof (500/500 bounds suspicion — shared-blind-spot failures need independent oracles: second brute force via different method, or property checks like output-sortedness/monotonicity).

```javascript
// GOOD: edges oversampled, seeds fresh, agreement counted (methodology, not luck)
// gen: 20% edge shapes (empty/single/all-equal/extreme) + 80% uniform tiny (verified 500/500 pattern).
// CI: fixed seed (deterministic green); dev: fresh seeds each run (coverage grows per run).
// confidence: 500 clean trials ≈ suspicion halved 500 times (roughly — shared blind spots excepted).
// BAD: 5 medium hand tests ("representative") —
// representative of thoughts, not shapes; edge coverage accidental where stress makes it systematic
```

### 3) **Shrink failures minimally**

**Definition** — delta-debugging by hand: on disagreement, minimize the failing input (remove elements while failure persists — halve repeatedly: which half keeps the bug? — until the smallest reproducer remains). Minimal cases teach maximally (3-element failure exposes the logic slip; 12-element failure buries it in noise). The shrink loop: halve → retest vs oracle → keep failing half → repeat (binary search over inputs — Domain 02 §3.1's halving wearing debugging clothes).

- **Why it hurts when missing (correctness, maintainability)**: unshrunk failures debug by staring (12-element arrays with intertwined effects — which element matters? all of them, apparently; fixes address symptoms, bugs persist in smaller untested shapes). Shrunk failures debug by reading (3 elements, one violated invariant — the fix is evident, the test is permanent). Shrinking converts "fails sometimes" into "fails exactly here because" — the sentence that ends debugging sessions instead of extending them.
- **Modern guidance** — shrink before diagnosing (halve-until-minimal as reflex — diagnosis starts at the smallest reproducer, never the original). Automate the loop where valuable (delta-debugging scripts for recurring problem families — halve, test-vs-oracle, keep-failing-half). Preserve shrunk cases as regression tests (minimal reproducers *are* the edge matrix from leaf 1.1 — file them, don't discard). State the invariant violated alongside the fix ("window assumed distinctness; shrunk input `[a,a]` exposed it" — cause documented with cure).

```bash
# GOOD: shrink, then diagnose (smallest reproducer teaches most)
#  fail on 12 elements -> halve -> fails on 6 -> halve -> fails on 3 ([a,a,b]: duplicate handling).
#  diagnosis: last-seen guard missing `>= st` check (verified Domain 03 §2.2 pattern) — fix + regression test.
#  minimal case filed as edge test (matrix grows; future regressions caught, not rediscovered).
# BAD: debugging the 12-element failure directly ("more context helps") —
# noise buries signal; fixes address symptoms; shrunk cases never filed, bugs rediscovered quarterly
```

### 4) **Common confusion**

- "500 agreements prove correctness" — agreements *bound suspicion* (shared blind spots survive identically — independent second oracles or property checks close the gap). Proof needs reasoning; testing needs volume. Both, in that order.
- "Stress testing is only for contests" — oracles serve production refactors equally (optimized rewrite vs banked brute force — agreement monitored per deploy). Truth automation outlives any judge.
- "Hand tests suffice with experience" — experience predicts *common* bugs; oracles find *uncommon* ones (the distribution that matters — experience covers thoughts, randomness covers shapes).
- "Shrinking wastes debugging time" — shrinking *is* debugging (minimal cases diagnose themselves; originals obscure). Time spent shrinking returns 10× in diagnosis speed.

### 5) **Performance note**

Stress costs trials × (fast + brute) at tiny sizes (verified 500 trials single-digit seconds — cheap enough per refactor, strong enough per solution); shrinking costs log-steps × oracle-runs (halving converges fast — minimal cases in ~10 iterations from 1000-element failures); oracle maintenance costs one file beside the solution (rerun per change — pennies). Unverified shipping costs WA verdicts and production incidents (hours per ambiguous failure). Truth automation is the cheapest correctness control per dollar in problem solving.

### 6) **Mentor note**

Require stress harnesses beside every non-trivial solution ("where's the oracle?" — agreement monitored, not assumed). Drill shrinking live (12-element failure → 3-element diagnosis in front of juniors — the transformation teaches itself). Demand edge-weighted generation ("what shapes does uniform miss?" — empties, extremes, ties enumerated). Watch for the sample-only verifier ("confident" — fix with one oracle-found bug autopsied live) and the unshrunk debugger (staring at full failures — fix with halve-until-minimal as reflex). Review check: oracle banked, 500-trial agreement green, shrunk regressions filed, juniors can build harnesses unprompted.
