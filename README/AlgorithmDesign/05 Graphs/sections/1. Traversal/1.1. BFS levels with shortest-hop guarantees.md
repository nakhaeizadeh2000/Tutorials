## 1.1. BFS: levels with shortest-hop guarantees

### 1) **First visit is shortest**

**Definition** — breadth-first search visits vertices in nondecreasing hop-distance from the source (level 0, then 1, then 2 — FIFO order *is* distance order on unweighted graphs): the first time BFS reaches a vertex, no shorter path exists — longer paths are still queued behind it. Verified: from node 1, distances `1:0, 2:1, 3:1, 4:2` — level by level, exact. The guarantee needs unweighted edges (every hop costs 1 — weights break FIFO ordering; Dijkstra restores it in leaf 2.1) and a visited discipline (next section).

- **What problem it solves**: shortest-hop questions without BFS nest or guess — DFS finds *a* path (not shortest — depth-first arrival order is arbitrary in distance), repeated single-source scans cost `O(V·E)`, and "fewest connections" queries (degrees of separation, minimum moves, hop budgets) need distance, not reachability. BFS converts hop-counting into level enumeration: each level costs its frontier, total `O(V+E)`, distances proven by construction rather than compared after.
- **Modern guidance** — reach for BFS on unweighted shortest-path (grids with obstacles, word ladders, social hops, minimum-move puzzles — distance *is* levels). Terminate early on target found (first visit proves optimal — no need to drain the queue; state the early-exit explicitly). Prefer bidirectional BFS on huge graphs with known target (two frontiers halving the exponent — `b^(d/2)` each way vs `b^d` — the meeting check costs a hash lookup per expansion).

```javascript
// GOOD: levels prove distances — verified 1:0,2:1,3:1,4:2
function bfsDist(adj, s) {
  const d = new Map([[s, 0]]), q = [s];   // FIFO: dequeue order IS distance order (unweighted)
  while (q.length) {
    const u = q.shift();
    for (const v of adj.get(u) || []) {
      if (!d.has(v)) { d.set(v, d.get(u) + 1); q.push(v); }  // first visit = shortest (levels before)
    }
  }
  return d;
} // O(V+E) time (each vertex/edge processed once), O(V) space (distances + frontier).
// BAD: DFS "shortest path" by tracking min depth ("simpler, one function") —
// depth-first arrival is arbitrary in distance; min-tracking explores everything: O(V+E) work, no guarantee
```

### 2) **Visited sets prevent rework**

**Definition** — mark-on-*enqueue* (when discovered), never mark-on-dequeue: the vertex enters the visited set at push time, so parallel frontier edges can't enqueue duplicates. Mark-on-dequeue admits the same vertex many times (each undiscovered edge re-queues it — exponential rework on dense graphs, wrong counts where visit-count matters). The rule is one word apart in code (`d.set` before `q.push` vs after `q.shift`) and exponential apart in behavior.

- **Why it matters (correctness)**: enqueue-discipline bugs are silent-performant on trees (no revisits possible — tests pass) and catastrophic on dense graphs (re-enqueue avalanches: same vertex processed per incoming edge — `O(E)` extra work per vertex, timeouts on grids with 4-connectivity). Worse, distance corruption where first-visit-wins is assumed (dequeue-marked duplicates reprocess with stale distances — levels lie). The discipline converts BFS from "usually works" to "provably once-each."
- **Modern guidance** — mark at discovery always (set-then-push as an atomic two-liner — never separated by logic); audit with visit-counts in tests (each vertex dequeued exactly once — assert counts, not just distances); use distance-maps as visited-sets (presence *is* visited — one structure, two jobs, zero drift). For bipartite checks and connected-component sweeps (next leaf's cousins), the same discipline carries — mark-on-enqueue is BFS's universal hygiene.

```javascript
// GOOD: set-then-push atomic — duplicates impossible by construction
if (!d.has(v)) { d.set(v, d.get(u) + 1); q.push(v); }  // mark ON enqueue: parallel edges see it marked
// BAD: mark on dequeue ("equivalent") —
// dense graphs re-enqueue per edge (exponential rework); distance maps lie where first-visit assumed
```

### 3) **Levels structure the answer**

**Definition** — length-snapshot loops process exactly one level per iteration (`for (i = q.length; i > 0; i--)` — snapshot before draining): shortest-path lengths, level averages, zigzag alternation, right-side views, bipartite two-coloring (alternate colors per level — same-color edge proves odd cycle). The snapshot is what makes "level k" addressable — without it, BFS yields distances but not *groupings* (which vertices share a level, what the level aggregates to).

- **Why it hurts when missing (correctness, maintainability)**: level-shaped questions answered with raw distances regroup awkwardly (filter-by-distance passes per level — `O(levels × V)` re-scans; off-by-one level boundaries in zigzag/view problems). Snapshot loops emit levels directly (one pass, grouped output — the structure interviews expect). Bipartite checking *needs* level parity (color by level index — snapshots carry the index free). Levels are BFS's native output format; distances are the derived one.
- **Modern guidance** — snapshot per level when the question is level-shaped (views, averages, zigzag, bipartite — group during traversal, never regroup after). Carry depth explicitly only when snapshots don't fit (early-exit target search — distance map suffices). Test bipartite on odd cycles (triangle → non-bipartite detected — the three-node case that catches color-by-discovery shortcuts). State level semantics per use ("level = hops from source" — the sentence that prevents depth-confusion with DFS depths).

```javascript
// GOOD: levels emitted, not regrouped (snapshot loop)
function levels(adj, s) {
  const seen = new Set([s]), out = []; let q = [s];
  while (q.length) {
    const lvl = [], n = q.length;            // snapshot: exactly this level
    for (let i = 0; i < n; i++) {
      const u = q.shift(); lvl.push(u);
      for (const v of adj.get(u) || []) if (!seen.has(v)) { seen.add(v); q.push(v); }
    }
    out.push(lvl);
  }
  return out;
}
// BAD: distances first, group-by-distance after ("same info") —
// O(levels x V) regrouping plus boundary bugs; snapshot emits groups natively
```

### 4) **Common confusion**

- "BFS is slower than DFS" — same `O(V+E)` envelope (each vertex/edge processed once with mark-on-enqueue); BFS pays frontier memory (`O(V)` width) where DFS pays stack depth (`O(h)`). Different space shapes, identical time class.
- "BFS finds shortest paths" — shortest *unweighted-hop* paths (verified). Weighted edges need Dijkstra (leaf 2.1 — FIFO order stops proving optimality the moment hops cost differently).
- "Visited sets are optional on trees" — trees can't revisit (acyclic by definition — the discipline is vacuous, not absent). Graphs revisit constantly; the discipline is load-bearing exactly where trees don't need it.
- "`shift()` is fine for queues" — `shift()` is `O(n)` per dequeue (Domain 03 §3.1's tax — array reindexing). Fine at interview scale; head-index management past ~10⁴ dequeues. Know the tax before paying it at scale.

### 5) **Performance note**

BFS costs `V` dequeues + `E` edge inspections (verified probes single-digit ms at these sizes) with `O(V)` frontier space (width-bounded — grids hold rows, trees hold half). Bidirectional search squares the root of the exponent (`b^(d/2)` × 2 — the optimization that matters on huge implicit graphs). `shift()`-based queues add `O(V²)` reindexing worst-case (head indices or linked chunks past scale). Optimize visit discipline first (correctness before speed — rework dwarfs constants), queue mechanics second (head indices), bidirectionality third (known-target huge graphs only).

### 6) **Mentor note**

Teach FIFO-as-proof ("dequeue order *is* distance order — why?" until levels imply optimality reflexively), then break it with weights ("same graph, weighted edges — what breaks?" → leaf 2.1 motivation delivered as a question). Drill mark-on-enqueue with dense-grid rework arithmetic (re-enqueue counts on 4-connected grids convert skeptics). Demand snapshot loops for level-shaped questions ("group during, never after"). Watch for the DFS-shortest substituter ("simpler" — fix with arbitrary-arrival counterexample) and the dequeue-marker ("equivalent" — fix with dense-graph rework counts). Review check: enqueue-discipline visible, levels snapshotted where grouped, early-exit stated on target search, juniors can prove first-visit-shortest in one sentence.
