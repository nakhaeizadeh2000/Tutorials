## 2.1. Dijkstra: weighted shortest paths

### 1) **Cheapest-unsettled-first is optimal**

**Definition** — Dijkstra settles vertices in order of current-best distance (min-heap frontier: pop the cheapest unsettled vertex, finalize it, relax its edges): with *nonnegative* weights, finalization is forever-correct — any alternative path must pass through an unsettled vertex costing ≥ current (weights can't go negative, so no later discovery undercuts). Verified: distances from 1 → `1:0, 2:3, 3:2, 4:6` exact (note 3 < 2 in value but settled correctly — order follows distance, not labels). `O((V+E) log V)` with binary heaps (each edge relaxed once into the heap, each vertex extracted once).

- **What problem it solves**: weighted shortest paths without Dijkstra cost Bellman-Ford's `O(V·E)` (correct but slow — the generality tax) or BFS-shaped wrongness (hop-counting on weighted graphs — verified-wrong wherever weights differ). Dijkstra occupies the sweet middle: optimal *and* efficient for the most common weight regime (nonnegative — road networks, link costs, game grids with movement prices). The settling order *is* the proof made mechanical: finalization sorted by distance, each step irrevocable because nonnegativity forbids surprises.
- **Modern guidance** — reach for Dijkstra on static nonnegative weights (routing, maps, game pathing — the default weighted-shortest engine). Implement with the domain's heaps (Domain 04 §3.1's PQ serves the frontier — decrease-key via lazy deletion: push duplicates, skip stale pops — simpler and usually faster than textbook decrease-key). Terminate early on target settle (first finalization of the destination *is* optimal — no need to drain the frontier). State nonnegativity as precondition ("requires w ≥ 0" — the sentence that prevents the next section's incident).

```javascript
// GOOD: settling order proves distances — verified 1:0,2:3,3:2,4:6
function dijkstra(adj, s) {
  const INF = Number.POSITIVE_INFINITY;
  const d = new Map([[s, 0]]), done = new Set(), pq = [[0, s]];  // frontier: [dist, node]
  while (pq.length) {
    pq.sort((a, b) => a[0] - b[0]);            // (production: binary heap, Domain 04 §3.1)
    const [du, u] = pq.shift();
    if (done.has(u)) continue;                 // stale duplicate: skip (lazy deletion)
    done.add(u);                               // settle: cheapest-unsettled, final (w >= 0)
    for (const [v, w] of adj.get(u) || []) {
      const nd = du + w;
      if (nd < (d.has(v) ? d.get(v) : INF)) { d.set(v, nd); pq.push([nd, v]); }
    }
  }
  return d;
} // O((V+E) log V) time (heap ops dominate), O(V) space. Nonnegative weights ONLY (next section).
// BAD: BFS "shortest path" on weighted graphs ("distances are small") —
// hop-counting ignores weights entirely; verified-wrong wherever prices differ
```

### 2) **Heaps serve the frontier**

**Definition** — the priority queue *is* Dijkstra's engine room: extract-min selects the next settlement (`O(log V)`), relaxations push candidates (`O(log V)` each, ≤ `E` pushes), lazy deletion skips stale duplicates (re-relaxed vertices leave corpses in the heap — popped, recognized settled-or-outdated, discarded). Total: `O((V+E) log V)` with binary heaps (each vertex extracted once usefully, each edge relaxed once into the heap). Fibonacci heaps improve to `O(E + V log V)` theoretically — rarely implemented (constants + complexity vs binary-heap practicality — the theory/practice split stated honestly).

- **Why it matters (correctness)**: frontier mechanics decide both complexity and correctness-adjacent behavior (stale-skip logic *is* the lazy-deletion contract — missing it reprocesses corpses: still correct via done-set, slower by duplicates; array-scanned minima ("simpler") bill `O(V)` per extraction → `O(V²)` total — fine below ~10³ vertices, dominating past). The heap isn't an optimization atop Dijkstra — it *is* Dijkstra's selection step, and its `log V` is where the complexity lives.
- **Modern guidance** — use binary heaps (library or five-line sift — Domain 04 §3.1) for the frontier; lazy deletion over textbook decrease-key (simpler, usually faster — stale corpses cost heap space, save index bookkeeping). Size the frontier honesty (`O(E)` heap entries worst-case with duplicates — memory follows edges, not vertices). For dense graphs (`E ≈ V²`), plain-array minima (`O(V²)` total, no heap overhead) can win constants — know the crossover, measure past 10⁴ vertices. Never hand-roll Fibonacci heaps in application code (theoretical win, practical loss — borrow binary, cite theory).

```javascript
// GOOD: lazy deletion — corpses skipped, books unbalanced never
if (done.has(u)) continue;   // stale duplicate from re-relaxation: discard, no reprocessing
// (textbook decrease-key updates heap position in place — O(log V) with index maps;
//  lazy push-duplicate + skip-stale matches it amortized with a tenth of the code.)
// BAD: decrease-key hand-rolled with index maps ("optimal") —
// correct but intricate; lazy deletion wins engineering (simpler, measured-equivalent) nearly always
```

### 3) **Negatives need Bellman-Ford**

**Definition** — negative edges break settling-finality: a finalized vertex can later be undercut via a negative edge (verified premature finality — node 2 settled at **4** while the true shortest via node 3 is **2**: finalization lied, nonnegativity was the warranty). Bellman-Ford answers: relax *all* edges `V−1` times (paths use ≤ `V−1` edges without cycling — after that, distances are optimal), then one more pass detects negative *cycles* (further relaxation possible ⟺ exploitable loop — arbitrage, the use case that needs detection, not just distances). Cost: `O(V·E)` time (generality priced), `O(V)` space.

- **Why it hurts when missing (correctness, maintainability)**: Dijkstra-on-negatives fails *silently* (distances returned, some wrong — verified settle-at-4 vs true-2: no error, no warning, just a wrong number in a map). The failure hides in mixed graphs (one negative edge among thousands — tests pass on positive subgraphs, production routes through the negative one). Negative *cycles* are worse (shortest undefined — unbounded exploitation; Bellman-Ford's extra pass names them, Dijkstra loops or lies). Weight-sign auditing is the precondition check most teams skip and most postmortems cite.
- **Modern guidance** — audit weight signs before choosing (all ≥ 0 → Dijkstra; any negative → Bellman-Ford or reweighting; negative cycles possible → Bellman-Ford's detection pass mandatory). Prefer Johnson's reweighting for all-pairs with sparse negatives (Bellman-Ford once for potentials + Dijkstra per source — the composition that beats `V` Bellman-Fords). Treat negative-cycle detection as a feature (arbitrage/currency – the detector *is* the product there). Verified pair as team lore: settle-4-vs-true-2 (finality needs nonnegativity) and Bellman-Ford `[0,2,5]` (generality costs `V·E`).

```javascript
// GOOD: sign audit picks the algorithm (verified pair as evidence)
function bellmanFord(edges, V, s) {
  const d = new Array(V).fill(Infinity); d[s] = 0;
  for (let i = 0; i < V - 1; i++)                     // V-1 passes: simple paths need no more
    for (const [u, v, w] of edges) if (d[u] + w < d[v]) d[v] = d[u] + w;
  return d;  // +1 pass for negative-cycle detection (further relaxation ⟺ exploitable loop)
} // verified [0,2,5] where Dijkstra settled 2@4 (wrong): generality O(V*E) vs Dijkstra O((V+E) log V).
// BAD: Dijkstra "with a negative-edge filter" (clamp to zero? absolute values?) —
// transforms the problem instead of solving it; shortest on doctored weights answers nothing asked
```

### 4) **Common confusion**

- "Dijkstra works with small negatives" — any negative edge voids the finality proof (verified settle-4-vs-true-2 on weights 4, 5, −3 — smallness irrelevant). Nonnegativity is binary: holds or the proof doesn't.
- "Bellman-Ford is just slower Dijkstra" — different guarantees (negative-capable + cycle-detecting vs fast settling), different use (audited-negative graphs, arbitrage detection). Slower *and* stronger — the trade, not a ranking.
- "Settled means visited" — settled means *finalized* (distance proven — the heap order guarantees it under nonnegativity); visited in BFS/DFS means *seen* (leaf 1.1–1.2 — no optimality attached). Finality is Dijkstra's exclusive property.
- "Priority queues sort the frontier" — heaps serve extremes on demand (Domain 04 §3.1 — internal order heap-shaped, not sorted). Sorted output would cost `n log n` per selection round; extreme-serving costs `log n`.

### 5) **Performance note**

Dijkstra costs `(V+E)` heap ops at `log V` each (verified probes single-digit ms; constants favor binary heaps over Fibonacci in practice — theory/practice split honored); Bellman-Ford costs `V·E` relaxations (the generality tax — 100×+ slower on dense graphs, worth it exactly when negatives exist); lazy deletion adds heap-space overhead per re-relaxation (bounded by `E` corpses — memory follows edges). Optimize algorithm choice first (sign audit picks the rung), heap mechanics second (binary + lazy), Fibonacci never (application code).

### 6) **Mentor note**

Demonstrate premature finality live (settle-2@4 vs true-2 — "finalization lied; nonnegativity was the warranty" converts sign-auditing from pedantry to survival). Narrate settling order as proof ("cheapest-unsettled finalized — why can't anything undercut it?" until nonnegativity answers itself). Drill the sign audit as review gate ("weights ≥ 0? prove it from the domain, not the tests"). Watch for the BFS-on-weighted substituter ("distances are small" — fix with priced counterexample) and the negativity-minimizer ("just one negative edge" — fix with verified settle-4-vs-true-2 on exactly that shape). Review check: nonnegativity stated or Bellman-Ford chosen, heap serving frontier (no array-scan past scale), early-exit on target settle, juniors can narrate finality proof in two sentences.
