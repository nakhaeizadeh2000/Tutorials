## 2.2. Union-find: connectivity in near-constant time

### 1) **Union by rank, find with compression**

**Definition** — disjoint-set union over a forest: `find` follows parent pointers to the root (path compression flattens visited nodes onto the root — future finds skip levels); `union` attaches shorter tree under taller (union by rank/size — depth stays logarithmic without compression, near-flat with it). Combined amortized cost: inverse Ackermann `α(n)` — below 5 for every input that fits in the universe (effectively constant, honestly near-constant). Verified: unions (0,1),(3,4) → `0~1:true, 0~2:false`, repeat-union `false` (already united — idempotent, the contract that prevents double-counting).

- **What problem it solves**: dynamic connectivity (edges arriving over time — "are these connected *yet*?") defeats static sweeps (re-traverse per query: `O(Q·(V+E))` — leaf 1.2's tax, restated for evolving graphs) and adjacency matrices (union is not a matrix operation). Union-find maintains connectivity incrementally: near-constant per operation, `O(n)` memory, online by construction. Kruskal's MST (cheapest edges first, union-if-disjoint — spanning for free as a side effect), percolation, network partitions, and image regions all reduce here.
- **Modern guidance** — implement both optimizations together (rank + compression — either alone gives logarithmic; together give Ackermann; the pair is one idea: keep trees flat). Return booleans from union (merged vs already-united — callers count components/edges without re-querying). Prefer iterative find in production hand-rolls (recursion depth follows pre-compression chains — bounded in practice, explicit on principle). Size parent/rank arrays at construction (static sizing is the structure's contract — dynamic node addition needs remapping discipline).

```javascript
// GOOD: flat by construction — verified true/false/false semantics
function UnionFind(n) {
  const parent = [...Array(n).keys()], rank = new Array(n).fill(0);
  function find(x) { return parent[x] === x ? x : (parent[x] = find(parent[x])); }  // compress on the way up
  function union(a, b) {
    a = find(a); b = find(b);
    if (a === b) return false;                    // already united: idempotent (verified)
    if (rank[a] < rank[b]) [a, b] = [b, a];       // shorter under taller (rank discipline)
    parent[b] = a;
    if (rank[a] === rank[b]) rank[a]++;
    return true;
  }
  return { find, union };
} // amortized α(n) per op (effectively constant), O(n) space. Both optimizations or neither.
// BAD: naive parent-chasing without compression ("simpler") —
// degenerate chains bill O(n) per find; the "simplification" removes the entire analysis
```

### 2) **Connectivity and cycle questions collapse**

**Definition** — one primitive answers a family: same-set (`find(a)===find(b)` — connectivity queries in near-constant), cycle-on-arrival (union returns false ⟺ edge closes a loop — Kruskal's filter: sort edges by weight, union-if-disjoint, skip-if-united → MST in `O(E log E)` dominated by the sort), component counting (successful unions decrement a counter from `n` — islands without traversal). Each reduces graph questions to equality checks — the sweep from leaf 1.2, made incremental.

- **Why it matters (correctness)**: cycle detection per inserted edge via traversal costs `O(V+E)` *each* (dynamic graphs pay per arrival — `m` arrivals bill `m·(V+E)`); union-find bills `α(n)` each (total near-linear — the gap that decides online feasibility). Kruskal without union-find sorts then re-verifies acyclicity by DFS per edge (correct, quadratic-ish); with it, the sort dominates and the structure disappears into the background. Collapsing questions to one primitive also collapses testing (one invariant — partition maintained — instead of per-algorithm correctness arguments).
- **Modern guidance** — reach for union-find on incremental connectivity (network links, percolation thresholds, Kruskal, dynamic islands — merges over time). Count components with a decrementing counter (unions that succeed reduce the count — `O(1)` answer to "how many?" at any moment). Prefer Kruskal for sparse MST (sort + union-find — simple, near-optimal); Prim's heap variant for dense (fewer edges than vertices-squared flips the choice — density decides, per Domain 05's modeling leaf). State idempotence in docs (repeat-union `false` — callers rely on it for edge deduplication).

```javascript
// GOOD: Kruskal — sort dominates, union-find disappears into the background
function kruskal(n, edges) {
  edges.sort((a, b) => a[2] - b[2]);              // sort by weight: O(E log E) dominates
  const uf = UnionFind(n); let cost = 0; const mst = [];
  for (const [u, v, w] of edges)
    if (uf.union(u, v)) { cost += w; mst.push([u, v]); }  // false = would cycle: skipped
  return { cost, mst };
} // O(E log E) time, O(n) space. Cycle check per edge: α(n) — traversal-free.
// BAD: DFS-per-edge cycle checks in Kruskal ("no extra structure") —
// O(E·(V+E)) total where α(n)-per-edge applies; structure-blindness billing multiplicatively
```

### 3) **Dynamic connectivity's only structure**

**Definition** — fully-dynamic connectivity (insertions *and* deletions of edges with queries interleaved) is genuinely hard (polylogarithmic structures exist — Euler-tour trees, Holm-de-Lichtenberg-Thorup — research-grade, rarely shipped); but *incremental-only* (insertions/merges, no deletions — union-find's home) covers the practical majority (network build-up, percolation, Kruskal, agglomerative clustering). Deletions need offline divide-and-conquer (segment-tree-over-time: add edges to covering intervals, DFS with rollback union-find — advanced, named here for completeness, detailed in specialized treatments).

- **Why it hurts when missing (correctness, maintainability)**: deletion-capable requirements met with union-find corrupt silently (no un-union exists — "remove edge" has no inverse; implementations that fake it by rebuilding bill `O(n)` per deletion while claiming dynamic). The failure is architectural (wrong structure for the workload — discovered when deletions arrive, quarters after the choice). Naming the boundary up front (incremental → union-find; fully-dynamic → research structures or offline division) prevents the most expensive category of rework: correct code for the wrong problem.
- **Modern guidance** — choose by mutation profile (insertions-only → union-find, no hesitation; deletions required → offline segment-tree + rollback, or literature structures with eyes open; queries-only on static graphs → one sweep, leaf 1.2). Implement rollback-capable union (no path compression — union-by-rank alone, changes logged on a stack — undoable in LIFO order) where offline division applies. Document the mutation contract beside the structure ("insertions only — deletions unsupported by design" — the sentence that prevents architectural mismatch).

```bash
# GOOD: mutation profile picks the structure (decided before code, not during incidents)
#  static graph, batch queries  -> one sweep (leaf 1.2) — no dynamic structure needed
#  insertions only               -> union-find (this leaf) — α(n), online, simple
#  insertions + deletions        -> offline segment-tree + rollback UF (advanced) or literature
# BAD: union-find "extended" with deletion support by rebuilding per delete ("pragmatic") —
# O(n) per deletion mislabeled dynamic; the profile demanded research structures, got rework
```

### 4) **Common confusion**

- "Union-find is `O(1)`" — amortized inverse-Ackermann (effectively constant, honestly near-constant — the analysis names Ackermann; the practice never observes above 5). Precision matters because the proof (rank + compression together) is the screened knowledge.
- "Rank means subtree size" — rank bounds *height* (union attaches shorter under taller; path compression doesn't maintain exact heights — rank stays a valid upper bound, which is all union needs). Size-variant exists separately (attach smaller under larger — equivalent guarantees, different bookkeeping).
- "Kruskal needs union-find" — Kruskal needs *cycle testing per edge in weight order*; union-find is the near-constant implementation (DFS-per-edge is the correct-but-slow twin). Structure serves algorithm; algorithm doesn't require structure.
- "Components need traversal" — static components need one sweep (leaf 1.2); union-find serves *incremental* merges. Same answers, different workloads — match structure to mutation profile.

### 5) **Performance note**

Union-find costs `α(n)` amortized per op (verified probes single-digit ms; constants tiny — array accesses + occasional recursion), `O(n)` memory (two integer arrays — the leanest structure in this domain). Kruskal costs `E log E` sort + `E·α(V)` unions (sort dominates past dozens of edges — structure choice never the bottleneck). Rebuild-per-delete costs `O(n)` each (the fake-dynamic tax — profile mismatch priced). Optimize mutation-profile matching first (right structure for the workload), rank+compression pairing second (both or logarithmic), array layout third (cache-friendly flat arrays beat node objects).

### 6) **Mentor note**

Teach flatness with the two optimizations as one idea ("shorter-under-taller builds shallow; compression flattens stragglers — together Ackermann"). Demonstrate idempotence live (repeat-union `false` — "already united" as contract, not accident). Place structures by mutation profile as a group exercise (static/insert-only/fully-dynamic → sweep/union-find/offline — routing drills). Watch for the compression-skipper ("simpler without" — fix with degenerate-chain arithmetic) and the deletion-faker (rebuild-per-delete "dynamic" — fix with profile honesty). Review check: both optimizations present, union boolean consumed (counts/edges, not re-queries), mutation contract documented, juniors can narrate Ackermann-intuition in one sentence ("trees stay flat, finds flatten stragglers").
