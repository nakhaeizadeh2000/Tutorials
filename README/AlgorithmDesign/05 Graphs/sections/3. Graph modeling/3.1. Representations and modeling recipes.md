## 3.1. Representations and modeling recipes

### 1) **Lists for sparse, matrices for dense**

**Definition** — adjacency lists (per-vertex neighbor arrays — `Map<V, V[]>`) cost `O(V+E)` memory and iterate neighbors in degree time; adjacency matrices (`V×V` booleans/weights) cost `O(V²)` memory with `O(1)` edge queries. Verified arithmetic: sparse `V=10⁴,E=2·10⁴` → lists **391KB** vs matrix **95MB** (243× gap — matrices drown sparse graphs); dense `V=10³,E=5·10⁵` → lists 7820KB vs matrix **977KB** (matrices win where edges saturate). Representation follows density — the choice is arithmetic, not taste.

- **What problem it solves**: representation mismatch bills structurally — matrices on sparse graphs waste 99%+ memory (95MB holding 391KB of edges — the OOM that "shouldn't" happen), lists on dense graphs waste iteration (neighbor scans over mostly-present edges where matrix indexing is constant). Worse, edge-existence queries flip cost (`O(1)` matrix vs `O(degree)` list) — dense algorithms (Floyd-Warshall, dense Prim) assume matrix-speed lookups. Density decides once; everything downstream inherits.
- **Modern guidance** — default to adjacency lists (most real graphs are sparse — social, web, road, dependency graphs all sit far below `V²` edges). Reach for matrices on dense graphs (complete-ish, Floyd-Warshall contexts, bitset-optimized traversals — bitsets compress matrices 64× and vectorize neighbor ops). Store weights alongside (list-of-pairs, matrix-of-numbers-with-∞ — representation carries weights natively, never in side maps). State density with the choice ("sparse: lists" — one line that prevents matrix-rot).

```javascript
// GOOD: density decides — verified 243x gap sparse, matrix win dense
// sparse (social/web/road: E << V^2) -> Map<V, V[]> adjacency lists: O(V+E) memory, degree-time neighbors.
// dense (complete-ish, Floyd contexts) -> V x V matrix/Uint8Array: O(V^2) memory, O(1) edge queries.
// weights: list-of-[v,w] pairs or matrix-of-numbers (Infinity = absent) — carried natively, never sided.
// BAD: matrix "for simplicity" on a 10^6-vertex sparse graph —
// 10^12 cells (terabytes) holding 10^7 edges; simplicity billing in petabytes
```

### 2) **Model statements into vertices and edges**

**Definition** — graph modeling translates problem statements: grid cells → vertices, moves → edges (maze/shortest-path); words → vertices, one-letter-diffs → edges (word ladder); tasks → vertices, prerequisites → directed edges (scheduling — leaf 1.2's topo); states → vertices, transitions → edges (puzzles, parsers — implicit graphs below); people/flights/packages → vertices, relationships → weighted edges. The translation *is* the solution's hard half — algorithms after modeling are textbook invocations (BFS/Dijkstra/topo from leaves 1.1–2.1).

- **Why it matters (correctness)**: modeling errors produce correct algorithms on wrong graphs (8-connectivity assumed where 4-connectivity rules — diagonal "shortcuts" through walls; undirected edges where directedness matters — one-way streets traversed backwards; unweighted hops where costs differ — BFS on weighted terrain). Each passes unit tests (small hand-made graphs match the modeler's mental image) and fails production (real maps violate the assumption). Model-checking ("does every edge correspond to a legal move?") precedes algorithm selection, always.
- **Modern guidance** — write the mapping explicitly before code (vertices = ?, edges = ?, directed?, weighted? — four answers that select BFS/Dijkstra/topo/union-find per the checklist leaf). Verify edges against rules (each generated neighbor legality-checked — the verified grid probe excludes blocked/out-of-bounds: `(1,1)` in 3×3 blocked `(1,2)` → exactly `[[2,1],[0,1],[1,0]]`). Test the model separately from the algorithm (neighbor-generation unit tests — modeling bugs isolated from traversal bugs). Reuse canonical reductions (grid→BFS, prerequisites→topo, links→Dijkstra, connectivity→union-find — the interview playbook from leaf 5.1).

```javascript
// GOOD: mapping explicit, neighbors verified (blocked + bounds excluded)
// vertices: free cells; edges: 4-moves to free cells (undirected, unweighted -> BFS shortest).
// gridNbrs(1,1) in 3x3 blocked(1,2) -> [[2,1],[0,1],[1,0]] verified (3 of 4: wall excluded).
// algorithm follows mapping: unweighted hops -> BFS (leaf 1.1); costs -> Dijkstra (leaf 2.1).
// BAD: "graph search" on hand-rolled adjacency built inline ("faster to just code") —
// modeling errors hide inside traversal code; separate mapping (tested) from walking (textbook)
```

### 3) **Implicit graphs search without building**

**Definition** — implicit graphs generate neighbors on demand (function of state, not stored structure): puzzle states (8-puzzle moves computed per position), word ladders (one-letter variants generated per word — alphabet × length candidates filtered by dictionary-set), game trees (moves from rules). Memory drops from `O(states)` to `O(frontier)` — infinite state spaces become searchable (the graph *exists* mathematically, never materially). BFS/DFS/Dijkstra run unchanged atop generator functions — algorithms consume neighbor-iterables, not adjacency structures.

- **Why it hurts when missing (correctness, maintainability)**: materializing implicit graphs explodes (8-puzzle: 181k states storable, barely; Rubik's: 43 quintillion — unbuildable; word ladders over full dictionaries: edges quadratic in vocabulary). Teams that build-first hit memory walls where generate-on-demand walks free — and precomputation also *stales* (dynamic obstacles, changing dictionaries — rebuilt graphs rot; generators read current truth). Implicit search trades repeated neighbor computation for unbounded reach — the only trade that scales to state spaces larger than RAM.
- **Modern guidance** — generate neighbors per expansion (pure function of state + rules — testable in isolation, the verified grid probe *is* an implicit generator). Memoize visited by state-hash (Map from encoded state — the visited discipline from leaf 1.1, keyed by serialization). Bound the search explicitly (depth caps, visited caps, beam widths — infinite spaces need termination contracts, not hope). Prefer bidirectional implicit search with known targets (two generators halving depth — leaf 1.1's exponent-halving, now memory-free on both sides).

```javascript
// GOOD: states computed, never stored (verified generator + BFS consumption)
// neighbors(state) -> legal moves (pure, tested: grid probe above).
// BFS over generator: visited-Map keyed by state encoding; frontier only in memory.
// 8-puzzle: 181k states reachable but never materialized together — O(frontier) memory.
// BAD: precomputing full game graphs "for speed" —
// memory walls at state-space scale; generators trade recomputation for unbounded reach
```

### 4) **Common confusion**

- "Graphs need Graph classes" — graphs need *neighbor access* (adjacency, generator, matrix row — the algorithm consumes an interface, not a class). Over-engineered Graph frameworks obscure the mapping that matters.
- "Dense graphs are rare" — dense appears in disguise (complete pairwise similarities, Floyd-Warshall contexts, tournament brackets, correlation matrices). Density is measured, not assumed — count edges before representing.
- "Implicit search is approximate" — implicit search is *exact* with full visited discipline (same BFS/Dijkstra guarantees — generation changes storage, not semantics). Approximation enters only with caps/beam cutoffs (stated explicitly when used).
- "Modeling is obvious, algorithms are hard" — inverted: algorithms are textbook (this domain), modeling is the screened skill (translation errors outnumber traversal bugs 10-to-1 in interviews and incidents). Budget accordingly.

### 5) **Performance note**

Representation costs verified arithmetic (391KB vs 95MB sparse — representation *is* the memory budget at scale); implicit generation costs recomputation per expansion (neighbor function × visits — cache hot generators where profiles point); modeling costs nothing at design, everything when wrong (wrong-graph-correct-algorithm incidents debug as algorithm failures — misattributed hours). Optimize representation first (density arithmetic), generation purity second (testable neighbors), modeling verification third (edge-legality unit tests).

### 6) **Mentor note**

Teach density with the verified arithmetic (391KB vs 95MB — "representation follows density" lands as money, not advice). Drill modeling as translation ("vertices = ?, edges = ?, directed?, weighted?" — four answers before any algorithm talk). Demonstrate implicit search on grids first (verified neighbor probe — generation testable in isolation), then word ladders (dictionary-filtered variants — the canonical implicit interview problem). Watch for the matrix-default ("simpler" — fix with sparse arithmetic on their own sizes) and the build-first modeler (materializing state spaces — fix with "generate per expansion" plus memory math). Review check: representation justified by density, mapping explicit with legality tests, implicit where state spaces exceed RAM, juniors can model-then-select aloud.
