## 4.1. Graphs checklist (habits mentors insist on)

### 1) **Weighted? Directed? Cyclic?**

**Definition** — three questions pick the algorithm before any code: *weighted?* (no → BFS levels; yes → Dijkstra if ≥ 0, Bellman-Ford if negatives possible); *directed?* (cycle semantics, topological validity, indegree/outdegree bookkeeping differ); *cyclic?* (DAG → topological orderings available; cyclic → shortest-path and ordering need cycle-tolerant variants). Unasked questions default wrong (BFS on weighted, topo on cyclic, undirected handling on directed).

- **What problem it solves**: algorithm-first graph code misfires structurally — Dijkstra imported for hop-counting (overkill hiding sign-blindness), DFS-topo attempted on cyclic graphs (order emitted, invalid — no error, just a "sort" violating edges), BFS on weighted terrain (verified-wrong distances, Domain 05 §2.1's warning wearing checklist clothes). Three questions in review ("weighted? directed? cyclic?") take thirty seconds and prevent the quarter's graph incident — selection by properties, not by familiarity.
- **Modern guidance** — ask in order (weights decide BFS/Dijkstra/Bellman-Ford; directedness decides cycle/topology handling; cyclicity decides ordering availability), document answers beside the algorithm choice ("unweighted undirected grid → BFS; nonneg weighted digraph → Dijkstra"). Re-ask when inputs evolve (unweighted today, priced tomorrow — weights arrive with feature requests; the checklist item that catches drift). Default on ignorance to the general variant (Bellman-Ford tolerates what Dijkstra assumes — slower, safer; then measure into specificity).

```bash
# GOOD: properties pick the algorithm (thirty seconds, zero incidents)
#  unweighted + any direction -> BFS (levels prove hops)
#  weighted >= 0              -> Dijkstra (settling proves distances)
#  weights possibly negative  -> Bellman-Ford (detection included)
#  ordering needed + DAG      -> topo (postorder reversed); cyclic -> order impossible, say so
# BAD: "we use Dijkstra everywhere" (hop-counting overkill + sign-blindness) or
#      "topo sort the dependencies" on cyclic input (invalid order emitted silently)
```

### 2) **Visited discipline stated**

**Definition** — BFS marks on *enqueue* (leaf 1.1 — parallel edges must see it marked), DFS colors three ways on directed cycle duty (leaf 1.2 — gray/black separation is the proof), Dijkstra settles once via heap order (leaf 2.1 — finality needs nonnegativity), union-find compresses on find (leaf 2.2 — flattening amortizes). Each discipline is stated per traversal ("mark-on-enqueue", "three colors", "settle-once", "compress-on-find") — unstated discipline is where rework avalanches, false cycles, premature finalities, and degenerate chains breed.

- **Why it matters (correctness)**: visited-discipline bugs are silent-performant on easy inputs (trees need no discipline — tests pass; sparse graphs forgive) and catastrophic on real ones (dense re-enqueues, diamond false-cycles, negative undercuts, chain finds). The pattern recurs per algorithm because each traversal *redefines* what "seen" means (discovered vs finished vs finalized vs flattened). Stating the local meaning converts discipline from folklore ("always use visited sets") into mechanism (which set, marked when, guaranteeing what).
- **Modern guidance** — write the discipline beside the traversal (comment first: "mark-on-enqueue: parallel edges see it"; "gray = on path: re-entry proves cycle"). Assert visit-counts in tests (each vertex dequeued/processed exactly once — counts catch discipline drift before distances lie). Review discipline before logic (correct updates with wrong marking still fail — marking is load-bearing, not boilerplate). When porting traversals across graph types (directed ↔ undirected), re-derive the discipline (parent exceptions, color needs — ports break exactly here).

```javascript
// GOOD: discipline stated per traversal (the sentence reviewers check)
// BFS: mark ON enqueue (d.set before q.push) — parallel edges see it marked.
// DFS cycles: three colors (gray re-entry proves; black skips finished).
// Dijkstra: settle once via heap order (finality needs w >= 0 — stated beside).
// Union-find: compress on find (flatten stragglers; rank disciplines union).
// BAD: bare `visited.add()` with no when/why ("standard") —
// standard for which traversal? enqueue, finish, settle, and flatten differ — unstated drifts
```

### 3) **Model before code**

**Definition** — vertices, edges, weights, directedness explicit *before* traversal code (leaf 3.1's mapping discipline): what each vertex represents, what each edge permits, what weights price, which questions the model must answer. Translation errors (8- vs 4-connectivity, directedness dropped, weights ignored, states conflated) outnumber traversal bugs 10-to-1 — modeling is the screened skill, algorithms the textbook invocation after.

- **Why it hurts when missing (correctness, maintainability)**: model-first failures hide inside correct traversals (BFS perfect on the wrong graph — distances exact for edges that shouldn't exist; Dijkstra optimal over mispriced weights — precision on fiction). Debugging misattributes (traversal code audited repeatedly while the mapping stays wrong — hours spent on correct code). The mapping line ("vertices = free cells, edges = 4-moves, unweighted undirected") takes seconds to write and anchors every subsequent review comment to something checkable.
- **Modern guidance** — write the mapping as the file's first comment block (vertices/edges/weights/directedness — four lines, reviewable). Unit-test neighbor generation separately (legality assertions — leaf 3.1's verified grid probe as template). Reuse canonical reductions where they fit (grids→BFS, prerequisites→topo, links→Dijkstra, merges→union-find — recognition over invention). Re-verify mapping when rules change (movement rules, costs, directedness evolve with features — the model rots first, silently).

```bash
# GOOD: mapping first, algorithm second (four lines that prevent misattribution)
#  vertices: free grid cells; edges: 4-moves to free cells; weights: none; directed: no.
#  -> BFS shortest hops (leaf 1.1). Neighbor legality unit-tested (leaf 3.1 probe shape).
# BAD: traversal code with the model implicit ("graph search over the grid") —
# 4-vs-8 connectivity unstated, weights unmentioned; debugging audits correct BFS for mapping sins
```

### 4) **Common confusion**

- "Checklists replace graph fluency" — checklists *route* to the right algorithm with the right discipline; fluency executes traversals. Routing first (properties → algorithm → discipline), execution second.
- "Small graphs don't need checklists" — small graphs need them *most* (tests pass without discipline — dense rework, false cycles, and sign-blindness surface at scale, far from the code). Properties are cheapest to check when graphs are smallest.
- "Visited is visited" — discovered ≠ finished ≠ finalized ≠ flattened (four meanings across four traversals). One word, four contracts — state which.

### 5) **Performance note**

The checklist costs a minute per graph problem (three property questions, discipline line, mapping block) against structural incidents (wrong-algorithm distances, silent invalid orders, rework avalanches — hours of debugging correct code for wrong selections). Highest-leverage item is properties-first (selects algorithm + discipline together); second is mapping-explicit (isolates translation bugs from traversal bugs). Minutes preventing misattribution — graphs' best attention rate.

### 6) **Mentor note**

Convert this leaf into the domain's selection runbook: properties → algorithm → discipline → mapping, in that order, every time. Quiz juniors on routing ("weighted digraph with possible negatives?" → Bellman-Ford; "ordering over dependencies?" → topo-with-cycle-check; "merges over time?" → union-find) until answers are environmental. Watch for checklist decay (properties asked for a sprint, assumed thereafter — fix with mapping blocks as review-blocking) and discipline drift ("visited is visited" — fix with per-traversal meaning drills). Review check: properties documented, discipline stated, mapping tested — and the mentor's own graph code modeling all three visibly.
