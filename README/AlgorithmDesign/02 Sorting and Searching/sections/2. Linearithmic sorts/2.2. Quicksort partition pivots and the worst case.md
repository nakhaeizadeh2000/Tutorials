## 2.2. Quicksort: partition, pivots, and the worst case

### 1) **Partition around a pivot, recurse both sides**

**Definition** — pick a pivot value, rearrange so smaller elements precede it and larger ones follow (one linear pass — the *partition*), then sort both sides recursively. Two classic partition shapes: *Lomuto* (single index sweeping, pivot parked at the end — simple, more swaps) and *Hoare* (two indices converging from both ends — fewer swaps, subtler invariant). Either shape plus recursion is quicksort; the invariant ("left of the boundary < pivot ≤ right") is what makes it correct, and stating it is what makes implementations reviewable.

- **What problem it solves**: merge sort's guarantee costs `O(n)` scratch (previous leaf) — quicksort sorts in place (`O(log n)` stack average) with superb constants (tight inner loop, cache-friendly sequential-ish access, no merge buffer traffic). For general in-memory sorting without stability requirements, nothing beats well-engineered quicksort per element — which is why it dominated libraries for decades and still rules where stability is waived.
- **Modern guidance** — implement Lomuto for clarity (interviews, teaching — the invariant fits in one sentence), Hoare for production hand-rolls (fewer swaps, better partition balance on duplicates with 3-way variants). In real code, supply comparators to the library (TimSort/introsort hybrids already choose) rather than hand-rolling either — this leaf teaches the machinery so you can reason about it, not so you can replace tested engineering.

```javascript
// GOOD: Lomuto — the invariant in one sentence (verified numbers below)
function quickSort(x, lo = 0, hi = x.length - 1) {
  if (lo >= hi) return x;
  const p = x[hi]; let i = lo;                        // pivot parked at end
  for (let j = lo; j < hi; j++)                       // single sweep: x[lo..i) < p
    if (x[j] < p) { [x[i], x[j]] = [x[j], x[i]]; i++; }
  [x[i], x[hi]] = [x[hi], x[i]];                      // pivot to its final slot
  quickSort(x, lo, i - 1); quickSort(x, i + 1, hi);   // recurse both sides
  return x;
}
// BAD: partition without a statable invariant ("swap things until sorted-ish") —
// unreviewable, untestable at boundaries (duplicates, sorted input, size-2 arrays)
```

### 2) **Pivots decide the rung**

**Definition** — the pivot splits the range; balanced splits recurse logarithmically deep, degenerate splits recurse linearly deep. Naive last-element pivot on sorted (or reverse-sorted) input never splits at all — one side empty, the other `n−1`: verified exactly on sorted 200 → **19900 comparisons = `n(n−1)/2`** and recursion depth **200** (linear stack — the `RangeError` territory from Domain 01 §2.2). Defenses, in escalating strength: random pivot (adversary can't aim), median-of-three (kills sorted/reversed cheaply), shuffle-once upfront (randomizes all downstream choices), introsort guard (switch to heapsort past `2·log n` depth — worst case *impossible by construction*).

- **Why it matters (correctness)**: pivot collapse is a correctness-adjacent failure with security flavor — sorted input is the *common* case (timestamps, IDs, logs arrive ordered), and crafted input is the *adversarial* case (algorithmic-complexity DoS: feed sorted data to a naive quicksort and watch the service burn quadratic). The degenerate isn't exotic — it's Tuesday's telemetry and the attacker's cheapest payload. Pivot discipline converts the most likely inputs from worst cases into best-behaved ones.
- **Modern guidance** — never ship fixed-position pivots (first/last without defense — the collapse is one sorted input away). Minimum viable discipline: median-of-three plus insertion fallback below ~16 (leaf 1.1's hybrid). Serious discipline: random pivot or shuffle-once (expected `n log n` with constants ~1.3× optimal — verified 167,915 vs 132,877 ceiling at `n=10⁴` shuffled, depth 33 ≈ `2.5·log₂n`). Maximum discipline: introsort (libraries chose this — depth-guarded, collapse-proof). State the defense beside the implementation, always.

```javascript
// GOOD: pivot defense stated with the code — collapse engineered away
function quickSortSafe(x, lo = 0, hi = x.length - 1, depth = 0) {
  while (lo < hi) {
    if (depth > 2 * Math.log2(x.length)) return heapSortFallback(x, lo, hi); // introsort guard
    const m = medianOfThree(x, lo, (lo + hi) >> 1, hi);                       // sorted-input killer
    const p = partition(x, lo, hi, m);
    if (p - lo < hi - p) { quickSortSafe(x, lo, p - 1, depth + 1); lo = p + 1; } // recurse small side,
    else { quickSortSafe(x, p + 1, hi, depth + 1); hi = p - 1; }                 // loop large side: O(log n) stack
  }
}
// Verified collapse it prevents: last-pivot on sorted200 = 19900 comps + depth 200 (degenerate).
// BAD: textbook Lomuto-verbatim in production ("it's the standard implementation") —
// standard for teaching; the standard library vendors all added pivot defenses — follow them
```

### 3) **Average-case royalty, worst-case liability**

**Definition** — with pivot discipline, quicksort averages `~1.39·n·log₂n` comparisons (random permutations — near the information-theoretic floor) with `O(log n)` stack (loop-over-large-side shape above bounds it strictly) and in-place partitioning (`O(1)` aux beside the stack). Without discipline, worst case is `O(n²)` time *and* `O(n)` stack — verified simultaneously (19900 comps, depth 200). Royalty and liability are the same algorithm with different pivots — which is why the pivot section, not the partition section, decides production fitness.

- **Why it hurts when missing (correctness, maintainability)**: teams adopt "quicksort is fastest" as unconditional truth and inherit conditional safety — fast on random data, quadratic on ordered data, crashing stack on large ordered data (depth 200 at `n=200` extrapolates past V8's ~13,920 limit (Domain 01 §2.2) around `n≈14⁴` sorted elements — a Tuesday-sized log file). The failure arrives as latency (quadratic burn) then as outage (stack overflow), on the most innocent-looking input imaginable: already-sorted data. Royalty quoted without liability is how outages get introduced by engineers who read half the leaf.
- **Modern guidance** — quote both halves in one breath ("expected `n log n` with random pivots, quadratic without — we use introsort, collapse impossible"). Prefer library sorts (TimSort/introsort — defenses included, measured, maintained). When hand-rolling is genuinely required (constrained runtimes, pedagogical code, interview), ship the guarded version (median-of-three minimum, depth guard for seriousness, insertion threshold per leaf 1.1) and state all three defenses in review. Royalty earned by engineering, not by algorithm name.

```javascript
// GOOD: both halves quoted, defenses shipped (verified numbers as the receipt)
// shuffled n=10000: 167915 comps (~1.26x n*log2n ceiling 132877), max depth 33 (~2.5x log2) — royalty.
// sorted n=200 naive: 19900 comps (= n(n-1)/2 exact), depth 200 — liability, engineered away above.
// BAD: "quicksort: O(n log n)" as the whole story —
// the average without the worst is half a contract; the half that bills arrives sorted
```

### 4) **Common confusion**

- "Quicksort is always fastest" — fastest *in-place average* on random-ish data with good constants. Merge wins on guarantees and stability; insertion wins small; TimSort wins nearly-sorted. "Fastest" needs "...at what, under which constraints?"
- "Random pivot makes worst case impossible" — random pivots make worst case *improbable* (vanishingly, per input), not impossible. Only depth guards (introsort) make it structurally impossible. Probability vs impossibility is the security-relevant distinction.
- "Depth 200 at n=200 means depth scales as n" — only for degenerate pivots (each level removes one element). Balanced recursion removes a constant *fraction* per level — that's what buys logarithmic depth. The pivot decides the fraction.
- "Hoare is just an optimization" — Hoare does fewer swaps *and* handles duplicates better with 3-way extension (equal keys stop skewing partitions). On duplicate-heavy data that's correctness-adjacent, not cosmetic.

### 5) **Performance note**

Partition costs `n` comparisons per level (verified 19900 total across 200 degenerate levels = 19900/200 ≈ 99.5/level — the arithmetic of collapse); balanced levels cost the same `n` but number only `log n` (verified 167915/≈14 levels ≈ 12k/level at `n=10⁴`). Constants favor quicksort over merge (~30–50% fewer comparisons typical, zero buffer traffic, better locality) — the margin that made it royalty. Depth-guard overhead is one comparison per level (negligible); median-of-three costs two extra comparisons per partition (negligible). Defenses are free; collapses are bankrupting — the cheapest insurance in sorting.

### 6) **Mentor note**

Demonstrate the collapse live (sorted-200 → depth 200 + 19900 comps, exact `n(n−1)/2` — "the most innocent input produces the exact worst case" lands harder than any warning), then fix it three ways in ascending strength (median-of-three, shuffle-once, depth guard) and re-measure each. That arc — collapse, defense, verification — teaches pivot discipline permanently. Drill partition invariants by hand-tracing size-5 arrays (Lomuto's sweep, Hoare's convergence) before allowing implementations. Watch for the textbook-verbatim shipper ("standard implementation" — fix with sorted-input testing as a review requirement) and the royalty-quoter ("`n log n`, done" — fix with "and the worst case is...?"). Review check: pivots defended (named defense), depth bounded (guard or proof), insertion threshold present, worst case stated beside the average with the collapse mechanism named.
