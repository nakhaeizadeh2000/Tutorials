## 2.1. Merge sort: the divide-and-conquer flagship

### 1) **Halve, sort, merge — `T(n) = 2T(n/2) + O(n)`**

**Definition** — split the array in halves, sort each half recursively, merge the two sorted halves with one linear pass: the recurrence from Domain 01 §2.1 instantiated — `log₂n` levels × `n` combine work → `O(n log n)` in *all* cases (best = worst = average; no input perturbs the shape). Verified on Node v20.20.2: 1000 elements cost 5044 comparisons reversed and 4932 sorted (both ≈ `n·log₂n/2`, far under the `n·log₂n ≈ 9966` ceiling) — the guarantee is visible: input order barely moves the count.

- **What problem it solves**: quadratics die at scale (leaf 1.1's ladder eviction at ~10⁴) and naive fast sorts carry worst-case cliffs (next leaf's quicksort collapse). Merge sort is the predictable middle: guaranteed linearithmic on *every* input, with constants modest enough to ship. When the requirement reads "must sort 10⁷ records within budget regardless of incoming order," merge sort is the shape that answers without asterisks.
- **Modern guidance** — reach for merge sort (or its descendants — TimSort in `Array.prototype.sort`) when worst-case guarantees matter more than memory (external datasets, SLAs, adversarial inputs). Implement the merge with `<=` (stability — equal left elements first), a single reusable auxiliary buffer (half the allocation of per-level copies), and the insertion fallback below ~32 (leaf 1.1's hybrid). Never re-derive the bound per use — link the recurrence (Domain 01 §2.1), price the merge pass, done.

```javascript
// GOOD: the flagship — guaranteed linearithmic, stable, honest about memory
function mergeSort(a) {
  const aux = new Array(a.length);              // one O(n) buffer, reused (not per level)
  (function sort(lo, hi) {
    if (hi - lo <= 1) return;
    const m = (lo + hi) >> 1;
    sort(lo, m); sort(m, hi);                   // 2T(n/2)
    for (let i = lo; i < hi; i++) aux[i] = a[i];
    let i = lo, j = m, k = lo;
    while (i < m && j < hi) {                   // O(n) merge; <= keeps stability
      if (aux[i] <= aux[j]) a[k++] = aux[i++]; else a[k++] = aux[j++];
    }
    while (i < m) a[k++] = aux[i++]; while (j < hi) a[k++] = aux[j++];
  })(0, a.length);
  return a;
} // O(n log n) all cases (verified 5044/4932 at n=1000), O(n) aux, stable.
// BAD: per-level slice/concat merging ("cleaner") —
// O(n log n) extra allocation traffic for readability nobody benchmarks
```

### 2) **Stable and predictable, never in-place**

**Definition** — merge sort's contract in full: time `O(n log n)` best/worst/average (verified near-identical counts sorted vs reversed), space `O(n)` auxiliary (the merge buffer — plus `O(log n)` call stack), stability guaranteed (the `<=` tie-break preserves equal-key order — verified V8-sort stability relies on the same property downstream). The `O(n)` buffer is structural, not incidental: merging two sorted runs into place without scratch is possible but intricate (in-place merge gymnastics cost more than the buffer on modern hardware).

- **Why it matters (correctness)**: predictability is a feature teams pay memory for — real-time pipelines, SLA-bound services, and adversarial inputs (user-ordered data attacking quicksort's pivots, next leaf) all prefer the algorithm whose worst case equals its average. And stability isn't cosmetic: multi-key sorts (sort by date, then stable-sort by name) compose *only* with stable primitives — an unstable merge silently un-sorts the previous pass. The buffer buys both; budget it explicitly (Domain 01 §2.2: `O(n)` aux stated beside the bound).
- **Modern guidance** — choose merge sort when guarantees beat memory (large in-memory datasets with SLAs, untrusted input orders, multi-key pipelines needing stability). Choose otherwise when memory dominates (embedded, giant datasets exceeding RAM — external merge, next section — or heapsort's `O(1)` aux with `n log n` guarantee, leaf 3.2's teaser). State the trade per use: "linearithmic-guaranteed at `O(n)` scratch" — the sentence that picks merge over quick honestly.

```javascript
// GOOD: stability composes — multi-key sorts need stable primitives
records.sort((a, b) => a.date - b.date);   // pass 1 (stable: TimSort-class, verified stable)
records.sort((a, b) => a.name.localeCompare(b.name)); // pass 2 stable -> name-major, date-minor within names
// With an UNSTABLE primitive the second pass would scramble equal-name groups' dates silently.
// BAD: "merge sort wastes memory, quicksort is strictly better" —
// the O(n) buffer buys worst-case equality + stability; "waste" is the guarantee's price, stated up front
```

### 3) **External sorting's only choice**

**Definition** — when data exceeds RAM, only sequential-access algorithms survive: external merge sort chunks the input into memory-sized runs (sorted internally), then merges runs with bounded buffers — disks and tapes stream, never seek randomly. Quicksort's random-access partitioning dies on rotational media (seek latency dominates); heaps need random access too. Merge's linear passes are the access pattern storage hardware rewards — the algorithm and the medium agree.

- **Why it hurts when missing (correctness, maintainability)**: teams that outgrow RAM discover their in-memory sort can't stream — and "just add memory" stops working at 10× while run files scale linearly with disks. External merge is the standard answer (databases, MapReduce shuffles, log processors all run variants), and its absence from a senior's toolkit shows at exactly the scale where interviews and incidents both live. The pattern generalizes: match access pattern to medium (sequential for disk, random tolerable for RAM) before optimizing comparisons.
- **Modern guidance** — below RAM: library sort (TimSort-class hybrid, already merge-descended). Above RAM: external merge with tuned run sizes (memory-sized chunks, k-way merge with heap-selected minima — Domain 04's heap, previewed) and replacement selection for longer runs. Never quicksort across the memory boundary (random seeks at disk latency — the ladder rung is the least of its problems). State the regime per system: "in-memory to 10⁷ rows, external merge beyond" — the boundary documented before it's crossed.

```bash
# GOOD: regime-aware sorting — the boundary stated before it's crossed
#  < RAM:        Array.prototype.sort (TimSort-class hybrid, stable, measured)
#  > RAM:        external merge — memory-sized runs + k-way bounded merge (sequential I/O only)
# BAD: quicksort "optimized" for a 100GB dataset on spinning disks —
# random-access partitioning at seek latency; the access pattern defeats the algorithm
```

### 4) **Common confusion**

- "Merge sort is always `n log n` so input doesn't matter" — comparisons barely move (verified 5044 vs 4932), but *allocation traffic, branch prediction, and cache behavior* vary with order. Same rung, different constants — measure at shipped sizes (Domain 01 §3.1).
- "The `O(n)` space makes it inferior" — inferior *where memory binds*; superior *where guarantees bind*. Algorithms aren't ranked absolutely — they're matched to constraints (leaf 1.1's decision table, extended).
- "TimSort *is* merge sort" — TimSort descends from merge sort (runs + galloping merge + insertion on small runs) with adaptive engineering atop. Descendant, not identity — the hybrid chapter (leaf 1.1) explains the additions.
- "Stable only matters for objects" — stability matters wherever *previous order carries meaning* (multi-key passes, UI lists preserving user arrangement, deterministic outputs for tests). Primitives are the special case.

### 5) **Performance note**

Merge costs `n·log₂n/2 … n·log₂n` comparisons in practice (verified ~5000 at `n=1000` — half the ceiling, both orders) plus one linear allocation pass per level without buffer reuse (the reusable-buffer optimization halves traffic). Cache behavior is merge's quiet virtue (sequential passes prefetch cleanly) and its quiet cost (two streams + output exceed L1 at large `n` — blocked merging exists for the obsessed). Optimize the buffer first (reuse), the threshold second (insertion below ~32), the merge loop last (sentinels vs bounds-checks — single-digit percentages).
