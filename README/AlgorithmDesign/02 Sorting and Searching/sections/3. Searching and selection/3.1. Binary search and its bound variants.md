## 3.1. Binary search and its bound variants

### 1) **Halve the range on sorted data**

**Definition** — maintain a half-open range `[lo, hi)` containing the answer, probe the midpoint, discard the half the comparison rules out: `T(n) = T(n/2) + O(1)` → `O(log n)` time, `O(1)` space. Verified on 2,000,000 sorted elements: 20 comparisons against a ceiling of ⌈log₂2M⌉ = 21 — thirty probes devour billions, and the count barely moves with input size (double the array, pay one more comparison).

- **What problem it solves**: sorted data is an *indexed* structure only if something halves — linear scan of sorted data pays `O(n)` for order it never uses (the index that isn't consulted). Binary search converts sortedness into logarithmic queries: dictionaries, version lookups, bisect tooling (Git's `bisect run` automates exactly this loop over history — same halving, different array). The precondition is non-negotiable (sorted, random-access) — and checking it is part of using the algorithm, not someone else's problem.
- **Modern guidance** — reach for binary search on static sorted data with many queries (amortize nothing — each query is independent `log n`); prefer hash maps for unsorted or dynamic-heavy workloads (Domain 04 — `O(1)` average beats `log n` where ordering is unneeded). In JS, hand-roll on arrays (no stdlib bisection — the loop is ten lines, the invariant is the hard part, next section) and verify sortedness at API boundaries (assert in debug, document in release).

```javascript
// GOOD: halving with a statable invariant — verified 20 comps on 2M elements
function lowerBound(a, t) {           // invariant: answer in [lo, hi); a[0..lo) < t, a[hi..] >= t
  let lo = 0, hi = a.length;
  while (lo < hi) {
    const m = (lo + hi) >> 1;
    if (a[m] < t) lo = m + 1; else hi = m;
  }
  return lo;                          // first index with a[i] >= t (insertion point if absent)
}
// lowerBound(dup2M, 500000) -> idx 1000000, found, 20 comps (ceiling 21). O(log n) time, O(1) space.
// BAD: linear scan "because the array is small" without measuring the query count —
// 10^6 queries x 10^3 scan = 10^9 wasted on sorted data (halving costs 20 steps each)
```

### 2) **Invariants, not indices**

**Definition** — every correct binary search maintains a loop invariant (a truth preserved each iteration — stated above: answer in `[lo, hi)`) and terminates by shrinking a finite measure (`hi − lo` strictly decreases — the `>> 1` midpoint with `lo = m+1` / `hi = m` guarantees progress, no infinite loop on size-1 ranges). Off-by-one errors are invariant violations wearing index clothing: `<` vs `<=`, `m` vs `m+1`, closed vs half-open ranges — each choice must preserve the invariant *and* shrink the measure, or the loop lies or spins.

- **Why it matters (correctness)**: binary search is the most notorious correct-looking-wrong algorithm in the field (Bentley's history: published 1946, first correct implementations *decades* later; Java's `Arrays.binarySearch` carried an overflow bug ` (lo+hi)/2 ` for nine years). The failure mode is always the same: indices adjusted without invariant reasoning — works on tested sizes, fails on empty arrays, single elements, or present-at-boundary targets. Invariant-first is the only implementation method with a track record.
- **Modern guidance** — write the invariant as a comment before the loop (the contract future readers verify against), use half-open `[lo, hi)` uniformly (empty range `lo == hi` terminates naturally — verified: empty array → `idx 0`, 0 comparisons, no special case), compute midpoints overflow-safely (`(lo+hi) >> 1` or `lo + ((hi-lo) >> 1)` — 32-bit-safe in JS for arrays; the habit ports to languages where it isn't), and test the boundary matrix (empty, single present/absent, first/last, duplicates, all-equal — six cases that catch every classic bug).

```javascript
// GOOD: invariant commented, boundaries tested (verified matrix)
// invariant: a[0..lo) < t <= a[hi..]; measure hi-lo shrinks every iteration.
lowerBound([], 5);            // -> 0 (empty: terminates, insertion point 0, 0 comps — verified)
lowerBound([7], 7);           // -> 0, found (single present)
lowerBound([7], 5);           // -> 0, absent (before all)
lowerBound([7], 9);           // -> 1, absent (after all — insertion point == length, legal)
// BAD: closed-range [lo, hi] with (lo+hi)/2 and <= loop "from memory" —
// the exact recipe behind the historic overflow + infinite-loop bugs (invariant unstated, uncheckable)
```

### 3) **Lower and upper bounds generalize it**

**Definition** — `lowerBound` (first `≥ t`) and `upperBound` (first `> t`) reduce a family of queries to one pattern: membership (`a[lower] == t`), run length (`upper − lower` — verified: run of 7s measures exactly 2), insertion point (either bound on absence — verified `500000.5` → index 1000002, `found: false`), range counting (`upper(hi) − lower(lo)` — elements in `[lo, hi)` without enumerating), and "first true" predicates (any monotonic boolean array — peak finding, capacity search, version bisection all reduce to lower-bound on `true`).

- **Why it hurts when missing (correctness, maintainability)**: teams re-derive per query — a membership loop here, a counting loop there, an insertion scan elsewhere — each with fresh off-by-one risk and linear cost on sorted data. The bound pair collapses the family: learn two functions, answer six question shapes, each logarithmic. And the predicate generalization (`firstTrue(monotonic)`) extends halving beyond arrays entirely — Git bisect, capacity planning, and threshold searches are lower-bounds in disguise.
- **Modern guidance** — implement both bounds once (tested matrix from previous section), then compose instead of re-deriving (membership = `lower` + equality check; counting = bound difference; insertion = bound on absence). Reach for the predicate form whenever the data is ordered but not an array (version ranges, timestamps, "first bad commit" — the pattern ports; the indices don't). Document which bound each call site needs (first-`≥` vs first-`>` — the one-character difference that decides duplicates handling).

```javascript
// GOOD: one pattern, six questions — verified compositions
const upperBound = (a, t) => { let lo = 0, hi = a.length;
  while (lo < hi) { const m = (lo + hi) >> 1; if (a[m] <= t) lo = m + 1; else hi = m; } return lo; };
const runLength = (a, t) => upperBound(a, t) - lowerBound(a, t);  // verified: run of 7 -> exactly 2
const countIn = (a, lo, hi) => lowerBound(a, hi) - lowerBound(a, lo); // range count, no enumeration
// BAD: six hand-rolled loops (member/scan, count/scan, insert/scan...) —
// six off-by-one surfaces, six linear costs, one pattern unrecognized
```

### 4) **Common confusion**

- "Binary search needs distinct elements" — duplicates are handled by bounds (first-`≥` vs first-`>`), not by uniqueness assumptions. Distinctness simplifies nothing the bounds don't already cover.
- "`O(log n)` means ~10 steps always" — steps scale with `log n`: 20 at 2M (verified), 30 at a billion, 40 at a trillion. "Thirty steps devour billions" is the slogan; the ceiling formula is the tool.
- "Interpolation search is strictly better" — better *average* on uniform data (`O(log log n)`), worse worst case (`O(n)` on skewed distributions — leaf 1.2's distribution honesty applies). Prefer binary's unconditional guarantee unless uniformity is proven and measured.
- "The midpoint can't overflow in JS" — true for arrays (lengths < 2³², and `>> 1` coerces safely here), false as a habit — write `lo + ((hi − lo) >> 1)` anyway; the portable form costs nothing and survives translation to languages where it matters.

### 5) **Performance note**

Binary search costs `⌈log₂(n+1)⌉` comparisons worst-case (verified 20/21 — near-ceiling, as theory predicts for present targets) with `O(1)` space and branchy-but-predictable access (midpoints jump — cache-unfriendly vs linear scan's prefetch, which is why tiny arrays scan faster: crossover typically <100 elements, measured). Bound compositions cost two searches (constant factor 2 — halve it with single-pass variants only when profiles demand). Optimize the *call count* first (cache results, batch queries) — per-search constants are already near floor.

### 6) **Mentor note**

Teach invariants before indices: state the contract, derive the updates from it ("which half keeps the answer?"), prove termination by the shrinking measure — then write code that falls out of the proof. Test with the six-case matrix (empty/single/boundary/duplicates/all-equal) until green is boring. Then generalize live: membership → run length → insertion → predicate form, each composed from the same two bounds — the "one pattern, six questions" reveal converts technicians into designers. Watch for the memorizer (closed-range recipe from memory — fix with "state the invariant first") and the linear-on-sorted pragmatist ("small array" without query counts — fix with queries × scan arithmetic). Review check: invariant commented, half-open ranges, overflow-safe midpoints, boundary matrix green, bound choice (lower vs upper) justified per call site.
