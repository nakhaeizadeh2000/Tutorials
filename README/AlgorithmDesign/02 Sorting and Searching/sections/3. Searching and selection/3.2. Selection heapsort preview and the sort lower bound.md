## 3.2. Selection, heapsort preview, and the sort lower bound

### 1) **Quickselect finds k-th in `O(n)` average**

**Definition** — partition (leaf 2.2's machinery), then recurse into *only the side containing k* — discarding the other side sight-unseen. Expected `O(n)` (geometric series `n + n/2 + n/4 + … < 2n` — each level halves the live range on average), worst `O(n²)` with naive pivots (same collapse, same defenses: median-of-three minimum). Verified: median of 10,001 shuffled elements found exactly (5000) in 40,188 comparisons vs ~132,877 for full quicksort — selecting costs a third of sorting, because most partitions get thrown away.

- **What problem it solves**: sorting to select is overpaying by a logarithmic factor — medians, percentiles, top-k, and order statistics need *one* position, not total order. Full sort computes `n log n` information to answer an `n`-sized question; quickselect computes the answer directly by pruning. Percentile dashboards, streaming quantiles' batch cousins, and "k smallest" queries all reduce here — anywhere the deliverable is a rank, not an ordering.
- **Modern guidance** — reach for quickselect (or introselect — the depth-guarded twin, same introsort logic as sorting) whenever the output is positional: medians, quartiles, top-k (keep k on the right side only). Reuse partition code with the sort (one tested partition serves both — DRY across the domain). Mind the worst case identically (pivot defenses travel with the partition — median-of-three in the verified probe). For *many* order statistics on one dataset, sort once (selection queries amortize only past `log n` of them).

```javascript
// GOOD: prune, don't sort — verified 3.3x cheaper than full quicksort
function quickSelect(x, k, lo = 0, hi = x.length - 1) {
  while (lo < hi) {
    const m = (lo + hi) >> 1; [x[m], x[hi]] = [x[hi], x[m]];  // median-ish defense
    const p = partition(x, lo, hi);                            // leaf 2.2 machinery, reused
    if (p === k) return x[k];
    if (p < k) lo = p + 1; else hi = p - 1;                    // keep ONE side — the savings
  }
  return x[k];
} // median(10001 shuffled) = 5000 exact, 40188 comps vs ~132877 sorting. O(n) average, O(n) worst-naive.
// BAD: [...xs].sort((a,b) => a-b)[k] for one percentile —
// n log n information computed for an n-sized question (fine once, wasteful per query)
```

### 2) **Comparison sorts can't beat `n log n`**

**Definition** — the decision-tree lower bound: any sort using only pairwise comparisons must distinguish `n!` possible input orders; a binary decision tree with `n!` leaves needs height ≥ `log₂(n!) = Ω(n log n)` (Stirling: `n·log₂n − n/ln2 + …` — ~118,000 for `n = 10,001`). So merge sort, heapsort, and well-pivoted quicksort are *asymptotically optimal* among comparison sorts — no future cleverness beats them by more than constants. Verified-adjacent: the measured sorts in this domain (167,915 shuffled quicksort vs ~132,877 ceiling) sit within small constants of the floor — the bound is tight, not theoretical decoration.

- **Why it matters (correctness)**: lower bounds end arguments — "can't we sort faster?" gets a proof instead of an opinion, and engineering effort redirects from impossible speedups to possible ones (better constants, non-comparison methods, exploiting structure). It also certifies optimality: shipping merge sort isn't settling, it's arriving — the algorithm meets the floor. Every "faster sort" claim gets exactly one question first: "comparison-based?" — yes closes the discussion at `n log n`; no opens counting/radix territory (below).
- **Modern guidance** — cite the bound to *stop* work (no comparison-sort research spikes — the floor is proven) and to *start* the right work (structure exploitation: counting sort `O(n+k)` for bounded integers, radix `O(d·n)` for fixed digits, TimSort adaptivity for presorted runs — each beats `n log n` by declining the comparison game, not by winning it). State the escape hatch with every citation: "Ω(`n log n`) *for comparison sorts* — non-comparison methods exempt." The bound is a wall with labeled doors.

```javascript
// GOOD: the floor proven, the doors labeled
// Any comparison sort on n=10001 needs >= ~118000 comparisons (log2(10001!) via Stirling).
// Our quicksort used 167915 (~1.4x floor — near-optimal, constants only).
// Escape hatches (NOT comparison sorts, bound inapplicable):
//   countingSort(xs, k): O(n + k) — bounded integer keys (frequency table, stable)
//   radixSort(xs):       O(d * n) — fixed-digit keys, d passes of counting sort
// BAD: "our new comparison sort beats n log n on benchmarks" —
// beats it on constants (possible, admirable) or the benchmark is broken (likely) — never asymptotically
```

### 3) **Heapsort teaser, heaps in Domain 04**

**Definition** — heapsort in one paragraph (full treatment in Domain 04, where heaps live): build a max-heap in `O(n)` (bottom-up heapify — linear, not `n log n`, the subtle analysis), then repeatedly extract-max to the array's end — `n` extractions × `O(log n)` sift-down = `O(n log n)` guaranteed, `O(1)` auxiliary, *unstable* (distant swaps scramble equal keys). The promise recorded: guaranteed linearithmic *and* in-place — the only comparison sort offering both (merge needs scratch, quick risks quadratic).

- **Why it preview here (correctness of scope)**: the sorting story needs its third corner — merge (guaranteed, scratch), quick (fast average, collapse risk), heap (guaranteed, in-place, unstable, worse constants). Naming heapsort's contract now lets every "which sort?" discussion in this domain resolve completely; deferring the *structure* keeps heaps single-sourced (PROMPT §5: full treatment once, in Domain 04). The teaser is a promise with a delivery address, not a cliffhanger.
- **Modern guidance** — reach for heapsort (or introsort's heap fallback — leaf 2.2's depth guard *is* heapsort on standby) where guarantees meet memory constraints (embedded, kernels, real-time-adjacent batch). Everywhere else prefer TimSort-class library sorts (better constants, stability, adaptivity — heapsort's cache behavior loses the constants race it wins on paper). When Domain 04 lands, convert this teaser's forwards into the heap leaves — the curriculum's most load-bearing cross-link after recurrence.

### 4) **Common confusion**

- "Lower bound means sorting is solved" — the bound closes *comparison* sorting asymptotically; constants (TimSort vs heapsort differ 2–3×), adaptivity (presorted runs), and non-comparison methods remain open engineering. Solved in theory, competitive in practice.
- "Quickselect is just quicksort that stops early" — structurally yes (same partition), analytically no (`n + n/2 + …` geometric vs `n log n` level-full). The pruning changes the rung, not just the constant.
- "Heapsort's guarantee makes it the best default" — guarantees cost constants (heap's cache-hostile jumps lose to merge's streams and quick's tight loops at equal `n`). Best default remains the adaptive hybrid library sort; heapsort is the specialist.
- "Counting sort breaks the lower bound" — counting sort declines the comparison game (indexes by value, never compares pairs). Bounds bind their model; change the model, change the bound. No contradiction, just scope.

### 5) **Performance note**

Selection costs `~2n` average (verified 40k at `n=10⁴` — geometric pruning visible) vs sorting's `~1.4·n·log n` floorMultiple (verified 168k) — the 3–4× gap is structural, not constant. Lower-bound tightness (~1.4× floor for good quicksort) means comparison-sort optimization has bounded upside — past ~1.2× floor, effort belongs in structure exploitation or constants, not "better comparing." Heapsort constants run ~2× merge's in practice (cache effects) — paper parity, silicon gap.
