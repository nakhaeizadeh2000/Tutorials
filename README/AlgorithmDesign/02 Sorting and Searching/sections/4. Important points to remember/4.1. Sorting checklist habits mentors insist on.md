## 4.1. Sorting checklist (habits mentors insist on)

### 1) **Stability is a requirement, not a feature**

**Definition** — equal keys keep their relative order through the sort — guaranteed by stable algorithms (merge, insertion, TimSort-class library sorts — verified V8 stability), destroyed by unstable ones (selection verified scrambling pairs; quicksort/heapsort without care). Stability composes: multi-key pipelines (sort by date, then by name) work *only* with stable passes — each pass preserves the previous ordering within equal groups.

- **What problem it solves**: unstable sorts corrupt composed orderings silently — no error, no warning, just downstream joins, renders, and dedups operating on shuffled equals. The bug surfaces far from its cause (the report mis-groups; the UI reorders on refresh; the test flakes on ties), and the sort is the last suspect because "sorting works." Stability stated up front converts the mystery into a line item: required → stable algorithm, documented.
- **Modern guidance** — default to stable (library sorts are stable — verified — so the default is already correct; custom sorts must earn instability with measured justification). State stability in every sort choice ("stable merge for the multi-key pipeline" vs "unstable selection acceptable: keys unique by construction"). Test with tagged duplicates (the `0a,0b` probe from leaf 1.1 — five lines that audit any implementation's stability claim).

```javascript
// GOOD: stability required, verified, composed
records.sort((a, b) => a.date - b.date);
records.sort((a, b) => a.name.localeCompare(b.name)); // stable -> name-major, date-minor (verified pattern)
// audit any custom sort: tag equals (0a,0b,...), sort, confirm order — leaf 1.1's probe, reused.
// BAD: "stability doesn't matter here" without proving keys unique —
// unproven uniqueness + unstable sort = silent reorder incidents downstream
```

### 2) **Know your input before your algorithm**

**Definition** — three answers pick the sort before any code: *sortedness* (random? nearly-sorted? reversed? — insertion adores presorted, quicksort fears it unguarded), *size* (below ~32 → insertion; to 10⁷ → linearithmic library; beyond RAM → external merge), and *memory budget* (`O(1)` aux required → heap/introselect territory; scratch affordable → merge's guarantee). Unknown inputs get the robust default (library sort — adaptive, guarded, stable); known inputs get the tuned choice.

- **Why it matters (correctness)**: algorithm-first selection inverts the decision (quicksort-everywhere meets sorted telemetry; merge-everywhere on embedded targets) — the mismatch bills at production scale, where "works on tests" meets Tuesday's import. Input-first selection is three questions in review ("sortedness? size? memory?") that take a minute and prevent the quarter's performance incident. Data describes; algorithms obey.
- **Modern guidance** — ask the three questions for every sort call that matters (hot paths, data planes, user-scale inputs); accept the library default everywhere else (TimSort-class adaptivity covers unknown inputs better than any hand-pick). Document the answers beside non-default choices ("insertion: inputs bounded at 40, measured faster than library below 64" — the justification travels with the code). Re-ask at 10× growth (answers expire with scale — the checklist item that prevents yesterday's tuning from becoming today's bottleneck).

```javascript
// GOOD: input answers select the algorithm (three questions, one minute)
// telemetry presorted, n ~ 10^5, RAM ample -> insertion-friendly? No: runs long -> TimSort (adaptive) wins.
// embedded, n ~ 10^4, O(1) aux hard limit -> heapsort (guaranteed, in-place) over merge (scratch forbidden).
// BAD: one sort for all inputs ("we standardized on quicksort") —
// standards that ignore sortedness/size/memory standardize incidents, not engineering
```

### 3) **Standard library first, custom second**

**Definition** — `Array.prototype.sort` (TimSort-class: adaptive, stable verified, hybrid with insertion on small runs, heavily measured) beats hand-rolled sorts on every axis that matters (correctness, constants, edge cases) for every general-purpose use. Custom sorts earn their place only with measured superiority on a specific workload (bounded keys → counting; fixed digits → radix; constrained memory → heap) — proven by doubling experiments (Domain 01 §3.1), not by theory admiration.

- **Why it hurts when missing (correctness, maintainability)**: hand-rolled sorts import the entire bug surface this domain documents (pivot collapse, instability, off-by-one bounds, missing hybrid thresholds) in exchange for worse constants — library engineers already paid those costs across millions of users. Every custom sort is a maintenance liability (who re-verifies the pivot defense in three years?) plus a correctness risk (which boundary case was never tested?). The burden of proof runs one direction: library by default, custom by measurement.
- **Modern guidance** — supply comparators, not sorts (the comparator is your logic — total order, transitivity, NaN/undefined handling; the sort is the engine's). When custom wins measured (counting sort on bounded IDs at 10× the library — plausible and common), isolate it (named function, documented workload bounds, benchmark beside the code, re-verified per engine upgrade). Delete custom sorts whose workload changed (the bounded IDs grew unbounded — the exemption expired with the input).

```javascript
// GOOD: logic supplied, machinery borrowed
events.sort((a, b) => a.ts - b.ts || a.seq - b.seq);  // comparator is yours (tie-break explicit, stability composes)
// custom only by measurement: countingSort(ids, MAX_ID) with benchmark proving 10x on shipped distribution.
// BAD: hand-rolled quicksort "for performance" without a single benchmark —
// imports pivot collapse + instability + threshold absence; outperforms nothing measured
```

### 4) **Common confusion**

- "Checklists slow down shipping" — checklists slow down *shipping bugs*: three questions (stability? input? library?) take a minute and prevent the quarter's sort incident. Speed without placement is how quadratics reach production.
- "Library sorts are always optimal" — optimal *generally*; beaten *specifically* (counting/radix on structured keys, insertion below threshold). Library-first means "beat with measurement," not "never beat."
- "Stability costs performance" — stability costs nothing in TimSort-class sorts (it's structural, not added); unstable sorts aren't faster *because* they're unstable (their speed comes from elsewhere — partitioning, constants). Don't trade away composition for a discount that isn't offered.

### 5) **Performance note**

The checklist costs a minute per sort call (three questions + library-default) against incident costs in hours (quadratic-on-import, unstable-reorder mysteries, pivot-collapse outages). The highest-leverage question is input sortedness (selects adaptivity needs); the second is the library default (eliminates entire bug classes free). Minutes preventing rewrites — analysis discipline with the track's best attention-to-avoidance ratio.
