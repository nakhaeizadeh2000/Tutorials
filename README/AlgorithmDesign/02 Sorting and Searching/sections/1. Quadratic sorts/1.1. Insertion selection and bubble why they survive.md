## 1.1. Insertion, selection, and bubble — why they survive

### 1) **Small-`n` champions with different virtues**

**Definition** — three `O(n²)`-worst sorts, each with a virtue that keeps it employed: *insertion* (build the sorted prefix left-to-right, shifting larger elements right — adaptive, stable, online: handles streaming input one element at a time); *selection* (repeatedly take the minimum of the unsorted suffix — minimal writes: ≤ `n−1` swaps, verified 8 on `n=16`); *bubble* (repeatedly swap adjacent inversions — the pedagogical baseline that teaches swapping and early-exit, shipped nowhere serious).

- **What problem it solves**: every sorting pipeline meets small inputs — base cases of recursive sorts, short UI lists, nearly-sorted streams — where linearithmic machinery costs more overhead than the quadratic work itself. The trio are the small-`n` toolkit: insertion for adaptive/streaming cases, selection where writes cost (EEPROM, flash wear), bubble for teaching (and nothing else — knowing *why* it's never shipped is the lesson).
- **Modern guidance** — default to insertion among the three (adaptive + stable + online covers the most real small cases); reach for selection only when swap cost dominates comparison cost (rare — measured, not assumed); relegate bubble to whiteboard history (if bubble appears in production code, replace with insertion and measure). All three lose past ~10⁴ elements — the ladder (Domain 01 §1.1) evicts them on schedule.

```javascript
// GOOD: insertion — adaptive, stable, online (verified stable: a/b order preserved)
function insertionSort(xs) {
  const x = [...xs];
  for (let i = 1; i < x.length; i++) {
    const k = x[i]; let j = i - 1;
    while (j >= 0 && x[j] > k) { x[j + 1] = x[j]; j--; }  // shifts, not swaps
    x[j + 1] = k;
  }
  return x;
} // O(n) best (sorted: 0 shifts verified) -> O(n^2) worst (reversed: 4950 at n=100 verified), O(1) aux, stable.
// BAD: bubble in production ("it's simple") —
// same O(n^2) worst with worse constants, no adaptivity worth naming, swaps instead of shifts
```

### 2) **Best cases differ, worst cases agree**

**Definition** — the trio's contract table: insertion best `O(n)` (sorted input: 0 shifts — verified), selection best `O(n²)` (always scans the full suffix — no early exit exists; verified 120 comparisons = `n(n−1)/2` exactly at `n=16`), bubble best `O(n)` *with* the swapped-flag optimization (`O(n²)` without it — the unwary implement the pessimized version). Worst cases unify at `O(n²)`; verified: reversed-100 insertion shifts 4950. Space all `O(1)` auxiliary (in-place); stability splits: insertion ✓, bubble ✓, selection ✗.

- **Why it matters (correctness)**: best-case blindness picks selection for nearly-sorted streams (pays full quadratic where insertion pays linear — a 10⁴× throughput gap on sorted telemetry), and stability blindness picks selection where equal-key order matters (verified scramble: pairs `0a,0b` emerge as `…,2,3,0,1` — downstream joins and renders silently reorder). The table isn't trivia — it's the selection criteria: adaptive+stable → insertion; write-constrained → selection; never → bubble.
- **Modern guidance** — memorize the table as *decisions*, not facts: "nearly sorted?" → insertion (linear on presorted runs); "equal keys with meaning?" → never selection (verified instability corrupts); "writes expensive?" → selection (≤ `n−1` swaps, verified); "teaching loops?" → bubble, then delete it. State all three axes (time-best/worst, space, stability) when choosing — one axis is how bugs ship.

```javascript
// GOOD: the contract table, verified — choose by row, not by familiarity
//            best    worst   aux    stable | verified notes
// insertion  O(n)    O(n^2)  O(1)   yes    | sorted100: 0 shifts; reversed100: 4950
// selection  O(n^2)  O(n^2)  O(1)   NO     | n=16: 120 comps exact, 8 swaps; pairs scrambled
// bubble     O(n)*   O(n^2)  O(1)   yes    | *only with swapped-flag; without it O(n^2) best too
// BAD: selection on nearly-sorted data ("fewer swaps") —
// swaps saved: ~0; comparisons wasted: full n^2/2 (adaptivity beats write-count where writes are cheap)
```

### 3) **Hybrids keep them employed**

**Definition** — production sorts don't choose between quadratic and linearithmic — they *hybridize*: recurse linearly (merge/quick) down to a threshold (~16–32 elements), then finish with insertion (adaptive, cache-friendly, branch-predictable on tiny runs). V8's TimSort descends from merge sort with insertion on small runs; introsort (quicksort + heapsort guard) inserts below 16. The crossover is measured per engine (Domain 01 §3.1), not derived — theory ranks, measurement sets the threshold.

- **Why it hurts when missing (correctness, maintainability)**: hand-rolled "pure" sorts either recurse to singletons (function-call overhead dominating tiny partitions — slower *and* deeper stacks) or quadratic the whole input (ladder eviction at 10⁴). Hybrids dominate both in practice by matching algorithm to scale *within one sort*: linearithmic where it matters (large partitions), quadratic where it wins (small runs). Reimplementing either half naively (pure merge to singletons, pure insertion past thousands) forfeits the engineering the standard library already did.
- **Modern guidance** — never hand-roll what `Array.prototype.sort` does (verified stable, TimSort-class, hybrid internally — Domain 01 §4.1's library-first rule). When custom ordering is needed, supply the comparator, not the sort (the comparator is your logic; the hybrid is the engine's). When teaching or interviewing, implement the hybrid explicitly (threshold constant named, measured justification cited) — "pure" implementations signal theory without engineering.

```javascript
// GOOD: hybrid structure — linearithmic above, insertion below (the production shape)
function hybridSort(xs, lo = 0, hi = xs.length) {
  if (hi - lo <= 16) { insertionSortRange(xs, lo, hi); return xs; } // measured threshold, not magic
  // ... partition/recurse (leaf 2.2) ...
} // comparator supplied by caller; hybrid structure by measurement (Domain 01 §3.1 crossover).
// BAD: "pure merge sort to singletons" in production —
// call overhead per element where insertion would finish in shifts; theory without the crossover
```

### 4) **Common confusion**

- "Quadratic sorts are obsolete" — obsolete *at scale*; dominant *below threshold* (every production sort embeds one). Obsolete describes the rung, not the algorithm.
- "Selection's fewer swaps make it fastest" — swaps matter only where writes dominate (exotic media); comparisons dominate everywhere else, and selection never skips any. Count what costs, not what's countable.
- "Bubble with early-exit is competitive" — early-exit bubble matches insertion's best case with worse constants and no stability-of-implementation story. Competitive with what, exactly?
- "Stability doesn't matter for numbers" — stability matters for *records sorted by one key among many* (sort by date, then by name — unstable second sort scrambles the first). Numbers are the special case, not the rule.

### 5) **Performance note**

Quadratic sorts cost `n²/2` operations at scale (verified 4950/100 for reversed insertion) vs insertion's `n` on sorted runs — the adaptivity gap is the whole ballgame for streams. Below threshold (~16–32), constants rule: insertion's tight shift loop beats merge's allocation and quick's call overhead (measured crossover, engine-specific). Hybrid threshold tuning buys single-digit percentages; choosing the right family (quadratic vs linearithmic) buys orders of magnitude. Optimize the family first (ladder), the threshold second (measurement).

### 6) **Mentor note**

Have juniors implement all three, then run the verified probes themselves (0 vs 4950 shifts; 120 comparisons exact; stability scramble visible in output) — numbers they produce beat numbers they read. Then ask the selection questions in order: "nearly sorted?" → "equal keys meaningful?" → "writes expensive?" — until the table becomes decisions. Watch for the familiarity-picker ("I always use bubble" — fix with the verified table side-by-side) and the purity-rewriter (hand-rolled sorts in production — fix with library-first plus comparator-injection). Review check: no quadratic past threshold without measured justification, stability stated wherever equal keys exist, hybrids named with thresholds.
