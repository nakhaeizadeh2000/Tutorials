# 1.2. Nested routers and composition

## 1. Routers mount subtrees (resources nesting — paths composing, never flattening)

**Definition** — nested routers: routers mounting inside routers (subtrees composing — resources nesting (paths joining — handlers focusing (modules owning — boundaries holding); mounts chaining (app → api → v1 → users (prefixes accumulating — tables composing (declaration centralizing — implementation distributing (navigation preserving — growth accommodating); versions scoping (v1/v2 coexisting — routers versioning (clients migrating — contracts evolving (compatibility holding — breakage declining). Subtrees mounting (resources nesting — paths composing (flattening declining — hierarchy showing).

**What problem it solves** — the flat-table trio: *routes sprawling* (tables flattening — prefixes repeating (strings duplicating — renames missing (drift scheduling — consistency hoping (hierarchy hiding — navigation confusing); *versions forking* (v1/v2 duplicating — handlers copying (contracts diverging — clients splitting (maintenance doubling — breakage risking (evolution hoping — compatibility assuming); *middleware scoping missing* (guards globaling — auth checking publicly (waste spending — precision missing (protection blunting — performance taxing (scopes ignoring — boundaries blurring). Nested routers converting flats to trees (subtrees mounting — versions scoping (middleware bounding — paths composing); reviewers opening trees, not grepping (nesting composing → verifiable; flattening → returned).

**Modern guidance** — the nesting lines per API (review-enforced — examples complete, `node --check` validated): *resources nesting* (subtrees mounting — paths composing (handlers focusing — modules owning (boundaries holding — navigation preserving (flattening declining — hierarchy showing); *versions scoping* (v1/v2 routers — clients migrating (contracts evolving — compatibility holding (breakage declining — evolution owning (coexisting planning — deprecation dating); *middleware bounding* (guards scoping — subtrees protecting (waste declining — precision rising (protection focusing — performance keeping (scopes owning — boundaries holding).

```javascript
// GOOD: subtrees mounting — resources nesting, versions scoping, middleware bounding (complete, runnable).
const express = require('express');
const app = express();
app.use(express.json());
const v1 = express.Router();
const users = express.Router();
users.get('/', (req, res) => res.json([])); // resources nesting — handlers focusing, modules owning
users.get('/:id', (req, res) => res.json({ id: req.params.id }));
v1.use('/users', users); // subtrees mounting — paths composing, flattening declining
app.use('/api/v1', v1); // versions scoping — clients migrating, compatibility holding
app.listen(3000);
```

```javascript
// BAD: tables flattening — routes sprawling, versions forking, scopes missing (real failure shape).
// app.get('/api/v1/users', ...); app.get('/api/v1/users/:id', ...); // prefixes repeating — renames missing (drift scheduling)
// app.get('/api/v2/users', copyOfV1); // versions forking — handlers copying (contracts diverging — maintenance doubling).
// app.use(auth); // guards globaling — public checking (waste spending — precision missing). Nest deliberately.)
```

**Common confusion** — *"nesting deepens URLs needlessly (shallow routing cleaner)."* Nesting reflecting resources (trees modeling — hierarchies showing (URLs reading — clients navigating (structure communicating — understanding aiding (nesting meaning — shallowness confusing); shallows hiding relations (flats listing — parents missing (hierarchy flattening — navigation guessing (structure obscuring — understanding blocking); versions requiring namespaces (v1 scoping — clients migrating (contracts evolving — compatibility holding (namespaces needing — nesting justifying). "Needlessly" describing arbitrary depth (nesting showing off — structure performing); resources describing trees (hierarchies showing — clients navigating). Nest resources (trees modeling — structure communicating); version explicitly (namespaces scoping — compatibility holding).

**Performance note** — nesting economics: mounts costing layers per level (prefixes matching — routers reaching (overhead stacking — organization preserving (navigation earning — velocity sustaining); versions costing router sets (clients migrating — contracts evolving (compatibility holding — breakage declining (evolution owning — deprecation dating); scoping saving guard runs (subtrees protecting — waste declining (precision rising — performance keeping); flat equivalents costing drift + copies (renames missing — handlers copying). Nest cheaply (layers — organization); scope guards (subtrees — precision).

**Mentor note** — teach "URLs are trees, routers are branches" (juniors nesting per resource design composable APIs on first hearing; flat tables interrogated ("hierarchy?" — nesting demanding per API). Mount one tree once (api → v1 → users composing — nesting tangible (hierarchy visible — flattening ending permanently). Nest resources; scope versions — composition discipline in two habits, reviewed per API.

## 2. mergeParams shares parents (children inheriting — scopes composing, duplication declining)

**Definition** — mergeParams: child routers inheriting parent params (`Router({ mergeParams: true })` — parents sharing (children reading (`:orgId` flowing — scopes composing (params cascading — handlers accessing (duplication declining — fetching centralizing); nesting deepening (orgs → teams → members (levels stacking — params accumulating (contexts growing — handlers simplifying (scopes widening — logic focusing); defaults isolating (merging off — children blind (parents hiding — params scoping (independence defaulting — sharing opting (coupling declining — clarity preserving). **What problem it solves** — the reparam trio: *params redeclaring* (children restating (`:orgId` repeating — routes duplicating (strings copying — drift scheduling (updates missing — consistency hoping); *fetching reduplicating* (orgs loading per level (queries multiplying — databases hitting (performance hoping — access tangling (loaders scattering — consistency varying); *coupling hiding* (children assuming (parents implying — contracts unstating (scopes surprising — behavior confusing (dependencies hiding — testing mocking blindly). Merged params converting restating to inheriting (parents sharing — children reading (scopes composing — duplication declining); reviewers checking router options, not routes (sharing opting → verifiable; redeclaring → returned).

**Modern guidance** — the merge lines per nesting (review-enforced): *parents sharing* (mergeParams opting — children reading (scopes composing — duplication declining (fetching centralizing — consistency holding (params cascading — handlers accessing); *levels stacking* (orgs → teams (params accumulating — contexts growing (handlers simplifying — scopes widening (nesting deepening — logic focusing); *defaults respecting* (merging off defaulting — sharing opting (coupling declining — clarity preserving (independence keeping — surprises declining (contracts stating — dependencies showing).

```javascript
// GOOD: parents sharing — children inheriting, levels stacking, defaults respecting (complete, runnable).
const express = require('express');
const app = express();
const teams = express.Router({ mergeParams: true }); // parents sharing — children reading, scopes composing
teams.get('/', (req, res) => res.json({ org: req.params.orgId })); // inheriting, not redeclaring
teams.get('/:teamId', (req, res) => res.json({ org: req.params.orgId, team: req.params.teamId })); // levels stacking
app.use('/orgs/:orgId/teams', teams); // nesting deepening — handlers simplifying, duplication declining
app.listen(3000);
```

```javascript
// BAD: params redeclaring — children restating, fetching reduplicating, coupling hiding (real failure shape).
// teams.get('/:orgId/...') redeclared per child (routes duplicating — strings copying — drift scheduling (updates missing).
// Orgs loading per level (queries multiplying — databases hitting — performance hoping (loaders scattering — consistency varying).
// Children assuming parents (contracts unstating — scopes surprising — behavior confusing). Opt into merging.)
```

**Common confusion** — *"mergeParams couples routers (independence preferring)."* Merging declaring dependence (parents naming — children reading (contracts stating — scopes showing (coupling owning — clarity preserving (dependencies visible — testing mocking (params providing — handlers isolating); redeclaring duplicating (strings copying — drift scheduling (updates missing — consistency hoping (coupling hiding — clarity destroying (dependencies concealing — testing duplicating); independence scoping singly (flat routers isolating — params owning (sharing declining — duplication accepting (clarity costing — reuse refusing). "Coupling" describing hidden dependence (contracts unstating — scopes surprising); merging describing declared dependence (contracts stating — scopes showing). Declare dependence (merging — clarity); duplicate never (redeclaring — drift).

**Performance note** — merge economics: sharing costing option flags (parents naming — children reading (contracts stating — scopes showing (clarity preserving — duplication declining); stacking costing param growth (contexts widening — handlers simplifying (nesting deepening — logic focusing (scopes composing — fetching centralizing); respecting costing defaults (independence keeping — surprises declining (contracts stating — dependencies showing); redeclared equivalents costing drift + queries (strings copying — databases hitting). Share explicitly (options — clarity); stack deliberately (levels — focus).

**Mentor note** — teach "children inherit, never redeclare" (juniors merging per nesting design DRY routers on first hearing; restating children interrogated ("mergeParams?" — sharing demanding per nesting). Show one inheritance once (orgId flowing parent→child — sharing tangible (duplication ending visibly — restating never). Opt into merging; stack levels — inheritance discipline in two habits, reviewed per nesting.

## 3. Composition scales teams (modules owning — boundaries holding, velocity sustaining)

**Definition** — team-scale composition: modules mapping to owners (routers bounding (teams owning — files limiting (reviews routing — expertise concentrating (knowledge localizing — velocity sustaining (ownership assigning — buses surviving); boundaries holding (contracts interfacing — routers exposing (consumers depending — internals hiding (coupling managing — changes containing (blast limiting — refactors scoping); velocity sustaining (parallel developing — merges rarely conflicting (independence enabling — throughput composing (teams shipping — organization scaling).
