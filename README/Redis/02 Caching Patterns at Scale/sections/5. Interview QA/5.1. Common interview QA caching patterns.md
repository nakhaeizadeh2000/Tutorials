# 5.1. Common interview QA caching patterns

## 1. Cache strategies under pressure (aside/through/back placed by workload — judgment, not fashion)

**Definition** — the strategy-placement answer interviewers grade: given a workload, name the write pattern ([1.1](<../../sections/1. Write patterns/1.1. Cache-aside write-through write-back.md>)) with its staleness contract and price — cache-aside for read-heavy TTL-tolerant data (stale ≤ TTL — invalidation owned per write path); write-through for freshness-critical reads (zero staleness — availability coupled, cache-down failing writes); write-back for ingest-heavy latency-sensitive writes (speed now — durability window stated, crash-loss bounded). "Under pressure" means follow-ups attack the choice (cache down? thundering reads? crash mid-window? — answers priced, never hoped).

**What problem it solves** — the fashion-answer trio: *patterns recited without contracts* (aside/through/back named (staleness unstatable — follow-ups collapsing (pressure revealing recitation (understanding absent — choices unjustified); *trade-offs unpriced* (through chosen "for consistency" (availability coupling unmentioned — cache-down behavior undesigned (coupling discovered in production); *workloads unmatched* (write-back for read-heavy data (queues idle — windows pointless (complexity unbought benefit — pattern fashionable, fit absent). Placed patterns convert recitation to judgment (workload → pattern → contract → price — each link defensible); interviewers grading chains, not names (placement reasoned → hired; recited → rejected).

**Modern guidance** — the placement lines (interview-enforced): *read-heavy, TTL-tolerant* (cache-aside (stale ≤ TTL — invalidation per write path (DB authoritative — misses bounded by TTL discipline); *freshness-critical* (write-through (zero staleness — cache-down failing writes loudly (coupling priced — availability designed, never assumed); *ingest-heavy, latency-bound* (write-back (async persistence — window measured in seconds (crash-loss bounded numerically — durability priced); *follow-ups answered with prices* (cache down → through fails / aside degrades to DB (behaviors stated); crash → back loses ≤ window (bounds stated); stampede → jitter/coalescing ([1.2](<../../sections/1. Write patterns/1.2. Stampede prevention.md>) — defenses stated). Every placement carrying contract + price (judgment demonstrable — pressure survivable).

```javascript
// GOOD: placement reasoned — workload → pattern → contract → price (interview-grade answer shape).
// "Read-heavy product catalog, minutes-tolerant freshness → cache-aside (stale ≤ 300s TTL — invalidation on
// price/stock write paths (ownership explicit). Cache down → degrades to DB (availability preserved — latency
// spikes, correctness intact). Hot keys jittered ±10% (herds dispersed — [1.2] defense stated)."
// BAD: fashion answer — pattern named, contract absent (real rejection shape).
// "We use write-through for consistency." (Cache down? — undesigned (coupling discovered in production).
// "Write-back for speed." (Window? crash loss? — unstated (durability hoped). Follow-ups collapse recitation.)
// Name patterns with contracts and prices; survive follow-ups.)
```

**Common confusion** — *"write-through is strictly better than cache-aside (always fresh)."* Freshness priced in availability (cache-down failing writes (coupling explicit — outages correlated (cache incidents becoming write incidents — blast radius doubled); latency priced per write (synchronous cache + DB (writes slower — latency budget spent on freshness (read-heavy workloads paying per write for reads' benefit — mispriced); complexity priced in invalidation absence (through still needing TTL/eviction discipline (memory unbounded otherwise — freshness solving staleness, not capacity). "Strictly better" ignores prices (availability + latency + capacity — through costing all three); aside winning read-heavy TTL-tolerant workloads structurally (availability preserved — latency minimal — staleness bounded). Better per workload (judgment); strictly never (fashion).

**Performance note** — placement economics: aside costs TTL-misses (DB load per expiry — bounded by TTL discipline); through costs write latency + availability coupling (freshness priced per write — outages correlated); back costs crash-loss windows + queue operations (speed priced in durability seconds); fashion answers cost offers (recitation rejected — judgment hired). Place per workload (contracts stated — prices explicit); recite never (fashion transparent under pressure).

**Mentor note** — teach "contract + price per placement" (juniors answering workload → pattern → contract → price place strategies on first hearing; pattern-only answers interrogated ("staleness? cache-down?" — contracts demanded per placement). Mock drill: interviewer attacking each choice (down/crash/stampede follow-ups — pressure practiced, not theorized). Place by workload; price every choice; survive follow-ups — strategy judgment in three habits, reviewed per placement.

## 2. Stampedes and races live (thundering herds, check-and-set — diagnosed with fixes, priced)

**Definition** — the failure-diagnosis answer interviewers grade: given symptoms, name the mechanism with fix and price — thundering herd (hot keys expiring synchronously (uniform TTLs — misses simultaneous — DB N× hammered; fix: jitter ±10% + single-flight coalescing ([1.2](<../../sections/1. Write patterns/1.2. Stampede prevention.md>) — dispersion structural, sharing explicit); check-and-set race (read-then-write interleaved (concurrent clients clobbering — oversold/double-spend; fix: Lua indivisibility ([2.1](<../../sections/2. Atomic multi-step/2.1. Lua scripting for atomic multi-step.md>)) — races structurally impossible); WATCH-abort retry storms (optimistic contention hot (retries multiplying — liveness degrading; fix: Lua instead of WATCH on hot keys ([2.2](<../../sections/2. Atomic multi-step/2.2. Transactions MULTI EXEC WATCH.md>) — pessimism priced once). "Live" means diagnosed with fixes (symptoms → mechanism → remedy → price — chains complete).

**What problem it solves** — the symptom-only trio: *herds undescribed* ("slow sometimes" (mechanism unnamed — expiry synchrony unconsidered (uniform TTLs unexamined — dispersion unoffered (diagnosis absent — fixes random); *races unrecognized* (oversells called "DB issues" (interleaving windows unconsidered — check-then-set unexamined (Lua unoffered — correctness hoped); *retries unbounded* (WATCH loops spinning (contention unmeasured — backoff absent (liveness degrading — Lua alternative unconsidered). Diagnosed failures convert incidents to mechanisms (symptoms mapping to causes — fixes structural — prices explicit); interviewers grading diagnosis (mechanism + fix + price → hired; symptoms-only → rejected).

**Modern guidance** — the diagnosis lines (interview-enforced): *herd symptoms* (latency spikes aligned with TTL boundaries (expiry synchrony — uniform TTLs herding misses; fix jitter + coalescing (dispersion structural — sharing explicit; *race symptoms* (oversells/double-counts under concurrency (interleaving windows — check-then-set hoping; fix Lua (indivisibility structural — races impossible; *retry-storm symptoms* (WATCH aborts climbing with contention (optimism mismatched — hot keys contending; fix Lua on hot keys (pessimism priced once — retries eliminated); *prices stated per fix* (jitter free — single-flight a Map — Lua microseconds on loop (costs explicit — fixes adopted, not feared). Symptoms → mechanism → fix → price (chains complete — pressure survivable).

```javascript
// GOOD: diagnosed with fix and price — symptoms mapping to mechanisms (interview-grade answer shape).
// "p99 spikes every 5 minutes (= our TTL) → thundering herd (uniform expiry synchronizing misses — DB N×
// hammered). Fix: jitter ±10% (dispersion structural — free) + single-flight Map (sharing explicit —
// microseconds). Spikes gone post-deploy (mechanism confirmed — diagnosis closed, not hoped)."
// BAD: symptoms only — mechanism absent, fixes random (real rejection shape).
// "Latency spikes sometimes — we scaled the DB." (Expiry synchrony unconsidered — spikes persisting at larger
// cost (provisioning absorbing, not preventing — diagnosis absent). Oversells called "DB issues" (interleaving
// unconsidered — Lua unoffered). Diagnose mechanisms; price fixes; confirm post-deploy.)
```

**Common confusion** — *"caching bugs are timing flukes (unreproducible, ignore)."* Flakes reproduce under concurrency (load tests colliding (windows × rate = certainty — single-threaded tests fiction (production concurrent — collisions scheduled); TTL boundaries reproduce on clocks (expiry synchronized — spikes aligned with TTL (reproducible by watching clocks — herds scheduled); races reproduce with parallel clients (interleaving forced (parallel decrementers overselling deterministically — Lua fixing deterministically). "Flukes" describes unloaded observation (single-client fiction — timing uncontended); production contends (mechanisms deterministic under load — reproducibility requiring concurrency, not luck). Reproduce with concurrency (load + parallel clients + clock-watching); dismiss never.

**Performance note** — diagnosis economics: herd fixes cost jitter arithmetic + a Map (free-ish — dispersion structural); race fixes cost Lua microseconds on the loop (indivisibility priced per execution — bounded by script review); retry-storm fixes cost one Lua conversion (pessimism priced once — retries eliminated); undiagnosed equivalents cost N× DB loads + oversells + degraded liveness (prices unbounded — incidents discovering mechanisms). Diagnose cheaply (clocks + concurrency + counters); fix structurally (dispersion/indivisibility/pessimism); confirm post-deploy (mechanisms closed, never hoped).

**Mentor note** — teach "symptoms → mechanism → fix → price" (juniors chaining per failure diagnose stampedes/races on first hearing; symptom-only answers interrogated ("mechanism? fix? price?" — chains demanded per failure). Reproduction drill: synchronized TTLs stampeding in staging, parallel clients overselling without Lua (mechanisms tangible — trust earned by watching failures reproduce, not by documentation claims). Diagnose mechanisms; fix structurally; confirm post-deploy — failure judgment in three habits, reviewed per incident.

## 3. Eviction and Lua live (policies chosen, scripts bounded — operations answers, not trivia)

**Definition** — the operations answer interviewers grade: given capacity/consistency scenarios, name the policy/script discipline with prices — eviction (maxmemory bounded ([3.1](<../../sections/3. Memory governance/3.1. Eviction policies and memory safety.md>)) — TTL'd caches volatile-lru (candidates existing — effectiveness structural); unkeyed sessions allkeys-lru (uniform protection — hot surviving); critical-narrow noeviction-scoped (errors explicit — capacity managed); Lua bounded (scripts small/fast ([2.1](<../../sections/2. Atomic multi-step/2.1. Lua scripting for atomic multi-step.md>)) — microseconds on loop (long scripts blocking — review-bounded; SHA-cached (bandwidth saved — NOSCRIPT fallback handled). "Live" means chosen with reasons (policies matched — scripts bounded — operations answers, never trivia recited).

**What problem it solves** — the trivia-answer trio: *policies recited unmatched* (volatile-lru named (TTL-less datasets unconsidered — candidates absent — effectiveness zero (matching unexamined — recitation failing production); *maxmemory unset* (ceilings unconsidered (OOM killer as policy — eviction by murder (boundedness unowned — operations hoped); *Lua unbounded* (scripts stuffing business logic (event loop blocked — latency spiking (boundedness unreviewed — scripts growing organically (complexity unowned). Chosen policies/scripts convert trivia to operations (matching reasoned — ceilings configured — scripts bounded); interviewers grading operations (choices + reasons + prices → hired; names-only → rejected).

**Modern guidance** — the operations lines (interview-enforced): *TTL'd caches* (volatile-lru (candidates existing — hot surviving (TTL discipline from [Domain 01 §1.2](<../../../01 Redis Foundations and Mental Model/sections/1. What Redis is/1.2. Strings keys and expiry.md>) — eviction effective); *unkeyed sessions* (allkeys-lru (uniform protection — hot surviving statistically); *critical narrow* (noeviction scoped (errors explicit — capacity headroom guaranteeing space); *Lua* (small/fast/bounded (microseconds — review-gated (SHA-cached — NOSCRIPT handled); *monitoring stated* (used_memory gauged — hit rates tracked — evicted_keys watched ([3.1](<../../sections/3. Memory governance/3.1. Eviction policies and memory safety.md>) — saturation visible pre-incident). Policies matched, scripts bounded, saturation gauged (operations complete — trivia never).

```bash
# GOOD: operations answer — policy matched with reasons (interview-grade answer shape).
# "TTL'd product cache → volatile-lru (candidates existing — hot surviving structurally). maxmemory 2gb per
# instance (ceilings configured — OOM killer retired). Gauges at 70/85/95% (saturation visible — eviction
# designed, never discovered). Mismatch returned: volatile on TTL-less sessions (candidates absent — zero effect)."
# BAD: trivia answer — names recited, matching absent (real rejection shape).
# "We use allkeys-lru." (On what dataset? primaries evicted? — matching unexamined (durability violated —
# recitation failing production). maxmemory unset (OOM killer as policy — boundedness unowned). Lua stuffing
# business logic (loop blocked — boundedness unreviewed). Match policies; bound scripts; gauge saturation.)
```

**Common confusion** — *"eviction configuration is ops trivia (developers ship features)."* Policy *matching* lives with design (which keys may die (decided per dataset — developers knowing discardability — matching calibrated, not defaulted); ceilings live with capacity math (dataset + overhead + headroom — designers sizing ([Domain 01 §2.2](<../../../01 Redis Foundations and Mental Model/sections/2. Core structures/2.2. Choosing structures by access.md>) — bounds specified where knowledge lives); gauges live with thresholds (normal ranges known by designers — ops operating dashboards/alerts jointly (interface, not handoff). "Ops trivia" describes operation (dashboards/runbooks — SRE-owned); matching belongs to designers (policies/ceilings chosen per dataset — unmatchable-by-design systems unoperable in production). Match with design; operate jointly.

**Performance note** — operations economics: matched policies cost sampling O(N) per eviction (bounded, small — effectiveness structural); ceilings cost configuration lines (reviewer-checked — OOM kills avoided); bounded Lua costs review gates (scripts staying small — loop unblocked); trivia equivalents cost ineffectiveness (volatile on TTL-less — zero effect); OOM kills (eviction by murder); blocked loops (latency spiking fleet-wide). Match policies (effectiveness structural); configure ceilings (boundedness explicit); bound scripts (loop unblocked).

**Mentor note** — teach "which keys may die?" per dataset (juniors answering with eviction policies design memory operations on first hearing; unanswerable policies interrogated ("evict what?" — discardability demanded per dataset). Policy-matching drill: TTL'd→volatile, unkeyed→allkeys, critical→scoped-noeviction (placements timed, mismatches failing rounds). Match policies; bound scripts; gauge saturation — memory operations in three habits, reviewed per dataset.
