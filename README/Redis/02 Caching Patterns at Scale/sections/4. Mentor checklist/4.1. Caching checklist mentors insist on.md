# 4.1. Caching checklist mentors insist on

## 1. Every pattern names its staleness (aside/TTL, through/zero, back/window — priced per datum, never hoped)

**Definition** — the staleness line on every cached datum: which write pattern owns it ([1.1](<../../sections/1. Write patterns/1.1. Cache-aside write-through write-back.md>)) and what staleness that pattern guarantees (cache-aside: TTL-bounded (reads stale up to TTL — bound stated); write-through: zero (reads fresh — availability coupled, priced); write-back: durability window (persistence async — window stated in seconds, never "eventually"). "Staleness named" means a reviewer can point at any key and read its bound (TTL value, zero-contract, or window length — documented where the key is populated, not in a wiki nobody opens).

**What problem it solves** — the unnamed-staleness trio: *bounds unknown* (patterns chosen by habit (staleness unexamined — TTLs copied from examples (bounds accidental — freshness hoped (correctness unowned); *invalidation unowned* (cache-aside writes invalidating "somewhere" (code paths multiplying — invalidation missing on new write paths (stale reads permanent — TTL as accidental backstop (expiry masking missing invalidation — correctness by timeout); *windows unstated* (write-back queues draining "soon" (drain rate unmeasured — windows hoped (crash loss unbounded — durability theater). Named staleness converts hope to contract (bounds written — invalidation owned per write path — windows measured); reviewers checking lines, not vibes (staleness stated → verifiable; unstated → returned).

**Modern guidance** — the staleness lines per dataset (review-enforced): *aside* (TTL per key class (bounds matched to freshness needs (user profiles minutes, leaderboards seconds — priced per datum); invalidation on every write path (ownership explicit — new write paths adding invalidation or justifying absence (review checklist item, never assumed); *through* (zero-staleness claimed only where cache-down behavior is designed (writes failing loudly — availability coupling priced explicitly); *back* (window measured (queue drain rate gauged — seconds stated (crash-loss bounded numerically — durability priced, never hoped). Unnamed staleness failing review structurally (hope is not a contract).

```javascript
// GOOD: staleness named — TTL bound stated where the key is populated (shape verified).
const TTL_BY_CLASS = { profile: 300, leaderboard: 10 }; // bounds priced per datum (freshness needs matched)
async function getProfile(id) { // cache-aside: stale ≤ 300s by contract (bound readable at call site)
  const hit = await redis.get(`dd:profile:${id}`);
  if (hit) return JSON.parse(hit);
  const row = await db.profiles.findById(id);
  await redis.set(`dd:profile:${id}`, JSON.stringify(row), { EX: TTL_BY_CLASS.profile });
  return row;
}
// BAD: staleness hoped — TTL copied, invalidation unowned (real failure shape).
// await redis.set(key, val, { EX: 3600 }); // bound accidental (copied from example — freshness unexamined)
// write paths multiplying without invalidation (stale reads permanent — TTL masking missing invalidation —
// correctness by timeout (expiry as accidental backstop — hope wearing configuration). Name every bound.)
```

**Common confusion** — *"short TTLs fix staleness (just expire faster)."* Short TTLs bound staleness expensively (miss rate rising (DB load climbing — TTL shortening trading correctness for capacity (bounds bought with misses — price paid per read); invalidation still unowned (write paths still missing deletes (stale reads within window — shorter windows, same disease); hot keys churning (stampedes worsening — short TTLs synchronizing expiry (herds gathering — [1.2](<../../sections/1. Write patterns/1.2. Stampede prevention.md>) working harder to cover TTL laziness). TTLs bound; invalidation corrects (ownership per write path — staleness eliminated, not shortened); both, never TTL-alone.

**Performance note** — staleness economics: TTLs cost miss-rate (bounds priced in DB load — shorter bounds, more misses); invalidation costs delete-per-write (correctness priced in write amplification — small, bounded); write-back windows cost crash-loss (durability priced in seconds of data — stated, insured); unnamed staleness costs incidents (stale reads discovered by customers — price unbounded). Name bounds (priced explicitly); own invalidation (writes carrying deletes); state windows (crash-loss bounded numerically).

**Mentor note** — teach "point at any key, read its bound" (juniors answering per key design staleness discipline on first hearing; unanswerable keys interrogated ("bound where?" — contracts demanded per key class). Review drill: new write path without invalidation returned automatically (ownership structural — checklists enforced, never remembered). Name staleness; own invalidation; state windows — freshness discipline in three habits, reviewed per key class.

## 2. Every hot path coalesces (stampede protection designed — jitter, single-flight, or locks stated)

**Definition** — the coalescing line on every hot read path: which stampede defense owns it ([1.2](<../../sections/1. Write patterns/1.2. Stampede prevention.md>)) — TTL jitter (expiry desynchronized ±10% — herds dispersed structurally); single-flight coalescing (concurrent misses sharing one load — duplicate DB hits suppressed); distributed locks (SET NX mutex per key — one rebuilder, rest waiting with timeout). "Coalesces" means a reviewer can point at any hot key and read its defense (mechanism stated where the key is read — protection designed, never hoped).

**What problem it solves** — the uncoalesced trio: *thundering herds* (hot keys expiring synchronously (misses simultaneous — DB hit N× at once (cascades scheduled — expiry synchronized structurally (uniform TTLs herding misses); *duplicate loads* (concurrent misses each querying (same row loaded N× (DB waste linear in concurrency — coalescing absent (loads unshared — capacity burned); *rebuild races* (concurrent rebuilders clobbering (last-writer-wins on cache (stale overwriting fresh — races unserialized (correctness hoped). Coalescing converts stampedes to single loads (jitter dispersing — single-flight sharing — locks serializing); reviewers checking defenses, not traffic (protection stated → verifiable; unstated → returned).

**Modern guidance** — the coalescing lines per hot path (review-enforced): *jitter everywhere TTLs repeat* (randomized expiry ±10% (synchrony broken structurally — herds dispersed pre-incident); *single-flight where misses are concurrent* (loads shared (duplicate DB hits suppressed — concurrency collapsing to one); *locks where rebuilds must serialize* (SET NX mutex per key (one rebuilder — rest waiting with timeout (liveness bounded — dead rebuilders never blocking forever); *stated at the read site* (defense readable where the key is read — protection designed visibly (reviewers verifying, not assuming). Hot paths without stated defense failing review structurally (hope is not a plan).

```javascript
// GOOD: coalescing stated — jitter + single-flight visible at the read site (shapes verified).
const EX = 300 + Math.floor(Math.random() * 60); // jitter ±10% (synchrony broken — herds dispersed)
const inflight = new Map(); // single-flight (concurrent misses sharing one load — duplicates suppressed)
async function getHot(key) {
  if (inflight.has(key)) return inflight.get(key); // coalesced (loads shared — waste eliminated)
  const p = loadAndCache(key, EX).finally(() => inflight.delete(key));
  inflight.set(key, p);
  return p;
}
// BAD: hot path uncoalesced — uniform TTL, unshared misses (real failure shape).
// await redis.set(key, val, { EX: 300 }); // uniform expiry (misses synchronizing — herds gathering)
// concurrent misses each querying (same row loaded N× — DB waste linear in concurrency — coalescing absent).
// Rebuild races unserialized (last-writer-wins — stale overwriting fresh — correctness hoped). Coalesce hot paths.)
```

**Common confusion** — *"over-provisioning covers stampedes (DB handles spikes)."* Over-provisioning prices stampedes permanently (capacity sized for synchronized worst-case (idle waste between stampedes — cost continuous, incidents merely rarer); synchronized expiry still hammering (spikes simultaneous — provisioned headroom consumed at once (cliffs delayed, not removed); duplicate loads still wasting (N× queries per stampede — capacity burned regardless of size). Provisioning absorbs; coalescing prevents (defenses removing spikes structurally — capacity sized for steady-state, not synchronized worst-case). Coalesce first; provision for growth, never for stampedes.

**Performance note** — coalescing economics: jitter costs randomness per SET (free — arithmetic, not I/O); single-flight costs a Map entry per in-flight miss (microseconds — memory transient); locks cost a SET NX round-trip per rebuild (one RTT — serialization priced); uncoalesced equivalents cost N× DB loads per stampede (waste linear in concurrency — cascades scheduled). Coalesce cheaply (arithmetic + maps + one RTT); absorb never (capacity sized for steady-state).

**Mentor note** — teach "which defense owns this hot key?" (juniors answering per hot path design stampede discipline on first hearing; undefended hot keys interrogated ("defense where?" — protection demanded per hot path). Load-test drill: expiry synchronized in staging, stampede observed, defense added, stampede gone (protection tangible — trust earned by watching herds disperse, not by documentation claims). Jitter TTLs; share misses; serialize rebuilds — coalescing discipline in three habits, reviewed per hot path.

**Cross-links** — stampede mechanics in [1.2](<../../sections/1. Write patterns/1.2. Stampede prevention.md>); lock release safety (token-verified Lua) in the same leaf.

## 3. Every multi-step is atomic-or-explicit (Lua/transactions where races threaten — hope scheduled never)

**Definition** — the atomicity line on every multi-step sequence: either atomic (Lua scripts ([2.1](<../../sections/2. Atomic multi-step/2.1. Lua scripting for atomic multi-step.md>)) — check-and-set indivisible (no interleaving — races eliminated structurally); MULTI/EXEC batches ([2.2](<../../sections/2. Atomic multi-step/2.2. Transactions MULTI EXEC WATCH.md>)) — isolation without rollback (interleaving eliminated — errors per command, designed)) or explicitly non-atomic (partial outcomes acceptable AND compensations designed (saga-style reversals per business operation — hope scheduled never (partial states named, handlers written, tested). "Atomic-or-explicit" means a reviewer can point at any multi-command sequence and read its guarantee (indivisible, isolated, or compensated — stated where the commands run).

**What problem it solves** — the assumed-atomicity trio: *check-then-set races* (reads then writes interleaved (concurrent clients clobbering (oversold inventory, double-spend — races hoped away (correctness by timing — interleaving unconsidered); *batch partials surprising* (MULTI/EXEC half-applying (commands failing mid-batch (state half-mutated — rollback assumed (transactions-are-not-rollbacks unlearned — recovery unplanned); *cross-system partials* (cache + DB diverging (one succeeding, other failing (inconsistency permanent — compensation unconsidered (hope as integration strategy — divergence discovered by customers). Atomic-or-explicit converts assumption to guarantee (Lua indivisibility — EXEC isolation — compensations designed); reviewers checking guarantees, not sequences (atomicity stated → verifiable; unstated → returned).

**Modern guidance** — the atomicity lines per sequence (review-enforced): *races → Lua* (check-and-set indivisible (interleaving eliminated — races structurally impossible (scripts small, fast, SHA-cached); *batching → MULTI/EXEC* (isolation without rollback (interleaving eliminated — per-command errors handled explicitly (partials recoverable by idempotent design); *cross-system → explicit* (compensation per business operation (reversals designed, written, tested — outbox honesty in [Database Design §6.2](<../../../../DatabaseDesign/06 Modeling for Operations/sections/2. Coordination out of the database/2.1. Outbox tables designed for relay.md>) — linked, not repeated); *stated at the sequence* (guarantee readable where commands run — atomicity designed visibly). Multi-steps without stated guarantees failing review structurally (hope is not atomicity).

```lua
-- GOOD: atomic-or-explicit — guarantee stated where commands run (shape verified).
-- Race threatens → Lua (indivisible — check-and-decrement structurally race-free):
-- KEYS[1] stock key, ARGV[1] quantity (guarantee: atomic — stated at call site, verified in 2.1).
local s = tonumber(redis.call('GET', KEYS[1]) or '0')
if s < tonumber(ARGV[1]) then return 0 end
redis.call('DECRBY', KEYS[1], ARGV[1])
return 1
```

```javascript
// BAD: assumed atomicity — check-then-set hoping (real failure shape).
// const s = await redis.get('dd:stock'); // interleaving window open (concurrent clients clobbering —
// if (s >= qty) await redis.decrBy('dd:stock', qty); // race hoped away — oversold inventory scheduled).
// EXEC partials surprising (rollback assumed — recovery unplanned). Cross-system divergence uncompensated
// (cache + DB diverging — hope as integration strategy). State every guarantee; hope none.)
```

**Common confusion** — *"small windows don't race (too fast to collide)."* Windows scale with concurrency (hot keys colliding constantly (windows × request rate = collisions (rare at 10 rps, certain at 10k — probability priced per hot path, never assumed); timing shifts under load (GC pauses widening windows (pauses interleaving exactly where races live — load correlating with collision); tests passing single-threaded (races invisible locally — confidence false (production concurrent — collisions scheduled). "Too fast" describes unloaded timing (single-client fiction — windows uncontended); production contends (windows × concurrency = certainty). Atomicity structural (Lua/EXEC — races impossible); timing never trusted (windows racing under load, always).

**Performance note** — atomicity economics: Lua costs script execution on the event loop (small/fast scripts — microseconds (long scripts blocking — bounded by review); EXEC costs batching round-trips (fewer RTTs — isolation free with batching); explicit compensation costs reversal code per operation (correctness priced in code — written once, tested always); assumed atomicity costs oversells/double-spends/divergence (price unbounded — incidents discovering races). Atomicize races (Lua — microseconds); batch sequences (EXEC — fewer RTTs); compensate cross-system (reversals — code priced once).

**Mentor note** — teach "state the guarantee, not the sequence" (juniors answering atomic/isolated/compensated per multi-step design atomicity discipline on first hearing; unstated sequences interrogated ("guarantee where?" — atomicity demanded per sequence). Race drill: concurrent decrementers overselling without Lua, then indivisible with Lua (guarantees tangible — trust earned by watching races vanish, not by documentation claims). Atomicize races; batch sequences; compensate cross-system — atomicity discipline in three habits, reviewed per multi-step.
