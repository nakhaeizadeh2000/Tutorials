# 1.1. Cache-aside write-through write-back

## 1. Three writes, three staleness contracts (aside/TTL-bounded, through/zero, back/async)

**Definition** — the three write patterns (chosen per datum, never defaulted globally): **cache-aside + TTL** (writes to DB only, reads populating cache lazily ([Domain 01 §3.1](<../../../01 Redis Foundations and Mental Model/sections/3. First caching/3.1. Hello caching with cache-aside.md>) performed — staleness bounded by TTL + invalidation ([Domain 01 §3.1](<../../../01 Redis Foundations and Mental Model/sections/3. First caching/3.1. Hello caching with cache-aside.md>) — invalidation named per datum); **write-through** (mutations updating cache synchronously (verified live below — SET on write path, GET serving fresh — staleness zero *between* writes (reads never stale — writes paying cache round trips (latency added per mutation — availability coupled (cache failures failing writes unless decoupled); **write-back** (mutations queued for async persistence (verified live: LPUSH write-intent + BRPOPLPUSH reliable handoff — durability window = queue drain time (stated, monitored — async persistence with loss window explicit, never hoped).

**What problem it solves** — the unchosen-write trio (writes defaulting to cache-aside everywhere (hot-write workloads paying DB latency per mutation (write-heavy counters/leaderboards hammering primaries — write path uncached by habit (counters incrementing in Postgres — row locks contending — Redis INCR unexamined); write-through everywhere (reads-always-fresh dogma (write latency including cache round trips (slow path per mutation — cache failures failing writes (availability coupled — worse trade for read-heavy workloads (freshness overpriced); write-back nowhere-or-everywhere (async persistence unexamined (durability windows unstated — loss windows hoped (crash losing unflushed intents — durability fiction). Pattern-per-datum converts defaults to decisions (hot writes → write-back/counters (latency minimal); fresh reads → write-through (staleness zero — coupling priced); read-heavy → cache-aside (lazy efficiency — staleness TTL-bounded).

## 2. Write-through couples availability (reads always fresh — writes failing cache-down, priced explicitly)

**Definition** — the coupling contract: write-through guarantees read-freshness (cache updated synchronously per mutation — reads never stale (staleness zero *between* writes — verified live: SET then GET serving fresh); prices availability coupling (cache failures failing writes (cache-down → mutation errors (primary writable, writes blocked — auxiliary system gating primary (absurd inversion — availability coupled); latency coupling (cache round trips per mutation (p99 write latency including cache (user-facing writes slower — latency billed per write). Coupling priced explicitly (freshness value vs availability risk — business tolerance deciding, never hope); decoupled variants where coupling unacceptable (write-behind with acknowledgment (durability window stated — availability preserved structurally).

**What problem it solves** — the coupled-write duo: *freshness dogma* (write-through everywhere ("reads must be fresh" — flat requirement across data (product catalogs needing write-through freshness (TTL+invalidation serving equivalently fresh at fraction of coupling — dogma overpricing); *cache-down cascades* (cache failures failing writes (outage in auxiliary felling primary mutations (availability inverted — cache SLA exceeding database SLA effectively (weaker system gating stronger — absurdity operationalized). Priced coupling converts dogma to decisions (freshness-critical + write-infrequent → write-through (coupling priced, accepted explicitly); read-heavy → invalidate-on-write (freshness equivalent (write-propagation latency — coupling declined (writes succeeding cache-down — availability preserved).

**Modern guidance** — the coupling lines per write-through adoption (review-enforced): *freshness need* (reads requiring zero staleness (balances? inventory counts? (TTL+invalidation insufficient — write-propagation latency unacceptable — freshness genuinely required (stated with business reason — "reads must be fresh" interrogated ("fresh within what window?" — milliseconds (write-through) vs seconds (invalidate+short-TTL — usually sufficient — dogma distinguished from need); *coupling price* (write latency including cache (p99 impact measured — user-facing writes slower — latency budgeted); cache-down behavior designed (writes succeeding cache-down (decoupled — availability preserved) vs failing (coupled — freshness guaranteed — tradeoff stated explicitly, never defaulted); *fallback* (decoupled mode on cache failure (writes proceeding DB-direct (freshness degrading gracefully to TTL-bounded (degradation ordered — cache outage not blocking mutations — fallback tested, not hoped).

# Price: write latency + cache round trips (p99 impact measured — budgeted explicitly).
# Fallback: cache-down → DB-direct writes (degraded freshness (TTL-bounded) — availability preserved).
# Verified live pattern: SET then GET fresh (write path populating — reads fresh between writes).

```bash

# Product catalogs write-through (TTL+invalidation serving equivalently fresh (dogma overpricing —
# write latency per mutation for freshness unneeded (tolerance unasked — milliseconds worshipped).
# Cache-down cascading (failures failing writes (outage in auxiliary felling primary mutations —
# availability inverted — cache SLA exceeding database SLA effectively (absurdity operationalized).

```

**Common confusion** — *"invalidate-on-write equals write-through (same freshness)."* Invalidate-then-lazy-load serves *post-propagation* freshness (write → DEL → next read misses → DB loads fresh (staleness window = propagation + first-miss latency (milliseconds typically — equivalent practically); write-through serves *immediate* freshness (cache updated in write path — zero window (microseconds tighter — priced in coupling (writes failing cache-down — availability coupled). "Equals" ignores coupling (same freshness, different availability — invalidate decoupled (writes surviving cache-down); through coupled (writes dying with cache). Freshness equivalent practically; availability differing structurally — choose per coupling tolerance, never per freshness dogma.

**Performance note** — coupling economics: write-through costs cache round trips per mutation (latency added to writes — p99 write latency including cache (user-facing writes slower — budgeted); cache-down failures (mutations erroring — availability coupled — fallback designed (decoupled mode preserving availability); invalidate-on-write costs DEL per mutation (single command — cheap — staleness at propagation latency (milliseconds — freshness equivalent practically); TTL backing costs nothing per mutation (expiry handling staleness — bounded regardless). Freshness priced per strategy (zero/void... zero-window vs propagation-window — business tolerance deciding); availability preserved via decoupling (writes succeeding cache-down — fallback tested). Price freshness; preserve availability.

**Mentor note** — teach "freshness within what window?" (juniors answering in milliseconds-vs-seconds place strategies accurately on first hearing; "always fresh" interrogated (window demanded — zero (write-through, coupling priced) vs propagation (invalidate, decoupled) vs TTL (simplest, tolerance-allowed). Freshness windows priced like latency budgets (numbers, not adjectives — milliseconds stated, coupling accepted explicitly). Window stated; coupling priced; fallback designed — freshness discipline in three habits, reviewed per datum.

## 3. Write-back buys speed with risk (async persistence — durability windows stated, never hoped)

**Definition** — the async contract: write-back acknowledges writes at cache speed (mutations completing in microseconds — durability deferred (queue depth = loss window (crash losing unflushed intents — window stated in seconds-to-minutes (monitored — backlog gauged, alerts firing); flush workers persisting to primaries (drain latency bounded (throughput matched — workers keeping pace (backlog stable, not growing — lag dashboarded); verified live pattern: LPUSH intent + BRPOPLPUSH reliable handoff (crash-safe processing — workers dying mid-handoff recoverable (processing list reclaimable — at-least-once preserved). Speed bought (microsecond writes); risk priced (loss window explicit — durability deferred, never denied).

**What problem it solves** — the synchronous-write ceiling (hot writes bottlenecked on primary latency (counters/leaderboards/analytics-ingest hammering databases (write latency milliseconds per mutation (throughput = 1/latency per connection — counters unscalable synchronously; row locks contending (hot rows serializing writers — throughput collapsing to lock-hold latency); and the async-denial duo (durability windows unstated (crash losing unflushed intents — loss discovered post-crash (windows hoped (durability fiction); queue unbounded (backlog growing under sustained load (drain rate < ingest rate — lag growing unboundedly (loss window widening silently — alerts absent (backlog unmonitored). Async persistence converts ceilings to windows (microsecond acknowledges — throughput decoupled from primary latency); stated windows convert fiction to engineering (loss bounded (seconds-to-minutes — business-accepted explicitly (signed, not hoped).

**Modern guidance** — the async lines per write-back adoption (review-enforced — verified live shapes): *window stated* (durability window in seconds-to-minutes (crash losing unflushed intents within window (loss accepted explicitly (business-signed — windows hoped never); *drain matched* (flush throughput ≥ ingest rate (backlog stable (gauged — lag dashboarded (alerts firing on growth — workers scaled proactively (drain keeping pace — lag bounded); *handoff reliable* (BRPOPLPUSH processing lists (verified live pattern — crash-safe handoff (workers dying mid-handoff recoverable — at-least-once preserved (duplicates idempotent-handled downstream — [Database Design §6.2 analogue applied — outbox honesty referenced, not repeated); *recovery rehearsed* (crash drills (unflushed intents quantified post-crash (loss measured vs window stated — windows validated, not hoped (discrepancies tightening windows or quickening drains).
