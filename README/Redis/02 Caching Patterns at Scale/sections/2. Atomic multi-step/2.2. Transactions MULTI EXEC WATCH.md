# 2.2. Transactions MULTI EXEC WATCH

## 1. MULTI queues, EXEC runs (optimistic batching — commands queued, executed atomically-ish)

**Definition** — transactions: `MULTI` opening queue mode (commands buffered client-side-or-server-side (queued, not executed — syntax validated per command (errors surfacing at queue time for malformed commands (early failure, cheap); `EXEC` executing queued commands atomically-ish (all-or-nothing *issuance* — commands running sequentially without interleaving (isolation during execution); `DISCARD` abandoning queues (queued commands dropped (client-side abort — no-op server-side (clean cancellation). Atomic-ish, precisely: isolation guaranteed (no interleaving mid-EXEC); rollback absent (runtime errors mid-EXEC persisting prior commands (next promise details — errors isolated per command, designed, never assumed atomic).

**What problem it solves** — the round-trip tax (N related commands × network latency (chatty clients paying per command (milliseconds × N — throughput divided by chattiness (pipelining helping partially (responses still per-command — client processing per reply); and the interleaving hazard (multi-command updates racing concurrent writers (read-modify-write across clients (balances checked then set (interleavings corrupting (correctness scheduled — races inherent to separated commands). MULTI/EXEC converts round trips to one (commands batched — network crossed once (latency divided by N); interleaving eliminated during execution (atomic-ish issuance — no concurrent commands interleaving mid-batch (isolation structural for the execution window).

**Modern guidance** — the transaction lines per multi-command unit (review-enforced): *batch related* (dependent commands queued together (read-own-writes within EXEC visible per subsequent queued command (client libraries surfacing queued results appropriately — check client semantics (node-redis returns EXEC array (results ordered — correlation positional); *discard deliberately* (abandoning malformed queues (DISCARD on build errors (queued garbage never executing — hygiene); *errors expected per command* (runtime failures mid-EXEC persisting priors (next promise owns the semantics — callers handling partial application (verified shapes — errors isolated, never rolled back). Missing batching where round trips dominate → request changes (chattiness taxed per command — batching free structurally).

```bash

# MULTI (queue mode opened — commands buffered, syntax validated per command)
# SET + INCR + EXPIRE batched (related mutations — one round trip (latency divided by N))
# EXEC (executed atomically-ish — no interleaving mid-batch (isolation structural for the window))

```


**Common confusion** — *"MULTI/EXEC is ACID transactions (like Postgres)."* MULTI/EXEC provides *isolation-during-execution* (no interleaving — atomic issuance); ACID adds *atomicity-on-error* (all-or-nothing persistence — rollback on failure — absent here (runtime errors persisting priors (next promise details — partial application designed around, never assumed away); *durability* (fsync policies — Redis persistence orthogonal (Domain 04 owns — transactions not making data durable (conflation scheduled otherwise); *consistency* (invariants maintained — application-enforced via WATCH-patterns (next promise — optimistic checks, not constraint engines). Isolation yes; atomicity-on-error no; durability orthogonal; consistency application-owned. ACID-quarter (I alone) — name precisely, assume never.

**Performance note** — batching economics: MULTI/EXEC costs one round trip (vs N separate (latency divided by batching — throughput multiplied structurally); queue validation costs syntax checks per command (malformed failing fast at queue time — cheap errors, early signals); unbatched equivalents cost N round trips (latency × N (chattiness taxing throughput — network dominating microsecond commands); interleaving hazards cost races (correctness scheduled — incidents quarterly). Batch related (round trips minimized); validate at queue (errors early); isolate during execution (interleaving eliminated).

**Mentor note** — teach "batch related commands" (juniors queueing multi-command units design round-trip-efficient flows on first hearing; chatty sequences interrogated ("batchable?" — batching demanded per related unit). Demonstrate interleaving elimination once (concurrent writers around EXEC batches (isolation visible — no interleaving mid-batch — tangibility converting permanently — batching trusted because observed, not hoped). Batch related; discard malformed; isolate execution — transaction discipline in three habits, reviewed per multi-command unit.

## 2. WATCH aborts on change (check-and-set across keys — concurrent modification retrying)

**Definition** — optimistic locking: `WATCH key` monitoring (server tracking watched keys per connection (modifications flagged (any writer changing watched keys (including the watcher itself elsewhere — self-modification aborting own transactions (correctness over convenience — surprising once, understood permanently); `EXEC` aborting on flagged changes (verified live pattern below: concurrent modification → abort (nil historically — node-redis v6 *throwing* `WatchError` instead (verified live this session — client-version behavior, code handling both (nil-check OR catch — compatibility across client versions); retry loops re-reading fresh state (aborts handled by re-executing business logic on current data (optimistic concurrency — contention paying retries, uncontended fast-paths paying nothing).

**What problem it solves** — the check-and-set race (read balance → decide → write new (concurrent deciders interleaving (both reading 100, both writing 90 (lost update — correctness evaporating under concurrency (verified live pattern inverted: WATCH detecting mid-transaction modification — abort instead of clobber (correctness preserved structurally); and the pessimistic alternative (distributed locks per check-and-set (lock acquisition latency per decision (round trips + TTL management + release safety — coordination overhead for single-key decisions (locks pricing what WATCH provides free (optimistic checks costing nothing uncontended — pessimism taxing always). WATCH converts races to retries (aborts on change — correctness preserved; retry on abort — progress guaranteed sans contention storms (bounded retries with backoff — livelock avoided structurally).

## 3. Transactions are not rollbacks (partial EXEC failures persist — errors isolated per command)

**Definition** — the semantic boundary: EXEC executes queued commands sequentially, collecting per-command results/errors (runtime error in command 3 of 5 → commands 1–2 persist (applied, durable per persistence config — no rollback (Redis has none — design decision, not missing feature (simplicity over atomicity-on-error — documented, deliberate); error returned alongside successes (callers inspecting per-command outcomes (partial application visible — handling designed, never hoped). Atomic-ish issuance (isolation during execution — no interleaving); non-atomic persistence (errors isolated per command — prior effects standing). Both properties simultaneously — isolation without rollback, always.

**What problem it solves** — the rollback-assumption duo: *assuming atomicity-on-error* (multi-command units with mid-batch failures leaving partial state (commands 1–2 applied, 3 errored (callers checking only final status (partial application unnoticed — inconsistency scheduled (half-applied business operations persisting (compensations unplanned — orphans accumulating); and *compensating naively* (manual rollback on EXEC errors (inverse commands issued (non-atomic compensation itself (races interleaving (compensation failing midway — doubly-partial states (original partial + compensation partial — archaeology squared). Per-command error handling converts both (results inspected per command (partial application visible — designed responses per failure point (compensate where safe, alert where manual (judgment per command, never blanket rollback).

**Modern guidance** — the error-handling lines per transaction (review-enforced): *inspect per command* (EXEC results walked (successes confirmed, errors located (partial application visible — handling designed per failure point (compensate automatable failures (idempotent inverses — safe to retry); alert manual ones (judgment-required — paged, never auto-compensated); *design idempotent units* (transaction contents retry-safe (re-execution converging (same end state reapplied (partial + retry = complete — idempotency making partial application recoverable structurally); *compensate deliberately* (compensating transactions designed per business operation (saga-style reversals — [Database Design... saga/outbox patterns (relational/document context — compensation philosophy shared, never repeated); *avoid error-prone batching* (commands validated pre-queue where feasible (argument checking client-side (type/range validated — runtime errors preempted structurally (failures prevented beat failures handled).

**Common confusion** — *"Redis transactions are broken (no rollback)."
