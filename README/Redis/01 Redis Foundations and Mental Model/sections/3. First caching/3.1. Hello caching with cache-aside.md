# 3.1. Hello caching with cache-aside

## 1. Cache-aside flow (read cache, miss loads DB, write back with TTL — performed)

**Definition** — cache-aside (lazy loading): reads check cache first (`GET` — hit returns (fast path — sub-millisecond); miss loads the database (source of truth queried — slow path, tolerated occasionally); result written back with TTL (`SET ... EX` — subsequent reads hitting (amortizing the miss cost across TTL window). Writes go to the database (cache *not* updated on write — invalidation separate (next promise) — readers repopulating lazily (stale window bounded by TTL + invalidation policy). Application orchestrating (cache + DB + TTL in code — three systems coordinated per read — the dominant caching pattern industry-wide for good reason: simple, robust, failure-tolerant (cache loss degrading to DB reads — never correctness).

**What problem it solves** — the uncached hot path (every read hitting the database (hot rows queried thousands/second (connection pressure, query load, latency milliseconds — database scaling for cacheable reads (expensive horizontal scaling for repeated identical answers); and the write-through-everywhere overkill (all writes populating cache synchronously (write latency including cache round trips (slow path per write — cache failures failing writes (availability coupled — cache outage blocking database writes absurdly). Cache-aside converts hot reads to memory hits (miss cost amortized over TTL window — 800k/day reads served from RAM (database unbothered); write path decoupled from cache health (writes succeeding cache-down (readers repopulating on recovery — availability preserved structurally).

**Modern guidance** — the cache-aside lines per cached read (review-enforced — verified live shapes on Redis 8.0.2 + node-redis 6.3.0): *read path* (GET → hit: return (fast); miss: DB load → SET EX → return (verified live below: miss→hit→TTL 300→invalidate→miss — full cycle observed); *TTL per entry* (lifetimes declared per write (hot data long-lived (hours — churn minimal); volatile data short (minutes — freshness bounded); *miss handling* (thundering herds on synchronized expiry — jittered TTLs ±10% (expiry desynchronized — stampedes dispersed ([1.2](<../1. What Redis is/1.2. Strings keys and expiry.md>)); *failure mode* (cache-down → DB reads directly (degraded latency, correct answers — availability preserved (cache loss degrading performance, never correctness — circuit-breaking cache calls where DB-direct fallback exists).

```javascript
// GOOD: cache-aside performed — miss, load, write-back, hit, invalidate (verified live: 8.0.2 + node-redis).
async function getUser(id) {
  const k = "dd:cache:user:" + id;
  const hit = await c.get(k);
  if (hit) return { src: "hit", v: hit };   // fast path (sub-millisecond — verified live pattern)
  const v = db["u:" + id];                  // miss: source of truth (slow path, tolerated occasionally)
  if (v) await c.set(k, v, { EX: 300 });    // write-back with TTL (verified live: TTL 300 observed)
  return { src: "miss", v };
}
// Live: 1st miss → 2nd hit → ttl 300 → DEL → miss (verified output — full cycle observed, keys cleaned).
```

**Common confusion** — *"cache-aside risks stale data (use write-through always)."* Staleness priced per TTL (bounded window (minutes-to-hours — business-tolerated where declared (product/session data stale-tolerant; financial balances not — staleness contracts per datum, never global); invalidation covering writes (next promise — explicit invalidation on mutation (staleness window shrinking to write-propagation latency). "Risky" describes unbounded staleness (TTL-less caches (fossilizing — freshness decaying silently); write-through-everything prices differently (write latency including cache round trips (slow path per write — cache failures failing writes (availability coupled — worse trade for read-heavy workloads). Price staleness per datum (TTL + invalidation — bounded, declared); couple availability never (writes succeeding cache-down).

**Performance note** — cache-aside economics: hits cost sub-millisecond RAM reads (p50/p99 flat — hot paths unblocked — API latencies dominated by compute, never data-fetch); misses cost DB read + write-back (amortized over TTL window (800k/day reads, 1k misses (miss ratio 0.1% — DB unbothered (load reduced 1000× — database sizing for misses, not reads); invalidation costs DEL per mutation (writes paying invalidation (cheap — single command — staleness bounded structurally). Uncached equivalents cost database-per-read (connection pressure (pool exhaustion via cacheable reads); query load scaling with traffic (horizontal scaling for static answers); latency milliseconds per read (p99 dominated by fetch). Cache lazily; invalidate explicitly; expire always.

**Mentor note** — teach "miss, load, write-back" (juniors narrating the three steps design cache-aside correctly on first hearing; unexamined caching interrogated ("miss path? TTL? invalidation?" — three questions, seconds each, unexamined caches returned). Demonstrate miss→hit live once (verified live pattern above (miss, hit, TTL observed, invalidate, miss again — full cycle tangible — trust earned by watching laziness work, not by documentation claims). Miss, load, write-back — caching discipline in three verbs, reviewed per cached read.

## 2. Invalidation named upfront (write-through vs invalidate vs TTL-only — staleness priced per choice)

**Definition** — the invalidation triad (chosen per datum at design time, never discovered in production): **invalidate-on-write** (mutations DELeting affected keys (staleness window = write-propagation latency (milliseconds — freshest lazy option; failure mode: missed invalidation paths (writers forgetting keys — stale serving until TTL (TTL backing invalidation — belt and suspenders, always); **write-through** (mutations updating cache synchronously (reads always fresh (staleness zero — write latency including cache round trips (slow path per write — cache failures failing writes unless decoupled (availability coupled — worse trade for read-heavy); **TTL-only** (no explicit invalidation (staleness bounded by TTL alone (minutes-to-hours — simplest correct where tolerance allows (product catalogs, configs, leaderboards — freshness non-critical). Staleness priced per choice (milliseconds vs zero vs TTL-window — business tolerance deciding, never hope).

**What problem it solves** — the invalidation duo: *invalidation absent* (writes never clearing (stale data served indefinitely (TTL-less caches fossilizing — freshness decaying silently (invalidation unconsidered — caches write-once/read-forever (correctness expiring on first mutation); and *invalidation hopeful* ("the app clears cache" — unwitnessed paths (new writers forgetting (backfills/admin/scripts bypassing application invalidation (stale serving for unexamined writers — coverage hoped, not enforced). Named invalidation converts hope to procedure (strategy per datum (invalidate/write-through/TTL-only — staleness priced; writers enumerated (application + backfill + console + future services — invalidation paths owned per writer (TTL backing all (belt and suspenders — invalidation missed → TTL expiring (freshness bounded regardless).

**Modern guidance** — the invalidation lines per cached datum (review-enforced): *strategy* (invalidate-on-write default (staleness minimal — write-propagation latency; write-through where freshness critical AND writes infrequent (balances read fresh — mutation paths few — cache failures decoupled (writes succeeding cache-down (availability preserved — TTL-only where tolerance allows (product/configs/leaderboards — simplicity correct); *writers enumerated* (application + backfill + console + future services (invalidation paths owned per writer — new writers inheriting invalidation duty (documented in writer onboarding — coverage enforced, never hoped); *TTL backing* (all strategies TTL-bounded (invalidation missed → TTL expiring (freshness bounded regardless — belt and suspenders, always — TTL-only entries self-evidently bounded). Missing strategy → request changes (unstated staleness failing structurally — freshness hoped, never priced).

**Common confusion** — *"write-through is strictly better (always fresh)."* Freshness priced in write latency + availability coupling (cache round trips per mutation (slow path per write — p99 write latency including cache (user-facing writes slower — latency billed per mutation); cache failures failing writes (availability coupled — cache outage blocking database writes (absurd inversion — auxiliary system gating primary). "Strictly better" ignores price (freshness free — false (latency + coupling billed per write); invalidate-on-write matches freshness closely (write-propagation latency — milliseconds — at fraction of coupling (writes succeeding cache-down — availability preserved). Price freshness (latency + coupling per strategy); match tolerance (TTL-only where allowed — simplest correct wins).

**Performance note** — invalidation economics: invalidate-on-write costs DEL per mutation (single command — cheap — staleness minimal (milliseconds); write-through costs cache round trips per mutation (latency added to writes — p99 write latency including cache (user-facing writes slower); TTL-only costs nothing per mutation (expiry handling staleness — zero write overhead — staleness bounded by TTL (minutes-to-hours). Staleness priced per strategy (milliseconds vs zero vs TTL-window — business tolerance deciding); availability preserved via decoupling (writes succeeding cache-down — TTL backing all strategies (belt and suspenders). Price staleness; preserve availability; back with TTL.

Invalidation paths enumerated per writer (application + backfill + console + future — coverage enforced, never hoped). Name staleness; enumerate writers; back with TTL — invalidation discipline in three habits, reviewed per cached datum.

## 3. Cold starts priced (thundering herds on empty caches — warming and coalescing designed)

**Definition** — the cold-start problem: empty/expired caches meeting traffic spikes (deploys flushing (restarts wiping (persistence unconfigured — cold start per deploy); synchronized TTL expiry (thousands of keys expiring simultaneously (miss storm — all requests hitting database at once (connection saturation — pool exhaustion via cache miss (thundering herd — linear cause (one expiry wave), exponential harm (retry-amplified outage); viral traffic on cold keys (launch spikes hitting uncached paths (database absorbing full launch load — provisioning for peaks instead of warming). Warming (pre-populating post-deploy/restart — hot keys loaded before traffic) + coalescing (single-flight miss handling — concurrent misses sharing one DB load (duplicate misses suppressed structurally) + jitter (TTL ±10% desynchronizing expiry — herds dispersed).

**What problem it solves** — the cold-start trio: *deploy-flush outages* (restarts wiping caches (persistence unconfigured — cold start per deploy (traffic hitting databases directly post-restart (saturation scheduled per release — deploys causing incidents (velocity punishing reliability); *synchronized stampedes* (TTL-aligned expiries (thousands expiring same second — miss storm (all requests loading database simultaneously (connection saturation — pool exhaustion via cache miss (thundering herd — linear cause, exponential harm); *viral cold paths* (launch traffic on uncached features (database absorbing full spike (provisioned for peaks (over-provisioned permanently for minutes-long spikes — capacity wasteful) or saturated (outages official). Warming/coalescing/jitter convert all three (pre-populated caches (traffic served from warm — deploys non-events); desynchronized expiry (herds dispersed — stampedes structurally impossible); coalesced misses (single-flight loading — duplicate DB hits suppressed).

**Modern guidance** — the cold-start lines per cache (review-enforced): *warming* (post-deploy/restart pre-population (hot keys loaded before traffic (warming jobs/scripts — caches warm at traffic arrival — deploys non-events (restarts rehearsed with warming — cold starts eliminated structurally, never hoped away); *coalescing* (single-flight miss handling (concurrent misses sharing one DB load (duplicate misses suppressed — first miss loading, rest waiting (promises shared — thundering herd reduced to one query (stampedes structurally impossible); *jitter* (TTL ±10% randomized (expiry desynchronized — synchronized waves dispersed (herds impossible — [1.2](<../1. What Redis is/1.2. Strings keys and expiry.md>) performed); *persistence* (RDB/AOF warming across restarts (Domain 04 owns fully — warm caches surviving deploys (persistence configured — cold starts eliminated at the storage layer (restarts rehearsed, data intact).

**Common confusion** — *"bigger databases handle cold starts (over-provision)."* Over-provisioning handles *steady* peaks (sustained traffic growth — capacity planning ([Database Design §5.2](<../../../../DatabaseDesign/05 Evolution Growth and Partitioning/sections/2. "Bigger" prices steady-state (sustained load — provisioned); warming/coalescing/jitter price transients (spikes absorbed structurally — stampedes impossible regardless of provisioned size). Provision steady-state (capacity math); absorb transients structurally (warming/coalescing/jitter). Both, always — neither alone suffices.

**Performance note** — cold-start economics: warming costs pre-population jobs (hot keys loaded pre-traffic — minutes per deploy — deploys non-events); coalescing costs promise-sharing code (single-flight per key — duplicate DB hits suppressed — stampedes structurally impossible); jitter costs randomness per TTL (±10% — expiry desynchronized — herds dispersed); unpriced equivalents cost saturation incidents (miss storms — connection exhaustion (pools draining — cascading retries amplifying); viral outages (unprovisioned spikes — saturated officially); deploy incidents (restarts wiping — traffic hitting databases directly). Warm cheaply (jobs); coalesce structurally (promises); jitter always (randomness).

Warm caches; coalesce misses; jitter expiries — cold-start discipline in three habits, reviewed per cache.
