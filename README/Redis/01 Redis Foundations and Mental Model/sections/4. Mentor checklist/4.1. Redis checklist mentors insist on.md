# 4.1. Redis checklist mentors insist on

## 1. Every key earns its namespace and TTL (no bare keys, no immortal transients)

**Definition** — the review's first pass over Redis usage: every key arrives namespaced (`app:domain:id[:field]` — ownership visible ([1.2](<../1. What Redis is/1.2. Strings keys and expiry.md>)) and TTL'd where transient (sessions/tokens/caches/locks/rate-windows — lifetimes declared ([1.2](<../1. What Redis is/1.2. Strings keys and expiry.md>)) — or explicitly permanent with reason (config permanent by design (documented); data permanent by audit (retention decided — permanence deliberate, never defaulted). Bare keys (unprefixed — ownership unknown) and immortal transients (TTL-less sessions — memory leaking) fail review structurally — naming and lifetimes stated per key, never hoped.

**What problem it solves** — the unnamed-unbounded duo (flat keyspaces (ownership unknown — archaeology per incident (keyspace inscrutable — debugging blind); collisions scheduled (two features, one name — last-writer-wins across domains (sessions overwriting carts — cross-domain clobbering); immortal transients (memory growing per login/token/cache-write (leak scheduled (retention infinite by default — capacity fiction); locks petrifying (crashed holders blocking forever — toil scheduled). Namespaces convert flat chaos to navigable order (ownership visible, collisions structurally avoided, operations patterned); TTLs convert leaks to cycles (memory reclaimed structurally — leak impossible where lifetimes declared).

**Modern guidance** — the key review lines (review-enforced): *namespace* (`app:domain:id[:field]` — 3–4 segments (ownership visible — registry documented (owners paged per keyspace incident); *TTL* (transients expiring (EX/PX at write — lifetimes declared — verified live patterns (NX+EX conditional bounded creates; TTL observed 300); permanence deliberate (TTL-less keys enumerated periodically (immortals justified (config by design) or TTL'd (accidents fixed); *patterns* (SCAN MATCH per namespace (operations patterned — per-namespace TTL sweeps/migrations/purges — targeted, never global). Missing namespace/TTL → request changes; permanence unstated → justify or expire (immortal by omission failing structurally).

```bash
# GOOD: the key review artifact — namespaced, bounded, patterned (excerpt).
# Keys: shop:session:* (auth-owned, EX 3600 — transients dying on schedule ✓).
# shop:cache:product:* (TTL 300 + invalidate-on-write (staleness bounded doubly ✓).
# config:theme (TTL-less by design — documented permanence (reviewed, never defaulted) ✓).
# Patterns: SCAN MATCH per namespace (operations targeted ✓). Verdict: approve keys.
```

```bash
# BAD: the unnamed-unbounded keyspace — flat, immortal, unpatterned (real failure shapes).
# session123 (whose? — archaeology per incident (ownership unknown — debugging blind).
# temp / data / cache (collisions scheduled — cross-domain clobbering (sessions overwriting carts).
# Tokens TTL-less (memory leaking per login — retention infinite by default — capacity fiction).
# Patterns: none (SCAN * required — per-key surgery needing full enumeration (millions scanned).
# Flat keys; immortal transients; unpatterned operations. Review minutes vs outage quarters.)
```

**Common confusion** — *"naming conventions are bike-shedding (any names work)."* Names carry *ownership and operability* (namespaced keys routable (SCAN MATCH per domain — operations targeted); TTL-carrying conventions auditable (lifetimes visible per pattern — retention reviewed); flat names carrying neither (ownership unknown — operations global — lifetimes unstated). "Bike-shedding" describes aesthetic debates (tabs vs spaces — taste without consequence); namespaces decide operability (ownership/operations/lifetimes — consequence-laden). Name functionally (ownership/patterns/lifetimes visible); debate never (conventions documented once, followed always).

**Performance note** — naming/TTL economics: namespaces cost bytes per key (measured overhead — verbose namespaces taxing per-key RAM (brevity balanced with clarity — conventional abbreviations documented); TTLs cost expiry bookkeeping (negligible per key — millions managed routinely); unexamined equivalents cost archaeology (ownership unknown — debugging blind — hours per incident); leaks (memory growing per transient — capacity fiction); petrification (locks blocking forever — toil scheduled). Name briefly-but-clearly; expire always; pattern operations.

**Mentor note** — teach "namespace + TTL per key" (juniors expiring namespaced keys design bounded keyspaces on first hearing; bare/immortal keys interrogated ("namespace? TTL?" — two questions, seconds each, unexamined keys returned). Registry habit (keyspace maps documented — namespaces/owners/TTLs/patterns — onboarding reading maps, not archaeology). Name owners; bound lifetimes; pattern operations — namespace discipline in three habits, reviewed per keyspace.

## 2. Every structure matches its access (shapes justified per workload — fashion declined)

**Definition** — the review's second pass over Redis usage: every structure chosen for its access (counters→INCR (atomic — races eliminated); objects→hashes (field-addressed — transfer intentional); queues→lists (ordered — sequence preserved); membership→sets (duplicates impossible — O(1) lookups); rankings→zsets (order maintained — top-K constantish) — [2.1](<../2. Core structures/2.1. Core structures hash list set zset.md>) performed, [2.2](<../2. Core structures/2.2. Choosing structures by access.md>) mapped). Unmatched structures fail review (strings for counters (races scheduled); blobs for field-reads (transfer wasteful); sets for timelines (order lost); lists for membership (duplicates admitted) — fashion placed, access unexamined (mismatches scheduled per render).

**What problem it solves** — the fashion-placed structure (hashes for everything ("objects map naturally" — counters incremented via fetch-parse-store (races scheduled — HINCRBY declined where available); rankings sorted client-side (transfer full sets per top-10 — bandwidth billed per render); strings for structured data (blobs per entity — field access fetching megabytes (structures available, unapplied — memcached thinking). Access-matched structures convert fashion to fitness (patterns listed — shapes matched — transfer minimized, races eliminated, rankings native). Selection without access mapping optimizes familiarity (known structures reused — mismatches scheduled); with mapping optimizes fitness (shapes serving workloads — costs priced, surprises preempted).

**Modern guidance** — the structure review lines (review-enforced): *access listed* (reads/writes/queries per datum — patterns enumerated (wholes/partials/rankings/memberships — access mapped first); *shape matched* (counters→INCR; objects→hashes; queues→lists; membership→sets; rankings→zsets — fashion declined structurally); *memory priced* (overhead audited (MEMORY USAGE sampled — small-value tax quantified; encodings checked (listpack/embstr confirmed — compactness verified); *growth bounded* (unbounded structures bucketed/capped (streams bucketed — Domain 03; arrays capped — ceiling math ([Database Design §4.3 analogue applied — bound audits per nested structure (cap/rate/breaker — growth scheduled, never hoped). Missing mapping → request changes (fashion-placed structures returned — access demanded per structure).

**Common confusion** — *"one structure per entity (model uniformly)."* Uniformity serves simplicity (one shape per domain — developers holding one mental model — onboarding eased); access diversity demands variety (counters + profiles + rankings per user entity (three access patterns — one structure serving all three poorly (blobs for counters (races); strings for rankings (sorts per read); hashes for streams (unbounded growth). Uniform where access uniform (genuinely simple entities — single shape serving); varied where access varies (most entities — shapes per pattern, documented).

**Performance note** — structure-review economics: matched shapes perform natively (INCR atomic — races eliminated; HMGET subsets — transfer minimal; ZRANGE top-K — constantish; SADD/SISMEMBER O(1) — membership instant); mismatched shapes bill per access (blobs per field-read (transfer wasteful — bandwidth billed per field); client sorts per render (CPU linear in set size — p99 scaling with membership); application races per increment (correctness evaporating — lost updates scheduled). ## 3. Every cache has an invalidation story (staleness priced, cold starts planned — hope scheduled never)

**Definition** — the review's closing act over cached data: every cached datum arrives with its invalidation strategy (invalidate-on-write (mutations DELeting affected keys — staleness window = write-propagation latency); write-through (mutations updating cache synchronously — reads always fresh — availability coupled (priced explicitly); TTL-only (no explicit invalidation — staleness bounded by TTL alone — simplest correct where tolerance allows ([3.1](<../3. First caching/3.1. Hello caching with cache-aside.md>) performed); cold-start plan (warming/coalescing/jitter — stampedes preempted structurally); writers enumerated (application + backfill + console + future services — invalidation paths owned per writer). Unstoried caches fail review (strategies unstated — staleness hoped; writers unenumerated — coverage hoped; cold starts unplanned — stampedes scheduled).

**What problem it solves** — the storiless cache (strategies unstated (staleness unbounded — TTL-less caches fossilizing (freshness decaying silently — invalidation absent AND expiry absent — double unprotected); writers unenumerated (backfills bypassing application invalidation (stale serving for unexamined writers — coverage hoped, not enforced); cold starts unplanned (deploys flushing (restarts wiping — traffic hitting databases directly post-restart (saturation scheduled per release); synchronized TTLs expiring together (miss storms — all requests loading simultaneously (thundering herds — linear causes, exponential harms). Storied caches convert hope to procedure (strategy priced — writers enumerated — cold starts planned — staleness bounded, coverage enforced, stampedes preempted).

**Modern guidance** — the story lines per cached datum (review-enforced): *strategy* (invalidate/write-through/TTL-only — staleness priced per choice (milliseconds/zero/TTL-window — business tolerance deciding, never hope); *writers* (application + backfill + console + future enumerated (invalidation paths owned per writer — new writers inheriting invalidation duty (documented in writer onboarding — coverage enforced); *cold starts* (warming/coalescing/jitter designed (stampedes preempted structurally — deploys non-events, expiries desynchronized, misses coalesced); *TTL backing* (all strategies TTL-bounded (invalidation missed → TTL expiring (freshness bounded regardless — belt and suspenders, always). Missing story → request changes (unstoried caches failing structurally — staleness hoped, writers hoped, cold starts hoped).

**Common confusion** — *"invalidation review is premature for small caches (overhead)."* Review scales with risk (single-key session caches: strategy one line (TTL + DEL on logout — seconds); fleet caches: full stories (strategies/writers/cold-starts — minutes); unreviewed small caches grow into unreviewed large ones (sessions multiplying — TTL-less millions (leaks scheduled — small beginnings, large endings). "Overhead" framing counts review seconds while ignoring leak/staleness/stampede quarters — full ledger favors stories by orders of magnitude, permanently. Story proportionally; hope never.

**Performance note** — story economics: invalidation design costs minutes per datum (strategy priced — writers enumerated — cold starts planned); TTL backing costs nothing per mutation (expiry handling staleness — staleness bounded regardless); unstoried equivalents cost leaks (memory growing per transient — capacity fiction); fossilization (staleness unbounded — freshness decaying silently); stampedes (miss storms — connection exhaustion — thundering herds). Story minutes prevent leak/fossil/stampede quarters — invalidation ROI exceeding all other caching investments (storied caches performing boringly; unstoried performing dramatically).

**Mentor note** — teach "story per cache" (juniors narrating strategy/writers/cold-starts design storied caches on first hearing; unstoried caches interrogated ("invalidation? writers? cold starts?" — three questions, seconds each, unstoried caches returned). Story templates per cache type (session/token/catalog/leaderboard — stories pre-sketched (strategy typical, writers enumerated, cold-starts planned — templates accelerating, never replacing thought). Story caches; template types; hope never — invalidation discipline in three habits, reviewed per cached datum.
