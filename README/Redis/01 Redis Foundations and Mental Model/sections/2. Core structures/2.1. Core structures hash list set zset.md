## 1. Hashes are objects (field-level access without whole-document transfer)

**Definition** — hashes: string→field maps per key (`HSET user:1 name ann logins 0` — verified live: 2 fields; `HGETALL` reading all (verified live); `HGET`/`HMGET` reading subsets (transfer intentional — needed fields only); `HINCRBY` atomic counters per field (verified live: 0→1 server-side — races eliminated structurally). Objects without serialization (no JSON parse/stringify per access — fields addressed directly (server understanding structure — transfer minimal (requested fields, never whole documents).

**What problem it solves** — the serialized-object tax (JSON blobs per entity in strings (field reads fetching megabytes (whole-document transfer per single field — bandwidth billed per access, needed fraction unknown); read-modify-write races (fetch-parse-increment-serialize-store cycles (concurrent writers clobbering (lost updates under concurrency — races scheduled); schema-less drift (blob contents uninspectable server-side (field existence unknowable without fetching (validation hoped, TTL-per-field impossible). Hashes convert blobs to fields (server-addressed (transfer intentional); atomically incrementable (races eliminated); individually expirable? No — hashes expire per *key*, not per field (TTL granularity understood — field-lifecycle needs separate keys (design honesty, not hope).

**Modern guidance** — the hash lines per object (review-enforced — verified live shapes on Redis 8.0.2): *fields over blobs* (objects with independently-read fields → hashes (profiles/sessions/configs — field access without document transfer); *counters as fields* (`HINCRBY logins` (verified live — atomic server-side (races eliminated — application-side counting declined); *subsets read* (`HMGET` needed fields (transfer intentional — full `HGETALL` only where all fields needed (small hashes — big hashes projected); *key-scoped TTL* (hashes expiring per key (TTL granularity — field-level lifecycles needing separate keys (sessions-per-key expiring independently — design honesty). Missing field-access need → strings suffice (blobs where wholes always travel — hashes unjustified (ceremony without benefit).

```bash
# GOOD: hashes field-addressed — transfer intentional, counters atomic (verified live: 8.0.2).
$ redis-cli HSET dd:user:1 name ann logins 0   # 2 (verified — fields stored, no serialization)
$ redis-cli HINCRBY dd:user:1 logins 1         # 1 (verified — atomic server-side, races eliminated)
$ redis-cli HGETALL dd:user:1                  # name ann logins 1 (verified — fields addressed)
$ redis-cli DEL dd:user:1                      # (cleaned with siblings below — 0 residue)
```

```bash
# BAD: objects as serialized blobs — whole-document transfer per field (real failure shapes).
# SET user:1 '{"name":"ann","logins":0,...40KB of profile...}'  (field read fetching megabytes
# (HGET user:1 name impossible — blob opaque (transfer billed per field-access — needed fraction unknown).
# Increment: fetch-parse-+1-serialize-store (races under concurrency (lost updates scheduled —
# HINCRBY declined where available). TTL per field: impossible (blob expiring whole — field lifecycles
# unservable). Blobs opaque; transfer wasteful; races scheduled. Hashes field-addressed.)
```

**Common confusion** — *"hashes are just JSON with extra steps (same thing)." JSON stores *documents* (client-parsed wholes — structure invisible server-side (field access impossible — transfer whole-or-nothing; races inherent (read-modify-write cycles — concurrency unhandled); hashes store *fields* (server-addressed — partial transfer (HMGET subsets); atomic field ops (HINCRBY — races eliminated). "Same" confuses serialization format (both represent objects — superficially) with access semantics (field-addressed vs whole-fetched — structurally different (transfer/race/TTL behaviors diverging completely). Documents where wholes travel (blobs honest); hashes where fields travel independently (access intentional).

**Performance note** — hash economics: field access transfers requested fields (bytes billed per need — HMGET subsets vs HGETALL wholes — intentional per read); HINCRBY costs one round trip (vs fetch-parse-increment-store four-step races (latency quartered, correctness gained — atomicity free with the command); hash memory overhead per field (~90B+ baseline measured — tiny hashes efficient (dozens of fields — overhead negligible); giant hashes (>100 fields or MB values) reconsidered (HGETALL transfer heavy — subsets mandatory (HMGET discipline — wholes hoped never). Field-address intentionally; increment atomically; subset routinely.

**Mentor note** — teach "fields vs blobs" (juniors choosing hashes for independently-read fields design intentional transfer on first hearing; blob-defaults interrogated ("fields read separately?" — access patterns demanded per object). Demonstrate HINCRBY atomicity live once (concurrent increments without races — server-side execution tangible — fetch-increment-store races understood by contrast). Field-address intentionally; increment atomically; subset routinely — hash discipline in three habits, reviewed per object.

## 2. Lists and sets order and deduplicate (queues, timelines, membership — each shape honest)

**Definition** — lists (ordered string sequences — `LPUSH`/`RPUSH` appends (verified live: 3 elements), `LRANGE` slices (verified live: all three), `LPOP`/`BLPOP` consumption (blocking pops coordinating workers — Domain 03 owns queues fully); sets (unique unordered members — `SADD` (verified live: 2 added), `SISMEMBER` O(1) lookup (verified live: 1), `SMEMBERS`/`SINTER`/`SUNION` set algebra (membership + intersections server-side). Lists preserve order (timelines, logs, job queues — sequence meaningful); sets enforce uniqueness (tags, memberships, dedup filters — duplicates impossible structurally, never filtered hopefully).

**What problem it solves** — the shape-mismatch duo: *ordered data in sets* (timelines as sets (order lost — sorted client-side per read (sorting transfer + CPU per render — order hoped); duplicates admitted where harmful (applied-twice jobs re-queued (idempotency absent — double-processing scheduled); and *unique data in lists* (memberships as lists (duplicates accumulating (SISMEMBER-less duplicates — applied-twice processing; membership checks scanning O(N) (linear per lookup — sets serving O(1) — algorithmic mismatch billing per query). Shape honesty converts both (ordered → lists (sequence preserved); unique → sets (duplicates impossible); both → sorted sets (ordered + unique — next promise).

**Modern guidance** — the shape lines per collection (review-enforced — verified live shapes): *ordered* (timelines/logs/queues → lists (RPUSH appends, LRANGE slices, LPOP consumes — verified live pattern (3 elements, all sliced); *unique* (tags/members/filters → sets (SADD dedupes — verified live (2 added, duplicates impossible); SISMEMBER O(1) — membership checked, never scanned); *both* → sorted sets (ranked members — next promise performs); *consuming* (queue pops via LPOP/BLPOP (workers coordinating — blocking pops idling efficiently (no polling loops — Domain 03 owns queue patterns fully); *algebra where needed* (SINTER/SUNION for cohort overlaps (set math server-side — application loops declined (transfer minimal — results computed, not fetched-then-computed).

```bash
# GOOD: shapes honest — ordered lists, unique sets (verified live: 8.0.2).
$ redis-cli RPUSH dd:q:jobs a b c   # 3 (verified — ordered appends, sequence preserved)
$ redis-cli LRANGE dd:q:jobs 0 -1   # a b c (verified — slices served, order intact)
$ redis-cli SADD dd:tags red blue   # 2 (verified — uniqueness enforced on write)
$ redis-cli SISMEMBER dd:tags red   # 1 (verified — O(1) membership, never scanned)
$ redis-cli DEL dd:q:jobs dd:tags   # (cleaned with siblings — 0 residue total: 4 keys)
```

```bash
# sequence hoped). RPUSH tags red red blue (duplicates accumulating (membership unexpressible —
# applied-twice processing scheduled; checks scanning O(N) (linear per lookup — sets serving O(1)
# declined). Ordered-in-sets (sequence lost); unique-in-lists (duplicates admitted). Mismatch itemized.)
```

**Common confusion** — *"lists are queues (same thing)."* Lists are *sequences* (ordered storage — queues *implemented* with lists (LPUSH producers + BLPOP consumers — pattern atop structure); streams are *durable* queues (consumer groups, acknowledgment, history — Domain 03 owns fully (forward — unbuilt)). "Queues" describes usage (work distribution — lists serving simply (BLPOP coordination); streams serving durably (ack/history/groups). Lists for simple queues (at-most-once acceptable, history unneeded); streams for durable ones (acknowledged, replayable — Domain 03 performs). Structure vs pattern — lists store, patterns coordinate.

**Performance note** — list/set economics: LPUSH/RPUSH O(1) per element (head/tail ops — constant, never scanning); LRANGE O(N) per slice (slices bounded — pagination cursors (`LRANGE key 0 49` pages — unbounded ranges transferring megabytes (slices bounded per read); SADD/SISMEMBER O(1) average (hash-table membership — constant regardless of set size — linear scans never); SINTER/SUNION O(N×M) (set algebra server-side — large-set intersections CPU-priced (measured per hot path — application-side alternatives compared honestly). Constant ops free; slices bounded; algebra measured.

**Mentor note** — teach "ordered→lists, unique→sets, both→zsets" (juniors reciting per collection place shapes correctly on first hearing — mantra first, fluency follows — twin of "singular vs plural" naming drills, structure-flavored). Mantra memorized; shape checked; mismatch returned — collection discipline in three habits, reviewed per key.

## 3. Sorted sets rank (scores order members — leaderboards, timelines, priority queues natively)

**Definition** — sorted sets: unique members with float scores, ordered (ZADD member-score pairs (verified live: ann 100, bo 250 — 2 added); ZRANGE/ZREVRANGE by rank (verified live: bo 250 ann 100 top-2 with scores); ZSCORE/ZRANK per member (rank/score lookups O(log N)); ZRANGEBYSCORE/ZREMRANGEBYSCORE range operations (windows/trimming server-side (sliding windows, TTL-like purging by score — retention enforced structurally). Ranked uniqueness (members distinct, order total — leaderboards/timelines/priorities native (no application sorting — order maintained per write, not computed per read).

**What problem it solves** — the sort-per-read tax (leaderboards from sets/hashes (members fetched, sorted client-side per render (transfer full sets (thousands of members for top-10 (bandwidth billed per render — needed fraction unknown); CPU sorting per request (latency linear in set size — p99 scaling with membership, not with displayed rank); rank queries unanswerable efficiently ("what rank is ann?" — full sort to locate one member (O(N log N) per rank lookup — algorithmic mismatch billing per query). Sorted sets convert sorting to maintenance (order kept per write (ZADD O(log N) — reads O(log N + M) for M results — top-K constantish regardless of set size (millions of members, top-10 in microseconds — rank native, never computed).

**Modern guidance** — the ranking lines per ordered-unique collection (review-enforced — verified live shapes): *scores meaningful* (timestamps for timelines (score = epoch — recency ordered); counters for leaderboards (score = points — rank ordered); priorities for queues (score = urgency — workers popping max (ZREVRANGE + ZREM pattern or BLMOVE-class consumption — Domain 03 owns queue consumption fully); *ranges served* (top-K via ZRANGE/ZREVRANGE LIMIT (transfer bounded — full sets never fetched for leaders); windows via ZRANGEBYSCORE (sliding windows server-side — rate limiting/timelines trimmed structurally); *trims scheduled* (ZREMRANGEBYRANK/ZREMRANGEBYSCORE purging (retention enforced — unbounded growth capped (leaderboards keeping top-N (rest archived/purged — growth bounded, never hoped).

**Common confusion** — *"sorted sets are just sorted lists (same thing)."* Lists order by *insertion* (sequence preserved — positional access (index-based — rankings recomputed externally on score change (remove + reinsert (two ops — races between); sorted sets order by *score* (rank maintained — score updates repositioning atomically (ZADD existing member updates score (re-ranked server-side — single op, race-free). "Sorted" describes maintenance (score-ordered continuously — rank queries O(log N)) vs sequence (insertion-ordered — rank queries O(N log N) per computation). Rank-maintained vs sequence-preserved — different structures, different complexities, chosen per access (rank queries → zsets, always).

**Performance note** — zset economics: ZADD O(log N) per write (rank maintained — millions of members scaling logarithmically — write cost bounded); ZRANGE O(log N + M) per read (top-K constantish (M results — set size irrelevant past log factor — top-10 over billions in microseconds); ZRANK/ZSCORE O(1)-ish lookups (rank/score per member — point queries, never scans); ranges server-side (windows/trims executing without transfer — retention enforced structurally). Native ranking beats computed sorting by orders of magnitude past thousands of members — measure once, believe permanently.
