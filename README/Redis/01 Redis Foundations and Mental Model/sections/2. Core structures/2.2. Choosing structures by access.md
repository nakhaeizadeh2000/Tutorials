# 2.2. Choosing structures by access

## 1. Access decides shape (read/write/query patterns mapped — structure following workload)

**Definition** — the selection procedure: for each cached/stored datum, map its access (reads: whole or partial? (wholes → strings/blobs; partials → hashes (field-addressed); writes: increments? (counters → INCR/HINCRBY (races eliminated); appends? (streams/lists — order preserved); membership tests? (sets — O(1) lookups); rankings? (sorted sets — order maintained); queries: by key? (point lookups — any structure); by pattern? (SCAN MATCH — namespaced keys ([1.2](<../1. What Redis is/1.2. Strings keys and expiry.md>)); by rank? (ZRANGE — sorted sets only). Access mapped first (patterns listed per datum — reads/writes/queries enumerated); structure selected second (shapes matching access — fashion declined structurally, never hoped).

**What problem it solves** — the fashion-first selection (hashes for everything ("objects map naturally" — counters incremented via fetch-parse-store (races scheduled — HINCRBY declined where available); rankings sorted client-side (transfer full sets per top-10 — bandwidth billed per render); queues as pub/sub channels (history unneeded — complexity unneeded (channels without persistence — durability hoped); strings for structured data (blobs per entity — field access fetching megabytes (structures available, unapplied — memcached thinking). Access-mapped selection converts fashion to fitness (patterns listed — shapes matched — transfer minimized, races eliminated, rankings native). Selection without access mapping optimizes familiarity (known structures reused — mismatches scheduled); with mapping optimizes fitness (shapes serving workloads — costs priced, surprises preempted).

**Modern guidance** — the mapping lines per datum (review-enforced): *reads* (whole → strings (blobs honest where wholes travel); partial → hashes (field-addressed (transfer intentional); ranked → sorted sets (order maintained — top-K constantish); *writes* (increments → INCR/HINCRBY (atomic server-side — races eliminated); appends → lists/streams (order preserved — streams/queues owned by Domain 03 (forward — unbuilt)); membership → sets (duplicates impossible); *queries* (by key → any structure (point lookups universal); by rank → sorted sets only (rank queries O(log N) — unmappable elsewhere (full sorts per lookup — algorithmic mismatch); by pattern → namespaced SCAN (transfer pruned — traversal unavoidable). Missing mapping → request changes (fashion-placed structures returned — access demanded per datum).

# Counters (session logins, rate windows): INCR/HINCRBY (atomic — races eliminated — verified 1.1/2.1).
# Profiles (partial reads): hashes (HMGET subsets — transfer intentional — verified 2.1).

```

# Counters via GET+SET application-side (races scheduled — INCR available, unapplied (atomicity declined).
# Rankings via sets + client sort (transfer full sets per top-10 — bandwidth billed per render (ranked
# structures available, unused). Queues via pub/sub channels (history unneeded? unasked — durability hoped
# (channels dropping on disconnect — messages lost silently). Memberships via lists (duplicates accumulating —
# sets declined (uniqueness unenforced — applied-twice processing scheduled). Fashion placed; access unexamined.)
```

**Common confusion** — *"one structure per entity (model uniformly)."* Uniformity serves simplicity (one shape per domain — developers holding one mental model — onboarding eased); access diversity demands variety (counters + profiles + rankings per user entity (three access patterns — one structure serving all three poorly (blobs for counters (races); strings for rankings (sorts per read); hashes for streams (unbounded growth). "Uniform" confuses simplicity with fitness (cognitive ease purchased with transfer/race/rank bills — misplacement priced quarterly); varied shapes serve varied access (counters/objects/rankings each native — fitness maximal, complexity honest (three shapes documented per entity — navigable). Uniform where access uniform (genuinely simple entities — single shape serving); varied where access varies (most entities — shapes per pattern, documented).

**Performance note** — mapping economics: matched shapes perform natively (INCR atomic — races eliminated; HMGET subsets — transfer minimal; ZRANGE top-K — constantish; SADD/SISMEMBER O(1) — membership instant); mismatched shapes bill per access (blobs per field-read (transfer wasteful — bandwidth billed per field); client sorts per render (CPU linear in set size — p99 scaling with membership); application races per increment (correctness evaporating — lost updates scheduled). Match shapes (access mapped — transfer minimal, races eliminated, rankings native); mismatch never (fashion placed — bills quarterly). Access mapped; shapes matched; fashion declined.

**Mentor note** — teach "access first, shape second" (juniors listing reads/writes/queries per datum place shapes correctly on first hearing; shape-first placements interrogated ("which access?" — patterns demanded per structure). Access-mapping drills (ten data, ninety seconds each — reads/writes/queries listed, shapes placed — verdicts timed, fashion failing visibly under time pressure). Map access; match shapes; decline fashion — selection discipline in three habits, reviewed per keyspace.

## 2. Memory math per structure (overhead per key, per element, per encoding — priced before scaling)

**Definition** — the memory ledger: per-key overhead (~90B+ baseline — key names, expires, dict entries — verified live pattern below: 5-byte value occupying 64 bytes (overhead dominating small values — 13× multiple); per-element overhead (hash fields/list nodes/set members/zset skiplist nodes — encodings mattering (listpack/ziplist for small collections (verified live: hash encoding listpack — compact; embstr for short strings (verified live — small-string optimization); per-structure multipliers (small collections compact, large promoted (memory jumping at thresholds — tuning owned by Domain 06 (forward — unbuilt)); sizing math owned here (this leaf).

**What problem it solves** — the unmeasured dataset (memory sized by data bytes (10GB values → 12GB instance — overhead uncounted (per-key tax compounding (billions of tiny keys — overhead dominating (10× data-size RAM billed — capacity fiction); encoding transitions unexamined (small collections promoting at thresholds (memory jumping discontinuously — growth crossing listpack limits (surprises scheduled); replicas uncounted (primaries + followers + buffers — total arithmetic missing (single-instance sizing for replicated topology — OOM on failover (followers needing equal RAM — capacity halved silently). Measured math converts fiction to capacity (overhead audited (MEMORY USAGE sampled — small-value tax quantified); encodings checked (OBJECT ENCODING per shape — compactness verified); totals multiplied (dataset × overhead × replicas — arithmetic complete).

Missing math → request changes (capacity fiction failing structurally — OOM scheduled, eviction churning).

## 3. Wrong-structure symptoms (serialization soup, key explosions, scan storms — diagnosed with fixes)

**Definition** — the diagnostic catalog: three misplacement syndromes with signatures and cures — **serialization soup** (JSON blobs where fields travel independently (symptom: whole-document transfer per field-read (bandwidth billed per access — needed fraction unknown); fix: hashes with HMGET subsets (transfer intentional); **key explosions** (one key per micro-fact (millions of tiny keys (overhead dominating (10× multiples — capacity fiction); fix: hashes grouping related fields (hundreds of keys collapsing to dozens — overhead divided); streams/buckets for series (unbounded keys bucketed — bucket pattern analogue (growth bounded — [Database Design document bucketing](<../../../DatabaseDesign/03 Document Modeling for Scale/sections/3. Patterns and change/3.1. Schema patterns that scale.md>) linked)); **scan storms** (KEYS */pattern-less SCAN per request (O(N) traversal per render — event loop churning (latency spiking fleet-wide — full keyspaces walked per query (toil per render). Fix: namespaced SCAN MATCH ([1.2](<../1. What Redis is/1.2. Strings keys and expiry.md>) — patterns pruning transfer (traversal unavoidable, results bounded); secondary indexes as sets (query-shaped member lists — lookups O(1), never scanned).

**What problem it solves** — the misdiagnosed shape (symptoms treated as scaling problems (slow reads → bigger instances (transfer wasteful regardless of size — bandwidth billed per field-access — hardware masking structural waste (faster network serving megabytes unnecessarily — misdiagnosis priced in tiers); key explosions → more RAM (overhead structural — tax compounding per key (bigger instances postponing, never preventing — capacity fiction funded); scan storms → read replicas (scans fanning out (replicas scanning identically — load multiplied, never reduced). Shape-correct fixes convert scaling spending to remodeling minutes (hashes field-addressing (transfer minimal); keys grouped (overhead divided); patterns indexed (lookups O(1)). Diagnose shapes first (syndrome identified — fix structural); scale second (resourced bottlenecks only — hardware for genuine load).

**Modern guidance** — the diagnostic lines per symptom (review-enforced): *soup* (whole-document transfer per field (bandwidth measured — needed fraction computed (fields/total — fractions <50% migrating to hashes (transfer halved or better — migration priced once, savings per read forever); *explosions* (key counts vs overhead (MEMORY USAGE sampled — tax quantified (10× multiples triggering regrouping (hashes/buckets collapsing counts — overhead divided structurally); *storms* (SCAN frequency × keyspace size (traversal load measured — storms quantified (O(N) per render × renders/day — toil arithmetic); patterns/indexes remediating (MATCH pruning transfer (results bounded); secondary sets serving lookups (O(1) — scans eliminated). Missing diagnosis → request changes (scaling prescribed for structural problems — misdiagnosis scheduled).
