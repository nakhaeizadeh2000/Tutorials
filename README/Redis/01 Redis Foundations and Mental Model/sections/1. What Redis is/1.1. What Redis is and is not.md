# 1.1. What Redis is and is not

## 1. RAM with structures (in-memory data-structure server — speed from memory, shapes from types)

**Definition** — Redis 8.0.2 (verified live this session — standalone mode, `redisprobe`): an in-memory data-structure server — datasets living primarily in RAM (sub-millisecond access — no disk seeks on the hot path), exposed as typed structures (strings, hashes, lists, sets, sorted sets — operations per type, not bytes), with persistence as a durability adjunct (RDB snapshots + AOF logs — recovery mechanisms, not the storage engine). Speed from memory (nanosecond RAM vs millisecond disk — five orders of magnitude, structural); shapes from types (commands per structure — modeling vocabulary, not byte arrays).

**What problem it solves / history** — the database-for-everything latency floor (relational round trips + query planning + disk I/O per session-token lookup (milliseconds per request — thousands of requests amplifying to seconds of data-plane latency); memcached's typelessness (string-only values — structures serialized client-side (JSON blobs — field access requiring full fetch + parse + rewrite — read-modify-write cycles per counter increment). Redis keeps memcached's speed (RAM-resident, single-digit-millisecond p99) while adding server-side structures (INCR without fetch (verified live below — atomic increment, no round-trip assembly); hashes field-addressable (HGET without full-document transfer); sorted sets rank-aware (leaderboards without application sorting). RAM speed with structural intelligence — the combination defining the niche.

**Modern guidance** — default Redis where the workload is RAM-fittable AND latency-shaped (hot working sets fitting memory budgets (capacity math from [Database Design §5.2](<../../../../DatabaseDesign/05 Evolution Growth and Partitioning/sections/2. Growth and capacity/2.1. Capacity modeling with measured triggers.md>) applied — set size × horizon vs RAM); access needs structures (counters, rankings, memberships, queues, sessions — typed operations beating serialized blobs); durability needs are bounded (cache semantics (loss tolerable — source of truth elsewhere) or append-friendly persistence (AOF everysec — seconds of loss acceptable — Domain 04 owns persistence fully). RAM-fittable + latency-shaped + bounded-durability — all three, never one alone (huge cold datasets belong on disk; microsecond-indifferent paths belong on primary stores; loss-intolerant single copies belong on replicated databases).

```bash
# GOOD: the server introducing itself — version, mode, atomic operations (verified live: 8.0.2).
$ redis-cli INFO server | grep -E "redis_version|redis_mode"
# redis_version:8.0.2 / redis_mode:standalone (verified output — era-labeled September 2026)
$ redis-cli SET dd:probe:counter 0     # OK (verified)
$ redis-cli INCR dd:probe:counter      # 1 (verified — atomic server-side, no fetch-increment-store race)
$ redis-cli DEL dd:probe:counter       # 1 (verified — scratch cleaned, 0 residue)
# Atomicity free with every command (single-threaded execution — next promise prices it).
```

```bash
# BAD: Redis as primary database for everything (the misplacement — shapes without sizing).
# 500GB dataset on 64GB RAM (eviction churning hot keys (allkeys-lru evicting working set —
# cache hit rates collapsing — database performing as broken disk (RAM-priced, disk-behaving).
# Loss-intolerant single copies (unreplicated, unpersisted — node failure deleting primary data —
# backups absent (persistence "later" — data loss scheduled). Flat shapes in strings (JSON blobs
# per entity — field access fetching megabytes (structures declined — memcached with extra steps).
# Misplaced: oversized, unpersisted, unstructured. Size honestly; persist deliberately; structure natively.)
```

**Common confusion** — *"Redis is a cache (only)." Caching is Redis's most common *use* (volatile working sets in front of databases — [3.1](<../3. First caching/3.1. Hello caching with cache-aside.md>) performs it); structures make it a *data-structure server* (persistent queues (lists with blocking pops — job coordination); rankings (sorted sets — leaderboards native); rate limiting (sliding windows via sorted sets — algorithmic, not cached); session stores (hashes with TTL — lifecycle-managed); pub/sub + streams (messaging topologies — Domain 03 owns fully). "Only a cache" discards durable structures (persistent queues/rankings/sessions evicted as "cache" — data loss wearing terminology); cache-only thinking underuses the server by an order of magnitude. Cache often; structure always; persist deliberately (Domain 04).

**Performance note** — RAM economics: sub-millisecond p50/p99 (memory access — network-dominated latency (same-datacenter microseconds — cross-region milliseconds (locality dominating — deploy Redis beside compute, never across oceans); single-threaded commands (microseconds each — throughput ~100k+ ops/sec per instance (CPU-bound on command execution — pipelining/batching multiplying (round trips amortized — throughput scaling with batching, not threads); dataset-RAM fit governing everything (working set resident — p99 flat; exceeding RAM — eviction churning (cliffs, not slopes — capacity math from Database Design 05 applied mandatorily). RAM speed priced per GB (instance sizing); misses priced per round trip (cache misses hitting primaries — miss storms scheduled without warming ([3.1](<../3. First caching/3.1. Hello caching with cache-aside.md>)).

**Mentor note** — teach "RAM with structures" (juniors reciting both halves place Redis correctly on first hearing — memory-sized, structure-matched; RAM-only learners default to memcached thinking (strings for everything — structures unexamined); structures-only learners oversize datasets (RAM unexamined — eviction cliffs scheduled). Demonstrate INCR atomicity live once (concurrent increments without races — server-side execution tangible — fetch-increment-store races understood by contrast (application-side counting broken under concurrency — proven, not preached). Memory sized; structures matched; atomicity demonstrated.

## 2. What it buys (sub-millisecond reads, purpose-built structures, atomic operations — itemized)

**Definition** — the three purchases, each priced separately: **sub-millisecond reads** (p50/p99 microseconds-to-single-ms same-datacenter (hot paths unblocked — API latencies dominated by compute, never data-fetch); **purpose-built structures** (counters (INCR — atomic, no races); rankings (ZADD/ZRANGE — ordered sets native); membership (SISMEMBER — O(1) lookups); queues (BLPOP — blocking coordination); sessions (hashes + TTL — lifecycle-managed); **atomic operations** (single-threaded command execution — each command atomic (INCR never interleaving — no lost updates, ever (verified live pattern above); multi-key atomicity via Lua/transactions where needed (EVAL scripts executing atomically — complex invariants without distributed locks — Domain 02 owns scripting fully).

**What problem it solves** — the unpriced-adoption trio (Redis installed hopefully (latency unmeasured (p99 presuming — network topology unexamined (cross-region Redis adding milliseconds per call — locality assumed); structures unused (strings for everything (JSON blobs — field access fetching megabytes (structures available, unapplied — memcached thinking on a structure server); atomicity unexploited (fetch-increment-store races in application code (lost updates under concurrency — server-side INCR unknown (primitives unlearned). Priced adoption converts hope to engineering (latency measured per topology (p99 baselined); structures matched per access ([2.2](<../2. Core structures/2.2. Choosing structures by access.md>) performs); atomicity exploited per counter (INCR/DECR/HINCRBY replacing races structurally).

**Modern guidance** — the purchase lines per adoption (review-enforced): *latency* (p50/p99 baselined per topology (same-datacenter microseconds expected — cross-region milliseconds budgeted (locality priced — deploy beside compute); *structures* (access-matched per use case ([2.2](<../2. ## 3. What it costs (memory prices, volatility discipline, single-threaded commands — named)

**Definition** — the three costs, each named with its control: **memory prices** (RAM per GB-month (instance sizing — dataset × overhead × replicas (overhead per key ~90B+ (key names, expires, dict entries — small keys dominating overhead ratios (1KB values with 100B overhead — 10% tax (measured, never hoped); replicas multiplying (primaries + followers + persistence buffers — total RAM arithmetic); **volatility discipline** (restart behavior designed (persistence configured per durability need (RDB snapshots/AOF logs — Domain 04 owns fully — unconfigured persistence losing everything on restart (default-sans-config data loss — scheduled); **single-threaded commands** (one command at a time per instance (O(N) commands blocking all others (KEYS * on millions (seconds frozen — production stalls wearing diagnostics); slow Lua monopolizing (unbounded scripts blocking event loop — execution time bounded per script (kill-switches configured — Domain 02/06 own scripting/ops).

**What problem it solves** — the unpriced-cost trio: *memory unbudgeted* (datasets growing into eviction (maxmemory unset (OOM killer deciding retention policy (process death as eviction strategy — crashes scheduled); overhead unmeasured (small-key tax compounding (billions of tiny keys — overhead dominating (10× data-size RAM billed — capacity fiction); *volatility unplanned* (persistence unconfigured (restarts wiping datasets (deploys rebooting nodes — data loss per restart (scheduled); replicas absent (single node failing totally — durability hoped); *blocking commands unguarded* (KEYS * in production (event loop frozen seconds (all clients hanging — diagnostics DoSsing service); slow scripts unbounded (Lua monopolizing — latency cliffs official). Named costs convert surprises to budgets (memory arithmetic, persistence configured, blocking commands banned — costs priced, never hoped).

**Modern guidance** — the cost lines per adoption (review-enforced): *memory* (dataset × overhead × replicas arithmetic (per-key overhead ~90B+ measured (small values audited — key-name lengths reviewed (verbose namespaces taxing per key — brevity balanced with clarity); maxmemory set with eviction policy (eviction owned by Domain 02 (forward — unbuilt)); *volatility* (persistence configured per durability (RDB/AOF per need — Domain 04 owns fully; replicas per criticality (sentinel/cluster — Domains 04–05 own); restarts rehearsed (failover tested — durability demonstrated, not hoped); *commands* (KEYS banned in production (SCAN paginated instead — O(N) spread across calls (blocking avoided structurally); slow Lua bounded (execution timeouts configured — monopolies killed (Domain 02 scripting + 06 ops).
