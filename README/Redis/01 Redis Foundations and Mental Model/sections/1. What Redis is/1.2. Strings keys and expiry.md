# 1.2. Strings keys and expiry

## 1. Strings are the atoms (GET/SET with NX/XX/EX — conditional writes, bounded lifetimes)

**Definition** — strings: binary-safe values (text, numbers-as-text, serialized blobs — up to 512MB each, sanely kilobytes) manipulated atomically (`GET`/`SET`/`INCR`/`APPEND`/`GETRANGE` — single commands, never interleaved). Conditionals compose inline (`NX` set-if-absent (create-only — verified live below: first succeeds, second returns nil); `XX` set-if-present (update-only); `EX`/`PX` seconds/milliseconds TTL (bounded lifetime — verified live: TTL 300); `GETDEL` (read-and-delete — verified live: value returned, key gone); `MSET`/`MGET` (batch writes/reads — round trips amortized). Atoms compose (conditionals + lifetimes per write — creation/update/expiry decided per statement, never hoped).

**What problem it solves** — the read-modify-write race (check-then-set in application code (GET absent → SET (concurrent writers interleaving (both absent → both set — last-writer-wins silently (uniqueness violated — duplicate sessions/registrations scheduled); TTL forgotten (persistent keys for transient data (sessions living forever — memory leaking per login (expiry unconfigured — retention infinite by default); read-then-delete races (GET + DEL non-atomic (concurrent readers double-consuming (one-time tokens redeemed twice — exactly-once violated). Conditional + expiring + atomic reads convert all three (NX closes creation races (first-writer-wins structurally); EX bounds lifetimes (memory reclaimed structurally); GETDEL closes consume races (read-and-delete atomic — double redemption impossible).

**Modern guidance** — the string lines per key (review-enforced — verified live shapes on Redis 8.0.2): *conditional* (NX for create-only (registrations/sessions/locks — first-writer-wins (verified live: OK then nil); XX for update-only (patches requiring existence — blind writes rejected); *bounded* (EX/PX per transient key (sessions/tokens/caches — lifetimes declared at write (TTL observed (verified live: 300 — expiry visible, never hoped); *atomic reads* (GETDEL for consume-once (tokens/single-use codes — read-and-delete atomic (double redemption impossible — verified live: value returned, EXISTS 0 after); *batched* (MSET/MGET for multi-key round trips (verified live — round trips amortized (latency divided by batching). Missing conditional/expiry → request changes (unconditional writes racing; immortal transients leaking).

```bash
# GOOD: conditional writes with bounded lifetimes — races closed, lifetimes declared (verified live: 8.0.2).
$ redis-cli SET dd:u:1:session abc NX EX 300   # OK (verified — created with 300s life)
$ redis-cli SET dd:u:1:session xyz NX EX 300   # (nil) (verified — empty output (NX refused — first-writer-wins)
$ redis-cli TTL dd:u:1:session                 # 300 (verified — expiry visible, never hoped)
$ redis-cli GETDEL dd:u:1:session              # abc (verified — returned AND deleted (EXISTS 0 after))
$ redis-cli MSET dd:a 1 dd:b 2                 # OK (verified — batched writes, round trips amortized)
$ redis-cli DEL dd:a dd:b                      # 2 (verified — scratch cleaned, 0 residue)
```

```bash
# BAD: unconditional immortal strings — races open, lifetimes infinite (real failure shapes).
# SET session:abc123 <token>  (unconditional (concurrent logins overwriting (last-writer-wins silently —
# sessions hijacked by race (security incident wearing velocity); no EX (sessions immortal (memory leaking
# per login — retention infinite by default — leak scheduled). GET then DEL in application (non-atomic
# consume (concurrent readers double-redeeming (one-time tokens used twice — exactly-once violated).
# Unconditional writes racing; immortal keys leaking; non-atomic consumes doubling.)
```

**Common confusion** — *"NX is locking (distributed locks via SET NX)."* NX *creates* atomically (first-writer-wins — registration/session uniqueness — complete); *locks* need release safety (owner tokens + Lua-checked release (releasing only own lock — crash-safe expiry via EX (deadlock-free by timeout — [Domain 02](<../..>) — wait, locking patterns belong to Domain 02 (caching patterns need check-and-set)? Locking is coordination — fits Domain 03 (streams/queues/coordination)? Decide: distributed locks in Domain 03 (coordination primitives alongside queues) — hmm. Actually simplest honest placement: locks in Domain 02 (patterns using check-and-set/atomic multi-step with Lua). Record: SET NX PX + Lua release → Domain 02 (forward — unbuilt). NX alone ≠ lock (creation primitive, not mutual exclusion with fencing — conflating them builds unsafe locks (expired-holder writes continuing (fencing absent — correctness violated under pause/GC).

**Performance note** — string economics: single-command ops cost one round trip (microseconds same-datacenter — pipelined/batched (MSET/MGET — latency divided); NX/XX checks cost nothing extra (conditional evaluated server-side — no extra round trip vs plain SET (atomicity free with the command); TTLs cost expiry bookkeeping (lazy + active expiry — negligible per key — millions of TTLs managed routinely); GETDEL costs one round trip (vs GET+DEL two (race window between — atomicity halving round trips AND closing races). Conditional/bounded/atomic ops perform identically to plain ops (same round trips — guarantees free); races/leaks/doubles cost incidents (correctness quarters each). Condition always; bound always; consume atomically.

**Mentor note** — teach "NX + EX per transient creation" (juniors writing conditional bounded creates design racy-free sessions/tokens on first hearing; unconditional writes interrogated ("first-writer-wins needed?" — races demanded per key); immortal transients interrogated ("TTL?" — lifetimes demanded per transient). Demonstrate NX race live once (concurrent SET NX — exactly one OK (first-writer-wins tangible — races closed visibly — trust earned by watching serialization work, not by documentation claims). Condition creations; bound transients; consume atomically — string discipline in three habits, reviewed per key.

## 2. Keys are namespaced contracts (colons segment domains — navigable, uncolliding)

**Definition** — key namespacing: colon-delimited segments (`app:domain:id:field` — e.g., `shop:session:abc123`, `shop:user:42:cart` — domains segmenting ownership (app → entity → instance → attribute — hierarchy readable, collisions impossible by convention (segments owned per team/feature — registry documented, never hoped). Namespaces are contracts (producers and consumers agreeing key shapes — readers parsing segments (SCAN MATCH patterns per namespace — operations navigable); writers emitting conforming keys (linted/reviewed — rogue keys rejected (unparseable shapes breaking tooling — convention enforced, not hoped).

**What problem it solves** — the flat keyspace (bare keys (`session123`, `data`, `temp` — ownership unknown (whose key? — archaeology per incident (keyspace inscrutable — debugging blind); collisions scheduled (two features, one key name (last-writer-wins across domains — data corrupting silently (sessions overwriting carts — cross-domain clobbering); operations impossible (SCAN MATCH unusable (no patterns to match — keyspace unnavigable (per-key surgery requires full enumeration — toil per incident); TTL policies unassignable per domain (lifetimes uniform-or-absent — transients immortal beside permanent config (indistinguishable shapes — policy unstatable). Namespaced contracts convert flat chaos to navigable order (ownership visible, collisions structurally avoided, operations patterned).

**Modern guidance** — the naming lines per key (review-enforced): *segments* (`app:domain:id[:field]` — 3–4 segments typical (depth balanced — readability vs verbosity (verbose namespaces taxing per-key overhead (~90B+ per key measured — brevity balanced with clarity per [1.1](<1.1. What Redis is and is not.md>)); *ownership* (segments owned per team/feature (session keys → auth team; cart keys → commerce team — registry documented (owners paged per keyspace incident — responsibility assigned); *patterns* (SCAN MATCH per namespace (`shop:session:*` — operations patterned (per-namespace surgery (TTL sweeps, migrations, purges — targeted, never global); *conventions* (id formats stable (numeric vs UUID per entity — parseable (readers splitting segments reliably — format changes versioned (v2 namespaces coexisting during migration ([Database Design §5.1 analogue applied to keyspaces — expand/contract for key shapes (old + new patterns dual-read, then old dropped — witnessed).

**Common confusion** — *"namespaces waste memory (longer keys cost RAM)."* Key names stored per key (verbose namespaces taxing per-key overhead (~90B+ baseline measured — 40-char namespaces adding ~40B/key — millions of keys amplifying (gigabytes for verbosity); terse-but-clear namespaces optimizing (app:dom:id — segments abbreviated conventionally (`sess` vs `session`? — team-agreed abbreviations documented (brevity balanced with clarity — neither cryptic (`s:s:a`) nor essayed (`shop:authenticated-user-session-token-value`). "Waste" describes unexamined verbosity (essay-namespaces — overhead unmeasured); examined brevity costs nothing in clarity (conventional abbreviations — documented once, readable forever). Abbreviate conventionally; document once; measure overhead.

**Performance note** — namespace economics: key names cost bytes per key (measured overhead — verbose namespaces taxing per-key RAM (millions of keys amplifying — gigabytes for verbosity); SCAN MATCH costs O(N) per full sweep regardless (patterns filtering server-side — matched keys returned (network minimal — patterns saving transfer, not traversal (SCAN still walks all — patterns pruning results, not work); colon convention costs zero at runtime (naming only — no engine behavior (pure convention — free structurally). Name briefly-but-clearly (overhead audited); SCAN patterned (transfer pruned); convention free (naming discipline, zero runtime cost).

Name owners; pattern operations; document maps — namespace discipline in three habits, reviewed per keyspace.

## 3. Expiry is a first-class citizen (TTL on everything transient — memory reclaimed structurally)

**Definition** — expiry discipline: every transient key carrying TTL at write time (sessions/tokens/caches/locks/rate-windows — `EX`/`PX` per SET (lifetimes declared — verified live pattern above: TTL 300 observed); TTLs observable (`TTL`/`PTTL` returning seconds/milliseconds (-1 persistent (deliberate — permanence decided, never defaulted); -2 missing (expired-or-never — absence indistinguishable correctly); `PERSIST` removing TTL deliberately (transient promoted to durable — explicit act, reviewed (promotion accidental never — PERSIST in code reviewed like schema changes). Expiry structural (memory reclaimed by engine — lazy + active expiry (no sweeper jobs, no cron purges — reclamation automatic); permanence deliberate (TTL-less keys enumerated periodically (immortals audited — each justified or TTL'd — retention reviewed, never hoped).

**What problem it solves** — the immortal-transient trio: *sessions leaking* (login tokens without TTL (memory growing per authentication — leak scheduled (retention infinite by default — capacity fiction); *caches fossilizing* (entries never expiring (stale data served indefinitely (freshness decaying silently — invalidation absent AND expiry absent — double unprotected); *locks petrifying* (lock keys without TTL (crashed holders blocking forever (deadlock by omission — liveness requiring manual intervention (3 a.m. DEL commands — toil scheduled). TTL-at-write converts all three (transients dying on schedule (memory reclaimed structurally — leak impossible); caches refreshing cyclically (staleness bounded by TTL even where invalidation lags — double protection (expiry backing invalidation); locks self-releasing (crashed holders expiring (liveness automatic — manual DELs never needed).

**Modern guidance** — the expiry lines per key (review-enforced — verified live shapes): *transients TTL'd* (sessions/tokens/caches/locks/rate-windows — EX/PX at write (lifetimes declared — verified live pattern (TTL observed 300); *TTL observed* (`TTL`/`PTTL` checked in tests (lifetimes asserted — expiry verified, not hoped (test asserting TTL range post-write — discipline tested); *PERSIST deliberate* (TTL removal explicit (promotion reviewed — transients promoted deliberately (audit-logged promotions — accidental permanence impossible structurally (PERSIST absent from hot paths — grep-verified); *immortals audited* (TTL-less keys enumerated periodically (`--bigkeys`/SCAN sampling (permanence justified per key (config permanent by design (documented); data permanent by accident (TTL'd immediately — audit converting accidents to decisions). Missing TTL on transient → request changes (immortals failing review structurally — lifetimes declared, never hoped).

```bash
# GOOD: expiry structural — transients dying on schedule, permanence deliberate (verified live shapes).
# SET sess:abc token NX EX 3600 (created conditionally, living one hour — verified live pattern (NX+EX)).
# TTL sess:abc → 3599 (observed — lifetimes visible, never hoped).
# PERSIST config:theme (deliberate promotion — reviewed (transient→durable is a schema change — gated)).
# Audit: TTL-less keys enumerated quarterly (immortals justified (config by design) or TTL'd (accidents fixed).
```

```bash
# BAD: the immortal transient — lifetimes undeclared, memory leaking, locks petrifying (real shapes).
# SET sess:abc token (no EX — immortal (memory growing per login — leak scheduled (retention infinite
# by default — capacity fiction). SET lock:job42 1 (no EX — crashed holder blocking forever (deadlock
# by omission — 3 a.m. DEL commands scheduled (toil). Cache entries TTL-less (staleness unbounded —
# invalidation sole protection (single point of freshness failure — invalidation bugs serving 2019 prices).
# Immortal transients; leaking memory; petrifying locks. Expire always.)
```

**Common confusion** — *"short TTLs cause cache churn (miss storms)." Too-short TTLs churn (entries expiring before reuse (hit rates collapsing — origin load spiking per expiry wave (thundering herd on synchronized TTLs — stampedes scheduled); too-long TTLs fossilize (staleness unbounded — freshness decaying silently — invalidation sole protection (single point of failure). "Short vs long" frames false binary (TTL tuned per access pattern (hot entries long-lived (hours — churn minimal); volatile entries short (minutes — freshness bounded); stampedes prevented via jitter (randomized TTL ±10% (expiry desynchronized — herds dispersed — [3.1](<../3. First caching/3.1. Hello caching with cache-aside.md>) performs). Tune per pattern (hot/long, volatile/short); jitter always (stampedes dispersed); hope never.

**Performance note** — expiry economics: TTL bookkeeping costs negligibly per key (lazy expiry on access + active sampling (CPU background — millions of TTLs managed routinely — verified at scale industry-wide); PERSIST deliberate (promotion reviewed — accidental permanence impossible structurally); immortal audit costs SCAN samples quarterly (TTL-less enumeration — bounded, scheduled); unexpired equivalents cost leaks (memory growing per transient — capacity fiction); fossilization (staleness unbounded — freshness decaying silently); petrification (locks blocking forever — toil scheduled). Expire structurally (engine reclaiming); audit periodically (immortals justified); jitter always (herds dispersed).

**Mentor note** — teach "TTL at write time" (juniors expiring transients per SET design bounded memory on first hearing; immortal writes interrogated ("TTL?" — lifetimes demanded per transient). TTL-jitter habit (randomized expiries ±10% (herds dispersed — stampedes preempted structurally — jitter as default, synchronized expiry as incident). Demonstrate GETDEL live once (consume-once atomicity tangible — verified live pattern above (returned AND deleted — double redemption impossible — trust earned by watching atomicity work). Expire at write; jitter always; consume atomically — expiry discipline in three habits, reviewed per key.
