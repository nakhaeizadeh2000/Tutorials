# 5.1. Common interview QA Redis foundations

## 1. Strings versus hashes under pressure (access-priced, not dogmatic)

**Definition** — the question behind the question: *"store user profiles — strings or hashes?"* (the access filter). The failing answers are absolute ("hashes always — structured" — transfer unexamined (whole-hash fetches for single fields — HGETALL per name lookup (transfer wasteful — HMGET unconsidered); "strings always — simple" — blobs per entity (field access fetching megabytes — structures declined). The passing answer prices access (whole-reads → strings (blobs honest where wholes travel); partial-reads → hashes (HMGET subsets — transfer intentional); counters → INCR/HINCRBY (atomic — races eliminated). Pressure answers show judgment performing (access mapped, transfer priced, races eliminated — ninety seconds, complete).

**What problem it solves** — tool questions filter for access thinking (most candidates answer tribally ("my team used hashes" — habit reporting; "JSON is flexible" — fashion reciting (blobs unexamined — transfer/race costs unpriced). Interviewers probe placement because it reveals whether engineers *price access* (reads/writes priced per shape — engineering) or *inherit* shapes (fashion/defaults — cargo cult). Priced placements signal production judgment (transfer minimal, races eliminated — costs budgeted); inherited answers signal tutorial-following (shapes used, prices unknown — surprises scheduled). Price access; state shapes; date triggers — hired.

**Modern guidance** — the ninety-second shape: (1) examine access ("profile reads: full or partial? (full → strings (blobs honest); partial → hashes (HMGET subsets); counters present? (INCR/HINCRBY — atomic, never fetched)"); (2) price options ("strings: whole-transfer per read (bandwidth billed per access — needed fraction unknown); hashes: field-transfer (intentional — subsets served); atomic field ops (races eliminated — HINCRBY vs fetch-parse-store)"); (3) verdict with trigger ("hashes here (partial reads dominate — transfer intentional); trigger: wholes-only future → strings re-evaluated (recorded, not hoped"). Shapes examined, options priced, verdict triggered — three beats, no absolutes, no tribalism.

```bash
# GOOD (spoken, 90 seconds — priced verdict with trigger):
# "Access: profile reads partial (name/email per render — wholes unneeded); logins increment per visit.
# Options: strings-as-JSON (whole-transfer per field (bandwidth billed — needed fraction unknown);
# fetch-parse-increment races (correctness evaporating); hashes (HMGET subsets (transfer intentional —
# verified live pattern; HINCRBY atomic (races eliminated — verified live). Verdict: hashes (partial
# reads dominate — transfer intentional); trigger: wholes-only future → strings re-evaluated (dated)."
```

```bash
# BAD (spoken): the absolute — tribal, unpriced, context-free (real failure shapes).
# "Hashes — structured data goes in hashes." (Access? Unexamined (whole-reads fetching full hashes
# (transfer identical to blobs — structure without benefit); counters? Unasked (fetch-parse-store races
# scheduled — HINCRBY declined unexamined). Or: "Strings — simpler." (Partial reads fetching megabytes
# (transfer wasteful — needed fraction unknown); increments racing (correctness evaporating).
# Absolutes hire nowhere senior — access analysis hires everywhere.)
```

**Common confusion** — *"the interviewer wants a data type name."* Names without prices are guesses (correct shape, wrong reasons — unhirable reasoning with lucky verdicts); prices without names are evasion ("it depends" — verdict deferred indefinitely — analysis without decision). Name *with* prices (verdict + access-math — decisive and grounded — hirable reasoning with earned verdicts). "Hashes, because..." (verdict first, prices following — confidence with evidence); never "it depends" trailing off (evidence without verdict — analysis paralyzed). Verdicts priced; prices triggering; triggers dated.

**Performance note** — volunteer access economics unprompted ("hashes: HMGET subsets (transfer minimal — field-level reads); HINCRBY atomic (races eliminated — no application round trips wasted on lost updates); strings: whole-transfer (bandwidth per read — needed fraction billed knowingly)"). Economics with access (numbers per shape — transfer bytes, race freedom — arithmetic, not adjectives). Unvolunteered economics invites "at scale?" probing (reactive answers scoring lower). Volunteer economics; preempt probing.

**Mentor note** — drill as rapid-fire placements (ten data, ninety seconds each — shape + prices + trigger — verdicts timed, absolutes failing rounds). Speed forces internalization (access reflex, not reference — fashion failing visibly under time pressure). Tribal answers die in drills (absolutes indefensible at speed — prices demanded, verdicts timed); judgment performs (priced, triggered, dated — hired). Drill placements; require prices; date triggers.

## 2. Expiry and eviction live (TTL vs maxmemory policies — memory-safety answers)

**Definition** — the follow-up: *"how do you keep Redis from running out of memory?"* (the operations filter). The graded answer layers three defenses (TTL discipline (transients expiring at write (verified live patterns — NX+EX conditional bounded creates; TTL observed 300; GETDEL consuming atomically); eviction policies (maxmemory + policy per dataset (volatile-lru/ttl for cache workloads (transients evicted — hot data surviving; allkeys-lru where keys lack TTLs (uniform eviction — Domain 02 owns fully); monitoring (MEMORY USAGE sampled (overhead audited — small-value tax quantified); maxmemory gauges alerting (saturation visible pre-incident — eviction designed, never discovered). TTL + eviction + monitoring — defense in depth, never single point.

**What problem it solves** — memory questions filter for operations maturity (most candidates answer configurationally ("set maxmemory" — policy unexamined (eviction defaulting to noeviction (writes failing at limit — availability cliff (errors instead of eviction — misconfiguration masquerading as safety); TTLs unmentioned (transients immortal (leaks scheduled — eviction compensating for missing discipline (churn masking leaks); monitoring absent (saturation invisible — OOM killer deciding retention policy (process death as eviction strategy — crashes scheduled). Layered answers signal production judgment (TTL discipline + eviction policy + monitoring — memory safe by construction); single-knob answers signal tutorial-following (maxmemory set — policy/eviction/observability unexamined).

**Modern guidance** — the ninety-second shape: (1) TTL discipline ("transients expiring at write (verified live patterns — NX+EX creates, TTL observed, GETDEL consuming — lifetimes declared, never hoped); (2) eviction policy ("maxmemory + volatile-lru/ttl for cache workloads (transients evicted — hot data surviving); allkeys-lru where TTLs absent (uniform eviction — Domain 02 owns fully); noeviction never for caches (writes failing at limit — availability cliff — misconfiguration declined structurally)"); (3) monitoring ("MEMORY USAGE sampled (overhead audited — verified live: 64B/embstr/listpack); maxmemory gauges alerting (saturation visible pre-incident — eviction designed, never discovered). TTL + policy + monitoring — memory safe by construction, never by default.

```bash
# GOOD (spoken, 90 seconds — layered defenses, all evidenced):
# "TTL discipline first (transients expiring at write — verified live patterns (NX+EX, TTL observed,
# GETDEL consuming — lifetimes declared). Eviction policy: maxmemory + volatile-lru (transients evicted —
# hot data surviving; Domain 02 owns policy selection fully). Monitoring: MEMORY USAGE sampled (overhead
# audited — verified live: 64B/embstr); maxmemory gauges alerting (saturation visible pre-incident).
# Layered: TTL (prevention) + eviction (backstop) + monitoring (visibility). Memory safe by construction."
```

```bash
# BAD (spoken): the single knob — maxmemory set, discipline absent (real failure shapes).
# "Set maxmemory." (TTL discipline? Unmentioned (transients immortal — leaks scheduled (eviction compensating
# for missing discipline — churn masking leaks). Policy? Unstated (default noeviction (writes failing at limit —
# availability cliff — misconfiguration masquerading as safety). Monitoring? Absent (saturation invisible —
# OOM killer deciding retention policy (process death as eviction strategy — crashes scheduled). Single knob;
# triple absence. Memory hoped; OOM scheduled.)
```

**Common confusion** — *"eviction loses data (dangerous by definition)."* Eviction discards *regenerable* data (cache entries rebuildable from primaries (miss cost bounded — recomputation priced (TTL windows refilling — availability preserved); volatile-* policies evicting expirable keys first (hot data surviving — working set protected structurally). "Loses data" describes unreplicated primaries (eviction destroying single copies — misconfiguration (volatile data on noeviction-less stores without persistence — architecture wrong, not eviction). Cache entries evictable by definition (rebuildable — miss-bounded); primary data never evicted (persisted/replicated — durability designed). Evict caches (regenerable); persist primaries (irreplaceable) — confuse never.

**Performance note** — volunteer memory economics ("TTL discipline preventing most evictions (transients expiring — working set self-maintaining); volatile-lru evicting coldest transients first (hot data surviving — hit rates preserved); monitoring catching saturation pre-incident (gauges firing — eviction designed, never discovered)"). Economics with layers (discipline + policy + monitoring — defense in depth, never single point). Unvolunteered economics invites "at scale?" probing (reactive answers scoring lower). Volunteer economics; preempt probing.

**Mentor note** — drill memory-safety Q&A (ten scenarios, ninety seconds each — immortal sessions, unconfigured eviction, unmonitored saturation — verdicts timed, layers stated, policies named). Speed forces internalization (TTL/policy/monitoring reflex — fashion failing visibly under time pressure). Layered answers perform (discipline + policy + monitoring — memory safe by construction); single-knob answers fail (maxmemory set — discipline/policy/monitoring absent). Drill scenarios; demand layers; name policies.

## 3. Design a cache live (keys, structures, invalidation — narrated out loud, priced throughout)

**Definition** — the closer: *"design sessions caching for X users"* (the synthesis exercise). The graded performance narrates keys → structures → invalidation live (keys namespaced (`shop:session:{id}` — ownership visible — [1.2](<../1. What Redis is/1.2. Strings keys and expiry.md>) performed); structures matched (sessions as hashes-or-strings per access (partial reads → hashes (HMGET subsets); whole reads → strings (blobs honest); TTL bounded (EX at write — lifetimes declared); invalidation named (logout DEL + TTL backing (staleness bounded doubly — explicit + temporal); cold starts planned (warming/coalescing/jitter — stampedes preempted). Narrated continuously (thinking aloud — decisions audible, always); priced throughout (transfer/overhead/staleness numbers per choice — arithmetic, not adjectives).

**What problem it solves** — cache-design questions filter for integrated judgment (most candidates answer partially (keys unnamespaced (ownership unknown — collisions scheduled); structures unexamined (blobs defaulted — transfer unpriced); TTL unstated (lifetimes hoped — leaks scheduled); invalidation absent (staleness unbounded — freshness decaying silently); cold starts unplanned (stampedes scheduled — deploys flushing). Interviewers listen for completeness (keys + structures + TTL + invalidation + cold starts — all five stated — production caches designed, not sketched); prices per choice (transfer/overhead/staleness numbers — arithmetic evidencing judgment). Partial answers hire juniors (shapes named); complete answers hire seniors (systems priced — incidents preempted structurally).

**Modern guidance** — the five-minute shape: (1) *keys* (1 min — namespaced (`shop:session:{id}` — ownership visible ([1.2](<../1. What Redis is/1.2. Strings keys and expiry.md>)); (2) *structures* (1 min — hashes-or-strings per access (partial reads → hashes (HMGET subsets — transfer intentional); session counters via HINCRBY (atomic — races eliminated); (3) *TTL* (1 min — EX at write (lifetimes declared — verified live pattern (TTL observed); (4) *invalidation* (1 min — logout DEL + TTL backing (staleness bounded doubly — writers enumerated (application + backfill + console); (5) *cold starts* (1 min — warming + coalescing + jitter (stampedes preempted — deploys non-events). Narrated continuously (decisions audible); priced throughout (numbers per choice — transfer/overhead/staleness arithmetic).
