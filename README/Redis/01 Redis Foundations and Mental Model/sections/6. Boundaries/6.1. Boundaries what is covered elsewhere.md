**Definition** — outward boundary (unchanged across all boundaries in this repo — patterns consume shapes, never define them): how code *talks to* cached shapes — client wrappers, repository caching decorators, cache-aside helpers, invalidation middleware — is owned elsewhere and never re-taught here ([DesignPatterns 06](<../../../../DesignPatterns/06 Modern Patterns and Anti-Patterns/README.md>) — repository seam, pub-sub consumption; ORM track — repository patterns consuming ([ORM 01 §2.2](<../../../../ORM/01 Data Access Foundations and Mental Model/sections/2. Influence flows one way: caching decisions constrain code structure, never the reverse — same rule as relational/document/ORM tracks, sixth restatement across the repo, final at track scale here.

**What problem it solves** — consumer-first caching ("how will the ORM cache this?" — mapper caching decorators dictating key shapes (TTL policies following framework defaults — lifetimes unexamined); "which client wrapper?" — wrapper APIs dictating command patterns (pipelining unexamined — round trips multiplying); "cache-aside helper library X" — helper opinions dictating invalidation (strategies unchosen — staleness hoped). Consumers serve shapes; shapes serve workloads — inverting the dependency caches for tools, not for access (framework upgrades reshaping keyspaces; wrapper migrations redefining TTLs; helper adoptions inheriting staleness policies). Decide shapes here (workload-derived, gauge-serving, bounded); map them there (adapters absorb tool friction — friction is information, not a veto).
