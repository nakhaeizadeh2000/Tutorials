# 2.1. Consumer groups

## 1. Groups partition deliveries (XREADGROUP per consumer — each entry to exactly one member, PEL tracking)

**Definition** — consumer groups: named reader sets over a stream (XGROUP CREATE dd:pp dd:g1 0 MKSTREAM — verified live: OK (group `g1` from ID 0 (full history — new groups reading everything (onboarding complete, never partial); MKSTREAM creating empty streams (groups before producers — ordering decoupled (consumers ready pre-traffic); XREADGROUP GROUP dd:g1 dd:c1 COUNT 2 STREAMS dd:pp `>` — verified live: both entries delivered to c1 (`>` = undelivered only (each entry to exactly one member — parallelism safe (no two consumers processing same entry — coordination server-side, never hoped); PEL tracking (pending-entries list per group (delivered-unacked entries recorded (work-in-flight visible — crashes surfacing structurally, never silently).

**What problem it solves** — the uncoordinated-consumption trio: *competing pops racing* (BLPOP parallelism unpartitioned (same entry popped once — safe but unscalable (one slow consumer blocking all (head-of-line coupling — throughput hoped); *deliveries untracked* (reads unrecorded (crashes losing work silently (in-flight invisible — losses discovered by customers (visibility absent); *replays unowned* (popped entries gone (new members starting empty (history absent — scaling resetting progress (growth punishing). Partitioned groups convert racing to division (entries divided (each to one member — parallelism coordinated); PEL tracking (in-flight visible — crashes surfacing); history retained (members joining anytime — progress preserved).

**Modern guidance** — the group lines per stream (review-enforced — verified live shapes on Redis 8.0.2): *groups per consumer class* (orders-group, notifications-group (independent positions (classes progressing separately — coupling absent (one class stalling never blocking others); *`>` for new work* (undelivered only (each entry once per group — partitioning structural (duplicates across members impossible — coordination server-side); *COUNT bounding* (batch sizes capped (transfer bounded — members processing pages (memory protected — sizes stated, never hoped); *explicit IDs for history* (ranges instead of `>` (replays reading delivered entries (backfills natural — onboarding complete).

**Common confusion** — *"consumer groups load-balance like round-robin (equal shares)."* Groups deliver on demand (members requesting via XREADGROUP (fast members pulling more (shares proportional to speed — fast consumers processing many (slow consumers few — balance emergent, never equal); idle members receiving nothing (no pushing — pulls only (work following capacity — backpressure natural (slow members unburdened — overload impossible structurally); crashed members holding PEL (entries pending — claimed per promise 3 (work reassigned — stalls temporary, never permanent). "Round-robin" describes pushing (equal shares — capacity ignored); groups pulling (shares following speed — backpressure structural). Pull scales (demand-driven — capacity honored); push never (shares equal — slow members drowning).

## 2. ACK completes explicitly (XACK per processed ID — unacked entries visible in XPENDING, never silently lost)

**Definition** — explicit completion: XACK dd:pp dd:g1 <id> per processed entry (verified live: acking first ID returning 1 (completion recorded — PEL entry clearing (work finished — visibility updated); unacked entries persisting (XPENDING listing (verified live shape: pending count per consumer (work-in-flight visible — crashes surfacing (unacked entries naming their holders — responsibility explicit); no auto-ack (delivery ≠ completion (members crashing post-delivery holding PEL (redelivery managed — promise 3 performing (losses impossible — stalls temporary). Completion explicit (processed → acked — states named); delivery provisional (received → pending — work tracked).

**What problem it solves** — the assumed-completion trio: *delivery equaling done* (members processing-then-acking reversed (acks before work (crashes losing processed-unacked... acked-unprocessed work (losses silent — completion hoped (delivery mistaken for durability); *unacked invisible* (PEL unmonitored (stalls accumulating (crashed members holding entries forever (work stuck — visibility absent (losses-by-stall scheduled); *no completion contract* (handlers exiting without acking (entries pending indefinitely (PEL growing — redelivery never triggering (work abandoned — completion unowned). Explicit ACKs convert delivery to completion (processed → acked (states named — crashes redelivering (losses impossible); PEL monitored (stalls visible — claims triggering (work reassigned).

**Modern guidance** — the completion lines per consumer (review-enforced): *process-then-ack* (work before XACK (crashes redelivering (losses impossible — duplicates absorbed ([2.2](<../../sections/2. Reliable consumption/2.2. Delivery semantics and idempotency.md>) — order: process, then complete, never reverse); *ack per ID* (entries completed individually (partial batches acking processed subset (granularity exact — crashes reprocessing only unacked (waste minimal — completion precise); *PEL monitored* (XPENDING gauged (verified live shape — pending per consumer (stalls alerting (idle thresholds breaching — claims triggering (visibility pre-incident); *unacked bounded* (PEL ceilings alerting (growth investigating — members stalled or producers surging (causes distinguished — fixes placed).

```bash

# [process entry fully] → XACK dd:pp dd:g1 1791027335340-0 → 1 (verified live — completion recorded)
# XPENDING dd:pp dd:g1 → 1 remaining (verified live shape — in-flight visible, crashes surfacing)
# PEL gauged per consumer (stalls alerting — idle thresholds breaching — claims triggering per promise 3)
```

```bash

# XACK before processing (crashes losing acked-unprocessed work (losses silent — delivery mistaken durability).
# PEL unmonitored (stalls accumulating — crashed members holding entries forever (work stuck — visibility absent).
# Handlers exiting unacked (PEL growing — redelivery never triggering — work abandoned). Process, then ack.)
```

**Common confusion** — *"acking in batches is unsafe (only per-entry acks are correct)."* Batch ACKs completing processed subsets (XACK multi-ID (processed entries acking together — granularity per batch (crashes reprocessing unacked remainder (waste bounded by batch — correctness preserved (processed acked, unprocessed pending — states exact); per-entry ACKs taxing throughput (command per entry (RTTs multiplying — completion priced per message (pipelining mitigating — cost real, benefit zero where batches atomic); unsafe acking pre-work (order reversed — crashes losing (unsafety in ordering, never batching). "Unsafe" describes ack-before-process (ordering violated — losses silent); batch-after-process safe (granularity coarser — correctness identical). Order correctly (process-then-ack — always); batch freely (granularity — per throughput needs).

**Performance note** — ACK economics: XACK costs a command per call (batched multi-ID — RTTs amortized (throughput taxed lightly); PEL entries cost RAM while pending (in-flight stored — cleared on ack (memory transient — stalls accumulating; monitored per promise); process-then-ack costs redelivery on crash (duplicates absorbed ([2.2](<../../sections/2. Reliable consumption/2.2. Delivery semantics and idempotency.md>) — correctness priced in idempotency); ack-before-process costs silent losses (price unbounded — customers discovering). Ack after (losses impossible — duplicates absorbed); monitor PEL (stalls visible — claims triggering).

Demonstrate XPENDING before/after once (2→1 — verified live pattern above (tangibility converting permanently — completion concrete, never claimed). ## 3. Claim the stalled (XCLAIM/XAUTOCLAIM on idle — crashed consumers' entries reassigned, liveness preserved)

**Definition** — stall recovery: entries pending beyond idle thresholds reassigned (XCLAIM dd:pp dd:g1 dd:c2 <min-idle-ms> <ids> — explicit IDs claimed (crashed members' work moving (ownership transferring — liveness preserved (stalls temporary — progress resuming); XAUTOCLAIM dd:pp dd:g1 dd:c2 0 0-0 COUNT 10 — verified live: remaining entry claimed to c2 (cursor-scanning PEL (0-0 start — idle threshold 0 (all eligible — production thresholds minutes (crashes distinguished from slowness — patience priced); cursor returned (scans paging (PEL large — claims iterating (completeness guaranteed — entries unskipped structurally).
