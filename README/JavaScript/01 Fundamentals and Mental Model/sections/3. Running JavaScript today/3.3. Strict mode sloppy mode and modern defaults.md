## 3.3. Strict mode (sloppy-mode legacy, opt-in rules, and modern defaults)

### 1) **Strict mode removes footguns**

**Definition** — strict mode is an ES5 opt-in execution mode that turns several silent failures into errors and closes accidental-global leaks.

What changes under strict mode:

| Sloppy behavior | Strict behavior |
|-----------------|-----------------|
| Assignment to undeclared name creates a global | Throws `ReferenceError` |
| Writes to non-writable properties silently fail | Throws `TypeError` |
| `this === undefined` coerces to global object in bare calls | Stays `undefined` |
| Duplicate parameter names allowed | SyntaxError |
| `delete someVar` silently fails | Throws `SyntaxError` |
| Octal literals `010` allowed | SyntaxError |

### 2) **It's an opt-in pragma — except it isn't anymore**

Classic opt-in: `'use strict';` as the first statement of a script or function body. But two modern constructs are **always strict regardless**:

- ES modules (including `<script type="module">`)
- Class bodies (all code inside a class)

So contemporary defaults make most newly written code strict without any pragma:

```js
"use strict";
function sloppyVsStrict() {
  // this function inherits script-level strictness
  leaked = 42; // ReferenceError instead of creating a global
}
try {
  sloppyVsStrict();
} catch (e) {
  console.log(e.name); // ReferenceError
}
```

### 3) **Sloppy mode exists only for legacy pages**

- Billions of old pages depend on sloppy semantics — removal is impossible (web compat law, see [1.1](<../1. What JavaScript is/1.1. From LiveScript to ECMAScript history editions and legacy quirks.md>)).
- You will still meet sloppy code: ancient scripts, third-party tags, dynamically evaluated strings without their own pragma.
- **Modern guidance**: never write new sloppy code. Enforce via lint rules (`strict`, `no-implicit-globals`) or simply use modules everywhere.

### 4) **Common confusion**

- The pragma must be a *directive prologue*: comments may precede it, any real statement voids it.
- It applies per script/function scope — a sloppy outer script can contain strict functions and vice versa; `eval` strings have their own rules.
- "Strict mode is faster" — historically marginally true (fewer dynamic cases); today choose it for correctness, not speed.

### 5) **Mentor note**

When reviewing legacy bugs, ask early: "was this running strict?" The implicit-global bug and the wrong-`this` bug produce *different symptoms* across modes — knowing the mode halves debugging time. In teaching repos, set `"type": "module"` from day zero and never mention the pragma again.
