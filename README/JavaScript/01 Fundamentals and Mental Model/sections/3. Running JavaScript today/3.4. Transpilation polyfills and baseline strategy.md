## 3.4. Transpilation, polyfills, and baseline strategy

### 1) **Transpilers rewrite newer syntax down**

**Definition** — a transpiler (Babel, SWC, esbuild) reads modern JavaScript and emits equivalent code for older engines:

```js
// Source (ES2020-era syntax):
const first = users?.[0] ?? null;

// Emitted for an older target (conceptually):
var _users;
var first = ((_users = users) === null || _users === void 0 ? void 0 : _users[0]) !== null && _users !== undefined ? _users[0] : null;
```

- Syntax transforms are mechanical and safe-ish; they also generate **source maps** so stack traces point back to your real code.
- Class fields, generators, async functions on ancient targets need *runtime helpers* too (`regenerator-runtime` etc.) — transpilation alone is not always enough.

### 2) **Polyfills add missing built-ins at runtime**

- A polyfill detects a missing global/method and installs its own implementation (`core-js` is the standard suite):

```js
// Guarded hand-rolled polyfill shape:
if (!Array.prototype.at) {
  Object.defineProperty(Array.prototype, "at", {
    value: function at(index) {
      const i = index < 0 ? this.length + index : index;
      return i >= 0 && i < this.length ? this[i] : undefined;
    },
    writable: true, configurable: true,
  });
}
console.log([10, 20].at(-1)); // 20
```

- **Risk**: emulation may diverge from native (edge cases, performance). Prefer guarded, minimal polyfills over blanket imports; prefer *not needing them at all*.

### 3) **Define a support matrix first**

Decide targets explicitly before choosing tooling:

| Audience | Sensible strategy |
|----------|-------------------|
| Server-side on Node LTS | No transpile/polyfill — use the runtime's native support |
| Internal tool / admin UI | Modern evergreen browsers only — ship native ESM |
| Public web app | Define Baseline-style targets; transpile + polyfill to the floor |

- The web-platform **Baseline** project labels features "newly available" or "widely available" across evergreen browsers — a defensible default policy.
- **Modern guidance**: check your matrix against MDN/caniuse per feature ([1.3](<../1. What JavaScript is/1.3. The TC39 process stages and how to read MDN vs the spec.md>)); revisit the floor when you bump it — every supported legacy target costs bundle size and speed forever.

### 4) **Common confusion**

- "Babel handles everything new" — Babel transforms *syntax*; missing *built-ins* need polyfills, and some semantics (e.g., subclassable built-ins on old engines) can't be faithfully emulated.
- "Polyfill == shim == ponyfill" — polyfill installs globally if missing; ponyfill never touches globals (importable pure functions); shim patches regardless.
- Transpiling for Node server code — usually waste; upgrade the runtime instead.

### 5) **Performance note**

Every downleveled feature ships more bytes and slower code to everyone — including users with capable browsers. Measure bundle impact; consider differential serving or dropping the legacy target outright.

### 6) **Mentor note**

Review question: "what is our minimum supported engine and where is it written?" If no one can answer without archaeology, build steps have grown by inertia. Record the decision next to the build config, not in tribal memory.
