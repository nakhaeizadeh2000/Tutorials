## 1.3. The TC39 process and reading documentation (stages 0–4, MDN vs the specification)

### 1) **Five stages gate every feature**

**Definition** — TC39 is the committee that evolves ECMAScript. Every proposal climbs numbered stages; each stage means a concrete commitment:

| Stage | Name | Meaning |
|-------|------|---------|
| 0 | Strawman | An idea someone brought — expect nothing |
| 1 | Proposal | Problem + shape accepted; APIs may still change |
| 2 | Draft | Spec text exists; details settling |
| 3 | Candidate | Design complete; waiting on implementation/test262 feedback — **may still change or die** |
| 4 | Finished | Merged into the next annual edition |

- Editions are snapshots each June: whatever reached stage 4 ships in that year's spec (ES2026 ratified June 30, 2026 — its headline addition is Temporal).

### 2) **Ratified ≠ available**

- Stage 4/spec inclusion is a *paper* event. Engines then ship implementations on their own schedules — sometimes behind flags, sometimes months later.
- Example (ES2026 era): Temporal is in the spec, but browser/runtime rollout is uneven — production use needs a support check (or the official polyfill).

```js
// Feature-detect instead of assuming:
if (typeof Array.prototype.findLast === "function") {
  // ES2023 method — safe here
  console.log([1, 2, 3].findLast(x => x > 1)); // 3
} else {
  console.log("fallback path");
}

// Guarding an entire bleeding-edge global (Temporal):
const hasTemporal = typeof globalThis.Temporal !== "undefined";
console.log(hasTemporal);
```

- **Modern guidance**: stage 3 = experiment in prototypes; stage 4 + your support matrix green = production. Check MDN compat tables / caniuse, never user-agent sniffing.

### 3) **MDN for daily use, spec for truth**

- **MDN Web Docs**: readable explanations, runnable examples, browser-compat tables — your default reference.
- **ECMA-262**: the normative text. Written as precise abstract algorithms ("Return ? ToNumber(value)") — unreadable for browsing, indispensable for resolving *disputes* about edge-case semantics.
- **test262**: the official conformance test suite; what "implemented correctly" measurably means.
- Proposal READMEs (tc39/proposal-* repos) are the best source while a feature moves through stages.

### 4) **Common confusion**

- "It's stage 3, let's use it" — stage 3 has died before; design changes at 3 have happened. Treat it as beta.
- "Polyfill makes it identical" — polyfills emulate observable behavior, often imperfectly (performance and edge cases differ).
- Reading the spec top-to-bottom to learn — wrong tool; learn from tutorials/MDN, consult the spec surgically.

### 5) **Mentor note**

Train the habit: every time someone proposes a shiny API in review, ask "which stage?" and "what's our minimum supported runtime?" If both answers aren't crisp, the feature is a future option, not a plan.
