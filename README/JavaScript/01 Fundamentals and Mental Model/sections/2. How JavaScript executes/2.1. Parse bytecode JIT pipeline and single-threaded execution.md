## 2.1. Parse → bytecode → JIT pipeline (and single-threaded execution)

### 1) **Source becomes AST, then bytecode, then optimized machine code**

**Definition** — engines execute your code in tiers:

1. **Parse** — source text → Abstract Syntax Tree (syntax errors are thrown here, before anything runs).
2. **Interpret** — the AST compiles to bytecode fast; an interpreter runs it (V8's tier is called Ignition).
3. **Profile + optimize** — hot functions are recompiled to machine code under assumptions gathered while profiling (V8: Sparkplug → Maglev → TurboFan).
4. **Deoptimize** — when an assumption breaks (e.g., a function always saw objects of one shape and suddenly gets another), execution falls back to slower tiers and may re-optimize later.

```js
// Shape stability matters to the optimizing compiler:
function totalX(points) {
  let sum = 0;
  for (const p of points) sum += p.x;
  return sum;
}

const mono = [{ x: 1 }, { x: 2 }, { x: 3 }];      // one shape: { x }
const poly = [{ x: 1 }, { y: 9, x: 2 }, { x: 3 }]; // mixed shapes
// Same result...
console.log(totalX(mono), totalX(poly)); // 6 6
// ...but `mono` stays optimized; `poly` risks deopt/reopt churn in hot paths.
```

- **Performance note**: this is why "add properties in consistent order, keep object shapes stable" is real advice for hot paths — not folklore. Measure before/after with realistic data volumes; micro-benchmarks lie.

### 2) **One thread runs your code per realm**

- All your synchronous JS executes on **one thread** (per agent/realm). Two functions can never interleave mid-execution.
- Concurrency exists, but at the host level: the event loop interleaves tasks, platform threads perform I/O behind the scenes, and Workers give you separate threads with no shared mutable state.
- Practical consequence: CPU-heavy loops block everything else on that thread — responsiveness depends on yielding control back to the loop.

### 3) **Optimization is heuristic — measure, don't guess**

- Engines differ in tier names and heuristics (SpiderMonkey: Baseline/Warp; JSC: LLInt/DFG/FTL), so micro-level claims ("inline caching makes X faster") must be verified on *your* target engine and version.
- Startup vs steady-state: interpreters start fast, optimizers need warmup — short scripts may never benefit from the JIT at all.
- **Modern guidance**: write boring, predictable code; reach for Workers/streaming only after profiling shows actual pressure.

### 4) **Common confusion**

- "JavaScript is interpreted" — outdated half-truth; every mainstream engine JIT-compiles.
- "`async` makes my function run on another thread" — no; it schedules continuations on the *same* thread's queues (see the event-loop leaf next).
- Syntax errors appear at parse time, but many type errors appear whenever the offending line first executes — dynamic dispatch means failures are temporal, not structural.

### 5) **Mentor note**

Draw the pipeline once, then connect every later performance discussion to it: closures/shapes → inline caches; polymorphic call sites → deopts; big sync loops → blocked event loop. Students who own this model stop cargo-culting performance tips.
