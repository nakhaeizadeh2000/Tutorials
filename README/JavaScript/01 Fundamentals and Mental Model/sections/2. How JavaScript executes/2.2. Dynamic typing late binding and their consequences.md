## 2.2. Dynamic typing and late binding (what they cost and buy you)

### 1) **Types live on values, not variables**

**Definition** — JavaScript is *dynamically typed*: variables are just named bindings; every value carries its own type at runtime, and a binding can reference different types over time.

```js
let x = 42;        // number value
console.log(x);    // 42

x = "now a string"; // perfectly legal — the binding is untyped
console.log(x.toUpperCase()); // NOW A STRING

function len(thing) { // works with ANY value that has .length (duck typing)
  return thing.length;
}
console.log(len("abc"), len([1, 2, 3])); // 3 3
```

- The `len` function never asked "are you a string?" — structural capability is all that matters at call time.

### 2) **Late binding defers lookup to call time**

Method resolution happens when the call executes, through the object itself:

```js
const reader = { format: () => "v1" };
console.log(reader.format()); // v1

reader.format = () => "v2";   // rebinding the property changes behavior...
console.log(reader.format()); // v2
// ...even for code written before the change. This is "monkey patching".
```

- **What it buys**: plugins, mocks in tests, extending objects you don't own.
- **What it costs**: any code between definition and call may have swapped the method — behavior becomes temporal, and refactoring tools can't statically guarantee calls.

### 3) **The bill arrives at runtime**

Because nothing validates types ahead of execution:

```js
function total(items) {
  return items.map(i => i.price).reduce((a, b) => a + b, 0);
}
total([{ price: 10 }, {}]); // TypeError: i.price is undefined → NaN? No:
// reduce gets NaN only if price were NaN; here i.price is undefined →
// 10 + undefined = NaN silently! The bug surfaces later, far from the cause.
```

- **Modern guidance** — compensate deliberately, don't hope:
  - Validate at boundaries (API/IO edges), trust inside.
  - Lint (`no-implicit-any`-style rules where tooling allows) and type-check via JSDoc or TypeScript (separate track).
  - Tests execute the paths static analysis cannot see.

### 4) **Common confusion**

- "Dynamic = weak" — two different axes: JS is dynamically typed AND weakly coerced (`"3" + 1`). Coercion mechanics get their own domain (Values, Types, and Coercion).
- "`typeof` protects me" — it tells you what a value is now, not whether your logic assumed correctly.

### 5) **Performance note**

Unpredictable types keep JIT optimizations from sticking (polymorphic sites deopt). Stable shapes and consistent types per call site are performance advice *because* of this model — see [2.1](<2.1. Parse bytecode JIT pipeline and single-threaded execution.md>).

### 6) **Mentor note**

Review checklist item: "where does data enter this module, and who validates it?" If the answer is nowhere/nobody, flag it — dynamic typing makes boundary validation non-negotiable, not optional polish.
