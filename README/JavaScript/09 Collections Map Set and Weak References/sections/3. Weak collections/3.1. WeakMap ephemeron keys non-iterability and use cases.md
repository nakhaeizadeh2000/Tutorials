## 3.1. WeakMap ephemeron keys non-iterability and use cases

### 1) **Object-only keys and ephemeron lifetime**

**Definition** — `WeakMap` maps *object* keys → arbitrary values with ephemeron semantics: if the key object is unreachable elsewhere, the entry does not keep it alive and disappears after GC. Keys must be objects (or non-registered symbols? — no, only objects/functions; primitives throw). No `size`, no iteration, no `clear` (observable enumeration would expose GC timing).

```js
// Only objects as keys — primitives throw
const wm = new WeakMap();
const key = { id: 1 };
wm.set(key, "value");
console.log(wm.get(key)); // 'value'
console.log(wm.has(key)); // true
try { wm.set("string", 1); } catch (e) { console.log(e.name); } // TypeError

// Primitives, including symbols, are not allowed as keys (symbol is primitive)
try { wm.set(Symbol("s"), 1); } catch (e) { console.log(e.name); } // TypeError

// Non-iterability is intentional — no size, no keys/values/entries, no clear, no for-of
console.log(typeof wm.size); // undefined
console.log(typeof wm[Symbol.iterator]); // undefined
try { for (const x of wm) {} } catch (e) { console.log(e.name); } // TypeError

// Ephemeron: when key dies, entry vanishes (GC non-deterministic — demo is structural, not timing-asserted)
let obj = { data: "payload" };
wm.set(obj, { computed: 42 });
console.log(wm.has(obj)); // true
// Drop the only strong reference to obj — now only WeakMap holds a weak reference
obj = null;
// At some future GC, the entry will disappear — you cannot assert when (see 4.1/4.2)
// Correct mental model: WeakMap does NOT prevent GC of its keys
```

- *History* — added in ES2015 for private state and object-keyed caches without leaks; `size`/iteration deliberately omitted to avoid leaking GC nondeterminism into observable semantics.

### 2) **No stringification, no enumeration, no leak**

```js
// No stringification — distinct objects stay distinct (unlike plain object)
const wm2 = new WeakMap();
const k1 = {};
const k2 = {};
wm2.set(k1, "k1");
wm2.set(k2, "k2");
console.log(wm2.get(k1), wm2.get(k2)); // 'k1' 'k2'

// Plain object collapses — WeakMap/Mapprecisely fixes this without leaking
const plain = {};
plain[k1] = "k1";
plain[k2] = "k2";
console.log(plain[k1], plain["[object Object]"]); // 'k2' 'k2' — one string key

// No enumeration means GC can reclaim without your code holding it alive via iteration snapshot
// Contrast Map: holds keys strongly — unbounded Map cache leaks
// (see incident in 7.1 — unbounded Map vs WeakMap)
function strongCache() {
  const cache = new Map();
  return key => {
    if (!cache.has(key)) cache.set(key, { computed: Math.random() });
    return cache.get(key);
  };
}
function weakCache() {
  const cache = new WeakMap();
  return key => {
    if (typeof key !== "object" || key === null) throw new TypeError("WeakMap key must be object");
    if (!cache.has(key)) cache.set(key, { computed: Math.random() });
    return cache.get(key);
  };
}
console.log(typeof strongCache, typeof weakCache); // function function — both memoize, but Map pins every key forever

// has/get/set/delete are the complete surface
const wm3 = new WeakMap();
const k = {};
wm3.set(k, 1);
console.log(wm3.has(k), wm3.get(k)); // true 1
console.log(wm3.delete(k), wm3.has(k)); // true false
// No clear — if you need bulk eviction, discard the whole WeakMap reference
```

### 3) **Canonical patterns: private state and object-keyed memoization**

**Pattern A — truly private instance state (pre-`#private` alternative, still valid for library-level branding):**

```js
// Private state via WeakMap — per-instance, GC-friendly, no property exposure
const _state = new WeakMap();

class Counter {
  constructor(start = 0) { _state.set(this, { n: start }); }
  inc() { const s = _state.get(this); s.n += 1; return s.n; }
  get() { return _state.get(this).n; }
}
const c = new Counter(5);
console.log(c.inc(), c.get()); // 6 6
console.log(Object.hasOwn(c, "n"), c.n); // false undefined — not a property
console.log(_state.has(c)); // true — association lives in WeakMap, not on the instance
// When c is collected, its entry disappears — no leak
```

**Pattern B — object-keyed memoization without growing forever:**

```js
// Memoize computed view per object key — if the key object dies, cache entry doesn't keep it alive
function memoizeObjectArg(fn) {
  const cache = new WeakMap();
  return key => {
    if (cache.has(key)) return cache.get(key);
    const result = fn(key);
    cache.set(key, result);
    return result;
  };
}
const heavy = memoizeObjectArg(obj => ({ view: JSON.stringify(obj).length }));
const a = { x: 1, y: 2 };
console.log(heavy(a).view); // computed once
console.log(heavy(a) === heavy(a)); // true — cached
// Primitive args need Map fallback — WeakMap throws (see 5.1 decision table)
```

**Pattern C — metadata / branding without polluting the object:**

```js
// Attach metadata to third-party objects without mutating them
const metadata = new WeakMap();
function tag(obj, info) { metadata.set(obj, info); }
function getTag(obj) { return metadata.get(obj); }
const node = { id: 1 };
tag(node, { source: "api" });
console.log(getTag(node)); // { source: 'api' }
console.log(Object.keys(node)); // [ 'id' ] — no extra keys added
```

- *Anti-pattern* — using `Map` for object-keyed caches that outlive the keys → unbounded growth and OOM (see [7.1](<../7. Common pitfalls to production bugs/7.1. Real production bugs caused by collection mistakes.md>)). *Why it hurts* — `Map` entries are strong refs; every object ever seen stays reachable. *Instead* — `WeakMap` for object keys when lifetime should follow the key.
- *Anti-pattern* — trying to enumerate a `WeakMap` to "count" or "persist" it → impossible by spec. *Instead* — if you need enumeration/persistence, use `Map`.

### 4) **Common confusion**

- "`WeakMap` has `size`" — no. Observing size would expose GC timing; spec omits it. If you need count, you don't want `WeakMap`.
- "`WeakMap` keys can be strings" — no, only objects/functions. Primitives throw `TypeError`.
- "`WeakMap` prevents GC" — opposite. It *doesn't* keep keys alive (ephemeron). `Map` does keep them alive.
- "`WeakMap` is iterable" — no iteration, no `clear`, no `keys`/`values`/`entries`.

### 5) **Performance note**

`WeakMap` lookup is hash-probe like `Map`, but engines store it as an ephemeron table scanned by GC (mark-and-sweep must check liveness). For live keys, cost similar to `Map`. The GC advantage: discarding the key allows reclaim without explicit `delete` — less manual bookkeeping, less leak risk. Don't use `WeakMap` for string/symbol keys (falls back to throwing) — use `Map`.

### 6) **Mentor note**

Ask juniors to build a per-object cache twice — once with `Map`, once with `WeakMap` — then ask "which one leaks if callers drop their objects?" If they answer `Map`, the ephemeron model is solid. In review, flag any `Map` keyed by objects whose lifetime should not pin the value (reporter caches, DOM node → data) — suggest `WeakMap`; flag any attempt to `for (const [k] of weakMap)` — suggest `Map`.
