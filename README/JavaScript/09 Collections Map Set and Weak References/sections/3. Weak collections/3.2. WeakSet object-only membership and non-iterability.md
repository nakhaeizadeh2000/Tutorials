## 3.2. WeakSet object-only membership and non-iterability

### 1) **Object-only values, no primitives, no iteration**

**Definition** — `WeakSet` is the ephemeron counterpart of `Set`: it stores *object* values with weak membership. No primitives, no `size`, no iteration, no `clear`. Surface is only `add`/`has`/`delete`.

```js
// Only objects — primitives throw
const ws = new WeakSet();
const obj = { id: 1 };
ws.add(obj);
console.log(ws.has(obj)); // true
try { ws.add("string"); } catch (e) { console.log(e.name); } // TypeError
try { ws.add(42); } catch (e) { console.log(e.name); } // TypeError
try { ws.add(Symbol("s")); } catch (e) { console.log(e.name); } // TypeError

// No size / no iteration / no clear — spec omits them (GC nondeterminism)
console.log(typeof ws.size); // undefined
console.log(typeof ws[Symbol.iterator]); // undefined
try { for (const x of ws) {} } catch (e) { console.log(e.name); } // TypeError
console.log(typeof ws.clear); // undefined
console.log(typeof ws.values); // undefined — no enumeration

// has/add/delete are the full API
const k = {};
ws.add(k);
console.log(ws.has(k)); // true
console.log(ws.delete(k), ws.has(k)); // true false
```

- *Why no iteration?* — if you could enumerate members, you'd observe which objects have been collected, leaking GC timing into program semantics (and forcing engines to keep a strong list).

### 2) **Ephemeron-by-membership: reachability follows members**

**Definition** — `WeakSet` does not keep its members alive. When a member object becomes unreachable elsewhere, its membership vanishes after GC. Same ephemeron intuition as `WeakMap` (there the key's liveness gates the value).

```js
// Membership vanishes when the member dies (demo is structural — GC timing non-deterministic, see 4.1)
let node = { tag: "div" };
const seen = new WeakSet([node]);
console.log(seen.has(node)); // true
let alias = node;
console.log(seen.has(alias)); // true — same identity
node = null; // drop one strong reference; alias still keeps it alive
console.log(seen.has(alias)); // true — still reachable via alias
alias = null; // now only WeakSet holds a weak ref
// At some future GC, seen.has(node) would be false for the collected object — but you cannot hold a reference to test it without keeping it alive (the observer paradox)

// Contrast: Set keeps members alive — even after you drop your references, Set still pins them
let strongNode = { tag: "span" };
const strongSeen = new Set([strongNode]);
strongNode = null;
// strongSeen still holds { tag:"span" } strongly — not collectible until removed or Set discarded
console.log(strongSeen.size); // 1 — still there (observable leak)
```

- *Observer paradox* — you cannot write a synchronous test "after GC it was removed" without retaining a `WeakRef` to observe (see [4.1](<../4. Weak references and cleanup/4.1. WeakRef semantics deref and lifetime reality.md>)). This is why `WeakSet` has no `size` to assert.

### 3) **Use cases: tagging and branding without leaking**

**Pattern A — visited / seen tagging without preventing GC:**

```js
// Tag objects you've processed without keeping them alive after callers drop them
const visited = new WeakSet();
function process(node) {
  if (visited.has(node)) return "already";
  visited.add(node);
  // ... do work
  return "processed";
}
const a = { id: 1 };
const b = { id: 2 };
console.log(process(a), process(a), process(b)); // 'processed' 'already' 'processed'
// No iteration to "list visited" — by design; if you need listing, use Set and accept the leak/cleanup cost
```

**Pattern B — brand check / capability without property mutation:**

```js
// Brand objects as "authentic" without adding a visible property
const branded = new WeakSet();
class Token {
  constructor(secret) {
    this.secret = secret;
    branded.add(this);
  }
  static isToken(obj) { return branded.has(obj); }
}
const t = new Token("s3cret");
console.log(Token.isToken(t)); // true
console.log(Token.isToken({ secret: "s3cret" })); // false — different identity
console.log(Token.isToken(t)); // true — brand survives but doesn't prevent GC of t
// Alternative: private field brand (see Prototypes 3.3) — WeakSet is the pre-private-field equivalent and remains useful for cross-realm branding
```

**Pattern C — transient listener / observer set that doesn't pin sources:**

```js
// Track active subscriptions without keeping dead targets alive
const active = new WeakSet();
function subscribe(target) { active.add(target); }
function isActive(target) { return active.has(target); }
let target = { url: "/api" };
subscribe(target);
console.log(isActive(target)); // true
// If target is later discarded by callers, isActive would eventually be false without manual unsubscribe
```

- *Anti-pattern* — using `Set` for long-lived "seen" of transient objects (DOM nodes, request contexts) → heap grows with every object ever seen. *Instead* — `WeakSet`.
- *Anti-pattern* — trying to `JSON.stringify` or `Array.from` a `WeakSet` → throws / empty. If you need persistence, you need `Set`.

### 4) **Common confusion**

- "`WeakSet` has `size`" — no, GC-nondeterminism prevents observable size.
- "`WeakSet` stores primitives" — no, only objects. `has(1)` always false; `add(1)` throws.
- "`WeakSet` prevents GC" — opposite — it doesn't keep members alive. `Set` does.
- "`WeakSet` is iterable" — no. If you need iteration, use `Set` and manage lifetime explicitly.

### 5) **Performance note**

`WeakSet.has/add/delete` hash-probe cost similar to `Set` for live members. No iteration means no iteration-cost surprises. GC ephemeron scanning adds minor collector work — negligible vs the leak-avoidance win. Don't use for string/symbol tags — primitives throw; use `Set`.

### 6) **Mentor note**

Have juniors implement `seen` once with `Set`, once with `WeakSet`, then ask "what happens if the caller drops all refs to the objects?" (`Set` retains, `WeakSet` lets GC reclaim). In review, flag any `Set` that tracks transient objects with indefinite growth and no eviction — suggest `WeakSet` if enumeration isn't needed, or `Map`+LRU/WeakRef if it is.
