## 4.1. WeakRef semantics deref and lifetime reality

### 1) **A WeakRef doesn't keep its target alive**

**Definition** — `WeakRef` holds a *non-owning* reference: `new WeakRef(target)` requires an object, `deref()` returns the target if still alive, otherwise `undefined`. It does not prevent garbage collection. Created to allow caches, observers, and interning that don't pin.

```js
// Constructor requires an object — primitives throw
try { new WeakRef(42); } catch (e) { console.log(e.name); } // TypeError
try { new WeakRef(null); } catch (e) { console.log(e.name); } // TypeError
try { new WeakRef("hi"); } catch (e) { console.log(e.name); } // TypeError

const target = { id: 1 };
const ref = new WeakRef(target);
console.log(ref.deref() === target); // true — still alive while target is reachable
console.log(ref.deref()?.id); // 1 — optional chain because deref may be undefined after GC

// Practical cache pattern
function weakCache(fn) {
  let ref; // may hold WeakRef to last result
  let lastKey;
  return key => {
    if (ref && lastKey === key) {
      const cached = ref.deref();
      if (cached !== undefined) return cached;
    }
    const result = fn(key);
    if (typeof result === "object" && result !== null) {
      ref = new WeakRef(result);
      lastKey = key;
    }
    return result;
  };
}
const makeView = weakCache(k => ({ view: String(k).toUpperCase() }));
const v1 = makeView("hello");
const v2 = makeView("hello");
console.log(v1 === v2); // true — cached while alive

// Symbols are primitives — cannot be WeakRef targets
try { new WeakRef(Symbol("s")); } catch (e) { console.log(e.name); } // TypeError
```

### 2) **Non-deterministic lifetime — GC decides, spec promises nothing**

**Definition** — the spec guarantees nothing about *when* collection happens. `deref()` may stay alive for a long time or become `undefined` soon — depending on GC, engine, memory pressure, and whether `--expose-gc` was used. Never write correctness that depends on prompt collection. Testing requires `node --expose-gc` and even then only best-effort.

```js
// GC timing is non-deterministic — this block illustrates the shape, not a timing assertion
// Run with: node --expose-gc your-file.js ; then call global.gc() to nudge collection
let obj2 = { payload: "data" };
let ref2 = new WeakRef(obj2);
console.log(ref2.deref() !== undefined); // true — obj2 is still strongly reachable via `obj2` variable
obj2 = null; // drop the strong ref — now only WeakRef holds a weak reference
// global.gc?.(); // if --expose-gc, you may nudge collection, but even then not guaranteed
// console.log(ref2.deref()); // may be undefined after GC, or may still be object — both are correct
console.log("deref after dropping strong ref may be undefined after GC — never assert immediately");

// Correct usage always handles undefined
function useWeak(ref) {
  const target = ref.deref();
  if (target === undefined) return "collected";
  return `alive: ${target.payload}`;
}
// Callers must branch on undefined — never .payload directly on deref() without check
let tmp = { payload: "x" };
const r = new WeakRef(tmp);
console.log(useWeak(r)); // 'alive: x'
tmp = null;
// useWeak(r) may be 'collected' after GC — handle both

// Common misuse: branching on if (ref.deref()) loses falsy-but-alive? — no, deref returns object or undefined only
// But treat "undefined means collected" — don't confuse with stored undefined values (WeakRef stores objects, never undefined)
```

- *Bad practice* — `if (ref.deref()) { use(ref.deref()) }` double-deref races GC between calls. *Why it hurts* — GC may collect between the check and use, second `deref()` returns `undefined` → TypeError. *Instead* — `const target = ref.deref(); if (target !== undefined) { use(target); }` single deref, local strong reference for the scope.

```js
// Bad: double deref — GC can intervene
const badRef = new WeakRef({ id: 1 });
if (badRef.deref()) {
  // GC could run here — next line may throw
  try { console.log(badRef.deref().id); } catch (e) { console.log(e.name); }
}

// Good: single deref, local binding keeps it alive for the block
const goodRef = new WeakRef({ id: 2 });
const target2 = goodRef.deref();
if (target2 !== undefined) {
  console.log(target2.id); // safe — target2 is a strong ref for this block
}
// Holding target2 keeps that object alive until this scope exits — that's the intended "resurrection for scope" pattern
```

### 3) **WeakRef vs strong ref vs WeakMap entry lifetime**

| Holder | Keeps target alive? | Observable enumeration? | Use |
|--------|---------------------|-------------------------|-----|
| Variable / property / `Map`/`Set` entry | **yes** — strong | yes | ownership |
| `WeakMap` key | **no** — ephemeron (key → value) | no — no enumeration | assoc without pinning |
| `WeakSet` member | **no** — ephemeron membership | no | tagging without pinning |
| `WeakRef` | **no** — weak | no — `deref()` may be undefined | non-owning handle / cache |

```js
// Map pins (strong) — wrong for transient cache
const map = new Map();
let key = { id: 1 };
map.set(key, { data: "big" });
key = null; // Map still holds both key and value strongly — leak
console.log(map.size); // 1 — entry persists

// WeakMap doesn't pin — preferred for keyed cache (see 3.1)
const wm = new WeakMap();
let k2 = { id: 2 };
wm.set(k2, { data: "big" });
k2 = null; // only WeakMap holds weak key — may be collected (no size to check)

// WeakRef doesn't pin — manual cache that drops under pressure
let value = { bytes: new Uint8Array(1e6) };
let weak = new WeakRef(value);
value = null; // only WeakRef left — may be collected
console.log(weak.deref() === undefined || typeof weak.deref() === "object"); // true — either state valid

// Resurrection hazard: holding the deref result pins it again
const wr = new WeakRef({ temp: 1 });
let pinned = wr.deref(); // now pinned is a strong ref — object won't be collected while pinned is live
console.log(pinned.temp); // 1 — safe
pinned = null; // drop strong ref — now collectible again
```

### 4) **Common confusion**

- "`WeakRef.deref()` throws if collected" — no, returns `undefined`.
- "GC runs immediately when last strong ref drops" — no, timing is engine- and pressure-dependent; may be much later or never before process exit.
- "Two `deref()` calls return the same object" — not guaranteed if GC runs between them; cache the single result.
- "`WeakRef` can hold strings/symbols/numbers" — no, only objects. Primitives throw.

### 5) **Performance note**

Creating a `WeakRef` is cheap, but `deref()` must check GC state — slightly more than a plain variable read. Don't wrap every reference; reserve for caches/interning where pinning would leak. Holding a `WeakRef` never speeds up GC — it just doesn't block it. The GC may scan weak refs at collection time (minor pause). Using `WeakRef` for tiny short-lived objects adds overhead with no leak benefit — plain scope variables are better.

### 6) **Mentor note**

Have juniors write a `WeakRef` cache with double-deref and watch it flake under forced GC (run with `--expose-gc` + `global.gc()` in a loop). Fixing to single-deref + `!== undefined` check makes the lesson stick. In review, flag any `ref.deref().prop` without `undefined` check and any correctness that assumes `deref()` became `undefined` promptly (e.g., "after `obj = null`, ref is cleared" in next line — never true).
