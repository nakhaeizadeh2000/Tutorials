## 4.2. FinalizationRegistry cleanup and timing reality

### 1) **Registration does not keep the target alive — cleanup is best-effort**

**Definition** — `FinalizationRegistry` lets you register a target object with a held value and optional unregister token; when the target is collected, the registry's callback is enqueued to run with the held value (not the target). Registration never keeps the target alive. Invocation is best-effort: may run late, or never (process exit, non-GC runtimes, or engine decide not to collect).

```js
// Basic shape
const registry = new FinalizationRegistry(heldValue => {
  console.log(`cleaned up ${heldValue}`);
});

let resource = { id: 1 };
registry.register(resource, "resource-1"); // target, heldValue
// Optional token for later unregister: registry.register(target, heldValue, unregisterToken)

console.log("registered"); // callback NOT called yet — target still alive

resource = null;
// global.gc?.(); // even with --expose-gc, callback is enqueued asynchronously, not synchronously after null

// Second form with token
const token = {};
let obj = { id: 2 };
registry.register(obj, "resource-2", token);
// token keeps no reference to obj; it's for unregister
obj = null;

// Held value is what the callback receives — never the target itself
const r2 = new FinalizationRegistry(held => {
  // held is "my-held-value", not the collected object
  console.log("held:", held, "target is NOT available here");
});
let t = { data: "x" };
r2.register(t, "my-held-value");
t = null;
```

- *History* — added with `WeakRef` in ES2021 (ECMA-262 §26.2) after years of absence; replaces non-standard `Object.prototype` finalizers from older hosts.

### 2) **Held value vs token and unregister discipline**

**Definition** — the held value should **not** strongly reference the target (otherwise you'd pin it). The unregister token (third argument) lets you cancel a registration before collection; `unregister(token)` removes all registrations with that token.

```js
// Held value MUST NOT reference the target — else you'd keep it alive via the registry's strong-held table
const reg = new FinalizationRegistry(held => {
  console.log(`finalize ${held}`);
});

let target = { name: "file-handle" };
let badHeld = target; // BAD — holding the target itself in held value pins it? — actually spec stores held value strongly, so if held === target, that strong ref keeps target alive via registry
// reg.register(target, badHeld); // would pin — don't do this
reg.register(target, "file-handle-id-42"); // GOOD — held is an id/primitive, not the target
target = null;
// target now collectible because held is just a string

// Unregister pattern — cancel cleanup if resource was explicitly closed
const cleanup = new FinalizationRegistry(id => {
  console.log(`fallback close ${id} — should not double-close if explicit`);
});

function openResource(id) {
  const handle = { id, close() { console.log(`explicit close ${id}`); cleanup.unregister(handle); } };
  cleanup.register(handle, id, handle); // use handle itself as token (object identity)
  return handle;
}

let h = openResource("A");
h.close(); // explicit — unregister prevents fallback
h = null; // even if GC later, callback won't fire for this target

let h2 = openResource("B");
h2 = null; // dropped without explicit close — fallback may eventually fire (best-effort)
// global.gc?.(); // callback may be enqueued sometime after collection — not immediate

// Multiple registrations with same token are all removed by one unregister(token)
const tok = {};
let a = { id: "a" };
let b = { id: "b" };
const r3 = new FinalizationRegistry(v => console.log("final", v));
r3.register(a, "held-a", tok);
r3.register(b, "held-b", tok);
r3.unregister(tok); // removes both registrations for tok
a = b = null;

// unregister returns boolean (ES2021+)
console.log(r3.unregister({})); // false — token not found
```

### 3) **Never use finalizers for resource correctness**

**Rule** — file handles, locks, sockets, `setInterval`, WASM memory, `Worker` termination must be released by explicit `dispose`/`close`/`using` (Explicit Resource Management proposal, `Symbol.dispose` / `using` in modern runtimes). `FinalizationRegistry` is only for best-effort fallback, diagnostics, or metrics — not correctness. If cleanup not running breaks invariants, you have a bug.

```js
// BAD — relying on finalizer to close a file
let file = { fd: 42, closed: false };
const badReg = new FinalizationRegistry(heldFD => {
  // This may run late, or never, or on a GC pause that blocks main thread — never reliable for fd leak
  console.log(`would close fd ${heldFD} — but too late / maybe never`);
});
badReg.register(file, file.fd);
file = null; // "closed"? — no, fd leaks until GC (maybe never)

// GOOD — explicit disposal with using / try-finally
function useFile(path) {
  const handle = { fd: 42, close() { console.log("explicit close"); } };
  try {
    console.log(`work with ${handle.fd}`);
  } finally {
    handle.close(); // deterministic
  }
}
useFile("/tmp/x");

// Modern Explicit Resource Management (Node 22+ supports Symbol.dispose / using)
{
  const res = {
    [Symbol.dispose]() { console.log("disposed via using"); }
  };
  // using res = ...; // when proposal lands in your baseline, use `using`
  // Fallback today: try/finally as above
  res[Symbol.dispose]();
}

// Acceptable use of FinalizationRegistry — observability / best-effort cache eviction metrics
const cache = new Map();
const metrics = new FinalizationRegistry(id => {
  console.log(`evicted ${id} — metric only, not correctness`);
  // Do NOT do state-mutating correctness here; engines warn that callback shouldn't resurrect or allocate heavily
});
let k = { key: "k" };
cache.set(k.id || "k", "value"); // example
metrics.register(k, "k-cache");
// When k is collected, metric fires — if it doesn't fire before process exit, nothing breaks
k = null;
```

### 4) **Common confusion**

- "`FinalizationRegistry` callback runs synchronously after last reference drops" — no, enqueued asynchronously after GC, and may never run.
- "Held value can be the target" — technically allowed but defeats the purpose (strong ref to target keeps it alive — leak). Hold an id/key, not the target.
- "`unregister` needs the target" — no, needs the *token* (third arg). If you registered without a token, you cannot unregister.
- "Finalizers run on every GC" — no, only when a registered target is collected; multiple targets may batch.

### 5) **Performance note**

Callbacks run on the microtask queue after collection, not during the mark phase — but heavy work in callbacks (allocation, I/O) can jank. Keep callbacks tiny (increment a counter, schedule async cleanup). Registering millions of targets adds GC bookkeeping — prefer one registry per resource kind, not per closure. Using finalizers for correctness often masks leaks that grow unobserved until OOM — explicit `dispose` is cheaper than chasing GC timing.

### 6) **Mentor note**

Have juniors implement a `WeakMap` cache with a `FinalizationRegistry` metric and then ask "can you `await` collection?" (no — no promise). Show that `global.gc()` even with `--expose-gc` still doesn't guarantee timely callback — flakiness is the lesson. In review, flag any `FinalizationRegistry` that closes sockets/files/locks without an explicit path — demand a `try/finally` or `using` primary. Flag any held value that captures the target — suggest an id.
