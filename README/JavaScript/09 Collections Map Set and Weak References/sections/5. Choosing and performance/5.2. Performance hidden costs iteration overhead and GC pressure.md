## 5.2. Performance hidden costs iteration overhead and GC pressure

### 1) **`Map`/`Set` iteration cost vs object key enumeration**

**Definition** — `Map`/`Set` keep insertion-order linked lists; iteration walks that list and allocates an iterator object (`entries()`/`values()`). Object key enumeration (`Object.keys`/`entries`) returns a new array (allocation) and — for ordinary objects — walks hidden-class ordered keys. Both have costs; neither is free.

```js
// Map iteration allocates an iterator — forEach can reuse internal walk on some engines
const m = new Map(Array.from({ length: 1e4 }, (_, i) => [i, i * 2]));
// Hot loop variant A: for-of (allocates iterator)
let sumA = 0;
for (const [k, v] of m) sumA += v;
// Hot loop variant B: forEach (no iterator on some engines — measure)
let sumB = 0;
m.forEach(v => { sumB += v; });
console.log(sumA === sumB); // true — same sum, different allocation profile (measure with --allow-natives-syntax microbenchmark)

// Object.keys allocates an array of keys — additional O(n) memory
const obj = Object.fromEntries(m); // string keys "0".."9999"
const keys = Object.keys(obj); // allocates 10k-length array
console.log(keys.length, typeof keys[0]); // 10000 'string' — note keys became strings

// Cross-check: Map numeric keys stay numeric-type
console.log(typeof [...m.keys()][0]); // 'number' — Map preserves number key type; object stringifies

// Iteration mutation costs: deleting during Map/Set iteration is supported (iterator skips), but touching Object prototype during enumeration can deoptimize
```

- *History note* — `for-in` on objects walks the chain and is historically the slowest; `Object.keys`+`for-of` replaced it for data loops (see [Objects 2.3](<../../../06 Objects in Depth/sections/2. Properties and descriptors/2.3. Enumerability enumeration order and for-in mechanics.md>)). `Map`/`Set` iteration has been stable since ES2015 with iterator protocol (domain 10 owns the protocol deep dive).

### 2) **Weak collections and GC pressure — what actually leaks**

**Definition** — leak = reachable but unused memory. `Map`/`Set`/`Array`/`Object` hold strong refs → leak if you forget to `delete`/`clear` and the collection lives. `WeakMap`/`WeakSet`/`WeakRef` hold weak/ephemeron refs → no leak for keys/members, but values/held values are strong.

```js
// Leak via strong Map — unbounded cache that pins every object ever seen (see 7.1 real incident)
let nextId = 0;
const leak = new Map();
function cacheStrong(obj) {
  if (!leak.has(obj)) leak.set(obj, { id: ++nextId, view: obj });
  return leak.get(obj);
}
// Every distinct object argument is now pinned in `leak` forever — even after callers drop the object

// Fix via WeakMap — key death evicts
const fixed = new WeakMap();
function cacheWeak(obj) {
  if (typeof obj !== "object" || obj === null) throw new TypeError("WeakMap key must be object");
  if (!fixed.has(obj)) fixed.set(obj, { id: ++nextId, view: obj });
  // Watch: value { id, view: obj } strongly refs obj again via view — if value holds the key, entry stays alive (self-pin)
  // Better: don't hold the key strongly in the value, or accept the cycle is the entry itself
  return fixed.get(obj);
}
// After callers drop the object, GC can reclaim both key and value (if value doesn't separately pin key elsewhere)

// Anti-pattern: value pins key — still leaks via value's strong ref (see 7.1)
const subtle = new WeakMap();
function subtleLeak(obj) {
  if (!subtle.has(obj)) subtle.set(obj, { ref: obj }); // value ref keeps obj alive via value's own strong ref? — but value liveness is gated by key, so not a leak by itself
  // More subtle: an external Map holding the value pins it, which keeps key via value→key edge only if you reintroduce it
}

// WeakRef cache drops under pressure — correct for "keep if convenient"
let strong = { payload: new Uint8Array(1e6) };
let weakHandoff = new WeakRef(strong);
strong = null; // only WeakRef left — collectible (may go soon under pressure)
// weakHandoff.deref() may be undefined after GC — that is correct, not a bug
console.log(weakHandoff.deref() === undefined || typeof weakHandoff.deref() === "object");

// FinalizationRegistry for metrics only — never for correctness (see 4.2)
const metrics = new FinalizationRegistry(id => console.log(`metric: ${id} collected`));
let target = { id: "metric-target" };
metrics.register(target, target.id);
target = null; // collection may eventually enqueue callback — not deterministic

// Effective mitigation for strong collections: bounded LRU or explicit eviction, not "wait for GC"
function createLRU(limit = 100) {
  const map = new Map();
  return {
    get(k) { const v = map.get(k); if (v !== undefined) { map.delete(k); map.set(k, v); } return v; },
    set(k, v) { if (map.has(k)) map.delete(k); else if (map.size >= limit) map.delete(map.keys().next().value); map.set(k, v); },
    size() { return map.size; }
  };
}
const lru = createLRU(2);
lru.set("a", 1); lru.set("b", 2); lru.set("c", 3); // evicts "a"
console.log(lru.size(), lru.get("a")); // 2 undefined — bounded, not leaking
```

### 3) **Measure-don't-guess framing**

| Misleading microbenchmark | Why it lies | What to measure instead |
|---------------------------|-------------|------------------------|
| `Map` vs `{}` at `n=3` | hidden-class inline cache wins at tiny `n` | representative `n`, hit-rate, and iteration vs lookup mix |
| `Set.has` vs `Array.includes` at `n=5` | linear scan faster than hash at tiny `n` | growing `n` + many probes (cache vs scan) |
| `WeakRef.deref` tight loop | no GC pressure → always alive | pressure + allocation rate, not empty loop |
| `FinalizationRegistry` promptness | assumes immediate callback | liveness after process-exit, not timing |

```js
// Naive time-it and the pitfall
function timeIt(fn, iter = 1e5) {
  const t0 = performance.now();
  for (let i = 0; i < iter; i++) fn();
  return performance.now() - t0;
}
const smallSet = new Set([1, 2, 3]);
const smallArr = [1, 2, 3];
console.log("small Set.has vs Array.includes — small n, Set may lose due to hash overhead:", timeIt(() => smallSet.has(2)) < timeIt(() => smallArr.includes(2)) ? "set wins" : "array wins");

const bigSet = new Set(Array.from({ length: 1e5 }, (_, i) => i));
const bigArr = Array.from({ length: 1e5 }, (_, i) => i);
console.log("big Set.has vs Array.includes — large n, Set must win:", timeIt(() => bigSet.has(99999), 1e4) < timeIt(() => bigArr.includes(99999), 1e4) ? "set wins" : "array wins");

// engine hints, not contracts — label such claims (as of August 2026: V8 fast paths for packed maps/sets, dictionary mode for sparse objects — see Arrays 1.1/Objects 1.2 notes)
console.log("profile with real workloads — microbenchmarks are hints, not contracts");
```

### 4) **Common confusion**

- "`Map`/`Set` are always faster than object/array" — no, size and shape matter. Tiny fixed-shape `object` wins on inline cache; large dynamic sets win on hash.
- "`WeakMap` makes GC faster" — no, ephemeron tables add GC scanning work; the win is correctness (no leak), not pause time.
- "`WeakRef` resurrection inside callback is free" — holding `deref()` pins the object for that scope; don't hold long-lived.
- "`FinalizationRegistry` callbacks run promptly" — best-effort, delayed, may batch or never.

### 5) **Mentor note**

Give juniors an unbounded `Map` cache and a heap snapshot (`node --heapsnapshot-signal=SIGUSR2`) growing without bound, then replace with `WeakMap` and show the snapshot flatlines. Then have them compare `Set` vs `Array` at `n=1e5` — the linear scan cliff makes the algorithmic argument visceral. In review, flag any strong collection with no size bound and no eviction policy — demand a `Weak*`, LRU, or TTL.
