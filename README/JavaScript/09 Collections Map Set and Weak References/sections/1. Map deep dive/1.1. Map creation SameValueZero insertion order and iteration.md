## 1.1. Map creation SameValueZero insertion order and iteration

### 1) **Creation and literal intent — why there is no Map literal**

**Definition** — `Map` is the ordered, identity-keyed dictionary. There is no literal syntax; you create it with `new Map(iterable)` where the iterable yields `[key, value]` pairs (usually from another `Map`, `Object.entries` output, or a generator). `Map.groupBy` (ES2024) is a factory that groups an iterable by a callback's return value into a `Map`.

**What problem it solves / history** — plain objects stringify keys via `ToPropertyKey` (`{}` becomes `"[object Object]"`, `1` becomes `"1"`, `-0` becomes `"0"`). `Map` preserves key identity so objects, `NaN`, `-0`, and symbols keep distinct or SameValueZero-equal semantics without collision. Added in ES2015 to give the language a real hash map; `Map.groupBy` in ES2024 replaced ad-hoc `reduce` grouping.

**Modern guidance** — default to `new Map()` for any dictionary whose keys may be non-strings or whose string keys come from untrusted input (no prototype pollution). Use `Map.groupBy` when grouping; otherwise `new Map(entries)`.

```js
// No literal — use constructor or factory
const empty = new Map();
console.log(empty.size); // 0

const fromPairs = new Map([["a", 1], ["b", 2]]);
console.log([...fromPairs]); // [ [ 'a', 1 ], [ 'b', 2 ] ]

// Object.entries → Map round-trip keeps keys as strings here, but becomes identity-safe for non-string keys
const obj = { x: 10, y: 20 };
const m = new Map(Object.entries(obj));
console.log(m.get("x")); // 10
console.log(Object.fromEntries(m)); // { x: 10, y: 20 }

// Map.groupBy — ES2024 (Node 21+) groups by callback return value
const nums = [1, 2, 3, 4, 5, 6];
const byParity = Map.groupBy(nums, n => n % 2 === 0 ? "even" : "odd");
console.log(byParity.get("even")); // [ 2, 4, 6 ]
console.log(byParity.get("odd")); // [ 1, 3, 5 ]

// Non-string keys keep identity — what Object cannot do
const k1 = {};
const k2 = {};
const idMap = new Map();
idMap.set(k1, "first");
idMap.set(k2, "second");
console.log(idMap.get(k1), idMap.get(k2)); // 'first' 'second'
console.log(idMap.get({})); // undefined — different object identity

// Contrast: plain object collapses them
const objMap = {};
objMap[k1] = "first";
objMap[k2] = "second"; // same string key "[object Object]"
console.log(objMap[k1], objMap["[object Object]"]); // 'second' 'second'
```

### 2) **SameValueZero is the comparator — not `===`**

**Definition** — `Map`/`Set` compare keys via SameValueZero (ECMA-262 §7.2.10): like `===` except `NaN` equals `NaN` and `-0` equals `+0`. `Object.is` differs on the second point (`Object.is(-0, +0)` is `false`); `===` differs on the first (`NaN === NaN` false).

| Operation | `===` | `Object.is` | SameValueZero (`Map`/`Set`) |
|-----------|-------|-------------|------------------------------|
| `NaN` vs `NaN` | `false` | `true` | `true` — single entry |
| `-0` vs `+0` | `true` | `false` | `true` — single entry |
| `0` vs `-0` | `true` | `false` | `true` |

```js
// NaN deduplicates in Map/Set — unlike ===
const nanMap = new Map();
nanMap.set(NaN, "a");
nanMap.set(NaN, "b"); // same key under SameValueZero
console.log(nanMap.size); // 1
console.log(nanMap.get(NaN)); // 'b'
console.log(NaN === NaN); // false — would have expected 2 entries if ===

// -0 and +0 are the same key in Map/Set — unlike Object.is
const zeroMap = new Map();
zeroMap.set(-0, "neg");
zeroMap.set(+0, "pos");
console.log(zeroMap.size); // 1
console.log(zeroMap.get(-0), zeroMap.get(+0)); // 'pos' 'pos'
console.log(Object.is(-0, +0)); // false — Object.is distinguishes them
console.log(-0 === +0); // true — === matches SameValueZero here
console.log(1 / -0, 1 / +0); // -Infinity Infinity — if you need the sign back, you lost it as a Map key

// Set uses the same comparator
const s = new Set([NaN, NaN, -0, +0, 0]);
console.log(s.size); // 2 — { NaN, 0 } (all zeros collapse, all NaNs collapse)
console.log(s.has(NaN), s.has(-0), s.has(+0)); // true true true

// Object keys cannot preserve this at all — they stringify
const o = {};
o[NaN] = 1;
o[NaN] = 2;
console.log(Object.keys(o)); // [ 'NaN' ] — string "NaN", not the numeric NaN identity
o[-0] = 3;
o[+0] = 4;
console.log(o["0"], Object.keys(o)); // 4 [ '0', 'NaN' ] — -0 became "0"
```

- *History vs bad mental model* — teaching `Map` as "`===` for keys" silently mispredicts `NaN` lookup. Correct model: "SameValueZero" — memorize the two rows (`NaN` and `-0`).

### 3) **Insertion order iteration with stable mutation semantics**

**Definition** — `Map` iterates in insertion order: `keys()`, `values()`, `entries()` (and `for-of` which is `entries`), and `forEach`. Updating the value of an existing key does **not** move it; deleting and re-adding moves it to the end. Iteration supports live mutation: entries added during iteration may be visited, deleted entries are skipped.

```js
// Insertion order is the iteration order
const m2 = new Map([["b", 2], ["a", 1], ["c", 3]]);
console.log([...m2.keys()]); // [ 'b', 'a', 'c' ]
console.log([...m2.values()]); // [ 2, 1, 3 ]
console.log([...m2]); // [ [ 'b', 2 ], [ 'a', 1 ], [ 'c', 3 ] ] — same as entries()

// Updating a value does NOT reinsert
m2.set("a", 99);
console.log([...m2.keys()]); // [ 'b', 'a', 'c' ] — "a" stays in its original slot
console.log(m2.get("a")); // 99 — value updated

// Delete + re-add moves to end
m2.delete("a");
m2.set("a", 100);
console.log([...m2.keys()]); // [ 'b', 'c', 'a' ] — now last

// forEach visits in insertion order with (value, key, map)
const seen = [];
m2.forEach((v, k) => seen.push(`${k}:${v}`));
console.log(seen); // [ 'b:2', 'c:3', 'a:100' ]

// Live mutation during iteration — new entries added after current position are visited
const m3 = new Map([["a", 1], ["b", 2], ["c", 3]]);
const visited = [];
for (const [k, v] of m3) {
  visited.push(k);
  if (k === "a") m3.set("d", 4); // added after "a" but before end
  if (k === "b") m3.delete("c"); // c removed before visit → skipped
}
console.log(visited); // [ 'a', 'b', 'd' ] — "c" skipped, "d" visited (engine walks live list)
console.log([...m3.keys()]); // [ 'a', 'b', 'd' ]

// Map is iterable; spread/destructuring/for-of all use entries()
const entries = [...m2.entries()];
console.log(entries[0]); // [ 'b', 2 ]
const [[k0, v0]] = m2; // destructuring via iteration
console.log(k0, v0); // 'b' 2
```

### 4) **Common confusion**

- "`Map` keys use `===`" — no, SameValueZero (`NaN` equal, `-0` conflated). Test with `NaN` lookup in review.
- "`Map` has a literal like `{}`" — no. `new Map([["k","v"]])` or `Map.groupBy` are the idioms.
- "Updating a `Map` entry reorders it" — no, only delete+re-add moves to end.
- "`Object.keys` order equals `Map` order" — both are insertion-order for strings since ES2015, but `Object` interleaves integer indices first (ascending) per [Objects 2.3](<../../../06 Objects in Depth/sections/2. Properties and descriptors/2.3. Enumerability enumeration order and for-in mechanics.md>); `Map` keeps exact insertion order regardless of key shape.

### 5) **Performance note**

`Map` insertion/lookup/delete are average O(1) hash — but each entry carries a linked-list node for order and an iterator object on `for-of`/`entries()`. For tiny fixed key sets (< ~10 string keys known at author time), a plain object literal is faster to create and often faster to read (hidden class). For large dynamic sets or non-string keys, `Map` wins on algorithmic complexity and correctness. Hot loop over a `Map` via `for (const [k,v] of map)` allocates an iterator per loop; `map.forEach` can be faster on some engines — measure with representative `n`.

### 6) **Mentor note**

Ask juniors to predict `m.get(-0)` after `m.set(+0, 1)` and `m.get(NaN)` after `m.set(NaN, 1)` — if they answer "miss", the `===` mental model is still active. Have them contrast `obj[{}]` collapse vs `map.set({}, 1)` identity — that one demonstration fixes object-as-map confusion permanently. In review, flag any `obj[dynamicKey]` where `dynamicKey` may be object/`NaN` — suggest `Map`.
