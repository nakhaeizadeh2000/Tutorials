## 8.1. Common interview Q&A: objects, descriptors, prototypes

### 1) **The classics with mechanism-level answers**

**Q1. What defaults does `Object.defineProperty(o, "x", { value: 1 })` give?**
A — `writable: false, enumerable: false, configurable: false`. So later `o.x = 2` silently fails in sloppy (TypeError strict) and `Object.keys(o)` hides `x`. Fix: spell `{ writable: true, enumerable: true, configurable: true }` when you want a normal data field, or use a literal `{ x: 1 }` which gives `true/true/true` (→ [2.1](../2. Properties and descriptors/2.1. Data vs accessor descriptors and attribute defaults.md>)).

**Q2. Does `{ ...obj }` deep-clone?**
A — no; enumerable own string+symbol properties shallowly — nested objects/arrays share references. Mutating `clone.inner.x` mutates `obj.inner.x`. Use `structuredClone(obj)` for deep acyclic clones (→ [4.1](../4. Object utilities and copying/4.1. Assign merging shallow copy and fromEntries.md>)).

**Q3. `Object.keys` vs `Object.getOwnPropertyNames` vs `Reflect.ownKeys`?**
A — `keys` → enumerable own strings. `getOwnPropertyNames` → all own strings (including non-enumerable). `Reflect.ownKeys` → all own strings + symbols (→ [4.2](../4. Object utilities and copying/4.2. Keys values entries hasOwn and reflection APIs.md>)). None walks the chain; `for-in` does (strings, enumerable, own+inherited → [2.3](../2. Properties and descriptors/2.3. Enumerability enumeration order and for-in mechanics.md>)).

**Q4. `Object.hasOwn(obj, k)` vs `obj.hasOwnProperty(k)` vs `k in obj`?**
A — `hasOwn` → own only (strings+symbols), safe on `Object.create(null)` (ES2022). `hasOwnProperty` → own only but via `Object.prototype` lookup — `TypeError` on null-proto objects. `in` → own + inherited. Use `hasOwn` for own checks; `in` only when you deliberately probe the chain (→ [4.2](../4. Object utilities and copying/4.2. Keys values entries hasOwn and reflection APIs.md>)).

**Q5. Is `{ a: 1, a: 2 }` an error?**
A — no; last wins(`2`). Insertion order still has `a` at its first position (value replaced, position not moved). `delete obj.a; obj.a = 3` *does* move `a` to the end of string-insertion order (→ [2.3](../2. Properties and descriptors/2.3. Enumerability enumeration order and for-in mechanics.md>)).

**Q6. When does `{ __proto__: p }` link the prototype?**
A — only the exact literal key `__proto__: p` wires `[[Prototype]]`. Computed `["__proto__"]: p` creates a plain string key named `"__proto__"`; `Object.create(null)` objects have no `__proto__` accessor to link via later `obj.__proto__ = p` (use `Object.setPrototypeOf` if you must mutate — prefer `Object.create` at birth → [1.2](../1. Object creation and literals/1.2. Creation patterns literal Object create and constructors.md>) / [3.1](../3. Prototype linkage intro/3.1. The prototype chain getPrototypeOf setPrototypeOf and Object.create.md>)).

**Q7. Does `Object.freeze(obj)` freeze nested objects?**
A — no; shallow only. `freeze({ inner: { x: 1 } })` still allows `obj.inner.x = 2`. Deep freeze requires recursion over `Reflect.ownKeys` with cycle guard (→ [5.1](../5. Integrity and immutability/5.1. Prevent extensions seal freeze and shallow immutability.md>)). `seal` similarly shallow and keeps `writable: true`; `preventExtensions` only blocks adds.

**Q8. What order does `Object.keys` guarantee?**
A — ES2015+ `OrdinaryOwnPropertyKeys` partition: integer indices (`"0"` ≤ i < 2^32−1) ascending, then strings insertion order, then symbols insertion (→ [2.3](../2. Properties and descriptors/2.3. Enumerability enumeration order and for-in mechanics.md>)). `"02"` / `"-1"` are not integer indices — they stay in string-insertion order.

**Q9. Does `Object.assign` copy getters/setters as descriptors?**
A — no; it reads values (getters fire) and assigns via `target[key] = value` (setters fire). So an accessor source becomes a data property on the target. To copy descriptors, use `Object.defineProperties(target, Object.getOwnPropertyDescriptors(source))` (→ [4.1](../4. Object utilities and copying/4.1. Assign merging shallow copy and fromEntries.md>) / [2.2](../2. Properties and descriptors/2.2. Defining observing and configuring properties.md>)).

**Q10. Rest `{ a, ...rest }` keeps the prototype?**
A — no; `rest` is always a plain `Object.prototype`-backed object with enumerable own leftovers (strings+symbols, shallow). Non-enumerable and inherited keys are omitted; prototype link is not preserved (→ [4.3](../4. Object utilities and copying/4.3. Destructuring rest and spread patterns for objects.md>)).

**Q11. Difference between an object's `[[Prototype]]` and a function's `prototype`?**
A — objects *have* `[[Prototype]]` (the chain link read via `getPrototypeOf`). Functions *have* a `.prototype` property that `new` stamps into fresh instances' `[[Prototype]]`. `Dog.prototype` is not `Dog`'s own prototype; `Object.getPrototypeOf(Dog) === Function.prototype` (→ [3.1](../3. Prototype linkage intro/3.1. The prototype chain getPrototypeOf setPrototypeOf and Object.create.md>)).

**Q12. `Object.is(NaN, NaN)` vs `NaN === NaN`?**
A — `NaN === NaN` is `false`; `Object.is(NaN, NaN)` is `true` (SameValue). `0 === -0` is `true`; `Object.is(0, -0)` is `false`. `Object.is` affects only numeric edges — objects still test reference identity in both (→ [4.2](../4. Object utilities and copying/4.2. Keys values entries hasOwn and reflection APIs.md>)).

### 2) **What interviewers actually probe for**

- Tracing descriptor installs: "after `defineProperty(o, 'x', { value: 1 })` what does `o.x = 2` do in strict vs sloppy?" — tests default-false + mode split, not API recall.
- Own vs chain vs enumerable: "which keys survive `keys` vs `ownKeys` vs `assign` vs spread vs `for-in`?" — tests the three-dichotomy matrix (→ [6.1](../6. Important points to remember/6.1. Object checklist reflex rules mentors screen for.md>)).
- Prototype wiring: "why does `['__proto__']` not link, and why does `instanceof` break after `Ctor.prototype = {...}`?" — tests `__proto__` accessor vs slot + `instanceof` walk.
- Shallow vs descriptor copy: "how would you preserve a getter when cloning?" — expects `getOwnPropertyDescriptors` + `defineProperties`, not `assign`.

### 3) **Grading guidance**

| Signal | Junior | Mid | Senior |
|--------|--------|-----|--------|
| Names defaults correctly (`defineProperty` ⇒ `false/false/false`) | ✓ | ✓ | ✓ |
| Explains why `assign`/spread share nested refs | — | ✓ | ✓ |
| Distinguishes `hasOwn` / `in` / `hasOwnProperty` on `null`-proto; traces `for-in` vs `keys` | — | — | ✓ |
| Calls out shallow seal/freeze + deep-freeze cycle guard | — | — | ✓ |

Red flags: "freeze is deep", "`assign` copies descriptors", "`for-in` is own-only", "`__proto__` key always links", "`hasOwnProperty` works on `Object.create(null)`", "spread throws on `null`".
