## 1.2. Creation patterns: literal, Object, Object.create, and constructors

### 1) **{} vs new Object() vs Object.create — same idea, different prototype and intent**

**Definition** — every object is born with an internal `[[Prototype]]` (the link the engine walks on property lookup). How you create it decides that link and how explicit the intent reads:

| Pattern | `[[Prototype]]` | When to read it as intent |
|---------|----------------|---------------------------|
| `{}` / `{ a: 1 }` | `Object.prototype` | "a data record" — default dictionary |
| `new Object(value)` | `Object.prototype` (or wrapper prototype if `value` is primitive) | legacy factory — avoid; literal does the same without the constructor trap |
| `Object.create(proto)` | `proto` (or `null`) | "I choose the prototype precisely" |
| `Object.create(null)` | `null` — no prototype at all | "pure dictionary" — no `toString`/`hasOwnProperty` pollution |
| `new Ctor()` | `Ctor.prototype` | "instance with shared behavior" — full story in Prototypes and Classes (textual forward ref) |

```js
// {} and new Object() are twins — prefer {}
const a = {};
const b = new Object();
console.log(Object.getPrototypeOf(a) === Object.prototype); // true
console.log(Object.getPrototypeOf(b) === Object.prototype); // true
console.log(a.__proto__ === Object.prototype); // true — __proto__ accessor reflects [[Prototype]]
console.log(a.toString === Object.prototype.toString); // true — inherited

// new Object(value) wraps primitives — a special case, not a pattern to use
console.log(new Object(42) instanceof Number); // true — legacy wrapping
console.log(typeof new Object("hi")); // object — boxed String

// Object.create controls the prototype explicitly
const proto = { kind: "proto", greet() { return "hi"; } };
const child = Object.create(proto, {
  // second arg is a descriptor map (→ [2.2](../2. Properties and descriptors/2.2. Defining observing and configuring properties.md))
  id: { value: 1, writable: true, enumerable: true, configurable: true }
});
console.log(child.kind); // proto — found via prototype chain
console.log(Object.getPrototypeOf(child) === proto); // true
console.log(child.hasOwnProperty("kind")); // false — on prototype, not own

// Null-prototype dictionaries: no inherited keys to collide with
const dict = Object.create(null);
dict["__proto__"] = "just a key";
dict["toString"] = "not a method";
console.log(dict["__proto__"]); // just a key — no prototype magic
console.log(Object.getPrototypeOf(dict)); // null
console.log("toString" in dict); // true — own key, not inherited method
try { console.log(dict.toString()); } catch (e) { console.log(e.name); } // TypeError — no prototype to delegate to
console.log(Object.prototype.toString.call(dict)); // [object Object] — can still call via borrow

// Literal __proto__ sets the prototype once, at birth (not a plain key)
const base = { base: true };
const withProto = { __proto__: base, own: 1 };
console.log(Object.getPrototypeOf(withProto) === base); // true — __proto__ in literals wires [[Prototype]]
console.log(withProto.base); // true — via prototype
// Contrast: computed ["__proto__"] creates a plain data key, not a link
const notProto = { ["__proto__"]: base, own: 1 };
console.log(Object.getPrototypeOf(notProto) === Object.prototype); // true — NOT linked
console.log(notProto["__proto__"] === base); // true — just a string key named "__proto__"
```

- Modern guidance: default to `{}` for data; use `Object.create(null)` when the object is a lookup table keyed by untrusted strings (user input, JSON keys) to avoid prototype pollution and `__proto__` aliasing; use `Object.create(proto)` when you need differential inheritance without a constructor; avoid `new Object()` — its wrapping behavior on primitives is a bug magnet.

### 2) **Factory vs constructor — why both still exist**

Two styles produce instances that share behavior — factories keep state in closures ([Variables §3.3](<../../../04 Variables Scope and Closures/sections/3. Closures/3.3. Closure patterns privacy factories memoization.md>)), constructors/classes share methods via the prototype (→ Prototypes and Classes forward ref). This domain covers the creation mechanics; the inheritance story belongs to domain 07.

```js
// Factory: private state via closure, methods as own properties (one copy per instance)
function makeCounter(start = 0) {
  let n = start; // private — not a property
  return {
    inc() { n += 1; return n; },
    get() { return n; }
  };
}
const c1 = makeCounter(5);
const c2 = makeCounter(5);
console.log(c1.inc(), c1.get()); // 6 6
console.log(c1.inc === c2.inc); // false — each instance owns its own function

// Constructor: shared methods via prototype, one copy across instances
function Counter(start = 0) { this.n = start; }
Counter.prototype.inc = function () { this.n += 1; return this.n; };
Counter.prototype.get = function () { return this.n; };
const d1 = new Counter(5);
const d2 = new Counter(5);
console.log(d1.inc(), d1.get()); // 6 6
console.log(d1.inc === d2.inc); // true — shared on prototype
console.log(d1 instanceof Counter); // true

// Class syntax is sugar over the same mechanism (ES2015 era, stable — forward ref to domain 07)
class CounterK { constructor(s = 0) { this.n = s; } inc() { this.n += 1; return this.n; } get() { return this.n; } }
console.log(new CounterK(1).inc()); // 2

// Literal + Object.assign factory (shallow, no closure privacy)
function makePoint(x, y) { return { x, y, toString() { return `${this.x},${this.y}`; } }; }
console.log(makePoint(2, 3).toString()); // 2,3
```

- Trade-offs: factories give real privacy (closures) and no `new`/`this` mistakes, but pay per-instance function cost and miss prototype optimizations; constructors/classes give sharing and `instanceof` + `extends` but expose state as properties (use `#private` in classes for privacy — domain 07). For pure data bags, skip both — use a literal.

### 3) **Choosing the creation site**

```js
// 1) Data record — literal (fastest to read, fastest for engines to optimize)
function user(name, id) { return { name, id, createdAt: Date.now() }; }
console.log(user("ada", 1)); // { name: 'ada', id: 1, createdAt: ... }

// 2) Dictionary keyed by external strings — null prototype to avoid collisions
function buildLookup(pairs) {
  const dict = Object.create(null);
  for (const [k, v] of pairs) dict[k] = v;
  return dict;
}
const lookup = buildLookup([["__proto__", 1], ["constructor", 2]]);
console.log(Object.getPrototypeOf(lookup)); // null
console.log(lookup["__proto__"]); // 1 — safe
console.log("toString" in lookup); // false — no inherited toString

// 3) Object that intentionally exposes a prototype API — Object.create or constructor
const greeterProto = { greet() { return `hi, ${this.name}`; } };
const ada = Object.create(greeterProto);
ada.name = "ada";
console.log(ada.greet()); // hi, ada

// 4) Avoid: new Object(x) wrapping — use literal/Number/String or Object() as function only for explicit coercion
console.log(Object(42) instanceof Number); // true — but prefer { value: 42 } or Number(42) explicitly
```

- *Common pitfall* — mutating the prototype after birth (`Object.setPrototypeOf(obj, newProto)` or `obj.__proto__ = ...`) forces the engine to discard the hidden class and re-optimize; never do it in hot paths. Set the right prototype at creation time (`{ __proto__: proto }`, `Object.create(proto)`, or `new Ctor()`), then leave the link alone.

### 4) **Common confusion**

- "`__proto__` is the prototype" — `__proto__` is a legacy accessor on `Object.prototype`; `[[Prototype]]` is the internal slot. `{ __proto__: x }` in a literal *does* wire `[[Prototype]]` (one spec-mandated exception), but `obj.__proto__ = x` post-creation mutates via the accessor (slow path) — prefer `Object.getPrototypeOf`/`Object.create`.
- "`Object.create(null)` objects have `hasOwnProperty`" — they don't; `dict.hasOwnProperty` is `undefined`. Use `Object.hasOwn(dict, k)` (ES2022) or `Object.prototype.hasOwnProperty.call(dict, k)`.
- "`new Object()` and `{}` differ" — they don't for zero args; `new Object("hi")` *does* differ (boxes), but that's rarely wanted — write `{}` and be explicit about boxing with `String("hi")` or `new String` only when you intend a wrapper (almost never).
- "Factories vs classes is style only" — semantics differ: per-instance closures vs shared prototype, `instanceof` availability, and memory shape. Choose on semantics, not taste.

### 5) **Performance note**

Literal shapes with a fixed key set compile to a monomorphic hidden class; adding keys later via `obj.newKey = ...` transitions the class. Factories that build objects with different key orders produce polymorphic shapes — keep key order stable. `Object.create(null)` skips the `Object.prototype` lookup entirely — measurable in tight lookup loops that pollute the prototype, but the bigger win is correctness (no accidental `__proto__` alias). `Object.setPrototypeOf` in a loop forces deoptimization — set at birth and freeze the choice.

### 6) **Mentor note**

Ask trainees to build a safe frequency table from `["__proto__", "toString", "a", "a"]` and verify `freq["__proto__"]` doesn't pollute `Object.prototype`. If they reach for `Object.create(null)` without prompting, the model is solid. In review, grep `new Object(` (replace with `{}`), bare `{}` used as dictionary keyed by untrusted input (suggest `Object.create(null)` or `Map`), and post-creation `__proto__` assignment (suggest literal `__proto__` or `Object.create`).
