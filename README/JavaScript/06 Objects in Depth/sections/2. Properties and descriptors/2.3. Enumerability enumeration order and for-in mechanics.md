## 2.3. Enumerability, enumeration order, and for-in mechanics

### 1) **enumerable gates for-in, Object.keys, and spread**

**Definition** — `enumerable` is the descriptor attribute that controls whether a property appears in *enumerations*: `for...in`, `Object.keys`, `Object.values`, `Object.entries`, `...spread`, and `JSON.stringify`. It does **not** hide a property from `getOwnPropertyNames`, `getOwnPropertySymbols`, `Reflect.ownKeys`, or direct access (`obj[k]`). Non-enumerable properties still exist and are reachable — they just stay out of the "data" paths.

```js
const obj = {};
Object.defineProperties(obj, {
  visible: { value: 1, enumerable: true, configurable: true, writable: true },
  hidden:  { value: 2, enumerable: false, configurable: true, writable: true },
  alsoHidden: { get() { return 3; }, enumerable: false, configurable: true }
});

console.log(Object.keys(obj)); // [ 'visible' ] — only enumerable string keys
console.log(Object.values(obj)); // [1]
console.log(Object.entries(obj)); // [ [ 'visible', 1 ] ]
console.log({ ...obj }); // { visible: 1 } — spread copies only enumerable own
console.log(JSON.stringify(obj)); // {"visible":1}
for (const k in obj) console.log("for-in", k); // visible only

// Non-enumerable is still there
console.log(Object.getOwnPropertyNames(obj)); // [ 'visible', 'hidden', 'alsoHidden' ] — all string keys
console.log(Object.getOwnPropertyDescriptor(obj, "hidden").enumerable); // false
console.log(obj.hidden); // 2 — direct access works
console.log(Reflect.ownKeys(obj)); // [ 'visible', 'hidden', 'alsoHidden' ]

// Methods added via class syntax are non-enumerable by design; concise methods in literals are enumerable
class C { method() {} }
console.log(Object.getOwnPropertyDescriptor(C.prototype, "method").enumerable); // false — class hides it
const lit = { method() {} };
console.log(Object.getOwnPropertyDescriptor(lit, "method").enumerable); // true — literal keeps it enumerable
```

- *Why the split?* Built-ins (`toString`, `hasOwnProperty`) are `enumerable: false` so `for-in` on plain objects doesn't flood you with inherited noise. Libraries mirror that: internal helpers are hidden, data payload is enumerable — `JSON.stringify`/spread serializes only the data surface.

### 2) **Own-property order is specified since ES2015**

Engines now follow ECMA-262 `OrdinaryOwnPropertyKeys` sorting for every reflective method (`Reflect.ownKeys`, `Object.getOwnPropertyNames`, `Object.keys`, spread iteration, `for-in`'s own-key pass, `JSON.stringify`):

1. **Integer indices** — strings that canonically represent an integer `0 ≤ i < 2^32−1` (e.g. `"0"`, `"42"`), in **numeric ascending order**.
2. **String keys** — all remaining strings, in **insertion order**.
3. **Symbol keys** — all symbols, in **insertion order**.

```js
const mixed = {};
mixed.b = 1;
mixed["0"] = 2; // integer index "0" — bracketed to show intent
mixed.a = 3;
mixed["2"] = 4;
mixed["1"] = 5;
const symA = Symbol("A"), symB = Symbol("B");
mixed[symA] = 6;
mixed["c"] = 7;
mixed[symB] = 8;

console.log(Object.keys(mixed)); // [ '0', '1', '2', 'b', 'a', 'c' ] — integers sorted, then strings by insertion
console.log(Object.getOwnPropertyNames(mixed)); // same — plus non-enumerable if any
console.log(Reflect.ownKeys(mixed)); // [ '0','1','2','b','a','c', Symbol(A), Symbol(B) ] — symbols appended
for (const k in mixed) console.log(k); // same as Object.keys for own+enumerable (no inherited here)

// Deleting and re-adding moves the key to the end of insertion order
const o = { a: 1, b: 2, c: 3 };
delete o.b;
o.b = 20;
console.log(Object.keys(o)); // [ 'a', 'c', 'b' ] — b reinserted at end

// Numeric strings that are NOT integer indices stay in string-insertion order
const edge = {};
edge["02"] = 1;  // "02" is not a canonical index (leading zero) → string insertion order
edge["1.5"] = 2; // not integer → string order
edge["1"] = 3;   // integer index → sorted before strings anyway
edge["-1"] = 4;  // negative → string order
console.log(Object.keys(edge)); // [ '1', '02', '1.5', '-1' ] — "1" sorted as integer, rest insertion-ordered
```

- *History* — pre-ES2015, order was unspecified; relying on it was a portability bug. Since ES2015 enumeration order is guaranteed; still, never rely on cross-engine string-insertion order for logic correctness when receiving JSON whose key order you don't control — sort explicitly if order matters.
- *Inherited `for-in`*: `for-in` visits enumerable keys on the object **plus** enumerable keys on prototypes (strings only, symbols skipped), walking the chain. Order still respects the same partition per object, chained in prototype-order — and if a prototype key shadows an own key, the own key's position wins and the prototype copy is suppressed.

```js
const base = { inherited: 1, shared: "base" };
const child2 = Object.create(base);
child2.shared = "child"; // owns "shared" — prototype's "shared" suppressed
child2.own = 2;
for (const k in child2) console.log(k);
// own/shared/inherited interleaved — order still integers-first then strings, but own keys visited before probing prototype
console.log(Object.keys(child2)); // [ 'shared', 'own' ] — keys is own-only, base not included
```

### 3) **for-in walks the chain and skips symbols — and why keys + for-of replaced it for data**

`for-in` enumerates string-keyed enumerable inherited properties too. That made it dangerous for arrays (inherited enumerable extensions on `Array.prototype` would appear) and for objects where prototype pollution injected keys. Since ES2015 the safe replacement is `Object.keys(obj) + for-of` for own data, and `Reflect.ownKeys` / `getOwnPropertyNames` / `getOwnPropertySymbols` for full reflection.

```js
// for-in is chain-aware and symbol-blind
const sym = Symbol("s");
const proto = { inherited: 1, [sym]: 2 };
const mine = Object.create(proto);
mine.a = 3;
mine[sym] = 4;
Object.defineProperty(mine, "hidden", { value: 5, enumerable: false });

for (const k in mine) console.log("for-in", k); // a, inherited — symbols and non-enumerable skipped, hidden skipped
console.log(Object.keys(mine)); // [ 'a' ] — own enumerable strings only
console.log(Reflect.ownKeys(mine)); // [ 'a', 'hidden', Symbol(s) ] — all own keys regardless of enumerable/symbol

// Guard rails instead of raw for-in
const data = { x: 1, y: 2, __proto__: "maybe polluted" };
for (const k of Object.keys(data)) console.log(k, data[k]); // safe: only own enumerable strings
console.log(Object.hasOwn(data, "__proto__")); // true only if it was own — not a prototype check

// The array trap for-in caused
Array.prototype.extra = "oops";
const arr = ["a", "b"];
for (const k in arr) console.log(k); // 0 1 extra — inherits prototype enumerable string
delete Array.prototype.extra;
for (const k of arr) console.log(k); // a b — for-of iterates values, not keys
for (const k of Object.keys(arr)) console.log(k); // 0 1 — keys skips prototype
```

| Operation | Own? | Inherited? | Enumerable only? | Symbols? | Order guaranteed? |
|-----------|------|------------|------------------|----------|--------------------|
| `for-in` | yes | yes (strings) | yes | no | yes per ES2015 partition |
| `Object.keys / values / entries` | yes | no | yes (strings) | no | yes |
| `Reflect.ownKeys` / `getOwnPropertyNames` / `getOwnPropertySymbols` | yes | no | no | varies | yes |
| `...spread` / `Object.assign` | yes | no | yes | yes (spread) | yes |
| `JSON.stringify` | yes | no | yes (strings) | no | yes |

- Modern guidance: **default** to `Object.keys`/`entries` + `for-of` for data iteration (own only, no prototype surprise). Use raw `for-in` only when you explicitly want inherited enumerable strings (rare — usually a prototype-walk helper is clearer). Remember `for-in` never exposes symbols; if you need them, use `getOwnPropertySymbols`.

### 4) **Common confusion**

- "`Object.keys` lists all properties" — only enumerable string own keys; non-enumerable, symbol, and inherited keys are invisible. Use `Reflect.ownKeys` for completeness.
- "`for-in` order is random" — not since ES2015; it follows integer→strings→symbols partitions per object, chained.
- "Spread on arrays enumerates indices in insertion order" — arrays are objects with integer-index keys; spread/`assign`/keys follow the same integer-ascending sort.

### 5) **Performance note**

`for-in` that must walk the prototype chain is slower than `Object.keys` on the same object (V8 must probe each prototype). `Reflect.ownKeys` that collects symbols is also slower than string-only `keys`. In hot paths that iterate plain data dictionaries (`Object.create(null)`), `Object.keys` + indexed loop avoids the prototype walk entirely.

### 6) **Mentor note**

Have juniors predict `Object.keys(mixed)` for an object with `"0"`/`"1"` integer keys plus `b`/`a` insertion-order strings — if they put integers first regardless of creation order, the ordering model is solid. In review, flag every raw `for (k in obj)` without `hasOwn` guard — suggest `for (k of Object.keys(obj))` or `for (k in obj) if (Object.hasOwn(obj,k))`.
