## 2.1. Data vs accessor descriptors and attribute defaults

### 1) **Two descriptor families, one slot**

**Definition** — every own property is held as a *property descriptor*: either **data** (`value` + `writable`) or **accessor** (`get` + `set`). Both share **shared attributes** `enumerable` and `configurable`. A property is one family or the other — never both. `writable` means assignment updates the value; `enumerable` means it appears in `for-in`/`keys`/spread; `configurable` means you can delete it or change its family/attributes. Inspect with [getOwnPropertyDescriptor](<./2.2. Defining observing and configuring properties.md>), not by reading the value.

```js
// Data descriptor: value + writable, accessor: get/set
const dataObj = { a: 1 }; // literal installs data descriptor
console.log(Object.getOwnPropertyDescriptor(dataObj, "a"));
// { value: 1, writable: true, enumerable: true, configurable: true }

const accessObj = {
  _x: 1,
  get x() { return this._x; },
  set x(v) { this._x = v; }
};
console.log(Object.getOwnPropertyDescriptor(accessObj, "x"));
// { get: [Function: get x], set: [Function: set x], enumerable: true, configurable: true }

// You cannot mix families — defineProperty will throw TypeError
try {
  Object.defineProperty(dataObj, "b", { value: 2, get() { return 3; } });
} catch (e) { console.log(e.name); } // TypeError

// Accessor without setter is effectively read-only; without getter reads as undefined
const ro = { get now() { return Date.now(); } };
console.log(Object.getOwnPropertyDescriptor(ro, "now").set); // undefined
console.log(ro.now, typeof ro.now); //  ... number — getter runs on every access
try { "use strict"; ro.now = 42; } catch (e) { console.log(e.name); } // TypeError in strict (read-only accessor)
```

- *What problem it solves* — descriptors let objects model more than bags of values: read-only fields (`writable: false`), hidden fields (`enumerable: false`), computed fields (`get`/`set`), and locked shapes (`configurable: false`). Without them every property would be mutable, enumerable, deletable — impossible to build reliable APIs or hide internals.

### 2) **Literal vs defineProperty defaults diverge — the top bug class**

The same four attributes exist everywhere, but **literals default to `true`** (convenient for data) while **`Object.defineProperty` defaults to `false`** (safe for library code that adds one non-enumerable method without leaking). Confusing the two silently creates non-writable/non-enumerable properties that break later assignment or iteration.

```js
// Literal: all true
const lit = { a: 1 };
console.log(Object.getOwnPropertyDescriptor(lit, "a"));
// { value: 1, writable: true, enumerable: true, configurable: true }

// defineProperty with only value: the other three become false
const def = {};
Object.defineProperty(def, "b", { value: 2 });
console.log(Object.getOwnPropertyDescriptor(def, "b"));
// { value: 2, writable: false, enumerable: false, configurable: false }

// Consequence: assignment silently fails in sloppy, throws in strict; enumeration skips it
def.b = 99;
console.log(def.b); // 2 — assignment ignored (sloppy silent)
console.log(Object.keys(def)); // [] — non-enumerable, invisible to keys/for-in/spread
console.log({ ...def }); // {} — spread also skips non-enumerable (→ [2.3](./2.3. Enumerability enumeration order and for-in mechanics.md))

function strictTest() { "use strict"; def.b = 99; }
try { strictTest(); } catch (e) { console.log(e.name); } // TypeError — strict fails loud

// Correct explicit defaults: spell the three booleans when using defineProperty for data
const ok = {};
Object.defineProperty(ok, "c", { value: 3, writable: true, enumerable: true, configurable: true });
console.log(Object.getOwnPropertyDescriptor(ok, "c").enumerable); // true
ok.c = 4;
console.log(ok.c); // 4 — writable
```

| Creation | `writable` | `enumerable` | `configurable` | Typical surprise |
|----------|------------|--------------|----------------|-------------------|
| `{ a: 1 }` or `obj.a = 1` | `true` | `true` | `true` | none |
| `Object.defineProperty(o, k, { value: v })` | `false` | `false` | `false` | future write / iteration silently broken |
| `Object.defineProperty(o, k, { get: fn })` | n/a | `false` | `false` | getter hidden and locked |

- Modern guidance: **never** call `defineProperty` with just `{ value }` for a normal data field — always spell `{ writable: true, enumerable: true, configurable: true }` unless you *intend* non-default behavior. Make intent explicit: `enumerable: false` for internal helpers/methods you don't want serialized, `writable: false` for constants, `configurable: false` only when sealing semantics are wanted (→ [5.1](../5. Integrity and immutability/5.1. Prevent extensions seal freeze and shallow immutability.md>)).

### 3) **Reading the descriptor is the source of truth**

`getOwnPropertyDescriptor` shows the actual installed attributes without invoking a getter (accessing `obj.x` *does* invoke `get`). Use it to audit objects before debugging "why can't I write this key?".

```js
const obj = {};
Object.defineProperties(obj, {
  visible: { value: 1, writable: true, enumerable: true, configurable: true },
  hidden:  { value: 2, enumerable: false, writable: true, configurable: true },
  computed: { get() { return this.visible * 2; }, enumerable: true, configurable: true },
  locked: { value: 3, writable: false, enumerable: true, configurable: false }
});

for (const k of ["visible", "hidden", "computed", "locked"]) {
  console.log(k, Object.getOwnPropertyDescriptor(obj, k));
}
console.log(Object.keys(obj)); // [ 'visible', 'computed', 'locked' ] — hidden skipped
console.log(obj.computed); // 2 — getter ran, value is live computation, not stored

// Descriptor query does NOT invoke getter; reading does
let calls = 0;
const spy = { get x() { calls += 1; return 1; } };
console.log(Object.getOwnPropertyDescriptor(spy, "x").get); // function — not invoked
console.log(calls); // 0
console.log(spy.x); // 1 — invocation happens here
console.log(calls); // 1

// Whole-object snapshot (ES2017)
console.log(Object.getOwnPropertyDescriptors(obj)); // { visible: {…}, hidden: {…}, … }
```

### 4) **Common confusion**

- "`obj.a = 1` and `defineProperty(obj, 'a', { value: 1 })` are the same" — no; the former gives `true/true/true`, the latter `false/false/false`. After the second form, later assignment and `Object.keys` will mysteriously fail.
- "Accessor `get` without `set` makes a constant" — read-only, yes, but not constant: the getter runs on every access and can return different values (think `get now() { return Date.now(); }`).
- "`writable: false` prevents delete" — no; `writable` guards *assignment*; `configurable: false` guards *delete* and descriptor changes. Locking both is how `freeze` works (→ [5.1](../5. Integrity and immutability/5.1. Prevent extensions seal freeze and shallow immutability.md>)).

### 5) **Performance note**

Descriptor queries are slow-path (C++ handle). Don't call `getOwnPropertyDescriptor` in hot loops to test existence — use `hasOwn`/`in` (→ [4.2](../4. Object utilities and copying/4.2. Keys values entries hasOwn and reflection APIs.md>)). Installing many non-configurable/non-writable properties at startup is free; doing `defineProperty` per-frame is not — the JIT can't inline property access for objects whose shape is mutated via descriptors (shape transitions deopt — see [JIT](<../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md>)).

### 6) **Mentor note**

Give juniors an object created half with literals and half with `defineProperty({ value })` and ask why `Object.keys` "loses" half the keys — the answer is the default `enumerable: false` trap. In review, flag any `defineProperty` with only `value` or only `get` that doesn't spell `enumerable` — require explicit choice. Prefer a literal or a small helper `addHidden(obj, k, v)` that documents intent.
