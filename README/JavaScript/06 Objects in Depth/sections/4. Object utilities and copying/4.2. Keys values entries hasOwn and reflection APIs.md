## 4.2. Keys, values, entries, hasOwn, and reflection APIs

### 1) **keys / values / entries — enumerable string keys only**

**Definition** — `Object.keys(obj)` returns an array of **enumerable own string-key** names; `Object.values` and `Object.entries` return corresponding values/pairs in the same [enumeration order](<../2. Properties and descriptors/2.3. Enumerability enumeration order and for-in mechanics.md>) (integers ascending → strings insertion → *symbols excluded*). All three skip non-enumerable, symbol, and inherited keys. They are the workhorse for iterating the "data surface" — the part that serializes via `JSON.stringify` and `...spread`.

```js
const base = { inherited: 99 };
const obj = Object.create(base);
Object.defineProperties(obj, {
  a: { value: 1, enumerable: true },
  b: { value: 2, enumerable: true },
  hidden: { value: 3, enumerable: false },
  [Symbol("s")]: { value: 4, enumerable: true }
});

console.log(Object.keys(obj)); // [ 'a', 'b' ] — strings only, enumerable own, insertion order
console.log(Object.values(obj)); // [1, 2]
console.log(Object.entries(obj)); // [ ['a',1], ['b',2] ]
for (const [k,v] of Object.entries(obj)) console.log(k,v); // a 1 / b 2

// Missing: hidden non-enumerable, symbol, inherited — use reflection APIs for those
console.log(Object.getOwnPropertyNames(obj)); // [ 'a', 'b', 'hidden' ] — strings incl. non-enumerable, still own only
console.log(Object.getOwnPropertySymbols(obj)); // [ Symbol(s) ]
console.log(Reflect.ownKeys(obj)); // [ 'a','b','hidden', Symbol(s) ] — all own keys regardless of enumerable
console.log("inherited" in obj); // true — in walks chain (→ [3.1](../3. Prototype linkage intro/3.1. The prototype chain getPrototypeOf setPrototypeOf and Object.create.md>))
console.log(Object.keys(obj).includes("inherited")); // false — own only

// keys/values/entries respect enumeration order partitions
const ordered = {};
ordered.b = 1;
ordered["0"] = 2;
ordered.a = 3;
console.log(Object.keys(ordered)); // [ '0', 'b', 'a' ] — integer "0" sorted first
```

- *Bad vs good* — raw `for (k in obj)` mingles inherited enumerable strings (→ [2.3](<../2. Properties and descriptors/2.3. Enumerability enumeration order and for-in mechanics.md>)); `for (k of Object.keys(obj))` is own-only and safe for data. Prefer entries + destructuring for key+value loops — no separate `obj[k]` lookup needed.

### 2) **Object.hasOwn vs hasOwnProperty vs in — own vs inherited, string vs symbol, and the Object.create(null) pitfall**

Three distinct questions:

| API | Own? | Inherited? | Symbols? | Fails on null-proto? |
|-----|------|------------|----------|----------------------|
| `Object.hasOwn(obj, k)` (ES2022) | yes | no | yes | no — safe for `Object.create(null)` |
| `obj.hasOwnProperty(k)` | yes | no | depends on call target | **yes** — `null`-proto objects have no method |
| `k in obj` | yes | yes | yes | no (but conflates) |
| `Reflect.has(obj,k)` | yes | yes | yes | no — alias of `in` |
| `Object.hasOwnProperty.call(obj,k)` | yes | no | yes | no — workaround |

```js
const proto = { inherited: 1 };
const dict = Object.create(proto);
dict.own = 2;
dict[Symbol("s")] = 3;

console.log("inherited" in dict); // true — in checks entire chain
console.log(Reflect.has(dict, "inherited")); // true — same
console.log(Object.hasOwn(dict, "inherited")); // false — own only
console.log(Object.hasOwn(dict, "own")); // true
console.log(Object.hasOwn(dict, Symbol.for("x"))); // false — different symbol identity

// The classic hasOwnProperty trap on null-prototype dictionaries
const safe = Object.create(null);
safe.x = 1;
safe.y = 2;
console.log(Object.hasOwn(safe, "x")); // true — works
try { console.log(safe.hasOwnProperty("x")); } catch (e) { console.log(e.name); } // TypeError — no prototype to inherit method
console.log(Object.prototype.hasOwnProperty.call(safe, "x")); // true — borrow pattern (pre-ES2022)
console.log(Object.hasOwn(safe, "x")); // true — preferred since ES2022

// __proto__ key confusion (string key vs prototype link — → [1.2](../1. Object creation and literals/1.2. Creation patterns literal Object create and constructors.md))
const tricky = {};
tricky["__proto__"] = 123;
console.log(Object.hasOwn(tricky, "__proto__")); // true — own string key via bracket
console.log(Object.getPrototypeOf(tricky) === Object.prototype); // true — not a link (literal computed assignment isn't literal __proto__ syntax)
const withLiteralProto = { __proto__: { wired: true } };
console.log(Object.getPrototypeOf(withLiteralProto).wired); // true — literal __proto__ DOES wire

// Symbol keys round-trip through hasOwn/Reflect but not through plain keys
const sym = Symbol("id");
const container = { [sym]: 99 };
console.log(Object.hasOwn(container, sym)); // true
console.log(Object.keys(container).includes(sym)); // false — keys excludes symbols
console.log(Reflect.ownKeys(container).includes(sym)); // true
```

- Modern guidance: **always** use `Object.hasOwn(obj, k)` for own checks (ES2022 baseline is widely available as of 2026). Lint `obj.hasOwnProperty` → `Object.hasOwn` (ESLint `prefer-object-has-own`, Unicorn). Use `in` only when you deliberately want inherited checks (rare — usually you're probing the prototype chain itself → [3.1](<../3. Prototype linkage intro/3.1. The prototype chain getPrototypeOf setPrototypeOf and Object.create.md>)).

### 3) **is vs === for object-adjacent checks**

**Definition** — `Object.is(a, b)` follows SameValue (as `===` but with `Object.is(NaN, NaN) === true` and `Object.is(0, -0) === false`). For object *values* there is no distinction — both test reference identity. `is` matters only for numeric edge cases that leak through boxed comparisons or map keys.

```js
// Object references — both test identity
const o1 = {}, o2 = {};
console.log(o1 === o2); // false — different references
console.log(Object.is(o1, o2)); // false
console.log(o1 === o1); // true
console.log(Object.is(o1, o1)); // true

// Where === and is diverge — numeric edges (→ [Values §2.2](<../../../03 Values Types and Coercion/sections/2. The conversion algorithms/2.2. ToString and ToNumber the exact conversion tables.md>))
console.log(NaN === NaN); // false
console.log(Object.is(NaN, NaN)); // true
console.log(0 === -0); // true — === conflates zeros
console.log(Object.is(0, -0)); // false — SameValue distinguishes

// Practical uses: dedup/caching where -0 vs 0 or NaN matters
const seen = new Set();
seen.add(NaN);
console.log(seen.has(NaN)); // true — Set uses SameValueZero (NaN counts, -0/+0 conflated)
console.log(Object.is(0, -0)); // false — but Set considers them equal

// Choosing for reflection: hasOwn/in don't care about is vs ===; neither does keys ordering
console.log(Object.hasOwn({ "0": 1, "-0": 2 }, "0")); // true — keys are strings; numeric is vs === irrelevant except via Number keys path
console.log(Object.keys({ "0": 1 })[0] === "0"); // true — string key

// Full reflection table for completeness
const full = {};
Object.defineProperties(full, {
  plain: { value: 1, enumerable: true },
  hidden: { value: 2, enumerable: false },
  [Symbol("s")]: { value: 3, enumerable: true }
});
console.log(Object.keys(full)); // [ 'plain' ] — data surface
console.log(Object.getOwnPropertyNames(full)); // [ 'plain', 'hidden' ] — all string own
console.log(Object.getOwnPropertySymbols(full)); // [ Symbol(s) ]
console.log(Reflect.ownKeys(full)); // [ 'plain', 'hidden', Symbol(s) ] — all own
console.log(Object.getOwnPropertyDescriptors(full)); // descriptor map — non-invoking inspection (→ [2.2](<../2. Properties and descriptors/2.2. Defining observing and configuring properties.md>))
```

- *Cross-language perf note* — `Object.is` itself is a single branch; no cost concern. The bigger distinction is `Map` vs plain object for numeric/symbol keys: `Map` preserves `0` vs `-0` per SameValueZero and accepts object keys without stringification; plain object stringifies.
- Modern guidance: default to `===` for everyday equality; reach for `Object.is` only when code explicitly cares about `NaN` self-equality or `-0` vs `0` (DSP, serialization dedup, or a test assertion like `expect(a).toBe(b)` vs `toEqual`). Never use `Object.is` to "compare objects deeply" — it still checks reference only.

### 4) **Common confusion**

- "`Object.keys` includes symbols" — no; string keys only. Symbols require `getOwnPropertySymbols` or `Reflect.ownKeys`.
- "`obj.hasOwnProperty` is the safe own check" — not on `Object.create(null)`; `Object.hasOwn` is the ES2022 replacement.
- "`in` means own" — `in` walks the chain; `hasOwn`/`hasOwnProperty` are own-only. Conflating them hides prototype leakage.
- "`Object.is` deep-compares objects" — no; reference only. Deep equality requires a recursive walk (or `assert.deepStrictEqual` in Node).

### 5) **Performance note**

`Object.keys` that allocates an array per call is fine off hot path but avoid it inside a tight per-frame loop over many small objects — intern a keys array. `Reflect.ownKeys` that also collects non-enumerable + symbols is slower and rarely needed for data. As ever, [measure](<../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md>).

### 6) **Mentor note**

Give juniors an object with `hidden` non-enumerable, an inherited enumerable `inherited`, and a symbol key, plus a `null`-proto dict, and ask them to predict `keys`, `getOwnPropertyNames`, `Reflect.ownKeys`, `hasOwn`, and `in` for each key. If they place every key correctly, the own/enumerable/symbol/inherited matrix is solid. In review, grep `\.hasOwnProperty\(` and `for (.. in` — suggest `Object.hasOwn` and `Object.keys`+`for-of`.
