## 3.1. The prototype chain: getPrototypeOf, setPrototypeOf, Object.create, and __proto__

### 1) **Every object has an internal [[Prototype]] — or null**

**Definition** — each ordinary object carries an internal slot `[[Prototype]]` that is either another object or `null`, set at birth and walked on property lookup (and by `in`, `instanceof`, `Object.hasOwn` vs prototype checks). When `obj.x` misses on `obj`, the engine checks `[[Prototype]]`, then *that* object's `[[Prototype]]`, until `null` — returning `undefined` if never found. `__proto__` is not the mechanism; it's a legacy accessor on `Object.prototype` that reflects `[[Prototype]]` for historical code.

```js
// Prototype chain in action
const grand = { a: 1 };
const parent = Object.create(grand);
parent.b = 2;
const child = Object.create(parent);
child.c = 3;

console.log(child.c); // 3 — own
console.log(child.b); // 2 — one hop
console.log(child.a); // 1 — two hops via grand
console.log(child.toString); // function — reaches Object.prototype (parent of grand since grand's proto is Object.prototype)
console.log(Object.getPrototypeOf(child) === parent); // true
console.log(Object.getPrototypeOf(parent) === grand); // true
console.log(Object.getPrototypeOf(grand) === Object.prototype); // true
console.log(Object.getPrototypeOf(Object.prototype)); // null — terminus
console.log(child.d); // undefined — chain exhausted

// in vs hasOwn vs getOwnProperty: own vs inherited distinction
console.log("a" in child); // true — in walks the chain
console.log(Object.hasOwn(child, "a")); // false — own only (ES2022)
console.log(child.hasOwnProperty("a")); // false — same but breaks on null-proto (→ [1.2](../1. Object creation and literals/1.2. Creation patterns literal Object create and constructors.md))
console.log(Object.hasOwn(child, "c")); // true — own

// Shadowing: own key suppresses prototype key; prototype key not duplicated in enumeration
const proto2 = { x: 10, y: 20 };
const o = Object.create(proto2);
o.x = 99; // own "x" shadows proto's "x"
console.log(o.x); // 99 — own wins
console.log(Object.getOwnPropertyDescriptor(proto2, "x").value); // 10 — proto unchanged
for (const k in o) console.log(k); // x (own) — y? y is inherited enumerable, so for-in visits y too (→ [2.3](../2. Properties and descriptors/2.3. Enumerability enumeration order and for-in mechanics.md))
console.log(Object.keys(o)); // [ 'x' ] — keys is own only, so y not listed

// null prototype ends the chain immediately
const bare = Object.create(null);
bare.a = 1;
console.log(Object.getPrototypeOf(bare)); // null
console.log("toString" in bare); // false — no Object.prototype delegation
try { bare.toString(); } catch (e) { console.log(e.name); } // TypeError — method not inherited
console.log(Object.prototype.toString.call(bare)); // [object Object] — borrow works
```

- *What problem it solves* — prototypes give sharing: methods live once on the prototype, instances delegate to them. Without the chain every instance would copy every method (factory pattern's cost) or require manual dispatch.

### 2) **Creation fixes the link**

`[[Prototype]]` is wired once at construction; mutating it later is possible but deoptimizes (engines cache hidden classes keyed by prototype). Three creation sites set it correctly:

```js
// A) Literal __proto__ — single spec-mandated link site at birth (not a plain key)
const base = { greet() { return "base"; } };
const lit = { __proto__: base, x: 1 };
console.log(Object.getPrototypeOf(lit) === base); // true
console.log(lit.greet()); // base — delegated
// Computed ["__proto__"] in same literal is a plain data key — NOT a link (→ [1.2](../1. Object creation and literals/1.2. Creation patterns literal Object create and constructors.md))
const notLinked = { ["__proto__"]: base, x: 1 };
console.log(Object.getPrototypeOf(notLinked) === Object.prototype); // true — default, not base
console.log(notLinked["__proto__"] === base); // true — string key named "__proto__"

// B) Object.create(proto, descriptors?) — explicit and most readable for link-control
const linked = Object.create(base, {
  y: { value: 2, writable: true, enumerable: true, configurable: true }
});
console.log(Object.getPrototypeOf(linked) === base); // true
console.log(linked.y); // 2 — own

// C) new Constructor() — prototype from Constructor.prototype (deep dive → Prototypes and Classes forward ref)
function Ctor(n) { this.n = n; }
Ctor.prototype.inc = function () { return this.n + 1; };
const inst = new Ctor(5);
console.log(Object.getPrototypeOf(inst) === Ctor.prototype); // true
console.log(inst.inc()); // 6

// Post-creation mutation paths (slow — avoid in hot code)
const a = { a: 1 };
Object.setPrototypeOf(a, base); // standardized mutator — works, but forces deopt
console.log(Object.getPrototypeOf(a) === base); // true
a.__proto__ = null; // legacy accessor — also mutates (and is forbidden in null-proto objects where accessor missing)
console.log(Object.getPrototypeOf(a)); // null
// Perf axiom: set at birth, never rewire.
```

| Site | Form | Cost | When to choose |
|------|------|------|----------------|
| Literal | `{ __proto__: p, ... }` | fast (birth) | one-off record delegating to known `p` |
| `Object.create` | `Object.create(p, desc?)` | fast (birth) | dictionary/branch creation, explicit |
| `new` | `new F()` | fast (birth) | constructor pattern with shared `F.prototype` |
| Mutators | `setPrototypeOf` / `__proto__=` | **slow** (deopt) | migration/legacy only; never in loop |

### 3) **Prototype vs prototype property — the classic confusion**

Objects *have* `[[Prototype]]`; functions *have* a `prototype` property that `new` uses as the `[[Prototype]]` for fresh instances. Confusing the two collapses creation and delegation.

```js
// Function's .prototype is the TEMPLATE for instances' [[Prototype]]
function Dog(name) { this.name = name; }
Dog.prototype.bark = function () { return this.name + " woof"; };
const d = new Dog("rex");
console.log(Object.getPrototypeOf(d) === Dog.prototype); // true
console.log(Dog.prototype === d.__proto__); // true-ish — __proto__ reflects [[Prototype]]
console.log(Dog.__proto__ === Function.prototype); // true — functions' [[Prototype]] is Function.prototype (functions are objects too)
console.log(typeof Dog.prototype); // object — just a plain object until constructor assigns it
console.log(Dog.prototype.bark); // function — shared method

// Reassigning Function.prototype affects FUTURE instances, not past ones
Dog.prototype = { howl() { return "howl"; } };
const d2 = new Dog("bob");
console.log(typeof d.bark); // function — d still linked to OLD prototype
console.log(typeof d.howl); // undefined
console.log(typeof d2.howl); // function — d2 linked to new prototype
console.log(d instanceof Dog); // false — instanceof walks current Dog.prototype, d's chain still holds old object
// Hence: never replace .prototype after instances exist; mutate it or create a fresh constructor.

// Objects' [[Prototype]] vs function prototype — naming trap
const obj = {};
console.log(Object.getPrototypeOf(obj) === Object.prototype); // true — object's [[Prototype]] is Object.prototype
console.log(Object.prototype instanceof Object); // false — instanceof needs a function on the left; Object.prototype is not an instance
console.log(obj.prototype); // undefined — plain objects don't have .prototype (only functions do)
```

- *Common bug* — `obj.prototype` is `undefined`; `Object.getPrototypeOf(obj)` is the link. `Func.prototype` is not `Func`'s prototype — `Object.getPrototypeOf(Func)` is.

### 4) **Common confusion**

- "`__proto__` is the prototype" — `[[Prototype]]` is the slot; `__proto__` is a getter/setter on `Object.prototype` that proxies it. `Object.getPrototypeOf` is the canonical read; `Object.setPrototypeOf` the canonical (slow) write; `Object.create` the canonical creation.
- "`obj.__proto__ = p` always works" — not on `Object.create(null)` objects (they lack the accessor). Use `Object.setPrototypeOf` if you must mutate.
- "Setting `__proto__` in a literal always links" — only the literal key `__proto__: value` does; computed `["__proto__"]` or spread does not (it creates a data property named `"__proto__"`).
- "`instanceof` checks the object's type" — it checks whether `Constructor.prototype` appears in the object's prototype chain at call time — so reassigned prototypes break it.

### 5) **Performance note**

Prototype chain length directly scales property-miss cost (engine must walk hops). Keep chains shallow (1–2 hops) for data objects; reserve deep chains for class hierarchies where method sharing outweighs miss cost. Mutating `[[Prototype]]` after birth forces a megamorphic re-layout in V8 — orders of magnitude slower than creating with the right link. ### 6) **Mentor note**

Have trainees explain `new Dog()` in three steps: allocate object whose `[[Prototype]]` is `Dog.prototype`, call `Dog` with that object as `this`, return `this` (or explicit object). If they can diagram `d` → `old Dog.prototype` → `Object.prototype` → `null` vs `Dog` → `Function.prototype` → `Object.prototype` → `null`, the two kinds of prototype are distinct. In review, flag every `setPrototypeOf`/`__proto__=` on a hot path — suggest `Object.create` at birth.
