## 1.2. Temporal dead zone: why early access throws

### 1) **Declared-but-not-ready: the zone between scope entry and initialization**

**Definition** — when execution enters a scope, every `let`, `const`, and `class` name in it is *registered immediately* but stays *uninitialized* until its declaration line runs. The window between those two moments is the **temporal dead zone (TDZ)**; touching the binding there throws:

```js
function demo() {
  try { console.log(later); }
  catch (e) { console.log(e.name, "|", e.message); }
  // ReferenceError | Cannot access 'later' before initialization
  let later = "ready";   // ← the line that ends the TDZ
  return later;
}
console.log(demo());     // ready

// var has no TDZ — it starts initialized to undefined:
console.log(oldStyle);   // undefined (silent!)
var oldStyle = 1;
```

- It is called *temporal* deliberately: the zone is about **when code runs**, not where lines sit. A function defined earlier can read a `let` safely as long as it is *called* after the declaration line executed:

```js
function readLater() { return later2; } // definition alone touches nothing
let later2 = 42;
console.log(readLater());               // 42 — call happens after initialization
```

- `class` declarations live in the TDZ too — unlike old constructor functions, using one before its line never silently returns a broken value:

```js
try { new C(); }
catch (e) { console.log(e.name, "|", e.message); }
// ReferenceError | Cannot access 'C' before initialization
class C { constructor() { this.ok = true; } }
console.log(new C().ok);                // true — after the line, all good
```

### 2) **Even `typeof` throws inside a TDZ**

The famous `typeof` safety net covers only identifiers that don't exist anywhere. A TDZ name *does* exist — it's just not initialized yet — so the usual trick reports nothing:

```js
function t() {
  try { typeof hidden; }
  catch (e) { console.log(e.name, "|", e.message); }
  // ReferenceError | Cannot access 'hidden' before initialization
  let hidden = 1;
}
t();

console.log(typeof neverDeclared);      // undefined — only UNDECLARED names get this mercy
```

- Same for all other operations: assignment, `delete`, even passing it as an argument — any evaluation of the identifier in the zone throws.

### 3) **Why the TDZ exists: fail-fast beats silent garbage**

Before ES2015, reading too early produced `undefined`, which flowed onward until it detonated far from the cause (`undefined + 1` → NaN → corrupted report — see the coercion bug catalog in the [Values domain](<../../../03 Values Types and Coercion/sections/7. Common pitfalls to production bugs/7.1. Real production bugs caused by coercion.md>)). The TC39 design turns that into an immediate, correctly located error. Two consequences worth internalizing:

- **Self-reference is now caught**: `let x = x + 1;` throws instead of yielding NaN.
- **Shadowing becomes honest**: once an inner scope declares its own binding, references from *scope entry* onward mean the inner one — so early reads fail loudly rather than quietly grabbing the outer value:

```js
let outer = 1;
{
  try { console.log(outer); }           // you might expect 1…
  catch (e) { console.log(e.name, "|", e.message); }
  // ReferenceError | Cannot access 'outer' before initialization
  let outer = 2;                        // …because THIS owns the whole block scope
  console.log("inner:", outer);
}
```

### 4) **Common confusion**

- "TDZ means hoisting doesn't happen" — backwards. The binding *is* created at scope entry (that's precisely why accessing it can throw a targeted error instead of resolving outward or globally). Only *initialization* waits.
- "`const` needs its value at compile time" — it needs its initializer *executed*; conditional/derived initializers are perfectly legal (`const size = input.length ?? 0`).
- Parameter lists have their own mini-scope ahead of the body: `function f(a = b, b = 2) {}` throws on `f()` (evaluating `a`'s default reads `b` before its initializer runs) but works on `f(1)` ([verified](#6-mentor-note)) — rare in practice, beloved by interviewers.
- TDZ errors are *runtime* ReferenceErrors, not SyntaxErrors — they surface only when the offending line actually executes, which is why dead branches can hide them.

### 5) **Performance note**

TDZ checks are statically analyzable: engines prove at parse time whether a use can precede initialization and emit the check only where uncertainty remains, so the common case costs nothing after compilation. Never trade correctness for imagined TDZ overhead — [measure, don't guess](<../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md>).

### 6) **Mentor note**

Teach the two-step mantra — *"declaration registers, initialization arms"* — and the TDZ stops feeling arbitrary. In review: after any refactor that moves declarations below their first use, run the tests (the ReferenceError fires only on the executed path); enable ESLint `no-use-before-define` to catch it statically.
