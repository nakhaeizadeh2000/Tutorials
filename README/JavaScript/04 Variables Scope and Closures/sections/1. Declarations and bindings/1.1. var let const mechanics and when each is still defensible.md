## 1.1. var, let, const: mechanics and when each is still defensible

### 1) **Three declarators, three contracts**

**Definition** — a *declaration* creates a binding (a named slot for a value) in a scope. The declarator you pick decides the binding's scope, whether it can be redeclared, and when it becomes usable:

| | `var` | `let` | `const` |
|---|-------|-------|---------|
| Scope | enclosing **function** (or global) | enclosing **block** | enclosing **block** |
| Redeclaration in same scope | allowed | SyntaxError | SyntaxError |
| Usable before its line | yes (`undefined`) | no (TDZ → [1.2](<./1.2. Temporal dead zone why early access throws.md>)) | no (TDZ) |
| Requires initializer | no | no | **yes** |
| Reassignment | allowed | allowed | TypeError |
| Becomes `globalThis` property at top level (scripts) | yes | no | no |

```js
function readBoth() {
  if (true) {
    var x = 1;   // belongs to the FUNCTION — blocks are invisible to var
    let y = 1;   // belongs to this BLOCK
  }
  console.log(x);                    // 1 — survived the block
  try { console.log(y); }            // y does not exist at function level
  catch (e) { console.log(e.name); } // ReferenceError
}
readBoth();

var status_ = "draft";
var status_ = "published";           // legal: var redeclares itself silently
console.log(status_);                // published

let retries = 3;
{
  let retries = 9;                   // different scope: shadowing, not redeclaring
  console.log(retries);              // 9
}
console.log(retries);                // 3
```

- The block-scoping row is the whole modernization story: pre-ES2015, every `var` floated to the top of its function, so an `if`/loop block could never contain a variable privately.

### 2) **`const` freezes the binding, never the value**

```js
const MAX = 10;
try { MAX = 11; }
catch (e) { console.log(e.name, e.message); } // TypeError Assignment to constant variable.
// const EMPTY;        // SyntaxError: Missing initializer in const declaration

const user = { name: "ada" };
user.name = "grace";                 // mutation of the OBJECT — binding untouched
console.log(user.name);              // grace

const [head] = [1, 2, 3];            // destructuring satisfies the initializer rule
const { id = 0 } = {};               // defaults count too
console.log(head, id);               // 1 0
```

- Read the error message literally: *assignment to constant variable* — only reassignment is refused. Actual immutability needs `Object.freeze` or immutable data structures ([copying and identity](<../../../03 Values Types and Coercion/sections/1. The value model/1.2. Immutability identity and copying how primitives and objects differ.md>)).
- Destructuring declarations (`const [a, b] = pair`) follow `const` rules as a group: legal once, never reassigned wholesale.

### 3) **Modern guidance: default `const`, escalate to `let`, retire `var`**

```js
// const signals "this name will never point elsewhere" — readers skim past it:
const baseUrl = "https://api.example.com";

// let only where rebinding is the actual mechanism (counters, swaps, reassignment):
let attempt = 0;
while (++attempt < 3) { /* ... */ }
console.log(attempt);
```

- Why default `const`: it converts "did anything else rebind this?" from a question into a guarantee, which matters most in larger functions and shared modules. It is documentation the compiler enforces.
- Where `var` remains defensible: legacy codebases that haven't migrated (consistency within old files), transpile targets that must emit ES5 verbatim, and quick REPL scratch work. None justify `var` in new production code.
- Loop heads have their own per-iteration contract: `for (const ch of …)` is legal because each iteration gets a fresh binding, while `for (const i = 0; …; i++)` throws because the classic `for` *reassigns* one counter — full mechanics in [3.2](<../3. Closures/3.2. Loops and closures var let and per iteration capture.md>).

### 4) **Common confusion**

- "`const` makes objects immutable" — see §2; it makes *rebinding* impossible, nothing more.
- "`var x` inside `{}` is private to the block" — no; only functions (and modules) bound `var`. This single fact explains most pre-2015 closure bugs.
- Shadowing vs redeclaration — same name in a *nested* scope is fine (shadowing); same name twice in the *same* `let`/`const` scope is a SyntaxError caught before any code runs.
- Multiple declarators share rules per keyword: `let a = 1, b = 2;` is one declaration with two bindings — lint style usually prefers one per line.

### 5) **Performance note**

After parsing, engines treat all three identically: a binding is a stack/context slot, and `const`'s guarantee rarely changes generated code (JITs prove non-reassignment themselves in hot paths). The wins from `const` are correctness and review speed, not nanoseconds — [measure, don't guess](<../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md>).

### 6) **Mentor note**

Enforce mechanically so reviews stop debating taste: ESLint `prefer-const` + `no-var` make the default real. In review, the signal to screen for isn't "did they use `const` everywhere" but *do they know why the mutable ones are mutable* — ask what would break if a given `let` became `const`; a blank stare means the rebinding path isn't understood.
