## 2.2. Hoisting: the reality — creation phase, not magic

### 1) **Nothing moves; initialization timing differs per declarator**

**Definition** — "hoisting" is the folk name for a two-phase execution model: when a scope is *entered*, all its declarations are registered (**creation phase**); then code runs top-to-bottom (**execution phase**), and each declarator decides what its binding holds at phase one:

| Declared with | At scope entry | Before its line | After |
|---|---|---|---|
| `function f() {}` (declaration) | created **and initialized** | fully callable | callable |
| `var` | created, value `undefined` | readable `undefined` — silent bug fuel | assigned |
| `let` / `const` / `class` | created, uninitialized | TDZ → throws ([1.2](<../1. Declarations and bindings/1.2. Temporal dead zone why early access throws.md>)) | assigned |

```js
console.log(early());          // ready — callable from scope entry
function early() { return "ready"; }

console.log(oldVar);           // undefined — exists, empty
var oldVar = 1;

try { console.log(newLet); }
catch (e) { console.log(e.name); } // ReferenceError — exists, locked
let newLet = 1;
```

- The accurate mental model replaces "declarations get moved to the top": nothing relocates; only *when each name becomes usable* differs. This matters because side effects stay in place — a function declaration's body never runs early, it merely becomes callable.

### 2) **Function expressions follow variable rules**

Only declarations hoist as functions. An expression assigns a function *value* to an ordinary variable, so the variable's declarator governs:

```js
console.log(typeof varExpr);   // undefined — variable hoisted, function not born yet
var varExpr = function () { return 1; };

try { console.log(typeof letExpr); }
catch (e) { console.log(e.name); } // ReferenceError — letExpr sits in TDZ
let letExpr = () => 2;

// Named function expression: the name exists ONLY inside the function itself
const countdown = function fact(n) { return n <= 1 ? 1 : n * fact(n - 1); };
console.log(countdown(5));     // 120 — recursion via the inner name
try { console.log(fact); }
catch (e) { console.log(e.name); } // ReferenceError — invisible outside
```

- Consequence: "call it before you define it" works for declarations, explodes for expressions. Modern style sidesteps the whole class of question by declaring before use regardless ([checklist](<../5. Important points to remember/5.1. Scope checklist reflex rules mentors screen for.md>)).

### 3) **Function declarations inside blocks: mode-dependent minefield**

ES2015 made in-block declarations block-scoped under strict mode; Annex B of the spec then re-added legacy behavior for sloppy mode so old pages kept working. The result diverges by mode — verified on Node v22:

```js
function strictBlock() {
  "use strict";
  {
    console.log(inBlock());            // strict block fn — hoisted within the BLOCK
    function inBlock() { return "strict block fn"; }
  }
  try { inBlock(); }
  catch (e) { console.log("outer after block:", e.name); } // ReferenceError — gone
}
strictBlock();

function sloppyBlock() {
  console.log("before block:", typeof annexC);  // undefined — outer binding not yet assigned
  {
    console.log("inside block pre-line:", typeof annexC); // function — block-local hoist
    function annexC() {}
  }
  console.log("outside block:", typeof annexC); // function — Annex B leaks it out AFTER the block
}
sloppyBlock();
```

- Conditional declarations are worse: in strict mode an untaken branch leaves no usable name (`typeof` → ReferenceError); in sloppy mode Annex B still creates the outer binding but never assigns it (`typeof` → `"undefined"`; *calling* it throws TypeError). Same source, different failure.
- Guidance: never declare functions inside blocks. If you need conditional behavior, assign a function expression in the branch — explicit, mode-independent, reviewable.

### 4) **Common confusion**

- "`var x = …` below its use is fine because var hoists" — it runs without throwing and silently computes with `undefined`, which is precisely the bug class the TDZ was invented to kill ([coercion fallout](<../../../03 Values Types and Coercion/sections/7. Common pitfalls to production bugs/7.1. Real production bugs caused by coercion.md>)).
- Conflicting declarations in the same scope (`let` twice, or `function` vs `let`) are SyntaxErrors detected at parse time — even if the code sits in a branch that never executes. Duplicate `function` declarations don't error: last one wins.
- Load order at program start: imports initialize first, then module/script bodies run their creation+execution phases ([modules domain](<../../../14 Modules and Code Organization/README.md>) — textual forward reference until that domain lands).
- "Arrow functions hoist differently" — arrows are expressions like any other; only their assigned variable's declarator matters.

### 5) **Performance note**

Creation-phase registration happens once per scope entry and is essentially free; there is no runtime penalty for declaring functions after use *if* calls happen later — engines resolve bindings through fixed context slots, not repeated searching ([2.1](<./2.1. Lexical scope and the scope chain how name lookup works.md>)). The cost of relying on hoisting is human: readers must simulate the compiler to know what's defined where.

### 6) **Mentor note**

Kill the phrase "JavaScript moves your code up." Teach the table instead — juniors memorize three rows and stop writing bugs; seniors learn that Annex B exists and choose strict/module code so it never applies. Review rule: `no-use-before-define` on, and any function declaration nested deeper than function level gets rewritten on sight.
