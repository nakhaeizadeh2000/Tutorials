## 2.1. Lexical scope and the scope chain: how name lookup works

### 1) **Scope is decided by where code is written, not where it runs**

**Definition** — *lexical scoping* means every function's visible variables are fixed by its physical nesting in the source at parse time. Where a function is later *called* is irrelevant:

```js
function makeInner() {
  const label = "outer";                        // inner's birthplace
  return function inner() { return label; };
}
function callerScope() {
  const label = "caller";                       // exists at CALL time…
  const fn = makeInner();
  return fn();                                  // …and is invisible to inner
}
console.log(callerScope());                     // outer
```

- Languages with *dynamic* scope would print `caller` here; JavaScript never does. If you've met shell scripting or CSS cascade intuition ("nearest active context wins"), unlearn it for variable resolution — only the nesting of the *definition* matters.
- This single rule is what makes closures possible: `inner` carries its birthplace's variables wherever it goes ([3.1](<../3. Closures/3.1. Closures functions that remember their birth environment.md>)).

### 2) **Lookup walks outward and stops at the first match**

When a name is evaluated, the engine searches the current scope, then the enclosing one, and so on up to the global level. The **first** binding found wins (*shadowing*); nothing found anywhere → `ReferenceError`:

```js
const level = "global";
{
  const level = "block";
  console.log(level);                          // block — nearest match wins
}
console.log(level);                            // global

function len(x) { return x.length; }           // a function is just another binding
{
  const len = (n) => n * 2;
  console.log(len(21));                        // 42 — shadowed by the local
}

try { console.log(missingName); }
catch (e) { console.log(e.name, "|", e.message); }
// ReferenceError | missingName is not defined
```

- Shadowing is a tool, not an accident: loop counters, parameters, and short-lived locals may reuse common names safely because their scopes are narrow ([checklist](<../5. Important points to remember/5.1. Scope checklist reflex rules mentors screen for.md>)). It turns hostile when the scopes are wide and the names identical by coincidence — reviewers flag same-name-different-scope pairs spanning many screens.
- What creates scopes: **modules** (one big scope each), **functions** (parameters + everything declared inside), **blocks** `{}` attached to `if`/`for`/`while`, bare blocks, class bodies, `switch` clauses, and **catch clauses** (`catch (err)` binds per-clause). Notably NOT: `if` without braces' implicit statements, object literals, or `case:` labels alone.

### 3) **The global level has two layers**

At the very top of the chain sits the global scope, and it is split: declarations behave differently depending on declarator and host context:

```js
// Classic-script semantics (browser <script>, node -e, REPL):
(0, eval)("var vGlobal = 1; function fGlobal() {}"); // simulated here; see note below
let lGlobal = 2;

console.log(typeof globalThis.vGlobal, typeof globalThis.fGlobal);
// number function — var/function declarations BECOME globalThis properties

console.log(typeof globalThis.lGlobal, lGlobal);
// undefined 2 — let/const live in a parallel "declarative record":
// reachable by name everywhere, but not ON the global object
```

- Note on the demo: this repository runs examples as CommonJS/ESM files where top-level bindings are module-local, so the line uses indirect eval to exhibit genuine classic-script semantics. In a browser `<script>`, plain top-level `var vGlobal = 1` does exactly what the eval'd line shows. Full treatment of scripts vs modules → [4.1](<../4. Top level scopes scripts modules and eval/4.1. Script vs module top level globalThis and the declarative record.md>).
- Why two layers? Backward compatibility: pre-ES2015 the global object was the only game in town; `let`/`const` got a clean record so modern globals can't collide with legacy `window` properties or be deleted/stomped as easily.

### 4) **Common confusion**

- "Inner functions search upward at call time through callers" — that's dynamic scope; it does not exist here. The chain is built from nesting at definition time.
- "Blocks are cosmetic" — true for `var` (which ignores them), false for `let`/`const`/`class` and for catch bindings; mixing the mental models produces exactly the bugs cataloged in [6.1](<../6. Common pitfalls to production bugs/6.1. Real production bugs caused by scoping mistakes.md>).
- "`with` statements change lookup" — `with` existed to fake dynamic scope and is forbidden in strict mode; treat any sighting as a migration emergency.
- Reading a name that resolves to an uninitialized TDZ binding throws instead of continuing outward — [1.2](<../1. Declarations and bindings/1.2. Temporal dead zone why early access throws.md>) explains why that's deliberate.

### 5) **Performance note**

The nested-scope model costs less than it looks: engines compile identifier references into direct context slots or inline-cache lookups rather than walking records at runtime. Deeply nested reads are still a readability smell first — long chains make provenance hard to audit — while genuinely hot paths get their lookups optimized away entirely. Profile before restructuring for speed ([JIT mindset](<../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md>)).

### 6) **Mentor note**

Draw the nesting as boxes-in-boxes with arrows pointing outward for unresolved names; juniors who can trace three levels on paper stop fearing shadowing. In review, the highest-value check is *scope width*: a binding used twice 400 lines apart should move closer to its use or become an explicit parameter — explicit data flow beats ambient variables every time.
