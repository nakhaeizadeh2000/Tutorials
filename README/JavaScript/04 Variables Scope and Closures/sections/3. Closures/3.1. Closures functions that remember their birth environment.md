## 3.1. Closures: functions that remember their birth environment

### 1) **A closure = function + the variable environment it was created in**

**Definition** — every function carries a hidden reference to the scope chain where it was *defined* ([2.1](<../2. Scope and lookup/2.1. Lexical scope and the scope chain how name lookup works.md>)). When that outer scope would otherwise die — its function returned long ago — the reference keeps the environment alive, and the inner function keeps full read/write access:

```js
function makeCounter() {
  let count = 0;                        // ordinary local…
  return function increment() {
    count += 1;                         // …still alive here
    return count;
  };
}
const nextA = makeCounter();
const nextB = makeCounter();            // second call → a SECOND environment
console.log(nextA(), nextA(), nextA()); // 1 2 3
console.log(nextB());                   // 1 — independent state per instance
```

- This is the standard way to give a function private, persistent state without classes: `count` is reachable only through `increment`, so nothing can corrupt it from outside.
- Strictly speaking, *every* function in JavaScript is a closure over its birthplace — even `[1,2].map(n => n * factor)` below closes over `factor`. The interesting cases are the ones where the birthplace has already returned:

```js
const factor = 3;
console.log([1, 2, 3].map((n) => n * factor)); // [ 3, 6, 9 ] — mundane closure
```

### 2) **Captured variables are live bindings, not snapshots**

The closure stores a *link to the variable*, not a copy of its current value. Writes made after the fact — by anyone holding the same environment — are visible everywhere:

```js
function makeThermostat() {
  let temperature = 20;
  return {
    read: () => temperature,
    set: (t) => { temperature = t; },
  };
}
const ts = makeThermostat();
const snapshotAttempt = ts.read;   // alias made BEFORE any set()
ts.set(31);
console.log(snapshotAttempt());    // 31 — NOT the 20 it saw at creation

// sibling closures share one environment:
const tank = makeThermostat();
tank.set(80);
console.log(tank.read(), ts.read()); // 80 31 — separate calls, separate environments
```

- One environment, many functions: all methods returned from a single call close over the *same* bindings — that's how multi-method objects keep coherent internal state.
- Parameters are locals too: naming a parameter like an outer variable cuts the closure link deliberately (`function greet(name)` uses its parameter, never the outer `name`) — shadowing as a feature.

### 3) **Closures capture variables — never call-time state**

A closure freezes *where names resolve*, not what `this` or `arguments` will be. Regular functions receive `this` from their **call site** at invocation time, so it is not part of the captured environment; arrow functions are the exception that closes over the surrounding `this` lexically. The complete rules — call-site binding, bind/call/apply, arrow capture — belong to the Functions Deep Dive domain (textual forward reference until it lands); the scoping takeaway here: variable lookup and `this` resolution are two independent mechanisms that merely coexist in one function body.

```js
let handle;
function setup() {
  let secret = "born here";
  handle = () => secret;      // captures `secret` — no `this` involved anywhere
}
setup();
console.log(handle());        // born here — environment survived via `handle`
```

### 4) **Common confusion**

- "The closure copied the value when I created it" — no: live binding ([§2](#2-captured-variables-are-live-bindings-not-snapshots)). If you need a snapshot, copy explicitly (`const frozen = value;` then close over `frozen`).
- Loop callbacks all printing the last index — the most famous consequence of one shared environment; mechanism and fixes in [3.2](<./3.2. Loops and closures var let and per iteration capture.md>).
- "Closures leak memory by definition" — they *retain* deterministically ([3.4](<./3.4. Closures and garbage collection what stays alive.md>)); leaks require unbounded growth.
- "I need closures only when returning functions" — every callback, listener, and comparator is one; recognizing them in place is what prevents accidental retention.

### 5) **Performance note**

Each escaping closure can force its captured environment onto the heap (one allocation per outer-call instance), and per-instance method objects mean per-instance memory — the reason class prototypes share methods across instances (Prototypes domain, textual forward reference). Engines aggressively optimize non-escaping closures back onto the stack, so idiomatic callback code is rarely measurably worse; pay the allocation where you buy encapsulation, and [measure before optimizing](<../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md>).

### 6) **Mentor note**

Teach with `makeCounter`, then immediately break it on purpose: return two counters, ask why they disagree; mutate through one method, ask why another sees the change. Both answers are "same environment / live bindings" — once a junior can say that unprompted, closures are done. Review checklist: does each factory's returned interface really need all the closed-over variables, or is one field pinning something huge? (→ [3.4](<./3.4. Closures and garbage collection what stays alive.md>))
