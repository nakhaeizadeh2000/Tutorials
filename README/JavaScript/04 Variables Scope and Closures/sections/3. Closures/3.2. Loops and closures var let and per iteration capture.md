## 3.2. Loops and closures: var, let, and per-iteration capture

### 1) **The classic bug: one binding shared by every callback**

**Definition** — a `var` loop counter belongs to the *function*, not the iteration ([1.1](<../1. Declarations and bindings/1.1. var let const mechanics and when each is still defensible.md>)). Every closure created inside that loop closes over the **same single variable**, so when they finally run, they all see its final value:

```js
const bugFns = [];
for (var i = 0; i < 3; i++) bugFns.push(() => i);
console.log(bugFns.map((f) => f())); // [ 3, 3, 3 ] — three views of ONE variable

// The async version is where it historically detonated:
(async () => {
  for (var x = 0; x < 3; x++) setTimeout(() => process.stdout.write(`v${x} `));
  for (let y = 0; y < 3; y++) setTimeout(() => process.stdout.write(`l${y} `));
  await new Promise((r) => setTimeout(r, 50));
  console.log();                     // v3 v3 v3 l0 l1 l2
})();
```

- Why "3" and not "2": the loop exits only when `i === 3`, and that last value is what the shared binding holds forever after.
- Why callbacks don't see values "as they were": closures capture live bindings, not snapshots ([3.1](<./3.1. Closures functions that remember their birth environment.md>)) — the snapshot intuition is precisely the misconception this bug punishes.

### 2) **`let` in a loop head: a fresh binding per iteration**

When a classic `for`, `for-in`, or `for-of` head declares its variable with `let` (or `const` for the two latter), the spec mandates copying the binding at each iteration's start — every closure captures its own private copy:

```js
const okFns = [];
for (let j = 0; j < 3; j++) okFns.push(() => j);
console.log(okFns.map((f) => f())); // [ 0, 1, 2 ]

// Same guarantee for element/key loops:
const ofFns = [];
for (const v of ["a", "b", "c"]) ofFns.push(() => v);
console.log(ofFns.map((f) => f())); // [ 'a', 'b', 'c' ] — const legal BECAUSE fresh

const inFns = [];
for (const k in { p: 1, q: 2 }) inFns.push(() => k);
console.log(inFns.map((f) => f())); // [ 'p', 'q' ]
```

- This is normative behavior (ECMA-262's per-iteration environment creation), not an engine courtesy — it works identically everywhere ES2015+ does.
- Fresh ≠ frozen: within one iteration, mutating the binding is still visible to closures made earlier *in that same iteration* (`mutators[0]() → 100` if you `z += 100` after pushing). Freshness separates iterations; liveness holds within them.

### 3) **Know exactly which loops copy — the line everyone misses**

The magic lives in the **head of those three loop forms**, not in `let` generally:

```js
// while has NO special head semantics — one shared binding:
const wFns = [];
let n = 0;
while (n < 3) {
  wFns.push(() => n);   // all close over the SAME n
  n++;
}
console.log(wFns.map((f) => f())); // [ 3, 3, 3 ]

// Fix by introducing a per-iteration block binding yourself:
const wOk = [];
let m = 0;
while (m < 3) {
  const current = m;      // re-created on EVERY entry into the body block
  wOk.push(() => current);
  m++;
}
console.log(wOk.map((f) => f())); // [ 0, 1, 2 ]
```

| Loop form | Head declares | Binding per iteration? |
|---|---|---|
| `for (let i…)` / `for (const i…)`* | yes | **fresh copy each round** |
| `for (const v of xs)` / `for (const k in obj)` | yes | **fresh per element** |
| `while` / `do-while`, counter outside | no | shared — bind inside the body |
| `for (var i…)` | function-scoped | shared — the original bug |

\* `const` in a classic `for` head throws on the update expression ([1.1](<../1. Declarations and bindings/1.1. var let const mechanics and when each is still defensible.md>)).

### 4) **Common confusion**

- "`let` fixed hoisting/scoping so any loop is safe now" — only loop *heads*. A `let total` declared above a `while` behaves exactly like the old `var` for capture purposes: shared.
- The historical workaround — wrapping the body in an IIFE `(function (captured) { … })(i)` — works because the call creates a new scope with its own parameter per iteration. Recognize it in legacy code; never write it again.
- "Callbacks run during the loop" — usually not (timers, event handlers, fetch continuations). The bug only shows up *after* the loop finished, which is why it survives testing environments that assert synchronously.
- `for-of` over objects you also mutate mid-loop, index-vs-element confusion, and array-modification hazards are iteration-semantics issues — [Language Basics §2](<../../../02 Language Basics/sections/2. Control flow/2.3. for-of vs for-in iteration semantics and traps.md>) owns those; here we only care about *capture*.

### 5) **Performance note**

Per-iteration environments mean more allocations than one shared binding — measurable only when closures actually escape huge loops (thousands of captured contexts). Engines inline the common cases; if a profiler ever blames loop-closure allocation, the fix is restructuring (index math instead of captured counters), not switching back to `var`. [Measure, don't guess](<../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md>).
