## 3.4. Closures and garbage collection: what stays alive

### 1) **An environment lives as long as any function that can reach it**

**Definition** — the garbage collector reclaims a scope's variables only when *no* reachable function references them anymore ([3.1](<./3.1. Closures functions that remember their birth environment.md>)). Returning a closure is a lifetime extension for everything in its birth scope, not just what it reads:

```js
function makeHolder() {
  const big = new Array(1_000_000).fill("payload");
  return { read: () => big.length };
}
let holder = makeHolder();
console.log(holder.read());   // 1000000 — `big` alive because `read` reaches it
holder = null;                // last path gone → whole environment now collectable
```

- Mental model for review: draw an arrow from every surviving closure to its birth environment; if any arrow exists, the entire environment (all of that scope's bindings) is pinned.
- This is deterministic reachability, not a "leak": the collector behaves exactly as specified. Trouble starts when lifetimes outlive their purpose without anyone noticing.

### 2) **One field used, whole world retained — and the explicit fix**

Per the spec model, closing over *one* variable keeps the *entire* scope environment reachable:

```js
function attachStatsNaive(bigData) {       // imagine megabytes
  const count = bigData.length;            // you only need this…
  return { count: () => count };           // …but `bigData` sits in the same env
}
const reportA = attachStatsNaive(new Array(500).fill(0));
console.log(reportA.count());              // 500
```

Engines may optimize unused slots away (V8 has improved this repeatedly), but **nothing in the spec promises it**, and behavior differs across engines and versions — never bet production memory on it. The robust pattern costs one line:

```js
function attachStatsFixed(bigData) {
  const count = bigData.length;
  bigData = null;                          // cut the pin explicitly
  return { count: () => count };           // now only `count` plausibly survives
}
const reportB = attachStatsFixed(new Array(500).fill(0));
console.log(reportB.count());              // 500
```

- Corollaries: narrow scopes shrink environments ([2.1](<../2. Scope and lookup/2.1. Lexical scope and the scope chain how name lookup works.md>) — declare at last responsible moment); factories returning many methods over one huge config keep that config alive per instance ([3.3](<./3.3. Closure patterns privacy factories memoization.md>)).

### 3) **Timers and listeners pin closures until cleared**

Host APIs hold your closures from outside, so the GC can never collect them — or anything they capture — while registered:

```js
function startPolling() {
  let ticks = 0;
  const id = setInterval(() => { ticks += 1; }, 5);
  return { stop: () => clearInterval(id), getTicks: () => ticks };
}
(async () => {
  const poller = startPolling();
  await new Promise((r) => setTimeout(r, 40));
  poller.stop();                            // ONLY here does the env become collectable
  console.log(poller.getTicks() > 0);       // true
})();
```

- The retention chain: registry → interval callback → environment → whatever the callback closes over (response buffers, users arrays…). Forgetting `clearInterval`/`clearTimeout`/`removeEventListener`/`AbortSignal` teardown leaks by design.
- Browser event listeners follow the same rule; listener-lifecycle specifics belong to platform documentation — the scoping lesson transfers unchanged.

### 4) **Retention vs leak: growth is the tell**

A bounded cache that pins 100 entries is healthy retention; the same code without the bound is next quarter's OOM incident:

```js
function createCache(limit) {              // insertion-order eviction → simple FIFO cap
  const store = new Map();
  return {
    put(k, v) {
      if (store.size >= limit) store.delete(store.keys().next().value);
      store.set(k, v);
    },
    get: (k) => store.get(k),
    size: () => store.size,
  };
}
const cache = createCache(2);
cache.put("a", 1); cache.put("b", 2); cache.put("c", 3);
console.log(cache.size(), cache.get("a"), cache.get("c")); // 2 undefined 3 — bounded
```

- Diagnosing real cases: heap snapshots (DevTools Memory tab or `node --inspect`) show *what* retains *what* — look for growing lists of closures/environments between two snapshots. Node's `--expose-gc` flag enables forced collections for lab experiments only.
- Deep collector internals — generational design, WeakRef/FinalizationRegistry escape hatches, why they exist and why you rarely need them — belong to the Memory Management domain (textual forward reference until it lands).

### 5) **Common confusion**

- "Closures leak memory" — they *retain* deterministically; leak implies unbounded unintended growth. The distinction decides whether you fix ownership (design) or chase a bug (incident).
- "`delete obj.prop` / setting variables to null everywhere helps GC" — nulling matters exactly where §2 shows it: cutting long-lived pins to large data. Sprinkled micro-management elsewhere is noise.
- "The collector will figure it out once nothing uses it" — *uses* is wrong; *reaches* is right. An interval nobody reads but nobody cleared still counts as a root path.

### 6) **Mentor note**

Drill one review question: *"who can still reach this closure, and what does its birth scope hold?"* Timers, listeners, caches, and module-level singletons are the four usual answers. Teach juniors the §2 one-line fix as a habit after extracting a small value from something huge; teach seniors to confirm with snapshots instead of folklore.
