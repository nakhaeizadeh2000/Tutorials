## 3.3. Closure patterns: privacy, factories, memoization

### 1) **Private state without classes**

**Definition** — variables declared inside a function are unreachable from outside except through the functions returned from it ([3.1](<./3.1. Closures functions that remember their birth environment.md>)). That is encapsulation with zero ceremony:

```js
function createSession(userId) {
  let touches = 0;
  let closed = false;                    // invisible from outside
  return {
    userId,
    touch() {
      if (closed) throw new Error("session closed");
      touches += 1;
      return touches;
    },
    close() { closed = true; },
    isClosed: () => closed,
  };
}
const s = createSession("u1");
console.log(s.touch(), s.touch(), s.isClosed()); // 1 2 false
s.close();
console.log(s.isClosed());                       // true
try { s.touch(); } catch (e) { console.log(e.message); } // session closed
```

- The guarantee is real but *narrow*: privacy of the **variable**, not of capabilities — anyone holding the object can call `close()`. For genuinely tamper-proof fields, class `#private` syntax is the modern tool (Prototypes and Classes domain, textual forward reference); [Symbol-keyed properties](<../../../03 Values Types and Coercion/sections/5. The exotic primitives Symbol and BigInt/5.1. Symbol unique property keys beyond strings.md>) hide keys but not access.
- Recognize the pre-ESM incarnation: an IIFE returning a method bag ("module pattern") was how entire libraries were namespaced before ES modules existed — read it fluently, write ES modules instead (Modules domain, textual forward reference):

```js
const LegacyCart = (() => {
  let items = [];                        // truly module-private
  return {
    add: (x) => items.push(x),
    size: () => items.length,
  };
})();
LegacyCart.add("apple");
console.log(LegacyCart.size());          // 1
```

### 2) **Factories configure behavior at creation time**

A factory returns a small function pre-loaded with its settings — configuration captured once instead of threaded through every call:

```js
const makeGreeter = (greeting) => (name) => `${greeting}, ${name}!`;
const hi = makeGreeter("Hi");
console.log(hi("ada"));                  // Hi, ada!

const inRange = (min, max) => (n) => n >= min && n <= max;
const isPort = inRange(1, 65535);
console.log(isPort(8080), isPort(70000)); // true false
```

- Why it beats option-objects for narrow cases: fewer arguments per call, impossible to pass mismatched config at use sites, and each product carries only its own two bindings.
- When it hurts: deep factory-chains hide data flow ("where did `max` come from?") — beyond two levels, prefer a named function with explicit parameters ([checklist](<../5. Important points to remember/5.1. Scope checklist reflex rules mentors screen for.md>)).

### 3) **Memoize and once: computation wrapped in a cache closure**

```js
function memoize(fn) {
  const cache = new Map();               // one cache per wrapped function
  return (...args) => {
    const key = args[0];                 // single-primitive-arg contract
    if (!cache.has(key)) cache.set(key, fn(...args));
    return cache.get(key);
  };
}
let calls = 0;
const square = memoize((n) => { calls += 1; return n * n; });
console.log(square(4), square(4), square(5), calls); // 16 16 25 2
```

- Each `memoize` call creates a fresh `cache` — wrapping two functions yields two independent caches (verified above: a second wrapper starts at zero calls). This "state per wrapper" property is the general shape of middleware/decorators.
- Correctness caveats before performance dreams: memoizing impure functions returns stale lies; multi-argument or object-argument keys need composite strategies (Map internals and WeakMaps for keyed caches → Collections domain, textual forward reference).
- Same shape, different goal — run-at-most-once:

```js
function once(fn) {
  let done = false;
  let result;
  return (...args) => {
    if (!done) { result = fn(...args); done = true; }
    return result;
  };
}
const boot = once(() => "booted");
console.log(boot(), boot());             // booted booted — body ran once
```

### 4) **Common confusion**

- "Closure-based privacy means immutable" — the state is mutable *and* hidden; immutability is a separate design decision ([value model](<../../../03 Values Types and Coercion/sections/1. The value model/1.2. Immutability identity and copying how primitives and objects differ.md>)).
- "The pattern leaks" — retention follows reachability rules ([3.4](<./3.4. Closures and garbage collection what stays alive.md>)): a memoize cache holds every key you ever passed *by design*; that's unbounded growth unless bounded on purpose.
- Factories vs classes: both create objects with private-ish state; factories excel when instances are few, interfaces are small, or behavior varies structurally; classes win on shared-method memory and `instanceof` ergonomics — decide per case, not by ideology.

### 5) **Performance note**

Closure-per-instance privacy allocates a new function per method per instance, while prototype methods are shared across all instances (Prototypes domain, textual forward reference). For dozens of sessions this is noise; for millions of particles it dominates. Rule of thumb: closures for low-count, high-cohesion objects; classes for swarms. As ever, [measure](<../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md>).

### 6) **Mentor note**

Teach §1 by removing `closed` from the return statement and asking what breaks — nothing does, which proves the variable was private all along. Review checklist: does the returned interface expose exactly the operations the state needs (no accidental `getRaw()` escape hatches)? Are cached computations pure? Is any cache bounded?
