## 7.1. Common interview Q&A: variables, scope, and closures

### 1) **Q&A**

1. **Q: What exactly is a closure?**
   **A:** A function bundled with (a reference to) the variable environment where it was created. It keeps full read/write access to that environment even after the outer function returned — e.g. `makeCounter()` returning an incrementer whose `count` survives and stays private. Bonus signal: every JS function is technically a closure over its birthplace, not just returned ones.

2. **Q: What does this print, why, and what are two fixes?**
   ```js
   const fns = [];
   for (var i = 0; i < 3; i++) fns.push(() => i);
   fns.forEach((f) => console.log(f()));
   ```
   **A:** `3 3 3`. `var i` is one function-scoped binding shared by all three closures; after the loop it holds 3, and closures read bindings *live* at call time. Fixes: declare with `let` in the loop head (spec-guaranteed fresh binding per iteration), or historically wrap the body in an IIFE `(function (c) { … })(i)` creating a new scope per call.

3. **Q: Give three concrete differences between `var`, `let`, and `const`.**
   **A:** Scope (function vs block vs block); redeclaration (allowed vs SyntaxError vs SyntaxError); pre-line access (`undefined` vs TDZ throw vs TDZ throw). Plus `const` requires an initializer and forbids reassignment while permitting object mutation. Strong answers mention `var`/function declarations becoming globalThis properties in classic scripts.

4. **Q: What is the temporal dead zone and what problem does it solve?**
   **A:** The window where a `let`/`const`/`class` binding exists (created at scope entry) but isn't initialized yet; any access throws `ReferenceError`. It converts silent `undefined` propagation into immediate located errors — and makes shadowing honest: once an inner scope declares `x`, early reads fail instead of quietly grabbing the outer value.

5. **Q: Is "hoisting" real? Explain precisely.**
   **A:** Nothing moves. Scopes have a creation phase (all declarations registered) followed by top-to-bottom execution; declarators differ in what creation leaves behind: functions fully initialized, `var` set to `undefined`, `let`/`const`/`class` uninitialized (TDZ). Senior add-on: Annex B makes in-block function declarations behave differently in sloppy vs strict mode — avoid them entirely.

6. **Q: Trace this snippet:**
   ```js
   let x = 10;
   function read() {
     console.log(x);
     let x = 20;
   }
   read();
   ```
   **A:** `ReferenceError: Cannot access 'x' before initialization`. The inner `let x` owns `read`'s whole scope from entry (shadowing), so the first line hits the inner binding's TDZ rather than reading outer 10.

7. **Q: Do closures cause memory leaks?**
   **A:** They *retain* deterministically: any reachable closure keeps its entire birth environment alive. That becomes a leak only when growth is unbounded/unintended — uncleared intervals or listeners pinning payloads, caches without bounds. Fix ownership (clear timers, bound caches, null large refs you don't close over), not by fearing closures.

8. **Q: How do you implement private state in JavaScript? Compare approaches.**
   **A:** Closure variables (per-instance methods cost memory, zero syntax, works everywhere); class `#fields` (engine-enforced, shared prototype methods, modern default); WeakMap keyed by instance (privacy plus garbage-collection friendliness for metadata). Symbols are NOT privacy — hidden keys, but accessible to anyone holding the object.

9. **Q: Differences between classic scripts and ES modules at top level?**
   **A:** Scripts share the global stage: `var`/function declarations become `globalThis` properties, `this === globalThis`. Modules get their own scope, are always strict, expose only exports, and evaluate top-level `this` as `undefined`.

10. **Q: Does `const user = {}` prevent `user.name = "x"`?**
    **A:** No — `const` freezes the *binding*, not the value; reassignment throws but mutation works. Real immutability needs `Object.freeze` (shallow) or immutable structures. Probe follow-up: how would you deep-freeze? (Recursive freeze — with its cycles caveat.)

11. **Q: Which loops give each callback its own variable?**
    **A:** Only declarations in the heads of `for`, `for-of`, and `for-in`. A counter declared above a `while` — even with `let` — is one shared binding across iterations ([3.2](<../3. Closures/3.2. Loops and closures var let and per iteration capture.md>)); fix by binding inside the body.

12. **Q: Arrow functions vs regular functions inside callbacks — scoping angle?**
    **A:** Arrows close over the surrounding `this` lexically as part of their environment; regular functions receive `this` from the call site at invocation time. Variable lookup is identical for both. Full rules — [call-site taxonomy](<../../../05 Functions Deep Dive/sections/3. this binding/3.1. ### 2) **Grading guidance (mentor note)**

- Q1–Q3 gate juniors: expect live-binding phrasing on Q1/Q2 ("shared variable", not "copied value"); memorized `3 3 3` without mechanism is a soft fail.
- Mid signal: unprompted TDZ reasoning on Q6, retention-vs-leak distinction on Q7, and `prefer-const` policy surfacing around Q10.
- Senior signal: Q5 answered via creation-phase model *plus* Annex-B awareness; Q8 trade-offs stated per context (instance count, engine guarantees) instead of one-true-way.
- Red flags: "hoisting moves your code", "`let` fixed everything about loops", claiming closures always leak, or asserting `const` freezes objects.
