## 4.1. Script vs module top level: globalThis and the declarative record

### 1) **Classic scripts share one global stage**

**Definition** — a classic `<script>` (no `type="module"`) executes *in the global scope itself*. Its `var`s and function declarations become **properties of `globalThis`**, visible to every later script on the page:

```js
// Simulating genuine classic-script semantics here via indirect eval —
// see the host table below for why a plain Node file can't show this:
(0, eval)(`
  var stageVar = 1;
  function stageFn() { return "on stage"; }
  console.log(typeof globalThis.stageVar, typeof globalThis.stageFn);
`);                                   // number function — ON the global object

// let/const/class at classic-script top level join the "declarative record":
// reachable by bare name from every script, but NOT as object properties:
let recordLet = 2;
console.log(recordLet);               // 2 — by name
console.log(globalThis.recordLet);    // undefined — not a property
```

- Consequence: two classic scripts that both declare `var config = …` at top level are *one* variable — last writer wins. Whole generations of "works alone, breaks combined" bugs come from this sharing ([pitfalls](<../6. Common pitfalls to production bugs/6.1. Real production bugs caused by scoping mistakes.md>)).
- The two-layer design is deliberate compatibility engineering: pre-ES2015 the global *object* was the only global; ES2015 added the parallel record so modern globals (`let`/`const`/`class`) stay name-resolvable without stomping legacy object properties ([2.1](<../2. Scope and lookup/2.1. Lexical scope and the scope chain how name lookup works.md>)).

### 2) **Modules get their own top-level scope, always strict**

An ES module's entire body is one function-like scope wrapping everything; nothing escapes except through explicit exports. Two-file illustration (label: multi-file by nature — each file is complete):

```js
// [multi-file illustration — file 1 of 2] counter.mjs
var internalCount = 0;                     // module-private despite `var`
export const increment = () => ++internalCount;
```

```js
// [multi-file illustration — file 2 of 2] main.mjs (run together: node main.mjs)
import { increment } from "./counter.mjs";
console.log(increment(), increment());     // 1 2 — state lives inside the module
```

```js
// What modules guarantee (verified on Node v22):
console.log(this === undefined);       // true  — top-level this is NOT globalThis
var mVar = 1;
console.log(globalThis.mVar);          // undefined — nothing leaks to globals
// plus: strict mode is mandatory ('use strict' implied), so sloppy-mode
// behaviors like implicit globals are impossible in module code.
```

- Exports are *the* interface and stay live-bound to module internals (import mechanics, circular imports, default-vs-named ergonomics → Modules domain, textual forward reference until it lands). The scoping takeaway: modules made "private by default, exported on purpose" the language default.

### 3) **Top-level `this`: object vs undefined — and the full host table**

| Host context | Top-level scope | Top-level `this` | `var` becomes `globalThis.x`? |
|---|---|---|---|
| Browser classic `<script>` | shared global | `globalThis` | **yes** |
| ES module (browser or Node `.mjs`) | own scope + strict | `undefined` | no |
| Node CommonJS (`.js`) | wrapper-function scope | `module.exports` | no |
| `node -e`, REPL, indirect `(0,eval)` | global/script semantics | `globalThis` | **yes** |

- Verified locally: CJS prints `this === module.exports → true`; ESM prints `this === undefined → true`; the eval'd classic-script line sees its `var` land on `globalThis`.
- This makes `typeof module !== "undefined"` / `this === undefined` checks usable as environment sniffers in portable files — fragile but real-world common; prefer explicit build/host configuration when you control it.
- `eval`, briefly since it rounds out "whose scope does code run in": *direct* eval runs in the caller's current scope (sees locals); *indirect* eval — `(0, eval)(…)` — runs in global scope like a fresh script. Both are code-smell alarms; know them to read legacy code, avoid writing new ones.

### 4) **Common confusion**

- "Node files are scripts" — they're CommonJS modules wrapped in a function, so top-level `var count` is *file-private*, and `this` is `module.exports`. Porting browser-global assumptions to Node produces silent divergences, not errors.
- "`let` at script top level is 'more private'" — it's still global-scope-visible to every classic script loaded after; only module boundaries create real isolation.
- "`globalThis.x = …` equals declaring `var x`" — property assignment skips declaration semantics (no hoisting into other scopes, deletable, enumerable differences). Use it deliberately as an API, never as a declaration substitute.
- Strict-mode defaults: modules and class bodies are always strict; classic scripts opt in via `'use strict'` ([strict mode](<../../../01 Fundamentals and Mental Model/sections/3. Running JavaScript today/3.3. Strict mode sloppy mode and modern defaults.md>)).

### 5) **Performance note**

Module top-level bindings compile to direct slots exactly like function-local ones; there is no runtime tax for module isolation. Global-object properties (`globalThis.x`) are the slow path — dictionary-mode lookups and deoptimization hazards in hot code — one more reason hot-loop state belongs in local/module bindings rather than globals ([JIT mindset](<../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md>)).

### 6) **Mentor note**

The table in §3 is the exam answer; the teaching order matters more: juniors should first feel the *problem* (two classic scripts stomping one `config`) before seeing why modules fix it structurally. In review: any new code targeting browsers as classic scripts gets challenged — module or bundler output should be the default, and `window.X = …` style registration needs a stated reason (analytics beacons, old-school embeds).
