## 1.1. JSON grammar vs JavaScript literals history and the JSON superset

### 1) **Grammar in one table — seven values only**

**Definition** — JSON (RFC 8259, ECMA-404) is a strict *subset* of JavaScript literal syntax: only `object` (`{"k": v}`), `array`, `string` (double quotes only), `number`, `true`, `false`, `null`. No `undefined`, no `function`, no `Symbol`/`BigInt`, no comments, no trailing commas, no single quotes, no hex/binary numbers.

**What problem it solves / history** — Crockford proposed JSON as an interoperable data interchange format (RFC 4627, 2006); browsers added `JSON` as a single host object in ES5.1 (2009) so JS could produce/consume it without `eval`. Strictness is intentional: every language can parse the same byte sequence deterministically in one pass with no code execution.

```js
// Valid JSON vs JavaScript-only literals — JSON.parse enforces the distinction
console.log(JSON.parse('{"a":1,"b":[2,3],"c":null,"d":true}')); // { a:1, b:[2,3], c:null, d:true }
console.log(JSON.parse('"hello\\nworld"')); // hello + newline — escapes are mandatory JSON escapes
console.log(JSON.parse('{"x": 1.5e-2 }').x); // 0.015 — numbers are decimal with optional e/E exponent only

// These look like objects in JS but are SyntaxError as JSON — no trailing commas, no single quotes, no comments
for (const bad of ['{a:1}', "{'a':1}", '{"a":1,}', '{"a":1 /* x */}', '{"a": undefined}', '{"a": NaN}']) {
  try { JSON.parse(bad); console.log("parsed unexpectedly", bad); } catch (e) { console.log(bad.slice(0,12), "→", e.name); }
}
//  '{a:1}' → SyntaxError — unquoted key illegal; "{'a':1} → SyntaxError — single quotes illegal; trailing , → SyntaxError
```

- **Modern guidance** — never `eval`/`new Function` JSON; use `JSON.parse`. Declare wire content-type `application/json`; treat JSON as *data*, never as code.

### 2) **History that matters — RFC vs ECMA and the JSON superset**

**Definition** — RFC 8259 mandates UTF-8, one top-level JSON value (object/array historically; RFC now any value), and the seven-value grammar. ECMA-262 §25.5 defines `JSON.stringify`/`parse` behavior inside JS. ES2019 "JSON superset" made JS string literals accept `U+2028 LINE SEPARATOR` and `U+2029 PARAGRAPH SEPARATOR` unescaped — characters JSON already allowed as `\u2028` — so every valid JSON text is now valid JS.

```js
// JSON superset (ES2019) — before ES2019 this was a SyntaxError in JS but valid JSON
console.log(JSON.parse('"\u2028"').charCodeAt(0).toString(16)); // 2028 — JSON encodes LS as \u2028, JS now accepts literal
console.log(eval('"\u2028"').charCodeAt(0).toString(16)); // 2028 — eval as JS literal now works (post-ES2019)
console.log(JSON.stringify("\u2028")); // "\u2028" — stringify escapes them as \u2028 for portability

// History artifact — JSON arrived as a single global object, not syntax
console.log(typeof JSON, typeof JSON.stringify, typeof JSON.parse); // object function function
console.log(Object.getOwnPropertyNames(JSON).sort()); // [ 'parse', 'stringify' ] — just two methods (plus Symbol.toStringTag)
```

- **What life was like before it** — no native JSON; `eval('(' + json + ')')` was the parser — executed code, broke on `U+2028`, and opened XSS.

### 3) **Why strictness is the feature — no execution, deterministic parsing**

**Definition** — `JSON.parse` does not execute code: it builds values only. Duplicate keys are allowed by RFC but last value wins; `JSON.parse('{"a":1,"a":2}').a` is `2` — parser does not preserve duplicates. Streaming or larger-than-memory documents require NDJSON or chunked parsing, not one-shot `JSON.parse`.

```js
// No execution — function payload stays a string, not code
const payload = '{"exec":"process.exit(1)"}';
console.log(JSON.parse(payload).exec); // "process.exit(1)" — string, never called

// Deterministic: duplicate key — last wins, not array, not error (RFC permits; ECMA parse produces last)
console.log(JSON.parse('{"a":1,"a":2}')); // { a: 2 }

// Strictness prevents silent drift — trailing comma / comment are errors, not leniency
try { JSON.parse('{"a":1,}'); } catch (e) { console.log("trailing comma:", e.message.slice(0,30)); }
try { JSON.parse('// hi\n{"a":1}'); } catch (e) { console.log("comment:", e.message.slice(0,30)); }
```

- **Modern guidance** — treat `SyntaxError` from `JSON.parse` as a *client error* (bad payload), not a retry; log with `cause` and reject at boundary.

### 4) **Common confusion**

- "`JSON is JavaScript`" — no: JSON is a *text format*; JS literals allow comments/trailing commas/single quotes/`undefined`/`NaN` — JSON allows none.
- "`JSON supports comments or trailing commas for config`" — no (and never use `eval` to allow them — use JSON5/YAML for configs if you need comments).
- "`U+2028 makes JSON invalid JS`" — not since ES2019 superset; that edge is historical — today every JSON text is valid JS when evaluated as an expression.
- "`JSON numbers support hex/octal`" — no, only decimal + exponent; `0x10` is `SyntaxError` in JSON though valid JS.

### 5) **Performance note**

`JSON.parse` is a single C++ pass over the UTF-8/16 text in V8 — faster than a JS loop decoding it. Never pre-validate with `RegExp` before `JSON.parse`; the parser is the validator. For large payloads (>10 MB), one-shot `parse` allocates the entire object graph at once — streaming (NDJSON, SAX) avoids heap spikes (see [5.2](<../5. Beyond JSON structuredClone and data exchange/5.2. Data exchange patterns APIs NDJSON binary and base64.md>)).

### 6) **Mentor note**

Drill the table: valid = 7 values + double-quoted strings + no trailing comma; everything else → `SyntaxError`. In review, flag any `eval(json)` and any `JSON.parse` without `try/catch` at a boundary. Ask juniors: "What does `JSON.parse('{"a": undefined}')` do?" — answer: throws, because `undefined` is not a JSON value; `JSON.stringify({a: undefined})` *omits* the key (see [2.1](<../2.
