## 2.3. toJSON protocol custom serialization and recursion

### 1) **The protocol — holder key and return-value substitution**

**Definition** — If a value has a `toJSON` method, `JSON.stringify` calls `value.toJSON(key)` with the holder key (`key` string, `""` for top-level) and uses its *return value* as if that value were the property value. `this` inside `toJSON` is the original object. Crucially, `toJSON` runs *before* the replacer function sees the value — replacer receives the `toJSON` return, not the raw object.

```js
const obj = {
  x: 1,
  toJSON(key) { console.log("toJSON key", JSON.stringify(key), "this.x", this.x); return { x: this.x, via: "toJSON" }; }
};
console.log(JSON.stringify(obj)); // {"x":1,"via":"toJSON"} — toJSON return serialized instead of object
// With replacer — replacer sees toJSON output, not the original
console.log(JSON.stringify(obj, (k, v) => { console.log("replacer", JSON.stringify(k), JSON.stringify(v)?.slice(0,30)); return v; }));

// Holder key for nested value
const inner = { toJSON(k) { return `key=${k}`; } };
console.log(JSON.stringify({ a: inner, b: inner })); // {"a":"key=a","b":"key=b"} — holder key is property name
console.log(JSON.stringify([inner])); // ["key=0"] — array index as string key
console.log(JSON.stringify(inner)); // "key=" — top-level key ""
```

- **Modern guidance** — use `toJSON` to expose a stable *wire shape* (never expose internal slots directly); keep it pure (no mutation) and JSON-compatible (return primitives/plain objects/arrays only).

### 2) **Built-ins that use it — Date as the canonical example**

**Definition** — `Date.prototype.toJSON` returns `this.toISOString()` (or `null` if the Date is invalid, via `toISOString` throwing internally then caught). This is why `JSON.stringify(new Date(...))` emits an ISO string without a replacer. No other built-ins have `toJSON` by default — `Map`, `Set`, `RegExp`, `TypedArray` do not.

```js
const d = new Date("2026-01-01T00:00:00.000Z");
console.log(d.toJSON()); // 2026-01-01T00:00:00.000Z
console.log(JSON.stringify({ d })); // {"d":"2026-01-01T00:00:00.000Z"} — via Date toJSON
console.log(JSON.stringify({ d }, (k, v) => typeof v === "string" && k === "d" ? `saw:${v}` : v)); // {"d":"saw:2026-01-01T00:00:00.000Z"} — replacer sees string

const invalid = new Date("oops"); // Invalid Date
console.log(invalid.toString()); // Invalid Date
console.log(invalid.toJSON()); // null — spec returns null for invalid
console.log(JSON.stringify({ d: invalid })); // {"d":null}

console.log(typeof Map.prototype.toJSON); // undefined — Map has no toJSON, hence {} surprise in 2.1
```

- **What life was like before it** — dates were serialized as `toString` locales (non-round-trippable); `toJSON` standardized ISO + UTC.

### 3) **Custom shapes — hiding internals while preserving wire stability**

**Definition** — Custom `toJSON` lets you project private fields, computed views, or versioned schemas. Because replacer sees post-`toJSON` value, double-transformation bugs arise if both `toJSON` and replacer try to handle the same type (e.g., both convert `Date`).

```js
class User {
  constructor(name, passwordHash) { this.name = name; this._hash = passwordHash; this.created = new Date("2026-03-10T10:00:00Z"); }
  toJSON() { return { name: this.name, created: this.created.toISOString() }; } // hide _hash
}
console.log(JSON.stringify(new User("Ada", "abc123"))); // {"name":"Ada","created":"2026-03-10T10:00:00.000Z"} — _hash omitted

// Versioned wire shape — toJSON can branch by key or return different type
const money = {
  cents: 1099,
  toJSON() { return { amount: (this.cents / 100).toFixed(2), currency: "USD" }; }
};
console.log(JSON.stringify(money)); // {"amount":"10.99","currency":"USD"}

// Pitfall: toJSON + replacer double-converting Date — replacer already sees string, Date check fails
const withDate = { d: new Date("2026-01-01T00:00:00Z") };
console.log(JSON.stringify(withDate, (k, v) => v instanceof Date ? v.toISOString() : v)); // replacer sees string, check false — toJSON already ran
```

- **Modern guidance** — centralize wire conversion in *one* place: either `toJSON` (per-type) *or* replacer (per-graph). If you use both, make replacer handle only post-`toJSON` types (string/number/plain object).

### 4) **Recursion guard — toJSON that returns a cycle still throws**

**Definition** — `toJSON` return value is still walked for circularity and for its own `toJSON` chain; returning `this` with a cycle or returning an object that reaches back to the parent still throws `TypeError`. No tail-call optimization.

```js
// toJSON return value is still walked for cycles — returning a graph that reaches back throws
const node = { id: 1, child: null };
node.child = { id: 2, toJSON() { return node; } }; // child's toJSON returns ancestor → cycle
try { console.log(JSON.stringify(node)); } catch (e) { console.log("cross-return cycle →", e.name); }

// Simpler data cycle without toJSON — same TypeError path
const a = { x: 1 }; a.self = a;
try { console.log(JSON.stringify(a)); } catch (e) { console.log("data cycle →", e.name); }

// Safe pattern — break identity before return (project id, not reference)
const safe = { id: 1, next: { id: 2 } };
safe.next.toJSON = function() { return { id: this.id }; };
console.log(JSON.stringify(safe)); // {"id":1,"next":{"id":2}} — no cycle
```

### 5) **Common confusion**

- "`toJSON must return a string`" — no; it returns *any* JSON-compatible value (object/array/primitive); `stringify` then serializes that value.
- "`Replacer sees raw object before toJSON`" — reverse: `toJSON` runs *first*; replacer sees its return.
- "`Providing toJSON on prototype silently changes wire output`" — yes (including inherited `toJSON`); inherited `toJSON` is found via prototype chain lookup.
- "`JSON.stringify respects getters`" — getters are invoked to obtain the value, then `toJSON` is checked on the *result*.

### 6) **Performance note**

Each value with `toJSON` adds one extra call plus allocation of its return object. In hot serialization of 10k `Date`s, `Date#toJSON` (`toISOString` call) dominates cost; replacer that then inspects strings for ISO pattern doubles work. Prefer `toJSON` only for domain types where projection matters; for uniform transforms over graphs, a single replacer may be cheaper than per-instance `toJSON` dispatch.

### 7) **Mentor note**

Have juniors predict `JSON.stringify({d: new Date() }, (k,v)=> typeof v==="string"? "s":v)` — answer: `"s"` because `toJSON` already made `d` a string. In review, flag any type that adds `toJSON` returning `this` (no-op but hides that it opts into protocol) and any class whose `toJSON` forgets a new field (stale wire contract — test `JSON.parse(JSON.stringify(new Instance()))` round-trip in unit tests).
