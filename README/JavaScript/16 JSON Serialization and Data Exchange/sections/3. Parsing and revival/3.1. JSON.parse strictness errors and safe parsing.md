## 3.1. JSON.parse strictness errors and safe parsing

### 1) **Strict grammar enforced — JSON.parse is not eval**

**Definition** — `JSON.parse(text, reviver?)` parses a *JSON text* per RFC 8259 grammar (see [1.1](<../1. JSON as a format/1.1. JSON grammar vs JavaScript literals history and the JSON superset.md>)). Anything outside the seven values, trailing commas, comments, single quotes, unescaped controls, or extra data after the value throws `SyntaxError`. Unlike `eval`, `JSON.parse` never executes code — `{"exec":"..."}'` stays a string.

```js
console.log(JSON.parse('{"a":1}')); // { a: 1 }
console.log(JSON.parse('[1, 2, 3]')); // [1, 2, 3]
console.log(JSON.parse('"\\u0041"')); // A — \u escape decoded

for (const bad of [
  '{a:1}',              // unquoted key
  "{'a':1}",            // single quotes
  '{"a":1,}',           // trailing comma
  '// x\n{"a":1}',      // comment
  '{"a": undefined}',   // undefined not a JSON value
  '{"a": NaN}',         // NaN illegal
  '{"a": 0x10}',        // hex numbers illegal
  '"\n"',               // raw control
  '{"a":1} extra',      // trailing data
]) {
  try { JSON.parse(bad); } catch (e) { console.log(bad.slice(0,12).replace("\n","\\n"), "→", e.name); }
}
```

### 2) **Error shape — always wrap at the boundary**

**Definition** — On failure `JSON.parse` throws `SyntaxError` with an engine-specific `message` (`"Unexpected token..."` vs `"Expected property name..."`). The error's `name` is `"SyntaxError"` and `stack` points to the parse call, not to the JSON payload location (no line/col in standard stack; `message` may include position). Always `try/catch` at ingestion.

```js
function parseJson(text) {
  try { return JSON.parse(text); }
  catch (low) { throw new SyntaxError(`invalid JSON: ${low.message.slice(0,40)}`, { cause: low }); }
}
try { parseJson('{bad'); } catch (e) { console.log(e.message.slice(0,40), "cause:", e.cause.name); }

// Message contains position hint but format varies by engine
try { JSON.parse('{"a":1,}'); } catch (e) { console.log("msg:", e.message.slice(0,50)); }
try { JSON.parse('{"a": undefined}'); } catch (e) { console.log("msg:", e.message.slice(0,50)); }

// Common boundary mistake — forgetting to catch and letting unhandled throw bubble as 500 not 400
async function fakeHandler(bodyText) {
  try { const data = JSON.parse(bodyText); return { status: 200, data }; }
  catch (e) { return { status: 400, error: e.message }; }
}
console.log(await fakeHandler('{"ok":1}')); // 200
console.log(await fakeHandler('{bad')); // 400 — controlled
```

- **Modern guidance** — parse at a single boundary function that wraps `SyntaxError` with `cause` and returns `400 Bad Request`; never propagate raw `SyntaxError` as `500`.

### 3) **Text first — parse expects a string, and reviver is second arg only**

**Definition** — `JSON.parse` `ToString`s its first arg (`JSON.parse(null)` → `JSON.parse("null")`? Actually `null` is not string, spec `ToString(null)` → `"null"` which parses as `null` — confusing). Prefer explicit `String(text)` guard or type check. Passing `undefined` returns? `JSON.parse(undefined)` throws because `ToString(undefined)` → `"undefined"` not valid JSON.

```js
console.log(JSON.parse("null")); // null — valid JSON document, not "no value"
console.log(JSON.parse(null)); // null — ToString(null) → "null" → parses as null (surprise — but do not rely on it)
try { console.log(JSON.parse(undefined)); } catch (e) { console.log("undefined arg →", e.name); } // SyntaxError: "undefined" not JSON
try { console.log(JSON.parse(42)); } catch (e) { console.log("number arg →", e.name); } // parses? ToString(42) → "42" → 42 valid — but confusing
console.log(JSON.parse(String(42))); // 42 — explicit conversion makes intent clear

// Reviver is second arg — passing it as first is a bug
console.log(JSON.parse('"2026-01-01T00:00:00.000Z"')); // string — without reviver, Date stays string
console.log(JSON.parse('"2026-01-01T00:00:00.000Z"', (k, v) => k === "" ? v : v)); // identity reviver — same
```

- **Modern guidance** — call `JSON.parse(text)` where `text` is known `string` from `fetch`/file; if `text` may be `null`/`undefined`, guard: `if (typeof text !== "string") throw new TypeError(...)` rather than relying on coercion.

### 4) **One-pass safety — no execution but still needs validation**

**Definition** — `JSON.parse` never calls functions or evaluates code, but the resulting object graph can still be dangerous (`__proto__` pollution, unexpected large arrays, duplicate keys last-wins).

```js
// No execution
console.log(JSON.parse('{"__proto__": {"polluted": true}}').polluted); // undefined — but Object.hasOwn? depends on reviver
const m = JSON.parse('{"__proto__": {"polluted": true}}');
console.log(Object.getPrototypeOf(m) === Object.prototype); // true — parse creates plain object with that key as own data (no wiring) on modern V8
// However Object.assign(target, parsed) would pollute — see Objects 7.1 and 3.2 filter pattern

// Duplicate key — last wins silently
console.log(JSON.parse('{"a":1,"a":2,"a":3}')); // { a: 3 } — no error, no array

// Large array — parse allocates entire graph (OOM vector if not limited — see 5.2 streaming)
```

### 5) **Common confusion**

- "`JSON.parse(null) returns null because null is valid JSON`" — true, but `JSON.parse(null)` coerces `null` → `"null"` first; `JSON.parse(undefined)` does *not* return `undefined` — it throws.
- "`SyntaxError message includes line number`" — not standard; `message` varies; parse your own position if you need structured errors (e.g., `jsonc-parser`).
- "`Extra data after JSON is ignored`" — no, `JSON.parse('{} {}')` throws — trailing non-whitespace is `SyntaxError`; only surrounding whitespace allowed.
- "`Comments make JSON more readable`" — not JSON; use JSON5/JSONC and strip before `parse` or configure tooling to accept them.

### 6) **Performance note**

`JSON.parse` is implemented in C++ and is faster than a JS incremental state machine. Do not wrap it with `tryParse` that swallows `SyntaxError` and returns `null` — the throw path for invalid JSON is still fast, but swallowing hides the boundary error and loses `cause`. For large arrays (>100k elements) `parse` allocates all at once; NDJSON per-line `parse` keeps peak heap lower (see [5.2](<../5. Beyond JSON structuredClone and data exchange/5.2. Data exchange patterns APIs NDJSON binary and base64.md>)).

### 7) **Mentor note**

Have juniors predict `JSON.parse(null)` vs `JSON.parse(undefined)` vs `JSON.parse("42")` before running — cements `ToString` coercion trap. In review, flag any `JSON.parse` without `try/catch` at handler boundary and any `JSON.parse` whose second arg is mistakenly the payload. Require `400` mapping for `SyntaxError` and `cause` preservation for diagnostics.
