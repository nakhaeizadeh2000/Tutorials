## 3.2. Non-mutating copies: toReversed, toSorted, toSpliced, and with (ES2023)

### 1) **Copy-era twins return new arrays, original untouched**

**Definition** — ES2023 added four non-mutating counterparts that *copy* then operate: `toReversed()`, `toSorted(compareFn?)`, `toSpliced(start, deleteCount, ...items)`, and `with(index, value)`. Each allocates a new array, performs the mutation-logic on the copy, and returns it — never touches `this`. Available in Node 20+ / modern browsers (ES2023).

**What problem it solves / history** — prior to ES2023 every ordering/mutation method mutated: `arr.sort()` and `arr.reverse()` corrupted shared state in Redux/React reducers — accidental mutation was the #1 array bug in state management. The copy-era was proposed (https://tc39.es/proposal-change-array-by-copy) to make immutable updates ergonomic without `arr.slice().sort()` idioms.

```js
// Mutating vs copy-era — same logic, different ownership
const a = [3, 1, 2];
console.log(a.toSorted()); // [1,2,3] — new array
console.log(a); // [3,1,2] — untouched
console.log(a.sort()); // [1,2,3] — mutates a!
console.log(a); // [1,2,3]

// toReversed
const b = [1, 2, 3];
console.log(b.toReversed()); // [3,2,1]
console.log(b); // [1,2,3] — original intact
console.log(b.reverse()); // [3,2,1] mutates b

// toSpliced — mirrors splice but non-mutating
const c = [1, 2, 3, 4];
console.log(c.toSpliced(1, 2, 99)); // [1,99,4]
console.log(c); // [1,2,3,4] — original intact
console.log(c.toSpliced(1, 1)); // [1,3,4] — delete one
console.log(c.toSpliced(1, 0, 9, 9)); // [1,9,9,2,3,4] — insert

// with — point update (the last mutating idiom: arr[i] = v)
const d = [1, 2, 3];
console.log(d.with(1, 99)); // [1,99,3]
console.log(d); // [1,2,3]
console.log(d.with(-1, 99)); // [1,2,99] — negative index like at()
try { console.log(d.with(10, 99)); } catch (e) { console.log(e.name); } // RangeError — out of bounds
try { console.log(d.with(-10, 99)); } catch (e) { console.log(e.name); } // RangeError

// Copy-era densifies holes (unlike slice/map which preserve) — hole becomes undefined in the copy
const sparse = [1, , 3];
console.log(sparse.toReversed()); // [3, undefined, 1] — hole densified to undefined
console.log(Object.hasOwn(sparse.toReversed(), "1")); // true — now dense
console.log([1, , 3].toSorted()); // [1, 3, undefined] — hole densified then sorted as undefined
console.log(sparse.with(1, 99)); // [1,99,3] — hole filled by with (also densifies)
console.log([1, , 3].toSpliced(1, 1)); // [1,3] — splicing a hole compacts (like splice)
console.log([1, , 3].slice()); // [1, <1 empty>, 3] — slice DOES preserve holes (contrast)
```

### 2) **When to copy vs mutate**

| Context | Prefer | Why |
|---------|--------|-----|
| Redux/React state, function pipeline, shared reference | `toSorted`/`toReversed`/`toSpliced`/`with` | caller keeps original; no alias corruption |
| Local, owned, hot loop building result | `sort`/`reverse`/`splice` | avoids allocation; O(1) extra memory |
| Chained transforms (`filter`→`map`→`sort`→`join`) | copy-era end step | earlier steps already allocate; don't mutate input |
| Sorting without comparator needed | neither — add comparator fix first (see §5.2) |

```js
// Bad — mutating shared state (Redux reducer bug)
function badReducer(state, action) {
  if (action.type === "SORT") {
    state.items.sort(); // mutates previous state — breaks time-travel, memoization
    return state;
  }
  return state;
}
const state = { items: [3, 1, 2] };
const s1 = state.items;
badReducer(state, { type: "SORT" });
console.log(s1); // [1,2,3] — alias corrupted! s1 was assumed [3,1,2]

// Good — copy-era returns new reference, old untouched
function goodReducer(state, action) {
  if (action.type === "SORT") {
    return { ...state, items: state.items.toSorted((a, b) => a - b) };
  }
  return state;
}
const state2 = { items: [3, 1, 2] };
const orig = state2.items;
const next = goodReducer(state2, { type: "SORT" });
console.log(orig); // [3,1,2] — preserved
console.log(next.items); // [1,2,3] — new array
console.log(orig !== next.items); // true — new reference triggers re-render correctly

// With — immutable point update without spread ceremony
const arr = [1, 2, 3];
const updated = arr.with(1, 99);
console.log(updated); // [1,99,3]
console.log(arr); // [1,2,3]
// Equivalent verbose spread (also dense-preserving but holes differ):
console.log([...arr.slice(0, 1), 99, ...arr.slice(2)]); // [1,99,3] — same result, more ceremony

// toSpliced for immutable insert/delete
const playlist = ["a", "b", "c"];
console.log(playlist.toSpliced(1, 0, "x")); // ["a","x","b","c"] — insert without mutating
```

### 3) **Shallow copies still share nested refs**

Copy-era methods shallow-copy the top array only (like `slice`/`spread`). Nested objects/arrays stay aliased — the same shallow reality as [Objects 5.1](<../../../06 Objects in Depth/sections/5. Integrity and immutability/5.1. Prevent extensions seal freeze and shallow immutability.md>).

```js
const orig2 = [{ x: 1 }, { x: 2 }];
const rev = orig2.toReversed();
console.log(rev !== orig2); // true — new outer array
console.log(rev[0] === orig2[1]); // true — same inner object! shallow
rev[0].x = 99;
console.log(orig2[1].x); // 99 — mutation leaked via alias

// If you need deep independence, copy depth you mutate:
const deep = orig2.map(o => ({ ...o })); // shallow-copy each element
const revDeep = deep.toReversed();
revDeep[0].x = 1;
console.log(deep[1].x); // 99 — deep copy isolated? Actually deep copy isolated — let's verify clean:
const clean = [{ x: 1 }, { x: 2 }];
const cleanRev = clean.map(o => ({ ...o })).toReversed();
cleanRev[0].x = 99;
console.log(clean[1].x); // 2 — untouched

// toSorted with objects — comparator reads, not clones
const people = [{ age: 30 }, { age: 20 }];
const sorted = people.toSorted((a, b) => a.age - b.age);
console.log(sorted !== people); // true
console.log(sorted[0] === people[1]); // true — same object, reordered
```

### 4) **Common confusion**

- "`toSorted()` without args sorts numbers correctly" — no, same default as `sort()` — stringifies then lexicographic (see §5.2). `toSorted` changes *ownership*, not *ordering*.
- "`with` is like `arr[i] = v`" — semantically yes, but `with` throws `RangeError` on out-of-bounds while `arr[100] = v` would grow with holes. Use `toSpliced` to grow/append immutably.
- "Copy-era is slower, avoid" — allocates one new backing store; for most UI/state pipelines the allocation is dwarfed by rendering. Hot loops over 1e6 elements should measure — mutating in place may win, but correctness often outweighs.

### 5) **Performance note**

Copy-era allocates a new array of `length` (or adjusted) plus copies elements via memmove. For `toSorted`, that's allocation + sort (TimSort) — same sort cost as `sort` plus allocation. For 1–1e3 elements the allocation is ~microseconds; for 1e6 elements it doubles memory briefly (old + new). If memory pressure matters and the input is owned (local variable not shared), mutating `sort` avoids the clone. Guidance: default to copy-era at API/state boundaries; mutate only when ownership is clear and measured hot.

### 6) **Mentor note**

Ask "why did React not re-render after `state.items.sort()`?" — alias still `===` same array, React bails out. Fix with `toSorted`. In review, any `arr.sort()`/`reverse()`/`splice()` on a function parameter or imported state should be flagged → `toSorted`/`toReversed`/`toSpliced`. Lint rule `prefer-array-copy-methods` (ESLint `unicorn`) catches it.
