## 2.2. Length invariants and the array index contract

### 1) **Index definition is `ToString(ToUint32(i)) === key` and `i < 2³²−1`**

**Definition** — per ECMA-262 §6.1.7, a property key `P` is an *array index* iff `ToString(ToUint32(P)) === P` and `ToUint32(P) !== 4294967295`. Concretely: strings `"0"` to `"4294967294"` inclusive are indices; `"4294967295)` (2³²−1), `"01"`, `"1.0"`, `"-0"`, `" 1"` are not. Numeric writes `arr[5]` and `arr["5"]` target the same index; `arr["01"]` creates an ordinary property.

```js
const a = [];
a["0"] = "zero"; // index 0
a[1] = "one"; // index 1 → length 2
a["01"] = "not index";
a["4294967295"] = "not index (max uint32)";
a[4294967294] = "max index"; // legal max
console.log(a.length); // 4294967295 — grew to maxIndex+1 (sparse)
console.log(Object.hasOwn(a, "01"), Object.hasOwn(a, "4294967295")); // true true — ordinary
console.log(Object.hasOwn(a, "4294967294")); // true — index
// Reset
a.length = 3;
console.log(a.length, a[4294967294], a["4294967295"], a["01"]); // 3 undefined "not index (max...)" "not index"
// Non-indices survive truncation

// Numeric vs string key identity
const b = [10, 20, 30];
console.log(b[1] === b["1"]); // true — same slot
console.log(b["1.0"] === b[1]); // false — "1.0" is not index, creates ordinary property
b["1.0"] = "weird";
console.log(b.length, b["1.0"], Object.hasOwn(b, "1"), Object.hasOwn(b, "1.0")); // 3 weird true true

// Negative zero, NaN, etc. are not indices
const c = [];
c[-0] = "negzero?"; // "-0" is not index, but 0 is
console.log(c.length, c[0], c["-0"]); // 0 undefined "negzero?" — length didn't grow
c[0] = "zero";
console.log(c.length, c[0], c["-0"]); // 1 zero negzero? — distinct keys
```

### 2) **Writing an index auto-bumps `length` to `i+1`; writing `length` deletes the tail**

Two invariants lock together:

- **Index write:** if `i >= length`, set `length = i+1` (holes fill the gap).
- **Length write:** if `n < oldLength`, `DeleteProperty` each index `n..oldLength-1`; if `n > oldLength`, extend with holes (no properties created).

```js
// Growing via index (creates holes)
const d = [1, 2];
d[5] = 99; // 5 >= 2 → length 6
console.log(d.length, d); // 6 [1,2,<3 empty>,99]
console.log(Object.hasOwn(d, "3"), Object.hasOwn(d, "4")); // false false — holes

// Truncating via length (deletes)
d.length = 2;
console.log(d, Object.hasOwn(d, "5")); // [1,2] false — deleted
console.log(d.length); // 2

// Extending via length (holes, not undefined values)
d.length = 5;
console.log(d.length, Object.hasOwn(d, "3"), d[3]); // 5 false undefined — hole
console.log(Object.keys(d)); // [ '0','1' ] — only existing indices

// length = 0 empties bare indices but keeps non-indices
const e = [1, 2, 3];
e.foo = "keep";
e["01"] = "keep too";
e.length = 0;
console.log(e.length, e), console.log(e.foo, e["01"]); // 0 []  keep keep too
console.log(Object.hasOwn(e, "0"), Object.hasOwn(e, "foo")); // false true

// Non-writable length blocks growth and truncation differently
const f = [1, 2, 3];
Object.defineProperty(f, "length", { writable: false });
console.log(Object.getOwnPropertyDescriptor(f, "length").writable); // false
try { f.push(4); } catch (err) { console.log(err.name); } // TypeError in strict/module
try { f.length = 1; } catch (err) { console.log(err.name); } // TypeError — also blocked
try { f[10] = 99; } catch (err) { console.log(err.name); } // TypeError — needs length bump
console.log(f.length, f[10]); // 3 undefined
// Cannot restore writable true once flipped (configurable false) — throws
try { Object.defineProperty(f, "length", { writable: true }); } catch (e) { console.log(e.name); } // TypeError
console.log(Object.getOwnPropertyDescriptor(f, "length").writable); // still false
// Workaround — copy to new array
const f2 = [1, 2, 3];
f2.length = 1;
console.log(f2); // [1] — new array truncates fine

// length is non-configurable — cannot delete or redefine as accessor
console.log(delete f.length); // false
try { Object.defineProperty(f, "length", { get() { return 0; } }); } catch (err) { console.log(err.name); } // TypeError

// Non-index numeric-like keys don't affect length
const g = [1, 2];
g["4294967295"] = "tail";
g["01"] = "pad";
console.log(g.length, g["4294967295"], g["01"]); // 2 tail pad
g[2] = "index 2"; // now length bumps
console.log(g.length); // 3 — only index 2 grew it
```

### 3) **Non-index properties ride along without touching `length`**

Arrays are still objects — `arr.foo`, `arr["01"]`, `arr[Symbol.iterator]` etc. are own properties that `length` ignores. They survive truncation unless they happen to be numeric indices.

```js
const arr = [1, 2, 3];
arr.meta = { source: "api" };
arr["01"] = "leading zero";
arr[Symbol("id")] = 123;
console.log(arr.length); // 3 — non-indices didn't grow

// Methods enumerate only indices in length-range
console.log(Object.keys(arr)); // [ '0','1','2','meta','01' ] — includes string keys, but length 3
console.log(arr.length, arr.meta); // 3 {source:"api"}
arr.length = 1;
console.log(arr.length, arr[1], arr.meta, arr["01"]); // 1 undefined {source:"api"} "leading zero"
console.log(Object.keys(arr)); // [ '0','meta','01' ] — non-indices kept

// Awkward: numeric string that looks like index but isn't
const h = [];
h["1"] = "index 1"; // index
h["01"] = "not index";
h[1.5] = "not index";
console.log(h.length, Object.hasOwn(h, "1"), Object.hasOwn(h, "01"), Object.hasOwn(h, "1.5")); // 2 true true true
console.log(h); // [ <1 empty>, 'index 1' ] but with extra own keys "01" and "1.5"
```

### 4) **Common confusion**

- "`arr.length = 100` creates 100 `undefined`s" — no, 100−oldLength holes (no properties). `arr.every(x => x === undefined)` would be true vacuously for holes (see §5.2) — check with `Object.hasOwn`.
- "`delete arr[0]` decrements `length`" — no, `delete` leaves length unchanged (hole). To compact, use `splice(0,1)` or `filter`.
- "`arr['5']` is slower than `arr[5]`" — identical: both coerce via `ToString`; engines optimize numeric access whether written as number or string.
- "`length` always writable" — by default yes, but `Object.freeze([1,2])` makes length non-writable via `freeze` (see [Objects 5.1](<../../../06 Objects in Depth/sections/5. Integrity and immutability/5.1. Prevent extensions seal freeze and shallow immutability.md>)).

### 5) **Performance note**

Dense `length` growth is cheap (backing store realloc with growth factor ~1.5). Frequent `length = 0` to clear a large array is O(n) deletions (must delete each index to keep invariants) — for GC-heavy clearing, `arr = []` (rebind) lets the old backing store be collected without per-element delete. Truncating from `1e6` to `0` via `length=0` touches 1e6 property deletions; rebinding is O(1). Engines optimize `length = 0` to a fast clear, but cross-engine cost still scales with old length. For repeated reuse of a buffer, `arr.length = 0` is idiomatic; for one-shot discard, rebind.

### 6) **Mentor note**

Ask trainees to predict `Object.keys` vs `length` for `[1,,3]` vs `[1, undefined, 3]` — then validate with `hasOwn`. Second probe: "what survives `arr.length = 0`?" (only non-indices). In review, flag any bare `arr.length = bigN` that intends to "pre-fill" — it creates holes, not `undefined`s; use `Array.from({length:n}, ...)` instead.
