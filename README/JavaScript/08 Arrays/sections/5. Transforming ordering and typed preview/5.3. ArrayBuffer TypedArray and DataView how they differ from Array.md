## 5.3. ArrayBuffer, TypedArray, and DataView — how they differ from Array

### 1) **Buffer owns bytes; views interpret them**

**Definition** — `ArrayBuffer` is a fixed-length byte container (`byteLength` bytes, not elements). Views interpret it: `TypedArray` (`Uint8Array`, `Int32Array`, `Float64Array`, …) as a typed numeric array, and `DataView` as an untyped, offset-based accessor with endianness control. All are dense, no holes, no `length` auto-growth, no exotic index magic.

**What problem it solves / history** — `Array` holds `any` values with holes/sparse overhead. For binary I/O, canvas pixels, WASM memory, and network packets, JavaScript needed raw bytes. ES2015 added `ArrayBuffer`/`TypedArray` (ES2017 added `SharedArrayBuffer`); before that, base64 hacks sufficed.

```js
// ArrayBuffer — raw bytes
const buf = new ArrayBuffer(8); // 8 bytes
console.log(buf.byteLength); // 8
console.log(buf); // ArrayBuffer { [Uint8Contents]: <00 00 00 00 00 00 00 00> }

// TypedArray view — typed, dense, indexed 0..length-1 where length = byteLength / BYTES_PER_ELEMENT
const u8 = new Uint8Array(buf); // view as 8 × uint8
console.log(u8.length, u8.BYTES_PER_ELEMENT); // 8 1
u8[0] = 255; u8[1] = 256; // 256 wraps to 0 for Uint8 (mod 256)
console.log(u8[0], u8[1]); // 255 0

const f64 = new Float64Array(buf); // same buffer as 1 × float64
console.log(f64.length); // 1 — 8 bytes / 8
f64[0] = 3.14;
console.log(u8); // bytes reinterpreted — same storage, different type (aliasing)
console.log(f64[0]); // 3.14

// DataView — byte-level with endianness
const view = new DataView(buf);
view.setUint16(0, 0x0102, true); // little-endian at offset 0
console.log(view.getUint16(0, true).toString(16)); // 102
console.log(view.getUint16(0, false).toString(16)); // 201 — big-endian reads swapped

// Views share buffer — mutating one mutates the buffer and all views
u8[2] = 99;
console.log(view.getUint8(2)); // 99 — shared

// Buffer is fixed — no push, no length growth
console.log(typeof u8.push); // undefined — no Array methods push/pop/shift
try { u8.push(1); } catch (e) { console.log(e.name); } // TypeError or undefined
console.log(u8.length); // 8 — fixed, writing beyond throws or is ignored? Actually write to out-of-bounds is silent no-op
u8[100] = 1;
console.log(u8[100]); // undefined — out of bounds not stored
```

### 2) **Typed arrays are numeric, dense, and clamped/typed**

Differences vs `Array`:

- **Typed** — each index holds a number of that type; non-numbers coerced via `ToNumber` then clamped/wrapped. `Uint8ClampedArray` clamps 0–255; `Uint8Array` wraps mod 2⁸.
- **Dense** — every index `0..length-1` exists (no holes); `Object.hasOwn` always true in range.
- **Fixed length** — `length` is derived from `byteLength`; no `push`/`pop`/`splice`; `.set(array, offset)` and `.subarray` replace them.
- **Array.isArray false** — `Array.isArray(new Uint8Array(0))` → `false`; check via `ArrayBuffer.isView`.
- **Methods overlap but not identical** — `map`/`filter`/`reduce`/`join`/`slice` exist but return same TypedArray type; `concat` does not exist (use `set`); `flat` etc. absent.

```js
// Typed vs clamped
const clamped = new Uint8ClampedArray([260, -10, 128]);
console.log(clamped); // Uint8ClampedArray [ 255, 0, 128 ] — clamped
const wrapped = new Uint8Array([260, -10, 128]);
console.log(wrapped); // Uint8Array [ 4, 246, 128 ] — wrapped mod 256 ( -10 → 246 )

// Dense — every index exists
const t = new Uint8Array(3); // [0,0,0] — zeros, not holes
console.log(Object.hasOwn(t, "0"), Object.hasOwn(t, "1"), t[0]); // true true 0
console.log(Array(3)); // [ <3 empty> ] — holes (contrast)
console.log(Object.hasOwn(Array(3), "0")); // false

// Fixed length — no growth
const u = new Uint8Array([1, 2, 3]);
console.log(u.length); // 3
u[3] = 99; // no-op, no length change
console.log(u.length, u[3]); // 3 undefined

// set and subarray — the TypedArray idioms
const dst = new Uint8Array(6);
dst.set([1, 2, 3], 2); // copy at offset 2
console.log(dst); // [0,0,1,2,3,0]
const sub = dst.subarray(2, 5); // view, not copy, into same buffer
console.log(sub); // [1,2,3]
sub[0] = 99;
console.log(dst[2]); // 99 — shared buffer

// Copy via slice (copy, not view)
const copy = dst.slice(2, 5); // copy (new buffer)
console.log(copy, copy.buffer !== dst.buffer); // Uint8Array [99,2,3] true — new buffer

// Methods — return same TypedArray species
console.log(new Uint8Array([1, 2, 3]).map(x => x * 2)); // Uint8Array [2,4,6]
console.log(new Uint8Array([1, 2, 3]).filter(x => x > 1)); // Uint8Array [2,3]
console.log(Array.isArray(new Uint8Array([1, 2, 3]))); // false
console.log(ArrayBuffer.isView(new Uint8Array([1]))); // true
console.log(ArrayBuffer.isView([1, 2])); // false

// DataView for mixed types and endianness (network packets)
const packet = new ArrayBuffer(4);
const dv = new DataView(packet);
dv.setUint8(0, 0xff);
dv.setUint16(1, 0x1234, false); // big-endian
dv.setUint8(3, 0x01);
console.log(dv.getUint8(0).toString(16), dv.getUint16(1, false).toString(16), dv.getUint8(3)); // ff 1234 1
// Same bytes via TypedArray view — but endianness is platform-dependent for TypedArray
```

### 3) **When to pick which**

| Need | Use | Why |
|------|-----|-----|
| General data, mixed types, sparse, growable | `Array` | exotic, holes, dynamic length, `concat`/`push` |
| Binary I/O, canvas `ImageData`, WASM memory, audio buffers | `TypedArray` / `ArrayBuffer` | dense, fixed, byte-backed, zero-copy transfers |
| Mixed-endian or unaligned reads (protocol parsing) | `DataView` | explicit endian, no alignment assumption |
| Inter-thread sharing (workers) | `SharedArrayBuffer` + `Atomics` | shared bytes across workers (→ Memory domain) |

```js
// Array for data pipeline
const scores = [10, 20, 30];
console.log(scores.map(x => x * 2)); // [20,40,60] — mixed types allowed, growable

// TypedArray for binary (canvas pixel — RGBA)
const pixels = new Uint8ClampedArray(4); // 1 pixel RGBA
pixels[0] = 255; pixels[1] = 0; pixels[2] = 0; pixels[3] = 255; // red
console.log(pixels); // [255,0,0,255]

// Transferability — ArrayBuffer is transferable to workers without copy
const buf2 = new ArrayBuffer(1024);
// postMessage(buf2, [buf2]) — neuters original, worker gets ownership (zero-copy)

// DataView for packet parse (mixed types at known offsets)
function parseHeader(buf) {
  const v = new DataView(buf);
  return { magic: v.getUint16(0, false), version: v.getUint8(2), len: v.getUint16(3, true) };
}
const hdr = new ArrayBuffer(5);
new DataView(hdr).setUint16(0, 0xcafe, false);
new DataView(hdr).setUint8(2, 2);
new DataView(hdr).setUint16(3, 512, true);
console.log(parseHeader(hdr)); // { magic: 0xcafe, version: 2, len: 512 }
```

### 4) **Common confusion**

- "`TypedArray` is an `Array`" — no, `Array.isArray(typed)` → `false`; prototype chain is `TypedArray.prototype`, not `Array.prototype`.
- "`new ArrayBuffer` grows like Array" — no, fixed `byteLength`; to resize use `ArrayBuffer.prototype.resize` (resizable buffers, ES2024) or allocate new buffer + `set`.
- "`Uint8Array` clamps like `Uint8ClampedArray`" — no, `Uint8Array` wraps mod 2⁸; only `Clamped` clamps.
- "`DataView` is slower but more correct" — both are fast; `DataView` is needed only for endian/unaligned; `TypedArray` is faster for bulk typed loops (JIT can vectorize).

### 5) **Performance note**

Typed arrays store as contiguous C-like buffers — indexed access is a direct memory load/store without hole checks, prototype walks, or string-key hashing. Bulk `set`/`subarray` are `memcpy` fast. For numeric compute over 1e6 elements, `Float64Array` loops can be 2–5× faster than `Array` (due to dense packing + no boxing). Use them when numeric homogeneity and buffer sharing matter; otherwise `Array` ergonomics win.

### 6) **Mentor note**

Ask trainees to contrast `Array(3)` (holes) vs `new Uint8Array(3)` (zeros, dense, fixed). Then show `new Uint8Array(3).map(x=>1)` → `[1,1,1]` (dense) vs `Array(3).map(x=>1)` → holes (see §1.2/5.1). In review, flag any `TypedArray` indexed write beyond `length` that assumes growth — it silently no-ops.
