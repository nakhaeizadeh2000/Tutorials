## 4.1. Wrapper objects vs primitives: boxing demystified

### 1) **Primitives have no methods, yet `"abc".toUpperCase()` works**

**Definition** — strings, numbers, booleans, symbols, and bigints are primitives: they have no properties of their own. When you access one as if it had properties, the engine **boxes** the value — creates a transient wrapper object (`String`, `Number`, `Boolean`, `Symbol`), reads/writes through it, then discards it:

```js
console.log("abc".length);          // 3   — boxed String wrapper read, then dropped
console.log("abc".toUpperCase());   // ABC
console.log((25.5).toFixed(1));     // "25.5"
```

- The wrapper is invisible and short-lived — property *reads* work exactly as if primitives had methods.
- `null` and `undefined` have no wrapper class: any property access on them throws `TypeError` (the classic `Cannot read properties of undefined`).

### 2) **`new String("a")` creates an object — almost always a bug**

Explicit wrappers produce objects, which behave differently from their primitive look-alikes:

```js
const wrapped = new String("a");
console.log(typeof wrapped);          // object  — NOT "string"
console.log(wrapped === "a");         // false   — reference vs value identity
console.log(wrapped == "a");          // true    — loose equality unwraps (the only reason it "works")
console.log(new Boolean(false) ? "TRUTHY!" : "falsy");  // TRUTHY! — objects are always truthy
```

- That last line is the canonical wrapper bug: a boxed false is still an object, so every boolean context treats it as true ([2.4](<../2. The conversion algorithms/2.4. ToBoolean the complete falsy list.md>)).
- Modern rules: never call `new String/Number/Boolean`. Use plain literals; convert with `Number()/String()/Boolean()` ([2.1](<../2. The conversion algorithms/2.1. Explicit conversion toolbox Number String Boolean parseInt parseFloat and unary plus.md>)).
- Symbols and bigints go further: `new Symbol()` and `new BigInt()` throw TypeError — only function-style conversion (`Symbol("d")`, `BigInt(5)`) exists.

### 3) **Writes through wrappers silently vanish**

Boxing is per-access: each write lands on a fresh disposable wrapper:

```js
// Sloppy mode:
const s = "x";
s.foo = 1;
console.log(s.foo);       // undefined — the write evaporated with its wrapper

// Strict mode needs its own script/function prologue:
(function () {
  "use strict";
  const t = "x";
  try {
    t.foo = 1;              // strict mode: TypeError instead of silent no-op
  } catch (e) {
    console.log(e.message); // Cannot create property 'foo' on string 'x'
  }
})();
```

- Same rule applies to number/boolean writes. This is one more reason modern code lives in strict mode by default ([strict mode](<../../../01 Fundamentals and Mental Model/sections/3. Running JavaScript today/3.3. Strict mode sloppy mode and modern defaults.md>)).

### 4) **The symbol exception: legal, deliberate boxing**

Symbols can be explicitly boxed for API interop — and identity semantics get subtle:

```js
const sym = Symbol("id");
const boxed = Object(sym);        // legal boxing (no constructor!)
console.log(typeof boxed);        // object
console.log(boxed == sym);        // true  — loose equality unwraps
console.log(Object(sym) === sym); // false — EVERY Object(sym) makes a NEW wrapper
console.log(Object(sym) === boxed); // true — same reference compared to itself
```

- You rarely need this; know it exists so library output doesn't surprise you (`typeof` says "object" where you expected "symbol").

### 5) **Common confusion**

- "`typeof str === "string"` proves strings are objects" — backwards; the tag distinguishes them FROM wrapper objects.
- "`new String("a") === "a"` fails but `==` passes, so use `==` here" — fix the value, not the operator: stop constructing wrappers.
- "Autoboxing is expensive, cache wrappers" — engines optimize transient boxing well; hand-rolled caching adds allocation without measurable gain. Measure first.
- Wrapper prototypes are where primitive methods actually live (`String.prototype.toUpperCase`) — subclassing/extending those affects both forms.

### 6) **Performance note**

V8/JSC inline-cache property reads on primitives so the box often never materializes. Explicit wrappers, however, are real heap allocations with real GC cost and break type feedback in numeric code paths ([shape stability](<../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md>)).

### 7) **Mentor note**

Demo `"abc".length` then immediately `new Boolean(false)` truthiness in front of juniors — the pair teaches both halves (invisible mechanism, visible bug) better than either alone. Review red flags: any `new String|Number|Boolean(` occurrence is a defect; `Object(sym)` needs a justifying comment.
