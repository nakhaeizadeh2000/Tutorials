## 7.1. Real production bugs caused by coercion

### 1) **Form input arithmetic: `"10" + 5` ships the wrong total**

Every DOM input, query param, and `dataset` value is a string. Arithmetic that assumes numbers works until `+` appears:

```js
const qty = "10";                 // from an <input> or URL
console.log(qty + 5);             // "105"  — concatenation
console.log(Number(qty) + 5);     // 15     — boundary conversion

// The nastiest form — a reducer poisoned mid-stream:
const cells = ["3", "", "7"];     // empty cell from a CSV/form row
const sum = cells.reduce((acc, c) => acc + c, 0);
console.log(sum, sum / 3);        // "037" 12.333… — plausible garbage, no error anywhere

// Fix: validate at the boundary, fail loudly on junk:
function parseCells(cells) {
  return cells.map((c, i) => {
    const n = Number(c);
    if (!Number.isFinite(n)) throw new Error(`row ${i}: "${c}" is not numeric`);
    return n;
  });
}
```

- Why it hurts: no exception fires; totals drift silently until accounting reconciles weeks later.
- Note the empty-string subtlety: it didn't produce NaN — it flipped `+` into concatenation and kept the *string* type alive through the whole fold ([falsy list](<../2. The conversion algorithms/2.4. ToBoolean the complete falsy list.md>)).

### 2) **Falsy-value defaults: `||` discards legitimate `0` and `""`**

```js
const getPort = (config) => config.port || 8080;
console.log(getPort({ port: 0 }));   // 8080!! explicit port zero silently replaced

const getName = (u) => u.name || "anonymous";
console.log(getName({ name: "" })); // "anonymous" — empty name became fake data
// Correct tool — nullish coalescing only fills null/undefined:
const getPortFixed = (config) => config.port ?? 8080;
console.log(getPortFixed({ port: 0 })); // 0
```

- Why it hurts: valid falsy values vanish without a trace; tests with truthy fixtures never catch it ([operator comparison](<../../../02 Language Basics/sections/3. Operators/3.3. Logical operators short circuit nullish and compound assignment.md>)).
- Same family: `if (queue.length)` vs `if (queue)` — one checks emptiness, the other only existence.

### 3) **NaN propagation: one bad cell ruins a whole report**

```js
const avg = (xs) => xs.reduce((a, b) => a + b, 0) / xs.length;
console.log(avg([1, Number("N/A"), 3]));   // NaN — and every derived stat after it
```

- NaN poisons every operation it touches and fails *no* comparison (`NaN !== NaN`), so `if (result === result)` guards look bizarre but work; better: stop NaN at entry (`Number.isFinite`) [2.1](<../2. The conversion algorithms/2.1. Explicit conversion toolbox Number String Boolean parseInt parseFloat and unary plus.md>).
- Why it hurts: dashboards show blank/NaN days later; nobody can trace which input caused it.

### 4) **Lexicographic sort of numeric strings**

```js
console.log([10, 9, 1].sort());              // [1, 10, 9] — default sort STRINGIFIES
console.log([10, 9, 1].sort((a, b) => a - b)); // [1, 9, 10]
console.log(["10", "9"].sort());             // ["10", "9"] — looks right by luck here…
console.log(["9", "10", "100"].sort());      // ["10", "100", "9"] — lexical order exposed
```

- Why it hurts: mixed-type arrays from JSON sort "randomly"; relational comparisons have the same trap (`"9" < "10"` is false as strings! [3.2](<../3. Coercion at work/3.2. Hidden coercion sites relational operators templates and property keys.md>)).
- Sort mechanics belong to the Arrays domain (forward reference); the coercion root lives here.

### 5) **ID collapse past 2^53: updating the wrong record**

```js
const idFromApi = 9007199254740993;   // arrived as JSON number
const storedId =   9007199254740992;  // different record!
console.log(idFromApi === storedId);  // true → wrong record matched/updated
```

- Why it hurts: identity checks pass for distinct entities; fixes require contract changes (IDs as strings) end-to-end [5.2](<../5. The exotic primitives Symbol and BigInt/5.2. BigInt integers beyond MAX_SAFE_INTEGER.md>).

### 6) **Mentor note**

Each incident above follows the same arc: *stringy/unvalidated data → implicit conversion → plausible wrong output → discovered late*. That's why mentors push boundary validation harder than algorithm memorization. Post-mortem template worth teaching: identify where the value entered, what conversion fired, and which guard would have caught it.
