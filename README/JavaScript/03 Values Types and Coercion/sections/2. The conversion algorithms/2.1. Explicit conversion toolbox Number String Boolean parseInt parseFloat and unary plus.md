## 2.1. Explicit conversion toolbox: Number(), String(), Boolean(), parseInt(), parseFloat(), unary +

### 1) **`Number()` parses whole strings or fails**

**Definition** — explicit conversion states intent: "make this a number, by the book". `Number(value)` applies the ToNumber algorithm ([full table](<./2.2. ToString and ToNumber the exact conversion tables.md>)); for strings that means *the whole string* must parse as a numeric literal:

```js
console.log(Number("42"), Number(" 42 "));   // 42 42 — surrounding whitespace trimmed
console.log(Number("42px"));                 // NaN — trailing junk fails the WHOLE parse
console.log(Number(""));                     // 0 — empty/whitespace-only → 0 (surprise!)
console.log(Number("0x1F"), Number("1e3"));  // 31 1000 — full literal syntax accepted
console.log(Number(true), Number(null), Number(undefined)); // 1 0 NaN
```

- Unary `+` is exactly `Number()` in operator form (`+"12.5"` → 12.5, `-"3"` → -3) — idiomatic for one-liners; `Number(...)` reads better at boundaries.

### 2) **`parseInt`/`parseFloat` scan prefixes**

Different contract: read from the start, stop at the first character that doesn't fit, return what accumulated (or `NaN` if nothing did):

```js
console.log(parseInt("42px"), parseFloat("3.14rem")); // 42 3.14
console.log(parseInt("42.9"));                        // 42 — stops at "."
console.log(parseFloat("3e2"));                       // 300 — exponent aware (parseInt is not)
console.log(parseInt("10", 2));                       // 2 — radix ALWAYS explicit
console.log(parseInt("08"));                          // 8 — no octal legacy in modern engines
console.log(parseInt(""));                            // NaN — nothing parsed ≠ Number("")'s 0!
console.log(isNaN(parseInt(null)));                   // true — String(null)="null" parses nowhere
```

- **Always pass the radix**: `parseInt(x, 10)` costs nothing and documents intent; without it, `0x` prefixes still work but reader assumptions vary.
- The two contracts fail differently: `Number("12abc")` → NaN loudly; `parseInt("12abc")` → 12 *silently* — which turns corrupted data into plausible numbers ([pitfall](<../7. Common pitfalls to production bugs/7.1. Real production bugs caused by coercion.md>)).

### 3) **`String()`/`Boolean()` never throw on ordinary values — with two symbol-shaped asterisks**

```js
console.log(String(null), String(undefined));  // "null" "undefined" — nicer than ""+x would lie? no: same
console.log(String(Symbol("id")));             // "Symbol(id)" — EXPLICIT form allowed
// console.log(`${Symbol("id")}`);             // TypeError! implicit ToString throws on symbols
console.log(Boolean(0), Boolean(""), Boolean({}), Boolean("false")); // false false true true
```

- `String(sym)` works but `${sym}` throws — the constructor takes an explicit-symbol branch the implicit ToString path doesn't ([2.2](<./2.2. ToString and ToNumber the exact conversion tables.md>)).
- `Boolean()` has exactly eight inputs that give `false` — the complete list is tabulated in [2.4](<./2.4. ToBoolean the complete falsy list.md>); note already here that any non-empty string (even `"false"`) is truthy.

### 4) **Common confusion**

- Global `isNaN`/`isFinite` **coerce first** (`isNaN("abc") === true`); the `Number.`-prefixed versions don't (`Number.isNaN("abc") === false`). Prefer the `Number.` forms — the globals answer "would this be NaN as a number", not "is this NaN".
- "`Boolean(x)` and `!!x` differ" — they don't (same result); pick one style per codebase.
- `new Number(5)` is NOT conversion — it boxes into an object ([4.1](<../4. Boxing and wrapper objects/4.1. Wrapper objects vs primitives boxing demystified.md>)).

### 5) **Performance note**

Explicit conversions are JIT-cheap when types are already correct (V8 fast-paths number→number). The real cost of skipping them isn't per-call overhead — it's downstream: mixed-type values poison hot loops' type feedback ([shape stability](<../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md>)).

### 6) **Mentor note**

The teachable rule: *parse with `Number` when validity matters, scan with `parseInt` when extraction matters*. Code-review signal: bare `parseInt(` without radix, global `isNaN`, and `Number()` applied to user input without a NaN check afterward are three greps worth automating.
