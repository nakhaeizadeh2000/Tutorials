## 5.2. BigInt: integers beyond Number.MAX_SAFE_INTEGER

### 1) **Arbitrary-precision integer math with literal suffix `n`**

**Definition** — `BigInt` (ES2020) is the eighth primitive: integers with no fixed size limit. The motivation is a hard ceiling in `Number`: IEEE-754 doubles represent integers exactly only up to `Number.MAX_SAFE_INTEGER` (2^53 − 1):

```js
console.log(Number.MAX_SAFE_INTEGER);            // 9007199254740991
console.log(9007199254740992 === 9007199254740993); // true!! — distinct integers collapse
console.log(BigInt("9007199254740992") === BigInt("9007199254740993")); // false — BigInt sees both

console.log(typeof 123n);        // "bigint"
console.log(0xffn, 0b101n);      // 255n 5n — hex/binary literals work too
console.log(BigInt(42), BigInt("42"));  // 42n 42n — from Number or string
try { BigInt(1.5); } catch (e) { console.log(e.constructor.name); } // RangeError — no fractions, ever
```

- Classic victims of the ceiling: 64-bit database IDs (snowflake IDs), file sizes, crypto math, nanosecond timestamps. If an ID exceeds 2^53 and arrives as a Number, comparisons silently lie.

### 2) **Never mixes with Number implicitly**

Arithmetic between bigint and number throws TypeError — the language refuses to guess rounding:

```js
console.log(7n / 2n, -7n / 2n);   // 3n -3n — division TRUNCATES toward zero
console.log(2n ** 63n);           // 9223372036854775808n — beyond any double

try { console.log(1n + 1); } catch { console.log("+ throws TypeError"); }
try { +1n; } catch { console.log("unary + throws"); }        // no ToNumber path at all
try { Math.floor(10n); } catch { console.log("Math.* rejects bigints"); }
try { -8n >>> 1n; } catch { console.log(">>> undefined for bigints"); }

// Comparisons mostly bridge the gap:
console.log(1n < 2, 1n == 1, 1n === 1, 2n > 1.5);   // true true false true
```

- The asymmetry: `==` compares mathematical values across types; `===` keeps the type gate; relational operators compare numerically. Arithmetic throws.
- Division truncation plus no floats means money/decimal work still doesn't belong in BigInt — that's a design decision for the Numbers domain (forward reference).
- Boolean contexts behave like numbers: `0n` falsy, everything else truthy ([falsy list](<../2. The conversion algorithms/2.4. ToBoolean the complete falsy list.md>)).

### 3) **JSON and Math reject it — plan the boundaries**

```js
const order = { id: 9007199254740993n };
try {
  JSON.stringify(order);
} catch (e) {
  console.log("TypeError: Do not know how to serialize a BigInt");
}
// Standard workaround — serialize as strings:
const json = JSON.stringify(order, (k, v) => typeof v === "bigint" ? v.toString() : v);
console.log(json);                        // {"id":"9007199254740993"}
```

- Convert at boundaries: parse ID strings into BigInt on the way in (`BigInt(id)`), stringify on the way out. Keep arithmetic inside your domain in bigint form.
- JSON domain will cover serialization strategies in full (forward reference).

### 4) **Common confusion**

- "`BigInt` is for decimals/money" — no: it's integer-only (`7n / 2n === 3n`). Money needs scaled-integer discipline or decimal libraries regardless.
- "`1n == 1` works so mixing is fine" — equality bridges; *arithmetic* doesn't. One careless `+` between them is a runtime TypeError.
- "`typeof x === "bigint"` vs `x instanceof BigInt`" — use typeof; primitives fail instanceof (wrappers only).
- Bitwise ops exist (`& | ^ << >> ~`) but unsigned right shift `>>>` has no bigint meaning and throws.

### 5) **Performance note**

BigInt operations allocate (arbitrary precision), so they're far slower than SMI/double paths — orders of magnitude in hot loops. Use BigInt where correctness *requires* it; keep hot numeric code in Number when values fit safely ([JIT type feedback](<../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md>)).

### 6) **Mentor note**

The interview-grade demo is section 1's collapse: two different integers strictly equal as Numbers. Seniors should connect it to real incidents (64-bit IDs from APIs compared after JSON round-trips). Review rule: any API contract containing IDs > 2^53 must specify strings-or-BigInt end to end — document it in the interface, not in tribal memory.
