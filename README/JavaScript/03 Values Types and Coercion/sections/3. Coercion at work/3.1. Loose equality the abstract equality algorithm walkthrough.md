## 3.1. Loose equality: the abstract equality algorithm walkthrough

### 1) **Same types reduce to strict equality immediately**

**Definition** — loose equality (`==`, spec name *IsLooselyEqual*) is not chaos; it's a deterministic algorithm whose coercion branches fire **only when operand types differ**:

1. **Same type?** → strict comparison (`===` semantics: value identity for primitives, reference identity for objects).
2. **`null` vs `undefined`?** → `true` (they pair with each other and nothing else).
3. **Number vs String?** → convert the string to number, re-run.
4. **BigInt vs String?** → parse the string as bigint, re-run.
5. **Boolean involved?** → convert that boolean to a number (0 or 1), re-run.
6. **Object vs primitive?** → ToPrimitive(object, default hint), re-run with the result.
7. **Anything else** → `false`.

```js
console.log(1 == 1, "a" == "b");        // true false — same types, plain strict
console.log("5" == 5);                  // true — rule 3
console.log(null == undefined);         // true — rule 2
```

- The "re-run" wording matters: conversions can chain (`[] == false` needs rules 5→6→3 before comparing).

### 2) **Four cross-type rules cover every case**

The practical content of the algorithm is four behaviors:

```js
// Rule 2 in action — null/undefined are an exclusive pair:
console.log("" == null, null == 0, null == false);   // false false false

// Rule 5 — booleans go numeric FIRST:
console.log("0" == false);          // true   — false→0, then "0"→0
console.log("" == false);           // true   — ""→0
console.log([2] == true);           // false! — true→1, "[2]"→NaN
console.log(undefined == false);    // false  — false→0, but undefined pairs only with null

// Rule 6 — objects unwrap via ToPrimitive(default hint):
console.log(["5"] == 5);            // true   — ["5"]→"5"→5
console.log([null] == 0);           // true   — [null]→""→0
console.log([[]] == 0);             // true   — [[]]→""→0
```

- Note what's absent: no boolean-context test anywhere. `x == true` means "ToNumber(x) === 1", not "is x truthy" ([2.4](<../2. The conversion algorithms/2.4. ToBoolean the complete falsy list.md>)).
- Rule 2's exclusivity explains why `x == null` is the one sanctioned use: it matches exactly null-and-undefined, nothing more ([guidance](<../../../02 Language Basics/sections/3. Operators/3.2. Equality loose vs strict and when either is safe.md>)).

### 3) **Worked examples build the reflex**

The famous party trick, narrated through the algorithm:

```js
console.log([] == ![]);
// Right side first (unary !): ![] uses ToBoolean — [] is an object → truthy → false
// Now: [] == false
// Rule 5: false → 0            → [] == 0
// Rule 6: [] → ToPrimitive     → "" == 0
// Rule 3: "" → ToNumber        → 0 == 0 → true
```

And the bigint/symbol bridges most devs have never seen fire:

```js
console.log(1n == 1);               // true  — mathematical comparison across types
console.log(1n === 1);              // false — strict keeps the type gate
console.log(1n == "1");             // true  — string parses as bigint
const sym = Symbol("s");
console.log(Object(sym) == sym);    // true  — wrapper unwraps to the same symbol
```

- `==` between bigint and number compares *mathematical* values (no TypeError), while arithmetic between them throws — asymmetric by design.

### 4) **Common confusion**

- "`==` compares after converting both sides to strings/booleans" — neither; consult the seven-step algorithm above.
- "`null == 0` because null converts to 0" — no; null/undefined never enter numeric conversion under `==` (that's ToNumber behavior, a different operation).
- "The algorithm is random" — it always produces these exact results on every engine; the problem isn't unpredictability, it's unreadability for humans. That's why team policy is `eqeqeq` with the documented `null` exception.
- NaN fails every comparison including with itself, under both operators.

### 5) **Performance note**

Strict equality is a cheap type+value check; loose equality may invoke user code (valueOf/toString/Symbol.toPrimitive). Irrelevant for occasional checks, but `==` inside hot loops over object operands adds dispatch overhead — another nudge toward `===`.

### 6) **Mentor note**

Interview signal: juniors should know outcomes ("[] == ![] is true"); mids should narrate the chain; seniors should articulate *why* teams ban `==` (human readability, not engine nondeterminism) while keeping `x == null`. Teach the algorithm once, then make people never need it again.
