## 1.1. Iterable vs iterator vs array-like and Symbol.iterator

### 1) **Iterable is `Symbol.iterator` returning an iterator; iterator is `next()` returning `{value, done}`**

**Definition** — an *iterable* is any object that has a method at `Symbol.iterator` with no arguments that returns an *iterator*. An *iterator* is any object with a `next()` method returning an *IteratorResult* `{ value, done }` (`done` false → value is yielded; `done` true → iteration finished). The well-known symbol `Symbol.iterator` is the protocol key — engines look for it, not a string name.

**What problem it solves / history** — before ES2015, "loopable" meant array-like length + indices or `for-in` enumeration, both broken for custom collections and strings with emoji (surrogate pairs). ES2015 introduced a single `Symbol.iterator` protocol so `Array`, `String`, `Map`, `Set`, `TypedArray`, `NodeList`, arguments, and generators all work with the same `for-of`/spread/`Array.from`/destructuring consumers.

**Modern guidance** — if you make a collection, implement `[Symbol.iterator]()` as a factory that returns a *fresh* iterator each call. Never cache a single iterator on the iterable; consumers expect independent traversals.

```js
// Minimal iterable — returns a fresh iterator each time
const counter = {
  *[Symbol.iterator]() { // generator helper; desugared below without generator too
    yield 1; yield 2; yield 3;
  }
};
console.log([...counter]); // [ 1, 2, 3 ]
console.log([...counter]); // [ 1, 2, 3 ] — second call is independent

// Without generator — explicit object
const explicit = {
  data: ["a", "b"],
  [Symbol.iterator]() {
    let i = 0;
    const data = this.data;
    return {
      next() {
        if (i < data.length) return { value: data[i++], done: false };
        return { value: undefined, done: true };
      },
      [Symbol.iterator]() { return this; } // iterators are iterable (see §3)
    };
  }
};
console.log([...explicit]); // [ 'a', 'b' ]
for (const v of explicit) console.log(v); // 'a' 'b'

// Built-ins are all iterable
console.log(typeof "hi"[Symbol.iterator]); // 'function'
console.log(typeof new Map([["k","v"]])[Symbol.iterator]); // 'function'
console.log(typeof new Set([1,2])[Symbol.iterator]); // 'function'
console.log(typeof [][Symbol.iterator]); // 'function'
console.log(typeof (function*(){}())[Symbol.iterator]); // 'function' — generators are iterable

// Detecting
function isIterable(x) { return x != null && typeof x[Symbol.iterator] === "function"; }
console.log(isIterable([1,2])); // true
console.log(isIterable("hi")); // true
console.log(isIterable({0:"a", length:1})); // false — array-like, not iterable (see §2)
console.log(isIterable(null)); // false — guard needed (null has no protocol)
```

### 2) **Array-like vs iterable — dual nature and detection**

**Definition** — *array-like* means `length` + indexed keys `0..length-1` (e.g. `{0:"a",1:"b",length:2}`, `arguments`, DOM `NodeList` legacy). *Iterable* means `Symbol.iterator` (e.g. `Set`, `Map`, string, generator). Some objects are both (`Array`, `String`, `TypedArray`, modern `NodeList`), some are only one.

**Modern guidance** — use `Array.from(x)` when `x` may be either iterable or array-like — it handles both (iterable path preferred). Use spread `[...x]` only when you know `x` is iterable (it throws on array-like without iterator). Check with `Symbol.iterator` first if uncertain.

```js
// Array-like without iterator — not iterable
const arrayLike = { 0: "a", 1: "b", length: 2 };
console.log(Array.from(arrayLike)); // [ 'a', 'b' ] — array-like path
try { console.log([...arrayLike]); } catch (e) { console.log(e.name); } // TypeError — not iterable

// Make it iterable by adding Symbol.iterator
arrayLike[Symbol.iterator] = Array.prototype[Symbol.iterator];
console.log([...arrayLike]); // [ 'a', 'b' ] — now iterable

// Arguments is both (ES2015+) — has length + iterator
function demo() {
  console.log(isIterable(arguments)); // true
  console.log(Array.isArray(arguments)); // false
  console.log([...arguments]); // works
}
demo(1,2,3);

// String is iterable by code points (see 2.2)
console.log([...arrayLike].length, [..."hi👋"].length); // 2 3 — "👋" is one iterable item, two UTF-16 units

// Map/Set are iterable — but not array-like
const m = new Map([["k",1]]);
console.log(m.length); // undefined — no length
console.log([...m]); // [ [ 'k', 1 ] ]

// Detection helper covering both paths
function toArray(x) {
  if (x == null) return [];
  if (isIterable(x)) return [...x];
  if (typeof x.length === "number") return Array.from(x); // array-like fallback
  throw new TypeError("not iterable or array-like");
}
console.log(toArray(arrayLike)); // [ 'a', 'b' ]
console.log(toArray(new Set([1,2]))); // [ 1, 2 ]
```

### 3) **The iterator is itself iterable (`[Symbol.iterator](){return this}`)**

**Definition** — by convention every iterator also implements `[Symbol.iterator]() { return this; }`, making it *iterable*. That lets `for-of` accept either an iterable *or* an iterator directly, and makes iterator consumers (spread, `Array.from`) accept iterators too. Spreading an iterator consumes it — subsequent spreads are empty.

```js
// Iterator is iterable
function* gen() { yield 1; yield 2; }
const it = gen();
console.log(typeof it[Symbol.iterator]); // 'function'
console.log(it[Symbol.iterator]() === it); // true — returns itself
console.log([...it]); // [ 1, 2 ] — spread consumes via iterator
console.log([...it]); // [] — already done (iterator exhausted, not reusable)

// Contrast: iterable factory returns fresh iterator
function* genFactory() { yield 1; yield 2; }
const iterable = { [Symbol.iterator]: genFactory };
console.log([...iterable]); // [ 1, 2 ]
console.log([...iterable]); // [ 1, 2 ] — fresh each time

// Built-in iterators are iterable
const map = new Map([["a",1],["b",2]]);
const mapIter = map[Symbol.iterator]();
console.log(typeof mapIter[Symbol.iterator]); // 'function'
console.log([...mapIter]); // [ [ 'a',1 ], ['b',2] ]
console.log([...mapIter]); // [] — consumed

// Why it matters — you can pass an iterator where an iterable is expected
function consume(iterable) { return [...iterable]; }
console.log(consume(gen())); // [ 1, 2 ] — passing iterator directly works because it's iterable

// Common pitfall: reusing an exhausted iterator thinking it's an iterable
const once = gen();
const a = [...once];
const b = [...once];
console.log(a, b); // [1,2] [] — b empty because once was already consumed
// Fix: pass a factory or the iterable, not a live iterator, if you need to reuse

// Manual iterator without generator — remember the self-iterable glue
function makeRange(n) {
  return {
    [Symbol.iterator]() {
      let i = 0;
      const iter = {
        next() { return i < n ? { value: i++, done: false } : { value: undefined, done: true }; },
        [Symbol.iterator]() { return this; }
      };
      return iter;
    }
  };
}
console.log([...makeRange(3)]); // [ 0, 1, 2 ]
```

### 4) **Common confusion**

- "`length` means iterable" — no. `{0:"a", length:1}` is array-like, not iterable; `[...it]` throws. Use `Array.from` or add `Symbol.iterator`.
- "`for-in` iterates iterable values" — no. `for-in` enumerates string keys (see [Language Basics 2.3](<../../../02 Language Basics/sections/2. Control flow/2.3. for-of vs for-in iteration semantics and traps.md>) and [Objects 2.3](<../../../06 Objects in Depth/sections/2. Properties and descriptors/2.3. Enumerability enumeration order and for-in mechanics.md>)); `for-of` uses `Symbol.iterator`. `for-in` on arrays yields indices + extras; `for-of` yields values.
- "Spreading an iterator can be repeated" — no. Iterators are stateful and consumed once; iterables can be re-iterated because `Symbol.iterator` returns a new iterator.
- "Every iterable is an iterator" — no. `[]` has `Symbol.iterator` but no `next` at the array level; the iterator is the object *returned* by `[][Symbol.iterator]()`.

### 5) **Performance note**

Iterating via `for-of` or spread allocates an iterator object (and for generators, a Generator object). For hot loops over dense arrays, a classic `for (let i=0;i<n;i++)` or `for (const v of arr)` after JIT inlining is ~same; the cost is the iterator allocation for custom iterables on very tight loops. `Array.from(arrayLike)` is faster than `[...arrayLike]`-then-map on some engines for huge `n` because it pre-allocates via length hint — measure, but prefer `Array.from(iterable, mapFn)` over `[...iterable].map(f)` to avoid the intermediate array when only a mapped array is needed.

### 6) **Mentor note**

Have juniors predict `[...{0:"a",length:1}]` before running — the throw cements the iterable vs array-like split. Then add `Symbol.iterator` and re-run. In review, flag any `[Symbol.iterator]` that returns `this` on the *iterable* itself (returns the same consumed iterator — subsequent loops see empty). The fix is to return a fresh object each call, not `this`.
