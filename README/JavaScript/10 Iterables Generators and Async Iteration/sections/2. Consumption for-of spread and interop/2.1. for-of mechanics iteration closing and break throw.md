## 2.1. for-of mechanics iteration closing and break throw

### 1) **Desugaring of `for-of` to GetIterator + loop + IteratorClose**

**Definition** — `for (const v of iterable) body` desugars (ES2015 §13.7.5) to roughly: `iter = GetIterator(iterable)`; `while (true) { {value,done}=iter.next(); if(done) break; v=value; body }` with `IteratorClose(iter)` on any abrupt completion (break/throw/return/continue-with-label). Each iteration creates a fresh per-iteration environment (like `for(let)`), so closures capture per-iteration values.

**What problem it solves / history** — manual `while` with `next()` is verbose and error-prone on early exits. `for-of` guarantees resource cleanup and per-iteration scoping without boilerplate.

```js
// Desugared form — what the engine does
function* src(){ yield 1; yield 2; yield 3; }
const iterable = src();
// for (const v of iterable) { console.log(v); if(v===2) break; }
{
  const iter = iterable[Symbol.iterator]();
  let step;
  try {
    while (!(step = iter.next()).done) {
      const v = step.value;
      console.log(v);
      if (v === 2) break; // abrupt → IteratorClose
    }
  } catch (e) {
    // if iter.return exists, called before propagating
    if (typeof iter.return === "function") try { iter.return(); } catch (_) {}
    throw e;
  } finally {
    // break path closes
    if (step && !step.done || true) { // simplified: if not already done
      if (typeof iter.return === "function") {
        // only if iteration was not completed normally
      }
    }
  }
}

// Simpler: for-of does it for you
for (const v of src()) {
  console.log("for-of", v);
  if (v === 2) break; // closes via return() → finally
}

// Per-iteration environment — closures capture correctly
const funcs = [];
for (const v of [10,20,30]) {
  funcs.push(() => v);
}
console.log(funcs.map(f=>f())); // [10,20,30] — not [30,30,30] (var-loop bug)
// This uses CreatePerIterationEnvironment (see Variables 3.2)
```

### 2) **Early exit paths — break continue return throw all close**

**Definition** — any abrupt completion inside `for-of` that exits the loop before the iterator is done triggers `IteratorClose` → `iter.return()` if present. That includes `break`, `throw`, `return` from enclosing function, and labeled `continue` that leaves the loop. Normal completion (iterator done) does not call `return()`.

```js
function* withFinally(label){
  try{ yield 1; yield 2; yield 3; }
  finally{ console.log(label, "finally"); }
}

// break triggers close
for(const v of withFinally("break")){ console.log(v); break; }
// 1, "break finally"

// throw triggers close, then propagates
try{ for(const v of withFinally("throw")){ console.log(v); throw new Error("abort"); } }
catch(e){ console.log("caught",e.message); }
// 1, "throw finally", caught abort

// return from function triggers close
function runReturn(){
  for(const v of withFinally("return")){
    console.log(v);
    return v; // IteratorClose before function returns
  }
}
console.log("returned", runReturn());
// 1, "return finally", returned 1

// continue does NOT close — still inside loop
for(const v of withFinally("continue")){
  if(v===1) continue;
  console.log(v);
  if(v===2) break;
}
// 2, "continue finally" — continue just skips, only break closed

// vs classic for index loop — never closes generators (leak if you manually drive)
const gen = withFinally("manual");
const it = gen[Symbol.iterator]();
console.log(it.next().value); // 1
// break without return() call → finally never runs (leak)
console.log("manual leak — no finally yet");
console.log(it.return()); // now finally runs
```

### 3) **`for-of` vs `for-in` vs `forEach` — which protocol each uses**

| Loop | Protocol | Values | Holes | Early close |
|------|----------|--------|-------|-------------|
| `for-of` | iterable (`Symbol.iterator`) | yielded values | visits holes as `undefined` via array iterator? actually skips holes as undefined but yields `undefined` (see Arrays 2.1) | yes (`return()`) |
| `for-in` | enumeration (keys) | string keys | skips holes (no property) | no |
| `Array.prototype.forEach` | callback | values (skips holes) | skips holes | no — cannot break |

```js
const arr = [1,,3]; // hole at 1
console.log("length", arr.length, "hasOwn1", Object.hasOwn(arr,"1"));
// for-of — visits hole as undefined (array iterator yields undefined for holes? actually yields undefined)
for (const v of arr) console.log("for-of", v); // 1, undefined, 3 — hole becomes undefined
// for-in — skips holes, enumerates keys as strings
for (const k in arr) console.log("for-in", k, typeof k); // "0", "2" — no "1", keys are strings
// forEach — skips holes entirely
arr.forEach(v => console.log("forEach", v)); // 1, 3 — hole callback not called

// for-of over Map/Set/string — iterable values
for (const [k,v] of new Map([["a",1]])) console.log(k,v); // a 1
for (const v of new Set([1,2,3])) console.log("set", v); // 1 2 3
for (const ch of "hi👋") console.log(ch); // "h" "i" "👋" — code points (see 2.2)

// forEach cannot be closed early — return doesn't break/forEach lacks return hook
let count = 0;
try{ [1,2,3].forEach(v=>{ count++; if(v===2) throw new Error("break"); }); }
catch(e){ console.log("forEach break via throw, count", count); } // 2, but awkward

// for-of break is idiomatic and close-safe
count = 0;
for(const v of [1,2,3]){ count++; if(v===2) break; }
console.log("for-of break count", count); // 2 — clean

// Common mistake: for-in on arrays — picks up added enumerable props
arr.extra = "oops";
for(const k in arr) console.log("for-in with extra",k); // includes "extra"
for(const v of arr) console.log("for-of ignores extra",v); // 1, undefined, 3 — extra is non-index? actually enumerable but iterator only yields indices
delete arr.extra;
```

### 4) **Common confusion**

- "`break` leaks resources" — not with `for-of`; it closes via `return()`. But manually driving `next()` and breaking without `return()` does leak — always use `for-of` or call `return()`.
- "`for-of` skips holes like `forEach`" — no. `for-of` yields `undefined` for holes (array iterator spec returns `undefined` for missing indices), `forEach`/`map` skip holes entirely, `for-in` skips holes because there's no key. See [Arrays 2.1](<../../../08 Arrays/sections/2. Holes sparsity and length/2.1. Holes vs undefined sparse arrays and empty slots.md>).
- "`continue` closes the iterator" — no, only exits that terminate the loop (`break`/`throw`/`return`/labeled `continue` outward). Plain `continue` stays in the loop.
- "`for-of` works on plain objects" — no, `{} ` is not iterable (`{}` has no `Symbol.iterator`); it throws `TypeError`. Use `for-in` or `Object.keys`/`entries` for objects.

### 5) **Performance note**

`for-of` over arrays is inlined by V8/Spidermonkey for dense arrays — same speed as index loop after JIT warmup. Over custom iterables/generators, there's a `next()` call per element + object allocation per result; for hot 1M-element tight loops, an index loop or `Array.from` may be faster. Don't micro-optimize until measured; prefer `for-of` for correctness and closing semantics. `forEach` allocates a callback closure per loop — `for-of` avoids that.
