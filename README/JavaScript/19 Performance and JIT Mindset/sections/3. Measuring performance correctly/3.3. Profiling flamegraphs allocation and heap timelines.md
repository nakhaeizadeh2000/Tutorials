## 3.3. Profiling flamegraphs allocation and heap timelines

### 1) **Definition — the three lenses**

- *Sampling profiler (CPU):* periodically samples the call stack → flamegraph. Bar width = time, height = call depth, color = package/IC state in some tools. Shows *self* vs *total* time and inlined frames (may be hidden).
- *Allocation timeline:* records which stack allocated nursery objects and how many survived per interval — links code to GC pressure, not just CPU.
- *Heap timeline/snapshot diff:* two snapshots taken before/after a scenario → delta shows retaining growth (see [Memory 5.1](<../../../18 Memory Management and GC/sections/5. Measuring and preventing leaks/5.1. Measuring memory heap snapshots allocation timeline and inspector.md>)).

### 2) **What problem it solves / history**

Sampling replaced instrumentation (which distorted time). V8's `--prof`/`--cpu-prof` and Chrome's Performance panel made flamegraphs mainstream; Wolf's `0x`, Clinic.js, and Speedscope standardized sharing. Allocation timelines (Chrome DevTools 2016+, Node `perf_hooks`/`v8` APIs) exposed nursery churn as a first-class metric alongside CPU.

### 3) **Modern guidance — profile before patch, re-profile after**

```js
const { performance } = require("node:perf_hooks");

// Example: cheap hot loop vs allocation-heavy hot loop — CPU + allocation story
function hotFast(n) {
  let s = 0;
  for (let i = 0; i < n; i++) s += i; // arithmetic, no allocation
  return s;
}
function hotAlloc(n) {
  let arr = [];
  for (let i = 0; i < n; i++) arr.push({ v: i }); // allocates per iter → nursery churn
  return arr.reduce((s, o) => s + o.v, 0);
}

const t0 = performance.now();
hotFast(100_000);
const t1 = performance.now();
hotAlloc(100_000);
const t2 = performance.now();
console.log("fast ms", (t1 - t0).toFixed(2), "alloc ms", (t2 - t1).toFixed(2));
// In a real profile, run:
//   node --cpu-prof --heapsnapshot-signal=SIGUSR2 app.js
//   kill -SIGUSR2 <pid>  # twice, diff snapshots
// Open the .cpuprofile in Chrome DevTools or speedscope.app — width shows the cost.

// Minimal self-time harness around the flame: keep bench retention (§3.1/3.2)
let sink;
sink = hotFast(50_000);
sink += hotAlloc(50_000);
globalThis.__sink = sink;
console.log("sink", sink > 0); // true — retained

// BAD: profiling without a representative workload — micro flame says nothing about route latency.
// GOOD: record a route: warmup → snapshot 1 → run scenario (10k requests) → snapshot 2 → diff
// Allocation timeline then says "stack X allocated 40 % of nursery that survived to old space."
```

### 4) **Common confusion**

- "Widest frame is the bug" — width is time, not blame. A wide `Array.push({})` frame is *allocation* pressure, not compute — the fix is reuse/batching ( §4.2 ), not faster `push`.
- "Flamegraphs show every call" — sampling omits short calls; inlined frames may be merged. Use `--trace-ic`/`--trace-deopt` alongside for IC/deopt marks (lab only).
- "Allocation timeline = heap snapshot" — timeline shows *where* objects were allocated and whether they survived nursery; snapshot diff shows *what* stayed alive. Use both: timeline for churn, snapshots for retention.

### 5) **Performance note**

Profiling overhead itself skews results (sampling rate, GC). Keep sampling at defaults (e.g., `node --cpu-prof` 1kHz) for overview, then zoom into a 5-second window around the scenario. For nursery story, DevTools Allocation instrumentation is the sharpest lens — it attributes each surviving allocation to its stack. Always profile the *path that matters* (a request, a frame, a batch job), not an isolated function. Log CPU + allocation + bundle parse time together (bundle §5.2) — a 5 ms flame win that adds 200 kB bundle can net lose on cold start.

### 6) **Mentor note**

Workshop flow: start from a user-visible latency (route p95), sample CPU → flame identifies a hot helper, overlay allocation timeline if the flame is shallow but GC spikes, heap diff if memory grows. Ask "is this CPU, allocation, or retain?" before choosing the fix — each wants a different patch (inline/monomorphic vs reuse/bounded vs `clear`/`dispose`). Require before/after profiles in PRs alongside the harness numbers.
