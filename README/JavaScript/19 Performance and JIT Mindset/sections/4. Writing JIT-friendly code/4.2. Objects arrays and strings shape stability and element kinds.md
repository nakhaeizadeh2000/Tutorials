## 4.2. Objects arrays and strings shape stability and element kinds

### 1) **Definition — the three shapes that matter for JIT**

- *Object shape (map):* defined by constructor/creation recipe + property add order + attributes. Stable shape → offset load; ad-hoc order/`delete` → dictionary/hash.
- *Array element kind:* the lattice `PACKED_SMI → PACKED_DOUBLE → PACKED_ELEMENTS → HOLEY_* → DICTIONARY`. Stay packed/densed for vector storage; mixing types or introducing holes widens the kind.
- *String shape:* internal rope vs flat; repeated `+=` in a loop builds rope chains and flattens later; `Array.join` builds in one pass.

### 2) **What problem it solves / history**

V8 stores objects as offset slots and arrays as typed backing stores precisely so the optimizer can speculate on layout. If layout is stable, `obj.x` and `arr[i]` compile to offset loads and loops inline; if it churns, every access becomes a type check or hash probe and loops stay unoptimized. Element kinds (2012–) and rope strings (earlier) were introduced to keep the common dense/numeric cases fast without penalizing correctness for the general case.

### 3) **Modern guidance — initialize up front, stay dense, don't delete**

As of V8 12–13 (engine-hint):

- Objects: construct via `class { constructor(...) { this.a=...; this.b=...; this.c=...; } }` or a `makeXxx` factory that assigns in the same order every time. Don't add fields later ad-hoc; set sentinel `null` instead of `delete`.
- Arrays: pre-size or push densely; don't `delete arr[i]`; don't `arr[1000]=v` on a small dense array; filter/map to densify if holes arrive from elsewhere.
- Strings: avoid `s += chunk` in a tight loop of many chunks; collect chunks and `join("")`, or use `Array.join`/`String` builder pattern. Don't intern via `s + "__proto__"` games — use `Map` keyed by identity.

```js
// Objects — GOOD vs BAD shape stability
class Point { constructor(x, y) { this.x = x; this.y = y; } }
const p1 = new Point(1, 2), p2 = new Point(3, 4); // same map
console.log(p1.x + p2.x); // 4 — monomorphic, inlineable

const q = {};
q.y = 1; q.x = 2; // reversed order vs Point → different map
console.log(q.x); // 2 — correct, different map (polymorphic if at same site)
q.extra = 3; delete q.y; // dictionary mode
console.log("y" in q, q.y); // false undefined
// Fix: sentinel, not delete, plus canonical factory
function makeXY(x, y) { return { x, y }; }
const r = makeXY(1, 2); r.extra2 = null; // sentinel keeps shape stable-ish
console.log(r.extra2); // null

// Arrays — keep kinds narrow
const packed = [1, 2, 3];      // PACKED_SMI
packed.push(4);                // stays PACKED_SMI
console.log(packed); // [1,2,3,4]
const widened = [1, 2, 3];
widened.push("hi");            // → PACKED_ELEMENTS (string widens)
console.log(widened); // [1,2,3,"hi"]
const holed = [1, 2, 3];
delete holed[1];               // → HOLEY — kills vector assumptions
console.log(1 in holed, holed); // false [1, empty, 3]
// Densify for follow-up hot loops
const dense = holed.filter(() => true);
console.log(dense, 1 in dense); // [1, 3]  true (compact index 1 exists)

// Strings — loop concat vs join
function concatBad(n) {
  let s = "";
  for (let i = 0; i < n; i++) s += "a"; // rope per iter, flattens later
  return s.length;
}
function concatGood(n) {
  const parts = [];
  for (let i = 0; i < n; i++) parts.push("a");
  return parts.join("").length; // one allocation per join, contiguous buffer
}
console.log(concatBad(100), concatGood(100)); // 100 100 — good scales better at large n

// Bonus: for-of on dense PACKED_SMI stays inline; for-in on arrays is dictionary-polymorphic — avoid.

function sumDense(arr) { let s = 0; for (const v of arr) s += v; return s; }
console.log(sumDense(packed)); // 10
```

### 4) **Common confusion**

- "Pre-allocate `new Array(100)` is always faster" — `new Array(100)` creates a *holey* array (HOLEY) with no elements; pushing into it still widens; `Array.from({length:100}, (_,i)=>i)` or `[]` + `push` often keeps `PACKED` when dense.
- "`delete` on an array frees memory and keeps it fast" — `delete` creates holes and widens to `HOLEY`/`DICTIONARY`; holes preserve as `empty` slots and iteration semantics change (map skips holes, `for...of` visits `undefined` for some methods — see Arrays §2.1).
- "String `+=` is always bad" — for a few concats, `+=` is fine (engine optimizes rope + flatten); the win for `join` appears at *many* chunks in a hot loop where rope chain depth matters.

### 5) **Performance note**

Element-kind widening is one-way and permanent for that array; you can't narrow back without copying (`filter`, `slice`, `Array.from`). So the cheapest fix is to keep the original dense: handle holes at the *producer* (normalize API pagination before storing in hot cache) rather than patching every consumer. Object maps compose: one `delete` in a factory that feeds a hot loop taints every object from that factory — measure the factory, not just the loop. In flamegraphs, kind instability shows as time in element-type checks and `LoadIC` misses; shape instability shows as `Maps`/`IC` misses near property loads.

### 6) **Mentor note**

Teach shape via a single rule: "build objects the same way every time, initialize everything up front, never delete, keep arrays dense". Put that in `CONTRIBUTING.md` and enforce with lint (`no-delete` custom rule on hot paths, `consistent-return` shape). In a code review, ask "show the creation sites for this type — do they share the same literal order/constructor?" If not, the perf fix belongs in the factory, not the loop. Demo the kind lattice with `packed` → `widened` → `holed` → `dense` above and let students spot which loop would deopt.
