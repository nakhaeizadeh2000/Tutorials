## 4.1. Functions inlining and monomorphic call sites

### 1) **Definition — inlining and monomorphic sites, plainly**

*Inlining* replaces `call f` with `f`'s body at the call site, letting the optimizer fold type checks and eliminate allocation. It happens when the call site is *monomorphic* (one receiver/callee shape), the callee is small/leafy, and heuristics permit (no `eval`/`with`, no megamorphic). A *monomorphic call site* sees one map/type at that `o.method()` or `fn(obj)` location; polymorphic/megamorphic sees many and either doesn't inline or inserts a polymorphic dispatch table.

### 2) **What problem it solves / history**

Inlining is the highest-leverage JIT optimization: it turns per-call overhead and type checks into straight-line code. Crankshaft already inlined aggressively but deoptimized on mismatch; TurboFan/Turboshaft kept inlining but made guard failure cheaper (faster deopt). Maglev added a mid-tier that inlines more trivially without paying TurboFan compile latency. The constraint stayed: the call site's feedback must stay narrow.

### 3) **Modern guidance — keep hot call sites monomorphic and small**

As of V8 12–13 (engine-hint, thresholds change — label version-dependent claims):

- Prefer factory boundaries that produce one shape: `makeItem(kind,x)` with same property order vs ad-hoc literals.
- Don't multiplex one hot helper across unrelated shapes/types; split call sites or dispatch outside the hot loop.
- Keep hot callees leafy (no `try/catch` wrapping the call, no `arguments` exotic, no `eval` inside). Hoist checks out of the loop.
- Prefer `for (const v of arr)` or classic `for` where ICs stay monomorphic — `for...in` on arrays is polymorphic by policy.

```js
// BAD: one helper, three shapes at the same call site → polymorphic → no inline.
function areaBad(o) { return o.w * o.h; } // site sees {w,h}, {w,h,extra}, {h,w} reversed
const r1 = { w: 2, h: 3 };
const r2 = { w: 2, h: 3, extra: 1 };
const r3 = { h: 3, w: 2 }; // reversed order → different map
let sBad = 0;
for (let i = 0; i < 20000; i++) { sBad += areaBad(i % 3 === 0 ? r1 : i % 3 === 1 ? r2 : r3); }
console.log("bad", sBad);

// GOOD: normalized shapes — one map, monomorphic site → inline candidate.
function makeRect(w, h) { return { w, h }; } // one creation recipe, same order
const g1 = makeRect(2, 3), g2 = makeRect(4, 5), g3 = makeRect(1, 1);
function areaGood(o) { return o.w * o.h; } // site sees only makeRect shapes
let sGood = 0;
for (let i = 0; i < 20000; i++) sGood += areaGood(i % 2 === 0 ? g1 : g2);
console.log("good", sGood);

// BAD: gigantic callee rarely inlines.
function hugeHelper(o) {
  for (let k in o) { /* enumerate, branch, allocate */ }
  return o.w * o.h + JSON.stringify(o).length;
}
// GOOD: leafy callee — inline-friendly.
function leafHelper(o) { return o.w * o.h; } // small, no allocate, no enumerate
console.log(leafHelper(g1), hugeHelper(g1)); // 6 vs larger — leaf wins for inlining

// Hoist type test out of the hot loop — one shape per loop.
const mixed = [g1, g2, g3];
function sumAreasMono(arr) {
  let s = 0; for (const o of arr) s += leafHelper(o); return s; // all makeRect shapes
}
function sumAreasPoly(arr) {
  // mixed shapes → polymorphic IC — dispatch outside would help if hot
  let s = 0; for (const o of arr) s += areaBad(o); return s;
}
console.log(sumAreasMono(mixed), sumAreasPoly(mixed));
```

### 4) **Common confusion**

- "Arrow vs function affects inlining" — arrow vs `function` matters for `this` (Functions §3.2), not directly for inlining; call-site shape matters more. Don't cargo-cult arrow rewriting for perf.
- "Inlining always helps" — inlining a large function bloats code and i-cache; the optimizer may un-inline. Keep hot callees small; let cold code stay cold.
- "Monomorphic means one type globally" — it means *one type per call site*. The same function called from two sites each monomorphically with different types is fine.

### 5) **Performance note**

Inlining benefit is measurable as *self-time* drop on the call stack in a flamegraph (the call overhead and type-check frames vanish). To see it, sample `node --cpu-prof` on the scenario, then after the fix the `areaGood` frame's self-time shrinks or disappears via inlining. Pair with IC trace (`--trace-ic` lab) to confirm the site is monomorphic. If the flame is flat, the bottleneck isn't the call — look at allocation (Memory 2.2) or bundle ( §5.2 ).

### 6) **Mentor note**

Review prompt: "How many shapes does this hot call site see — count them?" If >1, require normalization or call-site splitting before approving a micro-opt inside the helper. Teach `makeXxx` factory discipline once; then reuse it for objects (§4.2) and element kinds. Demo inlining by profiling the bad vs good loop above in a 5-second `node --cpu-prof` sample and comparing self-time — the narrative sticks better than listing V8 flags.
