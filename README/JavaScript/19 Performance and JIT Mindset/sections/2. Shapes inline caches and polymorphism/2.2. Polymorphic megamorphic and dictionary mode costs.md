## 2.2. Polymorphic megamorphic and dictionary mode costs

### 1) **Definition — when the fast path becomes the slow path**

A call site is *monomorphic* (one map), *polymorphic* (2–4 maps, small table), or *megamorphic* (many maps/types → hash lookup + prototype walk). *Dictionary mode* is when an object's properties are stored as a hash table rather than offset slots — triggered by `delete` on a non-last property, adding many computed keys, or prototype shenanigans. Both megamorphic ICs and dictionary mode turn an offset load into a hash probe + allocation, and they block many optimizations (inlining, loop peeling, allocation folding).

### 2) **What problem it solves / history**

Polymorphic ICs let one site handle a few shapes without bailing; megamorphic defends correctness when call sites truly see many shapes (e.g., a `render(item)` called with 10 component types). Dictionary mode exists because "fast" maps can't represent arbitrary `delete`/computed-key patterns without degenerating into hash anyway. The trade-off is intentional: predictable shapes get fast paths; chaos gets correctness at cost.

### 3) **Modern guidance — keep hot sites narrow, keep objects fast**

- Don't feed one hot helper many shapes. Split: `processCat(cat)` and `processDog(dog)` each monomorphic vs one `process(pet)` that sees both and becomes polymorphic.
- Never `delete` a hot property. Set to `null`/`undefined` or rebuild the object via spread/`Object.assign` into a new map without the key.
- Keep arrays dense and kind-stable; don't `delete arr[i]` or `arr[1000]=v` holes.
- Stable prototypes help: mutating `Object.prototype` or `__proto__` widens every access.

```js
// Polymorphic call site — one helper, three shapes, one hot site.
function kind(o) { return o.kind; } // IC site: o.kind
const a = { kind: "a", x: 1 };
const b = { kind: "b", x: 1, extra: 2 }; // extra prop → different map
const c = { y: 1, kind: "c" };           // different order → different map
// Hot loop sees three maps at `o.kind` → polymorphic → megamorphic widening.
for (let i = 0; i < 1000; i++) { kind(a); kind(b); kind(c); }
console.log(kind(a), kind(b), kind(c)); // a b c — correct, now megamorphic

// GOOD: normalize shapes at the boundary — one map per hot site.
function makeItem(kind, x) { return { kind, x }; } // one creation recipe
const a2 = makeItem("a", 1), b2 = makeItem("b", 1), c2 = makeItem("c", 1);
for (let i = 0; i < 1000; i++) kind(a2); // monomorphic loop — fast
console.log(kind(a2)); // a

// Dictionary mode trigger — delete on hot object
const hot = { x: 1, y: 2, z: 3 };
hot.w = 4;
delete hot.y; // → dictionary mode (engine-hint, V8 12–13) — subsequent h.x costs more
console.log("y" in hot, hot.y); // false undefined — correct, now hash-backed
// Fix: sentinel instead of delete
const hotFixed = { x: 1, y: 2, z: 3, w: 4 };
hotFixed.y = null; // stays fast (offset, no deopt)
console.log(hotFixed.y); // null

// Array dictionary trap — delete vs splice/filter
const arr = [1, 2, 3];
delete arr[1];           // holey + potentially dictionary widening
console.log(1 in arr, arr); // false [1, empty, 3]
const denseArr = arr.filter(() => true); // densify for follow-up hot loops
console.log(denseArr); // [1, 3]
```

### 4) **Common confusion**

- "Polymorphic is fine, megamorphic only hurts after 10 shapes" — thresholds are heuristic and version-dependent (V8 12–13 polymorphic is ~2–4 maps, but don't assert numbers in tests); the direction is what's stable: first shape addition costs a little, many costs a lot, and it happens per call site.
- "Dictionary mode is memory-only" — it's also CPU: property access becomes hash probe, inlining bails, and GC must walk hash structures vs compact slots.
- "Fix by caching `o.kind` in a variable" — that only helps if you read it once; the IC site *is* the `o.kind` read — caching after the first read doesn't change the site's polymorphic table. Fix the call site multiplicity, not one read.

### 5) **Performance note**

Megamorphic/dictionary costs compound: one megamorphic site inside a loop that also allocates widens element kinds and triggers GC pressure, so a flamegraph shows time split between `IC_Miss`, `Deoptimize`, and `GC`. If you fix shape stability, allocation rate often drops as a side effect (fewer map transitions → fewer allocations). Measure the *site* (`--trace-ic`/`--trace-maps` in a lab, then profile `node --cpu-prof` self-time on the loop) not the whole app. A 2 % branch-level win that turns a megamorphic site monomorphic can be 15 % on the hot route.

### 6) **Mentor note**

Review anti-pattern to grep: `delete obj.prop` on any object that flows to a hot helper; `arr[idx]=v` with sparse indices; factories returning different literal orders per branch. Require the fix to show the map disciplinarian: "all constructions use `makeItem`/`new Pt` with the same order, or `Map` keyed by identity instead of ad-hoc string mix". Teach that `in` vs `undefined` (Arrays §2.1) once, then lean on it for hole/dictionary demos. Connect polymorphism → deopt (§1.2) → object stability (§4.2) as a single narrative: shape → IC → speculate → bail → measure → fix.
