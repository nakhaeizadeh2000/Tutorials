## 2.1. Hidden classes maps and inline cache states

### 1) **Definition — maps and inline caches, plainly**

V8 doesn't hash every property access. Each object carries a *map* (hidden class) that describes its layout: which properties exist, in which order, at which offsets, with which attributes. Property access compiles to an *inline cache* (IC): a tiny stub that checks `obj.map === expectedMap` and then loads at the known offset. IC state evolves: *uninitialized → monomorphic (one map) → polymorphic (2–4 maps) → megamorphic (hash/dictionary)*. Monomorphic is a single comparison + offset load; megamorphic is a hash lookup or prototype walk.

### 2) **What problem it solves / history**

Pure dictionaries would make `obj.x` O(hash) every time. Hidden classes (introduced in V8/SquirrelFish circa 2008) turn most accesses into O(1) offset loads by sharing maps among objects created the same way. Polymorphic ICs (2013–) allowed 2–4 shapes per call site without falling to hash; megamorphic became the fallback for true chaos. Element kinds (PACKED_SMI etc.) extended the same idea to arrays: dense vectors when kinds are uniform, dictionary/spare when mixed.

### 3) **Modern guidance — keep maps shared and ICs monomorphic**

As of V8 12–13 (engine-hint, thresholds change):

- Construct objects the same way, same property order, all fields up front. `class Pt { constructor(x,y){ this.x=x; this.y=y; } }` and `new Pt(...)` produce one map; ad-hoc `{y:…, x:…}` vs `{x:…, y:…}` produce two.
- Element kinds are a one-way lattice: `PACKED_SMI → PACKED_DOUBLE → PACKED_ELEMENTS → HOLEY_* → DICTIONARY`. Don't `delete arr[i]` or `arr[100]=1` on a dense array — that widens to holey/dictionary.
- Keep hot call sites monomorphic: one shape per `obj.prop` site. If a function must handle three shapes, split it into three call sites or normalize at the boundary.

```js
// GOOD: shared map → monomorphic IC
class Point { constructor(x, y) { this.x = x; this.y = y; } }
const a = new Point(1, 2);
const b = new Point(3, 4);
function sumX(p) { return p.x; }
console.log(sumX(a), sumX(b)); // 1 3 — one map, one stub (monomorphic)
console.log(sumX(a) + sumX(b)); // 4

// BAD: two maps at one call site → polymorphic, then megamorphic widening
const c = { y: 2, x: 1 };  // reversed order → different map
const d = { x: 1, extra: 1 }; // extra property → another map
console.log(sumX(c), sumX(d)); // still correct, slower IC (polymorphic → megamorphic as shapes grow)

// Element kinds — PACKED lattice
const packed = [1, 2, 3];      // PACKED_SMI (dense ints)
packed.push(1.5);              // PACKED_DOUBLE (transition, one-way)
const holey = [1, 2, 3];
delete holey[1];               // HOLEY — dictionary/sparse fallback
console.log(packed.length, holey[1]); // 4 undefined (hole, not value)

// Recover element-kind discipline: don't delete, rebuild.
const dense = holey.filter(() => true); // dense copy without holes
console.log(dense.length, 1 in dense); // 3 false? actually filtered keeps 2 elements? — but dense, no hole kind
console.log(dense); // [1, 3] — demonstration of densify via filter

// Array hole test — `in` distinguishes hole from undefined (see Arrays §2.1)
console.log(1 in holey, 1 in dense); // false true (or true if dense compacted)
```

### 4) **Common confusion**

- "Same properties, any order, same speed" — order *is* the map. `{x,y}` and `{y,x}` are different maps; a hot `o.x` site seeing both is polymorphic.
- "`delete` is cheap cleanup" — `delete` on a hot shape often forces dictionary mode (hash table, not offsets) and widens element kinds; prefer `obj.prop = null` or rebuild via spread/`Map.delete`.
- "Element kinds are academic" — a single `arr[100]=1` turning `PACKED_SMI [1,2,3]` into `HOLEY_ELEMENTS` with a holey backing store can double iteration cost and block inlining of `for (const v of arr)`.

### 5) **Performance note**

Maps and IC states are invisible in the spec but dominant in profiles: a hot `o.x` that is megamorphic can be 10–100× slower than monomorphic in a tight loop, but the absolute effect depends on how hot the site is. Don't micro-opt cold constructors; do enforce shape discipline on handlers called per-request or per-frame. The most honest way to see IC state is a sampling profile's self-time on the access plus `--trace-ic` in a lab — not `typeof` folklore. Link IC analysis to allocation pressure (§18) — widening kinds and map divergence both increase heap metadata and GC walks.

### 6) **Mentor note**

Code-review cue: "does every construction of this type use the same recipe (constructor + order + element kind)?" If creation is ad-hoc via object literals in three branches, demand a factory/constructor. Teach `in` vs `undefined` for holes (Arrays §2.1) once, then rely on it. Demo with two `Point` variants and a hot `sumX` loop under `node --trace-ic` in the workshop — the log shows monomorphic vs megamorphic; then patch by normalizing construction.
