## 1.2. Deoptimization and bailouts when speculation fails

### 1) **Definition — deoptimization, plainly**

The optimizing compiler speculates: "this function always adds numbers, so skip type checks and inline the `+` as integer addition". It inserts *guards* (type/shape/bounds checks). If a guard fails at runtime, V8 *deoptimizes* (bails out): it reconstructs the unoptimized frame from bytecode state and resumes in Ignition/Maglev. Deoptimization is correctness — the optimized code was wrong for this input, so we abandon it.

### 2) **What problem it solves / history**

Without deoptimization, speculative optimization would be unsound: compiling `x + y` as `int + int` would corrupt results when `x` is `"a"`. Deoptimization lets V8 be optimistic by default and pay the cost only when assumptions break. Early Crankshaft already had deopts; TurboFan/Maglev refined them to allow more aggressive inlining and loop peeling while retaining a faithful fallback. Turboshaft (2024–26) keeps the same deopt protocol with a cheaper IR.

### 3) **Modern guidance — what triggers deopts and how to avoid the cliff**

Common triggers (engine-hint, V8 12–13 era):

- Shape change mid-hot-loop: `point.x` assumed one hidden class → object literal with different property order deopts.
- Element-kind transition: `PACKED_SMI` array that suddenly receives `undefined`/hole/object → `HOLEY_ELEMENTS`/`DICTIONARY`.
- Arguments exotic: accessing `arguments` object with non-trivial aliasing or leaking it.
- Out-of-bounds or type mismatch at a guarded site.

Guidance:

- Keep hot call sites *monomorphic* (one shape per site); hoist type tests out of the hot loop.
- Initialize objects fully up front; don't `delete` hot properties.
- Observe deopts locally: `node --allow-natives-syntax --trace-deopt --trace-opt file.js` then fix the shape, not the flag.

```js
// Deopt is observable as a performance cliff, not a throw.
// Monomorphic helper — stays optimized under V8 12–13 heuristics.
function addPoint(p) { return p.x + p.y; }
function Pt(x, y) { this.x = x; this.y = y; }

const a = new Pt(1, 2);
const b = new Pt(3, 4);
for (let i = 0; i < 50_000; i++) addPoint(a); // warm, monomorphic
console.log("mono", addPoint(a)); // 3

// Same call site now sees a different shape → guard fails → deoptimize.
// The result is still correct, but the optimized code is discarded.
const bad = { y: 2, x: 1 }; // reversed order → different map
console.log("mixed", addPoint(bad)); // 3 — still 3, but IC is now polymorphic
console.log("still correct", addPoint(a)); // 3 — resumes in unoptimized/ re-optimized

// Fix by normalizing at the boundary — one shape per hot path.
function normalize(p) { return new Pt(p.x, p.y); } // canonical map
console.log("norm", addPoint(normalize(bad))); // 3 — hot site sees Pt only
```

### 4) **Common confusion**

- "Deopt means the engine is broken" — deopt *is* the fix. A function that deoptimizes once and then re-optimizes with broader types is healthy; a function that deopts repeatedly in a tight loop is the bug (shape instability).
- "`%NeverOptimizeFunction` proves deopt" — `%NeverOptimizeFunction` suppresses optimization; it doesn't simulate deopt. Use `--trace-deopt` to see real deopts, not natives-syntax folklore.
- "Deopt is rare" — on shape-chaotic hot paths (factory returning 5 shapes into one call), deopt can be per-iteration and dominate latency.

### 5) **Performance note**

Deoptimization cost is the recompile + frame reconstruction + re-tiering lag, not the guard check (guards are near-free). One deopt on a cold path is noise; deopt *inside* a 100k-iteration loop is a cliff (TF recomputes). Measure with `--trace-deopt` on a representative workload: grep the log for `bailout`/`deoptimize` near your file, then patch the shape/element kind that triggered it. Never gate correctness on "no deopt" — correctness is unconditional; performance is about avoiding *repeated* deopts.

### 6) **Mentor note**

Teach "speculate then bail" as a contract, not magic. Workshop: run a file with `--trace-deopt` on a polymorphic loop, show the line that deopts, then fix by constructing objects uniformly. Ask "which guard could fail here — shape, kind, or bounds?" before diving into flamegraphs. Link explicitly to maps/ICs (§2) and measurement (§3) — deopt explains *why* shape discipline matters and *when* to measure it.
