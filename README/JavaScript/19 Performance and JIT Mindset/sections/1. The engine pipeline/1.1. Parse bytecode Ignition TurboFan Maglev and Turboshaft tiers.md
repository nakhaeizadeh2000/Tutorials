## 1.1. Parse bytecode Ignition TurboFan Maglev and Turboshaft tiers

### 1) **Definition — the pipeline, plainly**

JavaScript isn't "interpreted vs compiled" — since V8 5.9+ (and as of 2026, V8 12–13 era) every function goes through a tiered pipeline: *parse → Ignition (bytecode interpreter) → Sparkplug (baseline compiler) → Maglev (mid-tier) → TurboFan/Turboshaft (optimizing compiler)*. Each tier trades compile time for peak speed. Hot functions are promoted; cold ones stay in bytecode. The optimizer speculates based on observed types (feedback vectors) and can inline and eliminate checks.

### 2) **What problem it solves / history**

Early JS (SpiderMonkey/V8 circa 2008) was bytecode-only — predictable but slow. Crankshaft/TurboFan added speculative optimization: assume a function always sees `number` arguments and compile tight machine code; fall back if wrong. Ignition (2017) unified bytecode across architectures; Sparkplug (2021) made baseline fast enough that fewer functions need TurboFan; Maglev (2023) filled the gap between Sparkplug and TurboFan; Turboshaft (2024–26) replaced TurboFan's sea-of-nodes IR with a simpler, faster optimizing IR. Each step cut warmup time and deopt cost.

### 3) **Modern guidance — as of ECMAScript 2026 era, Node 24 LTS / 22 Maintenance / 26 Current, V8 12–13**

Tiers are *engine-hint, not contract*: the spec says nothing about JIT; Node and browsers may tier differently and thresholds change. Treat guidance as "stable for V8 12–13" and label engine-dependent claims:

- Cold start is parse + bytecode: keep bundles small and `import()` chunked — see [§5.2](../5. Runtime and delivery performance/5.2. Bundle size tree-shaking code splitting and load cost.md).
- Hot loops tier up after ~10k–100k iterations (threshold varies); type feedback drives it — stable shapes/element kinds help.
- `eval`, `with`, `Function` construction, and `try/catch` around hot call sites can block or delay optimization in some V8 versions — isolate them.

```js
// Lab-only observation: feedback-driven tiering is real, but numbers are illustrative.
// Run with: node --allow-natives-syntax --trace-opt --trace-deopt file.js (local, never in CI/prod).
function hotAdd(a, b) { return a + b; }

// Warmup with one shape → monomorphic feedback → eligible for optimization.
// On V8 12–13 this typically optimizes quickly; threshold is heuristic.
for (let i = 0; i < 100_000; i++) hotAdd(1, 2); // SMI
console.log(hotAdd(1, 2)); // 3 — hot, monomorphic, inlinable

// A second shape would broaden feedback (see §1.2 deopt, §2 polymorphism).
// Keep call sites monomorphic for your hottest helpers.

// Good: split by shape at the boundary — two monomorphic sites.
function addInts(a, b) { return a + b; }   // call site A: ints
function addStrs(a, b) { return a + b; }   // call site B: strings
console.log(addInts(1, 2));       // 3
console.log(addStrs("a", "b"));   // "ab"
```

### 4) **Common confusion**

- "JIT guarantees speed" — JIT only helps *hot, predictable* code. A function that handles five types at one call site stays megamorphic and never inlines — shape discipline (§2) matters more than "use JIT".
- "Bytecode is slow so avoid it" — Ignition bytecode is fast to generate and fine for cold code; optimizing cold code wastes compile time. The pipeline's job is to *not* optimize cold paths.
- "`--trace-opt` output is stable" — flags are V8-version dependent. Use them in a lab to diagnose, not as CI assertions.

### 5) **Performance note**

Parse cost dominates cold start (see bundle §5.2); optimized-code cost dominates steady-state loops. Don't conflate them: a micro that warms a loop for 1M iterations proves nothing about your route handler's first 50 calls. Profile cold (`node --cpu-prof` on startup) and hot (steady-state `perf_hooks` loop) separately. If you must assert a speedup, measure median + p95 over ≥10k runs with warmup discarded — see [§3.1](../3. Measuring performance correctly/3.1. Clocks hrtime performance.now and benchmark harnesses.md).

### 6) **Mentor note**

Teaching this: draw the pipeline as tiers, not a binary. Ask "what tier is this code in right now — cold bytecode or hot optimized?" before "how to make it faster". The first optimization is often *not* to micro-opt the loop but to keep feedback monomorphic so tier-up happens at all. Demo with `--trace-opt --trace-deopt` on a single file in a workshop; never check those flags into CI. Connect to deopt next (§1.2) — speculation explains both speed and cliffs.
