## 5.1. Event loop yielding responsiveness and scheduling

### 1) **Definition — the responsiveness triangle**

The same event loop (see [Async 1.1](<../../../13 Async Event Loop and Promises/sections/1. Event loop and the job queue/1.1. Call stack run-to-completion and the event loop.md>)) that runs your handler also must render, handle input, and drain I/O. A *long task* (>50 ms in browser RAIL, >16 ms per frame) blocks that loop. *Yielding* breaks a long task into queued chunks so the loop can interleave rendering/I/O; *scheduling* chooses the queue (microtask vs timer vs `requestAnimationFrame`/`requestIdleCallback` / `scheduler.yield`) and the concurrency bound (`p-limit` pools beat unbounded `Promise.all`).

### 2) **What problem it solves / history**

JS is run-to-completion: once a task starts, it can't be preempted. Early web apps froze on big loops; Gmail's chunked rendering (2006) and Node's `setImmediate` (2012) introduced cooperative yielding. `requestAnimationFrame` (2011) aligned work to 60 fps; `requestIdleCallback` (2015), `scheduler.yield` (2023, Chrome), and `scheduler.postTask` (2023) gave browser-prioritized yield points; on Node, `setImmediate` / `scheduler.yield` (via `node:timers/promises`) and `AbortSignal` wired concurrency bounds.

### 3) **Modern guidance — yield at the right granularity, bound the fans**

```js
// BAD: long task blocks loop — jank, input delay, I/O starvation.
function sumHugeBad(n) {
  let s = 0;
  for (let i = 0; i < n; i++) s += i; // 20M iterations → long task (>50ms)
  return s;
}
console.log(sumHugeBad(1_000_000)); // fast enough here, but scales to jank at 20M

// GOOD: chunked yielding — each chunk is a short task, loop interleaves.
async function sumHugeGood(n, chunk = 100_000) {
  let s = 0;
  for (let offset = 0; offset < n; offset += chunk) {
    const end = Math.min(offset + chunk, n);
    for (let i = offset; i < end; i++) s += i;
    // Yield to the loop: browser `scheduler.yield` or `setTimeout(0)`; Node `setImmediate`.
    // `queueMicrotask` would NOT yield to rendering (microtasks drain exhaustively) — avoid for yielding.
    await new Promise((res) => setTimeout(res, 0)); // yields to macrotask queue
  }
  return s;
}
sumHugeGood(1_000_000).then((v) => console.log("chunked", v)); // 499999500000

// Bounded concurrency — Promise.all fan-out vs p-limit pool.
async function fetchOne(i) { return i * 2; } // stand-in for I/O
async function allUnbounded(n) {
  const ps = Array.from({ length: n }, (_, i) => fetchOne(i));
  return Promise.all(ps); // n microtasks + n I/O at once — thundering herd
}
async function pooled(n, limit = 5) {
  let idx = 0, active = 0, out = Array(n);
  return new Promise((resolve, reject) => {
    function runNext() {
      while (active < limit && idx < n) {
        const cur = idx++;
        active++;
        fetchOne(cur).then((v) => {
          out[cur] = v; active--; if (idx === n && active === 0) resolve(out); else runNext();
        }, reject);
      }
    }
    runNext();
  });
}
Promise.all([allUnbounded(10).then((a) => console.log("all", a.length)), pooled(10, 3).then((a) => console.log("pooled", a.length))]);

// Choosing the queue:
// - queueMicrotask / Promise.then -> microtask queue — runs before next rendering/timer — use for "after current task, before I/O", not for yielding.
// - setTimeout(0) / setImmediate -> macrotask — yields to rendering and timers — use for chunking.
// - requestAnimationFrame (browser) -> before paint — use for DOM writes that must be in-frame.
// - requestIdleCallback / scheduler.yield (browser) -> idle-prioritized — use for non-urgent background.
function tickChoice() {
  queueMicrotask(() => console.log("micro — still same frame"));
  setTimeout(() => console.log("macro — next task, rendering could have run"), 0);
}
tickChoice();
```

### 4) **Common confusion**

- "`queueMicrotask` yields" — it doesn't. Microtasks drain exhaustively after every macrotask, so a microtask loop starves rendering and timers (Async §1.2). Use `setTimeout(0)`/`setImmediate`/`scheduler.yield` to yield.
- "`setTimeout(0)` is immediate" — it's minimum ~4 ms in nested browsers (clamped) and Node's timers phase; `setImmediate` (Node) or `scheduler.postTask` browser runs earlier in the check phase. All three yield — pick the one whose queue you want.
- "Bounded concurrency is slower" — unbounded fan-out is often *slower* under load due to contention, socket limits, and GC pressure from `n` simultaneous promises; bounded keeps p95 lower.

### 5) **Performance note**

Rendering budget is ~16 ms/frame at 60 fps; input responsiveness budget is ~50 ms. Measure your worst handler with `performance.now()` around the synchronous portion plus `PerformanceObserver` for long tasks / `queueMicrotask` depth. If any handler exceeds the budget, chunk it until the longest chunk < budget, then verify with a before/after `node --cpu-prof` trace: the single wide bar should become many narrow bars with gaps for rendering/I/O. Link yielding → GC pressure (§18): smaller chunks allocate less per task and recoup sooner.

### 6) **Mentor note**

Code-review rubric: every route/handler with a loop >10k iterations or `await` + `map` over user input must answer "what's the longest synchronous slice and what queue does it yield to?" Require `AbortSignal` wired through pools so cancellation actually stops the remaining chunks. Teach the three queues as a table (micro vs macro vs rAF) once, then reuse it. Demo with the chunked sum above measured via `performance.now()` before vs after.
