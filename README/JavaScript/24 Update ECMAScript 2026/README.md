## Update ECMAScript 2026 (feature map + where it lives in this repo)

This domain is an **index** for ECMAScript 2026-era language features (17th edition, ratified 2026-06-30 — ECMA-262 17.0). Deep explanations live in the linked topical domains below; this file only routes you there. No concept is re-taught here; every entry is a one-line mention + link per the anti-boilerplate law (§5).

> Scope: ES2026 added six specification groups — **`Array.fromAsync`**, **`Error.isError`**, **`Math.sumPrecise`**, **`Map.prototype.getOrInsert` / `getOrInsertComputed`** (and `WeakMap` variants), **`Uint8Array` Base64/Hex** (`toBase64`/`fromBase64`/`toHex`/`fromHex`/`setFromBase64`/`setFromHex`), and **`JSON.rawJSON` / `JSON.isRawJSON`**. Two high-profile proposals — **`Temporal`** and **Explicit Resource Management (`using`/`await using`)** — reached Stage 4 only after the June 30 cutoff and are **slated for ES2027** (see §7 below). Runtime support: `Array.fromAsync` + `JSON.rawJSON`/`isRawJSON` shipped in Node.js 22 (V8 12.4+ / Chrome 121+ / Firefox 115+ — already in Node 22.23.2); `Error.isError` in Node.js 24 (V8 13.4+ / Chrome 134+ / Firefox 138+); `Math.sumPrecise` in Node.js 24 (V8 13.7+ / Chrome 137+ / Firefox 136+); `Map.getOrInsert`/`getOrInsertComputed` in Node.js 24 (V8 14.4+ / Chrome 144+ / Firefox 139+); `Uint8Array` Base64/Hex in Node.js 24 (V8 13+ / Chrome 139+ / Firefox 133+). All claims labeled "ES2026 era" below.

## 1. `Array.fromAsync` — collect async iterables without the `for await` loop

### [1.1. Creating arrays — `Array.fromAsync(iterable, mapFn?, thisArg?)` as the async counterpart to `Array.from`](<../08 Arrays/sections/1. Arrays are exotic objects/1.2. Creating arrays literals the Array constructor trap Array.of and Array.from.md>)

1. **Why it exists** (`Array.from` handled sync iterables/array-likes but collecting an async iterable required `for await (const x of src) out.push(x)` or a helper; `Array.fromAsync` standardizes the pattern — `await Array.fromAsync(asyncGen)` awaits each element (and awaits promises yielded by sync iterables) and returns a dense `Array`)
2. **Production guidance** (`await Array.fromAsync(source)` where `source` is any async iterable, sync iterable of promises, or array-like of promises; optional `mapFn` `(value, index) => mapped` is awaited per element like `Array.from`'s second arg — `await Array.fromAsync(gen, x => x.id)` — errors reject the returned `Promise`; dense output — holes never appear because async sources produce values, not missing indices — see [holes vs undefined](<../08 Arrays/sections/2. Holes sparsity and length/2.1. Holes vs undefined sparse arrays and empty slots.md>) for why this differs from sparse sync arrays)
3. **Before vs after** (pre-ES2026: manual `for await` accumulation with per-gen boilerplate and inconsistent `mapFn` awaiting; now: single `await Array.fromAsync` — see [async iteration `for await...of`](<../10 Iterables Generators and Async Iteration/sections/4. Async iteration/4.1. Async iterables Symbol.asyncIterator and for await...of.md>) for the underlying protocol and [async generators](<../10 Iterables Generators and Async Iteration/sections/4. Async iteration/4.2. Async generators async yield and composition.md>) for source creation; contrast with `Promise.all` — `fromAsync` awaits *sequentially* per element, not concurrently)

## 2. `Error.isError` — realm-safe error check without `instanceof`

### [2.1. Error taxonomy — `Error.isError(value)` as the cross-realm predicate (ES2026)](<../15 Error Handling and Debugging/sections/1. Error taxonomy/1.1. Built-in Error types and when engines throw them.md>)

1. **Why it exists** (`value instanceof Error` fails across realms — each `iframe`/`worker`/`vm` has its own `Error` constructor so `new iframe.contentWindow.Error("x") instanceof Error === false`; `Error.isError` checks the internal `[[ErrorData]]` slot directly so it is `true` for any `Error` subtype (`TypeError`, `RangeError`, `DOMException`-derived `Error`) from any realm)
2. **Production guidance** (`Error.isError(x)` → `true` for any native `Error` instance, `false` for `throw "string"` / `{name:"Error", message:"hi"}` fakes; use at catch boundaries and in logging/reporters before reading `err.stack`/`err.cause` — see [throw semantics — why always `Error`](<../15 Error Handling and Debugging/sections/2. Throwing and catching/2.1. throw semantics what is throwable and why always Error.md>) and [custom errors with `cause`](<../15 Error Handling and Debugging/sections/1. Error taxonomy/1.2. Custom errors cause chaining and AggregateError.md>) for the guard pattern `if (!Error.isError(e)) throw new TypeError("expected Error", {cause:e})`)
3. **When `instanceof` still reads fine** (single-realm library code where the same `Error` constructor is guaranteed — `instanceof` is shorter and avoids the ES2026 baseline `typeof Error.isError === "function"` guard needed on Node < 24 / Safari < 18.4)

## 3. `Math.sumPrecise` — compensated summation without hand-rolled Kahan

### [3.1. Math — `Math.sumPrecise(iterable)` for numerically stable sums (ES2026)](<../12 Numbers Dates Math and Temporal/sections/3. Math/3.1. Math object constants trigonometry logs and rounding.md>)

1. **Why it exists** (IEEE-754 summation accumulates rounding error — `0.1 + 0.2 === 0.30000000000000004` and `[0.1,0.2,0.3,0.4].reduce((a,b)=>a+b,0) === 1.0000000000000002`; `Math.sumPrecise([0.1,0.2,0.3,0.4]) === 1.0` via a spec-mandated compensated algorithm that keeps a high-precision intermediate, not a naive left fold)
2. **Production guidance** (`Math.sumPrecise(iterable)` accepts any iterable of numbers (array, `Set`, generator); coerces each element via `ToNumber` — non-number throws `TypeError` (not silent `NaN`); `NaN`/`Infinity` propagate per IEEE-754; empty iterable → `0`; use for financial/scientific aggregation over many terms where naive `reduce` drift matters — measure with [performance and JIT](<../19 Performance and JIT Mindset/README.md>) not micro-benchmark folklore — see [Number model](<../12 Numbers Dates Math and Temporal/sections/1. Number model/1.1. Number primitives IEEE-754 NaN Infinity and negative zero.md>) for `NaN`/`±Infinity` stickiness that composes with precise sums)
3. **When not to reach for it** (two-term `a+b` or small integer sums need no compensation — fast path is plain `+`; `Math.f16round` (ES2025) vs `f64` precise sum is a separate half-precision concern — keep [safe-integer `BigInt` boundary](<../12 Numbers Dates Math and Temporal/sections/1. Number model/1.2. Safe integers BigInt boundary epsilon and precision.md>) for integer precision beyond 53 bits)

## 4. `Map` upsert — `getOrInsert` / `getOrInsertComputed`

### [4.1. Map creation — `Map.prototype.getOrInsert(key, defaultValue)` / `getOrInsertComputed(key, callback)` and `WeakMap` variants (ES2026)](<../09 Collections Map Set and Weak References/sections/1. Map deep dive/1.1. Map creation SameValueZero insertion order and iteration.md>)

1. **Why it exists** (the 3-line `if (!map.has(k)) map.set(k, [])` / `map.get(k).push(v)` upsert pattern appears in virtually every codebase — caches, group-by accumulators, memo tables — and is race-prone to duplicate; `getOrInsert` atomizes it: `map.getOrInsert(k, defaultValue)` returns the existing value or inserts `defaultValue` and returns it in one `SameValueZero`-keyed operation)
2. **Production guidance** (`map.getOrInsert(key, [])` returns `value` (existing or newly inserted); `map.getOrInsertComputed(key, k => compute(k))` calls `callback` only when the key is absent — receiving the `key` as its arg and sharing `SameValueZero` semantics (`NaN` matches `NaN`, `-0` ≡ `+0`); `WeakMap.prototype.getOrInsert` / `getOrInsertComputed` accept objects or non-registered `Symbol` (ES2023 symbols-as-weak-keys) — see [WeakMap ephemeron keys](<../09 Collections Map Set and Weak References/sections/3. Weak collections/3.1. WeakMap ephemeron keys non-iterability and use cases.md>) for lifetime rules; insertion honors [insertion order](<../09 Collections Map Set and Weak References/sections/1. Map deep dive/1.1. Map creation SameValueZero insertion order and iteration.md>) — existing entry keeps its order, new entry appends)
3. **Choosing which form** (`defaultValue` known cheap → `getOrInsert`; expensive-to-compute or key-derived → `getOrInsertComputed` to avoid eager construction — keep [choosing the right collection](<../09 Collections Map Set and Weak References/sections/5. Choosing and performance/5.1. Choosing the right collection Map vs Object vs Set vs Array and Weak variants.md>) for when a plain `Object`/`Array` still wins; for multi-step transactional upsert keep manual `has`/`set` under a lock, not as a style rule)

## 5. `Uint8Array` Base64 / Hex — native binary ↔ text without `atob`/`btoa` hacks

### [5.1. ArrayBuffer and TypedArray — `Uint8Array.prototype.toBase64` / `toHex` and static `fromBase64`/`fromHex` / `setFromBase64`/`setFromHex` (ES2026)](<../08 Arrays/sections/5. Transforming ordering and typed preview/5.3. ArrayBuffer TypedArray and DataView how they differ from Array.md>)

1. **Why it exists** (binary → `Base64`/`Hex` and back previously required `btoa`/`atob` (which are `Latin-1`-only and throw on bytes > 255), `Buffer.from(bytes).toString("base64")` (Node-only), or manual lookup tables — all inconsistent and allocation-heavy; native `Uint8Array` methods give a typed-array-owned encoding with `alphabet` + `omitPadding`/`strict` options per spec)
2. **Production guidance** (`bytes.toBase64(options?)` / `Uint8Array.fromBase64(string, options?)` and `bytes.toHex()` / `Uint8Array.fromHex(string)` and instance `bytes.setFromBase64(string, offset?)` / `setFromHex(string, offset?)` that write into an existing buffer and return `{read,written}`; options: `alphabet: "base64" | "base64url"` and `omitPadding: boolean` and `lastChunkHandling: "loose"|"strict"|"stop-before-partial"` for streaming — `strict` rejects non-canonical padding — see [data exchange patterns](<../16 JSON Serialization and Data Exchange/sections/5. Beyond JSON structuredClone and data exchange/5.2. Data exchange patterns APIs NDJSON binary and base64.md>) for when raw `ArrayBuffer`/`Blob` beats `Base64` (~33% expand) and `Response.arrayBuffer()`)
3. **Before vs after** (pre-ES2026: `btoa(String.fromCharCode(...bytes))` throws on large arrays (stack/arg-length limit) and corrupts bytes > 127; now: `bytes.toBase64()` handles arbitrary length and `Uint8Array.fromBase64` validates per spec — guard with `typeof Uint8Array.prototype.toBase64 === "function"` on Node < 24 / Firefox < 133)

## 6. `JSON.rawJSON` / `JSON.isRawJSON` — lossless high-precision JSON numbers

### [6.1. JSON grammar — `JSON.rawJSON(text)` and `JSON.isRawJSON(value)` for decimal-exact round-trips (ES2026)](<../16 JSON Serialization and Data Exchange/sections/1. JSON as a format/1.1. JSON grammar vs JavaScript literals history and the JSON superset.md>)

1. **Why it exists** (`JSON.stringify` serializes `Number` via `ToString` — `9007199254740993` already collapsed to `9007199254740992` before it hits the wire and `0.1` may round-trip as `0.100000000000000005`; `JSON.rawJSON("9007199254740993")` creates a *raw JSON text* wrapper whose `JSON.stringify({n: JSON.rawJSON("9007199254740993")})` emits `{"n":9007199254740993}` without quoting and without `Number` conversion, so 64-bit IDs and decimal financial values survive verbatim)
2. **Production guidance** (`JSON.rawJSON(text)` where `text` is a valid JSON number literal (`"123"`, `"-0.1e+10"`, `"9007199254740993.123"` — not `"NaN"`/`"Infinity"` which are not JSON); `JSON.isRawJSON(x)` tests for the wrapper; `JSON.stringify` inlines the raw text — `JSON.stringify({price: JSON.rawJSON("19.99")})` → `{"price":19.99}`; parsing still yields `Number` (so `9007199254740993` will still collapse on `JSON.parse` — keep IDs as strings when the consumer also needs lossless integers, or parse with a `reviver` that keeps the raw text — see [numbers beyond safe integer](<../16 JSON Serialization and Data Exchange/sections/4. Edge cases and lossy conversions/4.2. Numbers beyond safe integer Infinity NaN and negative zero.md>) and [toJSON protocol](<../16 JSON Serialization and Data Exchange/sections/2. Stringifying and serialization/2.3. toJSON protocol custom serialization and recursion.md>) for ordering — `toJSON` runs before raw inspection)
3. **When to keep string-IDs instead** (if any hop may `JSON.parse` without a raw-aware parser, the raw number will still become a `Number` and lose bits — prefer `{"id":"9007199254740993"}` string contracts for cross-language 64-bit safety and reserve `rawJSON` for hops where the emitter controls both ends or the receiver preserves raw text)

## 7. What is NOT in ES2026 (pushed to ES2027 — do not ship as ES2026)

1. **`Temporal` (the `Date` replacement) — ES2027, not ES2026** — immutable `Instant`/`PlainDate`/`ZonedDateTime`/`Duration` with time-zone and calendar support reached Stage 4 at the March 2026 TC39 meeting *after* the June 30 ES2026 cutoff; deep `Temporal` already lives in [Numbers, Dates, Math, Temporal](<../12 Numbers Dates Math and Temporal/README.md>) (`[5.1](<../12 Numbers Dates Math and Temporal/sections/5. Temporal/5.1. Temporal overview Instant PlainDate PlainTime PlainDateTime.md>)` / `[5.2](<../12 Numbers Dates Math and Temporal/sections/5. Temporal/5.2. Temporal ZonedDateTime Duration calendar and migration.md>)`) behind `typeof Temporal !== "undefined"` + `@js-temporal/polyfill` — this index will add a `Temporal` entry in the ES2027 update once the 18th edition ratifies it.
2. **Explicit Resource Management (`using`/`await using` + `Symbol.dispose`/`Symbol.asyncDispose` + `SuppressedError`) — ES2027, not ES2026** — deterministic scope-based cleanup (`using file = open(...)`) — pattern already referenced in [Error Handling](<../15 Error Handling and Debugging/sections/3. Defensive patterns/3.1. Cause wrapping context preservation and suppressed errors.md>) and [Memory Management](<../18 Memory Management and GC/sections/5. Measuring and preventing leaks/5.2. Preventing leaks bounded caches eviction WeakMap and dispose patterns.md>) as ES2024-era `SuppressedError` plus `using` Stage 4 post-cutoff; guarded with `Function("using x = null")` until ratified.
3. **How to track the boundary** — spec edition = ratification date: 14th ES2023 2023-06-13, 15th ES2024 2024-06-18, 16th ES2025 2025-06-25, **17th ES2026 2026-06-30** — any proposal whose Stage 4 vote landed after June 30 2026 belongs to the 18th edition (ES2027); check `tc39.es/ecma262` edition header, not polyfill READMEs, for the authoritative list.
