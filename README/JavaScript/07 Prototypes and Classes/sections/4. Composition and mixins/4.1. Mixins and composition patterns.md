## 4.1. Mixins and composition patterns

### 1) **Mixin as function that returns a subclass**

**Definition** — a *mixin* is `Base => class extends Base { ... }` — a function that takes a base constructor and returns a derived class adding traits. Composing mixins `M2(M1(Base))` builds a chain without multiple inheritance diamond. Each mixin should call `super()` in its constructor and use `super` in methods to preserve chain order.

```js
// Two traits
const Timestamped = (Base) =>
  class extends Base {
    constructor(...args) {
      super(...args);
      this.createdAt = Date.now();
    }
    ageMs() { return Date.now() - this.createdAt; }
  };

const Validatable = (Base) =>
  class extends Base {
    validate() {
      if (this.ageMs && this.ageMs() < 0) throw new Error("future");
      return true;
    }
  };

// Composition order matters: Timestamped first satisfies Validatable's dependency on ageMs
class Model { constructor(name) { this.name = name; } }
class User extends Validatable(Timestamped(Model)) {
  constructor(name) { super(name); }
}

const u = new User("ada");
console.log(u.name, typeof u.createdAt === "number", u.validate()); // ada true true
console.log(u instanceof User, u instanceof Model); // true true — chain preserved
console.log(Object.getPrototypeOf(User) === Validatable(Timestamped(Model)) ? "mixin chain" : "check");

// Alternative: M2(M1(Base)) helper
const compose = (...mixins) => (Base) => mixins.reduceRight((Cls, mix) => mix(Cls), Base);
class Article extends compose(Validatable, Timestamped)(Model) {}
console.log(new Article("post") instanceof Model); // true

// Why mixins beat deep hierarchies: each trait is orthogonal, testable in isolation, and order is explicit
```

- Modern guidance: prefer **factory-mixins** (function returning subclass) over `Object.assign(Prototype, trait)` because they respect constructor chain, `super`, and private brands (trait can add `#field` safely). Keep trait APIs narrow and document required `super` calls.

### 2) **Object-level mixins via Object.assign on prototypes**

**Definition** — copying method descriptors directly onto prototypes (or instances) via `Object.assign` or `Object.defineProperties + getOwnPropertyDescriptors` mixes behavior without subclassing. Use descriptor copy to preserve accessors and enumerability (→ [Objects §4.1](../../../06 Objects in Depth/sections/4. Object utilities and copying/4.1. Assign merging shallow copy and fromEntries.md)); assignment copy flattens accessors to values.

```js
// Trait as plain object
const Loggable = {
  log(msg) { console.log(`[${this.name ?? this.constructor.name}] ${msg}`); },
  get tag() { return this.name ?? "unnamed"; }
};

// Assign to prototype — assignment version flattens accessor
class Core {}
Object.assign(Core.prototype, Loggable);
console.log(Core.prototype.log); // function — method copied as data, works but tag became value? Actually assign invoked getter on source? No, Loggable.tag getter reads this of Loggable (no this.name) → "unnamed" flattened as data!
console.log(Object.getOwnPropertyDescriptor(Core.prototype, "tag").value); // unnamed — data, not accessor! Bad

// Correct: descriptor copy preserves accessor
class Core2 {}
Object.defineProperties(Core2.prototype, Object.getOwnPropertyDescriptors(Loggable));
console.log(typeof Object.getOwnPropertyDescriptor(Core2.prototype, "tag").get); // function — preserved
const c = new Core2(); c.name = "core2";
console.log(c.tag); // core2 — accessor works with this
c.log("hi"); // [core2] hi

// Per-instance assign
const s = new Core2();
Object.assign(s, { extra: 1 }); // own mixin — not via prototype, isolated to instance

// Trade-off vs subclass mixin: assign-mixins don't participate in instanceof, and cannot add private #fields
console.log(c instanceof Core2); // true — but not instanceof Loggable (Loggable is not a class)
```

### 3) **Composition vs inheritance decision table**

| Goal | Pick inheritance (`class extends`) | Pick mixin function | Pick object mixin / composition |
|------|------------------------------------|----------------------|---------------------------------|
| Taxonomy with `instanceof` | ✓ — `is-a` (Dog is Animal) | ✓ — chain still instanceof | ✗ — no chain identity |
| Add orthogonal trait (timestamp, validation, retry) | ✗ — hierarchy explosion | ✓ — compose traits | ✗/✓ — shallow copy, no `super` |
| Private encapsulation with `#field` | ✓ — brand-checked | ✓ — mixin can introduce own `#field` | ✗ — cannot add private |
| Share trait across unrelated bases | ✗ — single parent | ✓ — `Mixin(Base)` works for any Base | ✓ — assign to any prototype |
| Override + call `super` | ✓ — natural `super.method()` | ✓ — mixin overrides still use `super` | ✗ — no `super` in plain object (unless concise method with `__proto__`) |

```js
// Composition (has-a) often beats inheritance — delegate instead of extend
class Engine { start() { return "vroom"; } }
class Car {
  #engine = new Engine(); // composition: private field holds collaborator
  start() { return this.#engine.start() + " 🚗"; }
}
console.log(new Car().start()); // vroom 🚗 — no inheritance needed; Car not an Engine

// When is-a is real, inheritance is fine; when has-a, compose
// Heuristic: if you test Liskov substitution ("can Child stand in for Parent in every test?"), not always — then compose
```

### 4) **Common confusion**

- "Mixin needs multiple inheritance" — JavaScript has single inheritance chain; mixin functions *are* the composition mechanism (chaining `M2(M1(Base))` yields one linear chain).
- "`Object.assign` preserves getters" — no; it reads value (getter fires) and writes data. Descriptor copy preserves.
- "Mixin can access parent's `#private`" — no; each mixin's `#field` is distinct lexical brand; use protected accessor or constructor param to share.

### 5) **Performance note**

Mixin composition creates one subclass per `Mixin(Base)` call — done once at definition, not per instance. Object.assign mixins on hot prototypes that are created per request re-define descriptors per request (slow). Prefer subclass composition at class definition time; reserve `Object.assign` mixins for once-at-startup decoration. As ever, [measure](../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md).

### 6) **Mentor note**

Give trainees two traits `Timestamped` and `Validatable` where `Validatable` depends on `Timestamped` — have them discover the correct `Validatable(Timestamped(Model))` order vs the failing reverse. Ask them to convert the same traits from assign-mixin to subclass-mixin and predict `instanceof` and accessor preservation — if they choose subclass-mixin for brand and `super`, composition trade-offs are solid.
