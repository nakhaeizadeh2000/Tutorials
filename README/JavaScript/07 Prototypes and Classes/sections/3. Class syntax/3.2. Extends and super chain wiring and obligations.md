## 3.2. Extends and super: chain wiring and obligations

### 1) **extends wires two chains**

**Definition** — `class Child extends Parent` wires two `[[Prototype]]` links: instance chain `Child.prototype.[[Prototype]] = Parent.prototype` (instances delegate to parent methods), and constructor chain `Child.[[Prototype]] = Parent` (static members inherit: `Child.staticMethod` resolves via `Parent`). Either link is walkable via `Object.getPrototypeOf`.

```js
class Parent {
  static kind() { return "Parent static"; }
  method() { return "Parent method"; }
}
class Child extends Parent {
  method() { return super.method() + " → Child"; }
  static kind() { return super.kind() + " → Child static"; }
}

console.log(Object.getPrototypeOf(Child.prototype) === Parent.prototype); // true — instance delegation
console.log(Object.getPrototypeOf(Child) === Parent); // true — static inheritance

const c = new Child();
console.log(c.method()); // Parent method → Child — super in instance method (see §3 below)
console.log(Child.kind()); // Parent static → Child static — super in static method

// No extends → instance prototype is Object.prototype, constructor prototype is Function.prototype
class Plain {}
console.log(Object.getPrototypeOf(Plain.prototype) === Object.prototype); // true
console.log(Object.getPrototypeOf(Plain) === Function.prototype); // true

// extends null is a special case: prototype chain ends immediately, no super() needed
class NullBase extends null {
  constructor() { super(); } // still required in derived constructor but parent is null
}
console.log(Object.getPrototypeOf(NullBase.prototype) === null); // true — no Object.prototype delegation
console.log(typeof NullBase.prototype.toString); // undefined — no inherited toString

// extends expression is evaluated once at class definition — can be any constructor or null
function makeBase(flag) { return flag ? Parent : null; }
class Conditional extends makeBase(true) {}
console.log(Conditional.prototype instanceof Parent); // true-ish: getPrototypeOf check above
```

- Modern guidance: prefer `extends` over manual `Object.setPrototypeOf` / surrogate constructors. `extends` handles both instance and static chains atomically and keeps hidden classes stable (the fastest path).

### 2) **super() must run before this in derived constructors**

**Definition** — derived constructors (with `extends`) allocate `this` *inside* `super(...)` via the parent constructor's allocation. Accessing `this`, `super`, or returning before `super()` throws `ReferenceError: Must call super constructor in derived class before accessing 'this'`. `super(args)` calls `Parent.constructor` with `this` as if by `Parent.call(this, ...)` and returns the instance (or a replacement object if parent returns an object).

```js
class Base {
  constructor(id) { this.id = id; }
  static create() { return new this(); } // new.target-aware factory
}

class Derived extends Base {
  #extra;
  constructor(id, extra) {
    // console.log(this); // ReferenceError — this uninitialized
    // this.oops = 1;    // same
    super(id); // Parent allocates and initializes this.id; this now valid
    this.#extra = extra; // now safe — fields after super
  }
  get extra() { return this.#extra; }
}

console.log(new Derived(1, 2).extra); // 2
console.log(new Derived(1, 2).id); // 1 — set by super

// Omitting super in derived constructor without explicit constructor? Implicit super is inserted: Derived { } means constructor(...args){ super(...args); }
class Implicit extends Base {}
console.log(new Implicit(5).id); // 5 — synthetic super forwards all args

// super() forwarding vs explicit args
class A extends Base { constructor(a, b) { super(a + b); this.sum = a + b; } }
console.log(new A(1, 2).sum); // 3

// Which error to expect when forgetting super()
class Forget extends Base {
  constructor() { this.x = 1; } // missing super
}
try { new Forget(); } catch (e) { console.log(e.name, e.message.includes("super")); } // ReferenceError must call super

// super() may return a different object (if Parent constructor returns object) — derived this is then that object
class Replacer extends Base {
  constructor() { return { hijacked: true }; } // no super, replacing — only allowed if you don't use this before? Actually derived without super must not use super, but returning object replaces this
}
console.log(new Replacer().hijacked); // true — instance is not a Base instance post-replacement

// Also works with function constructors extended by class (but extending function with class allocates via function path)
function FuncBase(id) { this.id = id; }
class ExtendsFunc extends FuncBase {}
console.log(new ExtendsFunc(9).id); // 9 — works, but prefer class–class hierarchy for clarity
```

### 3) **super.prop inside methods follows the home object's prototype**

**Definition** — `super.foo` inside a method (concise method, class method, getter/setter, or constructor arrow? No — arrows have no `super`) resolves via the method's `[[HomeObject]]` = the prototype object where the method was defined, then walks one hop to `HomeObject.[[Prototype]]`. This is *not* the receiver's chain walk; it's lexical to the method definition site. `super()` in constructors is a distinct call form.

```js
class Parent2 {
  greet() { return "Parent2"; }
  static greet() { return "Parent2 static"; }
}
class Child2 extends Parent2 {
  greet() { return super.greet() + " → Child2"; } // HomeObject = Child2.prototype; walk to Parent2.prototype
  static greet() { return super.greet() + " → Child2 static"; } // HomeObject = Child2; walk to Parent2 (static chain)
}

console.log(new Child2().greet()); // Parent2 → Child2
console.log(Child2.greet()); // Parent2 static → Child2 static

// super in derived instance method that mutates via setter on parent
class Counter {
  #n = 0;
  get n() { return this.#n; }
  set n(v) { this.#n = v; }
  inc() { this.n += 1; return this.n; }
}
class Double extends Counter {
  inc() { super.inc(); return super.inc(); } // two parent increments
}
console.log(new Double().inc()); // 2 — super.inc() called twice with this = Double instance

// super vs explicit prototype call
class Child3 extends Parent2 {
  greetExplicit() { return Parent2.prototype.greet.call(this); } // manual, similar but not identical to super
}
console.log(new Child3().greetExplicit()); // Parent2 — but super handles home-object binding correctly for accessors too
// Why super matters for accessors: super getter calls with this = receiver, but looks up via home chain
class WithAccessor {
  get label() { return "base"; }
}
class Sub extends WithAccessor {
  get label() { return super.label + "-sub"; } // super walks to WithAccessor.prototype getter
}
console.log(new Sub().label); // base-sub

// Common bug: arrow method with super — arrows capture lexical super from surrounding non-method, often missing
class Bad {
  method() {
    const arrow = () => super.toString(); // SyntaxError? super in arrow inside method actually works (lexical super), but super in arrow defined as field is invalid
    return arrow();
  }
}
console.log(typeof new Bad().method); // function

// DRY alternative without super: explicit delegation is more verbose and brittle for private-link updates
```

- Modern guidance: use `super` for method overrides and `super()` for construction; avoid manual `Parent.prototype.method.call(this)` unless you need to call a specific prototype level out of order. Remember `super` is lexical to `[[HomeObject]]`, not dynamic to `this`.

### 4) **Common confusion**

- "`extends` only wires instance chain" — it wires *two* chains (instance + static).
- "`super()` is optional in derived constructors" — required before touching `this`/`super` or returning implicitly; only synthetic constructor auto-calls `super(...args)`.
- "`super` follows `this`'s prototype" — no; follows `[[HomeObject]].[[Prototype]]` lexically.
- "Class `extends` is sugar and removable" — it sets both links and sets `[[IsClassConstructor]]`, enforces `new`, and allocates correctly across built-ins (`class MyArray extends Array` correctly sets `Species` etc where manual `setPrototypeOf` would not).

### 5) **Performance note**

`extends` at class evaluation is a single map creation for both prototype links — the JIT's hottest path. Manual `Child.prototype.__proto__ = Parent.prototype` after class evaluation triggers deopt like any `setPrototypeOf`. Keep class definitions at top level (not inside hot functions) to avoid re-creating prototype maps per call. As ever, [measure](../../../01%20Fundamentals%20and%20Mental%20Model/sections/2.%20How%20JavaScript%20executes/2.1.%20Parse%20bytecode%20JIT%20pipeline%20and%20single-threaded%20execution.md).

### 6) **Mentor note**

Ask trainees to predict `Object.getPrototypeOf(Child)`, `Object.getPrototypeOf(Child.prototype)`, and what `super()` vs `super.method()` each bind `this` to. If they name both chains and the pre-`super` TDZ, inheritance is solid. In review, flag any derived constructor that assigns `this` before `super()` or manual `Child.prototype = ...` after `extends`.
