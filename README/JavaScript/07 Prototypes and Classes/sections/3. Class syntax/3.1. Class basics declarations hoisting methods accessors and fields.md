## 3.1. Class basics: declarations, hoisting, methods, accessors, and fields

### 1) **class is sugar over constructor + prototype — with real differences**

**Definition** — `class C { ... }` defines a constructor function `C` plus `C.prototype` wiring in one declarative form. Unlike function constructors, classes are: always strict, non-enumerable prototype methods/accessors, TDZ (like `let` — early use throws `ReferenceError`), must be called with `new` (`[[IsClassConstructor]]`), have no hoisted creation phase, and support `super`, `extends`, private `#fields`, and static blocks.

```js
// Desugared equivalence (approximate)
function FooA(x) { this.x = x; }
FooA.prototype.method = function () { return this.x; };
Object.defineProperty(FooA.prototype, "method", { enumerable: false }); // class methods are non-enumerable

class Foo {
  constructor(x) { this.x = x; }
  method() { return this.x; }
}
console.log(typeof Foo); // function
console.log(Object.getOwnPropertyDescriptor(Foo.prototype, "method").enumerable); // false — class sugar
console.log(Object.getOwnPropertyDescriptor(FooA.prototype, "method").enumerable); // false after we mimicked — function version default is true unless defined as above

// TDZ like let: class declarations not hoisted
try { new Early(); } catch (e) { console.log(e.name); } // ReferenceError — TDZ
class Early {}
console.log(new Early() instanceof Early); // true — after declaration

// Class declarations are block-scoped
{
  class BlockScoped {}
  console.log(typeof BlockScoped); // function — inside block
}
try { console.log(typeof BlockScoped); } catch (e) { console.log(e.name); } // ReferenceError — not leaked

// Class expressions can be anonymous or named (name inferred like NFE → [Functions §1.1](../../../05%20Functions%20Deep%20Dive/sections/1.%20Function%20forms%20and%20the%20function%20object/1.1.%20Function%20declarations%20expressions%20and%20hoisting.md))
const Expr = class Named { value() { return "hi"; } };
console.log(Expr.name); // Named — named class expression inner name
console.log(typeof Named); // undefined — inner name not in outer scope
```

- Modern guidance: prefer `class` for shared-behavior types — its non-enumerable methods don't pollute `for-in`/`keys`, its `new` enforcement prevents forgotten-`new` bugs, and its TDZ surfaces declaration-order mistakes early (unlike function hoisting which hid them).

### 2) **Instance fields, accessors, and computed names**

**Definition** — instance fields `field = value` / `field;` run *per instance* after `super()` (derived) and assign own properties (enumerable, writable, configurable:true). Accessors `get`/`set` on the prototype remain accessors. Computed names `[expr]` evaluate once at class evaluation.

```js
class Point {
  x = 1; // instance field — own, per instance
  static marker = "point"; // static field on constructor, not instance
  #private = 42; // private (→ [3.3](./3.3.%20Private%20fields%20and%20methods%20brand%20checks%20and%20encapsulation.md))

  constructor(y) { this.y = y; }
  get len() { return Math.hypot(this.x, this.y); } // accessor on prototype
  method() { return this.len; }
}

const p = new Point(2);
console.log(p); // Point { x: 1, y: 2 } — #private not shown (truly hidden)
console.log(Object.hasOwn(p, "x")); // true — instance field is own
console.log(Object.getOwnPropertyDescriptor(p, "x").enumerable); // true — fields are enumerable
console.log(Object.getOwnPropertyDescriptor(Point.prototype, "len").get); // function — accessor lives on prototype, not instance
console.log(Object.getOwnPropertyDescriptor(Point, "marker").value); // point — static on constructor
console.log(p.len); // √5 — accessor via delegation

// Field evaluation order: instance fields top-to-bottom, computed names evaluate left-to-right at class evaluation
let n = 0;
class Ordered {
  a = n++;
  b = n++;
  c = n++;
  ["d" + n] = n++; // computed field name evaluates in order
}
console.log(new Ordered()); // Ordered { a:0, b:1, c:2, d3: 3 } — order is declaration order

// Overriding field vs prototype method: field assignment after super shadows prototype method
class Base { method() { return "base"; } }
class Child extends Base {
  method = () => "field"; // instance field arrow shadows prototype method of same name
}
console.log(new Base().method()); // base — prototype method
console.log(new Child().method()); // field — own field wins (shadows) — usually a bug; avoid same name
console.log(Object.hasOwn(new Child(), "method")); // true — field is own
```

- *History* — public instance fields are ES2022; static blocks ES2022; private `#` ES2022. All now baseline widely available (2026). Older transpilers moved fields to constructor assignment.

### 3) **Common misread: class hoisting**

**Definition** — function declarations hoist (usable before line, see [Variables §2.2](../../../04%20Variables%20Scope%20and%20Closures/sections/2.%20Scope%20and%20lookup/2.2.%20Hoisting%20the%20reality%20creation%20phase%20not%20magic.md)), but `class` like `let` is in TDZ until declaration executes. Class expressions assigned to `const` also obey TDZ. This catches circular-dependency and top-down order mistakes.

```js
// Function hoists, class does not
console.log(typeof hoistedFn); // function — hoisted
function hoistedFn() {}

try { console.log(typeof HoistedClass); } catch (e) { console.log(e.name); } // ReferenceError — TDZ
class HoistedClass {}
console.log(typeof HoistedClass); // function — after

// Subclass TDZ: extends target also in TDZ
try { class Bad extends AlsoNotYet {} } catch (e) { console.log(e.name); } // ReferenceError
class AlsoNotYet {}
class Good extends AlsoNotYet {} // ok after base defined
console.log(new Good() instanceof AlsoNotYet); // true

// Methods vs fields: methods are on prototype, fields on instance — confusing them breaks inheritance expectations
class Counter {
  count = 0; // instance, per instance
  static nextId = 1; // static, shared on constructor
  inc() { this.count++; } // prototype method, shared
}
const a = new Counter(), b = new Counter();
a.inc(); a.inc();
console.log(a.count, b.count); // 2 0 — instance fields isolated
console.log(Counter.nextId, typeof Counter.nextId); // 1 number — static not on instances
console.log(a.inc === b.inc); // true — shared
console.log(a.count === b.count); // false — per instance
```

### 4) **Common confusion**

- "`class` is hoisted like `function`" — no; TDZ.
- "Instance field `x = 1` is on prototype" — no; own, per instance (like constructor assignment). Prototype methods are shared; fields are per instance.
- "Static members are on the prototype" — no; on constructor (`Class.staticMethod`, `Class.staticField`). Subclass statics inherit via `Child.__proto__ = Parent` (→ [3.2](./3.2.%20Extends%20and%20super%20chain%20wiring%20and%20obligations.md)).
- "Class methods are enumerable" — no; `enumerable: false` (like built-ins). Use `Object.keys(Point.prototype)` to see the difference vs `{ method(){} }` literal which is enumerable (→ [Objects §1.1](../../../06%20Objects%20in%20Depth/sections/1.%20Object%20creation%20and%20literals/1.1.%20Object%20literals%20shorthand%20computed%20properties%20and%20spread.md)).

### 5) **Performance note**

Class field per-instance assignment costs one define per field per instance — same as constructor `this.x = ...`. Non-enumerable prototype methods optimize better for `for-in` avoidance than enumerable methods that pollute `keys`. As ever, [measure](../../../01%20Fundamentals%20and%20Mental%20Model/sections/2.%20How%20JavaScript%20executes/2.1.%20Parse%20bytecode%20JIT%20pipeline%20and%20single-threaded%20execution.md).
