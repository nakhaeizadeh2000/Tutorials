## 3.4. Static members, static blocks, and class field order

### 1) **Static fields/methods live on the constructor**

**Definition** — `static` members are properties of the class *constructor* (function object) itself, not of `prototype`. Instances don't delegate to statics; constructors do via `Child.__proto__ = Parent` chain (→ [3.2](./3.2.%20Extends%20and%20super%20chain%20wiring%20and%20obligations.md)). Static methods can reference `this` as the *current* constructor (factory that respects subclassing) and `super` as the parent constructor.

```js
class Parent {
  static kind = "Parent";
  static greet() { return `${this.kind} static`; } // this === actual constructor (Parent or Child)
  static #counter = 0;
  static next() { this.#counter += 1; return this.#counter; }
}
class Child extends Parent {}

console.log(Parent.kind); // Parent
console.log(Child.kind); // Parent — inherited via Child.__proto__ === Parent (static chain)
Child.kind = "Child";
console.log(Parent.kind, Child.kind); // Parent Child — shadowing

console.log(Parent.greet(), Child.greet()); // Parent static Child static — this parameterized
console.log(Object.getPrototypeOf(Child) === Parent); // true — static inheritance link
console.log(Object.getPrototypeOf(Child.prototype) === Parent.prototype); // true — instance link (separate)

// Static private: per-class, accessible only inside declaring class (even subclasses see distinct counters)
console.log(Parent.next(), Parent.next()); // 1 2
try { console.log(Child.next()); } catch (e) { console.log(e.name + " on Child.next"); } // TypeError — brand check: Child not branded for Parent's static #counter (Child lacks Parent's static #counter brand)
try { console.log(Child.next()); } catch (e) { console.log(e.name); } // same throw, caught
// Fix: static private per class needs its own declaration in each class or protected via public static accessor

// Instance statics not delegated: instance cannot see static
const p = new Parent();
console.log(p.kind); // undefined — instances delegate to Parent.prototype, not Parent constructor
console.log(p.greet); // undefined
```

- Static field semantics like instance fields: `static field = expr` evaluates top-to-bottom, writable/enumerable/configurable true, but on the constructor.

### 2) **static {} runs once at class evaluation, with access to private names**

**Definition** — `static { ... }` (ES2022) runs *once* when the class (the constructor function) is created, `this` === constructor, lexical scope can access private `#names` of the enclosing class. No arguments, no own `super` outside `this.__proto__`-qualified calls, but `super.prop` works for parent statics.

```js
// Initialization that needs private scope or this — static block replaces imperative after-class code
let register = [];
class Widget {
  static size = 16;
  static #instances = 0;
  static #registry = new Map();
  static {
    // Runs exactly once, after static fields up to this point have evaluated, before class is usable later in file?
    // Actually static blocks run in declaration order interleaved with static field initializers — order matters (see §3)
    this.#registry.set("default", this.size);
    register.push("Widget block ran");
  }
  static count() { return this.#instances; }
  constructor() {
    this.id = ++Widget.#instances; // static private access via constructor name inside instance is allowed (lexical class)
  }
  static {
    register.push(`second block size=${this.size}`);
  }
}
const w1 = new Widget(), w2 = new Widget();
console.log(Widget.count(), w2.id); // 2 2 — private counter shared
console.log(register); // ["Widget block ran", "second block size=16"] — blocks ran once at evaluation, not per instance
// Widget.#registry outside class would be SyntaxError — static private only accessible inside class body
// Historically you would write Widget.registry = ... after class; static block keeps that logic lexically inside and private-aware

// super in static block
class Base { static base = 1; }
class Derived extends Base {
  static derived = 2;
  static { this.combo = super.base + this.derived; } // super in static block walks to Parent constructor
}
console.log(Derived.combo); // 3 — super.base is Base.base
```

- When to use `static {}` — deriving a second static from the first, populating a private `Map` cache, performing validation that needs private names, or registering the class in a framework registry without a post-class `Widget.register()` leak.

### 3) **Field order matters**

Instance fields and static fields/blocks evaluate *top-to-bottom* in declaration order; each initializer can see `this` (or `this.constructor` for statics) plus already-initialized preceding fields of the same `this`. In derived classes, instance fields evaluate *after* `super()` (because `this` doesn't exist until then).

```js
// Instance field order
let trace = [];
class Order {
  a = trace.push("a") && 1;
  b = trace.push("b") && 2;
  c = trace.push("c") && 3;
  constructor() { trace.push("constructor"); }
}
new Order();
console.log(trace); // ["a","b","c","constructor"] — fields before constructor body

// Static order: fields and blocks interleaved
let s = [];
class SOrder {
  static a = s.push("static a") && 1;
  static { s.push("block 1"); }
  static b = s.push("static b") && 2;
  static { s.push("block 2"); }
}
console.log(s); // ["static a","block 1","static b","block 2"] — textual order

// Derived class: base fields → super() → derived fields → derived constructor body
let dTrace = [];
class Base2 { baseField = dTrace.push("Base field") && "B"; constructor() { dTrace.push("Base ctor"); } }
class Derived2 extends Base2 {
  derivedField = dTrace.push("Derived field") && "D";
  constructor() { super(); dTrace.push("Derived ctor"); }
}
new Derived2();
console.log(dTrace.join(" → ")); // Base field → Base ctor → Derived field → Derived ctor — base fields before derived fields

// Shadowing via field after super vs prototype method (recap from [3.1](./3.1.%20Class%20basics%20declarations%20hoisting%20methods%20accessors%20and%20fields.md))
class HasMethod { method() { return "proto"; } }
class Override extends HasMethod {
  method = "field"; // instance field shadows prototype method
}
console.log(new HasMethod().method()); // proto
console.log(new Override().method); // field — not a function
console.log(typeof new Override().method); // string — shadowing is silent; avoid same name
```

- *Common bug* — instance field that references `this` parameter computed from constructor arg not yet assigned: `class C { x = this.id; constructor(id){ this.id=id; } }` — `x` evaluates before `this.id` set (if not relying on `super` order), so `x` is `undefined`. Fix: compute in constructor or initialize field as function of param via `x = null` then assign in constructor.

### 4) **Common confusion**

- "Static is on the prototype" — no; on constructor.
- "`static {}` runs per instance" — no; once per class evaluation.
- "Static private is inherited" — no; each class has distinct static `#` slots; parent's static `#field` not accessible via `Child`'s `this` (brand mismatch).
- "Field order doesn't matter" — it does; `a = this.b` before `b` evaluates `a` as `undefined`.

### 5) **Performance note**

Static fields/blocks run once — negligible unless static initializer does heavy work (e.g., building large `Map`). Instance fields add one assignment per field per instance — same cost as `this.x = ...` in constructor; order doesn't affect JIT beyond hidden-class stability (declare fields in stable order). As ever, [measure](../../../01%20Fundamentals%20and%20Mental%20Model/sections/2.%20How%20JavaScript%20executes/2.1.%20Parse%20bytecode%20JIT%20pipeline%20and%20single-threaded%20execution.md).

### 6) **Mentor note**

Have trainees predict `new Order()` trace and `Derived2` trace — if they interleave `Base field → Base ctor → Derived field → Derived ctor`, field order is solid. In review, flag `method = () => {}` shadowing a prototype method of same name — suggest rename or use method syntax.
