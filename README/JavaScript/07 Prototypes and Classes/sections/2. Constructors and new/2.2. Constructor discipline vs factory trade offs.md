## 2.2. Constructor discipline vs factory trade offs

### 1) **Constructors share methods; factories close over state**

**Definition** — constructors/classes put methods/accessors once on `prototype`; factories return a per-instance object literal that closes over private state (→ [Variables §3.3](../../../04 Variables Scope and Closures/sections/3. Closures/3.3. Closure patterns privacy factories memoization.md)). Both model "instances", but differ in memory, identity (`instanceof`), live updates, and privacy.

```js
// Constructor: shared prototype, instanceof, this-parameterized state
function CounterCtor(start = 0) { this.n = start; }
CounterCtor.prototype.inc = function () { this.n += 1; return this.n; };
CounterCtor.prototype.get = function () { return this.n; };

const cc1 = new CounterCtor(0), cc2 = new CounterCtor(0);
console.log(cc1.inc === cc2.inc); // true — shared
console.log(cc1.inc(), cc1.get(), cc2.get()); // 1 1 0 — isolated this.n
console.log(cc1 instanceof CounterCtor); // true

// Factory: per-instance closures, no prototype, true privacy without #
function makeCounter(start = 0) {
  let n = start; // private — not a property, not enumerable, not JSON-serializable
  return {
    inc() { n += 1; return n; },
    get() { return n; }
  };
}
const fc1 = makeCounter(0), fc2 = makeCounter(0);
console.log(fc1.inc === fc2.inc); // false — per-instance function
console.log(fc1.inc(), fc1.get(), fc2.get()); // 1 1 0
console.log(typeof fc1.n); // undefined — private
console.log(fc1 instanceof makeCounter); // false — factories have no prototype chain identity

// Memory trade-off: 10k ctor instances share one inc function; 10k factory instances allocate 10k inc functions + closures
function measureShared() {
  const arr = Array.from({ length: 10000 }, (_, i) => new CounterCtor(i));
  return arr[0].inc === arr[9999].inc; // true
}
console.log(measureShared()); // true

// Live updates: patch prototype and all existing ctor instances see new method; factories need re-create
CounterCtor.prototype.reset = function () { this.n = 0; };
console.log(typeof cc1.reset); // function — live delegation (→ [1.1](../1. Prototype delegation/1.1. Delegation mechanics lookup shadowing and dynamic updates.md))
console.log(typeof fc1.reset); // undefined — factory instance has no delegation link
```

- *When sharing matters* — UI components, domain entities, or service clients where many short-lived instances call the same hot method: prototype sharing wins on memory and JIT inlining. When true privacy without `#` or per-instance capture matters: factories.

### 2) **Forgetting new is a bug in sloppy mode and a TypeError in class land**

Constructors are just functions that *expect* `new`. Without it, `this` is `globalThis` (sloppy) or `undefined` (strict/class always strict) — causing global pollution or immediate `TypeError`. Three mitigations exist, only one is modern.

```js
// Sloppy forgotten new pollutes global (legacy)
function BadCtor(x) { this.x = x; } // sloppy by default (no "use strict")
BadCtor(10); // bare call — this === globalThis
console.log(globalThis.x); // 10 — leaked
delete globalThis.x; // cleanup

// Mitigation 1 (historic): new.target guard — manual factory fallback
function GuardedCtor(x) {
  if (!new.target) return new GuardedCtor(x); // auto-correct
  this.x = x;
}
console.log(GuardedCtor(5).x); // 5 — bare call still produced instance (but hides bug)

// Mitigation 2 (ES2015 correct): class — bare call throws, always strict, never pollutes
class Good { constructor(x) { this.x = x; } }
try { Good(5); } catch (e) { console.log(e.name); } // TypeError — class must be called with new
console.log(new Good(5).x); // 5

// Mitigation 3: naming convention + lint (eslint new-cap) flags bare BadCtor() calls; factories use camelCase so confusion disappears
function makePoint(x, y) { return { x, y }; } // factory — never needs new, never pollutes
console.log(makePoint(1, 2)); // { x:1, y:2 }

// Class also enforces this-after-super in derived constructors (→ [3.2](../3. Class syntax/3.2. Extends and super chain wiring and obligations.md))
class Base { constructor(id) { this.id = id; } }
class Derived extends Base {
  constructor(id, extra) {
    // console.log(this); // ReferenceError — this uninitialized before super()
    super(id);
    this.extra = extra;
  }
}
console.log(new Derived(1, 2).extra); // 2
```

- Modern guidance: default to `class` for shared-behavior types; use a factory function (`makeX`) when you want zero `new` ceremony and closure privacy or when you intentionally return a different shape per call (e.g., pooled objects). Never rely on the `!new.target` auto-correct — it masks the call-site bug instead of fixing it.

### 3) **When to pick which**

| Task | Pick | Why |
|------|------|-----|
| Many short-lived instances with hot methods | `class` / constructor + prototype | one shared function, monomorphic IC, `instanceof` support |
| Isolated state that must never be `Object.keys`/JSON-visible | factory with closure (`let n`) | true privacy without `#`, no enumerable leakage |
| Brand-checked encapsulation across files but still need `instanceof` | `class` with `#private` (→ [3.3](../3. Class syntax/3.3. Private fields and methods brand checks and encapsulation.md)) | privacy + chain identity |
| Dictionary keyed by untrusted strings | `Object.create(null)` literal, no constructor | no prototype pollution (→ [Objects §1.2](../../../06 Objects in Depth/sections/1. Object creation and literals/1.2. Creation patterns literal Object create and constructors.md)) |
| Single data record, few instances | literal `{ x, y }` | fastest to write/read, stable hidden class |

```js
// Heuristic: if you need instanceof or inheritance, constructor/class; otherwise literal/factory
const literal = { x: 1, y: 2, kind: "point" }; // data bag — no sharing needed

class Entity {
  #id; // private brand (→ [3.3](../3. Class syntax/3.3. Private fields and methods brand checks and encapsulation.md))
  constructor(id) { this.#id = id; }
  get id() { return this.#id; }
}
const e = new Entity(42);
console.log(e instanceof Entity); // true — brand + chain
console.log(e.id); // 42

// Factory alternative when you don't need instanceof and want trivial mocking
function makeEntity(id) {
  return {
    get id() { return id; }, // id captured, no field
    withId(n) { return makeEntity(n); } // functional update
  };
}
console.log(makeEntity(7).id); // 7
```

### 4) **Common confusion**

- "Factories and constructors are just style" — semantics differ: sharing, `instanceof`, `Object.getPrototypeOf`, enumeration, JSON shape, and private-state mechanism all diverge.
- "`new` is optional for constructors" — only `new.target` guarded legacy constructors tolerate bare calls; classes never do.
- "Private state needs closure" — since ES2022, `class` `#field` gives private state on instances without per-instance closures (brand-checked, not deletable, not enumerable).

### 5) **Performance note**

Factory per-instance closures allocate N functions + N environments; constructor prototypes allocate 1 function. For 10k instances, factory costs ~10k× function objects + environment slots vs constructor's 1× — measurable in GC pressure and compile time. For one-off instances, difference is noise. As ever, [measure](../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md).

### 6) **Mentor note**

Have trainees build the same `Counter` both ways and compare `a.inc === b.inc`, `instanceof`, `Object.keys`, and private `n` visibility — if they can predict all four, the trade-off is internalized. In review, flag any `Ctor` called bare (`eslint new-cap`, `no-invalid-this` with strict).
