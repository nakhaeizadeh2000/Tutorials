## 5.1. instanceof, isPrototypeOf, Symbol.hasInstance, and cross-realm failures

### 1) **instanceof walks prototype at call time**

**Definition** — `instance instanceof Constructor` is spec `OrdinaryHasInstance (→ InstanceofOperator)` → `Constructor[Symbol.hasInstance](instance)` → by default `IsPrototypeOf` walk: does `Constructor.prototype` appear anywhere in `instance`'s `[[Prototype]]` chain? Operands swapped vs `isPrototypeOf`: `A.prototype.isPrototypeOf(instance)` tests same walk but without the `Symbol.hasInstance` hook. Crucially the walk uses *current* `Constructor.prototype` at call time, not the prototype at instance birth.

```js
class Animal {}
class Dog extends Animal {}
const d = new Dog();

console.log(d instanceof Dog); // true — Dog.prototype in chain
console.log(d instanceof Animal); // true — Animal.prototype two hops up
console.log(d instanceof Object); // true — Object.prototype at root
console.log(Dog.prototype.isPrototypeOf(d)); // true — swapped form, no hasInstance hook
console.log(Animal.prototype.isPrototypeOf(d)); // true

// Reassigned prototype breaks earlier instanceof (the caveat from [2.1](../2.%20Constructors%20and%20new/2.1.%20The%20new%20operator%20prototype%20property%20new.target%20and%20return%20override.md))
// Use function constructor for this demo — class prototype reassignment would throw (class prototype is read-only)
function C() {}
const c1 = new C();
C.prototype = {}; // replace — allowed on function constructors; class would throw TypeError
console.log(c1 instanceof C); // false — c1 chain holds old prototype, current C.prototype not in chain
console.log(new C() instanceof C); // true — new instance links to new prototype
C.prototype = { restored: true }; // restore differently to avoid confusion
class D {} const d1 = new D(); // separate class demo — prototype replacement not shown here

// Primitives: instanceof throws on non-object LHS? Actually spec requires object; primitives return false or throw depending on @@hasInstance? Default: false for primitives
console.log("hi" instanceof String); // false — primitive not object
console.log(new String("hi") instanceof String); // true — object wrapper

// isPrototypeOf is the flipped, hook-free counterpart
console.log(Dog.prototype.isPrototypeOf(d)); // true
console.log(d instanceof Dog && Dog.prototype.isPrototypeOf(d)); // both true, but isPrototypeOf ignores Symbol.hasInstance customization
```

### 2) **Cross-realm and iframe/vm prototypes fail instanceof**

**Definition** — each *realm* (global) has its own set of built-ins: `window.Array`, `iframe.contentWindow.Array`, `vm.runInContext`'s `Array` are distinct function objects with distinct `.prototype` objects. An array created in one realm has `[[Prototype]] === realmA.Array.prototype`, so `arr instanceof realmB.Array` walks realmB's prototype → never found → `false`. Use realm-agnostic checks: `Array.isArray`, `Number.isFinite`, `typeof`, `Object.prototype.toString`, or brand check via `instanceof` with `Symbol.hasInstance` bridge.

```js
// Simulated cross-realm via vm (Node): two distinct Array constructors
// import vm from "node:vm"; // ESM import — illustration only; in CommonJS use: const vm = require("node:vm")
// const sandbox = vm.createContext({ Array: Array });
// const otherArrayCtor = vm.runInContext("Array", sandbox); // two distinct Array per realm — for demo we simulate via surrogate below
// Instead simulate realm failure by manual surrogate: create a second Array-like constructor that shares logic but not prototype identity
function FakeArray() { this.length = 0; }
FakeArray.prototype = Object.create(Array.prototype); // near but not ===
const arr = [];
console.log(arr instanceof FakeArray); // false — arr's chain holds real Array.prototype, not FakeArray.prototype
console.log(Array.isArray(arr)); // true — brand check, not prototype walk (ES5+)
console.log(Array.isArray([])); // true
console.log([] instanceof Array); // true — same realm, true
// But cross-iframe arr would be instanceof iframe.Array false; Array.isArray still true

// Cross-realm-safe alternatives
console.log(Array.isArray(new Array(3))); // true
console.log(Object.prototype.toString.call([]) === "[object Array]"); // true — toString brand (historical)
console.log(Array.isArray(new FakeArray())); // false — FakeArray not Array brand
console.log(typeof "hi" === "string"); // true — primitives: use typeof, not instanceof
```

- Modern guidance: never use `x instanceof Array` in library code that may receive `iframe`/`vm` values — use `Array.isArray(x)`. For other built-ins (`Error`, `TypedArray`, `Map`), `instanceof` is realm-fragile; prefer `Object.prototype.toString` or duck/private brand checks. For your own classes, prefer `#field in obj` brand checks over `instanceof` when you need true encapsulation.

### 3) **Symbol.hasInstance customizes instanceof**

**Definition** — defining `static [Symbol.hasInstance](value) { ... }` on a constructor customizes `value instanceof Constructor` result. The default `Function.prototype[Symbol.hasInstance]` does the prototype walk; your override can do brand, range, or duck checks. `isPrototypeOf` ignores this hook (it always walks).

```js
class Even {
  static [Symbol.hasInstance](x) { return typeof x === "number" && x % 2 === 0; }
}
console.log(4 instanceof Even); // true — custom hasInstance
console.log(5 instanceof Even); // false
console.log(4 instanceof Even && Even[Symbol.hasInstance](4)); // both true — instanceof delegates to hasInstance
console.log(Even.prototype.isPrototypeOf(4)); // false — isPrototypeOf still walks (4 is primitive, no prototype), and ignores Symbol.hasInstance

// Brand-like hasInstance for closure-private types (pre-#field pattern)
function makeToken() {
  const brand = Symbol("brand");
  class Token {
    constructor() { this[brand] = true; }
    static [Symbol.hasInstance](obj) { return !!(obj && obj[brand] === true); }
  }
  return Token;
}
const Token = makeToken();
const t = new Token();
console.log(t instanceof Token); // true — via Symbol.hasInstance brand check
console.log({} instanceof Token); // false
console.log(Token.prototype.isPrototypeOf(t)); // true — t's chain holds Token.prototype, isPrototypeOf still true but coincidentally

// Private brand vs hasInstance: #field in obj is a better brand than Symbol.hasInstance for private, because Symbol keys are still reachable via getOwnPropertySymbols
class Secure {
  #secret = 1;
  static isSecure(obj) { return #secret in obj; } // brand check without walking
}
const sec = new Secure();
console.log(Secure.isSecure(sec)); // true
console.log(Secure.isSecure({})); // false
try { console.log(5 instanceof Secure); } catch (e) { console.log(e.name); } // false — default prototype walk, 5 not object

// Overriding hasInstance breaks symmetry with isPrototypeOf — document when you do
```

### 4) **Common confusion**

- "`instanceof` tests the constructor used at birth" — no; tests *current* `Constructor.prototype` placement. Reassigning breaks earlier instances.
- "`instanceof` works across iframes" — no; realm-fragile. Use `Array.isArray` / `Number.isFinite` / `typeof`.
- "`isPrototypeOf` is `instanceof` swapped" — almost, but `isPrototypeOf` has no `Symbol.hasInstance` hook; swap is only true for default hasInstance.
- "Private `#field in obj` is `instanceof` " — `instanceof` walks prototype; `#field in obj` tests lexical brand — stricter and not chain-sensitive.

### 5) **Performance note**

`instanceof` walk is linear in chain length (typically 2–4). `Array.isArray` is a single brand bit check — faster and realm-safe. Custom `Symbol.hasInstance` that does heavy work (e.g., walking arrays) per `instanceof` check turns a cheap test into a hot-path cost; keep hasInstance logic O(1). As ever, [measure](../../../01%20Fundamentals%20and%20Mental%20Model/sections/2.%20How%20JavaScript%20executes/2.1.%20Parse%20bytecode%20JIT%20pipeline%20and%20single-threaded%20execution.md).

### 6) **Mentor note**

Have trainees create an `iframe`-like second Array constructor and predict `arr instanceof OtherArray` vs `Array.isArray(arr)` — if they pick `Array.isArray` as the realm-safe answer, the failure mode is internalized. Ask them to implement `Even[Symbol.hasInstance]` and contrast with `isPrototypeOf` ignoring it. In review, flag any `value instanceof Array` in shared library code — suggest `Array.isArray`.
