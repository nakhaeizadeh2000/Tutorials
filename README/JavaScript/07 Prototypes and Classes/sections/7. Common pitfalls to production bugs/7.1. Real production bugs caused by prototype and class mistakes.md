## 7.1. Real production bugs caused by prototype and class mistakes

### 1) **Forgotten new / super() ordering**

**The bug** — calling a function constructor without `new` pollutes `globalThis` (sloppy) or leaves `undefined` writes (strict always-throw but not enforced in sloppy); calling `super()` late in a derived constructor throws `ReferenceError` at runtime inside the request path — surfacing only on the subclass code path that tests didn't cover because base-only tests passed.

```js
// Forgotten new (legacy function constructor)
function User(name) { this.name = name; } // sloppy → this === globalThis when bare-called
User("ada"); // bare call — bug
console.log(globalThis.name); // ada — leaked to global (pollutes cross-request state in Node's global)
delete globalThis.name;
// In strict mode the same bare call would throw or be undefined, but sloppy modules still pollute
function StrictUser(name) { "use strict"; this.name = name; }
try { StrictUser("bob"); } catch (e) { console.log(e.name); } // TypeError — this is undefined
// Fix: use class (always strict + enforces new) or guard
class SafeUser { constructor(name) { this.name = name; } }
try { SafeUser("x"); } catch (e) { console.log(e.name); } // TypeError — must be called with new

// super() ordering: derived constructor touches this before super
class Base { constructor(id) { this.id = id; } }
class Derived extends Base {
  constructor(id, extra) {
    // this.extra = extra; // ReferenceError — this uninitialized before super
    super(id);
    this.extra = extra; // ok
  }
}
console.log(new Derived(1, 2).extra); // 2

// Why it slipped: happy-path tests only constructed Base; Derived path not covered until production subclass activated
```

### 2) **Shared mutable prototype state**

**The bug** — placing a mutable object/array on `prototype` makes it a cross-instance singleton. One user's `push` appears in another user's list — data leakage between requests/users.

```js
// Antipattern: mutable default on prototype
function Request() {}
Request.prototype.tags = []; // shared!
const r1 = new Request(), r2 = new Request();
r1.tags.push("r1");
console.log(r2.tags); // ["r1"] — BUG: r2 sees r1's tag via shared prototype array

// Class version of same bug (field vs prototype misplace)
class Session {
  tags = []; // instance field — per instance ✓ (correct)
}
class BadSession {
  // tags = []; // should be instance field, but someone moved to prototype for "sharing"
}
BadSession.prototype.tags = []; // same shared bug on class
const s1 = new Session(), s2 = new Session();
s1.tags.push("s1");
console.log(s2.tags); // [] — isolated ✓

const b1 = new BadSession(), b2 = new BadSession();
b1.tags.push("b1");
console.log(b2.tags, b1.tags === b2.tags); // ["b1"] true — BUG leaked

// Fix: always allocate mutable defaults per instance — class field `tags = []` or constructor `this.tags = []`, never `Prototype.tags = []`

// Related: extending built-ins without calling super correctly leaks species chain
class MyArray extends Array {
  constructor(...args) { super(...args); } // must forward to Array allocation; forgetting super leaves this uninitialized
}
console.log(new MyArray(1, 2, 3).length); // 3
```

### 3) **Private field brand confusion and this loss in callbacks**

**The bug** — private fields are brand-checked (`this` must belong to declaring class). Detaching a method (`const fn = obj.method`) and calling it bare loses `this` → brand check fails → `TypeError` in production callback (`Array.map`, `setTimeout`, event handler) even though `obj.method()` worked in unit tests where it was always called as `obj.method()`.

```js
class Store {
  #data = new Map();
  set(k, v) { this.#data.set(k, v); }
  get(k) { return this.#data.get(k); } // needs Guard brand === Store
}

const store = new Store();
store.set("a", 1);
console.log(store.get("a")); // 1 — direct call, this === store → brand ok

// Detached in callback: lost this → brand failure
const keys = ["a"];
try { console.log(keys.map(store.get)); } catch (e) { console.log(e.name); } // TypeError — this is undefined/window, not Store-branded
// Fix taxonomy same as Functions §3.1 lost-this (→ [Functions §3.1](../../../05%20Functions%20Deep%20Dive/sections/3.%20this%20binding/3.1.%20Call-site%20rules%20default%20implicit%20explicit%20new%20and%20strict%20mode.md)):
console.log(keys.map((k) => store.get(k))); // arrow closes over store lexically — brand preserved
console.log(keys.map(store.get.bind(store))); // bind permanent this
console.log(keys.map(function (k) { return store.get(k); })); // wrapper

// Static private brand confusion: Child inheriting Parent's method that accesses Parent's static private loses brand when called as Child
class Parent {
  static #ctr = 0;
  static next() { this.#ctr += 1; return this.#ctr; }
}
class Child extends Parent {}
console.log(Parent.next(), Parent.next()); // 1 2 — Parent branded
try { Child.next(); } catch (e) { console.log(e.name); } // TypeError — this is Child, not Parent brand for static #ctr
// Fix: make static accessor that doesn't use private brand for cross-class, or declare separate #ctr per subclass

// instanceof vs brand also bites: after prototype mutation instanceof breaks while brand survives (or vice versa confusion)
// Code that used instanceof as brand proxy fails after hot reload replaces prototype (→ [5.1](../5.%20Type%20checks%20and%20reflection/5.1.%20instanceof%20isPrototypeOf%20Symbol.hasInstance%20and%20cross-realm%20failures.md))
```

### 4) **Descriptor + enumeration surprises on prototypes**

`Object.assign` mixing flattens accessors, `for-in` leaks enumerable prototype extensions, and `Object.keys` on a class instance doesn't show prototype methods (they're non-enumerable) — all of which cause silent data loss or iteration bugs when code assumes copied behavior matches source.

```js
// Object.assign flattens accessor trait (from [4.1](../4.%20Composition%20and%20mixins/4.1.%20Mixins%20and%20composition%20patterns.md))
const Trait = {
  get tag() { return this._tag ?? "base"; },
  set tag(v) { this._tag = v; }
};
class Base2 {}
Object.assign(Base2.prototype, Trait); // flattened!
console.log(typeof Object.getOwnPropertyDescriptor(Base2.prototype, "tag").get); // undefined — getter lost, became data
console.log(typeof Object.getOwnPropertyDescriptor(Base2.prototype, "tag").value); // string? actually assign read tag getter on Trait (this===Trait) → "base" as data!
class Fixed {}
Object.defineProperties(Fixed.prototype, Object.getOwnPropertyDescriptors(Trait)); // preserve
console.log(typeof Object.getOwnPropertyDescriptor(Fixed.prototype, "tag").get); // function — correct

// for-in leak via accidental enumerable prototype extension (legacy polyfill style)
Object.prototype.pollute = "oops"; // enumerable! never do this (intentionally demonstrating leak)
const obj = Object.create({ inherited: 1 }); obj.own = 2;
for (const k in obj) { /* sees pollute + inherited + own when enumerable */ }
console.log(Object.keys(obj)); // ["own"] — own only; for-in would include pollute + inherited
delete Object.prototype.pollute; // cleanup — real fix: never extend Object.prototype enumerably

// Class methods vs object literal methods enumerability difference bites serialization expectations
class C { method() {} } // non-enumerable
const lit = { method() {} }; // enumerable (→ [3.1](../3.%20Class%20syntax/3.1.%20Class%20basics%20declarations%20hoisting%20methods%20accessors%20and%20fields.md))
console.log(Object.getOwnPropertyDescriptor(C.prototype, "method").enumerable); // false
console.log(Object.getOwnPropertyDescriptor(lit, "method").enumerable); // true
```

### 5) **Cross-realm instanceof / Array.isArray miss**

Library shared between main window and iframe receives an array created in the iframe: `value instanceof Array` is `false` (different `Array.prototype` per realm) → branch takes error path → production failure.

```js
// Simulated cross-realm: two distinct Array constructors with distinct prototypes
function RealArray() {}
function OtherArray() {}
const arr = [];
console.log(arr instanceof OtherArray); // false — different prototype chain
console.log(Array.isArray(arr)); // true — realm-safe brand check
console.log(arr instanceof Array); // true — same realm true, other realm false

// Fix: library array check must be Array.isArray, not instanceof
// Similarly for Error: `err instanceof Error` cross-realm fragile → use err.message / err.name or Object.prototype.toString
```
