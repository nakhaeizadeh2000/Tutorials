## 1.1. Delegation mechanics: lookup, shadowing, and dynamic updates

### 1) **Lookup walks [[Prototype]] until null**

**Definition** — every ordinary object has an internal slot `[[Prototype]]` (null or object). Property read `obj.prop` does: if `obj` has own property → return it; otherwise walk `Object.getPrototypeOf(obj)`, then that object's prototype, until `null` — return `undefined` if never found. The walk is *live*: adding a property to a prototype after instances are created makes it visible instantly; deleting it removes it. `in`, `for...in` (→ [Objects §2.3](../../../06%20Objects%20in%20Depth/sections/2.%20Properties%20and%20descriptors/2.3.%20Enumerability%20enumeration%20order%20and%20for-in%20mechanics.md)), and method calls all use the same walk.

*What problem it solves* — delegation shares behavior without copying: methods live once on `prototype`, instances delegate. Historically before `class`, this was how reuse was modeled; `class` still wires the same chain.

```js
// Chain: instance → Child.prototype → Parent.prototype → Object.prototype → null
const parentProto = { kind: "parent", greet() { return `hi from ${this.kind}`; } };
const childProto = Object.create(parentProto);
childProto.kind = "child";
childProto.ask = function () { return this.greet(); };

const inst = Object.create(childProto);
inst.kind = "inst";

console.log(inst.ask()); // hi from inst — this === inst, lookup found ask on childProto, greet on parentProto
console.log(Object.getPrototypeOf(inst) === childProto); // true
console.log(Object.getPrototypeOf(childProto) === parentProto); // true
console.log(Object.getPrototypeOf(parentProto) === Object.prototype); // true → toString etc

// Live delegation: adding after birth is seen
parentProto.newMethod = () => 42;
console.log(inst.newMethod()); // 42 — prototype mutation visible without touching inst

// Miss → undefined after walking to null
console.log(inst.missing); // undefined
console.log("missing" in inst); // false — in also walks but stops at null (→ [Objects §4.2](../../../06%20Objects%20in%20Depth/sections/4.%20Object%20utilities%20and%20copying/4.2.%20Keys%20values%20entries%20hasOwn%20and%20reflection%20APIs.md))

// Reflection without walking: own vs inherited
console.log(Object.hasOwn(inst, "kind")); // true — own shadows
console.log(Object.hasOwn(childProto, "kind")); // true — its own
console.log(inst.hasOwnProperty("kind")); // true — but breaks on null-proto (prefer hasOwn)
```

- Modern guidance: rely on delegation for methods/accessors, not for data. Data on prototypes becomes shared state; put data on instances (fields/constructor).

### 2) **Shadowing creates an own slot that hides the prototype**

**Definition** — assigning `obj.prop = value` when `prop` exists as a prototype *data* property creates/replaces an *own* data property (not mutating the prototype). If the prototype has an accessor with a setter, assignment *calls* the setter on the prototype with `this` = receiver (no shadowing). If prototype has a read-only data (`writable: false`) or accessor with no setter, strict assignment throws `TypeError` (sloppy silently fails).

```js
// Data shadowing: own slot hides prototype
const proto = { x: 10, y: 20 };
const obj = Object.create(proto);
console.log(obj.x); // 10 — delegated
obj.x = 99; // creates own x, proto untouched
console.log(obj.x); // 99 — own wins
console.log(proto.x); // 10 — unchanged
console.log(Object.getOwnPropertyDescriptor(obj, "x").value); // 99
delete obj.x; // removes own shadow
console.log(obj.x); // 10 — delegated again (until own recreated)

// Accessor shadowing vs setter call
const protoAcc = {
  _v: 1,
  get v() { return this._v; },
  set v(n) { this._v = n * 2; } // setter stores double
};
const child = Object.create(protoAcc);
console.log(child.v); // 1 — getter, this === child so this._v is child's _v? actually _v on proto, but set creates own _v
child.v = 10; // calls proto setter with this === child → child._v = 20 (own)
console.log(child.v); // 20 — getter reads child's _v
console.log(protoAcc._v); // 1 — proto unchanged
// Shadowing the accessor itself requires defineProperty, not assignment
Object.defineProperty(child, "v", { value: 99, writable: true, enumerable: true, configurable: true });
console.log(child.v); // 99 — own data now shadows accessor
console.log(Object.getOwnPropertyDescriptor(child, "v").value); // 99

// Read-only prototype blocks shadowing via assignment
const roProto = {};
Object.defineProperty(roProto, "fixed", { value: 42, writable: false, enumerable: true, configurable: true });
const roChild = Object.create(roProto);
try { roChild.fixed = 100; } catch (e) { console.log(e.name); } // TypeError in strict (modules are strict)
console.log(roChild.fixed); // 42 — assignment failed, no shadow
// defineProperty still fails if you try to shadow read-only? Actually creating own is allowed because distinct slot? No — spec checks prototype's writable: false blocks [[Set]] even for new own when prototype has non-writable same name and configurable? Assignment fails; defineProperty to create own data with same name is allowed because it doesn't use [[Set]] — it defines own directly.
Object.defineProperty(roChild, "fixed", { value: 100, writable: true, enumerable: true, configurable: true });
console.log(roChild.fixed); // 100 — shadowing via defineProperty bypasses setter/writable check
```

- Why it matters — `obj.x = 1` *not* always mutating `obj` alone: when a setter lives on the prototype, you mutated the prototype's logic target; when prototype is read-only, you mutated nothing and (in sloppy) silently kept stale data. Audit with `getOwnPropertyDescriptor` (→ [Objects §2.2](../../../06%20Objects%20in%20Depth/sections/2.%20Properties%20and%20descriptors/2.2.%20Defining%20observing%20and%20configuring%20properties.md)).

### 3) **Delegation is sharing, not copying**

Methods/accessors should live on the prototype; data fields on instances. Prototype methods share one function object; `this` parameterizes per call (→ [Functions §3.1](../../../05%20Functions%20Deep%20Dive/sections/3.%20this%20binding/3.1.%20Call-site%20rules%20default%20implicit%20explicit%20new%20and%20strict%20mode.md)). Copying methods onto each instance (factory) costs memory and loses live updates; mutating shared state on the prototype (e.g., `Ctor.prototype.items = []`) causes cross-instance leakage.

```js
// Sharing: one function, many receivers
function Counter(n) { this.n = n; }
Counter.prototype.inc = function () { this.n += 1; return this.n; };
const a = new Counter(0), b = new Counter(0);
console.log(a.inc === b.inc); // true — shared
console.log(a.inc(), a.inc(), b.inc()); // 1 2 1 — this parameterization isolates state

// Antipattern: mutable prototype state
function Bad() {}
Bad.prototype.tags = []; // shared array!
const x = new Bad(), y = new Bad();
x.tags.push("x");
console.log(y.tags); // ["x"] — BUG: prototype array polluted
// Fix: instance field
function Good() { this.tags = []; }
const gx = new Good(), gy = new Good();
gx.tags.push("x");
console.log(gy.tags); // [] — isolated

// Live delegation for accessors too
const base = {
  get label() { return `id-${this.id}`; }
};
const o1 = Object.create(base); o1.id = 1;
const o2 = Object.create(base); o2.id = 2;
console.log(o1.label, o2.label); // id-1 id-2 — accessor shares, this varies

// vs copying getters onto instances (wasteful and loses updates)
```

### 4) **Common confusion**

- "`obj.prop` finds only own" — no; it walks. Use `hasOwn` for own-only checks.
- "Assign always creates own" — not when prototype has setter or read-only data; then assignment delegates or throws.
- "Prototype methods are copied per instance" — no; one shared function, `this` parameterizes.
- "`for-in` vs `Object.keys` on prototypes" — `for-in` includes inherited enumerable strings; `Object.keys` is own-only (→ [Objects §2.3](../../../06%20Objects%20in%20Depth/sections/2.%20Properties%20and%20descriptors/2.3.%20Enumerability%20enumeration%20order%20and%20for-in%20mechanics.md)).

### 5) **Performance note**

Prototype chain walk is per-property-miss cost; V8 caches lookup for monomorphic chains but megamorphic re-shapes deopt. Keep chains shallow (2–3 hops). Adding methods to `Object.prototype` pollutes *all* lookups (and enumerations). As ever, [measure](../../../01%20Fundamentals%20and%20Mental%20Model/sections/2.%20How%20JavaScript%20executes/2.1.%20Parse%20bytecode%20JIT%20pipeline%20and%20single-threaded%20execution.md).

### 6) **Mentor note**

Have trainees diagram `inst → childProto → parentProto → Object.prototype → null` and predict `hasOwn` vs `in` vs `getOwnPropertyDescriptor` for each level. Ask them to fix a `Bad.prototype.tags = []` bug by moving `tags` to constructor/field — if they choose instance field without prompting, delegation vs data is solid.
