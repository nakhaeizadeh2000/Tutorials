## 1.2. Creation, mutation, and performance costs

### 1) **Birth sets the link; mutation deoptimizes**

**Definition** — `[[Prototype]]` is set once at *birth* via three fast paths: literal `__proto__`, `Object.create(proto)`, or `new Ctor()` (which stamps `Ctor.prototype`). Later mutation via `Object.setPrototypeOf(obj, newProto)` or `obj.__proto__ = newProto` (accessor on `Object.prototype`) forces the engine to abandon hidden-class optimizations for that object and often for all objects sharing its map — orders of magnitude slower.

```js
// Fast birth paths (all create with correct [[Prototype]] once)
const proto = { greet() { return "hi"; } };

// A) Literal __proto__ at birth — spec-mandated prototype set, not a data key
const fast1 = { __proto__: proto, x: 1 };
console.log(Object.getPrototypeOf(fast1) === proto); // true

// B) Object.create — explicit, most readable for branch creation
const fast2 = Object.create(proto, {
  x: { value: 1, writable: true, enumerable: true, configurable: true }
});
console.log(fast2.greet()); // hi

// C) new + .prototype — full story → [2.1](../2.%20Constructors%20and%20new/2.1.%20The%20new%20operator%20prototype%20property%20new.target%20and%20return%20override.md)
function Ctor() { this.x = 1; }
Ctor.prototype = proto; // replace BEFORE first new (see caveat in [3.1](../3.%20Class%20syntax/3.1.%20Class%20basics%20declarations%20hoisting%20methods%20accessors%20and%20fields.md))
const fast3 = new Ctor();
console.log(Object.getPrototypeOf(fast3) === proto); // true

// Computed ["__proto__"] in same literal is NOT a link — it's a plain string key
const slowish = { ["__proto__"]: proto, x: 1 };
console.log(Object.getPrototypeOf(slowish) === Object.prototype); // true — default, not linked
console.log(slowish["__proto__"] === proto); // true — data key named "__proto__"

// Slow mutation — works but penalizes
const obj = { a: 1 };
Object.setPrototypeOf(obj, proto); // forces deopt
console.log(Object.getPrototypeOf(obj) === proto); // true — but engine had to re-create map
obj.__proto__ = null; // legacy accessor path — same penalty and fails on null-proto objects (no accessor)
console.log(Object.getPrototypeOf(obj)); // null
```

- Modern guidance: choose the prototype at allocation; never rewire in hot loops or request handlers. `setPrototypeOf` is appropriate for polyfills/migration once at startup, not per request.

### 2) **Object.prototype is the root of most chains**

**Definition** — ordinary literals and `new` instances delegate to `Object.prototype` → `null`. This gives `toString`/`hasOwnProperty`/`valueOf` to every object. `Object.create(null)` opts out: `[[Prototype]] === null`, no inherited methods, safe for untrusted-key dictionaries (no `__proto__` alias, no pollution — → [Objects §1.2](../../../06%20Objects%20in%20Depth/sections/1.%20Object%20creation%20and%20literals/1.2.%20Creation%20patterns%20literal%20Object%20create%20and%20constructors.md)).

```js
// Normal chain ends at Object.prototype
const normal = {};
console.log(Object.getPrototypeOf(normal) === Object.prototype); // true
console.log(Object.getPrototypeOf(Object.prototype) === null); // true — terminus
console.log("toString" in normal); // true — inherited
console.log(normal.toString()); // [object Object]

// Array and Function have own prototypes that themselves delegate to Object.prototype
console.log(Object.getPrototypeOf([]) === Array.prototype); // true
console.log(Object.getPrototypeOf(Array.prototype) === Object.prototype); // true
console.log(Object.getPrototypeOf(function () {}) === Function.prototype); // true
console.log(Object.getPrototypeOf(Function.prototype) === Object.prototype); // true

// Null-prototype dictionaries — no Object.prototype methods
const dict = Object.create(null);
dict["__proto__"] = "just a string key";
dict["toString"] = "not a method";
console.log(dict["__proto__"]); // just a string key
console.log(Object.getPrototypeOf(dict)); // null — no delegation
console.log("toString" in dict); // true — own key only
try { dict.toString(); } catch (e) { console.log(e.name); } // TypeError — no inherited method
console.log(Object.prototype.toString.call(dict)); // [object Object] — borrow works
console.log(typeof dict.hasOwnProperty); // undefined — use Object.hasOwn(dict, k) (→ [Objects §4.2](../../../06%20Objects%20in%20Depth/sections/4.%20Object%20utilities%20and%20copying/4.2.%20Keys%20values%20entries%20hasOwn%20and%20reflection%20APIs.md))

// Extending Object.prototype is almost always a mistake — pollutes every chain
// Bad: Object.prototype.extra = 1; // now extra in every object, for-in leaks, etc.
```

- History — early libraries extended `Object.prototype` to add helpers; this broke `for-in` and `JSON` serialization globally. Modern code never mutates `Object.prototype`.

### 3) **Hidden classes key on prototype**

Engines (V8) encode object *shape* (hidden class / Map) as: property layout + prototype link. Instances sharing the same prototype and adding properties in the same order share the same Map → monomorphic inline-cache hits. Two penalties break this:

1. Changing `[[Prototype]]` per-instance → map divergence → megamorphic lookups.
2. Adding properties out-of-order after birth (e.g., conditional adds) → map transitions diverge.

```js
// Keep prototype stable per type — not per instance
function Point(x, y) { this.x = x; this.y = y; }
Point.prototype.len = function () { return Math.hypot(this.x, this.y); };
const p1 = new Point(1, 2);
const p2 = new Point(3, 4);
console.log(p1.len === p2.len); // true — shared, monomorphic shape

// Antipattern: per-instance prototype mutation (e.g., choose prototype per flag)
function make(flag) {
  const o = { id: 1 };
  const proto = flag ? { a() {} } : { b() {} };
  Object.setPrototypeOf(o, proto); // deopt per call — penalizes all o objects
  return o;
}
const m1 = make(true), m2 = make(false);
console.log(m1.a !== undefined || m2.b !== undefined); // true — but both deoptimized

// Antipattern: variable-order adds
function makeOrder(kv) {
  const o = {};
  if (kv.b) o.b = kv.b; // b before a sometimes
  if (kv.a) o.a = kv.a;
  return o;
}
// Fast: literal with stable order → { a, b } always a→b
function fastOrder({ a, b }) { return { a, b }; }

// Benchmark hint: in hot factory loops, literal with stable key order beats
// Object.create + conditional defines + setPrototypeOf by orders of magnitude
```

- Measurement heuristic: prototype walk cost scales with chain length. Keep chains shallow (2–3 hops) for data; reserve deep class hierarchies for behavior reuse where method sharing outweighs miss cost.

### 4) **Common confusion**

- "`{ __proto__: p }` always links" — only literal `__proto__: p` (uncomputed) links; `["__proto__"]: p` or `...obj` with `__proto__` does not.
- "`Object.setPrototypeOf` is the normal way to change inheritance" — it's a slow escape hatch; birth-time choice is the normal way.
- "`Object.create(null)` objects are plain objects without extras" — they're not plain; they lack `toString`/`hasOwnProperty`. Use them for dictionaries, not for API payloads expecting those methods.

### 5) **Performance note**

`Object.setPrototypeOf` in a per-request factory shows up in CPU profiles as `Map::TransitionToPrototype` and `IC miss`. Replacing it with `Object.create(proto)` at birth removes the penalty. As ever, [measure](../../../01%20Fundamentals%20and%20Mental%20Model/sections/2.%20How%20JavaScript%20executes/2.1.%20Parse%20bytecode%20JIT%20pipeline%20and%20single-threaded%20execution.md) — on modern V8, prototype-mutation deopt can be 10–100× for hot property reads.

### 6) **Mentor note**

Have trainees create 10k instances via `Object.create(proto)` vs `{}; setPrototypeOf` in a micro-benchmark and observe the order-of-magnitude gap — then forbid `setPrototypeOf` in review except in a one-time migration helper. Flag any `obj.__proto__ =` outside test setup.
