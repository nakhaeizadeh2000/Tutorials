## 3.2. Chaining then catch finally and error propagation

### 1) **`then` returns a new promise — chaining as `map` over async values**

**Definition** — `p.then(onFulfilled, onRejected)` returns a new `Promise` `q`. `q` fulfills with what `onFulfilled` returns (thenable-unwrapped), or rejects if `onFulfilled` throws or returns a rejected promise/thenable; likewise for `onRejected`. A missing handler forwards the settlement (value pass-through on fulfill, reason pass-through on reject), so `then` works like `map` and `flatMap` for async values.

**What problem it solves / history** — chaining turns nested callbacks into a linear pipeline where each step can transform the value or introduce new async work without re-nesting.

**Modern guidance** — keep chains linear; prefer `async/await` for readability when branching outside the chain is needed (see [5.1](<../5. Async functions concurrency and migration/5.1. async await desugaring error handling and gotchas.md>)). Never pass `null` to skip a handler implicitly — omit it.

```js
// Value transform — map over pending value
Promise.resolve(2)
  .then((v) => v * 3) // 6
  .then((v) => { console.log("chain", v); return v; }) // 6
  .then((v) => Promise.resolve(v + 1)) // thenable unwrapped → 7
  .then((v) => console.log(v)); // 7

// Async transform — returning a promise flattens (flatMap)
function delayValue(v, ms) { return new Promise((r) => setTimeout(() => r(v), ms)); }
Promise.resolve("start")
  .then((v) => delayValue(`${v}→a`, 5))
  .then((v) => delayValue(`${v}→b`, 5))
  .then((v) => console.log(v)); // start→a→b

// Pass-through when handler missing — identity
Promise.resolve("keep").then().then((v) => console.log(v)); // keep
Promise.reject(new Error("oops")).then().catch((e) => console.log(e.message)); // oops — reject passes through the empty then

// Throwing transforms to rejection
Promise.resolve(1)
  .then(() => { throw new Error("from onFulfilled"); })
  .catch((e) => console.log(e.message)); // from onFulfilled

// Returning a rejected promise also rejects q
Promise.resolve(1)
  .then(() => Promise.reject(new Error("rejected inner")))
  .catch((e) => console.log(e.message)); // rejected inner
```

### 2) **`catch` and `finally` — `catch` is `then(null, onRejected)`, `finally` is transparent**

**Definition** — `p.catch(onRejected)` is `p.then(null, onRejected)`. `p.finally(onFinally)` runs `onFinally` regardless of fulfillment or rejection, passing through the original outcome unless `onFinally` throws or returns a rejecting thenable (which overrides).

```js
// catch as sugar — placement matters (catch covers upstream only)
Promise.resolve(1)
  .then(() => { throw new Error("boom"); })
  .then(() => console.log("skipped — prior step rejected"))
  .catch((e) => console.log("caught", e.message)); // caught boom

// finally is transparent on value
Promise.resolve("val")
  .finally(() => console.log("cleanup")) // runs either way, value passes through
  .then((v) => console.log(v)); // val

// finally that throws — overrides the original outcome
Promise.resolve("ok")
  .finally(() => { throw new Error("finally boom"); })
  .catch((e) => console.log(e.message)); // finally boom — not "ok"

// finally that returns a rejecting promise — also overrides
Promise.resolve("ok")
  .finally(() => Promise.reject(new Error("finally reject")))
  .catch((e) => console.log(e.message)); // finally reject

// finally with async cleanup — awaited before passing through
Promise.resolve("data")
  .finally(async () => { await new Promise((r) => setTimeout(r, 5)); console.log("async finally done"); })
  .then((v) => console.log(v)); // data — after async finally

// Equivalent desugarings (keep in mind — see 5.1)
const q = Promise.resolve(1);
console.log(q.catch((e) => 42) === q.then(null, (e) => 42)); // false — different returned promises, same logic
// finally mental model: then(onFulfill => { onFinally(); return val; }, reason => { onFinally(); throw reason; })
```

### 3) **Error propagation and unhandled rejections — where throws land**

**Definition** — errors inside `then`/`catch`/`finally` reject the *next* promise in the chain; a missing `catch` propagates rejection downstream until caught. If no handler catches by the turn's end, the host fires `unhandledrejection` (browsers: `window.onunhandledrejection`, Node: `process.on("unhandledRejection")`) and, if later handled, `rejectionhandled`/`rejectionHandled`.

```js
// Propagation — downstream catch handles upstream throw
Promise.resolve()
  .then(() => { throw new Error("mid"); })
  .then(() => console.log("never"))
  .catch((e) => { console.log("propagated", e.message); return "recovered"; })
  .then((v) => console.log(v)); // recovered

// Unhandled detection — observe without suppressing by accident
if (typeof process !== "undefined" && process.on) {
  process.on("unhandledRejection", (reason) => console.log("unhandled", reason.message));
  process.on("rejectionHandled", () => console.log("later handled"));
}
const late = Promise.reject(new Error("late catch"));
setTimeout(() => late.catch((e) => console.log("caught late", e.message)), 10);
// Node: unhandled → later handled → caught late (if handlers installed)

// Top-level guard in script (browser)
if (typeof window !== "undefined") {
  // window.addEventListener("unhandledrejection", (e) => console.log("window unhandled", e.reason));
  console.log("browser guard exists");
}

// Anti-pattern — swallowing errors by forgetting to return/reject
Promise.resolve("a")
  .then((v) => { if (v === "a") return; console.log("unreachable"); }) // returns undefined, not a rejection
  .then((v) => console.log("got", v)); // got undefined — not an error, so no catch
// If that was an error, you needed: .then(v => { if (v==="a") throw new Error("invalid a"); })

// Keeping stacks useful — throw Error with message, not string
Promise.resolve()
  .then(() => { throw new Error("explicit Error"); })
  .catch((e) => console.log(e.stack.split("\n")[0])); // Error: explicit Error
```

### 4) **Common confusion**

- "`finally` receives the value/reason" — no; `finally` takes no args and the original value passes through unchanged unless `finally` throws/returns rejected.
- "`then` must receive functions, so `null` vs `undefined` both pass through" — `null` and any non-callable are treated as absent (identity/noop), but don't pass `null` explicitly — omit the arg.
- "An unhandled rejection crashes the process" — default is a warning that becomes termination in future Node versions; always add a terminal `catch` or `process.on("unhandledRejection")` handler.
- "Throwing inside `then` terminates the chain synchronously" — no; it rejects the returned promise asynchronously (next job).

### 5) **Performance note**

Each `catch`/`finally` adds one promise allocation. A hot loop `arr.map(x => Promise.resolve(x).then(...).catch(...))` over 10k items creates 20k extra promises; for pure sync transforms, stay synchronous. Long unhandled chains hold the rejection reason alive until the next turn — capturing `Error` there pins its stack for a tick.

### 6) **Mentor note**

Have juniors trace `resolve → then → throw → then → catch → then → finally(throw)` and write the outcome at each step — the pass-through vs override rules click when they must name the promise that holds the error. In review, flag any terminal promise chain without a `catch` (or `await` with `try/catch`), any `finally` that returns a value expecting it to replace the chain's value, and any `throw "string"` inside promises — require `throw new Error`.
