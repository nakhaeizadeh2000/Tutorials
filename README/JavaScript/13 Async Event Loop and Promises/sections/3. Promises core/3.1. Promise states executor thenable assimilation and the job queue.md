## 3.1. Promise states executor thenable assimilation and the job queue

### 1) **Three states — pending → fulfilled / rejected, settled once, never back**

**Definition** — a `Promise` is a container for a future value with exactly three states: *pending* (no outcome yet), *fulfilled* (with `value`), *rejected* (with `reason`). The executor `new Promise((resolve, reject) => ...)` runs *synchronously* during construction. The first call to `resolve` or `reject` settles; later calls and throws after settling are ignored.

**What problem it solves / history** — callbacks split success/error and don't compose; promises reify the outcome so it can be returned, queued, and chained uniformly (ES2015). Previous libraries used `Deferred`; the spec chose the executor shape to guarantee the capability pair is created together.

**Modern guidance** — use `Promise.withResolvers()` (ES2024) when you need deferred resolve/reject outside the executor — never create a manual `let resolve` capture inside `new Promise` (the deferred anti-pattern).

```js
// Executor is synchronous — ordering surprise for juniors
console.log("A");
const p = new Promise((resolve, reject) => {
  console.log("B executor runs now");
  resolve(42);
  console.log("C still inside executor");
});
console.log("D after new Promise");
p.then((v) => console.log("E then", v));
// Order: A → B → C → D → E — E is a job, always async

// Settle once — later calls ignored
const once = new Promise((resolve, reject) => {
  resolve("first");
  resolve("second"); // ignored
  reject(new Error("too late")); // ignored
  throw new Error("also ignored — already settled");
});
once.then((v) => console.log("once", v)); // first

// Throw inside executor rejects
const bad = new Promise(() => { throw new Error("boom"); });
bad.catch((e) => console.log(e.message)); // boom

// Deferred done right — withResolvers (ES2024)
let d;
if (typeof Promise.withResolvers === "function") {
  d = Promise.withResolvers();
  console.log(typeof d.promise, typeof d.resolve, typeof d.reject); // object function function
  d.promise.then((v) => console.log("deferred", v));
  d.resolve("via withResolvers");
} else {
  // Fallback — manual deferred (still inside executor, but at least contained)
  let _resolve;
  const fallback = new Promise((r) => { _resolve = r; });
  fallback.then((v) => console.log("fallback deferred", v));
  _resolve("via fallback");
}
```

### 2) **Thenable assimilation — any object with `then` is unwrapped one level per job**

**Definition** — `Promise.resolve(x)` and `resolve`/`reject` inside handlers perform *thenable assimilation*: if `x` is an object with a callable `then`, its `then` is called with `resolvePromise`/`rejectPromise`; resolution recurses until a non-thenable. This lets foreign thenables participate in the chain, but each unwrap is a separate job (one microtask per level).

```js
// Non-thenable is fulfilled immediately (one job later)
Promise.resolve(10).then((v) => console.log("plain", v)); // plain 10

// Thenable — called with resolve/reject, one extra job per layer
const foreign = {
  then(onFulfill) { console.log("foreign then called"); onFulfill(99); },
};
Promise.resolve(foreign).then((v) => console.log("assimilated", v));
// foreign then called → assimilated 99 (after one extra microtask)

// Getter that throws — assimilation rejects instead of throwing synchronously
const evil = {
  get then() { throw new Error("then getter boom"); },
};
Promise.resolve(evil).catch((e) => console.log(e.message)); // then getter boom

// Nested thenables — two jobs deep
const inner = { then(r) { r(1); } };
const outer = { then(r) { r(inner); } };
Promise.resolve(outer).then((v) => console.log("nested", v)); // 1 after two hops

// Promise.resolve vs new Promise — thenable handling is identical, but executor throw semantics differ
// Promise.reject vs reject() — Promise.reject(reason) creates an already-rejected promise

// Assimilation never flattens arrays — only thenables
Promise.resolve([Promise.resolve(1), 2]).then((v) => console.log(Array.isArray(v), v[0])); // true 1 (but still a promise object inside? actually resolved array — elements not awaited)
// To await inner promises, use all — see 4.1
```

### 3) **Jobs not tasks — `then` handlers always run as microtasks, never inline**

**Definition** — `p.then(onFulfilled, onRejected)` registers reactions that run as *jobs* (spec `HostEnqueuePromiseJob`) after the current task completes, even if `p` is already fulfilled. Ordering among jobs is queue order. This de-zalgo guarantee lets you reason about ordering: no handler runs synchronously.

```js
// Already-fulfilled still async — de-zalgo
const fulfilled = Promise.resolve("now");
fulfilled.then(() => console.log("then 1"));
console.log("after then registration");
// after then registration → then 1 — never the reverse

// Job ordering — queue order is preserved
const p2 = Promise.resolve();
p2.then(() => console.log("job A"));
p2.then(() => console.log("job B"));
queueMicrotask(() => console.log("job C queueMicrotask"));
Promise.resolve().then(() => console.log("job D"));
// A → B → C → D — A,B were enqueued first on same promise, then C, then D (separate promise)

// Thenable resolution also deferred — never inline
let sync = false;
Promise.resolve({ then(r) { r(1); sync = true; } }).then(() => console.log("sync inside thenable?", sync));
console.log("after resolve thenable, sync?", sync); // false — assimilation happened as a job, sync still false at this point
// Next microtask shows assignment
queueMicrotask(() => console.log("after drain, sync?", sync)); // true

// Anti-pattern — relying on "already resolved means sync"
// BAD: let cache = null; Promise.resolve(5).then(v => cache = v); console.log(cache); // null
// GOOD: const val = await Promise.resolve(5); console.log(val);
```

### 4) **Common confusion**

- "`Promise` constructor is async" — the *executor* is sync; only `then`/`catch`/`finally` callbacks are async jobs.
- "`Promise.resolve(thenable)` extracts `.then` once synchronously" — the `then` getter is read during resolution, which itself is scheduled as a job; a throwing getter rejects without throwing out.
- "A promise that is already fulfilled calls `then` synchronously" — never; spec mandates job queuing even for same-tick fulfilled.
- "`new Promise` without `resolve`/`reject` does something" — it stays pending forever (and any `await` on it hangs).

### 5) **Performance note**

Each `then` allocates a new promise + reaction record plus a job. A chain of 10k `.then` calls queues 10k jobs and 10k promises (~hundreds of KB). For fan-out of N independent items, `Promise.all(arrayOfPromises)` enqueues fewer intermediate promises than `.reduce` chaining. Thenable assimilation adds one job per layer — deeply nested foreign thenables are a DoS vector; normalize once.

### 6) **Mentor note**

Have juniors predict the five-line `A/B/C/D/E` order — those who place `E` before `D` reveal the "executor is async" misconception. In review, flag any `let resolve; new Promise((r)=> resolve=r)` (deferred anti-pattern) and require `Promise.withResolvers`; flag any code that reads a value set inside `then` on the next line expecting it to be ready — require `await` or continuation inside `then`.
