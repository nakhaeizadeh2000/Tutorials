## 1.1. Call stack run-to-completion and the event loop

### 1) **Single thread run-to-completion — one task at a time, never preempted**

**Definition** — JavaScript has a call stack (frames for the current synchronous call chain), a heap (objects), and a host-provided event loop that repeatedly takes one queued task (macrotask) and runs it to completion. While that task runs, no other task starts — rendering, timer callbacks, and I/O completions wait until the stack empties.

**What problem it solves / history** — the browser's original 1995 design made UI and script share one thread so page script could never race the DOM halfway through an update. Node.js kept the same discipline and multiplexes I/O off-thread, posting completions back as tasks. You get cooperative concurrency without locks for ordinary state.

**Modern guidance** — write every task as short and bounded; break CPU-heavy work into yielded chunks (see [1.2](<./1.2. Microtasks vs macrotasks queueMicrotask and starvation.md>) and [2.2](<../2. Timers and scheduling/2.2. Scheduling patterns debounce throttle and yielding.md>)). Never rely on preemption — if you block, the loop blocks.

```js
// Run-to-completion — timers wait until the stack is empty
console.log("A sync");

// A long synchronous loop blocks the next task
let sum = 0;
for (let i = 0; i < 1e6; i++) sum += i; // still synchronous
console.log("B after loop", sum > 0); // true — before any timer

setTimeout(() => console.log("C timer after stack empties"), 0);
console.log("D end of current task");
// Order: A → B → D → C — C cannot interrupt the for loop

// Call stack trace — each nested call pushes a frame
function a() { b(); }
function b() { c(); }
function c() { console.log("stack:", new Error().stack.split("\n")[1].trim()); }
a(); // stack: at c (...)

// Nothing preempts you — shared counter stays consistent without locks
let counter = 0;
function inc() { const tmp = counter; tmp; counter = tmp + 1; } // no interleaving inside
inc(); inc();
console.log(counter); // 2 — not 1, because inc never interleaves half-way
```

### 2) **Browser vs Node — same language, different loop phases**

**Definition** — the spec defines jobs (microtasks) precisely; macrotask phases are host-defined. Browsers interleave a render step between tasks (≈60Hz). Node's libuv loop has phases: `timers` → `pending callbacks` → `idle/prepare` → `poll` (I/O) → `check` (`setImmediate`) → `close callbacks`, with a `nextTick` queue that drains before microtasks each time.

```js
// Node-only phase intuition — run with node (browser has no process.nextTick / setImmediate in the same place)
// Predict before running:
console.log("1 sync");

if (typeof process !== "undefined" && process.nextTick) {
  process.nextTick(() => console.log("2 nextTick"));
}
Promise.resolve().then(() => console.log("3 promise microtask"));
if (typeof queueMicrotask === "function") queueMicrotask(() => console.log("4 queueMicrotask"));
if (typeof setImmediate === "function") setImmediate(() => console.log("5 setImmediate (check)"));
setTimeout(() => console.log("6 setTimeout (timers)"), 0);
console.log("7 sync end");
// Typical Node order: 1 → 7 → 2 → 3 → 4 → 6 → 5
// Browser (no nextTick/setImmediate): 1 → 7 → 3 → 4 → 6

// Browser rendering interleaving (conceptual — no API to observe directly):
//  task → drain microtasks → rAF → style/layout/paint → next task
// Keep tasks < ~16ms for 60fps or move work to Workers.
```

### 3) **Cooperative yielding — breaking long tasks into queued chunks**

**Definition** — when work exceeds a frame budget, yield explicitly so the loop can handle I/O and rendering between chunks. Three yields with different priorities: `queueMicrotask` / `Promise` job (highest, before rendering), `setTimeout(0)` (macrotask, after rendering on browsers), and `scheduler.yield()` (browser explicit yield to input/paint where available).

```js
// BAD — blocking the loop freezes everything during the burst
function badSum(n) {
  let s = 0;
  for (let i = 0; i < n; i++) s += i; // 10M iterations blocks painting/timers
  return s;
}
console.log(badSum(1e6) > 0); // true — but loop was blocked the whole time

// GOOD — chunked with yields (macrotask yield lets rendering happen)
async function goodSum(n, chunk = 200_000) {
  let s = 0;
  for (let i = 0; i < n; i++) {
    s += i;
    if (i % chunk === 0 && i !== 0) {
      await new Promise((r) => setTimeout(r, 0)); // yield as macrotask
    }
  }
  return s;
}
goodSum(1e6).then((s) => console.log("good sum done", s > 0)); // true, without blocking

// Microtask yield — runs before rendering (finer but can starve — see 1.2)
async function microYield() { await Promise.resolve(); console.log("micro-yield back"); }
console.log("before micro");
microYield();
console.log("after micro");
// Order: before micro → after micro → micro-yield back

// Feature check for the new explicit scheduler.yield (Chrome 115+)
if (typeof scheduler !== "undefined" && scheduler.yield) {
  // await scheduler.yield(); — yields to input/paint explicitly (best for UI)
  console.log("scheduler.yield available");
} else {
  console.log("scheduler.yield not available — setTimeout(0) fallback");
}
```

### 4) **Common confusion**

- "`setTimeout(fn, 0)` runs immediately" — no; it queues a macrotask after the current task and all pending microtasks, with a minimum delay (clamped to ~4ms when nested in browsers).
- "JavaScript is parallel because I can `Promise.all` 10 fetches" — concurrent scheduling, not parallel execution; JS still runs one task at a time — parallelism needs `Worker` threads.
- "`await` creates a new thread" — no; `await` suspends the current `async` function (enqueues its continuation as a job), the thread returns to the loop.
- "Long tasks only affect background tabs" — they block the loop on the thread that runs them; in the main thread they freeze painting and input.

### 5) **Performance note**

Splitting 50ms work into five 10ms chunks with `setTimeout(0)` yields to rendering and keeps input responsive. Yielding via microtasks does *not* yield to rendering — it still starves paint (see [1.2](<./1.2. Microtasks vs macrotasks queueMicrotask and starvation.md>)). `setTimeout` per-chunk costs a macrotask hop (~1–4ms clamping); `await Promise.resolve()` costs a microtask hop (~µs). Use macrotask yields when responsiveness matters.

### 6) **Mentor note**

Have juniors predict `sync → microtask → timer` ordering on `Promise.resolve().then(...)` vs `setTimeout(...,0)` before running — the three-step narration (current task → drain microtasks → next macrotask + render) becomes the mental model for every later async bug. In review, flag any synchronous loop over 10k items in UI code that isn't chunked or moved to a Worker.
