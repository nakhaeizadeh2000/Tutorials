## 1.2. Microtasks vs macrotasks queueMicrotask and starvation

### 1) **Two queues with a fixed drain order — microtasks drain exhaustively after every macrotask**

**Definition** — after a macrotask finishes, the loop drains *all* pending microtasks (promise reaction jobs, `queueMicrotask`, `MutationObserver` callbacks on browsers) before picking the next macrotask or rendering. Microtasks queued *by* microtasks also drain in the same flush, so a microtask chain can delay the next macrotask indefinitely.

**What problem it solves / history** — ES2015 needed promise reactions to be consistently asynchronous but earlier than timers: `then` handlers became spec "Jobs" (microtasks) so `Promise.resolve().then(fn)` always runs after the current task but before `setTimeout(fn,0)`. The trick in the spec is `HostEnqueuePromiseJob`.

**Modern guidance** — use queue choice to convey priority: `queueMicrotask`/`Promise` for "soon but after the current call" (state coalescing, batching), `setTimeout(0)` for "after rendering/timers" (responsiveness), `setImmediate`/`nextTick` on Node when you need to run before I/O polling.

```js
// Canonical ordering — predict before running
console.log("1 sync");

setTimeout(() => console.log("5 macrotask timer"), 0);
console.log("2 sync");

Promise.resolve().then(() => console.log("3 microtask promise"));
queueMicrotask(() => console.log("4 microtask queueMicrotask"));

console.log("6 sync end");
// Order: 1 → 2 → 6 → 3 → 4 → 5
// Rationale: current task to completion → drain microtasks (3,4 in order queued) → next macrotask (5)

// Microtasks queued by microtasks still drain before the timer
Promise.resolve().then(() => {
  console.log("A");
  queueMicrotask(() => console.log("B from microtask"));
  Promise.resolve().then(() => console.log("C nested promise"));
});
setTimeout(() => console.log("D timer"), 0);
// A → B → C → D — A queues B and C, both drain before D

// MutationObserver (browser) is also a microtask-like flush — queued on mutation, drains as microtask
// Node: fs callbacks are poll-phase macrotasks, not microtasks — they wait for microtask drain.
```

### 2) **`queueMicrotask` vs `process.nextTick` vs `setImmediate` — ordering and platform quirks**

**Definition** — Node has a third queue, `nextTick`, that drains *before* the spec microtask queue after each task (and before `setImmediate`/`setTimeout`). `queueMicrotask`/`Promise.then` are spec jobs; `nextTick` is Node-specific and runs even between microtask drains when scheduled inside a microtask. `setImmediate` runs in the `check` phase after `poll` (after pending microtasks).

```js
// Node ordering lab — run with node (browser skips nextTick/setImmediate)
console.log("A");

if (typeof process !== "undefined" && process.nextTick) {
  process.nextTick(() => console.log("B nextTick"));
}
Promise.resolve().then(() => console.log("C promise"));
queueMicrotask(() => console.log("D queueMicrotask"));
if (typeof setImmediate === "function") setImmediate(() => console.log("E setImmediate"));
setTimeout(() => console.log("F setTimeout"), 0);
console.log("G");
// Typical Node: A → G → B → C → D → F → E
// Browser:      A → G → C → D → F  (no B, E is postMessage fallback if polyfilled)

// Promisified microtask — same queue
async function microViaAwait() { await null; console.log("H after await (microtask)"); }
microViaAwait();
console.log("I");
// I → H → before next macrotask — await resumption is a promise job

// Bulk batching via microtask — coalesce multiple synchronous calls into one flush
let pending = false;
let value = 0;
function setValue(v) {
  value = v;
  if (!pending) {
    pending = true;
    queueMicrotask(() => { pending = false; console.log("flush", value); }); // one flush per task
  }
}
setValue(1); setValue(2); setValue(3);
// Logs once: flush 3 — two earlier values coalesced
```

### 3) **Starvation — unbounded microtask chaining blocks rendering and timers**

**Definition** — because microtasks drain exhaustively, a microtask that schedules another microtask never lets the loop reach the next macrotask or browser render. Recursive `queueMicrotask` or `then` chains starve timers, I/O, and painting; the tab appears frozen even without a synchronous infinite loop.

```js
// Starvation demo — uncomment to observe (limit iterations so you can stop it)
// let n = 0;
// function starve() {
//   n++;
//   if (n < 1000) queueMicrotask(starve); // never reaches setTimeout while queue drains
//   else console.log("starved 999 microtasks");
// }
// starve();
// setTimeout(() => console.log("timer finally runs — only after microtasks exhausted"), 0);
// Fix: yield to macrotask periodically

async function microStarver(limit, yieldEvery) {
  for (let i = 0; i < limit; i++) {
    if (i % yieldEvery === 0 && i !== 0) {
      // periodic macrotask yield unblocks rendering/timers
      await new Promise((r) => setTimeout(r, 0));
    } else {
      await Promise.resolve(); // microtask yield — does NOT unblock timers/render
    }
  }
  console.log("done without starvation");
}
microStarver(20, 10).then(() => console.log("microStarver settled"));

// Detecting a runaway — microtask recursion warning pattern
function guardedQueue(fn, budget = 1000) {
  let count = 0;
  (function loop() {
    fn();
    if (++count > budget) {
      console.log("microtask budget exceeded — yielding to macrotask");
      setTimeout(loop, 0);
      return;
    }
    queueMicrotask(loop);
  })();
}
// guardedQueue(() => {}, 5); // yields after 5 to avoid starvation

// Common cause — recursive promise resolution (then returns itself)
let p;
try {
  const self = Promise.resolve(1);
  p = self.then(() => p); // TypeError on assimilation — promise cannot resolve to itself
  p.catch((e) => console.log(e.name)); // TypeError
} catch (e) { console.log(e.name); }
```

### 4) **Common confusion**

- "`queueMicrotask` is the same as `setTimeout(0)`" — no; microtasks run before the next macrotask and before rendering; timers run after. Ordering is deterministic.
- "Starvation only happens with `while(true)`" — recursive microtask scheduling (`then`→`then`→`then`) starves equally, but with a call-stack-friendly shape that looks async.
- "`process.nextTick` is just an alias for `queueMicrotask`" — on Node, `nextTick` drains *before* promise microtasks and can nest even deeper; using it carelessly worsens starvation.
- "Browsers and Node order `setImmediate` the same" — `setImmediate` only exists on Node (and IE legacy); browsers use `setTimeout`/`MessageChannel`/`scheduler.yield`.

### 5) **Performance note**

Each microtask is a job allocation plus a queue hop. 100k `Promise.resolve().then` chains allocate 100k promise/job pairs and keep the loop from painting. For hot synchronous transforms, don't microtask per element — batch into one microtask (the `setValue` coalescing pattern) or yield per chunk via macrotask. Measure with `performance.now()` around the task; profile "Long task" markers in DevTools.

### 6) **Mentor note**

Give candidates `Promise.resolve().then(() => queueMicrotask(() => console.log("B")))` vs `setTimeout` and ask which runs first and why — then ask "what if `B` queues another `queueMicrotask`?" The starvation follow-up surfaces whether they understand exhaustive draining or think "microtask is just faster timer". In review, flag any unbounded `queueMicrotask`/`then` recursion without a periodic `setTimeout(0)` or `scheduler.yield` escape hatch; require a comment stating the intended queue priority.
