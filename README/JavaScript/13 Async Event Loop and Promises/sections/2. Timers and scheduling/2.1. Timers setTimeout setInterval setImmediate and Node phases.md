## 2.1. Timers setTimeout setInterval setImmediate and Node phases

### 1) **`setTimeout`/`setInterval` — minimum delay, clamping, and the `0` vs `4ms` rule**

**Definition** — `setTimeout(fn, delay, ...args)` queues a macrotask to run after at least `delay` ms; `setInterval(fn, delay, ...args)` queues repeatedly. The delay is a *minimum* — actual firing waits for the current task + drained microtasks + earlier timers. Browsers clamp nested timers (depth ≥5) to at least 4ms (`setTimeout(..., 0)` inside a timer becomes 4ms).

**What problem it solves / history** — the original `window.setTimeout` was the only scheduler; clamping was added when ad code abused `setTimeout(0)` loops to starve rendering. Extra `...args` forwarding avoids closure allocation for simple data.

**Modern guidance** — always pass `AbortSignal` or clear handles where lifecycle matters; never rely on `0` meaning "immediate" — it never runs before microtasks.

```js
// Minimum delay — never before microtasks
console.log("A");
setTimeout(() => console.log("C timer 0"), 0);
Promise.resolve().then(() => console.log("B microtask"));
console.log("D");
// A → D → B → C

// Extra args — no closure needed
setTimeout((x, y) => console.log("args", x, y), 0, 10, 20); // args 10 20

// Nested clamping (browser): depth 5+ → 4ms minimum — here we measure ordering not ms
let depth = 0;
function nested() {
  depth++;
  if (depth < 3) setTimeout(nested, 0);
  else if (depth === 3) console.log("nested depth 3 done", depth);
}
setTimeout(nested, 0);

// clearTimeout — cancelled task never runs
const h = setTimeout(() => console.log("should not fire"), 50);
clearTimeout(h);
console.log("cleared before fire");

// Node ref/unref — interval keeps loop alive unless unref'd (Node-only, guarded)
if (typeof setInterval === "function") {
  const iv = setInterval(() => {}, 1000);
  if (iv.unref) { iv.unref(); clearInterval(iv); console.log("interval unref pattern shown"); }
}

// AbortSignal with setTimeout (Node 15+, browsers 20+)
if (typeof AbortSignal !== "undefined" && typeof setTimeout === "function") {
  const ac = new AbortController();
  const t = setTimeout(() => console.log("signal timeout fired"), 1000);
  // clear on abort — manual wiring where runtime lacks signal-aware timers
  ac.signal.addEventListener("abort", () => { clearTimeout(t); console.log("aborted timer"); });
  ac.abort(); // aborted timer
}
```

### 2) **`setImmediate` vs `setTimeout(0)` vs `nextTick` — where each runs in Node's phases**

**Definition** — Node's loop phases in one iteration: `timers` (`setTimeout`/`setInterval`) → `pending callbacks` → `idle/prepare` → `poll` (I/O completions) → `check` (`setImmediate`) → `close callbacks`. `process.nextTick` drains before microtasks after *every* phase. Consequences: `nextTick` queued inside a microtask still runs before the next microtask; `setImmediate` always runs *after* poll (after pending I/O), while `setTimeout(0)` runs in the next `timers` check.

```js
// Phase ordering lab — run with node
if (typeof process !== "undefined" && process.nextTick && typeof setImmediate === "function") {
  console.log("phase: sync");
  setTimeout(() => console.log("phase: timers"), 0);
  // pending/poll simulated via fs (poll phase), so also:
  setImmediate(() => console.log("phase: check (setImmediate)"));
  process.nextTick(() => console.log("phase: nextTick"));
  Promise.resolve().then(() => console.log("phase: microtask promise"));
  queueMicrotask(() => console.log("phase: queueMicrotask"));
  console.log("phase: sync end");
  // Typical: sync → sync end → nextTick → promise → queueMicrotask → timers → check
}

// Why it matters — setImmediate after I/O
if (typeof require !== "undefined") {
  try {
    const fs = require("fs");
    fs.readFile(__filename || "dummy", () => {
      console.log("poll callback (readFile)");
      setTimeout(() => console.log("timer after I/O"), 0);
      setImmediate(() => console.log("check after I/O — runs before timers in this iteration"));
    });
    // Inside poll callback: setImmediate fires before the next timers pass
  } catch {}
}

// Browser polyfill — no native setImmediate: use MessageChannel or postMessage
if (typeof setImmediate === "undefined" && typeof MessageChannel !== "undefined") {
  const ch = new MessageChannel();
  ch.port1.onmessage = () => console.log("polyfilled immediate via MessageChannel");
  ch.port2.postMessage(null);
}
// Prefer queueMicrotask for next-tick micro work, setTimeout(0) for next macrotask on browsers.
```

### 3) **Cancellation and handle discipline — `clearTimeout`/`clearInterval` and orphaned timers**

**Definition** — timers hold the loop alive (Node `ref`, browser page lifecycle) until cleared. An uncanceled `setInterval` that closes over growing state leaks memory and CPU; a `setTimeout` recursion that never clears or aborts keeps retry storms alive.

```js
// Leak: forgotten interval survives module teardown
function startPolling(ms, label) {
  const id = setInterval(() => console.log(label, Date.now()), ms);
  return () => { clearInterval(id); console.log("polling stopped", label); };
}
const stop = startPolling(100, "poll");
setTimeout(stop, 250); // stops after ~2 ticks — teardown pattern

// BAD — unbounded recursive setTimeout without signal
async function badRetry(fn, delay = 50) {
  while (true) { // never stops externally
    try { return await fn(); } catch { await new Promise((r) => setTimeout(r, delay)); }
  }
}
// GOOD — signal-aware
async function goodRetry(fn, { delay = 50, signal } = {}) {
  while (true) {
    if (signal?.aborted) throw signal.reason ?? new Error("aborted");
    try { return await fn(); } catch {
      await new Promise((resolve, reject) => {
        if (signal?.aborted) return reject(signal.reason);
        const id = setTimeout(resolve, delay);
        signal?.addEventListener("abort", () => { clearTimeout(id); reject(signal.reason); }, { once: true });
      });
    }
  }
}
const ac = new AbortController();
let attempts = 0;
goodRetry(async () => { if (++attempts < 2) throw new Error("flaky"); return "ok"; }, { delay: 5, signal: ac.signal })
  .then((v) => console.log("retry", v)); // ok

// Debounced timers also need cancel — see 2.2
```

### 4) **Common confusion**

- "`setTimeout` delay is exact" — it's a lower bound; GC, long tasks, clamped nesting, and pending microtasks all add delay.
- "`setImmediate` === `setTimeout(0)`" — only in non-I/O contexts they may swap order nondeterministically; after I/O, `setImmediate` wins reliably in Node.
- "`nextTick` is a microtask" — close but Node drains `nextTick` *before* spec microtasks; don't intermix them as identical.
- "Browsers have `setImmediate`" — no (except legacy IE); `MessageChannel`/`scheduler.yield` or `setTimeout(0)` are the browser equivalents.
- "Cancelling a promise cancels its timer" — promises have no cancellation; cancel the *signal* wired to the timer.

### 5) **Performance note**

Creating a `setTimeout` per element (10k timers) enqueues 10k macrotasks; prefer one batched timer or `Promise.all` with chunked delays. `setInterval` drift is host-queued, not precise clock — for animation, use `requestAnimationFrame` (browser) or `setInterval` + timestamp correction, not tight `setTimeout` recursion assuming zero drift.

### 6) **Mentor note**

Give juniors `fs.readFile` → `setTimeout` vs `setImmediate` inside the callback and ask which logs first — the deterministic `setImmediate` before `setTimeout` in the poll→check transition teaches the phase model concretely. In review, flag any `setInterval` without a corresponding `clearInterval`/`unref` on teardown, any `setTimeout` recursion without `AbortSignal`, and any browser code assuming `setImmediate` exists.
