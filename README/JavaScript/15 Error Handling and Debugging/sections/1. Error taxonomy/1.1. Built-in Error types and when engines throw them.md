## 1.1. Built-in Error types and when engines throw them

### 1) **Native hierarchy — `Error` base and its seven children**

**Definition** — `Error` is the base constructor every builtin error inherits from. Seven historic children specialize by cause: `SyntaxError`, `ReferenceError`, `TypeError`, `RangeError`, `URIError`, `EvalError` (legacy), `AggregateError` (ES2021). All share `name`, `message`, and (non-standard but universal) `stack`; `AggregateError` adds `errors`; ES2022 adds optional `cause` to any `Error`.

**What problem it solves / history** — early JS used `throw "string"` and callers parsed `.toString()`. The hierarchy lets `catch` branch by intention (`RangeError` = bounds, `TypeError` = illegal operation) instead of regex on messages that change across engines/locales.

**Modern guidance** — always construct specific subtypes. `new TypeError("x must be a number")` carries actionable semantics; `new Error` is the generic fallback. Subclass your domain errors from `TypeError`/`RangeError` when that semantic fits — see [1.2](<./1.2. Custom errors cause chaining and AggregateError.md>).

```js
// Hierarchy — all builtins inherit Error
const cases = [
  new Error("generic"),
  new SyntaxError("bad syntax"),
  new ReferenceError("missing binding"),
  new TypeError("illegal operation"),
  new RangeError("out of range"),
  new URIError("bad URI"),
  new EvalError("eval misuse"),
  new AggregateError([new Error("a")], "many"),
];
for (const e of cases) {
  console.log(e.name, "instanceof Error:", e instanceof Error, "msg:", e.message);
}
// name drives the header of stack — `TypeError: illegal operation`
console.log(new TypeError("x").name, new TypeError("x").toString().slice(0, 30));

// Subclass hint — set name explicitly or it stays "Error"
class NotFoundError extends Error { constructor(m){ super(m); this.name = "NotFoundError"; } }
console.log(new NotFoundError("id 42").name, new NotFoundError("id 42") instanceof Error);
```

### 2) **When the engine throws — parse vs early vs runtime `throw`**

**Definition** — engines throw at three phases: *parse* (`SyntaxError` before any code runs), *early errors* at instantiation (duplicate bindings, bad `break`), and *runtime* execution (`ReferenceError`/`TypeError`/`RangeError`/`URIError`) via the `throw` completion. Understanding phase explains why `try/catch` can or cannot catch.

| Phase | Example code | Thrown | Catchable with runtime `try`? |
|-------|--------------|--------|-------------------------------|
| Parse | `eval("for(")` | `SyntaxError` at parse | No for outer file; yes if inside `try { eval("for(") }` |
| Early | `'use strict'; delete x` | `SyntaxError` at instantiation | Same as parse — per script/module |
| Runtime | `undeclaredVar` sloppy | `ReferenceError` at execution | Yes |
| Runtime | `null.x` | `TypeError` | Yes |
| Runtime | `new Array(-1)` | `RangeError` | Yes |
| Runtime | `decodeURI("%")` | `URIError` | Yes |
| Throw completion | `throw new Error("hi")` | propagates until `catch` or job boundary | Yes if caught |

```js
// Parse vs runtime — try inside eval can catch what outer try cannot for file-level parse
try { eval("for("); } catch (e) { console.log("caught eval parse:", e.name); } // SyntaxError
try { Function("for(")(); } catch (e) { console.log("caught Function parse:", e.name); } // SyntaxError

// Runtime cases
try { console.log(undeclaredXYZ); } catch (e) { console.log(e.name); } // ReferenceError
try { null.x; } catch (e) { console.log(e.name); } // TypeError
try { new Array(-1); } catch (e) { console.log(e.name); } // RangeError
try { decodeURI("%"); } catch (e) { console.log(e.name); } // URIError
try { (function f(n){ if(n<=0) return; f(n-1); f(n-1); })(1e6); } catch (e) { console.log(e.name); } // RangeError stack overflow (approx)
```

### 3) **Instance checks — `instanceof Error` vs `err.name ===` and cross-realm pitfalls**

**Definition** — `err instanceof Error` walks the prototype chain of the current realm's `Error`. `err.name` is a string property. Cross-realm errors (from `vm` context, `iframe`, `worker`) have a *different* `Error` constructor, so `instanceof` fails even though it is logically an error.

**Modern guidance** — prefer `err instanceof Error` within a single realm, but guard cross-realm and `throw non-Error` with `Error.isError(err)` (ES2025, polyfill as `typeof err === "object" && err !== null && "name" in err && "message" in err`) or duck-typing `typeof err?.message === "string"`. For precise branching, check `err.code` (Node `ERR_*`) before `name`.

```js
// instanceof vs name vs cross-realm
console.log(new TypeError("t") instanceof Error, new TypeError("t") instanceof TypeError); // true true
console.log(new TypeError("t").name === "TypeError"); // true — but name is writable!

// Cross-realm failure — vm context has its own Error
let vmErr;
try {
  const vm = require("node:vm");
  const ctx = vm.createContext({});
  vmErr = vm.runInContext("new TypeError('from vm')", ctx);
} catch { vmErr = null; }
if (vmErr) {
  console.log("vmErr instanceof Error (outer):", vmErr instanceof Error); // false — different realm
  console.log("vmErr.name:", vmErr.name); // TypeError
  console.log("duck:", typeof vmErr.message === "string"); // true
  // ES2025: Error.isError when available
  const isErr = typeof Error.isError === "function" ? Error.isError(vmErr) : (vmErr instanceof Error || typeof vmErr?.stack === "string");
  console.log("isError:", isErr);
}

// Anti-pattern — relying on message substring
function badBranch(e){ return /not found/i.test(e.message); } // fragile across locales
function goodBranch(e){ return e.code === "ENOENT" || e.name === "NotFoundError"; }
console.log(typeof badBranch, typeof goodBranch);
```

### 4) **Properties engines actually set — `name`/`message`/`stack`/`cause` and Node `code`**

**Definition** — spec defines only `name` (`"Error"` on `Error.prototype.name`) and `message` (first arg). `cause` (ES2022 options bag `{cause}`) is spec. `stack` is de-facto V8/SpiderMonkey (not in ECMA-262) but universal; `code` (`"ERR_INVALID_ARG_TYPE"` etc.) is Node-only convention for `SystemError`-like errors.

**Modern guidance** — read `err.message` for humans, `err.cause` for chain, `err.code` for machine branching (Node), and `err.stack` for on-call triage (always log). Never parse `stack` for control flow; never set `stack` manually unless wrapping with `captureStackTrace`.

```js
// What each constructor stores
const low = new TypeError("bad id type");
const high = new Error("load failed", { cause: low }); // ES2022
console.log(high.message, high.cause === low, high.name, typeof high.stack);

// stack is V8-formatted — header + frames
console.log(high.stack.split("\n")[0]); // "Error: load failed"
console.log(high.stack.includes("at ")); // true

// Node code — fs errors carry code
const fs = require("node:fs");
try { fs.readFileSync("/no/such/file-xyz-15-1-1"); } catch (e) {
  console.log(e.name, e.code, e.message.slice(0, 40));
  console.log("cause?", e.cause);
}

// Message is whatever you pass — coerce early to string for safety
function makeType(msg){ return new TypeError(String(msg)); }
console.log(makeType(42).message);
```

### 5) **Common confusion**

- "`TypeError` means wrong type annotation" — it means an illegal operation on the runtime type (`null.x`, calling a non-function). `ReferenceError` is missing binding/TDZ ([Variables Scope](<../../../04 Variables Scope and Closures/sections/1. Declarations and bindings/1.2. Temporal dead zone why early access throws.md>)).
- "`SyntaxError` can always be caught" — only if the `try` wraps the `eval`/`Function` that parses that string. A syntax error in the file itself aborts evaluation before any runtime `try` runs.
- "`instanceof Error` is sufficient" — cross-realm `vm`/`worker` errors fail the check; use `Error.isError` or duck-type.
- "`stack` is standard" — it is not in ECMA-262; format differs V8 vs JSC. Treat as diagnostic string only.

### 6) **Performance note**

Constructing `Error` eagerly captures a stack (walking `CallSite`s, allocating strings). In hot paths where you branch on expected conditions, prefer guards/Result instead of `throw` (see [3.2](<../3. Defensive patterns/3.2. Assertions guards Result Either and when not to throw.md>)). Set `Error.stackTraceLimit` low in tight loops only if you must throw.

### 7) **Mentor note**

Have juniors classify 10 throws by bucket (`SyntaxError` vs `ReferenceError` vs `TypeError` vs `RangeError` vs `URIError`) — misbucketing signals missing spec mental model. In review, flag string `throw` and `instanceof Error` across `vm`/`worker` boundaries; require `name`/`code` branching and `cause` chaining.
