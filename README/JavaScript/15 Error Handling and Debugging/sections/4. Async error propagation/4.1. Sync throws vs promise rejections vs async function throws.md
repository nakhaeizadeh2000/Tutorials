## 4.1. Sync throws vs promise rejections vs async function throws

### 1) **Sync throw vs async reject — thrown sync never becomes a rejection unless awaited**

**Definition** — synchronous `throw` unwinds the call stack to the nearest `try/catch`. A `Promise` rejection is a settled async value; it is observed only via `.catch`/`await`/`unhandledrejection`. They are distinct completion types. `new Promise` executor `throw` is automatically converted to `reject`, but a plain sync function that returns a rejecting promise does *not* throw.

**What problem it solves / history** — mixing `throw` and `reject` caused dropped errors: `try { fetch() } catch` never catches network rejection because `fetch` returns a promise, not throws.

**Modern guidance** — `try/catch` handles sync `throw`; `await`/`catch` handles rejections. Never expect `try { promise } catch` without `await` to catch.

```js
// Sync throw — caught by try/catch
function syncThrow(){ throw new Error("sync"); }
try { syncThrow(); } catch (e){ console.log("sync caught:", e.message); }

// Promise rejection — NOT caught by try/catch without await
function asyncReject(){ return Promise.reject(new Error("async")); }
try { asyncReject().catch(()=>{}); } catch (e){ console.log("never:", e); } // not caught — need .catch or await
asyncReject().catch(e => console.log("promise catch:", e.message));

// Executor throw becomes reject automatically
const pExec = new Promise(() => { throw new Error("exec throw"); });
pExec.catch(e => console.log("exec throw -> reject:", e.message));

// async function throw becomes reject
async function asyncFnThrow(){ throw new Error("async fn throw"); }
asyncFnThrow().catch(e => console.log("async fn throw -> reject:", e.message));
console.log("asyncFnThrow returns promise, does not throw sync:", asyncFnThrow().catch(()=>{}) instanceof Promise);

// Pattern: normalize sync or async failures to promise
function safeCall(fn){ try { return Promise.resolve(fn()); } catch (e) { return Promise.reject(e); } }
safeCall(() => { throw new Error("from sync"); }).catch(e=>console.log("safeCall caught:", e.message));
safeCall(() => Promise.reject(new Error("from async"))).catch(e=>console.log("safeCall async:", e.message));
```

### 2) **`await` rethrow translation — `await rejected` throws at suspension point**

**Definition** — `await expr` suspends, and if `expr` settles as rejection, it *throws* at the suspension point with the rejection reason as the thrown error. Thus `try { await p } catch (e)` catches rejections; `try { p } catch` without `await` does not.

**Modern guidance** — always `await` inside `try` when you intend to `catch` that operation. `return await` vs `return p` inside `try/finally` matters (see [Async Event Loop 5.1](<../../../13 Async Event Loop and Promises/sections/5. Async functions concurrency and migration/5.1. async await desugaring error handling and gotchas.md>)).

```js
// await translates reject to throw
async function demoAwaitCatch(){
  try { await Promise.reject(new Error("awaited reject")); }
  catch (e){ console.log("await catch:", e.message); }
}
demoAwaitCatch();

// Without await — not caught
async function demoNoAwait(){
  try { Promise.reject(new Error("no await")).catch(()=>{}); } catch(e){ console.log("no"); }
  console.log("demoNoAwait continued — try/catch did not fire");
}
demoNoAwait().catch(()=>{});
demoNoAwait().catch(()=>{}); // suppress unhandled for demo — actually leaks, see 4.2

// return await vs return p inside try — subtle
async function returnAwait(){
  try { return await Promise.reject(new Error("return await")); }
  catch(e){ console.log("return await caught:", e.message); return "recovered"; }
}
async function returnBare(){
  try { return Promise.reject(new Error("return bare")); }
  catch(e){ console.log("return bare caught — never", e); return "recovered"; }
}
(async () => {
  console.log(await returnAwait()); // recovered — caught
  console.log(await returnBare().catch(e=> "recovered bare: "+e.message)); // rejection escapes try
})();

// then handler throw becomes rejection of chained promise (see 4.2)
Promise.resolve(1).then(() => { throw new Error("then throw"); }).catch(e=>console.log("then throw -> reject:", e.message));
```

### 3) **Callback-to-promise bridges — `promisify`, `withResolvers`, and thenable assimilation throwing**

**Definition** — callback APIs communicate errors via `(err, value)`. Bridges (`util.promisify`, `Promise.withResolvers`) translate `err` to `reject` and `throw` inside `then`/`executor` to rejection. Thenable assimilation unwraps `thenable` one level per job; a `then` getter throwing rejects.

```js
const fs = require("node:fs");
const { promisify } = require("node:util");
const readFile = promisify(fs.readFile);

// promisify converts (err,val) -> reject/resolve
// For demo we simulate error-first callback
function cbOp(x, cb){ setTimeout(()=> x ? cb(null, x*2) : cb(new Error("bad x")), 0); }
const cbProm = promisify(cbOp);
cbProm(21).then(v=>console.log("promisify ok:", v));
cbProm(null).catch(e=>console.log("promisify err:", e.message));

// Promise.withResolvers — deferred without executor anti-pattern (ES2024)
const { promise, resolve, reject } = Promise.withResolvers();
promise.then(v=>console.log("withResolvers:", v)).catch(()=>{});
resolve(42);

// Throw inside executor rejects synchronously but as a job — catch via .catch
const pThen = Promise.resolve(1).then(v => { if (v===1) throw new TypeError("bad 1"); return v; });
pThen.catch(e=>console.log("then throw ->", e.name));

// Thenable that throws on access — assimilation rejects
const badThenable = { get then(){ throw new Error("then getter throw"); } };
Promise.resolve(badThenable).catch(e=>console.log("thenable throw:", e.message));

console.log("bridges ready — unhandled cases handled via catch or await");
```

### 4) **Common confusion**

- "`try/catch` around `fetch()` catches network failure" — only `try { await fetch() } catch`. Bare `try { fetch() }` completes before settlement.
- "`async` function without `await` still throws" — if it `throw`s before first `await`, it still returns a *rejected promise*, not a sync throw. The caller must `.catch`/`await`.
- "`return await` is redundant" — inside `try` it is not; `return p` without `await` bypasses `catch`. ESLint `no-return-await` has an exception for `try`.
- "`Promise.reject` needs `try/catch`" — it needs `.catch`/`await`/`unhandledrejection` handler, not sync `try`.

### 5) **Performance note**

Each `await` allocates a promise job (microtask). Tight loops doing `await` per item pay that cost. Prefer `Promise.all` batch for independent operations (see [13 4.1](<../../../13 Async Event Loop and Promises/sections/4. Promise combinators and utilities/4.1. Promise.all and allSettled parallel aggregation.md>)); keep `await` for sequential dependencies only.

### 6) **Mentor note**

Have juniors rewrite `try { fetchData() } catch` (no await) to correctly handle both sync throw (`TypeError` pre-check) and async reject (`await` + `cause` wrap). In review, flag `try { promise } catch` missing `await` — require `await` or `.catch`. Flag manual deferred anti-pattern `let resolve; new Promise(r=> resolve=r)` — require `Promise.withResolvers`.
