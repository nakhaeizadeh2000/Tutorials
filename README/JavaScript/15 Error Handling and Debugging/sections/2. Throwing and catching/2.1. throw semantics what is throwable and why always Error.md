## 2.1. throw semantics what is throwable and why always Error

### 1) **Anything can be thrown — but only `Error` preserves a stack and chain**

**Definition** — `throw expr;` evaluates `expr` and unwinds to the nearest `catch`/`finally` or job boundary, completing with `throw`. `expr` may be any value (`string`, `number`, `null`, object) — the language does not require `Error`.

**What problem it solves / history** — allowing any throwable predates structured errors; early code threw strings for brevity (`throw "bad"`). Tooling (loggers, reporters) evolved to expect `Error.stack`/`name`/`cause`.

**Modern guidance** — always `throw new Error` (or subtype). Throwing non-`Error` loses `stack`, breaks `cause` chaining, breaks `instanceof Error` guards, and breaks error-reporting grouping.

```js
// What you can throw
try { throw "oops-string"; } catch (e) { console.log(typeof e, e, e instanceof Error); } // string false
try { throw 42; } catch (e) { console.log(typeof e, e instanceof Error); } // number false
try { throw null; } catch (e) { console.log(e, e instanceof Error); } // null false
try { throw new Error("oops-Error"); } catch (e) { console.log(e.name, typeof e.stack); } // Error string

// Why non-Error hurts — no stack
try { throw "not found: 42"; } catch (e) {
  console.log("string throw has stack?", typeof e.stack); // undefined — triage blind
}
try { throw new Error("not found: 42"); } catch (e) {
  console.log("Error throw head:", e.stack.split("\n")[0]);
}

// Rule: normalize at boundary — if you must interop with string throws:
function normalize(e){ return e instanceof Error ? e : new Error(String(e), { cause: e instanceof Error ? undefined : e }); }
try { throw "legacy"; } catch (e) {
  const n = normalize(e);
  console.log(n.name, n.message, typeof n.stack);
}
```

### 2) **Throw is a statement — expression position, `throw` vs `Error` construction, and ASI hazard**

**Definition** — `throw` is a statement requiring same-line expression (`throw expr`), not an operator. `new Error("msg")` constructs but does not throw; `throw` initiates unwinding.

**Common pitfalls** — newline after `throw` triggers `SyntaxError` (ASI does not insert a value). Ternary must wrap the throw in a function/IIFE because `throw` is not an expression (use `() => { throw ... }` or `throw` inside block).

```js
// Newline hazard — SyntaxError: Illegal newline after throw
try { Function("throw\nnew Error('hi')")(); } catch (e) { console.log(e.name); } // SyntaxError

// Good — same line
function fail(msg){ throw new Error(msg); }
try { fail("boom"); } catch (e) { console.log(e.message); }

// new Error without throw does nothing — silent bug:
function badValidate(x){
  if (!x) new Error("required"); // constructed then discarded — no throw, no side effect
  return x;
}
console.log(badValidate("") === ""); // true — bug: should have thrown

function goodValidate(x){
  if (!x) throw new Error("required");
  return x;
}
try { goodValidate(""); } catch (e) { console.log(e.name); } // Error

// throw in ternary — must wrap:
const value = null;
try {
  const r = value ?? (() => { throw new Error("missing"); })();
  console.log(r);
} catch (e) { console.log("ternary throw:", e.message); }
```

### 3) **Non-Error throws break tooling — stacks, `instanceof`, reporters, and `cause` expect `Error`**

**Definition** — loggers group by `err.name`/`err.stack`, alert rules branch `err instanceof TypeError` or `err.code`, and serialization walks `err.cause`/`err.errors`. Non-`Error` throws lack these, so grouping fails and on-call loses triage.

| Throw | `instanceof Error` | `stack` | `cause` | Reporter grouping | Remedy |
|-------|-------------------|---------|---------|------------------|--------|
| `throw "x"` | false | missing | no | one bucket `"string"` | `throw new Error("x")` |
| `throw {message:"x"}` | false | missing | maybe manual | `"Object"` | `throw new Error("x", {cause})` |
| `throw null` | false | missing | no | crash on `e.message` access | `throw new Error("null throw")` |
| `throw new Error("x")` | true | V8 stack | yes | per `name` | keep |

```js
// Broken reporter grouping with string throw
function report(e){
  const key = e instanceof Error ? e.name : `NonError:${typeof e}`;
  console.log("report key:", key);
}
try { throw "db timeout"; } catch (e) { report(e); } // NonError:string — loses granularity
try { throw new Error("db timeout"); } catch (e) { report(e); } // Error — correct

// cause requires Error wrapping
try {
  const low = new TypeError("bad id");
  throw "wrap failed"; // lost cause
} catch (e) { console.log("lost cause, is Error?", e instanceof Error); }

try {
  const low = new TypeError("bad id");
  throw new Error("wrap failed", { cause: low });
} catch (e) { console.log("kept cause:", e.cause.name); }

// Guard at catch site — narrow to Error before reading .stack/.cause
function handle(e){
  if (!(e instanceof Error)) e = new Error(String(e));
  console.log(e.name, typeof e.stack);
}
try { throw 42; } catch (e) { handle(e); }

// ES2025 Error.isError — realm-safe guard
const isError = typeof Error.isError === "function" ? Error.isError : (x) => x instanceof Error;
console.log(isError(new Error("hi")), isError("hi"));
```

### 4) **Common confusion**

- "`throw` returns a value like `return`" — it does not; completion is `throw`, not a value. `const x = throw new Error()` is `SyntaxError`; `const x = (()=>{ throw new Error()})()` throws past assignment.
- "`new Error` throws" — construction captures stack but does not unwind. Bug `if (!ok) new Error("bad")` is silent.
- "`throw null` is caught as `null`" — true, and `catch (e) { e.message }` then throws `TypeError: Cannot read properties of null` hiding original.
- "`throw` after `await` is caught by sync `try/catch` around promise creation" — no, `await` translation requires `try { await p }` not `try { p }`.

### 5) **Performance note**

`throw` that is actually thrown unwinds and captures a stack — two allocations plus deoptimization of the throwing function. `new Error` without `throw` never captures? Actually V8 captures stack at construction already, so avoid `new Error` on happy path. Prefer guards before constructing errors.

```js
// BAD — always allocates Error even when valid:
function badParse(s){ const err = new Error("bad"); if (!s) throw err; return s; }
// GOOD — allocate only on failure:
function goodParse(s){ if (!s) throw new Error("bad"); return s; }
console.log(goodParse("hi"));
try { goodParse(""); } catch (e) { console.log(e.message); }
```

### 6) **Mentor note**

Lint `throw` sites: flag `throw "` / `throw '` / `throw 42` / `throw null` / `throw {` with `no-throw-literal` (ESLint). Require each `throw` target to be `new Error`/`TypeError`/`custom extends Error`. In review, grep `new Error(` without preceding `throw` — likely discarded error construction bug.
