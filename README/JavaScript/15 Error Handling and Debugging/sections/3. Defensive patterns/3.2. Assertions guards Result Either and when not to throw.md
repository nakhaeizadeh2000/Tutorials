## 3.2. Assertions guards Result Either and when not to throw

### 1) **Invariants — `assert`/`invariant` for programmer errors that should never be caught**

**Definition** — an *invariant* is a condition that must hold for the program to be correct; violating it is a programmer bug, not a recoverable runtime condition. `assert(cond, msg)` throws if `cond` is falsy. `invariant` is Node's assertion that throws `AssertionError`.

**What problem it solves / history** — exceptions for programmer errors should fail fast near the bug, not be caught and retried. Guarding with `if (!ok) return null` hides misuse; assertions surface it during dev/test.

**Modern guidance** — use `assert`/`invariant` at function entry for preconditions that callers must guarantee; strip heavy assertions in prod via `process.env.NODE_ENV` guard if hot. Node imports `node:assert/strict` for deep equality.

```js
// Node assert vs console.assert
const assert = require("node:assert/strict");
try { assert.equal(1, 2, "oops"); } catch (e) { console.log(e.name, e.message.slice(0,20)); }
console.assert(1 === 1, "this prints nothing");
console.assert(1 === 2, "console.assert logs but does NOT throw — not an invariant!");

function invariant(cond, msg){ if(!cond) throw new Error(msg); } // minimal
function getUser(id){
  invariant(typeof id === "string" && id.length > 0, "getUser: id must be non-empty string");
  return { id };
}
console.log(getUser("u1"));
try { getUser(""); } catch (e){ console.log(e.message); }

// Exhaustive check with assertNever — catches unhandled union member at compile time (TS) / runtime throw here:
function assertNever(x){ throw new Error(`Unhandled variant: ${String(x)}`); }
function handleStatus(s){
  if (s === "ok" || s === "err") return s;
  assertNever(s);
}
try { handleStatus("unknown"); } catch(e){ console.log(e.name); }
```

### 2) **Guards vs throws — validate at boundary (`if (!ok) throw`) vs recoverable paths**

**Definition** — *boundary validation* (API edge) throws `TypeError`/`RangeError`/`ValidationError` to signal caller misuse. *Internal recoverable* paths return early or default; throwing for expected user mistakes complicates control flow.

| Context | Pattern | Why |
|---------|---------|-----|
| Public function, caller must satisfy contract | `if (!ok) throw new TypeError` | fast fail, stack points to caller |
| User input from form/network | validate → return `{errors}` or `Result` | expected failure, not exceptional |
| Internal loop hot path | guard + early `return`/`continue` | `throw` deoptimizes and allocates |
| Library helper that callers retry | throw with `code`/`cause` | caller branches `if (e.code==="RETRYABLE")` |

```js
// BAD — throwing for expected user input hides control flow:
function badSaveUser(input){
  if (!input.email) throw new Error("email required"); // outside boundary the UI catches? awkward
  // caller forced to try/catch for normal validation
}

// GOOD — boundary throw for programmer misuse, Result for user input:
function parseEmailBoundary(email){
  if (typeof email !== "string") throw new TypeError("email must be string"); // caller bug
  return email; // internal may still validate
}
function validateUser(input){
  const errors = [];
  if (!input.email) errors.push("email required");
  else if (!input.email.includes("@")) errors.push("email must contain @");
  return errors.length ? { ok:false, errors } : { ok:true, value: { email: input.email } };
}
console.log(parseEmailBoundary("a@b.com"));
try { parseEmailBoundary(42); } catch(e){ console.log(e.name); }
console.log(validateUser({ email: "" }), validateUser({ email: "a@b" }));

// Guard before heavy work — avoid throw in tight loop:
function sumValid(xs){
  let s=0;
  for (const x of xs) { if (typeof x !== "number" || !Number.isFinite(x)) continue; s += x; }
  return s;
}
console.log(sumValid([1, 2, "x", NaN, 3])); // 6 — guard skips without throw
```

### 3) **Result/Either style — `{ok, value/error}` or discriminated union instead of exceptions for expected failures**

**Definition** — *Result* type encodes success/failure as data (`{ok:true,value}` vs `{ok:false,error}`) instead of control flow via `throw`. Callers must handle both branches; no stack unwinding.

**Modern guidance** — use `Result` when failures are *expected* and frequent (validation, parsing, cache miss) or when you want exhaustive handling. Translate to `throw` at the boundary where the caller expects exceptions (e.g., HTTP handler).

```js
// Minimal Result
/** @typedef {{ok:true, value:any} | {ok:false, error:Error}} Result */
function ok(value){ return { ok:true, value }; }
function err(error){ return { ok:false, error }; }
function tryParse(json){
  try { return ok(JSON.parse(json)); } catch (e){ return err(e); }
}
const a = tryParse('{"a":1}');
const b = tryParse("{bad");
console.log(a.ok, a.value, b.ok, b.error.name);
if (!b.ok) console.log("branch must handle error:", b.error.message.slice(0,20));

// Either as discriminated union for exhaustive switch:
function validateAge(raw){
  if (typeof raw !== "number") return { ok:false, error: new TypeError("age must be number") };
  if (!Number.isInteger(raw) || raw < 0) return { ok:false, error: new RangeError("age must be integer >=0") };
  return { ok:true, value: raw };
}
for (const v of [20, -1, "x"]) {
  const r = validateAge(v);
  if (r.ok) console.log("age", r.value);
  else console.log("age error", r.error.name, r.error.message);
}

// Interop — throw at boundary that expects exceptions:
function parseOrThrow(json){ const r = tryParse(json); if(!r.ok) throw r.error; return r.value; }
try { parseOrThrow("{bad"); } catch(e){ console.log("orThrow:", e.name); }

// Why not always throw — throw in hot path deoptimizes:
console.log("Result avoids stack allocation per item; throw allocates stack per failure — measure, but bias to Result for >1% failure rate");
```

### 4) **Common confusion**

- "`console.assert` throws" — it does not; it logs to stderr and continues. Use `node:assert` or `invariant` for throwing.
- "`Result` means never throw" — hybrids are fine; parse with `Result` internally, throw at API boundary if contract says so.
- "`assert` should be caught" — no, invariant failures are *not* caught locally; they crash to surface the bug. Catching them hides the programmer error.
- "`throw` for control flow is idiomatic" — in JS it is not; use `Result`/guards for expected branches; `throw` for truly exceptional paths.

### 5) **Performance note**

`throw` + `catch` on a hot loop (e.g., 1e5 iterations with 10% throws) is measurably slower than `Result` guards due to stack capture + deoptimization. Benchmark with `performance.now()` before choosing. `Error.stackTraceLimit` still costs per `throw`; guarding avoids the cost entirely.

```js
// Tiny bench illustration — count guard vs throw in 50k loop
function withThrow(xs){
  let s=0;
  for (const x of xs) try { if (typeof x!=="number") throw new TypeError(); s+=x; } catch { /* ignore */ }
  return s;
}
function withGuard(xs){
  let s=0;
  for (const x of xs) if (typeof x==="number") s+=x;
  return s;
}
const data = Array.from({length: 50000}, (_,i)=> i%10===0 ? "x" : i);
console.time("throw"); withThrow(data); console.timeEnd("throw");
console.time("guard"); withGuard(data); console.timeEnd("guard");
```
