## 1.2. Safe integers BigInt boundary epsilon and precision

### 1) **Safe integers — `MAX_SAFE_INTEGER` and why `9007199254740992 === 9007199254740993`**

**Definition** — a *safe integer* is one that can be represented exactly as a double: `-(2^53-1)` to `2^53-1` inclusive (`Number.MIN_SAFE_INTEGER`/`MAX_SAFE_INTEGER` = `±9007199254740991`). Beyond that, the 53-bit mantissa cannot encode every integer — gaps appear: every second integer is missing after `2^53`, every fourth after `2^54`, etc. `Number.isSafeInteger(x)` checks finiteness + integrality + range.

```js
console.log(Number.MAX_SAFE_INTEGER); // 9007199254740991 — 2^53 - 1
console.log(Number.MIN_SAFE_INTEGER); // -9007199254740991
console.log(Number.isSafeInteger(9007199254740991)); // true
console.log(Number.isSafeInteger(9007199254740992)); // false — 2^53 itself is integral but not safe? Actually 2^53 IS representable but next integer is not — spec says safe iff |x| <= 2^53-1
console.log(9007199254740992 === 9007199254740993); // true — collapse: both encode as 2^53
console.log(9007199254740992 + 1 === 9007199254740992); // true — increment lost
console.log(9007199254740992 + 2 === 9007199254740994); // true — but +2 lands on next representable (gap of 2)
console.log(Number.isInteger(9007199254740992)); // true — still integer, just colliding
console.log(Number.isSafeInteger(1e15)); // true — 1e15 < 2^53
console.log(Number.isSafeInteger(1e16)); // false — 1e16 > 2^53, gaps

// JSON loses safety silently
const id = 9007199254740993;
console.log(JSON.stringify({ id })); // {"id":9007199254740992} — truncated before it leaves JS
console.log(JSON.parse('{"id":9007199254740993}').id === 9007199254740992); // true — parse already collapsed
```

### 2) **`EPSILON` and floating-point comparison — never `===` on computed floats**

**Definition** — `Number.EPSILON` (`2^-52` ≈ `2.220446049250313e-16`) is the gap between `1` and the next representable double. It quantifies rounding error near `1`. Computed floats (like `0.1 + 0.2`) must be compared with tolerance, not `===`. The naïve `Math.abs(a-b) < Number.EPSILON` works near `1`; for arbitrary magnitude, scale by `Math.max(Math.abs(a), Math.abs(b))`.

```js
// 0.1 has no exact binary representation — it is 0.10000000000000000555...
console.log(0.1 + 0.2); // 0.30000000000000004 — not 0.3
console.log(0.1 + 0.2 === 0.3); // false — the classic trap
console.log(0.1.toFixed(20)); // "0.10000000000000000555" — the stored value
console.log((0.1 + 0.2).toFixed(20)); // "0.30000000000000004441"

// EPSILON-based comparison — correct near 1
function approxEqual(a, b, eps = Number.EPSILON) {
  return Math.abs(a - b) < eps;
}
console.log(approxEqual(0.1 + 0.2, 0.3)); // true — within 1 ULP near 1? actually 0.1+0.2 error is < EPSILON
console.log(approxEqual(0.1 + 0.2, 0.3000001)); // false

// Scaled epsilon for large magnitude — EPSILON is for numbers near 1
console.log(Number.EPSILON); // 2.220446049250313e-16
console.log(1 + Number.EPSILON === 1); // false — next representable after 1 is 1+EPSILON
console.log(1000 + Number.EPSILON === 1000); // true — gap at 1000 is larger than EPSILON (gap ~ 2^-42)
function approxEqualScaled(a, b) {
  // Relative tolerance — handles large magnitude
  const diff = Math.abs(a - b);
  const largest = Math.max(Math.abs(a), Math.abs(b));
  return diff <= largest * Number.EPSILON;
}
console.log(approxEqual(1000.0000000000002, 1000)); // true — within relative epsilon
console.log(approxEqualScaled(1e12 + 100, 1e12)); // false — 100 >> gap at 1e12 (~0.00024? actually gap 2^-? — but 100 exceeds)
console.log(approxEqualScaled(1e12 + 0.0001, 1e12)); // true — within relative

// When tolerance is wrong — money: use integers (cents) or BigInt/Decimal proposal, not EPSILON rounding
const cents = Math.round(0.1 * 100) + Math.round(0.2 * 100); // 10 + 20 = 30 cents
console.log(cents / 100); // 0.3 — exact via integer cents
```

### 3) **When to reach for `BigInt` vs staying in `Number`**

**Definition** — `BigInt` (`10n`, `BigInt(10)`) is an arbitrary-precision integer type (distinct from `number` — `typeof 10n === "bigint"`). It represents integers beyond 53 bits exactly, but cannot mix with `number` in arithmetic (`10n + 1` throws `TypeError`), and `Math` does not accept `BigInt`.

```js
// Beyond 53 bits — Number collapses, BigInt does not
console.log(typeof 10n); // "bigint"
console.log(9007199254740993n === 9007199254740992n + 1n); // true — exact
console.log(9007199254740993n + 1n); // 9007199254740994n — still exact
console.log(Number.MAX_SAFE_INTEGER + 1 === Number.MAX_SAFE_INTEGER + 2); // true — Number collapsed

// Mixing throws — explicit conversion required
try { console.log(10n + 1); } catch (e) { console.log(e.name); } // TypeError — cannot mix
console.log(Number(10n) + 1); // 11 — convert BigInt → Number (may lose safety)
console.log(10n + BigInt(1)); // 11n — stay in BigInt

// Math is number-only
try { console.log(Math.sqrt(4n)); } catch (e) { console.log(e.name); } // TypeError
console.log(typeof Math.sqrt(Number(4n))); // "number" — convert first

// When to pick which — decision discipline
function addIds(a, b, as) {
  // IDs from DB are 64-bit — may exceed safe integer → keep as string or BigInt, not Number
  if (as === "bigint") return BigInt(a) + BigInt(b);
  if (as === "string") return String(BigInt(a) + BigInt(b)); // JSON-safe: keep as string
  return Number(a) + Number(b); // unsafe if > 2^53 — caller opts in knowingly
}
console.log(addIds("9007199254740993", "1", "bigint")); // 9007199254740994n
console.log(addIds("9007199254740993", "1", "string")); // "9007199254740994"
console.log(addIds("9007199254740993", "1", "number")); // 9007199254740992 — wrong — demonstrates Number collapse

// Serialization — BigInt does not JSON.stringify; keep IDs as strings on the wire
try { console.log(JSON.stringify({ id: 10n })); } catch (e) { console.log(e.name); } // TypeError
console.log(JSON.stringify({ id: String(10n) })); // {"id":"10"} — safe

// Performance: Number arithmetic is hardware-FPU fast; BigInt is software big-integer (allocation + loop) — order of magnitude slower for tight loops. Keep hot numeric compute in Number when ≤53-bit range suffices.
```

### 4) **Common confusion**

- "`Number.isInteger` means safe" — no, `9007199254740992` is integer but not safe; safe requires `|x| ≤ 2^53-1`.
- "`EPSILON` is the smallest difference between any two numbers" — no, it is the gap at `1`; gaps scale with exponent (larger numbers have larger gaps).
- "`0.1 + 0.2 === 0.3` should be true" — no, `0.1` and `0.2` cannot be represented exactly; the stored values sum to `0.30000000000000004`.
- "`BigInt` is just a bigger `Number`" — no, it is a different type (`typeof` `"bigint"`), cannot mix, no `Math`, and truncates division (`10n/3n → 3n`).
- "`MAX_VALUE` is the safe limit" — no, `MAX_VALUE` is the largest finite double (`1.79e308`), unrelated to integer safety (`MAX_SAFE_INTEGER` is `9e15`).

### 5) **Performance note**

`Number.isSafeInteger` is a few integer comparisons (fast). `approxEqual` with `Math.abs` is cheap, but scaling per `Math.max` adds a branch — hoist `largest` out of hot loops. `BigInt` addition beyond 64 bits allocates a variable-length array of limbs (GC pressure, not FPU); in a tight loop of 1e6 iterations, `BigInt` sums can be 10–50× slower than `Number` — measure, and stay in `Number`/`TypedArray` when domain fits 53 bits. `JSON.stringify` on large `Number` IDs silently collapses before the string is emitted — no throw, so the bug is silent (see [7.1](<../7. Common pitfalls to production bugs/7.1. Real production bugs caused by number and date mistakes.md>)).

### 6) **Mentor note**

Have juniors predict `9007199254740992 === 9007199254740993` and `(0.1+0.2).toFixed(20)` before running — the two reveals anchor the 53-bit and binary-fraction stories. In review, flag any `===` on computed floats (require epsilon function), any `JSON.stringify` of a `number` ID that may exceed 53 bits (require string/`BigInt` + comment), and any `BigInt` + `number` mix (require explicit conversion). Require `Number.isSafeInteger` gate at DB/API boundaries when IDs are 64-bit.
