## 1.1. Number primitives IEEE-754 NaN Infinity and negative zero

### 1) **IEEE-754 double — 64-bit layout and the three special values**

**Definition** — `typeof 42 === "number"` means an IEEE-754 binary64 (double): 1 sign bit, 11 exponent bits, 52 mantissa (fraction) bits. Every JavaScript `number` is this one format (there is no separate `int` or `float` — integers are doubles that happen to be integral). The encoding yields exactly three families of special values: `NaN` (not-a-number, exponent all 1s + non-zero mantissa), `+Infinity`/`-Infinity` (exponent all 1s + zero mantissa, sign distinguishes), and the finite range `±5e-324` to `±1.7976931348623157e+308`.

**What problem it solves / history** — 1995 JavaScript borrowed Java's `double` because CPUs already had hardware double support and one numeric type kept the language tiny. The trade-off: integer arithmetic beyond 53 bits loses precision (see [1.2](<./1.2. Safe integers BigInt boundary epsilon and precision.md>)), and decimal fractions like `0.1` have no exact binary representation (see [2.2](<../2. Parsing and formatting/2.2. Formatting numbers toString toFixed toPrecision toExponential and Intl.NumberFormat.md>)).

**Modern guidance** — treat `number` as "double that may be special". Every division, parse, or `Math` call can yield `NaN` or `±Infinity`; handle them explicitly at boundaries (API input, `JSON` round-trip, `parseInt` failure) rather than letting `NaN` poison later arithmetic.

```js
// Layout intuition — integers are doubles
console.log(typeof 42, typeof 3.14); // "number" "number" — same type
console.log(Number.MAX_VALUE); // 1.7976931348623157e+308 — largest finite
console.log(Number.MIN_VALUE); // 5e-324 — smallest positive subnormal (non-zero)
console.log(Number.MIN_VALUE > 0); // true — but Number.MIN_SAFE_INTEGER < 0

// Special values arise from overflow and invalid ops
console.log(1 / 0); // Infinity
console.log(-1 / 0); // -Infinity
console.log(0 / 0); // NaN — the only value not equal to itself
console.log(Math.sqrt(-1)); // NaN
console.log(Number.isNaN(NaN)); // true — coercion-free check
console.log(NaN === NaN); // false — never use ===
console.log(1e309); // Infinity — literal overflow (1e308 is finite, 1e309 is Infinity)

// NaN is sticky — any arithmetic with NaN stays NaN
let x = Math.sqrt(-1);
console.log(x + 10); // NaN — poison spreads
console.log(x > 0, x < 0, x === x); // false false false — NaN compares false to everything
```

### 2) **Negative zero — where `0` and `-0` diverge**

**Definition** — IEEE-754 has two zeros distinguished by the sign bit. JavaScript preserves both: `0` and `-0`. They compare `===` true, but diverge under division and `Object.is`.

```js
// Creation — -0 arises from signed underflow or literal
console.log(0 === -0); // true — === hides the sign
console.log(Object.is(0, -0)); // false — Object.is distinguishes
console.log(Object.is(-0, -0)); // true
console.log(1 / 0); // Infinity
console.log(1 / -0); // -Infinity — the observable difference
console.log(1 / -0 === -Infinity); // true

// Other sign-sensitive sites
console.log(Math.atan2(0, -0)); // ~3.14 (π) vs Math.atan2(0, 0) → 0 — quadrant matters
console.log((-0).toString()); // "0" — stringification loses sign
console.log(String(-0)); // "0"
console.log(JSON.stringify(-0)); // "0" — JSON erases -0
console.log(JSON.stringify([0, -0])); // "[0,0]" — both become "0"

// Map/Set use SameValueZero: +0 and -0 are the same key
const m = new Map();
m.set(0, "pos");
m.set(-0, "neg");
console.log(m.size); // 1 — SameValueZero treats 0/-0 as same (see Collections 1.1)
console.log(m.get(0), m.get(-0)); // "neg" "neg" — last write wins
console.log(Object.is(m.get(0), "neg")); // true — value is "neg", key collapse is the point

// Detecting -0 intentionally (rare — needed for 1/x sign or serialization)
function isNegativeZero(v) { return Object.is(v, -0); }
console.log(isNegativeZero(-0), isNegativeZero(0), isNegativeZero(1)); // true false false
```

### 3) **Detection — `Number.isNaN` vs global `isNaN`, `Number.isFinite` vs global `isFinite`, `Object.is` for `-0`**

**Definition** — `Number.isNaN`/`Number.isFinite` are coercion-free: they return `true` only if the value is already the right type and value. The legacy globals `isNaN`/`isFinite` coerce via `ToNumber` first, so `isNaN(" ")` → `false` (because `Number(" ")` → `0`) while `Number.isNaN(" ")` → `false` for a different reason — both false here, but `isNaN("foo")` → `true` (coerces to `NaN`) vs `Number.isNaN("foo")` → `false`.

```js
// isNaN vs Number.isNaN
console.log(isNaN("foo")); // true — legacy: Number("foo") → NaN → true (misleading)
console.log(Number.isNaN("foo")); // false — correct: "foo" is not NaN, it's a string
console.log(Number.isNaN(NaN)); // true
console.log(Number.isNaN(Number("foo"))); // true — coerce explicitly first if you want coercion

// isFinite vs Number.isFinite
console.log(isFinite("10")); // true — legacy: Number("10") → 10 → finite true
console.log(Number.isFinite("10")); // false — "10" is a string, not a finite number
console.log(Number.isFinite(10)); // true
console.log(Number.isFinite(Infinity)); // false
console.log(Number.isFinite(NaN)); // false

// Object.is for -0 and NaN (SameValue, not SameValueZero)
console.log(Object.is(NaN, NaN)); // true — unlike ===, Object.is regards NaN equal to NaN
console.log(Object.is(0, -0)); // false — distinguishes
console.log(NaN === NaN); // false — the trap Object.is fixes

// Practical guard — boundary check at API edge
function toFiniteNumber(input) {
  const n = Number(input); // explicit coercion (see 2.1 for strict vs lenient)
  if (!Number.isFinite(n)) throw new TypeError(`expected finite number, got ${String(input)} → ${String(n)}`);
  if (Object.is(n, -0)) return 0; // normalize -0 if downstream JSON/stringify matters
  return n;
}
console.log(toFiniteNumber("42")); // 42
try { toFiniteNumber("foo"); } catch (e) { console.log(e.name); } // TypeError
try { toFiniteNumber(Infinity); } catch (e) { console.log(e.name); } // TypeError
console.log(toFiniteNumber("-0")); // 0 — normalized

// Division guard — preserve sign if your domain needs it (e.g., 1/x)
function reciprocalSign(n) {
  const r = 1 / n;
  if (!Number.isFinite(r)) return r; // Infinity / -Infinity / NaN pass through
  return r;
}
console.log(reciprocalSign(0)); // Infinity
console.log(reciprocalSign(-0)); // -Infinity — sign preserved
```

### 4) **Common confusion**

- "`NaN === NaN` should be true" — no, IEEE-754 mandates `NaN !== NaN`; use `Number.isNaN(x)` (or `x !== x` as the polyfill, but prefer the named check).
- "`isNaN` is the NaN test" — no, global `isNaN` coerces and gives `true` for `"foo"`; use `Number.isNaN`.
- "`0` and `-0` are identical everywhere" — they are `===` equal and `Map`/`Set` collapse them (SameValueZero), but `1/0` vs `1/-0`, `Object.is`, and `Math.atan2` distinguish; `JSON.stringify` erases the sign.
- "`typeof NaN === 'number'` is a bug" — no, `NaN` is a number value per IEEE-754; the type is `number` even though it means "not a number".
- "`Infinity` throws" — no, it is a normal value that flows through arithmetic: `Infinity + 1 → Infinity`, `Infinity - Infinity → NaN`, `1/Infinity → 0`.

### 5) **Performance note**

`Number.isNaN`/`Number.isFinite`/`Object.is` are engine intrinsics — single comparison, no allocation. Avoid `x !== x` micro-optimizations: JITs already intrinsify `Number.isNaN`. `1 / x` to detect `-0` is slower than `Object.is(x, -0)` and mixes concern (division vs identity check). `JSON.stringify` erasing `-0` is spec-mandated stringification, not a JIT quirk — normalize before serializing if sign matters.

### 6) **Mentor note**

Have juniors predict `NaN === NaN`, `isNaN("foo")` vs `Number.isNaN("foo")`, and `Object.is(0,-0)` before running — the three predictions cement the coercion-free discipline. In review, flag any `x === NaN`, `x == NaN`, or global `isNaN`/`isFinite` on external input; require `Number.isNaN`/`Number.isFinite` after explicit `Number()` coercion and `Object.is` for intentional `-0` checks. Require a comment when `-0` normalization is intentional (e.g., `// normalize -0 → 0 for JSON`).
