## 2.2. Formatting numbers toString toFixed toPrecision toExponential and Intl.NumberFormat

### 1) **`toString(radix)` and `toFixed`/`toPrecision`/`toExponential` contracts**

**Definition** — `num.toString(radix)` (2–36) returns base-`radix` digits (`10 → "10"`, `16 → "ff"`). `toFixed(n)` fixes *fraction* digits (0–100, rounds half-away, returns string with exactly `n` decimals). `toPrecision(n)` fixes *significant* digits (1–100). `toExponential(n)` returns `m.e±p` exponential notation. All do *decimal* rounding on the binary double, so ties and `0.1` surprises appear.

```js
// toString radix
console.log((255).toString(16)); // "ff"
console.log((255).toString(2)); // "11111111"
console.log((35).toString(36)); // "z" — radix 36 max digit
console.log((-10).toString(2)); // "-1010" — sign preserved
console.log((10).toString()); // "10" — default radix 10
try { console.log((10).toString(1)); } catch (e) { console.log(e.name); } // RangeError — radix 2–36
try { console.log((10).toString(37)); } catch (e) { console.log(e.name); } // RangeError
console.log((NaN).toString()); // "NaN"
console.log((Infinity).toString()); // "Infinity"
console.log((-0).toString()); // "0" — again -0 stringifies to "0" (see 1.1)

// toFixed — fraction digits, rounding
console.log((0.1 + 0.2).toFixed(2)); // "0.30" — formats the stored 0.3000...04 rounded to 2 decimals
console.log((1.005).toFixed(2)); // "1.00" — surprise: 1.005 is stored as 1.004999... so rounds down (binary tie)
console.log((1.015).toFixed(2)); // "1.01" or "1.02" depending on binary — see below
console.log((10).toFixed(2)); // "10.00" — pads zeros
console.log((10.1).toFixed(0)); // "10"
try { console.log((10).toFixed(101)); } catch (e) { console.log(e.name); } // RangeError — 0–100
console.log((1.5).toFixed(0), (2.5).toFixed(0)); // "2" "3" — ties round away from zero? Actually 1.5→2, 2.5→3 (half-up in decimal rounding)

// toPrecision — significant digits
console.log((123.456).toPrecision(4)); // "123.5"
console.log((0.00123).toPrecision(2)); // "0.0012"
console.log((1234).toPrecision(2)); // "1.2e+3" — switches to exponential when needed
console.log((1.005).toPrecision(3)); // "1.00" — same binary representation issue
try { console.log((10).toPrecision(0)); } catch (e) { console.log(e.name); } // RangeError — 1–100

// toExponential — exponential notation
console.log((123.456).toExponential(2)); // "1.23e+2"
console.log((0.00123).toExponential(2)); // "1.23e-3"
console.log((123.456).toExponential()); // "1.23456e+2" — without arg, as many digits as needed
console.log((NaN).toExponential(2)); // "NaN"
console.log((Infinity).toExponential(2)); // "Infinity"

// 0.1+0.2 formatting surprise — stored value vs displayed rounding
console.log(0.1 + 0.2); // 0.30000000000000004 — raw
console.log((0.1 + 0.2).toFixed(1)); // "0.3" — rounded for display
console.log((0.1 + 0.2).toFixed(20)); // "0.30000000000000004441" — the true stored decimal
```

### 2) **`Intl.NumberFormat` — locale-aware grouping, currency, rounding modes**

**Definition** — `Intl.NumberFormat(locale, options)` formats per CLDR locale data without manual grouping logic. It handles thousands separators, decimal commas, currency symbols, and rounding modes (`halfExpand`, `ceil`, `floor`, `trunc`) that `toFixed` cannot express. Locale `undefined` means host default; options include `style`, `currency`, `minimumFractionDigits`/`maximumFractionDigits`, `useGrouping`, `notation`.

```js
// Locale grouping — same number, different separators
console.log(new Intl.NumberFormat("en-US").format(1234.5)); // "1,234.5" — comma grouping, dot decimal
console.log(new Intl.NumberFormat("de-DE").format(1234.5)); // "1.234,5" — dot grouping, comma decimal
console.log(new Intl.NumberFormat("fr-FR").format(1234567.89)); // "1 234 567,89" — narrow no-break space grouping
console.log(new Intl.NumberFormat("en-US", { useGrouping: false }).format(1234567)); // "1234567" — no grouping

// Fraction digits and rounding modes (ES2023+ roundingMode)
console.log(new Intl.NumberFormat("en-US", { minimumFractionDigits: 2, maximumFractionDigits: 2 }).format(1)); // "1.00"
console.log(new Intl.NumberFormat("en-US", { maximumFractionDigits: 0 }).format(1.5)); // "2" — default halfExpand
console.log(new Intl.NumberFormat("en-US", { maximumFractionDigits: 0, roundingMode: "ceil" }).format(1.1)); // "2" — ceil
console.log(new Intl.NumberFormat("en-US", { maximumFractionDigits: 0, roundingMode: "trunc" }).format(1.9)); // "1" — trunc

// Currency — style: currency requires currency code
console.log(new Intl.NumberFormat("en-US", { style: "currency", currency: "USD" }).format(1234.5)); // "$1,234.50"
console.log(new Intl.NumberFormat("de-DE", { style: "currency", currency: "EUR" }).format(1234.5)); // "1.234,50 €"
console.log(new Intl.NumberFormat("ja-JP", { style: "currency", currency: "JPY" }).format(1234)); // "￥1,234" — no fraction for JPY

// Notation — compact and scientific
console.log(new Intl.NumberFormat("en-US", { notation: "compact" }).format(1234567)); // "1.2M"
console.log(new Intl.NumberFormat("en-US", { notation: "scientific" }).format(1234567)); // "1.235E6"
console.log(new Intl.NumberFormat("en-US", { notation: "engineering" }).format(1234567)); // "1.235E6" — exponent multiple of 3

// toFixed vs Intl — Intl respects locale, toFixed is always en-like dot decimal
console.log((1234.5).toFixed(2)); // "1234.50" — no grouping, dot decimal, en-style only
console.log(new Intl.NumberFormat("de-DE", { minimumFractionDigits: 2 }).format(1234.5)); // "1.234,50"

// Availability — Intl is host-provided; Node ships CLDR subset (full via full-icu). Check support:
console.log(typeof Intl.NumberFormat); // "function"
console.log(Intl.NumberFormat.supportedLocalesOf("en-US")); // ["en-US"] — supported
```

### 3) **Round-trip and loss — `parseFloat(num.toString())` and `JSON` precision loss beyond 53 bits**

**Definition** — `num.toString()` → `parseFloat` round-trips exactly for finite numbers within 53-bit integer safety, because `toString` emits enough digits to uniquely identify the double. Beyond 53 bits, `toString` already reflects the collapsed value, and `JSON.stringify`/`parse` preserve that collapsed value — not the original integer.

```js
// Round-trip within safe range — exact
const n = 123.456;
console.log(parseFloat(n.toString()) === n); // true — toString emits minimal round-trip digits
console.log(Number(n.toString()) === n); // true

// Large integer round-trip — collapsed before stringification
const big = 9007199254740993; // already collapsed to 9007199254740992 at parse time (see 1.2)
console.log(big); // 9007199254740992 — collapsed literal
console.log(big.toString()); // "9007199254740992" — string of collapsed value
console.log(parseFloat(big.toString()) === big); // true — but both are the wrong integer
console.log(big === 9007199254740992); // true — collapse demonstrated

// JSON round-trip preserves the double, not the intended integer
const payload = { id: 9007199254740993 }; // JS already collapsed
console.log(JSON.stringify(payload)); // {"id":9007199254740992}
console.log(JSON.parse(JSON.stringify(payload)).id); // 9007199254740992 — loss persisted
console.log(JSON.stringify({ id: "9007199254740993" })); // {"id":"9007199254740993"} — string preserves

// When to keep as string/BigInt — IDs, money in minor units beyond 53 bits
const idStr = "9007199254740993";
console.log(BigInt(idStr).toString() === idStr); // true — BigInt round-trips as decimal string exactly
console.log(Number(idStr) === 9007199254740992); // true — Number does NOT round-trip

// Formatting does not fix precision — toFixed rounds the stored double, not the intended decimal
console.log((1.005).toFixed(2)); // "1.00" — not "1.01" — because stored 1.005 is 1.004999...
console.log(Number((1.005).toFixed(2))); // 1 — parsing the rounded display gives 1, not 1.005
// For decimal money, operate in integer cents or use Decimal proposal (stage 3) / integer arithmetic
const cents = 100 + 5; // $1.00 + $0.05 in cents
console.log((cents / 100).toFixed(2)); // "1.05" — exact via integers
```

### 4) **Common confusion**

- "`toFixed(2)` correctly rounds any decimal" — no, it rounds the *binary double* (`1.005` is stored below `1.005`, so `toFixed(2)` gives `"1.00"`).
- "`toString(16)` works on any radix" — only 2–36; `37` throws `RangeError`.
- "`Intl.NumberFormat` is manual string replace" — no, it uses CLDR locale data; grouping/decimal/currency differ per locale (`,` vs `.` vs ` `).
- "`parseFloat(num.toString())` always recovers original" — only within 53-bit safety; beyond, the original was already lost at literal parse time.
- "`Number` formatting is locale-aware" — no, `toFixed`/`toString` are locale-agnostic; only `Intl` is locale-aware.

### 5) **Performance note**

`toFixed`/`toPrecision` allocate a new string per call (GC). In a hot loop formatting 1e6 numbers for CSV, pre-create one `Intl.NumberFormat` instance and reuse `format` — constructing `new Intl.NumberFormat` per iteration parses locale + options (10–100× slower). `Intl` instances are stateless and can be shared across calls. `toString(radix)` for radix 10 is fast-path in V8; non-10 radixes do repeated division.

### 6) **Mentor note**

Have juniors predict `(1.005).toFixed(2)` and `new Intl.NumberFormat("de-DE").format(1234.5)` before running — the two surprises anchor binary rounding and locale grouping. In review, flag any `toFixed` on money without integer-cents context (require comment or `Intl` with `roundingMode`), any `toString(radix)` without `RangeError` guard for dynamic radix, and any `JSON.stringify` of a numeric ID > `MAX_SAFE_INTEGER` (require string/`BigInt`). Require `Intl.NumberFormat` reuse (hoist out of loop) in hot paths.
