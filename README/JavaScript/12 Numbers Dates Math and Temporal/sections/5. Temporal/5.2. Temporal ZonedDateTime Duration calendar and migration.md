## 5.2. Temporal ZonedDateTime Duration calendar and migration

### 1) **`ZonedDateTime` — instant + `timeZone` + `calendar` with DST-correct arithmetic**

**Definition** — `Temporal.ZonedDateTime` is the *only* type that ties a wall-clock to an instant and a timezone: `2026-03-08T01:30:00-05:00[America/New_York]` → instant `2026-03-08T06:30:00Z`. It is immutable, DST-aware, and distinguishes "add 1 calendar day" (`add({days:1})` → same wall time next day, 23/25h duration) from "add 24 hours" (`add({hours:24})` → exactly 24h later, possibly different wall time).

```js
if (typeof Temporal !== "undefined") {
  const zdt = Temporal.ZonedDateTime.from("2026-03-08T01:30:00-05:00[America/New_York]"); // before spring-forward
  console.log(String(zdt)); // "2026-03-08T01:30:00-05:00[America/New_York]"
  console.log(zdt.timeZoneId, zdt.calendarId); // "America/New_York" "iso8601"
  console.log(zdt.toInstant().toString()); // "2026-03-08T06:30:00Z" — the UTC instant
  console.log(zdt.withTimeZone("Asia/Tehran").toString()); // same instant, Tehran wall time

  // Calendar day vs 24h on DST spring day (Mar 8 2026 gap 02:00→03:00)
  const nextDay = zdt.add({ days: 1 }); // calendar day: same wall time next day (02:30 next day? Actually 01:30+1 day → Mar 9 01:30 EDT)
  console.log(String(nextDay)); // "2026-03-09T01:30:00-04:00[America/New_York]" — offset changed -05→-04, wall 01:30 preserved
  const plus24h = zdt.add({ hours: 24 });
  console.log(String(plus24h)); // "2026-03-09T02:30:00-04:00[America/New_York]" — 24h later → 02:30 wall (different)
  console.log(nextDay.toInstant().epochNanoseconds - zdt.toInstant().epochNanoseconds); // 23h ns — short day
  console.log(plus24h.toInstant().epochNanoseconds - zdt.toInstant().epochNanoseconds === 24n * 60n * 60n * 1_000_000_000n); // true

  // Fall gap normalization — constructing 02:30 on spring gap rolls forward
  const gap = Temporal.ZonedDateTime.from("2026-03-08T02:30:00[America/New_York]"); // 02:30 does not exist
  console.log(String(gap)); // "2026-03-08T03:30:00-04:00[America/New_York]" — disambiguation: compatible → later
  console.log(gap.hour); // 3 — not 2

  // Immutable with — returns new ZDT, original untouched
  console.log(String(zdt.with({ hour: 12 }))); // "2026-03-08T12:00:00-04:00[America/New_York]" — noon
  console.log(String(zdt)); // "2026-03-08T01:30:00-05:00[America/New_York]" — original
} else {
  console.log("Temporal not available — ZonedDateTime demo skipped (see 5.1 guard)");
  // Calendar day vs 24h divergence cannot be expressed with legacy Date without a library
  // Legacy Date only knows host TZ; arbitrary zone arithmetic needs Temporal or luxon/date-fns-tz
  const utc = new Date("2026-03-08T06:30:00.000Z");
  console.log(utc.toISOString(), new Date(utc.getTime() + 24 * 60 * 60 * 1000).toISOString()); // 24h later UTC — always 24h
  console.log("For calendar days in America/New_York, use Temporal polyfill — legacy Date cannot do DST-aware add");
}

// DST repeat — fall-back Nov 1 2026 02:00→01:00 (01:30 occurs twice)
if (typeof Temporal !== "undefined") {
  const first = Temporal.ZonedDateTime.from("2026-11-01T01:30:00-04:00[America/New_York]"); // first 01:30 EDT
  const second = Temporal.ZonedDateTime.from("2026-11-01T01:30:00-05:00[America/New_York]"); // second 01:30 EST
  console.log(String(first), String(second)); // offsets differ
  console.log(first.toInstant().epochNanoseconds !== second.toInstant().epochNanoseconds); // true — different instants, same wall
  console.log(first.add({ hours: 1 }).toString()); // moves to second 01:30? Actually +1h from first 01:30 EDT → 01:30 EST (repeat)
}
```

### 2) **`Duration` and calendar systems — ISO-8601 durations, `compare`/`round`/`total`, non-Gregorian calendars**

**Definition** — `Temporal.Duration` (`P1Y2M3DT4H5M6.7S`) is a *calendar-aware* duration with fields `years`/`months`/`weeks`/`days`/`hours`/`minutes`/`seconds`/`milliseconds`/`microseconds`/`nanoseconds`. It is not a fixed ms count because months/days vary (Feb 28 days, DST 23/25h). `Duration.compare`/`round`/`total` require a `relativeTo` (a `PlainDate` or `ZonedDateTime`) to resolve calendar length. Calendars (`iso8601` default plus `persian`, `hebrew`, `japanese`, … via `Intl` support) change year/month/day.

```js
if (typeof Temporal !== "undefined") {
  const d = Temporal.Duration.from("P1Y2M3DT4H"); // 1y 2m 3d 4h
  console.log(d.years, d.months, d.days, d.hours); // 1 2 3 4
  console.log(String(d)); // "P1Y2M3DT4H"
  console.log(d.total({ unit: "hours", relativeTo: "2026-01-01" })); // hours in 1y2m3d+4h relative to Jan 1 2026 — calendar-aware

  // Months vs days — not fixed ms
  const jan31 = Temporal.PlainDate.from("2026-01-31");
  console.log(String(jan31.add({ months: 1 }))); // "2026-02-28" — February length respected
  console.log(String(jan31.add({ days: 31 }))); // "2026-03-03" — 31 days is not "1 month"

  // Duration compare needs relativeTo for calendar fields
  console.log(Temporal.Duration.compare("P1M", "P30D", { relativeTo: "2026-02-01" })); // -1 or 1 depending on Feb length (28 vs 30)
  console.log(Temporal.Duration.compare("P1M", "P30D", { relativeTo: "2026-01-01" })); // compare Jan (31) vs 30

  // Round/total — convert duration to smallest unit relative to start
  const dur = Temporal.Duration.from({ hours: 36 });
  console.log(String(dur.round({ largestUnit: "days", relativeTo: "2026-01-01T00:00:00Z" }))); // "P1DT12H" — 36h → 1d 12h UTC

  // Calendar systems — same instant, different calendar wall dates
  const iso = Temporal.PlainDate.from({ year: 2026, month: 3, day: 8, calendar: "iso8601" });
  console.log(iso.calendarId, String(iso)); // "iso8601" "2026-03-08"
  // Persian calendar (Solar Hijri) — when Intl calendar data available
  const persian = iso.withCalendar("persian");
  console.log(persian.calendarId, String(persian)); // "persian" — year ~1404
  console.log(persian.year, persian.month, persian.day); // Persian year/month/day
} else {
  console.log("Temporal not available — Duration/calendar demo skipped");
  // Legacy fallback — durations as ms for fixed units only; calendar months need manual lookup
  function daysInMonth(y, m) { return new Date(Date.UTC(y, m, 0)).getUTCDate(); } // m 1-indexed
  console.log(daysInMonth(2026, 2)); // 28 — Feb 2026 non-leap
  console.log(daysInMonth(2024, 2)); // 29 — leap
  console.log("For calendar-aware Duration, use Temporal polyfill — legacy ms cannot encode months");
}

// Legacy ms cannot encode "1 month" — variable length
console.log(30 * 24 * 60 * 60 * 1000); // 2592000000 — 30 days, not "1 month" (28–31)
```

### 3) **Migrating from `Date` — mapping table (`new Date()`→`Instant.fromEpochMilliseconds`, `getHours`→`ZonedDateTime.hour`, `toISOString`→`toString`)**

| `Date` (mutable, ms) | `Temporal` (immutable) | Note |
|----------------------|------------------------|------|
| `new Date()` | `Temporal.Now.instant()` / `Temporal.Now.zonedDateTimeISO()` | instant vs wall+zone |
| `Date.now()` | `Temporal.Now.instant().epochMilliseconds` | ms |
| `new Date(ms)` | `Temporal.Instant.fromEpochMilliseconds(ms)` | |
| `date.getTime()` | `instant.epochMilliseconds` / `zdt.epochMilliseconds` | |
| `date.getHours()` (host) | `zdt.hour` (explicit `timeZone`) | `Date` only host |
| `date.toISOString()` | `instant.toString()` / `zdt.toInstant().toString()` | UTC |
| `new Date("2026-03-08")` | `Temporal.PlainDate.from("2026-03-08")` | wall vs instant |
| `date.setDate(d+1)` | `plainDate.add({days:1})` / `zdt.add({days:1})` | calendar-aware |
| `Intl.DateTimeFormat` | `zdt.toLocaleString(locale, options)` | `Temporal` has `toLocaleString` |

```js
// Incremental adoption — boundary converters (when Temporal available)
if (typeof Temporal !== "undefined") {
  // Date → Instant
  const inst = Temporal.Instant.fromEpochMilliseconds(Date.now());
  console.log(String(inst).endsWith("Z")); // true — UTC
  // Instant → Date (interop)
  console.log(new Date(Number(inst.epochMilliseconds)).toISOString() === inst.toString().replace(/\.(\d+)Z/, ".000Z").slice(0, 24) + "Z" || true); // ms truncation may differ

  // PlainDate wall date — keep as wall, not instant
  const wall = Temporal.PlainDate.from("2026-03-08");
  console.log(String(wall)); // "2026-03-08" — no time, no zone

  // Zoned wall → instant for storage
  const zdt = Temporal.ZonedDateTime.from("2026-03-08T12:00:00[Asia/Tehran]");
  console.log(zdt.toInstant().toString()); // UTC instant — store this
  console.log(zdt.toPlainDate().toString()); // "2026-03-08" — wall date for display
} else {
  console.log("Temporal not available — mapping table is spec; keep Date ms for storage and ISO string for wall dates until polyfill");
  // Practical migration today: keep Date for instants, ISO string for wall dates, Intl for display; replace with Temporal per file
  const wallStr = "2026-03-08"; // wall date — do not new Date it
  const instantMs = Date.now(); // instant — store ms
  console.log(wallStr, new Date(instantMs).toISOString());
}
```

### 4) **Common confusion**

- "`ZonedDateTime` is UTC with an offset" — no, it is *wall time* + `timeZone` + `calendar` → instant; offset is derived, not stored (DST changes offset).
- "`Duration` `P1M` is `30` days" — no, months are calendar months (28–31 days); without `relativeTo`, `Duration` cannot be totalled to days/hours.
- "`add({days:1})` is always `+24h`" — no, on DST days it is 23h or 25h real time; `add({hours:24})` is always 24h.
- "`Temporal` is a drop-in `Date` replacement" — no, `PlainDate` vs `Instant` vs `ZonedDateTime` are distinct; pick by whether you mean instant, wall date, or zoned wall.
- "`Temporal` polyfill is slower so avoid it" — polyfill is slower than native, but calendar-correct logic with `Date` is *wrong*; correctness outweighs micro-cost (see [7.1](<../7. Common pitfalls to production bugs/7.1. Real production bugs caused by number and date mistakes.md>)).

### 5) **Performance note**

`ZonedDateTime` arithmetic consults IANA timezone data (CLDR) — `add({days:1})` does a zone transition lookup (fast in native, ~microseconds via ICU). Polyfill does JS lookup (10–100× slower). `Duration.total` with `relativeTo` does calendar math (month lengths + DST). For hot loops of 10k `ZonedDateTime.add`, native is ~10k ops/ms, polyfill ~1k/ms — still fine for non-hot business logic; for hot timestamp sorting, stay with `Instant.epochNanoseconds` (`BigInt`) compare.

### 6) **Mentor note**

Have juniors predict `ZonedDateTime` `add({days:1})` vs `add({hours:24})` on a DST spring day before running — the 1h wall difference cements calendar-vs-duration. In review, flag any `Duration` without `relativeTo` when months/days are involved (require `relativeTo` or comment explaining fixed-unit), any `ZonedDateTime` constructed without `timeZone` (require explicit zone), and any `Date` arithmetic targeting non-host zone (require `Temporal` or `date-fns-tz` until it lands).
