## 4.1. Legacy Date creation mutability and parsing pitfalls

### 1) **`new Date` is mutable and month-indexed — the two oldest footguns**

**Definition** — `Date` stores a single number: milliseconds since Unix epoch UTC (`1970-01-01T00:00:00.000Z`). `new Date()` captures `Date.now()` (current ms), `new Date(ms)` wraps that ms, `new Date(y,m,d,h,min,s,ms)` interprets args in *local* time with month `0–11`. Every `set*` method (`setMonth`, `setDate`, `setHours`, …) mutates the *same* instance and returns the new timestamp — `Date` is not immutable.

```js
// Creation — ms since epoch UTC, but local getters confuse
const now = new Date();
console.log(typeof now, now instanceof Date); // "object" true
console.log(typeof Date.now()); // "number" — ms
console.log(now.getTime() === Date.now() || Math.abs(now.getTime() - Date.now()) < 10); // true — close

// Month is 0-indexed — January is 0, December is 11
const jan = new Date(2026, 0, 15); // Jan 15, 2026 local midnight
console.log(jan.getMonth(), jan.getDate()); // 0 15
console.log(jan.toDateString()); // "Thu Jan 15 2026" (local)
const dec = new Date(2026, 11, 25);
console.log(dec.getMonth(), dec.getDate()); // 11 25 — December
console.log(new Date(2026, 12, 1).getMonth()); // 0 — month 12 overflows to Jan 2027

// Mutation — set* mutates same object (not a new Date)
const d = new Date(2026, 0, 15, 12, 0, 0); // Jan 15 noon local
const t = d.setMonth(1); // mutate to Feb
console.log(t === d.getTime()); // true — setMonth returns ms, not a new Date
console.log(d.getMonth()); // 1 — original mutated
console.log(d === now); // false — different instances, but aliasing hurts
const alias = d;
alias.setDate(20);
console.log(d.getDate()); // 20 — alias mutated original

// Safe clone before mutation — new Date(ms) or new Date(date)
const orig = new Date(2026, 0, 15);
const clone = new Date(orig); // clone via ms copy
clone.setDate(20);
console.log(orig.getDate(), clone.getDate()); // 15 20 — orig untouched
console.log(new Date(orig.getTime()).getDate()); // 15 — via ms

// getTime is the only safe arithmetic base (UTC ms)
console.log(orig.getTime()); // ms — use this for diffs, not getDate
```

### 2) **`Date.parse` / `new Date(string)` — only ISO-8601 `YYYY-MM-DDTHH:mm:ss.sssZ` is reliably portable**

**Definition** — `Date.parse(string)` (and `new Date(string)`) parses per ECMA-262 `Date.parse` which mandates correct parsing only for ISO-8601 extended format (`YYYY-MM-DDTHH:mm:ss.sssZ` with `T`, timezone `Z` or `±HH:MM`). Other forms (`MM/DD/YYYY`, `DD-MM-YYYY`, `2026-01-02` without `T`) are *implementation-dependent* — V8 may parse `"01/02/2026"` as Jan 2 (US) while another engine parses as Feb 1.

```js
// Reliable — ISO-8601 with T and Z
console.log(new Date("2026-01-15T12:00:00.000Z").toISOString()); // "2026-01-15T12:00:00.000Z" — round-trips
console.log(Date.parse("2026-01-15T12:00:00.000Z")); // ms — same
console.log(new Date("2026-01-15T12:00:00Z").toISOString()); // without millis — still ISO

// Unreliable — date-only without time (UTC vs local midnight ambiguity)
console.log(new Date("2026-01-15").toISOString()); // "2026-01-15T00:00:00.000Z" — ES5+ says date-only is UTC midnight (but verify)
console.log(new Date(2026, 0, 15).toISOString()); // local midnight → UTC offset — different instant for non-UTC hosts
// On a +01:00 host, new Date(2026,0,15) → 2026-01-14T23:00:00.000Z — not the same instant as "2026-01-15" UTC midnight

// Implementation-dependent — slash and dash non-ISO
console.log(new Date("01/02/2026").toString()); // who knows: Jan 2 or Feb 1 — engine-dependent (V8: Jan 2 in en-US)
console.log(new Date("2026/01/02").toString()); // also non-standard
console.log(isNaN(Date.parse("not a date"))); // true — NaN on failure
console.log(isNaN(new Date("not a date").getTime())); // true — Invalid Date

// Robust parsing — manual split + Date.UTC for UTC, or new Date(y,m,d) for local, never new Date(string) for non-ISO
function parseIsoDateOnly(s) {
  // "YYYY-MM-DD" → UTC midnight ms, no local ambiguity
  const [y, m, d] = s.split("-").map(Number);
  if (![y, m, d].every(Number.isFinite)) return NaN;
  return Date.UTC(y, m - 1, d); // month 0-indexed, UTC
}
console.log(new Date(parseIsoDateOnly("2026-01-15")).toISOString()); // "2026-01-15T00:00:00.000Z" — explicit UTC
console.log(parseIsoDateOnly("01/02/2026")); // NaN — correctly rejects non-ISO

// Invalid Date object — still an object, but getTime is NaN
const bad = new Date("not a date");
console.log(String(bad)); // "Invalid Date"
console.log(isNaN(bad.getTime())); // true
console.log(bad instanceof Date); // true — still a Date, just invalid
console.log(typeof bad.getTime()); // "number" — NaN
```

### 3) **`getTime` is milliseconds since epoch UTC — the only safe arithmetic base for legacy `Date`**

**Definition** — `date.getTime()` returns the UTC millisecond timestamp (the internal slot). All `get*` vs `getUTC*` accessor pairs read that same ms but convert via host timezone: `getHours()` → local hour, `getUTCHours()` → UTC hour. Arithmetic via `setDate(getDate()+1)` can break on DST (see [4.2](<./4.2. Date timezones UTC vs local DST and arithmetic traps.md>)); `getTime()` + `24*60*60*1000` is *timestamp* math (always 24h), while "next calendar day" needs calendar arithmetic (Temporal).

```js
// getTime is UTC — independent of host timezone
const utc = new Date(Date.UTC(2026, 0, 15, 12, 0, 0)); // Jan 15 12:00 UTC
console.log(utc.toISOString()); // "2026-01-15T12:00:00.000Z"
console.log(utc.getUTCHours(), utc.getHours()); // 12 and local hour (depends on host TZ — e.g., 13 in +01:00)
console.log(utc.getTime()); // ms — use for storage/compare/diff

// Diff via getTime — correct
const a = new Date("2026-01-15T12:00:00.000Z");
const b = new Date("2026-01-16T12:00:00.000Z");
console.log(b.getTime() - a.getTime()); // 86400000 — 24h ms
console.log((b - a) === 86400000); // true — subtraction coerces via valueOf → getTime

// Midnight local vs UTC — store UTC, display via Intl
const localMidnight = new Date(2026, 0, 15); // Jan 15 00:00 local
console.log(localMidnight.toISOString()); // e.g., "2026-01-14T23:00:00.000Z" on +01 — not midnight UTC
console.log(Date.UTC(2026, 0, 15)); // 1768435200000 — UTC midnight ms
console.log(new Date(Date.UTC(2026, 0, 15)).toISOString()); // "2026-01-15T00:00:00.000Z" — UTC midnight

// Mutation vs timestamp arithmetic
const d2 = new Date("2026-01-15T12:00:00.000Z");
d2.setUTCDate(d2.getUTCDate() + 1); // mutate via UTC accessors — safe for UTC calendar
console.log(d2.toISOString()); // "2026-01-16T12:00:00.000Z" — UTC next day
// Timestamp add is always 24h wall-time, not calendar day (DST gap makes calendar day 23h or 25h)
const plus24h = new Date(a.getTime() + 24 * 60 * 60 * 1000);
console.log(plus24h.toISOString()); // "2026-01-16T12:00:00.000Z" — same as UTC next day here (no DST that date)
```

### 4) **Common confusion**

- "`new Date('2026-01-15')` is local midnight" — no, ISO date-only is UTC midnight per spec; `new Date(2026,0,15)` is local midnight.
- "`getMonth()` is 1–12" — no, `0–11`; January is `0`.
- "`setMonth` returns a new `Date`" — no, it mutates in place and returns the timestamp `number`.
- "`Date` is immutable like `Temporal`" — no, `Date` is mutable; `Temporal` instances are immutable (see [5.1](<../5. Temporal/5.1. Temporal overview Instant PlainDate PlainTime PlainDateTime.md>)).
- "`Date.parse` handles any date string" — no, only ISO-8601 `YYYY-MM-DDTHH:mm:ss.sssZ` is portable; others are implementation-dependent.

### 5) **Performance note**

`new Date()` allocates a heap object (GC). In hot loops of 1e6 iterations creating dates for sorting, allocation dominates — reuse timestamps (`number` ms) and convert to `Date` only for display. `Date.now()` is faster than `new Date().getTime()` (no object). `toISOString` formats via UTC and allocates a string — batch formatting via `Intl.DateTimeFormat` with reused formatter is faster for bulk locale display.

### 6) **Mentor note**

Have juniors predict `new Date(2026,0,15).getMonth()` and `new Date("2026-01-15").toISOString()` vs `new Date(2026,0,15).toISOString()` on a non-UTC host before running — the two reveal month-indexing and UTC-vs-local. In review, flag any `new Date(string)` where the string is not ISO-8601 with `T` and `Z` (require manual `split`+`Date.UTC` or `Temporal`), any `set*` without cloning intent (require `new Date(orig)` clone comment), and any `getMonth()+1` missing +1.
