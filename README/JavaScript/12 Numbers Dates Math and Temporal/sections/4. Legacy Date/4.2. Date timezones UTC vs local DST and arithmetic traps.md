## 4.2. Date timezones UTC vs local DST and arithmetic traps

### 1) **Internal UTC vs local accessors — `getHours` vs `getUTCHours` and the host timezone trap**

**Definition** — a `Date` stores UTC milliseconds; every accessor pair converts that instant to either UTC (`getUTCHours`, `getUTCDate`, `toISOString`) or the *host* timezone (`getHours`, `getDate`, `toString`). The host timezone is the OS/Node `TZ` — server UTC vs user local vs `TZ=America/New_York` can differ, and `toString` reflects the host while `toISOString` is always UTC.

```js
// Same instant, two views
const utc = new Date(Date.UTC(2026, 0, 15, 12, 0, 0)); // Jan 15 12:00 UTC
console.log(utc.toISOString()); // "2026-01-15T12:00:00.000Z" — always UTC
console.log(utc.toString()); // e.g. "Thu Jan 15 2026 15:30:00 GMT+0330 (Iran Standard Time)" — host local
console.log(utc.getUTCHours(), utc.getHours()); // 12 and 15 — UTC vs local (+03:30)
console.log(utc.getTimezoneOffset()); // e.g., -210 — minutes to add to local to get UTC (negative = local ahead of UTC)
// getTimezoneOffset flips sign vs ISO offset: +03:30 → -210

// Creating "noon local" vs "noon UTC" are different instants
const noonLocal = new Date(2026, 0, 15, 12, 0, 0); // Jan 15 noon local
const noonUTC = new Date(Date.UTC(2026, 0, 15, 12, 0, 0)); // Jan 15 noon UTC
console.log(noonLocal.toISOString()); // e.g., "2026-01-15T08:30:00.000Z" — 12:00 +03:30 → 08:30Z
console.log(noonUTC.toISOString()); // "2026-01-15T12:00:00.000Z"
console.log(noonLocal.getTime() === noonUTC.getTime()); // false — different instants (3.5h apart)

// Display — Intl respects requested timeZone, Date accessors respect host only
console.log(new Intl.DateTimeFormat("en-US", { timeZone: "UTC", hour: "2-digit", minute: "2-digit", timeZoneName: "short" }).format(utc)); // "12:00 PM UTC"
console.log(new Intl.DateTimeFormat("en-US", { timeZone: "America/New_York", hour: "2-digit", minute: "2-digit", timeZoneName: "short" }).format(utc)); // "07:00 AM EST" (Jan, EST)
console.log(new Intl.DateTimeFormat("en-US", { timeZone: "Asia/Tehran", hour: "2-digit", minute: "2-digit", timeZoneName: "short" }).format(utc)); // host zone

// Storage rule — persist UTC ms or ISO string; never rely on host local for logic
const store = utc.toISOString(); // "2026-01-15T12:00:00.000Z" — portable
console.log(new Date(store).getTime() === utc.getTime()); // true — round-trips via UTC
```

### 2) **DST gaps and repeats — why `setHours`/`setDate` break on transition days**

**Definition** — DST transitions cause a *gap* (spring-forward, clocks jump 02:00→03:00 — 02:30 never exists) and a *repeat* (fall-back, 02:00→01:00 — 01:30 occurs twice). Legacy `Date` `setHours`/`setDate` do *local wall-time* arithmetic and then normalize the overflow, so adding "1 day" via `setDate(getDate()+1)` can skip or repeat a local day, and `getTimezoneOffset` flips on that day.

```js
// Show host current offset (Iran abolished DST 2022 — so this host has no DST; we demonstrate conceptually via America/New_York)
console.log("host offset (minutes):", new Date().getTimezoneOffset());
// To observe DST, set TZ=America/New_York when running: node --TZ or env TZ

// Conceptual DST timeline — America/New_York 2026 spring-forward Mar 8 02:00→03:00
// 2026-03-08T01:59:59 EST → 03:00 EDT — 02:xx does not exist; fall-back Nov 1 02:00→01:00 — 01:xx twice

// Why setDate(+1) breaks — local wall-time normalization
// On DST spring day, adding 24h via timestamp vs calendar "next day" diverge:
// Timestamp +24h = 24h wall-time later (may be 23h or 25h calendar)
// Calendar +1 day = same wall time next calendar day (DST-aware)
// Legacy Date has no calendar-aware add; Temporal does (see 5.2)

// Demonstrate with known UTC instants (deterministic, no host DST needed)
const beforeSpringUTC = new Date("2026-03-08T06:30:00.000Z"); // 01:30 EST in NY (UTC-5)
const plus24h = new Date(beforeSpringUTC.getTime() + 24 * 60 * 60 * 1000);
console.log(beforeSpringUTC.toISOString(), plus24h.toISOString()); // 24h later UTC — always 24h
// In NY, beforeSpringUTC wall time 01:30 EST, plus24h wall time 02:30 EDT? Actually 06:30Z +24h → 06:30Z next day → 02:30 EDT (DST) — not 01:30

// The legacy trap — mutating via local setters on a DST gap time
// Constructing 02:30 on spring gap in NY normalizes to 03:30 (gap → forward)
if (process.env.TZ === "America/New_York") {
  const gap = new Date(2026, 2, 8, 2, 30, 0); // Mar 8 02:30 local — does not exist
  console.log(gap.toString()); // normalized to 03:30 EDT
  console.log(gap.getHours()); // 3 — not 2
}
// On this host (Asia/Tehran, no DST 2026), gap normalization does not trigger — deterministic for this run

// getTimezoneOffset flips on transition (when DST exists)
const janNY = new Date(Date.UTC(2026, 0, 15, 12, 0, 0));
const julNY = new Date(Date.UTC(2026, 6, 15, 12, 0, 0));
// Format with NY zone to see DST offset change via Intl (host offset is Tehran, so use Intl)
console.log(new Intl.DateTimeFormat("en-US", { timeZone: "America/New_York", timeZoneName: "short", hour: "2-digit" }).format(janNY)); // EST
console.log(new Intl.DateTimeFormat("en-US", { timeZone: "America/New_York", timeZoneName: "short", hour: "2-digit" }).format(julNY)); // EDT

// Safe pattern for "next calendar day at noon" with legacy Date — anchor at noon UTC to avoid gap
function nextCalendarDayNoonUTC(date) {
  const d = new Date(date); // clone
  d.setUTCDate(d.getUTCDate() + 1);
  d.setUTCHours(12, 0, 0, 0); // noon UTC — never in DST gap (UTC has no DST)
  return d;
}
console.log(nextCalendarDayNoonUTC(new Date("2026-03-07T12:00:00.000Z")).toISOString()); // "2026-03-08T12:00:00.000Z"
```

### 3) **Duration math with `Date` — don't add `24*60*60*1000` for "next day"**

**Definition** — "24 hours later" (`getTime()+86400000`) is a *duration* (exact 24h). "Same time tomorrow" is a *calendar day* (may be 23h or 25h across DST). Billing cycles, cron, and "daily at 09:00" need calendar days, not durations. Legacy `Date` cannot do calendar math correctly in the presence of DST; `Temporal` can (see [5.2](<../5. Temporal/5.2. Temporal ZonedDateTime Duration calendar and migration.md>)).

```js
// 24h duration vs calendar day — the divergence
const startUTC = new Date("2026-03-08T07:00:00.000Z"); // 02:00 EST NY → after gap 03:00 EDT
const plus24hDuration = new Date(startUTC.getTime() + 24 * 60 * 60 * 1000);
console.log(plus24hDuration.toISOString()); // "2026-03-09T07:00:00.000Z" — 24h later UTC

// What "same wall time tomorrow" means in NY: Mar 8 02:00 does not exist, so calendar "next day" is Mar 9 02:00 EST? Actually Mar 8 gap day
// Legacy Date cannot express this correctly without timeZone awareness — it only knows host TZ
// The robust bridge: use Intl to display in target zone, but Temporal to add calendar days

// Legacy workaround — for host TZ only, setDate with noon anchoring reduces gap risk but still not DST-correct for arbitrary zones
function addCalendarDaysLegacy(date, days, zone = "UTC") {
  if (zone === "UTC") {
    const d = new Date(date);
    d.setUTCDate(d.getUTCDate() + days);
    return d;
  }
  // For non-UTC calendar days, legacy Date is insufficient — use Temporal or a library
  throw new Error("calendar days for non-UTC zone require Temporal — see 5.2");
}
console.log(addCalendarDaysLegacy(new Date("2026-03-08T12:00:00.000Z"), 1, "UTC").toISOString()); // "2026-03-09T12:00:00.000Z"
try { addCalendarDaysLegacy(new Date(), 1, "America/New_York"); } catch (e) { console.log(e.name, e.message.slice(0, 40)); } // Error calendar

// Duration that is calendar-aware vs exact hours
console.log(new Date("2026-01-15T00:00:00.000Z").getTime() + 30 * 24 * 60 * 60 * 1000); // 30×24h — not "1 month"
// Months have variable length (28–31 days); legacy Date has no Duration type — manual month addition via setUTCMonth drifts
const jan31 = new Date(Date.UTC(2026, 0, 31));
jan31.setUTCMonth(1); // Feb 31 → overflows to Mar 3 (2026 non-leap)
console.log(jan31.toISOString()); // "2026-03-03T00:00:00.000Z" — overflow normalization, not "last day of Feb"
```

### 4) **Common confusion**

- "`Date` stores local time" — no, it stores UTC ms; local getters convert via host timezone.
- "`getTimezoneOffset()` is the ISO offset" — it is *negated* minutes: `+03:30` → `-210`; ISO `+03:30` is `-"offset"` inverted.
- "`setDate(getDate()+1)` is 'next day'" — it is *host*-local calendar +1, which breaks on DST gap/repeat and ignores target zone (e.g., user in NY while server in UTC).
- "`24*60*60*1000` is 'a day'" — it is *24 hours* (duration), not a calendar day (23/25h on DST).
- "`Date` handles non-UTC zones" — no, `Date` only knows host TZ and UTC; arbitrary zones require `Intl` for display and `Temporal` for arithmetic.

### 5) **Performance note**

`Intl.DateTimeFormat` construction parses `timeZone` and CLDR data (10–100× heavier than `Date` accessor). In a hot loop formatting 10k dates for a table, hoist `new Intl.DateTimeFormat(locale,{timeZone})` out of the loop and reuse `format`. `getTimezoneOffset()` is cheap (single conversion). `Date.UTC` is pure arithmetic (no allocation) vs `new Date(Date.UTC(...))` which allocates.

### 6) **Mentor note**

Have juniors predict `new Date(2026,0,15).toISOString()` on a non-UTC host and `new Date("2026-03-08T02:30:00")` in `TZ=America/New_York` (gap → `03:30`) before running — the two cement host-vs-UTC and gap normalization. In review, flag any `setDate(getDate()+1)` for "next day" (require UTC anchoring or `Temporal`), any `24*60*60*1000` labeled "a day" (require `Duration`/`Temporal` comment), and any `Date` arithmetic that targets a non-host zone (require `Temporal`/`Intl`).
