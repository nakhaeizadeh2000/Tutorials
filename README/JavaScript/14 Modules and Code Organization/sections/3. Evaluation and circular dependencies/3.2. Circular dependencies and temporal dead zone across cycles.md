## 3.2. Circular dependencies and temporal dead zone across cycles

### 1) **Why cycles can still work — live bindings wire before bodies finish**

**Definition** — a cycle `a.js → b.js → a.js` is *linked* before any body runs: the host creates `[[Import]]`/`[[Export]]` slots for both directions during linking, then evaluates in post-order starting from the entry. When evaluating `a.js`, `b.js` hasn't finished but the binding for `a.js`'s export already exists (as an uninitialized TDZ slot). `b.js` can reference that binding via closure/function without forcing immediate read of its value. The binding will become initialized when `a.js`'s initializer line executes. So cycles succeed if they access imports *lazily* (inside functions called after both modules initialized) and fail if they read eagerly at top level.

**What problem it solves / history** — cycles are unavoidable in domain models (`User` imports `Post`, `Post` imports `User`). CJS allows cycles by returning a partially-filled `module.exports` object (mutation visible, assignment not). ESM generalizes this with per-binding live views plus TDZ to surface uninitialized reads early. Without live bindings, one side of a cycle would see a snapshot of `undefined`.

```js
// Simulated cycle wiring — two modules circular:
// a.js: import { y } from "./b.js"; export let x = 1; export function getY(){ return y; }
// b.js: import { x } from "./a.js"; export let y = 2; export function getX(){ return x; }
// Linking: slots for x,y created before evaluation, getters live.

// Simulate evaluators that mimic lazy vs eager:
let _x, _y;
const nsA = {}, nsB = {};
Object.defineProperty(nsA, "x", { get(){ return _x; }, enumerable: true });
Object.defineProperty(nsB, "y", { get(){ return _y; }, enumerable: true });
function getY() { return nsB.y; } // reads y lazily after both init
function getX() { return nsA.x; }

// Simulated evaluation order: a first (entry) -> b -> back
// Evaluate a partially? spec post-order picks leaves first — but for cycle, it breaks recursion via "already evaluated" map
// So b evaluates before a's `let x = 1` has run:
console.log("Before init, slots uninitialized — would be TDZ in real ESM if read now");
// b's top-level would see _x as uninitialized? In sim we default undefined, but spec throws ReferenceError
// After both inits:
_x = 1; _y = 2;
console.log(getY(), getX()); // 2 1 — lazy function reads succeed post-init
console.log("Lazy access via exported functions succeeds; eager top-level read would have failed");
```

### 2) **The TDZ across a cycle — reading a `let`/`const`/`class` before its initializer throws**

**Definition** — bindings for `let`/`const`/`class` remain in TDZ until their declaration initializer executes. During cycle evaluation, if module `b.js` eagerly does `import { x } from "./a.js"; console.log(x)` at top level while `a.js`'s `let x = 1` hasn't yet evaluated (because `a.js`'s evaluation is suspended awaiting `b.js`), reading `x` throws `ReferenceError: Cannot access 'x' before initialization`. Function declarations do not have TDZ (hoisted `function foo(){}` is initialized on environment creation), so `import { foo }` followed by eager `foo()` inside the cycle often works.

**Bad vs Good:**

```js
// BAD — eager read of cyclic let at top level (simulated TDZ throw)
let _circularX; // would be TDZ — we simulate throw by flag
let initialized = false;
const cycNS = {};
Object.defineProperty(cycNS, "x", {
  get() {
    if (!initialized) throw new ReferenceError("Cannot access 'x' before initialization");
    return _circularX;
  },
  enumerable: true,
});
console.log("Module b eagerly reads x at top-level while a still pending:");
try { console.log(cycNS.x); } catch (e) { console.log(e.name, e.message); } // ReferenceError
initialized = true; _circularX = 42;
console.log(cycNS.x); // 42 — now ok

// BAD pattern in real ESM — b.js:
// import { x } from "./a.js";
// console.log("eager", x); // ReferenceError if a.js's `export let x` not yet initialized due to cycle

// GOOD — read lazily inside function, called after evaluation:
function lazyReader() { return cycNS.x; }
console.log(lazyReader()); // 42 — after init

// GOOD — export function instead of raw value on cyclic edge:
console.log("Export function `getX(){ return x; }` instead of raw `x` so readers call after init");
console.log("Or extract shared third module `common.js` both import, breaking the cycle");
```

```js
// Function hoisting survives cycles — let/class do not:
console.log("export function helper(){} is safe across cycles; export let value = 1 is not at top-level read");
console.log("export class User {} has TDZ until class definition evaluates — eager read before that throws");
```

### 3) **Designing cycles that survive — export functions/classes not raw values avoid top-level reads**

**Definition** — make cyclic dependencies depend on *behavior* (functions/classes that capture the binding lazily) not *data* (raw `let` values read at module top level). Three refactor patterns: (1) expose a function `getUserSchema()` rather than `export const userSchema = ...` that touches the other side at creation; (2) move shared constants/types to a third `common.js` both import; (3) inject via caller (`function use(user){}`) rather than importing directly. Detect cycles in CI (`madge --circular src/`, `eslint-import/no-cycle`).

**Modern guidance** — if a cycle is required (entity graphs, recursive types), at least one direction should import only a type-like value (class/function) not an evaluated value; for runtime cycles, add a test that imports the entry and asserts no `ReferenceError`.

```js
// BAD cyclic edge — eager value read
console.log("BAD: a.js: export const routes = [{ handler: bHandler }]; // bHandler imported from b.js which imports routes — routes read before init => TDZ");

// GOOD: lazy closure or third module
let routes;
function getRoutes() { return routes; } // lazy read after init
routes = [{ name: "ok" }];
console.log(getRoutes()); // ok — function defers read

// GOOD: break cycle via common.js
// common.js: export const EVENTS = { START: "start" };
// a.js: import { EVENTS } from "./common.js";
// b.js: import { EVENTS } from "./common.js"; // no longer a<->b cycle
console.log("Shared third module breaks the cycle — both depend on leaf, not each other");

// Cycle detection tip — run gate:
console.log("Gate: `npx madge --extensions js,mjs --circular src/`");
console.log("Lint: `import/no-cycle` flags `a->b->a` during development");
```

### 4) **Common confusion**

- "Cycles always need refactoring away" — small, intentionally lazy cycles (entity↔repo factories returning functions) are tolerated; Tooling shows cycles are ok if at least one edge is function-only. Eliminate when the eager TDZ fires or the mental model burden exceeds the coupling benefit.
- "CJS cycles are same as ESM cycles" — CJS returns the *partially filled* `module.exports` object — mutation of `exports.x` after cycle is visible, reassignment of object is not; ESM's per-binding live view can throw TDZ rather than silent `undefined`, surfacing bugs earlier.
- "`export const x = import('./x.js')` is same as `import {x}`" — top-level `await import` in cycles blocks evaluation (TLA) and can deadlock if both sides await each other; static `import {x}` with lazy function is the pinch point.

### 5) **Performance note**

Linking a cycle walks imports transitively to resolve each `[[Import]]` to its `[[Export]]` slot; depth of cycle does not affect per-access cost (still one getter), but link time is `O(edges in SCC)`. Repeated `await import()` of a cyclic entry during hot path hits the module map (cached) after first evaluation — no re-evaluation cost, but TLA cycles that block the entry can stall all dependents until resolution, so keep cyclic modules free of top-level `await`.

### 6) **Mentor note**

Have the team predict output of a two-file cycle where `b.js` does `import { x } from "./a.js"; console.log("b sees", x)` vs `export function show(){ console.log(x);} ` — the first throws TDZ, the second works when called later. Those who say "both work" need the TDZ gap explained. In review, prohibit eager top-level reads of imports coming from a file that also imports back (lint + comment `// cyclic — keep reads lazy`), and require that any new cycle be documented with comment `// cycle: a <-> b via getX(), not raw x`.
