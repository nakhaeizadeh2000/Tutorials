## 3.1. Evaluation order single evaluation and hoisting

### 1) **Depth-first post-order — leaves evaluate before parents then import hoisting wires bindings first**

**Definition** — ESM evaluation is two phases: *Linking* (resolve all `import`/`export` wires, detecting syntax errors and missing exports without running code) then *Evaluation* (run module bodies in *depth-first post-order*: a module's dependencies are evaluated before the module itself; among siblings, textual order defines discovery order but evaluation still satisfies leaves-first). `import` hoisting means every imported binding exists before *any* body runs — an importer can call a function declared later in its dependency even though textual order suggests otherwise.

**What problem it solves / history** — CJS `require` inside a function runs on demand — order is imperatively what you coded. ESM chose deterministic post-order so the graph's side effects run once per leaf before parents observe them, and bundlers can statically order chunks. This also makes `import "./polyfill.js"` timing predictable (polyfill installs before parents run).

**Modern guidance** — never count on textual `import` order for value ordering beyond leaves-first; depend on exported *values* only after evaluation finished (avoid reading a dependency's mutable `let` at importer's top-level interleaved evaluation).

```js
// Depth-first post-order with memoization — runnable conceptual trace
// Graph: app.js -> [b.js, c.js]; b.js -> d.js; c.js -> d.js (diamond with shared d)
const order = [];
const seen = new Set();
function evalModule(name, deps, body) {
  if (seen.has(name)) return;
  seen.add(name);
  deps.forEach(d => d());
  order.push(name);
  body();
}
const d = () => evalModule("d", [], () => console.log("eval d"));
const b = () => evalModule("b", [d], () => console.log("eval b"));
const c = () => evalModule("c", [d], () => console.log("eval c"));
const app = () => evalModule("app", [b, c], () => console.log("eval app"));
app();
console.log("order", order.join(" -> ")); // d -> b -> c -> app (d once, leaves first)

// Side-effect import timing — polyfill before parent:
console.log("side-effect import './polyfill.js' implies d/ polyfill eval before app body");

// Import hoisting — conceptual (real ESM would allow `add` use before import line):
let hoisted = "available before textual import";
console.log(hoisted); // linking made it exist before evaluation
```

```js
// Module body sees dependency side-effects — do not read mutable let early at top-level
let depValue = "initial";
function depInit() { depValue = "ready"; }
depInit();
console.log(depValue); // ready — evaluation already ran before this line if dep is parent of leaf
```

### 2) **Single evaluation — every module runs once even if imported many times including diamonds**

**Definition** — the host keeps a *Module Map* keyed by *resolved specifier* (`https://cdn/x.js`, `file:///proj/app/math.js`). The first request triggers evaluation; later importers (including `await import()` with same specifier) receive the already-evaluated namespace without re-running the body. This guarantees singleton initialization (stateful `counter.js` incremented once) and makes side-effects idempotent across fan-in. Resolution normalization matters — `./math.js` vs `./math` may be two keys (Node ESM requires extension, so they either both error or resolve distinctly).

```js
// Single evaluation — count evaluations
let evalCount = 0;
function getModule() {
  // simulate module map: function body runs only once per key
  const map = getModule.map || (getModule.map = new Map());
  const key = "./counter.js";
  if (map.has(key)) return map.get(key);
  evalCount++;
  const ns = { count: 0, inc(){ return ++this.count; } };
  map.set(key, ns);
  return ns;
}
const modA = getModule(); const modB = getModule();
console.log(modA === modB, evalCount); // true 1 — same instance, one eval
modA.inc();
console.log(modB.count); // 1 — shared state

// Diamond still one eval via post-order dedup: D via B and via C
console.log("D evalCount remains 1 even though two paths reach D — post-order de-duplicates");

// Specifier normalization trap:
console.log("Module map key is RESOLVED specifier after Node resolution (extension + exports map)");
console.log("./math vs ./math.js may be distinct keys — ESM requires ./math.js in Node (see 5.3)");
```

```js
// BAD: expecting re-execution on re-import to reinitialize state
let initCalls = 0;
function badMod() { initCalls++; return { v: initCalls }; }
console.log(badMod().v); // 1
console.log(badMod().v); // would be 2 if body re-ran — but real ESM would still be 1
console.log("GOOD: export an explicit reset() function instead of relying on re-evaluation");

// GOOD: idempotent module bodies (no ambient mutation on second import expected)
console.log("Module bodies should be safe to import many times — evaluation is once");
```

### 3) **Hoisting and TDZ across modules — exported functions declared after import still work**

**Definition** — within a module, declarations hoist normally (`function` hoisted, `class`/`let` TDZ until initializer). *Across* modules, the linking phase makes imported bindings exist before evaluation, but their *initializers* have only run if the exporting module has already been evaluated in post-order. If cycle-free (a DAG), the exporter is *always* a leaf or earlier — so its initializers have run by the time the importer evaluates. Thus `import { add }` where `add` is `export function add(){}` at bottom of `math.js` works: `math.js` evaluates fully before `app.js` evaluates, so `add` is initialized.

```js
// Within-module hoisting — works intra-file:
console.log(typeof hoistedFn); // function
function hoistedFn() { return 1; }
try {
  console.log(typeof notYet); // ReferenceError if let/const
  let notYet = 2;
} catch (e) { console.log(e.name, "for let before init"); }

// Cross-module analogous — importer sees initialized export because exporter (leaf) evaluated first:
let exporterAdd;
function evaluateExporter() { exporterAdd = function add(a,b){ return a+b; }; }
function evaluateImporter() { console.log(exporterAdd(2,3)); } // 5 — exporter already evaluated
evaluateExporter();
evaluateImporter();

// BAD: would-be TDZ only arises with cycles — acyclic path is safe (see 3.2)
console.log("DAG: importer's top-level read of imported binding is safe; cycle: may throw TDZ");

// For `export default` function expressions: `export default function foo(){}` hoists foo
// but `export default () => {}` has no local hoisted name — only `default` binding
console.log("named default hoisted, anonymous default not — mirrors 2.1");
```

### 4) **Common confusion**

- "`import` order among files decides which side-effect runs first" — not textual order but depth-first post-order determines sequence; side-effect import `"./a.js"` before `"./b.js"` textual only controls discovery order among siblings at same parent — leaves still precedence.
- "Importing a module twice runs its top-level twice" — evaluation is once; counting on re-execution for re-init is a bug — provide an explicit `init()`/`reset()` export instead.
- "`require` inside a function gives same single-evaluation guarantee as ESM" — yes for `require.cache`, but CJS resolution key is *filename* after synchronous resolution + wrapper execution per `require` call site; ESM map key is *resolved specifier* via host resolver — subtle divergence for conditional/specifier variants.

### 5) **Performance note**

Single evaluation makes module-level memoization effective — `export const parsed = expensiveParse(json)` parses once regardless of import fan-in. Over-eager top-level `await fetch()` in a widely imported module blocks all dependents (TLA blocking — [Async 5.2](<../../../13 Async Event Loop and Promises/sections/5. Async functions concurrency and migration/5.2. Concurrency patterns sequential vs parallel vs race and top-level await.md>)). Keep top-level work in shared leaf modules lightweight or lazy (`export function getParsed(){...}`) if many importers must not pay fetch cost.

### 6) **Mentor note**

Draw the diamond `app→b,c→d` and have juniors predict `d` evaluation count (1) and order (`d,b,c,app`). Those saying `d,b,d,c,app` reveal double-evaluation folklore. In review, flag any module top-level `await fetch` without comment on TLA blocking fan-in, and any expectation that re-importing refreshes state — require explicit `reset`/`refresh` export.
