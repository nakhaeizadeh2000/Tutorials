## 7.1. Real production bugs caused by module mistakes

### 1) **Dual-package singleton split — two `EventEmitter` instances where one was expected**

**Incident** — library `pkg` ships `lib/cjs/index.js` (CJS) and `lib/esm/index.js` (ESM) via `exports` {`import`,`require`}. App's server code uses `require("pkg")` (CJS service), while newly migrated route handler uses `import "pkg"` (ESM). Each face has `let emitter = new EventEmitter(); export/emitter`. Publishing event via `require` face does not reach listeners registered via `import` face — messages silently lost. Test suite that uses only one loader never catches it; production mixed-loader build does.

**Root cause** — module map key differs: `require("pkg")` resolves to `lib/cjs/index.js` via `require` condition; `import "pkg"` resolves to `lib/esm/index.js` via `import` condition. Two evaluations → two `emitter` instances (see [5.2](<../5. CommonJS interop and resolution/5.2. ESM and CJS interop dual packages and migration.md>)). State at module root (`let cache = new Map()`) is therefore duplicated.

**Fix** — ship pure ESM (prefer — `type: module`, single `./index.js`, single cache). If dual needed, externalize shared state via `globalThis.__pkg_state` or sole JSON file, or make both conditions point to one adaptive file that exposes both via conditional export shim. Gate with singleton-identity test: `assert.strictEqual(require("pkg").emitter, (await import("pkg")).emitter)`.

```js
// Simulated dual split vs single fix:
function makeInstance(label){ let c=0; return {inc(){return ++c;}, label}; }
const cjsInst = makeInstance("cjs"), esmInst = makeInstance("esm");
console.log(cjsInst.inc(), esmInst.inc()); // 1 1 — two instances, not shared
cjsInst.inc(); console.log("cjs hits", cjsInst.label, "esm hits", esmInst.label); // separate

// Fix: shared host singleton
const sharedState = (globalThis.__pkg = globalThis.__pkg || { hits:0, inc(){ return ++this.hits; } });
console.log(sharedState.inc(), sharedState.inc()); // 1 2 — shared across faces

// Gate:
console.log("Gate: require('pkg').inst === (await import('pkg')).default.inst → must be strictly equal");
```

### 2) **Live-binding illusion vs object-share — `export default obj; obj = {}` does not propagate as expected**

**Incident** — `config.mjs` does `let cfg = { timeout: 1000 }; export default cfg; export function reload(){ cfg = { timeout: 2000 }; }`. `app.mjs` does `import cfg from "./config.mjs"; const local = cfg; reload(); console.log(local.timeout, cfg.timeout)`. Ops reconfigures `reload()` after deploys; `local.timeout` stays 1000 (stale handle) while `cfg.timeout` becomes 2000 — HB timeout not respected, connections leak.

**Root cause** — live binding tracks `default` rebind (`cfg` getter sees new object), but `local = cfg` snapshotted the object identity at import time (see [2.2](<../2. Exports and live bindings/2.2. Live bindings why imports are not copies.md>)). Holding `default` object reference is shared-identity capture, not live binding read.

**Fix** — never snapshot `default` object when exporter may rebind; always re-read via live binding (`cfg` imported name) or accessor (`export function getCfg(){ return cfg; }`), or avoid rebinding `default` — mutate: `Object.assign(cfg, newCfg)`.

```js
// Trap demo (simulated live default)
let cfg = { timeout: 1000 };
const defaultNS = {};
Object.defineProperty(defaultNS,"default",{get(){return cfg;},enumerable:true});
const local = defaultNS.default; // snapshot
console.log(local.timeout, defaultNS.default.timeout); // 1000 1000
cfg = { timeout: 2000 }; // reload rebinds
console.log(local.timeout, defaultNS.default.timeout); // 1000 2000 — stale vs live
console.log("Fix: do not hold local = default; always read defaultNS.default or use getCfg()");
function getCfg(){return cfg;}
console.log(getCfg().timeout, defaultNS.default.timeout); // 2000 2000 — fresh

// Correct mutation without rebind:
cfg = { timeout: 1000 }; // reset for demo
const cfg2 = { timeout: 1000 };
Object.defineProperty(defaultNS,"default2",{get(){return cfg2;},enumerable:true});
const local2 = defaultNS.default2;
Object.assign(cfg2, { timeout: 2000 }); // mutate same object
console.log(local2.timeout, cfg2.timeout); // 2000 2000 — shared handle, no rebind
```

### 3) **Cycle TDZ crash — `ReferenceError: Cannot access 'X' before initialization` in production only on cold start**

**Incident** — `a.mjs` `export let ready = false; import { init } from "./b.mjs"; export function start(){ ready = true; } init();` and `b.mjs` `import { ready } from "./a.mjs"; console.log("b sees", ready); export function init(){ console.log(ready);}`. Cold startup (graph evaluated top-down via `app.mjs → a → b`) makes `b`'s top-level `console.log(ready)` run while `a`'s `let ready` still in TDZ → crash. Local dev imported `b` first directly in REPL, masking cycle.

**Root cause** — eager read of cyclic `let` at top-level before initializer executed (see [3.2](<../3. Evaluation and circular dependencies/3.2. Circular dependencies and temporal dead zone across cycles.md>)). `let`/`const`/`class` have TDZ across cycles; `function` does not.

**Fix** — make cyclic edge lazy: `b.mjs` exports function `show(){ console.log(ready);}` and calls after both modules initialized, or break cycle via `common.mjs`. Lint `import/no-cycle` and test by importing entry in fresh Node.

```js
// Simulated TDZ across cycle — eager vs lazy
let _ready;
let initDone = false;
const cyc = {};
Object.defineProperty(cyc,"ready",{get(){
  if(!initDone) throw new ReferenceError("Cannot access 'ready' before initialization");
  return _ready;
},enumerable:true});
console.log("Eager read at b top-level while a not yet init:");
try { console.log(cyc.ready); } catch(e){ console.log(e.name, e.message); } // ReferenceError
initDone = true; _ready = false;
console.log(cyc.ready); // false — now ok
// Lazy after init:
function show(){ console.log(cyc.ready); }
_ready = true; show(); // true — works

console.log("Fix: b should export function that reads ready lazily, not log at top-level");
console.log("Detect: npx madge --circular src/ && eslint import/no-cycle");
```

### 4) **Bare specifier deploy break — works locally via `exports` fallback but fails in browser without import map**

**Incident** — `import "pkg/feature"` works in Node (resolved via `exports` map). Deployed frontend bundle forgot `importmap` entry for `pkg`; native browser ESM (no bundler) throws `Failed to resolve module specifier "pkg/feature"` at load — blank page in prod, no error in Node tests.

**Root cause** — bare specifiers mean *host wants mapping*. Node maps via `node_modules`/`exports`; browsers require explicit `<script type="importmap">` (see [5.3](<../5. CommonJS interop and resolution/5.3. Specifiers package.json exports import maps and organization.md>)). Bundler hides gap by resolving at build-time and emitting relative chunks; unbundled/prod preview without bundler path tests misses it.

**Fix** — for browser native ESM, add `importmap` entry or bundle; for libraries, ensure `exports` map lists `./feature` explicitly and CI tests browser load via `npx serve` + headless.

```js
// Simulated bare resolution:
console.log("Node: import 'pkg/feature' → ./lib/feature.js via exports field — success");
console.log("Browser without importmap: import 'pkg/feature' → TypeError Failed to resolve");
console.log("Fix: <script type=\"importmap\">{\"imports\":{\"pkg/feature\":\"/js/pkg/feature.js\"}}</script>");
console.log("Or bundle: esbuild resolves bare → relative at build time");

// Extension trap also fits here:
console.log("Also: import './utils' (no .js) works in CJS via extension fallback, fails in Node ESM — bare-like deploy break");
```

### 5) **JSON `assert` vs `with` deprecation — warning spam + future hard failure**

**Incident** — `import data from "./config.json" assert { type: "json" }` logs `DeprecationWarning: assert is deprecated, use with` on Node 22 (hundreds per process) and will become SyntaxError when `assert` removed. `npm ci` logs pollute but not fail — team ignores until CI flips to hard error after upgrade.

**Fix** — replace all `assert` with `with { type: "json" }` (ES2025, Node 17.5+). `grep -rn "assert { type"`. For dynamic JSON: `await import("./c.json", { with: { type: "json" } })`.

```js
console.log("Replace: import x from './c.json' assert {type:'json'} → with {type:'json'}");
console.log("Dynamic: await import('./c.json', { with: { type: 'json' } })");
console.log("Module specifier must include .json extension: './config.json' not './config'");
```
