## 5.2. ESM and CJS interop dual packages and migration

### 1) **Importing CJS from ESM — `import pkg from "cjs-pkg"` gets the `module.exports` as `default`**

**Definition** — when ESM does `import pkg from "cjs"` (where the target is a CommonJS file/package), Node synthesizes an ESM wrapper whose `default` export is the CJS `module.exports` value and no named exports exist except via `module.createRequire` / ESM shim. `import * as pkg from "cjs"` likewise produces a namespace whose `default` is `module.exports` and whose named keys mirror `module.exports` properties as a convenience on Node, but the spec only guarantees `default` — named import `import { readFile } from "fs"` works for Node *built-ins* because Node provides a built-in ESM facade, not for arbitrary CJS files.

**What problem it solves / history** — vast CJS ecosystem must be usable inside ESM without rewriting every package. The `default` wrapping lets `import express from "express"` obtain the `function express(){}` that CJS assigned to `module.exports`. Named imports from arbitrary CJS remain risky — some bundlers synthesize them by reading `module.exports` properties at link, others reject them.

**Modern guidance** — when importing CJS from ESM, default import the namespace and then pick properties: `import pkg from "cjs-pkg"; const { a, b } = pkg;`. Do not use `import { a } from "cjs-pkg"` for non-Node CJS packages — it may be undefined or live differently across tools. For Node built-ins (`fs`, `path`), either style is portable on current Node but prefer default+pick for consistency.

```js
// Simulated CJS→ESM wrapper — what Node does
const cjsExports = { add(a,b){ return a+b; }, VERSION: 1 }; // module.exports in cjs-pkg
const esmNs = { default: cjsExports };
Object.defineProperty(esmNs, "add", { // Node convenience: also exposes named as getters over default
  get(){ return cjsExports.add; }, enumerable: false
});
console.log(esmNs.default === cjsExports); // true — default IS module.exports
console.log(typeof esmNs.add); // function — Node shim; arbitrary CJS packages may NOT have this in future

// BAD — assuming named import from arbitrary CJS works in spec:
console.log("BAD: import { add } from \"./cjs-pkg.js\"; // may be undefined on some hosts/tools");
// GOOD — default import + destructure:
console.log("GOOD: import pkg from \"./cjs-pkg.js\"; const { add } = pkg; // portable");

// Node built-in ESM facade — special case, spec-sanctioned shim:
console.log("Node built-ins have ESM facade: import { readFile } from 'node:fs' works reliably");
console.log("But for user CJS files, treat only `default` as guaranteed");

// Runnable: verify that esmNS.default mutations reflect cjsExports (same object identity)
esmNs.default.EXTRA = 99;
console.log(cjsExports.EXTRA); // 99 — same object
```

### 2) **Requiring ESM from CJS — `require("./esm.mjs")` throws `ERR_REQUIRE_ESM`**

**Definition** — `require()` is synchronous; ESM evaluation is async-capable (TLA, `import()`). Node refuses the synchronous crossing: `require("./esm.mjs")` or `require("cell")` where `package.json type: module` or file `.mjs` → throws `Error [ERR_REQUIRE_ESM]: require() of ES Module ... not supported. Instead change the require to a dynamic import() which is available in all CommonJS modules`. The bridge is `await import("./esm.mjs")` inside CJS (turn the caller `async` or top-level wrapper), or `createRequire` is not the remedy here — it creates a CJS `require` inside ESM, not the reverse.

**What problem it solves / history** — prevents deadlocks where a sync `require` would block on a pending TLA module graph. The spec deliberately made ESM→ESM and CJS→CJS sync but ESM→CJS async boundary explicit. Mid-migration code must choose an async boundary (make `require` site async via `import()`).

```js
// BAD — sync require of ESM:
// try { require("./esm.mjs"); } catch(e){ console.log(e.code); } // ERR_REQUIRE_ESM
console.log("BAD: require('./esm.mjs') → ERR_REQUIRE_ESM in Node");

// GOOD — dynamic import inside CJS (runnable via data URL):
(async () => {
  const ns = await import("data:text/javascript,export const value = 7; export default 10;");
  console.log(ns.value, ns.default); // 7 10 — CJS can await ESM via import()
})();

// Migration wedge — CJS caller that cannot be async yet: use `.then` chain
console.log("Migration wedge: `import('./esm.mjs').then(ns => ...)` keeps CJS sync path but ESM consumer async");

// `createRequire` is opposite direction (ESM→CJS), not CJS→ESM:
console.log("createRequire creates require() inside ESM to pull in CJS, not ESM inside CJS");
```

```js
// Real verification of ERR_REQUIRE_ESM via temporary files would need FS access — simulate type:
console.log("Node: type: module package's .js are ESM; requiring them from CJS throws");
console.log("Fix options: rename to .cjs, or `await import()` inside CJS");
```

### 3) **Dual packages — `type` `.mjs`/`.cjs` `"exports"` conditional and state-duplication hazard**

**Definition** — a *dual package* ships both CJS and ESM entry points so old `require()` callers and new `import` callers both work. Contracts: `package.json` `"type"` field sets default for bare `.js` (absent = `commonjs`), `.mjs` forces ESM, `.cjs` forces CJS, and `"exports"` maps `"import"` vs `"require"` conditions to different files:

```json
{
  "type": "commonjs",
  "exports": {
    ".": { "import": "./lib/esm/index.js", "require": "./lib/cjs/index.js" },
    "./feature": { "import": "./lib/esm/feature.js", "require": "./lib/cjs/feature.js" }
  }
}
```

**State-duplication hazard** — if both faces maintain separate `let state = {}` (each file's module scope is isolated, each has its own cache/module map entry), `require("pkg")` and `import "pkg"` see *two* singleton instances. A library that counts connections or caches in module root (`let cache = new Map()`) will split across the two loaders — bugs that only surface in mixed-loader projects (tests with one loader, prod with both). The fix is either *single source*: ship only ESM (prefer for new libs), or make both faces share state via a shared JSON/WSH, or use the Node `exports` condition to point to *one* file that lazily adapts.

```js
// Dual package hazard — simulated two instances
function makePkgInstance(label) {
  let hits = 0;
  return { label, inc(){ return ++hits; }, get hits(){ return hits; } };
}
const cjsInstance = makePkgInstance("cjs");
const esmInstance = makePkgInstance("esm");
console.log(cjsInstance.inc(), esmInstance.inc()); // 1 1 — separate counters! not shared
console.log(cjsInstance.inc(), cjsInstance.hits, esmInstance.hits); // 2 2 1 — split
console.log("Bug: connection pool, event bus, cache now duplicated");

// GOOD: single-format package — pure ESM (recommended for new libs)
// package.json: { "type": "module", "exports": { ".": "./index.js" } }
// Then both require via createRequire(import.meta.url) and import resolve to same file

// GOOD: shared singleton via external host storage when dual needed
// state.js shared via globalThis.__pkg_state || (globalThis.__pkg_state = {hits:0}) — but be explicit
const shared = (globalThis.__sharedPkg = globalThis.__sharedPkg || { hits: 0 });
function pkgShared(label) { return { inc(){ return ++shared.hits; } }; }
const a = pkgShared("a"), b = pkgShared("b");
console.log(a.inc(), b.inc(), shared.hits); // 1 2 2 — now shared
console.log("Migration path: ship pure ESM + CJS compat wrapper that re-exports the same .mjs via createRequire trick");

// package.json rules summarized:
const rules = [
  'No "type" → .js is CJS; .mjs is ESM; .cjs is CJS',
  '"type":"module" → .js is ESM; .mjs is ESM; .cjs is CJS',
  '"exports" import condition wins for import; require condition wins for require',
  'Missing .cjs when type:module and CJS tool requires file without extension → ERR',
];
console.log(rules.join("\n"));
```

### 4) **Common confusion**

- "`import { readFile } from \"fs\"` proves named CJS imports work generically" — `fs` is a Node built-in with explicit ESM facade; arbitrary `import { x } from "./my-cjs.js"` may not expose `x` on spec ESM hosts — treat Node built-ins as special.
- "`require()` can load ESM if I add `type:commonjs`" — `require` is file-typed, not caller-typed; requiring an `.mjs` or a `.js` inside a `type:module` package still throws `ERR_REQUIRE_ESM` even if the *requirer* is CJS.
- "Dual packages are harmless — they just give two syntaxes for same code" — state outside the export value (module-root `let`, caches) is duplicated across CJS and ESM instances; only export *value* sharing is sometimes present via default wrapping, but internal singletons are split.

### 5) **Performance note**

Dual packages double the parse/compile cache: Node compiles both CJS and ESM variants of the same logic (2× JIT input, 2× code cache). The `require.cache` vs ESM module map are separate structures — mixed `import`+`require` for `N` dual files holds `2N` cache entries. Pure ESM ships half. If staying dual, build both variants from one source via bundler but keep `lib/cjs` plain transpilation minimal to avoid 2× run-time divergence cost.

### 6) **Mentor note**

Have team audit `package.json` `exports` with `node --check` and verify `import "pkg"` vs `require("pkg")` hit the same source via `fs.realpath` logging of the resolved file — divergence signals dual-split. In review, prohibit shipping a library that both `module.exports =` and `export default` in the same file (confuses `default` wrapping) and require that any dual-package refactor include a singleton-split test: `assert.strictEqual(require("pkg").cache === (await import("pkg")).cache)`.
