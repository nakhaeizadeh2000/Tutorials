## 5.3. Specifiers package.json exports import maps and organization

### 1) **Specifier taxonomy — relative (`./`) absolute bare and subpath imports (`#utils`)**

**Definition** — an *import specifier* string is either *relative/bare-relative* (`"./math.js"`, `"../lib/add.js"`, `"/absolute/path.js"` in Node), *bare* (`"lodash"`, `"@scope/pkg"`, `"react/jsx-runtime"`), or *internal subpath import* (`"#utils"` via `imports` map). ESM in Node *requires* the full filename + extension for relative imports: `import "./math.js"` valid, `import "./math"` SyntaxError/MODULE_NOT_FOUND (Node does not append `.js` like CJS did). `node:fs` prefix is the explicit way to signal built-ins (`"node:fs"` vs `"fs"`). In browsers, any bare specifier throws without an import map.

**Why it matters** — specifier discipline is the contract for resolution determinism. Allowing extension-less or directory imports (`"./utils"` resolving to `./utils/index.js`) makes resolution filesystem-dependent and non-portable to browsers/bundlers.

**Modern guidance** — always include extension in relative ESM specifiers (`"./math.js"` not `"./math"`), avoid directory imports (`"./utils"` → `"./utils/index.js"`), prefer `node:` prefix for built-ins, and use `#internal` via `imports` for package-internal aliases instead of deep relative `../../..`.

```js
// Specifier examples shown as strings — keep CJS-runnable:
const specifiers = [
  './math.js          — relative, must include .js in Node ESM',
  '../lib/add.js      — parent relative',
  '/var/app/lib.js    — absolute (rare in source, valid in Node)',
  'lodash             — bare → node_modules / exports map / importmap',
  '@scope/pkg         — scoped bare',
  'node:fs            — explicit built-in (preferred)',
  '#utils             — subpath import alias via "imports" field',
];
console.log(specifiers.join("\n"));

// Verification: Node ESM resolution requires extension — simulate via import() error:
(async () => {
  try {
    // Missing .js extension — Node ESM rejects (in real ESM would throw ERR_MODULE_NOT_FOUND)
    // In this CJS context, dynamic import with bare relative will still enforce file existence
    // We simulate by trying to import a file without extension via data URL wrapper? Instead show message:
    console.log("Node ESM: import './math' (no .js) → ERR_MODULE_NOT_FOUND (extension required)");
    console.log("Node CJS: require('./math') implicitly tries ./math.js, ./math/index.js — ESM does not");
  } catch (e) { console.log(e.message); }

  // Preferred node: prefix:
  const fsMod = await import("node:fs");
  console.log(typeof fsMod.readFile); // function — explicit built-in
})();

// BAD: directory import (implicit index):
console.log("BAD: import { x } from './utils'; // Node ESM will not look for ./utils/index.js implicitly");
// GOOD: explicit file:
console.log("GOOD: import { x } from './utils/index.js';");
```

### 2) **`package.json` `exports`/`imports` and `type` — the public surface contract**

**Definition** — `"exports"` controls what consumers can `import` from your package (and which file they actually get per condition). `"imports"` (with leading `#`) controls your *own* internal subpath imports (`import { ok } from "#utils"`). `"type"` controls how bare `.js` are interpreted (`commonjs` default vs `module`). `"exports"` entries are *subpath patterns* since Node 14/20:

```json
{
  "type": "module",
  "exports": {
    ".": { "import": "./lib/esm/index.js", "require": "./lib/cjs/index.js" },
    "./feature": "./lib/feature.js",
    "./feature/*": "./lib/feature/*.js",
    "./*": "./lib/*.js"
  },
  "imports": {
    "#utils": "./src/utils/index.js",
    "#cfg": { "node": "./src/cfg-node.js", "default": "./src/cfg.js" }
  }
}
```

Without `"exports"`, consumers can deep-import any file (`"pkg/src/private.js"`). With `"exports"`, deep imports of unexported paths throw `ERR_PACKAGE_PATH_NOT_EXPORTED` — so `"exports"` is the module-level encapsulation contract (parallels `export` vs non-export inside a file).

```js
// Simulated exports resolution — HostResolve rule:
// import "pkg/feature" → if pkg has "exports" "./feature": "./lib/feature.js" → resolve to that
// import "pkg/private.js" → if not in exports → ERR_PACKAGE_PATH_NOT_EXPORTED
console.log("With exports map: import 'pkg' → ./lib/esm/index.js (import condition)");
console.log("Without exports map: import 'pkg/private.js' silently allowed — couples to internals");

// imports alias — internal alias without deep relative dots:
console.log("imports: \"#utils\": \"./src/utils/index.js\" → import \"#utils\" from any package file");
console.log("Avoids ../../../utils across package — refactors via one map entry");

// type trap:
console.log(JSON.stringify({ "type: commonjs": ".js is CJS; .mjs is ESM, .cjs is CJS", "type: module": ".js is ESM; .mjs ESM, .cjs CJS" }));
console.log("Mixed .js without explicit type leads to surprise — set type explicitly or use .mjs/.cjs");

// Runnable: verify imports map via package.json read (simulated):
const fakePkg = {
  type: "module",
  exports: { ".": "./lib/esm/index.js", "./feature": "./lib/feature.js" },
  imports: { "#utils": "./src/utils/index.js" }
};
console.log("fake pkg exports keys", Object.keys(fakePkg.exports));
console.log("fake pkg imports keys", Object.keys(fakePkg.imports));
```

### 3) **Import maps and organization — browser/deno `importmap` barrel files vs direct `sideEffects` and tree-shaking**

**Definition** — browsers have no `node_modules`; bare specifiers (`"lodash"`) must be mapped via `<script type="importmap">{ "imports": { "lodash": "https://" }}</script>` (or Deno `deno.json` imports map). *Barrel files* (`export *` aggregator `utils/index.js`) trade a single import point (`"pkg/utils"`) for an extra resolution hop and potential bundling cost. `sideEffects: false` in `package.json` (or `"sideEffects": ["*.css"]`) tells bundlers the modules are *pure* — unused named imports can be dropped without evaluating the file for side effects. Without it, `import "./w.css"` or `import "pkg"`'s side effects force keep.

**Bad vs Good:**

```js
// Import map — browser/Deno mapping for bare specifiers:
console.log("Browser importmap:");
console.log('<script type="importmap">{"imports":{"lodash":"https://cdn.skypack.dev/lodash","@pkg/utils":"/js/utils/index.js"}}</script>');
console.log('Then `import _ from "lodash"` works without node_modules — map rewrites bare → URL');

// Barrel vs deep — trade-off:
console.log("Barrel: `export * from './add.js'; export * from './mul.js'` in utils/index.js");
console.log(" Consumer: `import { add } from \"@pkg/utils\"` — ergonomic but bundler must walk barrel");
console.log(" Deep:   `import { add } from \"@pkg/utils/add.js\"` — precise, no barrel walk");
console.log(" Prefer deep for hot paths; barrel OK for small/medium libs where ergonomics wins");

// sideEffects — bundler gate:
console.log("package.json: \"sideEffects\": false → `import {a} from 'pkg'` with unused a can drop entire module");
console.log("With sideEffects unspecified, bundler must keep modules with potential side effects (polyfill, css)");
console.log("For css side-effect imports, list them: \"sideEffects\": [\"*.css\"]");

// Runnable: simulate tree-shaking reachability — barrel drags everything if importer uses barrel without shake:
const barrel = { add: () => 1, mul: () => 2, heavy: () => 3 };
const used = (({ add }) => ({ add }))(barrel); // destructure picks one — but naive bundle without tree-shake still bundles heavy? Bundlers analyze export-level
console.log("With tree-shake: heavy not bundled when unused; without: barrel payload included");

// Import map in Node via --experimental-vm-modules flag or bundler? Not native Node importmap yet (Node 22 no browser importmap)
// Instead show via data URL that import.meta.resolve proposal would resolve specifiers:
// In true ESM: `import.meta.resolve("lodash")` → resolved URL (proposal, Node 22 behind --experimental-vm-modules)
console.log("import.meta.resolve not standard yet — Node 22 exposes `import.meta.resolve()` behind --experimental-vm-modules");
```

### 4) **Common confusion**

- "`./math` without extension is fine in ESM like CJS" — Node CJS appends `.js` via `require.extensions`; Node ESM requires explicit `.js` — `./math` → `ERR_MODULE_NOT_FOUND`.
- "`exports` in `package.json` is just docs" — it *enforces* the import surface; deep imports of non-exported paths throw at runtime.
- "Import maps are Node's resolver" — Node uses `exports`/`imports` + `node_modules` walk; browsers use `<script type="importmap">` for bare specifiers — different mechanisms, same goal. Deno merges them via `deno.json`.
- "`sideEffects: false` is safe always" — only true if modules truly have no global side effects (no `window.X`, `Object.prototype` patching, `fetch` at top-level). Marking a polyfill module as side-effect-free will cause bundler to drop it.

### 5) **Performance note**

Barrel re-export `export *` adds a link-time walk per barrel level (depth). A barrel three deep that aggregates 200 modules costs `O(3×200)` resolution but application start in unbundled native ESM still loads each source file via fetch (HTTP/2). In bundled production, tree-shaking of a pure barrel eliminates unused leaves, but `sideEffects: false` must be present to let the bundler skip evaluating side-effect-free modules. Prefer deep imports for hot leaf modules you never tree-shake (`import { tick } from "./utils/tick.js"`), keep barrels shallow (≤1) for ergonomics.

### 6) **Mentor note**

Have juniors rewrite `import { cfg } from "../../utils/cfg.js"` (deep relative) to `import { cfg } from "#utils/cfg.js"` via `imports` alias — tests whether they distinguish filesystem relative vs package alias. In review, require every relative ESM import to include `.js` extension (lint `import/extensions`), require `node:` prefix for built-ins, require an `exports` map for published packages, and flag barrels >1 depth that aggregate >50 exports without `sideEffects:false`.
