## 4.2. import.meta import attributes and JSON modules

### 1) **`import.meta` — the module's own metadata (`url` resolve helpers env injection)**

**Definition** — `import.meta` is an object each module gets describing its own host context. The standard property is `import.meta.url` — the resolved URL of the current module (e.g. `file:///proj/app/main.mjs` or `https://cdn/pkg/main.js`). It enables `new URL("./data.json", import.meta.url)` to locate sibling assets relative to the current file rather than relative to the process cwd (`process.cwd()`) or host HTML URL. Hosts may add properties (`import.meta.env` in Vite, `import.meta.resolve` proposal), but only `url` is spec-standard and portable.

**What problem it solves / history** — CJS had `__filename`/`__dirname` for file-relative resolution. ESM removed them; without `import.meta.url`, a utility `fetch("./config.json")` would resolve against `location.href` or `process.cwd()` unpredictably. `import.meta.url` restores per-file locality, and `new URL(..., import.meta.url)` is the explicit idiom for "sibling file relative to this module."

**Modern guidance** — use `import.meta.url` for every file-relative asset path in ESM. In Node, derive `__dirname`-equivalent when porting: `const __dirname = path.dirname(new URL(import.meta.url).pathname)` (or `fileURLToPath`). Never hardcode `process.cwd()`-relative paths for sibling resources.

```js
// In real ESM: console.log(import.meta.url)
// Here we simulate because this leaf itself is run as CJS via test harness:
const fakeUrl = "file:///proj/app/main.mjs";
const sibling = new URL("./data.json", fakeUrl);
console.log(sibling.href); // file:///proj/app/data.json — sibling relative to this file

const upOne = new URL("../config.json", fakeUrl);
console.log(upOne.href); // file:///proj/config.json

// Runnable: Node's fileURLToPath dance to recover FS path
const path = require("node:path");
const { fileURLToPath } = require("node:url");
function dirnameFromImportMeta(url) { return path.dirname(fileURLToPath(url)); }
console.log(dirnameFromImportMeta(fakeUrl)); // /proj/app
console.log(dirnameFromImportMeta("file:///tmp/x/y.mjs")); // /tmp/x

// Why not process.cwd():
console.log("process.cwd()", process.cwd(), "— varies by launch dir, not file location");
console.log("import.meta.url", fakeUrl, "— tied to module file, stable");

// Vite-style extra (non-standard) — guard:
console.log("Standard import.meta has only url; host extras like import.meta.env are tool-specific");
```

```js
// Dynamic import specifier building via import.meta.url — pattern:
console.log("await import(new URL(\"./features/a.js\", import.meta.url).href)");
console.log("This builds an absolute URL so dynamic import resolves against this file, not cwd");
```

### 2) **Import attributes/assertions — `with { type: "json" }` vs deprecated `assert`**

**Definition** — import attributes let you tell the host *type* of the imported resource. For JSON modules, Node (17.5+, stable 22) and browsers support `import data from "./config.json" with { type: "json" }` — the `with` clause is the ES2025 standard; earlier proposal `assert { type: "json" }` is deprecated but still accepted in Node `--experimental-json-modules`. `with` is required to block MIME-sniffing: the host checks the attribute matches the fetch/file type before evaluating. Without it, importing JSON as ESM is a SyntaxError/TypeError (JSON is not JS syntax).

**Modern guidance** — always use `with { type: "json" }` (not `assert`) for JSON modules — `assert` emits a deprecation warning on Node 22 and may be removed. For dynamic JSON: `await import("./c.json", { with: { type: "json" } })` or `await import("data:application/json,...") with attributes`.

```js
// Static JSON import shapes — shown as strings (ESM syntax):
const jsonShapes = [
  'import data from "./config.json" with { type: "json" };      // static — data.default or data.* depending on host',
  'import config from "./config.json" with { type: "json" };     // alias',
  'const { default: data } = await import("./config.json", { with: { type: "json" } }); // dynamic',
];
console.log(jsonShapes.join("\n"));

// Runnable: what Node would do — simulate JSON namespace:
const fakeJsonNs = { default: { port: 3000, env: "prod" } };
console.log(fakeJsonNs.default.port); // 3000

// Deprecated assert — still works but warned:
console.log('Deprecated: import x from "./x.json" assert { type: "json" } → use with');
try {
  // Node 22 will warn on assert — simulate deprecation notice
  console.log("Node 22 warning: `assert` is deprecated, use `with` instead (ES2025)");
} catch {}

// Attribute validation — second arg to dynamic import mirrors static with:
console.log('await import("./c.json", { with: { type: "json" } })  // valid');
console.log('await import("./c.json", { assert: { type: "json" } }) // deprecated compat');

// File extension still required: "./config.json" not "./config"
console.log("Module specifier for JSON must include .json extension and with attribute");
```

```js
// BAD: trying to import JSON without attribute — SyntaxError in Node ESM
console.log('BAD: import data from "./config.json"; // SyntaxError: Needs with {type:"json"} in ESM');

// GOOD: explicit attribute + extension
console.log('GOOD: import data from "./config.json" with { type: "json" };');

// GOOD: dynamic path for computed JSON config
console.log('GOOD: const path = "./configs/" + env + ".json"; const {default:d}=await import(path,{with:{type:"json"}});');
```

### 3) **Non-JS modules — CSS WASM workers via import attributes/bundler loaders**

**Definition** — the spec reserves `with { type: ... }` for host-defined module types. Node natively only handles `"json"` (and implicitly `"javascript"`). Other types (`"css"`, WebAssembly) are not native Node ESM without flags/loader; bundlers and browsers (CSS Module Scripts, via `with {type:"css"}` in Chrome) extend this. For WASM, `import wasm from "./mod.wasm"` is not standard without `with {type:...}` / compiler path; workers import via `new Worker(new URL("./worker.js", import.meta.url))`.

**Why it matters** — teaching "import JSON directly" without `with` hides a deprecation (learners copy `assert` from old tutorials) and hides that CSS/WASM imports are *host/loader-dependent*, not portable ESM syntax.

```js
// Host/loader matrix — summarized:
const matrix = [
  "Node 22 ESM native: js (default), json (with {type:\"json\"}) — css/wasm via --experimental-vm-modules or bundler",
  "Browser native: js, json (with), css (Chrome with {type:\"css\"}) — else via importmap + bundler",
  "Bundler (Vite/Webpack/esbuild): js, json (often without with), css, wasm, assets via loader config",
];
console.log(matrix.join("\n"));

// Worker via import.meta.url — portable pattern:
console.log('const worker = new Worker(new URL("./worker.js", import.meta.url)); // file-relative');
console.log('const css = await import("./styles.css", { with: { type: "css" } }); // browser CSS modules');

// Verification: data: URL with json type (Node 22 supports via dynamic import with attribute)
(async () => {
  try {
    const ns = await import("data:application/json,{\"a\":1}", { with: { type: "json" } });
    console.log("data json import", ns.default.a); // 1 where supported
  } catch (e) {
    console.log("data json import fallback:", e.message.slice(0, 60), "→ JSON needs wrapper on older hosts");
  }
})();
```

### 4) **Common confusion**

- "`import.meta` is available everywhere like `globalThis`" — only inside module scope (`type="module"` / `.mjs`); accessing `import.meta` in classic script or CJS throws `SyntaxError: Cannot use 'import.meta' outside a module`.
- "`assert { type: \"json\" }` is still the right syntax" — superseded by `with { type: "json" }` (ES2025); Node still accepts `assert` with deprecation warning — update all `assert` to `with`.
- "JSON modules export named keys directly" — Node's JSON module namespace exposes only `default` (`import data from "./x.json" with {type:"json"}` then `data` is the parsed object); `import { a } from "./x.json"` is not standard — use `data.a`.

### 5) **Performance note**

`import.meta.url` is a string constant per module — accessing it costs a lexical load, no fetch. `new URL(..., import.meta.url)` allocates a `URL` object per call (tens of bytes). For hot file-relative reads (logging config per request), hoist `const cfgUrl = new URL("./cfg.json", import.meta.url).href` at module top-level rather than per-request. JSON `with {type:"json"}` parsing validates JSON at evaluate time; huge JSON (multi-MB) blocks the module evaluation microtask — prefer dynamic `import()` so parse is awaitable and parallelizable.

### 6) **Mentor note**

Have juniors rewrite a `fs.readFileSync("./config.json","utf8")` at module top-level to `import data from "./config.json" with {type:"json"}` — signals file-relative vs cwd-relative reasoning. In review, flag any `assert { type: "json" }` (rename to `with`), any JSON import without extension, and any `import.meta` usage outside module scope (grep `import\.meta` in CJS files).
