## 2.1. Export forms re-exports and aggregators

### 1) **Export declaration forms — named declaration default and list**

**Definition** — `export` declares what the module exposes. The core forms are: *named declaration exports* (`export const x = 1`, `export function add(){}`), *list exports* (`export { x, y }` inside same file, with renames `export { x as y }`), and *default exports* (`export default expr`). `export` may only appear at top level; it creates live bindings over the declared variables/functions/classes, not copies.

**What problem it solves / history** — before ESM, `module.exports` was assignment — tooling had to execute the file to know what it shipped. ESM exports are parse-time enumerable: the host can build `[[ExportNames]]` without evaluating, which enables link-time cycle handling and bundler reachability analysis. `export { x }` after declarations also solves the IIFE "API at the end, reading the surface in one block" ergonomics.

**Modern guidance** — prefer named exports for library surfaces (discoverable, rename-safe, tree-shakable). Reserve `default` for single-primary-value modules (main entry, component) and never combine a rebinding `default` with live-named state (see [2.2](<./2.2. Live bindings why imports are not copies.md>)).

```js
// Named declaration exports — bindings, not snapshots:
export const PI = 3.14; // in real .mjs: export const PI = 3.14
// Simulated here via live object to keep this fence CJS-runnable:
let _PI = 3.14;
let _listX = 10;
const fakeExports = {};
Object.defineProperty(fakeExports, "PI", { get() { return _PI; }, enumerable: true });
Object.defineProperty(fakeExports, "x", { get() { return _listX; }, enumerable: true });
console.log(fakeExports.PI, fakeExports.x); // 3.14 10

// List export with rename — sugar for { x as y } wiring:
let _a = 1;
const exp = {};
Object.defineProperty(exp, "y", { get() { return _a; }, enumerable: true });
console.log("export { a as y } => importer sees y", exp.y); // 1
_a = 2;
console.log(exp.y); // 2 — live

// Default export — syntactic sugar for the name "default":
// `export default class Foo {}` semantically: `class Foo {}; export { Foo as default }` (with hoisting rule)
// `export default 123` is expression, not declaration: exports value 123 live? see 2.2 trap
console.log('export default 123  →  exports { default => 123 }');
console.log('export default function foo(){} — hoisted; export default function(){} anonymous — not hoisted as named');
```

```js
// Default hoisting difference —Runnable conceptual:
try {
  // In ESM: `export default function foo(){}` creates `foo` name hoisted
  // `export default function(){}` has no local binding — only `default`
  // Simulate hoisted vs anonymous:
  function foo() { return "named default export — hoisted"; }
  const _default_anon = function() { return "anon default — not hoisted by name"; };
  console.log(foo(), _default_anon());
} catch (e) { console.log(e.message); }
```

### 2) **Re-export aggregators — `export * from` `export * as ns from` `export { a } from`**

**Definition** — a module may re-expose another's exports without importing them into its own scope: `export * from "./mod.js"` (relay all except `default`), `export * as ns from "./mod.js"` (relay as namespace), `export { a, b as c } from "./mod.js"` (selective), `export { default as Folks } from "./mod.js"` (rename default as named). Re-exports are *not* local bindings — `export { x } from "./x.js"` does not create a local `x` in the re-exporter, so `x` is not usable inside the re-exporter's body.

**Why it matters** — aggregators build *barrels* (`export * from "./add.js"; export * from "./mul.js"` in `math/index.js`) so consumers write `import { add } from "@pkg/math"`. They also keep the graph analyzable — bundlers can trace `export { add } from "./add.js"` without evaluating `index.js`.

```js
// Re-export taxonomy — shown as strings to keep CJS-runnable:
const reexports = [
  'export * from "./add.js";             // relay all named (not default)',
  'export * as math from "./add.js";     // relay as namespace math',
  'export { add } from "./add.js";       // single',
  'export { add as sum } from "./add.js"; // renamed',
  'export { default as Main } from "./Main.js"; // default→named',
  'export { default } from "./Main.js";  // default→default (re-exposed)',
];
console.log(reexports.join("\n"));

// Runnable mental model: re-export is a wiring, not a local binding
// Simulate: a re-exporter does NOT get a local `a`:
let _srcA = 10;
const srcNS = {};
Object.defineProperty(srcNS, "a", { get() { return _srcA; }, enumerable: true });
const reExporterNS = {};
// `export { a } from "./src.js"` → link reExporterNS.a directly to srcNS.a (no local copy)
Object.defineProperty(reExporterNS, "a", { get() { return srcNS.a; }, enumerable: true });
console.log(reExporterNS.a); // 10
_srcA = 20;
console.log(reExporterNS.a); // 20 — live through the chain
// Attempt local use in reExporter would be ReferenceError — no local `a`:
// console.log(a); // ReferenceError in real reExporter
console.log("re-export does not create local binding — a is not defined in re-exporter");

// export * skips default — explicitly:
console.log("export * from './m.js' does NOT re-export `default`; use export {default} or export * as ns");
```

### 3) **Default export quirks — one per module syntactic sugar anonymous hoisting**

**Definition** — a module may have at most one `export default`. `export default 123` is not aDeclaration — the `123` is evaluated once and stored as the `default` binding (live only if the default is an object reference that later mutates, see [2.2](<./2.2. Live bindings why imports are not copies.md>)). Anonymous class/function `export default class {}` does not create a local binding; named `export default class Foo {}` creates both `Foo` (hoisted) and `default`.

```js
// One default per module — second would be SyntaxError:
// export default 1; export default 2; // SyntaxError: Only one default export allowed

// Anonymous vs named default hoisting:
// ESM: `export default class { static x = 1; }` — no binding `ClassName` inside module
// ESM: `export default class Foo {}` — binding `Foo` hoisted, Foo usable before line
function Foo() {} // simulate named default creates Foo binding
console.log(typeof Foo, Foo.name); // function Foo

// Mixing default + named:
console.log("Module can have both default and named:");
console.log('  export default MyLib; export const version = 1;');
console.log('  import MyLib, { version } from "./lib.js";');

// BAD: `export default { a: 1, b: 2 }` hides individual `a`/`b` from tree-shaking
// GOOD: `export const a = 1; export const b = 2;` per-export reachability
console.log("Tree-shaking sees named exports individually but default is one blob");

// Verification: only one default
try {
  new Function('import("x").then(()=>{}); export default 1; export default 2;');
} catch (e) {
  console.log(e.name); // SyntaxError on parse if in module context; in script context import throws first
  console.log("Rule: one default per module — enforce via lint");
}
```

### 4) **Common confusion**

- "`export { x } from './y.js'` gives me a local `x` to use next line" — no, it re-exports without creating a local binding; `x` is not in scope inside the re-exporter. Use `import { x } from './y.js'; export { x }` if you need local `x`.
- "`export *` includes `default`" — it skips `default`; `import * as ns` includes it as `ns.default`, but `export * from` does not forward it. Use `export { default } from` or `export * as ns from` to expose default explicitly.
- "`export default obj = {}` rebinding propagates" — rebinding `default` with a new object does not propagate through the live object reference already captured (`import def` saw the old object identity — see 2.2 trap).

### 5) **Performance note**

Re-export chains (`a.js` re-exports from `b.js` which re-exports from `c.js`) cost a transitive resolution pass at link time. For a single leaf `add`, the resolver walks `a → b → c` to find the declaration for error reporting, even though evaluation runs each module once. Bundlers inline to eliminate hops; in unbundled native ESM, keep barrel depth shallow (≤2) and import leaf directly for hot paths.

### 6) **Mentor note**

Have juniors rewrite a barrel `export * from "./x.js"` as explicit `export { a, b } from "./x.js"` — reveals whether they understand `default` skipping and why explicit subsets tree-shake better. In review, flag `export { x } from` where `x` is later referenced inside same file (will be ReferenceError) and any `export default { ...20 keys }` that should be decomposed into named exports for reachability.
