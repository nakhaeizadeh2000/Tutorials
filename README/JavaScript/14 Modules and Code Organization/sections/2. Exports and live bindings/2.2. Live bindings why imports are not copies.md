## 2.2. Live bindings why imports are not copies

### 1) **The live window — imported bindings track the exporter's variable**

**Definition** — ESM bindings are *live, read-only views*. For `export let count = 0` in `counter.js` and `import { count } from "./counter.js"` in `app.js`, the importer sees whatever `count` currently holds in the exporter — not a snapshot at link time. Spec wiring (ECMA-262 `CreateImportBinding` with `[[IsLive]]`) creates a getter on the importer's environment that forwards to the exporter's slot. Assignment inside the exporter mutates the shared slot and shows through immediately; the exporter may `count++` and importers observing `count` or `ns.count` see the new value in the same microtask.

**What problem it solves / history** — copies would break cycles (each side would freeze the other's incomplete snapshot) and prevent singleton patterns (incrementing a shared counter, registering a service via mutable list). Live bindings make cycles work without executing bodies twice (see [3.2](<../3. Evaluation and circular dependencies/3.2. Circular dependencies and temporal dead zone across cycles.md>)) and let singletons share mutable state without explicit getters.

**Modern guidance** — treat imported names as constants at the call site (assigning throws). Mutate shared state only via exporter functions (`increment()`) not via `export let` exposed raw — still live but encapsulation is clearer.

```js
// Simulated live binding — real ESM does this wiring before evaluation ends
let exporterCount = 0; // `export let count = 0`
const liveNS = {};
Object.defineProperty(liveNS, "count", { get() { return exporterCount; }, enumerable: true });

// importer sees current value:
console.log(liveNS.count); // 0
exporterCount++;
console.log(liveNS.count); // 1 — live

exporterCount = 42;
console.log(liveNS.count); // 42

// GOOD: encapsulate mutation via function so live `let` not directly exposed
let _private = 0;
const api = {};
Object.defineProperty(api, "value", { get() { return _private; }, enumerable: true });
function inc() { _private++; }
console.log(api.value); // 0
inc();
console.log(api.value); // 1

// Imported binding snapshot trap — copy at destructure loses liveness:
let _x = 1;
const ns = {}; Object.defineProperty(ns, "x", { get() { return _x; }, enumerable: true });
const snapshot = ns.x; // snapshot, not live
_x = 2;
console.log(snapshot, ns.x); // 1 2 — snapshot frozen, live still moves
console.log("const local = importedX copies once; bare importedX stays live");
```

### 2) **Mutability surface — `let`/`var` exports are mutable by the exporter only**

**Definition** — the exporter may `let`/`var` exports and reassign them (`export let mode = "dev"; mode = "prod"`); every importer sees the new value. The importer may *not* assign the binding (`mode = "x"` in importer throws `TypeError: Assignment to constant variable`). `export const` is also live (a getter over the underlying slot) but throwing on the exporter's assignment attempt plus initialization once. Object/array bindings give shared identity — mutating `obj.prop` through any importer is shared, but reassigning the binding is not (see §3).

```js
// Exporter's mutability — importer's readonly view
let mode = "dev"; // export let mode
const importView = {};
Object.defineProperty(importView, "mode", {
  get() { return mode; },
  enumerable: true,
});
// Exporter mutates:
mode = "prod";
console.log(importView.mode); // prod

// Importer assignment throws — simulate via strict assignment to imported-like const:
try {
  // In real importer: `import { mode } from "./cfg.js"; mode = "x"; // TypeError`
  // Simulate importer side as const binding:
  Function('"use strict"; const mode = "prod"; mode = "x";')();
} catch (e) {
  console.log(e.name); // TypeError
}

// `const` still live via getter (but exporter cannot reassign — throws at exporter site)
// So live≠mutable — live means getter, mutable means exporter may reassign.

// Object identity sharing — live binding + shared handle
let cfg = { timeout: 100 }; // export let cfg = {timeout:100}
const cfgView = {};
Object.defineProperty(cfgView, "cfg", { get() { return cfg; }, enumerable: true });
console.log(cfgView.cfg.timeout); // 100
cfgView.cfg.timeout = 200; // mutating through shared object — visible to exporter
console.log(cfg.timeout); // 200 — shared handle

// Reassigning `cfg = {timeout:300}` in exporter WOULD change cfgView.cfg live (new identity)
// but mutating previous object's `.timeout` also shared — two different live layers: binding vs object
cfg = { timeout: 300 };
console.log(cfgView.cfg.timeout); // 300 — new object after reassignment
console.log("Live binding tracks which object is bound; object identity shares mutation");
```

```js
// BAD: exporting raw mutable `let` invites any importer to rely on timing:
let _flag = false; // export let ready = false
const nsFlag = {}; Object.defineProperty(nsFlag, "ready", { get(){ return _flag; }, enumerable: true });
console.log(nsFlag.ready); // false — importer may poll, but race on when exporter flips true
_flag = true;
console.log(nsFlag.ready); // true

// GOOD: exporter function gates the state:
let _ready = false;
function setReady(v) { _ready = v; }
function isReady() { return _ready; }
setReady(true);
console.log(isReady()); // true — encapsulation over raw live `let`
```

### 3) **The `default` mutable trap — `export default obj` shares object but rebinding is not propagated as live mutation? Correction: `default` IS live for rebind, but object capture already happened**

**Definition** — `export let obj = {a:1}; obj = {a:2}` propagates to `import {obj} from`. `export default obj` where `obj` was `let obj = {a:1}` and later `obj = {a:2}` *does* propagate via the `default` binding's getter — importers seeing `import def from` do see the new identity. *But* if the importer captured the object identity early (`const local = def` after first `await import`, or `const {default: d} = await import(...)` then `d` snapshotted), or if the default exported an *object literal* (`export default {a:1}` generates a `default` binding over that one object — rebinding via `obj =` elsewhere does not exist), the live trap is about already-held handles, not binding semantics. The teachable trap: creating a default-exported object, then reassigning the local variable holding it without expecting consumers that saved the old reference to see the new one.

**Bad vs Good:**

```js
// Trap: importer saves reference, exporter later rebinds
let obj = { count: 0 }; // export default obj; plus export function set()
const defaultView = {};
Object.defineProperty(defaultView, "default", { get(){ return obj; }, enumerable: true });

// importer captures:
const importerSaved = defaultView.default; // snapshot identity at this moment
console.log(importerSaved.count); // 0
// exporter rebinds to new object:
obj = { count: 99 };
console.log(defaultView.default.count); // 99 — live binding sees new identity
console.log(importerSaved.count); // 0 — old reference stale! the importer saved the old object

// So two live layers confused: live binding (default getter) vs held object identity
console.log("defaultView.default is live (99), but importerSaved still points to old {count:0}");

// GOOD: avoid holding `default` object reference when exporter may rebind; either:
// 1) Always read via live binding (re-import or use accessor function), or
// 2) Mutate the same object instead of rebinding, or 3) Use named exports for mutable identity:
let _cfgCount = 0;
const namedView = {};
Object.defineProperty(namedView, "cfgCount", { get(){ return _cfgCount; }, enumerable: true });
function incCfg(){ _cfgCount++; }
incCfg();
console.log(namedView.cfgCount); // 1 — always fresh via getter, no object identity trap
console.log("Prefer named live bindings for counters; default + rebind is subtle");

// Verification: assigning imported default throws (read-only view)
try {
  Function('"use strict"; const def = {}; def = {};')();
} catch (e) { console.log(e.name); } // TypeError
```

### 4) **Common confusion**

- "`import { x }` copies the value" — opposite: it *never* copies; use `const y = x` to snapshot or `structuredClone(x)` for deep clone when you need isolation.
- "`const` export means immutable across importers" — `const` only prevents *reassignment* of that binding; the object value `export const cfg = {a:1}; cfg.a = 2` still mutates shared state across importers.
- "Live binding means polling is the idiom" — reaching via live getter at top-level during module evaluation before the exporter's initializer has run can hit TDZ (see [3.2](<../3. Evaluation and circular dependencies/3.2. Circular dependencies and temporal dead zone across cycles.md>)). Avoid reading cyclic live bindings synchronously at top level.

### 5) **Performance note**

Live bindings are getters on the module environment, not `Object.defineProperty` per-access. The cost is one indirect load per `import { x }` access — same as a local `let` get in JIT — no allocation per use. Snapshotting (`const localX = x`) removes that indirection for hot loops but loses liveness; use when the value is known to be stable (e.g., pure constants). Holding `default` objects and rebind-checking each loop iteration adds branch cost — prefer named scalar bindings for tight loops.

### 6) **Mentor note**

Give the `count` kata: `// counter.js: export let count = 0; export function inc(){ count++; }` — ask "after `inc(); inc();` what does `import {count} from "./counter.js"` see? (2)." Those answering "0" carry copy folklore. In review, prohibit `importedName = ...` (TypeError) and require that any `export default` that may be reassigned be replaced by `export let`/`export const` named bindings or accessor functions — call out the saved-handle staleness bug in [7.1](<../7.
