## 1.1. Script vs module and the evolution from IIFEs to ESM

### 1) **Script vs module contracts — strict scoped evaluated once**

**Definition** — a *classic script* (`<script>` without `type="module"`, or `node script.js` when not in module mode) shares the global scope: `var`/function declarations become `globalThis` properties, top-level `this === globalThis`, code is not strict unless you opt in, and every `<script>` tag re-runs independently. An *ES module* (ESM) — `type="module"` in browsers, `.mjs` or `.js` with `"type":"module"` in Node — has its own lexical top-level scope, is *always* strict, `this === undefined` at top level, and is evaluated once per resolved specifier even if imported many times (the module map guarantee — see [3.1](<../3. Evaluation and circular dependencies/3.1. Evaluation order single evaluation and hoisting.md>)).

**What problem it solves / history** — scripts made every file a global namespace: `var config` in one file stomped same name in another ([Variables scope](<../../../04 Variables Scope and Closures/sections/4. Top level scopes scripts modules and eval/4.1. Script vs module top level globalThis and the declarative record.md>)). Modules fix isolation by default — `export` is the only escape hatch — and static structure lets tools analyze dependencies without running code (tree-shaking, cycles, pre-loading).

**Modern guidance** — author new code as ESM. Only produce classic-script output via a bundler's build step. In Node, choose the file-level contract explicitly via extension or package `type` — never rely on implicit CJS for `.js` you intend as ESM (see [5.3](<../5. CommonJS interop and resolution/5.3. Specifiers package.json exports import maps and organization.md>)).

```js
// Classic-script semantics simulated via indirect eval — Node .js files are CJS-wrapped
// and do NOT leak var to globalThis unless you force script mode:
(0, eval)(`var scriptVar = 1;`);
console.log(typeof globalThis.scriptVar, globalThis.scriptVar); // number 1 — leaked
console.log(typeof scriptVar === "undefined" ? "scriptVar not in module scope" : scriptVar);
// CJS module-local var — file-private even with `var`:
var moduleVar = 2;
console.log(typeof globalThis.moduleVar, moduleVar); // undefined 2

// ESM contract (run this as data: URL ESM to verify; in CJS this file, we simulate):
// `import()` of an ESM data URL runs in true module scope:
const esmSrc = `export const x = 1; console.log(this === undefined ? "esm this undefined" : "bad");`;
console.log("esmSrc prepared", esmSrc.slice(0, 20) + "...");

// Detection — file type matters more than content:
console.log(JSON.stringify({ cjsThisIsModuleExports: typeof module !== "undefined" && typeof exports !== "undefined" }));
console.log("Node package type defaults to commonjs unless package.json sets \"type\":\"module\" — then bare .js is ESM");
```

```js
// export const tick = () => ++counter;
// var counter = 0;

// [multi-file illustration — ESM: file 2 of 2] app.mjs

```

### 2) **The ancestry — IIFE → CommonJS/AMD → ESM**

**Definition** — before modules, teams faked privacy with *IIFEs* — `(function(){ var privateState; ... }())` exposing only `window.API` ([IIFE ancestry](<../../../05 Functions Deep Dive/sections/4. First-class and execution patterns/4.2. IIFE module ancestry and modern replacements.md>)). Node popularized *CommonJS* (`require`/`module.exports`) in 2009 — synchronous, wrapping each file in `(exports, require, module, __filename, __dirname) => {}`. Browsers invented AMD `define()` (async ordering). ESM (ES2015, shipped browsers 2017, Node behind flag 2018, unflagged 2020) unified the shape with static syntax the engine can parse before evaluation.

| Era | Shape | Isolation | Loading | Analyzability |
|-----|-------|-----------|---------|----------------|
| IIFE | `(function(){...}())` + `window.X` | closure only, globals leak by convention | tags in order, manual | none — bundler must run code |
| CommonJS | `require("./x")` / `module.exports.y` | wrapper-function scope | sync, cached per filename | runtime — conditional `require` possible |
| AMD | `define(["./x"], (x)=>{})` | factory function | async callback | runtime factory |
| ESM | `import x from "./x.js"` / `export y` | true lexical module scope, strict always | async graph, preload-friendly | static — specifier must be string literal |

**Why ESM won** — static structure gives the host three powers CJS cannot: *link* before evaluate (cycles with live bindings), *tree-shake* (export-by-export reachability without execution), and *parallel prefetch* (browser can discover the full graph from `import` statements during parse, before any body runs).

```js
// IIFE privacy then CJS wrapping — the mental lineage
// IIFE (legacy):
const IIFEMod = (() => { let count = 0; return { inc(){ return ++count; } }; })();
console.log(IIFEMod.inc(), IIFEMod.inc()); // 1 2 — closure privacy, still lives in global scope

// CJS wrapper conceptual (what Node does to every .js when type: commonjs):
// File `util.js` contents — conceptually wrapped before evaluation:
// (function(exports, require, module, __filename, __dirname) {
//   let hidden = 1; exports.get = () => hidden++;
// })(exports, require, module, __filename, __dirname);
// So `var` does NOT become globalThis — it's function-scoped wrapper arg scope.

// ESM contrast — static and strict by default:
// In CJS, sloppy `undeclared = 1` creates globalThis.undeclared (non-strict wrapper still sloppy unless opted in)
// In ESM, same line throws ReferenceError — always strict, no implicit globals.
try { (0, eval)(`"use strict"; undeclared = 1;`); } catch (e) { console.log(e.name); } // ReferenceError
```

### 3) **What ESM fixed — static structure enables tree-shaking and cycles**

**Definition** — *static* means the set of imports/exports can be enumerated from the source text without evaluation: specifiers are string literals at top level, `import` cannot be inside `if`, and `export` names are declared identifiers. The host performs *Linking* (wire all import bindings to their exported bindings) before *Evaluation* (run bodies). This two-phase split is why cyclic `import`s can resolve (bindings exist before bodies finish — [3.2](<../3. Evaluation and circular dependencies/3.2. Circular dependencies and temporal dead zone across cycles.md>)) and why bundlers can drop unused exports without executing code.

**Bad → Good** — choosing between dynamic flexibility and analyzability:

```js
// BAD (CJS-friendly but non-statically-analyzable) — ESM forbids this:
let name = "./math.js";
// if (useAlt) { import { add } from name; } // SyntaxError in ESM — must be literal
// GOOD: static import for analyzable path, dynamic import() for conditional:
console.log("static import (analyzable): import { add } from \"./math.js\"");
console.log("dynamic import (conditional): await import(name)");

// BAD: re-exporting via runtime assignment hides from tree-shaker
// CJS: module.exports.all = { ...utils, ...helpers } // black box to tooling
// GOOD: barrel re-exports are explicit per-export
console.log("export { add } from \"./math.js\"  // visible to link + tree-shake");
console.log("export * as ns from \"./math.js\"  // also visible — ns namespace");

// Verification: ESM `import` is hoisted like declarations — bindings exist before body:
console.log("Module linking wires bindings before evaluation — an import can be used");
console.log("before its textual line in the sense that the binding is already created");
console.log("but the exporter's initializer may not yet have run (TDZ on cycles) — see 3.2");

// Performance note — single evaluation + static graph:
console.log("Because the module map is keyed by resolved specifier, `import 'x'` 10 times");
console.log("evaluates `x` once and reuses the namespace — side effects run once (see 3.1)");
```

### 4) **Common confusion**

- "`.js` is ESM if it uses `import`" — resolution cares about `package.json "type"` and extension (`.mjs` = ESM, `.cjs` = CJS, bare `.js` follows `type`), not content until parse. A file with `import` under CJS `type` throws `SyntaxError: Cannot use import statement outside a module` rather than switching mode.
- "ESM is just CJS with nicer syntax" — evaluation model differs: CJS `require` runs synchronously on demand with per-file `module.exports` objects; ESM links live bindings before evaluation and caches namespaces globally — cycles, `await` ordering, and tree-shaking behave differently.
- "Modules make bundles obsolete" — browsers now handle native `import` + import maps, but bundlers still shard chunks for `import()` code splitting and apply tree-shaking + minification for production.

### 5) **Performance note**

Module evaluation is once; repeated `import "x"` costs a map lookup, not re-execution. Bare re-imports are nearly free after the first evaluation. Over-barreling (re-exporting all via `export *` through multiple layers) costs at link time — each re-export must be resolved transitively — but the per-namespace overhead is one exotic object per evaluation, not per importer. For hot paths, import the deep leaf directly (`import { add } from "./math.js"`) rather than through a three-deep barrel that aggregates 200 exports, then let the bundler inline.

### 6) **Mentor note**

Have juniors predict whether `var x = 1` at the top of an ESM file becomes `globalThis.x` (no) vs same line in a classic script (yes) — failure signals missing contract. In review, flag any `.js` file that mixes `require` and `import` without an ESM-CJS bridge (see [5.2](<../5. CommonJS interop and resolution/5.2. ESM and CJS interop dual packages and migration.md>)), and require explicit `.mjs`/`.cjs` or package `type` when a repo mixes both systems.
