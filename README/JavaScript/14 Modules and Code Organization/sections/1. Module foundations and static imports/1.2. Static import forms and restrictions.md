## 1.2. Static import forms and restrictions

### 1) **The six import shapes — side-effect default named renamed namespace mixed**

**Definition** — `import` is declarative and static: every form declares at parse time which bindings the module depends on. The six canonical shapes are: side-effect-only (`import "./init.js"`), default import (`import def from "./m.js"`), named imports (`import { a, b } from "./m.js"`), renamed named (`import { a as local }`), namespace (`import * as ns from "./m.js"`), and combined default+named (`import def, { a } from "./m.js"`). Namespace imports bind a Module Namespace Exotic Object whose properties are the live exports — you cannot destructure the namespace (access is `ns.a`), and the object is sealed.

**What problem it solves / history** — CJS `const x = require(cond ? "./a" : "./b")` is dynamic — the graph is only knowable by running code. ESM chose parse-time visibility so hosts can *link* without *evaluate*, enabling cycles, static type checking, and tooling. The cost is explicitness: conditional loading must use `import()` ([4.1](<../4. Dynamic import and meta/4.1. Dynamic import async loading and code splitting.md>)).

**Modern guidance** — prefer named imports for discoverability and tree-shaking (`import { add }`) over default for library surfaces; use namespace only when you intend to enumerate (`Object.keys(ns)` is not the right way — use dynamic inspection intentionally). Reserve side-effect imports for polyfills/registry code and document why they exist.

```js
// All six forms illustrated as strings — ESM syntax (run as .mjs or bundle).
// Shown here as string literals so this leaf's fences stay CJS-runnable:
const forms = [
  'import "./polyfill.js";                // 1 — side-effect (module runs, no bindings)',
  'import def from "./mod.js";            // 2 — default',
  'import { a, b } from "./mod.js";       // 3 — named',
  'import { a as local } from "./mod.js"; // 4 — renamed',
  'import * as ns from "./mod.js";        // 5 — namespace (ns.a, ns.default)',
  'import def, { a } from "./mod.js";     // 6 — mixed',
];
console.log(forms.join("\n"));

// Runnable: what a namespace object feels like (ECMA-262 Module Namespace Exotic Object)
// Simulate the frozen-property behavior:
const fakeNs = Object.preventExtensions({ a: 1, b: 2, __proto__: null });
console.log(Object.isExtensible(fakeNs)); // false — real ns is also not extensible
console.log(Object.getOwnPropertyDescriptor(fakeNs, "a")); // {value:1,writable:true,enumerable:true,configurable:false} alike

// Named import renaming is just local binding, not export rename:
let a = 10;
const local = a; // alias — `import { a as local }` behaves like this at link time
console.log(local); // 10

// Default is just the export named "default" — sugar for flexibility:
console.log('import def from "./x.js"  ===  import { default as def } from "./x.js"');
```

```js
// Side-effect import — why it exists and how to spot it
console.log("Side-effect import runs the target's top-level code once (3.1) — e.g. registers a custom element");
console.log("Module evaluation is still once even if side-effect imported from 5 places");
console.log("Flag side-effect-only imports in review — they hide coupling; prefer explicit exported API");
```

### 2) **Static means static — top-level only string-literal specifiers hoisted like declarations**

**Definition** — an `import` declaration may appear only at the top level of a module (not inside `if`, functions, blocks, or `try`). Specifiers must be string literals (`"./x.js"`), not computed (`import x from y` is not grammar). Declarations are *hoisted* in effect: the host links all imports before evaluating any module body, so an `import` can textually appear at the file bottom yet its bindings are available throughout the file (mirrors function hoisting but for links). Violations throw SyntaxError at parse, not at runtime.

**Bad vs Good:**

```js
// BAD — attempted conditional / block import → SyntaxError at parse in ESM
const cond = Math.random() > 0.5;
console.log("If this were real ESM, the following would be a SyntaxError, not runtime branching:");
// if (cond) { import { a } from "./a.js"; } // ← SyntaxError
// for(let i=0;i<2;i++) import "./x.js";     // ← SyntaxError
// const m = "./a.js"; import * as ns from m; // ← SyntaxError (specifier must be literal)

// GOOD — static path for analyzable deps, dynamic import() for conditional:
console.log("GOOD canonical patterns:");
console.log('  import { a } from "./a.js"; // always — analyzable');
console.log('  if (cond) { const { a } = await import("./a.js"); } // conditional — dynamic');
console.log('  const ns = await import(`./lang/${locale}.js`); // computed — dynamic');

// Runnable proof that host-level hoisting is parse-time, not line-order:
// Node ESM would see this as: all imports linked before any body runs.
// Simulate ordering: bindings logically exist before statement 10:
let linkingDone = true;
console.log("linkingDone before body?", linkingDone); // true — concept

// SyntaxError check via runtime parsing of an ESM snippet (Node will reject it)
try {
  // Use Function constructor is NOT module context — so we test ESM syntax via dynamic import of data URL
  // Data URL with SyntaxError — Node will reject eagerly
  // This `import()` data approach itself is valid dynamic import (see 4.1)
  // Instead, demonstrate via `new Function` emulation that `import` is illegal in non-module:
  new Function('import x from "y"'); // throws SyntaxError in script context
} catch (e) {
  console.log(e.name, e.message.slice(0, 40)); // SyntaxError ... Cannot use import statement outside a module
}
```

```js
// Import hoisted above use — conceptual demonstration
// Real ESM (two views):
// math.mjs:   export const add = (a,b)=>a+b;
// app.mjs:    console.log(add(1,2)); import { add } from "./math.mjs"; // still works — binding hoisted
console.log("In ESM, the order of import statements among themselves does not dictate evaluation order");
console.log("Evaluation order is depth-first post-order (see 3.1), but linking is before any evaluation");
```

### 3) **Bindings not values — importing creates a live read-only view**

**Definition** — `import { count } from "./counter.js"` where `counter.js` does `export let count = 0` does *not* copy `0`. It creates a binding that always reads `count`'s current value via a getter over the exporter's environment ([2.2](<../2. Exports and live bindings/2.2. Live bindings why imports are not copies.md>)). Imported bindings are read-only views: `count++` inside the importer throws `TypeError: Assignment to constant variable`. The module namespace object `ns` similarly exposes getters, not data copies, and is not extensible (`Object.isExtensible(ns) === false`, no `Object.defineProperty` adding).

```js
// Simulated live binding via getter — what the spec wiring feels like
let exporterCount = 0;
const ns = {};
Object.defineProperty(ns, "count", {
  get() { return exporterCount; },
  enumerable: true,
  configurable: false,
});
// importer view:
console.log(ns.count); // 0
exporterCount++;
console.log(ns.count); // 1 — live! importer sees exporter's mutation

// Imported binding is read-only — simulate:
try {
  // imagine: import { count } from "./counter.js"; count = 1;
  // would throw TypeError at runtime (assignment to import)
  Function('"use strict"; let count=0; count = 1; console.log("assign ok")')();
  // To show readonly throw, we mimic via caught import operation:
  const frozen = Object.defineProperty({}, "x", { value: 1, writable: false, configurable: false });
  frozen.x = 2; // sloppy would silent, strict throws — so use define check
  console.log("direct frozen write check", Object.getOwnPropertyDescriptor(frozen, "x").writable);
} catch (e) { console.log(e.name); }

// ESM caller would see: TypeError: Assignment to constant variable. on `count++` against an import

// BAD: two modules each do `import { config } from "./cfg.js"; config.timeout = 5000` —
// they share the same object identity (live object reference); mutation is shared across importers!
// That's "live object sharing" distinct from "live binding" — see 2.2 for full table.

// Verification that namespace is sealed:
const ns2 = Object.preventExtensions({ default: {}, __proto__: null });
console.log(Object.isExtensible(ns2)); // false — mirrors spec ns exotic
try { Object.defineProperty(ns2, "newProp", { value: 1 }); } catch (e) { console.log(e.name); } // TypeError in strict
```

### 4) **Common confusion**

- "`import { x }` makes a snapshot" — no, it's a live getter; `x` reflects later mutations in the exporter. Snapshotting requires destructuring into a new variable (`const local = x` copies at that moment, but later `x` still moves while `local` stays).
- "Namespace `import * as ns` can be spread `...ns`" — no; namespace exotic intentionally blocks spread/deconstruction patterns that hide static structure. Access `ns.named` explicitly.
- "`import` is conditionally executed like a statement" — it is linked before any code runs; the `import` line's textual position does not imply execution order (evaluation order is depth-first post-order, not textual order — see 3.1).

### 5) **Performance note**

Namespace creation is one Module Namespace Exotic Object per evaluation, regardless of how many importers reference it. `import * as ns` and individual `import {a,b}` have identical post-link cost; choose for readability, not perf. The static graph cost is at link time (`O(exports + imports + re-exports)` walk). A three-deep barrel that re-exports 200 names costs a transitive walk but not a per-importer N× overhead — still prefer deep imports (`import { add } from "./math/add.js"`) over `import { add } from "@lib"` barrel for hot paths to avoid dragging extra transitive resolution.
