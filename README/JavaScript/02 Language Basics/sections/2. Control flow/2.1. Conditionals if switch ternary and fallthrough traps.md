## 2.1. Conditionals: if, switch, ternary (fall-through traps included)

### 1) **switch matches one value with strict equality**

**Definition** — `if/else` evaluates arbitrary conditions; `switch` compares one expression against `case` values using `===` semantics; the ternary operator is the *expression* form of a two-way branch.

```js
// if/else: compound and range conditions
function grade(score) {
  if (score >= 90) return "A";
  if (score >= 80) return "B";
  return "F";
}

// switch: one value, discrete cases
function httpVerbLabel(verb) {
  switch (verb) {
    case "GET":
    case "HEAD":          // intentional grouping — comment it!
      return "read";
    case "POST":
    case "PUT":
      return "write";
    default:
      return "other";
  }
}
console.log(httpVerbLabel("HEAD"), httpVerbLabel("PATCH")); // read other
```

- Ranges in switch require gymnastics (`case true:` tricks or `switch (true)`); prefer if-chains or lookup structures instead.
- Many switches are really **data lookups** — an object/Map literal is flatter and testable:

```js
const labels = { GET: "read", HEAD: "read", POST: "write", PUT: "write" };
const labelOf = verb => labels[verb] ?? "other";
```

### 2) **Fall-through is a loaded weapon**

Omitting `break` silently executes the next case's body:

```js
// BAD — deliberate demonstration of the trap:
function bad(level) {
  let msg = "";
  switch (level) {
    case 1: msg += "[1] ";
    case 2: msg += "[2] ";   // level 1 falls through here!
      break;
    case 3: msg += "[3] ";
  }
  return msg;
}
console.log(bad(1)); // "[1] [2] " — almost never what anyone meant
```

- ESLint's `no-fallthrough` flags accidental fall-through; intentional grouping should carry a `// falls through` comment so reviewers can distinguish intent from bug.

### 3) **Ternary produces values, not actions**

```js
// Good: choosing between values
const speed = isDraft ? 0 : limit;

// BAD — action-chaining ternary; use if:
// isReady ? start() : queue();
```

- Nested ternaries beyond one level (`a ? b ? c : d : e`) consistently produce misreads — convert to early-return functions.

### 4) **Common confusion**

- "switch is faster than if-chains" — historically for dense integer cases; modern JITs make this noise. Choose by readability.
- `case` values need not be constants (any expression works, evaluated top-down until first match) — legal but rarely wise.
- Missing `default` on user-input-driven switches hides unhandled states; either handle or explicitly throw in default.

### 5) **Mentor note**

Review heuristic: more than ~6 cases → table/map; any case without break → must have comment; ternary with side effects → rewrite as statement. These three rules eliminate most conditional review churn.
