## 3.2. Equality: loose vs strict (and when either is safe)

### 1) **=== compares type AND value without conversion**

**Definition** — strict equality (`===`) returns `true` only when operands share type and value. No coercion, no surprises beyond two special cases:

```js
console.log(1 === 1, 1 === "1");        // true false — type gate first
console.log(NaN === NaN);               // false — NaN is defined as unequal to everything
console.log(Object.is(NaN, NaN));       // true — Object.is fixes exactly that
console.log(0 === -0);                  // true — signed zero collapses
console.log(Object.is(0, -0));          // false — and distinguishes them (rarely needed)
const a = { x: 1 }, b = { x: 1 };
console.log(a === b, a === a);          // false true — objects compare by reference
```

- Reference semantics for objects: "equality" means "same object", not "same contents" — structural comparison must be explicit (`JSON.stringify` hacks are lossy; write/choose a deep-equal function).

### 2) **== coerces first**

Loose equality applies the Abstract Equality Algorithm — operand-type-dependent conversions before comparison. Its outcomes are why teams ban it:

```js
console.log("0" == false);   // true  — booleans coerce to number first: false → 0
console.log("" == 0);        // true  — empty string coerces to 0
console.log(null == undefined); // true  — the ONE sanctioned pairing
console.log([] == ![]);      // true  — [] → "" → 0; ![] → false → 0 — absurd but lawful
```

- The algorithm isn't random — it's deterministic and spec'd — but it's memorization-hostile, which is the practical problem.
- **The two sanctioned uses of `==`**:
  1. `x == null` — matches both `null` and `undefined` in one test.
  2. Nothing else.

### 3) **Default to strict everywhere**

```js
// Enforce mechanically:
// ESLint: "eqeqeq": ["error", "always", { null: "ignore" }]
const input = null;
if (input == null) console.log("missing"); // allowed shorthand with eqeqeq null-ignore

if (input === null || input === undefined) console.log("equivalent explicit form");
```

- `Object.is` for the rare NaN/sign-sensitive check; `Array.prototype.includes` uses SameValueZero (NaN-friendly) internally — another reason it beats `indexOf`.

### 4) **Common confusion**

- "=== compares deeply" — no; object identity only.
- "`==` to boolean checks truthiness" — no; `x == true` coerces *x* to number (`[2] == true` is false!). Truthiness tests use `if (x)`.
- `NaN !== NaN` being "a bug" — it follows IEEE 754; JS inherits it. Use `Number.isNaN(x)` to test.

### 5) **Mentor note**

Interview probe: ask for `[] == ![]` reasoning. Strong candidates narrate both coercion chains without looking it up; excellent ones conclude "this is why my team runs `eqeqeq`". Teach juniors the one-liner rule and defer algorithm details to the coercion domain.
