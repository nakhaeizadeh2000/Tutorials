## 1.1. Statements, expressions, and semicolons (ASI reality)

### 1) **Statements act; expressions produce values**

**Definition** — an *expression* evaluates to a value; a *statement* performs an action. Everything you write is one or the other, and many constructs accept both.

```js
// Expression: produces a value (usable anywhere a value fits)
const sum = 2 + 3;                 // 5
const label = sum > 4 ? "big" : "small"; // ternary is an expression

// Statement: performs control flow — no value
if (sum > 4) {
  console.log("big");
}

// Expression-oriented style: functions return expressions,
// avoiding imperative accumulation:
const describe = n => n > 100 ? "large" : n > 10 ? "medium" : "small";
console.log(describe(42)); // medium
```

- Practical payoff: `x && y`, `cond ? a : b`, IIFEs, and arrow bodies all exploit "expressions everywhere".

### 2) **ASI has precise rules (not folklore)**

**Automatic Semicolon Insertion** inserts a semicolon when the next token *cannot* continue the current statement. The risky set is small and learnable:

| Hazard | Example | What happens |
|--------|---------|--------------|
| Line starts with `(` | `a = b` ⏎ `(f)()` | Parsed as `a = b(f)()` |
| Line starts with `[` | `a = b` ⏎ `[1]` | Parsed as `a = b[1]` |
| Line starts with `` ` `` | `a = b` ⏎ `` `text` `` | Parsed as tagged template |
| `return/throw/break/continue` + newline | `return` ⏎ `{}` | Returns `undefined` (restricted production) |
| Postfix `++`/`--` on next line | `a` ⏎ `++b` | Parses as `a; ++b` |

```js
// The classic production bug:
function getStatus() {
  return        // ASI: returns undefined HERE
  {
    ok: true,   // dead code — object literal never returned
  };
}
console.log(getStatus()); // undefined

// Correct:
function getStatusFixed() {
  return {
    ok: true,
  };
}
console.log(getStatusFixed()); // { ok: true }
```

### 3) **Mechanical consistency beats personal taste**

Both policies work — semicolons always, or none with formatter discipline (Prettier's no-semi style handles leading `(`/`[` hazards by prepending semicolons). Pick one, enforce via tooling, stop debating.

### 4) **Common confusion**

- "JS doesn't need semicolons" / "missing semicolons crash randomly" — both wrong; rules above are deterministic.
- `no-return-await`, lint rules etc. can't catch ASI logic errors reliably — only formatting policy prevents them.
- Semicolons in `for(;;)` headers are not optional — that's grammar, not ASI territory.

### 5) **Mentor note**

Teach ASI as a five-row hazard table (above), then mandate a formatter. Candidates who can recite the table but ship unformatted code have learned trivia, not engineering.
