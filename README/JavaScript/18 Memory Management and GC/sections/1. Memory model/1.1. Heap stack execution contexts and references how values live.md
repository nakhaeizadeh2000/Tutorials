## 1.1. Heap stack execution contexts and references how values live

### 1) **Definition**

The V8 heap holds every object, array, function, closure environment, and boxed value that can outlive the current call. The call stack holds execution contexts — each context has its local bindings and a slot for its `this` and return address — and it is unwound on return. References are not values: a variable or object field stores a pointer (an edge) into the heap graph, and copying that variable copies the edge, not the subgraph.

```js
// Two variables, one object — copying the edge, not the object.
const a = { x: 1, nested: { y: 2 } };
const b = a;                // b points to the same heap node as a
b.x = 99;
console.log(a.x, b === a);  // 99 true  — mutation via either edge reaches the same node

const c = { ...a, nested: a.nested }; // shallow copy: new root object, shared nested edge
c.nested.y = 77;
console.log(a.nested.y);    // 77 — outer copied, inner still shared

// Primitives are immutable values; reassigning a binding swings the edge.
let n = 7;
let m = n;  // m receives the value 7, not a reference to n's slot
n = 8;
console.log(m, n); // 7 8
```

***What problem it solves / history*** — early JS engines (SpiderMonkey 1.x, JScript) documented "primitives on stack, objects on heap" as if it were the language rule. The spec never says that; it describes an *object graph* abstracted away from memory. As closures and `eval` shipped, "stack vs heap" folklore misled developers into thinking `delete x` freed memory or that block exit always freed objects. The real model is *reachability*, which arrived fully with ES2015 closure refinements and ES2021 weak refs.

***Modern guidance*** — as of the ECMAScript 2026 era (Node 24 Active LTS, 22 Maintenance): reason about *edges* and *liveness*, not byte addresses. Assume nothing about where V8 places a value — engine optimizations (escape analysis, allocation folding, SMI tagging) can keep short-lived objects stack-allocated or scalars in registers.

### 2) **The three zones: heap, stack, host queues**

```js
function outer(bigTag) {
  // Execution context for outer() is pushed on the stack.
  const big = { tag: bigTag, payload: new Array(100).fill("x") };
  console.log("inside outer, big.tag:", big.tag); // heap object, reachable via the context's `big` slot
  return function inner() { return big.tag; };    // inner closes over the context
}
let fn = outer("hello");
console.log(fn()); // hello — context for outer is gone but its heap env survives via fn
fn = null;         // that heap env is now unreachable
```

- *Stack*: LIFO chain of execution contexts. Each context holds argument slots, local bindings, and internal state. Return pops it; the locals die unless another heap edge (closure, registry) keeps the environment object.
- *Heap*: a graph of objects linked by references (properties, elements, `[[Prototype]]`, closure environment slots, `Map` entries, promise capability queues). Size is reported by `process.memoryUsage().heapUsed` and `v8.getHeapStatistics()`.
- *Host queues*: the event loop's micro/macrotask queues and timer registries are GC roots held outside JS heap. A queued callback is reachable even if no user variable points at it.

```js
// Heap size is observable, but the spec never says when collection happens.
console.log(typeof process !== "undefined" && typeof process.memoryUsage === "function"
  ? `heapUsed ~${Math.round(process.memoryUsage().heapUsed / 1024)} KiB`
  : "process.memoryUsage not available on this host");
```

### 3) **Copying references vs cloning graphs**

```js
// Array assignment copies the reference; mutation crosses the alias.
const xs = [1, 2, 3];
const ys = xs;
ys.push(4);
console.log(xs, ys, xs === ys); // [1,2,3,4] [1,2,3,4] true

// Structured clone vs JSON vs shallow spread — three different graph policies.
const original = { a: 1, b: { c: 2 }, d: new Date("2026-01-01") };
const viaSpread = { ...original };               // shallow — b shared, Date shared
const viaJSON = JSON.parse(JSON.stringify(original)); // JSON: Date becomes string, prototype gone
viaJSON.b.c = 99;
console.log(original.b.c, viaSpread.b === original.b, typeof viaJSON.d); // 2 true string

const viaClone = typeof structuredClone === "function" ? structuredClone(original) : null;
if (viaClone) {
  viaClone.b.c = 55;
  console.log(original.b.c, viaClone.b === original.b, viaClone.d instanceof Date); // 2 false true
}
```

- Shallow spread/clone: new container node, same child edges.
- `structuredClone` (ES2021 HTML, Node 17+): deep clone per HTML structured-clone algorithm — copies `Date`/`Map`/`Set`/`ArrayBuffer` graphs faithfully but drops functions/`WeakMap` and loses class prototype — see [JSON §5.1](<../../../16 JSON Serialization and Data Exchange/sections/5. Beyond JSON structuredClone and data exchange/5.1. structuredClone deep cloning and limitations.md>) for the full table.
- No language operator "frees" — you cut edges; the collector reclaims unreachable nodes later. `delete obj.prop` removes the slot edge; `obj.prop = null` swings the edge to `null`.

### 4) **Common confusion**

- "`delete` frees memory" — `delete` removes a property slot so the target may become unreachable, but `delete` itself is just an edge removal plus hidden-class transition to dictionary mode (see [GC pressure §2.2](<../2. GC engine and allocation/2.2. Allocation hidden classes inline caches and GC pressure.md>)). Prefer `obj.field = null` or `Map.delete(key)` when shape matters.
- "Primitives are always stack, objects always heap" — V8 smis (small ints) are tagged pointers kept inline; escape analysis can keep object literals on stack frames when they never escape; `BigInt` storage varies. Treat "stack vs heap" as a mental model, not a layout promise.
- "Scope exit frees" — leaving a block nulls the locals on the stack, but any surviving closure/environment object (see [Lifetimes §3.1](<../3. Lifetimes what stays alive/3.1. Closures timers listeners maps and the lifetime of a graph.md>)) keeps its captured graph in the heap.

### 5) **Performance note**

Heap graphs are cheap per edge but expensive per policy violation. Two habits keep allocation pressure low without sacrificing readability:

```js
// BAD: allocates a new mapping + object per keystroke-style call.
function handleBad(events) { return events.map((e) => ({ id: e.id })); }

// GOOD: reuse a pre-allocated or shared shape when it matters on a hot path
// (but keep it boxed to this module — leaking the buffer reverses the win).
function handleGood(events, out) {
  out.length = 0;
  for (const e of events) out.push({ id: e.id });
  return out;
}
const out = [];
console.log(handleGood([{ id: 1 }, { id: 2 }], out)); // [ { id: 1 }, { id: 2 } ]
```

Shape and pressure details belong to [§2.2](<../2. GC engine and allocation/2.2. Allocation hidden classes inline caches and GC pressure.md>); this leaf only frames the split: *heap vs stack is an edge graph, not two memory pools you can reason about statically*.

### 6) **Mentor note**

Have juniors draw a graph: nodes are heap objects, edges are variables/fields/prototype links/closure slots/queue entries. Review prompt: *"if I null this one edge, is there still another path from a root?"* That question replaces "does this variable go out of scope?" Senior check: verify the edge list isn't folklore — find the real retaining edge via a heap snapshot (taught in [§5.1](<../5. Measuring and preventing leaks/5.1. Measuring memory heap snapshots allocation timeline and inspector.md>)).
