## 5.1. Measuring memory heap snapshots allocation timeline and inspector

### 1) **Two snapshots, diff, retaining paths — the reliable leak workflow**

Never read a single heap number and call it "a leak." Growth compounds across events; a single large snapshot on a fresh start is not evidence. Capture two snapshots around a repeatable action (e.g., 10 mutations), diff object counts/sizes, and follow retaining paths on the delta.

```js
// Report what `process` and V8 expose — for lab consoles, not product metrics.
function report() {
  const pm = typeof process !== "undefined" && process.memoryUsage ? process.memoryUsage() : null;
  const vm = (() => { try { return require("node:v8").getHeapStatistics(); } catch { return null; } })();
  if (pm) console.log(`rss ${Math.round(pm.rss / 1024)} heapUsed ${Math.round(pm.heapUsed / 1024)} arrayBuffers ${Math.round((pm.arrayBuffers ?? 0) / 1024)} ext ${Math.round((pm.external ?? 0) / 1024)} (KiB)`);
  if (vm) console.log(`v8 totalHeapSize ${Math.round(vm.total_heap_size / 1024)} used ${Math.round(vm.used_heap_size / 1024)} (KiB)`);
}
report();
```

Toolchain (as of ECMAScript 2026 era, Node 22 LTS / 24 Current, Chrome 130+):

- DevTools Memory (Chrome/Edge): **Heap snapshot** → column view shows constructors → shallow/retained sizes. **Comparison** view between snapshot 1 and 2 surfaces delta.
- DevTools **Allocation instrumentation on timeline**: record allocations while interacting; the call stacks with the most allocations are the allocation *sources*, not just where retained paths land.
- Node `--inspect`: `node --inspect app.js` + `chrome://inspect` → DevTools Memory (same views); CLI alternative `node --heapsnapshot-signal=SIGUSR2` → `kill -USR2 <pid>` writes `<pid>.heapsnapshot`; `node:inspector` can also trigger `heapProfiler.takeHeapSnapshot`.
- Node `--expose-gc` / DevTools **Collect garbage** button are *lab* ways to force collection before diffing — to remove collectable noise, not to profile user-perceived retention.

### 2) **`RSS` vs `heapUsed` vs `heapTotal` vs `external` vs `arrayBuffers` — which number answers which question**

| Metric | Source | What it means | When to watch it |
|--------|--------|---------------|-----------------|
| `rss` | `process.memoryUsage().rss` | resident set — OS pages for the whole process | deployment OOM threshold (container limit), not heap health |
| `heapUsed` | `process.memoryUsage().heapUsed` | V8 heap bytes reached by live graphs (post-last-GC snapshot) | leak delta between two post-GC snapshots on same workload |
| `heapTotal` | `process.memoryUsage().heapTotal` | heap bytes currently allocated to V8 (committed pages) — includes freelists | capacity/pressure, not live-set size |
| `external` | `process.memoryUsage().external` | C++ memory bound to JS objects (ArrayBuffer backing, native handles on heap) | large `Buffer`/`ArrayBuffer` retention (often shows up in snapshot `ArrayBuffer` backing) |
| `arrayBuffers` | `process.memoryUsage().arrayBuffers` | subset of external for ArrayBuffers | buffer leak check (large contiguous bytes not in `heapUsed`) |
| `v8.getHeapStatistics().used_heap_size`/`total_heap_size`/`peak_*` | `node:v8` | same as above but names vary by source — use one family consistently per run | cross-run stability |

A single `heapUsed = 140 MiB` proves nothing — *slope* across repeats does. For array-buffers the witness is often `arrayBuffers` climbing even when `heapUsed` is flat (see [Arrays §5.3](<../../../08 Arrays/sections/5. Transforming ordering and typed preview/5.3. ArrayBuffer TypedArray and DataView how they differ from Array.md>) for transfer vs copy).

### 3) **Reading a retaining path bottom-up**

In DevTools, search (Ctrl+F) by constructor name (e.g., your leaky `Session`) and open **Retainers**:

```
Leaked Session {payload:[…]}  ← selected object at the bottom
  ↖ property `value` of Map entry (id = "k42")                ← immediate retainer
  ↖ `[[MapEntries]]` of Map `cache: Map(3)` at index 2        ← collection edge
  ↖ variable `cache` in closure `createCache/<closure>`       ← environment edge
  ↖ property `cache` of (global) @12345                       ← GC root (globalThis)
```

- Strong-edge path fully shown → unbounded or uncleared `Map`/`Set`/`Array` retaining the graph.
- Path ending in an internal `system / Map` / `array` internal → the leaked array/map itself is the accused.
- No path to a leaked object reachable via snapshot search often means the object already died and another metric (buffers/external) is the culprit.

### 4) **Allocation timeline complements the snapshot delta**

```js
// Runnable shape that timeline counts correlate with. Record while running this loop.
function churnAndRetain() {
  const cache = new Map();
  for (let i = 0; i < 100; i++) cache.set(`k${i}`, { arr: new Array(200).fill(i) });
  console.log(cache.size); // 100 — the timeline will show `allocLongLived`-like sites
  // Fix is explicit, reviewable:
  cache.clear();           // or bounded policy — see [Preventing leaks §5.2](<./5.2. Preventing leaks bounded caches eviction WeakMap and dispose patterns.md>)
}
churnAndRetain();
```

Snapshot delta answers *"what retained what"* (the path). Timeline answers *"where was it allocated"* (the stack that churns). Fixes need both: sometimes allocation moves out of a hot loop; sometimes retention is capped by a policy.

### 5) **Common confusion**

- "One big snapshot means I'm leaking" — base footprint includes engine overhead, compiled code, and `Buffer` backing. Only **delta** over equal-workloads, measured *after forcing GC in the lab*, isolates true growth.
- "`performance.memory` gives me Node's `heapUsed`" — the `performance.memory` API is Chrome-only, approximate, and coarse. In Node compare `process.memoryUsage().heapUsed` across snapshot markers instead.
- "Force GC in prod to reduce latency" — see [When GC runs §2.3](<../2. GC engine and allocation/2.3. When GC runs determinism idle scheduling and --expose-gc.md>): forcing majors in production harms incremental scheduling and makes timeline data irrecoverable.

### 6) **Performance note**

Heap snapshots are expensive: full-mark + serialization can pause for hundreds of ms on large heaps and produce multi-hundred-MiB JSON. Never auto-capture in production per request. Sample at coarse interval (e.g., post-deploy, post-migration, on a canary host) and cap file output. `node --heapsnapshot-near-heap-limit=3` can auto-dump before OOM as a safety valve (lab-gate it).

### 7) **Mentor note**

Require one artifact per leak PR fix: a filtered snapshot diff showing `CountΔ` counter per constructor going `>0 → 0` for the accused (or `arrayBuffersΔ → 0`), plus the fixed retaining-path root named in review ("`cache` at `createCache/<closure>` → entry → Session"). Teaches the team to reason in retaining paths, not heap sizes.
