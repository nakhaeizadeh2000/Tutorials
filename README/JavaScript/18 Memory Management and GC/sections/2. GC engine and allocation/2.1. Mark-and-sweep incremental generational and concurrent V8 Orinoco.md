## 2.1. Mark-and-sweep incremental generational and concurrent V8 Orinoco

### 1) **Definition — tracing, not counting**

Every modern JS engine is a tracing collector. From the [root set](<../1. Memory model/1.2. Reachability roots retaining paths and object death.md>) it *marks* every reachable node (transitive closure of strong edges), then *sweeps* unmarked pages and returns them to the free list or compacts them. No reference count, no `free()` call — only marking decides death. Reclamation is an engine-internal side-effect of that trace, not a language-visible event.

```js
// Mental mark sweep: pretend you are the collector between two snapshots.
let a = { name: "keep" };               // heap node A
let b = { peer: a };                    // heap node B → A
globalThis.__keepB_for_demo = b;        // root edge — B and A both marked live
a = null;                               // cutting `a` is irrelevant: B still reaches A
console.log(globalThis.__keepB_for_demo.peer.name); // keep
delete globalThis.__keepB_for_demo;     // last path to B cut — next trace can sweep both
```

### 2) **Generational hypothesis — most objects die young**

V8 (as of 2026) splits the heap into a small *new space / nursery* (young generation, ~1–16 MiB configurable) and a large *old space* (long-lived graphs), with dedicated spaces for `ArrayBuffer` backing stores (see [Arrays §5.3](<../../../08 Arrays/sections/5. Transforming ordering and typed preview/5.3. ArrayBuffer TypedArray and DataView how they differ from Array.md>)) and for the `Oilpan` managed C++ DOM bindings in Chrome.

- *Minor (Scavenge/Young) GC*: nursery is evacuated semi-space style — survivors are copied/promoted to old space, the rest reclaimed. Cheap, frequent, often pause-free outside main-thread work.
- *Major GC*: tracing the old space — marking transitives of long-lived graphs. Expensive, runs less often, tuned to avoid world-stops.
- *Write barriers & remembered sets*: store edges from old→young must be remembered so nursery collection can treat promoted references as roots without scanning the entire old space.

```js
// Short-lived churn promotes differently than long-lived retention.
function churn(n) {
  // Each iteration builds a throwaway graph that ideally dies in the nursery.
  for (let i = 0; i < n; i++) ({ x: i, y: [i, i + 1] });
}
churn(5000);
console.log("churned — nursery survivors promoted, rest swept quickly");

const pinned = new Map();
function retain(n) {
  for (let i = 0; i < n; i++) pinned.set(`k${i}`, { payload: new Array(200).fill(i) });
}
retain(100);
console.log("pinned", pinned.size, "— survivors promoted to old space, not swept until major");
pinned.clear(); // explicit edge cuts, not GC timing, retire the graph
```

Modern guidance (ECMAScript 2026 era, V8 12–13 era, Node 22/24): the nursery/old split *exists* but exact sizes, tenuring ages, and semi-space vs page-promotion details change per engine version. Label version-specific numbers as engine-hint, not contract.

### 3) **Incremental and concurrent — Orinoco and Oilpan**

Classic mark-and-sweep paused the world. V8's *Orinoco* project (shipping since ~2018, evolving through 2026) makes both phases incremental (sliced into small main-thread tasks interleaved with JS) and concurrent (background thread traces while JS runs).

- *Incremental marking*: mark work is broken into steps yielding to the event loop, respecting latency budgets.
- *Concurrent marking*: a helper thread performs much of the graph walk without stopping the mutator (your JS thread). Final "stop-the-world" steps remain only to catch up on writes done during concurrency.
- *Concurrent sweeping/compacting*: freed pages are rethreaded without scanning kept objects on the main thread.
- *Oilpan*: C++ heap for Blink/DOM objects on a unified GC (Chrome) — JS engine leads the trace through cross-language references. Library JS seldom needs to reason about it, but retained paths can transit through native handles.

```js
// No JS API exposes "incremental step" directly. Observable correlate: responsiveness under churn.
function* longMarkYielder(items) {
  // Cooperative yield is what incremental marking also does internally — not the same mechanism,
  // but the same latency goal (avoid monolithic pause).
  for (let i = 0; i < items.length; i++) {
    if (i % 1000 === 0) console.log("yield point", i);
    yield items[i];
  }
}
console.log([...longMarkYielder(new Array(5).fill(0))].length); // 5
```

What it costs and when it pauses — see [§2.2](<./2.2. Allocation hidden classes inline caches and GC pressure.md>) for pressure, and [§2.3](<./2.3. When GC runs determinism idle scheduling and --expose-gc.md>) for scheduling. For JS authors the takeaway is throughput vs latency: allocating many throwaway graphs increases *frequency* of minor collections; retaining large long-lived graphs increases the *cost* of major marking.

### 4) **Mark bits, sweep vs compact**

- Sweeping links free chunks into freelists within pages (fragmentation may accumulate).
- Compaction moves surviving objects to coalesce holes — cost is updating pointers and invalidating inline-cache assumptions (again, [§2.2](<./2.2. Allocation hidden classes inline caches and GC pressure.md>)).
- `ArrayBuffer` backing stores are GC-managed but their bytes live off-heap in many engines; freeing them may release OS pages, visible in `process.memoryUsage().arrayBuffers`.

```js
// Allocation pattern drives sweep/compact economics — but you can't control it precisely.
const buffers = [new ArrayBuffer(1024), new ArrayBuffer(2048)];
console.log(buffers.length, buffers[0].byteLength); // 2 1024
// buffers themselves are heap objects; backing bytes are accounted under arrayBuffers/external in many hosts
// Dereference and reclaim is reachability, not `delete`:
buffers.length = 0; // cut one path; engine decides when bytes return to OS
```

### 5) **Common confusion**

- "Manual GC with `gc()`" — no. The collector traces when heuristics decide (allocation rate, pressure, idle, external hints). See [§2.3](<./2.3. When GC runs determinism idle scheduling and --expose-gc.md>) for how little `gc()` promises.
- "Reference counting or destructors" — never. Finalizers (§4.3) are not destructors; unreachable does **not** mean "soon freed."
- "All V8 versions behave alike" — Orinoco thresholds, concurrent helpers, and tenuring policy shift across versions. Treat them as hints when reading `--trace-gc` logs.

### 6) **Performance note**

The healthy habit is to read `--trace-gc`/`--trace-gc-verbose` in a lab run (Node flags) only when you already have a growth signal, not to benchmark in isolation:

```sh
# Lab only — do not ship with these flags.
# node --trace-gc app.js           # prints [Scavenge] / [MarkSweep] events
# node --trace-gc-verbose app.js   # richer tenuring/pause timing
```

Pair those logs with a workload representative allocation rate. A microbenchmark that churns one typed-array shape tells you nothing about the incremental/concurrent trade-off on your actual page.

### 7) **Mentor note**

Teach juniors mark-then-sweep in one sentence: "*trace live from roots, free the rest.*" Avoid the "search and destroy" horror metaphor. Teach seniors to read a minor vs major entry in `--trace-gc` and to say "this minor pause grew because our frame loop allocates a new mapping" rather than "GC was slow." Both answers lead to different fixes.
