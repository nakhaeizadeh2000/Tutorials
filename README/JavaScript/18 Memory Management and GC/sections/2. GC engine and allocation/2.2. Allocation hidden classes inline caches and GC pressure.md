## 2.2. Allocation hidden classes inline caches and GC pressure

### 1) **Allocation in a generational heap — why rate matters more than heap size**

New space uses a bump pointer: each allocation advances the pointer contiguously, and out-of-space triggers a minor collection. Old space maintains freelists/compaction. That makes *allocation rate* the primary driver of GC frequency: building 10,000 throwaway mid-size objects per frame drives nursery evacuations far more than holding one long-lived 10,000-entry `Map`.

```js
function allocShortLived(n) {
  for (let i = 0; i < n; i++) ({ tmp: i, arr: [i, i + 1] }); // dies in nursery
}
function allocLongLived(map, n) {
  for (let i = 0; i < n; i++) map.set(`k${i}`, { payload: new Array(200).fill(i) });
}
const pinned = new Map();
allocShortLived(5000);           // many minors, cheap — but noise still pollutes caches
allocLongLived(pinned, 100);     // few majors, expensive if never cleared
console.log("map", pinned.size, "— survivors promoted, not swept until major + clear");
pinned.clear();
```

- *Short-lived churn* stresses nursery evacuation (copying survivors) and interim CPU caches.
- *Long-lived bloat* stresses old-space marking (tracing deep graphs) and, if freelist-heavy, compaction pauses.
- Both pressures are legitimate under spec; only your *workload* says which matters. Lab numbers without representative churn mislead.

### 2) **Hidden classes (maps) — how shape drives inline-cache success**

V8 assigns each object a hidden class ("map") derived from its construction method and the *order* in which properties are added. Objects with identical construction path and property order share a map; monomorphic inline caches (ICs) then devirtualize property access.

```js
// GOOD: same construction order → shared hidden class → monomorphic IC
function Point(x, y) { this.x = x; this.y = y; }
const a = new Point(1, 2);
const b = new Point(3, 4);
console.log(a.x + b.x); // 4 — two maps converge, access is fast

// BAD: ad-hoc order + delete → dictionary mode / polymorphic IC
const c = {};
c.y = 2;        // y first
c.x = 1;        // x second — different insertion order vs Point
console.log(c.x, c.y); // 1 2 — still correct, slower access pattern
delete c.y;     // transitions c to dictionary mode in many engines
c.y = 9;        // re-add still dictionary mode
console.log(c.y); // 9

// Worse: punning the shape with mixed types in one call site deoptimizes the IC.
function sumX(objs) {
  let s = 0;
  for (const o of objs) s += o.x;
  return s;
}
console.log(sumX([a, b]));              // monomorphic call site — fast
console.log(sumX([a, { x: "str" }]));   // polymorphic — same `o.x` site sees two shapes
```

- Stable shape *uses* heap more efficiently (maps are shared) and makes GC cheaper (known slot layout). Shape churn wastes it (maps diverge, freelists fragment, GC walks more pages).
- `delete` on a non-last property frequently forces dictionary mode — prefer `obj.field = null` / `Map.delete(key)` / rebuild with spread if you need shape stability while logically discarding a field.
- Version-sensitive claim (as of August 2026, V8 12–13): exact dictionary thresholds, megamorphic limits, and `elements` kinds for arrays (fast vs dictionary) change across versions — treat as engine-hint, not contract. The direction is stable; the thresholds are not.

### 3) **GC pressure — two families with two fixes**

```js
// Family 1 — allocation churn: allocate less, or allocate once and reuse.
// BAD: new wrapper per call on a hot path
function formatBad(items) { return items.map((x) => ({ id: x })); }
console.log(formatBad([1, 2]).length); // 2

// GOOD (when hot): caller-owned reusable buffer — ownership is explicit.
// Keep the buffer scoped, not global, so the saving doesn't become a leak.
function formatGood(items, out) {
  out.length = 0;
  for (const x of items) out.push({ id: x });
  return out;
}
const reusable = [];
console.log(formatGood([1, 2], reusable).length); // 2 — one container graph reused

// Family 2 — retained pressure: bound the live set.
// BAD: unbounded Map grows for the lifetime of the process
const cacheBad = new Map();
function memoBad(key, val) { cacheBad.set(key, val); return cacheBad.get(key); }
memoBad("k1", new Array(100).fill(1));
console.log(cacheBad.size); // 1 and never shrinks

// GOOD: bounded/FIFO or WeakMap — policy decides death, not hope.
function createBounded(limit) {
  const store = new Map();
  return {
    set(k, v) { if (store.size >= limit) store.delete(store.keys().next().value); store.set(k, v); },
    size: () => store.size,
  };
}
const cacheGood = createBounded(2);
cacheGood.set("k1", 1); cacheGood.set("k2", 2); cacheGood.set("k3", 3);
console.log(cacheGood.size()); // 2 — eviction policy kept the live set bounded
```

- Churn fix is structural: remove an allocation site or hoist it out of a tight loop; `ArrayBuffer` reuse via `TypedArray` subarray/views helps only when ownership stays disciplined.
- Retention fix is lifecycle: choose `Map` vs `WeakMap` vs bounded (`LRU` via `lru-cache`-like) deliberately, document which edge is weak/bounded, and test size under realistic load — see [Preventing leaks §5.2](<../5. Measuring and preventing leaks/5.2. Preventing leaks bounded caches eviction WeakMap and dispose patterns.md>).
- The toxic combo is *high churn + long retention* (alloc-heavy inserts into an unbounded cache) — it fills nursery and bloats old space simultaneously.

### 4) **Common confusion**

- "Pre-allocate arrays to avoid GC" — pre-allocation helps throughput only when you demonstrably reuse the buffer; random pre-size wastes nursery and harms `elements` kind assumptions (`Array(100)` is holed vs `Array.of(100)` is dense — different story in [Arrays §2.1](<../../../08 Arrays/sections/2. Holes sparsity and length/2.1. Holes vs undefined sparse arrays and empty slots.md>)).
- "`delete` cleans memory instantly" — `delete` removes a slot but may deopt the map; absorption into GC wait is heuristic and rarely immediate. Prefer explicit data-structure deletion (`Map.delete`), scoping, or `null`-ing plus a policy, not scattered `delete` for memory hygiene.
- "Hidden classes are about speed, not memory" — they are about both: sharing maps shrinks metadata and keeps IC/heap walks cheap; dictionary mode bloats both.

### 5) **Performance note**

Don't benchmark GC in isolation. A micro that churns `new Array(3)` vs `reusedArray` proves nothing about *your* frame loop's nursery rate. Profile representative code with allocation timeline (DevTools) or `--trace-gc`/`--heapsnapshot-signal` in a lab, and read the *retaining volume* (how much survived minor vs how much reached old space). The most honest metric for "pressure" is *allocation rate × survival rate* during a real session, not a tight loop's ops/sec.

### 6) **Mentor note**

Review checklist for pressure-sensitive PRs: *"which object is allocated per iteration vs per session? does every growable container have an eviction rule? is any `delete` on a hot shape?"* If the answer is "unknown", require a snapshot delta in CI on a realistic workload before approving. Teach folklore-free trade-offs: monomorphic ICs are not bikeshedding — they reduce both IC misses and GC metadata, which composes well when applied consistently.
