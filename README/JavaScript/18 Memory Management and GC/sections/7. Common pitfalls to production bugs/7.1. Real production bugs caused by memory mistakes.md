## 7.1. Real production bugs caused by memory mistakes

### 1) **Unbounded `Map` history cache that pins every request — OOM after a deploy**

A per-request metadata cache grows keyed by request id (a *string*, so no weak keying applies). One deploy that doubled traffic promoted the leak from "grows slowly" to "crashes after 40 minutes."

```js
// BAD — unbounded, string-keyed, cross-request lifetime (module global).
const historyBad = new Map();
function handleBad(id, payload) { historyBad.set(id, payload); return payload; }
for (let i = 0; i < 5; i++) handleBad(`req-${i}`, { buf: new Array(500).fill(i) });
console.log("historyBad size after 5 requests:", historyBad.size); // 5 and grows

// GOOD — bounded with an explicit policy; liveness is policy, not GC timing.
function createBounded(limit) {
  const m = new Map();
  return {
    set(k, v) { if (m.size >= limit) m.delete(m.keys().next().value); m.set(k, v); },
    size: () => m.size, has: (k) => m.has(k),
  };
}
const historyGood = createBounded(3);
for (let i = 0; i < 5; i++) historyGood.set(`req-${i}`, { buf: new Array(10).fill(i) });
console.log(historyGood.size(), historyGood.has("req-0")); // 3 false — bounded by policy
```

Why GC can't fix it: `historyBad` is a GC root's (`globalThis`/module export) strong edge to every entry; no mark will ever clear them without `delete`/`clear`. WeakMap would not help here because keys are strings — string keys are not weakly held. See measurement workflow in [§5.1](<../5. Measuring and preventing leaks/5.1. Measuring memory heap snapshots allocation timeline and inspector.md>) and bounded policies in [§5.2](<../5. Measuring and preventing leaks/5.2. Preventing leaks bounded caches eviction WeakMap and dispose patterns.md>).

Incident signal: `process.memoryUsage().heapUsed` slope is monotonic across equally-sized request batches; two snapshots' comparison view shows `Map`-dominated retained size plus `req-*` string keys.

### 2) **Forgotten interval that pins a huge buffer graph**

One `setInterval` retains its callback's closure graph forever — often a `Buffer` or fetch-response parsed JSON tens of KiB per poll. The fix is teardown discipline, not heap-size tuning.

```js
function startBad(raw) {
  const big = { raw, parsed: new Array(1000).fill(raw.slice(0, 1)) };
  const id = setInterval(() => console.log(big.parsed.length), 1_000_000);
  id.unref?.();
  // Leak demo: return length without exposing id —interval would stay pinned in real bug
  const leakLen = "leaked — no handle to clear".length;
  clearInterval(id); // fence-runner cleanup — remove in true leak incident
  return leakLen;
}
console.log(startBad(["payload-" + "x".repeat(500)]));

// Fixed: host registry edge is the only root — clear it.
function startGood(raw, controller) {
  const big = { raw };
  const id = setInterval(() => console.log(big.raw.length), 1_000_000);
  controller.signal.addEventListener("abort", () => clearInterval(id), { once: true });
  return { stop: () => controller.abort() };
}
const ac = new AbortController();
const h = startGood(["good-payload"], ac);
h.stop(); // single abort cuts interval host edge → big becomes collectable
console.log("interval cleaned via signal", true);
```

Signal: interval callback appears in the retaining path from `setInterval` registry to your `Buffer` type; see host roots in [Reachability §1.2](<../1. Memory model/1.2. Reachability roots retaining paths and object death.md>) and lifecycle ownership in [§3.1](<../3. Lifetimes what stays alive/3.1. Closures timers listeners maps and the lifetime of a graph.md>).

### 3) **Closure pinning the whole config to read one number**

Same bug as [Variables §3.4](<../../../04 Variables Scope and Closures/sections/3. Closures/3.4. Closures and garbage collection what stays alive.md>) but now with concrete heap impact: a factory returning `n` closures over one huge `config` pins `config` `n` times.

```js
function makeReaderBad(config) {
  return { port: () => config.port }; // env retains entire config
}
let reader = makeReaderBad({ port: 8080, secret: new Array(1000).fill("s") });
console.log(reader.port()); // 8080 — secret still pinned
reader = null;

function makeReaderGood(config) {
  const port = config.port;
  config = null;             // one-line cut: config graph no longer in env
  return { port: () => port };
}
let reader2 = makeReaderGood({ port: 8080, secret: new Array(1000).fill("s") });
console.log(reader2.port()); // 8080 — secret edge cut
reader2 = null;
```

In many V8 builds slot pruning would reduce this, but the spec (ECMA-262) promises nothing — see [heap-vs-scope §1.2](<../1. Memory model/1.2. Reachability roots retaining paths and object death.md>) and [Lifetimes §3.1](<../3. Lifetimes what stays alive/3.1. Closures timers listeners maps and the lifetime of a graph.md>).

### 4) **Finalizer relied on to close a file/socket — runs too late, never under pressure, or not at all**

```js
// BAD — correctness depends on host-enqueued job that may never run.
let fhBad = { path: "/tmp/x", fd: 99 };
const regBad = new FinalizationRegistry((held) => console.log("BAD finalizer would close fd for", held));
regBad.register(fhBad, fhBad.path); // at least heldValue is not `fhBad` — but still wrong for correctness
fhBad = null; // file may still be open until later major + queue drain — or forever
console.log("BAD: close was never called; file may stay open");

// GOOD — deterministic + finalizer only as leak telemetry.
class FHandle {
  constructor(p) { this.path = p; this._closed = false; }
  close() { this._closed = true; }
  [Symbol.dispose]() { this.close(); }
}
let fhGood = new FHandle("/tmp/y");
const regGood = new FinalizationRegistry((held) => console.log("TELEMETRY only: leaked", held));
regGood.register(fhGood, fhGood.path);
fhGood.close(); // deterministic correctness — registry at most reports a leak elsewhere
fhGood = null;
console.log("GOOD: deterministically closed before drop", true);
```

Rule: `FinalizationRegistry` is observability, never resource correctness — see [§4.3](<../4. Weak references and cleanup deep dive/4.3. FinalizationRegistry cleanup never for correctness hosted discipline.md>). The non-weak correctness is `close`/`[Symbol.dispose]`/`using` — see [Error Handling §3.1](<../../../15 Error Handling and Debugging/sections/3. Defensive patterns/3.1. Cause wrapping context preservation and suppressed errors.md>).

### 5) **Self-referential `WeakMap`/`heldValue` keeping its own key alive — weak collection that never weakens**

```js
let key = { id: "sess-1" };
const wm = new WeakMap();
wm.set(key, { owner: key, data: new Array(100).fill(1) }); // value → key → circular pin
console.log(wm.has(key)); // true — yet now can't clear because value holds key
key = null;               // WRONG fix — value still points at original key object inside the table

// Correcting the value shape to be key-agnostic:
let key2 = { id: "sess-2" };
const wm2 = new WeakMap();
wm2.set(key2, { createdAt: Date.now(), tag: "sess-2" }); // no backlink
console.log(wm2.get(key2).tag); // sess-2
key2 = null; // eligible — value doesn't pin

// Same self-pin family for FinalizationRegistry heldValue — don't pass `obj` as second arg.
// Correct: register(obj, "descriptor-string"); Wrong: register(obj, obj)
let obj = { id: 3 };
const reg3 = new FinalizationRegistry(() => {});
const tok = {};
reg3.register(obj, `tag-${obj.id}`, tok); // held string doesn't pin obj
obj = null;
reg3.unregister(tok); // cancellation discipline
console.log("Weak self-pin bugs: hold data descriptors, not object references", true);
```

Retaining path often shows `WeakMap → value object → key object`, which is the inverted edge that defeated ephemeron semantics — see [WeakMap §4.1](<../4. Weak references and cleanup deep dive/4.1. WeakMap and WeakSet ephemeron semantics revisited deep.md>) and [WeakRef §4.2](<../4. Weak references and cleanup deep dive/4.2. WeakRef deref hazards lifetime reality and resurrection ordering.md>).

### 6) **`WeakRef` double-deref across `await` using stale data**

```js
// BAD — stale cached deref after yield
async function badWeak(wr) {
  const liveAtEntry = wr.deref();
  await new Promise((r) => setTimeout(r, 0)); // GC window
  return liveAtEntry?.value; // may be stale / should re-check
}
// GOOD — re-deref at use and treat undefined as missing
async function goodWeak(wr) {
  const live = wr.deref(); if (!live) return undefined; return live.value;
}
let o = { value: 42 };
const wr = new WeakRef(o);
goodWeak(wr).then((v) => console.log("goodWeak", v)); // 42
o = null;
```

Why this hurts in production: cache hits sporadically miss after idle GC, causing intermittent "not found" → retried with population back-pressure — see [WeakRef §4.2](<../4. Weak references and cleanup deep dive/4.2. WeakRef deref hazards lifetime reality and resurrection ordering.md>) for the slot-clearing hook.
