## 4.3. FinalizationRegistry cleanup never for correctness hosted discipline

### 1) **Contract — registration is weak; callback is best-effort hosted cleanup**

`new FinalizationRegistry(callback)` lets you register a target object with a held value and optional unregister token. Registration itself never keeps the target alive. When the target becomes unreachable the host enqueues a cleanup job whose argument is the *held value*, not the target. The callback may run later, in batches, aggregated with other unreachable registrations, or not at all — the host may never drain cleanups before process exit.

```js
let obj = { tag: "session-42" };
const cleaned = [];
const registry = new FinalizationRegistry((held) => cleaned.push(held));
registry.register(obj, "session-42 token"); // heldValue is a string descriptor, not `obj` itself
console.log(cleaned.length); // 0 — object still reachable via `obj`
obj = null;                  // target eligible — callback may eventually receive "session-42 token"
console.log("registered; cleanup is future & best-effort", true);
```

### 2) **Held value vs token vs target — the pin rule**

- *Held value* is the only thing the registry stores strongly. If you pass `obj` itself as held value (`register(obj, obj)`) you hold a strong edge to the target and prevent collection — defeating the whole mechanism.
- *Target* is the weakly held key the registry watches via ephemeron edge — reading `registry` from JS never exposes it after death.
- *Unregister token* is an object reference you keep strongly; `unregister(token)` cancels any pending cleanup for that token.

```js
// BAD: self-holding — registry keeps obj alive via heldValue
// (throws TypeError on modern engines because spec forbids target === holdings — guarded for fence runner)
let bad = { id: 1 };
const regBad = new FinalizationRegistry((v) => console.log("bad held", v?.id));
try { regBad.register(bad, bad); } catch (e) { console.log("self-pin correctly throws", e.name); } // TypeError on spec-compliant engine — proves the pin is invalid
console.log("bad registration self-pins (if no throw) or self-pin rejected — either way, fix the second argument", true);
bad = null;                // BAD case stays pinned until you fix the second argument

// GOOD: tokenized, descriptor-only heldValue + explicit cancellation
let good = { id: 2 };
const log2 = [];
const regGood = new FinalizationRegistry((held) => log2.push(`clean:${held}`));
const token = {};
regGood.register(good, "good-2", token);
good = null;               // eligible — held string doesn't pin
regGood.unregister(token); // cancelled — callback will not queue
console.log(log2.length, "— cancelled via token", 0 === log2.length ? "ok" : "flaky timing");
```

### 3) **Never for correctness — explicit `close`/`dispose`/`using` is the correctness path**

A finalizer is not a destructor. File handles, locks, sockets, DB transactions, and reference-counted resources need a synchronous, deterministic release. `FinalizationRegistry` is appropriate for telemetry — metrics collection, double-free detection, leak logging — whose result may be lost without breaking correctness.

```js
// Resource with deterministic correctness + best-effort telemetry.
class FileHandle {
  constructor(path) {
    this.path = path;
    this.fd = path.length;         // mock — real code holds an fd integer via node:fs
    this._closed = false;
  }
  close() { this._closed = true; console.log("closed deterministically", this.path); }
  [Symbol.dispose]() { this.close(); }
}
let fh = new FileHandle("/tmp/x");
const leaked = [];
const regFile = new FinalizationRegistry((hp) => leaked.push(`leaked handle ${hp}`));
regFile.register(fh, fh.path);     // held is the path string, not the handle object
fh.close();                         // correctness — deterministic
fh = null;                          // no callback needed; if the caller forgot close(), at most the telemetry fires late

// With explicit resource management (ES2024, Node 22+ guarded) the language makes the pattern enforceable:
{
  let closableHandle = null;
  try {
    closableHandle = new FileHandle("/tmp/y");
    console.log("using-block would auto-dispose here on exit", closableHandle.path);
  } finally {
    closableHandle?.close?.(); // fallback when `using` not available in this runner
  }
}
```

For the `using`/`explicit resource management` statement and `Symbol.dispose`/`Symbol.asyncDispose` / `SuppressedError` model referred to above, see [Error Handling §3.1](<../../../15 Error Handling and Debugging/sections/3. Defensive patterns/3.1. Cause wrapping context preservation and suppressed errors.md>).

### 4) **GC-powered observer: testing with retry loops + forced GC + microtask drain**

```js
async function labFinalizes() {
  if (typeof FinalizationRegistry === "undefined" || typeof global.gc !== "function") {
    console.log("lab probe skipped — run with `node --expose-gc`");
    return;
  }
  const hits = [];
  const reg = new FinalizationRegistry((h) => hits.push(h));
  let target = {};
  const tok = {};
  reg.register(target, "probe", tok);
  target = null;

  for (let attempt = 0; attempt < 12; attempt++) {
    global.gc();
    // Registry callbacks are enqueued as jobs after ClearKeptObjects — drain microtasks/queue
    await new Promise((r) => setTimeout(r, 12));
    if (hits.length) break;
  }
  console.log("FinalizationRegistry hit?", hits[0] === "probe" ? "yes (observed)" : "unknown timing — retry or treat as not-yet");
  // Cancellation discipline
  let t2 = {};
  const tok2 = {};
  const hits2 = [];
  const reg2 = new FinalizationRegistry((h) => hits2.push(h));
  reg2.register(t2, "dont-run", tok2);
  reg2.unregister(tok2);
  t2 = null;
  global.gc();
  await new Promise((r) => setTimeout(r, 12));
  console.log("after unregister, hits2", hits2.length); // 0 — cancelled job never enqueues
}
labFinalizes();
```

Flaky-timing acknowledgement is intentional: host-enqueued callbacks are jobs drained by the event loop, and batching is permitted. A test that asserts `hits[0] === "probe"` without retry and forced GC is a guaranteed flake — and the prod system must never depend on the hit anyway.

### 5) **Common confusion**

- "Registration keeps the target alive" — no, the target edge is weak. What's strong is the held value you choose. If you make that value a fresh descriptor, the target remains ephemeral.
- "Callbacks run promptly when GC sweeps" — not "when swept" but "after major's ClearKeptObjects posts jobs"; timing includes microtask drain and host batching. No ordering guarantee is given among co-collected targets.
- "`WeakRef` resurrection re-enqueues a cancelled finalizer" — no. After the job is enqueued, re-establishing a strong edge doesn't cancel it; after cancellation via `unregister`, no job is posted.

### 6) **Performance note**

Every live `FinalizationRegistry` registration adds an ephemeron entry the collector must trace. Thousands of per-element registrations (e.g., one per DOM-like row) cost more than one registry watching many targets via a shared callback and descriptor map. Keep registrations coarse (`session`/`connection`) not fine (`cell`).

### 7) **Mentor note**

Review phrase: *"this registry callback is observability, not correctness — show me the deterministic `close`/`dispose`/`using` that actually owns the resource."* Approve telemetry via finalizers; reject resource lifetimes whose correctness depends on one. Ask authors to name `heldValue` and `token` in a comment at every `register` site so the pin rule is reviewable.
