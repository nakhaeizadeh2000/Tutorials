## 4.1. WeakMap and WeakSet ephemeron semantics revisited deep

### 1) **Definition — ephemeron aliveness flows from the key/member**

`WeakMap` and `WeakSet` are *ephemeron tables*: an entry is kept iff its key (or, for `WeakSet`, its member) is itself reachable through some other strong path. When that key/member dies — meaning no non-weak edge reaches it — the engine removes the entry atomically as part of the marking pass. That non-observability is the contract: there is no `size`, no enumeration, no `clear` exposing "are you dead yet?" — only `get`/`set`/`has`/`delete` (and `add` for `WeakSet`).

```js
let user = { id: 1 };
const meta = new WeakMap();
meta.set(user, { notes: new Array(100).fill("private") });
console.log(meta.has(user), meta.get(user).notes.length); // true 100

// Correct iteration is over the live population, not the WeakMap itself.
// To iterate, you hold the objects separately — WeakMap only answers "given this live key, what meta?".
const liveUsers = [user];
console.log(liveUsers.map((u) => meta.get(u)?.notes.length)); // [100]

// For contrast: same with a strong Map leaks the whole history
const leakDemo = new Map();
leakDemo.set({ id: 2 }, "strong"); // key is unrelated edge — this entry can outlive usefulness
console.log(leakDemo.size);        // 1 — tells you exactly what WeakMap refuses to reveal
```

### 2) **The self-reference bug that defeats weakness**

Adding the key as part of the value keeps the key alive through that value edge — the entry never weakens.

```js
let obj = { id: 42 };
const wm = new WeakMap();
wm.set(obj, { self: obj }); // BAD — value references key → key stays reachable via the entry's value
console.log(wm.has(obj));   // true — but entry can never clear even after user drops obj

// GOOD — descriptor that doesn't point back at the key
wm.set(obj, { createdAt: Date.now(), tag: "session-42" });
console.log(wm.get(obj).tag); // session-42

obj = null; // last strong path to {id:42} is gone; entry is now eligible (when GC eventually runs)
console.log("eligible, not guaranteed collected immediately", true);
```

The modern phrasing (ECMAScript 2026 era, ES2015+ engines): keep `WeakMap` values *key-agnostic*. If you need a backlink, store an `id` string, not the object reference — or use a `FinalizationRegistry` `heldValue` that explicitly ignores the target (see [§4.3](<./4.3. FinalizationRegistry cleanup never for correctness hosted discipline.md>)).

### 3) **Private state via `WeakMap` — why closures aren't the only answer**

```js
const _state = new WeakMap(); // module Singleton is the policy: private but not leaking
class Session {
  constructor(name) {
    this.name = name;
    _state.set(this, { token: Math.random(), createdAt: Date.now() });
  }
  token() { return _state.get(this)?.token; }
}
let s = new Session("alice");
console.log(typeof s.token() === "number"); // true
console.log(typeof s._state);               // undefined — no property on the instance
s = null;                                   // instance dies → _state entry evaporates (weak)
console.log("Session instance released", true);
```

- Trade-off vs closure-private (seen in [Prototypes §3.3](<../../../07 Prototypes and Classes/sections/3. Class syntax/3.3. Private fields and methods brand checks and encapsulation.md>) with `#private` brand): `#private` is per-instance identity checked by the engine; `WeakMap` branding is by registry identity and can be module-split. `WeakMap` is also usable for objects you don't own (wrap a foreign instance without mutating its shape). GC behavior is the same: private entry lifetime tracks the instance.

### 4) **GC interaction — marking does the weak sweep atomically**

During marking the engine treats `WeakMap`/`WeakSet` specially: a key/member reached only through its own entry's value edges does not count as live. After marking, unreachable-key entries are removed before the sweep phase so that sweep never has to resurrect via that edge. That is ECMA-262 `ClearKeptObjects` host semantics — see the detailed hook in [WeakRef §4.2](<./4.2. WeakRef deref hazards lifetime reality and resurrection ordering.md>) for how `WeakRef` and `FinalizationRegistry` contents are cleared by the same atomic step.

```js
// Lab demonstration that an entry is invisible to enumeration
const wm2 = new WeakMap();
let k1 = {};
let k2 = {};
wm2.set(k1, 1);
wm2.set(k2, 2);
console.log(wm2.has(k1), wm2.has(k2)); // true true — only way to ask
console.log(typeof wm2.size, typeof wm2[Symbol.iterator]); // undefined undefined — no enumeration API
k1 = null; k2 = null; // entries become collectable — not observable without forcing GC
```

### 5) **Common confusion**

- "WeakMap caches never leak" — they can, via self-referential values. A cache that stores `{ key, value: { key, payload }}` is a pin.
- "WeakMap size tells me memory saved" — there is no `size`. If you need accounting, hold a parallel bounded `Map` with expiration (see [Preventing leaks §5.2](<../5. Measuring and preventing leaks/5.2. Preventing leaks bounded caches eviction WeakMap and dispose patterns.md>)).
- "WeakSet tracks 'was seen'" — `has` is correct; membership *tracks liveness*, not history. For "seen at any point in the past" you need a strong `Set`, explicitly pruned.

### 6) **Performance note**

Ephemeron tables are allocation-light but mark-phase heavy when entries are many. The engine must chase weak keys alongside strong roots. Don't create a `WeakMap` per function call in a tight loop — allocate one table at module level and reuse it. The per-entry overhead is small but the relabeling cost grows with population under mark pressure.

### 7) **Mentor note**

Have juniors answer out loud: *"does this value reference the key?"* If yes, it's not weak. Drill one PR exercise: rewrite an `Array` of last-100-users-caches as `WeakMap` keyed by the user object and show the "after logoff" query returns `undefined` without calling `clear`.
