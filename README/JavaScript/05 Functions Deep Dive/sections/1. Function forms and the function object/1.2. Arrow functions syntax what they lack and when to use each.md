## 1.2. Arrow functions: syntax, what they lack, and when to use each

### 1) **Syntax: concise vs block bodies and sugaring rules**

**Definition** — an *arrow function* is `params => expression-or-block`, a function whose `this`/`arguments`/`super` are lexical (inherited from the surrounding scope) and which can never be used as a constructor. Introduced in ES2015, it is the default spelling for callbacks.

```js
// 0 params — parens required; 1 param — parens optional; 2+ — parens required
const id  = (x) => x;
const id2 = x => x;
const add = (a, b) => a + b;
console.log(id(7), add(2, 3)); // 7 5

// Concise body: implicit return of the expression value
const square = n => n * n;
console.log(square(4)); // 16

// Block body: explicit return required
const withLog = (n) => {
  console.log("computing", n);
  return n * n;
};
console.log(withLog(5)); // logs + 25

// Object-literal concise body needs parens — otherwise {} parses as a block
const makePoint = (x, y) => ({ x, y });
console.log(makePoint(1, 2)); // { x: 1, y: 2 }
const bad = x => { x: x };           // label + expression statement, returns undefined
console.log(bad(1));                 // undefined
const fixed = x => ({ x: x });
console.log(fixed(1));               // { x: 1 }

// async arrow is the same shape with promise wrapping
const fetchJson = async (url) => ({ url, ok: true });
fetchJson("https://example.com").then((v) => console.log(v.ok)); // true
```

- *History* — before arrows, every `function (x) { return x; }` callback captured `this` from the call site, forcing `var self = this` or `.bind(this)`; arrows closed that gap by making callback `this` lexical.

### 2) **What arrows don't have — one design decision, five consequences**

Arrows are *non-constructible, non-prototype, lexical-this* functions. Five things are absent by design:

```js
// 1) No own `this` — closed over; call/apply/bind cannot rebind it (→ [3.2](<../3. this binding/3.2. Arrow lexical this and why callbacks break or heal.md>))
const obj = {
  value: 42,
  arrow: () => console.log("arrow this === obj?", this === obj),
  method() { return (() => this.value)(); },
};
console.log(obj.method()); // 42 — arrow inherited method's this

// 2) No `arguments` object — use rest params instead (→ [2.1](<../2. Parameters and arguments/2.1. Defaults destructuring rest and the arguments object.md>))
function outer() {
  const arrow = () => arguments[0];
  // arrow sees outer's arguments, not its own
  return arrow();
}
console.log(outer(99)); // 99 — lexical arguments from outer
try {
  const alone = () => arguments[0]; // ReferenceError in module-like top level (no outer arguments)
  console.log(alone());
} catch (e) { console.log(e.name); } // ReferenceError (no outer function)

// 3) No `prototype` — not constructible
const fn = () => {};
console.log(typeof fn.prototype); // undefined
try { new fn(); } catch (e) { console.log(e.name); } // TypeError

// 4) No `super` of its own — lexical super from surrounding method
// (super only legal inside concise methods; arrow inside method inherits it — [1.3](<./1.3. Methods getters setters and the function object.md>))

// 5) No `caller`/`callee` linkage in strict code; no own generator/async-generator form
console.log(fn.hasOwnProperty("prototype"), typeof fn); // false function
```

- The five are not a checklist to memorize — they follow from one invariant: *arrows never get a fresh this/arguments/super binding*, so engines never allocate one.

### 3) **Choosing arrow vs function — the decision rule**

```js
// Callback that needs surrounding this → arrow (heals "lost this")
class Timer {
  constructor() { this.ticks = 0; }
  start() {
    // regular function would see globalThis/undefined here
    setTimeout(() => { this.ticks += 1; console.log(this.ticks); }, 0);
  }
}
new Timer().start(); // 1 (after timeout)

// Method that needs call-site this → function (or concise method)
const counter = {
  count: 0,
  inc() { this.count += 1; return this.count; }, // concise method — dynamic this
  // incArrow: () => { this.count += 1; } // ← bug: this would be outer (module) this, not counter
};
console.log(counter.inc(), counter.count); // 1 1

// Constructor / prototype method → function
function Point(x, y) { this.x = x; this.y = y; } // constructible
const p = new Point(1, 2);
console.log(p.x); // 1

// Callback that must NOT capture → still use function when you need arguments or dynamic this
const handlers = {
  name: "handlers",
  items: [1, 2],
  run() {
    return this.items.map(function (n) { return this.name + ":" + n; }, this); // explicit thisArg
  },
};
console.log(handlers.run()); // [ 'handlers:1', 'handlers:2' ]
```

- Decision table:

| Use | Form |
|-----|------|
| Standalone callback closing over outer `this` | `() =>` |
| Object/prototype method, constructor, needs `arguments`/`super`/`new` | `function` / concise method |
| Top-level utility with no `this` sensitivity | either — prefer `function` declarations for hoisted API, arrow `const` for expression/conditional |

### 4) **Common confusion**

- "`() => { prop: 1 }` returns an object" — no; it's a labeled statement block. Wrap in `({ ... })`.
- "Arrow `this` can be re-bound with `call`/`bind`" — never; `call`'s first argument is ignored for arrows ([3.3](<../3. this binding/3.3. call apply bind and bound functions.md>)).
- "`arguments` inside an arrow is its own arguments" — it is lexical; in top-level/module scope there is no outer `arguments` and it throws.
- "Arrow functions are just shorter functions" — they are a *different kind* (non-constructible, no prototype, lexical `this`) — the brevity is incidental.

### 5) **Performance note**

Arrows and functions optimize identically once created; arrow capture of `this` avoids the `bind`/closure allocation that `function() { ... }.bind(this)` would allocate per call. The real cost is *creating closures inside hot loops* regardless of spelling — hoist invariant callbacks. No measurable steady-state difference between the two forms in V8/JSC — [measure](<../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md>).

### 6) **Mentor note**

Have a junior rewrite a `self = this` method to arrows, then ask them to write an object-literal method as an arrow and predict `this` — the second case must fail before they trust the rule. In review, flag `method: () =>` inside any object literal or class field that reads `this` without an obvious lexical outer — that arrow almost always captures the wrong target.
