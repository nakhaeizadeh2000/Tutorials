## 1.1. Function declarations, expressions, and hoisting

### 1) **Declarations vs expressions vs named function expressions**

**Definition** — JavaScript has four syntactic shapes that create functions, and the shape decides *what name is created, where,* and *when the value exists*:

- **FunctionDeclaration** — `function f() {}` at statement level: creates binding `f` in the enclosing scope, initialized before any code runs.
- **FunctionExpression** — `const f = function () {}` or `const f = () => {}` as a value: creates the function at evaluation time; the surrounding variable follows `let`/`const`/`var` rules ([TDZ](<../../../04 Variables Scope and Closures/sections/1. Declarations and bindings/1.2. Temporal dead zone why early access throws.md>)).
- **Named FunctionExpression (NFE)** — `const f = function inner() {}`: outer binding `f` plus an inner-only name `inner` visible exclusively inside the function body.
- **Arrow** — covered in [1.2](<./1.2. Arrow functions syntax what they lack and when to use each.md>); **Method definition** — covered in [1.3](<./1.3. Methods getters setters and the function object.md>).

```js
// Declaration: usable before its line (creation phase — see [hoisting §2](#2-hoisting-reality-for-functions))
console.log(typeof declared); // function — exists before evaluation reaches it
function declared() { return 1; }

// Expression: variable follows let/const rules
try { console.log(typeof notYet); } catch (e) { console.log(e.name); } // ReferenceError (TDZ)
const notYet = function () { return 2; };
console.log(notYet()); // 2

// NFE: inner name is scoped to the function body — self-reference without polluting outer scope
const fac = function fact(n) { return n <= 1 ? 1 : n * fact(n - 1); };
console.log(fac(5)); // 120
try { console.log(typeof fact); } catch (_) {}
console.log(typeof fact); // undefined — no outer binding leaked
console.log(fac.name);    // fact — name property captures the inner name
```

- *What problem this solves* — NFE gives recursion and reliable stack traces without creating a second outer binding; anonymous expressions produce `name === ""` or inferred names that can be less precise (inference → [1.3](<./1.3. Methods getters setters and the function object.md>)).
- Why both exist historically: declarations give a hoisted API surface (mutually recursive helpers can appear in any order); expressions give conditional definition and first-class assignment (`const fn = cond ? a : b`).

### 2) **Hoisting reality for functions**

Nothing moves. Scopes have a creation phase before top-to-bottom execution. Each declaration form registers differently:

| Form | Binding created when | Value usable when |
|------|---------------------|-------------------|
| `function f(){}` (top-level / function body) | scope entry — `f` bound to the function object | immediately |
| `const f = function(){}` / `let` | scope entry — TDZ | after initializer line |
| `var f = function(){}` | scope entry — `f` is `undefined` | after assignment line |
| Named `function inner(){}` inside an NFE | inside the function body only | inside body only |

```js
// Functions hoist ahead of var — the canonical ordering question
console.log(typeof dup); // function — declaration wins over var's undefined
var dup = 42;
function dup() { return "fn"; }
console.log(typeof dup); // number — assignment overwrote the function at runtime

// Expression follows variable, not function, rules
var expr = function named() { return typeof named; };
console.log(expr());          // function — inner name visible inside
console.log(typeof named);    // undefined — not in outer scope

// Block-level declarations are the trap — strict mode keeps them block-scoped
function strictBlockDemo() {
  "use strict";
  {
    function blockFn() { return "inside"; }
    console.log(blockFn());              // inside — exists here
  }
  try { console.log(blockFn()); }
  catch (e) { console.log(e.name); }     // ReferenceError — not leaked
}
strictBlockDemo();

// Sloppy mode on some engines exhibits Annex B web-compat leakage (see Decisions).
// Never rely on conditional function declarations:
function choose(useA) {
  let fn;
  if (useA) fn = function a() { return "A"; };
  else      fn = function b() { return "B"; };
  return fn(); // correct conditional-definition pattern
}
console.log(choose(true), choose(false)); // A B
```

- Modern guidance: use **declarations** for stable, always-available helpers; use **`const` + expression** for conditional, reassignable, or callback-position definitions; avoid block-level `function` declarations entirely — write an expression assigned to a `let`/`const` instead (consistent across strict/sloppy and across engines).

### 3) **When each form is the right tool**

```js
// Top-level API — declaration keeps the export order free
function parseConfig(raw) { return JSON.parse(raw); }
function validateConfig(obj) { return typeof obj.port === "number"; }

// Conditional definition — expression is the only sane spelling
function makeLogger(verbose) {
  const log = verbose ? function (m) { console.log("[verbose]", m); }
                      : function (_m) {};
  return log;
}
console.log(typeof makeLogger(true)); // function

// Self-reference without outer pollution — NFE
const countdown = function tick(n) {
  if (n <= 0) return "done";
  return tick(n - 1); // tick resolves to the inner name, not the outer const
};
console.log(countdown(3)); // done

// Expression position vs statement position matters for ASI — see [ASI](<../../../02 Language Basics/sections/1. Program structure and syntax/1.1. Statements expressions and semicolons ASI reality.md>)
const run = () => {
  // IIFE via expression position (details → [4.2](<../4. First-class and execution patterns/4.2. IIFE module ancestry and modern replacements.md>))
  const value = (function () { return 42; })();
  return value;
};
console.log(run()); // 42
```

### 4) **Common confusion**

- "Functions always hoist" — only declarations hoist as functions; expressions hoist as variables ([scope creation phase](<../../../04 Variables Scope and Closures/sections/2. Scope and lookup/2.2. Hoisting the reality creation phase not magic.md>)).
- "`function f() {}` inside `if` conditionally defines `f` globally" — no; in strict mode it's block-scoped and after the block it's gone; in sloppy mode Annex B makes it leak in surprising assignment-on-entry ways — avoid entirely.
- "`const f = function f() {}` duplicates the name" — no; outer `const f` and inner NFE `f` are distinct bindings; shadowing is intentional to enable recursion after outer reassignment.
- "`fn.name` is always the variable name" — `name` inference exists but NFE's explicit inner name takes precedence and is the only reliable self-reference.

### 5) **Performance note**

Declaration vs expression has zero steady-state cost — after parsing, both are function objects on the heap; engines inline and optimize either identically. NFE's extra inner binding is one more scope slot, negligible. Costlier is *creating functions inside hot loops* (new closure per iteration — see [loop capture](<../../../04 Variables Scope and Closures/sections/3. Closures/3.2. Loops and closures var let and per iteration capture.md>)) — hoist invariant functions out of loops instead. As ever, [measure](<../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md>).

### 6) **Mentor note**

Teach §1 with a two-question drill: (a) "what does `typeof fn` print *before* this line?" for each form; (b) "where is `fact` visible?" for an NFE. If a junior answers (a) with TDZ vocabulary and (b) with "only inside", the model is solid. In review, grep `^function` inside `if`/`for`/`while` blocks — replace every hit with `const fn = function...`.
