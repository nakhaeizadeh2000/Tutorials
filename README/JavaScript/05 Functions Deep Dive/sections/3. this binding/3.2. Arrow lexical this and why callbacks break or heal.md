## 3.2. Arrow lexical this and why callbacks break or heal

### 1) **Arrows close over `this` like any lexical variable**

**Definition** — an arrow function has no own `this` binding; the identifier `this` inside its body resolves exactly like a variable lookup — walking outward to the nearest non-arrow function's `this` (or the top-level `this`). It is *never* re-bound by call-site rules:

```js
function regular() { return this; }
const arrow = () => this;

console.log(regular.call({ id: 1 }).id); // 1 — explicit rule wins
console.log(arrow.call({ id: 1 }) === this); // true — call's first arg is ignored (lexical)

// Demonstration: arrow inherits method's this
const obj = {
  value: 42,
  method() {
    const arrow = () => this.value;
    function inner() { return this; } // regular — call-site
    return { arrow: arrow(), innerThis: inner() };
  },
};
console.log(obj.method().arrow); // 42 — arrow saw method's this
console.log(obj.method().innerThis === globalThis || obj.method().innerThis === undefined); // true — inner uses default rule

// call/apply/bind cannot rebind an arrow — ever
const captured = (() => this)(); // at top level: globalThis or undefined depending on host
const warmer = { val: 99 };
console.log((() => this).call(warmer) === captured); // true — call ignored
const boundArrow = (() => this).bind(warmer);
console.log(boundArrow() === captured); // true — bind ignored
```

- Why the invariant exists: arrows are designed for *callbacks that outlive their method's call frame* — `setTimeout`, `map`, `then` — where preserving the surrounding `this` is the common case.

### 2) **Where arrow `this` heals — callbacks inside methods**

Every healed case is a regular function that would have defaulted:

```js
class Store {
  constructor() { this.items = [1, 2, 3]; this.prefix = "item:"; }
  // Heal: arrow inside method preserves this for the async callback
  load() {
    setTimeout(() => {
      console.log(this.prefix, this.items.length); // this = Store instance
    }, 1);
  }
  // Heal: iterator callback inside method
  labeled() {
    return this.items.map((n) => `${this.prefix}${n}`);
  }
  // Heal: promise handler inside method
  async fetchCount() {
    const n = await Promise.resolve(this.items.length);
    return (() => n + (this.prefix.length))();
  }
}
const s = new Store();
console.log(s.labeled()); // [ 'item:1', 'item:2', 'item:3' ]
s.load();                 // item: 3 (after timeout)
s.fetchCount().then((v) => console.log(v)); // 8 (3 + 5)

// Without arrow, each site needed manual binding
class LegacyStore {
  constructor() { this.items = [1, 2]; this.prefix = "x:"; }
  labeledBind() {
    return this.items.map(function (n) { return this.prefix + n; }.bind(this));
  }
  labeledThisArg() {
    return this.items.map(function (n) { return this.prefix + n; }, this); // thisArg param
  }
}
console.log(new LegacyStore().labeledBind());   // [ 'x:1', 'x:2' ]
console.log(new LegacyStore().labeledThisArg()); // [ 'x:1', 'x:2' ]
```

### 3) **Where arrow `this` hurts — object methods, prototypes, and handlers needing dynamic `this`**

```js
// 1) Object-literal method as arrow → captures outer (module) this, not the object
const counter = {
  count: 0,
  incArrow: () => { this.count = (this.count || 0) + 1; return this.count; }, // bug
  incMethod() { this.count += 1; return this.count; },
};
console.log(counter.incMethod()); // 1 — this is counter
console.log(counter.incArrow() !== 1); // true — arrow's this is not counter (globalThis/undefined property)
console.log(typeof counter.count); // number — counter.count is still 1, arrow mutated outer

// 2) Prototype method as arrow field vs method
class Button {
  constructor(label) { this.label = label; }
  // method — dynamic this (correct for prototype)
  click() { return this.label; }
  // field arrow — lexical this = instance's construction this (captures per-instance, not prototype)
  clickArrow = () => this.label;
}
const b = new Button("ok");
console.log(b.click());       // ok
console.log(b.clickArrow());  // ok — both happen to work on the instance…

// …but detachment semantics diverge:
// method detached loses this (needs bind), arrow field keeps it
const m = b.click;
try { console.log(m()); } catch (e) { console.log(e.name); } // TypeError
console.log(b.clickArrow.call({ label: "other" })); // ok — arrow ignored call's this, still original instance

// 3) DOM/event-style handler that expects dynamic this (textual — browser)
// element.addEventListener("click", function () { console.log(this === element); }); // true — dynamic
// element.addEventListener("click", () => console.log(this === element));           // false — lexical

// 4) Nested arrow inherits through multiple levels — no way to "re-dynamicize" mid-chain
const outer = {
  id: "outer",
  make() {
    return () => {
      const innerArrow = () => this.id;
      return innerArrow();
    };
  },
};
console.log(outer.make()()); // outer — outer's this propagated through two arrow layers
```

- *Decision rule* — use arrows *only* when you want `this` from the surrounding method/scope; never spell a method that callers will invoke as `obj.method()` with an arrow at the top level of that property — it is a silent caller-contract violation.

### 4) **Common confusion**

- "`this` inside arrow is `null`" — no; it's whatever the surrounding scope's `this` is (instance inside a method, `undefined` at ESM top level, `globalThis` in sloppy scripts).
- "`call`/`bind` can fix an arrow's `this`" — never; explicit binding is ignored on arrows ([3.3](<./3.3. call apply bind and bound functions.md>)).
- "Arrow methods are more performant because they auto-bind" — they capture per-construction (field arrow allocates per instance), while prototype methods share one function; correctness, not performance, decides (→ [1.3](<../1. Function forms and the function object/1.3. Methods getters setters and the function object.md>)).
- "Lexical `this` means arrows are closures over `this`" — exactly; `this` is looked up like a local variable, which is why `outer.make()()` chains preserve it.

### 5) **Performance note**

Lexical `this` avoids the branch that resolves `this` at call time — trivially cheaper, not measurably faster. The meaningful cost is *per-instance field arrows* (`class C { m = () => {} }`) allocating one function per instance vs a shared prototype method. For thousands of instances, prefer prototype methods plus explicit bind/arrow wrappers only at callback sites — [measure](<../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md>).

### 6) **Mentor note**

Teach with a broken object-literal arrow method (`incArrow: () => this.count++`) and ask for `counter.incArrow()` output — the answer must name the outer `this`, not counter. Next, show the same arrow nested inside a concise method (`inc() { const f = () => this.count++; return f(); }`) — now it heals. The contrast locks the rule. In review, flag `key: () => this` inside any object literal that reads `this` — that arrow almost always captures the wrong target; replace with `key() {}`.
