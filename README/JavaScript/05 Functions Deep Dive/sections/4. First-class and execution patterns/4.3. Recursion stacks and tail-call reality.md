## 4.3. Recursion, stacks, and tail-call reality

### 1) **Recursion shape: base case + progress**

**Definition** — a *recursive* function calls itself (directly or mutually). Every correct recursion has two parts that must be provable: a *base case* that terminates without recursing, and *progress* toward it on every recursive step:

```js
// Canonical linear recursion — O(n) stack
function factorial(n) {
  if (n <= 1) return 1; // base case
  return n * factorial(n - 1); // progress: n decreases
}
console.log(factorial(5)); // 120

// Mutual recursion — still needs both properties across the pair
function isEven(n) { return n === 0 ? true : isOdd(n - 1); }
function isOdd(n)  { return n !== 0 && isEven(n - 1); }
console.log(isEven(42), isOdd(42)); // true false

// Tree recursion — two recursive calls per node (e.g. naive Fibonacci)
function fib(n) {
  if (n <= 1) return n;
  return fib(n - 1) + fib(n - 2);
}
console.log(fib(10)); // 55 — correct but exponential work

// Guard against missing progress — without it, you loop until stack exhaustion
function bad(n) {
  if (n === 0) return 0;
  return bad(n); // no progress when n !== 0 → infinite recursion
}
try { bad(1); } catch (e) { console.log(e.name); } // RangeError
```

### 2) **Stack limits and rewriting strategies**

JavaScript has a finite call stack (engine-dependent, typically tens of thousands of frames). Deep linear recursion exhausts it:

```js
// Stack depth probe — how deep can we go before RangeError?
function depth(n) {
  if (n <= 0) return 0;
  return 1 + depth(n - 1);
}
try { console.log(depth(10000)); } catch (e) { console.log(e.name, e.message.slice(0, 40)); } // 10000 or RangeError — engine-dependent
try { console.log(depth(50000)); } catch (e) { console.log(e.name); } // RangeError on most engines

// Iterative rewrite — O(1) stack, O(n) time, when recursion depth is data-dependent
function factorialIter(n) {
  let acc = 1;
  for (let i = 2; i <= n; i++) acc *= i;
  return acc;
}
console.log(factorialIter(5)); // 120 — same result, constant stack

// Tail recursion still allocates frames in most engines (see §3), so iterate when depth correlates with input size
function sumRangeTail(n, acc = 0) { // tail position, but not optimized except in JSC
  if (n <= 0) return acc;
  return sumRangeTail(n - 1, acc + n);
}
console.log(sumRangeTail(1000)); // 500500 — works but deep stacks still counted

// Trampoline — turn recursion into iteration via thunks (bounded stack, composable)
const thunk = (fn, ...args) => () => fn(...args);
function trampoline(result) {
  while (typeof result === "function") result = result();
  return result;
}
function sumTramp(n, acc = 0) {
  if (n <= 0) return acc;
  return thunk(sumTramp, n - 1, acc + n);
}
console.log(trampoline(sumTramp(100000, 0))); // 5000050000 — depth 100k without stack blowup
```

- Decision rule: recursion for *structurally recursive data* (ASTs, trees, divide-and-conquer) where depth is logarithmic; iteration/trampoline for linear depth tied to input length (linked lists, `n` up to 1e5).

### 3) **Tail calls: spec promise vs engine reality**

ES2015 specifies *proper tail calls* (PTC): a call in tail position must not grow the stack. In practice only JavaScriptCore (Safari) ships PTC; V8 and SpiderMonkey do not (V8 prototyped then removed; SpiderMonkey never shipped):

```js
// Not tail — n * factorial(n-1) needs stack to multiply after return
function factorialNonTail(n) {
  if (n <= 1) return 1;
  return n * factorialNonTail(n - 1); // multiply awaits recursive result → not tail
}

// Tail — recursive result is the function's own return value, no work after
function factorialTail(n, acc = 1) {
  if (n <= 1) return acc;
  return factorialTail(n - 1, n * acc); // call is the last action → tail position
}
console.log(factorialTail(5)); // 120

// Mutual tail call — also PTC-eligible (but not optimized off JSC)
function evenTail(n) { return n === 0 ? true : oddTail(n - 1); }
function oddTail(n)  { return n === 0 ? false : evenTail(n - 1); }
console.log(evenTail(42), oddTail(42)); // true false

// Do NOT rely on PTC in production — write iterably
function sumPtcUnsafe(n) {
  // Looks tail but will throw RangeError on V8/Spidermonkey at large n
  function loop(k, acc) { return k <= 0 ? acc : loop(k - 1, acc + k); }
  return loop(n, 0);
}
try { console.log(sumPtcUnsafe(50000)); } catch (e) { console.log(e.name); } // RangeError on V8/Spidermonkey

// Bounded alternative — iterate
function sumSafe(n) {
  let acc = 0;
  for (let k = 1; k <= n; k++) acc += k;
  return acc;
}
console.log(sumSafe(50000)); // 1250025000 — always safe
```

- *History* — ES2015 PTC was aspirational for functional style; engine implementers deferred it over debuggability/stack-trace concerns. Treat it as non-portable.
- When a codebase claims "tail recursion" as an optimization, verify on V8/Node — assume it doesn't help.

### 4) **Common confusion**

- "Recursion is always slower" — not for tree-structured data; rewriting `fib` iteratively with O(n) memory may be clearer, but divide-and-conquer quicksort recurses naturally.
- "Tail recursion prevents RangeError everywhere" — only on JSC; V8/SpiderMonkey still throw.
- "Trampolines are free" — they trade stack for heap thunks and a loop; fine for rare deep calls, overkill for shallow ones.
- "Mutual recursion is rarer than self-recursion" — mutual recursion is common in parsers and state machines; same exhaustion rules apply.

### 5) **Performance note**

Call overhead dominates deep linear recursion; each frame saves return address + locals. Trampolines replace frames with heap thunks — slower per step but bounded. For hot numeric loops, a plain `for` loop is fastest (no per-call overhead) — [measure](<../../../01 Fundamentals and Mental Model/sections/2. How JavaScript executes/2.1. Parse bytecode JIT pipeline and single-threaded execution.md>).

### 6) **Mentor note**

Have a junior make `factorial(100000)` throw, then fix it iteratively — the lesson is "depth correlates with input → iterate". Then show the trampoline as a middle ground when recursion shape is genuinely clearer. In review, flag any recursion where depth is `n` from external input (API page count, file lines, retry count) — that `n` will eventually be 1e5 in production.
