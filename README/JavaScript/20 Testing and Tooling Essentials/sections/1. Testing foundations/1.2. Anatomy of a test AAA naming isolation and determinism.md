## 1.2. Anatomy of a test AAA naming isolation and determinism

### 1) **AAA — Arrange, Act, Assert in one screen**

**Definition** — AAA is the three-line narrative: *Arrange* puts the world in a known state, *Act* calls exactly one behavior, *Assert* checks one observable outcome (return value, thrown error, or interaction). One screen ≈ 10–20 lines; if longer, extract a builder helper.

**What problem it solves / history** — before AAA, tests were "script that happened to use `assert`" with interleaved setup and multiple acts, producing failures that didn't point to a cause. AAA (Bill Wake, 2001) isolates the cause to the Act, so the failure diff tells you *which behavior* broke, not *which script* failed.

**Modern guidance** — one act per test, one behavior per name. Prefer `Arrange: const input = …` on its own lines over `assert.equal(fn(makeInput()))` one-liners. Keep Arrange minimal — only fields the Act reads.

```js
const assert = require("node:assert/strict");

function clamp(n, lo, hi) { return Math.min(Math.max(n, lo), hi); }

// Good: AAA visible, one act, one assertion focus
{
  // Arrange
  const n = -2, lo = 0, hi = 10;
  // Act
  const got = clamp(n, lo, hi);
  // Assert
  assert.equal(got, 0);
}

// Bad: two acts and two concerns in one test (which act broke?)
{
  assert.equal(clamp(-2, 0, 10), 0);
  assert.equal(clamp(12, 0, 10), 10); // split into two tests with two names
}

// Extract builder when Arrange repeats
function makeOrder(overrides = {}) {
  return { id: "a", qty: 2, price: 9, ...overrides };
}
assert.equal(makeOrder({ qty: 5 }).qty, 5);
console.log("AAA ok");

// Teardown is the 4th A when needed: Arrange/Act/Assert/After
// Node's afterEach/after hooks are the After — see runner leaf.
```

**Common confusion** — "AAA means three `//` comments." Comments help juniors, but the structure is about *isolated Act* and *minimal Arrange*, not comment count.

### 2) **Naming as documentation — `when/then` and `should` vs `it renders`**

**Definition** — a good name states the *scenario* (`when qty > hi`) and the *expected contract* (`then clamps to hi`), or the invariant (`should reject non-string id`). A bad name restates the code (`test clamp` or `it works`).

**Modern guidance** — two proven forms:
- `when <input/boundary> then <outcome>` — precise for unit branches.
- `should <contract> when <condition>` — good for validation.

Bad names hide intent; good names survive without reading the body and make `node --test --test-name-pattern` filtering useful.

```js
const assert = require("node:assert/strict");

function isValidId(id) {
  return typeof id === "string" && id.trim().length >= 3 && !/\s/.test(id);
}

// Bad names — you must read the body to know what is tested
function bad1(){ assert.equal(isValidId(" ab"), false); }
bad1();

// Good names — the name is the spec; --test-name-pattern can filter by "when"
const cases = [
  ["when id has leading space then invalid", " ab", false],
  ["when id is exactly 3 chars then valid", "abc", true],
  ["when id empty then invalid", "", false],
];
for (const [name, input, want] of cases) {
  const got = isValidId(input);
  assert.equal(got, want, name);
}
console.log("naming ok");

// Output-focused name for a throwing contract
function parseQty(s) {
  const n = Number(s);
  if (!Number.isInteger(n)) throw new RangeError("qty must be int");
  return n;
}
assert.throws(() => parseQty("3.5"), { name: "RangeError", message: /int/ });
console.log("naming contract ok");
```

**Mentor note** — in review, if you can delete the name and still know what the test covers from the assertion message, the name is noise. Rewrite it. Use `describe` to group a subject, `it("when … then …")` to state each branch.

**Performance note** — naming has zero runtime cost, but filtering cost matters: `node --test --test-name-pattern="when qty"` should select exactly the branch suite. Vague names break selective re-runs.

### 3) **Isolation and determinism — seeded RNG, no shared mutable, no wall clock**

**Definition** — a test is *isolated* when its outcome depends only on its own Arrange, not on another test's leftovers. It is *deterministic* when the same code always yields the same pass/fail (no `Date.now`/`Math.random`/global `Map` bleed).

**What problem it solves** — shared mutable (`let db = new Map()` at file top) and wall-clock (`Date.now()`) make tests order-dependent and flaky (`sleep(10)` passes on your laptop, fails in CI). Determinism is why `mock.timers` and clock seams exist.

**Modern guidance** — three rules:
1. **No shared mutable** — create fresh `Map`/`object` per test in `beforeEach` or inside the test; reset module state with `mock.reset()` or `t.after`.
2. **No wall clock** — pass a `clock = { now: () => Date.now() }` seam; in tests inject `{ now: () => 1_700_000_000_000 }` or enable `mock.timers` (see [4.2](../4. Async timing and flake control/4.2. Determinism fake timers race timeouts retries and flake hygiene.md)).
3. **No unseeded RNG** — inject a `rand` or use a seeded PRNG (e.g. `mulberry32`) rather than `Math.random()`.

```js
const assert = require("node:assert/strict");

// Bad: shared mutable leaks across tests (order-dependent)
let shared = { n: 0 };
function incBad(){ return ++shared.n; }
assert.equal(incBad(), 1);
assert.equal(incBad(), 2); // second test's expectation depends on first test having run
shared = { n: 0 }; // manual reset is a smell — use fresh per test

// Good: fresh Arrange per test
function incFresh(state){ return state.n + 1; }
assert.equal(incFresh({ n: 0 }), 1);
assert.equal(incFresh({ n: 0 }), 1); // same input → same output, always

// Bad: wall clock — today passes, tomorrow fails if you assert an absolute ISO string
function isExpiredBad(expiryIso){ return new Date(expiryIso) < new Date(); }
// Good: clock seam — deterministic
function isExpired(expiryMs, clock = { now: () => Date.now() }) { return expiryMs < clock.now(); }
const frozen = { now: () => 1_700_000_000_000 };
assert.equal(isExpired(1_700_000_000_001, frozen), false);
assert.equal(isExpired(1_699_999_999_999, frozen), true);

// Bad: Math.random makes snapshot / branch nondeterministic
function pickBad(arr){ return arr[Math.floor(Math.random()*arr.length)]; }
// Good: seeded PRNG for reproducible tests
function mulberry32(seed){ return function(){ let t = seed += 0x6D2B79F5; t = Math.imul(t ^ t>>>15, t|1); t ^= t + Math.imul(t ^ t>>>7, t|61); return ((t ^ t>>>14) >>> 0) / 4294967296; }; }
const rand = mulberry32(42);
function pick(arr, rnd = rand){ return arr[Math.floor(rnd()*arr.length)]; }
assert.equal(pick(["a","b","c"], () => 0.1), "a");
console.log("isolation ok");
```
