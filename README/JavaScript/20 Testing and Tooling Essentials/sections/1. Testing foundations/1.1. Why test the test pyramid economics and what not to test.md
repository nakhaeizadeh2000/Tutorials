## 1.1. Why test the test pyramid economics and what not to test

### 1) **Pyramid over ice-cream — unit dominates, e2e caps**

**Definition** — the test pyramid is a proportion rule: many fast, isolated unit tests at the base, fewer integration tests that wire two real collaborators in the middle, a handful of slow end-to-end (e2e) paths at the top. The inverted "ice-cream cone" (few units, many e2e) is the anti-pattern. "Diamond" (bulging integration) appears when every unit is mocked and confidence comes only from integration suites.

**What problem it solves / history** — without a pyramid, suites are either too slow to run on every save (e2e-only) or too mocked to catch wiring bugs (unit-only with over-mocking). The pyramid comes from Mike Cohn's agile testing (2009) and survives because it balances *feedback speed* (units run in ms), *confidence* (integration catches contract drift), and *cost* (e2e flake and maintenance are ~10× a unit).

**Modern guidance** — as of ECMAScript 2026 / Node 22 LTS: aim ~70 % unit, ~20 % integration, ~10 % e2e by *count* (not by line coverage). Unit = one JS module's exported function, no I/O. Integration = your `parseOrder` + real `JSON.parse` + a fake `fetch` or an in-memory `Map` DB, not a full HTTP server. e2e = `node --test` spawning a real subprocess or Playwright hitting a route. If e2e outnumber units, invert.

```js
// Pyramid shape — what each layer owns (not what framework to pick)
const assert = require("node:assert/strict");

// Unit: pure logic, no I/O, runs in ~0.2 ms
function clamp(n, lo, hi) { return Math.min(Math.max(n, lo), hi); }
assert.equal(clamp(5, 0, 10), 5);
assert.equal(clamp(-2, 0, 10), 0);
assert.equal(clamp(12, 0, 10), 10);

// Integration: two real collaborators (parser + validator), fake clock not needed
function parseOrder(json) {
  const o = JSON.parse(json); // real JSON
  if (typeof o.id !== "string") throw new TypeError("id string");
  return { id: o.id, qty: clamp(o.qty, 1, 99) };
}
assert.deepEqual(parseOrder('{"id":"a","qty":200}'), { id: "a", qty: 99 });
assert.throws(() => parseOrder('{"qty":2}'), /id/);

// e2e (illustrative — would be a separate process / HTTP call in a real suite)
// here just documented as "one path that hits the real entry point"
assert.equal(typeof parseOrder, "function");
console.log("pyramid demo ok");
```

**Common confusion** — "more tests = more safety." A tautological test (`assert.equal(getX(), obj._x)`) adds maintenance without catching a wiring or branch bug. Pyramid *size* without *branch* thought is theater.

**Performance note** — unit suites should finish in seconds, not minutes, so they run on every save. If your `npm test` takes >30 s for 200 tests, you have an ice-cream cone (likely e2e hitting disk/network in what should be units). Move I/O behind a `clock`/`fs` seam and fake it — see [3.1](../3. Mocks and test doubles/3.1. Test doubles taxonomy dummy stub spy mock fake and when each fits.md) and [§4.2](../4. Async timing and flake control/4.2. Determinism fake timers race timeouts retries and flake hygiene.md).

**Mentor note** — make juniors draw the pyramid for their current PR: label each new test as U/I/E. If E > U, require a rewrite. The interview signal is "pyramid as cost/benefit trade-off," not "pyramid as dogma."

### 2) **Economics — cost of a bug × probability vs cost of a test × flake rate**

**Definition** — a test is worth writing when `E[cost of bug] > E[cost of test]` over the lifetime of the code. `E[cost of bug] = severity × reach × probability`; `E[cost of test] = write cost + (run time × runs) + (flake rate × triage time)`.

**Modern guidance** — prioritize: parsing/coercion branches (see [Values 2.2](<../../../03 Values Types and Coercion/sections/2. The conversion algorithms/2.2. ToString and ToNumber the exact conversion tables.md>)), money-rounding/Date math (see [Numbers 7.1](<../../../12 Numbers Dates Math and Temporal/sections/7. Common pitfalls to production bugs/7.1. Real production bugs caused by number and date mistakes.md>)), and concurrency/yielding (see [Async 7.1](<../../../13 Async Event Loop and Promises/sections/7. Common pitfalls to production bugs/7.1. Real production bugs caused by async mistakes.md>)). Deprioritize trivial accessors that have no branching and are covered transitively by integration tests. Table of ROI:

| Code under test | Bug cost if wrong | Test cost | Verdict |
|---|---|---|---|
| `clamp` / `isValidId` / `parseOrder` branch | high (silent data corruption) | 3 lines + 2 ms | **must test** |
| `getX() { return this._x; }` | low (no branch) | tautology + churn | **skip** |
| `Date.plusDays` DST path ([Numbers 4.2](<../../../12 Numbers Dates Math and Temporal/sections/4. Legacy Date/4.2. Date timezones UTC vs local DST and arithmetic traps.md>)) | high (billing off by 1 day) | 5 lines, deterministic | **must test** |
| UI pixel value `MARGIN = 8` | low | snapshot churn | **visual fixture, not unit** |

```js
const assert = require("node:assert/strict");
// High ROI: branch that silently corrupts money/reporting
function toCents(s) { // "12.34" → 1234
  if (!/^\d+\.\d{2}$/.test(s)) throw new SyntaxError("cents format");
  return Math.trunc(Number(s) * 100); // 12.34*100 may be 1233.999...
}
assert.equal(toCents("12.34"), 1234);
assert.throws(() => toCents("12.3"), SyntaxError);

// Low ROI: tautology — this test only asserts you typed the same literal twice
const MARGIN = 8;
assert.equal(MARGIN, 8); // don't ship — no branch, no contract, no bug

// Better: test the *use* of the constant, not the constant itself
function layout(w) { return w - MARGIN * 2; }
assert.equal(layout(100), 84);
console.log("economics demo ok");
```

**Mentor note** — require a one-sentence "why this test pays for itself" in PR descriptions. The senior signal is distinguishing *branch* tests from *literal* tests.

### 3) **What not to test — framework invariants and tautologies**

**Definition** — don't test what you didn't write: stdlib invariants (`Array.isArray`, `Object.keys`, `JSON.parse` RFC compliance), language syntax, or a function that is a renamed field. Do test *your* translation of external data into your domain contract.

**Modern guidance** — three filters before adding a test:
1. **Branch filter** — does the code contain `if`/`?:`/`switch`/`throw`/`?.`/`??`/coercion that can take two paths? If not, a test is a copy of the declaration.
2. **Contract filter** — is there an external caller that depends on the output shape/error type? If the caller is only the test, delete it.
3. **Bug-history filter** — has this area produced a bug in the last year (coercion, Date DST, `Promise` fan-out)? Prioritize those.

```js
const assert = require("node:assert/strict");
// Bad: testing the language, not your code
assert.equal([1,2].map(x=>x*2).length, 2); // tests Array.prototype.map exists
assert.equal(typeof "hi", "string");

// Bad: tautology getter
class Box { constructor(x){ this._x = x; } get x(){ return this._x; } }
const b = new Box(3);
assert.equal(b.x, 3); // copies declaration — no branch

// Good: test your domain predicate (coercion branch you own)
function isValidId(id) {
  return typeof id === "string" && id.trim().length >= 3 && !/\s/.test(id);
}
assert.equal(isValidId(" ab"), false); // coercion + trim + length vs regex — 3 branches
assert.equal(isValidId("abc"), true);
assert.equal(isValidId(""), false);

// Good: test data-boundary translation, not the literal
function parseQty(v) { // external string → internal int | throw
  const n = Number(v);
  if (Number.isNaN(n)) throw new TypeError("qty NaN");
  if (!Number.isInteger(n)) throw new RangeError("qty int");
  return n;
}
assert.equal(parseQty("3"), 3);
assert.throws(() => parseQty("3.5"), RangeError);
console.log("what-not-to-test demo ok");
```

**Common confusion** — "100 % line coverage means done." Line coverage can be 100 % with 0 % branch coverage on `return a ?? b` or `x ? y : z` — see [5.1](../5. Quality gates and tooling/5.1. Coverage with c8 v8 line branch function thresholds and lies.md) for why branch gates matter.
