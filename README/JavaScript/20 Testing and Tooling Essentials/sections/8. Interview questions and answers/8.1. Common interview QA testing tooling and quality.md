## 8.1. Common interview Q&A testing tooling and quality

### 1) **The classics with mechanism-level answers**

**Q1 — Pyramid vs diamond vs ice-cream — which shape and why?**
*Answer:* pyramid — many fast units, fewer integration, handful e2e — gives fast feedback (units ~ms) and confidence (integration catches wiring), while ice-cream (few units, many e2e) is slow/flaky and diamond (integration bulge) appears when every unit is mocked. See [1.1](../1. Testing foundations/1.1. Why test the test pyramid economics and what not to test.md).

**Q2 — AAA — what does each A own and why one Act?**
*Answer:* Arrange (known state), Act (one behaviour), Assert (one observable outcome), plus implicit After (teardown). One Act isolates the cause so the failure diff points to that behaviour. Multiple acts in one test need splitting.

**Q3 — `node:assert/strict` vs `node:assert` — which import and why?**
*Answer:* `node:assert/strict` — its `equal`/`deepEqual` are `strictEqual`/`deepStrictEqual` via `===`/`Object.is`, so `1 == "1"` correctly fails and `NaN`/`-0` behave per spec. Loose `node:assert` hides coercion. See [2.2](../2. Node test runner and assertions/2.2. node assert strict deepStrictEqual throws rejects and assertion ergonomics.md).

**Q4 — `deepStrictEqual` vs `deepEqual` — when do they diverge?**
*Answer:* `deepStrictEqual` uses `Object.is` at leaves (`NaN` equals `NaN`, `-0` vs `0` different, `Buffer`/`Date` by value strictly); `deepEqual` is loose and treats `1` vs `"1"` as equal on some paths. Use `deepStrictEqual`.

**Q5 — `assert.throws` vs `assert.rejects` — which for `Promise`?**
*Answer:* `throws` for sync `throw`, `rejects` for a `Promise` rejection — must `await assert.rejects(promise)`. `throws` on a `Promise` that rejects passes silently.

**Q6 — `toBe` vs `toEqual` vs `toContain` — what equality?**
*Answer:* `toBe` is `Object.is` (distinguishes `NaN`/`-0`), `toEqual` is deep-strict, `toContain` is membership. `expect(a).toBe(b)` on objects checks reference; `toEqual` checks value. See [2.3](../2. Node test runner and assertions/2.3. Matchers snapshots and assertion libraries expect style and custom matchers.md).

**Q7 — Snapshot — when helpful and when rot?**
*Answer:* helpful for *wide* stable outputs (rendered report, error shape); rot when capturing time/id/unsorted keys. Freeze clock, seed id, narrow to contract fields; `--update` must be a reviewed PR.

**Q8 — Dummy vs stub vs spy vs mock vs fake — pick for `fetch`.**
*Answer:* dummy (fill arity, never called), stub (canned `200` for `GET /a`), spy (record `calledWith("/a")`), mock (spy + expectation), fake (in-memory `fetch` that really parses URL). Prefer stub/spy for queries, fake for `fetch`/`clock`, mock rarely for protocol. See [3.1](../3. Mocks and test doubles/3.1. Test doubles taxonomy dummy stub spy mock fake and when each fits.md).

**Q9 — `mock.fn` vs `mock.method` — what restores?**
*Answer:* `mock.fn()` creates a standalone spy; `mock.method(obj,"m")` replaces `obj.m` in place and is restored by `mock.restoreAll()` / `mockFn.mock.restore()`. Every `mock.method` needs `t.after(() => mock.restoreAll())` — leak poisons the next test.

**Q10 — `mock.timers` — what does `tick` do to `setInterval`?**
*Answer:* `enable({ apis: ["setTimeout","Date"] })` fakes those globals; `tick(ms)` advances virtual time and fires every timer whose deadline falls in the window — `setInterval(fn,10); tick(35)` fires 3 times. Disable with `(disable ?? reset)` per Node version.

**Q11 — `Promise` fan-out without `await` — why does the test "pass"?**
*Answer:* the runner finishes before the orphaned `Promise` settles; rejection becomes `unhandledRejection` after the test already passed. Must `await Promise.all(array.map(async …))` or `return` the promise. See [4.1](../4. Async timing and flake control/4.1. Testing promises async await event emitters and rejections.md).

**Q12 — `once(emitter,"event")` vs `emitter.once("event", cb)` — testable?**
*Answer:* `once` returns a `Promise` you can `await` and combine with `AbortSignal.timeout`; `emitter.once` registers a callback that needs manual `done` wrangling and hangs if the event never fires.

**Q13 — Deterministic time — clock seam vs `mock.timers`?**
*Answer:* seam (`clock = { now: () => … }` injected, frozen in tests) is stable on every Node; `mock.timers` fakes global `setTimeout`/`Date` for timer chains and must be `(disable ?? reset)` afterwards. Seam for deadlines, `mock.timers` for debounces.

**Q14 — `withTimeout(promise, ms)` vs `await sleep(100)` — which flakes?**
*Answer:* `sleep(100)` assumes the scheduler fired in 100 ms — flakes on slow CI. `Promise.race([p, AbortSignal.timeout(ms)])` + `withTimeout` is deterministic and leaks no handle after settle.

**Q15 — Coverage `lines 90` vs `branches 85` — which lies?**
*Answer:* `lines` can be 100 % with `branches` 50 % — `return a ?? b` is one line, two branches. Gate both; a single-line `?:` needs two tests. `catch` branch often uncovered behind a green line count.

**Q16 — Coverage lie — call without assert?**
*Answer:* calling a function increments the counter; `c8` reports covered even if no `assert` checked the result. Require an assertion for every counted call and cover `default`/`catch` explicitly.

**Q17 — ESLint `eqeqeq` + `no-floating-promises` — what do they protect?**
*Answer:* `eqeqeq` flags `==` coercion (`"" == 0` true); `no-floating-promises` flags a `Promise` that was created but not `await`ed/returned/caught — the two most common JS bug classes.

**Q18 — `npm ci` vs `npm install` in CI?**
*Answer:* `ci` deletes `node_modules` and respects `package-lock.json` byte-for-byte; `install` may mutate the lockfile and produce a green CI that doesn't reproduce locally. See [5.2](../5. Quality gates and tooling/5.2. Linting formatting static analysis ESLint Prettier type checks npm scripts workspaces and CI gates.md).

```js
const assert = require("node:assert/strict");

// Spot checks — if these fail, the classic is misunderstood
assert.equal(Object.is(NaN, NaN), true);           // toBe semantics (Q6)
assert.equal(Object.is(-0, 0), false);
assert.deepEqual({ a: NaN }, { a: NaN }); // deepStrictEqual would do the same, but == would not
try { assert.deepStrictEqual({ a: -0 }, { a: 0 }); } catch (e) { assert.equal(e.name, "AssertionError"); } // Q4

async function neg(q) { if (q<0) throw new RangeError("neg"); return q; }
(async () => { await assert.rejects(neg(-1), RangeError); })(); // Q5 — throws would miss a Promise rejection

function labelOrAnonymous(v) { if (v == null) return "anonymous"; return String(v); } // Q17 — only == null allowed with comment
assert.equal(labelOrAnonymous(null), "anonymous");

console.log("QA spot checks ok");
```

### 2) **What interviewers actually probe for**

Senior: narrating *pyramid as cost/benefit* → AAA as cause isolation → `await`+`t.after` as the async discipline → branch coverage as proof → lint as gate — in that order, not "100 % coverage means correct." Ask for a flake story: the answer should contain `mock.timers`/`clock seam`/`t.after` and `await Promise.all`, not "`sleep` and retry."

### 3) **Grading guidance**

| Signal | Junior | Mid | Senior |
|---|---|---|---|
| Pyramid | names it | applies to a PR (labels U/I/E) | justifies U vs I vs fake per economics ([1.1](../1. Testing foundations/1.1. Why test the test pyramid economics and what not to test.md)) |
| Assert | uses `ok` | uses `deepStrictEqual`/`throws` | demands `{ name, message }` + diff-aware |
| Mock | knows `mock.fn` | uses `t.after` restore | distinguishes spy vs fake vs DI seam and when to inject |
| Async | uses `async/await` | `await Promise.all` | explains orphan `unhandledRejection` and `once`+`AbortSignal` |
| Tooling | runs `npm test` | gates `c8` branch + `eslint` | owns `npm ci` vs `install` and `workspaces`/`exports` |

**Red flags:** "coverage equals quality," " `setTimeout` in a test is fine," "mock every dependency," " `toBe` is `===`," " `npm install` in CI is the same as `ci`," " `snapshot` captures the whole payload including `Date`."
