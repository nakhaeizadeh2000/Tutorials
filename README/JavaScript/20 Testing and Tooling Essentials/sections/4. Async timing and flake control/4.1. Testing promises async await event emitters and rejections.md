## 4.1. Testing promises async await event emitters and rejections

### 1) **The async contract — every `Promise` must be returned or `await`ed or chained to `t`**

**Definition** — a test that creates a `Promise` without `return`ing or `await`ing it creates an *orphan*. The runner considers the test finished before the promise settles; a rejection becomes an `unhandledRejection` (which `node --test` treats as a failure, but only after the test already passed), and a resolution is never asserted.

**What problem it solves / history** — the classic `map(async` without `await all` bug that also plagues production ([Async 7.1](<../../../13 Async Event Loop and Promises/sections/7. Common pitfalls to production bugs/7.1. Real production bugs caused by async mistakes.md>)) first appears in tests: `users.map(async u => assert.equal(await fetchUser(u), …))` without `await Promise.all` passes while assertions run *after* the test closed.

**Modern guidance** — three correct forms (pick one per test):
- `async (t) => { await promise; assert... }`
- `return promise.then(v => assert.equal(v, …))`
- `await Promise.all(array.map(async …))` inside an `async` test
Never fire-and-forget; never use `done(err)` callback style in new code — `async/await` subsumes it.

```js
const assert = require("node:assert/strict");

async function fetchQty(q) {
  if (q < 0) throw new RangeError("neg");
  return q * 2;
}

// Good: async test awaits every promise it creates
(async () => {
  await assert.rejects(fetchQty(-1), { name: "RangeError" });
  assert.equal(await fetchQty(3), 6);
  // fan-out: await the all, otherwise rejections become orphaned
  const vals = await Promise.all([1,2,3].map(async n => fetchQty(n)));
  assert.deepEqual(vals, [2,4,6]);
  console.log("awaited promises ok");
})();

// Bad: unawaited fan-out — illustrates the orphan (caught here only by awaiting at top level)
(async () => {
  const orphans = [1,2,3].map(async n => fetchQty(n));
  // missing: await Promise.all(orphans) — assertions would run after this block "passes"
  const joined = await Promise.all(orphans);
  assert.deepEqual(joined, [2,4,6]);
  console.log("fan-out must be awaited");
})();

// t-aware variant: in node:test you would `return promise` from the test fn
// test("fan-out", async () => { await Promise.all(ids.map(fetchQty)); });
console.log("async contract illustrated");
```

**Common confusion** — "`async` test handles every `Promise` inside it." It handles only the one you `await` or `return`. A `Promise.all` you create but don't `await` is invisible to the runner, even inside an `async` test.

### 2) **Reject paths — `assert.rejects` vs `try { await p; assert.fail() }`, `t.after` for cleanup, and `unhandledRejection` as a test failure**

**Definition** — `assert.rejects(promise, expected)` asserts that `promise` rejects with an error matching `expected` (`{ name, message, cause }`). The manual alternative `try { await p; assert.fail('should reject'); } catch(e){ assert.equal(e.name, …) }` is equivalent but verbose. `t.after` registers cleanup that runs even if the reject assertion fails, preventing resource leaks (open handles) from poisoning the next test.

**Modern guidance** — prefer `assert.rejects` for the happy path of rejection; use `try/catch` only when you need to assert on *multiple* properties of the error or on state after the rejection. Always pair a resource-creating async Act with `t.after(() => resource.close())` so the handle is cleared even on failure (see [Memory 5.2](<../../../18 Memory Management and GC/sections/5. Measuring and preventing leaks/5.2. Preventing leaks bounded caches eviction WeakMap and dispose patterns.md>) for dispose discipline).

```js
const assert = require("node:assert/strict");

async function fetchQty(q) {
  if (q < 0) throw new RangeError("neg");
  if (q > 100) throw new Error("too big", { cause: new RangeError("cap") });
  return q;
}

// assert.rejects — concise
(async () => {
  await assert.rejects(fetchQty(-1), { name: "RangeError", message: /neg/ });
  await assert.rejects(fetchQty(200), { name: "Error", message: /too big/ });
  await assert.doesNotReject(fetchQty(5));
  console.log("rejects ok");
})();

// manual try/catch when you need to inspect cause or side effects
(async () => {
  try {
    await fetchQty(200);
    assert.fail("should have rejected");
  } catch (e) {
    assert.equal(e.name, "Error");
    assert.equal(e.cause instanceof RangeError, true);
  }
  console.log("manual catch ok");
})();

// t.after cleanup — simulated
(async () => {
  const t = { cleanups: [], after(fn){ this.cleanups.push(fn); }, async flush(){ for(const f of this.cleanups) await f(); } };
  let opened = true;
  t.after(async () => { opened = false; });
  // Act that would reject
  await assert.rejects(fetchQty(-1), RangeError);
  await t.flush();
  assert.equal(opened, false);
  console.log("t.after cleanup ok");
})();

// unhandledRejection in a test suite fails the run — illustrate handler
process.on("unhandledRejection", (e) => {
  // In a real suite, this is a test failure — here just note it would be caught
  assert.equal(e instanceof Error, true);
});
Promise.reject(new Error("orphan")).catch(() => {}); // swallowed to keep runner green in this demo
console.log("reject paths ok");
```

**Mentor note** — in review, flag `await fetchQty(-1)` without `assert.rejects` as "asserting the wrong thing." The rejection *is* the expected outcome, not a failure to be caught.

### 3) **`EventEmitter` and streams — `once(emitter,'event')` / `on` + `AbortSignal` vs callback `done(err)` pattern**

**Definition** — some stdlib APIs are not `Promise`-based but `EventEmitter`-based (`stream`, `child_process`, `EventTarget`). Testing them means bridging events to a `Promise` so the async contract can be honoured. Node supplies `once(emitter, event, { signal })` (`node:events`) which resolves when the event fires or rejects on `error`/`abort`.

**Modern guidance** — use `const { once } = require("node:events"); await once(emitter, "ready")` rather than callback `emitter.once("ready", () => { assert…; done(); })` — the `once` promise can be `await`ed and participates in `Promise.race` timeouts naturally. Pair with `AbortSignal` so a failing test does not hang.

```js
const assert = require("node:assert/strict");
const { EventEmitter, once } = require("node:events");

// Good: once() bridges emitter → promise so await works
(async () => {
  const ee = new EventEmitter();
  const pr = once(ee, "data");
  setTimeout(() => ee.emit("data", 42), 5);
  const [val] = await pr;
  assert.equal(val, 42);
  console.log("once ok");
})();

// Stream-like: once rejects if emitter emits error before the event
(async () => {
  const ee = new EventEmitter();
  const pr = once(ee, "ready");
  setTimeout(() => ee.emit("error", new Error("boom")), 5);
  await assert.rejects(pr, /boom/);
  console.log("once rejects on error ok");
})();

// AbortSignal timeout for hanging emitters — no indefinite hang
(async () => {
  const ee = new EventEmitter();
  const ac = new AbortController();
  const pr = once(ee, "never", { signal: ac.signal });
  setTimeout(() => ac.abort(new Error("timeout")), 5);
  await assert.rejects(pr, (e) => e.name === "AbortError" && /abort/i.test(e.message));
  console.log("abort timeout ok");
})();

// Legacy done(err) anti-pattern — do not use in new tests
// test("legacy", (t, done) => { ee.once("data", v => { assert.equal(v,42); done(); }); })
// → if the event never fires, the test hangs; await once + assert is strictly better

console.log("emitter testing ok");
```

**Common confusion** — " `emitter.once` and `once(emitter,…)` are the same." `emitter.once` registers a callback; `once(emitter, …)` returns a `Promise` that the runner can `await` and that can be combined with `Promise.race`/`AbortSignal`. The latter is testable; the former needs manual `done` wrangling.
