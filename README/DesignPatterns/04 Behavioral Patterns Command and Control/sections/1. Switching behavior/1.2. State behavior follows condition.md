## 1.2. State: behavior follows condition

### 1) **States as strategy holders**

**Definition** — State encapsulates condition-dependent behavior in state objects (order lifecycle: `new`/`paid`/`shipped`/`done` — each state defines legal moves; the context delegates to its current state): behavior changes when *state* changes (transitions move the strategy internally — clients never select). Verified: `new→paid→shipped→done` lifecycle completes; illegal `new→shipped` refused with `illegal: new -> shipped` (unrepresentable transitions *unexecutable*, not just undocumented).

- **What problem it solves**: conditional behavior scatters across methods (`if (state === ...)` per operation — every method re-derives the state machine; new states touch all methods; illegal transitions possible wherever checks are forgotten). State objects centralize per-condition behavior (each state implements the interface — transitions move between complete behaviors; illegal moves refused structurally — transition tables enforced, not remembered). TCP stacks, order lifecycles, UI wizards, game entities all share the shape.
- **Modern guidance** — reach for State on condition-driven behavior with explicit transitions (lifecycles, protocols, wizards — states enumerable, moves constrained). Model transitions as data (allowed-moves table — verified `NEXT` map; illegal moves throw named errors — refusal tested per pair). Keep states behavior-complete (each state answers the full interface — partial states force `instanceof` checks downstream, defeating the pattern). Name states as domain nouns (`Paid`, `Shipped` — lifecycle language, not `State1/State2`).

```typescript
// GOOD: transitions as data, illegal moves unexecutable — verified lifecycle + refusal
const NEXT: Record<St, St[]> = { new: ["paid"], paid: ["shipped"], shipped: ["done"], done: [] };
move(to: St): void {
  if (!NEXT[this.st].includes(to)) throw new Error(`illegal: ${this.st} -> ${to}`);  // refused, verified
  this.st = to;
} // new->paid->shipped->done completes (verified); new->shipped throws (unrepresentable unexecutable).
// BAD: status strings with if-chains per method ("simpler, no classes") —
// transitions scattered (each method re-derives); illegal moves possible wherever checks forgotten
```

### 2) **Transitions explicit, not scattered**

**Definition** — legal moves declared once (transition table/map — all valid edges visible in one structure; illegal pairs absent by construction — no code path produces them): states don't decide destinations ad hoc (no `if`-ladders inside states choosing next — table-driven, reviewable, testable exhaustively). Verified refusal *is* the table working (absent pair → throw — the table's closed-world assumption enforced at runtime).

- **Why it matters (correctness)**: scattered transitions drift inconsistently (method A allows `paid→shipped`, method B allows `paid→done` — same lifecycle, contradictory rules; new states added to half the switches — partial transitions silently wrong). Explicit tables centralize the machine (one structure reviewed — additions/removals visible as data diffs; exhaustive testing enumerates the table — every pair covered: legal moves succeed, illegal throw). Statecharts (hierarchical/orthogonal states — SCXML/UML tools) extend tables where nesting demands.
- **Modern guidance** — declare transitions as data (maps/tables — reviewable diffs; code-generated diagrams where tooling exists). Test the table exhaustively (legal pairs succeed, illegal pairs throw — matrix green, the machine proven). Version transition changes explicitly (new edges reviewed as behavior changes — silent transition additions break downstream assumptions). Prefer statecharts past ~10 states (flat tables tangle — hierarchy composes, orthogonality parallelizes; tools over hand-rolls at that scale).

```bash
# GOOD: transitions reviewable as data (one table, exhaustive tests)
#  NEXT = { new: [paid], paid: [shipped], shipped: [done], done: [] } (4 states, 3 edges, 0 ambiguity).
#  tests: legal pairs succeed (3) + illegal sample throws (new->shipped verified) — matrix green.
# BAD: transition logic distributed across methods ("colocated with behavior") —
# contradictory rules per method (A allows, B forbids); new states touch all methods (scattered evolution)
```

### 3) **State vs strategy split**

**Definition** — same structure (composition + delegation to behavior holders), opposite selection ownership: Strategy varies by *client/config choice* (caller selects — leaf 1.1: `use()` called externally); State varies by *internal condition* (context transitions itself — moves triggered by domain events, never caller selection). Misclassified ownership inverts control wrongly (client-selectable states leak lifecycle control outward; context-owned strategies hide configurability inward).

- **Why it hurts when missing (correctness, maintainability)**: ownership errors corrupt lifecycles both directions (callers forcing states — `order.state = "done"` assignments bypassing transition validation, illegal states reachable by API misuse; contexts hiding strategies — configuration changes requiring context surgery instead of injection). Each passes tests (happy paths select correctly by accident) and fails at boundaries (adversarial callers force illegal states; operators can't reconfigure without deploys). Ownership asked per behavior ("who switches — caller or context?") prevents both.
- **Modern guidance** — ask ownership first (external choice → Strategy with `use()` API; internal condition → State with event-triggered moves). Never expose state setters (moves validated through transition methods — direct assignment bypasses the table; `private` + validated movers only). Never hide strategy selection inside contexts (configuration belongs at composition roots — leaf 1.2-of-02's explicit wiring; contexts receive, never choose). Reclassify on drift (client-selected "states" → strategies; context-driven "strategies" → states — names track ownership).

```bash
# GOOD: ownership asked per behavior (selection routed correctly)
#  sort order per user toggle    -> STRATEGY (caller selects: ctx.use(), leaf 1.1).
#  order status per payment event -> STATE (context transitions: move() validated, no public setter).
# BAD: order.state = "done" assignments ("flexible") or sort-strategy chosen inside SorterCtx ("encapsulated") —
# lifecycle bypassed (illegal states reachable); configurability buried (swaps need surgery)
```

### 4) **Common confusion**

- "State is just Strategy with more classes" — Strategy varies by *external choice* (caller-owned); State varies by *internal condition* (context-owned transitions). Same delegation mechanics, opposite control flow — ownership is the pattern.
- "Enums plus switches implement State" — switches reintroduce scattered transitions (leaf's core warning); table-driven moves + state objects centralize. Enums name states fine (as *data*); switches *decide* poorly.
- "Illegal transitions should be impossible statically" — typestate (states as types — Rust-flavored) proves statically where available; runtime tables with throwing refusal (verified) serve dynamic languages. Static where possible, loud refusal otherwise — never silent.
- "Statecharts are overkill" — statecharts organize past ~10 flat states (hierarchy + orthogonality — complexity absorbed structurally); flat tables below that (simpler, reviewable). Scale decides formalism.

### 5) **Performance note**

States cost one delegation hop per operation (nanoseconds — current-state dispatch, JIT-inlined at stable states) plus transition-table memory (edges × entries — trivial beside business data). Switch-chains cost branch prediction per condition (degrading with state count — strategies win measurably past ~5 states). Illegal-transition checks cost one map lookup per move (nanoseconds — refusal safety essentially free). Optimize ownership correctness first (lifecycle integrity — incidents), dispatch second (stable-state monomorphism), table size never (transitions are data, not hot paths).

### 6) **Mentor note**

Demo refusal live (verified `illegal: new -> shipped` — "unrepresentable transitions unexecutable" converts tables from documentation to enforcement). Contrast ownership explicitly ("who switches here — caller or context?" per behavior until reflexive). Trace transitions as data review (table diffs read faster than switch diffs — demonstrate on one real change). Watch for the status-string switcher ("simpler" — fix with forgotten-check autopsy: find the unguarded transition) and the ownership-blind ("flexible" setters/config-hiding — fix with lifecycle-bypass vs configurability-burial demo). Review check: transitions tabulated, illegal refused + tested, ownership asked per behavior, juniors can place new states/transitions unprompted.
