## 1.1. Strategy: interchangeable algorithms

### 1) **Family behind one interface**

**Definition** — Strategy encapsulates each algorithm behind a shared interface and makes them interchangeable (sorters: `Quick`/`Reverse` behind `Sorter` — verified `1,2,3` then `3,2,1` from one context): clients code against the interface (never the implementations), selection happens at runtime (configuration, user choice, input characteristics — decided when running, not when compiling). Algorithms become *values* (passed, stored, swapped — first-class behavior).

- **What problem it solves**: algorithm conditionals fossilize (switch-on-kind per sort/compress/route — leaf 1.2-of-01's tax wearing algorithm clothes: every new algorithm edits the conditional, re-earns its tests, conflicts per contributor). Strategies distribute algorithms to files (one class per approach — tested alone, reviewed by owners, added without touching clients). Runtime selection follows free (configuration picks implementations — behavior changes without deploys where selection is data-driven).
- **Modern guidance** — reach for Strategy on runtime-selected algorithms (sorting orders, compression codecs, routing rules, pricing engines — families varying by context). Inject strategies via constructors (context holds current — `use()` swaps explicitly; selection logic lives in callers/composition, never inside strategies). Keep strategies stateless where possible (pure algorithm objects — shared safely, tested deterministically; stateful strategies document their state lifecycle). Name strategies after approaches (`QuickSort`, `GzipCodec` — algorithm visible, selection readable).

```typescript
// GOOD: algorithms as values — verified swap pair from one context
interface Sorter { sort(xs: number[]): number[]; }
class SorterCtx {
  constructor(private s: Sorter) {}
  use(s: Sorter): void { this.s = s; }            // runtime swap: THE signature move (verified below)
  run(xs: number[]): number[] { return this.s.sort(xs); }
}
// ctx.run([3,1,2]) -> 1,2,3 (Quick); ctx.use(new Reverse()); -> 3,2,1 verified (same context, new behavior).
// BAD: sort(kind, xs) with if/else per algorithm ("simpler, one function") —
// every algorithm edits one function (conflicts); runtime selection needs redeploys (frozen at compile)
```

### 2) **Composition over conditional**

**Definition** — strategy injection retires switch-on-kind (each branch becomes a class — conditionals shrink as strategies grow: inverse maintenance curves). Verified economics from leaf 1.2-of-01 restated for algorithms: N algorithms as branches = N edits to one function (conflicts, blast radius, test matrices); as strategies = N files, zero edits to clients (independent review, isolated tests, conflict-free merges). The conditional doesn't disappear (selection *somewhere* picks — factory, config, caller) — it moves to composition roots where change is cheap.

- **Why it matters (correctness)**: algorithm conditionals corrupt under growth (branch #9 duplicates branch #3's logic drifted — copy-paste across cases; untested combinations (flag A + kind B — matrix untestable at scale); merge conflicts per algorithm addition — all contributors editing one function). Strategies isolate each algorithm's correctness (tested alone — contract suite per strategy; reviewed alone — domain expert per approach; broken alone — one strategy fails without implicating siblings).
- **Modern guidance** — extract at the second algorithm (first duplication of approach-selection logic — strategy immediately, not at the fifth branch; the rule preventing conditional fossilization). Select at composition roots (factories/config/caller choice — selection logic centralized, testable, flaggable). Share contract suites across strategies (same input/output assertions per implementation — behavioral parity where promised, divergence documented where intended). Delete the conditional when strategies land (dead branches removed, not commented — fossil code confuses).

```bash
# GOOD: conditionals shrink as strategies grow (inverse curves)
#  1 algorithm:  direct call (no pattern — YAGNI holds).
#  2 algorithms: extract strategy (second branch = yellow flag; conditional retired).
#  N algorithms: N strategy files + 1 selection site (conflict-free merges, isolated tests).
# BAD: "one more branch" × 12 algorithms ("contained") —
# contained conditionals grow unbounded; strategies would have flattened at branch two
```

### 3) **Runtime swapping is the signature**

**Definition** — strategies change *mid-life* (verified `use(new Reverse())` on a live context — behavior pivots without reconstruction): configuration flips (dark mode toggles sorting? — feature flags selecting strategies per request), adaptive selection (input size picks algorithm — small arrays insertion, large merge — measured thresholds from [AlgorithmDesign](<../../../../AlgorithmDesign/README.md)>), user choice (sort-order toggles, codec preferences — UI state mapping to strategy instances). Static selection (chosen once at construction, never changed) works identically with plain polymorphism — swapping is what *requires* Strategy.

- **Why it hurts when missing (correctness, maintainability)**: static-wired algorithms resist runtime change (rebuild contexts per switch — state transfer bugs; restart processes per config — downtime for behavior flips; redeploy per A/B variant — experiments gated on releases). Swappable strategies convert behavior changes into assignments (one `use()` call — tested paths, no reconstruction). A/B testing, feature flags, and adaptive algorithms all *need* mid-life swaps — static wiring forces workarounds (context pools keyed by strategy — accidental registries; conditional re-creation — switch-statements resurrected).
- **Modern guidance** — expose `use()`/setter switching deliberately (documented API — strategies designed for swapping carry the method; single-shot contexts omit it). Validate swaps cheaply (strategy change re-runs smoke assertions — swapped behavior verified, not hoped). Prefer immutable context+new-strategy where state transfer risks (fresh contexts avoid half-migrated state — swapping *references* beats mutating *internals*). Test every strategy through one context (swap matrix green — all implementations behind shared assertions).

```typescript
// GOOD: mid-life pivots as API (swapping designed, not hacked)
// ctx.use(new Reverse()) mid-session -> subsequent runs reversed (verified 3,2,1 — no reconstruction).
// feature flags map to strategies (flag state -> strategy instance — behavior flips without deploys).
// BAD: rebuilding contexts per behavior change ("cleaner") —
// state transfer bugs (half-migrated contexts); downtimes for flips; experiments gated on releases
```

### 4) **Common confusion**

- "Strategy needs many algorithms" — Strategy needs *varying* algorithms (2+ with runtime selection — second branch triggers extraction); single-algorithm code with strategy ceremony is speculative generality (YAGNI holds until variation arrives).
- "Strategy vs State" — Strategy varies by *client/config choice* (caller selects — leaf 1.2's ownership question); State varies by *internal condition* (context transitions itself — next leaf). Same structure (composition + delegation), opposite selection ownership.
- "Strategy vs simple polymorphism" — polymorphism *is* the mechanism; Strategy is the *pattern of use* (family + runtime selection + composition root). All strategies use polymorphism; not all polymorphism is strategic.
- "Function parameters replace Strategy" — first-class functions *implement* strategies elegantly (callbacks as strategies — idiomatic TS/JS); classes add stateful strategies (configurable algorithms — constructor parameters per instance). Functions for stateless, classes for stateful — same pattern, two spellings.

### 5) **Performance note**

Strategies cost one indirection per invocation (interface dispatch — nanoseconds, devirtualized at monomorphic sites; megamorphic contexts cost inline-cache misses — stable strategy choice per hot loop). Conditionals cost branch prediction per kind (correctly-predicted branches ~free; growing branch counts degrade prediction — strategies win measurably past ~5 kinds). Runtime swaps cost assignment + smoke assertions (microseconds — negligible against behavior-change value). Optimize selection stability first (hot loops monomorphic — avoid per-iteration swaps), branch-count second (extract past ~5), dispatch never (nanoseconds, inlined).

### 6) **Mentor note**

Demo swapping live (verified pair from one context — "same object, new behavior, one call" converts runtime selection from claim to observable). Drill extraction timing ("second branch = strategy now" — conditional fossilization prevented structurally). Contrast State explicitly ("who switches — caller or context?" — ownership decides pattern, asked per use). Watch for the switch-accumulator ("one more kind" × N — fix with inverse-curves arithmetic) and the static-strategist (strategies never swapped — fix with "what selects at runtime here? nothing → polymorphism suffices"). Review check: families behind interfaces, selection at roots, swaps tested per strategy, juniors can place new algorithms unprompted.
