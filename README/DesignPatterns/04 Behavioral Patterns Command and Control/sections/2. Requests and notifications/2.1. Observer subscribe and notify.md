## 2.1. Observer: subscribe and notify

### 1) **One-to-many without coupling**

**Definition** — Observer distributes events to subscribers without either side naming the other (subjects hold callback lists — `sub()` registers, `pub()` notifies; verified fan-out: 2 subscribers, both receive `hi`): subjects never import observers (new subscriber types arrive without subject edits — OCP satisfied structurally); observers never poll subjects (push replaces polling loops — latency event-driven, not interval-bound). EventEmitter, signals, and reactive primitives all wear this shape.

- **What problem it solves**: polling wastes (interval checks for rare events — CPU burned on unchanged state; latency floored at interval length — responsiveness capped by timer granularity), and direct notification welds (subject importing concrete observers — new subscriber kinds edit the subject; N×M wiring between producers/consumers — topologies only architects fully map). Observer decouples both directions (producers emit, consumers attach — independently evolvable, independently testable).
- **Modern guidance** — reach for Observer on state-change fan-out (model updates → views, events → handlers, data → derived computations — one-to-many with producer ignorance). Depend on subscriber *interfaces* (callback signatures — `(m: string) => void`; concrete observers invisible to subjects). Prefer platform primitives where they exist (EventEmitter, signals, RxJS Subjects — the future [RxJS track](<../../../../README.md>) will own stream mechanics; borrowed mechanics, owned usage here). Keep payloads immutable (frozen event objects — subscriber mutation corrupting siblings is the shared-state incident wearing events).

```typescript
// GOOD: decoupled fan-out — verified both receive, neither named by subject
class News {
  private subs = new Map<number, (m: string) => void>();  // callbacks, not concretes
  sub(f: (m: string) => void): number { /* register, return id */ return 0; }
  pub(m: string): void { for (const f of [...this.subs.values()]) f(m); }  // snapshot (next section)
} // pub("hi") -> ["a:hi","b:hi"] verified (producer ignorant, consumers attached independently).
// BAD: subject importing observers ("direct") —
// new subscriber kind edits subject (OCP violated); N×M wiring tangles; polling fallback wastes + lags
```

### 2) **Order-independence required**

**Definition** — observers must tolerate *any* notification sequence (subscription order is incidental — verified `a` before `b` today, reversed tomorrow after unsubscribe/resubscribe cycles; concurrent dispatch interleaves arbitrarily): depending on order couples observers through the subject (hidden sequencing contracts — B assumes A ran first; reorderings break B silently). Snapshot iteration (`[...subs.values()]` — verified pattern) additionally tolerates mutation-during-notify (unsubscribing mid-dispatch doesn't skip or double-deliver).

- **Why it matters (correctness)**: order-dependent observers fail on reordering inputs (test suites subscribing in fixed order pass; production attaching dynamically breaks — sequence assumptions violated by arrival order); mutation-during-notify corrupts iteration (unsubscribe shifting live arrays — observers skipped; subscribe appending mid-loop — new observers partially notified, inconsistent worldviews). Both failures are silent-ordering (outputs plausible, sequence wrong — debugging misattributes to logic instead of dispatch).
- **Modern guidance** — document order-independence as contract ("observers execute in unspecified order" — stated on `sub()`, enforced by shuffling in tests). Snapshot before dispatch (`[...values()]` — mutation-safe iteration; cost one array alloc per event — negligible beside handler work). Test with shuffled subscription orders (permutation coverage — order-dependent observers fail loudly in CI, not silently in production). Never rely on dispatch sequence for correctness (priority needs explicit phases — ordered pipelines, not observer order).

```typescript
// GOOD: order-tolerant by contract, mutation-safe by snapshot (verified pattern)
// [...this.subs.values()] — dispatch over a snapshot (mid-notify unsub/resub shifts nothing).
// contract: "notification order unspecified; observers must tolerate any sequence" (stated on sub()).
// BAD: "first subscriber runs first" relied upon ("consistent in practice") —
// resubscribe cycles, dynamic attach, concurrent dispatch all reorder; incidental order is not contract
```

### 3) **Leak discipline mandatory**

**Definition** — subscriptions are resources: `sub()` returns an id/handle, `unsub(id)` releases (verified: 2 subs → unsub one → count **1** — pairing enforced); undisposed subscriptions leak (lapsed listeners — destroyed UI components still notified: exceptions on dead views, memory held by subject references, zombie updates corrupting new state). Every subscribe needs a paired unsubscribe (RAII-shaped discipline — acquisition returns releaser; teardown calls it unconditionally).

- **Why it hurts when missing (correctness, maintainability)**: lapsed-listener leaks are the top observer incident shape (long-lived subjects × short-lived observers — app-lifetime event buses holding destroyed components: memory grows per navigation, stale handlers fire on dead views, exceptions cascade from ghost contexts). Each leaks silently (no error at subscribe time — accumulation visible only in heap snapshots or ghost-update bugs). Frameworks mitigate (auto-unsubscribe on destroy — Angular `async` pipe, React effect cleanups, AbortController signals), but manual subscriptions need manual discipline everywhere else.
- **Modern guidance** — pair every `sub` with `unsub` structurally (return disposables — `{ [Symbol.dispose]: () => unsub(id) }` with `using` where supported; effect-cleanup returns in React; `takeUntil(destroy$)` in RxJS). Prefer weak references where listeners shouldn't prolong subjects (WeakRef observers — GC collects unreachable listeners; lapsed-listener class eliminated structurally). Assert subscription counts in tests (count 1 after unsub — verified pattern as unit-test shape; growth assertions catch leaks in CI, not production heap dumps).

```typescript
// GOOD: subscriptions as resources (paired lifecycle — verified 2 → unsub → 1)
// sub() returns id; unsub(id) releases (boolean result — double-unsub visible, not silent).
// count assertion in tests (subs: 1 verified — leak discipline unit-tested, not hoped).
// frameworks: effect-cleanup returns, async-pipe auto-unsub, AbortController signals (discipline mechanized).
// BAD: "fire-and-forget subscriptions" in long-lived subjects ("GC handles it") —
// subject references PROLONG observers (reachable = uncollectable); lapsed listeners accumulate per navigation
```

### 4) **Common confusion**

- "Observer means EventEmitter" — EventEmitter *implements* Observer (named channels + fan-out — one mechanics choice); Observer means *decoupled one-to-many* (signals, callbacks, reactive streams all qualify). Pattern vs implementation — again.
- "More observers = better decoupling" — observers decouple *producer from consumers*; consumer-count growth taxes dispatch (fan-out latency per event — N handlers × cost; ordering hazards multiply). Decouple structurally, budget fan-out arithmetically.
- "Unsubscribe is optional cleanup" — unsubscribe is *correctness* (lapsed listeners corrupt — ghost updates, memory growth, stale exceptions), not hygiene. Optional cleanup is for cosmetics; pairing is for correctness.
- "Synchronous dispatch is always right" — sync dispatch couples producer timing to slowest observer (UI jank per heavy handler); async/microtask dispatch decouples timing (ordering guarantees weaken — choose per latency contract, document the choice).

### 5) **Performance note**

Observer dispatch costs handlers × cost-each per event (verified probes single-digit ms at these sizes; fan-out linear in subscribers — budget per event type, not per system); snapshot iteration adds one array alloc per dispatch (negligible beside handler work — safety essentially free); lapsed listeners cost memory per survivor plus exception risk per ghost-fire (unbounded accumulation — the incident economics dwarf dispatch constants). Optimize fan-out breadth first (subscriber counts per event — split hot topics), handler cost second (slow observers async-decoupled), dispatch mechanics never (Map iteration + snapshot already near floor).
