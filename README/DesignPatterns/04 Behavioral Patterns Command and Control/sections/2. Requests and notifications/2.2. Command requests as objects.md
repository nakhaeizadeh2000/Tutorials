## 2.2. Command: requests as objects

### 1) **Encapsulate invocation**

**Definition** — Command reifies a request as an object (receiver + action + arguments frozen as values — `Inc(counter)` holding its target; `do()` executes, `undo()` reverses): invocations become storable (histories), passable (queues), composable (macros), loggable (journals) — verbs turned into nouns with lifecycles. Verified: two `do()` → count **2**, one `undo()` → **1** (history-stack discipline working — each command knows its own inverse).

- **What problem it solves**: direct invocation discards request structure (method called — arguments evaluated, receiver bound, moment passed — nothing retained for undo/retry/audit/scheduling). Reifiable needs (undo stacks, macro recording, request queues, transactional journals, remote execution — all requiring *the request itself* as data) have nowhere to live without Command. Encapsulation converts calls from events into objects (inspectable, storable, reversible — the vocabulary undo/redo/queue/log needs).
- **Modern guidance** — reach for Command on reifiable-request needs (undo/redo, macros, queues, journals, schedulers — lifecycle verbs attached). Encapsulate receiver + arguments together (command owns everything its execution needs — no ambient state consulted at `do()` time; determinism by construction). Keep commands small and single-purpose (one action per class — macro commands *compose* singles; god-commands recreate the objects they replaced).

```typescript
// GOOD: requests as values — verified 2 → undo → 1
interface Cmd { do(): void; undo(): void; }
class Inc implements Cmd {
  constructor(private c: Counter) {}   // receiver + (no) args frozen at construction
  do(): void { this.c.n++; }
  undo(): void { this.c.n--; }         // inverse known by construction (not derived later)
}
// do();do() -> 2 verified; undo() -> 1 verified (history-stack discipline: each command reverses itself).
// BAD: method calls + separate "undo log" of strings ("simpler") —
// log entries lack receivers/arguments (reconstruction guesswork); inverses hand-derived per case (drift)
```

### 2) **Undo/redo/queue/log fall out**

**Definition** — one pattern, four dividends: *undo* (history stack — pop reverses; verified), *redo* (undone-stack replayed on new-branch-clear — standard two-stack discipline), *queue* (commands scheduled/delayed/batched — invokers need no receiver knowledge), *log* (command journals replayed for crash recovery — event sourcing's primitive). Each dividend reuses the same `do()`/`undo()` contract — implemented once per command, composed freely by invokers (macro commands nesting singles — trees of reversibility, leaf 3.1-of-03's composite wearing behavior).

- **Why it matters (correctness)**: ad-hoc undo reimplements per feature (editor undo vs form undo vs canvas undo — three mechanisms, three bug surfaces, zero shared testing; queueing bolted onto direct calls — retry logic duplicating invocation knowledge; audit trails as afterthought logs — irreproducible summaries instead of replayable journals). Command unifies (one contract per action — undo/redo/queue/log compose from shared primitives; tested once, dividend four times). Macro composition extends (nest commands arbitrarily — reversibility composes structurally).
- **Modern guidance** — implement `undo()` with every `do()` (pairs shipped together — undo-less commands are tech debt with interest; code review rejects solo `do()`). Clear redo on new branches (standard discipline — new action invalidates replayed futures; documented, tested). Journal critical commands (persisted `do()` streams — crash recovery replays journals; event sourcing *is* Command at architectural scale — Domain 06's territory previewed). Bound history explicitly (cap stacks — unbounded undo is memory incident wearing UX; ring buffers or count caps, stated).

```bash
# GOOD: one contract, four dividends (implemented once per command, composed per invoker)
#  undo: history.pop().undo() (verified 2->1) / redo: undone-stack replay (cleared on new branch).
#  queue: scheduler holds Cmd[] (receivers unknown to invoker — decoupling preserved).
#  log: journal do() stream (crash recovery replays — event sourcing primitive, Domain 06).
# BAD: per-feature undo mechanisms ("tailored") —
# editor/form/canvas undo reimplemented thrice (bug surfaces tripled); queues bolted onto direct calls
```

### 3) **Commands vs callbacks split**

**Definition** — callbacks fire-and-forget (functions invoked — no lifecycle, no inverse, no identity); commands persist with lifecycle (constructed → queued/executed → undoable/loggable — reifiable throughout). Callbacks suit fire-once notifications (event handlers without undo needs — leaf 2.1's observers *are* callbacks, correctly); commands suit managed invocations (anything needing undo/queue/retry/audit — lifecycle verbs that functions can't carry). Choosing by lifecycle need, not familiarity.

- **Why it hurts when missing (correctness, maintainability)**: callbacks stretched into command duty lose lifecycle silently (undo via closure-captured inverses — hand-derived per case, untestable in isolation; queues of closures — opaque payloads, undebuggable backlogs; retry by re-calling — arguments reconstructed approximately). Commands stretched into callbacks over-engineer (one-shot notifications wrapped as classes — ceremony without lifecycle payoff). The split is lifecycle-shaped: needs undo/queue/log/audit → Command; needs fire → callback.
- **Modern guidance** — default to callbacks for fire-once (handlers, completions, notifications — no lifecycle needed, none built). Graduate to Command at first lifecycle verb (undo *or* queue *or* retry *or* audit — one need justifies reification; two mandate it). Keep commands data-rich (receiver + args + metadata — debuggable queues show *what* waits; opaque closures show addresses). Interoperate freely (commands constructed from callbacks where fire-meets-manage — adapters between, Domain 03 §1.1's translation at the seam).

```typescript
// GOOD: lifecycle decides (fire → callback; manage → command)
// notify: observer callbacks (leaf 2.1 — fire-once, no undo needed, correctly light).
// edit: command objects (undo/redo/queue/log needed — lifecycle verbs functions can't carry).
// BAD: closure-queues for undoable work ("lighter") —
// opaque payloads (undebuggable backlogs); hand-derived inverses (untestable drift); lifecycle faked
```

### 4) **Common confusion**

- "Command needs a framework" — Command needs *two methods* (`do`/`undo` — the contract fits in an interface; invokers are arrays with discipline). Frameworks scale command systems (routers, buses); the pattern starts with a stack.
- "Undo requires mementos" — undo requires *inverses* (command-known reversals — `n--` for `n++`); mementos snapshot *state* (Domain 05 — restore-without-inverse-knowledge). Inverses where computable (arithmetic, toggles); snapshots where not (complex mutations) — complementary, not competing.
- "Commands are just callbacks with extra steps" — callbacks lack identity/lifecycle (fire-once values); commands carry both (reifiable throughout). Extra steps *are* the pattern (undo/queue/log need them).
- "Macro commands need special support" — macros *compose* commands (tree of `do()`/`undo()` — leaf 3.1-of-03's composite wearing behavior; nesting free once singles exist). Composition, not machinery.

### 5) **Performance note**

Commands cost one allocation per invocation (object vs bare call — short-lived, GC-nursery cheap; hot loops batch commands or revert to direct calls where profiles demand). Histories cost entries × command size (bounded explicitly — caps stated; unbounded undo is memory incident). Queues cost holding time (backlog memory — depth monitored, overflow policies stated). Callback alternatives cost nothing per call (direct invocation — cheapest fire-once). Optimize lifecycle-need first (commands where managed, callbacks where fired — correct shape dominates), allocation second (pool only profiled hot command paths).
