## 3.1. Template Method: skeleton with hooks

### 1) **Invariant skeleton, variant steps**

**Definition** — Template Method defines an algorithm's *sequence* in a base method (generate: header → body → footer, owned once) while *steps* vary by subclass (abstract `buildBody()` required; `header()`/`footer()` defaulted overridable hooks): subclasses fill blanks, never reorder. Verified: `Sales` → `H|sales|F`; `SalesVerbose` (header hook only) → `H+|sales|F` (sequence identical, step varied — skeletons stable, hooks flexible).

- **What problem it solves**: algorithm duplication across variants (report generators copying header/footer sequencing per report — order drift per copy; ETL pipelines re-sequencing extract/transform/load per source — step-skipping bugs where sequences diverge). Skeletons centralize order (sequence written once — all variants share it); hooks distribute variation (steps overridden per kind — each variant supplies differences only). New variants add steps, never re-derive sequences.
- **Modern guidance** — reach for Template Method on fixed-sequence/varying-step workflows (reports, ETL, request pipelines, test fixtures — skeletons stable, steps pluggable). Declare steps abstract-or-defaulted explicitly (required vs optional visible in the base — subclass authors see obligations vs opportunities). Keep skeletons final where reordering breaks invariants (`generate()` non-overridable — sequence closed per Domain 01 §1.2; steps open per hook contracts). Name hooks after roles (`buildBody`, `beforeSave` — step semantics, not `hook1`).

```typescript
// GOOD: sequence owned once, steps supplied per kind — verified H|sales|F + H+|sales|F
abstract class Report {
  generate(): string {  // skeleton: FINAL sequence (never overridden — order closed)
    return [this.header(), this.buildBody(), this.footer()].join("|");
  }
  protected abstract buildBody(): string;       // required hook (subclasses MUST supply)
  protected header(): string { return "H"; }    // default hook (override optional)
  protected footer(): string { return "F"; }
}
class SalesVerbose extends Sales { protected override header(): string { return "H+"; } }
// Sales().generate() -> H|sales|F verified; SalesVerbose -> H+|sales|F verified (sequence stable, step varied).
// BAD: copy-pasted generate() per report kind ("explicit") —
// sequences drift per copy (footer forgotten somewhere); new steps touch all copies (scattered evolution)
```

### 2) **Hooks documented as API**

**Definition** — hooks *are* the extension API (abstract steps: must-implement — compile-enforced; default hooks: may-override — documented semantics; final skeleton: must-not-reorder — closed by design): subclass authors program against hook contracts, never base internals. Undocumented hooks invite override hazards (overriding `generate()` itself — sequence broken silently; relying on call order uncleared — base refactors fracture subclasses, Domain 01 §3.1's fragile shape wearing template clothes).

- **Why it matters (correctness)**: hook contracts unstated produce the fragile-base incident *within* the pattern designed to prevent it (subclasses depending on undocumented self-call order — base adding a step breaks overrides; overriding the skeleton method — custom sequences bypassing new validation steps). Documented hooks convert subclassing from archaeology ("which methods may I touch?") into API use (required/optional/closed labeled per member — enforced by `abstract`/`final`/docs triple).
- **Modern guidance** — label every base member (abstract = implement; virtual-with-default = may override with documented semantics; final = never touch — three categories, all explicit). Document self-call guarantees ("`generate()` calls `header/buildBody/footer` in order, once each" — subclass reliance bounded by statement). Test hooks through subclasses (each hook overridden in tests — contract exercised, not just declared). Prefer composition where hooks multiply past ~5 (strategy injection over hook forests — template bloat signals Strategy territory, leaf 1.1).

```typescript
// GOOD: hook categories explicit (API, not archaeology)
// abstract buildBody(): string;   // REQUIRED: implement (compile-enforced).
// protected header(): string      // OPTIONAL: override with same contract (documented semantics).
// generate(): string              // FINAL: never override (sequence closed — leaf 1.2-of-01 applied).
// BAD: undocumented overridables ("extend freely") —
// subclasses depend on self-call order unstated; base evolution fractures them silently (fragile, again)
```

### 3) **Hollywood Principle named**

**Definition** — "don't call us, we'll call you": frameworks own control flow (skeleton runs — subclasses plug in), inverting library direction (libraries *called by* user code; frameworks *call* user code at hooks). Template Method is Hollywood at method level (base sequences, hooks filled); DI containers at composition level (wiring owned centrally — Domain 06); test runners at process level (setup/test/teardown hooks per suite). Recognizing the direction decides who owns sequence bugs (framework — fix centrally; all users benefit) vs step bugs (subclass — fix locally).

- **Why it hurts when missing (correctness, maintainability)**: direction-blind code inverts wrongly (user code calling framework internals — version upgrades break callers; framework details leaking into hooks — subclass authors depending on undocumented flow). Hollywood violations tangle control (who sequences? — answered "both" means answered never; sequence bugs batted between framework and user teams). Named direction assigns ownership (flow bugs → framework; step bugs → subclass — routed correctly on sight).
- **Modern guidance** — name the direction per framework relationship ("Report owns sequence; subclasses own steps" — stated in base docs). Keep framework calls into documented hooks only (undocumented entry points are backdoors — versioned away or promoted explicitly). Test both sides (skeleton sequence tests + per-hook subclass tests — flow and steps verified independently). Graduate to Strategy where steps vary *at runtime* (hook binding is compile-time per subclass — dynamic selection needs composition, leaf 1.1's `use()` over inheritance).

```bash
# GOOD: direction named, ownership routed (flow vs steps, framework vs user)
#  framework owns: sequence (generate order — bugs fixed centrally, all subclasses benefit).
#  user owns: steps (buildBody content — bugs fixed locally, blast radius one subclass).
# BAD: "flexible" frameworks with undocumented flow + user-callable internals ("powerful") —
# sequence bugs batted between teams (ownership undiscovered); upgrades break callers silently
```

### 4) **Common confusion**

- "Template Method needs inheritance" — skeletons need *overridable steps* (subclassing canonical; strategy-injected steps work identically — skeleton calls composed strategies; inheritance-free templates where hierarchies cost too much).
- "Hooks are just overridable methods" — hooks carry *contracts* (call guarantees, ordering, optionality labeled — API, not accident); plain overridables carry archaeology (behavior discovered by reading base internals).
- "Final skeletons are rigid" — final sequences protect *invariants* (validation steps unskippable — security/correctness gates survive subclasses); rigidity where order matters is safety, not stubbornness.
- "Hollywood Principle means frameworks always" — Hollywood describes *control direction* (caller-vs-called at any scale — methods, containers, runners); frameworks are one venue. Direction named per relationship.

### 5) **Performance note**

Templates cost one virtual dispatch per step (nanoseconds — hook calls devirtualize at monomorphic hierarchies) plus skeleton overhead (join/format per run — inherent to the workflow, not the pattern). Duplicated sequences cost per-variant maintenance (human pipeline — drift bugs per copy) and test matrices (sequence coverage per duplicate). Optimize sequence centralization first (one skeleton replaces N copies), hook granularity second (coarse steps — fewer dispatches, clearer contracts), dispatch overhead never (nanoseconds, inlined).

### 6) **Mentor note**

Demo skeleton stability live (verified pair — "sequence identical, step varied" converts templates from abstraction to observable). Demand hook labeling ("abstract/optional/final per member — no unlabeled overridables"). Contrast runtime selection explicitly ("steps varying at runtime need Strategy, not hooks" — binding-time decides pattern). Watch for the skeleton-overrider ("flexible" generate() overrides — fix with final + incident autopsy: skipped validation step) and the hook-forest grower (12 hooks per base — fix with strategy extraction past ~5). Review check: sequences final, hooks contracted, Hollywood direction named, juniors can fill blanks without reordering unprompted.
