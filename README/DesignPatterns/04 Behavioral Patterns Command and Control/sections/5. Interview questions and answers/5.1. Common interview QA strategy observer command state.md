## 5.1. Common interview QA: strategy, observer, command, state

### 1) **Strategy vs State — same code?**

**Definition** — the ownership screen: identical delegation structure (context holds behavior object, delegates calls), opposite selection ownership (Strategy: *caller/config* selects — `use()` called externally, verified swap pair; State: *context itself* transitions on domain events — moves validated by tables, verified lifecycle + refusal). Same code shape answers "who switches?" differently — ownership decides the pattern, structure merely implements.

- **What a good answer sounds like**: ownership first ("who selects — external config/user → Strategy with `use()` API; internal events → State with validated moves"), structure second ("both compose + delegate — mechanics shared, control flow opposite"), misclassification consequences named (client-selectable states leak lifecycle control — assignments bypass validation; context-hidden strategies bury configurability — swaps need surgery). Then the naming close (Strategy for caller choice, State for condition response — asked per behavior, never defaulted).
- **Modern guidance** — interviewers listen for *ownership analysis* (selector named before mechanics described): candidates who ask "who switches here?" pass; candidates who describe delegation generically fail the control-flow follow-up. Red flags: "State is complex Strategy" (complexity framing misses ownership — the load-bearing distinction), "use Strategy always, simpler" (caller-selection forced where lifecycle rules — assignments bypassing validation).

```bash
# The ownership answer, structured (leaves 1.1 + 1.2 as interview response)
#  external choice (config/user/toggle) -> STRATEGY (use() API; verified swap pair).
#  internal condition (events/lifecycle) -> STATE (validated moves; verified lifecycle + refusal).
#  misclassified: caller-forced states (bypassed validation) or hidden strategies (buried config).
```

### 2) **Observer without leaks?**

**Definition** — the lifecycle screen: decoupled fan-out *with* subscription pairing (subscribe returns id/handle — verified; unsubscribe releases — verified count 2→1; order-independence contracted — tolerance, not sequence). Expected answer pairs every lifetime claim (subjects outlive observers — pairing mandatory; observers outlive subjects — weak refs or explicit teardown; same lifetimes — pairing still documented). Leaks prevented structurally, not hopefully.

- **What a good answer sounds like**: pairing first ("every `sub()` returns a disposable — teardown unconditional; counts asserted in tests — verified 2→1 pattern"), order-contract second ("notification sequence unspecified — observers tolerate any order; verified pair today, reshuffled tomorrow"), payload discipline third ("frozen event objects — subscriber mutation corrupting siblings prevented structurally"). Then the framework close (effect cleanups / async-pipe / AbortController — discipline mechanized where available, manual where not).
- **Modern guidance** — grade *lifecycle completeness* (subscribe/unsubscribe/order/payload — all four addressed): candidates covering all four pass; candidates covering fan-out only fail the production follow-up ("who unsubscribes destroyed views?"). Instant fail: "GC handles unsubscribes" (referenced = alive — reachability lesson unlearned; lapsed listeners accumulate per navigation).

```bash
# The lifecycle answer, structured (leaf 2.1 as interview response)
#  pair (sub returns id/handle; teardown unconditional; counts asserted: verified 2->1).
#  tolerate (order unspecified + contracted; payloads frozen against sibling corruption).
#  mechanize (framework cleanups where available; manual discipline + weak refs elsewhere).
```

### 3) **Undo architecture?**

**Definition** — the command screen: reified requests with paired inverses (`do()`/`undo()` shipped together — verified 2→1), history stacks with redo discipline (undone-stack cleared on new branches), bounded retention (caps stated — ring buffers/counts), macro composition (nested commands — reversibility structural). Expected answer scales the pattern (single undo → redo → queue → journal/event-sourcing — one contract, four dividends from leaf 2.2).

- **What a good answer sounds like**: reification first ("requests as objects — receiver + args frozen; inverses known by construction, not derived later"), pairing second ("`undo()` with every `do()` — review rejects solos; verified 2→1"), bounds third ("histories capped — unbounded undo is memory incident wearing UX"), composition fourth ("macros nest commands — trees of reversibility; journals persist streams — event sourcing primitive"). Then the callback split (fire-once → callbacks; managed → commands — lifecycle decides).
- **Modern guidance** — listen for *inverse knowledge* (commands knowing their own undo vs derived/inferred reversals — construction-time knowledge is the pattern's core): candidates who center it pass; candidates who describe stacks generically fail the pairing follow-up ("where does `undo()` live relative to `do()`?"). Red flags: closure-queues for undoable work ("lighter" — opaque payloads, hand-derived inverses, untestable drift), unbounded histories ("users expect infinite undo" — memory incidents scheduled).

```bash
# The command answer, structured (leaf 2.2 as interview response)
#  reify (receiver+args frozen; inverses by construction) -> pair (do/undo shipped together; verified 2->1).
#  bound (caps stated) -> compose (macros nest; journals persist -> event sourcing, [Domain 06/2.2](<../../../06 Modern Patterns and Anti-Patterns/sections/2. Pipelines and events/2.2. Publish-subscribe and event sourcing.md>)).
#  split (fire->callbacks; manage->commands — lifecycle decides, familiarity doesn't).
```

### 4) **Common confusion**

- Candidates who answer ownership questions with mechanics ("both use composition" — true and insufficient; selector identity is what's screened).
- "Observer coverage means testing notifications fire" — coverage means *lifecycle* tested (pairing, order-shuffling, payload-freezing — fan-out alone proves the easy third).
- Treating undo as stack trivia ("pop and reverse") — undo is *inverse-knowledge architecture* (paired contracts, bounded histories, macro composition — the stack is incidental).

### 5) **Performance note**

Behavioral QA answers should be compact: ownership split (90 seconds — selector named, misclassification priced), lifecycle pairing (two minutes — subscribe/unsubscribe/order/payload), undo architecture (two minutes — reify/pair/bound/compose). Candidates who narrate with verified receipts (swap pair, 2→1 counts, lifecycle matrix) take the same time as generalizers and prove triple — structure is speed, in behavioral interviews as in analysis.

### 6) **Mentor note**

Use Q1 as the ownership screen (selector named before mechanics), Q2 as the lifecycle screen (pairing + tolerance + payloads, all evidenced), Q3 as the architecture screen (reification → pairing → bounds → composition). Rubric: junior — correct shapes with examples; mid — ownership stated, lifecycles paired, inverses co-shipped unprompted; senior — misclassification priced, framework choices justified (disposable mechanisms, bound policies), borrow-vs-build discipline without prompting. Keep the verified receipts ready (swap pair, fan-out counts, 2→1 undo) — structure narrated with evidence hires. Red-flag fails: ownership-blindness, pairing-optional attitudes, closure-queue undo.
