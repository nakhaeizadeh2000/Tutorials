## 1.1. Selecting patterns under constraints

### 1) **Constraints pick patterns**

**Definition** — pattern selection driven by context (team size, latency budgets, change rates, regulatory surface — constraints named before patterns shortlisted): small team + stable domain → boring patterns (direct calls, simple factories — ceremony unjustified); large team + volatile domain → seams everywhere (extension points, registries, contracts — coordination needs structure); latency-bound → constants-first selection (verified-shape reasoning from [AlgorithmDesign](<../../../../AlgorithmDesign/README.md>); regulated → audit-friendly patterns (journals, mementos, explicit state machines — provenance built in).

- **What problem it solves**: fashion-driven selection misfits systematically (microservices for a blog — network latency, deploy matrices, debugging across services for unneeded independence; event sourcing for CRUD — journal complexity without audit need; DDD tactical patterns for scripts — ceremony dwarfing logic). Constraint-driven selection inverts the flow (context → shortlist → trade-off → choice — each step evidenced, fashion never consulted). Wrong-pattern incidents (over-distributed monoliths, over-abstracted scripts) trace to selection without constraints without exception.
- **Modern guidance** — list constraints first (team/pain/latency/regulatory — four answers before any pattern named). Shortlist by fit (2–3 candidates max — wider fields signal vague constraints, not rich options). Decide by trade-off arithmetic (complexity cost vs problem fit — boring wins ties, always). Document the decision (ADR per significant choice — context, options, trade-offs, review date; future teams re-derive instead of cargo-culting).

```bash
# GOOD: context picks patterns (constraints first, fashion never)
#  3-person blog, stable domain  -> monolith + direct calls (boring wins ties; no distributed tax).
#  50-engineer platform, volatile -> seams/registries/contracts (coordination needs structure).
#  trading engine, microseconds  -> constants-first (verified-shape reasoning; patterns audited per nanosecond).
# BAD: "we do microservices/event-sourcing/DDD here" (identity) —
# decisions by belonging; costs billed silently (latency, deploys, debugging); benefits assumed loudly
```

### 2) **Boring wins ties**

**Definition** — where two designs both satisfy constraints, ship the simpler (direct calls over patterns, monoliths over services, functions over frameworks — boredom as selection criterion): complexity must *earn* its place (measured benefit beating simplicity — not anticipated, not fashionable, measured). Boring code reads fast (newcomers productive in days), debugs directly (stack traces without indirection mazes), deletes cleanly (no abstraction layers to unwind).

- **Why it matters (correctness)**: excitement-driven design bills in comprehension (clever abstractions understood by authors, opaque to maintainers — bus factor one per cleverness; debugging through six indirection layers — incident time multiplied per hop; onboarding measured in quarters — novelty taxed per hire). Boring designs fail boringly (obvious failure modes — debugged directly; obvious extension points — grown without archaeology). Excitement belongs where novelty pays (measured 10× wins — performance cliffs, scale walls, genuinely novel domains).
- **Modern guidance** — default to boring (direct, obvious, standard-library-first — excitement requires justification, not permission). Demand measured wins for cleverness (benchmarks, incident-rate deltas, onboarding-time comparisons — numbers, not adjectives). Sunset cleverness that stopped paying (abstractions whose variation never arrived — deleted on sight; speculative flexibility is complexity unpaid-for). Celebrate deletions equally with additions (net-negative-line quarters — simplicity as team metric, not just velocity).

```bash
# GOOD: boredom as criterion (simplicity winning ties structurally)
#  CRUD service, 3 engineers -> monolith + direct calls + boring ORM (novelty unjustified by scale).
#  measured 10x need (perf cliff at 10^7 rows) -> targeted cleverness (indexed/cached/partitioned — evidenced).
# BAD: "boring is for juniors" (excitement as seniority signal) —
# cleverness billing comprehension per hire; incidents debugged through indirection mazes
```

### 3) **Document the decision**

**Definition** — Architecture Decision Records per significant choice (context → options → trade-offs → decision → review date — five slots, one page): future teams re-derive instead of cargo-culting (why *this* pattern *here* — readable rationale beats tribal memory); decisions expire explicitly (review dates trigger re-evaluation — constraints drift, choices follow); reversals reference originals (superseding ADRs link predecessors — decision archaeology without git-blame spelunking).

- **Why it hurts when missing (correctness, maintainability)**: undocumented decisions fossilize silently ("we've always done it this way" — reasons evaporated with authors; challenging requires re-deriving from zero — nobody pays that tax, so nobody challenges; constraints drift underneath frozen choices — microservices for a team that shrank to four, event sourcing for audits nobody runs). ADRs convert tribal memory into versioned reasoning (decisions reviewable, expirable, reversible — architecture as maintained artifact, not oral tradition).
- **Modern guidance** — write ADRs for significant choices (pattern adoptions, topology decisions, vendor commitments — one page each, template-enforced). Date every decision for review (6–12 month triggers — constraints re-checked, choices re-affirmed or reversed). Link supersessions explicitly (new ADR references old — decision lineage traceable; reversals celebrated as learning, not failures). Store beside code (versioned with the system it governs — docs/ folder, reviewed like code, never wiki-sidebar orphans).

```bash
# GOOD: decisions versioned (rationale maintained like code)
#  ADR-014: Abstract Factory for themes (context: 3 themes + 2 forecasted; options: per-component flags (rejected:
#  drift), factory suites (chosen: atomic coherence); review: 2027-03 (revisit on theme count).
# BAD: "we discussed it in Slack" as architecture record ("agile") —
# reasons evaporate with scrollback; challenges require re-derivation; drift unnoticed (fossilized by default)
```

### 4) **Common confusion**

- "Constraints limit creativity" — constraints *direct* creativity (feasible approaches enumerated — design energy spent where it pays, not on impossible branches). Unlimited design wanders; constrained design converges.
- "Boring means unskilled" — boring means *appropriate* (complexity matched to problem — senior judgment visible in restraint; juniors over-engineer to impress, staff simplify to ship). Boredom is the senior aesthetic.
- "ADRs are bureaucracy" — ADRs are *versioned reasoning* (one page per significant choice — cheaper than re-derivation, faster than archaeology). Bureaucracy slows decisions; ADRs accelerate revisits.

### 5) **Performance note**

Selection discipline costs minutes per decision (constraints listed, boring checked, ADR written) against fashion incidents (over-distributed latency, over-abstracted onboarding, over-ceremonied velocity — quarters of compounding drag) and fossilized choices (unrevisited decisions billing obsolete constraints indefinitely). Highest-leverage item is boring-wins-ties (prevents excitement debt structurally); second is ADR dating (expires fossilization); third is constraint-first shortlisting (prevents misfit families). Minutes preventing quarters — selection's best attention rate.

### 6) **Mentor note**

Enforce constraints-first ("name four constraints before any pattern" — no selection talk until context stated). Celebrate boring publicly ("simplest sufficient design" praised in reviews — culture rewarding restraint, not cleverness). Demand ADRs for significant choices ("where's the record?" — undocumented decisions rejected like untested code). Watch for the fashion-selector ("industry does X" — fix with constraint arithmetic on *our* context) and the cleverness-performer ("impressive" abstractions — fix with onboarding-time + debug-path costing). Review check: constraints stated, boredom checked, decisions recorded — and the mentor's own selections modeling all three visibly.
