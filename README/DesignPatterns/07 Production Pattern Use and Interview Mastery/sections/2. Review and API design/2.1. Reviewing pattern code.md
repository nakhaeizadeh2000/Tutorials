## 2.1. Reviewing pattern code

### 1) **Checklists per pattern family**

**Definition** — review gates shaped per family (creational: seams counted, singletons justified, builders thresholded — Domain 02 §4.1; structural: jobs named, intents stated, sharing declared — Domain 03 §4.1; behavioral: selection structured, lifecycles paired, skeletons contracted — Domains 04 §4.1/05 §4.1; modern: explicitness audited, contracts tested, smells named — Domain 06 §4.1): family checklists applied per PR (relevant section only — creational PRs skip behavioral gates; full-track review on every change is ceremony, scoped gates are discipline).

- **What problem it solves**: pattern review without checklists degrades to taste ("looks fine" — unexamined seams, unjustified singletons, unnamed intents shipping per PR; expert reviewers catching what novices miss inconsistently — quality varying with reviewer assignment). Family checklists convert pattern review from connoisseurship into procedure (applicable gates listed — checked mechanically; violations named per catalog — routed explicitly). Review quality stabilizes across reviewers (juniors gating like seniors on checklist items — mentorship scaled structurally).
- **Modern guidance** — apply family checklists per PR scope (creational changes → Domain 02 §4.1 gates; structural → 03 §4.1; behavioral → 04/05 §4.1; wiring → 06 §4.1 — scoped, never whole-track). Encode recurring gates in automation (lint rules for `new`-in-policy, thresholds for positional params, coverage floors on seams — mechanical teeth where checklists recur). Calibrate checklist strictness per risk (core paths full gates; leaf features sampled gates — rigor proportional to blast radius, leaf 1.2-of-01 restated for review).

```bash
# GOOD: scoped gates per PR (family checklists applied, never whole-track)
#  factory PR -> Domain 02 §4.1 (seams counted? singletons justified? builders thresholded?).
#  observer PR -> Domain 04 §2.1 + 05 §4.1 (pairing? order-tolerance? termination?).
#  automation: lint (new-in-policy) + thresholds (positional count) + coverage (seams).
# BAD: "looks good to me" on pattern code (taste-based) or full-track review per PR (ceremonial) —
# unexamined seams ship (former); reviewers burn out gating everything always (latter)
```

### 2) **Smells named with routings**

**Definition** — review findings stated as catalog-entry + fix-route (leaf: Domain 06 §3.1 applied live — "god object (auth+billing+notify) → extract per stakeholder + Facade" beats "this is messy" by actionability; "anemic Order + OrderService → relocate behavior into Order"; "shotgun tax change (6 files) → strategy seam"). Named findings route themselves (entry implies fix family — god→split, anemic→relocate, shotgun→seam, hammer→boring-alternative, premature→delete).

- **Why it matters (correctness)**: unnamed findings stall (vague discomfort debated without resolution — "feels off" threads consuming review cycles; authors guessing at remedies — fixes misaimed at symptoms; repeat findings per PR — same smells recurring because never precisely named). Named findings close (entry cited → fix family known → patch scoped → verified in one round). Review velocity *is* vocabulary precision (naming speed bounds review speed — catalog fluency pays per finding).
- **Modern guidance** — name catalog entries in findings (required vocabulary — "god object", "shotgun surgery", "speculative seam" stated plainly with file:line). Route per entry (god→split-by-reason, anemic→relocate-behavior, shotgun→insert-seam, hammer→boring-alternative, premature→delete-or-justify). Keep tone blameless (structures criticized, authors respected — catalog terms describe code-needs, never coder-worth; review culture modeled per comment). Track finding frequency (recurring smells per area signal systemic causes — training or architecture gaps, not individual lapses).

```bash
# GOOD: findings self-routing (names imply fixes)
#  "UserManager: god object (auth+billing+notify) -> extract per stakeholder + Facade (Domain 01 §1.1/03 §1.2)."
#  "Order{data}+OrderService{logic}: anemic -> relocate behavior into Order (Domain 06 §3.1 routing)."
#  "tax logic × 6 files: shotgun -> strategy seam (single edit point created)."
# BAD: "this feels messy, maybe refactor?" (affect without action) —
# authors guess remedies (misaimed fixes); findings recur per PR (unnamed smells never routed)
```

### 3) **Tests prove the pattern**

**Definition** — pattern tests verify *pattern properties*, not just outputs (seam tests: new kinds land extension-shaped — OCP proven per addition; substitutability matrices: subtypes run supertype suites — LSP proven per hierarchy; pairing tests: subscribe/unsubscribe counts asserted — lifecycle proven per event system; contract suites per factory/strategy/observer — behavioral parity where promised). Output-only tests miss pattern failures (correct outputs via wrong structure — working today, unextensible tomorrow, undebuggable next quarter).

- **Why it hurts when missing (correctness, maintainability)**: untested patterns decay structurally (seams bypassed silently — direct construction creeping past factories; substitutability broken quietly — new subtype violating untested contracts; lifecycles leaking unnoticed — pairing unasserted). Output suites stay green throughout (behavior correct *today* — structural rot invisible until extension/swap/teardown demanded). Pattern tests convert structural properties into CI-enforced invariants (violations fail builds, not productions).
- **Modern guidance** — test seams (extension-shaped additions — new kinds without core edits, asserted structurally where feasible). Test substitutability (contract matrices per hierarchy — every subtype green on supertype suites). Test lifecycles (pairing counts, history bounds, termination paths — verified shapes from Domains 04–05 as oracle patterns). Test contracts per factory/strategy/observer (shared suites across implementations — parity enforced, divergence documented). Run pattern tests in CI standard gates (structural properties green-required, not advisory).

```bash
# GOOD: properties tested, not just outputs (structural invariants in CI)
#  seams: new-kind-without-core-edit asserted (OCP proven per addition, not hoped).
#  substitution: supertype suites × every subtype green (LSP proven per hierarchy).
#  lifecycles: pairing counts + history bounds + termination paths green (verified shapes as oracles).
# BAD: "outputs correct, patterns evident" (behavior-only suites) —
# structural rot invisible (bypassed seams, broken substitutability, leaked lifecycles surface in production)
```

### 4) **Common confusion**

- "Checklist reviews are slow" — checklist reviews are *fast* (scoped gates per family — applicable items only; whole-track review is what's slow). Slowness blamed on checklists belongs to unscoped gating.
- "Smell-naming is nitpicking" — smell-naming is *routing* (findings self-directing to fixes — review cycles collapse from debate to action). Nitpicking fusses over trivia; catalogs target structural costs.
- "Pattern tests duplicate unit tests" — pattern tests assert *properties* (seams/substitution/lifecycles — structural invariants); unit tests assert *behaviors* (outputs per inputs). Different questions, complementary suites.

### 5) **Performance note**

Review checklists cost minutes per PR (scoped gates checked — applicable family only) against unfocused reviews (hours debating taste — unscoped) or absent reviews (incidents from unexamined seams — unbounded). Pattern tests cost seconds in CI (property suites alongside unit suites — machine time, parallel). Smell-naming costs vocabulary acquisition once (catalog learned — findings accelerate forever after). Optimize gate scoping first (family-relevant only), property coverage second (structural invariants in CI), review thoroughness third (depth on flagged items, speed elsewhere).

### 6) **Mentor note**

Run checklist reviews live (family gates applied to real PRs — "which items fire here?" converts procedure from document to habit). Practice smell-naming ("name it + route it" per finding — vocabulary + actionability in one motion). Demand pattern tests ("what property proves this pattern?" — outputs insufficient alone). Watch for the taste-reviewer ("looks fine/doesn't feel right" — fix with gate/scent/property demands per finding) and the whole-track gater ("check everything always" — fix with scoping: family-relevant gates only). Review check: gates scoped, smells named+routed, properties tested — and the mentor's own reviews modeling all three visibly.
