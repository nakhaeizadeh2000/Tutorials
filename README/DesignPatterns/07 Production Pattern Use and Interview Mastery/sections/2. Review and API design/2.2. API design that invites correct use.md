## 2.2. API design that invites correct use

### 1) **Pit-of-success naming**

**Definition** — APIs where the obvious path is the correct one (names guiding toward seams — `create()` over `new` where validation matters; defaults safe — strictest options default-on; dangerous operations verbose — `forceDelete()` vs `remove()`, friction proportional to risk): misuse requires *effort* (workarounds visible in review — `as any` casts, flag combinations unexplained, private-field reaching all flag themselves). Pit-of-success measured by misuse difficulty (wrong uses awkward by construction, not by documentation).

- **What problem it solves**: neutral APIs misuse symmetrically (all paths equally easy — wrong ones chosen at chance rates; boolean blindness — `process(true)` meaning what?; null-vs-undefined ambiguity — callers guessing, naturally splitting on guesses). Guided APIs skew correct (obvious path right — newcomers succeed by default; dangerous paths verbose — risk-takers self-identify in diffs; misuse visibly awkward — reviewers spot workarounds instantly). Design effort converts user error rates structurally (naming + defaults + verbosity doing what docs beg for).
- **Modern guidance** — name the happy path shortest (primary use = fewest tokens; advanced uses progressively verbose — frequency inversely proportional to length). Default safely (strictest validation, narrowest permissions, smallest blast radius — opt-out of safety, never opt-in). Make danger verbose (destructive/irreversible operations long-named with confirmation shapes — friction proportional to risk). Audit misuse in the wild (support tickets + bug reports traceable to API shapes — confusing APIs generate characteristic misuses; redesign the shape, not the docs).

```typescript
// GOOD: obvious path correct (misuse awkward by construction)
// connect({ url }) with TLS/verify/timeouts defaulted strict (safe defaults — relaxation explicit per field).
// deleteUser(id, { confirm: true, reason }) (danger verbose — friction proportional to irreversibility).
// BAD: process(data, true, false, null) ("flexible") —
// boolean blindness (which flag?); null-ambiguity (absent or empty?); misuse at chance rates (neutral design)
```

### 2) **Invalid states unrepresentable**

**Definition** — types forbidding meaningless states (unions over booleans — `Loading | Ready | Failed` instead of `isLoading + isError` flags combinable into nonsense; branded IDs over strings — wrong-kind arguments uncompilable; builders over telescoping — incomplete objects unbuildable per Domain 02 §2.2): impossible states *uncompilable* (misuse rejected before runtime — the strongest possible guidance). Boolean pairs multiply invalid combos (2 flags = 4 states, 1+ meaningless — unrepresentable design eliminates the meaningless fraction structurally).

- **Why it matters (correctness)**: representable-invalid states fail at runtime (loading+error simultaneously — UI branches unhandled; null fields accessed — TypeErrors in production paths tests never combined; mutually-exclusive flags both-set — logic undefined exactly where untested). Each traces to types permitting nonsense (booleans/strings/nullables composing freely — invalid combinations representable, therefore reachable). Unrepresentable design converts runtime errors into compile errors (misuse caught at authorship — cheapest possible detection point).
- **Modern guidance** — model states as unions (discriminated states — impossible combinations unrepresentable by construction; exhaustive switches with `never` defaults prove coverage). Brand domain primitives (IDs/currencies/emails — wrong-kind arguments rejected at compile; parsing once at boundaries — validated values flow, raw strings stop). Build complex objects via builders (leaf: Domain 02 §2.2 — incomplete unbuildable; telescoping banned past threshold). Prefer total functions (defined on all inputs of their types — partial functions documented with explicit error returns, never undefined behavior).

```typescript
// GOOD: nonsense uncompilable (invalid states unrepresentable by construction)
type LoadState = { s: "loading" } | { s: "ready"; data: string } | { s: "failed"; err: string };
// loading+error simultaneously: UNREPRESENTABLE (union members exclusive — compiler enforces).
// vs { loading: boolean; error: string | null } (4 combos, 1+ meaningless — runtime-checked, hopefully).
// BAD: stringly/booleanly-typed APIs ("simple") —
// invalid combos reachable (loading+error); wrong kinds passable (userId vs orderId strings); misuse compiling clean
```

### 3) **Errors guide repair**

**Definition** — error messages naming fixes (expected-vs-actual with recovery path — "unknown theme 'drak'. Did you mean 'dark'? Available: light, dark." vs "invalid input"): failed operations teach (message states what was wanted, what arrived, and what repairs — three parts, always); typed errors route programmatically (`instanceof` narrowing — callers branch on error *kinds*, not message substrings); unrecoverable errors fail loudly with context (stack + inputs + correlation IDs — debuggable without reproduction).

- **Why it hurts when missing (correctness, maintainability)**: unhelpful errors tax every consumer (cryptic messages debugged per occurrence — support load proportional to vagueness; string-matched handling — brittle `includes("timeout")` checks breaking on rewording; silent swallowing encouraged — useless errors get caught-and-ignored, hiding real failures). Guiding errors convert failure into instruction (fix named — self-service resolution; kinds typed — programmatic handling; context attached — single-occurrence diagnosis).
- **Modern guidance** — write errors as instructions (wanted/arrived/repair triple — every thrown message reviewed for all three parts). Type error kinds (discriminated error unions — handlers narrow exhaustively; `never`-defaulted switches prove coverage). Attach correlation context (request IDs, input echoes, component paths — debuggable without reproduction). Never string-match errors across boundaries (typed kinds or codes — rewording-safe handling; message text is human UI, not API).

```typescript
// GOOD: failures instruct (wanted/arrived/repair triple, typed kinds)
// throw new UnknownThemeError(`unknown theme '${name}'. Did you mean '${suggest}'? Available: light, dark.`);
// catch (e) { if (e instanceof UnknownThemeError) return fallback(e.suggest); throw e; } (kinds, not substrings).
// BAD: throw new Error("invalid") / .includes("timeout") handling ("sufficient") —
// unactionable messages (support load per occurrence); brittle matching (rewording breaks handling silently)
```

### 4) **Common confusion**

- "Good APIs need rich features" — good APIs need *correct defaults* (pit-of-success — obvious path right; features accrete on demand, never upfront). Richness without guidance misleads; guidance without richness still serves.
- "Types restrict power users" — types restrict *invalid* uses (unrepresentable nonsense — power users need expressiveness within validity, which precise types preserve better than loose ones). Power flows through precise types, not around them.
- "Error messages are UX polish" — error messages are *API surface* (programmatic handling + human repair — both consumers first-class). Polish decorates; messages instruct and route.
- "Boolean params are fine with docs" — documented booleans still misread at call sites (positional booleans unreadable in review — `process(x, true)` means what, forever ambiguous). Options objects/named variants replace, docs supplement.

### 5) **Performance note**

API design costs thought per signature (naming/defaults/verbosity deliberated — minutes) plus type machinery (unions/brands/builders — compile-time only, zero runtime). Misuse costs support load (vague errors debugged per occurrence), incident rates (invalid states failing in production), and review drag (positional/boolean calls decoded per site). Highest-leverage item is pit-of-success naming (correct-by-default usage); second is unrepresentable states (compile-time misuse elimination); third is guiding errors (self-service failure resolution). Design minutes preventing support hours — API's best attention rate.

### 6) **Mentor note**

Audit call sites live ("read this invocation aloud — what does it do?" — undecipherable calls prove the design gap on the spot). Demand unrepresentable states ("show me the impossible combination this type forbids" — none named means none prevented). Rewrite one error message together (vague → wanted/arrived/repair triple — the transformation teaches itself). Watch for the boolean-parameterist ("documented, fine" — fix with call-site read-aloud test) and the helpful-error skeptic ("users don't read errors" — fix with support-ticket arithmetic: vague errors bill per occurrence). Review check: happy path shortest, invalid unrepresentable, errors instructive — and the mentor's own APIs modeling all three visibly.
