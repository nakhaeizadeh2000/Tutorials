## 6.1. Boundaries: what is covered elsewhere

### 1) **Every pattern underneath**

**Definition** — the complete track map, final: principles (SRP/OCP/LSP/ISP/DIP/composition → [Domain 01](<../../../01 SOLID Principles and Design Foundations/README.md>)); creational (singletons/factories/builders/prototypes → [Domain 02](<../../../02 Creational Patterns/README.md>)); structural (adapters/facades/decorators/proxies/composites/bridges → [Domain 03](<../../../03 Structural Patterns/README.md>)); behavioral command (strategies/states/observers/commands/templates → [Domain 04](<../../../04 Behavioral Patterns Command and Control/README.md>)); behavioral distribution (iterators/mediators/mementos/chains/visitors → [Domain 05](<../../../05 Behavioral Patterns Distribution and Interpretation/README.md>)); modern wiring (DI/repos/middleware/events/smells → [Domain 06](<../../../06 Modern Patterns and Anti-Patterns/README.md>)). This domain orchestrates all six into judgment, review, and narration — techniques referenced, never re-taught.

- **Why the boundary matters**: capstone duplication is the most tempting kind (re-explaining strategies for interview answers, re-deriving OCP for estimation questions, re-teaching observers for event design — each feels self-contained, each rots independently). Single source of truth at track scale: six domains of technique, one domain of orchestration. This leaf is the map that keeps those lines short for the track's final domain — and, as the last boundaries leaf, the map of the whole territory.
- **Modern guidance** — if a passage here needs more than one sentence of any pattern, stop and link instead. The one-sentence versions per domain: split by reasons (01), build behind seams (02), wrap transparently (03), select/inject/notify/reify (04), traverse/coordinate/capture (05), wire/testify/name-smells (06). Everything else here is *judgment* (select), *review* (gate), and *narration* (perform).

### 2) **Platform and language specifics**

**Definition** — framework docs, cloud consoles, broker operations (documented per vendor — specifics churning quarterly); JavaScript/TypeScript mechanics (syntax, engines, libraries — [JavaScript track](<../../../../JavaScript/README.md>), [TypeScript track](<../../../../TypeScript/README.md>)); interview platforms (format/rules/timing per venue — prepared per target). Map-style stop-list (the whole track, final): principles → 01, creation → 02, structure → 03, command/control → 04, distribution → 05, modern → 06, mastery → here (07), mechanics → JS/TS tracks, words → IT Vocabulary.

- **Why the boundary matters**: platform specifics churn (limit changes, new judges, engine upgrades) while pattern truth stands for decades — embedding console paths or engine constants in tutorial leaves guarantees rot within a year. Worse, specifics vary by venue (whiteboard vs IDE vs take-home — same patterns, different performances). Teaching the portable core (method, verification, narration) keeps every leaf durable; linking the specifics keeps every leaf honest.
- **Modern guidance** — name the control, link the venue: "measure at shipped scale (methodology: portable; budget: *your* platform's limits)" stays true across venues; hardcoded numbers don't. When platform curiosity strikes mid-method ("what are the exact limits?"), follow the venue link — this track answers with method plus control names, not navigation.

```bash
# GOOD: portable core, linked specifics (durable across venues and versions)
#  method (solve/verify/narrate) -> this domain (portable: interviews, reviews, incidents alike)
#  budgets (limits/platforms/engines) -> venue docs + measured probes (methodology here, numbers there)
# BAD: "passes in 1s" embedded in tutorial leaves —
# accurate until limits change, venue-locked from birth, hardware-bound throughout
```

### 3) **Vocabulary naming**

**Definition** — what process words *mean in a meeting* (refactoring, tech debt, code review, behavioral interviews as vocabulary) belongs to [IT Vocabulary](<../../../../ITVocabulary/README.md>); this track never re-teaches definitions those leaves own. The concept gets its full treatment once, everywhere else one line plus a link — the DRY contract's final application, closing the track exactly as Domain 01 opened it (boundaries as maps, all the way down).

- **Why the boundary matters**: every boundary crossed here is duplication that rots — process glossaries copied into mastery leaves go stale when industry usage shifts, while the words-track stays current. Seven domains, seven maps, zero duplication — that was the design working, from the first boundaries leaf (01 §6.1) to this last one.
- **Modern guidance** — when writing or reviewing Domain 07 content, ask "does a sibling domain, track, or venue own this sentence?" If yes, compress to a link. The domain stops at: production judgment, review/API design, pattern composition — everything about *how the patterns work*, *where the consoles live*, or *what the words mean* lives elsewhere.


### 4) **Common confusion**

- "Mastery is where advanced patterns live" — mastery is *orchestration*; the advanced mechanics distribute across Domains 01–06. This leaf maps the summit; the climbs live below.
- "Boundaries leaves are filler" — they are the DRY contract made visible: each states what its domain deliberately does *not* teach so the repo can teach it once. Seven domains, seven maps, zero duplication — that was the design working.

### 5) **Performance note**

No runtime cost to boundaries — the performance is editorial: one-line links instead of copied sections keep every leaf short, searchable, and single-sourced. When venue limits change, zero leaves update (only venue links); when Domain 01 changes reason-naming guidance, one domain updates instead of seven.

### 6) **Mentor note**

Use this leaf as the graduation map: hand juniors the seven-domain stop-list and have them place any design question from their week into exactly one bucket — placement accuracy *is* track mastery (Domain 01's review check, now track-wide). Quiz the full arc: principles (01), creation (02), structure (03), command (04), distribution (05), modern (06), mastery (07). Correct placement across all seven means the learner sees design as a system, not a bag of tricks — the outcome this track was built to produce.
