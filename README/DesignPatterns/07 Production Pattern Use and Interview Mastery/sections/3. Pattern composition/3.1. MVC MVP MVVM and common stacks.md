## 3.1. MVC, MVP, MVVM, and common stacks

### 1) **MVC composes three patterns**

**Definition** — Model-View-Controller as pattern composition (not a pattern itself): Observer synchronizes views to model state (verified pair `5,50` — two subscribers, one state change; Domain 04 §2.1 mechanics); Strategy dispatches controller actions (input handling varies by context — leaf: Domain 04 §1.1); Composite structures view hierarchies (nested widgets treated uniformly — Domain 03 §3.1). MVC names the *wiring* (model notifies, view observes, controller strategizes); the catalog supplies the *pieces* (composed, not reinvented).

- **What problem it solves**: UI logic without architecture tangles all three concerns (state mutation inside render code — views untestable without DOM; input handling scattered per widget — behavior undiscoverable; data flow implicit — "which update refreshed this?" unanswerable). MVC separates along pattern lines (state observable — tested without rendering; actions strategized — dispatched per context; views composite — nested uniformly). Each piece independently understood (catalog knowledge transfers directly — MVC learned in an afternoon given Domains 03–04).
- **Modern guidance** — recognize MVC-instances by composition (Observer + Strategy + Composite present? — MVC-shaped regardless of framework branding; name the pieces explicitly in architecture docs). Test per piece (model logic without views — observer contracts asserting; controller strategies in isolation — swap matrices; view trees via composite oracles). Evolve pieces independently (view framework swaps without model changes — boundaries placed at pattern seams, not framework edges). Distrust MVC-labeled monoliths (all three concerns in one class — name misapplied; decompose per pattern, not per label).

```typescript
// GOOD: composition recognized (three catalog patterns, one architecture)
// Model (observable state) -> Views observe (verified 5,50 pair: two subscribers, one change).
// Controller dispatches strategies (per-context actions); Views nest as composites (uniform trees).
// BAD: "MVC" single class handling state+render+input ("pragmatic") —
// composition unrecognized (patterns present but fused); testing requires full stack (pieces inseparable)
```

### 2) **MVP/MVVM shift the seams**

**Definition** — Model-View-Presenter (presenter mediates *all* view logic — view passive, presenter tested without UI; explicit view interfaces per presenter — test doubles slide in) and Model-View-ViewModel (bidirectional bindings synchronize view/viewmodel — declarative updates; viewmodel exposes bindable state, view renders declaratively): same Model core, different view-coupling (MVP: presenter pushes to passive views — testability maximized; MVVM: bindings sync automatically — boilerplate minimized, magic maximized).

- **Why it matters (correctness)**: seam placement decides testability (MVP views need no logic tests — presenter unit-tested fully; MVVM bindings need binding tests — synchronization verified, not hoped) and failure modes (MVP: presenter bloat (god-presenter risk — split per view-complexity); MVVM: binding loops/cascades (circular updates — termination discipline required; stale bindings (observation gaps — verified-update patterns from Domain 04 §2.1, restated). Choosing by testing strategy (unit-heavy → MVP; binding-heavy → MVVM with binding tests) beats choosing by fashion.
- **Modern guidance** — choose MVP for testability-first UI (presenters fully unit-tested — views thin enough to trust untested; explicit view interfaces per presenter — doubles slide in). Choose MVVM for binding-heavy UI (declarative sync — boilerplate minimized; binding tests mandatory — synchronization verified per pair). Guard MVVM loops (circular binding detection — termination contracted; cascade depth bounded — update storms prevented structurally). Migrate MVP↔MVVM per testing economics (binding tests cheaper than presenter suites? — or vice versa; measured, not debated).

```bash
# GOOD: seams placed by testing strategy (testability decides architecture)
#  MVP: presenter unit-tested fully (views thin — trusted untested; doubles per view interface).
#  MVVM: bindings tested per pair (sync verified — declarative power with proven connections).
# BAD: "MVVM because modern" (fashion) with untested bindings ("declarative, obviously right") —
# synchronization hoped (cascade bugs); presenter logic untestable (views fatten silently)
```

### 3) **Stacks, not silver bullets**

**Definition** — frameworks compose catalog patterns with opinions (React: unidirectional data flow + component composites + hooks-as-strategy-injection; Express: middleware chain + router-facade + error lanes — Domain 06 §2.1 mechanics wearing framework branding; NestJS: DI containers + decorators + module facades — Domain 06 §1.1 + TS 14 + Domain 03 §1.2 composed). Recognizing pieces evaluates frameworks structurally (which patterns? composed how well? — beyond marketing into mechanics); silver-bullet thinking adopts wholes uncritically (framework identity substituting for pattern judgment).

- **Why it hurts when missing (correctness, maintainability)**: framework-monoculture thinking misattributes (framework bugs blamed on patterns — "observers are broken" when the *wiring* misfires; pattern virtues credited to frameworks — "React is fast" for virtual-DOM diffing, a structural technique). Composition recognition enables migration (frameworks swapped per piece — state management replaced without view rewrites; routers exchanged under stable facades). Silver-bullet loyalty blocks both (criticism framed as disloyalty; alternatives unevaluated structurally).
- **Modern guidance** — decompose frameworks into catalog pieces on adoption (name each pattern present — Observer/Strategy/Composite/DI/middleware identified; evaluate piece quality separately — strong composition + weak state story is common). Migrate per piece, never wholesale where avoidable (state layer swapped under stable views — strangler discipline from leaf 1.2, applied to frameworks). Choose frameworks by piece-fit (needed patterns strong + unneeded complexity absent — boring wins ties, leaf 1.1's criterion restated at framework scale).

```bash
# GOOD: frameworks evaluated as compositions (pieces named, wiring judged)
#  React: unidirectional flow (predictable) + composites (uniform trees) + hooks (strategy injection).
#  Express: middleware chain (ordered layers) + router facade (single entry) + error lanes (contracted).
#  adopt per piece-fit (needed strong + unneeded absent — boring wins ties at framework scale too).
# BAD: "standardized on X" without piece analysis (identity) —
# strengths uncredited precisely (what to keep in migrations?); weaknesses unexamined (what bites later?)
```

### 4) **Common confusion**

- "MVC is outdated" — MVC *composes* timeless patterns (Observer/Strategy/Composite don't expire); *frameworks* implementing MVC age (wiring choices, not pattern choices). Criticize implementations, not compositions.
- "MVVM eliminates presenters" — MVVM *relocates* presentation logic (viewmodels carry it — testable units, binding-tested; presenters vanish as classes, reappear as viewmodel responsibilities). Elimination claims misread relocation.
- "Recognizing pieces is academic" — piece recognition *routes* decisions (swap state layer? — pieces bound the blast radius; upgrade framework? — pieces name what's kept). Academic labels would sit unused; these direct migrations.
- "One architecture fits all UIs" — architectures fit *constraints* (testability needs → MVP; binding density → MVVM; simplicity → MVC-classic; scale → flux/Redux shapes — Domain 06 territory). Constraint-fit, never identity-fit.

### 5) **Performance note**

Composition awareness costs architecture-review time (piece identification per framework — hours once, dividends per migration decision); framework monoculture costs migration blindness (wholesale rewrites where piece-swaps sufficed — quarters) and misattributed incidents (pattern vs wiring confusion — debugging misrouted). MVVM bindings cost sync overhead per pair (verified-shape reasoning from Domain 04 §2.1 — binding counts scale with view complexity); MVP costs presenter indirection (nanoseconds per delegation — negligible beside testability dividends). Optimize piece recognition first (migration optionality), binding counts second (sync overhead measured), framework loyalty never (identity isn't architecture).

### 6) **Mentor note**

Decompose one framework live (team's own stack → catalog pieces on a whiteboard — "which patterns are we actually running?" converts framework identity into structural understanding). Contrast MVP/MVVM with testing economics ("what does each choice cost to verify?" — testability deciding architecture, not fashion). Practice strangler migrations on paper (piece-by-piece framework swaps — blast radius bounded per piece). Watch for the framework loyalist ("our stack does X" as argument-ender — fix with piece analysis: name patterns, evaluate separately) and the silver-bullet hunter ("which framework solves Y?" — fix with constraint-first selection, leaf 1.1 restated). Review check: pieces named, seams placed per testing strategy, migrations piece-scoped, juniors can decompose new frameworks unprompted.
