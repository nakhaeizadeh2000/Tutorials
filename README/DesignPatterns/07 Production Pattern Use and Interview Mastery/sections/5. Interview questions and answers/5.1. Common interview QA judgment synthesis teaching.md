## 5.1. Common interview QA: judgment, synthesis, teaching

### 1) **Design a URL shortener, narrated**

**Definition** — the systems screen: shortened-URL service designed aloud in fifteen minutes (requirements clarified → capacity estimated → APIs shaped → storage picked → scale-out sketched → trade-offs named): patterns placed per need (Factory for encoders, Repository for mappings, Cache-aside + CDN for reads, consistent hashing for shards — catalog applied at system scale). Graded on *structure* (layered reasoning: functional → scale → failure modes), not completeness (no fifteen-minute design finishes — prioritization *is* the test).

- **What a good answer sounds like**: clarified scope ("reads 100:1 over writes? custom aliases? TTL/expiry? analytics?" — questions before architecture), estimated scale ("100M URLs/month → ~40 writes/s average, 4k reads/s peak; 5 bytes × 10⁹ stored ≈ 50GB + index — single Postgres handles years; cache + CDN absorb reads"), seamed storage ("Repository over mappings — policy never sees SQL; consistent hashing past one node — shard by hash prefix"), failure-handled (idempotent creation — same long URL returns same short; collision retries bounded; cache-aside with TTL — stale mappings impossible by construction).
- **Modern guidance** — interviewers listen for *constraint-driven selection* (numbers before patterns — capacity arithmetic picks stores; traffic shape picks caches; consistency needs pick journals): candidates who estimate first pass; candidates who name-drop patterns fail the sizing follow-up ("how many machines?" unanswered). Red flags: microservices-first for hundreds of RPS ("scale" without numbers — fashion, not engineering), no failure analysis (happy-path architecture — partitions/unavailability unaddressed), skipping estimation entirely (design without budgets — the cardinal systems sin).

```bash
#  clarify (read/write ratio? aliases? expiry? analytics?) -> estimate (40 w/s, 4k r/s, 50GB + index).

#  fail (collision retries bounded; cache-aside TTL; dead-letters monitored).
```

### 2) **Refactor this live**

**Definition** — the judgment screen: real smelly code refactored aloud (god method + switch-on-kind + scattered construction — catalog entries named live: "god method (3 reasons) → extract per stakeholder"; "switch → strategy seam (leaf: Domain 04 §1.1)"; "inline `new`s → factory (leaf: Domain 02 §1.2)"), equivalence kept (existing tests green throughout — behavior preserved per step, strangler discipline from leaf 1.2 at code scale), narration continuous (decisions attached per edit — reviewers hear reasoning, not just typing).

- **What a good answer sounds like**: smells named before touched ("god method: pricing+persistence+notify — extracting per reason; switch-on-kind: strategy seam; scattered news: factory"), strangler-shaped edits (seam first — new structure beside old; migrate callers incrementally — tests green per step; delete old last — carcass removed loudly), equivalence evidenced (tests green throughout — no flag-day rewrites; behavior diffs reviewed, not hoped). Then the trade close (stopped where value thins — perfect refactors unbounded; time-boxed judgment over gold-plating).
- **Modern guidance** — grade *live judgment* (smell prioritization — blast-radius first, aesthetics last; strangler mechanics — seams before moves; equivalence discipline — green throughout): candidates who narrate trade-offs while refactoring pass; candidates who rewrite silently fail the collaboration screen (teammates can't follow unspoken plans). Instant fail: big-bang rewrite proposal ("cleaner to restart" — behavior unpreserved, risk unbounded, strangler unconsidered).


### 3) **Teach a pattern in five minutes**

**Definition** — the mastery screen: "explain Observer/Strategy/Builder as if I'm a smart junior" — explanation *is* understanding made audible (Feynman-shaped hiring: teachers debug their own models live; memorizers recite without transfer). Expected arc: problem in one sentence → idea in one sentence → hand-trace on toy input (verified numbers where known: fan-out counts, swap pairs, gate errors) → trade-offs stated → misuse named (when *not* to use it — judgment completing knowledge).

- **What a good answer sounds like**: Observer in five minutes ("many need to know when one changes — subject holds callbacks, notifies on change (verified fan-out); subscribers attach/detach freely (pairing!); use where producers mustn't name consumers; avoid where call graphs need explicitness — debugging event spaghetti"). Idea first, trace second, bounds third, misuse fourth — the arc that proves derivation over memorization. Questions welcomed mid-explanation (dialogue, not lecture — teaching *with*, not *at*).
- **Modern guidance** — listen for *verified numbers deployed casually* (fan-out counts, swap pairs, gate errors — measured evidence woven into teaching signals genuine mastery, not slideware). Red flags: definition recitation without traces (jargon without contact), limitation-free explanations ("no downsides" — every pattern has costs; omitting them signals shallow), monologue impervious to questions (teaching *at* — collaboration signal inverted). Follow-up separating staff: "when would you *refuse* this pattern?" (misuse conditions named — judgment behind knowledge).

```bash
# The teaching arc, timed (five minutes: problem, idea, trace, trade-offs, misuse)
#  1 problem ("many need state changes") -> 1 idea ("subject holds callbacks; notify on change").
#  -> 1 trace (verified fan-out live) -> trade-offs (decoupling vs lifecycle) -> 1 misuse (debugging spaghetti).
#  questions welcomed throughout (dialogue proves transfer; monologue proves memory).
```

### 4) **Common confusion**

- Candidates who treat systems design as pattern-dropping ("use Observer here, Factory there" — names without numbers; constraints unestimated, budgets uncomputed).
- "Live refactoring tests speed" (speed over judgment — rushed edits breaking equivalence; strangler discipline abandoned under watch). Methodical pace with narration outscores frantic typing.
- Treating teaching demos as performances (polish over precision — smooth delivery of approximate content; interviewers audit claims, not charisma).

### 5) **Performance note**

Mastery QA answers should be compact: systems design (fifteen minutes max — clarify/estimate/seam/scale/fail, prioritized not completed), live refactor (ten minutes — name/seam/migrate/delete with green throughout), teaching demo (five minutes — problem/idea/trace/trade-offs/misuse). Candidates who narrate with verified receipts take the same time as generalizers and prove triple — structure is speed, in mastery interviews as in analysis.

### 6) **Mentor note**

Use Q1 as the systems screen (constraints estimated, seams placed, failures handled), Q2 as the judgment screen (smells named, strangler mechanics, equivalence kept), Q3 as the mastery screen (traces with verified numbers, misuses owned, dialogue welcomed). Rubric: junior — structured attempts with counting shown; mid — trade-offs stated, edges covered, equivalence kept unprompted; senior/staff — constraint-driven selection, strangler economics, piece-evaluated frameworks without prompting. Keep the verified receipts ready (migration deltas, fan-out counts, gate errors) — structure narrated with evidence hires. Red-flag fails: numbers-free systems, rewrite prescriptions, limitation-free teaching.
