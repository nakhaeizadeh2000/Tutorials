## 5.1. Common interview QA: creational patterns

### 1) **Singleton vs static vs DI-singleton?**

**Definition** — the lifetime screen: three "one instance" shapes with different testability (classic Singleton: private constructor + global address — proven singularity, welded reachability; static class: no instance at all — no polymorphism, no seams, no reset hooks; DI-singleton: container creates once, injects everywhere — singularity arranged, global address never). Same cardinality, opposite engineering properties — the distinction interviews actually screen (lifetime confused with reachability by juniors).

- **What a good answer sounds like**: reachability-first analysis ("classic: globally addressable (untestable without resets); static: uninstantiable (unseamed — no fakes possible); DI: injected singly (testable — fakes slide in; swappable — vendors change)") plus whitelist discipline ("classic justified only for immutable-config/hardware-facade with freezing proof — leaf 1.1; else DI"). Then the production close (concurrency: JS event loop dodges data races but not async-interleaving — eager init or mutex where racy).
- **Modern guidance** — interviewers listen for *testability consequences* per shape (seams present/absent — the property that decides in production): candidates who analyze reachability pass; candidates who compare syntax ("static has no `new`") fail the engineering follow-up. Red flags: "singletons are anti-patterns, always" (absolutism — immutable-config/hardware entries legitimate) or "use whichever, same thing" (reachability blindness — the verified ignored-arg trap unmentioned).

```bash
# The lifetime answer, structured (leaf 1.1 as interview response)
#  classic:  proven singularity + global address (testability cost; whitelist + freeze required).
#  static:   no instance (no seams at all — fakes impossible; utilities only, never policy).
#  DI:       arranged singularity, injected reach (testable + swappable — default choice).
#  rule: inject; classic only with whitelist entry + freezing proof (verified ignored-arg trap cited).
```

### 2) **Factory Method vs Abstract Factory?**

**Definition** — the scope screen: Factory Method defers *one product* via subclassing (creator declares, subclass decides — leaf 1.2's verified render:pdf/html); Abstract Factory composes *families* via injection (suite coherence — leaf 2.1's verified light+light/dark+dark). Kind-axis growth favors the former (new product = new subclass, OCP-clean); family-axis growth favors the latter (new family = new factory, OCP-clean). Choosing by *growth forecast*, not by familiarity.

- **What a good answer sounds like**: axis analysis ("how will this vary — more kinds or more families? — Factory Method scales kinds (verified extension without edits); Abstract Factory scales families (verified one-line swaps); product additions tax families (N implementations — priced upfront)"). Then the composition close (creators injected with abstract factories where both vary — patterns compose; callers abstraction-typed throughout — leaf 1.2's rule, scaled). Seniors add the static-factory cousin (validation/naming without subclasses — pragmatic tier below both).
- **Modern guidance** — grade *forecast-based selection* (growth direction named before pattern picked): candidates who ask "will kinds or families multiply here?" pass; candidates who default to either fail the roadmap follow-up. Instant fail: "Abstract Factory is just bigger Factory Method" (different axes — inheritance vs composition, kinds vs families; conflation guarantees misselection on one axis).

```bash
# The scope answer, structured (leaves 1.2 + 2.1 as interview response)
#  kinds multiply, families stable   -> Factory Method (new subclass per kind; callers untouched).
#  families multiply, kinds stable   -> Abstract Factory (new factory per family; one-line swaps).
#  product additions                 -> priced upfront (N-family tax where applicable — no mid-sprint surprise).
```

### 3) **Builder vs telescoping constructor?**

**Definition** — the readability screen: fluent stepwise construction with build-gate validation (leaf 2.2's verified full/preset/gate outputs) vs positional overloads collapsing past ~4 parameters (unreadable call sites, scattered validation, boolean blindness). Threshold mechanical (~4 params — builder mandated past it; options-objects below it where shapes stay simple). Directors encode team recipes (top-3 configurations named — knowledge centralized).

- **What a good answer sounds like**: threshold reasoning ("past four positionals, call sites need comments to parse — comments admitting defeat; builder self-documents"), gate placement ("validation at `build()` — setters see fragments legitimately invalid mid-build; gate sees the whole"), recipe awareness ("directors for team-standard configurations — timeouts/retries decided once"). Then the honesty close ("options-objects below threshold — builder ceremony unjustified where destructuring suffices").
- **Modern guidance** — listen for *gate placement reasoning* (fragments vs whole — the decision that separates understanding from shape-memory): candidates who justify build-time validation pass even with shaky fluent syntax; candidates who validate in setters fail the legitimate-ordering follow-up. Red flags: "builders are verbose" without readability arithmetic (positional decode-cost per call site vs chain overhead — measured in review minutes, not keystrokes).

```bash
# The readability answer, structured (leaf 2.2 as interview response)
#  <= 4 params: positional/options-object (simple shapes, destructured defaults suffice).
#  >= 5 params: builder (fluent steps + build-gate + directors; verified full/preset/gate).
#  gate at build (fragments legitimately invalid mid-build); recipes named (team knowledge centralized).
```

### 4) **Common confusion**

- Candidates who answer lifetime questions with syntax comparisons ("static has no instance") — reachability/testability consequences are what's screened, not language trivia.
- "Bigger factory = better design" — factory granularity follows variation axes (kinds vs families); oversized factories for stable singles tax readers without coherence payoff.
- Treating builder threshold as taste ("I prefer...") — thresholds are mechanical (4 params — review-enforced); taste debates end where rules begin.

### 5) **Performance note**

Creational QA answers should be compact: lifetime distinctions (two minutes — reachability/testability per shape + whitelist), scope selection (two minutes — axes forecast + tax priced), readability threshold (90 seconds — gate reasoning + recipe awareness). Candidates who narrate with verified receipts (identity trap, render outputs, gate errors) take the same time as generalizers and prove triple — structure is speed, in creational interviews as in analysis.

### 6) **Mentor note**

Use Q1 as the lifetime screen (reachability analyzed, whitelist applied), Q2 as the scope screen (forecast-based selection, tax priced upfront), Q3 as the readability screen (gate reasoning, threshold mechanics). Rubric: junior — correct pattern names with mechanics shown; mid — trade-offs stated (testability, axes, gates) unprompted; senior — forecast-based selection, priced pragmatism, borrow-vs-build discipline without prompting. Keep the verified numbers ready (identity trap, render outputs, gate error) — receipts separate narrators from memorizers. Red-flag fails: reachability blindness, axis-blind factory choice, taste-based thresholds.
