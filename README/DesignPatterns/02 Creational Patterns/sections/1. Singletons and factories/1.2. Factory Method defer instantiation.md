## 1.2. Factory Method: defer instantiation

### 1) **Creators declare, subclasses decide**

**Definition** — Factory Method defines object creation as an *overridable step*: an abstract creator declares `make()` (returning a product abstraction) and implements workflows *around* it (`render()` calling `this.make()` — framework logic stable); subclasses override `make()` to supply concrete products (`PdfCreator`/`HtmlCreator` — verified `render:pdf`/`render:html`, identical workflow, divergent products). Callers use creators polymorphically (never naming concretes — extension adds subclasses, never edits).

- **What problem it solves**: hardcoded instantiation welds workflows to products (`new Pdf()` inside `render()` — every new format edits the workflow, re-earns its tests, conflicts per contributor). Factory Method inverts the weld (workflow depends on creator abstraction — new products arrive as new subclasses, existing code untouched — leaf 1.2-of-01's OCP wearing GoF clothes). Framework/library design *is* this pattern (callers extend by subclassing creators — inversion of control at construction time).
- **Modern guidance** — reach for Factory Method when workflows outlive product kinds (renderers, parsers, validators — stable processes, growing product families). Declare products as abstractions (return `Doc`, never `Pdf` — callers depend on product interfaces, concretes invisible). Keep creators focused (one factory method per product axis — multi-axis creation is Abstract Factory's job, leaf 2.1; single-axis deferred cleanly here). Name creators after workflows (`DocRenderer`), not mechanics (`PdfFactoryForRender`).

```typescript
// GOOD: workflow stable, products pluggable — verified render:pdf/render:html
abstract class DocCreator {
  abstract make(): { kind: string };              // subclasses decide WHAT (deferred instantiation)
  render(): string { return `render:${this.make().kind}`; }  // creator decides HOW (stable workflow)
}
class PdfCreator extends DocCreator { make(): { kind: string } { return { kind: "pdf" }; } }
class HtmlCreator extends DocCreator { make(): { kind: string } { return { kind: "html" }; } }
// New format = new subclass (zero edits to DocCreator/render — OCP verified live).
// BAD: render(kind: string) with if/else per format ("simpler, no classes") —
// every format edits one function (leaf 1.2-of-01's switch tax, restated for products)
```

### 2) **Callers depend on products, never concretes**

**Definition** — the dependency rule completing the pattern: client code names product *abstractions* (parameters, returns, fields typed as `Doc`/`Shape` — never `Pdf`/`Circle`), and construction sites narrow to factory implementations (one `new PdfCreator()` per kind, at composition roots — leaf 2.2-of-01's explicit wiring). Concretes exist at exactly two places (their class definition, their factory's `make()`) — everywhere else, abstractions flow. Blast radius of new products: two files (product + factory), zero callers.

- **Why it matters (correctness)**: concrete-typed callers shatter per product (adding `SvgDoc` means editing every `Pdf`-typed parameter, return, and field — the shotgun surgery factories exist to prevent; each edit site risks mistyped assumptions about the new kind). Abstraction-typed callers absorb products silently (new kinds flow through existing signatures — substitutability proven per leaf 2.1-of-01, or the type system would refuse). The rule converts product growth from codebase-wide edits into factory-local additions.
- **Modern guidance** — type all cross-boundary positions as abstractions (parameters, returns, public fields, collection elements — concretes stop at factory doors). Centralize construction per kind (one factory method/class each — `new` countable per product, auditable in review). Enforce with lint where valuable (no-restricted-imports on concrete product modules from client code — mechanical abstraction discipline). Document the closed set where finite (three document kinds, extension via subclass — callers stable, families explicit).

```typescript
// GOOD: abstractions flow, concretes hide (two files per new product, zero caller edits)
function publish(doc: { kind: string }): string { return `pub:${doc.kind}`; }  // abstraction-typed
publish(new PdfCreator().make());  // new kinds arrive without touching publish (verified pattern).
// BAD: publish(doc: Pdf) concretely typed ("we only have PDFs") —
// first Html requirement edits publish + callers + tests (shotgun surgery for a one-kind assumption)
```

### 3) **Static factories are the pragmatic cousin**

**Definition** — static factory methods (`User.create()`, `Money.fromCents()`, `Config.parse()`) deliver factory benefits without subclasses (named construction — `fromCents` reads better than `new Money(100, true)`; validation at the gate — invariants enforced once; caching/memoization — canonical instances returned; subtype selection — return type wider than any branch). [TS 06 §1.2 owns the typing mechanics](<../../../../TypeScript/06 Classes and Object-Oriented Types/sections/1. Class Type Fundamentals/1.2. Constructors parameter properties and instance creation.md>) (private constructors, `static create` shapes — linked, never re-taught); this leaf owns the *pattern judgment* (when statics suffice vs full Factory Method).

- **Why it hurts when missing (correctness, maintainability)**: public constructors scatter validation (every `new User(raw)` site re-checks email/branding — or doesn't, leaking invalid shapes), hide intent (boolean/positional args unreadable at call sites — `new Money(100, true)` means what?), and forbid evolution (caching/flyweight/subtype returns need signature-compatible surgery later). Named statics centralize all three (one validation gate, readable names, future-flexible returns — same call sites keep working as factories grow smarter).
- **Modern guidance** — prefer static factories for validation-heavy construction (invariants once, at the named gate — `User.create(raw)` throwing on invalid). Name by semantics (`fromCents`, `parse`, `empty` — call sites self-document). Hide constructors where factories own creation (`private constructor` + statics — the only path runs through validation). Graduate to full Factory Method when *workflows* (not just construction) vary by kind (render/parse/validate pipelines per product — subclass territory, leaf's main pattern).

```typescript
// GOOD: named gates with validation (statics where subclasses overkill)
// static fromCents(c: number): Money { if (!Number.isInteger(c)) throw new RangeError("cents"); ... }
// static parse(raw: string): Config { /* validate once, cache by content */ }
// call sites read intent (Money.fromCents(100) vs new Money(100, true)); gates enforce invariants once.
// BAD: public constructors + "validate at use" ("flexible") —
// invalid shapes reach instances (email unvalidated, ids unbranded); flexibility billing per consumer
```

### 4) **Common confusion**

- "Factory Method means factory classes" — Factory Method means *deferred instantiation via override* (creator declares, subclass decides); standalone factory *functions/objects* are Simple Factory (useful, non-GoF — no subclassing involved). Names matter because mechanics differ.
- "Abstract Creator must be abstract" — creators need *overridable* `make()` (template-method shape — concrete defaults with documented hooks qualify where subclasses refine rather than define). Abstractness is typical, not definitional.
- "Static factories replace Factory Method" — statics centralize *construction* (validation/naming/caching); Factory Method defers *product choice through workflows* (render/parse pipelines varying by kind). Overlapping tools, different jobs — statics first, subclasses when workflows vary.
- "More factories = better design" — factories serve *varying* products (kinds arriving over time); stable single products need plain constructors (factory ceremony without variation taxes readers). Variation decides, not uniformity.

### 5) **Performance note**

Factories cost one indirection per creation (virtual dispatch — nanoseconds, devirtualized at monomorphic sites) plus subclass count (files, not runtime). Switch-statements cost branch prediction + re-test blast radius per kind (human pipeline — days). Static factories cost nothing over constructors (same call, better name — free readability). Optimize caller stability first (abstraction-typed call sites absorb products free), construction clarity second (named gates beat positional args), dispatch overhead never (nanoseconds, optimized away).

### 6) **Mentor note**

Contrast live (switch-`render(kind)` vs creator-hierarchy on a new format — "watch the diff: one function edited vs one file added" converts deferral from theory to observable). Drill product-abstraction typing ("name one concrete in client code" as review failure — concretes stop at factory doors). Practice static-factory naming (boolean/positional constructors rewritten as named gates — call-site readability transformations). Watch for the switch-accumulator ("one more kind" × N — fix with factory extraction at kind two) and the factory-proliferator (factories for stable singles — fix with "what varies here?"). Review check: creators declare/products decide, callers abstraction-typed, statics named with gates, juniors can place new kinds unprompted.
