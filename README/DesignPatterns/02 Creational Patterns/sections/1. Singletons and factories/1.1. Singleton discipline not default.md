## 1.1. Singleton: discipline, not default

### 1) **One instance with a global address**

**Definition** — Singleton guarantees one instance (private constructor — `new` forbidden outside) with global access (static accessor — `Config.get()` from anywhere). Verified: two `get()` calls return identical reference (`true`), and the second call's argument is *ignored* (`apiUrl` stays `https://api.prod` — the classic gotcha: parameters after first initialization vanish silently). Testability dies proportionally (global state shared across tests — order-dependent suites, parallel runs conflicting).

- **What problem it solves**: genuinely singular resources need exactly-once semantics (hardware handles, process-wide registries, immutable configuration loaded once — duplication *breaks* correctness, not just wastes memory). Singleton encodes singularity in the type system (unconstructible elsewhere — private constructor *proves* uniqueness where discipline merely promises). The pattern's value is entirely in proven singularity; everywhere else it's global state wearing a tuxedo.
- **Modern guidance** — reach for Singleton only with *written* singularity justification ("exactly one because hardware/config-immutability demands it" — the sentence that separates use from abuse). Prefer dependency injection of a single shared instance (constructor takes `Config` — testability preserved, singularity arranged at the composition root, leaf 2.2-of-01's seams at work). Freeze shared instances (`Object.freeze` — [TS 06's readonly-leak lesson](<../../../../TypeScript/06 Classes and Object-Oriented Types/sections/5. Common pitfalls to production bugs/5.1. Real production bugs caused by class type misunderstandings.md>), linked never re-taught: `readonly` erases, aliases mutate).

```typescript
// GOOD: singularity proven (private constructor) — verified identity + ignored-arg gotcha
class Config {
  private static inst: Config | undefined;
  private constructor(public readonly apiUrl: string) {}
  static get(url = "https://api.prod"): Config {
    if (!Config.inst) Config.inst = new Config(url);  // first call wins; later args vanish (verified)
    return Config.inst;
  }
} // get() === get("https://other") -> true; apiUrl stays prod (gotcha documented, not hidden).
// BAD: Singleton "for convenience" (one database pool "everywhere") —
// test pollution (suites share connections), hidden coupling (imports lie about dependencies),
// concurrency hazards (parallel tests racing one pool) — global state, tuxedoed
```

### 2) **Shared mutable state is the liability**

**Definition** — mutable singletons concentrate every shared-state hazard (test-order dependence — suite passes alone, fails in sequence; hidden coupling — import graphs lie about data flow; concurrent mutation — races without locks, torn reads without atomics; stale reads across request scopes — per-request data leaking via singleton fields). Each hazard scales with singleton *count* and *mutability*: immutable singletons carry ~zero (frozen config — safe); mutable ones carry all four (the toothbrush problem: strangers sharing state nobody owns).

- **Why it matters (correctness)**: singleton incidents are process-global by construction (one corrupted instance poisons *every* consumer — request A's data in request B's response; test 12's setup leaking into test 40; race windows open across the whole runtime). Debugging misattributes (symptoms appear far from the shared write — request-scoped thinking applied to process-scoped state). The liability is structural (singularity × mutability × global-reach), not incidental — only removal (injection) or freezing (immutability) discharges it.
- **Modern guidance** — freeze what must be singular (immutable config post-load — `Object.freeze` + `readonly`; stateless service facades — pure functions behind singleton addresses). Scope what varies (per-request state in request contexts — AsyncLocalStorage, explicit parameters; never singleton fields). Isolate tests from singletons (reset hooks between tests at minimum — better: inject fakes per test, leaf 2.2-of-01's dividend). Audit mutability per singleton quarterly (mutable-singleton count should trend toward zero — each survivor re-justified in writing).

```typescript
// GOOD: singular AND immutable (liability discharged structurally)
// const CONFIG = Object.freeze({ apiUrl: "https://api.prod", retries: 3 });  // frozen: sharing safe
// Per-request state travels in parameters/contexts — never singleton fields (scope discipline).
// BAD: mutable UserSession singleton ("current user, globally") —
// request bleed (A sees B), test coupling (order-dependent suites), race windows (concurrent mutation) —
// three incident classes, one `static current`
```

### 3) **Legitimate singletons are rare and boring**

**Definition** — the whitelist (short, deliberately): immutable process configuration (loaded once, frozen — reads scale freely); single hardware/OS handles (one GPU context, one serial port — singularity imposed by physics, not preference); idempotent service facades with zero state (pure-function namespaces needing an address — loggers without buffers, clocks without offsets). Each is *boring* (no behavior worth testing in isolation, no state worth mutating) — boredom is the qualification. Interesting singletons (caches, pools, registries with behavior) want injection (testability) or explicit lifecycle (pools with drain — managed, not global).

- **Why it hurts when missing (correctness, maintainability)**: singleton-by-default codebases calcify around globals (every new feature reaches for the pattern — "consistent" architecture of shared mutable everything; testing degrades to integration-only (unit isolation impossible — fakes can't replace globals); concurrency retrofits fail structurally (locks bolted onto designs assuming singularity of *access*). The boring-whitelist disciplines adoption (novel singleton proposals name their whitelist entry — or get injected instead). Rarity is the feature: each legitimate singleton *reduces* alternatives considered.
- **Modern guidance** — check the whitelist before `private constructor` (immutable config? hardware handle? stateless facade? — none matches → inject). Prefer DI-singleton lifetime (container creates once, injects everywhere — singularity *arranged*, globally addressable *never* — leaf 5.1's lifetime screen previews the distinction). Document each singleton's whitelist entry ("immutable config — frozen at load" — the sentence preventing cargo-cult copies). Review new singletons skeptically (default answer: inject; singleton requires written singularity proof).

```bash
# GOOD: whitelist-checked singularity (boring, frozen, justified)
#  immutable config (frozen post-load) ...... singleton OK (reads scale, writes impossible).
#  GPU context (physics: one) ............... singleton OK (singularity imposed, not chosen).
#  connection pool (stateful, testable!) .... INJECT (test doubles, lifecycle mgmt, no globals).
#  "current user" (per-request!) ............ CONTEXT/PARAM (singleton = request bleed, verified shape).
# BAD: singleton-by-default ("consistent architecture") —
# consistency of shared mutability; testing/integration-only; concurrency retrofit structurally blocked
```

### 4) **Common confusion**

- "Singleton vs static class" — statics lack lazy init, polymorphism (no interface implementation — untestable seams), and reset hooks (tests can't replace); singletons add all three (lazy accessor, `implements` seams, resettable for tests — with discipline). Different tools sharing global reach.
- "DI singletons are the same" — DI containers *arrange* one instance and *inject* it (no global address — testability preserved); classic singletons *address* globally (coupling welded). Lifetime shared, reachability opposite — reachability is what bills.
- "Thread-safe singleton = double-checked locking" — JS single-threaded event loop dodges data races (but not async interleaving — `await` between check-and-set reintroduces races; mutex or eager init where racy). Import the pattern's reasoning, not Java's implementation.
- "Freezing hurts performance" — `Object.freeze` costs one pass at creation (shallow — deep-freeze recursively where nested mutation threatens); reads run full speed (hidden-class stable — V8 optimizes frozen shapes normally). Safety free at steady state.

### 5) **Performance note**

Singletons cost one allocation ever (memory minimal — the pattern's only honest performance argument) plus global-cache locality (single address, always hot). Mutable singletons cost test time (order-dependent suites rerun/debugged), incident time (process-global corruption archaeology), and concurrency retrofits (locks bolted late — contention designed in). Optimize incident avoidance (immutability/injection eliminate whole classes) over allocation counting (one object saved vs suites debugged). Boring singletons are free; interesting ones bill forever.
