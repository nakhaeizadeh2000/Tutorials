## 4.1. Creational checklist (habits mentors insist on)

### 1) **`new` lives behind seams**

**Definition** — construction sites counted and justified (each `new` of a domain type either behind a factory/builder/registry seam or documented why direct): callers receive abstractions (leaf 1.2's rule — concretes stop at factory doors), families compose at roots (leaf 2.1's one-line swaps), configurations clone from catalogs (leaf 3.1's registries). Unseamed `new` in client code is the review flag (each instance either justified in place or routed behind a seam).

- **What problem it solves**: scattered construction scatters creation knowledge (validation logic per call site — leaf 1.2's leak; theme consistency per component — leaf 2.1's drift; setup costs per instance — leaf 3.1's recomputation). Seam-behind creation centralizes all three (gates, coherence, amortization — each owned once, consumed everywhere). The checklist converts "where is this built?" from archaeology into seam lookup.
- **Modern guidance** — count `new` per product kind in review (one site per kind ideal — factory/registry/builder; more sites need justification each). Type cross-boundary positions as abstractions (parameters/returns/fields — concretes stop at seams). Route family decisions to roots (bootstrap/tests choose; mid-graph construction is prop-drilling wearing `new`). Test construction paths ( Factories/registries under contract suites — creation correctness proven, not hoped).

```bash
# GOOD: construction counted, seamed, tested (reviewable creation)
#  kinds: 4 products x 1 factory site each (counted, justified) + registry catalog (reviewed).
#  callers: abstraction-typed throughout (concretes stop at factory doors — grep verifies).
#  tests: factory contract suites green (creation proven per kind).
# BAD: `new Pdf()` in 14 files ("direct") —
# validation scattered, themes drifted, setup recomputed (creation knowledge archaeologized per change)
```

### 2) **Singletons justified, never defaulted**

**Definition** — each singleton carries written justification (whitelist entry: immutable config / hardware handle / stateless facade — leaf 1.1) plus freezing proof (`Object.freeze` or statelessness demonstrated — shared mutability discharged structurally). Unjustified singletons route to injection (constructor takes the dependency — testability preserved, singularity arranged at roots). Default answer in review: inject; singleton requires proof.

- **Why it matters (correctness)**: default singletons calcify test suites (order-dependence, parallel conflicts — suite reliability decays per singleton), weld vendors (untestable without live services — leaf 2.2-of-01's dividend forfeited), and schedule concurrency retrofits (locks bolted late — contention designed in). Justification-per-singleton converts adoption from habit into decision (boring whitelist entries pass quickly; interesting ones get injected — both fast, both correct).
- **Modern guidance** — demand whitelist + freezing per singleton in review ("which entry? frozen proof?" — two questions, thirty seconds). Prefer DI-singleton lifetime (container arranges singularity — globally addressable never). Reset hooks as minimum hygiene (between-test resets where injection genuinely impossible — legacy seams, documented as debt with removal dates). Audit singleton count quarterly (trending toward zero mutable — each survivor re-justified or refactored).

```bash
# GOOD: singularity evidenced (whitelist + freezing, per instance)
#  CONFIG: immutable-config entry + Object.freeze proof (reads scale, writes impossible).
#  POOL: not singleton — injected (test doubles, lifecycle mgmt). USER: context/param (per-request scope).
# BAD: "consistent singleton architecture" (habit) —
# test pollution + vendor welding + concurrency debt (three incident classes, one default)
```

### 3) **Builders past four parameters**

**Definition** — telescoping constructors banned past ~4 parameters (fluent builders or options-objects mandated — leaf 2.2's threshold): call sites self-document (named steps over positions), validation gates at `build()` (incomplete unbuildable — atomic construction), directors encode team recipes (top-3 configurations named, reviewed, versioned). Threshold enforced in review (5th positional parameter triggers builder conversion — mechanical rule, no taste debates).

- **Why it hurts when missing (correctness, maintainability)**: positional calls misread silently (swapped same-type args compile cleanly — `new Money(100, true)` vs `(true, 100)` both typecheck, one lies; boolean blindness compounds per parameter — readability decays exponentially past four). Validation scatters without gates (per-setter fragments or post-construction checks — incomplete objects escape somewhere). Team recipes drift without directors (12 timeout variants — no standard to converge on). The threshold converts all three from judgment calls into review mechanics.
- **Modern guidance** — enforce the four-parameter rule mechanically (5th positional = builder conversion required — no debates, just threshold). Gate validation at `build()` exclusively (setters accumulate — fragments legitimately invalid mid-build). Name top-3 recipes as directors (reviewed defaults — knowledge centralized). Prefer options-objects below threshold (destructured bags — builder ceremony unjustified where shapes stay simple).

```bash
# GOOD: threshold enforced (mechanical, not tasteful)
#  <= 4 params: positional or options-object (simple shapes, destructured defaults).
#  >= 5 params: builder mandated (fluent steps + build-gate + directors for top-3 recipes).
#  5th positional in review -> convert (rule, not discussion).
# BAD: "readable enough" 7-positional constructors ("team knows the order") —
# knowledge tribal, swaps silent, validation scattered (readability billed per call site forever)
```

### 4) **Common confusion**

- "Checklists replace pattern fluency" — checklists *trigger* the right pattern at the right moment (seam? justification? threshold?). Fluency implements factories/builders/registries. Both, in that order.
- "Small codebases don't need creation discipline" — small codebases need *lighter* versions (one factory per kind, builder past threshold, whitelist per singleton), not zero: undisciplined creation fossilizes as it grows (seams retrofitted under load cost 10×).
- "Counting `new` is pedantry" — construction count *is* creation knowledge distribution (scattered = unowned). Pedantry that prevents shotgun surgery is engineering.

### 5) **Performance note**

The checklist costs minutes per creation decision (seam placement, justification writing, threshold checking) against scattered-construction incidents (validation leaks, theme drift, recomputed setups — hours of debugging answers that aren't errors) and test-suite decay (order-dependence, live-service coupling — reliability billed per run). Highest-leverage item is seam-behind-`new` (centralizes gates/coherence/amortization); second is singleton justification (prevents test/incident classes); third is builder threshold (readability at scale). Minutes preventing rewrites — creational's best attention rate.

### 6) **Mentor note**

Convert this leaf into the team's creation runbook: seams counted, singletons justified, builders thresholded — every product kind, every PR. Quiz juniors on routing ("which checklist item fires for a 6-positional constructor? for global state? for theme variants?") until answers are environmental. Watch for checklist decay (creation discipline for a sprint, abandoned under deadline — fix with `new`-counting and threshold rules as review-blocking) and pattern-theater ("factory everywhere" without variation — fix with "what varies here?"). Review check: construction seamed, singletons evidenced, builders thresholded — and the mentor's own construction code modeling all three visibly.
