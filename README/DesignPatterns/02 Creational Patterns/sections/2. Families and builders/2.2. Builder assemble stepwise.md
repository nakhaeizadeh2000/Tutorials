## 2.2. Builder: assemble stepwise

### 1) **Fluent steps replace telescoping constructors**

**Definition** — Builder assembles objects through chained setters (each returns `this` — calls read as sentences) instead of positional constructors (telescoping overloads collapsing past 4–6 parameters — which argument is `true`? which `5000`?). Verified: full chain produces `{"method":"POST","url":"https://x","timeout":1000,"retries":2}` (self-describing at every step); preset produces `{"method":"GET","url":"https://y","timeout":5000,"retries":0}` (defaults documented in one place). Readability scales with parameter count (fluent constant, positional exponential decay).

- **What problem it solves**: telescoping constructors rot readability combinatorially (overload #7 differs from #6 by one middle boolean — call sites become positional riddles; optional parameters interact (timeout-without-retries meaning what?) without expressing it). Fluent builders name every argument at use (`.timeout(1000)` self-documents; order irrelevant; omission explicit via defaults). Code review reads *intent* (named steps) instead of decoding positions (the 4th argument of 7 — archaeology per call site).
- **Modern guidance** — reach for Builder past ~4 parameters (the threshold where positional calls need comments to parse — comments admitting defeat; builder never does) or with complex defaults/interactions (timeout-retries coupling expressed in `build()`, not scattered). Keep steps chainable uniformly (every setter returns `this` — broken chains from void setters are the classic implementation bug; type the return, test the chain). Prefer options-objects for simple cases (one bag parameter, destructured defaults — builder ceremony unjustified below threshold).

```typescript
// GOOD: sentences, not positions — verified full + preset outputs
class ReqBuilder {
  private r: Partial<Req> = {};
  method(m: string): this { this.r.method = m; return this; }  // uniform this-return (chains never break)
  url(u: string): this { this.r.url = u; return this; }
  timeout(ms: number): this { this.r.timeout = ms; return this; }
  retries(n: number): this { this.r.retries = n; return this; }
  build(): Req { /* validate + defaults (next section) */ return null as unknown as Req; }
}
// new ReqBuilder().method("POST").url("https://x").timeout(1000).retries(2).build() (verified above).
// BAD: new Req("POST", "https://x", 1000, 2, false, null, 0) ("fewer files") —
// positional riddle (which 0?); optional interactions inexpressive; review decodes per call site
```

### 2) **Validation at `build()` time**

**Definition** — the builder accumulates *possibly-invalid* partial state, then validates *once* at `build()` (required fields present? ranges sane? interactions consistent? — verified gate: missing URL throws `"url required"`). Incomplete objects are *unbuildable* (no half-constructed instances escape — construction atomicity: all-or-validated-nothing). Contrast per-setter validation (rejects valid intermediate states — partially-built objects can't pass through invalid middles legitimately needed en route).

- **Why it matters (correctness)**: validation scattered across setters either over-constrains (intermediate states rejected — builder unusable for legitimate orderings) or under-constrains (invalid finals constructed — invariants enforced nowhere, caught downstream as mysterious misbehavior). Single-gate validation sees the *whole* object (cross-field rules checkable — timeout-required-with-retries expressed once; defaults applied coherently — GET/5000/0 documented together, verified in preset output). Invalid objects become unrepresentable (the type plus the gate prove it — callers downstream never validate again).
- **Modern guidance** — validate exclusively in `build()` (setters accumulate blindly — intermediate freedom; gate decides finally). Fail with named errors (`"url required"` — which field, why — debuggable in one read). Apply defaults beside validation (one place documents the full default surface — GET/5000/0 together, verified). Return frozen products where immutability matters (`Object.freeze` on built value objects — post-build mutation defeats gate validation silently).

```typescript
// GOOD: gate validation, atomic construction — verified gate fires on missing URL
build(): Req {
  const { method = "GET", url, timeout = 5000, retries = 0 } = this.r;  // defaults co-located
  if (!url) throw new Error("url required");                            // gate: incomplete unbuildable
  return { method, url, timeout, retries };
} // build() without url -> throws "url required" verified (atomicity: no partial Req escapes).
// BAD: validating setters ("fail fast") —
// legitimate orderings rejected (timeout-before-url fails url-check prematurely); gates belong at build
```

### 3) **Directors encode recipes**

**Definition** — directors are named preset-builders (`ReqBuilder.quick(url)` — common configurations as one call: verified `{"method":"GET","url":"https://y","timeout":5000,"retries":0}`): recipes encode team knowledge (sane timeouts, retry policies, standard headers — decisions made once by experts, consumed by everyone). Callers choose recipes over raw builders where standard fits (one call, reviewed defaults); raw builders remain for custom cases (full control, explicit responsibility).

- **Why it hurts when missing (correctness, maintainability)**: preset knowledge scattered per call site drifts (timeouts 1000 here, 30000 there — no standard, retry policies invented per feature — incident variance; header X set in 12 places, missed in the 13th — partial application of team decisions). Directors centralize recipes (one `quick()` reviewed by the team — timeout/retry/header decisions versioned together; call sites choose by name — intent visible in code: `quick` vs `patient` vs custom). Drift converts to deliberate deviation (custom builds *named* as such — reviewers see nonstandard choices explicitly).
- **Modern guidance** — encode the top-3 configurations as directors (quick/patient/batch — named after use cases, not parameters; reviewed defaults, versioned together). Keep directors thin (delegate to the builder — no parallel construction logic to drift). Name custom builds distinctively (raw builder usage signals deliberate nonstandard — reviewers verify intent, not just correctness). Retire stale recipes (defaults drift with infrastructure — directors reviewed yearly, deprecated loudly).

```typescript
// GOOD: recipes as named entry points — verified preset output
static quick(url: string): Req { return new ReqBuilder().url(url).build(); }  // sane defaults, one call
// team knowledge centralized (timeouts/retries/headers decided once); custom builds explicit (raw builder).
// BAD: copy-pasted builder chains per call site ("flexible") —
// 12 timeout variants, 3 header sets, 0 standards (drift); recipes unfound where most needed
```

### 4) **Common confusion**

- "Builder means fluent chaining" — chaining is *syntax*; Builder means *stepwise validated construction* (accumulate → gate → atomic product). Fluent setters without `build()` validation are just setters that return `this`.
- "Options objects replace builders" — options objects replace *simple* builders (flat params, independent defaults — destructuring suffices); stepwise validation, conditional steps, and recipes need real builders (gates, directors, ordered accumulation). Threshold ~4 params/complex interactions.
- "Directors are just helper functions" — directors encode *reviewed team decisions* (defaults versioned together, named by use case); helpers encode *convenience* (shorter calls, no decisions). Recipes carry authority; helpers carry brevity.
- "Validation belongs in setters" — setters see *fragments* (intermediate states legitimately invalid mid-build); `build()` sees the *whole* (validation with full context). Fail-fast misplaced rejects valid constructions.

### 5) **Performance note**

Builders cost one partial object + chain calls per construction (nanoseconds — allocation trivial beside I/O-bound request lifecycles; hot-path construction pools or reuses builders where profiles demand). Validation costs one pass at gate (vs scattered per-setter checks — fewer total validations, better locality). Telescoping alternatives cost readability (review time per call site — human pipeline) and defect risk (positional mistakes — swapped args compiling cleanly). Optimize review clarity first (named steps beat positions), allocation second (pool only profiled hot paths).

### 6) **Mentor note**

Contrast live (7-positional constructor vs fluent chain on identical objects — "which call would you approve at 2 AM?" converts readability from taste to observable). Drill gate placement ("validate where? — setters see fragments, build sees whole" until unanimous). Practice recipe naming (top-3 team configurations as directors — knowledge centralized visibly). Watch for the telescoper ("fewer files" positional riddles — fix with call-site readability review) and the premature-validator (setter gates rejecting legitimate orderings — fix with gate-at-build discipline). Review check: chains unbroken (`this` returns), gates at `build()`, recipes named, juniors can convert positional calls fluently unprompted.
