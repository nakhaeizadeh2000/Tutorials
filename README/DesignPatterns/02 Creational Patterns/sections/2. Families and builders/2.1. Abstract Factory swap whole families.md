## 2.1. Abstract Factory: swap whole families

### 1) **Interfaces per product, factory per family**

**Definition** — Abstract Factory provides an interface for creating *families* of related products (buttons + checkboxes × light/dark themes) without naming concretes: one factory interface (`button()`, `checkbox()`), one implementation per family (`LightFactory`, `DarkFactory`), clients composed with a factory (theme consistency guaranteed structurally — light buttons never meet dark checkboxes because no code path mixes factories). Verified: `renderUI(LightFactory)` → `light-btn+light-chk`, `DarkFactory` → `dark-btn+dark-chk` — consistent suites from one injected seam.

- **What problem it solves**: product families drift inconsistently without it (theme passed per-component — light button beside dark checkbox after one missed call site; platform variants constructed ad hoc — Windows dialog with macOS button; test doubles swapped partially — half-mocked subsystems). Family factories make consistency *structural* (one seam selects the universe — all products cohere by construction, not by discipline). Mixed-family bugs become unrepresentable (no code path combines across factories — the type system enforces what reviews used to beg).
- **Modern guidance** — reach for Abstract Factory on product *suites* varying together (themes, platforms, vendors, tenants — dimensions where partial swaps corrupt). Define one method per family member (factory interface mirrors the suite — Button + Checkbox + Scrollbar together, never piecemeal). Inject the factory at composition roots (theme/platform chosen once per app/test — entire product line pivots on one seam). Keep families genuinely parallel (members used together in practice — forced grouping of unrelated products taxes implementers per family).

```typescript
// GOOD: consistency structural — verified light+light / dark+dark (mixing unrepresentable)
interface UIFactory { button(): Button; checkbox(): Checkbox; }  // suite shape, family-agnostic
class LightFactory implements UIFactory {
  button(): Button { return new LightButton(); }
  checkbox(): Checkbox { return new LightCheckbox(); }
}
function renderUI(f: UIFactory): string { return f.button().paint() + "+" + f.checkbox().check(); }
// renderUI(new LightFactory()) -> light-btn+light-chk; DarkFactory -> dark-btn+dark-chk (verified).
// BAD: theme string threaded per component ("flexible") —
// one missed call site mixes families (light button, dark checkbox); consistency by discipline rots
```

### 2) **Family swaps are one-line composition changes**

**Definition** — swapping product families means changing *which factory is injected* (composition root: `LightFactory` → `DarkFactory` — one line; tests: real → fake factory — same seam): all products pivot together (buttons, checkboxes, scrollbars — coherent by construction), zero client edits (callers depend on factory + product abstractions — leaf 1.2's rule, scaled to suites), zero mixed states (old and new families never coexist in one composition — atomicity by seam).

- **Why it matters (correctness)**: family migrations without the pattern edit per product (theme change touching every construction site — dozens of edits, partial application mid-migration (half-themed UI shipped), test doubles requiring per-product mocks (mock drift across suite members). One-seam swaps convert migrations from multi-file edits into configuration (feature flags select factories — dark mode rolls out by config; A/B variants compose per cohort; vendor failover reroutes wholesale). Atomicity is the deliverable (all-or-nothing family coherence, never transitional mixes).
- **Modern guidance** — inject factories at roots (app bootstrap, test setup — family chosen once per composition). Flag-gate family selection (config picks Light/Dark — rollout/rollback without deploys). Test per family against shared suites (contract tests run each factory's products — behavioral parity across families enforced, leaf 2.1-of-01's matrices wearing factory clothes). Document family membership explicitly (which products constitute a suite — additions reviewed against the suite contract, leaf 3 below prices them).

```bash
# GOOD: migrations as configuration (one seam, atomic coherence)
#  bootstrap: UIFactory = flags.dark ? new DarkFactory() : new LightFactory() (whole suite pivots).
#  tests: contract suite x {Light, Dark, Fake} factories (parity enforced per family).
#  failover: vendor factory swapped at root (policy untouched — leaf 2.2-of-01's dividend, scaled).
# BAD: per-product theme parameters ("granular control") —
# migration = N edits + transitional mixes + per-product mocks (atomicity absent everywhere)
```

### 3) **New products cost across families**

**Definition** — the openly-priced trade: adding a product kind (Scrollbar) to the suite means extending *every* family factory (Light/Dark/Fake scrollbar implementations + interface method — N families × 1 method). Factory Method scales by *kinds* (new product = new subclass, OCP-clean); Abstract Factory scales by *families* (new family = new factory, OCP-clean) — each pattern's cheap axis is the other's expensive one. The trade is structural, not incidental: choose by expected growth direction.

- **Why it hurts when missing (correctness, maintainability)**: product additions to family-factories surprise (three implementations + interface change + all callers compiling against the extended interface — "just add Scrollbar" bills across the codebase; teams discover the trade mid-sprint, estimates blown). Misselected patterns invert the pain permanently (family-factory for kind-growing suites — every product pays N-family tax; factory-method for family-growing suites — every family pays per-kind edits). Naming the trade up front converts surprise into budgeting (product roadmap vs factory count — reviewed together).
- **Modern guidance** — choose Abstract Factory when *families* grow (themes/platforms/vendors multiplying — new factories land cleanly); choose Factory Method when *kinds* grow (products multiplying within stable families — new subclasses land cleanly). Default parameters/adapters cushion product additions (optional members with defaults — families extend without breaking existing implementers; full interface conformance deferred). Revisit on roadmap shifts (kind-growth forecasted on family-factories → migrate to factory-method *before* the third product bills N-family tax).

```typescript
// GOOD: trade stated with the structure (growth direction decides)
// kind-growth (new widgets, stable themes)   -> Factory Method (new subclass per kind, OCP-clean).
// family-growth (new themes, stable widgets) -> Abstract Factory (new factory per family, OCP-clean).
// Scrollbar added to Light/Dark/Fake: 3 impls + interface (priced upfront — no surprise mid-sprint).
// BAD: "we'll add products later, decide then" (deferred to mid-sprint surprise) —
// growth direction forecast at design time; pattern follows forecast, refactoring follows surprise
```

### 4) **Common confusion**

- "Abstract Factory = big Factory Method" — Factory Method defers *one product* via subclassing (kind axis); Abstract Factory composes *suites* via injection (family axis). Different axes, different mechanics (inheritance vs composition), different growth economics.
- "One factory per product is fine" — per-product factories lose suite coherence (mixed families representable — the exact bug Abstract Factory makes unrepresentable). Granularity follows coherence units (suites, not products).
- "Adding products is always expensive" — expensive *across families* (N implementations); cheap *within Factory Method* (one subclass). Cost lives on the non-favored axis — pattern choice prices it upfront.
- "Inject factories everywhere" — inject at *roots* (bootstrap, tests — family chosen once per composition); mid-graph factory-passing is prop-drilling wearing patterns (context/modules carry family decisions, not every function signature).

### 5) **Performance note**

Factories cost one indirection per creation (virtual dispatch — nanoseconds; creation-frequency rarely hot — products built per request/component, not per loop iteration). Family coherence costs interface surface (methods per suite member — files, not runtime). Per-product construction costs full test matrices (contract suites × families — CI minutes, the real price of families). Optimize coherence first (unrepresentable mixes prevent incident classes), suite-test economics second (shared contract suites amortize per family), dispatch overhead never (creations aren't loops).

### 6) **Mentor note**

Demo family coherence live (swap `LightFactory`→`DarkFactory` in one line — "watch the whole UI pivot without touching callers" converts suites from theory to observable). Price product additions explicitly ("add Scrollbar: count the files" — N-family tax computed before committed). Drill axis selection ("kinds growing or families?" — forecast decides pattern, not taste). Watch for the per-product factorer ("granular" factories losing coherence — fix with mixed-family bug demo) and the kind-blind abstractor (family-factory for kind-growth — fix with N-tax arithmetic on their roadmap). Review check: families coherent by construction, swaps one-line, product additions priced upfront, juniors can place new kinds/families unprompted.
