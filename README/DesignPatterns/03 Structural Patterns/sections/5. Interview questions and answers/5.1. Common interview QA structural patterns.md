## 5.1. Common interview QA: structural patterns

### 1) **Decorator vs inheritance vs composition?**

**Definition** — the extension screen: three ways to add behavior (inheritance: subclass overrides — taxonomy-bound, fragile-base risk; composition: hold-and-delegate — flexible, explicit; decorator: wrap-and-stack — order-meaningful runtime layering). Same goal (extended behavior), different economics (subclass: compile-time frozen, exponential combos; composition: explicit wiring per use; decorator: linear wrappers, exponential combos at runtime). Candidates place per need (static few → subclass tolerable; dynamic many → decorator mandatory; behavior reuse without layering → composition).

- **What a good answer sounds like**: economics compared ("4 toggles: 16 subclasses vs 4 wrappers + composition (verified pair pattern) vs composed helpers per use — exponential vs linear vs explicit"), order addressed ("decorator sequence *is* semantics — verified `<b><i>` vs `<i><b>`; inheritance/composition lack ordering questions entirely"), fragility named ("subclass depends on base internals — verified 2→0 shape; decorator depends on interfaces only"). Then the selection close (static-few → subclass tolerable; dynamic-many → decorator; reuse-without-layering → composition).
- **Modern guidance** — interviewers listen for *economics-first* reasoning (combinatorial arithmetic before taste): candidates who count classes-vs-wrappers pass; candidates who prefer by familiarity fail the scaling follow-up ("6th behavior arrives — now what?"). Red flags: "inheritance is bad" absolutism (static-few cases tolerate it fine — dogma, not analysis), "composition solves everything" (layering order needs decorators — composition *wires*, decorators *stack*).

```bash
# The extension answer, structured (leaves 2.1 + Domain 01 §3.1 as interview response)
#  static + few      -> subclass (taxonomy affordable; fragile-base documented).
#  dynamic + many    -> decorator (linear wrappers; order semantics stated; verified pair).
#  reuse w/o layering-> composition (explicit delegation; no ordering questions).
```

### 2) **Proxy vs decorator — same code?**

**Definition** — the intent screen: identical structure (wrapper implementing subject interface, delegating inward), opposite purpose (proxy *controls access* — guarding/deferring/logging; decorator *adds behavior* — layering capabilities). Same code answers "which question?" differently (who may use / when built / what's observed → proxy; what else does it do → decorator). Candidates distinguish by *review routing* (security eyes on proxies, feature eyes on decorators) and *stack order* (guard outermost — denied work never downstream).

- **What a good answer sounds like**: structure acknowledged ("twins — same delegation shape"), intent separated ("control vs extend — verified gate vs verified nesting pair"), order reasoned ("guard-outside-log: denied attempts logged but never downstream — order chosen for auditability"), naming prescribed ("GuardedVault vs BoldText — intent in identifiers, never *Wrapper"). Then the syntax footnote (language `Proxy` traps vs pattern classes — [JS 17 mechanics](<../../../../JavaScript/17 Metaprogramming Symbols Proxy Reflect/README.md>) vs domain control, linked).
- **Modern guidance** — grade *intent-first* analysis (purpose named before mechanics described): candidates who ask "control or behavior?" pass; candidates who describe delegation generically fail the review-routing follow-up ("who reviews this wrapper — security or features?"). Instant fail: "interchangeable" (mechanics shared, reviews opposite — interchangeability collapses under audit).

```bash
# The intent answer, structured (leaf 2.2 as interview response)
#  structure: twins (wrap + delegate + same interface).
#  intent: control (guard/defer/log — verified gate + 0-then-1) vs extend (verified nesting pair).
#  order: guard outermost (auditability decided); names track intent (routed reviews).
```

### 3) **Design a file system API**

**Definition** — the composition screen: files + directories with uniform operations (size/render/search — leaf 3.1's verified 15-shape), transparency-vs-safety decided explicitly (uniform `add()` with loud leaf errors vs safe groups + factory construction), recursion structural (operations as node methods), depth budgeted (iterative twins past risk). Candidates produce the component interface first (`FsNode { size() }` — verified shape), then kinds, then the trade statement.

- **What a good answer sounds like**: interface first ("one component type — files and dirs answer identically"), recursion structural ("size aggregates children — clients never branch on kind"), trade stated ("transparent `add()` throwing loudly on files *or* safe groups with factories — chosen per construction-vs-reading mix, documented"), depth addressed ("iterative twins past depth risk — unbalanced trees threaten stacks"). Then the extension close (new node kinds implement the interface — OCP satisfied structurally).
- **Modern guidance** — listen for *uniformity-first* design (single interface before kinds — the pattern's whole point): candidates who start from `File`/`Dir` classes separately fail the composition screen (uniformity retrofitted, never designed). Red flags: `instanceof` switches in operations ("pragmatic" — the exact branching composite eliminates), silent no-op leaves ("lenient" — dropped children without error, data loss wearing tolerance).

```bash
# The composition answer, structured (leaf 3.1 as interview response)
#  interface first (FsNode.size — uniform treatment) -> kinds (File leaf, Dir aggregate, verified 15)
#  -> trade stated (transparent-loud vs safe-factory) -> depth budgeted (iterative twins past risk).
```

### 4) **Common confusion**

- Candidates who answer structural questions with class diagrams but no trade-offs (shape without economics — uniformity costs, transparency risks, order semantics unmentioned).
- "Adapter/Facade/Decorator/Proxy are all wrappers" (containment shared, jobs distinct — fit/use/extend/control named per wrapper; collapsing loses review routing).
- Treating order-insensitivity as default ("wrapping order rarely matters" — verified markup pair refutes; middleware short-circuiting refutes; filter sequencing refutes).

### 5) **Performance note**

Structural QA answers should be compact: extension economics (two minutes — counts, order, fragility), intent split (90 seconds — structure twins, purpose opposites, order decided), composition design (two minutes — interface, kinds, trade, depth). Candidates who narrate with verified receipts (nesting pair, gate counts, size-15 oracle) take the same time as generalizers and prove triple — structure is speed, in structural interviews as in analysis.

### 6) **Mentor note**

Use Q1 as the extension screen (economics counted, order addressed, fragility named), Q2 as the intent screen (purpose before mechanics, order decided, names tracking), Q3 as the composition screen (interface first, trade stated, depth budgeted). Rubric: junior — correct shapes with examples; mid — trade-offs stated (transparency, order, depth) unprompted; senior — economics quantified (class counts, audit routing, sharing ratios), misuses named (fossil adapters, lock-in facades, silent leaves) without prompting. Keep the verified receipts ready (nesting pair, gate matrix, 15-oracle) — structure narrated with evidence hires. Red-flag fails: wrapper-blur, order-blindness, `instanceof` operations, silent no-ops.
