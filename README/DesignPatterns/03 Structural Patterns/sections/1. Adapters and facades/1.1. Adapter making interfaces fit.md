## 1.1. Adapter: making interfaces fit

### 1) **Translate at the boundary**

**Definition** — Adapter converts one interface into another clients expect (legacy XML database behind a modern JSON port — verified `{"id":"a1"}` from `<r id="a1"/>`): the client codes against the *target* interface (stable, owned), the adapter *wraps* the adaptee (translation isolated in one class). Neither side changes (legacy untouched — too risky/expensive; clients unwritten-to-legacy — too late) — the adapter absorbs the mismatch as its entire job.

- **What problem it solves**: interface mismatches without adapters fork codebases (client logic duplicated per legacy variant — XML parsing scattered across features; or legacy rewritten to match (risk without budget — working systems re-broken for aesthetics). Adapters quarantine incompatibility (one translation class — tested once, reused everywhere; legacy evolves behind the seam without touching clients, clients evolve without touching legacy). Third-party SDKs, versioned APIs, and acquired-company systems all integrate this way.
- **Modern guidance** — wrap at system boundaries (external/legacy/versioned code — adapters face outward, owned interfaces face inward). Translate fully (no leaking adaptee types through the adapter — leakage reintroduces the coupling the pattern removes; return owned shapes only). Prefer object adapters (composition — wrap the instance; swappable, testable) over class adapters (multiple inheritance — unavailable in TS/JS single-inheritance, and brittle where available). Name adapters after the translation (`XmlToJsonStore` beats `Adapter` — direction visible).

```typescript
// GOOD: mismatch quarantined in one class — verified {"id":"a1"}
class XmlAdapter implements JsonStore {
  constructor(private db: LegacyXmlDb) {}       // wraps (composition — swappable, testable)
  get(id: string): { id: string } {
    const m = this.db.fetch(id).match(/id="([^"]+)"/);  // translation isolated HERE, nowhere else
    return { id: m![1] };                        // owned shape out (adaptee types never leak)
  }
}
// clients code against JsonStore (stable, owned); LegacyXmlDb untouched (too risky to rewrite).
// BAD: XML parsing scattered per feature ("just parse inline") —
// N translation sites drifting (regex variants!); legacy change fans out to every caller
```

### 2) **Object adapters over class adapters**

**Definition** — object adapters *hold* the adaptee (composition — `constructor(private db)`; swappable per instance, mockable in tests, no inheritance constraints); class adapters *extend* it (multiple inheritance required — unavailable in TypeScript/JavaScript single-inheritance; brittle where available — base evolution fracturing adapters silently, Domain 01 §3.1's fragile-base shape recurring). GoF lists both; working TypeScript uses object adapters essentially always (language constraints aligning with design preference for once).

- **Why it matters (correctness)**: class-adapter inheritance couples adapters to adaptee *internals* (overridable-method dependence — base refactors break adapters without touching their code; verified-shape risk from Domain 01 §3.1, restated). Object adapters couple only to the adaptee's *public interface* (method signatures — refactorings preserving signatures preserve adapters). Swappability differs structurally (object: different adaptee per instance — test doubles slide in; class: fixed at declaration — testing needs subclasses of subclasses).
- **Modern guidance** — default to object adapters (composition — swappable, mockable, inheritance-free). Inject adaptees via constructors (test doubles implement the adaptee interface — adapter logic tested without legacy systems). Favor function-shaped adapters for simple translations (one-function wrappers where class ceremony exceeds translation complexity — `(id) => parse(db.fetch(id))` beats a class with one method). Reserve class extension for framework-mandated hierarchies (documented hooks only — never for adaptation convenience).

```typescript
// GOOD: composition-based wrapping (swappable per instance, mockable per test)
// constructor(private db: LegacyXmlDb) — test double implements fetch(); adapter logic tests legacy-free.
// function-shaped twin for simple cases: const getJson = (id: string) => parse(db.fetch(id)) (no class needed).
// BAD: extends LegacyXmlDb ("fewer files") —
// base internals coupled (fragile-base shape); adaptee fixed at declaration (untestable in isolation)
```

### 3) **Adapters are temporary by design**

**Definition** — adapters bridge *toward* migration (legacy scheduled for replacement — adapter buys time) or *across* permanent boundaries (third-party SDKs, versioned protocols — no migration possible, only insulation): temporary ones carry removal dates (version N+2 deletes the adapter *and* its adaptee — scheduled, tracked); permanent ones carry ownership (boundary team maintains translation — version drift monitored, never surprising). Undated adapters fossilize workarounds (temporary becoming eternal by neglect — the most common adapter incident).

- **Why it hurts when missing (correctness, maintainability)**: fossilized adapters accumulate translation debt (three adapter layers stacked — XML→JSON→GraphQL→gRPC, each adding latency and failure modes; workarounds nobody remembers the reason for — removal feared, preservation unjustified). Migration stalls where adapters comfort (why replace legacy when it "works through the adapter"? — the question that kills modernization quarters). Dated adapters force the conversation (removal scheduled → migration planned → legacy dies on time).
- **Modern guidance** — date temporary adapters at creation (`TODO(v3): remove with LegacyXmlDb` — tracked in issues, not just comments; comments rot, tickets nag). Monitor permanent boundaries (SDK changelogs subscribed — translation updated proactively; contract tests pinning adaptee behavior — drift detected, not discovered). Never stack adapters without consolidation reviews (two layers = yellow flag; three = mandatory simplification sprint). Retire loudly (removal announced — dependents migrate first, deletion second, never reversed).

```bash
# GOOD: adapters with lifecycles (temporary dated, permanent owned)
#  XmlAdapter: TODO(v3 Q2): remove with LegacyXmlDb retirement (ticket #482, owner named).
#  StripeAdapter: permanent boundary (SDK subscribed, contract tests pin v2026-04 behaviors).
#  stacked count: 1 per boundary (two-layer review triggered automatically).
# BAD: AdapterUtils.ts (2019) still translating a system retired in 2021 ("don't touch it") —
# fossilized workaround; removal feared precisely because understanding evaporated
```

### 4) **Common confusion**

- "Adapter changes the adaptee" — adapters *wrap* without modifying (legacy untouched — the pattern's whole point is change-free integration). Changing the adaptee is refactoring, not adapting.
- "Adapter vs Facade" — Adapter *translates interfaces* (mismatch resolved — different shapes made compatible); Facade *simplifies subsystems* (leaf 1.2 — complexity reduced, shapes unchanged). Translation vs simplification — different problems sharing wrapping syntax.
- "Adapters are just wrappers" — wrappers *contain*; adapters *translate* (interface conversion is the deliverable — pass-through wrappers add nothing and deserve no pattern name). Translation intent separates pattern from plumbing.
- "One adapter per method" — adapters wrap *interfaces* (coherent translation units — whole ports, not functions); per-method functions are translators, not adapters (useful, unnamed — pattern granularity matters for review).

### 5) **Performance note**

Adapters cost one indirection per call (delegation — nanoseconds, JIT-inlined at monomorphic sites) plus translation work (parsing/reshaping — the actual cost, inherent to format difference, not pattern overhead). Stacked adapters multiply translation (XML→JSON→GraphQL per call — latency and failure modes per layer; consolidation reviews exist for this arithmetic). Rewrites cost migrations (quarters); adapters cost nanoseconds (structure). Optimize layer count first (consolidate stacks), translation hot paths second (cache parsed forms where valid), dispatch never (nanoseconds, inlined).

### 6) **Mentor note**

Demo translation live (XML in, JSON out — "legacy untouched, clients unwritten-to-legacy, mismatch absorbed here" converts boundaries from theory to observable). Drill composition-vs-inheritance choice ("which adaptee coupling?" — public-interface-only wins). Demand removal dates on temporary adapters ("when does this die?" — undated answers rejected). Watch for the inline-parser ("just parse here" × N sites — fix with drift arithmetic on their own call count) and the fossil-keeper ("don't touch AdapterUtils" — fix with understanding-recovery sprint, then dated removal). Review check: translation isolated, adaptee types contained, lifecycles dated/owned, juniors can place adapters unprompted.
