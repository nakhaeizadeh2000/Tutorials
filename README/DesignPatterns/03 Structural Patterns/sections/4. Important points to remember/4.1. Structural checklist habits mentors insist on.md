## 4.1. Structural checklist (habits mentors insist on)

### 1) **Wrap for fit, simplify for use**

**Definition** — adapters translate mismatched interfaces (leaf 1.1 — boundary quarantine, legacy untouched); facades simplify subsystem clusters (leaf 1.2 — one-call orchestration, subsystems reachable). Each at its boundary, never both jobs (adapters don't orchestrate multi-object flows; facades don't translate shapes). Misplaced patterns bill wrong (adapter-shaped facades translate nothing — pure indirection; facade-shaped adapters simplify nothing — mismatch persists behind a "simpler" front).

- **What problem it solves**: boundary confusion scatters integration logic (translation inline per caller — leaf 1.1's drift; orchestration per caller — leaf 1.2's ordering bugs; both fixed by naming the job per boundary). The checklist routes by question ("shapes mismatch?" → adapter; "cluster complex?" → facade; both? → adapter *behind* facade, layered honestly). Reviewers check placement, not just presence (right pattern at the wrong boundary fails identically to no pattern).
- **Modern guidance** — name the boundary job per integration (translate/simplify/coordinate — one word deciding the pattern; two jobs → two layers, explicitly stacked). Date temporary adapters (removal scheduled — leaf 1.1's fossil discipline); keep facades thin (delegation + order — god-object drift rejected). Test boundaries directly (translation tables green; orchestration sequences asserted — boundary behavior proven, not hoped).

```bash
# GOOD: jobs named per boundary (placement reviewable)
#  legacy XML -> JsonStore port (translate: adapter, dated v3 removal).
#  decode/filter/encode -> convert(file) (simplify: facade, subsystems reachable).
# BAD: "integration layer" doing both unnamed ("flexible boundary") —
# translation drift + orchestration sprawl in one unreviewable file
```

### 2) **Stack behavior, guard access**

**Definition** — decorators add capabilities (leaf 2.1 — order-meaningful stacking, interface preserved); proxies control interaction (leaf 2.2 — guarding/deferring/logging, same interface). Identical structure distinguished by intent (extend vs control — names track intent: `BoldText` vs `GuardedVault`, never `*Wrapper`). Stacks order deliberately (guard outermost — denied work never downstream; log outside behavior — observations cover full stacks).

- **Why it matters (correctness)**: intent-blind wrapping misroutes review (security logic in feature-named files — skipped by feature reviewers; behavior in guard-named files — audited for threats that don't exist). Order-arbitrary stacks corrupt auditability (logged-denied vs denied-unlogged — order decides evidence; accidental order decides wrong). The checklist converts wrapper review from shape-checking ("it's a wrapper, fine") into intent verification (control or behavior? order justified?).
- **Modern guidance** — name wrappers by intent (control/behavior visible in identifiers — review routed correctly on sight). Order stacks explicitly (guard → log → behavior — denied/outermost documented; deviations justified per stack). Test per intent (proxies: allowed/denied/deferred matrix; decorators: output pairs per meaningful stack — verified shapes from leaves 2.1–2.2 as oracle patterns). Distinguish pattern-decorators from syntax-decorators per conversation (runtime vs annotation — leaf 2.1's vocabulary discipline, restated as routine).

```bash
# GOOD: intent named, order deliberate (review routed on sight)
#  GuardedVault (control: allowed/denied matrix green) outside LoggedVault (observation: audit trail).
#  Bold(Italic(x)) documented outer-first (sequence semantics stated where observable).
# BAD: WrapperManager stacking unnamed layers ("composable") —
# intent undiscoverable (control? behavior?); order accidental (auditability decided by chance)
```

### 3) **Share structure deliberately**

**Definition** — composite uniformity (leaf 3.1 — one interface, recursive ops, transparency decided), bridge independence (leaf 3.2 — M+N over M×N, axes owned separately), flyweight sharing (leaf 3.2 — intrinsic pooled + frozen, extrinsic carried). Each priced before adopted (uniformity vs safety trade stated; axis forecast justifies bridge; redundancy ratio justifies flyweight). Deliberate sharing documents its contract (transparency choice, axis ownership, immutability proof — stated per use, reviewed per change).

- **Why it hurts when missing (correctness, maintainability)**: casual sharing corrupts broadly (mutable flyweights poisoning catalogs — thousands affected per bad write; transparent leaves throwing in untested paths — runtime surprises; coupled hierarchies multiplying per axis member — estimates blown). Each failure traces to undeclared sharing semantics (shared *what*, mutable by *whom*, uniform *where* — unanswered because unasked). Stated contracts convert sharing from risk into structure (bounds known, mutations impossible, uniformity tested).
- **Modern guidance** — declare sharing semantics per structure (uniform? independent axes? pooled + frozen? — three questions, answered in docs). Prove with counts (sharing ratios measured — 8/4 verified shape as template; uniformity tested — same op across leaf/group/nest). Freeze pooled state structurally (`Object.freeze` at registration — sharing + writability never coexist). Re-audit on growth (axis members added? redundancy ratios fallen? — sharing decisions expire with scale and use).

```bash
# GOOD: sharing declared, priced, proven (per structure)
#  composite: uniform + loud leaves (transparency stated, tested).
#  bridge: axes independent, M+N counted (forecast justifies seam).
#  flyweight: pooled + frozen, ratio measured (sharing + immutability evidenced).
# BAD: "shared for efficiency" without semantics (what shared? mutable by whom? uniform where?) —
# efficiency unmeasured, corruption unscheduled, uniformity untested
```

### 4) **Common confusion**

- "Checklists replace structural fluency" — checklists *route* to the right structure with the right contract; fluency implements adapters/decorators/composites. Both, in that order.
- "Small integrations don't need structure" — small integrations need *lighter* versions (function adapters, single facades, documented sharing), not zero: unstructured integration fossilizes as it grows (seams retrofitted under load cost 10×).
- "One wrapper pattern suffices" — adapter/decorator/proxy/facade answer different questions (fit/use/extend/control — collapsing them loses the distinctions reviews depend on). Four names, four jobs.

### 5) **Performance note**

The checklist costs minutes per structural decision (job named, intent stated, sharing declared) against integration incidents (translation drift, ordering bugs, audit gaps, sharing corruption — hours of debugging answers that aren't errors) and taxonomy explosions (exponential classes, multiplicative hierarchies — estimates blown per feature). Highest-leverage item is job-naming per boundary (routes patterns correctly); second is intent-naming per wrapper (routes reviews correctly); third is sharing-declaring per structure (prevents corruption classes). Minutes preventing rewrites — structural's best attention rate.

### 6) **Mentor note**

Convert this leaf into the team's structural runbook: fit→adapter, use→facade, extend→decorator, control→proxy, trees→composite, axes→bridge, massive-sharing→flyweight — routing table memorized. Quiz juniors on placement ("which checklist item fires for theme variants? for lazy heavies? for part-whole trees?") until answers are environmental. Watch for checklist decay (structures placed by familiarity under deadline — fix with job/intent/sharing questions as review-blocking) and wrapper-blur ("it's all wrapping" — fix with four-jobs drill: fit/use/extend/control named per wrapper). Review check: jobs named, intents stated, sharing declared — and the mentor's own structural code modeling all three visibly.
