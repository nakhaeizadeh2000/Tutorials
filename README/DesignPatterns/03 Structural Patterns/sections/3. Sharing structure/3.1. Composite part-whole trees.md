## 3.1. Composite: part-whole trees

### 1) **Uniform treatment of leaves and groups**

**Definition** — Composite lets clients treat individual objects and compositions identically (files and directories both answer `size()` — verified total 15 across nested structure: 10 + (5)): one component interface (`size()`, `render()`, `validate()`), leaves implementing directly, composites aggregating children recursively. Client code never branches on node kind (no `instanceof` switches — operations recurse structurally, uniformity enforced by the type system).

- **What problem it solves**: part-whole hierarchies without uniformity fork every operation (size/render/validate each switching on leaf-vs-group — N operations × 2 branches, new node kinds multiplying branches; recursive structures traversed with type tests — brittle, unextensible). Composite collapses the fork (one interface, recursive implementation — new operations implement per node kind once; new node kinds implement all operations once). Trees (DOM, filesystems, org charts, UI layouts, expression ASTs) all share the shape.
- **Modern guidance** — reach for Composite on recursive part-whole structures (trees with uniform operations — size/render/search/validate across leaves and groups). Define the component interface minimally (operations meaningful for *both* — leaf methods that make no sense on groups signal the transparency/safety trade, next section). Recurse structurally (composites delegate to children — clients see one interface, trees handle themselves). Test uniformity explicitly (same operation on leaf, group, and nested mix — verified 15 pattern as oracle shape).

```typescript
// GOOD: one interface, recursive aggregation — verified 15 across nesting
interface FsNode { size(): number; }
class FsFile implements FsNode { constructor(private n: number) {} size(): number { return this.n; } }
class FsDir implements FsNode {
  private kids: FsNode[] = [];
  add(n: FsNode): void { this.kids.push(n); }
  size(): number { return this.kids.reduce((s, k) => s + k.size(), 0); }  // recursion does the work
} // dir(10 + dir(5)) -> 15 verified (clients never branch on kind).
// BAD: sizeFile()/sizeDir() pairs with instanceof switches per operation ("explicit") —
// N operations x 2 branches (new kinds multiply); uniformity unenforced, extensibility manual
```

### 2) **Recursion does the work**

**Definition** — composite operations recurse by construction (each composite delegates to children — depth handled by call stack, breadth by iteration; clients invoke the root once). Correctness follows structurally (induction over trees: leaves correct by definition, composites correct if children are — the proof mirrors the code). Depth risk follows equally (unbalanced trees recurse thousands deep — Domain 01-of-Algo... recursion depth priced per [AlgorithmDesign 01 §2.2](<../../../AlgorithmDesign/01 Complexity and Algorithmic Thinking/sections/2. Analyzing algorithms/2.2. Space analysis and the time-memory trade.md>), linked never re-derived: ~14k frames ceiling).

- **Why it matters (correctness)**: manual tree-walking without composite recursion reimplements traversal per operation (stacks managed by hand — push/pop discipline bugs; visited tracking duplicated — state leaks across walks; depth limits rediscovered — each operation its own ceiling incident). Structural recursion centralizes traversal (one mechanism — the composite itself; operations plug in as methods). Depth handled once (iterative twins where trees run deep — [AlgorithmDesign 04 §2.2's spine pattern](<../../../AlgorithmDesign/04 Hashing Trees and Heaps/sections/2. Trees/2.2. Traversals inorder pre post and level.md>), linked).
- **Modern guidance** — implement operations as methods on node kinds (recursion structural — no external walkers for standard ops). Externalize visitors where operations multiply independently (Visitor pattern — Domain 05: operations as objects visiting stable structures; composites stay closed, visitors extend). Bound depth explicitly (iterative twins past depth risk — spine-managed traversal where trees run deep). Name recursion in reviews ("structural" — the word distinguishing composite traversal from manual walking).

```typescript
// GOOD: traversal structural (operations plug into node kinds)
// size/render/validate as methods (each kind implements once); Visitor objects for independent operation sets (Domain 05).
// depth: iterative twins where trees run deep (spine pattern — AlgorithmDesign 04 §2.2, linked).
// BAD: external tree-walkers per operation ("flexible") —
// traversal reimplemented N times (stack bugs × N); depth rediscovered per walker (ceilings hit serially)
```

### 3) **Transparency vs safety trade**

**Definition** — the composite dilemma: *transparent* composites expose child management on the component interface (`add()` on `FsNode` — uniform treatment complete, but leaves inherit meaningless `add` — FsFile.add throws or no-ops, the safety hole); *safe* composites restrict `add()` to group types (leaves clean — but clients downcast to compose, uniformity broken at construction). Transparency favors clients (no kind-checks ever); safety favors leaves (no meaningless operations). No universally-right answer — the trade is per-use-case, stated explicitly.

- **Why it hurts when missing (correctness, maintainability)**: undeclared tradeoffs surprise both directions (transparent leaves throwing at runtime — `file.add()` exploding in production paths nobody tested; safe composites forcing client downcasts — `as Dir` sprinkled per construction site, type-safety theater). Explicit choice converts surprises into contracts (transparent + documented leaf behavior — throws `Error("leaves have no children")` loudly; or safe + builder helpers — construction without downcasts via factory functions). halfway designs (sometimes-uniform interfaces) deliver neither benefit.
- **Modern guidance** — choose transparent for read-mostly trees (rendering, sizing, searching — uniform reads dominate; leaf `add()` throwing documented and tested). Choose safe for construction-heavy trees (builders/editors — downcasts contained in factory functions, clients never see them). Document the choice at the interface (`FsNode.add` throws on leaves vs absent — stated, tested, reviewed). Prefer safe + builders in TypeScript (type system enforces at compile — downcasts visible in factories only, never client code).

```typescript
// GOOD: trade stated, enforced (transparent + loud leaves here)
// interface FsNode { size(): number; add(n: FsNode): void; }  // transparent: uniform treatment
// class FsFile { add(): never { throw new Error("leaves have no children"); } }  // loud, tested, documented.
// safe twin: add() only on FsDir + makeDir() factories (clients never downcast — construction contained).
// BAD: add() silently no-op on leaves ("lenient") —
// construction bugs vanish (children dropped without error); leniency billing as data loss
```

### 4) **Common confusion**

- "Composite means tree classes" — Composite means *uniform part-whole treatment* (one interface, recursive operations — trees are the common shape, not the definition; nested menus, org units, expression nodes all qualify with different branching).
- "Leaves should support all operations" — leaves support *meaningful* operations (transparency-vs-safety decides child-management — stated per interface; uniformity where sensible, loud errors or absence where not).
- "Composite replaces Visitor" — Composite structures *data* uniformly; Visitor adds *operations* without modifying structures (complementary — composites closed for operations they own, visitors extend operation sets; Domain 05 owns the pairing).
- "Recursion depth is free" — depth bills stack frames per level (linked ceiling — unbalanced trees threaten; iterative twins exist precisely here). Structural recursion still needs depth budgeting.

### 5) **Performance note**

Composites cost one dispatch per node per operation (nanoseconds — `n` nodes visited once each, optimal for whole-tree operations); transparency costs nothing extra (same dispatch, wider interface); safety costs downcasts at construction (compile-time with factories — zero runtime). Manual multi-branch alternatives cost per-operation type tests (branch prediction + code size per kind — worse constants, worse extensibility). Optimize uniformity first (single recursion replaces N switches), depth-safety second (iterative twins past risk), dispatch overhead never (nanoseconds, inlined).

### 6) **Mentor note**

Demo uniformity live (verified 15 from mixed nesting — "no instanceof anywhere in the sizing code" converts uniformity from claim to observable). Force the transparency choice explicitly ("what does `file.add()` do?" — loud-throw vs absent-interface decided per codebase, never defaulted). Contrast manual switches (two operations × two kinds = four branches, growing) with structural recursion (one method per kind, fixed). Watch for the switch-writer ("explicit" instanceof chains — fix with uniformity arithmetic on their operation count) and the silent-no-op adder ("lenient" leaves — fix with dropped-children data-loss autopsy). Review check: single component interface, recursion structural, transparency choice stated + tested, juniors can extend with new node kinds unprompted.
