## 3.2. Bridge and Flyweight: decouple and share

### 1) **Bridge splits abstraction from implementation**

**Definition** — Bridge separates an abstraction hierarchy (shapes: Circle/Square) from its implementation hierarchy (renderers: Vector/Raster) with a composed seam — each varies independently (new shape × existing renderers work immediately; new renderer serves all shapes at once). Verified: `Circle(Vector)` → `vec(5)`, `Circle(Raster)` → `rast(5)` (same abstraction, swapped implementation, one constructor argument). `M×N` combinations collapse to `M+N` classes (the arithmetic that justifies the indirection).

- **What problem it solves**: coupled hierarchies multiply (CircleVector/CircleRaster/SquareVector/SquareRaster — 2×2 today, 5×4 tomorrow = 20 classes; each new shape *or* renderer multiplies the other axis). Bridged hierarchies add (new shape: 1 class + existing renderers; new renderer: 1 class serving all shapes). The seam converts multiplicative growth into additive — verified-swappable at runtime (renderer chosen per instance, per config, per test double).
- **Modern guidance** — reach for Bridge on two independent variation axes (abstraction × implementation: shapes×renderers, views×platforms, reports×formats — axes varying for different reasons, owned by different teams). Compose across the seam (abstraction holds implementor reference — constructor-injected, Domain 01 §2.2's explicitness). Name both hierarchies honestly (Renderer/Platform/Driver suffixes — implementation side visible, never hidden behind generic "helpers"). Test cross-products representatively (each shape × each renderer once — matrix coverage, not exhaustive pairs).

```typescript
// GOOD: M+N classes, M×N combinations — verified vec(5)/rast(5) from one Circle
interface Renderer { drawCircle(r: number): string; }  // implementation hierarchy (Vector/Raster)
class Circle {
  constructor(private renderer: Renderer, private r: number) {}  // seam: composed, injected
  draw(): string { return this.renderer.drawCircle(this.r); }    // abstraction delegates across
}
// 3 shapes x 4 renderers: 7 classes (bridged) vs 12 (coupled) — arithmetic decides, taste doesn't.
// BAD: CircleVector/CircleRaster/... per-combo classes ("explicit") —
// multiplicative growth (new axis member multiplies the other); runtime swapping impossible (baked at compile)
```

### 2) **Flyweight shares intrinsic state**

**Definition** — Flyweight splits object state into *intrinsic* (shared: glyph shape+font — identical across uses) and *extrinsic* (carried by context: positions, selections — passed per operation): a factory pools intrinsics (verified: 8 characters → **4** shared glyphs, `same-a: true` — a's identity shared across positions). Memory collapses with redundancy (text rendering, game entities, particle systems — thousands of instances sharing dozens of states).

- **Why it matters (correctness)**: unshared repetition bills memory linearly with instances (million-character documents × glyph objects — gigabytes where megabytes suffice; game entities per duplicate stats — heap pressure triggering GC pauses at frame budget). Sharing converts instance-count memory into state-count memory (4 glyphs for 8 chars — verified; million chars over 100 shapes → 100 objects). Extrinsic discipline is the price (positions *must* travel with calls — shared state never holds per-use data, or uses corrupt each other).
- **Modern guidance** — reach for Flyweight on massive instance counts over small state spaces (glyphs, tiles, particles, cell styles — sharing ratio 100×+ justifies the pattern). Split intrinsic/extrinsic rigorously (shared: immutable shape data; carried: positions/selections/context — per-call parameters, never pooled fields). Pool behind factories (verified `GlyphFactory.get` — canonical instances per key; unknown keys construct, known return shared). Freeze intrinsics (`Object.freeze` on pooled objects — shared mutation is shared corruption, prevented structurally).

```typescript
// GOOD: sharing by structure — verified 8 chars / 4 glyphs (redundancy compressed 2x; scales to 1000x)
class GlyphFactory {
  private pool = new Map<string, Glyph>();       // canonical instance per intrinsic key
  get(ch: string, font: string): Glyph {
    const k = ch + "|" + font;
    if (!this.pool.has(k)) this.pool.set(k, new Glyph(ch, font));
    return this.pool.get(k)!;                    // shared identity verified (same-a: true)
  }
}
// extrinsic positions travel per call (draw(glyph, x, y) — never stored in Glyph).
// BAD: per-character full objects ("simpler model") —
// memory linear in instances (millions x object overhead); GC pauses at interaction budgets
```

### 3) **Sharing demands immutability**

**Definition** — shared state mutated is shared corruption (one client's glyph mutation re-renders every document using it — aliasing at catalog scale; flyweight pools without freezing are global-mutable registries wearing pattern clothes). Immutability makes sharing safe structurally (frozen intrinsics — writes impossible, reads race-free; extrinsic carried per call — no shared fields to race on). Verified-shape reasoning from leaf 3.2-of-02 (spread-aliasing leak demonstrated) applies at pool scale: aliasing bugs multiply by sharing ratio.

- **Why it hurts when missing (correctness, maintainability)**: mutable-flyweight incidents corrupt *broadly* (one bad write poisons all sharers — thousands of documents/particles/entities simultaneously; symptoms appear everywhere, cause sits in one pool entry; debugging misattributes per-instance because sharing is invisible at use sites). Concurrency multiplies it (shared mutation across workers — races without locks, torn reads without atomics). Immutability converts the class from incidents to impossibilities (unwritable shared state can't corrupt — enforced by `freeze`, not discipline).
- **Modern guidance** — freeze pooled intrinsics at registration (`Object.freeze` in factory `get`-miss path — sharing + writability never coexist). Carry extrinsic per call (positions/contexts as parameters — never pooled fields; the discipline that keeps sharing safe). Audit sharing ratios periodically (instances-per-intrinsic — falling ratios erode the pattern's value; below ~10×, plain instances win on clarity). Document sharing explicitly (pooled/flyweight in type names or docs — callers must know identity is shared to avoid mutation assumptions).

```typescript
// GOOD: sharing + immutability (corruption structurally impossible)
// factory miss path: const g = Object.freeze(new Glyph(ch, font)); pool.set(k, g); (frozen at birth).
// extrinsic: draw(glyph, x, y) — positions per call (shared fields never hold per-use data).
// BAD: mutable pooled glyphs with "don't mutate" docs ("trusted callers") —
// one mutation poisons all sharers (thousands); docs don't enforce; freeze does
```

### 4) **Common confusion**

- "Bridge is just composition" — Bridge *is* composition applied to *two hierarchies varying independently* (axes × axes — the M+N arithmetic). Composition is the mechanism; independent variation is the pattern's reason.
- "Flyweight is just caching" — caching *avoids recomputation* (memoization — [AlgorithmDesign 01 §2.1](<../../../AlgorithmDesign/01 Complexity and Algorithmic Thinking/sections/2. Analyzing algorithms/2.1. Time analysis loops recurrence and amortization.md>) — time saved); flyweight *shares representation* (memory saved — same object identity across uses). Time vs space — different resources, different patterns.
- "Adapter and Bridge are the same" — Adapter *retrofits* mismatched interfaces (after-the-fact translation — leaf 1.1); Bridge *designs* separated axes upfront (independent variation planned). Retrofit vs planned separation — timing and intent differ.
- "Sharing always wins" — sharing wins where redundancy is high (verified 2× at toy scale, 100×+ at production scale); indirection + pool management cost where instances are unique (sharing ratio ~1:1 — pattern overhead without payoff). Redundancy decides.

### 5) **Performance note**

Bridge costs one delegation hop per call (nanoseconds — implementor dispatch, JIT-inlined at stable seams) plus hierarchy surface (M+N files — tooling handles granularity). Flyweight saves instance-count memory (verified 8→4; production 1000×+ ratios — megabytes reclaimed) at pool-lookup cost per acquisition (hash + Map get — nanoseconds, dwarfed by construction avoided). Coupled hierarchies cost multiplicative classes (human pipeline — estimates doubling per axis member). Optimize redundancy capture first (sharing ratio decides adoption), seam stability second (implementor swaps without abstraction edits), hop overhead never (nanoseconds, inlined).

### 6) **Mentor note**

Demo axis independence live (swap Vector→Raster in one constructor arg — "same Circle, different universe" converts M+N arithmetic from claim to observable). Count sharing live (8 chars → 4 glyphs verified — "where did four objects go?" teaches compression structurally). Demand immutability proof on pooled state ("show me the freeze" — sharing without freezing rejected). Watch for the hierarchy-coupler ("explicit per-combo classes" — fix with multiplicative arithmetic on their roadmap) and the mutable-sharer ("trusted callers" — fix with one-poison-many autopsy). Review check: axes independent (M+N, not M×N), sharing measured (ratio justifies pattern), pooled state frozen, juniors can split intrinsic/extrinsic unprompted.
