## 2.1. Decorator: stacking behavior

### 1) **Wrap to extend, order matters**

**Definition** — Decorator wraps objects in behavior-adding layers sharing one interface (Bold/Italic around Plain — each wrapper holds a `Markup`, adds its tags, delegates inward): composition sequence *is* semantics (verified `<b><i>hi</i></b>` vs `<i><b>hi</b></i>` — different nesting, different output, same pieces). Extension without subclasses (behaviors combine multiplicatively — 3 wrappers × N bases = all combinations, zero new classes per combo) and without touching wrapped code (closed core, open stacking — Domain 01 §1.2 wearing GoF clothes).

- **What problem it solves**: behavior multiplication without decorators explodes subclasses (Bold × Italic × Underline × Strikethrough = 16 classes for 4 independent toggles — exponential taxonomy; each new behavior doubles the hierarchy). Decorators linearize (4 wrappers + composition — combinations emerge at runtime, classes stay flat). Subclass-per-combo also freezes combinations at compile time (runtime toggling needs rebuilding); wrappers compose per instance, per request, per user preference — dynamically.
- **Modern guidance** — reach for Decorator on independent stackable behaviors (formatting, middleware pipelines, stream filters — order-meaningful layering). Preserve interface transparency (wrappers implement the wrapped type — interchangeable everywhere the base flows; type-visible wrapping breaks substitutability, leaf 2.1-of-01). Document order semantics (outer-vs-inner meaning per stack — Bold(Italic(x)) reads "bold of italic" — composition order documented where it changes output). Unwrap deliberately (decoration is one-way by default — `getInner()` escape hatches where teardown matters).

```typescript
// GOOD: behaviors stack, order speaks — verified pair differs by nesting
class Bold implements Markup { constructor(private t: Markup) {} render(): string { return `<b>${this.t.render()}</b>`; } }
class Italic implements Markup { constructor(private t: Markup) {} render(): string { return `<i>${this.t.render()}</i>`; } }
// new Bold(new Italic(new Plain())).render() -> <b><i>hi</i></b> verified (bold OUTSIDE italic).
// new Italic(new Bold(new Plain())).render() -> <i><b>hi</b></i> verified (sequence IS semantics).
// BAD: BoldItalicUnderlineStrike class ("explicit") —
// 16 classes for 4 toggles (exponential taxonomy); runtime combos need rebuilding (frozen at compile)
```

### 2) **Decorator pattern vs decorator syntax**

**Definition** — related words, different mechanics: the *Decorator pattern* wraps objects at runtime (composition layers — this leaf: behavior stacking through delegation); TypeScript *decorator syntax* (`@Component`, `@observable` — annotations triggering compile/design-time transformations) decorates *declarations*, not objects ([TS 14 owns the syntax](<../../../../TypeScript/14 Decorators and Metadata/README.md>) — linked, never re-taught: `experimentalDecorators` vs standard, metadata emission, DI-with-decorators mechanics live there). Confusing them merges runtime composition with static annotation (different axes sharing a name — the interview trap this section defuses).

- **Why it matters (correctness)**: syntax-applied where pattern-needed fails structurally (`@bold` on a class bakes one combination at declaration — runtime toggling impossible; per-instance variation needs per-instance wrappers, not class annotations). Pattern-applied where syntax-needed over-engineers (wrapper classes for declarative metadata — composition machinery where annotations suffice). Teams mixing the vocabularies review past each other ("just decorate it" meaning opposite implementations). Naming which decorator (pattern with wrappers vs syntax with `@`) ends the confusion per conversation.
- **Modern guidance** — use the pattern for runtime behavior composition (per-instance/per-request layering — order-meaningful stacking); use the syntax for declarative metadata (annotations consumed by frameworks/compilers — routing, validation, observability markers). Never implement pattern-decorators via decorator-syntax (annotation-driven wrapping obscures composition order — the sequence semantics from previous section need visible construction). Cross-link deliberately (TS 14's DI-with-decorators *uses* pattern thinking underneath — syntax enabling composition, documented in both places, duplicated in neither).

```typescript
// GOOD: words disambiguated per use (pattern vs syntax, stated)
// runtime layering (user toggles bold/italic live) -> PATTERN: new Bold(new Italic(base)) (visible order).
// declarative metadata (@Component({...}), @observable) -> SYNTAX: TS 14 mechanics (annotations, metadata).
// BAD: "@bold class ..." for runtime toggling ("decorator either way") —
// declaration-baked combination (runtime variation impossible); vocabulary collision shipping wrong mechanics
```

### 3) **Subclass explosion alternative**

**Definition** — the arithmetic that justifies decorators: N independent binary behaviors need 2^N subclasses (4 toggles → 16 classes; 6 → 64 — exponential taxonomy) vs N wrappers + composition (4 wrappers serve all 16 combos; 6 serve 64 — linear classes, exponential combinations). Each new behavior adds *one* wrapper (not doubling the hierarchy — marginal cost constant). Subclassing survives only where combinations are few and static (2–3 fixed variants — taxonomy affordable, composition ceremony wasteful).

- **Why it hurts when missing (correctness, maintainability)**: subclass explosions rot through combinatorial maintenance (16 classes sharing 90% logic via fragile deep hierarchies — Domain 01 §3.1's fragile-base shape at scale; new behavior doubles the tree — estimates blown per feature; testing multiplies per class — suites grow exponentially with behaviors). Decorator flattening converts exponential classes into linear wrappers (each independently tested — combination coverage via composition tests, not class-per-combo suites).
- **Modern guidance** — count combinations before choosing (2^N classes vs N wrappers — arithmetic decides, taste doesn't; threshold ~3 independent behaviors favoring wrappers). Keep wrappers single-behavior (one addition each — Bold adds boldness, nothing else; multi-duty wrappers recreate taxonomy inside). Test wrappers singly + key compositions (unit per wrapper, integration per meaningful stack — not per combination; combinatorial suites are the disease decorators cure). Migrate subclass trees to wrappers incrementally (extract deepest branches first — strangler pattern wearing decorator clothes).

```bash
# GOOD: arithmetic decides (exponential classes vs linear wrappers)
#  4 toggles: 16 subclasses vs 4 wrappers (all combos via composition — verified pair pattern).
#  new behavior: +1 wrapper (constant marginal) vs x2 classes (exponential marginal).
#  threshold: ~3 independent behaviors (below: subclasses tolerable; above: wrappers mandatory).
# BAD: "a few subclasses never hurt" at 5 behaviors ("manageable") —
# 32 classes (manageable until the 6th behavior doubles to 64 mid-quarter)
```

### 4) **Common confusion**

- "Decorator changes the interface" — decorators *preserve* it (transparency — wrapped flows everywhere base flows; changed interfaces are Adapters, leaf 1.1). Preservation is definitional; breaking it silently is the classic decorator bug.
- "Order never matters for independent behaviors" — order matters wherever nesting is observable (verified markup pair; middleware short-circuiting; filter sequencing). Independence of *code* doesn't imply commutativity of *effects*.
- "TypeScript decorators implement the pattern" — syntax annotates declarations (static); pattern wraps objects (runtime). Overlapping vocabulary, disjoint mechanics (section 2 exists because teams confuse them weekly).
- "More wrappers always better" — wrappers add indirection per layer (deep stacks complicate debugging — 12-layer traces; order reasoning burdens reviewers). Stack depth budgeted (meaningful layers only — ceremony wrappers rejected).

### 5) **Performance note**

Decorators cost one delegation hop per layer per call (nanoseconds each — 5-layer stacks still sub-microsecond; JIT inlines monomorphic chains routinely) plus wrapper allocations per composition (short-lived — GC-nursery cheap). Subclass explosions cost hierarchy maintenance (human pipeline — estimates doubling per behavior) and test matrices (suites per class — CI minutes per behavior). Optimize taxonomy size first (linear wrappers over exponential classes), delegation depth second (meaningful layers only), hop overhead never (nanoseconds, inlined).

### 6) **Mentor note**

Demo order-dependence live (verified pair side by side — "same pieces, different nesting, different output" converts sequence-semantics from claim to observable). Disambiguate vocabulary explicitly ("pattern or syntax?" per decorator conversation — miscommunication caught in one question). Count combinations aloud ("4 toggles → ?" until 16-vs-4 is reflexive). Watch for the subclass-accumulator ("a few more won't hurt" × 30 classes — fix with exponential arithmetic on their roadmap) and the syntax-confuser ("@whatever for runtime" — fix with declaration-vs-object distinction demoed). Review check: wrappers single-behavior, order documented where observable, subclasses counted against wrappers, juniors can place new behaviors unprompted.
