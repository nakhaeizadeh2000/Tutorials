## 2.2. Proxy: standing in

### 1) **Same interface, controlled access**

**Definition** — Proxy implements the subject's interface while *controlling* the interaction (guarding, deferring, logging, remoting — identical signatures, supervised behavior): protection proxies gate by authorization (verified `secret` vs `denied` on one boolean), virtual proxies defer construction (verified 0 constructions before use, 1 after two uses), remote proxies marshal across boundaries, logging proxies observe without altering. Clients can't distinguish proxy from subject (transparency — same interface, substitutable per Domain 01 §2.1) except through the controlled dimension (auth required, laziness visible in timing, logs emitted).

- **What problem it solves**: cross-cutting access concerns without proxies scatter through business logic (auth checks per method — forgotten somewhere, bypassed elsewhere; lazy-init flags per call site — double-checked locking hand-rolled repeatedly; remote marshaling inline — protocol details in domain code). Proxies centralize each concern in one interchangeable layer (guard once, defer once, log once — business logic never names the concern). Separation survives evolution (add caching proxy without touching subjects *or* clients — stackable with Decorator, leaf 2.1's composition).
- **Modern guidance** — reach for Proxy on access-shaped problems (authorization gates, lazy heavies, remote stand-ins, audit trails — control, not behavior). Preserve interface exactly (proxy IS-A subject type-wise — substitutability tested via contract suites; divergent signatures are Adapters, leaf 1.1). Compose proxies with decorators freely (guarding wrapper outside logging wrapper — control + observation stacking; order documented where observable). Prefer language `Proxy` traps for cross-cutting universals (validation/logging metaprogramming — [JavaScript 17 owns the mechanics](<../../../../JavaScript/17 Metaprogramming Symbols Proxy Reflect/README.md>), linked; hand-rolled classes where logic is domain-specific).

```typescript
// GOOD: control centralized, interface preserved — verified gate + laziness
class GuardedVault implements Vault {
  constructor(private v: Vault, private authed: boolean) {}
  read(): string {
    if (!this.authed) throw new Error("denied");  // gate: authorization in ONE place
    return this.v.read();
  }
} // authed -> "secret" verified; unauthed -> "denied" verified (same interface, controlled access).
// BAD: auth checks scattered per method ("explicit") —
// forgotten somewhere (bypass), duplicated everywhere (drift), untestable in isolation (no seam)
```

### 2) **Lazy loads on first use**

**Definition** — virtual proxies defer expensive construction until first access (verified: 0 constructions before use, exactly 1 after two uses — cost paid once, on demand, never upfront): startup stays fast (heavy reports/databases/connections unbuilt until needed), unused paths cost zero (constructed-never for unvisited features — pure savings), thread-safety handled once (double-checked or eager-where-racy — the pattern's only sharp edge, documented in leaf 5.1's QA). Laziness is *deferred payment*, not avoided payment (first use bills full price — latency spikes belong in budgets).

- **Why it matters (correctness)**: eager heavies tax every startup (10s init for features 1% of sessions touch — cold starts billed to all users for some users' needs; test suites constructing production heavies — slow suites run less often, coverage decays). Lazy proxies convert fixed costs to variable (pay-per-use — unused paths free; used paths billed once). First-use latency needs budgeting (spike documented — loading states, timeouts adjusted; surprise spikes are incidents wearing optimization).
- **Modern guidance** — proxy per heavyweight-behind-interface (reports, connections, models — construction deferred uniformly). Count constructions in tests (exactly-once assertion — verified pattern: 0 before, 1 after N uses; double-construction fails loudly). Document first-use latency (loading UX + timeout budgets account the spike — no surprise). Prefer eager where racy-and-cheap (async interleaving defeats check-then-set — mutex or eager init; laziness needs atomicity analysis, Domain 01 §4.1's review item).

```typescript
// GOOD: cost deferred to demand — verified 0-then-1 constructions
class LazyReport {
  private real: HeavyReport | undefined;
  data(): string {
    if (!this.real) this.real = new HeavyReport();  // once, on demand (count asserted in tests)
    return this.real.data();
  }
} // before use: 0 verified; after 2 uses: 1 verified (paid once, never upfront).
// BAD: eager HeavyReport in constructors app-wide ("simpler lifecycle") —
// startup taxed per heavyweight (10s cold starts); unused features billing all sessions
```

### 3) **Proxy vs decorator split**

**Definition** — identical structure (wrapper implementing subject interface, delegating inward), opposite intent: Proxy *controls access* to the subject (guarding/deferring/logging — subject unchanged, interaction supervised); Decorator *adds behavior* (new capabilities layered — subject extended functionally). Same code shape answers "which question?" differently (who may use / when built / what's observed → Proxy; what else does it do → Decorator). Misclassified wrappers still *work* (structure runs either way) but mislead reviewers (intent undocumented — control logic audited as feature code, or vice versa).

- **Why it hurts when missing (correctness, maintainability)**: intent-blind wrapping misplaces logic (auth checks inside "decorators" — security review skips feature-named files; logging inside "proxies" nobody audits for completeness — observability gaps where control was assumed). Combined stacks order wrong (guard-outside-log vs log-outside-guard — denied attempts logged or not? — order decides auditability; intent unnamed → order arbitrary). Naming the pattern per wrapper (Proxy-for-control, Decorator-for-behavior) routes review attention correctly (security eyes on proxies, feature eyes on decorators).
- **Modern guidance** — name wrappers by intent (`GuardedVault`, `LazyReport` — control visible; `BoldText`, `RetryableFetcher` — behavior visible; never `*Wrapper`/`*Proxy`-as-decoration). Order stacks deliberately (guard outermost — denied work never logs/retries downstream; log outside behavior-additions — observations cover full stacks). Test per intent (proxies: access matrix — allowed/denied/deferred counts; decorators: behavior outputs per stack — verified pairs from leaf 2.1). Reclassify on drift (behavior-adding "proxy" renamed decorator — names track intent, refactors rename).

```bash
# GOOD: intent named, order deliberate (review routed correctly)
#  GuardedVault (Proxy: control — security review) outside LoggedVault (Decorator: observation).
#  denied attempts: guarded (no downstream) + logged (audit trail) — order chosen, both properties hold.
# BAD: AccessWrapper / LoggingProxy / DecoratorService ("wrappers") —
# intent unnamed (control? behavior?); review attention misrouted; stack order accidental
```

### 4) **Common confusion**

- "Proxy and Decorator are interchangeable" — structurally twins, intentionally opposite (control vs extend — same code answering different questions). Interchangeable mechanics, non-interchangeable reviews.
- "Language `Proxy` replaces the pattern" — traps implement *universal* interception (validation/logging metaprogramming — [JS 17 mechanics](<../../../../JavaScript/17 Metaprogramming Symbols Proxy Reflect/README.md>)); hand-rolled proxies implement *domain* control (auth rules, lazy policies — logic traps can't express). Different layers sharing a name.
- "Lazy always wins" — lazy wins *unused-path* savings; eager wins racy/cheap cases (async interleaving defeats check-then-set — verified-shape risk from concurrent first-uses). Deferral needs atomicity analysis, not default.
- "Protection proxies replace auth middleware" — proxies gate *object access* (in-process boundaries); middleware gates *request pipelines* ([Domain 06/2.1](<../../../06 Modern Patterns and Anti-Patterns/sections/2. Pipelines and events/2.1. Middleware pipelines.md>) — transport boundaries). Complementary layers, different perimeters.

### 5) **Performance note**

Proxies cost one delegation hop per call (nanoseconds — inlined at monomorphic sites) plus concern work (auth checks, lazy construction once, log writes — the actual cost, inherent to the concern). Lazy saves unused-path construction entirely (verified 0 — pure savings where paths go untraveled). Eager alternatives cost startup latency (heavies per launch) and test time (production construction in suites). Optimize concern placement first (one layer vs scattered checks — review/incident economics), hop overhead never (nanoseconds, inlined).

### 6) **Mentor note**

Contrast control-vs-extend live (GuardedVault vs BoldText side by side — "same structure, which question does each answer?" converts intent from vocabulary to observable). Count lazy constructions in tests (0-before/1-after assertion — laziness proven, not hoped). Drill stack ordering ("guard outside log — why?" — denied-work auditability decided explicitly). Watch for the intent-blind wrapper ("*Wrapper/*Manager" names — fix with control-vs-behavior question per wrapper) and the scattered-guarder ("explicit checks" per method — fix with bypass autopsy: find the forgotten one). Review check: wrappers intent-named, proxies gate-tested (allowed/denied/deferred matrix), lazy counts asserted, juniors can split control from behavior unprompted.
