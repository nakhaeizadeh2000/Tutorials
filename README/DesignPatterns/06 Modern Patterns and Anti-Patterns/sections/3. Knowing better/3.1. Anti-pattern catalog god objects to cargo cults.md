## 3.1. Anti-pattern catalog: god objects to cargo cults

### 1) **God objects, anemic models, shotgun surgery**

**Definition** — the structural trio (each with a diagnostic): *god objects* (multi-reason classes — Domain 01 §1.1's invoices: blast radius per edit, conflicts per sprint — diagnosed by reason-count > 1); *anemic models* (data without behavior — getters/setters only, logic in "services" manipulating naked state — encapsulation inverted: procedures over records, OO syntax without OO design); *shotgun surgery* (one change fans across N files — missing seams forcing coordinated edits; the inverse of god objects with identical cost — scattering vs concentration, both billed per change).

- **What problem it solves**: unnamed smells persist (teams feel pain without vocabulary — "this code is hard to change" without naming *which* structure causes it; reviews approve incrementally-worse code — no shared terms to object with). Named catalog entries convert feelings into findings ("god object: 4 reasons, split by stakeholder" — actionable; "anemic: logic in OrderService, data in Order" — relocatable; "shotgun: tax change touches 6 files" — seam-missing, fixable). Vocabulary *is* the code-review tooling for design (precise names beat vague discomfort).
- **Modern guidance** — name smells in review comments (catalog terms, not essays — "god object (auth+billing+notify)" routes to leaf 1.1-of-01; "anemic (logic in service)" routes to behavior-relocation; "shotgun (6-file tax change)" routes to seam insertion). Fix incrementally (extract one reason per PR — strangler pattern over big-bang rewrites; behavior relocated method-by-method with tests green throughout). Track smell density (god-file count, anemic-ratio, shotgun-change frequency — trending metrics, not one-time audits).

```typescript
// GOOD: smells named, fixes routed (catalog as review vocabulary)
// god object (UserManager: auth+billing+notify) -> extract per reason (Domain 01 §1.1; Facade over pieces).
// anemic Order {data} + OrderService {logic} -> relocate behavior into Order (methods own their data).
// shotgun tax change (6 files) -> insert seam (strategy/registry — one edit point created).
// BAD: "this is messy, rewrite someday" (unnamed, unrouted, unscheduled) —
// feelings without vocabulary never convert to findings; findings never convert to fixes
```

### 2) **Golden hammers and cargo cults**

**Definition** — *golden hammer* (one favored pattern/tool applied everywhere — microservices for a blog, event sourcing for CRUD, Kubernetes for static sites — familiarity masquerading as judgment); *cargo cult* (ceremony without cause — daily standups reporting to no one, story points estimated but unused, design patterns implemented "for completeness" — rituals detached from the problems that justified them). Both substitute familiarity/ritual for analysis (decisions made by habit, defended by identity).

- **Why it matters (correctness)**: golden hammers misprice systematically (microservice overhead — network latency, deploy matrices, debugging across services — billed on workloads monoliths serve free; event sourcing on CRUD — journal complexity without audit need). Cargo cults tax without benefit (ceremonies consuming hours — standups/estimations/retros performed, outcomes unused; patterns adding layers — abstraction without variation, leaf 1.2-of-01's speculative-generality warning restated). Each persists because questioning feels disloyal (team identity wrapped around tools/rituals — dissent framed as non-collaboration).
- **Modern guidance** — ask "what problem does this solve *here*?" per adoption (golden-hammer test — specific problem named with measured alternative rejected, or default declined). Audit rituals quarterly (standups/estimations/patterns reviewed for *outcomes produced* — kept where producing, dropped where performing). Prefer boring technology for boring problems (monoliths for CRUD, functions for scripts, direct calls for stable singles — excitement budgeted where novelty pays). Dissent structurally (blameless "why do we X?" retrospectives — familiarity challenged on schedule, not just in crises).

```bash
# GOOD: adoptions justified per context (problems named, alternatives measured)
#  microservices: bounded contexts + independent deploy needs (verified team-scale) — else monolith (boring wins).
#  event sourcing: audit/replay requirements (verified) — else CRUD tables (journal complexity unjustified).
#  standup: blockers surfaced daily (measured unblocking) — else async updates (ceremony retired with data).
# BAD: "we do microservices here" (identity) / "always estimate in points" (ritual) —
# decisions by belonging, defended by loyalty; costs billed silently, benefits assumed loudly
```

### 3) **Premature abstraction and analysis paralysis**

**Definition** — *premature abstraction* (seams/frameworks/generics built for variation that never arrives — speculative generality billing readers for flexibility unused; YAGNI violated with architecture astronautics); *analysis paralysis* (modeling without shipping — decision matrices unmade, spikes unbuilt, perfect design pursued past diminishing returns). Opposite failures sharing a root (action without evidence — abstracting before variation vs deciding without data; both skip the empirical step that would route correctly).

- **Why it hurts when missing (correctness, maintainability)**: premature abstractions tax every reader (indirection without payoff — "flexible" code navigated slowly, debugged indirectly; removal feared — "something might use it" preserves dead flexibility forever). Paralysis taxes delivery (quarters modeling what weeks of building would reveal — spikes answer faster than diagrams for most technical unknowns; perfect plans rot as requirements move). Both mistake motion for progress (abstraction activity / analysis activity substituting for shipped learning).
- **Modern guidance** — abstract on second occurrence (rule of three for abstractions — first use direct, second copy tolerated, third extracts with evidence; premature = abstracting on zero-to-one). Spike unknowns time-boxed (days, not quarters — working code answers architecture questions diagrams can't; spikes disposable by design — throwaway permission explicit). Ship behind flags where uncertain (dark launches validate with production traffic — evidence beats analysis for behavioral unknowns). Sunset speculative seams (unused abstractions deleted on sight — flexibility unexercised is complexity unpaid-for).

```bash
# GOOD: evidence-gated abstraction and action (empiricism over anticipation)
#  duplicate twice -> extract on third (rule of three — evidence, not foresight).
#  unknown architecture -> time-boxed spike (days — code answers, diagrams speculate).
#  uncertain behavior -> flagged ship (production traffic decides — analysis bounded).
# BAD: "framework first, app second" (astronautics) or "quarterly planning, no spikes" (paralysis) —
# action without evidence in opposite directions (both skip the empirical step that routes correctly)
```

### 4) **Common confusion**

- "Anti-patterns are just bad code" — anti-patterns are *recurring bad solutions* (named shapes with known costs and known fixes — catalog entries, not insults). Bad code is instance-level; anti-patterns are pattern-level (systematic enough to name, fix, and teach against).
- "Catalogs encourage pattern-shaming" — catalogs enable *precise review* ("god object, split by stakeholder" beats "this is messy" — actionable vs affective). Shame targets people; catalogs target structures (blameless naming, same as incident reviews).
- "Knowing anti-patterns prevents them" — recognition *plus* review gates prevents them (naming without enforcement decorates decay — lint rules, thresholds, and checklists mechanize the catalog; knowledge alone watches).
- "Modern stacks outgrew classic smells" — stacks change (serverless/micro-frontends/AI-assisted), smells recur (god handlers, anemic DTOs, shotgun config changes — new venues, same shapes). Catalogs track structures, not technologies.

### 5) **Performance note**

Anti-patterns cost review velocity (god objects slow every PR touching them; shotgun changes multiply reviewers; ceremony taxes calendars), incident rates (untestable seams fail silently; unmonitored duplication drifts), and onboarding time (newcomers map accidental complexity as if essential). Catalog-driven review costs naming effort per finding (seconds — terms applied, fixes routed). Optimize naming speed first (shared vocabulary — findings stated in words, not essays), gate mechanics second (lint/thresholds/checklists enforcing the catalog), rewrite heroics never (incremental strangling beats big-bang purity).

### 6) **Mentor note**

Teach smells with live specimens (team's own god file opened in review — "count the reasons with me" converts catalog from literature to mirror). Drill fix-routing ("which leaf fixes this? — 01 §1.1/§3.1/02 §2.2 named per smell, not vaguely"). Practice golden-hammer interrogation ("what problem does X solve *here*?" until habitual). Watch for the shameless-shipper ("works, merge it" — fix with smell-naming as review requirement) and the purity-rewriter ("burn it down" — fix with strangler economics: incremental beats heroic). Review check: smells named per finding, fixes routed per catalog entry, ceremonies audited quarterly, juniors can smell unprompted (the nose trained, not just the vocabulary).
