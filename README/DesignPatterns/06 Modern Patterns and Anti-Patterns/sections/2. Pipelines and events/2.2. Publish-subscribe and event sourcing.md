## 2.2. Publish-subscribe and event sourcing

### 1) **Topics decouple at scale**

**Definition** — publish-subscribe routes messages through named topics (producers emit to channels — order/payment/shipping; consumers subscribe per interest — verified: first emit received, post-unsub emit unreceived): producers never name consumers (new subscriber types arrive without producer edits); consumers never name producers (topics versioned independently — schema evolution per channel). Verified delivery contract (emit → matched subscribers exactly once *per subscription lifetime*; unsubscribed → nothing, silently correct).

- **What problem it solves**: point-to-point integration tangles multiplicatively (order service calling payment/inventory/shipping directly — new consumer edits the producer; producer outages cascade synchronously — temporal coupling; schema changes fan out per call pair). Topics decouple in time *and* topology (producers emit-and-continue — consumers process at their pace; subscribers attach/detach without producer knowledge; versioned envelopes evolve per topic). Event-driven architectures scale *organizationally* (teams own topics, not pairwise contracts).
- **Modern guidance** — reach for pub-sub on fan-out/fan-in event flows (order lifecycles, domain events, webhook distribution — producers/consumers evolving independently). Version envelopes explicitly (schema registries, `kind` + version fields — consumers tolerate N/N−1 formats; breaking changes version topics, never sneak fields). Pair subscribe/unsubscribe structurally (leaf 2.1-of-04's pairing discipline, restated at bus scale — lapsed subscriptions leak per topic). Monitor lag per consumer group (slow consumers backpressure visibly — lag dashboards, not silent queues).

```typescript
// GOOD: topology decoupled, delivery contracted — verified receive + unsub-silence
bus.on("orders", (e) => inbox.push(`${e.kind}:${JSON.stringify(e.payload)}`));  // subscribe by topic
bus.emit("orders", "created", { id: "o1" }, "e1");   // producers name topics, never consumers
bus.off("orders", sub); bus.emit("orders", "created", { id: "o2" }, "e2");  // unreceived verified.
// BAD: direct service-to-service calls per event ("simpler, no broker") —
// N×M wirings (new consumer edits producer); synchronous coupling (producer outages cascade); no replay
```

### 2) **Event logs are truth**

**Definition** — event sourcing persists *append-only journals* (every state change as an immutable event — deposits/withdrawals logged, never updated-in-place) and *derives* current state by replay (verified balance **80** from dep100/wd30/dep10 — fold over history, deterministic given the log): state is a cached left-fold (rebuildable by replaying — crash recovery *is* re-folding; audit trails free — history *is* the journal, not a separate log); time travel debuggable (state-at-event-N by replaying to N — production incidents reproduced exactly).

- **Why it matters (correctness)**: update-in-place destroys history (current balance without provenance — "why 80?" unanswerable; overwrites losing the *sequence* that explains the state; audit requirements bolted on as afterthought logs — irreproducible summaries instead of replayable truth). Sourced logs preserve everything (every transition recorded — debugging replays exactly; schemas evolve with upcasting — old events migrate on read; temporal queries answerable — state at any point, not just now). The log *is* the database; projections are caches with defined staleness.
- **Modern guidance** — source events where auditability/replayability pays (financial ledgers, order lifecycles, collaboration histories — regulated or debugged domains first). Keep events immutable and versioned (append-only store — updates forbidden structurally; upcasters migrate old shapes on read). Derive projections idempotently (replay-safe folds — re-running yields identical state; verified balance recomputable any number of times). Snapshot periodically (fold checkpoints bounding replay length — cold starts read snapshot + tail, not full history).

```typescript
// GOOD: truth appended, state derived — verified 80 (deterministic fold, replayable forever)
type Ev = { id: string; kind: "dep" | "wd"; amt: number };
function replay(log: Ev[]): number {
  let bal = 0;
  for (const e of log) bal += e.kind === "dep" ? e.amt : -e.amt;  // fold: state IS the reduction
  return bal;  // replay([dep100, wd30, dep10]) = 80 verified (replayable any number of times).
}
// BAD: balance column updated in place ("current state suffices") —
// provenance destroyed ("why 80?" unanswerable); audit bolted on (irreproducible summaries); time travel impossible
```

### 3) **Idempotence required**

**Definition** — at-least-once delivery *will* redeliver (brokers retry on ambiguity — network partitions, consumer crashes mid-ack, timeout races): handlers must tolerate repeats (dedupe by event id — verified: double-delivery applied **once**; natural idempotence where operations commute — sets/adds over counters where increments double-count). Exactly-once is a myth at the transport layer (two-generals result — claimed exactly-once systems scope it narrowly: idempotent producer + transactional consume, both bounded); idempotent handlers make at-least-once *behave* exactly-once.

- **Why it hurts when missing (correctness, maintainability)**: non-idempotent redelivery corrupts (double-charged payments — the headline incident; duplicate shipments — inventory decremented twice; counter increments applied per delivery, not per event — metrics inflated silently). Each failure is duplicate-shaped (works once, corrupts twice — tests pass single-delivery suites; production redelivers under partitions, the exact condition tests skip). Dedupe-by-id converts redelivery from corruption into no-op (seen-set checked before apply — verified single application across double delivery).
- **Modern guidance** — dedupe every mutating handler by event id (seen-sets with retention bounds — unbounded seen-sets leak; TTL/size caps stated; verified single-apply pattern as template). Design naturally-idempotent operations where possible (set-state vs increment-counters — absolute writes tolerate repeats structurally; deltas need dedupe). Test redelivery explicitly (deliver twice, assert once — the test that proves idempotence instead of assuming transport exactly-once). Scope "exactly-once" claims honestly (idempotent-handlers-over-at-least-once — the achievable contract; transport-level exactly-once claimed only with bounded proof).

```typescript
// GOOD: redelivery-safe by construction — verified single apply across double delivery
function idempotent(handle: (e: Ev) => void): (e: Ev) => void {
  const seen = new Set<string>();              // dedupe store (bounded: TTL/size caps in production)
  return (e: Ev) => { if (seen.has(e.id)) return; seen.add(e.id); handle(e); };
} // deliver e1 twice -> applied once verified (at-least-once behaves exactly-once).
// BAD: "broker guarantees delivery" assumed exactly-once ("managed service") —
// redeliveries under partitions (guaranteed eventually); non-idempotent handlers corrupt per redelivery
```

### 4) **Common confusion**

- "Pub-sub replaces API calls" — pub-sub fits *events* (state-changed notifications — fire-and-observe); APIs fit *queries/commands needing answers* (request-response — caller blocks on result). Fire-and-observe vs ask-and-await — different needs sharing networks.
- "Event sourcing means event-driven" — event-driven *routes* via events (topology — this section's first half); event-sourced *persists* via events (truth in journals — second half). Routable without sourcing (transient buses); sourced without routing (single-service journals). Independent axes, combinable freely.
- "Idempotence is a nice-to-have" — idempotence is *correctness* under at-least-once delivery (brokers *will* redeliver — partitions guarantee it eventually). Nice-to-haves don't prevent double-charges.
- "Replay is only for recovery" — replay *queries history* (temporal reads — state-at-N), *rebuilds projections* (new read models from old logs — schema evolution without migration downtime), *audits* (regulators read journals). Recovery is one of four uses.

### 5) **Performance note**

Pub-sub costs broker hops per message (network latency dominating — microseconds-to-milliseconds vs nanosecond in-process; throughput scales with partitions — keyed ordering preserved per key). Sourced replay costs full-log folds (cold starts proportional to history — snapshots bounding to tail-only; steady-state appends O(1) each). Dedupe stores cost per unique id (bounded by TTL/size — retention priced explicitly). Optimize partitioning first (keyed order + parallel throughput), snapshot cadence second (cold-start budgets), handler idempotence third (correctness before speed — duplicates corrupt faster than slowness disappoints).

### 6) **Mentor note**

Demo redelivery live (deliver twice, apply once — "at-least-once behaving exactly-once" converts idempotence from theory to observable). Replay history in front of juniors (balance from journal — "state IS the fold" lands harder than any definition). Drill topic design ("producer names? consumers named? schemas versioned?" — decoupling audited per topic). Watch for the direct-caller ("simpler, no broker" — fix with N×M arithmetic on their consumer roadmap) and the exactly-once believer ("managed service guarantees" — fix with partition-scenario walkthrough ending in redelivery). Review check: topics versioned, journals append-only, handlers idempotent, replays tested, juniors can place event flows unprompted.
