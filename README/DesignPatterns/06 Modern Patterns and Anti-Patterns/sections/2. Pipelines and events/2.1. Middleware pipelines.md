## 2.1. Middleware pipelines

### 1) **Composed request processors**

**Definition** — middleware pipelines thread requests through ordered layers (each receives request + `next()` — handles, transforms, or delegates downstream): compositional request processing (logging → auth → validation → handler — cross-cutting concerns as stackable units). Verified: `log[handled:ok]` (outer log wraps handler output) vs `log[rejected]` (inner short-circuit — handler never ran, outer still observed). Order *is* semantics (auth-before-handler enforced structurally; reversed order authenticates responses — nonsense with types).

- **What problem it solves**: request processing without pipelines tangles cross-cutting concerns (logging/auth/validation copy-pasted per handler — N handlers × M concerns matrix; ordering implicit per handler — auth-after-handler bugs where sequence matters; short-circuiting ad hoc (early returns scattered — unhandled paths fall through silently). Pipelines linearize concerns (one layer per cross-cutting need — ordered explicitly, tested singly, composed declaratively).
- **Modern guidance** — reach for middleware on layered request processing (HTTP servers, message consumers, CLI command chains — cross-cutting + ordered + short-circuitable). Order deliberately (auth → validation → handler — security before work; logging outermost — observations cover full stacks; verified pair demonstrates both). Keep layers single-concern (one layer, one job — auth *or* logging, never both; composability requires granularity). Type the `next()` contract (call-once semantics — verified guard below; terminal default when layers exhaust).

```typescript
// GOOD: layers decide pass/respond — verified wrap + short-circuit
const app = pipe(
  (r, n) => `log[${n()}]`,              // outer: observes all (logging outermost)
  (r, n) => (r === "bad" ? "rejected" : n()),  // inner: short-circuits bad (handler never runs)
);
app("ok");   // log[handled:ok] verified (full stack traversed).
app("bad");  // log[rejected] verified (short-circuit observed; handler skipped structurally).
// BAD: per-handler auth/log/validate blocks ("explicit") —
// N handlers x M concerns matrix (ordering implicit per copy); short-circuits ad hoc (fall-through silent)
```

### 2) **Termination contracted**

**Definition** — every pipeline specifies its end (terminal default handler — verified `handled:${req}` when layers exhaust; short-circuit responses — verified `rejected` bypassing downstream; error lanes — next section): unhandled requests surface (defaults logged, 404s returned, dead-letters monitored — never vanish). Double-`next()` guarded structurally (verified `next() twice` throw — re-entrant dispatch detected, not double-executed).

- **Why it matters (correctness)**: unterminated pipelines lose requests silently (fall-through `undefined` — callers proceed on garbage; middleware forgetting `next()` *and* response — hangs, not errors; double-`next()` executing handlers twice (non-idempotent side effects duplicated — charges double-billed, emails double-sent). Each failure is silent-path (no error — absence or duplication discovered downstream). Termination contracts convert pipeline ends from emergent behavior into specified guarantees.
- **Modern guidance** — terminate every pipeline explicitly (default handler mandatory — terminal response stated; short-circuit responses specified per layer). Guard `next()` single-call (verified throw on double-invoke — re-entrancy detected structurally, not debugged eventually). Time out hanging layers (deadline per pipeline — stalled middleware fails loudly, never hangs callers). Test termination paths deliberately (exhausted/ short-circuited/error lanes — all three green required, not just happy-path).

```typescript
// GOOD: ends specified, re-entrancy guarded — verified guard + error lane
if (n <= i) throw new Error("next() twice");   // verified guard (double-execution structurally impossible).
return fn ? fn(req, () => dispatch(n + 1)) : `handled:${req}`;  // terminal default (exhaustion defined).
// error lane: try { pipe(req) } catch -> 500:db down verified (failures route, never fall through).
// BAD: "middlewares always call next() exactly once" as convention ("documented") —
// conventions unenforced re-enter (double side effects) or stall (hangs); guards enforce, docs describe
```

### 3) **Error lanes separate**

**Definition** — errors travel dedicated lanes (4-arity error middleware — `(err, req, res, next)` signatures distinguished by arity; error boundaries per pipeline segment — failures route centrally, never fall through): happy-path layers stay clean (no try/catch per middleware — error handling centralized); error layers specialize (logging + status mapping + alerting per error class — operational concerns composed like regular layers). Verified: throwing layer → `500:db down` (error lane caught, mapped, returned — pipeline intact).

- **Why it hurts when missing (correctness, maintainability)**: unhandled pipeline errors crash processes (uncaught throws in async middleware — Node process exits on unhandled rejections; partial responses sent then errored — headers-sent crashes; error context lost (which layer? which request? — debugging without lane discipline misattributes). Central error lanes convert crashes into responses (mapped statuses, logged contexts, alerted severities — operational maturity per pipeline).
- **Modern guidance** — separate error arity explicitly (4-arg signatures / dedicated error arrays — type-distinguished from happy layers; routing automatic). Map errors centrally (status codes per error class — client contracts stable; internal details logged, never leaked — information boundaries enforced). Alert on lane traffic (error-rate dashboards per pipeline — spikes page; silent error lanes are dead code with extra steps). Test error paths deliberately (throwing fixtures per layer — lane coverage green, not hoped).

```typescript
// GOOD: failures routed, mapped, alerted (lanes separate by construction)
// try { return pipe(req); } catch (e) { return onErr(e); }  // verified 500:db down (central mapping).
// error middleware: (err) => log + status + alert (operational concerns composed, not scattered).
// BAD: try/catch per middleware ("defensive") —
// error policy scattered (inconsistent statuses); uncaught async paths crash processes (lanes absent)
```

### 4) **Common confusion**

- "Middleware equals Chain of Responsibility" — middleware *processes through all layers* (all-match pipelines — leaf 2.2-of-05's pass-through semantics); CoR *classifies at first match* (first-handler-wins). Same sequence shape, opposite termination (exhaust-all vs first-match).
- "Order doesn't matter with independent middleware" — order decides short-circuiting (auth-before-handler enforced; reversed authenticates responses — nonsense), observation scope (outer sees all; inner sees remainder), and error capture (lanes catch downstream only). Independence of code ≠ commutativity of effects.
- "More layers means better separation" — layers multiply per-request overhead (hop cost × depth — measurable past dozens) and debugging indirection (12-layer traces). Separation pays per *concern* (one layer per cross-cutting need); ceremony layers tax without benefit.
- "Error middleware is optional polish" — error lanes are *correctness infrastructure* (uncaught pipeline errors crash processes — availability, not polish). Optional polish is formatting; lanes are availability.

### 5) **Performance note**

Middleware costs one hop per layer per request (nanoseconds each + layer logic — depth × cost; 5-layer stacks sub-microsecond overhead typical) plus short-circuit savings (rejected requests skip downstream — negative work avoided structurally). Unbounded stacks cost traceability (12-layer debug traces — incident time, not CPU) and ordering fragility (sequence assumptions untested). Optimize layer count first (one concern per layer — ceremony layers deleted), short-circuit placement second (reject early — wasted downstream avoided), hop overhead never (nanoseconds, inlined).
