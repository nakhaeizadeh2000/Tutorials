## 1.1. Dependency injection containers

### 1) **Registrations resolved with wiring**

**Definition** — DI containers centralize object-graph construction (registrations map keys to factories — `bind("db", () => new MemUsers())`; resolution builds graphs recursively — `get("svc")` constructs dependencies first): wiring lives in one composition root (bootstrap/tests configure; application code receives). Verified: resolved repo stores/gets (`ann`, count 1); unbound keys throw `unbound: missing` (fail loud at resolve-time, never `undefined` downstream).

- **What problem it solves**: manual wiring scatters construction (nested `new` across call sites — dependency order hand-managed; test doubles requiring constructor surgery per test — fakes can't slide in; vendor swaps touching policy files — leaf 2.2-of-01's weld recurring at scale). Containers convert wiring from scattered `new`s into declared registrations (graph built once per composition — tests compose fakes, production composes reals, same constructors both). Lifetime management rides free (singleton/scoped/transient per registration — next section).
- **Modern guidance** — reach for containers past ~10 wired types (manual roots suffice below — explicit `new` chains readable; containers pay past the point manual graphs tangle). Register factories, not instances (lazy construction — singletons cached per lifetime policy, transients fresh per resolve). Fail loud on misses (verified `unbound: missing` — typo'd keys error at startup, not as `undefined` three layers deep). Keep registration code reviewable (one module per boundary — registrations read as architecture documentation).

```typescript
// GOOD: wiring declared once, resolved everywhere — verified store/fetch + loud miss
const c = new Container();
c.bind("db", () => new MemUsers());                    // factory registered (lazy, replaceable)
c.bind("svc", () => ({ users: c.get<MemUsers>("db") })); // graph composed (dependencies resolved recursively)
c.get<MemUsers>("db").add({ id: "u1", name: "ann" });  // ann/count:1 verified (wiring works).
c.get("missing");  // throws "unbound: missing" verified (typos fail at resolve, never downstream).
// BAD: new MemUsers() scattered per consumer ("direct") —
// test doubles need constructor surgery per site; vendor swaps touch policy files (welds at scale)
```

### 2) **Lifetimes managed explicitly**

**Definition** — registrations declare lifetimes (singleton: one instance per container — verified repo shared across resolves; scoped: one per request/tenant — context-bound creation/disposal; transient: fresh per resolve — stateless workers, cheap construction): lifetime mismatches cause the classic DI bugs (singleton holding request state — cross-request bleed; transient holding expensive connections — pool exhaustion by re-creation; scoped resolved from root — lifetime escalation exceptions). Explicit lifetimes make ownership reviewable (scope stated per registration — captured dependencies checked against owner lifetimes).

- **Why it matters (correctness)**: lifetime errors corrupt silently (request-scoped user in singleton service — user A sees user B (verified-shape risk from leaf 1.1-of-02's bleed class, wearing DI clothes); disposable singletons never released — resource leaks with container lifetime; captive dependencies (long-lived holding short-lived — stale data served indefinitely). Each traces to undeclared lifetime (defaults assumed — singleton-everywhere or transient-everywhere, neither examined). Stated lifetimes convert these from incidents into review items.
- **Modern guidance** — declare lifetimes per registration (singleton/scoped/transient keywords — reviewers verify capture safety: longer-lived must never capture shorter-lived). Default to transient for stateless (fresh instances, no sharing questions); singleton for expensive-shared (pools, config — thread-safety reviewed); scoped for request data (disposal paired with scope end — using-blocks, middleware teardown). Visualize the graph periodically (container dump tools — lifetime violations visible as long→short edges; audit quarterly).

```bash
# GOOD: lifetimes explicit (capture safety reviewable)
#  singleton: Config, Pool (expensive/shared/thread-safe — stated, frozen where immutable).
#  scoped:    RequestCtx, Tenant (per-request creation/disposal — never captured by singletons).
#  transient: Validators, Mappers (stateless — fresh per resolve, zero sharing questions).
# BAD: default-singleton containers ("simple") —
# request state captured in singletons (cross-request bleed); disposables never released (leaks by default)
```

### 3) **Containers wire, never hide**

**Definition** — containers *compose* explicitly-wired constructors (injected code states dependencies as parameters — leaf 2.2-of-01's explicitness preserved *through* container use); service locators *hide* them (global `resolve()` calls inside business logic — dependencies invisible in signatures, untestable without container boot, unanalyzable statically). Same container library serves both shapes (registration/resolution vs global-service-locator anti-pattern — usage decides, not tooling).

- **Why it hurts when missing (correctness, maintainability)**: locator-pattern code resists testing (unit tests boot full containers — slow suites run less often, coverage decays; fakes require container reconfiguration — global state mutated per test, order-dependence returns); resists analysis (dependency graphs unrecoverable from signatures — architecture archaeology per change); resists refactoring (hidden dependents break silently on interface changes — compiler can't see string-keyed resolutions). Explicit constructors preserve all three (signatures document, tests inject directly, refactors typecheck).
- **Modern guidance** — inject via constructors always (container fills parameters — code testable with `new` + fakes, container-free). Call `get()` only at composition roots (bootstrap/tests — one resolve cascade per app start; business logic never imports the container). Ban service-locator imports in domain code (lint rule — container references outside roots rejected; the mechanical guard for explicitness). Prefer manual roots below ~10 types (explicit `new` chains — container ceremony unjustified; migrate when graphs tangle, not before).

```typescript
// GOOD: explicit constructors, container at roots (testable with new, wired by container)
// class Shift { constructor(private noti: Notifier) {} }  // dependency VISIBLE (leaf 2.2-of-01 pattern).
// bootstrap: c.bind("noti", () => new Smtp()); new Shift(c.get("noti")) (wiring centralized, code explicit).
// tests: new Shift(fake) (container-free — fakes slide in, no boot needed).
// BAD: Container.get("noti") inside Shift methods ("flexible") —
// hidden dependency (signatures lie); tests boot containers (slow suites); refactors break silently (string keys)
```

### 4) **Common confusion**

- "DI requires a framework" — DI requires *constructor parameters* (one language feature, zero dependencies); containers *scale* wiring past ~10 types. Framework-first inverts adoption (ceremony before need).
- "Singleton lifetime equals Singleton pattern" — lifetime describes *container behavior* (one instance arranged); pattern describes *global address* (leaf 2.1-of-02 — reachability welded). Arranged singularity (testable) vs addressed singularity (coupled) — different properties sharing a count.
- "More abstraction in wiring is better" — wiring abstraction beyond registrations (conditional graphs, convention scanning, auto-mocking) obscures the graph under test (debugging wiring becomes archaeology). Explicit registrations scale to hundreds of types; magic scales to confusion.
- "Transient is always safe" — transient *shares nothing* (safe) but *rebuilds everything* (expensive state reconstructed per resolve — pools as transients exhaust; config re-parsed per injection). Safety yes, cost maybe — lifetime follows expense + mutability.

### 5) **Performance note**

Containers cost resolution-time graph walks (microseconds per root resolve — once per app/test, negligible) plus per-resolve factory calls (transients constructed per injection — hot paths pool or singleton-ify where profiles demand). Manual wiring costs nothing extra (direct `new` — fastest possible). Service-locator hiding costs test time (container boots per suite — seconds × suites) and refactor safety (string-keyed resolutions invisible to compilers — breakage discovered at runtime). Optimize explicitness first (constructors state needs — testability + safety), container adoption second (~10-type threshold), resolution micro-costs never (startup-once).

### 6) **Mentor note**

Contrast wiring shapes live (scattered `new`s vs registered graph — "count the construction sites" converts centralization from taste to arithmetic). Break lifetime rules deliberately (singleton capturing request state — cross-request bleed demoed; transient pools — exhaustion demoed). Drill locator-vs-injection ("where's the `get()` call? — roots only" as review gate). Watch for the framework-mandater ("need container first" at 3 types — fix with manual-roots-until-tangled rule) and the locator-hider ("flexible" global resolves — fix with test-boot-time autopsy + hidden-dependency audit). Review check: registrations explicit with lifetimes, `get()` at roots only, tests container-free, juniors can wire graphs unprompted.
