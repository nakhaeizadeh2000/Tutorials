## 1.2. Repository: collection-like persistence

### 1) **Domain code sees collections**

**Definition** — Repository presents persistence as in-memory collections (`add`/`byId`/`find`/`remove` — domain language, zero storage vocabulary): policy code manipulates `users.byId("u1")` exactly as it would a `Map` (verified add/get/count — `ann`, 1). SQL/HTTP/files live behind the implementation (infrastructure detail, swappable per environment). Ubiquitous language preserved across the boundary (domain terms in, driver terms never out).

- **What problem it solves**: persistence-coupled domain logic rots in three directions (SQL strings in policy code — injection surface + untestable without databases; HTTP calls in use cases — network flakiness in unit tests; ORM entities leaking framework types — upgrades fan out through business rules). Repositories sever all three (policy depends on collection-shaped seams — tested with in-memory fakes; infrastructure implements per store — swapped per environment; queries expressed as specifications — next section).
- **Modern guidance** — reach for Repository at every persistence boundary (databases, APIs, file stores — each gets a collection-shaped seam; no driver types cross into policy). Mirror collection semantics faithfully (`add`/`remove`/`find` behave like their in-memory twins — same contracts, async where genuinely remote). Return domain types always (entities/records owned by policy — driver rows mapped at the boundary, never leaked). Name repositories after aggregates (`Users`, `Orders` — ubiquitous language, not `UserRepositoryImplFactory`).

```typescript
// GOOD: persistence as collections — verified add/get/count
class MemUsers {
  private rows = new Map<string, User>();
  add(u: User): void { this.rows.set(u.id, u); }
  byId(id: string): User | undefined { return this.rows.get(id); }  // collection semantics (Map twin)
  get count(): number { return this.rows.size; }
} // db.add({id:"u1",name:"ann"}); byId("u1")?.name -> "ann" verified; count 1 verified.
// policy: users.byId(id) (collection-shaped — storage invisible, test doubles trivial).
// BAD: SQL in use cases ("pragmatic") —
// injection surface + untestable without DB + driver upgrades fan out through policy (triple tax)
```

### 2) **Persistence ignorance tested**

**Definition** — in-memory fakes honoring repository contracts prove policy correctness without infrastructure (same interface, zero I/O — suites run in milliseconds, parallel-safe, deterministic): fakes implement the seam (`MemUsers` above — verified behavior identical to any future Postgres twin for tested paths); contract suites run against *all* implementations (fake in unit CI, real store in integration gates — behavioral parity enforced, drift detected). Persistence ignorance *tested* (policy suites never import drivers — enforced by lint where valuable).

- **Why it matters (correctness)**: infrastructure-coupled suites decay (slow tests run less often — coverage rots as suites grow; flaky network/database state — red builds ignored as "infra flakiness," real regressions hiding inside; untestable branches — error paths requiring staged outages never covered). Fake-backed suites stay fast/deterministic/complete (milliseconds per run — executed per change; coverage includes error paths — fakes simulate failures on demand). Parity suites catch drift (fake diverging from Postgres semantics — contract tests fail on the fake, not in production).
- **Modern guidance** — fake every repository in unit tests (in-memory twins — same contracts, zero I/O; error injection trivial — fakes throw/fail/lag on demand). Share contract suites across implementations (fake + real green on identical behaviors — parity enforced continuously). Gate integration separately (real-store suites in CI integration stage — slower, scheduled, still automated). Enforce ignorance mechanically (no driver imports in policy modules — lint rule; the guard for seam discipline).

```bash
# GOOD: ignorance tested (fast deterministic suites + parity gates)
#  unit: MemUsers fakes (milliseconds, parallel, deterministic — error injection on demand).
#  contract: shared suite x {Mem, Postgres} (parity enforced — drift fails loudly, not in prod).
#  integration: real-store stage (slower, scheduled — still automated, never manual).
# BAD: "integration tests cover it" as the only suite ("realistic") —
# slow/flaky/rare suites (coverage rots); error paths uncovered (outages untestable); policy untestable alone
```

### 3) **Queries stay inside**

**Definition** — query logic lives in repositories as *specification objects* (criteria composed: `active().olderThan(30)` — combinable, testable, storage-agnostic) or *named finder methods* (`byEmail()`, `overdue()` — intent-named, singly-implemented): never string-scattered (SQL fragments concatenated per call site — injection surface + untestable composition; query builders leaking into policy — driver vocabulary in domain code). Specifications compose (AND/OR/NOT combinators — complex queries from simple predicates, each independently tested).

- **Why it hurts when missing (correctness, maintainability)**: scattered queries rot through duplication (same filter logic in five call sites — diverging slowly; one site's fix never propagates — inconsistency as default state) and injection (concatenated values — the vulnerability class repositories exist to prevent; ORM-raw escapes per query — discipline unenforced). Centralized specifications collapse both (one implementation per query — tested once; compositional combinators — complex queries from verified parts).
- **Modern guidance** — name queries after intent (`overdue()`, `activeAdults()` — domain language, not SQL fragments). Compose via specifications (criteria objects combining — AND/OR/NOT per requirement; each predicate unit-tested). Parameterize always (bound values, never concatenated — injection structurally impossible, not carefully avoided). Keep repositories aggregate-rooted (one repository per aggregate — `Users`, not `UserEmails`; cross-aggregate queries compose repositories, never bypass them).

```typescript
// GOOD: queries owned, composed, safe (intent-named, combinable, parameterized)
// byEmail(email) (named finder — one implementation, tested once).
// active().olderThan(days) (specification combinators — complex from simple, each part tested).
// parameters bound always (injection structurally impossible — never concatenated, never escaped-later).
// BAD: SQL strings per call site ("flexible querying") —
// duplication drifts (five copies diverging); injection surface per concatenation (discipline, not structure)
```

### 4) **Common confusion**

- "Repository equals DAO" — DAOs map *tables* (data-access mechanics — CRUD per entity, storage-shaped); repositories model *collections* (domain-shaped aggregates — business language, collection semantics). Table-thinking vs aggregate-thinking — different centers.
- "In-memory fakes prove nothing" — fakes prove *policy logic* (all of it — deterministic, fast, complete); contract suites prove *parity* (fake ≡ real on shared behaviors); integration proves *wiring* (real store connected). Three suites, three questions — fakes answer the biggest one.
- "Specifications over-engineer queries" — specifications *compose* queries (combinators replacing concatenation — complexity managed structurally); string queries *accrete* (fragments concatenated — complexity unmanaged). Composition scales; accretion rots.
- "One repository per table" — one repository per *aggregate* (consistency boundary — `Order` + lines together; separate tables behind one seam). Table-per-repo leaks storage shape into domain design.

### 5) **Performance note**

Repositories cost one indirection per operation (interface dispatch — nanoseconds; in-memory fakes run at Map speed — suites in milliseconds). Real stores cost I/O per operation (network/disk latency dominating — batching/N+1 discipline matters, pattern overhead doesn't). Scattered queries cost duplication (maintenance) + injection surface (incidents) + untestability (slow suites run rarely). Optimize query shape first (N+1 elimination, batching, indexing — data-access performance lives here), seam overhead never (nanoseconds beside I/O milliseconds).

### 6) **Mentor note**

Contrast policy-with/without seams live (SQL in use-case vs `users.byId` — "which version tests in milliseconds?" converts ignorance from principle to observable). Demand fakes per repository ("show me the in-memory twin" — untestable seams rejected). Drill specification composition ("combine these three filters without strings" — combinators vs concatenation, decided live). Watch for the string-scatterer ("flexible querying" — fix with injection + drift autopsy on multi-site filters) and the DAO-confuser (table-shaped seams — fix with aggregate language: "what's the consistency boundary?"). Review check: policy driver-free, fakes honoring contracts, queries named/composed/parameterized, juniors can place persistence seams unprompted.
