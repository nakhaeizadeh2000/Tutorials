## 2.2. Interface segregation and dependency inversion

### 1) **Small cohesive interfaces over fat ones**

**Definition** — the Interface Segregation Principle: depend on *methods used*, never on interfaces bundling unused surface — clients shouldn't implement (or depend on) operations they never call. Verified trap: fat `ShopWorker { work(); eat(); }` forces `Robot.eat()` to `throw new Error("robots do not eat")` — an LSP violation (leaf 2.1) *smuggled* via ISP violation (throwing where the contract promises lunch). Segregated `Workable`/`Eatable` let `Robot2` implement only `work()` (verified `welding`) — no lies, no throws.

- **What problem it solves**: fat interfaces couple clients to unused surface (recompiles/reviews/tests triggered by methods never called — blast radius without benefit), force fake implementations (throw-stubs, no-ops returning lies — each a latent LSP violation awaiting a polymorphic caller), and freeze evolution (adding one method to a fat interface breaks *all* implementers — the many-forced-migrations tax). Segregation confines each change to its users: `Eatable` evolves without touching `Robot2`.
- **Modern guidance** — split by client (interfaces shaped by *consumers* — what does this caller need? — not by providers lumping capabilities). Prefer many small interfaces composed at use sites (`Workable & Loggable` intersections — [TS 04 mechanics](<../../../../TypeScript/04 Objects Interfaces and Type Aliases/README.md>)) over few large ones. Treat throwing-stubs as ISP alarms (any `throw new Error("not supported")` in an implementation names a fat interface to split — fix the seam, not the stub). Name interfaces after roles (`Workable`, `Eatable` — capability adjectives), never aggregates (`IWorkerManagerService`).

```typescript
// GOOD: depend on methods used — verified welding/lunch, no throws
interface Workable { work(): string; }
interface Eatable { eat(): string; }
class Robot2 implements Workable { work(): string { return "welding"; } }  // eats nothing, promises nothing
class Human implements Workable, Eatable {
  work(): string { return "coding"; }
  eat(): string { return "lunch"; }
}
// BAD: fat ShopWorker { work(); eat(); } —
// Robot.eat() throws "robots do not eat" (verified): ISP violation smuggling an LSP violation (leaf 2.1)
```

### 2) **Depend on abstractions**

**Definition** — the Dependency Inversion Principle: high-level policy modules own the interfaces they need (abstractions defined *by* the policy's requirements), and low-level details implement them (direction of dependency inverts vs naive layering — details depend on policy, not policy on details). `Shift` depends on `Notifier` (its abstraction — `send(msg)`), never on `EmailNotifier`/`SmsNotifier` (details plug in via constructor). Policy stable across detail churn (swap vendors without touching scheduling logic).

- **Why it matters (correctness)**: concrete dependencies weld policy to accidents (vendor SDKs in business logic — SDK upgrade rewrites scheduling; database drivers in domain code — migration rewrites rules; `new SmtpClient()` in `Shift` — untestable without a mail server, unswappable without editing). Inversion severs the weld (policy compiles against interfaces it owns — details injected, mocked, swapped behind the seam). Testability is the visible dividend (fakes slide in — verified `["done"]` log); swappability the structural one (vendors change, policy stands).
- **Modern guidance** — define abstractions at the policy level (interfaces live beside their consumers — `Notifier` in scheduling code, not in email code). Inject via constructors (explicit dependencies — `new Shift(fake)` in tests, `new Shift(smtp)` in production; no hidden `new` inside policy). Reserve service locators for composition roots (global registries hide dependencies — constructor injection states them; DI containers *wire*, never *hide*). Name abstractions after policy needs (`Notifier`, `OrderStore` — what policy requires), never implementations (`EmailService` as a type — detail leaking upward).

```typescript
// GOOD: policy owns the abstraction — verified ended + ["done"] via injected fake
interface Notifier { send(msg: string): void; }  // lives with Shift (policy), not with email code
class Shift {
  constructor(private noti: Notifier) {}          // explicit: testable, swappable
  end(): string { this.noti.send("done"); return "ended"; }
}
const log: string[] = [];
new Shift({ send: (m) => log.push(m) }).end();   // fake slides in: ["done"] verified, no mail server.
// BAD: `new SmtpClient()` inside Shift.end() ("simpler, one less file") —
// policy welded to vendor (untestable without SMTP, unswappable without editing Shift)
```

### 3) **Inversion enables testing and swapping**

**Definition** — constructor-injected abstractions make both directions free: *testing* (fakes/mocks/stubs implement the seam — verified fake records `["done"]`; contract tests run the same suite against real and fake — behavioral parity enforced); *swapping* (vendor B implements `Notifier` — one-line composition-root change reroutes production; feature-flagged dual-send composes two implementations behind one interface — [Decorator, Domain 03/2.1](<../../../03 Structural Patterns/sections/2. Decorators and proxies/2.1. Decorator stacking behavior.md>)). The seam pays per use, forever — testing speed daily, vendor freedom quarterly, incident response (swap the broken detail *now*) on demand.

- **Why it hurts when missing (correctness, maintainability)**: concrete-bound policy resists every lateral move (vendor incident at 2 AM — can't reroute without editing policy + full test cycle; flaky integration tests — no fake exists, suite needs live services; multi-tenant variants — `if tenant` branches accrete in policy code). Each absence converts a configuration change into a code change (deploy risk, review latency, test blast radius — leaf 1.1's invoices, restated for dependencies). Inversion converts code changes back into configuration (compose differently — policy untouched, proofs intact per leaf 1.2).
- **Modern guidance** — fake at every seam in tests (contract suite shared across implementations — real and fake green on identical behaviors; divergence fails loudly, not silently). Compose at a single root (one wiring file per app — `main.ts` builds the graph; policy files never `new` details). Flag-gate vendor swaps (dual implementations behind the seam during migration — traffic splits by config, rollback is reconfiguration). Audit `new` in policy code during review (each concrete construction is a missing seam — justify or inject).

```bash
# GOOD: lateral moves as configuration (seams paying per use)
#  vendor incident 2AM: compose Notifier=SmsBackup (one-line root change, policy untouched, deploy in minutes).
#  flaky suite: fake Notifier records (verified ["done"]) — no live services in unit tests, ever.
#  multi-tenant: per-tenant Notifier impls behind one seam (branches never enter policy code).
# BAD: "we'll abstract when we need a second vendor" (second vendor arrives during an outage) —
# seams under pressure are refactors under fire; seams upfront are one interface + constructor param
```

### 4) **Common confusion**

- "ISP means tiny interfaces always" — ISP means *client-shaped* interfaces (consumer needs decide size — a genuinely broad consumer justifies a broader seam). Tiny-for-tiny's-sake splinters (leaf 1.1's nano-class warning, restated for interfaces).
- "DIP means layers with interfaces between" — DIP means *ownership direction* (policy owns abstractions — details implement upward). Layer diagrams with interfaces facing the wrong way (details defining types policy consumes) invert nothing.
- "Injection needs a DI framework" — injection needs *constructor parameters* (one language feature, zero dependencies); frameworks *wire graphs* at scale (dozens of nodes — manual composition roots suffice below that). Framework-first inverts the adoption curve.
- "Segregated interfaces multiply files pointlessly" — files multiply with *clients*, each shaped to its consumer (cohesion per file rises as surface narrows). Pointless multiplication is unshaped splitting (interfaces per method — client-blind).

### 5) **Performance note**

Segregation costs interface count (files, imports — tooling handles granularity; JIT devirtualizes monomorphic seams to direct calls). Injection costs indirection per call (nanoseconds — constructor-stored references, no lookup overhead). Fat interfaces cost recompiles/reviews/tests per unused-surface change (human pipeline — days). Concrete welding costs incident response (vendor swap = code change + full cycle — hours at 2 AM). Optimize the human/incident pipeline (days/hours) over dispatch/file-count overhead (nanoseconds/files).

### 6) **Mentor note**

Hunt throwing-stubs live ("robots do not eat" — verified trap: "find the fat interface" converts ISP from slogan to observable). Drill seam ownership ("who defines this interface — policy or detail?" — direction stated per seam). Practice vendor-swap tabletops (reroute production in review — one-line root changes vs policy edits). Watch for the stub-tolerator ("just don't call eat()" — fix with "polymorphic callers *will*" + leaf 2.1) and the framework-mandater ("need DI container first" — fix with constructor params *today*, containers at graph scale). Review check: throwing-stubs absent, policy owns abstractions, constructors inject (no `new` of details in policy), juniors can place seams unprompted.
