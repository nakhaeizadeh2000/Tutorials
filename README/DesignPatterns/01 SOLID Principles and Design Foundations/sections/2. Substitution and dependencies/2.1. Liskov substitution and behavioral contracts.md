## 2.1. Liskov substitution and behavioral contracts

### 1) **Subtypes honor supertype contracts**

**Definition** — the Liskov Substitution Principle: code written against a supertype must work *unchanged* with any subtype — which means subtypes preserve *behavioral* contracts (preconditions weakenable-only: accept at least what the supertype accepts; postconditions strengthen-only: guarantee at least what the supertype guarantees; invariants maintained). Nominal conformance (extends/implements compiling) is necessary and insufficient — the compiler checks signatures, only tests plus reasoning check behavior.

- **What problem it solves**: substitutability violations corrupt polymorphically (collections of supertypes behaving differently per concrete element — the loop that works for 9 subtypes and breaks on the 10th; plugin architectures where one plugin violates the host's assumptions — host crashes blamed on the framework). Behavioral contracts convert "any X works here" from hope into guarantee: pre/post/invariant discipline per type, substitutability matrices per hierarchy (leaf: testing every subtype against supertype contracts, not just its own).
- **Modern guidance** — state contracts on supertypes explicitly (doc comments with pre/post/invariants — the behavioral specification compilers can't express; TypeScript mechanics in [TS 06](<../../../../TypeScript/06 Classes and Object-Oriented Types/README.md>), contracts here). Weaken inputs in overrides (accept wider — never narrow parameter types or add throwing preconditions). Strengthen outputs (return subtypes, preserve guarantees — never weaken postconditions or drop invariant maintenance). Bonus from verification: TS2611 *statically* rejects accessor-over-property overrides (the compiler catching one LSP smell — heed it as contract evidence, not annoyance).

```typescript
// GOOD: contracts stated, honored (supertype promises, subtype keeps)
// Rect contract: setW/setH independent; area() === w*h after any sequence.
// Subtypes must preserve independence — Square cannot (mutators couple), so Square must NOT extend Rect.
// BAD: nominal conformance treated as substitutability ("extends compiles, ships") —
// signatures match, behavior diverges; the loop breaks on the 10th element (verified below)
```

### 2) **Rectangle-square is the canonical trap**

**Definition** — Square extending Rect with coupled mutators (setW sets both sides — squareness invariant) violates Rect's independent-mutator contract: verified `stretch()` (setW(4), setH(5), area()) returns **20** for Rect but **25** for Square-as-Rect (setH(5) re-squared to 5×5 — contract says 20, subtype delivers 25). Same interface, different behavior on identical call sequences — the textbook substitutability failure, executable in six lines.

- **Why it matters (correctness)**: the trap recurs wherever mutators couple (read-only views over mutable bases, cached derivations that stale, "convenience" subclasses tightening method contracts — each *compiles* as substitution and *behaves* as violation). The failure is silent-value (25 instead of 20 — no error, just wrong geometry downstream: layouts misrender, physics miscompute, totals mis-sum). "Is-a" in prose doesn't imply substitutable in behavior — mathematics (squares *are* rectangles) misleads engineering (mutable squares *aren't* mutable rectangles).
- **Modern guidance** — refuse inheritance where mutator contracts diverge (Square and Rect as *siblings* implementing `Shape { area() }` — verified `Square2(5).area()` = 25, honestly its own contract). Prefer composition for code reuse without substitutability (leaf 3.1 — share implementation, don't inherit contracts). Test substitutability explicitly (run supertype contract suites against every subtype — the matrix from the intro; Square fails `stretch`, correctly excluded). Teach the trap early (every OO curriculum's rite of passage — recognized here, never shipped past it).

```typescript
// GOOD: siblings under an honest contract — verified 20 vs 25 separation
class Rect {
  constructor(private _w = 0, private _h = 0) {}
  setW(v: number): void { this._w = v; }
  setH(v: number): void { this._h = v; }          // independent mutators: THE contract
  area(): number { return this._w * this._h; }
}
class Square extends Rect {                        // TRAP (demonstration — do not ship):
  override setW(v: number): void { super.setW(v); super.setH(v); }  // couples: violates independence
  override setH(v: number): void { super.setW(v); super.setH(v); }
}
function stretch(r: Rect): number { r.setW(4); r.setH(5); return r.area(); }
stretch(new Rect());    // 20 verified (contract holds)
stretch(new Square());  // 25 verified (contract says 20 — substitutability VIOLATED)
// Square2 implements Shape separately: area 25, own contract, no inheritance lie.
// BAD: "Square is-a Rect (math!)" shipped as extends —
// mathematics describes immutable shapes; engineering mutates — mutable is-a needs behavioral proof
```

### 3) **Contracts enforced by types and tests**

**Definition** — three enforcement layers: *types* (parameter/return positions encode pre/post — branded IDs reject wrong-kind arguments at compile time; `readonly` + getters protect invariants structurally); *asserts* (runtime invariant checks at boundaries — constructor validation, method preconditions throwing `RangeError`/`TypeError` with messages); *substitutability matrices* (every subtype run against the supertype's contract suite — stretch-like probes per hierarchy, filed as tests, green required).

- **Why it hurts when missing (correctness, maintainability)**: unenforced contracts decay into documentation (accurate on write day, aspirational by quarter three — subtypes added without contract review, violations discovered in production value-errors). The three layers cost differently (types: free at compile; asserts: nanoseconds per call; matrices: one test file per hierarchy) and fail differently (types catch signature drift; asserts catch runtime violations; matrices catch subtype divergence). Skipping all three converts LSP from principle into poster.
- **Modern guidance** — brand parameters crossing trust boundaries (`UserId` vs `string` — wrong-kind arguments rejected before behavior diverges). Assert invariants at construction + mutation (fail fast with named errors — `throw new RangeError("width >= 0")` beats silent negatives). Maintain contract suites per polymorphic hierarchy (supertype behaviors as shared tests — every subtype green, every PR; the matrix from the intro, mechanized). Review new subtypes against contracts explicitly ("which supertype promises could this break?" — the question that prevents the next Square).

```typescript
// GOOD: three layers (types catch drift, asserts catch violations, matrices catch divergence)
type UserId = string & { readonly __brand: "UserId" };  // wrong-kind args rejected at compile
class BoundedRect extends Rect {
  override setW(v: number): void {
    if (v < 0) throw new RangeError("width >= 0");      // precondition asserted (strengthened? NO — added!)
    super.setW(v);
  }
} // NOTE: added preconditions NARROW the contract (callers passing 0..n now fail on negatives they passed
// before) — LSP forbids strengthening preconditions; validate at construction, not per-mutator.
// BAD: contract suites "identical to unit tests, skip" —
// unit tests prove subtypes work alone; contract suites prove them interchangeable (different question)
```

### 4) **Common confusion**

- "LSP is about inheritance hierarchies" — LSP is about *substitutability wherever polymorphism flows* (subclasses, interface implementations, duck-typed callbacks, plugin contracts — any "any X works here" claim). Hierarchies are one venue.
- "TypeScript's `extends` guarantees LSP" — `extends` guarantees *nominal* conformance (signatures align); behavior is yours (verified 25-vs-20 compiles cleanly — the compiler checked shapes, not contracts). TS2611 catches one smell (accessor/property mismatch); the rest is reasoning + tests.
- "Square-rectangle is pedantry" — the trap's *shape* (coupled mutators under independent contracts) recurs in production weekly (cached views, convenience subclasses, mutating decorators). Pedantry that prevents silent-value incidents is engineering.
- "Strengthening preconditions is safer" — safer *locally* (fewer states to handle), violating *globally* (callers relying on supertype acceptance break — substitutability fails outward). Validate at construction boundaries, keep mutators contract-faithful.

### 5) **Performance note**

Contracts cost nothing at design (sentences in docs), nanoseconds at runtime (asserts on hot paths — measurable only past millions of calls/second; strip via invariant-hoisting where profiles demand), and one test file per hierarchy (matrices run in CI seconds). Violations cost silent-value incidents (wrong geometry/totals/layouts — hours of debugging answers that aren't errors) plus hierarchy rewrites (Square-extends-Rect refactored under production load). Optimize enforcement cheapness (types free, asserts nanoseconds, matrices seconds) over violation risk (incidents unbounded).

### 6) **Mentor note**

Demonstrate the trap live (20 vs 25 on identical call sequences — "same interface, same calls, different answers" converts LSP from slogan to observable). Teach contracts-before-hierarchy ("state pre/post/invariants first, then decide extends-vs-sibling" — order that prevents the trap structurally). Drill substitutability matrices (supertype suites run against every subtype — stretch-like probes filed per hierarchy). Watch for the math-appealer ("is-a, obviously" — fix with mutability distinction: immutable shapes vs mutable contracts) and the nominalist ("compiles, ships" — fix with verified 25-vs-20 on their own hierarchies). Review check: contracts stated per supertype, preconditions never strengthened in overrides, matrices green per hierarchy, juniors can narrate the trap unprompted.
