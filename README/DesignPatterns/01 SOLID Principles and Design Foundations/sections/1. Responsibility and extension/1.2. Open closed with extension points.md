## 1.2. Open-closed with extension points

### 1) **Open for extension, closed for modification**

**Definition** — the Open-Closed Principle: modules accept new behavior through *extension* (new classes implementing existing seams) without *modification* (existing tested code untouched). Verified: `Checkout` depending on a `Discount` interface prices `NoDiscount`→100 and `Pct(0.1)`→90; adding `Holiday` (−10 over 50) requires zero edits to `Checkout` (new file, old tests still green — verified 90/30 outputs). Contrast `payBad(kind)` (switch-on-string — every rule edits the function and re-earns its tests).

- **What problem it solves**: modification taxes tested code (every edit to a working function re-opens its defect window — tests re-earned, reviewers re-reading, deploys re-risked). Branch-per-feature conditionals (`if kind...`) centralize all variation in one ever-growing function (merge conflicts per feature, combinatorial test matrices, the file everyone fears). Extension points distribute variation to new files (each rule isolated, tested alone, reviewed by its owner — leaf 1.1's single-reason modules plugging into stable seams).
- **Modern guidance** — depend on interfaces at variation axes (discount rules, validators, renderers, parsers — wherever requirements say "more kinds coming"). Add kinds by implementing, never by editing (new file per rule — the seam *is* the extension mechanism). Keep the core closed ruthlessly (no "just this once" branches in `Checkout.pay` — one exception reopens the tax for all future kinds). TypeScript mechanics (interfaces, `implements`) express seams — [TS 04 owns the how](<../../../../TypeScript/04 Objects Interfaces and Type Aliases/README.md>), this leaf owns the *where-to-cut*.

```typescript
// GOOD: new behavior, zero edits — verified outputs (existing 100/90 untouched, new 90/30 added)
interface Discount { apply(total: number): number; }
class Checkout {
  constructor(private rule: Discount) {}
  pay(total: number): number { return this.rule.apply(total); }  // closed: never edited per rule
}
class Holiday implements Discount {  // open: new file, new behavior
  apply(t: number): number { return t >= 50 ? t - 10 : t; }
}
// BAD: switch-on-kind (payBad: if/else per rule) —
// every rule edits one function (conflicts), re-earns all tests (blast radius), grows without bound
```

### 2) **Extension points designed, not discovered**

**Definition** — seams placed *where change arrives* (variation axes identified up front: pricing rules, notification channels, parsers per format — each gets an interface before the second kind exists), not retrofitted after the third `if` (refactoring switch-statements into strategy *after* they hurt — costlier with every accumulated branch). Designed seams cost one interface early; discovered seams cost a refactor plus migrated callers plus re-earned tests late.

- **Why it matters (correctness)**: undiscovered variation hardens into structure (callers depend on concrete classes — `new Pct()` scattered across code; adding `Holiday` means editing every construction site, not just one function). Designed seams centralize construction (factories/DI own instantiation — [Domain 02's creational patterns](<../../../02 Creational Patterns/README.md>); callers depend on `Discount`, never `Pct`). Late discovery also misplaces seams (interfaces drawn around *current* kinds instead of *variation axes* — the seam fits today's rules and breaks on tomorrow's).
- **Modern guidance** — predict one axis ahead (requirements saying "more X coming" → seam now, even with one implementation — YAGNI waived where roadmaps speak). Draw seams around *variation*, not examples (`Discount` abstracts pricing-rule-ness — not `Pct`'s shape; `Notifier` abstracts channels — not email's API). Refactor discovered switches promptly (second branch = yellow flag; third = mandatory extraction — the rule preventing switch-statement fossilization). Keep seam count proportional (every interface is a commitment — unneeded seams tax readers; needed-but-missing tax editors).

```typescript
// GOOD: seam at the variation axis (pricing-rule-ness, not Pct-shape)
// interface Discount { apply(total: number): number; } — second kind (Pct) already justified it;
// third kind (Holiday) landed with zero edits (verified above).
// BAD: interface per concrete class ("IDiscountCalculatorFactoryManager" bloat) —
// seams without variation axes tax readers for flexibility never exercised (speculative generality)
```

### 3) **Modification risk priced per edit**

**Definition** — every modification to tested code re-opens its defect window (tests re-run *and* re-trusted — green on ($) changed lines proves less than green on untouched lines; reviewers re-read context — changed-line attention dilutes across diffs; deploys re-risk — rollback scope widens). Closed modules keep their proofs (untouched code carries its test history forward intact — green means what it meant). Pricing modification risk per edit converts "just a small change" from reassurance into accounting.

- **Why it hurts when missing (correctness, maintainability)**: casual edits to core paths cause the classic "unrelated" outages (one-line tweak in shared validation breaks three features' edge cases — blast radius unmeasured because modification risk was unpriced). Teams that price it gate core edits (two reviewers, expanded test runs, canary deploys — friction proportional to blast radius); teams that don't discover blast radius in production (the invoice OCP was designed to prevent). Closed-for-modification isn't rigidity — it's risk accounting with enforcement.
- **Modern guidance** — price edits by blast radius (callers × test scope × deploy exposure — one-line core change outranks hundred-line leaf change in review rigor). Protect closed modules mechanically (CODEOWNERS on seams, branch protection on core paths — [Git 06 §1.1 policy](<../../../../Git/06 Workflows Tags Stash and Releases/sections/1. Branching strategy/1.1. Trunk-based GitHub Flow and GitFlow shapes.md>), test-coverage floors that fail PRs deleting tests). Prefer extension-shaped PRs in review ("could this land as a new implementation?" — the question that keeps cores closed). Reopen deliberately, never casually (seam redesigns happen — versioned, announced, migrated — not snuck into feature PRs).

```bash
# GOOD: risk accounting per edit (blast radius priced, gates proportional)
#  leaf addition (new Discount impl): 1 reviewer, focused tests — closed core untouched, proofs intact.
#  core edit (Checkout.pay change): 2 reviewers, full suite, canary — blast radius = all rules.
# BAD: "just a small change to core" waved through ("one line") —
# lines don't price risk; callers x tests x exposure do (the invoice arrives in production)
```

### 4) **Common confusion**

- "OCP means never modify code" — OCP means *extend behavior* without modifying *stable abstractions* (refactors, bug fixes, and seam redesigns modify freely — with versioning and migration). Closed for *behavioral* modification via new kinds, open for everything else with process.
- "Interfaces everywhere = OCP" — interfaces at *variation axes* = OCP (proven change arrival); interfaces everywhere = speculative generality (reader tax without editor payoff). Seams follow predicted variation, not uniformity.
- "Switch statements always violate OCP" — switches over *closed* sets (AST node kinds, protocol versions — exhaustive, rarely extended) are honest; switches over *open* kinds (discount rules, parsers — extended routinely) violate. Openness of the set decides, not the statement shape.
- "Plugin architectures are overkill" — plugin shape *is* OCP at system scale (seams + discovery + isolation); overkill judgments need variation forecasts (three kinds certain → seam now; one kind forever → YAGNI holds).

### 5) **Performance note**

Extension costs indirection (interface dispatch — nanoseconds, devirtualized by JIT at monomorphic call sites) and file count (module granularity — bundlers handle it). Modification costs review latency (multi-stakeholder re-reads), test time (blast-radius suites), and incident risk (defect windows reopened per edit). Optimize the human pipeline (reviews, tests, incidents — days) over dispatch overhead (nanoseconds, optimized away). Seams pay once in structure, save per change forever.

### 6) **Mentor note**

Demonstrate closedness live (add `Holiday` with zero `Checkout` edits — "watch the diff: one new file, zero changed lines" converts OCP from slogan to observable). Drill seam placement ("where will the third kind arrive?" — predicted axes before second implementations). Price modification risk aloud in reviews ("blast radius = ?" until juniors compute callers×tests×exposure reflexively). Watch for the switch-accumulator ("one more branch" × 12 — fix with third-branch-mandatory-extraction) and the interface-sprayer (seams without variation — fix with "name the arriving kind or delete the seam"). Review check: variation axes carry seams, new kinds land extension-shaped, core edits priced by blast radius, juniors can place seams unprompted.
