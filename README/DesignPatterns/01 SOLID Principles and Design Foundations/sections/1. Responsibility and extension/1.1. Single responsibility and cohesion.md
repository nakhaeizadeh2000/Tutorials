## 1.1. Single responsibility and cohesion

### 1) **One reason to change per module**

**Definition** — the Single Responsibility Principle: a module (class, function, file) should have one *reason to change* — one axis of variation (business rule *or* persistence schema *or* notification format — never all three). Reasons, not duties: a class doing three related things for one stakeholder can cohere; a class doing one thing each for three stakeholders will fracture. Cohesion measures shared reasons (high: everything changes together for one cause); coupling measures cross-reasons (edits for cause A breaking cause B's tests).

- **What problem it solves**: multi-reason modules bill every change three times — pricing-rule edits rerun persistence tests (blast radius), schema migrations touch notification code (merge conflicts), notification rewords invalidate pricing reviews (sprawl). Each stakeholder's change drags unrelated code through review, test, and deploy risk. SRP confines blast radius to the changed reason: one cause, one module, one test file, one reviewer who owns the domain.
- **Modern guidance** — split by *change reason*, not by verb count ("saves + notifies" can cohere under one workflow owner; "prices + persists" splits across rule-owner vs schema-owner). Name the reason per module in docs ("changes when tax rules change" — review checks the name, not just the code). Prefer small cohesive units composed at boundaries (leaf 3.1's composition) over medium mixed ones. TypeScript mechanics (classes, `private`, `readonly`) implement the split — [TS 06 owns the how](<../../../../TypeScript/06 Classes and Object-Oriented Types/README.md>), this leaf owns the *where-to-cut*.

```typescript
// GOOD: one reason to change each — verified behavioral equivalence (18/18, saved:a1 both)
class Pricer { total(items: number[]): number { return items.reduce((s, x) => s + x, 0); } } // changes: pricing rules
class OrderRepo {  // changes: persistence schema
  constructor(private store = new Map<string, Order>()) {}
  save(o: Order): void { this.store.set(o.id, o); }
  get(id: string): Order | undefined { return this.store.get(id); }
}
class Notifier { saved(o: Order): string { return `saved:${o.id}`; } } // changes: notification format
// BAD: OrderService { price() + save() + notify() } ("simpler, one class") —
// pricing edits rerun persistence tests; schema migrations touch notification code; one class, three invoices
```

### 2) **Splitting by change cadence**

**Definition** — change *rates* cluster responsibilities better than change *topics*: fast-moving code (pricing experiments, feature-flagged rules — weekly) separated from stable code (persistence schemas, audit formats — yearly), even when topically adjacent. Cadence-split modules change at one speed: fast files iterate without destabilizing slow ones; slow files review rarely with full attention. Same-cadence code coheres naturally (one release rhythm, one test strategy, one owner).

- **Why it matters (correctness)**: mixed-cadence modules force false coupling between release trains (pricing experiment blocked on schema-review queue — velocity taxed by the slowest stakeholder; or worse, schema change smuggled inside a pricing PR — review attention split, migration bugs slip). Cadence is observable (commit history per file — `git log --follow` shows who changes what, how often — [Git 02 §2.1 archaeology](<../../../../Git/02 Core Workflow Add Commit and Inspect/sections/2. Reading history/2.1. Log filtering formatting and the questions log answers.md>)); split where frequencies diverge.
- **Modern guidance** — audit cadence with history (`log -- <path>` per candidate split — weekly vs yearly adjacent files are the seam). Put volatile rules behind interfaces (leaf 1.2's extension points — fast code plugs in, stable code never moves). Keep stable modules dependency-light (few imports — nothing fast may depend on nothing slow breaking it; direction matters: stable ← volatile, never reversed). Re-split yearly (cadences drift with org growth — today's stable core is tomorrow's experiment substrate).

```typescript
// GOOD: cadence-separated — volatile rules plug into stable seams
interface PricingRule { total(items: number[]): number; }  // stable seam (changes: almost never)
class WeeklyPromo implements PricingRule { total(items: number[]): number { /* experiments here */ return 0; } }
// pricing experiments iterate weekly; OrderRepo persists yearly — neither blocks the other.
// BAD: promo logic inside OrderRepo.save() ("one place for orders") —
// weekly experiments queue behind yearly schema reviews; velocity taxed by slowest stakeholder
```

### 3) **God objects billed on every edit**

**Definition** — god objects (hundreds of methods, dozens of reasons — `UserManager` handling auth + billing + notifications + reporting + admin) invoice *every* edit: full-file review (no reviewer owns all reasons), full-suite tests (blast radius = everything), merge conflicts on every concurrent change (all stakeholders touch one file), and onboarding walls (understand everything to change anything). The invoices compound: each added reason raises the next change's cost — god objects grow *and* slow simultaneously.

- **Why it hurts when missing (correctness, maintainability)**: god-object incidents are the most expensive category of "simple" bugs (one-line pricing fix breaks notification tests nobody ran — blast radius unmeasured; schema migration conflicts with three in-flight features — merge archaeology; new hire's first PR touches auth accidentally — review couldn't scope). Each traces to multi-reason structure, not code quality — good engineers in god objects produce god incidents. Decomposition is prevention, not refactoring theater.
- **Modern guidance** — decompose by reason (extract per stakeholder/axis — one class per invoice-payer; facade over the pieces where callers need one entry ([Domain 03's Facade](<../../../03 Structural Patterns/sections/1. Adapters and facades/1.2. Facade simplifying the front.md>) — coordination without coupling). Measure before/after (test-file count per change, reviewers per PR, conflicts per sprint — decomposition pays in all three within a quarter). Forbid regrowth (review rule: new methods must name their module's single reason — unnamed additions rejected; lint via file-length budgets as tripwires, not law).

```bash
# GOOD: decomposition economics (measured, not aesthetic)
#  before: UserManager.ts (900 lines, 6 reasons) -> pricing PR touches 900 lines, 4 reviewers, 12 test files.
#  after:  Pricer/Repo/Notifier/... (6 files, 1 reason each) -> pricing PR touches 60 lines, 1 reviewer, 1 test file.
# BAD: "we'll split it when it hurts" (it hurts now — invoices arrive per edit, the pain IS the signal)
```

### 4) **Common confusion**

- "SRP means one method per class" — one *reason to change*, not one method (a cohesive pricing engine has many methods, one axis). Method-counting is cargo-cult; reason-naming is analysis.
- "Small classes are always better" — splintered nano-classes scatter reasons across files (change requires touching twelve one-method classes — coupling *worse* than the god object). Cohesion first (shared reasons together), then size judgment.
- "God objects are faster to write" — faster *once* (first feature ships today); slower forever after (every subsequent edit pays all reasons' taxes). Speed measured per feature over quarters, not per file on day one.
- "Splitting needs permission/architect review" — splitting needs *reason names* (each piece's axis stated — reviewable by anyone). Bureaucracy-free decomposition: name reasons, extract, facade.

### 5) **Performance note**

SRP costs indirection (method calls across pieces — nanoseconds, inlined by JIT at these shapes) and file count (module load trivial — bundlers/tree-shaking handle granularity). God objects cost review latency (multi-reason PRs wait for all stakeholders), test time (blast-radius suites per change), and merge-conflict resolution (hours per sprint at scale). Optimize the human pipeline (reviewers, tests, conflicts — the bottleneck), never the call graph (nanoseconds irrelevant beside review days).

### 6) **Mentor note**

Teach reason-naming before extraction ("what are this module's reasons to change? — list them aloud" until multi-reason code *looks* wrong). Drill cadence audits with real history (`log --follow` on team files — weekly-vs-yearly adjacencies jump out). Demonstrate invoices with the before/after table (lines-touched, reviewers, test files — decomposition economics as arithmetic). Watch for the duty-counter ("three methods, fine" — fix with "how many *reasons*?") and the splinterer (nano-classes everywhere — fix with cohesion-first: shared reasons stay together). Review check: every module names one reason, cadence-mismatches separated, god objects decomposed with facades, juniors can list reasons unprompted.
