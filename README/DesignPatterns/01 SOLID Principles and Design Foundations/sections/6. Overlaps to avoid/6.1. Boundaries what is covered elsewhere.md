## 6.1. Boundaries: what is covered elsewhere

### 1) **Language mechanics**

**Definition** — classes, interfaces, modifiers, generics, decorators *syntax*, mixins mechanics — the *how* of writing typed code — belong to the [TypeScript track](<../../../../TypeScript/README.md>) (notably 04 interfaces/aliases, 06 classes, 08 generics, 14 decorators); this track uses those mechanics to express *design decisions* (principles selecting structures, patterns organizing behavior). When a leaf here shows `implements Discount`, the *syntax* is a link, and only the *seam placement* is new. Recorded overlap: TS 14's logging/memoization/DI *decorator examples* vs Domain 03/06's Decorator-pattern and DI coverage — syntax there, pattern judgment here, linked both ways (03 landed; 06 pending).

- **Why the boundary matters**: mechanics re-taught per principle rots independently — five class-syntax explanations diverging, three decorator-syntax framings drifting. Single source of truth: language mechanics get their full treatment once (TypeScript track), everywhere else one line plus a link. This leaf is the map that keeps those lines short for the whole track.
- **Modern guidance** — if a passage here needs more than one sentence of TypeScript mechanics, stop and link instead. The one-sentence versions: classes structure (TS 06), interfaces type contracts (TS 04), decorators annotate (TS 14), generics parameterize (TS 08). Everything else here is *design* (principles selecting, patterns organizing).

```typescript
// GOOD: one line here, depth behind the link
class Holiday implements Discount { /* ... */ }  // implements mechanics: TS 04; seam placement: here.
// BAD: re-teaching class/interface/decorator syntax inside principles leaves
```

### 2) **Concrete patterns**

**Definition** — creational (Singleton, Factory, Builder, Prototype → [Domain 02](<../../../02 Creational Patterns/README.md>)); structural (Adapter, Decorator, Facade, Proxy, Composite → [Domain 03](<../../../03 Structural Patterns/README.md>)); behavioral command-and-control (Strategy, Observer, Command, State → [Domain 04](<../../../04 Behavioral Patterns Command and Control/README.md>)); behavioral distribution (Iterator, Mediator, Visitor, Chain → [Domain 05](<../../../05 Behavioral Patterns Distribution and Interpretation/README.md>)); modern practice and anti-patterns (DI containers, repositories, middleware → Domain 06, planned, see LOG). Principles applied there; mechanics owned there.

- **Why the boundary matters**: every pattern re-explained here duplicates its home domain (Strategy inside OCP leaves, Observer inside DIP leaves — pattern tutorials wearing principles clothes). Single source of truth: each pattern gets its full treatment once (intent, structure, consequences, sample code — Domains 02–06); principles leaves reference patterns as *examples* (one line: "Strategy *is* OCP applied to algorithms"), never re-teach them.
- **Modern guidance** — memorize the forward map used here and defer the rest: creation → [02](<../../../02 Creational Patterns/README.md>), structure → 03, command/control behavior → [04](<../../../04 Behavioral Patterns Command and Control/README.md>), distributed behavior → 05, modern/anti → 06, mastery → 07. When pattern curiosity strikes mid-principle ("but how does Strategy *compose*?"), follow the forward links — [Domain 02](<../../../02 Creational Patterns/README.md>) answers creation, [Domain 04](<../../../04 Behavioral Patterns Command and Control/README.md>) answers behavior — with code and trade-offs, not prose.

### 3) **Vocabulary naming**

**Definition** — what principle and pattern names *mean in a meeting* (SOLID as an acronym, "singleton" as shorthand, "just use a factory" in planning) belongs to [IT Vocabulary](<../../../../ITVocabulary/README.md>); this track never re-teaches definitions those leaves own. Map-style stop-list: principles → here (01), creation → 02, structure → 03, behavior → 04–05, modern → 06, mastery → 07, mechanics → TypeScript track, words → IT Vocabulary.

- **Why the boundary matters**: every boundary crossed here is duplication that rots — glossaries copied into principles leaves go stale when industry usage shifts, while the words-track stays current. The concept gets its full treatment once, everywhere else one line plus a link.
- **Modern guidance** — when writing or reviewing Domain 01 content, ask "does a sibling domain or track own this sentence?" If yes, compress to a link. The domain stops at: SOLID principles, composition/coupling judgment — everything about *how the language works*, *which pattern to use*, or *what the words mean* lives elsewhere.

### 4) **Common confusion**

- "Principles are where advanced design lives" — principles are *foundations*; the advanced mechanics distribute across pattern domains (02–06). This domain is the bedrock, not the whole building.
- "Boundaries leaves are filler" — they are the DRY contract made visible: each states what its domain deliberately does *not* teach so the repo can teach it once.

### 5) **Performance note**

No runtime cost to boundaries — the performance is editorial: one-line links instead of copied sections keep every leaf short, searchable, and single-sourced. When TypeScript 07 ships syntax changes, zero pattern leaves update (only TS leaves); when [Domain 04](<../../../04 Behavioral Patterns Command and Control/README.md>) changes Observer guidance, one domain updates instead of seven.

### 6) **Mentor note**

Use this leaf as the "where do I look?" map for juniors arriving with design-adjacent questions: mechanics → TypeScript track, patterns → Domains 02–06, words → IT Vocabulary. Quiz: "where does Strategy live?" (02/04), "where do class mechanics live?" (TS 06), "where does SOLID-as-vocabulary live?" (ITV). Correct answers mean the track's architecture landed — the most valuable thing a boundaries leaf can teach.
