## 3.1. Composition over inheritance and coupling budgets

### 1) **Compose behavior, inherit interface**

**Definition** — assemble behavior by *delegating* to held components (constructor-injected collaborators — leaf 2.2's seams at work) while inheriting only *interfaces* (type contracts without implementation); override implementation inheritance except where substitutability is proven (leaf 2.1 decides). Verified incident: `CountingCart` overriding `add` counts 2 under base-v1, then **0** after the base optimizes `addAll` to bypass `this.add` (items present, count silently wrong); the composed `Cart` (loop over injected `Storer`) stays correct across both base versions — no override, no hazard.

- **What problem it solves**: implementation inheritance couples subclasses to base *internals* (which methods call which overridables — unwritten contracts the base may change without notice). Base-class edits then break subclasses silently (verified 2→0: no error, no test failure at the base level — the subclass's invariant died in someone else's refactor). Composition severs the coupling (components interact through owned interfaces — base changes can't reach composed behavior because no override paths exist). Fragile-base incidents are inheritance's signature failure; delegation removes the signature.
- **Modern guidance** — default to composition (hold collaborators, delegate explicitly — the structure that survives base evolution); inherit interfaces freely (type contracts compose safely — `implements` carries no implementation risk); override implementation only with substitutability proof (leaf 2.1's contract suite green — proven, not hoped). Audit existing hierarchies for self-call dependence (base methods calling overridables — each is a latent fragile incident; document or decompose).

```typescript
// GOOD: owns its loop, delegates storage — immune to base evolution (verified a,b correct)
interface Storer { put(x: string): void; list(): string[]; }
class Cart {
  constructor(private store: Storer) {}
  add(x: string): void { this.store.put(x); }
  addAll(xs: string[]): void { for (const x of xs) this.store.put(x); }  // no override path exists
  items(): string[] { return this.store.list(); }
}
// BAD: CountingCart extends BaseCart overriding add (verified 2 -> 0 across base versions) —
// subclass invariant coupled to base internals (addAll calling this.add); base refactor kills it silently
```

### 2) **Coupling budgeted per boundary**

**Definition** — coupling measured per module boundary (afferent = incoming dependents — who breaks if this changes; efferent = outgoing dependencies — what breaks this when *they* change; instability = efferent/(total) — volatile modules should be depended-upon little, stable modules depended-upon widely). Budgets set direction (stable ← volatile per leaf 1.1's cadence rule — dependencies point toward stability), and violations get flagged (volatile module with many dependents = incident scheduled; stable module depending on volatile = inversion missing).

- **Why it matters (correctness)**: unbudgeted coupling concentrates risk invisibly (god-adjacent utility depended upon by 200 modules — one change, 200 blast radii; volatile vendor SDK imported by domain core — vendor churn rewrites rules). Budgets make coupling *visible* (counts per boundary — reviewable numbers, not vibes) and *governable* (new dependencies need justification past thresholds — direction checked: toward stability?). Stable-dependencies principle (depend toward stability) and stable-abstractions principle (stability implies abstractness — volatile concretions hide behind owned seams) complete the picture.
- **Modern guidance** — count couplings per boundary in review (imports in/out per module — numbers beside the code; thresholds team-set, e.g. "core domain: efferent ≤ 3, all abstract"). Direct dependencies toward stability (policy depends on owned abstractions — leaf 2.2; concretions injected at roots). Isolate volatility behind seams (vendor/IO/framework details never imported by domain code — adapters at boundaries, Domain 03's Adapter named early). Re-audit quarterly (coupling drifts with features — budgets enforced continuously or decoratively).

```bash
# GOOD: coupling budgeted and directed (numbers per boundary, direction toward stability)
#  domain core: efferent 2 (Notifier, OrderStore abstractions) <- 47 dependents (stable, abstract).
#  vendor adapters: efferent 5 (SDKs, volatile) <- 1 dependent each (composition root — isolated).
#  new import of SDK into domain core? rejected (direction violation — seam required).
# BAD: "just import it, it's faster" per boundary ("pragmatic") —
# pragmatism unmeasured accrues as 200-dependents-on-volatile; budgets make it visible first
```

### 3) **Inheritance reserved for substitutability**

**Definition** — implementation inheritance permitted exactly where leaf 2.1's contracts hold (subtype honors supertype behaviorally — proven by contract suite, not by `extends` compiling): template-method frameworks (base defines skeleton, subclasses fill *documented* hooks — self-calls specified as extension API, not internals), genuine is-a with coupled evolution (subclass maintained *with* base — same team, same reason to change per leaf 1.1). Everything else composes (delegation first, inheritance last — the default ordering).

- **Why it hurts when missing (correctness, maintainability)**: inheritance-by-default produces taxonomy fantasies (`Manager extends Employee extends Person` — behavior diverges by level three, overrides contradict, LSP fails silently) and reuse-by-inheritance (shared helpers via base classes — coupling every consumer to the helper's evolution). Both rot identically (base edits fracture subclasses eventually — verified 2→0 shape recurring). Reservation converts inheritance from default to decision (proven substitutability or documented framework hooks — stated per hierarchy, reviewed per change).
- **Modern guidance** — ask "substitutable?" before `extends` (contract suite conceivable? — yes with proof → inherit; no/unsure → compose). Document framework self-calls as API (template methods list their overridable hooks *and* their call guarantees — "addAll calls add per element" stated would have prevented the verified incident — or its removal versioned). Prefer final/sealed bases where extension isn't designed (closed by default — leaf 1.2's closedness applied to hierarchies; openness granted per hook, not per class). Review hierarchies for depth (beyond 2–3 levels, substitutability reasoning collapses — flatten via composition).

```typescript
// GOOD: inheritance with documented self-call contract (framework honesty)
// abstract class CartBase {
//   add(x: string): void { this.items.push(x); }
//   addAll(xs: string[]): void { for (const x of xs) this.add(x); }  // DOCUMENTED: calls overridable add
// } // subclasses rely on stated behavior; base changes version the guarantee (leaf 1.2 closedness, applied).
// BAD: deep Manager->Employee->Person hierarchies ("domain modeling") —
// behavior diverges by level three; substitutability unprovable; composition flattens correctly
```

### 4) **Common confusion**

- "Composition is verbose" — delegation boilerplate (forwarding methods) is real but tiny (IDE-generated, one line per method); fragile-base incidents cost orders more (silent wrongness + archaeology). Verbosity priced in keystrokes, incidents in outages.
- "Inheritance models the domain" — inheritance models *substitutability contracts* (leaf 2.1); domain taxonomies model with composition + interfaces (roles composed, not inherited). Taxonomy fantasies break at level three without exception.
- "Coupling metrics are academic" — afferent/efferent counts predict blast radius (verified-shape reasoning: dependents × change-rate = incident surface). Academic names production numbers.
- "Final classes are hostile" — final-by-default is *honest* (extension undesigned → closed; hooks granted explicitly). Hostility is undocumented self-calls, not closed doors.

### 5) **Performance note**

Delegation costs forwarding calls (nanoseconds, JIT-inlined at monomorphic shapes — composition's runtime tax rounds to zero). Inheritance saves those nanoseconds while risking silent-value incidents (verified 2→0 — wrong answers, not slow ones). Coupling budgets cost review attention (counts per boundary — minutes). Optimize incident avoidance (silent wrongness unbounded cost) over call overhead (nanoseconds bounded). Composition wins every performance argument that counts in production.

### 6) **Mentor note**

Reproduce the fragile incident live (2→0 across base versions — "same subclass, same calls, count died in someone else's refactor" converts composition from preference to survival). Drill seam-vs-hierarchy decisions ("substitutable with proof? — else compose" until reflexive). Audit coupling with counts ("dependents? dependencies? direction?" — numbers per boundary). Watch for the taxonomist (deep domain hierarchies — fix with "prove substitutability per level") and the forwarding-grumbler ("verbose" — fix with 2→0 autopsy). Review check: delegation default, inheritance proven-or-documented, coupling counted and directed, juniors can narrate the incident unprompted.
