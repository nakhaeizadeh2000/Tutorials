## 4.1. Foundations checklist (habits mentors insist on)

### 1) **One reason to change, stated**

**Definition** — every module names its change axis in docs ("changes when tax rules change" — leaf 1.1's reviewable name): stated reasons get verified in review (does the code match the name? — drift detected), unstated reasons accumulate silently (god objects grow one "just this" method at a time). The name *is* the contract between author intent and reviewer verification — unnamed modules can't be reviewed for cohesion, only for syntax.

- **What problem it solves**: reason-blind review approves structural decay (methods added where convenient, not where coherent — each PR locally reasonable, globally rotting). Stated reasons convert review from style-checking into architecture-checking ("does this method serve the named reason?" — no sends it elsewhere). Newcomers navigate by names (module purposes readable without archaeology — onboarding measured in hours, not weeks).
- **Modern guidance** — write reason-names in module docs (one line per file/class — the cheapest architectural control). Challenge additions against names in review ("which named reason covers this method?" — none names a new module or a reason update, both explicit). Audit quarterly (reason-names vs actual change history — `git log` per file should show one stakeholder; drift triggers re-split, leaf 1.1's economics restated as routine).

```typescript
// GOOD: reason named, additions judged (reviewable cohesion)
// /** Changes when: tax rules change. Owner: billing team. */
// class TaxPricer { /* pricing methods only — persistence/notification additions rejected with pointer elsewhere */ }
// BAD: "miscellaneous helpers" / "utils" / "managers" (unnamed reasons —
// unreviewable cohesion; every convenience method lands here; god object with humble name)
```

### 2) **Extension without modification**

**Definition** — variation axes carry seams (leaf 1.2's interfaces at predicted change points): new behavior lands in new files (extension-shaped PRs — closed cores untouched, proofs intact), core edits priced by blast radius (callers × tests × exposure — rigor proportional). Second branches trigger extraction (two `if`-kinds tolerated, third mandates strategy — the rule preventing switch fossilization).

- **Why it matters (correctness)**: modification-shaped growth reopens defect windows per feature (tested cores re-earned constantly — green means less each time; merge conflicts centralize on the growing conditional). Extension-shaped growth preserves proofs (untouched code carries test history forward — green means what it meant). The checklist item converts OCP from principle into PR shape (reviewers check *form*: new file vs edited core — visible in the diff stat before reading a line).
- **Modern guidance** — require extension-shaped PRs for new kinds (new implementations, closed cores — diff stat shows additions, not modifications). Price core edits explicitly (blast radius stated in the PR description — callers/tests/exposure computed, rigor matched). Extract at the third branch (switch-count rule — mechanical trigger, no judgment needed). Protect seams mechanically (CODEOWNERS + coverage floors — leaf 1.2's enforcement, restated as routine).

```bash
# GOOD: PR shape checked before code read (form reveals discipline)
#  +120/-0 across 2 new files (extension: closed core untouched — fast review, focused tests).
#  vs +15/-40 in Checkout.ts (core edit: blast radius stated? tests re-earned? canary planned?).
# BAD: "small diff, quick approve" on core modifications ("one line") —
# lines don't price risk (leaf 1.2); blast radius does — unpriced merges invoice in production
```

### 3) **Substitute provably, depend abstractly**

**Definition** — substitutability evidenced (contract suites green per hierarchy — leaf 2.1's matrices, run in CI), dependencies injected (constructors state collaborators — leaf 2.2's explicitness, no hidden `new`), composition default (delegation first — leaf 3.1's ordering, inheritance proven-or-documented). The three together mean: anything swappable *is* swappable in practice (tests prove interchange, seams permit exchange, structure avoids fragile paths) — not just in principle diagrams.

- **Why it hurts when missing (correctness, maintainability)**: unproven substitution fails at integration (plugin architectures where one plugin violates host assumptions — host crashes blamed on framework; test doubles diverging from reals — green suites over lying fakes). Hidden dependencies fail at change time (vendor incident requiring reroute — policy welded to SDK, swap needs refactor under fire). Default inheritance fails at evolution (base refactors fracturing subclasses — verified 2→0 shape recurring). Each is a different facet of unproven interchangeability — the checklist covers all three jointly because systems fail jointly.
- **Modern guidance** — run contract suites per hierarchy in CI (supertype behaviors as shared tests — every subtype green, every PR). Inject at every boundary (composition roots own wiring — policy files never `new` details). Default composition in reviews ("substitutable with proof?" — no/unsure composes; documented framework hooks excepted). Audit `new` + `extends` quarterly (each concrete construction and implementation inheritance re-justified — or refactored to seams/delegation).

```bash
# GOOD: interchangeability evidenced three ways (proven, not diagrammed)
#  contract suites green per hierarchy (substitution proven — leaf 2.1 matrices in CI).
#  constructors inject (dependencies explicit — leaf 2.2 seams, no hidden new).
#  delegation default (fragile paths absent — leaf 3.1 ordering, inheritance proven-or-documented).
# BAD: "loosely coupled" claimed without matrices/seams/delegation ("feels modular") —
# feelings don't substitute under load; evidence does (all three kinds, green, current)
```

### 4) **Common confusion**

- "Checklists replace design judgment" — checklists *trigger* design reasoning at the right moments (reasons named? seams placed? contracts proven?). Judgment executes; checklists route. Both, in that order.
- "Small codebases don't need foundations" — small codebases need *lighter* versions (reason names, one seam per axis, contract tests for hierarchies), not zero: undecomposed small code becomes undecomposable large code (growth without seams fossilizes).
- "SOLID slows down shipping" — SOLID slows *first* features marginally (seam design, reason naming) and accelerates every subsequent one (extension-shaped PRs, focused tests, swappable vendors). Speed measured per feature over quarters, not per file on day one.

### 5) **Performance note**

The checklist costs minutes per module (reason named, seam placed, contract tested) against god-object incidents (blast-radius debugging per edit), modification outages (reopened defect windows), substitution failures (silent-value corruption), and weld-locked incidents (vendor swaps under fire). Highest-leverage item is reason-naming (prevents god-object economics at zero runtime cost); second is extension-shaped PRs (preserves proofs continuously); third is contract matrices (converts interchange from hope to evidence). Minutes preventing rewrites — foundations' best attention rate.

### 6) **Mentor note**

Convert this leaf into the team's design runbook: reasons named, seams placed, contracts proven — every module, every PR, every hierarchy. Quiz juniors on routing ("which checklist item fires for a third switch branch? for a new subtype? for a vendor import?") until answers are environmental. Watch for checklist decay (foundations applied for a sprint, abandoned under deadline — fix with PR-template checkboxes and CI matrices as mechanical teeth) and principle-theater ("SOLID-compliant" claimed without names/seams/matrices — fix with evidence demands per item). Review check: reasons stated, PRs extension-shaped, substitution evidenced — and the mentor's own designs modeling all three visibly.
