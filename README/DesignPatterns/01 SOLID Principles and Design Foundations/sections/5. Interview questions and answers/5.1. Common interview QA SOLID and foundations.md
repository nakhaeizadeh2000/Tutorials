## 5.1. Common interview QA: SOLID and foundations

### 1) **Refactor this god class — narrate axes**

**Definition** — the decomposition screen: a 900-line `UserManager` (auth + billing + notifications + reporting + admin) on the whiteboard, candidate narrating *axes of change* (which stakeholder edits which methods? which cadence each? — leaf 1.1's reasons, discovered aloud), then extracting per axis with seams between (Pricer/Repo/Notifier shape — verified 18/18 behavioral equivalence in our leaves). Graded on *axis discovery* (reasons named before code moves), not extraction speed.

- **What a good answer sounds like**: reasons first ("auth-team edits login flows weekly; billing edits pricing monthly; notifications reword quarterly — three axes, three modules"), seam placement ("extract per axis behind interfaces — callers depend on seams from minute one"), equivalence proof ("behavior preserved — verified 18/18 pattern: same outputs before/after, Facade over pieces where callers need one entry"), cadence note ("weekly experiments no longer queue behind yearly schema reviews" — leaf 1.1's velocity argument, applied).
- **Modern guidance** — interviewers listen for *change-reason thinking* (stakeholders + cadences named unprompted — the analysis that transfers to every decomposition); candidates who split by method-count ("three methods each" — arithmetic without axes) fail the follow-up ("which piece changes when tax rules change?"). Red flags: big-bang rewrite proposals ("rewrite from scratch" — behavior unpreserved, risk unbounded; strangler-extraction wins), duty-count splitting (equal-sized pieces, incoherent axes — reorganization theater).

```bash
# The decomposition answer, structured (leaf 1.1 as interview response)
#  axes (auth-weekly/billing-monthly/notify-quarterly) -> extract per axis + seams
#  -> equivalence verified (18/18 pattern) -> Facade where callers need one entry ([Domain 03/1.2](<../../../03 Structural Patterns/sections/1. Adapters and facades/1.2. Facade simplifying the front.md>)).
#  velocity: weekly experiments unblocked from yearly reviews (cadence argument, priced).
```

### 2) **When would you violate SOLID?**

**Definition** — the judgment question separating principled engineers from dogmatists: pragmatism *with priced trade-offs* (deadlines, prototypes, spikes — violated knowingly, documented explicitly, revisited scheduled) vs dogma (principles regardless of context — velocity sacrificed for purity nobody needed) vs ignorance (violations undiscovered — the actual failure mode). Strong answers name *specific* violations with *priced* reasons and *revisit* triggers.

- **What a good answer sounds like**: priced pragmatism ("prototype week: god object acceptable — single engineer, throwaway code, revisit trigger: second feature touching it; startup MVP: concrete dependencies tolerated — vendor unknown, seam tax premature, revisit at vendor two; hotfix: core edit bypassing review gates — incident clock beats blast radius, retro scheduled Monday"). Each violation: reason stated, cost priced, revisit dated — pragmatism with accounting, not excuses. Then the boundary ("never: substitutability lies (silent-value corruption — leaf 2.1) and secret leaks (irreversible exposure) — some principles don't bend at any deadline").
- **Modern guidance** — grade *trade-off articulation* (costs both sides, revisit triggers, non-negotiables named): candidates who price violations pass; candidates who never-violate (dogma) or always-violate (anarchy) fail opposite halves. Red flags: "SOLID always, no exceptions" (unshipped purity — velocity reality unacknowledged), "principles slow us down" wholesale (god-object invoices unpriced — leaf 1.1's economics unread), no revisit triggers (temporary violations fossilize — scheduled revisits separate pragmatism from decay).

```bash
# The judgment answer, priced (pragmatism with accounting)
#  violate: prototypes (throwaway, revisit at feature 2), MVPs (vendor unknown, revisit at vendor 2),
#           hotfixes (incident clock > blast radius, retro Monday).
#  never: substitutability lies (silent corruption), secret exposure (irreversible), unreviewed core edits.
#  each: reason + price + revisit date (temporary without triggers fossilizes).
```

### 3) **Square-rectangle: inherit or compose?**

**Definition** — the substitutability trap, live: "Square is-a Rectangle — model it" (inheritance bait for the math-minded). Expected answer refuses with evidence (verified 20-vs-25 violation — identical calls, different answers; mutator coupling breaks Rect's independence contract), then composes correctly (siblings under `Shape { area() }` — verified `Square2(5)` = 25, honest separate contract; shared implementation via delegation where reuse genuinely pays — leaf 3.1, no contract inheritance).

- **What a good answer sounds like**: trap recognized ("mathematically yes, behaviorally no — mutable squares aren't mutable rectangles"), evidence cited ("`stretch` returns 20 for Rect, 25 for Square-as-Rect on identical sequences — verified violation, not opinion"), correct model stated ("siblings implementing `Shape` — area contracts separate; composition for shared code, never contract inheritance"), generalization volunteered ("this shape recurs: cached views, convenience subclasses, mutating decorators — coupled mutators under independent contracts, refused everywhere").
- **Modern guidance** — listen for *behavioral* reasoning (contracts compared, not shapes admired): candidates who ask "what are Rect's mutator guarantees?" before answering pass; candidates who answer from geometry ("squares are rectangles") fail the engineering follow-up. Instant fail: "inherit, it's obviously is-a" without contract analysis (the trap working as designed — on the candidate). Follow-up separating senior: "when *would* you inherit here?" (immutable value objects — no mutators, no coupling, substitutability holds trivially — context decides, dogma doesn't).

```bash
# The trap answer, evidenced (leaf 2.1 as interview response)
#  refuse: stretch() 20 vs 25 verified (mutator coupling breaks independence contract).
#  remodel: siblings under Shape (separate honest contracts) + composition for reuse (no contract inheritance).
#  generalize: cached views, convenience subclasses (same shape — coupled mutators, refused everywhere).
```

### 4) **Common confusion**

- Candidates who answer decomposition with method-counts ("split into three equal classes") — axes, not arithmetic (reasons decide boundaries; counts follow).
- "Pragmatism means ignoring principles" — pragmatism means *pricing* violations (reason + cost + revisit); ignoring means undiscovered decay. Accounting separates them.
- Treating square-rectangle as trivia ("heard it before") — reciting the answer without the *contract analysis* fails the generalization follow-up (cached views, same shape, unrecognized).

### 5) **Performance note**

Foundations answers should be compact: decomposition (three minutes — axes, extraction, equivalence, velocity), pragmatism judgment (two minutes — priced violations, non-negotiables, revisits), substitutability trap (two minutes — evidence, remodel, generalization). Candidates who narrate with receipts take the same time as generalizers and prove triple — structure is speed, in foundations interviews as in analysis.

### 6) **Mentor note**

Use Q1 as the decomposition screen (axes named before code moves), Q2 as the judgment screen (priced pragmatism with non-negotiables), Q3 as the contracts screen (evidence over geometry). Rubric: junior — correct moves with reasons attempted; mid — axes/cadences/contracts stated unprompted, equivalence verified; senior — trade-offs priced with revisits, trap generalized to production shapes, dogma refused in both directions. Keep the verified numbers ready (18/18, 100/90, 20/25, 2→0) — receipts separate narrators from memorizers. Red-flag fails: duty-count splitting, unpriced pragmatism, geometry-based inheritance.
