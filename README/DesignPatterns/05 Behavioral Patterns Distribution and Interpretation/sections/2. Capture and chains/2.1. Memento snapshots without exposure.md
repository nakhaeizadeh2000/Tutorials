## 2.1. Memento: snapshots without exposure

### 1) **State captured opaquely**

**Definition** — Memento externalizes state as *opaque tokens* (caretaker holds snapshots — `save()` returns a value it never inspects; `restore(token)` reinstates — originator owns both directions): encapsulation survives saving (private fields never cross the boundary — tokens are black boxes to holders). Verified: `hello` → type `!!!` → save/restore cycle returns `hello` (state captured, mutated, reinstated — contents never exposed to the caretaker).

- **What problem it solves**: state-saving without mementos breaks encapsulation (getters exposing privates for snapshotting — invariants bypassable by any holder; serialization formats freezing internal layouts — refactorings break saved data; friend-access widening — C++-shaped holes in capability discipline). Opaque tokens preserve boundaries (originator defines save/restore — format private, versioned internally; caretakers store/return tokens — capabilities limited to hold-and-give-back). Undo checkpoints, transaction savepoints, and draft states all need saving *without* seeing.
- **Modern guidance** — return opaque snapshots (branded types or closures hiding contents — `save(): Snapshot` where `Snapshot` exposes nothing; holders can't depend on internals they can't see). Version snapshot formats internally (originator migrates old tokens on restore — saved data outlives code versions; migration owned beside the state). Bound snapshot retention (tokens accumulate per save — ring caps or explicit discard; unbounded checkpoints are memory incidents wearing undo).

```typescript
// GOOD: opacity by construction — verified hello!!! → restore → hello
class Editor {
  constructor(private text = "") {}
  type(s: string): void { this.text += s; }
  save(): string { return this.text; }            // token opaque by convention (string payload here —
  restore(snap: string): void { this.text = snap; } // production: branded/structured tokens, versioned)
} // caretaker holds strings, never fields (encapsulation intact across save/restore boundary).
// BAD: getText()/setText() pair "for saving" ("simpler") —
// privates exposed to all holders (invariants bypassable); format frozen publicly (refactors break savers)
```

### 2) **Encapsulation survives saving**

**Definition** — originator-exclusive format knowledge (only the originator constructs/parses snapshots — private fields, version tags, integrity checks all internal): caretakers treat tokens atomically (store, return, discard — never inspect, compare, or fabricate). Verified-shape reasoning: the probe's caretaker (test code) holds a string without knowing it's text (could be JSON, protobuf, encrypted blob — holder code identical). Refactors preserve the boundary (field renames touch originator only — holders recompile untouched).

- **Why it matters (correctness)**: exposed-state saving couples savers to internals (field rename breaks caretakers — blast radius per refactor; version skew between savers/restorers — old snapshots unrestorable after "compatible" changes; fabricated snapshots bypassing validation — invariants unenforceable at restore). Opaque discipline confines all three (format changes stay inside the originator — caretakers recompile clean; versioning lives beside state — migrations owned; fabrication impossible without internals — restore paths validate by construction).
- **Modern guidance** — hide snapshot types maximally (branded opaques — `type Snapshot = string & {__brand}` — construction confined to originator; structural exposure zero). Validate on restore (version tags checked, integrity verified — corrupt/foreign tokens rejected loudly, never applied). Keep caretakers dumb (store/return/discard only — any logic reading snapshot contents migrates into the originator immediately). Test save/restore round-trips per version (current + N−1 formats — migration coverage, not hope).

```typescript
// GOOD: format knowledge confined (originator-only construction/parsing)
// type Snapshot = string & { readonly __snap: unique symbol };  // branded: only originator mints
// save(): Snapshot (version-tagged internally); restore(s: Snapshot) (validates version, then applies).
// caretakers: Map<string, Snapshot> held (atomic tokens — contents unknowable, refactorings invisible).
// BAD: caretakers parsing snapshot JSON ("need to display saved state") —
// format knowledge leaked (refactors break savers); fabrication enabled (validation bypassed structurally)
```

### 3) **Memento vs command-undo split**

**Definition** — two reversal strategies, different trade-offs: *mementos* restore *state* (snapshot before, reinstate after — operation-agnostic: any mutation sequence reversible without knowing what it did); *commands* invert *actions* (Domain 04 §2.2 — `do()`/`undo()` pairs — operation-aware: reversal logic per action). Snapshots cost state-size per checkpoint (large states expensive — differential/journal alternatives where deltas are small); inverses cost design-per-action (each command needs its undo — unimplementable where inverses don't exist: external side effects, one-way functions).

- **Why it hurts when missing (correctness, maintainability)**: mismatched reversal corrupts (command-inverses for non-invertible effects — sent emails "unsent" by deleting logs; snapshots for giant states per keystroke — memory avalanches with typing speed). Each failure traces to strategy mismatch (state-restore where action-inversion fit, or vice versa). The split decides by invertibility (actions with clean inverses → commands; opaque mutations → snapshots) and state size (small states snapshot cheaply; large states journal differentially).
- **Modern guidance** — choose snapshots for opaque/complex mutations (editor buffers, canvas states, configuration wholesale — inverse unknown, state capturable). Choose command-inverses for discrete invertible actions (counters, toggles, list edits — inverse known, state large). Combine where valuable (coarse snapshots + fine command logs between — checkpoints bounding journal replay; databases do exactly this — WAL + snapshots, the industrial pairing). Bound both (snapshot caps + history caps — retention policies stated, never ambient).

```bash
# GOOD: reversal matched to action shape (invertibility + state size decide)
#  counter++/-- (invertible, tiny state) .... command inverses (verified 2->1, Domain 04 §2.2).
#  editor buffer (opaque mutations) ......... snapshots (verified hello-restore; journal between checkpoints).
#  sent email (non-invertible effect) ....... compensating action (apology flow — reversal impossible, honesty required).
# BAD: "undo = restore last snapshot" universally ("uniform") —
# giant-state snapshots per keystroke (memory avalanches); non-invertible effects "restored" cosmetically
```

### 4) **Common confusion**

- "Memento needs caretaker classes" — memento needs *opaque holding* (variables, maps, stacks all qualify — caretaker is a role, not a class). Ceremony without need obscures the one-line pattern.
- "Snapshots duplicate state wastefully" — snapshots cost state-size per checkpoint (priced honestly — copy-on-write/persistent structures share unchanged parts where scale demands; immutable state makes snapshots O(1)-ish structurally).
- "Command-undo subsumes mementos" — inverses cover *known* actions; snapshots cover *unknown* mutations (third-party edits, complex interactions — reversal undesigned). Complementary strategies, different coverage.
- "Serialization equals mementos" — serialization *persists* (formats cross process boundaries — versioning/migration dominate); mementos *checkpoint* (in-memory tokens — opacity dominates). Overlapping mechanics, different contracts.

### 5) **Performance note**

Snapshots cost state-size per checkpoint (verified probes single-digit ms; large states — megabytes per keystroke without bounds — the incident shape); command-inverses cost design-per-action (one-time) + `O(1)` per undo (cheapest reversal where inverses exist); copy-on-write/persistent structures amortize snapshot costs (shared unchanged parts — O(delta) per checkpoint where adopted). Optimize strategy-match first (snapshots vs inverses per action shape), retention bounds second (caps stated), snapshot mechanics third (structural sharing where scale demands).
