## 1.2. Mediator: peers coordinate through hubs

### 1) **Colleagues never address each other**

**Definition** — Mediator centralizes peer communication in a hub (chat users send *through* the hub — verified routed `true`, unknown-recipient `false`, inbox `["a: hi"]`): colleagues know the mediator (one dependency each), never each other (zero peer references — new colleague types arrive without touching existing ones). Topology collapses from N×M peer wirings to N×1 hub spokes (onboarding one colleague touches one file — the hub registration).

- **What problem it solves**: peer-to-peer wiring tangles multiplicatively (chat users addressing users directly — each new type edits all existing types; dialog widgets cross-referencing — enable/disable logic scattered per pair; microservices calling services — dependency graphs only architects fully map). Hubs convert meshes to stars (routing owned once — colleagues evolve independently; topology visible in one file — onboarding reads the hub, not the mesh). Traffic control towers exist because plane-to-plane negotiation doesn't scale — same arithmetic.
- **Modern guidance** — reach for Mediator on peer coordination (chat rooms, dialog control, tower/airport dispatch, team workflows — many-to-many through one brain). Keep colleagues hub-ignorant of each other (peer references forbidden — constructor takes mediator only; peer-to-peer imports rejected in review). Return delivery status explicitly (verified `true`/`false` — routed vs lost distinguished; silent drops are the signature bug, next section's contract). Name hubs after coordination domains (`ChatHub`, `Tower`, `DialogDirector` — topology visible in identifiers).

```typescript
// GOOD: star topology — verified routed/lost/inbox
class ChatHub {
  private users = new Map<string, string[]>();
  join(name: string): void { this.users.set(name, []); }
  send(from: string, to: string, msg: string): boolean {  // hub owns topology + delivery
    const box = this.users.get(to);
    if (!box) return false;                              // unknown recipient: explicit false (verified)
    box.push(`${from}: ${msg}`);
    return true;
  }
  inbox(name: string): string[] { return this.users.get(name) ?? []; }
} // send(a,b) -> true + ["a: hi"] verified; send(a,z) -> false verified (lost, reported).
// BAD: users holding user references ("direct") —
// new colleague type edits all existing types (N×M wiring); topology visible nowhere (archaeology per change)
```

### 2) **N×M wiring collapses to N×1**

**Definition** — without mediator: each of N colleague types addresses N−1 others (N×M wirings — onboarding touches N files); with mediator: each addresses the hub (N spokes — onboarding touches 1 file + hub registration). Verified-shape reasoning from the probe (2 users, hub-mediated — add user `c`: one `join` call; direct-wired alternative: references in `a` *and* `b`). Onboarding cost converts from multiplicative to additive — the economics that justify hubs.

- **Why it matters (correctness)**: mesh wiring rots through coupling density (each peer change ripples to N−1 counterparts — blast radius maximal; circular imports emerge structurally — A→B→C→A untestable in isolation; protocol upgrades fan out per edge — version skew across pairs). Star wiring confines change (peer internals evolve freely — hub contract stable; hub evolves with all peers visible — impact assessable in one file). Coupling *count* is the metric (edges in the dependency graph — mediators minimize it structurally).
- **Modern guidance** — count wirings per onboarding (new colleague touches: hub registration only — one file; more signals mesh residue — refactor toward star). Keep hub contracts minimal (route/deliver/lookup — coordination verbs; business logic lives in colleagues, never the hub — next section's thinness rule). Test topology explicitly (new-type onboarding test: register → communicate → no existing-type edits — the test that proves N×1). Document the star (hub README names members + protocols — topology readable without code archaeology).

```bash
# GOOD: onboarding arithmetic (additive, not multiplicative)
#  new chatter joins: hub.join("c") (1 call, 0 existing-type edits — verified pattern scales).
#  new widget in dialog: register with director (1 file + hub; siblings untouched).
# BAD: "just import the peer directly" per feature ("faster") —
# N×M edges re-accumulate (each shortcut re-meshes); onboarding cost returns to multiplicative
```

### 3) **Hubs stay thin or rot**

**Definition** — mediators route and coordinate *only* (topology + delivery + protocol enforcement); business logic lives in colleagues (message *content* decisions, domain rules, rendering — hub never interprets payloads). Fat hubs recentralize what mediation distributed (god-mediator: routing + validation + transformation + persistence — the god object wearing hub clothes, leaf 1.1-of-01 recurring). Thinness is enforced by code review (hub diffs touching payload semantics rejected — route, don't read).

- **Why it hurts when missing (correctness, maintainability)**: god-mediators become the system's most dangerous file (all traffic flows through — blast radius total; all logic accumulates — merge conflicts per feature; all knowledge centralizes — bus factor one). Teams route *around* fat hubs eventually (direct peer links reappearing — mesh resurrected beside the hub; shadow protocols bypassing validation — correctness split-brained). Thin hubs stay boring (routing tables + delivery + protocol checks — reviewable in minutes); fat hubs become legacy in quarters.
- **Modern guidance** — restrict hubs to routing/topology/protocol (three duties max — stated in hub docs; fourth duty triggers extraction). Push payload logic to colleagues (validation/transformation/rendering at edges — hub passes opaque envelopes). Split god-hubs by subdomain (chat-hub vs notification-hub vs presence-hub — federated mediators coordinating through narrow protocols, never one mega-hub). Audit hub size quarterly (lines-of-hub trending up without member growth = logic accreting — extract on sight).

```typescript
// GOOD: thin hub (routes envelopes, reads nothing)
// send(): topology lookup + delivery + boolean status (3 duties, stated). Payload `${from}: ${msg}` opaque.
// colleagues validate/transform/render (edges own meaning; hub owns movement).
// BAD: validating/transforming/persisting inside send() ("centralized logic") —
// god-mediator forming (all traffic + all logic); bypasses inevitable (peers route around); bus factor one
```

### 4) **Common confusion**

- "Mediator is just an event bus" — event buses *broadcast* (topic fan-out — leaf 2.1-of-04's observer at scale); mediators *coordinate* (directed routing with topology knowledge — recipients addressed, delivery reported). Broadcast vs routed — different guarantees.
- "Hubs are single points of failure" — hubs are single points of *coordination* (failure domain = routing logic — testable, replicable, failover-capable); business logic stays distributed (colleagues fail independently). Distinguish coordination outage (hub down — all traffic pauses, visibly) from logic outage (colleague bug — isolated by hub boundaries).
- "Peer-to-peer is more scalable" — P2P scales *throughput* (no hub bottleneck — BitTorrent shapes); hubs scale *coordination* (topology owned — onboarding/consistency cheap). Throughput vs coordination — different axes, different winners.
- "Small teams don't need mediators" — small teams need *thin* mediators (even a 30-line hub beats N×M imports at 4 colleagues); need grows with peers, not headcount. Four peers already justify the file.

### 5) **Performance note**

Mediators cost one hop per message (hub dispatch — nanoseconds; routing-table lookup, JIT-inlined at stable topologies) plus hub state (member registry — `O(N)` entries, trivial). Mesh alternatives cost per-edge maintenance (human pipeline — onboarding/impact analysis scaling multiplicatively) and protocol drift (per-pair version skew — incident surface). Fat hubs cost central latency (all traffic through one logic mass — contention + blast radius). Optimize topology first (star over mesh — onboarding arithmetic), hub thinness second (routing-only discipline), hop overhead never (nanoseconds, inlined).

### 6) **Mentor note**

Demo onboarding live (add user `c` with one `join` — "zero existing-type edits" converts N×1 from claim to observable). Break delivery-silence deliberately (drop the boolean — "how do senders know?" exposes silent-drop signatures). Bloat a hub on purpose in review exercises ("add validation here" — watch god-mediator form, then extract). Watch for the direct-importer ("faster" peer links — fix with onboarding arithmetic on their roadmap) and the hub-stuffer ("centralized logic" — fix with blast-radius + bus-factor autopsy). Review check: colleagues hub-only imports, delivery statuses explicit, hubs thin (≤3 duties), juniors can onboard peers unprompted.
