## 5.1. Common interview QA: iterator, mediator, memento, chain, visitor

### 1) **Iterator vs Observer — both decouple?**

**Definition** — the decoupling screen: Iterator decouples *traversal from representation* (uniform protocol — clients loop without knowing backing; pull-controlled); Observer decouples *producers from consumers* (fan-out without naming — push-driven). Same word "decouple," opposite directions (client *pulls* through iterators; subject *pushes* to observers). Candidates place per data-flow (polling needs → iterator; eventing needs → observer; both → reactive streams, Domain 06 territory previewed).

- **What a good answer sounds like**: direction first ("who drives — caller pulling (iterator, verified 3–6 yield) or subject pushing (observer, verified fan-out)?"), control second ("pause/zip/merge need pulls — callbacks can't synchronize; lifecycle needs pairing — pulls have none"), combination third ("push-then-pull hybrids: observable streams with iterator operators — the reactive shape, named not built"). Seniors add backpressure (fast producers overwhelm pull-less consumers — bounded buffers/flow-control decide the pattern at scale).
- **Modern guidance** — interviewers listen for *direction analysis* (pull vs push named before mechanics): candidates who ask "who drives here?" pass; candidates who describe both as "loose coupling" fail the control-flow follow-up. Red flags: "use Observer for traversal" (push where pull composes — pause/zip/merge impossible), "use Iterator for events" (polling where push fits — latency floored at interval, CPU burned on unchanged state).

```bash
# The decoupling answer, structured (leaves 1.1 + Domain 04 §2.1 as interview response)
#  caller drives, uniform traversal -> ITERATOR (pulls; verified yields; zip/merge composable).
#  subject drives, fan-out delivery -> OBSERVER (pushes; verified fan-out; pairing mandatory).
#  both (streams with operators)   -> reactive hybrids (Domain 06 territory — named, not built here).
```

### 2) **Middleware pipeline: chain or decorator?**

**Definition** — the layering screen: middleware pipelines (Express/Koa request processing) sit *between* Chain (pass-until-handled with termination contracts — leaf 2.2) and Decorator (wrap-and-stack with order semantics — Domain 03 §2.1): Express-style `next()` chains = Chain (each middleware decides pass/respond — first-response wins, termination by response); wrapping middleware (higher-order handlers adding behavior) = Decorator (composition stacking). Same pipeline shape, different question (routing-to-handler vs layering-around).

- **What a good answer sounds like**: semantics first ("does each layer *decide* (chain — handle-or-pass with termination contract) or *augment* (decorator — wrap with order semantics)?"), Express mapped ("`next()` chains classify (auth→validate→handle — first-response wins; unhandled falls to 404 default — termination contracted)"), error-handling placed (error middleware as chain tail with 4-arity signature — errors route like requests, handled centrally). Then the composition close (wrapping middleware *inside* chain links — decorator-per-link, chain across links — patterns compose, never compete).
- **Modern guidance** — grade *termination awareness* (default handlers named — unhandled requests surface; silent drops rejected): candidates who contract termination pass; candidates who describe pipelines without miss behavior fail the production follow-up. Instant fail: "middleware is just functions in an array" (structure without semantics — pass-vs-wrap undecided, termination uncontracted, order unjustified).

```bash
# The layering answer, structured (leaf 2.2 + Domain 03 §2.1 as interview response)
#  decide-per-layer (auth/validate/handle, first-response wins) -> CHAIN (termination contracted: 404 default).
#  augment-per-layer (logging/timing/retry around)               -> DECORATOR (order semantics stated).
#  composed: decorator-per-link inside chain sequence (both patterns, each at its post).
```

### 3) **Undo: memento or command?**

**Definition** — the reversal screen: snapshots restore *state* (leaf 2.1 — opaque tokens, originator-owned formats, retention bounded) vs commands invert *actions* (Domain 04 §2.2 — `do()`/`undo()` pairs, history stacks, macro composition). Decided by invertibility (actions with clean inverses → commands — arithmetic, toggles, list edits; opaque mutations → snapshots — editor buffers, canvas states) and state size (small states snapshot cheaply; giant states journal differentially).

- **What a good answer sounds like**: invertibility first ("do you *know* the inverse? — counters/toggles yes → commands (verified 2→1); buffer mutations no → snapshots (verified restore)"), size second ("state-size per checkpoint vs per-action design cost — small snapshots win simply; giant states need journals"), composition third ("coarse snapshots + fine command logs between — checkpoints bounding replay; databases do exactly this"). Seniors add non-invertible effects (sent emails — compensating actions, honesty required — reversal impossible, acknowledged).
- **Modern guidance** — listen for *shape-matched* reasoning (invertible→commands, opaque→snapshots, giant→journals): candidates who route by action shape pass; candidates defaulting to one fail half the inputs. Red flags: "snapshots always" (giant-state avalanches per keystroke — memory incidents scheduled), "commands always" (non-invertible effects faked — cosmetic reversal, dishonest history).

```bash
# The reversal answer, structured (leaf 2.1 + Domain 04 §2.2 as interview response)
#  invertible actions (counters/toggles) -> COMMANDS (do/undo pairs; verified 2->1; histories bounded).
#  opaque mutations (buffers/canvas)     -> MEMENTOS (opaque tokens; verified restore; retention capped).
#  non-invertible effects (sent email)   -> COMPENSATION (apology flows — reversal impossible, stated).
```

### 4) **Common confusion**

- Candidates who answer distribution questions with single-object reasoning (iterators without protocol thinking, mediators without topology counting, visitors without kind-stability analysis) — distribution *is* multi-object thinking; solo reasoning misses the pattern.
- "More patterns cited = better answer" — precision beats inventory (right pattern with trade-offs stated outscores five names recited). Routing accuracy is what's screened.
- Treating QA answers as performances (polish over receipts) — verified numbers woven into answers (3–6 yields, fan-out counts, 2→1 undo) separate narrators from memorizers.

### 5) **Performance note**

Distribution QA answers should be compact: decoupling direction (90 seconds — pull vs push with control consequences), layering semantics (two minutes — decide vs augment with termination), reversal routing (two minutes — invertibility + size with composition). Candidates who narrate with verified receipts take the same time as generalizers and prove triple — structure is speed, in distribution interviews as in analysis.

### 6) **Mentor note**

Use Q1 as the direction screen (pull vs push named before mechanics), Q2 as the semantics screen (decide vs augment with termination contracted), Q3 as the routing screen (invertibility + size decide strategy). Rubric: junior — correct patterns with examples; mid — trade-offs stated (order, lifecycle, size) unprompted; senior — composition fluency (decorator-per-link, snapshots-plus-journals, pull-push hybrids), misuses named (silent drops, unbounded histories, kind-churn visitors) without prompting. Keep the verified receipts ready (yields, fan-out, undo counts) — structure narrated with evidence hires. Red-flag fails: direction blindness, termination silence, one-strategy-fits-all reversal.
