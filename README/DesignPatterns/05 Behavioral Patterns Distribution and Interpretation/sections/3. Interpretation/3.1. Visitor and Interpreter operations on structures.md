## 3.1. Visitor and Interpreter: operations on structures

### 1) **Visitors add operations without modifying**

**Definition** — Visitor separates operations from structures via double dispatch (nodes `accept(visitor)` — each kind calls back its own method; visitors implement per-kind logic — `Eval` sums, `Print` parenthesizes): new operations land in new visitor classes (structures closed — zero edits to node kinds), new node kinds cost visitor updates (all visitors extend — the known trade, stated upfront). Verified: one expression evaluates **9** and prints `(2+(3+4))` through the same `accept` seam — operations multiplied, structures untouched.

- **What problem it solves**: operation growth on stable structures otherwise edits every node kind (new operation × N kinds — `instanceof` switches per operation, scattered identically; node-kind additions touch all operations anyway — symmetry of pain). Visitors invert the axis (operations grouped per visitor — eval/print/typecheck each coherent in one file; node kinds stable — closed hierarchies where visitors shine). Compilers, linters, and document processors live here (ASTs stable for quarters, analyses multiplying weekly).
- **Modern guidance** — reach for Visitor on stable-kind/many-operation shapes (ASTs, document models, IR nodes — kinds closed, operations growing). Implement double dispatch literally (`accept` per kind calling `visitKind` — TypeScript overloads or method-per-kind interfaces; the two-call sequence *is* the pattern). Accept the kind-addition tax explicitly (new node kind = update all visitors — priced upfront; visitors suit kind-stable domains, not kind-churning ones). Prefer pattern matching where available (exhaustive `switch` with `never` defaults — visitor-equivalent for closed unions, less machinery).

```typescript
// GOOD: operations multiplied, structures untouched — verified 9 + (2+(3+4))
interface Expr { accept<R>(v: Visitor<R>): R; }   // node kinds: stable, closed (Num/Add)
interface Visitor<R> { num(n: Num): R; add(a: Add): R; }  // operations: open, added freely
class Eval implements Visitor<number> {
  num(n: Num): number { return n.v; }
  add(a: Add): number { return a.l.accept(this) + a.r.accept(this); }  // recursion through seam
} // new operation (Typecheck) = new visitor class (zero node edits — verified pattern scales).
// BAD: operation-switches per node kind ("direct") —
// new operations edit all kinds (scattered); new kinds edit all operations (symmetric pain, no pattern relief)
```

### 2) **Interpreters evaluate small languages**

**Definition** — Interpreter represents grammar rules as classes (expressions above *are* an interpreter — `Eval` executes the language; `Print` renders it): sentences become syntax trees (parsing separate — hand-rolled or generated), evaluation recurses structurally (each node knows its semantics — compositional meaning). Terminals (literals, variables with environments) plus nonterminals (operators combining sub-results) cover small DSLs (config expressions, query filters, rule engines, math input).

- **Why it matters (correctness)**: ad-hoc evaluators entangle parsing with meaning (regex-matched expressions evaluated inline — precedence bugs, associativity errors, untestable semantics; `eval()` on user input — injection by construction). Interpreter separates (parse once → tree; evaluate by recursion — precedence encoded in grammar, not in nested conditionals; each node independently testable). Small languages stay small safely (grammar-sized complexity — bounded, reviewable; `eval()`-shaped holes never open).
- **Modern guidance** — reach for Interpreter on small composable languages (filters, formulas, rules — grammar fits on one page; larger needs parser generators — yacc/antlr territory, not hand-rolled). Separate parse from evaluate strictly (tree produced once — evaluation pure over structure; mixing produces precedence bugs that tests miss). Environment-parameterize variables (lookup maps threaded through — scoping explicit; globals avoided structurally). Prefer existing engines past toy scale (JS engines, SQLite expressions, RegExp — borrowed language machinery beats hand-rolled at production scale/complexity).

```bash
# GOOD: grammar-sized interpreters (parse once, evaluate recursively)
#  filter DSL (status=active AND age>30): parse -> tree (verified Eval-shape recursion); evaluate per record.
#  rule engine: conditions as Expr nodes (new operators = new node kinds + visitor methods — both explicit).
# BAD: eval(userInput) ("expressive") or regex-evaluated expressions ("pragmatic") —
# injection by construction; precedence by accident; semantics untestable (no tree to inspect)
```

### 3) **Cyclic-visit discipline required**

**Definition** — visitors assume acyclic structures (trees/DAGs — recursion terminates by construction; depth bounded by longest path): cyclic graphs need visited-sets (re-entry detection — leaf: Domain 04 §2.2's three-color discipline restated for visitors; infinite recursion on cycles otherwise — stack death, not wrong answers). State the acyclicity assumption per visitor (trees assumed — documented; graphs accepted — visited-set required, implemented, tested).

- **Why it hurts when missing (correctness, maintainability)**: cyclic structures visited naively recurse forever (object graphs with back-pointers — parent links cycle by design; doubly-linked structures — neighbor links loop; prototype chains with cycles — pathological but real). Stack overflow manifests far from the cycle (deep recursion *looks* like big data — misdiagnosed as performance, actually termination failure). Visited discipline converts hangs into traversals (seen-sets per visit — memory for termination, always worth it where cycles are possible).
- **Modern guidance** — assume trees, verify graphs (acyclicity precondition stated — visitors document "trees/DAGs only"; graph inputs get visited-sets unconditionally). Implement seen-sets by identity (object-identity Sets — value equality insufficient for cycles; `WeakSet` where lifetimes allow — GC-friendly visitation). Test cyclic inputs explicitly (back-pointer fixtures — termination proven, not hoped). Prefer iterative visitors past depth risk (explicit stacks — Domain 04 §2.2's spine discipline, restated for visitor recursion).

```typescript
// GOOD: acyclicity stated, cycles guarded (termination proven per input class)
// trees/DAGs: plain recursion (depth-bounded by longest path — stated assumption).
// general graphs: WeakSet visited per visit (re-entry skipped — termination structural, memory GC-friendly).
// cyclic fixture test (back-pointer graph terminates — proven, not hoped).
// BAD: "trees in practice" visitors on graph inputs ("same code") —
// infinite recursion on first cycle (stack death misdiagnosed as performance — termination assumed, unproven)
```

### 4) **Common confusion**

- "Visitor replaces polymorphism" — Visitor *organizes* polymorphic operations (grouped per operation across kinds); method overriding distributes them per kind. Grouping axis differs (operation-coherent vs kind-coherent) — complementary, not competing.
- "Interpreter means parsers" — Interpreter means *tree evaluation semantics* (parsing produces trees — separate concern, often borrowed; evaluation recurses structurally). Parser generators welcome upstream; interpreter pattern downstream.
- "Double dispatch is over-engineering" — double dispatch *is* the visitor mechanism (kind-selected method call — without it, operations switch on kinds manually, reintroducing the scattered conditionals visitors exist to retire).
- "Acyclic assumptions are safe defaults" — safe only where structures guarantee trees (ASTs, composites — by construction); graphs assume cycles until proven otherwise (back-pointers ubiquitous — default visited-sets on graph inputs).

### 5) **Performance note**

Visitors cost double dispatch per node (two virtual calls — nanoseconds each, JIT-inlined at stable hierarchies) plus per-operation code size (one class per operation — files, not runtime); kind additions cost all-visitors updates (the stated trade — infrequent by design-domain choice). Interpreters cost tree-build once + recursive evaluation per run (verified probes single-digit ms at these sizes; parsing dominates evaluation — grammar size decides). Optimize operation grouping first (visitor per coherent operation set), cycle discipline second (visited-sets where graphs possible), dispatch overhead never (nanoseconds, inlined).
