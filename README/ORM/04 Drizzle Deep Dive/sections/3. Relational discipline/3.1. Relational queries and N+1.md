# 3.1. Relational queries and N+1

## 1. with: batches relations (relational queries per path — constant statements, counted)

**Definition** — the batching rule performed Drizzle-specifically (general rule in [Domain 01 §4.1](<../../01 Data Access Foundations and Mental Model/sections/4. Mentor checklist/4.1. **What problem it solves** — the unbatched traversal (per-parent queries beside the client (N+1 wearing Drizzle syntax — batching available via `with:`, declined — loops visible but uncounted ("only a few" growing unboundedly — staging's tens of rows hiding production's ten-thousands); relation-less finds followed by manual assembly (parents fetched, children fetched separately per parent (two queries becoming N+1 by loop — assembly code per feature, mapping bugs per relation); over-`with:` (everything included "just in case" — transfer bloat + multi-list fan-out ([Database Design §4.3](<../../../DatabaseDesign/04 Relationships at Scale/sections/3. Skew and hot relationships/3.1. Hot keys and skew.md>)) — cartesian products on dual list-`with:` (statements few, rows multiplied — sums fictionalized downstream). `with:`-per-path with columns-trimming converts all three (absent→deliberate, looped→batched, bloated→projected).

**Modern guidance** — the strategy lines per relational read (review-enforced — verified live shapes): *with: stated* (relations listed explicitly per query — `with: { orders: true }` (verified live: 1 statement batched (vs 3 looped — delta measured, not hypothesized); *nested composed deliberately* (multi-level `with:` priced per level (joins multiplying — depth examined (2 levels typical max — deeper nesting split into separate batched queries (fan-out controlled); *counts asserted* (statement bounds per list test — ≤N derived from shape — N+1 failing builds (asserted, not hoped); *transfer trimmed* (`columns: {...}` + nested columns (verified live: id,email only — wide rows narrowed — transfer intentional). Missing strategy → request changes; present strategy → verify with counts (asserted, not hoped).

**Common confusion** — *`with:` always prevents N+1 (batching magic).* `with:` batches *declared* paths (verified live — 1 statement); hand loops bypass batching (per-parent queries — N+1 fully manual — verified live — framework unable to help undeclared traversals); multi-list `with:` multiplies transfer (batched statements, combinatorial rows — N+1 absent, fan-out present — different failure, same unexamined strategy). "Always prevents" credits batching with loop prevention (loops unbatched by definition — authorial) and fan-out immunity (transfer unexamined — multiplicative). Batching declared; loops counted; fan-out split — all three, always (same verdict as Prisma 02/2.2 and TypeORM 03/3.1 — restated Drizzle-flavored, permanently).

**Performance note** — with-economics: declared paths cost one statement per query (batched — constant regardless of N — verified live: 1 vs 3 — N+1 immunity structural); hand loops cost N+1 statements (linear — latency scaling with data — batching declined); multi-list `with:` costs combinatorial transfer (statements few, rows multiplied — transfer dominating — split per Database Design 04). Statements bounded via `with:`; transfer bounded via columns/split; counts asserted via tests — three bounds, complete read performance (same triple as siblings — restated, enforced identically).

**Mentor note** — teach "with: per relation" (juniors stating `with:`/columns per relational read design bounded reads on first hearing; unstated relations interrogated ("which relations, and why these?" — strategy demanded per query). Counting demonstrated live once (loop-3 vs with-1 — verified live pattern (counted, not theorized — tangibility converting permanently). State strategies; count always; split fans — read performance in three habits, reviewed per PR.

## 2. Partial selects trim transfer (columns() projections — wide rows narrowed deliberately)

**Definition** — the projection discipline performed Drizzle-specifically: `columns: { id: true, email: true }` in relational queries (verified live — keys id,email only (unneeded columns unfetched — transfer intentional); `db.select({ id: users.id })` partial column lists in builder queries (needed fields only — SELECT-* declined structurally); nested columns trimmings (`with: { orders: { columns: { total: true } } }` — per-level projection (transfer minimized per nesting level — wide child rows narrowed where parents need summaries). Projection trims transfer (bytes billed per row knowingly); SELECT-* ships hope (all columns — needed or not — transfer unexamined).

**What problem it solves** — the SELECT-* duo: *relational bloat* (`with:` fetching full child rows (wide payloads, JSONB blobs, histories — per render, unexamined — transfer billed per row, needed fraction unknown); and *builder SELECT-** (`db.select().from()` unprojected (all columns — future columns auto-included (schema growth widening transfer silently — today's lean query obese tomorrow — unexamined). Projection discipline converts both (relational columns trimmed per path (needed fields — transfer intentional); builder selects listed explicitly (needed columns — schema growth never widening transfer silently). Transfer intentional per query, never hoped per table.

**Modern guidance** — the projection lines per read (review-enforced): *relational columns* (`columns: {...}` per `with:` level — verified live pattern (id,email — needed fields); *builder selects* (explicit column lists (`db.select({ id: users.id, email: users.email })` — needed fields — SELECT-* rejected on sight (transfer hoped — fan-out unexamined); *nested trimming* (per-level columns in nested `with:` (parents slim, children slimmer — summaries over full rows where parents aggregate — transfer minimized per level); *growth-proofing* (new columns excluded by default (explicit lists ignoring additions — schema growth never widening transfer silently — SELECT-* including silently (the asymmetry deciding the discipline). Missing projection where wide rows travel → request changes (transfer intentional or transfer examined — hoped never).

```typescript
// GOOD: projections deliberate — columns listed, transfer intentional (verified live shapes).

// (builder projection — needed fields (new columns excluded by default — growth-proofed).
```

// (wide payloads, histories, blobs — per render, unexamined — transfer billed per row, needed
// fraction unknown). const all = await db.select().from(nusers);  // SELECT-* (all columns —
// future columns auto-included (schema growth widening transfer silently — today's lean query
// obese tomorrow). Projected never; transferred hopefully. Intentional transfer beats hoped bytes.

**Common confusion** — *"projection is premature optimization (fetch all, filter in code)."* Projection trims *transfer* (bytes billed per row per render — network + serialization + memory — measured per hot path, never premature); code-filtering wastes transfer to save keystrokes (all columns shipped, most discarded — bandwidth billed for discarded bytes — memory holding unneeded rows). "Premature" describes tuning unmeasured hot paths (index fiddling pre-evidence); projection describes bounding known transfer (wide rows × hot renders — certainty, not suspicion). Bound transfer (correctness-adjacent — linear bytes are bugs wearing performance costumes); tune on evidence. Project always; filter in database; transfer intentionally.

**Performance note** — projection economics: listed columns cost keystrokes per query (explicit lists — reviewer-visible — transfer intentional); SELECT-* costs transfer per row (all columns — needed fraction unknown — bandwidth billed per render, memory per process); wide-row projections save most (JSONB/blob columns excluded — kilobytes per row avoided — dashboard transfer collapsing). Transfer arithmetic per hot read (columns × rows × renders — priced, never hoped); growth-proofing free (explicit lists ignoring additions — future columns excluded by default). Project deliberately; exclude structurally; transfer intentionally.

**Mentor note** — teach "which columns, and why?" per read (juniors listing needed columns design intentional transfer on first hearing; SELECT-* interrogated ("all columns needed?" — almost never (proven per asking — projections following inevitably). Demonstrate growth-proofing once (new wide column added — explicit lists unaffected (transfer constant); SELECT-* queries widening silently (transfer growing — unexamined). Intentional transfer survives schema growth; hoped transfer degrades with it. List columns; exclude structurally; grow safely.

## 3. Counted like all lists (statement bounds per test — N+1 fails builds, same detector)

**Definition** — the counting rule performed Drizzle-specifically (general rule in [Domain 01 §4.1](<../../01 Data Access Foundations and Mental Model/sections/4. Mentor checklist/4.1. Data-access checklist mentors insist on.md>), Prisma twin in [Domain 02 §3.1](<../../02 Prisma Deep Dive/sections/3. Performance discipline/3.1. Counting universal (all lists, all layers, all tools — same detector, enforced identically — track-wide discipline, never per-tool optional).

**What problem it solves** — the uncounted Drizzle list (client queries assumed batched (`with:` present — transfer unexamined (multi-list fan-out — cartesian products on dual list-`with:`); hand loops beside the client (per-parent queries — N+1 wearing Drizzle syntax — batching available via `with:`, declined); counting absent (tests green on fixtures — linear in production ten-thousands — latency discovered at scale). Counting converts linear latencies to build failures (tests red before merge — N+1 fixed in development); `with:`-strategies convert loops to batches (constant statements — verified live delta: 3→1); projections convert bloat to intent (transfer bounded — columns listed). Counted, batched, projected — complete list performance, Drizzle edition.

**Modern guidance** — the counting lines per list endpoint (review-enforced — verified live pattern): *count* (client-query wrapper in tests (statements per render observed — verified live: 3 looped vs 1 batched — delta measured, not hypothesized); *assert* (bounds per list (≤N derived from shape (1 + fans, never 1 + N) — N+1 failing builds (asserted, not hoped); *strategize* (`with:` per relation path — explicit includes — lazy absent structurally (Drizzle has no lazy loading — unstrategized access *visible* as hand loops, not hidden as magic — loops countable easily); *project* (columns per path — transfer intentional — wide rows narrowed). Missing assertion → request changes; unstrategized loops → batching demanded (`with:` or joins — loops rewritten, never tolerated).

**Common confusion** — *"Drizzle has no N+1 (explicit queries only)."* Explicitness prevents *magic* N+1 (no lazy loading — traversals never hidden — true, structural); hand loops N+1 identically (per-parent explicit queries — N+1 wearing explicitness — verified live: 3 statements looped (explicit loop, linear cost). "No N+1" credits explicitness with batching (explicit loops still linear — visibility aiding detection (loops seen), not preventing (loops still N+1). Explicitness aids counting (loops visible — countable easily); batching prevents (with: — constant); assertions enforce (bounds tested). Visible loops counted; batched paths constant; bounds asserted — explicitness + discipline, never explicitness alone.

**Performance note** — counting economics (same pattern as every QA leaf, Drizzle-evidenced): assertions cost test milliseconds (statement counting per list test — bounded, fast); strategies cost thought per relation (`with:`/columns per path — minutes, once); logging costs log volume (dev-only — negligible). Uncounted equivalents cost linear latencies (page time × data growth — discovered at scale — quarters of remediation: eager rewrites, cache bandages, pagination retrofits). Milliseconds in tests prevent quarters in production — counting ROI unchanged across tools (gauges migrated per major, discipline permanent).

**Mentor note** — teach "count first" with live wrapper (juniors wiring counting wrappers discover N+1 shapes tangibly — 3 vs 1 measured live — counted, not theorized; explicit loops visible (countable easily — visibility aiding detection). Counting taught as reflex ("how many statements?" per list PR — asked until automatic); batching taught as remedy (`with:` per path — loops rewritten); assertions taught as immunity (bounds in tests — N+1 fails builds). Count always; batch deliberately; assert permanently — list performance in three habits, reviewed per PR.
