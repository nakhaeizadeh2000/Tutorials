# 2.2. Migrations via drizzle-kit

## 1. Generate diffs from code (kit generate renders reviewable SQL — read fully)

**Definition** — the generation flow: `drizzle-kit generate` diffs table definitions (code) against migration snapshots (history) and renders versioned SQL files (`drizzle/0000_name.sql` + `meta/_journal.json` — numbered history with snapshots — verified live below: `CREATE TABLE "dz_widgets" (... GENERATED ALWAYS AS IDENTITY ... UNIQUE ...)` rendered without touching any database). Snapshots capture declared state per migration (journal versioned — history reproducible from files alone); diffs render transitions (SQL reviewable — BIGSERIAL-equivalent identity, UQ/PK constraints named — all visible pre-commit).

**What problem it solves** — the undiffed schema change (table definitions edited, SQL hand-written separately (drift between code and migrations — definitions declaring what DDL forgot (columns missing (runtime errors on deploy); constraints absent (integrity hoped); indexes omitted (scans scheduled); or DDL hand-applied bypassing definitions (definitions stale — code lying about schema — type inference built on fiction). Generated diffs convert code changes to reviewed SQL mechanically (definitions diffed — every delta rendered — SQL read fully before applying — drift structurally impossible (single source: code; derivation: SQL; review: humans).

**Modern guidance** — the generation lines (verified live shapes on drizzle-kit 0.31.11): *config* (`drizzle.config.ts` — schema path + out dir + dialect + dbCredentials — reviewed like code (paths correct? dialect matching? credentials scoped? — misconfiguration generating wrong-dialect SQL (MySQL-isms in Postgres migrations — caught at review, never at deploy); *generate* (diffs rendered per schema change — SQL read fully (identity forms visible (GENERATED ALWAYS AS IDENTITY — sequence options explicit); constraints named (UQ/PK reviewed — enforcement intended); downs absent by design (kit migrations forward-only per file — reversibility via new migrations (down discipline differing from TypeORM — forward-fix policy, stated); *journal committed* (meta snapshots versioned alongside SQL — history reproducible (fresh environments building from files alone — snapshots guaranteeing).

```sql
-- GOOD: generated SQL reviewed fully (verified live: drizzle-kit generate output).
CREATE TABLE "dz_widgets" (
	"id" bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY (... START WITH 1 CACHE 1),
	"name" varchar(255) NOT NULL,
	CONSTRAINT "dz_widgets_name_unique" UNIQUE("name")   -- reviewed: enforcement intended
);
-- + meta/_journal.json (version 7, entries indexed — history reproducible from files alone).
-- Reviewer notes: phase EXPAND (additive table — compatible ✓); FKs: none yet (N/A stated).
```

```sql
-- BAD: the unread diff — generated, unreviewed, flag-dayed (real failure shapes, kit edition).
-- (NOT NULL without default on live tables (blocking rewrites — breaking shipped as additive —
-- generator-authored, human-waved). Renames inferred as drop+create (history destroyed with
-- applause — undeclared renames, unwitnessed drops). Missing FK indexes (discipline unapplied
-- through diffs — parent writes scanning). Generated quickly; approved blindly; incidents automated.
-- Tooling trusted; discipline absent. Generate always; approve never-blindly.)
```

**Common confusion** — *"kit diffs replace migration review (automation suffices)."* Diffs automate *detection* (structural deltas captured completely — nothing forgotten); review supplies *judgment* (phases classified, renames declared, indexes verified, witnesses planned — contextual, ungeneratable). "Replace" confuses completeness with correctness (complete diffs of wrong changes — flag-days rendered perfectly — automation executing undesigned transitions flawlessly). Detection automated (gratefully); judgment reviewed (always); confusion never (tooling-trust fails structurally — reviewers reading diffs fully, classifying phases, witnessing contracts).

**Performance note** — generation economics: diff rendering costs seconds (code compared — complete deltas, SQL rendered); review costs minutes per migration (phases/witnesses/indexes checked); hand-authoring costs deltas missed (forgotten columns/indexes/downs — incidents per omission — quarters of archaeology untangling drifted history). Generated-then-reviewed is cheaper *and* more complete than hand-written (seconds + minutes vs hours + omissions). Generate always first; hand-augment for intent (data moves, phased constraints — judgment layered); review everything.

**Mentor note** — teach "read the generated SQL" (juniors reading kit output line-by-line discover generators' assumptions permanently (identity forms, constraint names, missing FK indexes — generated code reviewed like hand code, always). Demonstrate journal mechanics once (snapshots versioned — fresh environments building from files (reproducibility tangible — history trusted because rebuildable). Read diffs; trust journals; review fully — migration literacy in three habits, reviewed per schema PR.

## 2. Push for prototypes, migrate for teams (direct sync vs versioned history — environments decide)

**Definition** — the two application modes: `push` (schema pushed directly to the database — no history files (synchronous, immediate — prototyping velocity: disposable databases converging instantly); `migrate` (versioned SQL applied in order, tracked (`__drizzle_migrations` bookkeeping — pending-only replay — production reproducibility from history alone). Push serves disposability (dev/prototype databases — resettable freely — velocity unblocked); migrate serves durability (shared/staging/production — reviewed history — reproducibility guaranteed). Modes chosen per environment (disposable → push; durable → migrate — never crossed (push against production is synchronize-by-another-name — auto-mutation incidents wearing kit CLI).

**What problem it solves** — the mode confusion duo: *push to shared* (prototyping convenience against team databases (unreviewed DDL applied instantly (flag-day nullability, drop+create renames, missing indexes — incidents at machine speed); history absent (states unrecorded — environments diverging silently (dev pushed differently than staging — bugs environmental, undiagnosable); *migrate-ceremony for prototypes* (versioned history for disposable databases (migration files reviewed for throwaway schemas — process without beneficiaries — velocity taxed per prototype iteration (generate/review/apply cycles for schemas deleted tomorrow). Push where disposable (velocity); migrate where durable (governance) — environments deciding, never habits (push-habit reaching production; migrate-habit slowing prototypes).

**Modern guidance** — the mode lines per environment (enforced, never hoped): *prototypes/dev-disposable* (push permitted (databases resettable — velocity free — schema following code without history files); *shared/staging/production* (migrate exclusively (versioned SQL reviewed (diffs read fully); pending-only application (history replayed, tracked); status/check observed (divergence alerting); *push prohibition past disposable* (linted where feasible (push commands flagged in CI for protected environments — machines tireless); *migration path prototype→team* (push-era schemas baselined into migrations before first governed deploy (history starting honest — generate from current reality, review fully — normal flow after). Missing mode discipline → request changes (push commands in production pipelines fail structurally — auto-mutation incidents preempted).

```sql
-- GOOD: modes per environment — velocity where disposable, governance where durable.
-- Prototype (disposable DB): drizzle-kit push (schema converging instantly — velocity free;
-- reset freely — nothing durable to lose). Team flow: generate (diffs reviewed fully) →
-- migrate (pending-only, tracked — production reproducible from history alone).
-- Prototype→team: baseline push-era reality into migrations (history honest after — normal flow).
-- Check observed (consistency validated — verified live non-mutating run). Verdict: mode per environment.
```

```sql
-- BAD: modes crossed — push to shared, ceremony for throwaways (real failure shapes).
-- drizzle-kit push against staging ("faster than migrations" — unreviewed DDL applied instantly
-- (flag-day nullability (blocking), drop+create renames (history loss), missing indexes (scans) —
-- velocity executing incidents). Or: full migration ritual for weekend prototypes (generate/review/apply
-- cycles for schemas deleted Monday — process without beneficiaries — velocity taxed per iteration).
-- Crossed modes: incidents at machine speed (push-shared) or velocity taxed pointlessly (migrate-disposable).
```

**Common confusion** — *"push is just synchronize with better marketing."* Push and synchronize share immediacy (direct application — no history files); they differ in *intent and tooling* (push: explicit command per sync (deliberate act — reviewed as action, logged); synchronize: automatic per connection (ambient behavior — every boot mutating (typo'd decorators dropping columns fleet-wide — review impossible by design). Explicit-push (deliberate, logged, disposable-scoped) vs ambient-sync (automatic, unlogged, everywhere-configured) — intent differing totally, risk differing accordingly. Push deliberately (disposable only); synchronize never past dev (ambient auto-mutation — prohibited structurally). Deliberation distinguishes; automation endangers.

**Performance note** — mode economics: push costs seconds per sync (direct application — velocity free on disposable DBs); migrate costs minutes per change (generate/review/apply — bounded, calm — fluency making it cheap); crossed modes bill incidents (push-shared: unreviewed DDL at machine speed — quarters each) or velocity (migrate-disposable: ritual per throwaway iteration — toil without beneficiaries). Mode matched to environment durability (disposable→push, durable→migrate — seconds vs minutes correctly budgeted). Match modes; never cross.

**Mentor note** — teach "push prototypes, migrate teams" (juniors internalizing environment-matched modes deploy calmly forever — disposable velocity, durable governance — both served, neither confused). Demonstrate push velocity once (prototype converging instantly — speed tangible); demonstrate migrate governance once (reviewed history replaying — safety tangible). Velocity felt; governance witnessed; modes matched — environment discipline in three habits, reviewed per database touched.

## 3. Check drift scheduledly (consistency validated — history true throughout)

**Definition** — the consistency habit: `drizzle-kit check` validating migration consistency (verified live: non-mutating run completing cleanly — snapshots/journal coherent); drift detection scheduled (snapshot-vs-database comparison surfacing divergence — hotfixes applied directly ("temporarily" — permanent — history fiction compounding per incident); status observed (pending/applied enumerated — expected pendings matching releases — unexpected pendings investigated, never waved). Consistency validated continuously (checks scheduled — divergence alerting); history true throughout (reality == migrations, always — verifiable, enforceable).

**What problem it solves** — the consistency trio: *unvalidated journals* (snapshots drifting from SQL files (hand-edited migrations diverging from snapshots — subsequent diffs fiction-built (deltas computed against false baselines — wrong SQL generated confidently); *uninvestigated drift* (direct DDL bypassing migrations ("urgent hotfix" — history bypassed — subsequent generates building on fiction (deltas wrong — deploys failing mysteriously on foundations nobody mapped); *unobserved status* (pending migrations accumulating (forgotten branches merged with migrations — deploys applying stale intentions — surprises scheduled). Scheduled checks convert all three (journals validated (snapshots coherent); drift investigated fresh (small, fixable — hotfixes reverse-engineered into migrations); status observed (pendings matching releases — unexpected investigated). Consistency scheduled; history true; surprises extinct.

**Modern guidance** — the consistency lines (verified live behaviors + scheduled discipline): *check regularly* (`drizzle-kit check` validating (verified live non-mutating run — snapshots/journal coherent — scheduled in CI (consistency validated per pipeline — drift failing builds, not deploys); *drift investigated fresh* (direct-DDL divergence surfaced early (small, fixable — hotfix reverse-engineered into migration files (history true again) or database restored to history (direction decided per case, recorded always); *status observed* (pending/applied enumerated per environment (expected pendings matching releases — drift failing gates — unexpected pendings investigated, never waved). Missing check → request changes (unvalidated journals drifting silently); drift aged → archaeology scheduled (stale divergence — untangling months of direct DDL — forensics hourly-billed).

```sql
-- GOOD: consistency scheduled — validated, investigated fresh, observed always (verified live run).
-- $ drizzle-kit check (verified live: clean output, non-mutating (0 residue — tables absent after).
-- Snapshots coherent (journal valid — history reproducible). Scheduled in CI (consistency per pipeline).
-- Drift fresh-investigated (hotfixes reverse-engineered (history true) or DBs restored (direction recorded).
-- Status observed (pendings matching releases — unexpected investigated). Ledger true throughout.
```

```sql
-- BAD: consistency hoped — journals unvalidated, drift aged, status unobserved (real shapes).
-- Snapshots hand-edited ("fixing" journal directly — subsequent diffs fiction-built (deltas computed
-- against false baselines — wrong SQL generated confidently). Drift aged (hotfixes direct for months —
-- history fiction compounding per incident — deploys failing mysteriously on unmapped foundations).
-- Status unobserved (pending migrations accumulating (forgotten branches — stale intentions applied as
-- surprises). Hoped per environment; fictional across them. Consistency scheduled or surrendered.
```

**Common confusion** — *"check duplicates CI tests (redundant automation)."* Tests verify *behavior* (features working — green suites); checks verify *history integrity* (snapshots coherent, drift absent, status expected — ledger true). Behavioral green with fictional history ships time bombs (features passing on drifted foundations — deploys failing mysteriously (foundations unmapped — archaeology scheduled). "Redundant" confuses test axes (behavioral vs historical — orthogonal, both required). Test behavior (suites green); check history (ledgers true) — automate both, confuse never.

**Performance note** — consistency economics: scheduled checks cost seconds per pipeline (validation runs — bounded, calm); fresh drift investigation costs minutes per hotfix (small divergences — reversible, fixable); aged drift archaeology costs quarters (stale divergence — untangling months of direct DDL — forensics hourly-billed). Checks scheduled (seconds); drift fresh (minutes); archaeology avoided (quarters saved). Validate continuously; investigate freshly; observe always — consistency cheap, fiction dear.

**Mentor note** — teach "validate history, not just behavior" (juniors checking journals/drift/status design trustworthy pipelines on first hearing; behavior-only testing interrogated ("history true?" — ledger demanded per pipeline). Demonstrate check live once (clean output on coherent history — validation tangible — trust earned by watching guards work, same as P3005/reset-refusal demos). Validate ledgers; investigate drift; observe status — history integrity in three habits, scheduled per pipeline.
