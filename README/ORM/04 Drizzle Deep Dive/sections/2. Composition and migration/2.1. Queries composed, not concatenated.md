# 2.1. Queries composed, not concatenated

## 1. Selects build incrementally (conditions arrays — branches composed, never interpolated)

**Definition** — incremental composition: dynamic queries built as condition arrays (`const conds: SQL[] = []; if (kind) conds.push(eq(...)); ... .where(and(...conds))` — verified live pattern below) — branches contributing conditions (never strings), emptiness handled explicitly (no conditions → unfiltered query (separate call path — `and()` with zero args is degenerate, avoided structurally). Composition replaces concatenation (string branches interpolated per filter — injection per branch, untestable composition, untyped results); conditions arrays preserve all builder guarantees per branch (parameterized, typed, logged — dynamics with discipline, never hope).

**What problem it solves** — the string-branch habit (dynamic filters concatenated (`WHERE 1=1` + appended `AND col = '${v}'` — injection per interpolation (input becoming code — the 2000s never ended here); untestable composition (branch combinations unenumerable — 2^n paths, tested none); untyped results (raw strings returning `any` — refactors breaking at runtime). Conditions arrays convert dynamics to data (branches pushing expressions — combinations composed, not concatenated; parameterized always — injection closed structurally per branch; typed throughout — inference from table definitions, refactors via compiler). Dynamics composed (safe, typed, logged); strings reserved for the genuinely unmappable ([3.1](<../3. Relational discipline/3.1. Relational queries and N+1.md>) fences raw remainder).

**Modern guidance** — the composition lines per dynamic query (review-enforced — verified live shapes): *conditions array* (`SQL[]` typed — branches pushing `eq/like/inArray/isNull` expressions (verified live: kind + prefix filters composing — 1 row returned for both-filters); *emptiness explicit* (zero conditions → separate unfiltered call path (degenerate `and()` avoided structurally — two paths, both typed — empty-filter semantics stated, never accidental); *parameterized always* (expressions binding values (`eq(col, userInput)` — `$n` parameters — user input never concatenated (interpolation absent — injection impossible structurally); *logged like all SQL* (composed statements visible per render — surprises pre-merge — dynamics observed identically to statics (no dark branches).

```typescript
// GOOD: dynamics composed — branches as data, emptiness explicit, all typed (verified live: 0.45.3).
const conds: SQL[] = [];
if (kind !== undefined) conds.push(eq(ditems.kind, kind));       // branch contributes expression
if (prefix !== undefined) conds.push(like(ditems.name, `${prefix}%`));  // value BOUND ($n — never interpolated)
const rows = conds.length > 0
  ? await db.select().from(ditems).where(and(...conds)).orderBy(desc(ditems.id)).limit(10)
  : await db.select().from(ditems).orderBy(desc(ditems.id)).limit(10);   // empty explicit (separate path)
// Live: both-filters → 1 row ("alpha"); unfiltered → all rows. Composed, parameterized, logged.
```

```typescript
// BAD: dynamics concatenated — injection per branch, combinations untested, results untyped.
// let q = `SELECT * FROM dzitems WHERE 1 = 1`;
// if (kind) q += ` AND kind = '${kind}'`;      // interpolation (input becomes code — injection structural)
// if (prefix) q += ` AND name LIKE '${prefix}%'`;  // untestable composition (2^n branch combos — tested none)
// const rows = await db.execute(sql.raw(q));  // untyped (any rows — refactors breaking at runtime —
// unlogged-structured (dark SQL — budgets blind). Branches interpolated; combinations untested;
// results untyped. Concatenation itemized; composition declined.
```

**Common confusion** — *`$dynamic()` is required for conditional queries (special API).* Conditions arrays compose statically-typed queries without special APIs (verified live pattern — plain `.where(and(...conds))` — no `$dynamic()` needed for branch-conditional filters); `$dynamic()` (builder method — verified absent as export in 0.45 (research unit: `$dynamic: false` as named export — method form on builders where supported) serves *reusable partial-query* composition (base query extended across functions — advanced pattern, rarely needed). "Required" overstates (arrays suffice for filter dynamics — the common case, fully typed); method form serves query-fragment reuse (uncommon — reached for deliberately, never by default). Arrays default; methods deliberate.

**Performance note** — composition economics: parameterized branches plan-stably (bound values — plan reuse across filter combinations — interpolated strings replanning per distinct text (parse overhead per combination — plan cache defeating); typed results refactor safely (column changes breaking at compile — velocity preserved); logged statements profiled per combination (hot filter-combos EXPLAINed — Databases 06 mechanics — slow combos optimized with evidence). Composition costs array lines (branches as data — reviewer-visible); concatenation costs replans + risk (parse overhead per string + injection surface per branch). Compose data; concatenate never (except fenced raw remainder — [3.1](<../3. Relational discipline/3.1. Relational queries and N+1.md>)).

**Mentor note** — teach "branches push, never interpolate" (juniors composing conditions arrays design safe dynamics on first hearing; interpolating branches interrogated ("parameterized how?" — binding demanded per branch). Demonstrate injection once (interpolated filter exploited in staging (`' OR '1'='1` returning all rows — faces paling, conversion permanent); composed equivalent immune (bound parameters — same input harmless — contrast tangible). Push conditions; bind values; log statements — dynamics discipline in three habits, reviewed per dynamic query.

## 2. Joins explicit per query (leftJoin with on-conditions — assembly visible, transfer intentional)

**Definition** — the join rule performed Drizzle-specifically (general rule: undeclared combinations joined explicitly (never looped — loops assembling what one join serves is N+1 by choice); declared relations read via `db.query...with:` ([1.2](<../1. Schema as code/1.2. Relations declared beside tables.md>) — navigability declared); ad-hoc combinations joined per query (`leftJoin(users, eq(...))` with on-conditions — assembly visible in the statement (transfer intentional — columns selected explicitly, never SELECT-*-joined). Joins explicit (conditions stated — assembly reviewable); loops rejected (batching declined — rewrite to joins); `with:` preferred where declared (relations API over manual joins — convenience where navigability exists).

**What problem it solves** — the assembly duo: *loops where joins serve* (per-parent queries assembling multi-entity screens (N+1 wearing builder syntax — batching available via joins or `with:`, declined — loops visible but uncounted ("only a few" growing unboundedly); and *SELECT-*-joins* (joined queries fetching all columns of all tables (transfer bloated — wide rows × joined multiplicity — fan-out transfer ([Database Design §4.3](<../../../DatabaseDesign/04 Relationships at Scale/sections/3. Skew and hot relationships/3.1. Hot keys and skew.md>)) — joined shapes unprojected (columns unexamined — transfer hoped). Explicit joins with selected columns convert both (loops → joins (constant statements); SELECT-* → projections (transfer intentional).

**Modern guidance** — the join lines per multi-entity query (review-enforced): *join where undeclared* (combinations without declared relations — explicit `leftJoin` with on-conditions (assembly visible — transfer intentional); *`with:` where declared* (navigability existing — relations API preferred (convenience + batching — manual joins duplicating declared paths rejected (redundant assembly — declared paths maintained once); *project always* (columns selected explicitly (needed fields only — SELECT-* joined rejected on sight (transfer hoped — fan-out unexamined); *fan-out checked* (multi-list joins multiplying — split per Database Design 04 rule (cause removed) or accept documented (transfer priced, sums never computed over products).

```typescript
// GOOD: joins explicit — conditions stated, columns projected, fan-out checked (shapes verified).
const rows = await db.select({ orderId: orders.id, customerEmail: users.email })
  .from(orders)
  .leftJoin(users, eq(orders.customerId, users.id));   // on-condition explicit (assembly visible)
// Columns projected (needed fields only — transfer intentional — SELECT-* declined structurally).
// Multi-list joins: split per Database Design 04 (fan-out cause removed) or accept documented.
```

```typescript
// BAD: loops where joins serve + SELECT-* where projections serve (extremes, both wrong).
// const orders = await db.select().from(ordersTable);
// for (const o of orders) o.customer = await db.select().from(users).where(eq(users.id, o.customerId));
// (N+1 assembling what one join serves — loops where joins belong — batching declined.)
// Or: .select().from(orders).leftJoin(users, ...).leftJoin(lines, ...)  (SELECT-* joined —
// transfer bloated (all columns all tables); fan-out multiplying (lists × lists — sums fictionalized
// downstream). Loops unbatched; projections untrimmed. Join explicitly; project always.)
```

**Common confusion** — *explicit joins duplicate `with:` relations (redundant APIs).* `with:` serves *declared* navigability (relations registered — convenience + batching — declared paths); joins serve *undeclared* combinations (analytics across unassociated tables, multi-entity assembly without relations, conditional traversals — control per query). Overlap misleads (both fetching related rows — different contracts: declared-navigable (maintained once, served often) vs composed-explicit (assembled per need, controlled fully). Duplication would re-implement declared paths as manual joins (redundant assembly — maintained twice, drifting); proper use separates (declared → `with:`, undeclared → joins). Declare navigability; join combinations; duplicate never.

**Performance note** — join economics: explicit joins cost one query (vs N+1 loops — latency divided by batching, locks brief); projected columns cost transfer intentionally (needed fields — bytes billed per row knowingly); SELECT-* joins cost transfer hopefully (all columns — bloat per row × fan-out multiplicity — bandwidth billed per render, unexamined). Loops cost linear statements (latency scaling with data); fan-out costs combinatorial transfer (rows multiplied — sums fictionalized). Join explicitly; project always; split fans — multi-entity reads complete, permanently.

**Mentor note** — teach "joins over loops" with live counts (verified live pattern from 03/3.1 (1 query joined vs 1+N looped — counted, not theorized — tangibility converting permanently); builder composition as loop replacement (loops rewritten to joins live in review — batching demonstrated, not described). Count statements; compose joins; project columns — builder fluency in three habits, reviewed per multi-entity query. Joins composed; loops eliminated; transfer intentional.

## 3. Aggregates compose too (groupBy/having/orderBy — analytics without leaving the builder)

**Definition** — the composition ceiling raised: aggregations composed in-builder (`select({ kind, n: sql`count(*)` })` + `.groupBy(kind)` + `.having(...)` — verified live below: per-kind counts returned typed); ordering composed (`orderBy(desc(...))` — deterministic paging — nondeterministic order rejected (unordered + limit paginating lies — page contents shifting — order stated always); raw SQL fragments fenced for the genuinely unmappable (recursive CTEs, window analytics — `sql` template pieces, reasoned, logged — escape discipline from [Domain 02 §3.1](<../../02 Prisma Deep Dive/sections/3. Performance discipline/3.1. N+1 strategies and raw escapes.md>) applied through builder). Analytics without leaving the builder (grouped, ordered, typed — composition complete through reporting queries, raw reserved for recursion/windows).

**What problem it solves** — the aggregation exile duo: *raw analytics* (GROUP BY queries written as strings beside composed CRUD (untyped results (any rows — refactors breaking at runtime); unlogged-structured (dark SQL — budgets blind); injection per dynamic grouping (interpolated GROUP BY columns — injection structural); and *application-side aggregation* (rows fetched ungrouped, reduced in JavaScript (transfer wasteful — millions of rows for dashboard sums — database aggregating in microseconds, application aggregating in seconds + memory). Composed aggregates convert both (groupBy/having/orderBy in-builder — typed, logged, parameterized; database aggregating — transfer O(groups), not O(rows)).

**Modern guidance** — the aggregation lines per reporting query (review-enforced — verified live shapes): *group explicitly* (`.groupBy(cols)` — dimensions stated (per-kind counts — verified live output below); *filter groups* (`.having(...)` — post-aggregation predicates (count ≥ N — HAVING, not WHERE-postprocessing (database filtering — transfer minimal); *order deterministically* (`.orderBy(...)` — unordered + limit rejected (page contents shifting — order stated always); *raw remainder fenced* (recursion/windows via `sql` pieces (reasoned per fragment — "recursive traversal beyond combinators" — logged like all SQL — escape discipline applied). Missing group-by where aggregation needed → request changes (application-side sums rejected — database aggregates, applications render).

```typescript
// GOOD: aggregates composed — grouped, filtered, ordered, typed (verified live on dbprobe).
const grouped = await db.select({ kind: ditems.kind, n: sql`count(*)::int` })
  .from(ditems).groupBy(ditems.kind).having(sql`count(*) >= 1`);
// Live: [{"kind":"tool","n":1},{"kind":"book","n":2}] (verified — grouped, counted, typed).
// Transfer O(groups) (3 rows — not O(rows)); database aggregating (microseconds); types complete.
```

```typescript
// BAD: aggregation exiled — raw strings or application-side sums (extremes, both wrong).
// const rows = await db.execute(sql.raw(`SELECT kind, COUNT(*) FROM dzitems GROUP BY kind`));
// (untyped (any rows — refactors breaking); unlogged-structured (dark SQL — budgets blind).)
// Or: const all = await db.select().from(ditems); const sums = _.countBy(all, "kind");
// (transfer O(rows) for O(groups) answers (millions of rows for dashboard sums — database
// microseconds vs application seconds + memory). Exiled analytics: untyped or wasteful.)
```

**Common confusion** — *"builders can't do real analytics (use raw)." Real analytics spans composition (groupBy/having/orderBy/aggregates — verified live working — typed, logged, parameterized — genuinely sufficient for reporting queries); raw serves the remainder (recursion, windows, exotic operators — reasoned per fragment — fenced, logged). "Can't" describes unlearned combinators (groupBy unknown — raw reached prematurely); genuinely-unmappable is narrower (recursion/windows — stated per fragment). Learn combinators fully (composed analytics covering ~95% of reporting); fence raw remainder (recursion/windows — reasoned, logged). Combinators default; raw deliberate.

**Performance note** — aggregation economics: composed aggregates transfer O(groups) (dashboard sums in rows, not millions — transfer minimal); application-side sums transfer O(rows) (millions for dashboard numbers — bandwidth billed per render, memory per process); raw-string aggregates transfer correctly but untyped/unlogged (right answers, wrong guarantees — refactors breaking, budgets blind). Database aggregation microseconds vs application seconds (measured per hot dashboard — composition winning by orders of magnitude where groups ≪ rows). Compose aggregates; transfer groups; fence remainder.

**Mentor note** — teach "database aggregates, applications render" (juniors grouping in-builder discover transfer economics tangibly — O(groups) vs O(rows) measured live (dashboard latency collapsing — conversion permanent); application-side aggregation interrogated ("transferred how many rows for how many groups?" — waste quantified per query). Group in database; render in application; fence remainder — analytics discipline in three habits, reviewed per reporting query.
