# 1.1. Schema as code

## 1. Tables are values (importable, composable, testable as TypeScript)

**Definition** — code-first schema: tables declared as TypeScript values (`const users = pgTable("users", {...})` — importable across modules (shared table definitions — single source, never duplicated); composable (table references passed to helpers — column sets reused, constraints factored); testable as code (definitions unit-testable — table configs asserted (columns present? types correct?) without databases). Schema lives in `.ts` (versioned with code, refactored via compiler, reviewed like code — no second language, no separate schema files, no drift between declaration dialects).

**What problem it solves** — the schema-language split (Prisma schemas in `.prisma` (second language — editors/configured separately, refactors spanning two syntaxes); TypeORM decorators (TypeScript-embedded but metadata-magic — runtime behavior invisible in source, initiation failures scheduled). Code-first keeps everything in TypeScript (tables as values — imported where needed (migrations via kit reading the same values — single source flowing to DDL *and* queries); columns as expressions (constraints chained fluently — `.notNull().unique()` — intent visible inline); refactors via compiler (column renamed — TypeScript errors everywhere referenced — refactors guided end-to-end, never hoped). One language, zero drift, full inference.

**Modern guidance** — the code-first contract (verified live shapes on Drizzle 0.45.3 this session): *values* (`pgTable(name, columns, indexes)` — table objects exported per domain module — shared imports, never redeclared); *identity* (`.primaryKey()` + `.generatedAlwaysAsIdentity()` for PG identity columns — verified live: omitting identity makes inserts demand `id` explicitly (tsc error TS2769 — the compiler enforcing what the database would reject — explicitness required, never defaulted); *naming* (table/column string names explicit (`pgTable("dz_users", ...)`, `bigint("id", ...)` — database identifiers decoupled from TS variable names (renames safe either side — mapping explicit, never conventional); *inference* (row types from table values (`typeof users.$inferSelect` — refactors renaming columns via compiler across queries — end-to-end types without generation step (zero codegen — build pipeline unmodified — CI seconds saved per build vs generated clients).

```typescript
// GOOD: schema as TypeScript values — imported, inferred, explicit (verified live: 0.45.3 + dbprobe).
import { pgTable, pgEnum, bigint, varchar, timestamp, index } from "drizzle-orm/pg-core";

export const roleEnum = pgEnum("dz_role", ["USER", "ADMIN"]);  // closed set (DB-native enum)

export const users = pgTable("dz_users", {
  id: bigint("id", { mode: "number" }).primaryKey().generatedAlwaysAsIdentity(),
  // ^ identity EXPLICIT (verified live: omitted → tsc demands id on insert (TS2769) — explicitness enforced)
  email: varchar("email", { length: 255 }).notNull().unique(),
  role: roleEnum().notNull().default("USER"),
  createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
}, (t) => [
  index("dz_users_email_idx").on(t.email),  // hot predicate indexed at birth (review-enforced)
]);
// Live: insert({email}) → defaults applied (role USER, createdAt set — verified output).
// Rows inferred (typeof users.$inferSelect — refactors via compiler, no codegen step).
```

```typescript
// BAD: schema as strings — tables untyped, columns guessed, drift scheduled (real shapes).
// const USERS = "dz_users";  // table as string constant (columns unknown — selects untyped (any rows —
// refactors breaking at runtime); constraints undescribed (uniqueness unenforced in code — hoped in DB);
// identity implicit (inserts omitting id failing opaquely — explicitness absent); indexes separate
// (migration archaeology — hot predicates unindexed until incidents). Strings naming tables;
// types absent; drift scheduled. Values carry types; strings carry hope.
```

**Common confusion** — *"code-first means no migrations (schema is code)."* Code-first changes *declaration* (TypeScript values instead of schema files — single language, compiler-checked); migrations still *version transitions* (drizzle-kit diffs values-vs-database — SQL rendered, reviewed, applied — [2.2](<../2. Composition and migration/2.2. Migrations via drizzle-kit.md>) owns the pipeline fully). "No migrations" confuses declaration language with evolution discipline (values still change over time — transitions still need phases/witnesses/reversibility — [Database Design §5.1](<../../../DatabaseDesign/05 Evolution Growth and Partitioning/sections/1. Schema evolution/1.1. Expand and contract migrations.md>) applies through kit-generated SQL identically). Declare in code; evolve via migrations; confuse never.

**Performance note** — code-first economics: zero-generation builds (no codegen step — CI unmodified — seconds saved per build vs generated clients — velocity compounding daily); inference free at runtime (types erased — zero overhead — ergonomics compile-time-only); explicit identity/indexes priced once (declaration lines — reviewer-checked — empty-table builds instant). Undeclared equivalents bill storage (widths unpriced), queries (unindexed scans), quality (typo'd enums branching). Declare completely; generate nothing; infer everything.

**Mentor note** — teach "tables as values" (juniors importing table definitions across modules discover single-sourcing tangibly — one definition, all queries — drift impossible structurally, not disciplinarily). Review tables like code (values named, columns typed, indexes justified — table PRs held to code standards *and* schema standards — both lenses, every definition). Values shared; inference trusted; drift impossible — code-first fluency in three habits, reviewed per table.

## 2. Columns chosen deliberately (types, modes, constraints — parsing decided per column)

**Definition** — the column contract: every column declares type + mode + constraints deliberately — types (`varchar(n)` bounded honestly vs `text` unbounded honestly; `timestamp(withTimezone)` for instants (zones explicit); `numeric` for money (exact, never float); `bigint(mode)` with parsing choice (`mode: "number"` convenient (verified live: id 1, not "1") vs `mode: "bigint"` correct past 2^53 (JS number precision ends — silently wrong arithmetic beyond — correctness over convenience where ids grow unboundedly)); constraints chained (`.notNull().unique().default()` — presence/identity/shape decided inline — reviewed per column, never defaulted).

**What problem it solves** — the defaulted-column trio (unbounded TEXT for bounded strings (300-char titles beside 3MB pastes — storage/index unexamined); naive timestamps (zone-naive instants corrupting across zones — incidents, not microseconds); bigint-as-default-numbers (ids past 2^53 miscomparing silently (`9007199254740993 === 9007199254740992` → true — identity collisions in JavaScript, not the database — correctness evaporating at scale). Deliberate columns convert post-incident patches to pre-merge contracts (bounds honest, zones explicit, parsing chosen — each decided per column with reason recorded (or defaulted consciously — defaults chosen, never inherited blindly).

**Modern guidance** — the column checklist per field (review-enforced — verified live shapes): *text bounds* (`varchar(n)` where bounded (index-efficient, honestly capped); `text` where unbounded (honesty over arbitrary limits — arbitrary caps rejected as false precision); *time zones* (`timestamp(withTimezone: true)` always for instants (verified live pattern — zones explicit — naive timestamps forbidden by review (corruption scheduled otherwise); *numbers* (`bigint` + mode decided (`number` convenient ≤2^53 (verified live: 1 parsed — safe range stated); `bigint` correct beyond (unbounded ids — correctness over convenience — mode chosen per growth forecast, never defaulted); `numeric` for money (exact — float drift declined structurally); *enums* (`pgEnum` closed sets (verified live: USER applied, typos rejected — open sets as relations (growth accommodated without migrations).

```typescript
// GOOD: columns deliberate — bounds, zones, parsing all chosen (verified live shapes).
// varchar("email", { length: 255 }).notNull().unique()  (bounded + identity — enforced from row one)
// bigint("id", { mode: "number" }).primaryKey().generatedAlwaysAsIdentity()
//   (number-parsed (verified live: 1 — convenient AND stated-safe ≤2^53; bigint mode past it))
// timestamp("created_at", { withTimezone: true }).notNull().defaultNow()  (zones explicit — always)
// roleEnum().notNull().default("USER")  (closed + defaulted — verified live output USER)
// numeric for money (exact — float drift declined); pgEnum for closed sets (typos rejected).
```

```typescript
// BAD: columns defaulted — intent absent, patches post-incident (real shapes).
// text("email")  // unbounded + unindexed + non-unique (duplicates accumulating — cleaned quarterly;
// 3MB pastes beside addresses — storage/index unexamined). bigint("id") default mode (string-parsed
// ("1" — math on strings (concatenation instead of addition — "1" + 1 = "11" — correctness incident
// wearing default settings). timestamp("at") naive (zones ambiguous — corruption scheduled).
// Defaults unexamined; intent absent; patches post-incident. Choose per column or bill per row forever.
```

**Common confusion** — *`mode: "number"` is always fine (ids are small)."* Safe to 2^53 (9 quadrillion — sufficient for most tables' lifetimes — stated-safe with the bound named); catastrophic past it (silent miscomparison — identity collisions in JavaScript (joins mismatching, caches poisoning — correctness evaporating without errors (worst failure class: silent + structural). "Always fine" confuses current scale with all scales (growth unexamined — today's thousands, tomorrow's viral billions — mode chosen once, paid forever). State the bound (≤2^53 documented beside number-mode); choose bigint mode past it (correctness over convenience — one generic parameter, permanent safety). Bounds stated; modes chosen; silence never.

**Performance note** — column economics: varchar bounds (index prefix efficiency — bounded strings indexing tighter); number-mode parsing (convenience — zero BigInt friction — arithmetic native); bigint-mode correctness (unbounded safety — correctness priced over convenience); timestamptz (zone-explicit storage — same bytes, unambiguous semantics — free correctness). Undeclared equivalents bill storage (TEXT widths), indexes (unbounded looseness), quality (typo branches, zone corruption, precision collisions). Decide per column (seconds now); bill per row never (absence billed forever).

**Mentor note** — teach "which mode, and why?" per bigint (juniors answering number-vs-bigint with the 2^53 bound internalize precision thinking permanently — parsing chosen, never defaulted). Closed-vs-open drill ("roles: enum or table?" — fixed → enum; growing → relation — 30-second verdicts, drilled per entity — twin of Prisma 02/1.1's and TypeORM 03/1.1's drills, code-flavored). Modes chosen deliberately; growth examined honestly; typos rejected structurally — column discipline in three habits, reviewed per table PR.

## 3. Indexes declared beside tables (hot predicates indexed at birth — review-enforced)

**Definition** — the index discipline, Drizzle-flavored (general rule from [Database Design §4.1](<../../../DatabaseDesign/04 Relationships at Scale/sections/1. Foreign keys at volume/1.1. Foreign keys that survive traffic.md>) — every FK indexed, review-enforced — performed here as table-config indexes): `index()`/`uniqueIndex()` in the table callback (`(t) => [index("...").on(t.email)]` — colocated with table definition — reviewed per table (hot predicates named: FK columns, lookup keys, ordering keys — each justified or explicitly deferred with trigger); composite indexes ordered by dominant traversal (leading column = dominant predicate — [Database Design §4.2](<../../../DatabaseDesign/04 Relationships at Scale/sections/2. Many-to-many and polymorphism/2.1. Junction tables at scale.md>)'s bidirectional rule through index definitions).

**What problem it solves** — the unindexed launch (FK columns without indexes (parent writes scanning — [Database Design §4.1](<../../../DatabaseDesign/04 Relationships at Scale/sections/1. Foreign keys at volume/1.1. Foreign keys that survive traffic.md>)'s freeze, ORM edition — constraints declared, indexes omitted (tooling generating tables without index review — correctness without traffic-safety); lookup keys unindexed (email/username/slug queried per request — seq scans per login — latency linear in users, discovered at scale); ordering keys unindexed (created_at sorts scanning — feeds crawling). Colocated index definitions convert post-incident retrofits (CONCURRENTLY under load — Databases 02 mechanics — hours under traffic) to birth-indexing (empty-table builds — instant — seconds at authoring, never hours under load).

**Modern guidance** — the index lines per table (review-enforced): *FKs indexed* (every relations foreign key — junction directions both (composite PK + reverse — Database Design 04 rules through `index()` definitions); *lookups indexed* (email/username/slug queried per request — uniqueIndex where identity (enforcement + lookup, one structure); *ordering indexed* (created_at sorts — feeds/timelines — composite (predicate + order) where filters combine (leading column = equality predicate, second = order — leftmost-prefix discipline); *reviewed* (hot predicates named per table — each justified (query cited) or deferred with trigger (unindexed-by-decision with revisit date — documented, never omitted-by-oversight). Missing index → request changes; unindexed-by-decision → trigger recorded (revisit dated — growth re-examined, never hoped).

  index("dz_users_email_idx").on(t.email),   // lookup key (per-request queries — point-fast from row one)

**Common confusion** — *"too many indexes slow writes (index sparingly)."* Write amplification per index is real (B-tree maintenance per INSERT — microseconds each — measured, bounded); *missing* indexes cost scans per read (milliseconds-to-seconds per query — recurring, unbounded — reads outnumbering writes 10–1000× in most workloads (write-amplification arithmetic loses to read-scan arithmetic by orders of magnitude). "Sparingly" describes unmeasured frugality (indexes feared without counting — reads suffering measurably); discipline describes priced coverage (hot predicates indexed (reads fast), cold columns unindexed (writes lean) — each decided per workload, never feared globally). Price per predicate (reads × cost vs writes × maintenance); fear never.

**Performance note** — index economics: birth-indexing costs seconds per table (empty builds — instant — reviewer-checked); retrofit costs hours per index under load (CONCURRENTLY builds — I/O under traffic, lag monitored — Databases 02 mechanics); missing indexes cost scans per query (linear latencies — discovered at scale — quarters of remediation). Colocated definitions cost lines (index callback per table — reviewed); deferred indexes cost incidents (freeze/timeout/crawl classes — one per missing index, eventually). Index at birth (seconds); retrofit never; miss never (review-enforced).

**Mentor note** — teach "which predicates, and why?" per table (juniors naming hot predicates (FKs, lookups, orderings — each justified with citing query) design indexed tables on first hearing; unexamined tables interrogated ("queried by what?" — predicates demanded per table). Index audits on legacy tables (unindexed FKs found via catalog queries — [Database Design §4.1](<../../../DatabaseDesign/04 Relationships at Scale/sections/1. Foreign keys at volume/1.1. Foreign keys that survive traffic.md>)'s audit — hits scheduled as incidents prevented). Name predicates; justify indexes; audit legacy — index discipline in three habits, reviewed per table PR.
