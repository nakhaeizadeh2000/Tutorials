# 1.2. Relations declared beside tables

## 1. relations() maps associations (one/many per side — navigability declared)

**Definition** — Drizzle relations: `relations(table, ({ one, many }) => ({...}))` imported from `drizzle-orm` root (verified live: NOT from pg-core — `relations` absent there (import error caught live — root import required); `db.query` relational API requires schema passed (`drizzle(client, { schema })` — verified live: missing schema yields `DrizzleTypeError` (schema generic missing — declared relations invisible without registration). Relations declared beside tables (same module — associations colocated with table values — reviewed per table, never in separate mapping files).

**What problem it solves** — the undeclared association (relations known to developers, unknown to the mapper — graph queries hand-assembled per feature (joins hand-written beside a relations-capable tool — ceremony paid, convenience declined); reverse traversals unservable (one-directional relations — author→books declared, book→author absent — navigation half-built — admin screens traversing backwards unserved); unregistered relations (declared but unpassed to `drizzle()` — `db.query` blind to them (type error at query time — declarations existing, registration missing — half-wired relations failing confusingly). Declared + registered relations convert hand-assembly to `with:` queries (one option per path — batched, typed — graph convenience delivered structurally, not hoped).

**Modern guidance** — the relations lines per association (review-enforced — verified live shapes): *declared* (`relations(dusers, ({ many }) => ({ orders: many(dorders) }))` + reverse `one(dorders→dusers, { fields, references })` — both sides where traversed (navigability declared, never hoped); *imported from root* (`drizzle-orm`, not pg-core — verified live import error otherwise — import paths reviewed (wrong-module imports failing at compile (visible) not runtime (confusing)); *registered* (schema object passed to `drizzle(client, { schema })` — `db.query.*` served only for registered relations (verified live type error otherwise — registration checked per relational query use); *fields/references explicit* (FK columns + referenced columns named per `one` (ownership visible — [Database Design §4.1](<../../../DatabaseDesign/04 Relationships at Scale/sections/1. Foreign keys at volume/1.1. Foreign keys that survive traffic.md>)'s ownership rule through relation options).

```typescript
// GOOD: relations declared, imported, registered — navigable both ways (verified live: 0.45.3 + dbprobe).
import { relations } from "drizzle-orm";   // ROOT import (verified: pg-core lacks it — import error live)
import { pgTable, bigint, varchar } from "drizzle-orm/pg-core";

export const usersRelations = relations(dusers, ({ many }) => ({
  orders: many(dorders),   // forward: user→orders (collection side declared)
}));
export const ordersRelations = relations(dorders, ({ one }) => ({
  customer: one(dusers, { fields: [dorders.customerId], references: [dusers.id] }),
  // reverse: order→customer (fields + references explicit — ownership visible)
}));
const db = drizzle(client, { schema: { dusers, dorders, usersRelations, ordersRelations } });
// ^ registered (verified: missing schema → DrizzleTypeError — declarations invisible unregistered)
const withOrders = await db.query.dusers.findMany({ with: { orders: true } });
// Live: relational with: 2 (verified). Reverse: customer.email read (verified live).
```

```typescript
// BAD: relations half-wired — declared xor imported xor registered (three failure modes, one family).
// import { relations } from "drizzle-orm/pg-core";  // WRONG MODULE (verified live import error —
// TS2305 catching what runtime would confuse — import paths reviewed, never assumed).
// const db = drizzle(client);  // schema unpassed (db.query.* blind — DrizzleTypeError at query time —
// declarations existing, registration missing — half-wired relations failing confusingly).
// One-directional relations (forward declared, reverse absent — author→books served, book→author
// unservable — navigation half-built). Half-wired: declared xor imported xor registered — wholes required.
```

**Common confusion** — *`db.query` vs `db.select` for relations (which one?).* `db.query.*` serves *declared relations* (`with:` per path — batched, typed — relations API for graph reads); `db.select().from().leftJoin()` serves *ad-hoc joins* ([2.1](<../2. Composition and migration/2.1. Queries composed, not concatenated.md>) — explicit per query — undeclared combinations, analytics, multi-entity assembly). "Which" answered by declaration (relations declared → `db.query` (convenience); combinations undeclared → explicit joins (control). Overlap misleads (both fetching related rows — different contracts: declared-navigable vs composed-explicit). Declared → query API; undeclared → joins; confuse never.

**Performance note** — relations-query economics: `with:` paths batched per path (verified live — one round trip per query — constant statements regardless of N — N+1 immunity structural); undeclared combinations hand-joined (explicit joins — control per query — [2.1](<../2. Composition and migration/2.1. Queries composed, not concatenated.md>) performs); unregistered relations erroring (type errors, not slow queries — failure loud, never silent-slowness). Batching declared; joining composed; errors loud — relations performance complete, permanently.

**Mentor note** — teach "declare, import, register" as the relations triple (juniors reciting per association internalize completeness before speed — triple first, fluency follows — twin of Prisma's four-part relations mantra ([Domain 02 §1.2](<../../02 Prisma Deep Dive/sections/1. Schema authoring/1.2. Relations in schema.md>)), Drizzle-flavored). Review relations by triple (declared both sides? imported from root? registered in schema? — structural review in seconds, incompleteness visible instantly). Triple memorized; checklist enforced; relations navigable — three verbs, zero half-wired associations.

## 2. References stay explicit (fields + references options — FK columns named, actions stated)

**Definition** — reference explicitness: every `one()` names `fields` (local FK columns) + `references` (target columns) — ownership visible per association ([Database Design §4.1](<../../../DatabaseDesign/04 Relationships at Scale/sections/1. Foreign keys at volume/1.1. Foreign keys that survive traffic.md>)'s JoinColumn rule, Drizzle-flavored); delete actions stated where the DDL expresses them (Drizzle relations describe navigation — FK actions live in column/table definitions or migrations ([2.2](<../2. Composition and migration/2.2. Migrations via drizzle-kit.md>) — separation: relations navigate, constraints govern — each declared where enforced, never conflated). Explicit references reviewable (FK columns named — strategy-independent); implicit references conventional (naming guessed — environments disagreeing silently).

**What problem it solves** — the implicit-reference trio: *unnamed fields* (relations without fields/references (association resolving by convention — FK guessed (naming strategy dependent — environments disagreeing silently — staging vs production FK names diverging); *actionless relations* (delete behavior undeclared anywhere (relations navigating, constraints defaulting — NO ACTION answering deletes at runtime — surprises scheduled); *conflated layers* (relations expected to enforce (navigation options doubling as constraints — unenforced — hope wearing declaration). Explicit fields/references convert convention to contract (named columns, strategy-independent); stated actions (in DDL/migrations) convert defaults to policy (governed deletes, never runtime surprises); separated layers convert conflation to clarity (navigate here, constrain there — each declared where enforced).

**Modern guidance** — the reference lines per association (review-enforced): *fields named* (local FK columns explicit (`fields: [dorders.customerId]` — verified live pattern — strategy-independent (renames safe either side — mapping explicit); *references named* (target columns explicit (`references: [dusers.id]` — composite FKs listing all columns (order significant — mismatched orders joining wrong — reviewed carefully); *actions stated in DDL* (onDelete/onUpdate in column definitions or migrations ([2.2](<../2. Composition and migration/2.2. Migrations via drizzle-kit.md>) — Cascade/Restrict/SetNull per relationship — both lenses (domain + volume — Database Design 04 rule through Drizzle DDL); *navigability tested* (both directions traversed in integration tests — untested directions assumed working (assumption failing at 3 a.m. — traversal errors in production paths — verified live both directions this session as the standard).

```typescript
// GOOD: references explicit — fields + references named, actions in DDL (verified live shapes).
customer: one(dusers, { fields: [dorders.customerId], references: [dusers.id] }),
// fields: local FK explicit (strategy-independent — renames safe); references: target explicit
// (composite FKs listing all — order significant, reviewed); actions: in column/migration DDL
// (ON DELETE RESTRICT verified live table — engine enforces; relations navigate).
// Bidirectional test: dusers.with.orders AND dorders.with.customer traversed (both verified live).
```

```typescript
// BAD: references implicit — convention trusted, actions floating, layers conflated.
// customer: one(dusers)  // fields/references omitted (FK guessed by convention — naming strategy
// dependent (environments disagreeing silently — staging vs production FK names diverging);
// actions absent everywhere (relations navigating, constraints defaulting — NO ACTION answering
// deletes at runtime — surprises scheduled); relations expected to enforce (navigation options
// doubling as constraints — unenforced — hope wearing declaration). Implicit references guess;
// explicit references contract. Contract always.
```

**Common confusion** — *"Drizzle relations enforce integrity (like FKs)."* Relations *navigate* (query paths declared — traversal served); constraints *enforce* (FK actions in DDL/migrations — engine guaranteeing — [2.2](<../2. Composition and migration/2.2. Migrations via drizzle-kit.md>) performs). "Enforce" describes DDL (ON DELETE actions — engine-executed); relations describe access (fields/references — client-navigated). Conflating them leaves integrity to navigation options (unenforced — orphans accumulating while relations read beautifully). Navigate via relations; enforce via DDL; confuse never — layers distinct, both owned.

**Performance note** — reference economics: explicit fields cost lines (options per association — zero runtime); convention drift costs archaeology (environment-divergent FK names — migrations differing — forensics hourly-billed); stated actions cost thought (policy per relation — minutes, once); defaulted actions cost incidents (NO ACTION surprises — support tickets per delete-blocked user). Review minutes per association (fields/references/actions stated); quarters avoided per incident class (drift/surprise/blocked-states). State references; price actions; separate layers.

**Mentor note** — teach "fields + references, always" (juniors stating both per `one()` design ownership deliberately; omissions interrogated ("which columns?" — explicitness demanded per association). The question generalizes (every association in every mapper answers it — Prisma scalar lists, TypeORM JoinColumns, raw FKs — ownership universal, syntax local). Ask per association; state per schema; review per PR — ownership thinking in three habits, reviewed always.

## 3. Graph queries via db.query (with: per relation — explicit per read, same N+1 discipline)

**Definition** — the relational read rule performed Drizzle-specifically (general rule in [Domain 01 §4.1](<../../01 Data Access Foundations and Mental Model/sections/4. Mentor checklist/4.1. Data-access checklist mentors insist on.md>), Prisma twin in [Domain 02 §2.2](<../../02 Prisma Deep Dive/sections/2. Migrations and client/2.2. Client queries and relations.md>)): `db.query.users.findMany({ with: { orders: true } })` batches relations per path (verified live — 2 orders with user, one round trip); nested `with:` composes multi-level graphs (`with: { orders: { with: { items: true } } }` — depth priced per level (each level a join/batch — depth examined, never hoped); partial selects trim (`columns: { id: true, email: true }` + nested `columns` — transfer minimized, shape precise). Schema declares relations (promises above); queries strategize loads — declaration without strategy impossible to price (navigable but unbudgeted — transfer/statement costs unexamined).

**What problem it solves** — the unstrategized graph read (relations fetched without `with:` decisions (bare `db.query.users.findMany()` — unloaded relations (deliberate? unasked?); hand loops beside the client (per-parent queries — N+1 wearing Drizzle syntax — batching declined where `with:` would serve); over-`with:` (everything included "just in case" — transfer bloat + multi-list fan-out ([Database Design §4.3](<../../../DatabaseDesign/04 Relationships at Scale/sections/3. Skew and hot relationships/3.1. Hot keys and skew.md>)) — cartesian products on dual list-`with:` (statements few, rows multiplied — sums fictionalized downstream). `with:`-per-path with columns-trimming converts all three (absent→deliberate, looped→batched, bloated→projected).

**Modern guidance** — the strategy lines per relational read (review-enforced): *with: stated* (relations listed explicitly per query — `with: { orders: true }` (verified live — 2 orders batched); *columns trimmed* (`columns: {...}` + nested columns (wide rows narrowed — transfer intentional (SELECT id/email, not SELECT * — projection discipline, same as raw); *multi-list caution* (two list-`with:` multiply — fan-out transfer — split queries per Database Design 04 rule (cause removed) or accept documented (transfer priced, sums never computed over products); *counts asserted* (statement bounds per list test — 01/4.1 detector enforced from adoption — N+1 fails builds (hand loops) and fan-out fails review (multi-list `with:` documented). Missing strategy → request changes; present strategy → verify with counts (asserted, not hoped).

```typescript
// GOOD: strategy per relation — with: stated, transfer trimmed, counts asserted (verified live).
const withOrders = await db.query.dusers.findMany({ with: { orders: true } });
// (verified live: orders.length 2 — one round trip, relation batched — strategy performed.)
const slim = await db.query.dusers.findMany({ columns: { id: true, email: true } });
// (projection — orders unfetched (unneeded relations unloaded deliberately — transfer minimal).
// Test: statement counts asserted per list (≤N bounds — N+1 fails builds — 01/4.1 detector).
```

**Common confusion** — *`with:` always prevents N+1 (batching magic).* `with:` batches *declared* paths (verified live — one round trip); hand loops bypass batching (per-parent queries — N+1 fully manual — framework unable to help undeclared traversals); multi-list `with:` multiplies transfer (batched statements, combinatorial rows — N+1 absent, fan-out present — different failure, same unexamined strategy). "Always prevents" credits batching with loop prevention (loops unbatched by definition — authorial) and fan-out immunity (transfer unexamined — multiplicative). Batching declared; loops counted; fan-out split — all three, always (same verdict as Prisma 02/2.2 and TypeORM 03/3.1 — restated Drizzle-flavored, permanently).

**Performance note** — with-economics: declared paths cost one round trip per query (batched — constant statements regardless of N — N+1 immunity structural, verified live); hand loops cost N statements (linear — latency scaling with data — batching declined); multi-list `with:` costs combinatorial transfer (statements few, rows multiplied — transfer dominating — split per Database Design 04). Statements bounded via `with:`; transfer bounded via columns/split; counts asserted via tests — three bounds, complete read performance (same triple as siblings — restated, enforced identically).

**Mentor note** — teach "with: per relation" (juniors stating `with:`/columns per relational read design bounded reads on first hearing; unstated relations interrogated ("which relations, and why these?" — strategy demanded per query). Include audits per hot path (production `with:` reviewed quarterly — unneeded relations trimmed (transfer shrinking), missing relations added (loops batched) — strategies living documents, not birth decisions). State strategies; audit quarterly; assert always — read performance in three habits, reviewed per PR.
