## 1. The N+1 avalanche (loops beside clients — Domains 02–04 strategies unapplied)

**Definition** — the incident: list endpoints firing per-parent queries (1 + N statements — verified live patterns S2–S4 (3-vs-2 Prisma, absent-vs-2 TypeORM, 3-vs-1 Drizzle — deltas measured, not hypothesized); latency linear in data (staging tens hiding production ten-thousands — fixtures unrepresentative (data-scaled thinking absent); discovery via p99 cliffs (averages fine — tails official — p99 alerting where averages reassure). Root cause always structural (unstrategized traversals — includes/relations/with: absent where batching would serve — strategy unexamined, not unknown (all three tools documenting batching — docs unread or unapplied).

**What problem it solves (by cataloging)** — N+1 avalanches recur because each generation rediscovers them (new team, new tool, same hand loops — the cycle from [Domain 01 §4.1](<../../../01 Data Access Foundations and Mental Model/sections/4. Postmortems citing catalog entries close faster (diagnosis pre-written — verify, don't derive); prevention cites the same entry (review ritual from [1.2](<../1. Track synthesis/1.2. **Common confusion** — *"N+1 is a junior mistake (seniors immune)."* N+1 is a *strategy omission* (includes unstated — any author, any level (senior codebases N+1ing identically where review skips strategy lines — expertise not conferring immunity (only assertion conferring it (bounds enforced — regressions failing builds regardless of author seniority). "Junior mistake" blames persons (experience preventing — false (unasserted seniors N+1 identically); structures prevent (assertions failing builds — author-independent immunity). Blame structures, not seniors — assert counts, immunize all levels equally.

**Performance note** — avalanche economics: unbatched lists cost linear latency (page time × data growth — discovered at scale — quarters of remediation: eager rewrites, cache bandages, pagination retrofits); batched lists cost constant statements (verified live deltas — N+1 immunity structural); asserted lists cost test milliseconds (bounds per list — N+1 failing builds); unasserted recurrence costs re-diagnosis per incident (triage repeated — counts/plans re-examined — hours each). Batch structurally (constant); assert permanently (immunity); register fleet-wide (siblings audited). Minutes per list prevent quarters per avalanche.

Stories prevent; assertions detect; parables stick — all three, always.

## 2. The pool exhaustion (defaults × replicas vs limits — Domain 06 sizing unapplied)

**Definition** — the incident: "too many clients" pages under load (connections refused — cascading retries amplifying (retry storms converting saturation to outage — exponential harm, linear cause); arithmetic unexamined (max × instances vs limit − headroom — multiplication unchecked (defaults × replicas exceeding limits — exhaustion by arithmetic ([Domain 06 §1.1](<../../../06 Production ORM Use/sections/1. Connections and transactions/1.1. Pool sizing per tool.md>) unapplied); waits infinite (requests hanging until gateway timeouts — backpressure absent (saturation invisible until cascading); statements unbounded (runaway queries holding connections indefinitely — pool starvation via one statement (service-wide stalls from minimal cause). Root cause always arithmetic (multiplication unchecked — sizing unexamined, never mysterious).

**What problem it solves (by cataloging)** — exhaustion incidents recur because arithmetic feels beneath review (senior engineers configuring pools by default (max 10 "standard" — instances uncounted (50 replicas — multiplication unexamined — limits exceeded fivefold); waits defaulted (infinite hangs — backpressure undesigned); statements unbounded (timeouts unconfigured — runaways unbound). The catalog entry converts rediscovery to reference ("pool exhaustion — see 06/1.1 arithmetic (max × instances ≤ limit − headroom), waits finite, statements bounded — fix: size arithmetically, bound waits/timeouts, isolate workloads"). Postmortems citing catalog entries close faster (arithmetic pre-computed — verify, don't derive); prevention cites the same entry (review ritual — pool lines enforced per service).

**Modern guidance** — the fix sequence (runbook-shaped): (1) **relieve** (shed load — throttle ingress (backpressure imposed emergently — traffic shaped down to pool capacity (breathing room created — firefighting enabled); kill runaways (long-running statements canceled (connections reclaimed — pool refilling); (2) **size** (max × instances vs limit − headroom computed (arithmetic performed under fire — calm math amidst incident (numbers grounding panic); per-tool options configured (adapter/extras/passthrough — sizing owned explicitly); (3) **bound** (waits finite (acquire timeouts failing fast — backpressure honest going forward); statements bounded (timeouts per role — runaways killed structurally); (4) **isolate + register** (workload pools separated where interference measured (noisy neighbors isolated — analytics off OLTP pools); postmortem → pool review ritual (arithmetic per service going forward — exhaustion designed out structurally).

```typescript

// (1) Relieve: throttle ingress (traffic shaped to pool capacity — breathing room); kill runaways
// (long statements canceled — connections reclaimed — pool refilling).
// (2) Size: max × instances ≤ limit − headroom computed (arithmetic under fire — calm math).
// Per-tool options configured (adapter/extras/passthrough — sizing owned explicitly).
// (3) Bound: waits finite (backpressure honest); statements bounded (runaways killed structurally).
// (4) Isolate + register: workload pools separated (interference measured); postmortem → ritual.
// Storm closed, recurrence barred (arithmetic reviewed per service — exhaustion designed out).
```

```typescript
// BAD: the scaling reflex — more connections, bigger pools, larger databases (real failure shapes).
// max raised (more clients hammering saturated database (contention worsening — refused connections
// multiplying — pool growth amplifying saturation (more scanners, same missing capacity).
// Database enlarged (limits raised — arithmetic still unexamined (defaults × replicas growing into new
// ceilings — exhaustion rescheduled, not prevented). Waits/timeouts unconfigured (hangs/runaways
// persisting regardless of size — bigger pools hanging identically (saturation delayed, never designed
// out). Scaling reflexively; arithmetic absent; exhaustion rescheduled (larger numbers, same surprise).)
```

**Common confusion** — *"pool exhaustion needs bigger databases (scale vertically)."* Bigger databases raise limits (headroom increasing — arithmetic improving); unexamined sizing re-exhausts larger limits (defaults × replicas growing into new ceilings — multiplication unchecked at every scale (exhaustion recurring predictably — limits raised, arithmetic skipped); waits/timeouts unexamined (hangs/runaways persisting regardless of size — bigger pools hanging identically (saturation delayed, never designed out). "Bigger" describes limits (raised — headroom gained); sizing describes concurrency (derived — waits bounded, statements timed out). Raise limits *and* size arithmetically (both, always); raise-only reschedules exhaustion (larger numbers, same surprise).

**Performance note** — exhaustion economics: relief costs throttling (shed load briefly — availability dipped, bounded — communicated); sizing costs arithmetic minutes (max/waits/timeouts decided — reviewer-checked); isolation costs connections (dedicated pools consuming limit budget — arithmetic including all pools); unexamined equivalents cost cascading outages (retry storms — exponential harm; hung requests — gateway timeouts; total collapse — partial saturation felling whole services). Bounded waits + retries + fallbacks perform gracefully under saturation (degraded, responsive, self-healing); unbounded equivalents perform catastrophically. Bound everything saturable; ladder everything critical.

**Mentor note** — teach pool exhaustion as *the* arithmetic parable (twin of N+1 avalanches for reads: juniors computing max × instances vs limit design bounded concurrency on first hearing; uncomputed pools interrogated ("max? instances? limit? headroom?" — four numbers, seconds each, unexamined pools returned). Parable pair (avalanches for reads, exhaustion for concurrency — two stories covering the track's twin failure families) told in onboarding week one, referenced per service PR ("arithmetic holds?" — two words ending re-litigation). Stories prevent; arithmetic bounds; parables stick — all three, always.

## 3. The magic upgrade (defaults flipping silently — Domains 02–04 inventories unapplied)

**Definition** — the incident: mapper major upgrade changing behavior silently (relation defaults flipping (N+1 appearing post-upgrade — strategies un re-audited (magic assumed stable — versions moving underneath); observability idioms removed (v7 `$use` gone — counters dead silently (gauges absent since migration — N+1 unobserved exactly when observability lapsed — verified live S2 (breakage demonstrated, not theorized); feature-flagged defaults activating (untested behaviors running production traffic — surprises scheduled). Discovery: green tests (old behaviors passing — coverage green on stale assumptions — novelties unexamined); production behavior drifting (new defaults executing — surprises paging (novelty unreviewed — upgrades unexamined).

**What problem it solves (by cataloging)** — upgrade incidents recur because majors merge on green tests (behavioral coverage passing — defaults flipping unexamined (relation strategies un re-audited (N+1 appearing — magic assumed stable); gauges dead (observability idioms removed — counters absent since migration (N+1 unobserved exactly when observability lapsed — blindness arriving with the upgrade meant to improve things); ledgers fossil (costs priced at adoption — versions moving — stale prices guiding new versions (mismatches compounding). The catalog entry converts rediscovery to reference ("magic upgrade — see 06/2.1 magic re-audit + 06/2.2 upgrade ops (defaults re-listed, gauges re-verified, rehearsals/canaries/rollbacks performed — surprises preempted). Postmortems citing catalog entries close faster (magic named — inventories updated — ledgers re-priced); prevention cites upgrade ritual (rehearse/canary/rollback/re-price per major).

**Modern guidance** — the fix sequence (runbook-shaped): (1) **pin** (rollback to last-known-good major (downgrade rehearsed? — reversibility proven pre-upgrade ideally (unrehearsed rollbacks improvised under fire — downgrade tested live if untested before (reversibility verified, even late); (2) **inventory** (defaults/idioms/APIs re-listed version-to-version (breaking inventoried — surprises named (relation strategies re-verified (N+1 posture intact?); observability idioms current (counters firing?); flags reviewed (new behaviors examined?); (3) **rehearse-then-canary** (staging upgraded with inventoried deltas (gauges compared pre/post — deltas investigated); canary service-by-service (blast bounded — gauges compared per wave — promotion gated on evidence); (4) **register** (ledgers re-priced for new major (costs current — stale prices retired); postmortem → upgrade ritual (rehearse/canary/rollback/re-price per major going forward — magic inventoried continuously, never once-and-done).

**Common confusion** — *"green tests mean safe upgrades (CI passing suffices)."* Tests assert *old* behaviors (written against previous defaults — passing irrelevantly post-change (strategies unexamined (new defaults untested — coverage green on stale assumptions); gauges unwired to new idioms (counters testing removed APIs (passing vacuously — observability dead silently); flags unexamined (new behaviors untested (default paths uncovered — surprises scheduled). "Green" describes old-behavior conformance (regression absent for tested paths); safety requires new-behavior examination (defaults re-listed, gauges re-verified, flags reviewed — audit beyond green). Green necessary (regressions caught); insufficient alone (novelties unexamined). Green + audit; never green-alone (restated from 06/2.1 — permanent value).

**Performance note** — upgrade-incident economics: pinning costs downgrade rehearsal (reversibility proven — failure recovery tested); inventorying costs review minutes per major (defaults re-listed — surprises preempted); rehearsal/canary costs staging hours + baking days (breakage surfacing calmly — blast bounded); ledger re-pricing costs minutes (costs current — decisions evidence-backed). Unexamined equivalents cost upgrade incidents (N+1 appearing (strategies un re-audited); gauges dead (observability lapsed); stranded versions (rollback unknown — forward-fix under fire). Rehearsal hours prevent incident quarters — upgrade insurance with the best ratio in operations (practice cheap, drama dear).

**Mentor note** — teach magic upgrades as *the* version parable (twin of avalanches/exhaustion completing the trio: juniors re-listing defaults per major design upgrade safety on first hearing; unexamined upgrades interrogated ("defaults re-listed? gauges verified? flags reviewed?" — three questions, seconds each, unexamined upgrades returned). Parable trio (avalanches/reads, exhaustion/concurrency, upgrades/versions — three stories covering the track's failure families) told in onboarding week one, referenced per upgrade PR ("magic inventoried?" — two words ending re-litigation). Stories prevent; audits detect; parables stick — all three, always.
