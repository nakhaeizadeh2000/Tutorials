# 2.2. From incidents to prevention

## 1. Postmortems name missing artifacts (which checklist, gauge, or trigger would have caught it)

**Definition** — the data-access postmortem: blameless incident review whose output is *named missing artifacts* — which review line unasked (layer placed? strategy stated? counts asserted? magic inventoried? — [1.2](<../1. Track synthesis/1.2. Review as a practice across tools.md>)'s L-S-C-M); which gauge absent (pool depth? relay lag? statement counts? — [Domain 06 §2.1](<../../06 Production ORM Use/sections/2. Operating mappers/2.1. Production observability per mapper.md>)); which trigger unset (pool threshold? version budget? migration gate? — [Domain 05 §1.2](<../../05 Comparing and Choosing/sections/1. Selection by workload/1.2. Cost ledgers per tool.md>)). "Human error" and "be careful" banned outputs (moral judgments, not artifacts — unrepeatable, unimprovable); missing-artifact lists the only acceptable finding (concrete, assignable, verifiable — incidents converted to checklist deltas).

**What problem it solves** — the moral postmortem ("engineer should have batched includes" — blame without artifact (same engineer batching next time by luck, missing by workload — humans don't scale as controls); "process failed" without naming which line (vague improvement theater — "strengthen reviews" — unmeasurable, unenforced, forgotten by next quarter)). Artifact-naming converts incidents to improvements mechanically (missing strategy line → review template updated; missing gauge → dashboard built with owner; missing trigger → threshold set with runbook). Postmortems producing artifact deltas improve systems; postmortems producing judgments degrade culture (blame suppressing reporting — incidents hidden, learning stopped — the opposite of reliability).

**Modern guidance** — the postmortem template (run within a week, owners present, blameless facilitated): *timeline* (what happened, when — facts, no interpretations (p99 cliff Tuesday, N+1 diagnosed Thursday, batch deployed Friday — sequence, not story); *missing artifacts* (review lines unasked? gauges absent? triggers unset? — each mapped to track leaves ([2.1](<2.1. Classic data-access incidents and their fixes.md>)'s catalog consulted — incident classified first (avalanche/exhaustion/upgrade — known class (fix prescribed) vs novel (new catalog entry written); *deltas* (template updates, gauge dashboards, trigger thresholds — assigned with dates — improvements as tickets, never intentions); *sharing* (story-bank entry written — next promise — team learns without re-experiencing). Facilitation rule: every "should have" sentence rewritten as artifact ("should have counted statements" → "statement-count assertion absent — added to list tests + CI gate"). Language shapes learning; artifacts shape systems.

```typescript
// GOOD: the postmortem output — artifacts named, deltas ticketed, story banked (excerpt).
// Incident: order-list p99 cliff (N+1 avalanche — 1+8k statements (loops beside client — batching declined).
// Missing artifacts: strategy line unasked (includes absent — 01/4.1 detector unenforced); counts unasserted
// (bounds absent — N+1 failing nothing); gauges absent (statements unobserved — surprises scheduled).
// Deltas: strategy template updated (includes required per relation read); counts asserted fleet-wide
// (sibling lists audited — fix class, not instance); gauges dashboarded with owner (statements observed).
// Story banked (next promise): "order-list avalanche" told at onboarding henceforth.
```

```typescript
// BAD: the moral postmortem — judgments rendered, artifacts unnamed, recurrence scheduled (real shapes).
// "Engineer should have used includes. Team must be more careful with queries. Process needs
// strengthening." (Which review line? Unnamed — template unupdated. Which gauge? Unset — dashboard
// unbuilt. Which trigger? Unset — thresholds unconfigured. Story banked? Unwritten — next hire
// re-discovers via identical incident.) Judgments without artifacts; intentions without tickets;
// learning without record. Blame assigned; system unchanged; recurrence certain (same gaps, new quarter).
```

**Common confusion** — *"blameless means no accountability."* Blameless means *system* accountability (artifacts assigned to owners with dates — stronger accountability than blame: verifiable completion vs felt guilt) instead of *personal* accountability theater (blame assigned, system unchanged — accountability performed, learning prevented). Owners own deltas (template updated? gauge dashboarded? trigger set? — checkable); nobody owns guilt (uncheckable, unproductive, reporting-suppressing). Accountability for artifacts, blamelessness for humans — both maximal, never traded (restated from Database Design synthesis — permanent value across tracks).

**Performance note** — postmortem economics: artifact postmortems cost hours (facilitated session + delta tickets — bounded, scheduled); moral postmortems cost culture (reporting suppressed — incidents hidden longer, discovered worse — MTTR growing invisibly); unexamined incidents cost recurrence (same gaps, new quarters — full incident price repaid per recurrence). Deltas compound (each postmortem's template-lines/gauges/triggers preventing classes, not instances — prevention ROI growing per incident *declining*); blame compounds negatively (each moral postmortem suppressing the reports that would have triggered artifact postmortems). Artifact culture pays compound interest; blame culture charges it.

**Mentor note** — facilitate first postmortems visibly well (seniors modeling artifact-naming teach more than any process doc — "which leaf prescribes it?" asked per finding, links collected live). Ban "should have/be careful" in real time (rewrite aloud — facilitation as teaching: every moral sentence converted to artifact sentence publicly demonstrates the habit). Teams experiencing one good artifact postmortem demand them thereafter (learning palpable — deltas ticketed, systems visibly improving); teams experiencing moral ones avoid postmortems entirely (learning absent — process resented). Facilitate excellently once; culture follows.

## 2. Prevention is scheduled (triggers, audits, and drills from every incident — never hoped)

**Definition** — the scheduling rule: every postmortem delta gets a calendar entry (trigger thresholds monitored from date X — pool depth alerts, N+1 count bounds, version budgets; audit sweeps recurring quarterly from date Y — register reviews, magic re-inventories, strategy audits; drills rehearsed monthly from date Z — upgrade rehearsals, rollback drills, kill-switch flips). Prevention *scheduled* (owned, dated, recurring — verifiable: did the audit run? did the drill happen? did the trigger fire-or-hold?) versus prevention *hoped* ("we'll watch for this" — unwatched; "team knows now" — turnover erases; "won't happen again" — famous last words, statistically). Scheduled prevention is verifiable (calendar evidence); hoped prevention is indistinguishable from forgetting (no evidence either way — absence of incidents attributed to improvement, actually luck, until luck expires).

**What problem it solves** — the action-item graveyard (postmortem notes listing improvements, nobody scheduling, all forgotten within a quarter — "enforce strategies" without CI ticket, owner, or date — intention decaying to zero within weeks); and the drill-less team (procedures documented, never rehearsed (upgrade runbooks untested (fails when needed — stale commands, changed topology); rollback drills undrilled (downgrades failing live — reversibility theoretical); kill-switch flips unpracticed (incident response via pipeline anyway — switches decorative). Scheduling converts intentions to events (calendar entries with owners — executed or visibly skipped, never silently forgotten); drills convert documentation to capability (rehearsed procedures working under pressure — tested, not hoped).

**Modern guidance** — the scheduling contract per delta: *triggers* (threshold + gauge + owner + start-date — monitored from the date, firing or holding visibly — unmonitored triggers are hopes with thresholds); *audits* (register sweeps, magic re-inventories, strategy audits — quarterly from date X — calendar invites sent during the postmortem, owners attending); *drills* (upgrade rehearsals, rollback drills, kill flips — monthly-to-quarterly per criticality — rehearsed with notes (what broke in rehearsal? — fixed before incidents); *verification* (deltas confirmed complete — assertions merged? gauges dashboarded? template updated? — postmortem re-opened until deltas land, never closed on intentions). Postmortem status: OPEN until deltas complete (tracking issue, reviewed weekly — closure on evidence, never on meeting adjournment).

```typescript
// GOOD: prevention scheduled — calendar entries, owners, verification (excerpt).
// Trigger: N+1 count bounds (asserted per list — CI failing builds — postmortem stays OPEN until merged).
// Audit: magic re-inventory quarterly from Nov (defaults re-listed — surprises preempted).
// Drill: upgrade rehearsal monthly from Dec (runbook tested — gaps fixed same day).
// Verification: postmortem OPEN (weekly review — closes when all deltas evidence-complete).
```

```typescript
// BAD: prevention hoped — intentions minuted, nothing scheduled (real shapes).
// "Action items: enforce strategies, watch pools, consider gauges." (Tickets? None filed — intentions in
// meeting notes (unread thereafter). Owners? Unassigned — everybody's job is nobody's. Dates? Absent —
// "soon" decaying to never. Verification? None — postmortem closed at adjournment (learning celebrated,
// systems unchanged). Next quarter: identical incident, identical action items, identical hopes.
// Hoped prevention is forgotten prevention with better minutes. Schedule or surrender.)
```

**Common confusion** — *"scheduling prevention is bureaucratic overhead."* (Asked and answered per-tempo across both tracks; restated finally for postmortem deltas.) Scheduled deltas cost calendar entries + verification minutes (bounded, visible); hoped deltas cost recurrence (full incident price per repeat — unbounded, certain). "Overhead" framing counts scheduling seconds while ignoring recurrence quarters — full ledger favors scheduling by orders of magnitude, seventh and final domain, track nearly complete. Schedule deltas; verify completion; close on evidence.

**Performance note** — scheduled-prevention economics close the track's prevention argument finally: triggers firing early convert incidents to tickets (cheap, calm, scheduled responses); audits sweeping quarterly convert decay to maintenance (boring, effective, calendared); drills rehearsing convert procedures to capabilities (working under pressure — tested, not hoped). Unscheduled equivalents convert tickets to incidents (expensive, panicked, paged), maintenance to archaeology (heroic, resented, incomplete), procedures to documentation (untested, failing when needed). Schedule converts cost centers to routines — the operations maturity arc complete, track nearly closed.

**Mentor note** — teach "ticketed or it didn't happen" (juniors leaving postmortems with tickets (numbers, owners, dates) learn improvement-as-workflow; juniors leaving with intentions learn improvement-as-theater). Review postmortem openness weekly (OPEN postmortems listed — deltas progressing? blocked? — attention sustained until evidence-complete). Close postmortems on evidence publicly ("deltas landed — assertions merged, gauges live, template updated — closing with thanks" — closure celebrated as improvement delivered, not meeting ended). Ticketed deltas, evidenced closure, celebrated improvement — culture in three habits.

## 3. Incident stories teach (the story bank habit — war stories per domain, told early)

**Definition** — the story bank: a living collection of team (and track-catalog) incidents told as narratives (situation → surprise → diagnosis → fix → prevention — five beats, five minutes) — three war stories per domain minimum (N+1 avalanches, pool exhaustions, magic upgrades from [2.1](<2.1. Classic data-access incidents and their fixes.md>) seeding the bank; team incidents added post-postmortem), told to every junior early (onboarding week one — stories before schemas: consequences felt before rules learned), retold per relevant review ("counts asserted?" — two words invoking the full parable). Stories are compressed experience (years of incidents in minutes of narrative — the highest-bandwidth teaching medium in engineering).

**What problem it solves** — rule amnesia (checklists followed mechanically — lines checked without comprehension — judgment absent where rules end (novel situations ungoverned — "the template didn't cover it" — correct, templates never cover everything; judgment covers the rest, judgment needs stories)); and experience bottlenecks (seniors' judgment locked in seniors' heads — juniors repeating incidents seniors survived a decade prior — organizational learning rate capped at mentorship bandwidth). Stories transfer judgment (not just rules — *why* rules exist, felt through consequences — comprehension surviving where compliance fades); banks scale transfer (written once, told infinitely — mentorship bandwidth multiplied — juniors learning from incidents they never experienced, seniors teaching without repeating).

**Modern guidance** — the bank habit (build once, tell always): *collect* (postmortem → story-bank entry — five beats, anonymized where sensitive (blameless extends to storytelling — systems, never persons), linked to home-domain leaves); *curate* (three per domain minimum — best-told retained, duplicates merged, outdated retired (fixed systems' stories kept as history — "how we learned pools" — heritage, not clutter)); *tell early* (onboarding week one — avalanches/exhaustion/upgrades before schemas — consequences first, rules as their names); *invoke per review* ("counts asserted? pools sized? magic inventoried?" — two-word invocations carrying full parables — review shorthand with narrative backing); *refresh* (new incidents added post-postmortem — bank living, never finished — stale banks (untouched yearly) signal incident-free luck or report-suppression — investigate which, celebrate or fix accordingly).

```typescript
// GOOD: the bank living — collected, curated, told early, invoked per review (excerpt).
// Bank: avalanche-2024 (loops beside client → p99 cliff → includes + assertions — told onboarding day 2);
// exhaustion-2025 (defaults × replicas vs limits → pages → arithmetic + bounds — invoked per service PR);
// upgrade-2026 ($use removal breaking gauges → N+1 unobserved → events migrated — invoked per major).
// Told early (consequences before rules); invoked briefly (shorthand with backing); refreshed post-incident.
```

```typescript
// BAD: the unbanked team — incidents experienced, learning evaporated (real shapes).
// Avalanche 2024 (fixed heroically — postmortem skipped ("too busy") — knowledge in two heads, both departed).
// Exhaustion 2025 (fixed silently — arithmetic unrecorded — next service defaulting identically).
// Upgrade 2026 (migrated painfully — magic uninventoried — next major surprising identically).
// Juniors repeating all three (unheard stories can't prevent); seniors tired of re-teaching (unbanked knowledge
// re-taught per hire, degrading per retelling — telephone game with incidents). Experienced thrice, learned never.
```

**Common confusion** — *"stories are anecdotes, not engineering."* Anecdotes *illustrate*; parables *transfer judgment* (rules + consequences + emotion — comprehended, retained, applied — cognitive science on narrative memory vs list memory, consistently one-sided). Checklists govern known situations (complete, verifiable — keep them); stories govern judgment (novel situations, trade-off feel, consequence imagination — irreducible to lines). Engineers need both (lists for completeness, narratives for wisdom — the track's pedagogy pairing checklists (§4s) with war stories (§5s) per domain deliberately). Dismissing stories keeps lists and loses wisdom — complete reviews, hollow judgment.

**Performance note** — story economics: banking costs minutes per incident (five beats written post-postmortem — hot context, cheapest capture); telling costs minutes per junior (onboarding hour covering the bank — highest-bandwidth teaching available); invoking costs seconds per review (two-word shorthand — comprehension compressed); unbanked incidents cost recurrence (full incident price per repeat — quarters each). Bank ROI exceeding 1000× on first prevented repeat (minutes banked vs quarters repeated — the track's steepest return curve, stated finally). Stories compound (each telling slightly better — narrators improving); incidents without banks repeat identically (unlearned lessons, full price, every time).

**Mentor note** — become the team's storyteller-in-chief (seniors telling parables well teach more than any documentation — narrative craft as mentorship skill: five beats, vivid consequences, named artifacts, linked leaves — practiced deliberately, performed naturally). Collect others' stories (juniors' incidents banked with credit — storytelling democratized, bank diversified); retire stale ones (fixed systems' stories kept as heritage — "how we learned" — pride, not clutter). Storytelling leadership compounds mentorship (one telling reaches all listeners — bandwidth seniors can't match 1:1). Tell stories; bank them; invoke briefly; teach narrators — culture in four verbs, track nearly complete.
