# 3.1. Cross-tool interview synthesis

## 1. Follow the question across tools (raw → builder → mapper — one answer, three lenses)

**Definition** — the synthesis skill: interview questions answered by *traveling* tools visibly — "how would you fetch users with orders?" answered through raw (hand join — control complete, toil visible), builder (Drizzle composed — dynamics safe, types inferred), mapper (Prisma include / TypeORM relations / Drizzle with: — batching declarative) — each lens applied briefly, transitions narrated ("hand join works — builder composes safer — mapper batches declaratively"), depth allocated by question emphasis (tool-specific loops dwell deep; comparison loops travel widely). Single-tool answers pass single-tool loops; traveling answers pass senior+ loops (breadth with prices, method visible throughout).

**What problem it solves** — the excellent-fragment interview (candidate brilliant on Prisma, silent on Drizzle composition, blank on raw trade-offs — depth without breadth — hired as specialist, rejected for senior-generalist scope); and the shallow-tour interview (all three tools touched in ninety seconds each — breadth without depth — vocabulary parade, no prices anywhere). Traveling answers balance dynamically (dwell where probed — follow interviewer emphasis; touch all lightly — show range; price everywhere — numbers per lens). Interviewers probe depth by dwelling (follow-up questions deepening one lens — answered deeply, then re-broadened unprompted — "deeper on Drizzle composition? gladly — then back to selection"). Depth on demand, breadth by default — the senior interview shape.

**Modern guidance** — the traveling method (same skeleton as [Domain 01 §5.1](<../../01 Data Access Foundations and Mental Model/sections/5. Interview QA/5.1. Common interview QA data-access foundations.md>)'s whiteboard, extended track-wide): (1) *raw* (2 min — hand join, parameterized, typed rows — control complete, toil visible); (2) *builder* (3 min — Drizzle composed (conditions arrays, explicit joins — dynamics safe, types inferred — control retained); (3) *mapper* (4 min — Prisma include / TypeORM relations / Drizzle with: per path (batching declarative — verified live deltas S2–S4 (3→2, absent→2, 3→1 — constant regardless of N); (4) *selection* (2 min — positions mapped per workload (graphs/dynamics/flatness — triggers dated — verdicts temporary, correct for current context); (5) *operations close* (1 min — pools sized, gauges owned, upgrades rehearsed — reliability designed). Transitions narrated ("raw works — builder composes safer — mapper batches declaratively"); prices per lens (numbers everywhere); stopping reasoned (time-boxed breadth, offered depth — "happy to go deeper anywhere").

```typescript
// GOOD (traveling answer, users-with-orders — 12 min narrated, lenses traced):
// "Raw: hand join, parameterized ($1 bound — injection closed), rows typed (control complete —
// toil visible: assembly per query). Builder: Drizzle composed (conditions arrays — dynamics safe;
// explicit joins — assembly visible; types inferred). Mapper: include per path (Prisma/TypeORM/Drizzle —
// verified live deltas S2–S4 (3→2, absent→2, 3→1 — constant regardless of N — batching declarative).
// Selection: graphs earn mappers here (relations traversed — jurisdiction placed); triggers dated.
// Operations: pools sized, gauges owned. Deeper anywhere? (offered — depth on demand, breadth delivered.)"
```

```typescript
// BAD (single-tool brilliance — depth without travel):
// "db.user.findMany({ include: { orders: true } }) — done." (Raw trade-offs? Unstated (control/toil
// unexamined — hand joins never considered (fine here — reasoning absent). Builder alternative?
// Unmentioned (dynamics unexamined — composition unknown). Selection reasoning? Absent (tool assumed —
// jurisdiction unplaced — fashion wearing fluency). Strategies unstated (counts unasserted — N+1
// prevented hopefully, not structurally). Brilliant Prisma; silent Drizzle/raw/selection.
// Depth admired; breadth absent; senior scope unproven. Or the mirror: three tools in three sentences
// (tour without prices — vocabulary parade).)
// Travel default, dwell on demand — T performed live (broad base narrated briskly, deep stem extended
// on follow-ups, re-broadened unprompted after).
```

**Common confusion** — *"senior interviews want deep expertise in one tool."* Staff/senior loops want *T-shaped* depth (one lens deep — dwell where probed, genuine expertise demonstrated — plus all lenses traveled — range proven, prices everywhere). Pure-I candidates (single-tool brilliant) hire as specialists; pure-dash candidates (tour without prices) hire nowhere senior. Travel default, dwell on demand — T performed live (broad base narrated briskly, deep stem extended on follow-ups, re-broadened unprompted after). T-shape performed, not claimed — interviewers grade the shape, not the assertion.

**Performance note** — traveling answers carry per-lens prices (same habit as every QA leaf in this track, seventh and final domain: raw toil priced (assembly per query); builder composition priced (branches safe, types inferred); mapper batching priced (verified live deltas — constant regardless of N); selection priced (ceremony/toil per misfit — triggers dated). Prices prove production contact (unpriced breadth is tourism — visited lenses, lived in none); per-lens numbers prove residence (lived experience per tool — incidents survived, ledgers kept). Tourists describe; residents price — interviewers distinguishing via numbers, always. Price every lens visited; dwell where numbers run deepest.

**Mentor note** — drill traveling answers with phase timing (raw 2min, builder 3min, mapper 4min, selection 2min, operations 1min — timed segments, transitions narrated — same phase-timing prescription as all QA leaves). Grade travel completeness ("which lens skipped?" — skipped lenses fail the exercise regardless of covered brilliance) and transition narration ("raw works — builder safer — mapper batches" — transitions audible, method visible). Timed travel drills convert fragment-experts to traveling seniors in weeks — the final interview transformation, track nearly complete.

## 2. System-design adjacent answers (capacity, evolution, operations in data-access interviews)

**Definition** — the adjacency skill: data-access interview answers extended — briefly, priced — into system-design territory (capacity math beside table shapes (rows/day × widths × horizon — headroom priced ([Database Design §5.2](<../../../DatabaseDesign/05 Evolution Growth and Partitioning/sections/2. Growth and capacity/2.1. Capacity modeling with measured triggers.md>)); migration phases beside tool choices (expand/contract through mappers — zero-downtime by phases ([Database Design §5.1](<../../../DatabaseDesign/05 Evolution Growth and Partitioning/sections/1. Schema evolution/1.1. Expand and contract migrations.md>)); outbox/gauges beside entities (relay surfaces + lag ownership — [Database Design §6.2](<../../../DatabaseDesign/06 Modeling for Operations/sections/2. Coordination out of the database/2.1. Outbox tables designed for relay.md>)). Adjacency demonstrates scope (data-access decisions with systems consequences — stated, priced, owned) without derailing (data access remains the subject — adjacent topics visited (30–60 seconds each), never occupied — depth offered ("happy to go deeper on partitioning"), breadth delivered).

**What problem it solves** — the data-access-in-vacuum interview (tables/queries designed without capacity (500M-row implications unmentioned — "and at scale?" asked late, answered vaguely); without evolution (flag-day migrations assumed — "how do you ship this live?" met with silence); without operations (dual-write notifications proposed — honesty architecture absent). Vacuum answers hire implementers (correct shapes, unexamined consequences); adjacent answers hire owners (shapes with systems envelopes — capacity/evolution/operations priced per shape). Staff loops probe envelopes deliberately ("and the migration?" "and at 10×?" "and the notifications?" — three adjacencies, each expected); vacuum candidates fail all three; adjacent candidates collect all three as scoring opportunities.

**Modern guidance** — the adjacency habit (three envelopes per data-access answer, 30–60 seconds each): *capacity envelope* ("50k/d × 420B × 18mo ≈ 33GB — 7% budget — trigger partition at 80M" — [Database Design §5.2](<../../../DatabaseDesign/05 Evolution Growth and Partitioning/sections/2. Growth and capacity/2.1. Capacity modeling with measured triggers.md>) compressed); *evolution envelope* ("email column ships expand/contract — nullable, backfill chunked, contract witnessed — zero-downtime by phases" — [Database Design §5.1](<../../../DatabaseDesign/05 Evolution Growth and Partitioning/sections/1. Schema evolution/1.1. Expand and contract migrations.md>) compressed); *operations envelope* ("notifications via outbox (relay surface + purge windowed); money audited (mirror); gauges owned (lag, depth)" — [Database Design §6](<../../../DatabaseDesign/06 Modeling for Operations/README.md>) compressed). Envelopes offered, not imposed (data access first — envelopes after the shape lands — depth on invitation ("deeper on any envelope?")). Adjacent breadth, data-access depth — proportions honored, scope proven.

```typescript
// GOOD (data-access answer with envelopes — shapes plus systems, priced):
// "Users/orders via Prisma (graphs earn mappers — explicit includes — N+1 prevented).
// Envelopes: capacity 33GB/18mo (7% — partition trigger 80M set); evolution phased
// (email expand/contract — backfill chunked, contract witnessed); operations outboxed
// (relay surface + purge windowed, audit mirror on money, gauges owned). Drizzle alongside
// for admin dynamics (bounded polyglotry — boundaries documented). Deeper on any envelope?
// (offered — depth available, breadth delivered.)"
```

```typescript
// BAD (vacuum data access — correct shapes, unexamined systems):
// "Users, orders via Prisma. Done." (Capacity? Unmentioned — 500M-row future unpriced. Evolution?
// Unmentioned — flag-day assumed. Operations? Unmentioned — dual-write proposed when asked, honesty
// absent. Polyglot? Unmentioned — single tool assumed universal. Correct shapes, vacuum-sealed. Staff
// loop asks three envelope questions; vacuum candidate answers vaguely thrice. Shapes hired junior;
// envelopes hire staff.)
```

**Common confusion** — *"adjacency derails data-access interviews (stay on topic)."* Envelopes *are* the topic at staff scope (data access lives in systems — capacity/evolution/operations inseparable from shapes that survive). Derailing means occupying adjacent topics (10-minute partitioning lecture uninvited — depth misplaced); adjacency means visiting briefly (30–60 seconds per envelope — breadth demonstrated, depth offered). Visit, don't occupy — offer, don't impose — envelope, don't derail. Interviewers inviting deeper ("tell me more about the migration") reward the visit with extended scoring; interviewers moving on bank the breadth silently. Both outcomes favorable — adjacency never penalized when proportioned.

**Performance note** — envelope economics in interviews (same pattern as every QA leaf: numbers prove residence — capacity percentages, migration chunk sizes, relay lag gauges — arithmetic per envelope, 30 seconds each). Unenveloped data access reads as unoperated (designed, never run — the junior tell at staff loops); enveloped data access reads as operated (run at scale, migrated live, paged on gauges — the staff tell). Operated-ness performed via envelopes — three numbers (capacity %, migration chunks, relay lag) proving production contact in ninety seconds total. Numbers hire; shapes qualify; envelopes promote.

**Mentor note** — teach envelopes as "and..." habit (juniors finishing data-access answers add "and capacity... and evolution... and operations..." — three ands, thirty seconds each — practiced until reflexive). The "and" reflex generalizes beyond interviews (design docs enveloped, PR descriptions enveloped, incident reviews enveloped — completeness as habit, not performance). Drill "and" thrice per whiteboard exercise (shapes, then three ands — timed, graded) — reflexive completeness within weeks. And capacity, and evolution, and operations — always, forever, hired.

## 3. Narrate method, not recall (jurisdictions, prices, triggers — the performance that hires)

**Definition** — the meta-skill closing the track's interview arc (stated per-domain from 01 through 06, synthesized here finally): interviews grade *method performed* (jurisdictions placed live — layer/tool verdicts with reasons ([Domain 01 §1.2](<../../01 Data Access Foundations and Mental Model/sections/1. Why data-access layers/1.2. Query builders versus ORMs versus raw drivers.md>), [Domain 05 §1.1](<../../05 Comparing and Choosing/sections/1. Selection by workload/1.1. Workload-matched selection.md>)); prices computed live (ledgers consulted — build/strategy/magic costs stated ([Domain 05 §1.2](<../../05 Comparing and Choosing/sections/1. Selection by workload/1.2. Cost ledgers per tool.md>)); triggers named live (graphs/dynamics/majors with revisit dates ([Domain 05 §4.1](<../../05 Comparing and Choosing/sections/4. Mentor checklist/4.1. Selection checklist mentors insist on.md>)). Method narrated out loud is unmistakable and unfakeable (interviewers hear decisions happening — jurisdictions placed, then prices, then triggers); recall recited is equally unmistakable (definitions first, application absent — "DataMapper separates concerns" followed by silence on the codebase at hand).

**What problem it solves** — the recall trap (candidates studying definitions (ActiveRecord/DataMapper recited, N+1 defined, outbox described — vocabulary without derivation); neglecting method (jurisdictions unplaced live — prices uncomputed — triggers unnamed — derivation absent). Recall answers interview *questions* ("define DataMapper" — recited); method answers interview *exercises* ("place tools for this API" — derived live — the exercise form senior loops use exclusively). Recall-heavy preparation optimizes the wrong test (junior phone screens quiz definitions; senior loops stage exercises — preparation mismatched to loop level fails upward-bound candidates systematically). Method preparation (timed placements/pricings/triggers performed live, repeatedly) optimizes the exercised form — hired at every level, promoted at senior ones.

**Modern guidance** — the method performance (three moves, every exercise, narrated aloud): *jurisdictions* ("graphs earn mappers here (relations traversed — placement reasoned); dynamics earn builders there (filters composed — control retained); flat remainder typed raw (ceremony declined — honesty)" — verdicts with reasons, live); *prices* ("generation seconds per build; strategies minutes per relation; magic reviews per major — ledgers consulted live, costs stated" — numbers with sources, live); *triggers* ("graphs past 2 relations re-evaluate; majors re-price ledgers yearly; revisits calendared — horizons dated, live). Moves performed in order (jurisdictions → prices → triggers — the track's sequence compressed to method), narrated continuously (silence ungradeable — thinking aloud, always).

```typescript
// GOOD (method performed — jurisdictions, prices, triggers, narrated continuously):
// "Jurisdictions first: order screens graph-heavy (mappers earn — relations traversed);
// admin lists dynamic (builders earn — filters composed); config flat (raw suffices).
// Prices: generation seconds per build (CI-measured); strategies minutes per relation
// (batching designed); magic reviews per major (surprises preempted). Triggers: graphs past 2
// relations re-evaluate (dated); majors re-price yearly (calendared). Method visible throughout —
// jurisdictions placed, then prices, then triggers; verdicts derived, never recited."
```

```typescript
// BAD (recall recited — vocabulary without derivation, silence where method belongs):
// "DataMapper separates concerns. N+1 is the per-parent query problem. Outbox ensures reliable
// messaging. Drizzle is SQL-like." (Jurisdictions? Unplaced (tools unpositioned — verdicts absent).
// Prices? Uncomputed (costs unstated — ledgers unconsulted). Triggers? Unnamed (horizons undated —
// revisits unscheduled). Four definitions, zero derivations. Vocabulary parade, method absent.
// Recited, not performed. Ungradeable beyond junior recall.)
```

**Common confusion** — *"method narration feels slow (just give the answer)."* Narration speed follows fluency (practiced method narrates briskly — jurisdictions in seconds, prices in a minute — timed drills from every §5.1 compressing performance to interview pace); silent "answers" arrive ungradeable (verdict without derivation — correct-or-not coin flip, no partial credit path, no follow-up surface). Interviewers score derivation steps (jurisdiction placed: points; prices computed: points; triggers named: points — partial credit per move); silent verdicts score binary (right/wrong — no recovery from wrong). Narrated method maximizes expected score (partial credit per move + follow-up surface per step); silent answers minimize it (binary, fragile). Narrate briskly; score continuously.

**Performance note** — method performance *is* interview performance (same pattern as every QA leaf, seventh and final synthesis): timed drills compressing jurisdictions/prices/triggers to interview pace (minutes per move — fluency measurable in rehearsal times); phase timing per exercise (layers 2min, tools 4min, selection 2min, operations 2min — budgets honored live); transition narration (audible method — "layers placed — tools positioned — verdicts priced" — interviewers tracking progress, never wondering). Rehearse timed; perform briskly; transition audibly — interview mechanics mastered like query mechanics (measured, drilled, owned).

**Mentor note** — teach method-first preparation (juniors drilling placements/pricings/triggers over definitions (flashcards, glossaries) — preparation matched to exercised loops, not quizzed ones). The preparation audit ("show me your last timed derivation" — rehearsal evidence, not study hours) diagnoses readiness precisely (fluent method = ready; fluent definitions = junior-loop ready only). Preparation prescribing derivations hires seniors; prescribing definitions hires juniors. Prescribe derivations; time them; perform them; hired — the track's pedagogy performing whole, mentors equipped, track nearly complete.
