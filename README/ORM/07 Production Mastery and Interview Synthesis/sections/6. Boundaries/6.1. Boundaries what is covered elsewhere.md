# 6.1. Boundaries what is covered elsewhere

## 1. This track ends at data access (usage, design, code, systems beyond — the edges)

**Definition** — the track's outer boundary, stated finally: ORM teaches *data-access layers* (jurisdictions placed, tools operated, verdicts priced, operations owned — six domains, complete). Beyond its edges: **usage** (operating databases — SQL fluency, EXPLAIN tuning, backup execution, monitoring operation — [Databases track](<../../../../Databases/README.md>)); **design** (entities, dependencies, forms, evolution — shapes layers map ([Database Design track](<../../../../DatabaseDesign/README.md>) — mappers projecting discipline, never redefining it); **code** (mapping shapes into programs — repositories, worker frameworks, flag SDKs — [DesignPatterns 06](<../../../../DesignPatterns/06 Modern Patterns and Anti-Patterns/README.md>) + TypeScript track (decorators/type theory — consumption, never redefinition); **systems** (topology, distribution, infrastructure — sharding operations, broker topologies, cluster management — SystemDesign/Microservices/DevOps tracks (textual forwards — unbuilt or sibling-owned). Edges crisp, crossings linked, repetitions zero — the DRY contract honored at track scale, complete.

**What problem it solves** — track sprawl in both directions (data-access track absorbing EXPLAIN tutorials (usage mechanics — no layer decision — thesis diluted); broker topologies (infrastructure — decisions without mapping content); ODM mapping internals (consumption mechanics — shapes redefined per mapper — authority inverted); and track timidity (data access refusing adjacent necessities — capacity numbers without measurement functions? triggers without monitoring? — edges drawn so sharply the track starves its own procedures). Edges placed where layers end (decisions made) and execution begins (usage/code/systems operating) — procedures referenced across edges (measurement functions linked, monitoring assumed, mappings consumed), mechanics never re-taught. Crisp edges, rich crossings — bounded completeness, track complete.

**Modern guidance** — the edge map (decision → execution, per neighbor): layers → SQL fluency (write/operate them — Databases 01–04); triggers → monitoring operation (dashboards/alerts/runbooks executing — Databases 06–07); shapes → mappers projecting discipline (entities audited — Database Design consumed, never remodeled); outbox/job/flag shapes → code mappings (repositories/workers/SDKs consuming — Patterns 06, ORM textual); partition/shard keys → topology operation (resharding, rebalancing — SystemDesign textual); audit/retention shapes → compliance operation (legal processes consuming certificates — outside all tracks — one line per DRY). Design reviews cite edges ("execution per Databases 06 runbook — linked"); execution reviews cite designs ("shape per DatabaseDesign 05/2.2 — linked"). Bilateral boundaries (each side referencing the other — stated in both tracks' boundary leaves — rot slower than unilateral claims, verified at every closeout).

**Common confusion** — *"boundaries mean isolation (tracks never interact)."* Boundaries mean *ownership* (each concept one home — DRY at repo scale), crossings mean *interaction* (links everywhere concepts meet — references dense, repetitions zero). Isolated tracks duplicate (same concept taught thrice, drifting); interacting tracks reference (taught once, linked widely — closeouts verifying links track-wide: 800+ and counting). Ownership without interaction is silos; interaction without ownership is duplication. Both, always: owned concepts, linked crossings — the repo's architecture in one sentence, track complete.

Decide upstream; tune downstream — the track's final performance sentence, complete.

## 2. Siblings consume this track (API shapes, service boundaries — downstream, never repeated)

**Definition** — the downstream boundary: sibling tracks consume ORM outputs without re-teaching them — API tracks shape responses from aggregates/entities served through mappers (endpoints serving designed units — response envelopes referencing, not remodeling); Microservices/CleanArchitecture tracks draw boundaries informed by repository seams (consistency boundaries informing service cuts — [Domain 01 §2.2](<../../../01 Data Access Foundations and Mental Model/sections/2. Mapping patterns/2.2. The repository seam.md>) consumed — contract suites shared, never redefined). Consumption flows one way (layers constraining code — never reverse — the track's standing rule, sixth restatement across domains, final at track scale).

**What problem it solves** — upstream inversion at track scale (API-first shaping ("REST needs nested JSON" — response formats dictating aggregates/entities — mappers bending to serialization (N+1 scheduled per nested response — presentation dictating persistence); service-first boundaries ("one service per table" — deployment topology dictating consistency — distributed monoliths with cross-service FKs unenforceable); test-first tooling ("mock the Prisma client" — framework mocks replacing seam contracts (canned data per test — contracts unverified anywhere — production diverging silently while suites celebrate). Consumption designed downstream (response envelopes referencing aggregates — seams abstracting tools — contracts shared); inversion scheduled incidents (presentation dictating persistence — topology dictating consistency — mocks replacing contracts).

**Modern guidance** — the consumption map (producer → consumer, linked one-way): entities/aggregates → API response shapes (endpoints serving designed units — envelope/pagination added downstream — response needs never reshaping aggregates (chips/subsets serving screens without merging lifecycles — Database Design 03 consumed correctly)); repository seams → service boundaries (services owning aggregates whole — cross-service refs eventual (sagas/outbox — Database Design 06/2.1 consumed) — split aggregates across services never (distributed consistency without boundary — the microservices failure mode starting in data access); contract suites → testing tracks (shared suites run against fakes + real implementations — drift caught structurally — MemUsers pattern consumed, never redefined). Consume downstream; constrain upstream; link one-way.

**Common confusion** — *"greenfield services should design data and code together."* Together, yes — with direction (layers constraining code: aggregates informing service cuts; shapes informing models; invariants informing APIs — co-design with upstream authority, not negotiation among equals); without direction, negotiation trades layers for convenience (mapper conveniences dictating entities — response formats dictating aggregates — topology dictating consistency — convenience winning per negotiation, integrity losing per compromise). "Together" without direction negotiates (peers trading integrity for convenience); "together" with direction collaborates (code informing layers with usage reality — feedback valued, authority clear — friction resolved mapping-side first). Co-design directed (upstream constrains, downstream informs); never negotiated (peers trading integrity for convenience). Direction dignifies collaboration; absence corrupts it into compromise.

**Performance note** — none specific — consumer performance (API serialization, service latency, test speed) lives downstream by design. This track's downstream contribution, stated finally: shapely layers serving fast consumers (bounded queries hydrating cheaply, indexed relationships joining fast, gauge-serving tables observable natively — consumer performance inherited from layer quality). Consumer tuning atop unshaped layers (N+1 over reference-spaghetti, hydration of unbounded nests, polling of ungauged queues) is remediation, not optimization — shaped upstream prevents it structurally. Shape well; consume cheaply — the downstream dividend, track complete.

**Mentor note** — teach "who consumes this layer?" per design (juniors naming API/services/tests per table discover downstream implications early — layers designed consumable (bounded, indexed, gauged) versus layers designed in vacuum (correct, unusable — mappers choking, endpoints assembling, services splitting)). Consumer-awareness without consumer-submission (layers serving consumers while constraining them — hospitality with authority — the senior posture toward downstream). Aware, not submissive — hospitable, never inverted. Posture taught per design; direction held per career.

## 3. The method travels (new tools, new mappers — lenses transfer, shapes adapt — graduation, not goodbye)

**Definition** — the graduation thesis: this track teaches *lenses*, not just tools — layer placement (raw/builder/mapper per feature — any stack with data access); cost ledgers (generation/strategies/magic priced — any mapper with trade-offs); N+1 detection (statement counting — any layer with lists); migration discipline (phases/witnesses/reversibility — any schema evolution); trigger gauges (pools/versions/counts monitored — any production data path). New tools (next-gen mappers? post-relational clients? — future engines, same questions: which layer? what strategies? what magic? how migrate? who operates?) yield to the same lenses with adapted shapes (clients differ, ledgers persist; syntax shifts, strategies transfer; versions turn, triggers hold). Graduation, not goodbye — lenses traveling beyond every tool taught here.

**What problem it solves** — the track's terminal risk: graduates fluent in three tools' APIs but blind to fourth-tool novelty ("we adopted X — none of the track applies!" — APIs differing, lenses unrecognized — relearning from zero, repeating all six domains' mistakes in the new tool). Lens-transfer prevents it (jurisdictions placed on day one with X (workload centers recognizable — graphs/dynamics/flatness persisting across tools); ledgers priced immediately (generation/strategies/magic asked per tool — costs investigated from release notes, not incidents); N+1 counted from first list (detector applied — linearities caught pre-production); migrations phased from first schema (witnesses demanded — flag-days declined). Shapes adapt per tool (syntax differing — APIs learning curves); lenses persist per thinking (questions outliving tools — careers outliving stacks).
