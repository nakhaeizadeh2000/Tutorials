# 1.1. Workload-matched selection

## 1. Graphs earn mappers (relations traversed per feature — hand-mapping liability within quarters)

**Definition** — the graph jurisdiction: features traversing relations per screen/request (order-with-lines-and-customer, user-with-posts-and-comments, dashboard aggregating across entities — object graphs as the workload, not the exception) earn generated mappers (Prisma explicit includes, TypeORM relations option — batching declarative, types end-to-end, N+1 structurally preventable). "Earn" means hand-mapping liability exceeds mapper ceremony within quarters (assembly code per feature, mapping bugs per relation, N+1 by habit — toil compounding past the ceremony it avoided). Measured live this session (5 users × 4 posts): raw-loop 6 statements vs Prisma-include 2 vs Drizzle-with 1 vs TypeORM-relations 1 — mappers batching where loops multiply (evidence, not slogans).

**What problem it solves** — the hand-mapping liability (graph features on raw/builders — assembly code per screen (joins hand-written, results hand-nested — mapping bugs per relation (miskeyed assembly, dropped rows, N+1 by habit — loops visible but uncounted); toil compounding per feature (each graph screen re-solving assembly — no shared relation metadata to analyze (N+1 undetectable structurally — manual loops uncounted by tooling). Generated mappers convert assembly to traversal (relations declared once — loaded per strategy — batched structurally (measured: constant statements regardless of N); mapping bugs eliminated (framework assembling — tested once, reused everywhere); N+1 detectable (relation metadata analyzable — detectors enforced — [Domain 01 §4.1](<../../../01 Data Access Foundations and Mental Model/sections/4. Mentor checklist/4.1. Data-access checklist mentors insist on.md>)).

**Modern guidance** — the graph test per feature (review-enforced): *relations traversed?* (per screen/request — count them (1–2 joins: builder territory honestly (ceremony unjustified — mappers declined with reason); 3+ relations or nested graphs: mapper territory (hand-mapping liability within quarters — toil priced, ceremony justified); *measured comparison* (same workload, candidate tools, statement counts (verified live pattern below — raw-loop 6, raw-join 1, drizzle-with 1, prisma-include 2, typeorm-relations 1 — batching strategies compared, not benchmarked (counts, not milliseconds — [3.1](<../3. Measurement honesty/3.1. Benchmarks that inform (and deceive).md>) owns timing honesty); *trigger dated* (graphs arriving past 2 relations → mapper re-evaluation (recorded — flat-today features monitored for graph-growth (domains grow graphs the way junctions grow attributes — [Database Design §4.2](<../../../../DatabaseDesign/04 Relationships at Scale/sections/2. Many-to-many and polymorphism/2.1. Junction tables at scale.md>)'s law, workload edition).

// Graphs earn; flatness declines. Misplacement itemized.
```

**Common confusion** — *"more relations always means ORM (graphs everywhere)."* Relations *traversed* earn mappers (per-feature reads navigating graphs — batching valuable); relations *existing* but untraversed don't (FKs present for integrity (Database Design discipline — constraints, not traversals) — joins never issued (integrity without reads — mapper ceremony unjustified (constraints enforced identically under raw/builders). "Traversed per feature" is the criterion (reads navigating — batching earning); "declared in schema" is not (constraints constraining — mappers irrelevant). Traverse earns; declare doesn't — price reads, not schemas.

**Performance note** — graph economics (measured live numbers): hand loops cost 1+N statements (linear — verified: 6 for N=5 (scales with users — latency linear in data); manual joins cost 1 statement (skill-intensive per query — toil per feature, expertise per author); declared batching costs 1–2 statements (constant regardless of N — verified: drizzle 1, typeorm 1, prisma 2 (dataloader second query) — N+1 immunity structural). Statements decide speed (measured, not benchmarked — counts, never milliseconds, at selection time); ceremony decides velocity (mapping toil vs generation — quarters per feature). Batch structurally; count always; benchmark never (at selection — [3.1](<../3. Measurement honesty/3.1. Benchmarks that inform (and deceive).md>)).

**Mentor note** — teach "count relations traversed" (juniors counting per feature place mappers accurately on first hearing (0–2 joins: builders honestly; 3+: mappers earned — jurisdictions reflex, not reference); fashion interrogated ("which relations does this feature traverse?" — unexamined mappers exposed instantly). Measured comparisons beat asserted placements (same workload, candidate tools, statement counts — evidence over fashion — run the comparison live once per team (numbers shared, tribalism ended). Count traversals; measure candidates; place deliberately.

## 2. Dynamics earn builders (filters composed per request — strings declined structurally)

**Definition** — the dynamics jurisdiction: features composing queries per request (filtered lists, admin screens with optional clauses, reports with sorting/pagination variants — SQL varying by input, not just values) earn builders (Drizzle conditions arrays — branches pushing expressions, parameterized always, typed throughout — [Domain 04 §2.1](<../../../04 Drizzle Deep Dive/sections/2. Composition and migration/2.1. Queries composed, not concatenated.md>) performed). "Earn" means string dynamics cost more than builder ceremony (injection per branch (input becoming code); combinations untestable (2^n paths, tested none); results untyped (any rows — refactors breaking) — risks compounding per filter, ceremony fixed once). Dynamics composed (safe, typed, logged); strings declined structurally (interpolation rejected severity-1 — never negotiated as style).

**What problem it solves** — the string-dynamics trio (interpolated filters per branch (injection structural — input becoming code — the 2000s never ended here); untestable combinations (2^n branch paths — tested none — coverage fiction); untyped results (raw strings returning `any` — refactors breaking at runtime). Builder composition converts all three (branches pushing expressions — parameterized always (injection impossible); combinations composed (typed throughout — branch coverage testable); results inferred (table definitions flowing — refactors via compiler). Dynamics priced per branch (safe composition); strings priced per incident (injection/security/typing — quarters each).

**Modern guidance** — the dynamics test per feature (review-enforced): *filters varying?* (per-request composition — optional clauses, sorting variants, pagination shapes — dynamics present → builders (conditions arrays — verified live pattern in 04/2.1 (kind+prefix → 1 row); *static shapes?* (fixed queries with bound values — find APIs serving fully (Prisma/TypeORM composed finds — dynamics absent — builders unjustified (find APIs covering — ceremony declined honestly); *strings present?* (interpolated branches — rejected on sight (severity-1 — injection reviewed as data loss — because it becomes data loss — rewrite to arrays immediately, never next quarter). Dynamics present → builders (composed); static → finds (composed APIs); strings → rejected (always, with prejudice).

**Common confusion** — *"builders are just ORMs with extra steps (same choice)."* Builders compose *queries* (SQL varying per request — dynamics served — control per statement); ORMs map *graphs* (objects traversed — relations served — convenience per model). Different centers (statements vs models), different prices (composition ceremony vs N+1/magic risks), different jurisdictions (dynamics vs graphs — features needing both use both (builders for lists, mappers for graphs — polyglot per feature ([2.2](<../2. Changing tools/2.2. Polyglot persistence honestly.md>) — deliberate, documented). Statements vs models — choose per workload center, never by fashion (one tool for dynamics + graphs = misfit somewhere, always).

**Performance note** — dynamics economics: composed branches plan-stably (bound values — plan reuse across combinations — interpolated strings replanning per text (parse overhead per combination — plan cache defeating); typed results refactor safely (column changes breaking at compile — velocity preserved); logged statements profiled per combination (hot combos EXPLAINed — evidence per workload). Composition costs array lines (branches as data — reviewer-visible); concatenation costs replans + risk (parse overhead per string + injection surface per branch). Compose data; concatenate never (except fenced raw remainder — [Domain 02 §3.1](<../../../02 Prisma Deep Dive/sections/3. Performance discipline/3.1. N+1 strategies and raw escapes.md>)).

**Mentor note** — teach "branches push, never interpolate" (juniors composing conditions arrays design safe dynamics on first hearing; interpolating branches interrogated ("parameterized how?" — binding demanded per branch). Demonstrate injection once (interpolated filter exploited in staging — faces paling, conversion permanent); composed equivalent immune (bound parameters — same input harmless — contrast tangible). Push conditions; bind values; log statements — dynamics discipline in three habits, reviewed per dynamic query.

## 3. Flatness declines both (typed raw suffices — ceremony without graphs, toil without control)

**Definition** — the flat jurisdiction: features with flat shapes and static queries (key-value reads, single-table CRUD, config surfaces, health checks — no relations traversed, no filters composed — shapes simple, queries fixed) decline both builders and mappers (typed raw suffices — parameterized queries + inferred row types + pooled client — safety + management, zero mapping ceremony, zero composition ceremony). "Declines" is active judgment (ceremony evaluated, found unjustified — toil evaluated, found unjustified — typed raw chosen deliberately with trigger (graphs/dynamics arriving → re-evaluate (recorded, not hoped).

**What problem it solves** — the ceremony duo: *mapper ceremony without graphs* (Prisma schema + client generation + migration tooling for key-value reads (build seconds per generation, magic surface inventoried, upgrade churn priced — all for single-row fetches — ceremony serving nothing); *builder ceremony without dynamics* (composition framework for static finds (conditions arrays with one branch — abstraction without variance — toil without control benefit (find APIs serving identically with less code). Flatness honestly assessed converts both (typed raw: safety + management, zero ceremony — velocity maximal for flat shapes; triggers recorded (graphs/dynamics arriving → re-evaluate — flatness monitored, not assumed permanent).

**Modern guidance** — the flatness test per feature (review-enforced): *relations traversed?* (none → mappers declined (ceremony unjustified — generated clients wrapping single-row fetches); *filters varying?* (none → builders declined (composition unjustified — static finds serving fully); *typed raw serving?* (parameterized + inferred + pooled (safety + management bought à la carte ([Domain 01 §1.1](<../../../01 Data Access Foundations and Mental Model/sections/1. Why data-access layers/1.1. What problem data-access layers solve and create.md>)) — flatness confirmed (no graphs, no dynamics — typed raw sufficient, honestly); *trigger recorded* (graphs past 2 relations → mapper re-evaluation; dynamics arriving → builder adoption — flatness monitored (domains grow graphs/dynamics the way junctions grow attributes — triggers firing, graduation scheduled). Flat confirmed + trigger dated → typed raw approved.

// branch (abstraction without variance — find APIs serving identically with less code). Flat shapes;
// towering ceremony. Jurisdiction unexamined; velocity taxed; upgrades billed. Decline honestly.)
```

**Common confusion** — *"typed raw doesn't scale (teams outgrow it)."* Typed raw scales *within flatness* (static queries + flat shapes — volume scaling via indexes/pools/caching (infrastructure, not layers — millions of flat reads served excellently); outgrown via *shape change* (graphs/dynamics arriving — triggers firing (recorded) — graduation scheduled (mappers/builders adopted deliberately). "Doesn't scale" confuses volume scaling (infrastructure — indexes/pools serve millions of flat reads) with shape evolution (graphs/dynamics — triggers graduate layers). Scale volume with infrastructure (always); evolve layers on triggers (recorded, dated). Flatness scales volumetrically; shapes evolve jurisdictionally.

**Performance note** — flatness economics: typed raw costs zero ceremony (no generation per build, no magic surface, no upgrade ledgers — thinnest possible path); volume served via infrastructure (indexes/pools/caches — Databases mechanics — millions of flat reads excellently); trigger monitoring costs nothing (graphs/dynamics arriving observed in reviews — graduation scheduled on evidence). Ceremony-for-flatness costs build seconds (generation per trivial change), magic inventory (quarterly, benefitless), upgrade ledgers (per major, serving nothing). Thinnest sufficient wins (ceremony justified per shape, never defaulted); triggers guard evolution (flatness monitored, graduation scheduled).

**Mentor note** — teach "flatness is a jurisdiction" (juniors assessing flat-vs-graph-vs-dynamic per feature place typed raw confidently (no shame in simplicity — thinnest sufficient is optimal, not primitive); ceremony-for-flatness interrogated ("which relations? which dynamics?" — silence failing structurally). Simplicity praised ("good raw call — flat confirmed, trigger recorded" — behavior praised, repeated); ceremony-for-flatness questioned (jurisdiction demanded per tool). Thinnest sufficient celebrated; ceremony justified; flatness monitored.
