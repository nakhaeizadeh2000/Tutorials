# 5.1. Common interview QA data-access foundations

## 1. ORM versus raw under pressure (the trade-off answer — control, safety, cost)

**Definition** — the question behind the question: *"would you use an ORM here?"* (or "raw SQL or Prisma for X?"). The failing answers are absolute ("ORMs always — productivity" — costs unpriced; "raw always — control" — toil unpriced). The passing answer is a *jurisdiction verdict*: shapes examined (flat? dynamic? graph?), options priced (control/safety/cost per layer — [1.2](<../1. Why data-access layers/1.2. Query builders versus ORMs versus raw drivers.md>)), verdict stated with trigger ("typed raw here (flat shapes) — graphs arriving trigger mapper re-evaluation"). Pressure answers show judgment performing (prices consulted, verdicts stated, triggers dated — ninety seconds, complete).

**What problem it solves** — tool questions filter for economic thinking (most candidates answer tribally ("my last team used Prisma" — habit reporting; "ORMs are slow" — slogan reciting). Interviewers probe layer choice because it reveals whether engineers *price abstractions* (control/safety/cost per option — engineering) or *inherit* them (fashion/defaults — cargo cult). Priced verdicts signal production judgment (abstractions adopted deliberately, costs monitored); inherited answers signal tutorial-following (tools used, prices unknown — surprises scheduled). Price layers; state verdicts; date triggers — hired.

**Modern guidance** — the ninety-second shape: (1) examine shapes ("three flat tables, no relations — flat jurisdiction; filtered lists — dynamics present"); (2) price options ("raw+types: full control, hand-mapping trivial (no graphs); Drizzle: typed composition for dynamics; Prisma: ceremony without graphs (generation per build, magic surface — unjustified)"); (3) verdict with trigger ("Drizzle here (dynamics earn builders — flatness declines mappers); graphs arriving (relations >2) trigger Prisma re-evaluation — recorded, not hoped"). Shapes examined, options priced, verdict triggered — three beats, no absolutes, no tribalism. Absolutes fail ("always/never" — context unexamined); triggers pass (verdicts revisable — judgment, not dogma).

```typescript
// GOOD (spoken, 90 seconds — priced verdict with trigger):
// "Shapes: three flat tables (no relations) + filtered admin lists (dynamics present).
// Options: raw+types (full control — hand-mapping trivial, dynamics hand-concatenated
// unsafely — dynamics disqualify pure raw); Drizzle (typed composition — dynamics safe,
// zero mapping ceremony — jurisdiction match); Prisma (ceremony without graphs — generation
// per build, magic surface, zero graph benefit — declined explicitly). Verdict: Drizzle
// (dynamics earn builders); trigger: relations past 2 → Prisma re-evaluation (dated)."
// Examined, priced, triggered. No absolutes survived; judgment performed.
```

```typescript
// BAD (spoken): the absolute — tribal, unpriced, context-free.
// "Prisma — it's the modern standard, types end-to-end." (Shapes? Unexamined — flat tables
// under mapper ceremony. Costs? Unpriced — generation, magic, upgrades for zero graphs.
// Trigger? Absent — graphs never arriving, ceremony permanent.) Or the mirror: "Raw SQL —
// ORMs are slow, control matters." (Dynamics? Hand-concatenated (injection per branch).
// Toil? Unpriced (mapping per feature, N+1 by habit). Fashion? Inverted (control romanticism
// as dogma.) Absolutes hire nowhere senior — context hires everywhere.
```

**Common confusion** — *"the interviewer wants a tool name."* Names without prices are guesses (correct tool, wrong reasons — unhirable reasoning with lucky verdicts); prices without names are evasion ("it depends" — verdict deferred indefinitely — analysis without decision). Name *with* prices (verdict + ledger — decisive and grounded — hirable reasoning with earned verdicts). "Drizzle, because..." (verdict first, prices following — confidence with evidence); never "it depends" trailing off (evidence without verdict — analysis paralyzed). Verdicts priced; prices triggering; triggers dated.

**Performance note** — volunteer the performance clause unprompted ("equivalent SQL performs equivalently — statements decide speed (same planner); mapping CPU negligible beside I/O; N+1 governed by strategy here (explicit per query — detector enforced from adoption)"). Performance clauses preempt follow-ups ("but is it fast?" — answered before asked — control demonstrated); unvolunteered performance invites probing (interviewer digging — "what about N+1?" — reactive answers scoring lower than proactive ones). Volunteer performance; preempt probing; control narrative.

**Mentor note** — drill as rapid-fire verdicts (ten features, ninety seconds each — tool + prices + trigger — same prescription as all QA leaves): speed forces internalization (jurisdictions reflex, not reference — fashion failing visibly under time pressure); prices required per verdict (unpriced verdicts failing rounds — "numbers?" exposing tribalism instantly). Tribal answers die in drills (fashion indefensible at speed — prices demanded, verdicts timed); judgment performs (priced, triggered, dated — hired). Drill verdicts; require prices; date triggers.

## 2. N+1 on a whiteboard (spot it, fix it, prevent it — three beats)

**Definition** — the exercise: *"this list endpoint is slow — diagnose live"* (code with per-parent queries — the interview staple). The graded performance is three beats: **spot** (count statements per render — "N orders → 1 + N queries — linear in data, found by counting, not profiling"); **fix** (batch the fan — join/include/relations per query — constant statements regardless of page fullness — verified by recount); **prevent** (assert counts in tests — bounds enforced — strategies stated per relation — detector from [4.1](<../4. Mentor checklist/4.1. Data-access checklist mentors insist on.md>) adopted). Spot-fix-prevent in order (diagnosis → remedy → immunity — complete performance, never partial).

**What problem it solves** — N+1 questions filter for measurement discipline (candidates guessing ("add an index?" — unmeasured remedy for uncounted problem); candidates theorizing ("probably the database" — blame without counting); candidates counting ("1 + N statements — N+1 confirmed — batch to 2" — measured, fixed, prevented). Interviewers watch *where eyes go first* (logs/counts → measurers; code staring → guessers; EXPLAIN before counting → premature optimizers). Counting first is the senior tell (measure before remedy — always, everywhere); fixing second proves competence; preventing third proves seniority (immunity designed, not just incidents fixed).

**Modern guidance** — the five-minute shape: (1) *count* (1 min — "statements per render? 1 + N (N orders, N line-queries) — N+1 confirmed by counting (logs/assertions — evidence, not suspicion)"); (2) *fix* (2 min — "batch: include/relations/join per query — 2 statements regardless of N (orders + lines batched) — recount confirms (constant vs page fullness — verified, not hoped)"); (3) *prevent* (2 min — "assert ≤N statements per list test (N+1 fails builds); strategies stated per relation (explicit includes — defaults audited); logging on in dev/test (surprises pre-merge)"). Count-fix-prevent, timed, complete — diagnosis measured, remedy verified, immunity designed.

```typescript
// GOOD (whiteboard, order list — 5 min, three beats performed):
// "Count first: 1 orders query + N line-queries (N=page size — linear in data — staging's
// 10 rows hiding production's 10k (data-scaled thinking, stated). Fix: include lines per
// query (explicit strategy — 2 statements regardless of N — recount at max page confirms).
// Prevent: assert ≤3 statements per list test (N+1 fails builds); relations' strategies stated
// (explicit includes — lazy defaults flipped where lists traverse); logging on (surprises
// pre-merge). Counted, fixed, immunized. Three beats, complete performance."
```

```typescript
// BAD (whiteboard): the unmeasured remedy — tuning what wasn't counted.
// "Add an index on order_lines(order_id)?" (Counted? Never — statements uncounted (maybe 2
// already (no N+1 present — index tuning a healthy query); maybe 10k (N+1 present — index
// irrelevant (counts dominate, not lookups)). Remedy without diagnosis (tuning unmeasured
// paths — premature optimization wearing expertise); prevention unmentioned (next list
// N+1s identically — immunity undesigned). Guess, tune, repeat — performance theater.
// Count first (always); fix second (measured); prevent third (designed).
```

**Common confusion** — *"N+1 is an ORM problem (raw SQL immune)."* N+1 is a *loop* problem (per-parent queries in application loops — raw/builder/mapper all loop identically; ORM lazy-loading merely automates the loop (magic billing per touch — same N+1, less visible). Raw loops N+1 by hand (visible loops, uncounted — "only a few" growing unboundedly); builders N+1 by composition gaps (per-parent subqueries composed innocently); mappers N+1 by default strategies (lazy traversals — magic). Loops cause; layers vary visibility (explicit loops countable easily; magic loops countable with logging — count all, excuse none). Count loops, not layers — N+1 is layer-agnostic, detection-universal.

**Performance note** — volunteer the counted math ("1 + 10k statements → 2 batched (page-independent constant) — transfer O(page), queries O(1) — linear eliminated structurally, not tuned away"). Counted math proves measurement (numbers from logs, not adjectives); structural fix proves competence (batching, not indexing unmeasured paths); prevention proves seniority (assertions + strategies + logging — immunity trio). Math + structure + immunity — the complete N+1 answer in one extra breath, expert depth for free.

**Mentor note** — demonstrate N+1 live once per junior (staging seeded production-scale — list rendering thousands of logged queries — latency visible, faces paling — conversion instant, permanent — same prescription as 04/4.1's demo). Counting taught as reflex ("how many queries?" per list PR — asked until automatic); fixing taught as batching (include/relations/join per query — remedies verified by recount); prevention taught as assertions (bounds in tests — immunity designed). Demo once (conversion); ask always (reflex); assert permanently (immunity). Three verbs, zero N+1 shipped.

## 3. Which tool when (Prisma/TypeORM/Drizzle placed by workload — judgment, not fashion)

**Definition** — the closer: *"which would you pick — Prisma, TypeORM, or Drizzle?"* (the fashion trap). The graded answer places per workload (graphs + greenfield + end-to-end types → Prisma; class idioms/legacy/mixed-flavors → TypeORM; SQL-control + dynamics + thin abstraction → Drizzle — [2.1](<../2. Mapping patterns/2.1. ActiveRecord versus DataMapper.md>)'s positions, performed). Single-winner answers fail (fashion stated — context unexamined — mismatches scheduled); workload-matched answers pass (positions mapped — triggers dated — yearly revisits (majors re-price — Prisma 7→8 RC watch cited live — versions move, placements re-derived). Match per feature, default per team, revisit yearly — complete selection judgment.

**What problem it solves** — tool questions filter for anti-fashion (most candidates answer with adoption history ("we used X" — habit reporting) or community vibes ("X is modern" — fashion reciting). Interviewers probe placement because it reveals whether engineers *match tools to workloads* (positions mapped — triggers dated — revisits scheduled) or *standardize by comfort* (one tool everywhere — misfits scheduled — velocity taxed per misfit). Matched placement signals senior judgment (tools serving workloads); standardized comfort signals junior tribalism (workloads serving tools). Match deliberately; standardize thoughtfully (default + exceptions); revisit yearly.

**Modern guidance** — the ninety-second shape: (1) positions stated ("Prisma: graphs+greenfield+types; TypeORM: classes/legacy/both-flavors; Drizzle: SQL-control+dynamics+thin" — [2.1](<../2. Mapping patterns/2.1. ActiveRecord versus DataMapper.md>) performed from memory — positions, not podiums); (2) matched to *this* workload ("order graph, 12 relations, greenfield typed API → Prisma (graphs earn mappers); admin lists, dynamic filters → Drizzle (dynamics earn builders); billing legacy, class idioms → TypeORM (idioms + mixed flavors)"); (3) triggers dated ("graphs arriving past 2 relations → Prisma re-evaluation; majors (Prisma 8 RC watch active) → ledger re-price yearly; team default Drizzle (ADR-001) with exceptions filed"). Positions, matches, triggers — ninety seconds, fashion absent, judgment present.

```typescript
// GOOD (spoken, 90 seconds — positions, matches, triggers):
// "Positions: Prisma graphs+greenfield+types; TypeORM classes/legacy/both-flavors; Drizzle
// SQL-control+dynamics+thin. This workload (order graph, 12 relations, greenfield): Prisma
// (graphs earn mappers — explicit includes, migration tooling, end-to-end types). Admin lists
// alongside: Drizzle (dynamics earn builders — flat shapes decline mappers). Triggers: graphs
// past 2 relations re-evaluate Prisma anywhere; Prisma 8 RC watch → yearly ledger re-price;
// team default Drizzle (exceptions filed with reasons). Matched per feature, defaulted per team,
// revisited yearly. Fashion absent; judgment present."
```

```typescript
// BAD (spoken): the podium answer — one winner, all workloads, fashion stated.
// "Prisma — it's the modern standard, best DX." (Graphs? Unasked (flat admin tools under
// ceremony). Dynamics? Unasked (hand-tunable reports under graph mappers). Legacy/classes?
// Unasked (idioms ignored). Triggers? Absent (mismatches permanent — ceremony billed quarterly,
// toil billed per feature). Podium stated; workloads unexamined; mismatches scheduled.
// Winners hire nowhere senior — matches hire everywhere. Positions, not podiums.)
```

**Common confusion** — *"knowing all three tools is expected."* Foundations expected (patterns in this domain — AR/DM, builders/mappers, ledgers — tool-agnostic, learned once); one tool deeply (daily driver — complete fluency — hired competence); others positionally (placed accurately — jurisdictions + triggers — selection judgment). "All three deeply" is senior-staff scope (leads choosing stacks — breadth earned over years); "one deeply + positions" is senior scope (the interview's actual bar — depth demonstrated, breadth mapped). Depth + positions hire seniors; foundations + one depth hire mids. Calibrate scope honestly; place accurately always.

**Performance note** — close with placement economics ("matched tools perform natively (strategies fitting workloads — N+1 preventable, SQL tunable, ceremony justified); mismatched tools bill quarterly (ceremony without graphs, toil without control, coupling without simplicity — misfit taxes recurring). Match price: decision paragraph (recorded, dated); mismatch price: quarters per misfit. Paragraphs beat quarters — place deliberately, review yearly."). Economics with triggers (revisit dates — versions moving, workloads shifting — placements living documents, never tattoos). Price matches; date triggers; review yearly.

**Mentor note** — teach positions, not preferences (juniors placing tools per workload shape (graphs/flat/dynamics — with reasons stated) decide reviewably; juniors preferring tools per vibes decide tribally (fashion defended passionately, workloads unexamined). Preference interrogated ("why Prisma here?" — flat workload answer exposing fashion instantly); positions drilled (rapid-fire placements — tool + reason + trigger — fashion failing visibly under time pressure). Positions drilled; preferences interrogated; fashion retired. Place deliberately; prefer never.
