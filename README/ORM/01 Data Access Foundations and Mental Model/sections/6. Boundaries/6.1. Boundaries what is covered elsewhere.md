**Definition** — inbound boundary (the shapes this track's layers map): entities and lifecycles ([Database Design §1](<../../../../DatabaseDesign/01 Modeling Foundations and Mental Model/README.md>)); keys and identity ([Database Design §1.2](<../../../../DatabaseDesign/01 Modeling Foundations and Mental Model/sections/2. Layers map shapes; shapes designed there — mappers consume discipline, never redefine it (mapper limitations dictating entities is upstream inversion — failed at architecture review, not just schema review).

**What problem it solves** — shapeless mapping (ORM entities designed from mapper convenience — tables mirroring form fields, relations mirroring screens — normalization unexamined, dependencies unasked, anomalies scheduled); and mapper-dictated design ("Prisma can't map composite keys — use surrogates everywhere" — tool limitations weakening invariants track-wide; "embed for the API response" — response formats merging lifecycles). Shapes designed in Database Design (entities audited, forms proven, relationships priced, evolution phased) arrive here mappable (mappers projecting discipline — friction resolved mapping-side first, shape-side second with ADR — never mapper-dictated). Design upstream (constrains); map downstream (adapts — friction informative, never vetoing).

**Modern guidance** — the crossing map backward: entities/lifecycles/keys → Database Design 01 (verified index + key leaf above); dependencies/forms/copies → Database Design 02 (verified index above); documents/aggregates → Database Design 03 (verified index above); relationships/volume/skew → Database Design 04 (verified index above); evolution/migrations/capacity → Database Design 05 (verified index + expand/contract leaf above); operations shapes → Database Design 06 (verified leaf: outbox table design — relay surfaces mapped, not remodeled). Readers arriving here without Database Design should detour for 01 §1–§2 minimum (entities + keys — mappers assume shapes, shapes assume discipline). Links verified (indexes + three deep leaves — paths checked, not hoped).

**Common confusion** — *"ORM-first teams can skip data modeling (mappers handle it)."* Mappers persist shapes; they don't design them (entities unmodeled → tables mirroring forms → anomalies scheduled, mappers faithfully persisting garbage with types — typed garbage, still garbage). "Mapper handles it" confuses storage with structure (persistence executing, design absent — execution without design is acceleration toward incidents). Design first (Database Design — shapes disciplined); map second (this track — discipline projected); operate third (Databases — projections executed). Sequence, not substitution — skipping design mortgages every layer above it.

**Performance note** — none specific beyond §§1–3's own economics — the inbound point *is* performance-relevant though: disciplined shapes make mappers fast (indexed FKs joining cheaply, bounded documents hydrating cheaply, priced copies preventing N+1 structurally); undisciplined shapes make mappers slow regardless of tuning (unindexed relationships scanning, unbounded nests hydrating megabytes, fan-out queries multiplying — mapper-level tuning can't fix shape-level debt). Shape debt bills mapper performance with interest — design upstream pays dividends downstream, permanently.

**Mentor note** — teach "shapes before mappers" (juniors modeling entities before entities-classes (Database Design 01 first, ORM entities second — discipline preceding persistence); mappers projecting shapes (friction resolved mapping-side — custom types, composite support — shapes unchanged, ADRs filed). Shape-first onboarding (modeling weeks before mapping weeks — sequence enforced in curricula, never suggested); mapper-second fluency (generated clients projecting understood shapes — conveniences transparent). Order matters absolutely (design, map, operate — downhill always, uphill never).
