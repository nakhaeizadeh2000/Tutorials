# 3.1. Hello database three ways

## 1. Prisma: schema-first client (models declared, client generated)

**Definition** — Prisma 7.10.0 stable (v8.0.0-rc.19 prerelease tagged `latest` — this track teaches v7 stable, per track index): models declared in `schema.prisma`, a typed client generated (`prisma generate`), queries via the client (`db.user.findMany/create` — relations via explicit `include`). Schema-first means the schema file is the source of truth (migrations generated from it — `prisma migrate dev` in development; client regenerated per schema change — types flowing database→code end-to-end). As of v7: datasource connection URLs moved out of the schema (into `prisma.config.ts` + adapter/`accelerateUrl` at the `PrismaClient` constructor — verified live below, the v7 shape that v6-era tutorials get wrong).

**What problem it solves** — the untyped-client gap (raw queries returning `any` — refactors breaking at runtime; hand-written repositories drifting from schema — types maintained by discipline, decaying by default). Generated clients close it structurally (schema change → regenerate → compiler errors everywhere affected — refactors guided, never hoped). Prisma's specific value over generic DataMapper: end-to-end type flow with minimal code (no entity classes, no decorators, no repository boilerplate — schema + client calls, the thinnest path to fully-typed data access). Price: generation step per schema change (build pipeline integration — seconds, always) and client opinions (relation loading via `include` — explicit per query — N+1 prevented by strategy stated, never defaulted).

**Modern guidance** — the v7 hello path (verified live end-to-end on dbprobe this session — schema → generate → create + findUnique, all passing): schema declares models (`BigInt @id @default(autoincrement())`, `String @unique` — generator `prisma-client-js` with `output` to chosen path); connection configured in `prisma.config.ts` (`defineConfig` + datasource URL — schema carries no URL in v7); client constructed with adapter (`new PrismaClient({ adapter: new PrismaPg({ connectionString }) })` — @prisma/adapter-pg — direct connections without Accelerate); queries typed end-to-end (create/findUnique/first include — relations explicit). Migrations via `prisma migrate` (development flow — production through expand/contract review ([Database Design §5.1](<../../../../DatabaseDesign/05 Evolution Growth and Partitioning/sections/1. Schema evolution/1.1. Expand and contract migrations.md>)) — tooling executes, discipline governs).

```prisma
// GOOD: Prisma 7 hello — schema declares, client generates, queries type (verified live: generate + create + find).
datasource db {
  provider = "postgresql"   // v7: NO url here (moved to prisma.config.ts — v6 tutorials stale)
}

generator client {
  provider = "prisma-client-js"
  output   = "../client"
}

model User {
  id    BigInt @id @default(autoincrement())
  email String @unique
}
```

```typescript
// GOOD: client use — adapter-wired, typed end-to-end (verified live against dbprobe).
import { PrismaClient } from "./client/default.js";
import { PrismaPg } from "@prisma/adapter-pg";

const adapter = new PrismaPg({ connectionString: process.env["DATABASE_URL"] });
const db = new PrismaClient({ adapter });   // v7: adapter at construction (no schema URL)
await db.user.create({ data: { email: "ann@example.com" } });
const found = await db.user.findUnique({ where: { email: "ann@example.com" } });
// Live result: {"id":1,"email":"ann@example.com"} (BigInt parsed — client owns translation).
await db.$disconnect();
// Relations: include: { orders: true } per query (explicit — N+1 prevented by strategy stated).
```

```typescript
// BAD: v6-shaped Prisma 7 (stale tutorials applied blindly — fails loudly, thankfully).
// datasource db { provider = "postgresql"; url = env("DATABASE_URL") }  // v7 ERROR P1012:
// url unsupported in schema (verified live — generate refuses; fix: prisma.config.ts + adapter).
// const db = new PrismaClient();  // v7 without adapter/accelerateUrl (connection unconfigured —
// runtime failure). Stale shapes fail fast (validation errors, not silent wrongness) —
// version-skewed tutorials cost an afternoon, never production. Check versions first (track index).
```

**Common confusion** — *"Prisma replaces SQL knowledge."* Generated clients cover CRUD + relations fluently; unmappable queries (recursive CTEs, window-function analytics, COPY bulk loads) escape to `$queryRaw`/`$executeRaw` (typed via generics — same as raw drivers — SQL fluency required exactly where generators stop). "Replaces" promises coverage generators disclaim (raw escapes exist *because* coverage ends — escape hatches as designed features, not failures). SQL learned (queries composed, EXPLAIN read — Databases fluency assumed by this track) + client operated (generated paths typed, raw paths escaped) — both, always, each where fit.

**Performance note** — Prisma economics: generation per schema change (seconds per build — CI-integrated, never manual); query-count discipline via explicit `include` (relations loaded per statement — N+1 structurally preventable — detector from [4.1](<../4. Mentor checklist/4.1. Data-access checklist mentors insist on.md>) enforced from adoption); adapter pooling inherited (pg Pool beneath — sizing per Databases 04 mechanics — client pooling configured, never defaulted blindly). Velocity (end-to-end types, zero mapping code) with discipline (strategies stated, SQL shown via logging) — graph-heavy APIs earning Prisma within quarters ([2.1](<../2. Mapping patterns/2.1. ActiveRecord versus DataMapper.md>)'s placement, performed).

**Mentor note** — teach generate-first (juniors running `prisma generate` + reading generated types discover end-to-end typing tangibly — schema tweak → regenerate → compiler errors guiding refactors — the loop felt in minutes, believed permanently). Version-pin explicitly (v7 stable taught — v8 RC watched per track index — majors re-price ledgers ([1.1](<../1. Why data-access layers/1.1. What problem data-access layers solve and create.md>)) — upgrades rehearsed, never hoped). Generate often; read generated code sometimes (client internals legible — demystifying magic); pin versions always.

## 2. TypeORM: decorated classes (entities as classes — DataMapper and ActiveRecord)

**Definition** — TypeORM 1.1.1 stable (`latest`; `legacy` 0.3.31 — as of September 2026, per track index): entities as decorated TypeScript classes (`@Entity/@Column/@PrimaryGeneratedColumn` — decorator mechanics owned by TypeScript track §14, linked) used in two flavors — ActiveRecord (`class User extends BaseEntity` + `user.save()` — [2.1](<../2. Mapping patterns/2.1. ActiveRecord versus DataMapper.md>)) or DataMapper (`DataSource.getRepository()` + `repo.save()` — both verified live this session: API surface via require, full save/findOneBy round-trip against dbprobe). Longest history of the three (0.x lineage since 2016 — patterns stable, ecosystem deep, legacy baggage real — 1.x modernizes while carrying 0.3 idioms).

**What problem it solves** — the class-idiom gap (teams thinking in classes — domain models as classes with methods, validation, behavior — needing persistence that respects the idiom (decorated entities — behavior + mapping colocated (AR) or behavior-only with external mapping (DM) — both class-shaped); and the legacy continuum (0.3 codebases upgrading to 1.x — same decorators, same repositories, modernized internals — migration path, not rewrite). Classes carry behavior naturally (rich entities per [2.1](<../2. Mapping patterns/2.1. ActiveRecord versus DataMapper.md>) — methods testable without databases in DM flavor); decorators declare mapping beside fields (co-located schema knowledge — reviewed per class, never in separate files).

**Modern guidance** — the 1.x hello path (verified live: DataSource init + repository save/findOneBy against dbprobe, all passing): `DataSource` configured (type/host/port/credentials/database + entities array — `synchronize: false` in anything shared (schema via migrations — reviewed, never auto-synced in production — synchronize:true is development-only, production-forbidden)); entities decorated (both flavors verified importing + typechecking — tsc with experimentalDecorators + emitDecoratorMetadata on TS 7.0.2, passing); repositories operated (`getRepository(User)` → save/findOneBy — DataMapper default per [2.1](<../2. Mapping patterns/2.1. ActiveRecord versus DataMapper.md>)'s graduation logic — AR for trivial lifecycles only, triggers recorded). Flavor chosen per context (mixed deliberately — AR admin tool + DM order service in one codebase is fine, documented per boundary — accidental mixing is tech debt wearing flexibility).

```typescript
// GOOD: TypeORM 1.x hello — DataSource + DataMapper repository (verified live against dbprobe).
import "reflect-metadata";   // decorators' runtime (required once, entry point — forget it and
                             // decorators silently do nothing (the classic TypeORM initiation bug))
import { DataSource, Entity, PrimaryGeneratedColumn, Column } from "typeorm";

@Entity({ name: "orm_users" })
class OrmUser {
  @PrimaryGeneratedColumn()
  id!: number;

  @Column({ unique: true })
  email!: string;
}

const ds = new DataSource({ type: "postgres", host: "localhost", port: 5433,
  username: "postgres", password: "probe", database: "postgres",
  entities: [OrmUser], synchronize: false, logging: false });
await ds.initialize();
const repo = ds.getRepository(OrmUser);
await repo.save({ email: "ann@example.com" });
const found = await repo.findOneBy({ email: "ann@example.com" });
// Live result: {"id":1,"email":"ann@example.com"} (verified). await ds.destroy();
// tsc: experimentalDecorators + emitDecoratorMetadata (TS 7.0.2 passing — verified).
```

```typescript
// BAD: the two classic TypeORM initiation failures (both bitten widely, both structural).
// Missing reflect-metadata import (decorators evaluate silently inert — entities unmapped —
// "RepositoryNotFoundError: No repository for X" (the error naming everything except its cause).
// synchronize: true in production (schema auto-mutated per deploy — columns dropped by typo'd
// decorators (data loss wearing convenience); concurrent deploys racing schema writes).
// reflect-metadata always (entry-point first line — linted); synchronize never past development
// (migrations reviewed — Databases 04/2.2 mechanics + Database Design 05/1.1 discipline).
```

**Common confusion** — *"TypeORM is legacy — 0.3 is old news."* 1.x is current stable (1.1.1 `latest` — verified via dist-tags — modernized internals, same decorator idioms); 0.3 lineage means ecosystem depth (recipes for every edge — Stack Overflow answers rank, mostly still valid) AND legacy surface (0.3-era patterns lingering in tutorials — `getRepository()` statics, connection-manager idioms — version-check every tutorial (track index versions first — stale shapes fail or mislead). "Legacy" describes age honestly (a decade of production use — battle-tested) and pejoratively only where 0.3 idioms persist unexamined (statements dated pre-1.0 — verify per version). Current stable, deep history — respect both, verify everything.

**Performance note** — TypeORM economics: decorator metadata cost at startup (entity scanning + metadata building — seconds on large models — cold-start priced for serverless (lazy relations + limited entities per DataSource where cold matters); query-count discipline via relations options (`relations: {...}` per find — explicit like Prisma includes — N+1 prevented by strategy stated); `synchronize: false` discipline (schema static in production — no per-deploy DDL surprises — migrations reviewed, executed deliberately). Velocity (class idioms, both flavors, deep ecosystem) with discipline (strategies + inventories + migration review — 1.1's ledger applied per mapper).

**Mentor note** — teach reflect-metadata first (juniors importing it line-one internalize decorator mechanics' runtime requirement permanently — the initiation bug vaccinated in one lesson); synchronize-never second (production horror stories (dropped columns via typo — real, recurring) teach faster than rules — tell one, mandate migrations, never revisit). Flavor choice third (AR vs Repository per [2.1](<../2. Mapping patterns/2.1. ActiveRecord versus DataMapper.md>) — triggers recorded at adoption). Three lessons, first week with TypeORM — initiation complete, pitfalls preempted, flavors placed.

## 3. Drizzle: code-first tables (schema as code, SQL-shaped queries)

**Definition** — Drizzle 0.45.3 stable (1.0.0-rc in prerelease tags — this track teaches 0.45.x stable, per track index): schema declared as TypeScript code (`pgTable` + column builders — verified live in [1.2](<../1. Why data-access layers/1.2. Query builders versus ORMs versus raw drivers.md>): table definitions typechecking strict-clean, selects running live against dbprobe with number-parsed BigInts); queries composed SQL-shaped (`db.select().from().where()` — builder jurisdiction from 1.2); relations declared (`usersRelations` — `with:` graph queries — builder grown honestly into graphs). Code-first means schema lives in TypeScript (versioned with code, refactored via compiler, no separate schema language — single source in `.ts`).

**What problem it solves** — the schema-language split (Prisma schemas in `.prisma` (second language — editors/configured separately, refactors spanning two syntaxes); TypeORM decorators (TypeScript-embedded but metadata-magic — runtime behavior invisible in source). Drizzle's code-first keeps everything in TypeScript (tables as values (`const users = pgTable(...)` — importable, composable, testable as code); columns as expressions (constraints chained — `.notNull().unique()` — fluent, typed); queries as composition (builders returning builders — dynamic filters without string branches). SQL developers get SQL shapes (logged statements reading hand-written — control retained fully); TypeScript developers get inference (row types from table values — refactors via compiler end-to-end).

**Modern guidance** — the 0.45 hello path (verified live: table definition + typed select + live row against dbprobe — [1.2](<../1. Why data-access layers/1.2. Query builders versus ORMs versus raw drivers.md>) performed it; this leaf places it): tables as code (`pgTable(name, {cols})` — `bigint(mode:'number')` parsing choice explicit (number vs bigint semantics — decided per column, never defaulted blindly); relations declared beside tables (`defineRelations`/`usersRelations` — graph queries via `with:` — explicit per query like Prisma includes); client via node-postgres driver (`drizzle(client)` — pooling inherited (pg Pool beneath — Databases 04 mechanics); migrations via drizzle-kit (SQL generated from table diffs — reviewed like all migrations — Database Design 05/1.1 discipline governs). Builder jurisdiction honored (dynamic queries composed — graphs via declared relations only where genuinely relational — 1.2's placement, performed).

```typescript
// GOOD: Drizzle hello — tables as code, queries composed, rows inferred (verified live: 0.45.3).
import { drizzle } from "drizzle-orm/node-postgres";
import { pgTable, bigint, text } from "drizzle-orm/pg-core";
import { eq } from "drizzle-orm";
import { Client } from "pg";

const users = pgTable("dd_users", {
  id: bigint("id", { mode: "number" }).primaryKey(),  // number-parsed (verified live: 1, not "1")
  email: text("email").notNull().unique(),
});
const db = drizzle(client);  // over node-postgres Client/Pool (pooling inherited — Databases 04)
const rows = await db.select().from(users).where(eq(users.email, "ann@example.com"));
// Generated: SELECT "id", "email" FROM "dd_users" WHERE "email" = $1 (logged shape = hand shape).
// Relations: usersRelations declared → db.query.users.findMany({ with: { orders: true } })
// (builder-grown graphs — explicit per query, same N+1 discipline as all mappers — 4.1 detector).
```

```typescript
// BAD: Drizzle as untyped query runner (adopting the dependency, declining the guarantees).
// const rows: any[] = await db.execute(sql`SELECT * FROM dd_users`);  // inference declined
// (unknown rows — refactors breaking at runtime — types available, unused); raw strings for
// composable filters (branches interpolated — injection per branch — builders bypassed);
// mode defaults unexamined (bigint-as-string surprising math — parsing choice available, ignored).
// Dependency adopted (bundle weight, upgrade churn), guarantees declined (types, composition,
// parsing — all available, all bypassed). Ceremony without safety (1.2's verdict — restated
// for Drizzle: compose typed or concatenate honestly raw — middle ground is worst ground).
```

**Common confusion** — *"Drizzle is just a query builder (no ORM features)."* 0.45 spans the builder→mapper continuum (relations + `with:` queries + RQB-positioned ergonomics — graph queries served; zero-generation philosophy (no client codegen step — tables as code *are* the types — build pipeline unmodified); migrations via kit (diffs generated — schema evolution tooled). "Just a builder" understates relations/migrations (graph + evolution covered — mapper-adjacent genuinely); "full ORM" overstates (no unit-of-work, no identity map, no lazy loading — explicitness retained deliberately — magic declined structurally). Continuum position stated honestly (builder-grown, mapper-adjacent — thinnest abstraction serving graphs — 1.2's placement, performed).

**Performance note** — Drizzle economics: zero-generation builds (no codegen step — CI unmodified — seconds saved per build vs generated clients); query-count discipline explicit (joins/`with:` written per query — N+1 impossible by accident — same structural property as builders, extended to relations); number/bigint parsing chosen per column (mode:'number' convenience vs bigint correctness past 2^53 — decided, never defaulted — parsing semantics priced per column). Velocity (code-first, inferred, SQL-shaped) with discipline (strategies stated per graph query — 4.1's detector enforced from adoption — same as all mappers, no exception for thinness).

**Mentor note** — teach Drizzle third (raw fluency → builder composition (1.2 performed Drizzle basics already — this leaf places the full tool) → mapper graphs (Prisma/TypeORM above) — downhill pedagogy, each layer legible). Juniors composing typed queries discover SQL *through* Drizzle (autocomplete teaching clauses — same tutor property as builders generally); mapper learners arriving from Drizzle profile generated SQL naturally (logged shapes read hand-written — N+1 visible pre-merge). Order matters absolutely (raw, builders+Drizzle basics, mappers+Drizzle relations — never relations-first). Downhill always; magic never.
