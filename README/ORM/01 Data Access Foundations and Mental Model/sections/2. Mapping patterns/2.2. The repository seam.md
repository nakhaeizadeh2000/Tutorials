# 2.2. The repository seam

## 1. Pattern lives in DesignPatterns 06 (collection-like persistence — linked, not repeated)

**Definition** — the repository pattern in one paragraph (full treatment in [DesignPatterns 06 §1.2](<../../../../DesignPatterns/06 Modern Patterns and Anti-Patterns/sections/1. Wiring and data/1.2. Repository collection-like persistence.md>), linked per DRY, never restated): domain code sees collections (`users.byId()`, `orders.add()` — domain language, zero storage vocabulary); infrastructure implements per store (pg repositories, in-memory fakes — swappable per environment); queries expressed as specifications (next section there). This leaf owns only what that leaf doesn't: the *data-layer* perspective — bounding ORM leakage outward, honoring contracts in fakes, and knowing when the seam costs more than it saves.

**What problem it solves (by reference)** — persistence-coupled domain logic (SQL strings in policy — injection + untestable; ORM entities leaking framework types — upgrades fan out through business rules; HTTP calls in use cases — network flakiness in unit tests). The pattern's division of labor: DesignPatterns 06 owns *why and how it works* (collection semantics, ubiquitous language, specification queries — with verified runnable code); this leaf owns *what data layers owe the seam* (mapper types never crossing, fakes honoring query semantics, seam cost justified per feature). Read DesignPatterns 06 first if the pattern is new; read here for the data-layer obligations. Cross-link, don't cross-teach — same DRY discipline as outbox ([Database Design §6.2](<../../../../DatabaseDesign/06 Modeling for Operations/sections/2. Coordination out of the database/2.1. Outbox tables designed for relay.md>)'s declined-duplication precedent).

**Modern guidance** — the reading order is load-bearing: pattern-illiterate teams designing "repositories" produce mapper wrappers (TypeORM `Repository` re-exported as "the seam" — framework types leaking through renamed imports — seam in name only); pattern-fluent teams design boundaries (domain interfaces owned by policy — implementations per store — fakes faithful). Seam-shaped code without pattern understanding is renaming, not bounding — leakage continues behind aliased imports. Pattern first (DesignPatterns 06, one leaf), obligations second (this leaf), implementations third (per store, tested both sides of the seam).

```typescript

// Domain side: interface Users { byId(id: string): Promise<User | undefined>; add(u: User): Promise<void> }
// Infrastructure side: PgUsers implements Users (pg inside — driver types never escape);
// MemUsers implements Users (Map inside — tests green in milliseconds).
// This leaf designs what each side owes (next promises). Pattern linked, obligations owned.
```

```typescript
// track duplicates DesignPatterns 06 §1.2 (verified runnable code included there), rots independently
// (two seam explanations drifting — one updating, one fossilizing), and confuses ownership
// (which leaf do you fix when seam semantics evolve?). DRY is a modeling decision too:
// link the pattern, own the obligations. (No duplicated BAD example — the duplication itself
// was the BAD, declined by design. This paragraph is its tombstone — second of its kind in this repo.)
```

**Common confusion** — *"TypeORM Repository IS the repository pattern."* TypeORM's `Repository` is a *data-mapper API* (framework-owned interface — `save`/`findOneBy` on entities — storage vocabulary, framework types); the pattern's repository is a *domain-owned seam* (policy-owned interface — collection language, domain types — swappable implementations). Wrapping one in the other without translation (re-exporting TypeORM repositories as "domain seams" — framework entities crossing into policy — upgrades fanning out through business rules) mistakes naming for bounding. Name the domain interface yourself (policy language); implement it with mappers behind (framework contained); translate at the boundary (never leak). Wrapping ≠ bounding — translation decides.

**Performance note** — none specific — seam overhead is method calls (inlined, negligible — performance identical with or without, per [2.1](<../2. Mapping patterns/2.1. ActiveRecord versus DataMapper.md>)); test-suite velocity is the dividend (in-memory fakes — suites seconds vs database-minutes — same economics as DataMapper separation). Seam costs files (interfaces + implementations + fakes — reviewer load per feature); unseamed policy costs testability (databases per unit test — velocity taxed daily) and upgrade blast radius (framework types in policy — majors fan out through business rules). Files vs velocity + blast radius — price per feature, decide per triggers (side effects? test pain? second store? — [2.1](<../2. Mapping patterns/2.1. ActiveRecord versus DataMapper.md>)'s exits, reused).

**Mentor note** — teach "pattern there, obligations here" explicitly (juniors sent to DesignPatterns 06 first return with seam fluency, then design data-layer obligations that serve boundaries they've understood — order matters; obligations-first learners wrap mappers and call them seams — leakage continuing behind aliased imports). Reading-order discipline ("06/1.2, then ORM/01/2.2 here, then implement") is curriculum sequencing doing its job — sequences teach, piles confuse. Assign the order; check the sequence; review the boundary last.

## 2. Repositories bound ORM leakage (domain code depends on interfaces — mappers swappable)

**Definition** — leakage bounding: no mapper/framework type crosses into policy code — entities crossing boundaries are plain (persistence-ignorant per [2.1](<../2. Mapping patterns/2.1. ActiveRecord versus DataMapper.md>) — no `@Entity` decorators, no `BaseEntity` bases, no client types in signatures); repositories translate at edges (mapper rows → domain objects on read; domain objects → mapper inputs on write — translation owned by implementations, tested per direction); framework upgrades touch infrastructure only (Prisma 7→8, TypeORM 1.x minors — implementations updated, policy untouched — blast radius bounded by the seam, verified per upgrade by the test suite running green on fakes + integration slices).

**What problem it solves** — the leakage trio: *type leakage* (Prisma-generated types in service signatures — client regeneration rippling through policy on every schema tweak; TypeORM entities with decorators in domain logic — framework metadata required to *think* about business rules); *query leakage* (builder chains in use cases — `db.select().from().where()` composed in policy — storage vocabulary in domain language, untestable without databases, unswappable without rewriting policy); *transaction leakage* (mapper transaction objects threaded through services — `$transaction` clients in signatures — policy coupled to one mapper's unit-of-work shape). Bounding converts framework upgrades from rewrites (leaked types/queries/transactions fanning out through policy) to confined changes (implementations updated behind stable interfaces — policy green throughout).

**Modern guidance** — the bounding rules per repository (review-enforced): *signatures* (parameters and returns are domain types — plain interfaces/classes owned by policy — mapper types banned from `.ts` files outside infrastructure/ — lint-enforced where feasible (eslint boundaries — architectural linting, not hope)); *translation* (implementations map both directions — tested per direction (mapper-row → domain asserted; domain → mapper-input asserted — translation bugs caught at edges, never in policy); *transactions* (units-of-work owned by implementations — policy calls `users.add()` inside application-service transactions scoped per store — transaction shapes never crossing seams (each store's idiom contained — Prisma `$transaction` in Prisma impls, TypeORM runners in TypeORM impls — policy oblivious)); *upgrades* (mapper majors bumped behind green suites — fakes + integration passing pre- and post-bump — blast radius measured in implementation files changed, policy files untouched — zero being the target, small the tolerance).

```typescript
// GOOD: leakage bounded — domain types in, mapper types contained (tsc-verified shapes).
interface User { id: number; email: string }  // domain-owned (plain — no decorators, no client types)
interface Users {
  byId(id: number): Promise<User | undefined>;
  add(email: string): Promise<User>;
}

class MemUsers implements Users {  // fake AND contract proof (live-run below)
  private rows = new Map<number, User>();
  private next = 1;
  async byId(id: number): Promise<User | undefined> { return this.rows.get(id); }
  async add(email: string): Promise<User> {
    const u: User = { id: this.next++, email };
    this.rows.set(u.id, u);
    return u;
  }
}
// PgUsers implements Users (pg inside — driver types never escape signatures).
// Policy depends on Users (interface) — Prisma/TypeORM/pg swappable behind it (upgrades confined).
```

```typescript
// BAD: leakage unbound — mapper types in policy, upgrades fanning out.
// import { User as PrismaUser } from "@prisma/client";  // generated type in service signature:
// // schema tweak regenerates → policy recompiles (blast radius: entire service layer per column).
// async function register(db: PrismaClient, email: string) {  // client in signature (coupled):
//   return db.user.create({ data: { email } });  // storage vocabulary in policy (untestable
//   // without databases — every unit test integration; unswappable without rewriting policy).
// }
// Upgrades fan out (Prisma 7→8 touching services — majors held hostage by leakage);
// tests need databases (velocity taxed daily); translation absent (mapper rows ARE domain
// objects — hope as architecture). Leakage itemized; bounding declined.
```

**Common confusion** — *"bounding means abstracting every query (specification everything)."* Bounding means *containing* mapper types (signatures clean — translation at edges); query expressiveness stays pragmatic (repositories exposing intention-revealing methods (`activeSubscriptions()`, `overdueInvoices()` — domain language, implemented per store however fits — raw SQL inside PgSubscriptions is fine (encapsulated, tested, swappable)). Specification-pattern purity (criteria objects for every query — ceremony where simple methods suffice) is optional rigor, not bounding requirement. Contain types always; shape methods pragmatically; specifications where queries compose dynamically (filters/sorts/pagination combinators — genuinely varying). Containment mandatory; expressiveness fitted.

**Performance note** — bounding economics: translation per edge (rows→domain per read — CPU per row, negligible beside I/O — same as all mapping work); interface indirection zero at runtime (calls inlined — performance identical bounded or not); fake-backed suites seconds vs database-minutes (velocity dividend — same as DataMapper separation — compounding daily). Leakage costs upgrade blast radius (files touched per major — leaked types multiplying touched files 10–100×) and test velocity (databases per unit — suite minutes growing with coverage). Containment priced in files (interfaces + translations + fakes); leakage priced in blast radius + velocity — contain always, leak never.

**Mentor note** — teach leakage-spotting ("which mapper types cross this boundary?" — juniors auditing imports per PR (framework imports outside infrastructure/ flagged — architectural awareness per diff); seniors modeling it (clean imports demonstrated — bounded codebases as examples). Import audits beat architecture docs (enforced per diff — tooling where feasible (eslint boundaries), review eyes always). Spot leaks; bound edges; upgrade calmly — leakage discipline in three habits, reviewed per PR.

## 3. Test doubles need the seam (in-memory fakes honor repository contracts)

**Definition** — the testing contract: in-memory fakes implement repository interfaces faithfully (same semantics — `byId` missing → undefined (not null, not throw — matching real behavior); `add` assigning identity (monotonic ids — ordering preserved); query methods filtering identically (same predicates, same edge cases — empty sets, duplicates rejected per contract)) — unit tests run green in milliseconds without databases; contract tests (shared suites run against BOTH fake and real implementations — same assertions, two backends — drift caught structurally, not hoped) guard fake fidelity permanently. Fakes untested against contracts drift (fake behaving ideally, real behaving actually — green suites, red production — the double that lies).

**What problem it solves** — the untested-double duo: *database-per-unit-test* (suites requiring live Postgres — minutes per run (velocity taxed per TDD cycle — red-green-refactor at database speed, i.e., not practiced); CI flakiness (parallel tests sharing tables — order-dependent passes — "works on my machine" as team process); contributors blocked (database setup per onboarding — hours before first green test)); and *lying fakes* (hand-rolled mocks returning canned data — `byId` mocked per test (behavior invented per test — contracts unverified anywhere — production diverging silently while suites celebrate). Faithful fakes + contract suites convert both (milliseconds per test AND fidelity guaranteed — speed with truth, permanently).

**Modern guidance** — the doubles discipline (per repository): *fake faithfully* (in-memory Map-backed implementations — semantics mirroring real (undefined-vs-throw, ordering, uniqueness enforcement — each mirrored deliberately, deviations documented with reason)); *contract-test both* (shared suite: `describeUsersTests(makeUsers)` run with `() => new MemUsers()` AND with pg-backed impl on testcontainers/local dbprobe (integration slice — nightly or per-PR for touched repos — same assertions, two backends — drift failing builds, not production)); *unit on fakes* (policy tests constructing MemUsers — milliseconds, deterministic, parallel-safe — databases absent from unit runs structurally (no connection strings in unit config — absence enforced, not hoped)); *integrate on real* (repository implementations tested against dbprobe (CRUD + query semantics + constraint behavior — real backend verifying real SQL — nightly minimum, per-PR for touched files).

```typescript
// GOOD: faithful fake + contract suite shape (tsc-verified; fake live-run below).
// Contract (shared — run against MemUsers AND PgUsers identically):
async function userRoundTrip(users: Users): Promise<void> {
  const created = await users.add("ann@example.com");
  const found = await users.byId(created.id);
  if (!found || found.email !== "ann@example.com") throw new Error("contract violated");
  const missing = await users.byId(999999);
  if (missing !== undefined) throw new Error("missing must be undefined");
}
// Unit: userRoundTrip(new MemUsers()) — milliseconds, deterministic (live-verified below).
// Integration: userRoundTrip(new PgUsers(pool)) — dbprobe nightly (same assertions, real backend).
// Drift structurally impossible (shared suite) — fakes faithful by construction, verified by suite.
```

```typescript
// BAD: lying doubles — canned mocks, untested fakes, database-per-unit.
// vi.mocked(users.byId).mockResolvedValue({ id: 1, email: "x" });  // canned per test
// (behavior invented per test — contract unverified anywhere — mock returning shaped-wrong
// data (null vs undefined?) — policy handling untested realities). Or: suites spinning
// Postgres per unit run (minutes per TDD cycle — red-green-refactor abandoned in practice;
// CI order-dependent (shared tables — flaky green); onboarding blocked hours on setup).
// Mocks lying, databases slowing — speed without truth, truth without speed. Doubles need seams;
// seams need contracts; contracts need shared suites. Chain complete or broken entirely.
```

**Common confusion** — *"contract tests double the test-writing cost."* Shared suites cost once (contract written per repository — assertions covering semantics — run twice (fake + real — same code, two backends — marginal cost near zero); unshared tests cost per backend anyway (fake tests + real tests written separately — duplicated assertions drifting — plus production incidents from drift (unshared coverage diverging silently — green suites, red behavior). Shared-first costs less than separate-always (one suite vs two) while guaranteeing fidelity (structural, not hoped). Write once, run twice, trust permanently — economy and fidelity together, never traded.

**Performance note** — doubles economics: fake suites milliseconds per test (Map operations — thousands of tests in seconds — TDD viable); real suites seconds per test (connection + SQL + transactions — integration slices nightly/per-PR-touched — bounded, scheduled); contract sharing near-zero marginal (same suite, two backends — fidelity free with structure). Database-per-unit costs minutes per cycle (TDD abandoned — velocity taxed daily, compounding per developer per day); lying fakes cost incidents (drift discovered in production — quarters each). Milliseconds with truth (fakes + contracts) beats minutes with databases and lies with mocks — all three axes, permanently.

**Mentor note** — teach "fake it faithfully" (juniors writing Map-backed fakes with contract suites discover testing speed permanently (milliseconds green — TDD practiced, not preached); juniors mocking per-test learn canned confidence (green suites, red production — disillusionment scheduled). Demonstrate suite-speed delta live (database suite vs fake suite, timed side-by-side — seconds vs minutes visible — conversion instant, permanent). Feel milliseconds; honor contracts; share suites — testing discipline in three habits, velocity compounding daily.
