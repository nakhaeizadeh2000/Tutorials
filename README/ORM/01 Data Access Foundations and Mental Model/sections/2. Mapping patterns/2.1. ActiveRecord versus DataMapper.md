# 2.1. ActiveRecord versus DataMapper

## 1. ActiveRecord carries itself (records save themselves — simple, coupled)

**Definition** — Active Record (Fowler's pattern): domain objects carry persistence behavior — `user.save()`, `order.delete()`, `Product.find(id)` — the record knows its table, its connection, its lifecycle. One class per table, behavior colocated with data, zero indirection between intent and storage. TypeORM's `BaseEntity` flavor, Rails' default, Django models' heritage — the pattern beginners reach first because the distance from thought ("save the user") to code (`user.save()`) is zero.

**What problem it solves** — the ceremony objection (repositories, mappers, units-of-work for three-table CRUD — indirection without beneficiaries: simple features drowning in layers prescribed for complex ones). Active Record collapses the stack (model = persistence = validation site — one class reviewed, one file changed per feature, tests constructing records directly without seam plumbing). Prototypes, admin tools, and genuinely simple domains ship fast (features measured in files, not layers — velocity honest, not hoped). Coupling priced later (below), simplicity banked now — the trade stated upfront, never discovered.

**Modern guidance** — default Active Record where lifecycles are trivial (CRUD without side effects — records saved/loaded/deleted, nothing else listening; single-database features — no cross-store coordination; team- or prototype-scale code — readers == authors, roughly). TypeORM's ActiveRecord surface (verified 1.1.1 exports: `BaseEntity` present — `class User extends BaseEntity` + `@Entity/@Column` + `await user.save()`, `await User.findOneBy({...})`). Exit trigger (recorded at adoption — the honest part): side effects arriving (emails on save, events on delete — behavior beyond persistence), test pain arriving (database required per unit test — seam missing), second database arriving (records bound to one connection — sharding/multi-store refactors). Triggers firing → DataMapper (next promise) — graduation scheduled, not hoped.

```typescript
// GOOD: Active Record where lifecycles stay trivial (TypeORM 1.1.1 shapes, exports verified).
import { BaseEntity, Entity, PrimaryGeneratedColumn, Column } from "typeorm";

@Entity()
class User extends BaseEntity {
  @PrimaryGeneratedColumn()
  id!: number;

  @Column({ unique: true })
  email!: string;
}

// Usage: record carries itself (verified API surface — BaseEntity/Entity/Column present).
// const u = User.create({ email: "ann@example.com" }); await u.save();
// const found = await User.findOneBy({ email: "ann@example.com" });
// One class, zero indirection — trivial lifecycles served trivially. Exit triggers recorded beside it.
```

```typescript
// BAD: Active Record past its jurisdiction — side effects smuggled into records.
// class Order extends BaseEntity {
//   async place() { await this.save(); await sendEmail(this); await publishEvent(this);
//     await chargeCard(this); }  // persistence + notifications + events + billing in one method:
//   // untestable without databases AND mailers AND brokers (seam absent — every test integration);
//   // unreusable across contexts (admin imports triggering customer emails — behavior coupled
//   // to persistence lifecycle); second database impossible (records bound to one connection).
//   // Trivial-lifecycle pattern carrying nontrivial behavior — coupling scheduled, incidents pending.
// }
```

**Common confusion** — *"Active Record is an anti-pattern."* Active Record is a *pattern with a jurisdiction* (trivial lifecycles — small scope, few side effects, single store — genuinely optimal: simplicity without ceremony). "Anti-pattern" describes usage past jurisdiction (side-effect-laden records, untestable suites, multi-store refactors blocked — pattern overstayed, not pattern wrong). Judge per feature (lifecycles trivial? → AR honest; side effects arriving? → graduate per triggers), never per fashion (Rails nostalgia vs enterprise ceremony — both vibes, neither engineering). Jurisdiction, not dogma — the track's standing rule applied to patterns.

**Performance note** — Active Record performance is per-operation transparent (one method ≈ statements it issues — `save()` = INSERT/UPDATE — profilable per call, no hidden batching to surprise). Costs arrive via side-effect smuggling (place() issuing N+1 notification/event/billing calls — latency linear in smuggled behavior, invisible in the method name) and test-suite drag (database per unit test — suite minutes growing with coverage — velocity taxed daily). Transparent operations profiled cheaply; smuggled behavior billed opaquely — keep records trivial (side effects exit to services on triggers), profiles clean.

**Mentor note** — teach "when would you graduate this record?" per ActiveRecord class (juniors answering with triggers (side effects? test pain? second store?) design exits at adoption — graduation scheduled, never panicked). Review AR classes for smuggled behavior (methods beyond persistence — emails/events/charges hiding in save-paths — extracted to services on sight). Triggers recorded, smuggling reviewed, graduation celebrated (DataMapper adoption as growth milestone — teams maturing, not failing). Graduate deliberately; smuggle never.

## 2. DataMapper separates concerns (entities ignorant, mappers responsible)

**Definition** — Data Mapper (Fowler's pattern): entities are persistence-ignorant plain objects (no save/find/delete methods — data + domain behavior only); mappers/repositories own all storage (TypeORM `Repository` via `DataSource.getRepository()` — `repo.save(entity)`, `repo.findOneBy(...)` — verified 1.1.1 exports: `DataSource`, `Repository` present). The seam between domain and storage is explicit (in-memory fakes honor repository contracts — unit tests without databases — [2.2](<2.2. The repository seam.md>) owns the seam fully); entities testable in isolation (plain construction — no connection, no decorators-at-runtime beyond metadata — behavior verified without infrastructure).

**What problem it solves** — Active Record's three exits, arrived (side effects needing homes (services calling repositories — notifications/events/billing beside persistence, never inside records); tests needing speed (in-memory repository fakes — suites in seconds, databases reserved for integration slices); stores multiplying (repositories bound per context — read/write splits, multi-tenant stores, sharding — mappers configured per need, entities untouched). Separation converts growth from refactor (AR-to-DM migrations under side-effect pressure — rewrites mid-flight) to configuration (repositories swapped/added — entities stable — new stores onboarded without touching domain code). Priced upfront (indirection per feature — files, interfaces, fakes), profitable at scale (velocity sustained past triviality — teams growing without rewrites).

**Modern guidance** — default DataMapper where AR's exit triggers fire (side effects present, tests slowing, stores multiplying — graduated deliberately per recorded triggers); choose upfront for bounded contexts with evident complexity (order management with payments/notifications/inventory — side effects day one — mapper seam from birth, never retrofitted); keep entities anemic-or-rich per domain need (anemic + services for transaction scripts; rich with domain methods (no persistence calls — behavior without storage — testable, expressive) for complex logic — richness orthogonal to mapping, juniors conflating rich with ActiveRecord corrected once). TypeORM's DataMapper surface (verified 1.1.1: `DataSource` + `getRepository()` + `Repository.save/findOneBy` — same shape as 0.3 lineage — stable API, version-labeled).

```typescript
// GOOD: ignorance + responsibility separated (TypeORM 1.1.1 DataMapper shapes, exports verified).
import { DataSource, Entity, PrimaryGeneratedColumn, Column } from "typeorm";

@Entity()
class User {
  @PrimaryGeneratedColumn()
  id!: number;

  @Column({ unique: true })
  email!: string;
  // No save/find/delete — persistence-ignorant (testable without databases — plain `new User()`).
}

// Storage owned by repository (injected, faked in tests — seam explicit):
// const repo = dataSource.getRepository(User);
// await repo.save({ email: "ann@example.com" });
// const found = await repo.findOneBy({ email: "ann@example.com" });
// Entities stable across stores (repositories reconfigured — multi-tenant/shard-ready, entities untouched).
```

```typescript
// BAD: DataMapper ceremony without cause — indirection serving simple CRUD (the mirror misplacement).
// IUserRepository interface + UserRepositoryPg class + UserRepositoryFake class +
// DI container wiring + unit-of-work abstraction — for a three-table admin tool with
// trivial lifecycles (no side effects, one store, readers==authors). Six files where one
// ActiveRecord class sufficed (indirection without beneficiaries — velocity taxed per feature,
// onboarding burdened per hire ("to save a user, first understand the seam...")). Ceremony
// without cause is the mirror of 1.1's BAD (coupling without need) — misplacement both ways.
```

**Common confusion** — *"DataMapper means anemic entities (no behavior)."* Mapping ignorance (no persistence calls) ≠ behavioral poverty (domain methods welcome — `order.total()`, `user.canAccess(x)` — behavior without storage calls — rich *and* ignorant, testable without databases). Anemic-vs-rich is a *domain* decision (transaction scripts vs domain models — complexity-driven); ignorant-vs-carrying is a *persistence* decision (mapper vs record — lifecycle-driven). Orthogonal axes conflated constantly ("rich entities need ActiveRecord" — false (rich + ignorant via DataMapper — behavior tested without infrastructure); "DataMapper forces services-everything" — false (rich entities hold logic — services orchestrate, entities decide)). Decide separately; combine freely.

**Performance note** — DataMapper economics: indirection overhead zero at runtime (method calls — inlined, negligible — performance identical to AR per statement); test-suite velocity the real dividend (in-memory fakes — suites seconds vs database-minutes — developer feedback loops 10–100× faster — velocity compounding daily); multi-store configuration priced once (repositories per context — setup cost bounded, entities untouched thereafter). Ceremony costs files (interfaces + implementations + fakes — reviewer load per feature); simplicity saves them where lifecycles stay trivial (AR honest there — 1.1's jurisdiction respected, never invaded). Files vs velocity — price per feature, decide per triggers.

**Mentor note** — teach "ignorant entities" via test-speed demonstration (suite with database vs suite with fakes — minutes vs seconds live — juniors *feeling* the velocity difference adopt seams permanently; described benefits persuade never). Ignorance demonstrated (plain `new User()` in unit tests — no connection, no container — tests green in milliseconds); seam honored (repository contracts faked faithfully — fakes reviewed like implementations — contract drift caught per change). Feel velocity; honor seams; graduate deliberately — DataMapper learned once, applied forever.

## 3. This track's tools placed (Prisma, TypeORM, Drizzle mapped honestly)

**Definition** — the placement (versions per track index, as of September 2026): **Prisma 7** (DataMapper-flavored — generated client per schema (`db.user.findMany/create` — client owns storage, models are plain results — entities never carry methods; relations via explicit `include` — graph queries, mapper-owned); **TypeORM 1.x** (both flavors — `BaseEntity` ActiveRecord *or* `Repository` DataMapper — team choice per context, mixed deliberately never accidentally); **Drizzle 0.45** (mapper-adjacent builder — tables as code, queries composed (`db.select().from()`), relations declared (`with:`) — explicit per statement, closest to raw with types). Placements honest (each tool's center stated — client/repositories/composition — fashion excluded, jurisdictions mapped).

**What problem it solves** — tool-choice by hype ("Prisma is modern" — adopted for flat workloads needing typed raw; "TypeORM is enterprise" — adopted with ActiveRecord defaults for side-effect-heavy domains needing seams; "Drizzle is fast" — adopted for graphs needing eager strategies). Misplaced tools bill identically to misplaced patterns (ceremony without graphs, coupling without simplicity, composition without dynamics — 1.1/1.2's misplacements wearing vendor logos). Placement maps tools to jurisdictions (Prisma: typed greenfield APIs with graphs; TypeORM: class idioms/legacy/both-flavors-needed; Drizzle: SQL-control with types, dynamic queries) — matched per feature, never per fashion (Domain 05 compares completely — selection guide with ledgers).

**Modern guidance** — the placement rule (per feature, recorded): graphs + greenfield + end-to-end types → Prisma (schema-first, generated client — DataMapper discipline bundled); classes/decorators idioms OR mixed-flavor needs OR 0.3-legacy → TypeORM (flavor chosen per context — AR for trivial, Repository for growing — mixed deliberately with triggers); SQL-control + dynamic queries + thin abstraction → Drizzle (builder-grown relations — composition retained, ceremony minimal). Default team-wide one primary (cognitive load bounded — polyglot persistence per feature, not per whim — exceptions recorded with reasons); revisit yearly (majors re-price ledgers — Prisma 7→8 RC watch active per track index — versions move, placements re-derived, never inherited blindly).

**Common confusion** — *learning three tools means mastering none.* Foundations transfer (patterns in this domain — AR/DM, builders/mappers, N+1/magic ledgers — tool-agnostic, learned once); tools instantiate (each domain 02–04 teaches one completely — depth per tool, sequenced); comparison selects (Domain 05 — ledgers per workload). "Three tools" is one foundation + three instantiations + one selection method — curriculum, not clutter. Specialists deepening one tool keep foundations portable (job changes, version churns — patterns persist, APIs refresh). Foundations once; tools per need; selection always.

**Performance note** — placement economics close the promise: matched tools perform (Prisma graphs with strategies — N+1 prevented; Drizzle dynamics composed — tuned SQL retained; TypeORM classes persisting — familiar velocity); mismatched tools bill (ceremony without graphs — build times + magic surface for flat fetches; toil without control — hand-mapping under graph mappers; coupling without simplicity — AR past triggers). Match price: correct placement costs a decision paragraph (recorded, dated); mismatch costs quarters (ceremony/incidents/toil per misfit). Paragraphs beat quarters — place deliberately, review yearly.

**Mentor note** — teach placement as "jurisdiction matching" (juniors placing tools per feature shape — graphs/flat/dynamics — with reasons stated — decisions reviewable, revisable, recorded). Placement drills (ten features, ninety seconds each — tool + reason + trigger — rapid-fire verdicts, same prescription as all QA leaves): speed forces internalization (jurisdictions reflex, not reference). Fashion resists drills poorly ("Prisma everywhere" failing flat-workload rounds visibly — misfits exposed in seconds, not quarters). Drill placements; record verdicts; revisit yearly — matching permanent, fashioning temporary.
