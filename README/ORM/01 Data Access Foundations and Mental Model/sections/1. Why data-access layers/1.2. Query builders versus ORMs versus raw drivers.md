# 1.2. Query builders versus ORMs versus raw drivers

## 1. Raw drivers are the truth (full control, zero abstraction — the baseline)

**Definition** — raw drivers (node-postgres `pg` 8.23.0, as of September 2026) send SQL strings with parameters and return rows — no mapping, no query building, no opinions. Every abstraction in this track compiles to driver calls; every bug eventually debugs at driver level (connection errors, type parsing, pool exhaustion surface here, never in prettier wrappers). Raw is the baseline everything prices against: control complete, tedium unremoved, guarantees minimal (parameterization yes, everything else yours).

**What problem it solves** — the wrapper-trap (debugging generated SQL without knowing driver semantics — type-parsing surprises (BIGINT-as-string from 1.1 — driver behavior, not ORM bug); pool exhaustion blamed on the ORM (pool owned by driver config — wrapper merely forwards); connection errors read as framework failures). Raw fluency first means wrapper failures diagnose in minutes (driver layer legible — errors mapped to causes); wrapper-first fluency means driver failures mystify (abstraction hiding the layer where the answer lives). Learn the truth before the conveniences — debugging flows downhill to drivers, always.

**Modern guidance** — default raw where shapes are simple (single-table CRUD, reports with hand-tuned SQL, migrations-adjacent scripts — driver + types + pool, honestly sufficient); graduate when tedium compounds (ten hand-mapped shapes with relations — mapping code exceeding query code — builders/mappers earning keep); never default raw for graphs (relation traversals hand-joined per feature — N+1 by habit, assembly bugs per screen — generators' home turf, conceded early). Raw is a choice with a jurisdiction (simple shapes, tuned SQL, scripts) — not a virtue (hand-mapping graphs is toil, not purity) and not a sin (wrapping simple queries is ceremony, not safety).

```typescript
// GOOD: raw with discipline — parameterized, typed, pooled (verified live: pg 8.23.0, dbprobe).
import { Pool } from "pg";

const pool = new Pool({ host: "localhost", port: 5433, user: "postgres", password: "probe", database: "postgres", max: 10 });

interface UserRow { id: number; email: string }  // translation typed at the boundary (1.1)
async function findByEmail(email: string): Promise<UserRow | undefined> {
  const { rows } = await pool.query<UserRow>(
    "SELECT id, email FROM users WHERE email = $1",  // hand-tuned SQL — full control
    [email],                                          // parameterized — injection closed
  );
  return rows[0];  // mapping trivial (one table, no relations — raw's jurisdiction)
}
// Jurisdiction honored: single table, tuned query, typed rows — no layer needed, none wanted.
```

**Common confusion** — *"raw is faster than ORMs."* Equivalent SQL performs equivalently (same statements, same planner — overhead differs only in mapping CPU (microseconds per row — negligible beside I/O) and query *count* (N+1 vs joined/eager — the actual performance variable, governed by access discipline, not layer choice). "Raw is faster" benchmarks hand-tuned single queries against unprofiled ORM defaults (rigged comparison — tuned-vs-untuned, not raw-vs-mapped). Tune either, profile both — speed follows statements, never layers.

**Performance note** — raw economics: zero mapping overhead (rows used directly — thinnest possible path); full tuning access (hints, exotic SQL, COPY — unreachable behind some mappers — raw reaches everything the engine offers); hand-mapping cost per shape (developer time — the price, paid per feature — graphs multiplying it past justification). Profile at the statement level (EXPLAIN per query — Databases 06 mechanics — layer-independent); count at the request level (statements per render — N+1 visible in any layer with logging on). Statements decide speed; layers decide ergonomics — price each honestly, conflate never.

**Mentor note** — teach raw first (juniors writing parameterized queries + typed rows + pooled clients before touching builders/mappers — driver fluency making every later abstraction legible). Wrapper-first learners mystify at driver errors (connection/type/pool failures unreadable — abstraction hiding answers); raw-first learners debug wrappers in minutes (generated SQL mapped to driver calls mentally — conveniences transparent). Fluency flows downhill (raw → builders → mappers — each layer legible atop the last); teach downhill, never uphill.

## 2. Builders compose SQL (SQL-shaped code — control retained, tedium removed)

**Definition** — query builders (Drizzle 0.45.3 stable, Kysely-flavored kin — as of September 2026) construct SQL programmatically with full type inference — `db.select().from(users).where(eq(users.email, x))` compiles to parameterized SQL, rows typed from table definitions. SQL stays visible (logged statements read like hand-written queries — control retained: every clause expressible, raw escapes always open); tedium removed (no string concatenation — composition over interpolation; no manual mapping — row types inferred from schema-as-code). Builders are SQL with autocomplete — abstraction thinnest where control matters most.

**What problem it solves** — the string-SQL scaling wall (dynamic filters concatenated conditionally — `WHERE 1=1` + appended clauses — injection risk per branch, untestable composition, untyped results throughout); and the mapper-mismatch middle (graphs too simple for ORMs (two-table joins — mapper ceremony unjustified) but dynamic enough to pain string code (optional filters, sorting, pagination — branches multiplying). Builders occupy the middle honestly: dynamic queries composed safely (each combinator parameterized — injection closed structurally per branch), results fully typed (inference from table definitions — refactors rename columns via compiler), SQL always reachable (logged, EXPLAINable, raw-escapable — control never surrendered).

**Modern guidance** — default builders for dynamic relational queries (filtered lists, reports with optional clauses, paginated admin screens — composition earners); prefer builders over mappers where relations stay shallow (1–2 joins, no graph traversal — mapper ceremony unjustified: client generation, relation config, migration coupling — skipped honestly); prefer mappers over builders where graphs dominate (deep relations per feature — hand-composed joins re-implementing eager loading badly — Domains 02–03 territory, conceded). This track's stance: builders are the honest default for most service code (SQL visible, types complete, ceremony minimal — default here, justify mappers and raw per feature).

```typescript
// GOOD: SQL-shaped code — composed, typed, logged (verified live: drizzle-orm 0.45.3 + pg, dbprobe).
import { drizzle } from "drizzle-orm/node-postgres";
import { pgTable, bigint, text } from "drizzle-orm/pg-core";
import { eq } from "drizzle-orm";
import { Client } from "pg";

const client = new Client({ host: "localhost", port: 5433, user: "postgres", password: "probe", database: "postgres" });
await client.connect();

const users = pgTable("dd_users", {
  id: bigint("id", { mode: "number" }).primaryKey(),  // number-parsed (verified live: id 1, not "1")
  email: text("email").notNull().unique(),
});
const db = drizzle(client);
const rows = await db.select().from(users).where(eq(users.email, "ann@example.com"));
// Generated: SELECT "id", "email" FROM "dd_users" WHERE "email" = $1 (parameterized — logged shape = hand shape).
// Rows typed from table definition (inference — refactors rename via compiler). Control retained fully.
await client.end();
```

**Common confusion** — *"builders are just ORMs with extra steps."* Builders map *queries* (SQL composed — relations joined explicitly per query — control per statement); ORMs map *graphs* (objects traversed — relations loaded per access strategy — convenience per model). Different centers (statements vs models), different prices (composition tedium vs N+1/magic risks), different jurisdictions (dynamic queries vs object graphs). Conflating them misplaces both (builders blamed for N+1 they don't cause — explicit joins don't loop; mappers blamed for verbosity they remove). Statements vs models — choose per workload, never by fashion.

**Performance note** — builder economics: mapping CPU identical to raw (rows→objects per row — same work, typed); query count governed explicitly (joins written per query — N+1 impossible by accident (loops visible as loops — no lazy loading hiding per-access queries); eager patterns composed deliberately); generated SQL identical to hand-written (same planner, same plans — logged statements diffed against hand SQL match). Builders price like raw (statements decide speed) with types included (ergonomics free at runtime — compile-time only). Profile generated SQL once per hot path (identical-to-hand verified — then trusted structurally, spot-checked quarterly).

**Mentor note** — teach builders second (after raw fluency — generated SQL legible as hand SQL with types; before mappers — composition understood before graph magic). Juniors composing typed queries discover SQL *through* builders (autocomplete teaching clauses — SELECT/WHERE/JOIN learned with compiler guidance — SQL education disguised as productivity). Builders as SQL tutors (autocomplete + types + logged statements — learning reinforced per query); mappers as graph tools (relations traversed — convenience earned after composition understood). Order matters: raw, builders, mappers — downhill always.

## 3. ORMs map graphs (objects with relations — convenience priced in queries)

**Definition** — ORMs (Prisma 7.10.0 stable with v8.0.0-rc.19 prerelease noted; TypeORM 1.1.1 stable — as of September 2026, per track index) map object graphs to relational rows — models with relations traversed as properties (`order.customer.email` — relation loading per access strategy: eager, lazy, or explicit include). Convenience priced in queries (each traversal potentially a statement — N+1 by default where strategies unexamined; magic per tool (cascades, timestamps, defaults — inventoried per [1.1](<1.1. What problem data-access layers solve and create.md>)). Graphs served whole (nested reads/writes in single calls — the productivity thesis); prices itemized per access (statements counted, strategies stated — the operations discipline).

**What problem it solves** — the graph-mapping toil (hand-joining twelve related tables per order screen — assembly code per feature, mapping bugs per relation, N+1 by habit — [1.1's BAD](<1.1. What problem data-access layers solve and create.md>) generalized across every graph-heavy feature). ORMs collapse graph access to traversals (relations declared once — loaded per strategy — nested writes transacted by the mapper); migrations coupled to models (schema declared beside code — reviewed together — drift structurally prevented); types generated end-to-end (database → client types — refactors renaming columns via compiler across the stack). Graph-heavy products (e-commerce, social, admin suites — relations per screen) earn ORMs quickly (mapping toil dominating feature cost within quarters); graph-light services never do (three flat tables — mapper ceremony unjustified indefinitely).

**Modern guidance** — adopt ORMs where graphs dominate (relations traversed per feature — hand-mapping liability within quarters — Domains 02–03 teach each tool completely); constrain with loading strategies stated (eager vs explicit-include defaults per relation — N+1 prevented by strategy, not hope — [4.1](<../4. Mentor checklist/4.1. Data-access checklist mentors insist on.md>)'s detector enforced from adoption); inventory magic per tool (cascade/timestamp/transaction defaults — listed, surprising entries disabled — 1.1's ledger applied per mapper); keep raw escapes known (unmappable queries — recursive CTEs, exotic SQL — escape hatches exercised deliberately, never feared). **Common confusion** — *"Prisma/TypeORM/Drizzle compete — pick a winner."* Tools occupy different positions (Prisma: schema-first generated client, strongest typing/end-to-end DX; TypeORM: decorator classes, ActiveRecord-or-DataMapper choice, longest history; Drizzle: code-first SQL-shaped, thinnest abstraction, builder-grown relations) — workloads match positions (greenfield typed APIs → Prisma; decorator/class idioms or legacy → TypeORM; SQL-control with types → Drizzle — Domain 05 compares completely). "Winner" framing forces one tool for all workloads (mismatches scheduled — flat workloads under mappers, dynamic queries under graph tools). Positions, not podiums — match per feature, never per fashion (Domain 05's selection guide formalizes this).

**Performance note** — ORM economics (same pattern as 1.1's ledger, graph edition): convenience (graph access per call — feature velocity on relational products — quarters of mapping toil avoided); query-count discipline (strategies stated — include/relations per query — N+1 structurally preventable, detector-enforced); magic inventory (defaults listed — cascade/timestamp/transaction surprises removed); escape hatches (raw reachable — unmappable queries exercised deliberately). Velocity with discipline (strategies + detectors + inventories) outperforms raw toil on graphs (feature quarters vs mapping quarters) and underperforms raw honesty on flat shapes (ceremony without graphs — misplacement priced). Graphs earn; flatness declines — ledger per feature.

**Mentor note** — teach mappers last (raw fluency → builder composition → graph mapping — downhill pedagogy, each layer legible atop the last). Juniors mapping graphs without SQL fluency mystify at generated statements (N+1 invisible — no mental SQL model — surprises scheduled); SQL-fluent juniors profile mappers naturally (generated statements mapped to hand SQL mentally — strategies chosen knowingly). Order matters absolutely (raw, builders, mappers — never mappers-first — uphill teaching produces magic-believers, not engineers). Downhill always; magic never (strategies stated, SQL shown, prices itemized — conveniences transparent).
