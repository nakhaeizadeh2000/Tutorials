# 1.1. What problem data-access layers solve and create

## 1. Mapping is the problem (objects and rows structure differently)

**Definition** — the object-relational mismatch: application code thinks in object graphs (nested customers with orders, behavior attached, identity by reference), databases think in flat rows (normalized tables, joins assembled, identity by key). A data-access layer is the translator between the two — every query translated object→SQL, every result translated rows→objects. The translation is never free (shapes differ structurally — nesting vs joining, graphs vs sets, references vs keys) — layers price it differently (manual mapping, generated mapping, query-shaped code), never eliminate it.

**What problem it solves / history** — pre-layer data access (string-concatenated SQL per query — injection-prone, untyped, untestable; or stored-procedure sprawl — logic locked in the database, versioned never, tested rarely). Layers emerged to move data access into typed, testable, versioned application code: drivers parameterized (injection closed structurally), builders composed (queries built, not concatenated), mappers generated (rows typed as objects — compile-time shape knowledge). Each generation kept the previous one's guarantees while removing its tedium — drivers removed concatenation, builders removed repetition, ORMs removed manual mapping. The mismatch remains (translation priced forever); the ergonomics compound.

**Modern guidance** — choose the translation point deliberately per feature (1.2 prices the three options; [2.1](<../2. Mapping patterns/2.1. ActiveRecord versus DataMapper.md>) places the patterns; [3.1](<../3. First contact/3.1. Hello database three ways.md>) shows all three running). Default posture for this track: typed always (raw SQL in TypeScript with inferred row types counts — `pg` + type annotations, or query builders with full inference — untyped `any`-rows fail review regardless of layer), manual mapping where shapes are simple (one table, no relations — mapping code trivial, layer ceremony wasteful), generated mapping where graphs dominate (relations traversed per feature — hand-mapping N+1-prone, generator-measured). Translation priced per feature, never defaulted per codebase.

```typescript
// GOOD: the translation made explicit — parameterized, typed, minimal (verified: pg 8.23.0 live).
import { Client } from "pg";

const client = new Client({ host: "localhost", port: 5433, user: "postgres", password: "probe", database: "postgres" });
await client.connect();

interface UserRow { id: number; email: string }  // rows typed — translation visible, checked
const { rows } = await client.query<UserRow>(
  "SELECT id, email FROM users WHERE email = $1",  // parameterized — injection closed structurally
  ["ann@example.com"],
);
await client.end();
// Every layer in this track compiles down to something shaped like this —
// SQL over the wire, rows back, translation at the boundary. Layers differ in
// who writes the translation (you, the builder, the generator) — never whether it happens.
// Live note (verified): node-postgres returns BIGINT as string ("1", not 1) —
// parse (parseInt) or use pg-types parsing; mappers handle this per-column-type,
// another translation piece layers own that raw drivers leave to you.
```

```typescript
// BAD: translation denied — strings concatenated, rows untyped, mapping hoped.
// const email = req.body.email;
// const { rows } = await client.query(`SELECT * FROM users WHERE email = '${email}'`);
// Injection open (input becomes code — the 2000s never ended here); SELECT * (shape
// unknown — columns added upstream break downstream silently); rows any-typed (mapping
// errors surface at runtime, in production, per field). Denying the translation doesn't
// remove it — it performs it blindly, per query, forever. Layers exist because this fails.
```

**Common confusion** — *"ORMs eliminate SQL."* ORMs *generate* SQL (inspectable — query logging shows every statement; tunable — raw escapes exist in all three tools). "Eliminate" promises what generated-SQL profilers disprove weekly (N+1 queries wearing object syntax — translation priced per access, invisibly). Engineers who believe elimination stop reading generated SQL ( then discover N+1 in production — the layer's price billed as surprise). Believe generation (inspectable, tunable, priced); disbelieve elimination (translation always happens — the only question is who writes it and who profiles it).

**Performance note** — translation costs: manual mapping (CPU per row — negligible next to I/O; developer time per shape — the real price, paid per feature); generated mapping (hydration overhead per row — object construction + relation wiring — measurable in benchmarks, invisible in production next to network + query time); unprofiled translation (N+1 — queries per parent row — linear in data, the dominant data-access cost everywhere — [4.1](<../4. Mentor checklist/4.1. Data-access checklist mentors insist on.md>)'s detector exists because this dominates). Profile generated SQL from day one (query logging on in development — every statement visible — N+1 caught pre-merge, never post-deploy).

**Mentor note** — teach "show me the SQL" as the layer-agnostic review question (juniors producing ORM code narrate the generated statements — understanding claimed only where SQL shown; seniors skipping the question get it regardless of rank). Layers abstract writing, never reading — readers of generated SQL debug production; believers in elimination page through it. Two reviews of SQL-narration and authors arrive with queries pre-logged — the review teaches profiling by repetition, same pedagogy as every checklist in this repo.

## 2. What layers buy (type safety, migration discipline, connection management — itemized)

**Definition** — the three purchases, each priced separately: **type safety** (row shapes known at compile time — refactors rename columns across the codebase via compiler errors, not production exceptions; relation traversals checked — `order.customer.email` typechecked, not hoped); **migration discipline** (schema changes versioned, reviewed, reversible — expand/contract from [Database Design §5.1](<../../../../DatabaseDesign/05 Evolution Growth and Partitioning/sections/1. Schema evolution/1.1. Expand and contract migrations.md>) executed through tooling, not raw DDL hope); **connection management** (pooling, checkout discipline, transaction scoping — connections acquired per unit-of-work, released deterministically — pool exhaustion designed out, not discovered).

**What problem it solves** — the untyped-unversioned-unpooled trio (column renamed — 40 queries break at runtime across three services, discovered per deploy; migration applied by hand on production console — unwitnessed, unreviewed, unrepeatable; connections opened per request never closed — pool exhaustion under load — the 3 a.m. "too many clients" page). Each purchase converts a production-incident class to a development-time property (compiler errors, reviewed migrations, scoped pools — failures moved left, from pages to red squiggles and failed builds). Bought together they feel like "just using Prisma"; itemized they're three independent reliabilities — adoptable separately (typed raw SQL buys safety without migrations; pooled drivers buy management without mapping).

**Modern guidance** — buy à la carte first (typed queries over pooled drivers — safety + management, zero mapping ceremony — sufficient for simple services, honestly far), add mapping where graphs dominate (relations traversed per feature — hand-mapping N+1-prone at scale — generators earn their keep where object graphs are the workload, not the exception), adopt migrations with the first shared database (solo prototypes migrate informally; team databases migrate reviewed — the discipline arrives with the second writer, never before). Purchases justified per service (CRUD API over three tables: typed raw + pooled — mapping ceremony unjustified; order graph with twelve relations: generated mapping — hand-mapping liability). Price per service, never per dogma.

```typescript
// GOOD: bought à la carte — typed + pooled, mapping deferred honestly (pg 8.23.0 shapes).
import { Pool } from "pg";

const pool = new Pool({ host: "localhost", port: 5433, user: "postgres", password: "probe", database: "postgres", max: 10 });
// Connection management bought (bounded pool — exhaustion designed out), mapping deferred
// (rows typed at query sites — safety bought without ceremony). Graphs absent here —
// no relations traversed, no generator needed. Purchases itemized: safety ✓ management ✓
// mapping ○ (deferred honestly — adopted when graphs arrive, per 2.1's patterns).
await pool.end();
```

```sql
-- BAD: unbought basics — untyped, unversioned, unpooled (the trio, itemized as debt).
-- Untyped: SELECT * rows as any (refactors break at runtime — column renamed, 40 queries
-- failing per deploy, discovered by customers). Unversioned: console-applied DDL
-- (unwitnessed, unreviewed — staging and production drifting silently). Unpooled: new
-- Client per request, never closed (pool exhaustion under load — "too many clients" at 3 a.m.).
-- Each unbought purchase bills quarterly (incidents, archaeology, pages). Buy à la carte early;
-- the trio costs minutes at project start, quarters when discovered in production.
```

**Common confusion** — *"adopting an ORM buys all three automatically."* ORMs bundle all three (Prisma: generated types + migrate tooling + pooled client — convenient), but bundling ≠ understanding (generated types unread → `any` escapes proliferate; migrate tooling unreviewed → flag-day migrations wearing tooling; pooled defaults untuned → exhaustion at defaults' limits). Bundles accelerate adoption; itemized understanding operates them (types read, migrations reviewed, pools sized — per-purchase competence, bundle or not). Adopt bundles; understand purchases — operate each knowingly, never by installer-default.

**Performance note** — purchase economics: type safety costs compile time (seconds per build — cheapest reliability available — errors moved from pages to squiggles); migration discipline costs review minutes (phased migrations, witnessed contracts — [Database Design](<../../../../DatabaseDesign/README.md>)'s ledger); pooling costs sizing thought (max connections vs database limits vs workload concurrency — Databases 04 mechanics — misconfigured pools throttle (too small — queueing) or flood (too large — database contention)). Each purchase priced in minutes-to-hours once; each unbought incident priced in quarters recurring. Buy early; price explicitly; operate knowingly.

**Mentor note** — teach purchases separately (juniors adopting typed-queries first (week one — compiler errors as friends), pooling second (load-tested pools — exhaustion designed out), mapping third (graphs demanding — generators earned) — sequenced adoption building layered understanding). Bundled-first learners conflate the three (Prisma "handles it" — unexamined until incidents separate them forcibly). Sequence purchases; understand each; bundle knowingly — adoption order shaping operational competence permanently.

## 3. What layers cost (abstraction leaks, N+1, magic — each named with its detector)

**Definition** — the three costs, each with its detector: **abstraction leaks** (generated SQL surprising (unexpected joins, missing indexes, cartesian products) — detector: query logging on in development, EXPLAIN on suspicion — leaks found where SQL shown); **N+1** (per-parent queries in loops — `users.map(u => fetchOrders(u))` — N+1 statements for N parents — detector: query counting per request (log line counts in tests — assertions on statement counts — [4.1](<../4. Mentor checklist/4.1. Data-access checklist mentors insist on.md>)); **magic** (convention behavior invisible (cascade defaults, lazy/eager loading defaults, timestamp auto-management) — detector: behavior audits ("what does save() *do*?" — traced per operation, documented per team — magic inventoried, never assumed).

**What problem it solves** — the unpriced-layer failure (ORM adopted for convenience — leaks undiscovered (cartesian products in production — "slow database," actually shape bug); N+1 shipped (list pages firing thousands of queries — latency linear in data, discovered at scale); magic biting (cascade defaults deleting production parents — the ORM's cascade meeting a cleanup script — [Database Design §4.1](<../../../../DatabaseDesign/04 Relationships at Scale/sections/1. Foreign keys at volume/1.1. Foreign keys that survive traffic.md>)'s warning, ORM edition). Naming costs with detectors converts surprises to checks (leaks logged, N+1 counted, magic inventoried — each cost monitored from adoption, never discovered in production). Costs priced beat costs hoped — every layer, always.

**Modern guidance** — the cost ledger per layer adopted (written at adoption, reviewed quarterly): *leaks* (query logging on — development default; EXPLAIN reviews for hot paths — Databases 06 mechanics; raw-escape hatches known per tool — Domains 02–04 teach each); *N+1* (statement-count assertions in tests — lists bounded (N+1 fails builds — [4.1](<../4. Mentor checklist/4.1. Data-access checklist mentors insist on.md>)'s detector); eager/lazy defaults stated per relation — loading strategy decided, never defaulted); *magic* (behavior inventory per tool — cascades, timestamps, soft-delete hooks, transaction defaults — listed, reviewed, surprising entries removed or documented). Ledger reviewed when upgrading tools (new versions change defaults — magic re-audited per major — Prisma 7→8 RC watch noted in track index). Costs monitored; upgrades re-priced; magic inventoried.

```typescript
// GOOD: costs instrumented — leaks logged, N+1 asserted, magic inventoried (shapes verified).
// Leaks: query logging on (every statement visible in development — surprises pre-merge).
// N+1: test asserts statement counts (lists bounded — e.g. "order list renders in ≤3
// statements" — N+1 fails builds, not pages). Magic inventoried per tool (cascade defaults
// listed — surprising entries disabled or documented with reason + owner).
// Ledger reviewed quarterly + per major upgrade (defaults change — magic re-audited).
```

```typescript
// BAD: costs unpriced — convenience adopted, surprises scheduled.
// Leaks: logging off ("noisy") — cartesian products discovered via p99 cliffs in production.
// N+1: uncounted (list pages firing thousands of queries — latency linear in data, found at scale).
// Magic: uninventoried (cascade default deleting parents in cleanup script — data loss wearing
// convenience; lazy-loading defaults N+1-ing every traversal — magic billing per access).
// Adopted for ergonomics; operated on hope; billed in incidents. Costs unpriced, itemized post-hoc.
```

**Common confusion** — *"these costs mean ORMs aren't worth it."* Costs argue for *instrumentation*, not abstinence (layers with detectors outperform manual mapping without them — hand-written N+1 is equally possible, less detectable (no relation metadata to analyze — manual loops uncounted); hand-written leaks equally real (string SQL unlogged — surprises identical). Layers concentrate costs where detectors exist (relation metadata enables N+1 analysis — tooling sees what strings hide). Price costs, instrument detectors, keep layers — abstinence forfeits both convenience *and* detectability. Instrumented layers beat hopeful strings — always, measurably.

**Performance note** — cost economics close the promise: leak detection costs log volume (development-only — production sampling — negligible); N+1 assertions cost test milliseconds (statement counting per list test — bounded, fast); magic inventories cost review minutes (per tool adoption + per major upgrade). Unpriced equivalents cost incidents (p99 cliffs, linear latencies, cascade data loss — quarters each). Detection priced in minutes-to-hours once; incidents priced in quarters recurring. Instrument early; review quarterly; re-price per major — costs managed, never surprising.

**Mentor note** — teach "name the cost" per layer adopted (juniors adopting Prisma listing leaks/N+1/magic with detectors — adoption proposals including cost ledgers — reviewed completely, operated knowingly). Cost-blind adoptions ("Prisma is nice") vs cost-aware ones ("Prisma, with logging/assertions/inventory per ledger") — review distinguishes in one question ("and the costs?" — silence fails structurally). Name costs; instrument detectors; review ledgers — adoption complete only when costs priced. Priced adoptions; operated layers; no surprises.
