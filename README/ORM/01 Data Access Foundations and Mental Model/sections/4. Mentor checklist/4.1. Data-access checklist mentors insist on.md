# 4.1. Data-access checklist mentors insist on

## 1. Name the layer per feature (raw, builder, or ORM — chosen, not drifted)

**Definition** — the review's first pass over data access: for each feature touching the database, the author names its layer (raw + types, builder-composed, or mapper-operated — with the jurisdiction reason: shapes simple? queries dynamic? graphs dominant? — [1.2](<../1. Why data-access layers/1.2. Query builders versus ORMs versus raw drivers.md>)'s placement applied). Unnamed layers fail review structurally — code unexamined until the layer choice is stated (layer determines which checks apply: raw → parameterization + types audit; builder → composition safety + inference audit; mapper → strategy + magic audit). Choice first, code second — always.

**What problem it solves** — layer drift (features accreting data-access styles per author per month — raw strings beside Prisma calls beside Drizzle compositions in one service — each unreviewed as a choice, all coexisting as sediment; onboarding asking "which do we use?" — answer: "all of them, historically"). Drift taxes comprehension (three idioms per codebase — readers context-switching per file), upgrades (three ledgers per major — magic re-audited thrice), and hiring (candidates assessed on all three surfaces). Named layers convert drift to decisions (recorded per feature — team default + documented exceptions — uniformity where shapes agree, deliberate variety where workloads differ).

**Modern guidance** — the layer review lines per feature: layer named ("Drizzle — dynamic filtered lists, 1–2 joins — builder jurisdiction"); alternatives declined with reason ("Prisma: no graphs here (ceremony unjustified); raw: filters dynamic (string branches unsafe)"); team default relationship stated ("default Drizzle per ADR-001 — this feature conforms (or exception #12 filed with reason + revisit)"); migration path named where applicable ("reads raw today, mapper when graphs arrive — trigger recorded (relations >2 → re-evaluate)"). Missing line → request changes; "we've always used X" → asks for the jurisdiction reason (tradition unstated is drift with seniority — re-derive or record exception, never coast).

```typescript
// GOOD: the layer review artifact — named, reasoned, default-related (excerpt).
// Feature: admin user list (filters + sorting + pagination, 2-table join).
// Layer: Drizzle (builder — dynamic composition, typed inference, SQL visible).
// Declined: Prisma (no graphs — ceremony unjustified); raw (dynamic filters — string branches unsafe).
// Default: team Drizzle per ADR-001 — conforms (no exception). Migration trigger: none
// (graphs unforeseeable here — stated, dated). Verdict: approve layer.
```

```typescript
// BAD: the layer-blind review — code examined, choice unasked.
// "Queries look fine. +1." (Layer? Unstated — Prisma client wrapping single-row fetches
// (ceremony without graphs). Alternatives? Unconsidered — dynamic filters hand-concatenated
// beside mapper calls (injection beside abstraction — worst of both). Default? Unknown —
// fourth data-access idiom this quarter (drift compounding). Triggers? Absent — graphs
// arriving unplanned, mappers unadopted.) Code approved; layer drifted; consequences scheduled.
```

**Common confusion** — *"one layer per codebase (standardize everything)."* Uniformity serves onboarding and upgrades (one idiom, one ledger, one upgrade path — genuine benefits); per-feature jurisdiction serves correctness (flat admin tools under mappers (ceremony), dynamic reports under graph tools (control surrendered), graphs under raw strings (toil + N+1)). "One layer everywhere" confuses uniformity with fitness (standardized misfits — velocity taxed per misfit). Team default + documented exceptions (uniformity where shapes agree — most code; deliberate variety where workloads differ — recorded, revisited). Default strongly; except explicitly; drift never.

**Performance note** — layer review is upstream performance work (same argument as every checklist leaf in this repo: misplaced layers bill perversely (mapper ceremony on flat shapes — build times + magic surface, zero graph benefit; raw toil on graphs — N+1 + assembly bugs, zero control benefit); placed layers perform natively (statements tuned per jurisdiction — builders composing, mappers strategizing, raw hand-tuning). Review minutes convert to incident-quarters avoided at the usual rate — highest-ROI minutes in data-access work, permanently true.

**Mentor note** — teach "name the layer" as the data-access review opener (juniors stating jurisdictions design deliberately from the first PR; seniors skipping get the same question regardless of rank). Two reviews of enforced naming and authors arrive pre-decided (layer + reasons + default relationship stated upfront — review accelerating instead of interrogating). Praise placed layers ("good builder call — dynamics justify it") louder than clever queries — teams optimize for praised behavior, and clever misplaced queries have had enough admirers.

## 2. Count the queries (N+1 detector on every list — measured, never hoped)

**Definition** — the review's second pass over reads: every list/collection endpoint arrives with its statement count asserted (tests logging statements per render — bounded: "order list ≤3 statements" — N+1 failing builds, not pages). Counting is structural (query logging in test env — every statement visible; assertions on counts per list test — bounds enforced; relation strategies stated per query (include/relations/with — eager by decision, never default). Uncounted lists fail review — "should be fine" is hope with syntax (hope unmeasured, N+1 scheduled).

**What problem it solves** — the shipped N+1 (list pages firing per-parent queries — latency linear in data — discovered at scale ("slow with real data" — staging's ten rows hiding production's ten thousand); ORM relation traversals lazy by default (per-access statements — magic billing per touch — [1.1](<../1. Why data-access layers/1.1. What problem data-access layers solve and create.md>)'s price uncollected); hand-rolled loops (raw/builder code fetching per parent — loops visible but uncounted — "only a few" growing unboundedly). Counting converts linear latencies to build failures (tests red before merge — N+1 fixed in development, never paged in production). Measured lists stay fast; hoped lists degrade with data — data always grows, hope always expires.

**Modern guidance** — the counting contract per list endpoint: *assert* (statement-count assertions in tests — bound derived from shape (1 + fans, never 1 + N) — [Domain 04 §3.1](<../../../../DatabaseDesign/04 Relationships at Scale/sections/3. Skew and hot relationships/3.1. Hot keys and skew.md>)'s fan-out rule applied to queries); *strategize* (relation loading stated per query — include/relations/with explicit — defaults audited (lazy defaults flipped where lists traverse — strategy decided per relation, never defaulted globally); *log* (query logging on in development/test — every statement visible per render — surprises pre-merge); *budget* (statements-per-render budgeted like latency (paginated lists: constant statements regardless of page fullness — page-size growth never multiplying queries — budget enforced, not hoped). Missing assertion → request changes; "tested manually, looked fine" → staging's ten rows prove nothing (data-scaled tests or it didn't happen).

```typescript
// GOOD: the counting review artifact — asserted, strategized, logged, budgeted (excerpt).
// Endpoint: GET /orders (paginated, 50/page, lines included).
// Assert: ≤3 statements/test (orders page + lines batch + count — N+1 fails builds) ✓.
// Strategy: lines via explicit include (stated per query — lazy default flipped here) ✓.
// Log: statements visible per test render (surprises pre-merge) ✓.
// Budget: constant vs page fullness (50 rows ≠ 50 queries — verified at max page) ✓.
// Verdict: approve reads.
```

```typescript
// BAD: the uncounted list — hope with endpoints (N+1 scheduled, scale-billed).
// Endpoint: GET /orders (controller returning ORM objects with lazy relations).
// Assert: none ("works in staging" — ten rows, two queries — production's ten thousand
// rows firing ten thousand and two). Strategy: defaults (lazy everywhere — per-access
// statements — magic billing per touch). Log: off ("noisy" — surprises scheduled).
// Budget: none (page growth multiplying queries — linear latency, discovered at scale).
// Hope approved; N+1 shipped; latency linear; pages scheduled (dateless, as usual).
```

**Common confusion** — *"counting queries is premature optimization."* Optimization without measurement is premature; counting *is* measurement (statements per render observed — bounds enforced — N+1 prevented structurally). "Premature" describes tuning unmeasured hot paths (index fiddling pre-evidence); counting describes bounding known-linear failure (N+1 scales with data — certainty, not suspicion). Bounds are correctness-adjacent (linear latency is a bug wearing a performance costume — budgets enforced like correctness). Count always; tune on evidence; confuse never.

**Performance note** — counting economics: assertions cost test milliseconds (statement counting per list test — bounded, fast); strategies cost thought per relation (eager/explicit decisions — minutes, once); logging costs log volume (development/test only — negligible). Uncounted equivalents cost linear latencies (page time × data growth — discovered at scale — quarters of remediation: eager rewrites, cache bandages, pagination retrofits). Milliseconds in tests prevent quarters in production — the steepest testing ROI in data-access work (stated finally — count everything list-shaped, always).

**Mentor note** — teach "how many queries?" per list PR (juniors answering with counts design bounded reads on first hearing; answering "not sure" learn the detector in one question). Demonstrate N+1 live once (staging with production-scale seed — list rendering thousands of queries logged — latency visible, faces paling — conversion instant, permanent). Counted lists stay fast; demonstrated N+1 stays remembered (one live demo beats ten lectures — show, don't tell, then enforce). Ask counts; demo scale; enforce bounds.

## 3. Migrations are reviewed like code (expand-compatible, witnessed, reversible)

**Definition** — the review's closing act over schema changes through data-access tooling (Prisma migrate, TypeORM migrations, drizzle-kit diffs): same discipline as [Database Design §5.1](<../../../../DatabaseDesign/05 Evolution Growth and Partitioning/sections/1. Schema evolution/1.1. Expand and contract migrations.md>) — expand-compatible (old code runs against new schema — stated per migration), witnessed (contract verified — grep zero + freeze observed — drop ships on evidence), reversible (rollback per phase — expand drops additions, migrate switches readers, contract unreturned — verification precedes). Tooling executes; discipline governs — generated migrations reviewed line-by-line (diffs read like hand DDL — auto-generated never auto-approved), phases honored regardless of generator.

**What problem it solves** — the tooling-trust failure (generated migrations applied unreviewed ("Prisma made it" — flag-day NOT NULLs wearing tooling; drops unwitnessed — dashboards breaking Monday; renames as drop+create (data loss wearing migration — generator defaulting destructive when renaming undeclared); synchronize:true in production (TypeORM auto-mutating per deploy — typo'd decorators dropping columns — [3.1](<../3. First contact/3.1. Hello database three ways.md>)'s initiation failures, operationalized). Tooling accelerates DDL authoring; discipline governs DDL shipping — confused, generators ship incidents at machine speed (flag-days automated, drops unwitnessed, renames destructive — velocity without judgment, billed quarterly).

**Modern guidance** — the migration review lines per tool-generated diff: phase named (expand/migrate/contract — [Database Design §5.1](<../../../../DatabaseDesign/05 Evolution Growth and Partitioning/sections/1. Schema evolution/1.1. Expand and contract migrations.md>) — generator output classified, never assumed safe); compatibility both directions stated (old writers/new readers — [Domain 05 §1.2 analogue applied through tooling — tooling doesn't exempt compatibility, it executes phases); renames declared (Prisma `// @renamed` / explicit rename mapping — drop+create diffs rejected on sight — data-preserving renames only); drops witnessed (grep zero + freeze — same sacrament, tooling-executed); synchronize forbidden past development (TypeORM flag — CI fails on `synchronize: true` outside dev — linted, never hoped). Generated diffs read fully (every line — diffs are code — review completeness enforced, not hoped).

```sql
-- GOOD: the migration review artifact — phased, compatible, witnessed, reversible (excerpt).
-- Diff: ADD COLUMN email TEXT nullable (expand — old writers safe ✓); backfill job linked
-- (chunked 5k, lag-throttled ✓); readers switched with COALESCE fallback (ticketed removal ✓).
-- Renames: none (declared-nothing — drop+create absent — verified by diff reading).
-- Drops: none this phase (contract later — grep + freeze scheduled, not hoped).
-- synchronize: false (linted). Verdict: approve migration.
```

```sql
-- BAD: the tooling-trust merge — generated, unreviewed, flag-dayed.
-- Diff: ADD COLUMN email TEXT NOT NULL (flag-day NOT NULL — old writers failing — generator
-- authored, human approved blindly ("migrate made it")). RENAME detected as DROP+CREATE
-- (data loss wearing migration — undeclared rename, unwitnessed drop — history destroyed
-- with applause). synchronize: true (production auto-mutating — typo'd decorator dropping
-- emails fleet-wide — convenience executing data loss). Tooling trusted; discipline absent;
-- incidents automated. Generate always; approve never-blindly.
```

**Common confusion** — *"migration tooling handles safety automatically."* Tooling handles *mechanics* (diff generation, ordered application, checksums, rollbacks of application — valuable, real); discipline handles *compatibility* (phases, witnesses, reversibility judgments — human, contextual, ungeneratable). "Handles safety" conflates mechanics with judgment (tools executing flag-days flawlessly — perfectly-executed incidents — speed without wisdom). Mechanics automated (gratefully); judgment reviewed (always); confusion never (tooling-trust fails structurally — reviewers reading diffs fully, classifying phases, witnessing contracts — humans governing, tools executing).

**Performance note** — migration-review economics (same argument as every checklist leaf in this repo, ORM edition): phased tooling-migrations distribute load (no blocking rewrites in windows); witnessed contracts prevent repair migrations (most expensive kind — incident-pressured, unrehearsed); synchronize-forbidden prevents auto-mutation outages (typo'd decorators contained to review, never executed). Review minutes convert to outage-quarters avoided at the usual rate — highest-ROI minutes in data-access operations, permanently true.

**Mentor note** — teach "read the generated diff" (juniors reading tool output line-by-line discover generators' assumptions (drop+create renames, flag-day nullability, synchronize mutations) permanently — generated code reviewed like hand code, always). Automate the checkable half (CI: synchronize-true fails builds; drop-without-witness fails; undeclared-rename drop+create fails — linters for migrations, same as 05/4.1's); review the judgment half (phases, compatibility, witnesses). Machines check shape; mentors check sequence — split accordingly, first domain running, permanent value.
