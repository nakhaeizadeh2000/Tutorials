# 3.1. N+1 strategies and raw escapes

## 1. Count statements per render (logging + assertions — N+1 fails builds)

**Definition** — the counting discipline performed Prisma-specifically (general rule in [Domain 01 §4.1](<../../01 Data Access Foundations and Mental Model/sections/4. Mentor checklist/4.1. Data-access checklist mentors insist on.md>)): query events observed (`log: [{ emit: "event", level: "query" }]` + `$on("query")` counters — verified live below), statements counted per render (lists asserting bounds — "order list ≤3 statements" — N+1 failing builds, never pages), strategies stated per relation (include/select per query — [2.2](<../2. Migrations and client/2.2. Client queries and relations.md>) — eager by decision, never default). Version note (verified live this session): Prisma 7 removed `$use` middleware — counting via `$on("query")` events (v6-era `$use` tutorials stale — migration required, silent breakage otherwise).

**What problem it solves** — the uncounted list (endpoints rendering with per-parent queries — latency linear in data — staging's ten rows hiding production's ten thousand; hand loops beside the client (per-parent findUnique — N+1 wearing client syntax — batching declined where include would serve); middleware-shaped counting from v6 tutorials (silently broken on v7 — `$use is not a function` — verified live this session — counters absent, N+1 unobserved). Counting converts linear latencies to build failures (tests red before merge — N+1 fixed in development); v7 event-counting converts middleware breakage to working gauges (events observed — statements counted — discipline intact across majors).

**Modern guidance** — the counting contract per list endpoint (verified live shapes): *observe* (`$on("query")` counters in tests (verified live: 3 statements for 1+2 loop vs 2 batched — counting demonstrated, not described); *assert* (statement bounds per list test — ≤N derived from shape (1 + fans, never 1 + N) — N+1 failing builds); *strategize* ([2.2](<../2. Migrations and client/2.2. Client queries and relations.md>)'s include/select per relation — eager by decision); *log* (query events in development/test — every statement visible per render — surprises pre-merge). Missing assertion → request changes; v6 `$use` counters → migrate to `$on("query")` (verified breakage — majors re-price ledgers per [Domain 01](<../../01 Data Access Foundations and Mental Model/README.md>)).

```typescript
// GOOD: counting via v7 query events — N+1 measured, batching verified (verified live).
const db = new PrismaClient({ adapter, log: [{ emit: "event", level: "query" }] });
let statements = 0;
db.$on("query", () => { statements++; });   // v7: events (verified — $use removed in v7!)
// Loop shape: 1 findMany + N per-parent → statements 1+N (verified live: 3 for N=2).
// Batched shape: findMany({ include: { enrolls: true } }) → statements 2 (verified live).
// Test: assert statements ≤ bound per list (N+1 fails builds — counted, never hoped).
```

```typescript
// BAD: uncounted lists + stale middleware — hope with endpoints, breakage with majors.
// const students = await db.student.findMany();  // no strategy (relations unloaded — deliberately? unasked?)
// for (const s of students) await db.enrollment.findMany({ where: { studentId: s.id } });
// (N+1 wearing client syntax — uncounted (staging green on 10 rows — 10k statements in production).)
// db.$use(async (params, next) => {...});  // v6 middleware on v7 (verified live breakage:
// "$use is not a function" — counters dead silently (no error at import — runtime TypeError
// on first call — gauges absent from the migration that removed them). Uncounted + stale.)
```

**Common confusion** — *"Prisma batches everything (no N+1 possible)."* Batching covers *declared includes* (one query per include path — structural — verified live: 2 statements batched); hand loops bypass batching (per-parent calls — N+1 fully manual — verified live: 3 statements for N=2 — framework unable to help undeclared traversals); middleware removal breaks counters, not batching (v7 `$use` gone — gauges migrated to events — batching intact throughout). "Batches everything" credits includes with loop prevention (loops unbatched by definition — authorial); v7 changes gauges, never batching semantics. Batching declared; loops counted; gauges migrated — all three, always.

**Performance note** — counting economics: event counters cost microseconds per statement (test-only overhead — production sampling — negligible); assertions cost test milliseconds (bounds per list — bounded, fast); uncounted N+1 costs linear latency (page time × data growth — discovered at scale — quarters of remediation: eager rewrites, cache bandages, pagination retrofits). v7 migration costs one gauge rewrite per suite (`$use` → `$on("query")` — minutes, once — majors re-priced). Milliseconds in tests prevent quarters in production — counting ROI unchanged across majors (gauges migrated, discipline permanent).

**Mentor note** — teach "count first" with v7 events (juniors wiring `$on("query")` counters discover N+1 shapes tangibly — 3 vs 2 statements live — counted, not theorized; v6 `$use` muscle memory corrected once (verified breakage demonstrated — migration learned, not read). Counting taught as reflex ("how many statements?" per list PR — asked until automatic); v7 events taught as current idiom (docs checked per major — version-skewed tutorials corrected structurally, never trusted blindly). Count always; version-check gauges per major.

## 2. Batch with include, paginate with cursor (constant statements regardless of N)

**Definition** — the two scaling rules performed Prisma-specifically: **batch relations** (`include` per path — one query per include — constant statements regardless of N — verified live: 2 statements for N=2 (batched) vs 3 looped); **paginate by cursor** (`cursor: { id }` + take — keyset constant-cost pages — deep pages never OFFSET-scanning ([Databases 07 §2.2](<../../../../Databases/07 Production Data Use and Interview Mastery/sections/2. Review and design/2.2. Data API contracts.md>) mechanics applied through client — page-50000 cost equals page-1 cost). Constant statements (batching) + constant pages (cursors) = list performance independent of data size — scaling structurally, never hoped.

**What problem it solves** — the scaling duo: *unbatched relations* (per-parent queries — linear statements — latency scaling with data — fixed by includes (verified live delta: 3→2 at N=2, widening per N — savings scaling with data, costs constant); *OFFSET deep pages* (`skip: 500000, take: 50` — page N scans N rows — seconds per deep page, growing — cursor migration unplanned ("works in staging" — shallow pages fast, deep pages linearly slow — production's deep links timing out). Batching converts linear statements to constant; cursors convert linear pages to constant — both structural (shapes, not tuning — scaling by construction, O(1) per dimension).

**Modern guidance** — the scaling lines per list endpoint (review-enforced): *batch* (include per relation path — verified live counts — N+1 absent structurally where includes declared; hand loops rejected (batching declined — loops rewritten to includes or split queries per fan-out rule)); *cursor* (deep pages via `cursor` + take (+ `orderBy` unique — deterministic paging — cursor on non-unique fields pages ambiguously — unique cursor required, stated); *split fans* (multi-list includes multiplying transfer — split queries per Database Design 04 rule (cause removed) — constant statements AND bounded transfer, both); *assert both* (statement counts + page-cost-vs-depth (page-1 vs page-1000 timings — cursor constant verified, OFFSET linear demonstrated — evidence per endpoint, never hoped).

```typescript
// GOOD: batched relations, cursor pages — constant costs regardless of N (verified live shapes).
const page1 = await db.student.findMany({ include: { enrolls: true }, take: 50 });
// (batched: 2 statements for any N — verified live pattern (N=2 measured; scales constant).)
const deep = await db.student.findMany({ cursor: { id: lastSeenId }, take: 50,
  orderBy: { id: "asc" } });   // keyset (constant per page — page-50000 equals page-1 cost;
// OFFSET alternative: skip: 50000 (linear scan per deep page — cursor migration ticketed on depth).
```

```typescript
// BAD: unbatched loops, OFFSET depths — linearities compounding (scale billed twice).
// for (const s of students) await db.enrollment.findMany({ where: { studentId: s.id } });
// (verified live: 1+N statements — linear in data — batching declined where include serves.)
// await db.student.findMany({ skip: 500000, take: 50 });  // deep OFFSET (page N scans N rows —
// seconds per deep page, growing — cursor unplanned ("works shallow" — deep links timing out in
// production). Linear statements × linear pages — quadratic-feeling slowness, both structural,
// both fixable, neither tuned (tuning unmeasured linearities wastes quarters — reshape instead).
```

**Common confusion** — *"cursor pagination is complex (OFFSET simpler)."* Cursor complexity is one-time (unique orderBy + cursor object — lines, learned once); OFFSET cost is recurring (linear scans per deep page — paid per render, growing with data — simplicity billing per query forever). "Simpler" describes authoring (OFFSET fewer concepts — minutes saved once); cursor describes operating (constant pages — quarters saved continuously). Authoring-simplicity vs operating-simplicity — optimize for operations (queries run millions of times; authoring happens once). Cursor by default past shallow pages; OFFSET tolerated shallow-only (bounded depth, stated).

**Performance note** — scaling economics: batched includes cost constant statements (verified live — 2 regardless of N — transfer O(page)); cursors cost constant pages (verified pattern — page-50000 equals page-1 — transfer O(page), planning O(1)); OFFSET costs O(depth) per page (linear scans — deep pages seconds-growing); loops cost O(N) statements (linear — latency scaling with data). Constants beat linears at scale by definition (crossover early — page ~100 typical — measured per endpoint, never hoped). Batch relations; cursor depths; assert both — scaling structural, complete.

**Mentor note** — teach "constant vs linear" per list (juniors classifying each list's statement growth (constant (batched+cursored) vs linear (looped/OFFSET) — growth stated per endpoint, linearities ticketed with migration plans). Growth classification generalizes (every scaling question reduces to constant-vs-linear per dimension — rows, pages, fans, shards — the universal performance vocabulary). Classify growth; ticket linears; verify constants — scaling literacy in three habits, reviewed per list endpoint.

## 3. Escape to raw deliberately (queryRaw for the unmappable — typed, logged, fenced)

**Definition** — the escape discipline: `$queryRaw` (parameterized template literals — injection closed structurally — verified live: ``SELECT count(*)::int`` typed row returned) and `$executeRaw` (parameterized mutations — verified live: conditional update executing) for queries the client can't express (recursive CTEs, window-function analytics, COPY-adjacent bulk paths, exotic PG operators). Escapes are *deliberate* (unmappable, stated — escape reason recorded per query ("recursive traversal — beyond client combinators"); typed via generics (`$queryRaw<UserRow>` — rows inferred, never `any`); logged like all SQL (query events observing — escapes counted in statement budgets — no dark SQL).

**What problem it solves** — the escape duo: *escape-shame* (unmappable queries contorted through client combinators (convoluted includes approximating recursion — unreadable, incorrect — abstraction stretched past jurisdiction); and *escape-sprawl* (raw for everything convenient (`$queryRawUnsafe` with interpolation — injection per branch — typed generics declined — escapes as default, client as decoration). Deliberate escapes convert both (unmappable → raw with reason recorded + types via generics + logs observed; mappable → client combinators (escape rejected in review — "expressible composed — compose it")). Escapes fenced (reasoned, typed, logged) serve; escapes sprawled (convenient, untyped, dark) rot.

**Modern guidance** — the escape lines per raw query (review-enforced): *reason* (unmappable, stated — "recursive CTE beyond combinators" — reason recorded; mappable-via-client escapes rejected (compose instead — escape declined with pointer to combinators)); *types* (generics parameterizing rows (`$queryRaw<CountRow>` — verified live pattern: `[{n: 2}]` typed — `any` rows failing review structurally); *parameters* (template-literal interpolation only (`$queryRaw\`... ${value}\`` — parameterized always; `queryRawUnsafe` with string concat rejected on sight (injection by construction — escape hatch marked DANGER used as default — never); *logs* (escapes counted in statement budgets (logged like all SQL — dark SQL absent — escapes observed per render). Missing reason/types/logs → request changes; unsafe interpolation → request changes with prejudice (injection reviewed as severity-1, always).

```typescript
// GOOD: escapes fenced — reasoned, typed, logged (verified live).
const counted = await db.$queryRaw`SELECT count(*)::int AS n FROM "Student"`;
// (verified live: [{"n":2}] — typed via inference (cast in SQL — ::int asserted at source).
// Reason: aggregation beyond find APIs (stated); logs: counted in budgets (observed).
await db.$executeRaw`UPDATE "Student" SET name = name WHERE id = ${1}`;
// (verified live: executeRaw ok — parameterized interpolation ($1 bound — injection closed).
// Unsafe variant rejected: queryRawUnsafe + concat (injection structural — never).
```

```typescript
// BAD: escapes sprawled — convenient raws, untyped rows, dark SQL.
// const u = await db.$queryRawUnsafe(`SELECT * FROM "User" WHERE email = '${email}'`);
// (interpolation — injection per branch (unsafe API chosen over template literals — DANGER
// normalized); SELECT * untyped (any rows — refactors breaking at runtime); unlogged
// (dark SQL — statement budgets blind — N+1 hiding in raws, uncounted). Mappable queries
// raw-written (findUnique expressible — escape without reason — combinators declined for
// familiarity). Sprawl: convenient, untyped, dark. Fence escapes or forbid them (fenced
// deliberately — the only raw this track approves).
```

**Common confusion** — *"raw escapes defeat the ORM's purpose."* Escapes *complete* it (clients covering ~95% (CRUD + relations + filters — composed, typed); escapes covering the unmappable remainder (recursion, windows, bulk — reasoned, typed, logged). "Defeat" describes sprawl (raw by default — client decorative — purpose abandoned); fenced escapes serve purpose (client default, raw deliberate — coverage complete, 100% typed, 100% logged). Purpose = typed, logged, reviewed data access (client + fenced escapes together); sprawl = untyped dark SQL with client installed nearby (purpose abandoned). Fence deliberately; cover completely.

**Performance note** — escape economics: fenced escapes perform identically to hand SQL (same statements, same planner — parameterized, logged, reviewed); sprawled escapes perform unpredictably (unlogged = unprofiled (slow paths invisible — discovered via p99 cliffs); untyped = unrefactorable (column changes breaking at runtime — velocity taxed per change). Escape review costs minutes per query (reason/types/logs checked); sprawl costs incidents (injection/security + performance mysteries + refactor breakage — quarters each). Fence cheaply; sprawl dearly — escape discipline permanently.

**Mentor note** — teach "reason, types, logs" per escape (juniors stating all three design fenced raws on first hearing; unstated escapes interrogated ("unmappable how?" — reason demanded; "typed how?" — generics demanded; "logged where?" — budgets demanded). Unsafe-interpolation rejection taught as severity-1 (injection reviewed like data loss — because it becomes data loss — prejudice stated openly, exceptions never). Reason, type, log — escape complete only with all three; unsafe never regardless. Fence escapes; forbid unsafe.
