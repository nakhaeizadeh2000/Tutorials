# 2.2. Client queries and relations

## 1. Find APIs compose precisely (where/orderBy/take — filters typed end-to-end)

**Definition** — Prisma find APIs (`findMany`/`findUnique`/`findFirst` + `where`/`orderBy`/`take`/`skip`/`cursor`) compose queries programmatically with end-to-end types (filters checked against schema — `where: { emial }` fails compilation (typo caught, not queried); orderings constrained to sortable fields; pagination typed (take/skip numbers, cursor objects — shapes checked, never hoped). Composition replaces concatenation (dynamic filters built as objects — `...(cond && { field })` — injection impossible structurally (values parameterized always — builders' guarantee inherited); untyped strings absent (no SQL fragments in application code — the layer's boundary honored).

**What problem it solves** — the string-filter habit (dynamic WHERE concatenated per branch — injection per interpolation, untestable composition, untyped results — [Domain 01 §1.2](<../../../01 Data Access Foundations and Mental Model/sections/1. Why data-access layers/1.2. Query builders versus ORMs versus raw drivers.md>)'s string-SQL wall, Prisma edition); and the untyped-result habit (`any` rows from raw queries — refactors breaking at runtime — column renames failing per deploy, discovered by customers). Typed composition converts both (filters as objects — compiler-checked; results as generated types — refactors guided; pagination as typed combinators — shapes checked). Composition typed, results inferred, pagination structured — queries as code, complete.

**Modern guidance** — the find contract per query (review-enforced): *filters* (where-objects composed — conditionals via spread (falsy branches omitted — no `WHERE 1=1` scaffolding); operators typed (`contains/mode/gt/in` — per-field operators checked — invalid operators fail compilation); *ordering* (orderBy per sortable field — multi-field arrays ordered deterministically — nondeterministic order (no orderBy + take — page contents shifting per query — pagination lying) rejected in review); *pagination* (take/skip for shallow pages (OFFSET economics — page N scans N rows — acceptable shallow, budgeted); cursor for deep pages (`cursor: { id }` + take — keyset constant-cost — [Database Design... Databases 07 §2.2 mechanics applied through client — deep pages never OFFSET). Missing orderBy with take → request changes; deep OFFSET → cursor migration ticketed.

```typescript
// GOOD: finds composed precisely — filters typed, ordering deterministic, pages bounded (verified live).
const page = await db.user.findMany({
  where: { role: "USER" },            // typed filter (typos fail compilation — verified pattern)
  orderBy: { createdAt: "desc" },     // deterministic (pagination honest — no shifting pages)
  take: 10,                           // bounded (page size explicit — transfer capped)
  select: { id: true, email: true },  // projected (unneeded columns unfetched — transfer trimmed)
});
// Live: findMany page: 1 (verified against dbprobe — where/orderBy/take/select all executing).
```

```typescript
// BAD: finds composed hopefully — strings, any-types, unbounded pages.
// const users = await db.$queryRawUnsafe(`SELECT * FROM "User" WHERE role = '${role}'`);
// (interpolation — injection per branch (unsafe-query API chosen over composed finds — escape hatch
// as default — DANGER normalized); SELECT * (shape unknown — columns added upstream breaking
// downstream silently); no orderBy/take (unbounded, unordered — full-table transfer per render,
// page contents shifting — pagination lying structurally). Composed finds declined; strings hoped.)
```

**Common confusion** — *"find APIs can't express complex queries (need raw)."* Finds express CRUD + relations + filters + ordering + pagination completely (the overwhelming majority — composed, typed, logged); raw escapes serve the genuinely unmappable (recursive CTEs, window analytics, COPY — [3.1](<../3. Performance discipline/3.1. N+1 strategies and raw escapes.md>) owns escapes fully). "Can't express" usually means "haven't learned the combinators" (nested where/or, relation filters (`posts: { some: ... }`), aggregations (`_count`) — expressive surface, documented, typed). Learn combinators first (composed queries cover ~95%); escape deliberately for the remainder (unmappable, stated, logged like all SQL). Combinators default; escapes deliberate.

**Performance note** — find economics: composed queries generate parameterized SQL (same planner, same plans as hand-written — logged statements diffed match); select-projection trims transfer (fetched columns paid per row — projection discipline halving wide-row transfer routinely); take-bounding caps pages (transfer O(page), never O(table) — unbounded finds are full-table transfers wearing pagination UI). Pagination depth priced (OFFSET shallow OK — deep cursor per Databases 07 §2.2 — page-N cost examined, never hoped). Compose precisely; project always; bound pages; cursor deep.

**Mentor note** — teach "where/orderBy/take/select per find" (juniors stating all four per query design bounded reads on first hearing; unstated finds interrogated ("ordered? bounded? projected?" — three questions, seconds each, unexamined finds returned). Demonstrate unbounded-find transfer once (SELECT * without take on 1M rows — transfer measured in GBs — faces paling, conversion permanent). Four clauses stated; transfer bounded; unbounded finds extinct. State clauses; bound pages; project always.

## 2. Include and select shape reads (relations loaded explicitly — N+1 prevented by strategy)

**Definition** — the load rule performed Prisma-specifically (general rule in [Domain 01 §4.1](<../../../01 Data Access Foundations and Mental Model/sections/4. Mentor checklist/4.1. Data-access checklist mentors insist on.md>)): `include: { posts: true }` batches relations per query path (verified live below — user + posts in one round trip); `select` trims columns + nests relation projections (`select: { id: true, posts: { select: { title: true } } }` — transfer minimized, shape precise); lazy absent structurally (unincluded relations inaccessible as properties — compile-time absence, not runtime N+1 — Prisma's design gift: unstrategized access *fails builds* instead of slowing production). Schema declares relations ([1.2](<../1. Schema authoring/1.2. Relations in schema.md>)); queries strategize loads — declaration without strategy impossible (absent properties), strategy without declaration impossible (unknown relations) — both enforced, neither hoped.

**What problem it solves** — the unstrategized traversal trio (lazy-by-default N+1 (other mappers' magic — per-access statements — Prisma structurally immune (no lazy loading exists — immunity by design, not discipline); hand loops beside the client (per-parent findUnique calls — N+1 wearing client syntax — batching declined where include would serve — loops visible, counts unasserted); over-including (everything included "just in case" — transfer bloat + multi-list fan-out ([Database Design §4.3](<../../../../DatabaseDesign/04 Relationships at Scale/sections/3. Skew and hot relationships/3.1. Hot keys and skew.md>)) — cartesian products on dual list-includes (statements few, rows multiplied — sums fictionalized downstream). Include-per-query with select-trimming converts all three (absent→compile error; looped→batched; bloated→projected).

**Modern guidance** — the strategy lines per relation read (review-enforced): *include stated* (relations listed explicitly — `include: { posts: true }` (verified live: 1 post with user, one round trip); *select trimmed* (columns + nested projections — `select` over `include` where transfer matters — wide rows projected, never SELECT-*-included); *multi-list caution* (two list-includes multiply — fan-out transfer — split queries per Database Design 04 rule (cause removed) or accept documented (transfer priced, sums never computed over products); *counts asserted* (statement counts per list test — 01/4.1 detector enforced from adoption — N+1 fails builds (hand loops) and fan-out fails review (multi-list includes documented). Missing strategy → request changes; present strategy → verify with counts (asserted, not hoped).

```typescript
// GOOD: strategy per relation — include stated, transfer trimmed, counts asserted (verified live).
const user = await db.user.findUnique({
  where: { email: "ann@example.com" },
  include: { posts: true },   // batched (verified live: posts.length 1 — one round trip)
});
const slim = await db.user.findMany({ select: { id: true, email: true } });
// (projection — posts unfetched (unneeded relations unloaded deliberately — transfer minimal).
// Test: statement counts asserted per list (≤N bounds — loops fail builds, fan-out fails review).
```

```typescript
// BAD: unstrategized traversal — loops beside the client, includes unexamined.
// const users = await db.user.findMany();  // no include (relations unloaded — deliberately? unasked?)
// for (const u of users) {  // loop forming (per-parent posts query next — N+1 in client clothing —
//   u.posts = await db.post.findMany({ where: { authorId: u.id } });  // batching declined (include
//   // capable — unused); counts unasserted (green on 10 rows — 10k statements in production).
//   // Or the mirror: include: { posts: true, orders: true, events: true } (lists multiplying —
//   // fan-out transfer — 50× rows shipped, downstream sums fictionalized). Unstrategized both ways.
// }
```

**Common confusion** — *"include always prevents N+1 (batching magic)."* Include batches *declared* paths (one query per include path — structural); hand loops bypass batching (per-parent calls — N+1 fully manual — framework unable to help undeclared traversals); multi-list includes multiply transfer (batched statements, combinatorial rows — N+1 absent, fan-out present — different failure, same unexamined strategy). "Always prevents" credits batching with loop prevention (loops unbatched by definition — authorial, not framework) and fan-out immunity (transfer unexamined — multiplicative). Batching covers declared paths; discipline covers loops and fan-out — both required, neither automatic (same verdict as [1.2's promise 3](<../1. Schema authoring/1.2. Relations in schema.md>) — restated at client level, permanently).

**Performance note** — include economics: declared includes cost one query per path (batched — constant statements regardless of N — N+1 immunity structural); hand loops cost N statements (linear — latency scaling with data — batching declined); multi-list includes cost combinatorial transfer (statements few, rows multiplied — transfer dominating — split per Database Design 04). Statements bounded via includes; transfer bounded via select/split; counts asserted via tests — three bounds, complete read performance (same triple as [1.2](<../1. Schema authoring/1.2. Relations in schema.md>) — restated at client level, enforced identically).

**Mentor note** — teach "strategy per include" (juniors stating include/select per relation read design bounded reads on first hearing; unstated includes interrogated ("which relations, and why these?" — strategy demanded per query). Include audits per hot path (production includes reviewed quarterly — unneeded relations trimmed (transfer shrinking), missing includes added (loops batched) — strategies living documents, not birth decisions). State strategies; audit quarterly; assert always — read performance in three habits, reviewed per PR.

## 3. Nested writes transact graphs (create/update with nested connects — one call, atomic)

**Definition** — nested writes: relation mutations inline in parent operations (`user.create({ data: { email, posts: { create: [{ title }] } } })` — verified live: 2 posts created with user, one call; `connect: { id }` linking existing rows (verified live); `connectOrCreate`, `upsert` with nested paths — full graph mutations expressible per call). Atomicity: nested writes execute transactionally (all-or-neither persisted — partial graphs impossible structurally — the mapper's unit-of-work for graphs); interactive transactions (`$transaction(async (tx) => ...)` — verified live: user + post created atomically, email returned) compose multi-operation atomicity explicitly (callback API — commit/rollback by return/throw — timeouts configured (`maxWait/timeout` — contention windows bounded, never indefinite).

**What problem it solves** — the multi-statement graph write (parent created, children looped, links connected — N+1 statements with partial-failure windows (parent persisted, children half-written — inconsistent graphs committed piecemeal; rollback hand-rolled (compensating deletes — error-prone, untested paths); concurrent interleavings corrupting multi-step writes (races between statements — isolation absent across calls). Nested writes collapse graphs to atomic units (one call — all-or-neither — partial graphs structurally impossible); interactive transactions collapse multi-operation units (callback-scoped atomicity — commit by return, rollback by throw — isolation across the callback). Graphs persisted whole or not at all — partial persistence eliminated structurally, not hoped away.

**Modern guidance** — the write lines per graph mutation (review-enforced): *nest where atomic* (parent+children in one create/update (verified live — user + 2 posts, one call) — partial graphs impossible); *connect existing* (`connect: { id }` / `connectOrCreate` for maybe-existing (verified live pattern — idempotent-ish linking — duplicates handled per unique constraints, races closed by DB enforcement); *transact across operations* (`$transaction` callback for multi-call units (verified live — user + post atomic, email returned) — timeouts configured (maxWait/timeout bounded — contention windows finite); *upsert deliberately* (create-or-update paths explicit — race-safe via unique constraints + transactions — check-then-act across calls rejected (raced — upsert or unique-violation-handling instead). Missing atomicity → request changes (multi-statement graph writes without transactions fail structurally — partial graphs scheduled).

```typescript
// GOOD: graphs written whole — nested creates, transactions, upserts (verified live).
const u = await db.user.create({ data: { email: "ann@example.com",
  posts: { create: [{ title: "a" }, { title: "b" }] } }, include: { posts: true } });
// (verified live: nested create posts: 2 — one call, atomic — partial graphs impossible.)
const email = await db.$transaction(async (t) => {
  const u2 = await t.user.create({ data: { email: "bo@example.com" } });
  await t.post.create({ data: { title: "t", author: { connect: { id: u2.id } } } });
  return u2.email;   // commit by return (verified live: tx email — atomic unit complete)
});  // Rollback by throw (exceptions aborting — all-or-neither); timeouts configured (bounded waits).
```

```typescript
// BAD: piecemeal graph writes — statements sequential, atomicity hoped.
// const u = await db.user.create({ data: { email } });  // committed alone (crash window opens)
// for (const t of titles) {  // looped children (N statements — partial graphs on failure:
//   await db.post.create({ data: { title: t, authorId: u.id } });  // crash at i=3: parent + 3/10
// }  // children committed (inconsistent graph persisted); rollback hand-rolled (compensating deletes —
// // untested paths, raced interleavings); concurrent writers interleaving (isolation absent across calls).
// // No transaction (multi-call unit unscoped — atomicity hoped); no nesting (graph unexpressed as unit).
// // Piecemeal persisted; partial possible; hope scheduled. Nest or transact — never sequence hopefully.
```

**Common confusion** — *"nested writes replace transactions."* Nested writes *are* transactional (single-operation atomicity — mapper-scoped unit); interactive transactions *compose* atomicity across operations (multi-call units — callback-scoped — timeouts bounded). Different scopes (one call vs many — nested for parent+children, transactions for cross-entity multi-step units); same guarantee (all-or-neither — partial states impossible structurally at both scopes). "Replace" confuses scopes (nested covering single-call graphs completely; transactions covering multi-call units necessarily). Nest single-call graphs; transact multi-call units; never sequence hopefully — scope-matched atomicity, always.

**Performance note** — nested-write economics: single round trip per graph (vs N+1 statements piecemeal — latency divided by batching, locks held briefly once — contention minimized structurally); transaction timeouts bounding contention (maxWait/timeout configured — finite waits — unbounded transactions blocking vacuum/locks rejected); upsert paths indexed (unique constraints serving connectOrCreate — races closed by enforcement, not hope). Atomic units perform better *and* safer (fewer round trips, shorter lock windows, no compensation code — atomicity as performance feature, not just correctness). Nest graphs; transact units; bound waits.

**Mentor note** — teach "graphs whole or not at all" (juniors nesting writes discover atomic graphs tangibly — partial states impossible to construct (try failing midway — rollback complete — trust earned by attempting failure, not by documentation claims). Failure drills (throw mid-transaction — verify nothing persisted — atomicity demonstrated, not described); timeout configuration (bounded waits — contention finite — unbounded transactions rejected in review). Attempt failure; verify rollback; bound waits — atomicity learned by breaking safely, trusted permanently.
