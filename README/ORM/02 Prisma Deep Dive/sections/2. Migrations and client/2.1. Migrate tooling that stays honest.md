# 2.1. Migrate tooling that stays honest

## 1. Dev flow generates reviewable SQL (migrate dev creates versioned SQL — read fully)

**Definition** — the development flow: `prisma migrate dev --name <change>` diffs schema against database, renders SQL migration files (`migrations/YYYYMMDDHHMMSS_name/migration.sql` — versioned, committed, reviewed), and applies them to the dev database. The SQL is the artifact (human-readable DDL — `CREATE TABLE "Widget" (... BIGSERIAL ...)` + `CREATE UNIQUE INDEX` — verified live via `migrate diff` below); the history is the ledger (`_prisma_migrations` tracking applied migrations — deploy replays history, never wishes). Tooling authors in seconds; humans govern by reading every generated line ([1.1](<../1. Schema authoring/1.1. Models fields and attributes.md>)'s review discipline, performed here).

**What problem it solves** — the unreviewed-diff failure (NOT NULL without default generated for live tables — blocking rewrites mid-deploy; renames inferred as drop+create — history destroyed with applause; missing FK indexes — parent writes scanning; all wearing "Prisma made it" approval). Generated SQL reviewed fully converts tooling velocity (seconds per diff) to governed velocity (minutes of review per diff — phases classified, witnesses planned, renames declared). Unreviewed diffs ship incidents at machine speed (flag-days automated, drops unwitnessed, renames destructive); reviewed diffs ship phases (expand/migrate/contract per [Database Design §5.1](<../../../../DatabaseDesign/05 Evolution Growth and Partitioning/sections/1. Schema evolution/1.1. Expand and contract migrations.md>) — tooling executing, humans sequencing).

**Modern guidance** — the dev-flow contract (verified live behaviors on Prisma 7.10.0 this session): `migrate dev` on dedicated dev databases (drifted/shared DBs refused without reset — verified live: reset demanded on dbprobe's shared public schema — protection, not obstruction — dev flow needs databases it owns, never shared ones); `migrate diff --from-empty --to-schema --config` renders reviewable SQL without touching anything (verified live output below — BIGSERIAL ids, UNIQUE indexes, all visible pre-commit); `migrate status` reports read-only (verified live: "No migration found" — state observed, never mutated — status checked in CI (pending migrations failing builds that should include them, unexpected pendings failing deploys)); renames declared (drop+create pairs in diffs rejected on sight — data-preserving renames via explicit mapping — history never destroyed by inference).

```sql
-- GOOD: generated SQL reviewed fully (verified live: migrate diff renders without touching the DB).
-- CreateSchema: CREATE SCHEMA IF NOT EXISTS "public";
-- CreateTable: CREATE TABLE "Widget" ("id" BIGSERIAL NOT NULL, "name" TEXT NOT NULL,
--   CONSTRAINT "Widget_pkey" PRIMARY KEY ("id"));   -- BigInt autoincrement → BIGSERIAL (visible)
-- CreateIndex: CREATE UNIQUE INDEX "Widget_name_key" ON "Widget"("name");  -- UNIQUE enforced
-- Reviewer notes: phase EXPAND (additive table — compatible ✓); FKs: none yet (N/A stated);
-- deploy via migrate deploy (pending-only ✓). Verdict: approve migration.
```

```sql
-- BAD: the trusted diff — generated, unreviewed, flag-dayed (real failure shapes, Prisma edition).
-- -- AlterTable: ADD COLUMN "email" TEXT NOT NULL (no default — 50M-row rewrite + old-writer
-- failures — breaking shipped as safe, generator-authored, human-waved).
-- -- DropTable "legacy_temp" + CreateTable "legacyTemp" (rename inferred as drop+create —
-- history destroyed with applause — undeclared rename, unwitnessed drop).
-- -- AlterTable: ADD COLUMN "authorId" BIGINT (no index — parent deletes scanning — FK discipline
-- from Database Design 04 unapplied through tooling). Generated quickly; approved blindly;
-- incidents automated. Tooling trusted; discipline absent.
```

**Common confusion** — *"migrate dev handles safety (it warns about destructive changes)."* Warnings flag *destructiveness* (drops, data-loss risks — valuable, real — verified family: reset demanded, P3005 baselining required — tooling refusing dangerous defaults, genuinely); safety requires *compatibility judgment* (phases, witnesses, stragglers — human, contextual — warnings unheeded ship incidents with acknowledged risks). The verified refusals (no reset on shared DBs, no deploy without baseline) prove tooling guards *mechanics*; reviewers guard *compatibility* (old writers? new readers? stragglers? — unasked by any CLI flag). Warnings inform; reviewers decide — judgment layered atop tooling, never replaced.

**Performance note** — dev-flow economics: diff rendering costs seconds (reviewable SQL without database contact — cheapest review artifact available); dev apply costs per-migration seconds (dedicated dev DBs — disposable, resettable — velocity unblocked); unreviewed flag-days cost blocking rewrites in deploy windows (50M-row ALTERs — locks, lag, timeouts — "quick migration" paging). Review minutes convert to outage-quarters avoided at the usual rate — highest-ROI minutes in Prisma operations, permanently true.

**Mentor note** — teach "read the generated SQL" (juniors reading migrate-dev/diff output line-by-line discover generators' assumptions (drop+create renames, flag-day nullability, missing FK indexes) permanently — generated code reviewed like hand code, always). Demonstrate refusals live once (reset demanded on shared DB, P3005 without baseline — tooling protecting data visibly — trust earned by watching guards fire, not by documentation claims). Read diffs; watch guards; classify phases — migration fluency in three habits, reviewed per schema PR.

## 2. Deploy applies, never improvises (migrate deploy runs pending only)

**Definition** — the deploy contract: `prisma migrate deploy` applies pending migrations from the committed history, in order, exactly once each (tracked in `_prisma_migrations` — applied state recorded per migration (checksum + timing — audit trail of schema evolution); non-empty databases without baselines refused (verified live: P3005 + baselining pointer on dbprobe's shared schema — protection, not obstruction); nothing generated at deploy time (history closed — deploy executes, never authors — improvisation structurally impossible). Production schemas change exclusively through reviewed, committed, ordered history — wishes never executed, regardless of urgency.

**What problem it solves** — the deploy-time improvisation trio: *`migrate dev` in production* (dev commands generating + applying unreviewed (shadow databases created, resets one flag away — development tooling with production credentials — incidents wearing convenience); *manual console DDL* (hotfixes applied directly — history diverging (database ahead of migrations — subsequent deploys conflicting or duplicating — drift institutionalized per incident); *unbaselined brownfields* (deploy against legacy schemas — P3005 refused (verified — the guard working) — teams bypassing via direct DDL instead of `migrate resolve --baseline` (proper adoption path — drift instead of history). Deploy-only discipline (deploy executes history; dev never runs past development; brownfields baselined honestly) converts all three to procedure (history single-sourced, production reproducible from migrations alone).

**Modern guidance** — the deploy lines (CI/CD-enforced): `migrate deploy` as the sole production migration runner (pipeline step — credentials scoped to migrate-only where feasible — developers without console DDL on production — access reflecting discipline); `migrate status` gating deploys (pending migrations expected (matching the release) vs unexpected (drift or forgotten commits — both failing the gate — status checked pre-deploy, always — verified live read-only behavior); baselines via `migrate resolve` (brownfield adoption: baseline existing schema as migration zero — history starting honestly from reality — then normal flow forever after — verified command family in CLI help); failed migrations via `resolve` (marked rolled-back or applied after manual remediation — repair recorded in history, never around it — [2.1... resolve mechanics touch Prisma docs per edge (linked per need, not repeated)). History closed at deploy (nothing authored — improvisation impossible structurally).

```sql
-- GOOD: deploy as history replay — pending only, tracked, baselined where brownfield.
-- CI: prisma migrate status (expected pendings match release ✓ — drift fails gate).
-- Deploy: prisma migrate deploy (pending applied in order, checksummed, recorded in
-- _prisma_migrations — production reproducible from history alone ✓).
-- Brownfield: migrate resolve --applied <baseline> (existing schema adopted as history zero —
-- honest start, normal flow after ✓). Failed: resolve after manual fix (repair in history ✓).
-- Production executes reviewed history. Nothing else ever runs there.
```

```sql
-- BAD: deploy-time improvisation — history bypassed per urgency (urgency recurring, bypasses permanent).
-- migrate dev against production ("just this once" — unreviewed diff applied + dev shadow assumptions
-- (reset one flag away — production deletable by typo); console hotfix DDL (history diverging —
-- next deploy conflicting (already-applied statements re-running — failures) or duplicating
-- (objects recreated — downtime); P3005 bypassed via direct DDL (baselining declined — drift
-- institutionalized — history fiction henceforth). Improvisation under urgency feels fast
-- (minutes saved); history repair costs quarters (divergence archaeology — which statements ran
-- where? — unanswerable post-hoc). Urgency improvises; discipline replays.
```

**Common confusion** — *"deploy is just dev with a different flag."* Dev *authors* (diffs generated, shadows created, resets available — creative tooling for development databases); deploy *executes* (pending history applied, checksummed, recorded — reproductive tooling for production). Different verbs (author vs execute), different databases (owned-dev vs shared-prod), different failure modes (dev mistakes resettable in seconds; deploy mistakes need resolve procedures + potential rollbacks). "Just a flag" collapses authoring into execution (unreviewed diffs reaching production — flag-day automation — the exact failure deploy-only discipline prevents). Author in dev; execute in prod; never cross the streams.

**Performance note** — deploy economics: pending-only application costs seconds per deploy (bounded, predictable — migrations small by review discipline — deploy windows unaffected); baselining costs one honest procedure per brownfield (resolve --applied — minutes, once); improvised history repair costs archaeology quarters (divergence untangling — statement-by-statement forensics across environments — unanswerable questions billed hourly). History-closed deploys perform boringly (same steps, same order, every release — boring deploys are successful deploys); improvised deploys perform dramatically (each unique — drama billed in pages). Boring by procedure; dramatic never.

**Mentor note** — teach "production executes history" (juniors internalizing deploy-only discipline deploy calmly forever — history reviewed, status gated, deploy replaying — calm as procedure, not temperament). Demonstrate P3005 live once (unbaselined deploy refused with baselining pointer — guard firing visibly — trust earned by watching protection work, same as reset-refusal). Gate status in CI (pending expectations encoded — drift failing builds — automation enforcing discipline tirelessly). History closed; deploys boring; mentors calm — operations maturity in three habits.

## 3. Baselines and drift handled explicitly (resolve for baselines, repairs, hotfixes)

**Definition** — the honesty procedures: **baselining** (`migrate resolve --applied <migration>` — marking existing schema as history-adopted without executing (brownfield databases joining managed history — reality acknowledged as baseline, normal flow after); **failed-migration repair** (`resolve --rolled-back` after manual remediation — history corrected through recorded resolution, never around it (direct table edits to `_prisma_migrations` forbidden — history's integrity is the system's integrity)); **drift detection** (`migrate status`/`diff` surfacing database-vs-history divergence — drift investigated (which statements ran outside history? — forensics), reconciled (resolve or re-align), never ignored (drift accepted silently compounds — subsequent deploys building on fiction). Explicitness converts brownfield/failed/drifted states from shameful secrets (hidden, worked around, compounding) to managed history (recorded, resolved, resumed).

**What problem it solves** — the history-fiction trio: *unbaselined brownfields* (legacy databases "managed" by wishful deploy attempts (P3005 refusing, correctly — teams bypassing via console DDL — history fiction from day one (migrations claiming states never applied — reproducibility void)); *unresolved failures* (half-applied migrations retried blindly (already-applied statements re-running — duplicate-object failures; or silently skipped (history ahead of reality — subsequent migrations building on absent objects — cascading failures); *uninvestigated drift* (hotfixes applied directly "temporarily" (temporary permanent — history diverging per incident — deploys eventually failing mysteriously on fiction-built foundations). Explicit resolve procedures (baseline/repair/reconcile — all recorded in history itself) keep one true ledger (reality == history, always — verifiable via status, enforceable via gates).

**Modern guidance** — the honesty lines per non-greenfield state: *brownfield* (baseline once: `resolve --applied` for the migration matching current reality (reality inventoried first — diff current schema vs candidate baseline — match verified, not assumed — then normal flow forever (first honest commit — history starting true)); *failed* (remediate manually (complete or roll back the half-applied statements by hand — judgment, contextual), then `resolve` accordingly (history recording the truth — rolled-back (retry cleanly) or applied (continue forward) — never neither (limbo states corrupting subsequent runs)); *drifted* (status/diff regularly (CI-scheduled drift detection — divergence alerting, not quarterly archaeology); reconcile immediately (drift fresh = small = fixable (hotfix reverse-engineered into a migration, or database restored to history — direction decided per case, recorded always). History fictional nowhere, limbo tolerated never, drift aged never.

```sql
-- GOOD: honesty procedures — baselined, resolved, reconciled (all recorded in history).
-- Brownfield: diff reality vs candidate baseline (match verified) → resolve --applied
-- (history starts true — normal flow after — first commit honest).
-- Failed: manual remediation (complete/roll back half-applied by hand — judgment) →
-- resolve rolled-back|applied (history recording truth — subsequent runs clean).
-- Drifted: status/diff scheduled (divergence alerting) → reconcile fresh (reverse-engineer
-- hotfix into migration OR restore DB to history — direction recorded). Ledger true throughout.
```

```sql
-- BAD: history fiction — bypassed, limboed, drifted (secrets compounding).
-- Brownfield: console DDL "catching up" (history claiming unapplied states — reproducibility void;
-- new environments built from fiction (staging ≠ production structurally — bugs environmental,
-- undiagnosable). Failed: retried blindly (duplicate-object errors — then skipped manually
-- (history ahead of reality — cascading failures on absent objects). Drifted: hotfixes direct,
-- unrecorded ("temporary" — permanent — history fiction compounding per incident — deploys failing
-- mysteriously on foundations nobody mapped). Fiction, limbo, drift — unmanaged states compounding.
```

**Common confusion** — *"resolve rewrites history (dishonest by definition)."* Resolve *records* history's corrections (baseline/repair/reconcile entries in `_prisma_migrations` — ledger showing what happened, including fixes — audit-visible, reviewable); rewriting would *alter* past entries (changing applied migrations — integrity violated — forbidden structurally (checksums guarding — tampering detectable). Corrections appended (new ledger truth about old states — honest); past altered never (immutability preserved — trustworthy). "Rewriting history" smears appending (transparent correction) with altering (silent falsification) — opposites morally and mechanically. Append corrections; never alter pasts.

**Performance note** — honesty economics: baselining costs one inventory + resolve (hours once per brownfield — history true forever after); blind retries cost cascading failures (duplicate objects, absent foundations — incident per retry — quarters of archaeology untangling fiction-built foundations); drift detection costs scheduled status runs (seconds per schedule — divergence caught fresh (small, fixable)); drift archaeology costs quarters (stale divergence — untangling months of direct DDL — forensics hourly-billed). Honest procedures price in hours once; fiction prices in quarters recurring. Baseline once; resolve promptly; detect scheduledly.

**Mentor note** — teach "history never lies (resolve until true)" (juniors internalizing ledger integrity treat `_prisma_migrations` as sacrosanct (read often, edited never-directly, corrected only via resolve — integrity culture in one table). Demonstrate P3005 + resolve flow live once (refusal → inventory → baseline → green status — honesty performed end-to-end — trust earned by watching guards and corrections work together). Ledger integrity preached never (sermons ignored); performed once (remembered permanently). Perform honesty; ledger integrity follows.
