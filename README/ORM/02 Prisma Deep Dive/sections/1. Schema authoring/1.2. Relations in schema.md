# 1.2. Relations in schema

## 1. Relations declared both sides (back-references, referential actions stated)

**Definition** — Prisma relations are declared on both models (User.posts[] + Post.author/authorId — forward list plus back-reference with scalar FK + `@relation` naming fields/references). Referential actions stated per relation (`onDelete: Cascade/Restrict/SetNull` — the delete policy from [Database Design §4.1](<../../../DatabaseDesign/04 Relationships at Scale/sections/1. Foreign keys at volume/1.1. Foreign keys that survive traffic.md>), declared in schema, migrated to FKs). Both-sides declaration makes relations navigable both directions (user→posts, post→author — queries traversing either way); stated actions make deletes governed (cascade/restrict per relationship — business rules wearing schema syntax, never database defaults deciding at runtime).

**What problem it solves** — the half-declared relation (forward list without back-reference — reverse traversal unservable (post→author unqueryable via client — raw SQL escaping for routine navigation); scalar FK without `@relation` (unlinked columns — joins hand-written, integrity unenforced — mapper ceremony paid, graph convenience declined); defaulted delete actions (NO ACTION answering deletes at runtime — surprises in production, per Database Design 04). Both-sides + stated-actions converts relations from column pairs to navigable, governed associations (traverse either way via client; delete per policy, never per default).

**Modern guidance** — the relation checklist per association (review-enforced): *both sides declared* (list + back-reference + scalar FK + `@relation(fields/references)` — four parts, all present — verified live below); *actions stated* (onDelete per relation — Cascade for contained children (lines/posts), Restrict for history (orders), SetNull for optional links — [Database Design §4.1](<../../../DatabaseDesign/04 Relationships at Scale/sections/1. Foreign keys at volume/1.1. Foreign keys that survive traffic.md>)'s both-lenses rule applied through tooling); *1-1 via unique FK* (Profile.studentId `@unique` — one-to-one enforced structurally (verified live — second profile for one student rejected); *self-relations named* (manager/reports with explicit relation names — ambiguity resolved in schema, never guessed). Missing part → request changes; defaulted action → classify explicitly (defaults are decisions made by absence — absence unreviewed).

```prisma
// GOOD: relations declared both sides, actions stated (verified live: validate + generate + CRUD).
model Student {
  id      BigInt       @id @default(autoincrement())
  name    String
  profile Profile?     // back-reference (1-1 — navigable both ways)
  courses Course[]     // implicit m-n list (promise 2 owns the trade)
  enrolls Enrollment[] // explicit m-n list (promise 2 — attributes live here)
}

model Profile {
  id        BigInt  @id @default(autoincrement())
  bio       String
  student   Student @relation(fields: [studentId], references: [id], onDelete: Cascade)
  studentId BigInt  @unique   // 1-1 enforced (UNIQUE — second profile rejected structurally)
}
```

```prisma
//   title    String
//   authorId BigInt   // scalar without @relation (unlinked column — joins hand-written,
//   // integrity unenforced (orphans accumulating — FK absent); client navigation absent
//   // (post.author unqueryable — mapper ceremony paid, graph convenience declined).
//   // Delete action: default NO ACTION (runtime surprise — deleting authors fails live).
// }
// Columns paired; relations undeclared; actions defaulted. Pairing isn't associating.
```

**Common confusion** — *"back-references are optional (I only query one way)."* Reverse traversals arrive with features (author pages listing posts — unanticipated at authoring, required within quarters; admin screens traversing backwards — every relation read both ways eventually ([Database Design §1.4](<../../../DatabaseDesign/01 Modeling Foundations and Mental Model/sections/4. Mentor checklist/4.1. Modeling checklist mentors insist on.md>)'s both-ways rule, ORM edition). Undeclared back-references cost migrations later (schema edits under live traffic — expand/contract for missing navigability — quarters of ceremony for lines omitted at authoring). Declare both sides at birth (lines, free); add reverse traversal under migration pressure (phases, witnesses, downtime negotiations). Birth is cheap; retrofit dear.

**Performance note** — relation-declaration economics: back-references cost lines (schema text — zero runtime); stated actions cost thought (policy per relation — minutes, once); missing declarations cost migrations (retrofit under traffic — flag-day schema edits or phased ceremonies — quarters of process per omitted line). Reverse indexes follow relations (FK columns indexed per Database Design 04 — declared relations auditable for indexes; undeclared scalars invisible to index review — scans scheduled silently). Declare completely; index accordingly; delete governedly.

**Mentor note** — teach "both sides + action" as the relation mantra (juniors reciting per association internalize completeness before speed — mantra first, fluency follows). Review relations by checklist (four parts present? action stated? 1-1 unique? self named? — structural review in seconds, incompleteness visible instantly). Mantra memorized; checklist enforced; relations complete — three verbs, zero half-declared associations.

## 2. Many-to-many explicit beats implicit (implicit for simple links, explicit when links grow)

**Definition** — two m-n shapes: **implicit** (`Student.courses[]` + `Course.students[]`, no relation model — Prisma manages the `_CourseToStudent` join table invisibly — verified live below); **explicit** (`Enrollment` model with `@@id([studentId, courseId])` + attribute fields (grade, enrolledAt) — full model, queried directly). Implicit serves pure links (membership without metadata — zero ceremony); explicit serves attributed links (grade/enrolledAt describing the membership — [Database Design §4.2](<../../../DatabaseDesign/04 Relationships at Scale/sections/2. Many-to-many and polymorphism/2.1. Junction tables at scale.md>)'s growth law: junctions grow attributes, always). The trade is reversibility-asymmetric (implicit→explicit migrates data between shapes — planned work; explicit→implicit never needed — explicit serves pure links equally).

**What problem it solves** — the implicit trap (m-n declared implicit for "simplicity" — attributes arriving within quarters (enrolled_at, grade, status — homeless (no model to hold them — JSON blobs on students? parallel tables shadowing? — [Database Design §4.2](<../../../DatabaseDesign/04 Relationships at Scale/sections/2. Many-to-many and polymorphism/2.1. Junction tables at scale.md>)'s attribute-homeless crisis, ORM edition); migration implicit→explicit under live traffic (data moved between invisible and visible join tables — expand/contract for relationship shape — quarters of ceremony for lines saved at authoring). Explicit-by-default avoids the trap (attributes landing on existing models — zero migration); implicit justified per case (pure links with credible permanence — "no attributes ever" — stated with trigger ("attributes arriving → explicit migration, priced now")).

**Modern guidance** — default explicit where links *might* grow attributes (enrollments, memberships, assignments — business relationships accumulating metadata within years — virtually all of them); permit implicit where links are credibly pure (tag assignments? even tags gain tagged_at — audit honestly: pure links are rarer than claimed — default explicit unless purity argued with trigger). Explicit model checklist (verified live): `@@id([a, b])` composite PK (link invariant); attribute fields (grade, enrolledAt — membership-scoped); both relations with Cascade actions (orphan links die with endpoints); reverse indexes considered (both traversal directions — Database Design 04 rule through tooling — `@@index` where missing). Migration implicit→explicit when purity breaks (data moved, readers switched, old shape dropped — phased, witnessed — priced at purity-breaking time, not before).

```prisma
// GOOD: explicit m-n with attributes (verified live: create with grade, include with course).
model Enrollment {
  student   Student @relation(fields: [studentId], references: [id], onDelete: Cascade)
  studentId BigInt
  course    Course  @relation(fields: [courseId], references: [id], onDelete: Cascade)
  courseId  BigInt
  grade     String?                    // attribute on the link (membership-scoped — 2NF-clean)
  enrolledAt DateTime @default(now())  // audit column from birth (always wanted)
  @@id([studentId, courseId])           // link invariant (composite PK — verified live)
}
// Live: enroll.create({studentId, courseId, grade: "A"}) + include enrolls.course (grade read).
// Implicit m-n beside it (Student.courses[] — verified live: connect + include working).
```

```prisma
// BAD: implicit for growing links — purity assumed, attributes homeless within quarters.
// model Student { id ...; courses Course[] }   // implicit (pure link — "no attributes ever")
// model Course { id ...; students Student[] }  // ...then grade arrives (homeless: no model;
// // options: JSON on students (unqueryable); parallel grades table (dual truth); migration to
// // explicit under traffic (data moved invisible→visible, readers switched, drop witnessed).
// // "Simplicity" saved lines at authoring; migration bills quarters at growth. Purity assumed;
// // attributes arrived; homelessness scheduled. Explicit-by-default avoids the trap entirely.
```

**Common confusion** — *"explicit m-n is verbose (implicit is cleaner)."* Verbosity with attributes (explicit models holding grade/enrolledAt — lines serving data); brevity without home (implicit links blocking attributes — cleanliness preventing growth). "Clean" describes schema text (fewer models — aesthetic); "complete" describes growth accommodation (attributes landable — engineering). Aesthetic cleanliness expires at first attribute (migration quarters); engineering completeness persists (attributes landing free). Prefer complete; admire clean briefly; migrate never (explicit from birth — no migration needed, ever).

**Performance note** — m-n economics: implicit join tables (Prisma-managed `_AtoB` — indexed by generation — traversal both ways served opaquely); explicit models (composite PK + reverse indexes per Database Design 04 — both directions point-fast, attributes covering). Query shapes identical at runtime (joins through link tables either way — planner indifferent to declaration style); migration cost differs totally (implicit→explicit under traffic vs explicit from birth — quarters vs zero). Declaration style is migration economics wearing aesthetics — choose by growth forecast (attributes likely → explicit; purity credible → implicit with trigger), never by line count.

**Mentor note** — teach "will this link grow attributes?" per m-n (juniors answering from business knowledge (enrollments grade, memberships role, assignments expire — attributes foreseeable within years) place explicitly on first hearing; "pure link" claims interrogated ("trigger if attributes arrive?" — priced migration agreed upfront — purity with exit plan, never bare assertion). Attribute-foresight generalizes (junctions in SQL, embeds in documents — every link audited for future entity-hood — [Database Design §4.2](<../../../DatabaseDesign/04 Relationships at Scale/sections/2. Many-to-many and polymorphism/2.1. Junction tables at scale.md>)'s larval-entity lesson, ORM edition). Foresee attributes; place explicitly; migrate never.

## 3. Relation load strategy decided per query (include/select at read time — schema declares, queries strategize)

**Definition** — the load rule carried over from [Domain 01 §4.1](<../../01 Data Access Foundations and Mental Model/sections/4. Mentor checklist/4.1. Data-access checklist mentors insist on.md>) (strategies stated, N+1 prevented — stated there generally, performed here Prisma-specifically): every relation traversal declares its strategy per query — `include: { posts: true }` (eager batch in the same round trip — verified live: posts loaded with user in one call); `select: { id: true, posts: { select: ... } }` (projection + relation combined — transfer minimized, shape precise); lazy never (Prisma has no lazy loading by default — traversals without include fail loudly (property absent — compile-time visible, not runtime N+1 — the design choice making unstrategized access *impossible* rather than merely discouraged). Schema declares relations; queries strategize loads — declaration without strategy is navigation without a plan (possible everywhere, priced per access).

**What problem it solves** — the unstrategized traversal (relations accessed without include decisions — Prisma's explicitness converting would-be N+1 into compile errors (property absent — fail fast at build, not slow in production — the framework's structural gift); hand-rolled per-parent finds beside Prisma (loops calling findUnique per id — N+1 wearing client syntax — strategy absent where include would batch); over-including (include everything "just in case" — transfer bloat per render — cartesian products on multiple includes (verified caution below — two list-includes multiply rows — the fan-out from Database Design 04 wearing object syntax). Strategy-per-query converts all three (absent→compile error (structural); looped→batched (measured); over-included→projected (select trimming transfer)).

**Modern guidance** — the strategy lines per relation read (review-enforced): *include stated* (relations listed explicitly per query — `include: { posts: true }` (verified live — 1 post loaded with user); *select trimmed* (columns projected — `select: { id: true, email: true }` — transfer minimized (SELECT * never — projection discipline, same as raw); *multiple-list caution* (two `include: [listA, listB]` multiplies rows — fan-out ([Database Design §4.3](<../../../DatabaseDesign/04 Relationships at Scale/sections/3. Skew and hot relationships/3.1. Hot keys and skew.md>)) — split queries or accept with eyes open (documented per query — multiplicative transfer priced, never surprised); *counts asserted* (statement counts per list test — [Domain 01 §4.1](<../../01 Data Access Foundations and Mental Model/sections/4. Mentor checklist/4.1. Data-access checklist mentors insist on.md>)'s detector enforced from adoption — N+1 fails builds). Missing strategy → request changes; strategy present → verify with counts (asserted, not hoped).

**Common confusion** — *"Prisma has no N+1 (it batches automatically)."* Prisma batches *declared includes* (one query per include path — explicit relations — batched structurally); hand loops bypass batching entirely (per-parent client calls — N+1 fully manual — framework unable to help undeclared traversals); multiple list-includes multiply (fan-out — batched but combinatorial — transfer exploding while statements stay few). "No N+1" describes declared-include paths (true — batched); loops and fan-outs remain the author's responsibility (counted, split, asserted — discipline, not magic). Batching covers declared; discipline covers the rest — both required, neither automatic.

**Performance note** — include economics: declared includes cost one query per include path (batched — constant statements regardless of N — the N+1 immunity structural, not hoped); hand loops cost N statements (linear — latency scaling with data — discovered at scale, fixed by batching); multi-list includes cost combinatorial transfer (statements few, rows multiplied — transfer dominating — split queries per [Database Design §4.3](<../../../DatabaseDesign/04 Relationships at Scale/sections/3. Skew and hot relationships/3.1. Hot keys and skew.md>) (cause removed) over DISTINCT trimming (symptom trimmed). Statements bounded via includes; transfer bounded via select/split; counts asserted via tests — three bounds, complete read performance.

**Mentor note** — teach "strategy per include" (juniors stating include/select per relation read design bounded reads on first hearing; unstated includes interrogated ("which relations, and why these?" — strategy demanded per query). Include audits per hot path (production includes reviewed quarterly — unneeded relations trimmed (transfer shrinking), missing includes added (loops batched) — strategies living documents, not birth decisions). State strategies; audit quarterly; assert always — read performance in three habits, reviewed per PR.
