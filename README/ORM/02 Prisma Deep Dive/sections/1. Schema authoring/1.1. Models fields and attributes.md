# 1.1. Models fields and attributes

## 1. Models are tables declared once (fields, ids, defaults — one source of truth)

**Definition** — a Prisma model is a table declared in `schema.prisma`: scalar fields with types (`BigInt/String/Boolean/DateTime/Json`), an `@id` (usually autoincrementing BigInt or UUID), and defaults — the single source of truth from which migrations *and* the typed client both generate. Declare once, consume twice (DDL + types flowing from one artifact — drift between schema and code structurally impossible: regeneration overwrites stale types, never negotiates with them).

**What problem it solves / history** — the schema/code split (SQL migrations in one directory, TypeScript interfaces hand-maintained in another — column renamed in migration, interface stale until someone remembers — refactors breaking at runtime across services; or TypeORM-style decorators where schema knowledge scatters per class file — reviewed per file, never whole). Single-source models collapse the split (schema change → regenerate → compiler errors everywhere affected — refactors guided end-to-end; `prisma validate`/`format` enforcing schema hygiene — verified live this session). One artifact edited, two artifacts derived — drift impossible by construction, not by discipline.

**Modern guidance** — the authoring rules (verified live against Prisma 7.10.0 generate + client round-trip this session): ids explicit per model (`BigInt @id @default(autoincrement())` for PG sequences — or `@default(uuid())`/`@default(cuid())` for distributed generation — chosen per [Database Design key strategy](<../../../../DatabaseDesign/01 Modeling Foundations and Mental Model/sections/2. Identity and keys/2.1. Surrogate versus natural keys.md>), never defaulted blindly); nullability deliberate (`String?` optional vs `String` required — presence as contract, same as column discipline); defaults at the right layer (`@default(now())`/`@default(false)` for shape defaults — engine-enforced; application defaults for business logic — computed in code, never smuggled into schema); `createdAt/updatedAt` conventional (`@default(now())` + `@updatedAt` — audit-adjacent timestamps, cheap, always wanted — [Database Design §6.1](<../../../../DatabaseDesign/06 Modeling for Operations/sections/1. History and deletion/1.1. Audit trails that answer questions.md>)'s trigger mirrors remain the audit story, timestamps the convenience).

```prisma
// GOOD: models declared once — ids, nullability, defaults all explicit (verified: validate + generate passing).
model User {
  id        BigInt   @id @default(autoincrement())  // surrogate key (01/2.1 default, performed)
  email     String   @unique                        // natural identifier beside it (UNIQUE, unreferenced)
  name      String?                                 // optional: presence as contract (nullable = unknown OK)
  role      Role     @default(USER)                 // enum default (DB-level — verified live: USER applied)
  createdAt DateTime @default(now())                // shape default (engine-enforced — verified live)
  posts     Post[]                                  // relation field (1.2 owns the other side)
}
```

```prisma
// BAD: the undeclared model — implicit everything, intent nowhere.
// model User {
//   id    Int     @id               // Int autoincrement caps at 2B rows (fine — until viral; BigInt default costs nothing)
//   data  Json                      // schemaless escape (untyped payloads — validation hoped, queries unindexed)
//   // no createdAt (temporal questions unanswerable — "when?" asked of every row eventually)
//   // no relations declared (joins hand-written per query — mapper ceremony paid, graph convenience declined)
// }
// Defaults unexamined (Int where BigInt fits); typing declined (Json blobs); temporality absent;
// relations undeclared. The schema file exists; design doesn't. Declare deliberately or drift permanently.
```

**Common confusion** — *"Prisma models replace database design."* Models *record* design (entities, keys, constraints — decided per Database Design track, then declared); they don't *perform* it (undeclared dependencies stay undeclared — mappers persist unmodeled shapes faithfully, anomalies included). "Just write models" skips entities/dependencies/forms (shapes accreting per ticket — 3NF unaudited, cardinality unpriced — typed anomalies, still anomalies). Design first (Database Design — shapes disciplined); declare second (models projecting discipline); generate third (client + migrations flowing). Sequence, not substitution — mappers executing undisciplined shapes accelerate incidents, never prevent them.

**Performance note** — model-shape performance (id type width — BigInt 8B vs Int 4B vs UUID 16B per row + per FK index — priced once at authoring, paid forever per row); default placement (DB-level defaults cost nothing per write — engine fills; application defaults cost code paths per writer — backfills/consoles missing them); timestamp columns (createdAt indexed where recency queries filter — hot predicate, cheap index — unindexed temporal scans billed per dashboard). Authoring decisions compound per row (widths × billions) — price types at declaration (seconds now) vs storage/index/cache forever. Types chosen deliberately; widths priced honestly.

**Mentor note** — teach "declare once, consume twice" as the schema-file pitch (juniors editing models + regenerating + watching compiler errors guide refactors *feel* single-sourcing in minutes — drift-impossibility demonstrated, not described). Review models like code (every field earning its place — types, nullability, defaults questioned per line — schema PRs held to code standards, never waved as "config"). Declare deliberately; generate routinely; review rigorously — schema files are code with DDL consequences, treated accordingly from day one.

## 2. Attributes carry intent (unique, default, native types, enums — constraints beside fields)

**Definition** — schema attributes are column contracts declared inline: `@unique` (identity — one live claimant, enforced); `@default(...)` (shape defaults — engine-filled, writer-independent); native types (`@db.Text`, `@db.VarChar(n)`, `@db.Timestamptz` — storage granularity chosen, not defaulted); enums (`enum Role { USER ADMIN }` — closed vocabularies — DB-level CHECK-equivalent via native PG enums, verified live: `public.Role` type created, default applied). Attributes colocate constraints with fields (reviewed per line — intent visible where declared, never in separate migration archaeology).

**What problem it solves** — the constraint-afterthought habit (tables created bare — uniqueness added "when duplicates appear" (post-incident — duplicates already corrupting); defaults applied in code (backfills/consoles missing them — NULLs where values assumed); TEXT everywhere (widths unconsidered — storage/index/cache priced never); stringly-typed statuses (`status TEXT` — typos as data — 'actvie' rows accumulating, queries branching on misspellings). Attributes declared upfront convert post-incident patches to pre-merge contracts (uniqueness enforced from row one — duplicates impossible, not cleaned; defaults engine-filled — writers optional, not required; enums closed — typos rejected, not stored).

**Modern guidance** — the attribute checklist per field (review-enforced): *uniqueness* (identity fields `@unique` — emails, slugs, SKUs — enforced from first migration — duplicates impossible beats duplicates cleaned); *defaults* (shape defaults engine-side (`@default(false)`, `@default(now())`, enum defaults — verified live: role USER + published false applied without writer input); *native types* (`@db.VarChar(255)` where length bounded (index efficiency), `@db.Text` where not (honesty over arbitrary limits), `@db.Timestamptz` for instants (zones explicit — Databases 02 mechanics) — storage granularity decided, never defaulted); *enums* (closed sets as `enum` (roles, statuses, kinds — DB-native PG enums via Prisma — verified live: type created, values constrained) — open sets as relations (tags, categories — entities, not enums — growth accommodated without migrations).

```prisma
// GOOD: intent per field — uniqueness, defaults, natives, enums all declared (verified live).
enum Role {
  USER
  ADMIN   // closed set (DB-native PG enum "Role" — typos rejected structurally, verified)
}

model Post {
  id        BigInt  @id @default(autoincrement())
  title     String  @db.VarChar(300)   // bounded honestly (index-efficient, length-checked)
  published Boolean @default(false)    // shape default (verified live: false without writer input)
  author    User    @relation(fields: [authorId], references: [id], onDelete: Cascade)
  authorId  BigInt
}
// Live proof: create without role/published → defaults applied (USER, false — verified output).
```

```prisma
// BAD: attribute-free fields — intent absent, patches scheduled.
// model Post {
//   id     Int     @id               // Int cap unexamined (2B rows — viral-scale incident scheduled)
//   title  String                    // unbounded TEXT (300-char titles beside 3MB pastes — unexamined)
//   status String                    // open stringly-typed ('draft','DRAFT','draft ' — variants accumulating)
//   // no defaults (writers required for shape — backfills/consoles missing them — NULLs assumed)
//   // no enums (roles as strings — typos as data — 'admn' rows with privileges ambiguous)
// }
// Intent undeclared; patches post-incident; typos as data. Attributes cost lines at authoring;
// absence costs archaeology (which statuses exist? — DISTINCT queries answering design questions).
```

**Common confusion** — *"native types are premature optimization."* Native types are *correctness-adjacent* choices (VarChar bounds rejecting garbage (3MB titles — input bugs caught at storage, not in support tickets); Timestamptz preventing zone ambiguity (naive timestamps corrupting across zones — incidents, not microseconds); enum closure rejecting typos (data quality enforced — 'admn' never stored). "Optimization" describes shaving microseconds; natives prevent incidents (constraint violations failing fast at write time — hours saved per prevented support ticket). Correctness first (bounds/zones/closure), storage efficiency second (index sizes, cache residency — real but secondary). Decide deliberately; default never.

**Performance note** — attribute economics: enums as native PG types (4B OIDs vs TEXT strings per row — storage + index + cache all leaner — verified live: `Role` type created); VarChar bounds (index prefix efficiency — bounded strings indexing tighter than TEXT blobs); defaults engine-side (zero writer cost — filled at storage, not in code paths). Undeclared equivalents bill storage (TEXT where enums fit — bytes per row × billions), indexes (unbounded strings indexing loosely), and data quality (typo'd statuses branching queries — correctness incidents wearing performance costumes). Attributes priced per row-type once; absence billed per row forever.

**Mentor note** — teach "which native type, and why?" per field (juniors answering VarChar-vs-Text/enum-vs-relation/timestamptz-always internalize storage thinking permanently — types chosen, never defaulted). Closed-vs-open drill ("roles: enum or table?" — fixed set → enum; growing set → relation — decided by growth, not taste — 30-second verdicts, drilled per entity). Types decided deliberately; growth examined honestly; typos rejected structurally — attribute discipline in three habits, reviewed per schema PR.

## 3. Schema diffs are reviewed (generated migrations read fully — tooling authors, humans approve)

**Definition** — the review discipline carried over from [Domain 01 §4.1](<../../../01 Data Access Foundations and Mental Model/sections/4. Mentor checklist/4.1. Data-access checklist mentors insist on.md>) (migrations reviewed like code — stated there generally, performed here Prisma-specifically): every `prisma migrate dev`-generated SQL file read fully before commit (diffs are code — ADD COLUMN nullability checked, DROP TABLE questioned, index CONCURRENTLY-ness verified (migrate doesn't do CONCURRENTLY — large-table indexes need manual non-blocking application — known limitation, worked around deliberately)); renames declared (Prisma infers drop+create for renames unless guided — data loss wearing migration — rename intent stated via `prisma migrate diff` review or explicit mapping); phases honored ([Database Design §5.1](<../../../../DatabaseDesign/05 Evolution Growth and Partitioning/sections/1. Schema evolution/1.1. Expand and contract migrations.md>) — tooling executes phases, humans sequence them — expand/migrate/contract across deploys, never single-diff flag-days).

**What problem it solves** — the generated-diff trust failure (migrations applied unreviewed ("Prisma made it" — NOT NULL without default on 50M rows (blocking rewrite mid-deploy); inferred drop+create on renames (history destroyed with applause); missing indexes (relation scalar lists added without FK indexes — [Database Design §4.1](<../../../../DatabaseDesign/04 Relationships at Scale/sections/1. Foreign keys at volume/1.1. Foreign keys that survive traffic.md>)'s rule unapplied — parent writes scanning). Tooling accelerates authoring (diffs generated in seconds — velocity real); review governs shipping (humans classifying phases, witnessing contracts, sequencing deploys — judgment ungeneratable). Generated diffs read fully (every line — review completeness enforced); tooling trusted for mechanics (ordering, checksums — valuable, real), never for compatibility (phases, witnesses — human, contextual).

**Modern guidance** — the Prisma migration review lines (per generated diff): phase named (expand/migrate/contract — generator output classified per [Database Design §5.1](<../../../../DatabaseDesign/05 Evolution Growth and Partitioning/sections/1. Schema evolution/1.1. Expand and contract migrations.md>), never assumed safe); renames declared (drop+create pairs in diffs rejected on sight — data-preserving renames via explicit mapping or manual SQL — history never destroyed by inference); nullability checked (ADD NOT NULL without default on live tables — flag-day breaking shipped as safe — expand first (nullable → backfill → constrain)); indexes verified (relation FKs indexed — Prisma doesn't auto-index FKs (same engine truth as raw — index discipline from Database Design 04 applies through tooling — `@@index` added where missing, reviewed); deploy executed via `migrate deploy` (pending only — production executes history, never wishes — [2.1](<../2. Migrations and client/2.1. Migrate tooling that stays honest.md>) owns the pipeline fully).

```sql
-- GOOD: generated diff reviewed line-by-line (Prisma migrate dev output, human-gated).
-- -- AlterTable: ADD COLUMN "name" TEXT (nullable — expand phase ✓ — old writers safe)
-- -- CreateIndex: users_email_key reviewed (UNIQUE enforcement intended ✓)
-- Reviewer notes: phase EXPAND (compatible both directions ✓); no drops (nothing to witness);
-- FK indexes: authorId covered? (checked — @@index present ✓); deploy via migrate deploy
-- (pending-only ✓). Verdict: approve migration. (Tooling authored in seconds; humans governed in minutes.)
```

```sql
-- BAD: the trusted diff — generated, unreviewed, flag-dayed (real failure shapes).
-- -- AlterTable: ADD COLUMN "email" TEXT NOT NULL (no default — 50M-row rewrite + old-writer
-- failures fleet-wide — breaking shipped as safe, generator-authored, human-waved).
-- -- DropTable: "legacy_temp" + CreateTable "legacyTemp" (rename inferred as drop+create —
-- history destroyed with applause — undeclared rename, unwitnessed drop).
-- -- AlterTable: ADD COLUMN "authorId" BIGINT (no index — parent deletes scanning — FK discipline
-- unapplied through tooling). Generated quickly; approved blindly; incidents automated.
```

**Common confusion** — *"migrate dev handles safety (it warns about destructive changes)."* Warnings flag *destructiveness* (drops, data loss risks — valuable, real); safety requires *compatibility judgment* (phases, witnesses, stragglers — human, contextual — warnings unheeded ship incidents with acknowledged risks ("we saw the warning, proceeded anyway" — postmortem staple). Warnings inform; reviewers decide (warning + phase classification + witness evidence = approval; warning alone = information without verdict). Read warnings; classify phases; witness contracts — judgment layered atop tooling, never replaced by it.

**Performance note** — migration-review economics (same argument as every checklist leaf in this repo, Prisma edition): phased tooling-migrations distribute load (no blocking rewrites in windows); witnessed contracts prevent repair migrations (most expensive kind — incident-pressured, unrehearsed); FK indexes at birth cost seconds (empty-table builds — instant) vs retrofit hours (CONCURRENTLY under load — Databases 02 mechanics). Review minutes convert to outage-quarters avoided at the usual rate — highest-ROI minutes in Prisma operations, permanently true.

**Mentor note** — teach "read the generated SQL" (juniors reading migrate-dev output line-by-line discover generators' assumptions (drop+create renames, flag-day nullability, missing FK indexes) permanently — generated code reviewed like hand code, always). Automate the checkable half (CI: drop-without-witness fails; ADD-NOT-NULL-without-default on live tables fails; unindexed FKs fail — linters for migrations); review the judgment half (phases, compatibility, witnesses). Machines check shape; mentors check sequence — split accordingly, second domain running, permanent value.
