# 2.1. Production observability per mapper

## 1. Log sampled, alert thresholded (query events sampled in production — slow statements paging)

**Definition** — production logging discipline: query events sampled (fraction recorded — 1–10% typical (volumes manageable — full logging drowning storage/analysis (millions of statements daily — signal buried); slow statements logged always (threshold-exceeded queries recorded regardless of sampling (outliers captured — p99 investigated, not averaged away); alerts thresholded (slow-query rate/pattern alerting (paged on degradation — sustained slowness, not single spikes (spike tolerance avoiding alert fatigue — sustained-breach paging). Sampled volume, complete outliers, thresholded alerts — observability economical, never blind.

**What problem it solves** — the logging duo: *log-everything* (all statements recorded in production (storage exploding (terabytes of query logs — retention bankrupting; analysis impossible (signal buried in volume — slow queries hiding among millions of fast ones (needles in haystacks nobody searches); and *log-nothing* (production queries invisible (slow paths unidentified ("database slow" — which statements? — unanswerable (tuning unguided — EXPLAIN speculating); N+1 resurgent post-deploy (strategies regressing silently — unobserved (counts unasserted in production — staging green, production linear). Sampled logging with slow-always capture converts both (volume manageable — outliers complete — degradation alerting). Economical observability, complete outliers.

**Modern guidance** — the logging lines per service (review-enforced — verified live patterns): *sampled* (1–10% of statements recorded (volumes manageable — sampled traces representative (distributions preserved — p50/p99 estimable from samples); *slow-always* (threshold-exceeded statements recorded regardless (verified live: 326ms caught over 200ms threshold — outliers complete (slowest queries always visible — p99 investigated, never averaged); *thresholded alerts* (slow-query rate alerting (sustained degradation paging (spike tolerance — single slow query informing, never paging (fatigue avoided); *mappers instrumented* (Prisma `$on("query")` events (verified S2 pattern — v7 idiom); Drizzle/TypeORM logging callbacks (query events observed — per-tool idioms, same discipline (sample + slow-always + alert). Missing line → request changes (unobserved production failing structurally — surprises scheduled).

**Common confusion** — *"ORMs log automatically (observability included)."* Mappers emit query events (Prisma log events, Drizzle logging callbacks, TypeORM logging options — *mechanisms* available); observability requires *policy* (sampling rates decided (volumes manageable); slow thresholds set (outliers complete); alerts configured (degradation paging); dashboards built (gauges visible). "Automatic" confuses emission with observation (events flowing nowhere — unrecorded, unalerted, undashboarded — observability theater). Mechanisms available; policy designed (sample/threshold/alert/dashboard — four decisions, reviewed per service). Emit always (mechanisms on); observe deliberately (policy designed).

**Performance note** — observability economics: sampled logging costs fractions (1–10% volume — storage bounded — analysis feasible); slow-always costs outliers only (threshold-exceeded statements — complete slow set — p99 investigable); thresholded alerts cost attention wisely (sustained degradation paging — fatigue avoided (spike tolerance — single spikes informing); unobserved equivalents cost mystery slowness (which statements? — unanswerable (tuning unguided); N+1 resurgence (strategies regressing silently — linear latencies rediscovered quarterly); surprise cliffs (p99 official — pages without context). Sample cheaply (fractions); alert wisely (sustained); observe always.

**Mentor note** — teach "sample + threshold" (juniors configuring sampled logging with slow-always capture design economical observability on first hearing; log-everything interrogated ("retention cost?" — volumes priced); log-nothing interrogated ("slow queries visible how?" — outliers demanded). Demonstrate slowness detection live once (326ms caught over 200ms threshold — verified live pattern above (tangibility converting permanently — outliers complete, always). Sample fractions; threshold outliers; alert sustained — observability in three habits, reviewed per service.

## 2. Gauges per handoff (pool depth, relay lag, queue age — dashboarded from birth, owned per team)

**Definition** — handoff gauges: every asynchronous/data path exposing health metrics — pool depth (checked-out vs max — saturation visible (exhaustion approaching, not arrived); relay/outbox lag (oldest unrelayed age — [Database Design §6.2](<../../../DatabaseDesign/06 Modeling for Operations/sections/2. Coordination out of the database/2.1. Outbox tables designed for relay.md>) — delivery health); queue age/depth (pending counts + oldest-pending timestamps ([Database Design §6.2... ORM 03/2.2 job tables — depth/age dashboarded); migration lag (pending count — deploys current?). Gauges dashboarded from birth (metrics existing before incidents — baselines known (normal ranges established — deviations alerting); owned per team (humans paged — owners reviewing dashboards weekly (unowned gauges decaying (thresholds stale — alerts misfiring — dashboards abandoned).

**What problem it solves** — the ungauged handoff (pools saturating invisibly (exhaustion discovered via refused connections (pages without warning — depth unmonitored); relays stalling silently (lag growing unboundedly — customers discovering (complaints preceding alerts — embarrassment scheduled); queues deepening invisibly (pending months-deep — workers saturated long before anyone looked — gauges would have fired at 10× normal (unbuilt — hope as monitoring). Gauges convert decay to signal (saturation visible pre-incident (depth trending — alerts firing with lead time); stalls visible pre-complaint (lag dashboarded — relays fixed before customers notice); depth visible pre-saturation (pending trending — workers scaled proactively). Decay signaled; incidents preempted; customers never first to know.

**Modern guidance** — the gauge lines per handoff (review-enforced — verified live observability): *pool depth* (`pg_stat_activity` per application_name (verified live: pool conns visible (application_name tagging — pools distinguished (per-service visibility — shared databases disambiguated); *lag/age* (outbox oldest-unrelayed, queue oldest-pending (timestamps queried — lag dashboarded (thresholds firing — staleness bounded); *ownership* (gauges owned per team (humans paged — dashboards reviewed weekly (thresholds current — unowned gauges decaying (stale thresholds misfiring — dashboards abandoned within quarters); *baselines* (normal ranges established early (deviation alerting — novel services baselining first month (thresholds calibrated, not defaulted). Missing gauge → request changes (unobserved handoffs failing structurally — surprises scheduled); unowned gauge → assign owner (ownership demanded per metric).

**Common confusion** — *"gauges are monitoring config, not modeling."* Gauge-*serving columns* are modeling (occurred_at on outbox rows, claimed_at on jobs, status machines queryable — shaped at table creation ([Database Design §6.4](<../../../DatabaseDesign/06 Modeling for Operations/sections/4. Unshaped tables can't be gauged (lag unmeasurable without timestamps — monitoring discovers the gap, modeling fixes it a migration later). Gauges designed with tables (columns serving); dashboards operated after merge (thresholds firing). Co-designed, never retrofitted — modeling enabling monitoring structurally.

**Performance note** — gauge economics: gauge queries cost indexed point-lookups (lag/depth/age — microseconds — dashboard polling cheap); alert evaluation costs monitoring cycles (trivial — thresholds on existing metrics); unobserved equivalents cost mystery incidents (saturation/stalls/depth discovered via customers/pages (context absent — lead time zero — war rooms convened blind). Gauges cheapest insurance in async systems (microseconds per poll preventing quarters per incident — stated finally across both tracks (Database Design 06/4.1 twin — same verdict, ORM edition). Instrument everything async; alert ruthlessly; runbook calmly.

**Mentor note** — teach "what's the gauge?" per async path (juniors answering with lag/depth/age triples design observable systems on first hearing; answering "the cron runs" learn the distinction in one question). Gauge-first async design generalizes (every handoff — queues, relays, webhooks, syncs — gets gauges before code: lag, depth, errors, age — universal async vital signs). Review async PRs gauge-first ("show me the gauges" — missing gauges fail structurally); praise gauged handoffs publicly ("great lag gauge with owner"). Praise gauges; gauge praise's effect on incidents avoided.

## 3. Magic re-audited per deploy (defaults checked post-upgrade — behavior changes caught before customers)

**Definition** — the upgrade audit: mapper defaults re-examined per version change (dependency bumps, major upgrades, config edits — defaults checked: relation loading defaults (eager/lazy/explicit — changed? (v7 middleware removal breaking counters (verified live S2 — gauges dead silently post-upgrade — N+1 unobserved from the migration that removed observation); cascade/transaction defaults (cleanup scripts deleting parents — data loss wearing convenience — defaults re-listed per major); pooling/timeout defaults (adapter-managed pools resizing silently (sizing unknown post-upgrade — exhaustion redesigned); feature-flagged behaviors (new defaults behind flags — flipping post-upgrade (behavior changing without code changes — surprises scheduled). Re-audited per deploy touching dependencies (upgrades, bumps, config edits — magic inventoried continuously, never once-and-done).

**What problem it solves** — the upgrade surprise trio: *default changes* (majors altering defaults (relation strategies flipping (N+1 appearing post-upgrade — strategies un re-audited (magic assumed stable — versions moving underneath); *gauge breakage* (observability idioms removed (v7 `$use` gone — counters dead silently (N+1 unobserved exactly when observability lapsed — blindness arriving with the upgrade meant to improve things); *behavior flips* (feature-flagged defaults activating post-upgrade (unexamined new paths executing (untested behaviors running production traffic — surprises scheduled (flags flipping without review). Per-deploy magic audits convert all three (defaults re-listed (changes caught pre-production); gauges re-verified (counters working post-upgrade — observability continuous); flags reviewed (new behaviors examined pre-activation — surprises declined).

**Modern guidance** — the audit lines per dependency change (review-enforced): *defaults re-listed* (relation/cascade/transaction/pooling defaults compared version-to-version (changelog read fully — breaking-changes section first (surprises hiding in minor notes — minors reviewed like majors where defaults live); *gauges re-verified* (observability idioms tested post-upgrade (counters firing (v7 events replacing `$use` — migration verified live S2 — N+1 observable continuously); *flags reviewed* (new default behaviors examined (feature flags flipping — unexamined activations declined (flags held until reviewed — behavior changes scheduled, never surprised); *ledgers re-priced* ([Domain 05 §1.2](<../../05 Comparing and Choosing/sections/1. **Common confusion** — *"green tests mean safe upgrades (CI passing suffices)."* Tests assert *old* behaviors (written against previous defaults — passing irrelevantly post-change (strategies unexamined (new defaults untested — coverage green on stale assumptions); gauges unwired to new idioms (counters testing removed APIs (passing vacuously — observability dead silently); flags unexamined (new behaviors untested (default paths uncovered — surprises scheduled). "Green" describes old-behavior conformance (regression absent for tested paths); safety requires new-behavior examination (defaults re-listed, gauges re-verified, flags reviewed — audit beyond green). Green necessary (regressions caught); insufficient alone (novelties unexamined). Green + audit; never green-alone.

**Performance note** — audit economics: defaults re-listing costs review minutes per upgrade (changelog read — breaking section first — surprises caught pre-production); gauge re-verification costs test runs (counters firing post-bump — observability continuous); flag reviews cost examination minutes (new behaviors assessed — activations scheduled); unexamined equivalents cost upgrade incidents (N+1 appearing (strategies un re-audited); gauges dead (observability lapsed); flags flipped (behaviors surprising) — quarters each. Minutes per upgrade prevent quarters per incident — audit ROI exceeding all other upgrade investments (magic inventoried continuously; surprises extinct).

**Mentor note** — teach "re-audit per dependency change" (juniors re-listing defaults post-bump design upgrade safety on first hearing; unexamined upgrades interrogated ("defaults re-listed? gauges verified? flags reviewed?" — three questions, seconds each, unexamined upgrades returned). Dependabot-plus-audit (automated bumps triggering human audits — machines proposing, humans disposing — velocity with judgment). Audit upgrades; verify gauges; review flags — upgrade safety in three habits, reviewed per dependency change.
