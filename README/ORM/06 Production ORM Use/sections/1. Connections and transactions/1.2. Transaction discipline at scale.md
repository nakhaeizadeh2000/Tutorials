# 1.2. Transaction discipline at scale

## 1. Scope transactions minimally (shortest unit covering the invariant — locks brief, never conversational)

**Definition** — minimal scoping: transactions spanning exactly the statements sharing one invariant (order + lines + outbox row (atomic recording — [Database Design §6.2](<../../../DatabaseDesign/06 Modeling for Operations/sections/2. Coordination out of the database/2.1. Outbox tables designed for relay.md>)); balance debit + ledger entry (money moving — both-or-neither); nested graph writes (single mapper call — atomic by construction ([Domain 02 §2.2](<../../02 Prisma Deep Dive/sections/2. Migrations and client/2.2. Client queries and relations.md>))). Conversational transactions (opened, user input awaited, external API called, then committed — locks held across network round trips (lock windows spanning seconds-to-minutes — contention serializing all concurrent writers on touched rows — throughput collapsing to lock-hold latency).

**What problem it solves** — the scope trio: *conversational transactions* (transaction opened → HTTP call → user prompt → commit (locks held across seconds (row/page locks blocking concurrent writers — throughput = 1/lock-hold-latency — single slow dependency throttling entire tables); *kitchen-sink transactions* (dozens of statements in one unit (unrelated invariants sharing fate — failure anywhere aborting everything (blast radius maximal — retry cost maximal — partial progress impossible (atomicity overscoped — independent units coupled); *transactionless multi-writes* (related statements committed separately (partial graphs persisting on mid-sequence crashes — inconsistency scheduled (compensating cleanups untested — orphan states accumulating). Minimal scoping converts all three (invariant-sized units (locks brief — contention minimal); related writes atomic (partial states impossible); unrelated writes independent (failures isolated — blast radius minimal).

**Modern guidance** — the scoping lines per transaction (review-enforced): *invariant-sized* (statements sharing one business invariant per unit (order+lines+outbox (atomic recording); debit+ledger (money atomicity) — invariant named per transaction (unnamed invariants unscoped — scope unjustified); *network-free* (no HTTP/user/API calls inside (external latency excluded structurally — fetch-then-transact (data gathered pre-transaction — locks held across microseconds of local statements only); *timeout-bounded* (maxWait/timeout configured per transaction (verified pattern family — contention windows finite — unbounded transactions blocking vacuum/locks rejected); *verified rollback* (throw-to-abort tested (verified live: Drizzle `db.transaction` rolling back on throw — atomicity demonstrated, not described — rollback paths tested per transaction shape (abort verified, not hoped).

```typescript
// GOOD: invariant-sized transactions — locks brief, rollback verified (verified live shape).
await db.transaction(async (tx) => {
  await tx.execute("SELECT 1");   // local statements only (microseconds of lock-hold)
  throw new Error("rollback-me"); // abort path (verified live: rolled back on throw — atomicity demonstrated)
});   // Verified live output: "tx rolled back on throw" (db.transaction function — Drizzle 0.45.3).
// Invariant named per transaction (order+lines+outbox — atomic recording); network excluded
// (fetch-then-transact — locks brief); timeouts bounded (contention finite).
```

```typescript
// BAD: conversational and kitchen-sink transactions — locks sprawling, scopes unexamined (real shapes).
// await db.transaction(async (tx) => {
//   const user = await tx.find(...); const profile = await fetch(`https://api/...${user.id}`);
//   const answer = await promptUser(...);   // locks held across HTTP + human latency (seconds-to-minutes —
//   await tx.save(...);                     // contention serializing all concurrent writers (throughput = 1/latency).
// });  // Or: 40 unrelated statements, one unit (failure anywhere aborting everything — blast radius maximal).
// Or: three related writes, three transactions (partial graphs on mid-sequence crashes — inconsistency scheduled).
// Conversational/kitchen-sink/fragmented — scopes unexamined, locks sprawling, partials scheduled.
```

**Common confusion** — *"bigger transactions are safer (atomicity maximized)."* Atomicity protects *invariants* (statements sharing one business truth — all-or-neither correct); overscoping couples *independents* (unrelated statements sharing fate — failures cascading spuriously (one failure aborting 39 unrelated successes — blast radius maximal); locks sprawling (held across all statements — contention maximal — throughput minimal). "Safer" describes invariant coverage (complete per invariant — correct); overscoping trades coverage for coupling (safety theater with contention bills). Scope to invariants (minimal complete units); isolate independents (failures contained); bound durations (timeouts finite).

**Performance note** — scoping economics: minimal scopes hold locks briefly (microseconds of local statements — contention minimal — throughput maximal); conversational scopes hold locks across networks (seconds-to-minutes — contention serializing (throughput = 1/hold-latency — single slow dependency throttling tables); kitchen-sink scopes hold locks across dozens of statements (contention maximal — blast radius maximal — retry cost maximal). Lock-hold time is throughput (Little's-law bounded — concurrency = throughput × hold-time — hold minimal, throughput maximal). Scope minimally; exclude networks; bound durations.

**Mentor note** — teach "name the invariant" per transaction (juniors stating the shared business truth design minimal scopes on first hearing; invariant-less transactions interrogated ("which invariant needs atomicity here?" — scope unjustified without named invariant). Demonstrate rollback live once (throw mid-transaction — verified abort — atomicity tangible, not theoretical — trust earned by breaking safely). Name invariants; exclude networks; verify rollbacks — transaction discipline in three habits, reviewed per unit-of-work.

## 2. Isolation chosen deliberately (read committed default, stronger where anomalies threaten)

**Definition** — isolation levels as anomaly trade-offs (mechanics owned by Databases 05 — linked, never re-taught; decisions owned here): **read committed** default (each statement seeing committed data — anomalies possible (non-repeatable reads, phantoms — acceptable where re-reads tolerate drift (dashboards, listings, analytics — tolerance stated); **repeatable read / snapshot** where anomalies threaten (money-moving reads-then-writes (balance checks before debits — non-repeatable reads corrupting (check-then-act raced — serialization failures retried (optimistic, priced); **serializable** where correctness demands (inventory decrements, seat bookings — anomalies unacceptable (pessimistic correctness — serialization failures *expected* (retried with backoff — priced explicitly). Levels chosen per transaction (anomaly analysis, not defaults worshipped — defaults fitting most reads, threatening some writes).

**What problem it solves** — the isolation duo: *default-everywhere* (repeatable-read/snapshot needs running read-committed (check-then-act raced (balance checked, concurrently debited — overdrafts scheduled (anomalies billing as money); lost updates overwriting (read-modify-write cycles clobbering (increments lost — counters drifting); and *serializable-everywhere* (correctness maximalism (serialization failures on hot paths (throughput collapsing under contention — retries amplifying — correctness priced in availability (unexamined); read-only analytics serialized (snapshot isolation sufficing — serializable overkill taxing throughput pointlessly). Isolation matched per transaction (anomaly analysis — threat modeled, level chosen, retries priced); defaults worshipped nowhere (levels decided, never inherited blindly).

**Modern guidance** — the isolation lines per transaction (review-enforced): *default stated* (read committed assumed unless stated otherwise (dashboards/listings/analytics — drift-tolerant reads — tolerance stated, not hoped); *stronger where threatened* (money-moving check-then-act (repeatable-read/snapshot — serialization failures retried with backoff (optimistic, priced); inventory/seat contention (serializable — failures expected (retried — correctness maximal, availability priced); *retries designed* (serialization-failure handlers (backoff + jitter + budgets (amplification impossible — failures visible, not cascading); *documented per transaction* (isolation level stated in code comments (reviewers verifying anomaly analysis — levels decided visibly, never defaulted silently). Missing level → request changes where anomalies threaten (default accepted only with tolerance stated).

```typescript
// GOOD: isolation decided per transaction — levels stated, retries designed (shapes verified).
// Reads (dashboards/listings): default read committed (drift-tolerant — tolerance stated ✓).
// Money check-then-act: repeatable-read/snapshot (serialization failures retried w/ backoff ✓).
// Inventory decrement: serializable (failures expected — retried — correctness maximal, availability priced ✓).
// Retries: backoff + jitter + budgets (amplification impossible — failures visible ✓).
```

```typescript
// BAD: isolation unexamined — defaults worshipped, anomalies scheduled (real shapes).
// Balance check-then-debit at default isolation (non-repeatable reads racing (overdrafts scheduled —
// anomalies billing as money). Lost-update increments (read-modify-write clobbering (counters drifting —
// correctness evaporating silently). Serializable analytics (snapshot-sufficient reads serialized
// (throughput collapsing under contention — correctness maximalism taxing pointlessly).
// Defaults worshipped; anomalies scheduled; throughput taxed. Decide per transaction.)
```

**Common confusion** — *"stronger isolation is always safer (correctness maximalism)."* Stronger isolation trades availability for correctness (serialization failures under contention — retries amplifying (hot paths collapsing — correctness priced in throughput (unexamined pricing billing heedlessly); snapshot-sufficient reads serialized (overkill taxing pointlessly — correctness identical, throughput halved). "Safer" describes anomaly elimination (complete per level — genuine); availability priced alongside (failures retried — budgets enforced — hot paths measured). Correctness maximalism ignores price (availability unexamined); anomaly analysis prices both (threat modeled — level chosen — retries designed). Analyze threats; choose levels; design retries.

**Performance note** — isolation economics: read-committed costs baseline (statement snapshots — throughput maximal — anomalies possible (tolerated where stated); repeatable-read costs snapshot holds (versions retained per transaction — long snapshots bloating (VACUUM impeded — hot-standby feedback configured where replicas lag); serializable costs predicate tracking + abort rates (contention serializing — throughput = 1/contention-window — hot paths collapsing under contention (retries amplifying — budgets bounding). Levels priced per transaction (anomaly protection vs throughput/availability — arithmetic, not dogma). Analyze anomalies; price levels; bound retries.

**Mentor note** — teach "which anomaly threatens here?" per transaction (juniors naming non-repeatable/phantom/lost-update per unit design isolation deliberately on first hearing; unthreatened transactions defaulting (tolerance stated — read committed honestly); threatened transactions strengthened (levels chosen — retries designed). Anomaly vocabulary from Databases 05 (linked — mechanics there, decisions here). Name threats; choose levels; design retries — isolation discipline in three habits, reviewed per unit-of-work.

## 3. Timeouts bound everything (statement, transaction, lock — runaway work killed structurally)

**Definition** — the timeout trio (verified live patterns S6U4: `statement_timeout` canceling 1s sleep at 100ms — enforcement structural): **statement_timeout** per role (runaway queries killed (migrations/analytics scoped longer per statement — global relaxation never (one role's patience not all roles' — scoped exceptions, never blanket); **transaction/idle timeouts** (`idle_in_transaction_session_timeout` — abandoned transactions killed (connection leaks from uncommitted work — pool starvation via forgotten commits — timeouts reclaiming structurally); **lock_timeout** (lock waits bounded (deadlock-adjacent stalls failing fast — contention visible via errors, not hangs — waiting requests failing with diagnostics, not silence). Timeouts layered (statement < transaction < idle — each bounding its scope — runaway work killed at the tightest applicable bound, never surviving to looser ones).

**What problem it solves** — the unbounded trio: *runaway statements* (bad join/cartesian exploding (single query holding connections indefinitely — pool starvation via one statement (service-wide stalls from one query — blast radius maximal from minimal cause); *abandoned transactions* (uncommitted work holding locks (application crashes mid-transaction — connections leaked (pool draining silently — locks held indefinitely (vacuum blocked — bloat accumulating — cascading degradation from one forgotten commit); *indefinite lock waits* (contended rows queueing waiters unboundedly (lock chains growing — throughput zero for affected rows — diagnosis via piled-up backends, not errors (silence instead of signals). Bounded timeouts convert all three to fast failures (statements canceled (errors immediate — offending query identified); transactions reclaimed (locks released — pools refilled); lock waits diagnosed (errors naming contention — signals, not silence).

**Modern guidance** — the timeout lines per role/service (review-enforced — verified live enforcement): *statements* (`statement_timeout` per role (OLTP seconds (runaways killed — migrations/analytics scoped longer per statement (scoped exceptions with reasons — global relaxation never (one role's patience ≠ all roles'); *transactions* (idle-in-transaction timeouts (abandoned work reclaimed — pool starvation via forgotten commits structurally impossible); *locks* (`lock_timeout` bounded (lock waits failing fast with diagnostics — contention visible via errors (signals, not silence — deadlock-adjacent stalls diagnosed immediately); *verified* (timeouts tested (100ms canceling 1s sleep — verified live S6U4 — enforcement demonstrated, not documented (break glass tested — timeouts firing observed (gauges confirming — runaways actually killed, not theoretically bounded).

```sql
-- GOOD: timeouts layered — statements, transactions, locks all bounded (verified live enforcement).
-- SET statement_timeout = '30s';  -- OLTP role (runaways killed — verified live pattern: 100ms cancels 1s)
-- Migrations role: SET statement_timeout = '1h';  -- scoped exception (reason recorded — global never relaxed)
-- idle_in_transaction_session_timeout = '1min'  -- abandoned transactions reclaimed (pool starvation impossible)
-- lock_timeout = '5s'  -- lock waits failing fast with diagnostics (contention visible — signals, not silence)
```

```sql
-- statement_timeout unset (bad join exploding — single query holding connections indefinitely (pool
-- starvation via one statement — service-wide stalls from minimal cause). idle-in-transaction unset
-- (crashed app mid-transaction — locks held indefinitely (vacuum blocked — bloat accumulating —
-- cascading degradation from one forgotten commit). lock_timeout unset (contended rows queueing
-- unboundedly (throughput zero — diagnosis via piled-up backends, not errors). Unbounded timeouts;
-- unbounded consequences. Bound everything saturable.)
```

**Common confusion** — *"timeouts mask real problems (fix queries instead)."* Timeouts *bound* problems (runaways killed fast — blast radius contained — then fixed calmly (offending query tuned with EXPLAIN — root causes addressed post-containment); untimed queries *amplify* problems (one bad join starving pools (service-wide stalls — incidents cascading while tuning proceeds (tuning under fire — rushed, partial). "Masking" describes alerts suppressed (timeouts silent — unmonitored cancellations hiding systemic issues); bounded timeouts alert (cancellation logged + metered — systemic slowness visible via cancellation rates (tuning prioritized by evidence). Bound + alert (contained AND diagnosed); tune calmly (post-containment, never mid-fire). Timeouts first (blast radius); tuning second (root causes); monitoring always.

**Performance note** — timeout economics: bounded timeouts cost configuration lines (per role/service — reviewer-checked); cancellation false-positives cost legitimate long queries (migrations/analytics hitting OLTP timeouts — scoped exceptions preventing (roles separated — patience priced per workload); unbounded equivalents cost pool starvation (runaway-held connections — service-wide stalls); abandoned locks (vacuum blocked — bloat accumulating); indefinite waits (throughput zero — diagnosis via archaeology). Timeouts priced in lines (seconds to configure); unboundedness priced in outages (quarters each). Bound saturable; scope exceptions; alert cancellations.

**Mentor note** — teach "bound everything saturable" (juniors setting timeouts per role/service design finite failure modes on first hearing; unbounded configurations interrogated ("statement timeout? idle timeout? lock timeout?" — three questions, seconds each, unexamined timeouts returned). Demonstrate cancellation live once (100ms killing 1s sleep — verified live S6U4 (enforcement tangible — trust earned by watching kills work, not by documentation claims). Bound saturable; scope exceptions; alert cancellations — timeout discipline in three habits, reviewed per role.
