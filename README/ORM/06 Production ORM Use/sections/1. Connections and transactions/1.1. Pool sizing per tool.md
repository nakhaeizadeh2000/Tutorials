# 1.1. Pool sizing per tool

## 1. Pools bound concurrency (max connections sized from workload, never defaulted)

**Definition** — pool sizing: `max` connections per service instance bounded by arithmetic — `max × instances ≤ database max_connections − headroom` (headroom for admin/migrations/monitoring — 5–10 reserved, never zero); per-service max derived from concurrency (peak concurrent DB-touching requests × queries-per-request ÷ target utilization (~70% — queues absorbing bursts without timeouts); queueing configured (acquire timeouts finite — waiting requests failing fast with 503s, never hanging indefinitely). Defaults unexamined (pg default max 10 per pool × 50 replicas = 500 connections against a 100-connection database — exhaustion by multiplication, the most common pool incident, entirely arithmetic).

**What problem it solves** — the unpriced-pool trio (verified live behaviors this session): *exhaustion by multiplication* (defaults × replicas × services exceeding database limits — "too many clients" pages under load (connections refused — cascading failures (retries amplifying — retry storms converting saturation to outage); *unbounded queueing* (acquire waits infinite (requests hanging until timeouts elsewhere fire (gateway 504s — user-facing hangs, no fast failure — backpressure absent); *timeout-less queries* (runaway statements holding connections indefinitely (one bad migration/join starving the pool — single query DoSing the service (verified live: `statement_timeout` cancels at 100ms — enforcement structural, not hoped). Sized pools with finite waits convert all three (arithmetic bounding totals, timeouts failing fast, backpressure shedding gracefully).

**Modern guidance** — the sizing lines per service (review-enforced — verified live shapes): *max derived* (`max` = peak-concurrent-DB-requests × queries-per-request ÷ 0.7 (70% target utilization — bursts queueing briefly, never timing out; × instances summed vs database limit (headroom reserved — admin/migrations/monitoring never starved); *waits finite* (`connectionTimeoutMillis` set (acquire waits failing fast (503 + Retry-After — backpressure honest — hanging requests absent); *statements bounded* (`statement_timeout` per role (verified live: 100ms cancels 1s sleep — runaways killed structurally (migrations/rollups getting explicit longer timeouts per statement (scoped exceptions, never global relaxation); *verified live behavior* (max:1 serializes 3×0.5s → 1539ms measured (queueing, not failing — pools queue by default (latency absorbing bursts — timeouts bounding absorption).

  idleTimeoutMillis: 30000,         // idle connections recycled (resource hygiene — stale/closed reaped)
  // × 8 instances = 80 ≤ 100 limit − 10 headroom (admin/migrations/monitoring reserved — arithmetic holds)
});

**Common confusion** — *"bigger pools mean faster services (max generously)."* Connections beyond database capacity *contend* (PostgreSQL backends ~1-per-core effective (oversubscription context-switching — throughput *falling* past core-count multiples — bigger pools slowing services under load (contention, not parallelism); pool-queueing beats database-queueing (requests waiting in pool (cheap — application-side, observable) vs queries contending in database (expensive — lock waits, buffer churn — backpressure belongs pool-side, never engine-side). "Bigger" confuses capacity with throughput (connections ≠ parallelism past cores — Little's-law bounded (concurrency = throughput × latency — sized arithmetically, never generously). Size arithmetically (workload × queries ÷ utilization); headroom explicitly; generosity never.

**Performance note** — pool economics: sized pools cost thought once (arithmetic per service — max/waits/timeouts decided — reviewed yearly or per scaling event); queueing absorbs bursts (latency vs errors tradeoff — finite waits failing fast past absorption (backpressure honest); timeouts bound runaways (statement/transaction/lock timeouts — worst-case connection-hold finite — single-query DoS structurally impossible). Unsized equivalents cost exhaustion incidents (refused connections — cascading retries — retry storms); unbounded waits (hung requests — gateway timeouts — user-facing hangs); unbounded statements (runaway locks — pool starvation — service-wide stalls). Arithmetic once; timeouts always; hangs never.

**Mentor note** — teach "max × instances ≤ limit − headroom" (juniors computing per service design bounded concurrency on first hearing; uncomputed pools interrogated ("max? instances? limit? headroom?" — four numbers, seconds each, unexamined pools returned). Demonstrate exhaustion live once (max:1 + concurrent slows — 1539ms measured (queueing visible — timeouts bounding absorption — tangibility converting permanently). Compute arithmetic; bound waits; verify live — pool discipline in three habits, reviewed per service.

**Common confusion** — *"pooling is infrastructure (DevOps sizes pools)."* Pool *provisioning* is infrastructure (database max_connections, PgBouncer topology — ops-owned); pool *configuration per service* is application design (max per workload (concurrency arithmetic — service-known); waits/timeouts per path (backpressure semantics — service-decided); sharing per workload-class (interference measured — service-observed). ## 3. Exhaustion designed out (queueing, timeouts, backpressure — degraded gracefully, never hung)

**Definition** — the exhaustion contract: pools under load *queue briefly, then fail fast* (acquire waits bounded (`connectionTimeoutMillis` — verified live pattern: waits finite (requests failing with 503 + Retry-After past absorption — backpressure honest); statements bounded (`statement_timeout` — verified live: 100ms cancels 1s sleep — runaways killed structurally); retries bounded (exponential backoff + jitter + budgets (retry storms prevented — retry discipline (attempts capped, backoff jittered, budgets enforced — attempts capped, backoff jittered, budgets enforced — amplification impossible structurally); degradation graceful (read-only mode? cached responses? queued writes? — fallback ladder defined per service (degraded answers beating hung requests — UX surviving saturation).

**What problem it solves** — the saturation trio: *hung requests* (infinite acquire waits (requests hanging until gateway timeouts (user-facing hangs — no fast failure — backpressure absent (saturation invisible until cascading); *retry amplification* (failures retried immediately + aggressively (clients hammering saturated pools — retry storms converting saturation to outage (exponential harm — linear cause); *ungraceful collapse* (no fallback ladder (saturated → erroring everything (reads failing identically to writes — critical paths unprotected (checkout down because analytics saturated the shared pool — noisy neighbors + no isolation + no fallback = total outage from partial saturation). Bounded waits + bounded retries + fallback ladders convert saturation to degradation (slow/erroring gracefully — critical paths protected (isolation + priority) — recovery automatic on load drop (no intervention needed — saturation self-healing where bounded).

**Modern guidance** — the exhaustion lines per service (review-enforced — verified live patterns): *waits finite* (`connectionTimeoutMillis` 1–5s typical (acquire waits failing fast (503 + Retry-After — backpressure honest — hanging requests absent); *statements bounded* (`statement_timeout` per role (verified live enforcement — runaways killed structurally (migrations/analytics scoped longer per statement — global relaxation never); *retries bounded* (exponential backoff + jitter (thundering herds dispersed — synchronized retries stampeding avoided); budgets (N attempts then fail (amplification impossible — attempts capped (3 typical — then error surfacing (failures visible, not cascading); *fallback ladder* (saturation responses defined (read-only degraded mode? stale-cache serving? write queueing with user messaging? — degraded answers beating hung requests — UX surviving saturation (critical paths isolated (separate pools/limits — checkout protected from analytics — isolation priced, outages bounded).

**Common confusion** — *"backpressure means rejecting users (bad UX)." Backpressure means *responding fast with degraded answers* (503 + Retry-After (retry scheduled — clients backing off cooperatively); read-only degraded mode (cached/stale answers — information flowing, writes queued); prioritized shedding (critical paths protected (checkout isolated — analytics shed first — degradation ordered, never uniform). "Rejecting" describes unbounded failure (hung requests timing out opaquely — worst UX (waiting then failing); bounded backpressure *protects* UX (fast degradation — users informed, retries scheduled, critical paths alive). Fast-degraded beats hung-failed universally (latency honest — expectations managed — recovery automatic). Bound waits; budget retries; ladder fallbacks.

**Performance note** — exhaustion economics: finite waits cost configuration lines (timeouts set — reviewer-checked); bounded retries cost backoff code (libraries standard — jitter included — thundering herds dispersed); fallback ladders cost design thought (degraded modes defined — read-only paths identified — critical journeys protected); unhandled saturation costs cascading outages (retry storms — exponential harm; hung requests — gateway timeouts; total collapse — partial saturation felling whole services). Bounded waits + retries + fallbacks perform gracefully under saturation (degraded, responsive, self-healing); unbounded equivalents perform catastrophically (hung, amplifying, total). Bound everything saturable; ladder everything critical.

**Mentor note** — teach "saturation is normal" (juniors designing for saturation (bounds/timeouts/fallbacks from birth — load spikes expected (launches, virality, batch overlaps — saturation scheduled as weather, not disaster); unsaturation-assuming designs (infinite waits, unbounded retries, no fallbacks — fair-weather architectures (calm seas assumed — storms sinking). Load-test saturation deliberately (burst tests quarterly — bounds verified under fire (timeouts firing, fallbacks engaging, recovery automatic — saturation rehearsed, never hoped). Design saturated; test spiky; degrade gracefully — exhaustion discipline in three habits, reviewed per service.
