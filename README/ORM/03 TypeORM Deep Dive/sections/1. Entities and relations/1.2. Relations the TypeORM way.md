# 1.2. Relations the TypeORM way

## 1. Four decorators, four cardinalities (both sides where traversed)

**Definition** — TypeORM relations in four decorators (all verified present on 1.1.1 this session): `@OneToOne` (profile↔user via unique FK — one row each side); `@OneToMany`/`@ManyToOne` (author↔books — collection one side, reference the other — the workhorse); `@ManyToMany` (students↔courses — junction implicit or explicit — next promise). Both sides declared where traversed (forward list + back-reference — navigation either way via `relations: {...}`); owner side marked (`@JoinColumn` for 1-1/M-1 (FK holder), `@JoinTable` for implicit m-n (junction named) — owner holds the key, non-owner maps it).

**What problem it solves** — the half-declared relation (forward `@OneToMany` without `@ManyToOne` back (reverse traversal unservable — author.posts unreachable via client — raw SQL escaping for routine navigation); `@JoinColumn` omitted (owner ambiguous — FK placed by convention (naming strategy dependent — environments disagreeing); cascade/actions defaulted (NO ACTION answering deletes at runtime — surprises in production). Both-sides + owner-marked + actions-stated converts relations from column pairs to navigable, governed associations (traverse either way via relations option; delete per policy, never per default) — verified live below (1-N cascade save + relations include, all passing).

**Modern guidance** — the relation checklist per association (review-enforced — verified live shapes on TypeORM 1.1.1): *both sides* (OneToMany + ManyToOne pair (navigable both ways — `relations: { books: true }` (verified live: 2 books with author)); *owner marked* (`@JoinColumn({ name })` on M-1/1-1 owner (FK column named explicitly — strategy-independent); *actions stated* (`onDelete: "CASCADE"` for contained children (verified live — books cascade-saved via `{ cascade: true }` on OneToMany + DB-level Cascade); *1-1 via unique* (Profile.studentId unique + JoinColumn (one-to-one enforced — second profile rejected structurally). Missing part → request changes; defaulted action → classify explicitly (defaults are decisions made by absence — absence unreviewed).

```typescript
// GOOD: relations declared both sides, owner marked, actions stated (verified live on dbprobe).
@OneToMany(() => Book, (b) => b.author, { cascade: true })  // collection side (cascade: persist children with parent)
books!: Book[];

@ManyToOne(() => Author, (a) => a.books, { onDelete: "CASCADE" })  // reference side (owner below)
@JoinColumn({ name: "authorId" })   // owner marked (FK column named explicitly — strategy-independent)
author!: Author;
// Live: authors.save({ name, books: [{...},{...}] }) → 1-N books: 2 (cascade save verified).
// Live: authors.find({ relations: { books: true } }) → navigable both ways (verified).
```

```typescript
// BAD: half-declared relations — columns paired, associations absent (real failure shapes).
// @OneToMany(() => Book, (b) => b.author)
// books!: Book[];   // no cascade (nested saves failing — children persisted separately (piecemeal,
// // partial graphs on failure); no back-reference navigability tested (reverse traversal assumed).
// // @JoinColumn omitted (owner by convention — naming strategy drifting per environment).
// // onDelete defaulted (NO ACTION — deleting authors fails live — runtime surprise scheduled).
// Columns paired; relations undeclared; actions defaulted. Pairing isn't associating.
```

**Common confusion** — *"cascade: true and onDelete CASCADE are the same thing."* Different layers (cascade option = ORM-level (children persisted/removed via repository operations — application-driven, transaction-scoped); onDelete = DB-level (FK constraint action — engine-enforced, all writers including raw SQL/backfills/consoles). ORM cascade without DB action orphans on non-ORM writers (backfill deletes bypassing repositories — children stranded); DB action without ORM cascade surprises repository flows (children vanishing outside unit-of-work tracking — stale entities referencing deleted rows). Both stated where both writers exist (application + non-application paths — belt and suspenders, deliberately); either alone where single-writer (judged per relationship, recorded). Layers differ; state both; confuse never.

**Performance note** — relation-declaration economics: cascade saves batch children per parent (verified live — one save call persisting graph — round trips minimized); relations includes batch reads (one query per path — N+1 structurally preventable — [3.1](<../3. Loading and performance/3.1. Loading strategies and N+1.md>) performs); undeclared relations cost hand-queries per traversal (raw SQL escaping for routine navigation — mapper ceremony paid, graph convenience declined). Declaration lines free at runtime (metadata, not queries); traversal strategies priced per read (includes stated, counts asserted). Declare completely; strategize per query.

**Mentor note** — teach "both sides + owner + action" as the relation mantra (juniors reciting per association internalize completeness before speed — mantra first, fluency follows — twin of Prisma 02/1.2's mantra, class-flavored). Review relations by checklist (four parts present? action stated? 1-1 unique? cascade layered correctly (ORM vs DB distinguished)?). Mantra memorized; checklist enforced; relations complete — three verbs, zero half-declared associations.

## 2. JoinColumn owns the FK side (owner side holds the key — actions stated per owner)

**Definition** — ownership semantics: `@JoinColumn` marks the relation owner (the side holding the FK column — ManyToOne always (FK natural there); OneToOne either side (chosen — unique FK placed deliberately); OneToMany never (inverse side — mappedBy equivalent, keyless). Owner holds three responsibilities (FK column named (`@JoinColumn({ name })` — explicit, strategy-independent); delete action stated (`onDelete` on owner's relation — engine enforces); nullable decided (optional relations nullable FK — presence contracted). Non-owner references (`mappedBy`-style inverse — navigation only, no key, no action — traversal without ownership).

**What problem it solves** — the ownerless relation (JoinColumn omitted both sides (FK placed by convention — naming strategy dependent (environments disagreeing — staging vs production column names diverging silently); delete actions floating (neither side stating — NO ACTION default answering at runtime — surprises scheduled); nullable unconsidered (optional links non-nullable — legitimate absences rejected (guest checkouts blocked — business states forbidden by schema accident). Ownership stated converts convention to contract (named columns, stated actions, decided nullability — reviewed per relation, never defaulted). Convention serves prototypes (speed); contracts serve production (correctness) — graduate explicitly, never accidentally.

**Modern guidance** — the ownership lines per relation (review-enforced): *owner named* (`@JoinColumn` on M-1/chosen 1-1 side (FK column explicit — `authorId`, never strategy-derived); *action stated* (onDelete per owner relation — Cascade (contained), Restrict/NoAction (history), SetNull (optional) — [Database Design §4.1](<../../../DatabaseDesign/04 Relationships at Scale/sections/1. Foreign keys at volume/1.1. Foreign keys that survive traffic.md>)'s both-lenses rule applied through decorators); *nullable decided* (optional `@ManyToOne({ nullable: true })` — absence legitimate (guest orders); mandatory default non-nullable (presence contracted); *bidirectional navigability tested* (both directions traversed in integration tests — untested directions assumed working (assumption failing at 3 a.m. — traversal errors in production paths). Missing line → request changes; convention trusted → classify explicitly (conventions documented where kept, never inherited blindly).

```typescript
// GOOD: ownership stated — owner marked, action classified, nullability decided (verified live shapes).
@ManyToOne(() => Author, (a) => a.books, { onDelete: "CASCADE", nullable: false })
@JoinColumn({ name: "authorId" })   // owner: Book holds FK (named explicitly — strategy-independent)
author!: Author;                    // action: CASCADE (lines meaningless without orders — domain lens)
// nullable: false default (every line belongs to an order — presence contracted — guest lines nonexistent)
// Bidirectional test: author→books AND book→author traversed (both verified live — navigation proven).
```

```typescript
// BAD: ownerless relations — convention trusted, actions floating, nullability accidental.
// @ManyToOne(() => Author, (a) => a.books)
// author!: Author;   // JoinColumn omitted (FK named by strategy — environments disagreeing silently;
// // author_id vs authorId drift discovered per environment (migrations differing — archaeology).
// // onDelete absent (NO ACTION default — author deletes failing live — surprise scheduled).
// // nullable unconsidered (guest orders blocked — business states forbidden by schema accident).
// Convention trusted; contracts absent; surprises scheduled. Ownership stated or ownership hoped.
```

**Common confusion** — *`@JoinColumn` is optional boilerplate (convention suffices).* Conventions suffice where environments agree (single-database prototypes — strategy stable, drift absent); contracts required where they diverge (multi-environment pipelines — naming strategies differing per config (camel vs snake — drift silent); multi-writer systems (raw SQL alongside repositories — convention unknown to raw writers — FK names guessed). "Optional" describes prototypes (speed valued, drift absent); production requires explicitness (contracts surviving environments, writers, and time). Prototype with conventions (fast); produce with contracts (correct) — graduate the JoinColumn with the feature, never after the incident.

**Performance note** — ownership economics: explicit FK names cost lines (decorator options — zero runtime); convention drift costs archaeology (environment-divergent columns — migrations differing — forensics hourly-billed); stated actions cost thought (policy per relation — minutes, once); defaulted actions cost incidents (NO ACTION surprises — support tickets per delete-blocked user). Review minutes per relation (owner/action/nullable stated); quarters avoided per incident class (drift/surprise/blocked-states). State ownership; price actions; decide nullability.

**Mentor note** — teach "who holds the key?" per relation (juniors answering instantly design ownership deliberately; hesitation locates convention-trust (unexamined defaults — sent back to state explicitly). The question generalizes (every association in every mapper answers it — Prisma scalar lists, Drizzle references, raw FKs — ownership universal, syntax local). Ask per relation; state per schema; review per PR — ownership thinking in three habits, reviewed always.

## 3. Join tables explicit when growing (implicit @JoinTable vs entity junctions)

**Definition** — the two m-n shapes, TypeORM-flavored (verified live below): **implicit** (`@ManyToMany` + `@JoinTable({ name })` on one side (owner) — framework-managed junction (columns camelCased per convention — verified live: `tStudentId, tCourseId` (metadata-probed, not guessed — convention discovered, never assumed); **explicit** (junction entity with `@ManyToOne` × 2 + `@PrimaryColumn` composite or surrogate PK + attribute columns (grade, enrolledAt — membership-scoped). Implicit serves pure links (membership without metadata — zero ceremony); explicit serves attributed links (growth accommodated — [Database Design §4.2](<../../../DatabaseDesign/04 Relationships at Scale/sections/2. Many-to-many and polymorphism/2.1. Junction tables at scale.md>)'s law: junctions grow attributes, always).

**What problem it solves** — the implicit trap, TypeORM edition (verified live mechanics: implicit junction columns convention-named (`tStudentId` — undiscoverable without metadata probing — raw SQL against junctions guessing names (wrong guesses failing — convention opacity billing per raw query); attributes arriving homeless (grade/enrolledAt with no entity — JSON blobs, parallel tables, or implicit→explicit migration under traffic (data moved invisible→visible, readers switched — quarters of ceremony for lines saved). Explicit-by-default avoids the trap (attributes landing on existing entities — zero migration); implicit justified per case (pure links with trigger ("attributes arriving → explicit migration, priced now") — purity with exit plan, never bare assertion).

**Modern guidance** — default explicit where links *might* grow attributes (enrollments, memberships, assignments — business relationships accumulating metadata within years — virtually all); permit implicit where links credibly pure (tag assignments with trigger agreed — purity with exit plan). Implicit checklist (verified live): `@JoinTable({ name })` on owner side only (one owner — dual `@JoinTable` duplicating junctions — reviewed); junction columns probed from metadata (never guessed — `tStudentId` discovered via metadata, not assumed — raw SQL against junctions verified against probe); reverse index considered (both traversal directions — Database Design 04 rule through decorators — `@Index` where missing). Explicit checklist: composite PK (`@PrimaryColumn` × 2 or `@@id`-equivalent — link invariant); attributes membership-scoped (grade/enrolledAt — 2NF-clean); both relations with Cascade (orphan links dying with endpoints).

```typescript
// GOOD: implicit verified + explicit prescribed (verified live: connect + include passing).
@ManyToMany(() => Course, (c) => c.students)
@JoinTable({ name: "t_enroll" })   // owner side only (dual JoinTable duplicates junctions — reviewed)
courses!: Course[];
// Live: courses.save({ title, students: [s] }) + students.find({ relations: { courses: true } })
// → implicit m-n courses: 1 (verified). Junction columns probed: tStudentId, tCourseId (metadata —
// never guessed — raw SQL against junctions verified against probe, not convention-memory).
// Explicit when growing: Enrollment entity (composite PK + grade + enrolledAt — attributes landable).
```

```typescript
// BAD: implicit assumed + columns guessed — convention trusted twice over.
// @ManyToMany(() => Course) courses!: Course[];  // @JoinTable omitted (junction auto-named —
// environments agreeing hopefully); back-reference omitted (reverse traversal unservable).
// Raw SQL against junction: WHERE "t_studentId" = ... (guessed snake_case — verified live FAILURE:
// column "tStudentId" of relation "t_enroll" does not exist (actual camelCase — guess wrong —
// production error wearing convention-confidence). Attributes arriving homeless (no entity —
// migration under traffic). Guessed twice (names + growth); wrong twice. Probe metadata; place explicit.
```

**Common confusion** — *"implicit junctions can't be queried (limitation)."* Implicit junctions query via relations (find with relations option — traversal served — verified live: include-equivalent working); raw SQL against them needs probed names (metadata-discovered `tStudentId` — guessable never, probeable always); attribute queries need explicit migration (grade unqueryable on pure links — by design (attributes homeless by shape — migrate to explicit, priced). "Can't" describes attributes (true — shape lacks fields) and guessed raw SQL (true — convention opacity); relations traverse fine (verified live). Traverse via relations; probe before raw; migrate for attributes.

**Performance note** — junction economics: implicit junctions (framework-managed — indexed by convention — traversal both ways served opaquely); explicit entities (composite PK + reverse indexes per Database Design 04 — both directions point-fast, attributes covering); probed names enabling raw access (metadata-discovered columns — raw queries correct first time — guess-and-fail cycles eliminated). Query shapes identical at runtime (joins through link tables either way — planner indifferent); migration cost differs totally (implicit→explicit under traffic vs explicit from birth — quarters vs zero). Probe metadata; place explicitly; migrate never.

**Mentor note** — teach "probe, don't guess" with the live failure (verified this session: `t_studentId` guessed → error naming actual `tStudentId` — convention discovered via failure, cheap in staging (minutes), dear in production (pages). Metadata-probing demonstrated once (junction columns listed from metadata — convention visible, guesswork ended); explicit-default adopted (attributes landable — migrations never). Probe metadata; default explicit; guess never — junction discipline in three habits, reviewed per m-n.
