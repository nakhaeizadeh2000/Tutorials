# 3.1. Loading strategies and N+1

## 1. Eager versus lazy decided per relation (eager always loads — priced; lazy loads on access)

**Definition** — the loading choice: **eager** (`eager: true` on the relation — loaded with every find, no `relations` option needed — convenience priced per query (relations fetched whether needed or not — transfer overhead on every read); **lazy** (`lazy: true` — relations as `Promise<Book[]>` — loaded on awaited access (per-access statements — N+1 by default where traversed in loops — magic billing per touch); **explicit** (neither flag — `relations: { books: true }` per query (verified live below — relation loaded on demand, per-query decision — the default this track prescribes). Eager/lazy/explicit chosen per relation (not globally — different relations different access patterns — one default for all relations is strategy abdication).

**What problem it solves** — the loading-default duo: *eager-everywhere* (relations marked eager "for convenience" — every query fetching full graphs (list pages transferring megabytes per render — transfer billed per read, unexamined); *lazy-everywhere* (relations lazy by habit — traversals issuing per-access statements (N+1 wearing `await` — magic billing per touch — loops over lazy relations firing thousands of queries, discovered at scale). Explicit-per-query converts both (relations loaded where needed (includes stated — transfer intentional); unloaded elsewhere (properties absent — compile-time visible, not runtime-slow). Defaults decided per relation (hot paths eager-or-explicit, cold paths unloaded — strategy, never hope).

**Modern guidance** — the loading lines per relation (review-enforced): *explicit default* (neither eager nor lazy — `relations: {...}` per query (verified live — bare find excludes (properties absent — `bs present: false` verified); relations option includes (verified live — 2 books loaded); *eager where hot* (relations traversed in >80% of reads (parent-with-children screens — eager priced (transfer per read, measured) — eager justified by frequency, never convenience); *lazy almost never* (per-access statements — N+1 structural (loops over lazy relations firing per element — magic billing per touch — lazy justified only where single-entity traversals dominate AND counts asserted (rare — documented per relation with reason); *counts asserted* (statement bounds per list test — [Domain 01 §4.1](<../../../01 Data Access Foundations and Mental Model/sections/4. Mentor checklist/4.1. Data-access checklist mentors insist on.md>)'s detector enforced from adoption — N+1 failing builds regardless of strategy). Missing strategy → request changes; global defaults → per-relation decisions (one default for all relations fails review structurally).

```typescript
// GOOD: explicit per query — unloaded by default, batched on demand (verified live on dbprobe).
const bare = await repo.find();   // no relations option → bs absent (verified: present false —
  // compile-time visible (property undefined — unstrategized access impossible, not merely slow).
const withRels = await repo.find({ relations: { bs: true } });   // explicit per query
// (verified live: bs count 2 — one batched read — strategy performed, N+1 structurally absent).
```

```typescript
// BAD: eager-everywhere or lazy-everywhere — defaults substituting for strategy (real shapes).
// @OneToMany(() => Book, (b) => b.a, { eager: true })  // eager default (every author query
// fetching books (list pages transferring full graphs per render — transfer billed per read,
// unexamined — convenience priced quarterly). Or: { lazy: true } (traversals awaiting per access —
// for (const a of authors) await a.bs (N+1 wearing await — magic billing per touch — loops firing
// thousands, discovered at scale). Defaults decided globally; strategies absent locally.
// Eager bills transfer; lazy bills statements; explicit bills neither (decided per query).
```

**Common confusion** — *"eager loading prevents N+1 (always include everything)."* Eager prevents N+1 *statements* (relations batched — constant queries) while causing transfer bloat (full graphs per read — megabytes per list render — the cost merely moved from statement-count to bytes-shipped). "Prevents N+1" answers the statement question (true — batched); transfer unexamined (bloated — same unexamined strategy, different bill). Eager trades statements for bytes — profitable where relations needed per read (hot paths), wasteful where not (cold traversals fetched hotly). Price both axes (statements AND bytes — transfer measured per hot path, not hoped); strategize per relation (hot eager-or-explicit, cold unloaded).

**Performance note** — loading economics: explicit includes cost one query per path (batched — constant statements regardless of N — N+1 immunity structural); eager costs transfer per read (relations fetched whether needed or not — bytes billed per render — measured per hot path); lazy costs statements per access (N+1 structural — magic billing per touch — loops catastrophic). Unstrategized equivalents cost linear latencies (lazy loops at scale — quarters of remediation) or bloated transfers (eager graphs per list — bandwidth billed per render). State strategies; assert counts; measure transfer — three bounds, complete read performance.

**Mentor note** — teach "strategy per relation" (juniors stating eager/lazy/explicit per relation design bounded reads on first hearing; unstated strategies interrogated ("which relations load here, and why these?" — strategy demanded per query). Demonstrate bare-vs-included live once (properties absent vs batched — verified live pattern above (false vs 2) — compile-time absence vs one-round-trip presence — tangibility converting permanently). State strategies; demonstrate live; assert always — read performance in three habits, reviewed per PR.

## 2. Relations option batches reads (find with relations — explicit per query, counted per test)

**Definition** — the batching rule performed TypeORM-specifically (general rule in [Domain 01 §4.1](<../../../01 Data Access Foundations and Mental Model/sections/4. Mentor checklist/4.1. Data-access checklist mentors insist on.md>), Prisma twin in [Domain 02 §2.2](<../../../02 Prisma Deep Dive/sections/2. Migrations and client/2.2. Client queries and relations.md>)): `find({ relations: { bs: true } })` batches relation reads (verified live — 2 books in the batched read); nested relations composed (`relations: { books: { author: true } }` — multi-level batching per path — depth priced per level (each level a join/batch — depth examined, never hoped); counts asserted per list test (statement bounds — N+1 failing builds — detector enforced from adoption). Relations batched declaratively (option stated — framework joining); hand loops rejected (per-parent finds — N+1 wearing repository syntax — batching declined where available).

**What problem it solves** — the unbatched traversal (per-parent `findOneBy` loops beside repositories (N+1 wearing repository syntax — batching available, declined — loops visible but uncounted ("only a few" growing unboundedly); relation-less finds followed by manual assembly (parents fetched, children fetched separately per parent (two queries becoming N+1 by loop — assembly code per feature, mapping bugs per relation); over-relations (everything included "just in case" — transfer bloat + multi-relation fan-out ([Database Design §4.3](<../../../../DatabaseDesign/04 Relationships at Scale/sections/3. Skew and hot relationships/3.1. Hot keys and skew.md>)) — cartesian products on dual list-relations (statements few, rows multiplied — sums fictionalized downstream). Batched-declared converts first two (loops → relations option — constant statements); projected restrained converts third (select trimming — transfer bounded).

**Modern guidance** — the batching lines per relation read (review-enforced): *relations stated* (`relations: {...}` per read — verified live pattern (bs count 2 — batched); *nested composed deliberately* (multi-level relations priced per level (joins multiplying — depth examined (2 levels typical max — deeper nesting split into separate batched queries (fan-out controlled); *counts asserted* (statement bounds per list test — ≤N derived from shape — N+1 failing builds (asserted, not hoped); *transfer trimmed* (select/partial where wide rows travel (columns projected — unneeded payload unfetched — transfer intentional). Missing relations-option where loops exist → request changes (batching declined — loops rewritten to relations); unexamined nesting → depth priced (levels counted, fan-out checked).

```typescript
// GOOD: relations batched declaratively — constant statements, counted tests (verified live).
const withRels = await repo.find({ relations: { bs: true } });   // batched (verified live: 2 books)
// Test: statement counts asserted per list (≤N bounds — N+1 fails builds — 01/4.1 detector).
// Nested deliberately: relations: { books: { author: true } } (2 levels — priced per level;
// deeper split into separate batched queries (fan-out controlled — Database Design 04 rule).
```

```typescript
// BAD: unbatched loops beside repositories — batching available, declined (real shapes).
// const authors = await repo.find();  // no relations (unloaded — deliberately? unasked?)
// for (const a of authors) {  // loop forming (per-parent books query next — N+1 in repository syntax —
//   a.books = await bookRepo.find({ where: { author: { id: a.id } } });  // batching declined (relations
//   // option unused — loops visible but uncounted ("only a few" growing unboundedly — staging's ten rows
//   // hiding production's ten thousand). Counts unasserted (tests green on fixtures — linear in production).
//   // Or the mirror: relations: { books: true, orders: true, events: true } (lists multiplying — fan-out
//   // transfer — 50× rows shipped). Unbatched loops; unexamined nesting. Neither priced.
// }
```

**Common confusion** — *"relations option always prevents N+1 (batching magic)."* Relations batch *declared* paths (verified live — one batched read); hand loops bypass batching (per-parent repository calls — N+1 fully manual — framework unable to help undeclared traversals); nested multi-list relations multiply transfer (batched statements, combinatorial rows — N+1 absent, fan-out present — different failure, same unexamined strategy). "Always prevents" credits batching with loop prevention (loops unbatched by definition — authorial) and fan-out immunity (transfer unexamined — multiplicative). Batching declared; loops counted; fan-out split — all three, always (same verdict as Prisma 02/2.2 — restated TypeORM-flavored, permanently).

**Performance note** — relations-batch economics: declared relations cost one query per path (batched — constant statements regardless of N — N+1 immunity structural, verified live); hand loops cost N statements (linear — latency scaling with data — batching declined); nested multi-list costs combinatorial transfer (statements few, rows multiplied — transfer dominating — split per Database Design 04). Statements bounded via relations; transfer bounded via select/split; counts asserted via tests — three bounds, complete read performance (same triple as Prisma 02/2.2 — restated, enforced identically).

**Mentor note** — teach "relations option, not loops" (juniors batching via relations option design bounded reads on first hearing; loop authors interrogated ("batchable via relations?" — batching demanded where available). Demonstrate bare-vs-batched live once (absent vs 2-books-batched — verified live pattern (false vs 2) — tangibility converting permanently). Batch declaratively; count always; split fans — read performance in three habits, reviewed per PR.

## 3. QueryBuilder for the unmappable (composed SQL with types — escape fenced, logged)

**Definition** — the escape discipline, TypeORM-flavored (Prisma twin in [Domain 02 §3.1](<../../../02 Prisma Deep Dive/sections/3. Performance discipline/3.1. N+1 strategies and raw escapes.md>)): `createQueryBuilder(alias)` composing SQL programmatically (verified live below — leftJoinAndSelect with where-parameterized — 2 books joined); entities returned typed (`.getMany()` mapping to entity classes — decorators applying to composed results — types complete, never `any`); raw SQL via `.where()`/`.select()` fragments only where combinators stop (recursive CTEs, window analytics — fragments fenced (reasoned, logged — escape discipline from 02/3.1 applied through builder). Builders bridge repositories and raw (composed queries with entity mapping — middle jurisdiction honored, both extremes declined where middle serves).

**What problem it solves** — the expressiveness duo: *repository-insufficient queries* (complex joins/aggregations/subqueries beyond find options (find API covering CRUD + relations — analytics/grouping/having unserved — hand loops assembling what one composed query serves (N+1 assembling aggregations — loops where joins belong); and *raw-string relapse* (QueryBuilder abandoned for string SQL ("more control" — concatenation per branch — injection per interpolation — types unmapped (raw rows any-shaped — refactors breaking at runtime). QueryBuilder composes the middle (joins/aggregates/subqueries typed — expressiveness without strings; raw fragments fenced for the genuinely unmappable (recursion, windows — reasoned, logged). Middle honored; extremes declined where middle serves.

**Modern guidance** — the builder lines per complex query (review-enforced — verified live shapes): *compose over loop* (joins via leftJoinAndSelect (verified live: 2 books joined — one query — loops declined where joins serve); *parameterize always* (`.where("a.name = :n", { n })` — bound parameters (verified live pattern — injection closed structurally per branch); *map to entities* (`.getMany()` returning entity classes — decorators applying (types complete — raw rows never any-shaped); *fence raw fragments* (unmappable remainders via raw SQL pieces (reasoned per fragment — "recursive CTE beyond combinators" — logged like all SQL — escape discipline from 02/3.1 applied); *log everything* (query logging on in dev/test — composed statements visible per render — surprises pre-merge). Missing composition where joins serve → request changes (loops rewritten to joins); raw unfenced → reason/type/log demanded.

```typescript
// GOOD: builder composed — joined, parameterized, entity-mapped (verified live on dbprobe).
const qb = await repo.createQueryBuilder("a")
  .leftJoinAndSelect("a.bs", "b")              // join composed (verified live: 2 books joined)
  .where("a.name = :n", { n: "a1" })           // parameterized (bound — injection closed per branch)
  .getMany();                                  // entity-mapped (decorators applying — types complete)
// One query (joined — loops declined); parameters bound (injection closed); entities returned (typed).
```

```typescript
// BAD: loops where joins serve + strings where builders serve (extremes, both wrong).
// const authors = await repo.find();  // unloaded (deliberately? unasked?)
// for (const a of authors) a.books = await bookRepo.find({ where: { author: { id: a.id } } });
// (N+1 assembling what one join serves — loops where joins belong — batching declined.)
// Or: await ds.query(`SELECT * FROM t_a a JOIN t_b b ON b."aId" = a.id WHERE a.name = '${n}'`);
// (string relapse — interpolation per branch (injection); any-rows (refactors breaking); unlogged
// (dark SQL — budgets blind). Builder middle declined both ways — loops left, strings right.)
```

**Common confusion** — *"QueryBuilder is just raw SQL with extra steps."* Builders compose *typed* queries (entity-mapped results (decorators applying — types complete); parameterized branches (injection closed structurally); logged statements (visible per render — surprises pre-merge). Raw strings carry none of these (any-rows, interpolated branches, dark SQL — three absences billing quarterly). "Extra steps" framing counts builder lines while ignoring type/safety/visibility delivered (lines buying guarantees — cheapest lines in data-access code). Steps purchasing guarantees; strings purchasing risk. Compose typed; concatenate never (raw reserved for the genuinely unmappable — fenced, reasoned, logged).

**Performance note** — builder economics: composed joins cost one query (vs N+1 loops — latency divided by batching, locks brief); parameterized branches cost planning stability (bound parameters — plan reuse — interpolated strings replanning per value (parse overhead per distinct string — plan cache defeating); entity mapping costs CPU per row (negligible beside I/O — same as all mapping work). Loops cost linear statements (latency scaling with data); strings cost replans + risk (parse overhead + injection surface). Compose joins; bind parameters; map entities — builder performance complete, permanently.

**Mentor note** — teach "joins over loops" with live counts (verified live pattern above (1 query joined vs 1+N looped — counted, not theorized — tangibility converting permanently); builder composition as loop replacement (loops rewritten to joins live in review — batching demonstrated, not described). Count statements; compose joins; fence remainder — builder fluency in three habits, reviewed per complex query. Joins composed; loops eliminated; strings fenced.
