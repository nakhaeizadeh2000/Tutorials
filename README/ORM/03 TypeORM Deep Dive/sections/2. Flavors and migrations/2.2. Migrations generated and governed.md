# 2.2. Migrations generated and governed

## 1. Generate, never hand-write first (migration:generate diffs metadata vs database)

**Definition** — the generation flow: `typeorm migration:generate` diffs entity metadata against the live database and writes a timestamped migration class (`up`/`down` with raw SQL — verified live below: `CREATE TABLE "torm_users" (... BIGSERIAL ... UQ_... UNIQUE ... PK_...)` rendered without touching anything until run). Generate-first means diffs authored by tooling (complete — every metadata/database delta captured, including ones humans forget (dropped columns, altered lengths, missing indexes); hand-edits layered after (data migrations, phased constraints, backfills — human judgment augmenting generated structure, never replacing it).

**What problem it solves** — the hand-written drift (migrations authored from memory (columns forgotten (nullable mismatches — runtime errors on deploy); indexes omitted (parent writes scanning — FK discipline unapplied through hand SQL); down-migrations missing (rollback impossible — forward-only history, incidents unrecoverable without backup surgery). Generated diffs capture completely (metadata-compared — every delta present, up AND down rendered); hand-augmentation handles judgment (data moves, phased constraints, expand/contract steps — humans adding what diffs can't infer (intent — backfill values, phase sequencing, witness evidence). Generate completely; augment judiciously; hand-write never-first (greenfield DDL from memory is archaeology scheduled).

**Modern guidance** — the generation lines (verified live shapes on TypeORM 1.1.1): *diff against owned dev databases* (drifted/shared DBs generating fiction diffs (unrelated tables' drift attributed to your entities — generate on owned dev DBs, never shared — same protection logic as Prisma's reset-refusal ([Domain 02 §2.1](<../../02 Prisma Deep Dive/sections/2. Migrations and client/2.1. Migrate tooling that stays honest.md>))); *read generated SQL fully* (up/down both (BIGSERIAL ids visible, UQ/PK constraint names recorded, down-migration present — review completeness enforced — generated never auto-approved); *augment for intent* (data migrations appended (backfills chunked — [Database Design §5.1](<../../../DatabaseDesign/05 Evolution Growth and Partitioning/sections/1. Schema evolution/1.1. Expand and contract migrations.md>)'s batching); phased constraints (NOT VALID then VALIDATE — expand discipline through tooling); *output pathed deliberately* (`-o` directory explicit — generated files landing in reviewed locations (migrations dirs committed, never temp) — path lesson verified live below (run resolving migrations from configured directories — misplaced files silently unapplied ("no migrations pending" while files exist elsewhere — path discipline, not tooling bug)).

```javascript
// GOOD: generated migration reviewed fully (verified live: TypeORM 1.1.1 generate output).
module.exports = class Migs1790831370289 {
    name = 'Migs1790831370289'
    async up(queryRunner) {
        await queryRunner.query(`CREATE TABLE "torm_users" ("id" BIGSERIAL NOT NULL,
          "email" character varying NOT NULL,
          CONSTRAINT "UQ_f5e2d702cb40bcf0859eafceb2d" UNIQUE ("email"),
          CONSTRAINT "PK_d72aa3017cf52b1b44feb191e2c" PRIMARY KEY ("id"))`);
    }   // BIGSERIAL ids visible; UQ/PK constraints named (reviewed — enforcement intended)
    async down(queryRunner) {
        await queryRunner.query(`DROP TABLE "torm_users"`);
    }   // down-migration present (rollback possible — reversibility designed, not hoped)
}
```

```javascript
// BAD: hand-written-first migrations — memory-authored, drift-scheduled (real shapes).
// await queryRunner.query(`CREATE TABLE torm_users (id SERIAL PRIMARY KEY, email TEXT)`);
// (UNIQUE forgotten (duplicates accumulating — cleaned quarterly); down-migration missing
// (rollback impossible — forward-only history); BIGSERIAL-vs-SERIAL unexamined (2B cap
// scheduled silently); createdAt absent (temporal questions unanswerable). Memory-authored;
// drift-scheduled; reversibility absent. Generate completely; augment judiciously.)
```

**Common confusion** — *"generated migrations need no review (tooling is correct)."* Generation is *complete*, not *correct-by-intent* (diffs capture structural deltas faithfully — renames as drop+create (history loss wearing generation); flag-day nullability (breaking shipped as additive); missing FK indexes (discipline unapplied through diffs). "Correct" describes mechanics (valid SQL, ordered application — trustworthy); intent requires review (phases classified, renames declared, indexes verified — human, contextual). Complete generation + intent review (mechanics automated, judgments human); neither alone suffices (complete-but-unreviewed ships flag-days; reviewed-but-hand-written misses deltas). Generate; review fully; augment intentionally.

**Performance note** — generation economics: diff rendering costs seconds (metadata compared — complete deltas, up+down rendered); review costs minutes per migration (phases/witnesses/indexes checked); hand-authoring costs deltas missed (forgotten columns/indexes/downs — incidents per omission — quarters of archaeology untangling drifted history). Generated-then-reviewed is cheaper *and* more complete than hand-written (seconds + minutes vs hours + omissions). Generate always first; hand-augment for intent; review everything.

**Mentor note** — teach "generate, read, augment" (juniors generating then *reading* diffs line-by-line discover generators' assumptions permanently (drop+create renames, flag-day nullability, missing indexes — generated code reviewed like hand code, always). Demonstrate path discipline once (`-o` misplaced → "no migrations pending" with files existing — path lesson learned via confusion resolved, never repeated). Generate completely; read fully; augment intentionally — migration literacy in three habits, reviewed per schema PR.

## 2. Run pending, revert deliberately (migration:run/show/revert — history replayed, repairs recorded)

**Definition** — the execution discipline: `migration:show` reports state read-only (applied vs pending — verified live: "No migrations are pending" — state observed, never mutated); `migration:run` applies pending in order, tracked (bookkeeping table created on first run — verified live: `migrations` tracking table mechanics observed); `migration:revert` undoes last applied (down-migration executed — reversibility designed per migration, not hoped per incident). History replayed (run), reported (show), reversed (revert) — three verbs, complete lifecycle, repairs recorded (failures resolved through recorded procedures — [Domain 02 §2.1](<../../02 Prisma Deep Dive/sections/2. Migrations and client/2.1. Migrate tooling that stays honest.md>)'s honesty procedures, TypeORM-flavored).

**What problem it solves** — the execution trio: *unreported runs* (migrations applied blindly (pending unknown — already-applied re-run (duplicate-object failures) or missing skipped (history ahead of reality — cascading failures); *untracked history* (no bookkeeping consulted (which ran where? — environments diverging silently — staging ≠ production structurally — bugs environmental, undiagnosable); *irreversible migrations* (down-migrations absent (rollback impossible — forward-only history — incidents unrecoverable without backup surgery (hours + interim-write loss). Show-before-run (state known), tracked runs (history recorded), down-migrations present (reversibility designed) convert all three (known state, recorded history, possible rollback — execution governed end-to-end).

**Modern guidance** — the execution lines (verified live behaviors): *show first* (`migration:show` read-only (pending vs applied enumerated — expected pendings matching release (drift failing gate — unexpected pendings investigated, never waved); *run pending* (`migration:run` applying in configured directory (path lesson verified live: misplaced files → "no pending" while files exist elsewhere — migrationsDir configured deliberately, files committed there — run resolving what review approved, nothing else); *revert deliberately* (`migration:revert` executing down (reversibility per migration — downs reviewed like ups (destructive downs witnessed — data-destroying reversals gated, never casual); *track always* (`migrations` bookkeeping consulted (history recorded per environment — applied state queryable — drift between environments detectable via show diffs). Missing step → request changes/block deploys; history bypassed → fiction institutionalized (console DDL instead of run — divergence archaeology scheduled).

```javascript
// GOOD: execution governed — shown, run pending, reverted deliberately, tracked always.
// $ show (read-only — pendings enumerated: expected match release ✓ — drift absent).
// $ run (pending applied in order — bookkeeping recorded (migrations table observed live ✓).
// $ revert (down executed deliberately — reversibility designed per migration ✓).
// Tracking consulted (applied state per environment — environments agreeing structurally).
// Verdict: approve execution.
```

```javascript
// BAD: execution hoped — unreported runs, untracked history, irreversible migrations.
// $ run (pendings unknown — already-applied re-running (duplicate failures) or missing skipped
// (history ahead of reality — cascading). Tracking unconsulted (which ran where? — environments
// diverging silently — staging ≠ production structurally). Down-migrations absent (rollback
// impossible — forward-only history — incidents unrecoverable without backup surgery).
// Console DDL instead (history bypassed — fiction institutionalized — divergence archaeology
// scheduled quarterly). Hoped per environment; fictional across them.
```

**Common confusion** — *"revert is for development only (production moves forward)."* Revert covers *migration-level* rollback (bad migration caught pre-data (down executed — clean reversal — correct tool); production incidents usually need *forward fixes* (new migration correcting — history append-only (past unaltered — ledger integrity, same as Prisma resolve discipline ([Domain 02 §2.1](<../../02 Prisma Deep Dive/sections/2. Migrations and client/2.1. Migrate tooling that stays honest.md>))). "Forward-only production" is correct *policy* (rollbacks via new migrations — history honest); revert remains correct *tooling* (staging/dev reversal, failed-deploy recovery pre-data — contexts where down-migrations shine). Policy forward (production — new migrations correcting); tooling complete (revert available, reviewed, tested) — policy and tooling distinct, both owned.

**Performance note** — execution economics: show costs seconds (read-only state — cheapest deployment gate available); run costs per-migration seconds (bounded, predictable — migrations small by review discipline); revert costs down-migration design (reversibility per migration — authored once, available forever); ungoverned equivalents cost duplicate-object failures (blind reruns), environment divergence (untracked histories — archaeology quarters), unrecoverable incidents (missing downs — backup surgery with interim loss). Governed execution performs boringly (same steps, same order — boring deploys successful); hoped execution performs dramatically (each unique — drama billed in pages).

**Mentor note** — teach "show before run" (juniors checking state before applying internalize governed execution permanently — state known, history recorded, reversibility available — three properties verified per migration run). Demonstrate path lesson once (misplaced files → "no pending" confusion resolved — migrationsDir configured deliberately thereafter). State known; runs tracked; reversals designed — execution governed end-to-end, reviewed per deploy.

## 3. synchronize stays in development (auto-sync forbidden past dev — linted, never hoped)

**Definition** — the prohibition: `synchronize: true` (auto-mutating schema from entities on connection — convenient in development (prototyping velocity — schema following code without migration files); forbidden past development (production/staging/shared — auto-mutation executing unreviewed DDL per deploy (typo'd decorators dropping columns (data loss wearing convenience); concurrent deploys racing schema writes (lock contention + partial application); drift untracked (no history — applied states unrecorded — reproducibility void). Prohibition enforced structurally (CI fails on `synchronize: true` outside dev configs — linted, never hoped — grep-verified per pipeline); exceptions none (zero legitimate production uses — every case served better by reviewed migrations (emergencies included — emergency migrations reviewed fast, never bypassed).

**What problem it solves** — the auto-mutation trio: *typo-driven data loss* (`@Column({ name: "emial" })` — synchronize dropping `email`, creating `emial` (data stranded in dropped column — production data loss via typo — review absent by design (no migration file to read — mutation invisible until queried); *concurrent-deploy races* (two deploys synchronizing simultaneously (lock contention — partial application — schema half-migrated (application expecting wholes — failures); *history void* (auto-applied states unrecorded (which schema when? — unanswerable (no ledger — environments diverging silently (staging synchronized differently than production — bugs environmental, undiagnosable). Prohibition converts all three to reviewed migrations (typos caught in diffs, deploys serialized via history, states recorded per environment).

**Modern guidance** — the prohibition lines (enforced, never hoped): *config separation* (dev config `synchronize: true` permitted (prototyping velocity — disposable databases, resettable freely); staging/prod configs `false` always (no exceptions — emergencies included (emergency migrations reviewed fast (minutes) — bypass never faster than incident quarters); *CI enforcement* (grep/lint failing builds on synchronize-true outside dev (machines tireless — humans forgetful (config drift re-enabling — caught per build, never per incident); *migration path* (every synchronize-era schema baselined into migrations before first governed deploy (history starting honest — `migration:generate` from current reality (diff captured) — reviewed fully — normal flow after). Missing enforcement → request changes (hoped prohibitions fail silently — lint or accept auto-mutation incidents explicitly (no team accepts explicitly — enforcement universal).

```typescript
// GOOD: synchronize bounded — dev velocity, prod prohibition, CI enforced.
// dev.config: { synchronize: true }   // prototyping (disposable DBs — velocity, resettable freely)
// prod.config: { synchronize: false }  // forbidden (linted — CI failing synchronize-true outside dev)
// CI: grep synchronize collapses to dev-only (machines checking — humans forgetting coverage).
// Baseline: generate from synchronize-era reality (diff captured, reviewed fully — history honest after).
// Verdict: velocity where disposable, prohibition where durable.
```

```typescript
// BAD: synchronize everywhere — convenience executing data loss (real failure shapes).
// prod.config: { synchronize: true }  // typo'd decorator dropping emails fleet-wide (data stranded —
// review absent by design (no migration file — mutation invisible until queried); concurrent deploys
// racing schema writes (locks + partial application — half-migrated production); history void
// (applied states unrecorded — staging ≠ production structurally — environmental bugs undiagnosable).
// Convenience executing; review absent; history void. Auto-mutation incidents, itemized.
```

**Common confusion** — *"synchronize: false slows development (friction)."* Synchronization accelerates *prototyping* (disposable databases — schema following code — velocity real, risks absent (nothing durable to lose); governed migrations cost minutes per change in development (generate + review + run — bounded, calm — fluency making it cheap (practiced developers migrating in minutes). "Friction" describes unpracticed flows (first migrations slow — learning curve, not process cost); practiced flows run faster than incident recovery (minutes per migration vs quarters per auto-mutation incident — full ledger favoring governance by orders of magnitude). Prototype fast (synchronize, disposable); produce governed (migrations, durable) — speed matched to stakes, always.

**Performance note** — prohibition economics: dev synchronization costs nothing durable (disposable databases — velocity free); production synchronization costs typo-driven loss (data stranded per typo — unreviewed mutations), race contention (concurrent schema writes — locks + partial states), history void (archaeology quarters untangling drifted environments). CI enforcement costs one grep per build (seconds — cheapest prohibition available); hoped prohibition costs incidents (auto-mutation surprises — quarters each). Enforce via CI; prototype freely; produce governedly.

**Mentor note** — teach "synchronize is a development toy" (juniors hearing the framing place it correctly forever (toys for disposable contexts — velocity welcome; tools for durable contexts — migrations governed). Horror story once (typo'd decorator dropping production column — real, recurring industry-wide — told with consequences (data stranded, restore surgery, interim loss) — fear correctly calibrated, permanently). Toy framing sticks (playthings stay in sandboxes — production seriousness internalized with the vocabulary). Play in dev; govern in prod; lint always.
