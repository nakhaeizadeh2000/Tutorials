## 2. Repositories for growing domains (getRepository + .extend() customs, seam explicit)

**Definition** — operating DataMapper: `DataSource.getRepository(Entity)` (verified live API present) + custom methods via `.extend({...})` (verified live: `repo.extend({ bySku })` — custom function present, round-trip passing — the 1.x replacement for removed `@EntityRepository`/`getCustomRepository` (verified absent — migration required, not optional). **What problem it solves** — AR's three exits, arrived (side effects needing homes (services calling repositories — notifications/events/billing beside persistence, never inside records); tests needing speed (in-memory fakes — suites seconds vs database-minutes — velocity compounding daily); stores multiplying (repositories bound per context — read/write splits, multi-tenant stores — mappers configured per need, entities untouched). Graduated deliberately (triggers fired → repositories adopted → exits closed structurally).

## 3. Mix deliberately, never accidentally (flavor per bounded context — documented boundaries)

**Definition** — the mixing rule: flavors chosen per bounded context (AR for trivial-lifecycle contexts (admin tools, prototypes, config surfaces); DataMapper repositories for growing ones (orders, billing, identity) — documented per context boundary (which contexts use which flavor, and why — triggers recorded per AR context (graduation scheduled); repositories standard in DM contexts (seams explicit, fakes faithful). Mixed deliberately (boundaries documented — cross-flavor entity sharing versioned cautiously); never accidentally (flavor per author per month — sediment accumulating — onboarding asking "which do we use?" — answer: documented map, not archaeology).

**What problem it solves** — the accidental mix (AR entities beside repository entities with no boundary (same context, both flavors — readers context-switching per file; upgrades touching both idioms — blast radius doubled; onboarding learning both without map ("we use both, historically" — history unexplained); and the forced uniformity (one flavor mandated codebase-wide (AR mandated — growing contexts coupling (exits firing unacknowledged); DM mandated — trivial tools ceremonied (six files where one class sufficed). Deliberate mixing rightsizes per context (ceremony where growth, simplicity where triviality); accidental mixing confuses everywhere; forced uniformity misfits somewhere (always the growing-or-trivial extreme, whichever the mandate disfavors).

**Modern guidance** — the mixing contract (review-enforced): *map flavors* (context → flavor table (admin: AR (trivial, stable); orders: DM repositories (side effects, tests, growth); billing: DM (money-moving — strictness maximal) — map reviewed quarterly (contexts evolving — flavors re-evaluated per triggers); *bound entities* (AR entities never imported into DM contexts (boundary enforced — linted where feasible (import rules — architectural boundaries, not hope); shared kernels versioned (cross-context entities referenced via versioned contracts — duplication drifting, sharing carefully); *graduate on triggers* (AR context outgrowing triggers → DM migration scheduled (expand/contract for flavor — entities decoupled from BaseEntity incrementally — migration planned, never panicked). Missing map → request changes; unmapped mixing → classify ( deliberate with boundary, or accidental sediment — sediment refactored to map, promptly).
