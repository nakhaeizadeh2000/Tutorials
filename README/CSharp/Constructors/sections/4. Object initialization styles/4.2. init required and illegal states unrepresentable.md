# 4.2. `init` accessors, `required`, and “make illegal states unrepresentable”

## Topics

1. **`init` semantics** (assignment timing, invariants, and what it does *not* guarantee)
2. **`required` members** (compile-time enforcement, versioning constraints, and runtime validation)
3. **Combining `required` + constructors/primary constructors** (choose a clear contract)
4. **Immutability strategy** (shallow vs deep immutability; `readonly`, records, frozen collections)
5. **Failure modes** (deserialization, reflection, and “required bypass” paths)

## Key takeaways (mentor checklist)

- **Prefer constructor/factory invariants** for domain objects; use `required` for completeness of data carriers.
- **`required` is not validation**: untrusted inputs still need runtime validation.
- Avoid designs that create **transient invalid states** between constructor return and initializer assignments.
