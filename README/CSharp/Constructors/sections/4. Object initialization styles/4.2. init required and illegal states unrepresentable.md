## 4.2. `init` accessors, `required`, and “make illegal states unrepresentable”

## Topics

1. **`init` semantics** (assignment timing, invariants, and what it does *not* guarantee)
2. **`required` members** (compile-time enforcement, versioning constraints, and runtime validation)
3. **Combining `required` + constructors/primary constructors** (choose a clear contract)
4. **Immutability strategy** (shallow vs deep immutability; `readonly`, records, frozen collections)
5. **Failure modes** (deserialization, reflection, and “required bypass” paths)

---

### 1) **`init` semantics (assignment timing, invariants, and what it does *not* guarantee)**
`init` accessors allow assignment **only during object creation**:

- Inside a constructor of the type
- In an object initializer: `new T { P = ... }`

This is a *construction-time mutability* tool. It helps you keep types “mostly immutable” from the perspective of consumers.

What `init` *does* well:
- Makes it harder to accidentally mutate state after creation.
- Enables ergonomic object initializer syntax for data carriers.

What `init` does **not** guarantee:
- **Deep immutability**: `init` freezes the reference, not the referenced object. `public List<int> Items { get; init; }` is still mutable through the list.
- **Validity**: `init` doesn’t enforce invariants by itself; it only restricts timing of assignment.

**Mentor note**
- `init` is ideal for DTOs/config models. For domain objects with invariants, prefer constructors/factories so validity is guaranteed immediately.

---

### 2) **`required` members (compile-time enforcement, versioning constraints, and runtime validation)**
`required` is a **compile-time** requirement: the caller must provide a value during construction (via constructor/primary constructor or object initializer), or compilation fails/warns depending on settings.

What `required` is good for:
- Expressing **completeness** of a shape (request/response, config, DTO).
- Preventing accidental “forgot to set it” bugs at call sites.

What `required` is not:
- Not a runtime validation system.
- Not a security boundary (reflection/deserializers can bypass).

**Example (runnable): `required` + `init` for a DTO**

```csharp
public sealed class CreateUserRequest
{
    public required string UserName { get; init; }
    public required string Email { get; init; }
    public int? Age { get; init; }
}

var req = new CreateUserRequest
{
    UserName = "ada",
    Email = "ada@example.com",
    Age = 30
};
```

**Versioning note**
- Adding a new `required` member to a public type is a **source-breaking** change for consumers. In libraries, prefer additive optional members, or provide new types/overloads.

---

### 3) **Combining `required` + constructors/primary constructors (choose a clear contract)**
You can combine `required` with constructors, but avoid muddy contracts.

Good patterns:
- **Domain objects**: constructor/factory owns invariants; `required` is optional and usually redundant.
- **DTO/config**: `required` + `init` expresses required data; validation happens in a boundary layer.

Avoid:
- Two competing creation paths (a strict constructor *and* a loose object-initializer route that can bypass invariants).

**Example: choose one contract**
- If the invariant is “never null and validated”, prefer constructor parameters:

```csharp
using System;

public sealed class EmailAddress
{
    public string Value { get; }

    public EmailAddress(string value)
    {
        if (string.IsNullOrWhiteSpace(value))
            throw new ArgumentException("Email is required.", nameof(value));
        if (!value.Contains('@', StringComparison.Ordinal))
            throw new ArgumentException("Invalid email.", nameof(value));

        Value = value;
    }
}
```

- If the type is “a bag of data to validate elsewhere”, prefer `required` + `init`:

```csharp
public sealed class CreateUserRequest
{
    public required string UserName { get; init; }
    public required string Email { get; init; }
}
```

**See also**
- Primary constructors + `required` are treated deeply in section **2.2**.

---

### 4) **Immutability strategy (shallow vs deep immutability; `readonly`, records, frozen collections)**
Make “illegal states unrepresentable” usually means:
- Don’t allow creation of invalid objects.
- Don’t allow mutation that can break invariants.

Tools and what they actually guarantee:
- **`readonly` fields**: the reference/value can be assigned only in constructors/initializers (shallow).
- **`init` setters**: only assignable during creation (shallow).
- **Records**: *value-like* semantics by default; still not deep immutable automatically (see section **2.3**).
- **Frozen collections** (`System.Collections.Frozen`): make read-mostly collections efficient and effectively immutable by convention.

**Mentor rule**
- If the object owns a collection, expose it as `IReadOnlyList<T>` / `IReadOnlyDictionary<TKey, TValue>` (or `ReadOnlySpan<T>` in performance-focused APIs) and keep the mutable collection private.

---

### 5) **Failure modes (deserialization, reflection, and “required bypass” paths)**
Your invariants can be bypassed by:
- Reflection setting non-public members.
- Deserializers materializing objects without calling your intended constructors or without honoring `required`.
- ORMs setting private fields directly.

**Mentor guidance**
- Treat untrusted materialization (JSON/ORM) as boundary input. Use DTOs + mapping, or post-materialization validation.
- If you must allow framework materialization, contain it:
  - private/protected parameterless constructor (where supported),
  - private setters or private backing fields,
  - explicit “Validate()” invoked in the mapping layer.

See section **6.2** for the canonical guidance on serialization/ORM constructor constraints.

---

## Key takeaways (mentor checklist)
- **Prefer constructor/factory invariants** for domain objects; use `required` for completeness of data carriers.
- **`required` is not validation**: untrusted inputs still need runtime validation.
- Avoid designs that create **transient invalid states** between constructor return and initializer assignments.
