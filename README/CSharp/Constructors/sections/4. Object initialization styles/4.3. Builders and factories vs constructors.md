## 4.3. Builders and factories vs constructors (when you need names, steps, or async)

### 1) When constructors stop being the right tool
- Multiple creation “modes” that need names
- Stepwise construction / validation with partial data
- Async creation (constructors cannot be `async`)
- Caching / interning / pooling

### 2) Factory patterns you should know (modern .NET)
- Static factories (`Create`, `TryCreate`, `Parse`, `TryParse`)
- Dedicated factory types (DI-friendly, testable)
- Abstract factory vs strategy (when behavior varies)

### 3) Builder patterns (when they’re justified)
- Fluent builders for complex optional config
- Avoid builder allocations in hot paths (unless you measured and it’s fine)
- Prefer immutable “options” objects when possible

### 4) Error handling strategy
- Exceptions for “should never happen” invariant violations
- Try-pattern or Result types for expected failures (parsing/validation)
- Keep failure information actionable

### 5) Versioning and API evolution
- Stable creation surface: factories can add parameters/options without overload explosion
- Avoid optional parameters in public library APIs when defaults might change
