## 4.1. Object initializer syntax: power, limits, and invariants

1. **What an object initializer actually does** (mechanics)
2. **Correctness pitfalls** (transient invalid states, partial init, exceptions mid-init)
3. **Invariants strategy** (constructor/factory vs object initializer vs required/init)
4. **When object initializers are a great fit** (DTOs, configs, tests)
5. **When object initializers are a bad fit** (core domain models, invariants, thread-safety)
6. **Performance notes** (extra allocations, hidden work in setters, validation placement)

---

### 1) **What an object initializer actually does (mechanics)**
An object initializer is **syntax sugar**. Conceptually, this:

```csharp
var p = new Person("Ada") { Age = 30, Country = "UK" };
```

is roughly equivalent to:

```csharp
var p = new Person("Ada");
p.Age = 30;
p.Country = "UK";
```

Important consequences:
- The constructor runs **first**.
- Then each assignment runs **in source order**.
- It is **not atomic**: other code can observe the object in between assignments if you publish it.

**Good to know**
- Collection initializers (e.g., `{ Items = { 1, 2, 3 } }`) are also just a series of method calls (`Add`), not magic.

---

### 2) **Correctness pitfalls (transient invalid states, partial init, exceptions mid-init)**
Object initializers can create **transient invalid states**:

- Your constructor may establish invariants, but setters can later violate them.
- Your type might require multiple properties to be set consistently; object initializer sets them one by one.
- If a setter throws mid-way, you have a partially assigned object.

**Pitfall: publishing an object too early**
- If you pass `this` to an event/callback, store it in a shared collection, or otherwise publish it before the initializer completes, another thread can observe partial state.
- This is the same “don’t leak `this` during construction” rule, but object initializers extend the window where the object is mutable during creation.

---

### 3) **Invariants strategy (constructor/factory vs object initializer vs required/init)**
Choose the initialization mechanism based on what you are trying to guarantee:

- **Constructor / factory**: best for domain invariants (“valid-state-only”). The object is valid as soon as construction returns.
- **Object initializer**: best for *convenience* when transient invalid states are acceptable or are validated at a boundary.
- **`init` + `required`**: best for data carriers where you want compile-time completeness at call sites, but you still validate at the boundary for untrusted data.

**Mentor rule**
- For *domain objects*: invariants belong in constructors/factories. Use object initializers mainly for DTO/config/test scaffolding.

See section **4.2** for the canonical deep treatment of `init` + `required` and how they relate to invariants.

---

### 4) **When object initializers are a great fit (DTOs, configs, tests)**
Object initializers shine when:
- The type is a **data carrier** (DTO/request/response/config).
- Properties are mostly independent.
- Validation happens elsewhere (e.g., request validation pipeline, mapping layer).
- You want readable call sites without “constructor parameter explosion”.

**Example (runnable): DTO-style request**

```csharp
public sealed class CreateUserRequest
{
    public required string UserName { get; init; }
    public required string Email { get; init; }
    public int? Age { get; init; }
}

var req = new CreateUserRequest
{
    UserName = "ada",
    Email = "ada@example.com",
    Age = 30
};
```

---

### 5) **When object initializers are a bad fit (core domain models, invariants, thread-safety)**
Avoid object initializers when:
- The type has **non-trivial invariants** (e.g., “start <= end”, “currency must match”, “state machine rules”).
- You need the object to be valid immediately after creation for correctness or thread-safety.
- Setters trigger behavior (events, caching, external calls) — those side effects become order-dependent.

Better options:
- A constructor with explicit parameters.
- A named factory (especially for multiple creation modes).
- A builder only when it materially improves correctness/readability (see section **4.3**).

---

### 6) **Performance notes (extra allocations, hidden work in setters, validation placement)**
Object initializers themselves don’t allocate, but they encourage patterns that can:

- Add extra work in property setters (validation, normalization) executed multiple times.
- Create extra allocations if setters allocate (e.g., copying collections defensively per set).

**Performance note**
- Keep setters cheap; heavy validation and normalization should be centralized (constructor/factory) so it runs once.
