### 1) **Allocation vs initialization: what happens when you call `new`**
An instance constructor is the code that runs **after** the runtime has allocated memory for the object and set all instance fields to `default`.

- **For classes**: `new` allocates on the managed heap, zero-initializes the object, then runs field initializers and constructor bodies (base → derived).
- **For structs**: `new` creates a value on the stack (or inside another object/array), and initialization rules are different. The important part is: `default(T)` is always a valid value that exists even if you don’t call a user-defined constructor.

**Good to know**
- “Constructor runs” is not the first thing that happens. The runtime has already created a *zeroed* object. That’s why you must design constructors to turn **default state** into **valid state**.
- Execution order is subtle; this tutorial treats it deeply in one place. See section **1.3** and (canonical runtime details) `README/CSharp/Fields/sections/1. Field fundamentals/1.2. Field initialization and execution order.md`.

### 2) **Constructor responsibilities: invariants, validation, and safe defaults**
The constructor’s job is to establish **type invariants**: conditions that must be true for every observable instance of the type.

**Mentor rule**
- If an object can exist in an invalid state, your whole codebase pays interest forever: defensive checks, null checks, “maybe initialized” branches, and bugs from illegal transitions.

**What belongs in a constructor**
- **Argument validation** for invariants (cheap checks; fail fast).
- Assigning **required dependencies** and core state (often `readonly`).
- Establishing **derived state** that is cheap and deterministic.

**What typically does not belong**
- Anything that can fail for environmental reasons (network, disk, configuration discovery) unless the type’s entire meaning depends on it *and* you control when it runs (see “What not to do” below).

**Example (runnable): invariants + clear ownership**

```csharp
using System;

public sealed class EmailAddress
{
    public string Value { get; }

    public EmailAddress(string value)
    {
        if (string.IsNullOrWhiteSpace(value))
            throw new ArgumentException("Email is required.", nameof(value));

        // Keep validation proportional to the domain.
        if (!value.Contains('@', StringComparison.Ordinal))
            throw new ArgumentException("Invalid email format.", nameof(value));

        Value = value;
    }

    public override string ToString() => Value;
}
```

**Performance note**
- Throwing exceptions is fine for **programmer errors** and “this should never happen” invariant violations.
- For **expected validation failures in high volume** (parsing user input, ingestion pipelines), prefer a Try-pattern or a factory that returns a result type (see item 4).

### 3) **What not to do in constructors**
Constructors should be **fast**, **deterministic**, and **side-effect-light**.

Avoid:
- **I/O** (HTTP/DB/file): makes construction slow and unpredictable; introduces retries/timeouts into object creation.
- **Blocking on async**: `.Result` / `.Wait()` is a common deadlock vector (especially (frontend) with a UI `SynchronizationContext`) and can cause ThreadPool starvation even on servers.
- **Starting background work** (timers/tasks) without an explicit lifetime contract: you’ll leak work, hold objects alive, and make tests flaky.
- **Publishing `this`** (events, callbacks, passing `this` out): another thread can observe a partially constructed object.

**Better patterns**
- Use a **factory** (sync or async) for expensive creation.
- Separate construction (cheap) from activation (`Start()`, `InitializeAsync()`), and make lifetime explicit.

### 4) **Exceptions vs Try-pattern vs factories for expected failures**
Choose an error model that matches reality:

- **Throw exceptions** when the caller violated a contract or the state must never exist.
- **Try-pattern** (`bool TryCreate(..., out T value)`) when failure is expected and frequent.
- **Factory returning a result** (e.g., `Result<T>`, `OneOf`, `ValidationResult`) when you need rich error data without exceptions.
- **Async factory** (`Task<T> CreateAsync(...)`) when creation needs I/O (constructors cannot be `async`).

**Example (runnable): TryCreate avoids exceptions in expected failures**

```csharp
using System;

public sealed class Port
{
    public int Value { get; }
    private Port(int value) => Value = value;

    public static bool TryCreate(int value, out Port? port)
    {
        if ((uint)value > 65535u) { port = null; return false; }
        port = new Port(value);
        return true;
    }
}
```

**Good to know**
- For public libraries, your choice here becomes API policy. Don’t mix “sometimes throw, sometimes return false” for the same kind of error.

### 5) **Performance framing: hidden allocations, object graphs, and hot-path construction**
Most constructor performance issues come from **what you do inside** them, not the constructor itself.

Common hidden costs:
- **LINQ** allocations (`ToList`, `Select`) in constructors for hot-path types.
- **Capturing lambdas** that allocate closures.
- **`params` arrays** at call sites (allocation) when used heavily.
- Building **large object graphs** eagerly when only a small part is used.

**Mentor guidance**
- In hot paths, prefer:
  - passing already-validated inputs,
  - using spans/streaming APIs at boundaries (parsing belongs elsewhere),
  - deferring expensive work behind explicit methods.
- In non-hot code, prefer **clarity** and **correctness**, then measure with profilers if needed.
