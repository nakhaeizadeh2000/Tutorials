### 1) **Default constructor vs parameterless constructor (terms and reality)**
These terms get mixed up, so be precise:

- **Parameterless constructor**: a constructor you can call with no arguments, written explicitly as `public MyType() { ... }` (or other accessibility).
- **Default constructor**: a *compiler-provided* parameterless constructor that exists **only when you didn’t declare any instance constructors** (for classes). People often say “default ctor” when they mean “parameterless ctor”.

**Mentor note**
- Whether the parameterless ctor is compiler-provided or explicit matters for **API design**, **initialization intent**, and sometimes **framework behavior** (some tools look for a *public* parameterless ctor specifically).

---

### 2) **When the compiler provides one (classes vs structs) and when it doesn’t**
**Classes**
- If you declare **no** instance constructors, the compiler synthesizes a **public parameterless constructor** that just calls the base constructor.
- If you declare **any** instance constructor, the compiler **does not** add a parameterless one. If you still want one, you must write it.

**Structs**
- `default(T)` is always legal and produces the “all-zero” value.
- In modern C#, structs can define parameterless constructors, but you still cannot prevent `default(T)` from existing. That’s why “struct invariants” are fundamentally different from class invariants.

**Good to know (boundary rule)**
- If your type must *never* exist in an invalid state and you need enforceable invariants, a **class** (or an immutable struct used carefully) is usually the right shape. The deep “type shape choice” discussion belongs in `README/CSharp/CSharp Basic Object Oriented Programming/sections/2. Creating classes and objects/2.4. Choosing class vs struct vs record vs record struct.md`.

### 3) **`default(T)` and `new T()` (constraints, generics, and meaning)**
In generic code, you’ll see:

- `default(T)` — gives the default value for the type parameter:
  - `null` for reference types,
  - all-zero for structs (including `Guid.Empty`, `0`, etc.).
- `new T()` — only allowed when `T` has the `new()` constraint. It means “call a public parameterless constructor”.

**Important nuance**
- For `struct` type arguments, `new T()` effectively produces the same value as `default(T)` (a zeroed value), even if the struct declares a parameterless constructor. Don’t build designs that rely on `new()` for “enforced invariant initialization” in generic code.

**Example (runnable): generic “create” APIs are limited by `default` semantics**

```csharp
public static class Factory<T> where T : new()
{
    public static T Create() => new();
}
```

**Mentor guidance**
- Prefer explicit factories for domain objects: `EmailAddress.Parse(...)`, `Money.TryCreate(...)`, `OrderId.FromGuid(...)`. They communicate intent and avoid the misleading “`new()` means valid” assumption.

---

### 4) **Nullability + initialization contracts (what the compiler can/can’t prove)**
Nullable reference types help, but they are not magic:

- If you expose a parameterless constructor and set required state later through setters, you create a **transient invalid state**. The compiler cannot always prove “this property will be set before use”.
- `required` members improve compile-time enforcement at object creation, but are not a replacement for runtime validation when values come from untrusted sources.

**Good to know**
- If you’re forced to support a parameterless constructor for a framework, consider:
  - making it `private`/`protected` when possible,
  - using a separate DTO type for serialization,
  - doing a validation pass at the boundary (mapping layer).

See section **4.2** for the canonical “`init` + `required` and illegal states” treatment in this domain.

### 5) **Framework expectations (DI/serializers/ORMs) and how to avoid weakening invariants**
Some frameworks historically demanded parameterless constructors. Modern .NET tooling is often more flexible, but constraints still exist.

- **Dependency Injection** (ASP.NET Core built-in container): prefers the “best” public constructor it can satisfy; it does not require parameterless constructors. Keep “DI + constructor injection” as your default. See section **6.1** for the deep treatment.
- **Serialization**:
  - `System.Text.Json` supports parameterized constructors and source generation, but some shapes (especially mutable POCOs) still commonly use parameterless + setters.
  - Treat serialized types as **DTOs** unless you can strongly enforce invariants.
- **ORMs**:
  - Many ORMs can use non-public constructors for materialization, but rules differ; avoid twisting your domain model to fit an ORM if it weakens correctness.

**Mentor rule**
- Don’t let “a serializer wants a parameterless ctor” force invalid domain states. Create a DTO and map.

See section **6.2** for the canonical deep guidance on “parameterless constructors for frameworks” in this domain.

---

### 6) **Mentor rules (public API versioning + correctness)**
- **Public constructors are part of your API contract**. Removing or changing behavior is breaking.
- Prefer one “main” initialization contract (constructor or factory), and keep other overloads forwarding to it (see section **3.2**).
- Avoid public setters as a substitute for construction-time invariants; you’ll accumulate bugs and validation duplication.

**Performance note**
- Parameterless constructors + setters often lead to extra allocations and repeated validation because initialization is scattered. Centralizing initialization in one place is not only cleaner—it’s often faster.
