## 1.3. Execution order: field initializers, base constructors, and derived constructors

1. **The actual order for classes** (what really runs first)
2. **Field initializers vs constructor body** (source order and surprises)
3. **Base/derived interaction** (`base(...)` and what can be assumed)
4. **The “no virtual calls in constructors” rule** (why it exists)
5. **How to design around ordering hazards** (factories, composition, explicit init)

---

### 1) **The actual order for classes (what really runs first)**
This topic is subtle and frequently misremembered. The **canonical deep treatment** (including `beforefieldinit`, static vs instance ordering, and failure modes) is already in:

- See `README/CSharp/Fields/sections/1. Field fundamentals/1.2. Field initialization and execution order.md` for the full explanation.

Quick constructor-focused summary (instance creation for `class`):
- The runtime allocates and **zero-initializes** the object.
- **Base** instance field initializers run (in source order).
- **Base** constructor body runs.
- **Derived** instance field initializers run (in source order).
- **Derived** constructor body runs.

**Good to know**
- Field initializers run **before** the constructor body of that type.
- If a derived override runs before derived field initializers, it can see `null`/default values even for `readonly` fields.

---

### 2) **Field initializers vs constructor body (source order and surprises)**
Field initializers are executed **in the textual order they appear in the source file**, not alphabetical order and not “IDE order”.

Common surprises:
- An initializer that references another field depends on source order.
- “Helper methods” called from initializers can run before the constructor body, which can be surprising for logging or dependency use.

**Mentor rule**
- Keep field initializers **pure and cheap**. If initialization needs validation or can fail, prefer the constructor/factory.

---

### 3) **Base/derived interaction (`base(...)` and what can be assumed)**
`base(...)` determines which base constructor runs. The key design boundary:

- **Base** constructors must establish **base invariants** without relying on derived state.
- **Derived** constructors must assume base state is valid, but must not assume base called derived virtual logic safely.

**Good to know**
- Passing parameters to `base(...)` is a great way to make the base invariant boundary explicit.

---

### 4) **The “no virtual calls in constructors” rule (why it exists)**
If a base constructor calls a virtual method (directly or indirectly), the override in the derived type can execute **before** derived field initializers and the derived constructor body.

That means the override can observe:
- `null` in a `readonly` field that “will be assigned later”
- partially initialized collections
- invariants not yet established

**Example (runnable): virtual call during construction can break**

```csharp
using System;

public abstract class Base
{
    protected Base()
    {
        // BAD: virtual call during construction.
        OnConstructed();
    }

    protected virtual void OnConstructed() { }
}

public sealed class Derived : Base
{
    private readonly string _name = "ready";

    protected override void OnConstructed()
    {
        // _name is still default (null) here because derived field initializers haven't run yet.
        Console.WriteLine(_name.Length);
    }
}

public static class Program
{
    public static void Main()
    {
        _ = new Derived();
    }
}
```

**Mentor alternatives**
- Replace virtual initialization with **constructor parameters** and explicit composition.
- Use a **factory** that constructs the full object and then calls a virtual/override hook only after the derived constructor has finished (careful: still don’t publish partially built objects).
- If you must support override customization, consider the **Template Method** pattern invoked after construction via an explicit `Initialize()` call (and make it idempotent/testable).

---

### 5) **How to design around ordering hazards (factories, composition, explicit init)**
Good patterns:
- **Constructor chaining** to a single “core” constructor that establishes invariants (see section **3.2**).
- **Factories** for complex graphs and for async creation (constructors can’t be `async`).
- **Composition over inheritance** when initialization ordering becomes a correctness hazard.

**Performance note**
- Correctness bugs from initialization order often turn into “defensive checks everywhere”, which adds branches, extra allocations (fallback objects), and complexity. Fix the construction contract instead.
