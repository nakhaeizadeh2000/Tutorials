## 8.1. Interview Q&A: constructors, initialization order, and modern initialization contracts

1. **Default vs parameterless vs static constructor** (definitions + behavior)
2. **Initialization order** (fields, base/derived) and the “no virtual calls in constructors” rule
3. **Object initializer vs constructor vs `required` vs primary constructor** (when to use which)
4. **Constructor overloading + chaining** (how to keep invariants consistent)
5. **Factories vs constructors** (async creation, caching, error handling)
6. **DI / serialization / ORM constraints** (safe patterns without weakening invariants)
7. **Performance questions** (allocations, hidden work, static first-touch cost)
8. **Common pitfalls and mentor answers**

---

### 1) **Default vs parameterless vs static constructor**
What you must say correctly:
- **Parameterless constructor**: any `MyType()` constructor you can call with no args (explicit or compiler-provided).
- **Default constructor** (common usage): the compiler-synthesized parameterless constructor for a class when you declare no instance constructors.
- **Static constructor**: `static MyType()` type initializer; runs once, thread-safe, can “poison” the type if it throws.

Interview follow-ups:
- “When does the compiler generate a parameterless constructor for a class?”
- “Can you prevent `default(T)` for a struct?” (No.)

Canonical refs in this tutorial:
- Definitions + framework realities: see section **1.2**.
- Static init semantics: see `README/CSharp/Fields/sections/4. Static fields/4.2. Static initialization type constructors Lazy thread-safety.md` (canonical).

### 2) **Initialization order and “no virtual calls in constructors”**
What a strong answer includes:
- Base field initializers and base ctor run before derived field initializers and derived ctor.
- A base constructor calling a virtual method can execute the derived override before derived initialization has happened → partially initialized state.

What mentors listen for:
- You propose **design alternatives** (composition, passing data into base ctor, factories) rather than “just don’t do it”.

Canonical ref:
- See section **1.3** for the runnable example and patterns.

### 3) **Object initializer vs constructor vs `required` vs primary constructor**
Expected distinctions:
- **Constructor/factory**: best for invariants (“valid-state-only”), normalization, and deterministic creation.
- **Object initializer**: convenience; assignments happen after ctor; not atomic.
- **`required` + `init`**: compile-time completeness for DTO/config; not runtime validation.
- **Primary constructor**: syntax to express the creation contract at the type declaration; choose when it improves clarity.

Good answers mention:
- “`required` is not validation” and “object initializers can create transient invalid states”.

Canonical refs:
- Object initializer mechanics/pitfalls: section **4.1**.
- `init` + `required`: section **4.2** (canonical).
- Primary constructors + `required`: section **2.2** (canonical).

### 4) **Constructor overloading + chaining**
What you should emphasize:
- Keep overload sets small to avoid ambiguity.
- Centralize validation in one core ctor; other overloads delegate via `this(...)`.
- Avoid optional parameters in public APIs (caller-baked defaults).

Canonical refs:
- Overload pitfalls: section **3.1**.

### 5) **Factories vs constructors**
Interviewers are testing whether you know:
- Constructors can’t be `async`.
- Factories can return cached/interned instances.
- Factories can use Try-pattern or Result types for expected failures.

### 6) **DI / serialization / ORM constraints**
A mentor-grade answer:
- Prefer constructor injection; avoid service locator.
- Don’t weaken domain invariants for serializers/ORMs; use DTO + mapping or supported constructor binding.

### 7) **Performance questions**
The high-signal points:
- Constructors should be cheap/deterministic; avoid hidden work and allocations.
- Static initialization can cause first-touch p99 latency spikes.
- Avoid exceptions for expected failures in hot paths; use Try-pattern/factories.

Canonical refs:
- Constructor perf framing: section **1.1**.
- Static init p99 risks: section **2.1** (and canonical deep `Fields` static init section).

---

### 8) **Common pitfalls and mentor answers**
Common pitfalls:
- “Parameterless ctor + public setters everywhere” → transient invalid states.
- Doing I/O / blocking async / starting background work inside constructors.
- Publishing `this` during construction.

Mentor answers:
- “Design a single, explicit initialization contract.”
- “Use factories for async/caching/expected-failure creation.”
- “Prefer immutability; it simplifies correctness and publication.”
