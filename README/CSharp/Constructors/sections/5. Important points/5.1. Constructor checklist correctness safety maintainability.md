## 5.1. Constructor checklist: correctness, safety, and maintainability

### 1) Valid state and invariants
- Define invariants explicitly (what must always be true)
- Validate arguments at the boundary (constructor/factory)
- Prefer making invalid states unrepresentable (types, nullability, `required`, immutability)

### 2) What must NOT happen in constructors
- No I/O (HTTP/DB/file), no blocking on async (`.Result`/`.Wait()`)
- No starting background work without explicit lifetime management
- No taking locks that can be taken elsewhere during init (deadlock risk)

### 3) Avoid leaking `this` during construction
- No virtual calls from constructors
- Avoid subscribing events / publishing self references before fully initialized
- Beware closures capturing `this` and extending lifetime unexpectedly

### 4) API design and versioning
- Keep overload sets small and consistent (no “half-valid” overloads)
- Prefer a single “main” initialization contract (ctor vs factory vs object initializer)
- Public constructors are contracts: changing behavior is a breaking change

### 5) Testing and maintainability
- Prefer deterministic initialization (no ambient/global state)
- Keep constructor logic small; move complex logic into named methods/factories
- Consider DTO separation for serialization frameworks
