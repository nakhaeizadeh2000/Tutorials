## 6.2. Serialization and ORMs: when frameworks want parameterless constructors

1. **Domain model vs DTO model** (keep invariants intact)
2. **Parameterless constructors**: when you truly need them (and how to contain the damage)
3. **Modern serializer/ORM capabilities** (prefer these over weakening your model)
4. **Common pitfalls and mentor rules**
5. **Interview-ready Q&A prompts**

---

### 1) **Domain model vs DTO model (keep invariants intact)**
Treat “framework materialization” as a boundary concern.

- **Domain model**: your correctness engine. Constructors/factories enforce invariants; invalid states are not representable.
- **DTO model**: shaped for frameworks (JSON/ORM/binding). Often looser, easier to version, and easier for source generation.

**Mentor rule**
- Don’t weaken your domain model to satisfy a serializer/ORM. Put that flexibility in a DTO and map.

Common mapping patterns:
- **Explicit mapper** (hand-written): predictable, fast, debuggable.
- **Factory-based mapping**: `Order.Create(dto...)` centralizes invariants.
- **Projections** (ORM query projection): project into DTOs directly when possible.
- **Anti-corruption layer**: when integrating with messy external schemas.

---

### 2) **Parameterless constructors: when you truly need them (and how to contain the damage)**
Some frameworks and patterns still expect a parameterless constructor or can benefit from one.

If you must provide one:
- Prefer **`private`/`protected` parameterless constructors** (where the framework supports non-public activation) so normal code can’t create invalid instances accidentally.
- Keep it **empty** (no side effects, no I/O).
- Ensure invariants are restored via:
  - parameterized constructors + constructor binding (preferred), or
  - a mapping layer that validates after materialization.

**`init`/`required` interaction**
- `required` is compile-time only; a deserializer can bypass it.
- `init` restricts assignment timing in normal code, but frameworks can still set members via reflection or special binding.

**Mentor guidance**
- Assume untrusted data can violate your invariants. Validate at the boundary even if you use `required`.

---

### 3) **Modern serializer/ORM capabilities (prefer these over weakening your model)**
Prefer modern tooling that respects constructors and reduces reflection.

#### `System.Text.Json` (modern .NET)
- Prefer **constructor binding** (parameterized constructors) and **source generation** when feasible for speed and AOT/trimming friendliness.
- Keep “wire format” types as DTOs if your domain invariants are richer than what JSON can naturally express.

#### EF Core (ORM)
- EF Core supports **constructor binding** and can set **private fields** / **private setters** depending on configuration.
- Prefer mapping complex invariants in the domain and keep EF entities lean, or use owned types/value objects carefully.

**Performance note**
- Reflection-heavy materialization costs CPU and can be problematic under trimming/AOT. Source generation and explicit mapping improve predictability.

---

### 4) **Common pitfalls and mentor rules**
- **Half-initialized instances**: parameterless + setters creates transient invalid states; bugs appear when someone uses the object “too early”.
- **Default values vs missing data**: `default` is not “valid”. Be explicit about “missing vs zero/empty”.
- **Versioning**: adding a new required field/member can be breaking; plan schema evolution (defaults, migrations, compatibility).

**Mentor rule**
- Keep invariants in one place. Frameworks should adapt to you via DTOs/mapping, not the other way around.

---

### 5) **Interview-ready Q&A prompts**
- **When is a parameterless constructor required?**  
  Discuss serializers/ORMs/frameworks; emphasize modern alternatives and containment with non-public ctors.
- **How do you keep invariants with JSON/ORM frameworks?**  
  DTO + mapping + validation; constructor binding; avoid transient invalid states.
- **How do `required`/`init` affect serialization?**  
  Compile-time vs runtime; bypass paths; still validate.
