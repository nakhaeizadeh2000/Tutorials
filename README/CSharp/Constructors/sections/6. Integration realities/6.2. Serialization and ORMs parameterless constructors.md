## 6.2. Serialization and ORMs: when frameworks want parameterless constructors

### 1) Domain model vs DTO model (keep invariants intact)
- **What belongs in domain constructors** (invariants, validation, valid-state-only)
- **DTOs as framework shapes** (looser, mapping layer, source-gen friendly)
- **Mapping patterns** (explicit mappers, factories, projection, anti-corruption layer)

### 2) Parameterless constructors: when you truly need them (and how to contain the damage)
- **Private/protected parameterless constructor** pattern (where supported)
- **Init-only / required** interactions with serializers
- **Post-deserialization validation** (ensure invariants still hold)

### 3) Modern serializer/ORM capabilities (prefer these over weakening your model)
- **System.Text.Json** constructor binding / source generation (when applicable)
- **EF Core patterns** (constructor binding, private setters/fields, owned types)
- **Avoiding reflection-heavy runtime paths** (perf + trimming/AOT considerations)

### 4) Common pitfalls and mentor rules
- **Half-initialized instances** and transient invalid states
- **Default values vs missing data** (don’t let `default` silently mean “valid”)
- **Versioning** (adding members, changing requiredness, schema evolution)

### 5) Interview-ready Q&A prompts
- “When is a parameterless constructor required?”
- “How do you keep invariants with JSON/ORM frameworks?”
- “How do `required`/`init` affect serialization?”
