## 6.1. Constructors with Dependency Injection (DI): correct lifetimes and testability

1. **Constructor injection** as the default (explicit dependencies, invariants, tests)
2. **Lifetime correctness** (transient/scoped/singleton) and captive dependency bugs
3. **Factory patterns with DI** (async creation, policies, and named modes)
4. **Design boundaries** (domain models vs application services; avoid service locator)
5. **Performance notes** (what DI costs, what actually matters)

---

### 1) **Constructor injection as the default**
In modern .NET applications, **constructor injection** is the default pattern because it makes dependencies:

- **explicit** (readability),
- **mandatory** (correctness),
- **testable** (easy to substitute fakes/stubs),
- and **centralized** (invariants can be checked once).

**Example (runnable): a service with explicit dependencies**

```csharp
using System;

public interface IClock
{
    DateTimeOffset UtcNow { get; }
}

public sealed class SystemClock : IClock
{
    public DateTimeOffset UtcNow => DateTimeOffset.UtcNow;
}

public sealed class TokenService(IClock clock) // primary ctor works fine here
{
    private readonly IClock _clock = clock ?? throw new ArgumentNullException(nameof(clock));

    public string CreateToken(string userId)
    {
        if (string.IsNullOrWhiteSpace(userId))
            throw new ArgumentException("UserId is required.", nameof(userId));

        // Pretend token logic.
        return $"{userId}:{_clock.UtcNow:O}";
    }
}
```

**Mentor rule**
- The constructor should establish a valid, usable object. Don’t hide expensive I/O or background work behind “just constructing a service” (see section **1.1**).

---

### 2) **Lifetime correctness (transient/scoped/singleton) and captive dependencies**
DI is not just “how to create objects”; it’s **lifetime management**.

Common lifetime categories:
- **Transient**: new instance each time.
- **Scoped**: one instance per scope (e.g., per web request in ASP.NET Core).
- **Singleton**: one instance for the process lifetime.

The classic bug is a **captive dependency**:
- a **singleton** depends on a **scoped** service, so it captures a request-scoped object and uses it after the request ends.

**Mentor guidance**
- This is a correctness bug first (wrong data, disposed services), and often a performance bug (unexpected memory retention).
- Fix it with:
  - changing lifetimes to be compatible,
  - injecting a **factory** (`Func<T>`, `IServiceProvider`-free factory abstraction), or
  - moving the scoped dependency to the method boundary.

**Good to know**
- “Just inject `IServiceProvider` and resolve inside methods” is the **Service Locator** anti-pattern unless you are writing infrastructure composition code. Prefer explicit factories/interfaces instead.

---

### 3) **Factory patterns with DI (async creation, policies, named modes)**
Use factories when:
- creation needs **I/O** (constructors can’t be `async`),
- there are **multiple named creation modes**,
- creation involves policies (retry/backoff, caching, feature flags) you want to test.

Canonical discussion of factories vs constructors lives in section **4.3**.

**Example shape (DI-friendly):**

```csharp
public interface IClientFactory
{
    // Can be async if creation needs I/O.
    ValueTask<MyClient> CreateAsync(CancellationToken ct);
}

public sealed class MyClient;
```

---

### 4) **Design boundaries (domain models vs application services; avoid service locator)**
Keep these roles distinct:

- **Domain models/value objects**: invariants, “valid-state-only”, created via constructors/factories.
- **Application services**: orchestrate use cases, depend on infrastructure (DB, HTTP), and are composed by DI.

Avoid:
- injecting half the system into a domain constructor,
- domain objects depending on `HttpClient`, EF `DbContext`, or configuration lookups.

If your domain object “needs I/O to exist”, the domain boundary is likely wrong. Model “what you know” in the domain; perform I/O in application/infrastructure and then construct the domain object from validated data.

---

### 5) **Performance notes (what DI costs, what actually matters)**
Realistically:
- DI resolution has overhead, but it’s rarely your main bottleneck.
- The big costs are usually:
  - I/O,
  - allocations (object graphs, per-request work),
  - contention,
  - and expensive “first-touch” static initialization.

**Performance note**
- The DI mistake that *does* hurt a lot is doing expensive work in constructors that run frequently (per request / per message). Keep constructors cheap and move expensive initialization behind explicit methods, caching, or startup warm-up.
