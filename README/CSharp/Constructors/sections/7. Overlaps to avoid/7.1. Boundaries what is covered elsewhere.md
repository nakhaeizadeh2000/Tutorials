### 1) **Why this “boundaries” section exists (how to use it)**
This repo is structured so each important concept has **one canonical deep explanation**. Everything else should link to that canonical place instead of repeating it.

How to use this section:
- **As a learner**: when a topic in Constructors mentions “See X for the deep dive”, this section tells you *why* that deep dive lives there.
- **As an API designer**: it prevents “tutorial sprawl” (duplicated explanations that drift over time) and it mirrors how real codebases should avoid duplicated business rules.

**Mentor rule**
- Repetition is not clarity if it creates inconsistent truth. Canonicalize the deep explanation, then reference it everywhere else.

### 2) **Overlaps to avoid (canonical deep sources and why they own them)**
The Constructors domain intentionally does **not** re-teach these topics deeply. It references them.

#### 2.1) Static initialization, `Lazy<T>`, `beforefieldinit`, memory visibility
- **Canonical**: `README/CSharp/Fields`
- **Why**: static initialization is fundamentally about **where state lives**, **lifetime**, and **publication semantics**—that’s the Fields domain.
- **Start here**:
  - `README/CSharp/Fields/sections/4. Static fields/4.2. Static initialization type constructors Lazy thread-safety.md`
  - `README/CSharp/Fields/sections/1. Field fundamentals/1.2. Field initialization and execution order.md`

**Good to know**
- Constructors must mention static constructors (`static MyType()`), but the deep rules are shared with static fields and type initialization.

#### 2.2) OOP fundamentals, invariants, “valid states only”, type-shape choices
- **Canonical**: `README/CSharp/CSharp Basic Object Oriented Programming`
- **Why**: invariants and modeling are **design semantics**, not syntax. Constructors are one mechanism for enforcing invariants, but the deeper “what is an invariant / what is a value object / how to model identity” belongs to OOP.
- **Start here**:
  - `README/CSharp/CSharp Basic Object Oriented Programming/sections/3. Important points about objects/3.3. Encapsulation and invariants valid states only.md`
  - `README/CSharp/CSharp Basic Object Oriented Programming/sections/2. Creating classes and objects/2.4. Choosing class vs struct vs record vs record struct.md`

#### 2.3) Call-site semantics: overload resolution, optional params versioning, `params`, named args
- **Canonical**: `README/CSharp/Methods`
- **Why**: these are primarily about **call-site binding** and **parameter passing semantics**, and they apply to both methods and constructors.
- **Start here**:
  - `README/CSharp/Methods/sections/5. Overload resolution and overloading/5.1. Method overloading rules ambiguity API design.md`
  - `README/CSharp/Methods/sections/4. Passing objects and arguments/4.2. Optional parameters default arguments versioning correctness.md`

**Mentor note**
- Constructor overloads are just overloads. If you don’t understand method overload resolution, you don’t understand constructor overload resolution.

#### 2.4) Threading, synchronization, publication, .NET memory model deep dive
- **Canonical**: `README/CSharp/Cuncurrent & Parallel`
- **Why**: “safe publication” and memory visibility require the memory model + synchronization primitives, which is a concurrency topic.
- **Start here**:
  - `README/CSharp/Cuncurrent & Parallel/sections/4. Correctness, Testing, Diagnostics & Debugging in Concurrent Code/4.2. .NET memory model and visibility.md`
  - `README/CSharp/Cuncurrent & Parallel/sections/1. Core Terminology in Concurrency & Parallelism/1.4. Synchronization patterns and primitives.md`

#### 2.5) Runtime/GC/JIT/AOT framing and system-level performance
- **Canonical**: `README/CSharp/Fundamental Theories`
- **Why**: constructor performance ultimately becomes questions about **allocations**, **GC**, **JIT**, cold-start, and runtime services.
- **Start here**:
  - `README/CSharp/Fundamental Theories/sections/2. NET architecture/2.3. GC basics for app developers.md`
  - `README/CSharp/Fundamental Theories/sections/2. NET architecture/2.2. IL JIT tiered compilation AOT.md`

### 4) **Decision heuristics (fast way to choose the right domain)**
When you’re unsure where a topic belongs, use these heuristics:

- If the question is **“when does this run and what is initialized first?”**  
  - Start with Constructors `1.3`, then go deep in Fields execution-order canonical section.
- If the question is **“how should I shape my type so invalid states can’t exist?”**  
  - Start with OOP invariants/encapsulation canonical sections; Constructors shows the enforcement mechanism.
- If the question is **“why is this call ambiguous / which overload is chosen?”**  
  - Methods overload-resolution canonical section (applies equally to constructors).
- If the question is **“is this safe across threads / can another thread see partial state?”**  
  - Concurrency memory-model canonical sections; Constructors `5.3` only summarizes the minimum.
- If the question is **“why is this slow / why are there allocations?”**  
  - Constructors `5.2` for constructor-specific traps, then Fundamental Theories GC/JIT for the deep runtime view.

### 5) **Common overlap mistakes (what to avoid)**
Mistakes that cause duplicated explanations and duplicated bugs:

- **Putting validation in setters** because object initializers “feel nicer”.  
  Result: transient invalid states and order-dependent behavior. Canonical: Constructors `4.1` and `4.2`.
- **Using optional parameters for public constructors** and later changing defaults.  
  Result: old callers keep old defaults. Canonical: Methods optional-parameter versioning section.
- **Doing static initialization work in constructors “because it’s one-time anyway”.**  
  Result: unpredictable first-touch latency spikes and deadlocks. Canonical: Fields static initialization.
- **Trying to “enforce struct invariants” via constructors in generic code.**  
  Result: `default(T)` exists and bypasses your intent. Canonical: Constructors `1.2` and `2.2`.

**Mentor rule**
- Boundaries are not “documentation style”; they are how you keep large systems correct over time.
