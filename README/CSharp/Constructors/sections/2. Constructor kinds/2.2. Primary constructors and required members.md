### 1) **Primary constructors (what they solve)**
Primary constructors let you express “these values define how the instance is created” **at the type declaration**, reducing boilerplate and making the initialization contract more obvious.

They’re best when:
- The type is **small**, the invariants are **simple**, and the initialization logic is mostly “assign + validate”.
- You want to avoid **constructor overload soup** and keep initialization centralized.

They’re not a silver bullet:
- If construction logic is complex (multiple modes, heavy validation, conditional initialization), an explicit constructor/factory is often clearer.

**Example (runnable): primary constructor + invariant checks**

```csharp
using System;

public sealed class User(string userName, EmailAddress email)
{
    public string UserName { get; } =
        !string.IsNullOrWhiteSpace(userName) ? userName : throw new ArgumentException("UserName is required.", nameof(userName));

    public EmailAddress Email { get; } = email ?? throw new ArgumentNullException(nameof(email));
}

public sealed class EmailAddress(string value)
{
    public string Value { get; } =
        value.Contains('@', StringComparison.Ordinal) ? value : throw new ArgumentException("Invalid email.", nameof(value));
}
```

**Good to know**
- Primary constructors do not remove the need for *design thinking*. They only change syntax and some ordering/capturing behaviors.

---

### 2) **Primary constructors on classes vs structs vs records**
Where you use them changes the trade-offs:

- **Classes**: great for immutable “value-ish” objects and service objects with a small number of dependencies (though for DI you often still prefer explicit constructors for clarity and tooling).
- **Structs**: remember `default(T)` always exists. You can’t fully enforce invariants the same way you can with classes. If “invalid default” is a problem, a struct is usually the wrong shape.
- **Records**: positional records already provide a primary-constructor-like experience, plus generated value semantics. See section **2.3** for the canonical “records + construction” treatment.

**Mentor rule**
- If you need strong invariants and you can’t tolerate `default`, prefer a **class** (or a dedicated “strong type” class/record) over a struct.

### 3) **Capturing semantics and member initialization timing**
Primary constructor parameters are in scope for:
- field/property initializers
- base constructor calls (when applicable)

But be careful with:
- **capturing** parameters into lambdas or storing them in fields without validation (you’ve just deferred the bug).
- **ordering**: base/derived initialization order still matters. If initialization order becomes subtle, prefer explicit constructors and keep them small.

For the deep “what runs when” model, see:

### 4) **`required` members (what is enforced, and what is not)**
`required` is a **compile-time** rule: callers must set the member during object creation (object initializer or constructor) or the compiler warns/errors (depending on settings).

What `required` *does*:
- Prevents accidental “forgot to set it” at most call sites in normal code.
- Communicates intent clearly for **data-carrier** types (DTOs, requests, config models).

What `required` does *not* do:
- It is **not runtime validation**. Reflection/deserialization may bypass it.
- It does not guarantee non-null at runtime if the source is untrusted or uses null-forgiving patterns.

**Example (runnable): `required` with `init` for a DTO**

```csharp
public sealed class CreateUserRequest
{
    public required string UserName { get; init; }
    public required string Email { get; init; }
}

var req = new CreateUserRequest { UserName = "ada", Email = "ada@example.com" };
```

**Mentor rule**
- Use `required` to enforce **completeness**, not **validity**. Validity still belongs in domain constructors/factories.

---

### 5) **`required` vs constructor parameters (choosing one main contract)**
Pick one dominant contract for each type:

- Prefer **constructor parameters** when:
  - the type has invariants that must hold immediately,
  - you want “valid-state-only” by construction,
  - you need to validate and normalize inputs once.
- Prefer **`required` + init/object initializer** when:
  - the type is a data carrier (DTO/config),
  - ergonomics and readability at call sites matter,
  - validation is performed at a boundary layer (mapping/validation pipeline).

Avoid mixing in a way that creates confusion:
- A type with both a “strict constructor” and a “loose initializer-only path” tends to split the codebase into inconsistent creation patterns.

---

### 6) **Object initializers + `required` (ordering and pitfalls)**
Object initializers are not atomic. Mechanically, it is:
1) constructor runs
2) then member assignments run

That creates pitfalls:
- If your type is observable (events, virtual calls, multi-thread publication) before assignments, another component can see a partially initialized object.
- If a setter throws mid-initializer, the object exists but is partially assigned.

See section **4.1** for the canonical object initializer mechanics and correctness hazards.

---

### 7) **Versioning/public API considerations (additive vs breaking changes)**
Initialization contracts are part of your API surface:

- Adding a new constructor overload is usually **additive**.
- Changing the meaning of an existing constructor parameter is a **behavioral breaking change**.
- Adding a `required` member can be a **source-breaking change** for consumers (they must update object creation).

**Mentor guidance**
- For libraries, be extremely cautious with `required` changes: it’s an ecosystem-wide refactoring trigger.

---

### 8) **Performance notes (what is “just syntax” vs what allocates)**
- Primary constructors are mostly **syntax**; they don’t magically allocate less.
- The allocations come from:
  - what you do inside initialization (LINQ, closures, `params`, string building),
  - object graphs you build,
  - throwing exceptions on hot paths.

**Performance note**
- Prefer keeping creation cheap and pushing expensive work behind explicit methods when it impacts p95/p99 latency.

---

### 9) **Common pitfalls and mentor rules**
- **Using `required` as validation**: it only enforces “was assigned”, not “is correct”.
- **Struct invariants**: don’t pretend `required`/constructors make `default(T)` go away.
- **Too-clever primary constructors**: if you need complex logic, make it explicit; readability beats syntactic density.
- **Mixing many creation styles**: choose one main contract per type to keep the codebase consistent.
