### 1) **Static constructor semantics (what the runtime guarantees)**
A static constructor is the runtime’s one-time initialization hook for a type:

- Declared as `static MyType() { ... }`.
- Runs **at most once** per type (per `AssemblyLoadContext`).
- Runs **thread-safely**: other threads attempting to use the type wait until the initializer completes.
- If it throws, the type becomes **unusable** in that load context: future touches throw `TypeInitializationException`.

**Mentor note**
- A static constructor is effectively “hidden code executed somewhere before first use”. That makes it *high impact* for reliability and tail latency.

---

### 2) **Timing: first-touch cost, `beforefieldinit`, and predictability**
Static initialization can run at the first “touch” of a type:

- Accessing a static member
- Creating the first instance
- Or **earlier** than you expect when the type is marked `beforefieldinit` (when there is no explicit `static` constructor)

**Good to know**
- If cold-start predictability matters (server apps), prefer **explicit initialization at startup** over relying on “first use” in a random request path.

---

### 3) **Failure modes: `TypeInitializationException` and “poisoned” types**
If static initialization throws:

- The runtime wraps it in `TypeInitializationException`.
- The type is considered failed; future uses keep throwing.

**Mentor rule**
- Never put “might fail due to environment” work in a static constructor (network, disk, configuration discovery). Move that into explicit startup code where you can handle failures and retries intentionally.

---

### 4) **Deadlock and reliability pitfalls (locks, async blocking, cycles)**
Static initialization is a classic source of deadlocks because it can involve:

- Taking locks that other code also takes during type initialization
- Type initialization cycles (Type A initializes Type B; Type B initializes Type A)
- Blocking on async (`.Result` / `.Wait()`), which can deadlock (especially (frontend) UI apps) and can cause ThreadPool starvation on servers

**Good to know**
- Static initialization is effectively global state. Treat it with the same caution you treat singletons and static caches.

---

### 5) **Preferred patterns (in order)**
Use these patterns depending on cost and predictability needs:

1) **Simple `static readonly`** for cheap deterministic initialization.
2) **`Lazy<T>`** when initialization is expensive and might not be needed.
3) **Explicit initialization at app startup** when you want predictable cold-start behavior and error handling.

For code patterns and trade-offs, see the canonical file referenced above (`Fields` → static initialization).

---

### 6) **Performance notes (p99 latency, memory retention, contention)**
- Static initialization cost often shows up as **p99 latency spikes** when it happens on demand.
- Static objects become **GC roots** and can retain memory for the entire process lifetime.
- Poorly implemented lazy init can create **contention** under load.

**Performance note**
- If initialization is expensive, prefer explicit warm-up at startup so you control *when* you pay the cost.
