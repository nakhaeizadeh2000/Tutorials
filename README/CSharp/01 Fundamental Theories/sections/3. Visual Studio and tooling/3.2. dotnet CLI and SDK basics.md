## 3.2. dotnet CLI + SDK: restore/build/test/run/publish

1. **Build pipeline (`restore`, `build`, `test`; `run` vs `publish`; Debug vs Release pitfalls)**
2. **Package management (central package mgmt; lock files; vulnerability scanning/supply-chain hygiene)**
3. **Performance-first guidance (fast inner loop; trimming/AOT only when it fits; publish settings as hypotheses)**

### 1) **Build pipeline**
**Definition (what each command really means)**
- `dotnet restore`: resolves NuGet dependencies and writes the assets file (for SDK-style projects). It’s about **dependency resolution**, not compilation.
- `dotnet build`: compiles projects using MSBuild. It will restore implicitly unless you pass `--no-restore`.
- `dotnet test`: builds (unless `--no-build`) and runs tests via a test host (and typically produces TRX or other outputs).
- `dotnet run`: a *developer convenience* that builds + runs (usually **Debug** by default).
- `dotnet publish`: produces a deployable output (and is where “deployment knobs” apply: trimming, single-file, ReadyToRun, AOT, RID).

**When to use**
- **Local inner loop**:
  - `dotnet test` (fast correctness feedback)
  - `dotnet run` (quick manual checks)
- **CI**:
  - `dotnet restore --locked-mode` (if you use lock files)
  - `dotnet build -c Release`
  - `dotnet test -c Release`
- **Release**:
  - `dotnet publish -c Release` (use explicit publish settings)

**Common mistakes**
- Treating Debug results as “performance truth.”
  - Debug disables/changes optimizations and can change timing enough to hide races or create them.
- Relying on implicit restore/build in CI (harder to reason about caching and failure modes).
- Publishing without pinning runtime/architecture (`-r linux-x64`, `-r win-arm64`), then discovering native deps break at runtime.

**Minimal, runnable example (a safe default CI flow)**

```bash
dotnet restore --locked-mode
dotnet build -c Release --no-restore
dotnet test  -c Release --no-build
```

**Performance note**
- Use `-c Release` when measuring anything beyond correctness. Also separate cold start vs steady-state (see [2.2](<../2. NET architecture/2.2. IL JIT tiered compilation AOT.md>) for tiered compilation and AOT discussion).

### 2) **Package management**
**Modern defaults (C# 15-era)**
- Prefer **Central Package Management** (`Directory.Packages.props`) for multi-project repos:
  - One place to pin versions; fewer mismatches; easier upgrades.
- Prefer **lock files** for repeatable restores when you need reproducibility:
  - Enable with `RestorePackagesWithLockFile` and use `--locked-mode` in CI.
- Treat packages as a supply-chain surface:
  - Use `dotnet list package --vulnerable` routinely.

**Trade-offs**
- Central management adds a small learning curve, but drastically reduces “dependency drift.”
- Lock files improve reproducibility but require deliberate update workflows.

**Common mistakes**
- Floating versions in libraries (creates hard-to-diagnose downstream breaks).
- Unbounded transitive dependencies (huge graphs, trimming/AOT friction, slower restore/build).

**Good to know**
- The **SDK version** can affect restore/build outcomes. Keep a `global.json` in repos where determinism matters.

### 3) **Performance-first guidance**
**Mental model**
- Build/publish settings are **hypotheses**. Turn them on only with a measured reason (startup time, memory, artifact size).

**High-signal knobs (overview; deep details live in [2.4](<../2. NET architecture/2.4. Deployment and versioning model.md>))**
- **ReadyToRun**: improves startup at the cost of size; may affect steady-state depending on workload.
- **Trimming**: reduces size; requires discipline around reflection/dynamic code.
- **Single-file**: packaging convenience; can have extraction/dynamic loading caveats.
- **Native AOT**: best startup/memory profile for some scenarios; imposes feature constraints.

**Mentor notes**
- Optimize the big rocks first: **allocations**, **I/O**, **contention**, and **algorithmic complexity**. Publish knobs are not a substitute for good architecture.
- Avoid “async-over-sync” hacks (`Task.Run` around blocking I/O) unless you’re deliberately isolating a legacy dependency.
