## 3.1. Visual Studio: projects, solutions, and debugging model

1. **Solutions and projects (`.sln` vs SDK-style `.csproj`; multi-targeting; build configurations)**
2. **Debugging essentials (breakpoints; exception settings; CPU/memory/async profilers)**
3. **Mentor notes (debug vs prod behavior; reproducible perf tests; IDE + `dotnet` CLI proficiency)**

### 1) **Solutions and projects**
**Definition**
- A **project** (`.csproj`) is the unit of compilation: it defines **target frameworks**, **dependencies**, **build properties**, and outputs.
- A **solution** (`.sln`) is an **IDE/workspace grouping**: it collects projects for navigation and coordinated builds, but it is *not* the authoritative build definition (the `.csproj` is).
- **SDK-style** projects (modern .NET) are the default and should be considered “production standard” unless you are maintaining legacy `.NET Framework` code.

**When to use / how to structure**
- **One project per deployable** (service/app) is a good default; add class library projects only when you need a stable boundary (versioning, reuse, or build-time isolation).
- Prefer **PackageReference** and modern SDK-style conventions (implicit compile includes, `Directory.Build.props`, `Directory.Packages.props`).
- Use **multi-targeting** when you truly need it (e.g., library targeting both `net8.0` and `net9.0`), but don’t multi-target apps “just in case” (it increases testing surface).

**Trade-offs and common mistakes**
- **Mistake**: treating `.sln` as the build contract. CI should build from projects/solution consistently, but the truth is in MSBuild project files.
- **Mistake**: coupling build configuration names with environment meaning (“Debug = dev, Release = prod”).  
  - You can run Release locally and you can build Debug in CI; configuration is *a set of compiler/JIT-relevant knobs*, not your environment.
- **Mistake**: leaking platform-specific settings into general libraries (e.g. setting `RuntimeIdentifier` in a reusable class library).

**Good to know**
- Prefer **`Directory.Build.props`** for shared MSBuild properties and **`Directory.Packages.props`** for centralized version management (see [3.2](<./3.2. dotnet CLI and SDK basics.md>)).
- Keep `InternalsVisibleTo` decisions explicit and documented; it’s a strong coupling between assemblies.

### 2) **Debugging essentials**
**Breakpoints and stepping**
- Use **conditional breakpoints** and **tracepoints** to avoid recompiling or spamming logs.
- Prefer **“Just My Code” off** when you need to see framework-level behavior (but remember it adds noise).

**Exception settings (mentor-critical)**
- Turn on **break on thrown** for the exception types you’re investigating (especially `NullReferenceException`, `InvalidOperationException`, `ObjectDisposedException`).
- Understand that exceptions are **control-flow poison**: they are expensive and obscure intent. Use them for *exceptional* cases, not expected branches.

**Async debugging**
- Use the **Tasks** window and **Parallel Stacks** to understand continuations and deadlocks.
- A classic deadlock pattern is blocking on async with `.Result`/`.Wait()` on a context-bound thread (frontend/UI or ASP.NET legacy). In modern server code, it’s still harmful due to thread pool starvation.

**Profiling (CPU/memory/async)**
- **CPU profiler**: good for hot-path identification; validate with Release + representative inputs.
- **Memory profiler**: find allocation sources, retention graphs, and LOH pressure.
- **Async profiler**: identify blocked ThreadPool threads, sync-over-async, and “too many tasks”.

**Performance note**
- Always profile in **Release**, ideally with:
  - identical environment variables
  - representative container limits (CPU quota affects ThreadPool heuristics)
  - realistic data sizes

### 3) **Mentor notes**
**Debug vs production behavior**
- Debug builds disable many optimizations; timing, inlining, and allocation patterns change. Treat Debug as a *correctness* tool, not a performance signal.
- JIT tiering and PGO can make “first request” behavior very different from steady-state. See section **2.2** for the full treatment.

**Reproducible performance tests**
- Don’t “eyeball” performance. Use:
  - `BenchmarkDotNet` for microbenchmarks
  - load tests for service-level metrics (p95/p99)
  - `dotnet-counters` / `dotnet-trace` / `dotnet-gcdump` for runtime signals

**IDE + CLI proficiency**
- Treat the IDE as an accelerator, not a dependency. If you can’t do `restore/build/test/publish` via `dotnet`, you will struggle in CI/CD and containers. Section **3.2** is the deep CLI reference.
