## 4.2. Object lifetime and resource management

1. **GC vs deterministic cleanup (GC doesn’t close handles; `IDisposable`/`using`; `IAsyncDisposable`/`await using`)**
2. **Ownership boundaries (who creates/disposes; shared mutable state strategy; composition root/DI patterns)**
3. **Good to know (finalizers as last resort; pools/caches pressure; timeouts + cancellation as lifetime concerns)**

### 1) **GC vs deterministic cleanup**
**Definition**
- The **GC** manages *memory* for managed objects. It does **not** manage *external resources* (file handles, sockets, OS mutexes, database connections, native memory) unless you explicitly tie cleanup to those objects.
- **Deterministic cleanup** means you choose *exactly when* to release a resource, typically via `IDisposable`/`using` or `IAsyncDisposable`/`await using`.

**When to use**
- Implement **`IDisposable`** when your type owns:
  - OS handles (files, sockets), timers, `CancellationTokenSource`, `HttpResponseMessage`/`HttpContent`, `Stream`, etc.
  - Large managed buffers that you want to return to a pool (`ArrayPool<T>`, `MemoryPool<T>`) deterministically.
- Implement **`IAsyncDisposable`** when cleanup requires **async I/O** (e.g., flushing an async stream, gracefully closing an async resource).

**Common mistakes (mentor highlights)**
- **Mistake**: “The GC will eventually close it.”  
  - That is a *resource leak* until “eventually.” Under load, it becomes “process ran out of handles/sockets.”
- **Mistake**: Disposing something you don’t own (double-dispose) or forgetting to dispose what you do own (leak).
- **Mistake**: Using `finalizer` as the primary cleanup path. Finalizers:
  - run on a special thread at an unpredictable time,
  - extend object lifetime,
  - increase GC work,
  - make latency less predictable.

**Modern patterns (C# 15 era)**
- Prefer **`using var`** and `await using var` for tight scopes.
- Prefer `DisposeAsync()` when available (e.g. `await using` on streams/resources that support it).
- Prefer “owning wrapper types” that make ownership explicit and hard to misuse.

**Code example: correct ownership + sync/async disposal**

```csharp
using System;
using System.IO;
using System.Text;
using System.Threading.Tasks;

static async Task WriteTextAsync(string path, string text)
{
    // Owns the file handle => must be disposed deterministically.
    await using var stream = new FileStream(
        path,
        FileMode.Create,
        FileAccess.Write,
        FileShare.None,
        bufferSize: 64 * 1024,
        options: FileOptions.Asynchronous | FileOptions.SequentialScan);

    var bytes = Encoding.UTF8.GetBytes(text);
    await stream.WriteAsync(bytes);
}

await WriteTextAsync("out.txt", "hello");
```

**Performance note**
- Disposal is not only correctness—it's performance:
  - releasing sockets promptly reduces connection churn and TIME_WAIT buildup,
  - returning buffers to pools reduces GC pressure,
  - closing file handles reduces kernel contention under load.

### 2) **Ownership boundaries**
**Definition**
Ownership answers:
- **Who creates** the resource?
- **Who disposes** the resource?
- **Who is allowed to share** it?

In production systems, most lifetime bugs are *ownership bugs*, not language bugs.

**Guidelines that scale**
- **“Creator owns”** is a good default (the code that constructs disposes).
- If you pass an `IDisposable` into a component, decide and document whether that component:
  - **takes ownership** (it will dispose), or
  - **borrows** it (it must not dispose).
- Prefer APIs that *make ownership obvious*:
  - Accept factories instead of instances when you want to create/own internally.
  - Use `Stream` vs `Func<Stream>` depending on who owns the stream.

**Common mistakes**
- Hiding ownership in DI containers: registering a disposable as singleton and also disposing manually.
- Exposing raw mutable collections/buffers: callers mutate, and you lose invariants (and thread-safety).

**Code example: borrowing vs owning expressed in API**

```csharp
using System;
using System.IO;
using System.Text;

sealed class CsvWriter : IDisposable
{
    private readonly TextWriter _writer;
    private readonly bool _ownsWriter;

    public CsvWriter(TextWriter writer, bool ownsWriter = false)
    {
        _writer = writer ?? throw new ArgumentNullException(nameof(writer));
        _ownsWriter = ownsWriter;
    }

    public void WriteRow(ReadOnlySpan<string> cells)
    {
        for (var i = 0; i < cells.Length; i++)
        {
            if (i != 0) _writer.Write(',');
            _writer.Write(cells[i]);
        }
        _writer.WriteLine();
    }

    public void Dispose()
    {
        if (_ownsWriter) _writer.Dispose();
    }
}

using var file = new StreamWriter("data.csv", append: false, Encoding.UTF8);
using var csv = new CsvWriter(file, ownsWriter: false); // Borrowing: file disposed by caller.
csv.WriteRow(["id", "name"]);
csv.WriteRow(["1", "Ada"]);
```

**Good to know**
- For shared resources, consider “lifetime = process” singletons (e.g., `HttpClient`) with controlled shutdown.
- For per-request/per-operation resources, enforce scope at boundaries (web request scope, job scope).

### 3) **Good to know**
**Finalizers: last resort**
- Only use a finalizer if you wrap **native resources** and must provide a safety net.
- If you do, implement the full dispose pattern carefully; otherwise, prefer `SafeHandle`-based wrappers.

**Pooling and caching**
- Pools are not “free performance”:
  - they increase complexity and can increase memory retention.
- Start with “reduce allocations” before introducing pools. When you do pool:
  - cap sizes,
  - clear sensitive data,
  - monitor with metrics (GC, allocations, working set).

**Timeouts and cancellation as lifetime concerns**
- A resource that can block indefinitely is a resource you can’t reason about.
- Propagate `CancellationToken` through I/O APIs and enforce timeouts at boundaries (HTTP clients, DB calls, queue operations).
