## 1.4. .NET product evolution: Framework → Core → unified .NET

1. **Why .NET Framework is legacy now (Windows-only, GAC, servicing model; AppDomains context)**
2. **What .NET Core changed (cross-platform, side-by-side runtimes, modern hosting + dependency model, `dotnet` tooling)**
3. **Unified .NET (workloads; publish-time features like trimming/single-file/R2R/AOT; upgrade-driven perf gains)**

### 1) **Why .NET Framework is legacy now**
**Definition**
- **.NET Framework** is the original Windows-only runtime + BCL line. It is in **maintenance mode**: security and reliability fixes, but no meaningful new performance/runtime feature work compared to modern .NET.

**Why it matters (architect view)**
- Choosing .NET Framework today usually means accepting:
  - **Windows-only** hosting.
  - A **servicing model** that doesn’t deliver the same pace of runtime/JIT/GC improvements as modern .NET.
  - A shrinking ecosystem of “first-class” support (libraries/test infra/new runtime features focus on modern .NET).

**Key legacy concepts you’ll still encounter**
- **GAC (Global Assembly Cache)**: machine-wide assembly store; historically used for shared components. Modern .NET favors **app-local** dependencies and **NuGet restore**.
- **Assembly binding redirects** (`app.config` / `web.config`): used to coerce assembly version unification at runtime. Modern .NET uses `deps.json` + deterministic resolution (see **2.1**).
- **AppDomains**: used historically for isolation/unloading. Modern .NET removed most AppDomain-based isolation; use **process isolation** or **AssemblyLoadContext** (see **2.1** for deep loader material).

**Common mistake**
- “We’re stable on .NET Framework; upgrading is only risk.”  
  - In practice, *not upgrading* is risk too: you miss security hardening, GC/JIT improvements, better diagnostics, and modern deployment primitives.

**Note:**
- If you must integrate with a .NET Framework system, design a boundary: **out-of-proc** (HTTP/gRPC/queues) is often more maintainable than in-proc interop.

### 2) **What .NET Core changed**
**Core shifts**
- **Cross-platform**: Linux/macOS became first-class.
- **Side-by-side runtimes**: apps can carry their own runtime version (self-contained) or rely on a shared installed runtime (framework-dependent).
- **Modern hosting model**: `dotnet` host + standardized startup pipeline.
- **NuGet-first dependency model** with `deps.json`, eliminating most of the redirect-era pain.

**Operational impact (important)**
- You can move from “machine configuration” deployments to **artifact-based** deployments:
  - The deployed files fully describe the app + dependencies.
  - Reproducibility improves (when you pin packages and use lock files—see **3.2**).

**Trade-offs**
- Faster evolution means:
  - You should plan for **regular upgrades** (especially for server apps).
  - You must be mindful of **publish settings** (trimming/AOT can break reflection-heavy code).

**Good to know**
- Many “it got faster” stories are actually: newer runtime + improved GC/JIT + better libraries, *not* a magic compiler flag.

### 3) **Unified .NET**
**What “unified .NET” means**
- Starting with .NET 5, the product line converged into a single “modern .NET” platform:
  - Multiple app models (ASP.NET Core, worker, desktop, MAUI) share the same base runtime and libraries.
  - “Workloads” are delivered via the SDK for optional stacks (mobile, WASM, etc.).

**Publish-time features you should understand (modern defaults vary by app model)**
- **Trimming**: removes unused code at publish time; great for size but risky with reflection/dynamic patterns.
- **Single-file**: bundles most managed dependencies; useful for deployment ergonomics.
- **ReadyToRun (R2R)**: precompiles parts of IL to native code to improve startup; larger binaries, sometimes lower peak throughput.
- **Native AOT**: produces a native executable with aggressive trimming; best for fast startup/low memory footprint in certain workloads, but has feature constraints (see **2.2** for deep analysis).

**Mentor advice**
- Treat publish options as **measurable knobs**:
  - You’re trading **startup vs throughput vs size vs compatibility**.
  - Measure using representative workloads, not microbenchmarks.

**Performance note**
- The most impactful “upgrade” for many services is simply moving to a newer runtime baseline and re-testing: GC heuristics, ThreadPool tuning, HTTP stack improvements, and JIT changes compound.
