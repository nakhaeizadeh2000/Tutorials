## 5.1. Namespaces vs folders vs assemblies

1. **Namespace rules (avoid leaking internals; keep namespaces stable; avoid mega-namespaces)**
2. **Assembly boundaries (split vs single project; versioning blast radius; internals visibility/testing)**
3. **Mentor notes (maintainability first; small coherent public API; explicit deps and no cycles)**

### 1) **Namespace rules**
**Definition**
- A **namespace** is a *logical* name that scopes types (`namespace Company.Product.Feature;`). It is not a runtime boundary and it is not a deployment boundary.
- Namespaces primarily serve **discoverability**, **API organization**, and **name collision avoidance**.

**When to use / design goals**
- **Public libraries**: namespaces are part of your **public API surface**. Treat them as stable and intentionally designed.
- **Applications**: namespaces help architecture readability and navigation (IDE search, analyzers, docs).

**Rules of thumb (modern C#)**
- Prefer **file-scoped namespaces**:

```csharp
namespace Contoso.Billing.Invoices;

public sealed class InvoiceService { }
```

- Keep namespaces **cohesive**: a namespace should describe a concept (“Invoices”), not an implementation detail (“Helpers”).
- Avoid “mega-namespaces” that turn into dumping grounds (`Company.Product.Common`). Split by domain area instead.
- Avoid **leaking internals** through naming: if it’s an internal implementation, don’t put it in a public-sounding namespace.

**Common mistakes**
- Using folders as the “real structure” and letting namespaces drift randomly. This makes navigation and docs painful.
- Namespace churn: renaming namespaces frequently breaks source compatibility and forces churn across repos.

**Good to know**
- Folders and namespaces often align for sanity, but they don’t have to. Favor **conceptual clarity** over strict mirroring.

### 2) **Assembly boundaries**
**Definition**
- An **assembly** (`.dll`/`.exe`) is the unit of:
  - **Compilation** (what the compiler produces)
  - **Loading** (what the runtime loads)
  - **Versioning** (what gets updated as a unit)
  - **Trimming/AOT analysis** (what tooling treats as an analysis boundary)

**When to split vs keep together**
- **Split into multiple assemblies** when you need:
  - Clear architectural boundaries (e.g., `Domain`, `Infrastructure`, `Api`)
  - Different deployment cadence or versioning blast radius
  - Optional features/plugins
  - Isolation of heavy dependencies
- **Keep one assembly** when:
  - The code is tightly coupled and will evolve together
  - You want faster builds and simpler packaging

**Trade-offs**
- **More assemblies**:
  - **Pros**: clearer boundaries, smaller change impact, better dependency hygiene
  - **Cons**: more project files, slower builds/restore, more versioning surface
- **Fewer assemblies**:
  - **Pros**: simpler repo ergonomics
  - **Cons**: dependency sprawl, harder-to-enforce boundaries, larger “blast radius”

**Internals visibility and testing**
- Prefer keeping implementation types `internal` and exposing small public interfaces.
- If you must test internals, use `InternalsVisibleTo` intentionally (don’t default to “everything public for tests”).

### 3) **Mentor notes**
**Maintainability first**
- Namespaces are for humans; assemblies are for **runtime + packaging + governance**. Don’t confuse them.
- A clean public surface typically means:
  - Few public types
  - Predictable namespaces
  - Clear versioning story

**Explicit dependencies, no cycles**
- Enforce dependency direction (e.g., `Domain` does not depend on `Infrastructure`).
- Avoid circular project references; they are architectural debt that grows.

**Performance note**
- Most runtime performance issues do not come from “too many namespaces.” They come from allocations, I/O, and synchronization.
- Assembly design does matter indirectly for **build time**, **startup/publish (trimming/AOT)**, and operational complexity. Keep it intentional.
