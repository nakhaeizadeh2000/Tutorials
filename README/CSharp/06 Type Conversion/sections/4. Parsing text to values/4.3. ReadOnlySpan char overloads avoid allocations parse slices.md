## 4.3. `ReadOnlySpan<char>` overloads (avoid allocations, parse slices)

1. **Why spans help** (parse substrings without creating new strings)
2. **When you actually get spans** (slicing buffers, `String.AsSpan`, parsers/tokenizers)
3. **TryParse span overloads** (numeric types, `Guid`, etc. — where available)
4. **Avoiding intermediate allocations** (no `Split` + parse loops in hot paths)
5. **Practical patterns** (scan → slice span → `TryParse` with explicit culture)

---

### 1) **Why spans help** (parse substrings without creating new strings)

**Definition**

`ReadOnlySpan<char>` is a **stack-only view** over a contiguous region of characters. It lets you “point at” a slice of an existing string/buffer without allocating a new string.

This matters because many parsing workloads are dominated not by the numeric conversion itself, but by:

- allocating substrings (e.g., `text.Substring(...)`)
- allocating arrays (`Split`)
- allocating intermediate strings during tokenization

**Mentor stress**

- Use spans to **avoid allocations at boundaries** (parsing input text, protocol lines, logs, CSV/TSV, etc.).
- Keep span-based code **localized**. It’s great in hot parsing code; it’s often unnecessary in normal app logic.

**Performance note**

- Span-based parsing is primarily about **GC reduction** (fewer allocations), not about making `int.TryParse` itself faster.

---

### 2) **When you actually get spans** (slicing buffers, `String.AsSpan`, parsers/tokenizers)

You get spans in a few common situations:

- You have a `string` and you want to parse a slice:
  - `ReadOnlySpan<char> slice = text.AsSpan(start, length);`
- You’re building a tokenizer/scanner:
  - scan indices, then slice spans for each token
- You’re processing data that is already in buffers:
  - (advanced) `ReadOnlySpan<byte>` from IO, then decode or parse in a structured way (deep “bytes→chars” pipelines are outside this file)

**Example (runnable): slice without allocating**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        string line = "port=443;mode=prod";

        int start = "port=".Length;
        int end = line.IndexOf(';');
        ReadOnlySpan<char> portText = line.AsSpan(start, end - start);

        if (int.TryParse(portText, out int port))
            Console.WriteLine(port);
    }
}
```

**Good to know**

- `AsSpan()` does not allocate. The span is a small struct containing a reference + offset + length.
- Spans are **not safe to store** on the heap or across `await` boundaries. Keep them in synchronous methods or copy into a `string` if you must persist them.

### 3) **TryParse span overloads** (numeric types, `Guid`, etc. — where available)

Most core types provide `TryParse(ReadOnlySpan<char>, ...)` overloads (either directly or via overloads that accept span and provider/styles).

**Preferred shape for deterministic parsing**

- Use overloads that accept:
  - `NumberStyles` / `DateTimeStyles` (to define what you accept)
  - an explicit `IFormatProvider` (usually `CultureInfo.InvariantCulture` for non-UI data)

Example:

```csharp
using System;
using System.Globalization;

static class Demo
{
    static void Main()
    {
        ReadOnlySpan<char> text = "12345".AsSpan();

        if (int.TryParse(text, NumberStyles.Integer, CultureInfo.InvariantCulture, out int value))
            Console.WriteLine(value);
    }
}
```

**Legacy note**

- Avoid using culture-implicit overloads for wire formats. The deep reasoning and examples are in `4.2. Culture, IFormatProvider, and deterministic parsing`.

### 4) **Avoiding intermediate allocations** (no `Split` + parse loops in hot paths)

**The allocation-heavy pattern**

```csharp
// Avoid in hot paths:
// foreach (var part in line.Split(',')) { int.Parse(part); }
```

Problems:

- `Split` allocates an array and N substrings (unless using some newer overloads; still often allocates).
- `Parse` throws on invalid input (exceptions are expensive in repeated failure cases).

**Better pattern**

- Scan the string for separators.
- Slice spans for each token.
- Use `TryParse` on the span token.

**Example (runnable): comma-separated ints without Split**

```csharp
using System;
using System.Globalization;

static class Demo
{
    static void Main()
    {
        string csv = "10,20,300,-4";
        ReadOnlySpan<char> s = csv.AsSpan();

        int sum = 0;
        while (!s.IsEmpty)
        {
            int comma = s.IndexOf(',');
            ReadOnlySpan<char> token = comma >= 0 ? s[..comma] : s;

            if (!int.TryParse(token, NumberStyles.Integer, CultureInfo.InvariantCulture, out int value))
                throw new FormatException($"Invalid token: '{token.ToString()}'"); // exceptional here by policy

            sum += value;
            s = comma >= 0 ? s[(comma + 1)..] : ReadOnlySpan<char>.Empty;
        }

        Console.WriteLine(sum);
    }
}
```

**Performance note**

- This pattern avoids per-token allocations. In real parsers you’d also avoid `token.ToString()` on the failure path unless you truly need it.

### 5) **Practical patterns** (scan → slice span → `TryParse` with explicit culture)

**A mentor-grade recipe**

When you parse any “structured text” repeatedly (headers, config lines, protocol records):

1. **Define** what formats you accept (styles, culture, whitespace rules).
2. **Scan** the input (indices only).
3. **Slice** spans for tokens.
4. **TryParse** with explicit style/provider.
5. **Map** to a domain type once (see `6.2. Boundary types`).

**Common mistake**

- Parsing the same token multiple times (“just parse again here”). Parse once, store typed value.
