## 4.1. `Parse` vs `TryParse` (correctness, performance, and API shape)

1. **Exceptions are not control flow** (especially in loops / high-volume ingestion)
2. **Try-pattern shape** (return bool + `out` value; predictable and branch-friendly)
3. **Defaulting strategy** (don’t silently coerce invalid input unless the domain demands it)
4. **Validation boundaries** (parse at the edges, keep domain types strong)
5. **Testing strategy** (table-driven tests for formats, ranges, and cultures)

---

### 1) **Exceptions are not control flow** (especially in loops / high-volume ingestion)

**Definition**

Many parsing APIs come in two shapes:

- **Throwing**: `int.Parse(...)`, `DateTimeOffset.Parse(...)`, `Guid.Parse(...)`
- **Non-throwing Try-pattern**: `int.TryParse(...)`, `DateTimeOffset.TryParse(...)`, `Guid.TryParse(...)`

The throwing APIs are correct when failure is *exceptional* (programmer error, corrupted invariant, unexpected state). They are a poor fit when you’re validating user input, reading untrusted data, or processing high-volume streams where malformed values are expected.

**Why exceptions are a bad fit for expected failures**

- **CPU**: throwing an exception is expensive (stack capture, unwinding).
- **JIT/branching**: the “exceptional” path is not optimized for repeated use.
- **Observability**: exception-driven validation can flood logs/telemetry if you accidentally catch and log.

**Mentor rule**

- If the input can be wrong as part of normal operation, **do not use exceptions to decide the branch**. Use `TryParse` or a result type.

**Example (runnable)**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        foreach (var s in new[] { "42", "oops", "100" })
        {
            if (int.TryParse(s, out var value))
                Console.WriteLine($"ok: {value}");
            else
                Console.WriteLine($"invalid: '{s}'");
        }
    }
}
```

**Good to know**

- Some teams still use `Parse` inside a `try/catch` for “simplicity”. That simplicity disappears the moment you profile a hot path or you need deterministic error handling. Prefer `TryParse` for expected failures.

---

### 2) **Try-pattern shape** (return bool + `out` value; predictable and branch-friendly)

**What the pattern gives you**

The Try-pattern is a *contract*:

- returns `true` and sets `out value` to a valid result
- returns `false` and sets `out value` to a safe default (often `default`)

This API shape is:

- **easy to use correctly** (`if (TryX(..., out var v)) { ... }`)
- **fast** (no exceptions)
- **composable** (you can chain validations cleanly)

**Example: parse + validate range**

```csharp
using System;

static class Demo
{
    static bool TryParsePort(string text, out ushort port)
    {
        if (!int.TryParse(text, out var tmp) || (uint)tmp > 65535u)
        {
            port = default;
            return false;
        }

        port = (ushort)tmp;
        return true;
    }

    static void Main()
    {
        Console.WriteLine(TryParsePort("443", out var p) ? p : "invalid");
    }
}
```

**Performance note**

- The performance win is not the `out` parameter; it’s **avoiding exceptions** and keeping the failure path predictable.

See also: the language meaning of `out` is covered in [6.3. out parameters multiple returns Try patterns](<../../../05 Methods/sections/6. Parameter modifiers and ref-like patterns/6.3. out parameters multiple returns Try patterns.md>) (this file focuses on parsing decisions, not `out` mechanics).

### 3) **Defaulting strategy** (don’t silently coerce invalid input unless the domain demands it)

**The trap**

It’s tempting to write:

- “If parsing fails, treat it as 0”
- “If parsing fails, treat it as empty string”

This can quietly convert bad input into *valid-looking* data and can create security and correctness issues (e.g., defaulting an invalid price to 0).

**Better strategies**

- **Reject** invalid input and return a validation error.
- **Use a nullable** (`int?`) to represent “missing” but still reject malformed (`"abc"`).
- **Use a domain result type** when you need rich error information.

**Example: differentiate missing vs malformed**

```csharp
using System;

static class Demo
{
    static bool TryParseOptionalInt(string? text, out int? value)
    {
        if (string.IsNullOrWhiteSpace(text))
        {
            value = null; // missing
            return true;
        }

        if (!int.TryParse(text, out var parsed))
        {
            value = null; // malformed
            return false;
        }

        value = parsed;
        return true;
    }
}
```

**Mentor stress**

- Defaulting is a *business decision*, not a parsing convenience. Make it explicit and test it.

### 4) **Validation boundaries** (parse at the edges, keep domain types strong)

**Core idea**

Parsing is a boundary concern. You want to do it:

- **once**
- **close to the input**
- with the right **culture and styles** (see [4.2](<./4.2. Culture IFormatProvider and deterministic parsing.md>) for the deep treatment)

Then map into strong domain types so you don’t keep re-parsing and re-validating inside your core logic.

**Example: boundary mapping**

```csharp
using System;

public readonly record struct Port(ushort Value)
{
    public override string ToString() => Value.ToString();

    public static bool TryCreate(string text, out Port port)
    {
        if (!int.TryParse(text, out var tmp) || (uint)tmp > 65535u)
        {
            port = default;
            return false;
        }

        port = new Port((ushort)tmp);
        return true;
    }
}
```

See also: `6.2. Boundary types: parse once, validate once, carry a strong type` (full domain-modeling discussion belongs there).

### 5) **Testing strategy** (table-driven tests for formats, ranges, and cultures)

**What to test**

Parsing code breaks in production for a few repeatable reasons:

- **format drift** (extra spaces, separators, leading signs, unexpected decimals)
- **range** (min/max, overflow)
- **culture** (`,` vs `.`, month/day order, time zones)

**Table-driven testing (good habit)**

Even without showing a full test framework here, the idea is to build a table of input → expected outcome. For real code, put it in unit tests and include representative cultures (see [4.2](<./4.2. Culture IFormatProvider and deterministic parsing.md>)).

**Example (runnable “mini test” in a console app)**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        (string Input, bool Ok, int Value)[] cases =
        [
            ("0", true, 0),
            ("-1", true, -1),
            (" 42 ", true, 42),
            ("oops", false, 0),
            ("999999999999", false, 0), // overflow
        ];

        foreach (var c in cases)
        {
            var ok = int.TryParse(c.Input, out var v);
            if (ok != c.Ok || (ok && v != c.Value))
                throw new Exception($"Case failed: '{c.Input}'");
        }

        Console.WriteLine("All cases passed.");
    }
}
```

**Performance note**

- Tests also protect performance decisions: when you choose `TryParse` + span overloads, you can add a small benchmark later, but correctness tests come first.
