## 7.1. Type conversion checklist: correctness, performance, and maintainability

1. **Never use exceptions for expected input validation**
2. **Be explicit about culture and styles for parsing/formatting**
3. **Avoid silent lossy conversions in business logic**
4. **Watch for hidden allocations** (boxing, string slicing/copies, `Split`)
5. **Prefer conversions at boundaries** (UI/API/IO) not deep in the domain model

---

### 1) **Never use exceptions for expected input validation**

**Why mentors insist on this**

Exception-based validation:

- is **slow under repeated failure** (CPU + stack capture + unwinding)
- is **noisy** (logs/telemetry get polluted when someone “helpfully” logs exceptions)
- creates **hard-to-reason** control flow (failure paths aren’t explicit)

**Use instead**

- `TryParse` / `TryParseExact` for parsing (deep treatment: `4.1`, `4.2`)
- Try-pattern (`TryX(..., out ...)`) for lookups and conversions (see also the language `out` mechanics in `README/CSharp/05 Methods/sections/6. Parameter modifiers and ref-like patterns/6.3. out parameters multiple returns Try patterns.md`)
- result types when the caller must know “why” (see `6.2`)

**Good to know**

- Throwing is fine when the input is supposed to be **impossible** (violated invariant). Don’t ban exceptions; ban *exceptions as a normal branch*.

---

### 2) **Be explicit about culture and styles for parsing/formatting**

**Checklist**

- If it’s **user-facing UI**, use `CultureInfo.CurrentCulture` and produce friendly errors.
- If it’s **protocol/storage/log contract**, use:
  - `CultureInfo.InvariantCulture`
  - explicit `NumberStyles` / `DateTimeStyles`
  - often `TryParseExact` / `ParseExact` with a documented format

**Single source of truth**

See `4.2. Culture, IFormatProvider, and deterministic parsing` for full examples and the “user input vs wire format” split.

---

### 3) **Avoid silent lossy conversions in business logic**

**Loss can happen in multiple ways**

- numeric narrowing (`long` → `int`, `double` → `int`)
- floating-point rounding/precision (`double` cannot represent all integers exactly at large magnitudes)
- time-zone/offset loss (`DateTimeOffset` → `DateTime` without a clear policy)

**Mentor rule**

- If the conversion can lose information, make the policy **visible**:
  - explicit cast + `checked`
  - explicit range validation + Try-pattern
  - explicit rounding method (`Math.Round` with `MidpointRounding` choice)

**See**

- Overflow/checked/range checks: `3.1`
- Domain boundary types to avoid repeated lossy conversion: `6.2`

---

### 4) **Watch for hidden allocations** (boxing, string slicing/copies, `Split`)

**High-signal allocation sources in conversion code**

- **boxing**: value type → `object`/interface (deep treatment: `3.3`)
- `params object[]` / composite formatting (`string.Format`, some `Console.WriteLine` overloads)
- `Split`/`Substring` patterns in parsers (deep treatment + span alternative: `4.3`)

**Mentor habit**

- In hot paths, treat `object` and `params` as “allocation smells”.
- Use spans to slice tokens without allocating strings when you’re parsing many values.

---

### 5) **Prefer conversions at boundaries** (UI/API/IO) not deep in the domain model

**Why**

- conversion rules become centralized and testable
- domain code becomes simpler (works with validated types)
- you avoid repeated parsing and repeated validation

**Implementation pattern**

- parse/validate once at the edge
- map into a strong type (`record struct` / `readonly struct`)
- keep domain invariants inside the type

See: `6.2. Boundary types: parse once, validate once, carry a strong type`.
