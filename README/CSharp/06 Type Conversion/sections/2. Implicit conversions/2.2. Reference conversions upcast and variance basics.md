### 1) **Upcasting to base types/interfaces** (safe, common, and cheap)

**Definition**

An **upcast** converts a value of a *more specific* reference type to a *less specific* one:

- derived → base (`Dog` → `Animal`)
- concrete type → interface (`List<int>` → `IEnumerable<int>`)

This conversion is **always safe** (it can’t fail at runtime) because every `Dog` *is an* `Animal`.

**When to use**

- When you want **polymorphism**: call virtual/interface members without knowing the exact derived type.
- When you want to **reduce coupling**: accept interfaces (`IReadOnlyList<T>`, `IEnumerable<T>`, `IAsyncEnumerable<T>`) instead of concrete implementations.

**Trade-offs**

- You “forget” derived members (by design). If you frequently need derived-only behavior after an upcast, that’s a sign you should refactor:
  - add a virtual method
  - introduce a dedicated interface
  - use a discriminated shape (e.g., tagged union via inheritance + pattern matching)

**Example (runnable)**

```csharp
using System;
using System.Collections.Generic;

interface IAnimal
{
    string Speak();
}

sealed class Dog : IAnimal
{
    public string Speak() => "woof";
}

static class Demo
{
    static void Main()
    {
        Dog dog = new();

        // Upcast to interface (safe).
        IAnimal animal = dog;
        Console.WriteLine(animal.Speak());

        // Upcast to a more general abstraction for APIs.
        List<int> list = [1, 2, 3];
        IEnumerable<int> seq = list;
        foreach (var x in seq) Console.WriteLine(x);
    }
}
```

**Mentor stress**

- Prefer *accepting* abstractions (interfaces) in APIs, but be careful about *returning* overly broad abstractions if you need guarantees (ordering, count, index access). Use the most honest contract.

### 2) **Array covariance** (why it exists, why it can throw at runtime)

**What it is**

C# arrays are **covariant** for reference types: `Derived[]` is convertible to `Base[]`.

```csharp
string[] strings = ["a", "b"];
object[] objects = strings; // allowed (covariance)
```

**Why it can throw**

The runtime must protect the actual array element type. This can produce an **ArrayTypeMismatchException** at runtime:

```csharp
string[] strings = ["a"];
object[] objects = strings;
objects[0] = 123; // throws at runtime
```

**Mentor rule**

- **Avoid array covariance in application design**. Prefer generics (`IReadOnlyList<T>`, `T[]` kept strongly typed) or immutable/read-only abstractions.

**Performance note**

- Because array stores require runtime checks when using covariant references, you can get extra overhead and exceptions. It’s not your main performance lever, but it’s a correctness footgun.

### 3) **Generic variance** (`out`/`in` on interfaces and delegates; safe substitutability)

**Definition**

Generic variance lets you substitute generic interface/delegate types when it is **type-safe**:

- **Covariant** (`out T`): you can use a *more derived* `T` where a base `T` is expected.
- **Contravariant** (`in T`): you can use a *less derived* `T` where a more derived `T` is expected.

Classic examples:

- `IEnumerable<out T>` is covariant.
- `IComparer<in T>` is contravariant.
- Delegates often support variance on parameters/returns.

**Why it matters**

Variance gives you flexible APIs without unsafe casts:

```csharp
IEnumerable<string> s = ["a", "b"];
IEnumerable<object> o = s; // allowed because IEnumerable<out T>
```

**Trade-offs**

- Variance usually implies **read-only** views (covariant producers) or **write-only** roles (contravariant consumers). If a type both produces and consumes `T` (read/write), it’s typically invariant.

**Good to know**

- Variance is enforced at compile time and does **not** require per-element runtime checks like array covariance.

### 4) **Nullability and reference conversions** (nullable annotations vs runtime behavior)

**Key idea**

`string` vs `string?` is (mostly) a **static analysis contract**. At runtime they are both `System.String`.

**Mentor stress**

- Nullability is about **APIs and invariants**, not about “a different type at runtime”.
- A conversion like `string?` → `string` is *not* a runtime cast; it’s your promise you’ve validated or proved non-null.

Example:

```csharp
string? input = Console.ReadLine();
if (input is null) return;

string nonNull = input; // now safe; null-state analysis knows it
Console.WriteLine(nonNull.Length);
```

If you need a deep treatment of nullable reference types and API design, keep it in the type-system domain (not repeated here).

### 5) **Performance notes** (virtual dispatch vs devirtualization, interface calls)

**Reality check**

- Upcasts themselves are cheap.
- The cost, if any, is in **how you use the converted reference**:
  - virtual/interface dispatch
  - inability to inline in some polymorphic cases

**Good to know**

- Modern JITs can **devirtualize** and inline more than many developers expect (especially in sealed/internal contexts). Don’t micro-optimize away interfaces unless profiling shows it’s a hot spot.
- Prefer designing for correctness/maintainability first. Then measure.
