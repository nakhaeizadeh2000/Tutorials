### 1) **Widening vs narrowing** and what “no information loss” means in practice

**Definition**

- A **widening conversion** is one the language allows implicitly because it is *safe by rule* (not necessarily “perfect” in a mathematical sense). Typical examples:
  - `int` → `long`
  - `int` → `double`
  - `byte` → `int`
- A **narrowing conversion** can lose information (range, precision, or both) and therefore requires an **explicit cast**:
  - `long` → `int`
  - `double` → `int`
  - `decimal` → `double`

**What “no information loss” means (mentor clarification)**

This phrase is easy to misunderstand:

- For **integral widening** (e.g., `int` → `long`), it truly means the value is preserved exactly.
- For **integral → floating** (e.g., `int` → `double`), C# still allows it implicitly, but **not every integer is representable exactly** once you get large enough. So: “safe” here is about *range and typical expectations*, not about exactness for all values.

**When to use**

- Prefer widening conversions when you are:
  - **moving to a larger range** (`int` to `long`) to avoid overflow
  - preparing values for APIs that require a wider type

**Common mistakes**

- Assuming `double` can represent all `long` values exactly.
- Doing silent “widening” to floating types and later comparing for equality.

**Example (runnable)**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        int i = 123;
        long l = i;          // widening integral: exact
        double d = i;        // allowed implicitly, but not always exact for very large integers

        Console.WriteLine((l, d));
    }
}
```

**Good to know**

- If you care about decimal correctness (money/financial), prefer `decimal` over `double`/`float`. The “why” and the trade-offs are covered in item 5 below.

### 2) **Integral promotions** (why `byte + byte` becomes `int`)

**Definition**

C# performs **integral promotions** for many arithmetic operators:

- Smaller integral types (`sbyte`, `byte`, `short`, `ushort`, `char`) are promoted to `int` (or `uint`) before arithmetic.

This is why:

- `byte + byte` results in an `int`
- you can’t assign it back to `byte` without a cast (because the result might be > 255)

**Why the language does this**

- Keeps the operator set manageable (otherwise there would need to be a combinatorial explosion of overloads for every small integral type).
- Makes arithmetic consistent with the CPU’s natural word size and avoids surprising overflow during intermediate computations.

**Example (runnable)**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        byte a = 200;
        byte b = 30;

        int sum = a + b;     // int due to promotion
        Console.WriteLine(sum);

        // byte c = a + b;   // compile error
        byte c = checked((byte)(a + b)); // explicit + checked makes intent obvious
        Console.WriteLine(c);
    }
}
```

**Performance note**

- Promotions themselves are not your bottleneck. The real risk is **hidden narrowing** later or unchecked overflow.

### 3) **`char` conversions** (UTF-16 code unit; not “a letter”)

**Definition**

In .NET, `char` is a **16-bit UTF-16 code unit**, not a Unicode “character” in the human sense.

- `char` can be implicitly converted to numeric types like `int` (it’s essentially an unsigned 16-bit value).
- Many user-perceived characters (graphemes) require **multiple** UTF-16 code units (surrogate pairs, combining marks).

**When to use**

- Converting `char` → `int` is useful when you are working with code units:
  - ASCII/Latin checks
  - digit ranges (`'0'..'9'`)
  - low-level parsing

**Common mistakes**

- Treating `char` as “one user-visible character”.
- Using `char`-based indexing to slice strings in user-facing text (this can split surrogate pairs).

**Example (runnable)**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        char c = 'A';
        int codeUnit = c; // implicit
        Console.WriteLine(codeUnit); // 65

        // A single emoji can be multiple UTF-16 code units:
        string s = "😀";
        Console.WriteLine(s.Length); // 2 on UTF-16 because it's a surrogate pair
    }
}
```

**Good to know**

- For user-visible “characters”, you often want `Rune` or `TextElementEnumerator` (advanced text processing). That’s outside this domain; keep it as a reminder that `char` conversions are not “text correctness”.

### 4) **`nint`/`nuint` and platform width** (portability and interop)

**Definition**

`nint`/`nuint` are **native-sized integers**:

- 32-bit on x86
- 64-bit on x64/arm64

They’re useful for low-level work (interop, pointers, handles) where “pointer-sized” matters.

**When to use**

- Interop scenarios (`IntPtr`-like work) where you need arithmetic with pointer-sized values.
- Writing platform-aware low-level libraries.

**Trade-offs**

- **Portability**: behavior and range differ by process architecture.
- **Correctness**: converting `nint` to `int` can truncate on 64-bit.
- **Readability**: in application code, prefer explicit `long`/`int` unless pointer-sizing is actually required.

**Example (runnable)**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        nint size = IntPtr.Size; // 4 or 8
        Console.WriteLine(size);

        nint x = 123;
        long asLong = x; // implicit widening (native -> 64-bit signed)
        Console.WriteLine(asLong);
    }
}
```

**Good to know**

- `IntPtr`/`UIntPtr` exist for interop and are often what APIs expose. `nint`/`nuint` are language conveniences for the same idea.

### 5) **When “implicit” still surprises** (floating point precision, `decimal` rules)

Even when a conversion is implicit, the *resulting computations* may surprise you if you don’t know the numeric model.

**Floating point surprises (`float`/`double`)**

- `double` is binary floating point (IEEE 754). Many decimal fractions aren’t representable exactly.
- Implicit conversions to `double` can make subsequent equality comparisons unreliable.

**`decimal` surprises**

- `decimal` is base-10 oriented and great for financial correctness.
- But it’s typically slower than `double` and has different range/precision characteristics.

**Mentor rules**

- Prefer `decimal` for money; prefer `double` for scientific/continuous values where performance matters and rounding error is acceptable.
- Don’t compare floating values for exact equality unless you control the entire pipeline and know what you’re doing.

**Example (runnable)**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        double a = 0.1;
        double b = 0.2;
        Console.WriteLine(a + b == 0.3); // False (usually)

        decimal x = 0.1m;
        decimal y = 0.2m;
        Console.WriteLine(x + y == 0.3m); // True
    }
}
```

**Performance note**

- Most hot numeric code is dominated by algorithmic choices and data movement, not a single implicit cast. Focus on correctness first; optimize only after measuring.
