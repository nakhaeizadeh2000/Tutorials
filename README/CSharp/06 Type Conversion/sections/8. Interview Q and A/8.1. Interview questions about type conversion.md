### 1) **Implicit vs explicit conversions**

**Q: What’s the difference between implicit and explicit conversion in C#?**

**A:**

- **Implicit conversions** are conversions the compiler allows without a cast because the language rules deem them safe (e.g., `int` → `long`, derived → base reference). They do not indicate a “parse” or “validation”; they’re generally value-preserving or at least non-dangerous under the model.
- **Explicit conversions** require a cast because they can be **lossy** (precision/range) or **fail at runtime** (downcasts, unboxing). They make intent visible: “I accept the risk and I know what I’m doing.”

**Mentor angle:** “Implicit” does not mean “free of surprises” (e.g., integral → floating can lose precision for large values). Know your numeric model.

See full treatments:
- Implicit numeric rules: `2.1. Implicit numeric conversions and why they’re allowed`
- Explicit numeric casts + overflow: `3.1. Explicit numeric casts and overflow behavior`
- Safe downcasts: `3.2. Downcasts and safe casting patterns`

**Q: Does casting change the bits or the value?**

**A:** Normal casts change the **value** representation. Bit reinterpretation requires explicit APIs like `BitConverter.*Bits` (see `3.1`).

### 2) **`Parse` vs `TryParse`**

**Q: When should you use `Parse` vs `TryParse`?**

**A:**

- Use **`TryParse`** when invalid input is expected (user input, files, messages, configs). It avoids exceptions and makes the failure path explicit.
- Use **`Parse`** when invalid input indicates a bug or broken invariant (e.g., you’re parsing your own previously validated storage format and want fail-fast behavior).

**Mentor angle:** Exceptions are not control flow; repeated `try/catch` parsing can become a CPU hotspot and produce noisy telemetry.

### 3) **Boxing/unboxing and `object` conversions**

**Q: What is boxing and why does it matter?**

**A:**

- Boxing converts a value type to `object`/interface by allocating on the heap and copying the value.
- It matters in hot paths: extra allocations → more GC → latency/throughput impact.

**Q: Why does unboxing `object boxedInt = 1; long x = (long)boxedInt;` fail?**

**A:** Unboxing requires an **exact** value-type match. `boxedInt` contains an `int`, not a `long`. Unbox to `int` first, then convert.

### 4) **Culture pitfalls**

**Q: Why do parsing bugs show up only in production?**

**A:** Culture defaults differ across machines/containers/regions. If you parse/format using `CurrentCulture` implicitly, the same string can mean different values (decimal separators, date ordering).

**Mentor angle:** UI strings are localized; wire/storage formats should be deterministic contracts (often `InvariantCulture` + explicit format/styles).

See: `4.2. Culture, IFormatProvider, and deterministic parsing`.

### 5) **Design questions**

**Q: Where should conversions live in an application?**

**A:**

- **At boundaries** (UI/API/IO/config): parse/validate once; then map into strong domain types.
- **Inside the domain**: keep invariants; avoid repeated parsing and avoid “stringly typed” logic.

See: `6.2. Boundary types: parse once, validate once, carry a strong type`.

**Q: When are user-defined implicit conversions acceptable?**

**A:** Only when they are lossless, non-throwing, cheap, and unsurprising. Otherwise make them explicit or provide `TryCreate`/`TryParse`.

See: `6.1. User-defined implicit/explicit operators: when they help vs harm`.
