## 1.2. Categories of conversions you’ll use in real code

1. **Numeric conversions** (integral/floating/decimal; checked/unchecked)
2. **Reference conversions** (upcast/downcast, interface casts, pattern-based casting)
3. **Nullable conversions** (`T` ↔ `T?`, lifting, null coalescing strategies)
4. **Text conversions** (`Parse`, `TryParse`, formatting symmetry)
5. **Framework conversions** (`Convert.*`, `TypeConverter`, serialization-focused conversions)

Below is a practical taxonomy you can keep in your head. The key mentor idea is that “type conversion” is not one thing: **some conversions are pure and safe**, some are **lossy**, some can **fail**, and some are **really boundary concerns** (UI, IO, config, serialization).

If you keep those axes straight, you’ll naturally write code that is:

- **Correct**: no silent truncation/overflow surprises, no locale bugs.
- **Fast**: no exception-driven control flow, fewer allocations/boxing.
- **Maintainable**: conversions live at boundaries; the domain stays strongly typed.

---

### 1) **Numeric conversions** (integral/floating/decimal; checked/unchecked)

**What it is**

Numeric conversions are *representation* changes between numeric primitives: `int`, `long`, `double`, `decimal`, `nint`, etc.

- **Implicit** numeric conversions happen when the compiler can prove it’s safe by language rules (typically *widening*).
- **Explicit** numeric conversions require a cast and may **truncate** or **overflow**.

**When to use**

- Use numeric conversions when you are **changing numeric range/precision intentionally**.
- Prefer converting **once** at an API boundary (e.g., input parsing) rather than repeatedly inside loops.

**Trade-offs**

- **Correctness**: lossy conversions (e.g., `double` → `int`) can silently change meaning.
- **Overflow behavior**: depends on `checked` vs `unchecked` context.
- **Performance**: conversions themselves are cheap; the *real costs* are exceptions, repeated conversions, and hidden allocations around them.

**Common mistakes**

- Assuming casts are “bit reinterpretation” (they are not). For bit-level reinterpretation, see the guidance in `3.1` (full treatment there).
- Using `Parse` exceptions for numeric validation (use `TryParse` at boundaries; see `4.1`).

**See full treatment**

- Numeric implicit rules: `2.1`
- Numeric explicit/overflow/checked: `3.1`

### 2) **Reference conversions** (upcast/downcast, interface casts, pattern-based casting)

**What it is**

Reference conversions are conversions between reference types: base/derived, interface implementations, and some variance-enabled conversions (delegates/interfaces).

**When to use**

- **Upcasts** (derived → base/interface) are common and safe. They’re how polymorphism works.
- **Downcasts** (base/interface → derived) should be *rare* and usually signal a design issue unless you’re in a boundary layer (deserialization, reflection, plugin systems).

**Trade-offs**

- **Safety**: downcasts can throw `InvalidCastException`.
- **Maintainability**: frequent downcasts often mean the object model is missing a virtual method, interface, or discriminated shape.
- **Performance**: casts are generally cheap; the expensive path is exceptions or heavy interface dispatch in hot loops.

**Common mistakes**

- Using `(Foo)x` without checking; then catching `InvalidCastException` as control flow.
- Using `as` without null-check and later dereferencing.

**See full treatment**

- Upcast/variance basics: `2.2`
- Downcast patterns (pattern matching, `as`, `is`): `3.2`

### 3) **Nullable conversions** (`T` ↔ `T?`, lifting, null coalescing strategies)

**What it is**

Nullable conversions happen both for:

- **Value types**: `T` ↔ `T?` (e.g., `int` ↔ `int?`)
- **Reference types**: nullable *annotations* (`string?` vs `string`) which are compile-time analysis, not runtime type changes.

In numeric expressions, operators may be **lifted** to nullable forms (e.g., `int? + int?` → `int?`).

**When to use**

- Use nullable types to represent **absence** explicitly, instead of sentinel values (`0`, `-1`, empty string) unless the domain truly defines them.

**Trade-offs**

- **Correctness**: nullable value types can propagate null (`null` in, `null` out) which is often what you want, but it must be deliberate.
- **Performance**: `Nullable<T>` is a struct; it usually does not allocate. The main costs come from boxing (`int?` boxed is either `null` or boxed `int`) and careless APIs that force `object`.

**Common mistakes**

- Mixing “missing” and “zero” semantics.
- Forgetting that `string?` is mostly about *warnings* and API contracts; runtime still allows nulls unless you guard.

**Note**

This tutorial keeps nullable “deep theory” minimal to avoid overlap with broader type-system topics. When nullable behavior is relevant to a conversion topic (e.g., parsing into `T?`), it will be shown in the owning file for that topic (usually `4.1`).

### 4) **Text conversions** (`Parse`, `TryParse`, formatting symmetry)

**What it is**

Text conversions are *interpretation*: converting a character sequence into a value (`int`, `DateTimeOffset`, `Guid`, custom strong types).

This category is where most production bugs come from because it mixes:

- **Untrusted input**
- **Culture and formatting rules**
- **Failure handling**
- **Performance under load** (allocations + exceptions)

**When to use**

- Parse at the **edges** (UI, API, file, CLI) then carry strong types inside the app.
- Prefer `TryParse` for expected failures.

**Trade-offs**

- **Exceptions**: `Parse` throws and is expensive under repeated failure.
- **Culture**: `CurrentCulture` is user-facing; protocols/storage should use deterministic formats and usually `InvariantCulture`.
- **Allocations**: substring + `Split` patterns allocate; span-based parsing can avoid allocations in hot paths.

**See full treatment**

- `Parse` vs `TryParse`: `4.1`
- Culture/format providers and styles: `4.2`
- `ReadOnlySpan<char>` parsing patterns: `4.3`
- Formatting symmetry / round-trip: `5.2`

### 5) **Framework conversions** (`Convert.*`, `TypeConverter`, serialization-focused conversions)

**What it is**

This bucket is for framework-level conversion mechanisms that exist to support:

- working with `object` (`Convert.*`, `IConvertible`)
- component models/config binding (`TypeConverter`)
- broader ecosystems (serialization, reflection-heavy frameworks)

**When to use**

- Use `Convert.*` when your input is **object-typed** and you need well-defined null handling and `IConvertible` behavior.
- Use `TypeConverter` primarily in **framework integration** scenarios (binding/config/tooling), not in core domain logic.

**Trade-offs**

- **Discoverability**: “magic conversions” can surprise maintainers.
- **Correctness**: culture still matters; conversion behavior can be different from what you assume.
- **Performance**: object-based conversions can cause boxing and use slower paths than direct typed APIs.

**See full treatment**

- `Convert` vs casting vs parsing: `5.1`
- `TypeConverter`: `5.3`
