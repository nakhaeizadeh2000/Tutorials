## 1.1. What type conversion is in C# (and where it happens)

1. **Compile-time vs runtime conversions** (implicit conversions, explicit casts, boxing/unboxing)
2. **“Representation” vs “interpretation”** (numeric widening/narrowing vs parsing text)

4. **Performance framing** (exceptions, allocations, culture/format cost, hot paths)
5. **API design lens** (when conversions should live in your domain vs at boundaries)

### 1) **Compile-time vs runtime conversions**

**Definition**

In C#, “type conversion” is any operation that changes the *static type* (what the compiler thinks) and/or the *runtime type/representation* (what’s actually stored) of a value.

- **Compile-time conversions** are decided by the compiler based on the **static types** involved. Examples:
  - implicit numeric widening (`int` → `long`)
  - reference upcast (`Dog` → `Animal`)
  - nullable lifting (`int` → `int?`)
- **Runtime conversions** require runtime checks or runtime behavior. Examples:
  - **downcast** (`Animal` → `Dog`) which may fail
  - **boxing/unboxing** (value type ↔ `object`/interface) which can allocate and may fail on unbox
  - **user-defined conversions** (`operator implicit/explicit`) which are just method calls the compiler inserts

**Mentor stress**

- A cast like `(T)x` is not “magic”: it’s either
  - a **compile-time inserted** numeric conversion (possibly lossy), or
  - a **runtime check** (reference cast / unbox), or
  - a **method call** (user-defined conversion).

**Example (runnable)**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        // Compile-time numeric conversion (widening).
        int i = 42;
        long l = i;

        // Runtime reference cast (may throw).
        object o = "hello";
        if (o is string s) // preferred: runtime check + typed variable
            Console.WriteLine(s.Length);

        // Boxing allocates: int -> object.
        object boxed = i;
        // Unboxing requires exact type match:
        int unboxed = (int)boxed;
    }
}
```

**Performance note**

- **Boxing** allocates and increases GC pressure. Treat “value type → object/interface” as a potential hidden allocation.
- **Exceptions** from invalid casts are extremely expensive in hot paths; prefer **pattern matching** (`is`) for expected variability.

### 2) **“Representation” vs “interpretation”**

This distinction prevents a lot of production bugs.

- **Representation conversions** change how a value is represented in memory *as a value*.
  - Example: `int` → `long` (same numeric meaning, bigger range)
  - Example: `double` → `int` (numeric meaning changes due to truncation)
- **Interpretation conversions** take *data in one representation* (often text or bytes) and **interpret** it as a value.
  - Example: `"123"` → `int` via parsing
  - Example: `"2026-04-01T10:30:00Z"` → `DateTimeOffset` via parsing

**Common mistake**

Developers sometimes treat parsing as “casting”, which leads to:

- using `Parse` (exceptions) in loops
- ignoring culture/time-zone issues
- accepting ambiguous formats that later break

**Good to know**

- A cast can’t express “might fail without exceptions” for text. That’s why .NET uses the **Try-pattern** (`TryParse`) for expected failures.
- For serialization/wire formats, you usually want **InvariantCulture** and a stable, round-trippable format. The deep culture/format discussion belongs in [4.2](<../4. Parsing text to values/4.2. Culture IFormatProvider and deterministic parsing.md>).

### 3) **Failure modes**

Different conversion families fail differently. Knowing the failure mode determines the *correct API*.

- **Numeric narrowing** may:
  - silently overflow/wrap in `unchecked` context (default in many projects)
  - throw `OverflowException` in `checked` context
  - truncate/round (float → int truncates toward zero)
- **Reference downcasts** may throw `InvalidCastException` (or yield `null` with `as`)
- **Unboxing** may throw `InvalidCastException` if the boxed type isn’t exactly right
- **Parsing** may throw `FormatException`, `OverflowException`, `ArgumentNullException` (for some APIs), or return `false` with `TryParse`
- **Null handling**
  - Converting `null` to non-nullable value types is invalid (except some `Convert.*` helpers treat `null` specially—covered in [5.1](<../5. Conversion helper APIs/5.1. Convert vs casting vs parsing choose the right tool.md>))

**Mentor rule**

- If failure is part of normal control flow, prefer **Try-pattern APIs** (`TryParse`, `TryGetValue`, etc.). Exceptions are for *exceptional* situations.

For the deep “Parse vs TryParse” discussion, see [4.1](<../4. Parsing text to values/4.1. Parse vs TryParse correctness performance and API shape.md>).

### 4) **Performance framing**

Most conversion bugs and perf issues come from doing conversions in the wrong place or with the wrong API shape.

- **Exceptions**
  - Expensive to throw/catch (stack capture, unwinding, lost inlining opportunities).
  - Using exceptions for validation can become a CPU hotspot under load.
- **Allocations**
  - Boxing allocates.
  - Parsing from substrings can allocate if you create intermediate strings (e.g., `Split`).
  - Formatting can allocate if you build strings in tight loops.
- **Culture/format**
  - Culture-aware parsing is not “slow by default”, but in high-volume parsing you should be explicit and consistent, and avoid repeated expensive work.
- **Threading**
  - Conversions themselves are usually CPU-only and thread-safe, but *your* conversion pipeline can become non-thread-safe if you share mutable state (e.g., cached `StringBuilder`, custom converters without synchronization).

**Performance note**

- In ingestion pipelines, a high-leverage pattern is: **scan once → slice via `ReadOnlySpan<char>` → `TryParse`** (see [4.3](<../4. Parsing text to values/4.3. ReadOnlySpan char overloads avoid allocations parse slices.md>)).

### 5) **API design lens**

Where you put conversions matters more than which method you call.

- **Boundary conversions** (recommended):
  - Parse/convert at the boundaries: UI, HTTP, file IO, message queue, database reads.
  - Inside the domain, keep strong types and validated invariants.
- **Domain conversions** (use sparingly and intentionally):
  - Provide explicit conversion methods/operators for *lossless, unsurprising* conversions.
  - Avoid “magical” implicit conversions that hide work or can throw.

**Trade-offs**

- Putting conversions at boundaries improves **correctness** (validate once), **performance** (avoid repeated parsing), and **maintainability** (invariants are local).
- Overusing implicit conversions can reduce readability and make refactoring risky (calls compile but mean something different).
