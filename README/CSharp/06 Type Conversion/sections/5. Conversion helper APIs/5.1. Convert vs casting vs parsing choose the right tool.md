## 5.1. `Convert.*` vs casting vs parsing (choose the right tool)

1. **What `Convert` is for** (object-based conversions; null handling; IConvertible)
2. **Why it’s not a parsing API** (it often delegates; still format/culture concerns)
3. **When a cast is better** (compile-time guarantees; clarity)
4. **When `TryParse` is better** (expected failures; avoid exceptions)
5. **Performance pitfalls** (boxing, exceptions, and “objecty” call sites)

---

### 1) **What `Convert` is for** (object-based conversions; null handling; IConvertible)

**Definition**

`System.Convert` exists to answer a specific .NET question:

> “I have a value as `object` (or something similarly loosely typed). How do I convert it to a primitive in a consistent way?”

Common sources of `object`-typed values:

- reflection results
- legacy APIs
- data tables / weakly typed data containers
- configuration APIs that expose raw objects

`Convert` methods typically:

- handle `null` in a defined way (often returning default values for some targets)
- use `IConvertible` when available
- accept an `IFormatProvider` for some conversions (especially “object → number via string” paths)

**Mentor stress**

- If you have a strongly typed value, you almost never need `Convert`.
- `Convert` is most useful at **boundaries where you are forced into `object`**.

**Example (runnable)**

```csharp
using System;
using System.Globalization;

static class Demo
{
    static void Main()
    {
        object? a = null;
        Console.WriteLine(Convert.ToInt32(a)); // 0 (defined behavior)

        object b = "123";
        Console.WriteLine(Convert.ToInt32(b, CultureInfo.InvariantCulture)); // 123
    }
}
```

**Good to know**

- `Convert.ToInt32(null)` returns `0`, but `int.Parse(null!)` throws. These are different contracts.
- This “null becomes default” behavior is convenient for some legacy/interop contexts, but it can hide bugs in domain code.

---

### 2) **Why it’s not a parsing API** (it often delegates; still format/culture concerns)

`Convert` is not “a better `Parse`”. It often **delegates** to:

- a direct cast / numeric conversion when the input is already numeric
- `IConvertible.ToXxx(...)`
- or parsing when the input is a string

That means all the same problems exist:

- culture-dependent strings
- ambiguous formats
- exceptions for invalid input (most `Convert` conversions throw on malformed strings)

**Mentor rule**

- If your input is text, your primary choice should be **`TryParse` with explicit culture/styles** (see [4.1](<../4. Parsing text to values/4.1. Parse vs TryParse correctness performance and API shape.md>), [4.2](<../4. Parsing text to values/4.2. Culture IFormatProvider and deterministic parsing.md>), [4.3](<../4. Parsing text to values/4.3. ReadOnlySpan char overloads avoid allocations parse slices.md>)).

### 3) **When a cast is better** (compile-time guarantees; clarity)

**Prefer casts when:**

- both sides are already strongly typed (numeric or reference)
- you want the compiler to enforce intent
- failure is truly exceptional (e.g., internal invariants) and throwing is acceptable

Examples:

- numeric narrowing with explicit cast (prefer `checked` or range checks; see [3.1](<../3. Explicit conversions and casts/3.1. Explicit numeric casts and overflow behavior.md>))
- safe downcasts via pattern matching (see [3.2](<../3. Explicit conversions and casts/3.2. Downcasts and safe casting patterns is pattern matching as.md>))

**Example (runnable)**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        long big = 1_000_000;
        int smaller = checked((int)big); // explicit, visible policy
        Console.WriteLine(smaller);
    }
}
```

---

### 4) **When `TryParse` is better** (expected failures; avoid exceptions)

If your input is **external or user-provided**, failure is normal.

Use `TryParse` when:

- validating user input
- processing CSV/log lines
- reading config values that might be missing/wrong
- processing untrusted messages

**Why**

- You avoid exception cost (CPU + noise).
- You force a correct “success/failure” branch in code.

See the single-source deep discussion: `4.1. Parse vs TryParse`.

---

### 5) **Performance pitfalls** (boxing, exceptions, and “objecty” call sites)

**Boxing**

`Convert` is most often used with `object`. If your pipeline turns typed values into `object`, you may pay:

- boxing allocations (value types)
- extra casts later
- less JIT optimization

See: `3.3. Boxing/unboxing and hidden allocations`.

**Exceptions**

`Convert.ToInt32("oops")` throws. If that happens repeatedly (validation), it becomes a hotspot. Use `TryParse`.

**Mentor checklist**

- If you control the API, do not accept `object` “for flexibility”. Use overloads, generics, or discriminated shapes.
- Use `Convert` only when you are already in an `object` world and you need the framework’s standardized behavior.
