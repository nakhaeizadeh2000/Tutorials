## 2.1. Local variables and parameters: scope, lifetime, and definite assignment

1. **Scope** (small scopes reduce bugs; shadowing rules; pattern variables)
2. **Lifetime** (stack locals vs heap captures; when closures extend lifetimes)
3. **Performance notes** (avoid capturing large objects; prefer `ReadOnlySpan<T>` for parsing-heavy code where appropriate)

Local variables and parameters are “small” language features that quietly determine how readable, safe, and fast your methods are. If you master scope, lifetime, and assignment rules, you avoid entire categories of bugs (null misuse, accidental reuse, closure leaks) and performance traps (unexpected allocations).

---

### 1. **Scope**

**Definition**

Scope is *where a name is visible* and therefore where it can be used (and misused). In modern C#, a primary technique for reducing bugs is **shrinking scopes** so the compiler and the reader can reason about fewer possibilities at once.

**When to use small scopes**

- **Prefer declaring variables at the narrowest point of use**, not “at the top of the method”.
- Use **pattern variables** (`is`, `switch`) to keep values scoped to the checks that make them valid.
- Use **guard clauses** to validate inputs early and keep the “happy path” left-aligned.

**Shadowing rules (and why mentors dislike it)**

Shadowing means a local/parameter hides a name from an outer scope (or hides a field/property). C# prevents some confusing shadowing, but plenty of subtle shadowing is still possible (especially in nested scopes).

Common mistake:

- Reusing generic names like `result`, `value`, `tmp` across nested blocks, then accidentally using the wrong one.

Mentor rule:

- **Avoid shadowing unless it makes code objectively clearer**, and never shadow a field with a local of the same name.

**Pattern variables**

Pattern variables keep values correctly scoped:

```csharp
using System;

static int ParseOrDefault(string? text)
{
    if (text is not { Length: > 0 })
        return 0;

    return int.TryParse(text, out var value) ? value : 0;
}
```

Good to know:

- `out var value` scopes `value` to the *enclosing block* (here, the whole method body after the `if`), so keep blocks small if you want tight scope. For tighter scope, split into smaller blocks or early-return.

### 2. **Lifetime**

**Two “locations” matter: stack vs heap**

- **Most locals** are *logically* stack-bound and die when the method returns.
- Some locals/parameters become **captured** by closures (lambdas/local functions used as delegates) or by async state machines, which extends their lifetime beyond the method call.

Important nuance:

- Whether something is “on the stack” is an implementation detail, but the *observable* effect is clear: **captured variables can outlive the call** and may allocate.

**Closures extend lifetimes**

When a lambda captures a local, the compiler typically creates a hidden “display class” on the heap. That can keep references alive longer than intended.

```csharp
using System;
using System.Collections.Generic;

static Action BuildCallback(List<byte[]> buffers)
{
    // Captures 'buffers' => buffers stays alive as long as the returned delegate is alive.
    return () => Console.WriteLine(buffers.Count);
}
```

Pitfall:

- Capturing a *large object graph* (like `buffers` above) unintentionally keeps it all alive, increasing memory usage and GC pressure.

**Async also extends lifetimes**

In an `async` method, locals used across an `await` are lifted into the async state machine. This doesn’t always allocate (it often does), but it **does** extend lifetimes, which matters for large objects.

Guidance:

- Avoid keeping large buffers or big graphs “alive across awaits”. Scope them so they can be collected earlier.

---

### 3. **Performance notes**

**Avoid capturing when you don’t need it**

- Prefer **static local functions** when you can (see section `7.2`). They cannot capture, so they prevent accidental heap allocations and lifetime extension.
- Prefer passing state explicitly rather than capturing it.

**`ReadOnlySpan<T>`: the right tool in the right layer**

`ReadOnlySpan<T>` is great for high-performance parsing/processing because it:

- avoids allocations from slicing strings/arrays
- enables efficient scanning without copying

Constraints:

- spans are `ref struct` (stack-only): you cannot store them in fields, capture them in lambdas, or use them across `await`.

Example: allocation-free token scan

```csharp
using System;

static int CountCommas(ReadOnlySpan<char> text)
{
    var count = 0;
    while (!text.IsEmpty)
    {
        var idx = text.IndexOf(',');
        if (idx < 0) break;
        count++;
        text = text[(idx + 1)..];
    }
    return count;
}
```

Performance note:

- In hot paths, prefer span-based APIs *at the boundaries* where you can keep lifetimes simple. Don’t “infect” your entire domain model with spans.

نکته:

- Optimize with measurements. Many “scope/lifetime” choices are first about correctness; performance wins are a bonus when you keep code simple and avoid hidden allocations.
