## 7.1. Local functions: structure, scoping, and avoiding delegate allocations

1. **Why local functions** (keep helpers near usage; tighter scope; clearer invariants)
2. **Perf** (can avoid allocations compared to lambdas in some scenarios; still beware captures)
3. **Testing/design** (extract to private methods when reuse/testing matters)

Local functions are one of the most underused tools for writing methods that are **readable**, **correct**, and sometimes **faster** than the “lambda everywhere” style. They let you keep helper logic *exactly where it matters*—without widening the type’s public/private surface.

---

### 1. **Why local functions**

**Definition**

A *local function* is a named method declared inside another method (or inside an accessor / local function). It has:

- Access to the enclosing scope (it *can* capture locals and `this`, just like a lambda).
- A proper method body with statements, attributes (some), and generic parameters.
- Normal control flow (`return`, `throw`, `yield`), which often reads better than deeply nested lambdas.

**When to use**

- **Tiny helpers that are only meaningful inside one method**.
- When you want to name an internal step to improve readability without creating a separate private method.
- When a helper needs to access local variables but you want to keep those variables’ scope tight.

**Trade-offs**

- If overused, local functions can make a method “long but segmented”. Prefer keeping the outer method small too.
- Capturing is convenient but can hide lifetime/allocation costs (see below).

**Common mistakes**

- Turning a method into a “mini class” with many local functions. That’s usually a hint you should extract a new type.
- Capturing variables accidentally in callbacks, extending lifetimes unexpectedly (ties into `2.1`/`2.2`).

**Example: structure without widening surface**

```csharp
using System;

public static class EmailNormalizer
{
    public static string NormalizeOrThrow(string raw)
    {
        if (raw is null) throw new ArgumentNullException(nameof(raw));

        // Local function keeps helper next to usage and can access 'raw' if needed.
        static ReadOnlySpan<char> Trim(ReadOnlySpan<char> s)
        {
            var start = 0;
            var end = s.Length - 1;

            while (start <= end && char.IsWhiteSpace(s[start])) start++;
            while (end >= start && char.IsWhiteSpace(s[end])) end--;

            return s[start..(end + 1)];
        }

        var span = Trim(raw.AsSpan());

        // Minimal example; real email rules are more complex.
        if (span.Length == 0 || span.IndexOf('@') <= 0)
            throw new FormatException("Invalid email.");

        return span.ToString().ToLowerInvariant();
    }
}
```

نکته: using a **`static` local function** for `Trim` prevents accidental captures by design (deep dive in `7.2`).

### 2. **Perf**

Local functions can be faster than lambdas in specific scenarios, but the real guidance is:

- **Don’t guess**—understand the allocation model and measure in hot paths.

**Local function vs lambda: allocation model**

- A **non-capturing lambda** can often be represented as a cached delegate (no allocation per call site execution).
- A **capturing lambda** typically allocates a closure object (and often a delegate).
- A **local function** called directly is just a method call and can be inlined. If it is *converted to a delegate* (e.g., passed as a callback), it behaves more like a lambda (may allocate), especially if it captures.

**Mentor rule**

- If the helper is only used synchronously and locally, prefer calling the local function directly (no delegate).
- If you must pass a callback, prefer **non-capturing** (or use `static` local functions) in hot paths.

**Example: avoiding per-iteration allocations**

```csharp
using System;
using System.Collections.Generic;

public static class Filtering
{
    public static int CountPositive(List<int> values)
    {
        // Direct loop is usually the fastest and clearest in hot paths.
        var count = 0;
        foreach (var v in values)
            if (v > 0) count++;
        return count;
    }

    public static int CountPositiveWithPredicate(List<int> values)
    {
        // If you really need a predicate, keep it non-capturing.
        static bool IsPositive(int x) => x > 0;

        var count = 0;
        foreach (var v in values)
            if (IsPositive(v)) count++;
        return count;
    }
}
```

Performance note:

- LINQ (`values.Count(v => v > 0)`) is expressive but can add overhead (delegate invocation, iterator costs). In inner loops, prefer explicit loops unless profiling says otherwise.

### 3. **Testing/design**

**When to keep it local**

- The helper is an implementation detail with no independent meaning.
- You don’t want it to be callable from elsewhere (even private methods are callable from the whole type).

**When to extract**

- The helper is reused in multiple methods.
- You want direct unit tests of the helper behavior.
- The helper has meaningful dependencies / state and would benefit from becoming its own type.

Good to know:

- A local function cannot be called from outside the containing method, which is great for reducing surface area—but it also means you test it only through the outer method (usually the right choice for small helpers).
