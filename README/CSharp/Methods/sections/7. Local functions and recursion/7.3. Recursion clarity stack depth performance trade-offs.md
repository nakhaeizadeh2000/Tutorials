## 7.3. Recursion: clarity vs stack depth and performance trade-offs

1. **When it’s great** (tree traversal, divide-and-conquer, parsers)
2. **Risks** (stack overflow; repeated allocations; non-tail recursion; exception-heavy control flow)
3. **Alternatives** (explicit stack/queue; iterative loops; memoization when appropriate)

Recursion is a *tool for expressing structure*. Used well, it produces the most readable code for trees and divide-and-conquer algorithms. Used blindly, it produces stack overflows, slow code, and hard-to-debug crashes under real workloads.

---

### 1. **When it’s great**

**The sweet spot**

Recursion shines when the *problem is naturally recursive*:

- **Trees/graphs** (DOM-like structures, ASTs, directory trees, UI visual trees)
- **Divide-and-conquer** (quicksort/mergesort, binary search variants)
- **Parsers** (recursive descent)
- **Dynamic programming** (when paired with memoization)

Mentor rule:

- Use recursion when it makes the **invariants and base case obvious**.
- If you have to “simulate a loop” in your head to understand it, the recursion is probably not helping.

**Example: recursive vs iterative preorder traversal**

```csharp
using System;
using System.Collections.Generic;

public sealed class Node
{
    public required string Name { get; init; }
    public List<Node> Children { get; } = new();
}

public static class Traversal
{
    public static void PreorderRecursive(Node root, Action<Node> visit)
    {
        ArgumentNullException.ThrowIfNull(root);
        ArgumentNullException.ThrowIfNull(visit);

        Visit(root);
        return;

        void Visit(Node n)
        {
            visit(n);
            foreach (var child in n.Children)
                Visit(child);
        }
    }

    public static void PreorderIterative(Node root, Action<Node> visit)
    {
        ArgumentNullException.ThrowIfNull(root);
        ArgumentNullException.ThrowIfNull(visit);

        var stack = new Stack<Node>();
        stack.Push(root);

        while (stack.Count != 0)
        {
            var n = stack.Pop();
            visit(n);

            // Push in reverse to preserve left-to-right traversal.
            for (int i = n.Children.Count - 1; i >= 0; i--)
                stack.Push(n.Children[i]);
        }
    }
}
```

Good to know:

- The recursive version is often clearer; the iterative version makes stack usage explicit.
- For very deep trees, prefer the iterative version to avoid stack overflow.

---

### 2. **Risks**

**Stack overflow is the big one**

Every recursive call consumes stack space. .NET does not guarantee tail-call optimization, and even when the JIT can apply it, you should not rely on it for correctness.

- A chain of thousands (or tens of thousands) of recursive calls can crash the process with `StackOverflowException`.
- `StackOverflowException` cannot be caught reliably; treat it as process-fatal.

**Non-tail recursion and repeated work**

- Many recursive implementations recompute the same sub-problems. That’s a performance bug, not a “recursion thing”.
- Fix with memoization or convert to iterative DP.

**Allocations and closures**

- Recursion itself doesn’t allocate, but what you do inside it might (LINQ, iterator blocks, capturing lambdas).
- Avoid allocations in the recursive “hot path” (especially in tight loops over nodes).

**Exception-heavy control flow**

- Don’t use exceptions for base-case exits or expected “not found” outcomes. Prefer boolean returns or result types.
- Throwing inside deep recursion is expensive and can create large stack traces.

Performance note:

- In real systems, the recursion depth limit is often reached by *pathological inputs* (untrusted data) or *unexpected structures* (cyclic graphs). Always ask: “can input be adversarial?”

---

### 3. **Alternatives**

**Explicit stack/queue**

- Use `Stack<T>` for DFS, `Queue<T>` for BFS.
- Benefit: no stack overflow; easier to add cancellation and progress reporting.

**Iterative loops**

- For problems that are fundamentally linear, recursion usually harms readability and performance.

**Memoization**

- If subproblems repeat, store results. Use `Dictionary<TKey, TValue>` or arrays when keys are dense.
- Beware unbounded caches: they are memory leaks if you don’t bound them.

**When a graph can be cyclic**

Recursion assumes a tree unless you guard against cycles.

```csharp
using System;
using System.Collections.Generic;

public static class GraphWalk
{
    public static void Dfs<T>(T start, Func<T, IEnumerable<T>> neighbors, Action<T> visit)
        where T : notnull
    {
        ArgumentNullException.ThrowIfNull(start);
        ArgumentNullException.ThrowIfNull(neighbors);
        ArgumentNullException.ThrowIfNull(visit);

        var seen = new HashSet<T>();
        var stack = new Stack<T>();
        stack.Push(start);

        while (stack.Count != 0)
        {
            var n = stack.Pop();
            if (!seen.Add(n)) continue;

            visit(n);
            foreach (var next in neighbors(n))
                stack.Push(next);
        }
    }
}
```

نکته: For graphs, “recursive traversal without `seen`” can be an infinite loop (or a stack overflow). Make cycle-handling an explicit part of your method contract.
