## 6.1. Parameter modifiers (default): pass-by-value vs pass-by-reference mental model

1. **Default behavior** (value types copy the value; reference types copy the reference)
2. **Correctness** (mutating a referenced object vs reassigning the parameter are different things)
3. **Performance** (avoid premature `ref`; start with clear code and optimize with measurements)

This is the single most misunderstood area in C#: people say “C# passes objects by reference” and then build a wrong mental model on top. The correct statement is:

- **C# is pass-by-value by default**, always.
- What is *copied* depends on whether the parameter type is a **value type** or a **reference type**.

---

### 1. **Default behavior**

**Definitions**

- **Pass-by-value**: the callee receives a *copy* of the argument (a copy of the variable’s value).
- **Value type (`struct`)**: the value *is the data* (often stored inline).
- **Reference type (`class`)**: the value *is a reference* (a pointer-like handle) to an object on the managed heap.

So:

- Passing a `struct` parameter copies the entire struct value (unless optimized / enregistered by the JIT).
- Passing a `class` parameter copies the **reference**, not the object. Both caller and callee can now access the same object instance.

**Example: what gets copied**

```csharp
using System;

public sealed class Box { public int Value; }

public static class Demo
{
    public static void Mutate(Box b) => b.Value++;          // mutates shared object
    public static void Reassign(Box b) => b = new Box();     // reassigns local copy of the reference

    public static void Mutate(int x) => x++;                 // mutates local copy of the value
}

var box = new Box { Value = 10 };
Demo.Mutate(box);
Console.WriteLine(box.Value); // 11

Demo.Reassign(box);
Console.WriteLine(box.Value); // still 11 (caller’s variable not changed)

var n = 10;
Demo.Mutate(n);
Console.WriteLine(n); // still 10
```

Good to know:

- That “still 10” is not a bug; it’s pass-by-value working as designed.
- The only way to change the caller’s variable itself is `ref`/`out`/`in` (with different semantics).

---

### 2. **Correctness**

**Two different kinds of “change”**

When a parameter is a reference type (`class`), there are two separate operations:

1) **Mutating the object** the reference points to (visible to caller because it’s the same object)
2) **Reassigning the parameter variable** to point somewhere else (not visible to caller in pass-by-value)

Mentor rule:

- If a method **mutates input objects**, make it explicit in the API surface:
  - Name: `AddItem`, `Remove`, `NormalizeInPlace`
  - Doc: “Mutates `builder`”
  - Or better: accept a type designed for mutation (e.g., `List<T>`, `StringBuilder`) and return an immutable result elsewhere.

**Avoid surprising mutation**

Prefer immutable inputs for domain logic:

- Use `record`/`record struct` with `init`-only properties for DTOs/value objects.
- Use immutable collections (`System.Collections.Immutable`) when you truly need deep immutability.

Legacy/avoid:

- “Everything is mutable and has public setters” (leaks invariants; see section `1.2`).

---

### 3. **Performance**

**Don’t reach for `ref` first**

`ref`-like patterns are powerful but increase coupling and reduce readability. Start with clear pass-by-value code and optimize only when profiling shows a problem.

**Where copying hurts**

- Large structs (e.g., 64+ bytes) copied in tight loops can hurt CPU/cache.
- Repeated copying can also increase register pressure and reduce JIT optimization opportunities.

Modern alternatives before `ref`:

- Make structs **smaller** or use `readonly struct` to avoid defensive copies (see section `6.5`).
- Use **`ReadOnlySpan<T>` / `Span<T>`** for “view into data” APIs without copying.
- Use `in` for read-only by-ref *only if* it measurably helps (see section `6.5` for the defensive-copy story).

Performance note:

- Many “large struct copy” concerns are overestimated. The JIT can enregister and optimize aggressively. Always measure in realistic workloads.
