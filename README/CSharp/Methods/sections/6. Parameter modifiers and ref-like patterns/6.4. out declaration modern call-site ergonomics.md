## 6.4. `out` variable declaration: modern call-site ergonomics

1. **Inline declarations** (`if (TryX(..., out var value))`) reduce scope and bugs
2. **Pattern synergy** (combine with guard clauses and early returns for clean code)
3. **Mentor rule** (keep the declared variable scope minimal; don’t leak it across large blocks)

Modern C# lets you declare `out` variables *at the call site*. This is primarily a **readability and correctness** feature (scope minimization), and secondarily a performance feature (less code, fewer mistakes that lead to defensive allocations).

---

### 1. **Inline declarations**

**What it is**

Instead of:

- Declaring a variable earlier (often with a larger scope than needed), then calling a `Try...` method that assigns it

…you can declare the variable right inside the call:

```csharp
if (int.TryParse(text, out var value))
{
    // value is in scope only here (and in else if you use it)
    return value;
}
```

**When to use**

- Any time you call a `Try...` API and you only need the result inside the success path.
- Especially in parsing/validation pipelines and guard clauses.

**Trade-offs**

- Inline `out` can slightly reduce “reusability” of the variable across branches. That’s usually a *feature*—it forces you to be explicit about what you need where.

**Common mistakes**

- Declaring `out var x` and then using `x` later far from the check by “lifting” scope into a larger block. This reintroduces the exact bug class inline `out` is meant to prevent.

نکته: The compiler enforces definite assignment rules; `out` variables are always assigned on the success path. That eliminates a class of “maybe uninitialized” bugs.

---

### 2. **Pattern synergy**

Inline `out` combines extremely well with:

- **Guard clauses** (early return)
- **Pattern matching** (including property patterns and type patterns)
- **Minimal scopes** (variables exist only where correct)

**Example: guard clause + Try pattern**

```csharp
using System;

static int ParsePortOrThrow(string text)
{
    if (!ushort.TryParse(text, out var port))
        throw new ArgumentException("Invalid port.", nameof(text));

    return port;
}
```

Good to know:

- This still throws on invalid input because *the method contract* chooses to throw. In app/business code you often prefer returning a result (`bool`/`OneOf`/`Result<T>`) rather than throwing—exceptions are expensive and noisy for expected invalid user input. See section `6.3` for how Try-pattern APIs are usually shaped.

**Example: inline `out` + “TryGet” with collections**

```csharp
using System.Collections.Generic;

static bool TryGetUser(IReadOnlyDictionary<string, int> usersByName, string name, out int userId)
{
    // Forward the Try-pattern; the out var declaration stays at the call site.
    return usersByName.TryGetValue(name, out userId);
}
```

---

### 3. **Mentor rule**

**Keep scope minimal**

Prefer:

```csharp
if (Guid.TryParse(input, out var id))
{
    Use(id);
    return;
}
```

Avoid:

```csharp
Guid id;
if (Guid.TryParse(input, out id))
{
    // ...
}
// ... lots of code ...
Use(id); // easy to accidentally use id even when parsing failed in refactors
```

**If you must use the variable later**, restructure so correctness stays obvious:

- Return early on failure
- Or use separate methods to keep branches small

Performance note:

- Inline `out` itself doesn’t “make things faster”. What it does is help you write code that naturally avoids work on failure paths (early returns), avoids unnecessary allocations introduced by “defensive coding”, and keeps state local—improving both readability and the compiler/JIT’s ability to optimize.
