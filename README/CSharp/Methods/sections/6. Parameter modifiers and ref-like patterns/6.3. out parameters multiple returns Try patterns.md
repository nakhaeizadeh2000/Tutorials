## 6.3. `out` parameters: multiple returns and Try-pattern APIs

1. **Meaning** (callee must assign before returning; caller variable does not need to be initialized)
2. **Best practice** (use for Try-pattern APIs like `TryParse`; prefer tuples/records for multi-values in app code)
3. **Performance** (can avoid allocations vs returning objects; keep API shape consistent)

`out` is a language feature that exists for two main reasons: (1) to express “this method *returns* a value, but via a parameter”, and (2) to support highly-optimized, allocation-free “Try-pattern” APIs that avoid exceptions and avoid heap allocations.

---

### 1. **Meaning**

**Definition**

An `out` parameter is **passed by reference** with a specific rule:

- The callee **must assign** it before returning (the compiler enforces definite assignment).
- The caller’s variable **does not need** to be definitely assigned before the call.

At the IL/runtime level, `out` is essentially `ref` (by-ref). The difference is primarily **compile-time intent** and **definite assignment rules**.

**When to use**

- When failure is expected and you want to avoid exceptions: `TryParse`, `TryGetValue`, `TryDequeue`.
- When you want to return a value only on success, and you want call sites to naturally branch on the boolean.

**Common mistakes**

- Using `out` for “multiple returns” in application code where a tuple/record is clearer.
- Returning partially-valid output on failure. The convention is:
  - return `false`
  - set `out` to a safe default (often `default`)

**Example: classic Try-pattern**

```csharp
using System;

public static class InputParsing
{
    public static bool TryParsePort(ReadOnlySpan<char> text, out int port)
    {
        if (!int.TryParse(text, out port))
            return false;

        if ((uint)port > 65535u) // branch-friendly range check
        {
            port = default;
            return false;
        }

        return true;
    }
}
```

Note:

- `ReadOnlySpan<char>` avoids creating a temporary string when you already have spans (e.g., slicing an input buffer).
- Resetting `port` on failure prevents accidental use of stale values.

---

### 2. **Best practice**

**Prefer `out` for Try-pattern APIs**

In .NET, the Try-pattern is extremely common and idiomatic:

- `Dictionary<TKey,TValue>.TryGetValue(key, out value)`
- `int.TryParse(text, out value)`
- `ConcurrentQueue<T>.TryDequeue(out value)`

The key property is: **failure is normal**, and the API is shaped to keep that path fast and readable.

**For “multiple returns” in app code, prefer tuples/records**

For application-level code (where allocation pressure is usually not the first constraint), returning a tuple/record is often clearer:

- better names
- easier refactoring
- fewer “parameter direction” surprises

Example (clearer than multiple `out`s):

```csharp
public readonly record struct ParseResult(bool Success, int Port, string? Error);
```

If you need maximum performance and want to avoid allocations, you can still use structs/results—but decide based on measurement and API ergonomics.

**Avoid legacy patterns**

- **Legacy**: `bool TryX(..., out T value, out string error)`
- **Prefer**: `TryX(..., out T value)` and put diagnostics in logging, or return a structured result type if error details are part of the contract.

Mentor rule:

- If the caller must *always* look at a “why it failed” value, you might not want the Try-pattern at all—you want a **result type**.

---

### 3. **Performance**

**Why `out` can be faster**

- Avoids allocating a return object/tuple (especially if you’d otherwise allocate a class).
- Avoids exceptions (which are very expensive under load).
- Often enables branch-friendly code: `if (TryX(..., out var value)) { ... }`.

**But don’t overuse it**

The biggest cost in many real systems is not the `out` itself; it’s:

- doing work twice (e.g., lookup + lookup again)
- hidden allocations (LINQ, closures)
- I/O or locking

So treat `out` as a tool for:

- low-level libraries
- hot paths
- idiomatic Try-pattern APIs

Performance note:

- If your `out` API is frequently used in tight loops, consider also offering a `ReadOnlySpan<T>`-based overload (see section `6.7` for `params` allocation pitfalls and span alternatives).
