## 8.1. Method design checklist: correctness, readability, and performance

1. **Clarity first** (single responsibility; explicit names; small scopes; predictable side effects)
2. **Perf-aware habits** (avoid hidden allocations; avoid exceptions for expected control flow; validate at boundaries)
3. **API hygiene** (avoid optional parameters in public libraries; consistent async naming; keep overload sets coherent)

This section is meant to be the “mentor checklist” you apply during code review and before you ship. It intentionally repeats *principles* (not full explanations) and points to the deep sections for details.

---

### 1. **Clarity first**

**Single responsibility at method level**

- A good method answers: “What does this do?” in one sentence.
- If your sentence contains “and”, you probably have multiple responsibilities (validation + transformation + I/O + logging, etc.).

Good to know:

- It’s fine for a method to orchestrate multiple steps if it stays **thin** and delegates real work to cohesive helpers.

**Explicit names**

- Prefer verbs for actions: `Reserve`, `Commit`, `Normalize`, `TryParse`, `ComputeHash`.
- Encode failure mode in the name:
  - `TryX(...)` → returns `bool`, doesn’t throw for expected failure.
  - `GetXOrThrow(...)` → throws when missing/invalid.
  - `GetXOrDefault(...)` → default value is explicit.

**Small scopes**

- Declare variables as close as possible to usage.
- Prefer guard clauses + early returns to keep nesting shallow.
- Avoid reusing variables for different meanings (“variable recycling”).

See also:

- Scope/lifetime rules in section `2.1`.

**Predictable side effects**

- If a method mutates an argument or internal state, make it obvious via naming and API shape.
- Avoid hidden I/O (database, HTTP, file) inside “innocent-looking” methods unless the name clearly implies it.

Note:

- Hidden side effects are the #1 cause of “spooky action at a distance” and flakey tests.

### 2. **Perf-aware habits**

**Avoid hidden allocations**

Common silent allocation sources in method bodies:

- Capturing lambdas/closures (see `2.1`, `2.2`, `7.1`, `7.2`)
- LINQ in hot paths (iterator allocations, delegates)
- `params` arrays (see `6.7`)
- String concatenation in loops (prefer `string.Create`, `ValueStringBuilder` patterns, or `StringBuilder` when appropriate)

Performance note:

- Don’t pre-optimize everything. But in *hot loops*, prefer explicit loops over LINQ, and prefer spans for parsing-heavy code when it meaningfully reduces allocations.

**No exceptions for expected control flow**

- Use exceptions for unexpected failures (bugs, contract violations, system failures).
- Use `Try...`/result types for expected outcomes:
  - parsing
  - “not found”
  - validation failures

See also:

- Exception costs and performance framing in `1.1`.
- `out` and Try-patterns in `6.3` and `6.4`.

**Validate at boundaries**

- Validate inputs once at the public boundary and keep internal helpers assuming validity (see section `1.2`).
- Don’t repeatedly check invariants inside inner loops if the loop is fully controlled and inputs were validated.

**Async vs sync**

- Use async for I/O-bound work; keep CPU-bound work synchronous.
- Avoid `Task.Run` to “make it async” on servers; it usually just adds thread pool pressure.

Good to know:

- If you need true parallel CPU work, treat it as parallelism (partitioning, scheduling, cancellation) rather than “async”.

### 3. **API hygiene**

**Avoid optional parameters in public libraries**

- Optional parameter defaults are baked into the caller. Changing the default later breaks already-compiled consumers.
- Prefer overloads for public APIs. (Deep dive in `4.2`.)

**Consistent async naming**

- Async methods should end with `Async` (e.g., `ReadAsync`, `GetUserAsync`) unless following established BCL conventions.
- Prefer accepting `CancellationToken` as the last parameter.

**Coherent overload sets**

- Keep overloads small and consistent.
- Avoid overloads that differ only by “mystery” parameters (e.g., `object`, `dynamic`, `params object[]`) because they create ambiguity and weaken type safety.

See also:

- Overload resolution details and ambiguity traps in `5.1`.

**Prefer modern call-site clarity tools**

- Named arguments can improve readability, but they couple you to parameter names (deep dive in `4.3`).
- If an API has too many parameters, consider an options type (record) or builder—don’t rely on “named arguments everywhere” as a substitute for good design.
