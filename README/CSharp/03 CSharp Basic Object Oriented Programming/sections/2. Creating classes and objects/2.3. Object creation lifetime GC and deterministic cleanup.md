## 2.3. Object creation & lifetime: `new`, GC, and deterministic cleanup

1. **Allocation basics** (Gen0 allocations are cheap; too many allocations are not)

### 1) **Allocation basics (Gen0 is cheap; too many allocations are not)**
**Definition**
- `new` creates a *managed object* on the GC heap (for reference types). Allocation is typically fast (bump-pointer), often landing in **Gen0**.
- “Gen0 allocations are cheap” means the *act* of allocating is fast; the *total cost* comes later:
  - more objects → more frequent collections,
  - more surviving objects → promotion to Gen1/Gen2,
  - more memory traffic → worse cache behavior.

**When to care**
- If you allocate in a **hot loop** or per-request in a high-throughput server, allocations become a primary scalability limiter.
- If your app is mostly waiting on I/O, a few allocations may not matter; measure before micro-optimizing.

**Trade-offs**
- Fewer allocations often increases code complexity (pools, spans, caching). Complexity is a cost; don’t pay it without evidence.

**Common mistakes**
- Using allocations as control-flow: “just create objects and let GC handle it” in a tight path.
- Materializing sequences repeatedly (`ToList()`, `ToArray()`) in hot code.
- Building “one object per row” for large datasets when a contiguous representation would do.

**Performance note**
- High-level rule: **optimize object graph shape first**.
  - Fewer nodes + fewer edges (references) is usually a bigger win than micro-optimizing a method body.

### 2) **Ownership and disposal (`IDisposable`, `using`, `IAsyncDisposable`, `await using`)**
**Definition**
- The GC manages **memory**, not **external resources** (file handles, sockets, native memory, timers).
- Ownership means:
  - **who creates** the resource,
  - **who disposes** it,
  - **who may share** it.

**When to use**
- Use `using` / `using var` when your object owns a resource and its scope is clear.
- Use `await using` for `IAsyncDisposable` resources (async cleanup).

**Mentor rule**
- Make ownership **obvious in the API**. Ambiguous ownership is a top source of production leaks.

**Short example: ownership made explicit**

```csharp
using System;
using System.IO;

public sealed class ReportWriter : IDisposable
{
    private readonly TextWriter _writer;
    private readonly bool _ownsWriter;

    public ReportWriter(TextWriter writer, bool ownsWriter = false)
    {
        _writer = writer ?? throw new ArgumentNullException(nameof(writer));
        _ownsWriter = ownsWriter;
    }

    public void WriteLine(string message) => _writer.WriteLine(message);

    public void Dispose()
    {
        if (_ownsWriter) _writer.Dispose();
    }
}

using var file = new StreamWriter("report.txt");
using var report = new ReportWriter(file, ownsWriter: false); // borrowing
report.WriteLine("hello");
```

**Deprecated / legacy patterns**
- Avoid “finalizer as normal cleanup”. Finalizers are a last-resort safety net and have real GC costs. The deep explanation is in the referenced Fundamental Theories sections.

### 3) **Avoiding leaks (events, timers, static caches, long-lived graphs)**
**Definition**
- In managed code, a “memory leak” is often an **unintended strong reference** that keeps objects reachable.
- Your GC is correct: if something is reachable, it will not be collected.

**Common leak sources**
- **Events**: publisher holds a reference to subscriber via the delegate list.
  - If publisher is long-lived and subscriber is short-lived, you leak the subscriber unless you unsubscribe or use weak-event patterns.
- **Timers** (`System.Threading.Timer`, `PeriodicTimer` usage patterns):
  - long-lived timers capturing closures that capture services can keep object graphs alive.
- **Static caches**:
  - convenient, but “lifetime = process”; unbounded caches become unbounded memory.
- **Long-lived object graphs**:
  - e.g., DI singletons holding onto per-request services, or capturing `HttpContext` in a background task.

**Short example: event leak pattern**

```csharp
using System;

public sealed class Publisher
{
    public event EventHandler? SomethingHappened;
    public void Raise() => SomethingHappened?.Invoke(this, EventArgs.Empty);
}

public sealed class Subscriber : IDisposable
{
    private readonly Publisher _publisher;

    public Subscriber(Publisher publisher)
    {
        _publisher = publisher;
        _publisher.SomethingHappened += OnSomethingHappened;
    }

    private void OnSomethingHappened(object? sender, EventArgs e) { /* ... */ }

    public void Dispose() => _publisher.SomethingHappened -= OnSomethingHappened;
}
```

**Good to know**
- If you implement `IDisposable`, do it because you **own something that must be released**, not “because it’s a best practice”.
- Prefer bounded caches with eviction and metrics; treat caching as a performance feature with operational cost.
