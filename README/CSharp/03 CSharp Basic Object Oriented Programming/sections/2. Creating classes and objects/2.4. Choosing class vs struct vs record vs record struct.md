## 2.4. Choosing the right type shape: class vs struct vs record vs record struct

1. **Reference vs value semantics** (copying cost, aliasing bugs, mutation semantics)
2. **Equality** (reference equality, value equality, custom `Equals`/`GetHashCode` constraints)
3. **Performance guidance** (avoid large mutable structs; consider `readonly struct`; understand boxing)

---

### 1) **Reference vs value semantics**
**Definition**
- A **class** is a **reference type**: variables hold a *reference* (pointer-like) to an object on the managed heap.
  - Copying a class variable copies the **reference**, not the object.
- A **struct** is a **value type**: variables hold the **data itself** (inline), not a reference.
  - Copying a struct variable copies the **entire value**.
- A **record** is *not a third kind of runtime type* — it’s a *compiler feature* that generates:
  - value-like equality and deconstruction for **record class** (reference type)
  - value-like equality for **record struct** (value type)

**When to use which**
- Use a **class** when:
  - you need **identity** (“this specific object instance matters”),
  - instances are **mutable** and shared,
  - it represents an entity tracked over time (Customer, Session, Connection).
- Use a **struct** / **readonly struct** when:
  - it’s a **small value** (typically a handful of fields),
  - it behaves like a **number** (Money, Point, Range), and you want copy-by-value semantics,
  - it avoids heap allocations in hot paths (but only if you keep it small and immutable).
- Use a **record class** when:
  - you want a **value-like model** but still want reference-type behavior (nullable reference, identity sometimes irrelevant),
  - you want **non-destructive mutation** via `with` (it still creates a new instance).
- Use a **record struct** when:
  - you want a **value object** with generated equality + `with`,
  - you want to avoid heap allocation and keep data contiguous.

**Trade-offs and mistakes**
- **Mutable structs** are a common bug factory:
  - Copies happen implicitly (passing as parameter, returning, assigning), so mutations might affect a *copy*, not the original.
- **Large structs** are a performance trap:
  - copying becomes expensive, and you can end up worse than classes.
- **Class for everything** can create large object graphs → more allocations + more GC pressure.

**Example: copy semantics that surprises people**

```csharp
public struct Counter
{
    public int Value;
}

static void Increment(Counter c) => c.Value++; // increments a copy

var c1 = new Counter { Value = 10 };
Increment(c1);
Console.WriteLine(c1.Value); // 10 (not 11)
```

**Mentor guidance**
- If you choose `struct`, strongly prefer:
  - **immutability** (`readonly struct`) and
  - exposing behavior as methods that return a new value (or use `ref` carefully, only when you truly need it).

### 2) **Equality**
**Definition**
- **Reference equality**: two references point to the same instance (`ReferenceEquals(a, b)`).
- **Value equality**: two values represent the same logical value (`Equals`, `==`).

**Defaults (important)**
- `class` defaults:
  - `object.Equals` defaults to **reference equality** unless overridden.
- `struct` defaults:
  - `ValueType.Equals` performs **field-by-field** comparison (can be reflection-ish and slower than a custom implementation in some cases).
- `record` defaults:
  - record types generate **value-based equality** by default.

**When to customize equality**
- For **value objects** used as dictionary keys / set elements.
- When you want **case-insensitive** identity for strings (use `StringComparer` in collections rather than overriding equality on a type that wraps a string, unless you truly own that concept).

**Common mistakes**
- **Mutable key in a dictionary**:
  - If a key’s fields used in `GetHashCode` change after insertion, the dictionary becomes corrupted (the item becomes “lost”).
- **Inconsistent equality**:
  - If `Equals` is true but `GetHashCode` differs, collections misbehave.
- **Floating-point equality**:
  - `double`/`float` usually need tolerance-based comparisons; don’t use them as hash keys unless you fully understand the domain.

**Good practice**
- Implement `IEquatable<T>` for performance and correctness when you define value equality on non-record types.
- Prefer generated equality of `record` / `record struct` when it matches your semantics.

**Example: stable value equality key**

```csharp
public readonly record struct Email(string Value)
{
    public override string ToString() => Value;
}

var set = new HashSet<Email>();
set.Add(new Email("a@b.com"));
Console.WriteLine(set.Contains(new Email("a@b.com"))); // True (value equality)
```

### 3) **Performance guidance**
**Allocation and locality**
- `class` instances allocate on the managed heap.
  - Individual allocations are cheap, but *many* allocations increase GC work.
- `struct` values can live inline in arrays/other structs → better locality.

**Boxing**
- A value type **boxes** when converted to `object` or an interface it implements (unless constrained generics avoid it).
  - Boxing allocates and can create hidden GC pressure.

**Rules of thumb**
- Prefer **classes** for:
  - mutable entities, graph-like structures, DI-managed services.
- Prefer **records/structs** for:
  - small immutable values passed around frequently.
- Avoid:
  - large mutable structs,
  - frequent boxing in hot paths,
  - polymorphism-heavy designs in tight loops (see **3.5**).

**Performance note**
- Don’t pick `struct` just “to be faster”. Pick it because the semantics are right and it *helps locality/allocations* for your workload.
