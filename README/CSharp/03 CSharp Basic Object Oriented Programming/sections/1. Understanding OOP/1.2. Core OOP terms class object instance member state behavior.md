## 1.2. Core OOP terms (class, object, instance, member, state, behavior)

1. **Type vs instance** (compile-time shape vs runtime object)
2. **State vs behavior** (invariants + methods; keep state private and behavior explicit)
3. **Identity** (reference identity vs value equality; why this matters for bugs and collections)

---

### 1) **Type vs instance (compile-time shape vs runtime object)**
**Definition**
- A **type** (e.g., `Customer`) is the *compiler-known shape*: members, accessibility, constraints, and contracts.
- An **instance** (an *object*) is the *runtime value* created from a type (typically via `new`, deserialization, DI, or factories).

In C#, this distinction matters because:
- The compiler reasons about **static types** (what members you can call).
- The runtime executes operations on **runtime types** (what the actual object is).

**When to care**
- **API design**: expose the *narrowest useful type* (often an interface) to reduce coupling.
- **Testing**: program to contracts (interfaces/abstractions) so you can substitute fakes.
- **Performance/correctness**: understand when you pay for runtime checks (casts, pattern matching, virtual dispatch).

**Trade-offs**
- Exposing concrete types can be simpler and faster to navigate, but increases coupling and makes changes more breaking.
- Exposing interfaces improves flexibility, but too many abstractions can reduce readability and hinder debugging.

**Common mistakes (mentor notes)**
- **Mistake: leaking concrete implementation types** from your public API “because it’s easy”.
  - You lock callers into your representation (versioning pain).
- **Mistake: confusing compile-time and runtime types**:
  - Assuming `IAnimal a = new Dog();` means “a is an IAnimal” at runtime. It’s a `Dog` instance stored through an `IAnimal` reference.

**Example: static type vs runtime type**

```csharp
public interface IClock
{
    DateTimeOffset UtcNow { get; }
}

public sealed class SystemClock : IClock
{
    public DateTimeOffset UtcNow => DateTimeOffset.UtcNow;
}

static string Describe(IClock clock)
{
    // Compile-time type: IClock (only UtcNow is visible).
    // Runtime type might be SystemClock, FakeClock, etc.
    return $"{clock.GetType().Name} @ {clock.UtcNow:O}";
}
```

**Performance note**
- Interface calls can be slightly harder to inline/devirtualize than direct calls. In most app code this is irrelevant; in hot loops it can matter.
- If you need both abstraction and performance in tight paths, generics can help (e.g., `where TClock : IClock`), but only apply this when measurement proves it matters.

### 2) **State vs behavior (invariants + methods)**
**Definition**
- **State**: the data an object owns (fields/properties).
- **Behavior**: operations that change or depend on state (methods).
- **Invariant**: a rule that must always hold true for valid state.

**When to use what**
- Put **invariants** where they can’t be bypassed:
  - constructors, factories, and intention-revealing methods.
- Keep state **private** and expose behavior through a controlled surface.

**Trade-offs**
- Over-encapsulation can make mapping/serialization harder. Solve this with:
  - explicit DTOs,
  - mapping layers,
  - or carefully designed constructors/factories (not public setters everywhere).

**Common mistakes**
- **Anemic models**: everything is `get; set;` and invariants live in scattered services.
- **Property setters doing heavy work**: surprises callers, introduces hidden costs and exceptions.

**Example: “valid states only” via methods**

```csharp
public sealed class Cart
{
    private readonly List<CartLine> _lines = [];

    public IReadOnlyList<CartLine> Lines => _lines;

    public void AddItem(string sku, int quantity)
    {
        if (string.IsNullOrWhiteSpace(sku)) throw new ArgumentException("SKU is required.", nameof(sku));
        if (quantity <= 0) throw new ArgumentOutOfRangeException(nameof(quantity));

        _lines.Add(new CartLine(sku, quantity));
    }
}

public sealed record CartLine(string Sku, int Quantity);
```

**Good to know**
- Not every type needs deep behavior. Data-only DTOs are fine at boundaries (serialization, API contracts). The key is not to confuse DTOs with domain models that must enforce invariants.

### 3) **Identity (reference identity vs value equality)**
**Definition**
- **Reference identity**: two references point to the exact same object instance (`ReferenceEquals(a, b)`).
- **Value equality**: two values are considered equal because their *data* is equal (`a.Equals(b)`).

**Why this matters**
- Identity affects:
  - collection behavior (`Dictionary` keys, `HashSet` uniqueness),
  - caching,
  - tracking changes (ORMs),
  - and subtle bugs (mutating a shared reference).

**Common mistakes**
- Using mutable objects as dictionary keys (hash changes -> key becomes “lost”).
- Assuming records are “always safe”: records provide value equality, but if they contain mutable reference fields, you can still get surprises.
