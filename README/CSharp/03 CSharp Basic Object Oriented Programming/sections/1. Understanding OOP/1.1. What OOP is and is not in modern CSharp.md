## 1.1. What OOP is (and what it is not) in modern C#

1. **OOP goals** (modeling, encapsulation, local reasoning, change isolation) vs “just using classes”
2. **OOP vs data-oriented design** (when object graphs help vs when they fight performance/cache locality)
3. **Modern C# reality** (OOP + generics + functional-ish features + async; you choose the right tool per layer)

---

### 1) **OOP goals vs “just using classes”**
**Definition**
- **Object-Oriented Programming (OOP)** is primarily a *design approach*: you model a problem as a set of **objects** that combine:
  - **State** (data the object owns) and
  - **Behavior** (methods that operate on that state)
- The real goal is not “use classes everywhere”. The goal is to make code:
  - **Easy to change** without breaking unrelated parts (change isolation)
  - **Locally understandable** (you can reason about a part without reading the whole system)
  - **Correct by construction** (invariants are enforced at boundaries)

**When to use**
- Use OOP when you need:
  - **Long-lived domain concepts** with rules/invariants (Order, Money, InventoryItem).
  - A clear **ownership model** (who is responsible for what state).
  - **Extensibility** via stable contracts (interfaces), especially at boundaries (I/O, storage, payment gateways).

**Trade-offs**
- OOP can lead to:
  - **Over-abstraction** (too many tiny interfaces/types, hard navigation)
  - **Anemic domain models** (classes that only store data; rules live elsewhere)
  - **Indirection costs** (virtual calls, allocations, more object graphs)

**Common mistakes (mentor notes)**
- **Mistake: “Everything must be a class.”**
  - In modern C#, sometimes a *function* or a small *immutable value* is the right tool.
- **Mistake: exposing fields/mutable collections.**
  - You leak invariants, and future changes become breaking changes.
- **Mistake: mixing responsibilities.**
  - Your objects become “God objects” with too much knowledge.

**Example: encapsulation + invariants (minimal but real)**

```csharp
using System;
using System.Collections.Generic;
using System.Collections.ObjectModel;

public sealed class BankAccount
{
    private decimal _balance;
    private readonly List<string> _audit = [];

    public BankAccount(decimal openingBalance)
    {
        if (openingBalance < 0) throw new ArgumentOutOfRangeException(nameof(openingBalance));
        _balance = openingBalance;
        _audit.Add($"Opened with {_balance}");
    }

    public decimal Balance => _balance;
    public ReadOnlyCollection<string> Audit => _audit.AsReadOnly(); // don't leak mutability

    public void Deposit(decimal amount)
    {
        if (amount <= 0) throw new ArgumentOutOfRangeException(nameof(amount));
        _balance += amount;
        _audit.Add($"Deposit {amount} => {_balance}");
    }

    public bool TryWithdraw(decimal amount)
    {
        if (amount <= 0) return false;
        if (_balance < amount) return false;
        _balance -= amount;
        _audit.Add($"Withdraw {amount} => {_balance}");
        return true;
    }
}
```

**Performance note**
- OOP’s performance failures are rarely from “classes are slow”; they’re from:
  - **too many allocations** (object-per-element designs),
  - **poor locality** (pointer-chasing across large object graphs),
  - **unnecessary polymorphism** in hot loops.
Start with a clear design, then measure; optimize by reducing allocations and improving data layout if needed.

### 2) **OOP vs data-oriented design (DOD)**
**Definition**
- **OOP** organizes code around *objects* and their behaviors.
- **Data-oriented design** organizes code around:
  - the **shape of data** and
  - how the CPU processes it efficiently (cache locality, vectorization, minimal indirection).

**When OOP shines**
- Business/domain logic with complex rules, validations, permissions, workflows.
- Clear ownership and lifecycle boundaries (aggregate roots, entities, value objects).

**When DOD (or “less OOP”) wins**
- Hot-path processing over large collections:
  - parsing, numerics, simulation, image/audio processing, telemetry pipelines.
- Places where memory layout and cache locality dominate.

**Practical guidance (mentor rules of thumb)**
- Don’t turn your whole app into a “DOD-only” or “OOP-only” ideology.
- Use **OOP at the boundaries** where humans reason about behavior and rules.
- Use **data-oriented representations** in performance-critical kernels.

**Common mistake**
- Building large object graphs for what is essentially tabular data, then being surprised by:
  - higher GC pressure,
  - slower iteration,
  - more cache misses.

**Performance note**
- “Many small objects” often means:
  - more allocations,
  - more GC work,
  - more pointer chasing.
If you see performance issues, consider:
  - `struct` / `readonly struct` for small immutable values,
  - `Span<T>` / `ReadOnlySpan<T>` to avoid slicing allocations,
  - arrays or contiguous storage for bulk data (but keep design clarity).

### 3) **Modern C# reality: OOP + generics + functional-ish + async**
**Key idea**
Modern C# is multi-paradigm:
- OOP: classes/interfaces for modeling and contracts.
- Generics: type-safe reuse without runtime casts.
- Functional-ish features: immutability, expressions, pattern matching.
- Async/await: scalable I/O without blocking threads.

**What to prefer in C# 15 era**
- **Immutability where it fits**:
  - use `record` / `record struct` for value-like models.
- **Explicit contracts**:
  - interfaces for boundaries, not for every method.
- **Async for I/O end-to-end**:
  - don’t block on Tasks (`.Result`, `.Wait()`).
  - For the deep concurrency model, see: [1.1. High-level execution model concepts](<../../../29 Cuncurrent & Parallel/sections/1. Core Terminology in Concurrency & Parallelism/1.1. High-level execution model concepts.md>).

**Deprecated / legacy mindset to avoid**
- “Base classes everywhere” as the default extension mechanism.
  - Prefer composition + interfaces; keep inheritance shallow and intentional.

**Good to know**
- “Modern OOP” in C# often means:
  - **composition over inheritance**,
  - **small, stable public APIs**,
  - clear ownership and lifetime,
  - using language features (`required`, primary constructors, pattern matching) to prevent invalid states.
