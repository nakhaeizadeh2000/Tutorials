2. **Class vs object vs reference vs value type** (plus real pitfalls like boxing and mutable keys)
3. **Interface vs abstract class vs base class** (design + testability + versioning + perf framing)

---

### 1) **Explain OOP and the 4 pillars (C#-correct)**
**What interviewers actually want**
- You can explain **why** OOP exists (manage complexity and change), not just list words.
- You understand the **C#-specific** reality: you can do OOP with classes, records, interfaces; inheritance is optional; composition is common.

**Short definition (good interview version)**
- **OOP** models a system as **objects** that *own state* and *expose behavior* behind a boundary.
- The goal is **maintainability + correctness**, then performance where it matters.

**The 4 pillars (mentor-grade, C#-specific)**
- **Encapsulation**: Keep representation private; expose a small API that preserves invariants.  
  - In C#: private fields + methods/properties; avoid public setters by default.
  - Deep dive: see `README/CSharp/03 CSharp Basic Object Oriented Programming/sections/3. Important points about objects/3.3. Encapsulation and invariants valid states only.md`.
- **Abstraction**: Hide details behind a contract.  
  - In C#: interfaces (and sometimes abstract base classes) define what callers can rely on.
  - Deep dive: see `README/CSharp/03 CSharp Basic Object Oriented Programming/sections/4. Basic OOP design/4.2. Interfaces and dependency injection without overengineering.md`.
- **Inheritance**: Reuse/extend behavior by deriving from a base type.  
  - In C#: use *sparingly*; keep hierarchies shallow; prefer sealed types unless you truly need extension points.
  - Deep dive: see `README/CSharp/03 CSharp Basic Object Oriented Programming/sections/4. Basic OOP design/4.1. Composition over inheritance practical rules of thumb.md`.
- **Polymorphism**: Same call site, different behavior based on runtime type.  
  - In C#: via virtual/override, interface dispatch, pattern matching, and generics (compile-time polymorphism).
  - Performance deep dive: see `README/CSharp/03 CSharp Basic Object Oriented Programming/sections/3. Important points about objects/3.5. Virtual dispatch interface calls and performance basics.md`.

**Common pitfalls**
- Saying “OOP = inheritance”. In modern C#, *composition + interfaces* is often the safer default.
- Confusing **encapsulation** with “I used properties”. Properties can still leak invalid states.

**Micro example (encapsulation + polymorphism via interface)**

```csharp
public interface IDiscountPolicy
{
    decimal Apply(decimal subtotal);
}

public sealed class NoDiscount : IDiscountPolicy
{
    public decimal Apply(decimal subtotal) => subtotal;
}

public sealed class PercentageDiscount(decimal rate) : IDiscountPolicy
{
    public decimal Apply(decimal subtotal) => subtotal * (1 - rate);
}

public sealed class Order
{
    public decimal Subtotal { get; }
    public Order(decimal subtotal) => Subtotal = subtotal >= 0 ? subtotal : throw new ArgumentOutOfRangeException(nameof(subtotal));

    public decimal Total(IDiscountPolicy discount) => discount.Apply(Subtotal);
}
```

**Performance note**
- Interface dispatch is usually “fast enough” for business logic; avoid polymorphism only in **tight hot loops** (see 3.5).

### 2) **Class vs object vs reference vs value type (and the real pitfalls)**
**Definitions**
- **Class**: a *reference type* definition. In C#, instances live on the managed heap (conceptually; runtime may optimize).
- **Object / instance**: a runtime value created from a type (`new BankAccount(...)` creates an object/instance).
- **Reference type**: variables hold a reference (pointer-like) to an object; assignment copies the reference (**aliasing**).
- **Value type** (`struct`, `record struct`): variables hold the value inline; assignment copies the value (can be expensive if large).

**When to use which**
- Use **class** for:
  - entities with identity/lifetime/optional null,
  - polymorphism and shared mutable state (carefully).
- Use **struct / record struct** for:
  - small immutable values (Money, Point, DateRange),
  - performance-sensitive, allocation-free data that is copied cheaply.

**Key pitfalls to mention**
- **Boxing**: converting a value type to `object`/interface allocates and copies.  
  - Avoid “value type implements interface used in a hot path”.
- **Mutable structs**: can create bugs (copies mutate independently) and performance issues (defensive copies).
- **Mutable keys in dictionaries**: if `Equals/GetHashCode` depends on mutable state, keys “disappear”.
  - Deep dive: see `.../3.2. Equality hashing and identity in collections.md`.
- **Aliasing bugs**: two references can mutate the same object unexpectedly.
  - Deep dive: see `.../3.1. Reference semantics aliasing mutation defensive design.md`.

**One-liner you can say in an interview**
- “Classes are about **identity and encapsulated behavior**; structs are about **cheap values**. If a struct is big or mutable, I reconsider.”

### 3) **Interface vs abstract class vs base class (how to decide)**
**Core idea**
Pick the tool that matches what you need to guarantee and evolve.

**Interfaces**
- Best for **contracts** and “I depend on capabilities”.
- Great for **testability** and decoupling at boundaries.
- Versioning: adding members can be breaking; keep them small/cohesive.
- Prefer “role-style” interfaces (`IClock`, `IEmailSender`) not “everything” interfaces.

**Abstract classes**
- Use when you need:
  - shared implementation,
  - protected helpers,
  - a controlled extension surface.
- Risk: you lock consumers into a hierarchy; changes can be breaking.

**Concrete base classes**
- Use when you’re modeling a real “is-a” relationship and you own the hierarchy (e.g., framework internals).
- In application code: often avoid; prefer composition.

**Modern guidance (C# 15 era)**
- Prefer **interfaces + composition** as the default.
- Use inheritance intentionally, keep base classes small, and avoid deep chains.

**Performance framing**
- Interface/virtual dispatch adds indirection and can reduce inlining.
- In business code, that rarely matters; in hot paths, use generics or direct calls (see 3.5).

**Quick decision table**
- Want multiple interchangeable implementations? **Interface**
- Want shared code + a controlled customization point? **Abstract class**
- Want to reuse code but don’t need polymorphism? Consider **composition** (a field of a helper type) instead of inheritance.
