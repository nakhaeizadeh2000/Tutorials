## 5.2. Scenario questions: design a small model (and defend the trade-offs)

1. **Model a domain object** (invariants, encapsulation, nullability)
2. **Extensibility without inheritance** (strategies, composition, DI)
3. **Performance-aware answers** (avoid excess allocations, stable equality, correct lifetimes)

---

### 1) **Model a domain object (invariants, encapsulation, nullability)**
**What the interviewer is really testing**
- Can you identify **invariants** and enforce them **in one place**?
- Can you avoid invalid states and “bag-of-data” design?
- Do you use modern C# (nullable reference types, `required`, `init`, records) appropriately?

**A strong approach**
- Start by writing down invariants as sentences, e.g.:
  - “A `CartItem` quantity is always \( \ge 1 \)”
  - “A `Money` value has a currency and amount; arithmetic is currency-safe”
  - “An `Order` can’t be shipped before it’s paid”
- Choose **type shapes**:
  - Use a **`record struct` or `readonly struct`** for small immutable value objects (`Money`, `Sku`).
  - Use a **class** for entities with identity and lifecycle (`Order`).
- Keep state private; expose behavior via intention-revealing methods.

**Example: small model with invariants**

```csharp
using System;
using System.Collections.Generic;

public readonly record struct Sku(string Value)
{
    public Sku(string value) : this(value)
    {
        if (string.IsNullOrWhiteSpace(value)) throw new ArgumentException("SKU is required.", nameof(value));
    }
}

public sealed class Cart
{
    private readonly Dictionary<Sku, int> _items = [];

    public IReadOnlyDictionary<Sku, int> Items => _items;

    public void Add(Sku sku, int quantity = 1)
    {
        if (quantity <= 0) throw new ArgumentOutOfRangeException(nameof(quantity));

        _items.TryGetValue(sku, out int existing);
        _items[sku] = existing + quantity;
    }

    public bool TryRemove(Sku sku, int quantity = 1)
    {
        if (quantity <= 0) return false;
        if (!_items.TryGetValue(sku, out int existing)) return false;
        if (existing < quantity) return false;

        int remaining = existing - quantity;
        if (remaining == 0) _items.Remove(sku);
        else _items[sku] = remaining;
        return true;
    }
}
```

**Mentor notes**
- `IReadOnlyDictionary<,>` is a *read-only view*, not an immutable dictionary. That’s fine here because we never expose the mutable backing dictionary itself. If immutability is required, return a snapshot (which allocates).
- With nullable reference types enabled, prefer making “required data” non-null by construction rather than checking for null everywhere. If you need “optional”, model it explicitly.

### 2) **Extensibility without inheritance (strategies, composition, DI)**
**What interviewers like to hear**
- “I default to **composition over inheritance** because it avoids fragile base classes and makes behavior swappable/testable.”
- “I use interfaces for **boundaries**, not everywhere.”

**Example: strategy via composition**

```csharp
public interface IShippingCostPolicy
{
    decimal Calculate(decimal weightKg, decimal distanceKm);
}

public sealed class FlatRateShippingPolicy(decimal rate) : IShippingCostPolicy
{
    public decimal Calculate(decimal weightKg, decimal distanceKm) => rate;
}

public sealed class DistanceShippingPolicy(decimal perKm) : IShippingCostPolicy
{
    public decimal Calculate(decimal weightKg, decimal distanceKm) => perKm * distanceKm;
}

public sealed class CheckoutService(IShippingCostPolicy shipping)
{
    public decimal QuoteShipping(decimal weightKg, decimal distanceKm) =>
        shipping.Calculate(weightKg, distanceKm);
}
```

**Trade-offs**
- Composition may create more small objects and indirection, but it typically improves testability and maintainability.
- In hot paths, if polymorphism becomes a cost, you can:
  - keep the strategy stable (so JIT can sometimes devirtualize),
  - use generics where appropriate,
  - or move the hot kernel into a data-oriented function (see section [3.5](<../3. Important points about objects/3.5. Virtual dispatch interface calls and performance basics.md>) for perf framing).

### 3) **Performance-aware answers (allocations, equality, lifetimes)**
**What “performance-aware” means in an interview**
- You don’t prematurely micro-optimize, but you avoid known foot-guns:
  - allocating in loops,
  - mutable dictionary keys,
  - accidental boxing,
  - hiding expensive work behind “cheap-looking” properties,
  - leaking resources due to unclear ownership.

**A good checklist to mention**
- **Allocations**:
  - Prefer simple loops and streaming when appropriate; avoid materializing intermediate lists in hot paths.
  - Avoid per-item object creation in large collections unless necessary.
- **Equality**:
  - If the type is used as a key, equality and hashing must be stable; mutable keys are a common bug (see section [3.2](<../3. Important points about objects/3.2. Equality hashing and identity in collections.md>)).
  - Use explicit comparers (`StringComparer.Ordinal`) instead of default culture-sensitive comparisons.
- **Lifetimes**:
  - Define ownership (who disposes) clearly and keep it deterministic.
  - Don’t use finalizers as your primary cleanup mechanism.
