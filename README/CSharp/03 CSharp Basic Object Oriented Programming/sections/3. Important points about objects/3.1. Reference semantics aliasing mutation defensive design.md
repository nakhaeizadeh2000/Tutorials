## 3.1. Reference semantics: aliasing, mutation, and defensive design

1. **Aliasing hazards** (two references → same object; unexpected cross-effects)
2. **Immutability strategies** (records, readonly fields, private setters, copy-on-write patterns)
3. **Performance trade-offs** (immutability can allocate; measure hot paths; avoid unnecessary copying)

---

### 1) **Aliasing hazards**

**Definition**

- With **reference types** (`class`), a variable holds a **reference (pointer-like)** to an object on the managed heap.
- **Aliasing** means: *two or more references point to the same object*. Mutating through one reference affects what everyone else sees.

**Why it matters**

- Aliasing is a top source of “impossible” bugs: state changes far away from where you’re debugging.
- Aliasing + concurrency can become data races if the object is shared across threads without synchronization (deep treatment is in the concurrency domain).

**When aliasing is OK**

- When the object is **intentionally shared** and has a clear owner and thread-safety rules:
  - Immutable objects (safe to share).
  - Thread-safe objects (safe to share with correct synchronization).
  - Shared services (e.g., a singleton `HttpClient`), where mutation is either absent or internally synchronized.

**Common mistakes (mentor notes)**

- **Mistake: returning a mutable internal collection**:
  - Callers can mutate your internal state and break invariants.
- **Mistake: reusing mutable objects across requests** (especially in servers):
  - Hidden shared state becomes a correctness and security risk.
- **Mistake: “defensive copying everywhere”**:
  - It may fix aliasing bugs but can create a performance cliff (allocations and copying).

**Example: how aliasing bites**

```csharp
using System;
using System.Collections.Generic;

public sealed class Cart
{
    private readonly List<string> _items = [];

    // BAD: leaks internal mutable list => callers can mutate your state.
    public List<string> Items => _items;

    public void Add(string sku) => _items.Add(sku);
}

var cart = new Cart();
cart.Add("A");

// Aliasing bug: external code mutates internal state.
cart.Items.Clear();
Console.WriteLine(cart.Items.Count); // 0 (invariant broken from outside)
```

**Better: expose a read-only view**

```csharp
using System;
using System.Collections.Generic;
using System.Collections.ObjectModel;

public sealed class Cart
{
    private readonly List<string> _items = [];

    public ReadOnlyCollection<string> Items => _items.AsReadOnly();
    public void Add(string sku) => _items.Add(sku);
}
```

**Performance note**

- `AsReadOnly()` does **not** copy the list; it wraps it (cheap). It still reflects mutations you make internally—which is usually exactly what you want.
- If you need a snapshot, returning `items.ToArray()` gives isolation but allocates.

### 2) **Immutability strategies**

**Definition**

- An object is **immutable** if its externally observable state does not change after construction.
- Immutability reduces aliasing risk and makes concurrent sharing easier.

**Strategies in modern C#**

- **Records for value-like data**:
  - `record` and `record struct` give value-based equality by default (see **3.2** for equality rules).
- **Private setters + intention-revealing methods**:
  - Keep mutation behind methods that enforce invariants.
- **`readonly` fields**:
  - Prevent reassignment after construction (does not magically make nested objects immutable).
- **Copy-on-write**:
  - Create a new instance with changes instead of mutating an existing one.

**Example: record + with-expression (copy-on-write)**

```csharp
public sealed record CustomerId(string Value);

public sealed record Customer(CustomerId Id, string Name, string Email)
{
    public Customer Rename(string name) => this with { Name = name };
}
```

**Common mistakes**

- **Mistake: assuming `readonly` makes deep state immutable**:
  - A `readonly List<T>` field still points to a mutable list.
- **Mistake: mixing immutability with exposed mutable internals**:
  - A record that contains a `List<T>` is not meaningfully immutable unless you freeze it.

**Good to know**

- If you need “immutable collections”, prefer `System.Collections.Immutable` (NuGet) only when it actually helps; it’s not free. Often, “mutable privately + read-only externally” is enough.

---

### 3) **Performance trade-offs**

**Key trade-off**

- Immutability often means **more allocations** (new objects on every change).
- Mutability can be faster for hot paths but increases bug risk and coordination cost.

**Mentor guidance**

- Start with the design that makes invariants obvious (often immutable or encapsulated mutation).
- If performance becomes a problem:
  - Identify allocation hotspots (profilers, allocation traces).
  - Use targeted optimizations (pooling, struct/value types, avoiding per-item objects) only where necessary.

**Performance note**

- In .NET, **Gen0 allocations are cheap** but not free. Many small allocations increase GC frequency.
- Avoid “defensive copies on every getter” unless correctness requires it; prefer read-only views or explicit snapshot methods.
