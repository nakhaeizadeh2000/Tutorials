## 3.4. Copying and cloning: shallow vs deep copies (and when you need neither)

1. **Shallow copy meaning** (references copied, not the object graph)
2. **Deep copy hazards** (cycles, shared references, identity loss, performance)
3. **Better options** (immutability, with-expressions for records, explicit copy constructors)

---

### 1) **Shallow copy meaning (references copied, not the object graph)**
**Definition**
- A **shallow copy** duplicates the *top-level container*, but **does not duplicate the referenced objects** inside it.
- In C#, this typically means:
  - For **classes** (reference types): copying a variable copies the **reference**, not the object.
  - For **structs** (value types): assignment copies the struct’s fields; if it contains references, those references still point to the same underlying objects.

**When it matters**
- Anytime you have nested objects, collections, or a graph:
  - `Order` has `List<OrderLine>`; `OrderLine` has `Product`.
  - A shallow copy can unintentionally share the list and/or items.

**Common mistakes**
- Assuming `var b = a;` makes a “copy” of a class instance. It does not.
- Copying a type with a `List<T>` field and expecting independent lists.

**Example: shallow copy surprise**

```csharp
using System;
using System.Collections.Generic;

public sealed class Basket
{
    public List<string> Items { get; } = [];
}

var a = new Basket();
a.Items.Add("Milk");

var b = a;                 // not a copy; b references the same object
b.Items.Add("Bread");

Console.WriteLine(a.Items.Count); // 2 (same list)
```

**Good to know**
- `MemberwiseClone()` (protected on `object`) creates a **shallow copy**. It is rarely correct for domain models unless your type is effectively immutable or only contains value-like fields.

---

### 2) **Deep copy hazards (cycles, shared references, identity loss, performance)**
**Definition**
- A **deep copy** attempts to duplicate the entire object graph so the copy is independent.

**Why deep copying is hard**
- **Cycles**: A → B → A. Naive recursion can stack overflow or duplicate nodes incorrectly.
- **Shared references**: A → X and B → X. A “deep copy everything” might create X' twice and break the relationship.
- **Identity and semantics**:
  - Some references should stay shared (e.g., a cached singleton value).
  - Some objects represent identities (e.g., entity IDs); copying them can create semantic bugs.
- **Performance and memory**:
  - Deep copy can allocate a lot and can be \(O(n)\) or worse depending on graph size.

**When deep copy is appropriate**
- For **snapshots** of state for undo/redo, simulation steps, or isolation in tests—*when you truly need graph independence* and can define a correct copying policy.

**Common mistakes**
- Using serialization (JSON/BinaryFormatter) as a “deep clone” trick.
  - **BinaryFormatter is obsolete and insecure**; do not use it.
  - JSON-based copying can silently lose types, drop private state, break references, and is usually slow.

**Better approaches than “deep clone everything”**
- Define a **copy policy** explicitly:
  - Which parts are copied?
  - Which parts are shared?
  - What defines identity?
- Prefer immutable models or small value objects where copying is cheap and correct.

---

### 3) **Better options (immutability, with-expressions for records, explicit copy constructors)**
**Option A: Prefer immutability**
- If objects don’t change, you avoid the entire “how do I clone safely?” problem.
- Use:
  - `record` / `record struct` for value-like models.
  - `readonly` fields, private setters, and methods that return a new instance.

**Option B: Records + `with` expressions (best for value objects)**

```csharp
public sealed record Money(decimal Amount, string Currency);

var usd = new Money(Amount: 10m, Currency: "USD");
var usdAfter = usd with { Amount = 12m }; // non-destructive copy
```

**Option C: Explicit copy constructor / copy method (best for domain policy)**
- This is often the most maintainable because it’s explicit and reviewable.

```csharp
using System;
using System.Collections.Generic;

public sealed class Order
{
    private readonly List<OrderLine> _lines;
    public IReadOnlyList<OrderLine> Lines => _lines;
    public Guid Id { get; }

    public Order(Guid id, IEnumerable<OrderLine> lines)
    {
        Id = id;
        _lines = new List<OrderLine>(lines);
    }

    // Copy constructor with explicit policy: copy the list, reuse immutable lines (or copy them too).
    public Order(Order source)
    {
        Id = source.Id; // entity identity intentionally preserved (policy decision)
        _lines = new List<OrderLine>(source._lines);
    }
}

public sealed record OrderLine(string Sku, int Quantity);
```

**Performance note**
- If you copy frequently, focus on:
  - reducing the copied surface area,
  - using immutable components so sharing is safe,
  - avoiding deep copies of large graphs.
