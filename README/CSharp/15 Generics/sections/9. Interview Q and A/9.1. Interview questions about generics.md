### 1) **Explain “generic type” vs “generic method”** (and when to prefer each)

**Definition**

- A **generic type** has type parameters as part of the type’s identity: `List<T>`, `Dictionary<TKey, TValue>`, `Result<TValue, TError>`.
- A **generic method** has type parameters scoped to one method: `static T Identity<T>(T x) => x;`.

**How to choose (mentor rule: use the smallest abstraction that communicates intent)**

- Prefer a **generic method** when:
  - The genericity is local to a single operation.
  - You don’t need to store `T` as state across calls.
  - You want minimal surface area (less versioning risk).
- Prefer a **generic type** when:
  - `T` is part of the object’s ongoing state/invariant (e.g., a typed cache, a typed pipeline stage, a typed container).
  - The type has multiple methods that operate on the same `T` and you want call sites to remain clean.

**Trade-offs**

- Generic types can be easier to read at call sites because `T` is fixed once.
- Generic methods often infer `T`, reducing verbosity, but inference can fail in edge cases (see `Generics/1.2`).

**Mini example**

```csharp
using System;
using System.Collections.Generic;

public sealed class Cache<TKey, TValue>
    where TKey : notnull
{
    private readonly Dictionary<TKey, TValue> _map = new();

    public bool TryGet(TKey key, out TValue value) => _map.TryGetValue(key, out value);
    public void Set(TKey key, TValue value) => _map[key] = value;
}

public static class Algorithms
{
    public static T Identity<T>(T x) => x; // generic method: no need for a generic type
}
```

### 2) **Explain constraints** (what each constraint enables; why constraints affect both correctness and perf)

Constraints are part of your **public contract** and shape:

- **What operations are legal** inside the generic code (`T?`, `new()`, interface members, static abstract members).
- **What the compiler can prove** (nullability contracts, member availability).
- **How callers experience the API** (error messages, usability).
- Sometimes **performance characteristics** (e.g., enabling allocation-free paths, avoiding some boxing patterns).

### 3) **Explain variance** (producer/consumer model; why classes are invariant)

**Core mental model**

- **Producers** of `T` can often be **covariant** (`out T`) — e.g., `IEnumerable<out T>`.
- **Consumers** of `T` can often be **contravariant** (`in T`) — e.g., `IComparer<in T>`.
- Types that both **produce and consume** `T` (read/write) are usually **invariant**.

Where to study it deeply (single canonical place):

### 4) **Why `EqualityComparer<T>.Default` matters** (correctness + perf; avoids boxing and virtual dispatch patterns)

**What it is**

`EqualityComparer<T>.Default` chooses an equality strategy that is correct for the actual `T`:

- If `T` implements `IEquatable<T>`, it uses it (fast, avoids virtual dispatch patterns).
- Otherwise it falls back to `object.Equals` semantics for the type.

**Why it’s the right default in generic code**

- You cannot reliably use `==` for unconstrained `T`.
- You avoid many “accidental boxing” patterns that happen when you force values through `object`.

**Example**

```csharp
using System.Collections.Generic;

public static class GenericEquality
{
    public static bool AreEqual<T>(T left, T right) =>
        EqualityComparer<T>.Default.Equals(left, right);
}
```

Mentor note:

- For **hash-based collections**, pair it with `GetHashCode` via the same comparer (`EqualityComparer<T>.Default.GetHashCode(value)`), otherwise you can break dictionary invariants.

### 5) **Common perf pitfalls** (boxing, `object` APIs, `params object[]`, interface dispatch in hot paths)

**The shortlist interviewers actually care about**

- **Boxing**: value types flowing into `object`/non-generic interfaces/`params object[]` can allocate and increase GC pressure.
  - Deep source: **See** `README/CSharp/13 Structures/sections/3. Struct vs class/3.3. Boxing interfaces generics.md`.
- **Accidental allocations**: LINQ in hot paths, capturing lambdas, iterator allocations, `params` arrays.
  - If you need LINQ, keep it off the hot path or measure it.
- **Interface/virtual dispatch in tight loops**: can block inlining; sometimes fine, sometimes a real throughput tax.
  - Deep source for JIT behavior: **See** `README/CSharp/01 Fundamental Theories/sections/2. NET architecture/2.2. IL JIT tiered compilation AOT.md`.

**Mentor rule**

Performance isn’t “avoid interfaces”; it’s “avoid **unintentional costs** and measure hot paths.” Design the API so the fast path is also the easiest path.
