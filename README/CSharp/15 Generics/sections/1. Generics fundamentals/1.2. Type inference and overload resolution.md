## 1.2. Generic type inference and overload resolution (what the compiler decides)

1. **Inference rules** (when `T` can be inferred and when you must specify it)
2. **Ambiguity traps** (null/default literals, lambdas, method groups, overload sets)
3. **Mentor rule** (design APIs so the obvious call is also the correct one)

### 1) **Inference rules** (when `T` can be inferred and when you must specify it)

**Definition**

**Type inference** is the compiler’s process of figuring out the concrete type arguments for a generic method call:

```csharp
static T Identity<T>(T value) => value;

var x = Identity(123); // compiler infers T = int
```

This is **compile-time only**. At runtime there is no “inference step”; the method is already bound.

**What inference uses**

For method calls, inference primarily uses:

- **Argument expressions** and their **static types**
- The **target type** (assignment context / return type context) in some cases
- Generic constraints (to validate, not usually to “discover”)
- Lambda conversions (when a lambda is used as an argument)

**When inference fails (and what to do)**

Inference can fail when the compiler cannot uniquely determine `T` from the call-site information.

Common fixes:

- **Specify the type arguments** explicitly:

```csharp
static TResult Map<T, TResult>(T value, Func<T, TResult> f) => f(value);

var s = Map<int, string>(123, static x => x.ToString());
```

- **Add a cast** (especially with lambdas/method groups) to give the compiler a target delegate type.
- **Change the API signature** so the type arguments are discoverable from inputs (best for public APIs).

**Mentor stress: design for inference**

If a method is meant to be called frequently, aim for **signatures that infer naturally**. A typical inference-friendly shape is:

- `Foo<T>(T input, ...)`

Less inference-friendly shapes include:

- `Foo<T>(..., Func<T> factory)` when `T` doesn’t appear elsewhere
- `Foo<T>(object input)` (because `T` isn’t tied to input)

**Performance note**

- Inference has **zero runtime cost**. The performance impact comes indirectly: bad inference often leads teams to add overloads or `object`-typed fallbacks that introduce **boxing** or allocations.

### 2) **Ambiguity traps** (null/default literals, lambdas, method groups, overload sets)

Many “why is this ambiguous?” problems are not unique to generics, but generics amplify them because inference and overload resolution interact.

If you want the **full** overload-resolution mental model, see `README/CSharp/05 Methods/sections/5. Overload resolution and overloading/5.1. Method overloading rules ambiguity API design.md`. This section focuses on the **generic-specific** failure modes and the design patterns to avoid them.

#### Trap A: `null` / `default`

`null` provides little information. `default` provides *no* type until context gives it one.

```csharp
static T Echo<T>(T value) => value;

// var a = Echo(null);     // error: cannot infer T
// var b = Echo(default);  // error: cannot infer T

string? ok = Echo<string?>(default);
```

**Mentor rule**

- If `null` is a valid input for your API, make it **explicit** in the signature:
  - For reference types: consider `T?` + a constraint such as `where T : class` when appropriate.
  - For “not null allowed”: prefer `where T : notnull` (and validate at boundaries if inputs originate from untrusted sources).

#### Trap B: lambdas and method groups

A lambda can convert to many delegate types if the parameter/return shapes match.

```csharp
static void Use<T>(Func<T> f) { }
static void Use<T>(Func<int, T> f) { }

// Use(static () => 0); // ambiguous (both could work with different T)
Use<int>(static () => 0); // disambiguated by explicit type argument
```

**Mentor rule**

- Avoid public APIs where a “simple lambda” can bind to multiple overloads. Prefer naming the operation differently or using different parameter counts/types so calls are unambiguous.

#### Trap C: “overload soup” + generic overloads

Overloads that differ only by generic parameters tend to produce surprising ambiguities, especially when combined with:

- `params`
- optional parameters
- implicit numeric conversions
- nullable flow state differences

**Prefer**:

- A small overload set for common cases
- One “core” overload that everything funnels into

**Performance note**

- `params object[]`-shaped overloads are a classic footgun: they can allocate arrays and box value types. Prefer strongly typed overloads or span/handler-based APIs when performance matters.

### 3) **Mentor rule** (design APIs so the obvious call is also the correct one)

This is the part teams feel as “developer experience,” but it’s really **correctness** and **long-term maintainability**.

**What “obvious call” means**

- The call compiles without adding type arguments or casts in the common case.
- The call’s behavior is predictable (no “surprising overload selected”).
- The call doesn’t hide costly behavior (boxing, allocations, sync-over-async).

**Practical checklist for generic APIs**

- **Make the type parameter appear in input positions** (`T input`) so inference works.
- **Avoid** adding an `object` overload “for convenience.” If you must accept unknown types, provide a separate API name (e.g., `TryParseObject`) and keep the generic one clean.
- **Use honest abstractions**: if you only need to enumerate, accept `IEnumerable<T>`; if you need count/index, accept `IReadOnlyList<T>`/`IReadOnlyCollection<T>`.
- **Prefer `static` lambdas / `static` local functions** when you can, to avoid accidental captures and allocations in hot paths.

**Minimal example: inference-friendly projection**

```csharp
using System;
using System.Collections.Generic;

static IEnumerable<TResult> Select<T, TResult>(
    IEnumerable<T> source,
    Func<T, TResult> selector)
{
    foreach (var item in source)
        yield return selector(item);
}

var values = new[] { 1, 2, 3 };
var strings = Select(values, static x => x.ToString());
foreach (var s in strings) Console.WriteLine(s);
```

**Good to know**

- Good inference and non-ambiguous overloads reduce the need for “helper wrappers” and therefore reduce bugs and duplicated business logic.
