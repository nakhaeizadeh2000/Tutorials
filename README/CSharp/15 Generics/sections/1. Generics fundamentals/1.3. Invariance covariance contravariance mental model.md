### 1) **Why most generic types are invariant** (read/write roles make substitution unsafe)

**Definition**

- A generic type `G<T>` is **invariant** when `G<Derived>` is **not** assignable to `G<Base>`, even if `Derived : Base`.

Most generic **classes** (like `List<T>`, `Dictionary<TKey, TValue>`) are invariant because they usually both:

- **produce** `T` (you can read `T` out), and
- **consume** `T` (you can write `T` in).

If the runtime allowed covariance for such a type, you could break type safety.

**Classic pitfall**

Developers often think “I can upcast `Dog` to `Animal`, so I can upcast `List<Dog>` to `List<Animal>`.” You can’t—and it’s a good thing.

Minimal example:

```csharp
using System;
using System.Collections.Generic;

abstract class Animal { }
sealed class Dog : Animal { }
sealed class Cat : Animal { }

static class Demo
{
    static void Main()
    {
        List<Dog> dogs = [new Dog()];

        // List<T> is invariant, so this is illegal:
        // List<Animal> animals = dogs;

        // The reason: if it were allowed, you could do:
        // animals.Add(new Cat()); // would corrupt the original List<Dog>
        Console.WriteLine(dogs.Count);
    }
}
```

**Mentor stress**

- Invariance is not “C# being strict.” It prevents **runtime corruption** of collections.
- When you *want* substitutability, you often want a **read-only** or **write-only** abstraction, not a mutable collection.

**Performance note**

- Invariance is about **type safety**, not performance. The “performance” win is indirect: correct type constraints avoid runtime checks/casts and keep APIs honest.

### 2) **Where variance is allowed** (interfaces and delegates only; `out`/`in` rules)

**Key rule**

- Variance in C# is supported on **interfaces** and **delegates**, because their contracts can be restricted to safe producer/consumer roles.

High-level mapping:

- **Covariant** (`out T`) = **producer** = you can *return* `T` (read-only from caller perspective).
  - Example: `IEnumerable<out T>`, `IReadOnlyList<out T>`
- **Contravariant** (`in T`) = **consumer** = you can *accept* `T` (write-only from caller perspective).
  - Example: `IComparer<in T>`, `IEqualityComparer<in T>`, `Action<in T>`

Minimal, practical example:

```csharp
using System;
using System.Collections.Generic;

static class Demo
{
    static void Main()
    {
        IEnumerable<string> strings = ["a", "b"];
        IEnumerable<object> objects = strings; // allowed because IEnumerable<out T>
        Console.WriteLine(string.Join(", ", objects));

        IComparer<object> cmpObjects = Comparer<object>.Default;
        IComparer<string> cmpStrings = cmpObjects; // allowed because IComparer<in T>
        Console.WriteLine(cmpStrings.Compare("a", "b"));
    }
}
```

**Good to know**

- Generic **classes** can’t declare variance. They can *implement* variant interfaces (e.g., `List<T>` implements `IEnumerable<T>`).

### 3) **Practical API design** (producer vs consumer abstractions)

**When designing APIs, ask**

- “Is this parameter a **source** of data?” → accept `IEnumerable<T>` / `IAsyncEnumerable<T>` / `IReadOnlyList<T>`
- “Is this parameter a **destination** of data?” → accept `ICollection<T>` / `IList<T>` only if mutation is truly required
- “Is this both source and destination?” → invariance is expected; be explicit and document mutation

**Mentor rule**

- Don’t accept `List<T>` just because that’s what you have. Accept the **minimal honest contract** that the caller needs.

**Legacy patterns to avoid**

- Relying on **array covariance** (`Derived[]` → `Base[]`) for API flexibility. It can throw at runtime and is a correctness footgun.
  - Full explanation: see the variance section referenced above.
