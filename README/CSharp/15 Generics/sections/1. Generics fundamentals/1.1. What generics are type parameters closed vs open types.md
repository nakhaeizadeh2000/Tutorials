## 1.1. What generics are (type parameters, closed vs open constructed types, and “compile-time types”)

1. **The core promise** (type safety + reuse without `object` casts)
2. **Open vs closed generics** (`List<T>` vs `List<int>`; where runtime types exist)
3. **How the CLR sees generics** (metadata, instantiations, and why this is not “templates”)

### 1) **The core promise** (type safety + reuse without `object` casts)

**Definition**

**Generics** let you write *type-safe* algorithms and data structures that work for **any type** without falling back to `object` and runtime casts.

Think of it as: “Write the logic once, let the compiler enforce the types everywhere.”

**What problem generics solved**

Before generics, common .NET patterns looked like:

- Non-generic collections: `ArrayList`, `Hashtable`
- APIs that accept `object` and then cast

Those patterns cost you:

- **Correctness**: invalid casts become runtime exceptions.
- **Performance**: value types often **box** when passed as `object` or stored in non-generic collections.
- **Maintainability**: call sites lose intent and tooling help (IntelliSense, refactoring safety).

**Modern guidance (C# 15 era)**

- Prefer `List<T>`, `Dictionary<TKey, TValue>`, `HashSet<T>`, `IEnumerable<T>`, `IReadOnlyList<T>`, etc.
- Avoid “objecty” APIs for data paths that conceptually operate on \(T\).

**Runnable example (type safety)**

```csharp
using System;
using System.Collections.Generic;

static class Demo
{
    static void Main()
    {
        List<int> numbers = [1, 2, 3];
        numbers.Add(4);

        // numbers.Add("oops"); // compile-time error (good!)

        foreach (var n in numbers)
            Console.WriteLine(n);
    }
}
```

**Mentor note**

- Generics are not just “syntax sugar.” They are a cornerstone of *API design* and *performance hygiene* in .NET.

**Performance note**

- “Avoid boxing” is not micro-optimization. In high-throughput apps, boxing allocations can dominate CPU via GC pressure.

### 2) **Open vs closed generics** (`List<T>` vs `List<int>`; where runtime types exist)

**Key terms**

- **Type parameter**: `T` in `List<T>`. It’s a *placeholder* for a real type.
- **Open constructed type**: a generic type that still has type parameters.
  - Example: `List<T>` (open)
- **Closed constructed type**: a generic type where all type parameters are replaced with concrete types.
  - Example: `List<int>`, `Dictionary<string, Guid>` (closed)

**Why it matters**

- You can only *instantiate* closed constructed types:

```csharp
using System.Collections.Generic;

List<int> a = new();        // OK (closed)
// List<T> b = new();       // doesn't compile: T is unknown here
```

- Reflection and DI containers often need to reason about “open generic registrations” vs “closed types”.

**Common confusion**

- “Open generic” doesn’t mean “runtime chooses the type later.”
  - The generic type is still a *compile-time* concept; the runtime works with the resulting constructed type (and its metadata).

**Good to know**

- There’s also the term **generic type definition** (e.g., `typeof(List<>)`) which represents “the blueprint.”
- A closed constructed type like `List<int>` is a real runtime `System.Type`.

**Runnable example (open generic definition vs closed type)**

```csharp
using System;
using System.Collections.Generic;

static class Demo
{
    static void Main()
    {
        var openDef = typeof(List<>);
        var closed = typeof(List<int>);

        Console.WriteLine(openDef); // System.Collections.Generic.List`1[T]
        Console.WriteLine(closed);  // System.Collections.Generic.List`1[System.Int32]
    }
}
```

**Mentor note**

- When an API accepts `Type`, be explicit about what you expect:
  - “Must be a closed type” vs “can be an open generic definition.”

### 3) **How the CLR sees generics** (metadata, instantiations, and why this is not “templates”)

**High-level model**

The CLR stores generics in **metadata** and uses runtime mechanisms to create usable constructed types.

Important differences from C++ templates:

- **C++ templates** are “compile-time code generation” with no runtime notion of “generic type definition.”
- **.NET generics** have a runtime representation (metadata + `System.Type`) and are verified for type safety.

**What you should know as an application developer**

- Generic code can be **shared** between many instantiations in some cases (especially for reference types), but the CLR/JIT may still generate specialized code for some cases (notably value types).
- This affects:
  - **Throughput**: specialization may enable better inlining and optimizations.
  - **Memory/size**: specialization can increase code size.
  - **AOT/trimming**: reflection-based generic activation can be problematic if the trimmer can’t see the types.

For the full runtime-level deep dive (JIT/tiering/AOT), see:

- `README/CSharp/01 Fundamental Theories/sections/2. NET architecture/2.2. IL JIT tiered compilation AOT.md`

**Quick practical takeaway**

- If you build libraries that do “open generic activation” via reflection (e.g., `MakeGenericType`, `Activator.CreateInstance`), you must consider AOT/trimming compatibility in modern .NET.

**Runnable example (constructing a closed generic type at runtime)**

```csharp
using System;
using System.Collections.Generic;

static class Demo
{
    static void Main()
    {
        var open = typeof(Dictionary<,>);
        var closed = open.MakeGenericType(typeof(string), typeof(int));

        var instance = Activator.CreateInstance(closed);
        Console.WriteLine(instance?.GetType());
    }
}
```

**Good to know**

- Reflection-heavy patterns are not “deprecated,” but they are increasingly **constrained** in trimming/native AOT scenarios.
- Prefer source generation or explicit registration where you can (especially in high-scale services or AOT targets).
