## 6.2. Generic virtual methods and interface dispatch (correctness + perf realities)

---

### 1) **Virtual dispatch** (what gets inlined, what stays virtual, and why polymorphism has a cost)

**Definition**

- **Virtual dispatch** is when the runtime chooses an implementation based on the object’s runtime type (e.g., virtual methods, interface methods).
- In generic code, you’ll see this in two common forms:
  - calling members on **interface types** like `IEnumerable<T>`, `IComparer<T>`, `IEqualityComparer<T>`
  - calling members through **generic constraints** (e.g., `where T : IFoo` and you call `foo.Do()` on a `T`)

**When to use**

- You want **extensibility** and a stable contract: consumers provide implementations you can’t predict.
- You want to design APIs around **roles** (producer/consumer) rather than concrete types.
- You’re writing application code where readability and maintainability matter more than shaving nanoseconds.

**Trade-offs**

- **Inlining and devirtualization**: a virtual/interface call can block inlining, but modern .NET is better than old folklore:
  - the JIT can sometimes **devirtualize** calls when it can prove the concrete type (sealed/internal, PGO-informed, monomorphic call sites)
  - but you should still assume that **polymorphism is a real optimization barrier** in tight loops until measurement proves otherwise
- **Code size vs speed**: designs that remove virtual dispatch (e.g., more generics) can increase code generation (especially for value types) and hurt instruction-cache efficiency.

**Common mistakes**

- Treating “interface call” as always slow and over-optimizing prematurely (leading to rigid, hard-to-test designs).
- Returning `IEnumerable<T>` for something that is conceptually a **collection** and then callers accidentally cause repeated enumeration (correctness/perf bug). Prefer honest shapes like `IReadOnlyList<T>` when you mean “materialized and indexable”.

**Good to know**

- The cost of virtual dispatch is rarely the call itself; it’s often the **missed inlining** and the secondary effects (more bounds checks, more allocations, less loop optimization).
- For a deeper runtime/JIT view, see [2.2. IL JIT tiered compilation AOT](<../../../01 Fundamental Theories/sections/2. NET architecture/2.2. IL JIT tiered compilation AOT.md>).

### 2) **Interfaces over structs** (where boxing can reappear if you store structs as interfaces)

**Key rule**

If `S` is a `struct` that implements an interface `IDisposable`, then:

- **calling** generic code like `Use<T>(T value) where T : IDisposable` can be non-boxing
- but **storing** `S` in an interface-typed variable (`IDisposable d = s;`) **boxes** (allocates)

That boxing is not “a micro-issue” in hot paths: it becomes allocations → GC → CPU and tail-latency.

**Canonical deep dive**

Boxing-through-interfaces is covered in depth elsewhere in your repo. For the full treatment (including triggers and fixes), see:

- [3.3. Boxing interfaces generics](<../../../13 Structures/sections/3. Struct vs class/3.3. Boxing interfaces generics.md>)
- [4.2. Avoid boxing in modern CSharp](<../../../14 System Object Class/sections/4. object in APIs/4.2. Avoid boxing in modern CSharp.md>)

**Minimal, runnable reminder**

```csharp
using System;

public readonly struct S : IDisposable
{
    public void Dispose() { }
}

public static class Demo
{
    public static void Use<T>(T value) where T : IDisposable
    {
        // This call can stay generic (no interface-typed storage required).
        value.Dispose();
    }

    public static void Main()
    {
        var s = new S();

        Use(s); // can be non-boxing

        IDisposable d = s; // boxes (allocates)
        d.Dispose();
    }
}
```

**Mentor stress**

- If you need polymorphism + lifetime management, a **class** is often the correct semantic choice.
- If you need high-performance “generic over many numeric types”, prefer **static abstract interface members** patterns (covered under constraints in [4.1](<../4. Generic constraints/4.1. Constraint taxonomy and meaning.md>)) instead of “interfaces over structs stored in interface variables”.

### 3) **Practical rule** (prefer clear design first; optimize when profiling shows it matters)

**Rule of thumb**

- Default to **clean, honest abstractions** (`IReadOnlyList<T>`, `IEnumerable<T>`, `IComparer<T>`) and avoid “generic cleverness”.
- When something is hot, optimize the biggest wins first:
  1. allocations/boxing
  2. sync-over-async / ThreadPool starvation
  3. contention and locking
  4. only then: virtual dispatch and inlining barriers

**Performance note**

- In servers, the difference between “allocates per item” and “allocates per request” is enormous at scale.
- If you change an API just to avoid interface dispatch, you often increase coupling and reduce testability. Treat it as a trade-off requiring evidence.
