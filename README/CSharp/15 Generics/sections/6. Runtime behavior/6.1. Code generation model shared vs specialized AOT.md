## 6.1. Code generation model (shared generics, specialization, and AOT considerations)

1. **Reference-type instantiation sharing** (why many `List<T>` instantiations share code)
2. **Value-type instantiations** (often require specialized code; impacts size/startup)
3. **AOT/trimming caution** (reflection-heavy generic activation; linkability constraints)

Generics feel like a language feature, but their real behavior is a **runtime + JIT** story. Understanding this section helps you predict:

- when generic code is **fast** (specialized for value types),
- when it may add **code size** (many instantiations),
- and when publishing with **trimming / AOT** changes the rules.

### 1) **Reference-type instantiation sharing** (why many `List<T>` instantiations share code)

**Definition**

For many generic types/methods, the runtime can **share one machine-code body** across multiple instantiations when the generic type arguments are **reference types**.

- `List<string>` and `List<object>` can often use the **same underlying native code**, because at runtime a reference is a pointer-sized value and the machine code can treat it uniformly.

**What you should expect**

- **Throughput**: usually excellent.
- **Memory**: less code generated vs value-type instantiations.
- **Behavior**: still fully type-safe; there’s no casting by you, but the runtime tracks the actual generic type arguments in metadata.

**Good to know**

- “Shared code” does **not** mean “boxed.” References are already references.
- The JIT can still specialize based on other information (e.g., sealing, devirtualization), but the generic-sharing model influences what specialization is possible.

### 2) **Value-type instantiations** (often require specialized code; impacts size/startup)

**Definition**

When a generic type parameter is a **value type** (`int`, `Guid`, your `readonly struct`, etc.), the runtime typically needs a **specialized** implementation because:

- value types have different sizes/layouts (1 byte vs 16 bytes vs 64 bytes),
- copying/initialization rules differ,
- and calling conventions can differ.

**Why you care**

- **Performance upside**: this is a big reason generics are fast. `List<int>` stores `int` inline without boxing and has optimized code paths.
- **Code size downside**: lots of distinct value-type instantiations can increase total generated code, which can affect:
  - startup (more JIT work),
  - instruction cache pressure,
  - and deployment size in AOT scenarios.

**Mentor guidance**

- Don’t fear specialization—most apps benefit from it.
- Do be careful with “generic explosion” in libraries that are instantiated with many different value types across a large codebase.

### 3) **AOT/trimming caution** (reflection-heavy generic activation; linkability constraints)

**Key idea**

When you publish with **trimming** and/or **native AOT**, any pattern that “finds types at runtime” can break if the toolchain can’t see the usage statically.

This is not a generics-only issue, but generics amplify it because code often uses:

- `typeof(T)`
- `MakeGenericType`
- `Activator.CreateInstance`
- “scan assemblies and build closed generics at runtime”

**What to do instead (modern guidance)**

- Prefer **explicit registration** over reflection scanning for DI when AOT/trimming is a goal.
- Prefer **source generation** (compile-time) over runtime reflection when possible.
- If you must use reflection, use the appropriate **trimming annotations/config** and document AOT support constraints clearly.
