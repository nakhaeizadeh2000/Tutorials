## 2.3. Collections and generic composition patterns (real-world shapes)

1. **Expose minimal capabilities** (prefer read-only views; avoid leaking mutability)
2. **Avoid “generic wrapper soup”** (too many `Wrapper<Wrapper<T>>` layers kill readability)
3. **Performance framing** (iteration costs, allocations, and enumeration patterns)

---

This section is about **how to shape generic collection-like APIs** so they’re honest, ergonomic, and fast enough without being “clever”. Most production bugs here come from exposing the wrong abstraction (too weak or too strong), then being forced into breaking changes later.

### 1) **Expose minimal capabilities** (prefer read-only views; avoid leaking mutability)

**Definition (mentor framing)**

- A *collection abstraction* is a **promise**. If you return `IEnumerable<T>`, you’re promising only “I can be enumerated”, not that it’s in-memory, repeatable, finite, ordered, or cheap.
- The best APIs tend to expose the **minimum capability** required by callers, and keep mutation under your control.

**Choose the right “shape”**

- **`IEnumerable<T>`**: “sequence” (pull-based enumeration)
  - Great for streaming, pipelines, deferred execution.
  - Dangerous when callers assume they can enumerate multiple times or that enumeration is cheap.
- **`IReadOnlyCollection<T>`**: adds `Count` (still no indexing)
  - Good when callers need to pre-size or make decisions based on size.
- **`IReadOnlyList<T>`**: adds indexing + order
  - Good for materialized lists with stable ordering.
- **Concrete types (`T[]`, `List<T>`, `ImmutableArray<T>`)**: strongest guarantees
  - Great when you want to promise performance characteristics and semantics.
  - More coupling; versioning constraints.

**Mentor rule**

- **Accept broader abstractions than you return.**
  - Accept `IReadOnlyCollection<T>` or `IEnumerable<T>` as input (depending on needs).
  - Return the most honest type: if you already materialize to an array, returning `T[]` is often better than hiding it behind `IEnumerable<T>`.

**Runnable example: returning a lie hurts correctness and perf**

```csharp
using System;
using System.Collections.Generic;

public static class Demo
{
    // Looks harmless but can be expensive or wrong if called twice.
    public static IEnumerable<int> GetIds()
    {
        Console.WriteLine("Enumerating source...");
        yield return 1;
        yield return 2;
        yield return 3;
    }

    public static void Main()
    {
        var ids = GetIds();

        // Caller might do this accidentally:
        Console.WriteLine($"Count-ish: {string.Join(", ", ids)}");
        Console.WriteLine($"Again:     {string.Join(", ", ids)}"); // re-enumerates; could hit DB twice in real life
    }
}
```

**Good to know**

- If your sequence is expensive or one-shot (network stream, DB reader), consider returning an API that makes that explicit:
  - `IAsyncEnumerable<T>` for async streaming
  - a dedicated “enumerator” object with ownership semantics
  - or materialize once and return `ImmutableArray<T>`/`T[]` if that’s the real contract

### 2) **Avoid “generic wrapper soup”** (too many `Wrapper<Wrapper<T>>` layers kill readability)

**What it means**

Wrapper types are fine; *wrapper stacks* are not. When everything is a generic wrapper, your code becomes:

- hard to read at call sites,
- hard to debug (stack traces and types explode),
- hard to version (any wrapper change becomes viral),
- and sometimes slower (extra allocations, indirection, virtual dispatch).

**Healthy wrappers**

- A wrapper that enforces an invariant or policy:
  - `Result<T>`: “value or error”
  - `Option<T>`: “value or none”
  - `Validated<T>`: “value with validation evidence”
- A wrapper that changes lifetime/ownership:
  - `ReadOnlyMemory<T>` / `Memory<T>`: explicit memory/lifetime model

**Unhealthy wrapper soup**

- Wrappers that exist mostly to “avoid choosing” a concrete abstraction:
  - `EnumerableWrapper<ReadOnlyWrapper<MaybeWrapper<T>>>`

**Mentor guidance**

- If a wrapper’s meaning cannot be explained in one sentence, it probably shouldn’t be a type.
- Prefer one “primary” wrapper and keep the rest as **methods** or **extensions**.
- When you need multiple policies, consider:
  - a single options/config type (`record`/`record struct`),
  - strategy objects (interfaces),
  - or separate overloads for common cases.

**Performance note**

- Many wrappers are allocation-free if implemented as `readonly struct`, but that can introduce copying pitfalls and boxing if used via non-generic interfaces. If you go the struct-wrapper route, keep it small and avoid interface-typed storage. For the deep boxing story, see [3.3. Boxing interfaces generics](<../../../13 Structures/sections/3. Struct vs class/3.3. Boxing interfaces generics.md>).

### 3) **Performance framing** (iteration costs, allocations, and enumeration patterns)

**The performance “shape” of collection APIs**

The biggest levers are usually:

- **Materialization vs streaming**
  - Materializing (`ToArray`, `ToList`) allocates but makes repeated use cheap and predictable.
  - Streaming avoids allocations but may re-run work on each enumeration and may hold onto resources longer.
- **Enumerator allocation / boxing**
  - Most `foreach` over `IEnumerable<T>` is allocation-free for common types, but there are edge cases (especially with structs + interfaces).
  - Don’t guess: if this is hot, measure allocations with a profiler.
- **Async vs sync iteration**
  - Use `IAsyncEnumerable<T>` when the *source* is naturally async (network, DB).
  - Don’t fake async by wrapping sync work in `Task.Run` in server code; it burns ThreadPool threads.

**Practical “API shape” pattern (library-ish)**

- Provide a **streaming** API for large data:
  - `IAsyncEnumerable<T>` for async sources.
- Optionally provide a **materializing** helper for convenience:
  - `Task<ImmutableArray<T>>` / `Task<T[]>` if callers commonly need a stable snapshot.

**Legacy/deprecated patterns to avoid**

- Returning `ArrayList`, `Hashtable`, non-generic `IEnumerable` (they invite boxing and casts). Prefer generic collections (`List<T>`, `Dictionary<TKey, TValue>`, `IEnumerable<T>`).
