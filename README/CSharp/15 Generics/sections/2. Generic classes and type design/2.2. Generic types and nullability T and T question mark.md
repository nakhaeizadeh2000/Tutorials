## 2.2. Generic types and nullability (T, T?, and API contracts)

1. **The hard truth** (`T` can be reference or value; “nullable” depends on the constraint story)
2. **When to use constraints** (`where T : class` / `struct` / `notnull`)
3. **Correctness rule** (don’t pretend you can always return non-null for unconstrained `T`)

### 1) **The hard truth** (`T` can be reference or value; “nullable” depends on the constraint story)

**Definition (what the compiler is really dealing with)**

In a generic like `class Box<T>`, the type parameter `T` may be:

- a **reference type** (`string`, `HttpClient`, `object`)
- a **value type** (`int`, `Guid`, your `struct`)
- a **nullable value type** (`int?`, `Guid?`)

So “nullable” cannot be described with a single rule unless you add **constraints**.

**Key mental model**

- `T` is a **type parameter**, not “a reference type”.
- `T?` means “`T` with nullable annotations applied”, but the exact behavior depends on whether `T` is constrained to `class`/`struct`.

**Common mistake**

- Assuming `T` behaves like `object` and can always be `null`.
- Assuming `default(T)` is always `null`. It is `null` for reference types, but it is **zero-initialization** for value types (`0`, `Guid.Empty`, etc.).

**Good to know**

- Nullable reference types are mostly a **compile-time contract** (flow analysis + warnings). At runtime, `string` and `string?` are the same CLR type.

---

### 2) **When to use constraints** (`where T : class` / `struct` / `notnull`)

Constraints are the only way to give the compiler (and your users) a reliable contract about `null`.

#### `where T : class`

**Meaning**: `T` must be a non-nullable reference type (from the compiler’s perspective).

Use when:

- `null` is meaningful in your API (`T?` as “missing”) and you want the compiler to help.
- You need reference-type-only behaviors (like `null` checks without boxing).

Trade-offs:

- You exclude value types (often acceptable; be intentional).

Example:

```csharp
public sealed class Cache<T> where T : class
{
    private T? _value;

    public bool TryGet(out T value)
    {
        if (_value is { } v)
        {
            value = v;
            return true;
        }

        value = null!; // safe by contract: only returned when false
        return false;
    }

    public void Set(T value) => _value = value ?? throw new ArgumentNullException(nameof(value));
}
```

#### `where T : struct`

**Meaning**: `T` is a non-nullable value type.

Use when:

- You want to avoid `null` completely and you want “no allocation” semantics (value types).

Trade-offs:

- Value types copy; big structs can be expensive. (See `Structures/3.2` for “big struct” costs.)

#### `where T : notnull`

**Meaning**: `T` cannot be a nullable type (`string?`, `int?` are excluded).

Use when:

- `T` will be used as a **key** (e.g., in dictionaries) or stored where `null` breaks invariants.

Example:

```csharp
using System.Collections.Generic;

public sealed class KeyedIndex<TKey, TValue> where TKey : notnull
{
    private readonly Dictionary<TKey, TValue> _map = new();

    public void Add(TKey key, TValue value) => _map.Add(key, value);
    public bool TryGet(TKey key, out TValue value) => _map.TryGetValue(key, out value);
}
```

**Mentor note**

- `notnull` is often a better “library default” constraint for key-like generic parameters than `class`, because it supports both reference and value keys.

---

### 3) **Correctness rule** (don’t pretend you can always return non-null for unconstrained `T`)

If `T` is unconstrained, you must assume callers can instantiate it with:

- `T = string` (where `default(T)` is `null`)
- `T = int` (where `default(T)` is `0`)
- `T = SomeStruct` (where `default(T)` is zeroed struct)

So:

- Don’t claim you return a non-null `T` unless you can prove it for **all** `T`.
- Don’t write `return null;` in generic code without a `class` constraint (it will not compile).

Use patterns that correctly represent “maybe there is a value”:

- `bool TryX(out T value)` (works for all `T`)
- `T?` only when constraints make its meaning clear
- A discriminated result type, e.g. `Result<T>` / `Option<T>` pattern (app code), if it improves clarity

**Performance note**

- Avoid using `Nullable<T>` as a “universal maybe” when `T` might be a reference type: that’s not what it represents.
- Prefer `Try...` patterns in hot paths (no exceptions, predictable branches, no extra allocations).
