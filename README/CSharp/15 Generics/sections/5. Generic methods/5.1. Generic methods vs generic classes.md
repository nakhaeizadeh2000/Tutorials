## 5.1. Generic methods vs generic classes (choosing the smallest abstraction)

1. **Locality** (keep genericity where it’s needed; don’t generalize entire types prematurely)
2. **Inference ergonomics** (design signatures that infer well)
3. **Testability** (generic methods are easy to unit-test if they’re pure and deterministic)

---

### 1) **Locality** (keep genericity where it’s needed; don’t generalize entire types prematurely)

**Definition**

- A **generic method** is a method with its own type parameter list: `M<T>(...)`.
- A **generic class** is a type that carries type parameters everywhere: `C<T>`, so every member “inherits” `T`.

**When to prefer a generic method**

- Your algorithm is **self-contained** and does not need to store `T` in instance fields.
- You want generic behavior in **one place**, but you don’t want to force callers to create `SomeType<T>` objects.
- You want the compiler/JIT to keep the hot path **strongly typed** without pushing genericity into the whole design.

**When to prefer a generic class**

- The type’s identity is “a thing parameterized by \(T\)” (e.g., `List<T>`, `Dictionary<TKey, TValue>`, `IComparer<T>`, `IOptions<T>`-like patterns).
- You need to **store** `T` or `IEqualityComparer<T>` in fields and reuse it across methods.
- You want to expose a coherent “bundle” of behavior tied to `T` (often with constraints).

**Trade-offs (mentor view)**

- Generic classes can become **architecture gravity**: once a subsystem is `Something<T>`, everything around it tends to become generic too.
- Generic methods keep genericity **local** and prevent “type parameter leak” through many layers.
- A generic class is not “more reusable” by default—it can be *less usable* if it infects your public surface.

**Example: method-first design**

```csharp
using System;
using System.Collections.Generic;

public static class Algorithms
{
    public static T MaxBy<T>(IEnumerable<T> source, Comparison<T> comparison)
    {
        ArgumentNullException.ThrowIfNull(source);
        ArgumentNullException.ThrowIfNull(comparison);

        using var e = source.GetEnumerator();
        if (!e.MoveNext())
            throw new ArgumentException("Sequence is empty.", nameof(source));

        var best = e.Current;
        while (e.MoveNext())
        {
            var candidate = e.Current;
            if (comparison(candidate, best) > 0)
                best = candidate;
        }

        return best;
    }
}

public static class Demo
{
    public static void Main()
    {
        var xs = new[] { 3, 1, 4, 2 };
        var max = Algorithms.MaxBy(xs, static (a, b) => a.CompareTo(b));
        Console.WriteLine(max); // 4
    }
}
```

**Performance note**

- This example uses `IEnumerable<T>` to keep the API general; for very hot paths consider overloads for `ReadOnlySpan<T>` or `IReadOnlyList<T>` to avoid enumerator overhead/virtual calls (but only after measuring).

### 2) **Inference ergonomics** (design signatures that infer well)

**What “infers well” means**

Type inference succeeds when the compiler can “learn” \(T\) from **argument types**.

Good:

```csharp
static T Identity<T>(T value) => value;
_ = Identity(123); // T inferred as int
```

Painful:

```csharp
static void Create<T>() { }
// Create(); // cannot infer T
```

**Mentor rules for public APIs**

- Prefer signatures where `T` appears in the **parameters**, not only in the return type.
- Avoid generic overload sets that rely on subtle inference differences; they become brittle during refactors.
- If you have two equally plausible inferences, you’ll get call-site ambiguity. If that can happen, redesign.

### 3) **Testability** (generic methods are easy to unit-test if they’re pure and deterministic)

**What to aim for**

- Generic methods are easiest to test when they are **pure functions**: no hidden time, randomness, globals, threads, or I/O.
- If you need dependencies, pass them in explicitly (comparers, delegates, strategy objects).

**Common mistake**

- “Utility generic methods” that quietly capture ambient state (culture, time zone, random, DI service locator) are hard to test and will surprise production.

**Good to know**

- If a generic method needs many knobs, consider an immutable **options record** for app code, but keep public library surfaces conservative (options objects can become versioning baggage).
