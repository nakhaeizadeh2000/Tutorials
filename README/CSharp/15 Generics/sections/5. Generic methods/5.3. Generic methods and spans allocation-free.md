## 5.3. Generic methods and spans (allocation-free slicing when it fits)

1. **Why `Span<T>` exists** (slicing without allocations; stack-only safety constraints)
2. **API shapes** (`ReadOnlySpan<T>` inputs; avoid returning spans unless lifetime is crystal clear)
3. **Boundaries** (don’t force spans everywhere; use them where measurement shows wins)

---

### 1) **Why `Span<T>` exists** (slicing without allocations; stack-only safety constraints)

**Definition**

`Span<T>` / `ReadOnlySpan<T>` represent a **contiguous region of memory** (array, stackalloc, string chars, unmanaged memory) without allocating a new array.

- `ReadOnlySpan<T>`: read-only view.
- `Span<T>`: read/write view.

**Why it exists (the problem it solves)**

Before spans, a common pattern was:

- `Substring`, `Split`, `ToCharArray`, `ToArray`, `ArraySegment<T>` workarounds
- which often create **new strings/arrays** and add GC pressure

Spans let you **slice and parse** without those intermediate allocations.

**Core constraint**

`Span<T>` is a `ref struct` (stack-only). That implies:

- It **cannot** be stored on the heap (fields of classes, captured by lambdas, used across `await`, iterators).
- It is designed to be **memory-safe** by construction.

If you need the deep model of stack-only types, lifetimes, and why `ref struct` exists, see `README/CSharp/13 Structures/sections/4. Readonly structs/4.2. ref struct and stack-only types.md`.

**Runnable example (allocation-free slicing)**

```csharp
using System;

static class Demo
{
    static bool TryParseLeadingInt(ReadOnlySpan<char> s, out int value, out ReadOnlySpan<char> rest)
    {
        s = s.TrimStart();
        var i = 0;
        while (i < s.Length && char.IsDigit(s[i])) i++;
        if (i == 0)
        {
            value = default;
            rest = s;
            return false;
        }

        if (!int.TryParse(s[..i], out value))
        {
            rest = s;
            return false;
        }

        rest = s[i..];
        return true;
    }

    public static void Main()
    {
        ReadOnlySpan<char> input = "  12345,tail".AsSpan();
        if (TryParseLeadingInt(input, out var n, out var rest))
        {
            Console.WriteLine(n);               // 12345
            Console.WriteLine(rest.ToString()); // ,tail (ToString allocates, intentionally)
        }
    }
}
```

**Performance note**

- The parse/slice path above allocates **0** objects until you intentionally materialize (`ToString`).
- This can be a major win in high-throughput parsing (HTTP, CSV, telemetry).

### 2) **API shapes** (`ReadOnlySpan<T>` inputs; avoid returning spans unless lifetime is crystal clear)

**Best practice (mentor rule)**

- Prefer **accepting** `ReadOnlySpan<T>` for high-performance, allocation-free inputs.
- Be cautious about **returning** spans because the caller must respect the lifetime of the underlying memory.

**Good shapes**

- `bool TryX(ReadOnlySpan<char> input, out TResult result)`
- `int IndexOf(ReadOnlySpan<char> haystack, ReadOnlySpan<char> needle)`
- Overloads that accept both: `string` and `ReadOnlySpan<char>` (ergonomics + performance)

**Avoid returning spans from APIs that hide lifetimes**

Bad: returning `ReadOnlySpan<char>` that points into a temporary buffer you created inside the method.

If you need to return a view with controlled lifetime, consider:

- returning a `string` (ownership transfer, but allocates),
- returning a **slice descriptor** (start/length) over a caller-owned buffer,
- or using a pipeline where the caller provides the buffer.

**Good to know**

`ReadOnlyMemory<T>` / `Memory<T>` exist for heap-storable buffers and async boundaries (they are not `ref struct`).

---

### 3) **Boundaries** (don’t force spans everywhere; use them where measurement shows wins)

Spans are a sharp tool. They increase API complexity and can reduce ergonomics.

**When spans are worth it**

- Hot paths with measurable allocation pressure
- Parsing/formatting pipelines
- Working with buffers (I/O, serialization, protocols)

**When spans are not worth it**

- Regular business logic where allocations are not a bottleneck
- When you immediately materialize anyway (e.g., always calling `ToArray`/`ToString`)

**Common mistakes**

- Capturing spans in lambdas/async methods (won’t compile, by design)
- Returning spans that outlive the backing buffer (lifetime bug waiting to happen)
- Prematurely adding span overloads everywhere, making the API hard to learn

**Mentor closing**

Start with clear code, profile, then introduce span-based overloads **where you can prove** they reduce allocations and improve throughput or tail latency.
