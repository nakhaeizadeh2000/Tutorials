## 4.3. Constraints and API usability (don’t make your users suffer)

1. **Constraint minimalism** (add only what you truly need; constraints are part of your public contract)
2. **Error message quality** (constraints shape diagnostics; better constraints = clearer compiler errors)
3. **Alternative designs** (strategy objects, delegates, pattern matching, or overloads instead of constraints)

---

### 1) **Constraint minimalism** (add only what you truly need; constraints are part of your public contract)

**Definition**

A **generic constraint** is not an implementation detail. It is part of your **API contract**:

- It restricts what callers can pass.
- It changes what the compiler can prove (nullability, available members, construction).
- It can affect JIT optimizations and allocation patterns.

**Mentor rule (the “minimum necessary constraint” rule)**

- Add constraints only when they are required for:
  - correctness (you need a member or invariant),
  - performance (you want the allocation-free path to be the default),
  - or diagnostics (you want errors to be early and clear).

Every constraint you add:

- reduces applicability of the API,
- creates upgrade/versioning friction (removing a constraint is not always source-compatible in practice),
- and increases the cognitive load for users.

**Common mistake**

Adding constraints “just in case”:

- `where T : class` when you don’t actually depend on reference semantics
- `where T : new()` when factory/DI is intended (this one is especially common and often wrong)

**Good to know**

- Constraints are checked at compile time. At runtime you still can observe `default(T)` and weird states at boundaries (serialization, reflection, interop). Don’t put essential validation only inside generic constraints.

---

### 2) **Error message quality** (constraints shape diagnostics; better constraints = clearer compiler errors)

**Why this matters**

For public APIs, the *compiler error* is effectively your “first documentation page”.

If your constraint is too broad or too implicit, users get errors like:

- “`T` does not contain a definition for …”
- “The type `X` must be a non-nullable value type …”

Those can be good or terrible depending on how you shaped the API.

**Make constraints express intent**

Prefer constraints that match the *role* you need:

- Need non-null keys? Use `where TKey : notnull` (instead of letting `Dictionary<TKey, TValue>` fail later).
- Need numeric operations? Use static abstract members on an interface (see `4.1`) rather than “duck-typing” via reflection.

**Example: clearer errors with `notnull`**

```csharp
using System.Collections.Generic;

public sealed class Cache<TKey, TValue>
    where TKey : notnull
{
    private readonly Dictionary<TKey, TValue> _map = new();
}
```

Now `Cache<string?, int>` fails with a clear error at the call site, rather than allowing a “maybe null key” to leak into your invariants.

**Mentor note**

- Good constraints reduce “tribal knowledge” and prevent misuse.
- They also improve IDE experience (IntelliSense shows what is legal).

---

### 3) **Alternative designs** (strategy objects, delegates, pattern matching, or overloads instead of constraints)

Constraints are one tool. Sometimes they are the wrong one.

#### Option A: **Strategy object** (interface or abstract class)

Use when behavior varies and callers can supply an implementation:

- `IEqualityComparer<T>` for equality behavior
- `IComparer<T>` for ordering
- “policy objects” for formatting/serialization/normalization

This keeps the generic type broad while letting behavior be injected.

**Performance note**

- Strategy interfaces introduce virtual/interface dispatch.
- In many apps that’s fine. In hot paths, consider “two-layer” design:
  - generic fast path (e.g., `EqualityComparer<T>.Default`),
  - opt-in custom behavior path for special cases.

#### Option B: **Delegates** (`Func<>`, `Action<>`, `Comparison<T>`)

Use when you want minimal overhead and easy call sites:

- mapping/projection functions
- comparison callbacks

**Pitfall**

- Capturing lambdas allocate closure objects. In hot paths prefer:
  - `static` lambdas,
  - cached delegates,
  - or local functions with explicit state.

#### Option C: **Pattern matching / type switching**

Use when the set of supported types is limited and explicit:

```csharp
static int SizeOf<T>()
{
    return typeof(T) == typeof(int) ? 4
         : typeof(T) == typeof(long) ? 8
         : throw new NotSupportedException();
}
```

This is intentionally non-generic “in spirit” (it’s a finite set). Prefer explicit overloads when possible.

#### Option D: **Overloads instead of constraints**

If you have two intended “modes”, consider two overloads rather than a single generic method with a complicated constraint story.
