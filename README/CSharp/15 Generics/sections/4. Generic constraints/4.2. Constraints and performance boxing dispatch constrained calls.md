## 4.2. Constraints and performance (boxing, virtual dispatch, and “constrained calls”)

1. **Boxing avoidance** (keep pipelines generic; avoid `object` and non-generic interfaces in hot paths)
2. **Interface calls vs devirtualization** (what the JIT can often optimize; what it cannot)
3. **`EqualityComparer<T>.Default` and friends** (why they exist; when custom comparers matter)

Modern .NET’s performance story for generics is mostly about **what the JIT can prove** and **what your API shape forces**:

- Do you force values through `object` / non-generic interfaces? You’ll allocate (boxing) and lose optimization opportunities.
- Do you rely on interface dispatch in a hot loop? You may block inlining and pay in CPU/cache misses.
- Do you compare/Hash with the right helpers? You can avoid both correctness bugs and perf cliffs.

This file focuses on **performance-specific** generics guidance. For a full boxing deep dive (especially structs boxing via interface variables), see `README/CSharp/13 Structures/sections/3. Struct vs class/3.3. Boxing interfaces generics.md`.

### 1) **Boxing avoidance** (keep pipelines generic; avoid `object` and non-generic interfaces in hot paths)

**Definition (what “boxing” means here)**  
Boxing happens when a **value type** (a `struct`) is converted to a reference type such as `object` or a **non-generic interface**, which requires allocating a new object on the heap and copying the value into it.

**When this shows up in generic code**

- You write a “generic” algorithm, but store the values into `object` (or `IComparable`) internally.
- You accept `IEnumerable` (non-generic) instead of `IEnumerable<T>`.
- You use `params object[]` logging/formatting paths in hot loops.

**Mentor rule**  
If the data is conceptually \(T\), keep it \(T\) through the whole pipeline. **The first `object` in a hot path is usually a design smell.**

**Example: “looks generic” but boxes**

```csharp
using System;

public static class BoxingDemo
{
    public static void AddToSink<T>(T value, Action<object> sink)
        => sink(value!); // if T is a struct => boxing allocation

    public static void Main()
    {
        AddToSink(123, static o => Console.WriteLine(o)); // int boxes when passed to object
    }
}
```

**Better: keep the sink generic**

```csharp
using System;

public static class NoBoxingDemo
{
    public static void AddToSink<T>(T value, Action<T> sink)
        => sink(value);

    public static void Main()
    {
        AddToSink(123, static x => Console.WriteLine(x)); // no boxing
    }
}
```

**Good to know**

- Boxing is not “just one allocation”: it can become a **GC-driven throughput killer** at scale.
- The JIT can optimize a lot, but it can’t optimize away a heap allocation your API shape forces.

### 2) **Interface calls vs devirtualization** (what the JIT can often optimize; what it cannot)

**What you’re trading**

- **Interface dispatch** is a form of polymorphism: flexible, testable, decoupled.
- In hot loops, it can cost:
  - more indirect calls,
  - fewer inlining opportunities,
  - worse branch prediction and cache locality.

**Reality check (mentor framing)**  
Don’t cargo-cult “interfaces are slow”. In many codebases the bottleneck is **allocations** or **I/O**, not dispatch. But if you’re writing a *library primitive* that runs billions of times (parsers, math kernels, serialization), dispatch can matter.

**The “generic constraint” performance pattern**

If you constrain `T` to an interface and call the interface member on `T`, the runtime can sometimes use a **constrained call** that avoids boxing and can enable better codegen for structs.

```csharp
using System;

public interface IAdder<TSelf>
    where TSelf : IAdder<TSelf>
{
    static abstract TSelf operator +(TSelf left, TSelf right);
}

public readonly struct MyInt : IAdder<MyInt>
{
    public int Value { get; }
    public MyInt(int value) => Value = value;
    public static MyInt operator +(MyInt left, MyInt right) => new(left.Value + right.Value);
    public override string ToString() => Value.ToString();
}

public static class SumDemo
{
    public static T Sum<T>(ReadOnlySpan<T> values) where T : IAdder<T>
    {
        var acc = default(T);
        foreach (var v in values)
            acc = acc + v;
        return acc;
    }

    public static void Main()
    {
        MyInt[] items = [new(1), new(2), new(3)];
        Console.WriteLine(Sum(items));
    }
}
```

**Performance note**

- The biggest win here is often not the dispatch itself, but the ability to write an algorithm **once** while still generating efficient struct code.
- For a deeper runtime view (JIT behavior, tiering, AOT constraints), see `README/CSharp/01 Fundamental Theories/sections/2. NET architecture/2.2. IL JIT tiered compilation AOT.md`.

### 3) **`EqualityComparer<T>.Default` and friends** (why they exist; when custom comparers matter)

**Why this matters for correctness and performance**

- `==` is not available for unconstrained `T`.
- `object.Equals(a, b)` can cause boxing for structs and uses virtual dispatch.
- `EqualityComparer<T>.Default` selects the best available implementation:
  - uses `IEquatable<T>` when implemented,
  - avoids boxing for value types,
  - provides consistent semantics across reference/value types.

**Rule (library-grade default)**

- For equality: prefer `EqualityComparer<T>.Default.Equals(a, b)`
- For hashing: prefer `EqualityComparer<T>.Default.GetHashCode(value)`
- For ordering: prefer `Comparer<T>.Default` or accept an `IComparer<T>`

**Example: generic “contains” without boxing**

```csharp
using System.Collections.Generic;

public static class ContainsDemo
{
    public static bool Contains<T>(IEnumerable<T> source, T value)
    {
        var comparer = EqualityComparer<T>.Default;
        foreach (var item in source)
            if (comparer.Equals(item, value))
                return true;
        return false;
    }
}
```

**When custom comparers matter**

- You need non-default semantics (case-insensitive strings, culture rules, “key” projection).
- You need stable behavior across versions (e.g., avoid culture-dependent comparisons).
- You want to avoid repeated allocations: store and reuse the comparer instance, don’t create it per call.

**Common mistake**

- Building a `Dictionary<TKey, TValue>` with a default comparer when you actually need a specific one, then “fixing” it later by normalizing keys on every lookup (extra allocations and CPU).
