## 4.1. Constraint taxonomy (what each constraint actually buys you)

1. **Reference/value constraints** (`class`, `struct`, `unmanaged`, `notnull`)
2. **Construction/type constraints** (`new()`, base class, interface constraints)
3. **Member constraints** (static abstract interface members and generic math patterns)

Generics without constraints are intentionally flexible: \(T\) might be a reference type, a value type, nullable, non-nullable, managed, unmanaged… and the compiler/JIT must assume the broadest set of possibilities.

Constraints exist for three reasons:

- **Correctness**: you can *legally* do something (e.g., call an interface member, instantiate \(T\), rely on non-null).
- **API clarity**: your method/type communicates its real requirements (and produces better compiler errors).
- **Performance opportunities**: some constraints enable more efficient implementations (fewer branches/boxing, better JIT patterns) — but only when used carefully.

Below is the practical taxonomy you’ll use in real code.

---

### 1) **Reference/value constraints** (`class`, `struct`, `unmanaged`, `notnull`)

#### `where T : class`
**Meaning**

- \(T\) must be a **reference type**.

**What it enables**

- You can use `null` as a meaningful sentinel (and understand `default(T)` as `null`).
- You can write APIs that clearly return `T?` / accept `T?` under nullable reference types (NRT).

**Trade-offs**

- You exclude structs and `record struct` types — that may or may not be what you want.

**Common mistake**

- Using `class` because “I might use null” rather than modeling absence explicitly (e.g., `Try...`, `Optional<T>`, `Result<T, TError>`, or a dedicated sentinel object). Null is sometimes fine; just don’t let it become a hidden state machine.

#### `where T : struct`
**Meaning**

- \(T\) must be a **non-nullable value type** (i.e., *not* `Nullable<T>`).

**What it enables**

- `default(T)` is a *value* (zeroed struct) and not `null`.
- You can avoid many `null`-handling branches and represent optionality explicitly via `T?` (nullable value type).

**Trade-offs**

- `struct` does not mean “blittable/unmanaged”; it can still contain references.

**Common mistake**

- Assuming `struct` implies no allocations or no GC interaction. A struct can contain references and still keep objects alive.

#### `where T : unmanaged`
**Meaning**

- \(T\) must be an **unmanaged** type: it contains **no managed references** anywhere in its fields.

**What it enables**

- Efficient interop and low-level operations (`sizeof(T)`, stackalloc patterns, certain `Span<T>`/memory APIs).
- Safer use in high-performance/native-style code where you must ensure “no object references leak into unmanaged buffers”.

**Trade-offs**

- Excludes many otherwise reasonable structs (e.g., structs that contain `string`, arrays, or other reference-type fields).

**Mentor stress**

- Only use `unmanaged` when you truly need the guarantee. Don’t tighten your public API just to “feel faster.”

#### `where T : notnull`
**Meaning**

- \(T\) cannot be a *nullable* type:
  - not a nullable reference type (`string?`)
  - not a nullable value type (`int?`)

**What it enables**

- APIs where `null` keys are disallowed and you want the compiler to help enforce it.

**Canonical use**

- `Dictionary<TKey, TValue>` style keys: “a key must be non-null”.

**Trade-offs**

- `notnull` is primarily a **type-system contract**; it doesn’t magically make runtime null checks disappear for all cases.

**Example**

```csharp
using System.Collections.Generic;

static class Cache
{
    public static TValue GetOrAdd<TKey, TValue>(
        Dictionary<TKey, TValue> map,
        TKey key,
        System.Func<TKey, TValue> factory)
        where TKey : notnull
        => map.TryGetValue(key, out var value) ? value : (map[key] = factory(key));
}
```

### 2) **Construction/type constraints** (`new()`, base class, interface constraints)

#### `where T : new()`
**Meaning**

- \(T\) must have an **accessible parameterless constructor**.

**What it enables**

- You can call `new T()` inside generic code.

**Trade-offs**

- Many modern designs intentionally avoid public parameterless constructors (immutability, invariants, DI).
- This constraint often pushes you toward “anemic” types or weak invariants.

**Modern alternative**

- Prefer **factory injection** over `new()` for non-trivial creation:

```csharp
using System;

static class Builder
{
    public static T Create<T>(Func<T> factory) => factory();
}
```

Use `new()` only when the type is genuinely a “simple value holder” or when you control the constrained types.

#### Base-class constraint (`where T : SomeBase`)
**Meaning**

- \(T\) must derive from `SomeBase`.

**What it enables**

- Access to protected/public base members; shared implementation strategies.

**Trade-offs**

- Harder composition and testability; narrows caller types.
- Couples generic code to a class hierarchy; versioning constraints can become painful.

**Mentor rule**

- Prefer **interfaces** unless you need shared code or identity semantics that genuinely belong in a base class.

#### Interface constraints (`where T : IFoo`, multiple interfaces allowed)
**Meaning**

- \(T\) must implement one or more interfaces.

**What it enables**

- Compile-time availability of those members.

**Performance note**

- Calls through interface constraints are *still* interface calls (dispatch). The JIT can sometimes devirtualize in sealed/internal cases, but not always. Don’t assume “constraint = static dispatch.”

**Common mistake**

- Storing a value-type `T` into an interface variable (boxes). For a full boxing deep dive, see [3.3. Boxing interfaces generics](<../../../13 Structures/sections/3. Struct vs class/3.3. Boxing interfaces generics.md>).

### 3) **Member constraints** (static abstract interface members and generic math patterns)

Modern .NET supports a major capability: **static abstract members in interfaces**, which enables “generic math” and other compile-time member requirements.

**What it is**

- You define an interface that requires a static member (operator, property, method).
- You constrain \(T\) to that interface.
- Generic code can then call that static member in a strongly-typed way.

**Where it shines**

- Numeric algorithms over multiple numeric types without boxing or dynamic dispatch.

**Example (minimal, runnable)**

```csharp
using System;
using System.Numerics;

static class MathEx
{
    public static T Sum<T>(ReadOnlySpan<T> values) where T : INumber<T>
    {
        var sum = T.Zero;
        foreach (var v in values) sum += v;
        return sum;
    }
}

Console.WriteLine(MathEx.Sum<int>([1, 2, 3]));
Console.WriteLine(MathEx.Sum<double>([0.5, 1.5]));
```

**Trade-offs**

- Adds a dependency on `System.Numerics` interfaces and modern runtime support.
- Your API becomes more sophisticated; keep it in libraries that truly benefit from it.

**Good to know**

- This is the modern replacement for legacy patterns like:
  - `dynamic` numeric operations (slow, runtime failures)
  - `Convert.ToDouble`-based generic numeric hacks (allocations/boxing/culture pitfalls)
  - reflection-based operator discovery (AOT/trimming hostile)
