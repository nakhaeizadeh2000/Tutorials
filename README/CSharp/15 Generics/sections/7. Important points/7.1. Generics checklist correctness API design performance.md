## 7.1. Generics checklist: correctness, API design, and performance

1. **Keep APIs generic, not “objecty”** (type safety and perf; avoid hidden boxing)
2. **Constraints are contracts** (they affect callers, diagnostics, versioning, and performance)
3. **Avoid ambiguous overload sets** (inference failures and confusing call sites are real production costs)
4. **Pick honest abstractions** (`IEnumerable<T>` is not a collection; it’s a sequence)
5. **Avoid cleverness** (prefer readable generics; don’t emulate missing language features unless necessary)

---

### 1) **Keep APIs generic, not “objecty”**

**Mentor framing**

If the “real” type is \(T\), your API should accept/return \(T\) — not `object`. “Objecty” APIs:

- lose compile-time safety (casts move to runtime),
- often introduce boxing and extra allocations,
- hide intent (what is this `object` supposed to be?),
- and block optimizations (JIT can’t specialize as well once you erase types).

**Do**

- Accept `IEnumerable<T>` / `IReadOnlyList<T>` / `IReadOnlyDictionary<TKey, TValue>` when you only need those capabilities.
- Prefer `EqualityComparer<T>.Default`, `Comparer<T>.Default`, `IEqualityComparer<T>`, `IComparer<T>` (generic) for comparisons.
- Prefer the Try-pattern (`TryParse`, `TryGetValue`) over exceptions for expected failure.

**Avoid (legacy)**

- `ArrayList`, `Hashtable`, non-generic `IEnumerable`, non-generic `IComparable` in modern code.
- `params object[]` in hot paths (allocates an array + boxes value types).

**Performance note**

- Boxing is an allocation. Under load, allocation rate drives Gen0 frequency, which drives CPU and tail latency.
- If you’re designing a “hot path” API (parsers, serializers, message handlers), make the allocation-free call path the easiest one.

### 2) **Constraints are contracts**

**Definition**

A constraint is not a “compiler hint”. It’s a **public contract** that affects:

- which types callers are allowed to use,
- what operations you are allowed to perform inside the generic code,
- your error messages and usability,
- and sometimes performance (e.g., enabling `unmanaged`/`struct` paths).

**Mentor rules**

- Add constraints only when they buy you something real (correctness, expressiveness, or measurable performance).
- Treat “adding constraints later” as a breaking change for consumers.
- Prefer `notnull` when your algorithm requires dictionary keys / set elements that must not be null.

### 3) **Avoid ambiguous overload sets**

**Why it matters**

Ambiguity costs are real:

- call sites fail to compile when you add “one more overload”,
- callers start adding casts and `!` just to appease overload resolution,
- and your API becomes hostile to refactoring.

**Mentor patterns**

- Keep overload sets small and coherent.
- Prefer one “core” overload and delegate.
- If you expect `null` to be passed, don’t offer overloads differing by unrelated reference types.

- Overload resolution rules and common traps are covered deeply in `README/CSharp/05 Methods/sections/5. Overload resolution and overloading/5.1. Method overloading rules ambiguity API design.md`. This Generics domain focuses on inference- and constraint-driven gotchas.

### 4) **Pick honest abstractions**

**Mentor rule**

Don’t lie to callers:

- `IEnumerable<T>` means “sequence you can iterate”. It does **not** promise:
  - cheap `Count`,
  - repeatability,
  - index access,
  - or stable ordering.

If you require those, accept the tighter contract.

**Practical examples**

- Need index access? Use `IReadOnlyList<T>` (or `IList<T>` if mutation is required).
- Need membership test? Accept an `ISet<T>` / `IReadOnlySet<T>` (if available in your target) or an `IEqualityComparer<T>` plus `IEnumerable<T>` and build a `HashSet<T>` once.
- Need key lookup? Accept `IReadOnlyDictionary<TKey, TValue>` or `IDictionary<TKey, TValue>` depending on mutation.

**Performance note**

The wrong abstraction often leads to accidental \(O(n)\) work (`Count()` over an iterator) or repeated enumeration (re-running an expensive query).

---

### 5) **Avoid cleverness**

**Why mentors insist on this**

Generics let you build very abstract code. The problem is that **humans** have to maintain it.

Avoid:

- “type gymnastics” that mimic missing language features (e.g., HKT emulation) unless the domain truly needs it,
- meta-programming when a clear loop is fine,
- and generic wrappers whose only purpose is “being generic”.

Prefer:

- small, intention-revealing generic methods,
- clear names (`TKey`, `TValue`, `TResult`),
- and explicit “escape hatches” (strategy objects / delegates) instead of constraint puzzles.

**Good to know**

If your generic API requires callers to regularly specify type arguments explicitly, that’s a smell: inference ergonomics (and your public shape) needs improvement.
