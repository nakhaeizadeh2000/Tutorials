## 5.1. Property initializers: deterministic defaults without constructors

1. **Where they shine** (simple defaults, collections, option objects, immutable-ish models)
2. **Nullability** (avoid “null until set”; prefer non-null defaults or required initialization)
3. **Order and pitfalls** (initializer runs before constructor body; avoid referencing `this` in unsafe ways)

---

### 1) **Where they shine** (simple defaults, collections, option objects, immutable-ish models)
Property initializers let you provide **per-instance defaults** without writing boilerplate constructors.

Use them when:
- The default is **cheap**, **deterministic**, and **does not fail**.
- The property is part of the “shape” of the object (especially for DTO/config/test models).
- You want to enforce “never null” by default (e.g., empty collections instead of `null`).

Common good fits:
- **Option/config objects** with sensible defaults.
- **DTOs** where a default empty value is acceptable.
- **Immutable-ish models** where most properties are `get`-only/`init` and defaults reduce constructor overload noise.

Example (runnable): option object with defaults

```csharp
using System;

public sealed class RetryOptions
{
    public int MaxAttempts { get; init; } = 3;
    public TimeSpan BaseDelay { get; init; } = TimeSpan.FromMilliseconds(200);
    public bool Jitter { get; init; } = true;
}

public static class Program
{
    public static void Main()
    {
        var o = new RetryOptions { MaxAttempts = 5 };
        Console.WriteLine($"{o.MaxAttempts} {o.BaseDelay.TotalMilliseconds} {o.Jitter}");
    }
}
```

Good to know:
- A property initializer is just **compiler-generated assignment** during construction. It’s not “static shared state”.
- Prefer **simple expressions**. If the default needs I/O, environment probing, randomness, or heavy computation, push that into a factory or explicit initialization step.

Performance note:
- Defaults like `= 0`, `= ""`, `= TimeSpan.FromSeconds(1)` are trivial.
- Defaults that allocate object graphs (e.g., large collections, big buffers) increase allocation cost of *every* instance. Consider lazy initialization when this is measurable.

---

### 2) **Nullability** (avoid “null until set”; prefer non-null defaults or required initialization)
In modern C# with nullable reference types enabled, “null until someone sets it” is usually a bug factory.

Preferred patterns:
- **Provide a non-null default** when “empty” is valid.
- Use **`required`** when “must be provided by caller” is the real contract (mostly for DTO/config).
- For domain invariants, prefer **constructors/factories** (don’t rely on callers setting properties correctly).

Example (runnable): “never null” list property by default

```csharp
using System;
using System.Collections.Generic;

public sealed class Basket
{
    public List<string> Items { get; } = []; // per-instance empty list (C# 12+ collection expression)
}

public static class Program
{
    public static void Main()
    {
        var b = new Basket();
        b.Items.Add("Coffee");
        Console.WriteLine(b.Items.Count);
    }
}
```

Mentor warning:
- Exposing `List<T>` publicly is a *representation leak*. This example is about nullability/defaults only.
- The canonical “don’t leak mutable collections” guidance belongs in `5.2. Collection defaults: avoid shared mutable state bugs` (this domain).

See also:
- Deep `required` / `init` guidance: `README/CSharp/Constructors/sections/4. Object initialization styles/4.2. init required and illegal states unrepresentable.md`

### 3) **Order and pitfalls** (initializer runs before constructor body; avoid referencing `this` in unsafe ways)
Property initializers run **before the constructor body** of the containing type.
For the full, canonical execution-order model (base/derived, field init order, static rules), see:
- `README/CSharp/Fields/sections/1. Field fundamentals/1.2. Field initialization and execution order.md`

Practical consequences you should care about:
- Initializers run in **source order** within the type.
- Initializers can’t safely depend on complex state that the constructor sets up later.
- Avoid calling **virtual members** or using `this` in ways that depend on derived initialization (same reason as “no virtual calls in constructors”).

Example (runnable): initializer uses constructor parameter (safe) vs depends on later mutation (unsafe)

```csharp
using System;

public sealed class User
{
    private readonly string _userName;

    public string NormalizedUserName { get; } // computed once

    public User(string userName)
    {
        _userName = userName;
        // If you need normalization, do it here (or in a factory) so it’s deterministic and validated.
        NormalizedUserName = Normalize(_userName);
    }

    private static string Normalize(string value) => value.Trim().ToUpperInvariant();
}
```

Good to know:
- If a default needs validation (e.g., “must be positive”), do validation in the constructor/factory. Avoid “throwing from a property initializer” unless you’re absolutely sure it can’t become a surprise failure path.
