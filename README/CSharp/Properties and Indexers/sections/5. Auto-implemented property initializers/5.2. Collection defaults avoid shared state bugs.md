## 5.2. Collection and reference defaults: avoid shared mutable state bugs

1. **Per-instance allocation** (don’t accidentally share a mutable instance across objects)
2. **Read-only exposure** (return safe views; avoid representation leaks)
3. **Performance** (allocate only when needed; consider lazy init where it’s measurable)

---

### 1) **Per-instance allocation** (don’t accidentally share a mutable instance across objects)
When you use an auto-property initializer like:

```csharp
public List<int> Values { get; } = new();
```

you get a **new list per instance**. That’s what you want for mutable collections: each object owns its own state.

The bug you’re avoiding is **accidentally sharing a single mutable instance** between multiple objects—usually by using:

- a `static` mutable field/property, or
- a “default value” that is stored once and reused.

**Example (runnable): the classic static-sharing bug**

```csharp
using System;
using System.Collections.Generic;

public sealed class BadBasket
{
    // BUG: shared mutable list for all baskets.
    private static readonly List<string> _items = new();
    public IReadOnlyList<string> Items => _items;

    public void Add(string sku) => _items.Add(sku);
}

public static class Program
{
    public static void Main()
    {
        var a = new BadBasket();
        var b = new BadBasket();

        a.Add("A");
        b.Add("B");

        Console.WriteLine(string.Join(",", a.Items)); // A,B
        Console.WriteLine(string.Join(",", b.Items)); // A,B  (unexpected coupling)
    }
}
```

**Better (per-instance ownership)**

```csharp
using System;
using System.Collections.Generic;

public sealed class Basket
{
    private readonly List<string> _items = new();
    public IReadOnlyList<string> Items => _items;
    public void Add(string sku) => _items.Add(sku);
}
```

**Good to know**
- This is *not* only about correctness; shared mutable state often becomes a scalability bottleneck due to locking/contended updates.

---

### 2) **Read-only exposure** (return safe views; avoid representation leaks)
Having per-instance allocation is only half the story. You also need to avoid **representation leaks**: handing callers a reference that allows them to mutate your internal collection and bypass invariants.

Canonical deep treatment lives in the Fields domain:
- See `README/CSharp/Fields/sections/2. Accessibility and encapsulation for fields/2.2. Read-only exposure patterns.md`.

Here’s the short “properties-and-initializers” view:

- **Prefer** `IReadOnlyList<T>` / `IReadOnlyDictionary<TKey,TValue>` for a live read-only view (cheap and common).
- **Expose snapshots explicitly** via methods like `ToArray()` when you truly need a stable copy.
- **Avoid** returning `List<T>`/`Dictionary<,>` from public APIs unless mutation by callers is intended.

**Example (runnable): live view + explicit snapshot**

```csharp
using System.Collections.Generic;

public sealed class Inventory
{
    private readonly List<string> _skus = new();

    public IReadOnlyList<string> Skus => _skus;     // live view, no allocation
    public string[] GetSkusSnapshot() => _skus.ToArray(); // explicit allocation
}
```

**Performance note**
- A property getter that allocates (e.g., `public string[] Skus => _skus.ToArray();`) is a hidden GC cost and surprises callers. Prefer an explicit snapshot method.

---

### 3) **Performance** (allocate only when needed; consider lazy init where it’s measurable)
Auto-property initializers are great for readability, but they **allocate eagerly**.

Mentor guidance:
- If almost every instance uses the collection, eager allocation is fine and simpler.
- If most instances never use it (cold path), consider **lazy allocation** to avoid memory churn.

**Example (runnable): lazy init without locks (not thread-safe)**

```csharp
using System.Collections.Generic;

public sealed class LazyNotThreadSafe
{
    private List<int>? _values;
    public List<int> Values => _values ??= new();
}
```

If the object can be accessed concurrently, make the policy explicit:
- Either require external synchronization / single-threaded ownership, **or**
- implement a thread-safe lazy init (usually `Lazy<T>` or `Interlocked.CompareExchange` patterns).

Full deep concurrency/memory-model coverage is in `README/CSharp/Cuncurrent & Parallel`.
