## 1.1. Properties vs fields: contract vs storage (boundary, not overlap)

1. **What a property represents** (an API surface and contract; not “just a field with syntax”)
2. **Why properties exist** (encapsulation, invariants, versioning, binding/serialization friendliness)
3. **Performance reality** (JIT inlines trivial accessors; correctness and API evolution matter more than micro-optimizing)

---

### 1) **What a property represents**

A **property** is a **member that exposes a value-shaped API** while giving the type an **interception point** for access:

- `get`: value retrieval
- `set` / `init`: controlled mutation (runtime vs construction-time)

In C# and .NET, a property is part of your **public contract** in a way a private field isn’t:

- Callers compile against the property name and accessor shape (`get`-only vs `get; set;` vs `init`).
- Reflection and many frameworks treat properties as the primary “shape” of your object model.

**Don’t duplicate the full “fields vs properties vs methods” deep dive here.**
That comparison is already covered in depth here:

- See `README/CSharp/CSharp Basic Object Oriented Programming/sections/2. Creating classes and objects/2.1. Defining a class fields vs properties vs methods.md` for the complete treatment (binary compatibility, evolving representation, and API design rules).

What matters specifically for this domain is the **property contract** idea:

- A property communicates **“this is state you can observe”** (and maybe mutate, depending on accessors).
- A method communicates **“this is an action / operation”**.
- A field is **storage**, not a contract (and should usually be `private`).

**Mentor rule**
- If reading the member could be **surprising** (I/O, locks, heavy computation, network, database), it should likely be a **method**, not a property.

**Runnable example: stable contract, evolvable internals**

```csharp
using System;

public sealed class Counter
{
    // Representation is private and can change.
    private int _value;

    // Contract is public and stable.
    public int Value => _value;

    public void Increment() => _value++;
}

public static class Program
{
    public static void Main()
    {
        var c = new Counter();
        c.Increment();
        Console.WriteLine(c.Value); // 1
    }
}
```

**Good to know**
- In metadata terms, properties are “syntactic sugar” over methods (`get_Value`, `set_Value`), plus property metadata. That metadata is what many tools/frameworks use to discover and bind to your model.

### 2) **Why properties exist**

Properties exist because they let you **combine**:

- **Encapsulation**: you can keep representation private (fields) and expose a stable surface (properties).
- **Invariants**: accessors can validate and keep the object in a valid state after each mutation.
- **Versioning / evolution**: you can start with a simple auto-property, and later:
  - add validation,
  - add lazy initialization,
  - add change notifications (frontend),
  - change internal storage,
  - without changing call sites.
- **Tooling friendliness**: many serializers, binders, and mapping tools prefer properties.

**Common mistakes mentors see**

1. **“Setter as command”**: doing real work in `set` (e.g., writing to DB, calling HTTP, publishing messages).
   - Use a method (`ApplyX`, `UpdateY`, `ReloadZAsync`) for work.
2. **Getters with side effects**: “reading changes state” surprises callers and breaks caching assumptions.
3. **Throwing from getters under normal conditions**: disastrous for logging/binding/debugging because a simple inspection triggers exceptions.
4. **Leaking representation**: exposing a mutable collection through a property lets callers mutate behind your back.
   - For the full “representation leak” discussion, see `README/CSharp/Fields/sections/2. Accessibility and encapsulation for fields/2.2. Read-only exposure patterns (without leaking mutable state).md`.

**Frontend note**
- UI binding frameworks (WPF/WinForms/MAUI) often *require* properties and may observe changes via events (e.g., `INotifyPropertyChanged`). That’s a separate concern from core domain modeling; keep domain models clean and map to view models where needed. (When we cover notifications later, it will be marked **(frontend)**.)

### 3) **Performance reality**

In modern .NET (assume .NET 9+), **trivial accessors** are typically:

- **inlined** by the JIT in Release builds,
- optimized well enough that “field vs auto-property” is almost never your bottleneck.

**What actually hurts performance**

- **Hidden allocations**: LINQ in getters, string building, boxing, iterator allocations.
- **Locks / contention**: putting synchronization inside accessors without a design-level policy.
- **Expensive computed properties** called repeatedly in hot paths (accidental \(O(n)\) per read).
- **Exceptions** for expected outcomes (misses, validation failures).

**Performance note**
- If a property is computed and non-trivial, treat it like an API contract: either
  - make it cheap and cache correctly (with clear invalidation), or
  - expose it as a method (`ComputeTotal()` / `TryGetX(out ...)`) so callers know it does work.

**Thread-safety note**
- Properties do not make state thread-safe. If multiple threads read/write the underlying state, you need a clear synchronization strategy. For the full memory model / synchronization deep dive, see `README/CSharp/Cuncurrent & Parallel/README.md`.
