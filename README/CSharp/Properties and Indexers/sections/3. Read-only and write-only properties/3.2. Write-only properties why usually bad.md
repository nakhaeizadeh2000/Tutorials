## 3.2. Write-only properties: why they’re usually a bad API

1. **Design smell** (callers can’t observe state; debugging and correctness suffer)
2. **Better alternatives** (methods that express intent; command-style APIs; “Try” patterns where failures are expected)
3. **When they exist** (rare integration/binding scenarios; keep them narrow and documented)

---

### 1) **Design smell** (callers can’t observe state; debugging and correctness suffer)

A *write-only property* looks like this:

```csharp
public string Password { set => _passwordHash = Hash(value); } // no getter
```

Mentors dislike this API shape because it hides too much:

- **No observability**: callers can’t read the value back to verify what they set (including tests).
- **Harder debugging**: you can’t inspect state meaningfully without stepping into the setter or peeking at private fields.
- **Ambiguous semantics**: is it storing data? Is it performing an operation? Is it validating? Is it best-effort?
- **Surprising side effects**: property assignment reads like “set a value”, not “run a workflow”.

In C# API design, properties are best when they model a *value* (state) that is **cheap to read** and **has predictable semantics**. A write-only property nearly always means the “thing” you’re doing is actually a **command**, and commands belong as **methods**.

**Good to know**
- There is no technical limitation: the language supports write-only properties. This is a design guidance rule, not a compiler rule.
- If you *never* want a value to be read back (e.g., secrets), that’s usually a *domain/security* concern. The solution is still rarely “write-only property”.

---

### 2) **Better alternatives** (methods that express intent; command-style APIs; “Try” patterns where failures are expected)

#### Prefer intention-revealing methods

If setting the value has logic (validation, hashing, normalization, I/O, eventing), name the action:

```csharp
using System;
using System.Security.Cryptography;
using System.Text;

public sealed class UserCredentials
{
    private byte[] _salt = RandomNumberGenerator.GetBytes(16);
    private byte[] _hash = [];

    public void SetPassword(string password)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(password);

        // Minimal demo: use a KDF in real systems. (This is just a shape example.)
        using var sha = SHA256.Create();
        _hash = sha.ComputeHash(Encoding.UTF8.GetBytes(password));
    }

    public bool VerifyPassword(string password)
    {
        using var sha = SHA256.Create();
        var candidate = sha.ComputeHash(Encoding.UTF8.GetBytes(password));
        return CryptographicOperations.FixedTimeEquals(_hash, candidate);
    }
}
```

Why this is better:
- **The API communicates side effects**: `SetPassword` is clearly an action.
- **Testing is direct**: call `VerifyPassword` rather than needing a getter.
- **You can evolve behavior** without breaking the “property means value” mental model.

#### Prefer Try-pattern when failure is expected (no exceptions-as-control-flow)

If setting can fail as part of normal operation (e.g., parsing, validation you want to surface without exceptions), a Try-pattern is clearer and more performant under repeated failure:

```csharp
public sealed class Percentage
{
    private int _value;
    public int Value => _value;

    public bool TrySet(int value)
    {
        if ((uint)value > 100) return false;
        _value = value;
        return true;
    }
}
```

**Performance note**
- Exceptions are expensive when thrown frequently. If invalid input is a normal case (user input, parsing, business rules), prefer a Try-style API.
- For a deeper “exceptions vs Try-pattern” treatment, see `README/CSharp/Type Conversion/sections/7. Important points and common pitfalls/7.1. Type conversion checklist correctness performance maintainability.md`.

### 3) **When they exist** (rare integration/binding scenarios; keep them narrow and documented)

The only defensible cases are *integration constraints* where a framework expects a property-like “sink”:

- **(frontend)** Some binding systems historically interacted with properties more naturally than methods.
- Some serializers/tools might set properties by convention.

Even then, prefer:

- **Keep it non-public** if possible (`private set`, `internal set`) and expose a method for real usage.
- **Document intent**: why it exists and what it does.
- **Avoid irreversible side effects** in the setter (especially I/O). If it must do work, keep it deterministic and fast.

**Mentor rule**
- If you think you need a write-only property, start by writing the method you *wish* callers had (e.g., `ApplySecret(...)`, `Configure(...)`, `SetPassword(...)`). Only add the property if a specific framework requires it, and keep it as a thin adapter.
