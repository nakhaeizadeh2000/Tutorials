## 2.1. Manual properties with backing fields: when you actually need them

1. **When manual is required** (validation, lazy initialization, caching, raising events, atomic updates)
2. **Correctness** (avoid recursion; preserve invariants; keep setter logic centralized)
3. **Performance** (avoid repeated expensive computations; consider caching vs staleness and memory growth)

---

### 1) **When manual is required** (validation, lazy initialization, caching, raising events, atomic updates)

An **auto-property** (`public int X { get; set; }`) gives you a hidden backing field and trivial accessors. You switch to a **manual property with a backing field** when you need *behavior* at the boundary:

- **Validation / normalization**: enforce range, trim strings, reject invalid states.
- **Coordinated updates / invariants**: updating one value must update another (e.g., `Balance` + `LastUpdated`).
- **Lazy initialization**: allocate/compute only if the value is actually needed.
- **Caching computed values**: avoid recomputing \(O(n)\) or expensive operations on each access.
- **Change notifications** (frontend): e.g., `INotifyPropertyChanged` (WPF/WinUI/MAUI) or reactive models.
- **Atomic updates / concurrency boundaries**: you need `Interlocked`, `Volatile`, or a `lock` around reads/writes.

**Mentor rule**
- Start with an auto-property. Switch to manual only when you can name the concrete requirement above.
- If the “property” performs meaningful work (I/O, locking, network calls, database writes), it should almost always be a **method**, not a property. See `README/CSharp/CSharp Basic Object Oriented Programming/sections/2. Creating classes and objects/2.1. Defining a class fields vs properties vs methods.md` for the full reasoning.

**Example (runnable): validation + normalization**

```csharp
using System;

public sealed class Person
{
    private string _name = "";

    public string Name
    {
        get => _name;
        set
        {
            var trimmed = value?.Trim();
            if (string.IsNullOrEmpty(trimmed))
                throw new ArgumentException("Name is required.", nameof(value));

            _name = trimmed;
        }
    }
}

public static class Program
{
    public static void Main()
    {
        var p = new Person { Name = "  Ada  " };
        Console.WriteLine(p.Name); // Ada
    }
}
```

**Good to know**
- Prefer **guard clauses** that fail fast. If invalid input is expected (e.g., parsing), use a Try-pattern instead of exceptions (deep coverage in `README/CSharp/Type Conversion/...`).

**Example (runnable): lazy initialization without double allocation**

```csharp
using System;
using System.Threading;

public sealed class ExpensiveThing
{
    public Guid Id { get; } = Guid.NewGuid();
}

public sealed class Holder
{
    private ExpensiveThing? _value;

    public ExpensiveThing Value
    {
        get
        {
            // Thread-safe, allocation-safe lazy initialization.
            var existing = Volatile.Read(ref _value);
            if (existing is not null) return existing;

            var created = new ExpensiveThing();
            var winner = Interlocked.CompareExchange(ref _value, created, comparand: null);
            return winner ?? created;
        }
    }
}
```

**Performance note**
- `Lazy<T>` is also valid, but it allocates a helper object and can hide policies. Manual patterns are fine when you can keep them correct and small.
- For deep thread-safety/memory-visibility rules, see `README/CSharp/Cuncurrent & Parallel/README.md` (memory model + synchronization primitives).

### 2) **Correctness** (avoid recursion; preserve invariants; keep setter logic centralized)

Manual properties introduce new failure modes. The most common production bugs are *self-inflicted* by accessor logic.

**Avoid recursion**

```csharp
// BUG: infinite recursion
public int Count
{
    get => Count;         // calls itself
    set => Count = value; // calls itself
}
```

Correct version uses a backing field:

```csharp
private int _count;
public int Count
{
    get => _count;
    set => _count = value;
}
```

**Keep invariants centralized**
- If the invariant is “value must be in range,” enforce it in exactly one place (often the setter).
- If multiple properties must change together, consider an **intention-revealing method** (`SetRange(min, max)`), because object initializers and independent setters can temporarily violate cross-property invariants. See `README/CSharp/Constructors/sections/4. Object initialization styles/4.1. Object initializer syntax power limits invariants.md` for the full treatment of partial initialization hazards.

**Don’t let getters throw for normal reasons**
- Getters should be cheap and unsurprising. If access can fail (cache miss, lookup not found), use a method:
  - `TryGetX(out ...)`
  - `GetXOrDefault()`
  - `GetXOrThrow()` (explicit)

### 3) **Performance** (avoid repeated expensive computations; consider caching vs staleness and memory growth)

The main performance risks with manual properties are:

- **Hidden allocations** inside getters/setters (LINQ, string formatting, capturing lambdas, `params` arrays).
- **Accidental \(O(n)\)** getters (computed properties that scan collections every call).
- **Over-caching** (memory growth, stale values, cache invalidation bugs).

**Prefer “work is explicit”**
- If a property has to compute something expensive, a method communicates the cost better: `ComputeTotal()` or `GetTotal()` (naming is a policy choice, but make it consistent).

**If you cache, define the invalidation policy**
- Cache is never “free.” You must answer:
  - What invalidates it?
  - Is it per instance or shared?
  - Is it thread-safe?
  - What’s the memory ceiling?

**Example (pattern): cached computed property with explicit invalidation**

```csharp
using System;
using System.Collections.Generic;

public sealed class Basket
{
    private readonly List<decimal> _prices = new();
    private decimal? _cachedTotal;

    public decimal Total
    {
        get
        {
            if (_cachedTotal is { } total) return total;

            decimal sum = 0;
            foreach (var p in _prices) sum += p;
            _cachedTotal = sum;
            return sum;
        }
    }

    public void Add(decimal price)
    {
        if (price < 0) throw new ArgumentOutOfRangeException(nameof(price));
        _prices.Add(price);
        _cachedTotal = null; // invalidation policy: any mutation invalidates
    }
}
```

**Performance note**
- If `Total` is used rarely, caching can be wasted memory/state.
- If `_prices` changes frequently, caching can be wasted CPU (recompute anyway) and adds complexity. Measure and choose intentionally.
