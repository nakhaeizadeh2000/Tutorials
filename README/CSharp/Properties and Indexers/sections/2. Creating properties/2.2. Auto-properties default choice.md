## 2.2. Auto-properties: default choice for most code

1. **Why auto-properties** (less boilerplate; fewer bugs; cleaner refactors)
2. **Guidance** (start with auto; switch to manual when a real requirement appears)
3. **Versioning** (you can evolve from auto-property to manual without breaking callers)

---

### 1) **Why auto-properties** (less boilerplate; fewer bugs; cleaner refactors)

An **auto-property** is a property where the compiler generates the backing field for you:

```csharp
public sealed class User
{
    public string UserName { get; init; } = "";
    public int Reputation { get; private set; }
}
```

**Why mentors default to auto-properties**

- **Less room for mistakes**: no accidental recursion (`get => Value;`) and no forgotten assignments.
- **Clear intent**: “this is simple state with no special behavior”.
- **Easier refactors**: rename, change accessibility, add attributes, add nullability, etc., with less noise.
- **Plays well with tooling/frameworks**: serializers, binders, mappers, analyzers.

**Good to know**

- “Auto-property” does **not** mean “slow”. The JIT can inline trivial accessors, and the generated backing field is just a field.
- Auto-properties can still be **computed** via expression-bodied getters, but then they’re not “auto” in the strict sense (no generated backing field). For computed properties with real work, see `README/CSharp/Properties and Indexers/sections/1. Properties fundamentals/1.3. Property invariants validation and anti-patterns.md`.

---

### 2) **Guidance** (start with auto; switch to manual when a real requirement appears)

**Start with auto-properties when**

- the getter/setter is pure storage,
- you don’t need validation or side effects,
- you want clean API surface with minimal code.

**Switch to a manual property when you need one of these**

- **Validation** (range checks, normalization): see `2.1`.
- **Lazy initialization** or **caching**: see `2.1`.
- **Change notification** (frontend): `INotifyPropertyChanged` patterns typically need manual set logic.
- **Atomic updates / thread-safety**: e.g., `Interlocked`, `Volatile`, locks (deep concurrency guidance lives in `README/CSharp/Cuncurrent & Parallel`).
- **Coupled state updates**: changing one property must update others while preserving invariants.

**Mentor rule**

- Don’t put “real work” in a property just because you can. If it’s an *operation* (might allocate, might throw, might block, might lock), make it a **method** so cost and behavior are explicit.

**Example (runnable): idiomatic auto-properties with shaped mutability**

```csharp
using System;

public sealed class Order
{
    public required string Id { get; init; }

    public DateTimeOffset CreatedAt { get; } = DateTimeOffset.UtcNow;

    // Publicly read-only; internally controlled mutation.
    public OrderStatus Status { get; private set; } = OrderStatus.Created;

    public void MarkPaid()
    {
        if (Status != OrderStatus.Created) throw new InvalidOperationException("Invalid transition.");
        Status = OrderStatus.Paid;
    }
}

public enum OrderStatus { Created, Paid }
```

Performance note:

- This is allocation-free beyond the object itself and is easy for the JIT to optimize.

### 3) **Versioning** (you can evolve from auto-property to manual without breaking callers)

**Key idea**: A property is a **contract**. You can change its internal implementation later.

If you start with:

```csharp
public int Age { get; set; }
```

you can later evolve it to:

```csharp
private int _age;
public int Age
{
    get => _age;
    set => _age = value is >= 0 and <= 150
        ? value
        : throw new ArgumentOutOfRangeException(nameof(value));
}
```

without changing how callers use it.

**What can still be breaking**

- Tightening accessibility (`public set` → `private set`) is a breaking change for callers.
- Changing semantics (e.g., setter starts throwing or normalizing) is a behavior change that can break consumers.
- Adding `required` to an existing public type is source-breaking for consumers (see `README/CSharp/Constructors/sections/4. Object initialization styles/4.2. init required and illegal states unrepresentable.md` for the full treatment).

Good to know:

- If you care about **binary compatibility** across compiled consumers, changing a *public field* to a property is breaking. Changing a property’s implementation is typically not (but changing signature/accessibility is). For the deep cross-cutting view, see `README/CSharp/CSharp Basic Object Oriented Programming/sections/2. Creating classes and objects/2.1. Defining a class fields vs properties vs methods.md`.
