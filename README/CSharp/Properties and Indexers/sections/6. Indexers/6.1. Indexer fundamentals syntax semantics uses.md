## 6.1. Indexer fundamentals: syntax, semantics, and typical uses

1. **What an indexer is** (parameterized property; often models a lookup/collection-like view)
2. **Typical patterns** (dictionary-style lookup, matrix/2D access, cache facade, span-like element access)
3. **Correctness** (argument validation; exception vs Try-pattern; predictable behavior)

---

### 1) **What an indexer is** (parameterized property; often models a lookup/collection-like view)
An **indexer** is a *property with parameters*. It lets consumers use *indexing syntax* (`obj[key]`) to access values.

In C#, an indexer:
- Is declared with `this[...]`.
- Can have `get`, `set`, `init`, and even `ref` returns (advanced; see `6.2`).
- Must live on a type (class/struct/record), not on a static class.

**Mental model**
- `obj[key]` should feel like *accessing an element* or a *lookup*.
- If the operation is *not* element access (it triggers I/O, does heavy computation, or has surprising side effects), it should usually be a **method** instead.

**Language notes (C# 15 era)**
- Indexers participate in normal member accessibility and nullability rules.
- You can overload indexers by parameter list (e.g., `this[int i]` and `this[string name]`), but avoid “indexer overload soup” because it hides intent.

**Good to know**
- Indexers are widely recognized by tooling and frameworks as “collection-like”; that can be helpful (intellisense expectations), but it also means consumers expect predictable behavior.

---

### 2) **Typical patterns** (dictionary-style lookup, matrix/2D access, cache facade, span-like element access)
Indexers are best when your type *is conceptually a container*.

#### A) Dictionary-style lookup (key → value)

```csharp
using System;
using System.Collections.Generic;

public sealed class Headers
{
    private readonly Dictionary<string, string> _map = new(StringComparer.OrdinalIgnoreCase);

    public string? this[string name]
    {
        get => _map.TryGetValue(name, out var value) ? value : null;
        set
        {
            if (string.IsNullOrWhiteSpace(name)) throw new ArgumentException("Header name is required.", nameof(name));
            if (value is null) _map.Remove(name);
            else _map[name] = value;
        }
    }
}

public static class Demo
{
    public static void Main()
    {
        var h = new Headers();
        h["Content-Type"] = "application/json";
        Console.WriteLine(h["content-type"]);
        h["Content-Type"] = null; // remove
        Console.WriteLine(h["Content-Type"] is null);
    }
}
```

**Mentor note**
- Returning `null` for “missing key” is a policy choice. For non-nullable APIs, consider `TryGetValue` style methods to avoid ambiguity (missing vs present-null).

#### B) 2D / matrix-like access

```csharp
using System;

public sealed class Matrix
{
    private readonly double[,] _data;

    public Matrix(int rows, int cols)
    {
        if (rows <= 0) throw new ArgumentOutOfRangeException(nameof(rows));
        if (cols <= 0) throw new ArgumentOutOfRangeException(nameof(cols));
        _data = new double[rows, cols];
    }

    public double this[int row, int col]
    {
        get => _data[row, col];
        set => _data[row, col] = value;
    }
}
```

**Performance note**
- Bounds checks are fine and usually optimized well. Don’t micro-optimize until you’ve measured. If you truly need to reduce checks in hot loops, consider exposing `Span<T>`-based access patterns (advanced and workload-specific).

#### C) Cache facade (be careful)
Indexers can be tempting for caches (`cache[key]`), but caches involve policy:
- misses vs hits
- eviction
- thread-safety
- possibly async I/O for population

If `cache[key]` can block, allocate, lock heavily, or perform I/O, prefer explicit methods like `GetOrAdd`, `TryGet`, `GetOrAddAsync`.

See: `README/CSharp/Cuncurrent & Parallel/README.md` for deep concurrency primitives and patterns if your cache is shared across threads.

### 3) **Correctness** (argument validation; exception vs Try-pattern; predictable behavior)
**Predictability is the contract.** Consumers expect indexers to be:
- **Fast** (no I/O, no long waits)
- **Deterministic** (same input → same result unless underlying data changes)
- **Safe** (clear behavior on missing keys or out-of-range indices)

#### Validation
- Use `ArgumentOutOfRangeException` for invalid indices.
- Use `ArgumentException` for invalid keys (empty/whitespace) when appropriate.

#### Missing elements: exceptions vs Try-pattern
Mentor rule:
- If “missing” is **exceptional**, throwing can be acceptable (e.g., matrix index out of bounds).
- If “missing” is **expected**, do *not* make throwing the normal branch.
  - Prefer `TryGetValue(...)` methods or a nullable return (`T?`) when that’s unambiguous.

#### Avoid side effects in indexers
Don’t do these in `get`:
- network calls / disk I/O
- logging as part of normal reads
- taking heavy locks
- modifying state unexpectedly

If you need that behavior, expose a method with an explicit name (`LoadAsync`, `Compute`, `Refresh`, `GetOrAdd`).
