## 7.2. `goto`: why it exists, when it’s acceptable, and safer alternatives

1. **`goto case` in `switch` (the one common legitimate use)**
2. **Why `goto` is usually a maintainability trap**
3. **Alternatives (loops + flags, extracted methods, state machines)**

### 1) **`goto case` in `switch`**
**Why it exists**
- `goto case` lets you reuse a case’s logic *without* duplicating code.
- It can be reasonable for small “fall-through-like” sharing, especially in command/menu handling.

**Example**

```csharp
Console.Write("Choice (1=Add, 2=Subtract, 3=Quit): ");
var input = Console.ReadLine();

if (!int.TryParse(input, out var choice))
{
    Console.WriteLine("Invalid choice.");
    return;
}

switch (choice)
{
    case 1:
        Console.WriteLine("Add selected.");
        break;

    case 2:
        Console.WriteLine("Subtract selected.");
        break;

    case 0:
        // Reuse the same behavior as “Quit” (e.g., aliases)
        goto case 3;

    case 3:
        Console.WriteLine("Bye.");
        break;

    default:
        Console.WriteLine("Unknown choice.");
        break;
}
```

**Mentor note**
- If you have many aliases, `goto case` can be fine. If you have many intertwined transitions, you likely need a clearer design.

**Parsing note**
- This example uses `int.TryParse` for brevity. Canonical parsing + culture guidance is in **[2.1](<../2. Console I-O/2.1. The System.Console class input output formatting.md>)**:

### 2) **Why `goto` is usually a trap**
**What goes wrong**
- It creates non-local jumps that make control flow harder to reason about.
- It increases the chance of skipping initialization/validation, which becomes a correctness bug.
- It makes debugging and refactoring riskier (the compiler can’t “help you” as much).

**Performance reality**
- `goto` is not a performance tool for normal apps. Any micro “savings” is irrelevant compared to the cost of complexity and bugs.

### 3) **Safer alternatives**
**Alternative A: extract a method (preferred)**
- When multiple places need the same behavior, move it to a function.

```csharp
static void PrintUnknownChoice() => Console.WriteLine("Unknown choice.");
```

**Alternative B: use a loop with a clear state**
- A small state machine can be clearer than jumps.

```csharp
while (true)
{
    Console.Write("Choice (1=Run, 2=Help, 3=Quit): ");
    var input = Console.ReadLine();
    if (!int.TryParse(input, out var choice))
    {
        Console.WriteLine("Invalid.");
        continue;
    }

    switch (choice)
    {
        case 1:
            Console.WriteLine("Running...");
            break;
        case 2:
            Console.WriteLine("Help...");
            break;
        case 3:
            return;
        default:
            Console.WriteLine("Unknown.");
            break;
    }
}
```

**Alternative C: use a mapping**
- For menu actions, mapping input to actions can eliminate branching noise:

```csharp
var actions = new Dictionary<int, Action>
{
    [1] = () => Console.WriteLine("Run"),
    [2] = () => Console.WriteLine("Help"),
    [3] = () => Console.WriteLine("Quit"),
};
```

**Mentor guidance**
- As soon as `goto` seems tempting, treat it as a signal: the function is doing too many things or the state transitions aren’t explicit enough.
