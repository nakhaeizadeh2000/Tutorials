## 1.2. Creating your first app (Console + top-level statements)

1. **Two ways: Visual Studio vs `dotnet new console` (same result, different workflow)**
2. **Top-level statements vs explicit `Main` (what the compiler generates)**
3. **Good defaults (nullable enabled, implicit usings, predictable entry point)**

### 1) **Two ways: Visual Studio vs `dotnet new console`**
**What you’re creating**
- Both approaches produce the same concept: an SDK-style `.csproj` + a `Program` entry point.
- The difference is the *workflow*: IDE-driven debugging/profiling vs CLI-first repeatability.

**Visual Studio (IDE-first)**
- Create a new project → **Console App** (C#) → target a modern framework (assume .NET 9+).
- Best when you want integrated debugging, watch windows, and profilers from day one.

**dotnet CLI (workflow-first)**

```bash
dotnet new console -n HelloBasics
cd HelloBasics
dotnet run
```

**Trade-offs**
- **CLI-first** is closer to CI/CD and containers (repeatable, scriptable, works everywhere).
- **IDE-first** is faster for learning and debugging when you’re exploring behavior step-by-step.

**Common mistakes**
- Picking “whatever template” without noticing the target framework. You want modern .NET so you’re learning modern APIs and runtime behavior.
- Confusing `dotnet run` with “deployment”. It’s a convenience; shipping is `dotnet publish` (see Fundamental Theories tooling sections for the full pipeline).

### 2) **Top-level statements vs explicit `Main`**
**Top-level statements (default template)**

```csharp
Console.WriteLine("Hello, world!");
```

**What the compiler generates (practical understanding)**
- The compiler synthesizes a `Program` type and an entry point method, then places your statements inside it.
- This reduces ceremony for small programs and examples.

**When to prefer top-level statements**
- Tiny demos, katas, quick throwaway experiments, teaching snippets.
- Early learning: fewer distractions before control flow is understood.

**When to prefer an explicit `Main`**
- When you want the app shape to be obvious (entry point + arguments + return codes).
- When you want to structure code into types/methods and keep the “root” explicit.

```csharp
public static class Program
{
    public static int Main(string[] args)
    {
        Console.WriteLine($"Args: {args.Length}");
        return 0;
    }
}
```

**Good to know**
- Top-level files can still declare types and local functions; don’t let one file become a “dumping ground”.
- If you need async startup, top-level statements support `await` as well (the compiler generates an async entry point).

### 3) **Good defaults (nullable enabled, implicit usings, predictable entry point)**
**Nullable reference types**
- Keep nullable enabled and treat warnings as real design feedback.
- Nullability improves correctness and makes APIs clearer.

**Implicit global usings**
- Helpful for small projects and teaching material. In larger codebases, some teams disable it to make dependencies more explicit.

**Predictable entry point**
- Don’t create multiple top-level statement files in the same project unless you intend to; it confuses “where does the program start?”.

**Performance framing (mentor-critical)**
- Your early performance wins are almost never about syntax.
- They come from:
  - doing less work (avoid repeated parsing/formatting),
  - avoiding needless allocations,
  - keeping I/O out of tight loops,
  - and choosing appropriate algorithms/data structures.
