## 3.1. Variables, identifiers, and assignment fundamentals

1. **Declaration forms (`var`, explicit types, `const`, `readonly`)**
2. **Definite assignment + scope (why the compiler “won’t let you”)**
3. **Mentor notes (readability-first `var`, avoid “stringly typed” flags, prefer small scopes)**

### 1) **Declaration forms (`var`, explicit types, `const`, `readonly`)**
**Definition (what “a variable” really is in C#)**
- A variable is a *name* bound to a value with a **compile-time type**.
- That type drives:
  - **Correctness**: which operations compile, what overflow rules apply, nullability warnings
  - **Performance**: copying costs, boxing, allocations, and (sometimes) JIT optimizations
  - **API clarity**: what your teammates think the value represents

**`var` vs explicit types**
- `var` is still **statically typed**; it’s type inference, not dynamic typing.
- Use `var` when the type is obvious from the RHS or the name:

```csharp
var users = new List<string>();
var count = users.Count;
```

- Prefer explicit types when it improves readability or teaches intent:

```csharp
DateTimeOffset now = DateTimeOffset.Now; // “moment in time” is explicit
string name = "Ada";
```

**Trade-offs**
- `var` can *hide* important types (e.g., `IEnumerable<T>` vs `List<T>` vs `Span<T>`). If the type affects behavior/perf, be explicit.
- Explicit types can become noisy and reduce refactoring flexibility; don’t “type everything” by habit.

**Common mistakes**
- Using `var` with ambiguous method calls and then misunderstanding the type:

```csharp
var seq = Enumerable.Range(0, 10); // IEnumerable<int>, deferred execution
```

If you intend materialization, do it explicitly (and understand allocations).

**`const`**
- `const` values are **inlined at compile time** into callers.
- Great for *private* constants and local code.
- Be cautious with public constants in libraries: changing a public `const` requires consumers to recompile to see the new value.

```csharp
const int MaxRetries = 3;
```

**`readonly`**
- `readonly` applies to **fields** (not locals). It enforces “assign only in initializer/constructor”.
- Use it to communicate invariants and reduce accidental mutation.

```csharp
public sealed class Config
{
    public readonly string EnvironmentName;
    public Config(string environmentName) => EnvironmentName = environmentName;
}
```

Good to know:
- If you’re designing an API, immutable data models often benefit from *properties* rather than public fields (encapsulation, validation, versioning).

### 2) **Definite assignment + scope (why the compiler “won’t let you”)**
**Definite assignment**
- The compiler prevents reading uninitialized locals. This eliminates an entire class of bugs and improves refactor safety.
- This is a compile-time rule; it’s about correctness and maintainability, not runtime speed.

```csharp
int x;
// Console.WriteLine(x); // error: use of unassigned local variable

if (DateTime.UtcNow.Ticks % 2 == 0)
    x = 1;
else
    x = 2;

Console.WriteLine(x); // ok: assigned on all paths
```

**Scope**
- Smaller scope means fewer accidental dependencies and easier reasoning.
- Declare variables near first use; don’t “pre-declare” everything at the top of the method.

**Common mistakes**
- Declaring variables too early, then accidentally reusing them for a different purpose (“variable reuse”), which hides bugs in plain sight.
- Making a variable nullable “just to satisfy the compiler”, instead of structuring control flow so the variable is assigned on all paths.

Performance note:
- Locals are cheap; don’t optimize by reusing variables. Optimize by reducing work and allocations.

### 3) **Mentor notes (readability-first `var`, avoid “stringly typed” flags, prefer small scopes)**
**Readability-first `var`**
- Use `var` when the type is obvious.
- Avoid `var` when the type affects semantics, lifetime, or performance.

**Avoid “stringly typed” flags**
- Don’t encode decisions in strings/integers scattered across the codebase.
- Prefer `enum` (or a small type) to make invalid states harder to represent:

```csharp
enum UserRole { Guest, Member, Admin }
```

If the values come from user input, parse once at the boundary and keep typed values internally.
