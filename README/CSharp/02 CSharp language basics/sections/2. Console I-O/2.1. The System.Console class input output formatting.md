## 2.1. The `System.Console` class: input, output, formatting

1. **Write/WriteLine, ReadLine, ReadKey (and when each is appropriate)**
2. **Formatting (interpolation, composite formatting, culture, and performance implications)**

### 1) **Write/WriteLine, ReadLine, ReadKey (and when each is appropriate)**
**Mental model**
- `Console` is a *global, process-wide* façade over standard streams:
  - `Console.In` (`TextReader`) usually reads from **stdin**
  - `Console.Out` / `Console.Error` (`TextWriter`) write to **stdout/stderr**
- Those streams may be **interactive** (terminal) or **redirected** (piped from / to a file or another process). Your program should behave correctly in both modes.

**Output APIs**
- Use `Console.WriteLine(...)` for normal user-facing output.
- Use `Console.Write(...)` for prompts that should remain on the same line.
- Use `Console.Error.WriteLine(...)` for *errors* (keeps errors separate from output; important for scripting/pipelines).

**Input APIs**
- `Console.ReadLine()` reads a line and returns `string?`:
  - `null` means **end-of-input** (Ctrl+Z/Ctrl+D, or redirected file ended).
- `Console.ReadKey(intercept: true)` reads a single key without echoing; good for “press any key” and minimal menus.
  - Don’t use it for “real text input”: editing, backspace handling, IME, etc. are not handled like a proper console UI library.

**When to prefer `Console.In/Out`**
- If you want your logic to be testable, don’t hardcode `Console.ReadLine()` everywhere—pass `TextReader`/`TextWriter` in, or at least centralize reads/writes in one place.

```csharp
static void Run(TextReader input, TextWriter output)
{
    output.Write("Name: ");
    var name = input.ReadLine();
    if (name is null) return;
    output.WriteLine($"Hello, {name}!");
}

Run(Console.In, Console.Out);
```

**Performance note**
- Console I/O is *slow* compared to CPU work. Optimize by reducing the **number of writes** (batch output), not by micro-optimizing string formatting.
- `Console` is thread-safe for basic usage, but mixed concurrent writes can interleave and become unreadable. Prefer one “writer” or use a lock if multiple threads write.

### 2) **Formatting (interpolation, composite formatting, culture, and performance implications)**
**Prefer modern formatting**
- Interpolation is the default for readability:

```csharp
var total = 12.5m;
Console.WriteLine($"Total: {total}");
```

**Composite formatting is legacy-but-valid**
- `Console.WriteLine("Total: {0}", total)` still works, but is less readable and easier to mismatch.

**Culture is not optional**
- Human-facing output: **current culture** (default formatting is typically OK).
- Machine-facing output (logs/files/protocols): choose a deterministic format and typically use **invariant culture**.

```csharp
using System.Globalization;

var value = 12_345.67;
Console.WriteLine(value.ToString(CultureInfo.CurrentCulture));   // for the user
Console.WriteLine(value.ToString(CultureInfo.InvariantCulture)); // for machines
```

**Parsing is part of Console I/O (canonical guidance for this tutorial)**
- Don’t throw exceptions for normal user mistakes. Use `TryParse` + clear error messages.
- If parsing needs to be culture-stable, pass `CultureInfo.InvariantCulture`.

```csharp
using System.Globalization;

static bool TryReadInt(TextReader input, TextWriter output, string prompt, out int value)
{
    output.Write(prompt);
    var text = input.ReadLine();
    if (text is null)
    {
        value = default;
        return false; // end-of-input
    }

    if (!int.TryParse(text, NumberStyles.Integer, CultureInfo.CurrentCulture, out value))
    {
        output.WriteLine("Invalid integer.");
        return false;
    }

    return true;
}
```

**Allocation note**
- Formatting creates strings. That’s fine for normal console apps.
- If you’re printing in a tight loop, first reduce I/O frequency. Only after that consider buffering output (e.g., `StringBuilder`) and printing once.

### 3) **Common pitfalls (null input, blocking reads, encoding, flushing, testing console apps)**
**Pitfall: assuming `ReadLine()` never returns null**

```csharp
var line = Console.ReadLine();
if (line is null)
{
    // End-of-input: handle gracefully (especially when piped).
    return;
}
```

**Pitfall: “sync over sync” that blocks forever**
- Console reads are synchronous and blocking. That’s usually fine for console apps.
- If you need to integrate with cancellation, structure your program so the console read is *not* on a critical path, or treat cancellation as “stop after current input”.
  - Avoid spinning threads to “cancel” console input; it’s brittle and platform-dependent.

**Pitfall: encoding surprises**
- If you print non-ASCII characters, consider setting UTF-8 explicitly:

```csharp
using System.Text;
Console.OutputEncoding = Encoding.UTF8;
```

Good to know:
- Changing encoding affects terminals and redirected output. Do it deliberately and early.

**Pitfall: mixing prompts + output in pipelines**
- In pipelines, prompts make output hard to parse. Consider:
  - writing prompts to `Console.Error`
  - or disabling prompts when input is redirected (`Console.IsInputRedirected`)

**Pitfall: untestable console code**
- Keep console I/O at the boundary:
  - Core logic in pure functions/classes
  - A thin “adapter” that reads from `TextReader` and writes to `TextWriter`
