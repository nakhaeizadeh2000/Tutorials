## 2.2. Types of inheritance in C#: single inheritance + interfaces + “multiple inheritance of behavior” patterns

1. **Single inheritance for classes** (why C# forbids multiple base classes; diamond problem framing)
2. **Interfaces for multiple contracts** (including default interface members: when to use vs avoid)
3. **Modern alternatives** (composition, strategy, decorators, source generators, static abstract interface members where they fit)

---

### 1) **Single inheritance for classes** (why C# forbids multiple base classes; diamond problem framing)
**What C# allows**
- A class can inherit from **exactly one** base class.
- This keeps object layout and method dispatch rules simpler and prevents classic ambiguity problems.

**Why multiple base classes are forbidden (the “diamond” problem)**
- If `D : B, C` and both `B` and `C` inherit from `A`, which `A` implementation/state does `D` contain?
- Resolving that requires either:
  - complex runtime rules (like C++’s virtual inheritance), or
  - explicit disambiguation rules that become a permanent source of bugs.

**Good to know**
- You still get “multiple inheritance of *contracts*” via interfaces.
- You can simulate “multiple inheritance of *behavior*” via composition/delegation (see item 3).

---

### 2) **Interfaces for multiple contracts** (including default interface members: when to use vs avoid)
**What interfaces give you**
- Multiple independent **capabilities** / **contracts**.
- A clean way to decouple callers from concrete implementations.

```csharp
public interface IClock
{
    DateTimeOffset UtcNow { get; }
}

public sealed class SystemClock : IClock
{
    public DateTimeOffset UtcNow => DateTimeOffset.UtcNow;
}
```

**Default interface members (DIM)**
- Interfaces can provide default implementations.
- They are useful mainly when you **own the interface** and need to evolve it without breaking all implementers.

**Mentor guidance (DIM): use deliberately**
- Prefer DIM for **versioning** of libraries/frameworks (adding a new member with a sensible default).
- Avoid DIM as your “normal” code-sharing tool inside an app; it can:
  - hide behavior in surprising places,
  - create “which default runs?” confusion with explicit implementations,
  - complicate testing and reasoning.

**Performance note**
- Interface calls are also dynamically dispatched. The JIT can sometimes devirtualize/in-line, but you shouldn’t rely on it.
- For the canonical performance treatment, see:
  - `README/CSharp/03 CSharp Basic Object Oriented Programming/sections/3. Important points about objects/3.5. Virtual dispatch interface calls and performance basics.md`

### 3) **Modern alternatives** (composition, strategy, decorators, source generators, static abstract interface members where they fit)
**Composition + strategy (common, simple, testable)**

```csharp
public interface ICompression
{
    ReadOnlyMemory<byte> Compress(ReadOnlySpan<byte> data);
}

public sealed class Compressor(ICompression compression)
{
    public ReadOnlyMemory<byte> Run(ReadOnlySpan<byte> data) => compression.Compress(data);
}
```

**Decorator (add behavior without inheritance trees)**
- Good for logging, caching, validation, retries (especially around I/O boundaries).

**Source generators (modern replacement for reflection-heavy “magic”)**
- Use to generate repetitive glue code (mapping/serialization) instead of inheritance-based frameworks where possible.

**Static abstract interface members (generic math / shape constraints)**
- Useful when you want polymorphism resolved at **compile-time** (via generics) rather than runtime virtual dispatch.
- This is not a drop-in replacement for inheritance; it’s for algorithms over “capable types”.

**Mentor rule**
- If you’re tempted to create “BaseX, DerivedX1, DerivedX2, …” just to vary one behavior, reach for **strategy + composition** first.
