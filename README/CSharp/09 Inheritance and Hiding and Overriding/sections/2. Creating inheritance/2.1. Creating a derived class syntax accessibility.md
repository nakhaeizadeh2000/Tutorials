## 2.1. Creating a derived class: `:` syntax, accessibility, and member visibility

1. **Basic mechanics** (single class inheritance, multiple interface implementation)
2. **Access rules** (`public/protected/internal/private`; `protected internal` vs `private protected`)
3. **What you inherit** (instance members) vs what you don’t (constructors; private members are not accessible)

---

### 1) **Basic mechanics** (single class inheritance, multiple interface implementation)
**Syntax**
- A type can inherit from **one** base class and implement **many** interfaces.

```csharp
public abstract class Base { }

public interface IReadable { string Read(); }
public interface IWritable { void Write(string value); }

public sealed class Derived : Base, IReadable, IWritable
{
    public string Read() => "ok";
    public void Write(string value) { /* ... */ }
}
```

**Good to know**
- If you omit a base class, your class implicitly derives from `object`.
- Structs do not inherit from other structs/classes (they implicitly derive from `System.ValueType`), but they can implement interfaces.
- Records/record structs follow the same inheritance rules as their underlying kind (`class` vs `struct`).

---

### 2) **Access rules** (`public/protected/internal/private`; `protected internal` vs `private protected`)
**The two often-confused combos**
- `protected internal`: accessible from **anywhere in the same assembly** *OR* from **derived types in any assembly**.
- `private protected`: accessible **only** from derived types **in the same assembly**.

```csharp
public class Base
{
    protected internal int A;  // assembly OR derived-anywhere
    private protected int B;   // derived-in-same-assembly only
}
```

**What derived code can access**
- `public`: everywhere
- `protected`: only in derived types (including across assemblies)
- `internal`: only within the same assembly
- `private`: only within the declaring type

**Mentor rule**
- Avoid `protected` members unless you are intentionally designing an inheritance contract. `protected` expands the “surface area you must keep compatible forever”.

---

### 3) **What you inherit** (instance members) vs what you don’t (constructors; private members are not accessible)
**Inherited**
- Instance fields, properties, methods, events, indexers that are not `private`.
- Virtual members participate in override chains.

**Not inherited (common misconceptions)**
- **Constructors are not inherited**. Derived constructors can only *call* base constructors via `base(...)`.
- **Private members exist** in the object, but are not accessible in derived code. You must expose behavior via `protected` or `protected` methods/properties if you want derived types to interact with base state.
- **Static members** are not “inherited” in the polymorphic sense; they are accessed through the declaring type and do not dispatch virtually.
