## 6.1. Virtual members: designing extension points safely

1. **When to make something virtual** (stable contract, expected customization, documented invariants)
2. **Non-virtual by default** (keep base APIs small; seal types/members unless you explicitly need overrides)
3. **Correctness** (document required `base` calls; guard invariants; avoid calling virtuals from constructors)

---

### 1) **When to make something virtual** (stable contract, expected customization, documented invariants)
**Definition**
- A **virtual member** is an explicit **extension point**: derived types can change behavior via `override`.
- A virtual is a **contract** between the base author and derived authors: what must always remain true (invariants), what may change, and what callers can rely on.

**When it’s the right tool**
- You’re writing a **framework-like base type** (even internally) where customization is expected and supported.
- You need a **template method**: base orchestrates the algorithm, derived provides customizable steps.
- You can commit to **versioning compatibility**: overrides written today should keep working after base evolves.

**A good shape: “non-virtual public API + protected virtual hooks”**

```csharp
using System;

public abstract class BatchProcessor
{
    public void Run(ReadOnlySpan<int> items)
    {
        if (items.IsEmpty) return;

        OnBeforeRun(items);
        ProcessCore(items);
        OnAfterRun(items);
    }

    protected virtual void OnBeforeRun(ReadOnlySpan<int> items) { }
    protected abstract void ProcessCore(ReadOnlySpan<int> items);
    protected virtual void OnAfterRun(ReadOnlySpan<int> items) { }
}

public sealed class SumProcessor : BatchProcessor
{
    public int Sum { get; private set; }

    protected override void ProcessCore(ReadOnlySpan<int> items)
    {
        var sum = 0;
        foreach (var x in items) sum += x;
        Sum = sum;
    }
}
```

**Mentor note**
- Keep the public entrypoint (`Run`) **non-virtual** so callers get a stable behavior boundary.
- Make override points **narrow** and **well-named** (hooks, not “override anything”).

---

### 2) **Non-virtual by default** (keep base APIs small; seal types/members unless you explicitly need overrides)
**Default rule**
- If you don’t *need* overriding, don’t allow it.

**Why**
- Every virtual member increases:
  - testing matrix (base + every derived override),
  - debugging complexity (behavior depends on runtime type),
  - versioning risk (base changes can break derived overrides),
  - potential performance sensitivity in hot loops (rare, but real).

**Practical approach**
- Prefer `sealed` types in application code.
- Prefer **interfaces** for seams between components, and **composition** for behavior variation.
- Use virtual only where it models a genuine “family” of types with shared invariants.

### 3) **Correctness** (document required `base` calls; guard invariants; avoid calling virtuals from constructors)
**Document base-call requirements**
- If a derived override must call `base.SomeMethod()`, treat that as part of the contract and make it obvious:
  - in docs/tests,
  - by structuring your base so *skipping* `base` is hard or unnecessary.

**Guard invariants in the base**
- Base class should protect itself:
  - validate inputs at the public boundary,
  - keep state transitions consistent,
  - avoid letting derived bypass invariants by overriding the wrong method.

**Never call virtual members during construction**
- A virtual call from a base constructor can execute a derived override before derived fields are initialized.
- This is a high-frequency production bug pattern.
