## 6.2. Overriding rules and modifiers: `override`, `abstract`, `sealed override`, and `new` interactions

1. **Legal combinations** (`virtual`→`override`; `abstract`→must override; `sealed override` stops further overrides)
2. **Hiding vs overriding interactions** (what `new` does to a virtual chain; why it’s almost always wrong)
3. **Versioning mindset** (adding virtuals, changing virtual behavior, and binary compatibility concerns in libraries)

---

### 1) **Legal combinations** (`virtual`→`override`; `abstract`→must override; `sealed override` stops further overrides)
**The overriding chain rule**
- A member can only be overridden if the base declares it `virtual` or `abstract`.
- A derived override must use `override` (not `new`) to stay in the virtual chain.

**Common legal shapes**
- `virtual` → `override`
- `abstract` → `override` (must override in the first non-abstract derived type)
- `override` → `sealed override` (override here, but prevent further overrides)

**Runnable example: abstract + override + sealed override**

```csharp
using System;

public abstract class Base
{
    public abstract string Format(int value);
}

public abstract class Mid : Base
{
    // Provide a default implementation for many derived types.
    public override string Format(int value) => value.ToString("N0");
}

public sealed class Final : Mid
{
    // Freeze behavior (no one can override beyond this point).
    public sealed override string Format(int value) => $"[{base.Format(value)}]";
}

public static class Demo
{
    public static void Main()
    {
        Base b = new Final();
        Console.WriteLine(b.Format(12345)); // [12,345]
    }
}
```

**Good to know**
- `sealed override` is a strong signal: “this override establishes final invariants/behavior”.
- You can’t override a `non-virtual` member, even if you match its signature exactly; that’s hiding, not overriding.

### 2) **Hiding vs overriding interactions** (what `new` does to a virtual chain; why it’s almost always wrong)
**What happens if you “hide” a virtual member**
- You create a *new* member that is not in the override chain.
- Calls through a base-typed reference still participate in virtual dispatch, but will never see your hidden member.

**Runnable example: hiding a virtual is a semantic landmine**

```csharp
using System;

public class Base
{
    public virtual string Name() => "Base";
}

public sealed class Derived : Base
{
    public new string Name() => "Derived (hidden)";
}

public static class Demo
{
    public static void Main()
    {
        Derived d = new();
        Base b = d;

        Console.WriteLine(d.Name()); // Derived (hidden)
        Console.WriteLine(b.Name()); // Base   (virtual dispatch chain ignores hidden member)
    }
}
```

**Mentor rule**
- If the base is `virtual` and you want polymorphism, use `override`.
- If you think you need `new` on a virtual member, you almost certainly want a different API shape (rename, overload, or composition).

### 3) **Versioning mindset** (adding virtuals, changing virtual behavior, and binary compatibility concerns in libraries)
**Treat virtuals as long-term contracts**
- Making a member virtual means: “third parties may override this forever”.
- Once shipped, you must assume overrides exist that you never anticipated.

**Versioning pitfalls**
- Adding a new virtual that your base calls can change behavior in derived types (even if they didn’t override it, they might hide it, or their overrides might assume a different call order).
- Changing validation/order in a base virtual can break derived types (fragile base class problem).
- Adding `abstract` members is breaking: all derived types must implement.

**Mentor guidance for public libraries**
- Prefer **non-virtual public API** + explicit extension points (interfaces, protected hooks with strict rules).
- Consider making the type `sealed` and exposing extensibility via composition (interfaces/DI) rather than inheritance.

**Performance note**
- Versioning is usually more expensive than dispatch. Optimize for maintainability first; measure performance in hot paths and redesign with data/generics when needed.
