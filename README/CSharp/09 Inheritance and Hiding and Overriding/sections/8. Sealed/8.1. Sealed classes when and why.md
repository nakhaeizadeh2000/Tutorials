## 8.1. Sealed classes: when and why to stop inheritance

1. **Design reasons** (prevent invalid extension, protect invariants, simplify reasoning/testing)
2. **Performance angle** (enables stronger devirtualization; reduces dispatch uncertainty in some cases)
3. **API stability** (sealed public types reduce “you broke my derived type” versioning pain)

---

### 1) **Design reasons** (prevent invalid extension, protect invariants, simplify reasoning/testing)
**Definition**
- `sealed` on a class means: **no other class can derive from it**.
- This is first and foremost a **design constraint**: “this type is not an extensibility point”.

**Why mentors like sealing**
- **Protect invariants**: derived types can’t bypass assumptions by overriding virtual members or by adding state that changes semantics.
- **Simplify reasoning**: behavior is fully contained in one type; fewer “unknown overrides”.
- **Improve testability** (counterintuitive but real): you test behavior directly. For mocking, prefer interfaces/abstractions at boundaries rather than inheriting from concrete types.

**Example: sealing a type that owns an invariant**

```csharp
public sealed class Money
{
    public Money(decimal amount)
    {
        if (amount < 0) throw new ArgumentOutOfRangeException(nameof(amount));
        Amount = amount;
    }

    public decimal Amount { get; }
}
```

If `Money` were inheritable, a derived type could introduce “negative money” semantics or override behaviors you relied on elsewhere (e.g., formatting, arithmetic helpers).

**Good to know**
- Sealing is especially valuable for “value-like domain concepts” and “infrastructure components” where override points are not part of the contract.

---

### 2) **Performance angle** (enables stronger devirtualization; reduces dispatch uncertainty in some cases)
**What sealing can enable**
- If a type is sealed, the runtime/JIT has more certainty that a virtual call target will not change, which can sometimes help **devirtualization** and inlining.

**Important reality**
- Sealing is not a magic speed button. It’s a design decision with potential performance side benefits.
- The canonical deep performance discussion of virtual/interface dispatch is already covered elsewhere:
  - See [3.5. Virtual dispatch interface calls and performance basics](<../../../03 CSharp Basic Object Oriented Programming/sections/3. Important points about objects/3.5. Virtual dispatch interface calls and performance basics.md>).

**Performance note**
- If performance is truly critical, you usually win more by removing allocations, improving algorithms, using `Span<T>` for parsing, avoiding contention, or moving polymorphism out of inner loops.

---

### 3) **API stability** (sealed public types reduce “you broke my derived type” versioning pain)
**Why this matters in libraries**
- If your public type is inheritable, consumers can subclass it. Any change you make can break them in ways you cannot predict or test.

Common breaking changes for derived consumers:
- Adding a new virtual method and calling it from existing code (changes override expectations).
- Changing the order/timing of virtual calls.
- Tightening validation in base methods.
- Changing protected members.

**Mentor rule**
- Publicly inheritable types are **framework commitments**. If you’re not willing to support arbitrary derived types, seal the type and provide extensibility via:
  - interfaces,
  - composition (strategy/decorator),
  - explicit callbacks/delegates,
  - source-generation hooks where appropriate.
