## 8.2. `sealed override`: stop further overrides while still inheriting from a base

1. **When it’s useful** (finalizing behavior at a certain level in a hierarchy)
2. **Correctness** (lock down invariants; avoid extension points you can’t support)
3. **Performance reality** (may help devirtualization; measure before you claim wins)

---

### 1) **When it’s useful** (finalizing behavior at a certain level in a hierarchy)
`sealed override` is for the “middle of a hierarchy” case:
- You inherit from a base type that defines a virtual member.
- You override it (to provide your implementation).
- You want to *stop* further derived classes from overriding it again.

```csharp
public abstract class Base
{
    public virtual string Normalize(string input) => input;
}

public class AppBase : Base
{
    // Derived types can still inherit AppBase,
    // but they can't change normalization anymore.
    public sealed override string Normalize(string input) => input.Trim();
}
```

Typical real-world uses:
- **Framework adaptation layers**: you inherit from a framework base type, override a hook, then seal it in your app layer so your own codebase doesn’t create accidental override chains.
- **Finalizing invariants**: you need a consistent behavior from this level down.

---

### 2) **Correctness** (lock down invariants; avoid extension points you can’t support)
Mentor framing: every virtual member is an “extension point contract”. If you can’t support arbitrary overrides without risking correctness, don’t expose the extension point.

Use `sealed override` when:
- You have established an invariant (validation, state transitions, logging/auditing) that must always run.
- You discovered that allowing further overrides creates security/correctness risks.

Avoid relying on “derived developers will behave”.
- Make it **impossible** to override behavior you must guarantee.

---

### 3) **Performance reality** (may help devirtualization; measure before you claim wins)
Sealing an override can make it easier for the JIT to reason about call targets (and sometimes inline), but:
- The benefit is workload-dependent.
- The biggest wins usually come from reducing allocations and avoiding polymorphism in inner loops.
