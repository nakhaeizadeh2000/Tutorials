## 4.1. Construction order: field initializers + base ctor + derived ctor (and why virtual calls are dangerous)

1. **Actual order** (defaults → base field initializers → base ctor → derived field initializers → derived ctor)
2. **The classic hazard** (virtual dispatch during construction + partially initialized derived state)
3. **Safe patterns** (non-virtual initialization, factories, composition; keep constructors cheap and deterministic)

---

### 1) **Actual order** (defaults → base field initializers → base ctor → derived field initializers → derived ctor)
This topic is already covered in depth (including subtle ordering rules and pitfalls) in the `Constructors` domain.

- See `README/CSharp/07 Constructors/sections/1. Constructor fundamentals/1.3. Execution order fields base derived.md` for the canonical deep explanation.

Inheritance-specific short summary (classes):
- The runtime allocates and **zero-initializes** the object.
- **Base** instance field initializers run (in source order).
- **Base** constructor body runs.
- **Derived** instance field initializers run (in source order).
- **Derived** constructor body runs.

**Good to know**
- `base(...)` (constructor initializer) runs **before** the derived constructor body.
- If your base ctor depends on derived state, your design is already in the danger zone.

---

### 2) **The classic hazard** (virtual dispatch during construction + partially initialized derived state)
**Why it happens**
- During base construction, the runtime still knows the **runtime type** is the derived type, so virtual dispatch can route to the derived override **before** derived fields are initialized.

**Minimal runnable example (why “don’t call virtuals in ctors” exists)**

```csharp
using System;

public abstract class Base
{
    protected Base()
    {
        // BAD: virtual call during construction.
        OnInit();
    }

    protected virtual void OnInit() { }
}

public sealed class Derived : Base
{
    private readonly string _name = "ready";

    protected override void OnInit()
    {
        // _name can still be null here in real scenarios depending on init order.
        Console.WriteLine(_name.Length);
    }
}

public static class Program
{
    public static void Main()
    {
        _ = new Derived();
    }
}
```

**Mentor notes**
- This bug class is *rarely* fixed by “clever null checks”; it’s fixed by **changing the design boundary**.
- If you truly need polymorphic initialization, do it **after** construction with an explicit method, and keep it non-virtual unless you’re building a framework.

---

### 3) **Safe patterns** (non-virtual initialization, factories, composition; keep constructors cheap and deterministic)
**Patterns that work**
- **Non-virtual initialization**: keep ctor logic concrete and deterministic.
- **Factory methods**: create the object, then run any post-construction steps explicitly.
- **Composition**: inject collaborators rather than relying on base/derived override chains to “wire things up”.

**Example: explicit post-construction init (framework-style only)**

```csharp
public abstract class Base
{
    // Non-virtual construction; explicit init step.
    public void Initialize() => InitializeCore();

    protected abstract void InitializeCore();
}
```

**Performance note**
- Keep constructors cheap: expensive work in constructors turns allocations into latency spikes and makes performance unpredictable (especially with large object graphs).
