## 7.1. The key difference: dispatch depends on static type vs runtime type

1. **Hiding** (compile-time selection) vs **overriding** (runtime selection)
2. **Correctness consequences** (polymorphism expectations; LSP thinking)
3. **Mentor heuristics** (use overriding for polymorphism; avoid hiding unless forced by legacy constraints)

---

### 1) **Hiding vs overriding: compile-time selection vs runtime selection**
If you only memorize one sentence, memorize this:

- **Hiding (`new`)**: which member is called depends on the **static type** at the call site.
- **Overriding (`virtual`/`override`)**: which implementation runs depends on the **runtime type** of the object.

**Runnable comparison**

```csharp
using System;

public class Base
{
    public void H() => Console.WriteLine("Base.H (non-virtual)");
    public virtual void O() => Console.WriteLine("Base.O (virtual)");
}

public sealed class Derived : Base
{
    public new void H() => Console.WriteLine("Derived.H (hidden)");
    public override void O() => Console.WriteLine("Derived.O (override)");
}

public static class Demo
{
    public static void Main()
    {
        Derived d = new();
        Base b = d;

        d.H(); // Derived.H
        b.H(); // Base.H  (static type is Base)

        d.O(); // Derived.O
        b.O(); // Derived.O (runtime type is Derived)
    }
}
```

**Good to know**
- Hiding and overriding can coexist in the same type, which is one reason code reviews should treat `new` as “high scrutiny”.

---

### 2) **Correctness consequences** (polymorphism expectations; LSP thinking)
**Why hiding is dangerous**
- Callers using a base-typed reference expect **polymorphic behavior** to follow the runtime object.
- Hiding violates that expectation for that member, which can create bugs that appear only when a value flows through a base-typed API.

**LSP framing (mentor-friendly)**
- If `Derived` is a `Base`, a caller should not need to “know” it’s derived to get correct behavior.
- Overriding is how you *safely* refine behavior while preserving the base contract.
- Hiding is how you create **two unrelated members with the same name**, selected by static type—this is almost always the opposite of substitutability.

**Performance note**
- Avoid “semantic optimization”: using hiding because you think it avoids virtual dispatch is almost always wrong.
- If virtual dispatch is truly hot, redesign (data layout/generics/specialization). Don’t break correctness.

---

### 3) **Mentor heuristics** (use overriding for polymorphism; avoid hiding unless forced by legacy constraints)
Use **override** when:
- You want runtime polymorphism.
- You’re implementing a documented extension point.
- You want derived behavior to apply through base references.

Use **new (hiding)** only when:
- You are forced by legacy/interop constraints and have no ability to change the base contract.
- You can clearly document that base-typed calls will intentionally use the base member.

Prefer **neither** (rename / overload / composition) when:
- You’re just trying to reuse implementation.
- You want a type-specific convenience API (prefer overloads or extension methods).
