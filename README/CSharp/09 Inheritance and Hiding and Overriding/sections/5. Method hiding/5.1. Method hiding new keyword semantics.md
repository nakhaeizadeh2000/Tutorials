## 5.1. What method hiding is: “shadowing” a member in the derived type

1. **Meaning of `new`** (chooses which member is used based on compile-time static type, not runtime type)
2. **What happens without `new`** (compiler warnings; still hiding, but accidentally)
3. **When hiding is acceptable** (rare: interop/versioning constraints; avoid for normal domain modeling)

---

### 1) **Meaning of `new`** (chooses which member is used based on compile-time static type, not runtime type)
**Definition**
- **Method hiding** (a.k.a. **shadowing**) happens when a derived type declares a member with the same name/signature as a base member, but **does not participate in the virtual override chain**.
- In C#, you mark intentional hiding with the `new` modifier:
  - It does **not** mean “allocate a new object”. It means “introduce a *new member* that hides the inherited one”.

**The key semantic**
- The member that gets called is chosen based on the **static type of the reference** at the call site.
- That’s the opposite of overriding, where the implementation is chosen based on the **runtime type**.

**Runnable example: hiding is compile-time selection**

```csharp
using System;

public class Base
{
    public void M() => Console.WriteLine("Base.M");
}

public sealed class Derived : Base
{
    public new void M() => Console.WriteLine("Derived.M (hidden)");
}

public static class Demo
{
    public static void Main()
    {
        Derived d = new();
        Base b = d;

        d.M(); // Derived.M (hidden)
        b.M(); // Base.M  (static type is Base)
    }
}
```

**Mentor takeaway**
- Hiding breaks substitutability expectations: a `Derived` used as a `Base` behaves like a `Base` for that member.

**Performance note**
- Hiding is not a performance trick. It’s a semantic choice. If you need performance in hot paths, solve it with algorithm/data layout/generics—not with dispatch surprises.

---

### 2) **What happens without `new`** (compiler warnings; still hiding, but accidentally)
If you declare a member with the same signature as a base member without `new`, C# still hides it, but the compiler warns you because it’s usually accidental:

```csharp
public class Base { public void M() { } }

public class Derived : Base
{
    // Warning: hides inherited member. Use the new keyword if hiding was intended.
    public void M() { }
}
```

**Mentor rule**
- Treat that warning as a “design alarm”. Decide explicitly:
  - Do you mean **override**? (Then the base must be `virtual` and you must use `override`.)
  - Do you mean **hide**? (Then add `new` and accept the semantic cost.)
  - Or do you mean **neither**? (Rename the member; often best.)

---

### 3) **When hiding is acceptable** (rare: interop/versioning constraints; avoid for normal domain modeling)
Hiding can be justified in a few narrow cases:

- **Interop / legacy APIs**: you can’t change the base type (BCL / third-party) and need a differently-shaped member for compatibility.
- **Versioning constraints**: you must keep a base member for binary compatibility but want a better API on the derived type (still risky; prefer extension methods or composition).
- **Intentional “type-specific API”**: a derived type adds a strongly-typed convenience method while keeping the base for generic use. Even here, prefer **overloads** (different signature) rather than hiding same-signature members.

**What to prefer instead**
- **Override** when the goal is polymorphism.
- **Overload** (different signature) when the goal is convenience.
- **Composition** when you’re just trying to reuse implementation.
