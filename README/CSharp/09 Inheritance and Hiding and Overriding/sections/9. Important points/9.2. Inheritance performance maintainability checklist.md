## 9.2. Performance and maintainability checklist: dispatch, allocations, and API shape

1. **Prefer non-virtual by default** (virtual only when it’s an explicit extension point)
2. **Avoid polymorphism in hot loops** (consider generics, data-oriented layouts, or function pointers where appropriate)
3. **Keep hierarchies shallow** (deep hierarchies increase mental load; increase coupling; complicate initialization and testing)

---

### 1) **Prefer non-virtual by default** (virtual only when it’s an explicit extension point)
**Mentor rule**
- A `virtual` member is an **extensibility promise**. Once it’s public/protected, you’re effectively committing to support overrides (and the implied behavior contract) forever.
- Make members virtual only when you can clearly answer:
  - “What invariants must overrides preserve?”
  - “Must overrides call `base`?”
  - “What can I change later without breaking derived types?”

**Good to know**
- Prefer a small set of well-named virtual hooks over many “maybe overridable” members.
- If you control the entire hierarchy (internal types), inheritance is safer; public inheritance is framework-author territory.

---

### 2) **Avoid polymorphism in hot loops** (consider generics, data-oriented layouts, or function pointers where appropriate)
**Performance framing**
- Polymorphism costs usually come from **missed inlining** and **branch misprediction**, not from “virtual is slow”.
- If a polymorphic call is on the inner loop of a tight computation, consider refactoring:
  - **Batch work by concrete type** (reduce virtual calls),
  - **Use generics** to shift polymorphism to compile time,
  - **Use data-oriented design** (process contiguous arrays of data rather than object graphs).

**See also**
- The deep performance explanation for virtual/interface calls lives in:
  - [3.5. Virtual dispatch interface calls and performance basics](<../../../03 CSharp Basic Object Oriented Programming/sections/3. Important points about objects/3.5. Virtual dispatch interface calls and performance basics.md>)

**Good to know**
- Don’t use method hiding (`new`) as a “performance hack”. It changes semantics and makes code harder to reason about.

---

### 3) **Keep hierarchies shallow** (deep hierarchies increase mental load; increase coupling; complicate initialization and testing)
**Maintainability costs of deep inheritance**
- Hidden behavior via overrides makes local reasoning difficult (“what really runs?”).
- Refactoring becomes risky: base changes can break derived types.
- Testing often requires complicated setups due to implicit base behavior.

**Mentor heuristics**
- If you need more than ~2 levels, ask whether you’re modeling:
  - a **taxonomy** (which inheritance is bad at), or
  - a **pipeline of behaviors** (composition/decorators usually win).

**Good to know**
- Shallow inheritance + composition tends to produce clearer DI graphs and fewer “spooky action at a distance” bugs.
