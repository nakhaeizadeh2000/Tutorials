## 9.1. Correctness checklist: invariants, construction, and substitutability

1. **LSP framing** (derived must be usable wherever base is expected; don’t strengthen preconditions or weaken postconditions)
2. **Initialization rules** (base constructed first; no virtual calls during construction; never leak partially constructed `this`)
3. **Override contract discipline** (document expectations; keep side effects predictable; avoid surprising exceptions)

---

### 1) **LSP framing** (derived must be usable wherever base is expected; don’t strengthen preconditions or weaken postconditions)
**What LSP means in practice (mentor version)**
- If a method accepts `Base`, it should not have to “know” which derived type it got to behave correctly.
- The derived type must preserve the **behavioral contract** of the base:
  - **Don’t strengthen preconditions**: if base accepts all strings, derived can’t reject half of them “just because”.
  - **Don’t weaken postconditions**: if base guarantees a non-null return, derived can’t sometimes return null.
  - **Don’t change invariants**: if base says `Count` is always non-negative, derived can’t temporarily go negative.

**Good to know**
- LSP is about *behavior*, not syntax. You can `override` correctly and still violate LSP.

**Example: strengthening preconditions (bug)**

```csharp
public class BaseParser
{
    public virtual int Parse(string input)
    {
        ArgumentNullException.ThrowIfNull(input);
        return int.Parse(input);
    }
}

public sealed class DerivedParser : BaseParser
{
    public override int Parse(string input)
    {
        // BAD: base accepted any non-null string; derived now rejects whitespace-only,
        // which can break callers that were valid against BaseParser's contract.
        if (string.IsNullOrWhiteSpace(input))
            throw new ArgumentException("No whitespace.", nameof(input));

        return base.Parse(input);
    }
}
```

**Mentor rule**
- If you need “stricter” behavior, expose it as a **new API** (a different method) or use composition/configuration.

### 2) **Initialization rules** (base constructed first; no virtual calls during construction; never leak partially constructed `this`)
This domain keeps the inheritance-focused checklist here and points to the canonical deep treatment for ordering details.

- See [1.3. Execution order fields base derived](<../../../07 Constructors/sections/1. Constructor fundamentals/1.3. Execution order fields base derived.md>) for full construction ordering and the “no virtual calls in constructors” explanation with examples.

**Quick checklist**
- Base constructor runs before derived field initializers and derived ctor body.
- Never call virtual members from constructors (directly or indirectly).
- Don’t publish `this` during construction (events, callbacks, `Task.Run`, storing in static/global collections).

**Performance note**
- Construction bugs often turn into “rare” production crashes; the cost is not CPU—it’s incident time. Be strict.

---

### 3) **Override contract discipline** (document expectations; keep side effects predictable; avoid surprising exceptions)
**What “override contract” means**
- When a base member is virtual, it’s effectively a mini-framework hook. You must define:
  - whether derived overrides **must call `base`**
  - which invariants must be preserved
  - which exceptions are allowed/expected
  - thread-safety expectations (re-entrancy, concurrency)

**Common mistakes**
- Making a virtual method “do a lot” without documenting whether overrides can skip base logic.
- Throwing new exceptions in overrides that callers were not prepared to handle.
- Changing observable side effects (logging, events, ordering) in ways that break caller assumptions.

**Mentor pattern**
- Prefer **non-virtual public** methods that enforce invariants, and **protected virtual** hooks for customization (template method).
