## 3.2. `base(...)` in constructors: selecting base constructor overloads

1. **Why it exists** (base must be constructed before derived)
2. **Overload selection** (which base ctor is called, and what happens if you don’t specify one)
3. **API design** (keep base ctors minimal; prefer factories when initialization is complex or async)

---

### 1) **Why it exists** (base must be constructed before derived)
Every instance of a derived class *contains* the base portion of the object. That means the runtime must construct the base part first.

In C#:
- A derived constructor **always** calls a base constructor, either explicitly via `: base(...)` or implicitly.
- If you don’t specify `base(...)`, the compiler inserts a call to the **parameterless** base constructor (if it exists).

**Good to know**
- `base(...)` is not a “method call”; it’s part of the constructor initializer syntax and runs **before** the derived constructor body.

---

### 2) **Overload selection** (which base ctor is called, and what happens if you don’t specify one)
**Rule**
- `: base(args)` selects the base constructor overload using normal overload resolution rules.

**Example: choosing the correct base constructor**

```csharp
using System;

public abstract class Base
{
    protected Base(string name)
    {
        Name = string.IsNullOrWhiteSpace(name) ? throw new ArgumentException("Name required.") : name;
    }

    public string Name { get; }
}

public sealed class Derived : Base
{
    public Derived(string name, int version) : base(name)
    {
        Version = version;
    }

    public int Version { get; }
}
```

**What happens if you don’t specify one**
- If `Base` has a parameterless constructor, `Derived()` implicitly calls `Base()`.
- If `Base` does **not** have a parameterless constructor, `Derived()` must explicitly call `base(...)`, otherwise you get a compile error.

**Mentor pitfall**
- Don’t “fix” the compile error by adding a meaningless parameterless base constructor just to satisfy the compiler. That often weakens invariants. Prefer making the required base state explicit via constructor parameters.

---

### 3) **API design** (keep base ctors minimal; prefer factories when initialization is complex or async)
**Constructor responsibilities**
- Establish **invariants** cheaply and deterministically.
- Do not do I/O, blocking, or background work.

**If initialization is complex**
- Prefer a **factory method** (static `Create(...)`) that can:
  - validate more thoroughly,
  - return a `Result`-style outcome if exceptions are undesirable,
  - be `async` (constructors cannot).
