## 1.2. Runtime dispatch model: non-virtual, virtual/override, interface calls (high level)

1. **Compile-time binding vs runtime dispatch** (overload resolution vs virtual dispatch)
2. **Virtual dispatch + performance reality** (often “fast enough”; can matter in hot loops; JIT can devirtualize sometimes)
3. **Design guidance** (make extension points explicit; keep inheritance shallow; prefer sealed where appropriate)

---

### 1) **Compile-time binding vs runtime dispatch** (overload resolution vs virtual dispatch)
**Two different “choices” happen when you call a method**

- **Overload resolution (compile-time)**: the compiler chooses *which signature* you meant, based on the **static type** at the call site.
- **Virtual dispatch (runtime)**: if the chosen member is **virtual** (or an **interface** call), the runtime chooses *which implementation* runs, based on the **runtime type** of the object.

**Rough mental model**
- “Which method name/signature?” → **compile-time**
- “Which override implementation?” → **runtime** (only for virtual/interface)

**Example: overload resolution vs virtual dispatch**

```csharp
using System;

public class Base
{
    public void M(int x) => Console.WriteLine("Base.M(int)");         // non-virtual
    public virtual void V(object x) => Console.WriteLine("Base.V");   // virtual
}

public sealed class Derived : Base
{
    // Overload (not override)
    public void M(long x) => Console.WriteLine("Derived.M(long)");

    public override void V(object x) => Console.WriteLine("Derived.V");
}

public static class Demo
{
    public static void Main()
    {
        Base b = new Derived();

        b.M(1);      // compile-time picks Base.M(int) (static type is Base) -> prints Base.M(int)
        b.V("x");    // compile-time picks Base.V(object), runtime dispatch picks Derived override -> prints Derived.V
    }
}
```

**Good to know**
- `new` (hiding) changes *which member is visible* at compile time; it does **not** participate in virtual dispatch. (Deep treatment is in the `Method hiding` sections.)

### 2) **Virtual dispatch + performance reality** (often “fast enough”; can matter in hot loops; JIT can devirtualize sometimes)
**What virtual dispatch costs**
- A virtual/interface call adds an indirection compared to a direct call.
- That indirection can prevent **inlining**, which is often the bigger performance impact (tiny methods called in tight loops).

**Mentor framing**
- In typical business applications, the difference is usually drowned out by:
  - allocations,
  - I/O,
  - locks/async scheduling,
  - algorithmic complexity.
- It matters when you execute the call **millions of times** per second and the callee is tiny.

**Devirtualization (what the JIT can sometimes do)**
- The JIT can sometimes prove the concrete type and treat a virtual call like a direct call (enabling inlining), especially when:
  - the type is **sealed**,
  - the call site sees an exact type,
  - profile-guided optimization (PGO) helps.

This domain doesn’t duplicate the full performance deep dive.
- See `README/CSharp/03 CSharp Basic Object Oriented Programming/sections/3. Important points about objects/3.5. Virtual dispatch interface calls and performance basics.md` for the canonical performance treatment.

**Performance note**
- Don’t “optimize” by replacing virtual dispatch with method hiding (`new`). Hiding changes semantics and breaks substitutability; it’s almost never a valid performance trade.

---

### 3) **Design guidance** (make extension points explicit; keep inheritance shallow; prefer sealed where appropriate)
**Rules that scale (and keep you out of trouble)**

- **Default to non-virtual**. Make a member virtual only when you are deliberately defining an override contract.
- **Prefer `sealed` types** unless you explicitly want inheritance as a supported scenario.
- **Prefer `sealed override`** when you inherit from a framework base type but want to stop further override chains in your own hierarchy.
- **Keep inheritance shallow**. If you need a 5-level tree, it’s usually a sign you want composition or a different model.

**Good to know**
- The more override points you expose, the more you must think like a framework author: invariants, call ordering, thread-safety, and versioning compatibility.
