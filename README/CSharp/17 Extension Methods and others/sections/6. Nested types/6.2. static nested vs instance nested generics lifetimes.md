## 6.2. `static` nested classes vs instance nested classes (generics and lifetimes)

1. **When `static` nested is the default** (pure helpers, builders, stateless factories)
2. **Instance nesting** (tight coupling to outer instance; mind unintentional lifetime extension)
3. **Generic outer types** (nested generic arity and readability; avoid “type soup”)

---

### 1. **When `static` nested is the default**

**Definition**:

- A **static nested type** (e.g., `public static class Outer.Helpers`) has **no implicit reference** to an outer instance. It’s just a type whose name is scoped under `Outer`.
- A **non-static nested class** (e.g., `public sealed class Outer.Inner`) created inside `Outer` is still a normal reference type, but it can have an **implicit association** with an outer instance if it needs one (see item 2).

**Mentor default**: prefer **static nested types** for implementation details, builders, and helpers that don’t need access to an outer instance.

**Why use static nested at all (instead of a top-level type)?**

- **Encapsulation of intent**: `Order.Parser` reads as “parser belonging to Order”.
- **Surface area control**: you can keep it `private`/`internal` to hide implementation details (similar goal to file-local types; see section [6.4](<./6.4. File-local types vs nested types.md>) for the comparison).
- **Name collision reduction**: avoids flooding the namespace with small helper type names.

**Example: static nested helper as an implementation detail**

```csharp
public sealed class Money
{
    public Money(decimal amount) => Amount = amount;
    public decimal Amount { get; }

    public override string ToString() => Formatting.Format(this);

    private static class Formatting
    {
        public static string Format(Money m) => $"{m.Amount:0.00}";
    }
}
```

**Trade-offs**:

- **Pros**: no hidden outer-instance capture; simpler lifetimes; clearer that the helper is stateless.
- **Cons**: can be overused to create “types inside types inside types” that hide important concepts; keep nesting shallow.

---

### 2. **Instance nesting**

**Definition**: A non-static nested class can conceptually be “part of” the outer type, but it becomes risky when the inner type holds a reference to the outer instance (directly or indirectly). That reference can unintentionally extend lifetimes.

**The lifetime trap**:

- If an `Inner` instance references an `Outer` instance and the inner escapes (stored in a cache, event handler, async closure, static field), the outer can become **GC-rooted longer than you expect**.

**Example: inner capturing outer (surprising lifetime)**

```csharp
public sealed class ConnectionPool
{
    private readonly string _connectionString;

    public ConnectionPool(string connectionString) => _connectionString = connectionString;

    public Connector CreateConnector() => new(this);

    public sealed class Connector
    {
        private readonly ConnectionPool _outer;
        public Connector(ConnectionPool outer) => _outer = outer;

        public string ConnectionString => _outer._connectionString;
    }
}
```

This is sometimes exactly what you want, but it should be **deliberate**.

**Mentor guidance**

- Prefer passing only the needed data into the nested type instead of the entire outer instance.
- If the nested type is logically independent, make it a **top-level** type or a **file-local** type (section [6.4](<./6.4. File-local types vs nested types.md>)).
- Be cautious with events: subscribing an inner instance to a long-lived event source can keep the outer alive.

**Performance note**

- The performance risk here is usually **memory retention** (longer object lifetimes → more work for the GC), not CPU cycles.

---

### 3. **Generic outer types**

**Definition**: Nested types inside a generic outer type are scoped under the generic type, which can quickly become unreadable if you stack multiple layers of generics.

**Example: readability cliff**

```csharp
public sealed class Cache<TKey, TValue>
{
    public sealed class Entry
    {
        public required TKey Key { get; init; }
        public required TValue Value { get; init; }
    }
}
```

This is fine. But in complex cases, you get signatures like:

- `Cache<TKey, TValue>.Entry`
- `Outer<T1>.Inner<T2>.Node<T3>`

**Trade-offs**:

- **Pros**: the nested type naturally “inherits” the outer’s generic parameters (which can be exactly what you want).
- **Cons**: type names become long; error messages get noisy; public APIs become harder to read.

**Mentor recommendations**

- If the nested type is public and important, consider making it **top-level** with a good name to keep APIs readable.
- Keep nested generic types **internal/private** unless they’re part of a carefully designed public surface.
