## 6.1. Nested types taxonomy (class, struct, record, interface, enum, delegate)

1. **Access rules** (private nested types for implementation hiding; `protected` nesting for advanced scenarios)
2. **Relationship to outer type** (how the outer instance context works for non-static nested classes)
3. **Idioms** (small cohesive helpers that aren’t part of the public surface)

---

### 1. **Access rules**

**Definition**: A *nested type* is a type declared inside another type. In C#, the nested type is a real CLR type whose name is scoped to the containing type, and whose accessibility can be **more restrictive** than the outer type.

#### What nesting buys you (the real reason to use it)

- **Encapsulation**: You can keep implementation details private without creating file/namespace clutter.
- **API shaping**: You can expose a small public surface while hiding helpers.
- **Reviewability**: A nested type signals “this is only meaningful in the context of the outer type”.

#### Accessibility rules mentors expect you to remember

- A nested type can be `private`, `protected`, `internal`, `protected internal`, `private protected`, or `public`.
- **The outer type can access private members of the nested type and vice versa** (because they are part of the same containing type scope), which can be useful—but also increases coupling.

**Common mistake**: Using `public` nested types as a substitute for proper namespace design. If a type is truly broadly reusable, it usually belongs at namespace scope, not nested.

**Good to know (file-local vs nested)**:

- If your goal is **“hide this helper type from other files”**, a *file-local type* (`file class ...`) is often better than nesting. See section [6.4](<./6.4. File-local types vs nested types.md>) for the deep comparison.

### 2. **Relationship to outer type**

Nested types come in two broad categories:

- **Static-like nested types**: `static` nested classes, nested `struct`, nested `record struct`, nested `enum`, nested `delegate`, and nested `interface` do **not** capture an outer instance.
- **Instance nested classes** (non-`static` nested `class` / `record class`): each instance carries a hidden reference to the **outer instance**.

#### Why the hidden outer reference matters

- **Lifetime extension**: If a nested instance object escapes (stored somewhere long-lived), it can keep the outer object alive unexpectedly.
- **Memory**: extra reference field + possible GC retention graph.
- **Threading**: nested instance classes often access outer state; if the outer type isn’t thread-safe, neither is the nested instance type.

**Example: nested instance class captures outer instance**

```csharp
public sealed class Cache
{
    private readonly Dictionary<string, string> _map = new();

    public Entry GetEntry(string key) => new(this, key);

    public sealed class Entry
    {
        private readonly Cache _owner;
        private readonly string _key;

        internal Entry(Cache owner, string key)
        {
            _owner = owner;
            _key = key;
        }

        public string? Value => _owner._map.TryGetValue(_key, out var v) ? v : null;
    }
}
```

This is legitimate, but note the coupling: `Entry` cannot exist meaningfully without a `Cache` instance.

**Mentor guidance**:

- Default to **static nested** unless you explicitly need access to the outer instance.
- If you need outer state but want to avoid accidental lifetime extension, consider passing explicit dependencies instead of nesting (often clearer).

### 3. **Idioms**

This subsection is about “good nesting”, not “nesting everything”.

#### Idiom A: private implementation types

Use nested `private sealed class` / `private readonly struct` to hide helper types that should never leak into your public API.

#### Idiom B: tightly scoped builders/options

Nested `public sealed class Options` can be reasonable when it is **meaningful only for the outer type** and you want a clear relationship:

```csharp
public sealed class FileIngestor
{
    public sealed record Options(int BufferSize, bool LeaveOpen);

    public FileIngestor(Options options) { /* ... */ }
}
```

If `Options` is used across many components, move it out—don’t nest.

#### Idiom C: discriminated “tags” / private enums

`private enum State { ... }` nested in the type that uses it keeps the concept local and reduces naming collisions.

**Common mistake**: creating deep “Russian doll” nesting that hides complexity instead of reducing it. If you need three+ layers of nested types, it’s often a signal to extract a module or rethink cohesion.
