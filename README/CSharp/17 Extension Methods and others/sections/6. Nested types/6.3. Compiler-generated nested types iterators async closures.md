## 6.3. Compiler-generated nested types ( iterators, async state machines, closures )

1. **What the compiler generates** (why debugging sometimes shows “weird” nested types)
2. **Performance awareness** (closures allocate; async methods generate state machines)
3. **Mental model** (your source-level “nested type” is not the same as compiler machinery—don’t conflate them in design discussions)

---

### 1. **What the compiler generates**

**Definition**: Some C# language features are implemented by the compiler by generating **helper types** (often nested/private, sometimes with “weird” names like `<>c__DisplayClass...` or `<MethodName>d__...`). You didn’t write those types, but they affect:

- debugging,
- memory lifetimes,
- allocations,
- and sometimes performance.

The three most common generators are:

- **Closures** (captured locals in lambdas/local functions) → display classes like `<>c__DisplayClass...`
- **Iterators** (`yield return`) → iterator state machine type like `<Foo>d__...`
- **Async methods** (`async`/`await`) → async state machine type like `<Foo>d__...`

**Example (closure)**:

```csharp
public static Func<int> MakeCounter()
{
    var i = 0;
    return () => ++i; // captures i => compiler generates a display class holding i
}
```

**Example (iterator)**:

```csharp
public static IEnumerable<int> CountUpTo(int n)
{
    for (var i = 0; i < n; i++)
        yield return i; // compiler generates an iterator state machine
}
```

**Example (async)**:

```csharp
public static async Task<int> GetLengthAsync(HttpClient http, Uri uri, CancellationToken ct)
{
    var s = await http.GetStringAsync(uri, ct);
    return s.Length; // compiler generates an async state machine
}
```

**Good to know**

- The generated types are typically **private** to the containing type/method and are not “API surface” in the source sense.
- They still show up in stack traces and profilers, so recognizing the patterns helps you diagnose issues faster.

---

### 2. **Performance awareness**

This is the practical part: what costs can appear, and how to avoid accidental allocations or lifetime extension.

#### Closures: allocations + lifetime extension

**What happens**: if a lambda captures locals, the compiler typically allocates a **closure object** to hold those captured variables.

```csharp
public static IEnumerable<int> Filter(IEnumerable<int> xs, int threshold)
{
    // Captures threshold; the predicate is a delegate that may allocate a closure object.
    return xs.Where(x => x >= threshold);
}
```

**Mitigations** (pick the simplest that keeps code clear):

- **Avoid capture** by passing state explicitly (e.g., use `static` lambdas when possible):

```csharp
return xs.Where(static x => x >= 0); // no capture => no closure allocation
```

- **Move state into a local variable that you don’t capture** (often not possible; be honest about it).
- **Prefer loops** in hot paths where LINQ would allocate enumerators/closures (see section [3.2](<../3. Extension methods performance and deployment/3.2. Allocations captures LINQ-like patterns.md>) for LINQ-like patterns and allocation trade-offs).

#### Iterators: state machine + allocations

Iterator blocks allocate a state machine object when enumeration begins. This is usually fine for readability, but be careful in hot paths or when the method is called extremely frequently.

Mitigations:

- Use `IEnumerable<T>` iterators for clarity when not hot.
- For hot, allocation-sensitive paths, consider:
  - returning `ReadOnlySpan<T>` (when the data is contiguous and lifetime is safe),
  - or writing a custom struct enumerator (advanced; only after measuring).

#### Async: state machine + `Task` allocation behavior

Async methods generate a state machine. On modern .NET, `Task` allocation can sometimes be avoided for synchronous completion paths, but you should not rely on that implicitly.

**Mentor guidance**:

- Use `async`/`await` for correctness and readability.
- For performance-critical APIs that often complete synchronously, consider `ValueTask` **only** when you can enforce correct consumption patterns (single await, no multiple awaits, no caching without care).
- Avoid blocking (`.Result`, `.Wait()`) on tasks in server code; it can cause thread pool starvation.

---

### 3. **Mental model**

**The correct model**: “Some language features are compiled into helper types and method rewrites.”

That leads to good decisions:

- **Debugging**: don’t panic when you see `<Foo>d__12.MoveNext()`—it’s the compiler’s state machine.
- **API design**: don’t design your codebase around the generated type names; those are implementation details that can change between compiler versions.
- **Performance**: reason in terms of *allocations and lifetimes*:
  - captured locals can keep objects alive longer,
  - iterator/async state machines are objects with fields and references,
  - and these show up in GC pressure under load.
