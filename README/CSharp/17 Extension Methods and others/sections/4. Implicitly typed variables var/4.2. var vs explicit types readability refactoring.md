## 4.2. `var` vs explicit types (readability, refactoring, API boundaries)

1. **Mentor default** (use `var` when the type is obvious from the right-hand side; be explicit at public API edges)
2. **Refactoring safety** (renames and type changes: explicit types sometimes catch mistakes earlier)
3. **Numeric literals** (`var` + numeric literals can surprise—know the inferred type rules)

---

### 1. **Mentor default**

**Core idea**: `var` is **compile-time typing**, not dynamic typing. You are not “hiding type information from the compiler”; you are choosing to hide it from the reader when the RHS already makes it obvious.

**Mentor default**:

- Use `var` when the type is **obvious from the right-hand side** or repeating it adds noise.
- Prefer explicit types when the type conveys **meaning**, not just mechanics—especially at **API boundaries** (public members, parameters, return types), or where the RHS is not self-explanatory.

**Examples (readability wins with `var`)**:

```csharp
var utcNow = DateTimeOffset.UtcNow;
var customers = new List<Customer>(capacity: 128);
var id = Guid.NewGuid();
```

**Examples (explicit type communicates intent)**:

```csharp
// Clarifies semantics: a "duration", not "some number".
TimeSpan timeout = TimeSpan.FromSeconds(5);

// Clarifies precision/units and avoids accidental widening/narrowing confusion.
decimal price = 19.99m;

// Clarifies interface boundary (programming-to-abstraction).
IReadOnlyList<Customer> snapshot = customers;
```

**Common mistake**: using `var` with “mystery factory” methods where the type is not obvious.

```csharp
var x = Create(); // What is x? What lifetime/ownership rules apply?
```

If the type matters, be explicit or rename the factory to convey it (`CreateCustomerRepository()`).

**Performance note**:

- `var` does not change runtime performance. It is syntactic sugar for “let the compiler infer the type”.
- Performance issues are almost always about *the inferred type you unintentionally got* (e.g., boxing, `IEnumerable<T>` vs concrete type), not about `var` itself.

---

### 2. **Refactoring safety**

**Definition**: Refactoring safety is about whether code changes produce **compile-time failures** when behavior would change unintentionally.

`var` can be safer or riskier depending on context:

- **Safer**: when the RHS type is stable and obvious (e.g., `new()` expressions, `Guid.NewGuid()`, `Array.Empty<T>()`).
- **Riskier**: when the RHS can change type “silently” during refactors (e.g., conditional expressions, LINQ, factory methods, method groups).

**Example: conditional expression inference can surprise**

```csharp
var result = condition ? GetFoo() : GetBar();
// 'result' type becomes the best common type, which may be wider than you expect.
```

If the intended type is important (or you need a specific overload later), be explicit:

```csharp
IFoo result = condition ? GetFoo() : GetBar();
```

**Mentor note**:

- At **public API edges**, explicit types are a form of documentation and a strong refactoring guardrail.
- Inside small, well-scoped methods, `var` usually improves readability when used consistently.

---

### 3. **Numeric literals**

Numeric inference is the #1 place where `var` bites even experienced developers.

**Common pitfalls**:

- `var x = 1;` => `int`
- `var x = 1L;` => `long`
- `var x = 1.0;` => `double`
- `var x = 1.0f;` => `float`
- `var x = 1.0m;` => `decimal`

**Example: silent overflow/precision intent**

```csharp
var seconds = 60 * 60 * 24 * 365; // int arithmetic
// If you intended long arithmetic:
long secondsLong = 60L * 60 * 24 * 365;
```

**Mentor rule**:

- If units/precision matter, be explicit (`decimal`, `TimeSpan`, `long`) or use suffixes intentionally (`m`, `L`).
- Don’t use `var` as a “shorter type name” for numeric code where overflow/precision is a correctness issue.
