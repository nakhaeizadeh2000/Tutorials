## 4.1. `var` rules (legality, inference, anonymous types, `var` patterns)

1. **What must be inferable** (compiler errors vs “obvious to human” debates)
2. **Anonymous types** (`var` is often mandatory; projection shapes and maintenance)
3. **Pattern integrations** (`var` in patterns/`is`, deconstruction—where readability improves or suffers)

---

### 1. **What must be inferable**

**Definition**: `var` means **implicit typing**: the compiler infers the *exact* static type from the right-hand side **at compile time**. `var` is not “weak typing” and it is not `dynamic` (see section [5.1](<../5. Dynamic typing/5.1. What dynamic means bind at runtime.md>) for `dynamic` semantics).

**Core rule**: the initializer must provide a type the compiler can infer *without* guessing.

#### Legal, obvious inference

```csharp
var n = 42;                 // int
var s = "hello";            // string
var list = new List<int>(); // List<int>
```

#### Not legal (no inference)

```csharp
// var x;                 // error: must be initialized
// var y = null;          // error: null has no type
// var f = () => 123;     // error: lambda needs a target delegate type
```

#### Subtle inference that surprises people

```csharp
var a = 1;          // int
var b = 1L;         // long
var c = 1.0;        // double
var d = 1m;         // decimal
var e = 1u;         // uint
var f = 1f;         // float
```

**Mentor guidance**:

- Use `var` when the type is **obvious from the expression** (e.g., `new(...)`, `Create(...)` returning a well-known type).
- Be explicit when the inferred type can be misunderstood or when it changes behavior (numeric literals, conditional expressions, `default`, `new()` with unclear target type).

**Common mistakes**

- Assuming `var` “keeps code flexible”. It doesn’t. It locks in an exact type at compile time.
- Using `var` with APIs that return interface/abstractions when you intended to program to the abstraction:
  - `var stream = File.OpenRead(path);` makes the variable `FileStream`, not `Stream`. If you want the abstraction, write `Stream stream = ...;`

**Performance note**

- `var` itself has **zero runtime cost**. The only risk is human: if you accidentally infer a wider/narrower type, you can change allocations/boxing or choose slower overloads. Treat `var` as a *readability tool*.

### 2. **Anonymous types**

**Definition**: Anonymous types are compiler-generated reference types created with `new { ... }`. Their name is not expressible in C#, so `var` (or `object`) is the normal way to hold them—`var` preserves the **strong type**.

```csharp
var projection = new { Id = 123, Name = "Ada" };
Console.WriteLine(projection.Name);
```

**When to use**

- Projections in LINQ queries where the shape is local and short-lived.
- Test code and ad-hoc grouping where introducing a named type would be noise.

**Trade-offs**

- **Pros**: strong typing without boilerplate.
- **Cons**: anonymous types don’t cross method boundaries well; they can encourage “mystery shapes” that are hard to refactor.

**Mentor guidance**

- Keep anonymous types **local** (inside a method) and short-lived.
- If the shape is important across layers, use a named `record` (C# 9+) or a dedicated DTO.

**Common mistakes**

- Returning `object`/`dynamic` to “pass around” an anonymous type. That deletes tooling support and makes refactors risky. Prefer a named type.

### 3. **Pattern integrations**

Modern C# uses `var` in patterns for *binding*, not inference of a declaration type in the same way as `var x = ...;`.

#### `is var` pattern (rare but useful)

```csharp
object o = "hello";
if (o is var anything) // always true; binds the value with the best static type (object here)
{
    Console.WriteLine(anything);
}
```

This is mainly useful in advanced pattern compositions; in normal code it’s often unnecessary.

#### Deconstruction

```csharp
var (x, y) = (10, 20);
```

`var` can make deconstruction very readable, but if the element types are non-obvious or important (e.g., `DateTimeOffset` vs `DateTime`), consider explicit types for clarity.

#### `switch` and property patterns (useful)

```csharp
static string Describe(object? value) => value switch
{
    null => "null",
    string { Length: 0 } => "empty string",
    string s => $"string: {s}",
    int n => $"int: {n}",
    _ => "other"
};
```

**Good to know**

- `var` in patterns can be great for readability, but it can also hide important type distinctions. Use it when it clarifies intent, not as a default.
