## 4.4. `var` with `ref`, `readonly ref`, `scoped`, and ref safety (C# 11+ / 12+ / 13+ / 14+ / 15)

1. **Ref locals** (`ref var` patterns; don’t confuse “infer type” with “infer ref-ness”)
2. **Readability in low-level code** (sometimes explicit types improve ref safety reviews)
3. **Mentor rule** (prefer clarity in ref-heavy code; `var` is not a virtue when safety review suffers)

---

### 1. **Ref locals**

**Definition**: `var` can be combined with `ref` to form **ref locals**:

- `ref var x = ref something;` declares a *ref local* (an alias to storage).
- `ref readonly var x = ref something;` declares a *ref readonly local* (alias, but prevents mutation through this reference).

**Mentor warning**: `var` never “infers ref-ness”. The `ref` keyword is the ref-ness. `var` only infers the **element type**.

**Runnable example: ref local aliases storage**

```csharp
var data = new[] { 10, 20, 30 };

ref var slot = ref data[1];
slot = 999;

Console.WriteLine(data[1]); // 999
```

**Common mistakes**

- **Returning refs to temporaries** (illegal / unsafe). The compiler prevents many cases, but you should still reason about lifetimes.
- **Thinking `ref var` is “fast var”**: it’s about aliasing storage, not about inference.

**Performance note**

- Ref locals can avoid copies of large structs and enable in-place updates. But aliasing can also block some optimizations and make code harder to reason about. Use it where it buys something measurable or clarifies intent (e.g., “this updates the original buffer”).

---

### 2. **Readability in low-level code**

In ref-heavy code, readability isn’t a luxury—it’s a correctness tool.

**Mentor guidance**

- If a reviewer must understand whether a variable is a ref alias, make it obvious:
  - prefer `ref`/`ref readonly` plus a **clear name** (`ref var element = ...;` → `ref var current = ...;`)
  - consider **explicit element types** when the inferred type is not obvious.
- Keep ref locals as **small-scope** as possible (declare close to use).

**Example: explicit type can help**

```csharp
ReadOnlySpan<int> span = stackalloc[] { 1, 2, 3 };

// `var` is fine because RHS shows the type clearly.
ref readonly var first = ref span[0];

// But for non-trivial expressions, explicit can reduce reviewer burden:
ref readonly int first2 = ref span[0];

Console.WriteLine(first);
Console.WriteLine(first2);
```

---

### 3. **Mentor rule**

**Rule of thumb**:

- Use `var` freely when the type is obvious *and* ref-ness is explicit.
- Prefer explicit types when:
  - the inferred type is subtle (generics, LINQ, conditional expressions),
  - ref-safety is under review (buffer code, parsers, interop),
  - or the code is already “dense” with `ref`/`readonly`/`scoped`.

**Good to know (`scoped`)**

- `scoped` exists to help the compiler enforce lifetimes for refs/`ref struct` values across method boundaries. If your code needs `scoped`, you’re in a low-level area—bias toward clarity over brevity.
