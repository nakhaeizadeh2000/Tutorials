## 2.2. Extension methods vs alternatives (instance members, static helpers, local functions)

1. **When an instance method is the right default** (core domain behavior belongs on the type)
2. **When static helpers win** (pure utilities with no “receiver story”)
3. **When local functions win** (private algorithm chunks; avoid polluting IntelliSense)

---

### 1. **When an instance method is the right default**

**Definition**: An instance method is behavior that is part of a type’s **core contract** and is discoverable without importing any namespace. It can participate in polymorphism (virtual/override/interface) and can enforce invariants.

**Prefer an instance method when**:

- The behavior is part of the type’s **domain model** (it’s meaningful for every instance).
- The behavior depends on the type’s **invariants** and should be maintained alongside the type’s state.
- You need **polymorphism** (overrides, interface implementations, mocking via interface boundaries).
- You own the type and can evolve it safely.

**Trade-offs**:

- **Pros**: better encapsulation, stronger invariants, fewer `using`-driven surprises (see section [1.4](<../1. Extension methods language rules/1.4. Versioning adding instance methods and using graph changes.md>)).
- **Cons**: you must modify the type; not possible for BCL/third-party types; can bloat a type if you add “convenience” methods without discipline.

**Common mistake**:

- Treating extension methods as a way to avoid designing the type properly (“we’ll keep the type small and put real behavior in extensions”). That often makes invariants invisible and spreads domain logic across random namespaces.

**Example**:

```csharp
public sealed class Money
{
    public Money(decimal amount, string currency)
    {
        if (amount < 0) throw new ArgumentOutOfRangeException(nameof(amount));
        ArgumentException.ThrowIfNullOrWhiteSpace(currency);
        Amount = amount;
        Currency = currency;
    }

    public decimal Amount { get; }
    public string Currency { get; }

    // Core domain behavior belongs here (invariants + discoverability).
    public Money Add(Money other)
    {
        if (!string.Equals(Currency, other.Currency, StringComparison.Ordinal))
            throw new InvalidOperationException("Currency mismatch.");
        return new Money(Amount + other.Amount, Currency);
    }
}
```

### 2. **When static helpers win**

**Definition**: A static helper is a normal static method used when there is no strong “receiver story” or when you want **explicitness** over fluent call-site style.

**Prefer a static helper when**:

- The operation is **pure utility** and would read oddly as `receiver.Operation(...)`.
- You want to avoid extension-method discovery and binding hazards (sections [1.2](<../1. Extension methods language rules/1.2. Invocation binding precedence instance vs extension.md>) and [1.4](<../1. Extension methods language rules/1.4. Versioning adding instance methods and using graph changes.md>)).
- The method is an implementation detail and shouldn’t appear in IntelliSense on the receiver type.
- You want consumers to notice they’re using a separate component (e.g., `Hashing.Sha256(...)` is clearer than `"x".Sha256()` in many codebases).

**Trade-offs**:

- **Pros**: explicit call sites; fewer collisions; simpler mental model.
- **Cons**: less fluent; you don’t get the “instance-syntax” readability when a receiver truly is the main subject.

**Example**:

```csharp
public static class Hashing
{
    public static string Sha256Hex(ReadOnlySpan<byte> bytes)
    {
        Span<byte> hash = stackalloc byte[32];
        _ = System.Security.Cryptography.SHA256.HashData(bytes, hash);
        return Convert.ToHexString(hash);
    }
}
```

**Performance note**:

- Don’t force an extension method onto a hot path “for performance”. Extensions are static calls anyway (section [3.1](<../3. Extension methods performance and deployment/3.1. What the JIT sees static calls inlining.md>)). Prefer whichever shape improves correctness and reduces accidental misuse.

### 3. **When local functions win**

**Definition**: A local function is a named method declared inside another method. It’s the best tool for **private algorithm pieces** that don’t belong in the type’s public surface (and don’t belong in global extension namespaces either).

**Prefer a local function when**:

- You need to structure a single method without adding a new private method or helper type.
- The helper is tightly coupled to one method’s control flow and doesn’t deserve broader visibility.
- You want to avoid allocations sometimes caused by lambdas capturing state (local functions can still capture, but are often clearer and can avoid delegate allocations when passed as method groups).

**Example**:

```csharp
public static int CountDigits(int value)
{
    if (value == 0) return 1;
    value = Math.Abs(value);

    return Count(value);

    static int Count(int v)
    {
        var digits = 0;
        while (v != 0)
        {
            v /= 10;
            digits++;
        }
        return digits;
    }
}
```

**Common mistake**:

- Using extensions as “private helpers” because they look neat in call sites. That leaks helper methods into IntelliSense everywhere and increases long-term collision risk.
