## 2.1. Designing fluent, discoverable extensions (names, namespaces, arity)

1. **Namespace placement** (one feature area per namespace; avoid dumping everything into `Extensions`)
2. **Naming** (method name reads well at call site; avoid abbreviations that obscure side effects)
3. **Parameter design** (optional parameters + extensions + overload sets: keep the matrix small)

---

### 1. **Namespace placement**

**Definition**: The “real” API surface of extension methods is not just the method signatures—it’s also **where they live**. The namespace determines who sees them (via `using`) and which call sites they can affect (see binding/precedence in section `1.2`).

**Mentor rule**: Use **feature-area namespaces**, not one monolithic `*.Extensions` namespace.

- Good: `MyCompany.Text`, `MyCompany.Json`, `MyCompany.Http`, `MyCompany.Collections`
- Risky: `MyCompany.Extensions` (becomes “ambient API” and increases collision/ambiguity risk)

**Why this matters in production**

- **Discoverability**: Callers should be able to “opt in” to a capability by importing one namespace and immediately seeing relevant methods in IntelliSense.
- **Safety**: A broad namespace imported everywhere makes it easy for a new extension to accidentally change binding at distant call sites (section `1.4`).
- **Maintainability**: Feature namespaces become natural ownership boundaries for reviews and changes.

**Common mistakes**

- **“Dump-everything” containers**: One `Extensions` folder and a single namespace for unrelated domains.
- **Extending `object`**: It effectively makes your method show up on everything and pollutes overload resolution. Many teams ban this with analyzers (see section `2.3`).

**Good to know**

- `global using` is powerful, but treat it as an **API decision**. If you make extensions global, you’ve essentially made them “always-on” features with all the versioning risks that implies (section `1.4`).

---

### 2. **Naming**

**Definition**: The best extension method name reads like an obvious, honest instance member *and* it does not hide costs or side effects.

#### Naming rules that scale

- **Prefer verbs that match semantics**:
  - Pure transforms: `ToXxx`, `AsXxx`, `WithXxx`, `SelectXxx`
  - Validation/throw: `EnsureXxx`, `ThrowIfXxx`
  - Try-pattern: `TryGetXxx`, `TryParseXxx`
  - I/O or effects: `WriteToXxx`, `SaveToXxx`, `LoadFromXxx`
- **Encode side effects and latency**:
  - Async I/O should be `...Async` and accept `CancellationToken`.
  - Avoid `ToJson()` if it does allocations + uses options + may throw; prefer `ToJsonString(...)` or `WriteJsonTo(...)` depending on behavior.
- **Avoid “generic verbs” in shared libraries** (`Add`, `Normalize`, `Format`) unless you’re in a very narrowly scoped domain namespace (collision risk; section `1.4`).

**Example: honest naming for side effects**

```csharp
public static class StreamExtensions
{
    // Honest: "CopyToFileAsync" makes I/O and asynchrony obvious.
    public static async ValueTask CopyToFileAsync(
        this Stream source,
        string path,
        CancellationToken ct = default)
    {
        ArgumentNullException.ThrowIfNull(source);
        ArgumentException.ThrowIfNullOrWhiteSpace(path);

        await using var destination = File.Create(path);
        await source.CopyToAsync(destination, ct);
    }
}
```

**Mentor note**

- If you are tempted to create an extension with a name that could plausibly become an instance member on the receiver type in the future, that’s a warning sign—consider a more specific name or a different design (section `2.2`).

### 3. **Parameter design**

**Goal**: Make call sites simple, overload resolution predictable, and performance characteristics obvious.

#### Keep overload sets small

**Trade-off**:

- More overloads can make IntelliSense nicer, but they also:
  - increase ambiguity risk when other namespaces introduce similar extensions,
  - make versioning harder (adding overloads can change “best match”),
  - complicate documentation and testing.

**Mentor default**: prefer **a few explicit overloads** over optional-parameter matrices.

#### Avoid optional parameters when they change semantics

Optional parameters are fine when they represent minor tweaks, but they are risky when they:

- change algorithmic behavior (e.g., `mode = Fast/Accurate`),
- impact security or correctness,
- or create “surprising defaults” that callers don’t notice.

Prefer distinct method names or an options type for meaningful behavior switches.

#### Prefer `CancellationToken` on async extensions that do I/O

```csharp
public static class HttpClientExtensions
{
    public static async Task<string> GetStringOrThrowAsync(
        this HttpClient http,
        Uri uri,
        CancellationToken ct = default)
    {
        ArgumentNullException.ThrowIfNull(http);
        ArgumentNullException.ThrowIfNull(uri);

        using var resp = await http.GetAsync(uri, ct).ConfigureAwait(false);
        resp.EnsureSuccessStatusCode();
        return await resp.Content.ReadAsStringAsync(ct).ConfigureAwait(false);
    }
}
```

*(Library code note: `ConfigureAwait(false)` is harmless on modern server code and avoids depending on a synchronization context. If you are writing UI code, see your UI domain guidelines.)*

#### Performance note (allocations, delegates, `params`)

- Extensions that accept delegates (`Func<>`, `Action<>`) can allocate if the lambda captures (closures). See section `3.2`.
- `params` on hot paths can allocate an array; use it intentionally.
  - Modern .NET adds more span-friendly APIs, but don’t over-engineer: prefer clarity unless profiling shows a real hotspot.

**Common mistakes**

- Hidden allocations: returning new collections by default in “helper” extensions.
- Surprising null contracts: `this T` but then silently treating null as empty. If you accept null, annotate `this T?` and document behavior (section `1.3`).
