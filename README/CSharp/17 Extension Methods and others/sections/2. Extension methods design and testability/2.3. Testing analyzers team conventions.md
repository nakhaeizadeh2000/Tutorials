## 2.3. Testing, analyzers, and team conventions

1. **Unit testing extensions** (test like static functions; mind reduced discoverability vs instance APIs)
2. **Roslyn analyzers** (ban patterns: e.g., extensions on `object`, extensions that hide I/O)
3. **Code review checklist** (namespace collisions, nullability contracts, overload traps)

---

### 1. **Unit testing extensions**

**Definition**: An extension method is a **static method** (section `1.1`). Test it like any other deterministic function: inputs → outputs, with explicit coverage for boundary conditions and nullability behavior (section `1.3`).

**What to test**

- **Contract behavior**: nullability, exceptions, side effects.
- **Edge cases**: empty input, large input, invalid data, cancellation (for async I/O).
- **Performance-sensitive semantics** (only when relevant): “does not enumerate twice”, “does not allocate per element”, etc. (see section `3.2` for common allocation traps).

**Example (xUnit-style)**

```csharp
using Xunit;

public static class StringExtensions
{
    public static string OrEmpty(this string? value) => value ?? string.Empty;
}

public sealed class StringExtensionsTests
{
    [Fact]
    public void OrEmpty_Null_ReturnsEmpty()
    {
        string? value = null;
        Assert.Equal(string.Empty, value.OrEmpty());
    }

    [Fact]
    public void OrEmpty_NonNull_ReturnsSameInstance()
    {
        var value = "abc";
        Assert.Same(value, value.OrEmpty());
    }
}
```

**Mentor note**

- For library code, treat extension methods as public API. Tests are part of your stability contract, especially because binding can change via `using` graphs and instance shadowing (section `1.4`).

### 2. **Roslyn analyzers**

**Definition**: Roslyn analyzers (built-in + custom) enforce conventions automatically. They’re the most scalable way to prevent extension-method footguns from spreading across a codebase.

**High-value analyzer rules (recommended)**

- **Ban extensions on `object`** (pollutes IntelliSense and overload resolution).
- **Ban catch-all extension namespaces** (e.g., `Company.Extensions`) or restrict them heavily.
- **Require XML docs** for public extension methods (extensions are discoverability-driven).
- **Require explicit nullability**: disallow `this T` methods that accept null silently; enforce `this T?` when null is supported.
- **Side effects naming**: warn if a method name suggests purity (`ToXxx`, `AsXxx`) but performs I/O, locking, or starts background work.

**Good to know**

- Prefer turning “must-fix” rules into **build errors** (after a short adoption period) to prevent backsliding.
- Avoid “warning fatigue”: start with a small set of high-signal rules and expand gradually.

**Modern replacement for legacy enforcement**

- Legacy: “We’ll enforce this in code reviews only.”
- Modern: **Analyzer + code fix + review**. Reviews should focus on intent; analyzers catch mechanical issues consistently.

### 3. **Code review checklist**

Use this as a practical, copy-paste checklist in PR reviews.

- **Receiver correctness**: Is the receiver the real domain subject? If not, consider a static helper (section `2.2`).
- **Namespace placement**: Feature-area namespace (section `2.1`), not global utility soup.
- **Collision risk**:
  - Could the extended type plausibly gain an instance member with this signature? (section `1.4`)
  - Are we introducing ambiguous overloads when consumers import multiple feature namespaces?
- **Nullability contract**: `this T` vs `this T?` matches behavior (section `1.3`).
- **Overloads/optional parameters**: keep small, predictable; avoid semantic switches via optional parameters (section `2.1`).
- **Async & cancellation**:
  - I/O extensions: `CancellationToken` and honest naming (`...Async`).
  - No hidden `Task.Run` or background thread usage.
- **Performance**:
  - Avoid delegate-capture allocations in hot paths (section `3.2`).
  - Avoid repeated enumeration (`IEnumerable<T>` traps) unless documented.
