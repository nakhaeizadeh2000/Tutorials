## 3.3. Trimming, AOT, and reflection surprises

1. **Trimming** (reflection-based discovery of extension methods is fragile; prefer explicit calls)
2. **Native AOT constraints** (dynamic features and some patterns don’t port mechanically)
3. **Practical guidance** (validate publish modes early if extensions are central to your API surface)

---

### 1. **Trimming**

**Definition**: *Trimming* removes IL that the linker believes is unused during publish (common in modern .NET publish modes). This is great for size and startup, but it makes **reflection-based discovery** fragile because “unused” members can be removed.

Extension methods often enter trimming conversations in two ways:

- **You call extension methods normally** (static call compiled in). This is typically safe; the method is referenced and therefore kept.
- **You discover/call extension methods dynamically** (reflection scan + `Invoke`, or building a dynamic pipeline). This is fragile: the linker may trim methods it doesn’t see as referenced.

**Mentor rule**: If extension methods are part of your “plugin system”, don’t rely on “scan all assemblies for `[Extension]` methods” unless you’ve designed for trimming explicitly.

**Common mistake**

- Treating reflection scanning as harmless in libraries. Under trimming, “it works on Debug” and “it works on untrimmed publish” but fails in trimmed/AOT modes.

**Performance note**

- Reflection scanning costs CPU at startup and can create allocations and metadata pressure. Even if it works, it often hurts startup time and cold-path performance.

---

### 2. **Native AOT constraints**

**Definition**: *Native AOT* compiles your app ahead of time. Many dynamic patterns still work, but the general rule is: **the more the runtime must “discover” at runtime**, the more likely you are to hit constraints.

Extension-method related pitfalls:

- **`dynamic` + DLR**: `dynamic` is late-bound and can be limited or more expensive; avoid it in AOT scenarios unless you control and test it (see section `5.x` for `dynamic` guidance).
- **`System.Reflection.Emit`**: not supported in many AOT scenarios.
- **“Open world” reflection**: calling methods that aren’t statically referenced may fail if the method body or metadata isn’t preserved.

**Mentor take**: Native AOT is not “just flip a switch”; if your design relies on reflection to wire behaviors, you need explicit preservation or a different design (source generators, explicit registration, etc.).

---

### 3. **Practical guidance**

#### Use explicit calls or explicit registration

- If you control the extension usage, prefer **explicit calls** (normal extension syntax) so the call is statically referenced.
- If you need “discoverability”, prefer an **explicit registration API**:
  - e.g., a library method `AddMyFeature(...)` that registers known behaviors,
  - or a compile-time approach (source generator) that produces a registry.

#### If you must use reflection, be intentional

- Narrow the scanning scope (specific assemblies/types).
- Avoid scanning “everything in AppDomain” as a default.
- Plan and test for publish modes early: trimmed, ReadyToRun, Native AOT.

#### Don’t confuse “extensions” with “reflection”

Extension methods themselves are not inherently dynamic; they’re static calls.
It’s the **runtime discovery** patterns built around them that collide with trimming/AOT.
