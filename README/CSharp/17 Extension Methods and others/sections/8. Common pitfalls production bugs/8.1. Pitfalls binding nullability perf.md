## 8.1. Pitfalls: binding surprises, nullability holes, and perf traps

1. **Adding `using` changes extension resolution** (silent behavior changes across files)
2. **Extension on null** (can run if static call allows it—don’t assume instance method guarantees)
3. **`var` obscuring risky conversions** (especially with conditional expressions and method groups)
4. **`dynamic` leaking outward** (turns large regions into late-bound code)
5. **Nested types holding references to outer instance** (unexpected lifetimes + test pain)

---

### 1. **Adding `using` changes extension resolution**

**What goes wrong**: A new `using` (or a new `global using`, or a new package that adds extensions into a commonly imported namespace) changes the compiler’s extension candidate set. Your call site `x.DoThing()` stays the same, but the bound method can become:

- different (a “better match” appears), or
- ambiguous (compile error), or
- shadowed by a newly introduced instance method (classic silent change).

**See**: section `1.2` (binding/precedence) and section `1.4` (versioning and using-graph drift).

**Good to know**:

- Treat “importing extension namespaces globally” as a library/API decision, not a style preference.
- Prefer feature-area namespaces (section `2.1`) to minimize accidental cross-domain collisions.

---

### 2. **Extension on null**

**What goes wrong**: Because extensions are static calls (section `1.1`), the receiver can be `null` at runtime and the method will still be invoked—until it dereferences.

**See**: section `1.3` for the deep nullability contract and safe patterns (`this T` vs `this T?`, fail-fast vs null-tolerant APIs).

**Common mistake**:

- Writing `public static string Foo(this string s) => s.Trim();` and assuming it can never be called on null “because it looks like an instance call”.

---

### 3. **`var` obscuring risky conversions**

**What goes wrong**: `var` is compile-time inference (section `4.1`), but it can hide:

- an inferred numeric type you didn’t intend (`var x = 1;` is `int`, `var y = 1u;` is `uint`),
- conditional expression “type unification” that widens the type unexpectedly,
- method group/lambda inference that becomes less obvious at a glance.

**See**: section `4.2` for the mentor-style guidance on when to use `var` vs explicit types, and section `4.1` for inference legality and rules.

**Performance note**:

- `var` itself has *no runtime cost*, but confusing inferred types can lead to hidden boxing/conversions. Review hot-path types carefully.

---

### 4. **`dynamic` leaking outward**

**What goes wrong**: One `dynamic` value can turn large regions of code into late-bound behavior where refactors become runtime failures.

**See**: section `5.4` for reliability/tooling hazards and how to keep `dynamic` behind narrow boundaries; section `5.2` for modern alternatives (generics, source generators, `System.Text.Json`).

**Mentor rule**:

- Contain `dynamic` at the edge (interop/legacy boundary). Convert to strongly typed data immediately.

---

### 5. **Nested types holding references to outer instance**

**What goes wrong**: An instance nested class implicitly keeps a reference to its containing instance. This can:

- extend lifetimes unintentionally,
- retain large object graphs,
- complicate testing and serialization.

**See**: section `6.2` for static vs instance nesting and lifetime implications, and section `6.4` for file-local types as an alternative for encapsulation without instance coupling.
