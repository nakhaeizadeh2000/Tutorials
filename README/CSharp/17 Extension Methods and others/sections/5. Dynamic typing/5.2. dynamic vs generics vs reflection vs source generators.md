## 5.2. `dynamic` vs generics vs reflection vs source generators

1. **Prefer compile-time solutions** when performance and correctness tooling matter
2. **When `dynamic` is still reasonable** (interop boundaries, small surfaces, throwaway tooling)
3. **Modern alternatives** (source generators, `System.Text.Json` polymorphism, interface-based designs)

---

### 1. **Prefer compile-time solutions**

**Definition**: In modern C# (.NET 9+ era), you generally want the compiler (and analyzers) to prove as much as possible: types, nullability, overload resolution, and refactoring safety. `dynamic` postpones binding to runtime, which trades correctness tooling for flexibility.

**Prefer generics / interfaces / static typing when**:

- You’re writing **core domain logic**.
- You care about **refactoring safety** (rename, signature changes, dead code detection).
- You care about **performance** (JIT optimizations, inlining, less boxing/late binding).
- You want strong **analyzer coverage** (nullable flow, CA rules, custom analyzers).

**Example: generic + interface boundary instead of `dynamic`**

```csharp
public interface IClock
{
    DateTimeOffset UtcNow { get; }
}

public sealed class SystemClock : IClock
{
    public DateTimeOffset UtcNow => DateTimeOffset.UtcNow;
}

public static class TokenFactory
{
    public static string CreateToken(IClock clock, TimeSpan ttl)
        => $"exp={clock.UtcNow.Add(ttl):O}";
}
```

This is testable, analyzable, and fast. There’s no reason for `dynamic`.

**Trade-offs**:

- Compile-time designs require more up-front modeling (interfaces, types, DTOs).
- `dynamic` can be quicker for *one-off glue code*.

**Mentor note**: Don’t optimize for “fewer keystrokes.” Optimize for **local reasoning** and **upgrade safety**.

---

### 2. **When `dynamic` is still reasonable**

`dynamic` is a tool for **interop boundaries**, not a default typing strategy.

**Reasonable scenarios**:

- **COM interop**: Office automation, legacy COM APIs (still relevant in some enterprises).
- **Script-like tooling**: internal admin scripts where compile-time guarantees matter less than speed of writing.
- **Very small adapter layers**: a thin layer that normalizes a dynamic API into a strongly typed domain model.

**Unreasonable scenarios** (common mistakes):

- Using `dynamic` to “solve” generic constraints or overload resolution problems.
- Letting `dynamic` leak into business logic: once it spreads, you lose refactoring safety and analyzer value.
- Using `dynamic` inside tight loops or hot paths (see performance in section `5.3`).

**Containment pattern: keep dynamic behind a narrow facade**

```csharp
public sealed class ComExcelFacade
{
    private readonly dynamic _excel;

    public ComExcelFacade(dynamic excel) => _excel = excel;

    public void SetCellText(int row, int col, string text)
    {
        // dynamic is contained here; callers remain strongly typed.
        _excel.Cells[row, col].Value2 = text;
    }
}
```

**Good to know**:

- Exceptions from `dynamic` member binding show up at runtime as binder exceptions; treat this like reflection: validate inputs and add focused tests.

---

### 3. **Modern alternatives**

#### Alternative A: source generators

Use when you want “dynamic-like” convenience but still want **compile-time safety** and good perf.

- Example use cases: mapping, serialization glue, strongly typed API clients, DI wiring, regex generation.
- Benefits: no runtime binder cost; great analyzers; better trimming/AOT friendliness than reflection-heavy approaches.

#### Alternative B: `System.Text.Json` with explicit models

Prefer strongly typed DTOs + `JsonSerializer` when possible.

- If you need “unknown shape” handling, use `JsonDocument` / `JsonElement` as an explicit DOM—not `dynamic`.

```csharp
using System.Text.Json;

JsonElement root = JsonSerializer.Deserialize<JsonElement>(json);
if (root.TryGetProperty("name", out var nameProp) && nameProp.ValueKind == JsonValueKind.String)
{
    var name = nameProp.GetString();
}
```

#### Alternative C: reflection (careful) + caching

Reflection is sometimes appropriate for frameworks, but in .NET 9+ it comes with:

- trimming/AOT hazards (see section `3.3`),
- perf costs unless you cache delegates,
- weaker analyzer/refactoring guarantees.

**Mentor rule**: if you can express it with generics/interfaces, do that. If you can’t, prefer generators or explicit DOMs before `dynamic`.
