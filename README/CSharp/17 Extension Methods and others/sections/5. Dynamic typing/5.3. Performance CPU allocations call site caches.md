## 5.3. Performance and memory (CPU, allocations, call-site caches)

1. **CPU cost model** (late binding, fewer inlining opportunities, harder JIT optimization)
2. **Allocation behavior** (understand hotspots; don’t use `dynamic` in tight loops by default)
3. **Profiling story** (`dynamic` can obscure bottlenecks—use targeted benchmarks)

---

### 1. **CPU cost model**

**Mental model**: a `dynamic` call is not “slow because it’s dynamic”; it’s slower because the runtime must:

- determine the target member at runtime (binding),
- often go through the DLR call-site machinery,
- and it blocks many compile-time optimizations (including “obvious” inlining and devirtualization).

**What usually happens at a hot call site**:

- The **first** call pays the highest cost (binding and rule creation).
- Later calls can be faster due to **call-site caching**, but you still typically pay more overhead than a normal static/virtual call.

**When the CPU cost matters**

- Tight loops (parsers, numeric kernels, large-data transformations)
- High-throughput server code where micro overhead becomes macro cost due to volume
- Any path where you’d otherwise expect inlining + JIT specialization to do real work

**When it usually doesn’t**

- Tooling, scripts, one-off migrations
- UI glue code (where I/O and user latency dominate) *(frontend)*
- Low-frequency admin paths

**Common mistake**: using `dynamic` for convenience inside a hot loop because “it’s only a small amount of code”.

**Performance note**

- If you need performance and late binding, prefer designs that allow the JIT to optimize:
  - interfaces with known members,
  - generic algorithms,
  - source-generated serializers/mappers.

---

### 2. **Allocation behavior**

`dynamic` itself doesn’t always allocate per call, but the patterns that accompany `dynamic` often do:

- **boxing** (value types flowing through `object`/`dynamic`),
- **reflection interop** allocations (when `dynamic` is replaced by reflection to “fix” problems),
- and occasionally **temporary objects** created by dynamic frameworks.

**Example: accidental boxing**

```csharp
static long SumWithDynamic(int[] xs)
{
    dynamic sum = 0; // sum is dynamic; value types can box across operations depending on runtime rules
    foreach (var x in xs)
        sum += x;
    return (long)sum;
}
```

Prefer:

```csharp
static long SumFast(int[] xs)
{
    long sum = 0;
    foreach (var x in xs)
        sum += x;
    return sum;
}
```

**Mentor guidance**:

- Keep `dynamic` **at the boundary** (interop layer). Convert to strong types immediately.
- Avoid “sprinkling dynamic” through domain code, because it tends to force repeated conversions and hides costs.

---

### 3. **Profiling story**

`dynamic` complicates profiling and diagnosis because:

- stack traces and call stacks can show DLR infrastructure rather than your logical target,
- JIT inlining patterns change,
- and you can accidentally benchmark “binder overhead” instead of business logic.

**Practical guidance**

- If performance matters, write a tiny micro-benchmark using `BenchmarkDotNet` comparing:
  - static call,
  - interface dispatch,
  - `dynamic`,
  - reflection (if that’s the alternative).
- Use allocation profiling (e.g., `dotnet-trace`, `dotnet-counters`, or your IDE profiler) to confirm whether `dynamic` is causing:
  - boxing,
  - delegate/closure allocations,
  - or hidden intermediate objects.

**Good to know**

- If your goal is “dynamic JSON”, modern .NET APIs increasingly reward strong typing:
  - prefer `System.Text.Json` with source generation for speed and trimming/AOT friendliness (see section `5.2`),
  - keep `JsonElement`/`JsonNode` usage localized when schema is truly unknown.
