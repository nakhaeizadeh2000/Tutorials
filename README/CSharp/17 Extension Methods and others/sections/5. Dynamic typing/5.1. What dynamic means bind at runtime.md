## 5.1. What `dynamic` means in C# (bind at runtime, not “duck typing”)

1. **`dynamic` vs `object`** (late-bound calls vs explicit casts)
2. **Call sites and caching** (DLR rules at a high level; why repeated calls can stabilize)
3. **Interop scenarios** (COM, some dynamic JSON/XML models—know the escape hatches)

---

### 1. **`dynamic` vs `object`**

**Definition**:

- `dynamic` means: *treat this expression as “unknown until runtime” for member binding*. The compiler still type-checks the rest of the program, but **member resolution** (method/prop/indexer/operator) is deferred to runtime.
- `object` means: *the static type is `object`*. Member access is compile-time limited to members of `object` unless you cast.

**Key difference (what errors you get, and when)**:

```csharp
object o = "hi";
// o.Length;             // compile-time error: object has no Length
Console.WriteLine(((string)o).Length); // ok after explicit cast

dynamic d = "hi";
Console.WriteLine(d.Length); // compiles; runtime binder resolves "Length" on string
```

**Mentor warning**: `dynamic` is not “a nicer `object`”.

- With `object`, the compiler forces you to be explicit with casts, so refactors fail fast at compile time.
- With `dynamic`, a rename or signature change can compile cleanly and fail **only at runtime**.

**Common mistake**:

- Using `dynamic` as a “quick fix” for generic inference or overload resolution. That often spreads late binding across a codebase and destroys tooling value (see section `5.2` for alternatives).

---

### 2. **Call sites and caching**

**Definition**: When the compiler sees a `dynamic` operation (e.g., `d.Foo(123)`), it emits a *dynamic call site* that uses the DLR (Dynamic Language Runtime) binder.

**Practical implications** (what you should know without needing IL details):

- The first time a given dynamic call site executes for a particular runtime shape (receiver type + argument types), it performs binding work and usually caches a rule.
- Repeated execution at the same call site with the same shapes is typically faster than “first hit”, but still generally slower than static binding (deep perf in section `5.3`).

**Behavior gotcha**:

- Dynamic binding depends on **runtime types**, not just values.

```csharp
dynamic x = 1;
Console.WriteLine(x + 2); // int + int => int

x = 1.0;
Console.WriteLine(x + 2); // double + int => double (different binding)
```

**Mentor note**:

- “Caching” does not make `dynamic` free. It just makes repeated patterns less awful.
- Hot loops + `dynamic` is a red flag until proven by profiling.

---

### 3. **Interop scenarios**

`dynamic` still has legitimate uses, mostly at **interop boundaries**:

- **COM interop** (Office automation, older automation APIs).
- Some dynamic languages / scripting hosts.
- Some legacy “dynamic object model” APIs.

**Modern .NET guidance for JSON/XML**:

- For JSON, prefer **`System.Text.Json` with typed models**, source generation, or `JsonNode`/`JsonDocument` depending on needs. Avoid `dynamic` for JSON in production—errors become runtime-only and trimming/AOT becomes harder (see section `3.3` for deployment constraints).

**Boundary pattern mentors insist on**:

- Keep `dynamic` behind a narrow adapter interface, convert to strong types ASAP, and don’t leak `dynamic` into your domain layer.

```csharp
public interface IExternalThing
{
    string Id { get; }
}

public sealed class ExternalThingAdapter : IExternalThing
{
    private readonly dynamic _raw;
    public ExternalThingAdapter(dynamic raw) => _raw = raw;

    public string Id => (string)_raw.Id; // explicit cast makes failure obvious
}
```

**Good to know**

- If you need “shape-based” behavior, consider an explicit interface + implementations, or code generation/source generators (section `5.2`). Those preserve analyzers, refactoring, and performance.
