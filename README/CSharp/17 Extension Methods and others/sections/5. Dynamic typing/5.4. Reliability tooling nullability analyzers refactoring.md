## 5.4. Reliability and tooling (nullability, analyzers, refactoring)

1. **Analyzer limitations** (fewer compile-time guarantees; tests become more important)
2. **Refactoring hazards** (rename/method changes may fail at runtime)
3. **Mentor boundary** (keep `dynamic` behind narrow interfaces; don’t spread it across the domain layer)

---

### 1. **Analyzer limitations**

**Definition**: `dynamic` disables most compile-time member checking for the expressions that flow through it. The compiler still produces IL, but member resolution is deferred to runtime via the DLR (deep mechanics in section [5.1](<./5.1. What dynamic means bind at runtime.md>)).

**What analyzers can’t reliably do** (once `dynamic` is involved):

- **Nullability flow**: the compiler can’t prove much about runtime member calls, so nullable warnings are less actionable.
- **Refactoring correctness**: rename/move operations won’t update string-based member names and may not catch runtime bind failures.
- **Dead code detection / contract checking**: “this method is never called” becomes less reliable if calls are late-bound.

**Mentor guidance**

- Treat `dynamic` like an **interop boundary**: it’s acceptable at the edge, but it is not a good “mainline type system”.
- If you need flexibility inside core code, prefer **interfaces/generics** (section [5.2](<./5.2. dynamic vs generics vs reflection vs source generators.md>)) so tooling stays effective.

**Testing note**

- With `dynamic`, you need **more runtime tests** (unit + integration) for the same confidence level because compile-time checks have been traded away.

---

### 2. **Refactoring hazards**

**Definition**: With `dynamic`, many failures become “runtime binder errors” (or method-not-found exceptions) rather than compile-time errors.

**Common refactoring traps**

- **Renaming a member** used via `dynamic`:
  - With static typing, this is a compile-time break and fixable via tooling.
  - With `dynamic`, it compiles and breaks at runtime.
- **Changing overload sets**:
  - A dynamic call might bind to a different overload after a change, shifting behavior subtly.
- **Changing numeric types**:
  - Dynamic arithmetic and conversions can change runtime binding and throw unexpected exceptions or produce different results.

**Practical mitigations**

- Keep dynamic usage **local and encapsulated**:
  - Wrap dynamic objects inside a typed adapter.
  - Convert early to a strong type (DTO, interface, record) and keep the rest of the app static.
- Prefer **explicit casts** at the boundary when reasonable to force a stable contract:

```csharp
public static int GetCount(dynamic d)
{
    // This cast fails early and predictably if the payload isn't as expected.
    // It also makes intent obvious in code review.
    return (int)d.Count;
}
```

**Good to know**

- This isn’t about being “anti-dynamic”; it’s about being honest that `dynamic` moves failure modes to runtime and tests must pick up that slack.

---

### 3. **Mentor boundary**

**Rule**: `dynamic` should rarely cross an architectural boundary into your domain.

**Good boundary shapes**

- **Interop adapters**:
  - One assembly/project that talks to COM/Office/old APIs using `dynamic`.
  - It exposes strongly typed interfaces/records to the rest of the system.
- **Parsing layer**:
  - Parse external data into strongly typed models (`System.Text.Json` source generation, polymorphism config, etc.) and keep `dynamic` out of business logic.

**Bad boundary shapes**

- “We’ll store `dynamic` in our entities and figure it out later.”
- “We’ll return `dynamic` from service methods.”

Those patterns turn large regions of the codebase into runtime-typed code and make performance and correctness harder to reason about (see section [5.3](<./5.3. Performance CPU allocations call site caches.md>)).

**Performance note**

- `dynamic` itself is not an allocation, but it often *enables* allocation-heavy patterns (boxing, reflection-like access, adapter objects) and blocks optimizations like inlining and devirtualization in hot paths.
