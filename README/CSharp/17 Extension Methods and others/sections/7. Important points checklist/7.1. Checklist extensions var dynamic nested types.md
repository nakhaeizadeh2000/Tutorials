## 7.1. Checklist: extensions, `var`, `dynamic`, nested types

1. **Extensions are static** (discovery and versioning rules can bite teams that treat them like instance members)
2. **`var` is not `dynamic`** (inference is compile-time; `dynamic` defers binding)
3. **Prefer explicit types at API boundaries** (public members: make contracts obvious)
4. **Nested types are a visibility tool** (not a license for mega-classes—keep outer types cohesive)
5. **Measure `dynamic` and allocation-heavy extensions** (CPU + allocations + thread pool interactions in server code)

---

### 1. **Extensions are static**

- **Remember**: `x.Ext()` is syntax sugar for a **static call**. Binding depends on `using` scopes and is vulnerable to shadowing by new instance members.
- **Good to know**:
  - **Binding/precedence**: See section [1.2](<../1. Extension methods language rules/1.2. Invocation binding precedence instance vs extension.md>).
  - **Versioning hazards** (silent shadowing, `using` graph drift): See section [1.4](<../1. Extension methods language rules/1.4. Versioning adding instance methods and using graph changes.md>).
  - **Null receiver reality**: See section [1.3](<../1. Extension methods language rules/1.3. Extension methods and nullability nullable receivers.md>).
- **Team habit**: Keep extensions in **feature-area namespaces** (see section [2.1](<../2. Extension methods design and testability/2.1. Designing fluent discoverable extensions.md>)) and avoid “ambient” global extension imports unless you’re intentionally taking on that coupling.

### 2. **`var` is not `dynamic`**

- **Remember**:
  - `var` is **compile-time** type inference (the variable has a real static type).
  - `dynamic` is **runtime binding** (member resolution happens at runtime; tooling guarantees weaken).
- **Full treatment**:
  - `var` legality/inference/patterns: section [4.1](<../4. Implicitly typed variables var/4.1. var rules legality inference anonymous types.md>)
  - `dynamic` semantics + DLR call sites: section [5.1](<../5. Dynamic typing/5.1. What dynamic means bind at runtime.md>)
- **Pitfall**: Using `dynamic` to “make generic code compile” usually trades a compile-time error for a runtime failure (see section [5.2](<../5. Dynamic typing/5.2. dynamic vs generics vs reflection vs source generators.md>)).

### 3. **Prefer explicit types at API boundaries**

- **Remember**: Public APIs are contracts. Favor explicit types in:
  - public method signatures and public properties,
  - returned values (especially when nullability matters),
  - cross-assembly boundaries.
- **Why**: This improves readability, reduces refactor hazards, and makes nullability contracts reviewable.
- **Full treatment**: See section [4.2](<../4. Implicitly typed variables var/4.2. var vs explicit types readability refactoring.md>) for mentor-grade rules and trade-offs.

### 4. **Nested types are a visibility tool**

- **Remember**: Nesting is primarily about **encapsulation/cohesion**, not about “organizing files”.
- **Big pitfall**: instance nested types can accidentally capture and extend the lifetime of the outer instance.
- **Full treatment**:
  - taxonomy + access rules: section [6.1](<../6. Nested types/6.1. Nested types taxonomy class struct record interface enum delegate.md>)
  - static vs instance nesting + lifetimes: section [6.2](<../6. Nested types/6.2. static nested vs instance nested generics lifetimes.md>)
  - compiler-generated nested types (async/iterators/closures): section [6.3](<../6. Nested types/6.3. Compiler-generated nested types iterators async closures.md>)
  - file-local types vs nesting: section [6.4](<../6. Nested types/6.4. File-local types vs nested types.md>)

### 5. **Measure `dynamic` and allocation-heavy extensions**

- **Remember**:
  - `dynamic` can reduce inlining and add runtime binder costs; don’t put it in hot loops by default.
  - Fluent chains can allocate (iterators, closures, enumerators).
- **Full treatment**:
  - `dynamic` performance model: section [5.3](<../5. Dynamic typing/5.3. Performance CPU allocations call site caches.md>)
  - allocations/captures/LINQ-like patterns: section [3.2](<../3. Extension methods performance and deployment/3.2. Allocations captures LINQ-like patterns.md>)
  - profiling guidance: section [3.1](<../3. Extension methods performance and deployment/3.1. What the JIT sees static calls inlining.md>) and [5.3](<../5. Dynamic typing/5.3. Performance CPU allocations call site caches.md>)
