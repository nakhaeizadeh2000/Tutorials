## 1.5. Extension methods vs default interface methods (when each is appropriate)

1. **Capability model** (DIM puts behavior on the abstraction; extensions attach from outside)
2. **Versioning trade-offs** (DIM + override rules vs extension collisions)
3. **Performance and dispatch** (virtual/interface dispatch vs static call sites—think hot paths)

---

### 1. **Capability model**

**Definition**:

- **Extension method**: a **static** method callable with instance syntax when its namespace is imported. It **attaches behavior from the outside** and is opt-in via `using` (deep mechanics in sections [1.1](<./1.1. What extension methods are syntax sugar this parameter static container.md>) and [1.2](<./1.2. Invocation binding precedence instance vs extension.md>)).
- **Default interface method (DIM)**: a method body **defined on an interface**. It becomes part of the abstraction and can be inherited by implementers that do not provide an override.

**Architectural meaning**:

- **DIM** answers: “This behavior is part of the *contract* of the interface.”
- **Extension** answers: “This behavior is a *capability* we provide for callers that opt into it.”

#### When DIM is the better fit

- **You own the interface** and want to evolve its functionality without forcing every implementer to update immediately.
- The behavior is **universally valid** for all implementers (or can be expressed in terms of other interface members).
- You want the method to be discoverable on the interface without requiring `using` a specific namespace.

#### When extensions are the better fit

- You **do not own** the target type/interface (e.g., BCL types, third‑party libraries).
- The behavior is **contextual** (domain-specific) and should not be “baked into” the abstraction.
- You want **opt-in discoverability** by namespace (feature-area namespaces keep IntelliSense clean).

**Example: the same idea expressed both ways**

```csharp
namespace Demo;

public interface IHasName
{
    string? Name { get; }

    // DIM: part of the abstraction.
    bool HasName() => !string.IsNullOrWhiteSpace(Name);
}

public sealed class User : IHasName
{
    public string? Name { get; init; }
}

public static class HasNameExtensions
{
    // Extension: attaches from outside; opt-in via 'using Demo;' (or whatever namespace you choose).
    public static bool HasNameExt(this IHasName self)
        => !string.IsNullOrWhiteSpace(self.Name);
}

public static class Program
{
    public static void Main()
    {
        IHasName u = new User { Name = "Ada" };
        Console.WriteLine(u.HasName());     // DIM call
        Console.WriteLine(u.HasNameExt());  // extension call
    }
}
```

**Mentor guidance**:

- If you can truthfully say “every implementation should have this behavior”, prefer **DIM**.
- If the behavior is “nice to have” or domain-specific, prefer **extensions** in a feature namespace.

### 2. **Versioning trade-offs**

This is where teams get hurt in production if they treat DIM vs extensions as “just style”.

#### Extensions: collision and shadowing risks

Extensions are vulnerable to:

- **Instance-member shadowing**: a type later adds a real member with the same signature, and it wins (deep in section [1.4](<./1.4. Versioning adding instance methods and using graph changes.md>)).
- **`using` graph drift**: adding/removing imports changes candidate sets and can change binding or cause ambiguity (section [1.4](<./1.4. Versioning adding instance methods and using graph changes.md>)).

**What this means**:

- Publishing widely-imported extension namespaces is effectively publishing **ambient API**. That requires discipline (namespaces, naming, analyzers).

#### DIM: evolution and implementation constraints

DIM allows you to add behavior to an interface without immediately breaking all implementers *at the source level*, but there are constraints:

- The default implementation can only use what the interface exposes. If you need access to concrete state, DIM is a poor fit.
- Multiple interfaces can provide methods with the same signature; implementers may need explicit implementations or overrides to disambiguate.

**Mentor rule**:

- Use DIM to **evolve an interface you own** safely (add a *new method with a default implementation*), but be careful with:
  - public API compatibility promises,
  - diamond/ambiguity scenarios,
  - and keeping defaults semantically correct for all implementations.

#### “Which one is safer to publish?”

- For **public libraries**, DIM can be safer *when you own the interface* because it reduces reliance on `using` scopes and avoids extension shadowing by “new instance members”.
- Extensions can still be safe if you keep them:
  - in **narrow namespaces**,
  - with **specific names**,
  - and behind clear “capability” boundaries.

**Legacy pattern to avoid**:

- “We can’t change the interface, so we’ll just add a bunch of extensions everywhere.” This often creates a long-term maintainability tax: ambiguous calls, hidden coupling, and broken discoverability. If you own the interface, consider DIM (or a new interface version) instead.

### 3. **Performance and dispatch**

**The core performance reality**:

- **Extension calls** are **static calls**; they are typically easy for the JIT to inline when small and visible (see section [3.1](<../3. Extension methods performance and deployment/3.1. What the JIT sees static calls inlining.md>)).
- **DIM calls** are **interface dispatch** (virtual-like). The JIT can sometimes devirtualize, but interface dispatch is generally a harder optimization target than a direct static call.

**However**: in real systems, the dispatch difference is rarely your bottleneck compared to:

- allocations,
- I/O,
- cache misses,
- algorithmic complexity,
- and `IEnumerable<T>` pipelines.

**Where it matters**:

- In tight loops on hot paths (parsers, serializers, numeric code), a static call that inlines can be a real win.
- In high-level application code, prefer **clarity and correctness**. Pick the construct that matches the ownership and versioning model first.

**Performance note (allocations and closures)**:

- Extensions often accept delegates (`Func<>`, `Action<>`) for fluent APIs; captured lambdas can allocate closures (see section [3.2](<../3. Extension methods performance and deployment/3.2. Allocations captures LINQ-like patterns.md>)).
- DIM doesn’t magically avoid allocations; the default implementation can still allocate depending on what it does.

**Mentor recommendation**:

- Choose DIM vs extensions primarily by **ownership + contract semantics**.
- If you later discover a hot path, optimize with measurement and consider:
  - moving critical code to non-interface static helpers,
  - using `Span<T>`/`ReadOnlySpan<T>` where appropriate,
  - or providing specialized implementations.
