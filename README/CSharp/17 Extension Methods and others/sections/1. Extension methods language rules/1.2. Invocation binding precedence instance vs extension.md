## 1.2. Invocation, binding, and precedence (instance vs extension, extension vs extension)

1. **Instance methods win** (if applicable, instance members reduce extension candidates)
2. **Overload resolution + extension methods** (how the compiler builds the candidate set; “nearest” `using` scope)
3. **Generic extension methods** (type inference interactions; where ambiguity appears)

---

### 1. **Instance methods win**

**Definition**: When you write `receiver.M(...)`, the compiler **first** tries to bind to an **instance member** on the compile-time type of `receiver`. Only if no applicable instance member exists does it consider **extension methods**.

That rule is the root of many “nothing changed but behavior changed” bugs.

**Example: an instance member silently shadows an extension**

```csharp
namespace Demo;

public sealed class Widget
{
    // Imagine this is added in v2 of a library you consume.
    public string Normalize() => "instance";
}

public static class WidgetExtensions
{
    public static string Normalize(this Widget w) => "extension";
}

public static class Program
{
    public static void Main()
    {
        var w = new Widget();
        Console.WriteLine(w.Normalize()); // prints "instance" (instance wins)
    }
}
```

**When to use this knowledge**

- **Library evolution**: If you publish extensions against a type you don’t own, you must assume the owner might later add a real instance member with the same signature. This is why “cute” short names for extensions (e.g. `Add`, `Where`, `Select`) are collision-prone outside LINQ conventions.
- **Team design**: If your team owns the type, prefer an instance member when the behavior is part of the type’s core contract. Keep extensions for optional, opt-in capabilities.

**Common mistakes**

- **Assuming extensions are “less important” but still stable**: stability comes from *versioning discipline*, not from being an extension.
- **Forgetting compile-time type matters**: `IFoo foo = new Foo(); foo.Bar()` binds based on `IFoo`, not runtime type `Foo`.

**Good to know (how to force a specific call)**:

- If you want the extension no matter what, call it **as a static method**: `WidgetExtensions.Normalize(w)`. This is explicit and reviewable.

---

### 2. **Overload resolution + extension methods**

**Definition**: If no applicable instance method exists, the compiler:

1. Collects extension methods that are **in scope** (via `using`/global usings) and are **accessible**.
2. Filters them to those whose first parameter can accept the receiver (`this` parameter type compatibility).
3. Performs **normal overload resolution** across the remaining candidates (including generics, optional parameters, params, implicit conversions, etc.).

**The part mentors stress**: *your `using` directives participate in overload resolution*.

**Example: adding a `using` changes what method gets picked**

```csharp
namespace A;
public static class Extensions
{
    public static string Format(this int x) => $"A:{x}";
}

namespace B;
public static class Extensions
{
    public static string Format(this int x) => $"B:{x}";
}

// ---------------------------
// Call site:
using A;
// using B;

Console.WriteLine(123.Format()); // A:123
```

If you now add `using B;`, you can get:

- **Ambiguity** (compile error) if both candidates are equally good.
- Or a **different chosen method** if overload resolution finds a “better” match among a larger candidate set (this can happen with overloads that differ by parameter types).

**Trade-offs**

- **Pros**: Extensions allow *opt-in capabilities*—a key design tool for APIs (see section `2.1`).
- **Cons**: They introduce **non-local coupling**: a file-level `using` can change runtime behavior without changing the call site.

**Common mistakes**

- **Dumping extensions into broad namespaces** imported everywhere (global using “utility soup”).
- **Overloading too aggressively**: lots of overloads + lots of imported namespaces increases ambiguity and maintenance load.
- **Relying on “nearest using scope” folklore**: C# doesn’t pick extensions by “closest file”; it picks based on the formal candidate set + overload resolution. The practical “nearest” effect you feel is usually just “which namespaces are imported in this file”.

**Good to know (mitigations that scale)**

- **Use feature-area namespaces** instead of one mega `Extensions` namespace, so callers import what they mean.
- **Prefer explicit static calls** at critical call sites (hot paths, security-sensitive behavior, and places where collisions are plausible).
- **Avoid extensions on `object`**: they apply *everywhere* and make overload resolution noisy and fragile.

**Performance note**

- Overload resolution happens at **compile time**, not runtime. Runtime cost is about the chosen target method (allocations, interface dispatch, etc.), not about “how many candidates existed”.

---

### 3. **Generic extension methods**

**Definition**: Generic extensions participate in normal generic method type inference. This can be powerful, but it’s also where ambiguity and surprising inferred types appear.

**Example: generic inference can pick a different overload than you expect**

```csharp
public static class EnumerableLikeExtensions
{
    public static T? FirstOrDefault<T>(this IEnumerable<T> source)
        => source.FirstOrDefault();

    public static T FirstOrDefault<T>(this IEnumerable<T> source, T fallback)
        => source.FirstOrDefault() ?? fallback;
}

var xs = new List<string?> { null };

// Inference chooses T as string? here; fallback is string (non-null),
// which is fine because it converts to string?.
var value = xs.FirstOrDefault("fallback");
Console.WriteLine(value);
```

This is *correct*, but in more complex cases (especially with method groups, lambdas, and nullable flows) you can get “works but the inferred type is wider than intended”.

**Mentor guidance**

- **Keep generic extension surfaces small**: prefer 1–2 overloads with crisp semantics over a large matrix of optional parameters and generic overloads.
- **Be explicit at boundaries**: if a call site is subtle, help the compiler (and the reader) with an explicit type argument: `source.FirstOrDefault<MyType>()` or by introducing a well-named local variable with an explicit type.
- **Do not use `dynamic` to “fix” generic inference**. If you’re tempted, you’re probably mixing concerns (see section `5.2` for modern alternatives).

**Common mistakes**

- **Overload sets that differ only by `where` constraints**: humans struggle to predict which method is applicable; compilers are consistent but error messages can be painful.
- **Accidentally enabling boxing**: generic extensions on `IEnumerable<T>` that force `T` to `object` (or accept `IEnumerable` non-generic) can allocate/box in hot paths.

**Performance note**

- Generic extensions can be very fast when they keep work in generic code paths (JIT specializes many cases). The performance pitfalls tend to come from:
  - **Interface-based iteration** (`IEnumerable<T>` on hot paths) vs using `Span<T>`/`ReadOnlySpan<T>` where appropriate (deep dive in section `3.2`).
  - **Delegate parameters** that capture (closures allocate).
