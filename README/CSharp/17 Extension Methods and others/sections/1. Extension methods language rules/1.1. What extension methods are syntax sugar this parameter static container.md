## 1.1. What extension methods are (syntax sugar, `this` parameter, static container)

1. **IL shape** (static method + `[Extension]` attribute; no real instance member on the extended type)
2. **Accessibility and discovery** (namespace + `using`; the extended type must be in scope)
3. **First mental model** (you are calling a static helper with the receiver as the first argument—design and test accordingly)

---

### 1. **IL shape**

**Definition**: An *extension method* is a **static method** that the C# compiler lets you call using **instance-method syntax**. The extended type is **not modified**; there is no “real” member added to the type.

**What it compiles to** (conceptually):

```csharp
// Call-site (instance syntax)
var trimmed = "  hi  ".TrimFast();

// Compiler rewrites to (static call)
var trimmed2 = StringExtensions.TrimFast("  hi  ");
```

**Minimal, runnable example**:

```csharp
namespace Demo;

public static class StringExtensions
{
    public static string TrimFast(this string value) => value.Trim();
}

public static class Program
{
    public static void Main()
    {
        var s = "  hi  ";
        Console.WriteLine(s.TrimFast());
    }
}
```

**Important consequences**:

- **No polymorphism**: extension methods are **not virtual** and cannot be overridden. If you call an extension on a variable typed as an interface/base type, the call is still a static call chosen at compile time.
- **`this` is just the first parameter**: the receiver is passed as argument 0. That matters for **null** (see note below) and for **perf** (it’s typically as cheap as any static call).
- **No access to private members**: even if you write the extension method in the same assembly/namespace, it does not gain access to the type’s private state (unless you use reflection, which is a separate trade-off).

**Good to know (null receiver)**:

- Because it’s a static call, the receiver expression can be `null` at runtime and the extension method can still be invoked—**until you dereference** inside it.
- Prefer encoding intent with nullable annotations (covered deeply in section `1.3`): if `null` is acceptable, write `this string? value` and handle it deliberately.

**Performance note**:

- The call overhead is the same as a normal static call and is often **inlined** if the method is small and visible to the JIT. What typically hurts performance is what you do inside the extension (allocations, iteration, virtual calls), not “being an extension”.

---

### 2. **Accessibility and discovery**

**Definition**: Extension methods are in scope based on:

- **The namespace of the static class that contains them**, and
- **Whether that namespace is imported** in the calling file via `using ...;` (or global usings), and
- **Whether the receiver type is in scope** (you can’t extend a type you cannot reference).

**Key rule**: If the compiler doesn’t see the extension method in the candidate set, it doesn’t exist for that call site—even if the method is in your project.

**Example: discovery via `using`**

```csharp
// File A
namespace MyCompany.Text;

public static class StringExtensions
{
    public static bool IsBlank(this string? s) => string.IsNullOrWhiteSpace(s);
}

// File B
using MyCompany.Text;

Console.WriteLine("   ".IsBlank()); // true
```

**Trade-offs mentors care about**:

- **Discoverability vs noise**: putting everything into a catch‑all `Extensions` namespace makes IntelliSense noisy and increases name collision risk. Prefer **feature-area namespaces** (designed deeply in section `2.1`).
- **Hidden coupling**: a seemingly harmless `using` can change which method gets called (binding rules are treated deeply in section `1.2`). This becomes a production risk in large solutions.

**Common mistakes**:

- **“Why doesn’t my extension show up?”**
  - The containing namespace isn’t imported (or a different namespace is imported).
  - The method is not `public` (or the containing type isn’t accessible).
  - The method is not in a `static` class (required).
  - The first parameter is missing `this` (so it’s just a normal static method).
- **Extensions on `object`**: this pollutes all call sites, harms IntelliSense, and increases ambiguity. Many teams ban this via analyzers (see section `2.3`).

**Good to know (global usings)**:

- In modern .NET projects, `global using` can make extensions appear “everywhere”. This is powerful but increases the risk of silent binding changes; treat it as a library design decision, not a convenience trick.

---

### 3. **First mental model**

**The correct model**: “I’m calling a static helper, passing the receiver as the first argument.”

That model leads to good decisions:

- **Testing**: unit test it like any other static method—pure input/output where possible.
- **API design**: keep the receiver meaningful. If the receiver is merely a random parameter you wanted to put first, it’s often better as a normal static method (see section `2.2`).
- **Side effects**: extension methods that do I/O, lock, allocate heavily, or hide asynchronous work are easy to misuse because they *look* like “simple instance methods”. If you must do side effects, name it loudly (e.g., `SaveTo...`, `WriteTo...`, `ToXxxAsync`) and document it.

**Example: good vs questionable receiver choice**

```csharp
public static class StreamExtensions
{
    // Good: the receiver is the object being acted upon.
    public static async ValueTask CopyToFileAsync(
        this Stream source,
        string path,
        CancellationToken ct = default)
    {
        await using var destination = File.Create(path);
        await source.CopyToAsync(destination, ct);
    }
}

public static class QuestionableExtensions
{
    // Questionable: receiver is a "flag" that doesn't represent the domain object.
    public static bool IfTrueThen(this bool condition, Func<bool> compute) => condition && compute();
}
```

**Mentor rule of thumb**:

- Prefer extension methods when they provide **domain-fluent** operations on a type you don’t own (or when you intentionally want an opt‑in “capability” via `using`).
- Prefer instance members when behavior is **core to the type’s invariants** and should be discoverable without `using`.
- Prefer regular static helpers or local functions for **pure utilities** that don’t have a strong “receiver story”.

**Performance note (async)**:

- If you write async extensions that may complete synchronously, consider `ValueTask` to reduce allocations *only when it’s justified and you understand the trade-offs* (consumption rules, multiple awaits, etc.). Otherwise, use `Task` for simplicity and correctness.
