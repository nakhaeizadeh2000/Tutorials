## 1.4. Versioning and evolution (adding instance methods later; changing `using` graphs)

1. **Why extensions can silently stop applying** (a new instance method can shadow your extension for the same call shape)
2. **Public API discipline** (extensions as part of your library’s discoverability story; XML docs and namespaces)
3. **Team workflow** (code review rules for extension method additions—collision checks)

---

### 1. **Why extensions can silently stop applying**

**Definition**: Extension method calls are **bound at compile time** and are **always lower priority than instance members** (see section [1.2](<./1.2. Invocation binding precedence instance vs extension.md>)). That means a library upgrade can change which method `x.Foo()` binds to **without changing your call sites**.

There are two broad “silent change” classes:

- **Instance-member shadowing**: the extended type (or an interface it implements) gains a new instance method with the same name/signature shape as your extension.
- **Candidate-set drift**: the set of extension methods *in scope* changes (adding/removing a `using`, introducing a `global using`, adding a package that introduces an extension with the same signature, etc.).

#### Case A: instance member added later (classic breaking change)

```csharp
namespace Demo;

public sealed class Widget
{
    // v1: no Normalize() instance method
    // v2: library adds:
    public string Normalize() => "instance";
}

public static class WidgetExtensions
{
    // Your library shipped this earlier:
    public static string Normalize(this Widget w) => "extension";
}

public static class Program
{
    public static void Main()
    {
        var w = new Widget();
        Console.WriteLine(w.Normalize()); // "instance" (extension silently stops applying)
    }
}
```

**Mentor take**: shipping public extensions against types you don’t own is a **versioning bet**. You’re effectively reserving method names that the owner might want later.

#### Case B: `using` graph changes (silent ambiguity or changed “best” overload)

Even if the type never changes, importing a new namespace (or enabling a new global using) can:

- produce **ambiguity** (compile break), or
- introduce a “better match” overload and therefore change which method is selected.

**Good to know**:

- “Silent behavior change” via new extension overloads is less common than instance shadowing, but it happens in large solutions with shared utility libraries.
- This is one reason teams often prefer **feature-area extension namespaces** over “Utilities.Extensions imported everywhere” (deep design guidance in section [2.1](<../2. Extension methods design and testability/2.1. Designing fluent discoverable extensions.md>)).

**Performance note**:

- These are **compile-time** effects. The runtime cost is about the chosen target method, not about how many extensions exist.

### 2. **Public API discipline**

If you publish extensions as part of a reusable library, treat them as **first-class API surface**:

#### Namespaces are part of your API design

**Mentor rule**: Create namespaces that reflect a capability boundary.

- Good: `MyCompany.Text`, `MyCompany.Json`, `MyCompany.Http`
- Risky: `MyCompany.Extensions` (everything everywhere, maximum collision potential)

This matters because consumers “opt in” by adding `using ...;`. Importing one namespace should not drag in 200 unrelated extensions.

#### XML docs, examples, and nullability are not optional

- Extension methods are **discoverability-driven**: they show up in IntelliSense lists next to real instance members. If they are undocumented or have unclear semantics, you get misuse at scale.
- Always provide:
  - **Nullability annotations** that match reality (deep treatment in section [1.3](<./1.3. Extension methods and nullability nullable receivers.md>))
  - A brief **summary** that states side effects (I/O, locking, allocations, async)
  - Meaningful **parameter names** and cancellation tokens for async I/O

#### Versioning contract: avoid signature collisions proactively

**Prefer names that encode intent** rather than short, generic verbs in shared libraries.

- Risky in general-purpose libraries: `Add`, `Remove`, `Format`, `Normalize`, `ToJson`, `Map`, `Convert`
- Better: `ToInvariantNormalizedForm`, `WriteJsonTo`, `TryGetXxx`, `EnsureXxx`

You can still have short names in *domain-specific* namespaces where the meaning is constrained and collisions are less likely.

#### Legacy patterns to avoid

- **Extensions on `object`**: they effectively become “ambient methods” and create widespread ambiguity/noise.
- **Extensions that hide expensive work** behind innocent names (e.g. `ToXxx()` that does network I/O). Make side effects explicit.
- **Reflection-based scanning for extensions** at runtime as a “plugin system”. It’s fragile under trimming/AOT (see section [3.3](<../3. Extension methods performance and deployment/3.3. Trimming AOT reflection surprises.md>)).

### 3. **Team workflow**

This is the practical part that prevents “mystery behavior changes” months later.

#### Code review rules (high-signal, low-friction)

- **Namespace review**: Is the extension placed in the narrowest reasonable feature namespace?
- **Collision review**:
  - Search for an existing instance member with the same signature on the extended type (and its interfaces).
  - Search your solution for other extensions with the same name/shape on the same receiver type.
- **Nullability contract review**: Is the receiver annotated truthfully (`this T` vs `this T?`) and does the implementation match?
- **Overload discipline**: Is the overload set small and unambiguous? Optional parameters + multiple overloads can create “best overload” surprises.
- **Side effects & async**:
  - Async extensions must accept `CancellationToken` for I/O.
  - Avoid capturing `SynchronizationContext` assumptions; library code should be context-agnostic (in modern .NET, `await` does not capture by default unless a context exists, but you still shouldn’t depend on it).

#### Automated guardrails (recommended)

If your repo uses analyzers, consider rules like:

- Ban extensions on `object`.
- Ban extensions in a catch-all namespace.
- Require XML docs on public extensions.
- Require explicit nullability annotations and disallow `!` inside public extensions except with a justification.

See section [2.3](<../2. Extension methods design and testability/2.3. Testing analyzers team conventions.md>) for where analyzers belong in team conventions and how to use them without creating “warning fatigue”.

#### “Breaking change” mindset for libraries

**Guideline**: Adding a new extension method to a commonly imported namespace can be a **source-compatible but behavior-changing** update for consumers (due to overload resolution shifts).

Treat these additions like you would treat:

- adding a public member to an interface,
- adding a new overload that might become a better match,
- or adding a new global using.

When in doubt, keep the extension in a **more explicit namespace** and let consumers opt in deliberately.
