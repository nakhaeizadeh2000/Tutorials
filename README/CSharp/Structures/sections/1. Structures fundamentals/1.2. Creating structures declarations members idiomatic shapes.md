## 1.2. Creating structures: declarations, members, and idiomatic shapes

1. **Declaration forms** (`struct`, `readonly struct`, `record struct`; when each is appropriate)
2. **What belongs in a struct** (small, cohesive value; stable equality; minimal mutation surface)
3. **What usually does *not* belong** (large mutable state, long-lived identity, heavy inheritance-like design)

---

### 1) **Declaration forms** (`struct`, `readonly struct`, `record struct`; when each is appropriate)

**Definition and intent**

- **`struct`**: a value type with value semantics by default. Use when you want a *small, self-contained value* that is cheap to copy and has no identity.
- **`readonly struct`**: a struct whose instance fields cannot be mutated by instance members. Use when the value should be immutable and you want to reduce accidental mutation and some defensive-copy patterns. (Full defensive-copy mechanics are covered in **section 4.1**; here we focus on choosing the shape.)
- **`record struct`**: a value type whose *primary purpose* is “data with value-based equality”. The compiler generates `Equals`, `GetHashCode`, and `ToString` with value semantics. Use when you want a *value DTO-like type* and the generated equality is correct for your domain.
- **`readonly record struct`**: record struct + immutability by default. Often the best default for “true value objects”.

**When to choose which**

- **Prefer `readonly record struct`** when:
  - The type is a *pure value object* (e.g., `Money`, `Temperature`, `RgbColor`) and equality is structural.
  - You want a safe, maintainable default (immutability + correct equality).
- **Prefer `readonly struct`** when:
  - You need full control over equality/hashing or you want to avoid record-generated `ToString` formatting.
  - You’re implementing a performance-critical primitive-like value with carefully designed APIs.
- **Prefer plain `struct`** when:
  - The type is inherently mutable *and stays private/internal* (e.g., inside a tight algorithm). Public mutable structs are a common source of “impossible” bugs; see **section 5.2**.
- **Prefer `class`** (not a struct) when:
  - The type has identity, is long-lived, is shared, or is large/mutable (deep guidance in **section 3.1** and **section 3.2**).

**Common mistakes**

- **Using `record struct` for “identity-based” entities**: record equality is value-based; if your type represents a database row with identity, that’s usually a `class` (or a separate immutable key value object).
- **Assuming `readonly struct` makes deep immutability**: it only prevents mutating *its own fields*. If a field is a reference (e.g., `string`, arrays, `List<T>`), the reference can point to mutable state.
- **Publishing a mutable struct API**: consumers get copies; mutations often mutate a copy rather than the original (see **section 5.2**).

**Focused example: value object as `readonly record struct`**

```csharp
using System;

public readonly record struct Meter(double Value)
{
    public static Meter From(double value)
        => value >= 0 ? new Meter(value) : throw new ArgumentOutOfRangeException(nameof(value));

    public override string ToString() => $"{Value} m";
}

public static class Demo
{
    public static void Main()
    {
        var a = Meter.From(1.5);
        var b = Meter.From(1.5);
        Console.WriteLine(a == b); // True (value equality)
        Console.WriteLine(a);      // "1.5 m"
    }
}
```

**Performance note**

- `record struct` generates equality/hashing that *touches all fields*. For large structs, that may be expensive; see **section 3.2** for “big struct” costs. For hot paths, implement a cheaper hash/equality if your domain allows it (but keep it correct).

### 2) **What belongs in a struct** (small, cohesive value; stable equality; minimal mutation surface)

**Rule of thumb**

A struct should represent a **single concept** with **value semantics**, be **small**, and have a **stable meaning** over time.

**Good candidates**

- Numeric-like values and units (`Duration`, `Angle`, `Percent`) with validation at construction.
- Coordinates (`Point2D`), ranges (`IndexRange`), colors (`Rgb`), IDs that are purely value-based (`OrderId` wrapping a `Guid`).
- “View” types over existing data when stack-only is appropriate (`Span<T>`-style patterns; deep dive in **section 4.2**).

**Design practices mentors insist on**

- **Keep fields minimal and cohesive**: fewer fields → cheaper copies → fewer bugs.
- **Prefer immutability** (`readonly struct` / `readonly record struct`) for public types.
- **Implement equality deliberately**:
  - If you’re not using record structs, implement **`IEquatable<T>`** and override `GetHashCode`/`Equals(object?)`.
  - Keep equality consistent with domain meaning (e.g., `Money(1.00 USD)` equals `Money(1 USD)`? Decide).
- **Make `default` intentional**:
  - If `default` is valid (e.g., `Meter(0)`), document it and make it safe.
  - If `default` is invalid, design a detectable sentinel/validation strategy (deep dive in **section 2.2**).

**Focused example: explicit equality without record**

```csharp
using System;

public readonly struct Rgb : IEquatable<Rgb>
{
    public byte R { get; }
    public byte G { get; }
    public byte B { get; }

    public Rgb(byte r, byte g, byte b) => (R, G, B) = (r, g, b);

    public bool Equals(Rgb other) => R == other.R && G == other.G && B == other.B;
    public override bool Equals(object? obj) => obj is Rgb other && Equals(other);
    public override int GetHashCode() => HashCode.Combine(R, G, B);

    public static bool operator ==(Rgb left, Rgb right) => left.Equals(right);
    public static bool operator !=(Rgb left, Rgb right) => !left.Equals(right);
}
```

**Good to know**

- `HashCode.Combine(...)` is the modern, readable default for combining fields. Avoid legacy custom hash mixing unless you have a measured reason.

### 3) **What usually does *not* belong** (large mutable state, long-lived identity, heavy inheritance-like design)

**Avoid in structs**

- **Large structs** (copy cost dominates quickly). If the type gets large or frequently passed around, prefer `class` or redesign the data layout. Deep performance treatment: **section 3.2**.
- **Mutable public structs** (copying makes mutation unintuitive). Deep bug patterns: **section 5.2**.
- **Types that “own resources”**:
  - `IDisposable`-like ownership in a struct is easy to misuse via copies (double-dispose patterns). If you *must* do it, make it stack-only (`ref struct`) or use a class. Prefer safe ownership patterns (e.g., `SafeHandle`, `using` with class wrappers).
- **Polymorphic hierarchies**:
  - Structs do not participate in class inheritance. Trying to emulate inheritance via interfaces often introduces boxing and virtual dispatch. Deep dive: **section 3.3**.

**Legacy patterns to avoid (and modern replacements)**

- **Non-generic collections** (`ArrayList`, `Hashtable`) cause boxing and runtime casts.
  - **Prefer** `List<T>`, `Dictionary<TKey, TValue>`, `ImmutableArray<T>` (when appropriate), or specialized collections.
- **`IComparable` (non-generic)**:
  - **Prefer** `IComparable<T>` to avoid boxing and improve type safety.

**Performance note**

- If a struct is used through a **non-generic interface** in a hot path, it will typically **box** (allocate). Use generic constraints (e.g., `where T : struct, IEquatable<T>`) and generic APIs to keep operations allocation-free (deep dive: **section 3.3**).
