## 4.1. `readonly struct`: what it guarantees (and what it doesn’t)

1. **What it prevents** (mutating instance fields through instance members)
2. **Defensive copies** (why they happen; how readonly can reduce them; how `readonly` members help)
3. **API hygiene** (prefer `readonly` members; avoid exposing setters that undermine value semantics)

---

### 1) **What it prevents** (mutating instance fields through instance members)

**Definition.** `readonly struct` tells the compiler and the runtime-facing tooling: “instances of this type are treated as immutable from the outside.” Concretely:

- Inside an **instance member**, `this` is treated as `in` (read-only reference).
- You cannot mutate **instance fields** from instance members (unless you explicitly opt into mutation via `mutable`-like designs, which C# intentionally doesn’t support directly).
- You can still mutate **static** fields (because they aren’t part of the instance).

**What it does *not* guarantee**

- It does **not** guarantee deep immutability. If your struct contains a reference field (e.g., `string`, array, `List<T>`, custom class), the reference itself can be readonly while the referenced object may still be mutable.
- It does **not** prevent mutation via **unsafe** code or reflection-based tricks (don’t design for adversarial reflection).

**When to use**

- Public value objects that should behave like values: IDs, coordinates, money, ranges.
- Types used as dictionary keys or set members (immutability is essential; see `5.1` and `5.2` for pitfalls).
- Anytime you want to reduce “accidental mutation of a copy” bugs and make your API easier to reason about.

**Trade-offs**

- Adds constraints: some patterns that rely on mutating `this` (e.g., “builder struct”) are no longer possible without redesign.
- If you actually need mutation (especially in performance-critical code), keep a **mutable internal struct** private to an algorithm and expose an immutable public type.

**Common mistake**

- Marking the type `readonly` but exposing mutation through reference fields (e.g., `readonly struct S { public List<int> Items { get; } }`). Consumers can still mutate `Items`. If you want immutability, use immutable collections, or expose read-only views (`IReadOnlyList<T>`) and still be explicit about the underlying mutability.

**Good to know**

- `readonly record struct` is often the “best default” for value objects when record semantics match your domain (see section `1.2` for choosing shapes).

---

### 2) **Defensive copies** (why they happen; how readonly can reduce them; how `readonly` members help)

**Problem.** When you call an instance member on a struct through a *read-only* reference, the compiler/JIT must preserve the rule “the original value cannot be mutated.” If the instance member might mutate `this` (or the compiler can’t prove it won’t), the runtime may operate on a **copy** instead. This is called a **defensive copy**.

Defensive copies matter because they:

- **Increase CPU** (copying work)
- **Increase memory bandwidth pressure** (big structs)
- Can create subtle behavioral differences if you expected mutation to “stick” (it won’t—because it’s a copy)

**Where read-only references appear**

- `in` parameters
- `readonly` fields
- `ref readonly` returns
- When a struct is a field on a `readonly struct`, that field is effectively read-only

**How to reduce defensive copies**

- Prefer making the whole type `readonly struct` when it’s conceptually immutable.
- Mark non-mutating instance members explicitly as `readonly` (so the compiler can call them without copying when `this` is readonly).

**Focused example: `readonly` members**

```csharp
using System;

public struct Counter
{
    private int _value;

    // Not marked readonly: compiler must assume it could mutate this.
    public int Value => _value;

    // Marked readonly: safe to call through readonly references without copying.
    public readonly int ValueReadonly => _value;

    public void Increment() => _value++;
}

public static class Demo
{
    public static void Main()
    {
        var c = new Counter();
        c.Increment();

        UseIn(in c);
    }

    static void UseIn(in Counter counter)
    {
        // Accessing Value may force a defensive copy in some scenarios/versions,
        // because the member isn't declared readonly.
        Console.WriteLine(counter.Value);

        // Declared readonly; can be invoked directly on readonly refs.
        Console.WriteLine(counter.ValueReadonly);
    }
}
```

**Mentor guidance**

- In *public* APIs, either:
  - Make the struct `readonly`, and keep it truly immutable; or
  - If it must be mutable, keep it small and avoid exposing it broadly (see `5.2`).
- For performance-sensitive libraries, consider adding `readonly` to members that do not mutate state even if the struct itself is not readonly. This is a maintainability win too: it documents intent.

**Performance note**

- Defensive copies are often “invisible” in code review. If you have a large struct that’s frequently passed as `in` and you see regressions, inspect member readonlyness and measure with BenchmarkDotNet.
- Passing by `in` is not automatically faster; for small structs it can be worse due to indirection. Full trade-offs are in `3.2`.

### 3) **API hygiene** (prefer `readonly` members; avoid exposing setters that undermine value semantics)

**Rules mentors enforce**

- **No public setters** on public value objects. If a type is conceptually a value, it should not be “half mutable.” Prefer construction-time validation and “with”-style creation (record structs) or explicit methods returning a new value.
- Keep the struct **small** and cohesive. If it grows, you’ll pay in copying, hashing, and equality checks (see `3.2`).
- Implement equality deliberately:
  - `readonly record struct` gives you structural equality by default.
  - Otherwise implement `IEquatable<T>` (see examples in section `1.2`).
- If it’s a dictionary key: **must be immutable** and have stable hash code for its entire lifetime. Never mutate a value used as a key.

**Legacy/anti-pattern callout**

- “Mutable struct as property on a class” is a classic pitfall:
  - `obj.Point.X++` usually mutates a copy (deep bug patterns in `5.2`).
  - Modern replacement: make `Point` immutable and assign a new point: `obj.Point = obj.Point with { X = obj.Point.X + 1 };` (or `obj.Point = obj.Point.IncrementX();`).
