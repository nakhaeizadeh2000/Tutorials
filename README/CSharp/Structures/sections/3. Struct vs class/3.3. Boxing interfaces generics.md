## 3.3. Boxing, interfaces, and generics (where structs silently allocate)

1. **Boxing triggers** (to `object`, to non-generic interfaces, to `System.ValueType`, and some `params`/formatting paths)
2. **Avoiding boxing** (generic APIs, `IEquatable<T>`, avoiding non-generic collections, careful logging/formatting)
3. **Hot path rule** (if it boxes, it allocates; if it allocates, it can dominate CPU via GC under load)

---

### 1) **Boxing triggers** (when a value type becomes an object)

**Definition.** **Boxing** converts a value type (`struct`) into a reference type by allocating a new object on the managed heap and copying the struct’s bits into that object. The runtime then treats the value via an `object` reference (or interface reference).

**Why it exists**
- The CLR’s `object` model requires reference types for polymorphism, metadata, and uniform handling.
- Value types are not objects, so when you need “an object,” the runtime boxes (unless the call is generic and can stay unboxed).

**The most common boxing triggers**
- **To `object` / `System.ValueType`**:
  - `object o = myStruct;`
  - `ValueType v = myStruct;`
- **To non-generic interfaces**:
  - `IComparable c = myStruct;` (boxes)
  - `IFormattable f = myStruct;` (boxes)
  - `IEnumerable e = myStructEnumerable;` (struct enumerator boxed)
- **To an interface when the compile-time type is the interface** (even if the runtime value is a struct):
  - `IDisposable d = myStructDisposable;`
- **Params / formatting paths** (depends on overload selection):
  - `string.Format("{0}", myStruct)` often boxes unless an overload exists for the exact type or the compiler can keep it generic.
  - `Console.WriteLine(object)` boxes; `Console.WriteLine(int)` does not.
- **Non-generic collections** (`ArrayList`, `Hashtable`) store items as `object` -> boxing.

**What does *not* necessarily box**
- **Generic methods where `T` stays as `T`**:
  - `static void Log<T>(T value) { ... }` called as `Log(myStruct)` does not box *for the call*.
- **Generic interfaces used via generic type**:
  - `IEquatable<MyStruct>` does not box when called directly (but boxing can still happen if you upcast to `object` or non-generic interfaces).

**Minimal example: boxing and its absence**

```csharp
using System;

public readonly struct S
{
    public int X { get; }
    public S(int x) => X = x;
    public override string ToString() => $"S({X})";
}

public static class Demo
{
    static void TakesObject(object o) => Console.WriteLine(o);
    static void TakesGeneric<T>(T value) => Console.WriteLine(value);

    public static void Main()
    {
        var s = new S(123);

        TakesObject(s);  // boxes
        TakesGeneric(s); // no boxing for passing; still formats for output
    }
}
```

**Performance note**
- Boxing creates **GC pressure** and can also increase CPU due to allocation/collection.
- Boxing in a hot loop is a classic “death by a thousand allocations.”
- Boxing also changes **identity semantics**: each boxing creates a distinct object, even if the underlying values are equal.

**Good to know**
- The full value-semantics vs object-identity picture is in section `1.1`.
- The “primitive types are structs” angle (so boxing is everywhere) is in section `1.3`.

### 2) **Avoiding boxing** (modern C# 15 patterns)

**Principle.** Boxing happens when your API *forces* a value type into `object` or a non-generic interface. Avoid those shapes in hot paths.

#### Prefer generic collections and interfaces
- **Avoid**: `ArrayList`, `Hashtable`, `IEnumerable` (non-generic), `IComparable`
- **Prefer**: `List<T>`, `Dictionary<TKey, TValue>`, `IEnumerable<T>`, `IComparable<T>`

#### Implement `IEquatable<T>` for struct equality
If your struct is used as a key or compared frequently, implement `IEquatable<T>` to avoid virtual dispatch and reduce overhead.

See section `1.2` for the canonical equality/hashing pattern.

#### Keep APIs generic when you can
If you control the API surface, accept `T` (generic) rather than `object`.

```csharp
using System;
using System.Collections.Generic;

public readonly struct OrderId : IEquatable<OrderId>
{
    public Guid Value { get; }
    public OrderId(Guid value) => Value = value;
    public bool Equals(OrderId other) => Value == other.Value;
    public override bool Equals(object? obj) => obj is OrderId other && Equals(other);
    public override int GetHashCode() => Value.GetHashCode();
}

public static class Demo
{
    public static void Main()
    {
        var map = new Dictionary<OrderId, int>();
        map[new OrderId(Guid.NewGuid())] = 1; // no boxing
    }
}
```

#### Be careful with interface-typed variables
Even if a struct implements an interface, **storing it in an interface-typed variable** will box:

```csharp
using System;

public readonly struct S : IDisposable
{
    public void Dispose() { }
}

public static class Demo
{
    public static void Main()
    {
        S s = new();
        IDisposable d = s; // boxing allocation
        d.Dispose();
    }
}
```

If you need the behavior in a polymorphic way, prefer:
- A **class** (identity/polymorphism is a better fit), or
- A **generic** constraint (`where T : IDisposable`) in performance-sensitive code (but be careful: if you store `T` into `IDisposable`, you reintroduce boxing).

#### Logging/formatting: choose overloads that don’t force boxing
- Prefer structured logging APIs that accept strongly-typed arguments without `params object[]` allocations (depends on the logger).
- Avoid passing value types through `object` just to call a convenience method.
- When you need custom formatting, implement `ToString()` (non-allocating itself, but it can allocate when building strings) and keep it simple.

**Legacy/deprecated guidance**
- **Avoid non-generic `IComparable`**: it requires `object` and often boxes.
- **Avoid `string.Format` / `params object[]` patterns in hot paths**: many usages allocate arrays and box values. Prefer interpolated strings for readability in non-hot code; for hot code prefer span-based formatting patterns (beyond this section’s scope).

### 3) **Hot path rule** (if it boxes, it allocates; if it allocates, it can dominate CPU via GC under load)

**Mentor rule.** If your code runs often (per-request, per-message, per-frame), treat boxing like a bug until proven otherwise.

**How boxing becomes a scalability issue**
- A few allocations per operation may be fine in desktop apps, but in servers it multiplies by throughput and concurrency.
- Allocation rate drives **Gen0 frequency**, which drives CPU. Under load, that reduces throughput and increases tail latency.

**What to do**
- Design APIs so the common path is **generic and non-boxing**.
- Keep structs **small and immutable** (see sections `3.2` and `4.1`) so they’re cheap even when copied.
- If you truly need interface polymorphism with many implementations, consider using a **class hierarchy** or a **discriminated union pattern** (often via `record` classes) rather than “interfaces over structs.”

- `3.2` for how “big structs” and `in`/temporaries interact with perf in hot paths.
- `5.2` for production bugs that come from mixing mutation + copying + boxing surprises.
