## 2.1. Struct constructors: parameterless, parameterized, and initialization rules

1. **Why `default` exists** (you can always get a zeroed struct; your API must tolerate it or block it intentionally)
2. **Parameterless constructors** (what modern C# allows; when to use them; why they don’t remove `default(T)`)
3. **Field/property initialization rules** (ensuring all fields are definitely assigned; avoiding “half-initialized” designs)

---

### 1) **Why `default` exists**

**Definition.** `default(T)` for a value type is the “all-zero bits” value. This is a *runtime and CLR invariant*: any `struct` can be created in the default state via:

- `default(MyStruct)`
- `new MyStruct()` (still possible even if you define a parameterless ctor; this expression calls the parameterless ctor, but **`default(MyStruct)` remains possible**)
- `new MyStruct[n]` (array elements start as `default`)

**Why the runtime requires it**
- **Generic code** must be able to create a `T` without knowing anything about it.
- **Arrays** and low-level memory operations assume “zero-init” semantics for safety.
- **Interop/serialization** frameworks may materialize a struct without calling your preferred constructor.

**Mentor rule.** “Your API must tolerate `default` or detect it.” That is not optional for structs.
- If “all-zero” is a valid value in your domain, make it behave correctly.
- If it’s invalid, make invalidity **cheaply detectable** and validate at boundaries (deep dive: section `2.2`).

**Common mistakes**
- **Assuming invariants enforced only in constructors**. Someone can always obtain `default(T)` and bypass them.
- **Throwing in getters when `default`**. This often pushes exceptions into hot paths and makes innocent operations (like logging or serialization) hazardous.

**Performance note**
- `default(T)` is essentially free.
- Re-checking invariants on every property access is not; validate once at the boundary (parsing, DTO mapping, API entry) and keep hot-path code simple.

---

### 2) **Parameterless constructors**

**Modern C# allows parameterless struct constructors**, but they do **not** remove `default(T)`.

**What a parameterless struct ctor is good for**
- Providing a **non-zero “preferred default”** when users write `new MyStruct()` in application code.
- Establishing “nice ergonomics” for developers while acknowledging that `default(MyStruct)` can still exist (especially in generics and arrays).

**What it does *not* guarantee**
- It does not prevent `default(MyStruct)` from existing.
- It does not guarantee the constructor is called in all creation paths (e.g., `default`, array initialization).

**When to use it**
- When your type has a sensible conventional value (e.g., `Angle.Zero`, `Duration.Zero`, a default comparer-like configuration).
- When you can still define semantics for `default` (either valid or detectably invalid).

**Focused example: “preferred default” vs `default(T)`**

```csharp
using System;

public readonly struct TemperatureC
{
    public double Value { get; }

    // Preferred "new TemperatureC()" value (application code ergonomics)
    public TemperatureC() : this(20.0) { }

    public TemperatureC(double value) => Value = value;

    public override string ToString() => $"{Value:0.##} °C";
}

public static class Demo
{
    public static void Main()
    {
        var a = new TemperatureC();              // 20 °C
        var b = default(TemperatureC);           // 0 °C (all-zero bits)

        Console.WriteLine(a);
        Console.WriteLine(b);
    }
}
```

**Good to know**
- If “0” is *not* a valid temperature in your domain (or `0` is meaningless), then `TemperatureC` is a bad example for that domain—choose a sentinel strategy (section `2.2`) or use a class.

### 3) **Field/property initialization rules**

Struct initialization rules exist to prevent “half-initialized” values when calling constructors. In C#:
- A struct constructor must ensure **all instance fields are definitely assigned** before returning.
- Field initializers are allowed in modern C#, but you still must satisfy definite assignment rules.

**Mentor guidance: avoid tricky partial state**
- Prefer **immutable** designs (`readonly struct` + get-only properties).
- Keep the number of fields small and cohesive (section `1.2`).
- Don’t mix “sometimes-initialized” fields with public setters; you’ll create states that are hard to reason about and hard to validate.

**Recommended patterns**
- **Single validating constructor** that assigns all fields.
- Optional **factory methods** (`TryCreate`, `Parse`, `FromX`) when validation can fail (section `2.2`).
- Use `init` setters sparingly on structs: they create a “mutable during initialization” surface and can amplify copy surprises when used on properties/collection elements (see pitfalls in `5.2`).

**Example: “valid states only” with a single ctor**

```csharp
using System;

public readonly struct Percent
{
    public int Value { get; } // 0..100

    public Percent(int value)
    {
        if ((uint)value > 100u)
            throw new ArgumentOutOfRangeException(nameof(value), "Percent must be 0..100.");
        Value = value;
    }

    public override string ToString() => $"{Value}%";
}
```

**Performance note**
- Argument validation is great at the boundary; avoid repeating it inside tight loops.
- If you need “unchecked” construction for trusted internal code, use a private constructor or internal `UnsafeCreate` factory and keep it out of public surface area.
