## 4.2. `global using` (project-wide imports) and when to use it

1. **Why it exists** (reduce repetition across many files)
2. **Best practice** (keep global usings small and boring; avoid “magic” imports that hide dependencies)
3. **Build and maintenance** (global usings affect compilation; be intentional in libraries)

### 1. **Why it exists**
`global using` makes a `using` directive apply to **every file in the compilation** (project). It exists to reduce repetition and churn in large codebases where the same imports appear everywhere.

Typical targets for global usings:
- **Common BCL namespaces** used in most files (e.g., `System`, `System.Collections.Generic`).
- **Your project’s “core” abstractions** that are genuinely ubiquitous (e.g., `Company.Product.Abstractions`).
- **Test projects**: frameworks like xUnit/NUnit often justify a few global usings to reduce boilerplate.

**Good to know**
- The SDK can generate **implicit global usings** (modern default in many templates). This is convenient, but you should still be intentional about additional ones you add.
- `global using` is a compile-time feature; it doesn’t change runtime behavior.

#### Minimal, runnable example (global usings live in one place)

```csharp
// File: GlobalUsings.cs (any name works)
global using System;
global using System.Collections.Generic;
```

```csharp
// File: Program.cs
// No `using` lines needed here because they are global.
Console.WriteLine(new List<int> { 1, 2, 3 }.Count);
```

### 2. **Best practice**
**Make global usings “boring” and predictable.** The more “magic” you introduce, the harder onboarding, code review, and debugging become.

Recommended approach (mentor-grade rules):
- **Prefer a dedicated file** (commonly `GlobalUsings.cs`) at the project root so global imports are discoverable.
- **Keep the set small**: treat each addition like adding a public dependency—ask “does *most* of the project need this?”
- **Avoid domain-specific globals** that obscure important dependencies:
  - If only a few files need `System.Text.Json`, keep it local to those files.
  - If only one feature area needs `Company.Product.Payments`, keep it in that feature’s files.
- **Avoid global aliases that create a mini-language**. If you must use global aliases, do it sparingly and document the convention in section **5.2**.

**Common mistakes**
- **Spooky action at a distance**: adding one global `using` changes compilation of many files (especially extension method availability). This can cause surprising overload/extension binding changes. See section **4.1** and **7.2**.
- **Hiding architectural boundaries**: a global import can make it look like “everything depends on everything”. If you care about layering, don’t paper over it with globals—enforce it with project structure/analyzers (covered elsewhere; see **8.1**).

### 3. **Build and maintenance**
`global using` affects **compilation context**:
- **Name lookup & candidate sets**: more usings can expand the set of types and extension methods in scope, increasing ambiguity risk.
- **Build determinism**: when a global using changes, many files might effectively recompile because the compilation environment changed.

**Performance note**
- The runtime doesn’t get faster or slower. The “performance” cost is usually **human performance** (surprise dependencies) and **build-time** overhead in very large solutions. Optimize for clarity first; treat massive global-using sets as a code smell.

**Modern guidance**
- Prefer **file-scoped namespaces** (section **2.2**) + a **small, explicit global using set**.
- For libraries, be extra conservative: consumers reading examples/docs benefit from explicit `using` statements that show dependencies.
