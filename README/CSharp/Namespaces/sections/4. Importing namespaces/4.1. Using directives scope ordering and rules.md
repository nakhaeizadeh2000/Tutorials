## 4.1. `using` directives: file scope, namespace scope, and ordering

1. **Where `using` applies** (top-of-file; inside `namespace {}`; `global using` for project-wide)
2. **Style guidance** (consistent ordering; minimize noise; prefer analyzer-enforced formatting)
3. **Correctness gotchas** (ambiguous type names; extension method selection changes)

### 1. **Where `using` applies**
In modern C# you can import names in three main ways:

- **File scope `using`** (most common):
  - Placed at the top of a file (before any type declarations).
  - Applies to the entire file.
- **Namespace scope `using`** (only with block-scoped namespaces):
  - Placed *inside* `namespace X { ... }`.
  - Applies only within that namespace block.
  - Not compatible with file-scoped namespaces because there is no enclosing `{ ... }` block.
- **`global using`** (project scope):
  - Declared once (usually in a single “Usings” file).
  - Applies across the project compilation.
  - Covered in depth in section **4.2**.

**Good to know**
- The compiler “sees” a file as a compilation unit. Imports affect **name lookup** and (for extension methods) the candidate set for method binding.
- A `using` directive does **not** change runtime behavior by itself; it changes which symbols you can refer to unqualified and which candidates are considered.

#### Minimal example (file vs namespace scoped using)

```csharp
// Demonstrates that namespace-scoped `using` only works with block-scoped namespaces.

using System;

namespace Demo.BlockScoped
{
    using System.Text; // Only affects code inside this namespace block.

    public static class Example
    {
        public static void Run()
        {
            var sb = new StringBuilder();
            sb.Append("ok");
            Console.WriteLine(sb.ToString());
        }
    }
}
```

### 2. **Style guidance**
Your `using` policy is a codebase-wide readability decision. The goal is **predictability**: readers should quickly know where a type likely comes from and how to make a file compile.

- **Prefer file-scoped namespaces** (`namespace X;`) and **top-of-file usings** for most codebases (see section **2.2**).
- **Keep usings minimal**:
  - If a file uses exactly one type from some namespace and the type is uncommon, consider fully qualifying it instead of importing a whole namespace.
  - For common BCL namespaces (`System`, `System.Collections.Generic`, etc.), importing is usually fine.
- **Let analyzers/formatters enforce consistency**:
  - Prefer `.editorconfig` + dotnet formatters/analyzers (Roslyn) rather than informal “style by review”.
  - Consistency avoids “diff noise” and reduces cognitive load.

**Recommended conventions (typical modern default)**
- Sort usings:
  - `System.*` first, then others.
  - Groups separated by a blank line.
- Prefer **explicit** usings over relying on implicit usings when teaching/learning; in production, implicit usings can be fine but should be understood (see section **4.2** for global/implicit import discipline).

**Mentor note**
- A surprising number of “architecture problems” are really “searchability problems”. Overly broad usings and heavy global usings make it harder to grep and to understand dependencies.

### 3. **Correctness gotchas**
`using` directives can change which code compiles and which method is called.

#### Gotcha A: ambiguous type names
If two namespaces both contain `Widget`, importing both can break compilation:

```csharp
using LibA;
using LibB;

// error CS0104: 'Widget' is an ambiguous reference between 'LibA.Widget' and 'LibB.Widget'
Widget x = new();
```

**Fix options**
- **Prefer an alias** when the ambiguity is frequent or the names are inherently colliding (see section **5.1**):

```csharp
using AWidget = LibA.Widget;
using BWidget = LibB.Widget;
```

- **Fully qualify** at the usage site when it’s rare:

```csharp
var x = new LibA.Widget();
```

#### Gotcha B: extension method selection changes
Extension methods are only considered if the namespace containing the static extension class is imported.

- Adding a `using` can cause a previously-compiling call to bind to a **different extension method** (or become ambiguous).
- This is a correctness and maintainability risk, especially in large solutions where new packages are added.

**Good to know**
- Extension method lookup rules are subtle. The key practical guidance: keep extension method namespaces **tight and intentional**, and be conservative with global usings that import extension-heavy namespaces. Section **7.2** has production pitfalls and how to debug them.

**Performance note**
- The runtime cost is the cost of the final method that gets called. The main risk here is calling the *wrong* method (allocations, async scheduling, culture-sensitive formatting, etc.) because a new `using` changed binding.
