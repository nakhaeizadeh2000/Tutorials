## 5.1. Alias a namespace or a type

1. **Resolve collisions** (two `JsonSerializer`, two `Task`, etc.)
2. **Clarify intent** (make domain types explicit without long fully-qualified names)
3. **Maintainability** (aliases are local contracts; keep them short and meaningful)

### 1. **Resolve collisions**
**A `using` alias is the most explicit way to resolve name collisions without forcing fully-qualified names everywhere.**

Common collision scenarios in modern .NET solutions:
- **Two packages expose the same short type name** (e.g., multiple `JsonSerializer`, `ILogger`, `User`, `Result`, `Task`-like names).
- **Your domain model matches a BCL name** (e.g., `File`, `Path`, `Task`, `ValueTask`—don’t do this, but it happens).
- **Nested types and generic type names** become unreadable when fully-qualified.

#### Example: aliasing two types with the same name

```csharp
using System.Text.Json;
using StjSerializer = System.Text.Json.JsonSerializer;
using NjSerializer = Newtonsoft.Json.JsonConvert;

public static class Demo
{
    public static string ToJson(object value)
    {
        // Explicit and grep-friendly: you can find every use of StjSerializer quickly.
        return StjSerializer.Serialize(value);
    }

    public static T FromJson<T>(string json)
    {
        // Newtonsoft has different semantics; the alias makes that choice explicit.
        return NjSerializer.DeserializeObject<T>(json)!;
    }
}
```

**Good to know**
- Aliases are compile-time only; they don’t create wrapper types or allocate.
- Aliases can target **types** or **namespaces**.

### 2. **Clarify intent**
Aliases are also a readability tool: they can make “which type did we mean?” obvious in a large codebase.

Patterns that usually read well:
- **Domain intent**: `using Money = Company.Product.Billing.Money;`
- **External vs internal**: `using ExternalUser = VendorSdk.User; using User = Company.App.User;` (use sparingly—this can still confuse newcomers)
- **Namespace alias** to shorten deep qualifiers when a file touches many types from a deep namespace:

```csharp
using Billing = Company.Product.Billing.Domain;

namespace Company.Product.Billing.App;

public sealed class InvoiceService
{
    public Billing.Invoice CreateInvoice(Billing.CustomerId customerId) => new(customerId);
}
```

**Mentor guidance**
- Prefer aliases when the alternative is **sprinkling long fully-qualified names** across a file.
- Prefer fully-qualified names when the alias would **hide the real dependency** (e.g., in a very small file, `System.Text.Json.JsonSerializer.Serialize(...)` is already clear).

### 3. **Maintainability**
An alias is a small “contract” for the file (or project, if it’s global). Make it easy to live with.

Rules that keep aliases healthy:
- **Keep names short and unambiguous**: `StjSerializer` (System.Text.Json) is clearer than `Json1`.
- **Use consistent conventions** across the solution:
  - Prefix external deps: `AwsS3`, `EfCore`, `Dapper`, `Grpc`, etc.
  - Or use suffixes: `*Client`, `*Serializer`, `*Model`.
- **Avoid “clever” aliases** that form a DSL (hard to search, hard to onboard).

**Common mistakes**
- **Creating aliases that shadow common names**: `using Task = MyCompany.Threading.Task;` will cause endless confusion.
- **Over-aliasing**: if every file has 10 aliases, the alias layer becomes a second namespace system.
- **Using aliases to paper over poor naming**: if your own API is confusing, fix naming at the source.

**Performance note**
- Aliases are a compile-time feature; they do not impact runtime performance. The real “performance win” is human: fewer ambiguous references and fewer accidental API choices.
