## 7.2. Common pitfalls that show up in production

1. **Ambiguous type names after adding a package** (sudden compile errors; fix with aliases/qualification)
2. **Extension method selection changes** (adding a `using` can change which extension method binds)
3. **Overusing `using static`** (readability + debugging/searchability regressions)
4. **Global usings becoming “spooky action at a distance”** (hard-to-explain dependencies; review discipline needed)

### 1. **Ambiguous type names after adding a package**
This is one of the most common “it worked yesterday” failures: a new NuGet package introduces a type with the same simple name as one you already use, and now the compiler can’t decide.

**What it looks like**
- You add `using Some.New.Package;` (or a package adds implicit usings / you add a `global using`).
- Suddenly you get: **“The type name 'X' is ambiguous…”**.

**Fix patterns (best → acceptable)**
- **Alias the type** when you truly need both in the same file:

```csharp
using SystemTextJson = System.Text.Json.JsonSerializer;
using NewtonsoftJson = Newtonsoft.Json.JsonConvert;

public static class JsonDemo
{
    public static string A(object value) => SystemTextJson.Serialize(value);
    public static string B(object value) => NewtonsoftJson.SerializeObject(value);
}
```

- **Fully-qualify at the call site** for a one-off:

```csharp
var s = System.Text.Json.JsonSerializer.Serialize(value);
```

- **Narrow the `using` scope** (file-scope vs namespace-scope) to avoid importing the conflicting namespace where you don’t need it. See section **4.1**.

**Common mistakes**
- “Fixing” by removing a `using` that other code relied on, causing more breakage.
- Creating extremely clever aliases (`J`, `S`, `X1`) that make code unreadable; prefer meaningful names.

**Good to know**
- If two assemblies define the *same full name* (namespace + type name) in the same compilation, you can also hit identity collisions. That’s not a “using” problem; it’s a packaging/design issue. See section **1.2** for the boundary between namespaces and assemblies.

### 2. **Extension method selection changes**
Extension methods are discovered based on **what namespaces are in scope**. Adding a `using` can add new extension candidates, and overload resolution can pick a different method than before.

**Why this is dangerous**
- It can change semantics **without** compile errors (the call still binds, just to a different method).
- It can change performance (allocations, LINQ vs Span-based implementations) depending on which extension you picked.

**Mitigation patterns**
- **Prefer explicit calls for “important” operations** when ambiguity is plausible:
  - Instead of `source.Select(...)` in perf-critical code, consider explicit APIs on the type or explicit `Enumerable.Select(source, ...)` (still an extension method, but explicitly chosen).
- **Keep `global using` minimal** (section **4.2**) so “new extension sets” don’t silently appear everywhere.
- **Use analyzers** to catch risky patterns (e.g., “prefer explicit qualification” in some layers).

**Example: make the chosen extension explicit**

```csharp
using System.Linq;

public static class ExtensionChoice
{
    public static int[] Map(int[] values)
        => Enumerable.Select(values, static x => x * 2).ToArray();
}
```

**Good to know**
- Overload resolution is deterministic, but it’s complicated. The “mentor” rule is: *if an extension method call is business-critical or perf-critical, make its origin obvious.*

### 3. **Overusing `using static`**
`using static` is a sharp tool. It’s great for *math-like* code, but quickly becomes a readability trap in general-purpose code.

**Symptoms**
- Readers can’t tell where `Min`, `Clamp`, `Create`, or `Parse` came from.
- Code search gets worse (“find all call sites” becomes noisy).
- Debugging gets worse (harder to know which method you’re stepping into).

**Recommendation**
- Restrict to a tiny set of “universally recognized” classes (e.g., `System.Math`) and narrow contexts (e.g., numeric algorithms).
- In shared libraries, prefer explicit qualification unless the team has strong conventions.

See section **6.1** for safe usage guidance and section **6.2** for choosing between static imports vs other abstractions.

### 4. **Global usings becoming “spooky action at a distance”**
This is a maintainability failure mode: code compiles because of an import “somewhere else,” and engineers don’t know *why* a type or extension method is in scope.

**Typical causes**
- `global using` grows over time and starts importing “convenience” namespaces (especially extension-heavy ones).
- Different projects in a solution drift and each has different global imports, so code moves between projects and “mysteriously” stops compiling.

**Disciplined strategy**
- **Keep global usings boring**: BCL basics and stable project-wide primitives only. (See section **4.2**.)
- **Centralize them**: a single `GlobalUsings.cs` (or equivalent) per project makes intent obvious.
- **Code review rule**: treat “new global using” like changing a shared header in C/C++—it deserves scrutiny.

**Performance note**
- This is mainly a *human performance* issue: it increases time-to-understand and defect rate. However, extra global imports can also increase candidate sets for extension methods and overload resolution in large builds, which can be measurable at scale.
