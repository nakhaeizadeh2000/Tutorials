## 7.1. Checklist: correctness, maintainability, and performance-adjacent concerns

1. **Keep public namespaces stable** (moving types breaks consumers; plan your “package shape”)
2. **Avoid hidden dependencies** (don’t overuse `global using`; make key dependencies obvious)
3. **Minimize ambiguity** (collisions cost time; use aliases or fully-qualified names deliberately)
4. **Keep namespaces coherent** (each namespace should “tell a story”; avoid grab-bag namespaces)
5. **Tooling alignment** (formatters/analyzers + consistent conventions are a scalability multiplier)

### 1. **Keep public namespaces stable**
If consumers reference your types, **the namespace is part of the API contract**. Moving a public type between namespaces is a source-breaking change (and can be a runtime breaking change for reflection-based frameworks that store type names).

- **When it matters most**: NuGet libraries, shared company SDKs, and any “platform” assemblies used by multiple solutions.
- **When it matters less**: app-internal code where you can change all call sites in one repo (still avoid churn; churn has a real defect cost).

**Good to know**
- The “cost” isn’t just fixing compilation. Consumers have:
  - **Using directives / aliases** to update
  - **Source generators / analyzers** that might reference names
  - **Configuration** and **serialization metadata** that may store full type names

**See section**
- For the deep reasoning and namespace layering patterns, see **3.2**.

### 2. **Avoid hidden dependencies**
Every `using` is a dependency your reader must keep in mind. **Global usings are powerful**, but they can make dependencies harder to see.

- **Prefer**: project-level `global using` only for genuinely ubiquitous imports (common BCL namespaces, a single shared “primitives” namespace).
- **Avoid**: importing lots of domain namespaces globally in libraries; it blurs API boundaries and increases ambiguity risk.

**Mentor rule of thumb**
- If a `using` tells the reader something important about the file (e.g., “this is an EF Core repository”), keep it **local**.

**See section**
- For `global using` strategy and placement, see **4.2**.

### 3. **Minimize ambiguity**
Ambiguity is both a correctness risk and a productivity tax.

- **Type-name collisions**: `Task`, `File`, `JsonSerializer`, `Path`, `Timer`, `Result`, `User`, `Error`…
- **Extension-method collisions**: two different packages add `AddXyz(...)` on the same type.

**What to do**
- Use **type aliases** (`using Json = System.Text.Json.JsonSerializer;`) when it clarifies the dominant choice.
- Use **fully-qualified names** in narrow spots where you want “no magic” and maximum grep-ability.

**See section**
- For aliases (including `global using` aliases) see **5.1** and **5.2**.
- For extension method binding gotchas, see **4.1** and **7.2**.

### 4. **Keep namespaces coherent**
Treat each namespace as a small “chapter title” for what’s inside it.

- **Prefer**: domain-based grouping (`Company.Product.Billing`), with sub-namespaces for major subdomains or layers.
- **Avoid**: dumping grounds (`.Helpers`, `.Common`, `.Utils`) where ownership and boundaries dissolve.

**Good to know**
- Coherence improves:
  - Discoverability in IDE tooling
  - Review quality (“does this type belong here?”)
  - Migration paths (moving one coherent namespace is easier than untangling a bucket)

**See section**
- For naming and depth guidance, see **3.1**.

### 5. **Tooling alignment**
In large codebases, convention enforcement is a multiplier.

- **Use analyzers/formatters** (EditorConfig + analyzer rules) to keep:
  - `using` ordering consistent
  - file-scoped namespaces as the default (unless exceptions apply)
  - global usings centralized (when you choose to use them)
- **Make code search reliable**: if your team can’t consistently grep “where did this type come from?”, productivity drops.

**Performance-adjacent note**
- Most namespace decisions don’t change runtime CPU/allocations. The “performance” here is **engineering throughput and correctness**: fewer ambiguous binds, fewer refactors, fewer accidental API breaks.
