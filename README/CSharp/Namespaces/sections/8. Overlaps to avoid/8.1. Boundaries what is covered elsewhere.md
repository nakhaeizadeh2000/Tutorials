## 8.1. Boundaries: what is covered elsewhere in this repo

1. **Namespaces vs assemblies and packaging boundaries** (covered in `Fundamental Theories` → “Namespaces vs folders vs assemblies”)
2. **Access modifiers and API exposure (`public`, `internal`, `private`, etc.)** (covered in `Fundamental Theories` and OOP domains)
3. **Project references, NuGet, and dependency graphs** (covered in `Fundamental Theories` → tooling/deployment topics)

### 1. **Namespaces vs assemblies and packaging boundaries**
This Namespaces domain explains **naming and import mechanics** in C# (compile-time scopes, `using`, aliases, `global using`, and related correctness pitfalls).

For the **real boundary concepts**—the things that affect deployment, versioning, trimming/AOT, and runtime loading—see the referenced Fundamentals material:

- **Assemblies**: what the runtime loads; how type identity includes assembly + namespace + type name.
- **Packages (NuGet)**: how you ship and version code across repos/solutions.
- **Project boundaries**: build graph, compilation units, incremental builds.

**Reminder**
- A namespace can span multiple assemblies, and an assembly can contain many namespaces. That’s normal and often desirable in large ecosystems (the BCL does it heavily).

### 2. **Access modifiers and API exposure (`public`, `internal`, `private`, etc.)**
Namespaces are **not** access control.

- If you need encapsulation, use **access modifiers** and, where needed, assembly-level techniques such as `InternalsVisibleTo`.
- If you need enforcement of architectural boundaries, combine access modifiers with analyzers (and/or project/assembly boundaries).

See the referenced OOP/Fundamentals domains for the complete, in-depth treatment of those topics.

### 3. **Project references, NuGet, and dependency graphs**
This domain intentionally avoids deep coverage of:

- **ProjectReference** graphs, transitive dependencies, and build-time constraints
- NuGet restore resolution, central package management, and version pinning strategies
- Dependency inversion at the solution level (how to break cycles across projects)

Those belong in tooling/deployment and architecture domains.

**Good to know**
- Namespaces can *suggest* layering (e.g., `.Abstractions`, `.Internal`, `.Implementation`), but your actual dependency graph is defined by **project and assembly references**, not by namespace names.
