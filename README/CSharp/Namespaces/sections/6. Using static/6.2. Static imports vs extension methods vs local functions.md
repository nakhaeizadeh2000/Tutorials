## 6.2. Static imports vs extension methods vs local functions

1. **Choose the right abstraction** (extension methods for fluent APIs; local functions for internal helpers; static imports for narrow math-like utilities)
2. **Correctness and ambiguity** (name clashes; overload resolution surprises)
3. **Performance note** (static import is syntax-only; performance is determined by the called method, allocations, and inlining)

### 1. **Choose the right abstraction**
These three features can all make code “shorter”, but they serve different design goals.

- **`using static`**: a *syntax convenience* for accessing static members without qualification.
  - Best for **math-like / constant-like** utilities where the origin is obvious and stable: `Math`, `BitOperations`, `Convert`, `Constants`.
  - Weak for domain code where “where did this method come from?” matters.
- **Extension methods**: a way to add *discoverable* instance-style methods to existing types.
  - Best when you are building a **fluent API** or a **small surface area** of well-named operations on a type you don’t own.
  - Risk: they participate in name lookup and can change binding when you add a `using`. See **4.1** and **7.2**.
- **Local functions**: a way to name a helper inside a method for **encapsulation** and readability.
  - Best for algorithms where you want to keep helper logic close, avoid class-level clutter, and capture local variables safely.
  - Prefer local functions over private lambdas when the helper is non-trivial, needs recursion, or you want clearer stack traces.

#### Decision table (mentor rule-of-thumb)
- **If the helper is only meaningful inside one method** → **local function**.
- **If you want a library-style operation “on” a type** and can keep names unambiguous → **extension method**.
- **If you are just removing `Math.` noise** and the call site stays obvious → **`using static`**.

#### Focused example (all three in one small program)

```csharp
using System.Numerics;
using static System.Math;

namespace Demo;

public static class Program
{
    public static void Main()
    {
        // 1) using static: good when origin is obvious
        var hypotenuse = Sqrt(3 * 3 + 4 * 4);
        Console.WriteLine(hypotenuse); // 5

        // 2) extension method: fluent, discoverable, reusable
        Console.WriteLine("Hello".IsNullOrWhiteSpaceFast()); // False

        // 3) local function: encapsulated helper with captured variables
        int SumSquares(ReadOnlySpan<int> values)
        {
            var sum = 0;
            foreach (var v in values)
            {
                sum += Square(v); // local helper keeps intent readable
            }
            return sum;

            static int Square(int x) => x * x;
        }

        Console.WriteLine(SumSquares(stackalloc[] { 1, 2, 3 })); // 14
    }
}

public static class StringExtensions
{
    // A tiny example: keep extension method names precise to reduce collisions.
    public static bool IsNullOrWhiteSpaceFast(this string? value) => string.IsNullOrWhiteSpace(value);
}
```

**Good to know**
- If you’re writing a **public library**, be conservative with extension methods: they effectively become part of user’s IntelliSense and can pollute call sites.
- Local functions can be marked `static` (as shown) when they don’t need captures; this avoids accidental capturing and makes intent explicit.

### 2. **Correctness and ambiguity**
**Ambiguity is the real danger, not syntax.**

- **Name clashes**:
  - `using static` can create ambiguous simple names if multiple static classes expose the same member name.
  - Extension methods can “appear” or “disappear” based on `using` directives (and `global using`).
- **Overload resolution surprises**:
  - Adding a new `using` might bring a different extension method into scope and change which overload binds.
  - Adding a package can introduce a type with the same name as yours and break compilation until you alias/qualify.

**Mentor practice**
- When a call site is not obvious without IDE help, prefer explicit qualification or a carefully chosen alias.
- Avoid “cute” extension method names that are likely to collide (`ToInt`, `As`, `Map`, `Do`) unless they are in a tightly controlled codebase.

### 3. **Performance note**
- **`using static` has no runtime cost**: it does not create delegates or wrappers; it only changes how you write member access.
- **Local functions vs lambdas**:
  - A local function is a method; it **does not allocate a delegate** unless you convert it to one.
  - A capturing lambda often allocates a closure (depending on captures and optimizations). If this matters, measure, but a safe default is: **prefer local functions for non-trivial helpers**.
- **Extension methods** are just static method calls. Performance depends on:
  - Whether the method can be inlined.
  - Whether it causes allocations (e.g., LINQ, iterator blocks).
  - Whether it introduces virtual/interface dispatch.

**Performance note**
- If you need allocation-free pipelines, prefer `Span`/`ReadOnlySpan`, `CollectionsMarshal`, and explicit loops—those topics belong in performance-focused domains; in this tutorial, the key point is: **namespace/import style doesn’t make code fast—API choice does.**
