## 1.2. Namespace vs folder vs project vs assembly (quick map)

1. **Folders ≠ namespaces** (conventions help, but the compiler doesn’t care about directories)
2. **Projects/assemblies ≠ namespaces** (assemblies ship; namespaces name; keep them aligned but not coupled)
3. **Practical rule** (stable public namespaces, flexible internal folders)

### 1. **Folders ≠ namespaces**
**A folder is an OS/filesystem organization tool; a namespace is a language-level name.** The C# compiler does not infer namespaces from directories.

- **What controls the namespace?**
  - The explicit `namespace ...` declaration in the `.cs` file.
  - If you omit `namespace`, the type goes into the **global namespace** (almost always a mistake in production code unless you’re writing small scripts or very special interop code).
- **Why people align folders and namespaces anyway**:
  - It makes code discoverable (searching the folder tree roughly matches IntelliSense grouping).
  - It reduces merge conflicts (one “thing” per folder + one “thing” per namespace).
  - It supports consistent conventions (e.g., `Company.Product.Feature` maps to `/Feature/`).

**Common mistakes**
- **Assuming “moving a file” moves a type’s namespace**: it doesn’t. You must change the `namespace` declaration.
- **Relying on folder layout as an architectural boundary**: it’s not enforceable. Use `internal`, analyzers, and packaging boundaries (see **8.1** for where those topics are covered elsewhere in this repo).

#### Minimal example (folder move doesn’t change namespace)

```csharp
// File path before: Features/Payments/Charge.cs
// File path after:  Features/Billing/Charge.cs
// Namespace stays whatever you declare here.

namespace Company.Product.Payments;

public sealed class Charge;
```

### 2. **Projects/assemblies ≠ namespaces**
**A project produces an assembly; a namespace is a naming scheme inside and across assemblies.** These are related, but not the same.

- **Assembly** (runtime/deployment unit):
  - Loaded by the runtime.
  - Has versioning, binding, trimming/AOT considerations, and deployment behavior.
  - The same namespace can appear in many assemblies (that’s common in the BCL).
- **Namespace** (compile-time naming + API organization):
  - Groups types for humans and tooling.
  - Helps avoid collisions and improves discoverability.
  - Does **not** prevent a type from referencing another type in a different namespace.

**Why “align but don’t couple”**
- **Align** for usability: consumers often assume `Company.Product.*` lives in `Company.Product` packages/assemblies.
- **Don’t couple** because refactors happen:
  - You may split a big project into multiple assemblies for build parallelism or deployment reasons.
  - You may merge assemblies to reduce packaging complexity.
  - You may move implementation types between assemblies without wanting to rename public namespaces (renaming is breaking; see **3.2**).

**Good to know**
- **Type identity at runtime** includes **assembly + namespace + type name** (and generic arity). Two assemblies can both define `MyCompany.Foo.Widget`—that becomes a **type identity collision** if both are loaded and referenced in the same compilation context. Avoid this in your own code: keep your *public* type full names globally unique across your shipped surface.

### 3. **Practical rule**
**Keep public namespaces stable; keep internal code organization flexible.**

- **Public surface (libraries, shared packages)**:
  - Treat namespaces like part of your API contract. Changing them is a breaking change for consumers (source-level and sometimes reflection-based).
  - Prefer a small number of coherent top-level namespaces.
  - Use intentional “sub-namespaces” to communicate layering (see **3.2**).
- **Internal app code**:
  - You can reorganize folders more freely as the codebase evolves.
  - Still keep namespace/folder alignment as a convention because it scales better.

**Mentor guidance**
- **Don’t encode version numbers in namespaces** (e.g., `.V2`) unless you are intentionally shipping side-by-side versions in the same process. Versioned namespaces are a heavy tool and increase cognitive load. Prefer normal semantic versioning with stable namespaces; when breaking changes are unavoidable, consider new package identity or carefully planned migration paths.

**Performance note**
- Most “namespace vs assembly” decisions are about **engineering productivity** and **deployment/build** characteristics, not per-request runtime performance. If you split assemblies, you may affect build parallelism and startup/load behavior in some hosting models, but the namespace name itself does not make code faster.
