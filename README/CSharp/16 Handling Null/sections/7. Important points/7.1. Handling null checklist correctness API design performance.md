## 7.1. Handling null checklist: correctness, API design, performance

1. **Make contracts explicit**: `T` vs `T?`, Try-patterns, and domain models beat “magic nulls”.
2. **Prefer guards to chains**: validate once, then write normal code (better readability and debuggability).
3. **Don’t silence warnings**: fix causes; use `!` only when you can prove safety.
4. **Be intentional with defaults**: `??` is a decision; ensure it doesn’t hide corrupt or unexpected inputs.
5. **Measure hot paths**: avoid boxing/logging allocations; avoid exception-driven flows.

### 1) **Make contracts explicit**: `T` vs `T?`, Try-patterns, and domain models
Checklist questions (mentors ask these in reviews):
- **What does null mean here?** (optional, not found, not applicable, invalid, not loaded?)
- **Is that meaning acceptable?** If behavior differs by “absence reason”, do not use a single `null`.
- **Does the signature tell the truth?** If you accept null, use `T?`. If you never return null, use `T` and ensure it’s true.

Practical rules:
- Prefer **non-nullable by default** in domain/core models.
- Allow null mostly at **boundaries** and normalize quickly.
- For “not found” use **Try-pattern** or result types when callers must handle absence as normal flow.

See also (no duplication):
- Generic `T`/`T?` contracts and constraints are explained in [2.2. Generic types and nullability T and T question mark](<../../../15 Generics/sections/2. Generic classes and type design/2.2. Generic types and nullability T and T question mark.md>).

### 2) **Prefer guards to chains**: validate once, then write normal code
Rule of thumb:
- If a value is required, **prove it once** (guard/validation) and then write normal code.
- Avoid long chains like `a?.b?.c` in core logic unless the whole chain is truly optional.

Example pattern:

```csharp
public static string NormalizeUserName(string? raw)
{
    if (string.IsNullOrWhiteSpace(raw))
        throw new ArgumentException("User name is required.", nameof(raw));

    return raw.Trim();
}
```

Mentor note:
- Guards improve debuggability because failures happen close to the source, not deep inside a call chain.

---

### 3) **Don’t silence warnings**: fix causes; use `!` only when you can prove safety
Rules:
- Treat nullable warnings as **design feedback**. If the warning is correct, fix the contract or flow.
- If the warning is wrong, change the structure so the compiler can see the proof (guards, locals, pattern matching, attributes).

Acceptable uses of `!`:
- Interop with frameworks where invariants exist but aren’t expressible in types, and you can justify the proof.

Unacceptable use:
- Systematically appending `!` to make the build green.

See also (no duplication):
- `!` deep guidance is in `Handling Null/4.3` ([4.3. Null-forgiving operator last resort](<../4. Operators and constructs/4.3. Null-forgiving operator last resort.md>)).

### 4) **Be intentional with defaults**: `??` is a decision
Defaulting questions:
- “If this is missing, what should the system do?” (reject, retry, record missing, best-effort output?)
- “Is this default safe for correctness/security?” (IDs, auth claims, routing keys should rarely default)
- “Do we need observability?” (metrics/logs for missing required fields upstream)

Prefer:
- `??` for documented defaults at boundaries
- guard + error for invariant violations
- result types when the reason for missing matters

See also (no duplication):
- `??` / `??=` deep guidance is in `Handling Null/4.2`.

### 5) **Measure hot paths**: avoid boxing/logging allocations; avoid exception-driven flows
Performance checklist:
- Are we throwing exceptions in an expected path? Replace with Try-pattern or explicit `T?`.
- Are we boxing nullable value types (or any value types) into `object`/`params object[]` in loops?
- Are we doing expensive default computations repeatedly due to poor caching/lazy init?

Practical advice:
- Keep “missing optional data” out of exception paths.
- Keep logging/formatting out of tight loops or use allocation-aware APIs provided by your logging stack.
