## 1.2. Null-related failure modes in production (what actually breaks)

1. **NRE sources**: unexpected `null` from boundaries (I/O, deserialization, DI, external libs, legacy code).
2. **Silent logic bugs**: incorrect fallbacks (`??`) masking bad states; “defaulting” hides data quality issues.
3. **Correctness vs resiliency**: when to fail fast vs when to recover (and how to make that explicit).

### 1) **NRE sources**: unexpected `null` from boundaries
**What this really means**
- Most `NullReferenceException` bugs are not “you forgot to check null” bugs. They’re **contract** bugs: a value that was assumed non-null crossed a boundary where that assumption was false.

Common boundary sources (real-world):
- **I/O input**: `Console.ReadLine()` can return `null`; HTTP headers may be absent; query params may be missing.
- **Deserialization**: missing JSON properties, `null` JSON tokens, mismatched casing/shape, and “default” values.
- **Configuration**: environment variables absent, config keys missing, secrets not loaded.
- **DI / service location**: mis-registered services, optional dependencies, lazy factories that return null.
- **External libraries / legacy code**: “oblivious” nullable context, weak annotations, and old APIs that return null for “not found”.

**Mentor pattern: boundary normalization**
- Convert untrusted, nullable, and messy inputs into **validated, non-null domain values** as early as possible.
- Keep core logic on **non-null types** (`string`, not `string?`) so the compiler can help you.

Example (boundary normalization with clear errors):

```csharp
public static string RequireNonEmpty(string? value, string paramName)
{
    if (string.IsNullOrWhiteSpace(value))
        throw new ArgumentException("Value must be provided.", paramName);

    return value;
}
```

**Good to know**
- Prefer `ArgumentNullException.ThrowIfNull(value);` for pure “must not be null”.
- Prefer `ThrowIfNullOrWhiteSpace`-style helpers (your own or library) when the contract is “non-empty string”.

### 2) **Silent logic bugs**: incorrect fallbacks (`??`) masking bad states
**The dangerous part about `??` is not correctness—it’s *meaning*.**

Fallbacks often hide:
- **Data corruption**: if a field “must exist” but you default it, you may store/emit wrong output.
- **Broken invariants**: a required relationship becomes optional and nobody notices.
- **Monitoring blindness**: instead of failing with an obvious signal, you emit “Unknown” and lose the trail.

Example (bug masking):

```csharp
// If CustomerId is required, this is a bug-masking fallback:
var customerId = request.CustomerId ?? "unknown";
```

Preferred approach: distinguish between “optional” and “invalid”.

```csharp
if (request.CustomerId is null)
    return Results.BadRequest("CustomerId is required."); // boundary decision

var customerId = request.CustomerId; // non-null after guard
```

**Mentor rule**
- Use `??` when “missing” is an *expected, acceptable state* with a well-defined business default.
- Avoid `??` when “missing” indicates a violated invariant. Fail fast at the boundary instead.

**Performance note**
- “Silent defaults” are cheap at runtime but expensive in operations: they increase support/debug time and can cause costly downstream behavior (bad caching keys, wrong routing, wrong authorization decisions).

### 3) **Correctness vs resiliency**: when to fail fast vs when to recover (and how to make that explicit)
Null-handling is a decision about **system behavior under uncertainty**:

- **Fail fast** when null indicates a programmer error, contract breach, or corrupt state.
  - Example: internal invariants, required dependencies, required fields after validation.
- **Recover** when null is a normal part of the domain (optional data) or when resilience is required (best-effort output).
  - Example: optional display name, optional UI hints, optional telemetry enrichment.

How to make this explicit (not implicit):
- **Method signatures**: `T` vs `T?` is the first line of communication.
- **Return shapes**: Try-patterns, result types, discriminated states.
- **Naming**: `TryGetXxx`, `GetXxxOrDefault`, `OptionalXxx` communicate intent.
- **Layering**: boundaries decide “recover vs reject”; core logic assumes validated inputs.

Example (Try-pattern avoids exceptions and avoids null ambiguity):

```csharp
public static bool TryGetHeader(
    IReadOnlyDictionary<string, string> headers,
    string name,
    out string value)
{
    if (headers.TryGetValue(name, out var v) && !string.IsNullOrWhiteSpace(v))
    {
        value = v;
        return true;
    }

    value = string.Empty;
    return false;
}
```

**Good to know**
- Don’t use exceptions (including NRE) for **expected absence**. Exceptions are for exceptional states, and they’re expensive.
- If you’re deciding between “return null” and “Try-pattern”, prefer the Try-pattern when *callers must handle absence as normal control flow*.
