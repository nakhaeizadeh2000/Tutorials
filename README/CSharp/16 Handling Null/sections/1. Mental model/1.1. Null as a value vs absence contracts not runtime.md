## 1.1. Null as a value vs null as “absence” (contracts, not just runtime behavior)

1. **Two different meanings**: “unknown/not provided” vs “not applicable” (don’t overload one `null` for both).
2. **API contract framing**: *who* is allowed to return `null`, *when*, and *what the caller must do*.
3. **Mentor rule**: treat null-handling as **domain modeling + contract design**, not “sprinkle `?.` everywhere”.

### 1) **Two different meanings**: “unknown/not provided” vs “not applicable”
**Definition**
- **Unknown / not provided**: the value exists conceptually, but you don’t have it (yet). Example: user didn’t enter a phone number.
- **Not applicable**: the value does not exist for this case. Example: “VAT number” for non-business customers.

**Why mentors care**
- Both are “missing”, but they imply **different behavior**:
  - Unknown may trigger **collection/retry** flows.
  - Not applicable should **not** trigger “data quality” alerts.

**Common mistake**
- Reusing one `null` for multiple meanings:

```csharp
// Ambiguous: is null "unknown", "not applicable", or "not loaded"?
public sealed record Customer(string Name, string? VatNumber);
```

This ambiguity leaks into every caller, forcing “guessing” fallbacks.

**Preferred modeling options (modern C#)**
- **Discriminated shapes (recommended when behavior differs)**:

```csharp
public abstract record VatNumberState
{
    public sealed record NotProvided : VatNumberState;
    public sealed record NotApplicable : VatNumberState;
    public sealed record Provided(string Value) : VatNumberState;
}
```

- **Separate flags (acceptable for simple models if naming is explicit)**:

```csharp
public sealed record CustomerProfile(
    string Name,
    string? VatNumber,
    bool IsVatNumberApplicable);
```

**Good to know**
- “Optional” in domain language often hides multiple states. If the states change behavior, model them explicitly.

---

### 2) **API contract framing**: who can return `null`, when, and what the caller must do
Nullability is an **API contract**, not a runtime fact:
- `string` means: “I guarantee a non-null string (or I throw).”
- `string?` means: “Caller must handle null.”

Where contracts break in real systems:
- **Boundaries** (I/O, configuration, JSON/DB materialization, env vars).
- **Legacy/third-party libraries** compiled in an “oblivious” nullable context.

Mentor pattern: **validate at boundaries, keep the core non-null**.

```csharp
public static Uri ParseBaseUri(string? raw)
{
    if (string.IsNullOrWhiteSpace(raw))
        throw new ArgumentException("Base URI must be provided.", nameof(raw));

    return new Uri(raw, UriKind.Absolute);
}
```

After that point, you should be able to work with `Uri` (non-null) rather than `Uri?`.

**Performance note**
- One early guard is cheap; repeated exception throwing is not.
- Avoid “defensive null checks everywhere” that hide the real source of invalid data.

---

### 3) **Mentor rule**: treat null-handling as **domain modeling + contract design**
Null-handling is not “syntax trivia”; it’s design:
- If `null` is **invalid**, fail fast at the boundary (guard + clear error).
- If `null` is **expected**, handle it deliberately in a narrow scope and keep the rest of your code normal.

**Common mistake**: using null-operators to make warnings/NREs disappear.

```csharp
// Looks "safe", but can hide a broken invariant:
var city = order?.Customer?.Address?.City ?? "Unknown";
```

If `Order.Customer` is required for a valid `Order`, that line converts a correctness bug into a silent data-quality bug.

**Good to know**
- If you see long chains like `a?.b?.c?.d`, pause and ask whether your model is missing invariants or your boundary validation is too late.
