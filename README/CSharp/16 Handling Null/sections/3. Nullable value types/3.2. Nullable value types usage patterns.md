## 3.2. `GetValueOrDefault`, `HasValue`, and pattern matching for clarity and speed

1. **Branching explicitly** beats clever expressions when correctness matters.
2. **Avoid exceptions**: don’t use `.Value` unless you proved `HasValue`.
3. **Performance note**: `T?` avoids allocations; watch for boxing when converting to `object`/interfaces.

### 1) **Branching explicitly** beats clever expressions when correctness matters
Nullable value types are one of the best examples where *explicit code is safer than clever code*.

Prefer clear, readable patterns:

```csharp
public static string Describe(int? value)
{
    if (value is null) return "no value";
    return $"value={value.Value}";
}
```

Or avoid `.Value` by pattern matching:

```csharp
public static string Describe(int? value) =>
    value is int v ? $"value={v}" : "no value";
```

Mentor guidance:
- If `null` is meaningful, handle it **once** and then continue on non-null data.
- Avoid compressing null + validation + computation into one unreadable expression.

**Good to know**
- `value is int v` works because `Nullable<T>` participates naturally in pattern matching.

---

### 2) **Avoid exceptions**: don’t use `.Value` unless you proved `HasValue`
`Nullable<T>.Value` throws `InvalidOperationException` when `HasValue == false`. That means:
- `.Value` is fine **after a proof** (guard or match).
- `.Value` is not fine as a “maybe it’s there” access in normal control flow.

Bad (exception-driven control flow):

```csharp
public static int BadSum(int? a, int? b)
{
    // Throws if either is null.
    return a.Value + b.Value;
}
```

Good (explicit intent):

```csharp
public static int SumOrZero(int? a, int? b)
{
    if (a is not int av || b is not int bv) return 0;
    return av + bv;
}
```

Mentor rule:
- Use exceptions for **unexpected** states. “optional data is missing” is usually expected.

**Performance note**
- Throwing exceptions is expensive (stack capture, unwinding, disruption of hot paths). Don’t build “null means throw” into frequently-hit logic unless it’s a deliberate fail-fast boundary decision.

---

### 3) **Performance note**: `T?` avoids allocations; watch for boxing to `object`/interfaces
`int?` (and other `T?`) are structs. They do not allocate by themselves.

Where allocations can appear:
- **Boxing to `object`**:

```csharp
object o1 = (int?)42;   // boxes (as boxed int), allocation
object o2 = (int?)null; // becomes null (no box)
```

- **`params object[]`** and logging APIs can allocate (array + boxing):

```csharp
static void Log(string message, params object?[] args) { /* ... */ }

int? x = 42;
Log("x={0}", x); // boxes + allocates args array
```

Preferred approaches in hot paths:
- Use structured logging APIs that avoid boxing where possible (depends on logging library).
- Prefer interpolated string handlers where supported by the target logging API (modern .NET patterns).
- Or keep logging out of hot loops entirely.
