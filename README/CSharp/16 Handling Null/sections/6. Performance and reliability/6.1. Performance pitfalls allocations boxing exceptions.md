## 6.1. Performance pitfalls: allocations, boxing, and exceptions

1. **Exceptions are expensive**: don’t use NREs as control flow; design for “expected absence”.
2. **Boxing traps**: `T?` boxed to `object` can allocate; avoid `params object[]` logging in hot paths.
3. **Branching vs cleverness**: clearer null guards often JIT well and are easier to profile and optimize.

### 1) **Exceptions are expensive**: don’t use NREs as control flow
This is the simplest performance truth about null-handling:
- **A null check is cheap.**
- **A thrown exception is expensive.**

Why exceptions are expensive (in practice):
- They disrupt normal control flow, inhibit some optimizations, and force stack capture/unwind.
- They often trigger error logging, telemetry, and retries, multiplying cost.

Mentor rule:
- Use exceptions for **unexpected** states (contract breaches).
- Use **normal control flow** for expected absence (Try-patterns, `T?`, results).

Bad: “missing data” uses exceptions as branching:

```csharp
public static int BadParse(string raw)
{
    // Throws for normal absence; also allocates exception objects repeatedly.
    return int.Parse(raw);
}
```

Better: treat absence as expected:

```csharp
public static bool TryParsePositiveInt(string? raw, out int value)
{
    if (!int.TryParse(raw, out var v) || v <= 0)
    {
        value = default;
        return false;
    }

    value = v;
    return true;
}
```

**Good to know**
- “Fail fast” is still correct at boundaries (e.g., required config keys). The key is: **fail fast once**, not repeatedly in a hot loop.

### 2) **Boxing traps**: `T?` boxed to `object` can allocate
Nullable value types are structs. They are allocation-free **until** you flow them into APIs that require `object` or non-generic interfaces.

Common boxing triggers:
- **`object o = someNullable;`**
- **`params object?[]`** methods (formatting/logging) because values must be boxed
- **Non-generic collections** (`ArrayList`, `Hashtable`) (legacy; avoid)

Runnable example:

```csharp
int? x = 42;

object boxed1 = x;       // allocates (boxed int)
object? boxed2 = (int?)null; // becomes null, no box

Console.WriteLine(boxed1.GetType().FullName); // System.Int32
Console.WriteLine(boxed2 is null);            // True
```

Mentor guidance:
- Keep hot-path APIs **generic**: `IReadOnlyList<T>`, `IEnumerable<T>`, `Span<T>`, etc.
- Avoid `params object[]`-style logging in tight loops; prefer modern logging patterns that avoid boxing when available in your logging stack.

### 3) **Branching vs cleverness**: clear null guards are usually fastest *and* safest
Developers sometimes “code golf” null-handling into expressions that are hard to read and hard to profile.

Mentor rule:
- **Prefer an explicit guard** when:
  - the branch is domain-critical,
  - the fallback has side effects,
  - you need to log/measure missing data,
  - multiple steps depend on the value.

Example (clear and JIT-friendly):

```csharp
public static string NormalizeOrThrow(string? value)
{
    if (value is null)
        throw new ArgumentNullException(nameof(value));

    return value.Trim();
}
```

Performance note:
- Branch prediction matters in extreme hot paths, but the biggest wins almost always come from reducing allocations and avoiding exception-heavy paths.
