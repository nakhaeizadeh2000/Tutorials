## 8.1. Interview Q&A: nullability, operators, and API design

1. **Explain `string` vs `string?`** and how NRT changes code review expectations.
2. **When would you use `??` vs `?:` vs `if` guards** (and what’s the readability/perf trade-off)?
3. **When is `!` acceptable** and what are the risks?
4. **How do you design “not found” APIs** (null return vs Try-pattern vs result type) and why?
5. **How can concurrency bugs look like null bugs** (publication, races, lifetime)?

### 1) **Explain `string` vs `string?`** and how NRT changes code review expectations
**Answer (mentor-level)**
- `string` means: **non-null by contract**. Callers may assume it’s never null; the implementation must uphold that or throw.
- `string?` means: **nullable by contract**. Callers must handle null explicitly.

What changes in code review when NRT is enabled:
- You stop reviewing “did you remember to check null?” and start reviewing **contract correctness**:
  - Are boundaries validated?
  - Do signatures reflect truth?
  - Are warnings fixed correctly (guards/structure) rather than suppressed?
- Nullable warnings become **design feedback**, not “noise”.

Mini example:

```csharp
public static string NormalizeName(string? raw)
{
    if (string.IsNullOrWhiteSpace(raw))
        throw new ArgumentException("Name is required.", nameof(raw));

    return raw.Trim();
}
```

**Good to know**
- NRT is compile-time only. It improves correctness by making contracts explicit, not by changing runtime behavior.

### 2) **When would you use `??` vs `?:` vs `if` guards** (readability/perf trade-off)?
**Answer**
- Use **`??`** when you are choosing a fallback for a nullable value and the fallback meaning is legitimate and documented.
- Use **`?:`** when the condition is *not* “nullness” (or when the condition is more complex than nullness and you want it explicit).
- Use **`if` guards** when:
  - null indicates a contract breach (fail fast),
  - the fallback has side effects or is expensive,
  - multiple operations depend on the validated value,
  - you want to log/measure the missing-data path.

Examples:

```csharp
var display = name ?? "(unknown)"; // good for UI / optional display (frontend)
```

```csharp
if (customerId is null)
    return Results.BadRequest("CustomerId is required.");

// after guard, keep code normal
var id = customerId;
```

**Performance note**
- These operators compile down to branches. Performance differences are almost always dominated by what you do in the branches (allocations, I/O, exceptions), not by the operator choice.

### 3) **When is `!` acceptable** and what are the risks?
**Answer**
- `!` is acceptable only when you have a **real proof** that the value is non-null but the compiler cannot see it (interop, reflection-based frameworks, central validation pipelines).
- Risks:
  - You suppress the warning but keep the runtime NRE.
  - You destroy the safety signal: reviewers can no longer trust “non-null” code.

Example (acceptable-ish in a narrow scope with adjacent proof):

```csharp
ArgumentNullException.ThrowIfNull(service);
service!.Start(); // redundant but makes intent explicit in some code styles
```

Mentor guidance:
- Prefer restructuring/guards/attributes over `!`. If you must use it, keep the proof adjacent.

### 4) **How do you design “not found” APIs** (null return vs Try-pattern vs result type) and why?
**Answer**
- If “not found” is expected control flow and you don’t need error details: **Try-pattern**.
- If you must distinguish outcomes (not found vs invalid vs forbidden): **result type**.
- Returning `null` is acceptable only when:
  - it’s a small internal API,
  - the meaning of null is unambiguous,
  - and the call sites are disciplined (nullable enabled).

Try-pattern example:

```csharp
public static bool TryGetUser(
    IReadOnlyDictionary<int, string> users,
    int id,
    out string user)
{
    if (users.TryGetValue(id, out var u))
    {
        user = u;
        return true;
    }

    user = string.Empty;
    return false;
}
```

**Good to know**
- Returning `null` for “not found” becomes a trap when additional failure modes appear later.

### 5) **How can concurrency bugs look like null bugs** (publication, races, lifetime)?
**Answer**
- Data races can expose partially-initialized state (“sometimes null”), or stale values.
- Unsafe lazy initialization is a common source (and `!` makes it worse by hiding warnings).

Mentor triage checklist:
- Is the value stored in a **mutable field** shared across threads?
- Is it published with a known-safe pattern (`Lazy<T>`, `LazyInitializer.EnsureInitialized`, locks)?
- Can disposal/reset run concurrently with reads?
