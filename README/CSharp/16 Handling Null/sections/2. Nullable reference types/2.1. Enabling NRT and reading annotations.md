## 2.1. Enabling NRT and reading the annotations (`string` vs `string?`)

1. **Project-level defaults**: `Nullable` context, warnings as errors, and “fix the warnings, don’t suppress them”.
2. **Annotation meaning**: `T` means “non-null by contract”, `T?` means “may be null”.
3. **Migration strategy**: annotate boundaries first; avoid “turn it on and suppress everything”.

### 1) **Project-level defaults**: `Nullable` context, warnings as errors, and “fix the warnings, don’t suppress them”
Nullable reference types (NRT) is the single biggest “correctness per line of code” upgrade you can make for null bugs. Treat it as **a contract system**:
- The compiler warns when your code violates the contract (e.g., you return `null` where you promised non-null).
- Your job is to make contracts accurate at boundaries and then keep your core code simple.

**Recommended defaults for modern .NET projects**
- **Enable nullable** at the project level (don’t rely on file-by-file `#nullable` unless migrating a legacy repo):

```xml
<PropertyGroup>
  <Nullable>enable</Nullable>
  <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
</PropertyGroup>
```

Mentor guidance on warnings as errors:
- In mature codebases, **treat nullable warnings as errors** (at least for new/changed code).
- In migrating legacy code, you can temporarily use a softer strategy (see item 3), but avoid long-term “warning debt”.

**Legacy/obsolete patterns to avoid**
- “Turn it on, then sprinkle `!` everywhere” is not migration—it’s silencing the compiler.
- “Disable nullable for the whole project” keeps the codebase permanently unsafe and makes future refactors riskier.

**Good to know**
- NRT is **compile-time** only: it doesn’t change runtime semantics. It prevents bugs by making contracts explicit and checked by the compiler and analyzers.

---

### 2) **Annotation meaning**: `T` means “non-null by contract”, `T?` means “may be null”
Think of annotations as **promises**:
- `string Name` → callers may assume **never null**.
- `string? MiddleName` → callers must handle **possibly null**.

**Rules mentors enforce in reviews**
- If a parameter is declared `string`, your method is allowed to assume it’s non-null. If you *also* accept null at runtime, then your signature is lying.
- If a method returns `string`, it must either return a non-null string or throw. Returning null is a contract violation and should be fixed, not suppressed.

**A small, runnable example (what changes with NRT)**

```csharp
public static string NormalizeEmail(string? raw)
{
    if (string.IsNullOrWhiteSpace(raw))
        throw new ArgumentException("Email must be provided.", nameof(raw));

    // After the guard, raw is treated as non-null by flow analysis.
    return raw.Trim().ToLowerInvariant();
}
```

**Oblivious code and nullability context**
- When you call code compiled without nullable annotations, the compiler often treats it as **oblivious** (neither `T` nor `T?` is trustworthy).
- This is not “the compiler being annoying”—it’s the compiler telling you it cannot prove the contract.

See also (no duplication):
- Generic `T` / `T?` nullability rules are tricky and covered in depth in [2.2. Generic types and nullability T and T question mark](<../../../15 Generics/sections/2. Generic classes and type design/2.2. Generic types and nullability T and T question mark.md>).

### 3) **Migration strategy**: annotate boundaries first; avoid “turn it on and suppress everything”
The practical migration strategy that works in real production repos:

**Step 1: enable nullable + keep the build green**
- Enable `<Nullable>enable</Nullable>`.
- If you cannot make all warnings errors immediately, still fix high-risk areas first (I/O boundaries, DTOs, serialization, DI wiring).

**Step 2: fix boundaries before internals**
- Null almost always enters via:
  - deserialization (JSON/XML),
  - HTTP headers/query/body,
  - configuration/environment,
  - DB materialization,
  - UI input (frontend),
  - legacy libraries.
- Validate/normalize there, then pass **non-null** values to your core logic.

**Step 3: use targeted suppression only when it’s true**
- Prefer proving non-null through guards/pattern matching over suppression.
- Use `!` only when you can *prove* it’s safe but the compiler can’t see the proof (interop, reflection-heavy frameworks).

**Performance note**
- The “fix warnings properly” approach typically *improves* performance indirectly by reducing exception paths (NREs) and making control flow clearer.
