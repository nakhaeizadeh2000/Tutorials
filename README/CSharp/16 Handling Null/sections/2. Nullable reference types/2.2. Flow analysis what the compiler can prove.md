## 2.2. Flow analysis: what the compiler can prove (and how to help it)

1. **Guard patterns**: `if (x is null) return;` then use `x` confidently.
2. **Pattern matching**: `is null`, `is not null`, property patterns, and `switch` expressions for exhaustive handling.
3. **Helping the compiler**: avoid confusing control flow; prefer small pure helpers; understand when analysis stops.

### 1) **Guard patterns**: prove non-null once, then write normal code
The nullability analyzer is at its best when your code is **simple and local**:
- Guard, return/throw, then continue with a non-null variable.
- Keep the “proof” near the usage.

Idiomatic guard forms (modern C#):

```csharp
public static int LengthOrThrow(string? value)
{
    ArgumentNullException.ThrowIfNull(value);
    return value.Length; // value is now non-null
}
```

```csharp
public static string NormalizeOrEmpty(string? input)
{
    if (string.IsNullOrWhiteSpace(input))
        return string.Empty;

    return input.Trim();
}
```

**Common mistake**: guarding but not in a way the compiler can see:

```csharp
static bool IsValid(string? s) => !string.IsNullOrWhiteSpace(s);

public static int Bad(string? s)
{
    if (!IsValid(s)) return 0;
    return s.Length; // warning: the compiler doesn't know IsValid implies non-null
}
```

Fix by using built-in guards/patterns or annotating helpers (see section 2.3 for attributes), or by restructuring:

```csharp
public static int Good(string? s)
{
    if (string.IsNullOrWhiteSpace(s)) return 0;
    return s.Length; // proven by a known guard
}
```

**Performance note**: A guard is essentially a branch; it’s cheap. Avoid designs where the “guard” is an exception thrown repeatedly in a hot path.

---

### 2) **Pattern matching**: make null-handling explicit and exhaustive
Pattern matching is the most readable way to combine:
- **Validation**
- **Extraction**
- **Exhaustive handling**

Examples:

```csharp
public static string ToDisplayName(string? first, string? last) =>
    (first, last) switch
    {
        (null, null) => "Anonymous",
        (null, not null) => last,
        (not null, null) => first,
        (not null, not null) => $"{first} {last}",
    };
```

Property patterns are great when nullability depends on an inner field/property:

```csharp
public sealed record Order(Customer? Customer);
public sealed record Customer(string? Email);

public static bool CanEmail(Order? order) =>
    order is { Customer: { Email: not null } };
```

Mentor guidance:
- Prefer `switch` expressions when you are **mapping states to values**; they make missing cases obvious.
- Prefer guards (`if`) when you are **rejecting invalid inputs** and continuing with normal flow.

---

### 3) **Helping the compiler**: keep proofs local, avoid analysis “blind spots”
The analyzer is conservative. It will stop proving null-safety across:
- **Complex control flow** (callbacks/events, captured locals, `async` boundaries)
- **Aliasing/mutation** (a field can be changed by another method/thread)
- **External method calls** without known contracts

Practical techniques:
- **Use locals** to “freeze” a value you just validated:

```csharp
public sealed class Holder
{
    public string? Name { get; set; }
}

public static int SafeLength(Holder h)
{
    var name = h.Name;
    if (name is null) return 0;
    return name.Length;
}
```

- **Prefer immutability** (`init`, `readonly`, records) so proofs remain stable.
- **Don’t fight warnings with `!`**. If you believe the value is non-null, make it provable by structure, guards, or attributes.
