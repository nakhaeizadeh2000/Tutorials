## 5.1. Constructor checklist: correctness, safety, and maintainability

1. **Valid state and invariants** (make “illegal states” unrepresentable)
2. **What must NOT happen in constructors** (I/O, async blocking, hidden background work)
3. **Avoid leaking `this` during construction** (virtual calls, events, callbacks, closures)
4. **API design and versioning** (constructor sets as contracts)
5. **Testing and maintainability** (determinism, boundaries, framework constraints)

---

### 1) **Valid state and invariants (make “illegal states” unrepresentable)**
Your constructor (or factory) is an **invariant boundary**: after it returns, the instance should be valid for all public operations.

Checklist:
- **Write invariants down** (even if only in your head): “never null”, “range”, “relationship constraints”, “state machine rules”.
- **Validate at the boundary** (constructor/factory), not scattered across methods.
- Prefer **strong types** and explicit shapes over “stringly typed” state (e.g., `EmailAddress`, `OrderId`).
- Prefer immutable state (`readonly`, `init`, records) *when it matches the domain* to reduce defensive checks and synchronization.

**Good to know**
- `required` improves call-site completeness, not validity. Canonical guidance: section **4.2**.
- Structs always have `default(T)`; don’t rely on constructors to prevent invalid defaults (canonical: section **2.2** item 2).

---

### 2) **What must NOT happen in constructors**
Avoid work that is slow, unpredictable, or hard to test:

- **No I/O** (HTTP/DB/file). Use factories or explicit initialization.
- **No blocking on async** (`.Result`, `.Wait()`): deadlocks in (frontend) UI apps; ThreadPool starvation risks on servers.
- **No starting background work** (timers/tasks) without an explicit lifecycle contract (`Start/Stop`, hosted services, etc.).
- **Avoid locks** during initialization when lock order can interact with other initialization paths (deadlock risk).

**See also**
- Static/type initialization pitfalls are treated canonically in [4.2. Static initialization type constructors Lazy thread-safety](<../../../04 Fields/sections/4. Static fields/4.2. Static initialization type constructors Lazy thread-safety.md>).

---

### 3) **Avoid leaking `this` during construction**
“Leaking `this`” means another component can access the instance before it’s fully initialized.

Common escape paths:
- **Virtual calls** from constructors (including indirect calls through methods). See section **1.3**.
- **Event subscriptions** where the publisher might invoke handlers immediately.
- Passing `this` into other objects that can call back during construction.
- **Closures** (lambdas/local functions) capturing `this` and extending lifetime unexpectedly.

**Mentor rule**
- If you need callbacks, wire them up *after* construction in a clearly named method, or pass dependencies in and keep the object self-contained.

---

### 4) **API design and versioning**
Public constructors are **public contracts**.

Checklist:
- Keep overload sets **small** and **consistent**; avoid “half-valid” overloads.
- Prefer one “main” contract (core constructor or factory); delegate other overloads via `this(...)`. Canonical chaining: section **3.2**.
- Avoid optional parameters for public APIs when defaults might change (defaults are baked into callers). Canonical: [4.2. Optional parameters default arguments versioning correctness](<../../../05 Methods/sections/4. Passing objects and arguments/4.2. Optional parameters default arguments versioning correctness.md>).

**Good to know**
- Adding a new overload can still be source-breaking if it creates ambiguity with `null` or numeric literals (canonical: section **3.1**).

---

### 5) **Testing and maintainability**
Constructors should be easy to reason about and easy to test:

- Prefer **deterministic initialization** (no ambient/global state unless intentionally injected).
- Keep constructor logic small; move complex policies into named methods/factories (`Create`, `TryCreate`, `CreateAsync`).
- Don’t weaken domain invariants for frameworks; prefer DTOs + mapping. Canonical: section **6.2**.

**Performance note**
- “Scattered initialization” (parameterless ctor + many setters) tends to produce repeated validation and extra allocations. Centralize initialization for both correctness and speed.
