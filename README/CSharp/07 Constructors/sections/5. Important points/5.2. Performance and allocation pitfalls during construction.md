## 5.2. Performance and allocation pitfalls during construction

1. **Hidden allocations in constructors** (what allocates and how to spot it)
2. **Object graph size and “constructor does too much”** (latency, GC pressure, and testability)
3. **Static/type initialization first-touch costs** (p99 spikes and memory retention)
4. **Design rules that scale** (fast-by-default constructors; explicit expensive work)
5. **Measuring guidance** (cold-start vs steady-state; allocation profiling)

---

### 1) **Hidden allocations in constructors (what allocates and how to spot it)**
Constructors don’t allocate “because they’re constructors” — they allocate because of patterns you put inside them.

Common hidden allocations:
- **LINQ** (`ToList()`, `Select(...)`, `Where(...)`) in hot-path ctors.
- **Closures**: lambdas capturing locals or `this` allocate a closure object.
- **`params`**: call sites allocate an array (even if your ctor body is tiny).
- **Strings**: interpolation/concatenation, `ToString()` in logging, `string.Format`, culture formatting.
- **Boxing**: passing value types to `object`/interfaces, interpolated strings in some cases.

**Good to know**
- If you’re constructing many small objects (e.g., parsing a file into records), Gen0 churn becomes a throughput limiter.
- “I only allocate a little” multiplied by millions is a production issue.

**Performance note**
- Prefer clarity first, then measure. But in constructors for hot-path types, be intentionally allocation-aware.

---

### 2) **Object graph size and “constructor does too much”**
A constructor that builds a large graph (loads config, creates caches, builds lookup tables, wires events, starts timers) has predictable outcomes:

- **Hard-to-test** (construction requires environment)
- **Hard-to-profile** (cost is hidden behind `new`)
- **Hard-to-reason** (side effects before object even “exists”)
- **Tail-latency spikes** (construction on request path)

Mentor alternatives:
- Keep construction cheap; do expensive work in:
  - a factory (`Create(...)` / `CreateAsync(...)`),
  - explicit initialization (`InitializeAsync()`),
  - application startup warm-up (composition root).

See section **1.1** for the canonical “what not to do in constructors” list and patterns.

### 3) **Static/type initialization first-touch costs (p99 spikes and memory retention)**
Static initialization is a common hidden p99 killer:
- “First touch” cost happens at an unpredictable time.
- Static graphs become GC roots and can retain memory for process lifetime.

### 4) **Design rules that scale (fast-by-default constructors; explicit expensive work)**
- **Keep constructors deterministic**: no I/O, no background work, no locks.
- **Centralize validation**: one core constructor/factory; other overloads forward (see section **3.2**).
- **Prefer immutability**: it reduces later defensive copying and synchronization.
- **Avoid work duplication**: normalize once, not in every overload.

---

### 5) **Measuring guidance (cold-start vs steady-state; allocation profiling)**
If performance matters, separate concerns:

- **Cold-start**: first-touch static init, JIT tiering, cache warm-up.
- **Steady-state**: allocation rate, GC frequency, throughput, contention.

Mentor checklist:
- Profile allocations (Gen0 churn is usually the first clue).
- Measure p95/p99 latencies (constructor costs show up in tails).
- Don’t optimize “field vs property”; focus on allocations and I/O.
