## 5.3. Thread-safety and publication: when constructed objects become visible to other threads

3. **Synchronization tools** (overview only; deep dive elsewhere)
4. **Performance framing** (contention vs immutability)
5. **Where to learn more** (repo boundary)

---

### 1) **Safe publication (the minimum you must know)**
“Publishing an object” means making a reference to it reachable by other threads (storing it somewhere shared, returning it to a multi-threaded caller, registering it with a singleton, etc.).

The rule you must internalize:
- **Never let a partially constructed object escape.**

Why:
- Another thread can observe “default” values and violate invariants.
- It becomes almost impossible to reason about correctness, because the object’s lifetime has a period where it exists but is not fully initialized.

**Mentor rule**
- The easiest safe-publication strategy is **immutability**: if the object can’t change after construction, you need far less synchronization.

---

### 2) **Common escape paths during construction (bugs)**
The most common ways `this` escapes before construction is truly “done”:

- **Registering `this` into shared state**: static cache, singleton registry, global event bus.
- **Starting background work** that captures `this` (timer callback, `Task.Run`, `ThreadPool.QueueUserWorkItem`).
- **Passing `this` to another object** that can call back immediately (including virtual calls from base constructors; see section **1.3**).

**Good to know**
- Object initializers widen the “unsafe window”: constructor completes first, then assignments run (see section **4.1**). Publishing the object before the initializer completes is a subtle bug.

---

### 3) **Synchronization tools (overview only; deep dive elsewhere)**
If you must publish mutable objects:
- use `lock` for mutual exclusion,
- use `Interlocked`/`Volatile` for low-level atomicity/visibility,
- use concurrent collections for shared data structures.

But this domain is not where you should learn the memory model.

**Canonical deep references**
- Memory model, visibility, synchronization primitives, and correctness reasoning: `README/CSharp/29 Cuncurrent & Parallel`
- Static publication and initialization order implications: `README/CSharp/04 Fields`

---

### 4) **Performance framing (contention vs immutability)**
Thread-safety “after the fact” often leads to:
- contention (throughput loss),
- extra allocations (defensive copies),
- complexity (hard-to-test code).

**Performance note**
- “Make it immutable” is often faster than “add locks everywhere”, because it reduces contention and lets you safely share objects without synchronization.
