## 4.3. Builders and factories vs constructors (when you need names, steps, or async)

1. **When constructors stop being the right tool** (names, steps, async, caching)
2. **Factory patterns you should know** (modern .NET)
3. **Builder patterns (when they’re justified)**
4. **Error handling strategy** (exceptions vs Try-pattern vs result types)
5. **Versioning and API evolution** (stable creation surface)

---

### 1) **When constructors stop being the right tool**
Constructors are great when:
- there is one clear creation mode,
- inputs are available at once,
- validation is cheap and deterministic,
- creation is synchronous and side-effect-light.

Prefer a factory/builder when you need any of the following:

- **Multiple creation “modes” that need names**  
  If `new` would be ambiguous, a named factory communicates intent:
  - `Money.FromDecimal(amount, currency)`
  - `OrderId.FromGuid(guid)`
  - `ConnectionString.ParseInvariant(text)`

- **Stepwise construction / validation with partial data**  
  When you can’t validate until you have a set of fields, a builder (or options object) can stage data and validate once.

- **Async creation**  
  Constructors can’t be `async`. If creation requires I/O, use an async factory:
  - `Task<MyClient> CreateAsync(...)`

- **Caching / interning / pooling**  
  If you want to return an existing instance (flyweight/interning) or reuse resources, a factory is the seam.

**Mentor rule**
- If `new` hides meaningful meaning (“which mode?”, “which policy?”), you need a named creation API.

---

### 2) **Factory patterns you should know (modern .NET)**
Common, maintainable patterns:

#### Pattern A: static factories on the type
Use when construction is primarily about invariants and normalization.

```csharp
using System;

public sealed class Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    private Money(decimal amount, string currency)
    {
        Amount = amount;
        Currency = currency;
    }

    public static Money From(decimal amount, string currency)
    {
        if (amount < 0) throw new ArgumentOutOfRangeException(nameof(amount));
        if (string.IsNullOrWhiteSpace(currency)) throw new ArgumentException("Currency is required.", nameof(currency));
        return new Money(amount, currency.Trim().ToUpperInvariant());
    }

    public static bool TryCreate(decimal amount, string currency, out Money? money)
    {
        money = null;
        if (amount < 0) return false;
        if (string.IsNullOrWhiteSpace(currency)) return false;
        money = new Money(amount, currency.Trim().ToUpperInvariant());
        return true;
    }
}
```

#### Pattern B: dedicated factory types (DI-friendly)
Use when creation has dependencies (clock, random, config, network clients) and you want testability:

```csharp
public interface ITokenFactory
{
    string Create();
}
```

This avoids static/global dependencies and composes well in DI (see section **6.1** for DI constructor guidance).

#### Pattern C: parse/try-parse style factories
Use at boundaries. Don’t smuggle parsing into constructors unless the type’s entire purpose is parsing/normalizing input.

For detailed parsing guidance (culture, spans, performance), see the canonical `Type Conversion` domain:
- [4.1. Parse vs TryParse correctness performance and API shape](<../../../06 Type Conversion/sections/4. Parsing text to values/4.1. Parse vs TryParse correctness performance and API shape.md>)

### 3) **Builder patterns (when they’re justified)**
Builders are justified when:
- there are many optional knobs,
- you want fluent call sites,
- you need validation across multiple fields,
- you want a stable API surface as options grow.

But builders have costs:
- They add a new type and often **allocate**.
- They can obscure “what is required” unless designed carefully.

**Mentor alternative**
- Prefer an immutable options object (`sealed record` / `sealed class`) with `required` for completeness when it stays readable. Builders should be the exception, not the default.

---

### 4) **Error handling strategy**
Pick the error model deliberately:

- **Exceptions** for invariant violations / programming errors.
- **Try-pattern** for expected failures with a single boolean outcome.
- **Result types** when you need rich error information without exceptions.

See section **1.1** for the canonical “exceptions vs Try-pattern vs factories” decision guidance in this domain.

---

### 5) **Versioning and API evolution**
Factories help versioning because you can:
- add new factory overloads with names,
- add optional parameters via an options type without exploding overloads,
- keep existing creation paths stable.

**Avoid this in public APIs**
- Optional parameters whose defaults might change, because defaults are baked into callers (canonical explanation: [4.2. Optional parameters default arguments versioning correctness](<../../../05 Methods/sections/4. Passing objects and arguments/4.2. Optional parameters default arguments versioning correctness.md>)).
