### 1) **Copy intent and API contract (what does “copy” mean?)**
Before you write any copying API, answer:

- Does the copy share references to internal objects (shallow), or duplicate them (deep)?
- Does the copy preserve invariants? (It must.)
- Is the copy a **snapshot** (independent view) or a **live view** (shared internal state)?

**Mentor rule**
- Never make copying ambiguous. “Surprising aliasing” is a top source of bugs (two objects mutate the same internal list).

---

### 2) **Copy constructors (when they help, when they harm)**
A copy constructor is typically `public MyType(MyType other)` and creates a new instance from an existing one.

Copy constructors help when:
- You want an explicit, discoverable “copy” API that can enforce invariants.
- You want to copy from a known internal representation (no interface ambiguity).
- You need to normalize/validate the source once and create a consistent new object.

They harm when:
- They imply “deep copy” but actually do shallow copy (callers assume independence and get aliasing bugs).
- Your type is large/graph-like and copying becomes expensive and accidental.
- Your type represents an **entity with identity** where copying is semantically wrong (it duplicates identity).

**Example (runnable): shallow vs explicit copying of owned collection**

```csharp
using System;
using System.Collections.Generic;

public sealed class TagSet
{
    private readonly List<string> _tags;

    public IReadOnlyList<string> Tags => _tags;

    public TagSet(IEnumerable<string> tags)
        => _tags = new List<string>(tags ?? throw new ArgumentNullException(nameof(tags)));

    // Copy constructor creates a snapshot (new list).
    public TagSet(TagSet other)
        => _tags = other is null ? throw new ArgumentNullException(nameof(other)) : new List<string>(other._tags);
}
```

**Good to know**
- If your type owns mutable state, copy constructors should usually create **new owned mutable objects** (like a new list) to avoid shared-mutation surprises.

### 3) **Shallow vs deep copy (and why deep copy is usually a red flag)**
- **Shallow copy**: copies references; both objects share sub-objects.
- **Deep copy**: duplicates an entire object graph.

Deep copy is often a red flag because:
- Cycles and shared subgraphs make “deep” ambiguous.
- It is expensive and easy to get wrong.
- It tends to hide performance costs (mass allocations).

### 4) **Modern alternatives (C# 15 era)**
Prefer designs that reduce or eliminate the need for copying:

- **Immutability**: if the type is immutable, “copying” is often just reusing the same instance.
- **Records + `with`**: great for immutable value objects. (See section **2.3** for records guidance in this domain.)
- **Explicit “copy-with-changes” APIs**: make intent clear and keep invariants centralized.

**Example: explicit copy-with-changes**

```csharp
using System;

public sealed class RetryPolicy
{
    public int MaxRetries { get; }
    public TimeSpan BaseDelay { get; }

    public RetryPolicy(int maxRetries, TimeSpan baseDelay)
    {
        if (maxRetries < 0) throw new ArgumentOutOfRangeException(nameof(maxRetries));
        if (baseDelay < TimeSpan.Zero) throw new ArgumentOutOfRangeException(nameof(baseDelay));
        MaxRetries = maxRetries;
        BaseDelay = baseDelay;
    }

    public RetryPolicy With(int? maxRetries = null, TimeSpan? baseDelay = null)
        => new(maxRetries ?? MaxRetries, baseDelay ?? BaseDelay);
}
```

**Mentor note**
- For public libraries, be careful with optional parameters’ default values (versioning). Here we use nullable overrides (`null` means “keep existing”), which avoids the “caller-baked default” pitfall. For the canonical optional-parameter versioning story, see `README/CSharp/05 Methods/sections/4. Passing objects and arguments/4.2. Optional parameters default arguments versioning correctness.md`.

### 5) **Performance and safety notes (allocations, aliasing, defensive copying)**
- Copying large graphs increases allocations and GC pressure; avoid accidental copies on hot paths.
- Defensive copying is sometimes necessary at trust boundaries (public APIs receiving arrays/lists), but it should be explicit and documented.
- Avoid “automatic cloning” (e.g., `ICloneable`) because it doesn’t define the copy depth/contract; prefer explicit APIs with clear semantics.
