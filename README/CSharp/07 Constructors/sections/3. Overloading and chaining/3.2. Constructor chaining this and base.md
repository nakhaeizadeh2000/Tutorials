## 3.2. Constructor chaining: `this(...)` and `base(...)` (centralize invariants)

1. **What chaining is** (and what it is not)
2. **`this(...)` chaining patterns** (one “core” ctor)
3. **`base(...)` and inheritance boundaries**
4. **Avoid duplicated work and inconsistent behavior across overloads**
5. **Pitfalls** (virtual calls, leaking `this`, order assumptions)
6. **Best practices (C# 15 era)**

---

### 1) **What chaining is (and what it is not)**
Constructor chaining is how you ensure multiple constructors in the same type produce **the same valid state** without duplicating logic.

- `this(...)` calls **another constructor in the same type**.
- `base(...)` calls a **constructor on the base type**.

What it is *not*:
- Not “run two constructors”: only one constructor body in your type actually runs; the others delegate.
- Not a replacement for initialization order knowledge. Base/derived ordering still applies (see section **1.3**).

---

### 2) **`this(...)` chaining patterns (one “core” ctor)**
The canonical pattern is: **one core constructor** establishes invariants; all other overloads forward to it.

**Example (runnable): one core constructor**

```csharp
using System;

public sealed class RetryPolicy
{
    public int MaxRetries { get; }
    public TimeSpan BaseDelay { get; }

    public RetryPolicy(int maxRetries, TimeSpan baseDelay)
    {
        if (maxRetries < 0) throw new ArgumentOutOfRangeException(nameof(maxRetries));
        if (baseDelay < TimeSpan.Zero) throw new ArgumentOutOfRangeException(nameof(baseDelay));

        MaxRetries = maxRetries;
        BaseDelay = baseDelay;
    }

    // Convenience overloads delegate to the core ctor.
    public RetryPolicy() : this(maxRetries: 3, baseDelay: TimeSpan.FromMilliseconds(200)) { }
    public RetryPolicy(int maxRetries) : this(maxRetries, baseDelay: TimeSpan.FromMilliseconds(200)) { }
}
```

**Mentor rule**
- Never let “convenience overloads” skip validation or set different semantics. If overload A and B produce objects with different invariants, they should be different *types* or named factories.

---

### 3) **`base(...)` and inheritance boundaries**
`base(...)` is where you communicate your dependency on base invariants.

Design boundary:
- The **base** constructor must not depend on derived state.
- The **derived** constructor must assume base invariants are satisfied after `base(...)` returns, but must not assume base called derived virtual logic safely.

If you need customization at construction time, prefer:
- passing data into `base(...)`, or
- composition (inject a strategy object), rather than
- virtual calls from constructors.

---

### 4) **Avoid duplicated work and inconsistent behavior across overloads**
Duplication leads to:
- bugs (“this overload forgot to validate X”),
- performance waste (same expensive normalization repeated),
- versioning pain (every overload must be updated consistently).

**Performance note**
- The simplest win is often to centralize normalization (e.g., `Trim()`, case normalization, precomputed derived values) in the core ctor so it runs once.

---

### 5) **Pitfalls**
- **Calling virtual members during construction**: see section **1.3** for why this breaks correctness.
- **Leaking `this`**: subscribing to events, passing `this` to callbacks, or publishing the instance from the constructor lets other code see partial state.
- **Assuming object initializers are “part of the constructor”**: object initializer assignments run *after* the constructor body. See section **4.1**.

---

### 6) **Best practices (C# 15 era)**
- Prefer fewer overloads; if you need many creation modes, use **named factories** (see section **4.3**).
- Avoid optional parameters for public APIs when defaults may change over time; prefer overloads or factories (canonical optional-parameter versioning: `README/CSharp/05 Methods/sections/4. Passing objects and arguments/4.2. Optional parameters default arguments versioning correctness.md`).
- Keep constructors cheap and deterministic; defer heavy work to explicit methods when needed (section **1.1**).
