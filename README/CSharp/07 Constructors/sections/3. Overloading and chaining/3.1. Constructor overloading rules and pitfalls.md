## 3.1. Constructor overloading rules (and how overload resolution bites)

1. **Overload resolution basics at construction time**
2. **Ambiguity traps** (`null`, numeric literals, `default`, optional parameters, `params`)
3. **Behavior consistency rule** (all overloads must produce valid objects)
4. **API design guidance** (avoid “overload soup”; prefer named factories where it improves intent)
5. **Performance notes** (avoid duplicate work; avoid hidden allocations at call sites)

---

### 1) **Overload resolution basics at construction time**
Constructor overload resolution works like method overload resolution: the compiler picks the “best” candidate based on argument types, conversions, and applicable overloads.

What mentors care about:
- Overload sets are part of your **public API design**. Every new overload is a new ambiguity surface.
- You don’t want call sites to depend on subtle rules like “better conversion” or “tie-breakers”.

**Good to know**
- If you ever need to explain why the compiler picked an overload, your overload set is probably too clever.
- The deep general rules are covered in one place: see `README/CSharp/05 Methods/sections/5. Overload resolution and overloading/5.1. Method overloading rules ambiguity API design.md`. This file focuses on constructor-specific design rules and common traps.

---

### 2) **Ambiguity traps (`null`, numeric literals, `default`, optional parameters, `params`)**
These are the constructor overload traps that repeatedly cause production bugs or painful refactors.

#### Trap A: `null` ambiguity
If you overload by reference types, `null` can match multiple overloads:

```csharp
public sealed class Widget
{
    public Widget(string name) { }
    public Widget(Uri endpoint) { }
}

// new Widget(null); // ERROR: ambiguous
```

**Mentor fixes**
- Don’t overload on unrelated reference types when `null` is a meaningful input.
- Prefer **named factories**: `Widget.FromName(...)`, `Widget.FromEndpoint(...)`.
- Or use one overload with a discriminated shape (e.g., `Widget(WidgetOptions options)`).

#### Trap B: numeric literal ambiguity (and “int by default”)
Numeric literals like `0` are `int` by default. Overloads with `byte`, `short`, `long`, `float`, `double`, etc. can become surprising or ambiguous.

**Mentor rule**
- Avoid overloads that differ only by numeric widths unless you have a very strong reason (low-level libraries).

#### Trap C: `default` / `default(T)` ambiguity
`default` can match many overloads and may silently choose a “wrong” one when new overloads are added.

**Mentor fix**
- Don’t design overloads where `default` is commonly passed. Prefer explicit `null`/`0`/`TimeSpan.Zero` etc., or named factories.

#### Trap D: optional parameters as “overloads”
Optional parameters are tempting for constructors, but they have versioning hazards: default values are **baked into the caller** at compile time.

**Canonical reference**
- See `README/CSharp/05 Methods/sections/4. Passing objects and arguments/4.2. Optional parameters default arguments versioning correctness.md`.

**Mentor rule**
- For public APIs (especially libraries), prefer **real overloads** or named factories over optional parameters.

#### Trap E: `params` arrays allocate
`params` makes call sites ergonomic but often allocates an array.

```csharp
public sealed class Logger
{
    public Logger(params string[] sinks) { }
}

var l = new Logger("a", "b"); // allocates string[] { "a", "b" }
```

**Mentor alternatives**
- If you need high-performance bulk inputs, prefer overloads accepting `ReadOnlySpan<T>` (where appropriate) or `IReadOnlyList<T>` / `IEnumerable<T>` with clear ownership semantics.

### 3) **Behavior consistency rule (all overloads must produce valid objects)**
Every public constructor overload must establish **the same invariants** and create an instance in a valid state.

Bad patterns:
- One overload “forgets” to validate.
- One overload sets different defaults (behavior drift).
- One overload creates a partially initialized object “to set later”.

**Mentor pattern: one core ctor**
- Have a single “core” constructor do all validation.
- All other overloads forward via `this(...)` to the core.

See section **3.2** for constructor chaining patterns.

---

### 4) **API design guidance (avoid overload soup; prefer named factories where it improves intent)**
Overloads scale poorly when:
- There are many optional features.
- There are multiple creation modes.
- Parameter lists become long and confusing.

Prefer:
- **Named factories** when the creation mode is meaningful:
  - `Money.FromDecimal(...)`
  - `Money.ParseInvariant(...)`
  - `Money.TryCreate(...)`
- **Options objects** when there are many optional knobs and you want future extensibility without overload explosion.

**Versioning note**
- Adding a new overload can still be source-breaking if it makes existing call sites ambiguous. Keep overload sets small.

---

### 5) **Performance notes (avoid duplicate work; avoid hidden allocations at call sites)**
Construction performance is usually dominated by:
- repeated validation performed in multiple overloads
- hidden allocations (LINQ, closures, `params`, string formatting)
- building object graphs eagerly

Mentor rules for fast, maintainable construction:
- Centralize validation in one place (core ctor or factory).
- Keep constructor logic cheap and deterministic (no I/O; no background work).
- Use factories for expensive setup so callers can choose when to pay the cost.
