## 2.1. Block-scoped namespaces: `namespace X { ... }`

1. **Syntax rules** (where it can appear; nesting types; multiple namespaces per file)
2. **Readability guidance** (limit indentation; don’t mix unrelated namespaces in one file)
3. **When to keep block-scoped** (generated code; files with multiple namespaces; special layout needs)

### 1. **Syntax rules**
Block-scoped namespaces are the “classic” form:

```csharp
namespace Company.Product.Feature
{
    public sealed class Widget { }
}
```

Key rules (modern C# / .NET):
- **Placement**: `namespace X { ... }` can appear after `using` directives at the top of the file, and you can have **multiple block-scoped namespaces** in one `.cs` file (legal, but usually discouraged for maintainability).
- **Nesting**: You can nest `namespace` blocks, but prefer dotted names (`namespace A.B.C {}`) for readability. See section **3.1** for the equivalence and guidance.
- **File-scope interaction**: A file can use **either** a file-scoped namespace (`namespace X;`) **or** block-scoped namespaces, **not both**. See section **2.2** for the full rules.
- **Where `using` can go**:
  - With **block-scoped**, `using` directives can be at the top-of-file (apply to the whole file) *or* inside the `namespace {}` block (apply only within that namespace block).
  - This matters when a single file intentionally contains multiple namespaces: you can scope imports per namespace block.

**Good to know**
- If you must put `using` directives inside a namespace block, treat it as a signal: the file is doing something “special”. Prefer splitting into separate files unless you have a concrete reason (e.g., source generation output, special compilation layout).

#### Minimal, runnable example (scoped `using` inside a namespace block)

```csharp
// Demonstrates that "using inside namespace" can limit scope in multi-namespace files.

namespace Demo.A
{
    using System.Text;

    public static class A
    {
        public static string BytesToHex(byte[] bytes) =>
            Convert.ToHexString(bytes); // Convert is in System
    }
}

namespace Demo.B
{
    // No "using System.Text" here. Different namespace block, different using scope.
    public static class B { }
}
```

### 2. **Readability guidance**
Block-scoped namespaces add **one indentation level** to every type in the file. The cost is small per file, but large across a codebase.

Mentor guidance:
- **Prefer file-scoped namespaces** as the default in new code (section **2.2**).
- **Keep “one namespace per file”** unless you have a strong reason. Multiple namespaces in one file harms searchability and increases review cognitive load.
- **Avoid deep nesting**: Namespaces should be shallow and domain-oriented; don’t use nesting to mimic folder structures beyond what helps discoverability (see **3.1**).

**Common mistakes**
- **Mixing unrelated concerns** in one file under different namespaces “because it compiles”: it creates long-lived maintenance debt.
- **Large indentation + wide lines**: pushing code past typical width limits reduces readability and increases diff noise.

### 3. **When to keep block-scoped**
Even in modern C# codebases, block-scoped namespaces still have legitimate uses:

- **Generated code**: generators often emit multiple namespaces/types into a single file; block-scoped provides flexibility and keeps compatibility with older tooling.
- **Multiple namespaces per file (rare, but real)**: e.g., tightly-coupled interop types that must be co-located, or multi-targeted shims where layout is intentional.
- **Namespace-scoped `using` directives**: when you truly need distinct import sets per namespace in the same file.
- **Special formatting/region layouts**: some code style policies in legacy repos still require it (but prefer modernizing rather than entrenching).

**Performance note**
- Namespace style has **no runtime performance impact**. The “cost” is human time: indentation noise, diff size, and the odds of accidental coupling when multiple namespaces share a file.
