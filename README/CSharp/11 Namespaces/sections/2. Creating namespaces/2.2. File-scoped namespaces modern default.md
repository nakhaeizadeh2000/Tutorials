## 2.2. File-scoped namespaces: `namespace X;` (modern default)

1. **What it changes** (removes one indentation level; applies to the whole file)
2. **Rules and limitations** (exactly one file-scoped namespace per file; cannot be combined with block-scoped in the same file)
3. **When it helps** (large codebases; analyzers/formatters; consistent style)

### 1. **What it changes**
**File-scoped namespaces make the namespace declaration apply to the entire file without an extra `{ ... }` block.** This removes one indentation level and tends to reduce “rightward drift” in modern C# code (especially with `record`, pattern matching, and nested types).

Compare:

```csharp
// Block-scoped
namespace Company.Product.Payments
{
    public sealed class ChargeService
    {
        // ...
    }
}
```

```csharp
// File-scoped (recommended default for new code)
namespace Company.Product.Payments;

public sealed class ChargeService
{
    // ...
}
```

**Good to know**
- File-scoped namespaces pair naturally with modern C# conventions: one type per file, top-level `using` directives, and analyzer-enforced formatting.
- They also reduce merge conflicts in large teams because fewer braces and less indentation change when you add/remove members.

### 2. **Rules and limitations**
The compiler rules are simple but strict:

- **Exactly one** file-scoped namespace per file.
- It must appear **before any type declarations** in that file.
- You **cannot mix** file-scoped and block-scoped namespaces within the same file.
- You can still place `using` directives at the top of the file; they apply as usual (see **4.1** for full rules and scope details).

**Common mistakes**
- **Trying to declare multiple namespaces in the same file** using file-scoped form. If you truly need multiple namespaces in one file (uncommon; sometimes in generated code), use block-scoped namespaces instead. See **2.1**.
- **Putting code before `namespace X;`** (other than comments, `using` directives, and attributes that are allowed in that position). Keep the file header clean.

### 3. **When it helps**
File-scoped namespaces are a net win when:

- **You have many files** and want consistent style with minimal indentation.
- **You use analyzers/formatters** (e.g., `.editorconfig`) and want an easy “modern default”.
- **You’re building libraries** where readability and predictable file layout matter for code review and onboarding.

**When not to use it**
- **Generated code** where tools expect block-scoped structure or emit multiple namespaces per file.
- **Special files** that intentionally contain multiple namespaces (rare in hand-written code).

**Performance note**
- This is purely a syntactic feature. It does not change runtime behavior, allocations, JIT output, or threading. The “performance” benefit is developer-time: less indentation noise and fewer braces to maintain.
