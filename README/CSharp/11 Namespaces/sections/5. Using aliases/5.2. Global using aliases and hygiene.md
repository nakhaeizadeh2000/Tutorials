## 5.2. `global using` aliases and “API surface hygiene”

1. **When it’s appropriate** (shared cross-cutting types; common BCL aliases are usually unnecessary)
2. **Avoid abuse** (don’t create a mini-DSL of aliases that new engineers can’t grep for)
3. **Interop benefit** (bridge legacy namespaces while migrating)

### 1. **When it’s appropriate**
**A `global using` alias is best when it reduces *repeated, mechanical noise* across many files without hiding important dependencies.**

Typical good uses:
- **Resolve a pervasive collision** once, in one place:
  - Two packages expose `JsonSerializer`, `Task`, `ValueTask`, `Logger`, etc.
- **Give a long namespace/type a stable “project nickname”** that matches your domain language.
- **Centralize platform-conditioned aliases** (multi-targeting) to keep `#if` noise out of your main code.

Typical *unnecessary* uses:
- **Aliasing common BCL types** (`String`, `Int32`, `List<T>`). This usually *reduces clarity* because it diverges from every C# developer’s expectations.
- **Renaming frameworks to “cute” names**. It reads like a DSL and hurts onboarding.

**Where to put them**
- Prefer a single `GlobalUsings.cs` (or a small set, like `GlobalUsings.*.cs`) at the project root.
- Keep `global using` lists *short* and stable; if they churn a lot, you’re pushing local decisions into global scope.

**Good to know**
- `global using` is implicitly applied to every file *in that compilation*. It does not “flow” across project references; each project decides its own globals.
- SDK-style projects can also enable **implicit global usings** (e.g., `ImplicitUsings`), but that’s a project setting; treat it as a baseline convenience, not an excuse to hide dependencies. (See section **4.2** for the full `global using` discussion.)

### 2. **Avoid abuse**
The hygiene rule: **if removing the global alias would make a file’s dependencies unclear, it probably shouldn’t be global.**

Common failure modes:
- **“Spooky action at a distance”**: a file compiles only because a global alias exists, and the file gives no clue where that alias is defined.
- **Mini-DSL syndrome**: dozens of global aliases that replace normal names. Search/grep and code review become painful.
- **Local intent becomes global policy**: a one-off disambiguation becomes a project-wide convention, even where it doesn’t help.

**Mentor practices (what to enforce in reviews)**
- **Limit scope first**: prefer file-level aliases (`using Foo = ...;`) unless the alias is used broadly.
- **Prefer explicitness in libraries**: for reusable libraries, consider *fewer* global aliases to keep code portable and predictable for contributors.
- **Name aliases like types/namespaces**: `PaymentsJson` is better than `J`. Favor clarity over brevity.

### 3. **Interop benefit**
Global aliases can be a pragmatic migration bridge when modernizing a codebase:

- **Legacy namespace rename**: keep old call sites readable while you incrementally update:
  - Example: your old namespace `Legacy.Payments` is being replaced by `Company.Product.Payments`.
- **Third-party API transitions**: if you swap packages that expose similar shapes, a controlled alias can reduce churn during the migration period.

#### Example: bridging two namespaces while migrating

```csharp
// GlobalUsings.cs
global using PaymentsApi = Company.Product.Payments;
// During migration you might temporarily map to Legacy.Payments instead:
// global using PaymentsApi = Legacy.Payments;
```

```csharp
// Anywhere in the project
namespace Demo;

public static class BillingFlow
{
    public static PaymentsApi.Charge CreateCharge() => new();
}
```

**Good to know**
- Treat “migration aliases” as **temporary**. Put them on a shortlist to remove; otherwise you permanently encode history into your API vocabulary.
