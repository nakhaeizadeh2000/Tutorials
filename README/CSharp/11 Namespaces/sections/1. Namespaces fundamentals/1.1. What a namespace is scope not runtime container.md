## 1.1. What a namespace is (scope + name, not a runtime container)

1. **Mental model** (namespaces are compile-time naming scopes; they don’t “contain” types at runtime)
2. **Why they matter** (avoid naming collisions; communicate API intent; scale codebases)
3. **Performance reality** (namespace choice doesn’t affect runtime speed directly; it affects design, build, and tooling ergonomics)

### 1. **Mental model**
**Namespace = a *name* (a qualifier) the compiler uses to form a type’s fully-qualified name.** It is not a runtime container, not a module loader, and not a memory boundary.

- **At compile time**: `namespace` participates in *name lookup* (which `User` type did you mean?) and *type identity* (two `User` types in different namespaces are different types).
- **At runtime**: the CLR cares about **assemblies** and **type full names** (namespace + type name). A namespace itself doesn’t “exist” as an object you can enumerate to find types.
- **Where the name is used**:
  - **Metadata**: the type is recorded with `Namespace` + `Name`.
  - **Reflection**: `typeof(MyType).Namespace` returns a string; it’s metadata, not a container.

**Good to know**
- **`namespace` is about *disambiguation* and *discoverability***. If you want runtime boundaries (loading, versioning, deployment), that’s **assemblies + packages**. See section **1.2** for the quick map and section **3.2** for API design consequences.

#### Minimal, runnable example (type identity + name lookup)

```csharp
// Compile with: dotnet build (any modern .NET)
// Demonstrates that namespaces separate type identities.

namespace Billing;
public sealed class User { public override string ToString() => "Billing.User"; }

namespace Identity;
public sealed class User { public override string ToString() => "Identity.User"; }

namespace Demo;

using BillingUser = Billing.User;
using IdentityUser = Identity.User;

public static class Program
{
    public static void Main()
    {
        var a = new BillingUser();
        var b = new IdentityUser();

        Console.WriteLine(a); // Billing.User
        Console.WriteLine(b); // Identity.User
        Console.WriteLine(a.GetType().FullName);
        Console.WriteLine(b.GetType().FullName);
        Console.WriteLine(a.GetType() == b.GetType()); // False
    }
}
```

### 2. **Why they matter**
Namespaces are one of the cheapest architecture tools you have: they “shape” code without adding runtime cost.

- **Avoid naming collisions**: Especially in real solutions where you combine BCL types + your types + NuGet packages.
- **Communicate intent**: `Company.Product.Payments` tells a reader more than `Helpers`.
- **Scale collaboration**: Teams can own namespaces as “API slices” with consistent conventions.
- **Support layering**: Namespaces are a good “hint” for architecture boundaries (though not enforcement by themselves). For enforcement, combine with `internal`, `InternalsVisibleTo`, analyzers, and packaging boundaries (covered elsewhere; see section **8.1**).

**Common mistakes**
- **Using namespaces to hide poor modularity**: A deep tree of namespaces doesn’t fix cyclic dependencies or unclear ownership; it can *hide* them.
- **Overusing “utility” buckets** (`.Helpers`, `.Common`, `.Utils`): They become dumping grounds; discovery and ownership degrade. See section **3.1** for naming guidance.
- **Treating namespace = security boundary**: It is not. Use access modifiers and assembly boundaries for encapsulation. See section **8.1** for where those topics live in this repo.

### 3. **Performance reality**
**Changing a namespace does not change runtime CPU speed, allocations, threading, GC, or inlining.** It is a compile-time and tooling construct.

What *can* be impacted indirectly:
- **Build times (large solutions)**: `global using` and broad `using` sets can increase compilation work and can change overload/extension method candidate sets. The effect is usually small, but in huge solutions it can matter. See section **4.2** for guidance.
- **Developer time (which is performance too)**: ambiguous names, “spooky” global imports, and inconsistent conventions increase time-to-change and defect rates. Sections **7.1** and **7.2** are the mentor checklists for this.

**Performance note**
- **Runtime perf is about what you call**, not how you named it. If a naming decision makes people choose the wrong API (e.g., confusing extension methods due to ambiguous imports), that’s an *indirect* correctness/performance risk—covered in sections **4.1** and **7.2**.
