## 9.1. Common interview questions: namespaces, file-scoped namespaces, global usings, aliases

1. **Explain namespace purpose and mechanics** (compile-time scope; collisions; API discoverability)
2. **Block-scoped vs file-scoped namespaces** (rules, benefits, and when not to use file-scoped)
3. **`using` vs fully-qualified names vs aliases** (trade-offs, collisions, readability)
4. **`global using` and large solution strategy** (where to put them; how to avoid hidden deps)
5. **`using static`** (when it’s acceptable; why it can be a readability trap)

### 1. **Explain namespace purpose and mechanics**
**Interview-grade answer:** A namespace is a **compile-time naming scope** that contributes to a type’s **fully-qualified name** and helps the compiler resolve symbols. It improves **discoverability** and prevents **name collisions**, but it’s not a runtime container and not an encapsulation boundary.

- **Key points to hit**
  - **Compile-time**: affects name lookup and type identity.
  - **Runtime**: the CLR loads **assemblies**; namespaces are metadata strings attached to types.
  - **Practical impact**: influences how consumers find your APIs and how often ambiguity happens.

**Where to go deep:** See **section 1.1** for the full mental model and a runnable type-identity example.

**Common follow-up trap**
- “Does namespace affect performance?”  
  - **Answer**: not directly (no CPU/GC effect), but poor conventions can cause **wrong API usage**, ambiguity, and maintainability issues. See **1.1** and **7.1**.

### 2. **Block-scoped vs file-scoped namespaces**
**Interview-grade answer:** File-scoped namespaces (`namespace X;`) reduce indentation and are the modern default for “one namespace per file.” Block-scoped namespaces (`namespace X { ... }`) are still useful when a file must contain multiple namespaces (rare, usually generated code or special layout needs).

- **What to mention**
  - **File-scoped**: exactly one per file; applies to the whole file.
  - **Block-scoped**: supports multiple namespaces in one file; increases indentation.
  - **Style**: consistency matters more than personal preference in large repos.

**Where to go deep:** See **2.1** and **2.2** for exact rules, limitations, and guidance.

### 3. **`using` vs fully-qualified names vs aliases**
**Interview-grade answer:** Prefer normal `using` directives for readability; use **fully-qualified names** or **aliases** to resolve ambiguity or make key types explicit. Aliases are the best tool when you have type-name collisions or you want to freeze a meaning locally.

- **Trade-offs**
  - **`using`**: clean code, but can introduce ambiguity and extension-method surprises.
  - **Fully-qualified**: unambiguous, but noisy; good for rare or “high-risk” names.
  - **Aliases**: explicit and readable when collisions exist; treat as a local contract.

**Where to go deep:** See **4.1** for scope/ordering/correctness gotchas and **5.1** for alias patterns.

### 4. **`global using` and large solution strategy**
**Interview-grade answer:** `global using` reduces repetition, but it’s easy to overuse and create hidden dependencies. In libraries, keep global usings **minimal and boring**; in applications, use them for ubiquitous BCL namespaces and stable cross-cutting concerns.

- **Best practices to mention**
  - Put them in a single obvious place (e.g., `GlobalUsings.cs`) so reviewers can reason about them.
  - Avoid globals for “feature-specific” namespaces.
  - Be cautious with globals that bring in lots of extension methods.

**Where to go deep:** See **4.2** for guidance and **7.2** for the “spooky action at a distance” failure mode.

### 5. **`using static`**
**Interview-grade answer:** `using static` is a readability tool for narrow domains (math-like APIs, constants) but can reduce code searchability and make origins unclear—especially in shared libraries. Use sparingly; prefer explicit qualification where ambiguity or onboarding cost is high.

**Where to go deep:** See **6.1** and **6.2** for safe usage rules and how it compares to extension methods and local functions.
