## 3.2. Namespace design as API design (public surface and versioning)

1. **Public namespace stability** (treat public namespaces like public method signatures)
2. **Layering** (e.g., `.Abstractions`, `.Internal`, `.Implementation`; keep contracts separate from concrete types)
3. **Tooling and discoverability** (IntelliSense search paths; consistent naming reduces cognitive load)

### 1. **Public namespace stability**
If you publish code for other projects to consume (shared internal libraries, NuGet packages, SDKs), **your public namespaces are part of your public contract**.

- **Source compatibility**: Consumers write `using Company.Product.Feature;` and refer to types by name. Moving a type changes `using`/qualification and breaks builds.
- **Binary / reflection compatibility**: Anything using reflection by full name (`"Company.Product.Feature.Widget, MyAssembly"`) can break when namespaces move.
- **Docs and discoverability**: Namespace changes break mental models, documentation links, and onboarding materials.

**Mentor guidance**
- **Prefer stability over perfection**: If a namespace is “slightly imperfect” but widely used, changing it usually costs more than it saves.
- **Do not “shuffle to tidy”**: Avoid cosmetic namespace reorganizations in public libraries; do them only with a clear product-level reason and a migration plan.
- **Avoid “temporary” public namespaces**: If something is experimental, keep it `internal` or put it under a clearly experimental namespace and document that policy.

**Good to know**
- If you need to move types internally without breaking consumers, typical strategies include:
  - **Leave a forwarding type** (obsolete wrapper) in the old namespace that points to the new type.
  - **Keep old namespace as thin facades** while new namespace hosts the “real” implementation.
  - **Multi-targeted packages** or “compat” packages (heavier; use only when truly necessary).

#### Minimal example (namespace move is a breaking change)

```csharp
// v1 (published)
namespace Company.Product.Payments;
public sealed class PaymentRequest;

// v2 (breaking change if moved)
namespace Company.Product.Billing;
public sealed class PaymentRequest;
```

### 2. **Layering**
Namespaces can communicate architecture. Done well, they reduce coupling and make it harder to “accidentally” depend on the wrong layer.

Typical patterns:

- **`.Abstractions`**: interfaces/contracts intended for broad consumption.
- **`.Internal`**: implementation details that should not be referenced by most code. Use `internal` access too; namespace alone is not enforcement.
- **`.Implementation` / `.Runtime` / `.Infrastructure`**: concrete implementations, adapters, and host-specific code.

**Trade-offs**
- **Pro**: Clear code navigation; better IntelliSense grouping; easier to enforce policies with analyzers (“no reference from `Core` to `Infrastructure`”).
- **Con**: Over-layering can create ceremony and artificial boundaries; you can end up with “interfaces for everything” without a reason.

**Common mistakes**
- **Using namespaces as an access control mechanism**: They are not. Use `internal`, project boundaries, and analyzer rules.
- **Putting contracts and implementations together**: If consumers must reference your implementation namespace, your “contract layer” isn’t a contract layer.

**Performance note**
- Layering is mostly about correctness and maintainability. Runtime performance comes from dependencies and code paths, not namespace strings.

### 3. **Tooling and discoverability**
In large codebases, the “API you experience” is what IDE tools expose. Namespace design strongly affects that experience.

- **IntelliSense**: coherent namespaces make type discovery fast; grab-bag namespaces force searches.
- **Searchability**: predictable naming patterns make `Ctrl+T`/search results meaningful.
- **Documentation**: namespaces become headings in API docs; keep them consistent and not overly deep.

**Practical guidance (what to optimize for)**
- **Optimize for readers**: stable, domain-based names that reflect what a consumer thinks in.
- **Keep it shallow**: deep nesting increases typing, line length, and cognitive load.
- **Avoid “junk drawer” sub-namespaces**: `.Helpers`, `.Common`, `.Misc` usually indicate unclear ownership; see section **3.1** for naming guidance.
