## 3.1. Nested namespaces: `A.B.C` vs nested blocks

1. **Equivalence** (`namespace A.B.C` vs `namespace A { namespace B { namespace C { ... }}}`)
2. **Naming guidance** (domain-based; keep it shallow; avoid “junk drawers” like `.Helpers`)
3. **API evolution** (moving public types between namespaces is a breaking change for consumers)

### 1. **Equivalence**
**`namespace A.B.C` and nested `namespace` blocks define the same fully-qualified names.** The difference is purely *syntax and formatting*, not runtime behavior.

- **Dotted form** (modern, usually best):

```csharp
namespace Company.Product.Payments;

public sealed class ChargeService;
```

- **Nested blocks** (equivalent identity, more indentation):

```csharp
namespace Company
{
    namespace Product
    {
        namespace Payments
        {
            public sealed class ChargeService;
        }
    }
}
```

**Good to know**
- In modern codebases targeting current .NET, **file-scoped + dotted namespaces** are the default style for readability (see section **2.2**).
- Use nested blocks only when you need block-scoped behavior (multiple namespaces per file, generator output, or a file that intentionally contains multiple logical roots). See section **2.1**.

### 2. **Naming guidance**
**A namespace is part of your architecture vocabulary.** Optimize for:
- **Coherence**: types in the same namespace should “belong together” and change for similar reasons.
- **Discoverability**: consumers should find types where they expect.
- **Stability**: avoid churn; rename/move less often than you refactor internal code.

#### A mentor-approved naming shape
- **Top-level**: `Company.Product` (or `Org.Product`)
- **Domain slice**: `.Payments`, `.Identity`, `.Orders`
- **Optional** sub-slices: `.Payments.Integration`, `.Payments.Processing`

#### What to avoid (and why)
- **“.Helpers/.Utils/.Common”**: these become dumping grounds; ownership and intent rot.
- **Too-deep trees**: deep nesting increases friction (“where do I put this?”). Prefer **shallower namespaces** and keep files organized by folders if you need extra grouping (folders are flexible; namespaces are API).
- **Namespace = layer enforcement**: naming hints are not enforcement. If you need enforcement, use `internal`, analyzers, and project/package boundaries (see section **8.1**).

**Common mistakes**
- **Mirroring every folder level into namespaces**: you end up with verbose namespaces that encode low-value structure.
- **Using namespaces as “tags”**: e.g., putting “Async”, “Impl”, “V2”, “Experimental” everywhere. Use types/assembly boundaries and documentation where appropriate; reserve namespace splits for meaningful API groupings (see **3.2**).

### 3. **API evolution**
**Moving a public type to a different namespace is a breaking change** for most consumers because their source uses the old fully-qualified name (directly or via `using`).

Typical breakages:
- **Compile failures**: `using Old.Namespace;` no longer resolves.
- **Reflection / serialization**: some systems use full type names (or assembly-qualified names). Renames can break deserialization, DI container scanning, plugin discovery, and configuration that names types.

#### Migration strategies (production reality)
- **Avoid moving public types unless there’s a strong reason.**
- If you must:
  - **Keep the old type as a shim** when feasible: leave a forwarding type in the old namespace that delegates to the new one (works best for interfaces, small wrappers, or obsolete types).
  - **Use `[Obsolete]`** with a clear message and a removal plan.
  - **Provide a codemod** (Roslyn analyzer/code fix) for large consumer bases.

**Performance note**
- Namespace moves don’t affect runtime performance, but they can cause **large downstream rebuilds** and **migration churn**. Treat them like API-breaking refactors, not “cleanup”.
