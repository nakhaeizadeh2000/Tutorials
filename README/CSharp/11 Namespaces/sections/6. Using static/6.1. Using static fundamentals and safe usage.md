## 6.1. `using static` fundamentals and safe usage

1. **Typical use** (`Math`, `Decimal`, `Array`, well-scoped helper classes)
2. **Readability trade-off** (implicit origins; can harm code search and onboarding)
3. **Recommendation** (use sparingly; prefer explicit qualification in libraries and shared code)

### 1. **Typical use**
`using static` imports the **static members** of a type so you can refer to them **without qualifying** the type name.

```csharp
using static System.Math;

var r = Sqrt(9);     // instead of Math.Sqrt(9)
var x = Clamp(5, 0, 3);
```

**When it is a good fit**
- **Math/primitive helpers**: `System.Math`, `System.MathF`, `System.BitOperations`, `System.Convert` (sparingly), `System.MemoryExtensions` (rarely—see note below).
- **Tests**: It can reduce noise in unit tests where readability wins and ambiguity is less costly.
- **Very local “vocabulary”**: a file that is essentially an implementation of a formula, parser, or algorithm where the imported members are the “language” of the file.

**When it is usually a bad fit**
- **Shared library/public API code**: consumers and maintainers pay the readability/searchability tax.
- **Types with many common member names** (`Create`, `From`, `Parse`, `TryParse`): you invite ambiguity and code-review confusion.
- **Extension-heavy static classes** (e.g., `System.Linq.Enumerable`): it hides where operators come from and makes it harder to spot allocations/deferred execution. Prefer explicit `Enumerable.` or query syntax as appropriate.

**Good to know**
- `using static` does **not** import extension methods “as extensions”. It imports static members; extension method invocation still depends on normal extension method rules and the namespace that contains the static class. For the full “extension method selection can change” story, see section **4.1**.

### 2. **Readability trade-off**
The trade-off is not runtime—it’s **human time**:

- **Implicit origin**: `Clamp(...)` gives you no clue whether it is `Math.Clamp`, a local helper, or another imported type.
- **Harder code search**: you can’t search for `Math.Clamp` because the call site no longer contains `Math`.
- **Debugging friction**: stepping into a call with a common name is more annoying when multiple candidates exist conceptually.

**Common mistake**
- **Importing multiple statics that define the same member names** (directly or via overload sets). This can lead to ambiguous call errors or (worse) the “wrong” overload being chosen when implicit conversions are involved.

### 3. **Recommendation**
**Mentor rule**: Use `using static` only when it makes the code *clearly* better for a reader who did not write it.

- **Prefer explicit qualification** in shared code: `Math.Clamp(value, 0, 100)` is self-documenting.
- **If you use it, keep it single-purpose**: typically one static import per file, and only for “obvious” types like `Math`.
- **Avoid “global static imports”**: C# does not have `global using static` by default in templates for a reason—making static members globally available tends to create confusion. If you consider adding it, reconsider the design (local functions or a small helper type often reads better).

**Performance note**
- `using static` is syntactic sugar. It does not change IL for the call. Any performance impact comes only from *which* method you end up calling or from API misuse hidden by less explicit code.
