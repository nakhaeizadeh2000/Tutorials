### 1) **Explain hiding vs overriding** (with a base-typed variable example and the dispatch rule)
**High-signal answer**
- **Hiding (`new`)**: which member runs is chosen by the **static type** of the reference at the call site.
- **Overriding (`virtual`/`override`)**: which implementation runs is chosen by the **runtime type** of the object.

**Example you can say out loud**

```csharp
using System;

public class Base
{
    public void H() => Console.WriteLine("Base.H");          // non-virtual
    public virtual void V() => Console.WriteLine("Base.V");  // virtual
}

public sealed class Derived : Base
{
    public new void H() => Console.WriteLine("Derived.H");   // hides
    public override void V() => Console.WriteLine("Derived.V");
}

public static class Demo
{
    public static void Main()
    {
        Base b = new Derived();
        b.H(); // Base.H  (static type is Base)
        b.V(); // Derived.V (virtual dispatch)
    }
}
```

**Pitfall to mention**
- Hiding breaks polymorphism; it’s usually a design smell unless forced by legacy/interop constraints.

### 2) **Explain virtual/override/abstract/sealed override** (legal combinations and design intent)
**Definitions**
- `virtual`: base provides a default implementation and allows overriding.
- `override`: derived provides the implementation for a virtual member.
- `abstract`: base requires derived types to implement (no base body).
- `sealed override`: override here, and **stop further overrides** down the chain.

**What interviewers want**
- You understand that “virtual” is an **API promise** and affects versioning.
- You know `sealed override` is about **locking down invariants** at a specific layer.

### 3) **Explain constructor order + “no virtual calls in constructors”** (what actually happens and how to design around it)
**Core explanation**
- Base constructors run before derived constructors.
- If the base constructor calls a virtual method, it can dispatch into the derived override **before derived fields are initialized** → partially constructed state bugs.

**What to say**
- “Avoid calling virtual members from constructors. Prefer non-virtual initialization, factory methods, or explicit initialization steps.”

### 4) **When to use sealed classes/methods** (design + versioning + performance framing)
**Mentor-grade answer**
- **Design**: seal when you don’t want to support inheritance as an extension point; it protects invariants.
- **Versioning**: sealing reduces the chance that future changes “break somebody’s derived type”.
- **Performance**: sealing can enable devirtualization/inlining opportunities (don’t oversell; measure).

### 5) **Design questions** (inheritance vs interfaces vs composition; defend trade-offs and mention correctness/perf)
**A strong answer pattern**
- Start with **requirements**: extension points, test seams, and invariants.
- Choose **composition + interfaces** by default (more flexible, less coupling).
- Use **inheritance** only when:
  - you have a stable base contract,
  - clear override points,
  - and you control the hierarchy (or you’re a framework author).

**Performance notes to mention**
- Virtual/interface dispatch is usually not the bottleneck; allocations, I/O, and algorithmic complexity dominate.
- Don’t put polymorphism inside tight loops unless you’ve measured and it matters.
