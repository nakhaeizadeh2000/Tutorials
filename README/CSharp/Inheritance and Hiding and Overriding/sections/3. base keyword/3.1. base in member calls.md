## 3.1. `base` in member calls: calling hidden/overridden base implementations intentionally

1. **Calling base implementations** (`base.M()` inside override; choosing base behavior vs replacing it)
2. **Avoiding accidental recursion** (calling your own override vs base implementation)
3. **Mentor rule** (call `base` only when the base contract requires it or it’s a deliberate extension point)

---

### 1) **Calling base implementations** (`base.M()` inside override; choosing base behavior vs replacing it)
`base.Member` means “access the base *implementation* of this member from within the derived type”.

Most commonly:
- Inside an `override`, `base.SomeVirtual()` calls the **base implementation** instead of re-invoking your override.
- When a derived type *hides* a member with `new`, `base.Member` can access the hidden base member (but this is usually a smell—see `5.*` for hiding).

**Example: override + extend base behavior**

```csharp
using System;

public abstract class Handler
{
    public virtual void Handle(string input)
    {
        if (string.IsNullOrWhiteSpace(input))
            throw new ArgumentException("Input is required.", nameof(input));
    }
}

public sealed class LoggingHandler : Handler
{
    public override void Handle(string input)
    {
        base.Handle(input); // keep base validation contract
        Console.WriteLine($"Handling: {input}");
    }
}
```

**Good to know**
- Calling `base` is a *semantic* choice: “I am extending the base contract, not replacing it.”
- If the base implementation is optional, the base type should say so explicitly (docs/tests).

---

### 2) **Avoiding accidental recursion** (calling your own override vs base implementation)
Inside an override, calling the method name without `base.` calls the **override** again (i.e., yourself), which usually becomes infinite recursion.

```csharp
public class Base
{
    public virtual int Compute() => 1;
}

public sealed class Derived : Base
{
    public override int Compute()
    {
        // return Compute() + 1;   // BUG: recursion
        return base.Compute() + 1; // correct: base implementation + extra work
    }
}
```

**Mentor note**
- If you find yourself needing `base` calls frequently, consider whether the base class is doing too much or exposing too many override points.

---

### 3) **Mentor rule** (call `base` only when the base contract requires it or it’s a deliberate extension point)
**Do call `base` when**
- The base contract explicitly requires it (e.g., framework types: `Stream.Dispose(bool)`, `Controller.OnActionExecuting`, etc.).
- The base method establishes invariants you are building on (validation, state transitions).

**Don’t call `base` when**
- You’re trying to “patch around” unclear base behavior. That’s usually a design smell; prefer composition.

**Performance note**
- `base.X()` is not inherently faster; it just selects a specific implementation.
