## 7.2. Real-world scenarios: choose `override`, choose `new`, or avoid inheritance entirely

1. **Framework base classes** (override required hooks; understand base contract)
2. **Library design** (prefer interfaces + composition; keep base classes internal when possible)
3. **Hot path considerations** (avoid polymorphism in tight loops; prefer generics/structural approaches when it matters)

---

### 1) **Framework base classes** (override required hooks; understand base contract)
Framework inheritance is one of the few common places where overriding is not only acceptable but required.

**How to approach it (mentor checklist)**
- Identify which members are the official extension points (`virtual`/`abstract`, documented hooks).
- Check whether you must call `base.SomeHook(...)` (many frameworks require it).
- Understand threading model and reentrancy rules (especially UI frameworks). If it’s UI-specific, mark it explicitly. (frontend)

**Example: overriding a framework-style hook safely**

```csharp
public abstract class PipelineStage
{
    public void Run(string input)
    {
        // Non-virtual orchestration
        OnBefore(input);
        Process(input);
        OnAfter(input);
    }

    protected virtual void OnBefore(string input) { }
    protected abstract void Process(string input);
    protected virtual void OnAfter(string input) { }
}

public sealed class LoggingStage : PipelineStage
{
    protected override void OnBefore(string input)
    {
        // Extends base behavior (no base call needed here because base is empty).
        Console.WriteLine($"Start: {input}");
    }

    protected override void Process(string input)
    {
        // Core step.
    }
}
```

**Good to know**
- In real frameworks, hooks may be called on specific threads or under locks. Read the docs; don’t guess.

### 2) **Library design** (prefer interfaces + composition; keep base classes internal when possible)
If you ship a library, public inheritance is a long-term support burden:
- Users can derive from your base type in arbitrary ways you didn’t anticipate.
- Any change to virtual behavior can become a breaking change.

**Preferred library pattern**
- Expose **interfaces** as contracts.
- Keep base classes **internal** (or at least sealed) unless you’re intentionally building a framework.
- If you need shared helpers, consider `internal` helper types, extension methods, or composition.

**Example: public interface + sealed implementation**

```csharp
public interface IParser
{
    bool TryParse(ReadOnlySpan<char> input, out int value);
}

public sealed class DecimalParser : IParser
{
    public bool TryParse(ReadOnlySpan<char> input, out int value)
        => int.TryParse(input, out value);
}
```

**Mentor note**
- If you feel you need a public base type “for testability”, an interface is usually the better seam.

---

### 3) **Hot path considerations** (avoid polymorphism in tight loops; prefer generics/structural approaches when it matters)
When runtime dispatch is inside a tight loop, you may lose:
- inlining,
- constant propagation,
- other JIT optimizations.

**First rule: measure**
- Don’t redesign around dispatch without evidence (profilers + benchmarks).

**Typical solutions (in order)**
- Move polymorphism out of the loop (batch work by type/strategy).
- Use **generics** so polymorphism is resolved at compile-time.
- Use data-oriented layouts (store data contiguously, reduce per-item indirections).
