## 1.1. Inheritance in C#: is-a vs implementation reuse (and why composition often wins)

1. **What inheritance actually provides** (substitutability + virtual dispatch + shared base implementation) vs “just code sharing”
2. **When inheritance is appropriate** (stable base contract, real is-a relationship, framework extension points)
3. **Costs and risks** (fragile base class, virtual dispatch limits devirtualization, initialization order hazards, versioning traps)

---

### 1) **What inheritance actually provides** (substitutability + virtual dispatch + shared base implementation) vs “just code sharing”
**Definition**
- **Inheritance** in C# means a derived type *is a* base type (subtype relationship). Practically it gives you:
  - **Substitutability**: a `Derived` instance can be used where `Base` is expected.
  - **A single shared implementation surface**: protected members, shared helpers, and shared state (fields) in the base.
  - **Runtime polymorphism** via **virtual dispatch** (`virtual`/`override`) and **abstract** members.

**Critical mentor framing**
- If you only want “reuse some code”, inheritance is rarely the best tool. “Reuse” is the **least important** benefit; the important part is the **contract** (what callers can rely on).

**Example: “is-a” contract vs “code sharing”**

```csharp
public abstract class StreamProcessor
{
    // The contract: derived types can customize the core step.
    public void Run(ReadOnlySpan<byte> payload)
    {
        Validate(payload);
        ProcessCore(payload);  // virtual/abstract dispatch boundary
    }

    protected virtual void Validate(ReadOnlySpan<byte> payload) { }
    protected abstract void ProcessCore(ReadOnlySpan<byte> payload);
}

public sealed class GzipStreamProcessor : StreamProcessor
{
    protected override void Validate(ReadOnlySpan<byte> payload)
    {
        if (payload.Length < 2) throw new ArgumentException("Too small.");
    }

    protected override void ProcessCore(ReadOnlySpan<byte> payload)
    {
        // ...
    }
}
```

Here, inheritance is used to define a **stable template** (`Run`) and a **customization point** (`ProcessCore`).

**Performance note**
- The dispatch boundary (`ProcessCore`) is a real runtime indirection. Most apps won’t care. If it becomes hot, you redesign around it (e.g., generics, function pointers, data-oriented layout). Don’t “inherit for speed”.

### 2) **When inheritance is appropriate** (stable base contract, real is-a relationship, framework extension points)
**Use inheritance when all of these are true**
- **True is-a**: substitutability makes sense (“a `Dog` is an `Animal`” is often *not* enough—what matters is behavioral contract, not vocabulary).
- **Stable base contract**: you can commit to base semantics long-term (especially in libraries).
- **Clear extension points**: it’s obvious which members are meant to be overridden (and which are not).
- **Hierarchy is shallow**: 1–2 levels is common; deeper trees often indicate a modeling problem.

**Typical good uses**
- **Framework hooks**: ASP.NET Core middleware base types, test framework base fixtures, serialization adapters (when required).
- **Template method pattern**: base orchestrates, derived supplies steps.
- **Domain-specific base type only when domain is stable** and derived types truly share invariants.

**Prefer composition when**
- You want to combine behaviors in different ways (“mix and match”): strategy/decorator.
- You need multiple independent dimensions of variation.
- You don’t control all derived types (public library) and can’t support arbitrary overrides safely.

**Good to know**
- “Composition over inheritance” is not anti-inheritance. It’s a reminder that inheritance creates **tight coupling** and a **shared fate** between base and derived.

### 3) **Costs and risks** (fragile base class, virtual dispatch limits devirtualization, initialization order hazards, versioning traps)
**Fragile base class problem**
- A base class change that “seems safe” can silently break derived behavior:
  - adding a call to a new virtual method
  - changing call order between virtual hooks
  - tightening validation
  - adding a new virtual member that derived accidentally hides

**Initialization hazards**
- Base construction runs before derived initialization. If base calls virtual members during construction, derived overrides can observe partially initialized state.
- Deep treatment exists elsewhere:
  - See `README/CSharp/Constructors/sections/1. Constructor fundamentals/1.3. Execution order fields base derived.md`.

**Versioning traps (especially for libraries)**
- Making a method `virtual` is a long-term promise: consumers can override it forever.
- Adding abstract members is breaking (derived types must implement).
- Changing behavior in base virtuals can break derived types in subtle ways.

**Performance reality**
- Virtual dispatch can inhibit inlining/devirtualization in hot loops.
- The canonical performance deep dive is already in the OOP domain:
  - See `README/CSharp/CSharp Basic Object Oriented Programming/sections/3. Important points about objects/3.5. Virtual dispatch interface calls and performance basics.md`.

**Mentor rule of thumb**
- Default to **non-virtual**.
- If you make something virtual, treat it like a public API: document expectations, invariants, and whether `base.SomeMethod()` must be called.
