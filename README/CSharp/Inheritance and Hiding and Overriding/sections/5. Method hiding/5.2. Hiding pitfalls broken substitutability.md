## 5.2. Hiding pitfalls: confusing APIs, broken expectations, and subtle bugs

1. **Substitutability breaks** (base-typed reference calls base member, not derived hidden member)
2. **Maintainability cost** (readers can’t predict behavior; refactors become dangerous)
3. **Performance note** (not a speed hack; it’s an API/dispatch choice, usually a design smell)

---

### 1) **Substitutability breaks** (base-typed reference calls base member, not derived hidden member)
If you hide a member, you violate the “a derived instance can be used as its base” intuition in a way that’s extremely non-obvious at call sites.

**Example (runnable): base-typed call ignores hidden member**

```csharp
using System;

public class Base
{
    public void Print() => Console.WriteLine("Base.Print");
}

public sealed class Derived : Base
{
    public new void Print() => Console.WriteLine("Derived.Print (hidden)");
}

public static class Demo
{
    public static void Main()
    {
        var d = new Derived();
        Base b = d;

        d.Print(); // Derived.Print (hidden)
        b.Print(); // Base.Print
    }
}
```

**Mentor note**
- This is not “polymorphism”. This is **two different members** that happen to share the same name.
- If the intent is polymorphic behavior, you wanted `virtual`/`override`, not `new`.

---

### 2) **Maintainability cost** (readers can’t predict behavior; refactors become dangerous)
Hiding creates a codebase where behavior depends on the **static type** at each call site. That is a refactoring trap:

- Changing a variable type from `Derived` to `Base` (e.g., storing in a collection of base types, introducing an interface, extracting a method parameter) silently changes which method runs.
- New team members (and future you) will read `obj.Print()` and assume “Derived overrides Base” when it does not.

**Common real-world bug patterns**
- “It worked in the unit test but not in production”: test called on `Derived`, production stores as `Base`.
- “Why did logging disappear?”: hidden method added logging but callers invoke base method.

**Good to know**
- The compiler warns you when you hide unintentionally (CS0114). Treat that warning as a design review prompt, not as noise to suppress.

---

### 3) **Performance note** (not a speed hack; it’s an API/dispatch choice, usually a design smell)
You do not use hiding to “avoid virtual dispatch”.

- If a hot loop can’t afford polymorphism, hiding is the wrong tool because it changes semantics.
- Prefer:
  - **generics** (compile-time polymorphism),
  - **data-oriented design** (batching, contiguous storage),
  - **specialization** (separate fast path types),
  - or **composition** where the strategy isn’t in the inner loop.
