## 4.2. Protected constructors, abstract bases, and framework-oriented inheritance

1. **Why protected ctors exist** (prevent invalid “base-only” instantiation while enabling derived types)
2. **Abstract base classes** (shared implementation + enforced overrides; when it’s better than interfaces)
3. **Interop realities** (serializers/ORMs/DI: when a parameterless ctor is required and how to contain the damage)

---

### 1) **Why protected ctors exist** (prevent invalid “base-only” instantiation while enabling derived types)
`protected` constructors are a way to say:

- “This type is not meant to be instantiated directly by consumers”
- “But derived types are allowed to construct the base portion correctly”

Common uses:
- **Abstract base classes** (where `new Base()` must not compile)
- **Framework base types** that require subclassing
- **Controlled construction** where you want only derived types (or factories) to create instances

```csharp
public abstract class Entity
{
    protected Entity(Guid id)
    {
        Id = id == Guid.Empty ? throw new ArgumentException("Id required.") : id;
    }

    public Guid Id { get; }
}

public sealed class Order(Guid id) : Entity(id);
```

**Mentor note**
- Prefer `protected` **only** if you are intentionally designing for inheritance. Otherwise, prefer `private` constructors + factories.

---

### 2) **Abstract base classes** (shared implementation + enforced overrides; when it’s better than interfaces)
An **abstract** base class gives you two things at once:
- a **contract** (abstract members that must be implemented)
- a **shared implementation** (non-abstract members, helpers, common state)

Use an abstract base class when:
- you need to share **state** (fields) or non-trivial helpers
- you need a **template method** where base orchestrates and derived supplies steps
- you want to **force** certain overrides (`abstract`)

Prefer interfaces when:
- you don’t need shared state/implementation
- you want multiple independent capabilities
- you want to keep inheritance trees shallow and avoid fragile base coupling

**Performance note**
- The key performance difference is rarely “abstract class vs interface”; it’s “dynamic dispatch vs no dynamic dispatch”.
- For deep performance framing on virtual/interface calls, see:
  - `README/CSharp/CSharp Basic Object Oriented Programming/sections/3. Important points about objects/3.5. Virtual dispatch interface calls and performance basics.md`

### 3) **Interop realities** (serializers/ORMs/DI: when a parameterless ctor is required and how to contain the damage)
Sometimes tooling wants a parameterless constructor:
- Some ORMs (and some serializers depending on configuration) historically required it.
- Some frameworks instantiate via reflection.

**Mentor strategy: don’t weaken your domain model**
- Keep your real invariant-enforcing constructor(s).
- If a parameterless constructor is required, make it **private/protected** and keep it minimal.
- Validate after materialization (mapping layer) before using the object as “domain-valid”.

```csharp
public class Customer
{
    // Real invariant constructor
    public Customer(string email)
        => Email = string.IsNullOrWhiteSpace(email) ? throw new ArgumentException("Email required.") : email;

    // Some ORMs need this; keep it non-public.
    protected Customer() { }

    public string Email { get; private set; } = "";
}
```
