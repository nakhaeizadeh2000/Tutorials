## 2.1. Assemblies, references, and the loader

1. **Assembly basics (`.dll`/`.exe`, manifest/metadata/resources, strong naming, satellite assemblies)**
2. **Dependency resolution (`deps.json`; NuGet vs runtime assemblies; redirects vs modern resolution)**
3. **Practical guidance (shallow dependency graphs; reflection vs trimming/AOT; explicit versioning strategy)**

### 1) **Assembly basics**
**Definition**
- An **assembly** is the primary deployment and versioning unit for managed code. It contains:
  - **IL** (CIL) + **metadata** (types/members, attributes, references)
  - **manifest** (assembly identity: name, version, culture, public key token if strong-named)
  - optional **resources** (embedded files) and **satellite assemblies** for localization
- A `.dll` and `.exe` are both assemblies; the `.exe` typically includes an entry point and host stub logic.

**When to use (mental model)**
- In modern .NET, you usually think in terms of **projects** and **NuGet packages**, but the runtime ultimately loads **assemblies**.
- Assembly boundaries matter for:
  - **load time** and startup behavior
  - **trimming/AOT compatibility** (reflection + dynamic loading)
  - **versioning blast radius** (how many consumers are impacted by a change)

**Strong naming (what it is, what it isn’t)**
- **Strong naming** gives an assembly a cryptographic identity (public/private key). It helps with:
  - binding identity (historically important in GAC-era .NET Framework)
  - some supply-chain integrity scenarios
- **Strong naming is not a security boundary**. Don’t treat it as a “trusted code” mechanism.

**Satellite assemblies**
- For localization, resource files can be compiled into a main assembly or placed into **culture-specific satellites** (e.g., `fr/MyApp.resources.dll`).
- Prefer modern localization APIs (e.g., `IStringLocalizer` in ASP.NET Core) rather than homegrown resource switching.

**Good to know**
- A “NuGet package” is a delivery format. At runtime you load assemblies; NuGet just provides the assemblies and assets.

### 2) **Dependency resolution**
**Definition (modern .NET)**
- At publish/build time, your app’s dependency graph is recorded in:
  - `*.deps.json`: what assemblies exist, their versions, and where they come from
  - `*.runtimeconfig.json`: what runtime you target, roll-forward policy, GC settings, etc.
- At runtime, the host resolves dependencies using those manifests and the configured probing paths.

**NuGet vs runtime assemblies**
- **NuGet packages** can include:
  - managed assemblies (your typical case)
  - native assets (`runtimes/<rid>/native/...`)
  - build-time tooling (analyzers/source generators) that don’t ship to production
- “It restored” doesn’t imply “it will load on the target OS/arch” when native assets are involved.

**Legacy pattern: binding redirects**
- **.NET Framework** used `app.config` binding redirects to deal with version conflicts.
- In modern .NET (`netcoreapp`/`netX`), redirects aren’t the normal solution; prefer:
  - resolving version conflicts at build time (central package mgmt, dependency constraints)
  - avoiding multiple major versions of the same package in one app

**Common mistakes**
- Shipping a self-contained app and assuming it won’t load additional assemblies.  
  - If you use plugin systems or `AssemblyLoadContext`, you can still load more.
- Assuming the loader error message points to the “missing package.”  
  - Loader failures often come from *transitive* missing dependencies or RID mismatch for native libraries.

**Code example: dynamic loading (advanced)**
Use this only when you truly need plugins. It complicates trimming/AOT and increases operational risk.

```csharp
using System;
using System.Reflection;
using System.Runtime.Loader;

var path = args.Length > 0 ? args[0] : throw new ArgumentException("Pass path to plugin dll.");
var alc = new AssemblyLoadContext("plugin", isCollectible: true);

try
{
    var assembly = alc.LoadFromAssemblyPath(path);
    Console.WriteLine($"Loaded: {assembly.FullName}");
}
finally
{
    alc.Unload();
}
```

**Performance note**
- Dynamic loading is typically not “slow” by itself, but it:
  - prevents many publish-time optimizations (trimming, AOT)
  - makes failures show up at runtime rather than build time

### 3) **Practical guidance**
**Keep dependency graphs shallow**
- Fewer dependencies means:
  - fewer security advisories
  - faster restores/builds
  - fewer version conflicts and smaller deployment artifacts

**Reflection vs trimming/AOT**
- Reflection-heavy systems (including many serializers) can break under trimming/native AOT without configuration.
- Prefer “compile-time friendly” approaches when possible:
  - source-generated serializers (`System.Text.Json` source generation)
  - explicit factory registration instead of scanning all types

**Versioning strategy**
- For apps: lock down versions (lock files), upgrade regularly, and treat runtime updates as a normal patching activity.
- For libraries: be conservative about public API surface, and understand that assembly identity/version choices affect consumers.

**نکته**
- If you’re designing a plugin model, decide early whether you can accept the extra complexity. Most applications don’t need runtime plugin loading; they need good modularity *at build time*.
