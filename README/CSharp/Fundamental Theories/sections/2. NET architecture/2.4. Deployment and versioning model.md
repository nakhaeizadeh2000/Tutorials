## 2.4. Deployment and versioning model (modern .NET)

1. **Deployment modes (framework-dependent vs self-contained vs single-file: meaning + limits)**
2. **Servicing and upgrades (security/perf patches; LTS vs STS cadence; upgrade planning)**
3. **Practical advice (repeatable builds; clear deployable units; publish settings as measurable knobs)**

### 1) **Deployment modes**
**Definitions**
- **Framework-dependent deployment (FDD)**: you ship your app (`.dll` + dependencies) and rely on a compatible **runtime installed on the machine**. The host is `dotnet`.
- **Self-contained deployment (SCD)**: you ship your app **with a runtime** for a specific **RID** (e.g. `linux-x64`, `win-arm64`). Users don’t need to install .NET.
- **Single-file**: packaging option where publish output is bundled into **one file** (usually alongside native dependencies). It’s about packaging, not magically eliminating all runtime/native dependencies.

**When to use**
- **FDD**: controlled environments where runtime management is centralized (e.g., enterprise desktops, build agents) and minimizing artifact size matters.
- **SCD**: services/apps where you want **predictable runtime behavior** and fewer “works on my machine” runtime drift issues (common for containers and server apps).
- **Single-file**: CLIs and edge deployments where “copy one thing” matters; also helps reduce deployment mistakes.

**Trade-offs**
- **Artifact size vs operational simplicity**:
  - FDD is small but shifts responsibility to runtime installation/patching.
  - SCD is bigger but makes runtime version part of your app release.
- **Cross-platform**: SCD is per-RID; you generally produce one artifact per target (linux-x64, linux-arm64, win-x64, …).
- **Startup/throughput**: publish knobs like **ReadyToRun** and **PGO** can shift startup vs steady-state (deep perf trade-offs are in **2.2**).

**Common mistakes**
- Assuming single-file means “no extraction ever.” Some configurations or native libraries may still require extraction. Validate on the target OS.
- Publishing Debug or benchmarking Debug.
- Shipping FDD without a clear policy for the target runtime version (you want a **floor**, not “whatever is installed”).

**Example: publish commands you should know**

```bash
# Framework-dependent (portable)
dotnet publish -c Release -f net9.0

# Self-contained for linux-x64
dotnet publish -c Release -f net9.0 -r linux-x64 --self-contained true

# Self-contained + single-file (typical CLI shape)
dotnet publish -c Release -f net9.0 -r linux-x64 --self-contained true /p:PublishSingleFile=true
```

**Performance note**
- Treat publish properties as **hypotheses** you measure. AOT/trimming/R2R can improve cold-start or reduce memory, but can also increase build time, constrain reflection, or reduce peak throughput depending on workload.

### 2) **Servicing and upgrades**
**What “servicing” means in .NET**
- Runtime and libraries receive security and reliability fixes. Upgrading the runtime can also deliver performance improvements (JIT/GC/ThreadPool changes).

**LTS vs STS**
- **LTS** (Long Term Support): the safer default for many production systems—longer patch runway and fewer breaking changes.
- **STS** (Short Term Support): faster access to new runtime features and improvements, but you must be disciplined about upgrade cadence.

**Mentor notes (the part teams forget)**
- Decide explicitly:
  - **Who owns** runtime upgrades (platform team vs app teams).
  - **How you validate**: integration tests + perf smoke tests (throughput/latency + GC counters).
  - **How you roll out**: canary + rollback.

**Common mistakes**
- Confusing **NuGet package updates** with **runtime updates**. They are different axes with different risk profiles (see **1.1**).
- Letting production drift across many runtime patch levels, then doing a giant “upgrade day.”

### 3) **Practical advice**
**Repeatable builds**
- Use deterministic builds and lock dependencies:
  - Prefer **Central Package Management** (`Directory.Packages.props`) for multi-project solutions.
  - Consider `packages.lock.json` where supply-chain repeatability matters.

**Clear deployable units**
- One service = one publish output with a clear RID policy.
- Avoid “shared bin folders” and ad-hoc copying; make `dotnet publish` the source of truth.

**Publish settings as measurable knobs**
- Document which knobs you touched and why:
  - `PublishTrimmed`, `PublishSingleFile`, `SelfContained`
  - `PublishReadyToRun`
  - (where appropriate) native AOT settings (see **2.2** for the deep constraints and reflection considerations)

**نکته**
- If you depend on reflection-heavy frameworks or dynamic plugin loading, you must validate trimming/AOT early; the earlier you design for it, the cheaper it is.
