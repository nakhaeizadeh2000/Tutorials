## 2.2. IL, JIT, tiered compilation, and (native) AOT

1. **JIT in production (tiered compilation; PGO where applicable; micro-benchmark pitfalls)**
2. **AOT options (ReadyToRun vs native AOT; startup/throughput/size trade-offs; feature constraints)**
3. **Performance guardrails (optimize allocations first; separate cold-start vs steady-state; avoid anti-JIT patterns)**

### 1) **JIT in production**
**Definition**
- **IL (CIL)**: the intermediate language emitted by the C# compiler. It’s portable across CPUs and OSes.
- **JIT** (Just-In-Time compilation): the runtime compiles IL to machine code at runtime, often *per method* on first execution.
- **Tiered compilation**: the runtime starts with faster-to-compile code (“Tier 0”) and, once a method is hot, recompiles it with more aggressive optimizations (“Tier 1”). This is how modern .NET balances startup vs throughput.
- **(Dynamic) PGO**: Profile-Guided Optimization where the runtime uses observed execution profiles to optimize hot paths (e.g., more accurate devirtualization/inlining decisions).

**When to use / why you care**
- **Server apps**: tiering + PGO can materially affect p95/p99 latency after warm-up; you need to separate *cold start* from *steady-state* measurements.
- **Short-lived CLI tools / functions**: startup matters more; you may prefer publish-time optimizations (ReadyToRun or native AOT) if they fit constraints.

**Trade-offs**
- **Tiering**:
  - **Pros**: faster startup without sacrificing long-run throughput.
  - **Cons**: first-run behavior differs from warmed-up behavior; benchmarking needs discipline.
- **PGO**:
  - **Pros**: better steady-state performance for complex polymorphic code.
  - **Cons**: profile quality depends on representative workloads; “weird” traffic can shift hot paths.

**Common mistakes (mentor notes)**
- **Benchmarking in Debug** or with a single short iteration and calling it “the performance.”
- **Assuming first request latency == steady-state latency** (tiering and caches distort early behavior).
- **Overusing virtual/Interface dispatch in hot loops** without measuring; sometimes it’s fine, sometimes it blocks inlining and costs cache misses.

**Good to know**
- JIT optimizations are extremely sensitive to **shape**: small changes (extra bounds checks, hidden allocations, exception paths) can change inlining decisions.
- Exceptions are optimized for the **non-throwing path**; throwing is expensive (stack unwinding + metadata work). Use exceptions for exceptional events.

### 2) **AOT options**
Modern .NET gives you multiple “compile ahead” knobs. They solve different problems; don’t treat them as a single feature.

**ReadyToRun (R2R)**
- **What it is**: publish-time compilation of IL to native code *embedded in the assembly* to reduce JIT work at runtime.
- **Pros**: faster startup; less JIT overhead on first-run.
- **Cons**: bigger binaries; you still carry IL and the runtime can still JIT in some cases; throughput may be slightly lower than pure JIT for some workloads (the JIT can specialize better at runtime).

**Native AOT**
- **What it is**: produce a native executable where much of the runtime + your app is compiled ahead of time.
- **Pros**: best cold-start; potentially smaller memory footprint at runtime; great for small utilities, containers, and some microservices.
- **Constraints** (the big one): reflection-heavy patterns can break or require explicit configuration. Dynamic code generation is limited. Trimming becomes real.

**Trimming (linking)**
- Not “AOT”, but tightly related. Trimming removes unused code to reduce size and startup costs.
- Reflection can hide usage from the trimmer unless you annotate or supply configuration.

**When to choose what (rule of thumb)**
- **Long-running server**: default to **JIT + tiering + PGO** unless you have a demonstrated cold-start problem.
- **Cold-start critical** (functions, scaling from zero, CLIs): consider **R2R** first; consider **native AOT** when your dependency graph is compatible and you can control reflection/dynamic features.

**Common mistakes**
- Turning on native AOT or trimming “because it’s faster” without validating feature compatibility and operational needs (diagnostics, dynamic plugins, runtime compilation).
- Confusing “fewer ms on cold start” with “higher throughput under load.”

### 3) **Performance guardrails**
**What a senior mentor will insist on**
- **Measure first**: optimize the biggest bottleneck, not what you *feel* is slow.
- **Separate**:
  - **Cold start**: first process start + first request.
  - **Warm start**: process alive, caches warm.
  - **Steady state**: sustained load after tiering/PGO stabilize.

**Avoid anti-JIT patterns**
- **Allocations in hot paths**: avoid hidden allocations from LINQ, closures, boxing, `string` churn. (See **2.3** for GC/alloc deep treatment.)
- **Polymorphism without intent**: virtual/interface calls in tight loops can block inlining. Prefer:
  - sealed types where appropriate
  - generic specialization (`where T : ...`) when it improves hot-path performance
  - but do this only after measuring
- **Accidental exceptions**: don’t use exceptions for control flow in hot loops.

**Micro-benchmark pitfalls (and the correct replacement)**
- **Pitfall**: `Stopwatch` in a tight loop in a random console app.
- **Replacement**: use BenchmarkDotNet with proper warmup/iterations and isolate noise.

**Minimal example: why “warm-up” exists**
This is not a full benchmark; it demonstrates that “first run” is a different regime.

```csharp
using System;
using System.Diagnostics;

static int Hot(int x)
{
    // Non-trivial enough for the JIT to have choices (inlining, bounds checks).
    var sum = 0;
    for (var i = 0; i < 50_000; i++)
        sum += (x + i) ^ (i * 31);
    return sum;
}

static long TimeOnce(int x)
{
    var sw = Stopwatch.StartNew();
    _ = Hot(x);
    sw.Stop();
    return sw.ElapsedTicks;
}

Console.WriteLine($"First: {TimeOnce(42)} ticks");
Console.WriteLine($"Next : {TimeOnce(42)} ticks");
```

**Performance note**
- The biggest wins in real systems are usually:
  - removing unnecessary allocations (reducing GC pressure),
  - removing blocking on the ThreadPool,
  - reducing contention and syscalls,
  - and improving I/O behavior.
  JIT/AOT knobs matter, but they’re rarely the first lever.
