## 2.3. GC basics for application developers

1. **Generations and pauses (Gen0/1/2; server vs workstation GC; latency modes)**
2. **Allocation patterns (LINQ/closures/boxing/string churn; `ArrayPool<T>`; LOH/pinning/fragmentation)**
3. **Best practices (`Span<T>` where it helps; avoid premature pooling; prefer streaming over materializing)**

### 1) **Generations and pauses**
**Definition**
- .NET uses a **generational, tracing GC**: most objects die young, so the GC optimizes for reclaiming short-lived allocations quickly.
- **Gen0 / Gen1 / Gen2**: young to old generations. Collections of higher generations are typically less frequent but more expensive.
- **STW (stop-the-world) pauses** happen because the GC needs a consistent view of object graphs. Background GC reduces pause impact for Gen2 but does not eliminate pauses.

**When to care**
- Latency-sensitive apps (APIs, trading, real-time-ish systems) care about **pause time distribution** (p95/p99), not just average CPU.
- High-throughput services care about **allocation rate** and **Gen0 frequency**, because it directly consumes CPU and can cause cascading slowdowns.

**Server vs Workstation GC**
- **Server GC** (common for servers/containers): uses multiple heaps and GC threads, aiming for throughput. Usually the right default for ASP.NET Core.
- **Workstation GC**: optimized for desktop/interactive scenarios.

**Latency modes (what they mean, practically)**
- `SustainedLowLatency` / `LowLatency` reduce some expensive collections in critical sections, but:
  - They **do not prevent allocations** from building up.
  - You can trade short-term latency for long-term spikes (eventually the GC must do the work).

**Common mistakes**
- Treating “GC pause” as a mystery instead of a symptom. In .NET, the usual root causes are:
  - **High allocation rate**
  - **Large object heap (LOH)** growth/fragmentation
  - **Pinned objects** (often from interop or long-lived buffers) preventing compaction
- Using finalizers for normal cleanup. Finalizable objects are more expensive and delay reclamation. Prefer `IDisposable`/`using` (see section **4.2** for the deep treatment of lifetime/ownership).

**Performance note**
- GC tuning is almost always second-order. First fix:
  - “Why are we allocating so much?”
  - “Why are these objects living so long?”
Then consider GC configuration for the remaining, measured problem.

### 2) **Allocation patterns**
**What allocates (often accidentally)**
- **LINQ over `IEnumerable<T>`** in hot paths: iterator allocations, delegate captures, and loss of loop fusion (unless you’re on `Span<T>`/arrays with special-cased APIs).
- **Closures**: capturing locals allocates a display-class object.
- **Boxing**: converting value types to `object` or non-generic interfaces allocates.
- **Strings**: concatenation in loops, `ToString()` in hot paths, and encoding/decoding.

**LOH, pinning, fragmentation**
- **LOH**: “large” allocations (implementation-defined threshold; conceptually “big buffers/arrays”) go to a separate heap that historically compacts less aggressively.
- **Pinning** (e.g., `fixed`, interop, some buffer APIs) prevents moving objects, which can fragment heaps and increase GC cost.

**Use pooling deliberately**
- `ArrayPool<T>.Shared` can reduce allocation and GC pressure for large/temporary buffers.
- But pooling can also:
  - Increase memory retention (buffers stick around).
  - Increase complexity and bug risk (returning arrays twice, using after return, leaking sensitive data).

**Runnable example: avoid accidental allocations**
This demonstrates a closure allocation vs a static delegate and shows a simple `ArrayPool<T>` buffer use.

```csharp
using System;
using System.Buffers;
using System.Threading.Tasks;

static Task<int> ComputeAsync(int value)
{
    // No closure allocation: static lambda cannot capture.
    return Task.FromResult(value + 1);
}

static int SumWithPool(ReadOnlySpan<int> data)
{
    // For small inputs, do NOT pool; stackalloc or direct loop is better.
    // This example is intentionally simple to illustrate correct pool usage.
    var pool = ArrayPool<int>.Shared;
    int[] rented = pool.Rent(data.Length);
    try
    {
        data.CopyTo(rented);
        int sum = 0;
        for (int i = 0; i < data.Length; i++)
            sum += rented[i];
        return sum;
    }
    finally
    {
        // Clear if the data may be sensitive; costs extra CPU.
        pool.Return(rented, clearArray: false);
    }
}

Console.WriteLine(await ComputeAsync(41));
Console.WriteLine(SumWithPool(stackalloc[] { 1, 2, 3, 4 }));
```

**Good to know**
- Pooling is most justified for **large buffers** on hot paths. For small allocations, pooling often loses (extra branches, cache misses, larger working set).
- Prefer APIs that accept `Span<T>` / `ReadOnlySpan<T>` / `IBufferWriter<T>` when building high-performance libraries; they allow callers to control allocation strategy.

### 3) **Best practices**
**Principles that age well**
- **Reduce allocation rate** before trying to “tune GC”.
- Keep object graphs **shallow and short-lived** in hot paths.
- Prefer **streaming** (process items as you read them) over materializing whole collections.

**`Span<T>`—where it helps**
- `Span<T>` helps when you can keep data **on the stack or in existing buffers** and avoid allocations for slicing/parsing.
- It’s not a universal speed button; it shines when it replaces intermediate `string`/`byte[]` allocations.

**Avoid premature pooling**
- Pools are shared mutable state. Treat them as an optimization you add only when you have:
  - A measured allocation hotspot
  - A clear ownership boundary that ensures buffers are returned correctly

**Diagnostics you should know**
- `dotnet-counters` and `dotnet-trace` are your first stop for live services.
- Metrics to watch:
  - Allocation rate (bytes/sec)
  - Gen0/1/2 collection counts
  - CPU in GC
  - LOH size trends

**Note:**
- If you see high Gen2 frequency, don’t immediately blame the GC. It often means **long-lived references** (caches, static events, DI singletons holding onto big graphs) are keeping too much alive.
