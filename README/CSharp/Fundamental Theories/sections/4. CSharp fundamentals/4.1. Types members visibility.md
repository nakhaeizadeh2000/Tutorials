## 4.1. C# program structure: types, members, and visibility

1. **Classes vs structs vs records (semantics; copy costs; runtime/interop constraints)**
2. **Members (fields vs properties; methods vs local functions; events/callback lifetimes)**
3. **Performance notes (avoid public fields in libs; prefer `readonly` where it helps; know common allocation sources)**

### 1) **Classes vs structs vs records**
**Definitions (what they *mean* in .NET)**
- **`class`**: a **reference type**. Variables hold a reference (pointer) to an object on the managed heap. Assignment copies the reference, not the object.
- **`struct`**: a **value type**. Variables hold the value inline (in locals/fields/array elements). Assignment copies the value (bitwise copy, plus field copies).
- **`record`**: a *shape of API intent*, not a new runtime kind.
  - `record class` is still a **reference type** but with **value-based equality** defaults and syntactic sugar for immutability-friendly design.
  - `record struct` is a **value type** with record-style equality/printing and often used for small immutable values.

**When to use**
- Use **`class`** for:
  - Entities with identity, long-lived graphs, polymorphism, DI, and most domain objects.
  - Types that are large, frequently passed around, or often mutated (copying large structs is expensive and error-prone).
- Use **`readonly struct`** / **`record struct`** for:
  - Small (often \(\le\) 16–32 bytes), immutable-ish values like IDs, coordinates, money components, timestamps wrappers.
  - High-throughput code paths where avoiding heap allocations and GC pressure matters.
- Use **`record class`** for:
  - Message/DTO types, request/response models, “data-without-identity” types.
  - When you want value equality and succinct creation (`with` expressions) as part of the design.

**Trade-offs**
- **Classes**:
  - **Pros**: no copying cost for passing around; polymorphism; simpler semantics.
  - **Cons**: heap allocations + GC pressure; potential for shared-mutable-state bugs.
- **Structs**:
  - **Pros**: can avoid heap allocations; better locality in arrays; fewer GC roots.
  - **Cons**: copying cost; boxing pitfalls; default value semantics can surprise; mutation can be confusing when copied.
- **Records**:
  - **Pros**: express intent (value-like), built-in equality, deconstruction, `with` cloning.
  - **Cons**: easy to accidentally allocate/copy more than expected (especially with `with` on large graphs); equality can be expensive if fields are large.

**Common mistakes**
- Making a struct **mutable** and then passing it around: callers often mutate a *copy*, not the original (especially when accessed via properties or interfaces).
- Returning `struct` through an **interface** or `object`: this **boxes** and allocates.
- Using structs for large types “to avoid allocations” but paying in copies and cache misses instead.

**Code example: small immutable value type**

```csharp
public readonly record struct OrderId(Guid Value)
{
    public override string ToString() => Value.ToString("N");
}

public sealed class Order
{
    public required OrderId Id { get; init; }
    public required decimal Total { get; init; }
}
```

**Performance note**
- Prefer **`readonly struct`** for immutable structs to avoid defensive copies.
- If a value type is bigger than a couple of machine words, pass it as `in` only when profiling shows it helps—`in` can introduce hidden copies if the compiler must create temporaries.

### 2) **Members (fields vs properties; methods vs local functions; events/callback lifetimes)**
**Fields vs properties**
- **Public fields** in libraries are almost always a design mistake: you can’t add validation, lazy-init, change representation, or instrument without breaking consumers.
- Prefer **properties** for public surface area:
  - `get; init;` for immutable construction-time assignment.
  - `get; private set;` when mutation is internal only.
- Use **fields** privately for:
  - backing storage with invariants enforced by the containing type.
  - performance-critical paths where a property would be noise (but note: auto-properties are typically inlined; “field vs property perf” is rarely your bottleneck).

**Methods vs local functions**
- Prefer **local functions** to:
  - keep helper logic near its usage without exposing it as a separate method.
  - avoid allocating a delegate/closure in some cases where lambdas would capture.
- Prefer **methods** when:
  - logic is reusable across multiple methods, needs testing in isolation, or would make the parent method too large.

**Events and callback lifetimes**
- Events create a **lifetime coupling**: subscribers must unsubscribe (or use weak patterns) or they can leak memory.
- Prefer `event EventHandler<T>` patterns for classic .NET events.
- For new designs, consider:
  - `IObservable<T>` / reactive patterns (with careful subscription lifetimes), or
  - `Channel<T>` / `IAsyncEnumerable<T>` for async streams (see concurrency section(s) for deep coverage when present).

**Common mistakes**
- Exposing settable properties on types that should be immutable (harder concurrency correctness).
- Using events for one-shot results where a `Task<T>` is clearer.
- Capturing `this` in callbacks that outlive the object (keeps it alive).

### 3) **Performance notes**
**Know the usual allocation sources**
- **Boxing**: value type to `object` / interface.
- **Closures**: lambdas capturing variables.
- **LINQ** in hot loops: iterator allocations and virtual calls (sometimes optimized, often not).
- **Strings**: interpolation, concatenation, formatting.
- **Exceptions**: throwing is expensive; use exceptions for exceptional cases.

**Modern guidance (C# 15 / .NET 9+)**
- Prefer `Try*` APIs for expected failures (`int.TryParse`, `Dictionary<TKey,TValue>.TryGetValue`, `Enum.TryParse`).
- Use `ReadOnlySpan<char>` overloads (`int.TryParse(ReadOnlySpan<char>, ...)`) in parsing-heavy scenarios to avoid substring allocations.
- Use `required` + `init` for invariants instead of telescoping constructors when it improves clarity.

**Nokte / نکته**
- “Avoid allocations” is not the same as “make everything a struct.” The best default is: design for clarity and correctness, then optimize after measuring (especially for library code).
