## 8.1. Naming that scales: readability, API design, and tooling

1. **Identifiers (`PascalCase` for types/public; `camelCase` for locals/params; meaningful names over abbreviations)**
2. **APIs and architecture (names reveal sync/async intent; `*Async` conventions; avoid catch-all “Manager/Helper/Util”)**
3. **Performance-aware naming (signal allocations like `ToArray`; prefer Try-pattern; analyzer-driven consistency)**

### 1) **Identifiers**
**Goal**
- Names are your first (and cheapest) correctness tool: they communicate intent, constraints, and cost model without reading implementation.

**Modern, idiomatic rules (C# 15 era)**
- **Types, methods, properties, events**: `PascalCase`
- **Locals, parameters**: `camelCase`
- **Private fields**: `camelCase` (common modern style) or `_camelCase` (still common). Pick one and enforce via `.editorconfig`.
- **Interfaces**: `IThing` (still the .NET ecosystem norm)
- **Generic type parameters**: `T`, `TKey`, `TValue`, `TOptions` (avoid `T1`, `T2` unless truly generic)
- **Async methods**: end in `Async` (see item 2)

**When to be explicit**
- Use names to surface **units** and **invariants**:
  - `timeout`, `timeoutMs`, `timeoutSeconds` (prefer `TimeSpan timeout` in modern APIs)
  - `maxRetries`, `maxConcurrency`, `bufferSizeBytes`

**Common mistakes**
- Abbreviations that hide meaning: `Mgr`, `Util`, `Cfg`, `Proc`. If you must abbreviate, do so only for *globally known* terms (HTTP, URI, JSON).
- “Leaky implementation” names (`FooList`, `FooArray`) in public APIs—prefer semantic names (`foos`, `items`, `candidates`) unless the representation is part of the contract.

**Note:**
- If renaming is painful, your code is too coupled to names—add tests, and treat naming as a refactoring tool, not a bikeshed.

### 2) **APIs and architecture**
**Names reveal API contracts**
- For a consumer, the method name should answer:
  - **Does it block?**
  - **Does it allocate / materialize?**
  - **Is it safe to call multiple times / concurrently?**
  - **Does it have side effects (I/O, caching, mutation)?**

**Async naming (modern guidance)**
- Use `*Async` for methods returning `Task`, `Task<T>`, `ValueTask`, `ValueTask<T>`.
- Do **not** use `*Async` for methods that are merely “fast” or “queued”; `Async` means **asynchronous completion**.
- Avoid `Begin*/End*` APM naming (legacy). Replacement: TAP (`Task`/`ValueTask`) + `CancellationToken`.

**Sync vs async pairs**
- If you expose both:
  - Prefer `Read(...)` + `ReadAsync(...)`
  - Same semantics, different execution model.
- If you only expose one, pick based on expected usage:
  - Libraries used by servers should often prioritize `Async` for I/O APIs.

**Avoid catch-all classes**
- “`*Manager`/`*Helper`/`*Util`” is often a sign of:
  - mixed responsibilities (violates SRP),
  - unclear boundaries,
  - poor discoverability.
- Better patterns:
  - `FooService` (domain behavior), `FooRepository` (persistence), `FooClient` (remote API), `FooCache`, `FooParser`, `FooFormatter`

**Frontend note**
- (frontend) In UI apps (WPF/WinForms/MAUI), include `Async` and design APIs to avoid blocking the UI thread; keep a clear separation between UI concerns and service clients.

### 3) **Performance-aware naming**
**Name costs so callers can choose**
- Materialization should be visible:
  - `ToArray()`, `ToList()`, `AsSpan()` (view) vs `ToImmutableArray()` (copy)
- Allocation vs view:
  - Prefer `GetSpan(...)` / `TryGetSpan(...)` for APIs that can return a view without allocating.

**Try-pattern (high-performance + correctness)**
- Use `TryXxx(out ...)` for parse/lookup patterns where failure is expected and should not throw.

```csharp
using System;

static bool TryParsePort(string text, out int port)
{
    if (!int.TryParse(text, out port)) return false;
    return (uint)port <= 65535;
}
```

**Exceptions and naming**
- If a method *can* throw for invalid inputs, but callers often expect “not found”, prefer `TryGet...` or `Get...OrDefault` to avoid exception-driven control flow.

**Analyzer-driven consistency**
- Treat analyzers as part of architecture:
  - `.editorconfig` naming rules reduce churn in PRs.
  - Roslyn analyzers catch API mistakes early (e.g., `CA` rules, async warnings).

**Performance note**
- Naming doesn’t change runtime speed, but it prevents performance bugs:
  - If the name signals allocation (`ToList`) or blocking (`Read` vs `ReadAsync`), reviewers catch regressions earlier and production has fewer surprises.
