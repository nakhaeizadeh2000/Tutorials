## 7.1. Versioning model: language vs runtime vs libraries

1. **Language version (compiler features; generators/analyzers; feature availability vs TFMs)**
2. **Runtime version (JIT/GC/threading changes; hosting/diagnostics; AOT/trimming maturity)**
3. **Library/API version (new BCL APIs; “prefer new API” patterns; obsolete vs not-preferred)**

### 1) **Language version (C# 15 era): compiler features and their real constraints**
**Definition**
- The **C# language version** is primarily a *compiler switch* (Roslyn). It controls syntax and compile-time rules (nullability, pattern matching forms, `required`, etc.).
- Language features can be limited by:
  - Your **target framework** (available BCL APIs)
  - Your **runtime** (JIT/GC/ThreadPool behavior)
  - Your **ILLink/AOT** pipeline (reflection friendliness)

**When it matters**
- **Library authors**: you must decide what syntax/features you want to require from consumers.
- **Teams**: you need consistency across projects to avoid “it builds here, not there” friction.

**Common mistakes**
- **Mistake**: assuming “C# 15” implies “latest runtime behavior.”  
  - Language version controls syntax; runtime changes come from the installed/targeted runtime.
- **Mistake**: enabling features without aligning analyzers and CI.  
  - Example: turning on nullable reference types but not enforcing warnings-as-errors leads to a false sense of safety.

**Good to know**
- Use `global.json` to pin SDK in repos that require deterministic builds.
- Use analyzers (`Microsoft.CodeAnalysis.*` + built-in analyzers) to keep style and correctness consistent.

### 2) **Runtime version: JIT/GC/ThreadPool/diagnostics evolve independently**
**Definition**
- The runtime version governs:
  - **JIT** codegen and heuristics (tiering, PGO, inlining behavior)
  - **GC** strategies and pause behavior
  - **Threading/async plumbing** (ThreadPool scheduling, I/O completion integration)
  - **Diagnostics** capabilities (EventPipe, counters, profiling hooks)

**When to care**
- If you operate production services, runtime upgrades are often **free performance** plus security fixes.
- If you do low-level optimization, runtime version can invalidate micro-bench results.

**Trade-offs**
- New runtimes can change performance characteristics; always validate with representative load.
- For maximum predictability, deploy **self-contained**; for smaller images, deploy framework-dependent and manage runtime patching (see section **2.4**).

### 3) **Library/API version: BCL and NuGet evolve fastest**
**Definition**
- “API version” means:
  - The BCL APIs available in your TFM (e.g., `net9.0`)
  - Additional libraries you reference from NuGet (plus their transitive dependencies)

**Mentor guidance: prefer “new API patterns”**
- Many improvements land as *new APIs* rather than breaking old ones.
- Prefer APIs that improve correctness/perf:
  - `TryParse` / `TryFormat` patterns (avoid exceptions for control flow)
  - `ReadOnlySpan<char>` overloads (reduce allocations)
  - `System.Text.Json` over Newtonsoft in modern apps unless you need specific features (and you accept perf trade-offs)

**Deprecated / legacy patterns to avoid**
- **BinaryFormatter**: obsolete/insecure; use `System.Text.Json`, protobuf, or custom formats depending on requirements.
- **AppDomains for isolation**: legacy; use processes/containers, AssemblyLoadContext, or plugin boundaries.

**Good to know**
- “Obsolete” isn’t the only signal. Sometimes APIs are not obsolete but are no longer preferred (newer alternatives are more efficient or safer). Treat docs + analyzers as your early warning system.
