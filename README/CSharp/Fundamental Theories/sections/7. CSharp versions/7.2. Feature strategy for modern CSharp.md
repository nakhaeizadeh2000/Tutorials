## 7.2. Feature strategy: learn what changes how you design

1. **Correctness and expressiveness (nullability; pattern matching; records/required members/immutability)**
2. **Performance and control (`Span<T>` + ref safety; async streams/primitives; source generation vs reflection)**
3. **Maintainability (file-scoped namespaces; modern/global `using` patterns; analyzers/formatting for consistency)**

### 1) **Correctness and expressiveness**
Modern C# isn’t “syntax sugar”; it’s about making **illegal states unrepresentable** and making intent obvious to both humans and the compiler.

**What to prioritize**
- **Nullable reference types (NRT)**: treat warnings as design feedback, not noise.
  - Enable at the project level and keep it on.
  - Use `required` (and/or constructor parameters) to make initialization rules explicit.
- **Pattern matching**: replaces fragile `if` chains with exhaustive, readable logic.
- **Records & immutability**: great for DTOs and value-like domain data, but understand equality and copying.

**Common mistakes**
- Enabling NRT but suppressing warnings wholesale. That deletes the value and leaves you with false confidence.
- Overusing records for entities that have identity and lifecycle; records default to **value-based equality** which can be surprising.

**Example: expressive and safe branching with patterns**

```csharp
static string Classify(object? value) => value switch
{
    null => "null",
    int i when i >= 0 => "non-negative int",
    int => "negative int",
    string { Length: 0 } => "empty string",
    string s => $"string({s.Length})",
    _ => value.GetType().Name
};
```

**Performance note**
- Pattern matching is generally optimized well by the compiler/JIT. Don’t micro-optimize away clarity unless profiling proves it matters.

### 2) **Performance and control**
The performance “superpowers” in modern C# are mostly about:
- reducing **allocations**,
- avoiding **virtual dispatch / reflection** in hot paths,
- keeping **async** truly non-blocking,
- exploiting **span-based** APIs safely.

**What to reach for**
- **`Span<T>`/`ReadOnlySpan<T>`**: for parsing/formatting and slice-oriented work without allocating.
- **Async streams** (`IAsyncEnumerable<T>`) for streaming results without buffering whole collections.
- **Source generation** over reflection for serializers, DI, logging, regex, etc. (when available in your stack).

**Trade-offs**
- `Span<T>` is stack-only and constrained by ref-safety rules; it’s powerful but not a general-purpose replacement for arrays.
- Source generators increase build complexity but usually reduce runtime costs and trimming/AOT friction.

**Example: allocation-free parsing with spans**

```csharp
using System;

static bool TryParseKeyValue(ReadOnlySpan<char> line, out ReadOnlySpan<char> key, out ReadOnlySpan<char> value)
{
    var idx = line.IndexOf('=');
    if (idx < 0) { key = default; value = default; return false; }
    key = line[..idx].Trim();
    value = line[(idx + 1)..].Trim();
    return true;
}

ReadOnlySpan<char> input = "mode = fast";
if (TryParseKeyValue(input, out var k, out var v))
    Console.WriteLine($"{k.ToString()} -> {v.ToString()}");
```

**Good to know**
- `.ToString()` on a span allocates; keep spans in spans as long as you can, then materialize at the boundary.

### 3) **Maintainability**
Maintainability is where teams “win” with modern C#—through consistency, tooling, and reducing incidental complexity.

**Use the language to enforce consistency**
- **File-scoped namespaces**: reduce indentation and noise.
- **Global usings**: reduce repetitive `using` directives; keep them deliberate (don’t hide surprising dependencies).
- **Analyzers + formatting**: let tooling enforce rules that humans are bad at enforcing consistently.

**Mentor notes**
- Prefer explicitness at module boundaries: public APIs should be unsurprising and stable.
- If you’re building a library, treat analyzer warnings as part of your API design review.

**Practical checklist**
- Keep public APIs small and coherent (see `5.1` for API surface boundaries).
- Avoid “utility” dumping grounds—namespaces and assemblies should encode architectural intent.
