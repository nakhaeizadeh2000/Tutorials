## 6.1. Language tokens and syntax categories

1. **Tokens (identifiers/keywords/literals/operators; trivia; contextual keywords)**
2. **Literals (numeric readability + overflow; string literal forms; interpolation + allocations)**
3. **Good to know (parsing vs execution; compiler-generated constructs; clarity over token golf)**

### 1) **Tokens**
**Definition**
- A **token** is the smallest unit the C# compiler consumes after lexical analysis: identifiers, keywords, literals, operators, and punctuation.
- **Trivia** (whitespace, comments, newlines) isn’t a token in the semantic sense, but it *is* relevant for formatting and tooling (Roslyn).
- **Contextual keywords** (`async`, `await`, `record`, `required`, `nameof`, etc.) act like keywords only in specific syntactic contexts; otherwise they can be identifiers.

**Why you should care**
- It explains “weird” compiler errors (you wrote valid-looking code, but the token stream means something else).
- It explains why tooling (formatters/analyzers/source generators) can be precise: the compiler pipeline has a stable token model.

**Common mistakes**
- Overusing contextual keywords as identifiers in public APIs (`class record { }`) — it creates friction and confusion.
- Assuming comments/whitespace change runtime behavior (they don’t), then missing the real issue (overflow, boxing, hidden allocations, etc.).

**Good to know**
- The compiler turns tokens → **syntax tree** → **semantic model** → IL. Only the latter stages impact runtime behavior.

### 2) **Literals**
**Numeric literals**
- Use `_` separators for readability, and prefer explicit suffixes when they communicate intent (`1_000_000L`, `1.0m`).
- Be deliberate about overflow:
  - Default integer literals are `int` when they fit; then `uint`, `long`, `ulong`.
  - Arithmetic overflow behavior depends on `checked` context (and compiler/project settings).

```csharp
checked
{
    int bytes = 1_500_000_000;
    int doubled = bytes * 2; // throws OverflowException in checked context
}
```

**String literal forms (choose for correctness, then readability)**
- **Regular**: `"a\nb"` (escape sequences)
- **Verbatim**: `@"c:\temp\file.txt"` (backslashes are literal; quotes doubled)
- **Raw string literals** (modern C#): great for JSON, regex, and multi-line templates without escaping.

```csharp
var json = """
{
  "name": "Ada",
  "id": 42
}
""";
```

**Interpolation and allocations**
- `$"{x}-{y}"` creates a string. In hot paths, prefer:
  - structured logging (so formatting happens only if the log is emitted),
  - or `string.Create` / `ValueStringBuilder` patterns when you truly need to avoid transient strings (usually advanced scenarios).

**Performance note**
- Don’t prematurely micro-optimize strings; the bigger wins are typically algorithmic, allocation frequency reduction, and avoiding large-object churn (see **2.3** for GC).

### 3) **Good to know**
**Parsing vs execution**
- Most “language trivia” concerns correctness/readability, not runtime performance—until it affects:
  - allocations (captured lambdas, LINQ materialization),
  - exceptions (throwing is expensive),
  - or async state machines (allocation and scheduling differences).

**Compiler-generated constructs (high impact)**
- `async` methods become a **state machine**; this is usually correct and worth it for scalability, but it changes control flow and allocations.
- Iterator blocks (`yield return`) become a state machine too.
- `foreach` can use different enumerator patterns depending on the type; this affects allocations.

**Clarity over token golf**
- Prefer code that makes ownership, lifetime, and async boundaries obvious over clever syntax compression. Maintainability is a performance feature.
