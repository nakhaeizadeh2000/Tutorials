## 1.1. What “.NET” means: runtime vs libraries vs tooling

1. **Runtime vs BCL vs SDK (CLR/CoreCLR, `System.*`, `dotnet` CLI/SDK workflow)**
2. **App model (console/web/worker/desktop; framework-dependent vs self-contained; x64/arm64 + OS targets)**
3. **Performance framing (CPU vs runtime services; allocations/LOH; fewer sync points and syscalls)**

### 1) **Runtime vs BCL vs SDK**
**Definition**
- **Runtime**: the executable environment that runs your managed code. Practically, this means **CoreCLR** (JIT, GC, ThreadPool, exception handling, type system), plus runtime host components that locate and start your app.
- **BCL** (Base Class Library): the foundational libraries you reference as `System.*` and friends (collections, IO, networking, threading primitives, etc.). The BCL is *not* “the runtime”; it *uses* runtime services.
- **SDK/tooling**: the developer toolchain (the `dotnet` CLI, MSBuild, NuGet restore, analyzers, test runners, publish pipeline). The SDK is what *builds* your app, not what *executes* it in production (though `dotnet run` is a dev convenience).

**When to care (mentor view)**
- **Production incidents** often come from mixing these layers:
  - “We updated a NuGet package” (BCL/third-party library) vs “we updated the runtime” (JIT/GC changes) vs “we updated the SDK” (build/publish differences).
- If you ship multiple services, treat **runtime updates** as a first-class operational concern (security + performance).

**Trade-offs / common mistakes**
- **Mistake**: “It compiles with SDK X, so it’ll behave the same on runtime Y.”  
  - Reality: language features are a **compiler** concern; execution characteristics depend on **runtime + libraries + platform**.
- **Mistake**: Over-relying on `dotnet run` for “it works” validation.  
  - `run` builds Debug by default; Debug builds materially change performance and sometimes timing behavior.

**Good to know**
- The same source code may produce different outcomes depending on:
  - **Target Framework Moniker (TFM)** (`net9.0`, etc.)
  - **Runtime Identifier (RID)** (`linux-x64`, `win-arm64`, etc.)
  - **Publish settings** (ReadyToRun, trimming, AOT)

### 2) **App model**
**Definition**
.NET “app model” is the combination of:
- **Host** (how the process starts): `dotnet MyApp.dll` for framework-dependent; or a native host executable for self-contained.
- **Workload/framework**: console, ASP.NET Core, worker services, desktop (WPF/WinForms), MAUI, etc.
- **Deployment shape**: framework-dependent vs self-contained vs single-file (see section **2.4** for the deep deployment treatment).
- **Platform target**: OS + CPU architecture (x64/arm64) and runtime features available on that OS.

**When to use what**
- **Console / worker**: long-running services, background jobs, CLIs. Great default for systems work and headless infrastructure.
- **ASP.NET Core (web)**: HTTP/gRPC endpoints, APIs, server-rendered UI, microservices—strong default for networked apps.
- **Desktop UI (frontend)**: WPF/WinForms are Windows-centric; MAUI is cross-platform but has different performance/packaging trade-offs.

**Trade-offs**
- **Framework-dependent**:
  - **Pros**: smaller deployments, shares runtime on machine.
  - **Cons**: you depend on installed runtime version (ops responsibility).
- **Self-contained / single-file**:
  - **Pros**: you control runtime version, predictable deployment.
  - **Cons**: larger artifacts; patching requires redeploying your app.

**Common mistakes**
- Shipping “Any CPU” without thinking about **arm64** vs **x64** and native dependencies.
- Assuming “single-file” means “one file, always.” (There are extraction behaviors and native dependencies; see **2.4**.)

### 3) **Performance framing**
**Definition (the mental model that scales)**
- Your app’s speed is a combination of:
  - **Your code**: algorithms, allocations, synchronization, I/O patterns.
  - **Runtime services**: JIT decisions, GC heuristics, ThreadPool behavior, exception handling costs.
  - **OS + hardware**: syscalls, scheduling, page faults, CPU caches, NUMA, filesystem/network stack.

**Mentor stress points**
- **Allocations** are not “just memory”; they create **GC work**, which creates **pauses** and throughput loss.
- **Synchronous blocking** is not “just waiting”; it ties up **ThreadPool threads**, can cause starvation, and increases context switches.
- **I/O** is usually the bottleneck; optimize CPU only after measuring where time is spent.

**Practical, modern guidance**
- Measure the right thing:
  - **Throughput** (requests/sec), **latency** (p50/p95/p99), and **resource usage** (CPU, RSS, GC).
  - Separate **cold start** from steady-state (JIT tiering and caches distort first-run).
- Prefer **async I/O** end-to-end for scalable servers; avoid “fake async” that blocks inside `Task.Run`.

**Code example: showing the “three layers” clearly**
This snippet prints what runtime you’re actually using and shows how publish/deploy choices surface at runtime:

```csharp
using System;
using System.Runtime.InteropServices;

Console.WriteLine($".NET: {RuntimeInformation.FrameworkDescription}");
Console.WriteLine($"OS  : {RuntimeInformation.OSDescription}");
Console.WriteLine($"Arch: {RuntimeInformation.OSArchitecture} / Process: {RuntimeInformation.ProcessArchitecture}");
Console.WriteLine($"CPU#: {Environment.ProcessorCount}");
```

**Performance note**
- Avoid drawing conclusions from Debug builds. Always validate performance in Release with representative environment settings (server GC, container limits, etc.). See **2.2** for JIT/tiering/AOT implications and **2.3** for GC fundamentals.
