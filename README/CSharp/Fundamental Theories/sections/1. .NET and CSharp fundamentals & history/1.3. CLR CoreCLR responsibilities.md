## 1.3. CLR/CoreCLR: what it really does

1. **Execution (JIT + tiering, inlining/devirtualization; AOT trade-offs; exceptions costs)**
2. **Memory management (generational GC; server vs workstation; LOH/pinning; allocation model)**
3. **Concurrency plumbing (ThreadPool; async I/O integration; sync costs: contention/context switches/cache lines)**

### 1) **Execution**
**Definition**
- **CoreCLR** (the modern CLR) is the runtime that:
  - Loads assemblies and type metadata
  - JIT-compiles IL to machine code (or uses precompiled code when publishing with ReadyToRun/AOT)
  - Implements exception handling, generics, reflection services, and interop boundaries

**JIT compilation in real life**
- Modern .NET uses **tiered compilation**:
  - **Tier 0**: compiles quickly to get the app running (lower optimizations).
  - **Tier 1**: recompiles “hot” methods with deeper optimizations once usage is observed.
- This means:
  - The first few requests/operations can be slower (cold start behavior).
  - Microbenchmarks must be designed to avoid measuring tier transitions instead of your algorithm.

**Inlining / devirtualization (why your “small method” matters)**
- The JIT can inline small methods and sometimes devirtualize calls when it can prove the exact type.
- “Clean code” and performance can align: small, predictable methods with stable types are easier to optimize than megamethods with dynamic dispatch everywhere.

**Exceptions are not control flow**
- Throwing exceptions is expensive: it captures stack, unwinds frames, and often prevents optimizations.
- Use exceptions for *exceptional* cases; for expected outcomes prefer:
  - `TryParse` / `Try*` patterns
  - `bool TryX(out T value)` / `T?` + validation

**Trade-offs**
- JIT often wins in steady-state throughput because it can optimize for the exact CPU/runtime environment.
- AOT can improve startup and reduce runtime JIT work, but often restricts reflection/dynamic code patterns and can increase build complexity (deep coverage in section **2.2**).

**Performance note**
- Always separate:
  - **Cold start**: first request, JIT/tier transitions, cache warmup
  - **Warm steady-state**: optimized code paths, stable caches

### 2) **Memory management**
**Definition**
- The runtime provides a managed heap with **generational garbage collection** (GC), plus helpers for:
  - Finalization, pinning, and interop marshaling
  - Stack vs heap rules for managed objects

**What the GC does (and what it does *not* do)**
- GC reclaims *managed memory*; it does not magically close OS handles or network sockets.  
  - That’s why `IDisposable` / `IAsyncDisposable` exist (deep in section **4.2**).

**Server vs workstation GC**
- **Server GC**: optimized for throughput and multi-core servers; uses more memory and parallelism.
- **Workstation GC**: optimized for interactive responsiveness (e.g., desktop apps).
- In ASP.NET Core services, server GC is typically the right default.

**LOH and pinning**
- Large objects (arrays/strings above a threshold) go to the **Large Object Heap (LOH)**. Excessive LOH churn increases fragmentation and pause times.
- **Pinning** (e.g., for interop) can prevent GC from compacting memory effectively. Prefer APIs that avoid long-lived pinned buffers.

**Mentor stress points**
- Most “GC issues” are really **allocation rate** issues.
- Optimize by reducing allocations in hot paths before reaching for exotic settings.

**See also**
- Full GC mechanics, allocation patterns, and practical tuning live in section **2.3**.

### 3) **Concurrency plumbing**
**Definition**
- CoreCLR provides:
  - **ThreadPool**: shared pool of worker threads used by tasks, timers, and async continuations.
  - **Async I/O integration**: async file/network I/O generally uses OS async primitives so it doesn’t require a dedicated thread while waiting.
  - **Synchronization primitives** (`Monitor`, `lock`, `SemaphoreSlim`, `WaitHandle`, etc.)

**What “async” really means**
- `async`/`await` is about **non-blocking waiting**, not about “using more threads”.
- With proper async I/O, the runtime can handle many concurrent operations with a relatively small number of threads.

**The cost model**
- **Blocking** (`Task.Result`, `Wait()`, `Thread.Sleep`, sync-over-async) consumes a thread while waiting.
  - On servers, this can cause **ThreadPool starvation** and a cascade of latency.
- **Contention** (`lock` hot spots) leads to:
  - context switches
  - cache-line bouncing
  - reduced throughput under load

**Common mistakes**
- Using `Task.Run` to “make it async” for I/O code.
  - `Task.Run` is for CPU-bound work you *choose* to offload; I/O should usually be truly async.
- Mixing `async` with `lock` and then awaiting inside a lock (deadlocks + poor throughput).
  - Use async-friendly primitives (`SemaphoreSlim`) or restructure.

**Good to know**
- ThreadPool heuristics evolve across runtime versions; upgrading the runtime can measurably change throughput/latency (one reason to track runtime versions operationally).
- Deep concurrency & parallelism guidance belongs in the dedicated Concurrency & Parallelism tutorial section; this file focuses on runtime responsibilities only.
