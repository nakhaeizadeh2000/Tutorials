## 1.2. CLI / CTS / CLS and standardization

1. **What CLI standardizes (CTS, metadata, IL/CIL, execution model)**
2. **Language interoperability (CLS rules; public API constraints; common interop breakers)**
3. **Why it matters (reflection/trimming/analyzers; standards ≠ identical performance)**

### 1) **What CLI standardizes**
**Definition**
- **CLI** (Common Language Infrastructure) is the standardized foundation that describes:
  - **CTS** (Common Type System): what “a type” is (classes, interfaces, value types, generics, arrays, references), and the rules for identity and compatibility.
  - **Metadata**: the self-describing tables stored in assemblies (types, members, attributes, references).
  - **IL/CIL**: the CPU-independent instruction set compiled from languages like C#.
  - **Execution model**: verification rules, exception semantics, calling conventions, and how the runtime binds metadata + IL to execution.

**When to care**
- You care whenever you:
  - Design **public APIs** (types, generics, exceptions, attributes).
  - Use **reflection**, source generation, or serialization.
  - Deal with **trimming/AOT**, where dynamic patterns can break (because metadata or code may be removed).

**Trade-offs / common mistakes**
- **Mistake**: Treating IL as a “portable performance format.”  
  - CLI standardizes *semantics*; performance is largely a runtime/JIT/GC + CPU/cache + OS scheduling story (see **1.3** and **2.2**).
- **Mistake**: Assuming “metadata is always there.”  
  - With trimming or native AOT, metadata can be reduced; you must design for it (see **2.2** for AOT/trimming constraints).

**Good to know**
- C# language features may compile down to older IL constructs (the runtime doesn’t “know” your high-level syntax).
- “Verifiable IL” matters in constrained environments; in normal server apps you mostly care because it shapes runtime guarantees and tooling.

### 2) **Language interoperability (CLS)**
**Definition**
- **CLS** (Common Language Specification) is a subset of CTS rules that languages agree on so that a **public API** can be consumed from many CLI languages.
- Think of it as “**public surface compatibility rules**.”

**When to use / why you might still care in 2026**
- If you publish libraries used beyond C# (F#, VB, PowerShell, tooling hosts), CLS still matters.
- Even if all your consumers are C#, CLS nudges you toward cleaner, less surprising APIs.

**Common CLS-related interop breakers**
- **Unsigned integers** (`uint`, `ulong`, `ushort`) in public APIs: not all languages treat them equally.
- **Overloads differing only by ref-ness** can be painful for some languages/tools.
- **Case-sensitive name collisions** (e.g., `Foo` and `foo`) in the same scope: some languages are case-insensitive.
- **Pointer types** and `unsafe` constructs in public surface: often not CLS-friendly.

**Practical guidance**
- If you build a general-purpose library:
  - Prefer `int/long` over `uint/ulong` in public APIs unless you truly need the range.
  - Prefer simple overload sets and avoid “clever” signatures that rely on C#-only features.

**Code example: marking CLS compliance**
```csharp
using System;

[assembly: CLSCompliant(true)]

public static class LibraryApi
{
    // CLS-friendly:
    public static bool TryParseCount(string? text, out int value) =>
        int.TryParse(text, out value);

    // Avoid in public APIs if you need broad language/tool compatibility:
    // public static uint GetFlags() => 0u;
}
```

**نکته**
- CLS compliance is about **public** surface. Internals can use whatever is best for performance and correctness.

### 3) **Why it matters (today)**
**Reflection, trimming, and AOT**
- Modern .NET apps increasingly use **publish-time features** (trimming, single-file, ReadyToRun, native AOT).
- Reflection-heavy patterns can become fragile under trimming/AOT unless you:
  - Use **source generators** where possible (compile-time metadata).
  - Use **reflection annotations** only when necessary (and keep them targeted).

**Analyzers and “the compiler as a platform”**
- Because metadata is standardized, tooling can reason about your code:
  - Roslyn analyzers enforce style and correctness.
  - Source generators produce code to replace reflection at runtime.

**Standards ≠ identical performance**
- Two runtimes can run the same IL correctly but with different performance characteristics (JIT heuristics, GC tuning, ThreadPool behavior).
- Mentor advice: treat runtime upgrades as both **security** and **performance** upgrades; validate hot paths after moving to a new .NET major version.
