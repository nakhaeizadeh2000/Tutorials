## 2.1. The `System.Console` class: input, output, formatting

1. **Write/WriteLine, ReadLine, ReadKey (and when each is appropriate)**
2. **Formatting (interpolation, composite formatting, culture, and performance implications)**
3. **Common pitfalls (null input, blocking reads, encoding, flushing, testing console apps)**

### 1) **Input and output fundamentals**
**Output**
- `Console.WriteLine(...)` is the default for human-readable output (adds a newline).
- `Console.Write(...)` is useful for prompts that should stay on the same line.
- Prefer *structured* output for machines (JSON/CSV) rather than “pretty” text if you intend to parse it later.

**Input**
- `Console.ReadLine()` reads a line and returns `string?` (it can be `null`, e.g., redirected input ends).
- `Console.ReadKey()` reads a single keypress; use it for “press any key” and simple menus, not for real text entry.

**Mentor rule**
- Treat console input as **untrusted**. Validate early, parse with `TryParse`, and handle end-of-input gracefully.

### 2) **Formatting (correctness first, then performance)**
**String interpolation vs composite formatting**
- Interpolation: `$"Total: {total}"` (clear and modern).
- Composite formatting: `Console.WriteLine("Total: {0}", total)` (older style; still fine, but less idiomatic).

**Culture matters**
- If you print or parse numbers/dates for humans, use **current culture**.
- If you print or parse for machines (logs, files, protocols), prefer **invariant culture**.

```csharp
using System.Globalization;

var price = 12.5;
Console.WriteLine($"User-facing: {price}"); // current culture
Console.WriteLine($"Machine: {price.ToString(CultureInfo.InvariantCulture)}");
```

**Performance reality**
- Console I/O is orders of magnitude slower than normal CPU work. Optimize **frequency of writes** (batch output) before optimizing formatting.
- Don’t put expensive formatting inside tight loops if you can accumulate and print once.

### 3) **Common pitfalls (and the “adult” fixes)**
**Pitfall: `ReadLine()` returns null**

```csharp
var line = Console.ReadLine();
if (line is null)
{
    // End-of-input (Ctrl+Z/Ctrl+D or redirected file ended)
    return;
}
```

**Pitfall: using exceptions for normal parsing**

```csharp
Console.Write("Age: ");
var text = Console.ReadLine();

if (!int.TryParse(text, out var age) || age < 0)
{
    Console.WriteLine("Please enter a valid non-negative integer.");
    return;
}
```

**Pitfall: encoding surprises**
- If your app prints non-ASCII characters, be explicit when needed:
  - `Console.OutputEncoding = Encoding.UTF8;`
  - But do this deliberately: changing encoding may affect redirected output or terminals.

**Pitfall: writing tests for console apps**
- Direct `Console.ReadLine()` makes testing hard. Prefer moving logic into pure functions and keep console I/O at the edges.
- If you later want testable I/O, consider injecting `TextReader`/`TextWriter` (`Console.In`, `Console.Out` patterns) instead of static calls everywhere.
