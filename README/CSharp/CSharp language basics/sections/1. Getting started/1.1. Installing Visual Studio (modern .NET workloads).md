## 1.1. Installing Visual Studio (modern .NET workloads)

1. **What to install (workloads, SDKs, and how they map to app types)**
2. **Project templates you should start with (Console, Web, Worker, Tests)**
3. **Mentor notes (Debug vs Release, x64 vs arm64, “it runs” vs “it deploys”)**

### 1) **What to install**
**Mental model (don’t guess; know what each thing is)**
- **.NET SDK**: compiler + build tooling (`dotnet`) + workloads. This is what actually builds your code.
- **Runtime**: what executes your app on a machine without the SDK.
- **Visual Studio**: an IDE that drives MSBuild/SDK and adds debugging/profiling tools. It is not “the build system”; the `.csproj` + SDK are.

**Recommended workloads (most learners)**
- **.NET desktop development**: only if you plan WinForms/WPF.
- **ASP.NET and web development**: if you plan to build APIs/web apps.
- **.NET cross-platform development**: if you plan MAUI (optional; heavier setup).
- Always ensure a **modern .NET SDK** is installed (use the latest stable your repo targets).

**Why this matters for performance**
- Your **runtime version** affects JIT/GC/ThreadPool behavior. Upgrading .NET can yield real perf wins without code changes.
- Your **target architecture** matters: `x64` vs `arm64` changes JIT codegen and sometimes throughput.

### 2) **Project templates you should start with**
**Good defaults**
- **Console App**: learn language + control flow with minimal framework noise.
- **ASP.NET Core Web API**: when you want HTTP + DI + configuration.
- **Worker Service**: background processing without web hosting.
- **Test Project**: start early; testing is a core “language skill” in real life.

**Mentor tip**
- Don’t start with a “kitchen sink” template. Choose the smallest template that demonstrates the concept you’re learning.

### 3) **Mentor notes**
**Debug vs Release**
- Debug builds are for correctness and debugging. **Performance conclusions must be validated in Release** because optimizations, inlining, and even timing behavior differ.

**x64 vs arm64**
- Prefer running and profiling on the same architecture you will deploy to. Otherwise you can “optimize” the wrong thing.

**“It runs” vs “it deploys”**
- Local runs (`dotnet run`, F5) are not the same as shipping (`dotnet publish`). Deployment introduces real constraints (RID, trimming/AOT choices, native dependencies).
