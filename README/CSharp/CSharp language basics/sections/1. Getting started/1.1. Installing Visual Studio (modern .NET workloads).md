## 1.1. Installing Visual Studio (modern .NET workloads)

### 1) **What to install (workloads, SDKs, and how they map to app types)**
**Mental model (know what you’re installing)**
- **.NET SDK**: compiler + MSBuild + `dotnet` CLI. This is what *builds* your code and determines your language/runtime features at build time.
- **.NET Runtime**: what *executes* apps on machines that don’t have the SDK.
- **Visual Studio**: an IDE that drives MSBuild/SDK, and adds debugging/profiling. It is not “the build”; the `.csproj` + SDK are.

**Workloads are just feature bundles**
- Workloads control which templates, tooling, and optional components are installed.
- Choose workloads to match *what you build* (desktop/web/mobile), not “install everything”.

**Recommended workloads (typical learner path)**
- **Console + libraries (default)**: no special workload required beyond a modern .NET SDK.
- **ASP.NET and web development**: for APIs and web apps.
- **.NET desktop development**: only if you are targeting **WinForms/WPF** (Windows).
- **.NET cross-platform development (MAUI)**: only if you are intentionally learning MAUI (bigger install surface).

**Trade-offs and common mistakes**
- **Mistake**: starting with legacy frameworks and templates.
  - Prefer modern .NET (9+) templates. Avoid `.NET Framework` unless maintaining legacy Windows-only apps.
- **Mistake**: treating the IDE as the build contract.
  - Learn to run `restore/build/test/run/publish` via CLI as well (deep treatment is in Fundamental Theories tooling sections).

**Performance note**
- Runtime upgrades can materially improve **JIT**, **GC**, and **ThreadPool** behavior. Keep runtime current when you care about performance.

### 2) **Project templates you should start with (and when to use them)**
**Console App**
- Best for learning language fundamentals and control flow with minimal framework noise.

**ASP.NET Core Web API**
- Choose when you need HTTP, DI, configuration, logging, and a production hosting model.

**Worker Service**
- Choose for background processing without a web surface (queues, polling, scheduled jobs).

**Test Project**
- Start early. Testing is a core professional skill and helps you learn the language through feedback loops.

**Mentor tip**
- Pick the smallest template that demonstrates the concept. Complexity is a cost: more moving parts, more confusion, slower iteration.

### 3) **Mentor notes (Debug vs Release, x64 vs arm64, “it runs” vs “it deploys”)**
**Debug vs Release**
- Debug is for correctness and debugging; optimizations differ. Validate performance in **Release**.

**x64 vs arm64**
- Prefer running and profiling on your *deployment* architecture. Codegen and throughput can differ.

**“It runs” vs “it deploys”**
- Running locally (`dotnet run`, F5) is not the same as shipping (`dotnet publish`).
- Publish introduces real constraints (runtime identifier, trimming/AOT decisions, native dependencies).
