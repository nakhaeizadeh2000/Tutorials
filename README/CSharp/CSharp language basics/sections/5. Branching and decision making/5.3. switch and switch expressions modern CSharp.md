## 5.3. `switch` and `switch` expressions (modern C#)

2. **`switch` expressions for value-producing decisions (and why they reduce bugs)**

### 1) **`switch` statement basics + `default` and fall-through rules**
**What `switch` is for**
- Use `switch` when you’re dispatching based on a *single value* (often an `enum`, an `int` choice, or a command token).
- A good `switch` makes decision logic **auditable**: one input, clearly separated cases, explicit defaults.

**Core rules (C# 15 era)**
- C# prevents accidental fall-through between non-empty cases.
  - This is a correctness feature: it removes an entire class of “forgotten break” bugs from older C-like languages.
- You can still share logic, but you must do it intentionally:
  - Use a shared method, or `goto case` when it’s truly the clearest option.
  - Deep guidance on `goto case` lives in **`7.2`**.
- Prefer switching on **typed values** (enums) once you move past toy programs.

**Patterns you should recognize**
- `switch` statement for *effects* (do work per case)
- `switch` expression for *values* (compute result per case) — see item 2

**Common mistakes**
- Switching on “magic strings” with inconsistent casing/whitespace.
  - Normalize once at the boundary (trim + a casing strategy), then branch.
  - For canonical boundary parsing + culture guidance, see **`2.1`**.
- Writing huge switches where each case is a mini-program. Extract functions; keep each case small.

Performance note:
- `switch` vs `if` is rarely your bottleneck. Pick the construct that reduces bugs and review time.

### 2) **`switch` expressions for value-producing decisions (and why they reduce bugs)**
**Why switch expressions matter**
- A switch expression *returns a value*, which pushes you toward:
  - fewer “declare then assign later” patterns,
  - fewer uninitialized variables,
  - more exhaustive thinking (“what should this return for every input?”).

**Example (mapping inputs → outputs)**

```csharp
static string DescribeHttpStatus(int code) => code switch
{
    200 => "OK",
    400 => "Bad Request",
    401 => "Unauthorized",
    404 => "Not Found",
    >= 500 and < 600 => "Server Error",
    _ => "Unknown"
};
```

**When not to use it**
- If the branch is primarily about validation + early exit, a guard clause with `if` is often clearer (see **`5.1`**).

Trade-off:
- A switch expression can become unreadable if each arm does heavy work. Keep arms simple; call methods for heavy work.
