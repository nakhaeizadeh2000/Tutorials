## 5.2. Nested `if` (when it’s ok) + refactoring alternatives

1. **Examples: multi-step decision trees (and where they go wrong)**
2. **Alternatives: guard clauses, `switch`, and splitting into small functions**
3. **Performance notes (branch predictability is real; clarity usually wins first)**

### 1) **When nested `if` is reasonable**
**Good reasons**
- You’re expressing a real **decision tree** where each check depends on the earlier one.
- You need to avoid doing expensive work unless earlier prerequisites hold.
- The nesting depth stays small (usually 2–3 levels max).

**Example (dependent prerequisites)**

```csharp
var input = Console.ReadLine();
if (input is not null)
{
    if (int.TryParse(input, out var n))
    {
        if (n is >= 0 and <= 100)
        {
            Console.WriteLine("Valid percentage.");
        }
        else
        {
            Console.WriteLine("Out of range (0..100).");
        }
    }
    else
    {
        Console.WriteLine("Not an integer.");
    }
}
```

### 2) **Refactoring alternatives (prefer these as complexity grows)**
**A) Guard clauses (early returns)**
- Convert “happy path” into straight-line code.
- Keep nesting shallow.

```csharp
static void HandlePercentageInput(string? input)
{
    if (input is null)
        return;

    if (!int.TryParse(input, out var n))
    {
        Console.WriteLine("Not an integer.");
        return;
    }

    if (n is < 0 or > 100)
    {
        Console.WriteLine("Out of range (0..100).");
        return;
    }

    Console.WriteLine("Valid percentage.");
}
```

**B) Split into small functions**
- When a nested branch becomes a “mini algorithm”, extract it.
- This improves testability and reduces the chance of “forgotten else paths”.

**C) Use `switch` / `switch` expressions**
- Use `switch` when you’re dispatching based on a single value (or patterns) and want explicit exhaustiveness.

### 3) **Performance notes (true, but not an excuse to write unreadable code)**
**Branch predictability**
- CPUs predict branches. Code with stable, predictable conditions can be faster.
- In most beginner programs, **I/O dominates**; focus first on correctness and clean structure.

**Avoid duplicated expensive conditions**
- If the condition calls a function, performs parsing, or does allocations, compute once then branch on the computed value.
