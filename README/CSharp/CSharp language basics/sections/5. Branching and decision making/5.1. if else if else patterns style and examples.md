## 5.1. `if`, `else if`, `else`: patterns, style, and examples

1. **Canonical forms (simple `if`, `if-else`, `else if` chains, nested `if`)**
2. **Examples: validation, range checks, and early returns**
3. **Best practices (guard clauses, keep nesting shallow, don’t duplicate expensive conditions)**

### 1) **Canonical forms**
**Simple `if`**

```csharp
if (isEnabled)
{
    Console.WriteLine("Enabled");
}
```

**`if-else`**

```csharp
if (age >= 18)
{
    Console.WriteLine("Adult");
}
else
{
    Console.WriteLine("Minor");
}
```

**`else if` chain**

```csharp
if (score >= 90)
    Console.WriteLine("A");
else if (score >= 80)
    Console.WriteLine("B");
else if (score >= 70)
    Console.WriteLine("C");
else
    Console.WriteLine("Needs work");
```

**Nested `if` (use sparingly)**

```csharp
if (user is not null)
{
    if (user.IsActive)
    {
        Console.WriteLine("Active user");
    }
}
```

### 2) **Examples (mentor-grade patterns)**
**Example: validate input with early returns (guard clauses)**

```csharp
static int ParsePositiveIntOrThrow(string? text)
{
    if (string.IsNullOrWhiteSpace(text))
        throw new ArgumentException("Value required.", nameof(text));

    if (!int.TryParse(text, out var value))
        throw new FormatException("Value must be an integer.");

    if (value <= 0)
        throw new ArgumentOutOfRangeException(nameof(text), "Value must be positive.");

    return value;
}
```

**Example: avoid duplicated expensive conditions**

```csharp
static bool IsValidUsername(string? name)
{
    if (string.IsNullOrWhiteSpace(name))
        return false;

    // compute once; don't repeat expensive checks or allocations
    name = name.Trim();

    if (name.Length is < 3 or > 32)
        return false;

    return true;
}
```

### 3) **Best practices (correctness + performance)**
**Prefer guard clauses**
- Guard clauses reduce indentation and make “failure paths” explicit.
- They also prevent accidentally running expensive work deeper in nested blocks.

**Keep conditions pure**
- Avoid doing I/O, mutation, or allocations inside conditions when you can.
- This makes code easier to test and easier to reason about for performance.

**Don’t “micro-optimize” branches**
- Branch prediction is real, but in most application code, the big wins are:
  - fewer allocations,
  - fewer I/O calls,
  - and less duplicated work.
