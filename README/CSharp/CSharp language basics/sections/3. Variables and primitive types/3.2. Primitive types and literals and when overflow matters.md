## 3.2. Primitive types and literals (and when overflow matters)

1. **Integral types (`byte`…`long`), floating point (`float`/`double`), and `decimal`**
2. **`char`, `bool`, `string`, `DateTime` vs `DateTimeOffset` (starter guidance)**
3. **Checked vs unchecked arithmetic (correctness first; performance is a second-order effect)**

### 1) **Integral types (`byte`…`long`), floating point (`float`/`double`), and `decimal`**
**Integers (exact)**
- Default to **`int`** for counters, small ranges, and general arithmetic.
- Use **`long`** when values can exceed ~2.1 billion (sizes in bytes, timestamps in ticks, large IDs).
- Use smaller integers (`byte`, `short`) mainly for **binary formats / interop / memory layout**, not by habit. The JIT commonly promotes arithmetic to `int` anyway.
- Use unsigned types (`uint`, `ulong`) only when their semantics are required (bit operations, hashes, interop). They can make APIs harder to reason about (especially mixing signed/unsigned).

**Floating point (approximate)**
- Prefer **`double`** as the default real-number type.
- `float` is mainly for large arrays / graphics / interop, where memory bandwidth matters.
- Don’t compare computed floating-point values for equality; use tolerances (keep the “AlmostEqual” helper in one canonical place—this file—if you need it later).

**`decimal` (base-10, high precision)**
- Prefer **`decimal`** for money and human-facing base-10 quantities where rounding must match business expectations.
- Trade-off: `decimal` is slower and larger than `double`, but correctness wins for financial code.

Good to know:
- Numeric operations can overflow (integers) or round (floating point). Bugs often come from assuming “math is exact”.

### 2) **`char`, `bool`, `string`, `DateTime` vs `DateTimeOffset` (starter guidance)**
**`bool`**
- Name boolean variables in a positive, readable way (`isEnabled`, `hasValue`, `shouldRetry`).
- Avoid double negatives in conditions; they increase bug density in reviews.

**`char`**
- `char` is a **UTF-16 code unit**, not necessarily a full user-perceived character (grapheme cluster). For beginner basics, treat it as “one UTF-16 unit”.

**`string`**
- Strings are immutable. Repeated concatenation in loops allocates many transient strings.
- Don’t jump to `StringBuilder` immediately—first reduce I/O and repeated work; then consider `StringBuilder` when you’ve proven concatenation is a hotspot.

**Time types**
- Prefer **`DateTimeOffset`** to represent a real moment in time that crosses machines/time zones.
- Use `DateTime` only for local concepts (“store opens at 09:00 local time”), and be explicit about `Kind` if you must.

### 3) **Checked vs unchecked arithmetic (correctness first; performance is a second-order effect)**
**What “checked” means**
- In a `checked` context, integer overflow throws `OverflowException`.
- In an `unchecked` context, integer overflow **wraps** (two’s complement) and silently produces the wrong answer *unless wraparound is intended*.

**When to use which**
- Business logic / counters / money / sizes: overflow is almost always a bug → prefer **`checked`** or use a wider type (`long`) and validate inputs.
- Low-level algorithms (hashing, bit mixing): wraparound is often intentional → use **`unchecked`** to make intent explicit.

**Example (runnable)**

```csharp
static int DoubleBytesChecked(int bytes)
{
    checked
    {
        return bytes * 2;
    }
}

static int DoubleBytesUnchecked(int bytes)
{
    unchecked
    {
        return bytes * 2;
    }
}

Console.WriteLine(DoubleBytesUnchecked(1_500_000_000)); // wraps (wrong for business logic)
// Console.WriteLine(DoubleBytesChecked(1_500_000_000)); // throws OverflowException
```

**Trade-offs**
- `checked` adds overflow checks. This is usually negligible in everyday code, and the correctness benefit is huge.
- Don’t use exceptions as “normal control flow” for expected user input; validate ranges before risky operations.
