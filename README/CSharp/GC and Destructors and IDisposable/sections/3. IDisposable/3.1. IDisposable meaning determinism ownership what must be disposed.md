## 3.1. What `IDisposable` means (determinism, ownership, and “what must be disposed”)

1. **Dispose is a contract** (idempotency, safe to call multiple times, “object after dispose” policy)
2. **Typical disposables** (streams, `HttpResponseMessage`, enumerators with resources, timers, CTS, pooled buffers)
3. **Ownership rules** (creator owns by default; borrowing must be explicit; avoid double-dispose)

### 1) **Dispose is a contract**
**Definition**
- `IDisposable.Dispose()` is a **deterministic cleanup protocol**. It is not “optional niceness”; it’s how you release **non-memory** resources promptly (handles, native memory, pooled buffers, subscriptions).
- Treat `Dispose()` as a **contract with callers**:
  - **When** it must be called (end of scope / end of ownership).
  - **What** it does (release owned resources, stop background activity, unsubscribe).
  - **What happens after dispose** (object is unusable vs “limited safe operations”).

**Idempotency (mentor rule)**
- Ideally `Dispose()` is **safe to call multiple times**. Many BCL types are tolerant; some are not. For your own types, design for idempotency unless you have a strong reason not to.

**After-dispose behavior**
- The common .NET convention: using an object after dispose throws `ObjectDisposedException`.
- Don’t hide disposal bugs by silently “no-oping” everything after dispose. Throwing is usually better for correctness.

**Common mistakes**
- Implementing `IDisposable` “because best practice” while owning nothing. That trains callers to dispose everything and obscures real ownership.
- Making `Dispose()` do heavy work or block on I/O. If cleanup must do I/O, that usually belongs in `IAsyncDisposable` (full treatment: **3.3**).
- Forgetting to stop background loops/timers in `Dispose()`. Disposal must shut down owned activity.

**Runnable example: a correct, idempotent disposable**

```csharp
using System;
using System.Threading;

public sealed class TickSource : IDisposable
{
    private readonly Timer _timer;
    private int _disposed;

    public event EventHandler? Tick;

    public TickSource(TimeSpan period)
    {
        _timer = new Timer(_ => Tick?.Invoke(this, EventArgs.Empty), null, period, period);
    }

    public void Dispose()
    {
        if (Interlocked.Exchange(ref _disposed, 1) != 0)
            return;

        _timer.Dispose();
        Tick = null; // break subscriber references; optional but often helpful
    }
}

using var source = new TickSource(TimeSpan.FromSeconds(1));
source.Tick += (_, _) => Console.WriteLine("tick");
```

**Performance note**
- `Dispose()` should be **fast and non-blocking** in hot paths; avoid locks that can contend heavily. If you must synchronize, keep the critical section minimal.

### 2) **Typical disposables**
**What “must be disposed” typically means**
- If the type owns something that the GC can’t reclaim on a useful timeline, it should be disposable. The usual categories:
  - **OS handles**: `Stream`, `FileStream`, `Socket`, `SafeHandle`, OS primitives.
  - **Network/HTTP**: `HttpResponseMessage`, `HttpContent`, response streams.
  - **Timers and schedulers**: `Timer` and other scheduling primitives that keep callbacks alive.
  - **Cancellation**: `CancellationTokenSource` (it can hold timers/registrations).
  - **Pooled buffers**: `IMemoryOwner<T>` from `MemoryPool<T>`, many high-perf pipelines.
  - **Enumerators with resources**: some enumerators wrap unmanaged resources (rare but exists).

**Modern guidance (avoid a common pitfall)**
- **Don’t dispose `HttpClient` per request**. It’s intended to be long-lived. Dispose responses, not the client.
  - This tutorial doesn’t deep-cover HTTP lifetimes; treat this as a quick reminder.

**Good to know**
- Not every type with a finalizer should be used as “cleanup mechanism”. Prefer `using` even when finalizers exist; finalizers are a safety net, not the plan (see **2.2–2.3** and **3.2**).

### 3) **Ownership rules**
**Definition**
- Ownership answers: **who disposes**?
- If a component owns a resource, it must dispose it. If it only **borrows** a resource, it must not dispose it.

**Default rule**
- “**Creator owns**” is a good default: the code that `new`s something disposes it.

**Make ownership explicit (API design)**
- If you accept a `Stream`, `TextWriter`, `DbConnection`, etc. decide if you:
  - **borrow** (caller disposes), or
  - **take ownership** (you dispose).
- Encode this explicitly (see **3.4** for deeper API shapes).

**Common mistakes**
- Disposing something you don’t own (double-dispose) because “it’s IDisposable”.
- Leaking because “someone else will dispose it” (no one does).
- Hidden ownership via DI: container-created scoped objects should be disposed by the scope, not manually.

**Good to know**
- Ownership is a **design boundary**. The best “IDisposable code” is often the code that makes ownership impossible to misunderstand.
