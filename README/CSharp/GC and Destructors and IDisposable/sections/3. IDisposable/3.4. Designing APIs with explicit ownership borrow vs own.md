## 3.4. Designing APIs with explicit ownership (borrow vs own, factories, and DI lifetimes)

1. **Borrowing vs owning parameters** (bool flag, wrapper types, or “factory in / instance out”)
2. **Factories as ownership boundaries** (`Func<T>`, `IServiceScopeFactory`, “create per operation”)
3. **DI interactions** (container disposes scopes; don’t manually dispose DI-owned instances)

### 1) **Borrowing vs owning parameters**
**Definition**
- Ownership is the decision of **who is responsible for calling `Dispose()` / `DisposeAsync()`**.
- An API that accepts an `IDisposable` can either:
  - **Borrow** it: use it but **must not dispose** it.
  - **Own** it: take responsibility and **dispose** it.

**Why mentors insist on this**
- Most resource bugs in real systems are **ownership bugs**:
  - double-dispose
  - use-after-dispose
  - “nobody disposed it”
  - “DI disposed it and we also disposed it”

**Make ownership explicit**
- **Prefer different types** (best when you own the API surface):
  - `TextWriter` (borrowed) vs `OwnedTextWriter` (owned wrapper) patterns
  - or “factory in, instance out” (see item 2)
- If you must use a flag, keep it **rare** and **highly visible** (named parameter), and default to **borrowing** unless there is a strong reason.

**Example: borrowing vs owning made explicit**

```csharp
using System;
using System.IO;

public sealed class CsvWriter : IDisposable
{
    private readonly TextWriter _writer;
    private readonly bool _ownsWriter;

    public CsvWriter(TextWriter writer, bool ownsWriter = false)
    {
        _writer = writer ?? throw new ArgumentNullException(nameof(writer));
        _ownsWriter = ownsWriter;
    }

    public void WriteRow(ReadOnlySpan<string> cells)
    {
        for (int i = 0; i < cells.Length; i++)
        {
            if (i != 0) _writer.Write(',');
            _writer.Write(cells[i]);
        }
        _writer.WriteLine();
    }

    public void Dispose()
    {
        if (_ownsWriter)
            _writer.Dispose();
    }
}
```

**Trade-offs**
- Flags are easy to misuse; wrapper/factory shapes are harder to misuse.
- Owning parameters can be surprising to callers—document it clearly.

**Good to know**
- `Dispose()` should be **idempotent** (safe if called multiple times). That doesn’t mean “everything is safe after dispose”—define and enforce your post-dispose behavior (throw `ObjectDisposedException`, no-op, etc.) in the *owning* type.

### 2) **Factories as ownership boundaries**
**Definition**
- A **factory** (`Func<T>`, `IServiceScopeFactory`, custom `Create…` method) makes ownership explicit by saying:
  - “I will create it” → “I will dispose it”.

**When to use**
- When you need a component to create **per-operation** resources:
  - per-request streams
  - per-operation DB connections/transactions
  - per-call scoped services in a background worker

**Example: factory-in / instance-out**

```csharp
using System;
using System.IO;

public sealed class ReportExporter
{
    private readonly Func<TextWriter> _createWriter;

    public ReportExporter(Func<TextWriter> createWriter)
        => _createWriter = createWriter ?? throw new ArgumentNullException(nameof(createWriter));

    public void Export(string line)
    {
        using var writer = _createWriter(); // exporter owns it
        writer.WriteLine(line);
    }
}
```

**Performance note**
- Factories can allocate when they capture state (closures). Prefer:
  - method group / static lambda where possible
  - passing dependencies explicitly rather than capturing large graphs

### 3) **DI interactions**
**Core rule**
- If an instance is **created by the DI container**, its disposal is typically **owned by the container** (scope).
- You generally **must not dispose** DI-resolved services manually, unless your DI setup explicitly says “you own it”.

**Common mistakes**
- Registering an `HttpClient` as transient and disposing per call (hurts performance; increases socket churn).
- Capturing a scoped service in a singleton (lifetime mismatch) and then trying to “fix” it by manual disposal.

**Correct patterns**
- For per-operation lifetimes in background work, use `IServiceScopeFactory` to create a scope and let the scope dispose scoped services.
- For shared long-lived resources (e.g., `HttpClient`), register as singleton (or use `IHttpClientFactory` in ASP.NET Core).
