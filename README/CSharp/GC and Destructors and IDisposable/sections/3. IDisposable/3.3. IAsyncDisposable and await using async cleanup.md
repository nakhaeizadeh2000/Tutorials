## 3.3. `IAsyncDisposable` and `await using` (async cleanup done right)

1. **When async disposal is real** (flush/close requiring I/O; async streams; network protocols)
2. **`await using` scope** (avoid sync-over-async during cleanup)
3. **Mixing sync/async** (choose a primary cleanup path; don’t hide blocking in `Dispose()`)

### 1) **When async disposal is real**
**Definition**
- `IAsyncDisposable` represents **asynchronous cleanup** via `ValueTask DisposeAsync()`.
- It exists because some cleanup is **inherently async**:
  - flushing buffered data to an underlying stream over I/O,
  - sending protocol “close” frames (e.g., WebSockets),
  - awaiting background operations that must finish to release resources safely.

**When to use**
- Use `IAsyncDisposable` when cleanup logically requires `await` (I/O, async coordination).
- Use plain `IDisposable` when cleanup is:
  - CPU-only,
  - releasing managed references,
  - releasing OS handles synchronously (common for many handle wrappers).

**Trade-offs**
- Async disposal introduces an async boundary at scope end. That boundary can:
  - be good (non-blocking),
  - or be a cost if you’re overusing it in extremely hot micro-scopes (rare; measure).

**Common mistakes**
- Implementing `IAsyncDisposable` “because everything is async now” when disposal is actually synchronous.
- Returning a `Task` (allocating) instead of `ValueTask` when you complete synchronously often.
- Hiding blocking I/O inside `Dispose()` (sync-over-async) and calling it on a request thread.

**Good to know**
- `DisposeAsync()` should be **safe to call multiple times** (idempotent) just like `Dispose()` unless you document otherwise.

---

### 2) **`await using` scope**
**What `await using` means**
- `await using var x = ...;` is compiler sugar for a `try/finally` that awaits `x.DisposeAsync()` in the `finally`.
- This is the “correct” shape: you get exception safety and you don’t block a thread waiting for async cleanup.

**Why this matters**
- Without `await using`, people often do one of these:
  - forget to dispose at all,
  - call `.DisposeAsync().AsTask().Wait()` / `.GetAwaiter().GetResult()` (deadlock/ThreadPool starvation risks),
  - call a sync `Dispose()` on a type that really needs async cleanup (data loss / protocol issues).

**Runnable example**

```csharp
using System;
using System.Threading.Tasks;

sealed class AsyncResource : IAsyncDisposable
{
    private bool _disposed;

    public async ValueTask DisposeAsync()
    {
        if (_disposed) return;
        _disposed = true;
        await Task.Delay(10); // stand-in for async I/O cleanup
    }
}

static async Task UseAsync()
{
    await using var r = new AsyncResource();
    // work...
}

await UseAsync();
```

**Performance note**
- `await using` does not “make your app slower” by itself. It avoids blocking threads, which is usually a net win for throughput and tail latency.

---

### 3) **Mixing sync/async**
**Rule of thumb**
- Pick one primary cleanup model and keep it honest:
  - if the cleanup can be synchronous, implement `IDisposable` only,
  - if the cleanup is inherently asynchronous, implement `IAsyncDisposable` and require `await using`.

**If you implement both**
- Some BCL types implement both for convenience. If you do this, be deliberate:
  - `Dispose()` should either call the synchronous equivalent safely, or (if unavoidable) do minimal work and delegate to a non-blocking shutdown signal.
  - Avoid calling `DisposeAsync()` from `Dispose()` by blocking on it.

**Common mistakes**
- Library code implementing async cleanup but only exposing `Dispose()`, forcing callers into sync-over-async.
- Disposing in a finalizer and attempting async work (not possible; finalizers can’t `await`).
