## 5.3. Reliability checklist (handle exhaustion, socket leaks, shutdown, and cancellation)

1. **Dispose promptly under load** (handles are finite; “eventually” becomes outage)
2. **Cancellation and timeouts** (infinite waits keep resources alive forever)
3. **Shutdown semantics** (background work + disposal ordering; avoid relying on finalization at exit)

### 1) **Dispose promptly under load**
**What this really means**
- Reliability failures from leaks usually aren’t “memory first”; they’re **quota first**:
  - file handles (`ulimit -n`), sockets/ports, DB connections, timers, kernel objects.
- If a request leaks *one* handle, a service can appear fine in dev and fail under production concurrency.

**When to care**
- Always, but especially in:
  - services that do lots of I/O (HTTP, DB, file, queues)
  - background workers processing many jobs
  - apps that run for days (anything server-side)

**Common mistakes**
- Disposing too late because of `using var` at a method scope when you actually needed block scope.
- “I’ll rely on finalizers”: non-deterministic timing turns a minor leak into handle exhaustion.
- Disposing objects you don’t own (double-dispose) which can cause sporadic ObjectDisposedExceptions or corrupt a pool/stream state.

**Good to know**
- Some framework types you must be careful with:
  - **`HttpResponseMessage` / `HttpContent`** should be disposed when you own them (e.g., from `HttpClient.SendAsync`).
  - **`CancellationTokenSource`** is `IDisposable` (it holds timers/registrations internally).
  - **Enumerators** can be disposable; most in-memory enumerators are cheap, but enumerators over I/O are not.

**Performance note**
- Prompt disposal improves **throughput** (fewer retries/timeouts) and reduces **tail latency** (less resource contention, fewer thread-pool stalls).

### 2) **Cancellation and timeouts**
**Definition**
- **Cancellation** is cooperative: you design operations so they can stop *and release resources*.
- **Timeouts** are a safety net: they bound how long resources can remain held.

**Rules that scale**
- Accept a `CancellationToken` in any API that can block on I/O or wait on synchronization.
- Use timeouts at **boundaries** (HTTP client calls, DB calls, queue operations), not deep in every helper.
- Treat “no timeout” as a conscious decision you document.

**Common mistakes**
- Forgetting to pass the token to the *actual* async I/O call.
- Using `CancellationToken.None` in library code “because it’s easier”.
- Creating a new `CancellationTokenSource` per tiny operation without measuring (extra allocations/timers).

**Runnable example: time-bound work without leaks**

```csharp
using System;
using System.Net.Http;
using System.Threading;
using System.Threading.Tasks;

static async Task<string> GetTextWithTimeoutAsync(Uri uri, TimeSpan timeout, CancellationToken cancellationToken)
{
    using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(cancellationToken);
    timeoutCts.CancelAfter(timeout);

    using var http = new HttpClient(); // App-level: prefer a long-lived/singleton HttpClient; this is demo-only.
    using var response = await http.GetAsync(uri, timeoutCts.Token).ConfigureAwait(false);
    response.EnsureSuccessStatusCode();
    return await response.Content.ReadAsStringAsync(timeoutCts.Token).ConfigureAwait(false);
}
```

**Good to know**
- In ASP.NET Core, prefer setting **HttpClient timeouts** and per-request cancellation from the request token.
- Avoid “sync-over-async” in cancellation paths; it can deadlock (frontend) or starve threads (server).

### 3) **Shutdown semantics**
**What you must design for**
- “Process exit” is not a cleanup mechanism. Containers can terminate quickly; the OS can kill the process.
- A reliable service has an explicit shutdown path:
  - stop accepting new work
  - signal cancellation
  - drain in-flight work if required
  - dispose resources in the correct order

**Ordering pitfalls**
- Don’t dispose shared singletons (e.g., logging, HttpClient handlers, DB pools) before the last user finishes.
- Ensure background loops stop before disposing the resources they use (channels, timers, sockets).

**Modern guidance**
- In hosted services, tie cleanup to host lifetime:
  - `IHostedService.StopAsync` should request cancellation and wait briefly for a graceful stop.
- Do not rely on finalizers to flush buffers or send “last messages”.

**See also**
- Finalizers’ unreliability and exit behavior are covered in depth in section **2.3**.
