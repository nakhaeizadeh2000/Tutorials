## 2.2. When a finalizer is justified (and when it is a code smell)

1. **Legit case** (wrapping native resources where a safety net is required)
2. **Code smell cases** (managed-only resources; “just in case”; business logic in finalizers)
3. **Modern guidance** (prefer `SafeHandle`; prefer composition; keep finalizers tiny)

### 1) **Legit case (native resource safety net)**
**Definition**
- A finalizer is justified only when your type directly or indirectly owns a **native resource** that must be released even if the consumer forgets to dispose.
- “Native resource” here means something outside managed memory that can leak **even when the managed object becomes unreachable**:
  - OS handles (file/socket/registry/mutex/event)
  - native memory allocations (interop / unmanaged libraries)

**When you actually need one**
- You are building a **low-level wrapper** over a native handle and you cannot delegate safety to an existing safe abstraction.
- You cannot express cleanup purely as managed disposal of other managed disposables.

**The preferred approach (modern .NET)**
- Prefer `SafeHandle` (or a BCL type that already uses it) so the tricky finalization behavior is handled by the runtime libraries.
- Your type usually becomes: “managed object with deterministic Dispose; safety net is `SafeHandle` finalization, not your own finalizer.”

**Minimal example: wrapping an `IntPtr` vs using `SafeHandle`**
The `IntPtr` version below is intentionally shown as a “what you end up doing” (and why it’s fragile). In production code, prefer a `SafeHandle` derivative (second example).

```csharp
using System;
using System.Runtime.InteropServices;

// Example only: a fragile IntPtr wrapper that must use a finalizer.
sealed class NativeBuffer_IntPtr : IDisposable
{
    private IntPtr _ptr;
    private int _size;
    private bool _disposed;

    public NativeBuffer_IntPtr(int size)
    {
        _size = size;
        _ptr = Marshal.AllocHGlobal(size);
    }

    ~NativeBuffer_IntPtr() => Dispose(disposing: false);

    public void Dispose()
    {
        Dispose(disposing: true);
        GC.SuppressFinalize(this);
    }

    private void Dispose(bool disposing)
    {
        if (_disposed) return;
        _disposed = true;

        if (_ptr != IntPtr.Zero)
        {
            Marshal.FreeHGlobal(_ptr);
            _ptr = IntPtr.Zero;
            _size = 0;
        }
    }
}
```

```csharp
using System;
using System.Runtime.InteropServices;
using Microsoft.Win32.SafeHandles;

// Better: let SafeHandle own finalization; your wrapper often needs no finalizer.
sealed class NativeBuffer_SafeHandle : IDisposable
{
    private readonly SafeBufferHandle _handle;
    private bool _disposed;

    public NativeBuffer_SafeHandle(int size)
        => _handle = new SafeBufferHandle(size);

    public void Dispose()
    {
        if (_disposed) return;
        _disposed = true;
        _handle.Dispose(); // deterministic; safety net remains in SafeHandle if consumer forgets
    }

    private sealed class SafeBufferHandle : SafeHandleZeroOrMinusOneIsInvalid
    {
        public SafeBufferHandle(int size) : base(ownsHandle: true)
            => SetHandle(Marshal.AllocHGlobal(size));

        protected override bool ReleaseHandle()
        {
            Marshal.FreeHGlobal(handle);
            return true;
        }
    }
}
```

**Good to know**
- Even when you “need a finalizer”, the best design often moves it into a `SafeHandle` type and keeps your public object finalizer-free.
- If your type only composes other `IDisposable` objects, **you almost never need a finalizer**.

**Performance note**
- Finalizers add GC overhead and extend lifetime (full cost model is in **2.3**). Use them only when the correctness benefit is real.

### 2) **Code smell cases**
**Red flags**
- **Managed-only cleanup**: “I have a `FileStream`/`HttpClient`/`Timer`, so I added a finalizer.”  
  - This is a smell. You should dispose deterministically; finalizers are not a substitute.
- **“Just in case” finalizers** on business/domain objects.
- **Doing work** in finalizers: logging, network calls, locking, waiting, calling into other objects.

**Why it’s a smell**
- You are hiding an ownership/lifetime bug instead of fixing it at the API boundary.
- You pay ongoing runtime tax (promotion, queue management, extra collections), and you still don’t get reliable cleanup timing.

**Common mistakes**
- Throwing exceptions from a finalizer (don’t).
- Touching managed objects in a finalizer assuming they’re still valid (finalizer order is not guaranteed).
- Attempting to “fix” missed disposal by calling `Dispose()` from the finalizer without understanding the `Dispose(bool)` pattern.

### 3) **Modern guidance (C# 15 / .NET 9+)**
**Rules that scale**
- Prefer **composition + deterministic disposal** (`using var`, `await using`) over finalizers.
- If native handles are involved, prefer **`SafeHandle`** over writing your own finalizer.
- Keep cleanup logic **idempotent** and safe for partial construction failures.

**Legacy/obsolete patterns to avoid**
- “Finalizer-only cleanup” (no `IDisposable`) for anything user code can scope deterministically.
- Overusing the classic “full dispose pattern template” on every type. Most app types only need a simple `Dispose()` that disposes owned fields.
