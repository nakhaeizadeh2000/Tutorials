## 4.2. `await using` and async scope management (correct cleanup without deadlocks)

1. **Why `await using` exists** (async cleanup is not optional for some resources)
2. **Pitfalls** (forgetting `await` on `DisposeAsync`; mixing with `ConfigureAwait` in libraries)
3. **Guidelines** (async all the way; no sync-over-async in cleanup paths)

### 1) **Why `await using` exists**
**Definition**
- `await using` is the async analog of `using`. It calls **`DisposeAsync()`** (returning `ValueTask`) and **awaits** it so cleanup can perform **asynchronous work** without blocking threads.
- It is used for types implementing **`IAsyncDisposable`**.

**When async disposal is real**
- Cleanup that must do I/O (or something *effectively* async):
  - flushing buffered writes to a remote destination
  - graceful protocol shutdown / draining
  - releasing a leased resource that requires an async handshake
- You’ll also see `IAsyncDisposable` for integration with async frameworks/components even if internal work is minimal; treat it as “cleanup may be async”.

**Trade-off**
- `await using` pushes you toward **async all the way**. If your call chain is synchronous, you cannot use it without introducing async at the boundary.

**Good to know**
- For the deeper “what is `IAsyncDisposable` and how to design it” guidance, see section **3.3** (`3.3. IAsyncDisposable and await using async cleanup.md`).

### 2) **Pitfalls**
**Pitfall: forgetting `await`**
- This:

```csharp
// WRONG: DisposeAsync is not awaited. Cleanup may not run to completion.
using var r = GetAsyncDisposable(); // won't compile unless IDisposable
```

- The fix is:

```csharp
await using var r = GetAsyncDisposable();
```

**Pitfall: sync-over-async during cleanup**
- Implementing `Dispose()` by calling `DisposeAsync().AsTask().GetAwaiter().GetResult()` is a classic deadlock/ThreadPool starvation trap and is almost always wrong in library code.
- Prefer:
  - **a real synchronous Dispose** path (if possible), or
  - **make the type async-only** (expose `DisposeAsync()`; provide `Dispose()` only if it’s truly safe and non-blocking).

**Pitfall: confusing `ConfigureAwait` rules**
- In modern .NET server code, `ConfigureAwait(false)` is often unnecessary, but **library code** may still need it as a correctness/perf tool when running under UI SynchronizationContext (frontend).
- If you are writing a library, be explicit about your async scheduling expectations and avoid capturing contexts unnecessarily.

**Pitfall: disposing too late**
- `await using var` extends scope to the end of the containing block. That is convenient, but it can keep scarce resources alive longer than intended.

### 3) **Guidelines**
**Rule: keep lifetimes short and obvious**
- Use block-scoped `await using` when the resource is scarce (connections/streams/locks):

```csharp
await using (var resource = await AcquireAsync())
{
    await resource.DoWorkAsync();
}
```

**Rule: do not hide blocking**
- If your cleanup needs async work, expose it as async.
- Don’t make callers “think it’s cheap” by hiding waits inside `Dispose()`.

**Rule: choose a primary disposal path**
- If you implement both `IDisposable` and `IAsyncDisposable`, decide which is “the real one” and ensure both are correct and consistent.
- A common pattern is:
  - `Dispose()` releases what it can synchronously and is safe/non-blocking
  - `DisposeAsync()` does the full async cleanup

**Performance note**
- `await using` protects the ThreadPool: it avoids blocking threads during cleanup in high-concurrency systems.
