## 4.3. Nested disposables and partial construction failure (robust patterns)

1. **Multiple resources** (acquire in order; dispose in reverse; avoid leaks on exceptions)
2. **Factory methods** (when constructors can’t express safe acquisition)
3. **High-perf note** (avoid excessive allocations; prefer structured ownership)

### 1) **Multiple resources (acquire in order; dispose in reverse; avoid leaks on exceptions)**
**Definition**
- “Nested disposables” means you acquire **more than one** resource in a scope, and you must ensure:
  - each successfully acquired resource is disposed **exactly once**
  - disposal happens even if later acquisition fails
  - disposal order is **reverse acquisition order** (common for dependent resources)

**When you hit this in real systems**
- Opening a file + wrapping it in a buffered stream + wrapping in a reader/writer.
- Creating a DB transaction + command + reader.
- Allocating a pooled buffer + creating an object that uses it.

**Correct pattern: let `using`/`await using` build the stack**
- The key property: each `using var` introduces a `try/finally`; if the next line throws, the earlier ones are still disposed.

```csharp
using System;
using System.IO;
using System.Text;

static string ReadFirstLine(string path)
{
    using var file = new FileStream(path, FileMode.Open, FileAccess.Read, FileShare.Read);
    using var reader = new StreamReader(file, Encoding.UTF8, detectEncodingFromByteOrderMarks: true);

    // If StreamReader construction throws, FileStream is still disposed.
    return reader.ReadLine() ?? string.Empty;
}
```

**Common mistakes**
- Putting multiple acquisitions inside a single `try` without disposing earlier partial state.
- Returning early before disposing (fixed by `using`).
- Using `Dispose()` calls manually and missing exception paths.

**Performance note**
- Shorter lifetimes reduce pressure on scarce resources (handles/sockets) and reduce tail latency under load.

### 2) **Factory methods (when constructors can’t express safe acquisition)**
**Why factories matter**
- Constructors can’t be `async`, and they can’t easily express “partial acquisition with rollback” while keeping the object in a valid state.
- A factory lets you:
  - acquire multiple dependencies safely
  - return a fully-initialized object or throw with no leaks
  - choose `Dispose` vs `DisposeAsync` correctly

**Pattern: `Create` / `CreateAsync` that returns an already-safe instance**

```csharp
using System;
using System.IO;
using System.Threading;
using System.Threading.Tasks;

public sealed class OwnedFile : IAsyncDisposable
{
    public FileStream Stream { get; }

    private OwnedFile(FileStream stream) => Stream = stream;

    public static async ValueTask<OwnedFile> CreateAsync(string path, CancellationToken ct = default)
    {
        // Acquire resource first. If anything throws after this, we must dispose it.
        var stream = new FileStream(path, FileMode.Create, FileAccess.Write, FileShare.None, 64 * 1024, useAsync: true);
        try
        {
            // Example placeholder: any async initialization work that may fail.
            await stream.FlushAsync(ct).ConfigureAwait(false);
            return new OwnedFile(stream);
        }
        catch
        {
            await stream.DisposeAsync().ConfigureAwait(false);
            throw;
        }
    }

    public ValueTask DisposeAsync() => Stream.DisposeAsync();
}
```

**Good to know**
- Prefer a factory when initialization requires I/O, can fail mid-way, or needs cancellation.
- If the type is a thin wrapper and doesn’t need async initialization, keep it simple: `using var` in the caller is often best.

---

### 3) **High-perf note (avoid excessive allocations; prefer structured ownership)**
**Where performance is lost**
- Creating many small disposable wrappers in tight loops when a single long-lived resource would do.
- Pool misuse: allocating wrappers around pooled buffers but failing to return buffers promptly.
- Accidental lifetime extension: `using var` at method scope when only a small block needs it.

**Practical heuristics**
- Prefer the narrowest scope that still reads well.
- If you wrap a pooled resource, make the wrapper the “owner” and ensure disposal returns it quickly.
- Avoid “Dispose in finalizer” patterns as a fallback; that’s both correctness- and performance-hostile (deep treatment: `2.3` and `3.2`).
