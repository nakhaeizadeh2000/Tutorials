## 1.4. GC configuration you should understand (server vs workstation, latency modes)

1. **Server vs Workstation GC** (throughput vs interactive; containers/ASP.NET Core defaults)
2. **Latency modes** (what they can/can’t do; “critical sections” vs inevitable debt)
3. **Tuning rules** (optimize allocation + object lifetimes first; config is second-order)

### 1) **Server vs Workstation GC**
**Definition**
- **Workstation GC** is the default for most desktop/interactive apps. It’s tuned for responsiveness on a single heap with less parallelism.
- **Server GC** uses **multiple heaps** and **multiple GC threads**, typically improving throughput on multi-core machines (common for services/containers).

**When to use which**
- **ASP.NET Core / background services**: server GC is usually the right default.
- **Desktop UI apps** (frontend): workstation GC is usually appropriate (interactive responsiveness).

**Trade-offs**
- Server GC can improve throughput but may change pause characteristics and memory footprint.
- Changing GC mode is a **runtime configuration** decision; treat it as a measurable knob, not a guess.

**Good to know**
- For the deeper “what the CLR does” context (JIT, GC, ThreadPool as runtime services), see:
  - `README/CSharp/Fundamental Theories/sections/1. .NET and CSharp fundamentals & history/1.3. CLR CoreCLR responsibilities.md`

### 2) **Latency modes**
**Definition**
- Latency modes adjust the GC’s strategy for balancing **pause time** vs **throughput**.
- Practically, latency modes can *defer some expensive work*, but they cannot delete it: the GC debt will be paid later.

**When to use**
- Consider latency modes only if you have a **measured tail-latency issue** (p95/p99 spikes) and you can clearly define a **critical section** (e.g., a trading window, audio frame processing) where you want fewer pauses.

**Common mistakes**
- Using latency modes as a substitute for fixing allocation/survival problems.
- Turning a knob globally instead of isolating the truly critical section (you can shift the problem to a worse time).

**Performance note**
- If you need the full “generations, pauses, and modes” overview, this repo already covers it deeply here:

### 3) **Tuning rules**
**Mentor rule (order of operations)**
1. **Fix allocation rate** (bytes/sec) and obvious hot-path allocators.
2. **Fix object lifetimes** (what is keeping objects alive? caches/events/singletons).
3. **Fix LOH/pinning** if present (buffers/interop).
4. Only then consider **GC configuration**.

**What to avoid**
- **`GC.Collect()` as a tuning tool** in production. If you think you need it, you almost always have an ownership/lifetime bug or an allocation hot spot.

**Good to know**
- Tuning without measuring typically backfires. Make “before/after” measurements repeatable (same load, same environment, same counters).
