## 6.3. Interview Q&A: `IDisposable` patterns, `using var`, and `await using`

1. **When should a type implement `IDisposable`?** (owning resources; not “because best practice”)
2. **`using` statement vs `using var`** (scope and lifetime)
3. **`IDisposable` vs `IAsyncDisposable`** (async cleanup; avoid sync-over-async)

### 1) **When should a type implement `IDisposable`?**
**Best answer (senior-level)**
- Implement **`IDisposable`** when your type has **ownership** of something that must be released deterministically:
  - **OS handles** (files, sockets, wait handles)
  - **Managed wrappers** around native resources (especially with `SafeHandle`)
  - **High-count resources** even if “small” (e.g., `Timer`, `CancellationTokenSource`)
  - **Pooled buffers** (`ArrayPool<T>`, `MemoryPool<T>`) you must return
- Do **not** implement it “because it’s a class” or “to be safe”. If you don’t own releasable resources, `Dispose()` becomes noise and creates misuse risk.

**Trade-offs / design pressure**
- Adding `IDisposable` to a public type makes lifetime a **required part of the API contract**:
  - Callers must now structure scopes, tests must dispose, DI lifetimes matter.
- In libraries, `IDisposable` in an interface can be viral. Prefer owning wrappers or factory methods where possible.

**Common mistakes**
- Disposing objects you **don’t** own (double-dispose, breaking shared lifetimes).
- Forgetting that **`CancellationTokenSource` is disposable** (timer registration and kernel objects can be involved).
- Implementing a finalizer “just in case” (see `2.*` for the finalizer cost model).

**Good to know**
- Deterministic cleanup is both **correctness** and **performance**: it reduces handle pressure and stabilizes latency under load.

### 2) **`using` statement vs `using var`**
**Correct comparison**
- `using (...) { ... }` is **block-scoped**: disposal happens at the end of the block.
- `using var x = ...;` is **scope-scoped**: disposal happens at the end of the **enclosing scope** (method / loop iteration / `try` block, etc.).

**What interviewers want you to say**
- Both compile to `try/finally`. The difference is **lifetime clarity**.
- Prefer the form that makes resource lifetime **obvious**:
  - If the resource must end before more code runs, use a `using { }` block.
  - If the resource should live for the rest of the method and the method is short, `using var` is great.

**Pitfall example (scope is longer than you think)**

```csharp
using var stream = File.OpenRead(path);
DoSomething();
// stream is still open here; disposal happens at method end, not after DoSomething().
```

**Performance note**
- A longer-lived handle can cause real pressure under concurrency. Scope is a performance tool.

### 3) **`IDisposable` vs `IAsyncDisposable`**
**Best answer**
- Use **`IAsyncDisposable`** when cleanup needs **awaitable work** (typically I/O): flushing, protocol shutdown, async streams.
- Use **`IDisposable`** for purely synchronous cleanup (release handle, return to pool, clear managed references).

**Rules of thumb**
- Don’t hide async cleanup inside `Dispose()` by doing `DisposeAsync().AsTask().GetAwaiter().GetResult()` (sync-over-async). This can deadlock (frontend) and harms throughput everywhere.
- If you implement both, decide what `Dispose()` means:
  - Either `Dispose()` performs best-effort synchronous cleanup and `DisposeAsync()` does the full async path,
  - Or `Dispose()` delegates to `DisposeAsync()` only when it can do so without blocking (rare).
