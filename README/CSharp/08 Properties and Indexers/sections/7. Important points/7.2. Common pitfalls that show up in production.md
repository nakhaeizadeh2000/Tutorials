## 7.2. Common pitfalls that show up in production

1. **Throwing from getters under normal conditions** (breaks debugging, logging, binding/serialization expectations)
2. **Expensive computed properties** (accidental \(O(n)\) per call; cache carefully and invalidate correctly)
3. **“Write-only” APIs** (hard to test and reason about; replace with intention-revealing methods)

---

### 1) **Throwing from getters under normal conditions**

**Why this is a production pitfall**

In C#, `get` accessors are *expected* to be:
- **Fast**
- **Side-effect free**
- **Safe to call repeatedly**

Real systems (debuggers, loggers, serializers, data-binding frameworks) often call getters:
- many times
- at surprising times
- on partially-initialized objects

If your getter throws during “normal” usage (not a violated invariant), it causes:
- **Noisy telemetry** (exceptions flood logs)
- **Hard-to-debug failures** (debugger watch window triggers exceptions)
- **Framework breakage** (binding/serialization fails unexpectedly)

**Mentor rule**
- Use exceptions in getters only for **impossible states** (bugs / invariant violations). For expected absence/failure, provide an explicit API.

**Better alternatives**
- Prefer a method that communicates possible failure:
  - `TryGetX(out ...)`
  - `GetXOrDefault()`
  - `GetXOrThrow()` (explicitly opt-in to throwing)

**Example (runnable): make failure explicit**

```csharp
using System;

public sealed class UserContext
{
    private string? _token;

    // Bad: property throws as part of normal flow.
    public string TokenBad => _token ?? throw new InvalidOperationException("Not authenticated yet.");

    // Better: explicit API shapes.
    public bool TryGetToken(out string token)
    {
        if (_token is null) { token = ""; return false; }
        token = _token;
        return true;
    }

    public string GetTokenOrThrow()
        => _token ?? throw new InvalidOperationException("Not authenticated yet.");

    public void Authenticate(string token)
        => _token = string.IsNullOrWhiteSpace(token) ? throw new ArgumentException("Token required.", nameof(token)) : token;
}
```

**Good to know**
- Some serializers/binders can be configured to ignore exceptions, but relying on that is brittle. Design the API so your object is pleasant to inspect.

### 2) **Expensive computed properties**

**The common trap**

Computed properties are fine when they are **cheap**. The trap is a property that looks like a field but actually does:
- allocations (LINQ, `ToArray`, `string.Join`, formatting)
- locks / contention
- I/O (filesystem/network/database) — *never acceptable in a property*
- repeated \(O(n)\) work every time it’s accessed

**Mentor rule**
- If it’s expensive, make it a **method** so the cost is obvious: `ComputeTotal()`, `BuildReport()`, `LoadXAsync()`.

**Example (runnable): accidental \(O(n)\) property**

```csharp
using System;
using System.Collections.Generic;
using System.Linq;

public sealed class Basket
{
    private readonly List<decimal> _prices = new();

    public void Add(decimal price) => _prices.Add(price);

    // Bad: callers treat this like a simple value; it scans the list each time.
    public decimal TotalBad => _prices.Sum();

    // Better: keep it explicit, or maintain a cached value (shown below).
    public decimal ComputeTotal() => _prices.Sum();
}
```

**If you cache, be explicit about invalidation**

If you choose caching, you must define:
- when cache updates (on every mutation vs lazy recompute)
- whether it is thread-safe
- memory growth policy (if caching per key)

See `README/CSharp/08 Properties and Indexers/sections/2. Creating properties/2.1. Manual properties with backing fields.md` for the canonical caching patterns in this domain.

**Performance note**
- Hidden allocations in getters (e.g., returning `ToArray()` each call) are a classic GC churn source. If you must allocate, provide an explicit `GetSnapshot()` method instead.

### 3) **“Write-only” APIs**

Write-only properties are covered as a design smell in:
- `README/CSharp/08 Properties and Indexers/sections/3. Read-only and write-only properties/3.2. Write-only properties why usually bad.md`

**Short recap**
- They hide intent (a “set” might actually do heavy work).
- They make debugging and observability hard (you can’t read the state back).
- They encourage “property setter as command”, which is a bad API contract.

**What to do instead**
- Prefer intention-revealing methods: `Configure(...)`, `Enable(...)`, `SetX(...)`, `TrySetX(...)`.
