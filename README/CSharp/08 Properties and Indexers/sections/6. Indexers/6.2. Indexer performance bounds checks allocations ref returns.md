## 6.2. Indexer performance: bounds checks, allocations, and ref returns (advanced)

1. **Avoiding hidden allocations** (boxing, string churn, LINQ, iterator allocations inside indexers)
2. **Exception strategy** (don’t throw for expected misses on hot paths; offer `TryGetValue`-style APIs)
3. **Advanced shapes** (ref returns for high-performance scenarios; keep them low-level and safe)

---

### 1) **Avoiding hidden allocations** (boxing, string churn, LINQ, iterator allocations inside indexers)
Indexers are often called in tight loops. The common trap is “it’s just `this[i]`”, while the getter:

- allocates an iterator (`yield return`)
- allocates due to LINQ (`Where`, `FirstOrDefault`, etc.)
- boxes value types because you route through `object` / non-generic interfaces
- allocates strings for formatting/errors on hot paths

**Mentor rule**
- An indexer should behave like a “cheap lookup/access” *unless the type name makes it obvious otherwise*.
- If access is expensive (I/O, locks, complex computation), use a **method** with an explicit name like `Compute…`, `Load…`, or `Get…Async`.

**Example: keep the indexer allocation-free**

```csharp
using System;

public sealed class IntTable
{
    private readonly int[] _data;

    public IntTable(int size)
    {
        if (size < 0) throw new ArgumentOutOfRangeException(nameof(size));
        _data = new int[size];
    }

    public int Length => _data.Length;

    public int this[int index]
    {
        get
        {
            if ((uint)index >= (uint)_data.Length)
                throw new ArgumentOutOfRangeException(nameof(index));
            return _data[index];
        }
        set
        {
            if ((uint)index >= (uint)_data.Length)
                throw new ArgumentOutOfRangeException(nameof(index));
            _data[index] = value;
        }
    }
}
```

**Performance note**
- The `(uint)index >= (uint)length` idiom is a micro-optimization that also keeps the code tidy (single branch for negative and too-large). Use it mainly in low-level code, not to “look clever” in business code.

If you need a deep reference on allocations (boxing, `params`, spans), see:

### 2) **Exception strategy** (don’t throw for expected misses on hot paths; offer `TryGetValue`-style APIs)
Indexers in .NET have two common “not found” semantics:

- **Throw on invalid key/index** (common for array/list-like indexers)
- **Return a default / null** (rarely safe because it’s ambiguous)

For dictionary-like lookups, the ecosystem norm is:
- `TryGetValue(key, out value)` for expected misses
- `this[key]` that throws (`KeyNotFoundException`) when the key doesn’t exist (fine when “missing is exceptional”)

**Mentor guidance**
- If “not found” is part of normal control flow, **don’t model it as an exception**. Exceptions are expensive under repeated failure and pollute logs/telemetry.
- Prefer a `TryGet` method alongside an indexer when you need both ergonomics and performance.

**Example: pair an indexer with TryGet**

```csharp
using System;
using System.Collections.Generic;

public sealed class UserDirectory
{
    private readonly Dictionary<string, int> _userIdByName = new(StringComparer.Ordinal);

    public int this[string userName] => _userIdByName[userName]; // throws if missing

    public bool TryGetId(string userName, out int id)
        => _userIdByName.TryGetValue(userName, out id);

    public void Add(string userName, int id)
        => _userIdByName.Add(userName, id);
}
```

Good to know:
- Avoid “sentinel” values (`-1`) unless the domain truly guarantees they’re impossible. Prefer `TryGet` or `int?` when appropriate.
- For “optional but required later”, it’s often better to represent the state explicitly rather than “null means missing”.

### 3) **Advanced shapes** (ref returns for high-performance scenarios; keep them low-level and safe)
Sometimes the cost is not the indexer itself, but copying large structs or wanting in-place mutation. C# allows:

- `ref`-returning indexers: `public ref T this[int index] => ref …;`

This is powerful and easy to abuse, because it can:
- expose internal storage (bypassing invariants)
- create aliasing and thread-safety problems

**Canonical deep treatment**
- Ref returns (rules, escape analysis, design guidance) are treated fully in:
  - See `README/CSharp/05 Methods/sections/6. Parameter modifiers and ref-like patterns/6.6. ref returns returning by reference safely.md`.

**Minimal example: ref-returning indexer for a numeric buffer**

```csharp
using System;

public sealed class Buffer
{
    private readonly int[] _data;
    public Buffer(int length) => _data = new int[length];

    public ref int this[int index]
    {
        get
        {
            if ((uint)index >= (uint)_data.Length)
                throw new ArgumentOutOfRangeException(nameof(index));
            return ref _data[index];
        }
    }
}

public static class Demo
{
    public static void Main()
    {
        var b = new Buffer(3);
        b[1] = 10;
        ref int cell = ref b[1];
        cell += 5;
        Console.WriteLine(b[1]); // 15
    }
}
```

**Thread-safety note**
- Ref-returning indexers are usually appropriate only when the buffer is **owned by one thread** or mutation is synchronized. For concurrency patterns, see `README/CSharp/29 Cuncurrent & Parallel/README.md`.
