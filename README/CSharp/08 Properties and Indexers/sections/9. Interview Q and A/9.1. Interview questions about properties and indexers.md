### 1) **Explain properties vs fields** (encapsulation, versioning, invariants, performance reality)
What a strong answer should cover:

- **Definition**:
  - A **field** is a storage slot (representation).
  - A **property** is an API surface (contract) that can be backed by a field today and evolve later.
- **Why mentors prefer properties**:
  - You can add validation, logging, lazy init, caching, change notification later without changing the public shape.
  - Public fields are a brittle commitment (hard to evolve, easy to break invariants).
- **Binary/versioning note**:
  - Changing `public int X;` to `public int X { get; set; }` breaks consumers. Starting with a property avoids that trap.
- **Performance reality**:
  - Trivial properties are typically inlined; performance issues are almost always about *work inside the accessor* (allocations, locks, I/O, \(O(n)\) computation), not “property vs field”.

### 2) **Explain `get`-only vs `private set` vs `init`** (immutability trade-offs; correctness and frameworks)
What a strong answer should cover:

- **`get`-only** (`public T P { get; }`):
  - Strongest “immutable-by-API” signal for consumers.
  - Usually assigned in constructor/initializer/primary constructor.
- **`private set`** (`public T P { get; private set; }`):
  - Publicly read-only, but the type can mutate internally (good for encapsulated state machines).
  - Works well with methods that enforce invariants.
- **`init`** (`public T P { get; init; }`):
  - Assignable only during object creation (object initializer or ctor).
  - Great for DTO/config; for domain invariants, constructors/factories are usually clearer.
- **Frameworks/interop**:
  - Some serializers/ORMs require setters or special support; don’t weaken your domain model for them—use DTOs + mapping where possible.

### 3) **Accessor accessibility** (how to shape an API; `public get; private set;` patterns)
What a strong answer should cover:

- **Goal**: expose what callers need while keeping mutation close to invariant logic.
- **Common shapes**:
  - `public T P { get; private set; }` (external read-only, internal mutation)
  - `public T P { get; internal set; }` (mutable inside the assembly; used in layered apps)
  - `public T P { get; private init; }` (construction-only from outside)
- **Rule**: make illegal states hard to represent. If a caller can set it, they can break invariants.

### 4) **Indexers vs methods** (when an indexer is appropriate; when it hides intent)
What a strong answer should cover:

- **Indexer is a parameterized property**: best when the type behaves like a collection/lookup.
- **Use indexers when**:
  - `obj[key]` communicates “lookup / element access” naturally (e.g., dictionary, matrix, cache).
- **Prefer methods when**:
  - Operation has side effects, can be expensive, or has meaningful failure modes.
  - You want to expose “Try” semantics (`TryGetX`) or error details.
- **Correctness**:
  - Decide if miss is exceptional (`KeyNotFoundException`) vs expected (`TryGetValue`).

### 5) **Performance questions** (computed properties, caching, exceptions vs Try-pattern; allocations in accessors)
What a strong answer should cover:

- **Keep getters cheap**:
  - No I/O, no blocking, no locks unless you have a measured reason.
  - Avoid hidden allocations (`ToArray()`, LINQ, boxing, `string` building) in hot getters.
- **Computed property vs method**:
  - If it’s \(O(1)\) and cheap, property is fine.
  - If it’s \(O(n)\) or expensive, make it a method (`ComputeTotal()`) or cache with explicit invalidation.
- **Exceptions are not control flow**:
  - For expected misses/invalid input, prefer `Try...` patterns.
- **Thread-safety**:
  - Ref returns / exposing internal storage can create races. If concurrency matters, design for it explicitly.
