## 3.1. Read-only properties: `get`-only, `private set`, and “immutability by API”

1. **Get-only vs private-set** (observable immutability vs internal mutation; invariants and testing impact)
2. **`init` vs `set`** (construction-time assignment for DTO/config vs runtime mutation)
3. **Domain guidance** (prefer immutability for value-like state; keep mutation explicit and controlled)

---

### 1) **Get-only vs `private set`** (observable immutability vs internal mutation; invariants and testing impact)

**Definitions**

- A **get-only property** (`public T P { get; }`) is *observably immutable* from the outside. The property can only be assigned:
  - at the declaration (property initializer),
  - in the constructor/primary constructor,
  - or by a backing field you mutate internally (the property still stays get-only).
- A **`private set` property** (`public T P { get; private set; }`) is *mutable by the type*, but read-only for consumers.

These look similar to callers (both are read-only), but they encourage different designs:

- **Get-only** pushes you toward *valid-by-construction* and explicit domain methods for state transitions.
- **Private-set** allows mutation without surfacing it; that can be useful, but it can also hide state changes and make invariants harder to reason about.

**Mentor rule**

- Prefer **get-only** for domain state that should not change arbitrarily.
- Use **`private set`** when the type must mutate a value over time but you still want to prevent external mutation. Pair it with **intention-revealing methods** that are the only mutation entry points.

**Testing impact**

- Get-only tends to be easier to reason about (fewer mutation paths).
- Private-set can be convenient for ORMs/serializers, but it’s also a common path to “property setters as commands” (bad) or “state changes scattered everywhere” (hard to maintain).

**Example (runnable): get-only + methods (domain-friendly)**

```csharp
using System;

public sealed class BankAccount
{
    public Guid Id { get; } = Guid.NewGuid();
    public decimal Balance { get; private set; } // internal mutation is fine, but only via methods

    public BankAccount(decimal openingBalance)
    {
        if (openingBalance < 0) throw new ArgumentOutOfRangeException(nameof(openingBalance));
        Balance = openingBalance;
    }

    public void Deposit(decimal amount)
    {
        if (amount <= 0) throw new ArgumentOutOfRangeException(nameof(amount));
        Balance += amount;
    }

    public bool TryWithdraw(decimal amount)
    {
        if (amount <= 0) return false;
        if (amount > Balance) return false;
        Balance -= amount;
        return true;
    }
}
```

**Good to know**

- For high-integrity domains, you can make even `Balance` **get-only** and mutate a private backing field, but keep the API readable. Choose the simplest shape that preserves invariants.

### 2) **`init` vs `set`** (construction-time assignment for DTO/config vs runtime mutation)

`init` is for **construction-time** assignment; `set` is for **runtime** mutation.

- Prefer `init` when you want a type that is “immutable after creation” from the outside, especially for **DTOs/config**.
- Prefer `set` (usually non-public) when a type is expected to evolve state during its lifetime (domain entities, caches, stateful components).

Important: `init` provides **shallow immutability** only. If the property type is mutable (`List<T>`, `Dictionary<,>`), the object can still be mutated through the reference.

**Single place (deep treatment)**

The full, in-depth explanation of `init`, `required`, object initializers ordering pitfalls, and immutability strategy lives in:

- See [4.2. init required and illegal states unrepresentable](<../../../07 Constructors/sections/4. Object initialization styles/4.2. init required and illegal states unrepresentable.md>)

Here we only apply the rule to “read-only properties” design.

**Example (runnable): `init` for a DTO**

```csharp
public sealed class CreateUserRequest
{
    public required string UserName { get; init; }
    public required string Email { get; init; }
}

var req = new CreateUserRequest { UserName = "ada", Email = "ada@example.com" };
```

### 3) **Domain guidance** (prefer immutability for value-like state; keep mutation explicit and controlled)

**When immutability pays off**

- **Correctness**: fewer invalid intermediate states, fewer race-condition surfaces.
- **Maintainability**: fewer mutation paths to audit.
- **Concurrency**: immutable objects are naturally thread-safe to share.

**When immutability is not free**

- You may need to create new instances for changes (potential allocations/copies).
- For large graphs, “copy-on-change” can be expensive; consider designing smaller immutable value objects and keeping large aggregates mutable behind methods.

**Practical patterns**

- **Value objects**: prefer get-only + constructor/primary constructor validation.
- **Entities**: prefer private-set properties or backing fields + domain methods (explicit state transitions).
- **Collections**: keep mutable collections private; expose read-only views.
  - Deep coverage of “representation leaks” and safe exposure patterns lives elsewhere:
    - See [1.2. Encapsulation with methods invariants boundaries](<../../../05 Methods/sections/1. Method fundamentals/1.2. Encapsulation with methods invariants boundaries.md>)

**Performance note**

- Don’t optimize “get-only vs private set” at the micro-level. The big costs come from:
  - allocations (especially collections and strings),
  - locks/contention,
  - and hidden work in setters/getters.
  Keep property accessors cheap and move meaningful work into methods with explicit names.
