## 4.2. `init` accessors + `required`: initialization contracts and correctness

1. **`required` for completeness** (compile-time enforcement of presence; still validate for untrusted inputs)
2. **DTO vs domain** (use `required`/`init` heavily in DTO/config; keep domain invariants strong)
3. **Interop realities** (serializers/ORMs; when to use constructors/factories vs `init`)

---

### 1) **`required` for completeness** (compile-time enforcement of presence; still validate for untrusted inputs)

This tutorial keeps the **canonical deep treatment** of `init` and `required` in the Constructors domain to avoid duplicating a subtle topic across multiple files.
See:

- `README/CSharp/07 Constructors/sections/4. Object initialization styles/4.2. init required and illegal states unrepresentable.md`

Here, we focus on the **property-level contract** aspect and how it interacts with public API design.

**What `required` actually enforces**

- `required` is a **compile-time** rule: the caller must set the member during object creation (object initializer, constructor, or primary constructor patterns).
- It does **not** replace runtime validation when input is untrusted (deserialization, user input, reflection, tests that use null-forgiving, etc.).

**Mentor rule**

- Use `required` to enforce **presence/completeness**.
- Use validation to enforce **correctness/validity**.

**Common mistake**

- Treating `required` like a runtime guarantee (“it can’t be null at runtime”). It can, depending on construction paths. Always treat boundary inputs as untrusted.

**Performance note**

- `required` itself has no meaningful runtime cost. The cost comes from what you do in validation and in property setters (allocations, exceptions, regex, etc.).

---

### 2) **DTO vs domain** (use `required`/`init` heavily in DTO/config; keep domain invariants strong)

**DTO/config model (good fit)**

- DTOs are typically *validated at the boundary* (model binding / input pipeline) and then mapped to domain types.
- `required` + `init` improves call-site correctness and readability.

**Domain model (be careful)**

- If the type’s invariants are strong (“always valid”), prefer **constructors/factories** as the primary contract.
- If you expose `init`/setters on domain state, you risk:
  - transient invalid states (object initializer assigns one property at a time),
  - multiple creation styles that fragment the codebase,
  - invariants enforced “sometimes” (in some callers, not others).

**Good to know**

- “Immutable by API” is often enough: `public string Name { get; }` with constructor validation is clearer than “immutable-ish with init” for domain objects.
- If you do use `init` in domain code, keep it for *optional* attributes or composition, not for core invariants.

---

### 3) **Interop realities** (serializers/ORMs; when to use constructors/factories vs `init`)

Frameworks can materialize objects in ways that **bypass your intended contract**:

- Some serializers can set private setters/fields (or use reflection).
- ORMs may require parameterless constructors, proxies, or field mapping.
- Some tooling may not respect `required` in all cases (or might treat it as advisory).

**Mentor guidance (avoid making domain weaker for tooling)**

- Prefer **DTOs for wire/storage shapes** and map into domain types with constructors/factories.
- If you must allow framework materialization, keep it narrow and explicit:
  - private/protected parameterless constructor where needed,
  - private setters/backing fields,
  - explicit post-materialization validation in a boundary layer.
