## 1.3. Property invariants: where validation belongs (and what not to do)

1. **Validation strategy** (validate at boundaries; keep objects valid at all times)
2. **Anti-patterns** (throwing from getters for “normal” control flow; expensive work in accessors)
3. **Thread-safety framing** (properties don’t make state thread-safe; synchronization belongs in design)

---

### 1) **Validation strategy** (validate at boundaries; keep objects valid at all times)

**Definition**

An **invariant** is a rule that must always hold for an object to be in a valid state (e.g., “quantity is non-negative”, “start is before end”, “email is normalized”, “balance never goes below zero”).

In C#, **properties are a boundary**, but they are not always the *right* boundary for enforcing invariants. The mentor-grade rule is:

- **Establish invariants at construction** (constructor/factory/primary constructor).
- **Preserve invariants on every state transition** (domain methods, or carefully designed setters).
- **Keep getters predictable**: getters should not “decide validity” at read-time.

If you’re unsure whether a rule belongs in a property setter vs a method, use this heuristic:

- If setting the value is a *meaningful domain operation* (“ApplyDiscount”, “Approve”, “Close”), prefer a **method**.
- If it is genuinely “assigning a value under constraints” (like `Name`, `Age`, `Limit`), a **setter** may be acceptable—*but keep it cheap and deterministic*.

- **Encapsulation and invariants at boundaries** are covered in depth in [1.2. Encapsulation with methods invariants boundaries](<../../../05 Methods/sections/1. Method fundamentals/1.2. Encapsulation with methods invariants boundaries.md>).

This file focuses on what’s *specific* to **properties**: validation placement, accessor behavior, and the classic traps.

#### Pattern A: “valid-state-only” domain objects

For core domain types, prefer **constructor/factory + intention-revealing methods**. Keep property setters private (or remove them).

```csharp
using System;

public sealed class Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency)
    {
        if (amount < 0) throw new ArgumentOutOfRangeException(nameof(amount));
        if (string.IsNullOrWhiteSpace(currency)) throw new ArgumentException("Currency is required.", nameof(currency));

        Amount = amount;
        Currency = currency;
    }
}
```

**Good to know**

- This style avoids “temporal coupling” bugs (e.g., `new Order(); order.Total = ...; order.Currency = ...;`).
- It also plays well with concurrency: immutable objects are easier to publish safely.

#### Pattern B: Setters as constrained assignment (when it’s OK)

If you choose a setter, keep it:

- **fast**
- **pure** (no I/O, no locks, no “hidden workflows”)
- **consistent** (same input always yields the same state or same exception)

```csharp
using System;

public sealed class UserProfile
{
    private string _displayName = "";

    public string DisplayName
    {
        get => _displayName;
        set
        {
            if (string.IsNullOrWhiteSpace(value))
                throw new ArgumentException("Display name is required.", nameof(value));

            _displayName = value.Trim();
        }
    }
}
```

**Performance note**

- Validation in a setter adds branches. That’s fine for most apps. If this is in a true hot path, measure, and consider moving normalization/validation to a boundary method where it runs once.

### 2) **Anti-patterns** (throwing from getters for “normal” control flow; expensive work in accessors)

#### Anti-pattern: “Getter does work / may throw normally”

Getters are often called implicitly by:

- debuggers and watch windows
- loggers / serializers / binders
- LINQ, formatting, interpolation
- UI binding frameworks (frontend)

If your getter can throw under normal circumstances, you create **non-local failures** that are hard to diagnose.

Bad:

```csharp
public decimal Total => _items.Count == 0
    ? throw new InvalidOperationException("No items.")
    : _items.Sum(i => i.Price); // also O(n) on each read
```

Better options:

- If it’s *computed and can fail*: use a **method** (`ComputeTotal()` / `TryComputeTotal(out var total)`).
- If it’s *computed but stable*: cache it with explicit invalidation (covered in [2.1](<../2. Creating properties/2.1. Manual properties with backing fields.md>) backing-field patterns).
- If it’s *a derived view*: keep it cheap (precompute, or use a cached aggregate updated on mutation).

#### Anti-pattern: “Property setter as command”

Bad:

```csharp
// Don’t do work like this in a setter:
// set { _ = _service.SaveAsync(value); }
```

Setters that:

- do I/O
- enqueue background work
- acquire locks with unknown contention
- trigger cross-thread callbacks

…are a maintainability and performance hazard. Prefer explicit methods (`SaveEmailAsync`, `UpdateEmail`) where the cost and failure mode are visible.

**Performance note**

- “Hidden work” inside properties is a frequent cause of thread-pool starvation and latency spikes in server apps: a “cheap-looking” read triggers allocations, locks, or I/O.

### 3) **Thread-safety framing** (properties don’t make state thread-safe; synchronization belongs in design)

**Key truth**

A property is just syntax around methods. It does **not** automatically provide:

- atomicity
- mutual exclusion
- memory visibility guarantees

If the underlying state is shared across threads, you still need a concurrency strategy:

- immutability (best default)
- confinement (single-thread ownership)
- synchronization (`lock`, `ReaderWriterLockSlim`, `Interlocked`, etc.)

**Deep reference (no duplication)**

Threading primitives and the memory model are covered in [29 Cuncurrent & Parallel](<../../../29 Cuncurrent & Parallel/README.md>) (and its sections). For field-level visibility pitfalls, see [04 Fields](<../../../04 Fields/README.md>) static/memory-model sections.

#### Example: “Looks safe, isn’t” (non-atomic compound operations)

```csharp
using System;

public sealed class Counter
{
    public int Value { get; private set; }

    // Not thread-safe: Value++ is a read-modify-write sequence.
    public void Increment() => Value++;
}
```

If you need a thread-safe counter, use `Interlocked` (full treatment in the concurrency domain), or design for immutability/confinement.

**Good to know**

- Declaring a property `get; private set;` does not make it immutable; it only restricts who can mutate.
- Even a simple `get` on a field is not a “thread-safety guarantee” if you have races. Define your thread-safety contract explicitly.
