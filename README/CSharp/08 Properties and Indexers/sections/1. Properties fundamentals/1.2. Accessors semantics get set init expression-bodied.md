## 1.2. Accessors and semantics: `get`, `set`, `init`, and expression-bodied members

1. **Accessor meaning** (`get` reads state, `set` mutates state, `init` is construction-time assignment)
2. **Expression-bodied accessors** (clarity vs debugging; when to avoid “clever” one-liners)
3. **Modern guidance (C# 15 era)** (prefer explicit contracts; avoid magic side effects in getters)

---

### 1) **Accessor meaning** (`get` reads state, `set` mutates state, `init` is construction-time assignment)

At runtime, a property is just **methods**:

- `get_P()` (getter)
- `set_P(value)` (setter), when present

So the real semantics are about **API design** and **invariants**, not “property magic”.

#### **`get`**
- **Purpose**: return the current value / view of state.
- **Mentor rule**: treat getters as **cheap, deterministic, and side-effect-free**.

Common mistakes:
- **Hidden work** in getters (I/O, database calls, locks, complex LINQ).
- **Throwing in getters** for expected states (breaks debugging, binding/serialization, logging).

If computing is non-trivial, prefer an **explicit method** (`ComputeTotal()`), or an explicitly named cached property like `CachedTotal` with clear invalidation rules (see `7.2` later in this domain for pitfalls).

#### **`set`**
- **Purpose**: mutate state.
- **Mentor rule**: a public setter is a **public state transition**. If you can’t describe that transition in plain language, you probably want a method instead.

Use `set` when:
- The property represents **configuration / data shape** (DTOs, settings objects), or
- The mutation is truly “set the value”, not an action with complex side effects.

Avoid `set` when:
- Changing the value requires coordinating other state, events, persistence, or business rules.

Prefer methods for “commands”:
- `Activate()`, `Deactivate()`, `ApplyDiscount(percent)`, `TryWithdraw(amount)`, etc.

#### **`init`**
`init` is a **construction-time assignment** tool: callers can set it in an object initializer, but not after creation.

This file is not the “deep home” for `init` and `required`.
- **See** `README/CSharp/07 Constructors/sections/4. Object initialization styles/4.2. init required and illegal states unrepresentable.md` for the full treatment (semantics, versioning, deserialization bypass, deep immutability).

Quick guidance:
- Use `init` + `required` primarily for **DTO/config** shapes.
- For **domain invariants**, prefer constructors/factories so the object is valid immediately.

#### Runnable example: `get`-only + method for mutation (domain-friendly)

```csharp
using System;

public sealed class Counter
{
    private int _value;

    public int Value => _value; // cheap getter

    public void Increment() => _value++; // explicit mutation
}

public static class Program
{
    public static void Main()
    {
        var c = new Counter();
        c.Increment();
        Console.WriteLine(c.Value);
    }
}
```

Good to know:
- This is also a common pattern for keeping **mutation searchable** (“where can `_value` change?”).

### 2) **Expression-bodied accessors** (clarity vs debugging; when to avoid “clever” one-liners)

Expression-bodied members are mostly a **style tool**:

```csharp
public int Count => _count;
public string Name { get => _name; private set => _name = value; }
```

When they help:
- The getter/setter is truly trivial.
- You want to reduce noise and keep the API readable.

When to avoid:
- The accessor needs **multiple statements** (validation, guards, normalization).
- You’re tempted to cram logic into a single expression that becomes hard to step through and maintain.

Mentor rule:
- Prefer **readability at the call site and maintainability at the definition site** over “one-line elegance”.

Performance note:
- Expression-bodied syntax does **not** make code faster. The JIT optimizes based on IL, not on your formatting choice.

### 3) **Modern guidance (C# 15 era)** (prefer explicit contracts; avoid magic side effects in getters)

#### **Pick an API shape intentionally**
Common “good” shapes:

- **Immutable to consumers**:
  - `public T Value { get; }` (set in constructor)
  - `public required T Value { get; init; }` (DTO/config; see Constructors 4.2 for full guidance)
- **Mutable but controlled**:
  - `public T Value { get; private set; }` plus methods that update it under invariants
  - `public T Value { get; internal set; }` inside a single assembly boundary

Avoid:
- `public T Value { get; set; }` on domain objects “because it’s easy”. It usually leaks invariants.

#### **Keep getters predictable**
If a property can be “missing”, prefer:
- `T?` (nullable) or an **explicit** `TryGetX(out T value)` pattern, rather than throwing from the getter.

#### **Thread-safety is not “automatic”**
Properties don’t create a threading policy. If multiple threads mutate/read shared state, you need a design:
- confinement (single thread owns mutation),
- immutability,
- or synchronization.

This file intentionally does not duplicate the deep threading discussion:
- **See** `README/CSharp/29 Cuncurrent & Parallel/README.md` for synchronization primitives and correctness patterns.

Good to know:
- “Auto-properties are atomic” is a myth. Even if a single read/write is atomic for some types, **visibility and ordering** across threads still requires proper synchronization.
