### 1. **Data races vs higher-level race conditions**

**Short definitions**

- **Data race** (memory-level):
  - Two or more threads **access the same memory location** concurrently.
  - At least one access is a **write**.
  - The accesses are **not ordered** by any happens-before relation (no `lock`, `Interlocked`, proper volatile usage, etc.).
  - Result: **undefined behavior** under the .NET memory model (see 4.2).

- **Race condition** (logical/semantic):
  - Program correctness depends on the **relative timing or ordering** of events/operations.
  - Different interleavings can produce different logical outcomes.
  - Includes data races, but also order-dependent bugs even when each access is individually "atomic".

**Why the distinction matters**

- Fixing **data races** is usually a matter of adding appropriate **synchronization**.
- Fixing **race conditions** often requires **re-designing invariants and protocols**, not just sprinkling `lock`.

**Example: data race vs race condition**

```csharp
using System;
using System.Collections.Generic;
using System.Threading;
using System.Threading.Tasks;

public sealed class CartWithDataRace
{
    // This list is not thread-safe.
    private readonly List<string> _items = new();

    public void Add(string item) => _items.Add(item); // Data race if called concurrently.

    public int Count => _items.Count;
}

public sealed class CartWithLock
{
    private readonly List<string> _items = new();
    private readonly object _lock = new();

    public void Add(string item)
    {
        lock (_lock)
        {
            _items.Add(item);
        }
    }

    public int Count
    {
        get
        {
            lock (_lock)
            {
                return _items.Count;
            }
        }
    }
}
```

- `CartWithDataRace` has a **data race**: concurrent `Add` calls can corrupt the list or throw exceptions.
- `CartWithLock` fixes the data race, but you might still have **higher-level race conditions**:
  - e.g., a thread checks `Count` then uses that information assuming no one else has changed the cart.

**Higher-level race example (check-then-act)**

```csharp
public sealed class CartWithRace
{
    private readonly List<string> _items = new();
    private readonly object _lock = new();

    public bool AddIfNotExists(string item)
    {
        lock (_lock)
        {
            if (_items.Contains(item)) // check
            {
                return false;
            }

            _items.Add(item);         // act
            return true;
        }
    }
}
```

- Inside a single `lock`, `AddIfNotExists` is **internally race-free** for `_items`.
- But if **other code** accesses `_items` directly or via other methods not using this lock, correctness can still depend on interleavings.

**Mentor emphasis**

- Treat **data races as bugs**: you don't "tolerate" them.
- Race conditions require reasoning in terms of **contracts and invariants**, not just primitives.

### 2. **Shared mutable state vs ownership and confinement**

**Two models**

- **Shared mutable state**:
  - Multiple threads access and mutate the same data structure.
  - You use synchronization (locks, `Interlocked`, `ReaderWriterLockSlim`, etc.) to make accesses safe.
- **Ownership / confinement**:
  - Each piece of mutable state has **exactly one owner** (thread, actor, or component).
  - Other code interacts by sending **messages/commands** rather than directly mutating state.
  - See **3.7** for actor-style patterns.

**When shared mutable state is OK**

- State is:
  - **small** and **local** to a subsystem.
  - accessed infrequently or with low contention.
  - protected by **simple locking** with clear ownership.
- Example: a cache dictionary protected by a single lock inside a single class.

**When to prefer confinement**

- You see:
  - complex locking patterns (multiple locks, nested locks, lock ordering rules).
  - repeated subtle bugs when new codepath touches shared state.
  - contention and performance issues around shared hot structures.
- Actor-style design (3.7) or per-resource ownership via Channels/Dataflow (3.3) often yields **simpler, safer code**.

**Example: shared-state counter vs confined actor counter**

```csharp
using System.Threading;

public sealed class SharedCounter
{
    private int _value;

    public void Increment() => Interlocked.Increment(ref _value);
    public int Value => _value;
}
```

- `SharedCounter` is safe and cheap; **Interlocked** is appropriate for simple shared counters.

```csharp
using System.Threading;
using System.Threading.Channels;
using System.Threading.Tasks;

public sealed class CounterActor
{
    private readonly Channel<int> _mailbox =
        Channel.CreateUnbounded<int>(new UnboundedChannelOptions { SingleReader = true });

    private int _value;
    private readonly Task _runner;

    public CounterActor()
    {
        _runner = Task.Run(async () =>
        {
            await foreach (var delta in _mailbox.Reader.ReadAllAsync().ConfigureAwait(false))
            {
                _value += delta; // confined state
            }
        });
    }

    public ValueTask IncrementAsync(int delta) => _mailbox.Writer.WriteAsync(delta);
    public int UnsafeSnapshotValue => _value; // read-only for illustration.
}
```

- For a simple counter, this actor is **overkill**.
- For complex mutable state (e.g., an order book, workflow engine, financial ledger), confinement wins.

**Good to know**

- Start with simple shared-state + locks for small, well-defined components.
- Move to confinement when:
  - locks become complicated, or
  - contention and correctness are real issues.

### 3. **Invariants, pre/post-conditions, and representation consistency**

**Invariants**

- A condition that should **always be true** for a given object except:
  - briefly inside a method body, and
  - during construction/destruction.
- Examples:
  - `Balance >= 0`
  - `Count == Items.Count`
  - `Start <= End`

**Pre-conditions**

- What must be true **before** a method is called for it to be valid.
  - e.g., `amount > 0`, `buffer != null`.

**Post-conditions**

- What a method guarantees will be true **after** it returns successfully.
  - e.g., `Balance == oldBalance + amount` for a deposit.

**Concurrent twist**

- Under concurrency:
  - Invariants must hold **even under interleavings** of operations.
  - Methods must either:
    - restore invariants before releasing locks / finishing a message, or
    - expose only **transactional views** that hide intermediate states.

**Example: bank account invariants**

```csharp
public sealed class Account
{
    private readonly object _lock = new();
    private decimal _balance;

    // Invariant: _balance >= 0
    public void Deposit(decimal amount)
    {
        if (amount < 0) throw new ArgumentOutOfRangeException(nameof(amount));
        lock (_lock)
        {
            _balance += amount;
        }
    }

    public bool TryWithdraw(decimal amount)
    {
        if (amount < 0) throw new ArgumentOutOfRangeException(nameof(amount));
        lock (_lock)
        {
            if (_balance < amount) return false;
            _balance -= amount; // invariant still: _balance >= 0
            return true;
        }
    }

    public decimal Balance
    {
        get { lock (_lock) return _balance; }
    }
}
```

- Inside the lock, the object may pass through intermediate values, but **before the lock is released**, the invariant must hold.

**Common mistake**

- Doing **multi-object** transactions with partial invariants:

```csharp
public static void Transfer(Account from, Account to, decimal amount)
{
    // BAD: no coordination -> race conditions across accounts.
    if (from.TryWithdraw(amount))
    {
        to.Deposit(amount);
    }
}
```

- For correctness across multiple accounts, you need a stronger invariant and coordinating mechanism (e.g., global lock ordering, actor per-account plus transactional messages, or a transactional store).

**Mentor emphasis**

- Write invariants down explicitly in code comments / docs.
- Ensure each public method either:
  - preserves them on its own, or
  - is clearly part of a **larger transaction** with appropriate locking/coordination.

### 4. **Ordering guarantees (happens-before, visibility, publication)**

> For a deeper dive into the memory model and reordering, see **4.2**. This section focuses on **how to think** about ordering when designing code.

**Happens-before**

- An operation A **happens-before** operation B if the program or synchronization rules guarantee that:
  - all effects of A are visible to B
  - A completes before B starts (logically).
- In .NET, happens-before edges are created by:
  - `lock`/`Monitor` (enter/exit)
  - `Interlocked` operations
  - properly used `volatile` fields
  - task completion & `await` (see 2.5, 4.2).

**Publication**

- The act of safely making an object visible to other threads:
  - Create it, fully initialize it, then publish a **reference** via a happens-before edge.
- Example: assigning to a `volatile` field, or assigning inside a locked region before another thread reads under the same lock.

**Example: safe vs unsafe publication**

```csharp
public sealed class Config
{
    public string ConnectionString { get; init; } = "";
}

// Unsafe: no barriers, data race if read concurrently with write.
public static class GlobalsUnsafe
{
    public static Config? Current;

    public static void Init()
    {
        Current = new Config { ConnectionString = "..." };
    }
}

// Safer: guarded by a lock.
public static class GlobalsWithLock
{
    private static readonly object _lock = new();
    private static Config? _current;

    public static void Init()
    {
        var config = new Config { ConnectionString = "..." };
        lock (_lock)
        {
            _current = config; // publish under lock
        }
    }

    public static Config? Get()
    {
        lock (_lock) return _current;
    }
}
```

**Async happens-before**

- In modern .NET, there is also a happens-before from:
  - setting a `TaskCompletionSource` result
  - **completing a `Task`**
  - to code that **awaits** that task.
- Intuitively: *"All writes before you call `SetResult` will be visible to the code after `await`."*

**Mentor emphasis**

- Don't rely on "it seems ordered in the source code."
- Use **logical happens-before** via:
  - locks / Interlocked
  - proper task/await boundaries
  - channel/queue operations.

### 5. **Idempotency, commutativity, and associativity in concurrent operations**

**Definitions**

- **Idempotent** operation:
  - Can be applied **multiple times** with the same effect as once.
  - Example: "set `Status = Closed`" is idempotent; "increment counter" is not.

- **Commutative** operations:
  - Order doesn't matter: `op(a, b) == op(b, a)`.
  - Example: integer addition is commutative; string concatenation is not.

- **Associative** operations:
  - Grouping doesn't matter: `op(op(a, b), c) == op(a, op(b, c))`.
  - Example: integer addition is associative; floating-point addition is not *strictly* (due to rounding), but often "good enough" for many domains if you accept small numeric differences.

**Why they matter in concurrency**

- **Idempotency**:
  - Makes retries and duplicate messages safe.
  - Crucial for at-least-once delivery, crash recovery, and idempotent APIs.

- **Commutativity & associativity**:
  - Make parallel aggregation easier:
    - you can partition data, aggregate locally, then combine results in any order.
  - Underpin many data-parallel strategies (PLINQ, Parallel.Aggregate, Map-Reduce).

**Example: concurrent logging and metrics**

```csharp
public sealed class Metrics
{
    // Commutative and associative: we can sum counts in any order.
    private long _requests;
    private long _errors;

    public void RecordRequest() => Interlocked.Increment(ref _requests);
    public void RecordError() => Interlocked.Increment(ref _errors);

    public (long Requests, long Errors) Snapshot()
        => (Interlocked.Read(ref _requests), Interlocked.Read(ref _errors));
}
```

- Because **increment** on a long is:
  - (effectively) commutative and associative at the logical level,
  - we can freely aggregate from multiple threads.

**Example: idempotent vs non-idempotent operations**

```csharp
public sealed class Order
{
    private readonly object _lock = new();
    private bool _isPaid;

    // Idempotent: calling multiple times has the same effect as once.
    public void MarkPaid()
    {
        lock (_lock)
        {
            _isPaid = true;
        }
    }

    // Non-idempotent: total will grow if applied twice.
    public void ApplyDiscount(decimal amount)
    {
        lock (_lock)
        {
            // ... adjust Price -= amount ...
        }
    }
}
```

- In a distributed or concurrent context, "MarkPaid" is safer to retry than "ApplyDiscount".

**Mentor emphasis**

- Whenever you design an operation that might be:
  - retried,
  - run in parallel,
  - or applied based on messages,
  ask:
  - Can it be **idempotent**?
  - Is it **commutative/associative** enough to parallelize safely?
- Building these properties into your API surface pays off massively in concurrent correctness and simplicity.
