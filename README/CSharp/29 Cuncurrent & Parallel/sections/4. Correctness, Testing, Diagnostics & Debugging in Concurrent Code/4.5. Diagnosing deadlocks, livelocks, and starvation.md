### 1. **Common deadlock patterns (lock ordering, sync-over-async, UI thread blocking)**

**Deadlock from lock ordering**

- **Classic deadlock**: Two threads acquire locks in different orders.

```csharp
public class DeadlockExample
{
    private readonly object _lock1 = new();
    private readonly object _lock2 = new();

    public void Method1()
    {
        lock (_lock1) // Thread 1 acquires lock1
        {
            Thread.Sleep(10); // Simulate work
            lock (_lock2) // Thread 1 tries to acquire lock2
            {
                // Critical section
            }
        }
    }

    public void Method2()
    {
        lock (_lock2) // Thread 2 acquires lock2
        {
            Thread.Sleep(10); // Simulate work
            lock (_lock1) // Thread 2 tries to acquire lock1 -> DEADLOCK!
            {
                // Critical section
            }
        }
    }
}
```

**Diagnosing lock ordering deadlocks**

- **Symptoms**: Application hangs, no CPU usage, threads blocked in `Monitor.Enter`.
- **Detection**: Use dump analysis (see 4.6) to see threads waiting on locks.
- **Prevention**: Always acquire locks in the **same order** across all methods.

**Fixed: consistent lock ordering**

```csharp
public class FixedDeadlockExample
{
    private readonly object _lock1 = new();
    private readonly object _lock2 = new();

    public void Method1()
    {
        lock (_lock1) // Always acquire lock1 first
        {
            lock (_lock2) // Then lock2
            {
                // Critical section
            }
        }
    }

    public void Method2()
    {
        lock (_lock1) // Same order: lock1 first
        {
            lock (_lock2) // Then lock2
            {
                // Critical section
            }
        }
    }
}
```

**Sync-over-async deadlock**

- **Classic pattern**: Blocking on async code from a synchronization context (e.g., UI thread).

```csharp
public class SyncOverAsyncDeadlock
{
    // BAD: Called from UI thread
    public string GetData()
    {
        // Deadlock: UI thread blocks waiting for async operation
        // Async operation tries to return to UI thread (ConfigureAwait(true) by default)
        return GetDataAsync().Result; // DEADLOCK!
    }

    public async Task<string> GetDataAsync()
    {
        await Task.Delay(1000); // Tries to return to UI thread
        return "Data";
    }
}
```

**Diagnosing sync-over-async deadlocks**

- **Symptoms**: UI freezes, application becomes unresponsive.
- **Detection**: Thread dump shows UI thread blocked on `Task.Result` or `.Wait()`.
- **Prevention**: Never use `.Result` or `.Wait()` on async methods. Use `await` instead.

**Fixed: proper async/await**

```csharp
public class FixedSyncOverAsync
{
    // GOOD: Async all the way
    public async Task<string> GetDataAsync()
    {
        return await GetDataInternalAsync();
    }

    private async Task<string> GetDataInternalAsync()
    {
        await Task.Delay(1000).ConfigureAwait(false); // Don't capture context
        return "Data";
    }
}

// If you MUST block (rare), use ConfigureAwait(false) in library code
public class LibraryCode
{
    public async Task<string> GetDataAsync()
    {
        await SomeOperationAsync().ConfigureAwait(false); // Library code shouldn't capture context
        return "Data";
    }
}
```

**UI thread blocking**

- **Pattern**: UI thread blocks waiting for a lock held by a background thread that's waiting for the UI thread.

```csharp
public class UIThreadDeadlock
{
    private readonly object _lock = new();
    private string _data = "";

    // Called from UI thread
    public void UpdateUI()
    {
        lock (_lock) // UI thread acquires lock
        {
            // UI thread needs to update UI, but background thread holds lock
            _data = "Updated";
        }
    }

    // Called from background thread
    public async Task BackgroundWorkAsync()
    {
        lock (_lock) // Background thread acquires lock
        {
            // Background thread needs to post to UI thread
            await Dispatcher.InvokeAsync(() => UpdateUI()); // DEADLOCK!
            // UI thread is waiting for lock, background thread is waiting for UI thread
        }
    }
}
```

**Fixed: avoid locking around UI operations**

```csharp
public class FixedUIThreadDeadlock
{
    private string _data = "";

    // GOOD: Don't lock around UI operations
    public void UpdateUI()
    {
        _data = "Updated"; // Simple assignment, no lock needed if only UI thread writes
    }

    public async Task BackgroundWorkAsync()
    {
        // Do work without holding lock
        var result = await DoWorkAsync();
        
        // Post to UI thread without holding lock
        await Dispatcher.InvokeAsync(() =>
        {
            _data = result; // Update UI
        });
    }
}
```

**Mentor emphasis**

- **Lock ordering**: Always acquire locks in the same order.
- **Sync-over-async**: Never use `.Result` or `.Wait()` on async code.
- **UI thread**: Don't hold locks while posting to UI thread.
- **Use `ConfigureAwait(false)`** in library code to avoid context capture issues.

### 2. **Detecting lock contention and hot locks**

**What is lock contention?**

- **Lock contention** occurs when multiple threads compete for the same lock.
- High contention causes threads to **wait** instead of doing useful work.
- This degrades performance even if no deadlock occurs.

**Symptoms of lock contention**

- **High CPU wait time**: Threads spend time waiting instead of running.
- **Low throughput**: More threads don't improve performance (may make it worse).
- **Thread pool starvation**: Threads blocked on locks can't process other work.

**Detecting contention with counters**

```csharp
using System.Diagnostics;

public class ContentionMonitor
{
    private readonly object _lock = new();
    private long _contentionCount = 0;
    private long _totalWaits = 0;
    private readonly Stopwatch _waitTime = Stopwatch.StartNew();

    public void EnterLock()
    {
        var sw = Stopwatch.StartNew();
        bool acquired = false;
        
        try
        {
            Monitor.TryEnter(_lock, 0, ref acquired);
            if (!acquired)
            {
                Interlocked.Increment(ref _contentionCount);
                Monitor.Enter(_lock); // Block until acquired
            }
        }
        finally
        {
            sw.Stop();
            Interlocked.Add(ref _totalWaits, sw.ElapsedMilliseconds);
        }
    }

    public (long ContentionCount, long TotalWaitMs) GetStats()
    {
        return (Interlocked.Read(ref _contentionCount), Interlocked.Read(ref _totalWaits));
    }
}
```

**Profiling lock contention**

- Use **PerfView** or **Visual Studio Profiler** to see:
  - **Lock contention events**: How often threads wait on locks.
  - **Wait time**: How long threads spend waiting.
  - **Hot locks**: Which locks have the most contention.

**Example: hot lock detection**

```csharp
public class HotLockExample
{
    private readonly Dictionary<string, int> _cache = new();
    private readonly object _lock = new(); // Single lock for entire cache

    // BAD: All operations contend for same lock
    public int GetValue(string key)
    {
        lock (_lock) // Contention hotspot
        {
            return _cache.TryGetValue(key, out var value) ? value : 0;
        }
    }

    public void SetValue(string key, int value)
    {
        lock (_lock) // Contention hotspot
        {
            _cache[key] = value;
        }
    }
}
```

**Reducing contention: fine-grained locking**

```csharp
public class FineGrainedLocking
{
    private readonly Dictionary<string, int> _cache = new();
    private readonly object[] _locks = new object[16]; // Multiple locks

    public FineGrainedLocking()
    {
        for (int i = 0; i < _locks.Length; i++)
        {
            _locks[i] = new object();
        }
    }

    private object GetLock(string key)
    {
        int hash = key.GetHashCode();
        return _locks[Math.Abs(hash % _locks.Length)]; // Hash to specific lock
    }

    public int GetValue(string key)
    {
        lock (GetLock(key)) // Only locks one bucket
        {
            return _cache.TryGetValue(key, out var value) ? value : 0;
        }
    }

    public void SetValue(string key, int value)
    {
        lock (GetLock(key)) // Only locks one bucket
        {
            _cache[key] = value;
        }
    }
}
```

**Reducing contention: lock-free structures**

```csharp
using System.Collections.Concurrent;

public class LockFreeExample
{
    // GOOD: ConcurrentDictionary uses lock-free algorithms internally
    private readonly ConcurrentDictionary<string, int> _cache = new();

    public int GetValue(string key)
    {
        return _cache.GetOrAdd(key, _ => 0); // No explicit locking
    }

    public void SetValue(string key, int value)
    {
        _cache[key] = value; // No explicit locking
    }
}
```

**Measuring contention in production**

```csharp
public class ContentionMetrics
{
    private static readonly Counter _lockContentionCounter = 
        Metrics.CreateCounter("lock_contention_total", "Number of lock contentions");
    
    private static readonly Histogram _lockWaitTime = 
        Metrics.CreateHistogram("lock_wait_seconds", "Time spent waiting for locks");

    public void EnterWithMetrics(object lockObj)
    {
        var sw = Stopwatch.StartNew();
        bool acquired = false;
        
        Monitor.TryEnter(lockObj, 0, ref acquired);
        if (!acquired)
        {
            _lockContentionCounter.Inc();
            Monitor.Enter(lockObj);
        }
        
        sw.Stop();
        _lockWaitTime.Observe(sw.Elapsed.TotalSeconds);
    }
}
```

**Mentor emphasis**

- **Monitor contention** in production with metrics.
- **Use fine-grained locking** or **lock-free structures** to reduce contention.
- **Profile** to identify hot locks.
- **Consider actor patterns** (see 5.7) to eliminate shared locks entirely.

### 3. **Recognizing livelock and priority inversion**

**What is livelock?**

- **Livelock**: Threads are running but making no progress because they keep interfering with each other.
- Unlike deadlock, threads are **not blocked**—they're actively running but stuck in a loop.

**Example: livelock**

```csharp
public class LivelockExample
{
    private bool _resource1Busy = false;
    private bool _resource2Busy = false;

    public void Thread1()
    {
        while (true)
        {
            if (!_resource1Busy)
            {
                _resource1Busy = true;
                if (!_resource2Busy)
                {
                    _resource2Busy = true;
                    // Do work...
                    _resource2Busy = false;
                    _resource1Busy = false;
                    return; // Success
                }
                else
                {
                    _resource1Busy = false; // Release and retry
                    Thread.Yield();
                }
            }
            else
            {
                Thread.Yield(); // Wait and retry
            }
        }
    }

    public void Thread2()
    {
        // Same pattern but acquires resources in opposite order
        // Can cause livelock if both threads keep retrying
    }
}
```

**Diagnosing livelock**

- **Symptoms**: High CPU usage, threads running but no progress, application appears hung.
- **Detection**: Thread dump shows threads in loops, no blocked threads.
- **Prevention**: Use proper synchronization (locks) instead of busy-waiting.

**Fixed: use proper locks**

```csharp
public class FixedLivelock
{
    private readonly object _lock1 = new();
    private readonly object _lock2 = new();

    public void Thread1()
    {
        lock (_lock1) // Proper synchronization
        {
            lock (_lock2)
            {
                // Do work...
            }
        }
    }
}
```

**Priority inversion**

- **Priority inversion**: A low-priority thread holds a lock needed by a high-priority thread, blocking the high-priority thread.
- The high-priority thread waits for the low-priority thread, effectively reducing its priority.

**Example: priority inversion**

```csharp
public class PriorityInversionExample
{
    private readonly object _lock = new();

    // Low-priority thread
    public void LowPriorityThread()
    {
        Thread.CurrentThread.Priority = ThreadPriority.Lowest;
        lock (_lock) // Holds lock
        {
            Thread.Sleep(10000); // Long operation
        }
    }

    // High-priority thread
    public void HighPriorityThread()
    {
        Thread.CurrentThread.Priority = ThreadPriority.Highest;
        lock (_lock) // Waits for low-priority thread
        {
            // Critical operation
        }
    }
}
```

**Diagnosing priority inversion**

- **Symptoms**: High-priority threads blocked by low-priority threads.
- **Detection**: Thread dump shows high-priority threads waiting on locks held by low-priority threads.
- **Prevention**: Avoid thread priorities, or use priority inheritance (not available in .NET).

**Mentor emphasis**

- **Livelock**: Use proper synchronization instead of busy-waiting.
- **Priority inversion**: Avoid thread priorities in managed code.
- **Monitor CPU usage**: High CPU with no progress suggests livelock.
- **Use locks**: Proper synchronization prevents both livelock and priority inversion.

### 4. **ThreadPool starvation: symptoms and root causes**

**What is ThreadPool starvation?**

- **ThreadPool starvation**: All ThreadPool threads are blocked, so new work items can't be processed.
- This causes the application to become unresponsive even though threads exist.

**Symptoms**

- **Requests timing out**: New requests can't be processed.
- **High thread count**: ThreadPool creates more threads (up to limit).
- **Low CPU usage**: Threads are blocked, not running.
- **Application appears hung**: No progress on new work.

**Example: ThreadPool starvation**

```csharp
public class ThreadPoolStarvationExample
{
    public async Task ProcessRequestAsync()
    {
        // BAD: Blocks ThreadPool thread
        Thread.Sleep(5000); // Blocks thread for 5 seconds
        // ThreadPool thread is unavailable for other work
    }

    public async Task ProcessRequestAsync2()
    {
        // BAD: Blocks on async operation
        var result = GetDataAsync().Result; // Blocks ThreadPool thread
        // If GetDataAsync() needs ThreadPool thread, deadlock/starvation
    }
}
```

**Diagnosing ThreadPool starvation**

- **Check thread count**: `ThreadPool.ThreadCount` shows high values.
- **Check available threads**: `ThreadPool.GetAvailableThreads()` shows low available threads.
- **Thread dump**: All ThreadPool threads blocked on locks or synchronous I/O.

**Monitoring ThreadPool health**

```csharp
public class ThreadPoolMonitor
{
    public static void LogThreadPoolStats()
    {
        ThreadPool.GetAvailableThreads(out int workerThreads, out int completionPortThreads);
        ThreadPool.GetMaxThreads(out int maxWorkerThreads, out int maxCompletionPortThreads);
        ThreadPool.GetMinThreads(out int minWorkerThreads, out int minCompletionPortThreads);

        Console.WriteLine($"Worker threads: {workerThreads}/{maxWorkerThreads} (min: {minWorkerThreads})");
        Console.WriteLine($"Completion port threads: {completionPortThreads}/{maxCompletionPortThreads} (min: {minCompletionPortThreads})");
        
        if (workerThreads < maxWorkerThreads * 0.1) // Less than 10% available
        {
            Console.WriteLine("WARNING: ThreadPool starvation detected!");
        }
    }
}
```

**Common causes**

1. **Blocking on async code**: `.Result` or `.Wait()` on async methods.
2. **Synchronous I/O**: File I/O, database calls without async.
3. **Long-running CPU work**: CPU-bound work on ThreadPool threads.
4. **Deadlocks**: Threads blocked waiting for locks.

**Fixed: proper async/await**

```csharp
public class FixedThreadPoolStarvation
{
    // GOOD: Use async/await, don't block
    public async Task ProcessRequestAsync()
    {
        await Task.Delay(5000); // Non-blocking delay
        // ThreadPool thread is released, can process other work
    }

    public async Task ProcessRequestAsync2()
    {
        var result = await GetDataAsync(); // Proper async/await
        // No blocking, ThreadPool thread released
    }
}
```

**Fixed: use dedicated threads for CPU work**

```csharp
public class FixedCPUWork
{
    // GOOD: CPU-bound work on dedicated thread, not ThreadPool
    public Task<int> ProcessCPUWorkAsync(int[] data)
    {
        return Task.Run(() => // Explicitly use ThreadPool for CPU work
        {
            // CPU-bound processing
            return data.Sum();
        });
    }

    // Or use TaskScheduler for long-running work
    public Task<int> ProcessLongRunningWorkAsync(int[] data)
    {
        var scheduler = TaskScheduler.Default;
        return Task.Factory.StartNew(() =>
        {
            // Long-running work
            return data.Sum();
        }, CancellationToken.None, TaskCreationOptions.LongRunning, scheduler);
    }
}
```

**Mentor emphasis**

- **Never block ThreadPool threads**: Use `await`, not `.Result` or `.Wait()`.
- **Use async I/O**: Prefer async file/database APIs.
- **Monitor ThreadPool**: Track available threads in production.
- **Use dedicated threads**: For long-running CPU work, use `TaskCreationOptions.LongRunning`.

### 5. **Diagnosing deadlocks in UI apps vs server apps**

**UI app deadlocks**

- **Common pattern**: UI thread blocks waiting for async operation that needs UI thread.

```csharp
// UI app (WPF/WinForms)
public partial class MainWindow : Window
{
    private async void Button_Click(object sender, RoutedEventArgs e)
    {
        // BAD: Blocks UI thread
        var data = GetDataAsync().Result; // DEADLOCK!
        TextBox.Text = data;
    }

    private async Task<string> GetDataAsync()
    {
        await Task.Delay(1000); // Tries to return to UI thread
        return "Data";
    }
}
```

**Diagnosing UI deadlocks**

- **Symptoms**: UI freezes, application unresponsive.
- **Detection**: UI thread blocked on `.Result` or `.Wait()`.
- **Thread dump**: UI thread shows `WaitOne` or `Monitor.Enter` waiting.

**Fixed: async/await in UI**

```csharp
public partial class MainWindow : Window
{
    // GOOD: Async event handler
    private async void Button_Click(object sender, RoutedEventArgs e)
    {
        var data = await GetDataAsync(); // Proper async/await
        TextBox.Text = data;
    }

    private async Task<string> GetDataAsync()
    {
        await Task.Delay(1000).ConfigureAwait(true); // Return to UI thread
        return "Data";
    }
}
```

**Server app deadlocks**

- **Common pattern**: ThreadPool thread blocks waiting for async operation that needs ThreadPool thread.

```csharp
// Server app (ASP.NET)
public class ApiController : ControllerBase
{
    [HttpGet]
    public string GetData()
    {
        // BAD: Blocks ThreadPool thread
        return GetDataAsync().Result; // DEADLOCK/STARVATION!
    }

    public async Task<string> GetDataAsync()
    {
        await Task.Delay(1000); // Needs ThreadPool thread to continue
        return "Data";
    }
}
```

**Diagnosing server deadlocks**

- **Symptoms**: Requests timeout, ThreadPool starvation.
- **Detection**: ThreadPool threads blocked on `.Result` or `.Wait()`.
- **Thread dump**: Multiple ThreadPool threads waiting.

**Fixed: async controllers**

```csharp
public class ApiController : ControllerBase
{
    // GOOD: Async controller method
    [HttpGet]
    public async Task<string> GetDataAsync()
    {
        return await GetDataInternalAsync(); // Proper async/await
    }

    private async Task<string> GetDataInternalAsync()
    {
        await Task.Delay(1000).ConfigureAwait(false); // Don't capture context
        return "Data";
    }
}
```

**Key differences**

- **UI apps**: Deadlock affects single UI thread, application freezes.
- **Server apps**: Deadlock affects ThreadPool, multiple requests fail.
- **Both**: Caused by blocking on async code (`.Result`, `.Wait()`).

**Debugging tips**

- **UI apps**: Use Visual Studio's "Freeze Thread" feature to see what UI thread is waiting for.
- **Server apps**: Use thread dumps and PerfView to see ThreadPool thread states.
- **Both**: Look for `.Result`, `.Wait()`, `.GetAwaiter().GetResult()` in stack traces.

**Mentor emphasis**

- **UI apps**: Use `async void` event handlers with `await`.
- **Server apps**: Use async controller methods with `await`.
- **Both**: Never use `.Result` or `.Wait()` on async methods.
- **Library code**: Use `ConfigureAwait(false)` to avoid context capture.

---

**Summary**

- **Deadlocks**: Caused by lock ordering, sync-over-async, or UI thread blocking.
- **Lock contention**: Detected by profiling, reduced by fine-grained locking or lock-free structures.
- **Livelock**: Threads running but making no progress; use proper synchronization.
- **ThreadPool starvation**: All threads blocked; avoid blocking on async code.
- **UI vs server**: Different symptoms but same root cause (blocking on async code).
