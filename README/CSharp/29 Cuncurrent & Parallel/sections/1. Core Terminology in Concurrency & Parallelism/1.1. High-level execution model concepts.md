## 1.1. High-level execution model concepts

This section defines the **core execution-model concepts** you will see everywhere in the rest of the tutorial. Other sections will assume you understand these ideas and will only reference them briefly (for example: *“See 1.1 for the full treatment of blocking vs non-blocking”*).

1. **Concurrency vs Parallelism**
2. **Asynchrony vs Multi-threading**
3. **Synchronous vs Asynchronous**
4. **Blocking vs Non-Blocking**
5. **CPU-Bound vs IO-Bound**

---

1. **Concurrency vs Parallelism**

**Short definition**

- **Concurrency**: Structuring a program so that **multiple tasks are in progress** (logically overlapped), even if they are not literally running at the same instant on the CPU. It is about **dealing with many things at once**.
- **Parallelism**: Executing **multiple operations at the same physical time**, on **multiple cores**. It is about **doing many things at once**.

In C#, concurrency usually shows up as **async/await**, `Task`, `IAsyncEnumerable<T>`, and message-passing pipelines. Parallelism usually shows up as **`Parallel.For`**, **PLINQ**, or many `Task`s doing CPU work simultaneously.

**When to use which**

- **Use concurrency** when you have:
  - Many independent I/O operations (HTTP, DB, disk, messaging).
  - Latency-sensitive systems (UIs, APIs) that must stay responsive.
  - Workflows that spend most of their time waiting on external resources.
- **Use parallelism** when you have:
  - Heavy **CPU-bound** computations (image processing, simulations, analytics).
  - Large data sets that can be processed in chunks on different cores.
  - Algorithms that can be expressed as **data parallel** (same operation on many items) or **task parallel** (independent subtasks).

You almost always want **concurrency** for scalable servers, and **parallelism** for computational kernels. Many real systems use both: e.g. one concurrent request pipeline, inside which some CPU-heavy step uses parallelism.

**Trade-offs**

- **Concurrency**
  - **Pros**:
    - Scales well for I/O workloads with minimal extra threads.
    - Better responsiveness: threads are not blocked while waiting.
    - Fits naturally with `async` APIs in modern .NET.
  - **Cons**:
    - Complex control flow (many small awaited operations).
    - Harder reasoning about ordering, cancellation, and error propagation.
    - If misused (e.g. sync-over-async), can still waste threads and deadlock.

- **Parallelism**
  - **Pros**:
    - Uses **multiple cores** to reduce wall-clock time for CPU work.
    - Clear mental model for data parallel operations (`Parallel.For`, PLINQ).
  - **Cons**:
    - Overhead of scheduling and synchronization can dominate for small tasks.
    - Risk of **contention** on shared data and increased GC pressure.
    - If you parallelize the wrong thing (tiny loops, heavy locking), you can make performance worse.

**Common mistakes (what a mentor would call out)**

- **Confusing concurrency with parallelism**:
  - Using `Parallel.ForEach` for I/O-bound work (e.g. HTTP calls) instead of `Task.WhenAll` + async I/O, leading to many **blocked** threads and Thread Pool exhaustion.
  - Assuming `async` means “runs in parallel”. `async` is about *when* a thread is used, not *how many* threads you have.
- **Ignoring the environment**:
  - Using aggressive parallelism inside ASP.NET Core request handlers can degrade throughput by starving other requests.
  - Using CPU-heavy parallelism on UI threads (frontend) without offloading to the Thread Pool freezes the UI.

**C# 15-style example: concurrency vs parallelism**

```csharp
using System.Net.Http;

// Concurrency: many I/O-bound operations overlapped with async/await.
static async Task<int[]> DownloadManyAsync(Uri[] uris, HttpClient httpClient)
{
    // Start all requests concurrently without blocking threads.
    var tasks = uris.Select(uri => httpClient.GetByteArrayAsync(uri)).ToArray();

    // Await them all: logical concurrency, minimal threads used.
    byte[][] results = await Task.WhenAll(tasks).ConfigureAwait(false);

    // Simple CPU post-processing (still single-threaded here).
    return results.Select(bytes => bytes.Length).ToArray();
}

// Parallelism: CPU-bound loop using multiple cores.
static void BlurImagesInPlace(Span<byte[]> images)
{
    Parallel.For(0, images.Length, i =>
    {
        ApplyBlurFilter(images[i]); // CPU-heavy algorithm, no I/O.
    });
}
```

**Performance note**

- For **I/O-heavy** workloads, prefer **async concurrency** (minimal threads, high scalability).
- For **CPU-heavy** workloads, consider **parallelism** but always **measure**:
  - Compare a single-threaded baseline vs `Parallel.For` vs `Task.WhenAll` of CPU tasks.
  - Watch for increased GC allocations and contention from shared state.

2. **Asynchrony vs Multi-threading**

**Short definition**

- **Asynchrony**: An *execution style* where an operation can start, then **yield**, and later resume when work is ready (e.g. I/O completion). It does **not require multiple threads**. In C#, this is primarily `async` / `await` and `Task`-based APIs.
- **Multi-threading**: Using **more than one thread** of execution (e.g. multiple OS threads) that may run in parallel or be time-sliced on a single core.

In modern .NET, **asynchrony is the default for I/O**; multi-threading is what the runtime uses underneath (e.g. the Thread Pool) and what you explicitly use when you create `Thread`s or long-running tasks.

**Key relationships**

- Asynchronous code may run mostly on **one thread** (e.g. a UI thread) but still perform many I/O operations concurrently.
- Multi-threaded code might be entirely **synchronous** (e.g. a manual pool of worker threads all blocking on queues).
- Async + multi-threading often combine: the runtime uses Thread Pool threads to run your async continuations.

**Why modern .NET strongly prefers asynchrony for I/O**

- Asynchronous I/O uses **kernel-level async primitives** and **does not block threads while waiting**.
- This allows thousands or tens of thousands of I/O-bound operations to be active with a relatively small number of threads.
- Manual multi-threading for I/O (e.g. `new Thread` per socket) is a legacy pattern with poor scalability.

**Good modern practices**

- For I/O-bound APIs (HTTP clients, DB clients, streams), expose and consume **async methods**:
  - Prefer `ValueTask` for performance-sensitive low-allocation scenarios where most calls complete synchronously.
  - Keep your public API primarily `Task` / `ValueTask` based; avoid exposing raw `Thread`s.
- For CPU-bound work:
  - Use `Task.Run` or `Parallel.*` for background execution and multi-core utilization.
  - Hide explicit `Thread` usage behind higher-level abstractions unless you truly need low-level control.

**Common mistakes**

- **Equating async with multithreading**:
  - Expecting `async` code to "run on a different thread" by default. In many contexts (especially frontend UI), continuations resume on the **same thread** (`SynchronizationContext`).
- **Using threads instead of async for I/O**:
  - Spawning threads that block on `Stream.Read` or `HttpClient.Send` instead of using `ReadAsync` / `SendAsync`.
  - This burns threads doing nothing and harms scalability.
- **Mixing blocking and async**:
  - Calling `.Result`, `.Wait()`, or `.GetAwaiter().GetResult()` on tasks from a context that expects asynchrony (UI thread, ASP.NET Core request) causing deadlocks or Thread Pool starvation. See section 1.3 and 2.5 for deeper scheduling details.

**Example: asynchrony without explicit multi-threading**

```csharp
// This method is asynchronous, but the caller doesn't care about threads at all.
// The runtime decides which thread runs the continuations.
static async Task<string> ReadFileAsync(string path, CancellationToken cancellationToken = default)
{
    await using var stream = File.OpenRead(path);
    using var reader = new StreamReader(stream);

    // Asynchronous I/O: thread is returned to the pool while the OS reads data.
    return await reader.ReadToEndAsync(cancellationToken).ConfigureAwait(false);
}
```

You did not manage any `Thread` here; you only worked with **asynchrony**. The runtime handled the **multi-threading** aspects.

**Performance note**

- Asynchrony shines when the dominant cost is **waiting** (I/O latency).
- Explicit multi-threading is useful when you need:
  - Dedicated threads with specific priorities or affinity (rare in normal apps).
  - Custom schedulers, low-latency constraints, or integration with legacy APIs that assume real threads.

3. **Synchronous vs Asynchronous**

**Short definition**

- **Synchronous**:
  - The **caller waits** for the operation to complete **before** continuing.
  - Control does not return to the caller until the work is finished.
  - In C#, this is a regular method that runs to completion before returning a result.
- **Asynchronous**:
  - The operation **starts and returns immediately** with a *handle* (`Task`, `ValueTask`, `IAsyncEnumerable<T>`).
  - The caller can continue executing or `await` at a later time.

In C# 15+/modern .NET, **asynchronous == Task-based or async-stream-based APIs**, not legacy callbacks or event-based patterns. See section 1.3 for deeper historical comparison (APM/EAP vs `async`/`await`).

**When to prefer synchronous**

- Operations that:
  - Are **very fast and CPU-bound** (simple calculations, small in-memory transformations).
  - Complete within a few microseconds or low-milliseconds and are not composed many times in parallel.
  - Are on hot paths where **allocation of `Task`/`ValueTask`** and context capturing costs matter.
- Public APIs that:
  - Are naturally synchronous and rarely chained with other async operations.

**When to prefer asynchronous**

- Operations that:
  - Perform **I/O** (network, disk, IPC).
  - May take **unpredictable or long time** (remote services, user input, long DB queries).
  - Need to scale to many concurrent operations.
- API boundaries in:
  - **ASP.NET Core**: request handling should be async end-to-end.
  - **frontend apps (UI)**: avoid blocking the UI thread; use async for anything that might block.

**Common mistakes**

- **Sync-over-async**:
  - Writing synchronous APIs that internally call async code and then block (`.Result`, `.Wait()`). This is a major anti-pattern.
  - Use a fully async pipeline instead: if something is async **inside**, consider making the whole call chain async.
- **Async-over-sync**:
  - Wrapping purely synchronous, CPU-bound methods in `Task.Run` and labeling them async “just because”.
  - This often adds overhead and can lead to unnecessary Thread Pool use without real benefit.

**Example: synchronous vs asynchronous API**

```csharp
// Synchronous, CPU-bound work. Perfectly fine to keep sync.
static int CountWords(ReadOnlySpan<char> text)
{
    int count = 0;
    bool inWord = false;

    foreach (char c in text)
    {
        if (char.IsWhiteSpace(c))
        {
            inWord = false;
        }
        else if (!inWord)
        {
            inWord = true;
            count++;
        }
    }

    return count;
}

// Asynchronous, I/O-bound work.
static async Task<int> CountWordsInFileAsync(string path, CancellationToken cancellationToken = default)
{
    var text = await File.ReadAllTextAsync(path, cancellationToken).ConfigureAwait(false);
    return CountWords(text.AsSpan());
}
```

**Good to know**

- `async` does not automatically make things faster; it improves **scalability** and **responsiveness** for appropriate workloads.
- Prefer **sync APIs that call sync code** and **async APIs that call async code**. Avoid crossing the boundary both ways unless you have very clear, well-documented reasons.

4. **Blocking vs Non-Blocking**

**Short definition**

- **Blocking**:
  - The current thread **cannot do any other work** until the operation finishes.
  - The thread is *parked* (e.g. waiting on I/O, monitor, semaphore, `Task.Wait()`).
- **Non-blocking**:
  - The current thread starts an operation and then **continues doing useful work** without being parked.
  - In .NET, most non-blocking operations are expressed using `async`/`await` over async I/O primitives.

**Important nuance**

- **Async is not automatically non-blocking** if you use it incorrectly:
  - Calling `task.Result` or `task.Wait()` **blocks** the current thread until the Task completes, even if the Task itself is based on async I/O.
  - True non-blocking style means you **await** and let the runtime schedule other work while you are waiting.

**Why blocking is dangerous in modern apps**

- **Frontend (UI) apps (frontend)**:
  - Blocking the UI thread (e.g. `Task.Delay(1000).Wait()`) freezes input and repaint, producing a visible “hang”.
  - Long-running synchronous operations should be moved off the UI thread and exposed as async commands.
- **Server apps (ASP.NET Core, gRPC, minimal APIs)**:
  - Blocking threads on I/O (database, HTTP, file) reduces the number of requests the server can handle.
  - Enough blocked threads can cause **Thread Pool starvation**, increasing latency for all requests.

**Common blocking operations in .NET**

- `Thread.Sleep`, `Task.Wait`, `Task.Result`, `Task.GetAwaiter().GetResult()`
- Synchronous I/O: `Stream.Read`, `Stream.Write`, `HttpClient.Send`, `File.ReadAllText`, many legacy APIs.
- Blocking synchronization primitives: `Monitor.Enter` / `lock`, `Semaphore.Wait`, `ManualResetEvent.WaitOne`, `Task.WaitAll`, etc.

**Non-blocking equivalents (modern .NET)**

- `await Task.Delay(...)` instead of `Thread.Sleep`.
- `await task` instead of `.Wait()` / `.Result`.
- `ReadAsync`, `WriteAsync`, `SendAsync`, `ReceiveAsync` for streams and sockets.
- `SemaphoreSlim.WaitAsync` instead of `Semaphore.WaitOne` in async code paths.

**Example: blocking vs non-blocking server code**

```csharp
// BAD: blocking I/O in an ASP.NET Core endpoint.
app.MapGet("/customers/{id}", (int id) =>
{
    // Blocks a Thread Pool thread while waiting on the DB.
    var customer = LoadCustomerFromDatabase(id); // synchronous I/O
    return Results.Ok(customer);
});

// GOOD: non-blocking async I/O.
app.MapGet("/customers/{id}", async (int id, CustomerDb db, CancellationToken ct) =>
{
    var customer = await db.LoadCustomerAsync(id, ct).ConfigureAwait(false);
    return Results.Ok(customer);
});
```

**Common mistakes**

- **Blocking in library code**:
  - Providing sync APIs that internally call async with `.Result` / `.Wait()`. This may deadlock some hosts and reduce scalability in others.
- **Mixing blocking and non-blocking on the same hot path**:
  - E.g. `await`ing a DB call, then doing a big synchronous file read.
  - Try to make I/O consistently async to avoid head-of-line blocking.

**Performance note**

- Non-blocking async I/O allows the runtime to reuse a small number of threads to serve many requests.
- For CPU-bound work, blocking vs non-blocking is about **cooperative yielding**:
  - Long-running CPU loops that never yield can starve other work.
  - Consider breaking long computations into chunks and using `await Task.Yield()` or scheduling work on the Thread Pool so other tasks can progress (see sections 2.5 and 3.1 for deeper patterns).

5. **CPU-Bound vs IO-Bound**

**Short definition**

- **CPU-bound work**:
  - Dominated by **computation**: arithmetic, parsing, encryption, compression, image processing, machine learning, etc.
  - Performance is limited by **CPU speed and core count**.
- **I/O-bound work**:
  - Dominated by **waiting for external resources**: disk, network, database, cache, message queues.
  - Performance is limited by **latency and throughput of external systems**, not the CPU itself.

These categories strongly influence whether you should use **async**, **parallelism**, or remain **synchronous**.

**Typical patterns**

- **CPU-bound**:
  - Good candidates for **parallelism** (`Parallel.For`, PLINQ, `Task.Run` + `Task.WhenAll`).
  - Often benefit from algorithms that reduce allocations, improve cache locality, and minimize synchronization.
- **I/O-bound**:
  - Best handled by **async I/O** with `async`/`await`.
  - Aim to keep threads **unblocked** while waiting on I/O completion.

**Examples**

```csharp
// CPU-bound: compressing a large in-memory buffer.
static byte[] Compress(byte[] data)
{
    using var output = new MemoryStream();
    using (var gzip = new System.IO.Compression.GZipStream(output,
               System.IO.Compression.CompressionLevel.SmallestSize))
    {
        gzip.Write(data, 0, data.Length); // computation-heavy
    }

    return output.ToArray();
}

// I/O-bound: downloading content from a remote server.
static async Task<string> DownloadStringAsync(Uri uri, HttpClient httpClient, CancellationToken ct = default)
{
    using var response = await httpClient.GetAsync(uri, ct).ConfigureAwait(false);
    response.EnsureSuccessStatusCode();

    return await response.Content.ReadAsStringAsync(ct).ConfigureAwait(false);
}
```

**Choosing strategies**

- For **CPU-bound** operations:
  - First, write a **clear, single-threaded** version.
  - Measure.
  - If CPU is the bottleneck and the algorithm can be parallelized:
    - Try `Parallel.For` or PLINQ.
    - Or offload to background tasks with `Task.Run` and coordinate with `Task.WhenAll`.
  - Watch for:
    - Contention on locks.
    - Heavy allocations causing GC pauses.
    - False sharing and poor cache locality (see sections 2.6 and 4.8 for deeper analysis).

- For **I/O-bound** operations:
  - Prefer fully async APIs.
  - Compose with `Task.WhenAll` for high-concurrency operations.
  - Avoid parallelizing I/O with `Parallel.For` + synchronous I/O; that just creates many blocked threads.

**Common mistakes**

- **Treating I/O-bound as CPU-bound**:
  - Using `Parallel.ForEach` with synchronous HTTP calls, causing many blocked threads and poor scalability.
  - Correct approach: use `HttpClient` with `GetAsync` and `Task.WhenAll`.
- **Treating CPU-bound as I/O-bound**:
  - Turning CPU-heavy code into `async` just by wrapping it in `Task.Run`, assuming it helps scalability.
  - This may be reasonable for UI responsiveness (offloading from the UI thread), but does not make the work less CPU-bound; it simply moves the load to the Thread Pool.

**Good to know**

- Many real operations have **both** aspects:
  - Example: reading a large file (I/O-bound) and parsing it (CPU-bound).
  - Design your pipeline to:
    - Use async I/O to fetch the data.
    - Then decide whether the CPU-heavy part benefits from parallelism.
- Classifying workload correctly is one of the highest-leverage decisions you can make when tuning performance in concurrent and parallel C# applications.
