## 1.6. Context and state management in async code

This section explains **context capture and state management in async/await code**. Other sections may reference these concepts and will point back here for the full treatment (for example: *"See 1.6 for ConfigureAwait"*).

1. **SynchronizationContext vs TaskScheduler**
2. **ConfigureAwait(true) vs ConfigureAwait(false)**
3. **Context capture vs context-free execution**

### 1. **SynchronizationContext vs TaskScheduler**

**Short definition**

- **`SynchronizationContext`**:
  - Represents an **execution context** that defines where and how code runs (e.g., UI thread, Thread Pool, custom context).
  - Used by `async`/`await` to determine where continuations execute after an `await`.
  - Examples: `WindowsFormsSynchronizationContext` (UI thread), `AspNetSynchronizationContext` (legacy ASP.NET), `null` (Thread Pool in ASP.NET Core).

- **`TaskScheduler`**:
  - Represents a **scheduling policy** for executing `Task` work items.
  - Determines which threads execute tasks and in what order.
  - Examples: `TaskScheduler.Default` (Thread Pool), `TaskScheduler.FromCurrentSynchronizationContext()` (UI thread), custom schedulers.

**When to use which**

- **`SynchronizationContext`**:
  - Used **implicitly** by `async`/`await` to capture and restore execution context.
  - You rarely interact with it directly in application code.
  - Framework code (UI frameworks, ASP.NET) sets up `SynchronizationContext` for you.

- **`TaskScheduler`**:
  - Used when you need **explicit control** over task scheduling (e.g., `Task.Factory.StartNew` with a scheduler).
  - Used for **custom scheduling** scenarios (e.g., single-threaded scheduler, limited-concurrency scheduler).
  - You typically use `TaskScheduler.Default` (Thread Pool) or create custom schedulers for specialized scenarios.

**Key relationship**: `SynchronizationContext` is captured by `async`/`await` and used to schedule continuations. `TaskScheduler` is used for explicit task scheduling. In many cases, `TaskScheduler.FromCurrentSynchronizationContext()` bridges the two.

**Trade-offs**

- **`SynchronizationContext`**:
  - **Pros**:
    - **Automatic**: `async`/`await` automatically captures and uses it.
    - **Framework integration**: UI frameworks and ASP.NET set it up for you.
    - **Context-aware**: Ensures UI code runs on the UI thread, etc.
  - **Cons**:
    - **Can cause deadlocks**: If you block on async code that tries to return to a captured context (e.g., UI thread).
    - **Performance overhead**: Capturing and restoring context has small overhead.
  - **Not always present**: ASP.NET Core doesn't have a `SynchronizationContext` by default.

- **`TaskScheduler`**:
  - **Pros**:
    - **Explicit control**: You decide exactly where tasks run.
    - **Flexible**: Can create custom schedulers for specialized scenarios.
  - **Cons**:
    - **More verbose**: Must explicitly specify scheduler when creating tasks.
    - **Less automatic**: Doesn't integrate as seamlessly with `async`/`await` as `SynchronizationContext`.

**Common mistakes (what a mentor would call out)**

- **Blocking on async code with captured context**:
  - Calling `.Result` or `.Wait()` on a task from code that has a `SynchronizationContext` (e.g., UI thread), causing deadlocks.
  - **Solution**: Use `await` instead of blocking, or use `ConfigureAwait(false)` in library code.

- **Assuming `SynchronizationContext` always exists**:
  - Writing code that depends on `SynchronizationContext.Current` being non-null (e.g., in ASP.NET Core or console apps).
  - **Solution**: Check for null, or use `ConfigureAwait(false)` in library code that doesn't need context.

- **Using `TaskScheduler.FromCurrentSynchronizationContext()` unnecessarily**:
  - Explicitly scheduling tasks to the UI thread when `async`/`await` would handle it automatically.
  - **Solution**: Let `async`/`await` handle context capture automatically; only use explicit schedulers when needed.

**C# 15-style example: SynchronizationContext vs TaskScheduler**

```csharp
// SynchronizationContext is captured automatically by async/await.
// In UI apps (WinForms, WPF, MAUI), continuations run on the UI thread.
public partial class MainWindow : Window
{
    private async void Button_Click(object sender, RoutedEventArgs e)
    {
        // SynchronizationContext is captured (UI thread context).
        var data = await FetchDataAsync().ConfigureAwait(true); // true is default.
        
        // This runs on the UI thread (SynchronizationContext restored).
        TextBox.Text = data;
    }

    private async Task<string> FetchDataAsync()
    {
        // I/O operation, thread is released.
        using var client = new HttpClient();
        return await client.GetStringAsync("https://api.example.com/data").ConfigureAwait(false);
    }
}

// TaskScheduler for explicit scheduling (less common in application code).
public class CustomSchedulerExample
{
    public static void ScheduleToUIThread(Task task)
    {
        // Explicitly schedule to UI thread using TaskScheduler.
        var uiScheduler = TaskScheduler.FromCurrentSynchronizationContext();
        task.ContinueWith(t => 
        {
            // This runs on the UI thread.
            Console.WriteLine("Completed on UI thread");
        }, uiScheduler);
    }

    public static void ScheduleToThreadPool(Task task)
    {
        // Explicitly schedule to Thread Pool.
        task.ContinueWith(t => 
        {
            // This runs on a Thread Pool thread.
            Console.WriteLine("Completed on Thread Pool");
        }, TaskScheduler.Default);
    }
}

// ASP.NET Core: No SynchronizationContext by default.
public class ApiController
{
    [HttpGet]
    public async Task<IActionResult> GetData()
    {
        // No SynchronizationContext in ASP.NET Core, continuations run on Thread Pool.
        var data = await FetchDataAsync().ConfigureAwait(false); // false is fine (and recommended).
        return Ok(data);
    }

    private async Task<string> FetchDataAsync()
    {
        using var client = new HttpClient();
        return await client.GetStringAsync("https://api.example.com/data").ConfigureAwait(false);
    }
}
```

**Performance note**

- Capturing `SynchronizationContext` has minimal overhead, but it can accumulate in high-throughput scenarios.
- In library code, use `ConfigureAwait(false)` to avoid unnecessary context capture and improve performance.
- In ASP.NET Core, there's no `SynchronizationContext`, so continuations run on the Thread Pool by default (no context capture overhead).

**Good to know**

- UI frameworks (WinForms, WPF, MAUI) provide a `SynchronizationContext` that posts continuations to the UI thread.
- ASP.NET Core **does not** have a `SynchronizationContext` by default (unlike legacy ASP.NET), so continuations run on the Thread Pool.
- `TaskScheduler.Default` is the Thread Pool scheduler and is used when no `SynchronizationContext` is present.
- See section 2.3 for deeper coverage of SynchronizationContext and application models.

### 2. **ConfigureAwait(true) vs ConfigureAwait(false)**

**Short definition**

- **`ConfigureAwait(true)`** (default):
  - **Captures** the current `SynchronizationContext` (if present) and schedules continuations to that context.
  - In UI apps, continuations run on the UI thread.
  - In legacy ASP.NET, continuations run on the request context.

- **`ConfigureAwait(false)`**:
  - **Does not capture** the `SynchronizationContext`.
  - Continuations run on a Thread Pool thread (or the current thread if the operation completes synchronously).
  - Avoids context capture overhead and potential deadlocks.

**When to use which**

- **Use `ConfigureAwait(true)`** (or omit it, as it's the default):
  - In **application code** where you need to return to the original context (e.g., UI thread).
  - When you need to access UI elements or context-specific resources after an `await`.

- **Use `ConfigureAwait(false)`**:
  - In **library code** that doesn't depend on a specific execution context.
  - In **ASP.NET Core** code (there's no `SynchronizationContext` anyway, but it's still good practice).
  - When you want to **avoid deadlocks** and improve performance in high-throughput scenarios.
  - **General rule**: Use `ConfigureAwait(false)` in library code unless you specifically need context.

**Trade-offs**

- **`ConfigureAwait(true)`**:
  - **Pros**:
    - **Context preservation**: Continuations run on the original context (e.g., UI thread).
    - **Convenient**: No need to explicitly marshal back to the UI thread.
  - **Cons**:
    - **Deadlock risk**: If you block (e.g., `.Result`, `.Wait()`) on code that tries to return to a captured context, you can deadlock.
    - **Performance overhead**: Small overhead for context capture and restoration.
    - **Thread Pool starvation risk**: In UI apps, if the UI thread is blocked, continuations queue up.

- **`ConfigureAwait(false)`**:
  - **Pros**:
    - **No deadlock risk**: Continuations don't try to return to a captured context.
    - **Better performance**: Avoids context capture overhead.
    - **More scalable**: Continuations can run on any Thread Pool thread.
  - **Cons**:
    - **Context loss**: Cannot access UI elements or context-specific resources after `await` (unless you explicitly marshal).
    - **Not suitable for UI code**: In UI apps, you usually need to return to the UI thread.

**Common mistakes**

- **Using `ConfigureAwait(false)` in UI code**:
  - Using `ConfigureAwait(false)` and then trying to access UI elements, causing cross-thread exceptions.
  - **Solution**: Use `ConfigureAwait(true)` (or omit it) in UI code, or explicitly marshal back to the UI thread.

- **Not using `ConfigureAwait(false)` in library code**:
  - Library code that captures context unnecessarily, causing deadlocks when called from blocking code.
  - **Solution**: Use `ConfigureAwait(false)` in library code unless you specifically need context.

- **Blocking on async code with `ConfigureAwait(true)`**:
  - Calling `.Result` or `.Wait()` on a task that uses `ConfigureAwait(true)` from code with a `SynchronizationContext`, causing deadlocks.
  - **Solution**: Use `await` instead of blocking, or use `ConfigureAwait(false)` in the awaited code.

**C# 15-style example: ConfigureAwait(true) vs ConfigureAwait(false)**

```csharp
// UI code: Use ConfigureAwait(true) or omit it (default).
public partial class MainWindow : Window
{
    private async void LoadDataButton_Click(object sender, RoutedEventArgs e)
    {
        // ConfigureAwait(true) is default - continuation runs on UI thread.
        var data = await FetchDataAsync().ConfigureAwait(true);
        
        // Safe to access UI - we're on the UI thread.
        DataTextBox.Text = data;
    }

    private async Task<string> FetchDataAsync()
    {
        using var client = new HttpClient();
        // Library code: use ConfigureAwait(false).
        return await client.GetStringAsync("https://api.example.com/data").ConfigureAwait(false);
    }
}

// Library code: Use ConfigureAwait(false).
public class DataService
{
    public async Task<string> GetDataAsync(CancellationToken cancellationToken = default)
    {
        using var client = new HttpClient();
        // No need for context - use ConfigureAwait(false).
        var response = await client.GetAsync("https://api.example.com/data", cancellationToken)
            .ConfigureAwait(false);
        
        return await response.Content.ReadAsStringAsync(cancellationToken).ConfigureAwait(false);
    }
}

// ASP.NET Core: Use ConfigureAwait(false) (no SynchronizationContext anyway).
[ApiController]
public class DataController : ControllerBase
{
    private readonly DataService _dataService;

    [HttpGet]
    public async Task<IActionResult> GetData(CancellationToken cancellationToken)
    {
        // ConfigureAwait(false) is fine - no SynchronizationContext in ASP.NET Core.
        var data = await _dataService.GetDataAsync(cancellationToken).ConfigureAwait(false);
        return Ok(data);
    }
}

// Deadlock example: Blocking on async code with ConfigureAwait(true).
public class DeadlockExample
{
    public static string GetDataBlocking() // Called from UI thread.
    {
        // DEADLOCK: UI thread is blocked, but continuation tries to return to UI thread.
        return FetchDataAsync().Result; // .Result blocks the UI thread.
    }

    private static async Task<string> FetchDataAsync()
    {
        using var client = new HttpClient();
        // ConfigureAwait(true) tries to return to UI thread, but UI thread is blocked.
        return await client.GetStringAsync("https://api.example.com/data").ConfigureAwait(true);
    }

    // Solution: Use ConfigureAwait(false) in library code.
    private static async Task<string> FetchDataAsyncFixed()
    {
        using var client = new HttpClient();
        // ConfigureAwait(false) doesn't try to return to UI thread - no deadlock.
        return await client.GetStringAsync("https://api.example.com/data").ConfigureAwait(false);
    }
}
```

**Performance note**

- `ConfigureAwait(false)` avoids context capture overhead, which can accumulate in high-throughput scenarios.
- In ASP.NET Core, there's no `SynchronizationContext`, so `ConfigureAwait(false)` is a no-op, but it's still good practice for library code.
- The performance difference is usually small, but in library code, `ConfigureAwait(false)` is the recommended default.

**Good to know**

- **General guideline**: Use `ConfigureAwait(false)` in library code, `ConfigureAwait(true)` (or omit it) in application UI code.
- In ASP.NET Core, there's no `SynchronizationContext`, so `ConfigureAwait(false)` doesn't change behavior, but it's still recommended for consistency and to avoid issues if the code is reused in contexts with a `SynchronizationContext`.
- Some analyzers (e.g., CA2007) recommend using `ConfigureAwait(false)` in library code.
- See section 2.5 for deeper coverage of scheduling semantics in async/await.

### 3. **Context capture vs context-free execution**

**Short definition**

- **Context capture**:
  - When `async`/`await` **captures** the current `SynchronizationContext` (or `TaskScheduler`) and uses it to schedule continuations.
  - Continuations run on the captured context (e.g., UI thread, request context).
  - Default behavior when `ConfigureAwait(true)` is used (or omitted).

- **Context-free execution**:
  - When `async`/`await` **does not capture** context, and continuations run on a Thread Pool thread (or the current thread if the operation completes synchronously).
  - Achieved by using `ConfigureAwait(false)`.
  - More scalable and avoids deadlock risks, but loses context-specific behavior.

**When to use which**

- **Use context capture**:
  - In **UI application code** where you need to return to the UI thread after `await`.
  - When you need to access context-specific resources (e.g., `HttpContext` in legacy ASP.NET).
  - When the convenience of automatic context restoration outweighs the performance and deadlock risks.

- **Use context-free execution**:
  - In **library code** that doesn't depend on a specific execution context.
  - In **ASP.NET Core** code (no `SynchronizationContext` anyway, but context-free is still the pattern).
  - When you want to **avoid deadlocks** and improve scalability.
  - **General rule**: Prefer context-free execution in library code; use context capture only when necessary.

**Trade-offs**

- **Context capture**:
  - **Pros**:
    - **Automatic marshaling**: Continuations automatically run on the correct context (e.g., UI thread).
    - **Convenient**: No need to explicitly marshal back to the UI thread.
    - **Framework integration**: Works seamlessly with UI frameworks and legacy ASP.NET.
  - **Cons**:
    - **Deadlock risk**: Blocking on async code that tries to return to a captured context can deadlock.
    - **Performance overhead**: Context capture and restoration have small overhead.
    - **Scalability issues**: In UI apps, if the UI thread is blocked, continuations queue up.
  - **Thread affinity**: Continuations are tied to a specific thread/context, which can limit parallelism.

- **Context-free execution**:
  - **Pros**:
    - **No deadlock risk**: Continuations don't try to return to a captured context.
    - **Better performance**: Avoids context capture overhead.
    - **More scalable**: Continuations can run on any Thread Pool thread, improving parallelism.
    - **Simpler mental model**: No need to think about context capture and restoration.
  - **Cons**:
    - **Context loss**: Cannot access UI elements or context-specific resources after `await` (unless you explicitly marshal).
    - **Not suitable for UI code**: In UI apps, you usually need to return to the UI thread.

**Common mistakes**

- **Mixing context capture and blocking**:
  - Using context capture (`ConfigureAwait(true)`) and then blocking (`.Result`, `.Wait()`), causing deadlocks.
  - **Solution**: Use `await` instead of blocking, or use `ConfigureAwait(false)` in the awaited code.

- **Using context-free execution in UI code**:
  - Using `ConfigureAwait(false)` in UI code and then trying to access UI elements, causing cross-thread exceptions.
  - **Solution**: Use context capture in UI code, or explicitly marshal back to the UI thread using `Dispatcher.Invoke` or similar.

- **Assuming context always exists**:
  - Writing code that depends on `SynchronizationContext.Current` being non-null (e.g., in ASP.NET Core or console apps).
  - **Solution**: Check for null, or use context-free execution (`ConfigureAwait(false)`) in library code.

**C# 15-style example: context capture vs context-free execution**

```csharp
// Context capture: UI code (continuations run on UI thread).
public partial class MainWindow : Window
{
    private async void Button_Click(object sender, RoutedEventArgs e)
    {
        // Context is captured (UI thread).
        var data = await FetchDataAsync(); // ConfigureAwait(true) is default.
        
        // We're on the UI thread - safe to access UI.
        TextBox.Text = data;
    }

    private async Task<string> FetchDataAsync()
    {
        using var client = new HttpClient();
        // Library code: context-free execution.
        return await client.GetStringAsync("https://api.example.com/data").ConfigureAwait(false);
    }
}

// Context-free execution: Library code (continuations run on Thread Pool).
public class DataService
{
    public async Task<string> GetDataAsync(CancellationToken cancellationToken = default)
    {
        using var client = new HttpClient();
        // Context-free: continuations run on Thread Pool.
        var response = await client.GetAsync("https://api.example.com/data", cancellationToken)
            .ConfigureAwait(false);
        
        return await response.Content.ReadAsStringAsync(cancellationToken).ConfigureAwait(false);
    }
}

// Explicit context marshaling: When you need context-free execution but must access UI.
public partial class MainWindow : Window
{
    private async void Button_Click(object sender, RoutedEventArgs e)
    {
        // Context-free execution in library code.
        var data = await FetchDataAsync().ConfigureAwait(false);
        
        // Explicitly marshal back to UI thread if needed.
        Dispatcher.Invoke(() =>
        {
            TextBox.Text = data; // Safe: explicitly on UI thread.
        });
    }

    private async Task<string> FetchDataAsync()
    {
        using var client = new HttpClient();
        return await client.GetStringAsync("https://api.example.com/data").ConfigureAwait(false);
    }
}

// ASP.NET Core: Context-free execution (no SynchronizationContext).
[ApiController]
public class DataController : ControllerBase
{
    private readonly DataService _dataService;

    [HttpGet]
    public async Task<IActionResult> GetData(CancellationToken cancellationToken)
    {
        // Context-free: continuations run on Thread Pool (no SynchronizationContext in ASP.NET Core).
        var data = await _dataService.GetDataAsync(cancellationToken).ConfigureAwait(false);
        return Ok(data);
    }
}
```

**Performance note**

- Context-free execution (`ConfigureAwait(false)`) avoids context capture overhead and improves scalability.
- In high-throughput scenarios (e.g., ASP.NET Core APIs), context-free execution can provide measurable performance benefits.
- The performance difference is usually small, but in library code, context-free execution is the recommended default.

**Good to know**

- **Best practice**: Use context-free execution (`ConfigureAwait(false)`) in library code; use context capture in UI application code.
- ASP.NET Core does not have a `SynchronizationContext` by default, so continuations run on the Thread Pool regardless of `ConfigureAwait` settings, but using `ConfigureAwait(false)` is still recommended for consistency and to avoid issues if code is reused in contexts with a `SynchronizationContext`.
- Some code analyzers recommend using `ConfigureAwait(false)` in library code to avoid deadlock risks.
- See section 2.3 for deeper coverage of SynchronizationContext and application models, and section 2.5 for scheduling semantics in async/await.
