## 1.5. Parallelism libraries in .NET

This section explains **parallelism libraries and APIs in .NET** and when to use each. Other sections may reference these concepts and will point back here for the full treatment (for example: *"See 1.5 for TPL vs manual threads"*).

1. **TPL (Task Parallel Library) vs manual threads**
2. **Parallel class (Parallel.For/ForEach/Invoke) vs PLINQ**
3. **PLINQ vs regular LINQ**
4. **Dataflow (TPL Dataflow) vs Channels**
5. **Parallelism vs vectorization (SIMD) in .NET**

### 1. **TPL (Task Parallel Library) vs manual threads**

**Short definition**

- **TPL (Task Parallel Library)**:
  - A high-level .NET library for parallel and concurrent programming, introduced in .NET Framework 4.0.
  - Provides `Task`, `Task<T>`, `Parallel.For`, `Parallel.ForEach`, `Parallel.Invoke`, PLINQ, and related APIs.
  - Built on top of the Thread Pool and provides automatic load balancing, cancellation, and exception handling.

- **Manual threads**:
  - Creating and managing `Thread` objects directly.
  - Low-level control over thread creation, priority, affinity, and lifetime.
  - More complex and error-prone than TPL.

**When to use which**

- **Use TPL** (preferred in C# 15/.NET 9+):
  - For all parallel and concurrent programming in application code.
  - When you need task parallelism (`Task.Run`, `Task.WhenAll`) or data parallelism (`Parallel.For`, PLINQ).
  - When you want automatic load balancing, cancellation support, and exception aggregation.

- **Use manual threads** only when:
  - You need **specialized scheduling** (e.g., custom event loop, real-time constraints, device polling).
  - You need to **control thread priority or processor affinity** for specific hardware integration.
  - You are writing **low-level framework code** that cannot depend on TPL abstractions.
  - You have **measured** that TPL overhead is unacceptable (extremely rare).

**Trade-offs**

- **TPL**:
  - **Pros**:
    - **High-level abstractions**: `Task`, `Parallel.For`, PLINQ are easier to use than manual threads.
    - **Automatic load balancing**: Thread Pool manages work distribution across cores.
    - **Cancellation support**: Built-in `CancellationToken` integration.
    - **Exception handling**: Aggregates exceptions from parallel operations.
    - **Composability**: Tasks can be chained, awaited, and composed with `Task.WhenAll`, `Task.WhenAny`.
    - **Resource efficiency**: Reuses Thread Pool threads instead of creating new threads.
  - **Cons**:
    - **Less control**: Cannot directly control thread priority, affinity, or scheduling details.
    - **Abstraction overhead**: Small overhead compared to raw threads (usually negligible).

- **Manual threads**:
  - **Pros**:
    - **Full control**: Direct control over thread creation, priority, affinity, and lifetime.
    - **No abstraction overhead**: Direct OS thread management (though this rarely matters).
  - **Cons**:
    - **Complexity**: Must manually manage thread lifecycle, exception handling, cancellation.
    - **Resource waste**: Creating many threads is expensive; Thread Pool is more efficient.
    - **Error-prone**: Easy to introduce deadlocks, race conditions, and resource leaks.
  - **Rarely needed**: TPL covers 99% of use cases in modern .NET.

**Common mistakes (what a mentor would call out)**

- **Using manual threads for parallel work**:
  - Creating `Thread` objects for CPU-bound parallel processing instead of using `Parallel.For` or `Task.Run`.
  - **Solution**: Use TPL APIs (`Parallel.For`, `Task.Run`, `Task.WhenAll`) for parallel work.

- **Creating too many threads**:
  - Spawning hundreds of threads for parallel work, causing context switching overhead and resource exhaustion.
  - **Solution**: Let TPL and the Thread Pool manage thread count automatically.

- **Not handling exceptions in manual threads**:
  - Forgetting to catch exceptions in thread procedures, causing unhandled exceptions and process crashes.
  - **Solution**: TPL automatically captures and aggregates exceptions; with manual threads, you must handle exceptions explicitly.

**C# 15-style example: TPL vs manual threads**

```csharp
// Using TPL for parallel work (preferred).
static async Task ProcessFilesInParallelAsync(string[] filePaths, CancellationToken cancellationToken = default)
{
    var tasks = filePaths.Select(path => 
        Task.Run(() => ProcessFile(path), cancellationToken)).ToArray();
    
    try
    {
        await Task.WhenAll(tasks).ConfigureAwait(false);
    }
    catch (AggregateException ex)
    {
        // TPL aggregates exceptions automatically.
        foreach (var innerEx in ex.InnerExceptions)
        {
            Console.WriteLine($"Error: {innerEx.Message}");
        }
    }
}

static void ProcessFile(string path)
{
    // CPU-bound work.
    var content = File.ReadAllText(path);
    var processed = content.ToUpperInvariant();
    File.WriteAllText(path, processed);
}

// Using Parallel.For for data parallelism (preferred for CPU-bound loops).
static void ProcessDataInParallel(int[] data)
{
    Parallel.For(0, data.Length, i =>
    {
        data[i] = ComputeHeavyOperation(data[i]); // CPU-bound work.
    });
}

// Manual threads (avoid in application code, only for specialized scenarios).
static void ProcessWithManualThreads(string[] filePaths)
{
    var threads = new Thread[filePaths.Length];
    var exceptions = new List<Exception>();

    for (int i = 0; i < filePaths.Length; i++)
    {
        int index = i; // Capture for closure.
        threads[i] = new Thread(() =>
        {
            try
            {
                ProcessFile(filePaths[index]);
            }
            catch (Exception ex)
            {
                lock (exceptions)
                {
                    exceptions.Add(ex);
                }
            }
        });
        threads[i].Start();
    }

    foreach (var thread in threads)
    {
        thread.Join(); // Blocking wait.
    }

    if (exceptions.Count > 0)
    {
        throw new AggregateException(exceptions);
    }
}
```

**Performance note**

- TPL is optimized for most scenarios and provides better performance than manual threads due to Thread Pool reuse and load balancing.
- Manual threads have higher creation overhead and don't benefit from Thread Pool optimizations.
- Only use manual threads if you have a specific, measured need that TPL cannot satisfy.

**Good to know**

- TPL is built into .NET Core/.NET 5+ and is the standard way to write parallel and concurrent code.
- `Task.Run` and `Parallel.For` use the Thread Pool internally, providing efficient thread management.
- See section 1.2 for Task vs Thread, and section 2.1 for Thread Pool details.

### 2. **Parallel class (Parallel.For/ForEach/Invoke) vs PLINQ**

**Short definition**

- **`Parallel` class** (`Parallel.For`, `Parallel.ForEach`, `Parallel.Invoke`):
  - Imperative APIs for data parallelism and task parallelism.
  - `Parallel.For` / `Parallel.ForEach`: Execute a loop body in parallel across multiple iterations.
  - `Parallel.Invoke`: Execute multiple actions in parallel.
  - Good for CPU-bound loops and independent operations.

- **PLINQ** (`AsParallel()`):
  - Declarative API that parallelizes LINQ queries.
  - Extends LINQ with parallel execution semantics.
  - Good for querying and transforming data collections in parallel.

**When to use which**

- **Use `Parallel.For` / `Parallel.ForEach`** when:
  - You have a **simple loop** that processes items independently.
  - You want **imperative control** over the parallel execution.
  - You need to **modify collections in place** or perform side effects.

- **Use PLINQ** when:
  - You have a **LINQ query** that can benefit from parallelization.
  - You want **declarative, functional-style** parallel processing.
  - You are **transforming, filtering, or aggregating** data collections.

- **Use `Parallel.Invoke`** when:
  - You have a **small number of independent actions** to execute in parallel.
  - You don't need to process a collection, just run multiple operations concurrently.

**Trade-offs**

- **`Parallel` class**:
  - **Pros**:
    - **Imperative control**: Clear, explicit loop structure.
    - **Side effects**: Easy to perform side effects or modify state.
    - **Simple API**: Straightforward for basic parallel loops.
  - **Cons**:
    - **Less composable**: Harder to chain operations compared to LINQ.
    - **Imperative style**: More verbose for complex transformations.

- **PLINQ**:
  - **Pros**:
    - **Declarative**: Functional, composable style.
    - **LINQ integration**: Works seamlessly with existing LINQ queries.
    - **Automatic optimization**: Query optimizer can reorder operations for efficiency.
  - **Cons**:
    - **Less control**: Less fine-grained control over parallel execution compared to `Parallel.For`.
    - **Overhead**: Small overhead for query setup (usually negligible).
  - **Side effects**: Less suitable for operations with side effects (though possible with care).

**Common mistakes**

- **Using `Parallel.For` for I/O-bound work**:
  - Using `Parallel.ForEach` with synchronous I/O operations, creating many blocked threads.
  - **Solution**: Use `async`/`await` with `Task.WhenAll` for I/O-bound operations. See section 1.3 for async/await vs Parallel.For.

- **Using PLINQ without measuring**:
  - Adding `AsParallel()` to every LINQ query without profiling.
  - **Solution**: PLINQ has overhead; only use it when the query is CPU-bound and benefits from parallelization.

- **Mixing `Parallel` and PLINQ unnecessarily**:
  - Using both in the same code path when one would suffice.
  - **Solution**: Choose one approach based on your use case (imperative vs declarative).

**C# 15-style example: Parallel.For vs PLINQ**

```csharp
// Using Parallel.For for CPU-bound loops (imperative style).
static void ProcessImagesParallelFor(byte[][] images)
{
    Parallel.For(0, images.Length, i =>
    {
        ApplyBlurFilter(images[i]); // CPU-bound work, side effect on array.
    });
}

// Using PLINQ for data transformation (declarative style).
static int[] ProcessNumbersPLINQ(int[] numbers)
{
    return numbers
        .AsParallel()
        .Where(n => n > 0)
        .Select(n => n * n)
        .OrderBy(n => n)
        .ToArray();
}

// Using Parallel.Invoke for independent actions.
static void ProcessMultipleIndependentTasks()
{
    Parallel.Invoke(
        () => ProcessFile("file1.txt"),
        () => ProcessFile("file2.txt"),
        () => ProcessFile("file3.txt")
    );
}

// Combining both: PLINQ for query, then Parallel.For for side effects.
static void ProcessAndSaveResults(int[] data)
{
    // PLINQ for transformation.
    var processed = data
        .AsParallel()
        .Select(ComputeHeavyOperation)
        .ToArray();

    // Parallel.For for I/O (though async would be better for real I/O).
    Parallel.For(0, processed.Length, i =>
    {
        SaveResult(processed[i], $"result_{i}.txt");
    });
}
```

**Performance note**

- Both `Parallel.For` and PLINQ are optimized for CPU-bound, data-parallel workloads.
- PLINQ has slight overhead for query setup, but this is usually negligible.
- Measure to determine which performs better for your specific scenario; often the difference is small.

**Good to know**

- `Parallel.For` and PLINQ both use the Thread Pool and similar partitioning strategies internally.
- PLINQ can automatically adjust parallelism based on query characteristics.
- See section 3.2 for deeper patterns on data parallelism with Parallel and PLINQ.

### 3. **PLINQ vs regular LINQ**

**Short definition**

- **Regular LINQ**:
  - Sequential execution of LINQ queries.
  - Operations execute one at a time on a single thread.
  - Simple, predictable, and appropriate for most queries.

- **PLINQ** (`AsParallel()`):
  - Parallel execution of LINQ queries.
  - Operations may execute concurrently across multiple threads.
  - Appropriate for CPU-bound queries over large collections.

**When to use which**

- **Use regular LINQ** (preferred by default):
  - For most queries, especially small collections or I/O-bound operations.
  - When simplicity and predictability are priorities.
  - When the query overhead would exceed the benefit of parallelization.

- **Use PLINQ** when:
  - You have a **CPU-bound query** over a **large collection**.
  - You have **measured** that parallelization provides a performance benefit.
  - The query operations are **independent** and can be safely parallelized.

**Important distinction**: PLINQ is for **CPU-bound** work. For **I/O-bound** operations (e.g., querying a database, making HTTP calls), use regular LINQ with `async`/`await` and `Task.WhenAll`, not PLINQ.

**Trade-offs**

- **Regular LINQ**:
  - **Pros**:
    - **Simple**: Easy to understand and debug.
    - **Predictable**: Sequential execution is easier to reason about.
    - **Low overhead**: No parallelization overhead.
    - **Works everywhere**: No special considerations needed.
  - **Cons**:
    - **Single-threaded**: Cannot utilize multiple CPU cores.
    - **Slower for CPU-bound work**: Large, CPU-intensive queries may benefit from parallelization.

- **PLINQ**:
  - **Pros**:
    - **Parallel execution**: Can utilize multiple CPU cores for CPU-bound work.
    - **Automatic optimization**: Query optimizer can reorder operations.
    - **Scalable**: Performance improves with more CPU cores (for appropriate workloads).
  - **Cons**:
    - **Overhead**: Setup and coordination overhead (can dominate for small collections).
    - **Complexity**: Ordering, side effects, and thread safety require careful consideration.
  - **Not for I/O**: PLINQ is not suitable for I/O-bound operations (use async/await instead).

**Common mistakes**

- **Using PLINQ for I/O-bound queries**:
  - Adding `AsParallel()` to a query that performs I/O (e.g., database calls, HTTP requests).
  - **Solution**: Use regular LINQ with `async`/`await` and `Task.WhenAll` for I/O-bound operations.

- **Using PLINQ without measuring**:
  - Adding `AsParallel()` to every query without profiling.
  - **Solution**: PLINQ has overhead; only use it when profiling shows a benefit.

- **Assuming PLINQ preserves order**:
  - Expecting `AsParallel().Select()` to preserve order when `AsOrdered()` is not specified.
  - **Solution**: Use `AsOrdered()` if order matters, or understand that parallel execution may reorder results.

- **Using PLINQ with side effects**:
  - Performing side effects (e.g., modifying shared state) in PLINQ operations without proper synchronization.
  - **Solution**: Avoid side effects in PLINQ, or use proper synchronization (though this often negates the performance benefit).

**C# 15-style example: regular LINQ vs PLINQ**

```csharp
// Regular LINQ (preferred for most cases).
static int[] ProcessNumbersSequential(int[] numbers)
{
    return numbers
        .Where(n => n > 0)
        .Select(n => n * n)
        .OrderBy(n => n)
        .ToArray();
}

// PLINQ for CPU-bound work on large collections (use only if measured).
static int[] ProcessNumbersParallel(int[] numbers)
{
    return numbers
        .AsParallel()
        .Where(n => n > 0)
        .Select(n => n * n) // CPU-bound operation.
        .OrderBy(n => n)
        .ToArray();
}

// WRONG: Using PLINQ for I/O-bound work.
static async Task<string[]> DownloadUrlsWrong(string[] urls)
{
    // PLINQ is not for I/O!
    return urls
        .AsParallel()
        .Select(url => DownloadString(url)) // Blocking I/O - BAD!
        .ToArray();
}

// CORRECT: Using regular LINQ with async/await for I/O-bound work.
static async Task<string[]> DownloadUrlsAsync(string[] urls, CancellationToken cancellationToken = default)
{
    using var client = new HttpClient();
    var tasks = urls.Select(url => 
        client.GetStringAsync(url, cancellationToken)).ToArray();
    return await Task.WhenAll(tasks).ConfigureAwait(false);
}

// PLINQ with ordering preserved.
static int[] ProcessNumbersParallelOrdered(int[] numbers)
{
    return numbers
        .AsParallel()
        .AsOrdered() // Preserve order.
        .Where(n => n > 0)
        .Select(n => n * n)
        .ToArray();
}

// PLINQ with degree of parallelism control.
static int[] ProcessNumbersParallelWithDegree(int[] numbers)
{
    return numbers
        .AsParallel()
        .WithDegreeOfParallelism(Environment.ProcessorCount / 2) // Limit parallelism.
        .Where(n => n > 0)
        .Select(n => n * n)
        .ToArray();
}
```

**Performance note**

- PLINQ has overhead for query setup and coordination; it only pays off for CPU-bound queries over large collections.
- As a rule of thumb, consider PLINQ only if:
  - The collection has thousands of items or more.
  - The operations are CPU-bound (not I/O-bound).
  - Profiling shows a measurable benefit.
- For small collections or I/O-bound operations, regular LINQ is faster and simpler.

**Good to know**

- PLINQ automatically partitions data and balances load across threads.
- Use `AsOrdered()` if you need to preserve order, but this may reduce parallelism.
- Use `WithDegreeOfParallelism()` to limit parallelism if needed (e.g., to avoid saturating other resources).
- See section 3.2 for deeper patterns on PLINQ tuning and when data parallelism is beneficial.

### 4. **Dataflow (TPL Dataflow) vs Channels**

**Short definition**

- **TPL Dataflow**:
  - A library for building **message-passing, actor-like** dataflow pipelines.
  - Provides blocks (`BufferBlock`, `TransformBlock`, `ActionBlock`, etc.) that process messages asynchronously.
  - Good for complex, multi-stage pipelines with fan-out/fan-in, backpressure, and custom processing logic.
  - Requires the `System.Threading.Tasks.Dataflow` NuGet package (or built into .NET Core 2.1+ as part of the runtime, but API access requires the package).

- **Channels** (`System.Threading.Channels`):
  - A lightweight, high-performance API for **producer-consumer** scenarios.
  - Provides `Channel<T>` for unbounded or bounded message passing.
  - Simpler than Dataflow, focused on basic producer-consumer patterns.
  - Built into .NET Core 2.1+.

**When to use which**

- **Use Channels** (preferred for simple scenarios):
  - For **simple producer-consumer** patterns.
  - When you need **high-performance, low-overhead** message passing.
  - When you want a **lightweight** solution without external dependencies.

- **Use TPL Dataflow** when:
  - You need **complex, multi-stage pipelines** (transform, filter, aggregate).
  - You need **fan-out/fan-in** patterns (one-to-many, many-to-one).
  - You need **backpressure** and flow control in complex pipelines.
  - You need **custom processing logic** with different block types.

**Trade-offs**

- **Channels**:
  - **Pros**:
    - **Lightweight**: Minimal overhead, high performance.
    - **Simple API**: Easy to understand and use.
    - **Built-in**: Part of .NET Core 2.1+, no external dependencies.
    - **Async-friendly**: Designed for `async`/`await` from the ground up.
  - **Cons**:
    - **Limited features**: No built-in transformation, filtering, or aggregation blocks.
    - **Manual pipeline building**: Must manually implement multi-stage pipelines.

- **TPL Dataflow**:
  - **Pros**:
    - **Rich feature set**: Many block types (transform, filter, batch, join, etc.).
    - **Pipeline composition**: Easy to build complex, multi-stage pipelines.
    - **Backpressure**: Automatic flow control and backpressure handling.
    - **Fan-out/fan-in**: Built-in support for one-to-many and many-to-one patterns.
  - **Cons**:
    - **More complex**: Steeper learning curve than Channels.
    - **External dependency**: Requires NuGet package (though runtime support is built-in).
    - **Higher overhead**: More features mean more overhead (though still efficient).

**Common mistakes**

- **Using Dataflow for simple producer-consumer**:
  - Using `BufferBlock` when a simple `Channel` would suffice.
  - **Solution**: Use Channels for simple producer-consumer; reserve Dataflow for complex pipelines.

- **Using Channels for complex pipelines**:
  - Manually building multi-stage pipelines with Channels when Dataflow would be simpler.
  - **Solution**: Use Dataflow for complex pipelines; Channels for simple producer-consumer.

- **Not handling backpressure**:
  - Creating unbounded channels or buffers that can grow indefinitely.
  - **Solution**: Use bounded channels or Dataflow blocks with appropriate capacity limits.

**C# 15-style example: Channels vs Dataflow**

```csharp
// Using Channels for simple producer-consumer (preferred for simple scenarios).
public class SimpleProducerConsumer
{
    private readonly Channel<string> _channel;

    public SimpleProducerConsumer()
    {
        var options = new BoundedChannelOptions(100)
        {
            FullMode = BoundedChannelFullMode.Wait // Backpressure: wait when full.
        };
        _channel = Channel.CreateBounded<string>(options);
    }

    public async Task ProduceAsync(string item, CancellationToken cancellationToken = default)
    {
        await _channel.Writer.WriteAsync(item, cancellationToken).ConfigureAwait(false);
    }

    public async Task ConsumeAsync(Func<string, Task> processor, CancellationToken cancellationToken = default)
    {
        await foreach (var item in _channel.Reader.ReadAllAsync(cancellationToken))
        {
            await processor(item).ConfigureAwait(false);
        }
    }

    public void Complete() => _channel.Writer.Complete();
}

// Using TPL Dataflow for complex pipeline (preferred for multi-stage processing).
public class DataflowPipeline
{
    private readonly TransformBlock<string, string> _transformBlock;
    private readonly ActionBlock<string> _actionBlock;

    public DataflowPipeline()
    {
        _transformBlock = new TransformBlock<string, string>(async input =>
        {
            await Task.Delay(10); // Simulate work.
            return input.ToUpperInvariant();
        }, new ExecutionDataflowBlockOptions
        {
            MaxDegreeOfParallelism = 4,
            BoundedCapacity = 100 // Backpressure.
        });

        _actionBlock = new ActionBlock<string>(async result =>
        {
            Console.WriteLine($"Processed: {result}");
        }, new ExecutionDataflowBlockOptions
        {
            MaxDegreeOfParallelism = 2,
            BoundedCapacity = 50
        });

        _transformBlock.LinkTo(_actionBlock, new DataflowLinkOptions { PropagateCompletion = true });
    }

    public async Task ProcessAsync(string item, CancellationToken cancellationToken = default)
    {
        await _transformBlock.SendAsync(item, cancellationToken).ConfigureAwait(false);
    }

    public async Task CompleteAsync()
    {
        _transformBlock.Complete();
        await _actionBlock.Completion.ConfigureAwait(false);
    }
}

// Fan-out/fan-in with Dataflow (harder to do with Channels).
public class FanOutFanInPipeline
{
    private readonly BroadcastBlock<string> _broadcast;
    private readonly TransformBlock<string, int>[] _workers;
    private readonly ActionBlock<int> _aggregator;

    public FanOutFanInPipeline(int workerCount)
    {
        _broadcast = new BroadcastBlock<string>(x => x);
        
        _workers = Enumerable.Range(0, workerCount)
            .Select(i => new TransformBlock<string, int>(async input =>
            {
                await Task.Delay(10);
                return input.Length * (i + 1);
            }))
            .ToArray();

        _aggregator = new ActionBlock<int>(result =>
        {
            Console.WriteLine($"Aggregated: {result}");
        });

        foreach (var worker in _workers)
        {
            _broadcast.LinkTo(worker);
            worker.LinkTo(_aggregator);
        }
    }
}
```

**Performance note**

- Channels are optimized for high-throughput, low-latency producer-consumer scenarios.
- Dataflow has slightly more overhead but provides more features and automatic backpressure.
- For simple producer-consumer, Channels are typically faster. For complex pipelines, Dataflow's features often outweigh the overhead.

**Good to know**

- Channels are built into .NET Core 2.1+ and are the modern replacement for `BlockingCollection` in many scenarios.
- Dataflow requires the `System.Threading.Tasks.Dataflow` NuGet package, though the runtime support is built into .NET Core 2.1+.
- See section 3.3 for deeper patterns on pipelines, Channels, and Dataflow.

### 5. **Parallelism vs vectorization (SIMD) in .NET**

**Short definition**

- **Parallelism**:
  - Executing **multiple operations simultaneously** across **multiple CPU cores**.
  - Uses multiple threads to process different data items in parallel.
  - Examples: `Parallel.For`, PLINQ, `Task.Run` with multiple tasks.

- **Vectorization (SIMD)**:
  - Executing **multiple operations simultaneously** on **a single core** using **SIMD (Single Instruction, Multiple Data)** instructions.
  - Uses CPU vector registers (SSE, AVX, etc.) to process multiple data items with a single instruction.
  - Examples: `Vector<T>`, `Vector128<T>`, `Vector256<T>` in .NET.

**When to use which**

- **Use parallelism** when:
  - You have **many independent operations** that can run on different cores.
  - You want to utilize **multiple CPU cores** for throughput.
  - The operations are **CPU-bound** and benefit from multi-core execution.

- **Use vectorization (SIMD)** when:
  - You have **data-parallel operations** on **arrays of numeric data** (e.g., adding two arrays element-wise).
  - You want to process **multiple data items per CPU instruction** on a single core.
  - You are writing **performance-critical numeric code** (e.g., image processing, scientific computing, game engines).

- **Use both together** when:
  - You have large arrays and want to utilize both SIMD (per core) and parallelism (across cores).
  - Example: Use `Parallel.For` to process chunks of an array in parallel, and use `Vector<T>` to process each chunk with SIMD.

**Trade-offs**

- **Parallelism**:
  - **Pros**:
    - **Utilizes multiple cores**: Can scale performance with core count.
    - **General-purpose**: Works for any parallelizable workload.
    - **Easy to use**: `Parallel.For`, PLINQ are simple APIs.
  - **Cons**:
    - **Thread overhead**: Context switching and synchronization overhead.
    - **Memory overhead**: Each thread has its own stack.
  - **Limited by core count**: Performance improvement is bounded by the number of CPU cores.

- **Vectorization (SIMD)**:
  - **Pros**:
    - **Very fast**: Can process 4, 8, or 16 items per instruction (depending on data type and CPU).
    - **No thread overhead**: Runs on a single thread, no synchronization needed.
    - **Efficient**: Utilizes CPU vector units that would otherwise be idle.
  - **Cons**:
    - **Limited scope**: Only works for numeric operations on arrays.
    - **Platform-dependent**: Requires CPU support for SIMD instructions (though .NET provides fallbacks).
    - **Complexity**: More complex than regular loops; requires understanding of SIMD concepts.
  - **Single-core**: Does not utilize multiple cores by itself (but can be combined with parallelism).

**Common mistakes**

- **Using parallelism for vectorizable operations**:
  - Using `Parallel.For` for simple array operations that could benefit from SIMD.
  - **Solution**: Consider `Vector<T>` for numeric array operations; it's often faster than parallel loops for small-to-medium arrays.

- **Not combining both**:
  - Using SIMD on a single thread when you could also parallelize across cores.
  - **Solution**: Use `Parallel.For` with `Vector<T>` to get both SIMD speedup per core and multi-core parallelism.

- **Assuming SIMD is always faster**:
  - Using SIMD for operations that don't benefit (e.g., complex branching, non-numeric data).
  - **Solution**: Measure; SIMD is best for simple, numeric operations on arrays.

**C# 15-style example: parallelism vs vectorization**

```csharp
// Using parallelism (multiple cores).
static void AddArraysParallel(float[] a, float[] b, float[] result)
{
    Parallel.For(0, a.Length, i =>
    {
        result[i] = a[i] + b[i]; // Simple operation, but uses multiple cores.
    });
}

// Using vectorization (SIMD, single core, but very fast per core).
static void AddArraysVectorized(float[] a, float[] b, float[] result)
{
    int vectorLength = Vector<float>.Count;
    int i = 0;

    // Process vector-sized chunks.
    for (; i <= a.Length - vectorLength; i += vectorLength)
    {
        var va = new Vector<float>(a, i);
        var vb = new Vector<float>(b, i);
        (va + vb).CopyTo(result, i);
    }

    // Handle remainder.
    for (; i < a.Length; i++)
    {
        result[i] = a[i] + b[i];
    }
}

// Combining both: parallelism across cores, SIMD within each core (best performance).
static void AddArraysParallelVectorized(float[] a, float[] b, float[] result)
{
    Parallel.For(0, a.Length / Vector<float>.Count, chunkIndex =>
    {
        int start = chunkIndex * Vector<float>.Count;
        var va = new Vector<float>(a, start);
        var vb = new Vector<float>(b, start);
        (va + vb).CopyTo(result, start);
    });

    // Handle remainder sequentially.
    int remainderStart = (a.Length / Vector<float>.Count) * Vector<float>.Count;
    for (int i = remainderStart; i < a.Length; i++)
    {
        result[i] = a[i] + b[i];
    }
}

// Modern .NET: Using Vector128/Vector256 for explicit SIMD (more control).
static void AddArraysVector128(float[] a, float[] b, float[] result)
{
    int vectorLength = Vector128<float>.Count;
    int i = 0;

    for (; i <= a.Length - vectorLength; i += vectorLength)
    {
        var va = Vector128.LoadUnsafe(ref a[i]);
        var vb = Vector128.LoadUnsafe(ref b[i]);
        var vResult = va + vb;
        vResult.StoreUnsafe(ref result[i]);
    }

    for (; i < a.Length; i++)
    {
        result[i] = a[i] + b[i];
    }
}
```

**Performance note**

- **SIMD can provide 4-16x speedup** for appropriate numeric operations (depending on data type and CPU).
- **Parallelism can provide Nx speedup** (where N is the number of cores) for parallelizable workloads.
- **Combining both** can provide near N×M speedup (N cores × M items per SIMD instruction), though real-world speedups are often lower due to memory bandwidth and other factors.
- Always **measure** to determine the best approach for your specific scenario.

**Good to know**

- .NET provides `Vector<T>`, `Vector128<T>`, and `Vector256<T>` for SIMD operations.
- `Vector<T>` automatically uses the widest SIMD instructions available on the CPU (128-bit, 256-bit, or 512-bit).
- SIMD is most effective for:
  - Simple arithmetic operations (add, subtract, multiply, divide).
  - Comparisons and masking.
  - Operations on arrays of numeric types (`int`, `float`, `double`, etc.).
- SIMD is less effective for:
  - Complex branching logic.
  - Non-numeric data types.
  - Operations that cannot be expressed as vector operations.
- See .NET documentation on `System.Numerics.Vector` and hardware intrinsics for advanced SIMD usage.
