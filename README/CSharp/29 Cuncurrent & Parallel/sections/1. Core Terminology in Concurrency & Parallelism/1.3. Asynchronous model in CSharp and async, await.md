## 1.3. Asynchronous model in C# and async/await

This section explains the **modern async/await model in C#** and how it compares to historical asynchronous patterns. Other sections may reference async/await concepts and will point back here for the full treatment (for example: *"See 1.3 for async/await vs legacy patterns"*).

1. **async/await vs callback-based asynchrony**
2. **async/await vs Task.ContinueWith**
3. **async/await vs Begin/End (APM pattern)**
4. **async/await vs Event-based Asynchronous Pattern (EAP)**
5. **async/await vs Parallel.For / Parallel LINQ**

---

### 1. **async/await vs callback-based asynchrony**

**Short definition**

- **Callback-based asynchrony**:
  - A pattern where you pass a **callback function** (delegate, lambda) that will be invoked when an operation completes.
  - The caller initiates the operation and provides "what to do next" as a callback.
  - Common in JavaScript, Node.js, and older .NET APIs (e.g., `WebClient.DownloadStringAsync` with `DownloadStringCompleted` event).

- **async/await**:
  - A **language-level feature** in C# that lets you write asynchronous code that looks like synchronous code.
  - The compiler transforms `async` methods into state machines that handle continuations automatically.
  - You write sequential code with `await`, and the runtime handles the callback mechanics under the hood.

**When to use which**

- **Use async/await** (modern C# 15/.NET 9+):
  - For all new code that performs asynchronous operations.
  - When composing multiple async operations (chaining, error handling, cancellation).
  - When you need readable, maintainable asynchronous code.

- **Callback-based patterns** are now **legacy**:
  - Only when integrating with old APIs that haven't been updated to Task-based patterns.
  - When you must work with event-driven APIs that predate async/await (see EAP below).

**Trade-offs**

- **async/await**:
  - **Pros**:
    - **Readability**: Code reads top-to-bottom, like synchronous code.
    - **Exception handling**: Natural try/catch works across async boundaries.
    - **Composability**: Easy to chain operations, use `Task.WhenAll`, `Task.WhenAny`.
    - **Debugging**: Better stack traces and debugging experience (though still complex).
    - **Language integration**: `using`, `foreach`, `lock` (with `SemaphoreSlim`) work naturally.
  - **Cons**:
    - **Compiler overhead**: State machine generation adds some code size and minor allocation overhead.
    - **Learning curve**: Developers must understand `async`/`await` semantics (context capture, ConfigureAwait, etc.).
    - **Potential for misuse**: Sync-over-async, deadlocks, Thread Pool starvation if used incorrectly.

- **Callback-based asynchrony**:
  - **Pros**:
    - **Explicit control**: You see exactly when callbacks are invoked.
    - **No compiler magic**: Simpler mental model for what happens at runtime (though the code is harder to write).
  - **Cons**:
    - **Callback hell**: Deeply nested callbacks become unreadable (pyramid of doom).
    - **Error handling**: Exceptions in callbacks are hard to propagate to the original caller.
    - **Composition**: Chaining multiple async operations requires manual callback nesting.
    - **Resource management**: `using` statements and cleanup are harder to manage across callbacks.

**Common mistakes (what a mentor would call out)**

- **Mixing callbacks with async/await incorrectly**:
  - Wrapping callback-based APIs in `TaskCompletionSource` without understanding the lifetime and error propagation.
  - Not properly handling cancellation tokens when bridging callback APIs to async/await.

- **Assuming async/await is "just syntactic sugar"**:
  - While it simplifies code, it also changes execution semantics (context capture, exception propagation, stack unwinding).
  - Understanding these semantics is crucial for avoiding deadlocks and performance issues.

**C# 15-style example: callback-based vs async/await**

```csharp
// Legacy callback-based pattern (avoid in new code).
static void DownloadWithCallback(string url, Action<string> onSuccess, Action<Exception> onError)
{
    using var client = new HttpClient();
    client.GetStringAsync(url).ContinueWith(task =>
    {
        if (task.IsFaulted)
        {
            onError(task.Exception?.GetBaseException() ?? new Exception("Unknown error"));
        }
        else
        {
            onSuccess(task.Result);
        }
    });
}

// Modern async/await pattern (preferred).
static async Task<string> DownloadWithAsyncAwait(string url, CancellationToken cancellationToken = default)
{
    using var client = new HttpClient();
    try
    {
        return await client.GetStringAsync(url, cancellationToken).ConfigureAwait(false);
    }
    catch (HttpRequestException ex)
    {
        // Natural exception handling.
        throw new InvalidOperationException($"Failed to download from {url}", ex);
    }
}

// Composing multiple async operations (much easier with async/await).
static async Task<string[]> DownloadManyAsync(string[] urls, CancellationToken cancellationToken = default)
{
    using var client = new HttpClient();
    var tasks = urls.Select(url => client.GetStringAsync(url, cancellationToken)).ToArray();
    return await Task.WhenAll(tasks).ConfigureAwait(false);
}
```

**Performance note**

- `async/await` has minimal overhead for I/O-bound operations (the state machine allocation is negligible compared to I/O latency).
- For CPU-bound work that completes synchronously, consider `ValueTask` to avoid allocations (see section 1.2 for Task vs ValueTask).
- Callback-based code can sometimes avoid allocations, but the complexity and maintainability cost usually outweighs the micro-optimization.

**Good to know**

- Modern .NET APIs (e.g., `HttpClient`, `Stream`, `DbConnection`) are designed around `async/await` and `Task`/`ValueTask`.
- If you encounter callback-based or event-based APIs, consider wrapping them with `TaskCompletionSource` to expose a Task-based API. See section 3.1 for patterns on bridging non-Task APIs.

### 2. **async/await vs Task.ContinueWith**

**Short definition**

- **Task.ContinueWith**:
  - A method on `Task` that allows you to **chain continuations** explicitly.
  - You provide a delegate that runs when the antecedent task completes.
  - Supports options for scheduling, cancellation, and continuation behavior.

- **async/await**:
  - **Language-level syntax** that the compiler transforms into continuation-based code (often using `TaskAwaiter` and continuations internally).
  - You write sequential code; the compiler generates the continuation logic.

**When to use which**

- **Use async/await** (preferred in C# 15):
  - For all application and library code where readability and maintainability matter.
  - When you need natural exception handling, `using` statements, and control flow (loops, conditionals).

- **Task.ContinueWith** is now **rarely needed**:
  - Only in very specialized scenarios where you need fine-grained control over continuation scheduling.
  - When you must avoid the compiler-generated state machine overhead (extremely rare, and usually premature optimization).
  - When integrating with code that expects explicit continuation delegates.

**Trade-offs**

- **async/await**:
  - **Pros**:
    - **Readability**: Sequential code is easier to understand and maintain.
    - **Exception handling**: `try/catch` works naturally across await points.
    - **Resource management**: `using`, `await using` work correctly.
    - **Debugging**: Better stack traces and logical call stacks.
    - **Composability**: Easy to use `Task.WhenAll`, `Task.WhenAny`, and other combinators.
  - **Cons**:
    - **State machine overhead**: Each `async` method generates a state machine struct/class (usually negligible).
    - **Context capture**: By default, continuations capture `SynchronizationContext` (can cause deadlocks if misused; see section 1.6).

- **Task.ContinueWith**:
  - **Pros**:
    - **Explicit control**: You can specify `TaskContinuationOptions` (e.g., `OnlyOnFaulted`, `NotOnCanceled`).
    - **No state machine**: Slightly lower allocation overhead in theory (rarely matters in practice).
  - **Cons**:
    - **Callback hell**: Deeply nested `ContinueWith` calls become unreadable.
    - **Exception handling**: Must manually check `task.IsFaulted` and unwrap `AggregateException`.
    - **Resource management**: `using` statements don't work well across continuations.
    - **Composition**: Chaining multiple operations requires nested continuations.

**Common mistakes**

- **Using ContinueWith when async/await would be clearer**:
  - Writing `task.ContinueWith(t => { ... })` instead of `await task; ...`.
  - This reduces readability without providing real benefits.

- **Incorrect exception handling with ContinueWith**:
  - Not checking `task.IsFaulted` or not unwrapping `AggregateException`, leading to lost exceptions.
  - In async/await, exceptions are automatically unwrapped and propagated.

- **Mixing ContinueWith and async/await unnecessarily**:
  - Using `ContinueWith` inside an `async` method when a simple `await` would suffice.

**C# 15-style example: ContinueWith vs async/await**

```csharp
// Using Task.ContinueWith (legacy style, avoid in new code).
static void ProcessWithContinueWith(string url)
{
    using var client = new HttpClient();
    client.GetStringAsync(url)
        .ContinueWith(antecedent =>
        {
            if (antecedent.IsFaulted)
            {
                var ex = antecedent.Exception?.GetBaseException();
                Console.WriteLine($"Error: {ex?.Message}");
            }
            else if (antecedent.IsCanceled)
            {
                Console.WriteLine("Canceled");
            }
            else
            {
                var content = antecedent.Result;
                ProcessContent(content)
                    .ContinueWith(second =>
                    {
                        if (second.IsCompletedSuccessfully)
                        {
                            Console.WriteLine($"Processed: {second.Result}");
                        }
                    });
            }
        }, TaskContinuationOptions.ExecuteSynchronously);
}

// Modern async/await (preferred).
static async Task ProcessWithAsyncAwait(string url, CancellationToken cancellationToken = default)
{
    using var client = new HttpClient();
    try
    {
        var content = await client.GetStringAsync(url, cancellationToken).ConfigureAwait(false);
        var result = await ProcessContentAsync(content, cancellationToken).ConfigureAwait(false);
        Console.WriteLine($"Processed: {result}");
    }
    catch (OperationCanceledException)
    {
        Console.WriteLine("Canceled");
    }
    catch (Exception ex)
    {
        Console.WriteLine($"Error: {ex.Message}");
    }
}

static async Task<string> ProcessContentAsync(string content, CancellationToken cancellationToken = default)
{
    await Task.Delay(100, cancellationToken).ConfigureAwait(false); // Simulate work
    return content.ToUpperInvariant();
}
```

**Performance note**

- `async/await` and `ContinueWith` have similar performance characteristics for I/O-bound work.
- The state machine generated by `async/await` has minimal overhead (typically a small struct allocation per async method).
- Prefer `async/await` for readability; only consider `ContinueWith` if profiling shows it's a bottleneck (extremely rare).

**Good to know**

- The C# compiler transforms `async/await` into code that uses `TaskAwaiter` and continuations internally.
- `Task.ContinueWith` is still useful in advanced scenarios (e.g., custom schedulers, conditional continuations), but for most code, `async/await` is the right choice.
- See section 3.1 for deeper patterns on composing tasks with `Task.WhenAll`, `Task.WhenAny`, and other combinators.

### 3. **async/await vs Begin/End (APM pattern)**

**Short definition**

- **Asynchronous Programming Model (APM)**:
  - A legacy .NET pattern from .NET Framework 1.x/2.0 era.
  - Methods come in pairs: `BeginXxx` (starts the operation, returns `IAsyncResult`) and `EndXxx` (completes the operation, returns the result).
  - Example: `Stream.BeginRead` / `Stream.EndRead`, `Socket.BeginReceive` / `Socket.EndReceive`.

- **async/await**:
  - Modern C# pattern using `Task`-based APIs.
  - Single method (e.g., `ReadAsync`) returns `Task<T>` or `ValueTask<T>`.
  - Consumed with `await`.

**When to use which**

- **Use async/await with Task-based APIs** (modern .NET 9+):
  - All new code should use `Task`-based async methods (e.g., `Stream.ReadAsync`, `Socket.ReceiveAsync`).
  - Legacy `BeginXxx`/`EndXxx` methods are **deprecated** in favor of `*Async` methods.

- **Begin/End (APM)** is **obsolete**:
  - Only encountered when maintaining legacy code or integrating with very old libraries.
  - Modern .NET Core/.NET 5+ has removed or deprecated most APM methods.
  - If you must use APM, wrap it with `Task.Factory.FromAsync` or `TaskCompletionSource` to expose a Task-based API.

**Trade-offs**

- **async/await with Task-based APIs**:
  - **Pros**:
    - **Simpler API**: One method instead of two (`BeginXxx` + `EndXxx`).
    - **Better composability**: Works naturally with `Task.WhenAll`, `Task.WhenAny`, `async/await`.
    - **Exception handling**: Exceptions are thrown directly, not wrapped in `IAsyncResult`.
    - **Cancellation**: Built-in `CancellationToken` support.
    - **Resource management**: `using` and `await using` work correctly.
  - **Cons**:
    - None significant for modern code.

- **Begin/End (APM)**:
  - **Pros**:
    - None in modern code; this pattern is legacy.
  - **Cons**:
    - **Complex API**: Requires two method calls and manual `IAsyncResult` handling.
    - **Callback-based**: Must use callbacks or `IAsyncResult.AsyncWaitHandle` (blocking).
    - **Exception handling**: Exceptions are only thrown when calling `EndXxx`, making error handling awkward.
    - **No cancellation**: No built-in cancellation token support (must use `Abort` or custom mechanisms).
    - **Hard to compose**: Difficult to chain multiple APM operations.

**Common mistakes**

- **Using APM methods in new code**:
  - Calling `BeginRead`/`EndRead` instead of `ReadAsync` in modern .NET.
  - Always prefer the `*Async` methods that return `Task` or `ValueTask`.

- **Incorrect APM usage when maintaining legacy code**:
  - Not calling `EndXxx` (required to clean up resources and propagate exceptions).
  - Calling `EndXxx` multiple times (should only be called once per `BeginXxx`).
  - Blocking on `IAsyncResult.AsyncWaitHandle` instead of using callbacks or wrapping with `Task.Factory.FromAsync`.

**C# 15-style example: APM vs async/await**

```csharp
// Legacy APM pattern (obsolete, avoid in new code).
static void ReadWithAPM(Stream stream, byte[] buffer, int offset, int count)
{
    stream.BeginRead(buffer, offset, count, ar =>
    {
        try
        {
            int bytesRead = stream.EndRead(ar); // Must call EndRead!
            ProcessBytes(buffer, offset, bytesRead);
        }
        catch (Exception ex)
        {
            Console.WriteLine($"Error: {ex.Message}");
        }
    }, null);
}

// Modern async/await (preferred).
static async Task ReadWithAsyncAwait(Stream stream, byte[] buffer, int offset, int count, CancellationToken cancellationToken = default)
{
    try
    {
        int bytesRead = await stream.ReadAsync(buffer.AsMemory(offset, count), cancellationToken).ConfigureAwait(false);
        ProcessBytes(buffer, offset, bytesRead);
    }
    catch (Exception ex)
    {
        Console.WriteLine($"Error: {ex.Message}");
    }
}

// If you must bridge APM to async/await (e.g., legacy library).
static Task<int> ReadAsyncFromAPM(Stream stream, byte[] buffer, int offset, int count, CancellationToken cancellationToken = default)
{
    return Task.Factory.FromAsync(
        (callback, state) => stream.BeginRead(buffer, offset, count, callback, state),
        stream.EndRead,
        cancellationToken);
}
```

**Performance note**

- Modern `*Async` methods (e.g., `Stream.ReadAsync`) are optimized and often use the same underlying I/O completion ports as APM.
- There is no performance advantage to using APM; the Task-based APIs are the recommended approach.

**Good to know**

- Most APM methods have been removed or marked obsolete in .NET Core/.NET 5+.
- If you encounter APM in legacy code, use `Task.Factory.FromAsync` to wrap it and expose a Task-based API.
- See section 2.4 for deeper coverage of async I/O architecture in .NET.

### 4. **async/await vs Event-based Asynchronous Pattern (EAP)**

**Short definition**

- **Event-based Asynchronous Pattern (EAP)**:
  - A legacy .NET pattern from .NET Framework 2.0 era.
  - Methods are named `XxxAsync` (e.g., `DownloadStringAsync`) and return `void`.
  - Completion is signaled via an **event** (e.g., `DownloadStringCompleted`).
  - Example: `WebClient.DownloadStringAsync` / `DownloadStringCompleted` event.

- **async/await**:
  - Modern pattern using `Task`-based APIs.
  - Methods return `Task<T>` and are consumed with `await`.
  - Completion and results are handled through the `Task`, not events.

**When to use which**

- **Use async/await with Task-based APIs** (modern .NET 9+):
  - All new code should use `Task`-based async methods.
  - EAP is **deprecated**; modern alternatives exist (e.g., `HttpClient` instead of `WebClient`).

- **EAP is obsolete**:
  - Only encountered in legacy code or very old libraries.
  - `WebClient` (the primary EAP example) is largely replaced by `HttpClient` in modern .NET.
  - If you must use EAP, wrap it with `TaskCompletionSource` to expose a Task-based API.

**Trade-offs**

- **async/await with Task-based APIs**:
  - **Pros**:
    - **Composability**: Easy to chain operations, use `Task.WhenAll`, `Task.WhenAny`.
    - **Exception handling**: Exceptions are thrown directly from `await`, not via event handlers.
    - **Cancellation**: Built-in `CancellationToken` support.
    - **Resource management**: `using` and `await using` work correctly.
    - **No event subscription overhead**: No need to subscribe/unsubscribe from events.
  - **Cons**:
    - None significant for modern code.

- **Event-based Asynchronous Pattern (EAP)**:
  - **Pros**:
    - None in modern code; this pattern is legacy.
  - **Cons**:
    - **Event subscription complexity**: Must subscribe to events, handle unsubscription, manage object lifetime.
    - **Exception handling**: Exceptions are passed via event args (`AsyncCompletedEventArgs.Error`), making error handling awkward.
    - **Hard to compose**: Difficult to chain multiple EAP operations (requires nested event handlers).
    - **No cancellation**: Limited cancellation support (often requires `CancelAsync` method, not integrated with `CancellationToken`).
    - **Memory leaks risk**: Forgetting to unsubscribe from events can cause memory leaks.

**Common mistakes**

- **Using EAP in new code**:
  - Using `WebClient.DownloadStringAsync` instead of `HttpClient.GetStringAsync` in modern .NET.
  - Always prefer Task-based APIs.

- **Incorrect EAP usage when maintaining legacy code**:
  - Not unsubscribing from events, causing memory leaks.
  - Not checking `AsyncCompletedEventArgs.Error` in event handlers.
  - Attempting to use EAP methods with `await` directly (they return `void`, not `Task`).

**C# 15-style example: EAP vs async/await**

```csharp
// Legacy EAP pattern (obsolete, avoid in new code).
static void DownloadWithEAP(string url)
{
    using var client = new System.Net.WebClient(); // WebClient is largely obsolete.
    client.DownloadStringCompleted += (sender, e) =>
    {
        if (e.Error != null)
        {
            Console.WriteLine($"Error: {e.Error.Message}");
        }
        else if (e.Cancelled)
        {
            Console.WriteLine("Canceled");
        }
        else
        {
            Console.WriteLine($"Downloaded: {e.Result}");
        }
    };
    client.DownloadStringAsync(new Uri(url));
}

// Modern async/await (preferred).
static async Task DownloadWithAsyncAwait(string url, CancellationToken cancellationToken = default)
{
    using var client = new HttpClient();
    try
    {
        var content = await client.GetStringAsync(url, cancellationToken).ConfigureAwait(false);
        Console.WriteLine($"Downloaded: {content}");
    }
    catch (OperationCanceledException)
    {
        Console.WriteLine("Canceled");
    }
    catch (Exception ex)
    {
        Console.WriteLine($"Error: {ex.Message}");
    }
}

// If you must bridge EAP to async/await (e.g., legacy library).
static Task<string> DownloadAsyncFromEAP(string url, CancellationToken cancellationToken = default)
{
    var tcs = new TaskCompletionSource<string>();
    using var client = new System.Net.WebClient();
    
    client.DownloadStringCompleted += (sender, e) =>
    {
        if (e.Error != null)
        {
            tcs.TrySetException(e.Error);
        }
        else if (e.Cancelled)
        {
            tcs.TrySetCanceled(cancellationToken);
        }
        else
        {
            tcs.TrySetResult(e.Result);
        }
    };
    
    cancellationToken.Register(() => client.CancelAsync());
    client.DownloadStringAsync(new Uri(url));
    
    return tcs.Task;
}
```

**Performance note**

- Modern Task-based APIs (e.g., `HttpClient`) are optimized and provide better performance than EAP-based APIs like `WebClient`.
- There is no performance advantage to using EAP; the Task-based APIs are the recommended approach.

**Good to know**

- `WebClient` (the primary EAP example) is largely obsolete in modern .NET; use `HttpClient` instead.
- If you encounter EAP in legacy code, use `TaskCompletionSource` to wrap it and expose a Task-based API.
- See section 3.1 for deeper patterns on bridging non-Task APIs with `TaskCompletionSource`.

### 5. **async/await vs Parallel.For / Parallel LINQ**

**Short definition**

- **Parallel.For / Parallel LINQ (PLINQ)**:
  - APIs for **data parallelism**: executing the same operation on multiple data items **simultaneously across multiple CPU cores**.
  - `Parallel.For` / `Parallel.ForEach` execute a loop body in parallel.
  - PLINQ (`AsParallel()`) parallelizes LINQ queries.
  - These are for **CPU-bound work** that benefits from parallel execution.

- **async/await**:
  - Primarily for **I/O-bound concurrency**: overlapping I/O operations without blocking threads.
  - Also used for coordinating multiple async operations (e.g., `Task.WhenAll`).
  - Not designed for parallelizing CPU-bound loops.

**When to use which**

- **Use async/await** when:
  - Performing **I/O-bound** operations (HTTP, database, file I/O, network).
  - You want to **overlap multiple I/O operations** without blocking threads.
  - Coordinating multiple async operations (e.g., `Task.WhenAll`, `Task.WhenAny`).

- **Use Parallel.For / PLINQ** when:
  - Performing **CPU-bound** work that can be parallelized (e.g., processing large arrays, image manipulation, mathematical computations).
  - You have a **data-parallel** problem (same operation on many items).
  - You want to utilize **multiple CPU cores** for computation.

**Important distinction**

- `async/await` is about **concurrency** (overlapping operations in time, often I/O-bound).
- `Parallel.For` / PLINQ are about **parallelism** (executing work simultaneously on multiple cores, CPU-bound).
- See section 1.1 for the full treatment of concurrency vs parallelism.

**Trade-offs**

- **async/await**:
  - **Pros**:
    - Excellent for I/O-bound operations (scales to thousands of concurrent operations with minimal threads).
    - Natural composition with `Task.WhenAll`, `Task.WhenAny`.
    - Works well with cancellation tokens and error handling.
  - **Cons**:
    - Not designed for parallelizing CPU-bound loops (though you can use `Task.Run` + `Task.WhenAll` for task parallelism).
    - Each `async` method has a small state machine overhead (negligible for I/O).

- **Parallel.For / PLINQ**:
  - **Pros**:
    - Efficiently utilizes multiple CPU cores for CPU-bound work.
    - Automatic partitioning and load balancing.
    - Good for data-parallel problems (same operation on many items).
  - **Cons**:
    - **Not suitable for I/O-bound work**: Using `Parallel.ForEach` with synchronous I/O (e.g., `HttpClient.Send`) creates many blocked threads and harms scalability.
    - Overhead of partitioning and synchronization can dominate for small workloads.
    - Risk of contention on shared data structures.

**Common mistakes (what a mentor would call out)**

- **Using Parallel.For for I/O-bound work**:
  - Writing `Parallel.ForEach(urls, url => httpClient.GetString(url))` instead of `Task.WhenAll(urls.Select(url => httpClient.GetStringAsync(url)))`.
  - This creates many blocked threads and causes Thread Pool starvation.
  - **Correct approach**: Use `async/await` with `Task.WhenAll` for I/O-bound operations.

- **Using async/await for CPU-bound parallelism**:
  - Writing `await Task.Run(() => ProcessLargeArray(array))` when `Parallel.For` would be more appropriate.
  - While `Task.Run` can parallelize work, `Parallel.For` is optimized for data-parallel CPU-bound scenarios.

- **Mixing both incorrectly**:
  - Using `Parallel.For` inside an `async` method for I/O operations (wrong tool for the job).
  - Using `async/await` inside `Parallel.For` loop bodies without understanding the implications (can work, but often unnecessary complexity).

**C# 15-style example: async/await vs Parallel.For**

```csharp
// WRONG: Using Parallel.For for I/O-bound work (creates many blocked threads).
static void DownloadManyWrong(string[] urls)
{
    using var client = new HttpClient();
    Parallel.ForEach(urls, url =>
    {
        // Synchronous I/O blocks threads - BAD!
        var content = client.GetString(url); // Blocking call
        ProcessContent(content);
    });
}

// CORRECT: Using async/await for I/O-bound work.
static async Task DownloadManyAsync(string[] urls, CancellationToken cancellationToken = default)
{
    using var client = new HttpClient();
    var tasks = urls.Select(url => DownloadAndProcessAsync(client, url, cancellationToken)).ToArray();
    await Task.WhenAll(tasks).ConfigureAwait(false);
}

static async Task DownloadAndProcessAsync(HttpClient client, string url, CancellationToken cancellationToken)
{
    var content = await client.GetStringAsync(url, cancellationToken).ConfigureAwait(false);
    ProcessContent(content);
}

// CORRECT: Using Parallel.For for CPU-bound work.
static void ProcessImagesInParallel(Span<byte[]> images)
{
    Parallel.For(0, images.Length, i =>
    {
        ApplyBlurFilter(images[i]); // CPU-heavy computation, no I/O.
    });
}

// Combining both: async I/O, then CPU-bound parallelism.
static async Task ProcessImagesFromUrlsAsync(string[] imageUrls, CancellationToken cancellationToken = default)
{
    using var client = new HttpClient();
    
    // Step 1: Download images concurrently (I/O-bound, use async/await).
    var downloadTasks = imageUrls.Select(url => 
        client.GetByteArrayAsync(url, cancellationToken)).ToArray();
    byte[][] images = await Task.WhenAll(downloadTasks).ConfigureAwait(false);
    
    // Step 2: Process images in parallel (CPU-bound, use Parallel.For).
    Parallel.For(0, images.Length, i =>
    {
        ApplyBlurFilter(images[i]);
    });
}
```

**Performance note**

- For **I/O-bound** operations, `async/await` with `Task.WhenAll` scales to thousands of concurrent operations with a small number of threads.
- For **CPU-bound** operations, `Parallel.For` / PLINQ efficiently utilize multiple cores, but measure to ensure the overhead doesn't dominate.
- **Never use `Parallel.For` for I/O-bound work**; it wastes threads and reduces scalability.

**Good to know**

- `async/await` and `Parallel.For` / PLINQ solve different problems:
  - `async/await`: I/O-bound concurrency (overlapping I/O operations).
  - `Parallel.For` / PLINQ: CPU-bound parallelism (utilizing multiple cores).
- You can combine both: use `async/await` for I/O, then `Parallel.For` for CPU-bound processing of the results.
- See section 1.1 for concurrency vs parallelism, section 1.5 for deeper coverage of Parallel.For and PLINQ, and section 3.2 for data parallelism patterns.
