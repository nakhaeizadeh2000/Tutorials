### 1. **Race condition vs data race**

**Short definition**

- **Race condition**:
  - A **logical error** where the correctness of a program depends on the **timing or ordering** of events that are not guaranteed.
  - The program may produce incorrect results depending on the interleaving of operations from different threads.
  - A broader concept that includes data races but also includes higher-level ordering issues.

- **Data race**:
  - A specific type of race condition where **multiple threads access the same memory location concurrently**, and at least one access is a **write**, and the accesses are **not synchronized**.
  - Violates the .NET memory model guarantees and leads to undefined behavior.
  - A lower-level, memory-model violation.

**When these occur**

- **Race conditions** occur when:
  - The correctness of your program depends on a specific ordering of operations that is not guaranteed.
  - Example: Check-then-act patterns (checking a condition, then acting on it, without atomicity).

- **Data races** occur when:
  - Multiple threads read/write the same variable without proper synchronization (locks, `Interlocked`, etc.).
  - Example: Incrementing a counter from multiple threads without `lock` or `Interlocked`.

**Trade-offs and implications**

- **Race conditions**:
  - **Broader category**: Includes both data races and higher-level logical errors.
  - **Hard to detect**: May only manifest under specific timing conditions.
  - **Can be correct by accident**: Sometimes works correctly due to fortunate timing, making bugs intermittent.

- **Data races**:
  - **Memory model violation**: Undefined behavior according to the .NET memory model.
  - **Can cause corruption**: May lead to torn reads, lost writes, or other memory corruption.
  - **Detectable by tools**: Static analyzers and runtime tools (e.g., ThreadSanitizer) can detect data races.

**Common mistakes (what a mentor would call out)**

- **Assuming single-threaded code is safe in multi-threaded contexts**:
  - Using non-thread-safe collections (e.g., `List<T>`) from multiple threads without synchronization.
  - **Solution**: Use thread-safe collections (e.g., `ConcurrentDictionary`) or protect access with locks.

- **Check-then-act race conditions**:
  - Checking a condition and then acting on it without atomicity (e.g., `if (count < max) count++;`).
  - **Solution**: Use atomic operations (`Interlocked.CompareExchange`) or locks to make the check-and-act atomic.

- **Ignoring compiler and CPU reordering**:
  - Assuming that operations execute in the order written, ignoring memory model reordering.
  - **Solution**: Use proper synchronization (locks, `Interlocked`, `volatile` when appropriate) to establish ordering guarantees.

**C# 15-style example: race condition vs data race**

```csharp
// Data race: Multiple threads writing to the same variable without synchronization.
public class DataRaceExample
{
    private int _counter = 0; // Data race: unsynchronized access.

    public void Increment()
    {
        _counter++; // Not atomic - data race!
    }

    public int Value => _counter; // Also a data race if read while writing.

    // Solution: Use Interlocked or lock.
    public void IncrementFixed()
    {
        Interlocked.Increment(ref _counter); // Atomic, no data race.
    }

    public int ValueFixed => Interlocked.CompareExchange(ref _counter, 0, 0); // Safe read.
}

// Race condition (check-then-act): Logical error, not just a data race.
public class RaceConditionExample
{
    private readonly List<string> _items = new();
    private readonly object _lock = new object();

    public void AddIfNotExists(string item)
    {
        // Race condition: check and add are not atomic.
        if (!_items.Contains(item)) // Check.
        {
            _items.Add(item); // Act - but another thread may have added it between check and act.
        }
    }

    // Solution: Make check-and-act atomic.
    public void AddIfNotExistsFixed(string item)
    {
        lock (_lock)
        {
            if (!_items.Contains(item))
            {
                _items.Add(item); // Atomic check-and-act.
            }
        }
    }

    // Better solution: Use thread-safe collection.
    private readonly ConcurrentDictionary<string, object> _itemsDict = new();

    public void AddIfNotExistsBetter(string item)
    {
        _itemsDict.TryAdd(item, null); // Atomic operation.
    }
}

// Higher-level race condition: Ordering dependency.
public class OrderingRaceCondition
{
    private bool _initialized = false;
    private string _data = string.Empty;

    public void Initialize(string data)
    {
        _data = data;
        _initialized = true; // Race condition: another thread may read _initialized before _data is set.
    }

    public string GetData()
    {
        if (_initialized)
        {
            return _data; // May read uninitialized _data if ordering is not guaranteed.
        }
        throw new InvalidOperationException("Not initialized");
    }

    // Solution: Use proper synchronization or make initialization atomic.
    private volatile bool _initializedFixed = false; // volatile provides ordering guarantee.

    public void InitializeFixed(string data)
    {
        _data = data;
        _initializedFixed = true; // volatile write ensures visibility.
    }
}
```

**Performance note**

- Preventing race conditions and data races requires synchronization, which has overhead.
- Use the lightest synchronization mechanism that provides the necessary guarantees:
  - `Interlocked` for simple atomic operations (lock-free, very fast).
  - `lock` for critical sections (moderate overhead, but necessary for complex operations).
  - Lock-free data structures (e.g., `ConcurrentDictionary`) when appropriate.

**Good to know**

- **All data races are race conditions, but not all race conditions are data races**.
- Data races are memory model violations and lead to undefined behavior.
- Race conditions are logical errors that may or may not involve data races.
- Use static analyzers, runtime tools, and code reviews to detect race conditions and data races.
- See section 4.1 for deeper coverage of reasoning about correctness in concurrent programs, and section 4.2 for the .NET memory model.

### 2. **Deadlock vs livelock vs starvation**

**Short definition**

- **Deadlock**:
  - A situation where **two or more threads are blocked forever**, each waiting for a resource held by another.
  - Classic example: Thread A holds Lock 1 and waits for Lock 2; Thread B holds Lock 2 and waits for Lock 1.
  - **No progress** is possible; the system is stuck.

- **Livelock**:
  - A situation where threads are **not blocked but make no progress** because they keep responding to each other in a way that prevents forward progress.
  - Threads are active but stuck in a loop, constantly retrying and failing.
  - Example: Two threads trying to acquire the same locks but repeatedly backing off and retrying in the same pattern.

- **Starvation**:
  - A situation where a thread is **unable to make progress** because other threads are consistently given priority or resources.
  - The thread is not blocked, but it never gets a chance to run or acquire resources.
  - Example: Low-priority threads never getting CPU time, or a thread waiting on a lock that is always acquired by other threads.

**When these occur**

- **Deadlocks** occur when:
  - Multiple locks are acquired in different orders by different threads.
  - Blocking operations (e.g., `.Result`, `.Wait()`) are used in contexts with `SynchronizationContext` (e.g., UI thread).
  - Circular dependencies exist in resource acquisition.

- **Livelocks** occur when:
  - Threads use **backoff strategies** that cause them to interfere with each other.
  - Lock-free algorithms have retry loops that can cause threads to keep retrying without progress.

- **Starvation** occurs when:
  - Thread priorities are mismanaged (low-priority threads never run).
  - Lock contention favors certain threads (e.g., unfair locks, always-acquiring threads).
  - Resource allocation is biased toward certain threads.

**Trade-offs and implications**

- **Deadlock**:
  - **Complete system halt**: No progress is possible until the deadlock is resolved (usually requires process restart).
  - **Hard to detect**: May only occur under specific timing conditions.
  - **Preventable**: Use consistent lock ordering, avoid blocking on async code, use timeouts.

- **Livelock**:
  - **System appears responsive**: Threads are active, but no useful work is done.
  - **Harder to detect**: May look like the system is working but making no progress.
  - **Preventable**: Use randomization in backoff strategies, avoid symmetric retry patterns.

- **Starvation**:
  - **Partial system failure**: Some threads make progress, but others don't.
  - **Can be subtle**: May appear as performance issues rather than complete failure.
  - **Preventable**: Use fair locks, avoid thread priorities unless necessary, monitor resource allocation.

**Common mistakes**

- **Inconsistent lock ordering**:
  - Acquiring locks in different orders in different code paths, causing deadlocks.
  - **Solution**: Establish a consistent lock ordering protocol (e.g., always acquire locks in a specific order).

- **Blocking on async code with SynchronizationContext**:
  - Calling `.Result` or `.Wait()` on a task from code with a `SynchronizationContext` (e.g., UI thread), causing deadlocks.
  - **Solution**: Use `await` instead of blocking, or use `ConfigureAwait(false)` in library code. See section 1.6 for ConfigureAwait.

- **Symmetric retry patterns**:
  - Using the same backoff strategy for all threads, causing livelock.
  - **Solution**: Use randomization in backoff strategies (exponential backoff with jitter).

**C# 15-style example: deadlock vs livelock vs starvation**

```csharp
// Deadlock: Circular lock dependency.
public class DeadlockExample
{
    private readonly object _lock1 = new object();
    private readonly object _lock2 = new object();

    public void Method1()
    {
        lock (_lock1)
        {
            Thread.Sleep(10); // Simulate work.
            lock (_lock2) // Waits for _lock2.
            {
                // Critical section.
            }
        }
    }

    public void Method2()
    {
        lock (_lock2)
        {
            Thread.Sleep(10); // Simulate work.
            lock (_lock1) // Waits for _lock1 - DEADLOCK if Method1 and Method2 run concurrently.
            {
                // Critical section.
            }
        }
    }

    // Solution: Consistent lock ordering.
    public void Method1Fixed()
    {
        lock (_lock1)
        {
            lock (_lock2) // Always acquire _lock1 before _lock2.
            {
                // Critical section.
            }
        }
    }

    public void Method2Fixed()
    {
        lock (_lock1) // Same order as Method1Fixed.
        {
            lock (_lock2)
            {
                // Critical section.
            }
        }
    }
}

// Livelock: Threads keep retrying in the same pattern.
public class LivelockExample
{
    private bool _resourceAvailable = false;
    private readonly object _lock = new object();

    public void Thread1()
    {
        while (true)
        {
            lock (_lock)
            {
                if (_resourceAvailable)
                {
                    _resourceAvailable = false;
                    break; // Success.
                }
            }
            Thread.Sleep(100); // Fixed backoff - can cause livelock.
        }
    }

    public void Thread2()
    {
        while (true)
        {
            lock (_lock)
            {
                if (!_resourceAvailable)
                {
                    _resourceAvailable = true;
                    break; // Success.
                }
            }
            Thread.Sleep(100); // Same backoff - threads may interfere.
        }
    }

    // Solution: Use randomization in backoff.
    private readonly Random _random = new Random();

    public void Thread1Fixed()
    {
        while (true)
        {
            lock (_lock)
            {
                if (_resourceAvailable)
                {
                    _resourceAvailable = false;
                    break;
                }
            }
            // Randomized backoff reduces livelock risk.
            Thread.Sleep(_random.Next(50, 150));
        }
    }
}

// Starvation: Low-priority threads never get CPU time.
public class StarvationExample
{
    public void HighPriorityThread()
    {
        Thread.CurrentThread.Priority = ThreadPriority.Highest;
        while (true)
        {
            // CPU-intensive work - may starve other threads.
            ComputeHeavyOperation();
        }
    }

    public void LowPriorityThread()
    {
        Thread.CurrentThread.Priority = ThreadPriority.Lowest;
        // May never get CPU time if high-priority threads are always running.
        DoWork();
    }

    // Solution: Avoid thread priorities unless necessary; use fair scheduling.
    public void BetterApproach()
    {
        // Use Task.Run with default scheduling - Thread Pool manages fairness.
        Task.Run(() => ComputeHeavyOperation());
        Task.Run(() => DoWork());
    }
}

// Deadlock with async/await and SynchronizationContext.
public class AsyncDeadlockExample
{
    // DEADLOCK: Blocking on async code from UI thread.
    public string GetDataBlocking()
    {
        // Called from UI thread with SynchronizationContext.
        return FetchDataAsync().Result; // Blocks UI thread.
    }

    private async Task<string> FetchDataAsync()
    {
        using var client = new HttpClient();
        // ConfigureAwait(true) tries to return to UI thread, but UI thread is blocked.
        return await client.GetStringAsync("https://api.example.com/data").ConfigureAwait(true);
    }

    // Solution: Use await instead of blocking, or ConfigureAwait(false).
    public async Task<string> GetDataAsync()
    {
        return await FetchDataAsync().ConfigureAwait(false); // No deadlock.
    }
}
```

**Performance note**

- Deadlocks, livelocks, and starvation all prevent progress and waste resources.
- Preventing these issues requires careful design (lock ordering, fair scheduling, proper async patterns).
- Use timeouts on lock acquisition to detect and recover from potential deadlocks.

**Good to know**

- **Deadlocks are the most common** of these three issues in typical applications.
- **Livelocks are rarer** but can be harder to detect (system appears responsive but makes no progress).
- **Starvation is often a design issue** (unfair resource allocation, excessive thread priorities).
- Use diagnostic tools (dumps, profilers) to detect deadlocks and starvation.
- See section 4.5 for deeper coverage of diagnosing deadlocks, livelocks, and starvation.

### 3. **Thread-safety vs reentrancy-safety**

**Short definition**

- **Thread-safety**:
  - A property of code that can be **safely executed by multiple threads concurrently** without data corruption or race conditions.
  - Ensures that shared data is accessed correctly when multiple threads are involved.
  - Example: A method that uses locks to protect shared state is thread-safe.

- **Reentrancy-safety**:
  - A property of code that can be **safely called again before a previous invocation completes** (e.g., from the same thread or a callback).
  - Ensures that code handles reentrant calls correctly (e.g., event handlers, callbacks, recursive calls).
  - Example: A method that handles being called from its own callback or event handler.

**When these matter**

- **Thread-safety** matters when:
  - Multiple threads access shared data concurrently.
  - You need to protect critical sections from concurrent access.
  - You use locks, `Interlocked`, or thread-safe collections.

- **Reentrancy-safety** matters when:
  - Code can be called from callbacks, event handlers, or recursive invocations.
  - Code uses locks that are not reentrant (e.g., `Monitor`, which is reentrant per thread, but `SemaphoreSlim` is not).
  - Code maintains state that could be corrupted by reentrant calls.

**Trade-offs**

- **Thread-safety**:
  - **Pros**:
    - Enables safe concurrent access to shared data.
    - Prevents data races and corruption.
  - **Cons**:
    - Requires synchronization overhead (locks, atomic operations).
    - Can reduce parallelism if locks are contended.

- **Reentrancy-safety**:
  - **Pros**:
    - Enables safe callback and event handler patterns.
    - Allows recursive calls without deadlocks (with reentrant locks).
  - **Cons**:
    - Can be complex to implement correctly.
    - May require additional state tracking to prevent reentrant issues.

**Common mistakes**

- **Assuming thread-safety implies reentrancy-safety**:
  - Using thread-safe code in reentrant contexts (e.g., event handlers) without considering reentrancy.
  - **Solution**: Understand that thread-safety and reentrancy-safety are different concerns.

- **Using non-reentrant locks in reentrant contexts**:
  - Using `SemaphoreSlim` (non-reentrant) in code that may be called reentrantly, causing deadlocks.
  - **Solution**: Use reentrant locks (e.g., `Monitor`/`lock`) or design to avoid reentrancy.

- **Not handling reentrant calls in event handlers**:
  - Event handlers that modify state without considering that the event may be raised again during handling.
  - **Solution**: Use guards, flags, or reentrancy-safe patterns.

**C# 15-style example: thread-safety vs reentrancy-safety**

```csharp
// Thread-safe but not reentrancy-safe: Event handler that can be called reentrantly.
public class ThreadSafeButNotReentrant
{
    private int _count = 0;
    private readonly object _lock = new object();

    public event EventHandler? CountChanged;

    public void Increment()
    {
        lock (_lock)
        {
            _count++;
            CountChanged?.Invoke(this, EventArgs.Empty); // May cause reentrant call.
        }
    }

    // Problem: If CountChanged handler calls Increment again, it's safe (lock is reentrant),
    // but if the handler does something else that's not reentrancy-safe, issues arise.
}

// Reentrancy-safe: Using a guard to prevent reentrant execution.
public class ReentrancySafeExample
{
    private int _count = 0;
    private readonly object _lock = new object();
    private bool _isHandling = false; // Guard flag.

    public event EventHandler? CountChanged;

    public void Increment()
    {
        lock (_lock)
        {
            if (_isHandling)
            {
                return; // Prevent reentrant execution.
            }

            _isHandling = true;
            try
            {
                _count++;
                CountChanged?.Invoke(this, EventArgs.Empty);
            }
            finally
            {
                _isHandling = false;
            }
        }
    }
}

// Thread-safe and reentrancy-safe: Using Monitor (reentrant lock).
public class ThreadSafeAndReentrantSafe
{
    private int _count = 0;
    private readonly object _lock = new object();

    public void Increment()
    {
        lock (_lock) // Monitor is reentrant - same thread can acquire multiple times.
        {
            _count++;
            DoSomethingElse(); // Can safely call methods that also use the same lock.
        }
    }

    private void DoSomethingElse()
    {
        lock (_lock) // Same thread, reentrant acquisition is safe.
        {
            // Additional work.
        }
    }
}

// Non-reentrant lock: SemaphoreSlim can cause deadlocks if used reentrantly.
public class NonReentrantLockExample
{
    private readonly SemaphoreSlim _semaphore = new SemaphoreSlim(1, 1);

    public async Task Method1Async()
    {
        await _semaphore.WaitAsync().ConfigureAwait(false);
        try
        {
            await Method2Async().ConfigureAwait(false); // Calls Method2Async which also waits.
        }
        finally
        {
            _semaphore.Release();
        }
    }

    public async Task Method2Async()
    {
        await _semaphore.WaitAsync().ConfigureAwait(false); // DEADLOCK if called from Method1Async!
        try
        {
            // Work.
        }
        finally
        {
            _semaphore.Release();
        }
    }

    // Solution: Use reentrant lock or redesign to avoid reentrancy.
    private readonly object _lock = new object();

    public void Method1Fixed()
    {
        lock (_lock) // Reentrant - safe.
        {
            Method2Fixed();
        }
    }

    public void Method2Fixed()
    {
        lock (_lock) // Same thread, reentrant acquisition is safe.
        {
            // Work.
        }
    }
}
```

**Performance note**

- Reentrant locks (e.g., `Monitor`) have slightly more overhead than non-reentrant locks, but the difference is usually negligible.
- Preventing reentrancy with guards adds minimal overhead but improves safety.
- Choose the right synchronization primitive based on your needs (reentrant vs non-reentrant).

**Good to know**

- **`Monitor` (used by `lock`) is reentrant**: The same thread can acquire the same lock multiple times.
- **`SemaphoreSlim` is not reentrant**: The same thread cannot acquire it multiple times (will deadlock or throw).
- **Thread-safety and reentrancy-safety are orthogonal**: Code can be thread-safe but not reentrancy-safe, and vice versa.
- Consider reentrancy when designing APIs that may be called from callbacks, event handlers, or recursive contexts.

### 4. **Exception handling in Tasks vs Threads**

**Short definition**

- **Exception handling in Tasks**:
  - Exceptions thrown in `Task`-based code are **captured and stored** in the `Task` object.
  - Exceptions are **not thrown immediately**; they are thrown when you `await` the task or access `.Result`.
  - `AggregateException` may wrap multiple exceptions from parallel operations.
  - Unobserved task exceptions can cause process crashes in some .NET versions (though this behavior has changed over time).

- **Exception handling in Threads**:
  - Exceptions thrown in thread procedures are **not automatically captured**.
  - Unhandled exceptions in threads cause the **thread to terminate** and may crash the process.
  - You must manually catch exceptions in thread procedures and handle them appropriately.

**When these matter**

- **Task exception handling** matters when:
  - You use `async`/`await`, `Task.Run`, `Parallel.For`, or other Task-based APIs.
  - You need to handle exceptions from asynchronous or parallel operations.
  - You compose multiple tasks with `Task.WhenAll`, `Task.WhenAny`.

- **Thread exception handling** matters when:
  - You create `Thread` objects directly (rare in modern .NET).
  - You need to handle exceptions in thread procedures manually.

**Trade-offs**

- **Task exception handling**:
  - **Pros**:
    - **Automatic capture**: Exceptions are captured and stored in the Task.
    - **Deferred throwing**: Exceptions are thrown when you observe the task (via `await` or `.Result`).
    - **Aggregation**: Multiple exceptions can be aggregated in `AggregateException`.
    - **Composable**: Works well with `Task.WhenAll`, `Task.WhenAny`, and other combinators.
  - **Cons**:
    - **Must observe exceptions**: Unobserved task exceptions can cause issues (though behavior varies by .NET version).
    - **AggregateException wrapping**: May need to unwrap `AggregateException` to get the actual exception.

- **Thread exception handling**:
  - **Pros**:
    - **Immediate**: Exceptions are thrown immediately (if not caught).
  - **Cons**:
    - **Manual handling**: Must manually catch and handle exceptions in thread procedures.
    - **Process crashes**: Unhandled exceptions in threads can crash the process.
    - **No aggregation**: No built-in mechanism to aggregate exceptions from multiple threads.

**Common mistakes**

- **Not observing task exceptions**:
  - Creating tasks and not awaiting them or handling exceptions, leading to unobserved exceptions.
  - **Solution**: Always await tasks or use `.ContinueWith` to handle exceptions.

- **Swallowing exceptions in threads**:
  - Catching exceptions in thread procedures and not logging or handling them, hiding errors.
  - **Solution**: Log exceptions and consider how to propagate them (e.g., via callbacks, events, or shared state).

- **Not unwrapping AggregateException**:
  - Catching `AggregateException` and not unwrapping it to get the actual exception.
  - **Solution**: Use `AggregateException.Flatten()` or `GetBaseException()` to get the underlying exception.

**C# 15-style example: exception handling in Tasks vs Threads**

```csharp
// Task exception handling: Exceptions are captured in the Task.
public class TaskExceptionHandling
{
    public async Task HandleTaskExceptionAsync()
    {
        try
        {
            var task = Task.Run(() => ThrowException());
            await task.ConfigureAwait(false); // Exception is thrown here when awaited.
        }
        catch (InvalidOperationException ex)
        {
            Console.WriteLine($"Caught: {ex.Message}");
        }
    }

    private void ThrowException()
    {
        throw new InvalidOperationException("Task exception");
    }

    // Multiple exceptions: AggregateException.
    public async Task HandleMultipleExceptionsAsync()
    {
        var tasks = new[]
        {
            Task.Run(() => throw new InvalidOperationException("Error 1")),
            Task.Run(() => throw new ArgumentException("Error 2")),
            Task.Run(() => throw new NullReferenceException("Error 3"))
        };

        try
        {
            await Task.WhenAll(tasks).ConfigureAwait(false);
        }
        catch (AggregateException ex)
        {
            // AggregateException contains all exceptions.
            foreach (var innerEx in ex.InnerExceptions)
            {
                Console.WriteLine($"Exception: {innerEx.Message}");
            }
        }
    }

    // Unobserved task exception: May cause issues (behavior varies by .NET version).
    public void UnobservedTaskException()
    {
        var task = Task.Run(() => throw new Exception("Unobserved"));
        // Not awaiting or observing the task - exception may be lost or cause issues.
    }

    // Solution: Always observe tasks.
    public async Task ObserveTaskAsync()
    {
        var task = Task.Run(() => throw new Exception("Observed"));
        try
        {
            await task.ConfigureAwait(false);
        }
        catch (Exception ex)
        {
            Console.WriteLine($"Observed exception: {ex.Message}");
        }
    }
}

// Thread exception handling: Must manually catch exceptions.
public class ThreadExceptionHandling
{
    public void HandleThreadException()
    {
        var thread = new Thread(() =>
        {
            try
            {
                ThrowException();
            }
            catch (InvalidOperationException ex)
            {
                Console.WriteLine($"Caught in thread: {ex.Message}");
                // Must handle exception here - cannot propagate easily.
            }
        });

        thread.Start();
        thread.Join();
    }

    private void ThrowException()
    {
        throw new InvalidOperationException("Thread exception");
    }

    // Unhandled exception in thread: May crash the process.
    public void UnhandledThreadException()
    {
        var thread = new Thread(() =>
        {
            throw new Exception("Unhandled"); // May crash the process!
        });

        thread.Start();
        thread.Join();
    }

    // Solution: Always catch exceptions in thread procedures.
    public void SafeThreadExceptionHandling()
    {
        var exceptions = new ConcurrentQueue<Exception>();

        var threads = Enumerable.Range(0, 3)
            .Select(i => new Thread(() =>
            {
                try
                {
                    if (i == 1)
                    {
                        throw new InvalidOperationException($"Thread {i} error");
                    }
                }
                catch (Exception ex)
                {
                    exceptions.Enqueue(ex); // Collect exceptions.
                }
            }))
            .ToArray();

        foreach (var thread in threads)
        {
            thread.Start();
        }

        foreach (var thread in threads)
        {
            thread.Join();
        }

        // Process collected exceptions.
        foreach (var ex in exceptions)
        {
            Console.WriteLine($"Exception: {ex.Message}");
        }
    }
}
```

**Performance note**

- Exception handling in Tasks has minimal overhead (exceptions are captured and stored).
- Exception handling in Threads requires manual try/catch, which has the same overhead as regular exception handling.
- The main concern is **correctness**, not performance; always handle exceptions appropriately.

**Good to know**

- **Task exceptions are deferred**: They are thrown when you observe the task (via `await` or `.Result`).
- **Unobserved task exceptions**: Behavior varies by .NET version; in modern .NET, unobserved exceptions are typically logged but don't crash the process (unless you subscribe to `TaskScheduler.UnobservedTaskException`).
- **Always observe tasks**: Use `await`, `.ContinueWith`, or `.GetAwaiter().GetResult()` to observe task exceptions.
- See section 4.3 for deeper coverage of testing async and concurrent code, including exception handling.

### 5. **Exception handling in Parallel.\*** (Parallel.For / Parallel.ForEach / Parallel.Invoke)

**Short definition**

- **Exception handling in `Parallel.For` / `Parallel.ForEach` / `Parallel.Invoke`**:
  - Exceptions thrown in parallel loop bodies or invoked actions are **captured and aggregated**.
  - All exceptions are wrapped in an `AggregateException`.
  - The parallel operation may **partially complete** before exceptions are thrown (some iterations may complete, others may throw).
  - Exceptions are thrown when the parallel operation completes (or when you access results).

**When this matters**

- When you use `Parallel.For`, `Parallel.ForEach`, or `Parallel.Invoke` for CPU-bound parallel work.
- When you need to handle exceptions from parallel iterations or actions.
- When you need to know which iterations succeeded and which failed.

**Trade-offs**

- **Pros**:
  - **Automatic aggregation**: All exceptions are collected and aggregated.
  - **Partial completion**: Some iterations may complete even if others throw.
  - **Comprehensive error information**: `AggregateException` contains all exceptions from all iterations.

- **Cons**:
  - **AggregateException wrapping**: Must unwrap `AggregateException` to get individual exceptions.
  - **Partial results**: Some iterations may complete while others fail, making it harder to reason about state.
  - **No guarantee of which iterations complete**: The parallel operation may stop early or continue partially.

**Common mistakes**

- **Not handling AggregateException**:
  - Catching `Exception` instead of `AggregateException`, missing multiple exceptions.
  - **Solution**: Catch `AggregateException` and iterate over `InnerExceptions`.

- **Assuming all iterations complete**:
  - Assuming that all iterations complete successfully when some may throw exceptions.
  - **Solution**: Check `AggregateException.InnerExceptions` to see which iterations failed.

- **Not handling partial completion**:
  - Not accounting for the fact that some iterations may complete while others fail.
  - **Solution**: Design your code to handle partial completion gracefully.

**C# 15-style example: exception handling in Parallel.\***

```csharp
// Exception handling in Parallel.For.
public class ParallelExceptionHandling
{
    public void ProcessItemsParallel(int[] items)
    {
        try
        {
            Parallel.For(0, items.Length, i =>
            {
                if (items[i] < 0)
                {
                    throw new ArgumentException($"Invalid item at index {i}");
                }
                ProcessItem(items[i]);
            });
        }
        catch (AggregateException ex)
        {
            // AggregateException contains all exceptions from all iterations.
            foreach (var innerEx in ex.InnerExceptions)
            {
                Console.WriteLine($"Exception: {innerEx.Message}");
            }
        }
    }

    private void ProcessItem(int item)
    {
        // Process item.
    }

    // Handling exceptions with partial results.
    public void ProcessItemsWithPartialResults(int[] items)
    {
        var results = new ConcurrentDictionary<int, string>();
        var exceptions = new ConcurrentQueue<Exception>();

        try
        {
            Parallel.For(0, items.Length, i =>
            {
                try
                {
                    var result = ProcessItemSafely(items[i]);
                    results[i] = result;
                }
                catch (Exception ex)
                {
                    exceptions.Enqueue(ex);
                }
            });
        }
        catch (AggregateException ex)
        {
            // Additional exceptions from the parallel loop itself.
            foreach (var innerEx in ex.InnerExceptions)
            {
                exceptions.Enqueue(innerEx);
            }
        }

        // Process results and exceptions.
        Console.WriteLine($"Processed {results.Count} items successfully");
        Console.WriteLine($"Encountered {exceptions.Count} exceptions");
    }

    private string ProcessItemSafely(int item)
    {
        if (item < 0)
        {
            throw new ArgumentException($"Invalid item: {item}");
        }
        return $"Processed: {item}";
    }

    // Exception handling in Parallel.ForEach.
    public void ProcessCollectionParallel(IEnumerable<string> items)
    {
        try
        {
            Parallel.ForEach(items, item =>
            {
                if (string.IsNullOrEmpty(item))
                {
                    throw new ArgumentException("Empty item");
                }
                ProcessItem(item);
            });
        }
        catch (AggregateException ex)
        {
            foreach (var innerEx in ex.InnerExceptions)
            {
                Console.WriteLine($"Exception: {innerEx.Message}");
            }
        }
    }

    private void ProcessItem(string item)
    {
        // Process item.
    }

    // Exception handling in Parallel.Invoke.
    public void InvokeMultipleActions()
    {
        try
        {
            Parallel.Invoke(
                () => Action1(),
                () => Action2(),
                () => Action3()
            );
        }
        catch (AggregateException ex)
        {
            // AggregateException contains exceptions from all actions.
            foreach (var innerEx in ex.InnerExceptions)
            {
                Console.WriteLine($"Exception: {innerEx.Message}");
            }
        }
    }

    private void Action1()
    {
        throw new InvalidOperationException("Action1 failed");
    }

    private void Action2()
    {
        // Succeeds.
    }

    private void Action3()
    {
        throw new ArgumentException("Action3 failed");
    }
}
```

**Performance note**

- Exception handling in parallel operations has minimal overhead (exceptions are captured and aggregated).
- The main concern is **correctness**: always handle `AggregateException` to see all failures.
- Consider using `ParallelLoopState.Stop()` or `ParallelLoopState.Break()` to control loop execution when exceptions occur.

**Good to know**

- **All exceptions are aggregated**: `Parallel.For`, `Parallel.ForEach`, and `Parallel.Invoke` collect all exceptions and wrap them in `AggregateException`.
- **Partial completion is possible**: Some iterations may complete while others throw exceptions.
- **Use `AggregateException.Flatten()`**: If you have nested `AggregateException`s, use `Flatten()` to get all exceptions in a flat list.
- See section 3.2 for deeper patterns on data parallelism with Parallel and PLINQ.

### 6. **Exception handling in PLINQ**

**Short definition**

- **Exception handling in PLINQ**:
  - Exceptions thrown in PLINQ query operations are **captured and aggregated**.
  - All exceptions are wrapped in an `AggregateException`.
  - The query may **partially execute** before exceptions are thrown (some elements may be processed, others may throw).
  - Exceptions are thrown when the query is **enumerated** (e.g., when calling `ToArray()`, `ToList()`, or iterating).

**When this matters**

- When you use PLINQ (`AsParallel()`) for parallel query execution.
- When you need to handle exceptions from parallel query operations.
- When you need to know which elements were processed successfully and which failed.

**Trade-offs**

- **Pros**:
  - **Automatic aggregation**: All exceptions are collected and aggregated.
  - **Partial execution**: Some elements may be processed even if others throw.
  - **Comprehensive error information**: `AggregateException` contains all exceptions.

- **Cons**:
  - **AggregateException wrapping**: Must unwrap `AggregateException` to get individual exceptions.
  - **Deferred execution**: Exceptions are thrown during enumeration, not when the query is defined.
  - **Partial results**: Some elements may be processed while others fail.

**Common mistakes**

- **Not handling exceptions during enumeration**:
  - Defining a PLINQ query and not handling exceptions when enumerating it.
  - **Solution**: Wrap enumeration (e.g., `ToArray()`, `ToList()`, `foreach`) in try/catch.

- **Assuming all elements are processed**:
  - Assuming that all elements are processed successfully when some may throw exceptions.
  - **Solution**: Check `AggregateException.InnerExceptions` to see which elements failed.

- **Not understanding deferred execution**:
  - Expecting exceptions to be thrown when the query is defined, not when it's enumerated.
  - **Solution**: Understand that PLINQ queries are deferred; exceptions are thrown during enumeration.

**C# 15-style example: exception handling in PLINQ**

```csharp
// Exception handling in PLINQ.
public class PLINQExceptionHandling
{
    public void ProcessNumbersPLINQ(int[] numbers)
    {
        try
        {
            var results = numbers
                .AsParallel()
                .Select(n =>
                {
                    if (n < 0)
                    {
                        throw new ArgumentException($"Invalid number: {n}");
                    }
                    return n * n;
                })
                .ToArray(); // Exception is thrown here during enumeration.

            foreach (var result in results)
            {
                Console.WriteLine(result);
            }
        }
        catch (AggregateException ex)
        {
            // AggregateException contains all exceptions from all elements.
            foreach (var innerEx in ex.InnerExceptions)
            {
                Console.WriteLine($"Exception: {innerEx.Message}");
            }
        }
    }

    // Handling exceptions with partial results.
    public void ProcessNumbersWithPartialResults(int[] numbers)
    {
        var results = new ConcurrentBag<int>();
        var exceptions = new ConcurrentQueue<Exception>();

        try
        {
            var processed = numbers
                .AsParallel()
                .Select(n =>
                {
                    try
                    {
                        if (n < 0)
                        {
                            throw new ArgumentException($"Invalid number: {n}");
                        }
                        return n * n;
                    }
                    catch (Exception ex)
                    {
                        exceptions.Enqueue(ex);
                        return -1; // Sentinel value for failed items.
                    }
                })
                .Where(r => r >= 0) // Filter out failed items.
                .ToArray();

            foreach (var result in processed)
            {
                results.Add(result);
            }
        }
        catch (AggregateException ex)
        {
            // Additional exceptions from the PLINQ query itself.
            foreach (var innerEx in ex.InnerExceptions)
            {
                exceptions.Enqueue(innerEx);
            }
        }

        Console.WriteLine($"Processed {results.Count} numbers successfully");
        Console.WriteLine($"Encountered {exceptions.Count} exceptions");
    }

    // Exception handling with deferred execution.
    public void ProcessNumbersDeferred(int[] numbers)
    {
        // Query is defined, but not executed yet.
        var query = numbers
            .AsParallel()
            .Select(n =>
            {
                if (n < 0)
                {
                    throw new ArgumentException($"Invalid number: {n}");
                }
                return n * n;
            });

        // Exception is thrown here when query is enumerated.
        try
        {
            foreach (var result in query) // Enumeration triggers execution.
            {
                Console.WriteLine(result);
            }
        }
        catch (AggregateException ex)
        {
            foreach (var innerEx in ex.InnerExceptions)
            {
                Console.WriteLine($"Exception: {innerEx.Message}");
            }
        }
    }

    // Using AggregateException.Flatten() for nested exceptions.
    public void ProcessNumbersFlattened(int[] numbers)
    {
        try
        {
            var results = numbers
                .AsParallel()
                .Select(n =>
                {
                    try
                    {
                        return ProcessNumber(n);
                    }
                    catch (Exception ex)
                    {
                        throw new InvalidOperationException($"Failed to process {n}", ex); // Nested exception.
                    }
                })
                .ToArray();
        }
        catch (AggregateException ex)
        {
            // Flatten nested AggregateExceptions.
            var flattened = ex.Flatten();
            foreach (var innerEx in flattened.InnerExceptions)
            {
                Console.WriteLine($"Exception: {innerEx.Message}");
            }
        }
    }

    private int ProcessNumber(int n)
    {
        if (n < 0)
        {
            throw new ArgumentException($"Invalid number: {n}");
        }
        return n * n;
    }
}
```

**Performance note**

- Exception handling in PLINQ has minimal overhead (exceptions are captured and aggregated).
- The main concern is **correctness**: always handle `AggregateException` when enumerating PLINQ queries.
- Consider using `Where` to filter out failed items if you want to continue processing successful ones.

**Good to know**

- **Exceptions are deferred**: PLINQ queries are deferred; exceptions are thrown during enumeration, not when the query is defined.
- **All exceptions are aggregated**: PLINQ collects all exceptions and wraps them in `AggregateException`.
- **Use `AggregateException.Flatten()`**: If you have nested `AggregateException`s, use `Flatten()` to get all exceptions in a flat list.
- **Partial execution is possible**: Some elements may be processed while others throw exceptions.
- See section 3.2 for deeper patterns on PLINQ usage and tuning.
