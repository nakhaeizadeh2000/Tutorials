> **Reminder**: `Task` is the compositional abstraction; the scheduler decides **where** it runs. For Thread Pool internals and starvation mechanics, see **section 2.1**.

### 1. **Default TaskScheduler and its relationship with the Thread Pool**

**Short definition**

- `TaskScheduler` is the runtime abstraction that decides **how tasks are queued and executed**.
- `TaskScheduler.Default` schedules tasks onto the **.NET Thread Pool**.
- Most application code should use the default scheduler implicitly (via `Task.Run`, `await`, `Parallel.*`, etc.).

**What runs on `TaskScheduler.Default`**

- `Task.Run(...)` always queues to the default scheduler (Thread Pool).
- In server/console apps, most `await` continuations resume on the Thread Pool (unless a special context is involved).

**Common misconception**

- `TaskScheduler` is not “a thread”. It is a *policy / routing layer* to decide where work runs.

**Good to know**

- `TaskScheduler.Current` depends on where you are executing. Inside a task scheduled on a custom scheduler, `Current` may not equal `Default`.

### 2. **TaskCreationOptions and TaskContinuationOptions impact on scheduling**

**Why these options matter**

- They influence:
  - continuation placement and behavior
  - parent/child attachment
  - whether work should be treated as long-running
  - whether continuations are executed inline vs queued

**Modern guidance (C# 15 / .NET 9+)**

- Prefer:
  - `async`/`await` for continuations
  - `Task.Run` for CPU-bound offloading
  - `Task.WhenAll` / `Task.WhenAny` for composition
- Avoid as a default:
  - `Task.Factory.StartNew` (sharp edges)
  - `Task.ContinueWith` (harder semantics; see section 1.3)

**`Task.Factory.StartNew` is a common footgun**

- It defaults to `TaskScheduler.Current` (not always Thread Pool).
- With `async` delegates, it can easily produce `Task<Task>` (nested tasks).
- It has many knobs that are easy to misconfigure and hard to review.

**Runnable example: `StartNew` pitfalls vs modern alternatives**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

static class StartNewPitfalls
{
    public static async Task DemoAsync(CancellationToken ct = default)
    {
        // Preferred for CPU-bound work.
        await Task.Run(CpuWork, ct).ConfigureAwait(false);

        // Footgun: StartNew + async lambda -> Task<Task>.
        Task<Task> nested = Task.Factory.StartNew(async () =>
        {
            await Task.Delay(10, ct).ConfigureAwait(false);
        }, ct);

        await nested.Unwrap().ConfigureAwait(false);

        // If you truly must use StartNew, specify scheduler explicitly.
        await Task.Factory.StartNew(
            CpuWork,
            ct,
            TaskCreationOptions.DenyChildAttach,
            TaskScheduler.Default).ConfigureAwait(false);
    }

    private static void CpuWork() => _ = Environment.TickCount;
}
```

**About continuation options**

- In modern code, the biggest “option” decision is usually not `TaskContinuationOptions`, but rather:
  - whether you capture context (`ConfigureAwait`) (see section 2.5 and 1.6)
  - whether you block vs await (see section 1.1 and 2.1)

**Performance note**

- Options that encourage inline execution can reduce scheduling overhead but can increase tail latency if you accidentally run heavy continuations on an important thread (UI thread, request thread). Defaults are usually correct unless you’re writing low-level libraries and you’ve measured.

### 3. **Long-running tasks and dedicated threads**

**What “long-running” means**

- Work that occupies a thread for a **long time** (seconds/minutes), often CPU-bound or blocking.

**Why it’s risky on the Thread Pool**

- Thread Pool threads are shared by the whole process. If long-running work consumes them, you reduce capacity for:
  - request handling
  - timers
  - async continuations
- This can cause **ThreadPool starvation** and latency spikes (see section 2.1).

**Preferred patterns**

- For long CPU work:
  - Use bounded parallelism (`ParallelOptions.MaxDegreeOfParallelism`)
  - Move to a background worker with explicit throttling/queues (see section 3.6 / 5.3)
- `TaskCreationOptions.LongRunning`:
  - hints the runtime to consider a dedicated thread
  - use sparingly; it’s an infrastructure choice, not a default pattern

**Runnable example: bounded CPU parallelism vs LongRunning**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

static class LongRunningDemo
{
    public static void BoundedParallelWork(int[] data, CancellationToken ct = default)
    {
        Parallel.For(0, data.Length, new ParallelOptions
        {
            CancellationToken = ct,
            MaxDegreeOfParallelism = Environment.ProcessorCount
        }, i =>
        {
            data[i] = data[i] * data[i];
        });
    }

    public static Task StartLongRunningLoopAsync(CancellationToken ct)
        => Task.Factory.StartNew(
            () => BusyLoop(ct),
            ct,
            TaskCreationOptions.LongRunning,
            TaskScheduler.Default);

    private static void BusyLoop(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            Thread.SpinWait(10_000);
        }
    }
}
```

### 4. **Custom TaskScheduler implementations (e.g., single-threaded, limited-concurrency)**

**When custom scheduling is justified**

- You need strict **single-threaded** execution (state confinement, ordering).
- You need an explicit **limited-concurrency** executor for a subsystem.
- You need deterministic scheduling in tests.

**Before writing a `TaskScheduler`, consider these first**

- `SemaphoreSlim` concurrency limiter (section 3.5)
- bounded `Channel<T>` pipelines / mailbox (section 3.3 and 3.7)
- TPL Dataflow blocks with bounded capacity (section 3.3)

**Example: single-threaded executor using `Channel<T>` (often better than subclassing `TaskScheduler`)**

```csharp
using System;
using System.Threading;
using System.Threading.Channels;
using System.Threading.Tasks;

public sealed class SingleThreadExecutor : IAsyncDisposable
{
    private readonly Channel<Func<Task>> _queue = Channel.CreateUnbounded<Func<Task>>(
        new UnboundedChannelOptions { SingleReader = true, SingleWriter = false });

    private readonly CancellationTokenSource _cts = new();
    private readonly Task _runner;

    public SingleThreadExecutor() => _runner = Task.Run(RunAsync);

    public ValueTask EnqueueAsync(Func<Task> work, CancellationToken ct = default)
        => _queue.Writer.WriteAsync(work, ct);

    private async Task RunAsync()
    {
        try
        {
            await foreach (var work in _queue.Reader.ReadAllAsync(_cts.Token).ConfigureAwait(false))
            {
                await work().ConfigureAwait(false);
            }
        }
        catch (OperationCanceledException) when (_cts.IsCancellationRequested) { }
    }

    public async ValueTask DisposeAsync()
    {
        _cts.Cancel();
        _queue.Writer.TryComplete();
        await _runner.ConfigureAwait(false);
        _cts.Dispose();
    }
}
```

**Performance note**

- State confinement (single-threaded execution) can remove locks and often wins under high contention.

### 5. **Interaction with SynchronizationContext-aware code**

**Key idea**

- `TaskScheduler` affects tasks you schedule explicitly.
- `SynchronizationContext` affects **async continuations** and any API that captures context.

**UI (frontend)**

- UI apps (WinForms/WPF/MAUI) have a UI `SynchronizationContext`.
- `TaskScheduler.FromCurrentSynchronizationContext()` can schedule tasks to the UI thread, but most UI code should use `await` and rely on capture by default.
- For library code, prefer context-agnostic continuations (`ConfigureAwait(false)`). See section **2.3** and **1.6**.

**ASP.NET Core**

- ASP.NET Core typically has **no** `SynchronizationContext`; continuations resume on the Thread Pool. See section **2.3**.

**Common mistake**

- Mixing `ContinueWith`/`StartNew` with UI context + blocking waits (`.Result`, `.Wait()`) → deadlocks and frozen UI.
- Fix: prefer `await`, avoid blocking, and use `ConfigureAwait(false)` in libraries.
