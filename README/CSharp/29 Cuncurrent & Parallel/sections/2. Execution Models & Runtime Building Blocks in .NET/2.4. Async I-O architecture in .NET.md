### 1. **Kernel-level async I/O primitives (I/O completion ports, etc.)**

**Big idea**

- “True async I/O” in .NET is usually **kernel-assisted**:
  - The OS starts an I/O operation.
  - The thread returns to do other work.
  - The OS signals completion later.
  - .NET schedules a continuation to process the result.

**OS primitives (high level)**

- **Windows**: I/O Completion Ports (**IOCP**) are the core scalability primitive.
- **Linux**: async I/O is typically built on readiness/completion mechanisms such as **epoll** (for sockets) and platform-specific async file I/O capabilities; the runtime abstracts this.
- **macOS**: uses different kernel mechanisms (kqueue, etc.); again, the runtime abstracts it.

**Why this matters**

- Kernel async I/O allows a small number of threads to manage **many** concurrent operations without blocking.
- That’s the foundation of high-concurrency servers.

**Mentor emphasis**

- The “async” in `ReadAsync`/`SendAsync` is valuable because it **does not block a thread** while waiting.
- If your “async” is implemented by “run sync work on a background thread”, you didn’t gain scalability—you just moved the blocking.

### 2. **How async file and network operations integrate with Tasks**

**Task completion lifecycle**

- In Task-based async APIs, the runtime returns a `Task`/`ValueTask` representing the pending operation.
- When the OS signals completion, .NET transitions the task to:
  - **RanToCompletion** with a result
  - **Faulted** with an exception
  - **Canceled** if cancellation wins the race (cooperatively)

**Where continuations run**

- Continuations generally run on:
  - a captured `SynchronizationContext` (UI apps), or
  - the Thread Pool (server/console), or
  - inline, if already completed and safe
See **section 2.5** for detailed scheduling semantics and **section 2.3** for app model differences.

**Modern .NET I/O APIs**

- Prefer:
  - `Stream.ReadAsync/WriteAsync` (Memory/ReadOnlyMemory overloads)
  - `File.ReadAllTextAsync`, `FileStream` with async methods
  - `Socket.ReceiveAsync/SendAsync` and `NetworkStream.ReadAsync/WriteAsync`
  - `HttpClient.SendAsync/GetAsync/GetStringAsync`
  - database providers’ `*Async` APIs (e.g., `ExecuteReaderAsync`)

**Minimal example: true async I/O**

```csharp
using System;
using System.IO;
using System.Threading;
using System.Threading.Tasks;

static class TrueAsyncIo
{
    public static async Task<long> CopyAsync(string src, string dst, CancellationToken ct = default)
    {
        await using var input = new FileStream(
            src, FileMode.Open, FileAccess.Read, FileShare.Read,
            bufferSize: 64 * 1024, useAsync: true);

        await using var output = new FileStream(
            dst, FileMode.Create, FileAccess.Write, FileShare.None,
            bufferSize: 64 * 1024, useAsync: true);

        await input.CopyToAsync(output, bufferSize: 64 * 1024, ct).ConfigureAwait(false);
        return output.Length;
    }
}
```

**Performance note**

- Prefer `Stream` APIs that accept `Memory<byte>` / `ReadOnlyMemory<byte>` to reduce allocations.
- Use reasonable buffer sizes (often 16–128 KiB). Measure for your workload.

### 3. **Difference between async I/O and background-thread I/O**

**Definitions**

- **Async I/O**: OS-managed async operation; thread is not blocked while waiting.
- **Background-thread I/O**: you call a synchronous I/O API on a Thread Pool thread (e.g., `Task.Run(() => File.ReadAllText(...))`), which **blocks** that thread.

**Why background-thread I/O is usually a trap**

- It scales poorly: each in-flight I/O consumes a thread.
- Under load, blocked threads cause **ThreadPool starvation** (see section 2.1).
- It increases memory usage (more threads) and CPU overhead (context switching).

**When background-thread I/O can be acceptable**

- When no true async API exists (rare in modern .NET).
- When you must wrap a legacy synchronous API that you can’t replace, and the call volume is low and bounded.
- Even then: **throttle** it aggressively (SemaphoreSlim) to avoid starving the Thread Pool.

**Runnable example: the anti-pattern and the fix**

```csharp
using System.IO;
using System.Threading;
using System.Threading.Tasks;

static class BackgroundThreadIoTrap
{
    // BAD: blocks ThreadPool thread.
    public static Task<string> ReadAllTextWrongAsync(string path, CancellationToken ct = default)
        => Task.Run(() => File.ReadAllText(path), ct);

    // GOOD: true async I/O.
    public static Task<string> ReadAllTextAsync(string path, CancellationToken ct = default)
        => File.ReadAllTextAsync(path, ct);
}
```

**Good to know**

- Async I/O frees threads while waiting; background-thread I/O consumes threads while waiting.
- “It uses async/await” does *not* guarantee it’s true async I/O. Inspect the underlying API.

### 4. **Scalability benefits of async I/O for high-concurrency servers**

**Why async scales**

- In server workloads, time is often dominated by waiting:
  - network latency
  - database round-trips
  - disk I/O
- Async lets one thread “own” many concurrent requests by not blocking during waits.

**What improves**

- **Throughput**: more requests handled with the same CPU.
- **Latency**: fewer requests stuck behind blocked threads.
- **Resource usage**: fewer threads → less memory and less context switching.

**Mentor emphasis**

- The biggest scalability gains come from “async all the way down”:
  - async HTTP
  - async DB
  - async file/network I/O
  - no `.Result` / `.Wait()`

**Good to know**

- Async doesn’t reduce total *work*; it reduces time wasted by blocked threads. Your CPU time still matters.

### 5. **Common pitfalls: sync-over-async and thread-pool exhaustion**

**Pitfall: sync-over-async**

- Doing something like:
  - `SomeAsync().Result`
  - `SomeAsync().Wait()`
  - `Task.WaitAll(...)`
in request-handling or UI code.

**Why it’s dangerous**

- UI: can deadlock (see section 2.3).
- Server: can cause Thread Pool starvation and massive latency spikes (see section 2.1).

**Pitfall: unbounded fan-out**

- Launching thousands of operations at once with `WhenAll` without any limits.
- Even if operations are async, you can overload:
  - remote services
  - sockets
  - connection pools
  - memory (buffers)

**Fix: add backpressure/throttling**

- `SemaphoreSlim` concurrency limits (section 3.5)
- bounded `Channel<T>` or Dataflow blocks (section 3.3)

**Minimal example: throttling true async I/O**

```csharp
using System;
using System.Net.Http;
using System.Threading;
using System.Threading.Tasks;

static class ThrottledHttp
{
    public static async Task<int> GetTotalBytesAsync(Uri[] uris, int maxConcurrency, CancellationToken ct = default)
    {
        using var http = new HttpClient();
        using var gate = new SemaphoreSlim(maxConcurrency, maxConcurrency);

        var tasks = new Task<int>[uris.Length];
        for (int i = 0; i < uris.Length; i++)
        {
            var uri = uris[i];
            tasks[i] = OneAsync(http, gate, uri, ct);
        }

        var sizes = await Task.WhenAll(tasks).ConfigureAwait(false);
        int total = 0;
        foreach (var s in sizes) total += s;
        return total;
    }

    private static async Task<int> OneAsync(HttpClient http, SemaphoreSlim gate, Uri uri, CancellationToken ct)
    {
        await gate.WaitAsync(ct).ConfigureAwait(false);
        try
        {
            var data = await http.GetByteArrayAsync(uri, ct).ConfigureAwait(false);
            return data.Length;
        }
        finally
        {
            gate.Release();
        }
    }
}
```

**Performance note**

- Thread Pool exhaustion is often a symptom of blocking or unbounded concurrency. Fix the design before “tuning” the Thread Pool.
