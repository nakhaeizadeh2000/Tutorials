### 1. **Producer/Consumer with BlockingCollection and concurrent queues**

**The pattern**

- Producers enqueue work items.
- Consumers dequeue and process them, typically on background threads.
- The queue provides decoupling and buffering.

**Modern guidance**

- `BlockingCollection<T>` is a classic option (works, but is fundamentally *blocking*).
- In modern async-heavy code, prefer:
  - `Channel<T>` (async-friendly, high throughput, built-in backpressure)
  - TPL Dataflow (richer pipeline blocks)

**When `BlockingCollection<T>` is still fine**

- Simple CPU-bound worker pools where blocking is acceptable and you want minimal dependencies.
- Legacy systems already built around blocking threads.

**Trade-offs**

- **BlockingCollection**:
  - **Pros**: simple; bounded capacity; `GetConsumingEnumerable`.
  - **Cons**: consumers block threads while waiting → can contribute to Thread Pool starvation if misused.
- **ConcurrentQueue / ConcurrentBag**:
  - **Pros**: lock-free-ish thread-safe collections.
  - **Cons**: no built-in blocking/backpressure; you must build signaling yourself.

**Common mistakes**

- Using unbounded queues without any backpressure → memory growth and latency collapse.
- Having consumers do synchronous I/O (blocking threads) at scale.

**Runnable example: bounded `BlockingCollection` worker**

```csharp
using System;
using System.Collections.Concurrent;
using System.Threading;
using System.Threading.Tasks;

static class BlockingCollectionDemo
{
    public static Task RunAsync(CancellationToken ct)
    {
        using var queue = new BlockingCollection<int>(boundedCapacity: 100);

        var producer = Task.Run(() =>
        {
            for (int i = 0; i < 1_000; i++)
            {
                ct.ThrowIfCancellationRequested();
                queue.Add(i, ct);
            }
            queue.CompleteAdding();
        }, ct);

        var consumer = Task.Run(() =>
        {
            foreach (var item in queue.GetConsumingEnumerable(ct))
            {
                // CPU-bound work.
                _ = item * item;
            }
        }, ct);

        return Task.WhenAll(producer, consumer);
    }
}
```

**Performance note**

- This pattern uses blocking waits; for I/O-heavy pipelines or very high concurrency, Channels/Dataflow scale better.

### 2. **Bounded vs unbounded Channels and backpressure**

**What `Channel<T>` is**

- `Channel<T>` is a high-performance async queue with:
  - `Writer` for producers
  - `Reader` for consumers
  - async `WriteAsync` / `ReadAsync` / `ReadAllAsync`

**Bounded vs unbounded**

- **Unbounded**:
  - Producers never wait.
  - Risk: unbounded memory growth under load.
- **Bounded**:
  - Capacity is limited.
  - Provides **backpressure**: producers slow down when consumers can’t keep up.

**Backpressure (why you want it)**

- It converts “unbounded memory growth + timeouts” into “controlled throughput”.
- It protects your system and downstream dependencies.

**Bounded channel full modes**

- `Wait`: producer waits until space is available (most common).
- `DropOldest` / `DropNewest` / `DropWrite`: load shedding strategies (useful for telemetry/UI updates).

**Runnable example: bounded channel with single consumer**

```csharp
using System;
using System.Threading;
using System.Threading.Channels;
using System.Threading.Tasks;

static class ChannelDemo
{
    public static async Task RunAsync(CancellationToken ct)
    {
        var channel = Channel.CreateBounded<int>(new BoundedChannelOptions(100)
        {
            SingleReader = true,
            SingleWriter = false,
            FullMode = BoundedChannelFullMode.Wait
        });

        var consumer = Task.Run(async () =>
        {
            await foreach (var item in channel.Reader.ReadAllAsync(ct).ConfigureAwait(false))
            {
                _ = item * item;
            }
        }, ct);

        for (int i = 0; i < 1_000; i++)
            await channel.Writer.WriteAsync(i, ct).ConfigureAwait(false);

        channel.Writer.Complete();
        await consumer.ConfigureAwait(false);
    }
}
```

**Good to know**

- Use `SingleReader` / `SingleWriter` when true: it enables internal optimizations and reduces overhead.

### 3. **Basic TPL Dataflow blocks (BufferBlock, TransformBlock, ActionBlock)**

**What Dataflow is**

- TPL Dataflow is a library for building **composable pipeline blocks** with:
  - built-in parallelism (`MaxDegreeOfParallelism`)
  - bounded capacity and backpressure
  - linking blocks with completion propagation

**When to use**

- Multi-stage pipelines with transformation steps.
- You want built-in parallelism per stage.
- You want bounded buffering and clear composition.

**Trade-offs**

- **Pros**: rich model; easier multi-stage orchestration; good backpressure story.
- **Cons**: extra dependency (`System.Threading.Tasks.Dataflow`); more concepts than Channels.

**Runnable example: Transform + Action with bounded capacity**

```csharp
// Requires NuGet: System.Threading.Tasks.Dataflow
using System;
using System.Threading.Tasks;
using System.Threading.Tasks.Dataflow;

static class DataflowBasics
{
    public static async Task RunAsync()
    {
        var transform = new TransformBlock<int, int>(x => x * x,
            new ExecutionDataflowBlockOptions
            {
                MaxDegreeOfParallelism = Environment.ProcessorCount,
                BoundedCapacity = 128
            });

        var sink = new ActionBlock<int>(x => Console.WriteLine(x),
            new ExecutionDataflowBlockOptions
            {
                MaxDegreeOfParallelism = 1,
                BoundedCapacity = 128
            });

        transform.LinkTo(sink, new DataflowLinkOptions { PropagateCompletion = true });

        for (int i = 0; i < 20; i++)
            await transform.SendAsync(i).ConfigureAwait(false);

        transform.Complete();
        await sink.Completion.ConfigureAwait(false);
    }
}
```

**Performance note**

- Dataflow blocks can be extremely efficient, but “too many blocks” and tiny message sizes still create overhead. Measure.

### 4. **Building multi-stage pipelines (fan-out/fan-in)**

**Pipeline anatomy**

- Stage A reads input, transforms, pushes to stage B.
- Stages can have:
  - different concurrency limits
  - bounded buffers between them
  - distinct failure/cancellation behavior

**Fan-out / fan-in**

- **Fan-out**: distribute one stream of work across multiple workers (parallel processing).
- **Fan-in**: merge worker results into one downstream consumer.

**Channels approach**

- Often modeled as:
  - 1 input channel
  - N worker tasks reading from it
  - 1 output channel (optional)

**Dataflow approach**

- Use `TransformBlock` with `MaxDegreeOfParallelism` for fan-out.
- Use linking and bounded capacities for backpressure.

**Common mistakes**

- Unbounded fan-out that overwhelms downstream dependencies (DB, HTTP, disk).
- Not propagating cancellation properly, leaving background work running after shutdown.
- Losing errors: exceptions in background workers that aren’t observed/logged.

**Runnable example: channel-based fan-out with bounded concurrency**

```csharp
using System;
using System.Threading;
using System.Threading.Channels;
using System.Threading.Tasks;

static class FanOutPipeline
{
    public static async Task RunAsync(int workerCount, CancellationToken ct)
    {
        var input = Channel.CreateBounded<int>(new BoundedChannelOptions(256)
        {
            SingleWriter = true,
            SingleReader = false,
            FullMode = BoundedChannelFullMode.Wait
        });

        Task[] workers = new Task[workerCount];
        for (int i = 0; i < workerCount; i++)
        {
            workers[i] = Task.Run(async () =>
            {
                await foreach (var item in input.Reader.ReadAllAsync(ct).ConfigureAwait(false))
                {
                    // CPU work (placeholder).
                    _ = item * item;
                }
            }, ct);
        }

        for (int i = 0; i < 10_000; i++)
            await input.Writer.WriteAsync(i, ct).ConfigureAwait(false);

        input.Writer.Complete();
        await Task.WhenAll(workers).ConfigureAwait(false);
    }
}
```

**Performance note**

- The bounded channel is the backpressure mechanism; the number of workers is the concurrency limit. Tune both based on CPU utilization and downstream capacity.

### 5. **Choosing between Channels, Dataflow, and custom queues**

**Pick Channels when**

- You need a fast async queue and you’re comfortable writing pipeline orchestration explicitly.
- Your topology is simple: producer/consumer, fan-out with worker tasks, single-writer mailbox.

**Pick Dataflow when**

- You want built-in pipeline blocks and clear stage-by-stage configuration.
- You need richer blocks (batching, join, broadcast, etc.) and completion propagation.

**Pick BlockingCollection when**

- You’re in a blocking/threaded design already and don’t want async.
- The concurrency level is modest and well-bounded.

**Avoid “custom queue + manual signaling” unless**

- You have measured a bottleneck and need custom behavior not offered by Channels/Dataflow.
- You can invest in correctness (memory ordering, cancellation, completion, backpressure).

**Mentor emphasis**

- Most concurrency bugs come from “clever custom queues”. Prefer well-tested primitives; spend your complexity budget on business logic.
