### 1. **Limiting concurrency with SemaphoreSlim**

**Core idea**

- `SemaphoreSlim` limits **how many concurrent operations** can enter a region of code.
- It’s async-friendly (`WaitAsync`) and much lighter than OS-level `Semaphore`/`Mutex`.

**When to use**

- To protect a **limited resource**:
  - DB connections
  - remote service rate limits
  - CPU-intensive algorithm that shouldn’t saturate all cores
- To control fan-out concurrency in `Task.WhenAll` patterns (see **3.1** and **2.1**).

**Pattern**

- Always pair `WaitAsync` with `Release` in a `try/finally`.
- Use one `SemaphoreSlim` per “resource pool” you are limiting.

**Runnable example: bounded HTTP concurrency**

```csharp
using System;
using System.Net.Http;
using System.Threading;
using System.Threading.Tasks;

static class HttpThrottling
{
    public static async Task<int[]> DownloadSizesAsync(
        Uri[] uris,
        int maxConcurrency,
        CancellationToken ct = default)
    {
        using var http = new HttpClient();
        using var gate = new SemaphoreSlim(maxConcurrency, maxConcurrency);

        var tasks = new Task<int>[uris.Length];
        for (int i = 0; i < uris.Length; i++)
        {
            var uri = uris[i];
            tasks[i] = DownloadOneAsync(http, gate, uri, ct);
        }

        return await Task.WhenAll(tasks).ConfigureAwait(false);
    }

    private static async Task<int> DownloadOneAsync(
        HttpClient http,
        SemaphoreSlim gate,
        Uri uri,
        CancellationToken ct)
    {
        await gate.WaitAsync(ct).ConfigureAwait(false);
        try
        {
            var data = await http.GetByteArrayAsync(uri, ct).ConfigureAwait(false);
            return data.Length;
        }
        finally
        {
            gate.Release();
        }
    }
}
```

**Performance note**

- Correct throttling often **increases** throughput and stability by avoiding overload and Thread Pool starvation.

### 2. **Using CancellationToken effectively (propagation, linked tokens)**

**Key rules**

- Pass a `CancellationToken` parameter on async methods that can be canceled.
- Do **not** store tokens globally; treat them as **per-operation** signals.
- Flow tokens downwards to all async calls that support it.

**Propagation**

- Each layer accepts a token and passes it further:

```csharp
public Task<User> GetUserAsync(Guid id, CancellationToken ct = default)
    => _userRepository.GetByIdAsync(id, ct);
```

**Linked tokens**

- Combine multiple cancellation sources:
  - request lifetime
  - longer-running operation timeout
  - manual cancellation

```csharp
using var cts = CancellationTokenSource.CreateLinkedTokenSource(requestToken, manualToken);
cts.CancelAfter(TimeSpan.FromSeconds(5));
await DoWorkAsync(cts.Token);
```

**Common mistakes**

- Ignoring tokens at the lower layers (only top-level honors them).
- Cancelling without observing `OperationCanceledException` (treating it as an error instead of a signal).

**Mentor emphasis**

- Cancellation is part of your API contract. Design with it from the start; bolting it on later is harder.

### 3. **Timeouts and cancellation scopes**

**Why timeouts matter**

- They bound the time spent on:
  - remote calls that might hang or be slow
  - complex workflows that shouldn’t run indefinitely
- They prevent “zombie” work eating resources after the caller no longer cares.

**Patterns**

- Use `CancellationTokenSource.CancelAfter` to create **scoped timeouts**:

```csharp
public static async Task<T> WithTimeoutAsync<T>(
    Func<CancellationToken, Task<T>> operation,
    TimeSpan timeout,
    CancellationToken outerToken = default)
{
    using var cts = CancellationTokenSource.CreateLinkedTokenSource(outerToken);
    cts.CancelAfter(timeout);
    return await operation(cts.Token).ConfigureAwait(false);
}
```

- Prefer scoped timeouts over “global static timeouts” sprinkled across code; it keeps the policy local and testable.

**Common mistakes**

- Applying multiple unrelated timeouts on the same call stack, causing surprising cancellations.
- Treating timeouts as generic exceptions rather than a distinct, expected condition.

**Good to know**

- Many .NET APIs have built-in timeout mechanisms (e.g., `HttpClient.Timeout`). Prefer those when they model your intent, but be aware they may apply to the entire request, not just a portion of your workflow.

### 4. **Batching vs per-item processing for throughput**

**Motivation**

- Fixed per-operation overhead (network, syscalls, locks, allocations) dominates small operations.
- Batching many small items into one larger operation improves throughput dramatically.

**Examples**

- DB: bulk insert vs single-row insert.
- HTTP: batch API endpoints vs per-item endpoints.
- In-memory: process 100 items per lock acquisition instead of 1.

**Trade-offs**

- **Batching pros**:
  - better throughput
  - fewer syscalls / round-trips
  - reduced contention
- **Batching cons**:
  - higher per-batch latency
  - more complex error handling (partial failures)
  - memory usage for buffering

**Runnable example: simple in-memory batching**

```csharp
using System;
using System.Collections.Generic;
using System.Linq;
using System.Threading;
using System.Threading.Channels;
using System.Threading.Tasks;

static class BatchingDemo
{
    public static async Task RunAsync(int batchSize, CancellationToken ct = default)
    {
        var channel = Channel.CreateUnbounded<int>(new UnboundedChannelOptions
        {
            SingleReader = true,
            SingleWriter = false
        });

        // Producer.
        _ = Task.Run(async () =>
        {
            for (int i = 0; i < 1000; i++)
                await channel.Writer.WriteAsync(i, ct).ConfigureAwait(false);

            channel.Writer.Complete();
        }, ct);

        // Consumer with batching.
        var batch = new List<int>(batchSize);

        await foreach (var item in channel.Reader.ReadAllAsync(ct).ConfigureAwait(false))
        {
            batch.Add(item);
            if (batch.Count >= batchSize)
            {
                ProcessBatch(batch);
                batch.Clear();
            }
        }

        if (batch.Count > 0)
            ProcessBatch(batch);
    }

    private static void ProcessBatch(List<int> items)
    {
        // Example: process a batch under one lock or operation.
        int sum = items.Sum();
        _ = sum;
    }
}
```

**Performance note**

- Always measure: the “right” batch size depends on:
  - workload characteristics
  - downstream limits
  - acceptable latency

### 5. **Graceful shutdown in servers and background services**

**What “graceful” means**

- Stop accepting new work.
- Let in-flight work finish (with timeouts/cancellation).
- Persist critical state.
- Release resources (connections, files, etc.).

**Patterns in ASP.NET Core / generic host**

- Use `IHostedService` / `BackgroundService` for long-running work.
- Observe the host’s `CancellationToken` to know when shutdown is requested.
- Combine host token with per-operation tokens.

**Minimal example: `BackgroundService` with cooperative shutdown**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;
using Microsoft.Extensions.Hosting;

public sealed class WorkerService : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await DoWorkAsync(stoppingToken).ConfigureAwait(false);
        }
    }

    private static async Task DoWorkAsync(CancellationToken ct)
    {
        // Simulate work.
        await Task.Delay(TimeSpan.FromSeconds(1), ct).ConfigureAwait(false);
    }
}
```

**Key steps for graceful shutdown**

- **Stop intake**:
  - stop reading from Channels/queues
  - stop accepting new HTTP requests (handled by host)
- **Drain pipelines**:
  - let consumers finish processing buffered items
  - apply a global timeout if needed
- **Cancel remaining work**:
  - cancel tokens so long-running operations can bail out

**Common mistakes**

- Killing the process without giving background work a chance to complete.
- Not wiring host cancellation into background loops (infinite loops ignoring `stoppingToken`).
- Using `Thread.Abort`-style patterns (not available/appropriate in modern .NET).

**Mentor emphasis**

- Design for graceful shutdown from the start:
  - every loop checks a token
  - every async operation accepts a token
  - queues/pipelines have a clear completion path
