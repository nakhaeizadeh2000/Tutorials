### 1. **Actor model concepts in the .NET ecosystem**

**Actor model (high level)**

- An **actor**:
  - encapsulates its **own state**
  - processes one **message at a time**
  - communicates with other actors via **message passing**, not shared memory
  - may send messages, create actors, or change its own behavior

**Core properties**

- **Isolation**: no shared mutable state across actors.
- **Single-threaded** per actor: one message at a time, no concurrent access to its state.
- **Asynchrony**: actors handle messages asynchronously.

**In .NET terms**

- An actor is often implemented as:
  - a **mailbox** (queue or `Channel<T>`)
  - a **loop** (`while` or `await foreach`) reading messages
  - private mutable state inside that loop

**Why this is compelling**

- Eliminates many locking bugs:
  - no need for fine-grained locks within actor state
  - concurrency is managed at the message level
- Scales well under high contention or complex invariants.

### 2. **Using Channels or Dataflow for mailbox-style processing**

**Channel-based actor**

- Use a `Channel<TMessage>` as an actor’s mailbox.
- A single reader (the actor loop) processes messages in order.
- Multiple writers (external callers) send messages.

**Runnable example: simple counter actor**

```csharp
using System;
using System.Threading;
using System.Threading.Channels;
using System.Threading.Tasks;

public sealed class CounterActor : IAsyncDisposable
{
    private readonly Channel<Message> _mailbox;
    private readonly CancellationTokenSource _cts = new();
    private readonly Task _runner;
    private int _value; // isolated state

    public CounterActor()
    {
        _mailbox = Channel.CreateUnbounded<Message>(new UnboundedChannelOptions
        {
            SingleReader = true,
            SingleWriter = false
        });
        _runner = Task.Run(RunAsync);
    }

    public ValueTask IncrementAsync(int amount, CancellationToken ct = default)
        => _mailbox.Writer.WriteAsync(new Increment(amount), ct);

    public Task<int> GetValueAsync(CancellationToken ct = default)
    {
        var msg = new GetValue();
        _mailbox.Writer.TryWrite(msg);
        return msg.Task;
    }

    private async Task RunAsync()
    {
        try
        {
            await foreach (var msg in _mailbox.Reader.ReadAllAsync(_cts.Token).ConfigureAwait(false))
            {
                switch (msg)
                {
                    case Increment inc:
                        _value += inc.Amount;
                        break;
                    case GetValue get:
                        get.SetResult(_value);
                        break;
                }
            }
        }
        catch (OperationCanceledException) when (_cts.IsCancellationRequested) { }
    }

    public async ValueTask DisposeAsync()
    {
        _cts.Cancel();
        _mailbox.Writer.TryComplete();
        await _runner.ConfigureAwait(false);
        _cts.Dispose();
    }

    private abstract record Message;
    private sealed record Increment(int Amount) : Message;

    private sealed record GetValue : Message
    {
        private readonly TaskCompletionSource<int> _tcs =
            new(TaskCreationOptions.RunContinuationsAsynchronously);

        public Task<int> Task => _tcs.Task;
        public void SetResult(int value) => _tcs.TrySetResult(value);
    }
}
```

**Dataflow-based actor**

- Dataflow’s `ActionBlock<T>` can also act as a mailbox:
  - it accepts messages asynchronously
  - processes them with configurable degree of parallelism (for actors, usually 1)

**Good to know**

- `Channel<T>` is generally lighter than Dataflow; Dataflow shines in more complex pipelines (see **3.3**).

### 3. **Single-threaded TaskScheduler and event-loop style executors**

**Concept**

- Instead of many small locks, you dedicate a **single thread or logical executor** to a component and run all its work there.
- This is essentially an actor where “mailbox” = task queue, and “loop” = event loop.

**Implementing an executor (simple pattern)**

- See `SingleThreadExecutor` in **2.2** as a general example.
- For actor-style code, that executor becomes the “thread” on which the actor’s state always lives.

**When this is useful**

- For components with complex state invariants where locking is hard to reason about.
- For persistent connections (e.g., per-socket loops) that must serialize operations.

**Common mistakes**

- Doing blocking I/O on the single thread → kills concurrency benefits.
- Running too many single-threaded executors (one per tiny thing) → many threads and scheduling overhead.

**Mentor emphasis**

- Use single-threaded executors/actors to **simplify correctness**, not to avoid learning async or locks.

### 4. **State confinement vs locking for thread safety**

**Two main strategies**

- **Locking**:
  - many threads can access shared state, but they take locks to coordinate.
  - simpler for small, infrequently modified objects.
- **State confinement (actors)**:
  - only one thread (or logical executor) ever touches the state.
  - other threads send messages/requests, not direct mutations.

**Trade-offs**

- **Locking**:
  - **Pros**: straightforward for small, local critical sections; integrates easily with existing code.
  - **Cons**: can lead to contention, deadlocks, complex lock hierarchies under load.
- **State confinement**:
  - **Pros**: easier reasoning about invariants; no lock ordering issues; great under high contention.
  - **Cons**: requires explicit message-passing API; potential single-thread bottleneck if not carefully designed.

**When confinement wins**

- High-contention scenarios (e.g., global counters, hot maps).
- Complex invariants spanning multiple fields (financial ledgers, complex workflows).
- Systems where you’d otherwise need coarse-grained locks.

**Good to know**

- You can mix approaches:
  - use actors for high-contention hot spots
  - use simple locks for low-contention local structures

### 5. **When actor-style concurrency is beneficial (high contention, complex invariants)**

**Good fit**

- **High contention**:
  - many threads updating the same data structure (e.g., order books, global registries).
- **Complex invariants**:
  - constraints involving multiple fields that must stay consistent.
- **Long-lived entities**:
  - per-user session, per-connection, per-tenant actors.

**Patterns**

- **Single-writer pattern**:
  - All writes go through one actor; reads may be served:
    - via messages (strong guarantee)
    - via snapshots/read-only copies (eventual consistency)
- **Sharding**:
  - Many actors, each owning a partition of the key space.
  - A router chooses which actor to send a message to.

**Anti-patterns**

- Creating thousands of actors each with their own dedicated thread:
  - threads are expensive; use shared executors/Thread Pool-backed loops and Channels instead.
- Ignoring backpressure:
  - mailboxes must be bounded or the actor can become a memory sink.

**Mentor checklist**

- Is the contention high enough that locks are hurting performance?
- Are the invariants complex enough that lock-based code is hard to reason about?
- Can you define a clean message-based API for the component?
- Do you have a bounded mailbox and clear shutdown path?
