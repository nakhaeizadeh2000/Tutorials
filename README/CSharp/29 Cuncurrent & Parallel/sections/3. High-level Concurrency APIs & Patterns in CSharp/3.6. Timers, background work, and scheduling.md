### 1. **System.Threading.Timer vs PeriodicTimer**

**`System.Threading.Timer`**

- Classic timer that:
  - invokes a **callback delegate** on a Thread Pool thread
  - can have an initial due time and a period
- Callback can overlap if execution time > period.

**`PeriodicTimer` (modern, async-friendly)**

- Added in .NET 6+; designed for **async loops**:
  - `WaitForNextTickAsync` returns `false` when the timer is disposed/canceled.
  - no overlapping ticks by default; your loop controls scheduling.

**When to use which**

- Prefer `PeriodicTimer` in `async` code and background services.
- `System.Threading.Timer` is still fine when:
  - you truly need callback-style behavior
  - the callback is small and non-async

**Common mistakes with `System.Threading.Timer`**

- Doing heavy or async work in the callback:
  - leads to overlap, contention, and reentrancy issues.
- Forgetting to dispose the timer:
  - can keep the process alive, or leak callbacks.

**Runnable example: `PeriodicTimer` in a background loop**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

static class PeriodicTimerDemo
{
    public static async Task RunAsync(TimeSpan period, CancellationToken ct)
    {
        using var timer = new PeriodicTimer(period);

        while (await timer.WaitForNextTickAsync(ct).ConfigureAwait(false))
        {
            await DoWorkOnceAsync(ct).ConfigureAwait(false);
        }
    }

    private static Task DoWorkOnceAsync(CancellationToken ct)
    {
        Console.WriteLine($"Tick at {DateTimeOffset.UtcNow}");
        return Task.CompletedTask;
    }
}
```

**Performance note**

- `PeriodicTimer` avoids the “timer callback overlapped” hazard by letting your loop decide when the next iteration happens.

### 2. **Scheduling recurring work in ASP.NET Core (IHostedService, BackgroundService)**

**Why use hosted services**

- They integrate with the **generic host**:
  - lifetime (start/stop)
  - DI
  - logging and configuration
- They provide a natural home for recurring or long-running background work.

**`IHostedService` vs `BackgroundService`**

- `BackgroundService` is an abstract base that implements `IHostedService` and gives you an `ExecuteAsync` loop with a `CancellationToken`.
- Most new code should derive from `BackgroundService`; only use raw `IHostedService` if you need full control over startup/shutdown.

**Runnable example: recurring job with `BackgroundService` + `PeriodicTimer`**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;
using Microsoft.Extensions.Hosting;

public sealed class CleanupService : BackgroundService
{
    private readonly TimeSpan _period = TimeSpan.FromMinutes(5);

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(_period);

        while (!stoppingToken.IsCancellationRequested &&
               await timer.WaitForNextTickAsync(stoppingToken).ConfigureAwait(false))
        {
            await RunCleanupAsync(stoppingToken).ConfigureAwait(false);
        }
    }

    private static async Task RunCleanupAsync(CancellationToken ct)
    {
        // Example clean-up logic.
        await Task.Delay(500, ct).ConfigureAwait(false);
    }
}
```

**Good to know**

- Register this service via `builder.Services.AddHostedService<CleanupService>();` in the ASP.NET Core / generic host setup.

### 3. **Delayed execution with Task.Delay and timers**

**`Task.Delay`**

- Simple, awaitable delay; does **not** block a thread.
- Ideal for:
  - backoff strategies
  - staggered retries
  - simple “wait N ms” in async code

**Timers vs `Task.Delay`**

- For one-off delays, prefer `Task.Delay`.
- For periodic work inside an `async` method, `while` loop + `Task.Delay` is okay but `PeriodicTimer` gives better semantics (see above).

**Example: exponential backoff**

```csharp
using System;
using System.Net.Http;
using System.Threading;
using System.Threading.Tasks;

static class BackoffDemo
{
    public static async Task<string> GetWithRetryAsync(
        HttpClient client,
        string url,
        int maxAttempts,
        TimeSpan initialDelay,
        CancellationToken ct = default)
    {
        var delay = initialDelay;
        Exception? lastError = null;

        for (int attempt = 1; attempt <= maxAttempts; attempt++)
        {
            try
            {
                return await client.GetStringAsync(url, ct).ConfigureAwait(false);
            }
            catch (Exception ex) when (attempt < maxAttempts && !ct.IsCancellationRequested)
            {
                lastError = ex;
                await Task.Delay(delay, ct).ConfigureAwait(false);
                delay = delay * 2;
            }
        }

        throw new InvalidOperationException($"Failed after {maxAttempts} attempts.", lastError);
    }
}
```

**Performance note**

- `Task.Delay` is cheap; busy-wait loops (`SpinWait`, polling without sleep) are not, unless you are in a very low-level, short-lived context.

### 4. **Avoiding timer drift and overlapping executions**

**Timer drift**

- Occurs when small inaccuracies in timing accumulate, causing your “every N seconds” job to slowly shift.
- A naive implementation:
  - `while (true) { await Task.Delay(period); await DoWork(); }`
  - If `DoWork` takes time, the actual period becomes `period + executionTime`.

**Overlap**

- If you use `System.Threading.Timer` with a period shorter than the execution time of the callback, callbacks can overlap and pile up.

**Patterns to avoid drift and overlap**

- Use `PeriodicTimer` and make the loop body wait for completion before the next tick.
- For strict schedule alignment (e.g., start at whole-minute boundaries), compute the next scheduled time explicitly and delay until then.

**Example: non-overlapping schedule anchored to wall-clock boundaries**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

static class AnchoredSchedule
{
    public static async Task RunEveryMinuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            var now = DateTimeOffset.UtcNow;
            var next = new DateTimeOffset(
                year: now.Year, month: now.Month, day: now.Day,
                hour: now.Hour, minute: now.Minute, second: 0, offset: now.Offset)
                .AddMinutes(1);

            var delay = next - now;
            if (delay > TimeSpan.Zero)
            {
                await Task.Delay(delay, ct).ConfigureAwait(false);
            }

            await DoWorkAsync(ct).ConfigureAwait(false);
        }
    }

    private static Task DoWorkAsync(CancellationToken ct)
    {
        // Do non-overlapping work scheduled on minute boundaries.
        return Task.CompletedTask;
    }
}
```

**Good to know**

- For many apps, “period + execution time” is perfectly acceptable; only invest in anchoring if the schedule really matters.

### 5. **Scheduling pitfalls (clock skew, long-running callbacks)**

**Clock skew**

- System time can change due to:
  - NTP corrections
  - manual time changes
  - VM/host adjustments
- If you rely on `DateTime.Now`/`UtcNow` for long-lived schedules, skew can cause:
  - skipped or duplicated intervals
  - timer misfires

**Mitigations**

- For short intervals, skew usually doesn’t matter much.
- For long-running, critical schedules:
  - use monotonic timers where possible (`Stopwatch`-based intervals)
  - re-check wall time occasionally but not as the only source of truth

**Long-running callbacks**

- Using `System.Threading.Timer` to invoke heavy work directly:
  - saturates Thread Pool threads
  - causes overlaps and reentrancy issues
- Prefer:
  - light callback that enqueues work to a bounded pipeline/queue
  - or a `BackgroundService` that owns the loop

**Mentor checklist for scheduled work**

- Is the body **idempotent** or at least safe to run twice (for resilience)?
- Is there a **global owner** (hosted service) that controls lifetime and cancellation?
- Are you using **bounded queues** and throttling for anything that can pile up (see **3.3** and **3.5**)?
- Are you measuring schedule accuracy and latency under load?
