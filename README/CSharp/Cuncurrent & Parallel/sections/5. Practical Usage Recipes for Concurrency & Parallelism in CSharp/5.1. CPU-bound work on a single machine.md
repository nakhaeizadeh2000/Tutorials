### 1. **Basic loop parallelization with Parallel.For and Parallel.ForEach**

**When to parallelize a loop**

- The loop body is **CPU-bound** (computation, not I/O).
- Each iteration is **independent** (or uses thread-safe aggregation).
- The work per iteration is **substantial enough** to amortize parallel overhead (typically > 1ms per iteration, or thousands of iterations total).
- You have **multiple cores** available (check `Environment.ProcessorCount`).

**Common patterns**

**Pattern 1: Independent per-index computation**

```csharp
using System;
using System.Threading.Tasks;

public static class ParallelBasics
{
    // Safe: each iteration writes to a unique index
    public static void SquareArrayInPlace(int[] data)
    {
        Parallel.For(0, data.Length, i =>
        {
            data[i] = data[i] * data[i];
        });
    }

    // Safe: thread-local aggregation
    public static long SumSquares(int[] data)
    {
        long total = 0;
        Parallel.ForEach(
            data,
            () => 0L, // localInit: initialize thread-local accumulator
            (item, loopState, localSum) => localSum + (long)item * item, // body
            localSum => Interlocked.Add(ref total, localSum) // localFinally: aggregate
        );
        return total;
    }
}
```

**Pattern 2: Parallel.ForEach with custom partitioning**

```csharp
using System;
using System.Collections.Generic;
using System.Linq;
using System.Threading.Tasks;

public static class ParallelPartitioning
{
    public static void ProcessLargeCollection<T>(IEnumerable<T> items, Action<T> processor)
    {
        // Parallel.ForEach automatically partitions; you can customize with Partitioner
        var partitioner = Partitioner.Create(items, loadBalance: true);
        
        Parallel.ForEach(partitioner, item =>
        {
            processor(item);
        });
    }
}
```

**Common mistakes**

1. **Mutating shared state without synchronization**
   ```csharp
   // ❌ WRONG: Race condition
   int sharedCounter = 0;
   Parallel.For(0, 1000, i => sharedCounter++);
   
   // ✅ CORRECT: Use Interlocked or thread-local aggregation
   int sharedCounter = 0;
   Parallel.For(0, 1000, i => Interlocked.Increment(ref sharedCounter));
   ```

2. **Locking inside the loop body**
   ```csharp
   // ❌ WRONG: Contention kills parallelism
   object lockObj = new();
   Parallel.For(0, 1000, i =>
   {
       lock (lockObj) { /* work */ }
   });
   
   // ✅ CORRECT: Use thread-local state, aggregate at the end
   ```

3. **Using async lambdas**
   ```csharp
   // ❌ WRONG: Parallel.For doesn't await; creates fire-and-forget tasks
   Parallel.ForEach(urls, async url => await DownloadAsync(url));
   
   // ✅ CORRECT: For async I/O, use Task.WhenAll with throttling (see 5.2)
   ```

4. **Parallelizing tiny work**
   ```csharp
   // ❌ WRONG: Overhead dominates
   Parallel.For(0, 10, i => array[i]++);
   
   // ✅ CORRECT: Only parallelize substantial work
   if (array.Length > 1000)
       Parallel.For(0, array.Length, i => HeavyComputation(array[i]));
   ```

**Performance notes**

- **Overhead**: Parallel.For has ~1-10μs overhead per partition. Ensure work per iteration >> overhead.
- **Thread Pool**: Parallel.For uses the Thread Pool. If you're already saturating it with async I/O, CPU-bound parallelism may compete. See **2.1**.
- **Degree of parallelism**: By default, Parallel.For uses up to `Environment.ProcessorCount` threads. You can limit it:
  ```csharp
  var options = new ParallelOptions { MaxDegreeOfParallelism = 4 };
  Parallel.For(0, count, options, i => { /* work */ });
  ```

**Good to know**

- For numeric arrays, consider SIMD vectorization (see **1.5**) combined with Parallel.For for very large datasets.
- Parallel.ForEach works with `IEnumerable<T>`, but if the source is expensive to enumerate, consider materializing it first or using `Partitioner.Create`.

### 2. **Data-parallel queries with PLINQ**

**What PLINQ is**

- PLINQ (`AsParallel()`) parallelizes LINQ queries automatically.
- It's ideal for **declarative data transformations** where you want parallelism without manual loop management.

**When to use PLINQ**

- You have a **CPU-bound query** over a collection (filter, map, reduce, aggregation).
- The query is **side-effect-free** (or uses thread-safe aggregations).
- The source collection is **large enough** to benefit from parallelism.

**Common patterns**

**Pattern 1: Filter and transform**

```csharp
using System;
using System.Linq;

public static class PLINQBasics
{
    public static int[] FilterAndSquare(int[] numbers)
    {
        return numbers
            .AsParallel()
            .Where(n => n > 0)
            .Select(n => n * n)
            .ToArray();
    }
}
```

**Pattern 2: Aggregation with thread-safe combiners**

```csharp
using System;
using System.Linq;

public static class PLINQAggregation
{
    public static long SumSquares(int[] numbers)
    {
        return numbers
            .AsParallel()
            .Select(n => (long)n * n)
            .Sum(); // PLINQ handles thread-safe aggregation internally
    }
    
    // Custom aggregation
    public static int CustomAggregate(int[] numbers)
    {
        return numbers
            .AsParallel()
            .Aggregate(
                seed: 0,
                func: (sum, item) => sum + item * item,
                resultSelector: result => result
            );
    }
}
```

**Pattern 3: Tuning parallelism and merge options**

```csharp
using System;
using System.Linq;

public static class PLINQTuning
{
    public static int[] ProcessWithTuning(int[] numbers)
    {
        return numbers
            .AsParallel()
            .WithDegreeOfParallelism(4) // Limit to 4 threads
            .WithMergeOptions(ParallelMergeOptions.NotBuffered) // Low latency
            .Where(n => n > 0)
            .Select(n => n * n)
            .ToArray();
    }
}
```

**Merge options explained**

- `ParallelMergeOptions.AutoBuffered` (default): Balances latency and throughput.
- `ParallelMergeOptions.NotBuffered`: Low latency, results available as soon as computed (useful for streaming).
- `ParallelMergeOptions.FullyBuffered`: Highest throughput, but waits for all results before returning.

**Common mistakes**

1. **Using PLINQ for I/O-bound work**
   ```csharp
   // ❌ WRONG: PLINQ doesn't help with I/O
   urls.AsParallel().Select(url => Download(url)).ToArray();
   
   // ✅ CORRECT: Use async/await with Task.WhenAll (see 5.2)
   ```

2. **Side effects in query operators**
   ```csharp
   // ❌ WRONG: Non-deterministic side effects
   int counter = 0;
   items.AsParallel().Select(x => { counter++; return x * 2; }).ToArray();
   
   // ✅ CORRECT: Pure transformations
   ```

3. **Forgetting to materialize**
   ```csharp
   // ⚠️ CAUTION: Query is deferred; parallelism happens on enumeration
   var query = items.AsParallel().Where(x => x > 0);
   // Parallelism occurs here:
   var results = query.ToArray();
   ```

4. **Over-parallelizing small collections**
   ```csharp
   // ❌ WRONG: Overhead dominates
   new[] { 1, 2, 3 }.AsParallel().Select(x => x * 2).ToArray();
   
   // ✅ CORRECT: Only use PLINQ for substantial collections
   ```

**Performance notes**

- **Partitioning**: PLINQ uses intelligent partitioning (range, chunk, striped). For custom collections, implement `IPartitioner<T>`.
- **Ordering**: By default, PLINQ doesn't preserve order (faster). Use `AsOrdered()` if needed:
  ```csharp
  items.AsParallel().AsOrdered().Select(x => x * 2).ToArray();
  ```
- **Cancellation**: Use `WithCancellation`:
  ```csharp
  items.AsParallel().WithCancellation(ct).Select(x => Process(x)).ToArray();
  ```

**Good to know**

- PLINQ falls back to sequential execution if it detects the query won't benefit from parallelism.
- Use `AsSequential()` to force sequential execution for part of a query:
  ```csharp
  items.AsParallel().Select(x => x * 2).AsSequential().Take(10).ToArray();
  ```

### 3. **Choosing between Parallel.\* and Task.Run + Task.WhenAll**

**The decision matrix**

| Scenario | Use |
|----------|-----|
| CPU-bound loop with independent iterations | `Parallel.For` / `Parallel.ForEach` |
| CPU-bound LINQ query | PLINQ (`AsParallel()`) |
| CPU-bound work that's already Task-based | `Task.Run` + `Task.WhenAll` |
| I/O-bound work (HTTP, DB, files) | `async`/`await` + `Task.WhenAll` (see **5.2**) |
| Mixed CPU+I/O in a loop | `Task.Run` + `Task.WhenAll` (or Channels/Dataflow) |
| Dynamic number of independent tasks | `Task.Run` + `Task.WhenAll` |

**When Parallel.\* is better**

- **Structured parallelism**: You have a clear loop/collection to parallelize.
- **Automatic partitioning**: Parallel.For handles work distribution efficiently.
- **Lower overhead**: Direct Thread Pool integration, no Task allocations per iteration.

**When Task.Run + Task.WhenAll is better**

- **Dynamic task creation**: Number of tasks isn't known at compile time.
- **Mixed workloads**: Some CPU-bound, some I/O-bound.
- **Fine-grained control**: You need per-task cancellation, error handling, or continuation logic.
- **Integration with async code**: You're already in an async context.

**Example: CPU-bound work with Task.Run**

```csharp
using System;
using System.Linq;
using System.Threading.Tasks;

public static class TaskBasedParallelism
{
    public static async Task<int[]> ProcessItemsAsync(int[] items, Func<int, int> processor)
    {
        // Create tasks for each item
        var tasks = items.Select(item => Task.Run(() => processor(item))).ToArray();
        
        // Wait for all to complete
        return await Task.WhenAll(tasks).ConfigureAwait(false);
    }
    
    // With cancellation
    public static async Task<int[]> ProcessWithCancellationAsync(
        int[] items, 
        Func<int, CancellationToken, int> processor,
        CancellationToken cancellationToken = default)
    {
        var tasks = items.Select(item => 
            Task.Run(() => processor(item, cancellationToken), cancellationToken)
        ).ToArray();
        
        return await Task.WhenAll(tasks).ConfigureAwait(false);
    }
}
```

**Example: When Parallel.For is simpler**

```csharp
// ✅ SIMPLER: Use Parallel.For for straightforward loops
public static void SquareArray(int[] data)
{
    Parallel.For(0, data.Length, i => data[i] = data[i] * data[i]);
}

// ⚠️ MORE COMPLEX: Task.Run + WhenAll adds unnecessary complexity here
public static async Task SquareArrayAsync(int[] data)
{
    var tasks = Enumerable.Range(0, data.Length)
        .Select(i => Task.Run(() => data[i] = data[i] * data[i]))
        .ToArray();
    await Task.WhenAll(tasks);
}
```

**Common mistakes**

1. **Using Task.Run for simple loops**
   ```csharp
   // ❌ WRONG: Unnecessary Task allocations
   var tasks = Enumerable.Range(0, 1000)
       .Select(i => Task.Run(() => Process(i)))
       .ToArray();
   await Task.WhenAll(tasks);
   
   // ✅ CORRECT: Use Parallel.For
   Parallel.For(0, 1000, i => Process(i));
   ```

2. **Using Parallel.For for async I/O**
   ```csharp
   // ❌ WRONG: Parallel.For doesn't await
   Parallel.ForEach(urls, url => DownloadAsync(url)); // Fire-and-forget!
   
   // ✅ CORRECT: Use Task.WhenAll
   var tasks = urls.Select(url => DownloadAsync(url)).ToArray();
   await Task.WhenAll(tasks);
   ```

3. **Creating too many tasks**
   ```csharp
   // ❌ WRONG: Creates 10,000 tasks
   var tasks = items.Select(item => Task.Run(() => Process(item))).ToArray();
   
   // ✅ CORRECT: Use Parallel.For or throttle with SemaphoreSlim
   ```

**Performance notes**

- **Task allocations**: `Task.Run` allocates a Task per item. For large collections, this can cause GC pressure. `Parallel.For` uses work-stealing queues and avoids per-iteration allocations.
- **Thread Pool saturation**: Both use the Thread Pool. If you're already saturating it, neither will help. See **2.1**.
- **Throttling**: `Task.Run` + `Task.WhenAll` doesn't throttle by default. Use `SemaphoreSlim` (see **3.5**) or `ParallelOptions.MaxDegreeOfParallelism`.

**Good to know**

- For CPU-bound work, `Parallel.For` is usually more efficient than `Task.Run` + `Task.WhenAll` due to better partitioning and lower overhead.
- Use `Task.Run` + `Task.WhenAll` when you need the flexibility of Task-based composition (cancellation tokens, continuations, error handling per task).

### 4. **Partitioning data for better cache locality**

**What cache locality means**

- Modern CPUs have multiple levels of cache (L1, L2, L3).
- Accessing data that's already in cache is **10-100x faster** than accessing RAM.
- **Cache locality**: Keeping related data together so it stays in cache.

**Why partitioning matters**

- Poor partitioning can cause **false sharing** (see **4.2**) and cache misses.
- Good partitioning keeps each thread working on **contiguous memory regions**.

**Pattern 1: Range partitioning for arrays**

```csharp
using System;
using System.Collections.Concurrent;
using System.Threading.Tasks;

public static class CacheLocalityOptimization
{
    // ✅ GOOD: Each thread works on a contiguous range
    public static void ProcessArrayWithRangePartitioning(int[] data)
    {
        Parallel.ForEach(
            Partitioner.Create(0, data.Length), // Range partitioner
            range =>
            {
                // Process contiguous range [range.Item1, range.Item2)
                for (int i = range.Item1; i < range.Item2; i++)
                {
                    data[i] = Process(data[i]);
                }
            }
        );
    }
    
    private static int Process(int value) => value * value;
}
```

**Pattern 2: Chunk partitioning for better locality**

```csharp
using System;
using System.Collections.Concurrent;
using System.Threading.Tasks;

public static class ChunkPartitioning
{
    public static void ProcessWithChunks<T>(T[] items, Action<T> processor)
    {
        var partitioner = Partitioner.Create(
            items,
            loadBalance: false // Prefer larger chunks for better locality
        );
        
        Parallel.ForEach(partitioner, item =>
        {
            processor(item);
        });
    }
}
```

**Pattern 3: Avoiding false sharing**

```csharp
using System;
using System.Runtime.InteropServices;
using System.Threading.Tasks;

public static class FalseSharingAvoidance
{
    // ❌ BAD: False sharing if counters are on the same cache line
    public class BadCounter
    {
        public int Count1;
        public int Count2; // Likely on same cache line as Count1
    }
    
    // ✅ GOOD: Pad to avoid false sharing
    [StructLayout(LayoutKind.Explicit, Size = 64)] // Cache line size
    public struct PaddedCounter
    {
        [FieldOffset(0)]
        public int Count1;
        // Padding ensures Count2 is on a different cache line
    }
    
    public static void CountWithPadding(int[] data)
    {
        var counters = new PaddedCounter[Environment.ProcessorCount];
        
        Parallel.For(0, data.Length, i =>
        {
            int threadIndex = Task.CurrentId.Value % Environment.ProcessorCount;
            counters[threadIndex].Count1++;
        });
    }
}
```

**Common mistakes**

1. **Not using range partitioning for arrays**
   ```csharp
   // ❌ WRONG: Poor cache locality
   Parallel.ForEach(data, item => Process(item));
   
   // ✅ CORRECT: Use range partitioning
   Parallel.ForEach(Partitioner.Create(0, data.Length), range => {
       for (int i = range.Item1; i < range.Item2; i++)
           Process(data[i]);
   });
   ```

2. **False sharing in shared counters**
   ```csharp
   // ❌ WRONG: False sharing
   int[] counters = new int[Environment.ProcessorCount];
   Parallel.For(0, data.Length, i => {
       counters[i % counters.Length]++;
   });
   
   // ✅ CORRECT: Use thread-local aggregation
   long total = 0;
   Parallel.ForEach(data, () => 0L, (item, state, local) => local + 1,
       local => Interlocked.Add(ref total, local));
   ```

**Performance notes**

- **Cache line size**: Typically 64 bytes on modern CPUs. Keep frequently accessed data separated by at least 64 bytes to avoid false sharing.
- **Prefetching**: CPUs prefetch sequential memory. Range partitioning leverages this.
- **Measuring**: Use profiling tools (PerfView, dotnet-counters) to identify cache misses. See **4.8**.

**Good to know**

- For very large arrays, consider `Memory<T>` and `Span<T>` for zero-copy slicing and better cache behavior.
- `Partitioner.Create` with `loadBalance: false` creates larger chunks, improving locality at the cost of potential load imbalance.

### 5. **Detecting when parallelization hurts more than helps**

**Signs that parallelization is hurting**

1. **Slower execution**: Parallel version takes longer than sequential.
2. **High CPU overhead**: `% Time in GC` increases significantly.
3. **Thread contention**: Many threads waiting on locks or shared resources.
4. **Cache thrashing**: Excessive cache misses due to poor locality.

**When parallelization is counterproductive**

**Scenario 1: Tiny work per iteration**

```csharp
// ❌ BAD: Overhead dominates
Parallel.For(0, 10, i => array[i]++);

// ✅ GOOD: Only parallelize substantial work
if (array.Length > 1000)
    Parallel.For(0, array.Length, i => HeavyComputation(array[i]));
```

**Scenario 2: High contention on shared resources**

```csharp
// ❌ BAD: Lock contention kills parallelism
object lockObj = new();
Parallel.For(0, 10000, i =>
{
    lock (lockObj)
    {
        SharedResource.Process(i);
    }
});

// ✅ GOOD: Eliminate contention (thread-local state, lock-free structures)
```

**Scenario 3: Memory-bound workloads**

```csharp
// ⚠️ CAUTION: If memory bandwidth is the bottleneck, more threads won't help
// Measure: If CPU utilization is low but parallelization doesn't help,
// you're likely memory-bound.
```

**Scenario 4: Already saturated Thread Pool**

```csharp
// ❌ BAD: Adding CPU-bound parallelism when Thread Pool is saturated by I/O
// Solution: Fix the I/O bottleneck first (see 5.2)
```

**Detection techniques**

**Technique 1: Benchmark sequential vs parallel**

```csharp
using System;
using System.Diagnostics;
using System.Linq;
using System.Threading.Tasks;

public static class ParallelizationBenchmark
{
    public static void MeasurePerformance(int[] data)
    {
        // Sequential baseline
        var sw = Stopwatch.StartNew();
        var sequential = data.Select(x => HeavyComputation(x)).ToArray();
        sw.Stop();
        var sequentialTime = sw.ElapsedMilliseconds;
        
        // Parallel version
        sw.Restart();
        var parallel = data.AsParallel().Select(x => HeavyComputation(x)).ToArray();
        sw.Stop();
        var parallelTime = sw.ElapsedMilliseconds;
        
        Console.WriteLine($"Sequential: {sequentialTime}ms, Parallel: {parallelTime}ms");
        Console.WriteLine($"Speedup: {(double)sequentialTime / parallelTime:F2}x");
        
        // If speedup < 1.2x, parallelization may not be worth it
    }
    
    private static int HeavyComputation(int x) => x * x; // Replace with real work
}
```

**Technique 2: Measure overhead**

```csharp
using System;
using System.Diagnostics;
using System.Threading.Tasks;

public static class OverheadMeasurement
{
    public static void MeasureOverhead(int iterations)
    {
        var sw = Stopwatch.StartNew();
        Parallel.For(0, iterations, i => { /* empty or trivial work */ });
        sw.Stop();
        
        var overheadPerIteration = sw.ElapsedTicks / (double)iterations;
        Console.WriteLine($"Overhead per iteration: {overheadPerIteration} ticks");
        
        // If your work per iteration is < 10x overhead, reconsider
    }
}
```

**Technique 3: Profile with dotnet-counters**

```bash
# Monitor Thread Pool and GC
dotnet-counters monitor --process-id <pid> System.Runtime
```

Look for:
- High `threadpool-thread-count`: May indicate Thread Pool starvation.
- High `gc-gen0-collections`: Parallelization may be causing allocation pressure.

**Decision framework**

```
Is the work CPU-bound? → No → Use async I/O (see 5.2)
    ↓ Yes
Is the work substantial (>1ms per iteration or >1000 iterations)? → No → Don't parallelize
    ↓ Yes
Is each iteration independent? → No → Use thread-local aggregation or redesign
    ↓ Yes
Are there multiple cores available? → No → Don't parallelize
    ↓ Yes
Benchmark: Is parallel version >1.5x faster? → No → Don't parallelize
    ↓ Yes
✅ Parallelize (but monitor in production)
```

**Common mistakes**

1. **Parallelizing everything by default**
   ```csharp
   // ❌ WRONG: Not all loops benefit from parallelization
   Parallel.For(0, 10, i => Process(i));
   
   // ✅ CORRECT: Measure first, parallelize only when beneficial
   ```

2. **Ignoring contention**
   ```csharp
   // ❌ WRONG: Contention makes parallelization worse
   Parallel.ForEach(items, item => {
       lock (sharedLock) { Process(item); }
   });
   ```

3. **Not measuring**
   ```csharp
   // ❌ WRONG: Assuming parallelization helps without measuring
   // ✅ CORRECT: Always benchmark
   ```

**Performance notes**

- **Amdahl's Law**: Maximum speedup is limited by the sequential portion of your code. If 10% is sequential, max speedup is 10x even with infinite cores.
- **Diminishing returns**: Beyond `Environment.ProcessorCount` threads, you usually see diminishing returns (or worse performance) for CPU-bound work.
- **GC pressure**: Parallelization can increase allocations. Monitor GC metrics.

**Good to know**

- Use `ParallelOptions` to limit parallelism and test different degrees:
  ```csharp
  var options = new ParallelOptions { MaxDegreeOfParallelism = 2 };
  Parallel.For(0, count, options, i => Process(i));
  ```
- Consider **SIMD** (see **1.5**) for numeric arrays before parallelization—it can be faster and use fewer threads.
- In production, use **feature flags** to toggle parallelization and measure real-world impact.
