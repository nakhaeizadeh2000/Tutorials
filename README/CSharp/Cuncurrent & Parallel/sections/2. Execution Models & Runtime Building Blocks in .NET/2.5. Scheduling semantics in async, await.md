### 1. **Cooperative vs preemptive behavior in async code**

**Short definition**

- **Preemptive multitasking**: the OS can interrupt a running thread at almost any point to run another thread.
- **Cooperative yielding (async)**: an `async` method continues running until it reaches an **`await` that is not yet complete**, at which point it yields control back to its caller/scheduler.

**What this means in practice**

- Between awaits, your code runs like normal synchronous code: if you do heavy CPU work without awaiting/yielding, you can still:
  - freeze the UI (frontend)
  - block request processing
  - starve other work on the same thread
- Async does not magically “time slice” your CPU loops; it only yields at await points.

**Common mistakes**

- **Long CPU loops inside async methods** without any yielding/cancellation checks.
- Using `await Task.Yield()` as a “performance fix” everywhere. It’s a scheduling tool; use only with intent.

**Mentor guidance**

- For CPU-bound work:
  - make it synchronous and call it from a background context (`Task.Run`) *when appropriate* (UI responsiveness)
  - or use parallelism APIs for multi-core (section 3.2)
  - keep it cancellable and chunkable

**Example: cooperative cancellation in a long loop**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

static class CooperativeAsync
{
    public static async Task<int> SumAsync(int n, CancellationToken ct)
    {
        int sum = 0;
        for (int i = 0; i < n; i++)
        {
            ct.ThrowIfCancellationRequested();
            sum += i;

            // Occasionally yield so other work can progress (use sparingly).
            if ((i & 0x3FFFF) == 0) // every ~262k iterations
            {
                await Task.Yield();
            }
        }
        return sum;
    }
}
```

**Performance note**

- Yielding too often adds overhead; yield only when you need responsiveness/fairness.

### 2. **Where continuations run by default (context vs Thread Pool)**

**The rule of thumb**

- After `await`, the continuation runs:
  - on the captured **`SynchronizationContext`** (UI apps), or
  - on the captured **`TaskScheduler`**, or
  - on the **Thread Pool** (common in ASP.NET Core / console), depending on what’s available and the awaiter.

**Application models**

- **UI apps (frontend)**: a `SynchronizationContext` exists; default `await` resumes on UI thread.
- **ASP.NET Core**: typically no `SynchronizationContext`; `await` resumes on Thread Pool.
- **Console/worker**: typically no `SynchronizationContext`; `await` resumes on Thread Pool.

See **section 2.3** for the deep coverage of these differences.

**Common misconception**

- `async` does *not* mean “runs on another thread”.
  - Many async methods start on the calling thread and may resume on the same context.
  - I/O-bound async often spends most of its lifetime with **no thread at all** while the OS performs I/O (see section 2.4).

### 3. **ConfigureAwait and controlling continuation scheduling**

**What `ConfigureAwait` controls**

- Whether the `await` captures a context (if any) and schedules the continuation back onto it.
- In modern .NET, you’ll see:
  - `await task.ConfigureAwait(false)` in **library/infrastructure** code
  - plain `await task` in **application UI** code

**Best-practice summary**

- **Library code**: default to `ConfigureAwait(false)` unless you *must* resume on the caller context.
- **UI application code (frontend)**: default to plain `await` so you can safely touch UI after.
- **ASP.NET Core**: `ConfigureAwait(false)` usually doesn’t change scheduling, but it keeps libraries safe when reused in UI contexts.

For the one deep explanation of `ConfigureAwait(true)` vs `ConfigureAwait(false)`, see **section 1.6** (do not duplicate here).

**Common mistake**

- Using `ConfigureAwait(false)` in UI code and then touching UI controls → cross-thread exceptions.

**Good to know**

- `ConfigureAwait(false)` does **not** mean “run on a background thread”. It means “don’t try to get back to the captured context”.

### 4. **Fire-and-forget tasks and their scheduling/risk profile**

**Why this is risky**

- If you start work and don’t observe the returned `Task`:
  - exceptions may go unobserved (lost failure)
  - cancellation may be ignored
  - shutdown may cut work off
  - concurrency may become unbounded

**When it is acceptable**

- Truly “best-effort” telemetry/logging with bounded resources and safe failure handling.
- Background queuing patterns where you enqueue work to a managed queue/hosted service rather than launching arbitrary tasks.

**Modern safe patterns**

- In ASP.NET Core: prefer `BackgroundService`/`IHostedService` and queue work via `Channel<T>` (section 5.3 / 3.3).
- For event handlers that must be `async void` (UI events): contain errors inside the handler; do not let exceptions escape.

**Minimal example: safe “fire-and-forget” with explicit error handling**

```csharp
using System;
using System.Threading.Tasks;

static class FireAndForget
{
    public static void Start(Func<Task> work, Action<Exception> onError)
    {
        _ = Run(work, onError);
    }

    private static async Task Run(Func<Task> work, Action<Exception> onError)
    {
        try
        {
            await work().ConfigureAwait(false);
        }
        catch (Exception ex)
        {
            onError(ex);
        }
    }
}
```

**Mentor emphasis**

- If you can’t afford to lose the work, it’s not fire-and-forget. Make it a tracked background job with persistence/queues.

### 5. **Interaction with timers, delays, and cancellation**

**Timers vs `Task.Delay`**

- `Task.Delay(...)` is an awaitable timer; it completes in the future without blocking a thread.
- `PeriodicTimer` is preferred for loops that need periodic ticks without overlapping (see section 3.6 for deep coverage; keep details there).

**Cancellation semantics**

- Cancellation is **cooperative**:
  - passing a `CancellationToken` doesn’t stop work by force
  - your code and the called APIs must observe it
- `Task.Delay(timeout, ct)` throws `OperationCanceledException` if canceled first.

**Common mistakes**

- Using `Thread.Sleep` instead of `Task.Delay` inside async methods (blocks a thread).
- Starting periodic work with timers that can overlap and pile up when the body is slow.
- Forgetting to pass cancellation tokens through to I/O calls.

**Minimal example: responsive delay with cancellation**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

static class DelayWithCancellation
{
    public static async Task RunAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            await Task.Delay(TimeSpan.FromSeconds(1), ct).ConfigureAwait(false);
            Console.WriteLine("Tick");
        }
    }
}
```

**Performance note**

- Timers and delays are cheap compared to blocked threads. Prefer awaitable delays; they scale.
