### 1. **Logical vs physical cores and hyper-threading**

**Definitions**

- **Physical core**: a real CPU core with its own execution resources.
- **Logical core**: what the OS exposes as a schedulable CPU. With hyper-threading (SMT), one physical core may expose 2 (or more) logical cores.
- **Hyper-threading / SMT**: allows a core to run multiple hardware threads to better utilize execution units when one thread stalls.

**What you should expect**

- Hyper-threading can improve throughput for some workloads, but it’s not “double the cores”.
- CPU-bound workloads with high utilization of execution units may see limited benefit from SMT.
- Memory-bound workloads (lots of cache misses) can benefit more because SMT helps hide latency.

**Common mistake**

- Assuming speedup scales linearly with `Environment.ProcessorCount`. It rarely does due to:
  - cache and memory bandwidth limits
  - contention (locks, shared data)
  - scheduler overhead

**Performance note**

- Treat `Environment.ProcessorCount` as a starting point, not a guarantee. Measure your workload.

### 2. **How the Thread Pool maps work to cores**

**Big idea**

- The Thread Pool is not “one thread per core”. It maintains a variable number of worker threads and schedules work onto them.
- The OS then schedules those threads onto cores.

**Key behaviors you should internalize**

- The Thread Pool tries to keep enough runnable threads to utilize cores, but not so many that context switching dominates.
- Work stealing and queueing patterns influence which thread runs what (see section **2.1**).

**Why this matters**

- If you block Thread Pool threads (locks, sync I/O, `.Wait()`), you reduce runnable workers and can cause starvation.
- If you create too many CPU-bound tasks, you create contention and context switching.

**Mentor emphasis**

- On servers: keep Thread Pool threads free by using async I/O and bounded concurrency (sections **2.4** and **2.1**).
- For CPU-bound work: use bounded parallelism and minimize shared mutable state (sections **3.2** and **1.4**).

### 3. **CPU-bound workloads and Parallel.* vs Tasks**

**Short guidance**

- Prefer `Parallel.*` / PLINQ for **data-parallel** CPU-bound workloads (arrays/lists, per-item independent work).
- Prefer `Task.WhenAll` of `Task.Run` for **task-parallel** CPU-bound workloads when:
  - you have a small number of heterogeneous tasks
  - you need async composition with other tasks
- Prefer a plain synchronous loop when the work is small; parallel overhead can dominate.

**Trade-offs**

- `Parallel.For/ForEach`:
  - **Pros**: partitioning, work-stealing, efficient use of cores, fewer allocations than “task per item”.
  - **Cons**: harder cancellation semantics (exception aggregation), side effects must be thread-safe.
- `Task.Run` + `WhenAll`:
  - **Pros**: great composability; explicit tasks; integrates naturally with async flows.
  - **Cons**: easy to create too many tasks (“task per item”) and harm performance.

**Common mistakes**

- Using `Parallel.ForEach` for **I/O-bound** work (see section 1.3 for the deep comparison).
- Doing “task per element” for large collections instead of using `Parallel.ForEach` or partitioning.
- Sharing mutable state across iterations without synchronization, causing contention or races (see section 1.4 and 1.7).

**Runnable example: tasks vs Parallel**

```csharp
using System;
using System.Threading.Tasks;

static class CpuParallelism
{
    public static int[] SquareWithParallel(int[] data)
    {
        var result = new int[data.Length];
        Parallel.For(0, data.Length, i => result[i] = data[i] * data[i]);
        return result;
    }

    public static async Task<int[]> SquareWithTasksAsync(int[] data)
    {
        // Only reasonable for a small number of coarse tasks.
        // This example avoids per-chunk allocations by writing into one result buffer.
        var result = new int[data.Length];
        int mid = data.Length / 2;

        Task t1 = Task.Run(() => SquareRangeInto(data, result, 0, mid));
        Task t2 = Task.Run(() => SquareRangeInto(data, result, mid, data.Length));

        await Task.WhenAll(t1, t2).ConfigureAwait(false);
        return result;
    }

    private static void SquareRangeInto(int[] src, int[] dst, int start, int end)
    {
        for (int i = start; i < end; i++)
            dst[i] = src[i] * src[i];
    }
}
```

**Performance note**

- The `SquareWithTasksAsync` example intentionally demonstrates composability but is *not* the most allocation-efficient approach. For real workloads, prefer `Parallel.For` or `Partitioner` patterns to avoid extra arrays and concatenation.

### 4. **Processor affinity and when (rarely) to care about it**

**What affinity is**

- CPU affinity restricts a process or thread to run only on specific cores.

**Modern guidance**

- Most .NET applications should **not set affinity**:
  - the OS scheduler is usually better at balancing load
  - affinity can reduce the scheduler’s ability to manage thermal/power constraints
  - incorrect affinity can *hurt* performance by reducing cache sharing opportunities or creating hotspots

**When it may matter (rare)**

- Ultra-low-latency systems (trading, realtime-ish control loops).
- Very specific performance experiments where you’re controlling noise.
- Integration with specialized hardware / NUMA considerations where you’ve measured a consistent win.

**Common mistake**

- Setting affinity as a “performance tweak” without measurement. It often backfires.

**Good to know**

- Affinity is OS- and container-environment dependent. In modern cloud environments, CPU sets, quotas, and cgroups can complicate assumptions.

### 5. **Measuring and tuning CPU utilization in concurrent apps**

**First principle: measure before tuning**

- Parallelism and scheduling “feel” intuitive, but the real bottlenecks are often:
  - lock contention
  - memory bandwidth
  - GC pressure / allocations
  - false sharing
  - downstream services

**What to measure**

- **CPU utilization** (per-core, not just total)
- **ThreadPool metrics** (queue length, worker threads, starvation symptoms)
- **GC metrics** (alloc rate, gen0/1/2 collections, pause times)
- **Lock contention** (time spent waiting)
- **Latency percentiles** (p50/p95/p99) under load

**Practical tooling (modern .NET)**

- `dotnet-counters` for live metrics (CPU, GC, ThreadPool).
- `dotnet-trace` for event traces.
- `dotnet-dump` for postmortem analysis.
- Visual Studio profiler / PerfView for deeper investigation.
See section **4.7** and **4.8** for deep coverage of observability and profiling.

**Tuning levers (ordered by impact)**

- **Algorithm and data structures** (reduce work, reduce allocations).
- **Reduce contention**:
  - use state confinement (actors / single-writer) when beneficial (section 3.7)
  - use `Interlocked` for simple counters (section 1.4)
  - avoid shared hot locks
- **Choose appropriate parallelism**:
  - cap `MaxDegreeOfParallelism` to avoid oversubscription
  - batch work into coarse-enough chunks
- **Avoid blocking**:
  - use async I/O (section 2.4)
  - eliminate sync-over-async (section 2.1/2.4)

**Mentor checklist**

- Start from a single-threaded baseline and measure.
- Add parallelism only where it reduces wall-clock time.
- Validate correctness under concurrency (races/deadlocks). See section 1.7 and section 4.x.
