1. **Data races vs higher-level race conditions**

### 1. **Data races vs higher-level race conditions**

**Cross-reference**: See section **1.7** for definitions and examples of race conditions vs data races. This section focuses on **reasoning about** these concepts and their implications for correctness.

**Reasoning framework**

When reasoning about correctness, distinguish between:

- **Data races** (memory model violations):
  - Multiple threads access the same memory location concurrently, at least one is a write, and accesses are unsynchronized.
  - Violates the .NET memory model; leads to undefined behavior (torn reads, lost writes, corruption).
  - **Detectable**: Static analyzers and runtime tools can identify data races.
  - **Fix**: Add synchronization (locks, `Interlocked`, `volatile` where appropriate).

- **Higher-level race conditions** (logical ordering errors):
  - Correctness depends on a specific ordering of operations that is not guaranteed.
  - May or may not involve data races; often involves check-then-act patterns or ordering dependencies.
  - **Harder to detect**: May only manifest under specific timing conditions.
  - **Fix**: Make operations atomic or establish proper ordering guarantees.

**Reasoning about data races**

To reason about data races:

1. **Identify shared mutable state**: What memory locations are accessed by multiple threads?
2. **Identify access patterns**: Which accesses are reads? Which are writes?
3. **Check synchronization**: Are all accesses properly synchronized (via locks, `Interlocked`, or other synchronization primitives)?
4. **Verify memory model compliance**: Do synchronization operations establish the necessary happens-before relationships?

**Example: Reasoning about a counter**

```csharp
// Incorrect: Data race.
public class UnsafeCounter
{
    private int _count = 0; // Shared mutable state.

    public void Increment()
    {
        _count++; // Data race: read-modify-write is not atomic.
    }

    public int Value => _count; // Data race: read without synchronization.
}

// Reasoning:
// - Shared mutable state: _count
// - Access patterns: Increment() writes, Value reads
// - Synchronization: None
// - Conclusion: Data race → undefined behavior
```

**Reasoning about higher-level race conditions**

Higher-level race conditions involve logical errors that may not violate the memory model but still lead to incorrect behavior:

1. **Check-then-act patterns**: Checking a condition and then acting on it without atomicity.
2. **Ordering dependencies**: Assuming operations execute in a specific order without guarantees.
3. **State consistency**: Assuming related state fields are updated atomically.

**Example: Reasoning about a check-then-act race condition**

```csharp
// Incorrect: Higher-level race condition (check-then-act).
public class UnsafeResourcePool
{
    private readonly List<string> _resources = new();
    private readonly object _lock = new object();

    public bool TryAcquire(string resource)
    {
        // Race condition: check and remove are not atomic.
        if (_resources.Contains(resource)) // Check.
        {
            _resources.Remove(resource); // Act - but another thread may have removed it.
            return true;
        }
        return false;
    }
}

// Reasoning:
// - No data race (lock protects _resources)
// - But: Check and act are separate operations
// - Another thread can remove the resource between check and act
// - Conclusion: Higher-level race condition → logical error
```

**Correct reasoning: Making operations atomic**

```csharp
// Correct: Atomic check-and-act.
public class SafeResourcePool
{
    private readonly HashSet<string> _resources = new();
    private readonly object _lock = new object();

    public bool TryAcquire(string resource)
    {
        lock (_lock)
        {
            // Atomic: check and remove in a single critical section.
            return _resources.Remove(resource);
        }
    }
}

// Reasoning:
// - Lock ensures atomicity of check-and-act
// - No race condition: operation is atomic
// - Conclusion: Correct
```

**Mentor guidance: Reasoning checklist**

When reasoning about race conditions:

- **Identify the shared state**: What data is shared across threads?
- **Identify the operations**: What operations are performed on that state?
- **Check atomicity**: Are multi-step operations atomic?
- **Check ordering**: Are ordering dependencies guaranteed?
- **Verify synchronization**: Is synchronization sufficient and correct?

**Performance note**

- Preventing race conditions requires synchronization, which has overhead.
- Use the lightest synchronization mechanism that provides necessary guarantees:
  - `Interlocked` for simple atomic operations (lock-free, very fast).
  - `lock` for critical sections (moderate overhead, necessary for complex operations).
  - Lock-free data structures (e.g., `ConcurrentDictionary`) when appropriate.

**Good to know**

- **All data races are race conditions, but not all race conditions are data races**.
- Data races are memory model violations and lead to undefined behavior.
- Higher-level race conditions are logical errors that may or may not involve data races.
- Use static analyzers, runtime tools, and code reviews to detect race conditions and data races.
- See section **1.7** for definitions and examples; see section **4.2** for the .NET memory model.

### 2. **Shared mutable state vs ownership and confinement**

**Cross-reference**: See section **3.7** for actor-style concurrency and state confinement patterns. This section focuses on **reasoning about** shared mutable state and ownership models.

**Reasoning about shared mutable state**

Shared mutable state is the root cause of most concurrency bugs. When reasoning about correctness:

1. **Identify shared state**: What data is accessible by multiple threads?
2. **Identify mutation points**: Where is that state modified?
3. **Check synchronization**: Is access properly synchronized?
4. **Verify invariants**: Are invariants maintained across all mutation points?

**The problem with shared mutable state**

- **Complexity**: Reasoning about correctness becomes exponentially harder as shared state grows.
- **Bugs**: Data races, race conditions, deadlocks, and livelocks all stem from shared mutable state.
- **Performance**: Synchronization overhead and contention reduce parallelism.

**Example: Reasoning about shared mutable state**

```csharp
// Problematic: Shared mutable state with complex invariants.
public class BankAccount
{
    private decimal _balance = 0;
    private readonly object _lock = new object();

    public void Deposit(decimal amount)
    {
        lock (_lock)
        {
            _balance += amount; // Mutation point 1.
        }
    }

    public void Withdraw(decimal amount)
    {
        lock (_lock)
        {
            if (_balance >= amount) // Invariant check.
            {
                _balance -= amount; // Mutation point 2.
            }
            else
            {
                throw new InvalidOperationException("Insufficient funds");
            }
        }
    }

    public decimal Balance
    {
        get
        {
            lock (_lock)
            {
                return _balance; // Read point.
            }
        }
    }
}

// Reasoning:
// - Shared mutable state: _balance
// - Mutation points: Deposit, Withdraw
// - Synchronization: lock protects all accesses
// - Invariants: _balance >= 0 (implicit)
// - Conclusion: Correct, but requires careful reasoning about lock scope
```

**Ownership and confinement**

**Ownership** means that a single thread (or logical executor) owns a piece of state and is the only one that can modify it. **Confinement** means keeping mutable state private to a single thread or component.

**Reasoning about ownership**

When reasoning about ownership:

1. **Identify the owner**: Which thread or component owns the state?
2. **Verify access patterns**: Do other threads access the state directly, or do they send messages/requests?
3. **Check boundaries**: Are ownership boundaries clearly defined and enforced?

**Example: Reasoning about ownership with message passing**

```csharp
// Correct: Ownership via message passing (actor-style).
public sealed class OwnedBankAccount : IAsyncDisposable
{
    private readonly Channel<Message> _mailbox;
    private readonly CancellationTokenSource _cts = new();
    private readonly Task _runner;
    private decimal _balance = 0; // Owned by the actor loop.

    public OwnedBankAccount()
    {
        _mailbox = Channel.CreateUnbounded<Message>(new UnboundedChannelOptions
        {
            SingleReader = true,
            SingleWriter = false
        });
        _runner = Task.Run(RunAsync);
    }

    public ValueTask DepositAsync(decimal amount, CancellationToken ct = default)
        => _mailbox.Writer.WriteAsync(new Deposit(amount), ct);

    public Task<decimal> GetBalanceAsync(CancellationToken ct = default)
    {
        var msg = new GetBalance();
        _mailbox.Writer.TryWrite(msg);
        return msg.Task;
    }

    private async Task RunAsync()
    {
        try
        {
            await foreach (var msg in _mailbox.Reader.ReadAllAsync(_cts.Token).ConfigureAwait(false))
            {
                switch (msg)
                {
                    case Deposit dep:
                        _balance += dep.Amount; // Only this loop modifies _balance.
                        break;
                    case GetBalance get:
                        get.SetResult(_balance); // Only this loop reads _balance.
                        break;
                }
            }
        }
        catch (OperationCanceledException) when (_cts.IsCancellationRequested) { }
    }

    public async ValueTask DisposeAsync()
    {
        _cts.Cancel();
        _mailbox.Writer.TryComplete();
        await _runner.ConfigureAwait(false);
        _cts.Dispose();
    }

    private abstract record Message;
    private sealed record Deposit(decimal Amount) : Message;
    private sealed record GetBalance : Message
    {
        private readonly TaskCompletionSource<decimal> _tcs =
            new(TaskCreationOptions.RunContinuationsAsynchronously);
        public Task<decimal> Task => _tcs.Task;
        public void SetResult(decimal value) => _tcs.TrySetResult(value);
    }
}

// Reasoning:
// - Ownership: _balance is owned by the RunAsync loop
// - Access patterns: Other threads send messages, don't access _balance directly
// - Boundaries: Clear ownership boundary (only RunAsync modifies _balance)
// - Conclusion: No synchronization needed; correctness is easier to reason about
```

**Confinement strategies**

1. **Thread confinement**: Keep mutable state on a single thread (e.g., `ThreadLocal<T>`, actor loops).
2. **Component confinement**: Keep mutable state private to a single component (e.g., private fields in a class that processes messages sequentially).
3. **Temporal confinement**: Keep mutable state only during a specific time window (e.g., local variables in async methods).

**Example: Reasoning about thread confinement**

```csharp
// Correct: Thread-local state (confinement).
public class ThreadLocalCounter
{
    private readonly ThreadLocal<int> _localCount = new ThreadLocal<int>(() => 0);

    public void Increment()
    {
        _localCount.Value++; // Each thread has its own copy.
    }

    public int Value => _localCount.Value ?? 0;
}

// Reasoning:
// - Confinement: Each thread has its own _localCount.Value
// - No sharing: No shared mutable state across threads
// - Conclusion: No synchronization needed; correct by design
```

**Trade-offs: Shared state vs ownership**

| Aspect | Shared mutable state | Ownership/confinement |
|--------|---------------------|----------------------|
| **Reasoning complexity** | High (must reason about all interleavings) | Low (single-threaded reasoning) |
| **Synchronization** | Required (locks, atomics) | Not required |
| **Performance** | Contention overhead | No contention, but message-passing overhead |
| **Scalability** | Limited by contention | Scales well (can shard actors) |
| **API design** | Direct method calls | Message-passing API |

**Mentor guidance: When to use which**

- **Use shared mutable state with locks** when:
  - State is simple (few fields, simple invariants).
  - Contention is low.
  - Direct method calls are preferred.

- **Use ownership/confinement** when:
  - State has complex invariants.
  - Contention is high.
  - You want simpler reasoning about correctness.

**Performance note**

- Ownership/confinement eliminates synchronization overhead but adds message-passing overhead.
- For high-contention scenarios, ownership often wins due to reduced contention.
- Use profiling to measure actual performance; don't assume one approach is always faster.

**Good to know**

- **Ownership simplifies reasoning**: Single-threaded reasoning is easier than multi-threaded reasoning.
- **Confinement eliminates races**: If state is confined, there are no races.
- **Message passing is the key**: Ownership requires message-passing APIs (Channels, Dataflow, or custom queues).
- See section **3.7** for actor-style patterns and implementation details.

### 3. **Invariants, pre/post-conditions, and representation consistency**

This section provides the **deep treatment** of invariants, pre/post-conditions, and representation consistency in concurrent programs. These concepts are essential for reasoning about correctness.

**Invariants**

An **invariant** is a condition that must always be true for an object or system. In concurrent programs, invariants must hold even when multiple threads are accessing and modifying state.

**Types of invariants**

1. **Class invariants**: Conditions that must hold for all instances of a class (e.g., `_balance >= 0` for a bank account).
2. **Loop invariants**: Conditions that hold at the beginning and end of each loop iteration.
3. **State invariants**: Conditions that relate multiple fields (e.g., `_count == _items.Count`).

**Reasoning about invariants in concurrent code**

When reasoning about invariants:

1. **Identify the invariant**: What condition must always be true?
2. **Identify mutation points**: Where is state modified?
3. **Verify maintenance**: Is the invariant maintained at all mutation points?
4. **Check visibility**: Are all threads guaranteed to see consistent state?

**Example: Reasoning about a class invariant**

```csharp
// Correct: Invariant maintained (_balance >= 0).
public class SafeBankAccount
{
    private decimal _balance = 0;
    private readonly object _lock = new object();

    // Invariant: _balance >= 0

    public void Deposit(decimal amount)
    {
        if (amount < 0)
            throw new ArgumentException("Amount must be non-negative", nameof(amount));

        lock (_lock)
        {
            _balance += amount; // Invariant maintained: _balance was >= 0, adding non-negative preserves it.
        }
    }

    public void Withdraw(decimal amount)
    {
        if (amount < 0)
            throw new ArgumentException("Amount must be non-negative", nameof(amount));

        lock (_lock)
        {
            if (_balance < amount)
                throw new InvalidOperationException("Insufficient funds");

            _balance -= amount; // Invariant maintained: _balance >= amount, so _balance - amount >= 0.
        }
    }

    public decimal Balance
    {
        get
        {
            lock (_lock)
            {
                return _balance; // Invariant holds: _balance >= 0.
            }
        }
    }
}

// Reasoning:
// - Invariant: _balance >= 0
// - Mutation points: Deposit, Withdraw
// - Maintenance: Both methods check preconditions and maintain invariant
// - Visibility: lock ensures all threads see consistent state
// - Conclusion: Invariant is maintained
```

**Pre-conditions and post-conditions**

- **Pre-condition**: A condition that must be true before a method executes.
- **Post-condition**: A condition that must be true after a method executes.

**Reasoning about pre/post-conditions**

When reasoning about pre/post-conditions:

1. **Identify pre-conditions**: What must be true before the method runs?
2. **Identify post-conditions**: What must be true after the method runs?
3. **Verify establishment**: Does the method establish the post-condition if the pre-condition holds?
4. **Check in concurrent context**: Are pre-conditions checked atomically? Are post-conditions visible to all threads?

**Example: Reasoning about pre/post-conditions**

```csharp
// Correct: Pre/post-conditions with atomicity.
public class SafeStack<T>
{
    private readonly List<T> _items = new();
    private readonly object _lock = new object();

    public void Push(T item)
    {
        if (item is null)
            throw new ArgumentNullException(nameof(item)); // Pre-condition check.

        lock (_lock)
        {
            _items.Add(item);
            // Post-condition: _items.Count > 0 && _items[_items.Count - 1] == item
        }
    }

    public T Pop()
    {
        lock (_lock)
        {
            // Pre-condition: _items.Count > 0
            if (_items.Count == 0)
                throw new InvalidOperationException("Stack is empty");

            var item = _items[^1];
            _items.RemoveAt(_items.Count - 1);
            // Post-condition: _items.Count == old(_items.Count) - 1 && result == old(_items[^1])
            return item;
        }
    }

    public int Count
    {
        get
        {
            lock (_lock)
            {
                return _items.Count;
            }
        }
    }
}

// Reasoning:
// - Push pre-condition: item != null
// - Push post-condition: item is on top of stack
// - Pop pre-condition: stack is not empty
// - Pop post-condition: top element is removed and returned
// - Atomicity: lock ensures pre/post-conditions are checked and established atomically
// - Conclusion: Correct
```

**Representation consistency**

**Representation consistency** means that the internal representation of an object (its fields) is consistent with its abstract state (what the object represents). In concurrent programs, representation consistency must be maintained even when multiple threads are accessing the object.

**Reasoning about representation consistency**

When reasoning about representation consistency:

1. **Identify the abstract state**: What does the object represent?
2. **Identify the representation**: How is that state stored in fields?
3. **Identify consistency rules**: What relationships must hold between fields?
4. **Verify atomicity**: Are updates to related fields atomic?

**Example: Reasoning about representation consistency**

```csharp
// Incorrect: Representation inconsistency (fields updated separately).
public class InconsistentPoint
{
    private int _x = 0;
    private int _y = 0;
    private readonly object _lock = new object();

    public void Move(int newX, int newY)
    {
        lock (_lock)
        {
            _x = newX; // Update x.
        }
        // Another thread may read (_x, _y) here and see inconsistent state.
        lock (_lock)
        {
            _y = newY; // Update y.
        }
    }

    public (int X, int Y) GetPosition()
    {
        lock (_lock)
        {
            return (_x, _y); // May read inconsistent state if Move is called concurrently.
        }
    }
}

// Reasoning:
// - Abstract state: A point (x, y)
// - Representation: _x, _y fields
// - Consistency rule: (_x, _y) should always represent a valid point
// - Problem: Move updates _x and _y in separate critical sections
// - Conclusion: Representation inconsistency possible
```

**Correct: Atomic updates**

```csharp
// Correct: Representation consistency (atomic updates).
public class ConsistentPoint
{
    private int _x = 0;
    private int _y = 0;
    private readonly object _lock = new object();

    public void Move(int newX, int newY)
    {
        lock (_lock)
        {
            _x = newX; // Update both fields atomically.
            _y = newY;
        }
    }

    public (int X, int Y) GetPosition()
    {
        lock (_lock)
        {
            return (_x, _y); // Always reads consistent state.
        }
    }
}

// Reasoning:
// - Abstract state: A point (x, y)
// - Representation: _x, _y fields
// - Consistency rule: (_x, _y) should always represent a valid point
// - Solution: Update both fields in a single critical section
// - Conclusion: Representation consistency maintained
```

**Complex invariants and multi-field consistency**

When invariants span multiple fields, updates must be atomic:

```csharp
// Correct: Multi-field invariant maintained atomically.
public class Rectangle
{
    private int _width = 0;
    private int _height = 0;
    private readonly object _lock = new object();

    // Invariant: _width > 0 && _height > 0 (for a valid rectangle)

    public void Resize(int newWidth, int newHeight)
    {
        if (newWidth <= 0 || newHeight <= 0)
            throw new ArgumentException("Dimensions must be positive");

        lock (_lock)
        {
            // Atomic update: both fields updated together to maintain invariant.
            _width = newWidth;
            _height = newHeight;
        }
    }

    public int Area
    {
        get
        {
            lock (_lock)
            {
                // Invariant holds: _width > 0 && _height > 0
                return _width * _height;
            }
        }
    }
}

// Reasoning:
// - Invariant: _width > 0 && _height > 0
// - Mutation point: Resize
// - Maintenance: Pre-condition check ensures invariant is maintained
// - Atomicity: Both fields updated in single critical section
// - Conclusion: Invariant maintained
```

**Mentor guidance: Reasoning checklist**

When reasoning about invariants and consistency:

- **Identify invariants**: What conditions must always be true?
- **Identify mutation points**: Where is state modified?
- **Verify maintenance**: Is the invariant maintained at all mutation points?
- **Check atomicity**: Are updates to related fields atomic?
- **Verify visibility**: Are all threads guaranteed to see consistent state?

**Performance note**

- Maintaining invariants requires synchronization, which has overhead.
- Use the lightest synchronization mechanism that provides necessary guarantees.
- Consider ownership/confinement for complex invariants to avoid fine-grained locking.

**Good to know**

- **Invariants simplify reasoning**: If invariants are maintained, you can reason about correctness more easily.
- **Pre/post-conditions document contracts**: They make the expected behavior explicit.
- **Representation consistency prevents bugs**: Inconsistent representations lead to incorrect behavior.
- **Atomicity is key**: Updates to related fields must be atomic to maintain consistency.

### 4. **Ordering guarantees (happens-before, visibility, publication)**

**Cross-reference**: See section **4.2** for the .NET memory model, reordering, visibility, and tearing. This section focuses on **reasoning about** ordering guarantees and their implications for correctness.

**Happens-before relationships**

A **happens-before** relationship is a partial ordering of operations that guarantees that one operation is visible to another. In .NET, synchronization operations establish happens-before relationships.

**Reasoning about happens-before**

When reasoning about happens-before:

1. **Identify synchronization points**: Where do synchronization operations occur (locks, `Interlocked`, `volatile`, etc.)?
2. **Identify ordering requirements**: What ordering is required for correctness?
3. **Verify happens-before**: Do synchronization operations establish the necessary happens-before relationships?

**Example: Reasoning about happens-before**

```csharp
// Correct: Happens-before established via lock.
public class PublicationExample
{
    private string? _data = null;
    private readonly object _lock = new object();

    public void Initialize(string data)
    {
        lock (_lock)
        {
            _data = data; // Write under lock.
        }
        // Lock release establishes happens-before for subsequent lock acquisitions.
    }

    public string? GetData()
    {
        lock (_lock)
        {
            // Lock acquisition establishes happens-before with previous lock release.
            return _data; // Read under lock - guaranteed to see _data if Initialize completed.
        }
    }
}

// Reasoning:
// - Synchronization point: lock
// - Ordering requirement: GetData must see _data if Initialize completed
// - Happens-before: Lock release in Initialize happens-before lock acquisition in GetData
// - Conclusion: Correct ordering guaranteed
```

**Visibility**

**Visibility** means that writes by one thread are visible to reads by another thread. In .NET, synchronization operations ensure visibility.

**Reasoning about visibility**

When reasoning about visibility:

1. **Identify writes**: Where is data written?
2. **Identify reads**: Where is data read?
3. **Check synchronization**: Are writes and reads properly synchronized?
4. **Verify visibility**: Do synchronization operations ensure visibility?

**Example: Reasoning about visibility**

```csharp
// Incorrect: No visibility guarantee.
public class InvisibleData
{
    private bool _initialized = false;
    private string _data = string.Empty;

    public void Initialize(string data)
    {
        _data = data; // Write without synchronization.
        _initialized = true; // Write without synchronization.
    }

    public string GetData()
    {
        if (_initialized) // Read without synchronization.
        {
            return _data; // Read without synchronization - may not see writes!
        }
        throw new InvalidOperationException("Not initialized");
    }
}

// Reasoning:
// - Writes: Initialize writes _data and _initialized
// - Reads: GetData reads _initialized and _data
// - Synchronization: None
// - Visibility: Not guaranteed - reads may not see writes
// - Conclusion: Incorrect - visibility not guaranteed
```

**Correct: Visibility via volatile**

```csharp
// Correct: Visibility via volatile.
public class VisibleData
{
    private volatile bool _initialized = false; // volatile ensures visibility.
    private string _data = string.Empty;
    private readonly object _lock = new object();

    public void Initialize(string data)
    {
        lock (_lock)
        {
            _data = data; // Write under lock.
        }
        _initialized = true; // volatile write ensures visibility.
    }

    public string GetData()
    {
        if (_initialized) // volatile read ensures visibility.
        {
            lock (_lock)
            {
                return _data; // Read under lock - guaranteed to see _data.
            }
        }
        throw new InvalidOperationException("Not initialized");
    }
}

// Reasoning:
// - Writes: Initialize writes _data (under lock) and _initialized (volatile)
// - Reads: GetData reads _initialized (volatile) and _data (under lock)
// - Synchronization: lock for _data, volatile for _initialized
// - Visibility: volatile ensures visibility of _initialized; lock ensures visibility of _data
// - Conclusion: Correct - visibility guaranteed
```

**Publication**

**Publication** is the act of making data visible to other threads. In .NET, proper publication requires synchronization to ensure visibility and ordering.

**Reasoning about publication**

When reasoning about publication:

1. **Identify the data**: What data is being published?
2. **Identify the publisher**: Which thread publishes the data?
3. **Identify the subscribers**: Which threads consume the data?
4. **Check synchronization**: Is publication properly synchronized?

**Example: Reasoning about safe publication**

```csharp
// Correct: Safe publication via lock.
public class SafePublisher
{
    private readonly object _lock = new object();
    private List<string>? _publishedData = null;

    public void Publish(List<string> data)
    {
        lock (_lock)
        {
            _publishedData = data; // Publication under lock.
        }
        // Lock release ensures visibility to other threads.
    }

    public List<string>? GetPublishedData()
    {
        lock (_lock)
        {
            return _publishedData; // Read under lock - guaranteed to see published data.
        }
    }
}

// Reasoning:
// - Data: _publishedData
// - Publisher: Publish method
// - Subscribers: GetPublishedData method
// - Synchronization: lock ensures visibility and ordering
// - Conclusion: Safe publication
```

**Initialization and publication**

A common pattern is initializing an object and then publishing it:

```csharp
// Correct: Safe initialization and publication.
public class LazyInitializer
{
    private readonly object _lock = new object();
    private ExpensiveObject? _instance = null;

    public ExpensiveObject GetInstance()
    {
        if (_instance is null) // Double-checked locking pattern.
        {
            lock (_lock)
            {
                if (_instance is null)
                {
                    _instance = new ExpensiveObject(); // Initialization and publication under lock.
                }
            }
        }
        return _instance; // Safe to read after null check (but see note below).
    }
}

// Note: In C# 15, prefer Lazy<T> or other thread-safe initialization patterns.
// This example illustrates the reasoning; see section 3.1 for modern patterns.

// Reasoning:
// - Initialization: ExpensiveObject created under lock
// - Publication: _instance assigned under lock
// - Synchronization: lock ensures visibility and ordering
// - Conclusion: Safe initialization and publication
```

**Modern C# 15 patterns for safe publication**

```csharp
// Preferred: Using Lazy<T> for thread-safe initialization.
public class ModernLazyInitializer
{
    private readonly Lazy<ExpensiveObject> _lazy = new Lazy<ExpensiveObject>(
        () => new ExpensiveObject(),
        LazyThreadSafetyMode.ExecutionAndPublication
    );

    public ExpensiveObject GetInstance() => _lazy.Value; // Thread-safe, efficient.
}

// Preferred: Using Interlocked for simple publication.
public class InterlockedPublisher
{
    private ExpensiveObject? _instance = null;

    public ExpensiveObject GetOrCreate()
    {
        var instance = Volatile.Read(ref _instance);
        if (instance is null)
        {
            var newInstance = new ExpensiveObject();
            instance = Interlocked.CompareExchange(ref _instance, newInstance, null) ?? newInstance;
        }
        return instance;
    }
}
```

**Mentor guidance: Reasoning checklist**

When reasoning about ordering guarantees:

- **Identify synchronization points**: Where do synchronization operations occur?
- **Identify ordering requirements**: What ordering is required for correctness?
- **Verify happens-before**: Do synchronization operations establish necessary happens-before relationships?
- **Check visibility**: Are writes visible to reads?
- **Verify publication**: Is publication properly synchronized?

**Performance note**

- Synchronization operations have overhead; use the lightest mechanism that provides necessary guarantees.
- `volatile` has minimal overhead but provides limited guarantees (visibility, not atomicity).
- `Interlocked` is lock-free and fast for simple operations.
- `lock` has moderate overhead but provides strong guarantees.

**Good to know**

- **Happens-before is transitive**: If A happens-before B and B happens-before C, then A happens-before C.
- **Visibility is not automatic**: Without synchronization, writes may not be visible to other threads.
- **Publication requires synchronization**: Simply assigning a value is not sufficient for safe publication.
- See section **4.2** for the .NET memory model and detailed coverage of reordering, visibility, and tearing.

### 5. **Idempotency, commutativity, and associativity in concurrent operations**

This section provides the **deep treatment** of idempotency, commutativity, and associativity in concurrent operations. These properties are essential for reasoning about correctness in concurrent systems.

**Idempotency**

An operation is **idempotent** if applying it multiple times has the same effect as applying it once. In concurrent programs, idempotency allows safe retries and duplicate processing.

**Reasoning about idempotency**

When reasoning about idempotency:

1. **Identify the operation**: What operation is being performed?
2. **Check idempotency**: Does applying the operation multiple times have the same effect as applying it once?
3. **Consider concurrency**: Is the operation idempotent even when applied concurrently?

**Example: Reasoning about idempotent operations**

```csharp
// Idempotent: Setting a value.
public class IdempotentSetter
{
    private string _value = string.Empty;
    private readonly object _lock = new object();

    public void SetValue(string value)
    {
        lock (_lock)
        {
            _value = value; // Idempotent: setting to the same value multiple times has the same effect.
        }
    }
}

// Reasoning:
// - Operation: SetValue
// - Idempotency: Setting _value to "X" multiple times has the same effect as setting it once
// - Conclusion: Idempotent

// Non-idempotent: Incrementing a counter.
public class NonIdempotentIncrementer
{
    private int _count = 0;
    private readonly object _lock = new object();

    public void Increment()
    {
        lock (_lock)
        {
            _count++; // Not idempotent: incrementing multiple times has different effects.
        }
    }
}

// Reasoning:
// - Operation: Increment
// - Idempotency: Incrementing multiple times has different effects (count increases)
// - Conclusion: Not idempotent
```

**Idempotency in concurrent operations**

For concurrent operations, idempotency must hold even when operations are applied concurrently:

```csharp
// Idempotent: Upsert operation (insert or update).
public class IdempotentDictionary<TKey, TValue>
{
    private readonly Dictionary<TKey, TValue> _dict = new();
    private readonly object _lock = new object();

    public void Upsert(TKey key, TValue value)
    {
        lock (_lock)
        {
            _dict[key] = value; // Idempotent: setting the same key-value pair multiple times has the same effect.
        }
    }
}

// Reasoning:
// - Operation: Upsert
// - Idempotency: Upserting the same key-value pair multiple times has the same effect
// - Concurrency: Lock ensures atomicity, so concurrent upserts are also idempotent
// - Conclusion: Idempotent
```

**Commutativity**

An operation is **commutative** if the order of operations does not matter. In concurrent programs, commutativity allows operations to be reordered safely.

**Reasoning about commutativity**

When reasoning about commutativity:

1. **Identify the operations**: What operations are being performed?
2. **Check commutativity**: Does the order of operations matter?
3. **Consider concurrency**: Are operations commutative even when applied concurrently?

**Example: Reasoning about commutative operations**

```csharp
// Commutative: Adding to a set.
public class CommutativeSet<T>
{
    private readonly HashSet<T> _set = new();
    private readonly object _lock = new object();

    public void Add(T item)
    {
        lock (_lock)
        {
            _set.Add(item); // Commutative: adding A then B has the same effect as adding B then A.
        }
    }
}

// Reasoning:
// - Operations: Add(A), Add(B)
// - Commutativity: Add(A) then Add(B) has the same effect as Add(B) then Add(A)
// - Conclusion: Commutative

// Non-commutative: Pushing to a stack.
public class NonCommutativeStack<T>
{
    private readonly Stack<T> _stack = new();
    private readonly object _lock = new object();

    public void Push(T item)
    {
        lock (_lock)
        {
            _stack.Push(item); // Not commutative: Push(A) then Push(B) has different effect than Push(B) then Push(A).
        }
    }
}

// Reasoning:
// - Operations: Push(A), Push(B)
// - Commutativity: Push(A) then Push(B) results in [B, A], Push(B) then Push(A) results in [A, B]
// - Conclusion: Not commutative
```

**Commutativity in concurrent operations**

For concurrent operations, commutativity allows safe reordering:

```csharp
// Commutative: Updating independent fields.
public class CommutativeUpdates
{
    private int _x = 0;
    private int _y = 0;
    private readonly object _lock = new object();

    public void UpdateX(int value)
    {
        lock (_lock)
        {
            _x = value; // Commutative with UpdateY: order doesn't matter.
        }
    }

    public void UpdateY(int value)
    {
        lock (_lock)
        {
            _y = value; // Commutative with UpdateX: order doesn't matter.
        }
    }
}

// Reasoning:
// - Operations: UpdateX(1), UpdateY(2)
// - Commutativity: UpdateX(1) then UpdateY(2) has the same effect as UpdateY(2) then UpdateX(1)
// - Conclusion: Commutative (because _x and _y are independent)
```

**Associativity**

An operation is **associative** if grouping does not matter. In concurrent programs, associativity allows operations to be parallelized safely.

**Reasoning about associativity**

When reasoning about associativity:

1. **Identify the operation**: What operation is being performed?
2. **Check associativity**: Does grouping matter?
3. **Consider parallelization**: Can the operation be parallelized safely?

**Example: Reasoning about associative operations**

```csharp
// Associative: Addition.
public class AssociativeAdder
{
    public int Add(int a, int b, int c)
    {
        // Associative: (a + b) + c == a + (b + c)
        return a + b + c;
    }
}

// Reasoning:
// - Operation: Addition
// - Associativity: (1 + 2) + 3 == 1 + (2 + 3) == 6
// - Conclusion: Associative

// Associative: String concatenation (in some contexts).
public class AssociativeConcatenator
{
    public string Concat(string a, string b, string c)
    {
        // Associative: (a + b) + c == a + (b + c) (same result, though performance may differ)
        return a + b + c;
    }
}

// Reasoning:
// - Operation: String concatenation
// - Associativity: ("a" + "b") + "c" == "a" + ("b" + "c") == "abc"
// - Conclusion: Associative (though allocation patterns differ)
```

**Associativity in parallel operations**

Associativity enables safe parallelization:

```csharp
// Associative: Sum operation (can be parallelized).
public class ParallelSum
{
    public int SumParallel(int[] numbers)
    {
        return numbers
            .AsParallel()
            .Aggregate(
                0,
                (sum, value) => sum + value, // Associative: (sum + a) + b == sum + (a + b)
                (left, right) => left + right // Associative merge: (left + right) + more == left + (right + more)
            );
    }
}

// Reasoning:
// - Operation: Sum
// - Associativity: (a + b) + c == a + (b + c)
// - Parallelization: Can safely parallelize because grouping doesn't matter
// - Conclusion: Associative, safe to parallelize
```

**Combining properties: Idempotent, commutative, and associative operations**

Operations that are idempotent, commutative, and associative are ideal for concurrent systems:

```csharp
// Ideal: Idempotent, commutative, and associative operation.
public class IdealConcurrentOperation
{
    private readonly HashSet<int> _set = new();
    private readonly object _lock = new object();

    public void Add(int value)
    {
        lock (_lock)
        {
            _set.Add(value);
            // Idempotent: adding the same value multiple times has the same effect
            // Commutative: adding A then B has the same effect as adding B then A
            // Associative: (add A, add B), add C has the same effect as add A, (add B, add C)
        }
    }
}

// Reasoning:
// - Idempotency: Adding the same value multiple times has the same effect
// - Commutativity: Order doesn't matter
// - Associativity: Grouping doesn't matter
// - Conclusion: Ideal for concurrent operations
```

**Mentor guidance: Using these properties**

When designing concurrent operations:

- **Idempotency**: Enables safe retries and duplicate processing.
- **Commutativity**: Allows safe reordering of operations.
- **Associativity**: Enables safe parallelization.

**Performance note**

- Operations that are idempotent, commutative, and associative are easier to parallelize and optimize.
- These properties reduce the need for strict ordering, which can improve performance.
- Use these properties to design lock-free or low-contention algorithms.

**Good to know**

- **Idempotency is essential for retries**: If an operation is idempotent, you can safely retry it.
- **Commutativity enables reordering**: Commutative operations can be reordered for performance.
- **Associativity enables parallelization**: Associative operations can be parallelized safely.
- **These properties simplify reasoning**: If operations have these properties, correctness is easier to reason about.

Reasoning about correctness in concurrent programs requires understanding:
