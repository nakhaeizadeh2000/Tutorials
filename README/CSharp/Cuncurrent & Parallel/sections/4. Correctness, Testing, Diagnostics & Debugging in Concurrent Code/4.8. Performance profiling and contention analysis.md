### 1. **Sampling vs instrumenting profilers**

**Sampling profilers**

- **Sampling profilers** periodically sample the call stack.
- **Low overhead** (typically 1-5%).
- **Statistical** view of where time is spent.
- Examples: **PerfView** (sampling mode), **Visual Studio Profiler** (sampling).

**How sampling works**

- Profiler interrupts execution at regular intervals (e.g., every 1ms).
- Records the current call stack.
- Aggregates samples to show hotspots.

**When to use sampling**

- **Initial profiling**: Find hotspots quickly.
- **Production profiling**: Low overhead allows profiling in production.
- **CPU-bound code**: Best for CPU-intensive workloads.

**Example: sampling profile output**

```
Function                    Samples    % of Total
ProcessItem                 5000       50%
ProcessData                 3000       30%
HelperMethod                2000       20%
```

**Instrumenting profilers**

- **Instrumenting profilers** inject code at method entry/exit.
- **Higher overhead** (typically 10-50%).
- **Precise** timing for each method call.
- Examples: **Visual Studio Profiler** (instrumentation), **dotTrace**.

**How instrumentation works**

- Profiler injects code before and after each method.
- Records entry/exit times.
- Tracks call counts and timing.

**When to use instrumentation**

- **Precise timing**: Need exact method timings.
- **Call counts**: Need to know how many times methods are called.
- **I/O-bound code**: Better for I/O operations.

**Example: instrumentation profile output**

```
Function                    Calls    Total Time    Avg Time
ProcessItem                 10000    5000ms        0.5ms
ProcessData                 5000     3000ms        0.6ms
HelperMethod                20000    2000ms        0.1ms
```

**Choosing the right profiler**

- **Start with sampling**: Low overhead, good for finding hotspots.
- **Use instrumentation**: When you need precise timing or call counts.
- **Combine both**: Use sampling to find hotspots, instrumentation to drill down.

**Mentor emphasis**

- **Start with sampling** for initial profiling.
- **Use instrumentation** for precise analysis.
- **Consider overhead** when profiling production systems.
- **Use both** for comprehensive analysis.

### 2. **Using PerfView / Visual Studio Profiler for async and parallel code**

**PerfView for async code**

- **PerfView** is a free profiling tool from Microsoft.
- Excellent for profiling async and parallel code.
- Shows thread time lines and async operations.

**Collecting a PerfView trace**

1. Run PerfView: `PerfView.exe collect`
2. Select "Thread Time" for async profiling.
3. Start collection, run your application.
4. Stop collection and analyze.

**Analyzing async code in PerfView**

- **Thread Time Stacks**: Shows where threads spend time.
- **CPU Stacks**: Shows CPU usage.
- **GC Stacks**: Shows garbage collection.

**Example: PerfView analysis**

- Look for threads blocked on `Task.Result` or `.Wait()`.
- Look for threads waiting on locks (`Monitor.Enter`).
- Look for ThreadPool starvation (all threads blocked).

**Visual Studio Profiler**

- **Visual Studio Profiler** is integrated into Visual Studio.
- Easier to use than PerfView for basic profiling.
- Good for CPU and memory profiling.

**Using Visual Studio Profiler**

1. **Debug → Performance Profiler**.
2. Select **CPU Usage** or **Instrumentation**.
3. Start profiling, run your application.
4. Stop and analyze results.

**Profiling async code in Visual Studio**

- **CPU Usage**: Shows CPU time per method.
- **Call Tree**: Shows call hierarchy.
- **Hot Path**: Shows the hottest execution paths.

**Example: profiling parallel code**

```csharp
public class ParallelProfilingExample
{
    public void ProcessParallel()
    {
        Parallel.For(0, 1000, i =>
        {
            ProcessItem(i); // Profile this method
        });
    }

    private void ProcessItem(int id)
    {
        Thread.Sleep(10); // Simulate work
    }
}
```

- Profiler shows time spent in `ProcessItem` across all threads.
- Can identify if parallelization is effective.

**Mentor emphasis**

- **Use PerfView** for detailed async/parallel analysis.
- **Use Visual Studio Profiler** for quick CPU profiling.
- **Look for blocking operations** (`.Result`, `.Wait()`, locks).
- **Analyze thread time lines** to see thread utilization.

### 3. **Identifying synchronization bottlenecks and excessive locking**

**What is a synchronization bottleneck?**

- **Synchronization bottleneck**: Code spends significant time waiting for locks or synchronization.
- Reduces parallelism and throughput.
- Can cause ThreadPool starvation.

**Detecting lock contention**

- **PerfView**: Look for `Monitor.Enter` or `WaitOne` in stacks.
- **Visual Studio Profiler**: Look for time spent in lock-related methods.
- **Custom counters**: Track lock acquisition time (see 4.5).

**Example: detecting contention**

```csharp
public class ContentionExample
{
    private readonly Dictionary<string, int> _cache = new();
    private readonly object _lock = new(); // Single lock for entire cache

    public int GetValue(string key)
    {
        lock (_lock) // Contention hotspot
        {
            return _cache.TryGetValue(key, out var value) ? value : 0;
        }
    }

    public void SetValue(string key, int value)
    {
        lock (_lock) // Contention hotspot
        {
            _cache[key] = value;
        }
    }
}
```

- Profiler shows time spent in `Monitor.Enter`.
- High contention indicates a bottleneck.

**Reducing contention**

- **Fine-grained locking**: Use multiple locks instead of one.
- **Lock-free structures**: Use `ConcurrentDictionary` instead of `Dictionary` with locks.
- **Reduce lock scope**: Hold locks for as short a time as possible.

**Example: reducing contention**

```csharp
public class ReducedContentionExample
{
    // GOOD: Use ConcurrentDictionary (lock-free internally)
    private readonly ConcurrentDictionary<string, int> _cache = new();

    public int GetValue(string key)
    {
        return _cache.GetOrAdd(key, _ => 0); // No explicit locking
    }

    public void SetValue(string key, int value)
    {
        _cache[key] = value; // No explicit locking
    }
}
```

**Measuring lock wait time**

```csharp
public class LockWaitTimeMeasurement
{
    private readonly object _lock = new();
    private long _totalWaitTimeMs = 0;
    private long _lockCount = 0;

    public void EnterLock()
    {
        var sw = System.Diagnostics.Stopwatch.StartNew();
        bool acquired = false;
        
        Monitor.TryEnter(_lock, 0, ref acquired);
        if (!acquired)
        {
            Monitor.Enter(_lock); // Block until acquired
        }
        
        sw.Stop();
        Interlocked.Add(ref _totalWaitTimeMs, sw.ElapsedMilliseconds);
        Interlocked.Increment(ref _lockCount);
    }

    public (long AvgWaitMs, long TotalWaits) GetStats()
    {
        var total = Interlocked.Read(ref _totalWaitTimeMs);
        var count = Interlocked.Read(ref _lockCount);
        return (count > 0 ? total / count : 0, count);
    }
}
```

**Identifying excessive locking**

- **Look for**: Locks held for long periods.
- **Look for**: Locks around I/O operations.
- **Look for**: Nested locks (potential deadlock risk).

**Example: excessive locking**

```csharp
public class ExcessiveLockingExample
{
    private readonly object _lock = new();

    public async Task ProcessAsync()
    {
        lock (_lock) // BAD: Lock held during async operation
        {
            await DoIOAsync(); // Blocks thread holding lock
        }
    }

    private async Task DoIOAsync()
    {
        await Task.Delay(1000); // I/O operation
    }
}
```

- This pattern causes contention and potential deadlocks.

**Mentor emphasis**

- **Profile to find contention**: Use PerfView or Visual Studio Profiler.
- **Reduce lock scope**: Hold locks for minimal time.
- **Use lock-free structures**: `ConcurrentDictionary`, `ConcurrentBag`, etc.
- **Measure lock wait time**: Track contention metrics.

### 4. **Measuring CPU vs I/O wait time in concurrent workloads**

**Why measure CPU vs I/O?**

- **CPU-bound** work benefits from parallelism (more cores = faster).
- **I/O-bound** work benefits from async/await (don't block threads).
- Understanding the mix helps choose the right approach.

**Measuring CPU time**

- **PerfView**: CPU Stacks show CPU time.
- **Visual Studio Profiler**: CPU Usage shows CPU time.
- **Process.GetCurrentProcess().TotalProcessorTime**: Programmatic measurement.

**Example: measuring CPU time**

```csharp
public class CPUTimeMeasurement
{
    public void MeasureCPUWork()
    {
        var process = Process.GetCurrentProcess();
        var startCpu = process.TotalProcessorTime;
        
        // CPU-bound work
        Parallel.For(0, 1000, i =>
        {
            var sum = Enumerable.Range(0, 1000).Sum();
        });
        
        var endCpu = process.TotalProcessorTime;
        var cpuTime = endCpu - startCpu;
        Console.WriteLine($"CPU time: {cpuTime.TotalMilliseconds}ms");
    }
}
```

**Measuring I/O wait time**

- **PerfView**: Thread Time Stacks show I/O wait.
- **Custom instrumentation**: Measure time spent in async I/O operations.

**Example: measuring I/O wait**

```csharp
public class IOWaitMeasurement
{
    public async Task MeasureIOWork()
    {
        var sw = System.Diagnostics.Stopwatch.StartNew();
        
        // I/O-bound work
        using var http = new HttpClient();
        await http.GetStringAsync("https://example.com");
        
        sw.Stop();
        Console.WriteLine($"Total time: {sw.ElapsedMilliseconds}ms");
        // I/O wait time is the difference between total time and CPU time
    }
}
```

**Profiling mixed workloads**

- **PerfView**: Shows both CPU and I/O wait in Thread Time Stacks.
- **Look for**: Threads blocked on I/O (`WaitOne`, `ReadFile`, etc.).
- **Look for**: Threads using CPU (`ProcessItem`, calculations, etc.).

**Example: mixed workload**

```csharp
public class MixedWorkloadExample
{
    public async Task ProcessMixedAsync()
    {
        // CPU-bound work
        var cpuResult = await Task.Run(() =>
        {
            return Enumerable.Range(0, 1000000).Sum();
        });
        
        // I/O-bound work
        using var http = new HttpClient();
        var ioResult = await http.GetStringAsync("https://example.com");
    }
}
```

- Profiler shows CPU time for calculations and I/O wait for HTTP call.

**Optimizing based on measurements**

- **CPU-bound**: Use `Parallel.For` or `PLINQ` for parallelism.
- **I/O-bound**: Use `async`/`await` to avoid blocking threads.
- **Mixed**: Combine both approaches.

**Mentor emphasis**

- **Measure CPU vs I/O** to choose the right approach.
- **Use PerfView** to see both CPU and I/O wait.
- **CPU-bound**: Parallelize with `Parallel.For`/`PLINQ`.
- **I/O-bound**: Use `async`/`await` to avoid blocking.

### 5. **Interpreting ThreadPool and GC metrics for tuning**

**ThreadPool metrics**

- **Thread Count**: Number of ThreadPool threads.
- **Available Threads**: Threads available for work.
- **Queue Length**: Pending work items.
- **Throughput**: Work items processed per second.

**Monitoring ThreadPool health**

```csharp
public class ThreadPoolMonitor
{
    public static void LogThreadPoolStats()
    {
        ThreadPool.GetAvailableThreads(out int workerThreads, out int completionPortThreads);
        ThreadPool.GetMaxThreads(out int maxWorkerThreads, out int maxCompletionPortThreads);
        ThreadPool.GetMinThreads(out int minWorkerThreads, out int minCompletionPortThreads);

        Console.WriteLine($"Worker threads: {workerThreads}/{maxWorkerThreads} (min: {minWorkerThreads})");
        Console.WriteLine($"Completion port threads: {completionPortThreads}/{maxCompletionPortThreads}");
        
        // Alert if low availability
        if (workerThreads < maxWorkerThreads * 0.1)
        {
            Console.WriteLine("WARNING: ThreadPool starvation risk!");
        }
    }
}
```

**ThreadPool tuning**

- **Increase MinThreads**: If threads are frequently created/destroyed.
- **Monitor Queue Length**: High queue length indicates starvation.
- **Check Available Threads**: Low availability indicates contention.

**GC metrics**

- **Gen 0/1/2 Collections**: Frequency of garbage collections.
- **GC Pause Time**: Time spent in GC pauses.
- **Allocation Rate**: Bytes allocated per second.

**Monitoring GC**

```csharp
public class GCMonitor
{
    public static void LogGCStats()
    {
        var gen0 = GC.CollectionCount(0);
        var gen1 = GC.CollectionCount(1);
        var gen2 = GC.CollectionCount(2);
        
        Console.WriteLine($"Gen 0 collections: {gen0}");
        Console.WriteLine($"Gen 1 collections: {gen1}");
        Console.WriteLine($"Gen 2 collections: {gen2}");
        
        // Alert if frequent Gen 2 collections
        if (gen2 > 10)
        {
            Console.WriteLine("WARNING: Frequent Gen 2 collections (performance impact)!");
        }
    }
}
```

**GC tuning**

- **Reduce allocations**: Fewer allocations = less GC pressure.
- **Use object pooling**: Reuse objects instead of allocating.
- **Monitor Gen 2 collections**: Frequent Gen 2 collections indicate memory pressure.

**Example: reducing allocations**

```csharp
public class AllocationReductionExample
{
    // BAD: Allocates on every call
    public string ProcessBad(int value)
    {
        return $"Processed {value}"; // String allocation
    }

    // GOOD: Reuse StringBuilder
    private readonly StringBuilder _sb = new();
    public string ProcessGood(int value)
    {
        _sb.Clear();
        _sb.Append("Processed ");
        _sb.Append(value);
        return _sb.ToString();
    }
}
```

**Using dotnet-counters for monitoring**

```bash
# Monitor ThreadPool
dotnet-counters monitor -p <process-id> System.Runtime[thread-pool]

# Monitor GC
dotnet-counters monitor -p <process-id> System.Runtime[gc]

# Monitor all runtime counters
dotnet-counters monitor -p <process-id> System.Runtime
```

**Interpreting metrics**

- **ThreadPool starvation**: Low available threads, high queue length.
- **GC pressure**: Frequent Gen 2 collections, high allocation rate.
- **Contention**: High lock wait time, low CPU utilization.

**Mentor emphasis**

- **Monitor ThreadPool** to detect starvation.
- **Monitor GC** to detect memory pressure.
- **Tune based on metrics**: Increase MinThreads, reduce allocations.
- **Use dotnet-counters** for real-time monitoring.
