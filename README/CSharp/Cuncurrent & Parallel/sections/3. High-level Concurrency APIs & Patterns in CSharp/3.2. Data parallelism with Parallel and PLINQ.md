### 1. **Parallel.For and Parallel.ForEach basic usage**

**What they are**

- `Parallel.For` and `Parallel.ForEach` are high-level APIs for running **independent iterations** across multiple cores.
- They are designed for **CPU-bound work** with minimal blocking.

**When to use**

- The body is:
  - mostly pure computation
  - independent per iteration (or uses thread-safe aggregation)
  - heavy enough to amortize parallel overhead

**When not to use**

- For **I/O-bound** work (HTTP, DB, file). Use async + `Task.WhenAll` and throttling instead. See **3.1** and **3.5**.
- When the per-iteration work is tiny (overhead dominates).

**Common mistakes**

- Mutating shared state inside the loop without synchronization → races/bugs (see **1.7**).
- Locking a shared resource in every iteration → contention removes parallelism.
- Using `Parallel.ForEach` with `async` lambdas:
  - `Parallel.ForEach` expects synchronous work; mixing `async` creates hidden tasks and incorrect completion semantics.
  - For async pipelines, use `Task.WhenAll` (with throttling) or Channels/Dataflow (sections **3.3** and **3.5**).

**Runnable example: in-place transform**

```csharp
using System;
using System.Threading.Tasks;

static class ParallelBasics
{
    public static void SquareInPlace(int[] data)
    {
        Parallel.For(0, data.Length, i =>
        {
            // Safe: each iteration owns a unique index.
            data[i] = data[i] * data[i];
        });
    }
}
```

**Performance note**

- For numeric arrays, consider SIMD vectorization (see **1.5**) and combine it with `Parallel.For` only when data is large enough.

### 2. **Parallel.Invoke and structured parallel regions**

**What it is**

- `Parallel.Invoke` runs a **small set of independent actions** in parallel.
- It is a good fit for “structured parallelism”: a region of code where you know the parallel branches up front.

**When to use**

- You have a handful of coarse tasks:
  - compress + encrypt + index in parallel
  - compute multiple independent summaries

**Trade-offs**

- **Pros**: very readable when there are a few branches; error handling aggregates exceptions.
- **Cons**: not suited to large dynamic item sets (use `Parallel.ForEach`/PLINQ).

**Runnable example**

```csharp
using System;
using System.Threading.Tasks;

static class ParallelInvokeDemo
{
    public static void Run()
    {
        int a = 0, b = 0, c = 0;

        Parallel.Invoke(
            () => a = Work(1),
            () => b = Work(2),
            () => c = Work(3));

        Console.WriteLine(a + b + c);
    }

    private static int Work(int x) => x * x * x;
}
```

**Good to know**

- Exceptions from multiple branches are aggregated (see section **1.7** for exception aggregation patterns).

### 3. **PLINQ query operators and partitioning strategies**

**What PLINQ is**

- PLINQ parallelizes LINQ queries:
  - `source.AsParallel().Where(...).Select(...).ToArray()`
- It’s best for **CPU-bound transformations/aggregations** over large in-memory collections.

**Partitioning (why it matters)**

- PLINQ partitions the input and schedules partitions across workers.
- Performance depends on:
  - how expensive the per-element work is
  - whether work is evenly distributed
  - whether ordering is required

**Key operators / knobs**

- `AsParallel()` enables parallelism.
- `AsOrdered()` preserves ordering (often reduces throughput).
- `WithDegreeOfParallelism(n)` caps concurrency.
- `WithMergeOptions(ParallelMergeOptions...)` influences buffering/latency of results.

**Common mistakes**

- Using PLINQ for I/O-bound work (still blocks threads; worse than async).
- Using PLINQ when the input is small (overhead dominates).
- Assuming results remain ordered without `AsOrdered()`.
- Side effects in query operators (writing to shared state) → contention/bugs.

**Runnable example: CPU-bound query**

```csharp
using System;
using System.Linq;

static class PlinqDemo
{
    public static int[] Transform(int[] data)
    {
        return data
            .AsParallel()
            .Where(x => x > 0)
            .Select(ExpensiveTransform)
            .ToArray();
    }

    private static int ExpensiveTransform(int x)
    {
        // Simulate CPU work.
        int y = x;
        for (int i = 0; i < 1_000; i++) y = (y * 31) ^ i;
        return y;
    }
}
```

**Performance note**

- If you need streaming/low-latency results, merge options can matter. If you need strict order, expect a throughput hit.

### 4. **Tuning degree of parallelism and merge options**

**Degree of parallelism**

- Default is usually near core count, but:
  - oversubscription increases context switching and contention
  - undersubscription leaves performance on the table
- Practical starting point:
  - `MaxDegreeOfParallelism = Environment.ProcessorCount`
  - then measure and adjust based on CPU saturation and throughput

**ParallelOptions (Parallel.*)**

- Use `ParallelOptions` to set:
  - `MaxDegreeOfParallelism`
  - `CancellationToken`

**PLINQ knobs**

- `WithDegreeOfParallelism(n)`
- `WithExecutionMode(ParallelExecutionMode.ForceParallelism)` (use only if you’ve measured; can make things worse)
- `WithMergeOptions(...)`:
  - affects buffering and how quickly results are produced vs overall throughput

**Runnable example: bounded parallel loop**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

static class TuningDemo
{
    public static void Process(int[] data, CancellationToken ct)
    {
        Parallel.For(0, data.Length, new ParallelOptions
        {
            MaxDegreeOfParallelism = Math.Max(1, Environment.ProcessorCount - 1),
            CancellationToken = ct
        }, i =>
        {
            data[i] = data[i] + 1;
        });
    }
}
```

**Good to know**

- In service environments, leaving one core for “everything else” can reduce tail-latency. Measure; don’t guess.

### 5. **When data parallelism is harmful (small workloads, UI, excessive contention)**

**Top reasons parallelism hurts**

- **Too small**: overhead dominates.
- **Contention**: shared locks, shared collections, shared cache lines (false sharing).
- **Memory bandwidth bound**: more threads just fight for the same memory throughput.
- **UI (frontend)**: CPU parallelism can starve UI responsiveness if done on UI thread; always offload from UI thread and avoid saturating all cores.

**Mentor checklist before parallelizing**

- Do you have a single-thread baseline measurement?
- Is the work CPU-bound and sufficiently large?
- Is the per-iteration body mostly independent?
- Can you avoid shared writes (or aggregate with thread-local state)?
- Can you cap parallelism to avoid oversubscription?

**Patterns to reduce contention**

- Use local variables and combine results at the end (thread-local aggregation).
- Prefer immutable inputs.
- Use partitioning to improve cache locality.
- Avoid per-iteration locks; if needed, batch work before locking.

**Performance note**

- If you see worse performance after parallelization, don’t “try harder” with more threads. Look for contention, allocation spikes, cache effects, and oversubscription. See **2.6** and **4.8** for measurement/profiling guidance.
