### 1. **Async streams with IAsyncEnumerable\<T\> and await foreach**

**What they are**

- `IAsyncEnumerable<T>` represents an **asynchronous sequence** of values over time.
- Consumption uses `await foreach`, which can `await` between elements.

**When to use**

- When you have **many items** that arrive over time:
  - reading lines from a file/socket
  - processing pages from a paged API
  - streaming events/logs/telemetry
- When you want to **start processing before you have all data**.

**When not to use**

- When you only ever need a **single result** (`Task<T>` is simpler).
- When the data set is small and easily materialized (a simple `List<T>` is cheaper).

**Producer pattern (async iterator)**

```csharp
using System.Collections.Generic;
using System.IO;
using System.Runtime.CompilerServices;
using System.Threading;
using System.Threading.Tasks;

static class AsyncStreamDemo
{
    public static async IAsyncEnumerable<string> ReadLinesAsync(
        string path,
        [EnumeratorCancellation] CancellationToken ct = default)
    {
        using var reader = new StreamReader(path);
        while (!reader.EndOfStream && !ct.IsCancellationRequested)
        {
            var line = await reader.ReadLineAsync().ConfigureAwait(false);
            if (line is null) yield break;
            yield return line;
        }
    }
}
```

**Consumer pattern**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

static class AsyncStreamConsumer
{
    public static async Task PrintLinesAsync(string path, CancellationToken ct = default)
    {
        await foreach (var line in AsyncStreamDemo.ReadLinesAsync(path, ct).ConfigureAwait(false))
        {
            Console.WriteLine(line);
        }
    }
}
```

**Good to know**

- Remember `[EnumeratorCancellation]` on the token parameter to allow `await foreach` to propagate cancellation.

### 2. **Push-based vs pull-based streams**

**Pull-based**

- The **consumer** pulls items when ready:
  - `IEnumerator<T>` (synchronous)
  - `IAsyncEnumerable<T>` (async)
- The consumer controls when iteration advances.

**Push-based**

- The **producer** pushes items as they occur:
  - events, callbacks, `IObservable<T>`
- The producer decides the pace; consumers must keep up or have buffering.

**Why it matters**

- Backpressure is **natural** with pull-based streams (consumer simply stops pulling).
- Backpressure must be **designed** for push-based streams (buffers, dropping, slowing down producers).

**Mentor emphasis**

- For I/O or CPU pipelines where you control the code on both sides, prefer **pull** (`IAsyncEnumerable<T>`) where possible; it’s easier to reason about.
- For external event sources (UI, OS events, Kafka, etc.), you’re often in a **push** world; use reactive patterns, queues, and backpressure strategies.

### 3. **Bridging IAsyncEnumerable\<T\> and IObservable\<T\>**

**When you need this**

- Your existing code or ecosystem uses **Rx** (`IObservable<T>`).
- Newer components prefer `IAsyncEnumerable<T>`.
- You need an adapter in either direction.

**From `IAsyncEnumerable<T>` to `IObservable<T>`**

```csharp
using System;
using System.Collections.Generic;
using System.Reactive.Linq;
using System.Threading;
using System.Threading.Tasks;

public static class AsyncEnumerableToObservableExtensions
{
    public static IObservable<T> ToObservable<T>(
        this IAsyncEnumerable<T> source,
        CancellationToken ct = default)
    {
        return Observable.Create<T>(async (observer, cancellationToken) =>
        {
            using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(ct, cancellationToken);

            try
            {
                await foreach (var item in source.WithCancellation(linkedCts.Token).ConfigureAwait(false))
                {
                    observer.OnNext(item);
                }
                observer.OnCompleted();
            }
            catch (OperationCanceledException) when (linkedCts.IsCancellationRequested)
            {
                observer.OnCompleted();
            }
            catch (Exception ex)
            {
                observer.OnError(ex);
            }
        });
    }
}
```

**From `IObservable<T>` to `IAsyncEnumerable<T>`**

```csharp
using System;
using System.Collections.Generic;
using System.Runtime.CompilerServices;
using System.Threading;
using System.Threading.Channels;
using System.Threading.Tasks;

public static class ObservableToAsyncEnumerableExtensions
{
    public static async IAsyncEnumerable<T> ToAsyncEnumerable<T>(
        this IObservable<T> source,
        [EnumeratorCancellation] CancellationToken ct = default)
    {
        var channel = Channel.CreateUnbounded<T>(new UnboundedChannelOptions
        {
            SingleReader = true,
            SingleWriter = false
        });

        using var subscription = source.Subscribe(
            onNext: item => channel.Writer.TryWrite(item),
            onError: ex => channel.Writer.TryComplete(ex),
            onCompleted: () => channel.Writer.TryComplete());

        await foreach (var item in channel.Reader.ReadAllAsync(ct).ConfigureAwait(false))
        {
            yield return item;
        }
    }
}
```

**Good to know**

- These bridges introduce buffering (Channels). Think about memory and backpressure; for high-volume streams, you may want bounded channels and drop strategies.

### 4. **Backpressure and rate limiting in streaming scenarios**

**Backpressure**

- The general idea that **slow consumers** can signal or enforce limits on **fast producers**, preventing unbounded buffering and overload.

**Patterns for backpressure**

- Pull-based: consumer simply stops pulling/awaiting; producer only yields when awaited.
- Push-based:
  - bounded queues (Channels, Dataflow bounded capacities)
  - dropping (sample, throttle, debounce) — especially for UI and telemetry
  - explicit protocols (ACKs, credits, window size)

**Rate limiting**

- Define a maximum rate of processing:
  - requests per second
  - items per time window
- Combine with backpressure to protect:
  - your own CPU/memory
  - downstream services (DBs, HTTP APIs)

**Minimal example: rate-limited async stream consumption**

```csharp
using System;
using System.Collections.Generic;
using System.Threading;
using System.Threading.Tasks;

static class RateLimitedStreaming
{
    public static async Task ConsumeWithRateLimitAsync<T>(
        IAsyncEnumerable<T> source,
        TimeSpan minInterval,
        Func<T, Task> handler,
        CancellationToken ct = default)
    {
        var last = DateTimeOffset.MinValue;

        await foreach (var item in source.WithCancellation(ct).ConfigureAwait(false))
        {
            var now = DateTimeOffset.UtcNow;
            var elapsed = now - last;
            if (elapsed < minInterval)
            {
                var delay = minInterval - elapsed;
                await Task.Delay(delay, ct).ConfigureAwait(false);
            }

            await handler(item).ConfigureAwait(false);
            last = DateTimeOffset.UtcNow;
        }
    }
}
```

**Performance note**

- Rate limiting often **improves** end-to-end latency and error rates by preventing overload. It is not just about “slowing things down”.

### 5. **Common streaming use cases (I/O, UI events, telemetry, logging) (frontend)**

**I/O streaming**

- Reading large files or HTTP responses incrementally.
- Consuming endless event streams (e.g., websockets, message queues).
- Good pattern: `IAsyncEnumerable<T>` for pull-style processing, plus Channels/Dataflow if you need fan-out or buffering (sections **3.3** and **3.5**).

**UI events (frontend)**

- Events are **push-based**:
  - button clicks
  - text changes
  - pointer movement
- Reactive patterns (Rx, `IObservable<T>`, or higher-level frameworks) shine here:
  - throttle/debounce
  - merge/combine/drop

**Telemetry/logging**

- Typically write-intensive, with lossy tolerances.
- Common strategies:
  - background writer with bounded channel
  - dropping or sampling under pressure
  - bulk/batch uploads to reduce overhead

**Good to know**

- For UI frontends: avoid doing long-running work on the UI thread when consuming streams. Offload processing to background tasks, and marshal only the minimal updates back to UI (see **2.3** and **5.5**).
