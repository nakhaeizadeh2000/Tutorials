### 1. **Core Task and ValueTask usage patterns**

**What to return**

- **Return `Task` / `Task<T>` by default** for async APIs.
- **Return `ValueTask` / `ValueTask<T>` only when** you have measured allocation pressure and a high rate of synchronous completion, and you can enforce correct usage. See **1.2** for the full trade-off.

**Signatures (modern best practice)**

- Async methods should usually accept:
  - `CancellationToken cancellationToken = default`
- Prefer:
  - `Task` for “no result”
  - `Task<T>` for “one result”
  - `IAsyncEnumerable<T>` for streaming results over time (see section **3.4**)

**Avoid these in production APIs**

- `async void` (except UI event handlers) — untestable and exceptions crash the process or go to the sync context.
- Synchronous wrappers over async (`.Result`, `.Wait()`, `.GetAwaiter().GetResult()`) — deadlocks/starvation. See **2.3** and **2.1**.

**Hot-path guidance (performance + allocations)**

- Avoid unnecessary `async` state machines when you can return an existing task:

```csharp
public static Task<string> GetCachedOrFetchAsync(bool cached, Task<string> fetchTask)
    => cached ? Task.FromResult("cached") : fetchTask;
```

- But don’t contort code prematurely: correctness and clarity win unless profiling proves otherwise.

**Good to know**

- `Task` allocations are often negligible in I/O-bound code (latency dominates). `ValueTask` is a sharp tool reserved for hot libraries.

### 2. **Composing tasks with Task.WhenAll, Task.WhenAny, and continuations**

**Core combinators**

- `Task.WhenAll(...)`:
  - wait for all tasks to complete
  - throws an exception that represents all failures (multiple exceptions can occur)
- `Task.WhenAny(...)`:
  - wait for the first task to complete
  - you decide what to do with the “losers” (often cancel them)

**Prefer structured composition**

- Prefer `await` + `WhenAll/WhenAny` over `ContinueWith`.
- Deep comparison is in **1.3**; scheduling semantics in **2.5**.

**Example: fan-out/fan-in with `WhenAll` (I/O-bound)**

```csharp
using System;
using System.Net.Http;
using System.Threading;
using System.Threading.Tasks;

static class FanOut
{
    public static async Task<int[]> DownloadSizesAsync(Uri[] uris, CancellationToken ct = default)
    {
        using var http = new HttpClient();

        var tasks = new Task<int>[uris.Length];
        for (int i = 0; i < uris.Length; i++)
        {
            var uri = uris[i];
            tasks[i] = DownloadSizeAsync(http, uri, ct);
        }

        return await Task.WhenAll(tasks).ConfigureAwait(false);
    }

    private static async Task<int> DownloadSizeAsync(HttpClient http, Uri uri, CancellationToken ct)
    {
        var bytes = await http.GetByteArrayAsync(uri, ct).ConfigureAwait(false);
        return bytes.Length;
    }
}
```

**Performance note**

- `WhenAll` fan-out can be dangerous if unbounded. For throttling/backpressure patterns, see **3.5** (deep) and **2.1/2.4** for starvation context.

**Example: first result wins (`WhenAny`) with cancellation of losers**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

static class FirstWins
{
    public static async Task<T> FirstSuccessfulAsync<T>(
        Func<CancellationToken, Task<T>>[] candidates,
        CancellationToken ct = default)
    {
        using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);

        var tasks = new Task<T>[candidates.Length];
        for (int i = 0; i < candidates.Length; i++)
            tasks[i] = candidates[i](cts.Token);

        while (tasks.Length > 0)
        {
            var winner = await Task.WhenAny(tasks).ConfigureAwait(false);
            try
            {
                var result = await winner.ConfigureAwait(false);
                cts.Cancel(); // cancel losers
                return result;
            }
            catch
            {
                // Remove the failed task and continue.
                tasks = tasks.Where(t => t != winner).ToArray();
            }
        }

        throw new InvalidOperationException("All candidates failed.");
    }
}
```

**Good to know**

- The above uses LINQ to keep the example short; for high-frequency paths, avoid repeated `ToArray()` allocations by using a list/indexing.

### 3. **TaskCompletionSource and bridging non-Task-based APIs**

**When you need it**

- You have an event/callback-based API (legacy, interop, or custom).
- You want to expose a `Task`-based API for composition with `await`.

**The right mental model**

- `TaskCompletionSource<T>` (TCS) is a manually-completed promise:
  - you complete it exactly once with success/fault/cancel
  - you must ensure completion in all paths (including errors and cancellation)

**Common mistakes**

- Completing the TCS twice (throws or fails silently depending on method used).
- Forgetting to handle cancellation → tasks that never complete.
- Capturing large closures, keeping objects alive → memory leaks.
- Running continuations inline and causing reentrancy surprises.

**Best-practice defaults**

- Use `TaskCreationOptions.RunContinuationsAsynchronously` to avoid running continuations inline on the completing thread (reduces reentrancy/deadlock hazards).

**Example: wrap a callback API into a `Task`**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

public static class CallbackBridge
{
    // Legacy API: BeginOperation(Action<Exception?, int> callback)
    public static Task<int> BeginOperationAsync(
        Action<Action<Exception?, int>> begin,
        CancellationToken ct = default)
    {
        var tcs = new TaskCompletionSource<int>(TaskCreationOptions.RunContinuationsAsynchronously);

        CancellationTokenRegistration reg = default;
        if (ct.CanBeCanceled)
        {
            reg = ct.Register(() => tcs.TrySetCanceled(ct));
        }

        try
        {
            begin((ex, value) =>
            {
                reg.Dispose();
                if (ex is not null) tcs.TrySetException(ex);
                else tcs.TrySetResult(value);
            });
        }
        catch (Exception ex)
        {
            reg.Dispose();
            tcs.TrySetException(ex);
        }

        return tcs.Task;
    }
}
```

**Good to know**

- If the legacy API supports cancellation, wire it up (don’t just cancel the `Task` while the real operation keeps running).
- For APM (`Begin/End`) specifically, prefer `Task.Factory.FromAsync` where available; see **1.3** (APM vs async/await).

### 4. **Error handling and cancellation patterns with Tasks**

**Error propagation**

- `await` unwraps exceptions and throws the original exception (not `AggregateException`) in most cases.
- `Task.WhenAll` may surface multiple exceptions; be prepared to inspect them in batch scenarios.

**Cancellation**

- Cancellation is **cooperative**, not forceful:
  - pass a `CancellationToken`
  - check it (`ThrowIfCancellationRequested`)
  - ensure called APIs receive it

**Pattern: cancellation + timeout**

- Prefer `CancellationTokenSource.CancelAfter` (or linked tokens) and pass the token down.
- Avoid “timeout by `Task.Delay` + `WhenAny`” unless you also cancel/cleanup losers (otherwise you leak work).

**Example: timeout scope**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

static class TimeoutScope
{
    public static async Task<T> WithTimeoutAsync<T>(
        Func<CancellationToken, Task<T>> operation,
        TimeSpan timeout,
        CancellationToken ct = default)
    {
        using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
        cts.CancelAfter(timeout);
        return await operation(cts.Token).ConfigureAwait(false);
    }
}
```

**Common mistakes**

- Catching `Exception` and swallowing `OperationCanceledException` unintentionally (cancellation should usually flow).
- Using `.Result` to “simplify error handling” → deadlocks/starvation. See **2.3** and **2.1**.

### 5. **Async-friendly resource lifetime and IAsyncDisposable**

**Why `IAsyncDisposable` exists**

- Some resources require async cleanup:
  - flushing buffers
  - closing network connections gracefully
  - completing async pipelines

**Rules**

- Use `await using` for `IAsyncDisposable`.
- If your type owns async resources, implement `IAsyncDisposable` and dispose them asynchronously.
- Don’t mix sync and async dispose incorrectly:
  - if a resource is `IAsyncDisposable`, prefer `await using` at the call site.

**Example: async disposal**

```csharp
using System;
using System.Threading.Tasks;

public sealed class AsyncResource : IAsyncDisposable
{
    public ValueTask DisposeAsync()
    {
        // Pretend we need to flush asynchronously.
        return new ValueTask(Task.Delay(10));
    }
}

static class AsyncDisposeDemo
{
    public static async Task UseAsync()
    {
        await using var r = new AsyncResource();
        // use r...
    }
}
```

**Performance note**

- Async disposal is about correctness and responsiveness under load (don’t block threads during cleanup). Keep disposal fast; if you must do heavy work, move it out of Dispose/DisposeAsync.
