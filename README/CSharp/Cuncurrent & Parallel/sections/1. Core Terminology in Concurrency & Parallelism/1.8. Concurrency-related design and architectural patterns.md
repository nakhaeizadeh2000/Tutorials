### 1. **Producer-Consumer vs Pipeline**

**Short definition**

- **Producer-Consumer pattern**:
  - A pattern where **one or more producer threads** generate data and put it into a **shared queue/buffer**, and **one or more consumer threads** take data from the queue and process it.
  - Producers and consumers are **decoupled**; they don't need to know about each other.
  - Example: A logging system where multiple threads produce log messages, and a single thread consumes and writes them to a file.

- **Pipeline pattern**:
  - A pattern where data flows through **multiple stages**, each stage processes the data and passes it to the next stage.
  - Each stage can run in parallel, processing different items simultaneously.
  - Example: Image processing pipeline: load → resize → filter → save, where each stage processes different images concurrently.

**When to use which**

- **Use Producer-Consumer** when:
  - You have **independent producers and consumers** that don't need to coordinate beyond the queue.
  - You want to **decouple** production and consumption (e.g., event processing, task queues).
  - You need to **buffer work** between producers and consumers (e.g., background job processing).

- **Use Pipeline** when:
  - You have **multi-stage processing** where each stage transforms data for the next stage.
  - You want to **process different items in parallel** across stages (e.g., data transformation pipelines).
  - You need **ordered processing** through stages (each item goes through all stages in order).

**Trade-offs**

- **Producer-Consumer**:
  - **Pros**:
    - **Simple**: Easy to understand and implement.
    - **Decoupled**: Producers and consumers are independent.
    - **Scalable**: Can have multiple producers and consumers.
    - **Buffering**: Queue provides natural backpressure and buffering.
  - **Cons**:
    - **Single stage**: Typically one processing stage (though you can chain multiple producer-consumer pairs).
    - **Ordering**: May not preserve order (depending on queue implementation).

- **Pipeline**:
  - **Pros**:
    - **Multi-stage**: Natural for complex processing workflows.
    - **Parallelism**: Different stages can process different items simultaneously.
    - **Composability**: Easy to add/remove stages.
  - **Cons**:
    - **More complex**: Requires coordination between stages.
    - **Backpressure**: Must handle backpressure at each stage.
    - **Ordering**: Maintaining order across stages can be complex.

**Common mistakes**

- **Using Producer-Consumer for multi-stage processing**:
  - Creating multiple producer-consumer pairs when a pipeline would be more appropriate.
  - **Solution**: Use a pipeline for multi-stage processing; use producer-consumer for simple decoupling.

- **Not handling backpressure**:
  - Creating unbounded queues that can grow indefinitely, causing memory issues.
  - **Solution**: Use bounded queues/channels and handle backpressure appropriately.

- **Not coordinating pipeline stages**:
  - Not properly handling completion, errors, and cancellation across pipeline stages.
  - **Solution**: Use proper coordination mechanisms (e.g., `TaskCompletionSource`, cancellation tokens).

**C# 15-style example: Producer-Consumer vs Pipeline**

```csharp
// Producer-Consumer pattern: Simple decoupling.
public class ProducerConsumerExample
{
    private readonly Channel<string> _channel;

    public ProducerConsumerExample()
    {
        var options = new BoundedChannelOptions(100)
        {
            FullMode = BoundedChannelFullMode.Wait
        };
        _channel = Channel.CreateBounded<string>(options);
    }

    // Producer: Generates data and puts it in the queue.
    public async Task ProduceAsync(string item, CancellationToken cancellationToken = default)
    {
        await _channel.Writer.WriteAsync(item, cancellationToken).ConfigureAwait(false);
    }

    // Consumer: Takes data from the queue and processes it.
    public async Task ConsumeAsync(Func<string, Task> processor, CancellationToken cancellationToken = default)
    {
        await foreach (var item in _channel.Reader.ReadAllAsync(cancellationToken))
        {
            await processor(item).ConfigureAwait(false);
        }
    }

    public void Complete() => _channel.Writer.Complete();
}

// Pipeline pattern: Multi-stage processing.
public class PipelineExample
{
    private readonly Channel<string> _inputChannel;
    private readonly Channel<string> _outputChannel;

    public PipelineExample()
    {
        _inputChannel = Channel.CreateUnbounded<string>();
        _outputChannel = Channel.CreateUnbounded<string>();
    }

    // Stage 1: Load data.
    public async Task Stage1LoadAsync(CancellationToken cancellationToken = default)
    {
        await foreach (var item in _inputChannel.Reader.ReadAllAsync(cancellationToken))
        {
            var loaded = await LoadDataAsync(item, cancellationToken).ConfigureAwait(false);
            await _outputChannel.Writer.WriteAsync(loaded, cancellationToken).ConfigureAwait(false);
        }
        _outputChannel.Writer.Complete();
    }

    // Stage 2: Process data.
    public async Task Stage2ProcessAsync(CancellationToken cancellationToken = default)
    {
        await foreach (var item in _outputChannel.Reader.ReadAllAsync(cancellationToken))
        {
            var processed = await ProcessDataAsync(item, cancellationToken).ConfigureAwait(false);
            // Pass to next stage...
        }
    }

    private async Task<string> LoadDataAsync(string item, CancellationToken cancellationToken)
    {
        await Task.Delay(10, cancellationToken).ConfigureAwait(false);
        return $"Loaded: {item}";
    }

    private async Task<string> ProcessDataAsync(string item, CancellationToken cancellationToken)
    {
        await Task.Delay(10, cancellationToken).ConfigureAwait(false);
        return $"Processed: {item}";
    }
}

// Pipeline with TPL Dataflow (more structured).
public class DataflowPipeline
{
    private readonly TransformBlock<string, string> _loadBlock;
    private readonly TransformBlock<string, string> _processBlock;
    private readonly ActionBlock<string> _saveBlock;

    public DataflowPipeline()
    {
        _loadBlock = new TransformBlock<string, string>(async input =>
        {
            await Task.Delay(10);
            return $"Loaded: {input}";
        });

        _processBlock = new TransformBlock<string, string>(async input =>
        {
            await Task.Delay(10);
            return $"Processed: {input}";
        });

        _saveBlock = new ActionBlock<string>(async result =>
        {
            await Task.Delay(10);
            Console.WriteLine($"Saved: {result}");
        });

        _loadBlock.LinkTo(_processBlock, new DataflowLinkOptions { PropagateCompletion = true });
        _processBlock.LinkTo(_saveBlock, new DataflowLinkOptions { PropagateCompletion = true });
    }

    public async Task ProcessAsync(string item, CancellationToken cancellationToken = default)
    {
        await _loadBlock.SendAsync(item, cancellationToken).ConfigureAwait(false);
    }

    public async Task CompleteAsync()
    {
        _loadBlock.Complete();
        await _saveBlock.Completion.ConfigureAwait(false);
    }
}
```

**Performance note**

- Producer-Consumer is efficient for decoupling producers and consumers with minimal overhead.
- Pipeline can provide better parallelism (different stages process different items simultaneously) but has more coordination overhead.
- Use bounded queues/channels to prevent unbounded memory growth and provide backpressure.

**Good to know**

- **Producer-Consumer is a building block**: You can chain multiple producer-consumer pairs to create pipelines.
- **Pipeline is a specialization**: A pipeline is essentially multiple producer-consumer stages chained together.
- Use `Channel<T>` or `BlockingCollection<T>` for simple producer-consumer, and TPL Dataflow for complex pipelines.
- See section 3.3 for deeper patterns on pipelines, Channels, and Dataflow.

### 2. **Fan-out/Fan-in vs Map-Reduce**

**Short definition**

- **Fan-out/Fan-in pattern**:
  - A pattern where you **distribute work to multiple workers** (fan-out) and then **collect and combine results** (fan-in).
  - Each worker processes a portion of the work independently.
  - Results are collected and optionally combined or aggregated.
  - Example: Processing multiple files in parallel and collecting results.

- **Map-Reduce pattern**:
  - A specific type of fan-out/fan-in where you **map** (transform) data items in parallel, then **reduce** (aggregate) the results.
  - The reduce phase combines all map results into a single result (e.g., sum, count, average).
  - Example: Counting words in multiple documents in parallel, then summing the counts.

**When to use which**

- **Use Fan-out/Fan-in** when:
  - You need to **distribute work** to multiple workers and **collect results**.
  - Results may need to be **combined, aggregated, or processed further**.
  - You want **flexibility** in how results are collected and combined.

- **Use Map-Reduce** when:
  - You have a **data transformation** (map) followed by an **aggregation** (reduce).
  - The reduce operation is **associative and commutative** (e.g., sum, count, max, min).
  - You want a **declarative, functional-style** approach.

**Trade-offs**

- **Fan-out/Fan-in**:
  - **Pros**:
    - **Flexible**: Can collect and combine results in various ways.
    - **General-purpose**: Works for any fan-out/fan-in scenario.
    - **Explicit control**: You control how work is distributed and results are collected.
  - **Cons**:
    - **More code**: Requires manual coordination of fan-out and fan-in.
    - **Less declarative**: More imperative than Map-Reduce.

- **Map-Reduce**:
  - **Pros**:
    - **Declarative**: Functional, composable style.
    - **Optimized**: PLINQ and similar frameworks can optimize map-reduce operations.
    - **Clear intent**: Map and reduce operations are clearly separated.
  - **Cons**:
    - **Limited to aggregation**: Reduce phase must be an aggregation operation.
    - **Less flexible**: Less control over how work is distributed and results are combined.

**Common mistakes**

- **Using Fan-out/Fan-in for simple aggregation**:
  - Manually implementing fan-out/fan-in when Map-Reduce (e.g., PLINQ) would be simpler.
  - **Solution**: Use Map-Reduce (PLINQ) for aggregation scenarios.

- **Using Map-Reduce for non-aggregation scenarios**:
  - Trying to use Map-Reduce when you need to collect results in a non-aggregated way.
  - **Solution**: Use Fan-out/Fan-in for flexible result collection.

- **Not handling partial failures**:
  - Not handling exceptions from individual workers in fan-out/fan-in scenarios.
  - **Solution**: Use `Task.WhenAll` with exception handling, or handle exceptions per worker.

**C# 15-style example: Fan-out/Fan-in vs Map-Reduce**

```csharp
// Fan-out/Fan-in: Distribute work and collect results.
public class FanOutFanInExample
{
    public async Task<Dictionary<string, int>> ProcessFilesFanOutFanIn(string[] filePaths, CancellationToken cancellationToken = default)
    {
        // Fan-out: Distribute work to multiple workers.
        var tasks = filePaths.Select(async path =>
        {
            var content = await File.ReadAllTextAsync(path, cancellationToken).ConfigureAwait(false);
            return ProcessFile(content); // Each worker processes independently.
        }).ToArray();

        // Fan-in: Collect results.
        var results = await Task.WhenAll(tasks).ConfigureAwait(false);

        // Combine results (flexible combination logic).
        var combined = new Dictionary<string, int>();
        foreach (var result in results)
        {
            foreach (var kvp in result)
            {
                combined[kvp.Key] = combined.GetValueOrDefault(kvp.Key, 0) + kvp.Value;
            }
        }

        return combined;
    }

    private Dictionary<string, int> ProcessFile(string content)
    {
        var words = content.Split(' ', StringSplitOptions.RemoveEmptyEntries);
        return words.GroupBy(w => w).ToDictionary(g => g.Key, g => g.Count());
    }
}

// Map-Reduce: Transform and aggregate.
public class MapReduceExample
{
    public int CountWordsMapReduce(string[] filePaths)
    {
        // Map: Transform each file into word counts.
        // Reduce: Aggregate all counts into a single total.
        return filePaths
            .AsParallel()
            .SelectMany(path => File.ReadAllText(path).Split(' ', StringSplitOptions.RemoveEmptyEntries))
            .Count(); // Reduce: Count all words.
    }

    public Dictionary<string, int> WordFrequencyMapReduce(string[] filePaths)
    {
        // Map: Transform each file into word frequencies.
        // Reduce: Aggregate frequencies across all files.
        return filePaths
            .AsParallel()
            .SelectMany(path => File.ReadAllText(path).Split(' ', StringSplitOptions.RemoveEmptyEntries))
            .GroupBy(word => word)
            .ToDictionary(g => g.Key, g => g.Count()); // Reduce: Aggregate by word.
    }
}

// Fan-out/Fan-in with explicit coordination.
public class ExplicitFanOutFanIn
{
    public async Task<List<string>> ProcessItemsFanOutFanIn(string[] items, CancellationToken cancellationToken = default)
    {
        // Fan-out: Process items in parallel.
        var tasks = items.Select(async item =>
        {
            try
            {
                return await ProcessItemAsync(item, cancellationToken).ConfigureAwait(false);
            }
            catch (Exception ex)
            {
                Console.WriteLine($"Error processing {item}: {ex.Message}");
                return null; // Handle failures gracefully.
            }
        }).ToArray();

        // Fan-in: Collect results (with null filtering).
        var results = await Task.WhenAll(tasks).ConfigureAwait(false);
        return results.Where(r => r != null).ToList()!;
    }

    private async Task<string> ProcessItemAsync(string item, CancellationToken cancellationToken)
    {
        await Task.Delay(10, cancellationToken).ConfigureAwait(false);
        return $"Processed: {item}";
    }
}
```

**Performance note**

- Fan-out/Fan-in and Map-Reduce both provide parallelism, but Map-Reduce (PLINQ) can be more optimized for aggregation scenarios.
- Use `Task.WhenAll` for fan-out/fan-in, and PLINQ for Map-Reduce scenarios.
- Both patterns scale well with the number of CPU cores for appropriate workloads.

**Good to know**

- **Map-Reduce is a specialization of Fan-out/Fan-in**: Map-Reduce is essentially fan-out/fan-in with specific map and reduce operations.
- **PLINQ provides Map-Reduce**: Use `AsParallel().Select().Aggregate()` or similar for Map-Reduce in .NET.
- **Fan-out/Fan-in is more general**: Use it when you need flexibility in how work is distributed and results are collected.
- See section 1.5 for PLINQ vs regular LINQ, and section 3.2 for data parallelism patterns.

### 3. **Actor Model vs shared-state concurrency**

**Short definition**

- **Actor Model**:
  - A concurrency model where **actors** are independent entities that communicate via **message passing**.
  - Each actor has **isolated state** and processes messages **sequentially** (one at a time).
  - Actors do not share state; they communicate only through messages.
  - Example: Each actor maintains its own state and processes messages from a mailbox.

- **Shared-state concurrency**:
  - A concurrency model where **multiple threads access shared data structures** with **synchronization** (locks, atomic operations).
  - Threads coordinate access to shared state using locks, `Interlocked`, or thread-safe collections.
  - Example: Multiple threads accessing a shared dictionary protected by locks.

**When to use which**

- **Use Actor Model** when:
  - You have **isolated state** that can be encapsulated in actors.
  - You want to **avoid locks** and reduce contention.
  - You have **complex state machines** or workflows that benefit from message-driven design.
  - You want **better scalability** for high-contention scenarios.

- **Use shared-state concurrency** when:
  - You have **simple, shared data structures** that need occasional synchronization.
  - You want **direct access** to shared data (no message passing overhead).
  - You have **low contention** and locks are not a bottleneck.
  - You need **fine-grained control** over synchronization.

**Trade-offs**

- **Actor Model**:
  - **Pros**:
    - **No locks**: Actors process messages sequentially, eliminating lock contention.
    - **Isolated state**: Each actor's state is private, reducing race conditions.
    - **Scalable**: Can scale to many actors with minimal contention.
    - **Clear ownership**: Each actor owns its state, making reasoning easier.
  - **Cons**:
    - **Message passing overhead**: Sending messages has overhead compared to direct access.
    - **Sequential processing**: Each actor processes messages one at a time (though many actors can run in parallel).
    - **Complexity**: Requires message passing infrastructure and actor management.

- **Shared-state concurrency**:
  - **Pros**:
    - **Direct access**: No message passing overhead.
    - **Simple**: Easy to understand for simple scenarios.
    - **Fine-grained control**: Can optimize synchronization for specific scenarios.
  - **Cons**:
    - **Lock contention**: Locks can become bottlenecks under high contention.
    - **Race conditions**: Requires careful synchronization to avoid race conditions.
    - **Deadlock risk**: Incorrect lock ordering can cause deadlocks.

**Common mistakes**

- **Using shared-state concurrency for high-contention scenarios**:
  - Using locks for frequently accessed data, causing contention and performance issues.
  - **Solution**: Consider actor model or lock-free data structures for high-contention scenarios.

- **Using Actor Model for simple scenarios**:
  - Over-engineering simple shared-state scenarios with actors.
  - **Solution**: Use shared-state concurrency for simple scenarios; reserve actors for complex state management.

- **Not handling actor lifecycle**:
  - Creating actors without proper lifecycle management (creation, shutdown, error handling).
  - **Solution**: Implement proper actor lifecycle management (start, stop, error recovery).

**C# 15-style example: Actor Model vs shared-state concurrency**

```csharp
// Shared-state concurrency: Using locks for shared data.
public class SharedStateCounter
{
    private readonly object _lock = new object();
    private int _count = 0;

    public void Increment()
    {
        lock (_lock)
        {
            _count++; // Shared state protected by lock.
        }
    }

    public int Value
    {
        get
        {
            lock (_lock)
            {
                return _count;
            }
        }
    }
}

// Actor Model: Isolated state with message passing.
public class ActorCounter
{
    private readonly Channel<CounterMessage> _mailbox;
    private int _count = 0; // Isolated state - only accessed by actor.

    public ActorCounter()
    {
        _mailbox = Channel.CreateUnbounded<CounterMessage>();
        _ = Task.Run(async () => await ProcessMessagesAsync()); // Actor loop.
    }

    public async Task SendAsync(CounterMessage message, CancellationToken cancellationToken = default)
    {
        await _mailbox.Writer.WriteAsync(message, cancellationToken).ConfigureAwait(false);
    }

    private async Task ProcessMessagesAsync()
    {
        await foreach (var message in _mailbox.Reader.ReadAllAsync())
        {
            // Process messages sequentially - no locks needed.
            switch (message)
            {
                case IncrementMessage:
                    _count++; // Isolated state - no synchronization needed.
                    break;
                case GetValueMessage getValue:
                    getValue.SetResult(_count);
                    break;
            }
        }
    }
}

public abstract class CounterMessage { }
public class IncrementMessage : CounterMessage { }
public class GetValueMessage : CounterMessage
{
    private readonly TaskCompletionSource<int> _tcs = new();
    public Task<int> Task => _tcs.Task;
    public void SetResult(int value) => _tcs.SetResult(value);
}

// Shared-state concurrency: Complex state with locks.
public class SharedStateBankAccount
{
    private readonly object _lock = new object();
    private decimal _balance = 0;

    public void Deposit(decimal amount)
    {
        lock (_lock)
        {
            _balance += amount; // Shared state - requires locks.
        }
    }

    public bool Withdraw(decimal amount)
    {
        lock (_lock)
        {
            if (_balance >= amount)
            {
                _balance -= amount;
                return true;
            }
            return false;
        }
    }
}

// Actor Model: Complex state with message passing.
public class ActorBankAccount
{
    private readonly Channel<AccountMessage> _mailbox;
    private decimal _balance = 0; // Isolated state.

    public ActorBankAccount()
    {
        _mailbox = Channel.CreateUnbounded<AccountMessage>();
        _ = Task.Run(async () => await ProcessMessagesAsync());
    }

    public async Task SendAsync(AccountMessage message, CancellationToken cancellationToken = default)
    {
        await _mailbox.Writer.WriteAsync(message, cancellationToken).ConfigureAwait(false);
    }

    private async Task ProcessMessagesAsync()
    {
        await foreach (var message in _mailbox.Reader.ReadAllAsync())
        {
            // Sequential processing - no locks, no race conditions.
            switch (message)
            {
                case DepositMessage deposit:
                    _balance += deposit.Amount;
                    break;
                case WithdrawMessage withdraw:
                    if (_balance >= withdraw.Amount)
                    {
                        _balance -= withdraw.Amount;
                        withdraw.SetResult(true);
                    }
                    else
                    {
                        withdraw.SetResult(false);
                    }
                    break;
            }
        }
    }
}

public abstract class AccountMessage { }
public class DepositMessage : AccountMessage
{
    public decimal Amount { get; set; }
}
public class WithdrawMessage : AccountMessage
{
    public decimal Amount { get; set; }
    private readonly TaskCompletionSource<bool> _tcs = new();
    public Task<bool> Task => _tcs.Task;
    public void SetResult(bool value) => _tcs.SetResult(value);
}
```

**Performance note**

- Actor Model eliminates lock contention but adds message passing overhead.
- Shared-state concurrency has lower overhead for low-contention scenarios but can become a bottleneck under high contention.
- Choose based on contention: use actors for high-contention scenarios, shared-state for low-contention scenarios.

**Good to know**

- **Actor Model is a design pattern**: You can implement actors using `Channel<T>`, TPL Dataflow, or dedicated actor frameworks.
- **Shared-state is the default**: Most .NET code uses shared-state concurrency with locks or thread-safe collections.
- **Both have their place**: Use actors for complex state management and high contention; use shared-state for simple scenarios.
- See section 3.7 for deeper patterns on actor-style concurrency in .NET.

### 4. **Message passing vs shared memory**

**Short definition**

- **Message passing**:
  - A concurrency model where threads/actors communicate by **sending messages** to each other.
  - No shared memory; data is copied or passed by reference through messages.
  - Examples: `Channel<T>`, TPL Dataflow, actor frameworks, message queues.

- **Shared memory**:
  - A concurrency model where threads **access the same memory locations** with synchronization (locks, atomic operations).
  - Threads read and write to shared data structures.
  - Examples: Shared variables protected by locks, thread-safe collections, `Interlocked` operations.

**When to use which**

- **Use message passing** when:
  - You want to **avoid locks** and reduce contention.
  - You have **isolated components** that communicate asynchronously.
  - You want **better scalability** for high-contention scenarios.
  - You need **decoupling** between components (e.g., microservices, event-driven systems).

- **Use shared memory** when:
  - You have **simple, shared data structures** that need occasional synchronization.
  - You want **low-latency access** to shared data (no message passing overhead).
  - You have **low contention** and locks are not a bottleneck.
  - You need **fine-grained control** over data access.

**Trade-offs**

- **Message passing**:
  - **Pros**:
    - **No locks**: Eliminates lock contention and deadlock risks.
    - **Isolation**: Components are isolated, reducing race conditions.
    - **Scalable**: Can scale to many components with minimal contention.
    - **Decoupled**: Components don't need to know about each other's implementation.
  - **Cons**:
    - **Message overhead**: Sending messages has overhead (allocation, copying, queuing).
    - **Latency**: Messages are asynchronous, adding latency compared to direct access.
    - **Complexity**: Requires message infrastructure and management.

- **Shared memory**:
  - **Pros**:
    - **Low latency**: Direct access to shared data, no message passing overhead.
    - **Simple**: Easy to understand for simple scenarios.
    - **Efficient**: No allocation or copying overhead for message passing.
  - **Cons**:
    - **Lock contention**: Locks can become bottlenecks under high contention.
    - **Race conditions**: Requires careful synchronization to avoid race conditions.
    - **Deadlock risk**: Incorrect lock ordering can cause deadlocks.
  - **Tight coupling**: Components are tightly coupled through shared data.

**Common mistakes**

- **Using shared memory for high-contention scenarios**:
  - Using locks for frequently accessed data, causing contention and performance issues.
  - **Solution**: Consider message passing or lock-free data structures for high-contention scenarios.

- **Using message passing for simple scenarios**:
  - Over-engineering simple shared-state scenarios with message passing.
  - **Solution**: Use shared memory for simple scenarios; reserve message passing for complex or high-contention scenarios.

- **Not handling message ordering**:
  - Assuming messages are processed in order when they may be processed out of order.
  - **Solution**: Use ordered channels or sequence numbers if ordering matters.

**C# 15-style example: message passing vs shared memory**

```csharp
// Shared memory: Direct access with locks.
public class SharedMemoryCounter
{
    private readonly object _lock = new object();
    private int _count = 0; // Shared memory.

    public void Increment()
    {
        lock (_lock)
        {
            _count++; // Direct access to shared memory.
        }
    }

    public int Value
    {
        get
        {
            lock (_lock)
            {
                return _count; // Direct read from shared memory.
            }
        }
    }
}

// Message passing: Communication via messages.
public class MessagePassingCounter
{
    private readonly Channel<CounterMessage> _channel;
    private int _count = 0; // Private state, not shared.

    public MessagePassingCounter()
    {
        _channel = Channel.CreateUnbounded<CounterMessage>();
        _ = Task.Run(async () => await ProcessMessagesAsync());
    }

    public async Task IncrementAsync(CancellationToken cancellationToken = default)
    {
        await _channel.Writer.WriteAsync(new IncrementMessage(), cancellationToken).ConfigureAwait(false);
    }

    public async Task<int> GetValueAsync(CancellationToken cancellationToken = default)
    {
        var message = new GetValueMessage();
        await _channel.Writer.WriteAsync(message, cancellationToken).ConfigureAwait(false);
        return await message.Task.ConfigureAwait(false);
    }

    private async Task ProcessMessagesAsync()
    {
        await foreach (var message in _channel.Reader.ReadAllAsync())
        {
            switch (message)
            {
                case IncrementMessage:
                    _count++; // Private state - no locks needed.
                    break;
                case GetValueMessage getValue:
                    getValue.SetResult(_count);
                    break;
            }
        }
    }
}

public abstract class CounterMessage { }
public class IncrementMessage : CounterMessage { }
public class GetValueMessage : CounterMessage
{
    private readonly TaskCompletionSource<int> _tcs = new();
    public Task<int> Task => _tcs.Task;
    public void SetResult(int value) => _tcs.SetResult(value);
}

// Shared memory: Thread-safe collection.
public class SharedMemoryCache
{
    private readonly ConcurrentDictionary<string, string> _cache = new(); // Shared memory.

    public void Add(string key, string value)
    {
        _cache[key] = value; // Direct access to shared memory (thread-safe collection).
    }

    public bool TryGet(string key, out string value)
    {
        return _cache.TryGetValue(key, out value!); // Direct read from shared memory.
    }
}

// Message passing: Communication via messages (actor-style).
public class MessagePassingCache
{
    private readonly Channel<CacheMessage> _channel;
    private readonly Dictionary<string, string> _cache = new(); // Private state.

    public MessagePassingCache()
    {
        _channel = Channel.CreateUnbounded<CacheMessage>();
        _ = Task.Run(async () => await ProcessMessagesAsync());
    }

    public async Task AddAsync(string key, string value, CancellationToken cancellationToken = default)
    {
        await _channel.Writer.WriteAsync(new AddMessage { Key = key, Value = value }, cancellationToken)
            .ConfigureAwait(false);
    }

    public async Task<string?> GetAsync(string key, CancellationToken cancellationToken = default)
    {
        var message = new GetMessage { Key = key };
        await _channel.Writer.WriteAsync(message, cancellationToken).ConfigureAwait(false);
        return await message.Task.ConfigureAwait(false);
    }

    private async Task ProcessMessagesAsync()
    {
        await foreach (var message in _channel.Reader.ReadAllAsync())
        {
            switch (message)
            {
                case AddMessage add:
                    _cache[add.Key] = add.Value; // Private state - no locks.
                    break;
                case GetMessage get:
                    _cache.TryGetValue(get.Key, out var value);
                    get.SetResult(value);
                    break;
            }
        }
    }
}

public abstract class CacheMessage { }
public class AddMessage : CacheMessage
{
    public string Key { get; set; } = string.Empty;
    public string Value { get; set; } = string.Empty;
}
public class GetMessage : CacheMessage
{
    public string Key { get; set; } = string.Empty;
    private readonly TaskCompletionSource<string?> _tcs = new();
    public Task<string?> Task => _tcs.Task;
    public void SetResult(string? value) => _tcs.SetResult(value);
}
```

**Performance note**

- Message passing has overhead (allocation, copying, queuing) but eliminates lock contention.
- Shared memory has lower overhead for low-contention scenarios but can become a bottleneck under high contention.
- Choose based on contention and latency requirements: use message passing for high-contention scenarios, shared memory for low-latency, low-contention scenarios.

**Good to know**

- **Message passing is a design pattern**: You can implement it using `Channel<T>`, TPL Dataflow, or message queues.
- **Shared memory is the default**: Most .NET code uses shared memory with locks or thread-safe collections.
- **Hybrid approaches**: You can combine both (e.g., use message passing for coordination, shared memory for data access).
- **Both have their place**: Use message passing for high-contention scenarios and decoupling; use shared memory for simple, low-contention scenarios.
- See section 3.3 for deeper patterns on message passing with Channels and Dataflow, and section 3.7 for actor-style concurrency.
