## 1.4. Synchronization patterns and primitives

This section explains **synchronization primitives in .NET** and when to use each. Other sections may reference these concepts and will point back here for the full treatment (for example: *"See 1.4 for lock vs Monitor"*).

1. **lock keyword vs Monitor**
2. **Mutex vs Semaphore vs SemaphoreSlim**
3. **ReaderWriterLockSlim vs simple lock**
4. **SpinLock vs blocking locks**
5. **Interlocked vs lock**
6. **Volatile vs implicit memory barriers in lock**

### 1. **lock keyword vs Monitor**

**Short definition**

- **`lock` keyword**:
  - C# language syntax that provides a convenient way to acquire and release a mutual-exclusion lock.
  - Compiles to `Monitor.Enter` / `Monitor.Exit` with proper exception handling (try/finally).
  - The most common synchronization primitive in C#.

- **`Monitor` class**:
  - The underlying .NET class that provides the mutual-exclusion mechanism.
  - `lock` is syntactic sugar over `Monitor.Enter` / `Monitor.Exit`.
  - `Monitor` also provides additional features: `TryEnter`, `Wait`, `Pulse`, `PulseAll` (for condition variables).

**When to use which**

- **Use `lock`** (preferred in C# 15):
  - For all standard mutual-exclusion scenarios (protecting shared data, critical sections).
  - When you need simple, exception-safe locking.

- **Use `Monitor` directly** when:
  - You need **timeout-based locking** (`Monitor.TryEnter` with timeout).
  - You need **condition variables** (`Monitor.Wait`, `Monitor.Pulse`, `Monitor.PulseAll`) for producer-consumer patterns.
  - You need to check if a lock is held (`Monitor.IsEntered` in .NET Core 2.1+).

**Trade-offs**

- **`lock` keyword**:
  - **Pros**:
    - **Exception safety**: Automatically releases the lock even if an exception is thrown (compiler generates try/finally).
    - **Readability**: Clear, concise syntax.
    - **Less error-prone**: Harder to forget to release the lock.
  - **Cons**:
    - **No timeout**: Cannot specify a timeout (must use `Monitor.TryEnter` directly).
    - **No condition variables**: Cannot use `Wait`/`Pulse` directly (must use `Monitor` explicitly).

- **`Monitor` class**:
  - **Pros**:
    - **More control**: `TryEnter` with timeout, condition variables (`Wait`/`Pulse`).
    - **Flexibility**: Can implement advanced synchronization patterns.
  - **Cons**:
    - **More verbose**: Must manually handle try/finally for exception safety.
    - **Easier to misuse**: Forgetting to call `Exit` in a finally block can cause deadlocks.

**Common mistakes (what a mentor would call out)**

- **Using `Monitor` directly without try/finally**:
  - Calling `Monitor.Enter` without ensuring `Monitor.Exit` in a finally block, leading to deadlocks if an exception occurs.
  - **Solution**: Use `lock` for simple cases, or always wrap `Monitor.Enter` in try/finally.

- **Nested locking without consistent ordering**:
  - Acquiring multiple locks in different orders in different code paths, causing deadlocks.
  - **Solution**: Establish a consistent lock ordering protocol, or use higher-level patterns (e.g., actor model, message passing).

- **Locking on public objects or `this`**:
  - Using `lock (this)` or `lock (publicField)` exposes your lock to external code, risking deadlocks.
  - **Solution**: Use a private, readonly object field as the lock target: `private readonly object _lock = new object();`

**C# 15-style example: lock vs Monitor**

```csharp
// Using lock keyword (preferred for simple cases).
public class Counter
{
    private readonly object _lock = new object();
    private int _value;

    public void Increment()
    {
        lock (_lock)
        {
            _value++;
        }
    }

    public int Value
    {
        get
        {
            lock (_lock)
            {
                return _value;
            }
        }
    }
}

// Using Monitor directly for timeout.
public class TimeoutCounter
{
    private readonly object _lock = new object();
    private int _value;

    public bool TryIncrement(TimeSpan timeout)
    {
        if (Monitor.TryEnter(_lock, timeout))
        {
            try
            {
                _value++;
                return true;
            }
            finally
            {
                Monitor.Exit(_lock);
            }
        }
        return false;
    }
}

// Using Monitor for condition variables (producer-consumer pattern).
public class BoundedQueue<T>
{
    private readonly object _lock = new object();
    private readonly Queue<T> _queue = new();
    private readonly int _capacity;

    public BoundedQueue(int capacity) => _capacity = capacity;

    public void Enqueue(T item)
    {
        lock (_lock)
        {
            while (_queue.Count >= _capacity)
            {
                Monitor.Wait(_lock); // Wait until space is available.
            }
            _queue.Enqueue(item);
            Monitor.Pulse(_lock); // Notify waiting consumers.
        }
    }

    public T Dequeue()
    {
        lock (_lock)
        {
            while (_queue.Count == 0)
            {
                Monitor.Wait(_lock); // Wait until items are available.
            }
            var item = _queue.Dequeue();
            Monitor.Pulse(_lock); // Notify waiting producers.
            return item;
        }
    }
}
```

**Performance note**

- `lock` and `Monitor` have the same performance characteristics (they compile to the same code).
- For high-contention scenarios, consider `ReaderWriterLockSlim` (multiple readers) or lock-free patterns with `Interlocked` (see below).
- Lock contention can become a bottleneck; measure and consider alternative designs (e.g., reducing shared state, using actor patterns).

**Good to know**

- `lock` is compiled to `Monitor.Enter` / `Monitor.Exit` with automatic exception handling.
- In modern .NET, `Monitor` uses efficient synchronization primitives (e.g., spin-waiting before blocking).
- For async code, use `SemaphoreSlim.WaitAsync` instead of `lock` (see section 1.4.2 and 3.5).

### 2. **Mutex vs Semaphore vs SemaphoreSlim**

**Short definition**

- **`Mutex`**:
  - A **system-wide** synchronization primitive that can be used across processes.
  - Provides mutual exclusion (only one thread/process can own it at a time).
  - Can be named and shared across processes.
  - More expensive than process-local locks.

- **`Semaphore`**:
  - A **system-wide** synchronization primitive that allows a specified number of threads/processes to enter.
  - Can be named and shared across processes.
  - More expensive than process-local alternatives.

- **`SemaphoreSlim`**:
  - A **lightweight, process-local** semaphore for use within a single process.
  - Supports both synchronous (`Wait`) and asynchronous (`WaitAsync`) waiting.
  - Preferred for most scenarios in modern .NET.

**When to use which**

- **Use `SemaphoreSlim`** (preferred in C# 15/.NET 9+):
  - For **process-local** synchronization (99% of cases).
  - When you need to limit concurrency (e.g., throttling I/O operations).
  - When you need async support (`WaitAsync`).
  - For rate limiting, resource pooling, and bounded concurrency.

- **Use `Mutex`** only when:
  - You need **cross-process** synchronization (e.g., ensuring only one instance of an application runs).
  - You need system-wide mutual exclusion.

- **Use `Semaphore`** only when:
  - You need **cross-process** semaphore semantics (rare).
  - You need to share a semaphore across multiple processes.

**Trade-offs**

- **`SemaphoreSlim`**:
  - **Pros**:
    - **Lightweight**: Fast, low-overhead for process-local scenarios.
    - **Async support**: `WaitAsync` for use in async/await code.
    - **Modern API**: Well-integrated with `CancellationToken`.
  - **Cons**:
    - **Process-local only**: Cannot be shared across processes.

- **`Mutex`**:
  - **Pros**:
    - **Cross-process**: Can be shared across processes (named mutex).
    - **System-wide mutual exclusion**: Ensures only one owner across the entire system.
  - **Cons**:
    - **Heavyweight**: More expensive than process-local locks.
    - **No async support**: Blocking only.
  - **Rarely needed**: Most applications don't need cross-process synchronization.

- **`Semaphore`**:
  - **Pros**:
    - **Cross-process**: Can be shared across processes (named semaphore).
  - **Cons**:
    - **Heavyweight**: More expensive than `SemaphoreSlim`.
    - **No async support**: Blocking only.
  - **Rarely needed**: Most applications don't need cross-process semaphores.

**Common mistakes**

- **Using `Mutex` for process-local locking**:
  - Using `Mutex` instead of `lock` or `SemaphoreSlim` for single-process scenarios.
  - **Solution**: Use `lock` for mutual exclusion, `SemaphoreSlim` for limiting concurrency.

- **Using `Semaphore` instead of `SemaphoreSlim`**:
  - Using the heavyweight `Semaphore` when `SemaphoreSlim` would suffice.
  - **Solution**: Use `SemaphoreSlim` unless you need cross-process synchronization.

- **Blocking on `SemaphoreSlim.Wait` in async code**:
  - Calling `semaphore.Wait()` in an async method instead of `await semaphore.WaitAsync()`.
  - **Solution**: Always use `WaitAsync` in async code to avoid blocking threads.

**C# 15-style example: Mutex vs Semaphore vs SemaphoreSlim**

```csharp
// Using SemaphoreSlim for throttling I/O operations (preferred).
public class ThrottledHttpClient
{
    private readonly HttpClient _httpClient;
    private readonly SemaphoreSlim _semaphore;

    public ThrottledHttpClient(HttpClient httpClient, int maxConcurrency)
    {
        _httpClient = httpClient;
        _semaphore = new SemaphoreSlim(maxConcurrency, maxConcurrency);
    }

    public async Task<string> GetStringAsync(string url, CancellationToken cancellationToken = default)
    {
        await _semaphore.WaitAsync(cancellationToken).ConfigureAwait(false);
        try
        {
            return await _httpClient.GetStringAsync(url, cancellationToken).ConfigureAwait(false);
        }
        finally
        {
            _semaphore.Release();
        }
    }
}

// Using Mutex for cross-process single-instance enforcement (rare).
public class SingleInstanceApp
{
    private static Mutex? _mutex;

    public static bool TryAcquireSingleInstance(string appName)
    {
        _mutex = new Mutex(initiallyOwned: true, name: appName, out bool createdNew);
        return createdNew; // If false, another instance is already running.
    }

    public static void ReleaseSingleInstance()
    {
        _mutex?.ReleaseMutex();
        _mutex?.Dispose();
    }
}

// Using SemaphoreSlim for resource pooling.
public class ConnectionPool<T>
{
    private readonly SemaphoreSlim _semaphore;
    private readonly ConcurrentQueue<T> _pool = new();

    public ConnectionPool(int maxConnections, Func<T> factory)
    {
        _semaphore = new SemaphoreSlim(maxConnections, maxConnections);
        for (int i = 0; i < maxConnections; i++)
        {
            _pool.Enqueue(factory());
        }
    }

    public async Task<T> AcquireAsync(CancellationToken cancellationToken = default)
    {
        await _semaphore.WaitAsync(cancellationToken).ConfigureAwait(false);
        if (_pool.TryDequeue(out var connection))
        {
            return connection;
        }
        throw new InvalidOperationException("Pool exhausted");
    }

    public void Release(T connection)
    {
        _pool.Enqueue(connection);
        _semaphore.Release();
    }
}
```

**Performance note**

- `SemaphoreSlim` is optimized for process-local scenarios and has minimal overhead.
- `Mutex` and `Semaphore` involve kernel transitions and are significantly slower; only use when cross-process synchronization is required.
- For high-contention scenarios, consider reducing the need for synchronization (e.g., using lock-free data structures, actor patterns).

**Good to know**

- `SemaphoreSlim` is the go-to choice for limiting concurrency in modern .NET applications.
- For async code, always use `SemaphoreSlim.WaitAsync` instead of blocking `Wait` methods.
- See section 3.5 for deeper patterns on throttling and coordination with `SemaphoreSlim`.

### 3. **ReaderWriterLockSlim vs simple lock**

**Short definition**

- **`lock` (simple mutual exclusion)**:
  - Only one thread can hold the lock at a time (exclusive access).
  - Simple, fast for low-contention scenarios.
  - No distinction between readers and writers.

- **`ReaderWriterLockSlim`**:
  - Allows **multiple readers** to hold the lock simultaneously, but **only one writer** (exclusive).
  - Optimized for scenarios where reads are much more common than writes.
  - More complex than `lock`, with higher overhead.

**When to use which**

- **Use `lock`** (preferred by default):
  - For most scenarios where you need mutual exclusion.
  - When reads and writes are roughly balanced, or when contention is low.
  - When simplicity and maintainability are priorities.

- **Use `ReaderWriterLockSlim`** when:
  - You have a **read-heavy** workload (many readers, few writers).
  - You have **measured** that `lock` is a bottleneck due to reader contention.
  - The performance benefit of allowing concurrent reads outweighs the complexity cost.

**Trade-offs**

- **`lock`**:
  - **Pros**:
    - **Simple**: Easy to understand and maintain.
    - **Fast**: Low overhead for low-contention scenarios.
    - **Exception-safe**: Works naturally with `lock` keyword.
  - **Cons**:
    - **Exclusive**: Even readers block each other.
    - Can become a bottleneck if many threads are reading frequently.

- **`ReaderWriterLockSlim`**:
  - **Pros**:
    - **Concurrent reads**: Multiple readers can proceed simultaneously.
    - **Better scalability**: For read-heavy workloads, can significantly improve throughput.
  - **Cons**:
    - **Complexity**: More complex API (EnterReadLock, EnterWriteLock, ExitReadLock, ExitWriteLock).
    - **Higher overhead**: More expensive than `lock` for low-contention scenarios.
    - **Potential for deadlocks**: Upgrading from read to write lock can deadlock if not careful.
  - **Risk**: If writes are frequent, `ReaderWriterLockSlim` can perform worse than `lock`.

**Common mistakes**

- **Using `ReaderWriterLockSlim` without measuring**:
  - Assuming it will be faster than `lock` without profiling.
  - **Solution**: Always measure; `lock` is often fast enough, and `ReaderWriterLockSlim` adds complexity.

- **Upgrading locks incorrectly**:
  - Calling `EnterWriteLock` while already holding a read lock (can deadlock).
  - **Solution**: Release the read lock before acquiring a write lock, or use `TryEnterWriteLock` with timeout.

- **Forgetting to release locks**:
  - Not calling `ExitReadLock` / `ExitWriteLock` in a finally block.
  - **Solution**: Always use try/finally, or consider helper methods that wrap the lock acquisition.

**C# 15-style example: lock vs ReaderWriterLockSlim**

```csharp
// Using simple lock (preferred for most cases).
public class SimpleCache<TKey, TValue>
{
    private readonly Dictionary<TKey, TValue> _cache = new();
    private readonly object _lock = new object();

    public TValue? Get(TKey key)
    {
        lock (_lock)
        {
            return _cache.TryGetValue(key, out var value) ? value : default;
        }
    }

    public void Set(TKey key, TValue value)
    {
        lock (_lock)
        {
            _cache[key] = value;
        }
    }
}

// Using ReaderWriterLockSlim for read-heavy scenarios (use only if measured).
public class ReadHeavyCache<TKey, TValue>
{
    private readonly Dictionary<TKey, TValue> _cache = new();
    private readonly ReaderWriterLockSlim _lock = new();

    public TValue? Get(TKey key)
    {
        _lock.EnterReadLock();
        try
        {
            return _cache.TryGetValue(key, out var value) ? value : default;
        }
        finally
        {
            _lock.ExitReadLock();
        }
    }

    public void Set(TKey key, TValue value)
    {
        _lock.EnterWriteLock();
        try
        {
            _cache[key] = value;
        }
        finally
        {
            _lock.ExitWriteLock();
        }
    }

    public void Dispose()
    {
        _lock.Dispose();
    }
}

// Helper method to reduce boilerplate (C# 15 style).
public static class ReaderWriterLockSlimExtensions
{
    public static T Read<T>(this ReaderWriterLockSlim rwLock, Func<T> func)
    {
        rwLock.EnterReadLock();
        try
        {
            return func();
        }
        finally
        {
            rwLock.ExitReadLock();
        }
    }

    public static void Write(this ReaderWriterLockSlim rwLock, Action action)
    {
        rwLock.EnterWriteLock();
        try
        {
            action();
        }
        finally
        {
            rwLock.ExitWriteLock();
        }
    }
}

// Usage with helper methods.
public TValue? GetWithHelper(TKey key)
{
    return _lock.Read(() => _cache.TryGetValue(key, out var value) ? value : default);
}
```

**Performance note**

- `lock` is typically fast enough for most scenarios; only consider `ReaderWriterLockSlim` if profiling shows reader contention is a bottleneck.
- `ReaderWriterLockSlim` has higher overhead than `lock`; it only pays off when you have many concurrent readers and few writers.
- For modern .NET, consider `ConcurrentDictionary` for thread-safe dictionaries instead of manual locking (see section 3.x for concurrent collections).

**Good to know**

- `ReaderWriterLockSlim` is a **slim** version (process-local, lightweight) compared to the older `ReaderWriterLock` (which is obsolete).
- Always dispose `ReaderWriterLockSlim` when done (implements `IDisposable`).
- Consider immutable data structures or lock-free alternatives (e.g., `ConcurrentDictionary`) before reaching for `ReaderWriterLockSlim`.

### 4. **SpinLock vs blocking locks**

**Short definition**

- **Blocking locks** (`lock`, `Monitor`, `Mutex`, `Semaphore`):
  - When a thread cannot acquire the lock, it **blocks** (suspends) and yields the CPU to other threads.
  - The OS scheduler manages blocked threads.
  - Appropriate for locks that may be held for longer periods or when contention is expected.

- **`SpinLock`**:
  - When a thread cannot acquire the lock, it **spins** (repeatedly checks if the lock is available) instead of blocking.
  - Keeps the CPU busy, consuming CPU cycles while waiting.
  - Appropriate only for very short critical sections with low contention.

**When to use which**

- **Use blocking locks** (`lock`, `Monitor`, `SemaphoreSlim`) by default:
  - For all normal synchronization scenarios.
  - When locks may be held for more than a few microseconds.
  - When you want to yield CPU to other threads while waiting.

- **Use `SpinLock`** only when:
  - You have **measured** that blocking overhead is a bottleneck.
  - Critical sections are **extremely short** (a few instructions).
  - Contention is **very low** (most attempts succeed immediately).
  - You are writing **high-performance library code** (not application code).

**Trade-offs**

- **Blocking locks**:
  - **Pros**:
    - **CPU-efficient**: Yields CPU to other threads while waiting.
    - **Appropriate for most scenarios**: Works well for locks held for any duration.
    - **Simple**: Easy to use correctly.
  - **Cons**:
    - **Context switch overhead**: Blocking involves a kernel transition and context switch (though modern .NET optimizes this).
  - **Latency**: Slight delay when a lock becomes available (thread must be woken up).

- **`SpinLock`**:
  - **Pros**:
    - **Low latency**: No context switch; acquires lock immediately when available.
    - **No kernel transitions**: Pure user-mode spinning.
  - **Cons**:
    - **CPU waste**: Spinning consumes CPU cycles that could be used by other threads.
    - **Not suitable for long waits**: Spinning for milliseconds wastes CPU.
    - **Complexity**: Must be a struct, cannot be used with `lock` keyword, more error-prone.
  - **Risk**: Can cause performance degradation if used incorrectly (wasting CPU on contended locks).

**Common mistakes**

- **Using `SpinLock` without measuring**:
  - Assuming it will be faster than `lock` without profiling.
  - **Solution**: Almost always use `lock`; `SpinLock` is a specialized optimization.

- **Using `SpinLock` for long critical sections**:
  - Holding a `SpinLock` for more than a few microseconds, causing other threads to waste CPU spinning.
  - **Solution**: Use blocking locks for any non-trivial work.

- **Using `SpinLock` incorrectly**:
  - Not using `Enter`/`Exit` correctly, or forgetting to check the return value of `TryEnter`.
  - **Solution**: `SpinLock` is a struct and must be passed by reference; prefer `lock` for simplicity.

**C# 15-style example: blocking lock vs SpinLock**

```csharp
// Using blocking lock (preferred, appropriate for most cases).
public class Counter
{
    private readonly object _lock = new object();
    private int _value;

    public void Increment()
    {
        lock (_lock)
        {
            _value++; // Short operation, but lock is still appropriate.
        }
    }
}

// Using SpinLock (only for very specialized, measured scenarios).
public struct SpinLockCounter
{
    private SpinLock _spinLock = new SpinLock(enableThreadOwnerTracking: false);
    private int _value;

    public void Increment()
    {
        bool lockTaken = false;
        try
        {
            _spinLock.Enter(ref lockTaken);
            _value++; // Extremely short critical section.
        }
        finally
        {
            if (lockTaken)
            {
                _spinLock.Exit();
            }
        }
    }
}

// Modern .NET note: Most blocking locks (lock, Monitor) use hybrid spinning
// internally - they spin briefly before blocking. You rarely need SpinLock.
```

**Performance note**

- Modern .NET's `lock` / `Monitor` use **hybrid spinning**: they spin briefly before blocking, getting the best of both worlds.
- `SpinLock` is rarely needed in application code; the runtime's optimizations are usually sufficient.
- Only use `SpinLock` if profiling shows that lock acquisition latency is a critical bottleneck and you've exhausted other optimizations.

**Good to know**

- `SpinLock` is a **value type** (struct) and must be passed by reference; it cannot be used with the `lock` keyword.
- Modern .NET's blocking locks already incorporate spinning optimizations; explicit `SpinLock` is a micro-optimization for very specific scenarios.
- Consider lock-free alternatives (e.g., `Interlocked`, `ConcurrentQueue`) before reaching for `SpinLock`.

### 5. **Interlocked vs lock**

**Short definition**

- **`lock`**:
  - Provides **mutual exclusion** for arbitrary code blocks.
  - Can protect complex operations, multiple statements, and non-atomic operations.
  - More general-purpose but has higher overhead.

- **`Interlocked` class**:
  - Provides **atomic operations** on individual variables (e.g., `Increment`, `Decrement`, `Add`, `CompareExchange`).
  - **Lock-free**: No blocking, no locks involved.
  - Very fast, but limited to simple, atomic operations.

**When to use which**

- **Use `Interlocked`** when:
  - You need to perform **simple atomic operations** on a single variable (increment, decrement, add, compare-and-swap).
  - You want **lock-free** performance for high-contention scenarios.
  - The operation can be expressed as a single atomic instruction.

- **Use `lock`** when:
  - You need to protect **multiple operations** or a **critical section**.
  - You need to perform **non-atomic operations** (e.g., check-then-act, read-modify-write of multiple variables).
  - You need **mutual exclusion** for complex logic.

**Trade-offs**

- **`Interlocked`**:
  - **Pros**:
    - **Lock-free**: No blocking, no deadlock risk.
    - **Very fast**: Atomic CPU instructions, minimal overhead.
    - **Scalable**: Performs well under high contention.
  - **Cons**:
    - **Limited scope**: Only works for simple, atomic operations on single variables.
    - **Cannot protect complex logic**: Cannot use for multi-step operations that need to be atomic together.

- **`lock`**:
  - **Pros**:
    - **General-purpose**: Can protect any code block.
    - **Flexible**: Works for complex critical sections.
  - **Cons**:
    - **Blocking**: Threads may block waiting for the lock.
    - **Higher overhead**: More expensive than `Interlocked` for simple operations.
  - **Risk**: Potential for deadlocks if used incorrectly.

**Common mistakes**

- **Using `lock` for simple atomic operations**:
  - Using `lock` to protect a single increment when `Interlocked.Increment` would suffice.
  - **Solution**: Use `Interlocked` for simple atomic operations on single variables.

- **Using `Interlocked` for non-atomic operations**:
  - Trying to use `Interlocked` to protect multi-step operations (e.g., check-then-act).
  - **Solution**: Use `lock` or `Interlocked.CompareExchange` in a loop (lock-free, but more complex).

- **Assuming `Interlocked` makes everything thread-safe**:
  - Using `Interlocked` on one variable while other variables are accessed without synchronization.
  - **Solution**: Thread safety requires careful design; `Interlocked` only makes individual operations atomic.

**C# 15-style example: Interlocked vs lock**

```csharp
// Using Interlocked for simple atomic operations (preferred when applicable).
public class LockFreeCounter
{
    private int _value;

    public void Increment() => Interlocked.Increment(ref _value);
    public void Decrement() => Interlocked.Decrement(ref _value);
    public int Value => Interlocked.CompareExchange(ref _value, 0, 0); // Read with memory barrier.

    public int Add(int amount) => Interlocked.Add(ref _value, amount);
}

// Using lock for complex operations (required for non-atomic logic).
public class ComplexCounter
{
    private readonly object _lock = new object();
    private int _value;
    private int _maxValue;

    public void IncrementWithMax(int max)
    {
        lock (_lock)
        {
            if (_value < max)
            {
                _value++;
                _maxValue = Math.Max(_maxValue, _value);
            }
        }
    }

    public (int value, int max) GetValues()
    {
        lock (_lock)
        {
            return (_value, _maxValue); // Multiple variables, need lock.
        }
    }
}

// Lock-free check-then-act using Interlocked.CompareExchange (advanced).
public class LockFreeStack<T>
{
    private Node<T>? _head;

    public void Push(T item)
    {
        var newNode = new Node<T> { Value = item };
        Node<T>? currentHead;
        do
        {
            currentHead = _head;
            newNode.Next = currentHead;
        }
        while (Interlocked.CompareExchange(ref _head, newNode, currentHead) != currentHead);
    }

    private class Node<T>
    {
        public T Value = default!;
        public Node<T>? Next;
    }
}
```

**Performance note**

- `Interlocked` operations are typically **10-100x faster** than `lock` for simple atomic operations.
- Use `Interlocked` when you can; it's lock-free and scales well under contention.
- For complex operations, `lock` is appropriate; the overhead is usually negligible compared to the work being protected.

**Good to know**

- `Interlocked` operations provide **full memory barriers** (acquire-release semantics), ensuring visibility of changes across threads.
- `Interlocked.CompareExchange` can be used to implement lock-free algorithms (e.g., lock-free stacks, queues), but these are complex and error-prone.
- For most application code, prefer `lock` for simplicity; use `Interlocked` only when profiling shows it's a bottleneck.

### 6. **Volatile vs implicit memory barriers in lock**

**Short definition**

- **`volatile` keyword**:
  - A C# keyword that ensures **visibility** of reads and writes to a field across threads.
  - Prevents compiler and CPU reordering optimizations for that field.
  - Provides **acquire semantics** for reads and **release semantics** for writes.
  - Rarely needed in modern C# with proper synchronization.

- **Implicit memory barriers in `lock`**:
  - The `lock` statement (and `Monitor.Enter`/`Exit`) provides **full memory barriers**.
  - Ensures that all memory operations inside the lock are visible to other threads after the lock is released.
  - More comprehensive than `volatile` for protecting critical sections.

**When to use which**

- **Use `lock`** (preferred):
  - For protecting shared data and critical sections.
  - The memory barriers provided by `lock` are usually sufficient.
  - `lock` provides both mutual exclusion and memory visibility guarantees.

- **Use `volatile`** only when:
  - You have a **simple flag or status field** that is written by one thread and read by others.
  - You **cannot use `lock`** for performance reasons (extremely rare).
  - You understand the .NET memory model deeply and have measured that `volatile` is necessary.

**Important note**: In modern C# 15/.NET 9+, `volatile` is **rarely needed**. Proper use of `lock`, `Interlocked`, or higher-level synchronization primitives usually provides the necessary memory visibility guarantees.

**Trade-offs**

- **`volatile`**:
  - **Pros**:
    - **Lightweight**: No locking overhead, just prevents reordering.
    - **Simple syntax**: Just add the `volatile` keyword.
  - **Cons**:
    - **Limited scope**: Only affects the specific field, not surrounding code.
    - **Easy to misuse**: Does not provide mutual exclusion; race conditions can still occur.
    - **Rarely sufficient**: Most scenarios need `lock` or `Interlocked` anyway.

- **Implicit memory barriers in `lock`**:
  - **Pros**:
    - **Comprehensive**: Protects entire critical sections, not just individual fields.
    - **Mutual exclusion**: Provides both visibility and mutual exclusion.
    - **Less error-prone**: Harder to misuse than `volatile`.
  - **Cons**:
    - **Blocking**: Involves locking overhead (though minimal in modern .NET).

**Common mistakes**

- **Using `volatile` instead of `lock`**:
  - Marking a field as `volatile` and assuming it makes operations on that field thread-safe.
  - **Solution**: `volatile` only ensures visibility, not atomicity or mutual exclusion. Use `lock` or `Interlocked` for thread-safe operations.

- **Overusing `volatile`**:
  - Adding `volatile` to fields "just to be safe" without understanding the memory model.
  - **Solution**: Use `lock` by default; `volatile` is a specialized tool for specific scenarios.

- **Assuming `volatile` is needed with `lock`**:
  - Marking fields as `volatile` when they are already protected by `lock`.
  - **Solution**: `lock` provides memory barriers; `volatile` is redundant inside locked sections.

**C# 15-style example: volatile vs lock**

```csharp
// Using volatile for a simple flag (rare, but sometimes appropriate).
public class CancellationFlag
{
    private volatile bool _cancelled;

    public void Cancel() => _cancelled = true;
    public bool IsCancelled => _cancelled;
}

// Using lock (preferred, provides both mutual exclusion and memory barriers).
public class ThreadSafeCounter
{
    private readonly object _lock = new object();
    private int _value; // No need for volatile - lock provides memory barriers.

    public void Increment()
    {
        lock (_lock)
        {
            _value++; // Memory barrier ensures visibility.
        }
    }

    public int Value
    {
        get
        {
            lock (_lock)
            {
                return _value; // Memory barrier ensures we see the latest value.
            }
        }
    }
}

// Modern alternative: using Interlocked (lock-free, provides memory barriers).
public class LockFreeCounter
{
    private int _value; // No need for volatile - Interlocked provides memory barriers.

    public void Increment() => Interlocked.Increment(ref _value);
    public int Value => Interlocked.CompareExchange(ref _value, 0, 0);
}
```

**Performance note**

- `volatile` has minimal overhead (prevents some compiler optimizations, but no runtime cost).
- `lock` has slightly more overhead but provides comprehensive protection.
- In practice, the performance difference is negligible; prefer `lock` for correctness and simplicity.

**Good to know**

- Modern .NET's memory model is strong; `lock`, `Interlocked`, and other synchronization primitives provide the necessary memory barriers.
- `volatile` is a **specialized tool** for specific scenarios (e.g., cancellation flags, status fields) and is rarely needed in well-designed concurrent code.
- If you find yourself using `volatile` frequently, reconsider your design; proper use of `lock`, `Interlocked`, or higher-level patterns (e.g., actor model, message passing) is usually better.
- See section 4.2 for deeper coverage of the .NET memory model and visibility guarantees.
