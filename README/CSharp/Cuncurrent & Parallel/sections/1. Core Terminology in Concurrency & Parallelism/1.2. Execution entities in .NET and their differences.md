## 1.2. Execution entities in .NET and their differences

This section explains the **core execution entities in .NET**. Other sections may briefly mention these concepts and will refer back here for the full explanation (for example: *“See 1.2 for the differences between Task and ValueTask”*).

2. **Thread vs Thread Pool Thread**
3. **Thread vs Task**
4. **Task vs ValueTask**
5. **Task vs IAsyncEnumerable**
6. **Foreground Thread vs Background Thread**

1. **Process vs Thread**

**Short definitions**

- **Process**:
  - An operating-system object that represents a **running application instance**.
  - Has its own **virtual address space**, handles, security context, and resources.
  - In .NET, each `dotnet` application typically runs in its own process (for .NET Core+/5+/6+/7+/8+/9+).

- **Thread**:
  - A **path of execution** inside a process.
  - Shares the process’s memory and resources with other threads in the same process.
  - Has its own **stack**, CPU registers, and scheduling state.

In other words, **a process is the container, threads are the workers inside the container**.

**When you care about the distinction**

- **Process-level concerns**:
  - Isolation and security boundaries between apps or services.
  - Memory limits and GC scope (each .NET process has its own managed heap and GC).
  - Crash isolation: one process crashing doesn’t take down others (unless externally coupled).
  - Deployment and hosting (e.g. separate microservices).

- **Thread-level concerns**:
  - Parallelism and concurrency inside the process.
  - Synchronization and sharing of in-memory data structures.
  - Deadlocks, race conditions, and scheduling.

**Mentor perspective**

- Use **separate processes** when you need **hard isolation** (e.g. untrusted plugins, different lifetimes, OS-level sandboxing, or resource governance using containers).
- Use **threads and tasks** when you need **concurrency or parallelism inside one application**, sharing state safely.

**Example: processes vs threads in modern .NET**

```csharp
// One process, many threads and tasks inside it.
// This code runs inside a single .NET process.

static async Task Main()
{
    // Logical concurrency: many operations as Tasks.
    var tasks = Enumerable.Range(0, 8)
        .Select(i => Task.Run(() => DoCpuBoundWork(i)))
        .ToArray();

    await Task.WhenAll(tasks).ConfigureAwait(false);
}

static void DoCpuBoundWork(int id)
{
    // Potentially running on different threads of the same process.
    Console.WriteLine($"Work item {id} running on thread {Environment.CurrentManagedThreadId}");
}
```

**Good to know**

- In .NET, **GC, Thread Pool, and most runtime services are per-process**.
- Starting many processes is usually more expensive than starting many threads, but processes provide stronger isolation and can run on different machines.

2. **Thread vs Thread Pool Thread**

**Short definitions**

- **Thread (dedicated / manually created)**:
  - Created explicitly via `new Thread(...)` or similar low-level APIs.
  - You control its lifetime, priority, and sometimes affinity.
  - You are responsible for managing when it starts and stops.

- **Thread Pool Thread**:
  - Managed by the **.NET Thread Pool** (`System.Threading.ThreadPool`).
  - Reused across many work items (e.g. `Task.Run`, async continuations, timers).
  - The runtime decides how many exist based on workload and heuristics.

In modern .NET, **most code should run on Thread Pool threads**, not on manually created threads.

**When to use each**

- **Prefer Thread Pool threads** (default) for:
  - Request handling in ASP.NET Core.
  - Background work (`Task.Run`, `BackgroundService`, timers).
  - Async continuations (by default they resume on a Thread Pool thread in server contexts).

- **Consider a dedicated thread** only when:
  - You need **special scheduling** (e.g. custom event loop, low-latency trading, device polling).
  - You need to **control priority or affinity** for specific hardware or real-time-ish scenarios.
  - You know exactly why the Thread Pool is insufficient and have measured it.

**Modern guidance (C# 15/.NET 9+)**

- Direct `Thread` creation is now a **specialized/advanced** tool.
- Use higher-level APIs:
  - `Task`, `Task.Run`, `Parallel.For`, `IHostedService`, `BackgroundService`.
  - `ThreadPool.UnsafeQueueUserWorkItem` only in very low-level libraries where you must avoid allocations and you fully understand the implications.

**Example: dedicated thread vs Thread Pool thread**

```csharp
// Dedicated thread (low-level, rarely needed).
var thread = new Thread(() =>
{
    while (true)
    {
        // Polling loop, e.g., reading from a device.
        PollDevice();
    }
})
{
    IsBackground = true
};
thread.Start();

// Thread Pool usage via Task.Run (preferred in most apps).
Task.Run(() => DoBackgroundWorkAsync());
```

**Common mistakes**

- Creating lots of dedicated threads for short-lived tasks instead of using the Thread Pool.
- Using `Thread.Sleep` on Thread Pool threads to implement backoff or delays instead of `Task.Delay`.
- Forgetting to stop dedicated threads gracefully, leading to resource leaks or preventing process shutdown (see foreground vs background threads below).

**Performance note**

- The Thread Pool:
  - Reduces **thread creation cost** by reusing threads.
  - Adjusts the number of threads based on workload.
  - Works best when tasks:
    - Are not too long-running (or explicitly marked as long-running with `TaskCreationOptions.LongRunning` — though even this should be used carefully).
    - Avoid blocking on I/O; use async instead.

3. **Thread vs Task**

**Short definitions**

- **Thread**:
  - An OS-level execution unit.
  - Has a stack, registers, and a position in the scheduler.
  - Can execute exactly one piece of code at a time.

- **Task (`System.Threading.Tasks.Task`)**:
  - A **.NET abstraction that represents a unit of work** that might be:
    - Running, completed, faulted, or canceled.
  - Maps to **one or more threads over time**, or sometimes **no thread at all** when in a waiting state (e.g. awaiting I/O).
  - Designed to compose: you can `await` it, `Task.WhenAll` it, pass it around.

You can think of a `Task` as a **promise of a future result**, while a thread is **one specific worker**.

**When to think in tasks instead of threads**

- Almost always in application-level C# code:
  - For **I/O-bound** work: `Task` + `async`/`await` is the primary pattern.
  - For **coordinating multiple operations**: `Task.WhenAll`, `Task.WhenAny`, `async` loops.
  - For **chaining operations**: `await` for readability instead of callbacks.

- Reserve **explicit thread thinking** for:
  - Debugging (understanding who is running what).
  - Integration with low-level OS or native components.
  - Specialized schedulers or advanced performance scenarios.

**Example: Task-based API vs thread-based API**

```csharp
// Task-based, async-friendly API (modern).
static async Task ProcessFileAsync(string path, CancellationToken ct = default)
{
    var content = await File.ReadAllTextAsync(path, ct).ConfigureAwait(false);
    var processed = Transform(content);
    await File.WriteAllTextAsync(path, processed, ct).ConfigureAwait(false);
}

// Caller does not care about which thread runs this, only about completion.
await ProcessFileAsync("data.txt", cancellationToken);
```

Compare this with a legacy, thread-based style:

```csharp
// Obsolete pattern: explicitly creating a thread to do work.
var thread = new Thread(() => ProcessFile("data.txt"));
thread.Start();
thread.Join(); // blocking
```

**Common mistakes**

- **Equating 1 Task = 1 Thread**:
  - A `Task` may run partially on different Thread Pool threads over time.
  - A waiting `Task` (e.g. HTTP request in flight) doesn’t hold any thread at all.
- **Using Task.Run excessively**:
  - Wrapping every method in `Task.Run` “to make it async” instead of using real async I/O.
- **Assuming Task exceptions behave like thread exceptions**:
  - Task exceptions are captured and must be **observed** (e.g. via `await`).
  - Unobserved tasks can lead to lost errors if you ignore returned `Task`s.
  - See section 1.7 and 4.x for deeper coverage of exception handling.

**Good to know**

- `Task` is **the compositional unit**; threads are the **execution resource**.
- Design APIs around `Task`, not `Thread`, unless you are working on a very low-level framework.

4. **Task vs ValueTask**

**Short definitions**

- **Task**:
  - Reference type (`class`).
  - Represents an operation that will complete in the future.
  - Allocated on the managed heap unless it is a cached/special Task.

- **ValueTask** (`System.Threading.Tasks.ValueTask` / `ValueTask<T>`):
  - Value type (`struct`).
  - Can represent **either**:
    - A result that is **already computed** (synchronous completion), or
    - A reference to a regular `Task`.
  - Designed to **avoid allocations** in high-throughput code where many operations complete synchronously.

**When to use which**

- **Use `Task` by default**:
  - Simpler mental model.
  - Well-understood by tooling and libraries.
  - Great for most application and library code.

- **Use `ValueTask` when** all of the following are true:
  - You are writing **low-level, high-throughput** library or framework code.
  - A **significant fraction** of calls complete synchronously (e.g. 90%+).
  - Allocation of a `Task` per call is a measurable bottleneck.
  - You are ready to handle the extra complexity and constraints of `ValueTask`.

**Important constraints of ValueTask**

- A `ValueTask` **must be awaited at most once** (unless you convert it to a `Task`).
- You should not:
  - Store it long-term.
  - Use `Task.WhenAll` / `Task.WhenAny` directly on `ValueTask`s without converting them.
  - Use multiple continuations on it.

**Example: Task vs ValueTask in a caching scenario**

```csharp
// Basic Task-based API (recommended default).
public interface ICache
{
    Task<string?> GetAsync(string key, CancellationToken ct = default);
}

// Advanced: using ValueTask to avoid allocations when cache hits are synchronous.
public interface IHighPerformanceCache
{
    ValueTask<string?> GetAsync(string key, CancellationToken ct = default);
}

public sealed class HighPerformanceCache : IHighPerformanceCache
{
    private readonly ConcurrentDictionary<string, string> _cache = new();

    public ValueTask<string?> GetAsync(string key, CancellationToken ct = default)
    {
        if (_cache.TryGetValue(key, out var value))
        {
            // Completed synchronously, no allocation of Task.
            return new ValueTask<string?>(value);
        }

        // Fall back to async load (may allocate a Task).
        return new ValueTask<string?>(LoadFromBackendAsync(key, ct));
    }

    private async Task<string?> LoadFromBackendAsync(string key, CancellationToken ct)
    {
        await Task.Delay(10, ct).ConfigureAwait(false); // simulate I/O
        var value = $"value-for-{key}";
        _cache[key] = value;
        return value;
    }
}
```

**Common mistakes**

- Switching from `Task` to `ValueTask` **everywhere** “for performance” without measurement. This usually adds complexity without real gains.
- Misusing `ValueTask` in APIs that expose tasks to external consumers who might:
  - Await it multiple times.
  - Store it for later.
  - Combine it with others via `Task.WhenAll`.

**Performance note**

- `ValueTask` can reduce **allocations** in very hot paths.
- But for most code, **`Task` is fast enough**, and your bottlenecks are elsewhere (I/O, algorithm complexity, locking).

5. **Task vs IAsyncEnumerable**

**Short definitions**

- **Task / Task<T>**:
  - Represents a single **eventual result** or completion.
  - A “one-shot” asynchronous operation.

- **IAsyncEnumerable<T>**:
  - Represents an **asynchronous sequence** of values over time.
  - Consumed with `await foreach`.
  - Each iteration may involve async work (I/O, timers, etc.).

You can think of `Task<T>` as **async scalar**, and `IAsyncEnumerable<T>` as **async stream**.

**When to use which**

- Use **`Task` / `Task<T>`** when:
  - You return **a single value** or just completion.
  - Example: get one user, save a record, upload a single file.

- Use **`IAsyncEnumerable<T>`** when:
  - You have **multiple values** that are naturally produced over time.
  - You want to start processing early results before the entire set is available.
  - Example: streaming large query results, reading lines from a log, live event feeds.

**Example: Task vs IAsyncEnumerable**

```csharp
// Single result: Task<T>.
static async Task<User?> GetUserAsync(Guid id, CancellationToken ct = default)
{
    // Asynchronous DB or HTTP call.
    return await _userRepository.GetByIdAsync(id, ct).ConfigureAwait(false);
}

// Multiple results over time: IAsyncEnumerable<T>.
static async IAsyncEnumerable<User> GetAllUsersAsync(
    [EnumeratorCancellation] CancellationToken ct = default)
{
    await foreach (var page in _userRepository.GetUserPagesAsync(ct))
    {
        foreach (var user in page)
        {
            yield return user;
        }
    }
}

// Consuming the async stream:
await foreach (var user in GetAllUsersAsync(ct))
{
    Console.WriteLine(user.Name);
}
```

**Common mistakes**

- Using `Task<List<T>>` everywhere when the consumer could stream results as `IAsyncEnumerable<T>`:
  - This **buffers everything in memory** before processing starts.
  - For large result sets, this increases memory usage and latency.
- Overusing `IAsyncEnumerable<T>` for cases that are naturally “single result”:
  - This complicates the API and the caller for no benefit.

**Good to know**

- `IAsyncEnumerable<T>` integrates well with async I/O, but you must remember:
  - To use `await foreach`.
  - To use `[EnumeratorCancellation]` if you want to flow a `CancellationToken`.
  - That enumeration may continue on different threads (similar to `Task` continuations).
- For deeper coverage of streaming and reactive flows, see section 3.4.

6. **Foreground Thread vs Background Thread**

**Short definitions**

- **Foreground thread**:
  - Keeps the **process alive** as long as any foreground thread is running.
  - By default, most manually created threads are foreground unless otherwise specified.

- **Background thread**:
  - Does **not prevent the process from exiting**.
  - When all foreground threads finish, the process may terminate even if background threads are still running.
  - Background threads are used heavily by the Thread Pool and many runtime services.

In modern .NET, **you rarely need to care about this distinction directly**, unless you create threads manually or host long-running work.

**When it matters**

- **Manual Thread creation**:
  - `thread.IsBackground = true` determines whether the thread keeps the process alive.
  - Background threads may be terminated abruptly at process exit without running `finally` blocks.

- **Long-running services / daemons**:
  - You want a **controlled shutdown**: avoid relying on background threads implicitly.
  - Use hosting patterns (`IHost`, `BackgroundService`) that handle lifetime for you.

**Example: foreground vs background**

```csharp
// Dedicated background thread that will not keep the process alive on its own.
var worker = new Thread(() =>
{
    try
    {
        while (true)
        {
            DoWork();
            Thread.Sleep(TimeSpan.FromSeconds(1));
        }
    }
    finally
    {
        // WARNING: This may not run if the process exits abruptly.
        Console.WriteLine("Worker shutting down.");
    }
})
{
    IsBackground = true
};

worker.Start();

Console.WriteLine("Main method completed.");
// Process may exit here even if worker is still in DoWork().
```

**Modern best practices**

- Avoid directly creating background threads for long-running jobs in **application code**.
- Prefer:
  - `IHostedService` / `BackgroundService` in ASP.NET Core and generic hosts.
  - `PeriodicTimer`, `Task.Delay`, and cooperative cancellation for background loops.
- These patterns integrate with the host’s **lifetime management**, allowing graceful shutdown and predictable cleanup.

**Common mistakes**

- Relying on background threads to flush logs or persist state at exit, only to see work lost when the process terminates.
- Creating foreground threads for one-off tasks, unintentionally preventing the process from shutting down.

**Good to know**

- Thread Pool threads are **background threads**.
- Clean shutdown in concurrent apps is less about foreground vs background and more about:
  - Using **cancellation tokens**.
  - Completing work gracefully.
  - Integrating with the hosting model’s lifetime hooks (see section 3.5 and 5.x recipes).
