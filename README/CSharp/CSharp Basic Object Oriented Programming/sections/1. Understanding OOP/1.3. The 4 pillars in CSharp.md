## 1.3. The 4 pillars: encapsulation, abstraction, inheritance, polymorphism (C#-specific)

1. **Encapsulation** (private fields + public methods/properties; invariants live here)
2. **Abstraction** (interfaces and small public surfaces; “tell, don’t ask” trade-offs)
3. **Inheritance & polymorphism** (when to use; how virtual dispatch affects extensibility and performance)

---

### 1) **Encapsulation**
**Definition**
- **Encapsulation** is the practice of **hiding representation** (how state is stored) and exposing a **minimal public surface** that keeps an object in a valid state.
- In C#, encapsulation is expressed with:
  - `private`/`protected`/`internal` visibility,
  - properties with controlled setters (`private set`, `init`),
  - methods that represent *operations* (not “set fields”),
  - types that prevent invalid states (e.g., `readonly record struct` for value objects).

**When to use**
- Always, for any type that has invariants or rules.
- Especially in libraries: public API shapes become long-term commitments.

**Trade-offs**
- “Perfect” encapsulation can reduce convenience:
  - More methods to model intent.
  - Slightly more code up front.
- But it repays with:
  - fewer invalid states,
  - fewer scattered validations,
  - easier refactoring.

**Common mistakes**
- **Public setters everywhere** → invariants are unenforceable.
- **Exposing internal collections** (`List<T>`) → callers mutate behind your back.
- **Doing heavy work in getters** → surprises callers; can create hidden allocations/latency.

**Example: don’t leak mutability**

```csharp
using System.Collections.Generic;
using System.Collections.ObjectModel;

public sealed class ShoppingCart
{
    private readonly List<CartLine> _lines = [];

    public ReadOnlyCollection<CartLine> Lines => _lines.AsReadOnly();

    public void AddItem(string sku, int quantity)
    {
        if (string.IsNullOrWhiteSpace(sku)) throw new ArgumentException("SKU is required.", nameof(sku));
        if (quantity <= 0) throw new ArgumentOutOfRangeException(nameof(quantity));

        _lines.Add(new CartLine(sku, quantity));
    }
}

public sealed record CartLine(string Sku, int Quantity);
```

**Performance note**
- Encapsulation is not a performance problem; hidden allocations are. The biggest “encapsulation perf bug” is returning new lists/arrays from properties repeatedly. Prefer:
  - cached read-only views,
  - iterators carefully (but avoid allocations in hot paths),
  - explicit methods (`CopyTo`, `EnumerateLines()`) when you need control.

### 2) **Abstraction**
**Definition**
- **Abstraction** is what you expose publicly: a **simplified contract** that hides details.
- In C# the most common abstractions are:
  - **interfaces** (contracts),
  - abstract base classes (partial shared implementation),
  - higher-level methods that express intent.

**When to use**
- Use abstraction when:
  - you need a stable boundary (I/O, storage, time, random, external services),
  - you want testability (mock/fake/stub at the boundary),
  - you expect multiple implementations.

**Trade-offs**
- Abstractions add indirection. Too many abstractions create “architecture tax”.
- The goal is **the simplest abstraction that survives change**.

**Common mistakes**
- **Interface-per-class** without a real need (creates noise and makes refactoring harder).
- **Leaky abstractions**: exposing implementation details (e.g., returning EF Core types or HTTP details from domain interfaces).
- **Tell, don’t ask** misapplied: forcing everything into “commands” even when a query is fine.

**Mentor guidance**
- Prefer **narrow, cohesive interfaces**:
  - good: `IClock { DateTimeOffset UtcNow { get; } }`
  - suspicious: `IUtilities` / `IManager`

**See also**
- Dependency injection and interface boundaries are covered in depth in **4.2** (`Interfaces and dependency injection`).

### 3) **Inheritance & polymorphism**
**Definition**
- **Inheritance** models an “is-a” relationship: `Dog : Animal`.
- **Polymorphism** means callers can depend on a base contract and the runtime dispatches to the correct override/implementation.
  - virtual methods (class inheritance),
  - interface dispatch (interface implementations).

**When inheritance is appropriate**
- Stable base contract + real is-a relationship.
- Framework extension points (e.g., `Stream`, `DbContext` in EF Core, custom `JsonConverter<T>`).
- When shared implementation is truly shared and unlikely to diverge.

**When to avoid inheritance**
- When you’re using it to “share code” but not modeling a real hierarchy.
- When base classes start accumulating hooks and optional overrides → fragile base class problem.
- When you need mix-and-match behavior (composition is better).

**Common mistakes**
- Deep hierarchies with many virtual methods, complex initialization order, and “template method” puzzles.
- Calling virtual methods from constructors (derived type not initialized yet).

**Performance note (important but often misunderstood)**
- Virtual/interface calls add indirection and can prevent some optimizations (inlining/devirtualization), especially across assembly boundaries.
- In most business apps, this cost is negligible; in hot loops it can matter.
  - For the deep performance framing and guidance, see **3.5** (`Virtual dispatch, interface calls, and performance basics`).

**Example: composition instead of inheritance**

```csharp
public interface ITaxPolicy
{
    decimal CalculateTax(decimal netAmount);
}

public sealed class Order(ITaxPolicy taxPolicy)
{
    public decimal NetAmount { get; private set; }
    public decimal Tax => taxPolicy.CalculateTax(NetAmount);

    public void AddLine(decimal lineNet)
    {
        if (lineNet <= 0) throw new ArgumentOutOfRangeException(nameof(lineNet));
        NetAmount += lineNet;
    }
}
```
