## 2.1. Defining a class: fields vs properties vs methods (and why it matters)

1. **Fields vs properties** (encapsulation, versioning, validation, binary compatibility)
2. **Auto-properties** (including `init`), backing fields, and computed properties
3. **Performance notes** (avoid “property does heavy work”; avoid accidental allocations in getters)

---

### 1) **Fields vs properties**
**Definition**
- A **field** is a raw storage slot. It has no interception point. Exposing it publicly couples callers to your internal representation.
- A **property** is an API surface that *can* be backed by a field today and compute/validate tomorrow. In C#, a property is the idiomatic way to expose state.

**When to use which**
- Use **private fields** to store state.
- Use **public properties** to expose state (especially in libraries and shared codebases).
- Use **methods** when an operation:
  - **changes state** (e.g., `AddItem`, `MarkPaid`),
  - has **meaningful side effects** (I/O, events, persistence),
  - or represents an **action** rather than a value (`CalculateTotal`, `ApplyDiscount`).

**Versioning and binary compatibility (mentor emphasis)**
- Changing a **public field** to a property is a breaking API change for consumers.
- Starting with a property preserves future options: add validation, lazy computation, logging, or change internal storage without breaking callers.

**Validation & invariants**
- Prefer enforcing invariants in:
  - constructors / factories (initial validity),
  - domain methods (state transitions),
  - and properties only when the property is a true “settable” part of the model.
- Be careful with “settable properties everywhere”: it makes it easy for callers to create invalid states. Prefer intention-revealing methods.

**Common mistakes**
- **Public fields** on mutable objects (hard to evolve; invariants leak).
- **“Property setters as commands”** (doing real work in `set` like network calls, DB writes, publishing messages).
  - Properties should be fast and unsurprising. Use a method for work.
- **Throwing from getters** because they do expensive work or depend on external state.

**Example: evolving representation safely**

```csharp
using System;

public sealed class Temperature
{
    // Private field: representation can change later.
    private double _celsius;

    // Public property: stable API surface.
    public double Celsius
    {
        get => _celsius;
        private set
        {
            if (value < -273.15) throw new ArgumentOutOfRangeException(nameof(value), "Below absolute zero.");
            _celsius = value;
        }
    }

    public Temperature(double celsius) => Celsius = celsius;

    // Intention-revealing behavior.
    public void AddDelta(double deltaCelsius) => Celsius += deltaCelsius;

    // Computed value: no separate storage needed.
    public double Fahrenheit => (Celsius * 9 / 5) + 32;
}
```

**Performance note**
- The JIT will inline simple property accessors aggressively in Release builds. The performance cost is rarely the *property*—it’s what you put inside it.
- If a getter allocates (e.g., `return _list.ToArray();`) or is expensive, consider:
  - returning a **read-only view** (`IReadOnlyList<T>`, `ReadOnlyCollection<T>`),
  - using **`ReadOnlySpan<T>`** where appropriate (advanced),
  - or exposing a method that makes the allocation explicit (e.g., `ToArray()`-style).

### 2) **Auto-properties (`init`), backing fields, computed properties**
**Auto-properties**
- Use auto-properties for simple state exposure, especially in **DTOs** or immutable-ish models:

```csharp
public sealed class Customer
{
    public required string Id { get; init; }
    public required string DisplayName { get; init; }
}
```

**When `init` is a win**
- `init` supports “set during construction, then immutable from the outside.”
- Combine with `required` to prevent “half-initialized objects”.

**Backing fields**
- Use a backing field when you need validation, normalization, or derived/cached values.
- Keep it simple: if you need complex logic, consider a method or a separate type.

**Computed properties**
- Great for derived values **when cheap** and deterministic.
- If computation is expensive, make it explicit:
  - either cache it carefully (with invalidation rules),
  - or provide a method like `ComputeX()` so callers understand it does work.

**Common mistakes**
- Overusing computed properties that do heavy work, causing hidden \(O(n)\) behavior in innocently-looking code like `if (obj.Total > 0)`.
- Returning new objects from getters repeatedly (`new StringBuilder(...)`, `new List<T>(...)`) which causes allocations and GC churn.

---

### 3) **Performance notes (what mentors watch for)**
**Avoid “work in getters”**
- Property access in C# communicates “cheap value lookup”. Violating that expectation is a readability and perf trap.

**Avoid accidental allocations**
- Typical allocation traps in getters:
  - `ToString()` building strings repeatedly,
  - `LINQ` (`_items.Select(...).ToList()`),
  - returning copies (`_list.ToArray()`),
  - string concatenation.

**Prefer stable views**
- Expose:
  - `IReadOnlyList<T>` or `IReadOnlyCollection<T>` for collections,
  - or `ReadOnlyCollection<T>` if you truly need a wrapper.

**Good to know**
- If you *must* return an allocation (e.g., snapshot array for thread safety), make it explicit and document it. In APIs, explicitness is a performance feature.
