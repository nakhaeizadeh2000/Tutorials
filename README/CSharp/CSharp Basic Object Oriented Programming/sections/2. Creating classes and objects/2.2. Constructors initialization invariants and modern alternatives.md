## 2.2. Constructors: initialization, invariants, and modern alternatives

1. **Constructor responsibilities** (establish valid state; no hidden expensive work)
2. **Primary constructors and `required` members (C# 15 era)** (intent-revealing initialization)
3. **Factories vs constructors** (async creation, caching, validation failures, and testability)

---

### 1) **Constructor responsibilities**
**Definition**
- A constructor’s job is to put the object into a **valid, usable state**.
- In OOP terms, a constructor is part of the type’s **invariant boundary**: it should prevent “impossible states” from ever being created.

**What belongs in a constructor**
- **Argument validation** that protects invariants.
- **Simple initialization** that cannot fail in surprising ways.
- Establishing **non-null required fields** and **derived state** that is cheap to compute.

**What usually does *not* belong in a constructor**
- **Slow I/O** (DB/HTTP/file), because:
  - it makes construction “blocking by default” and harder to test,
  - it can lead to deadlocks in (frontend) UI code when people try to block on async.
- **Work that can throw for environmental reasons** (network failures, config missing) unless the type’s whole meaning depends on it *and* you’ve designed for it explicitly.
- **Starting background work** (timers/Tasks) without explicit lifetime management. Prefer explicit `Start()`/`Stop()` or a hosting model.

**Common mistakes (mentor notes)**
- **Doing too much work**: constructors that build object graphs, parse huge data, and allocate large buffers. That hides performance costs and makes profiling harder.
- **Letting invalid objects exist**: public parameterless constructors that allow half-initialized instances “because frameworks”.
  - In modern .NET, most serializers/DI containers work fine with parameterized constructors; when you must support a serializer, consider dedicated DTOs.

**Example: enforce invariants at construction**

```csharp
using System;

public sealed class EmailAddress
{
    public string Value { get; }

    public EmailAddress(string value)
    {
        if (string.IsNullOrWhiteSpace(value))
            throw new ArgumentException("Email is required.", nameof(value));

        // Keep validation simple here; full RFC parsing is often overkill.
        if (!value.Contains('@', StringComparison.Ordinal))
            throw new ArgumentException("Invalid email format.", nameof(value));

        Value = value;
    }

    public override string ToString() => Value;
}
```

**Performance note**
- Constructor validation is almost always “cheap enough”. The expensive mistake is building **large object graphs** and doing **hidden allocations** in constructors that run on hot paths.

### 2) **Primary constructors and `required` members (C# 15 era)**
**Goal**
- Make initialization **intent-revealing** and harder to misuse.
- Reduce “constructor overload soup” and “set everything later” bugs.

**`required` members**
- Use `required` when callers must provide a value during object creation.
- Works especially well for **data carriers** and models that need a complete set of values.

```csharp
public sealed class CreateUserRequest
{
    public required string UserName { get; init; }
    public required string Email { get; init; }
}

var req = new CreateUserRequest { UserName = "ada", Email = "ada@example.com" };
```

**When *not* to use `required`**
- When a value is truly optional, or has a safe default.
- When you want to enforce invariants via a constructor/factory rather than “object initializer + post-validation”.

**Primary constructors**
- Primary constructors can reduce noise when the type’s identity is “these values”.
- Use them when it improves clarity; avoid them if they hide complex initialization logic.

```csharp
using System;

public sealed class User(string userName, EmailAddress email)
{
    public string UserName { get; } = userName ?? throw new ArgumentNullException(nameof(userName));
    public EmailAddress Email { get; } = email ?? throw new ArgumentNullException(nameof(email));
}
```

**Trade-offs**
- Primary constructors are great for **small, stable** types. For complex initialization, explicit constructors may be clearer.
- `required` is compile-time enforcement, but it does not replace runtime validation when values can come from untrusted sources (JSON, UI input).

**Legacy patterns to avoid**
- A “parameterless ctor + public setters everywhere” as the default.
  - It creates invalid transient states and makes invariants hard to enforce.

### 3) **Factories vs constructors**
**When a factory is better**
- **Async creation**: constructors can’t be `async`.
- **Validation that can fail without throwing**: return `bool`/`Result` instead of exceptions when failures are expected.
- **Caching / interning**: return existing instances (e.g., flyweight for small immutable values).
- **Multiple creation modes** with names that document intent (`CreateFromIsoString`, `CreateForTest`, `CreateWithDefaults`).

**Factory styles**
- **Static factory** on the type:

```csharp
using System;

public sealed class Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    private Money(decimal amount, string currency)
    {
        Amount = amount;
        Currency = currency;
    }

    public static bool TryCreate(decimal amount, string currency, out Money? money)
    {
        money = null;
        if (amount < 0) return false;
        if (currency is not ("USD" or "EUR" or "IRR")) return false;
        money = new Money(amount, currency);
        return true;
    }
}
```

**Trade-offs**
- Factories add an extra call site, but they:
  - make intent explicit,
  - can avoid exceptions for common failure paths,
  - can hide complex creation logic cleanly.

**Good to know**
- If construction allocates or is expensive, prefer a factory so you can later introduce pooling/caching without changing every call site (your public API is the seam).
