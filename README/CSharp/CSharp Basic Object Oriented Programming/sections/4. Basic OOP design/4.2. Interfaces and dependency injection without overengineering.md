## 4.2. Interfaces and dependency injection (without overengineering)

1. **Interfaces as contracts** (small, cohesive, stable)
2. **Constructor injection** (composition root; avoid service locator)
3. **Allocation/lifetime awareness** (transient vs scoped vs singleton; capture pitfalls)

---

### 1) **Interfaces as contracts**

**Definition**

- An **interface** is a **behavioral contract**: it describes *what you need* from a dependency, not *how it’s implemented*.
- In modern C#, interfaces are primarily a tool for:
  - **decoupling** (stable boundaries)
  - **substitutability** (testing, alternate implementations)
  - **API clarity** (a narrow surface that’s hard to misuse)

**When to use**

- Use interfaces at **boundaries**:
  - external I/O (clock, file system, HTTP, DB, message bus)
  - policies/strategies (pricing rules, retry policy, formatting rules)
  - orchestration points where you expect multiple implementations
- Avoid interfaces for “everything” inside a cohesive module. A class depending on another internal class is fine if the boundary is not real.

**Trade-offs**

- **Pros**:
  - clearer seams for tests
  - reduced coupling to concrete types
  - enables composition (plug different strategies)
- **Cons**:
  - too many interfaces becomes “abstraction noise”
  - premature generality: you pay complexity before you have a real need

**Common mistakes (mentor notes)**

- **Interface per class** by default. This often creates:
  - duplicated types (`IFoo` + `Foo`)
  - large DI registrations
  - no actual flexibility (only one implementation ever exists)
- **Fat interfaces**. Keep interfaces small and cohesive; prefer multiple small interfaces over one “kitchen sink”.
- **Leaking infrastructure** through the interface (e.g., returning EF Core entities from a repository interface) — you lose the abstraction.

**Good to know**

- It’s OK to start with a concrete class. Introduce an interface when:
  - you have a second implementation,
  - you need a test seam,
  - you want to decouple a stable boundary.

### 2) **Constructor injection (composition root; avoid service locator)**

**Definition**

- **Constructor injection** means dependencies are provided via the constructor, making them:
  - explicit (easy to see)
  - immutable (usually `readonly`)
  - test-friendly
- The **composition root** is the place where you wire up the object graph (often `Program.cs` for apps).

**Why mentors push this**

- It makes dependency graphs **visible**.
- It prevents hidden runtime surprises (“why is this dependency null / not configured?”).
- It makes unit tests straightforward: create the type with a fake.

**Avoid: service locator**

- “Service locator” is when code calls the container at runtime (e.g., `provider.GetService<T>()` inside business logic).
- It hides dependencies, complicates reasoning, and makes failures appear late.

**Minimal example (runnable)**

```csharp
using System;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;

public interface IClock
{
    DateTimeOffset UtcNow { get; }
}

public sealed class SystemClock : IClock
{
    public DateTimeOffset UtcNow => DateTimeOffset.UtcNow;
}

public sealed class GreetingService(IClock clock) // primary constructor style
{
    public string GetGreeting(string name)
        => $"Hello, {name}. Time: {clock.UtcNow:O}";
}

using IHost host = Host.CreateDefaultBuilder()
    .ConfigureServices(services =>
    {
        services.AddSingleton<IClock, SystemClock>();
        services.AddTransient<GreetingService>();
    })
    .Build();

var svc = host.Services.GetRequiredService<GreetingService>();
Console.WriteLine(svc.GetGreeting("Ada"));
```

**Common mistakes**

- **Doing work in constructors** that can fail due to external dependencies (network, DB).
  - Prefer factories or async initialization patterns when you truly need them.
- **Making everything `singleton`** “for performance”. Singletons can hide shared mutable state bugs.
- **Injecting too many dependencies** (10+). Often means the type has too many responsibilities.

### 3) **Allocation/lifetime awareness (transient vs scoped vs singleton; capture pitfalls)**

**Definitions (in typical .NET DI)**

- **Transient**: new instance every time it’s requested.
- **Scoped**: one instance per scope (commonly “per web request” in ASP.NET Core).
- **Singleton**: one instance for the lifetime of the container (often lifetime of the process).

**How to choose**

- **Singleton**:
  - stateless services
  - thread-safe caches with clear eviction rules
  - expensive-to-create, safe-to-share resources (example: `HttpClient` via `IHttpClientFactory`, or a shared serializer configuration)
- **Scoped**:
  - request-bound state (current user, correlation IDs) in server apps
  - units-of-work (DB contexts) where sharing across a request is intended
- **Transient**:
  - small, pure services with minimal state
  - adapters around dependencies

**Capture pitfalls (very common)**

- **Captive dependency**: a singleton depends on a scoped service.
  - This can cause wrong behavior (cross-request state bleed) or runtime failures.
  - Many containers detect this and throw; treat it as a correctness bug, not an annoyance.

**Performance note**

- Lifetime selection is *not* just about allocations. It’s also about:
  - **correctness** (shared state)
  - **resource lifetime** (disposing scoped resources)
  - **throughput** (excessive transients may allocate, but premature singletons can create contention)

**Good to know**

- Prefer **stateless + immutable** services. If a service needs mutable state, be explicit about:
  - ownership,
  - thread-safety,
  - scope boundaries.
