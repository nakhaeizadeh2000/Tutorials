## 4.1. Composition over inheritance (practical rules of thumb)

1. **When inheritance is OK** (true is-a, stable base contract, framework patterns)
2. **When composition wins** (behavior mix-and-match, test doubles, avoiding fragile base class problems)
3. **Performance** (composition is usually “fast enough”; design for clarity first, then measure)

---

### 1) **When inheritance is OK**
**Definition**
- **Inheritance** means a type reuses/extends behavior from a base type: “`Derived` *is-a* `Base`”.
- In C#, inheritance primarily expresses:
  - **shared contract + shared implementation**, and/or
  - a **framework-defined extension point** (override virtual methods).

**Use inheritance when all of these are true**
- The relationship is a real **substitutability** relationship (LSP): any `Derived` can be used wherever `Base` is expected *without surprising behavior*.
- The base class provides a **small, stable abstraction** that won’t change often.
- You control the base class design (or it is a well-designed framework base you deliberately opt into).
- You can document and test invariants for the base/derived interaction.

**Common legitimate cases**
- **Framework patterns**: e.g., ASP.NET Core middleware base types (rare), test frameworks, UI frameworks (frontend).
- **Template method** style: base class defines algorithm skeleton, derived overrides a few steps.
- **Closed hierarchies** (you know all derived types) — this reduces “unknown” behaviors. If a hierarchy is truly closed, consider alternatives like `sealed` + composition, or discriminated-union style modeling with pattern matching (where it fits).

**Common mistakes**
- Using inheritance just to “share code” (copy/paste avoidance). That’s often better expressed as:
  - a helper component (composition),
  - an extension method,
  - a base service extracted behind an interface.
- Making base classes “fat”: many protected members and hooks. This invites fragile coupling.

**Good to know**
- Inheritance is easiest to use *correctly* when the base class is **small** and **opinionated**.

---

### 2) **When composition wins**
**Definition**
- **Composition** means building a type out of other types:
  - “`OrderService` *has a* `IPricingPolicy` and `ITaxCalculator`” (collaboration),
  - rather than “`OrderService` *is a* `BaseOrderService`”.

**Why mentors prefer composition by default**
- **Local reasoning**: behavior is explicit in constructor parameters and fields.
- **Testability**: dependencies are swappable with fakes/mocks/stubs.
- **Avoids fragile base class problem**: base class changes can break derived classes in subtle ways.
- **Mix-and-match behavior**: strategies/decorators/policies are composable without combinatorial inheritance.

**Patterns that naturally use composition**
- **Strategy**: swap algorithms at runtime (pricing policy, retry policy).
- **Decorator**: wrap behavior (caching, logging, metrics).
- **Adapter**: wrap a dependency that has the “wrong” interface.

**Example: strategy via composition (no inheritance)**

```csharp
using System;

public interface IDiscountPolicy
{
    decimal Apply(decimal subtotal);
}

public sealed class NoDiscount : IDiscountPolicy
{
    public decimal Apply(decimal subtotal) => subtotal;
}

public sealed class PercentageDiscount(decimal percent) : IDiscountPolicy
{
    public decimal Apply(decimal subtotal)
        => subtotal - (subtotal * percent / 100m);
}

public sealed class CheckoutService(IDiscountPolicy discountPolicy)
{
    public decimal Total(decimal subtotal)
    {
        if (subtotal < 0) throw new ArgumentOutOfRangeException(nameof(subtotal));
        return discountPolicy.Apply(subtotal);
    }
}
```

**Common mistakes**
- “DI everywhere”: introducing interfaces for every class, even when there’s no variability or boundary.
  - Prefer interfaces for **boundaries** (I/O, storage, time, randomness, external services) and for domain policies that genuinely vary.

---

### 3) **Performance**
**Key idea**
- Composition and inheritance both compile down to ordinary method calls. The real performance considerations come from:
  - **virtual/interface dispatch** (can inhibit inlining and devirtualization),
  - **allocations** and **object graph size**,
  - **cache locality**.

**Practical guidance**
- Prefer composition for maintainability, then optimize hot paths.
- If you have a tight loop where polymorphism is measurable:
  - consider generics (static dispatch) or a small switch-based strategy, but only when justified by measurements.
- For a deep treatment of virtual/interface-call costs and guidance, see section `3.5. Virtual dispatch, interface calls, and performance basics` in this domain.

**Good to know**
- Modern .NET JIT can devirtualize in many cases (sealed types, known concrete types, PGO), but don’t rely on it as a design goal. Start with correctness and clarity.
