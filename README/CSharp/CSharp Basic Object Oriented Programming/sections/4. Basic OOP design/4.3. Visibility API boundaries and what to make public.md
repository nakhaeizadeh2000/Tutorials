## 4.3. Visibility, API boundaries, and “what to make public”

1. **Use the narrowest visibility** (`private`, `internal`, `protected` with intent)
2. **Avoid exposing mutable internals** (return read-only views; avoid leaking collections)
3. **Versioning mindset** (public APIs are promises; properties beat fields for evolution)

---

### 1) **Use the narrowest visibility**
**Definition**
- Visibility is the first and cheapest “architectural tool” you have in C#.
- It controls:
  - **What can be depended on** (coupling),
  - **What can change safely** (versioning),
  - **Where invariants can be enforced** (correctness).

**Recommended defaults (mentor rules)**
- Default to **`private`** for representation.
- Prefer **`internal`** for app-internal components (especially in a single repo).
- Use **`public`** only for APIs you deliberately support and intend to keep stable.
- Use **`protected`** sparingly:
  - It increases the surface area you must keep compatible for derived types.
  - It makes invariants harder to enforce (derived types can violate assumptions).

**When to use**
- **`private`**: internal state, helpers, invariants.
- **`internal`**: features shared across your application modules but not intended as a public library contract.
  - Combine with `InternalsVisibleTo` *only when necessary* (testing internal logic), and keep its usage intentional.
- **`public`**: boundary types (DTOs, public service contracts, public domain model in a shared library).

**Common mistakes**
- **Making everything `public` “for convenience”**:
  - You create accidental API that is hard to refactor later.
- **Using inheritance as a visibility escape hatch**:
  - “I’ll make it `protected` so tests/other code can access it” often backfires. Prefer extracting a dependency and injecting it (see **4.2**).

**Good to know**
- In modern SDK-style projects, a folder name does not define a boundary. **Assembly + visibility** does.
- Treat `public` members like a contract: changing them is a breaking change for callers.

---

### 2) **Avoid exposing mutable internals**
**Why this matters**
- If you expose internal mutable state, you lose control of:
  - invariants,
  - thread-safety,
  - performance characteristics (callers can add/remove/replace data unexpectedly).

**Common leaks**
- Returning a `List<T>` or `Dictionary<TKey, TValue>` directly.
- Exposing arrays (`T[]`) that callers can modify.
- Returning a `Span<T>`/`Memory<T>` that points to internal buffers without clear ownership rules.

**Preferred patterns**
- Return **read-only views**:
  - `IReadOnlyList<T>`, `IReadOnlyDictionary<TKey, TValue>`
  - `ReadOnlyCollection<T>` (wrapper over list)
  - `ImmutableArray<T>`, `ImmutableList<T>` when immutability is a real requirement (be mindful of allocations).
- Provide **methods** for controlled mutation:
  - `AddItem(...)`, `RemoveItem(...)`, `UpdateQuantity(...)` instead of `public List<Item> Items { get; }`.

**Example: don’t leak `List<T>`**

```csharp
using System.Collections.Generic;
using System.Collections.ObjectModel;

public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    // Callers can enumerate but cannot mutate your internal list.
    public ReadOnlyCollection<OrderLine> Lines => _lines.AsReadOnly();

    public void AddLine(OrderLine line)
    {
        ArgumentNullException.ThrowIfNull(line);
        _lines.Add(line);
    }
}

public sealed record OrderLine(string Sku, int Quantity);
```

**Performance note**
- `AsReadOnly()` returns a wrapper; it does not copy the list (cheap).
- Avoid returning `IEnumerable<T>` when callers need stable indexing/count; it can hide deferred execution and repeated enumeration.

---

### 3) **Versioning mindset**
**Key idea**
- Every `public` member is a promise. You can add new members easily, but changing semantics or removing members breaks callers.

**Fields vs properties**
- Prefer **properties** over public fields because properties allow you to:
  - introduce validation later,
  - add lazy computation,
  - maintain binary compatibility with existing callers (depending on usage),
  - participate in data binding/serialization conventions.
- In libraries, avoid `public` mutable fields almost always.

**Binary compatibility and evolution**
- Changing a field to a property is often a source/binary breaking change for consumers.
- Plan your public API shape early:
  - keep it small,
  - keep it cohesive,
  - avoid exposing internal data structures.

**Legacy patterns to avoid**
- “Make everything virtual for extensibility.”
  - This enlarges your compatibility surface and can block optimizations (see **3.5**).
  - Prefer explicit extension points (interfaces, delegates, composition).

**Good to know**
- If your “domain” is internal to one app, using `internal` aggressively is a strength: it unlocks refactoring.
- If you publish libraries, follow semantic versioning and consider analyzer packages to enforce API rules.
