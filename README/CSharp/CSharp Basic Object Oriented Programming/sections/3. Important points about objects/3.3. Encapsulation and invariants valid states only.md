## 3.3. Encapsulation and invariants: “valid states only”

1. **Invariants** (rules that must always be true; enforce at boundaries)
2. **Validation strategy** (constructor vs factory vs method-level; exceptions vs Try-pattern)
3. **API design** (avoid “set anything anytime”; prefer intention-revealing methods)

---

### 1) **Invariants (rules that must always be true)**
**Definition**
- An **invariant** is a condition that must be true for an object to be “valid” at all times *outside* of its own internal methods.
- Examples:
  - `Money.Amount >= 0`
  - `Order` can only transition `Draft -> Submitted -> Paid` (not `Paid -> Draft`)
  - `Range.Start <= Range.End`

**Why invariants are the heart of OOP**
- OOP isn’t “state + getters/setters”. It’s **state protected by behavior** that enforces rules.
- If invariants are not enforced inside the type, they end up scattered across callers, which:
  - increases bugs (missed checks),
  - makes refactoring dangerous,
  - forces “knowledge of rules” into unrelated places.

**When to enforce**
- Enforce invariants at **boundaries**:
  - constructor / factory (object creation),
  - methods that change state (mutations),
  - “aggregate root” methods in domain modeling.

**Common mistakes (mentor notes)**
- **Public setters everywhere**: makes it impossible to enforce invariants.
- **“Validate later” design**: you end up with partially-initialized objects and conditional logic everywhere.
- **Using null as a state**: e.g. `EndDate = null` meaning “still active”, without a domain concept.

**Example: invariant-driven type**

```csharp
using System;

public sealed class TemperatureCelsius
{
    // Invariant: temperature cannot be below absolute zero.
    private const double AbsoluteZero = -273.15;

    public double Value { get; }

    public TemperatureCelsius(double value)
    {
        if (value < AbsoluteZero)
            throw new ArgumentOutOfRangeException(nameof(value), $"Must be >= {AbsoluteZero}°C.");

        Value = value;
    }

    public TemperatureCelsius AddDelta(double delta) => new(Value + delta); // preserves invariant
}
```

**Good to know**
- Invariants do not require immutability, but **immutability makes invariants easier** because state can’t be changed from the outside (see section **3.1**).

---

### 2) **Validation strategy (constructor vs factory vs method-level)**
**Goal**
- Decide **where** validation lives so invalid states are impossible or short-lived.

**Constructor validation**
- Best for invariants that must hold for the object’s entire life.
- Keeps the object always valid once created.
- Downside: constructors can’t be async and can’t return “failure without exceptions” naturally.

**Factory validation**
- Use a factory when you need:
  - non-exceptional failure paths (`TryCreate`),
  - complex creation rules,
  - caching/interning,
  - potentially async work (then it becomes `CreateAsync`, not a constructor).

**Method-level validation**
- Use for rules that depend on *inputs* or *current state* at the time of mutation (e.g. “you can’t withdraw more than balance”).

**Exceptions vs Try-pattern**
- **Use exceptions** for *programmer errors* / invariant violations (unexpected invalid input, impossible states).
- **Use `TryXxx`** for expected invalid user input or business-level failures you expect callers to handle frequently.

**Example: `TryCreate` for user input**

```csharp
using System;

public readonly record struct Percentage
{
    public decimal Value { get; }
    private Percentage(decimal value) => Value = value;

    public static bool TryCreate(decimal value, out Percentage percentage)
    {
        if (value is < 0 or > 100)
        {
            percentage = default;
            return false;
        }

        percentage = new Percentage(value);
        return true;
    }
}
```

**Performance note**
- Avoid using exceptions as control flow in hot paths. Throwing is expensive (stack walking, allocation of exception objects, loss of inlining).
- For high-frequency validation, prefer Try-patterns.

---

### 3) **API design: prevent invalid states by construction**
**Principles**
- **Make illegal states unrepresentable** (when it doesn’t overcomplicate).
- Keep mutation points small and intention-revealing:
  - `order.AddItem(productId, quantity)` not `order.Items.Add(...)`
- Hide representation details; expose behavior and safe read models.

**Avoid leaking mutability**
- Don’t expose `List<T>` or mutable dictionaries directly.
- Return:
  - `IReadOnlyList<T>`, `IReadOnlyDictionary<K,V>` (API boundary),
  - or `ReadOnlyCollection<T>`,
  - or enumerables.

**Use modern C# features to help**
- `required` members for object initialization *when you allow object initializers*.
- `init` for one-time settable properties.
- `record` / `record struct` for value-like immutable models.

**Example: safe read-only exposure + intention-revealing behavior**

```csharp
using System;
using System.Collections.Generic;

public sealed class ShoppingCart
{
    private readonly Dictionary<string, int> _items = new(StringComparer.Ordinal);

    public IReadOnlyDictionary<string, int> Items => _items;

    public void AddItem(string sku, int quantity)
    {
        if (string.IsNullOrWhiteSpace(sku)) throw new ArgumentException("SKU is required.", nameof(sku));
        if (quantity <= 0) throw new ArgumentOutOfRangeException(nameof(quantity));

        _items.TryGetValue(sku, out int current);
        _items[sku] = checked(current + quantity);
    }
}
```

**Common mistakes**
- “Just expose everything; we’ll be careful.” You won’t be, especially at team scale.
- Trying to encode every rule in the type system; overdoing it can harm readability. Balance matters.
