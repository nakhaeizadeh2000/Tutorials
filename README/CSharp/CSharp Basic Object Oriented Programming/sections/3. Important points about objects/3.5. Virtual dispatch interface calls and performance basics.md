## 3.5. Virtual dispatch, interface calls, and performance basics

1. **Why virtual exists** (extension points) and its costs (devirtualization limits)
2. **Prefer composition** (inject strategies via interfaces; keep inheritance shallow)
3. **Hot path guidance** (avoid polymorphism in tight loops; prefer generics when appropriate)

---

### 1) **Why virtual exists (and what it costs)**
**Definition**
- **Virtual dispatch** is the runtime mechanism that selects which override implementation to call based on the *runtime type* of an object.
- In C#, this happens through:
  - **virtual/override** methods on classes
  - calls through **interfaces** (which are also dynamically dispatched at runtime)

**When to use**
- Use virtual methods/interfaces when:
  - You need a **stable contract** with multiple implementations (storage providers, payment gateways, clock/time abstraction, feature toggles).
  - You’re designing a **framework-style** base type where subclasses extend behavior (rare in most application code).
  - You need **testability**: swap a real implementation with a fake/stub.

**Trade-offs**
- **Pros**:
  - Extensibility without editing callers.
  - Decoupling: callers depend on contract, not concrete details.
- **Cons**:
  - **Indirection**: you can’t see which implementation runs without knowing runtime type.
  - **Optimization limits**: the JIT may be unable to inline or devirtualize a call, which can matter in hot loops.
  - More complex debugging and performance profiling if overused.

**Performance reality (mentor framing)**
- A virtual/interface call is not “slow” in typical business code; it’s usually irrelevant compared to I/O, allocations, and algorithmic complexity.
- It *does* matter when:
  - You execute the call **millions of times** per second in a tight loop.
  - The method is tiny and would benefit from **inlining**.

**Common mistakes**
- Using interfaces/virtual methods everywhere “just because SOLID”:
  - Abstraction is a tool, not a default.
  - If there is only one implementation and it’s not a boundary, abstraction may reduce clarity.
- Putting polymorphism in the inner loop:
  - e.g., per-element strategy objects for a large array.

**Good to know**
- The JIT can sometimes **devirtualize** when it can prove the concrete type (sealed types, exact type known, PGO feedback), but you should not rely on it as a design strategy.

### 2) **Prefer composition (interfaces as seams)**
**Definition**
- **Composition** means you build a type by *having* other components rather than *being* a subtype of a base class.
- In practice: “inject a dependency that does a thing” rather than “inherit and override a method”.

**When composition wins**
- You want to vary behavior by configuration, environment, or tests.
- You want to avoid “fragile base class” problems (base class changes break derived classes).
- You want multiple independent behaviors without deep inheritance trees.

**Example: composition with an injected strategy**

```csharp
public interface IDiscountPolicy
{
    decimal Apply(decimal subtotal);
}

public sealed class NoDiscount : IDiscountPolicy
{
    public decimal Apply(decimal subtotal) => subtotal;
}

public sealed class PercentageDiscount(decimal percent) : IDiscountPolicy
{
    public decimal Apply(decimal subtotal) => subtotal * (1 - percent);
}

public sealed class CheckoutService(IDiscountPolicy discountPolicy)
{
    public decimal Total(decimal subtotal) => discountPolicy.Apply(subtotal);
}
```

**Why this is mentor-approved**
- You can add new policies without editing `CheckoutService`.
- You can test `CheckoutService` by passing a fake policy.
- No inheritance tree required; each policy is a small, focused type.

**Performance note**
- If this becomes a hot path, you can:
  - use a **switch** on an enum (data-oriented) for a fixed set of policies, or
  - use **generics** to enable static dispatch (next section),
  - but only after measuring.

### 3) **Hot path guidance: avoid polymorphism in tight loops**
**Rule of thumb**
- If the call is inside a loop over **large data**, prefer designs that allow:
  - inlining,
  - fewer allocations,
  - better locality.

**Common patterns**
- **Interface/virtual in the loop (may be fine, may not):**

```csharp
static double SumAreas(IShape[] shapes)
{
    double sum = 0;
    foreach (var s in shapes)
        sum += s.Area(); // interface call per element
    return sum;
}

public interface IShape { double Area(); }
```

- **Generic (static) dispatch (often faster, less flexible):**

```csharp
public interface IAreaCalculator<T>
{
    static abstract double Area(in T value);
}

public readonly record struct Circle(double Radius) : IAreaCalculator<Circle>
{
    public static double Area(in Circle c) => Math.PI * c.Radius * c.Radius;
}

static double SumAreas<T>(ReadOnlySpan<T> values) where T : IAreaCalculator<T>
{
    double sum = 0;
    for (int i = 0; i < values.Length; i++)
        sum += T.Area(in values[i]); // resolved statically; no virtual dispatch
    return sum;
}
```

**Trade-offs**
- The generic/static approach is very fast but less flexible:
  - you can’t easily mix multiple shape types in one array without some form of union/discriminated representation.
  - it’s great for performance-critical kernels; not always ideal for domain modeling.

**Good to know**
- Boxing: avoid calling interfaces on value types in a way that forces boxing.
  - Example pitfall: `IComparable` on a struct via `object`.
  - Prefer `IEquatable<T>` and generic interfaces where possible.
