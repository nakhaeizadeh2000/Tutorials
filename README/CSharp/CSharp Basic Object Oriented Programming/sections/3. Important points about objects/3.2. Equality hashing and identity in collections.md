## 3.2. Equality, hashing, and identity in collections

1. **When to override `Equals`/`GetHashCode`** (value objects; stable keys)
2. **Pitfalls** (mutable keys in dictionaries, reference cycles, floating-point equality)
3. **Best practices** (`IEquatable<T>`, consistent equality rules, use `StringComparer` explicitly)

---

### 1) **When to override `Equals`/`GetHashCode`**

**Definition**

- **Equality** answers: *“Are these two instances considered the same for my domain?”*
- In .NET you typically deal with three related notions:
  - **Reference identity**: do two references point to the **same object**? (`ReferenceEquals(a, b)`).
  - **Value equality**: do two values represent the **same value**? (e.g., two Money values with same currency+amount).
  - **Ordering**: how to sort (`IComparable<T>`) — separate from equality.

**When you should override**

- Override (or define) equality when the type is a **value object**:
  - It has **no meaningful identity** beyond its values.
  - Two instances with the same values should be interchangeable (e.g., `Money`, `EmailAddress`, `ProductCode`).
- If instances will be used as **dictionary keys** or in **hash sets**, you must have:
  - a stable equality definition and
  - a matching `GetHashCode`.

**When you should *not* override**

- Don’t override for **entities** whose identity is “which one in the real world” (e.g., `CustomerId` identifies the customer; the `Customer` entity itself typically uses identity semantics).
- Don’t override if equality is ambiguous or changes with context (a smell that the type might be doing too much).

**Modern C# guidance**

- Prefer using `record` / `record struct` for “value object” types when the default structural equality matches your semantics.
- For classes that are value objects but shouldn’t be `record`, implement:
  - `IEquatable<T>`
  - `override bool Equals(object?)`
  - `override int GetHashCode()`
  - `==` and `!=` operators (optional, but nice if consistent)

**Example: value object implemented as a `readonly record struct`**

```csharp
public readonly record struct EmailAddress
{
    public string Value { get; }

    public EmailAddress(string value)
    {
        // Keep example minimal; in real code validate format.
        Value = value.Trim();
    }

    // record struct gives value equality + hash code automatically.
    public override string ToString() => Value;
}
```

**Performance note**

- Value equality often means reading multiple fields to compute hash codes.
  - Keep value objects **small and immutable**.
  - Avoid computing hash codes from expensive normalized transformations repeatedly; cache only if truly hot and immutable.

### 2) **Pitfalls**

#### **Pitfall: mutable keys in dictionaries**

If a dictionary key changes after insertion, lookups can break because the hash bucket is computed from the old hash.

```csharp
using System;
using System.Collections.Generic;

public sealed class BadKey
{
    public int Id { get; set; } // mutable
    public override int GetHashCode() => Id;
    public override bool Equals(object? obj) => obj is BadKey other && other.Id == Id;
}

var dict = new Dictionary<BadKey, string>();
var k = new BadKey { Id = 1 };
dict[k] = "value";

k.Id = 2;               // Key mutated AFTER insert
Console.WriteLine(dict.ContainsKey(k)); // false (often)
```

**Mentor rule**: keys must be **immutable for their entire lifetime as a key**.

#### **Pitfall: reference cycles and graph equality**

- “Deep equality” for object graphs is hard:
  - cycles cause infinite recursion,
  - shared references (two paths to same node) complicate “sameness”,
  - it’s expensive.
- Prefer defining equality on **stable identifiers** (IDs) for entities; keep deep graph comparisons to tests or special tooling.

#### **Pitfall: floating-point equality**

- `double`/`float` are approximations; exact equality is often wrong for computed values.
- Prefer:
  - exact comparisons only for values you control (e.g., persisted bits), or
  - tolerance-based comparisons in domain-specific places.

**Good to know**: `decimal` is often better for money, but it’s slower than `double`. Choose based on correctness first.

### 3) **Best practices**

#### **Implement equality as a coherent “contract”**

Your equality should obey:

- **Reflexive**: \(x == x\)
- **Symmetric**: \(x == y\) implies \(y == x\)
- **Transitive**: \(x == y\) and \(y == z\) implies \(x == z\)
- **Consistent**: repeated comparisons don’t change unless values used for equality change (immutability helps)
- **Hash code compatibility**: if \(x.Equals(y)\) then \(x.GetHashCode() == y.GetHashCode()\)

#### **Use `IEquatable<T>` for performance and correctness**

- Avoids boxing and virtual dispatch in generic collections.

#### **Be explicit with `StringComparer`**

Default string dictionary comparisons are **ordinal case-sensitive** unless you specify otherwise. Choose intentionally:

```csharp
using System;
using System.Collections.Generic;

var byId = new Dictionary<string, int>(StringComparer.Ordinal);           // fast, culture-invariant
var byEmail = new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase); // typical for emails/usernames
```

#### **Prefer `record` where it matches semantics**

- `record` (class) has value-based equality by default, but it’s still a reference type.
- `record struct` gives value equality and can reduce allocations for small values.

#### **Entity equality: prefer stable identity**

For entities, define equality in terms of an immutable ID:

```csharp
public sealed class Customer : IEquatable<Customer>
{
    public Guid Id { get; }
    public string Name { get; private set; }

    public Customer(Guid id, string name)
    {
        Id = id;
        Name = name;
    }

    public bool Equals(Customer? other) => other is not null && Id == other.Id;
    public override bool Equals(object? obj) => obj is Customer c && Equals(c);
    public override int GetHashCode() => Id.GetHashCode();
}
```

**Performance note**

- Hash-based collections are fast when hashing is cheap and keys are stable.
- Avoid “expensive equality” types as keys on hot paths (deep comparisons, allocations, culture-sensitive comparisons).
