## 4.2. Optional parameters (default arguments): versioning and correctness

1. **How defaults work** (baked into the caller at compile time; not “looked up” at runtime)
2. **Versioning rule** (changing defaults is a breaking behavior change for already-compiled consumers)
3. **Best practice** (prefer method overloads for public APIs; use optional parameters mainly within apps/internal code)

Optional parameters are convenient, but they have a non-obvious property that matters for production APIs: **the default value is baked into the *caller***. This section focuses on how that affects correctness, versioning, and API design.

---

### 1. **How defaults work**

**What actually happens**

When you write:

```csharp
Log("hello"); // omits optional arg
```

the compiler rewrites the call site as if you wrote:

```csharp
Log("hello", level: LogLevel.Info);
```

So:

- Defaults are **substituted at compile time**.
- The callee does **not** “look up” the current default value at runtime.

This is why optional parameters can be dangerous for libraries consumed by other compiled assemblies.

**What can be a default**

Defaults must be compile-time constants (or `default` / `default(Type)`), which leads to common patterns:

- `int retryCount = 3`
- `string? name = null`
- `CancellationToken cancellationToken = default`

Mentor rule:

- Prefer `CancellationToken cancellationToken = default` for optional cancellation in async APIs (token last).
- Avoid “magic number” defaults in public APIs without naming the concept clearly (`maxRetries = 3` is better than `x = 3`).

**Common mistake: using `new()` as a default**

This is illegal for optional parameters:

```csharp
// ❌ Not allowed (not a compile-time constant)
// public void M(List<int> items = new()) { }
```

If you need an optional collection, use `null` as the default and create inside:

```csharp
public static int SumOrEmpty(IReadOnlyList<int>? items = null)
{
    items ??= Array.Empty<int>();
    var sum = 0;
    for (var i = 0; i < items.Count; i++) sum += items[i];
    return sum;
}
```

Performance note:

- `Array.Empty<T>()` is allocation-free and cached.

---

### 2. **Versioning rule**

**Why changing defaults breaks behavior**

Because defaults are compiled into the caller, changing the default in a library does **not** affect callers compiled against the old version.

Example scenario:

- v1 of a library: `Timeout = 5s`
- v2 of a library: `Timeout = 30s`

Existing apps compiled against v1 and upgraded to v2 without recompiling will still pass `5s` at the call site.

Mentor rule (public libraries):

- Treat changing an optional parameter default as a **breaking behavior change**.

**Safe evolution techniques**

- Add **new overloads** instead of changing defaults.
- Add new optional parameters only at the **end** (otherwise call sites may bind differently).
- Prefer an **options type** for APIs that will evolve.

See also:

- Overload design and ambiguity: section [5.1](<../5. Overload resolution and overloading/5.1. Method overloading rules ambiguity API design.md>)
- Named arguments refactoring caveats: section [4.3](<./4.3. Named arguments readability maintainability.md>)

### 3. **Best practice**

**When optional parameters are fine**

- Internal application code where caller and callee ship together and are rebuilt together.
- Small, stable APIs where defaults are truly stable and unlikely to change.
- Convenience wrappers over a “core” overload.

**When to prefer overloads**

For public APIs and libraries, overloads make versioning safer:

```csharp
public enum LogLevel { Trace, Debug, Info, Warning, Error }

public static class Logger
{
    public static void Log(string message) =>
        Log(message, LogLevel.Info);

    public static void Log(string message, LogLevel level)
    {
        // write to sink...
    }
}
```

**When to prefer an options type**

If you have many knobs or expect growth, use an options record/struct:

```csharp
public sealed record HttpRetryOptions(
    int MaxRetries,
    TimeSpan BaseDelay,
    bool UseJitter);

public static class Retrier
{
    public static async Task RunAsync(
        Func<CancellationToken, Task> operation,
        HttpRetryOptions options,
        CancellationToken cancellationToken = default)
    {
        // Minimal example; focus is API shape.
        for (var attempt = 0; attempt <= options.MaxRetries; attempt++)
        {
            cancellationToken.ThrowIfCancellationRequested();
            try
            {
                await operation(cancellationToken).ConfigureAwait(false);
                return;
            }
            catch when (attempt < options.MaxRetries)
            {
                await Task.Delay(options.BaseDelay, cancellationToken).ConfigureAwait(false);
            }
        }
    }
}
```

Good to know:

- Options types help you avoid “boolean flag soup” and make call sites self-documenting.
- For high-performance hot paths, prefer `readonly record struct` options and pass by `in` only when measurements show it matters (see [6.5](<../6. Parameter modifiers and ref-like patterns/6.5. in parameters read-only by-ref defensive copies.md>)).
