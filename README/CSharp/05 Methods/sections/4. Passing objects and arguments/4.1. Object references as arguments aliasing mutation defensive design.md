## 4.1. Object reference as arguments: aliasing, mutation, and defensive design

1. **Reference semantics** (passing a reference copies the reference, not the object; aliasing hazards)
2. **Mutation strategy** (prefer immutable inputs; if mutating, make it explicit in naming and documentation)
3. **Perf + safety** (avoid unnecessary cloning; prefer stable ownership boundaries and clear “who mutates” rules)

Passing objects to methods is where many “it compiles but behaves weirdly” bugs come from: aliasing, invisible mutation, and unclear ownership. The goal is to design method boundaries so callers can predict what happens without reading the callee.

---

### 1. **Reference semantics**

**What C# actually passes**

By default, C# is **pass-by-value** for parameters. What gets copied depends on the parameter type:

- **Value type** (`struct`): the *value* is copied (unless you use `ref`/`in`/`out`).
- **Reference type** (`class`): the *reference* (pointer-like handle) is copied; both caller and callee now refer to the **same object**.

So: passing a reference type does **not** copy the object. It copies the reference.

**Aliasing hazard**

Aliasing means: two different variables refer to the same object. Any mutation through one alias is visible through the other.

```csharp
using System;
using System.Collections.Generic;

public static class Demo
{
    public static void AddAdminRole(List<string> roles)
    {
        // Mutates caller-owned collection (aliasing).
        roles.Add("Admin");
    }

    public static void Main()
    {
        var roles = new List<string> { "User" };
        AddAdminRole(roles);
        Console.WriteLine(string.Join(", ", roles)); // User, Admin
    }
}
```

Good to know:

- The method signature `AddAdminRole(List<string> roles)` silently implies mutation is possible. If that’s not intended, don’t accept `List<T>`.

**Design lever: choose input types that encode intent**

- If you do **not** want mutation: accept `IReadOnlyList<T>`, `IEnumerable<T>`, or `ReadOnlySpan<T>` (for temporary, allocation-free views).
- If you want to accept sequences but must materialize: accept `IEnumerable<T>` and materialize once (`ToArray`) at the boundary (document it).
- If you want to allow mutation explicitly: accept `ICollection<T>`/`List<T>` and name the method to signal it.

Note: “Read-only interface” prevents mutation *through that reference*, but does not guarantee the underlying object isn’t mutated elsewhere. True immutability requires immutable types or defensive copying.

---

### 2. **Mutation strategy**

**Default recommendation**

- Prefer **immutable inputs** and return a new value (pure function style) when feasible.
- If mutation is needed (performance, API requirements), make it **obvious**:
  - Method name signals mutation: `NormalizeInPlace`, `SortInPlace`, `AddX`, `RemoveX`.
  - Parameter names signal ownership: `destination`, `buffer`, `builder`, `output`.

**Modern patterns**

- For “build up a result” without mutation leakage: use a builder type (`StringBuilder`, pooled buffers, or custom builder) and return an immutable result.
- For transformations on data buffers: accept `Span<T>`/`Memory<T>` for explicit, caller-owned mutation.

```csharp
using System;

public static class Normalization
{
    // Pure: does not mutate input.
    public static string NormalizeUserName(string input)
        => input.Trim().ToUpperInvariant();

    // In-place: explicit mutation via Span.
    public static void TrimAsciiSpacesInPlace(Span<char> buffer, out int newLength)
    {
        int start = 0, end = buffer.Length - 1;
        while (start <= end && buffer[start] == ' ') start++;
        while (end >= start && buffer[end] == ' ') end--;

        newLength = Math.Max(0, end - start + 1);
        if (start == 0) return;

        buffer.Slice(start, newLength).CopyTo(buffer);
    }
}
```

Performance note:

- `Span<T>` avoids allocations but is stack-only; you can’t store it in fields or use it across `await`.
- If your method is async and needs to hold data, use `Memory<T>` (heap-based owner) rather than `Span<T>`.

**Common mistakes**

- Mutating inputs in a method whose name does not suggest mutation.
- Returning internal mutable collections (callers can change your internal state).
- Using `ref` parameters as a “clever optimization” in business code (see section [6.2](<../6. Parameter modifiers and ref-like patterns/6.2. ref parameters when to use.md>) and [6.5](<../6. Parameter modifiers and ref-like patterns/6.5. in parameters read-only by-ref defensive copies.md>) for ref-like trade-offs).

### 3. **Perf + safety**

**Avoid unnecessary cloning—but define ownership**

Copying has costs (CPU + allocations), but not copying has costs too (coupling + bugs). The answer is not “always clone” or “never clone”; it’s **choose clear ownership boundaries**:

- **Caller-owned inputs**: treat as read-only unless explicitly documented otherwise.
- **Callee-owned internal state**: never expose mutable references to it.

**Return types and allocation control**

- If a method naturally returns “many items”, prefer returning an **iterator** (`IEnumerable<T>`) only when deferred execution is intended and safe. Otherwise, return `T[]`/`List<T>`/`ImmutableArray<T>` with explicit materialization.
- Avoid returning lazily evaluated sequences that capture resources (like a DB reader) unless you control the lifetime carefully.

Performance note:

- “Allocations from convenience” are often the hidden killer: repeated `.ToList()` or `.ToArray()` in hot paths, repeated string concatenations, LINQ in tight loops. Optimize only where profiling shows it matters.

Good to know:

- If you need a “read-only view” of an internal array without copying, `ReadOnlyMemory<T>` can be a good fit for long-lived ownership, and `ReadOnlySpan<T>` for short-lived views.
