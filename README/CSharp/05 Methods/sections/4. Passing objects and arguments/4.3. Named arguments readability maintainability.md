## 4.3. Named arguments: readability vs long-term maintainability

1. **Where it shines** (many optional parameters; boolean “flag” parameters; readability at call sites)
2. **Refactoring caveat** (parameter renames can break call sites that use names)
3. **Mentor rule** (use named args to avoid ambiguity; avoid overusing them as a “poor man’s builder”)

Named arguments are a **call-site feature**: they change readability and the refactor surface area without changing the callee. Used well, they prevent bugs. Used carelessly, they create brittle call sites and “pseudo-builders” that should have been real types.

---

### 1. **Where it shines**

**What it is**

Named arguments allow specifying parameters by name at the call site:

```csharp
SendEmail(
    to: "dev@example.com",
    subject: "Build failed",
    body: "See logs...",
    highPriority: true);
```

**Best use cases**

- **Many optional parameters** where positional calls become unreadable.
- **Boolean / flag parameters** where `true/false` is ambiguous.
- **Same-type parameters** (e.g., multiple `int`/`string` parameters) where order bugs are common.
- **Long parameter lists** you cannot avoid (but see “mentor rule” below: long lists often indicate missing abstractions).

**Trade-offs**

- Readability improves, but the call site is now coupled to parameter names (see item 2).
- It can hide an API design smell: a method with too many responsibilities/options.

Note:

- Named arguments are a *tool for clarity*, not a license to create 10-parameter “god methods”.

---

### 2. **Refactoring caveat**

**The important rule**

If a consumer uses named arguments, then **renaming a parameter is a breaking change** for that consumer.

This matters most for:

- **Public libraries** (NuGet packages)
- Shared internal libraries consumed by multiple repos/teams

**What is safe vs risky**

- **Safe-ish**: rename parameters in app code you control, if you can refactor all call sites in one change.
- **Risky**: rename parameters in widely-consumed APIs—even if it “compiles for you”, it may break downstream builds.

**Common mistakes**

- Treating parameter names as “internal implementation details”. Once callers use names, they’re part of your API surface.
- Reordering parameters “because it looks nicer”. Named arguments reduce order dependency, but positional calls still exist.

See also:

- Overload interactions and ambiguity in section [5.1](<../5. Overload resolution and overloading/5.1. Method overloading rules ambiguity API design.md>) (named + optional + `params` can produce surprising compile-time choices).

---

### 3. **Mentor rule**

**Use named arguments to eliminate ambiguity**

Examples where named args prevent real bugs:

```csharp
using System;

static DateTimeOffset CreateExpiry(DateTimeOffset nowUtc, TimeSpan ttl)
    => nowUtc + ttl;

var expiry = CreateExpiry(nowUtc: DateTimeOffset.UtcNow, ttl: TimeSpan.FromMinutes(10));
```

**Don’t use named args as a “poor man’s builder”**

If call sites look like configuration blocks, consider replacing the parameter list with a type:

- **Options record** (immutable, easy to version)
- **Builder** (when incremental construction is necessary)

```csharp
public sealed record EmailOptions(
    string To,
    string Subject,
    string Body,
    bool HighPriority = false);

public static void SendEmail(EmailOptions options)
{
    // Implementation omitted.
}

SendEmail(new EmailOptions(
    To: "dev@example.com",
    Subject: "Build failed",
    Body: "See logs...",
    HighPriority: true));
```

Good to know:

- Records make versioning safer: adding a new optional property is typically less breaking than extending long parameter lists (still consider API compatibility and serialization concerns).
- For public libraries, prefer overloads or options types over optional parameters (see section [4.2](<./4.2. Optional parameters default arguments versioning correctness.md>)).
