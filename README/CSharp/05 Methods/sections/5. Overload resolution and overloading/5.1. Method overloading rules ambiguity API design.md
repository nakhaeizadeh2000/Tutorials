## 5.1. Method overloading: rules, ambiguity, and API design

1. **Overload resolution basics** (best match, conversions, generics, `params`, optional parameters interactions)
2. **Ambiguity traps** (numeric literals, null, lambdas, method groups, default literals)
3. **API design** (prefer small coherent overload sets; avoid “overload soup”; keep behavior consistent)

Overloading is powerful, but it is also where “looks obvious to humans” diverges from “the compiler has precise rules.” This section gives you the mental model to predict what happens and to design overload sets that remain safe for years.

---

### 1. **Overload resolution basics**

**What overload resolution is**

At each call site, the compiler builds a set of candidate methods and picks the **best function member**. This is purely **compile-time** and depends on:

- The **static types** of the arguments and receiver
- Available **implicit conversions**
- **Generic type inference**
- Whether `params` expansion and/or **optional parameter** substitution is permitted

Important: once an overload is selected, *runtime dispatch* (virtual/interface calls) determines which implementation runs. See section `1.1` for the compile-time vs runtime split.

**Key rules you should remember**

- **Exact matches win** over converted matches.
- **Identity conversions** win over numeric conversions.
- **Better conversions** win (e.g., `int` to `long` vs `int` to `double` can behave differently than intuition).
- **Generic inference** can change which overload is viable.
- `params` is considered, but **non-`params` candidates are preferred** when both are viable.
- **Optional parameters** are substituted by the compiler (caller side) and can interact with overload sets in surprising ways (see section `4.2`).

**Example: “why did it pick that overload?”**

```csharp
using System;

public static class Overloads
{
    public static void M(long x) => Console.WriteLine($"long: {x}");
    public static void M(double x) => Console.WriteLine($"double: {x}");
}

public static class Demo
{
    public static void Main()
    {
        Overloads.M(1);   // int literal: prefers long (integral conversion) over double (floating conversion)
        Overloads.M(1.0); // double literal: exact match
    }
}
```

Good to know:

- Literal typing and “better conversion” rules are why API overloads for numeric types can become surprising. Prefer explicit overload sets (or one type) unless you truly need multiple numeric types.

### 2. **Ambiguity traps**

These are the cases that most often break builds during refactors or when adding “just one more overload”.

#### Trap A: `null`

`null` is convertible to any reference type and nullable value type. If you have two overloads that accept different reference types, `null` can be ambiguous.

```csharp
public static class NullTrap
{
    public static void Log(string message) { }
    public static void Log(Exception ex) { }

    public static void Demo()
    {
        // Log(null); // ambiguous: could be string or Exception
        Log(message: null!); // disambiguate (but be careful)
    }
}
```

Mentor rule:

- Avoid overload sets that differ only by unrelated reference types if callers might pass `null`.

#### Trap B: lambdas and method groups

Lambdas can convert to many delegate types if the signatures are compatible, and method groups can convert similarly.

```csharp
using System;

public static class LambdaTrap
{
    public static void Register(Func<int> f) { }
    public static void Register(Func<long> f) { }

    public static void Demo()
    {
        // Register(() => 0); // ambiguous: 0 can be int or long; both conversions exist
        Register(static () => 0); // still ambiguous; static only affects captures
    }
}
```

Fix patterns:

- Add an explicit cast: `Register((Func<int>)(static () => 0));`
- Or make overloads more distinct (prefer this in public APIs).

#### Trap C: `default` literals

`default` has no type until context provides one.

```csharp
public static class DefaultTrap
{
    public static void Set(int value) { }
    public static void Set(DateTime value) { }

    public static void Demo()
    {
        // Set(default); // ambiguous
        Set(default(int)); // explicit
    }
}
```

#### Trap D: `params` + optional parameters

These features are caller-side conveniences that can make overload sets fragile.

- `params` may allocate an array (see section `6.7`).
- Optional defaults are baked into callers (see section `4.2`).

Mentor rule:

- Avoid mixing `params` + optional parameters + many overloads in the same API unless you test call-site behaviors and document them.

### 3. **API design**

**Keep overload sets small and coherent**

Overload “soup” is where:

- Call sites become hard to read (and hard to choose the correct overload).
- Additions become breaking changes due to new ambiguities.

Prefer:

- A small overload set for ergonomics (common cases).
- A single “core” overload (full parameter list) that others delegate to.

**Make behavior consistent across overloads**

Bad:

- One overload validates and throws; another silently clamps.
- One overload uses current culture; another uses invariant culture.

Good:

- All overloads follow the same invariants and failure strategy (`Try...` vs exceptions).

**Prefer explicit “options” over many overloads (in app code)**

If you keep adding overloads to represent combinations of knobs, consider:

- An options `record`/`record struct` (immutable configuration)
- Named arguments for rare options (see section `4.3`)

But for *public libraries*, be careful: options objects can become versioning constraints too. Sometimes overloads are still better—just keep them disciplined.

**Performance note**

- Overload resolution itself is compile-time; there’s no runtime cost.
- Runtime cost shows up if overloads lead you to choose allocations (e.g., `params` arrays) or interface dispatch in hot loops. Design your overloads so the allocation-free path is the easy path.
