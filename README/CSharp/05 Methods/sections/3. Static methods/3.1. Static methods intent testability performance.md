## 3.1. Static methods: intent, testability, and performance reality

1. **When static is right** (pure functions, utilities, factory methods, stateless transforms)
2. **API design** (prefer static over singleton mutable state; use dependency injection when behavior has dependencies)
3. **Performance** (often trivially inlineable; avoid hidden global state and contention)

Static methods are one of the most common tools for **clarity** (“this behavior doesn’t need an instance”) and **performance** (often easy to inline). The trap is confusing “static method” with “global mutable state”. This section is about making that distinction sharp.

---

### 1. **When static is right**

**Definition**

A static method is a method that:

- Has **no `this`** (no instance receiver).
- Can only access **static members** directly.
- Often represents behavior that is **pure** (output depends only on inputs) or at least **stateless** with respect to the type instance.

**Great use cases**

- **Pure functions / transforms**: normalization, parsing, formatting, projection.
- **Utility helpers** that are cohesive and discoverable (ideally as part of a type that owns the concept, not “random helpers”).
- **Factory methods**: `Create(...)`, `TryCreate(...)`, `FromX(...)` where you want validation and invariants at creation time.
- **Algorithmic helpers** used across instances (e.g., `Hash`, `Compare`, `Validate`).

**When static is *not* right**

- When behavior depends on varying external dependencies (time, randomness, I/O, configuration, database, HTTP).
- When you need polymorphism (behavior varies by implementation) and that variation is part of the design.

Mentor rule:

- If a method would need to read from “ambient state” (global variables, `static` caches, mutable singletons) to do useful work, **prefer injecting dependencies** instead.

**Example: static factory that enforces invariants**

```csharp
using System;

public readonly record struct EmailAddress(string Value)
{
    public static bool TryCreate(ReadOnlySpan<char> input, out EmailAddress email)
    {
        // Minimal example; real validation is more complex.
        if (input.IsEmpty || input.Length > 254 || input.IndexOf('@') <= 0)
        {
            email = default;
            return false;
        }

        // Allocation here is intentional: a value object needs stable storage.
        email = new EmailAddress(input.ToString());
        return true;
    }
}
```

Note: A factory (`TryCreate`) is a clean place to centralize validation (see section [1.2](<../1. Method fundamentals/1.2. Encapsulation with methods invariants boundaries.md>)) and avoid “invalid instance” states.

### 2. **API design**

**Static vs singleton vs DI (dependency injection)**

- **Static method**: fine. It’s *behavior without state*.
- **Singleton** (especially a mutable one): often a hidden global variable; tends to create test brittleness and concurrency bugs.
- **DI**: the modern default for behavior that depends on collaborators and runtime configuration.

**Avoid static “service classes” that hide dependencies**

This is a common anti-pattern:

- `static class UserService { static HttpClient _client; ... }`

Problems:

- **Testability**: hard to substitute dependencies.
- **Lifetime management**: resource leaks or incorrect reuse.
- **Concurrency**: shared mutable state needs synchronization.
- **Coupling**: anything can call it from anywhere.

Better patterns (C# 15 era):

- **Instance services** registered via DI.
- **Static pure helpers** (no I/O, no global state).
- **`TimeProvider`** for time dependencies (instead of `DateTime.Now` sprinkled everywhere).
- **`Random.Shared`** for lightweight randomness (still be careful in tests; inject an RNG if determinism matters).

**Extension methods**

Extension methods are static methods with instance syntax. Use them for:

- Adding *non-invasive* helpers on types you don’t own (e.g., `IEnumerable<T>`).
- Providing fluent utilities that do not need access to internals.

Be careful:

- Extension methods can reduce discoverability of “real ownership”.
- They can introduce ambiguity (see section [5.1](<../5. Overload resolution and overloading/5.1. Method overloading rules ambiguity API design.md>)).

### 3. **Performance**

**Inlining and call overhead**

Static methods are often trivially inlineable because there is no virtual dispatch. This can help in hot paths, but:

- Inlining is **not guaranteed**; the JIT decides.
- Design first for correctness and clarity; optimize with measurements (see section [1.1](<../1. Method fundamentals/1.1. Understanding methods signature body invocation.md>) for performance framing).

**Hidden global state is the real performance risk**

The biggest real-world performance problems from “static” come from:

- **Contention**: locks around shared mutable state.
- **Cache stampedes**: naive static caches under load.
- **Memory growth**: static collections that never evict.

Performance note:

- Prefer `ConcurrentDictionary` only when you truly need shared caches, and add explicit bounds/eviction where appropriate. Unbounded caches are memory leaks by design.

**Thread-safety**

- Pure static methods are naturally thread-safe.
- Static methods that touch static mutable state are **not** thread-safe unless you make them so (and even then, consider whether you should).

Good to know:

- Static does not mean “faster”; it means “no instance receiver”. The speed difference usually comes from avoided virtual dispatch or reduced allocations—not from the `static` keyword itself.
