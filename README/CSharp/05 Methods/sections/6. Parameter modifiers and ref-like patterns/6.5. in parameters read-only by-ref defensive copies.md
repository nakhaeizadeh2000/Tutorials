## 6.5. `in` parameters: read-only by-ref and the “defensive copy” story

1. **Intent** (read-only reference to caller data; useful for large structs)
2. **Reality** (`in` can still create temporaries/defensive copies in some cases—measure in hot paths)
3. **Guidance** (prefer `readonly struct` first; use `in` selectively where it actually helps)

`in` is a *promise* of read-only access, but it is not a magic “always faster” keyword. Used well, it avoids copying large value types. Used poorly, it can introduce hidden temporaries and reduce clarity.

---

### 1. **Intent**

**Definition**

An `in` parameter is passed **by reference**, but treated as **read-only** inside the method:

- The callee cannot assign to the parameter variable.
- The caller passes an initialized variable/expression (similar to `ref` in that sense).

Conceptually:

- `T value` (by value): copy `T`
- `in T value` (by read-only ref): pass address of `T` (no copy), but disallow writes via that alias

**When it helps**

- Large structs (e.g., `decimal`, `Guid`, custom structs with many fields)
- Tight loops where copying the struct becomes measurable
- APIs where you want to signal “I will not mutate your value”

Note: For small structs (like `int`, `long`, `DateTime`), the difference is usually noise; don’t make signatures harder for no gain.

---

### 2. **Reality**

**The “defensive copy” story**

Even though `in` *sounds* like “no copies”, the compiler/JIT may still create copies in some situations to preserve read-only semantics and enable safe code generation.

Common triggers (conceptually):

- Passing **non-variables** (temporaries) can force a temporary storage location.
- Accessing non-`readonly` instance members on a `readonly` receiver can force a copy of the struct to avoid mutating the original.

This is why `readonly struct` and `readonly` members matter: they reduce or eliminate defensive copies when interacting with `in` values.

**Example: `readonly` members reduce copies**

```csharp
public struct Point // not readonly
{
    public int X;
    public int Y;

    public int ManhattanDistance() => Math.Abs(X) + Math.Abs(Y);
}

public static class Example
{
    public static int Distance(in Point p)
        => p.ManhattanDistance(); // may cause a defensive copy in some cases
}
```

Better:

```csharp
public readonly struct Point
{
    public int X { get; }
    public int Y { get; }
    public Point(int x, int y) => (X, Y) = (x, y);
    public int ManhattanDistance() => Math.Abs(X) + Math.Abs(Y);
}
```

Performance note:

- If `in` is used for performance, you must **measure** in context (BenchmarkDotNet is the typical tool). The JIT is smart, but the best strategy depends on call frequency, struct size, and surrounding code.

---

### 3. **Guidance**

**Prefer design-first improvements**

Before adding `in` everywhere, consider:

- Make the struct a `readonly struct` when appropriate.
- Keep methods on structs `readonly` (or naturally readonly via `readonly struct`) so you don’t cause defensive copies.
- Prefer clear APIs; only add ref-like modifiers where you can justify them.

**API design guidance**

- For public libraries, don’t add `in` just because it exists—`in` changes overload sets and can complicate overload resolution (see section `5.1`).
- For internal/high-performance code, `in` can be a useful knob—especially when combined with `ReadOnlySpan<T>` patterns (see section `2.1`).

Good to know:

- `in` does not make a referenced *object* immutable. If `T` is a reference type, `in T` just makes the **reference** read-only (you can’t reassign it), but the object can still be mutated.
