## 6.2. `ref` parameters: when mutation of the caller’s variable is intended

1. **Meaning** (callee can reassign the caller’s variable; caller must pass an initialized variable)
2. **Good uses** (performance-sensitive code with large structs; low-level algorithms; Try-pattern optimizations)
3. **Risks** (aliasing, surprising side effects, harder reasoning/testing; avoid in “regular” business code)

`ref` exists for two main reasons: **correctness** (you truly want to mutate/reassign the caller’s variable) and **performance** (avoid copying large value types). It is powerful and therefore easy to misuse.

---

### 1. **Meaning**

**What `ref` means**

When a parameter is `ref`, the callee receives an *alias* to the caller’s variable storage:

- The callee can **read** it.
- The callee can **write** it.
- The callee can **reassign** it (for value types: overwrite the value; for references: change what the variable points to).

**Call-site rules**

- The caller must pass a **definitely assigned** variable (initialized).
- The call site must use the `ref` keyword too: `M(ref x)`.

**Important distinction**

- `ref` changes the **variable** itself.
- Passing a reference type *without* `ref` still allows mutating the **object** (because the reference is copied by value). See section [6.1](<./6.1. Parameter modifiers default pass-by-value vs pass-by-reference.md>) for the full mental model.

**Example: reassigning the caller’s reference**

```csharp
public sealed class Box
{
    public int Value;
}

public static class Demo
{
    public static void EnsureBox(ref Box? box)
        => box ??= new Box();
}
```

Usage:

```csharp
Box? b = null;
Demo.EnsureBox(ref b);
// b is now non-null
```

Note: This is different from `EnsureBox(Box box)`; without `ref`, you cannot change the caller’s variable to point at a new object.

---

### 2. **Good uses**

**A) Avoid copying large structs (measured hot paths)**

For large `struct`s (e.g., many fields, vector/matrix types), copying can be expensive. `ref` can avoid that—*but only if* you’ve measured that copying is a real bottleneck.

Modern guidance:

- Prefer designing large value types as `readonly struct` first.
- Consider `in` (read-only by-ref) when you do not intend to mutate (see [6.5](<./6.5. in parameters read-only by-ref defensive copies.md>)).
- Use `ref` only when you **intend to mutate** or must pass by-ref to a low-level API.

**B) Low-level algorithms that naturally operate “in-place”**

Sorting, partitioning, swapping, and tight loops over spans can naturally use `ref` for clarity and performance.

Example: ref swap for a span element

```csharp
using System;

public static class SpanAlgorithms
{
    public static void Swap<T>(Span<T> span, int i, int j)
    {
        ref T a = ref span[i];
        ref T b = ref span[j];
        (a, b) = (b, a);
    }
}
```

**C) Interop / APIs that require `ref`**

Some APIs (especially low-level, interop, and certain performance primitives) require by-ref parameters. In that case, `ref` is not optional.

---

### 3. **Risks**

**Aliasing and “action at a distance”**

Two `ref` parameters (or a `ref` plus a normal parameter) can refer to the **same** storage. That makes reasoning harder and can create subtle bugs.

```csharp
public static void IncrementBoth(ref int a, ref int b)
{
    a++;
    b++;
}

int x = 0;
IncrementBoth(ref x, ref x); // x becomes 2 (surprising to many readers)
```

Mentor rule:

- Design `ref` APIs to make aliasing *unlikely*, and document whether aliasing is allowed.

**Harder testing and maintainability**

- `ref` makes call sites noisier.
- It increases coupling (callers must have variables, not expressions).
- It can prevent refactoring because the by-ref requirement leaks into many layers.

**Thread-safety**

- `ref` is not inherently thread-unsafe, but it makes shared mutation easier to do accidentally.
- Avoid exposing `ref` APIs across threads unless you have a very clear ownership model and synchronization.

**Avoid in general business/domain APIs**

If your motivation is “I want to return multiple values” or “I want mutation”, prefer:

- Returning a new value/object (immutability-friendly)
- Returning a tuple/record for multi-values (app code)
- `TryX(out ...)` for parsing-style APIs (see [6.3](<./6.3. out parameters multiple returns Try patterns.md>) / [6.4](<./6.4. out declaration modern call-site ergonomics.md>))
