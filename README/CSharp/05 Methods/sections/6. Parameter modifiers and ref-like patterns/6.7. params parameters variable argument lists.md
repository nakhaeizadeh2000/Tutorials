## 6.7. `params` parameters: variable argument lists without overload explosion

1. **Ergonomics** (nice call sites; reduces overload count)
2. **Allocation note** (`params` can allocate an array; avoid in hot loops or provide span-based alternatives)
3. **API guidance** (consider `ReadOnlySpan<T>` overloads for high-performance libraries)

`params` is a call-site feature that trades a very nice API shape for a potential hidden allocation. In production-quality APIs, the key is to **offer a zero-allocation path for hot code** without sacrificing ergonomics for normal use.

---

### 1. **Ergonomics**

**What `params` means**

When a parameter is declared as `params T[]`, callers can pass:

- An existing array: `LogMany(messagesArray)`
- Or a comma-separated list: `LogMany("a", "b", "c")`

The second form is just compiler sugar.

**When to use**

- When the natural mental model is “any number of items”
- When you want to avoid multiple overloads (`Log(x)`, `Log(x,y)`, `Log(x,y,z)`, …)

**When not to use**

- Hot paths where “implicit array creation” becomes measurable
- APIs where callers already have spans/collections and you want to avoid forcing materialization

**Example**

```csharp
using System;

public static class ConsoleLog
{
    public static void WriteLines(params string[] lines)
    {
        foreach (var line in lines)
        {
            Console.WriteLine(line);
        }
    }
}
```

Good to know: Passing an existing array is typically allocation-free; the allocation risk comes from the “expanded arguments” form.

---

### 2. **Allocation note**

**The hidden allocation**

`WriteLines("a", "b", "c")` usually causes the compiler to synthesize a new array: `new[] { "a", "b", "c" }`.

That implies:

- **An array allocation**
- **Extra writes** to fill it
- More pressure on the GC in tight loops

Performance note:

- This is often irrelevant in typical app code, but it *hurts* in high-frequency logging/formatting/metrics code.

**Avoiding allocations in hot paths**

Prefer a span-based overload for library APIs:

```csharp
using System;

public static class Metrics
{
    public static int Sum(ReadOnlySpan<int> values)
    {
        var sum = 0;
        foreach (var v in values)
            sum += v;
        return sum;
    }

    public static int Sum(params int[] values) => Sum(values);
}
```

This pattern:

- Keeps the **ergonomic** `params` entry point
- Provides a **zero-allocation** path for callers who already have stack/array-backed data

Note: `ReadOnlySpan<T>` is stack-only; you must not store it. Use it for “compute now” APIs.

---

### 3. **API guidance**

**Interacts with overload resolution**

`params` participates in overload resolution and can create surprising choices/ambiguities when combined with:

- Other overloads
- Optional parameters
- `null` / default literals

See section `5.1` for the deep rules and traps.

**Design rules (mentor-grade)**

- Keep `params` overload sets **small** and behavior-consistent.
- If the method is public and performance-sensitive, consider a **span overload** (as shown).
- Avoid `params object[]` for “logging-style” APIs in hot code; it boxes value types and allocates arrays. Prefer structured logging patterns or generic overloads.

---

### 4. **C# 13+: `params` collections (not just arrays)**

**What changed**

- `params` can target **recognized collection types**, not only `T[]`.
- Common high-performance shapes include `params ReadOnlySpan<T>` / `params Span<T>` (per your SDK/language version), reducing the classic “compiler must allocate a `new[]` for expanded arguments” story—*when the overload you call is span/collection-based*.

**Mentor guidance**

- **Libraries**: offer **span** / **collection** `params` overloads for hot APIs; keep `params T[]` for convenience if needed.
- **Apps**: prefer passing an existing buffer (`ReadOnlySpan<T>`) when you already have data—avoid expanded `params` in tight loops.
- **Interop with overload resolution** (C# 13): optional attributes like **overload resolution priority** exist for advanced library scenarios—use rarely and document.
