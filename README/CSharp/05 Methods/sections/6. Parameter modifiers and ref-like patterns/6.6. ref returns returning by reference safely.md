## 6.6. Ref returns: returning by reference safely

1. **Use case** (indexers and high-performance APIs where you want to mutate an element without copying)
2. **Safety rules** (never return refs to locals/temporaries; understand ref escape rules)
3. **Design** (keep ref-returning APIs low-level and well-documented; prefer normal returns for general code)

Ref returns and `ref` locals let you *avoid copying* and *mutate data in-place* without going through setters or copying large structs. They’re powerful and easy to misuse. Treat them as **low-level tools** you reach for only when you can state a clear performance goal and enforce safety rules.

---

### 1. **Use case**

**What a ref return is**

A `ref` return returns an **alias** to an existing storage location, not a copy of a value. The caller can store that alias in a `ref` local and mutate the underlying storage directly.

Common legitimate uses:

- **Indexers over large structs** (avoid copying).
- **Tight loops** updating elements in arrays/spans.
- **Low-level libraries** (parsers, numeric kernels) where copies are measurable.

**Example: mutate an element without copying**

```csharp
using System;

public sealed class IntTable
{
    private readonly int[] _data;

    public IntTable(int size)
    {
        if (size < 0) throw new ArgumentOutOfRangeException(nameof(size));
        _data = new int[size];
    }

    public ref int this[int index]
    {
        get
        {
            if ((uint)index >= (uint)_data.Length) // unsigned trick avoids two comparisons
                throw new ArgumentOutOfRangeException(nameof(index));
            return ref _data[index];
        }
    }
}

public static class Demo
{
    public static void Main()
    {
        var t = new IntTable(3);
        t[1] = 10;                // works because indexer returns ref
        ref var cell = ref t[1];  // alias the same storage
        cell += 5;
        Console.WriteLine(t[1]);  // 15
    }
}
```

Performance note:

- This pattern can eliminate copies and setter overhead in hot paths. In business code, the readability cost often outweighs the gain—measure first.

---

### 2. **Safety rules**

**The rule you must internalize**

- A `ref` return must refer to a storage location that will **still be valid after the method returns**.

You must **never** return a `ref` to:

- A local variable
- A temporary value
- A `stackalloc` buffer local to the method
- A field of a temporary (`Get().Field`) where `Get()` returns a temporary

The compiler enforces many of these through *ref escape analysis* (it will reject invalid patterns), but don’t rely on “the compiler saved me” as your design strategy.

**Thread-safety caveat**

Returning `ref` into shared mutable storage (arrays, pooled buffers, shared structs) can create data races. If multiple threads might access it:

- Don’t expose `ref` at all, or
- Provide explicit synchronization around mutation, or
- Confine the data to a single thread / single owner.

Good to know:

- You cannot store a `Span<T>` in a field; this prevents many lifetime bugs. Ref returns don’t have that guardrail: your API design must supply it.

---

### 3. **Design**

**Keep ref-returning APIs low-level**

Mentor guidance:

- Prefer “normal” methods and properties for general consumption.
- If you expose ref returns publicly, document:
  - aliasing semantics (“mutating the returned ref mutates the container”)
  - thread-safety expectations
  - lifetime expectations

**Prefer safe alternatives when possible**

- Use `Span<T>`/`ReadOnlySpan<T>` for high-performance *call-site* code that naturally confines lifetime (see [2.1](<../2. Locals parameters and this/2.1. Local variables and parameters scope lifetime definite assignment.md>) for lifetime/capture and [6.7](<./6.7. params parameters variable argument lists.md>) for span-based alternatives).
- Use methods like `Get`/`Set` or `TryGet`/`TrySet` when invariants must be enforced.

Note:

- A ref return can bypass invariants if it exposes internal storage directly. If your type must preserve invariants, ref returns should be limited to internal/private APIs or return refs only to “raw data” whose mutation is allowed.
