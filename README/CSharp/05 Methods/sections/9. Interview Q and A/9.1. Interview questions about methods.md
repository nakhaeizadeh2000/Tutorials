### 1. **Explain pass-by-value vs pass-by-reference**

**What a strong answer includes**

- In C#, **arguments are passed by value by default**.
  - For **value types** (`struct`): the *value* is copied.
  - For **reference types** (`class`): the *reference* is copied (so both variables point to the same object).
- “Pass-by-reference” in C# means using **`ref`/`out`/`in`**, which pass a *managed reference* to the caller’s variable.
- Distinguish:
  - **Mutating the object** (possible when a reference points to a mutable object)
  - vs **reassigning the parameter variable** (does not affect caller unless `ref`/`out`)

See the full treatment in:

- [6.1](<../6. Parameter modifiers and ref-like patterns/6.1. Parameter modifiers default pass-by-value vs pass-by-reference.md>) for the default mental model and correctness pitfalls.
- [4.1](<../4. Passing objects and arguments/4.1. Object references as arguments aliasing mutation defensive design.md>) for aliasing/mutation/ownership design consequences.

**Quick “gotcha” follow-up**

- “What happens if you pass a `List<T>` to a method?”  
  You pass the reference by value; mutations of the list contents are visible to the caller, but reassigning the parameter isn’t.

### 2. **Explain `ref`, `out`, and `in`**

**What a strong answer includes**

- **`ref`**: caller variable must be definitely assigned; callee can read and write it (including reassign).
- **`out`**: caller variable need not be assigned; callee must assign before returning; common in **Try-pattern** APIs.
- **`in`**: read-only by-ref intent; useful for large structs, but can still cause **defensive copies** in some scenarios.

**Mentor-level nuance interviewers like**

- Use `ref`/`in`/`out` **selectively**. In typical business code, clarity and API stability dominate; in high-performance code, measure and then use ref-like features where they demonstrably help.

### 3. **Explain overload resolution**

**What a strong answer includes**

- Overload resolution is **compile-time**: based on *static types* at the call site, not runtime types.
- The compiler chooses the “best” candidate considering:
  - identity/implicit conversions (numeric conversions are a classic trap)
  - generic type inference
  - `params` and optional parameters
  - lambdas/method groups conversion rules
- Common ambiguity sources: `null`, numeric literals, lambdas, method groups, `default`, optional parameters, `params`.

See the full treatment in:

- [5.1](<../5. Overload resolution and overloading/5.1. Method overloading rules ambiguity API design.md>) (this is the canonical deep section).

**Quick “gotcha” follow-up**

- “Why did renaming a parameter break call sites?”  
  Because named arguments bind to parameter names at compile time (see [4.3](<../4. Passing objects and arguments/4.3. Named arguments readability maintainability.md>)).
