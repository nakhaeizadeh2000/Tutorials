## 7.2. Static local functions: opt out of capturing by design

1. **Guarantee** (cannot capture locals/`this`; prevents accidental closure allocations)
2. **When to use** (hot paths, callbacks, or any helper where capturing would be a bug)
3. **Rule of thumb** (default to `static` local functions when you don’t need captures)

`static` local functions are one of the cleanest ways to make “no capture” a **compile-time guarantee**. They’re a readability tool (your future self immediately knows there is no hidden state) and, in some cases, a performance tool (they prevent closure allocations).

---

### 1. **Guarantee**

**What the `static` keyword means on a local function**

A **static local function** is a local function that:

- Cannot capture **any** locals from the enclosing scope
- Cannot capture `this`
- Cannot use instance members unless you explicitly pass an instance in

This is different from “I promise I won’t capture” — the compiler enforces it.

**What capture means**

Capturing happens when a lambda/local function refers to a variable from the enclosing method. The compiler may then synthesize a “closure” object to hold that variable (and any others it needs), and that object lives on the heap.

See section [7.1](<./7.1. Local functions structure scoping avoiding allocations.md>) for the deep comparison of lambdas vs local functions and what allocates when.

**Example: compiler-enforced no-capture**

```csharp
using System;

public static class Demo
{
    public static int CountDigits(int value)
    {
        var v = Math.Abs(value);

        // Local helper that must not capture anything.
        static int CountDigitsCore(int x)
        {
            if (x == 0) return 1;

            var count = 0;
            while (x != 0)
            {
                x /= 10;
                count++;
            }

            return count;
        }

        return CountDigitsCore(v);
    }
}
```

Note:

- This local function is `static`, so it cannot accidentally capture `v` or `this`.
- The state it needs is explicit (`x`).

---

### 2. **When to use**

**Hot paths / tight loops**

If you’re in a performance-sensitive loop and you need a small helper:

- Use a local function for **structure**
- Make it `static` when capture would be accidental or harmful

**Callbacks and APIs that accept delegates**

When you pass a lambda to APIs like `Array.Sort`, LINQ, timers, event handlers, etc., capturing can:

- Allocate a closure
- Extend lifetimes of large objects (captured references)
- Accidentally keep `this` alive (memory leak patterns)

If you can express the callback without capture, consider:

- **Non-capturing lambda** (often allocation-free; still a delegate)
- **`static` lambda** (compile-time “no capture” guarantee)
- **Static local function** + explicit state parameter(s)

Good to know:

- For delegates, `static` local functions can be converted to delegates similarly to static methods. Whether a delegate instance allocates depends on caching and runtime behavior; the key win is preventing closure creation.

**Correctness: avoiding hidden shared state**

In multithreaded code, captures can accidentally close over variables that change (e.g., loop variables) or shared mutable objects. Making state explicit reduces these bugs.

---

### 3. **Rule of thumb**

**Default to `static` when you don’t need captures**

- If the helper uses only its parameters, make it `static`.
- If it needs something from the outer scope, pass it explicitly.

**Prefer explicit state passing over capture**

This is often more readable and testable:

- Captured state is “invisible input”.
- Explicit parameters show dependencies at the call site.

**Modern alternative: `static` lambdas**

If you’re using a lambda rather than a local function, you can also write `static` lambdas:

```csharp
using System;

public static class LambdaDemo
{
    public static int[] GetSquares(ReadOnlySpan<int> values)
    {
        // Example only; array allocation is intentional as output storage.
        var result = new int[values.Length];

        for (var i = 0; i < values.Length; i++)
        {
            // static lambda: cannot capture anything.
            result[i] = ((static int x) => x * x)(values[i]);
        }

        return result;
    }
}
```

Note: This is mostly useful when passing callbacks to other APIs. For plain computation, a normal local helper is typically clearer than an immediately-invoked lambda.
