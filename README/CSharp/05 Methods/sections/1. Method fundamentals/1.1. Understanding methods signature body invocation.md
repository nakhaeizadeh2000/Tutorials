## 1.1. Understanding methods: signature, body, and invocation

1. **Method signature** (name + parameters + return type; generic methods; accessibility and modifiers)
2. **Call semantics** (compile-time overload resolution vs runtime dispatch; extension methods as syntax)
3. **Performance framing** (inlining, virtual dispatch, allocations from lambdas/closures, and exception costs)

Below is the “real” mental model of methods in modern C# (C# 15, .NET 9+): how a method is *identified*, how it is *invoked*, and what costs you should assume until proven otherwise.

---

### 1. **Method signature**

**What it is**

In C#, the *signature* is what makes one method distinct from another for overload purposes. At a high level, you can think of it as:

- **Name**
- **Type parameters** (for generic methods)
- **Parameter list** (number, types, order, and modifiers like `ref`, `out`, `in`, `params`)

The **return type is *not* part of the overload signature**. You cannot overload solely by changing return type.

**What belongs to “method identity” beyond signature**

Other modifiers are not part of overload resolution, but they change meaning and API shape:

- **Accessibility**: `public`, `internal`, `protected`, `private`
- **Dispatch**: `static`, instance methods; `virtual`/`override`/`abstract`; `sealed override`
- **Safety/constraints**: `unsafe`, generic constraints (`where T : ...`)
- **Async**: `async` is not part of signature; it changes how the body is compiled and how exceptions/cancellation flow

**Generic methods**

Generic methods are part of modern “zero-allocation” and “zero-copy” API design:

- Prefer **generic methods** when the operation is truly type-agnostic and benefits from compile-time specialization.
- Use **constraints** to express requirements precisely (e.g., `where T : unmanaged`, `where T : notnull`, `where T : IComparable<T>`).
- Avoid “fake generic” methods where `T` is unused or only used for casting; that usually indicates a design smell.

**Modern best practices for signatures**

- **Prefer intention-revealing parameter names** (call sites matter as much as the method body).
- **Avoid `bool` flag parameters** in public APIs. Prefer enums, options records, or separate methods.
- **Prefer `CancellationToken` as the last parameter** in async APIs.
- **Prefer `ReadOnlySpan<T>` / `Span<T>`** for high-performance parsing/transform APIs, but only when you can keep lifetimes simple and avoid storing spans (spans are stack-only ref structs).

**Common mistakes**

- **Overloading by return type** (not allowed).
- **Accidentally creating overload ambiguity** with `null`, numeric literals, lambdas, optional parameters, and `params`. (See section `5.1` for the full treatment.)
- **Exposing `ref`/`out` in “regular” business APIs**: makes call sites harder to reason about and increases coupling.

**Example: signature choices that age well**

```csharp
using System;

public static class PathHelpers
{
    // Clear intent: "Try" communicates failure without exceptions.
    public static bool TryGetFileNameWithoutExtension(
        ReadOnlySpan<char> path,
        out ReadOnlySpan<char> fileNameWithoutExtension)
    {
        // Minimal example (not a full path implementation).
        var lastSlash = path.LastIndexOfAny('/', '\\');
        var name = lastSlash >= 0 ? path[(lastSlash + 1)..] : path;
        var dot = name.LastIndexOf('.');
        fileNameWithoutExtension = dot > 0 ? name[..dot] : name;
        return name.Length != 0;
    }
}
```

Note: The signature signals **no allocations** (span), **no exceptions for expected failure** (`Try...` + `out`), and **scoped output**.

### 2. **Call semantics**

**There are two distinct “choices” at a call site**

1) **Compile-time overload resolution**

The compiler picks *which method to call* based on the static types it sees. This includes:

- Implicit numeric conversions
- Generic type inference
- Method group conversions
- Lambda conversion to delegate/expression
- `params` expansion and optional parameter substitution
- Better-function-member rules

If you ever wonder “why did it call *that* overload?”, it’s almost always because of these rules. (Deep dive is in section `5.1`.)

2) **Runtime dispatch**

Once an overload is chosen, *runtime dispatch* decides **which implementation runs**:

- **Non-virtual instance methods**: direct call to a known target
- **Virtual calls (`virtual`/`override`/interface calls)**: resolved at runtime (usually through a vtable/dispatch stub)
- **`sealed` overrides**: enables more devirtualization opportunities

**Extension methods are syntax, not magic**

Extension methods are **static methods** that the compiler allows you to call using instance-method syntax. Resolution rules:

- Real instance methods win over extension methods.
- Extension methods must be in scope (via `using`).
- They participate in overload resolution like other candidates.

**Modern guidance**

- Prefer **instance methods** for behaviors that logically depend on an instance’s invariants.
- Prefer **static methods** for pure/stateless transforms (see section `3.1`).
- Be cautious with **overly clever extension methods** in shared namespaces; they can create “action at a distance” and ambiguity.

**Example: overload resolution vs runtime dispatch**

```csharp
using System;

public interface IFormatter
{
    string Format(int value);
}

public sealed class HexFormatter : IFormatter
{
    public string Format(int value) => value.ToString("X");
}

public static class Demo
{
    public static string FormatValue(IFormatter formatter, int value) // compile-time picks this method
        => formatter.Format(value); // runtime dispatch through interface

    public static string FormatValue(HexFormatter formatter, int value) // different overload
        => formatter.Format(value); // non-virtual call (sealed type)
}
```

Good to know:

- The **chosen overload** depends on the *static type* of the argument at the call site.
- The **implementation** for `formatter.Format` depends on runtime type when calling via interface/virtual dispatch.

### 3. **Performance framing**

The goal is not “micro-optimizing every method”, but understanding the *big levers* so you don’t accidentally ship expensive patterns.

**Inlining**

- The JIT may inline small methods, which can be a huge win (eliminates call overhead and enables further optimization).
- Inlining is **not guaranteed** and varies by runtime/JIT tiering.
- Keeping hot methods small and predictable often helps the JIT.

Performance note:

- Avoid patterns that prevent inlining in hot paths (very large methods, heavy exception handling paths interleaved, certain generic patterns). Measure before assuming.

**Virtual/interface dispatch**

- Virtual/interface calls add dispatch overhead and can block some optimizations (like constant propagation across the call).
- Often negligible in business code; can matter in tight loops.
- If it matters, consider `sealed`, avoid unnecessary interface calls in inner loops, or restructure (but keep design clean).

**Allocations from lambdas/closures**

- Capturing variables in lambdas/local functions can allocate a **closure object** (heap allocation) and extend lifetimes of captured objects.
- Non-capturing lambdas often compile to cached delegates and can be allocation-free.

See also: `7.1` and `7.2` for the “local functions vs lambdas” and “static local functions” deep dive.

**Exception costs**

- Throwing exceptions is expensive: stack unwinding, metadata, stack traces, and often poor branch predictability.
- **Do not use exceptions for expected control flow** (e.g., parsing user input).
- Prefer `Try...` methods (e.g., `int.TryParse`) or result types/`bool` returns.

**Async vs sync**

- `async` methods can allocate state machines and captured continuations depending on how they’re written and how often they complete synchronously.
- Don’t make everything async “by default”. Use async for I/O-bound work; keep CPU-bound work synchronous and consider parallelism separately.

Good to know:

- Avoid `Task.Run` inside server request handlers unless you are intentionally offloading CPU-bound work and understand thread pool implications.
- Prefer `ValueTask` only for performance-critical APIs where it reduces allocations and you can enforce correct consumption semantics; otherwise stick to `Task`.
