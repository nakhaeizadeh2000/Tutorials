## 1.2. Encapsulation with methods: invariants live at method boundaries

1. **Encapsulation** (state stays private; methods/properties enforce valid transitions)
2. **Design rules** (small public surface; intention-revealing method names; avoid “do everything” methods)
3. **Correctness + perf** (validate once at boundaries; avoid repeated expensive checks inside hot loops)

Encapsulation is not “OOP ceremony”; it is how you **make illegal states unrepresentable**, keep invariants true over time, and create APIs that remain safe as code evolves.

---

### 1. **Encapsulation**

**Definition**

Encapsulation means:

- **State is hidden** (usually `private` fields).
- Access happens through **methods/properties** that **enforce invariants** (rules that must always hold).
- The type controls **valid transitions** between states.

Encapsulation is a *correctness* tool first, and a maintainability tool second. Performance benefits often fall out naturally: fewer places to validate, fewer defensive copies, less “paranoia code” sprinkled everywhere.

**When to use**

- Always, for any type with invariants (most domain types).
- Especially when state updates must be coordinated (e.g., `Balance` + `LastUpdated`, cache + version, counters + timestamps).

**Trade-offs**

- More code up front (methods instead of public fields), but far fewer bugs later.
- Slightly more indirection, but with much clearer ownership and easier refactoring.

**Common mistakes**

- **Public setters everywhere** (“anemic” types) that allow invalid states.
- **Leaking internals** by returning mutable collections directly (`List<T>`, `Dictionary<TKey,TValue>`), enabling external mutation that bypasses invariants.
- **Partially-initialized objects** escaping constructors (publishing `this` too early via events/callbacks). See section [2.2](<../2. Locals parameters and this/2.2. this keyword instance context capturing pitfalls.md>) for the full treatment of capturing/leaking `this`.

**Example: invariants enforced at the boundary**

```csharp
using System;

public sealed class BankAccount
{
    private decimal _balance;

    public BankAccount(decimal openingBalance)
    {
        if (openingBalance < 0) throw new ArgumentOutOfRangeException(nameof(openingBalance));
        _balance = openingBalance;
    }

    public decimal Balance => _balance;

    public void Deposit(decimal amount)
    {
        if (amount <= 0) throw new ArgumentOutOfRangeException(nameof(amount));
        _balance += amount;
    }

    public bool TryWithdraw(decimal amount)
    {
        if (amount <= 0) return false;
        if (amount > _balance) return false;

        _balance -= amount;
        return true;
    }
}
```

Note:

- The invariant “balance is never negative” is preserved by *design*.
- Expected failures (`TryWithdraw`) don’t throw exceptions.
- The type owns the only mutation path.

---

### 2. **Design rules**

**Small public surface**

- Prefer `private`/`internal` by default; make members `public` only when you must.
- Public APIs are commitments. Once shipped, changing them becomes costly (compat and consumer code).

**Intention-revealing names**

Method names should encode:

- **Action** (`Reserve`, `Commit`, `Cancel`, `TryParse`, `Normalize`)
- **Side effects** (avoid surprising mutation)
- **Failure mode** (`TryX` returns `bool`; `GetXOrThrow` throws; `GetXOrDefault` is explicit)

Mentor rule:

- If you need to add a comment like “this mutates the argument” or “this can fail”, your signature/name should probably make it explicit.

**Avoid “do everything” methods**

Long methods tend to:

- Mix validation, I/O, domain logic, mapping, logging, and caching.
- Become hard to test and reason about.
- Hide performance problems (allocations, repeated work) inside a “ball of mud”.

Instead:

- Keep a **thin orchestration method** at the boundary.
- Move cohesive logic into **private helpers** or separate types.
- Use **local functions** for tiny helpers that shouldn’t leak outside the method (see section [7.1](<../7. Local functions and recursion/7.1. Local functions structure scoping avoiding allocations.md>)).

**SOLID connections (what matters for methods)**

- **S (Single Responsibility)**: one reason to change per method.
- **O (Open/Closed)**: add behavior via new types/overrides rather than editing a giant switch (when appropriate).
- **L/I/D**: keep abstractions minimal; don’t force callers to depend on methods they don’t need.

---

### 3. **Correctness + perf**

**Validate once at boundaries**

Boundaries are:

- Public methods
- Input parsing / deserialization
- External API edges (HTTP handlers, message consumers)
- Constructors / factory methods

If you validate at boundaries, internal helpers can assume valid input—making them smaller and faster.

**Avoid repeated expensive checks in hot paths**

Example pattern:

- Validate the whole request once.
- Precompute once.
- Then run the tight loop with minimal branching and no allocations.

**Exceptions are not control flow**

- Use exceptions for *unexpected* conditions (bugs, contract violations, system failures).
- For expected outcomes (not found, invalid input), prefer `Try...` or explicit result types.

Performance note:

- Throwing is expensive (stack capture, unwinding). Even if it “works”, it’s a scalability killer under load.

**Returning collections safely**

Prefer:

- `IReadOnlyList<T>` / `IReadOnlyDictionary<TKey,TValue>` for “read-only view”
- `ImmutableArray<T>` / `ImmutableDictionary<,>` when you need structural immutability
- `ReadOnlySpan<T>` for temporary high-performance views (no storage; stack-only)

Avoid:

- Returning `List<T>` directly if callers should not mutate it.

Good to know:

- A “read-only interface” is only a *compile-time* restriction. If you return the same underlying mutable collection instance, it can still be mutated if someone gets a reference. True immutability requires immutable data structures or copying.
