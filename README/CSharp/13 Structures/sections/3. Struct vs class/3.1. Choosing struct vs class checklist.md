## 3.1. Choosing `struct` vs `class`: a decision checklist

1. **Semantics first** (identity vs value; aliasing risks; mutation expectations)
2. **Performance second** (copy costs vs allocation/GC; caching and locality; avoid “struct for speed” cargo culting)
3. **Versioning and API design** (public shape is a contract; changing a struct’s size/copy behavior can be a breaking change in performance-sensitive code)

---

### 1) **Semantics first** (identity vs value; aliasing risks; mutation expectations)

**Definition.** The **primary** decision is semantic, not performance:

- **Choose `class`** when the type has **identity** (“this specific instance”), is **shared** (multiple owners/aliases), or is **meaningfully mutable over time**.
- **Choose `struct`** when the type represents a **value** (“these bits/fields”), is naturally **copied**, and **equality** is usually value-based.

**Mental model (mentor framing)**
- If you expect callers to ask “*which* instance is this?” (object identity), you’re in `class` territory.
- If you expect callers to ask “*what value* is this?” you’re in `struct` territory.

**Aliasing risk**
- With classes, aliasing is normal and often desired (shared mutable state, caching, object graphs).
- With structs, aliasing is not the default; accidental aliasing usually only appears via **boxing**, **ref returns**, or **unsafe** code.

**Mutation expectations**
- If mutation is part of the domain (e.g., “Customer accumulates orders over time”), that’s often a `class`.
- If mutation would be surprising (“Money changed itself”), prefer **immutable** struct shapes (`readonly struct` / `readonly record struct`). See section `4.1`.

**Common mistakes**
- **Public mutable structs**: callers modify a copy and think they modified the original. This produces bugs that are hard to reason about. See section `5.2`.
- **Modeling entities as `record struct`**: `record struct` implies value equality. Entities typically need identity semantics, so prefer `class` (or an immutable ID struct + entity class).

**Good to know**
- It’s perfectly normal to have a **small immutable struct** as a key/ID (`OrderId`), and a **class** for the entity (`Order`) that uses it.

---

### 2) **Performance second** (copy costs vs allocation/GC; caching and locality; avoid “struct for speed” cargo culting)

**Core trade-off**
- **Structs** avoid per-instance allocation and can improve locality (especially in `T[]` / `List<T>`). But they can incur **copy costs** and **boxing**.
- **Classes** incur allocation and GC overhead, but passing references is cheap, mutation is straightforward, and size doesn’t amplify copy costs.

**Practical heuristics (good defaults)**
- Prefer a struct when it is:
  - **Small** (think “a few fields”), and
  - **Immutable**, and
  - Used in large counts (arrays/lists), and
  - Not commonly used through non-generic interfaces (to avoid boxing).
- Prefer a class when it is:
  - **Large** or frequently passed around, or
  - **Mutable and shared**, or
  - Has **lifecycle/ownership** (resources, events, caching), or
  - Part of an inheritance/polymorphism design.

**Performance pitfalls**
- **Copy amplification**: a large struct in a loop, `foreach`, LINQ, async state machine, or property access can create many hidden copies. Full treatment in section `3.2`.
- **Boxing**: structs used as `object`/non-generic interfaces allocate. Full treatment in section `3.3`.

**Performance note**
- “Struct avoids allocation” is only a win if you also avoid:
  - large copies,
  - boxing,
  - and incidental allocations elsewhere (formatting/parsing/logging).
  Measure with realistic workloads; the fastest design is often “small immutable structs + classes for big mutable graphs.”

---

### 3) **Versioning and API design** (public shape is a contract; changing a struct’s size/copy behavior can be a breaking change in performance-sensitive code)

**Why structs are more “brittle” as public API**
- Changing a struct’s fields changes:
  - **size** (copy cost),
  - **layout** (interop/serialization expectations),
  - equality/hashing semantics if auto-generated or field-based.
- Callers may have “worked fine” but now regress due to extra copying (a *performance breaking change*).

**Guidelines for public structs**
- **Keep them small and stable**; avoid “just add a field later” unless you own all consumers.
- Prefer **immutable** structs so semantics remain stable.
- Implement **`IEquatable<T>`** and stable `GetHashCode` rules (see section `1.2` for patterns).
- If you must evolve:
  - consider creating a **new type** rather than mutating the existing struct’s shape,
  - or add optional behavior via methods rather than fields.

**Interop note**
- If the type participates in interop, layout decisions (`StructLayout`, packing) become part of the contract. Keep that in a dedicated interop-focused section (not covered deeply here).
