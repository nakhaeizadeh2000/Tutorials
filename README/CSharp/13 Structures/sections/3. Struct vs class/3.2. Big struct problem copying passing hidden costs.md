## 3.2. The “big struct” problem: copying, passing, and hidden costs

1. **Copy amplification** (loops, foreach, LINQ, async state machines, and accidental temporaries)
2. **`in` parameters** (when they help; when they hurt by forcing copies/temporaries—measure)
3. **Guidance** (prefer small structs; if it’s big and mutable, a class may be the safer and faster *overall* design)

---

### 1) **Copy amplification** (loops, foreach, LINQ, async state machines, and accidental temporaries)

**Definition.** Copy amplification is when a struct is copied *more times than you intended*, because the language and libraries are designed around value semantics: *reading a value returns a copy*, *iteration variables are copies*, and *capturing a value captures a copy*.

#### Where the copies come from (high-signal list)
- **Collections**: `list[i]`, `foreach (var x in list)` (iteration variable is a copy).
- **LINQ**: query operators often create enumerators and move values around; large `T` means lots of copying.
- **Async/iterators**: state machines capture locals; large structs may be copied into the state machine (or spilled) and copied again when passed around.
- **Properties**: `someStruct.Property` can return a copy; calling instance members on temporaries can force defensive copies (see also section `4.1`).
- **“Nice” APIs**: returning a large struct by value from frequently-called methods can be surprisingly expensive.

#### A minimal example that “looks harmless” but copies a lot

```csharp
using System;
using System.Collections.Generic;

public struct Big // intentionally big for demonstration
{
    public long A, B, C, D, E, F, G, H;
}

public static class Demo
{
    public static void Main()
    {
        var list = new List<Big>(capacity: 1_000);
        for (var i = 0; i < 1_000; i++) list.Add(new Big { A = i });

        long sum = 0;
        foreach (var x in list) // x is a copy of each element
            sum += x.A;

        Console.WriteLine(sum);
    }
}
```

**Good to know.**
- This is not “C# being slow.” This is *your type size* interacting with *value semantics*. The fix is almost always **type design** or **API shape**, not micro-optimizing the loop.

#### Fix patterns (choose the safest one first)
- **Make the struct smaller** (best). If you can reduce fields or pack data differently, you reduce *every* copy everywhere.
- **Make it immutable** (`readonly struct`) to avoid defensive copies (section `4.1`)—this doesn’t eliminate value copies, but it prevents “copy to protect readonly receiver” cases.
- **Use a class** when the data is large and shared/long-lived. You trade per-instance allocation + indirection for avoiding repeated large copies.
- **Use ref-return/ref-enumeration** only in advanced scenarios where the API guarantees safety (low-level libraries; `Span<T>`-like patterns). This is often **not** appropriate for general application code because it can create lifetime hazards.

**Performance note.**
- Copying is mostly memory bandwidth. On modern CPUs, “copying 128 bytes 10 million times” can dominate runtime even though no allocation happens.
- If your performance issue disappears when you change `struct` → `class`, that’s a strong signal the type is too big or too copy-heavy for value semantics.

### 2) **`in` parameters** (when they help; when they hurt by forcing copies/temporaries—measure)

**Definition.** `in T` passes a value by **readonly reference**. It can avoid a by-value copy of large structs *at the call boundary*.

#### When `in` helps
- The struct is **large enough** that copying is meaningful.
- The method uses the parameter **read-only** and does not store it.
- The call sites already have a stable variable (not an expression/temporary) to pass by reference.

#### When `in` can hurt (counterintuitive but common)
- **Temporaries**: if you pass an expression, the compiler may create a temporary local to take its address, introducing a copy you didn’t expect.
- **Defensive copies**: inside the method, calling non-`readonly` instance members on an `in` parameter can force a defensive copy of the receiver. (Modern guidance: mark instance members `readonly` when they don’t mutate; see section `4.1`.)
- **Inhibits some JIT optimizations**: the JIT must respect aliasing rules for byref, which can reduce CSE/register allocation in tight loops.

#### Example: write members as `readonly` to play well with `in`

```csharp
using System;

public readonly struct Vector3
{
    public readonly float X, Y, Z;
    public Vector3(float x, float y, float z) => (X, Y, Z) = (x, y, z);

    // Marked readonly: safe on readonly receivers (including `in` parameters).
    public readonly float LengthSquared() => (X * X) + (Y * Y) + (Z * Z);
}

public static class Demo
{
    static float Len2(in Vector3 v) => v.LengthSquared();

    public static void Main()
    {
        var v = new Vector3(1, 2, 3);
        Console.WriteLine(Len2(in v));
    }
}
```

**Mentor rule.**
- Don’t blanket-apply `in`. Use it where profiling shows copying is a real cost.
- Prefer “make it small” or “make it a class” over sprinkling `in` everywhere.

### 3) **Guidance** (prefer small structs; if it’s big and mutable, a class may be the safer and faster *overall* design)

**A practical checklist**
- **Is the type conceptually a value?** If not, it’s probably a `class` (see `3.1`).
- **Is it small (roughly a handful of fields) and immutable?** Struct is a strong candidate.
- **Is it large and/or frequently passed around?** Consider a `class`, or redesign data layout.
- **Is it mutable and public?** Avoid: this is a bug factory (deep examples in `5.2`).
- **Does it implement interfaces heavily?** Watch for boxing (deep dive in `3.3`).

**Versioning note (public APIs).**
Changing a struct by adding a field changes its size and copy cost. Even if it’s “source compatible,” it can be a *performance breaking change* for consumers. Consider:
- keeping structs internal unless you can commit to their shape,
- or using a class if you anticipate evolution.
