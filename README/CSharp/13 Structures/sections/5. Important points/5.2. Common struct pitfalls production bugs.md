## 5.2. Common pitfalls that cause production bugs

1. **Mutable struct properties** (e.g., `list[i].X++` patterns and “mutating a copy” surprises)
2. **Foreach over structs** (iteration variable copies; mutation doesn’t mutate the underlying collection)
3. **Async and iterators** (capturing copies into state machines; unintended copies from closures)
4. **Interlocked/volatile misconceptions** (atomicity and tearing; when struct reads/writes are not atomic)

---

### 1) **Mutable struct properties** (e.g., `list[i].X++` patterns and “mutating a copy” surprises)

**The pitfall.** Many “property/indexer returns a struct” APIs return a **copy**. Mutating a field/property on that returned value mutates the copy, then the copy is discarded.

**Classic production bug patterns**
- `list[i].X++` where `list[i]` is a struct: you increment a temporary copy.
- `someStructProperty.Field = ...` where `someStructProperty` is a struct returned by value: you mutate a temporary.
- `dictionary[key].Count++` where the value is a struct: you mutate a copy of the value, not the stored value.

**Minimal example**

```csharp
using System;
using System.Collections.Generic;

public struct Counter
{
    public int Value;
}

public static class Demo
{
    public static void Main()
    {
        var list = new List<Counter> { new() { Value = 1 } };

        // Looks like "increment element 0", but list[0] returns a copy.
        var c = list[0];
        c.Value++;
        Console.WriteLine(list[0].Value); // 1

        // Correct: write the modified struct back.
        c = list[0];
        c.Value++;
        list[0] = c;
        Console.WriteLine(list[0].Value); // 2
    }
}
```

**How to prevent it (mentor guidance)**
- **Prefer immutable structs** for public APIs (`readonly struct` / `readonly record struct`). Deep reasoning in sections [4.1](<../4. Readonly structs/4.1. readonly struct guarantees and limits.md>) and [1.2](<../1. Structures fundamentals/1.2. Creating structures declarations members idiomatic shapes.md>).
- **Avoid exposing struct-valued properties with setters on nested members**. If you must expose a struct, expose it as an immutable snapshot or provide explicit “with”-style methods on the parent.
- If you need in-place mutation in a collection, use APIs that support it explicitly (often by switching the value to a class, or by using specialized structures in performance-critical code).

**Performance note**
- These bugs are not just correctness issues; they also create **extra copies** that inflate CPU and memory bandwidth usage (see section [3.2](<../3. Struct vs class/3.2. Big struct problem copying passing hidden costs.md>)).

### 2) **Foreach over structs** (iteration variable copies; mutation doesn’t mutate the underlying collection)

**The pitfall.** In `foreach`, the iteration variable is a **copy** of each element for value types. Mutating it does not mutate the underlying collection element.

**Example**

```csharp
using System;

public struct Point
{
    public int X;
    public int Y;
}

public static class Demo
{
    public static void Main()
    {
        var arr = new[] { new Point { X = 1, Y = 2 } };

        foreach (var p in arr)
        {
            // Mutates the loop variable copy only.
            // p.X++; // won't compile if p is foreach iteration variable in some contexts; even if you can mutate, it won't affect arr[0]
        }

        // Correct: use a for loop and assign back.
        for (var i = 0; i < arr.Length; i++)
        {
            var p = arr[i];
            p.X++;
            arr[i] = p;
        }

        Console.WriteLine(arr[0].X); // 2
    }
}
```

**Mentor guidance**
- If your intent is “iterate and mutate elements,” use `for` and assign back.
- If your intent is “iterate without copying,” keep the struct small or design APIs that expose ref iteration (advanced; usually belongs in library/low-level code).

**Performance note**
- `foreach` can trigger **copy amplification** for large structs. Full coverage is in section [3.2](<../3. Struct vs class/3.2. Big struct problem copying passing hidden costs.md>).

### 3) **Async and iterators** (capturing copies into state machines; unintended copies from closures)

**The pitfall.**
- `async` methods and iterators (`yield return`) are compiled into state machines. Struct locals/parameters can be **copied** into the state machine fields.
- Lambdas/closures can capture locals; captured variables can be **lifted** to the heap (and structs get copied into the closure object).

**Why this bites**
- You “mutate `this`” in a struct method and expect the caller’s value to change, but the method is executing on a **copy** (common when calling on readonly variables or via `in`).
- You pass a large struct into an `async` method, and it gets copied multiple times (hidden cost).

**Mentor guidance**
- Avoid designing mutable structs whose instance methods mutate `this`. Prefer `readonly struct` and pure methods returning new values.
- Keep hot-path structs small so incidental copies are cheap.
- If you must pass a larger struct, consider `in` *after measuring* and understanding temporary creation (see section [3.2](<../3. Struct vs class/3.2. Big struct problem copying passing hidden costs.md>)).

**See also**
- Copy amplification and `in` trade-offs: section [3.2](<../3. Struct vs class/3.2. Big struct problem copying passing hidden costs.md>).
- Defensive copies and readonly members: section [4.1](<../4. Readonly structs/4.1. readonly struct guarantees and limits.md>).

### 4) **Interlocked/volatile misconceptions** (atomicity and tearing; when struct reads/writes are not atomic)

**The pitfall.** Developers often assume “assigning a struct is atomic” or that `volatile` makes composite reads/writes safe. That’s not generally true.

**Key points**
- **Atomicity is not guaranteed** for arbitrary-sized structs. Reads/writes can be torn (partially updated) when multiple threads access the same location without synchronization.
- `volatile` applies to specific types/fields and ordering semantics; it does **not** make complex multi-field updates atomic.
- `Interlocked` APIs work on certain primitive sizes and references; they do not magically support arbitrary structs.

**Mentor guidance (thread-safety)**
- Treat shared mutable structs like shared mutable anything: use **locks**, **immutable snapshots**, or **message passing**.
- Prefer immutable structs (`readonly struct`) so sharing is naturally safe.
- If you need atomic updates, redesign to use `long`/`int` fields with `Interlocked` or use a class with a lock—don’t try to “atomically swap” large structs without a measured, correct design.

**Performance note**
- Locking is often cheaper than debugging data races. In hot paths, prefer immutability and reduce sharing to avoid contention.
