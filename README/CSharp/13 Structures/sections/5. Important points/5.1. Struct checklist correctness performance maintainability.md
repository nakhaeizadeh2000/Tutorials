## 5.1. Checklist: correctness, performance, and maintainability for structs

1. **Avoid mutable structs as public API** (mutation + copying leads to bugs that look impossible)
2. **Don’t use structs to “avoid allocations” by default** (copying/boxing can be worse; measure)
3. **Be explicit about equality and hashing** (`IEquatable<T>`; stable hash codes; never mutate dictionary keys)
4. **Avoid large structs** (keep them small; pass by `in` only when proven)
5. **Watch for boxing** (interfaces/object/logging; it can erase all perf wins)
6. **Make `default` behavior intentional** (either valid, or detectably “uninitialized”)

### 1) Avoid mutable structs as public API
**Rule**: If a struct is **public** (or crosses assembly boundaries), default to **immutable** (`readonly struct` / `readonly record struct`).

**Why mentors care**
- Copy semantics + mutation create bugs that look like “the runtime ignored my change.”
- Callers can’t tell when they’re mutating an alias vs a copy (indexers, foreach, LINQ, async/closures).

**Allowed exceptions**
- Internal, short-lived algorithmic structs where you control all call sites (e.g., math kernels).
- Stack-only `ref struct` helpers that never escape (see [4.2](<../4. Readonly structs/4.2. ref struct and stack-only types.md>)).

**Good to know**
- If you must expose mutation, consider a **class** (identity + aliasing are explicit) or a dedicated mutable builder type.

### 2) Don’t use structs to “avoid allocations” by default
**Rule**: Choose `struct` for **semantics**, then validate performance with profiling.

**Why**
- Structs can still allocate via **boxing** (interfaces/object, some formatting/logging).
- Large structs can burn CPU via copying more than a single allocation + GC would have.

**Performance note**
- Measure in realistic scenarios (throughput + latency + allocations). A microbenchmark that ignores GC and branch behavior can lie.

### 3) Be explicit about equality and hashing
**Rule**: If a struct participates in equality (comparisons, dictionary keys, sets), define it deliberately.

**Preferred patterns**
- For “data value objects”: `readonly record struct` (generated structural equality) *when correct for your domain*.
- For custom control: implement **`IEquatable<T>`**, override `Equals(object?)` and `GetHashCode()`, and define `==`/`!=`.

**Pitfalls**
- **Never mutate a value used as a dictionary key**. If fields involved in hashing change, the key becomes “lost” inside the hash table.
- Be careful with floating-point equality and NaN semantics; prefer domain-specific comparison rules.

**Performance note**
- Implementing `IEquatable<T>` avoids virtual dispatch and reduces boxing risk in generic code.

### 4) Avoid large structs
**Rule**: Keep structs **small** and cohesive.

**Why**
- Every pass-by-value, return, assignment, and many collection operations copy the entire value.

**Guidance**
- If it grows beyond “a few fields,” reassess: can it be split, made a class, or redesigned around spans/refs?
- Use `in` selectively (see [3.2](<../3. Struct vs class/3.2. Big struct problem copying passing hidden costs.md>)): it can help for large readonly structs, but can also force temporaries/defensive copies.

### 5) Watch for boxing
**Rule**: If it boxes, it allocates. If it allocates, it can dominate CPU via GC under load.

**Hot-path red flags**
- `object` parameters, `params object[]`, non-generic interfaces, non-generic collections.
- Formatting/logging paths that go through `object` or `IFormattable` in a non-generic way.

**Mitigations**
- Prefer generic APIs and generic interfaces.
- Use `IEquatable<T>`, `IComparable<T>`.
- Avoid `ArrayList`/`Hashtable` and other legacy collections.

### 6) Make `default` behavior intentional
**Rule**: Every struct must have a coherent story for `default(T)`.

**Two acceptable strategies**
- **Default-valid**: `default` is a legitimate value (often the best UX).
- **Default-invalid but detectable**: define a cheap `IsInitialized` / `IsEmpty` check and validate at boundaries (see [2.2](<../2. Constructors in structs/2.2. Struct invariants factories valid states.md>)).

**Common mistake**
- Assuming constructors always run. They don’t for `default`, arrays, interop/serialization, and some generic paths.
