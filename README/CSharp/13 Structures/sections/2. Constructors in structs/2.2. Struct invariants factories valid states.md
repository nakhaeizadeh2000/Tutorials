## 2.2. Structs with constructors: invariants, factories, and “valid states only”

1. **Invariant strategy** (decide whether `default` is valid; if not, design an explicit “uninitialized” sentinel you can detect)
2. **Factories vs constructors** (when creation can fail, needs parsing/validation, or needs caching)
3. **Interop/serialization realities** (frameworks may create `default`; validate at boundaries, not deep inside hot loops)

---

### 1) **Invariant strategy** (decide whether `default` is valid; if not, design an explicit “uninitialized” sentinel you can detect)

**Goal:** Make every instance either:
- **Valid by construction**, or
- **Cheaply and reliably detectable as invalid/uninitialized**, with validation happening at boundaries.

Structs have a special constraint: **`default(T)` always exists** (see [1.1](<../1. Structures fundamentals/1.1. What a struct is value semantics storage defaults.md>) and [2.1](<./2.1. Struct constructors rules.md>)). So you can’t rely on “constructor always runs” as your enforcement mechanism.

#### Option A: “`default` is valid” (preferred when it matches the domain)

**Best ergonomics**: `default` becomes a meaningful value like “0”, “empty”, or “none”.

- Good for numeric-like values and units where zero is valid (`Meter`, `Duration`, `Percent`).
- Good for “empty value” semantics (`Range.Empty`, `Angle.Zero`).

**Mentor advice:** If you can make `default` valid without lying, do it. It removes an entire class of bugs and makes generic usage painless.

#### Option B: “`default` is invalid but detectable”

If the domain truly forbids the zero state (e.g., `EmailAddress`, `OrderId` that must be non-empty), you need a strategy that works with `default`.

**Patterns that work well**

- **Sentinel field**: store a field that can’t be “accidentally valid” in default.
  - Example: `Guid` default is `Guid.Empty`, which is an easy sentinel.
- **`IsInitialized`/`IsValid` property**: a cheap check used at boundaries.
- **Two-phase creation**: parsing/validation factories that return `bool` / `Result` and produce a valid instance only on success.

**Avoid these anti-patterns**

- **Throwing on every member access** when default: pushes exceptions into hot paths and surprises callers.
- **Hiding validation deep inside** `GetHashCode`/`Equals`: makes dictionaries and sets unpredictable and slow.

#### Focused example: sentinel + boundary validation

```csharp
using System;

public readonly record struct OrderId(Guid Value)
{
    public bool IsInitialized => Value != Guid.Empty;

    public static bool TryCreate(Guid value, out OrderId id)
    {
        if (value == Guid.Empty)
        {
            id = default;
            return false;
        }

        id = new OrderId(value);
        return true;
    }

    public override string ToString() => Value.ToString("D");
}

public static class Demo
{
    public static void Main()
    {
        // default exists and is detectable:
        OrderId x = default;
        Console.WriteLine(x.IsInitialized); // False

        if (OrderId.TryCreate(Guid.NewGuid(), out var id))
            Console.WriteLine(id);
    }
}
```

**Performance note**
- Make `IsInitialized` checks **branch-predictable** and cheap (simple comparisons).
- Validate once at the boundary; avoid re-validating repeatedly inside tight loops.

### 2) **Factories vs constructors** (when creation can fail, needs parsing/validation, or needs caching)

**Rule of thumb**
- Use a **constructor** when creation is *always valid* and cannot fail.
- Use a **factory** when creation can fail, needs normalization, parsing, external context, or caching.

#### When factories are better

- **Parsing** (input may be invalid): `TryParse` pattern avoids exceptions in normal control flow.
- **Normalization**: e.g., trimming, canonical casing, unit conversions.
- **Multiple representations**: `FromMeters`, `FromCentimeters`, `From(ReadOnlySpan<char>)`.
- **Caching / interning**: rarely needed for structs; if you need it, that’s often a sign it should be a class.

#### Prefer `TryXxx` over “throwing constructors” for user input

Throwing constructors are fine for *programmer errors* (violating a documented invariant), but for user input and untrusted data, prefer `TryCreate`/`TryParse` to avoid exception-driven hot paths.

```csharp
using System;

public readonly record struct Email(string Value)
{
    public static bool TryCreate(ReadOnlySpan<char> input, out Email email)
    {
        // Minimal example; real validation depends on your requirements.
        var s = input.Trim();
        if (s.Length < 3 || s.IndexOf('@') <= 0)
        {
            email = default;
            return false;
        }

        email = new Email(s.ToString()); // boundary allocation is explicit and intentional
        return true;
    }
}
```

**Good to know**
- If you return `bool`, you avoid allocations. If you return a richer error, consider a small error enum or a `Result<T>` type, but keep it allocation-free in hot paths.

### 3) **Interop/serialization realities** (frameworks may create `default`; validate at boundaries, not deep inside hot loops)

**Reality:** many frameworks can materialize structs as default:
- JSON serializers (depending on configuration)
- ORMs / mappers
- `Activator.CreateInstance<T>()`
- Arrays and `stackalloc` create default elements

**Best practice**
- Treat external data as **untrusted**.
- Validate at the **system boundary** (DTO -> domain mapping).
- Inside the domain model, assume invariants hold (so inner loops stay fast and simple).

**Practical boundary pattern**
- Keep a “raw” DTO where `default`/null/empty is acceptable.
- Map to a validated domain struct using `TryCreate` / `Parse` with explicit error handling.

**Performance note**
- Validation often involves string work and is allocation-heavy. Do it once, then keep the validated struct small and immutable so it’s cheap to copy and compare.
