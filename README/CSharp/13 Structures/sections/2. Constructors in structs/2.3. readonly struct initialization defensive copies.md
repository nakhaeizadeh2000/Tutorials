## 2.3. `readonly struct` and initialization patterns that avoid defensive copies

1. **Why readonly affects performance** (prevents hidden copies on member access in some cases)
2. **Immutability boundary** (readonly fields vs deep immutability; keep mutation explicit and localized)
3. **Design rule** (if a struct represents a value, make it *actually* behave like a value)

---

### 1) **Why readonly affects performance**

**Definition.** `readonly struct` is a promise: once constructed, the instance’s fields will not be mutated through instance members. This is primarily a **correctness** feature (value objects behave like values), but it also affects performance via **defensive copies**.

#### What is a “defensive copy” here?
The compiler/JIT may create a copy of a struct in order to call a non-`readonly` instance member on a `readonly` receiver, because calling a mutating member would otherwise violate the `readonly` guarantee.

**Typical triggers**
- A `readonly` field of a struct type (e.g., inside a class).
- A `readonly` local or parameter (`in` parameters are readonly by contract).
- A `readonly struct` calling an instance member that is not annotated `readonly`.

**Why it matters**
- Copies are often small and cheap, but in hot loops a hidden copy can become measurable.
- Defensive copies also obscure intent: you think you are operating on “the value,” but you might be operating on a **temporary**.

#### Minimal example: mark members `readonly` to avoid extra copies

```csharp
using System;

public readonly struct Counter
{
    private readonly int _value;
    public Counter(int value) => _value = value;

    // Important: annotate as readonly when the method is logically non-mutating.
    public readonly int Get() => _value;

    // Non-readonly member (even if it doesn't mutate) can force defensive copies
    // when called on a readonly receiver.
    public int GetWithoutReadonly() => _value;
}

public static class Demo
{
    private static readonly Counter s_counter = new(123);

    public static void Main()
    {
        Console.WriteLine(s_counter.Get());              // no defensive copy needed
        Console.WriteLine(s_counter.GetWithoutReadonly()); // may require defensive copy
    }
}
```

**Performance note**
- This is a “sharp edge” mostly for **non-trivial structs** and tight loops. Avoid guessing: measure in your actual scenario.
- The *design* win of `readonly` is usually bigger than the micro-optimization: it prevents whole classes of bugs from mutation + copying.

**Good to know**
- The full “defensive copy mechanics” and how to detect them (warnings/analyzers) are covered in **section `4.1`**. This section focuses on *initialization and patterns* that naturally avoid triggering them.

---

### 2) **Immutability boundary**

**Key idea.** `readonly struct` enforces *shallow immutability*:
- You cannot reassign its fields (through instance members).
- But if a field is a reference to a mutable object, that object can still mutate.

**Examples**
- `readonly struct` with a `string` field is effectively immutable (strings are immutable).
- `readonly struct` with a `byte[]` field is *not* deeply immutable (the array contents can change).

**Mentor rule**
- For public value objects, prefer fields that are themselves immutable, or encapsulate/defensively-copy mutable references (but be explicit about allocation cost).

#### Example: safe “view” vs owning copy

```csharp
using System;

public readonly struct Segment
{
    public ReadOnlyMemory<byte> Data { get; }
    public Segment(ReadOnlyMemory<byte> data) => Data = data;
}

public static class Demo
{
    public static void Main()
    {
        var buffer = new byte[] { 1, 2, 3, 4 };
        var seg = new Segment(buffer); // view over buffer; no allocation

        buffer[0] = 9; // changes what seg sees too
        Console.WriteLine(seg.Data.Span[0]); // 9
    }
}
```

**Good to know**
- A “view struct” like this is fine *when you document lifetime/ownership* (and when aliasing is acceptable).
- If you need deep immutability, you must copy the data (allocation) or use immutable collections.

---

### 3) **Design rule**

If a struct represents a value:
- **Make it behave like a value**: immutable, stable equality, stable hashing, no observable identity.
- **Make default behavior intentional** (see `2.2` for invariant strategy).
- **Avoid surprising mutation APIs** (especially setters); in many cases `readonly record struct` is the most maintainable default (see `1.2`).

#### Pattern: “validated creation, cheap use”

```csharp
using System;

public readonly record struct Port(ushort Value)
{
    public static bool TryCreate(int value, out Port port)
    {
        if ((uint)value <= ushort.MaxValue && value is >= 1 and <= 65535)
        {
            port = new((ushort)value);
            return true;
        }

        port = default;
        return false;
    }
}
```

**Performance note**
- Validate once at the boundary (`TryCreate`, parsing, DTO mapping).
- Keep inner-loop usage allocation-free and branch-light.
