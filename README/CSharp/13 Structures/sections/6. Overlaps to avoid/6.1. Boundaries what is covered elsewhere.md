## 6.1. Boundaries: what is covered elsewhere in this repo

1. **General OOP concepts and “type shape choice” overview** are introduced in `CSharp Basic Object Oriented Programming`
2. **`readonly` fields, static initialization, and memory model basics** are covered in `Fields`
3. **Boxing/unboxing and conversions** are covered deeply in `Type Conversion`
4. **Threading + memory model deep dive** is in `Cuncurrent & Parallel`
5. **CLR/JIT/GC big picture** is in `Fundamental Theories`

---

### 1) **General OOP concepts and “type shape choice” overview**
This Structures domain assumes you already know the OOP basics (encapsulation, immutability, “what is an object,” etc.).

- **See**: `CSharp Basic Object Oriented Programming` for the foundational explanations.
- **What this Structures domain covers instead**: the *value-type-specific* consequences (copying, inline storage, boxing, defensive copies, and API design rules that prevent real production bugs).

**Good to know**
- This repo’s Structures material is intentionally opinionated: **semantics first, performance second**. A “struct because it’s faster” decision without semantic fit is a common mistake; see [3.1](<../3. Struct vs class/3.1. Choosing struct vs class checklist.md>).

---

### 2) **`readonly` fields, static initialization, and memory model basics**
We mention `readonly` frequently here (especially `readonly struct`), but we do **not** re-teach:
- `readonly` fields vs `readonly` locals
- `static` initialization ordering
- the .NET memory model at a deep level

- **See**: `Fields` for the full treatment of `readonly` and initialization rules.
- **In this Structures domain**: we focus on **defensive copies** and “immutability boundary” issues specific to structs (see [4.1](<../4. Readonly structs/4.1. readonly struct guarantees and limits.md>) and [2.3](<../2. Constructors in structs/2.3. readonly struct initialization defensive copies.md>)).

**Performance note**
- “`readonly` = faster” is not universally true. It can *reduce defensive copies* in some patterns, but it can also introduce additional constraints. Always reason about **copying**, not slogans.

---

### 3) **Boxing/unboxing and conversions**
We cover boxing in this Structures domain because it’s a top source of hidden allocations for value types (see [3.3](<../3. Struct vs class/3.3. Boxing interfaces generics.md>)).
However, the *general* topic of conversions (numeric conversions, user-defined conversions, explicit/implicit, etc.) is not duplicated here.

- **See**: `Type Conversion` for the deep conceptual model and conversion rules.
- **In this Structures domain**: focus on *when* value types box (interfaces, `object`, legacy collections, formatting/logging paths) and how to design APIs to avoid it ([3.3](<../3. Struct vs class/3.3. Boxing interfaces generics.md>), [1.3](<../1. Structures fundamentals/1.3. Primitive types as structures implications.md>)).

---

### 4) **Threading + memory model deep dive**
We intentionally avoid duplicating deep concurrency content here.

- **See**: `Cuncurrent & Parallel` for the deep dive on threads, the thread pool, `Task`, scheduling, synchronization, and the .NET memory model.
- **In this Structures domain**: we only cover **struct-specific hazards** you must not miss:
  - “atomicity” misconceptions for structs
  - torn reads/writes for larger-than-native-word structs
  - why `volatile` and `Interlocked` don’t magically make “any struct” safe
  - pitfalls with `async`/iterators capturing copies

These are covered in [5.2](<../5. Important points/5.2. Common struct pitfalls production bugs.md>) with minimal repro snippets and fixes.

---

### 5) **CLR/JIT/GC big picture**
We reference JIT/GC consequences (copying vs allocation, GC pressure from boxing) but do not re-teach CLR internals.

- **See**: `Fundamental Theories` for the big picture of the CLR, JIT compilation, and GC.
- **In this Structures domain**: the practical guidance is:
  - allocating less is good *only if* you don’t replace it with more expensive copying/boxing
  - the “best” design depends on size, mutation, lifetime, and calling patterns; measure when it matters (see [3.2](<../3. Struct vs class/3.2. Big struct problem copying passing hidden costs.md>) and [3.3](<../3. Struct vs class/3.3. Boxing interfaces generics.md>))
