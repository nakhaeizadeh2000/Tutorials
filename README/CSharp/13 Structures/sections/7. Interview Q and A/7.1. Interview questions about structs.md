## 7.1. Interview Q&A: structs, readonly structs, and value semantics pitfalls

1. **Struct vs class** (semantics first; perf second; examples of real bugs with mutable structs)
2. **What is boxing and when do structs box?** (hot-path consequences; how to avoid)
3. **What does `readonly struct` change?** (defensive copies; API design)
4. **Why `default(T)` is always possible** (invariant strategy; detecting “uninitialized”)
5. **Why “struct for performance” can backfire** (copy amplification; interface calls; GC vs copying trade-offs)

---

Use these as **model answers**. In an interview, aim for: (1) correct definitions, (2) a concrete example, (3) trade-offs, (4) how you avoid production bugs.

### 1) Struct vs class
**Short answer**: Choose by **semantics first** (value vs identity), then **performance**, then **API/versioning risk**.

**What I’d say**
- **Struct**: a **value type** with value semantics (assign/pass copies) that should represent a small, cohesive value with no identity.
- **Class**: a **reference type** with identity; assignment copies references and enables aliasing/sharing and polymorphism.

**What a strong interviewer expects**
- You don’t claim “structs are stack-allocated” as a rule; you explain **inline storage**, **copying**, and **boxing**.
- You can name the classic mutable-struct bug: *mutating a copy from a property/indexer/foreach*.

**Example bug: mutating a copy**

```csharp
using System;
using System.Collections.Generic;

public struct Point { public int X; public int Y; }

public static class Demo
{
    public static void Main()
    {
        var list = new List<Point> { new() { X = 1, Y = 2 } };

        // points[0] returns a copy, so this does NOT mutate the list element.
        var p = list[0];
        p.X++;

        Console.WriteLine(list[0].X); // 1
    }
}
```

**Trade-offs (the actual “architect” answer)**
- **Struct wins** when it’s *small + immutable* and used in arrays/collections for locality and fewer GC allocations.
- **Class wins** when:
  - the object has **identity** / is shared among many owners,
  - it’s **large or mutable** (copy amplification becomes a real cost and a bug source),
  - you need **inheritance/polymorphism**, or
  - you need stable reference semantics (no accidental copies).

### 2) What is boxing and when do structs box?
**Definition**: **Boxing** converts a value type into an `object` (or an interface reference) by allocating a new object on the heap and copying the value into it.

**When it happens**
- Assigning a struct to `object`: `object o = myStruct;`
- Passing a struct to an API that takes `object` or a **non-generic** interface.
- Storing a struct in non-generic collections (legacy): `ArrayList`, `Hashtable`.
- Calling members through `System.ValueType` / `object` paths.

**Why interviewers care**
- Boxing is a **hidden allocation**; in hot paths it increases GC work and can dominate CPU.

**How I avoid it**
- Prefer **generic APIs** and **generic interfaces** (`IEquatable<T>`, `IComparable<T>`).
- Prefer **generic collections** (`List<T>`, `Dictionary<TKey, TValue>`).
- Avoid “object-typed” parameters in performance-sensitive code; add generic overloads.

**Micro example**

```csharp
using System;

static class Demo
{
    static void LogObject(object value) => Console.WriteLine(value);
    static void LogGeneric<T>(T value) => Console.WriteLine(value);

    public static void Main()
    {
        int n = 123;
        LogObject(n);   // boxing allocation
        LogGeneric(n);  // no boxing for parameter passing
    }
}
```

### 3) What does `readonly struct` change?
**Short answer**: It makes the type behave more like a “real value object” by forbidding mutations of instance fields through instance members, and it can reduce certain **defensive copy** patterns.

**Precise points**
- `readonly struct` prevents *instance members* from mutating instance fields (unless you use `mutable` tricks like `Unsafe`—don’t).
- It does **not** imply deep immutability: if you hold a reference to mutable state, that referenced state can still be mutated.
- It encourages API design where methods are **`readonly`** and parameters are **`in`** where appropriate.

**Defensive copies (what to mention)**
- The compiler may create defensive copies to preserve readonly guarantees when calling non-readonly members on a readonly receiver.
- Marking members `readonly` and designing immutable structs reduces surprises and can improve performance.

### 4) Why `default(T)` is always possible
**Key rule**: The runtime can always produce the “all-zero bits” value for any value type \(e.g. arrays, generics, interop\). Even if you define a parameterless constructor, **`default(T)` still exists**.

**What interviewers want**
- You understand that “constructor-enforced invariants” are weaker for structs than for classes.
- You propose a practical invariant strategy:
  - make `default` valid, or
  - make `default` invalid but *detectable* and validate at boundaries.

**Pattern (default invalid but detectable)**

```csharp
using System;

public readonly struct CustomerId
{
    private readonly Guid _value;
    public bool IsInitialized => _value != Guid.Empty;
    public Guid Value => IsInitialized ? _value : throw new InvalidOperationException("Uninitialized CustomerId.");

    public CustomerId(Guid value)
        => _value = value != Guid.Empty ? value : throw new ArgumentOutOfRangeException(nameof(value));
}
```

**Mentor note**
- Avoid throwing in hot loops; validate **once** at boundaries (parsing, DTO mapping, API entry points). Don’t sprinkle “default checks” everywhere.

### 5) Why “struct for performance” can backfire
**Short answer**: A struct can be “faster” than a class when it’s small/immutable and avoids allocations, but it can be **slower** when it:
- gets **big** (copy costs dominate),
- is used through **interfaces** (boxing / virtual dispatch),
- is **mutable** in public APIs (bugs + defensive copies + hard-to-reason performance),
- is captured into closures/async state machines (extra copying / escaping).

**What to mention**
- Performance is a trade-off between **copying costs** vs **allocation + GC costs**.
- The “big struct” problem is usually *memory bandwidth* and copy amplification, not just CPU instructions.
- Measure with `BenchmarkDotNet` if you’re making performance claims.
