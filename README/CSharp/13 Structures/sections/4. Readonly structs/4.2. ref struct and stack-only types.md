## 4.2. `ref struct` and stack-only types (Span-like patterns)

1. **What `ref struct` means** (stack-only, cannot be boxed, cannot cross async/iterator boundaries)
2. **When to care** (`Span<T>`, `ReadOnlySpan<T>`, high-performance parsing, slicing without allocations)
3. **Design constraints** (lifetime safety; avoiding capturing; designing APIs that make misuse impossible)

---

### 1) **What `ref struct` means** (stack-only, cannot be boxed, cannot cross async/iterator boundaries)

**Definition.** A `ref struct` is a struct with *stack-only lifetime rules* enforced by the compiler. The key property isn’t “performance” by itself; it’s **lifetime safety**: the type may contain references to stack memory or unmanaged buffers, so the compiler prevents it from escaping to the heap.

**What the compiler enforces**

- **No boxing**: you cannot convert a `ref struct` to `object` or to any interface type.
- **No heap capture**:
  - Cannot be a field of a class.
  - Cannot be used as a type argument in most places that could store it on the heap (e.g., `Task<T>`, `List<T>`, most `async` locals).
- **No crossing `async` / iterator boundaries**:
  - You cannot keep a `ref struct` alive across an `await`.
  - You cannot use it as a state machine field (including `yield return`).
- **No lambda capture**:
  - You can use a `ref struct` inside a method, but you cannot capture it in a lambda that might outlive the stack frame.

**Canonical examples**

- `Span<T>` and `ReadOnlySpan<T>` are `ref struct`s.
- Many high-performance parsers expose span-based APIs rather than allocating intermediate strings/arrays.

**Common mistake**

Trying to “store a span for later”:

```csharp
using System;

public static class Demo
{
    public static void Main()
    {
        ReadOnlySpan<char> s = "hello".AsSpan();
        // You can use it here...
        Console.WriteLine(s.Length);

        // ...but you cannot store it in a field for later use (won't compile).
        // See section 4.2.3 for the correct pattern: copy at the boundary.
    }
}
```

**Performance note**

- `Span<T>` enables *slicing without allocations*, but it can also make code faster because it improves locality and reduces GC pressure.
- The biggest “perf win” is often **avoiding intermediate allocations** (strings, arrays), not micro-optimizing stack vs heap.

---

### 2) **When to care** (`Span<T>`, `ReadOnlySpan<T>`, high-performance parsing, slicing without allocations)

Use stack-only/span-like patterns when you want:

- **Zero-allocation slicing**: work with substrings / subarrays without allocating.
- **Parsing and validation on hot paths**: HTTP headers, CSV/TSV, protocol parsing, numeric parsing.
- **IO-friendly APIs**: handle data from pipelines/streams without copying (when upstream provides memory).

**Modern guidance (C# 15 / .NET 9+)**

- Prefer APIs that accept spans:
  - `int.TryParse(ReadOnlySpan<char>, ...)`
  - `Guid.TryParse(ReadOnlySpan<char>, ...)`
  - `Utf8Parser.TryParse(ReadOnlySpan<byte>, ...)` (when working with UTF-8 bytes)
- Prefer returning spans *as views* within the same stack lifetime; return `string`/arrays only when you need ownership beyond the current operation.

**Focused example: parse without allocations**

```csharp
using System;

public static class Demo
{
    public static void Main()
    {
        string input = "lat=35&lon=51";
        ReadOnlySpan<char> s = input.AsSpan();

        if (TryGetQueryValue(s, "lon", out var lonSpan) &&
            int.TryParse(lonSpan, out var lon))
        {
            Console.WriteLine(lon);
        }
    }

    // Note: this returns spans that are only valid as long as 's' is valid.
    private static bool TryGetQueryValue(ReadOnlySpan<char> s, ReadOnlySpan<char> key, out ReadOnlySpan<char> value)
    {
        // very small demo parser: key=value&key=value
        while (!s.IsEmpty)
        {
            var amp = s.IndexOf('&');
            var pair = amp >= 0 ? s[..amp] : s;
            s = amp >= 0 ? s[(amp + 1)..] : ReadOnlySpan<char>.Empty;

            var eq = pair.IndexOf('=');
            if (eq < 0) continue;

            var k = pair[..eq];
            if (!k.SequenceEqual(key)) continue;

            value = pair[(eq + 1)..];
            return true;
        }

        value = default;
        return false;
    }
}
```

**Good to know**

- `ReadOnlySpan<T>` is often the best default for APIs that only need to read data.
- For binary data, `ReadOnlySpan<byte>` avoids encoding conversions and can be dramatically faster.

---

### 3) **Design constraints** (lifetime safety; avoiding capturing; designing APIs that make misuse impossible)

The hard part of `ref struct` design is not writing the type—it’s designing **APIs that enforce correct lifetimes**.

**Rules to follow**

- **Never store spans beyond their source lifetime**:
  - If you must store, convert to an owning representation: `string`, `byte[]`, `ImmutableArray<T>`, etc.
- **Keep span-based work inside a tight scope**:
  - Parse → validate → create owned value object → return it.
- **Avoid returning spans that outlive the input**:
  - Returning a span is fine if it clearly points into a parameter span (and the caller controls the lifetime).

**Boundary-copy pattern (the safe way)**

When you need to keep the data, copy it at the boundary:

```csharp
using System;

public readonly record struct UserName(string Value)
{
    public static bool TryCreate(ReadOnlySpan<char> input, out UserName userName)
    {
        input = input.Trim();
        if (input.IsEmpty || input.Length > 32)
        {
            userName = default;
            return false;
        }

        // Copy to an owned string exactly once at the boundary.
        userName = new UserName(input.ToString());
        return true;
    }
}
```

**Common mistakes**

- Using `async` methods that try to hold spans across `await`. The compiler blocks this for good reason.
- Returning `Span<T>`/`ReadOnlySpan<T>` from properties that depend on mutable buffers (lifetime confusion).

**Performance note**

- Copying once at the boundary is almost always a win compared to many intermediate allocations.
- If you’re tempted to keep a span in a long-lived type, you likely want a different abstraction (owned buffer + slicing APIs) rather than fighting the compiler.
