## 1.1. What a `struct` is in .NET (value semantics, storage, and defaults)

1. **Value semantics** (copies, aliasing differences vs classes, and what “assignment” really does)
2. **Where it lives** (inline in arrays/fields; stack vs heap is an implementation detail—focus on *ownership and copying*)
3. **`default(T)` / zero-initialization** (why it exists, and why “default is valid” is a design choice you must make explicit)

### 1) Value semantics
**Definition**: A `struct` is a *value type*. Its *value* is the bits of its fields. When you **assign**, **pass**, or **return** a struct, you typically copy that value (unless the JIT can elide/cse/keep it in registers, or you pass by reference explicitly).

**What this means in practice**
- **Assignment copies**: `b = a` copies the entire struct value into `b`. Afterwards, `a` and `b` are independent values.
- **Mutation affects only that value**: Mutating a copy does not mutate the original.
- **No identity**: Unlike classes, structs typically should not represent “the same entity over time.” They represent “a value now.”

**Compare with classes (reference types)**
- A class variable holds a **reference** (pointer-like). Assignment copies the reference, not the object.
- Two variables can **alias** the same object; mutating through one is observable through the other.

**Common mistake (the “I mutated it but nothing changed” bug)**

```csharp
using System;
using System.Collections.Generic;

public struct Point
{
    public int X;
    public int Y;
}

public static class Demo
{
    public static void Main()
    {
        var points = new List<Point> { new() { X = 1, Y = 2 } };

        // BUG: points[0] returns a copy; you mutate the copy, not the list element.
        var p = points[0];
        p.X++;
        Console.WriteLine(points[0].X); // still 1

        // Correct: assign the modified value back.
        p = points[0];
        p.X++;
        points[0] = p;
        Console.WriteLine(points[0].X); // 2
    }
}
```

**Mentor guidance**
- **Public mutable structs are risky**: they combine “copy semantics” + “mutation,” which creates surprising bugs (especially with properties, foreach, LINQ, async). Prefer **immutable** (`readonly struct` / `record struct`) for public APIs. Deep dive in section [4.1](<../4. Readonly structs/4.1. readonly struct guarantees and limits.md>) and [5.2](<../5. Important points/5.2. Common struct pitfalls production bugs.md>).
- **Value semantics shine for small, cohesive values**: coordinates, ranges, timestamps, IDs, small numeric types, options, result discriminants.

**Performance note**
- Copying a small struct (1–3 machine words) is extremely cheap and often faster than allocating a class + GC pressure.
- Copying a large struct repeatedly can dominate CPU and memory bandwidth. See section [3.2](<../3. Struct vs class/3.2. Big struct problem copying passing hidden costs.md>) for the “big struct” amplification patterns.

### 2) Where it lives
**Key idea**: Don’t build mental models around “structs are on the stack.” That’s a legacy simplification. In .NET, *where the bits live* depends on *who owns the value*.

**Typical storage locations**
- **Inline inside another object**: fields of a class that are structs live *inside* that object’s memory.
- **Inline in arrays**: `Point[]` stores the `Point` values *contiguously* (no per-element object allocation). This can be a major locality win.
- **On the stack**: locals can be stack-allocated *if they don’t escape*; the JIT decides.
- **On the heap (as part of something else)**:
  - Captured locals in closures / async state machines may be lifted to heap.
  - A struct can be **boxed**, which allocates an object that contains a copy of the value (covered deeply in section [3.3](<../3. Struct vs class/3.3. Boxing interfaces generics.md>)).

**Why “ownership and copying” is the right model**
- Arrays/fields store the value inline: fetching returns a **copy**, unless you use ref-return APIs (rare in general code; common in low-level libs).
- Passing by value copies; passing by `ref`/`in` does not copy the value *as a parameter passing mechanism*, but the compiler/JIT may still materialize temporaries in some cases (see section [3.2](<../3. Struct vs class/3.2. Big struct problem copying passing hidden costs.md>)).

**Good to know**
- Structs have **no object header**; arrays of structs are dense.
- `List<T>` stores `T[]` internally, so `List<SmallStruct>` can be very cache-friendly.
- But “dense” also means **bulk copying** during resizes and moves; design for small structs or use classes when mutation + size imply too much copying.

### 3) `default(T)` / zero-initialization
**Definition**: `default(T)` produces the all-zero bit pattern for `T`. For structs, that means every field is `default` too (e.g., ints = 0, refs = `null`, `bool` = `false`).

**Non-negotiable rule**: In .NET, you can always obtain a default value for any value type:
- `default(MyStruct)`
- `new MyStruct()` (this produces the same as `default` unless you define a parameterless ctor; even then, `default` still exists)
- Arrays and `stackalloc` initialize elements to default unless using “skip init” patterns (advanced).

**Design decision you must make**
- **Option A: “default is valid”**. Make the zero value represent a real, safe value (often the best ergonomics).
- **Option B: “default is invalid but detectable”**. Provide a cheap sentinel check (`IsInitialized`, `IsEmpty`, etc.) and validate at boundaries. Deep dive in section [2.2](<../2. Constructors in structs/2.2. Struct invariants factories valid states.md>).

**Common mistakes**
- **Assuming your constructor always runs**: Frameworks, serialization, and generic code can create `default`. Never rely on “constructor-enforced invariants” alone for structs.
- **Throwing on property getters for default**: This tends to push exceptions into hot paths and surprises callers. Prefer boundary validation (parsing, DTO mapping, API entry points).

**Modern pattern: Try-parse and factories**
When creation can fail, prefer `TryParse`-style APIs or factory methods returning `bool`/`Result` rather than “throwing constructors.” See section [2.2](<../2. Constructors in structs/2.2. Struct invariants factories valid states.md>) for the full treatment.

**Performance note**
- `default(T)` is free; it’s a compile-time concept.
- Validation can be expensive; structure your API so the *expensive checks happen once at the boundary*, not repeatedly in inner loops.
