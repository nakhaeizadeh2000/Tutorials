## 1.1 Exceptions as contract signals: prevent vs handle

1. **Contract framing**: decide what is a programmer error (preconditions) vs a runtime fault (IO/network/data corruption).
2. **Control-flow principle**: avoid exceptions for normal/expected paths; prefer `Try*` patterns or validation before risky work.
3. **Performance reality**: exception creation + stack trace capture is expensive; treat exceptions as cold-path signals.
4. **Correctness-first**: after failure, decide what must be true (cleanup, rollback, retry decision, error reporting).

---

### 1. **Contract framing**

**Programmer errors** (violated preconditions, impossible states) should be caught in development via tests, analyzers, and guards. **Runtime faults** (disk full, network reset, corrupt file) are often unavoidable at compile time.

Exceptions are **signals across abstraction boundaries**: they mean “this operation cannot complete its contract.” Your design should state **which failures are modeled as exceptions** vs return values / `Try` APIs.

**Good to know:** in C# 15 on modern .NET, nullable reference types and `required` members reduce some null-related surprises, but they do not remove IO or concurrency failures.

---

### 2. **Control-flow principle**

Using `try/catch` instead of `if` for ordinary branches hurts **readability** and **performance**. Prefer:

- `int.TryParse`, `Dictionary.TryGetValue`, `bool TryDequeue`, etc.
- Validation that returns a **result type** for expected validation failures in user-facing flows.

Reserve exceptions for **exceptional** conditions: violations you do not want every caller to branch on in the hot path.

---

### 3. **Performance reality**

Throwing captures a **stack trace** and unwinds frames—orders of magnitude slower than a branch. High-frequency paths (parsing millions of rows, tight loops) must not use exceptions for “not found” or “parse failed.”

**Performance note:** in .NET, **exception filters** (`catch when`) avoid entering a `catch` block when the filter is false, but evaluating a **true** filter still participates in the dispatch path—keep filters cheap (see §3.1).

---

### 4. **Correctness-first**

After a failure, define **invariants**: resources disposed? transaction rolled back? user told something actionable? For distributed systems, add **idempotency** and **retry policy** at the right layer—without swallowing root causes.

```csharp
// Prefer Try API for expected failure (no throw on invalid user input)
if (!int.TryParse(text, out var value))
    return ValidationProblem("Not a number");

// Exception for unexpected invariant break inside domain logic
if (_disposed)
    throw new ObjectDisposedException(nameof(MyService));
```

For deeper null-contract strategy, see *Handling Null*; this domain focuses on throw/handle mechanics and diagnostics.
