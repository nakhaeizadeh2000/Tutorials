### 1) **Examples** (Port, Email, Money, Percentage, TenantId, etc.)

**Definition**

A **boundary type** (also called a *strong type* or *value object*) is a small type that represents a domain concept with its own invariants, instead of using a primitive everywhere.

Examples:

- `Port` instead of `int`
- `Email` instead of `string`
- `Money` instead of `decimal`
- `TenantId` instead of `Guid`

**Why mentors push this pattern**

Primitives are too permissive:

- any `int` can be a port, an age, a quantity, or an error code
- any `string` can be an email, a file path, or a JSON blob

So bugs happen because “wrong but type-compatible” values flow through the system.

Boundary types:

- make invalid states harder to represent
- make conversion/validation **one-time and centralized**
- make APIs self-documenting

**Example (runnable): a `Port` type**

```csharp
using System;
using System.Globalization;

public readonly record struct Port(ushort Value)
{
    public override string ToString() => Value.ToString(CultureInfo.InvariantCulture);

    public static bool TryCreate(ReadOnlySpan<char> text, IFormatProvider? provider, out Port port)
    {
        // Ports are culture-invariant. Still accept provider for a consistent API surface.
        if (!int.TryParse(text, NumberStyles.None, CultureInfo.InvariantCulture, out var tmp) ||
            (uint)tmp > 65535u)
        {
            port = default;
            return false;
        }

        port = new Port((ushort)tmp);
        return true;
    }
}

static class Demo
{
    static void Main()
    {
        if (Port.TryCreate("443".AsSpan(), provider: null, out var port))
            Console.WriteLine(port);
    }
}
```

**Good to know**

- Prefer `readonly record struct` (or `readonly struct`) for small value objects: value semantics, low allocation, easy equality.
- Use `record struct` when value-based equality is what you want (it usually is for IDs and small concepts).

### 2) **TryCreate / Parse patterns** (result types vs Try-pattern; choose intentionally)

**Two good patterns**

1) **Try-pattern** (best when failure is expected and you want fast/branch-friendly code):

- `public static bool TryCreate(..., out T value)`

2) **Result type** (best when the caller needs structured error details):

- `public static ParseResult<T> TryCreate(...)`
- or `public static OneOf<T, Error>` style (library-dependent)

**Mentor rule**

- If the caller must always know *why* it failed, don’t overload `out string error` patterns everywhere. Use a small **result type**.

**Example: result type without allocations**

```csharp
public readonly record struct ParseResult<T>(bool Success, T Value, string? Error)
{
    public static ParseResult<T> Ok(T value) => new(true, value, null);
    public static ParseResult<T> Fail(string error) => new(false, default!, error);
}
```

Use it when you need error messages surfaced to the user (UI/API validation). For purely internal parsing, Try-pattern is usually enough.

**See also**

- For the “Parse vs TryParse” decision and exception costs: `4.1. Parse vs TryParse`

### 3) **Nullability and default values** (avoid “0 means missing” unless domain says so)

**Core idea**

There are three different states people often confuse:

1. **Missing** (no value provided)
2. **Malformed** (value provided but invalid)
3. **Valid** (value provided and valid)

If you collapse these states into a single default (`0`, empty string, `Guid.Empty`), you create bugs that look like “valid data”.

**Mentor patterns**

- Use `T?` for “missing”, and a boolean/result for “valid vs malformed”.
- Avoid “magic sentinel values” unless the domain defines them (e.g., `0` really means “unlimited”).

---

### 4) **Serialization strategy** (explicit converters, stable formats)

**Rule**

Serialization is a boundary. Keep it explicit:

- choose stable formats (`InvariantCulture`, `O` round-trip for timestamps)
- make conversion rules testable

**Where this belongs**

This domain mentions serialization only as it affects conversion. A deep serialization treatment belongs in a dedicated “Serialization/JSON” domain later (as noted in `7.2`).

**Practical guidance**

- For JSON, prefer explicit converters scoped to serialization rather than global conversion mechanisms.
- For config binding, prefer explicit parsing unless the framework requires `TypeConverter` (see `5.3`).

---

### 5) **Performance notes** (avoid repeated parsing and repeated allocations)

**Where performance is actually won**

- Parse once at the boundary.
- Avoid exception-driven validation (use `TryParse`/TryCreate).
- Avoid allocation-heavy tokenization (`Split`/substrings) in hot paths; use spans (see `4.3`).

**Mentor stress**

- Value objects do not automatically slow code down. The overhead is usually negligible compared to the correctness benefits, and the JIT often inlines small methods/operators.
