## 6.1. User-defined implicit/explicit operators: when they help vs harm

1. **Design rule** (implicit only if truly lossless and unsurprising)
2. **Prefer explicit for “might fail / might lose info”**
3. **Keep conversions near the type** (discoverability; prevents scattered helpers)
4. **Don’t smuggle parsing into operators** (operators can’t be Try-pattern; exceptions leak)
5. **Performance and JIT** (inlining, method call overhead is usually negligible vs clarity)

---

### 1) **Design rule** (implicit only if truly lossless and unsurprising)

**Definition**

C# allows *user-defined conversions* via operators:

- `public static implicit operator Target(Source value)`
- `public static explicit operator Target(Source value)`

The compiler treats these as **conversion candidates** during overload resolution and assignment, and inserts calls to them when applicable.

**Mentor rule (hard rule for production APIs)**

- Only make a conversion **implicit** if it is:
  - **lossless**
  - **non-throwing** in normal operation
  - **cheap** (no IO, no heavy parsing, no global lookups)
  - **unsurprising** to a reader who sees `Target t = source;`

If you violate any of these, you create “action at a distance” bugs where innocuous code now:

- allocates
- throws
- changes meaning under different cultures
- or becomes ambiguous with other overloads

**Good implicit example**

Wrapper types that simply expose a primitive value with no invariants are plausible candidates:

```csharp
public readonly record struct UserId(Guid Value)
{
    public static implicit operator Guid(UserId id) => id.Value;
}
```

Even here, consider whether implicit is worth it—sometimes explicit access (`id.Value`) is clearer.

---

### 2) **Prefer explicit for “might fail / might lose info”**

If a conversion can lose information (precision, range) or can fail (format errors, invalid state), make it **explicit** or expose a dedicated API (`TryCreate`, `Parse`, etc.).

**Examples**

- `Money` → `decimal` might be “lossless”, but `decimal` → `Money` might require currency/scale rules and validation.
- `Email` → `string` is likely fine; `string` → `Email` can fail.

**Pattern**

```csharp
public readonly record struct Percentage(decimal Value)
{
    public static explicit operator Percentage(decimal value)
    {
        if (value is < 0m or > 1m)
            throw new ArgumentOutOfRangeException(nameof(value));

        return new Percentage(value);
    }

    public static implicit operator decimal(Percentage p) => p.Value;
}
```

**Good to know**

- An explicit operator still throws on invalid input; if invalid input is expected (user input), prefer **Try-pattern** or a result type (covered in `6.2`).

---

### 3) **Keep conversions near the type** (discoverability; prevents scattered helpers)

**Why**

If conversion rules are scattered in helpers (`Converters.cs`, extension methods in random namespaces), they become:

- hard to discover
- easy to duplicate (rules drift)
- hard to test exhaustively

Putting conversion APIs on the type makes ownership clear:

- `Port.TryCreate(...)`
- `Money.ParseInvariant(...)`
- `TenantId.TryParse(...)`

**Mentor guidance**

- Keep one “source of truth” implementation per conversion rule.
- If you must support multiple parsing shapes, implement them in terms of one private core routine.

---

### 4) **Don’t smuggle parsing into operators** (operators can’t be Try-pattern; exceptions leak)

**Why**

Operators cannot follow the Try-pattern (`bool TryX(out ...)`) and therefore must signal failure via:

- exceptions, or
- sentinel values (which is worse)

That makes operators a bad place for parsing or anything that can fail due to external input.

**Anti-pattern**

```csharp
// Avoid: implicit conversion that parses text (can throw; culture-sensitive; hidden work).
public readonly record struct Port(ushort Value)
{
    public static implicit operator Port(string text) =>
        new Port(ushort.Parse(text)); // throws; also allows whitespace/culture surprises depending on API
}
```

**Preferred pattern**

- Provide `TryCreate`/`TryParse` on the type (see `6.2`) and keep operators for safe, cheap conversions only.

---

### 5) **Performance and JIT** (inlining, method call overhead is usually negligible vs clarity)

**Reality**

User-defined conversions are just method calls. In most cases:

- the JIT can inline them (especially if the type is in the same assembly and the operator is small)
- the overhead is negligible compared to parsing, allocations, IO, or exceptions

**Performance note**

- The real performance risk is not the call itself; it’s hiding expensive work behind an implicit conversion and accidentally executing it in tight loops.

**Good to know**

- User-defined conversions participate in overload resolution and can create ambiguous calls when combined with other implicit conversions. When in doubt, prefer explicit APIs for conversions that matter.
