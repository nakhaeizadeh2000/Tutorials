## 7.2. Overlaps to avoid (where this domain stops)

1. **Try-pattern mechanics** (covered in `Methods` → `out` and Try APIs)
2. **Basic primitive type definitions** (covered in `CSharp language basics`)
3. **General .NET runtime performance** (covered in `Fundamental Theories`)
4. **Serialization deep dives** (belongs in a dedicated Serialization/JSON domain later)
5. **Interop marshaling** (belongs in an Interop/PInvoke domain later)

---

### 1) **Try-pattern mechanics** (covered in `Methods` → `out` and Try APIs)

This domain uses the Try-pattern heavily (`TryParse`, `TryCreate`) because it’s the most reliable way to express “failure is normal” conversions without exceptions.

For the **deep language-level meaning of `out`** and how to design Try-pattern APIs, see:

- `README/CSharp/Methods/sections/6. Parameter modifiers and ref-like patterns/6.3. out parameters multiple returns Try patterns.md`

In this domain we focus on the *conversion decisions* (culture, styles, boundary placement), not on `out` mechanics.

---

### 2) **Basic primitive type definitions** (covered in `CSharp language basics`)

If you need the foundational details (ranges, literal forms, overflow basics, `decimal` vs `double` framing), use:

- `README/CSharp/CSharp language basics/README.md`
- `README/CSharp/CSharp language basics/sections/3. Variables and primitive types/3.2. Primitive types and literals and when overflow matters.md`

This domain assumes you already know the primitives and focuses on **conversion behavior and pitfalls**.

---

### 3) **General .NET runtime performance** (covered in `Fundamental Theories`)

Conversion performance is often dominated by runtime fundamentals:

- GC pressure (allocations, LOH/pinning)
- exceptions under load
- JIT inlining/devirtualization

For the deep runtime picture, see:

- `README/CSharp/Fundamental Theories/sections/2. NET architecture/2.3. GC basics for app developers.md`
- `README/CSharp/Fundamental Theories/sections/2. NET architecture/2.2. IL JIT tiered compilation AOT.md`

This domain calls out performance only where it is **conversion-specific** (boxing, parsing, culture, span slicing).

---

### 4) **Serialization deep dives** (belongs in a dedicated Serialization/JSON domain later)

Serialization is an ecosystem with its own correctness/performance rules (contract versioning, null handling, date/time rules, numeric policies, source generation).

In this Type Conversion domain we only cover the overlap:

- choosing stable, deterministic formats (`InvariantCulture`, `"O"` for timestamps)
- avoiding “pretty” strings as durable data
- keeping conversion rules explicit at boundaries

For now, treat serialization-specific conversion as a separate domain area.

---

### 5) **Interop marshaling** (belongs in an Interop/PInvoke domain later)

Interop conversion (marshaling) includes:

- blittable vs non-blittable types
- string encoding and pinning
- `Span<T>`/`Memory<T>` boundaries
- `nint`/`IntPtr` sizing issues

This domain only touches pointer-sized integers (`nint`/`nuint`) at a high level in `2.1`. Keep all marshaling conversion rules in a dedicated interop domain to avoid mixing concerns.
