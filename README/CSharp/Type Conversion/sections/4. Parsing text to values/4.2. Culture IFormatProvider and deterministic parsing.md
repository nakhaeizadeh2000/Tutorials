### 1) **CurrentCulture vs InvariantCulture** (correctness and “works on my machine” failures)

**Definition**

Most parsing/formatting APIs in .NET accept an `IFormatProvider` (typically a `CultureInfo`) that controls:

- decimal separator (`.` vs `,`)
- thousands separators
- date ordering (MM/dd vs dd/MM, etc.)
- month/day names, calendars, and more

There are two culture choices you must keep conceptually separate:

- **User culture** (`CultureInfo.CurrentCulture`): what the current user expects to *see and type*.
- **Deterministic culture** (`CultureInfo.InvariantCulture`): stable, language-agnostic formatting suitable for logs, protocols, and storage (when combined with stable formats/styles).

**Mentor rule**

- **UI/input meant for a human**: parse/format with `CurrentCulture` (or an explicit user-selected culture).
- **Wire formats / config / storage / telemetry**: parse/format with `InvariantCulture` and a stable format contract.

**Common mistake**

Code that parses with `CurrentCulture` but runs on machines with different locales:

- works on the developer laptop
- fails in production after deployment to servers in different regions
- produces wrong values without throwing if the format is ambiguous

**Example (runnable)**

```csharp
using System;
using System.Globalization;

static class Demo
{
    static void Main()
    {
        var us = CultureInfo.GetCultureInfo("en-US");
        var de = CultureInfo.GetCultureInfo("de-DE");

        // Same string, different meaning depending on culture:
        const string text = "1,234";

        Console.WriteLine(int.Parse(text, NumberStyles.Integer | NumberStyles.AllowThousands, us)); // 1234
        Console.WriteLine(int.Parse(text, NumberStyles.Integer, de));                               // 1234? (depends: "," is thousands or decimal)

        // Deterministic numeric parsing:
        Console.WriteLine(decimal.Parse("12.50", CultureInfo.InvariantCulture)); // always dot
    }
}
```

**Good to know**

- `CultureInfo.InvariantCulture` is not “US culture”. It’s a special, stable culture intended for programmatic interchange.

### 2) **NumberStyles / DateTimeStyles** (accept only what you mean to accept)

**Definition**

Parsing APIs often take a “style” flag enum to control which syntaxes are allowed:

- `NumberStyles` (for numeric parsing)
- `DateTimeStyles` (for date/time parsing)

**Why it matters**

Default parsing can be permissive in ways that surprise you:

- leading/trailing whitespace
- signs
- thousands separators
- exponent notation (depending on API and type)

You want to:

- accept *exactly* the formats you intend
- reject the rest deterministically

**Example: strict integer parsing**

```csharp
using System;
using System.Globalization;

static class Demo
{
    static void Main()
    {
        const string text = "1_000";

        // '_' is not accepted by numeric parsing; it's a C# literal feature only.
        Console.WriteLine(int.TryParse(text, NumberStyles.Integer, CultureInfo.InvariantCulture, out _)); // False

        // Strict, deterministic:
        Console.WriteLine(int.TryParse("1000", NumberStyles.None, CultureInfo.InvariantCulture, out var x)); // True
        Console.WriteLine(x);
    }
}
```

**Example: date parsing styles**

For date/time parsing, the styles interact with time zones and assumptions:

- `DateTimeStyles.AssumeUniversal`
- `DateTimeStyles.AdjustToUniversal`
- `DateTimeStyles.RoundtripKind`

If you’re parsing *protocol* timestamps, don’t use a loose “whatever the current culture does” approach. Prefer a stable format (see item 3).

**Good to know**

- When correctness matters, you usually want **explicit culture + explicit styles**, and often **exact formats** (e.g., `ParseExact` / `TryParseExact`) rather than “best effort parsing”.

### 3) **Round-trip formats** (`"O"` for DateTime/DateTimeOffset; stable serialization)

**Key idea**

For date/time values that you intend to round-trip through text, use a format that:

- encodes enough information to reconstruct the original value
- is culture-independent

The standard “round-trip” format specifier is `"O"` (“o”, ISO 8601-like).

**Mentor rule**

- Prefer **`DateTimeOffset`** for most business and distributed systems because it carries an offset and is harder to misuse than `DateTime`.
- When you must use `DateTime`, be explicit about `Kind` and conversions.

**Example (runnable)**

```csharp
using System;
using System.Globalization;

static class Demo
{
    static void Main()
    {
        var dto = DateTimeOffset.UtcNow;

        string text = dto.ToString("O", CultureInfo.InvariantCulture);
        Console.WriteLine(text);

        var parsed = DateTimeOffset.ParseExact(text, "O", CultureInfo.InvariantCulture, DateTimeStyles.RoundtripKind);
        Console.WriteLine(parsed);
    }
}
```

**Good to know**

- `"O"` is excellent for logs and wire formats when humans might also read it.
- For ultra-compact formats or domain-specific protocols, you may choose another contract—but then you must document and enforce it (usually with `TryParseExact`).

### 4) **User input vs wire formats** (different rules; don’t mix them)

**The split**

Treat these as two different products:

- **User input**: forgiving, localized, friendly error messages, can accept multiple formats.
- **Wire/storage**: strict, deterministic, versioned, round-trippable.

**Design guidance**

- Parse user input with `CurrentCulture` (or chosen culture), but normalize to a strong domain type immediately.
- For wire/storage, do not parse “random user strings”; parse **a contract** (stable format + invariant culture).

**Common mistake**

Saving user-formatted strings to a database and later trying to parse them back under a different culture.

**See also**

- Boundary mapping and strong types: `6.2. Boundary types: parse once, validate once, carry a strong type`

### 5) **Performance notes** (culture lookups and format parsing costs in tight loops)

**Reality check**

Culture-aware parsing is not “slow” in most apps. The performance cliffs are usually:

- throwing exceptions on expected failures
- allocating intermediate strings (`Split`, `Substring`, concatenation)
- repeated parsing instead of parsing once at the boundary

**High-volume parsing guidance**

- Use `TryParse` / `TryParseExact` (see `4.1`).
- Keep the `CultureInfo` instance in a local variable (avoid repeated lookups; improves clarity).
- Use `ReadOnlySpan<char>` overloads where available to avoid slicing allocations (see `4.3`).

**Thread-safety note**

`CultureInfo` instances are effectively immutable for reading and are safe to share; but don’t mutate global culture (`Thread.CurrentThread.CurrentCulture`) as a “conversion trick” in server code—this is a correctness bug factory.
