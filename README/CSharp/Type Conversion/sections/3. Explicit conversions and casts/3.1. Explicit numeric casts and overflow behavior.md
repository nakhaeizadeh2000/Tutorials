### 1) **Truncation and rounding** (float → int; toward zero; `Math` alternatives)

**Definition**

Casting from floating-point (`float`, `double`) to an integral type (`int`, `long`, etc.) is an **explicit numeric conversion** that:

- **truncates toward zero** (it does not round)
- can overflow if the value is outside the target range (behavior depends on `checked`/`unchecked`)

**When to use**

- When truncation is exactly what you intend (e.g., converting seconds to whole seconds by truncating fractional parts).
- When you already validated the range and want a fast conversion.

**Trade-offs**

- **Correctness**: truncation is easy to accidentally apply where you meant rounding.
- **Maintainability**: `(int)x` hides policy. A future reader can’t tell if truncation was intended.

**Prefer explicit intent**

- For rounding: `Math.Round`, `MathF.Round`
- For floor/ceil: `Math.Floor`/`Math.Ceiling` (double) and `MathF.*` (float)
- For clamping: `Math.Clamp` and then cast (still mind overflow policy)

**Example (runnable)**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        double x = 12.9;

        int trunc = (int)x;                          // 12
        int round = (int)Math.Round(x);              // 13 (banker's rounding by default)
        int floor = (int)Math.Floor(x);              // 12
        int ceil  = (int)Math.Ceiling(x);            // 13

        Console.WriteLine((trunc, round, floor, ceil));
    }
}
```

**Good to know**

- `Math.Round` defaults to **banker’s rounding** (to even). If you need “away from zero”, use `Math.Round(x, MidpointRounding.AwayFromZero)`.

### 2) **Overflow** and why it’s usually silent in `unchecked`

**What happens**

For integral conversions and arithmetic, C# has two overflow modes:

- **`unchecked`**: overflow wraps/truncates (no exception). Many codebases effectively run in unchecked mode unless configured otherwise.
- **`checked`**: overflow throws `OverflowException`.

For **explicit casts**, unchecked overflow can silently produce a value that looks valid but is wrong:

```csharp
long big = (long)int.MaxValue + 1;
int x = (int)big; // wraps/truncates in unchecked context
```

**When to use**

- `unchecked` is appropriate when you intentionally want wrap-around semantics (rare in business logic; common in hash functions or low-level code).
- For business logic, finance, identifiers, counts, sizes: prefer `checked` or explicit range validation.

**Common mistakes**

- Treating unchecked overflow as “it won’t happen”. In production, it *will* happen with new inputs, different sizes, or different load patterns.
- Converting lengths/sizes (`long`, `nint`) to `int` for APIs without validation.

### 3) **`checked` in modern code** (correctness-first arithmetic; where to apply it)

**Why `checked` matters**

Overflow bugs are among the most expensive to debug because they are:

- data-dependent
- often intermittent
- can corrupt downstream computations without obvious failures

**Where to apply `checked`**

- **At the boundary** where overflow becomes possible or meaningful (e.g., converting external inputs).
- Around arithmetic on values that can grow with data size (aggregations, counters, byte sizes, offsets).

**Patterns**

- Local `checked` blocks around critical code:

```csharp
checked
{
    int total = a + b;
}
```

- A project-wide policy (advanced): enabling overflow checks globally can be valuable in correctness-critical systems, but it may break legacy assumptions. This is a build configuration choice; apply intentionally.

**Example (runnable)**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        try
        {
            checked
            {
                int x = int.MaxValue;
                x += 1; // throws OverflowException
            }
        }
        catch (OverflowException)
        {
            Console.WriteLine("Overflow detected.");
        }
    }
}
```

**Performance note**

- In most application workloads, `checked` is not your dominant cost. Prefer correctness; optimize only if profiling shows it’s hot.

### 4) **Bit-level intent** (casts are not bit reinterpretation; use the right APIs)

**Key idea**

A numeric cast converts the **value**, not the raw bits. If you want bit reinterpretation, use explicit APIs:

- `BitConverter` for bytes ↔ primitives (be mindful of endianness)
- `System.Runtime.CompilerServices.Unsafe` / `MemoryMarshal` for advanced scenarios (rare; high-risk; requires deep understanding)

**Example: value conversion vs reinterpretation**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        float f = 1.0f;

        int valueConverted = (int)f;                 // 1 (value conversion)
        int bits = BitConverter.SingleToInt32Bits(f);// 1065353216 (bit pattern)

        Console.WriteLine((valueConverted, bits));
    }
}
```

**Mentor rule**

- If you find yourself “casting for bits”, stop. You almost certainly want `BitConverter.*Bits` APIs or explicit span/byte manipulation.

### 5) **Branch-friendly range checks** (patterns like `(uint)x <= max` for non-negative ranges)

**Why this exists**

Range validation is often required before a narrowing conversion (e.g., `int` → `ushort`, `int` → `byte`). A common pattern for non-negative ranges is to cast to `uint` and compare once:

- `(uint)x <= 65535u` validates \(0 \le x \le 65535\) in one comparison.

This works because negative values become very large when interpreted as `uint`, failing the check.

**Example (runnable)**

```csharp
using System;

static class Demo
{
    static bool TryToPort(int x, out ushort port)
    {
        if ((uint)x > 65535u)
        {
            port = default;
            return false;
        }

        port = (ushort)x;
        return true;
    }

    static void Main()
    {
        Console.WriteLine(TryToPort(443, out var p1));
        Console.WriteLine(p1);

        Console.WriteLine(TryToPort(-1, out _));     // false
        Console.WriteLine(TryToPort(70000, out _));  // false
    }
}
```

**Good to know**

- This is a micro-optimization *and* a clarity tool in low-level code. In most app code, a clear pair of comparisons is fine. Prefer whichever your team reads correctly.
