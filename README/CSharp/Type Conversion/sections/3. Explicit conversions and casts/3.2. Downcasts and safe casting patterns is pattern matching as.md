## 3.2. Downcasts and safe casting patterns (`is`, pattern matching, `as`)

1. **Prefer pattern matching** (`if (x is Foo foo)`) over raw casts
2. **When `as` is appropriate** (nullable refs; follow with null check)
3. **Avoid double casts** (use one check + one typed variable)
4. **InvalidCastException in hot paths** (exceptions are expensive under load)
5. **Design smell** (if you need many downcasts, reconsider polymorphism or data shape)

---

### 1) **Prefer pattern matching** (`if (x is Foo foo)`) over raw casts

**Definition**

A **downcast** converts a reference typed as a base class or interface to a more specific derived type. Unlike upcasts, downcasts can fail at runtime.

Modern C# gives you *pattern matching* that performs the runtime check **and** binds a strongly typed variable in one expression:

```csharp
if (x is Foo foo)
{
    // foo is Foo here
}
```

**Why this is the preferred pattern**

- **Single evaluation** of `x`
- **No exception** when the type doesn’t match
- **Clear control flow**: the success path is explicit
- Plays well with null-state analysis and avoids “maybe-null” warnings

**Example (runnable)**

```csharp
using System;

abstract class Shape;
sealed class Circle(double radius) : Shape { public double Radius { get; } = radius; }
sealed class Square(double side) : Shape { public double Side { get; } = side; }

static class Demo
{
    static void Main()
    {
        Shape s = new Circle(2);

        if (s is Circle c)
            Console.WriteLine(c.Radius);
        else if (s is Square sq)
            Console.WriteLine(sq.Side);
    }
}
```

**Good to know**

- For richer matching, use `switch` expressions with type patterns (still the same idea: check + bind, no exception).

---

### 2) **When `as` is appropriate** (nullable refs; follow with null check)

**What `as` does**

`as` performs a reference or nullable conversion that returns **null on failure** instead of throwing:

```csharp
Foo? foo = x as Foo;
if (foo is null) return;
```

**When it’s a good fit**

- You want the **“not this type”** path to be treated like “no value”, not as an exceptional condition.
- You’re in code where you already handle `null` cleanly (e.g., guard clauses).

**When not to use it**

- When a mismatch is a programmer error and you want to fail fast (e.g., internal invariants).
- When the result type is a **non-nullable value type** (it won’t compile except for nullable value types like `int?`).

**Example**

```csharp
using System;

interface IHandler { void Handle(); }
sealed class Handler : IHandler { public void Handle() => Console.WriteLine("ok"); }

static class Demo
{
    static void Main()
    {
        object candidate = new Handler();
        var h = candidate as IHandler;
        h?.Handle(); // safe: null if not compatible
    }
}
```

**Performance note**

`as` and `is` are both fast; choose based on clarity. The performance cliff is **exceptions**, not the cast operator.

---

### 3) **Avoid double casts** (use one check + one typed variable)

**The bug pattern**

This evaluates/casts twice and can also hide races if `x` can change between operations (rare, but possible with shared state):

```csharp
if (x is Foo)
{
    var foo = (Foo)x; // second check/cast
}
```

**Better**

```csharp
if (x is Foo foo)
{
    // use foo
}
```

**Mentor stress**

- “One check, one binding” is both more readable and less error-prone.

---

### 4) **InvalidCastException in hot paths** (exceptions are expensive under load)

**Reality**

Throwing `InvalidCastException` is slow:

- It captures stack information.
- It breaks branch prediction.
- It tends to appear in profiles as a CPU hotspot when used for control flow.

**Rule**

- If “not this type” is expected, use `is` / `switch` patterns and avoid exceptions entirely.
- If a mismatch is truly exceptional, a direct cast is fine—it fails fast and clearly.

**Boundary note**

Downcasts are sometimes unavoidable at boundaries (deserialization, reflection, plugin systems). Keep them **localized** and then convert to strong domain types.

---

### 5) **Design smell** (if you need many downcasts, reconsider polymorphism or data shape)

Frequent downcasts often indicate one of these issues:

- **Missing abstraction**: you need a virtual method or interface member.
- **Missing discriminant**: the data is really a “one-of” shape; use a closed hierarchy + pattern matching.
- **Leaky boundary types**: you’re passing DTOs/JSON shapes deep into the domain instead of mapping once at the edge.

**Refactoring direction**

- Add a virtual `Execute()`/`Accept(visitor)` style method when behavior belongs to the object.
- Use `switch` expressions over a closed set of derived types for simple mapping.
- Move conversion/typing logic to the boundary and keep the domain strongly typed (see `6.2. Boundary types: parse once, validate once, carry a strong type`).
