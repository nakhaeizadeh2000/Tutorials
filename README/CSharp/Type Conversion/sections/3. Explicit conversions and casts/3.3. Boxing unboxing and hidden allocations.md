## 3.3. Boxing/unboxing and hidden allocations

1. **What boxes** (value types to `object`/interfaces; closures can amplify)
2. **When unboxing fails** (type identity matters; `int` vs `long`)
3. **Performance impact** (heap allocation + GC + indirection)
4. **Avoiding boxing** (generic constraints, `Span<T>`, avoiding non-generic APIs)
5. **Common traps** (string concatenation with `object`, params arrays, non-generic collections)

---

### 1) **What boxes** (value types to `object`/interfaces; closures can amplify)

**Definition**

**Boxing** is the runtime operation of converting a **value type** (e.g., `int`, `DateTime`, a struct) into a reference typed as `object` or an interface. The runtime allocates a new object on the heap and copies the value into it.

Boxing happens when a value type is used in a context that requires a reference type, for example:

- passing a struct to a method that takes `object`
- storing a value type in a non-generic collection (`ArrayList`, `Hashtable`) (legacy)
- converting a value type to an interface it implements (e.g., `IFormattable`, `IComparable`) in a non-generic way

**Example (runnable)**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        int x = 123;

        object o = x;              // boxing allocation
        Console.WriteLine(o);      // still prints "123"

        IComparable cmp = x;       // boxing allocation (interface reference)
        Console.WriteLine(cmp.CompareTo(100));
    }
}
```

**Closures can amplify boxing (and allocations in general)**

Boxing is not the only allocation you can accidentally introduce. Capturing variables in lambdas can allocate a closure object; mixing that with boxing can create surprising GC pressure in tight loops.

Good to know:

- Prefer generic APIs (`IComparer<T>`, `IComparable<T>`, `EqualityComparer<T>`) to avoid boxing.
- Prefer `static` lambdas and avoid capturing when possible (this is more general allocation hygiene).

---

### 2) **When unboxing fails** (type identity matters; `int` vs `long`)

**Definition**

**Unboxing** extracts the value type out of a boxed object. It requires the boxed object to be **exactly** the target value type.

This means:

- Boxing an `int` and unboxing as `int` works.
- Boxing an `int` and unboxing as `long` fails (even though `int` can be converted to `long` normally).

**Example (runnable)**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        object boxedInt = 1; // boxed int

        int ok = (int)boxedInt;
        Console.WriteLine(ok);

        try
        {
            long nope = (long)boxedInt; // InvalidCastException
            Console.WriteLine(nope);
        }
        catch (InvalidCastException ex)
        {
            Console.WriteLine(ex.GetType().Name);
        }
    }
}
```

**Mentor stress**

- Unboxing is a runtime cast, not “numeric conversion”. If you need numeric conversion, unbox first (as the correct type), then convert.

### 3) **Performance impact** (heap allocation + GC + indirection)

Boxing has three main costs:

- **Allocation**: a heap object is created.
- **GC pressure**: more objects mean more frequent collections and more pause work.
- **Indirection**: accessing the value now goes through an object reference.

In isolation, one box is usually irrelevant. In **high-frequency paths** (parsing pipelines, telemetry, tight loops), boxing can become one of the dominant avoidable costs.

**Performance note**

- Boxing also kills some optimizations: you often lose inlining/devirtualization opportunities when everything becomes `object`.

---

### 4) **Avoiding boxing** (generic constraints, `Span<T>`, avoiding non-generic APIs)

**Prefer generic APIs**

Most of the BCL is designed so that if you stay in generic APIs, you avoid boxing:

- Prefer `List<T>` over `ArrayList`.
- Prefer `Dictionary<TKey,TValue>` over `Hashtable`.
- Prefer `IComparer<T>` and `IEqualityComparer<T>` over non-generic comparers.

**Prefer `TryParse` + typed values instead of “object pipelines”**

If you parse to `object`, you immediately make every consumer pay: casts, potential boxing, and less compile-time checking. Parse to a *specific type* or a *domain type*.

**Use spans to avoid allocation around conversions**

Spans don’t directly “fix boxing”, but they eliminate many string allocations that tend to coexist with boxed/object-heavy pipelines. For full parsing patterns with `ReadOnlySpan<char>`, see `4.3. ReadOnlySpan<char> overloads`.

**Avoid legacy patterns**

- **Legacy**: non-generic collections; APIs that accept `object` for “flexibility”.
- **Modern replacement**: generics + overloads + discriminated shapes (pattern matching) + result types.

---

### 5) **Common traps** (string concatenation with `object`, params arrays, non-generic collections)

**Trap: `params object[]`**

Many logging/formatting APIs accept `params object[]`. Passing value types will box, and the array itself allocates.

Modern alternatives:

- Use interpolated strings when you *actually need a string*.
- For high-volume logging, use structured logging APIs that support interpolation handlers (framework-dependent) to avoid work when disabled. (Keep the deep logging discussion outside this domain.)

**Trap: composite formatting**

```csharp
Console.WriteLine("x = {0}", 123); // boxes 123 + allocates params array
```

If this is in a tight loop, it can matter. If it’s occasional console output, it doesn’t.

**Trap: mixing generics and non-generics**

Accidentally calling a non-generic overload can reintroduce boxing. Prefer strongly typed overloads, and let analyzers help.

**Good to know**

- Boxing is not “bad”; it’s a tool. It’s bad when it’s accidental and repeated.
- If you see allocations in a profiler and you didn’t expect them, search for `object`, non-generic APIs, and `params`.
