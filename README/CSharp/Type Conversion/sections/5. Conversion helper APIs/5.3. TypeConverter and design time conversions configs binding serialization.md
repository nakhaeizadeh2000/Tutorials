## 5.3. `TypeConverter` and “design-time” conversions (configs, binding, serialization)

1. **What it’s good for** (config binding, component models, tooling)
2. **When not to use it** (core domain invariants; ambiguous global conversions)
3. **Alternatives** (explicit parsing + validation; custom JSON converters; source generators)
4. **Correctness guidance** (culture handling and error reporting)
5. **Maintainability** (discoverability and surprise conversions)

---

### 1) **What it’s good for** (config binding, component models, tooling)

**Definition**

`TypeConverter` (in `System.ComponentModel`) is a long-standing .NET mechanism that lets frameworks convert between **strings/objects** and a **target type** using a discoverable conversion service.

It exists primarily for:

- **component model / designers** (historically WinForms)
- **configuration & binding systems** that want a generic “string → type” conversion capability
- **tooling** that needs a common conversion story

**When to use**

- When you’re integrating with a framework that *already* uses `TypeConverter` (e.g., component model, certain binding/config scenarios).
- When you want a convention-based, pluggable conversion mechanism for *infrastructure* concerns.

**Good to know**

- `TypeConverter` is not inherently “deprecated”, but it is **not the modern default** for core domain conversion in most .NET 9+ apps.
- Many modern stacks prefer explicit parsing or serialization converters (see item 3).

---

### 2) **When not to use it** (core domain invariants; ambiguous global conversions)

**Mentor rule**

Do not put your domain invariants behind a globally discoverable “magic” converter unless the ecosystem forces you to.

Reasons:

- **Hidden behavior**: conversions may happen implicitly by framework code.
- **Ambiguous policies**: culture, whitespace rules, “what formats are accepted”, error messages—these become implicit and harder to test.
- **Surprising coupling**: a library consumer may trigger your converter without realizing it.

**Example smell**

- A “Money” type whose `TypeConverter` accepts many formats and silently normalizes them. That belongs in a **boundary** parser (or explicit domain factory), not as a global converter.

See also: `6.2. Boundary types: parse once, validate once, carry a strong type`.

---

### 3) **Alternatives** (explicit parsing + validation; custom JSON converters; source generators)

Choose the alternative based on *who* needs the conversion.

- **Your application/domain code**: prefer explicit `TryParse`/`Parse`/`TryCreate` APIs on the type, or a dedicated parser service.
- **JSON**: prefer a JSON converter (e.g., `System.Text.Json` converters) so the conversion is scoped to serialization.
- **High-performance pipelines**: prefer span-based parsing (`ReadOnlySpan<char>`) and avoid reflection where possible.

**Modern “domain-owned” pattern (recommended)**

```csharp
using System;
using System.Globalization;

public readonly record struct TenantId(Guid Value)
{
    public static bool TryParse(ReadOnlySpan<char> text, IFormatProvider? provider, out TenantId id)
    {
        // provider is unused here (Guid parsing is culture-invariant), but keeping it shows a consistent API design.
        if (!Guid.TryParse(text, out var g))
        {
            id = default;
            return false;
        }

        id = new TenantId(g);
        return true;
    }
}
```

**Source generation note**

Source generators are great when you need to avoid reflection and improve startup/perf (serialization, mapping). That’s a wider topic; don’t introduce generators just for parsing unless you have a measured need.

---

### 4) **Correctness guidance** (culture handling and error reporting)

**Culture**

If your converter parses numeric/date formats from strings, you must decide:

- **UI/user input**: `CurrentCulture` (or explicit user culture)
- **wire/config/storage**: `InvariantCulture` and stable formats

See `4.2. Culture, IFormatProvider, and deterministic parsing` for the full reasoning and examples.

**Error reporting**

`TypeConverter`-based conversion often throws exceptions on failure. That can be fine in configuration boot (fail fast), but it’s a bad fit for high-volume ingestion. For high-volume input validation, prefer `TryParse`-style APIs (see `4.1`).

---

### 5) **Maintainability** (discoverability and surprise conversions)

**Maintainability checklist**

- Keep conversion rules **documented and testable** (formats, styles, null handling).
- Prefer conversions that are **explicit at the call site** in your domain/business logic.
- If you must use `TypeConverter`, keep it thin and delegate to a single source of truth (usually a `TryParse`/`ParseExact` implementation owned by the type), so rules don’t diverge.

**Good to know**

- Global conversion mechanisms are easy to add and hard to remove. Treat them as infrastructure decisions, not local conveniences.
