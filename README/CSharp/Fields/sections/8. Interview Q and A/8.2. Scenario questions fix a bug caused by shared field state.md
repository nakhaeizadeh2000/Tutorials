## 8.2. Scenario questions: fix a bug caused by shared field state

1. **Aliasing bug** (two objects unexpectedly share the same mutable reference)
2. **Race condition** (static counter, cache, or singleton mutated concurrently)
3. **Good answer shape** (explain invariants, propose safe design, and mention perf trade-offs)

---

### 1) **Aliasing bug**
**Scenario**: Two objects appear independent, but they unexpectedly share a mutable reference stored in a field.

**Typical root cause**
- A field holds a reference type (e.g., `List<T>`, `Dictionary<,>`, `StringBuilder`, custom mutable type).
- A “copy” operation copies the reference, not the underlying object graph.

**Canonical deep reference**
- This topic (aliasing, reference semantics, defensive design) is covered in depth in:
  - «See `README/CSharp/CSharp Basic Object Oriented Programming/sections/3. Important points about objects/3.1. Reference semantics aliasing mutation defensive design.md` for the full treatment.»

**Minimal example + fix**

```csharp
using System;
using System.Collections.Generic;

public sealed class Basket
{
    // Mutable reference stored in a field.
    private readonly List<string> _items;

    public Basket(List<string> items) => _items = items;

    public void Add(string sku) => _items.Add(sku);
    public IReadOnlyList<string> Items => _items;

    // BUGGY "copy": shares the same list reference.
    public Basket ShallowCopy() => new(_items);

    // Safer: take a snapshot copy (explicit allocation).
    public Basket DefensiveCopy() => new(new List<string>(_items));
}

public static class Program
{
    public static void Main()
    {
        var a = new Basket(new List<string> { "A" });
        var b = a.ShallowCopy();
        b.Add("B");

        Console.WriteLine(string.Join(",", a.Items)); // A,B (surprise)
    }
}
```

**Mentor answer**
- Decide whether you want **sharing** or **independence**, then encode it:
  - For independence: defensive copies or immutable data structures.
  - For sharing: explicitly share a single owner object and expose behavior (methods) rather than raw lists.

**Performance note**
- Defensive copying allocates. Prefer it when correctness demands it, or when API boundaries require isolation.
- For high-throughput scenarios, consider immutability (records/value objects) or copy-on-write semantics.

---

### 2) **Race condition**
**Scenario**: A static field is mutated concurrently and sometimes produces wrong results, exceptions, or “impossible” states.

**Common root causes**
- Incrementing counters with `_count++` from multiple threads.
- Lazy initialization without synchronization (`_x ??= ...` in static property without a lock).
- Mutating non-thread-safe collections (`Dictionary<,>`, `List<T>`) concurrently.

**Canonical deep reference**
- For *why* this happens (visibility, reordering, tearing, `volatile`/`Interlocked` semantics), use the single deep reference:
  - «See `README/CSharp/Cuncurrent & Parallel/sections/4. Correctness, Testing, Diagnostics & Debugging in Concurrent Code/4.2. .NET memory model and visibility.md` for the full treatment.»

**Minimal example + fix**

```csharp
using System.Threading;

public static class GlobalStats
{
    private static int _count;

    // BUG: not atomic.
    public static void RecordBad() => _count++;

    // Good: atomic.
    public static void RecordGood() => Interlocked.Increment(ref _count);

    public static int Count => Volatile.Read(ref _count);
}
```

**Mentor answer**
- Pick the synchronization based on the invariant:
  - Single numeric state: `Interlocked`.
  - Multiple fields must change together: `lock`.
  - Shared mutable cache: `ConcurrentDictionary` or lock + clear ownership; also consider bounded cache/eviction.
  - One-time initialization: `Lazy<T>` or `LazyInitializer.EnsureInitialized`.

---

### 3) **Good answer shape**
Interviewers are testing whether you can reason from symptoms → invariants → design.

**A strong answer has this structure**
1. **Restate the invariant**: what must be true always? (e.g., “basket copy must not mutate original” / “count must equal number of calls”.)
2. **Identify the semantic trap**:
   - aliasing for reference fields, or
   - unsynchronized shared mutable static state (data race).
3. **Propose the simplest correct fix**:
   - defensive copy or immutability for aliasing,
   - `Interlocked`/`lock`/`Lazy<T>`/thread-safe collection for races.
4. **Call out trade-offs**:
   - allocations and GC pressure for copies,
   - contention and scalability for locks,
   - complexity and correctness risks for lock-free approaches.

**Note:**
- If you say “I’ll make it `volatile`”, you must also say: “`volatile` doesn’t make `++` atomic; it only helps with visibility.” That distinction is an expert signal.
