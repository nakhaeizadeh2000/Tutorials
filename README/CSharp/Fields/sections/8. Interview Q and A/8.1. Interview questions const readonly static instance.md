## 8.1. Common interview questions: const vs readonly vs static vs instance

1. **Explain differences** (meaning, runtime behavior, and where values are stored)
2. **Versioning and API design** (public const in libs, why it’s risky)
3. **Thread-safety framing** (static mutable fields, memory visibility, and safe publication)

---

### 1) **Explain differences**
Below is the “mentor answer” shape: precise definitions + the implication people actually get wrong.

**Instance field**
- One per object (`new` creates new storage).
- Lifetime: tied to the object’s lifetime (GC).
- Thread-safety: depends on how the object is shared; instance state can still be shared across threads.

**Static field**
- One per type (more precisely: per **closed generic type** and per **load context**).
- Lifetime: effectively the lifetime of the process/load context; can retain memory indefinitely.
- Thread-safety: if mutable and accessed concurrently, you must synchronize (or confine to one thread).

**`const`**
- A **compile-time constant**: the compiler substitutes the value into consuming code.
- Usually no runtime storage (conceptually a literal).
- Good for: truly universal values (e.g., `const int MaxRetries = 3;`) *within one compilation boundary*.
- Not good for: values you may want to change without recompiling consumers (see item 2).

**`readonly` (instance)**
- Assignment allowed only at declaration or in constructors.
- Helps enforce invariants and supports immutability-by-default designs.
- Not deep immutability: a `readonly` field holding a `List<T>` still points to a mutable list.

**`static readonly`**
- “Runtime constant”: initialized once at runtime (static initializer or static ctor), then reference/value cannot be reassigned.
- Useful for values that can’t be `const` (e.g., `Guid`, `DateTime`, `decimal` in some shapes, arrays, complex objects).

**Quick comparison table (high signal)**
- **Need compile-time literal?** `const`
- **Need one-time runtime init but stable afterward?** `static readonly`
- **Need per-instance invariant after construction?** `readonly` instance field
- **Need shared mutable state?** `static` (but design concurrency explicitly)

**Runnable example**

```csharp
using System;
using System.Threading;

public sealed class Demo
{
    // compile-time constant (inlined)
    public const int MaxRetries = 3;

    // runtime-initialized constant-like value
    public static readonly Guid AppId = Guid.NewGuid();

    // per-instance invariant
    private readonly string _name;

    // shared mutable state (must be synchronized if accessed from multiple threads)
    private static int _requests;

    public Demo(string name) => _name = name;

    public static void RecordRequest() => Interlocked.Increment(ref _requests);

    public override string ToString() => $"{_name} (AppId={AppId:N}, Requests={Volatile.Read(ref _requests)})";
}

public static class Program
{
    public static void Main()
    {
        var a = new Demo("A");
        var b = new Demo("B");
        Demo.RecordRequest();
        Console.WriteLine(a);
        Console.WriteLine(b);
    }
}
```

**Good to know**
- C# also has `readonly` **ref returns** and `readonly struct`—those are separate concepts. For readonly + structs performance and defensive copies, see section **6.3** in this domain.

### 2) **Versioning and API design**
This is where experienced engineers differentiate themselves: they answer with **binary compatibility** and **consumer recompilation**.

**The public `const` trap**
- If you ship a library with `public const int TimeoutMs = 5000;`, and later change it to 3000:
  - consumers that **don’t recompile** still run with **5000** because the value was inlined into their assemblies.

**Mentor guidance**
- In libraries: **avoid public const** unless it is *truly* a universal compile-time constant and you accept the “must recompile” contract.
- Prefer `public static readonly` for “constants” that may change across versions without forcing consumer recompilation.
- Prefer configuration (options pattern, environment, appsettings) for operational values; those should almost never be constants.

**Also avoid public fields**
- A public field (static or instance) is a frozen contract and hard to evolve. Prefer properties/methods for public API surface.

### 3) **Thread-safety framing**
Interviewers often want you to connect: **static mutable field** → **shared mutable state** → **synchronization required**.

**Correct framing**
- Static mutable fields are global shared state. Without synchronization, you get data races.
- The right primitive depends on the operation:
  - counter: `Interlocked`
  - multi-step invariant: `lock`
  - flag/publication: `volatile` / `Volatile` (carefully)

**Where to learn the “why” (single deep source)**
«See `README/CSharp/Cuncurrent & Parallel/sections/4. Correctness, Testing, Diagnostics & Debugging in Concurrent Code/4.2. .NET memory model and visibility.md` for the full treatment of visibility and reordering.»

**Performance note**
- Thread-safety is not “free”: locks add contention and context switching; atomics add cache-line traffic. Design to reduce sharing first (partitioning, immutability, confinement), then synchronize what remains.
