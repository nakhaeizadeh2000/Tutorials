## 1.2. Field initialization and execution order (instance vs static)

1. **Instance initialization order** (field initializers → base ctor → derived ctor; avoid calling virtuals)
2. **Static initialization order** (type initializer semantics, beforefieldinit, and first-touch costs)
3. **Failure modes** (type initialization exceptions, partial initialization, and how to keep startup predictable)

---

### 1) **Instance initialization order**
This is one of those topics that “seems obvious” until it breaks production code.

**The actual order for a `class` instance**
1. **All instance fields are set to `default`** (runtime).
2. **Base type instance field initializers run** (source order within base).
3. **Base constructor runs**.
4. **Derived type instance field initializers run** (source order within derived).
5. **Derived constructor runs**.

**Key mentor warning: don’t call virtual members from constructors**
- If a base constructor calls a virtual method, the override runs **before the derived fields are initialized**, so the override can observe partially-initialized state.
- This is a correctness hazard, not a “style” preference.

**Example: virtual call sees uninitialized derived fields (bug)**

```csharp
using System;

public abstract class Base
{
    protected Base()
    {
        // BAD: virtual call during construction.
        Initialize();
    }

    protected virtual void Initialize() { }
}

public sealed class Derived : Base
{
    private readonly string _name = "ready"; // Not initialized yet when Base ctor runs.

    protected override void Initialize()
    {
        Console.WriteLine(_name.Length); // NullReferenceException (because _name is still null here)
    }
}

public static class Program
{
    public static void Main()
    {
        _ = new Derived();
    }
}
```

**Better patterns**
- Use a **factory** (`Create(...)`) when initialization needs polymorphism.
- Use **non-virtual** initialization methods called after construction in the derived constructor.
- Prefer **composition** over inheritance when initialization ordering becomes tricky.

**Good to know**
- Field initializers run in **source order** within the type. Don’t rely on “alphabetical” or IDE order.
- Avoid using one field initializer that depends on another field initializer unless the ordering is obvious and deliberate.

### 2) **Static initialization order**
Static initialization matters because it affects:
- **first-use latency** (cold start),
- **deadlock potential** (if you lock/block inside a type initializer),
- **test determinism** (static state survives between tests in the same process),
- and **memory retention** (static roots live “forever”).

**Two relevant mechanisms**
- **Static field initializers** (e.g., `static readonly Foo X = ...;`)
- **Static constructor** (type initializer): `static MyType() { ... }`

**Execution rules (practical view)**
- The runtime ensures the type initializer runs **at most once**, **thread-safely**.
- The initializer runs **before the first use** of any static member *or* before the first instance is created (exact timing can vary if there is no explicit `static` constructor; see “beforefieldinit”).

**About `beforefieldinit`**
- If a type has *no explicit* static constructor, the compiler may mark it `beforefieldinit`, which allows the runtime to run static initialization **earlier** than “first use” (an optimization).
- You usually don’t need to micro-manage this. When timing matters, prefer an explicit `static` constructor or explicit initialization in app startup.

**Example: prefer simple static readonly initialization**

```csharp
using System;

public static class WellBehavedStatics
{
    // Good: cheap, deterministic, thread-safe publication.
    public static readonly Guid AppInstanceId = Guid.NewGuid();
}
```

**When you need lazy, use `Lazy<T>` (or explicit app init)**
- Prefer `Lazy<T>` when initialization is expensive and may never be needed.
- Prefer **explicit initialization** at startup for apps (dependency injection container setup, warm-up) so your latency is predictable.

See section **4.2** for the full mentor-grade patterns around `Lazy<T>`, static ctors, and “first-touch cost”.

---

### 3) **Failure modes**
Static and instance initialization can fail in different ways.

**TypeInitializationException**
- If static initialization throws, the runtime wraps it in `TypeInitializationException`.
- After that, the type is considered “failed” and future accesses keep throwing (within that load context).

**Partial initialization hazards**
- During a static ctor, you can observe partially-initialized static state if you re-enter the type via callbacks or other type initializers.
- Avoid taking locks, doing I/O, or calling into complex code from static constructors.

**Guidelines mentors insist on**
1. **Keep field initializers simple** (pure expressions, no I/O).
2. **Keep static initialization cheap** and **non-blocking**.
3. **Never block on async** in static constructors (`.Result` / `.Wait()`); it’s a deadlock vector. If you need async init, make it explicit at app startup.

**Performance note**
- Static initialization is effectively a one-time cost, but it can ruin p99 latency in server apps if it happens on a request path. Make “first-touch” predictable.
