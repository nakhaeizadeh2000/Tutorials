## 1.1. Understanding fields: storage, lifetime, and defaults

1. **What a field is** (a storage slot on an instance or a type; not an API surface)
2. **Where it lives** (instance fields in objects; static fields in type storage; stack locals are not fields)
3. **Defaults and initialization** (default(T), nullable context, initialization timing, and why “uninitialized” is a bug)

---

### 1) **What a field is**
A **field** is a named **storage location** that belongs to either:

- an **instance** (each object gets its own copy), or
- a **type** (a single shared storage location via `static`).

Fields are *state*. They are not, by themselves, a “contract” the way a public method/property is. That’s why mentors strongly prefer:

- **private fields** to store state, and
- **properties/methods** to expose behavior or a stable public surface.

**Why “fields are not an API surface” matters**
- **No interception point**: a field can’t validate, log, lazy-init, raise events, etc.
- **Binary compatibility**: changing a `public` field into a property is a breaking change for consumers (source + binary).
- **Invariants leak**: public mutable fields let callers create invalid states.

**Good to know**
- In IL and at runtime, fields are metadata + an offset (instance) or a location (static). The JIT can access them very efficiently.
- “Fields are faster than properties” is mostly a myth in modern .NET: simple properties are usually inlined. The cost is in what you *do* (allocations, locks, I/O), not in `get` vs direct field access.

**Common mistake**
- Treating fields as data-transfer shape in domain models (public fields everywhere). Use properties for public state; use fields privately.

---

### 2) **Where it lives**
**Instance fields**
- Live inside the **object** (for `class`) or inside the **containing storage** (for `struct` as a field/array element).
- Every instance has its own field values.

**Static fields**
- Live in **type-associated storage** (one per closed generic type, per `AssemblyLoadContext`).
- Exist for the **lifetime of the process / load context**. This is why static fields can “leak” memory by retaining references.

**Locals are not fields**
- Local variables are typically stored on the **stack** or in JIT-managed locations (registers, stack slots, or enregistered).
- Captured locals (closures) are lifted into compiler-generated **fields** on a hidden class. This is a key allocation trap in hot paths.

**Example: instance vs static**

```csharp
using System;

public sealed class Counter
{
    private int _instanceCount;          // one per object
    private static int _globalCount;     // one per type

    public void Increment()
    {
        _instanceCount++;
        _globalCount++;
    }

    public (int Instance, int Global) Snapshot() => (_instanceCount, _globalCount);
}

public static class Program
{
    public static void Main()
    {
        var a = new Counter();
        var b = new Counter();

        a.Increment();
        a.Increment();
        b.Increment();

        Console.WriteLine(a.Snapshot()); // (2, 3)
        Console.WriteLine(b.Snapshot()); // (1, 3)
    }
}
```

**Performance note**
- Instance field access is usually just pointer + offset. Static field access can include a **type initialization check** (first-touch). Keep expensive static initialization out of hot paths; see section **4.2** in this domain.

---

### 3) **Defaults and initialization**
In C#, fields always have a **definite value** at runtime:

- Value types: `default(T)` (all-zero bits, then “default” semantic)
- Reference types: `null`

So “uninitialized field” doesn’t mean “garbage memory” like in C/C++. Instead, the real bugs are:

- assuming a field has been set to a meaningful value when it’s still at `default`,
- mixing nullability annotations with runtime defaults, or
- relying on initialization order incorrectly.

**Nullable reference types (NRT)**
- With `#nullable enable`, the compiler warns if a non-nullable reference field might be `null`.
- You still must ensure proper initialization through constructors/initializers.

**Typical patterns**
- **Best default**: initialize in the constructor or via field initializer.
- For “must be provided by caller”: use `required` on properties (not fields) or a constructor parameter.

**Example: safe initialization**

```csharp
#nullable enable
using System;

public sealed class User
{
    private readonly Guid _id = Guid.NewGuid(); // always initialized
    private string _displayName;                // non-nullable by intent

    public User(string displayName)
    {
        // Guard clauses establish invariants early.
        _displayName = string.IsNullOrWhiteSpace(displayName)
            ? throw new ArgumentException("Display name is required.", nameof(displayName))
            : displayName;
    }

    public override string ToString() => $"{_id:N}:{_displayName}";
}
```

**Common mistakes**
- Leaving a field at `default` and “hoping” later code sets it (temporal coupling).
- Silencing nullability warnings with `null!` everywhere. Use it only when you truly establish the invariant by other means (e.g., DI framework sets it), and document/structure it so it’s hard to misuse.

**Good to know**
- Field initialization order (including base/derived and static init) is a common source of subtle bugs; the full ordering rules are in section **1.2**.
