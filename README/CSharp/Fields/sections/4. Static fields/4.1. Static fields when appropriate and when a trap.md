## 4.1. Static fields: when they’re appropriate (and when they’re a trap)

1. **Valid uses** (constants, caches with bounded growth, shared immutable singletons, counters/metrics)
2. **Hidden costs** (test coupling, order dependence, multi-tenant bugs, memory retention until process exit)
3. **Best practice** (prefer DI for dependencies; avoid static mutable state in libraries)

---

### 1) **Valid uses**
Static fields are not “evil” — they’re **global state**. That’s exactly why they’re powerful and dangerous.

Use static fields when the value is:

- **Truly global** for the process (or load context),
- **Stable** (immutable) or **explicitly synchronized**,
- and the lifetime “until process exit” is acceptable.

**Great fits**
- **`const`** / **`static readonly`** values that are conceptually constants.
  - Prefer `static readonly` for anything not allowed in `const` (see section **6.2** and **5.1**).
- **Shared immutable singletons** (e.g., reusable options objects).
- **Instrumentation counters** with `Interlocked` (simple and correct).
- **Caches** *only when you can bound them* (size limits / eviction / TTL).

**Example: static instrumentation counter**

```csharp
using System.Threading;

public static class RequestsMetrics
{
    private static long _total;

    public static void RecordRequest() => Interlocked.Increment(ref _total);

    public static long Total => Interlocked.Read(ref _total);
}
```

**Performance note**
- `Interlocked`-based counters are cheap; “global + lock” counters can become contention hotspots under load.
- If you need high-throughput metrics, consider batching (thread-local accumulation + periodic aggregation) — but only after measuring.

---

### 2) **Hidden costs**
Mentors care about static fields because they create hidden coupling:

1. **Test coupling**
   - Static mutable state leaks across tests in the same process.
   - Parallel test execution becomes flaky if tests touch the same statics.
2. **Order dependence**
   - Initialization might happen on the first request path (bad for latency).
   - If static initialization depends on environment or configuration timing, you get “works locally” bugs.
3. **Multi-tenant / multi-app model bugs**
   - In servers hosting multiple tenants, “static” is shared across tenants unless you isolate it by design.
4. **Memory retention**
   - Static references keep objects alive. A “cache” without eviction is a **memory leak by design**.

**Common mistake (static cache without bounds)**
- This often starts as “optimization” and ends as an OOM incident. See section **7.2** for patterns that fail in production.

---

### 3) **Best practice**
**Design guidance**
- **Apps** can sometimes use statics for convenience if lifetime is clear.
- **Libraries** should avoid static mutable state. It breaks composability and surprises consumers.

**Prefer dependency injection (DI) for dependencies**
- A static `HttpClient` field used to be a common recommendation; modern .NET encourages **`IHttpClientFactory`** in app code so lifetimes, DNS refresh, and policies are managed.
  - If you *must* use a static `HttpClient` in a small app, keep it **single** and **long-lived** and avoid per-request `new HttpClient()`.

**Thread-safety**
- If a static field is mutable, you must document and implement its synchronization strategy.
- For the fields-specific quick guide to visibility and safe publication, see section **4.3** (and the deep memory model reference it points to).
