## 4.3. Static fields in concurrent code: memory model basics you must know

1. **Visibility** (writes aren’t magically visible across threads without synchronization)
2. **Tools** (`lock`, `Interlocked`, `Volatile`, and immutable publication patterns)
3. **Common pitfall** (double-checked locking and “looks safe” patterns that aren’t)

### 1) **Visibility**
Static fields make sharing state *easy*, which means they make **data races** easy too.

**Core reality**
- Without synchronization, one thread can write to a static field and another thread can legally observe a **stale value**.
- “It works on my machine” is not evidence; it’s a typical symptom of undefined behavior under races.

**Common broken pattern: publish-before-fully-initialized**

```csharp
using System;
using System.Collections.Generic;

public sealed class BadPublication
{
    private static Dictionary<string, string>? _cache;

    public static Dictionary<string, string> Cache
    {
        get
        {
            // BUG: not synchronized. Another thread can see _cache != null while
            // the dictionary is still mid-construction or before other writes are visible.
            _cache ??= Build();
            return _cache;
        }
    }

    private static Dictionary<string, string> Build() => new(StringComparer.Ordinal);
}
```

**Mentor fix**
- If you need a lazily-built shared reference: use `Lazy<T>`, `LazyInitializer`, or a lock.
- If you need a mutable shared cache: design the concurrency behavior explicitly (lock, `ConcurrentDictionary`, or “single-writer” confinement).

### 2) **Tools**
Pick the tool that matches the operation’s shape:

- **`lock`**: correct default for *compound invariants* (multiple fields updated together).
- **`Interlocked`**: atomic operations on a single field (counters, flags with transitions).
- **`Volatile`**: visibility for simple flags / publication patterns; not for compound updates.
- **Immutable publication**: build an immutable object fully, then publish its reference once (often via `static readonly` or `Lazy<T>`).

**Example: static counter done correctly**

```csharp
using System.Threading;

public static class Metrics
{
    private static int _requests;
    public static int Requests => Volatile.Read(ref _requests);

    public static void RecordRequest() => Interlocked.Increment(ref _requests);
}
```

**Performance note**
- `Interlocked` is typically cheaper than `lock` for a simple counter, but don’t force it when you need multi-step invariants.

### 3) **Common pitfall**
**Double-checked locking** (DCL) is infamous because it’s easy to get subtly wrong.

**Modern guidance**
- If you just want lazy init: **prefer `Lazy<T>`**. It’s clear, correct, and fast enough for almost all cases.
- If you need custom behavior: use `LazyInitializer.EnsureInitialized`.

**Example: prefer `Lazy<T>`**

```csharp
using System;
using System.Collections.Generic;

public static class GlobalCache
{
    private static readonly Lazy<Dictionary<string, string>> _cache =
        new(() => new Dictionary<string, string>(StringComparer.Ordinal),
            isThreadSafe: true);

    public static Dictionary<string, string> Cache => _cache.Value;
}
```

**Good to know**
- `Lazy<T>` defaults to `ExecutionAndPublication` when you use the parameterless constructor; specifying `isThreadSafe: true` is explicit and readable.
