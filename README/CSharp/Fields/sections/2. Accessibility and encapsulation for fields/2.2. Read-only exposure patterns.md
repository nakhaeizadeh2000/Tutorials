## 2.2. Read-only exposure patterns (without leaking mutable state)

1. **Safe shapes** (`IReadOnlyList<T>`, `IReadOnlyCollection<T>`, `ReadOnlySpan<T>` where appropriate)
2. **Avoiding representation leaks** (don’t expose arrays/lists that callers can mutate)
3. **Perf notes** (avoid per-call copies; make allocations explicit when you need snapshots)

---

### 1) **Safe shapes**
“Read-only” should mean **callers cannot mutate your internal representation**. In .NET, there are multiple levels:

- **Read-only view (interface)**: callers can’t mutate *through the interface*, but the underlying collection may still change.
  - Examples: `IReadOnlyList<T>`, `IReadOnlyCollection<T>`, `IEnumerable<T>`
- **Read-only wrapper**: wraps a mutable collection, blocks mutation via wrapper methods, but still reflects internal mutations.
  - Example: `ReadOnlyCollection<T>`
- **Snapshot copy**: returns a new array/list each time; callers can mutate their copy safely.
  - Examples: `ToArray()`, `List<T>(...)`
- **Span-based view**: `ReadOnlySpan<T>` provides a fast, allocation-free view over contiguous memory (advanced).

**Mentor rule**
- If external callers must never affect your invariants, don’t hand them a reference to your mutable data.

**Example: typical safe exposure**

```csharp
using System;
using System.Collections.Generic;

public sealed class Order
{
    private readonly List<string> _items = new();

    public void AddItem(string sku)
        => _items.Add(string.IsNullOrWhiteSpace(sku) ? throw new ArgumentException("SKU required.", nameof(sku)) : sku);

    // Safe-ish: read-only interface (callers can't mutate through this member).
    // BUT internal code can still mutate; observers see changes over time.
    public IReadOnlyList<string> Items => _items;
}
```

**When `ReadOnlySpan<T>` is appropriate**
- You have a contiguous buffer (array, `string`, `stackalloc`, or memory from a pool) and you want **zero allocations** and **high performance**.
- It’s best for **internal** APIs or performance-sensitive libraries.

**Good to know**
- `ReadOnlySpan<T>` cannot be stored on the heap (it’s a `ref struct`). That’s a feature: it prevents lifetime bugs.

---

### 2) **Avoiding representation leaks**
Representation leaks happen when callers can:

- mutate your internals directly (breaking invariants),
- observe mutation timing they shouldn’t rely on,
- retain references longer than you expect (memory retention),
- couple your future refactorings to today’s layout.

**Classic leak (don’t do this)**

```csharp
using System.Collections.Generic;

public sealed class Bad
{
    public readonly List<int> Values = new(); // public mutable field: callers can do anything
}
```

**Better**
- Keep the field `private`.
- Expose a narrow API:
  - methods like `Add`, `Remove`, `TryGet`, `Enumerate`,
  - or a read-only view if you genuinely need to expose the contents.

**Arrays are especially easy to leak**
- Returning a `T[]` gives callers a direct mutation surface (`arr[0] = ...`).
- If you must expose an array-shaped view, prefer:
  - `ReadOnlySpan<T>` (advanced), or
  - `Array.AsReadOnly(array)` (wrapper) if you truly need a reference-type wrapper.

**Good to know**
- `IReadOnlyList<T>` is not deep immutability. It’s an *API restriction*, not a guarantee that data won’t change.

---

### 3) **Perf notes**
**Avoid per-call copies by default**
- `ToArray()` on every `get` is an allocation per call and can cause GC churn.

**When snapshots are the right choice**
- **Thread-safety**: you need a stable view without locks.
- **Temporal consistency**: you must guarantee the view won’t change while a caller iterates.
- **Security/robustness**: you must ensure callers can’t observe future mutations.

If you return a snapshot, make it explicit:

```csharp
using System.Collections.Generic;

public sealed class SnapshotExample
{
    private readonly List<int> _values = new();

    public IReadOnlyList<int> Values => _values; // live view

    public int[] GetValuesSnapshot() => _values.ToArray(); // explicit allocation
}
```

**Performance note**
- Prefer “live read-only view + explicit snapshot method” over “hidden snapshot allocation in a property getter”.
  - Properties are expected to be cheap; hidden allocations in getters are a maintainability/perf trap.
