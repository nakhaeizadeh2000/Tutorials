## 5.1. Constant fields (`const`): compile-time constants and inlining risks

1. **What `const` means** (compile-time substitution; no storage slot at runtime in most cases)
2. **Versioning trap** (changing a public const requires consumers to recompile; otherwise they keep the old value)
3. **What can be const** (primitives, enums, string, null; why most “config” should not be const)

---

### 1) **What `const` means**
`const` declares a **compile-time constant**. The key consequence is:

- The **compiler substitutes the value directly** into consuming code.
- In most cases there is no meaningful “storage location” to read at runtime (the value is embedded into IL where referenced).

**This is why `const` is about compilation, not about immutability.**

**Example**

```csharp
public static class HttpDefaults
{
    public const int DefaultTimeoutSeconds = 10;
}

// Anywhere else:
// the compiler emits the literal 10 at the call site (not a field read).
```

**When to use**
- **Truly universal constants**: mathematical constants, protocol magic numbers, compile-time switches that are *part of the contract*.
- **Private constants**: to name a value and improve readability without exposing a versioning contract.

**When not to use**
- “Configuration” that you may want to change without recompiling consumers (timeouts, feature flags, limits, environment-specific values).
  - Prefer `static readonly`, options/config systems, or DI for runtime configuration.

**Performance note**
- Since the value is embedded at the call site, `const` can be “fast” (no load), but that is almost never the deciding factor. Choose `const` for semantics and versioning, not micro-optimization.

---

### 2) **Versioning trap**
This is the mentor-grade gotcha: **public `const` in a library is a breaking *behavior* change unless consumers recompile.**

Why:
- Consumer assemblies compile the constant value into their own IL.
- If you ship an updated library with a different constant value, existing consumers keep using the **old** value until they recompile.

**Rule of thumb**
- In shared libraries: **avoid public `const`** except for values that are effectively immutable for the lifetime of the API.
- Prefer **`public static readonly`** for “runtime constants” so the value is read from the library at runtime.

**Good to know**
- This affects enums too (enum members are constants).
- It’s one of the most common “why didn’t my change apply?” issues in distributed systems with multiple services/packages.

---

### 3) **What can be const**
In C#, `const` is restricted to values the compiler can embed:

- Numeric primitives (`int`, `double`, etc.)
- `bool`, `char`
- `string`
- `enum`
- `null` (for reference types)

**Not allowed (common examples)**
- `Guid`, `DateTime`, `TimeSpan` (use `static readonly`)
- Arrays and most object graphs (use `static readonly` and ensure immutability)

**Example: runtime-constant pattern**
See section **6.2** (`static readonly`) for the full pattern and trade-offs.

**Common mistake**
- Using `const` for limits that might evolve (timeouts, cache sizes, max retries) in a library and later being surprised that consumers didn’t pick up the change. Use `static readonly` or configuration.
