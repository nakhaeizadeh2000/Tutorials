## 7.2. Patterns that look fine but fail in production

1. **Unbounded static caches** (memory leaks by design; require eviction/limits)
2. **Lazy init without synchronization** (races, double initialization, torn reads)
3. **“Readonly reference means immutable” fallacy** (it only freezes the reference, not the object)

---

### 1) **Unbounded static caches**
This is the classic “performance optimization” that slowly turns into an outage.

**Why it fails**
- A `static` cache is a **GC root**. Anything it references tends to stay alive until process exit.
- If the key space grows (user IDs, URLs, tokens, query strings…), the cache grows without bound.
- In servers, this becomes: **memory pressure → more GC → throughput drop → latency spikes → OOM**.

**Bad example**

```csharp
using System.Collections.Concurrent;

public static class BadCache
{
    private static readonly ConcurrentDictionary<string, byte[]> _cache = new();

    public static byte[] GetOrAdd(string key, Func<byte[]> factory)
        => _cache.GetOrAdd(key, _ => factory());
}
```

This looks thread-safe (it is), but it is not **capacity-safe**.

**Better options (modern .NET)**
- In **apps**, prefer `IMemoryCache` (bounded policies, eviction, expiration) via DI.
- In libraries, don’t hide global caches; let the host decide (DI + explicit lifetime).
- If you must keep a static cache, make it **bounded** and measurable:
  - max size / TTL,
  - metrics for hit rate and size,
  - explicit “clear” for tests.

**Performance note**
- Cache misses are often less expensive than the GC cost of retaining huge graphs. Optimize with measurement, not fear.

---

### 2) **Lazy init without synchronization**
The bug here is rarely “it throws”. The bug is “it sometimes corrupts data” or “it occasionally returns nonsense”.

**The trap**
- `x ??= new ...` is *not* magically thread-safe.
- Two threads can run the initializer concurrently, or one can observe partially-published state (visibility/reordering).

**Bad**

```csharp
using System.Collections.Generic;

public static class BadLazy
{
    private static Dictionary<string, string>? _map;

    public static Dictionary<string, string> Map
        => _map ??= new(StringComparer.Ordinal); // not thread-safe
}
```

**Preferred replacements**
- Use `Lazy<T>` for correctness + clarity.
- Or use `LazyInitializer.EnsureInitialized`.

See the fields-focused guidance in **4.2** and the deep memory-model explanation in  
`README/CSharp/Cuncurrent & Parallel/sections/4. Correctness, Testing, Diagnostics & Debugging in Concurrent Code/4.2. .NET memory model and visibility.md`.

**Performance note**
- A correct lock-free algorithm is harder than it looks. Prefer `Lazy<T>` unless profiling proves it’s a bottleneck.

---

### 3) **“Readonly reference means immutable” fallacy**
`readonly` on a reference field freezes the **reference**, not the referenced object.

**Example**

```csharp
using System.Collections.Generic;

public sealed class Basket
{
    private readonly List<string> _items = new();

    public void Add(string sku) => _items.Add(sku);
}
```

`_items` can’t be reassigned, but the list is still mutable.

**What to do instead**
- If you need true immutability, prefer:
  - immutable types (`string`, `Guid`, small `readonly struct` value objects),
  - `System.Collections.Immutable` collections (when the trade-offs fit),
  - or design APIs around **controlled mutation** (methods that preserve invariants).

**Good to know**
- “Deep immutability” is a property of the whole object graph, not a keyword on a single field.
