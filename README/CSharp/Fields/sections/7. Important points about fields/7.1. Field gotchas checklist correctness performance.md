## 7.1. Field “gotchas” checklist (correctness + performance)

1. **Avoid public mutable fields** (invariants, testability, and API evolution)
2. **Be explicit about thread-safety** (static mutable state needs synchronization or confinement)
3. **Understand const vs readonly** (compile-time inlining vs runtime initialization; versioning implications)

---

### 1) **Avoid public mutable fields**
This is the single most common “I didn’t know it was a problem” design trap.

**Why it’s a gotcha**
- **Invariants become unenforceable**: callers can assign any value at any time.
- **Versioning becomes painful**: you can’t add validation, lazy computation, or change representation without breaking callers.
- **Thread-safety becomes ambiguous**: public fields encourage unsynchronized access.

**Prefer**
- `private` fields + public methods/properties.
- If you truly need “data bag” types, prefer **records with init-only properties** or structs that are immutable-by-construction.

**Bad**

```csharp
public sealed class BadAccount
{
    public decimal Balance; // anyone can set negative, bypass invariants
}
```

**Better**

```csharp
using System;

public sealed class Account
{
    private decimal _balance;

    public decimal Balance => _balance;

    public void Deposit(decimal amount)
    {
        if (amount <= 0) throw new ArgumentOutOfRangeException(nameof(amount));
        _balance += amount;
    }

    public bool TryWithdraw(decimal amount)
    {
        if (amount <= 0) return false;
        if (_balance < amount) return false;
        _balance -= amount;
        return true;
    }
}
```

**Performance note**
- “Methods/properties add overhead” is rarely true in modern .NET; correctness and maintainability dominate. The real performance costs are allocations, contention, I/O, and algorithmic complexity.

### 2) **Be explicit about thread-safety**
Static fields, singletons, and shared caches are where races happen.

**Mentor rule**
- If multiple threads can access it and it’s mutable, you must pick a strategy: **lock**, **`Interlocked`**, **immutable publication**, or **confinement** (single-writer).

**Don’t duplicate the memory model here**
- For the deep model (reordering/visibility/volatile/Interlocked), see  
  `README/CSharp/Cuncurrent & Parallel/sections/4. Correctness, Testing, Diagnostics & Debugging in Concurrent Code/4.2. .NET memory model and visibility.md`.

**Quick guidance**
- Prefer `Lazy<T>` for lazy singleton-ish initialization (see section **4.2** in this domain).
- Prefer `ConcurrentDictionary<TKey,TValue>` only when your access pattern truly needs it; it’s not “free”.

### 3) **Understand const vs readonly**
This one is both correctness *and* deployment hygiene.

**The rule**
- `const` is a **compile-time substitution**.
- `readonly` is a **runtime value with a storage slot**.

**Mentor warning for libraries**
- Avoid `public const` for values that may change independently of consumers (e.g., default timeouts, feature flags). Consumers won’t see updates unless they recompile.
