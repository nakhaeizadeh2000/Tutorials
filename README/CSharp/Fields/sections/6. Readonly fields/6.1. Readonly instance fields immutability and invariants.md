## 6.1. `readonly` instance fields: immutability and invariants

1. **What it guarantees** (assignment only in declaration or constructors; supports “valid states only”)
2. **What it does NOT guarantee** (the referenced object can still be mutable; readonly is not deep immutability)
3. **Design guidance** (prefer immutable value objects; expose behavior, not mutability)

---

### 1) **What it guarantees**
An instance field marked `readonly` can only be assigned:

- at the **declaration site**, or
- inside an **instance constructor** (including a primary constructor body / generated ctor).

This is a powerful way to express and enforce **object invariants**:

- If something must never change after construction (identity, configuration, collaborators), make it `readonly`.
- It reduces accidental mutation, simplifies reasoning, and typically improves thread-safety *of the containing object’s structure*.

**Example: stable identity + stable collaborator**

```csharp
using System;

public sealed class Order
{
    private readonly Guid _id;
    private readonly IClock _clock;

    public Order(IClock clock)
    {
        _clock = clock ?? throw new ArgumentNullException(nameof(clock));
        _id = Guid.NewGuid();
    }

    public Guid Id => _id;
    public DateTimeOffset CreatedAt => _clock.Now;
}

public interface IClock { DateTimeOffset Now { get; } }
```

**Good to know**
- `readonly` is compile-time enforcement. The runtime doesn’t “freeze” memory; it enforces by preventing assignments in source.

---

### 2) **What it does NOT guarantee**
`readonly` is **shallow**:

- A `readonly` reference field means the **reference** won’t change.
- It does **not** make the referenced object immutable.

**Example: `readonly` reference to a mutable object**

```csharp
using System.Collections.Generic;

public sealed class Basket
{
    private readonly List<string> _items = new(); // reference is readonly, list is mutable
    public void Add(string sku) => _items.Add(sku);
}
```

If you want stronger guarantees:

- Prefer immutable types (`record`, immutable collections) or
- Keep the mutable object private and expose safe read-only views (see section **2.2**).

**Performance note**
- Immutability often trades CPU/allocations for simpler reasoning. Don’t “immutability-everything” a hot path without measuring.

---

### 3) **Design guidance**
Mentor-grade rules that scale:

1. **Make collaborators `readonly`**
   - Dependencies should not change after construction.
2. **Prefer `readonly` for identity and configuration**
   - IDs, names, bounds, options.
3. **Avoid “set later” fields**
   - Temporal coupling causes bugs. If something is required, force it in the constructor or use `required` properties (public API) instead of relying on an eventually-set field.

**Common mistakes**
- Using `readonly` as a substitute for thread-safety. It helps, but shared mutable state still needs a concurrency strategy (see **4.3** + the Concurrency domain memory model section).
