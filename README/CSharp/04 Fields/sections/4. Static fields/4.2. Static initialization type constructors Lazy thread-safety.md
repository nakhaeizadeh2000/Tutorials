## 4.2. Static initialization: type constructors, Lazy, and thread-safety

1. **Static ctor semantics** (runs once; thread-safe; can deadlock if you block on async or take locks badly)
2. **Lazy patterns** (`Lazy<T>`, `LazyInitializer`, and simple static readonly initialization)
3. **Perf guidance** (keep static initialization cheap; avoid heavy I/O; prefer explicit initialization in apps)

---

### 1) **Static ctor semantics**
A **static constructor** (`static MyType() { ... }`) is the runtime’s way of guaranteeing **one-time initialization**:

- It runs **at most once** per type (per `AssemblyLoadContext`).
- It’s **thread-safe**: the runtime serializes it so other threads wait until it completes.
- If it throws, the type is “poisoned” for the rest of the process/load context: future uses throw `TypeInitializationException`.

**Mentor warnings**
- **Avoid I/O** (network, disk, DB) in static ctors. This moves failures and latency into unpredictable code paths.
- **Avoid locks** (especially if they can be taken elsewhere during type initialization). Static init cycles are a classic deadlock source.
- **Never block on async** (`.Result` / `.Wait()`) in static ctors. If async init is required, do it explicitly in app startup.

**Good to know: “first-touch” cost**
- The first time a type is used, the runtime may need to run its type initializer. If that happens on a request path, you just created a p99 latency spike.

---

### 2) **Lazy patterns**
You usually want one of these patterns, in this order:

1. **Simple `static readonly`** for cheap, deterministic initialization.
2. **`Lazy<T>`** when initialization is expensive and might never be needed.
3. **`LazyInitializer.EnsureInitialized`** for special cases (custom storage, ref-return, etc.).
4. **Explicit initialization at app startup** when you want predictable cold-start behavior.

#### Pattern A: simple `static readonly` (best default)

```csharp
using System;

public static class Ids
{
    public static readonly Guid InstanceId = Guid.NewGuid();
}
```

- **Pros**: simple, safe publication, easy to reason about.
- **Cons**: always runs at some point (maybe earlier than you think if marked `beforefieldinit`).

#### Pattern B: `Lazy<T>` (thread-safe, clear)

```csharp
using System;

public sealed class ExpensiveService
{
    public ExpensiveService()
    {
        // pretend this is expensive
    }
}

public static class Services
{
    private static readonly Lazy<ExpensiveService> _service =
        new(() => new ExpensiveService(), isThreadSafe: true);

    public static ExpensiveService Service => _service.Value;
}
```

**Trade-offs**
- **Pros**: correct, readable, handles races, good for “maybe used” services.
- **Cons**: hides initialization latency behind first `Value` access (still a p99 risk if first-use is on a request).

#### Pattern C: `LazyInitializer.EnsureInitialized` (more control)

```csharp
using System.Threading;

public static class CacheHolder
{
    private static object? _lock;
    private static int[]? _data;

    public static int[] Data =>
        LazyInitializer.EnsureInitialized(ref _data, ref _lock, static () => new int[1024]);
}
```

**Mentor note**
- Only reach for this when `Lazy<T>` doesn’t fit (e.g., avoiding allocating a `Lazy<T>` object, or you need the pattern embedded in a larger type).

---

### 3) **Perf guidance**
Static initialization is a *design choice* with performance consequences.

**Rules that scale**
- Keep static initialization **pure** and **fast** (no I/O, no heavy reflection, no complex graph building).
- Prefer **explicit warm-up** at startup for server apps, so you control when work happens.
- Be intentional about caches: static caches live for the process lifetime unless you implement eviction and limits (see section **7.2**).

**Performance note**
- If you choose lazy init, prefer patterns that do **not allocate per call** and that do not create contention in high concurrency (e.g., `Lazy<T>` rather than manual double-checked locking).
