## 3.2. Sharing state intentionally: references, immutability, and defensive copying

1. **When sharing is fine** (immutable objects, interned strings, shared caches with clear ownership)
2. **When sharing bites** (mutable shared objects → accidental coupling, race conditions, and spooky action)
3. **Safer strategies** (immutability, copy-on-write, or explicit “owner” object that mediates mutation)

---

### 1) **When sharing is fine**
Sharing is not inherently bad; **uncontrolled, implicit sharing** is.

**Good reasons to share**
- **Immutable objects**: if the object graph can’t change, sharing is both safe and efficient.
- **Value objects** (especially `readonly record struct` / immutable `record class`): safe to pass around.
- **Interned / deduplicated data**:
  - `string` literals are interned by the runtime; sharing them is normal.
  - Carefully designed caches that store immutable results (e.g., parsed patterns) are OK.
- **Explicit shared service state** at the app layer (not library layer), with clear ownership and thread-safety rules.

**Mentor emphasis**
- Sharing is acceptable only when **mutations are impossible** or **mutations are centralized and synchronized**.

---

### 2) **When sharing bites**
Fields make sharing bugs easy because storing a reference in a field *feels* like storing “a value”, but for reference types it’s a pointer to shared state.

**Common failure modes**
- **Aliasing**: two objects unexpectedly reference the same mutable object; a mutation in one shows up in the other.
- **Temporal coupling**: callers rely on *when* a shared object changes (“it was empty earlier, now it isn’t”).
- **Concurrency bugs**: sharing a mutable object across threads without synchronization creates data races.

### 3) **Safer strategies**
#### A) Prefer immutability for shared data
If you must share, try to share **immutable** data:

```csharp
using System;

public sealed record CustomerProfile(string Id, string DisplayName);

public sealed class Customer
{
    // Safe to share: record is immutable by default design.
    private readonly CustomerProfile _profile;

    public Customer(CustomerProfile profile)
        => _profile = profile ?? throw new ArgumentNullException(nameof(profile));

    public string DisplayName => _profile.DisplayName;
}
```

**Good to know**
- Immutable sharing usually reduces the need for locks, which helps both correctness and scalability.

#### B) Defensive copying (only when you must)
If the input is mutable and you need to protect your invariants, copy the parts you need.

**Example: copy incoming list to avoid external mutation**

```csharp
using System;
using System.Collections.Generic;

public sealed class Team
{
    private readonly List<string> _members;

    public Team(IEnumerable<string> members)
    {
        ArgumentNullException.ThrowIfNull(members);
        _members = new List<string>(members); // defensive copy
    }

    public IReadOnlyList<string> Members => _members; // read-only view to prevent external mutation
}
```

**Trade-off**
- Defensive copies allocate and can be expensive for large data. Prefer immutability or ownership transfer when possible.

#### C) Centralize mutation behind an “owner”
If you need shared mutable state, enforce a single place that mutates it (single-writer), and expose read-only views or operations.

```csharp
using System;
using System.Collections.Generic;

public sealed class Inventory
{
    private readonly Dictionary<string, int> _stock = new(StringComparer.OrdinalIgnoreCase);
    private readonly object _lock = new();

    public void AddStock(string sku, int quantity)
    {
        if (string.IsNullOrWhiteSpace(sku)) throw new ArgumentException("SKU required.", nameof(sku));
        if (quantity <= 0) throw new ArgumentOutOfRangeException(nameof(quantity));

        lock (_lock)
        {
            _stock.TryGetValue(sku, out var current);
            _stock[sku] = checked(current + quantity);
        }
    }

    public bool TryReserve(string sku, int quantity)
    {
        if (string.IsNullOrWhiteSpace(sku)) throw new ArgumentException("SKU required.", nameof(sku));
        if (quantity <= 0) throw new ArgumentOutOfRangeException(nameof(quantity));

        lock (_lock)
        {
            if (!_stock.TryGetValue(sku, out var current) || current < quantity) return false;
            _stock[sku] = current - quantity;
            return true;
        }
    }
}
```

**Performance note**
- Locks are often fine when contention is low and critical sections are short. If this becomes hot, you can explore alternatives (concurrent dictionaries, sharding locks, actor/mailbox), but only after measuring.
