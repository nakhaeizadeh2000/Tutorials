## 3.1. Instance fields: each object gets its own state

1. **Per-instance independence** (two objects → two sets of instance fields)
2. **Copying references vs copying objects** (assignment copies references for classes; values for structs)
3. **Debugging mental model** (object identity, aliasing, and “why changing A changed B”)

---

### 1) **Per-instance independence**
An **instance field** belongs to an **object instance** (for `class`) or to the **value** stored in a variable/field/array element (for `struct`).

- For `class`: each `new` allocates a new object; that object contains its own instance fields.
- For `struct`: the “instance fields” live *inline* inside the struct value; copying the struct copies its fields.

**Mentor emphasis**
- “Each object has its own fields” is true — but **references inside those fields can still point to shared objects**. That’s where bugs usually come from (see 3.2).

**Example: two objects → two copies of instance fields**

```csharp
using System;

public sealed class Wallet
{
    private decimal _balance;

    public Wallet(decimal initial) => _balance = initial;

    public void Deposit(decimal amount) => _balance += amount;
    public decimal Balance => _balance;
}

public static class Program
{
    public static void Main()
    {
        var a = new Wallet(10);
        var b = new Wallet(10);

        a.Deposit(5);

        Console.WriteLine(a.Balance); // 15
        Console.WriteLine(b.Balance); // 10 (independent)
    }
}
```

---

### 2) **Copying references vs copying objects**
This is where “fields across multiple objects” becomes tricky:

- **Class variables copy references**. Assigning a variable (or passing a class to a method) copies a pointer-like reference, not the object.
- **Struct variables copy values**. Assigning a struct copies *all its fields* (bitwise copy / field-by-field copy).

Deep treatment of **reference semantics, aliasing, and mutation hazards** is already the canonical explanation in:
- See [3.1. Reference semantics aliasing mutation defensive design](<../../../03 CSharp Basic Object Oriented Programming/sections/3. Important points about objects/3.1. Reference semantics aliasing mutation defensive design.md>)

Here, the field-specific takeaway is:
- If an instance field is a **reference type**, copying the containing object reference does **not** duplicate the referenced object.
- If an instance field is a **struct**, copying the containing struct duplicates that field’s bits (and therefore its state).

**Example: aliasing through a reference field**

```csharp
using System;
using System.Collections.Generic;

public sealed class Cart
{
    private readonly List<string> _items = new();
    public void Add(string sku) => _items.Add(sku);
    public int Count => _items.Count;
}

public static class Program
{
    public static void Main()
    {
        var c1 = new Cart();
        var c2 = c1;          // copies the reference (alias!)

        c2.Add("ABC");

        Console.WriteLine(c1.Count); // 1 (same underlying object)
    }
}
```

**Good to know**
- This is *not* “a fields issue” — it’s object/reference semantics. But fields are how that state is stored, so field designs must anticipate aliasing.

---

### 3) **Debugging mental model**
When debugging “why did changing object A change object B”, mentors walk through:

1. **Are A and B the same reference?**
   - If yes: you have aliasing (`b = a;`).
2. **Do A and B hold a shared reference in a field?**
   - Example: both wallets reference the same `Account` object via a field.
3. **Is a struct being copied accidentally?**
   - Example: you get a struct via a property, mutate it, but you mutated a copy.

**Practical debugging tips**
- Log **reference identity** when needed:

```csharp
using System;
using System.Runtime.CompilerServices;

public static class DebugIds
{
    public static int Id(object o) => RuntimeHelpers.GetHashCode(o);
}
```

- Use the debugger to inspect whether two variables show the same object instance.

**Performance note**
- Misunderstanding copying rules often leads to “defensive copying everywhere”, which can allocate and churn GC. First, understand where aliasing actually happens; then choose one clear strategy (immutability, ownership, or explicit snapshots).
