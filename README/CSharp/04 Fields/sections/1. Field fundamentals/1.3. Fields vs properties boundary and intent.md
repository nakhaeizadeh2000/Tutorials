## 1.3. Fields vs properties: boundary and intent (no overlap, just the rule)

1. **Rule of thumb** (fields are implementation detail; properties are the public contract)
2. **Versioning** (public fields are a future-breaking promise; properties preserve evolution)
3. **Performance reality** (JIT inlines simple properties; “field vs property” is rarely the bottleneck)

---

### 1) **Rule of thumb**
- **Fields** are the *representation* of state (implementation detail).
- **Properties** are the *contract* (what you promise to callers).

If you’re writing anything beyond a tiny toy program, default to:
- `private` fields
- `public`/`internal` properties and methods

This isn’t “ceremony”; it’s how you keep your code evolvable and your invariants enforceable.

**Single deep reference**
- The full, in-depth discussion (including detailed examples and versioning/binary compatibility notes) is intentionally kept in the OOP domain:
  - See `README/CSharp/03 CSharp Basic Object Oriented Programming/sections/2. Creating classes and objects/2.1. Defining a class fields vs properties vs methods.md`.

Here in the Fields domain, we only apply the rule and add fields-specific guidance.

---

### 2) **Versioning**
Public fields are fragile for two reasons:

- **You can’t add logic later**: no validation, no lazy init, no change tracking, no threading policy.
- **Changing shape breaks callers**: converting `public int X;` to `public int X { get; set; }` breaks compiled consumers and source expectations.

**Mentor rule**
- In shared code (libraries, frameworks, “domain layer”): **never expose public mutable fields**.
- For performance in hot paths: you can still keep the field private and expose a thin property or method. If that isn’t enough, you’ll have a microbenchmark and a specific reason.

**Good to know**
- For *your own* internal code, `internal` fields can be acceptable when you control all consumers, but it still makes refactoring harder and can complicate invariants. Prefer `internal` properties if you expect evolution.

---

### 3) **Performance reality**
**In modern .NET**, simple property accessors (including auto-properties) are typically:
- inlined by the JIT in Release builds,
- optimized away when the value is constant or unused,
- not a measurable cost compared to allocations, cache misses, virtual dispatch, locks, I/O, or algorithmic complexity.

**Performance note**
- If your “property” does real work (allocates, locks, runs LINQ, does I/O, computes \(O(n)\)), that’s not a property problem—it's an API design problem. Make work explicit via a method (`ComputeTotal()`), and keep properties cheap and unsurprising.

**Common mistake**
- Using “fields for speed” as a blanket rule. In production code, it tends to create *more* bugs (invariants leak, thread-safety unclear) than it saves CPU cycles.
