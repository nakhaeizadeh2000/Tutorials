## 2.1. Access modifiers of fields: what’s allowed and what it means

1. **Visibility matrix** (`private`, `protected`, `internal`, `public`, and combinations like `protected internal`)
2. **Encapsulation** (keep mutable fields private; expose behavior and stable read-only views)
3. **Library hygiene** (prefer `internal` + tests, `InternalsVisibleTo`, and minimal public surface)

---

### 1) **Visibility matrix**
In C#, field visibility controls *who can directly touch your state*. Direct access is powerful and dangerous, so treat broad visibility as an explicit design decision.

**Access modifiers you can apply to fields**
- **`private`**: only within the containing type. This is the default and usually the best choice.
- **`protected`**: accessible in derived types. Use sparingly; it tightly couples derived classes to base representation.
- **`internal`**: accessible anywhere in the same assembly. Great for large apps where “module” = assembly.
- **`public`**: accessible everywhere. Rarely appropriate for fields (see below).
- **Combinations**:
  - **`protected internal`**: accessible either from derived types **or** within the same assembly (union).
  - **`private protected`**: accessible only from derived types **and** within the same assembly (intersection).

**Mentor rule**
- **Default to `private` fields** + expose behavior via methods/properties.
- If you think you need `protected` fields, ask: “Am I exposing representation instead of behavior?”

**Common mistake**
- Using `public` fields as “quick DTOs” in shared code. Even DTOs typically benefit from properties (`get; init;`) for versioning and serialization tooling.

---

### 2) **Encapsulation**
Encapsulation isn’t “hide everything” — it’s **protect invariants** and keep the mutation story explicit.

**Good pattern**
- Keep **mutable fields private**.
- Expose:
  - **methods** for actions/state transitions (`AddItem`, `Rename`, `Close`),
  - **read-only properties** for observing state (`Count`, `Id`, `IsClosed`),
  - and only allow mutation through well-defined paths.

**Why fields are risky as public surface**
- You cannot add validation or instrumentation later without breaking API.
- Callers can create invalid state at any time.
- Thread-safety becomes impossible to enforce from the outside.

**Example: encapsulated state**

```csharp
#nullable enable
using System;

public sealed class BankAccount
{
    private decimal _balance;

    public decimal Balance => _balance;

    public BankAccount(decimal openingBalance)
        => _balance = openingBalance < 0
            ? throw new ArgumentOutOfRangeException(nameof(openingBalance))
            : openingBalance;

    public void Deposit(decimal amount)
    {
        if (amount <= 0) throw new ArgumentOutOfRangeException(nameof(amount));
        _balance += amount;
    }

    public void Withdraw(decimal amount)
    {
        if (amount <= 0) throw new ArgumentOutOfRangeException(nameof(amount));
        if (amount > _balance) throw new InvalidOperationException("Insufficient funds.");
        _balance -= amount;
    }
}
```

**Performance note**
- A trivial property like `public decimal Balance => _balance;` is typically inlined; you are not paying meaningful overhead for “doing it right”.

---

### 3) **Library hygiene**
When you ship an assembly, **everything public becomes a promise**.

**Guidelines**
- Prefer **`internal`** for implementation details inside an assembly.
- Use **`InternalsVisibleTo`** for test projects rather than widening visibility to `public`.
- Keep base classes small; avoid `protected` fields in frameworks/libraries (it cements representation and makes refactoring painful).

**Good to know**
- Modern .NET toolchains (trimming/AOT) reward clear boundaries and minimal reflection-based access to internals. Encapsulation improves maintainability *and* makes publish-time optimization safer.
