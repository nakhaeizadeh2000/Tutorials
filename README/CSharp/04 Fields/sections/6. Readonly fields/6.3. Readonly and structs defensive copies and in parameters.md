## 6.3. Readonly and structs: `readonly struct`, defensive copies, and `in` parameters

1. **Why readonly matters for structs** (prevents hidden defensive copies and accidental mutation)
2. **`in` trade-offs** (can help for larger structs; can hurt if it forces temporaries—measure)
3. **Hot path rules** (avoid large mutable structs; prefer small immutable structs; watch boxing)

---

### 1) **Why readonly matters for structs**
Structs are copied by value. That’s the whole point—and the whole trap.

**Two “readonly” concepts that matter**
- **`readonly struct`**: the *entire instance* is immutable (from the compiler’s perspective). Instance members cannot mutate fields (unless you use `mutable` tricks; don’t).
- **`readonly` instance members** (methods/properties): guarantee they don’t mutate `this`, and allow the compiler/JIT to avoid defensive copies in more cases.

**Defensive copies: what they are**
- When you call a non-readonly instance member on a struct that the compiler treats as read-only (e.g., an `in` parameter, or a `readonly` field), the compiler may create a **copy** to preserve “read-only” semantics.
- That copy can be invisible but measurable on hot paths (extra copying, potentially extra memory traffic).

**Mentor guidance**
- Prefer **small, immutable structs** (often `readonly struct` / `readonly record struct`) for value-like concepts.
- Avoid large mutable structs. If it’s large and mutable, it probably wants to be a `class` (or an immutable struct with controlled construction).

**Example: value-like ID**

```csharp
public readonly record struct OrderId(Guid Value)
{
    public override string ToString() => Value.ToString("N");
}
```

**Good to know**
- A `readonly` field of a struct (e.g., `private readonly MyStruct _s;`) also influences how calls are made. Marking members as `readonly` can avoid hidden copies.

---

### 2) **`in` trade-offs**
`in T` passes a struct by **readonly reference**. The goal is to avoid copying when `T` is large.

**When `in` helps**
- `T` is large enough that copying it frequently is non-trivial.
- The callee mostly **reads** fields and calls **readonly members**.

**When `in` can hurt**
- The argument expression forces a temporary (the compiler must materialize a value to take its address).
- The callee calls non-readonly members, triggering **defensive copies**.
- The value would have been enregistered and cheap to pass by value, but `in` forces memory access.

**Mentor rule**
- Don’t use `in` “because it’s faster”. Use it after profiling shows it helps, or when you have a clear large-struct API boundary.

**Example: prefer simple by-value until proven otherwise**

```csharp
public readonly record struct Point(int X, int Y);

public static int ManhattanDistance(Point a, Point b)
    => Math.Abs(a.X - b.X) + Math.Abs(a.Y - b.Y);
```

If `Point` grows into a much larger struct and becomes hot, then consider:

```csharp
public static int ManhattanDistance(in Point a, in Point b)
    => Math.Abs(a.X - b.X) + Math.Abs(a.Y - b.Y);
```

---

### 3) **Hot path rules**
**Avoid boxing**
- Boxing happens when a struct is converted to `object` or an interface. That’s an allocation + copy.
- Prefer generics over `object`/interfaces in performance-sensitive paths.

**Avoid mutable struct properties**
- Mutating a struct through a property often mutates a **copy**, not the original (a classic bug).
- This is explained deeply in the OOP domain.  
  «See [2.4. Choosing class vs struct vs record vs record struct](<../../../03 CSharp Basic Object Oriented Programming/sections/2. Creating classes and objects/2.4. Choosing class vs struct vs record vs record struct.md>) for the full treatment of struct pitfalls and boxing.»

**Performance note**
- The biggest struct performance wins usually come from **data layout** (arrays of structs for locality) and **avoiding allocations**, not from micro-tuning `in`. Measure with BenchmarkDotNet if you’re optimizing a library/hot path.
