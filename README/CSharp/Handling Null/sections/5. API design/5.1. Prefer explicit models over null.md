## 5.1. Prefer explicit models over “null means many things”

1. **Domain types**: represent “optional” and “missing” intentionally (e.g., `Result`, discriminated shapes, dedicated types).
2. **Try-patterns**: `TryParse`, `TryGetValue`, and `out` results instead of returning null for control flow.
3. **Collections**: prefer empty collections over null collections (unless null is part of the contract).

### 1) **Domain types**: represent “optional” and “missing” intentionally
When you use `null` to represent multiple states, you push complexity onto every caller. A better approach is to make states explicit in your model.

Common domain states that should not all be encoded as `null`:
- **Not provided** vs **not applicable**
- **Not found** vs **found but empty**
- **Not loaded yet** vs **loaded and absent**
- **Invalid** vs **missing**

Modern modeling options (pick one and standardize):
- **Discriminated shapes** (via `record` hierarchies) when behavior differs by state.
- **Result types** when operations can fail in multiple ways (`NotFound`, `Forbidden`, `Invalid`, etc.).
- **Dedicated value objects** for validated inputs (`EmailAddress`, `CustomerId`) so “invalid” cannot exist inside the core model.

Example (result type for “not found” vs “invalid” without exceptions and without null):

```csharp
public enum LookupStatus { Found, NotFound, Invalid }

public readonly record struct LookupResult<T>(LookupStatus Status, T? Value)
{
    public bool IsFound => Status == LookupStatus.Found;
}

public static LookupResult<int> TryParsePort(string? raw)
{
    if (raw is null) return new(LookupStatus.NotFound, null);
    if (!int.TryParse(raw, out var port) || port is < 1 or > 65535)
        return new(LookupStatus.Invalid, null);

    return new(LookupStatus.Found, port);
}
```

**Good to know**
- If you’re building an API surface for many callers, a result type is often more maintainable than a “null + magic defaults” approach.

### 2) **Try-patterns**: return `bool` + `out` instead of null for control flow
Mentors push Try-patterns because they are:
- **Explicit**: “could fail” is in the signature.
- **Fast**: avoids exception costs for expected absence/invalid input.
- **Analyzer-friendly**: integrates well with NRT when annotated.

Canonical shape:

```csharp
using System.Diagnostics.CodeAnalysis;

public static bool TryGetCustomerId(
    string? raw,
    [NotNullWhen(true)] out string? customerId)
{
    if (string.IsNullOrWhiteSpace(raw))
    {
        customerId = null;
        return false;
    }

    customerId = raw.Trim();
    return true;
}
```

Callers get clean flow:

```csharp
if (!TryGetCustomerId(input, out var id))
    return;

Console.WriteLine(id.Length); // id is non-null here
```

**Common mistake**
- Returning `string?` and also using exceptions sometimes. Pick one policy per API.

**Performance note**
- `TryParse`/`TryGetValue` avoid exception overhead and reduce noise in traces and profilers.

---

### 3) **Collections**: prefer empty over null (unless null is part of the contract)
For collections, `null` rarely adds value and often adds bugs.

Recommended contract:
- A collection property/return should be **non-null** and may be empty.

```csharp
public sealed record Order(IReadOnlyList<string> Tags);

public static IReadOnlyList<string> NormalizeTags(IEnumerable<string>? tags) =>
    tags?.Where(t => !string.IsNullOrWhiteSpace(t)).ToArray()
    ?? Array.Empty<string>();
```

When `null` may be acceptable:
- When `null` means **“not loaded”** and empty means **“loaded but empty”** (but if you do this, document it and keep it consistent).

**Good to know**
- Avoid `new List<T>()` in defaults when you can return `Array.Empty<T>()` for zero-allocation empties.
