## 5.2. Public API contracts: parameter validation, return guarantees, and versioning

1. **Parameters**: accept `T?` only when you truly support null; validate early at boundaries.
2. **Returns**: don’t return null for “not found” if a Try-pattern or result type is clearer.
3. **Versioning**: changing nullability annotations is a breaking-change *signal*—treat it as public contract.

### 1) **Parameters**: accept `T?` only when you truly support null; validate early at boundaries
When you publish a method signature, you publish a contract.

- `void Save(User user)` means: **caller must provide a non-null `User`**.
- `void Save(User? user)` means: **null is a supported input**, and you define what it means.

Mentor guidance:
- Prefer **non-nullable parameters** for required values. It keeps core code simple and shifts validation to boundaries.
- Accept `T?` only when:
  - null is truly meaningful (optional argument), or
  - you are writing a boundary adapter for oblivious/legacy callers and you want to fail fast with a clear message.

Use the modern guard APIs:

```csharp
public static void Save(User user)
{
    ArgumentNullException.ThrowIfNull(user);
    // ...
}
```

If the contract is “non-empty string”, guard that explicitly:

```csharp
public static void SetDisplayName(string displayName)
{
    if (string.IsNullOrWhiteSpace(displayName))
        throw new ArgumentException("Display name must be provided.", nameof(displayName));
}
```

**Good to know**
- In ASP.NET Core and other frameworks, validation is often centralized (model validation, filters, pipeline). If you rely on that, document it and keep it consistent.

---

### 2) **Returns**: don’t return null for “not found” if a Try-pattern or result type is clearer
Returning `T?` for “not found” is sometimes fine, but it has two big downsides:
- It collapses multiple outcomes (“not found”, “not loaded”, “forbidden”, “error”) into one ambiguous `null`.
- It makes it easy for callers to forget handling, especially in oblivious contexts.

Prefer shapes that force explicit handling:

**Try-pattern** (best for “not found is normal” and no extra error info is needed):

```csharp
public static bool TryGetUserEmail(
    IReadOnlyDictionary<int, string> usersById,
    int id,
    out string email)
{
    if (usersById.TryGetValue(id, out var e))
    {
        email = e;
        return true;
    }

    email = string.Empty;
    return false;
}
```

**Result type** (best when you need “not found vs invalid vs error”):

```csharp
public readonly record struct Result<T>(bool IsSuccess, T? Value, string? Error)
{
    public static Result<T> Ok(T value) => new(true, value, null);
    public static Result<T> Fail(string error) => new(false, default, error);
}
```

Mentor rule:
- If the caller’s next step differs depending on why the value is missing, do **not** return `null`. Model the reason.

**Performance note**
- Try-patterns avoid exceptions on the “not found” path and can be very fast in tight loops.

---

### 3) **Versioning**: changing nullability annotations is a breaking-change signal
Even though nullability is “just warnings”, changing it changes:
- **Caller expectations**
- **Analyzer output**
- **Runtime behavior** (if callers were passing null and you now disallow it, you’ll start throwing)

Treat nullability as part of your public API:
- Changing a parameter from `T?` → `T` is a breaking change for callers who pass null.
- Changing a return from `T` → `T?` is a breaking change in *meaning* (callers now must handle null), even if binaries still run.

Mentor guidance for libraries:
- Be conservative and explicit.
- For large API surfaces, adopt a “nullable annotations are part of semantic versioning” rule.
