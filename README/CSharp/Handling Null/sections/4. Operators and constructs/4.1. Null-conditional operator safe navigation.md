## 4.1. Null-conditional operator (`?.`, `?[]`): safe navigation without hiding bugs

1. **What it does**: short-circuits member/index access when receiver is null.
2. **When it’s correct**: optional object graphs where “missing” is expected.
3. **When it’s dangerous**: hiding invariants that should be enforced (prefer guards + fail fast).

### 1) **What it does**: short-circuits member/index access when receiver is null
The null-conditional operators:
- **`?.`** for member access (`x?.Member`)
- **`?[]`** for indexer access (`x?[i]`)

They evaluate the *receiver* once, and if it is `null`, the entire access produces `null` (or the nullable default for the expression), without throwing.

Key semantic facts mentors expect you to know:
- `x?.Y` is *not* the same as `x == null ? default : x.Y` in all cases, but it is close enough for reasoning about null safety.
- The result is typically **nullable** because “missing receiver” yields “missing result”.
- It composes: `a?.b?.c` is allowed, but long chains are usually a design smell (see item 3).

Minimal example:

```csharp
public sealed record Address(string City);
public sealed record Customer(Address? Address);

public static string? TryGetCity(Customer? customer) =>
    customer?.Address?.City;
```

Indexer form:

```csharp
public static char? FirstCharOrNull(string? s) => s?[0];
```

**Good to know**
- `?.` does **not** catch exceptions thrown by the member itself. It only avoids the NRE from a null receiver.

---

### 2) **When it’s correct**: optional object graphs where “missing” is expected
Use `?.` when “missing” is part of the contract and you’re doing:
- **Best-effort enrichment** (optional fields, optional UI hints, optional telemetry)
- **Navigation of optional relationships** (e.g., `Customer` may have no `Address`)
- **“Try-get” style extraction** in read-only scenarios

Mentor framing:
- `?.` is best when the *output* is naturally optional too (`string?`, `int?`, etc.).
- Keep it **local**: use `?.` in a short expression close to where you handle the “missing” case.

Example (optional enrichment, not a required invariant):

```csharp
public static string FormatGreeting(string? displayName)
{
    // optional: if missing, choose a friendly default
    return $"Hello, {(displayName?.Trim() ?? "friend")}!";
}
```

**Performance note**
- `?.` is essentially a null check + branch. It’s fast and allocation-free.
- The real perf costs usually come from *what you do after*: string formatting, logging, allocations, I/O.

---

### 3) **When it’s dangerous**: hiding invariants that should be enforced
`?.` becomes dangerous when it silently changes semantics from “must exist” to “maybe exists”.

Smell:
- You have a long chain `a?.b?.c?.d` in core logic.
- You later default with `??` to “Unknown”, “N/A”, or `0` without recording that required data was missing.

Example of bug masking:

```csharp
// If order.Customer is required, this is not "safe"—it's hiding a broken invariant.
var email = order?.Customer?.Email ?? throw new InvalidOperationException("Missing customer email.");
```

Preferred approach:
- **Validate once** at the boundary (or construction) and keep core objects non-nullable.
- If a relationship is required, represent it as non-null (`Customer Customer`, not `Customer? Customer`).

Practical mentor rule:
- Use `?.` primarily at **boundaries** (parsing, mapping, formatting) or for **optional** features.
- In core domain logic, prefer **explicit invariants** + early guards.
