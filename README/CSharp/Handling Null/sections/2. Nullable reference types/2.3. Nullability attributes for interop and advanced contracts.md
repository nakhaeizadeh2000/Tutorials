## 2.3. Nullability attributes for interop and advanced contracts

1. **Interop reality**: consuming “oblivious” libraries and legacy APIs safely.
2. **Attributes toolbox**: `[NotNull]`, `[MaybeNull]`, `[AllowNull]`, `[DisallowNull]`, `[NotNullWhen]`, etc.
3. **Mentor note**: attributes are for expressing *truth* the compiler can’t infer—don’t use them to lie.

### 1) **Interop reality**: consuming “oblivious” libraries and legacy APIs safely
Nullable reference types (NRT) are only as good as the annotations you *actually have*. In production, you will interact with:
- **Legacy code** compiled with nullable disabled (the compiler treats it as “oblivious”).
- **Third-party packages** with incomplete/incorrect annotations.
- **Reflection / dynamic / interop** paths where the compiler can’t see invariants.

What the compiler does with “oblivious” APIs:
- It typically warns less (because it can’t trust the contract), which means **null bugs can still sneak in**.
- You must treat boundary values from oblivious APIs as **untrusted** and validate/normalize early.

Practical boundary pattern (normalize once):

```csharp
public static string NormalizeUserName(string? raw)
{
    if (string.IsNullOrWhiteSpace(raw))
        throw new ArgumentException("User name is required.", nameof(raw));

    return raw.Trim();
}
```

**Good to know**
- If you own the code, prefer **fixing annotations** over suppressing warnings.
- If you can’t fix upstream, wrap it: create a small adapter layer that validates and returns non-nullable types.

### 2) **Attributes toolbox**: express contracts the flow analysis can’t infer
These attributes live in `System.Diagnostics.CodeAnalysis` and are understood by the compiler’s nullability analysis.

Use-cases:
- **Try-patterns**: encode the relationship between a `bool` return and out-parameters.
- **Lazy initialization**: indicate that a field becomes non-null after a method succeeds.
- **Input/Output normalization**: declare “I allow null input but I never return null”.

The core set you’ll actually use:
- **`[NotNullWhen(true)]` / `[NotNullWhen(false)]`**: conditions on return value.
- **`[MaybeNull]`**: “this might return default/null even if `T` is non-nullable” (common in generic code).
- **`[NotNull]`**: member/out value is not null after the method returns (often used for fields/properties, but be careful: it must be true).
- **`[AllowNull]` / `[DisallowNull]`**: override nullability for setters/inputs.
- **`[DoesNotReturn]` / `[DoesNotReturnIf]`**: helps flow analysis for guard methods.

Example: Try-pattern with correct annotations:

```csharp
using System.Diagnostics.CodeAnalysis;

public static class Tokens
{
    public static bool TryParseToken(
        string? raw,
        [NotNullWhen(true)] out string? token)
    {
        if (string.IsNullOrWhiteSpace(raw))
        {
            token = null;
            return false;
        }

        token = raw.Trim();
        return true;
    }
}
```

Now callers get correct flow analysis:

```csharp
if (Tokens.TryParseToken(input, out var token))
{
    // token is treated as non-null here
    Console.WriteLine(token.Length);
}
```

Example: guard helper that teaches the compiler:

```csharp
using System.Diagnostics.CodeAnalysis;

public static class Guard
{
    public static void NotNull([NotNull] object? value, string paramName)
    {
        if (value is null)
            throw new ArgumentNullException(paramName);
    }
}
```

### 3) **Mentor note**: attributes must reflect reality (don’t lie)
Attributes are **a contract**. If you claim `[NotNull]` but you sometimes return null:
- You create **false confidence** for every caller.
- You cause **runtime NREs** that look “impossible” in code review.
- You make the codebase harder to reason about than if you had no annotations at all.

Mentor guidance:
- Prefer **structural fixes** first: validate earlier, redesign types, or wrap untrusted APIs.
- Use attributes only when you can state a **provable rule** the compiler can’t infer.

**Performance note**
- Attributes themselves don’t change runtime behavior; they change compile-time analysis.
- The runtime cost comes from your chosen strategy (exceptions vs Try-patterns, extra allocations from normalization, etc.).
