## 6.2. Concurrency + null: publication and visibility issues that look like null bugs

1. **Data races** can present as “sometimes null” (improper publication of references).
2. **Lazy init patterns**: choose safe patterns; don’t invent double-checked locking without deep knowledge.
3. **Mentor note**: if null appears “randomly”, suspect concurrency or lifetime bugs before blaming NRT.

### 1) **Data races** can present as “sometimes null” (improper publication of references)
When you see “it’s null only sometimes”, two categories dominate:
- **Contract/boundary bugs** (invalid data was accepted once)
- **Concurrency/lifetime bugs** (the object is observed before it’s fully initialized, or after disposal/reset)

In multi-threaded code, a reference becoming visible to another thread is called **publication**. If publication is not done safely, another thread can observe:
- a field still being `null`,
- a partially-initialized object graph,
- or a stale value (visibility issue).

Typical “sometimes null” patterns:
- A mutable field is assigned on one thread and read on another with no synchronization.
- A background initializer races with request processing.
- A cache uses a non-thread-safe dictionary.

Minimal example (unsafe publication):

```csharp
public sealed class ConfigHolder
{
    private Config? _config;

    public void Initialize(Config config) => _config = config; // no sync

    public string GetEndpoint()
    {
        // Might throw or return inconsistent results under data races
        return _config!.Endpoint;
    }
}

public sealed record Config(string Endpoint);
```

Mentor guidance:
- If `_config` is accessed across threads, either **publish it safely** (synchronization) or avoid shared mutable state.
- Don’t use `!` to “solve” concurrency: it hides the warning, not the race.

**Good to know**
- In ASP.NET Core, many services are singletons by default in DI patterns; singleton mutable state is a common source of these bugs.
- “It worked locally” is not evidence of thread-safety; races are schedule-dependent.

### 2) **Lazy init patterns**: choose safe patterns (don’t invent double-checked locking)
Lazy initialization is a common place where null meets concurrency.

Use cases:
- cache expensive computed value,
- delay I/O until first use,
- avoid startup cost for rarely-used features.

Safe approaches (choose based on requirements):
- **Thread-confined**: if a value is only used on one thread (e.g., UI thread, actor loop), simple `??=` is fine.
- **Duplicate computation allowed**: you can accept that two threads may compute the same value occasionally.
- **Single initialization required**: you must guarantee exactly-one factory execution and correct publication.

Recommended patterns:
- **`Lazy<T>`** for strong guarantees (simple and correct):

```csharp
private readonly Lazy<Config> _config = new(() => LoadConfig(), isThreadSafe: true);
public Config Config => _config.Value;
```

- **`LazyInitializer.EnsureInitialized`** for fields (low ceremony):

```csharp
using System.Threading;

private Config? _config;
private object? _configLock;

public Config Config => LazyInitializer.EnsureInitialized(
    ref _config, ref _configLock, static () => LoadConfig());
```

Mentor guidance:
- Avoid inventing double-checked locking unless you can prove correctness under the .NET memory model.
- Prefer a pattern that makes the synchronization obvious to reviewers.

**Performance note**
- `Lazy<T>` adds some overhead per access (usually tiny). Use it when correctness matters more than shaving nanoseconds.
- If a property is extremely hot, measure: you might prefer eager initialization or a specialized pattern.

### 3) **Mentor note**: if null appears “randomly”, suspect concurrency or lifetime bugs first
Before you blame nullable annotations:
- Check whether the object is **shared across threads**.
- Check whether it’s **mutated** after construction.
- Check whether there’s **a cache** with non-thread-safe access.
- Check whether disposal/reset happens while other code is still reading.

Debugging approach that works:
- Add logging around publication points (initialization, cache insert).
- Add metrics for “default/fallback taken”.
- Use stress tests that increase concurrency and randomize schedules.

Mentor rule:
- NRT helps you with **static contracts**, not runtime races. If the symptom is “sometimes”, assume scheduling and lifetime until proven otherwise.
