## 8.2. Performance checklist: dispatch costs, allocations, and scalability

1. **Prefer non-polymorphic fast paths in hot code** (generics, sealed types, specialization where it matters)
2. **Watch for boxing** (value types to interface; iterator allocations; delegate captures in default implementations)
3. **Keep interfaces small** (smaller surfaces are easier for humans and often easier for optimizers to reason about)

### 1) Prefer non-polymorphic fast paths in hot code

**Mentor framing:** Most applications are not bottlenecked by interface dispatch. But when they are, the fix is rarely “remove all interfaces” — it’s to design a **fast path** where the hot loop has a concrete, optimizable shape, while keeping abstraction at the boundary.

**Signals you’re in a hot path**
- You see the code on CPU profiles repeatedly (not once).
- It runs in tight loops (parsing, serialization, math, packet processing, high-throughput pipelines).
- You can quantify it: e.g., it’s a significant portion of request time under load.

**Practical strategies (C# 15 / .NET 9+)**
- **Keep polymorphism outside the loop**:
  - Resolve the implementation once, then run the loop against a concrete helper.
- **Use `sealed` types** for implementations where inheritance isn’t intended. This improves reasoning and can enable devirtualization.
- **Prefer generics** when the implementation type can be known at compile time (see **4.2** for the canonical explanation of “generics as a performance tool”).
- **Prefer `static abstract` interface members** for generic algorithms that need operators/factories (canonical in **3.3**).

**Minimal example (polymorphism at boundary, concrete in loop):**

```csharp
using System;

public interface IHasher
{
    int Hash(ReadOnlySpan<byte> data);
}

public sealed class XorHasher : IHasher
{
    public int Hash(ReadOnlySpan<byte> data)
    {
        int x = 0;
        foreach (var b in data) x ^= b;
        return x;
    }
}

public static class Hashing
{
    // Boundary is polymorphic (good for modularity)
    public static int HashMany(IHasher hasher, ReadOnlySpan<byte> data, int repetitions)
    {
        // But the hot work can be made concrete by checking known implementations once.
        // (In real systems, prefer better architecture than type checks; this is a teaching sample.)
        return hasher is XorHasher xor
            ? HashManyConcrete(xor, data, repetitions)
            : HashManyPolymorphic(hasher, data, repetitions);
    }

    private static int HashManyConcrete(XorHasher hasher, ReadOnlySpan<byte> data, int repetitions)
    {
        int sum = 0;
        for (int i = 0; i < repetitions; i++)
            sum += hasher.Hash(data);
        return sum;
    }

    private static int HashManyPolymorphic(IHasher hasher, ReadOnlySpan<byte> data, int repetitions)
    {
        int sum = 0;
        for (int i = 0; i < repetitions; i++)
            sum += hasher.Hash(data);
        return sum;
    }
}
```

**Good to know**
- Prefer designing your architecture so you don’t need `is` checks. The lesson is: **keep the loop shape simple** and avoid “accidental dynamic behavior” inside it.

### 2) Watch for boxing (and other hidden allocations)

**Boxing via interfaces (classic pitfall):**
- A **value type** (struct) implementing an interface can be boxed when used through that interface, allocating on the heap.
- Boxing often hides behind:
  - `IEnumerable` / `IEnumerator` (non-generic) usage,
  - storing structs in `object` or non-generic collections,
  - interface-typed fields/parameters.

**Minimal example (boxing):**

```csharp
public interface ICounter { int Next(); }

public struct Counter : ICounter
{
    private int _i;
    public int Next() => ++_i;
}

public static class Demo
{
    public static int Run(ICounter c) => c.Next(); // Counter passed here may box
}
```

**How to avoid it**
- Prefer **generic constraints**: `where T : struct, ICounter` and pass `T` by `ref` when appropriate (see **4.2** for the full canonical guidance).
- Prefer **generic collections** and generic `IEnumerable<T>` when enumeration is required.
- Be careful with **delegate captures** (closures allocate) and iterator blocks (`yield return` creates a state machine object).

**Allocator checklist**
- **Closures**: lambdas capturing locals allocate a display class.
- **Iterators**: `yield return` allocates an iterator object.
- **Async state machines**: `async` methods allocate a state machine object in some cases; `ValueTask` is not a “free win”.

### 3) Keep interfaces small

**Why small interfaces are faster (often indirectly)**
- Fewer members means fewer reasons to make contracts “fat”, fewer changes that break implementers, and less pressure to add default implementations (DIM).
- Small interfaces encourage **cohesion** and better caching/inlining opportunities at call sites.

**Design rules**
- Prefer **role interfaces** (“one reason to change”).
- If a consumer needs only 2 members, don’t force it to depend on 20.
- Split read vs write capabilities (`IReadableStore<T>` vs `IWritableStore<T>`), but don’t over-split to the point of noise.

**Performance note**
- The biggest performance wins typically come from **reducing allocations and unnecessary work**, not shaving nanoseconds off dispatch. Use the checklist to prevent the *real* traps from hiding behind abstraction.
