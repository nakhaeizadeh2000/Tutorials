## 2.3. Abstract base classes as shared implementation: power and pitfalls

1. **When shared code is worth it** (stable common behavior, cross-cutting invariants, internal frameworks)
2. **Fragile base class problem** (coupling, accidental overriding dependencies, versioning break risks)
3. **Performance reality** (virtual dispatch in hot paths; devirtualization limits; keep polymorphism off tight loops)

### 1) When shared code is worth it

**Thesis:** Abstract base classes are justified when you need **shared behavior with shared invariants** and you can enforce them centrally.

**Use an abstract base class when:**
- **There is real shared implementation** that would otherwise be duplicated (and duplication would diverge).
- The base can enforce **cross-cutting rules** (argument validation, state machine rules, idempotency guards).
- You want **partial customization** with a safe base algorithm (Template Method) where hooks are narrow and well-defined (see **2.2**).
- You’re building an **internal framework** (within one repo/team) where you can coordinate changes across implementers.

**Prefer interfaces + composition when:**
- You mostly want a contract but implementations are unrelated.
- You want multiple behaviors combined (“mix and match”) without a single shared state base.
- You want to avoid deep hierarchies and versioning fragility.

**Good to know:** Abstract bases are also a good place to provide **protected helpers** that keep derived code consistent, *as long as those helpers don’t become “secret coupling points”*.

### 2) Fragile base class problem (the real risk)

**Definition:** The fragile base class problem is when changes in a base class accidentally break derived classes because:
- Derived classes relied on undocumented behavior,
- Base class added new virtual calls / changed call order,
- Base class changed internal representation that derived code depended on indirectly.

**How it happens in production:**
- Base adds a new virtual method call in an existing method. A derived override runs in a new timing/context and breaks.
- Base changes a method from non-virtual to virtual, or changes which virtual members it calls.
- Base starts validating differently (throws exceptions) and derived code didn’t expect that.

**Mentor rules to reduce fragility**
- **Make virtual members rare and intentional**. If it’s virtual, treat it as a contract.
- **Document** preconditions/postconditions for every virtual/abstract method.
- Prefer a **non-virtual public method** that enforces invariants and calls a **protected abstract/virtual hook**:
  - This keeps invariants in the base and keeps overrides narrow.
- Avoid “kitchen sink” base classes. Keep bases **small and cohesive**.
- Consider making the base `internal` when possible (public inheritance is forever).

**Versioning note (libraries):**
- Public inheritance is a strong coupling. If you ship a public abstract base, you are implicitly supporting unknown derived types. That limits your ability to change internals, performance characteristics, and sometimes even bug fixes.
- If you need extensibility but want versioning safety, prefer **interfaces** (and optionally use **default interface members** cautiously for additive versioning; see **3.2**).

### 3) Performance reality: dispatch, inlining, and hot paths

**What costs in abstract bases:**
- Calls to `abstract`/`virtual` members are **dynamic dispatch**, which can prevent inlining and some optimizations.
- A base class often encourages **object graphs**, which can increase allocations and pointer chasing.

**What’s usually not the issue:**
- “Virtual calls are slow” is often overstated. For most application code, the dispatch overhead is tiny compared to I/O, allocations, and cache misses.

**When it matters:**
- Very tight loops, high-frequency per-element processing, parsing, or serialization.

**Strategies that keep design clean and fast:**
- Keep hot-path logic **non-virtual**; call a virtual method only at a coarse granularity.
- Use `sealed` types/methods where you can to help the JIT devirtualize.
- Consider **generic specialization** when polymorphism is hurting performance (see **4.2** for boxing/inlining strategies).

### Example: safe base algorithm + narrow hook (Template Method)

```csharp
using System;

public abstract class MessageHandler
{
    public void Handle(ReadOnlySpan<byte> payload)
    {
        if (payload.IsEmpty) throw new ArgumentException("Payload cannot be empty.", nameof(payload));

        // Invariants / orchestration live here:
        // - validation
        // - metrics
        // - error handling strategy (if any)
        ProcessCore(payload); // narrow customization point
    }

    protected abstract void ProcessCore(ReadOnlySpan<byte> payload);
}

public sealed class JsonMessageHandler : MessageHandler
{
    protected override void ProcessCore(ReadOnlySpan<byte> payload)
    {
        // Real parsing omitted: this is just showing shape.
        // Keep this method focused; avoid allocating unless you must.
        if (payload[0] != (byte)'{') throw new FormatException("Not JSON.");
    }
}
```

**Good to know:** Using `ReadOnlySpan<byte>` keeps the hot-path allocation-free. Your base class can enforce this shape consistently, which is difficult to guarantee via “convention” alone.
