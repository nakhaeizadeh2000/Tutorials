## 2.1. Abstract class fundamentals: what “abstract” means in C#

1. **Non-instantiable base type** (shared implementation + shared state option)
2. **Abstract vs virtual vs non-virtual** (required override vs optional customization vs sealed behavior)
3. **Accessibility and inheritance constraints** (`protected` members; protected constructors; base initialization rules)

### 1) Non-instantiable base type (shared implementation + optional shared state)

**Definition:** An **abstract class** is a class you **cannot instantiate**, intended to be a **base type**. It can provide:
- **Shared implementation** (common code),
- **Shared state** (fields/properties),
- **A common contract** (abstract members that derived types must implement).

This makes abstract classes a “**contract + partial implementation**” tool.

**When an abstract class is a good fit**
- **You need shared state or protected helpers** that multiple derived types must use.
- You’re building an **internal framework** with a stable base algorithm and clear extension points.
- You need to enforce invariants in base code while allowing derived “details” (see Template Method in **2.2**).

**When it’s usually the wrong tool**
- You only need a contract: prefer an **interface** (see **3.1**) to avoid inheritance coupling.
- You’re modeling domain concepts where inheritance tends to rot: prefer **composition** by default (see repo’s OOP domain for the broader guidance).

**Good to know**
- C# supports **single inheritance** for classes, so choosing an abstract base class consumes your “one base slot”.
- An abstract class can still implement interfaces, and derived classes inherit that.

### 2) Abstract vs virtual vs non-virtual (required override vs optional customization vs sealed behavior)

These are different “extension point strengths”:

- **Non-virtual**: implementation is fixed; safest for invariants and versioning.
- **virtual**: derived types *may* override; base provides a default.
- **abstract**: derived types *must* implement; base provides no implementation.
- **sealed override**: derived overrides and **stops further overrides** (useful to lock down behavior at a certain level).

**Mentor rule:** Prefer **non-virtual by default**. Make members virtual/abstract only when you are *explicitly* designing an extensibility point with a documented contract.

**Common mistakes**
- Making members `virtual` “just in case” → weakens invariants and complicates future changes.
- Mixing overridable members with base constructor logic → classic bugs (see **2.2** hazards).

**Minimal example: abstract vs virtual**

```csharp
public abstract class TextFormatter
{
    public string Format(string input)
    {
        if (input is null) throw new ArgumentNullException(nameof(input));
        input = Normalize(input);          // optional customization
        return ApplyCore(input);           // required customization
    }

    protected virtual string Normalize(string input) => input.Trim();
    protected abstract string ApplyCore(string input);
}

public sealed class UpperInvariantFormatter : TextFormatter
{
    protected override string ApplyCore(string input) => input.ToUpperInvariant();
}
```

Here `Format` is **non-virtual** to preserve invariants; `Normalize` is a safe optional hook; `ApplyCore` is required.

### 3) Accessibility and inheritance constraints (`protected`, protected constructors, base init rules)

**Key access modifiers in inheritance**
- `protected`: accessible in derived types, not by external callers.
- `protected internal`: accessible by derived types **or** same assembly.
- `private protected`: accessible by derived types **and** same assembly (tighter, often better for library design).

**Protected constructors**
- Use `protected` constructors to ensure only derived types can create instances.
- In abstract bases, protected constructors typically establish base invariants.

**Initialization rules you must internalize**
- Base construction happens **before** derived construction.
- Field initializers run in a defined order (base then derived).
- Avoid calling **virtual/abstract** members from constructors (full rationale in **2.2**).

**Good to know (modern C#)**
- If you’re using C# primary constructors in your project, keep in mind that base/derived initialization order and virtual-call hazards still apply; keep constructors cheap and deterministic.
