## 6.2. Marker interfaces and “semantic” interfaces: when they help and when they hurt

1. **Marker interfaces** (rarely necessary; often better as attributes or explicit registration)
2. **Semantic interfaces** (communicate intent; can guide DI/dispatch; document what the marker means)
3. **Alternatives** (attributes, generic constraints, discriminated unions/closed type sets, explicit capability properties)

### 1) Marker interfaces

**Definition:** A *marker interface* is an interface with **no members** (or no meaningful members) used only to “tag” a type, e.g. `ISerializable` (legacy) or `IMySpecialThing`.

**Why they exist:** Before attributes, source generators, and modern DI capabilities, marker interfaces were a convenient way to let code ask: “does this type belong to group X?”

**When marker interfaces can still be acceptable**
- **Very small internal codebases** where the meaning is stable and enforcement is centralized.
- **Generic constraints** where you want compile-time gating (but consider whether you actually need a marker vs a real capability).

**Common problems**
- **No discoverable semantics**: readers don’t know what the marker guarantees.
- **No enforcement**: a type can implement the marker but fail to satisfy the intended rules (there’s no API to implement).
- **Coupling and leakage**: marker becomes a cross-cutting global concept (“everything implements `ICacheable`”), making refactors harder.

**Legacy note:** Some framework marker interfaces are effectively legacy (e.g., binary serialization markers). In modern .NET, prefer explicit serializers and avoid unsafe binary serialization patterns.

### 2) Semantic interfaces

**Definition:** A *semantic interface* is an interface whose primary value is **meaning**, not methods. It communicates “this type participates in a protocol” even if the protocol is enforced elsewhere.

**When semantic interfaces are useful**
- **Architecture boundaries**: e.g. `ICommand`, `IQuery<TResult>` in a CQRS-style design where handlers enforce behavior.
- **DI registration conventions**: “all `IHostedService` implementations are background services” (this one is a real interface, not purely semantic).
- **Cross-cutting policies**: e.g. “these commands require idempotency” — but only if you can enforce it.

**Mentor rule:** If an interface has no behavioral surface, you must document:
- **What it guarantees**
- **Who enforces it** (compiler, analyzers, runtime checks, registration conventions)
- **What happens if you violate it**

**Example (semantic interface + enforcement):**

```csharp
public interface ICommand;

public sealed record CreateUser(string Email) : ICommand;

public interface ICommandHandler<in TCommand> where TCommand : ICommand
{
    ValueTask HandleAsync(TCommand command, CancellationToken ct);
}
```

Here the interface is semantic, but the *enforcement* is in the handler pipeline (validation, logging, retries, idempotency).

### 3) Alternatives (usually better in modern .NET)

**Attributes**
- Great for tooling, source generators, and declarative metadata.
- Trade-off: attributes are reflection-friendly but can be impacted by trimming/AOT if you rely on runtime reflection.

**Explicit registration / configuration**
- Prefer registering policies explicitly in your composition root rather than “magic scanning by marker”.

**Generic constraints (stronger than markers when you truly need compile-time gating)**
- If a generic algorithm needs a *capability*, use a real interface with members, or (for static capabilities) **static abstract members** (see **3.3**).

**Closed type sets / discriminated shapes**
- When the “set of cases” is closed, prefer a closed model (e.g., an `enum` + data or a sealed hierarchy) rather than markers. This improves exhaustiveness and readability.

**Explicit capability properties**
- Sometimes the simplest: a boolean/enum capability property, if it reflects real runtime state rather than type identity.

**Good to know (performance)**
- Marker/semantic interfaces are rarely a raw performance problem. The performance risk comes from *how you use them* (reflection scanning, repeated `is` checks in hot paths). If you need fast dispatch, design explicit lookups/caches and measure.
