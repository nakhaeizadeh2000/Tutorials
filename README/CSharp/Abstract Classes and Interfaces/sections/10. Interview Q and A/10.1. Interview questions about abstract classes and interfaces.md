## 10.1. Interview Q&A: abstract class vs interface, polymorphism, and explicit implementation

1. **Abstract class vs interface** (state, shared implementation, versioning, testing, and performance framing)
2. **When to use explicit interface implementation** (collision resolution, API hygiene, capability gating)
3. **Multiple inheritance with interfaces** (why C# forbids multiple base classes; how to design around it)
4. **Default interface members** (why they exist; when to avoid; versioning strategy)
5. **Performance questions** (interface dispatch vs virtual; boxing; avoiding polymorphism in tight loops; generics as an optimization)

These questions are common, but “good” answers are usually shallow. The mentor-grade answer ties **correctness**, **design intent**, **versioning**, and **performance** together—and uses small examples that demonstrate the actual runtime rules.

### 1) Abstract class vs interface (state, shared implementation, versioning, testing, performance)

**Core comparison (what you say first):**
- **Interface**: a **capability contract**. Best when you want *multiple unrelated implementations*, multiple inheritance of contracts, and clean DI seams.
- **Abstract class**: a **shared implementation + optional shared state** and **enforced overrides**. Best when you need a common algorithm, shared invariants, or internal frameworks.

**When an interface is the better default**
- You want **multiple implementations** and **multiple inheritance** of roles.
- You want to avoid the fragile base class problem and keep coupling low (see **2.3**).
- You want to keep types `sealed` by default and expose explicit extension points.

**When an abstract class is justified**
- You need **shared state** and **shared correctness constraints** (invariants) that must be enforced centrally.
- You want a **template method** where the base class controls the algorithm and derived types fill in small hooks (see **2.2**).
- You control the inheritance tree (internal code) and can evolve it safely.

**Versioning framing (important in libraries)**
- **Interfaces**: adding members is breaking for implementers unless you use **DIM** (see **3.2**). DIM helps versioning but adds behavior/dispatch complexity.
- **Abstract bases**: adding *abstract* members is breaking; adding *virtual* members can still be behavior-breaking if derived types relied on old behavior.

**Performance framing (don’t oversell)**
- Both interface and virtual dispatch can be fast; the real traps are usually **boxing/allocations** and **lost inlining** on hot paths (see **4.2**).
- If performance is critical and the set of behaviors is known, consider a **non-polymorphic fast path** (generics, `sealed`, or explicit `switch`), but only after measuring.

**Mini example you can explain quickly**

```csharp
public interface IClock
{
    DateTimeOffset UtcNow { get; }
}

public abstract class RateLimiterBase
{
    protected readonly IClock Clock;
    protected RateLimiterBase(IClock clock) => Clock = clock;

    public abstract bool TryAcquire();
}
```

**What to say about it:** The interface cleanly abstracts “time” for testability. The abstract base centralizes rate-limiter mechanics and enforces an override.

### 2) When to use explicit interface implementation

**Answer structure**
- Use it to **resolve name collisions**, to **hide plumbing**, and to implement **two different semantics** under the same member name (rare; document heavily).

**High-signal example (collision + API hygiene)**

```csharp
using System;

public interface IJsonSerializable
{
    string Serialize();
}

public sealed class User : IJsonSerializable
{
    public string Name { get; }
    public User(string name) => Name = name;

    // Public API remains intention-revealing:
    public string ToDisplayString() => Name;

    // Plumbing hidden from casual discovery:
    string IJsonSerializable.Serialize() => $"{{\"name\":\"{Name}\"}}";
}

public static class Demo
{
    public static void Main()
    {
        var u = new User("Ava");
        Console.WriteLine(u.ToDisplayString());

        var json = ((IJsonSerializable)u).Serialize();
        Console.WriteLine(json);
    }
}
```

**Mentor notes**
- Explicit implementations are **only callable through the interface** reference. That’s the point.
- Avoid having *different behavior* for “public method” vs “interface method” unless you have a strong reason; it confuses users and tests. See **7.1** for the canonical rules.

### 3) Multiple inheritance with interfaces

**What to say**
- C# forbids **multiple base classes** to avoid shared-state ambiguity (constructor order, state layout, invariants).
- Interfaces support multiple inheritance of **contracts**. It’s powerful, but keep roles cohesive (see **5.1**) and manage collisions deliberately (see **7.1**).

**Common follow-up**
- “Is this the same as multiple inheritance?”  
  No—interfaces don’t give you shared instance state. DIM adds *some* shared behavior but you must handle ambiguity carefully (see **5.2** and **3.2**).

### 4) Default interface members (DIM)

**What to say**
- DIM exists for **versioning**: add members to public interfaces without breaking old implementations.
- In application code, prefer **extension methods** or **composition**; avoid DIM-as-mixins.

**One-liner example**

```csharp
public interface IWidgetRenderer
{
    string Render();
    string RenderDebug() => $"[DEBUG] {Render()}"; // added later without breaking implementers
}
```

**Pitfalls**
- Diamond ambiguity and surprising behavior. Reference **3.2** for the full treatment.

### 5) Performance questions (dispatch vs boxing, hot loops, generics)

**What interviewers really want**
- You understand **what costs dominate**: allocations/boxing, missed inlining, iterator/delegate allocations—not “interfaces are slow”.

**Canonical points**
- **Boxing** occurs when a struct is used as an interface/object (allocates). See **4.2** for the full example and fixes.
- **Hot loop rule**: keep polymorphism out of the innermost loop when it matters; use generics/`sealed`/specialization.
- **Measure**: profile first; use BenchmarkDotNet for micro-benchmarks and real load tests for end-to-end.

**Best closing line**
- “Interfaces/abstract classes are design tools; I optimize for correctness and clarity, and only specialize for performance when profiling shows a bottleneck.”
