## 5.2. Avoiding the “diamond of death” in C# (and how DIM changes the discussion)

1. **Why multiple base classes are forbidden** (shared state ambiguity; constructor order; base invariants)
2. **What interfaces avoid** (no shared state by default; explicit composition)
3. **DIM caution** (default implementations can re-introduce ambiguity; be deliberate and document resolution)

### 1) Why multiple base classes are forbidden

**The problem is not “syntax”, it’s semantics.** If a class could inherit from two base classes, you immediately run into fundamental ambiguities:

- **Shared state ambiguity**: if both bases have fields, which copy exists? One? Two? How do they relate?
- **Constructor order**: in which order do base constructors run? What if both bases need invariants established first?
- **Member collisions**: if both bases provide `virtual void M()`, which one is the “real” base slot?
- **Fragile base class multiplied**: inheritance already couples derived types to base internals; multiple inheritance multiplies that coupling.

This is the classical “diamond problem”:

```
        A
      /   \
     B     C
      \   /
        D
```

If `A` has state, does `D` contain one `A` or two? Languages that support multiple inheritance have complicated rules (virtual inheritance, linearization). C# chose **simplicity and predictability**: *single* base class only.

**Mentor rule:** if you think you need multiple base classes, you almost always actually need **composition** or **interfaces**.

### 2) What interfaces avoid (and what they don’t)

**What interfaces avoid by default**
- **No instance fields** (so there’s no “which state wins?” question).
- **No constructor chaining** (interfaces don’t participate in object construction).
- **Multiple contracts** are explicit: `class X : IFoo, IBar`.

**What interfaces do not automatically solve**
- **Semantic ambiguity**: “this type claims two roles” can still become a design smell if the roles aren’t cohesive (see **5.1**).
- **Name collisions**: two interfaces can declare the same member signature with different meaning.
- **Versioning complexity**: interface inheritance can still be a breaking change (see **6.1**), unless you use DIM carefully (see **3.2**).

**Example: name collisions and how to keep them sane**

```csharp
public interface IReadable
{
    int Read(Span<byte> buffer);
}

public interface ILogReadable
{
    // Same signature, different semantics would be a design problem.
    int Read(Span<byte> buffer);
}
```

If those two `Read` methods mean different things, you created an API trap. Fix it by renaming or separating responsibilities (e.g., `ReadLogEntry`).

When collisions are *legit* (same signature but truly different contracts), use **explicit interface implementation** to force the caller to choose a view (canonical treatment in **7.1**).

### 3) DIM caution (default interface members can re-introduce ambiguity)

With DIM, interfaces can now contain behavior. That’s helpful for versioning, but it can also reintroduce “which implementation wins?” style issues.

**Ambiguity example**

```csharp
public interface IHasName
{
    string Name { get; }
    string Format() => $"Name={Name}";
}

public interface IHasId
{
    int Id { get; }
    string Format() => $"Id={Id}";
}

public sealed class User : IHasName, IHasId
{
    public string Name { get; } = "Alice";
    public int Id { get; } = 42;

    // Required: resolve ambiguity explicitly.
    public string Format() => ((IHasName)this).Format() + ", " + ((IHasId)this).Format();
}
```

**Mentor guidance**
- If multiple defaults could apply, **force an explicit choice** in the implementing type.
- Keep DIM defaults **small and obviously correct** (see **3.2**). If it’s complex, prefer an abstract base class or composition.

**Performance note**
- Resolving ambiguity via explicit interface calls (`((IHasName)this).Format()`) is usually not hot-path code. If it is, step back and design a clearer contract rather than stacking defaults.
