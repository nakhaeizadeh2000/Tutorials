## 5.1. Multiple interface implementation: modeling multiple roles safely

1. **Multiple roles, one type** (capabilities vs identity; keep responsibilities separated)
2. **Ambiguity management** (member name collisions; avoid same member names with different meaning)
3. **Design heuristics** (prefer composition if “implements everything”; use adapters/decorators to keep types focused)

### 1) Multiple roles, one type

**Definition:** In C#, a class/struct can implement **multiple interfaces**. This is the language’s intended way to model “this type can do multiple things” without inheriting state from multiple base classes.

**Mentor framing: roles vs identity**
- **Identity** is “what this object *is*” (often your domain type).
- **Roles/capabilities** are “what this object *can do*” (interfaces).

When a type implements many interfaces, ask: are these **cohesive roles** around one identity, or is this type becoming a “kitchen sink”?

**When it’s a great fit**
- **Adapters**: one type adapts a dependency to multiple caller expectations.
- **Cross-cutting capabilities**: e.g., `IDisposable` + domain interface; `IAsyncDisposable` where needed.
- **Framework integration**: e.g., a hosted service implements `IHostedService` and your own `IHealthCheckable`.

**When it’s a smell**
- Implementing interfaces that represent **unrelated responsibilities** (SRP violation).
- Implementing both “high-level policy” and “low-level mechanism” in one type (hard to test, hard to evolve).

**Example (one identity, multiple capabilities):**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

public interface IStartable
{
    Task StartAsync(CancellationToken cancellationToken);
}

public interface IStoppable
{
    Task StopAsync(CancellationToken cancellationToken);
}

public sealed class BackgroundPoller : IStartable, IStoppable, IAsyncDisposable
{
    private readonly PeriodicTimer _timer = new(TimeSpan.FromSeconds(5));
    private CancellationTokenSource? _cts;
    private Task? _loop;

    public Task StartAsync(CancellationToken cancellationToken)
    {
        if (_loop is not null) throw new InvalidOperationException("Already started.");

        _cts = CancellationTokenSource.CreateLinkedTokenSource(cancellationToken);
        _loop = RunAsync(_cts.Token);
        return Task.CompletedTask;
    }

    public async Task StopAsync(CancellationToken cancellationToken)
    {
        if (_cts is null || _loop is null) return;

        await _cts.CancelAsync().ConfigureAwait(false);
        await _loop.WaitAsync(cancellationToken).ConfigureAwait(false);
    }

    private async Task RunAsync(CancellationToken token)
    {
        while (await _timer.WaitForNextTickAsync(token).ConfigureAwait(false))
        {
            // Poll work…
        }
    }

    public async ValueTask DisposeAsync()
    {
        if (_cts is not null)
            await _cts.CancelAsync().ConfigureAwait(false);

        _timer.Dispose();
        _cts?.Dispose();
    }
}
```

**Good to know:** `PeriodicTimer` is the modern replacement for many `System.Threading.Timer` use cases (see `Cuncurrent & Parallel` for deep scheduling guidance).

### 2) Ambiguity management (member name collisions)

**The problem:** Two interfaces can declare members with the same name/signature but **different intent**. That creates ambiguity for readers and for API design.

**Avoiding collisions (best option)**
- Use **capability names** and specific members: `IJsonSerializer.Serialize(...)` vs `ISerializer.Serialize(...)`.
- Prefer **separate methods** with intent-revealing names over overloaded “do everything” methods.

**Handling collisions (when you must)**
- Use **explicit interface implementation** to keep both contracts but avoid polluting the public surface.
- Keep behavior consistent: don’t make the same-named members do wildly different things depending on cast.

For the canonical treatment of explicit implementation and collision resolution, see **7.1**.

### 3) Design heuristics (composition, adapters, decorators)

**Rule 1: if it “implements everything”, it probably shouldn’t.**
- Split roles into smaller components and compose them.
- Use a **facade** that coordinates smaller services rather than inheriting/implementing a giant surface.

**Rule 2: prefer adapters/decorators over multi-role “god types”.**
- **Adapter**: translate one interface to another.
- **Decorator**: wrap an implementation to add behavior (logging, caching, retries) without changing the core.

**Rule 3: keep interfaces small and stable.**
