## 3.4. Interface member forms: `private` helpers, `static`, `virtual`/`sealed` defaults, static abstract (overview)

### 1) Default interface methods (DIM)

1. **Purpose**: evolve interfaces without breaking implementers—see [3.2](<./3.2. Default interface members DIM.md>).
2. **Dispatch**: instance default members use **interface dispatch**—mind hot-loop costs.

### 2) Private interface methods

1. **Use** to share implementation between default members **without widening** the public surface.
2. **Not** the same as explicit interface implementation—private helpers are about **factoring**, not hiding public members.

### 3) Static abstract members in interfaces

1. See [3.3](<./3.3. Static abstract members in interfaces generic math.md>) for generic math / operator patterns.
2. **Perf**: can avoid boxing/dynamic patterns when modeled carefully.

### 4) Modifiers on overrides of DIM

1. `virtual`/`sealed` on overrides follows normal override rules—watch for **diamond** scenarios with multiple inheritance of interfaces.
2. **Testing**: default methods can surprise mock frameworks—design explicit seams for critical behavior.

### 5) Modern guidance (C# 15 era)

1. Keep interfaces **small** and **stable**; use DIM sparingly and intentionally.
2. Prefer **extension methods** when behavior is not part of the contract evolution story (trade-offs: see `Extension Methods and others`).
