## 3.1. Creating interfaces: syntax, intent, and what to put in an interface

1. **Interfaces as capability contracts** (small, cohesive, name by responsibility: `IStreamSerializer`, `IClock`)
2. **Interface surface rules** (avoid “fat” interfaces; prefer role interfaces; keep them stable)
3. **Nullability + async semantics** (annotate correctly; be explicit about cancellation and concurrency expectations)

### 1) Interfaces as capability contracts

**Definition:** An interface is a **contract**: it defines *what callers may rely on* and what implementers *must provide*. In modern C#, the best interfaces read like **capabilities** (“can do”), not like “types in my architecture”.

**Mentor rule:** start from the *consumer’s need*, not from the producer’s structure.

- Good: `IClock`, `IStreamSerializer<T>`, `IRateLimiter`, `IEmailSender`
- Suspicious: `IManager`, `IService`, `IHelper` (usually “god interfaces” hiding multiple responsibilities)

**When interfaces are a great fit**
- **Boundary inversion** (Dependency Inversion): domain depends on abstractions, infrastructure implements them.
- **Runtime substitution**: different implementations chosen by config/DI/plugins.
- **Test seams**: fakes replace slow/flaky integration code.

**When interfaces are the wrong tool**
- **No real substitutability** (there will be only one implementation, forever).
- **Pure data models** where you need stable shape for serialization (records/DTOs often fit better).
- **Hot path** code where interface dispatch + indirection makes optimization harder (see **4.2** for performance traps and fast-path patterns).

**Minimal example (capability boundary):**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

public interface IEmailSender
{
    Task SendAsync(string to, string subject, string body, CancellationToken cancellationToken = default);
}

public sealed class ConsoleEmailSender : IEmailSender
{
    public Task SendAsync(string to, string subject, string body, CancellationToken cancellationToken = default)
    {
        Console.WriteLine($"To: {to}\nSubject: {subject}\n\n{body}");
        return Task.CompletedTask;
    }
}
```

**Good to know:** an interface is also a **packaging decision**. Put it near the most important consumers, not in a giant “Contracts” project, unless you have a strong modularity reason (see **8.3**).

### 2) Interface surface rules (designing interfaces that scale)

**Goal:** Keep interfaces **small, cohesive, stable**. Every member you add is a long-term commitment (see **1.2** for contract/versioning mindset).

**Surface rules that prevent real production pain**
- **Single responsibility**: if an interface has methods used by different consumers, split it.
- **Prefer *role* interfaces** over “everything about this type”.
  - Example split: `IUserStore`, `IUserPasswordStore`, `IUserEmailStore` (ASP.NET Identity uses this idea for a reason).
- **Avoid “property bags”** as interfaces unless the abstraction is truly about data shape.
- **Avoid synchronous + asynchronous duplicates** unless you have a clear reason (it doubles surface area and ambiguity). Prefer async at boundaries that do I/O.
- **Keep behavior discoverable**: names should reveal intent, costs, and lifetime.
  - `Get*` vs `TryGet*`, `ReadAsync` (I/O) vs `Compute*` (CPU).

**Common mistakes**
- **Fat interface** → implementers become brittle, tests become mocks of everything, refactors become painful.
- **Leaky abstraction**: interface exposes internal domain objects or collections that callers mutate.
- **Ambiguous semantics**: method returns `bool` but doesn’t define what “false” means; throws sometimes, returns false other times.

**Design alternatives (sometimes better than an interface)**
- **Delegate parameters** for a single behavior variation.
- **Abstract base class** when you need shared code/state + controlled extension points (see **2.3**).
- **Discriminated shapes** (closed set) + pattern matching when cases are known and finite.

### 3) Nullability + async semantics (contracts you must make explicit)

**Nullability is part of the contract.**
- Turn on NRT (`<Nullable>enable</Nullable>`) in your projects (repo-wide policy).
- Annotate accurately: `string` means non-null; `string?` means may be null.
- For optional values, prefer *explicit option types* or Try-patterns when ambiguity is harmful.

**Async semantics to define on every async interface method**
- **Cancellation**: accept `CancellationToken` for cancelable operations. Prefer `CancellationToken cancellationToken = default` unless you want to enforce passing it.
- **Timeouts**: don’t bake timeouts into interfaces unless it’s truly part of the domain; timeouts are often policy at the call site.
- **Concurrency**: document whether the implementation is thread-safe. If it is not, document the required usage model (single-thread confinement, external synchronization, etc.).
- **Exception policy**: define which exceptions are expected and which indicate bugs/outages.

**Minimal example (async contract clarity):**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

public interface ICache<TKey, TValue>
    where TKey : notnull
{
    // Contract:
    // - Returns true if value exists (no exception for cache misses).
    // - Implementations must be safe for concurrent callers (thread-safe).
    ValueTask<(bool found, TValue? value)> TryGetAsync(TKey key, CancellationToken cancellationToken = default);

    ValueTask SetAsync(TKey key, TValue value, TimeSpan ttl, CancellationToken cancellationToken = default);
}
```

**Performance note**
- Prefer `ValueTask` only when it measurably avoids allocations and you control usage carefully; otherwise `Task` is simpler/safer.
- Avoid `async void` in interfaces (cannot be awaited; exception handling is broken). Use `Task`.
