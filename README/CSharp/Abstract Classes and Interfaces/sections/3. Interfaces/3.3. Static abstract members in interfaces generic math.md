## 3.3. Static abstract members in interfaces (modern generic math / type class style)

1. **What problem it solves** (generic algorithms needing operators or factory members)
2. **Where it fits** (numeric/geometry/units libraries; high-performance generic code)
3. **Trade-offs** (complexity, constraints, API ergonomics; keep it library-level, not domain-level by default)

### 1) What problem it solves

**The problem:** You want to write a generic algorithm that needs *static* capabilities (operators, identities like zero/one, parsing, factories), but classic interfaces only model **instance** members.

Historically, people used:
- **Delegates** passed into methods (works, but noisy and harder to compose),
- **`dynamic`** (slow, unsafe, trimming/AOT-unfriendly),
- **Reflection** (slow, allocation-heavy, trimming/AOT-unfriendly),
- **“Generic math via `where T : struct` + hand-written overloads”** (explodes in code size).

**Modern solution:** **Static abstract interface members** let you express “type-level capabilities” as compile-time constraints, enabling:
- **Strong typing** (no `dynamic`),
- **Performance** (JIT can inline/specialize; no reflection),
- **Composability** (generic algorithms over numeric-like types).

**Canonical example:**

```csharp
public interface IAdditiveMonoid<TSelf>
    where TSelf : IAdditiveMonoid<TSelf>
{
    static abstract TSelf Zero { get; }
    static abstract TSelf operator +(TSelf left, TSelf right);
}

public static class Algebra
{
    public static TSelf Sum<TSelf>(ReadOnlySpan<TSelf> values)
        where TSelf : IAdditiveMonoid<TSelf>
    {
        var acc = TSelf.Zero;
        for (var i = 0; i < values.Length; i++)
            acc += values[i];
        return acc;
    }
}

public readonly struct Counter : IAdditiveMonoid<Counter>
{
    public Counter(int value) => Value = value;
    public int Value { get; }

    public static Counter Zero => new(0);
    public static Counter operator +(Counter left, Counter right) => new(left.Value + right.Value);
}
```

This is **fully compile-time checked** and can be efficient in hot paths.

**Good to know:** .NET also provides built-in generic-math interfaces like `INumber<T>` in `System.Numerics`. Prefer those if they fit your domain; don’t reinvent algebra unless you’re building a specialized library.

### 2) Where it fits

**Best fit**
- Numeric libraries, geometry/units-of-measure types, signal processing, statistics.
- High-performance generic algorithms where you want **zero allocations** and **JIT-friendly** code.
- Shared libraries where the API consumer benefits from “generic over number-like things”.

**Not a great fit (most business apps)**
- CRUD/domain modeling: the abstraction cost usually isn’t worth the cognitive load.
- When a closed set of types is enough: explicit overloads or pattern matching can be clearer.

**Performance note**
- This approach can enable **inlining** and avoid virtual/interface dispatch in inner loops.
- Still measure: the biggest wins often come from data layout (`Span<T>`, contiguous memory) and reducing allocations, not from fancy constraints.

### 3) Trade-offs

**Complexity**
- Harder for juniors to read; more advanced generic constraints.
- Error messages can be verbose.

**API ergonomics**
- Requires implementers to conform to a specific static shape.
- You can accidentally design a “math framework” that’s overkill for the repo’s tutorial goals.

**Interop / ecosystem**
- Some serializers/ORMs won’t care, but this feature can be less familiar to toolchains and reviewers.

**Guidance**
- Use static abstract interface members when you can clearly articulate:
  - the *generic algorithm* you enable,
  - the *performance or correctness* benefit,
  - and why delegates or explicit overloads aren’t enough.
