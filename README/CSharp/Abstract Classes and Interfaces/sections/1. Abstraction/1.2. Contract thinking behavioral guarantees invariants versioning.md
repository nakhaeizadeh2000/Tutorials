## 1.2. “Contract” thinking: behavioral guarantees, invariants, and versioning

1. **Behavioral contract** (preconditions/postconditions; exceptions and cancellation semantics)
2. **Representation independence** (don’t leak concrete types/collections; expose capabilities, not data)
3. **Versioning mindset** (public APIs are promises; design for extension without breaking callers)

### 1) Behavioral contract

**Definition:** A *behavioral contract* is the set of guarantees callers can rely on: what inputs are valid, what outputs mean, which exceptions can be thrown, how cancellation/timeouts behave, whether the API is thread-safe, and what happens under concurrency.

In production code, “signature-only contracts” (just method names and types) are not enough. The hardest bugs happen when the **behavioral** expectations are implicit or inconsistent.

**What a good contract includes (C# 15 / .NET 9+ reality)**
- **Preconditions**: what must be true when calling (e.g., non-null inputs, ranges, state).
- **Postconditions**: what is true after the call completes successfully.
- **Failure behavior**:
  - Which **exceptions** are thrown and when.
  - Whether failures are **expected** (prefer Try-pattern) vs exceptional (throw).
- **Cancellation semantics** (async): whether a `CancellationToken` is required/optional, and whether cancellation is *best-effort* or *strict*.
- **Thread-safety**: is the type safe for concurrent callers? If not, what is the intended concurrency model?

**When to use exceptions vs Try-pattern**
- Use **exceptions** for *programmer errors* and truly exceptional situations (invalid state, corrupted data, unreachable resources).
- Use **Try-patterns** for *expected* failures on hot paths (parsing, cache lookups, dictionary hits).

**Example (Try-pattern + clear contract):**

```csharp
using System;
using System.Globalization;

public static class MoneyParsing
{
    // Contract:
    // - Returns true on successful parse.
    // - Does not throw for invalid user input.
    // - Uses invariant culture by default (explicit, predictable).
    public static bool TryParseDecimalInvariant(ReadOnlySpan<char> text, out decimal value)
        => decimal.TryParse(text, NumberStyles.Number, CultureInfo.InvariantCulture, out value);
}
```

**Good to know (async contracts)**
- Prefer `Task`/`ValueTask` return types and `CancellationToken` parameters for async APIs.
- Avoid **legacy async patterns**:
  - APM (`Begin*/End*`) and EAP (`FooAsync` events) are legacy. Modern replacement is `async`/`await` with `Task`.
  - `Task.ContinueWith` is almost always inferior to `await` for clarity/correctness (see `Cuncurrent & Parallel` domain for the deep dive).

### 2) Representation independence

**Definition:** Representation independence means callers can’t depend on your internal data structure, state layout, caching strategy, or concurrency mechanism. Your API exposes **capabilities** and **observable behavior**, not “how it’s built”.

**Why mentors care:** representation leaks are *versioning landmines*. The minute you return a `List<T>` or expose internal mutable state, you’ve made it hard to change without breaking consumers or introducing subtle bugs.

**Common representation leaks**
- Returning mutable collections (`List<T>`, `Dictionary<TKey,TValue>`) that are actually internal state.
- Exposing internal types in public signatures (especially `internal`-ish domain objects that you later want to refactor).
- Exposing *implementation-driven* configuration knobs (e.g., “useCachingLayer2=true”) rather than expressing intent.

**Modern C# shapes that help**
- Prefer **read-only views**:
  - `IReadOnlyList<T>`, `IReadOnlyDictionary<TKey,TValue>` for API-level contracts.
  - `ReadOnlySpan<T>` / `ReadOnlyMemory<T>` for high-performance, allocation-free access (with lifetime constraints).
- Prefer **domain queries** over exposing raw collections (e.g., `TryGetById`, `FindActiveUsers()`).

**Example (avoid leaking mutability):**

```csharp
using System;
using System.Collections.Generic;

public sealed class Catalog
{
    private readonly List<string> _items = [];

    // Good: callers can enumerate but can’t mutate internal state.
    public IReadOnlyList<string> Items => _items;

    public void Add(string item)
    {
        if (string.IsNullOrWhiteSpace(item)) throw new ArgumentException("Item is required.", nameof(item));
        _items.Add(item);
    }
}
```

**Performance note**
- `IReadOnlyList<T>` still uses interface dispatch. In hot paths, you may prefer returning a concrete array/`ImmutableArray<T>` or providing a `ReadOnlySpan<T>` accessor. Measure before optimizing.

### 3) Versioning mindset

**Definition:** Public APIs are **promises**. Versioning mindset is designing contracts such that you can add capabilities later without breaking existing callers and implementers.

**Two versioning directions to think about**
- **Caller-facing versioning**: can existing callers keep working if you change internals or add members?
- **Implementer-facing versioning** (interfaces/abstract bases): can existing implementers keep compiling/running if you add or change requirements?

**Practical guidance (C# 15 era)**
- **Prefer non-virtual by default**; make extension points explicit.
- **Be careful adding members to interfaces**: it breaks implementers unless you use **Default Interface Members** (DIM). DIM exists primarily for versioning, but it comes with trade-offs (see **3.2** for the canonical DIM treatment).
- **Be careful changing abstract base classes**: adding new abstract members breaks derived types; changing virtual behavior can break semantics.

**Good to know (binary compatibility)**
- Source compatibility (“it compiles”) is not the same as binary compatibility (“existing assemblies still run”). Public contracts in shared libraries must be designed with both in mind.

**Rule of thumb**
- If you want to evolve behavior over time with minimal breakage, prefer:
  - **composition + small interfaces**, and/or
  - **non-virtual concrete types** with explicit extension hooks,
  rather than deep inheritance hierarchies.

For how these versioning choices interact with abstract classes and interfaces in practice, see **2.3** and **3.2**.
