## 1.1. Abstraction vs encapsulation vs polymorphism (C#-specific mental model)

1. **Abstraction = limiting what callers can rely on** (stable contract, fewer coupling points, easier refactors)
2. **Encapsulation = hiding representation/invariants** (private state; “valid states only” enforcement)
3. **Polymorphism = multiple implementations behind one contract** (runtime dispatch trade-offs; testability vs overhead)

### 1) Abstraction = limiting what callers can rely on

**Definition (mentor framing):** Abstraction is the act of **choosing a smaller “surface of truth”** than the full implementation. You deliberately expose *capabilities* and *guarantees*, while hiding everything else so you can change it later without breaking callers.

**When abstraction is the right tool**
- **At boundaries**: UI/API ↔ domain ↔ data; your code ↔ external systems (HTTP, DB, filesystem).
- **When you need substitution**: multiple implementations (real vs fake; cached vs direct; local vs remote).
- **When you need long-term versioning freedom**: you want to evolve internals without updating every caller.

**Trade-offs**
- **Pros**: reduced coupling, easier testing, safer refactors, clearer layering.
- **Cons**: indirection can reduce clarity, slow debugging, and hide performance costs if overused.

**Common mistakes**
- **Abstracting too early** (“maybe we’ll need another implementation”) → unnecessary indirection.
- **Abstraction leakage**: returning concrete mutable types (`List<T>`), exposing internal exceptions, or leaking configuration flags that describe internals.
- **Over-general contracts**: “god” interfaces like `IService` or signatures like `DoWork(object)` are hard to reason about and hard to optimize.

**Good to know**
- Prefer **capability-based naming**: `IClock`, `IStreamSerializer`, `IRateLimiter`.
- Don’t create an interface if there is **no meaningful substitutability**. A concrete type is often the best abstraction inside a module.

**Minimal example (abstraction boundary):**

```csharp
public interface IClock
{
    DateTimeOffset UtcNow { get; }
}

public sealed class SystemClock : IClock
{
    public DateTimeOffset UtcNow => DateTimeOffset.UtcNow;
}
```

For deep API-contract/versioning guidance, see **1.2**.

### 2) Encapsulation = hiding representation/invariants

**Definition:** Encapsulation is about **protecting invariants** by hiding internal state and limiting mutation points. In C#, it’s typically **private fields + public methods/properties** that enforce rules.

**What strong encapsulation looks like (C# 15 era)**
- **Make invalid states unrepresentable** where possible (constructors/factories validate; mutation is explicit).
- **Avoid representation leaks**: don’t expose mutable collections; prefer read-only views or intent-revealing methods.
- **Be explicit about ownership** for resources (`IDisposable`/`IAsyncDisposable`).

**Common mistakes**
- Using **DTO-style public setters** on domain types (invariants become unenforceable).
- Returning internal `List<T>`/`Dictionary<TKey,TValue>` directly (callers mutate behind your back).
- Doing heavy work, I/O, or locking inside “simple” getters (hard to reason about; easy to misuse).

**Example (“valid states only”):**

```csharp
public sealed class BankAccount
{
    private decimal _balance;

    public BankAccount(decimal openingBalance)
    {
        if (openingBalance < 0) throw new ArgumentOutOfRangeException(nameof(openingBalance));
        _balance = openingBalance;
    }

    public decimal Balance => _balance;

    public void Deposit(decimal amount)
    {
        if (amount <= 0) throw new ArgumentOutOfRangeException(nameof(amount));
        _balance += amount;
    }

    public void Withdraw(decimal amount)
    {
        if (amount <= 0) throw new ArgumentOutOfRangeException(nameof(amount));
        if (amount > _balance) throw new InvalidOperationException("Insufficient funds.");
        _balance -= amount;
    }
}
```

**Performance note:** the cost is rarely the property; it’s allocations/locks/exceptions you hide behind it. For property-specific pitfalls, see the repo’s `Properties and Indexers` domain.

### 3) Polymorphism = multiple implementations behind one contract

**Definition:** Polymorphism means **one call site** can execute **different implementations** depending on runtime type. In C# this is most commonly **interface dispatch** and **virtual dispatch** (plus delegates as a lightweight alternative).

**When to use dynamic polymorphism**
- You need **open-ended extensibility** (plugins, DI, “providers”, serializers).
- You want **dependency inversion** at a boundary (domain ↔ infrastructure).

**When not to**
- You have a **closed set of known cases** (pattern matching/switch is often simpler and more explicit).
- The code is a **hot path** and polymorphism prevents inlining/devirtualization (design a non-polymorphic fast path; see **4.2**).

**Common mistakes**
- Making everything `virtual` “just in case” (weakens invariants and complicates versioning).
- Choosing an interface where a simple **delegate** parameter would be clearer.

**Performance note:** interface dispatch is usually fine, but boxing/allocations and lost inlining can dominate in hot loops. See **4.2** for the full treatment.
