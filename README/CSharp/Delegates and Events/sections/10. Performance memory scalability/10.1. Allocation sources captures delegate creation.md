## 10.1. Allocation sources: captures, delegate creation, and invocation list churn

1. **What allocates** (closures, expression trees, sometimes delegate instances; `GetInvocationList()` always allocates)
2. **What usually doesn’t** (method groups often avoid captures; trivial wrappers can inline)
3. **Rule of thumb** (avoid per-iteration handler creation; prefer caching and `static` lambdas)

### 1) What allocates (and why)
This section is your “spot the allocation” map for delegate/event-heavy code. The most common sources:

#### A) Capturing lambdas (closures)
When a lambda captures a local or `this`, the compiler typically generates a **closure class** to hold captured state. That closure is heap-allocated, and the delegate points to a method on that closure instance.

```csharp
using System;

static Func<int, int> MakeAdder(int delta)
{
    // Captures delta => closure allocation
    return x => x + delta;
}
```

Why it matters:
- **Allocations**: closure object (and usually a delegate instance)
- **Lifetime extension**: captured objects live as long as the delegate lives
- **GC pressure**: in tight loops, this is a common throughput killer

See `7.2` for the full closure model and common bugs; see `7.4` for `static` lambdas.

#### B) Expression trees
`Expression<TDelegate>` creates an object graph representing code-as-data. It is intentionally allocation-heavy.

If you don’t need inspection/translation, don’t use it “just in case”. See `8.1` and `8.2`.

#### C) `GetInvocationList()`
`Delegate.GetInvocationList()` **allocates an array** every time. It’s fine for occasional diagnostics or best-effort notification, but avoid it in hot paths.

See `3.2` for patterns and trade-offs.

#### D) Delegate churn from `+=`/`-=`
Delegates are immutable. Every `+=` / `-=` produces a new delegate instance representing a new invocation list.

```csharp
using System;

static void Demo()
{
    Action? a = null;
    for (var i = 0; i < 1_000; i++)
    {
        a += static () => { }; // allocates per iteration (new delegate + list node)
    }
}
```

The fix is architectural: subscribe once, cache the handler, or redesign to avoid per-iteration subscription patterns.

### 2) What usually doesn’t allocate
#### Method groups and `static` lambdas
Non-capturing callbacks don’t need closure objects:

```csharp
using System;

static void Log(int x) => Console.WriteLine(x);

static void Demo()
{
    Action<int> a1 = Log;                 // method group
    Action<int> a2 = static x => Log(x);  // still non-capturing
}
```

Notes:
- You may still see a delegate instance created, but you avoid closure allocations (the big win).
- JIT may cache certain delegates in some contexts, but **don’t rely on it** for correctness or perf guarantees.

#### Tiny wrappers and inlining
“Trivial wrapper methods” *can* inline and be optimized, but a delegate call itself is usually a boundary for inlining into the target. Optimize by removing allocations first; then measure call overhead.

### 3) Rule of thumb (mentor-grade)
- **Default**: prefer **method groups** or **`static` lambdas**.
- **Hot path**: avoid allocating per item per frame per request:
  - don’t create new capturing lambdas inside loops
  - don’t subscribe/unsubscribe frequently
  - avoid `GetInvocationList()` per event raise
- **Measure**:
  - Allocation tracking: `dotnet-counters` (GC alloc rate), PerfView/EventPipe
  - Microbenchmarks: BenchmarkDotNet

**Performance note**
Async can hide allocations too:
- `async` lambdas often allocate state machines.
- `async void` event handlers change failure semantics and can crash processes if exceptions escape. See `10.3` for event threading and reentrancy hazards, and keep async event patterns intentional.
