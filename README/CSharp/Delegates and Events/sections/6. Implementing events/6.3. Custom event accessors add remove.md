## 6.3. Custom event accessors (`add`/`remove`): locking, performance, and correctness

1. **Why you’d do it** (thread-safe storage, custom subscription logic, bridging to other sources)
2. **Correctness traps** (deadlocks, reentrancy, forgetting to remove, memory leaks)
3. **Performance reality** (locks vs lock-free; contention; don’t over-engineer without a reason)

### 1) Why you’d do it
Most code should use an auto-implemented event (`public event EventHandler? Foo;`). Custom accessors are for cases where you need behavior beyond the compiler-generated backing field:

- **Thread-safe subscription bookkeeping** with additional invariants (e.g., counting subscribers, enabling/disabling an underlying source).
- **Bridging** to another event source (wrapping a lower-level component).
- **Custom storage** (e.g., per-key event handlers, or sparse storage for many events).
- **Weak event** patterns (advanced; often UI-specific—see note below).
- **Instrumentation** (tracing subscribe/unsubscribe) without exposing the backing delegate.

**Frontend note (WPF/WinForms/MAUI)**: “weak events” are most common in UI frameworks to avoid leaks between long-lived publishers and short-lived views. If you’re not in a UI lifetime model, prefer explicit unsubscription via `IDisposable` (see `10.2`).

### 2) Correctness traps (the stuff that bites seniors too)
#### Trap A: raising under a lock (deadlocks + reentrancy)
If you lock in `add/remove`, do **not** invoke handlers while holding that lock. Subscribers can call back into the publisher (reentrancy) or take other locks → deadlocks.

Rule: **lock only to mutate the delegate field**, then invoke outside the lock using a snapshot.

#### Trap B: lost updates without atomic compare-exchange
Naively doing `_handlers += value;` inside `add` isn’t safe unless you protect it with a lock, because it is a read-modify-write sequence.

#### Trap C: not matching delegate instances on unsubscribe
Unsubscribe must remove the same method/target pair. Using inline lambdas makes this hard:

```csharp
// BAD: can't unsubscribe, you created a new delegate instance
publisher.Changed += (_, _) => Console.WriteLine("changed");
publisher.Changed -= (_, _) => Console.WriteLine("changed"); // does nothing
```

Prefer method groups or store the delegate in a field.

#### Trap D: leaking subscribers (lifetime bug)
Events create a strong reference from publisher → subscriber through the delegate’s target. If the publisher outlives the subscriber and you never unsubscribe, you leak. See `10.2` for the full “why” and mitigations.

### 3) Performance reality: choose the simplest correct thing
There are two common correct patterns:

#### Pattern A: `lock` (best default)
Simple, correct, and fast enough for most apps. Lock contention is rarely an issue unless you have extremely high-frequency subscribe/unsubscribe across threads.

```csharp
using System;

public sealed class Clock
{
    private readonly object _gate = new();
    private EventHandler<DateTime>? _tick;

    public event EventHandler<DateTime> Tick
    {
        add
        {
            if (value is null) throw new ArgumentNullException(nameof(value));
            lock (_gate) _tick += value;
        }
        remove
        {
            if (value is null) return;
            lock (_gate) _tick -= value;
        }
    }

    public void Raise(DateTime now)
    {
        EventHandler<DateTime>? snapshot;
        lock (_gate) snapshot = _tick;      // snapshot under lock
        snapshot?.Invoke(this, now);         // invoke outside lock
    }
}
```

#### Pattern B: lock-free with `Interlocked.CompareExchange` (advanced)
Use when you need very low-latency subscription updates and want to avoid contention. It’s more complex and easy to get wrong; use only if you’ve measured contention.

```csharp
using System;
using System.Threading;

public sealed class Signal
{
    private Action? _handlers;

    public event Action Fired
    {
        add
        {
            if (value is null) throw new ArgumentNullException(nameof(value));
            Action? current, updated;
            do
            {
                current = _handlers;
                updated = (Action?)Delegate.Combine(current, value);
            } while (Interlocked.CompareExchange(ref _handlers, updated, current) != current);
        }
        remove
        {
            if (value is null) return;
            Action? current, updated;
            do
            {
                current = _handlers;
                updated = (Action?)Delegate.Remove(current, value);
            } while (Interlocked.CompareExchange(ref _handlers, updated, current) != current);
        }
    }

    public void Raise() => Volatile.Read(ref _handlers)?.Invoke();
}
```

**Good to know**
- `Delegate.Combine/Remove` allocate in some cases and are not “free”; but subscribe/unsubscribe should not be a hot path in well-designed systems.
- Raising an event is typically far more frequent than subscription. Optimize raising first (snapshot + avoid work in handlers) before micro-optimizing add/remove.

**Performance note**
- The *fastest* event is the one you don’t raise too often. If you need extremely high-rate notifications, consider batching, channels, or pipelines instead of per-item events (but that belongs to concurrency/pipelines sections; see `13.1` boundaries).
