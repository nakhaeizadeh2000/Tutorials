## 8.2. Building and composing expression trees (performance + caching)

1. **Composition patterns** (parameter rebinding; avoiding accidental closures)
2. **Compile vs interpret** (trade-offs; caching compiled delegates)
3. **AOT/trimming considerations** (prefer explicit expression shapes; avoid heavy reflection)

### 1) Composition patterns (parameter rebinding without accidental closures)
Expression trees are immutable graphs. Composition means building a new graph that references (or replaces) nodes from existing graphs.

The most common composition mistake is trying to “reuse” parameters from different trees without rebinding them.

#### Example: compose two predicates into one

```csharp
using System;
using System.Linq.Expressions;

static class Expr
{
    public static Expression<Func<T, bool>> AndAlso<T>(
        Expression<Func<T, bool>> left,
        Expression<Func<T, bool>> right)
    {
        var p = Expression.Parameter(typeof(T), "x");
        var leftBody = new ReplaceParameter(left.Parameters[0], p).Visit(left.Body)!;
        var rightBody = new ReplaceParameter(right.Parameters[0], p).Visit(right.Body)!;
        return Expression.Lambda<Func<T, bool>>(Expression.AndAlso(leftBody, rightBody), p);
    }

    private sealed class ReplaceParameter(ParameterExpression from, ParameterExpression to) : ExpressionVisitor
    {
        protected override Expression VisitParameter(ParameterExpression node)
            => node == from ? to : base.VisitParameter(node);
    }
}

Expression<Func<int, bool>> gt10 = x => x > 10;
Expression<Func<int, bool>> even = x => (x & 1) == 0;

var combined = Expr.AndAlso(gt10, even);
Console.WriteLine(combined); // x => ((x > 10) AndAlso ((x & 1) == 0))
```

**Good to know**
- This approach avoids capturing locals inside the expression tree. If you capture local values (e.g., `threshold` from outer scope), the expression tree may contain a reference to a **closure object**, which:
  - is easy to accidentally keep alive
  - can be surprising for query translators (EF, etc.)

Mentor guidance:
- Prefer **parameters** over captured locals for values you intend to translate.
- If you must inject constants, use `Expression.Constant(value)` explicitly so it’s obvious and stable.

### 2) Compile vs interpret (and when to cache)
You have three “execution” options:
- **Pass the expression tree** to something that inspects/translates it (ORM/provider). No compile needed.
- **Compile** to a delegate (`expr.Compile()`): fastest execution after compilation, but compilation is expensive.
- **Interpret** (runtime dependent): in some cases an interpreter may be used; performance varies. Don’t assume it’s free.

Mentor rules:
- **Never call `Compile()` in a hot path** without caching.
- Cache compiled delegates by **expression shape** (or by stable keys), not by input data.

Example: cache by expression instance for internal use (simple and safe when you control the expression lifetime):

```csharp
using System;
using System.Collections.Concurrent;
using System.Linq.Expressions;

static class CompiledCache
{
    private static readonly ConcurrentDictionary<LambdaExpression, Delegate> _cache = new();

    public static Func<T, TResult> Get<T, TResult>(Expression<Func<T, TResult>> expr)
        => (Func<T, TResult>)_cache.GetOrAdd(expr, static e => ((Expression<Func<T, TResult>>)e).Compile());
}

Expression<Func<int, int>> sq = x => x * x;
var f = CompiledCache.Get(sq);
Console.WriteLine(f(12)); // 144
```

**Performance note**
- Expression trees allocate nodes; compilation can allocate dynamic methods and metadata structures. Caching reduces repeated work but can increase memory usage if you cache unboundedly.
- Be intentional: if expression instances are user-provided and unbounded, add eviction (size/time) or avoid caching.

### 3) AOT/trimming considerations (modern .NET)
Modern .NET increasingly targets:
- **Trimming** (unused code removal)
- **Native AOT**

Expression trees can interact poorly with these when you rely on reflection-heavy patterns or compile arbitrary expressions at runtime.

Mentor guidance:
- Prefer **known, explicit expression shapes** when targeting AOT/trimming.
- Avoid “build anything with reflection” expression builders in libraries unless you can provide:
  - a clear set of supported operations
  - tests against AOT/trimming
  - fallbacks (e.g., source generators) when appropriate

If you don’t need inspection/translation, use delegates (`Func<>`/`Action<>`) instead. See `8.1` for the core mental model and API guidance.
