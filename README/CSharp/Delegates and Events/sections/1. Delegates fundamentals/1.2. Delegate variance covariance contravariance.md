## 1.2. Delegate variance: covariance and contravariance in real APIs

1. **Why it exists** (plugging compatible handlers without adapter code)
2. **Common examples** (`Func<out TResult>`, `Action<in T>`, event handler signatures)
3. **Pitfalls** (overload resolution surprises; nullability contracts; generic inference)

### 1) Why it exists
**Variance** lets the compiler treat certain generic delegate types as assignment-compatible when their type arguments are in safe positions:

- **Covariance (`out`)**: you can use a *more derived* return type where a *base* return type is expected.
- **Contravariance (`in`)**: you can use a *less derived* parameter type where a *more derived* parameter type is expected.

This matters because delegates model *input/output*:
- Inputs (parameters) are consumed → contravariant is safe
- Outputs (return values) are produced → covariant is safe

Without variance you’d need adapter lambdas everywhere, which adds noise and sometimes allocations.

### 2) Common examples
#### `Func<in T, out TResult>` and `Action<in T>`
The built-in delegates are already annotated for variance:

```csharp
using System;

class Animal { public override string ToString() => "Animal"; }
sealed class Dog : Animal { public override string ToString() => "Dog"; }

static Animal MakeAnimal() => new Dog();
static void HandleAnimal(Animal a) => Console.WriteLine(a);
static void HandleDog(Dog d) => Console.WriteLine($"Dog: {d}");

Func<Animal> fAnimal = MakeAnimal;   // covariant return: Dog is an Animal

Action<Dog> aDog = HandleAnimal;     // contravariant input: Animal-handler can handle Dogs too

Console.WriteLine(fAnimal());        // prints "Dog"
aDog(new Dog());                     // prints "Dog"
```

#### Events and handler signatures
The classic .NET event pattern uses:

- `EventHandler` (no payload)
- `EventHandler<TEventArgs>` (payload)

These are delegates too, and variance can matter when you design your own callback types.

**Good to know**
- `EventHandler<TEventArgs>` is **contravariant** in `TEventArgs` in modern .NET, which allows handlers that accept a base event args type to be used where a derived args type is expected (within rules). This can be convenient, but also makes overload resolution more subtle.

### 3) Pitfalls
#### Pitfall A: thinking variance is “just inheritance”
Variance is *positional*. If a type parameter appears in both input and output positions, it cannot be variant safely.

Example (won’t compile as variant):

```csharp
public delegate T Bad<T>(T value); // T is both input and output => cannot be in/out
```

#### Pitfall B: overload resolution surprises
Variance can make more overloads “applicable”, so calls become ambiguous when you pass method groups.

Mentor guidance:
- If a method group is ambiguous, **target-type it** by assigning to a local with an explicit delegate type first, or use an explicit cast:

```csharp
// Example pattern (shape only)
// Action<Dog> handler = HandleAnimal; // target typing resolves the conversion
```

For the full treatment of method groups vs lambdas vs overload resolution, see `1.3. Method groups vs lambdas vs anonymous methods`.

#### Pitfall C: nullability contracts don’t automatically “lift”
With nullable reference types enabled, variance does **not** “sanitize” nullability expectations.

- `Action<string>` is **not** the same contract as `Action<string?>`.
- If you accept `Action<in T>` in public APIs, be explicit about whether `T` is nullable and document whether you may pass null.

**Good to know**
- Prefer **explicit nullability** on delegate parameters in public APIs. It prevents “handler assumed non-null” bugs that show up only at runtime.

#### Pitfall D: generic inference gets confusing
When you write higher-order APIs, type inference can pick unexpected `T`/`TResult` due to variance + implicit conversions.

Mentor guidance:
- Keep public callback-based APIs **narrow** (avoid too many overloads).
- If inference quality matters, use **named delegates** or **explicit generic arguments** at call sites.

**Performance note**
Variance conversions themselves don’t allocate; they’re compile-time typing rules. The allocation risk comes from using adapter lambdas to work around missing variance or ambiguous overloads—especially capturing adapters. Prefer target typing and method groups where possible.
