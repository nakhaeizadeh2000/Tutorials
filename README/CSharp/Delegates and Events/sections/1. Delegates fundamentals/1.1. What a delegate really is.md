## 1.1. What a delegate really is (type-safe function pointer + object + invocation list)

1. **Mental model** (a reference type that can point to a method; may also carry a target instance)
2. **How invocation works** (single-cast vs multicast; exceptions and return values semantics)
3. **Performance framing** (indirection, allocations, captures; don’t guess—measure allocations and throughput)

### 1) Mental model
**Delegate** in C# is a **reference type** that represents “something you can call” with a specific signature. Conceptually it carries:

- **A method to call** (a function pointer to a method entry point)
- **An optional target object** (for instance methods; `null` for static methods)
- **Optionally, an invocation list** (multicast delegates can have multiple entries)

You can treat a delegate as a strongly-typed callable object:

```csharp
using System;

static int Add1(int x) => x + 1;

Func<int, int> f = Add1;          // method group -> delegate
Console.WriteLine(f(41));         // 42
```

#### Delegate vs interface (when each fits)
- **Delegate**: best for “call me back with these parameters”, usually a *single method* contract, lightweight usage, higher-order APIs (filters, projections, notifications).
- **Interface**: best when you need a *named capability with multiple members*, versioning, dependency injection semantics, and richer discoverability.

**Good to know**
- Delegates support equality semantics: `d1 == d2` is true if they have the same invocation list (method + target pairs in order). This matters when unsubscribing from events: you must remove the *same* delegate instance or an equivalent method/target pair.
- Delegates are immutable. Combining/removing produces new delegate instances.

### 2) How invocation works
#### Single-cast vs multicast
- **Single-cast delegate**: one target method.
- **Multicast delegate**: multiple target methods; common with events.

Combine/remove is conceptually like building an immutable list:

```csharp
using System;

static void A() => Console.WriteLine("A");
static void B() => Console.WriteLine("B");

Action d = A;
d += B;        // combine => multicast
d();           // prints A then B

d -= A;        // remove one matching entry
d();           // prints B
```

#### Return values semantics (important)
For multicast delegates with a return type (e.g., `Func<int>`), **only the last subscriber’s return value is observed**.

That’s usually a **design smell**: fan-out notifications should not pretend to be a query. If you need to aggregate results, make that explicit (e.g., return `IReadOnlyList<T>`, or expose `IEnumerable<T>` results, or accept an `ICollector<T>`).

#### Exception semantics (important)
By default, invoking a multicast delegate:
- Calls subscribers in order
- **Stops at the first exception** (later subscribers are not called)

If you need “best-effort notification”, you must **isolate** exceptions per-subscriber (see `3.2` for invocation-list inspection and isolation patterns).

#### Nullability and “no subscribers”
Calling a `null` delegate throws `NullReferenceException`, so idiomatic code uses:

```csharp
handler?.Invoke(this, args);
```

For events, the event field can become `null` between check and call if you implement custom accessors incorrectly; see `2.3` and `6.3` for thread-safety and accessor patterns.

### 3) Performance framing
Delegates are fast enough for most code, but in hot paths you should know what costs exist.

#### What costs you pay
- **Indirect call**: a delegate invocation is not the same as a direct call; it may block inlining and incur an extra indirection.
- **Allocation sources**:
  - **Capturing lambdas** allocate a closure object (and sometimes extra delegate instances). This is the most common accidental allocation source; see `7.2` and `7.4`.
  - `GetInvocationList()` **always allocates** an array; see `3.2`.
  - Repeated `+=`/`-=` in tight loops churns delegate instances (immutability).

#### What usually does *not* allocate
- A **non-capturing** method group assigned to `Action`/`Func` typically does not allocate a closure object.
- A **`static` lambda** cannot capture and therefore avoids closure allocations by construction:

```csharp
Func<int, int> plus1 = static x => x + 1; // cannot capture external locals / this
```

#### Mentor rule: don’t optimize blind
If delegates are on a critical path:
- Use **BenchmarkDotNet** or at least measure allocations with **EventPipe** / **dotnet-counters** / PerfView.
- Prefer structural fixes:
  - avoid captures (`static` lambdas / method groups)
  - cache delegates used repeatedly (especially in subscription scenarios)
  - avoid per-iteration subscription churn

**Performance note**
Delegates can interact with async in surprising ways. An “async event handler” is almost always an `async void` delegate, which changes exception semantics and can crash processes if exceptions go unobserved. This is covered in depth in `10.3` (thread-safety/reentrancy) and referenced by `5.x/6.x` when events are raised from background threads.
