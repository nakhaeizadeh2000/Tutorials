## 7.5. Lambda explicit return type, default parameters, and parameter modifiers (C# 10–C# 15)

### 1) Explicit return type (`Func`-like inference)

1. Syntax: `static string () => "x"` or with explicit return: some forms allow specifying return when the compiler can’t infer cleanly.
2. **Why**: disambiguate overload resolution and make **public APIs** self-documenting.
3. **Perf**: no inherent runtime cost—still a delegate unless optimized away by inlining at the call site.

---

### 2) Default parameter values on lambdas (C# 12+)

1. Lets you write `(int x = 0) => ...` style lambdas where language allows.
2. **Overload interactions**: defaults participate in **overload resolution**—watch for ambiguity with `params` and extension methods.
3. **Captures**: defaults don’t create captures; **capturing `this`/locals** still allocates.

---

### 3) Parameter modifiers on lambdas without explicit types (C# 14+)

1. You can use `ref`, `out`, `in`, `scoped`, `ref readonly` on parameters **without** spelling parameter types when the compiler can infer from target delegate.
2. **`params` still requires** an explicitly typed parameter list (language rule).
3. **Mentor rule**: prefer explicit types at **library boundaries**; use inference for local glue code.

---

### 4) Performance checklist (delegates + lambdas)

1. Prefer **`static` lambdas** when you don’t need captures ([7.4](<./7.4. static lambdas prevent captures.md>)).
2. Avoid **allocating a new delegate** per loop iteration—cache or use method groups.
3. **`params` collections** (C# 13) can reduce array allocations when overloads use span/collection targets—see `Methods/6.7`.
