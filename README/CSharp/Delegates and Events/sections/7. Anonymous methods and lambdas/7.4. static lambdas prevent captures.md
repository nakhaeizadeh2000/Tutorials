## 7.4. `static` lambdas (C# 9+) and how they prevent accidental allocations

1. **Guarantee** (no captures; forces explicit parameters)
2. **Hot-path pattern** (callbacks in loops; event subscriptions; LINQ alternatives)
3. **Mentor rule** (default to `static` when feasible; it encodes intent)

### 1) Guarantee: “cannot capture” is a contract
A **`static` lambda** is a lambda expression that is **forbidden** from capturing any locals, parameters, or `this` from the enclosing scope.

That gives you two powerful properties:

- **Correctness**: you cannot accidentally close over a mutable variable (a common bug source).
- **Performance**: the compiler cannot generate a closure object for a `static` lambda, so you avoid a major allocation pitfall (see `7.2` for closure mechanics).

Example:

```csharp
using System;

var factor = 10;

Func<int, int> ok = x => x * factor;             // captures => closure allocation
// Func<int, int> nope = static x => x * factor; // error: cannot capture 'factor'

Func<int, int> explicit = static (int x) => x * 10;
Console.WriteLine(explicit(3)); // 30
```

**Good to know**
- `static` applies to the lambda, not the delegate variable. You can still assign a `static` lambda to a `Func<>`/`Action<>`.

### 2) Hot-path patterns (and why `static` helps)
Use `static` lambdas proactively when callbacks are:

- Used in **loops**
- Passed to **LINQ / collection APIs**
- Registered as **event handlers**
- Reused across many invocations

#### Pattern A: caching non-capturing delegates
If a callback doesn’t depend on instance state, cache it once:

```csharp
using System;

static class Filters
{
    public static readonly Predicate<int> IsEven = static x => (x & 1) == 0;
}
```

This is allocation-free per call site and conveys “no hidden state”.

#### Pattern B: event handlers without capturing `this`
Capturing `this` in a handler can create lifetime leaks if you forget to unsubscribe (see `10.2`).

Prefer a method group when you need instance state; otherwise, use a `static` handler and pass explicit state:

```csharp
using System;

sealed class Publisher
{
    public event EventHandler? Tick;
    public void Raise() => Tick?.Invoke(this, EventArgs.Empty);
}

static void OnTick(object? sender, EventArgs e) =>
    Console.WriteLine($"Tick from {sender?.GetType().Name}");

var p = new Publisher();
p.Tick += OnTick; // method group (non-capturing)
p.Raise();
```

#### Pattern C: LINQ alternative without accidental capture
If you *must* use LINQ in a hot path, `static` avoids closure allocations when possible:

```csharp
using System;
using System.Linq;

int[] xs = [1, 2, 3, 4];
var evens = xs.Where(static x => (x & 1) == 0).ToArray();
Console.WriteLine(string.Join(", ", evens));
```

### 3) Mentor rule
Treat `static` lambdas as “performance + intention encoding”:

- Default to **`static`** if you don’t need to capture.
- If you do need state, prefer **explicit parameters** or **method groups** over silent captures.
- If you capture, do it intentionally and keep captured state minimal (avoid capturing large objects or `this` casually).

**Performance note**
- The point is not “`static` makes the call faster”; it prevents the *closure allocation* and associated lifetime extension.
- In throughput-oriented code, removing even small per-iteration allocations reduces GC pressure and improves tail latency.
