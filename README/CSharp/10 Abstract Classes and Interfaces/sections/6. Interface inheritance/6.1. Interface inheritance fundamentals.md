## 6.1. Interface inheritance fundamentals: is-a vs capability refinement

1. **Refinement** (a derived interface adds guarantees/capabilities, not unrelated responsibilities)
2. **Avoid deep hierarchies** (prefer small role interfaces; keep composition simple)
3. **Versioning** (interface inheritance multiplies break risk; use DIM only when it’s a clear win)

### 1) Refinement: capability, not “dump more members”

**Definition:** Interface inheritance should represent **refinement**: `IDerived : IBase` means “everything promised by `IBase`, plus more guarantees/capabilities.” If the “more” is unrelated, it’s not refinement—it’s coupling.

**Good refinement examples**
- `IReadOnlyList<T> : IReadOnlyCollection<T>` (adds indexer capability).
- `IAsyncDisposable : IDisposable` would *not* be correct (async dispose has different semantics); .NET keeps them separate for a reason.

**Bad refinement examples**
- `IRepository : ILogger` (unrelated responsibilities).
- `IService : IDisposable : IAsyncDisposable : IComparable` (kitchen-sink).

**Mentor rule:** If a consumer needs only part of the behavior, they should be able to depend on the smaller interface. Don’t force consumers to depend on methods they don’t use.

**Example (capability refinement):**

```csharp
public interface IClock
{
    DateTimeOffset UtcNow { get; }
}

public interface IMonotonicClock : IClock
{
    // Additional guarantee: time never goes backwards.
    long Timestamp { get; } // e.g., Stopwatch ticks or similar monotonic measure
}
```

### 2) Avoid deep hierarchies

**Why deep hierarchies rot**
- Every new derived interface multiplies **cognitive load** (“what does this *really* require?”).
- It becomes hard to add new members without breaking implementers (see versioning below).
- It encourages “inheritance as taxonomy” rather than “capabilities that compose.”

**Prefer “role” interfaces**
- Make interfaces small and cohesive (see **3.1** for the canonical guidance).
- Compose capabilities on types: `class Foo : IBar, IBaz` is often clearer than `interface IFoo : IBar, IBaz`.

**Good to know:** Deep *type* hierarchies are sometimes unavoidable in framework code, but for application/domain code they rarely pay off.

### 3) Versioning: inheritance multiplies break risk

**Key point:** When you change a base interface, you affect **all derived interfaces** and **all implementers**. With interface inheritance, a single change can cascade widely.

**Practical versioning guidance**
- If the interface is public and implemented by third parties:
  - Prefer adding functionality via **new interfaces** (e.g., `IFoo2`) or via **extension methods** (if it’s truly optional).
  - Consider **DIM** only for carefully designed versioning (canonical treatment in **3.2**).
- If the interface is internal (you control all implementers):
  - You can evolve it more freely, but still keep the surface small to avoid churn.

**Reminder:** Contracts aren’t just “compile-time.” Behavioral changes are versioning changes too (see **1.2**).
