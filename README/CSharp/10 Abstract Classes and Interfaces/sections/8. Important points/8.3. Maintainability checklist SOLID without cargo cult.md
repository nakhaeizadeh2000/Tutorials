## 8.3. Maintainability checklist: SOLID without cargo-culting

1. **Prefer composition over inheritance by default** (inheritance only for true stable is-a + shared behavior)
2. **Don’t over-abstract** (avoid interfaces with a single implementation unless it buys testability/substitution/versioning)
3. **Name and package by responsibilities** (interfaces live near the consumers; avoid “Contracts” mega-projects)

### 1) Prefer composition over inheritance by default

**What this means (in practice):** Most business code should be built out of **small concrete types** wired together (composition) rather than deep class hierarchies. Inheritance is best reserved for:
- **True “is-a”** relationships *and* a stable base contract,
- framework extension points you don’t control,
- carefully designed internal hierarchies where you own both base and derived types.

**Why mentors push composition**
- **Local reasoning**: behavior is in the object you’re reading, not split across base/overrides.
- **Testability**: dependencies are explicit constructor parameters.
- **Versioning safety**: you don’t break “someone’s derived type” when you change a base class.

**Common mistake:** “I want code reuse, so I’ll create a base class.”  
Prefer **helpers**, **strategies**, and **decorators** before a base class. For the deeper inheritance pitfalls (fragile base class, constructor hazards), see **2.3**.

**Small example (composition + decorator):**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

public interface IUserStore
{
    ValueTask<User?> FindByIdAsync(UserId id, CancellationToken ct = default);
}

public sealed record UserId(Guid Value);
public sealed record User(UserId Id, string Name);

public sealed class CachingUserStore(IUserStore inner) : IUserStore
{
    private readonly IUserStore _inner = inner;
    private UserId? _cachedId;
    private User? _cachedUser;

    public async ValueTask<User?> FindByIdAsync(UserId id, CancellationToken ct = default)
    {
        if (_cachedId == id) return _cachedUser;

        var user = await _inner.FindByIdAsync(id, ct);
        _cachedId = id;
        _cachedUser = user;
        return user;
    }
}
```

**Good to know:** this trivial cache is **not thread-safe** (by design, for simplicity). In production, either confine it to a request scope, or add synchronization (and then measure contention).

### 2) Don’t over-abstract

**Rule of thumb:** An abstraction must buy you something:
- **Substitution** (multiple implementations, now or very likely soon),
- **test seam** (fakes for slow/flaky boundaries),
- **versioning boundary** (public API you must keep stable),
- **policy/mechanism separation** (domain vs IO).

If it doesn’t buy you one of these, a concrete type is usually better.

**The “single implementation interface” debate (mentor take):**
- It’s fine to have one implementation today **if** the interface is a boundary to an external system (clock, filesystem, DB, HTTP) or a seam for tests.
- It’s usually a smell if the interface exists only to “follow DI” inside a cohesive module.

**Common mistakes**
- “I need DI, so everything must be an interface.” (No—DI can inject concrete types too.)
- “Interfaces are always better for unit tests.” (Not if the contract is vague or huge.)

**See also:** Interface sizing and cohesion rules are covered in depth in **3.1**.

### 3) Name and package by responsibilities

**Naming guidance**
- Prefer **capability names** over “manager/service” names: `IClock`, `IHasher`, `IUserStore`, `IPaymentAuthorizer`.
- Avoid “utility” abstractions like `IHelper`, `IService`, `IManager`—they don’t communicate contract.

**Where interfaces should live**
- Near the **primary consumer** or the **domain boundary** they represent—not in a generic “Contracts” mega-project that everything references.
- Keep cohesion high: when you change a concept, you want to change a small number of files/projects.

**Performance note**
- Maintainability choices often drive performance indirectly: clearer ownership boundaries reduce accidental allocations, unbounded caching, and “sync-over-async”.
