## 8.1. Correctness checklist: contracts, invariants, and substitution

1. **Keep contracts explicit** (nullability, exceptions, cancellation, thread-safety assumptions)
2. **Protect invariants** (abstract bases: keep invariant enforcement in non-virtual code where possible)
3. **Avoid “action at a distance”** (no virtual calls in constructors; avoid hidden side effects in interface defaults)

### 1) Keep contracts explicit (nullability, exceptions, cancellation, thread-safety assumptions)

**What “explicit” means in practice**
- **Nullability**: enable nullable reference types and annotate accurately. Don’t “sprinkle `!`” to silence warnings—fix the contract.
- **Exceptions**: decide what failures are *exceptional* vs *expected* and design accordingly (Try-patterns for expected, exceptions for exceptional).
- **Cancellation** (async APIs): accept a `CancellationToken` and document:
  - whether cancellation is *best effort*,
  - whether you throw `OperationCanceledException`,
  - and whether partial work is possible.
- **Thread-safety**: state whether the type is:
  - **thread-safe** (safe for concurrent use),
  - **thread-compatible** (safe if externally synchronized),
  - or **thread-confined** (must be used from one thread / one logical executor).

**Common mistakes that create production bugs**
- “It’s probably thread-safe” (assumptions become incidents).
- “It might return null but we didn’t annotate it” (NREs migrate to runtime).
- “Async method ignores cancellation” (thread pool pressure + slow shutdown).

**Minimal example (explicit async contract):**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

public interface IUserDirectory
{
    // Contract:
    // - Returns null if user is not found (explicitly annotated).
    // - Throws OperationCanceledException if cancellation is requested.
    ValueTask<User?> FindByIdAsync(Guid id, CancellationToken cancellationToken);
}

public sealed record User(Guid Id, string DisplayName);
```

**Good to know:** If “not found” is frequent, a `TryGet` shape can be even clearer than returning nullable.

### 2) Protect invariants (abstract bases: keep invariant enforcement in non-virtual code where possible)

**The mentor rule:** invariants belong in **non-virtual** code that you own. If an invariant is enforced by a virtual method that derived types can override, you don’t have an invariant—you have a suggestion.

**Safer patterns**
- **Template method with non-virtual orchestration**: base validates and sequences; derived supplies small, focused hooks.
- **Prefer composition** when the invariant is complex or security-sensitive.

**Example (base enforces invariants; derived provides hook):**

```csharp
using System;

public abstract class CommandHandler<TCommand>
{
    public void Handle(TCommand command)
    {
        if (command is null) throw new ArgumentNullException(nameof(command));
        Validate(command);     // base-controlled invariant checks
        HandleCore(command);   // derived hook
    }

    protected virtual void Validate(TCommand command) { } // optional strengthening within rules
    protected abstract void HandleCore(TCommand command);
}
```

**Pitfall:** Don’t allow derived code to bypass invariants (e.g., by making `Handle` virtual).

### 3) Avoid “action at a distance”

“Action at a distance” means behavior changes in non-obvious ways due to inheritance, defaults, or implicit contracts.

**Most common sources**
- **Virtual/abstract calls in constructors**: derived state isn’t initialized yet; behavior depends on half-built objects.
- **Default interface members**: behavior can appear “from nowhere” if you forget the interface has a default.
- **Overridable methods used for critical logic**: derived types can break assumptions.

**Rules of thumb**
- Don’t call virtuals from constructors. If you need polymorphic initialization, use factories or explicit init methods.
- Keep DIM defaults small and obviously correct (see **3.2**).
- Prefer `sealed` where appropriate to stabilize behavior and enable stronger optimization.
