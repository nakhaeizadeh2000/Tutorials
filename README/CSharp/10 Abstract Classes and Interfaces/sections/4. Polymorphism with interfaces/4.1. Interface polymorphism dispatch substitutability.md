## 4.1. Interface-based polymorphism: runtime dispatch and substitutability

1. **Substitutability (LSP framing)** (don’t strengthen preconditions or weaken postconditions in implementations)
2. **Runtime dispatch** (interface calls vs virtual calls; what the JIT can/can’t optimize)
3. **Testability and design** (mocking vs fakes; prefer composition; keep contracts precise)

### 1) Substitutability (LSP framing)

**Definition:** Substitutability (Liskov Substitution Principle) means: *if code works with the interface, it must work with any implementation of that interface* without needing special-case knowledge.

In practice, LSP is about **behavior**, not inheritance diagrams:
- Don’t make the implementation require *more* than the interface promised (stronger preconditions).
- Don’t make the implementation guarantee *less* than the interface promised (weaker postconditions).
- Don’t add surprising side-effects, timing, or threading behavior that violates what callers reasonably rely on.

**Concrete LSP rules mentors enforce**
- **Preconditions**: an implementation must accept *at least* what the contract accepts.
  - If the interface says “any non-empty string”, an implementation must not require “string must be ASCII”.
- **Postconditions**: an implementation must produce *at least* what the contract guarantees.
  - If the interface says “returns an item if it exists”, an implementation shouldn’t randomly return null or throw for a normal miss.
- **Exception behavior**: if callers treat an operation as “Try”, don’t throw for expected cases.
- **Thread-safety/cancellation**: if the contract says “thread-safe” or “cancellable”, implementations must honor it.

**Common mistakes**
- Using “marker” interfaces to hide behavioral constraints (e.g., `IRepository` but behavior differs wildly per impl).
- Silent behavior changes (one implementation caches aggressively, another hits DB every time) without documenting contract expectations.
- Returning different units/semantics under the same method name (e.g., `Timeout` meaning “total” vs “per-try”).

**Good to know:** If you’re struggling to keep implementations substitutable, that’s a sign your interface is too broad or mixing responsibilities. See **3.1** (interface surface rules) for how to split roles.

### 2) Runtime dispatch (interface calls vs virtual calls; what the JIT can/can’t optimize)

**What happens at runtime**
- **Non-virtual calls** are resolved at compile time and are easiest to inline/optimize.
- **Virtual calls** use vtables (class hierarchy dispatch).
- **Interface calls** use interface dispatch machinery (more complex; still very fast in most code).

**Mentor framing:** dynamic dispatch is a *design tool*, not “free”. The performance cost is often small, but the **optimization restrictions** can be significant in hot code (inlining/devirtualization).

**Devirtualization reality (high level)**
- The JIT can sometimes devirtualize when it can prove the concrete type (common with `sealed` types, internal methods, or when the receiver is known).
- You should not depend on this for correctness or baseline performance; design explicit fast paths for hot loops (see **4.2**).

**Virtual vs interface: which is “faster”?**
- In modern .NET, the difference is often negligible relative to the work you do inside the method.
- What dominates in real systems: **allocations**, **boxing**, **cache misses**, **contention**, and **I/O**, not the dispatch itself.

**Legacy patterns to avoid**
- `dynamic` dispatch for polymorphism (runtime binder, allocations, unpredictable errors). Prefer interfaces/virtual, or pattern matching.
- Reflection-based dispatch for regular flow (prefer generics, source generation, or explicit mappings if performance matters).

### 3) Testability and design (mocking vs fakes; prefer composition; keep contracts precise)

**Core idea:** interfaces create seams. But not every seam should be a mock.

**Prefer fakes over mocks when**
- You can create a small in-memory implementation that behaves like production (deterministic, fast).
- You want to test behavior end-to-end without brittle “interaction tests”.

**Prefer mocks when**
- The dependency is expensive or external (HTTP, DB, clock, random, filesystem) and a fake would be complex.
- You need to verify *a specific interaction* is part of the contract (rare; do this sparingly).

**Design habits that scale**
- Keep interfaces **small and cohesive**.
- Name by responsibility: `IClock`, `IEmailSender`, `IUserStore`, not `IService`.
- Make threading/cancellation part of the contract when relevant:
  - `Task<T> GetAsync(..., CancellationToken ct)`
  - document whether the implementation is thread-safe.

**Minimal, runnable example (polymorphism + test seam):**

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

public interface ITimeProvider
{
    DateTimeOffset UtcNow { get; }
    Task Delay(TimeSpan duration, CancellationToken ct);
}

public sealed class SystemTimeProvider : ITimeProvider
{
    public DateTimeOffset UtcNow => DateTimeOffset.UtcNow;
    public Task Delay(TimeSpan duration, CancellationToken ct) => Task.Delay(duration, ct);
}

public sealed class FakeTimeProvider : ITimeProvider
{
    private DateTimeOffset _now;
    public FakeTimeProvider(DateTimeOffset start) => _now = start;
    public DateTimeOffset UtcNow => _now;
    public Task Delay(TimeSpan duration, CancellationToken ct)
    {
        ct.ThrowIfCancellationRequested();
        _now = _now.Add(duration);
        return Task.CompletedTask;
    }
}

public sealed class ExpiringTokenService
{
    private readonly ITimeProvider _time;
    public ExpiringTokenService(ITimeProvider time) => _time = time;

    public bool IsExpired(DateTimeOffset expiresAt) => _time.UtcNow >= expiresAt;
}
```

**Performance note:** the abstraction itself is cheap; what matters is whether you accidentally allocate in hot paths (closures, LINQ, boxing). That’s the focus of **4.2**.
