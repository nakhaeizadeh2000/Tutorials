## 4.2. Performance traps with interfaces: boxing, allocations, and hot loops

1. **Boxing via interfaces** (value types implementing interfaces; accidental allocations; how to spot it)
2. **Generics as a performance tool** (avoid interface dispatch in tight loops; consider generic constraints)
3. **Collections and enumerators** (`IEnumerable<T>`/`IEnumerator<T>` patterns; avoid unnecessary materialization in hot paths)

### Before we start: “performance trap” framing

Interfaces are a great *design* tool, and in most application code their overhead is negligible. The traps happen when:
- the code is on a **hot path** (runs millions of times),
- the interface boundary causes **allocations** (boxing, iterator objects, delegate captures),
- the interface prevents the JIT from **inlining/devirtualizing** a tiny method.

If you’re not in a hot path, optimize for **clarity and correctness** first.

### 1) Boxing via interfaces

**Definition:** *Boxing* happens when a value type (struct) is converted to `object` or to an interface it implements. Boxing allocates on the managed heap and copies the value.

**Why it surprises people:** you don’t have to explicitly write `object` for boxing to happen. Passing a struct to an interface-typed parameter is enough.

**Example (boxing):**

```csharp
using System;
using System.Collections.Generic;

public interface ICounter
{
    int Next();
}

public struct Counter : ICounter
{
    private int _value;
    public int Next() => ++_value;
}

public static class Demo
{
    public static void Main()
    {
        ICounter c = new Counter(); // BOXING here: struct -> interface
        Console.WriteLine(c.Next());

        // Also boxes: struct stored in interface-typed collection.
        var list = new List<ICounter> { new Counter() };
        Console.WriteLine(list[0].Next());
    }
}
```

**How to spot it**
- Allocation spikes in a profiler (`dotnet-trace`, VS Profiler, PerfView).
- A lot of `System.ValueType` / “boxing” in allocation stacks.
- Interface-typed collections holding value-type implementations.

**How to avoid it**
- Use **generic constraints** to keep the value type unboxed:

```csharp
public static int SumNext<TCounter>(ref TCounter counter, int n)
    where TCounter : struct, ICounter
{
    var sum = 0;
    for (var i = 0; i < n; i++)
        sum += counter.Next(); // no boxing
    return sum;
}
```

- If the value must be used polymorphically via interface, consider:
  - switching the implementation to a `class`, or
  - using a closed set of cases with pattern matching, or
  - designing a non-interface fast path for hot code.

**Good to know**
- `Nullable<T>` can box too, depending on conversions.
- Boxing copies the struct; mutations to the boxed copy do not update the original value-type variable.

### 2) Generics as a performance tool

**Key idea:** When you can express polymorphism at **compile time**, generics often enable the JIT to:
- inline more aggressively,
- specialize code for concrete types,
- avoid interface dispatch and boxing.

**Two common patterns**

1) **Generic algorithm with constraints** (fast path):

```csharp
public interface IHasher
{
    int Hash(ReadOnlySpan<byte> data);
}

public static int HashMany<THasher>(THasher hasher, ReadOnlySpan<byte> data, int repeat)
    where THasher : struct, IHasher
{
    var h = 0;
    for (var i = 0; i < repeat; i++)
        h ^= hasher.Hash(data);
    return h;
}
```

2) **Dual-path API**: keep an interface for architecture, but offer a generic overload for hot paths:

```csharp
public static class Hashing
{
    public static int HashMany(IHasher hasher, ReadOnlySpan<byte> data, int repeat)
    {
        var h = 0;
        for (var i = 0; i < repeat; i++)
            h ^= hasher.Hash(data);
        return h;
    }

    public static int HashMany<THasher>(THasher hasher, ReadOnlySpan<byte> data, int repeat)
        where THasher : struct, IHasher
        => HashMany(hasher: (IHasher)hasher, data, repeat); // NOTE: this line would box!
}
```

**Important:** don’t accidentally defeat the generic fast path by casting to the interface (as shown). The *fast* overload must call interface members without boxing (i.e., constrained calls, or `ref` usage, or careful design).

**Good to know**
- Sometimes the best performance tool is **removing polymorphism** from the hot loop entirely (compute once outside, then run a concrete loop).
- Sealing classes and avoiding virtual members can improve inlining (but don’t micro-opt based on guesses).

### 3) Collections and enumerators (`IEnumerable<T>` / `IEnumerator<T>`)

**The trap:** `IEnumerable<T>` is a wonderful abstraction, but it often hides:
- **iterator allocations** (state machine objects for `yield return`),
- **delegate allocations/captures** (LINQ),
- **virtual/interface calls** per element,
- accidental **materialization** (`ToList`, `ToArray`) inside loops.

**Canonical mentor rule for hot paths:** prefer **pulling data into a loop** you control:
- use `for` over arrays/lists,
- use `ReadOnlySpan<T>` for contiguous memory (no allocation),
- use `CollectionsMarshal.AsSpan(list)` (advanced; version-sensitive; use with care),
- avoid LINQ in tight loops unless you have measured it and it’s acceptable.

**Example: avoid materialization inside a loop**

```csharp
using System.Linq;

public static int CountEvenSlow(IEnumerable<int> source)
    => source.Where(x => (x & 1) == 0).Count(); // can allocate iterators/delegates

public static int CountEvenFast(IReadOnlyList<int> source)
{
    var count = 0;
    for (var i = 0; i < source.Count; i++)
        if ((source[i] & 1) == 0) count++;
    return count;
}
```

**Good to know**
- LINQ is fine for many business workloads; the danger is “LINQ everywhere” in per-request hot paths or tight loops.
- If you need high throughput + low allocations in pipelines, consider `System.Threading.Channels` or `IAsyncEnumerable<T>` with care (deep dive lives in `Cuncurrent & Parallel`).

### Summary checklist (what to measure first)

- **Allocations**: boxing, iterator objects, closures/delegates.
- **Dispatch**: can the JIT inline? are you calling through interface in a tight loop?
- **Data shape**: are you enumerating via `IEnumerable<T>` when you really have a `List<T>`/array?
