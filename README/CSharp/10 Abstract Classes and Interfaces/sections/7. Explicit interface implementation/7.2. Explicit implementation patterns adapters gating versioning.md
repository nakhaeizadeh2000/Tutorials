## 7.2. Explicit implementation patterns: adapters, capability gating, and versioning

1. **Capability gating** (expose advanced operations only through a specific interface)
2. **Adapter/Decorator friendly designs** (wrap an implementation; forward members intentionally)
3. **Versioning and binary compatibility** (changing interface members; adding members with DIM vs breaking changes)

### 1) Capability gating

**Idea:** Sometimes a type has a “safe public surface” for most callers and an “advanced surface” intended for a specific subsystem. **Explicit interface implementation** lets you expose the advanced members *only when the caller explicitly opts in* by using the interface type.

**When this is a good fit**
- You have an object with an intentionally minimal public API, but an infrastructure layer needs extra knobs.
- You want to prevent accidental misuse (“sharp edges”) by typical consumers.
- You want to keep IntelliSense clean for the common case.

**When it’s a smell**
- You’re using explicit implementation to hide a messy API rather than fixing the design.
- The “advanced” member is actually necessary for normal correct usage (then it isn’t optional).

**Example: capability gated member**

```csharp
using System;

public interface ICache
{
    bool TryGet(string key, out string value);
}

public interface ICacheMaintenance
{
    // Sharp edge: intended for ops/admin code only.
    void Clear();
}

public sealed class MemoryCache : ICache, ICacheMaintenance
{
    public bool TryGet(string key, out string value)
    {
        // Minimal sample: pretend cache miss always.
        value = string.Empty;
        return false;
    }

    // Capability gated: not visible on MemoryCache unless cast to ICacheMaintenance.
    void ICacheMaintenance.Clear()
    {
        // Clear internal storage...
    }
}

public static class Demo
{
    public static void Main()
    {
        var cache = new MemoryCache();

        // cache.Clear(); // does not compile (by design)
        ((ICacheMaintenance)cache).Clear(); // explicit opt-in
    }
}
```

**Good to know:** this is also a way to keep a type mostly immutable/safe while still supporting controlled mutation internally.

### 2) Adapter/Decorator friendly designs

**Goal:** If your system uses interfaces to represent capabilities, you often need wrappers:
- **Adapters** to translate one interface to another.
- **Decorators** to add behavior (logging, caching, retry, metrics).

Explicit interface implementation helps wrappers stay focused and prevents them from expanding the public surface unintentionally.

**Decorator example (no extra public members):**

```csharp
using System;

public interface IGreeter
{
    string Greet(string name);
}

public sealed class Greeter : IGreeter
{
    public string Greet(string name) => $"Hello, {name}.";
}

public sealed class LoggingGreeter : IGreeter
{
    private readonly IGreeter _inner;

    public LoggingGreeter(IGreeter inner) => _inner = inner;

    string IGreeter.Greet(string name)
    {
        Console.WriteLine($"Greet({name})");
        return _inner.Greet(name);
    }
}
```

**Mentor tip:** Prefer **wrapping the interface**, not inheriting and overriding. It composes better and avoids fragile base class problems (see **2.3**).

### 3) Versioning and binary compatibility

**The rule:** With public contracts, versioning is not “what compiles today” — it’s “what keeps working for consumers you don’t control”.

**Interface versioning**
- Adding a new member to an interface is usually a **breaking change** for implementers.
- DIM can reduce that pain, but it’s a **library compatibility tool**, not a general app design pattern. See **3.2** for DIM trade-offs and guidance.

**Explicit implementation and versioning**
- Explicit implementations can help you add members without cluttering the main public surface.
- But they can also confuse consumers if behavior differs between “class view” and “interface view”. Keep behavior consistent; hide only the member *visibility*, not its semantics.

**Binary compatibility reminder**
- If you’re building reusable libraries, think about **source compatibility** and **binary compatibility** separately (see **1.2** for the canonical “public APIs are promises” framing).

**Performance note**
- Versioning strategies often affect performance indirectly: over-abstracted designs can add allocations/dispatch in hot paths. When performance matters, design a fast path explicitly (see **4.2**) and measure.
