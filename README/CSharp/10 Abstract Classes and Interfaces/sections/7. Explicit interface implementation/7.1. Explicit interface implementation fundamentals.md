## 7.1. Explicit interface implementation fundamentals: syntax and semantics

1. **Why it exists** (member name collisions; hide “plumbing” members from the public surface)
2. **Dispatch behavior** (explicit members accessible only via interface-typed reference)
3. **API design** (keep explicit implementations small; avoid surprising behavior differences between class and interface view)

### 1) Why it exists

**Definition:** *Explicit interface implementation* is when a class implements an interface member **without** exposing it as a normal public member on the class. The member is only callable through an **interface-typed** reference.

This exists mainly for:
- **Name collisions**: two interfaces require members with the same signature but different intent.
- **API hygiene**: keep “plumbing” members off the main public surface so IntelliSense and typical usage stays clean.
- **Different “views” of the same object**: the class has a rich API, and the interface is a narrow capability contract.

**Minimal syntax example:**

```csharp
public interface IResettable
{
    void Reset();
}

public sealed class Counter : IResettable
{
    public int Value { get; private set; }

    public void Increment() => Value++;

    void IResettable.Reset() => Value = 0; // explicit: not visible as Counter.Reset()
}
```

In typical code, you want `counter.Increment()`, and *only* callers who intentionally treat it as `IResettable` should see `Reset`.

**Good to know**
- Explicit implementation is a *strong signal*: “this member is part of a contract, not the preferred surface”.
- It’s often a good fit for **framework interfaces** you must implement but don’t want to advertise (e.g., infrastructure glue).

### 2) Dispatch behavior

**Key rule:** An explicitly implemented member is **not callable** on the concrete type; it’s callable only via the interface.

```csharp
Counter c = new();
// c.Reset(); // does not compile

((IResettable)c).Reset(); // works
```

**Why this matters**
- It makes the “interface view” explicit at the call site, which improves readability and reduces accidental coupling.
- It also clarifies which contract is in play when debugging issues (“why did this method run?”).

**Pitfall: two interfaces, same signature**

```csharp
public interface ITextSource { string Read(); }
public interface IFileSource { string Read(); }

public sealed class Source : ITextSource, IFileSource
{
    string ITextSource.Read() => "text";
    string IFileSource.Read() => "file";
}
```

This is valid, but **dangerous** if callers don’t strongly understand which interface they’re using. Prefer avoiding such collisions if you control the contracts (see **5.1** on ambiguity management).

**Performance note**
- The dispatch cost difference between explicit and implicit implementation is usually irrelevant.
- What matters more is whether you introduce allocations/boxing around interface usage (canonical treatment in **4.2**).

### 3) API design (mentor rules)

**Use explicit implementation when**
- You need to resolve a member name collision cleanly.
- You want to hide rarely-used operations from the main API surface (capability gating).
- You’re implementing an interface mainly for integration, not as the “primary” way your type should be used.

**Avoid explicit implementation when**
- The member is a core part of how the type is used (it becomes annoying that callers must cast).
- You need discoverability for beginners or broad team usage (casts can feel like “magic”).

**Keep behavior consistent**
- If you also provide a public method with similar meaning, ensure the **semantics match**; don’t make the interface call do something subtly different “because it’s hidden”.
- If you truly need different behavior, document it clearly and consider separate types instead.

**Good to know (testing)**
- Explicit members can make mocking/faking simpler: you can test via the interface while keeping the concrete API minimal.
- But don’t let the cast hide design problems: if you cast in many places, you probably need a better abstraction boundary.
