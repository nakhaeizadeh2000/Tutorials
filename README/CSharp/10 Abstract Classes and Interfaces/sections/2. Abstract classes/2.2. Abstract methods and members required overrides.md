## 2.2. Abstract methods and abstract members: designing required overrides safely

1. **Abstract methods** (derived must implement; define the minimal required surface)
2. **Template Method pattern (carefully)** (base orchestration + derived hooks; keep invariants in base)
3. **Constructor/initialization hazards** (never call virtual/abstract members from constructors; avoid “leaking `this`”)

### 1) Abstract methods: required overrides with a real contract

**Definition:** An **abstract method** (or property/event/indexer) declares *a required member* that has **no implementation** in the base type. Any non-abstract derived type must provide an override.

**When abstract methods are the right tool**
- You have a **stable base contract** and **the derived type must provide a piece of behavior** for the base logic to work.
- You’re building a framework-style base type where **derived classes provide “hooks”**.
- You want to enforce “you must supply X”, and you do *not* want a default.

**When they’re the wrong tool**
- You just want to reuse code. Prefer **composition** or **helpers** unless there’s a real “is-a” + contract.
- The hook is optional or rarely customized. Consider `virtual` with a safe default, or push the behavior out into an injected collaborator (`IStrategy`).

**What a mentor stresses (correctness):** an abstract member must come with a **behavioral contract**:
- Preconditions and validation rules
- Nullability and allowed states
- Side effects
- Exception policy
- Thread-safety expectations

If you can’t state the contract clearly, it’s a sign you’re forcing inheritance.

### 2) Template Method pattern (carefully): base controls invariants

**Goal:** Keep invariants and orchestration in the base class, while derived types customize only the minimal steps.

**Preferred shape (non-virtual public API + protected virtual/abstract hooks)**

```csharp
using System;

public abstract class MessageHandler
{
    // Non-virtual public method: base owns orchestration + invariants.
    public void Handle(ReadOnlySpan<char> message)
    {
        if (message.IsEmpty) throw new ArgumentException("Message must not be empty.", nameof(message));

        // Base controls the pipeline.
        var normalized = Normalize(message);
        OnHandleCore(normalized);
        OnAfterHandle(normalized);
    }

    protected virtual ReadOnlySpan<char> Normalize(ReadOnlySpan<char> message) => message.Trim();

    // Required customization point.
    protected abstract void OnHandleCore(ReadOnlySpan<char> normalized);

    // Optional hook with default behavior.
    protected virtual void OnAfterHandle(ReadOnlySpan<char> normalized) { }
}

public sealed class AuditMessageHandler : MessageHandler
{
    protected override void OnHandleCore(ReadOnlySpan<char> normalized)
    {
        // Handle the message. Keep it deterministic and respect the base contract.
        Console.WriteLine($"AUDIT: {normalized.ToString()}");
    }
}
```

**Why this is safer**
- Callers see a stable `Handle` contract (no override surprises).
- Derived classes can’t bypass base validation unless you allow it.
- You can change internal steps without breaking external callers (but you must preserve derived hooks’ contracts).

**Common mistakes**
- Making the *public* entry point virtual (`public virtual void Handle(...)`) and hoping derived types “do the right thing”.
- Requiring derived classes to call `base.X()` without enforcing it. If base must run, base should own the entrypoint.

**Performance note:** Template Method itself is not a performance problem; the danger is *hidden* work in hooks (allocations, blocking, locks). Keep hooks small and document expectations.

### 3) Constructor/initialization hazards: the “virtual call during construction” trap

**Rule:** Don’t call `virtual`/`abstract` members from constructors (base or derived), finalizers, or field initializers.  
This is a correctness issue, not style.

**Why it’s dangerous**
- During base construction, the derived object is not fully initialized, but **virtual dispatch still targets the derived override**.
- Derived fields may still be default values, leading to null refs, invalid invariants, or subtle bugs.

**Bad example**

```csharp
public abstract class Base
{
    protected Base() => Initialize(); // calls derived override too early
    protected abstract void Initialize();
}

public sealed class Derived : Base
{
    private readonly string _path;
    public Derived(string path) => _path = path;
    protected override void Initialize() => Console.WriteLine(_path.Length); // _path may be null here
}
```

**Safe alternatives**
- Use a **static factory** that constructs then calls an initialization method.
- Or use a **two-phase init** pattern where initialization is called explicitly after construction.
- Or move initialization into non-virtual base logic and pass needed data via constructor parameters.
