## 3.2. Default interface members (DIM): when to use and when to avoid

1. **Why DIM exists** (versioning: add members without breaking implementations)
2. **Costs/risks** (surprising behavior, dispatch complexity, testing ambiguity, trimming/AOT considerations)
3. **Guidance** (use for carefully designed “traits” / versioning; avoid as a “mixin replacement” in typical apps)

### 1) Why DIM exists

**Definition:** *Default Interface Members* (DIM) let an interface provide a **default implementation** for a member. Implementing types can override that member, but they don’t have to.

Historically, adding a method to a public interface was a **breaking change** because every implementer had to implement the new method. DIM exists primarily to improve **library versioning**: you can add new capabilities without breaking existing implementers.

**What DIM enables**
- Adding a new method with a default implementation.
- Providing shared helper logic in an interface (carefully).
- Evolving “capability contracts” where you truly want multiple implementations, but you also want to grow the contract.

**Minimal example (versioning intent):**

```csharp
public interface IWidgetRenderer
{
    string Render();

    // Added in v2 without breaking old implementers:
    string RenderDebug() => $"[DEBUG] {Render()}";
}
```

**Good to know**
- DIM is **not** about making interfaces “like abstract classes”. It’s a constrained tool for compatibility.
- DIM interacts with interface dispatch rules and can surprise developers who think “interfaces have no behavior”.

### 2) Costs/risks

**Behavior surprises**
- Callers may get behavior they didn’t expect because the interface provides a default.
- Different call sites can observe different behavior depending on whether the receiver is typed as the interface or as the concrete type (especially when combined with explicit implementations; see **7.1**).

**Design ambiguity**
- DIM can blur “contract” vs “implementation”: when a default exists, is it part of the semantic contract or a convenience?
- If a default implementation changes across versions, you may create subtle behavioral changes in apps that didn’t recompile.

**Dispatch complexity**
- Interface dispatch is already more complex than non-virtual calls; DIM adds more possibilities.
- You can create “diamond” ambiguity with multiple interfaces providing defaults for the same member name (see **5.2** for the canonical ambiguity discussion).

**Testing and mocking**
- Some mocking approaches treat default interface implementations differently, and tests can accidentally validate the default rather than the intended override.
- Fakes that rely on defaults can mask missing behavior in real implementations.

**Trimming/AOT considerations**
- DIM itself isn’t “unsupported”, but any design that relies on reflection/dynamic loading + complex dispatch increases risk under trimming/native AOT.
- Library APIs intended for native AOT and trimming should be especially conservative with DIM and document behavior clearly.

### 3) Guidance (mentor-grade rules)

**Use DIM when**
- You are authoring a **public interface** consumed by third parties and you need to add a member without breaking implementers.
- The default implementation is **obviously correct**, stable, and can be expressed in terms of existing members.
- You can clearly state the semantic contract: “If you don’t override, you get this behavior.”

**Avoid DIM when**
- You’re trying to emulate “multiple inheritance of behavior” or mixins in application code.
- The default implementation would be complex, stateful, or performance-critical.
- You’d need the default implementation to access shared state (interfaces don’t have instance fields; if you need state, that’s an abstract class or composition problem).

**Prefer these alternatives in typical apps**
- **Extension methods** for optional helper functionality that shouldn’t be part of the contract.
- **Abstract base classes** when shared state/implementation is essential and you can control inheritance (see **2.3**).
- **Composition**: inject a helper/service rather than inheriting behavior.

**Performance note**
- Don’t use DIM as a micro-optimization trick. If performance matters, design explicit fast paths (see **4.2**) and measure with real workloads.
