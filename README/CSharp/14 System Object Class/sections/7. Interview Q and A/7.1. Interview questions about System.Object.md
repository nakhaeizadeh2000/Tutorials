### 1) **What methods does every .NET type have?** (and what the defaults do)

**Core fact**

Every .NET type has a relationship to `System.Object`:

- Every **class** derives (directly or indirectly) from `System.Object`.
- Every **struct** derives from `System.ValueType`, which derives from `object` (and can become an `object` via boxing).

That means you always have (at least) these instance methods available:

- `Equals(object?)`
- `GetHashCode()`
- `ToString()`
- `GetType()`

And these are also part of the practical “object contract”:

- `ReferenceEquals(object? a, object? b)` (static)
- `MemberwiseClone()` (protected on `object`)

**What the defaults do (high level)**

- **`GetType()`**: returns the *exact runtime type*; not virtual; used for diagnostics, reflection, and (carefully) type-based decisions.
- **`ToString()`**: default is typically the type name; useful for debugging but rarely domain-meaningful.
- **`Equals(object?)` / `GetHashCode()`**:
  - On `object` (for reference types): default is reference identity (two references are equal only if they point to the same object).
  - Many framework types override for value semantics (`string`, numerics, `DateTime`, `Guid`, records, etc.).

**Mentor note**

In interviews, explicitly separate these three ideas:

- **Identity**: “same instance” (`ReferenceEquals` / default `object.Equals` for classes)
- **Value equality**: “same value” (custom `Equals`, records, many BCL types)
- **Ordering**: `IComparable<T>`; not the same as equality

See:
- `2.1`–`2.6` for each method’s intent and pitfalls.
- `3.1`–`3.3` for overriding/equality design strategy.

### 2) **Explain `Equals` vs `==` vs `ReferenceEquals`** (with real examples and pitfalls)

**The short, correct definition**

- **`Equals`** expresses **semantic equality** (whatever your type decides equality means).
- **`==`** is an **operator**: it might mean identity (default for most classes), might be overloaded for value equality (like `string`), and for value types it’s usually value-based if defined.
- **`ReferenceEquals`** ignores overloads and tells you **identity** (same object reference).

**Key pitfalls interviewers expect you to mention**

- **Overloaded `==` can lie about identity** (intentionally). Example: `string` overloads `==` for value equality, so:

```csharp
using System;

string a = new string(['h', 'i']);
string b = new string(['h', 'i']);

Console.WriteLine(a == b); // True (value equality)
Console.WriteLine(object.ReferenceEquals(a, b)); // False (different objects)
```

- **`Equals` must agree with `GetHashCode`** for hash collections (see Q3 below).
- **Null handling**: `ReferenceEquals(null, null)` is `true`; calling `x.Equals(...)` when `x` is null will throw—so you typically use:
  - `x is null` checks
  - `EqualityComparer<T>.Default.Equals(x, y)` for generic code

**One safe generic equality pattern**

```csharp
using System.Collections.Generic;

static bool Same<T>(T? x, T? y) => EqualityComparer<T>.Default.Equals(x, y);
```

### 3) **Why must `GetHashCode` align with `Equals`?** (and what breaks when it doesn’t)

**The rule**

If `x.Equals(y)` is `true`, then `x.GetHashCode()` **must** equal `y.GetHashCode()`.

The reverse is not required (hash collisions are allowed), but good distribution is a performance feature.

**What breaks**

Hash-based collections (`Dictionary<TKey, TValue>`, `HashSet<T>`) use the hash code to find the bucket, then `Equals` to find the element.

- If equal objects have different hashes, the collection can’t find them reliably.
- If hash codes change while in a set/dictionary, entries become “lost”.

**Classic production bug**

Mutable key:

```csharp
using System;
using System.Collections.Generic;

sealed class BadKey
{
    public int Id { get; set; }
    public override bool Equals(object? obj) => obj is BadKey other && other.Id == Id;
    public override int GetHashCode() => Id;
}

var key = new BadKey { Id = 1 };
var dict = new Dictionary<BadKey, string> { [key] = "v" };

key.Id = 2; // mutated after insertion
Console.WriteLine(dict.ContainsKey(key)); // often False
```

**Mentor note**

If your type can be a dictionary key, the fields that participate in equality/hashing must be **effectively immutable** while used as a key.

See `2.4` for hash-code specifics and `5.1` for the production checklist.

### 4) **What is boxing/unboxing and why does it matter for performance?**

**Short answer**

- **Boxing**: value type → `object` / interface reference. Usually allocates a heap object and copies the value.
- **Unboxing**: extracting a value type from a boxed object. Requires an exact type match.

**Why it matters**

Boxing introduces:

- **Allocations** (GC pressure under load)
- **Loss of static typing** (more runtime checks, fewer compiler guarantees)
- Often **lost optimizations** (e.g., interface dispatch and object-based pipelines are harder to optimize)

### 5) **How do records change equality design?** (and when you should not use record equality)

**What records do**

- `record` (class): reference type with *value-based* `Equals`/`GetHashCode` generated over its components.
- `record struct`: value type with *value-based* equality generated over its components.

That means records naturally behave like value objects (when you model them that way).

**When record defaults are wrong**

- **Entities** with identity semantics (e.g., `Customer` where equality should be by `Id`).
- Types with fields you must exclude from equality (e.g., caches, timestamps, non-semantic metadata).
- Performance-sensitive deep graphs where structural equality is expensive or surprising.

**Mentor note**

Records are great, but don’t let the “nice syntax” choose your semantics:

- Decide **identity vs value** first.
- Then choose record/class/struct accordingly.

See `3.3` for the full details and examples.
