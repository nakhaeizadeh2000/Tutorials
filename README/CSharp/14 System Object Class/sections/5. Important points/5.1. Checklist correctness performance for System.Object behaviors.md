## 5.1. Checklist: correctness and performance for `System.Object` behaviors

1. **If you override equality, you must override hashing** (and keep it stable)
2. **Never use mutable objects as dictionary keys** (unless you *prove* the key fields never change)
3. **Don’t treat `ToString()` as data** (logging/debug only; define explicit serialization formats elsewhere)
4. **Avoid `object`-typed “catch-all” APIs in hot paths** (they invite boxing, type checks, and runtime failures)
5. **Measure before “optimizing”** (but treat broken hash/equality as correctness *and* performance bugs)

---

### 1) **If you override equality, you must override hashing** (and keep it stable)

**Mentor rule**: `Equals` and `GetHashCode` form a *single contract*. If you customize one, you almost always must customize the other.

**What must be true**

- If `a.Equals(b)` is `true`, then `a.GetHashCode()` **must** equal `b.GetHashCode()`.
- A hash code does **not** need to be unique. Collisions are allowed, but too many collisions destroy performance.
- Hash codes used by hash tables (e.g., `Dictionary<TKey, TValue>`, `HashSet<T>`) must be **stable** for as long as the object is used as a key.

**Common mistakes**

- Overriding `Equals` but forgetting `GetHashCode` (or vice versa).
- Using mutable fields in hashing/equality for keys.
- Using `ToString()` as a hash input (slow, allocates, and can change over time).
- “Randomized” hashes per call (breaks dictionaries).

**Good implementation shape (class value object)**

```csharp
using System;

public sealed class Money : IEquatable<Money>
{
    public decimal Amount { get; }
    public string Currency { get; } // e.g., "USD"

    public Money(decimal amount, string currency)
    {
        Amount = amount;
        Currency = currency ?? throw new ArgumentNullException(nameof(currency));
    }

    public bool Equals(Money? other)
        => other is not null
           && Amount == other.Amount
           && string.Equals(Currency, other.Currency, StringComparison.Ordinal);

    public override bool Equals(object? obj) => obj is Money m && Equals(m);

    public override int GetHashCode()
        => HashCode.Combine(Amount, StringComparer.Ordinal.GetHashCode(Currency));
}
```

**Performance note**

- Bad hashing is not a “micro-optimization” issue. It can turn near-\(O(1)\) operations into effectively linear-time behavior under adversarial or accidental collision patterns.
- `HashCode.Combine` is a good default. Don’t invent your own mixing unless you have a measured reason.

**Good to know**

- When you can, prefer `record` / `record struct` for value objects: you get consistent, tested equality+hashing generation. See `3.3. Records and generated equality`.

### 2) **Never use mutable objects as dictionary keys** (unless you *prove* the key fields never change)

This is the number one “my dictionary is haunted” production bug.

**What goes wrong**

Hash tables bucket keys by hash code. If the fields contributing to equality/hash change after insertion, the key becomes unreachable: lookups compute a new bucket and miss the original entry.

**Bad example (runnable)**

```csharp
using System;
using System.Collections.Generic;

public sealed class MutableKey
{
    public int Id { get; set; } // mutable
    public override int GetHashCode() => Id;
    public override bool Equals(object? obj) => obj is MutableKey other && other.Id == Id;
}

var dict = new Dictionary<MutableKey, string>();
var key = new MutableKey { Id = 1 };
dict[key] = "value";

key.Id = 2; // mutate key after inserting
Console.WriteLine(dict.ContainsKey(key)); // usually false
```

**Safe patterns**

- Make key types **immutable** (preferred).
- Use an **immutable ID** as the key (`Guid`, `int`, `CustomerId` value object).
- If the object must be mutable, **do not** use it as a key; use a separate immutable key.

**See also**

For the full equality/hashing and collections discussion (including entity vs value object semantics), see [3.2. Equality hashing and identity in collections](<../../../03 CSharp Basic Object Oriented Programming/sections/3. Important points about objects/3.2. Equality hashing and identity in collections.md>).

### 3) **Don’t treat `ToString()` as data** (logging/debug only; define explicit serialization formats elsewhere)

**What `ToString()` is for**

- A human-friendly representation for debugging, logs, and diagnostics.
- A best-effort summary: *readable, stable enough for humans, and non-throwing*.

**What it is not**

- A wire format.
- A persistence format.
- A stable contract you can parse in another component.

**Why this matters**

- `ToString()` is allowed to change between versions (including in the BCL).
- `ToString()` is often culture-sensitive if you’re not careful.
- Parsing `ToString()` turns “display” into a brittle runtime dependency.

**Modern replacements**

- For persistence/wire: define explicit serialization (e.g., JSON with explicit converters, or a stable textual format).
- For parsing: use `TryParse`/`Parse` on the specific type or create a domain type with `TryCreate`.

**See also**

For `ToString()` design details, performance, and modern formatting (`ISpanFormattable`, `TryFormat`, interpolated string handlers), see `2.2. ToString as a debugging contract not serialization`.

### 4) **Avoid `object`-typed “catch-all” APIs in hot paths** (they invite boxing, type checks, and runtime failures)

This isn’t about banning `object`; it’s about **making the performance and correctness costs explicit**.

**What goes wrong with “catch-all object”**

- **Boxing allocations** for structs and primitives.
- **Type checks** scattered around (`is`, `switch`, casts).
- **Runtime failures** (`InvalidCastException`) in places that should be compile-time errors.
- **Lost optimizations**: the JIT can’t specialize what it can’t see.

**Better API shapes**

- Prefer generics:

```csharp
public static void Add<T>(List<T> list, T item) => list.Add(item);
```

- Prefer discriminated designs at boundaries:
  - a small `enum` + payload,
  - a dedicated DTO hierarchy,
  - a `OneOf`-style union (library) when appropriate.

**When `object` is acceptable**

- Serialization frameworks, reflection-based tooling, DI containers.
- “Edge” layers where the shape is genuinely unknown until runtime.

**See also**

- For deep boxing/unboxing mechanics: [3.3. Boxing unboxing and hidden allocations](<../../../06 Type Conversion/sections/3. Explicit conversions and casts/3.3. Boxing unboxing and hidden allocations.md>).
- For object-centric guidance on boxing and object pipelines: `4.1. Boxing and unboxing: why object can allocate`.

### 5) **Measure before “optimizing”** (but treat broken hash/equality as correctness *and* performance bugs)

**What to measure**

- Allocations (boxing, string building, `params object[]`).
- Dictionary/HashSet performance under realistic key distributions.
- Hot-path behavior under load (not on a micro benchmark only).

**Tools**

- `dotnet-counters`, `dotnet-trace`, `dotnet-dump`
- IDE profilers (CPU + memory)
- BenchmarkDotNet for *micro* performance hypotheses (with correct setup)

**Mentor framing**

- Don’t prematurely contort code to avoid tiny costs.
- Do treat equality/hashing and accidental boxing as *systemic* risks: they show up under load, in GC pressure, and in “mystery dictionary failures”.
