## 4.2. Avoiding boxing in modern C# (without “micro-optimizing”)

1. **Prefer generic APIs** (avoid `object` parameters for value-typed data paths)
2. **Avoid non-generic collections and non-generic interfaces in hot paths**
3. **Formatting/logging pitfalls** (`params object[]`, string interpolation, and “hidden” boxing; prefer structured logging)

### 1) **Prefer generic APIs** (avoid `object` parameters for value-typed data paths)

**Core idea**

If your data is conceptually \(T\), your API should accept \(T\) — not `object`. Once you accept `object`, you:

- lose compile-time type checking,
- often introduce **boxing** for value types,
- make consumers pay for **casts and runtime failures**,
- block the JIT from optimizing (devirtualization/inlining becomes harder once values go through `object`).

**Example: “objecty” vs generic comparer**

```csharp
using System;
using System.Collections.Generic;

static class Demo
{
    static void Main()
    {
        var ints = new List<int> { 3, 1, 2 };
        ints.Sort(); // uses Comparer<int>.Default, no boxing

        // Avoid APIs that force object comparisons/parameters for value types.
    }
}
```

**Good to know**

- Prefer `EqualityComparer<T>.Default`, `Comparer<T>.Default`, `IEqualityComparer<T>`, `IComparer<T>` (generic) over non-generic comparers.
- Prefer `TryParse`/typed parsing pipelines over `object`-typed “values”.

### 2) **Avoid non-generic collections and non-generic interfaces in hot paths**

**Legacy patterns to avoid**

- `ArrayList`, `Hashtable` (non-generic collections)
- non-generic `IComparable`, `IEqualityComparer`, `IEnumerable` (when there is a generic alternative)

These patterns often exist for historical reasons and frequently **box structs**.

**Modern replacements**

- Use `List<T>`, `Dictionary<TKey, TValue>`, `HashSet<T>`, `IEnumerable<T>`, `IReadOnlyList<T>`, etc.
- Use `IComparable<T>`, `IEquatable<T>` and `IEqualityComparer<T>` (generic) where appropriate.

**Performance note**

Boxing here isn’t just “one allocation”. It also creates:

- more GC work under load,
- more indirection (worse cache locality),
- more dynamic dispatch / runtime checks.

If the code is not a hot path, don’t cargo-cult micro-optimizations. But if it is (parsers, telemetry, tight loops), **object-based APIs are almost always the wrong shape**.

### 3) **Formatting/logging pitfalls** (`params object[]`, string interpolation, and “hidden” boxing; prefer structured logging)

**The trap**

Any API shaped like `Log(string template, params object[] args)` (or similar) creates two common costs:

- the `object[]` allocation,
- boxing of value types inside that array.

**Prefer modern, C#-15 era approaches**

- If you need a string: use interpolation *intentionally* (it may still allocate the final string; that’s fine when you actually need it).
- For high-volume logging: prefer structured logging libraries/frameworks that support **interpolated string handlers** so the work can be skipped when the log level is disabled.

**Minimal example (demonstrating the allocation shape)**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        int x = 123;
        Console.WriteLine("x = {0}", x); // boxes x + allocates object[] (params)

        Console.WriteLine($"x = {x}");   // no boxing, but allocates a string (expected)
    }
}
```

**Mentor rule**

Don’t fight allocations where they don’t matter. Fight the ones that are:

- accidental,
- repeated,
- and in hot paths.

If a profiler shows unexpected allocations, search for `object`, non-generic interfaces/collections, and `params object[]`.
