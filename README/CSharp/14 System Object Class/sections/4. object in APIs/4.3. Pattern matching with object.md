## 4.3. Pattern matching with `object` (modern casting, safer branching)

1. **`is` patterns** (type patterns, property patterns, relational patterns for guards)
2. **Avoiding double work** (one match → one strongly typed variable)
3. **Maintainability** (pattern matching is great for boundaries; avoid turning core logic into a big `switch` on types)

### 1) **`is` patterns** (type patterns, property patterns, relational patterns for guards)

**Definition**

Pattern matching is the modern C# way to *test and extract* shape/type information in one expression. It replaces a lot of legacy code that was either unsafe (casts) or verbose (`as` + null-check + cast again).

**The patterns you actually use in production**

- **Type pattern**: check type and capture
- **Null pattern**: `is null` / `is not null` (reads better than `== null` in some contexts, and works cleanly with nullable analysis)
- **Property pattern**: inspect properties safely
- **Relational / logical patterns**: `is >= 0 and <= 100` for guards

**Example (runnable): boundary parsing without “double work”**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        object? input = "42";

        var result = input switch
        {
            null => "missing",
            int i => $"int {i}",
            string s when int.TryParse(s, out var i) => $"parsed {i}",
            _ => "unsupported"
        };

        Console.WriteLine(result);
    }
}
```

**Good to know**

- Use pattern matching mostly at **boundaries** (deserialization, config, dynamic inputs, interop). In core domain code, prefer strongly typed APIs.
- If you find yourself switching on lots of unrelated runtime types, that’s often a design smell: the code is doing a role best served by polymorphism, a discriminated union shape, or a strong domain model.

### 2) **Avoiding double work** (one match → one strongly typed variable)

**Problem**

A common anti-pattern is “check then cast”, which duplicates work and is easy to get wrong:

```csharp
// Avoid: two operations and easy to drift.
if (o is string)
{
    var s = (string)o;
    Console.WriteLine(s.Length);
}
```

**Modern pattern**

```csharp
if (o is string s)
{
    Console.WriteLine(s.Length);
}
```

Or for multiple types, prefer `switch` expressions:

```csharp
int length = o switch
{
    string s => s.Length,
    Array a => a.Length,
    _ => 0
};
```

**Performance note**

- `is T t` is typically cheap; it avoids exceptions and keeps control-flow explicit.
- The *big* perf win is usually **not** the `is` check itself; it’s avoiding the “object pipeline” that forces boxing/casting and reduces compile-time guarantees.

### 3) **Maintainability** (pattern matching is great for boundaries; avoid turning core logic into a big `switch` on types)

**Mentor framing**

- Pattern matching is a tool to handle **uncertainty** (unknown runtime input).
- Your goal is to make uncertainty *local*: accept `object?` at the edge, convert once, then work with strong types.

**When a big `switch` is a smell**

- Your `switch` grows over time as new types are introduced.
- Multiple places in the codebase have similar switches (duplication).
- Adding a new “kind” requires editing many switches (violates open/closed).

**Preferred replacements**

- **Polymorphism**: virtual/interface methods, when “kinds” are stable and owned by your code.
- **Data + strategy**: lookup dictionary from type/token → handler.
- **Strong discriminated shapes**: `enum` + data, or “union” style wrappers; use pattern matching *over your own* union instead of `object`.
