## 3.3. Records, record structs, and “generated” equality (C# 15 era)

1. **What you get by default** (value-ish equality for records; how positional members participate)
2. **When defaults are wrong** (identity-based entities; ignoring fields; normalization/canonicalization)
3. **Performance and API design** (immutability vs allocations; careful with large graphs and deep comparisons)

### 1) **What you get by default** (value-ish equality for records; how positional members participate)

**Key point**: records *change the default* from identity-based equality to **structural equality** (by value of members), but *only* for the record’s **own contract**.

- **`record` (class)**: reference type with generated equality members. Two record instances can be `Equals` even when they are different objects (different identity).
- **`record struct`**: value type with structural equality; no allocation for the value itself, but beware of copying for large structs.

**What the compiler generates (high-level)**:

- `Equals(object?)` and a strongly-typed `Equals(T?)` (for `record` class) / `Equals(T)` (for `record struct`)
- `GetHashCode()`
- `==` and `!=`
- For `record` class: a protected `EqualityContract` used to help with equality semantics in inheritance

**Positional vs non-positional members**

- In a positional record (`record Person(string First, string Last)`), the **primary constructor parameters** become properties and participate in equality/hash.
- Additional fields/properties also participate if they are in the synthesized equality contract (for typical records, *instance fields/properties* declared in the record are included; be explicit and test your expectation).

**Example: two objects, same value**:

```csharp
public record CustomerName(string First, string Last);

var a = new CustomerName("Ada", "Lovelace");
var b = new CustomerName("Ada", "Lovelace");

Console.WriteLine(ReferenceEquals(a, b)); // False (different objects)
Console.WriteLine(a == b);                // True  (structural equality)
```

**Good to know**

- Records are great for **DTOs, request/response models, value objects** where “same data” means “same value”.
- Records are not automatically “immutable”; immutability depends on your member design (init-only, private setters, etc.).

### 2) **When defaults are wrong** (identity-based entities; ignoring fields; normalization/canonicalization)

Records are dangerous when:

- The type is an **entity** (identity matters more than data), e.g. `Customer`, `Order`, `AggregateRoot`.
- Some fields should **not** participate in equality (timestamps, caches, lazy-loaded navigation properties, correlation IDs, computed transient state).
- Values require **canonicalization** (case normalization, trimming, culture rules) that the default equality won’t do.

**Rule of thumb**

- If you will ever say “these two instances are different even if all current fields match”, do **not** use default record equality for that type.

**Entity example (bad as record equality)**:

```csharp
public record Customer(Guid Id, string Name); // often wrong as an entity
```

Two distinct “Customer snapshots” from different times could compare equal if `Id` and `Name` match, even if they represent different lifecycle states in your domain. For entities, prefer **identity-based equality** (by immutable ID) or do not override at all and use explicit comparers.

**Ignoring fields**

If a field must be ignored, you usually have two options:

1. **Don’t use record equality** (use class/struct with explicit equality), or
2. Split the type: keep the value-equality part as a record (e.g. `CustomerId`, `CustomerName`) and keep the entity as a class.

**Normalization/canonicalization**

If equality should treat `"Alice "` and `"alice"` as equal, default record equality won’t do that unless you normalize at construction time (recommended).

```csharp
public sealed record EmailAddress
{
    public string Value { get; }

    public EmailAddress(string value)
        => Value = value.Trim().ToUpperInvariant(); // canonical form

    public override string ToString() => Value;
}
```

**Performance note**

Normalization strategies are a trade-off:

- Normalize once at creation: faster comparisons, consistent behavior.
- Normalize at comparison time: repeated cost and easy to get inconsistent.

---

### 3) **Performance and API design** (immutability vs allocations; careful with large graphs and deep comparisons)

**Immutability and allocations**

- `record` (class) instances allocate like any other object.
- `record struct` avoids allocation for the value itself, but may copy more in pass/return scenarios.

Choose based on **semantics first**, then performance:

- If identity and mutation matter: a `class` entity is often correct.
- If “a value” matters: a `record struct` or `readonly record struct` can be a great fit.

**Large graphs and deep comparisons**

Record equality is **member-wise**. If your record holds references to large collections or graphs, equality can become unexpectedly expensive and can even be **non-terminating** if you build cycles and implement deep equality yourself.

Mentor guidance:

- Keep records **shallow** (small number of scalar/value-object fields).
- Avoid putting **collections** as equality participants unless you truly want sequence-based equality and can afford it.
- Prefer explicit comparers (`IEqualityComparer<T>`) for “special-purpose” equality (e.g., case-insensitive, tolerance-based, partial comparisons).
