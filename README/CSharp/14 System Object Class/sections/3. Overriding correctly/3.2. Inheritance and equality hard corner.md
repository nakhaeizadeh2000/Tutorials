## 3.2. Inheritance + equality: the hardest corner

1. **Why it’s hard** (Liskov + substitutability + transitivity break easily)
2. **Design guidance** (prefer sealed value objects; prefer composition; be explicit about base/derived equality strategy)
3. **Type checks** (`GetType()` vs `is` in equality) and the trade-offs

### 1) **Why it’s hard** (Liskov + substitutability + transitivity break easily)

If you remember only one thing: **value equality + inheritance is where many “perfectly reasonable” implementations become mathematically invalid**.

The tension comes from three forces:

- **Substitutability (LSP)**: if `Derived : Base`, then a `Derived` instance must be usable anywhere a `Base` is expected.
- **Equality laws**: equality must be reflexive, symmetric, and transitive.
- **Evolving type hierarchies**: the moment you add a derived type, the “meaning” of base equality can shift.

#### The classic transitivity trap

Suppose `Base` equality ignores derived fields (because `Base` knows nothing about them):

- `b` (Base) equals `d1` (Derived with extra field = 1)
- `b` (Base) equals `d2` (Derived with extra field = 2)
- But `d1` must **not** equal `d2` if their extra fields matter

That breaks **transitivity**.

If you instead make `Derived` compare only base fields to preserve transitivity, you often break **domain semantics** (the derived field becomes “invisible” to equality).

#### Add `GetHashCode()` and collections get involved

Even if you “mostly” get equality right, **hash-based collections amplify tiny mistakes into production bugs**:

- `Dictionary<Base, TValue>` may store both `Base` and `Derived` keys.
- If base/derived types compute hash codes differently, lookups can fail even if `Equals` sometimes returns true.

**Good to know**: If your type participates in inheritance, the safest default is usually **identity equality** (don’t override) unless you have a very strong reason.

### 2) **Design guidance** (prefer sealed value objects; prefer composition; be explicit about base/derived equality strategy)

#### Mentor rule: “Value objects should be sealed”

If a type uses **value semantics** (its equality is based on fields), it should usually be:

- a `readonly record struct` (value type) or `record` (reference type), or
- a **sealed** class implementing `IEquatable<T>`

Sealing prevents the “someone derived from it later” problem from invalidating your equality contract.

#### Prefer composition over inheritance for “value + extra fields”

Instead of `Derived : Base`, model the relationship as **composition**:

```csharp
public sealed record BaseValue(int A, int B);

public sealed record ExtendedValue(BaseValue Base, int Extra);
```

Now equality is local and explicit; no LSP traps, no cross-type equality ambiguity.

#### If you must use inheritance: choose one of these strategies intentionally

There is no universally “correct” strategy, but there are **defensible** ones. Pick one and document it.

- **Strategy A: No cross-type equality (recommended for most class hierarchies)**  
  - Only equal if `GetType()` is exactly the same type.
  - Pros: preserves symmetry/transitivity; avoids surprises in collections.
  - Cons: base-typed code comparing base vs derived returns false even if they share “base values”.

- **Strategy B: Treat the base as an “equivalence class” (rarely a good idea)**  
  - Base equals derived if base fields match; derived ignores its extra fields or forces them irrelevant.
  - Pros: sometimes matches an intentional “projection” semantics.
  - Cons: derived fields become meaningless; very easy to create bugs.

When you’re writing libraries or domain models, **Strategy A is usually what you want**.

### 3) **Type checks** (`GetType()` vs `is` in equality) and the trade-offs

This choice is the “dial” that sets Strategy A vs Strategy B.

#### `GetType()` check (exact type equality)

```csharp
public override bool Equals(object? obj)
    => obj is not null
       && obj.GetType() == GetType()
       && Equals((MyType)obj);
```

- **Meaning**: only same runtime type can be equal.
- **Best for**: value equality on classes that might be inherited from (or where you want to forbid cross-type equality).
- **Pitfall**: if you later *want* cross-type equality, you can’t “add it” without breaking existing behavior.

#### `is` pattern (allows derived types to compare equal)

```csharp
public override bool Equals(object? obj)
    => obj is MyBase other && Equals(other);
```

- **Meaning**: derived types can be considered equal to base, depending on `Equals(MyBase)` implementation.
- **Best for**: very controlled hierarchies where the base type defines the full equality semantics.
- **Pitfall**: this is where transitivity breaks when derived adds fields that “should matter”.

#### Practical recommendation

- If the type is a **value object**, strongly consider making it **sealed** and using `GetType()` checks (or just use `record`/`record struct` and keep it sealed by design).
- If the type is an **entity** (identity-based), don’t do value equality across inheritance at all; equality should be **identity-based** (e.g., immutable `Id`) and should typically also be sealed or carefully designed.
