## 4.3. Enums vs better models: when to use enum, when to use types (C# 15 era)

1. **When enums are perfect** (closed set, stable list, low ceremony, interop)
2. **When enums hurt** (open sets, attached data, evolving variants, invalid combinations)
3. **Modern alternatives** (polymorphism, records, “smart enum” patterns, union-like modeling with pattern matching)

---

### 1) **When enums are perfect**

Enums shine when your domain concept is genuinely a **closed set** of named values with no additional data.

Use an enum when:

- The set of values is **small and stable** (e.g., `LogLevel`, `DayOfWeek`).
- Values are **pure labels** (no attached payload).
- You need **interop** (native, protocols, storage) with integer codes.
- You want **switch exhaustiveness** as a correctness tool (especially with `switch` expressions).

**Example: closed set + exhaustive `switch`**

```csharp
namespace Demo;

public enum PaymentStatus
{
    Unknown = 0,
    Pending = 1,
    Settled = 2,
    Failed = 3,
}

public static class PaymentStatusText
{
    public static string ToDisplayText(PaymentStatus status) => status switch
    {
        PaymentStatus.Pending => "Pending",
        PaymentStatus.Settled => "Settled",
        PaymentStatus.Failed => "Failed",
        PaymentStatus.Unknown => "Unknown",
        _ => "Unknown", // forward-compat: handle unseen future values
    };
}
```

Good to know:

- Even when you think the set is “closed”, the runtime can still produce unknown values via casts or deserialization. Design for it (see **4.1** for the deep versioning/serialization rules).

---

### 2) **When enums hurt**

Enums become a liability when your concept is not a simple closed set.

Common “enum pain” signals:

#### A) **Open set or user-defined values**

If new values can appear at runtime (config, database, plugins, upstream services), an enum is the wrong abstraction. You’ll end up with:

- `enum` + `Other = 9999` + “string value somewhere else”
- constant churn + “unknown” bugs

Prefer a **strong type** (e.g., `readonly record struct`) that can hold a validated value.

#### B) **Attached data**

If each “case” has payload (e.g., an error with a code + message + retryability), enums force you into parallel structures:

- `ErrorCode` enum
- separate mapping dictionaries
- missing invariants (“this error needs data but it’s not provided”)

Prefer a **type hierarchy** (sealed base + derived types) or records.

#### C) **Invalid combinations**

If you start combining enums to represent states that must obey rules (“these two values can’t happen together”), you’re encoding a state machine implicitly. This usually leads to:

- invalid states being representable
- scattered validation

Prefer explicit **state modeling** (types or a small state machine).

#### D) **Flags misuse**

If you try to represent *modes* with `[Flags]` when the values are mutually exclusive, you’ll create bugs and confusing APIs.

See **4.2** for the “flags done correctly” reference.

---

### 3) **Modern alternatives**

There is no perfect “sum type” built into C# like F# discriminated unions, but modern C# (C# 15 era) gives you several good options.

#### A) **Sealed hierarchy + pattern matching**

Use when:

- variants have different data
- you want exhaustiveness-like reasoning via pattern matching

```csharp
namespace Demo;

public abstract record PaymentResult
{
    private PaymentResult() { }

    public sealed record Settled(string TransactionId) : PaymentResult;
    public sealed record Failed(string Reason, bool IsRetryable) : PaymentResult;
}

public static class PaymentResultText
{
    public static string Describe(PaymentResult result) => result switch
    {
        PaymentResult.Settled s => $"Settled: {s.TransactionId}",
        PaymentResult.Failed f => f.IsRetryable ? $"Failed (retryable): {f.Reason}" : $"Failed: {f.Reason}",
        _ => "Unknown", // defensive
    };
}
```

Mentor note:

- Keep the hierarchy **sealed** (or keep constructors private) to retain “closed set” reasoning inside your assembly.
- This is often the cleanest way to model “enum + payload”.

#### B) **Strongly typed IDs / “codes” as value objects**

Use when:

- values come from outside and are open-ended (database/service)
- you still want type-safety and validation

```csharp
namespace Demo;

public readonly record struct CountryCode(string Value)
{
    public static bool TryCreate(ReadOnlySpan<char> input, out CountryCode code)
    {
        if (input.Length is 2 && char.IsAsciiLetterUpper(input[0]) && char.IsAsciiLetterUpper(input[1]))
        {
            code = new CountryCode(input.ToString());
            return true;
        }

        code = default;
        return false;
    }
}
```

This prevents “random strings everywhere” while still allowing new values.

#### C) **“Smart enum” pattern (use sparingly)**

This pattern can be useful when you need:

- enum-like named singletons
- attached behavior/data
- stable identity

But it adds complexity, allocations, and versioning surface. If you do this, be explicit about:

- how instances are created (usually static readonly singletons)
- how parsing works
- how equality is defined

Performance note:

- Smart-enum patterns allocate objects and often require dictionaries for parsing. That’s usually fine for control-plane code, but you should avoid it in tight hot loops unless measured.

---

### Summary decision guide

- Choose **enum** when: closed set, no payload, interop-friendly.
- Choose **`[Flags]` enum** when: independent options can be combined (and you follow the rules in **4.2**).
- Choose **sealed hierarchy / records** when: variants carry data or behavior.
- Choose **strong value object** when: open-ended external codes.
