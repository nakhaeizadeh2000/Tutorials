## 4.2. Flags enums (`[Flags]`): bitwise semantics done correctly

1. **Correct patterns** (power-of-two values; `None = 0`; combining and testing flags)
2. **Common mistakes** (non-unique bits; mixing “set” and “mode”; broken ToString/serialization expectations)
3. **Performance notes** (bit ops are cheap; the real cost is parsing/formatting/allocations)

---

### 1) **Correct patterns**

**What a `[Flags]` enum is**

A `[Flags]` enum models a **set of independent boolean options** using bits. It is not “an enum with multiple values”; it is a **bitmask**.

**Canonical shape**

- Use a **power-of-two** value for each option: \(1, 2, 4, 8, ...\)
- Include `None = 0` (empty set).
- Prefer an explicit underlying type when it matters for storage/interop (`byte`, `ushort`, `uint`, `ulong`).

```csharp
using System;

[Flags]
public enum FileAccessMask : byte
{
    None  = 0,
    Read  = 1 << 0,
    Write = 1 << 1,
    Exec  = 1 << 2,
}
```

**Combining and testing flags (modern, readable)**

```csharp
FileAccessMask perms = FileAccessMask.Read | FileAccessMask.Write;

bool canRead = perms.HasFlag(FileAccessMask.Read); // readable but can be slower in hot paths

// Hot-path friendly (no boxing; very explicit)
bool canWrite = (perms & FileAccessMask.Write) != 0;

// Check a combination
bool canReadWrite = (perms & (FileAccessMask.Read | FileAccessMask.Write))
                    == (FileAccessMask.Read | FileAccessMask.Write);
```

**Good to know**

- `HasFlag` is convenient, but in some runtimes it can be slower and may box depending on the enum type. In performance-sensitive code, prefer bitwise operations.
- Keep “sets of flags” and “single mode” enums separate. If you need a mode, don’t mark it `[Flags]`.

### 2) **Common mistakes**

#### Mistake A: **Non-unique bits**

```csharp
[Flags]
public enum BadFlags
{
    None = 0,
    Read = 1,
    Write = 2,
    ReadWrite = 3, // This is fine as a named combination (Read|Write) if intentional...
    AlsoWrite = 2, // ...but duplicating meanings creates confusion
}
```

Mentor guidance:

- Named combinations like `ReadWrite = Read | Write` are OK.
- Don’t reuse a bit with different names unless you are deliberately maintaining legacy naming.

#### Mistake B: **Mixing “mode” with “flags”**

Example smell: `Mode = Fast|Safe` as if those were independent. If “Fast” excludes “Safe”, it’s a **mode**, not a flag set.

Fix: model as a normal enum (no `[Flags]`) or use a richer type (see `4.3`).

#### Mistake C: **Assuming ToString/serialization are stable**

- `ToString()` on flags can change formatting and ordering; it’s not a stable wire format.
- Serializing numeric values is stable but makes the data harder to inspect.
- String serialization is readable but versioning must handle unknown values.

If you use JSON, choose a clear contract:

- numeric (stable; less readable)
- string names (readable; must tolerate unknowns)

The versioning/serialization strategy belongs in `4.1`. See `4.1` for the deep guidance.

### 3) **Performance notes**

**Bit operations are cheap**

The costs that usually matter are:

- converting to/from strings (`Enum.Parse`, `ToString`) which allocates
- logging/formatting in hot paths
- using `HasFlag` repeatedly in tight loops

**Guidelines**

- Prefer **bitwise checks** over `HasFlag` in hot code.
- Avoid string parsing for flags on hot paths. Parse once at boundaries (configuration load) and keep the enum value internally.

**Example: boundary parse (once) + internal bit checks**

```csharp
using System;

static FileAccessMask ParseMask(string input)
{
    if (!Enum.TryParse<FileAccessMask>(input, ignoreCase: true, out var value))
        throw new ArgumentException("Invalid mask.", nameof(input));

    return value;
}

static bool NeedsWrite(FileAccessMask mask) => (mask & FileAccessMask.Write) != 0;
```
