## 1.1. Partial classes: the real purpose (code generation + separation of concerns)

1. **What `partial` actually means** (one logical type split across files; compiled as one)
2. **Best uses** (source generators, designer code, interop/auto-generated code, large type partitioning)
3. **Costs** (discoverability, “type is everywhere”, review difficulty, and accidental coupling)

---

### 1) **What `partial` actually means**

**Definition**

A **partial type** is a single type whose definition is split across multiple source files (or multiple parts in the same file). The compiler **merges all parts into one type** in the same assembly.

**Key properties**

- **Same type, not composition**: after compilation, there is no “part A” and “part B”; there is just one type.
- **Compile-time only**: `partial` is a **compiler feature**, not a runtime feature. There is no runtime dispatch, no extra allocations, no reflection magic implied.
- **Same compilation unit**: all parts must be compiled together (same project/assembly). You can’t “extend” a type defined in another assembly using `partial`.
- **Same namespace**: all parts must be in the same namespace (including file-scoped namespaces).

**Good to know**

- Splitting a type doesn’t change the runtime layout. What changes is **humans’ ability to understand and review the type**.

**Minimal example (two files)**

File A:

```csharp
namespace Demo;

public partial class Order
{
    public required string Id { get; init; }
}
```

File B:

```csharp
namespace Demo;

public partial class Order
{
    public bool IsValid() => !string.IsNullOrWhiteSpace(Id);
}
```

At runtime, `Order` has both `Id` and `IsValid()` exactly as if you wrote them in a single file.

### 2) **Best uses**

Partial classes are a tool. They’re “best practice” only in a few narrow categories where they reduce risk or enable tooling.

#### A) **Code generation boundaries (the main reason partial exists)**

This is the #1 legitimate reason to use `partial`: you want generated code and hand-written code to cooperate without:

- editing generated files (which get overwritten)
- using reflection or dynamic discovery (slow, brittle, trimming/AOT-hostile)
- using virtual methods for generated “hooks” (exposes extension points you might not want)

Typical cases:

- **Source generators** (modern, C# 15 era): generator emits `partial` members/types and your code supplies the rest.
- **Designer-generated UI code** (legacy but still common): WinForms/WPF designers generate a partial class; you write behavior in the other file.
- **Interop codegen**: generated P/Invoke wrappers, strongly-typed clients, etc.

Mentor rule:

- If the reason is **“so I can regenerate safely”**, `partial` is the right tool.
- If the reason is **“my file is big”**, prefer refactoring the design first (see “Costs”).

#### B) **Separation of concerns inside one type (only when the type is truly one concept)**

Sometimes a type is legitimately one public contract but has two “faces” that you don’t want mixed:

- Public API surface vs internal implementation details
- Synchronous API + async helpers
- “Core logic” vs “serialization/ORM glue” (careful: this can be a smell)

Better than partial in many cases:

- Move helpers to **private nested types**
- Use **composition** (smaller types)
- Use **extension methods** for non-core helpers (be cautious: extension method discoverability and namespace placement matter; see `README/CSharp/Namespaces/sections/6. Using static/6.1. Using static fundamentals and safe usage.md` for static import hygiene and the `Namespaces` domain for placement strategy)

#### C) **Large type partitioning (only with strict conventions)**

This can be acceptable for “framework-ish” types that are necessarily large (e.g., Roslyn analyzers or generated DTOs), but it requires discipline:

- a single “entry point” file that clearly shows the type’s public surface
- other parts named by responsibility (`Order.Validation.cs`, `Order.Serialization.cs`, etc.)
- avoid “random” member placement

**Performance note**

Partial types have essentially **no runtime cost**. The cost is:

- **compile-time** (slightly more work for the compiler, usually negligible)
- **engineering cost**: harder code search, refactoring, and review

---

### 3) **Costs**

Partial is a maintainability trade:

#### A) **Discoverability cost**

- “Where is this method?” becomes a recurring question.
- IDE navigation helps, but reviewers and new team members pay an ongoing tax.

#### B) **Accidental coupling**

Because everything is one type, any part can touch any private members. Without rules, partial becomes a way to bypass good boundaries.

Mentor guidance:

- Treat each partial file like a **module boundary**, even though the compiler doesn’t enforce it.
- Keep private state close to the methods that use it. Avoid “shared private fields” scattered across parts.

#### C) **Merge conflicts and review difficulty**

- Parallel edits to the same logical type are more likely.
- A change that “looks small” in one file may have big implications elsewhere.

#### D) **API ambiguity**

In libraries, partial types can hide where a member “comes from” (handwritten vs generated). This matters for:

- documentation
- analyzers
- versioning decisions

**Good to know**

- Prefer `partial` when it *reduces* risk (generated code boundaries), not when it *increases* complexity (splitting for aesthetics).
