## 1.2. Rules and constraints for partial classes (what must match across parts)

1. **What must agree** (namespace, type name, kind, generic parameters, accessibility)
2. **What can differ** (members per file; attributes on parts; docs and analyzers)
3. **Common compiler errors** (mismatched constraints/modifiers; duplicate members; inconsistent accessibility)

---

### 1) **What must agree**

For the compiler, all `partial` parts are *fragments of the same type symbol*. That means some aspects must be identical across every file that participates.

**Must match across all parts**

- **Namespace**: `namespace A.B;` must be the same in each part (file-scoped vs block-scoped style doesn’t matter, the resulting namespace must match).
- **Type name** and **type kind**: `class` vs `struct` vs `record class` vs `record struct` must be consistent.
- **Generic arity and parameter names**: `partial class Box<T>` must not become `partial class Box<TItem>` or `Box<T,U>` in another part.
- **Generic constraints**: `where T : notnull` / `where T : class` / `new()` etc. must be consistent.
- **Type parameter variance** (interfaces/delegates): `out`/`in` must match.
- **Accessibility**: `public`/`internal`/`private` etc. must be consistent (in practice, you typically declare accessibility once and omit it in other parts—still, it must resolve to the same).
- **Base type list and implemented interfaces**: for partial classes/structs, the full base/interface list must combine consistently (you can *split* interfaces across parts, but you can’t make the type “inherit from two different base classes” across parts).

**Good to know**

- **Attributes** on the type can appear on multiple parts; they combine. That’s powerful, but it can also make it hard to discover why a type has a specific attribute (see item 2).

**Example: constraints must match**

```csharp
// File A
public partial class Cache<TKey, TValue> where TKey : notnull;

// File B (OK)
public partial class Cache<TKey, TValue> where TKey : notnull
{
}

// File C (ERROR: constraint mismatch)
public partial class Cache<TKey, TValue> where TKey : class;
```

### 2) **What can differ**

Once the type identity is fixed, partial parts can vary in ways that help structure the code.

**Common valid differences**

- **Member distribution**: fields/properties/methods/events/nested types can be split across files.
- **Using directives**: each file has its own `using` set; don’t assume a using in one part “applies to” another part.
- **Attributes**:
  - Member attributes live where the member is declared.
  - Type-level attributes can be spread, and the compiler aggregates them.
- **Documentation**: XML docs can be on any part, but you should designate one “owner” file for the main doc comment to avoid scattered docs.
- **Nullable context / pragmas**: `#nullable enable` is per file. Mixing nullable settings across parts is legal but dangerous.

**Mentor rule**

- Decide one file as the **type’s entry point** (the one you expect a reviewer to open first). Keep the most important public API and docs there. Use other partial files to group implementation details.

### 3) **Common compiler errors**

Most partial-related compiler errors are actually “the compiler is protecting you from accidentally creating two different types that you thought were one.”

**Frequent failures and how to fix**

1. **Mismatched modifiers / kind**
   - Example: one file uses `partial class`, another uses `partial record class`.
   - Fix: align the kind (and if you need record features, make the entire type a record).

2. **Generic constraint mismatch**
   - Example: one part has `where T : notnull`, another part omits constraints or uses a different one.
   - Fix: keep constraints identical in all parts (best: put constraints only on one canonical declaration).

3. **Duplicate members**
   - Example: both parts declare a `private const int Max = 10;`.
   - Fix: rename or move shared members into a single file; enforce naming conventions and file ownership.

4. **Inconsistent accessibility**
   - Example: one part says `public partial class X`, another says `internal partial class X`.
   - Fix: declare accessibility exactly once; treat it like a public contract decision.

5. **Conflicting base type**
   - Example: part A: `: BaseA`, part B: `: BaseB`.
   - Fix: only one base class is allowed. Move base class selection to the “owner” file.

**Performance note**

- Partial types themselves have **zero runtime overhead**. The risks are organizational:
  - hidden coupling and bigger diffs,
  - accidentally mixed nullable/pragma states,
  - and “where did this attribute come from?” debugging time.
