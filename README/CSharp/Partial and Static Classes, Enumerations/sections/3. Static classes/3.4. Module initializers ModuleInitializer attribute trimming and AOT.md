## 3.4. Module initializers (`[ModuleInitializer]`) — assembly-level startup hooks (C# 9+)

### What it is

1. **`[ModuleInitializer]`** marks a method that runs **before** other type members in the assembly are initialized (once per assembly load, **before** your `Main`).
2. **Use cases**: registering codecs, interceptors, source-generated wiring, or static caches that must exist early.

---

### Correctness and ordering

1. **Order is not a portable contract** between multiple module initializers—assume **unordered** unless you explicitly sequence via calls.
2. **Throwing** during module initialization can **poison** assembly load (`TypeInitializationException`-style failures are hard to diagnose).
3. **Do not** use for I/O-heavy startup—prefer explicit `app.Run` / host startup for predictable cold-start and testability.

---

### Performance and reliability

1. **CPU**: keep initializers **cheap**—they run on the critical path before user code.
2. **Threading**: treat as **static init**—avoid blocking on async; async isn’t available in sync static init.
3. **Memory**: static caches created here live for **process lifetime**—bound growth.

---

### Trimming, AOT, and reflection

1. **Native AOT / trimming**: static initialization and reflection-heavy registration patterns are **fragile**—prefer explicit registration or source generators that emit stable calls.
2. **Testability**: module initializers run when the assembly loads—tests may need isolation or explicit reset strategies.

---

### Modern alternatives (often better)

1. **Explicit host startup** in apps (`WebApplicationBuilder`, `Host.CreateApplicationBuilder`, etc.).
2. **Dependency injection** registration in a single composition root.
3. **Source generators** that emit normal registration code at compile time.
