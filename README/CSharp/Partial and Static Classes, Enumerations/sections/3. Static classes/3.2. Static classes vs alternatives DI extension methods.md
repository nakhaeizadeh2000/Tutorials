## 3.2. Static classes vs alternatives: instance services, modules, and extension methods

1. **Static vs DI** (testability, lifetimes, substitutability, composition roots)
2. **Static vs singleton** (global state and contention; why singleton is not a “pattern” in most modern apps)
3. **Extension method hygiene** (namespace placement, discoverability, and ambiguity management)

---

### 1) **Static vs DI**

If a component has **dependencies** (time, randomness, configuration, I/O, database, HTTP, logging, feature flags), a `static class` tends to turn those dependencies into **ambient globals**. That harms:

- **Testability**: you can’t easily substitute the dependency.
- **Correctness**: global state encourages “works on my machine” ordering bugs.
- **Maintainability**: any code anywhere can call it, bypassing architecture boundaries.

**Modern default (C# 15 / .NET 9+)**

- **Use DI for services with dependencies**.
- **Use static classes for pure functions** (no dependencies, no state) and for extension method containers.

**Example: DI-friendly service vs static anti-pattern**

Bad (static “service” hides dependencies):

```csharp
using System.Net.Http;

public static class WeatherService
{
    // Hidden global dependency + lifetime decision.
    private static readonly HttpClient _http = new();

    public static async Task<string> GetAsync(string city, CancellationToken ct)
        => await _http.GetStringAsync($"https://example/weather?city={city}", ct);
}
```

Better (explicit dependencies, testable):

```csharp
using System.Net.Http;

public sealed class WeatherService(HttpClient http)
{
    public async Task<string> GetAsync(string city, CancellationToken ct)
        => await http.GetStringAsync($"https://example/weather?city={city}", ct);
}
```

**Good to know**

- DI has a runtime cost, but in most apps it’s not the bottleneck. The big wins are **clarity**, **lifetime correctness**, and **controlled composition**.

### 2) **Static vs singleton**

**A singleton is (usually) a global variable with nicer marketing.**

Common misconceptions:

- “Singleton prevents multiple instances, so it’s safe.”
  - It prevents multiple instances, but it doesn’t prevent **shared mutable state problems**.
- “Singleton improves performance.”
  - It often introduces **contention**, **hidden caching**, and **memory retention** that are far worse than creating instances.

**When a singleton-like lifetime is correct**

- Truly process-wide components whose behavior must be shared (metrics registry, a bounded cache, a single background coordinator).
- Even then: prefer **registering as a singleton in DI**, not static globals, so you keep:
  - test substitutability
  - controlled shutdown
  - clear ownership in the composition root

**Performance note**

- The expensive part isn’t “one instance”. The expensive part is **unbounded static state**, locks, and cross-thread contention. See `3.3` for static-state risks and the deep memory model reference in `Cuncurrent & Parallel` → `4.2. .NET memory model and visibility`.

### 3) **Extension method hygiene**

Extension methods must live in a **static class**, but that doesn’t mean the static class should become a junk drawer.

**Guidelines that scale**

- **Namespace placement matters**: put extension methods in a namespace that callers can intentionally import.
- **Keep extension classes cohesive**: group by concept, not by “all extensions”.
- **Avoid ambiguous extensions**: the more extension methods you import, the easier it is to accidentally change overload resolution.

This repo already covers the “using/import” side in depth.

See the `Namespaces` domain for:

- extension-method ambiguity and conflict management: `README/CSharp/Namespaces/sections/7. Important points/7.2. Common pitfalls ambiguous names extension method surprises.md`

**Mentor rule**

- If you’re publishing a library, consider extension methods part of your **public API surface**: they affect discoverability and can create subtle source-breaking changes when you add overloads.
