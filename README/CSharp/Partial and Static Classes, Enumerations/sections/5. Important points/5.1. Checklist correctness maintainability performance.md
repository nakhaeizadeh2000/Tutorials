## 5.1. Checklist: correctness, maintainability, performance

1. **Partial types** (avoid scattering; keep an “entry” file; isolate generated code)
2. **Static classes** (pure is safe; mutable static is shared state—treat as concurrency + lifetime problem)
3. **Enums** (treat as a public contract; plan `Unknown = 0`; define serialization/versioning strategy)

---

### 1) **Partial types**

**Checklist**

- **Choose partial for the right reason**: generated-code boundary and compile-time augmentation.  
  - If the only reason is “this file is big”, treat it as a design smell and refactor the type into smaller types.
- **Keep an entry-point file**:
  - Put the type’s **purpose**, **invariants**, and the “main” public API in one file.
  - Use other partial files for cohesive secondary responsibilities.
- **Isolate generated code**:
  - Generated partial parts should be in predictable locations and clearly named.
  - Never hand-edit generated files; add behavior via partial methods/types or separate handwritten files.
- **Control visibility across parts**:
  - Don’t use partial to “smuggle” cross-cutting private fields everywhere.
  - Keep private state close to the behavior that owns it.
- **Keep compiler directives consistent**:
  - Nullable context is per file (`#nullable enable`). Mixing settings across partial parts is legal but produces subtle bugs.

**Good to know**

- Partial types have essentially **no runtime cost**; their main cost is **engineering friction** (review/search/refactor).

---

### 2) **Static classes**

**Checklist**

- **Prefer static only for**:
  - pure deterministic helpers (no I/O, no time, no randomness unless injected)
  - extension-method containers (cohesive, intentionally imported namespaces)
- **If there is a dependency, don’t hide it**:
  - For time: inject `TimeProvider` (instead of `DateTime.Now` sprinkled everywhere)
  - For randomness: inject an RNG when determinism matters; avoid static “global random” in core logic
  - For I/O/config/logging: use DI and explicit lifetimes (see `3.2`)
- **Treat mutable static state as a concurrency + lifetime problem**:
  - Define who can mutate it and under what synchronization.
  - Prefer instance services with lifetimes for anything non-trivial.

**Performance note**

- Static is not “automatically faster”. The performance hazards come from:
  - contention (locks around shared mutable state),
  - unbounded caches (memory retention),
  - expensive static initialization paid on first-touch (see `3.3`).

---

### 3) **Enums**

**Checklist**

- **Decide what 0 means**:
  - Usually `Unknown = 0` (or `None = 0` for flags) to make default values safe.
- **Validate at boundaries**:
  - Enums can hold invalid numeric values; don’t assume “the compiler prevents invalid states”.
- **Version consciously**:
  - Treat public enums as stable contracts. Prefer deprecating values over removing/reusing numeric codes.
- **Don’t use enums where they don’t fit**:
  - If you need payload, open-ended values, or complex invariants, consider types (see `4.3`).

**Good to know**

- String parsing/formatting is often the real cost. Parse once at the boundary and keep enums strongly typed inside the app (see `4.1` and `4.2`).
