## 5.2. Production pitfalls you’ll actually hit

1. **Static global state** (tests become order-dependent; memory leaks by design; multi-tenant bugs)
2. **Enum versioning and serialization** (deserializing unknown values; forwards/backwards compatibility)
3. **Partial misuse** (merge conflicts, “hidden” members, and onboarding/debugging friction)

---

### 1) **Static global state**

Static state is not “just a convenience”; it is a **process-wide lifetime decision** plus a **concurrency decision**.

Common production failures:

- **Order-dependent tests**: one test mutates static state, another test observes it.
- **Multi-tenant bugs**: one request/user/tenant changes static state and affects others.
- **Memory retention**: static references keep objects alive for the lifetime of the process.
- **Hidden contention**: static caches and global locks become hotspots under load.

**Mentor fixes**

- Prefer **DI + explicit lifetimes** for services (`singleton`/`scoped`/`transient` chosen in the composition root).
- Prefer immutable static data (`static readonly`) over mutable static state.
- If you must have shared state, write down the **thread-safety contract**: single-writer? lock? interlocked?

Performance note:

- Debugging a static-state race costs far more CPU hours than you saved by avoiding DI.

See also:

- For deep “static fields are a lifetime problem” guidance: `README/CSharp/Fields/sections/4. Static fields/4.1. Static fields when appropriate and when a trap.md`
- For safe publication and why naive patterns break: `README/CSharp/Cuncurrent & Parallel/sections/4. Correctness, Testing, Diagnostics & Debugging in Concurrent Code/4.2. .NET memory model and visibility.md`

### 2) **Enum versioning and serialization**

The most common production enum bug is not “wrong enum value”, it’s **unknown enum value**:

- a newer service sends a value older clients don’t know
- a DB row contains a value from a previous version
- logs/telemetry parse breaks because enum names changed

**Mentor rules**

- Always plan for **unknown values** at read boundaries.
- Use `Unknown = 0` (or `None = 0` for flags) unless you have a strict invariant and can enforce it everywhere.
- Treat `ToString()` as human-readable only, not a wire contract.

See the single deep reference for versioning details, safe parsing, and validation patterns:

- See `README/CSharp/Partial and Static Classes, Enumerations/sections/4. Enumerations/4.1. Enum fundamentals underlying type defaults versioning.md`.

### 3) **Partial misuse**

Partial types are most often misused as a “file splitting trick”.

Failure modes:

- **Public API scattered** across files (reviewers miss changes).
- **Invariants diluted**: part A assumes something that part B violates.
- **Nullable context mismatch** across parts (`#nullable enable` in one file, disabled in another).
- **Attributes scattered** (hard to see why something is `[Obsolete]`, `[JsonConverter]`, etc.).

**Mentor fixes**

- Keep one “owner” file that shows the public surface and main invariants (see `1.1` and `1.3` guidance).
- Put generated parts in a clearly named folder and treat them as read-only.
- Use naming conventions for partial files by responsibility: `Type.Validation.cs`, `Type.Serialization.cs`.

Good to know:

- Partial doesn’t enforce modularity; humans must enforce it with conventions and reviews.
