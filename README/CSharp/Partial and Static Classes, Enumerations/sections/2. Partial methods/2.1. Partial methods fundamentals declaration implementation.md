## 2.1. Partial methods fundamentals: declaration vs implementation (no runtime dispatch)

1. **Why they exist** (optional hooks for generated code without reflection or virtual dispatch)
2. **Semantics** (compile-time binding; how calls behave when no implementation exists)
3. **Design guidance** (use for narrow hooks; avoid using as “events” or public extensibility)

---

### 1) **Why they exist**

**Definition**

A **partial method** is a method that can be *declared* in one part of a partial type and *implemented* in another part. This is primarily a tool for **compile-time composition** between:

- generated code (source generators, designers)
- your handwritten code

…without runtime indirection.

**The core problem partial methods solve**

Generated code often wants to expose “hooks” like `OnCreated()` / `OnPropertyChanged()` without forcing you to:

- edit generated files (will be overwritten)
- pay runtime costs (virtual dispatch, reflection, delegates/events)
- broaden the public API surface (public virtual hooks are long-lived contracts)

Partial methods let generated code offer an optional hook that:

- is cheap when not used
- doesn’t require runtime discovery
- stays inside the type’s compilation boundary

**Where you see them in real code**

- **Source generator patterns** (modern): a generator emits `partial void OnXyz(...);` and calls it; you optionally implement it.
- **Designer-generated code** (legacy but still around): tools that generate part of a type may provide partial hooks.

**Good to know**

- Partial methods are **not** an extensibility mechanism across assemblies. They are for *one build* producing *one type*.

---

### 2) **Semantics**

Partial methods have intentionally “boring” semantics: everything is decided at compile time.

#### **Declaration vs implementation**

- A **declaration** introduces the signature.
- An **implementation** provides the body.
- The compiler ensures the two match.

In a typical generator hook pattern:

- The generator emits the declaration and a call site.
- Your code optionally adds the implementation.

#### **What happens if there is no implementation?**

This depends on the “shape” of the partial method (language rules evolved over C# versions):

- For “classic hook-style” partial methods (commonly `partial void` patterns), **if there is no implementation, the call is removed** at compile time. This means:
  - no runtime call
  - no delegate allocation
  - no branch needed
  - no JITed method body

If you’re using modern features like non-`void` return types and accessibility, treat partial methods as **real methods** that must be implemented (or must have well-defined behavior). This file focuses on fundamentals; see **2.2** for modern rule sets and what changes.

#### **No runtime dispatch**

- Partial methods are **not virtual**.
- There is no late binding, no interface dispatch, no “plug-in”.
- The generated call is a normal call after compilation.

**Performance note**

- The win is not “partial is faster than normal method” — the win is **zero cost when omitted** and **no extra indirection** when present.

---

### 3) **Design guidance**

#### **Use partial methods for narrow, internal hooks**

Good shape:

- “Tell me you did X” hooks
- “Validate/normalize this input before storing it”
- “Allow a generator to ask user code to contribute extra members/metadata”

Bad shape:

- Business logic spread across partial hooks (hard to reason about)
- Hooks that are effectively “events” but hidden
- Hooks used to “simulate dependency injection”

#### **Prefer explicit methods for real behavior**

If behavior matters to correctness, clarity, or testing, it should be explicit and discoverable:

- a normal method
- a strategy interface + DI (for app-level composition)
- a well-named helper type

Partial hooks are best when the hook is genuinely **optional** and primarily exists for tooling/generation.

#### **Avoid using partial methods as a public contract**

If you feel tempted to make partial methods public to let other code “plug in”, that’s a smell:

- it doesn’t work across assemblies anyway
- you’re creating hidden coupling and unclear dependencies

Prefer normal public APIs.

### Minimal, runnable example: generator-style hook without runtime overhead

Two files in the same project.

File A (often generated):

```csharp
namespace Demo;

public partial class Customer
{
    public Customer(string name)
    {
        Name = name;
        OnCreated();
    }

    public string Name { get; }

    partial void OnCreated();
}
```

File B (handwritten, optional):

```csharp
namespace Demo;

public partial class Customer
{
    partial void OnCreated()
    {
        // Put only small, local behavior here.
        // If this becomes "real business logic", refactor to explicit methods/services.
    }
}
```

If you remove File B, the call to `OnCreated()` is typically removed at compile time (no runtime work).
