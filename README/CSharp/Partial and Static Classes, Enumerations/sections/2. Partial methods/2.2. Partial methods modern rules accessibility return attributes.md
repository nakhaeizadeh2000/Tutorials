## 2.2. Partial methods in modern C#: accessibility, return values, and attributes

1. **What modern C# allows** (non-void returns, accessibility, attributes, generics—when paired correctly)
2. **Source generator patterns** (compile-time augmentation; analyzability; avoiding reflection)
3. **Performance framing** (no allocations by default; avoid capturing/closures in hot hooks)

---

### 1) **What modern C# allows**

Partial methods evolved from “very restricted, void-only, private-only hooks” into a practical tool for generator-friendly codebases.

**Modern rules (C# 15 era)**

- A partial method has a **declaration** and optionally an **implementation**, both marked `partial`.
- It is **compile-time composition**: there is no virtual dispatch, no reflection discovery, and no runtime “plug-in” behavior.
- Modern C# allows partial methods to have:
  - **Accessibility modifiers** (`private`, `internal`, etc.)
  - **Return values** (not only `void`)
  - **Attributes** (useful for analyzers and generators)
  - **Generic type parameters**
- Whether the call exists when there is no implementation depends on the method shape:
  - **If the method is `void`** and has **no out parameters**, the compiler may **remove the call** if there’s no implementation (so there is no runtime overhead).
  - If the method must return a value or has `out` parameters, then an implementation is required (otherwise you’d have an unsatisfied contract).

Mentor note:

- In generator scenarios, prefer **void hook methods** when the “no implementation” behavior is desirable and safe.
- If you need a value back, you’re defining a contract—make sure there’s exactly one clear owner for that contract to avoid “half-generated half-handwritten” ambiguity.

**Example: optional void hook (no implementation required)**

```csharp
namespace Demo;

public sealed partial class Parser
{
    public static bool TryParse(string input, out int value)
    {
        value = 0;
        if (string.IsNullOrWhiteSpace(input))
        {
            OnInvalidInput(input); // Removed by compiler if not implemented
            return false;
        }

        return int.TryParse(input, out value);
    }

    static partial void OnInvalidInput(string input);
}
```

If you don’t implement `OnInvalidInput`, the call is effectively not there. If you do implement it (possibly in generated code), it becomes a normal call.

**Example: contract-style partial (implementation required)**

```csharp
namespace Demo;

public sealed partial class Tokenizer
{
    public string NextToken(ReadOnlySpan<char> input)
        => TransformToken(input); // Needs implementation because it returns a value

    private static partial string TransformToken(ReadOnlySpan<char> input);
}
```

Good to know:

- For return-valued partial methods, think of them less like “optional hooks” and more like “split implementation across files”.

### 2) **Source generator patterns**

Partial methods are a sweet spot for source generators because they keep everything:

- **statically discoverable** (no reflection scanning),
- **linker/AOT-friendly** (no dynamic discovery),
- **reviewable** (generated code is explicit in source),
- **fast** (no extra allocations by default).

#### Pattern A: “Generated calls into your code” (hook points)

Generator emits a call:

```csharp
// generated
partial class Customer
{
    partial void OnValidated();

    public void Validate()
    {
        // ... generated validation rules ...
        OnValidated();
    }
}
```

You optionally implement:

```csharp
// handwritten
partial class Customer
{
    partial void OnValidated()
    {
        // optional extra checks or metrics
    }
}
```

Mentor rule:

- Keep hooks **narrow** and **side-effect disciplined**. Don’t turn them into an ad-hoc event system.

#### Pattern B: “Your code calls into generated code” (augmentation)

Your file declares signatures the generator will implement:

```csharp
namespace Demo;

public sealed partial class Customer
{
    public string Name { get; init; } = "";

    public partial string ToJson(); // generator provides the body
}
```

This is ideal when you want:

- predictable APIs,
- no reflection serialization,
- and control over allocations (e.g., writing to `IBufferWriter<byte>` in advanced scenarios).

Good to know:

- Prefer source generators over legacy reflection-heavy solutions when you care about trimming/AOT and startup performance.

### 3) **Performance framing**

**Where partial methods help performance**

- **No-implementation calls can be erased** (for eligible void hooks), meaning:
  - no call overhead
  - no delegate allocations
  - no event subscription infrastructure
- Avoids reflection (often the bigger win than micro-optimizing a call).

**Where partial methods can hurt (indirectly)**

- If your hook implementation captures state via lambdas or uses LINQ in hot paths, you may introduce allocations (closures, iterators).
- If partial methods are used to smuggle hidden static state, you can create contention and memory retention issues (the “static global state” trap is discussed in detail in `3.3`, and low-level memory model rules live in `README/CSharp/Cuncurrent & Parallel/sections/4. Correctness, Testing, Diagnostics & Debugging in Concurrent Code/4.2. .NET memory model and visibility.md`).

Performance note:

- Prefer passing required data as parameters (including `ReadOnlySpan<char>` / `ReadOnlySpan<byte>` when appropriate) rather than reading ambient state from statics.
- If you need async work, don’t force async into partial hooks “because it’s convenient”. Make the async boundary explicit in the public API (`Task`/`ValueTask`) so callers can reason about scheduling and cancellation (async scheduling deep dive: `Cuncurrent & Parallel` domain).
