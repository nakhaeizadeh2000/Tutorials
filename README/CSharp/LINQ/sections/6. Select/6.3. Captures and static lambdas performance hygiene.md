## 6.3. Captures and `static` lambdas (performance hygiene)

1. **Avoid accidental closure allocations**: when a lambda captures outer variables, the compiler generates closure objects; in hot paths prefer `static` lambdas where possible.
2. **Make captured values explicit**: pass needed values via local variables/parameters in a way that avoids capturing the whole surrounding scope.

---

### 1. **Closures**

A lambda that references locals or `this` becomes a **display class** instance in IL. That allocation can happen **once per outer scope activation**, not per element—but in tight loops creating **new** delegates tied to changing state, costs add up.

---

### 2. **`static` lambdas (modern C#)**

Use **`static`** when the lambda does not need captures:

```csharp
using System.Linq;

var nums = new[] { 1, 2, 3 };
var evens = nums.Where(static n => n % 2 == 0);
```

The compiler prevents accidental captures—good for reviews and JIT quality.

---

### 3. **Passing state without captures**

Use **`Select`** overloads with index, pass **constants** as parameters to local functions, or use **`Arg` objects** created once outside the hot path.

---

### 4. **Thread safety**

LINQ-to-Objects operators are **not** inherently thread-safe on shared mutable enumerators. **Do not** parallel-enumerate the same `IEnumerable<T>` instance without synchronization. For parallelism, use **PLINQ** or **`Parallel.ForEach`** with thread-safe sources—topics in *Concurrent & Parallel*.

**Performance note:** measure before micro-optimizing lambdas; clarity matters. Optimize hotspots proven by profiling.
