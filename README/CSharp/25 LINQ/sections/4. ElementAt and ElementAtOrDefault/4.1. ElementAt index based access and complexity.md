## 4.1. ElementAt: index-based access with possible O(n) enumeration

1. **Index access is not always O(1)**: for general `IEnumerable<T>`, LINQ must enumerate from the start until the requested index is reached (CPU `O(index)`).
2. **Special cases may exist**: implementations backed by `IList<T>`/arrays can sometimes use direct indexing; still, assume "enumerate until index" unless your input type guarantees random access.
3. **Use for "small indices" only**: if you frequently request large indices from a non-indexed enumerable, switch to a data structure that supports efficient indexing.

---

### 1. **General IEnumerable cost**

`ElementAt(k)` walks **`k` steps** from the start. Repeated random access patterns on a linked list or iterator pipeline devolve to **`O(n * m)`** behavior.

---

### 2. **Fast paths**

When the runtime detects **`IList<T>`** (including arrays), `ElementAt` can index directly—**amortized O(1)** per access. Do not rely on this unless you control the concrete type **and** document it.

---

### 3. **Design guidance**

If your algorithm needs many arbitrary indices, **materialize** to array/list once, or use **`ReadOnlySpan<T>`** / **`Memory<T>`** when you own contiguous memory (C# 15 / modern .NET patterns for hot paths).

```csharp
using System;
using System.Collections.Generic;
using System.Linq;

IEnumerable<int> seq = new LinkedList<int>(new[] { 1, 2, 3, 4, 5 });
// Potentially walks from head each call:
_ = seq.ElementAt(4);

int[] arr = { 1, 2, 3, 4, 5 };
_ = arr.ElementAt(4); // IList fast path when applicable
```

**Performance note:** for hot inner loops, **avoid** `ElementAt` on cold `IEnumerable<T>`; prefer arrays, spans, or direct indexing.
