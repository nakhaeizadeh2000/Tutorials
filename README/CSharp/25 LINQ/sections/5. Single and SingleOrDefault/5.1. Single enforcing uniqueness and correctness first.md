## 5.1. Single: enforcing uniqueness with correctness-first behavior

1. **Exactly one element required**: `Single` throws if the sequence is empty or if it contains more than one matching element.
2. **Short-circuit on second match**: `Single(x => predicate(x))` typically stops after it can prove there is more than one match, but you still need to design for possible near-full enumeration depending on where the second match occurs.
3. **Use when invariants exist**: `Single` is ideal when your domain guarantees uniqueness (e.g., ID lookups) and you want failures to surface loudly.

---

### 1. **Contract**

`Single()` requires **exactly one** element in the whole sequence. `Single(predicate)` requires **exactly one** match.

**Throws**

- **`InvalidOperationException`** if zero or **more than one** (for the predicate overload: more than one match).

---

### 2. **Enumeration behavior**

Implementation may stop early after seeing a **second** match. If only one match exists at the end of a long sequence, you still pay **O(n)** to learn the count is one.

---

### 3. **When to prefer `Single` over `First`**

- **Uniqueness is a business invariant** (primary key in a client-side collection, config flag that must appear once).
- You want **loud failure** if data is corrupt.

**Avoid** `Single` on unbounded or network streams where “more than one” cannot be detected without reading everything.

```csharp
using System;
using System.Linq;

var ids = new[] { 42 };
int id = ids.Single(); // OK

try
{
    _ = new[] { 1, 1 }.Single();
}
catch (InvalidOperationException)
{
    // more than one element
}
```

**Performance note:** prefer **`HashSet`** or database **unique constraints** to enforce uniqueness at the source; `Single` is a **runtime check**, not a structural guarantee.
