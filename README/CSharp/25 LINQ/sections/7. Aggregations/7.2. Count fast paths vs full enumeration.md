## 7.2. Count: fast paths vs full enumeration

1. **Count without predicate can be O(1)**: if the source implements a sizing interface (`ICollection<T>`, arrays), LINQ can often read `Count` directly.
2. **Count with predicate enumerates**: `Count(x => predicate(x))` must iterate to evaluate the predicate for all elements.
3. **Avoid repeated Count()**: calling `Count()` repeatedly on an `IEnumerable<T>` can re-enumerate and waste CPU; cache into a list/array when appropriate.

---

### 1. **`Count()` fast path**

When the object implements **`ICollection<T>.Count`** (or **`IReadOnlyCollection<T>.Count`** in applicable implementations), **`source.Count()`** may avoid iterating. Arrays and `List<T>` benefit.

---

### 2. **`Count(predicate)`**

Must test each element → **`O(n)`** time, **O(1)** extra memory (aside from iterator).

---

### 3. **Pitfall: cold `IEnumerable<T>`**

If `GetItems()` returns a **new iterator** each call, two `Count()` calls enumerate **twice**. Materialize if you need multiple facts (`Count` + `Sum`) unless you refactor to a single pass manually.

```csharp
using System.Linq;

var list = new List<int> { 1, 2, 3 };
int c = list.Count(); // often uses ICollection.Count

int pc = list.Count(x => x > 1); // enumerates
```

**Performance note:** for hand-tuned hot paths counting in a **`for`** loop over a span can eliminate iterator overhead—only after profiling.
