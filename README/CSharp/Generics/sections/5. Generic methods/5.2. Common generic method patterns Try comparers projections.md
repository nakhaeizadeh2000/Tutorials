## 5.2. Common generic method patterns (Try-pattern, comparers, projections)

1. **Try-patterns** (`TryParse`, `TryGetValue`, `Try…` with `out` + no exceptions for expected control flow)
2. **Comparer/equality injection** (`IComparer<T>`, `IEqualityComparer<T>`, `Comparison<T>`)
3. **Projection and mapping** (`Func<TIn, TOut>`; avoid allocations/captures in hot paths)

---

### 1) **Try-patterns** (`TryParse`, `TryGetValue`, `Try…`)

**Definition**

A **Try-pattern** method returns `bool` to indicate success, and writes the parsed/produced value via an `out` parameter:

- **Success path is allocation-free** (usually)
- **Failure is non-exceptional** (no stack unwinding)
- **Call sites remain clean** with modern `out var` syntax

This pattern is the default for “expected failure” scenarios: user input, optional fields, cache lookups, dictionary access, etc.

**When to use**

- **Parsing** (e.g., `int.TryParse`, `Guid.TryParse`, `DateTime.TryParseExact`)
- **Lookups** (e.g., `Dictionary<TKey, TValue>.TryGetValue`)
- **Optional computation** where failure is part of normal control flow

**Trade-offs**

- `out` parameters can make APIs feel less “functional” than returning a `T?` / `Option<T>`-like shape, but they are:
  - very efficient,
  - very idiomatic in .NET libraries,
  - easy for analyzers and code review to reason about.

**Common mistakes**

- **Throwing for expected failures** (e.g., parsing with `int.Parse` in a loop): exceptions are expensive and noisy.
- **Overloading semantics**: don’t make `TryX` sometimes throw; keep it predictable.

**Runnable example**

```csharp
using System;
using System.Collections.Generic;

static class Demo
{
    static bool TryParsePort(string? text, out int port)
    {
        if (!int.TryParse(text, out port))
            return false;

        return port is >= 1 and <= 65_535;
    }

    static void Main()
    {
        var inputs = new[] { "443", "0", "70000", "abc", null };

        foreach (var s in inputs)
        {
            if (TryParsePort(s, out var port))
                Console.WriteLine($"Valid port: {port}");
            else
                Console.WriteLine($"Invalid: {s ?? "<null>"}");
        }

        var dict = new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase)
        {
            ["apples"] = 2
        };

        if (dict.TryGetValue("Apples", out var count))
            Console.WriteLine(count);
    }
}
```

**Performance note**

- In hot paths, Try-patterns reduce **CPU** (no exception machinery) and **GC pressure** (fewer allocations from exception objects/stack traces).

### 2) **Comparer/equality injection** (`IComparer<T>`, `IEqualityComparer<T>`, `Comparison<T>`)

**Definition**

Comparer injection is the pattern where your generic algorithm accepts a comparer rather than hard-coding comparison rules.

Prefer:

- `IEqualityComparer<T>` for hashing/equality (`Dictionary`, `HashSet`, distinctness)
- `IComparer<T>` / `Comparison<T>` for ordering/sorting

**When to use**

- The algorithm must work for many `T` values but needs **custom semantics**:
  - case-insensitive keys,
  - domain-specific equality (e.g., SKU normalization),
  - culture-invariant ordering.

**Trade-offs**

- Comparers add an extra indirection (interface call) but often enable correct behavior and prevent subtle bugs.
- The default comparers are highly optimized: `EqualityComparer<T>.Default` is generally the right baseline.

**Common mistakes**

- Using `x == y` for unconstrained `T` (doesn’t compile / wrong semantics).
- Using `object.Equals(x, y)` and accidentally boxing or losing type-specific overrides.
- Creating new comparer instances repeatedly in hot loops (prefer static cached instances, or accept a comparer from the caller).

**Runnable example**

```csharp
using System;
using System.Collections.Generic;

static class Algorithms
{
    public static bool Contains<T>(IEnumerable<T> source, T value, IEqualityComparer<T>? comparer = null)
    {
        comparer ??= EqualityComparer<T>.Default;

        foreach (var item in source)
        {
            if (comparer.Equals(item, value))
                return true;
        }

        return false;
    }
}

static class Demo
{
    static void Main()
    {
        var words = new[] { "Hello", "world" };
        Console.WriteLine(Algorithms.Contains(words, "hello")); // False (Ordinal)
        Console.WriteLine(Algorithms.Contains(words, "hello", StringComparer.OrdinalIgnoreCase)); // True
    }
}
```

**Good to know**

- For dictionary keys, pick an explicit comparer (`StringComparer.Ordinal`, `OrdinalIgnoreCase`) rather than relying on culture or defaults.

### 3) **Projection and mapping** (`Func<TIn, TOut>`)

**Definition**

Projection is “turn \(TIn\) into \(TOut\)”. You see it everywhere:

- LINQ `Select`
- mapping DTOs ↔ domain models
- extracting keys for grouping/sorting

**When to use**

- You want to separate “how to traverse” from “how to transform”.
- You want to reuse an algorithm for different shapes.

**Trade-offs**

- Delegates can allocate when they **capture** variables (closure), and can cost CPU due to indirect calls in tight loops.
- Often totally fine in application code; in hot paths consider patterns that avoid capturing and reduce allocations.

**Common mistakes**

- Accidentally capturing large objects or `this`, extending lifetimes.
- Using LINQ in a hot loop without realizing it allocates enumerators/closures (depends on operators and source type).

**Runnable example (capture-free mapping)**

```csharp
using System;

static class Mapper
{
    public static TOut[] Map<TIn, TOut>(TIn[] input, Func<TIn, TOut> selector)
    {
        var result = new TOut[input.Length];
        for (var i = 0; i < input.Length; i++)
            result[i] = selector(input[i]);
        return result;
    }
}

static class Demo
{
    static void Main()
    {
        var ints = new[] { 1, 2, 3 };
        var strings = Mapper.Map(ints, static x => x.ToString()); // static lambda => no capture allocation
        Console.WriteLine(string.Join(", ", strings));
    }
}
```

**Performance note**

- Prefer **`static` lambdas** when you don’t need captures to avoid closure allocations.
- If mapping must be extremely high-performance, consider specialized overloads (e.g., span-based) and measure.
