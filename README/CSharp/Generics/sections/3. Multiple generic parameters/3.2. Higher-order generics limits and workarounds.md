## 3.2. Higher-order generics and “type constructor” workarounds (what C# can and cannot express)

1. **What’s missing** (no higher-kinded types; impacts on generic FP-style libraries)
2. **Common patterns** (interfaces/abstract factories; source generators; partial specialization workarounds)
3. **Mentor note** (prefer clarity over cleverness; don’t emulate HKT unless you truly need it)

---

### 1) **What’s missing** (no higher-kinded types; impacts on generic FP-style libraries)

**Definition (plain English)**  
In languages with **higher-kinded types (HKTs)**, you can write APIs that abstract over “a generic type constructor” such as `List<>` or `Task<>` itself, not just over `T`.

In C#, you can abstract over:

- a **type**: `T`
- a **generic type with concrete arguments**: `IEnumerable<T>`

But you cannot abstract over:

- “`F<>` where `F<T>` is *some* generic container” (the “type constructor”)

This is why you can’t express something like “a generic method that works over any `F<T>`” in the type system without additional patterns.

**Why you care**  
You’ll feel this most when you try to build:

- generic functional abstractions (`Functor`, `Monad`, “map over any container”)
- “container-agnostic” composition layers (e.g., “a pipeline that can run in `Task<>`, `ValueTask<>`, or a custom async container”)

**Mentor reality check**  
Most business applications do **not** need HKTs. When you do (libraries/frameworks), the solutions tend to trade ergonomics for power.

**Common mistake**  
Trying to emulate HKT-style APIs in normal application code: it often results in unreadable signatures and confusing error messages.

---

### 2) **Common patterns** (interfaces/abstract factories; source generators; partial specialization workarounds)

#### Pattern A: **Strategy + interface injection** (keep genericity at the edges)

When you can’t abstract over `F<>`, you often abstract over **operations** instead:

- provide an interface that represents the operation(s) you need
- keep the core algorithm generic over “the element type”, not the container kind

Example: instead of “map over any container,” accept a projection delegate and let the caller decide the container:

```csharp
using System;
using System.Collections.Generic;

public static class MapDemo
{
    // Container-agnostic algorithm: "project items" from any sequence.
    public static List<TOut> ProjectToList<TIn, TOut>(
        IEnumerable<TIn> source,
        Func<TIn, TOut> map)
    {
        ArgumentNullException.ThrowIfNull(source);
        ArgumentNullException.ThrowIfNull(map);

        var result = new List<TOut>();
        foreach (var item in source)
            result.Add(map(item));

        return result;
    }
}
```

This isn’t “HKTs,” but it’s often the right engineering trade-off: it’s readable, testable, and works across many concrete containers.

#### Pattern B: **Abstract factory for “container creation”**

If you must control the container shape, push that decision behind a factory:

- algorithm depends on a small `IBuilder<T>` / `ICollectionFactory<T>` abstraction
- you implement factories for the containers you care about (`List<T>`, `HashSet<T>`, etc.)

This keeps the type system simple while still allowing customization.

#### Pattern C: **Source generators for boilerplate-heavy patterns**

If you’re building a library and want a “nice” API without reflection, **source generators** can generate repetitive adapters:

- avoids runtime reflection (good for trimming/AOT)
- keeps call sites ergonomic

Trade-off: more complex build story; debug experience differs.

#### Pattern D: **“Partial specialization” via overloads / explicit types**

C# doesn’t support generic type specialization like “`Foo<List<T>>` has a special implementation”.

Workarounds:

- overloads for specific concrete types (pragmatic, but can grow)
- dedicated wrappers: `ListAdapter<T>` etc.

Mentor rule: do this only when you have real performance/behavior reasons and can keep the API coherent.

---

### 3) **Mentor note** (prefer clarity over cleverness; don’t emulate HKT unless you truly need it)

**Rule of thumb**  
If your team can’t read the type signature quickly, the design is probably too abstract.

**Prefer these before “clever generic frameworks”**:

- a small number of well-named overloads
- explicit types (`Task<T>`, `ValueTask<T>`, `IAsyncEnumerable<T>`) rather than “generic async containers”
- composition with delegates and small interfaces

**Performance note**  
The cost of over-abstracting is not just cognitive:

- more interface dispatch in hot paths
- harder inlining/devirtualization opportunities
- more allocations (wrappers, adapters) unless you’re extremely disciplined

When performance matters, measure. Prefer simple shapes that the JIT can optimize.
