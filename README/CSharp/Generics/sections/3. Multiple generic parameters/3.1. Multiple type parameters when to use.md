## 3.1. Two+ type parameters: when it’s right (and when it’s overengineering)

1. **Clear use cases** (`Dictionary<TKey, TValue>`, `Result<TValue, TError>`, `IMapper<TIn, TOut>`)
2. **API readability** (type parameter order; call-site clarity; avoiding `T1/T2` APIs)
3. **Maintenance** (type explosions and constraints that become hard to satisfy)

### 1) **Clear use cases**

Multiple type parameters are justified when each one represents a **distinct role** in your domain model or algorithm.

- **`Dictionary<TKey, TValue>`**: key identity vs stored payload are genuinely different concepts.
- **`Result<TValue, TError>`**: the *successful value* and the *failure representation* are different concepts.
- **`IMapper<TIn, TOut>`**: transforms from an input shape to an output shape.

When it’s *not* justified:

- You’re using extra type parameters to avoid making a small named type (you’re pushing complexity to every call site).
- Your type parameters are not roles; they’re just “T1/T2/T3” because you can’t name them well.
- You can’t explain the public API contract without examples—that’s a smell.

**Mentor stress**

- Generic parameters are part of your **public language**. If consumers need to “remember the order,” the API is already hard.
- Resist “generic everything.” For business apps, readability and debugging time usually dominate micro-performance wins.

**Example (runnable): a sane `Result<TValue, TError>`**

```csharp
using System;

public readonly record struct Result<TValue, TError>(TValue? Value, TError? Error)
{
    public bool IsOk => Error is null;

    public static Result<TValue, TError> Ok(TValue value) => new(value, default);
    public static Result<TValue, TError> Fail(TError error) => new(default, error);
}

public static class Demo
{
    static Result<int, string> ParseInt(string s)
        => int.TryParse(s, out var value)
            ? Result<int, string>.Ok(value)
            : Result<int, string>.Fail("Invalid integer");

    public static void Main()
    {
        var r = ParseInt("123");
        Console.WriteLine(r.IsOk ? r.Value : r.Error);
    }
}
```

**Good to know**

- This example uses a `record struct` to keep it value-like and easy to pass around.
- If you want nullability to be strict, see section `2.2` for the correct constraint strategies for `T`.

---

### 2) **API readability**

If a generic type has 2+ type parameters, spend design effort on:

- **Order**: put the “primary” concept first.
  - `Dictionary<TKey, TValue>` reads naturally.
  - `Task<TResult>` reads naturally.
  - For `Result<TValue, TError>`, value-first is typical.
- **Names**: use role-based names, not `T1/T2`.
  - Good: `TKey`, `TValue`, `TInput`, `TOutput`, `TError`, `TOptions`
  - Bad: `T1`, `T2` (unless it’s an internal/private helper you’re willing to delete freely)
- **Constraints**: add only what the API truly needs.
  - Constraints can improve diagnostics, but they also reduce applicability and become versioning constraints.

**Call-site clarity is a first-class requirement**

If the call site looks like:

```csharp
// Hard to read: what is what?
Cache<Foo, Bar, Baz> cache = new();
```

consider replacing it with:

- a named type (`FooCache`), or
- an options type (`CacheOptions`), or
- a smaller generic surface (one generic parameter + injected strategy).

**Performance note**

Readability affects performance indirectly: confusing generics cause wrong usage (allocations, boxing, unnecessary ToList/ToArray) and lead to “fixes” that are worse than the original code.

---

### 3) **Maintenance**

The “type parameter explosion” failure mode looks like this:

- `Pipeline<TIn, TMid1, TMid2, TMid3, TOut, TError, TContext, ...>`

Problems:

- **Every change ripples** through many call sites.
- Constraints become combinatorial.
- Error messages get worse, not better.

Better patterns:

- **Group related concepts** into a single type parameter:
  - `Pipeline<TStage>` where `TStage` is a discriminated union / interface family that represents stages.
- **Use composition**:
  - `ITransformer<TIn, TOut>` pieces combined in a pipeline type that is not itself parametrized by every intermediate type.
- **Use options objects** (in app code):
  - `PipelineOptions` as a `record` with named properties.

**Common mistake**

Don’t ship “clever generic frameworks” without a real use case. They tend to become the hardest thing to evolve and the first thing people work around.
