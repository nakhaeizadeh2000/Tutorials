## 8.1. Pitfalls: where generic code surprises even experienced devs

1. **Assuming `default(T)` means “null”** (it’s zero/null/empty depending on `T`)
2. **Wrong equality** (`==` doesn’t work for unconstrained `T`; use `EqualityComparer<T>.Default`)
3. **Boxing through interfaces/logging** (structs + non-generic interfaces + `params object[]`)
4. **Reusing generic types with incompatible nullability contracts** (unconstrained `T` is tricky)
5. **Leaking allocations** (LINQ, captures, enumerator boxing in edge cases; measure hot paths)

---

### 1) **Assuming `default(T)` means “null”**

**What it means**

`default(T)` is the *zero-initialized* value of \(T\):

- If \(T\) is a reference type → `default(T)` is `null`.
- If \(T\) is a value type → `default(T)` is the all-zero bit pattern (e.g., `0`, `false`, `DateTime.MinValue`, `Guid.Empty`, custom struct with all fields zeroed).

This is why **unconstrained** `T` is tricky: at compile time you don’t know which case you’re in.

**Common bug**

Treating `default(T)` as “missing” or “not found” in a generic API leads to incorrect behavior for value types where `default` can be a *valid* business value.

Bad (ambiguous sentinel):

```csharp
public static class Bad
{
    // "Not found" is indistinguishable from a value-type T whose value happens to be default(T).
    public static T FindOrDefault<T>(IEnumerable<T> source, Func<T, bool> predicate)
    {
        foreach (var item in source)
            if (predicate(item)) return item;

        return default!;
    }
}
```

Better (explicit success/failure):

```csharp
public static class Better
{
    public static bool TryFind<T>(IEnumerable<T> source, Func<T, bool> predicate, out T value)
    {
        foreach (var item in source)
        {
            if (predicate(item))
            {
                value = item;
                return true;
            }
        }

        value = default!;
        return false;
    }
}
```

**Mentor rule**

- If “not found” is possible, represent it as **`bool` + `out`** (Try-pattern), **`Nullable<T>`** (only when `T : struct`), or an explicit **`Option<T>`/`Result<T, TError>`** type.
- Don’t smuggle “not found” into `default(T)` unless your API *restricts* \(T\) and documents that `default` is never a valid value.

**Good to know**

- `default` literals (`default`) are context-typed and can become ambiguous in overload sets. See `Methods/5.1` for overload resolution pitfalls.

### 2) **Wrong equality (`==` doesn’t work for unconstrained `T`)**

**Why it fails**

The `==` operator:

- is not part of “the generic contract” for arbitrary \(T\),
- may not exist for a given \(T\),
- and even when it exists, it might not reflect the equality semantics you want (e.g., reference identity vs value equality).

So this won’t compile for unconstrained \(T\):

```csharp
public static bool Contains<T>(ReadOnlySpan<T> span, T value)
{
    foreach (var x in span)
    {
        // return x == value; // error: operator '==' cannot be applied to operands of type 'T' and 'T'
    }
    return false;
}
```

**Correct default: `EqualityComparer<T>.Default`**

```csharp
using System.Collections.Generic;

public static class Equality
{
    public static bool Contains<T>(ReadOnlySpan<T> span, T value)
    {
        var eq = EqualityComparer<T>.Default;
        foreach (var x in span)
        {
            if (eq.Equals(x, value)) return true;
        }
        return false;
    }
}
```

**Why mentors like it**

- It’s *correct* across reference/value types.
- It uses specialized implementations when available (e.g., when `T : IEquatable<T>`).
- It avoids many boxing traps that come from treating values as `object`.

**Performance note**

On hot paths, store `EqualityComparer<T>.Default` in a local (`eq` above) so you don’t recompute it repeatedly (it’s usually cheap, but you’re teaching the right habit).

**If you truly need “operator constraints”**

Use **static abstract interface members** (generic math style) so \(T\) is constrained to types that *promise* the operator exists.

See `Generics/4.1` for the full constraint taxonomy and static abstract members patterns.

### 3) **Boxing through interfaces/logging**

**Reminder**

Generics don’t magically prevent boxing if you:

- accept `object`,
- store a struct in an interface-typed variable,
- or pass value types through `params object[]` (classic logging/formatting APIs).

This is covered in depth elsewhere in this repo:

- See `README/CSharp/Structures/sections/3. Struct vs class/3.3. Boxing interfaces generics.md` for the full boxing + generics story.
- See `README/CSharp/System Object Class/sections/4. object in APIs/4.2. Avoid boxing in modern CSharp.md` for “avoid object-shaped APIs” guidance.

**Quick diagnostic tip**

If a generic hot path allocates unexpectedly, search for:

- `object`,
- non-generic interfaces (`IEnumerable`, `IComparable`, …),
- and `params object[]`.

### 4) **Reusing generic types with incompatible nullability contracts**

**The problem**

`T` is not “nullable” or “non-nullable” unless you constrain it. So designs like “this cache never returns null” are not representable with unconstrained \(T\).

Bad API (lies by omission):

```csharp
public sealed class Cache<T>
{
    private readonly Dictionary<string, T> _map = new();

    public T Get(string key) => _map[key]; // can throw, and might return default(T) if you used that as sentinel elsewhere
}
```

Better patterns:

- Add **`where T : notnull`** when keys/values must be non-null.
- Prefer **Try-pattern** for retrieval.

```csharp
using System.Collections.Generic;

public sealed class Cache<T> where T : notnull
{
    private readonly Dictionary<string, T> _map = new();

    public bool TryGet(string key, out T value) => _map.TryGetValue(key, out value!);
}
```

**Mentor rule**

- If `null` is a valid cached value (rare but possible), you need a richer representation: `Option<T>` / `Result<T, ...>` or a dedicated discriminated type.

**See also**

For a full treatment of `T`, `T?`, `notnull`, and constraints-driven API contracts, see `Generics/2.2`.

### 5) **Leaking allocations (LINQ, captures, enumerator boxing in edge cases)**

**The reality**

Generics help you avoid `object` and casts, but they don’t prevent:

- allocations from LINQ pipelines,
- allocations from delegate captures (closures),
- async state machines (when you choose async),
- and occasionally enumerator boxing when iteration happens through non-generic interfaces.

**What to do**

- Design APIs so the “fast path” doesn’t require delegates or allocation-heavy abstractions.
- Prefer `ReadOnlySpan<T>` / `Span<T>` overloads for parsing-heavy or hot-path loops when they fit (see `Generics/5.3`).
- Avoid “sync-over-async” and ThreadPool blocking; not a generics topic, but it shows up in real code. See `README/CSharp/Cuncurrent & Parallel` for the full treatment.

**Performance note**

- Measure allocations with a profiler (`dotnet-counters`, allocation profiler in VS/Rider). Fix the biggest allocation source first.
