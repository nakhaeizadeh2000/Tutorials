## 2.1. Designing generic classes (API honesty, naming, and ergonomics)

1. **Choosing abstractions** (`IReadOnlyList<T>` vs `IEnumerable<T>` vs concrete types)
2. **Naming type parameters** (`T`, `TKey`, `TValue`, `TOptions`, `TResult`; when *not* to invent names)
3. **Versioning** (how adding constraints/type parameters becomes a breaking change)

### 1) **Choosing abstractions** (`IReadOnlyList<T>` vs `IEnumerable<T>` vs concrete types)

**Definition**

In .NET, the abstraction you expose is your **contract**. For generic types, the contract choice often matters more than the implementation because the type parameter \(T\) tends to make the API look “flexible” even when the semantics are actually strict.

Common generic collection contracts and what they *really* promise:

- **`IEnumerable<T>`**: a **sequence**. You can enumerate items (possibly lazily) and that’s it.
  - No promise of *single vs multiple enumeration*.
  - No promise of *count*, *indexing*, *ordering stability* (beyond whatever the producer does), or *thread-safety*.
- **`IReadOnlyCollection<T>`**: sequence + **`Count`**.
- **`IReadOnlyList<T>`**: sequence + **`Count` + indexing** (random access).
- **`ICollection<T>` / `IList<T>`**: **mutable** collection contracts (add/remove/index set). These are strong promises you should expose only when you truly need external mutation.
- **Concrete types** (`List<T>`, `T[]`, `ImmutableArray<T>`, `Dictionary<TKey,TValue>`): strongest semantics, often best for performance guarantees, but highest coupling.

**When to use which (mentor guidance)**

- **Accept broader, return narrower** is usually the right instinct, but “broader” must still be honest:
  - **Accept**: `IReadOnlyList<T>` if you require indexing or stable count.
  - **Accept**: `IEnumerable<T>` when you only need streaming enumeration (and you will enumerate once).
  - **Return**: `IReadOnlyList<T>` / `ImmutableArray<T>` when callers benefit from count/indexing and you want to avoid “lazy surprises”.
  - **Return**: `IEnumerable<T>` only when laziness is intentional and documented (and safe regarding lifetime).

**Trade-offs**

- **API stability vs performance**: returning `IEnumerable<T>` can hide whether the sequence is materialized or deferred, which can create accidental repeated work or repeated allocations when consumers enumerate multiple times.
- **Testability**: broad abstractions are easier to fake, but excessively broad can allow “bad” implementations that violate assumptions.
- **Performance**:
  - Enumeration over `IEnumerable<T>` often involves an interface-based enumerator path. For arrays and lists, the JIT can optimize many cases, but not all (especially when the static type is the interface).
  - If you need **zero allocations** in hot paths, consider offering overloads that accept `ReadOnlySpan<T>` / `Span<T>` (see `Generics/5.3`) rather than forcing everything through `IEnumerable<T>`.

**Common mistakes**

- Returning `IEnumerable<T>` from a method that actually builds a list internally, then callers enumerate twice and unknowingly do the expensive work twice.
- Accepting `IEnumerable<T>` and then calling `.Count()` / `.ToList()` internally “because you need it” — this forces enumeration and allocations. If you need count or indexing, **ask for it** in the signature.

**Runnable example: “honest abstraction”**

```csharp
using System;
using System.Collections.Generic;

public static class ApiShapes
{
    // Honest: we need indexing and Count.
    public static T Middle<T>(IReadOnlyList<T> items)
    {
        if (items.Count == 0) throw new ArgumentException("Must not be empty.", nameof(items));
        return items[items.Count / 2];
    }

    // Honest: we only stream through once.
    public static int CountMatching<T>(IEnumerable<T> items, Func<T, bool> predicate)
    {
        ArgumentNullException.ThrowIfNull(items);
        ArgumentNullException.ThrowIfNull(predicate);

        var count = 0;
        foreach (var item in items)
            if (predicate(item)) count++;

        return count;
    }
}

public static class Demo
{
    public static void Main()
    {
        Console.WriteLine(ApiShapes.Middle(new[] { 1, 2, 3, 4, 5 }));
        Console.WriteLine(ApiShapes.CountMatching(new List<string> { "a", "bb", "ccc" }, static s => s.Length >= 2));
    }
}
```

**Performance note**

If you’re designing high-throughput APIs, consider offering two shapes:

- A general-purpose shape (e.g., `IEnumerable<T>`), and
- A high-performance shape (`ReadOnlySpan<T>`, `IReadOnlyList<T>`, or an overload taking `T[]`), so callers on hot paths can avoid allocations and avoid repeated enumeration.

### 2) **Naming type parameters** (`T`, `TKey`, `TValue`, `TOptions`, `TResult`; when *not* to invent names)

**Definition**

Type parameter names are not cosmetic: they are part of your API documentation and shape IDE IntelliSense.

**Rules of thumb (mentor-grade)**

- Use **`T`** when there is exactly one obvious “main” type.
- Use **role-based names** when there are multiple type parameters:
  - **`TKey`, `TValue`** for maps/dictionaries.
  - **`TIn`, `TOut`** / **`TSource`, `TDestination`** for transforms/mappers.
  - **`TOptions`** for configuration objects.
  - **`TResult`** for return payload type.
  - **`TItem`** for collections when you want to emphasize “item-ness”.
- Avoid:
  - `T1`, `T2`, `T3` in public APIs (reads like a math proof, not a library).
  - Long names that restate the containing type (noise).
  - Names that encode implementation (e.g., `TListImplementation`) — that’s a design smell.

**Trade-offs**

- More descriptive names improve readability, but can get verbose. Prefer concise role names.
- If you find yourself inventing very specific parameter names to “explain” the type, it may be a sign your generic abstraction is too broad.

**Runnable example: readability at the call site**

```csharp
using System;

public interface IMapper<in TIn, out TOut>
{
    TOut Map(TIn input);
}

public sealed class IntToStringMapper : IMapper<int, string>
{
    public string Map(int input) => input.ToString();
}

public static class Demo
{
    public static void Main()
    {
        IMapper<int, string> mapper = new IntToStringMapper();
        Console.WriteLine(mapper.Map(123));
    }
}
```

**Good to know**

Variance (`in`/`out`) is part of how you communicate producer/consumer roles. For a deep variance treatment, see `README/CSharp/Type Conversion/sections/2. Implicit conversions/2.2. Reference conversions upcast and variance basics.md`.

### 3) **Versioning** (how adding constraints/type parameters becomes a breaking change)

**Definition**

Once a generic type is public, its generic shape is part of your public contract:

- number of type parameters
- parameter ordering
- constraints (`where T : ...`)
- nullability annotations

**What changes are breaking (practical view)**

- Adding a **new type parameter**: obviously breaking for all call sites.
- Reordering type parameters: breaks all call sites and type inference patterns.
- Adding or tightening **constraints**:
  - Can break compilation for existing consumers who used types that no longer satisfy constraints.
  - Can also change runtime behavior if the JIT chooses different code paths due to constraints (especially for value types and interface calls).
- Changing nullability (`T` vs `T?` in the API) changes warnings and can break builds in “warnings as errors” codebases.

**When you should add constraints anyway**

- When the constraint is required for correctness (you rely on members or semantics that are not valid for all \(T\)).
- When it prevents a class of bugs *and* makes the error show at compile time with a clear message.

**Alternatives to breaking changes**

- Add a **new type** or **new overload** instead of changing the existing generic type.
- Use a strategy object / interface parameter rather than imposing constraints on \(T\).
- Introduce a new generic parameter in a new type while keeping the old one as a compatibility layer.

**Performance note**

Constraints can enable allocation-free and boxing-free paths, but don’t treat them as “free speed”. The largest design costs are still: repeated enumeration, hidden allocations, and accidental polymorphism in hot paths.
