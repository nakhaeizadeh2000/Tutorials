## 3.3. Static initialization and static state: keep it predictable and safe

1. **Initialization costs** (cold start p99; type initializer exceptions; “first touch” latency spikes)
2. **Thread-safety** (publication, `Lazy<T>`, `Interlocked`, and avoiding lock contention)
3. **Memory pressure** (static caches retain memory for process lifetime; bounded caches and eviction)

### 1) **Initialization costs**

Static initialization shifts work into **first-touch** time:

- The first call that touches a type/member may pay the cost of initializing static fields and/or running a type initializer.
- This shows up as **p99 latency spikes** if it happens on a request path (web/API), UI interaction, or any “cold start” code path.

**Mentor guidance**

- Keep static initialization **cheap and deterministic**.
- If you *need* expensive initialization, prefer **explicit warm-up** during app startup (so the latency is paid in a controlled place).

**Example: explicit warm-up instead of “surprise first touch”**

```csharp
using System;

public static class AppWarmup
{
    public static void Initialize()
    {
        // Touch the things you want initialized during startup.
        _ = ExpensiveCaches.UserLookup;
    }
}

public static class ExpensiveCaches
{
    public static readonly object UserLookup = BuildCache();

    private static object BuildCache()
    {
        // Keep it deterministic; avoid network I/O here.
        return new object();
    }
}
```

Good to know:

- In server apps, “warm-up” is often done during host startup (before serving traffic).
- If the initialization can fail, you want it to fail **early** and **loud**, not randomly on the first user request.

### 2) **Thread-safety**

Static state is shared across all callers in a process. That means it is implicitly a **concurrency and lifetime concern** even if your code “looks single-threaded”.

**Rule of thumb**

- If it’s **immutable** and safely published, static state is usually fine.
- If it’s **mutable**, you must define (and enforce) a thread-safety strategy:
  - single-writer confinement (preferred where possible),
  - `lock`/`SemaphoreSlim` (for multi-step invariants),
  - `Interlocked` (for simple counters/flags),
  - or remove the static state and move it behind an instance boundary (DI).

For the deep “what is safe publication?” explanation, do not duplicate it here.
See the memory model reference mentioned above.

**Example: safe static counter**

```csharp
using System.Threading;

public static class Metrics
{
    private static long _requests;

    public static void RecordRequest() => Interlocked.Increment(ref _requests);

    public static long Requests => Interlocked.Read(ref _requests);
}
```

Performance note:

- `Interlocked` is typically faster than locking for simple numeric state.
- If you find yourself needing multiple correlated fields, switch to `lock` (atomicity across multiple variables matters more than micro-optimizing).

**Anti-pattern: mutable static dependencies**

```csharp
public static class UserService // Don’t do this.
{
    public static object? Dependency; // Mutable, shared, untestable.
}
```

Why it’s bad:

- introduces hidden global state,
- creates test order dependencies,
- causes multi-tenant bugs,
- and usually becomes a hotspot for contention or lifecycle leaks.

Prefer instance services registered via DI. See [3.2](<./3.2. Static classes vs alternatives DI extension methods.md>) for guidance.

### 3) **Memory pressure**

Static state lives for a long time (often the whole process lifetime). That makes static caches *dangerous by default*:

- If it grows without bounds, it is effectively a **memory leak by design**.
- If it holds onto objects, it prevents them from being garbage collected.
- If it holds onto large graphs, it increases GC pressure and can push objects into Gen2/LOH.

**Mentor rules for caches**

- Every cache must have at least one of:
  - **size bound** (max entries),
  - **time bound** (TTL),
  - **eviction strategy** (LRU-ish),
  - or **explicit invalidation**.
- Be explicit about what “key” means and avoid keys that are unbounded (e.g., raw user input strings without normalization).

**Example: bounded cache shape (conceptual)**

This tutorial repo may not include a cache library, so keep the example focused on design intent:

```csharp
using System.Collections.Concurrent;

public static class SimpleBoundedCache
{
    private const int MaxEntries = 10_000;
    private static readonly ConcurrentDictionary<string, string> _cache = new();

    public static bool TryGet(string key, out string value) => _cache.TryGetValue(key, out value!);

    public static void Set(string key, string value)
    {
        _cache[key] = value;

        // Oversimplified: in real systems use a real eviction policy.
        if (_cache.Count > MaxEntries)
        {
            _cache.Clear(); // Clears are brutal; shown only to highlight the need for policies.
        }
    }
}
```

Good to know:

- `ConcurrentDictionary` is not a “free thread-safety wand”. It helps with concurrency, but it doesn’t solve **bounded growth** or **policy**.
- A better real-world solution is often an **instance cache** with lifetime control (DI) and a dedicated eviction strategy.
