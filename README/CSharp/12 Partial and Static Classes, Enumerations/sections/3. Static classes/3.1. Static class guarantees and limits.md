## 3.1. Static class basics: what a `static class` guarantees (and what it doesn’t)

1. **Rules** (no instances; only static members; sealed + abstract under the hood)
2. **Good use cases** (pure functions, cohesive helpers, extension method containers)
3. **Bad use cases** (hidden global state, “service locator”, static mutable dependencies)

---

### 1) **Rules**

**Definition**

A `static class` in C# is a type that:

- Cannot be instantiated (`new` is illegal).
- Can contain **only static members**.
- Cannot be inherited from (effectively **sealed**).

Under the hood, the compiler emits it as an **abstract sealed** type (IL concept). The important point is the *design intent*: “this is a namespace-like container for static members”, not an object.

**What this guarantees**

- You will not accidentally create multiple instances.
- Every member access is type-qualified (or imported via `using static`), which can signal “stateless helper”.

**What this does NOT guarantee**

- **Thread-safety**: static members can still mutate shared state.
- **No allocations**: static methods can still allocate (LINQ, closures, strings, collections).
- **Good design**: a static class can become an untestable “god helper” just as easily as an instance singleton.

**Minimal example**

```csharp
public static class Temperature
{
    public static double CelsiusToFahrenheit(double c) => (c * 9d / 5d) + 32d;
}
```

This is a good use: a pure function with no hidden state.

---

### 2) **Good use cases**

#### A) **Pure, deterministic functions**

The strongest “green flag” for `static` is: the method is a pure transform.

Mentor rule:

- If you can unit-test it with just inputs → outputs and no setup, static is usually fine.

Example (allocation-aware):

```csharp
using System;

public static class Hex
{
    public static bool TryParseByte(ReadOnlySpan<char> s, out byte value)
        => byte.TryParse(s, System.Globalization.NumberStyles.HexNumber, provider: null, out value);
}
```

Good to know:

- `ReadOnlySpan<char>` parsing avoids slicing allocations in hot paths. (Deep parsing guidance lives in `README/CSharp/06 Type Conversion`.)

#### B) **Extension method containers**

Extension methods must be declared in a static class. This is one of the most common and legitimate uses.

Guidance:

- Keep extension methods **cohesive** (one domain per class/namespace).
- Don’t create “Extensions” junk drawers that import everywhere.

Example:

```csharp
using System;

public static class StringExtensions
{
    public static bool IsNullOrWhiteSpace(this string? s) => string.IsNullOrWhiteSpace(s);
}
```

Note:

- In libraries, be conservative: extension methods affect overload resolution and can surprise consumers. (See the `Namespaces` domain for `using`/extension method pitfalls.)

#### C) **Stateless factories**

Static factory methods can help centralize validation and keep invariants tight.

```csharp
public readonly record struct EmailAddress(string Value)
{
    public static bool TryCreate(ReadOnlySpan<char> input, out EmailAddress email)
    {
        if (input.IsEmpty || input.Length > 254 || input.IndexOf('@') <= 0)
        {
            email = default;
            return false;
        }

        email = new EmailAddress(input.ToString()); // allocation is intentional (stable storage)
        return true;
    }
}
```

---

### 3) **Bad use cases**

#### A) **Hidden global mutable state**

Classic anti-pattern:

```csharp
public static class GlobalSettings
{
    public static string ConnectionString { get; set; } = "";
}
```

Why it’s harmful:

- **Order dependence**: tests and startup order decide behavior.
- **Multi-tenant bugs**: one caller changes state for everyone.
- **Thread-safety**: shared mutation requires synchronization (and correct publication).
- **Lifetime leaks**: static references keep objects alive for the lifetime of the process.

Better (C# 15 / modern .NET):

- Use **options + DI** (e.g., `IOptions<T>`) for app configuration.
- Use instance services with explicit lifetimes.

#### B) **“Service locator” static APIs**

```csharp
public static class Services
{
    public static IServiceProvider Provider { get; set; } = default!;
}
```

This is a correctness and maintainability trap:

- Any code can grab any dependency at any time.
- You lose compile-time visibility of dependencies.
- You make testing and refactoring harder.

Use DI properly: pass dependencies via constructors, or use factories where appropriate.

#### C) **Static caches without bounds**

Unbounded static caches are memory leaks by design. If you cache, cache with:

- explicit bounds,
- explicit eviction policy,
- explicit concurrency strategy.

See `3.3` for practical guidance on static initialization and shared state, and `README/CSharp/04 Fields/sections/4. Static fields/4.1. Static fields when appropriate and when a trap.md` for deeper “static state as a lifetime problem”.
