## 4.1. Enum fundamentals: underlying types, default values, and versioning

1. **Underlying storage** (`byte`/`int`/`long` etc.; interop and memory layout realities)
2. **Default value trap** (`default(TEnum)` is \(0\); why “0 means Unknown” is a design choice)
3. **Public API versioning** (adding values, removing values, renaming, and serialization compatibility)

---

Enums are one of the most common C# modeling tools. They’re also a frequent source of **latent bugs** because:

- `default(TEnum)` is always \(0\), whether or not you intended \(0\) to be valid.
- Enums are just numbers at runtime: you can hold invalid values unless you validate.
- Public enums are **versioned contracts**: serialization, logging, DB storage, and interop all depend on stable meaning.

This file is the **single deep reference** for enum fundamentals, versioning, and “what does 0 mean?” design.

For `[Flags]` bitwise enums, see **4.2**. For “don’t use enums, use types” modeling, see **4.3**.

---

### 1) **Underlying storage**

#### **What an enum is**

An enum is a named set of **integral constants**. Under the hood it has an **underlying integral type**:

- default underlying type is `int`
- you can choose: `byte`, `sbyte`, `short`, `ushort`, `int`, `uint`, `long`, `ulong`

```csharp
public enum HttpStatusCode : short
{
    Ok = 200,
    NotFound = 404
}
```

#### **How to choose the underlying type**

Mentor rule:

- **Prefer the default (`int`)** unless you have a strong reason.

Choose a smaller underlying type (`byte`, `short`) only when:

- you’re optimizing a hot, memory-packed structure (arrays of millions of values), *and*
- you measured memory pressure / cache behavior, *and*
- you control all serialization/interop boundaries (or you can explicitly enforce them).

Choose `long`/`ulong` when:

- values exceed `int` range, or
- you’re doing bit flags that need > 32 bits (rare; validate carefully).

**Performance note**

- The storage size can matter in large arrays (cache locality), but most enum “performance problems” come from:
  - excessive parsing/formatting (`Enum.Parse`, `ToString`)
  - boxing (e.g., `(object)myEnum`)
  - reflection-heavy usage

Prefer compile-time constructs (`switch` expressions) and avoid repeated string conversions in hot paths.

#### **Interop realities**

Interop (native, file formats, wire protocols) often wants a specific size. In those cases:

- choose the underlying type explicitly, and
- document the mapping, and
- validate inputs at boundaries.

### 2) **Default value trap**

#### **The rule**

`default(TEnum)` is always **zero**.

```csharp
public enum OrderState
{
    Unknown = 0, // deliberate
    Created = 1,
    Paid = 2,
    Shipped = 3
}

OrderState s = default; // Unknown
```

#### **Design choice: what should 0 mean?**

You have two defensible strategies:

1) **Make \(0\) a valid sentinel** (`Unknown` / `Unspecified` / `None`)  
   - Best for public APIs and serialization boundaries
   - Makes default values safe and predictable

2) **Make \(0\) invalid and validate aggressively**  
   - Useful in tightly controlled domains where “unknown” is not allowed
   - Requires you to prevent default initialization paths (hard in practice: arrays, fields, deserialization, ORM materialization)

Mentor recommendation (most production systems):

- **Prefer `Unknown = 0`** (or `None = 0` for flags) unless you have a strong invariant that rejects unknown states.

#### **Invalid values are always possible**

Enums do not enforce membership at runtime:

```csharp
OrderState s = (OrderState)12345; // compiles, runs
```

So at boundaries you should validate.

Modern validation options:

- `Enum.IsDefined(typeof(TEnum), value)` (works, but can be slow if called frequently and can be surprising with `[Flags]`)
- Prefer explicit validation logic or `switch` for hot paths.

**Example: boundary validation with a switch**

```csharp
static bool IsValid(OrderState s) => s is
    OrderState.Unknown or
    OrderState.Created or
    OrderState.Paid or
    OrderState.Shipped;
```

This avoids reflection and is easy to keep in sync for small enums.

### 3) **Public API versioning**

Public enums are contracts. The “meaning” of a numeric value leaks into:

- JSON payloads (as numbers or strings)
- database storage
- logs/telemetry
- backward/forward compatibility with older clients
- other languages and services

#### **Adding values**

Adding new values is usually source-compatible, but may break behavior if:

- code uses `switch` without a fallback
- code assumes the set is closed and exhaustive

Mentor rule:

- Treat switches over public enums as **non-exhaustive** unless you control all callers.

Use a default/fallback branch:

```csharp
static string Describe(OrderState state) => state switch
{
    OrderState.Created => "Created",
    OrderState.Paid => "Paid",
    OrderState.Shipped => "Shipped",
    OrderState.Unknown => "Unknown",
    _ => "Unknown" // forward-compatible
};
```

#### **Removing values**

Removing or reusing numeric values is risky:

- older persisted data may still contain the removed numeric value
- older clients may still send it

Prefer **deprecating** (keep value, stop producing it) over removing it.

#### **Renaming values**

Renaming doesn’t change the numeric value, but it can break:

- string serialization (if you serialize names)
- logs, dashboards, alert rules

If your wire format uses strings, be explicit about mapping (serializer settings / converters) and treat renames as a breaking change unless you support aliases.

#### **Serialization strategy**

Mentor guidance:

- Decide early: **numbers** or **strings** on the wire.
- If you serialize as strings, plan for unknown values and name changes.
- If you serialize as numbers, plan for “unknown numeric values” on read.

Do not rely on `Enum.Parse` as a “safe input validation” mechanism; it throws exceptions and can accept numeric strings in surprising ways.

**Example: parsing without exceptions**

```csharp
using System;

static bool TryParseOrderState(string? input, out OrderState state)
{
    if (Enum.TryParse(input, ignoreCase: true, out state) && IsValid(state))
        return true;

    state = OrderState.Unknown;
    return false;
}
```

Performance note:

- `Enum.TryParse` can allocate and do parsing work. Avoid calling it repeatedly in hot loops.
- For high-throughput services, consider parsing once at the boundary and carrying the enum through strongly-typed APIs.
