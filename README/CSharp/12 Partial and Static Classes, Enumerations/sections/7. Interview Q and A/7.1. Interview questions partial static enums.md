### 1) **When to use partial types**

**Q: Why do partial classes exist?**

**Answer**

- The primary reason is **code generation boundaries**: tooling can generate one part and you safely maintain the other part without merge conflicts or edits being overwritten.
- The compiler merges parts into **one** type; there is no runtime overhead.

**What a senior interviewer wants to hear**

- You use partial types mainly for **generated + handwritten cohabitation** (source generators, designer code).
- Using partial types “just to split a large file” is often a **design smell**: prefer decomposition (smaller types, composition) unless the type is genuinely one cohesive contract.

See for the full treatment:

- `README/CSharp/12 Partial and Static Classes, Enumerations/sections/1. Partial types/1.1. Partial classes purpose codegen separation.md`
- `README/CSharp/12 Partial and Static Classes, Enumerations/sections/1. Partial types/1.2. Partial type rules constraints.md`

**Good to know**

- Partial types cannot extend a type across assemblies. They’re a single-project compile-time feature.

### 2) **Partial methods semantics**

**Q: What happens if a partial method has no implementation?**

**Answer**

- For classic hook-style `partial void` methods (no `out` parameters), the compiler can **remove the call entirely** when no implementation exists. That’s the key benefit: “optional hook, zero runtime cost when unused”.
- For contract-style partial methods (return value / required outputs), an implementation is required because the call site needs a value.

See for the deep rules and modern capabilities:

- Fundamentals and a runnable hook example: `README/CSharp/12 Partial and Static Classes, Enumerations/sections/2. Partial methods/2.1. Partial methods fundamentals declaration implementation.md`
- Modern rules and generator patterns: `README/CSharp/12 Partial and Static Classes, Enumerations/sections/2. Partial methods/2.2. Partial methods modern rules accessibility return attributes.md`

**Pitfall**

- Treating partial methods like a public extensibility mechanism. They are not a plugin system; they are compile-time composition.

### 3) **Static class vs singleton vs DI**

**Q: When is a static class the right choice?**

**Answer**

- When the API is **pure/stateless** (input → output) or when you need a container for **extension methods**.

**Q: When is a static class the wrong choice?**

**Answer**

- When it hides dependencies (time, config, I/O) or stores mutable state. That becomes global state with lifetime and concurrency risks.

**Q: Why prefer DI over static singletons in modern .NET?**

**Answer**

- DI makes dependencies **explicit**, supports testing and substitution, controls lifetime, and avoids “spooky action at a distance”.

### 4) **Enum design**

**Q: Why do mentors insist on `Unknown = 0`?**

**Answer**

- Because `default(TEnum)` is always \(0\). Making \(0\) a valid sentinel makes default initialization, deserialization, and “unset” states predictable.

**Q: What are the versioning risks of enums?**

**Answer**

- Public enums are contracts. Adding values can break switches that assume exhaustiveness. Renaming breaks string-based serialization and dashboards. Removing values breaks persisted data and old clients.

### 5) **Performance questions**

**Q: What are the real performance risks with static?**

**Answer**

- Not “static keyword is slow/fast”, but:
  - expensive first-touch static initialization causing latency spikes,
  - contention on shared static mutable state,
  - unbounded static caches retaining memory for process lifetime.

See:

- Static initialization and state: `README/CSharp/12 Partial and Static Classes, Enumerations/sections/3. Static classes/3.3. Static initialization and shared state.md`
- Deep static initialization patterns: `README/CSharp/04 Fields/sections/4. Static fields/4.2. Static initialization type constructors Lazy thread-safety.md`

**Q: What’s the enum performance trap you see most in production?**

**Answer**

- Repeated string parsing/formatting (`Enum.Parse`, `ToString`) in hot paths. Prefer parsing once at boundaries and keep enums internal, and prefer bitwise checks for flags in tight loops.
