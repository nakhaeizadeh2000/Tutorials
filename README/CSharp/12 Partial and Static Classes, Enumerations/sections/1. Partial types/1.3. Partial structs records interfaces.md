## 1.3. Partial types beyond classes: structs, records, and interfaces (C# 15 era)

1. **Partial structs and records** (when it helps; pitfalls with invariants and generated members)
2. **Partial interfaces** (rare but useful with generated members / incremental augmentation)
3. **Modern guidance** (keep one “owner” file; isolate generated code; keep public surface obvious)

---

### 1) **Partial structs and records**

**Definition**

`partial` applies to most type declarations, not only `class`:

- **`partial struct`**
- **`partial record class` / `partial record struct`**
- **`partial interface`**

All parts combine into one logical type at compile time.

**When partial structs make sense**

- **Source generation**: generators add fast parsing/formatting, validation, or serialization helpers while you own the “domain shape”.
- **Interop**: partial structs that map to native layouts (careful: layout attributes become part of the contract).
- **Large value types**: rare; prefer smaller structs. Splitting a large struct can hide complexity and make it worse.

**Pitfalls (struct-specific)**

- **Large structs are expensive to copy**. A partial declaration can hide that a struct has become “too big”.
  - Mentor rule: if your struct is not trivially small and immutable, consider a class/record class instead, or redesign.
- **`readonly struct` / `in` parameters**: correctness and performance subtleties (defensive copies) belong in your `Fields` domain. See [6.3. Readonly and structs defensive copies and in parameters](<../../../04 Fields/sections/6. Readonly fields/6.3. Readonly and structs defensive copies and in parameters.md>) for the deep treatment.

**When partial records make sense**

Records are already often split by tooling:

- You define the record, invariants, and public surface.
- A generator adds: extra members, validation hooks, mapping, or serialization metadata.

**Pitfalls (record-specific)**

- **Generated members**: records have compiler-generated equality, `Deconstruct`, `with`, etc. Partial additions can accidentally change semantics (e.g., adding mutable state that equality ignores).
- **Invariants**: partial parts can add new ways to construct or mutate the type, undermining your invariant strategy.
  - Mentor rule: keep invariant enforcement centralized (primary constructor, validating factory, or `TryCreate`), and don’t scatter “extra mutation” into other partial parts.

**Example (minimal): record extended by generator-friendly partial**

```csharp
namespace Demo;

public readonly partial record struct Money(decimal Amount, string Currency);

// Another file (could be generated)
public readonly partial record struct Money
{
    public static Money Zero(string currency) => new(0m, currency);
}
```

Good to know:

- This is compile-time composition—no runtime plugin system.

### 2) **Partial interfaces**

**Why they’re rare**

Most interfaces are small, stable contracts; splitting them usually reduces clarity.

**When they help**

- **Incremental augmentation by tools**:
  - Source generators that add members based on attributes or conventions.
  - “Contract + generated helpers” patterns where you keep the interface readable.

**Pitfall**

- Interface changes are breaking changes for implementers. Partial doesn’t change that—it can just make the change harder to notice in code review.

**Example: partial interface used for generated members**

```csharp
namespace Demo;

public partial interface IHasDiagnostics
{
    string ComponentName { get; }
}

// Another file (potentially generated)
public partial interface IHasDiagnostics
{
    // A generator could add this signature conditionally.
    string Describe();
}
```

Mentor note:

- If you need “optional capabilities”, prefer **separate interfaces** rather than growing one interface across partial files.

---

### 3) **Modern guidance**

**Keep one “owner” file**

- Maintain one file that clearly communicates:
  - **What the type is**
  - **What its invariants are**
  - **What the supported construction paths are**

Everything else should feel additive—not essential to understand the type.

**Isolate generated code**

- Put generated partial parts under a clear folder (and keep them out of manual edits).
- Ensure generated files are easy to locate (naming conventions and consistent placement matter more than cleverness).

**Keep the public surface obvious**

- Avoid “surprise” public members hidden in secondary partial files.
- If you must add public members via generation, prefer making them obviously generated (naming/attributes) and document the contract at the owner file.

Performance note:

- `partial` is a compiler feature; it doesn’t directly affect runtime performance. The performance risks are **indirect**: hidden size/copy costs (structs), hidden allocations (helpers), and hidden static initialization (see [3.3](<../3. Static classes/3.3. Static initialization and shared state.md>) plus the deep static-init reference in `Fields`).
