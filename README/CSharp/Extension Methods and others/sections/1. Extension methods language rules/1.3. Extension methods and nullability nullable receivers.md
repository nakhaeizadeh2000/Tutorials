## 1.3. Extension methods and nullability (nullable receivers, annotations, and honest APIs)

1. **Nullable reference context** (what callers and implementers should assume about the receiver)
2. **Patterns** (guarding inside extensions; “fluent” chains vs surprise `NullReferenceException`)
3. **API hygiene** (prefer clarity over cute one-liners when null is plausible)

---

### 1. **Nullable reference context**

**Definition**: In a nullable-enabled project (`<Nullable>enable</Nullable>`), every extension method has a **nullability contract** for its receiver and parameters. Because extensions are **static methods** (see section `1.1`), the runtime does **not** enforce any instance-method “non-null receiver” guarantee: a caller can invoke an extension with a `null` receiver unless the call site is proven non-null by flow analysis.

**What the caller should assume**

- If the receiver is declared `this string value` (non-nullable), then:
  - **Intent**: the method expects a non-null receiver.
  - **Reality**: it can still be passed `null` at runtime (e.g., via `!`, via `dynamic`, via nulls coming from legacy code); the method should fail fast or guard if it’s a public API.
- If the receiver is declared `this string? value` (nullable), then:
  - **Intent**: the method accepts null and should document what it does (return default? throw? no-op?).

**What the implementer should assume**

- Treat the receiver like any other parameter:
  - **Non-nullable receiver**: validate for public APIs when `null` would be a bug that should be diagnosed early.
  - **Nullable receiver**: implement null behavior deliberately and keep it consistent across overloads.

**Minimal example: non-null vs nullable receiver**

```csharp
namespace Demo;

public static class StringExtensions
{
    // Contract: caller should pass non-null.
    public static bool HasText(this string value)
        => value.Length != 0 && !string.IsNullOrWhiteSpace(value);

    // Contract: caller may pass null; the method handles it.
    public static bool HasTextSafe(this string? value)
        => !string.IsNullOrWhiteSpace(value);
}

public static class Program
{
    public static void Main()
    {
        string? maybe = null;
        Console.WriteLine(maybe.HasTextSafe()); // false

        // The next line compiles only if flow analysis thinks it’s non-null,
        // or you suppress with ! (which makes potential runtime NRE your responsibility).
        // Console.WriteLine(maybe!.HasText());
    }
}
```

**Good to know**

- Nullable annotations are **compile-time tooling**, not runtime checks. They are still extremely valuable because:
  - they shape IntelliSense,
  - they drive analyzer warnings,
  - and they prevent large classes of bugs during refactors.

**Performance note**

- A null-check is a single branch; don’t avoid it for “performance” in public APIs. If you truly need a zero-branch hot path, make that method `internal`/private, validate at boundaries, and keep the hot path clean.

### 2. **Patterns**

This section is about keeping extension methods **honest and predictable** around nulls. The main trade-off is between:

- **Fluent style** (reads nicely), and
- **Safety/clarity** (null behavior explicit and consistent).

#### Pattern A: fail fast for “should never be null”

Use when `null` indicates a programming bug and you want fast diagnosis.

```csharp
public static class GuardedExtensions
{
    public static ReadOnlySpan<char> AsSpanNonNull(this string value)
    {
        ArgumentNullException.ThrowIfNull(value);
        return value.AsSpan();
    }
}
```

**Why this is mentor-approved**

- The exception type is correct and searchable.
- You preserve a clean contract: receiver is non-nullable and enforced.

#### Pattern B: null-tolerant helpers (return default / identity)

Use when null is part of expected data flow (parsing layers, optional inputs).

```csharp
public static class NullTolerantExtensions
{
    // Identity for null: return empty string.
    public static string OrEmpty(this string? value) => value ?? string.Empty;

    // Identity for null: return the input sequence (or empty).
    public static IEnumerable<T> OrEmpty<T>(this IEnumerable<T>? source)
        => source ?? Array.Empty<T>();
}
```

**Pitfall**: returning `Array.Empty<T>()` is great, but be careful not to “hide” bugs where `null` indicates a broken invariant. Use this pattern intentionally, not as a reflex.

#### Pattern C: “Try”-style to avoid exceptions and clarify failure

For operations that can legitimately fail due to data (not programmer error), prefer a `TryXxx` pattern over exceptions or null returns.

```csharp
public static class ParsingExtensions
{
    public static bool TryParseInt32(this string? text, out int value)
        => int.TryParse(text, out value);
}
```

#### Pattern D: fluent chaining without surprise NREs

If your extension is meant to be used in chains, either:

- make the receiver nullable and keep it null-tolerant, or
- keep it non-nullable and fail fast.

Avoid “half-safe” methods that sometimes dereference and sometimes don’t.

**Example: chain-friendly null-tolerant**

```csharp
public static class ChainExtensions
{
    public static string? TrimOrNull(this string? value)
        => value is null ? null : value.Trim();
}

var result = ((string?)null).TrimOrNull(); // null, not NRE
```

**Common mistake**: implementing `TrimOrNull(this string value)` and assuming callers won’t pass null “because it’s an instance call”. Extensions don’t get that guarantee.

**Performance note**

- For `IEnumerable<T>`-based fluent chains, null-tolerance can unintentionally allocate or mask expensive enumerations. If you’re designing high-performance pipelines, consider `Span<T>`/`ReadOnlySpan<T>` (see section `3.2`) and keep null out of the hot path by validating earlier.

### 3. **API hygiene**

**Goal**: make nullability behavior obvious at the call site, consistent across overloads, and robust during refactors.

**Mentor checklist**

- **Choose one null strategy per method**:
  - Throw (`ArgumentNullException`) for “programmer error”.
  - Return default/identity for “expected optional input”.
  - `Try...` for “data might be invalid”.
  - Do **not** mix these behaviors in overload sets.
- **Annotate intentionally**:
  - Use `this T?` only when you truly support null.
  - Keep return nullability truthful: don’t return `string` if you can return `null`.
- **Name things so null behavior is obvious**:
  - `OrEmpty`, `OrDefault`, `TrimOrNull`, `ToXxxOrNull`, `TryToXxx`.
- **Avoid “cute” one-liners hiding semantics**:
  - `x?.Foo().Bar()` can be fine, but if you publish an extension API, prefer **named methods** that communicate intent.

**Legacy/deprecated pattern to avoid**

- Returning `null` to indicate failure *without* encoding it in the name or type.
  - In modern C#, prefer `TryXxx`, `OneOf`-style result types, or throwing when it’s truly exceptional.

**Good to know (interop boundaries)**

- At boundaries with `dynamic`, reflection, COM, or older code that doesn’t use nullable annotations, treat nullability warnings as “best effort”. Validate aggressively at boundaries; keep your core domain strict.
