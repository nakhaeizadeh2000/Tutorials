## 9.1. Interview Q&A: concepts, resolution rules, and performance trade-offs

1. **How are extension methods implemented at the IL level?** (static method + attribute; receiver becomes argument)
2. **Why can an instance method “replace” an extension without changing call sites?** (binding precedence; shadowing story)
3. **When would you choose `var` vs an explicit type?** (readability, obviousness, numeric literals, API edges)
4. **What does `dynamic` defer until runtime?** (member resolution; contrast with compile-time typing)
5. **Nested class vs file-local type—why pick one?** (encapsulation, cohesion, discoverability, team conventions)
6. **How do extensions interact with trimming/AOT?** (reflection/discovery hazards; explicit calling patterns)
7. **CPU vs allocation trade-offs** (static calls vs interface dispatch; `dynamic` call sites; closure allocations)

---

### 1. **How are extension methods implemented at the IL level?**

**What interviewers want**: You know it’s **syntax sugar**. The type is not modified; the call becomes a static call.

- **Answer**: Extension methods compile to **static methods** on a static container class; the receiver becomes the **first parameter** (`this` parameter). The call `x.M()` becomes `Extensions.M(x)`.
- **Where to study deeply**: See section `1.1` (this is the canonical deep reference).

### 2. **Why can an instance method “replace” an extension without changing call sites?**

**What interviewers want**: You understand **binding precedence** and **versioning hazards**.

- **Answer**: Instance members are considered before extensions; if a new instance member appears with a compatible signature, it **shadows** the extension for the same call shape.
- **Where to study deeply**: See section `1.2` (precedence) and `1.4` (versioning/evolution hazards).

### 3. **When would you choose `var` vs an explicit type?**

**What interviewers want**: You can balance **readability** with **refactoring safety** and avoid common inference traps.

- **Answer**: Use `var` when the type is obvious from the right-hand side and the variable name carries meaning; be explicit at API boundaries and in ref-heavy/low-level code where safety review matters.
- **Where to study deeply**: See section `4.2` (style/trade-offs) and `4.4` (ref safety).

### 4. **What does `dynamic` defer until runtime?**

**What interviewers want**: You understand it’s not “magical duck typing”; it’s runtime binding with tooling trade-offs.

- **Answer**: Member resolution (method/prop/operator binding) happens at runtime via the DLR; you lose compile-time checking and many analyzer guarantees.
- **Where to study deeply**: See section `5.1` (semantics) and `5.4` (tooling/refactoring risks).

### 5. **Nested class vs file-local type—why pick one?**

**What interviewers want**: You can articulate **encapsulation** and **coupling/lifetime** impacts.

- **Answer**: Use nested types when the type is conceptually owned by the outer type and may need access to it (careful: instance nesting can capture outer instance and extend lifetimes). Use file-local types to hide implementation details at file scope without adding coupling to the outer type.
- **Where to study deeply**: See section `6.2` (static vs instance nesting) and `6.4` (file-local vs nested).

### 6. **How do extensions interact with trimming/AOT?**

**What interviewers want**: You know “reflection scanning for extensions” is fragile under modern publish modes.

- **Answer**: Extension methods themselves are fine, but reflection-based discovery patterns can break under trimming/NativeAOT unless you annotate and preserve metadata; prefer explicit calls or source generation.
- **Where to study deeply**: See section `3.3`.

### 7. **CPU vs allocation trade-offs**

**What interviewers want**: You can explain why micro-costs often lose to allocations, and when dispatch cost matters.

- **Answer**: Extensions are static calls and often inline well; interface/virtual dispatch can be more expensive but usually isn’t the bottleneck. Allocations (closures, iterator state machines, LINQ chains) often dominate.
- **Where to study deeply**: See section `3.1` (JIT/inlining), `3.2` (allocations/closures), `5.3` (`dynamic` CPU/alloc costs), and `6.3` (compiler-generated state machines/closures).
