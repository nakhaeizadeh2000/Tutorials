## 6.4. Modern related features (file-local types) and how they differ from nesting

1. **File-local types (C# 11)** (hide implementation details at file scope without nesting)
2. **Choose nesting vs file-local** (team conventions; testability; discoverability)
3. **Overlap guardrail** (don’t duplicate “implementation hiding” lessons across multiple mechanisms unnecessarily)

---

### 1. **File-local types (C# 11)**

**Definition**: A *file-local type* is declared with the `file` modifier and is only accessible **within the same source file**. This is a modern alternative to “hide it by nesting” when the helper type doesn’t actually need a relationship to the outer type.

**Example (runnable)**:

```csharp
namespace Demo;

public static class EmailParser
{
    public static bool TryParse(string input, out string user, out string domain)
        => Email.TryParse(input, out user, out domain);
}

// File-local helper: invisible to other files in the project.
file static class Email
{
    public static bool TryParse(string input, out string user, out string domain)
    {
        user = domain = string.Empty;
        if (string.IsNullOrWhiteSpace(input)) return false;

        var at = input.IndexOf('@');
        if (at <= 0 || at >= input.Length - 1) return false;

        user = input[..at];
        domain = input[(at + 1)..];
        return true;
    }
}
```

**When to use**

- You want **encapsulation** without implying an object relationship.
- You want to hide a helper type used by multiple top-level types in the same file.
- You want to avoid inflating the public/internal surface of a namespace while keeping code readable.

**Trade-offs**

- **Pros**: very strong encapsulation boundary; reduces “API surface creep”; avoids IntelliSense noise.
- **Cons**: file-based organization becomes more important. Overusing file-local types can lead to “mega-files”.

**Common mistakes**

- Treating file-local types as a license to put unrelated types into one file. Use this for cohesive implementation clusters, not as a dumping ground.

---

### 2. **Choose nesting vs file-local**

**Key difference**:

- **Nested type**: expresses a *logical relationship* (“this helper is conceptually part of the outer type”) and can use outer generic parameters and access outer private members (depending on accessibility and whether it’s within the same outer type).
- **File-local type**: expresses *visibility only* (“this helper is an implementation detail in this file”), without suggesting a semantic tie to one outer type.

**Mentor guidance**

- Prefer **file-local** when you’re using nesting only for hiding.
- Prefer **nesting** when the inner type:
  - strongly belongs to the outer type conceptually (e.g., `Enumerator`, `Builder`, `Options`, `Comparer`),
  - benefits from being grouped under the outer type name for readability,
  - or must be closely coupled to the outer type’s internal state.

**Testability note**

- Private nested and file-local types are intentionally hard to test directly. Prefer testing through the public surface. If you feel forced to test the helper type directly, it’s a sign the abstraction boundary may be wrong.

---

### 3. **Overlap guardrail**

Encapsulation tools you can choose from include:

- **private nested types**
- **internal types** (assembly boundary)
- **file-local types** (file boundary)

**Mentor rule**: pick the smallest visibility boundary that still keeps code understandable. Don’t use *multiple* hiding mechanisms for the same intent (e.g., file-local + private nested) unless there is a concrete reason.

**Performance note**

- The choice is mostly about readability and API surface. Performance differences are typically negligible compared to algorithmic choices and allocations.
