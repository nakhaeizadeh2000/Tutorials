## 4.3. Target-typed `new` (`new()`) and constructor inference

1. **When `new()` improves signal-to-noise** (repeated type names on the left already carry meaning)
2. **When it hurts** (complex initializations where the constructed type should be visible)
3. **Modern style** (pair with clear variable names—names carry more weight when types are elided)

---

### 1. **When `new()` improves signal-to-noise**

**Definition**: *Target-typed `new`* lets the compiler infer the constructed type from the **target type** (left-hand side, return type, parameter type, etc.). It reduces repetition where the type is already obvious.

**Great uses**:

- **Local variables with explicit type**:

```csharp
Dictionary<string, int> counts = new(StringComparer.Ordinal);
```

- **Field/property initializers**:

```csharp
private readonly List<string> _names = new();
```

- **Object/collection expressions where the target type is explicit**:

```csharp
ReadOnlyMemory<byte> payload = new byte[] { 1, 2, 3 };
```

**Mentor note**:

- Use it when the *type is already carrying meaning*. If the type is the important information, don’t hide it.

**Performance note**:

- Target-typed `new` is syntax only; it does not change allocations or runtime behavior. Pick it for readability.

---

### 2. **When it hurts**

`new()` becomes harmful when it reduces clarity at the exact place where the reader most needs the type.

**Avoid or reconsider when**:

- The target type is **not visually close** (e.g., returned from a long method or assigned through multiple steps).
- The constructor choice is subtle (overloads, options, comparers).
- The variable name does not carry the missing meaning.

**Example: too implicit**

```csharp
var result = Build(); // What is Build() returning? How expensive is it?
```

Sometimes the *right fix* is not “don’t use `new()`”, but “improve the API surface”:

- Return a clearly named type.
- Make factory methods explicit.
- Use explicit types at the declaration site if it’s a boundary.

**Common mistake**:

- Combining `var` + `new()` in a way that hides the type entirely. This is legal only when the compiler can infer the type, but it can be miserable to read:

```csharp
var x = new(); // not legal (no target type)
```

```csharp
SomeType x = new(); // legal, but might hide which SomeType in generic-heavy code
```

---

### 3. **Modern style**

**Mentor default**:

- Prefer `new()` when the **type is repeated** and adds no extra information.
- Prefer explicit construction when **the constructed type or constructor choice is significant**.

**Guidelines that keep codebases consistent**

- **Public API edges**: be explicit. Your callers shouldn’t have to “hover” to learn types.
- **Generic-heavy code**: be cautious. With `Outer<T>.Inner<U>`, explicit types can prevent “type soup” confusion.
- **Prefer descriptive names** when you elide types:

```csharp
Dictionary<string, int> userIdToCount = new();
```

**Good to know**

- Target-typed `new` complements `var` but is not a replacement for good naming and clear boundaries. Treat it as a readability tool, not a “modernity badge”.
