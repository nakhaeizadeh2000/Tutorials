## 3.2. Allocations, captures, and LINQ-like patterns

1. **Closures** (extensions that take `Func<>`/`Action<>` can allocate if they capture)
2. **Enumerable-heavy chains** (often allocation-heavy; `Span<T>`/`ReadOnlySpan<T>` alternatives where appropriate)
3. **`params` and modern overloads** (`params Span<T>` / `params ReadOnlySpan<T>` where available—reduce array allocations)

---

### 1. **Closures**

**Definition**: A *closure* is the compiler-generated object that stores captured variables for a lambda/local function. When an extension method accepts a delegate and you pass a **capturing** lambda, you often allocate:

- a delegate instance, and
- a closure object (aka “display class”) holding the captured state.

This is a common performance footgun in “fluent” extension APIs.

#### Example: capturing vs non-capturing

```csharp
public static class EnumerableExtensions
{
    public static int CountWhere<T>(this IEnumerable<T> source, Func<T, bool> predicate)
    {
        ArgumentNullException.ThrowIfNull(source);
        ArgumentNullException.ThrowIfNull(predicate);

        var count = 0;
        foreach (var item in source)
        {
            if (predicate(item))
                count++;
        }
        return count;
    }
}

var xs = Enumerable.Range(0, 10);

// Capturing: allocates a closure (captures 'threshold').
var threshold = 5;
var a = xs.CountWhere(x => x > threshold);

// Non-capturing: no closure allocation (still a delegate instance).
var b = xs.CountWhere(static x => x > 5);
```

**Mentor guidance**:

- Prefer `static` lambdas when you can. If the compiler complains, you are capturing something—decide if that allocation is acceptable.
- Keep delegate-taking extensions off hot paths unless they’re designed for performance (e.g., `Span<T>`-based loops).
- Avoid “cute” combinators that encourage lots of tiny capturing lambdas; they look elegant and benchmark poorly.

**Performance note**:

- Closure allocations add GC pressure. In server code under load, this can translate to higher CPU and more frequent Gen0 collections.

---

### 2. **Enumerable-heavy chains**

**Definition**: `IEnumerable<T>` pipelines (LINQ-style) are *lazy*, which is great for composability, but often imply:

- allocations of enumerators/iterators,
- virtual/interface dispatch through `IEnumerator<T>`,
- poorer inlining opportunities,
- repeated passes (if you enumerate multiple times), and
- hidden work due to deferred execution.

Extensions can make these chains “look free” while they’re doing meaningful work.

#### What to do instead (when performance matters)

- Use `for` loops on arrays/`List<T>` when you’re on a hot path.
- Use `Span<T>` / `ReadOnlySpan<T>` to express “contiguous memory” operations without allocations.
- Consider returning materialized results (`ToArray`, `ToList`) explicitly when you need a stable snapshot; don’t re-enumerate.

#### Example: a span-based extension vs IEnumerable

```csharp
public static class SpanExtensions
{
    public static int CountWhere(this ReadOnlySpan<int> values, Func<int, bool> predicate)
    {
        ArgumentNullException.ThrowIfNull(predicate);

        var count = 0;
        for (var i = 0; i < values.Length; i++)
        {
            if (predicate(values[i]))
                count++;
        }
        return count;
    }
}

int[] data = [1, 2, 3, 4, 5, 6];
var count = data.AsSpan().CountWhere(static x => (x & 1) == 0);
```

**Trade-offs**:

- `Span<T>` is stack-only and cannot be stored on the heap; it’s excellent for performance but affects API shapes.
- Don’t contort APIs into spans prematurely. Use spans when you’ve identified a hot path or you’re building a low-level library.

**Common mistakes**:

- Returning `IEnumerable<T>` from extensions that *actually* do expensive work repeatedly (because the caller enumerates multiple times).
- Using `IEnumerable<T>` extensions in inner loops and assuming they’re “just syntax”.

---

### 3. **`params` and modern overloads**

**Definition**: `params` usually means “the compiler creates an array at the call site” when you pass multiple arguments. That’s a real allocation in many cases.

#### Example: `params` allocation

```csharp
public static class LoggingExtensions
{
    public static string JoinNonEmpty(this string separator, params string?[] parts)
        => string.Join(separator, parts.Where(static p => !string.IsNullOrEmpty(p)));
}

var s = ", ".JoinNonEmpty("a", null, "b"); // creates a new string?[] array
```

**Mentor guidance**:

- Keep `params` for APIs where ergonomics matter more than micro-allocations (logging, tests, glue code).
- For high-performance APIs, prefer overloads that accept:
  - `ReadOnlySpan<T>` for contiguous inputs, or
  - `IReadOnlyList<T>` / `IEnumerable<T>` when callers already have a collection (with clear perf expectations).

**Good to know (modern patterns)**:

- .NET continues to add APIs that accept spans to avoid allocations. When you design your own performance-sensitive extensions, consider a span overload.
- Don’t overfit: a span overload is only useful if your consumers naturally have spans/arrays and you’re optimizing a real hotspot.
