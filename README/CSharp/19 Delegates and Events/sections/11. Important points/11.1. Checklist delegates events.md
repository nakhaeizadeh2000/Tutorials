## 11.1. Checklist: delegates and events you should not forget

1. **Prefer events for fan-out notifications; avoid multicast return-value APIs**
2. **Prefer method groups or `static` lambdas to avoid captures**
3. **Always treat event subscriptions as a lifetime/ownership concern**
4. **Never block or do heavy work in event handlers—offload intentionally**
5. **Use expression trees only when you truly need inspection/translation**

### 1) Prefer events for fan-out notifications; avoid multicast return-value APIs
If your goal is “notify many listeners”, model it as **an event** (or an explicit observer/stream abstraction), not as a `Func<T>` you combine.

- **Why**: multicast delegates with return values only keep the **last** result, which is misleading and fragile.
- **Instead**: make aggregation explicit (e.g., return a list of results) or invert control (publisher doesn’t ask listeners for data; it publishes facts).

See `3.1. Multicast delegates` and `5.1. What an event is` for the full semantics.

### 2) Prefer method groups or `static` lambdas to avoid captures
Captures/closures are the most common source of unexpected allocations and lifetime extension.

- **Do**: `button.Clicked += OnClicked;`
- **Do**: `list.ForEach(static x => Console.WriteLine(x));`
- **Avoid**: `button.Clicked += (_, _) => Console.WriteLine(this.State);` (captures `this`)

Full treatment: [7.2](<../7. Anonymous methods and lambdas/7.2. Captures closures allocations.md>) (captures/closures) and [7.4](<../7. Anonymous methods and lambdas/7.4. static lambdas prevent captures.md>) (`static` lambdas).

### 3) Always treat event subscriptions as a lifetime/ownership concern
Events hold **strong references** from publisher → subscriber. If the publisher outlives the subscriber (or vice versa), you can leak memory and keep objects alive unexpectedly.

- **Do**: unsubscribe deterministically (often via `IDisposable` subscription tokens).
- **Avoid**: “global event bus” patterns without explicit lifetimes.

Full treatment: `10.2. Events and memory leaks`.

### 4) Never block or do heavy work in event handlers—offload intentionally
Event handlers run on the raiser’s thread. Blocking there:
- increases latency,
- risks deadlocks (especially with synchronization contexts in frontend UI frameworks),
- starves the thread pool if you block worker threads.

Do one of:
- keep handler quick and schedule work (e.g., queue to a channel/background worker)
- design the event to carry enough data so handlers can be pure/fast

Full treatment: `10.3. Thread-safety and reentrancy`.

### 5) Use expression trees only when you truly need inspection/translation
Expression trees are **code-as-data** and come with real costs:
- allocations for the node graph,
- compile/interpret overhead,
- harder trimming/AOT behavior.

Use them for LINQ providers/ORM translation/rules engines. Otherwise prefer delegates (`Func<>`/`Action<>`) for execution.

Full treatment: [8.1](<../8. Expression trees/8.1. Expression vs Func mental model.md>) and [8.2](<../8. Expression trees/8.2. Building composing expression trees caching.md>).
