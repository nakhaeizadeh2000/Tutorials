## 13.1. Boundaries: what is covered elsewhere in this repo

1. **General overload resolution and method design** lives in `Methods` (this domain focuses on delegate-specific resolution and callback pitfalls)
2. **Switch statements/expressions (intro level)** live in `CSharp language basics/5.3` (here: switch-as-strategy for delegates)
3. **Async/await and callback-based asynchrony** live in `Cuncurrent & Parallel` (here: events/delegates as a callback mechanism, not the async model itself)
4. **Encapsulation and invariants (OOP big picture)** live in `CSharp Basic Object Oriented Programming` (here: event as an encapsulation boundary)
5. **Allocation theory and GC deep dive** live in `Fundamental Theories` and `GC and Destructors and IDisposable` (here: practical allocation sources from closures/events)

### 1) Overload resolution and method design
This domain covers **delegate-specific** overload resolution pitfalls: method groups, lambdas, variance interactions, and ambiguous “delegate-shaped overload” APIs.

If you need the broad “how overload resolution works in C#” foundation, see the `Methods` domain. Here, refer to:
- `1.3. Method groups vs lambdas vs anonymous methods` for delegate-focused resolution rules
- `1.2. Delegate variance` for variance-driven surprises

### 2) Switch statements/expressions (intro level) vs switch-as-strategy
This tutorial assumes you already know switch basics. Here, [9.2](<../9. Expression-bodied and switch expressions/9.2. Switch expressions mapping to delegates.md>) focuses on using switch expressions to **select callback strategies** while avoiding:
- per-call lambda allocations
- capture-related hidden allocations
- brittle default branches (correctness + nullability)

See `9.2. Switch expressions mapping to delegates` as the single deep reference inside this domain.

### 3) Async/await model vs “delegates as callbacks”
Delegates and events are often used as *callback mechanisms*, but they are **not** the async model.

This domain stresses:
- why `async void` event handlers are dangerous (exception semantics, lifetime)
- how to offload work intentionally without blocking publishers
- thread-safety + reentrancy hazards when raising events from background threads

For the complete async/await and concurrency model, see the `Cuncurrent & Parallel` domain. Within this domain, the deep coverage is in `10.3. Thread-safety and reentrancy with events`.

### 4) OOP encapsulation and invariants vs event encapsulation boundary
Events are an **API boundary**: they expose subscription but restrict invocation list mutation.

If you need OOP fundamentals (encapsulation, invariants, ownership), see `CSharp Basic Object Oriented Programming`.
For the event-specific boundary, see:
- `5.1. What an event is`
- [6.1](<../6. Implementing events/6.1. Declaring events explicit backing field.md>) / [6.3](<../6. Implementing events/6.3. Custom event accessors add remove.md>) for raising patterns, reentrancy, and correctness traps

### 5) GC theory vs practical allocation sources from delegates/events
This domain is pragmatic:
- closures/captures ([7.2](<../7. Anonymous methods and lambdas/7.2. Captures closures allocations.md>), [7.4](<../7. Anonymous methods and lambdas/7.4. static lambdas prevent captures.md>))
- invocation list inspection costs ([3.2](<../3. Multicast delegates/3.2. Invocation list inspection advanced.md>))
- subscription lifetime leaks ([10.2](<../10. Performance memory scalability/10.2. Events memory leaks subscription lifetimes.md>))

For GC fundamentals and deep theory, see the referenced GC/IDisposable domains.

**Mentor note**
The reason these boundaries matter is maintainability: duplicating deep explanations across domains makes the tutorial inconsistent over time. This delegates/events domain aims to be the single source for delegates/events-specific mechanics and pitfalls, while relying on the other domains for language-runtime and concurrency fundamentals.
