## 9.2. Switch expressions: mapping inputs to callbacks and strategies

1. **Pattern** (choose a strategy `Func<>`/`Action<>` based on input)
2. **Correctness** (exhaustiveness; default case; nullability)
3. **Performance** (avoid allocating lambdas repeatedly; cache strategy delegates)

### 1) Pattern: switch-as-strategy (choose a callback once, then execute)
Switch expressions are often the cleanest way to map an input to a **strategy delegate**:
- Readable: intent is “select behavior”
- Testable: you can unit test the mapping
- Extensible: adding a new case is obvious

This is especially useful when you want to keep the call site simple and avoid scattering `if`/`switch` logic across the codebase.

```csharp
using System;

enum PricingMode { Retail, Wholesale, Vip }

static Func<decimal, decimal> GetPricer(PricingMode mode) => mode switch
{
    PricingMode.Retail => static price => price,
    PricingMode.Wholesale => static price => price * 0.9m,
    PricingMode.Vip => static price => price * 0.8m,
    _ => throw new ArgumentOutOfRangeException(nameof(mode))
};

var pricer = GetPricer(PricingMode.Wholesale);
Console.WriteLine(pricer(100m)); // 90
```

**Good to know**
- Prefer `static` lambdas for these strategies when feasible. It prevents accidental captures and makes allocation behavior predictable. See [7.4](<../7. Anonymous methods and lambdas/7.4. static lambdas prevent captures.md>) for the deep explanation of `static` lambdas.

### 2) Correctness: exhaustiveness, defaults, and nullability
#### Exhaustiveness
One of the best features of switch expressions is that they encourage **exhaustive** handling:
- For enums: include all named cases and keep `_ => throw ...` as a guard.
- For type patterns: ensure you cover all relevant derived types.

#### Defaults that hide bugs
Avoid defaulting to some “reasonable” strategy in library/business code unless it’s truly correct. Silent fallbacks often mask missing cases and turn into production incidents.

#### Nullability
If the input can be null (reference types), make the null-handling explicit:

```csharp
using System;

static Func<string, bool> GetValidator(string? mode) => mode switch
{
    null => throw new ArgumentNullException(nameof(mode)),
    "len>3" => static s => s.Length > 3,
    "nonempty" => static s => s.Length != 0,
    _ => throw new ArgumentException($"Unknown mode '{mode}'", nameof(mode))
};
```

### 3) Performance: caching and avoiding repeated allocations
The switch expression itself is typically cheap. The performance traps are:

- **Allocating a new capturing lambda each call** (closure allocations; see [7.2](<../7. Anonymous methods and lambdas/7.2. Captures closures allocations.md>))
- **Rebuilding strategy delegates repeatedly** when the mapping is stable

#### Cache stable strategies
If a mapping is fixed, cache delegates once:

```csharp
using System;
using System.Collections.Generic;

enum Mode { A, B }

static readonly IReadOnlyDictionary<Mode, Action> Actions = new Dictionary<Mode, Action>
{
    [Mode.A] = static () => Console.WriteLine("A"),
    [Mode.B] = static () => Console.WriteLine("B"),
};

static Action GetAction(Mode mode) =>
    Actions.TryGetValue(mode, out var a) ? a : throw new ArgumentOutOfRangeException(nameof(mode));
```

Trade-offs:
- **Pros**: stable allocations, fast lookups, clean call sites
- **Cons**: memory for the table; needs update when cases change

**Performance note**
- If you only have a few cases, a switch expression returning a cached static delegate is often faster and simpler than a dictionary.
- If this is on a hot path, measure. The fastest structure depends on case count, branch predictability, and call frequency.
