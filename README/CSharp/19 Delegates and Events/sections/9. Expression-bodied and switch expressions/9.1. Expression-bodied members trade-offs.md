## 9.1. Expression-bodied members: readability and debugging trade-offs

1. **Where they help** (tiny wrappers, pure computed properties, guard clauses)
2. **Where they hurt** (complex logic; debugging; hidden allocations in “one-liners”)
3. **Delegate relevance** (avoid hiding captures and allocations behind terse syntax)

### 1) Where they help
Expression-bodied members (`=>`) are a *syntax tool*, not a performance feature. They shine when the member is:

- **Pure and tiny** (no side effects; obvious)
- **A simple guard clause**
- **A small wrapper** around another call

Examples:

```csharp
using System;

public sealed class Clock(Func<DateTimeOffset> now)
{
    public DateTimeOffset Now => now(); // thin wrapper over injected delegate
}
```

```csharp
using System;

public static class Guard
{
    public static T NotNull<T>(T? value, string paramName) where T : class =>
        value ?? throw new ArgumentNullException(paramName);
}
```

**Good to know**
- Expression-bodied members work great with **dependency-injected delegates** (e.g., time providers, policies) because they keep the “call through” obvious.

### 2) Where they hurt
They become harmful when they compress *non-trivial logic* into a single line that is:

- Hard to step through in a debugger
- Easy to “hide” **allocations** (capturing lambdas) or **exceptions**
- Harder to review and maintain (a long `=>` expression tends to grow)

Prefer a block body if:
- You need multiple steps
- You need meaningful local names
- You need nuanced error handling
- You’re tempted to inline a multiline lambda or LINQ chain that allocates

**Performance note**
- The syntax itself doesn’t allocate. What allocates is what you *put inside*—especially capturing lambdas and iterator/lazy pipelines.
- If you place a capturing lambda inside an expression-bodied property, you can accidentally allocate on every call. The full closure/allocation explanation is in [7.2](<../7. Anonymous methods and lambdas/7.2. Captures closures allocations.md>) and [10.1](<../10. Performance memory scalability/10.1. Allocation sources captures delegate creation.md>).

### 3) Delegate relevance (the mentor warning)
Expression-bodied style often pairs with delegates because it makes callback-heavy code look clean:

```csharp
using System;

public sealed class Notifier(Action<string> sink)
{
    public void Notify(string message) => sink(message);
}
```

That’s good—*until* you start hiding policies and captures:

```csharp
using System;

public sealed class BadExample
{
    private readonly string prefix;
    public BadExample(string prefix) => this.prefix = prefix;

    // This allocates a closure each call (capturing 'this'), if used as a value factory repeatedly.
    public Func<string, string> Formatter => s => $"{prefix}{s}";
}
```

Mentor guidance:
- If you return delegates from properties/methods, be explicit about whether they capture state.
- Prefer **method groups** or **`static` lambdas** for non-capturing callbacks (see [1.3](<../1. Delegates fundamentals/1.3. Method groups vs lambdas vs anonymous methods.md>) and [7.4](<../7. Anonymous methods and lambdas/7.4. static lambdas prevent captures.md>)).
