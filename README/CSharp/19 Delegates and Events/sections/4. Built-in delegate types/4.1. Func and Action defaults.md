## 4.1. `Func<>` and `Action<>`: the defaults for callbacks

1. **Choosing `Func` vs `Action`** (return values and intent)
2. **Nullability** (what `Func<T?>` vs `Func<T>` communicates)
3. **Performance tips** (prefer method groups; avoid captures; consider caching)

### 1) Choosing `Func` vs `Action` (intent matters)
In modern C#/.NET, **prefer the built-in delegate types** for most callback APIs:

- **`Action<...>`**: “do something” (no return value). Great for notifications and side-effect callbacks.
- **`Func<..., TResult>`**: “compute something” (returns a value). Great for policies, mapping, factories, and strategies.

Mentor framing:
- If the callback is **expected to fail** or “must succeed” for correctness, let exceptions bubble (don’t swallow).
- If it’s a **fan-out notification**, that’s usually an **event**, not a `Func` (see [5.1](<../5. Events fundamentals/5.1. What an event is.md>), [3.1](<../3. Multicast delegates/3.1. Multicast combine remove return values.md>)).

Minimal examples:

```csharp
using System;

static string Normalize(string s) => s.Trim().ToUpperInvariant();

static string Transform(string input, Func<string, string> transform) => transform(input);
static void Notify(string message, Action<string>? onMessage) => onMessage?.Invoke(message);

Console.WriteLine(Transform("  hi  ", Normalize));
Notify("done", static m => Console.WriteLine(m));
```

**Good to know**
- `Func<>`/`Action<>` support variance, which often improves ergonomics in generic APIs. See [1.2](<../1. Delegates fundamentals/1.2. Delegate variance covariance contravariance.md>) for the deep variance treatment.

### 2) Nullability: make the contract explicit
With nullable reference types enabled, your delegate types are part of the **API contract**:

- **Delegate variable nullability** answers: “is the callback optional?”
  - `Action? callback` means “may be missing”
  - `Action callback` means “must be provided”
- **Parameter/return nullability** answers: “may I pass/return null through this callback?”
  - `Func<string, string>` vs `Func<string, string?>`
  - `Action<string>` vs `Action<string?>`

Mentor guidance:
- Don’t “just use `?` everywhere”. If null is allowed, **justify it** and validate at boundaries.
- For public APIs, document:
  - Whether the callback can be null
  - Whether callback parameters can be null
  - Whether you may call the callback reentrantly or concurrently

### 3) Performance tips (CPU, allocations, thread-safety)
Delegates themselves are cheap, but a few patterns are performance-critical:

#### Avoid captures unless you mean it
Capturing lambdas allocate a closure object and extend lifetimes. Prefer:
- method groups, or
- `static` lambdas when no capture is required

See [7.2](<../7. Anonymous methods and lambdas/7.2. Captures closures allocations.md>) and [7.4](<../7. Anonymous methods and lambdas/7.4. static lambdas prevent captures.md>) for the deep closure + `static` lambda treatment.

#### Avoid per-iteration delegate creation in hot loops
If you register callbacks repeatedly (especially event subscriptions), cache the delegate:

```csharp
using System;

sealed class Publisher
{
    public event Action? Tick;
    public void Raise() => Tick?.Invoke();
}

sealed class Subscriber
{
    private readonly Action _onTick;
    public Subscriber() => _onTick = static () => { };

    public void Subscribe(Publisher p) => p.Tick += _onTick;
    public void Unsubscribe(Publisher p) => p.Tick -= _onTick;
}
```

#### Prefer clear sync/async shapes
If a callback is async, do **not** accept `Action` and “let callers use `async void`”.
Prefer:
- `Func<ValueTask>` (or `Func<Task>`) for asynchronous callbacks
- A clear “fire and forget” policy only when you truly want that behavior

For event-specific threading/reentrancy hazards, see [10.3](<../10. Performance memory scalability/10.3. Thread-safety reentrancy events.md>).

**Performance note**
- `Func<>`/`Action<>` are delegates; all delegate performance guidance applies (indirection, inlining, allocations from closures, invocation list churn). See [10.1](<../10. Performance memory scalability/10.1. Allocation sources captures delegate creation.md>) for the deep allocation sources treatment.
