## 4.2. `Predicate<T>`: legacy vs readability vs modern guidance

1. **Where it appears** (`List<T>.Find*`, `RemoveAll`, etc.)
2. **When to keep it** (API consistency with BCL; clarity at call sites)
3. **When to prefer `Func<T, bool>`** (general callback APIs; composability)

### 1) Where it appears
`Predicate<T>` is a built-in delegate type:

```csharp
public delegate bool Predicate<in T>(T obj);
```

It appears mostly in older or collection-specific APIs in the BCL, especially `List<T>`:
- `List<T>.Find(Predicate<T>)`
- `List<T>.FindAll(Predicate<T>)`
- `List<T>.Exists(Predicate<T>)`
- `List<T>.RemoveAll(Predicate<T>)`
- `Array.Find<T>(T[] array, Predicate<T> match)`

Example:

```csharp
using System;
using System.Collections.Generic;

var list = new List<int> { 1, 2, 3, 4, 5 };
var firstEven = list.Find(static x => (x & 1) == 0);
Console.WriteLine(firstEven); // 2
```

**Good to know**
- `Predicate<T>` is **contravariant** (`in T`), same safety rules as `Action<T>`.
- In practice, `Predicate<T>` is functionally equivalent to `Func<T, bool>` for most application code.

### 2) When to keep it
Keep `Predicate<T>` when:
- You are **calling an API that already expects it** (e.g., `List<T>.RemoveAll`), and you want minimal noise.
- You are designing an API that intentionally mirrors BCL patterns in a collection-like type and you want call sites to feel familiar.

Example: staying consistent with `List<T>`-style naming:

```csharp
public int RemoveAll(Predicate<T> match) { /* ... */ }
```

### 3) When to prefer `Func<T, bool>`
Prefer `Func<T, bool>` when:
- You are designing **general-purpose callback APIs** (pipelines, policies, validators, rules).
- You want better **composability** with LINQ and other higher-order APIs that standardize on `Func<...>`.
- You want to return/accept the callback as part of a larger algebra (e.g., pass to a combinator that already uses `Func<T, bool>`).

```csharp
using System;

static Func<T, bool> And<T>(Func<T, bool> left, Func<T, bool> right)
    => static x => throw new NotSupportedException("See note below");
```

The above illustrates an important point: naïve composition often forces captures if you close over `left`/`right`.
If composition is a real need, you typically:
- Accept the capture cost (usually fine), or
- Use structs/function objects in performance-critical scenarios, or
- Build expression trees (when you need translation), see section `8.x`.

**Mentor guidance**
- For **public APIs**, choose one and stick with it. Mixing `Predicate<T>` and `Func<T, bool>` across a library adds friction.
- For **internal code**, prefer `Func<T, bool>` unless you are directly feeding a BCL API that already wants `Predicate<T>`.

**Performance note**
- `Predicate<T>` vs `Func<T, bool>` is not a meaningful perf difference by itself; both are delegates.
- The real costs come from **captures/closures** and **allocation churn**. Prefer method groups or `static` lambdas where possible. For the deep closure treatment, see [7.2](<../7. Anonymous methods and lambdas/7.2. Captures closures allocations.md>) and [7.4](<../7. Anonymous methods and lambdas/7.4. static lambdas prevent captures.md>).
