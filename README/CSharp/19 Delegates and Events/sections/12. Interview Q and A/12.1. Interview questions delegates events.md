## 12.1. Common interview Q&A: delegates and events

1. **What’s the difference between a delegate and an event?**
2. **What is a multicast delegate and what are its return-value/exception semantics?**
3. **What is a closure and why can it allocate? How do `static` lambdas help?**
4. **Why do events cause memory leaks and how do you prevent them?**
5. **`Func` vs `Action` vs `Predicate` vs custom delegate—how do you choose?**
6. **Expression trees vs delegates—when do you need each?**
7. **Thread-safety and reentrancy: what can go wrong when raising events?**

### 1) What’s the difference between a delegate and an event?
**Short answer**: a **delegate** is a value you can invoke; an **event** is an **encapsulated subscription point** that restricts who can change the invocation list.

- **Delegate**:
  - Anyone holding it can `Invoke()` it.
  - Anyone holding it can overwrite it (`d = ...`) and can combine/remove.
- **Event**:
  - Outside code can only `+=` / `-=` (subscribe/unsubscribe).
  - Only the declaring type can raise it (invoke) and can decide how to store and dispatch it.

See `5.1. What an event is` for the full treatment.

### 2) What is a multicast delegate and what are its return-value/exception semantics?
- **Multicast**: a delegate with an invocation list (multiple method/target entries).
- **Return values**: only the **last** handler’s return value is observed. This is usually a design smell for fan-out notifications.
- **Exceptions**: by default, invocation stops at the first exception. If you need best-effort fan-out, you must isolate per-subscriber.

See [3.1](<../3. Multicast delegates/3.1. Multicast combine remove return values.md>) and [3.2](<../3. Multicast delegates/3.2. Invocation list inspection advanced.md>) for the deep explanation and isolation patterns (and their allocation trade-offs).

### 3) What is a closure and why can it allocate? How do `static` lambdas help?
- **Closure**: compiler-generated object that stores captured variables for a lambda/anonymous method.
- **Why it allocates**: captured state must live on the heap so the delegate can outlive the stack frame.
- **`static` lambda**: prevents capturing by construction, eliminating closure allocations and accidental lifetime extension.

See [7.2](<../7. Anonymous methods and lambdas/7.2. Captures closures allocations.md>) and [7.4](<../7. Anonymous methods and lambdas/7.4. static lambdas prevent captures.md>) for the full treatment and the hot-path patterns.

### 4) Why do events cause memory leaks and how do you prevent them?
- Subscribing to an event creates a **strong reference** from publisher → subscriber (via the invocation list).
- If publisher outlives subscriber and you never unsubscribe, subscriber stays alive → leak.

Prevention strategies (in order of preference):
- Deterministic unsubscribe tied to lifetime (`IDisposable`, scopes).
- Avoid “global” publishers that outlive everything unless you have explicit lifecycle management.
- Use weak-event patterns only when justified (more complexity, harder debugging).

See `10.2. Events and memory leaks` for production patterns.

### 5) `Func` vs `Action` vs `Predicate` vs custom delegate—how do you choose?
- Prefer `Action`/`Func` for internal code and general-purpose APIs.
- Use `Predicate<T>` when aligning with BCL APIs (`List<T>.Find`, `RemoveAll`) or for clarity in that specific context.
- Use a **custom delegate type** when you need:
  - domain-named callback in a public API,
  - attributes on the delegate type/parameters,
  - interop constraints or better discoverability.

See [4.1](<../4. Built-in delegate types/4.1. Func and Action defaults.md>), [4.2](<../4. Built-in delegate types/4.2. Predicate legacy vs Func.md>), and [2.1](<../2. Creating delegates/2.1. Creating custom delegate types.md>) for the detailed guidance.

### 6) Expression trees vs delegates—when do you need each?
- Use **delegate** when you want to execute code.
- Use **expression tree** when you need to **inspect/translate** code (ORMs, rule engines, query providers).

See [8.1](<../8. Expression trees/8.1. Expression vs Func mental model.md>) and [8.2](<../8. Expression trees/8.2. Building composing expression trees caching.md>) for cost model, caching, and AOT/trimming notes.

### 7) Thread-safety and reentrancy: what can go wrong when raising events?
- **Concurrency hazards**: subscribe/unsubscribe races, raising from background threads, handler ordering assumptions.
- **Reentrancy hazards**: handler calls back into publisher and mutates state or subscriptions mid-raise.
- **Thread pool hazards**: blocking work in handlers can starve the thread pool and collapse throughput.

See [10.3](<../10. Performance memory scalability/10.3. Thread-safety reentrancy events.md>) (deep) and [6.3](<../6. Implementing events/6.3. Custom event accessors add remove.md>) (custom accessors correctness) for production guidance.
