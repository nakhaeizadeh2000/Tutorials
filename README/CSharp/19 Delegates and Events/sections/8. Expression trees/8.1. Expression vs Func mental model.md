## 8.1. `Expression<TDelegate>` vs `Func<>`: what’s compiled, what’s inspected

1. **Use cases** (LINQ providers/ORMs, query translation, rules engines)
2. **Costs** (allocation-heavy graphs; compilation cost; caching requirements)
3. **Guidance** (keep expression APIs narrow; don’t expose expressions “because it’s cool”)

### 1) Use cases (when you need code-as-data)
Both delegates and expression trees represent “a piece of logic”, but they are used for different jobs:

- **Delegate (`Func<>`, `Action<>`)**: *code as execution* — you call it, it runs.
- **Expression tree (`Expression<TDelegate>`)**: *code as data* — you inspect/transform/translate it (often into SQL, Elastic queries, a rules engine graph, etc.).

Typical **legitimate** expression-tree scenarios:
- **LINQ providers** (EF Core, MongoDB LINQ, etc.): translate a predicate into a remote query.
- **Rule composition**: build a library of rules that can be combined and displayed.
- **Diagnostics**: show the user what rule/predicate is being applied.

If you don’t need inspection/translation, prefer a delegate. It’s simpler, faster to execute, and avoids heavy allocations.

```csharp
using System;
using System.Linq.Expressions;

// Code-as-execution
Func<int, bool> isAdult = static age => age >= 18;

// Code-as-data (inspectable)
Expression<Func<int, bool>> isAdultExpr = static age => age >= 18;

Console.WriteLine(isAdult(20));                 // True
Console.WriteLine(isAdultExpr.Body.NodeType);   // GreaterThanOrEqual
```

**Good to know**
- Whether a lambda becomes a `Func<>` or an `Expression<Func<...>>` is determined by the **target type**.
- Many APIs have overloads that accept either delegate or expression tree. Pick intentionally.

### 2) Costs (where the performance and memory go)
Expression trees are not “just delegates with syntax” — they are object graphs.

#### Costs you pay with `Expression<TDelegate>`
- **Allocations**: nodes (`BinaryExpression`, `MemberExpression`, `ConstantExpression`, ...) + parameter objects.
- **Compilation cost**: calling `expr.Compile()` can be expensive.
- **Trimming/AOT** considerations: expression compilation may require runtime codegen; in AOT contexts it can fall back to slower interpretation or be unsupported depending on environment and settings.

#### Costs you usually *avoid* with plain delegates
- No expression graph allocations.
- The JIT can sometimes inline through direct calls (less so through delegate calls, but still generally cheaper than expression compilation workflows).

**Performance note**
- If you accept expression trees and then immediately call `Compile()` on every invocation, you’ve paid the worst of both worlds. Prefer either:
  - accept a delegate, or
  - accept an expression and cache the compiled delegate (see [8.2](<./8.2. Building composing expression trees caching.md>)).

### 3) Guidance (API design and mentor rules)
#### Public API decision checklist
- **Do you need translation/inspection?** If no → accept `Func<>`/`Action<>`.
- **Do you need caller-side composability of predicates?** Maybe accept expressions, but keep them narrow and well-documented.
- **Do you need both?** Consider two overloads, but beware overload resolution ambiguity (see [1.3](<../1. Delegates fundamentals/1.3. Method groups vs lambdas vs anonymous methods.md>)).

#### Avoid “expression trees because it’s cool”
Expression trees increase:
- API complexity (what subset of C# is supported?)
- user confusion (why can’t I call arbitrary methods?)
- maintenance burden (parsing/visiting patterns)

If you need a rule DSL, sometimes it’s better to define your own explicit model rather than relying on “all of C# expressions”.

**Legacy/deprecated patterns**
- Avoid `Expression.Invoke` for remote translation scenarios: many providers cannot translate invocation and will throw at runtime or force client evaluation. Prefer rewriting by parameter substitution (covered in [8.2](<./8.2. Building composing expression trees caching.md>)).
