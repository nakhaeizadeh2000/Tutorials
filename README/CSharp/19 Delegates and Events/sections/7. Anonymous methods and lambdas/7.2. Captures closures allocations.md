## 7.2. Lambda captures and closures (the #1 performance and memory pitfall)

1. **What capture means** (extending lifetimes; heap allocations; hidden state machines)
2. **Common capture bugs** (loop variable capture, large object capture, capturing `this`)
3. **Modern best practices** (prefer method groups; use `static` lambdas when you don’t need captures)

### 1) What capture means (and why it can allocate)
A **capture** happens when a lambda (or anonymous method) uses variables that are **not parameters** of that lambda: locals, `this`, fields via `this`, etc.

When you capture, the compiler rewrites your code roughly like this:

- It creates a hidden **closure class** (a heap object) to store captured variables.
- It creates a delegate that points to an instance method on that closure object.
- The captured variables’ lifetimes extend to match the delegate’s lifetime (which can be *much longer* than the original scope).

This is a *correctness* feature, but it has consequences:

- **Allocations**: closure object (and sometimes extra delegate allocations).
- **GC pressure**: frequent captures in hot paths create lots of short-lived objects.
- **Unexpected lifetime retention**: a capture can keep large objects alive (including `this`).

Minimal example showing a capture:

```csharp
using System;

static Func<int> MakeCounter()
{
    var i = 0;
    return () => ++i; // captures i => closure object
}

var next = MakeCounter();
Console.WriteLine(next()); // 1
Console.WriteLine(next()); // 2
```

**Good to know**
- Captures are not “slow by default”, but they’re the most common *accidental* allocation in modern C# codebases.
- Capturing and **async/await** are different mechanisms. Async creates state machines; captures create closures. You can have both at once (and then you pay both costs).

### 2) Common capture bugs
#### Bug A: capturing `this` accidentally (memory leaks + unintended coupling)
This is the biggest “mentor warning” in event-driven code.

```csharp
using System;

sealed class Publisher
{
    public event Action? Tick;
    public void Raise() => Tick?.Invoke();
}

sealed class Subscriber
{
    private readonly string _name;
    public Subscriber(string name) => _name = name;

    public void Subscribe(Publisher p)
    {
        // Captures `this` (and therefore keeps Subscriber alive as long as Publisher lives)
        p.Tick += () => Console.WriteLine(_name);
    }
}
```

If `Publisher` outlives `Subscriber` and you don’t unsubscribe, you’ve likely created a leak.
See `10.2. Events and memory leaks` for the full lifecycle mitigation patterns.

#### Bug B: loop capture and “surprising values”
Modern C# fixed historical pitfalls with `foreach` loop variable capture, but **`for` loop locals** are still easy to get wrong when you capture *the same variable*.

```csharp
using System;
using System.Collections.Generic;

var actions = new List<Action>();
for (var i = 0; i < 3; i++)
{
    actions.Add(() => Console.WriteLine(i)); // captures i (single variable)
}

foreach (var a in actions) a();
// Often prints 3,3,3 (because i ends at 3).
```

Fix: create a copy inside the loop (or pass as a parameter to a static lambda):

```csharp
using System;
using System.Collections.Generic;

var actions = new List<Action>();
for (var i = 0; i < 3; i++)
{
    var copy = i;
    actions.Add(static () => { /* can't use copy here */ });
    actions[^1] = () => Console.WriteLine(copy); // capture copy (per-iteration variable)
}
```

Better: avoid capture entirely by passing state explicitly:

```csharp
using System;
using System.Collections.Generic;

var actions = new List<Action<int>>();
for (var i = 0; i < 3; i++)
{
    actions.Add(static x => Console.WriteLine(x)); // no capture
}

for (var i = 0; i < actions.Count; i++)
    actions[i](i);
```

#### Bug C: capturing large objects (retention and LOH surprises)
If you capture a large buffer, service client, or cache, you’re tying its lifetime to the delegate’s lifetime.
This can keep **Large Object Heap** allocations alive longer than intended and cause higher memory usage.

Mentor guidance:
- Avoid capturing large objects in lambdas stored long-term (events, caches, static fields).
- Prefer a **named method** on a type that owns the resource, and manage subscription/unsubscription deterministically.

### 3) Modern best practices (C# 15 era)
#### Prefer method groups or `static` lambdas when feasible
- Method groups are naturally non-capturing.
- `static` lambdas **cannot capture** by construction and will fail compilation if you accidentally reference locals/`this`.

```csharp
using System;

static int ParseOrDefault(string s) => int.TryParse(s, out var n) ? n : 0;

Func<string, int> f1 = ParseOrDefault;         // method group
Func<string, int> f2 = static s => ParseOrDefault(s); // static lambda (still non-capturing)
```

#### Make lifetimes explicit for event subscriptions
If you subscribe with a capturing lambda, you often can’t unsubscribe unless you stored the delegate instance:

```csharp
using System;

sealed class Example
{
    private Action? _handler;

    public void Subscribe(Publisher p)
    {
        _handler = () => Console.WriteLine("tick");
        p.Tick += _handler;
    }

    public void Unsubscribe(Publisher p)
    {
        if (_handler is not null)
            p.Tick -= _handler;
    }
}
```

This is one reason method-group event handlers are often superior for maintainability.

**Performance note**
- Captures in tight loops can dominate CPU via GC, not via the delegate call itself.
- The highest leverage fix is changing shape: avoid capture, cache non-capturing delegates, avoid repeated subscription churn.
