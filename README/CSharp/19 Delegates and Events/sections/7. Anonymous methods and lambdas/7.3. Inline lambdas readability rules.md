## 7.3. Inline lambda expressions at call sites (readability rules + avoiding “lambda soup”)

1. **When inline is great** (small predicates/projections; local policies)
2. **When to name it** (reused logic; unit testing; complex behavior; better stack traces)
3. **Performance note** (naming doesn’t fix captures—design does)

### 1) When inline is great
Inline lambdas shine when the callback is:

- **Short** (typically 1–3 simple expressions)
- **Local** to the call site (not reused elsewhere)
- **Obvious** from surrounding context

Good examples:

- LINQ projections (but see the performance note below)
- Guard clauses and small transformations
- Small policy knobs in APIs like retry/backoff, filtering, formatting

```csharp
using System;
using System.Linq;

var nums = new[] { 1, 2, 3, 4, 5 };
var evens = nums.Where(static x => (x & 1) == 0); // inline + static (no capture)
Console.WriteLine(string.Join(", ", evens));      // 2, 4
```

**Good to know**
- Inline does *not* mean “always lambda”: a **method group** is often clearer than `x => SomeMethod(x)` and avoids accidental captures (see [1.3](<../1. Delegates fundamentals/1.3. Method groups vs lambdas vs anonymous methods.md>) and [7.4](<./7.4. static lambdas prevent captures.md>)).

### 2) When to name it (and why mentors insist)
Name the callback (method, local function, or a named delegate variable) when:

- **Reused logic** appears in multiple places (DRY + consistency)
- The lambda is **non-trivial** (multiple branches, error handling, logging, IO)
- You want **unit tests** over the behavior
- You want **better stack traces** and easier debugging
- You need **documentation** on intent, contracts, and nullability

Options, in increasing “API surface”:

- **Local function** for one method’s scope
- **Private static method** for reuse and testability
- **Strategy type** (interface/class) when behavior has state and multiple operations

```csharp
using System;
using System.Collections.Generic;

static bool IsValidCustomerId(string id)
{
    if (string.IsNullOrWhiteSpace(id)) return false;
    return id.Length is >= 3 and <= 64;
}

var ids = new List<string?> { "A12", null, "   ", "B34" };
ids.RemoveAll(id => id is null || !IsValidCustomerId(id)); // method name carries intent
```

**Mentor guidance**
- Prefer **private static methods** for event handlers unless you truly need captures; it simplifies unsubscribe and avoids retaining `this` unexpectedly (see [10.2](<../10. Performance memory scalability/10.2. Events memory leaks subscription lifetimes.md>)).

### 3) Performance note: naming doesn’t fix captures—design does
Renaming a capturing lambda doesn’t stop it from capturing; only removing the capture does.

Common performance traps:

- Capturing `this` implicitly inside an instance method (`() => DoWork()` captures the instance if it touches instance state).
- Capturing large objects (e.g., a huge config, a `DbContext`, a `byte[]`) extends lifetimes and increases memory pressure.
- Creating new delegates in a hot loop (per-iteration allocations + GC).

Prefer:

- **`static` lambdas** when possible (forces you to pass dependencies as parameters).
- **Caching** delegates if they’re reused, especially in subscription scenarios.
- Avoid using LINQ in hot paths unless measured; consider loop-based code for zero allocations.

See [7.2](<./7.2. Captures closures allocations.md>) for the full closure/allocation model and [10.1](<../10. Performance memory scalability/10.1. Allocation sources captures delegate creation.md>) for allocation sources across delegates/events.
