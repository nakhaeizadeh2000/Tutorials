## 2.2. Creating delegates from methods (static/instance, open/closed delegates)

1. **Instance target binding** (how the target object is captured by the delegate)
2. **Open vs closed delegates** (advanced: shape affects allocation and call sites)
3. **Practical advice** (cache delegates when repeatedly subscribing; avoid per-call allocations in hot paths)

### 1) Instance target binding
When you create a delegate from an **instance method**, the delegate stores a strong reference to the **target instance** (unless you create an “open” delegate; see below). That has two key implications:

- **Lifetime**: the delegate keeps the target alive (important for memory leaks with long-lived publishers; see [10.2](<../10. Performance memory scalability/10.2. Events memory leaks subscription lifetimes.md>)).
- **Correctness**: if you subscribe an instance method to an event, you must unsubscribe it (or dispose the subscription) or you may keep the subscriber alive forever.

Example:

```csharp
using System;

sealed class Counter
{
    private int _value;
    public void Inc() => _value++;
    public int Value => _value;
}

var c = new Counter();
Action inc = c.Inc; // captures target instance c
inc();
Console.WriteLine(c.Value); // 1
```

**Good to know**
- A delegate to a static method has `Target == null`.
- A delegate to an instance method has `Target != null` (the instance) in the normal “closed” case.

### 2) Open vs closed delegates (advanced)
This topic is mostly relevant when you care about **call-site shape**, **allocations**, or **interop/reflection**.

- **Closed delegate**: target is already bound. Invocation requires only the method parameters.
  - Example: `Action inc = c.Inc;` (no parameters)
- **Open delegate**: target is *not* bound. The target is passed as the first argument at invocation time.
  - Example shape: `Action<Counter> inc = static c => c.Inc();` (this is an adapter lambda, not an open instance-method group)

In day-to-day code you most often create **closed** delegates via method groups or lambdas.

#### Creating “open” delegates intentionally
You typically do this via `Delegate.CreateDelegate` or reflection-based APIs. That’s a niche tool:

- **When it’s justified**: dynamic binding frameworks, high-performance serializers/ORMs, interop layers.
- **When it’s not**: business logic. Use normal method groups / lambdas for clarity.

**Performance note**
- Reflection-based delegate creation can be expensive; cache the resulting delegate if you do it at runtime.
- Adapter lambdas used to emulate “open” delegates can allocate if they capture. Prefer `static` lambdas to prevent capture.

### 3) Practical advice (mentor-grade)
#### Cache delegates in hot paths and long-lived subscriptions
If you repeatedly create the same handler in a loop, you may allocate delegates repeatedly (and capture accidentally):

```csharp
using System;

sealed class Publisher
{
    public event Action? Tick;
    public void Raise() => Tick?.Invoke();
}

var p = new Publisher();

// Bad in hot paths: creates a new delegate each iteration (and can capture)
for (int i = 0; i < 3; i++)
{
    p.Tick += () => Console.WriteLine("tick"); // capturing-free here, but still new delegate instance
}

// Better: create once, reuse
Action handler = static () => Console.WriteLine("tick");
p.Tick += handler;
```

#### Avoid accidental capture of `this`
Subscribing with `this.SomeHandler` is explicit and easy to unsubscribe. Subscribing with `() => this.SomeHandler()` often captures `this` and is harder to remove later.
