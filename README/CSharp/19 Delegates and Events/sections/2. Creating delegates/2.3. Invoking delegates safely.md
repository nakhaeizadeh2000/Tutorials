## 2.3. Invoking delegates safely and idiomatically (null checks, `?.Invoke`, and thread-safety)

1. **Idioms** (`handler?.Invoke(...)` and why it’s preferred)
2. **Thread-safety reality** (atomicity of read + call; unsubscribes during invocation; race considerations)
3. **Exception strategy** (when to let exceptions bubble vs isolating subscribers)

### 1) Idioms: null checks and `?.Invoke`
Delegates are nullable references in practice: a variable of type `Action`/`Func<...>` can be `null` meaning “no callback”.
The idiomatic and readable invocation is:

```csharp
handler?.Invoke(arg1, arg2);
```

This is preferred over:

```csharp
if (handler != null) handler(arg1, arg2);
```

because it is concise and (for delegates/events) maps to a pattern the compiler and runtime optimize well.

**Good to know**
- `?.Invoke` works for events too when you’re raising from inside the declaring type.
- For delegates with return values, `handler?.Invoke(...)` returns `default` when `handler` is null (e.g. `null` for reference types, `0` for `int`). That can hide “no handler registered” bugs. Consider explicit checks if “must have a handler” is part of your contract.

### 2) Thread-safety reality (atomicity and races)
The common rule you’ll hear is: “copy the delegate to a local variable, then invoke the local.”

Historically, that avoided the race where another thread unsubscribes between the null-check and invocation:

```csharp
using System;

static Action? handler;

static void Raise()
{
    var snapshot = handler;  // take an immutable snapshot of the delegate reference
    snapshot?.Invoke();
}
```

In modern C#, `handler?.Invoke()` is already *effectively* using the snapshot pattern for delegate invocation semantics (the delegate reference is read once for the call). Still, for clarity and for custom event accessors / non-trivial patterns, the explicit snapshot remains a good “mentor-approved” habit.

#### What about subscribe/unsubscribe during invocation?
- **Unsubscribing while invoking** does *not* affect the current invocation: the invocation list is effectively a snapshot at the moment of invocation because delegates are immutable.
- **Subscribing while invoking** also does not affect the current invocation.
- **Reentrancy** (subscriber calls back into publisher and changes handlers) can create subtle ordering and invariants problems. See `10.3. Thread-safety and reentrancy with events` for the full treatment.

#### Custom event accessors and thread-safety
If you implement custom `add`/`remove`, you are responsible for safe publication and atomic updates (usually with `lock` or an `Interlocked.CompareExchange` loop). See [6.3](<../6. Implementing events/6.3. Custom event accessors add remove.md>) for the correct patterns.

**Performance note**
- Snapshotting a delegate reference is just copying a pointer-sized value; it’s essentially free.
- The expensive operations are **churn** (frequent `+=`/`-=` in hot loops) and **captures/closures** (see [10.1](<../10. Performance memory scalability/10.1. Allocation sources captures delegate creation.md>) and [7.2](<../7. Anonymous methods and lambdas/7.2. Captures closures allocations.md>)).

### 3) Exception strategy (bubble vs isolate)
Decide early what your delegate/event contract means when subscribers throw:

#### Option A: let exceptions bubble (default)
This is the default behavior of delegate invocation and is often correct when a callback is part of a required workflow (e.g., validation pipeline).

Pros:
- Fail-fast; errors surface immediately
- Preserves stack traces naturally

Cons:
- In multicast scenarios, later subscribers don’t run

#### Option B: isolate per subscriber (best-effort fan-out)
If your delegate is a notification fan-out (especially events), you often want:
- “Call everyone”
- “Collect/log exceptions”

That requires iterating invocation list:

```csharp
using System;

static void RaiseBestEffort(Action? handlers)
{
    if (handlers is null) return;

    foreach (var d in handlers.GetInvocationList())
    {
        try
        {
            ((Action)d).Invoke();
        }
        catch (Exception ex)
        {
            // Decide: log, aggregate, or rethrow later
            Console.Error.WriteLine(ex);
        }
    }
}
```

This pattern is covered in more depth (including allocation implications) in `3.2. Invocation list inspection advanced`. Use it intentionally: `GetInvocationList()` allocates an array.

**Mentor rule**
- If a callback is part of correctness (must succeed), bubble.
- If a callback is a notification (best-effort), isolate and log/aggregate.
- Never silently swallow exceptions without a plan—hidden failures are worse than failures.
