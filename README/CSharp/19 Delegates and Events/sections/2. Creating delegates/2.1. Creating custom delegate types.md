## 2.1. Creating custom delegate types (`delegate` keyword): when you actually need it

1. **When custom delegates make sense** (domain-named callback types; interoperability; attributes)
2. **When not to** (prefer `Func<>`/`Action<>` for internal code; reduce surface area)
3. **API design** (names, nullability, exception expectations, sync/async clarity)

### 1) When custom delegates make sense
In modern C# and .NET, **`Func<>` / `Action<>`** cover most callback scenarios. You introduce a **custom delegate type** when it buys you *clarity* or *capabilities* that the built-ins can’t provide.

Common valid reasons:

- **Domain naming (API readability)**: a named delegate can communicate intent better than `Func<T1, T2, TResult>`.
- **Interop / framework shape**: sometimes you must match an existing signature or pattern (e.g., older .NET APIs, COM interop).
- **Custom attributes on the delegate type or parameters**: for source generators, analyzers, marshalling, or domain metadata.
- **Ref/out/in/pointer/unsafe shapes that don’t fit `Func<>`/`Action<>`**: built-in delegates don’t cover every parameter modifier scenario.
- **Public API stability**: a named delegate lets you evolve the API without spreading a long generic signature everywhere (though you still can’t change signature without breaking callers).

Example: a domain-named callback that reads clearly at the call site.

```csharp
using System;

public readonly record struct RetryDecision(bool ShouldRetry, TimeSpan Delay);

public delegate RetryDecision RetryPolicy(Exception exception, int attempt);

public static class Retrier
{
    public static void Run(Action work, RetryPolicy policy)
    {
        ArgumentNullException.ThrowIfNull(work);
        ArgumentNullException.ThrowIfNull(policy);

        for (var attempt = 1; ; attempt++)
        {
            try
            {
                work();
                return;
            }
            catch (Exception ex) when (attempt < 5)
            {
                var decision = policy(ex, attempt);
                if (!decision.ShouldRetry) throw;
                Thread.Sleep(decision.Delay);
            }
        }
    }
}
```

Why this is better than `Func<Exception, int, (bool, TimeSpan)>`: it documents intent, reads well in IntelliSense, and gives you a single type name to reference across your codebase.

**Good to know**
- You can declare delegates **as nested types** if they’re not meant to be part of the broader public surface area.

### 2) When not to
Prefer `Func<>`/`Action<>` when:

- The callback is **internal** (not public API) and the signature is simple.
- The callback is used only once or twice and a custom name would add noise.
- You’d create many tiny delegate types that increase API surface and documentation burden.

Example: internal plumbing is often clearer with built-ins:

```csharp
Func<int, bool> isValidId = static id => id > 0;
Action<string> log = Console.WriteLine;
```

**Performance note**
- Whether you use a named delegate or `Func<>`/`Action<>` does not inherently change runtime performance. Performance is dominated by **captures**, **allocation patterns**, and **invocation frequency** (see [7.2](<../7. Anonymous methods and lambdas/7.2. Captures closures allocations.md>), [7.4](<../7. Anonymous methods and lambdas/7.4. static lambdas prevent captures.md>), and [10.1](<../10. Performance memory scalability/10.1. Allocation sources captures delegate creation.md>)).

### 3) API design (mentor-grade guidance)
If you expose a delegate in a public API, treat it like any other API contract.

- **Name it by behavior**: `RetryPolicy`, `MessageFilter`, `UserValidator`, `OnItemAddedHandler` (avoid generic names like `Callback`).
- **Nullability is a contract**:
  - If you might pass null values, express it explicitly: `string?`.
  - Don’t “forget” nullability because it’s “just a callback”.
- **Define exception expectations**:
  - Will exceptions propagate to the caller? (default and usually correct)
  - Are exceptions isolated per-subscriber? (events sometimes do; delegates usually don’t)
  - If you swallow exceptions, document it loudly (and prefer logging + telemetry).
- **Be explicit about sync vs async**:
  - If the callback is asynchronous, prefer `Func<CancellationToken, ValueTask>` or `Func<CancellationToken, Task>` (not `async void`).
  - For events, async is tricky; see [10.3](<../10. Performance memory scalability/10.3. Thread-safety reentrancy events.md>) for the “async event handler” hazards and safe patterns.
- **Avoid ambiguous overloads**: if you have overloads that accept multiple delegate types, method groups and lambdas can become ambiguous. See [1.3](<../1. Delegates fundamentals/1.3. Method groups vs lambdas vs anonymous methods.md>) for overload resolution patterns.

**Deprecated/legacy patterns to avoid**
- **Custom delegates that reinvent `EventHandler`** for public event APIs without a strong reason. If you’re doing a classic event, either follow the pattern (`EventHandler<T>`) or intentionally design a modern alternative and document it (see [5.2](<../5. Events fundamentals/5.2. EventHandler patterns modern.md>)).
