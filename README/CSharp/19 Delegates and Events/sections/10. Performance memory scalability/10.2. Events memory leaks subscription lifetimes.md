## 10.2. Events and memory leaks (subscription lifetimes, strong references, and disposal patterns)

1. **Why leaks happen** (publisher holds strong refs to subscribers)
2. **Mitigations** (unsubscribe deterministically; tie to `IDisposable`; weak-event patterns where justified)
3. **Architectural guidance** (prefer scoped subscriptions; avoid “global event buses” without lifecycle control)

### 1) Why leaks happen
Events are a classic source of memory leaks because the **publisher holds strong references** to subscribers via the event’s invocation list.

If:

- Publisher lives “a long time” (singleton, static, app-wide service, long-running background component)
- Subscriber should be short-lived (UI view, request-scoped service, temporary object)

…then a subscription keeps the subscriber alive even if nothing else references it anymore.

In other words: **subscribing transfers lifetime responsibility** to whoever controls the publisher.

#### Minimal leak demonstration

```csharp
using System;

sealed class Publisher
{
    public event EventHandler? Tick;
    public void Raise() => Tick?.Invoke(this, EventArgs.Empty);
}

sealed class Subscriber
{
    public Subscriber(Publisher p) => p.Tick += OnTick;
    private void OnTick(object? sender, EventArgs e) { /* ... */ }
}
```

If `Publisher` stays alive and you create many `Subscriber` instances without unsubscribing, **none of those subscribers can be collected**, because the publisher references their handler delegates.

**Good to know**
- This is not a “GC bug”. The GC is doing exactly what it should: objects are still reachable.
- Capturing lambdas can make leaks worse by capturing `this` (see [7.2](<../7. Anonymous methods and lambdas/7.2. Captures closures allocations.md>) for the full closure explanation).

### 2) Mitigations
There are three “mentor-approved” mitigation families.

#### Mitigation A: deterministic unsubscribe (best default)
Unsubscribe when you no longer need the subscription. For long-lived publishers, make the subscription itself an `IDisposable` so callers can scope it.

**Pattern: subscribe returns an `IDisposable` token**

```csharp
using System;

sealed class TemperatureSensor
{
    private EventHandler<int>? _changed;
    public event EventHandler<int> Changed
    {
        add => _changed += value;
        remove => _changed -= value;
    }

    public IDisposable Subscribe(EventHandler<int> handler)
    {
        Changed += handler;
        return new Subscription(this, handler);
    }

    public void Publish(int value) => _changed?.Invoke(this, value);

    private sealed class Subscription : IDisposable
    {
        private TemperatureSensor? _owner;
        private EventHandler<int>? _handler;

        public Subscription(TemperatureSensor owner, EventHandler<int> handler)
        {
            _owner = owner;
            _handler = handler;
        }

        public void Dispose()
        {
            var owner = _owner;
            var handler = _handler;
            if (owner is null || handler is null) return;

            owner.Changed -= handler;
            _owner = null;
            _handler = null;
        }
    }
}
```

**Performance note**
- Returning an `IDisposable` allocates one object per subscription. That’s usually acceptable because subscriptions are relatively infrequent.
- If you need zero-allocation subscriptions in a high-frequency system, you’ll typically redesign (e.g., use channels, pipelines, or value-type subscription handles with careful lifetime rules). Don’t prematurely optimize event subscription patterns.

#### Mitigation B: tie subscription to an owner’s lifetime (`Dispose`)
A very common approach: if a subscriber is `IDisposable`, it unsubscribes in `Dispose`. This makes lifetime explicit and testable.

```csharp
using System;

sealed class Subscriber : IDisposable
{
    private readonly Publisher _publisher;

    public Subscriber(Publisher publisher)
    {
        _publisher = publisher;
        _publisher.Tick += OnTick;
    }

    public void Dispose() => _publisher.Tick -= OnTick;

    private void OnTick(object? sender, EventArgs e) { }
}
```

This is especially important for (frontend) UI elements where lifetimes are tied to view creation/destruction.

#### Mitigation C: weak-event patterns (advanced; use only with justification)
Weak events are used when:
- The publisher must not extend subscriber lifetime
- Deterministic unsubscription is difficult to enforce

Trade-offs:
- More complexity and CPU per invocation
- Harder debugging (handlers might disappear “unexpectedly”)
- Often requires custom infrastructure; many legacy “weak event managers” exist, but they’re not universally appropriate

**Mentor guidance**
- Prefer deterministic unsubscribe. Use weak events only when you can clearly justify why “unsubscribe” cannot be made reliable.

### 3) Architectural guidance
- **Avoid global event buses** without lifecycle control. They combine “long-lived publisher” with “random subscribers”, which is leak-prone by design.
- Prefer **scoped publishers** (per request, per view, per component) or explicit mediator patterns with clear ownership.
- If you need cross-cutting notifications at scale, consider message-based approaches (channels, queues, reactive streams) where subscriptions and lifetimes are explicit and testable.

**Good to know**
- If you must expose events publicly, document the lifetime contract: “callers must unsubscribe” vs “publisher returns an `IDisposable` subscription token”.
