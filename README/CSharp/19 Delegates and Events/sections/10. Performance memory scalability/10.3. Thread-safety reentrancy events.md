## 10.3. Thread-safety and reentrancy with events (real-world hazards)

1. **Reentrancy** (subscriber calls back into publisher; invariants and ordering)
2. **Concurrency** (subscribe/unsubscribe races; raising from background threads)
3. **Practical patterns** (immutable snapshots; minimal locks; don’t block in event handlers)

### 1) Reentrancy (the “it called back into me” hazard)
**Reentrancy** happens when an event handler calls back into the publisher (directly or indirectly) *while the publisher is mid-operation*. This is common and not “wrong”, but it breaks assumptions like “state can’t change during raise”.

Typical example:

```csharp
using System;

sealed class Counter
{
    private int _value;
    public event Action<int>? Changed;

    public void Increment()
    {
        _value++;
        Changed?.Invoke(_value); // a handler can call Increment() again (reentrancy)
    }
}
```

#### What can go wrong
- **Broken invariants**: you raise while inside a critical section or half-updated object.
- **Unexpected recursion**: handlers that call back can cause unbounded recursion.
- **Ordering bugs**: other handlers see intermediate state.

#### Mentor guidance
- Make “what is observable” explicit: raise **after** invariants are restored.
- Avoid raising while holding locks (more on that below).
- If reentrancy must be prevented, use a guard (but keep it minimal and well-documented):

```csharp
using System;

sealed class ReentrancyGuarded
{
    private int _inRaise;
    public event Action? Something;

    public void Raise()
    {
        if (_inRaise != 0) return; // or throw, depending on your contract
        _inRaise = 1;
        try { Something?.Invoke(); }
        finally { _inRaise = 0; }
    }
}
```

This is not “the” solution—sometimes you want reentrancy (e.g., reactive graphs). The key is to be intentional.

### 2) Concurrency (subscribe/unsubscribe races; cross-thread raising)
Events are **multicast delegates under the hood**, but the event keyword enforces encapsulation rules. Thread-safety concerns still exist:

#### Subscribe/unsubscribe while raising
- Delegate invocation uses a snapshot of the delegate reference (because delegates are immutable).
- The main risk is not that the invocation list “changes mid-iteration”; it’s that your **publisher’s state** is accessed concurrently by handlers, and that raising might happen from multiple threads.

#### Raising from background threads (frontend note)
If you’re in UI frameworks (WPF/WinForms/MAUI) (frontend), raising an event from a background thread that updates UI in handlers will throw or corrupt UI state. In UI code, handlers often must marshal to the UI thread (e.g., `Dispatcher`, `SynchronizationContext`).

This tutorial’s deep async/UI-thread marshaling lives outside this domain; see the repository’s async/concurrency materials referenced by `13.1` (boundaries).

### 3) Practical patterns (correctness + performance)
#### Pattern A: snapshot then invoke
This is the simplest and most common “correct enough” pattern:

```csharp
using System;

sealed class Publisher
{
    public event EventHandler? Tick;

    public void RaiseTick()
    {
        var snapshot = Tick;                // take a local snapshot
        snapshot?.Invoke(this, EventArgs.Empty);
    }
}
```

#### Pattern B: never invoke handlers under a lock
Invoking user code while holding a lock can create:
- **Deadlocks** (handler tries to call back and acquire the same lock)
- **Priority inversions / contention spikes**
- **Long critical sections** (handlers do I/O or heavy work)

Better approach:
- Take snapshots of both **state** and **delegate**, release lock, then invoke.

#### Pattern C: keep handlers fast; offload intentionally
Event handlers should be quick and non-blocking.

If you need to run background work, do it explicitly and safely:
- Use `Task.Run` *only* when appropriate (CPU-bound work you want on the thread pool).
- For I/O-bound work, prefer naturally-async APIs.

Avoid `async void` handlers unless you are forced by a signature (common in UI). If you need async notifications, consider designing an explicit async callback pipeline (e.g., `Func<T, CancellationToken, ValueTask>`) rather than a classic event—this is an API design decision, not a “sprinkle async” change.

**Performance note**
- Subscribing/unsubscribing is typically thread-safe for auto-implemented events in the sense that `+=`/`-=` are atomic with respect to the event field update, but it’s still easy to create races around your own state. When you add custom accessors (`6.3`), you must implement atomicity yourself.
