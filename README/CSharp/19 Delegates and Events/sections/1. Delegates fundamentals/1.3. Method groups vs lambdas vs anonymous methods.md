## 1.3. Method groups vs lambdas vs anonymous methods (selection + overload resolution)

1. **Choosing the right form** (readability, capture needs, testability)
2. **Overload resolution** (why “ambiguous call” happens; explicit casts and target typing)
3. **Best practices** (prefer method groups for non-capturing handlers; keep lambdas small and intention-revealing)

### 1) Choosing the right form
All three forms produce a delegate (or an expression tree, depending on context), but they differ in **readability**, **capturing**, and **type inference** behavior.

#### Method group (`SomeMethod`)
Use when you already have a suitably-named method and you **don’t need to capture** locals.

Pros:
- **Zero capture by construction** (no closure object)
- Usually most readable at call sites (especially for event handlers)
- Better stack traces (method name shows up)

Cons:
- Needs a named method (slightly more ceremony)
- If there are multiple overloads, you may need a cast to disambiguate

```csharp
using System;

static void Log(string message) => Console.WriteLine(message);

Action<string> write = Log;
write("Hello");
```

#### Lambda (`x => ...` / `(x, y) => ...`)
Use when the logic is **small** and/or you need **local policy** expressed inline.

Pros:
- Great for tiny transformations and predicates
- Can capture variables (sometimes that’s exactly what you want)

Cons:
- Captures can allocate and extend lifetimes (see [7.2](<../7. Anonymous methods and lambdas/7.2. Captures closures allocations.md>) and [7.4](<../7. Anonymous methods and lambdas/7.4. static lambdas prevent captures.md>))
- Easy to create “lambda soup” if the expression grows

```csharp
using System;

var suffix = " (prod)";
Func<string, string> format = s => s + suffix; // capture => closure allocation
Console.WriteLine(format("api"));
```

#### Anonymous method (`delegate (...) { ... }`)
This is largely legacy syntax. Prefer lambdas unless you have a specific reason.

When it can still be useful:
- When you want to omit parameter list types in older-style code while still writing a block (rare today)
- When porting old code and minimizing diffs

```csharp
using System;

Action<int> print = delegate (int x) { Console.WriteLine(x); };
print(123);
```

**Mentor guidance**
- Default to **method groups** or **`static` lambdas** for non-capturing callbacks.
- Use lambdas when they remain **small and intention-revealing**.
- If the callback is reused, complex, or deserves a name (and tests), make it a method.

### 2) Overload resolution (why “ambiguous call” happens)
Overload resolution involves the *target delegate type*. The compiler needs to know the delegate signature to decide which method overload to bind.

#### Common ambiguous case: method group with multiple overloads

```csharp
using System;

static void M(int x) => Console.WriteLine($"int {x}");
static void M(string s) => Console.WriteLine($"string {s}");

// Action<object> a = M; // error: cannot convert method group (no exact match)
Action<int> ai = M;      // picks M(int)
Action<string> @as = M;  // picks M(string)
```

If you need to force a specific choice, **cast the method group**:

```csharp
using System;

static void M(int x) => Console.WriteLine(x);
static void M(long x) => Console.WriteLine(x);

Action<int> a = (Action<int>)M;
```

#### Common ambiguous case: lambda with no target typing
Without a target delegate type, a lambda may not have enough information:

```csharp
// var f = x => x + 1; // error: cannot infer the type of x
Func<int, int> f = x => x + 1;
```

#### Another pitfall: overloads that differ by delegate type

```csharp
using System;

static void Use(Func<int, int> f) => Console.WriteLine(f(1));
static void Use(Func<int, long> f) => Console.WriteLine(f(1));

// Use(x => x); // ambiguous
Use((Func<int, int>)(x => x));
```

**Good to know**
- Target typing is much stronger in modern C#, but **overload sets with multiple delegate-shaped overloads** can still cause ambiguity. Make the intent explicit with a cast or named variable.

### 3) Best practices (mentor-grade)
- **Prefer method groups for events**: easiest to unsubscribe, no accidental capture of `this`.
- **Prefer `static` lambdas** when you don’t need captures:

```csharp
using System;

Func<int, bool> isEven = static x => (x & 1) == 0;
```

- **Avoid capturing loop variables accidentally**. Modern C# fixed many “foreach capture” issues, but captures still extend lifetimes. See [7.2](<../7. Anonymous methods and lambdas/7.2. Captures closures allocations.md>) for the full closure treatment.
- **Don’t hide work in one-liners**: expression-bodied members and concise lambdas can conceal allocations and thread hops; see [9.1](<../9. Expression-bodied and switch expressions/9.1. Expression-bodied members trade-offs.md>) and [10.1](<../10. Performance memory scalability/10.1. Allocation sources captures delegate creation.md>).

**Performance note**
- The *big* perf cliff is not “lambda vs method group”, it’s **capturing vs non-capturing**. Capturing creates a closure object which becomes extra allocations and GC pressure in hot paths.
