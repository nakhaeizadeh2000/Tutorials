## 3.1. Multicast delegates: combining/removing and the semantics of return values

1. **Combine/remove** (`+`, `-`, `Delegate.Combine`, `Delegate.Remove`)
2. **Return value rules** (last delegate wins; why this is usually a design smell)
3. **Exceptions** (one subscriber throwing stops later subscribers unless you isolate)

### 1) Combine/remove
A **multicast delegate** is a delegate whose invocation list has multiple entries. In practice, this is how C# events work under the hood, and you can also build multicast delegates directly with `+=` / `-=`.

#### Idiomatic syntax
For delegate variables:

```csharp
using System;

static void A() => Console.WriteLine("A");
static void B() => Console.WriteLine("B");

Action? d = null;
d += A;
d += B;
d?.Invoke(); // A then B

d -= A;
d?.Invoke(); // B
```

For *events*, only the declaring type can invoke; external code can only subscribe/unsubscribe (see [5.1](<../5. Events fundamentals/5.1. What an event is.md>)).

#### `+`/`-` vs `Delegate.Combine` / `Delegate.Remove`
- Prefer `+=` / `-=` for readability and consistency.
- `Delegate.Combine` / `Delegate.Remove` exist mainly for reflection-heavy scenarios and dynamic composition; they return `Delegate` and require casts back to the concrete delegate type.

#### How removal matches
Removal removes the **last matching occurrence** in the invocation list that has the same **method + target** pair.

Common pitfall:

```csharp
using System;

Action? d = null;

d += () => Console.WriteLine("Hi");
// d -= () => Console.WriteLine("Hi"); // does NOT unsubscribe: different delegate instance (and different closure)
```

**Mentor rule**: if you need to unsubscribe, prefer a **method group** or store the delegate instance in a variable and reuse it.

### 2) Return value rules (and why it’s often a smell)
If a multicast delegate has a return type (e.g., `Func<int>`), the invocation still calls all subscribers in order, but the *caller only sees the return value of the last subscriber*.

```csharp
using System;

static int One() => 1;
static int Two() => 2;

Func<int> f = One;
f += Two;

Console.WriteLine(f()); // 2 (last wins)
```

This is usually a **design smell** because multicast delegates are for **fan-out notifications**, not queries. Better designs:
- **Single handler** (single-cast) when a return value matters.
- **Explicit aggregation**: return `IReadOnlyList<T>` or accept a collector.
- **Pipeline pattern**: call handlers sequentially and explicitly decide what “combining results” means.

### 3) Exceptions
Default multicast behavior is fail-fast:
- Subscribers are invoked in order.
- If one throws, the invocation stops and the exception propagates.

If you need best-effort notification, you must isolate per subscriber by iterating `GetInvocationList()` and handling exceptions individually; see [3.2](<./3.2. Invocation list inspection advanced.md>) for the full pattern and allocation caveats.

**Performance note**
- Combining/removing delegates creates new delegate instances (immutability). In hot loops, this can create allocation churn and contention. Prefer stable subscription lifetimes and avoid per-iteration subscribe/unsubscribe.
