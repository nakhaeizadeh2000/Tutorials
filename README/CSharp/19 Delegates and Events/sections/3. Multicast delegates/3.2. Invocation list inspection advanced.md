## 3.2. Inspecting and invoking invocation lists (advanced + when not to)

1. **`GetInvocationList()`** (allocations and cost; use sparingly)
2. **Per-subscriber isolation** (logging failures without breaking others)
3. **Design rule** (prefer events for fan-out notifications; avoid “multicast delegate return values” APIs)

### 1) `GetInvocationList()` and its real cost
`Delegate.GetInvocationList()` returns an array of delegates representing each subscriber in call order.

Key facts:
- It **always allocates** a new array. Calling it on every event raise in a high-frequency path will add GC pressure.
- Each element is typed as `Delegate`, so you often need a cast back to the concrete delegate type to invoke.

```csharp
using System;

static void DumpHandlers(Action? handlers)
{
    if (handlers is null) return;

    foreach (var d in handlers.GetInvocationList())
        Console.WriteLine(d.Method);
}
```

**Good to know**
- The returned delegates are immutable snapshots; subscribing/unsubscribing concurrently won’t mutate the array you got.
- If you only need a thread-safe snapshot for invocation, prefer the cheaper pattern in `2.3` (copy the delegate reference to a local). Only reach for `GetInvocationList()` when you *need per-subscriber behavior* (isolation, diagnostics, etc.).

### 2) Per-subscriber isolation (best-effort fan-out)
If subscribers are independent observers, isolating failures is often the right policy:

```csharp
using System;
using System.Collections.Generic;

static IReadOnlyList<Exception> RaiseBestEffort(Action? handlers)
{
    if (handlers is null) return Array.Empty<Exception>();

    List<Exception>? errors = null;

    foreach (var d in handlers.GetInvocationList())
    {
        try
        {
            ((Action)d).Invoke();
        }
        catch (Exception ex)
        {
            errors ??= new List<Exception>(capacity: 1);
            errors.Add(ex);
        }
    }

    return (IReadOnlyList<Exception>?)errors ?? Array.Empty<Exception>();
}
```

Trade-offs:
- **Pros**: one bad handler doesn’t block others; you can aggregate errors and decide what to do.
- **Cons**: allocation from `GetInvocationList()` plus potential list allocation; also you may hide important failures if you ignore the returned exceptions.

**Performance note**
- If events fire frequently and you need best-effort semantics, consider pushing isolation to subscribers (they catch) or redesigning so that “must-not-throw observers” are enforced.
- If you must isolate centrally, avoid logging synchronously on hot paths; buffer or use structured logging with backpressure.

### 3) Design rule (when *not* to inspect invocation lists)
Use invocation-list inspection sparingly; it’s an advanced tool that can become an anti-pattern.

Avoid:
- APIs that expose multicast delegates as “business logic pipelines” where ordering matters but isn’t documented.
- Multicast delegates with return values (see `3.1`). If you need many results, make it explicit in the API design (e.g., `IEnumerable<TResult>`).

Prefer:
- **Events** for “many listeners might care” notifications (encapsulation boundary). See `5.1` and `6.x`.
- **Explicit pipelines** (e.g., a list of strategies or middleware) when ordering and composition are core to correctness; in that case, model it as `IReadOnlyList<IStrategy>` or similar rather than “magic multicast”.
