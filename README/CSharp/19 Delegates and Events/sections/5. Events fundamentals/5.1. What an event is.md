## 5.1. What an event is (restricted multicast delegate + encapsulation boundary)

1. **Why events exist** (prevent external code from overwriting the invocation list)
2. **Access rules** (subscribe/unsubscribe outside; raise inside)
3. **Key correctness idea** (events are an API boundary; lifetime management matters)

### 1) Why events exist
An **event** is a language feature built on delegates that enforces a crucial rule:

- External code can **subscribe/unsubscribe**.
- External code cannot **overwrite** the invocation list or **invoke** the event.

In other words: an event is a **restricted multicast delegate** that creates an **encapsulation boundary** between publisher and subscribers.

Why you should care:
- It prevents consumers from doing `publisher.Changed = null;` (wiping other subscribers).
- It makes the publisher the single authority over when notifications fire.

Compare “delegate as field” vs “event”:

```csharp
using System;

sealed class BadPublisher
{
    // Anyone can replace the whole callback list or invoke it.
    public Action? Changed;
}

sealed class GoodPublisher
{
    // Anyone can += / -=, but only this type can raise it.
    public event Action? Changed;

    public void Notify() => Changed?.Invoke();
}
```

### 2) Access rules (subscribe/unsubscribe outside; raise inside)
With a normal (field-like) event declaration:

```csharp
public event EventHandler? SomethingHappened;
```

- **Outside** the declaring type you may only use `+=` and `-=`:
  - `publisher.SomethingHappened += Handler;`
  - `publisher.SomethingHappened -= Handler;`
- **Inside** the declaring type you can invoke it:
  - `SomethingHappened?.Invoke(this, EventArgs.Empty);`

This is enforced by the compiler and is the primary reason events exist as a distinct feature.

**Good to know**
- Events can also have **custom accessors** (`add`/`remove`). That’s advanced and is covered in depth in `6.3. Custom event accessors`.
- An event is not “magically thread-safe”. It only restricts *who can do what* syntactically; you still must design for concurrency and reentrancy (see [10.3](<../10. Performance memory scalability/10.3. Thread-safety reentrancy events.md>)).

### 3) Key correctness idea: lifetime and ownership
The most common production bug with events is not syntax—it’s **lifetime**:

- The **publisher holds strong references** to subscribers via the invocation list.
- If a subscriber “forgets” to unsubscribe, it can be kept alive longer than intended → **memory leak**.

This is not theoretical; it’s one of the main reasons event-heavy architectures become fragile.

Mentor guidance:
- Treat event subscriptions like owning a resource.
- If a subscription has a clear scope, represent it as `IDisposable` (subscribe returns a token you dispose to unsubscribe).
- Avoid “global event buses” without strict lifecycle rules.

For the deep, production-grade explanation + patterns (including weak events and disposal), see `10.2. Events and memory leaks`.

**Performance note**
- Event invocation is synchronous by default. If handlers do heavy work or block, they slow down the publisher and can cause thread-pool starvation if raised on thread-pool threads. The correct design is to keep handlers small and explicitly offload work (see [10.3](<../10. Performance memory scalability/10.3. Thread-safety reentrancy events.md>)).
