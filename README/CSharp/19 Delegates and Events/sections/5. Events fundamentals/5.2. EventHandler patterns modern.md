## 5.2. EventHandler patterns: `EventHandler`, `EventHandler<TEventArgs>`, and modern alternatives

1. **Classic .NET pattern** (`sender`, `EventArgs`, naming conventions)
2. **Modern guidance** (avoid `EventArgs` inheritance when it adds no value; consider plain record payloads for internal code)
3. **Interop** (UI frameworks, legacy libraries, and why `EventHandler` still matters)

### 1) Classic .NET pattern (why it exists, and what the conventions mean)
The “standard” .NET event signature is:

- `EventHandler` for “something happened, no payload”
- `EventHandler<TEventArgs>` for “something happened, payload of type `TEventArgs`”

```csharp
using System;

public sealed class Clock
{
    public event EventHandler? Tick;

    public void RaiseTick() => Tick?.Invoke(this, EventArgs.Empty);
}
```

For payload:

```csharp
using System;

public sealed class TemperatureChangedEventArgs : EventArgs
{
    public TemperatureChangedEventArgs(decimal celsius) => Celsius = celsius;
    public decimal Celsius { get; }
}

public sealed class Thermometer
{
    public event EventHandler<TemperatureChangedEventArgs>? TemperatureChanged;

    public void Set(decimal celsius) =>
        TemperatureChanged?.Invoke(this, new TemperatureChangedEventArgs(celsius));
}
```

Conventions (these are not “just style”—they help discoverability and tooling):
- **Event name**: past-tense or noun phrase (`TemperatureChanged`, `Closed`, `Tick`)—what happened.
- **EventArgs type name**: `<EventName>EventArgs` for public APIs.
- **Raise method**: often `On<EventName>` (protected virtual) in inheritance-friendly designs.
- **`sender`**: object that raised the event. In instance events it’s usually `this`.

**Good to know**
- The event pattern is intentionally non-generic on the sender: `object? sender`. This keeps handlers compatible even across hierarchies and tooling.

### 2) Modern guidance (C# 15/.NET 9+ era)
You still use `EventHandler` in many *public* APIs for ecosystem compatibility, but you can modernize how you model payloads and lifetimes.

#### Avoid pointless `EventArgs` inheritance
If you’re not building a library meant to feel like “classic .NET”, `EventArgs` inheritance is optional. For internal code or service boundaries, a simple immutable payload is often clearer:

```csharp
using System;

public readonly record struct TemperatureChanged(decimal Celsius);

public sealed class Thermometer
{
    // Internal API: payload-first event handler
    public event Action<TemperatureChanged>? TemperatureChanged;

    public void Set(decimal celsius) =>
        TemperatureChanged?.Invoke(new TemperatureChanged(celsius));
}
```

Trade-offs:
- **Pros**: smaller surface area, no `sender` ambiguity, payload is explicit, record structs can avoid allocations.
- **Cons**: deviates from BCL conventions; less plug-and-play with frameworks expecting `EventHandler`.

#### Prefer “payload is non-null by contract”
For public events:
- Keep `TEventArgs` **non-nullable** (`EventHandler<MyArgs>` rather than `EventHandler<MyArgs?>`) unless you truly raise with `null`.
- If you need an “empty” payload, prefer `EventArgs.Empty` rather than `new EventArgs()`.

#### Consider `readonly record struct` for high-frequency payloads
If an event is raised *very frequently* (telemetry, high-rate sensors), allocating a new reference-type event args for every raise can be expensive. A `readonly record struct` payload can reduce GC pressure.

**Performance note**
- Struct payloads move cost from GC to copying. Keep them small (a few fields) and immutable.
- Don’t prematurely micro-optimize event args allocations if the event frequency is low or handlers do significant work.

#### Async is not “built in” to events
Classic events are synchronous fan-out. If you need async fan-out, treat it as a separate design:
- Use an explicit `Func<TPayload, ValueTask>` pipeline and decide semantics (sequential vs parallel, cancellation, error aggregation).
- Avoid `async void` handlers except UI message-loop scenarios (frontend) and only when you have an exception strategy.

For reentrancy and thread-safety hazards when raising from background threads, see `10.3. Thread-safety and reentrancy with events`.

### 3) Interop (when `EventHandler` still matters)
Use `EventHandler` / `EventHandler<T>` when:
- You are building a **library** that consumers expect to look/feel like .NET APIs.
- You integrate with **UI frameworks** (frontend) and common infrastructure that assumes `EventHandler` signatures.
- You want tooling and conventions (naming, discoverability, analyzers) to align with the ecosystem.

**Legacy patterns to avoid**
- `public delegate void SomethingHappenedHandler(object sender, SomethingEventArgs e);`
  - Prefer `EventHandler<SomethingEventArgs>` unless you need attributes on the delegate type or very specific interop.
- Public events exposing raw `Delegate`/`MulticastDelegate`
  - Prefer strongly typed `event EventHandler<T>` (or `Action<T>`) so call sites remain type-safe.
