## 6.1. Declaring events with backing delegates (explicit event field pattern)

1. **Standard form** (`public event EventHandler SomethingHappened;`)
2. **Raising correctly** (`?.Invoke`; ordering; nullability)
3. **Reentrancy considerations** (subscribers can call back into publisher; invariants must hold)

### 1) Standard form (what you actually write)
In C#, an **event** is a language feature that exposes a *subscription surface* while protecting the underlying multicast delegate from being overwritten by external callers.

The default, idiomatic declaration is an auto-implemented event:

```csharp
public event EventHandler? SomethingHappened;
```

However, sometimes you want the explicit “backing field” pattern so you can:
- Raise via a `protected virtual` method (`OnSomethingHappened`)
- Wrap the handler in instrumentation
- Provide a custom name for the backing field

Example (classic, production-friendly pattern):

```csharp
using System;

public sealed class Engine
{
    public event EventHandler? Started;

    public void Start()
    {
        // ... state transitions ...
        OnStarted();
    }

    private void OnStarted() => Started?.Invoke(this, EventArgs.Empty);
}
```

**Good to know**
- Prefer `EventArgs.Empty` over `new EventArgs()` to avoid allocations.
- Use nullable annotations: `EventHandler?` is correct because “no subscribers” is a valid state.

### 2) Raising correctly (ordering, nullability, thread-safety)
The core rule: **raise events from inside the declaring type**, and do it in a way that is robust against races and reentrancy.

#### Snapshot pattern (recommended for clarity)

```csharp
using System;

public sealed class Clock
{
    public event EventHandler? Tick;

    public void Pulse()
    {
        var snapshot = Tick;           // take immutable snapshot of delegate reference
        snapshot?.Invoke(this, EventArgs.Empty);
    }
}
```

This is cheap (pointer copy) and communicates intent: “invoke whoever was subscribed at this instant”.

#### Ordering / invariants
If the event logically signals “state has changed”, then:
- Update your internal state first (establish invariant)
- Then raise the event

This prevents observers from seeing partially-updated state.

**Performance note**
Raising an event does not allocate by itself. Allocations usually come from:
- Creating payload objects for every raise (avoid if possible)
- Capturing closures in handlers (subscriber-side)
- Iterating `GetInvocationList()` (publisher-side) — see [3.2](<../3. Multicast delegates/3.2. Invocation list inspection advanced.md>)

### 3) Reentrancy considerations (the sharp edge)
Reentrancy means: during event invocation, a subscriber calls back into the publisher and changes its state or subscription list.

Common hazards:
- A subscriber calls `Start()` again from inside `Started` → double-start bugs
- A subscriber unsubscribes/resubscribes mid-raise → unexpected ordering assumptions
- A subscriber calls into methods that assume “not currently raising”

Mentor-grade guidance:
- Treat event-raising methods as **public API boundaries**: keep them small, establish invariants first, and avoid holding locks while raising.
- If reentrancy is unsafe, guard with state:

```csharp
using System;
using System.Threading;

public sealed class Notifier
{
    public event EventHandler? Fired;
    private int _isRaising;

    public void Fire()
    {
        if (Interlocked.Exchange(ref _isRaising, 1) != 0)
            throw new InvalidOperationException("Reentrant Fire() is not allowed.");

        try
        {
            Fired?.Invoke(this, EventArgs.Empty);
        }
        finally
        {
            Volatile.Write(ref _isRaising, 0);
        }
    }
}
```

This is a strong policy; many designs instead allow reentrancy but ensure invariants hold.

For a deeper treatment of concurrency + reentrancy hazards with events (including raising from thread pool threads and UI thread marshaling), see `10.3. Thread-safety and reentrancy with events`.
