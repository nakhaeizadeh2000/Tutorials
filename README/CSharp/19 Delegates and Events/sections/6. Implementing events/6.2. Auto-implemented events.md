## 6.2. Auto-implemented events (what they mean, and why they’re “default good”)

1. **What the compiler provides** (hidden backing field)
2. **When they’re enough** (most cases)
3. **When they’re not** (custom storage, weak events, synchronization, or instrumentation)

### 1) What the compiler provides
An **auto-implemented event** is the default form:

```csharp
using System;

public sealed class Clock
{
    public event EventHandler? Tick;
}
```

The compiler generates a hidden backing field of the delegate type and emits the standard `add`/`remove` implementations for `+=`/`-=`.

What you get (mentally):
- **Encapsulation**: external code can only subscribe/unsubscribe; it cannot assign `Tick = ...` or invoke it.
- **A multicast delegate field** managed by the runtime.

**Good to know**
- The backing field is typically a `MulticastDelegate` instance (or `null`), replaced on every update because delegates are immutable.
- You still need a method inside the type to raise the event (and decide thread-safety/exception policy).

### 2) When they’re enough (most cases)
Auto events are “default good” because they are:
- **Readable**: idiomatic .NET; low cognitive overhead.
- **Correct-by-default** for typical scenarios: you avoid custom accessor bugs.
- **Low maintenance**: fewer lines, fewer traps, easier refactoring.

Typical use cases:
- Domain model notifications inside a bounded component
- Library events that follow the .NET `EventHandler` pattern
- Internal events in services (with explicit subscription lifetime management; see [10.2](<../10. Performance memory scalability/10.2. Events memory leaks subscription lifetimes.md>))

Raising pattern:

```csharp
using System;

public sealed class Clock
{
    public event EventHandler? Tick;

    public void Pulse() => Tick?.Invoke(this, EventArgs.Empty);
}
```

### 3) When they’re not (and what to do instead)
You need custom accessors when you need *custom subscription semantics* or *custom storage*.

Common reasons:
- **Thread-safety beyond the default**: e.g., you need to coordinate subscriptions with other state transitions.
- **Instrumentation**: track subscriber count, log subscriptions, etc.
- **Bridge to another event source**: subscribe to an underlying object only when you have at least one subscriber.
- **Weak events**: you want subscribers to not be kept alive by the publisher (advanced; see [10.2](<../10. Performance memory scalability/10.2. Events memory leaks subscription lifetimes.md>) for the core leak model and mitigation options).

Preferred modern approach:
- Use **custom `add`/`remove`** only when you can clearly state the invariant and test it. See [6.3](<./6.3. Custom event accessors add remove.md>) for correct patterns and common deadlocks.

**Performance note**
- Auto events are usually fast enough. Over-engineering custom accessors often introduces locks and contention that are worse than the default behavior.
- If you’re in a hot path, the bigger wins usually come from reducing handler churn and avoiding closures/captures (see [10.1](<../10. Performance memory scalability/10.1. Allocation sources captures delegate creation.md>) and [7.2](<../7. Anonymous methods and lambdas/7.2. Captures closures allocations.md>)).
