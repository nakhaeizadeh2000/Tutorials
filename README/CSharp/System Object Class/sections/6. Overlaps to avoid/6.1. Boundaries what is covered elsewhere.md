## 6.1. Boundaries: what is covered elsewhere in this repo

1. **General equality and hashing fundamentals in domain modeling** are covered in `CSharp Basic Object Oriented Programming`
2. **Boxing/unboxing and conversion categories** are covered deeply in `Type Conversion`
3. **Struct-specific boxing/interface pitfalls** are covered in `Structures`
4. **Virtual/override mechanics (language rules)** are covered in `Inheritance and Hiding and Overriding`
5. **Runtime/GC/JIT big picture** is covered in `Fundamental Theories`

Below is the explicit “contract” for this domain, so we keep the tutorial clean and avoid accidental duplication.

### 1) **General equality and hashing fundamentals in domain modeling** are covered in `CSharp Basic Object Oriented Programming`

This System.Object domain focuses on **the mechanics and consequences** of object methods in day-to-day .NET code:

- Why `object.Equals` defaults are rarely your domain intent
- How `ReferenceEquals` fits into correctness debugging
- How *object-typed APIs* can silently steer you into boxing/type checks

For the deep “design a value object/entity equality contract” treatment, see:

- **See** `README/CSharp/CSharp Basic Object Oriented Programming/sections/3. Important points about objects/3.2. Equality hashing and identity in collections.md`

### 2) **Boxing/unboxing and conversion categories** are covered deeply in `Type Conversion`

This domain gives **object-centric** guidance: where boxing enters *because you used `object`*, and how to avoid “object pipelines” in hot paths.

For the full, conversion-focused deep dive (what boxes, unboxing failure rules, and all common traps), see:

- **See** `README/CSharp/Type Conversion/sections/3. Explicit conversions and casts/3.3. Boxing unboxing and hidden allocations.md`

### 3) **Struct-specific boxing/interface pitfalls** are covered in `Structures`

In this System.Object domain you’ll see boxing mentioned as an **object interaction** problem. Struct-specific gotchas (interfaces, `foreach` copies, defensive copies, etc.) should stay in the Structures domain.

- **See** `README/CSharp/Structures/sections/3. Struct vs class/3.3. Boxing interfaces generics.md`

### 4) **Virtual/override mechanics (language rules)** are covered in `Inheritance and Hiding and Overriding`

This domain will show *how overriding object methods behaves* and the design constraints it creates (especially for equality). It does not attempt to re-teach the full language rule set of `virtual/override/new/sealed override`.

- **See** `README/CSharp/Inheritance and Hiding and Overriding/README.md` (then the relevant `sections/6.*`)

### 5) **Runtime/GC/JIT big picture** is covered in `Fundamental Theories`

In this domain we only talk about runtime details when they directly explain **why a certain object-based pattern allocates or becomes slow** (e.g., boxing pressure in tight loops; poor hash distribution).

- **See** `README/CSharp/Fundamental Theories/sections/2. NET architecture/2.3. GC basics for app developers.md`

### Good to know (how to use boundaries as a mentor)

- **If you find yourself writing “the whole story” twice**: keep the deep story in one file and turn the other into a short reminder + a “See …” reference.
- **If a code review argument starts with “but `object` does X”**: this domain is the right place. If it starts with “what is a value object / entity?”: the OOP domain is the right place.
