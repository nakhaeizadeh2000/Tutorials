## 1.2. The actual contract of `object` (what you inherit, always)

### 1) **The 4 methods you must understand** (`Equals`, `GetHashCode`, `ToString`, `GetType`)

These four are the “unavoidable” surface area every .NET developer relies on—directly or indirectly—because they are the glue behind **collections**, **debugging**, **logging**, **diagnostics**, and **runtime type reasoning**.

- **`Equals(object?)`**: defines *equality semantics*. Default (for reference types) is **reference identity** (same instance). Many types override to implement **value equality**.
- **`GetHashCode()`**: supports hash-based lookups (`Dictionary`, `HashSet`) and must be consistent with `Equals`.
- **`ToString()`**: defines a human-readable representation. Default is the fully-qualified type name; many types override.
- **`GetType()`**: returns the runtime type (`System.Type`) for an instance. Not virtual; always gives the exact runtime type.

**Mentor note**

- If you design public types, you’re designing these behaviors whether you touch them or not.
- Bugs in equality/hashing are not “small correctness issues”; they become **data structure corruption** and **performance collapse** under load.

Where they’re treated in depth in this domain:

- See `2.2` for `ToString()`.
- See `2.3` for `Equals` vs `==`.
- See `2.4` for `GetHashCode` and collections.

### 2) **The identity helpers** (`ReferenceEquals`) and cloning primitive (`MemberwiseClone`)

`System.Object` also provides two members that show up in production code in subtle ways:

- **`ReferenceEquals(object? a, object? b)`**:
  - Always checks **reference identity** (do these references point to the same object?) and is not affected by overloaded `==` operators.
  - It’s static and works even when instance `Equals` is overridden.
  - Commonly used as a defensive early-out inside `Equals` implementations.

- **`MemberwiseClone()`**:
  - Protected method that creates a **shallow copy** of the current object.
  - Field-by-field copy: value fields are copied; reference fields still point to the same referenced objects.
  - Useful in narrow scenarios (e.g., internal snapshotting) but often a bad public API (ambiguity: deep vs shallow; versioning; invariants).

**Good to know**

- `ReferenceEquals` can behave surprisingly with value types because boxing creates a new object each time (identity changes). This domain covers the *object-centric consequence* in `2.5` and `5.2`. For a deep boxing/unboxing treatment, see `README/CSharp/Type Conversion/sections/3. Explicit conversions and casts/3.3. Boxing unboxing and hidden allocations.md`.
- `MemberwiseClone` is usually a smell for “we need immutability / with-copy / explicit copy constructor”. See `2.6` for guidance.

### 3) **A mentor mental model** (identity vs value; representation vs meaning)

Think in three layers:

- **Identity**: “which object is this?” (reference equality). This is the default for classes unless you override it.
- **Meaning/value**: “what does it represent?” (value equality). This is what most domain models want for *value objects*.
- **Representation**: “how do humans see it?” (`ToString()`). This should help debugging/logging, not define data formats.

This mental model prevents three common mistakes:

1. **Accidentally using value equality where identity matters** (e.g., entities in caches or unit-of-work patterns).
2. **Accidentally using identity where value equality is expected** (e.g., deduplicating DTOs by reference).
3. **Treating strings as data** (using `ToString()` output as a serialization format).

**Performance note**

- Equality and hashing are on the hot path of many systems: dictionaries, sets, grouping, joins, de-duplication, memoization.
- Design for clarity first, then measure, but treat **hash/equality correctness** as a performance feature.
