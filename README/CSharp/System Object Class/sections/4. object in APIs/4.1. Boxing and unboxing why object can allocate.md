## 4.1. Boxing and unboxing: why `object` can allocate

1. **What boxing is** (value type → object: allocation + copy + type handle)
2. **Unboxing rules** (exact type match; invalid casts; null unboxing behavior)
3. **Hot path rule** (boxing is an allocation; allocations become GC work under load)

**Important boundary (single deep explanation rule).**
Boxing/unboxing is explained in depth in the Type Conversion domain. See `README/CSharp/Type Conversion/sections/3. Explicit conversions and casts/3.3. Boxing unboxing and hidden allocations.md` for the full treatment (examples + traps + performance framing).  
This section focuses on what *changes* when you introduce `object` into APIs and why boxing becomes a production issue there.

### 1) **What boxing is** (value type → object: allocation + copy + type handle)

**Definition**

- **Boxing** occurs when a **value type** (struct, primitive) is converted to `object` (or to a non-generic interface reference) so it can be treated as a reference at runtime.
- Mechanically, the runtime allocates a new object on the managed heap and copies the value into that box.

**Why `object` APIs trigger boxing**

- Any API that takes `object` (or non-generic interfaces like `IComparable`) becomes a boxing magnet when callers pass value types.
- This is often invisible in code reviews because the call site looks “normal”.

**Short example (runnable)**

```csharp
using System;

static class Demo
{
    static void AcceptObject(object value) => Console.WriteLine(value);

    static void Main()
    {
        AcceptObject(123);      // boxes int
        AcceptObject(DateTime.UtcNow); // boxes DateTime
    }
}
```

**Mentor note**

- Boxing is not “evil”. It’s a trade-off: it buys *uniform* APIs at the cost of allocations and weaker static typing.
- In application code, boxing is usually fine when it’s *rare*. It becomes a problem when it’s *systematic* (hot loops, high-throughput logging/telemetry pipelines, object-based “property bag” designs).

### 2) **Unboxing rules** (exact type match; invalid casts; null unboxing behavior)

**What juniors often get wrong**

- Unboxing is not numeric conversion.
- You must unbox to the **exact** value type that was boxed.

**Short example (runnable)**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        object boxed = 1;          // boxed int
        int ok = (int)boxed;       // ok

        try
        {
            long nope = (long)boxed; // InvalidCastException (not a numeric conversion)
        }
        catch (InvalidCastException)
        {
            Console.WriteLine("InvalidCastException");
        }

        object? n = null;
        try
        {
            int alsoNope = (int)n!; // throws (null cannot be unboxed)
        }
        catch (NullReferenceException)
        {
            Console.WriteLine("NullReferenceException");
        }
    }
}
```

**Good to know**

- Prefer pattern matching (`is int i`) over raw casts when the incoming `object` might not be the expected type.
- Prefer designs where the type is known at compile time (generic APIs) so you don’t need unboxing at all.

### 3) **Hot path rule** (boxing is an allocation; allocations become GC work under load)

**Why this matters beyond micro-optimization**

- A single allocation is usually irrelevant.
- Thousands to millions of accidental boxing allocations per second become:
  - increased Gen0 collections,
  - more CPU spent in GC,
  - less throughput and worse tail latencies.

**Practical guidance**

- If the data is strongly typed, use strongly typed APIs (generics, overloads).
- If you truly need heterogeneity (e.g., metadata bags), keep it at *boundaries* and avoid passing `object` through your core logic.

**Performance note**

- Boxing can also remove optimization opportunities by forcing `object`-typed flows: more runtime checks, more virtual dispatch, less inlining/devirtualization potential.
