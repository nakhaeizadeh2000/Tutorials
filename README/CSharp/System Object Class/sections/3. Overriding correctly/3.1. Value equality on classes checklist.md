## 3.1. Value equality on classes: the full checklist

1. **Implement `IEquatable<T>` for performance and correctness**
2. **Respect the equality laws** (reflexive, symmetric, transitive; consistent with hash code)
3. **Avoiding common production bugs** (mutable keys, floating-point edge cases, string comparer choices)

### 1) **Implement `IEquatable<T>` for performance and correctness**

`object.Equals(object?)` is **the universal equality entry point** in .NET, but for your own types it is rarely the best-performing or best-typed way to compare values.

For *value equality* on your own types, the modern “production contract” is:

- `bool IEquatable<T>.Equals(T? other)` for **fast typed comparisons** in generic collections and algorithms
- `override bool Equals(object? obj)` for **polymorphic correctness** (frameworks call this)
- `override int GetHashCode()` for **hash collections** (`Dictionary`, `HashSet`, caches)
- (optional) `==` / `!=` operators if they improve readability, but only if they are consistent

Why `IEquatable<T>` matters:

- **Avoids boxing** for value types used via `object` (and avoids some virtual/interface dispatch costs for classes too).
- **Avoids repeated type checks** and casts in hot paths (collections and algorithms will prefer the typed `Equals`).
- **Clarifies intent**: “this type has value semantics.”

**Minimal, correct pattern (class value object, immutable):**

```csharp
using System;

public sealed class Money : IEquatable<Money>
{
    public string Currency { get; }
    public decimal Amount { get; }

    public Money(string currency, decimal amount)
    {
        Currency = currency ?? throw new ArgumentNullException(nameof(currency));
        Amount = amount;
    }

    public bool Equals(Money? other)
        => other is not null
        && Amount == other.Amount
        && string.Equals(Currency, other.Currency, StringComparison.Ordinal);

    public override bool Equals(object? obj) => obj is Money m && Equals(m);

    public override int GetHashCode()
    {
        // HashCode is optimized and readable for combining fields.
        return HashCode.Combine(
            Amount,
            StringComparer.Ordinal.GetHashCode(Currency));
    }

    public static bool operator ==(Money? left, Money? right) => Equals(left, right);
    public static bool operator !=(Money? left, Money? right) => !Equals(left, right);
}
```

**Mentor note**

- If the type is a *value object*, make it **immutable** (or at least: fields used for equality/hashing must not change).
- If your type is an *entity*, you typically want **identity equality**, not full value equality. That belongs primarily in `CSharp Basic Object Oriented Programming` → equality and hashing section; here we focus on the “object contract” implications.

### 2) **Respect the equality laws** (and keep hash code consistent)

Your equality must obey these laws:

- **Reflexive**: \(x.Equals(x)\) is true (except for NaN-like special cases; see below).
- **Symmetric**: \(x.Equals(y)\) implies \(y.Equals(x)\).
- **Transitive**: \(x.Equals(y)\) and \(y.Equals(z)\) implies \(x.Equals(z)\).
- **Consistent**: result doesn’t change unless the compared state changes.

And the critical hash-law:

- If \(x.Equals(y)\) is true, then \(x.GetHashCode() == y.GetHashCode()\) must be true.

In production, the most common “looks fine until prod” bug is **breaking the hash-law**.

**Bad example (violates hash-law):**

```csharp
public sealed class Bad
{
    public required string Id { get; init; }
    public required string Name { get; init; }

    public override bool Equals(object? obj) => obj is Bad b && b.Id == Id && b.Name == Name;
    public override int GetHashCode() => Id.GetHashCode(); // WRONG: ignores Name
}
```

If `Name` participates in equality, it must participate in hashing too.

**Performance note**

- Hash codes don’t need to be globally unique; they need **good distribution** for your key set.
- A poor hash makes `Dictionary` behave like a linked list (more comparisons, more CPU). That is a real throughput issue.

### 3) **Avoiding common production bugs**

#### **Bug: mutable keys in dictionaries**

If an object’s hash-relevant state changes while it is a key in a dictionary/set, lookups can fail.

Rule of thumb:

- If it can be a key, it must be **effectively immutable** for its entire “key lifetime.”

If you need mutability, use:

- a stable identifier as the key (e.g., `CustomerId`)
- or store keys separately from mutable payloads

#### **Bug: floating-point equality**

If your equality includes `double`/`float`, be explicit:

- If values are persisted and compared as exact bits, exact equality is fine.
- If values are computed, tolerance-based comparisons might be required (domain-specific), but then:
  - your equality may no longer be transitive
  - hash-based collections may become inappropriate

In other words: **tolerance-based equality is usually not a good “object equality”**.

#### **Bug: string comparison defaults**

Decide if comparisons are:

- `StringComparison.Ordinal` / `OrdinalIgnoreCase` (typical for IDs, keys, protocols)
- culture-aware (rare for identity; more for UI sorting/display)

Also decide which comparer `Dictionary<string, ...>` uses (`StringComparer.Ordinal` vs ignore-case).

#### **Bug: inheritance + equality**

Equality over inheritance hierarchies is tricky and can break transitivity.

See section **3.2** in this domain for the “hard corner” and recommended strategies.
