## 2.2. `ToString()` as a debugging contract (not a serialization format)

1. **What good `ToString()` means** (stable, readable, non-throwing; safe around nulls/partially-built state)
2. **Avoiding accidental allocations** (hot-path logging; structured logging; avoid building strings you won’t emit)
3. **Modern guidance** (`ISpanFormattable`, `TryFormat`, interpolated string handlers, and when not to use them)

### 1) **What good `ToString()` means** (stable, readable, non-throwing; safe around nulls/partially-built state)

**Definition and intent**

`ToString()` is the universal “human-readable representation” hook on `object`. In real production code, it is used for:

- **Debugging** (watch windows, dumps, traces)
- **Diagnostics** (structured logs sometimes call it; exception messages sometimes include it)
- **Quick inspection** during local development

It is *not* a reliable serialization contract. Treating it like one creates versioning bugs and security/PII leaks.

**Mentor rules for a good `ToString()`**

- **Must not throw**. If `ToString()` can throw, it can bring down logging, exception formatting, debugger views, or telemetry pipelines—often in the worst possible moment.
- **Should be stable enough for debugging**. You can change it, but don’t make it random noise. Prefer deterministic fields.
- **Must not expose secrets/PII** by default. Redact tokens, passwords, auth headers, personal data. If the type might contain sensitive data, `ToString()` should either omit it or include a safe placeholder.
- **Prefer a small, unambiguous format**. “TypeName { Key = … }” is usually better than a prose paragraph.

**Example: safe debugging string**

```csharp
using System;

public sealed class SessionInfo
{
    public required string UserId { get; init; }
    public required string AccessToken { get; init; } // sensitive
    public DateTimeOffset ExpiresAt { get; init; }

    public override string ToString()
        => $"SessionInfo {{ UserId = {UserId}, ExpiresAt = {ExpiresAt:O}, AccessToken = <redacted> }}";
}
```

**Good to know**

- For *domain* types, prefer representing **meaningful identity** (IDs, key fields) rather than dumping entire graphs.
- For mutable types, ensure `ToString()` handles partially-initialized objects (including during construction or after disposal).

### 2) **Avoiding accidental allocations** (hot-path logging; structured logging; avoid building strings you won’t emit)

**The problem**

Formatting strings allocates. Sometimes it’s fine; sometimes it becomes one of the top allocations in profiling.

Common allocation sources:

- **Interpolated strings** (build a new string)
- **Composite formatting** (`string.Format`, `Console.WriteLine("x={0}", x)`) (can allocate arrays and box)
- **LINQ in `ToString()`** (allocations + hidden iterators)
- **Large object graph traversal** (CPU + allocations + potential recursion)

**Mentor framing**

- If `ToString()` is used in **rare paths**, optimize for clarity.
- If it’s used in **hot paths** (high-frequency logging, telemetry, or tight loops), you must treat it like any other performance-sensitive method.

**Prefer structured logging over manual string building (when available)**

Most modern logging frameworks (e.g., `Microsoft.Extensions.Logging`) support message templates that can defer formatting and avoid work when a log level is disabled. The exact APIs depend on your stack, so keep this domain focused on `ToString()` behavior.

**Performance note**

- If you see unexplained allocations, look for `ToString()` calls in logs/diagnostics and check if they’re executed even when the message won’t be emitted.
- Avoid building “pretty” strings from large collections inside `ToString()`—especially for types that can appear in exceptions or logs frequently.

### 3) **Modern guidance** (`ISpanFormattable`, `TryFormat`, interpolated string handlers, and when not to use them)

**When you should care**

If you are formatting **high-volume numeric/date/ID values**, modern .NET provides APIs to reduce allocations by formatting into a span/buffer.

Key APIs/patterns:

- **`ISpanFormattable`**: types that can format into `Span<char>`
- **`TryFormat`** pattern: “write into buffer, return success”
- **Interpolated string handlers**: enable *some* frameworks to skip formatting work when not needed

**Practical guidance**

- Don’t contort `ToString()` for micro-optimizations. `ToString()` by definition returns a `string`, so it will allocate the returned string anyway.
- Use span-based formatting when you control the *call site* (e.g., writing to buffers, serializers, high-performance log sinks), not inside a normal `ToString()` that returns `string`.
