## 2.5. `ReferenceEquals` and identity checks (when identity is the bug)

1. **Why it exists** (bypass overloaded equality and compare identity)
2. **When you actually use it** (defensive checks in `Equals`, cycles, caches, flyweights, interning scenarios)
3. **Pitfalls** (boxing changes identity for value types; don’t use it as a general “equals” substitute)

### 1) **Why it exists** (bypass overloaded equality and compare identity)

`object.ReferenceEquals(object? a, object? b)` answers a single question:

- **Do `a` and `b` refer to the exact same object instance?**

It is intentionally **not** affected by:

- `operator ==` overloads
- `Equals` overrides
- custom equality comparers

That makes it the “escape hatch” when you need to talk about **identity**, not **value**.

**Good to know**

- For reference types, `ReferenceEquals(a, b)` is essentially the same as `a is b` (same identity) but more explicit about intent.
- For value types, arguments are converted to `object`, which **boxes** them. That has two important consequences:
  - a boxing allocation can occur
  - the identity you test is the identity of the **box object**, not the original value (see pitfalls)

### 2) **When you actually use it** (defensive checks in `Equals`, cycles, caches, flyweights, interning scenarios)

#### **A) Fast “same instance” path in `Equals`**

For reference types implementing value equality, a typical first line is:

```csharp
public sealed class Person : IEquatable<Person>
{
    public required string NationalId { get; init; }
    public required string Name { get; init; }

    public bool Equals(Person? other)
    {
        if (ReferenceEquals(this, other)) return true;
        if (other is null) return false;

        return NationalId == other.NationalId;
    }

    public override bool Equals(object? obj) => obj is Person p && Equals(p);

    public override int GetHashCode() => StringComparer.Ordinal.GetHashCode(NationalId);
}
```

This:

- avoids work when comparing an instance to itself
- can help in object graphs where the same instance appears multiple times

#### **B) Cycle detection / graph algorithms**

When traversing graphs with potential cycles, identity is often the correct “visited” key:

```csharp
using System.Collections.Generic;
using System.Runtime.CompilerServices;

static bool HasCycle(object root)
{
    var visited = new HashSet<object>(ReferenceEqualityComparer.Instance);
    return Dfs(root, visited);

    static bool Dfs(object node, HashSet<object> visited)
    {
        if (!visited.Add(node)) return true; // same instance seen again
        // ... traverse references from node ...
        return false;
    }
}
```

**Mentor note**: don’t use “value equality” for cycle detection unless you *really* mean “same value shape”, because it can explode in cost and can be incorrect if equality is domain-specific.

#### **C) Caches, flyweights, interning**

If you implement or use caching patterns (e.g., string interning, object pools, identity maps), identity checks are the correct tool.

### 3) **Pitfalls** (boxing changes identity for value types; don’t use it as a general “equals” substitute)

#### **Pitfall: boxing means “identity of the box”, not identity of the value**

```csharp
object a = 42;   // boxes int
object b = 42;   // boxes another int

Console.WriteLine(ReferenceEquals(a, b)); // False
Console.WriteLine(a.Equals(b));           // True (value equality for boxed ints)
```

This surprises people because the values are equal, but the boxes are different objects.

#### **Pitfall: using ReferenceEquals as “a safe Equals”**

`ReferenceEquals` does **not** mean “equal” for value objects. It is an identity tool.

If you need value equality:

- for your own types, implement equality correctly (`IEquatable<T>`, `Equals`, `GetHashCode`)
- for general-purpose comparisons, use `EqualityComparer<T>.Default` / `object.Equals(a, b)` depending on type

#### **Performance note**

- Identity checks are constant-time, but don’t introduce `ReferenceEquals` into hot paths that are already strongly typed if it reduces clarity.
- Avoid calling `ReferenceEquals` on value types (it forces boxing) — if you have a value type, compare values, not identity.
