## 2.4. `GetHashCode()` and hash-based collections (the “don’t break dictionaries” rule)

1. **Stability requirement** (hash codes must not change while an object is a key in a hash-based collection)
2. **Good composition** (`HashCode` helper; avoid home-grown mixing unless you have a proven need)
3. **Performance reality** (poor hash distribution destroys performance; a correct hash is a throughput feature)

### 1) **Stability requirement** (hash codes must not change while an object is a key in a hash-based collection)

**Definition**

`GetHashCode()` returns an `int` that a hash-based collection uses to choose a bucket. The **only hard rule** you must respect:

- If `x.Equals(y)` is `true`, then `x.GetHashCode()` **must equal** `y.GetHashCode()`.

And for hash-based collections to behave correctly:

- The hash code of a key must be **stable while that instance is used as a key**.

If you violate stability, you don’t just “get worse performance” — you can get **broken lookups** that look like data corruption.

**Example: the classic production bug (mutable key)**

```csharp
using System;
using System.Collections.Generic;

sealed class MutableKey
{
    public int Id { get; set; }

    public override bool Equals(object? obj) => obj is MutableKey other && other.Id == Id;
    public override int GetHashCode() => Id;
}

static class Demo
{
    static void Main()
    {
        var dict = new Dictionary<MutableKey, string>();

        var k = new MutableKey { Id = 1 };
        dict[k] = "hello";

        k.Id = 2; // BUG: key changed after insertion

        Console.WriteLine(dict.ContainsKey(k)); // false (often)
    }
}
```

**Mentor rule**: if a type can be a key, make the key fields **immutable** (or ensure the object is never mutated while stored as a key).

**Good to know**

- Hash codes **do not need to be unique**.
- Hash codes **can change between process runs** (and that’s okay). Don’t persist them.

### 2) **Good composition** (`HashCode` helper; avoid home-grown mixing unless you have a proven need)

**Modern guidance**

In modern .NET, prefer:

- `System.HashCode` for combining multiple fields
- `EqualityComparer<T>.Default` for nested fields (respects custom equality)

**Example: `HashCode` for a value-based class**

```csharp
using System;

sealed class Money : IEquatable<Money>
{
    public string Currency { get; }
    public decimal Amount { get; }

    public Money(string currency, decimal amount)
    {
        Currency = currency;
        Amount = amount;
    }

    public bool Equals(Money? other)
        => other is not null
           && Amount == other.Amount
           && string.Equals(Currency, other.Currency, StringComparison.Ordinal);

    public override bool Equals(object? obj) => obj is Money other && Equals(other);

    public override int GetHashCode()
        => HashCode.Combine(
            StringComparer.Ordinal.GetHashCode(Currency),
            Amount);
}
```

**Why `StringComparer` matters**

If your equality uses a specific string comparison (e.g., `OrdinalIgnoreCase`), your hashing must use the **same comparer** or you break the equality/hash contract.

**Legacy patterns to avoid**

- Hand-rolled “prime number mixing” copied from old blog posts.
- Using `ToString()` to build hash codes (allocations + culture pitfalls + inconsistent semantics).

### 3) **Performance reality** (poor hash distribution destroys performance; a correct hash is a throughput feature)

**Big picture**

Hash tables are fast when:

- Hash computation is cheap, and
- Keys distribute well across buckets.

Bad hashing can degrade lookups toward \(O(n)\) behavior under collisions, and in real services that becomes **CPU + latency**.

**Performance notes**

- Don’t micro-optimize hashing before correctness. A wrong hash is a correctness bug.
- If the type is hot (e.g., used in `Dictionary` millions of times/sec), measure with a profiler. Sometimes:
  - computing hash from large strings dominates, or
  - deep equality dominates, and your fix is to **change the key shape** (use an ID, intern strings, pre-normalize, etc.).

**Good to know**

- `Dictionary<TKey, TValue>` uses the key’s `GetHashCode()` and `Equals()`. If you supply a custom comparer, it uses the comparer’s hash/equality instead. Choose comparers intentionally for correctness (culture vs ordinal) and performance.
