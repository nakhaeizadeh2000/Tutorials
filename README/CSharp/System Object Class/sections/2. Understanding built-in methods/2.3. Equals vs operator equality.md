## 2.3. `Equals(object?)` vs `==` (and why they often mean different things)

1. **Reference equality vs value equality** (what default `object.Equals` does and what `==` does by default)
2. **Operator overloading rules** (consistency requirements: if you overload `==`, also implement `Equals`/`GetHashCode`)
3. **Nullability and correctness** (`object?`, `T?`, and avoiding NullReferenceException in equality code)

### 1) **Reference equality vs value equality** (default behavior)

`System.Object` supports *both* concepts, but it does not unify them:

- **Reference identity**: “Are these the *same instance*?”  
  Use `ReferenceEquals(a, b)` (or `object.ReferenceEquals(a, b)`).
- **Value equality**: “Do these represent the *same value* for my domain?”  
  Use `a.Equals(b)` once the type has a correct equality implementation.

**Default behavior (when you do nothing)**

- For most **classes**, `object.Equals` is **reference equality** (same instance).
- For most **structs**, `ValueType.Equals` performs **field-by-field value equality** via reflection-ish mechanisms unless the runtime can optimize; many structs override/implement faster equality.

**`==` is not “the same thing as `Equals`”**

- If you do not overload it, `==` for **classes** is typically **reference equality**.
- Many BCL types *do* overload `==` to mean **value equality** (e.g., `string`), and records generate value-based equality operators.

**Mentor rule**

- Decide early whether the type is an **entity (identity)** or a **value object (value)**. Mixing both is a long-term bug factory.
- Prefer to keep “value equality” **stable and immutable** (or at least stable while used as a key).

**Example (runnable): identity vs value**

```csharp
using System;

sealed class Person // entity-like (identity)
{
    public Guid Id { get; } = Guid.NewGuid();
}

sealed class Money : IEquatable<Money> // value object
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency)
        => (Amount, Currency) = (amount, currency);

    public bool Equals(Money? other)
        => other is not null && Amount == other.Amount && Currency == other.Currency;

    public override bool Equals(object? obj) => obj is Money m && Equals(m);
    public override int GetHashCode() => HashCode.Combine(Amount, Currency);

    public static bool operator ==(Money? left, Money? right) => Equals(left, right);
    public static bool operator !=(Money? left, Money? right) => !Equals(left, right);
}

static class Demo
{
    static void Main()
    {
        var p1 = new Person();
        var p2 = new Person();
        Console.WriteLine(p1 == p2);                       // False (identity)

        var m1 = new Money(10m, "USD");
        var m2 = new Money(10m, "USD");
        Console.WriteLine(m1 == m2);                       // True (value)
        Console.WriteLine(ReferenceEquals(m1, m2));        // False (different instances)
    }
}
```

### 2) **Operator overloading rules** (consistency requirements)

If you overload `==`/`!=`, you are declaring that callers can use operators as a readable equality surface. That comes with obligations:

- **Consistency**: `x == y` must imply `x.Equals(y)` and `x.GetHashCode() == y.GetHashCode()` (for hash-based collections).
- **Null-safety**: `==` should behave sensibly when one or both operands are null.
- **No surprises**: avoid overloading `==` for types where identity semantics are expected (typical entity types).

**Good to know**

- Records generate correct `==`/`!=`, `Equals`, and `GetHashCode` for you *when* their “all members participate” semantics match your domain. If you need custom semantics, be explicit.

### 3) **Nullability and correctness** (avoid NullReferenceException)

Modern C# equality code should be written with nullable reference types in mind:

- Use `object?` in `Equals(object? obj)` (the signature already is, conceptually).
- Prefer pattern matching: `obj is T other && Equals(other)` rather than raw casts.
- In `==` operators, delegate to `Equals(left, right)` to get correct null handling.

**Common mistakes**

- Implementing `Equals` but forgetting to update `GetHashCode` → breaks `Dictionary`/`HashSet` behavior.
- Making equality depend on mutable state → collections and caches behave “randomly”.
- Using `ReferenceEquals` as “the real equality” after overloading `==` → you end up with two truths.

**Performance note**

- Implementing `IEquatable<T>` avoids boxing and virtual dispatch in generic collections; it’s a correctness + performance win for value equality types.
