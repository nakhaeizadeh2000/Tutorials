## 2.1. `GetType()` and runtime type identity

1. **Exact runtime type** (what it returns, why it’s not virtual, and what that implies)
2. **Avoiding type-check chains** (prefer polymorphism, pattern matching, or data-driven dispatch)
3. **Performance notes** (reflection can be expensive; cache where it’s a real hotspot, not by habit)

### 1) **Exact runtime type** (what it returns, why it’s not virtual, and what that implies)

**Definition**

- `object.GetType()` returns the **exact runtime type** (`System.Type`) of the instance.
- It is effectively a **runtime identity query**. You can think of it as “what the CLR says this object *really is* right now”.

**Why it’s not virtual (and why you should be glad)**

- If `GetType()` were virtual, a derived type could lie about its runtime type, which would break:
  - reflection and diagnostics
  - serializers and mappers
  - type-based caches
  - security checks and policy code
- `GetType()` being non-virtual is part of the “you can trust the runtime” contract.

**Common uses**

- Defensive programming in infrastructure code (logging, diagnostics, debugging, generic helpers).
- Building error messages that include the concrete type.
- Implementing some forms of equality in inheritance hierarchies (see note below).

**Important nuance**

- `GetType()` is about **runtime type**, not **static compile-time type**.

```csharp
object o = "hello";
Console.WriteLine(o.GetType().FullName); // System.String
```

**Good to know**

- Prefer `typeof(T)` when you already know the type at compile time; it avoids a virtual-like call on an instance and is clearer.

```csharp
Console.WriteLine(typeof(string).FullName); // System.String
```

### 2) **Avoiding type-check chains** (prefer polymorphism, pattern matching, or data-driven dispatch)

Type-check chains often appear as:

```csharp
// Smell: type-switch in “core logic”
if (obj is Foo) { ... }
else if (obj is Bar) { ... }
else if (obj is Baz) { ... }
```

They are sometimes necessary at **boundaries** (deserialization, message routing, interop), but they’re usually a design smell **inside** your core domain logic.

**Better options (in order of preference)**

- **Polymorphism**: let each type implement the behavior.
- **Pattern matching** (modern C#): fine at boundaries or in orchestrators.
- **Data-driven dispatch**: a dictionary from type → handler, or a visitor-like pattern, when you truly need external routing.

**Example: boundary routing with pattern matching**

```csharp
static string Describe(object value) => value switch
{
    null => "<null>",
    int i => $"int:{i}",
    string s => $"string:\"{s}\"",
    DateTime dt => $"datetime:{dt:O}",
    _ => $"{value.GetType().Name}:{value}"
};
```

**Mentor warning**

- If a type-switch keeps growing, it’s telling you the system wants:
  - a new abstraction (interface/base type)
  - a stable discriminant (an enum / “kind” property)
  - or that you’re modeling “variants” and should consider a discriminated-union style design (often `record` hierarchies + `switch`, or a dedicated sum-type library).

### 3) **Performance notes** (reflection can be expensive; cache where it’s a real hotspot, not by habit)

**Is `GetType()` “reflection”?**

- `GetType()` itself is cheap: it returns a `Type` object the runtime already has.
- What becomes expensive is **what you do next**, such as:
  - scanning attributes
  - enumerating properties/methods
  - dynamically invoking members
  - building expression trees / dynamic methods

**Performance note**

- Don’t pre-cache `GetType()` results “because performance”. Cache only if profiling shows it matters.
- If you are doing repeated reflection, consider **source generation** (modern .NET) to move work to compile time.
