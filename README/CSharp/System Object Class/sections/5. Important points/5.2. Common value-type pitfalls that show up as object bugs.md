## 5.2. Common struct/value-type pitfalls that show up as `object` bugs

1. **Boxing changes identity** (two boxes of the same value are different objects)
2. **Interface calls can box** (non-generic interfaces + structs)
3. **Accidental boxing in logging/formatting** (especially with `params` and object-based APIs)

### 1) **Boxing changes identity** (two boxes of the same value are different objects)

**What this means**

When you box a value type, the runtime allocates a *new* object containing a *copy* of the value. Two separate boxing operations therefore create two separate objects, even if the original values are equal.

That’s why this surprises people:

- `Equals` may return `true` (value equality)
- but `ReferenceEquals` will return `false` (different boxes, different identities)

**Runnable example**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        int x = 42;

        object a = x;   // boxes: allocates object #1
        object b = x;   // boxes: allocates object #2

        Console.WriteLine(a.Equals(b));                 // True (int.Equals compares values)
        Console.WriteLine(ReferenceEquals(a, b));       // False (different boxes)
    }
}
```

**Mentor pitfall**

- If you put boxed values into an identity-based cache (keyed by object reference), you can accidentally explode the cache with duplicates that “look equal”.
- If you rely on `object` identity as a stand-in for “uniqueness”, boxing breaks that assumption immediately.

**Good to know**

- `ReferenceEquals` is meaningful for **reference types**. For value types it’s usually a smell unless you’re explicitly reasoning about boxing.
- For full boxing/unboxing mechanics and the broader list of triggers, see `README/CSharp/Type Conversion/sections/3. Explicit conversions and casts/3.3. Boxing unboxing and hidden allocations.md`.

### 2) **Interface calls can box** (non-generic interfaces + structs)

**The rule**

If a struct is converted to an **interface type** (or `object`), it boxes unless the compiler/runtime can keep the call generic and constrained.

Common boxing sources:

- Passing a struct to a method taking a non-generic interface (e.g., `IComparable`, `IFormattable`)
- Storing structs in non-generic collections or interface-typed fields

**Runnable example**

```csharp
using System;

static class Demo
{
    static void PrintComparable(IComparable c) => Console.WriteLine(c.CompareTo(c));

    static void Main()
    {
        int x = 123;
        PrintComparable(x); // boxes (int -> IComparable)
    }
}
```

**Modern replacement**

Prefer generic/constrained forms:

- `IComparable<T>`, `IEquatable<T>`
- generic algorithms that accept `T` and (when needed) `where T : IComparable<T>`

**Performance note**

In tight loops, interface-boxing can be “death by a thousand allocations” (GC churn + lost devirtualization opportunities). In non-hot code, it’s usually irrelevant—don’t cargo-cult.

### 3) **Accidental boxing in logging/formatting** (especially with `params` and object-based APIs)

**The trap**

Many formatting/logging APIs accept `params object[]`. Passing value types:

- boxes each value type argument
- allocates the `object[]` array itself

**Runnable example**

```csharp
using System;

static class Demo
{
    static void Main()
    {
        int x = 5;
        Console.WriteLine("x = {0}", x); // boxes x + allocates object[]
    }
}
```

**Modern guidance**

- Prefer **structured logging** (framework-dependent) so formatting can be deferred and typed fields can remain typed.
- Prefer **generic APIs** for hot paths; avoid “object pipelines”.
- Don’t obsess about allocations in cold paths (startup, one-off diagnostics). Do care in high-volume telemetry/logging loops.

**Good to know**

Modern .NET supports **interpolated string handlers** that can avoid work when logging is disabled, but the exact APIs depend on your logging stack. This tutorial keeps that deep dive out of the `System.Object` domain to avoid duplication.
