## 6.1. Interview Q&A: GC generations, allocations, LOH, and pinning

1. **Explain Gen0/1/2 and promotion** (and what causes Gen2 pressure)
2. **What is the LOH and why do we care?** (fragmentation, large buffers, pooling)
3. **What is pinning?** (why it hurts compaction and increases GC work)

### 1) **Explain Gen0/1/2 and promotion**
**High-quality answer (what interviewers want)**
- .NET uses a **generational GC**: most allocations die quickly, so the runtime collects **Gen0** frequently and cheaply, promoting survivors to **Gen1** and then **Gen2**.
- **Promotion** is the real “tax”: once objects live long enough to become Gen2, they get scanned in more expensive collections, increasing CPU and pause-time risk.

**When Gen2 pressure happens**
- **Long-lived references**: caches, static fields, singleton services retaining big graphs.
- **Backpressure / slow consumers**: queues or buffers growing, keeping data alive.
- **Finalizable objects**: objects with finalizers survive at least one extra GC cycle (full treatment: see section **2.1** and **2.3** in this domain).

**Trade-offs / clarity**
- Gen0 allocations can be “cheap” individually, but **high allocation rate** can still dominate CPU.
- Optimizing for “zero Gen0” is usually wrong. Optimizing for **low promotion and healthy working set** is usually right.

**Common mistakes**
- “Gen2 GC happened, so the GC is bad.” Usually it’s your **lifetime graph**.
- Using `GC.Collect()` as a “fix” (it’s a global STW event and typically worsens tail latency).

### 2) **What is the LOH and why do we care?**
**High-quality answer**
- The **Large Object Heap (LOH)** is where **large allocations** (typically large arrays/buffers) go.
- The LOH matters because large allocations can increase **working set**, and LOH can become **fragmented**, which can increase memory usage and GC cost.

**When it shows up**
- Large `byte[]`/`char[]` buffers for serialization, compression, image processing, file/network I/O.
- “Accidental big arrays”: `ToArray()` on large sequences, materializing huge JSON payloads, etc.

**Trade-offs and mitigation**
- **Pooling** (`ArrayPool<T>`, `MemoryPool<T>`) can reduce LOH churn but may increase memory retention and bug risk (use-after-return).
- Prefer **streaming** over materializing big buffers when possible (e.g., stream JSON, stream network reads).

### 3) **What is pinning?**
**High-quality answer**
- **Pinning** prevents the GC from moving an object during compaction. This is required for some interop/I/O scenarios, but it reduces the GC’s ability to compact memory and can increase fragmentation and GC work.

**Where pinning commonly comes from**
- Interop (`fixed`, P/Invoke, native APIs needing stable pointers).
- Long-lived pinned buffers (e.g., “pin this forever for performance”).
- Some high-perf I/O patterns that use pinned buffers (rarely needed at app level).

**Trade-offs**
- Short, well-scoped pinning is often fine; **long-lived pinning** is the typical problem.
- Pinning interacts badly with large objects and LOH behavior.
