## 6.2. Interview Q&A: finalizers/destructors and `GC.SuppressFinalize`

1. **What does a destructor do in C#?** (finalizer semantics + thread + timing)
2. **Why are finalizers expensive?** (queue + longer lifetimes + extra collections)
3. **When do you call `GC.SuppressFinalize`?** (only when you have a finalizer and you cleaned up)

### 1) **What does a destructor do in C#?**
**Answer (what interviewers want)**
- A C# “destructor” (`~TypeName()`) is **syntax for a finalizer**. It does **not** run deterministically when an object goes out of scope.
- The runtime schedules finalizers on a dedicated **finalizer thread** sometime **after** the object becomes unreachable.
- Finalizers are intended as a **last-resort safety net** for unmanaged resources, not a normal cleanup mechanism.

**Key details (be precise)**
- You cannot predict **when** (or even if) a finalizer runs:
  - It runs after at least one GC notices the object is unreachable and moves it through the finalization pipeline.
  - Process termination can skip finalizers; crashes will skip them; time constraints can skip them.
- Finalizers run without your synchronization context and should be assumed to run **concurrently** with other application code.

**Common mistakes (what to say you avoid)**
- Putting business logic or I/O in a finalizer.
- Assuming ordering between finalizers of different objects.
- Assuming finalizer = `Dispose` (it’s not; it’s non-deterministic).

### 2) **Why are finalizers expensive?**
**Answer**
- Finalizable objects create extra GC work and **delay reclamation**:
  - They must be tracked for finalization.
  - They often survive longer (at least until finalization runs), increasing promotion pressure and Gen2 impact.
- They add work to the finalizer thread, which can become a bottleneck under load.

**What to emphasize**
- The cost is not just CPU; it’s **tail latency** and **resource pressure** (handles/sockets) because cleanup is delayed.

### 3) **When do you call `GC.SuppressFinalize`?**
**Answer (rule)**
- Call `GC.SuppressFinalize(this)` **only if your type has a finalizer** (directly or via base type) and you have already cleaned up the unmanaged resource deterministically in `Dispose`.

**Why**
- It removes the object from the finalization pipeline, preventing the finalizer from running later and saving work.

**Minimal correct pattern (sync dispose with a finalizer)**

```csharp
using System;
using System.Runtime.InteropServices;

public sealed class NativeBuffer : IDisposable
{
    private nint _ptr; // unmanaged memory pointer (example only)

    public NativeBuffer(int bytes)
    {
        if (bytes <= 0) throw new ArgumentOutOfRangeException(nameof(bytes));
        _ptr = Marshal.AllocHGlobal(bytes);
    }

    ~NativeBuffer()
    {
        // Finalizer: last resort safety net.
        FreeUnmanaged();
    }

    public void Dispose()
    {
        FreeUnmanaged();
        GC.SuppressFinalize(this);
    }

    private void FreeUnmanaged()
    {
        var ptr = _ptr;
        if (ptr == 0) return;
        _ptr = 0;
        Marshal.FreeHGlobal(ptr);
    }
}
```

**Mentor note**
- In real code, prefer `SafeHandle` (or types that already use it) over writing your own finalizer + pointer logic.
