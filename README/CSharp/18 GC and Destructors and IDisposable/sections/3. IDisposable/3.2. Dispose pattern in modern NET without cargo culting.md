## 3.2. The dispose pattern in modern .NET (without cargo-culting)

1. **Most types don’t need finalizers** (managed-only: implement `IDisposable` without finalizer)
2. **If you have a finalizer** (use `Dispose(bool)` + `GC.SuppressFinalize(this)` correctly)
3. **Prefer `SafeHandle`** for native handles (avoid writing your own fragile finalizer logic)

### 1) **Most types don’t need finalizers**
**Definition**
- A finalizer (`~Type()`) is a **non-deterministic** cleanup hook. Adding one makes the object **finalizable**, which changes its lifetime and GC behavior.
- Many types need deterministic cleanup, but **do not need a finalizer**. If your type owns only managed disposables, implement `IDisposable` and dispose those dependencies.

**When to use**
- Use **`IDisposable` without a finalizer** when you own:
  - other `IDisposable` objects (streams, timers, CTS, pooled buffers)
  - managed memory that should be returned to a pool deterministically
- Do **not** add a finalizer “just in case”. That moves you into the “finalization queue” pipeline and harms performance.

**Common mistakes**
- **Cargo-culting the old full pattern** (`Dispose(bool)`, finalizer, etc.) for every type, even when there is no unmanaged resource.
- Doing meaningful work in `Dispose()` that can throw, block, or run user callbacks unexpectedly.

**Modern minimal pattern (managed-only)**

```csharp
using System;
using System.Threading;

public sealed class Poller : IDisposable
{
    private readonly PeriodicTimer _timer = new(TimeSpan.FromSeconds(1));
    private bool _disposed;

    public void Dispose()
    {
        if (_disposed) return;
        _disposed = true;
        _timer.Dispose();
    }
}
```

**Good to know**
- Whether `Dispose()` must be thread-safe depends on your type’s contract. If multiple threads can call `Dispose()`, guard with `Interlocked` or a lock. Don’t guess—document it.

**Performance note**
- Finalizable objects are more expensive: they typically survive at least one GC and require extra bookkeeping. If you don’t need a finalizer, don’t pay the tax. (The pipeline is explained in depth in [2.1](<../2. Destructors and Finalizers/2.1. Destructor syntax vs runtime finalization queue.md>).)

### 2) **If you have a finalizer (use the pattern correctly)**
**When you actually need this**
- You need this when your type owns a **native resource** that *must* be released eventually even if the consumer forgets to call `Dispose()`.
- In modern .NET, that usually means you should wrap the native handle in a `SafeHandle` instead (see item 3). If you truly can’t, you must implement the pattern carefully.

**Correctness requirements**
- `Dispose()` must be **idempotent**: safe to call multiple times.
- `Dispose()` must release resources deterministically and then call `GC.SuppressFinalize(this)` to prevent the finalizer from running.
- The finalizer must do the minimum necessary to free unmanaged resources and must never depend on other managed objects being alive.

**Canonical pattern (only when you have a finalizer)**

```csharp
using System;
using System.Threading;

public sealed class NativeBufferOwner : IDisposable
{
    private IntPtr _ptr; // pretend this is native memory from a C library
    private int _disposed; // 0 = false, 1 = true

    public NativeBufferOwner(int bytes)
    {
        // Example only. Prefer SafeHandle or NativeMemory APIs when appropriate.
        _ptr = System.Runtime.InteropServices.Marshal.AllocHGlobal(bytes);
    }

    ~NativeBufferOwner() => Dispose(disposing: false);

    public void Dispose()
    {
        Dispose(disposing: true);
        GC.SuppressFinalize(this);
    }

    private void Dispose(bool disposing)
    {
        if (Interlocked.Exchange(ref _disposed, 1) != 0) return;

        // If disposing == true, you may dispose managed state here.
        // If disposing == false, you must NOT touch other managed objects (they may already be finalized).

        if (_ptr != IntPtr.Zero)
        {
            System.Runtime.InteropServices.Marshal.FreeHGlobal(_ptr);
            _ptr = IntPtr.Zero;
        }
    }
}
```

**Common mistakes**
- Calling `GC.SuppressFinalize` even though the type has no finalizer (it’s harmless but signals confusion).
- Making the finalizer call into managed components (logging, events, shared services). Finalizers run on a special thread and must be minimal.
- Throwing from `Dispose()` or finalizer. `Dispose()` should not throw in normal circumstances; finalizers should never throw.

**Good to know**
- You cannot rely on finalizers to run promptly (or at all during abnormal termination). If correctness depends on timely release, you must use `Dispose()`.

### 3) **Prefer `SafeHandle` for native handles**
**Why `SafeHandle` is the modern default**
- `SafeHandle` encapsulates the hard parts:
  - critical finalization correctness
  - handle release reliability
  - reduces the chance of writing a broken finalizer

**When to use**
- If you wrap OS handles (file handles, registry keys, tokens, etc.) or a native library handle, prefer a `SafeHandle` derived type provided by the BCL or generate one.

**Minimal usage example**

```csharp
using Microsoft.Win32.SafeHandles;
using System;
using System.IO;

public static void Example()
{
    // FileStream already uses SafeHandle internally; this is here to show the idea:
    using var fs = new FileStream("data.bin", FileMode.OpenOrCreate, FileAccess.ReadWrite, FileShare.None);
    SafeFileHandle handle = fs.SafeFileHandle;

    // You usually do not need to interact with SafeHandle directly unless you interop.
    Console.WriteLine(handle.IsInvalid);
}
```

**Legacy patterns to avoid**
- Hand-rolled finalizers that call `CloseHandle`/`free` directly without SafeHandle.
- “Dispose pattern templates” copied blindly from old blog posts targeting .NET Framework.
