## 1.1. The GC’s job: managed memory reachability, not “resource cleanup”

1. **Reachability and object graphs** (roots, references, cycles, “leaks” as unintended reachability)
2. **Memory vs resources** (handles/sockets/native memory are not freed by “waiting for GC”)
3. **Performance framing** (allocation rate, survival rate, working set; avoid superstition—measure)

### 1) **Reachability and object graphs**
**Definition**
- The .NET GC is a **tracing, generational garbage collector** for **managed memory**. It decides what memory can be reclaimed by walking the **object graph** starting from **GC roots** and marking what is **reachable**.
- If an object is reachable from any root, it is considered **alive**, even if you “don’t need it anymore”.

**What are “roots” (practically)?**
- **Thread stacks** (locals/parameters currently referenced)
- **Static fields** (process lifetime unless cleared)
- **GC handles** (e.g., created by runtime/interop/frameworks)
- **Finalization** references (finalizable objects have special reachability behavior; see section **2.1** for the deep model)

**Key mental model**
- A “memory leak” in managed code is usually not “GC failed”.
- It is usually **unintended reachability**: something is still holding a reference (often indirectly).

**Common leak shapes (high-signal)**
- **Events**: publisher keeps subscribers alive (delegate list holds references).
- **Timers**: callback delegates/closures capture services; timer lives longer than you think.
- **Caches**: static/unbounded dictionaries keep graphs alive forever.
- **Async**: long-lived tasks capturing request-scoped objects; “fire-and-forget” that never completes.

**Runnable example: reachability & “leak by event subscription”**

```csharp
using System;

sealed class Publisher
{
    public event EventHandler? Tick;
    public void Raise() => Tick?.Invoke(this, EventArgs.Empty);
}

sealed class Subscriber : IDisposable
{
    private readonly Publisher _publisher;
    public Subscriber(Publisher publisher)
    {
        _publisher = publisher;
        _publisher.Tick += OnTick;
    }

    private void OnTick(object? sender, EventArgs e) { /* work */ }

    public void Dispose() => _publisher.Tick -= OnTick;
}

static void Demo()
{
    var pub = new Publisher();

    // Subscriber stays alive as long as pub stays alive,
    // unless we unsubscribe (Dispose) explicitly.
    var sub = new Subscriber(pub);

    // If you drop all references to sub here, it is STILL reachable via pub.Tick.
    sub.Dispose(); // breaks the reachability chain
}

Demo();
```

**Good to know**
- Reference cycles (A → B → A) are **not** a GC problem by themselves. Cycles are collected if the cycle is **not reachable from roots**.
- If you need to observe object collection for diagnostics, prefer **`WeakReference<T>`** patterns instead of relying on finalizers.

**Performance note**
- The cheapest optimization is often **changing reachability** (break references earlier) rather than trying to “force GC”.

### 2) **Memory vs resources**
**Definition**
- **Managed memory** is the bytes used to represent managed objects.
- **Resources** are things the OS or other systems must release: file handles, sockets, OS locks, native memory, GPU handles, DB connections, etc.

**What the GC does not do**
- The GC does not know that your `FileStream` corresponds to an OS file handle in a way that guarantees timely release.
- Waiting for a collection is **not a cleanup strategy**. It becomes a production outage under load (handle exhaustion, socket leaks, etc.).

**Correct model**
- Use **deterministic cleanup** via `IDisposable` / `IAsyncDisposable` and `using` / `await using`.
- This domain provides the deep treatment in `3.*` and `4.*`.
- For a broader lifetime framing, see:
  - [4.2. Object lifetime and resource management](<../../../01 Fundamental Theories/sections/4. CSharp fundamentals/4.2. Object lifetime and resource management.md>)

**Common mistakes**
- Treating `finalizer` (`~Type()`) as “Dispose but automatic”. It is not (see **2.1–2.3**).
- Forgetting to dispose “small” things that are actually large in count:
  - `CancellationTokenSource`, `Timer`, `HttpResponseMessage`, `Stream`, enumerators that wrap resources.

**Performance note**
- Leaked resources usually fail as **throughput degradation** first (timeouts, retries, ThreadPool pressure), then as hard failures.

### 3) **Performance framing (measure the right things)**
**What actually drives GC cost**
- **Allocation rate** (bytes/sec): how fast you create garbage.
- **Survival rate**: how much of Gen0 lives long enough to get promoted.
- **Working set**: how much memory you keep live (and how fragmented/pinned it is).

**Trade-offs to understand**
- **Fewer allocations** often means more complexity (pooling, spans, caching). Complexity is a cost; pay it only where it matters.
- **Pooling** can reduce GC work but **increase memory retention**, amplify bugs (use-after-return), and complicate concurrency.

**Common anti-patterns**
- `GC.Collect()` in production to “fix memory”. It usually just moves pain elsewhere and can worsen tail latency.
- Blaming Gen2 pauses without checking:
  - are we promoting too much?
  - are we pinning?
  - are we holding onto large graphs via caches/events?

**What to measure first (practical)**
- Live process signals (preferred): allocation rate, GC CPU, Gen0/1/2 counts, LOH size trend.
- For diagnosis tooling and a “how to think about the numbers”, the deep, tool-centric explanation belongs in **1.5**.

**Good to know**
- Gen0 collections are often “normal”. If throughput is fine and latency is acceptable, don’t chase them.
- The scary cases are usually **high promotions** (Gen2 pressure) and **LOH/pinning** (see **1.3**).
