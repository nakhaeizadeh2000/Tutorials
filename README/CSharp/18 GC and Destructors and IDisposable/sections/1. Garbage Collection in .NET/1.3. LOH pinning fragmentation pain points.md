## 1.3. LOH, pinning, and fragmentation (the non-obvious GC pain points)

1. **Large Object Heap basics** (big buffers/arrays; fragmentation risk; compaction realities)
2. **Pinning costs** (interop, fixed buffers, long-lived pinned arrays; why it blocks compaction)
3. **Practical guidance** (`ArrayPool<T>`, `MemoryPool<T>`, `Span<T>`/`Memory<T>`; when pooling hurts)

### 1) **Large Object Heap (LOH) basics**
**Definition**
- The **LOH** is where the GC places **large allocations** (conceptually: big arrays/buffers). The exact threshold is runtime-dependent; treat it as “big enough that moving/copying it is expensive”.
- LOH is not “special because it’s large” only; it’s special because it’s a common source of:
  - **Fragmentation**
  - **Long-lived memory retention**
  - **Gen2 pressure** (many LOH objects are effectively Gen2-managed)

**When to care**
- You allocate large buffers repeatedly (serialization, image/video, crypto, networking, compression).
- Your service shows **LOH growth** and **Gen2 frequency** under load.
- You see “we have plenty of free memory but still OOM / high working set / long pauses” symptoms.

**Trade-offs**
- Avoiding LOH allocations often means:
  - pooling buffers (`ArrayPool<T>`, `MemoryPool<T>`)
  - streaming instead of materializing
  - redesigning APIs to accept `Span<T>`/`Memory<T>`/`IBufferWriter<T>`
- These increase complexity. Use them where the allocation hot path is measurable.

**Common mistakes**
- Calling `ToArray()` / `ToList()` on large sequences in hot paths “for convenience”.
- Building huge strings repeatedly (large intermediate `string` allocations).
- Assuming “the GC will compact it anyway” and ignoring fragmentation and pinning.

**See also (full GC basics elsewhere)**
- For the runtime-level overview of generations + LOH mention, see:
  - [2.3. GC basics for app developers](<../../../01 Fundamental Theories/sections/2. NET architecture/2.3. GC basics for app developers.md>)

**Performance note**
- LOH issues are often **working-set** problems first (memory pressure, cache misses), and **pause-time** problems second.

### 2) **Pinning costs**
**Definition**
- **Pinned** objects cannot be moved by the GC. Pinning is required for some interop scenarios and some high-performance APIs, but it has a cost:
  - it blocks compaction in regions,
  - increases fragmentation,
  - increases the cost of future collections.

**What pins memory (typical sources)**
- `fixed` statements on managed arrays/strings
- long-lived interop calls holding pointers
- some “hold a buffer and expose pointer” designs

**Trade-offs**
- Pinning for a **very short duration** is often fine.
- Long-lived pinning (especially of large objects) is where fragmentation becomes a real operational cost.

**Common mistakes**
- Pinning a buffer and keeping it pinned across awaits or long operations.
- Using pinned arrays as “poor man’s native memory” instead of using dedicated native allocations when needed.

**Good to know**
- If you need stable handles to OS resources, prefer `SafeHandle`-based wrappers (deep treatment in [3.2](<../3. IDisposable/3.2. Dispose pattern in modern NET without cargo culting.md>)).

### 3) **Practical guidance (pooling, `Span<T>`, and when pooling hurts)**
**Use pooling intentionally**
- Prefer `ArrayPool<T>.Shared` for **large temporary buffers** on hot paths.
- Always return rented arrays in a `finally`.
- Decide whether to clear based on sensitivity (clearing costs CPU).

**Runnable example: correct `ArrayPool<T>` usage**

```csharp
using System;
using System.Buffers;

static int CountCommas(ReadOnlySpan<char> text)
{
    var pool = ArrayPool<char>.Shared;
    char[] rented = pool.Rent(text.Length);
    try
    {
        text.CopyTo(rented);

        int count = 0;
        for (int i = 0; i < text.Length; i++)
        {
            if (rented[i] == ',') count++;
        }
        return count;
    }
    finally
    {
        // Clear only if rented buffer may contain sensitive data.
        pool.Return(rented, clearArray: false);
    }
}

Console.WriteLine(CountCommas("a,b,c,d"));
```

**When pooling hurts**
- Small buffers: pooling overhead + larger working set can be slower than allocating.
- Complex ownership: bugs like double-return/use-after-return are correctness issues.
- Security: pooled buffers can “leak” old data unless cleared.

**Modern API design guidance**
- If you’re writing libraries, prefer accepting `Span<T>`/`ReadOnlySpan<T>` and `IBufferWriter<T>` to let callers control allocation strategy.

**Performance note**
- Pooling improves GC pressure, but it can worsen cache locality and memory retention. Measure end-to-end.
