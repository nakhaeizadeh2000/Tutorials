## 1.5. Diagnosing GC and memory problems (tools + mental model)

1. **First-line tools** (`dotnet-counters`, `dotnet-trace`, dumps; allocation profiling)
2. **Common signals** (Gen2 frequency, LOH growth, pinned object count, high GC CPU)
3. **Root-cause patterns** (unbounded caches, event subscriptions, timers, large graphs, sync-over-async)

### 1) **First-line tools**
**What “good diagnostics” looks like**
- You want to answer, in order:
  1. **Are we allocating too much?**
  2. **Is too much surviving (promotion/Gen2 pressure)?**
  3. **Are we pinned/fragmented (LOH pain)?**
  4. **Is the process working set growing because objects are truly live (reachability), or because of fragmentation/pinning?**

**Tools you should reach for first (modern .NET)**
- **`dotnet-counters`**: live metrics, low overhead. Great for “is this a GC problem right now?” and trend watching.
- **`dotnet-trace`**: capture traces (EventPipe) to understand allocations, GC pauses, thread pool interactions.
- **`dotnet-dump`** (or `dotnet-gcdump`): capture snapshots for offline analysis when you need “who is keeping what alive?”
- **Visual Studio / Rider profilers**: allocation profiling in dev. Use them to find hot allocation sites and object retention.

**What to avoid**
- Treating a single tool output as “truth”. Always cross-check: allocation rate + Gen counts + working set + CPU.
- Relying on finalizers as “observability”. Finalizers are not a diagnostic API.

**Good to know**
- **Perf issues are often multi-causal**: e.g., a slow service allocates more due to retries/timeouts, which triggers more GC, which slows it more.

### 2) **Common signals**
**High-signal metrics (what they usually mean)**
- **High allocation rate (bytes/sec)**: you’re creating lots of short-lived objects. Often shows up as frequent Gen0 collections and GC CPU.
- **High Gen2 frequency / high % time in GC**: too much is surviving long enough to be promoted, or the live set is too big.
- **LOH size growth / fragmentation symptoms**: large buffers are being allocated and kept around or pinned; compaction is harder.
- **High pinned object count**: you’re preventing compaction (interop, long-lived buffers, some unsafe patterns).

**How to interpret without fooling yourself**
- High Gen0 count alone isn’t “bad” if:
  - throughput is fine,
  - tail latency is fine,
  - CPU isn’t dominated by GC.
- Gen2 pressure is often a **design/ownership problem**, not a “GC setting problem”:
  - caches keeping large graphs,
  - singletons holding onto request data,
  - event subscriptions keeping objects alive.

**Performance note**
- If tail latency (p95/p99) matters, correlate **GC pauses** with **request latency spikes** and **ThreadPool starvation**. GC and ThreadPool health are coupled in real systems.

### 3) **Root-cause patterns**
**1) Unbounded caches**
- A cache without limits turns into “keep everything alive forever”.
- Fix by introducing:
  - bounds/eviction,
  - TTLs,
  - size accounting,
  - metrics (hit rate, size, evictions).

**2) Event subscriptions and timers**
- Long-lived publishers/timers keep subscribers/closures alive.
- Fix by:
  - unsubscribing deterministically (`IDisposable` pattern),
  - using explicit lifetime scopes,
  - carefully using weak patterns only when you can accept their trade-offs.

**3) Large object graphs**
- “One object per item” designs can create huge graphs (many nodes/edges) that survive.
- Sometimes a flatter representation (arrays, structs, pooled buffers) is the right performance move—measure before you complicate.

**4) Sync-over-async and retry storms**
- Blocking on async (`.Result`, `.Wait()`) can cause ThreadPool starvation, timeouts, retries, and then memory pressure.
- Fix by “async all the way” and correct cancellation/timeout boundaries.
