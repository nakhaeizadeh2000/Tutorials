## 1.2. Generations (Gen0/1/2), pauses, and why “Gen2” is a big deal

1. **Why generational GC exists** (most objects die young; promotion is the real tax)
2. **Pause model basics** (STW, background GC; throughput vs latency)
3. **What to watch** (allocations/sec, collection counts, % time in GC, p95/p99 latency)

### 1) **Why generational GC exists (promotion is the real tax)**
**Definition**
- .NET GC is **generational**: it separates objects into **Gen0**, **Gen1**, **Gen2** based on age/survivorship heuristics.
- The key observation is empirical: **most objects die young**. So the runtime optimizes for collecting young garbage quickly.

**How to reason about it**
- **Allocation** for reference types is typically cheap (a bump-pointer in Gen0).
- The cost shows up later:
  - Surviving objects get **promoted** (Gen0 → Gen1 → Gen2).
  - Higher-generation collections usually touch more memory, do more work, and can create longer pauses.

**What “Gen2 pressure” usually means**
- Too many objects are:
  - **living too long** (caches, static references, event subscriptions, long-lived singletons holding graphs)
  - **too large** (buffers/arrays, LOH interactions; see **1.3**)
  - **pinned** (interop, long-lived buffers; see **1.3**)

**Common mistakes**
- Treating “Gen2 collection happened” as the problem. It’s usually a symptom.
- Assuming “I’m not allocating much” because you don’t see `new`:
  - Boxing, LINQ iterators, closures, string creation, `ToArray()`/`ToList()` can allocate heavily.

### 2) **Pause model basics (STW, background GC; throughput vs latency)**
**Definition**
- The GC needs a consistent view of the object graph, which leads to **stop-the-world (STW)** phases.
- Modern .NET uses **background GC** (especially relevant for Gen2) to reduce pause impact, but it does not eliminate pauses.

**Throughput vs latency**
- **Throughput goal**: maximize total work done per CPU time (often server workloads).
- **Latency goal**: minimize and stabilize response times (p95/p99) and avoid long tail spikes.

**Mentor framing**
- If your app has latency objectives, you must care about:
  - **pause distribution** (tail latency), not just averages
  - how GC interacts with **ThreadPool** scheduling (e.g., pauses can amplify queuing delays)

**Common mistakes**
- Forcing GC (`GC.Collect`) to “reduce memory” during request handling. This can:
  - create extra STW pauses
  - increase CPU
  - worsen tail latency
- Confusing “GC pause” with “thread blocked”: both can look like “latency spike”.

**Good to know**
- GC and JIT/tiered compilation can both create “cold path” spikes. Don’t misattribute.

### 3) **What to watch (metrics that map to decisions)**
**Core metrics (high signal)**
- **Allocation rate** (bytes/sec): how fast you create garbage.
- **Gen0/1/2 collection counts**: frequency is a proxy for pressure, not “badness” by itself.
- **% time in GC**: directly impacts throughput.
- **LOH size trend**: suggests large allocations or retention.
- **Pinned objects / pinned bytes** (where visible): a compaction killer.

**How to interpret**
- If allocation rate is high but latency is fine, you may be throughput-bound instead of latency-bound.
- If p99 latency spikes correlate with Gen2, focus on:
  - retention and promotion causes
  - LOH/pinning
  - finalizers (finalizable objects amplify lifetime; see **2.1–2.3**)
