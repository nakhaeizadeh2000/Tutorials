## 5.2. Performance checklist (allocation rate, survival, LOH/pinning, pooling trade-offs)

1. **Optimize allocations before GC tuning** (bytes/sec and survival rate drive cost)
2. **Prefer smaller/shorter-lived graphs** (object graph shape beats micro-optimizations)
3. **Pool carefully** (`ArrayPool<T>` can help; can also increase working set and bugs)

### 1) **Optimize allocations before GC tuning**
**Definition**
- In managed runtimes, most GC cost is not “collecting memory” in the abstract; it’s:
  - scanning/marking live objects,
  - copying/compacting survivors,
  - dealing with promotions and fragmentation.
- Those costs scale with **allocation rate** and **survival rate**.

**When to apply**
- High-throughput servers (ASP.NET Core, message consumers) where **allocations/sec** converts directly into **CPU in GC**.
- Latency-sensitive systems where promotion spikes appear as **tail latency** (p95/p99).

**Trade-offs**
- Many “allocation reducers” increase complexity:
  - pooling buffers,
  - avoiding LINQ/allocating iterators,
  - using `Span<T>`/`ReadOnlySpan<T>` to parse without slicing strings.
- Complexity is a cost; optimize only where measurements justify it.

**Common mistakes**
- “Tuning GC” first (server/workstation, latency mode) while still allocating excessively.
- Adding pooling everywhere: pooling can **increase** working set and reduce locality if misused.
- Fighting the compiler/runtime: micro-optimizing allocations in cold code.

**Good to know**
- “Gen0 allocations are cheap” means allocation is fast; it does **not** mean allocations are free at scale.

### 2) **Prefer smaller/shorter-lived graphs**
**Definition**
- The “shape” of your live object graph (number of objects + references) determines:
  - scan cost during collections,
  - cache locality,
  - promotion pressure.

**Practical heuristics**
- Prefer streaming over materializing:
  - process items as you read them rather than building huge lists.
- Prefer compact representations:
  - fewer wrapper objects, fewer intermediate allocations.
- Be mindful of “hidden reachability”:
  - events, timers, static caches, captured closures.

**Common mistakes**
- Unbounded caches (static dictionaries) with values that reference deep graphs.
- Capturing request-scoped services into long-lived singletons or background tasks.

**Good to know**
- A single long-lived reference to a root object can keep an entire graph alive.

### 3) **Pool carefully**
**Definition**
- Pooling reduces allocation churn by reusing buffers/objects (e.g., `ArrayPool<T>`, `MemoryPool<T>`).

**When pooling helps**
- Large buffers allocated frequently (e.g., 64KB–MB ranges).
- Hot paths where allocations show up clearly in allocation profiling.

**When pooling hurts**
- Small buffers (pool overhead > allocation cost).
- Security-sensitive data that must be cleared (clearing costs CPU; forgetting to clear leaks data).
- Complex ownership: returning buffers twice, returning while still in use, leaking references.

**Runnable example: correct `ArrayPool<T>` usage with clear ownership**

```csharp
using System;
using System.Buffers;

static int SumWithPool(ReadOnlySpan<int> data)
{
    // For small inputs, prefer direct loops/stackalloc; this example shows safe pool usage.
    var pool = ArrayPool<int>.Shared;
    int[] rented = pool.Rent(data.Length);
    try
    {
        data.CopyTo(rented);
        int sum = 0;
        for (int i = 0; i < data.Length; i++)
            sum += rented[i];
        return sum;
    }
    finally
    {
        // Use clearArray: true for sensitive data; it's extra CPU.
        pool.Return(rented, clearArray: false);
    }
}

Console.WriteLine(SumWithPool(stackalloc[] { 1, 2, 3, 4 }));
```

**Mentor rule**
- Treat pooling as a **feature** with operational cost. Add metrics and test ownership paths.
