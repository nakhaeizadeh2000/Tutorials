## 5.1. Correctness checklist (leaks, finalizers, ownership, and lifetime boundaries)

1. **GC is not cleanup** (it frees managed memory, not “your resources”)
2. **Finalizers are last resort** (and a performance tax)
3. **Ownership must be explicit** (who disposes; DI + scopes; events/timers as “lifetime glue”)

### 1) **GC is not cleanup**
**Mentor rule**
- The GC only answers: **is this managed object reachable?** It does **not** guarantee timely release of OS resources.
- Treat “we’ll let the GC handle it” for handles/sockets/timers as **a correctness bug** that usually becomes a production incident.

**What to do instead**
- If your type owns something that must be released, implement **`IDisposable`** (or **`IAsyncDisposable`** when cleanup is inherently async) and make callers use `using` / `await using`.
- Full treatment: see section **3.1–3.3** in this domain.

**Common mistakes**
- Creating an `HttpResponseMessage` / `Stream` / `CancellationTokenSource` / `Timer` and forgetting to dispose it because “it’s managed”.
- Relying on a finalizer as a primary cleanup mechanism (see **2.1–2.3**).

**Good to know**
- “Memory leak” in .NET is often **unintended reachability** (events, timers, caches). The GC is correct to keep reachable objects alive.
- Deep reachability model and leak patterns: see **1.1**.

### 2) **Finalizers are last resort**
**What to remember**
- `~Type()` is a **finalizer**, not a deterministic destructor. It runs:
  - on the **finalizer thread**,
  - at an **unpredictable time** (or not at all if the process terminates),
  - with **ordering not guaranteed** relative to other objects.

**When finalizers are justified**
- Only when you wrap **native resources** and must provide a safety net for callers who fail to dispose.
- Prefer `SafeHandle` so you don’t write fragile finalizer code yourself.
- Full treatment: see **2.2** and **3.2**.

**Common mistakes**
- Adding finalizers to “be safe” for **managed-only** resources (streams, managed timers, arrays). That makes things worse: more GC work, longer lifetimes, worse tail latency.
- Putting business logic or blocking I/O in a finalizer (can deadlock, can stall shutdown, can crash the process if it throws).

**Performance note**
- Finalizable objects live longer by design and increase GC bookkeeping. This is a correctness *and* performance tax. See **2.3**.

### 3) **Ownership must be explicit**
**Definition**
- Ownership answers:
  - **Who creates** the resource?
  - **Who disposes** it?
  - **Who may share** it (and under what thread-safety contract)?

**API shapes that prevent bugs**
- **Borrow vs own is explicit**:
  - Accept a factory if you want to own what you create.
  - Accept an instance if you want to borrow it (and document “caller disposes”).
- **DI interactions**:
  - If the DI container creates it (scoped/singleton), the container disposes it. Do not dispose DI-owned instances manually.
  - If you create an `IServiceScope`, you own/dispose that scope.
  - Full treatment: see **3.4**.

**Common leak sources that are “ownership glue”**
- Events, timers, background tasks, and caches often become hidden ownership channels.
- For the “how leaks happen” mental model, see **1.1**.

**Good to know**
- `Dispose()` should be safe to call multiple times (idempotent) and should not throw in normal use. Full contract guidance: see **3.1**.
