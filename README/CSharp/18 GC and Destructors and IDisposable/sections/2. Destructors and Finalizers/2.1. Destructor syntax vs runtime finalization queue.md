## 2.1. Destructor syntax vs runtime reality: the finalization queue

1. **What `~Type()` compiles to** (finalizer; not deterministic; not on your thread)
2. **Finalization pipeline** (finalization queue + finalizer thread; resurrection hazards)
3. **Cost model** (finalizable objects are more expensive; they survive longer by design)

### 1) **What `~Type()` compiles to**
**Definition**
- In C#, a *destructor* syntax `~MyType()` is not C++-style deterministic destruction. It compiles to a **finalizer** (CLR concept).
- The runtime calls finalizers **non-deterministically** on a dedicated **finalizer thread**, sometime *after* the object becomes unreachable.

**What you must assume**
- **Timing is unpredictable**: finalizers may run much later, or not at all before process termination.
- **Thread is not yours**: you cannot assume any SynchronizationContext, request context, or “UI thread” (frontend).
- **Ordering is not guaranteed**: if two objects reference each other, which finalizer runs first is not something to rely on.

**Legacy misconception (common interview trap)**
- “Destructor runs when object goes out of scope.”  
  - False in .NET. Scope end only makes a variable go out of scope; the object may still be reachable elsewhere.
  - Even if unreachable, collection and finalization happen later (if ever).

**Runnable example: finalizer timing is not deterministic**

```csharp
using System;
using System.Threading;

sealed class WithFinalizer
{
    private readonly int _id;
    public WithFinalizer(int id) => _id = id;

    ~WithFinalizer()
    {
        // DO NOT do this in production; it's for demonstration only.
        Console.WriteLine($"Finalizer ran for {_id} on thread {Environment.CurrentManagedThreadId}");
    }
}

static void Demo()
{
    _ = new WithFinalizer(1);
    _ = new WithFinalizer(2);
}

Demo();

// You can request collection, but you cannot *reliably* control finalization timing.
GC.Collect();
GC.WaitForPendingFinalizers();
Thread.Sleep(10);
```

**Good to know**
- `GC.Collect()` is almost always a **bad idea** in production. This snippet is purely didactic.
- If you need deterministic cleanup, implement `IDisposable`/`IAsyncDisposable` and use `using` / `await using` (deep treatment in `3.*` and `4.*`).

**Performance note**
- Adding a finalizer changes your type’s lifetime and GC behavior (details in **3)**). Treat it as a deliberate, measurable cost.

---

### 2) **Finalization pipeline**
**What happens at runtime (high-level but precise)**
- When an instance of a finalizable type becomes unreachable, it is not reclaimed immediately. Instead, it becomes eligible for finalization:
  - It is placed on the **finalization queue**.
  - A dedicated **finalizer thread** eventually executes the finalizer.
  - Only after finalization has run (and the object is still unreachable) can the memory be reclaimed by a later GC.

**Key implications**
- Finalizable objects effectively require **at least two GC cycles** to be fully reclaimed (one to discover they’re unreachable and queue them, another to reclaim after finalization).
- Finalization can be **backlogged**: if finalizers are slow or many objects queue up, the finalizer thread becomes a bottleneck and memory/handles can pile up.

**Resurrection hazard (advanced but important)**
- A finalizer can “resurrect” an object by storing `this` somewhere reachable (e.g., static field).
- This makes reasoning about lifetime extremely hard and can create long-lived leaks.
- Mentor rule: **never resurrect** unless you have a very specialized runtime component and a strict design review.

**Common mistakes**
- Doing *too much* work in finalizers: I/O, locking, logging, allocating, interacting with other finalizable objects.
- Relying on other objects being alive: the runtime does not guarantee finalization order across object graphs.

**Good to know**
- If your type *must* release an OS handle as a last resort, prefer wrapping it in `SafeHandle` rather than hand-writing complex finalizer logic. The deep “why” lives in `3.2`.

---

### 3) **Cost model**
**Why finalizable types are expensive**
- **GC bookkeeping overhead**: finalizable objects require extra runtime tracking.
- **Longer lifetime by design**: queued-for-finalization objects tend to survive longer, increasing **promotion pressure** (more objects end up in Gen1/Gen2).
- **Latency / tail-risk**: finalizer backlog can create unpredictable cleanup delay and memory/handle spikes.

**Practical consequences you can observe**
- Higher Gen2 frequency (more promotions).
- More time in GC.
- OS resource pressure (handles/sockets) because cleanup is delayed.

**Mentor guidance**
- If your type owns only managed resources (other `IDisposable` things), you almost never need a finalizer.
- If your type owns native resources, prefer:
  - **`SafeHandle`** (reliable finalization semantics designed for this), plus
  - `IDisposable` for deterministic release.
