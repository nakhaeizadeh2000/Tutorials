## 2.3. Finalizers and performance/latency (throughput vs p99 vs tail-risk)

1. **Why finalizers hurt** (extra GC bookkeeping; delayed reclamation; promotion pressure)
2. **Why finalizers are unreliable** (process termination, crashes, time constraints, ordering)
3. **Operational impact** (handle exhaustion, socket depletion, slower steady-state under load)

### 1) **Why finalizers hurt**
**Core cost model**
- A type with a finalizer (`~Type()`) is “special” to the runtime: instances become **finalizable objects**.
- Finalizable objects generally require **at least two GC cycles** to fully reclaim:
  - **GC #1** discovers the object is unreachable, but instead of reclaiming it, the runtime queues it for finalization and keeps it alive.
  - The **finalizer thread** runs `Finalize()`.
  - Only on a later GC (or after finalization when memory is eligible) can memory be reclaimed.

**Why this matters**
- **Longer lifetime** ⇒ more chance the object survives to older generations ⇒ **promotion pressure** ⇒ more expensive collections.
- Finalization has **global contention points** inside the runtime: extra tracking and queueing work, which can show up as CPU cost and latency.

**Common mistake**
- Adding a finalizer “just in case someone forgets Dispose”. That shifts the cost and risk onto every instance, including the correct ones.

**Performance note**
- If you need a safety net for a native handle, prefer `SafeHandle`-based designs (deep guidance in **2.2**). It gives you reliability with a smaller surface for mistakes than custom finalizers.

---

### 2) **Why finalizers are unreliable**
**Non-determinism (hard guarantees you do NOT get)**
- You do **not** control *when* finalizers run (or even whether they run before process exit).
- You do **not** control *the thread* they run on (finalizer thread, not your request/UI thread).
- You cannot rely on **ordering** (object A’s finalizer may run before B’s even if A referenced B).

**Process termination realities**
- On normal shutdown, the runtime *tries* to run finalizers, but:
  - hosts may terminate the process quickly,
  - crashes / `Environment.FailFast` bypass finalization,
  - container orchestrators can send SIGKILL-equivalent termination where you get no cleanup window.

**Common mistake**
- Doing “real work” in a finalizer: logging, network calls, waiting, locking, touching other objects. Finalizers must be tiny and defensive.

**Good to know**
- Finalizers run under extreme constraints: the process may be unstable, and other objects you might depend on can already be finalized.

---

### 3) **Operational impact**
**How finalizer misuse becomes outages**
- **Handle exhaustion**: if you rely on finalizers to close files/sockets, high-load bursts can create thousands of outstanding handles before finalization catches up.
- **Socket depletion**: delayed disposal increases open connections, TIME_WAIT buildup, and retries.
- **Latency spikes**: GC work + finalizer backlog can surface as p95/p99 regressions that are hard to reproduce locally.
- **Throughput collapse**: thread pool threads get tied up waiting on I/O caused by resource pressure (timeouts, backoffs), which then causes more allocations and more GC.

**Runnable demonstration (intentionally bad)**
This snippet shows why “eventually finalized” is not an operational plan. It is not meant as a pattern.

```csharp
using System;
using System.IO;

sealed class BadFileOwner
{
    private readonly FileStream _stream = File.OpenRead("some-large-file.bin");
    ~BadFileOwner() => _stream.Dispose(); // finalizer-only cleanup: non-deterministic and expensive
}

static void Demo()
{
    for (var i = 0; i < 100_000; i++)
        _ = new BadFileOwner();

    // Under real load, you may hit handle limits long before finalization catches up.
    // GC.Collect() would “work” in a lab, but is not a production strategy.
}
```

**Recommended replacement (production)**
- Own the resource and release it deterministically:
  - `using var stream = ...;`
  - or implement `IDisposable` (see `3.1` and `3.2`)
- If you wrap native handles, design around `SafeHandle` (see `2.2` / `3.2`).
