## 4.1. `using` statement vs `using var` declaration (scope and readability)

1. **Scope control** (block-scoped vs enclosing-scope; be intentional about lifetime)
2. **Exception safety** (`using` is `try/finally`; deterministic even on exceptions)
3. **Performance** (shorter lifetimes reduce handle pressure; avoid keeping disposables alive “by accident”)

### 1) **Scope control**
**Definition**
- Both the `using` statement and `using var` declaration ensure `Dispose()` runs, but they differ in **scope**:
  - **`using (...) { ... }`**: disposal happens at the end of the block.
  - **`using var x = ...;`**: disposal happens at the **end of the current scope** (usually the method), not “right after the next line”.

**When to use which**
- Use **`using var`** when:
  - the resource should live for the rest of the method and the scope is already clear,
  - nesting blocks would harm readability.
- Use a **`using` block** when:
  - you want a **short lifetime** inside a larger method,
  - you want to release resources before the end of the method (common in hot loops / request handlers),
  - you want to avoid accidental lifetime extension due to later code.

**Common mistake**
- Using `using var` at the top of a long method and unintentionally keeping a handle/socket open much longer than needed.

**Runnable example: lifetime difference**

```csharp
using System;
using System.IO;

static void UsingScopeDemo(string path)
{
    // Disposed at end of method scope (could be much later).
    using var a = File.OpenRead(path);

    // Disposed at end of this block (earlier).
    using (var b = File.OpenRead(path))
    {
        Console.WriteLine(b.Length);
    }

    // a is still alive here.
    Console.WriteLine(a.Length);
}
```

**Performance note**
- Scope control is performance control: shorter lifetimes reduce contention on OS resources and reduce “accidental retention” (files locked longer, sockets kept open longer, pooled buffers not returned promptly).

---

### 2) **Exception safety**
**What the compiler guarantees**
- `using` is compiled to a `try/finally` (conceptually):
  - even if an exception is thrown, `Dispose()` runs.
- This is one of the key reasons you should avoid manual `try/finally` unless you need custom behavior.

**Common mistakes**
- Forgetting to dispose on early returns when not using `using`.
- Swallowing exceptions in `Dispose()` (a correctness and debugging hazard). If `Dispose()` can throw, document it and keep it rare; most `Dispose()` implementations should be non-throwing in practice.

---

### 3) **Performance**
**High-signal guidance**
- The performance win of `using` is usually not “faster code”; it’s **preventing resource pressure**:
  - fewer open handles,
  - fewer sockets in limbo,
  - less kernel contention,
  - fewer retries/timeouts that cascade into ThreadPool pressure.

**Avoid cargo-cult micro-optimizations**
- Don’t replace `using` with manual pooling hacks unless a profiler says disposal/allocation is the bottleneck.
- Prefer readability first; choose shorter scopes when the resource is expensive or scarce.
