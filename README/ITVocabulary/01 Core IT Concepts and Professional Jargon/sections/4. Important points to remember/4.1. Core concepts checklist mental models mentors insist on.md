## 4.1. Core concepts checklist (mental models mentors insist on)

### 1) **Layer vocabulary**

Before describing any symptom, name the layer: hardware → OS → runtime → app → user (from [2.1](<../2. Core computing concepts/2.1. Hardware software OS and platform.md>)).

- **Check yourself**: "the checkout page fails" becomes "the checkout *app* returns 500 under the *production runtime* while the *OS and hardware* report healthy". Five extra words, and the investigation starts in the right place instead of paging the wrong team.
- **Bad habit to break**: layer-blind reports ("the server is broken", "the code doesn't work") — they force every reader to re-derive the layer you already knew.

### 2) **Unit discipline**

State the unit every time: bits vs bytes, decimal vs binary, and the encoding wherever text crosses a boundary (from [2.2](<../2. Core computing concepts/2.2. Data units bit byte and encoding basics.md>)).

- **Check yourself**: quotas ("512 MiB, binary"), speeds ("100 Mb/s, bits"), text boundaries ("UTF-8 declared in the Content-Type header"). If a number in your ticket, config, or contract has no unit, it is not a specification — it is a wish.
- **Bad habit to break**: bare "GB"/"MB" in limits and invoices; bare "text" at system boundaries. Both have caused real outages and real billing disputes.

### 3) **Acronym hygiene**

Expand on first use, use each acronym for exactly one thing per context, and decode unknowns by decomposing first (from [1.2](<../1. Learning vocabulary like a professional/1.2. How to decode unknown terms.md>), [3.1](<../3. Everyday professional jargon/3.1. Core acronyms API SDK SLA KPI and friends.md>)).

- **Check yourself**: first mention in any doc or message spells it out — "Service-Level Agreement (SLA)" — and no team reuses one acronym for two systems ("the pipeline" must point to exactly one pipeline; otherwise name them: "CI pipeline" vs "data pipeline").
- **Bad habit to break**: acronym-first writing that forces every new reader to guess; competing local meanings for one term across teams sharing a chat channel.

### 4) **Common confusion**

- "Checklists are for juniors" — pilots with 10,000 hours still run checklists; the failure mode they prevent (skipping the obvious under pressure) gets *worse* with experience, not better.
- "This is just common sense" — common sense is what you call a checklist after it becomes reflex; until then, write it down.

### 5) **Mentor note**

Turn this checklist into review criteria: reject incident reports without a layer, reject quota configs without units, reject docs that introduce unexplained acronyms. Three mechanical rules, enforced for a month, permanently raise a team's communication floor — and the juniors you train this way will out-communicate seniors who never learned it.
