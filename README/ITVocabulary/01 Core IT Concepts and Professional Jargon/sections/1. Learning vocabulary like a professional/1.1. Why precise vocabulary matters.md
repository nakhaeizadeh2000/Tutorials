## 1.1. Why precise vocabulary matters

### 1) **Precision prevents incidents**

**Definition** — Precise vocabulary means choosing the word that names the exact layer and symptom: "the checkout API returns 500" instead of "the server is down", "the deploy is stuck" instead of "nothing works".

- **What problem it solves**: every vague report triggers the wrong response. "The server is down" pages infrastructure engineers; the real fault — a bad app release returning 500s — needed the app team. Vague words buy a full round-trip of misdirected investigation before the real work starts.
- **Modern guidance** — name the layer first, then the symptom: *which system, which behavior, since when*. "Payments API (system) returns 500 on charge calls (behavior) since 14:20 UTC (onset)" routes itself to the right owner — as of the August 2026 era this is the standard incident-report shape in every major status-page culture.

```text
# Bad: routes nowhere, helps nobody
"The site is broken, please fix ASAP."

# Good: system + behavior + onset — self-routing
"Checkout API returns HTTP 500 on POST /charges since 14:20 UTC.
 App version 2.14.1, no infra alerts on the dashboard."
```

### 2) **Terms are compressed models**

Each technical term carries an agreed mental model, not just a dictionary gloss. Saying "cache" commits you to a specific story — a fast store consulted before the slow source, with staleness as the known trade-off — and your listener will reason from that story.

- **History in one paragraph**: jargon exists because experts needed shorthand for structures they manipulate daily. "Deploy", "rollback", "replica", "queue" each survived because the concept underneath kept recurring; the word is the handle the profession agreed to grip it by.
- **Modern guidance** — never use a term whose model you cannot sketch. If you say "eventual consistency" but cannot name what converges and what a reader might briefly see instead, you are reciting, not communicating — and seniors will notice within one follow-up question.

### 3) **Imprecision compounds in teams**

One vague word in a ticket becomes three wrong assumptions downstream: the writer meant "slow", the reader implements "caching", the reviewer approves "a new index" — and nobody re-checks the original symptom.

- **Why it hurts (correctness, maintainability)**: miscommunication is the only bug class that reproduces across people. Code mistakes are caught by tests; vocabulary mistakes are *amplified* by process — standups, tickets, and docs each add a layer of confident misunderstanding.
- **Modern guidance** — the cheapest fix in engineering is a clarifying question asked early: "when you say *slow*, do you mean latency over 2s or throughput under 100 rps?" One sentence now saves one sprint later.

### 4) **Common confusion**

- "Jargon is just showing off" — showing off is *unexplained* jargon; precise terms with shared models are the opposite of showing off, they are compression.
- "Everyone knows what I mean" — in a team of five, that sentence is wrong about at least two people; in a team of fifty it is wrong about forty.
- "Precision means long messages" — the good example above is two lines; precision is about *which* details, not how many.

### 5) **Mentor note**

Review vocabulary the way you review code: when a junior writes "fixed the bug" in a commit message, ask which bug, which cause, which layer — the same three questions you would ask about a vague incident report. Teams that enforce precise words in tickets and commits debug faster than teams that only enforce precise code, because half their incidents get routed correctly on the first sentence.
