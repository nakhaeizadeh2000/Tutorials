## 3.1. Core acronyms: API, SDK, SLA, KPI, and friends

### 1) **Interface words: API, SDK, CLI**

**Definitions** — An *API* (Application Programming Interface) is a contract for programs to talk to a system (endpoints, function signatures, protocols). An *SDK* (Software Development Kit) is a toolbox for developers targeting a platform (libraries + docs + samples + tooling). A *CLI* (Command-Line Interface) is how humans operate a system from a terminal.

- **What problem it solves**: these three answer "how do I touch this system?" for three different consumers — programs (API), developers building on it (SDK), operators driving it (CLI). Confusing them prescribes the wrong integration: reading SDK docs when you needed the raw API contract, or scripting clicks when a CLI flag existed.
- **Modern guidance** — reach in this order: CLI for one-off operations, SDK for application code on a supported stack, raw API when the SDK doesn't cover your case or hides behavior you must control (retries, headers, idempotency keys).

```text
# Bad: wrong consumer, wrong tool
"To check one failed payment, integrate the Python SDK into a script."

# Good: match the consumer to the interface
"One-off check → CLI: payctl charges get ch_123.
 App integration → SDK: stripe.charges.retrieve in code.
 Custom retry semantics → raw API: POST /charges with idempotency key."
```

### 2) **Agreement words: SLA, SLO, SOW**

An *SLA* (Service-Level Agreement) is a contractual promise with consequences (e.g., 99.9% uptime, credits if breached). An *SLO* (Service-Level Objective) is the internal target the team aims at to stay safely inside the SLA (e.g., 99.95%). A *SOW* (Statement of Work) scopes contracted work — deliverables, timeline, boundaries.

- **Why it matters (money and trust)**: SLA is the one with lawyers attached — breaching it costs credits and credibility. SLO is the engineering steering wheel: burn through the *error budget* (allowed failure room between reality and the SLO) too fast and you freeze risky releases until it recovers. SOW is where scope disputes live or die ("that wasn't in the SOW" ends more arguments than any meeting).
- **Modern guidance** — never quote an SLA you don't measure, never promise an SLO tighter than the SLA requires, and read the SOW before volunteering new scope in a client meeting.

### 3) **Measurement words: KPI, OKR, metric vs KPI**

A *metric* is anything you measure (latency, signups, deploys per week). A *KPI* (Key Performance Indicator) is a metric a decision rides on — key because someone acts when it moves. An *OKR* (Objectives and Key Results) is a goal-setting frame: an *objective* (qualitative direction) plus 2–5 measurable *key results*.

- **What problem it solves**: teams drown in dashboards because every metric looks equally important. The KPI question — "who changes what when this moves?" — deletes vanity metrics on contact. OKRs then aim the survivors at one quarter's actual goal instead of background noise.
- **Modern guidance** — cap KPIs at a handful per team, attach an owner and a response to each ("p99 checkout latency > 800ms → owner: payments team, response: freeze releases, investigate"), and expire OKRs quarterly. A metric with no owner and no response is decoration — label it as such or delete it.

### 4) **Common confusion**

- "API vs SDK" — the API is the contract, the SDK is one convenience wrapper around it; every SDK call ends at an API, but not every API has an SDK.
- "SLA vs SLO" — SLA faces the customer with penalties; SLO faces the team with an error budget. Hitting the SLO but breaching the SLA means the targets were set backwards.
- "Everything measured is a KPI" — measured ≠ key; key means a named human takes a named action when it moves.

### 5) **Mentor note**

Run a 15-minute acronym drill with every new hire using *your* systems as examples: "show me our API, our SDK, our CLI; what SLA do we promise, what SLO do we steer by, what are our three KPIs?" Generic definitions take minutes; mapping them onto the team's reality is the actual onboarding — and it exposes the terms the team uses loosely, which are precisely the ones that will cause the next misunderstanding.
