## 2.3. Programs, processes, compile vs interpret

### 1) **Program vs process vs thread**

**Definition** — A *program* is instructions on disk (a file you can copy). A *process* is a program being executed — loaded into memory by the OS with its own address space and resources. A *thread* is one path of execution inside a process; a process has at least one, and threads inside a process share its memory.

- **What problem it solves**: "restart the app" is ambiguous until you know these words — do you rebuild the program, kill and relaunch the process, or is one stuck thread blocking the rest? Each answer is a different command with different blast radius.
- **Modern guidance** — describe running software with all three nouns: "the Node *program* (v24) runs one *process* per container, each with a single main *thread* plus the libuv pool". Anyone hearing that sentence knows exactly what can fail independently.

```text
# Bad: one word for three things
"The app is stuck, restart the thing."

# Good: program vs process vs thread separated
"Process 412 (checkout worker, started 09:12) is unresponsive —
 one thread is blocked on a DB call. Kill process 412 only;
 the program binary is untouched, no rebuild needed."
```

### 2) **Compile vs interpret vs JIT**

*Compiling* translates source code to machine code ahead of time (C, Rust, Go); *interpreting* executes it line by line at run time (classic Python, shell); *JIT* (just-in-time) compilation compiles hot paths during execution — the hybrid modern engines (V8, JVM, .NET) use to get both flexibility and speed.

- **History in one paragraph**: the split is as old as high-level languages — compiled Fortran (1957) for speed, interpreted BASIC (1964) for immediacy. The modern world converged on hybrids: JavaScript engines parse to bytecode then JIT-optimize hot code, which is why "interpreted language" is a misleading label for anything with a tiered engine underneath.
- **Modern guidance** — use the words for what they predict: compiled ⇒ build step, fast start of pre-built binaries; interpreted ⇒ no build step, errors surface at the line that runs; JIT ⇒ warm-up effects — first requests are slower, benchmarks need warm-up iterations, and "it got faster on its own" is the optimizer, not magic.

### 3) **Runtime is where it actually runs**

The *runtime* (or *runtime environment*) is everything present during execution: the engine or VM, the OS services, env vars, mounted files, network access. A *runtime error* means failure during execution — as opposed to a *compile-time error* (rejected before running) or a *logic error* (runs fine, computes wrong).

- **Why it matters (correctness, debugging)**: error classes dictate tools. Compile-time errors need the compiler output; runtime errors need logs, repro steps, and the runtime's actual state (env, versions, inputs); logic errors need tests and reasoning. Misclassifying the error picks the wrong tool and burns the investigation.
- **Modern guidance** — quote runtime errors with the runtime attached: "TypeError at checkout.js:41 under Node 24, `CURRENCY` unset" — language, location, runtime version, environment. Four facts, zero follow-up questions needed to start.

### 4) **Common confusion**

- "Program and process are synonyms" — a program is static (disk), a process is dynamic (memory + OS bookkeeping); one program can run as many processes.
- "Interpreted means slow, compiled means fast" — JIT runtimes routinely beat naive compiled code; the honest axis is *when* translation happens, not speed.
- "Runtime just means Node.js" — Node.js is one runtime among many (browsers, Deno, Bun, JVM); "runtime" names the role, not the product.

### 5) **Mentor note**

When a junior says "it throws an error", train the triple-question reflex: *when* (compile, load, or run?), *where* (which layer of the stack from [2.1](<./2.1. Hardware software OS and platform.md>)?), *under what runtime* (versions, env)? Three answers turn a shrug into a searchable problem statement — the single highest-leverage debugging habit you can install.
