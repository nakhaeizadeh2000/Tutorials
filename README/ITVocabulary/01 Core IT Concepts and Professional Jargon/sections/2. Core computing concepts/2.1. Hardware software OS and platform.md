## 2.1. Hardware, software, OS, and platform

### 1) **Hardware executes, software instructs**

**Definition** — *Hardware* is the physical machine: CPU, RAM, disk, network card. *Software* is the set of instructions that tells the hardware what to do — from the operating system down to a one-line script.

- **What problem it solves**: half of all "my code doesn't work" confusion is a layer error — blaming the program when the machine is out of memory, or blaming the laptop when the program has a bug. Naming the two sides correctly is the first step of every diagnosis: *is the executor broken, or are the instructions wrong?*
- **Modern guidance** — when something fails, state both halves explicitly: "the program (software) crashes when the container (constrained hardware view) has 512 MB RAM". This habit alone separates junior reports from senior ones.

```text
# Bad: layer-blind
"My app is broken on the server."

# Good: executor vs instructions separated
"The app (software, v2.14.1) runs locally but OOM-crashes on the
 server (hardware view: 512 MB container limit). Same instructions,
 different executor resources — investigate memory, not logic."
```

### 2) **The OS is the broker**

The *operating system* (Linux, Windows, macOS) multiplexes one physical machine among many programs. Its *kernel* schedules CPU time and guards memory; *drivers* translate generic requests into hardware-specific signals; a *process* is one running program as the OS sees it.

- **History in one paragraph**: early computers ran one program at a time, hand-loaded by operators. Multitasking operating systems (Unix, 1969, being the lineage that matters most today) introduced the broker model: programs ask, the OS decides — which is why your code never truly "owns" the CPU, it rents slices of it.
- **Modern guidance** — learn these three OS words cold, because every later domain leans on them: *process* (a running program with its own memory), *thread* (a path of execution inside a process), *file descriptor* (the OS handle your program uses for files, sockets, and pipes alike).

### 3) **Platform means "what you build on"**

*Platform* is the full stack your code assumes: OS + language runtime + libraries + external services. "It works on my machine" is a platform-mismatch confession — the code was correct against one platform and wrong against another (different Node version, missing env var, case-sensitive filesystem).

- **Why it hurts (correctness, production bugs)**: platform drift is the #1 source of works-here-fails-there incidents. The code didn't change between laptop and server; the platform did — and nobody wrote the platform down.
- **Modern guidance** — pin the platform the way you pin dependencies: lockfiles, container images, `.nvmrc`/engine fields, documented env vars. If the platform isn't written down, it isn't reproducible — and "works on my machine" is a matter of time, not skill.

### 4) **Common confusion**

- "OS and platform are synonyms" — the OS is one layer of the platform; two identical OSes with different runtimes are different platforms.
- "Hardware doesn't matter anymore, everything is cloud" — cloud is rented hardware with extra steps; RAM limits, CPU throttling, and disk latency still page people at 3 AM.
- "Kernel vs OS" — the kernel is the privileged core; the OS is kernel plus user-space tooling (shell, drivers, services).

### 5) **Mentor note**

Draw the layer stack on every whiteboard discussion — hardware → kernel/OS → runtime → app → user — and force every symptom onto one layer before allowing solutions. Juniors who argue fixes before placing the symptom are guessing; the stack diagram turns guessing into locating.
