## 6.1. Boundaries: what is covered elsewhere

This domain names safety and flow — threats, identity, pipelines, and operate-side response. It deliberately stops at these borders:

1. **Security practice** (threat modeling, penetration testing, cryptography implementation, SOC operations) — the future Security track owns the craft; this domain owns threat/vulnerability/CVE/secrets as words ([1.1](<../1. Safety words/1.1. Threat vulnerability CVE and patch.md>), [1.2](<../1. Safety words/1.2. Auth identity secrets and least privilege.md>)).
2. **Pipeline configuration** (authoring workflows, runners, secret wiring, progressive-delivery operation) — future DevOps/Cloud tracks; automation vocabulary stays here ([2.1](<../2. Flow words/2.1. Pipeline observe and incident words.md>)), YAML lives there.
3. **Release-shape mechanics** (operating flag systems, canary analysis, deployment strategies in practice) — [Domain 03](<../../../03 Software Development and Engineering Terms/README.md>) names build→release words; operating them belongs to future tracks, not to vocabulary leaves.
4. **Cloud platform depth** (regions/zones/instances beyond naming, IAM policy authoring, cost engineering) — [Domain 02](<../../../02 Hardware Infrastructure and Platforms/README.md>) names the nouns; this domain uses them (least privilege, managed services) without re-teaching.
5. **Team process and agile** (sprints, roles, collaboration rituals) — [Domain 07 Teamwork Agile and Interview Vocabulary](<../../../07 Teamwork Agile and Interview Vocabulary/README.md>); incident *response* vocabulary stays here, process ownership lives there.

If you find yourself modeling threats, writing pipeline YAML, or operating flag systems inside this domain — stop; name the concept in one line, link the neighbor that owns the practice, and move on.
