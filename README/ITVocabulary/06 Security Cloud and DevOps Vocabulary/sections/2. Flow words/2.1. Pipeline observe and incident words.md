## 2.1. Pipeline, observe, and incident words

### 1) **Pipeline automates the path**

**Definition** — A *pipeline* (CI/CD pipeline) automates Domain 03's conveyor: every commit triggers build → test → stage → (gated) prod. *CI* (continuous integration) merges and verifies often; *CD* is *delivery* (always releasable, human releases) or *deployment* (automatic releases). *Artifact promotion* moves the same tested build between stages.

- **What problem it solves**: manual releases are snowflakes — unrepeatable, unreviewable, and terrifying at 5 PM on Friday. Pipelines convert tribal release knowledge into versioned configuration: the same steps, every time, with logs proving it. "It worked in CI" becomes meaningful precisely because CI is identical for everyone.
- **Modern guidance** — pipeline-as-code (workflow files in the repo, reviewed like code), green-main discipline (broken builds block merges, fixed immediately — a red main normalizes shipping blind), and stage parity (test what you ship: same artifact promoted, per [Domain 03, 2.1](<../../../03 Software Development and Engineering Terms/sections/2. Ship words/2.1. Build test release and deploy.md>)).

```text
# Bad: snowflake release (unrepeatable, unprovable)
"Deploying from my laptop — I ran the tests locally,
 built the bundle here, copying it to prod now."

# Good: pipeline release (repeatable, evidenced)
"Release 2.14.1: CI green (unit+integration+e2e logs linked),
 artifact sha:9f3c… promoted staging→prod. Same bits tested,
 same bits shipped — rollback is one revert."
```

### 2) **Logs, metrics, traces observe it**

The three observability pillars: *logs* (timestamped event lines — what happened), *metrics* (aggregated numbers over time — how much/how fast: latency, error rate, CPU), *traces* (request journeys across services — where time went). *Alerting* fires on metric thresholds; *dashboards* display them; *SLOs* ([Domain 01, 3.1](<../../../01 Core IT Concepts and Professional Jargon/sections/3. Everyday professional jargon/3.1. Core acronyms API SDK SLA KPI and friends.md>)) set the targets.

- **Why it matters (debugging, sleep)**: each pillar answers different questions — logs explain the single failure ("why did charge 123 fail?"), metrics reveal the pattern ("error rate tripled at 14:20"), traces locate the slow leg across services. Teams with one pillar debug with one eye closed; teams with none debug by user complaint — the most expensive monitoring there is.
- **Modern guidance** — structure logs (JSON with request IDs, never free-text-only), alert on symptoms (error budget burn, user-facing latency — not CPU wiggles), and trace across service boundaries (propagate correlation IDs). Alert fatigue kills on-call effectiveness faster than any outage — every alert must name an action, or it becomes a dashboard.

### 3) **Incident, severity, postmortem**

An *incident* is declared abnormal operation (formally opened, coordinated, resolved). *Severity* grades urgency (SEV1 = users down, money burning; SEV3 = degraded, workaround exists). A *postmortem* (blameless retrospective) extracts systemic fixes — never culprits — with owned action items.

- **Why it matters (learning, culture)**: undeclared incidents get ad-hoc responses (five people debugging five theories in DMs); ungraded ones get uniform panic (SEV3 paged like SEV1 burns the team out); blamed ones get silence next time (nobody reports near-misses, so the same failure recurs bigger). The three words are a learning machine: declare, grade, extract.
- **Modern guidance** — declare early (cheaper to downgrade than to discover late), communicate on a schedule (status every 15–30 min beats sporadic genius), and write postmortems within days with action items that have owners and dates. "No blame" is load-bearing, not kind: blame ends reporting, and unreported failures compound.

### 4) **Common confusion**

- "CI/CD means no humans" — automation removes toil, not judgment: releases still need decisions (when, how much, rollback criteria) — CD-deployment just executes decided policy fast.
- "More metrics means more observability" — unalerted, undashboarded metrics are write-only; observability is questions-answerable, not bytes-collected.
- "Postmortem means finding who caused it" — the cause is always systemic (why was the mistake possible? why undetected?); names in postmortems end the reporting that prevents recurrence.

### 5) **Mentor note**

Run game days (simulated incidents) quarterly: juniors practice declare-grade-communicate-postmortem on a fake SEV2 before facing a real SEV1 at midnight. Incident vocabulary learned calmly transfers to crises; vocabulary met first during a real outage arrives with panic attached and sticks poorly.
