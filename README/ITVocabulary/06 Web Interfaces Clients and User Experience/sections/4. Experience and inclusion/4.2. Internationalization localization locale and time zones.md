## 4.2. Internationalization localization locale and time zones

Changing a booking page's language does not tell the application which time zone
the user wants or which currency an amount represents. A translated label can
still accompany an ambiguous date, a clipped control or the wrong meeting time.
Separate the choices before calling the product localized.

### 1) **Distinguish preparation from audience-specific adaptation**

**Internationalization**, abbreviated **i18n**, is designing a product so it can
support audiences with different languages, regions and cultural conventions.
The 18 counts the letters between the initial i and final n. **Localization**,
abbreviated **l10n**, adapts the product for a particular audience; 10 similarly
counts the interior letters. These are abbreviations, not version numbers.
The [W3C explanation](https://www.w3.org/International/questions/qa-i18n)
provides the preparation/adaptation distinction and explicitly notes that usage
can vary.

Keeping translatable messages separate from application logic is an i18n measure.
Supplying reviewed translations and suitable formatting for a target audience is
localization work. **Translation** changes language content; localization can also
involve number/date presentation, names, text direction and layout. A product can
be prepared for another language before that translation exists.

**RTL** means **right-to-left**, and **LTR** means **left-to-right**, when describing
text direction. A direction change needs attention to actual reading and layout;
it is not a command to reverse every character or every icon. Mixed text, numbers
and identifiers need coherent presentation. The text-representation domain owns
Unicode/encoding mechanics; supporting Unicode alone does not provide every
localization decision.

For a small review exercise, compare “we extracted the message strings” with “the
new language is ready.” The first describes preparation. The second needs evidence
that messages are supplied, meaningful and usable in the actual workflow. Test
expanded labels and error messages as well as the default happy-path screen;
translation completeness and usable layout are different checks.

### 2) **Read locale language and formatting choices separately**

A **locale** is a set of language/regional conventions used for operations such as
formatting or sorting. A **language tag** identifies a language and possibly script,
region or other refinements. Tags such as `en-GB` can be used by APIs when selecting
locale behavior; a language tag does not identify a person's location or citizenship.
[W3C's language-tag guidance](https://www.w3.org/International/questions/qa-lang-2or3)
points to BCP 47 and the IANA subtag registry rather than inventing codes from
country names.

`en-GB` requests English with a regional refinement in relevant APIs. It does not
mean the user is physically in Britain, uses British currency for every transaction
or wants every event displayed in a British time zone. Set the choices needed by
the application instead of treating one preference as evidence of another.
[MDN's date/time formatter reference](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat)
shows locale and `timeZone` as distinct inputs.

Consider these **constructed display artifacts**:

| Artifact | Missing question |
|---|---|
| `03/04/2026` | Which date order and calendar were intended? |
| `1,234` | Is the comma a grouping mark or decimal mark under the stated convention? |
| `$25` | Which currency does the application contract mean? |
| `Meeting at 09:00` | On which date and in which time-zone context? |

The answer is not to guess from the reader's own defaults. Preserve structured
values and their meaning, then format them using an explicit or intentionally
selected preference. For a price, formatting a currency symbol does not convert
the amount to another currency. For a date, changing its presentation does not
change which calendar date or instant the application intended.

### 3) **Separate instants offsets zones and calendar dates**

An **instant** is a particular point on the timeline. **UTC**, **Coordinated Universal
Time**, is the reference used here to describe one. A **UTC offset** is the difference
between local clock time and UTC at a particular instant. A **time zone**, such as
`Asia/Tehran` or `Europe/London` in IANA naming, carries a location-related history
and rules for determining offsets. The identifier is not merely another spelling
of one permanent offset.

**DST**, **daylight saving time**, is a seasonal clock adjustment used in some
places. Rules can change, and a local clock reading near an offset transition may
be skipped or repeated. The [IANA Time Zone Database](https://www.iana.org/time-zones)
records rule history and receives updates for political changes. A fixed offset
can describe a particular conversion; it cannot by itself express all the future
rules of a named zone.

Run this deliberately **fixed-offset** observation. It does not consult a named
zone or assert a country's future policy. Save as `time_views.py`; run with
`python3 time_views.py`. Checked on Python 3.14.4/Linux x86_64, 2026-10-18, with
only the standard library and no time-zone database dependency.

```python
from datetime import datetime, timedelta, timezone

moment = datetime(2026, 10, 18, 12, 0, tzinfo=timezone.utc)
chosen_offset = timezone(timedelta(hours=3, minutes=30))
other_view = moment.astimezone(chosen_offset)

print("UTC view:", moment.isoformat())
print("Offset view:", other_view.isoformat())
print("Same instant:", moment == other_view)
```

Observed output:

```text
UTC view: 2026-10-18T12:00:00+00:00
Offset view: 2026-10-18T15:30:00+03:30
Same instant: True
```

The clock fields differ by three hours and thirty minutes, but describe the same
instant. `astimezone` converts the representation; it does not postpone the meeting.
The [Python datetime contract](https://docs.python.org/3.14/library/datetime.html#datetime.datetime.astimezone)
defines that conversion. The example supplies the offset explicitly, so the result
does not depend on the computer's default local zone.

A **calendar date** such as a birthday or a date-only booking field need not denote
an instant at all. “The office opens at 09:00 on future weekdays” is a recurring
local-time rule, also different from one completed event's timestamp. Preserve the
meaning required by the product: an event already observed, a date-only value and
a future local schedule need different context. “Store everything as a UTC instant”
is therefore not a sufficient data-model rule for all three.

A **timestamp** is a recorded time value in a stated representation and scale.
A bare number or offset-free text does not tell a reader its units or intended
zone. Ask for the representation and application contract before comparing logs
or deciding whether a meeting moved. Full calendar arithmetic remains deeper study.

### 4) **Common confusion**

Locale, UI language and time zone are related user preferences, not interchangeable
facts. A traveler can read English, use a non-Gregorian calendar and view a meeting
in its venue's time zone. Support the actual choice instead of inferring it from
the first available setting.

An offset is not a complete named-zone rule, and a formatting change is not a
change in the underlying value. The observed `True` concerns the two representations
in this example; it does not establish that two arbitrary local clock strings
identify the same moment.

### 5) **Performance note**

Translation lookup, formatting and loading locale/time-zone data can require work,
but the abbreviations themselves have no runtime effect. Data size and repeated
formatting costs depend on the library, runtime and use pattern. This example
checks conversion meaning, not formatting throughput. Do not justify dropping
needed locale or time-zone context with an unmeasured “UTC is faster” claim.

### 6) **Mentor note**

Ask what additional information each display artifact needs, then ask why changing
language must not silently change a meeting's instant. Follow with the birthday
case: a strong answer distinguishes a date-only value from an event timestamp.
For the runnable example, the learner should explain why different clock fields
can still compare equal and why the explicit offset is not a future zone policy.
