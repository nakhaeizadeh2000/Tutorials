## 6.1. Boundaries of client and experience vocabulary

You can now interpret “an installed client hydrates a generated page and restores
its draft” without assuming that the user completed the task. The next step is
knowing which explanation to revisit and which question requires implementation
work beyond vocabulary. That boundary keeps a short definition from pretending
to be a browser, design or platform engineering course.

### 1) **Route client questions to their existing conceptual owners**

Use this domain's canonical explanations for the following distinctions. A later
lesson can briefly remind the reader of the relevant meaning and link here rather
than rebuilding the entire comparison.

For example, a new API lesson may mention that browser-held state is sent under
applicable rules. It should introduce the minimum context needed to follow the
exchange, then link to the storage owner for the full lifetime comparison. This
boundary avoids both duplicate instruction and making beginners follow links just
to decode the current sentence.

### 2) **Separate terminology competence from implementation work**

JavaScript syntax, execution and language-specific formatting belong to the
existing JavaScript track. Its
[browser script lesson](<../../../../JavaScript/01 Fundamentals and Mental Model/sections/3. Running JavaScript today/3.1. Browser script tags DevTools console and module scripts.md>)
is a language-host route, while
[number formatting](<../../../../JavaScript/12 Numbers Dates Math and Temporal/sections/2. Parsing and formatting/2.2. Formatting numbers toString toFixed toPrecision toExponential and Intl.NumberFormat.md>)
provides the detailed JavaScript operations. This vocabulary domain owns the
cross-language meanings and limits, not a second implementation of those lessons.

Knowing the term hydration does not establish the ability to configure a framework,
repair every mismatch or design a streaming application. Knowing WebView does not
verify a native plugin or a mobile package. The root curriculum's React, Next.js,
Electron and Mobile tracks are deeper implementation routes when available; naming
them here does not make unbuilt content a prerequisite or a completed resource.
Use current originating platform/framework documentation for the actual supported
implementation and version.

Accessibility needs interaction design, content, implementation and evaluation.
This domain introduces terms and evidence questions; it does not certify a product
against WCAG. Likewise, translating words and recognizing locale tags is not a full
localization engineering or linguistic review. A substantive implementation task
needs its own requirements, appropriate expertise and verified environment.

Other approved vocabulary domains build on these concepts without owning them
again. API contracts explain exchanges; security explains identity and access
mechanisms; testing explains test scope; performance explains measurements. Those
are subsequent learning destinations. Do not use them as unexplained prerequisites
or infer that their entire engineering subject has been taught here.

### 3) **Write a precise handoff from a mixed product claim**

Consider this **constructed proposal**:

```text
We have a full-stack PWA, so it is native, offline and accessible everywhere.
The initial HTML contains the booking details, so hydration is already complete.
The draft reappears and the cookie exists, so the server saved the reservation.
Changing the UI language will choose the meeting time zone automatically.
```

A useful review separates the missing evidence rather than merely replacing the
sentence with more acronyms. For platform support, name the actual runtime and
checked installation/offline tasks. For accessibility, specify the complete booking
path and appropriate evaluation scope. Full-stack work describes a span of
responsibilities; it supplies none of those guarantees by itself.

For rendering, inspect generation and client initialization separately. HTML
content alone does not establish a hydration mechanism or completion. For state,
inspect the service's accepted result: local draft recovery and a stored cookie
do not decide whether the reservation exists. For localization, preserve the
meeting's intended time context rather than deriving it from a language preference.

An explained handoff is: “Document the supported client environments and required
offline tasks. Verify the booking interaction and access barriers independently
of initial content delivery. Trace the server's reservation result separately from
local draft and cookie state. Specify language/format and meeting-zone preferences
as distinct choices.” These are requirements for further evidence, not claims that
the implementation has been repaired or tested.

As practice, suppose the proposal adds a genuine service response confirming the
reservation identifier. That supplies new evidence for that reservation outcome;
it still does not establish every platform's offline support, accessibility or
meeting-zone behavior. Update the relevant conclusion without promoting one
successful operation into a universal product guarantee.

### 4) **Common confusion**

A vocabulary boundary does not mean the concepts are unrelated. A real booking
feature combines client state, service contracts, time semantics and accessible
interaction. The boundary assigns the full explanation to an owner so integration
can refer to it precisely.

A framework or platform name also does not replace a product requirement. “Use a
PWA” still leaves questions about supported browsers, installation, stored data,
recovery and successful user tasks. Start from the desired outcome and use the
name to investigate the relevant mechanisms.

### 5) **Performance note**

Naming owners and improving a handoff has no direct effect on application speed.
It helps keep a measurement attached to the right stage: server generation,
resource loading, client initialization, interaction or service response. This
proposal supplies no timing or workload evidence. A successful local draft restore
cannot serve as a benchmark for any of those stages.

### 6) **Mentor note**

Ask the learner to select one full explanation for each mistaken inference in the
proposal, then name the artifact a reviewer would need next. A strong answer uses
the existing owner, preserves known facts and requests a concrete missing result.
It should become more precise when the service confirmation is added, while
leaving unrelated platform and user-experience claims unresolved.
