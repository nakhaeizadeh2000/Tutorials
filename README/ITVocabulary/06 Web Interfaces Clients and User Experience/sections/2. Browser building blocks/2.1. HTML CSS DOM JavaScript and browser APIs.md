## 2.1. HTML CSS DOM JavaScript and browser APIs

A page can contain the right text in its saved file while showing different text
after a click. To describe that change precisely, distinguish the document source,
the browser's current document objects, presentation rules and the code using them.
This lesson uses a small complete page; it does not require a frontend framework.

### 1) **Identify the roles of the browser building blocks**

**HTML** means **HyperText Markup Language**. Markup identifies parts of a document
and their meaning: a heading, paragraph, link or button. A **tag** is source syntax
such as `<p>`; an **element** is the document component it describes. An **attribute**
adds information to an element, such as an identifier. HTML gives content structure
and semantics, rather than merely telling the browser which words to make large.
See [MDN's HTML introduction](https://developer.mozilla.org/en-US/docs/Web/HTML).

**CSS**, **Cascading Style Sheets**, expresses presentation rules, including layout
and text appearance. A **selector** identifies the elements a rule applies to;
a **declaration** gives a property and value. In `.changed { font-weight: bold; }`,
the selector matches elements with the `changed` class, and the declaration requests
bold text. CSS is a language with its own rules, not a JavaScript library.
[MDN's CSS introduction](https://developer.mozilla.org/en-US/docs/Web/CSS) explains
its presentation role. A browser also applies default styles, so removing author
CSS does not imply that every element will look identical.

**JavaScript** is the programming language used by this example to react to a
button action. Variables, functions and assignment belong to the language. The
**DOM**, **Document Object Model**, provides document objects and operations that
code can use. It represents a document as a tree of nodes, including elements and
text. The browser constructs these objects from HTML and can subsequently change
them. The DOM is not the saved HTML file or a screenshot of the page.

A **browser API** is a programming interface supplied by the browser environment.
The DOM is one such family of capabilities. Its presence is not guaranteed merely
because another environment runs JavaScript. The distinction between the language
and the document API is explained in
[MDN's DOM overview](https://developer.mozilla.org/en-US/docs/Web/API/Document_Object_Model).
Check a particular environment's API support instead of treating “JavaScript
supported” as a promise of every browser facility.

### 2) **Trace a complete source-to-document change**

Save the following as `page.html` in an otherwise empty example folder. It has no
external libraries, images or network dependencies. The browser runs the JavaScript;
Python only serves the file locally. The example was checked on Linux with Python
3.14.4 and Google Chrome 151.0.7922.173 on 2026-10-18. These are observed versions,
not a minimum browser-version claim.

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Vocabulary browser demo</title>
  <style>
    .changed { font-weight: bold; }
  </style>
</head>
<body>
  <h1>Vocabulary browser demo</h1>
  <p id="status">Status: waiting</p>
  <button id="update" type="button">Update status</button>
  <script>
    const statusLine = document.querySelector("#status");
    const updateButton = document.querySelector("#update");
    updateButton.addEventListener("click", () => {
      statusLine.textContent = "Status: updated";
      statusLine.classList.add("changed");
    });
  </script>
</body>
</html>
```

In a terminal whose working directory is that folder, run:

```bash
python3 -m http.server 8000 --bind 127.0.0.1
```

Open `http://127.0.0.1:8000/page.html` in the browser. If port 8000 is already in
use, choose an unused port and change both the command and browser address. Stop
the local server with Ctrl+C when finished. This is a local learning server, not
a production hosting setup.

Initially the page shows **Status: waiting** and an **Update status** button.
Activate the button: the paragraph becomes **Status: updated** in bold. Reloading
the page restores **Status: waiting**. The checked browser showed precisely these
transitions; text weight changed from its normal style to bold.

Read the cause in order. The HTML gives the paragraph the `id` value `status` and
the button the value `update`. An **ID** identifies an element in this document;
keep these IDs unique. The script is after those elements, so they already exist
when this example queries them. `document.querySelector("#status")` finds the
paragraph using an ID selector and stores the resulting object reference in
`statusLine`. The second query finds the button.

The call to `addEventListener` registers a function to handle the button's
`click` event. An **event** is a notification of something happening, and the
**listener** is code registered to respond. The function inside `() => { ... }`
runs when that event is handled; registering it does not itself update the text.
This vocabulary follows the
[EventTarget registration contract](https://developer.mozilla.org/en-US/docs/Web/API/EventTarget/addEventListener).
It differs from the earlier network meaning of a listener waiting for connections.

Inside the handler, assigning `textContent` replaces the paragraph's text content.
Then `classList.add("changed")` adds a class to that same element. The CSS rule now
matches and requests bold text. These are two separate changes: document content
and a class affecting presentation. The
[textContent](https://developer.mozilla.org/en-US/docs/Web/API/Node/textContent) and
[classList](https://developer.mozilla.org/en-US/docs/Web/API/Element/classList)
references define those operations. No server request or saved-file rewrite is
performed by the handler.

You can use the browser's developer tools **Elements** or **Inspector** panel to
inspect the current paragraph. After the click, it has the changed class and updated
text. Opening the saved `page.html` in an editor still shows the original waiting
text. Reload creates the page again from that original content; this example has
no persistence mechanism. A live document inspection and source-file inspection
therefore answer different questions.

### 3) **Attribute behavior and failures to the right capability**

Consider two variations as a reading exercise. If only the `<style>` block is
removed, the handler still updates the text and adds the class, but this example's
bold rule is absent. If only the `<script>` block is removed, the heading, paragraph
and native button still exist; the custom update is absent. HTML itself supplies
many built-in behaviors, such as following links and operating native controls.
Do not infer that every interaction requires author-written JavaScript.

Now consider a fictional report: “The button is visible, so our JavaScript works.”
The conclusion does not follow. HTML can provide the button even if the script did
not run. A better check observes the intended text change and then inspects an
error if it does not occur. If the text changes but the intended appearance does
not, check the class and applicable CSS rather than assuming the handler never ran.
These observations narrow the question; they do not rule out every other cause.

Use the same reasoning across hosts. A command-line JavaScript process can compute
strings and numbers without a page document. An API named `document` belongs to the
particular document environment, not to every execution of the language. Full
JavaScript syntax and host mechanics remain with their linked language owners.

### 4) **Common confusion**

A DOM node and an HTML tag are related but different: one is an object in the
current document representation, the other is source notation. Script changes can
make the current DOM differ from the source that initialized it. Conversely, a
screenshot shows appearance and cannot establish which source or API caused it.

“Class” also needs context. The `changed` CSS class is a label on an element used
for matching. It is not a JavaScript class declaration. A team saying “change the
class” should make the intended meaning clear from the artifact and operation.

### 5) **Performance note**

Loading resources, executing code and updating presentation can contribute to a
page's work. Merely identifying HTML, CSS or JavaScript establishes no timing or
speed ranking. This tiny demonstration checks state changes, not rendering cost
or a frame-rate target. Keep the content-change observation separate from any
later measurement of how long a larger update takes; the next lesson explains
rendering terminology rather than deriving speed from a technology name.

### 6) **Mentor note**

Ask the learner to point to the source of the initial text, the operation changing
it and the rule making it bold. Then ask what remains after removing just the
style block. A sound explanation preserves the JavaScript/DOM change and removes
only the rule's presentation contribution. Follow with the reload question to
check whether the learner has mistaken current document state for saved data.
