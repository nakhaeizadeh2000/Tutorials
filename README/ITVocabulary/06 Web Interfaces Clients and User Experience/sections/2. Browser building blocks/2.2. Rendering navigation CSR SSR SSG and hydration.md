## 2.2. Rendering navigation CSR SSR SSG and hydration

A catalog can show a product name before its custom filter starts working. It can
also change to another product without loading a new document. Neither observation
alone tells you where its initial content was generated. Read rendering claims by
separating content generation, document navigation and client initialization.

The HTML/CSS/DOM lesson is the prerequisite. The catalog timelines below are
constructed reading exercises, not measurements from a deployed application.

### 1) **Separate content generation from browser display and navigation**

**Rendering** means producing a representation for use or display, but the intended
stage matters. In “render HTML on the server,” software produces HTML representing
content. In “the browser renders the page,” the browser turns document content and
presentation information into the displayed result. Server-generated HTML still
needs a browser to display it. The server does not send the user's screen pixels
merely because a project uses server-side rendering.

**Navigation** means moving to another page or view. A **document navigation**
loads or restores a document in the browser. **Client-side navigation** commonly
means application code updates the view within the current document, possibly
changing the address and browser history too. Such a change can still fetch data
from a server; “no full page reload” does not mean “no network request.” A **route**
in this UI context is the application's mapping from a location to a view.

An **SPA**, **single-page application**, uses one document for a sequence of
application views updated by code. “Single page” does not mean one screen, one
address or no server. An **MPA**, **multi-page application**, organizes its experience
around multiple documents; an individual document can still contain scripted
updates. These labels describe navigation organization, not a rule assigning
where all initial HTML must be produced. See the
[MDN SPA explanation](https://developer.mozilla.org/en-US/docs/Glossary/SPA) for the
within-document model. A direct visit to an address and a later in-app transition
can take different paths, so record which action was inspected.

### 2) **Locate CSR SSR and SSG on a content timeline**

**CSR** means **client-side rendering**: browser-side JavaScript constructs or
updates the relevant document content. A common initial-load arrangement sends a
small page shell first and constructs the main view after the code and required
data arrive. That is an example, not a requirement that every CSR page start empty.
The [MDN CSR reference](https://developer.mozilla.org/en-US/docs/Glossary/CSR)
explicitly notes that client rendering and server rendering can coexist.

**SSR** means **server-side rendering**: server-side code generates HTML content
for delivery to the client. In comparisons with static generation, SSR commonly
means generating that content in response to a request. Some authors use SSR more
broadly for server-produced HTML, so ask about timing when it affects a decision.
SSR does not prohibit client code from updating the result later. The
[MDN SSR explanation](https://developer.mozilla.org/en-US/docs/Glossary/SSR)
distinguishes request-time generation from build-time generation.

**SSG** usually means **static site generation** in an architecture discussion, or
**static site generator** when naming the tool. It produces page files ahead of
requests, often during a build. A server can deliver those already generated files
without rebuilding the page for that request. The
[MDN generator entry](https://developer.mozilla.org/en-US/docs/Glossary/SSG)
explains the content-to-files role. “Static” describes that generated artifact;
it does not require every later interaction or data value in the browser to remain
unchanged. A generated documentation page can still have a scripted search box.

For the main product heading, compare these **fictional paths**:

| Path | Before the browser asks | Response and browser work | Supported description |
|---|---|---|---|
| A | A build produced product-page HTML | The server sends that file; the browser displays its heading | Static generation for that heading |
| B | No prepared product-page HTML exists | The request handler obtains product data, generates HTML and returns it | Request-time SSR for that heading |
| C | Only a shell and scripts are prepared | The browser receives the shell; code obtains data and creates the heading | CSR for that heading |

This table states how the artifacts were produced. Seeing a heading in an HTML
response establishes that the response contains it; it does not alone distinguish
A from B. To do that, inspect the generation process or reliable deployment/request
evidence. A filename ending in `.html` does not settle the question either.

Different parts of one page can follow different paths. A prebuilt article can
include a browser-generated account panel, while a server-generated first view
can use client-side navigation afterward. Describe the relevant region and action
instead of forcing the whole product into one exclusive box.

### 3) **Distinguish hydration from content visibility and later updates**

**Hydration** initializes client application behavior using HTML already generated
for that application. The client connects its logic and state to the existing
document structure instead of starting the view solely from an empty container.
The term is common in component frameworks; it does not mean adding water,
fetching every later response or simply displaying HTML.

For a concrete implementation contract, React's
[hydrateRoot reference](https://react.dev/reference/react-dom/client/hydrateRoot)
describes connecting React to its existing server-rendered HTML and expecting the
initial client output to match. This is evidence about that implementation, not
a requirement that every web page use React or hydration. Traditional links and
HTML controls can operate without a framework initialization step.

A **hydration mismatch** means the generated HTML and expected initial client
output disagree under the framework's rules. Imagine the server generated “Price:
20” while the initial client data produces “Price: 25.” Establish which data and
version each side used; hiding the warning alone does not explain or correct the
disagreement. Recovery behavior is implementation-specific. React warns that it
does not guarantee patching every attribute difference.

Read this **fictional catalog timeline**:

```text
The response already contains the product name, price and a Filter button.
The browser displays those elements.
The custom filter's client initialization has not completed.
Pressing Filter during that interval does not perform the promised filtering.
After initialization, the same action applies the filter.
Later, choosing another category updates the view in the same document.
```

The worked answer is that content visibility precedes readiness of this custom
behavior. The last row describes client-side navigation; it does not prove the
initial response was produced by CSR. Nor does the card establish request-time
SSR versus SSG, because it provides no generation-time evidence. If the framework
uses hydration, investigate that initialization path and any errors. Do not label
all visible-but-inactive controls “hydration bugs” without evidence of the mechanism.

Streaming SSR, partial hydration and selective hydration are further labels you
may encounter. Streaming sends generated response content in portions rather than
waiting for all of it. Partial/selective approaches limit or prioritize which
regions receive client initialization; exact meanings differ across tools. These
labels refine the timing and scope questions, not a guarantee that every control
is immediately usable. Framework-specific implementation belongs to deeper study.

### 4) **Common confusion**

SSR does not mean “no JavaScript,” SSG does not mean “no interaction,” and an SPA
need not use CSR for its first view. Each mistaken equation combines separate
questions. For the catalog, name the initial content producer, the later navigation
mechanism and the control's readiness separately.

“Prerendering” also needs context: it can mean preparing HTML before requests, or
a browser preparing a likely future navigation. Ask which actor and artifact are
intended before inferring either behavior. “Rehydration” is sometimes used as a
synonym for hydration and sometimes for restoring state; consult that tool's usage.

### 5) **Performance note**

Early visible content and fast response to an action are different outcomes.
Server work can delay the response; client generation or initialization can delay
useful behavior; prepared HTML can be reused without regenerating it per request.
The amount of work, data freshness needs and actual request path still matter.
The original [Rendering on the Web](https://web.dev/articles/rendering-on-the-web)
article by Jason Miller and Addy Osmani develops these trade-offs. Its labels are
useful questions, not a speed ranking. This lesson measures no server time,
client work, cache behavior or interaction delay.

### 6) **Mentor note**

Ask the learner to classify the heading in A–C, then remove the “build produced”
row from A. A strong answer reduces certainty about generation timing rather than
guessing from the HTML response. Next, ask why a button can be visible before its
custom behavior works, while a plain link may already work. The answer should
separate native browser behavior from the application's initialization contract.
