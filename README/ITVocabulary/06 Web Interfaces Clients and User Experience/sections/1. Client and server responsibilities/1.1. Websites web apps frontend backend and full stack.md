## 1.1. Websites web apps frontend backend and full stack

A booking page displays a button, checks an input and saves a reservation through
a server. The user sees one experience, but several responsibilities contribute
to its outcome. Calling a defect “frontend” merely because it appears on screen
can send the investigation to the wrong place.

This lesson builds on the network and software-tool vocabulary. The booking
feature is a constructed reading exercise; no website or booking service is
created, contacted or deployed.

### 1) **Distinguish a web experience from the roles serving it**

A **website** is a web presence made of related pages and resources. A **web app**
is a web experience emphasizing interactive tasks, such as editing a document
or making a reservation. These labels overlap. A site can contain an interactive
application, and an application can publish informational pages. Neither label
implies a particular framework, one-page design or required database.

For a particular web exchange, a **client** initiates a request and a **server**
handles it and sends a response. A browser commonly acts as a client, but these
are interaction roles. A server-side program can itself become the client of
another service. The relevant software may run on one development computer or
many machines; “server” does not require a special physical shape.

MDN's [web introduction](https://developer.mozilla.org/en-US/docs/Learn_web_development/Getting_started/Web_standards/How_the_web_works)
provides a useful browser/server orientation. Keep the roles precise rather than
treating every computer on the Internet as permanently one kind of participant.
The earlier network domain owns naming, addressing and transport; those steps
support the web interaction without defining its application meaning.

The browser can receive files already prepared for delivery, or content generated
for a request. Server code can return page content or data used by the client.
MDN's [client/server overview](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Server-side/First_steps/Client-Server_overview)
shows these different response responsibilities. “The page changed” does not
alone reveal which of them produced the new content; the rendering lesson will
make that distinction explicit.

### 2) **Separate frontend and backend responsibilities from deployment boxes**

**Frontend** commonly refers to the user-facing presentation and interaction
layer. **Backend** commonly refers to server-side application services, business
rules and data responsibilities. Team boundaries vary, so name the concrete work
when the labels could be ambiguous. These are useful responsibility categories,
not a universal standard assigning every file to exactly one team.

For the fictional booking feature, compare the following tasks:

| Task | Responsibility being discussed |
|---|---|
| Show the date picker and explain invalid input | User-facing presentation/interaction |
| Send the selected date in the agreed request | Client integration with the service contract |
| Decide whether the account may reserve this room | Server-side application policy |
| Check current availability and record a valid reservation | Server-side operation and authoritative state |
| Present the accepted reservation or a useful failure | User-facing outcome using the returned evidence |

**Authoritative state** here means the state the application treats as deciding
the reservation outcome. A browser can display a local selection before the
server accepts it. That preview does not make the reservation exist in the
application's deciding record. The database and API domains later develop the
relevant storage and contract terms; no database query language is needed here.

Client-side checks can help users correct input promptly. They cannot by themselves
establish that every incoming request satisfies a server's rules, because another
client can send different data. Conversely, a server rejection needs a useful
presentation if the user is to understand what happened. A correct rule and a
clear experience are related responsibilities, not competing definitions of
quality.

Do not classify layers solely by language. JavaScript can run in browser and
server environments, as the existing
[runtime/host owner](<../../../../JavaScript/01 Fundamentals and Mental Model/sections/1. What JavaScript is/1.2. Engines runtimes and hosts V8 SpiderMonkey JavaScriptCore Node Deno Bun.md>)
explains. Nor does “frontend” mean every contributing line executes only in the
browser: a server can generate user-facing page content. State execution location
separately from architectural responsibility.

Repository and deployment placement are different again. A single repository can
contain both layers, and one deployed service can deliver client files while
also handling application requests. Two teams or repositories can also collaborate
on one experience. None of those arrangements establishes an independently
deployable boundary without further evidence.

### 3) **Read full-stack and ownership claims as scoped work**

**Full stack** commonly describes work spanning frontend and backend. It can refer
to a developer's working scope, a team or a product framework. It does not promise
that one person has equal expertise in every security, accessibility, networking,
storage and operations topic. Ask which parts the role actually includes.

Use this **fictional failure card**:

```text
The user chooses a room and presses Reserve.
The client sends the documented room identifier and date.
The service rejects the request because another reservation now occupies it.
The client displays “Something broke” and offers no way to choose another room.
```

Where is the defect? The explained answer separates two questions. The card gives
no evidence that the conflict rejection is wrong: the room's state can change
between display and submission. The client's generic message, however, does not
help the user recover from the documented conflict. A useful change could explain
the current unavailability and preserve the user's other inputs, under the actual
product requirements.

The task may require checking the service's response contract and improving the
client's handling together. Assigning it to “the frontend” or “the backend” without
those details is less useful than naming the failed responsibility. If the card
instead showed a wrong room identifier in the request, the investigation would
change; the visible error location alone still would not settle it.

A clear handoff says: “Verify the conflict response contract and map that result
to a recoverable booking message. The server's stated rejection is consistent
with the changed room availability in this card. No successful reservation was
reported.” This connects ownership to evidence and an intended user outcome.

### 4) **Common confusion**

A website is not necessarily a set of unchanging pages, and a web app does not
necessarily need a large JavaScript framework. Those labels communicate emphasis,
not a mandatory implementation stack.

“The backend returned data” is also not “the user completed the task.” The client
must interpret and present the result, and the application contract must define
what was accepted. Keep the human workflow visible while identifying software
roles.

### 5) **Performance note**

Moving work between browser and server changes where processing, transfer and
waiting occur; a frontend/backend label does not establish a speedup. A responsive
input control can still wait on a slow application operation. This card measures
neither interaction delay nor reservation throughput, and it supplies no reason
to choose one deployment arrangement for performance.

### 6) **Mentor note**

Ask the learner to annotate the card with the actor, decision and observable
outcome at each step. Then change the evidence to a malformed client request.
A strong answer revises the investigation while retaining the same user goal,
and describes full-stack work as a concrete span of responsibilities rather than
an unlimited expertise claim.
