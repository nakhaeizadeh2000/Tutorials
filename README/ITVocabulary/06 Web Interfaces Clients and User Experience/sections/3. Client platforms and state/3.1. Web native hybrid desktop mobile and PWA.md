## 3.1. Web native hybrid desktop mobile and PWA

A product team says, “The mobile version is native, the desktop version uses web
technology, and the PWA works everywhere.” These statements mix device class,
implementation, distribution and capability. Separate those dimensions before
inferring what a user can install or do.

This lesson uses constructed product descriptions. No app, SDK, device permission
or browser installation is required. The earlier host/API lesson supplies the
execution-environment distinction; this lesson applies it to client products.

### 1) **Separate device targets from application implementation**

**Desktop** commonly describes applications intended for desktop/laptop operating
environments. **Mobile** commonly describes phone/tablet environments. These are
target and usage labels. They do not specify a programming language, require a
network connection or prove that a layout works with touch, keyboard and every
screen size.

A **web application** runs using web platform capabilities, usually through a
browser or embedded browser environment. It can be used on desktop and mobile.
A **platform-specific application** is built and packaged for a particular target
platform. **Native app** often means an app integrated with that platform's runtime,
UI or APIs, but teams use the word at different levels. Ask what is native: the
package, the interface controls, a library or the generated machine code.

“Native” is not a reliable synonym for “written without JavaScript.” For example,
[React Native's component introduction](https://reactnative.dev/docs/intro-react-native-components)
describes JavaScript working with platform-backed Android and iOS views. That is
a different interface model from rendering the whole UI as HTML in a WebView.
This example establishes a vocabulary distinction, not a requirement to learn
React or a claim that every component behaves identically on every platform.

**Cross-platform** means targeting more than one platform, often sharing some
source code. It does not promise that every file is shared, that all capabilities
are equal or that testing one platform verifies the others. Ask which platforms,
versions and features the claim covers. A shared calculation can coexist with
platform-specific window, input, notification and storage behavior.

### 2) **Recognize web containers and progressive web apps**

A **WebView** is a component that displays web content inside an application.
A **hybrid app** commonly combines web content with a platform application container
and access to selected native capabilities. A **bridge** or **plugin** can expose
an operation from that container to web-facing code. The availability and behavior
of the operation depend on its implementation and target platform.
[Capacitor's introduction](https://capacitorjs.com/docs) is one concrete example:
it describes a native container and plugin interfaces for web-focused applications.
Do not infer unlimited device access from the phrase “native container.”

Desktop apps can use web technology too.
[Electron's introduction](https://www.electronjs.org/docs/latest) describes desktop
applications built with HTML, CSS and JavaScript while embedding Chromium and
Node.js. The result is distributed as a desktop application; it does not need to
be a page in the user's ordinary browser tab. Conversely, an installed window
alone does not prove Electron was used. Product appearance does not identify its
implementation reliably.

A **PWA**, **progressive web app**, uses web technology with capabilities associated
with installed applications, such as an app-like launch experience and, where
implemented, offline behavior. It still depends on a browser engine. Installation
does not transform its code into another UI framework. See
[MDN's PWA overview](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/What_is_a_progressive_web_app)
for that runtime distinction.

A **web app manifest** supplies descriptive/install information, such as a name,
icons and launch configuration. A **service worker** is a separately managed web
script that can, among other uses, support request handling and offline strategies.
Installation and offline behavior are distinct questions. The current
[MDN installation guide](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)
explicitly notes that service workers are not required merely for installability.
It also documents browser-dependent installation behavior. Do not reuse an old
universal checklist requiring one installation rule across every browser.

**Offline support** means some specified tasks remain available without a network
connection. It needs a scope: opening an already stored article, editing a local
draft and confirming a server reservation are different tasks. An icon or cached
launch screen does not establish that all three work. **Background operation**
means work while the app is not actively in the foreground; platform scheduling,
permissions and implementation still constrain it.

### 3) **Read a capability claim as a testable product contract**

Use this **fictional implementation card**:

| Client | Stated implementation | Stated checked behavior |
|---|---|---|
| Browser client | Web application with an install manifest | Installation checked in one named browser/version; no offline task checked |
| Android client | Web UI in a native container with a scanner plugin | Scan checked on one device; sync requires the server |
| Desktop client | Packaged Electron application | Local draft editing checked; server submission untested |

A reasonable description calls the second client hybrid and the third a desktop
app using web technology. Neither description tells us their full capability set.
The browser row supports its stated installation observation, not “works offline.”
The desktop row supports a local editing workflow, not completed submission. The
Android row does not verify the scanner on iOS simply because the UI code is shared.

Now rewrite “Our cross-platform app works everywhere, including offline.” A useful
answer is: “We have three client implementations. Installation, scanning and local
draft editing have been checked only in the environments listed. Define the
required offline tasks and target platform versions, then verify those outcomes
and the server-dependent submission path separately.” This preserves actual
evidence and identifies the missing product questions.

The original [web.dev capability guide](https://web.dev/learn/pwa/capabilities)
recommends checking a feature before use rather than assuming equal support.
**Feature detection** means checking whether the needed capability is available;
**fallback** means an alternative path when it is not. A scanner workflow might
allow manual entry where scanning is unavailable. That alternative still needs
validation against the real task; silently displaying an unusable Scan button
would leave the user without a useful path.

### 4) **Common confusion**

Installed is a distribution/launch property, while native or hybrid describes an
implementation relationship. A PWA, hybrid client and platform-specific client
can all have launch icons. An icon does not identify their runtime or guarantee
background work, offline data or device APIs.

Mobile is also not the opposite of web. A phone can run a web application, and a
desktop application can use web content. State both the target device environment
and the implementation when both matter.

### 5) **Performance note**

These labels identify possible sources of work, not a measured ranking. Startup,
rendering, memory use, plugin calls and server communication depend on the actual
implementation and workload. Sharing code may reduce development duplication
without making an operation faster. This card contains no timing, memory or
battery observations, so it cannot justify “native is always faster” or “one
cross-platform build has the same cost everywhere.”

### 6) **Mentor note**

Ask the learner which card row proves offline submission. The sound answer is
none, with a reason tied to the stated checks. Then ask for two separate questions
about the Android client: one about the UI's implementation and one about scanner
availability on another platform. Reward the separation of artifact, environment
and supported task rather than a preference for a platform label.
