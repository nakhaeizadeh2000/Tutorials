## 3.2. Cookies browser storage sessions and local state

A user reloads a page: its draft remains, its selected tab resets, and the service
asks them to sign in again. “The session was lost” is too ambiguous to explain all
three observations. Identify which state was stored where, how long it was meant
to last and which component decides whether it is still valid.

This lesson is vocabulary and artifact reading. Its examples are fictional; they
do not inspect your browser data, set a real cookie or implement authentication.

### 1) **Separate application state from its storage mechanism**

**State** is information describing the current situation of a program or workflow:
the selected tab, draft text, remembered language or accepted reservation. **Local
state** means state maintained on a particular client or component in the current
context. It can be temporary in memory or saved in browser storage. “Local” alone
does not specify lifetime, confidentiality or whether a server has a corresponding
record.

An **origin**, for ordinary HTTP(S) web addresses here, is the combination of scheme,
host and effective port. Different schemes, hosts or ports can therefore give
separate storage areas. This is a brief prerequisite for storage scope; the API
domain later owns full origin/site distinctions. Browser privacy rules can further
partition or restrict storage, especially for embedded content.

Compare the mechanisms without treating this table as a complete storage policy:

| Mechanism | What the name tells you | What it does not establish |
|---|---|---|
| In-memory page state | Current code or document holds the value | Saved draft, server acceptance or recovery after a fresh load |
| `sessionStorage` | String key/value storage scoped to origin and page session, associated with a tab | A shared login session or permanent record |
| `localStorage` | Origin-scoped string key/value storage designed to survive browser sessions | A backup, indefinite retention or server-side validation |
| IndexedDB | Browser database API for structured client data | A remote database or automatic synchronization |
| Cookie | Browser-held name/value data eligible for transmission with matching requests | Proof that the server accepts an identity or that the value is secret |

The [Web Storage overview](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API)
distinguishes its two key/value mechanisms. They are separate stores; writing a
key into one does not write it into the other. Storage code can later send stored
values to a server, but Web Storage does not automatically attach them to each
HTTP request.

A [page session](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage)
survives reloads and can be restored. Its tab-associated storage is separate from
another tab's storage. A newly opened page can initially receive a copy from its
opener, but subsequent changes are independent. Do not teach “session means one
load” or infer a shared mutable store from equal initial values.

[`localStorage`](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)
has no built-in item expiry time. Applications can implement their own expiry
rules, and private browsing, user deletion or browser policy can limit persistence.
Saving there is not a guarantee that the data will exist forever. Changing from
HTTP to HTTPS also changes the origin; an apparent missing value may be a different
storage area rather than a deleted key.

### 2) **Read cookie and session lifetimes separately**

A **cookie** can be set through a server response's `Set-Cookie` header. The browser
stores accepted cookie data and can send it in a later request's `Cookie` header
when the applicable rules allow. A **header** is named message metadata; the next
API domain teaches complete HTTP exchanges. Cookie selection depends on scope,
attributes, request context and browser policy. Cookies are not sent indiscriminately
to every server or every request. Some cookies can also be managed by page code.
The [MDN cookie guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies)
explains this client/server relationship.

A **persistent cookie** declares a lifetime through `Max-Age` or `Expires`.
A **session cookie** has neither lifetime attribute. Browser session restore can
restore session cookies, so “close the browser to guarantee logout” is not a sound
application contract. The [Set-Cookie reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)
describes that limitation and the attribute meanings below.

| Attribute | Vocabulary meaning |
|---|---|
| `Domain` and `Path` | Scope contributing to which requests receive the cookie |
| `Max-Age` and `Expires` | Relative or date-based expiry information |
| `Secure` | HTTPS transmission restriction, with localhost handling exceptions |
| `HttpOnly` | Prevent page-script access to the cookie; matching requests can still carry it |
| `SameSite` | Restrict cookie sending in cross-site request contexts |
| `Partitioned` | Opt into a separate cookie partition associated with the top-level site |

These are different controls. `HttpOnly` does not stop the browser sending a cookie,
and `Secure` does not mean encrypted storage on the device. **CHIPS** expands to
**Cookies Having Independent Partitioned State**. Its
[partitioned-cookie explanation](https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/Third-party_cookies/Partitioned_cookies)
shows why an embedded service need not see the same cookie under unrelated top-level
sites. This established feature belongs in the initial vocabulary; support still
needs checking for the actual browser versions. It is not a promise that all
cross-site privacy or identity issues are solved.

An **application session** is a context connecting a sequence of interactions.
A service may use a cookie carrying an identifier to find a server-side session
record. That record has its own validity rules. The cookie's presence and browser
lifetime do not make the record valid. Other session designs exist; “session” does
not universally mean one particular database table or cookie format. Identity and
authorization mechanisms are deeper topics in the security domain.

### 3) **Diagnose a constructed state-loss report**

Read this **fictional implementation contract and evidence**:

```text
Selected tab: kept only in page memory; defaults to Overview on a fresh load.
Draft: explicitly saved to localStorage before reload and read back afterward.
Login context: cookie identifies a server-side record; service expires it after
15 minutes of inactivity. The cookie itself remains present for a longer period.
After 20 minutes without activity, a fresh page load shows Overview, restores the
draft, sends the matching cookie, and receives a “session expired” result.
```

The explained answer has three causes, all supplied by the card. The fresh load
initializes the selected tab again. The draft is read from a distinct saved store.
The service rejects its expired session record even though the browser still has
and sends the cookie. There is no evidence that `localStorage` controls login or
that a missing cookie caused this rejection.

A precise handoff is: “The selected view resets as documented, the locally saved
draft restores, and the server rejects an expired session record. Review whether
that reset and expiry match the intended product behavior; the observed draft
restore does not establish successful submission.” If the final row instead said
the cookie was absent from the request, investigate storage/sending rules first;
do not retain a diagnosis whose supporting evidence has changed.

When a report says only “the data is gone,” ask which value, origin, browser/profile,
tab and action were involved. Distinguish a fresh load, browser restoration and
site-data clearing. Check the read/write result and server response separately.
Do not use deletion of all browser data as a substitute for understanding which
state failed; it destroys evidence and can remove unrelated drafts or preferences.

### 4) **Common confusion**

`sessionStorage`, a session cookie and a server session are three different concepts.
Their names share a word, but their boundaries and lifetimes need not match.
Likewise, “stored locally” does not mean “never transmitted”: application code can
read an allowed value and send it later.

A restored draft is a local recovery result. It is not proof that the server saved
it, and a signed-in-looking page is not proof that a later service operation will
be accepted. Keep display state, storage state and authoritative application state
separate.

### 5) **Performance note**

Cookie bytes add to requests that carry them. Web Storage reads and writes are
synchronous: the call completes before the same JavaScript execution continues.
Large or frequent operations can therefore affect responsiveness. IndexedDB offers
an asynchronous storage model, but its costs still depend on the workload. The
original [Storage for the web](https://web.dev/articles/storage-for-the-web)
article discusses these mechanism and quota trade-offs. Avoid a universal “local
is fast” conclusion; this lesson contains no timing or capacity measurement.

### 6) **Mentor note**

Ask which artifact proves each state in the card: page initialization, local read,
request cookie and server result. Then remove the server expiry explanation. A
careful learner now reports rejection with an unknown cause rather than claiming
to know the session policy. Ask why extending cookie expiry alone would not prove
the server session remains valid.
