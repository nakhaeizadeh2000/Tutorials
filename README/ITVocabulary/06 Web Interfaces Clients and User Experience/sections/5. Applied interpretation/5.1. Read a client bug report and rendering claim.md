## 5.1. Read a client bug report and rendering claim

“The native mobile frontend is broken even though SSR made it responsive” combines
several claims without identifying a failed task. This lesson turns such a report
into a scoped description and a useful next check. It uses the existing vocabulary;
it does not create a new browser, accessibility or debugging implementation course.

### 1) **Extract the environment action and expected outcome**

A useful client report identifies the client implementation, relevant versions,
starting state, action and expected versus observed result. A **reproduction** is
a set of conditions and steps that lets another person attempt the same failure.
It is more informative than “on mobile,” because a phone browser, an installed web
app and a packaged hybrid client can have different capabilities and state.

Use this **fictional investigation packet**. Every recorded test below belongs to
the invented scenario, not an execution performed for this tutorial.

```text
Client: browser application build demo-17, Chrome 151 on a Linux desktop.
View: a 390-by-844 CSS-pixel viewport, not a physical phone test.
Product requirement: a staff member can select a date using a keyboard, submit
one reservation, and recognize confirmation of the service's accepted result.
Navigation: direct visit, followed later by one in-app category change.
Generation record: the request handler generates initial catalog HTML per request.
Initial response: contains catalog text and the Filter button.
Client initialization: completes four seconds after content becomes visible in
this controlled test. Filter has no effect before completion and works afterward.
Keyboard observation after initialization: focus cannot reach the only date picker.
Pointer observation after initialization: the tester selects a date and submits;
the service accepts the reservation, but the page shows only “Done”.
A new staff participant asks whether the room is actually reserved.
Narrow screenshot: fields stack neatly; an automated scan reports no findings.
No installed PWA, hybrid package, touch device or screen reader was tested.
```

The expected outcome is the staff member's full reservation task. The packet
supplies separate observations involving custom readiness, keyboard selection and
confirmation understanding. It identifies a browser and viewport, not a native
mobile implementation. Its response-generation record supports request-time SSR;
that conclusion comes from process evidence, not the screenshot or HTML alone.

A narrow viewport is useful layout evidence. Keep it accurately labeled as such.
It does not reproduce a physical phone's input, operating system, browser engine
or installation state. Do not remove the observation because it is limited; record
what question it answers and what remains untested.

### 2) **Separate observation diagnosis and unsupported claims**

An **observation** is the reported behavior under stated conditions. A **hypothesis**
is a proposed explanation to investigate. The packet supplies a four-second
initialization interval, but not why initialization takes that long. Downloading,
execution and another dependency are different candidates; the evidence does not
select one. Likewise, the unreachable picker needs implementation investigation
before naming its precise code defect.

Compare these statements:

| Claim | Assessment from the packet |
|---|---|
| The first catalog view uses request-time SSR | Supported by the generation record |
| SSR guarantees that Filter works as soon as it appears | Refuted for this custom control by the stated observation |
| The failure is definitely hydration | Unestablished: the client initialization mechanism is not identified |
| Responsive layout proves the task is accessible | Unsupported; the keyboard barrier concerns the same required task |
| Nothing was reserved | Refuted for the pointer attempt by the service acceptance evidence |
| The feedback is clear for all new staff | Unsupported; the participant's question is contrary evidence in this case |
| The bug affects every mobile client | Untested; no mobile implementation was exercised |

The word **responsive** needs its context. The screenshot supports one layout
adaptation; it does not establish immediate response to input. Even after custom
initialization completes, the packet's keyboard problem remains. Waiting longer
cannot be assumed to repair a separately observed input barrier.

A scan's empty result also does not outweigh the reported keyboard task failure.
The [WAI evaluation guidance](https://www.w3.org/WAI/fundamentals/accessibility-intro/)
explains why tools alone do not establish accessibility. Preserve the scenario's
specific barrier and the scan's scope without inventing a claim about what every
automated tool can detect.

Now remove the generation record as a variation. The HTML response would still
contain catalog text, but we could no longer establish request-time generation
rather than a prepared file. Remove the service acceptance row instead, and “Done”
alone would not establish either accepted or rejected reservation. A sound diagnosis
becomes less certain when its evidence is removed.

### 3) **Write a handoff and choose discriminating follow-up checks**

A useful rewrite of the original report is:

> In browser build demo-17 at the stated narrow viewport, the catalog appears
> before Filter becomes usable. After initialization, keyboard input still cannot
> reach the required date picker. A pointer submission is accepted by the service,
> but “Done” leaves the observed new staff participant unsure of the outcome.
> The packet establishes request-time initial HTML generation and one layout
> adaptation. Mobile packaging, touch and screen-reader behavior remain untested.

This version gives another engineer concrete work without assigning every symptom
to one layer. Investigate the control's initialization path and the keyboard
interaction; review confirmation wording against the actual acceptance contract.
The [original question-asking guidance](https://jvns.ca/blog/2021/10/21/how-to-get-useful-answers-to-your-questions/)
by Julia Evans is useful here: include current understanding and the specific
missing fact, rather than asking the recipient to guess the entire situation.

Choose a follow-up that changes what you know. For the readiness interval, inspect
when the required code and data become available and where initialization is
waiting or failing. For the keyboard barrier, attempt the complete date-selection
path with the intended keyboard interaction and inspect the responsible control.
For confirmation, expose the accepted result clearly and observe whether intended
users correctly recognize it. These are proposed checks, not passed tests.

Give the checks independent acceptance evidence. A faster Filter does not establish
keyboard access; an operable picker does not establish understandable confirmation;
a clearer message does not establish a successful server operation. For a mobile
support claim, run the required task in a defined target mobile environment rather
than relabeling the desktop viewport observation.

For an interview discussion, ask which issue should be investigated first. There
is no universal answer without impact and release requirements. A strong answer
notes that the packet's keyboard barrier prevents a required path even after
initialization, then asks about affected users, alternatives and the release's
acceptance criteria. It does not dismiss that barrier because pointer submission
works or declare the whole product inaccessible from this one packet alone.

### 4) **Common confusion**

The visible location of a symptom does not identify its cause or owner. A screen
can display a correct service rejection badly, or show success while the actual
operation failed. Here the acceptance evidence is supplied explicitly; retain it
instead of diagnosing from the word “Done.”

A reproduction is also not a universal prevalence claim. One well-described
failure can justify investigation while its frequency across platforms remains
unknown. Extending a conclusion to every mobile or installed client requires
additional evidence, not a broader adjective.

### 5) **Performance note**

The packet's four seconds are fictional readiness evidence, not a benchmark
measured by this tutorial. They describe one interval, not a percentile, universal
SSR overhead or the service's reservation response time. A useful performance
follow-up defines the action, start/end events and environment before comparing
a proposed change. Keep keyboard access and confirmation quality visible even
if a later measurement shows faster initialization.

### 6) **Mentor note**

Have the learner mark every sentence in the handoff as evidence, uncertainty or
proposed action. Then remove the acceptance row and request a revised handoff.
The expected improvement is a weaker outcome claim and a targeted service-result
check. Reward a clear change in reasoning, not a longer list of tools or acronyms.
