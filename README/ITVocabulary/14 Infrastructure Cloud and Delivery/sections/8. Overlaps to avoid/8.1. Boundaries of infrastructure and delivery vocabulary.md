## 8.1. Boundaries of infrastructure and delivery vocabulary

Infrastructure vocabulary helps you locate execution, responsibilities and change
records. It does not supply a production provisioning script, a recovery procedure
or a universal architecture. Choose the next explanation from the question you
need to answer, rather than from the longest collection of platform names.

Keep terms with several meanings scoped. A C4 container is an application or data
store in a diagram; it need not be a Linux process container. Git staging prepares
a snapshot; a staging environment hosts a version for selected checks. A source
repository and an image repository also have different contents and operations.
Use a brief clarification and the appropriate owner instead of expanding the
whole infrastructure course whenever one of these words appears.

### 2) **Choose deeper study from the implementation task**

Provisioning and operating real infrastructure belong to the planned **Cloud &
IaC** track. Container image construction, runtime behavior and Kubernetes work
belong to **Docker**; pipeline implementation and delivery automation belong to
**DevOps**. Network gateway configuration belongs to **Nginx** where applicable.
These are future learning routes, not links to published content or prerequisites
for understanding this domain's examples.

Language and host behavior already have more precise published owners.
[JavaScript engines runtimes and hosts](<../../../../JavaScript/01 Fundamentals and Mental Model/sections/1. What JavaScript is/1.2. Engines runtimes and hosts V8 SpiderMonkey JavaScriptCore Node Deno Bun.md>)
explain that execution boundary. [TypeScript environment portability](<../../../../TypeScript/20 Production Checklist Migration and Interoperability/sections/3. Interop and Portable Code/3.2. Environment-portable code node browser edge.md>)
compares declared interfaces with actual host adapters. Neither a container label
nor matching declarations establishes that an application works on another host.
Check the target's real capabilities, settings and relevant behavior.

Keep stored-data recovery with the existing data vocabulary and eventual database
implementation study. Keep access enforcement with security vocabulary and the
actual application policy. Platform management does not replace either subject.
For application-oriented backend study, the retained vehicle is NestJS with the
Fastify adapter; framework mechanics belong to their own subject.

Reliability measurement and operational evidence are the next vocabulary domain's
work. Later **Production Toolchain** and **System Design** study develops real
operational implementations and design choices. Do not turn this boundary leaf
into guessed performance targets, a provider purchasing guide or a new pipeline.

### 3) **Turn a mixed portability and recovery request into useful handoffs**

Read this **fictional message**:

> The image digest is pinned, the shared TypeScript interface compiles, and our
> infrastructure plan has no changes. We can move the app to the edge unchanged.
> If it fails, switch the old flag off and the data will roll back too.

The packet supplies no edge-provider adapter or target execution. The infrastructure
plan covers only registered VM resources, while the application uses a process-local
counter. The flag controls the interactive screen. Existing data is stored in a
separate database; no data-recovery action has occurred.

A useful response identifies distinct next questions:

> The digest fixes the selected image object; it does not verify the edge host's
> support. Ask the application and host owners for the target runtime, adapter,
> configuration and actual behavior evidence. The plan's VM scope does not assess
> that application portability. Ask how the counter meets its required lifetime.
> Turning off the screen flag also supplies no database recovery. The data owner
> needs the intended recovery state and a compatible, verified procedure.

This preserves the migration goal without prescribing an unexamined deployment
or destructive restore. The responsibility handoff and the conceptual-owner table
serve different purposes: one finds who acts, the other finds the explanation.

Practice: add a successful target-host adapter check covering only a static text
lookup. That strengthens the stated lookup's portability evidence. It does not
verify the process counter's required lifetime, registration writes, every host
API or database recovery. Broaden the claim only as the evidence broadens.

### 4) **Common confusion**

A vocabulary boundary is not a prohibition on useful examples. This domain used
small records to explain the distinction; a complete provisioning, orchestration
or operational recovery implementation needs its own requirements and checks.

“No changes” also has a scope. It may describe a tool's covered resources rather
than application state, permissions or user-visible behavior. Match the claimed
outcome to what the record actually inspected.

### 5) **Performance note**

Routing a question to the right owner has no direct effect on identical program
execution. It can prevent wasted investigation or an unsupported migration choice.
An unchanged image or a successful static lookup provides no before/after latency,
capacity or startup comparison for the full workload. No performance measurement
or recovery-duration experiment was run in this boundary exercise.

### 6) **Mentor note**

Ask the learner to assign each sentence of the mixed message to artifact, host,
infrastructure, application-lifetime, exposure or data evidence. A sound answer
selects precise owners and describes the check still needed. Add the lookup result
and ask them to revise the support claim without calling the entire application
portable. Reward bounded, useful guidance rather than a list of tool names.
