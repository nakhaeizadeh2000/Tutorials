## 3.1. Clusters nodes pods workloads services and orchestration

A diagram says “three replicas behind a Service.” Before interpreting that as
three available machines, ask what is replicated, where the instances run and
which endpoints can actually receive traffic. This lesson introduces Kubernetes
names as product-specific concepts rather than universal meanings of those words.

Read the preceding container and image lessons first. References use Kubernetes
1.37 documentation checked 2026-10-20. The fictional records below are static;
no cluster, installation or provider account is required.

### 1) **Map orchestration responsibilities to clusters nodes and Pods**

**Orchestration** coordinates workloads and their supporting resources according
to specified policies. Container orchestration can create workload instances,
place them on available execution resources and respond to changes. It does not
make the application correct or guarantee that every requested state is achievable.
**Kubernetes**, often shortened to **K8s**, is one platform providing such facilities.

A **Kubernetes cluster** consists of a **control plane** and one or more worker
nodes. The control plane manages cluster state and coordination. A **node** is an
execution machine, which can be physical or virtual. A small learning cluster can
use one machine for several roles; a production diagram must show the actual
placement rather than assume one box per physical server.

Within the control plane, the **API server** exposes the Kubernetes API. A
**scheduler** assigns an unscheduled Pod to a suitable node. A **kubelet** is a
node agent responsible for its assigned Pods and their containers, working with
a container runtime. The [component overview](https://kubernetes.io/docs/concepts/overview/components/)
distinguishes those roles. The scheduler chooses placement; it does not itself
execute the application inside the Pod.

A **Pod** is Kubernetes's smallest deployable computing unit. It groups one or
more containers that are co-located and co-scheduled, with shared networking and
available shared storage arrangements. The [Pod explanation](https://kubernetes.io/docs/concepts/workloads/pods/)
distinguishes that grouping from container replication. A Pod containing a web
container and a helper is one Pod, not two independent replicas of the web server.
The helper and web container can use different image artifacts.

Do not group unrelated applications into one Pod merely because they belong to
the same company. Grouping couples their placement and Pod lifetime. Use separate
Pods when the intended units need independent placement and replication, then
review their communication and data requirements explicitly.

### 2) **Separate desired workloads from observed instances and network access**

A **workload** is the application or work being run. Kubernetes **workload resources**
are API objects used to manage its Pod instances. A **controller** repeatedly
observes relevant state and acts toward a **desired state**. This comparison and
response is commonly called **reconciliation**. Desired state is an instruction;
observed state is evidence of what currently exists or is working.

For example, a **Deployment** manages replaceable application Pods through
**ReplicaSets**, which maintain the requested number of matching Pod replicas.
A **replica** here is another application instance; it does not automatically
mean a database copy or an independently located machine. “Replicas: 3” expresses
a target count, not proof that three instances are ready or spread across hosts.

Other resources express different lifecycle needs. A **StatefulSet** manages Pods
requiring distinct identities and associated state arrangements. A **DaemonSet**
manages a Pod on each eligible node in its selected scope. A **Job** manages work
toward completion; a **CronJob** creates Jobs according to a schedule. These
[workload-management categories](https://kubernetes.io/docs/concepts/workloads/controllers/)
are orientation, not automatic database replication, exactly-once execution or
recovery guarantees. Their detailed behavior and configuration belong to Kubernetes study.

Pods are replaceable. A replacement Pod has a different identity even if it
reuses a name. The [Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)
explicitly distinguishes replacement from moving the same Pod to another node.
Replacement can still fail or wait because capacity, storage, images, permissions
or other prerequisites are missing. “Self-healing” needs that scope and outcome.

A Kubernetes **Service** is a network-access abstraction defining endpoints and
how they are exposed. In a common selector-based arrangement, **labels** are
key/value metadata on Pods and a **selector** chooses which labels match. The
Service's endpoint information follows relevant backend changes. A Service is
not the application's business logic, a Pod, an OS service manager or the
controller that creates the Pods.

A common **ClusterIP Service** offers a cluster-internal virtual address. Other
Service types and headless arrangements differ. The
[Service documentation](https://kubernetes.io/docs/concepts/services-networking/service/)
explains this abstraction and exceptions, including Services without selectors.
The mere existence of a Service does not show that it has eligible backends, is
reachable by a particular caller or exposes an application to the public internet.

A Pod's **Running** phase and its readiness are different observations. Running
can include a container starting or restarting; it does not establish success
of an end user's workflow. **Readiness** concerns the configured condition for
accepting relevant traffic. Its usefulness depends on what is actually checked.
Do not turn one successful probe into proof of authorization, data correctness
or every application dependency.

### 3) **Read a placement and endpoint packet without inventing availability**

Consider these **fictional, simultaneous records**:

| Record | Supplied fact |
|---|---|
| Cluster W | Control plane plus worker nodes N1 and N2 |
| Hardware placement | N1 and N2 are VMs on the same physical host H |
| Deployment `report` | Desired replica count is three |
| Pod P1 | On N1; one report container; Running and Ready |
| Pod P2 | On N2; one report container; Running but not Ready |
| Pod P3 | Pending and not assigned to a node; scheduling event states no suitable capacity |
| Service `report` | ClusterIP Service selecting the report Pods; ordinary ready-endpoint routing, with special unready/terminating handling excluded |
| Current eligible endpoint set | P1 only |
| External request evidence | No public entry configuration or successful client request supplied |

There are two worker nodes, three desired report replicas and only one current
eligible report endpoint. Those are three different quantities. P2's Running
phase does not make it Ready. P3's desired existence does not create execution
capacity. The Service does not fix those conditions by being present.

The two workers also share H. Different node names and guest kernels do not
establish separate physical failure domains. A **failure domain** is a boundary
within which a failure can affect multiple components. Here, H is a shared hardware
dependency. The packet supports no public-reachability or continuous-availability
claim, even though one endpoint is eligible.

Now add only a later observation that P2 becomes Ready and the eligible endpoint
set becomes P1 and P2. That establishes two eligible endpoints at that later
observation. It does not move either node off H, make P3 scheduled or demonstrate
that a public client completes a report. Report each improvement at its boundary.

Practice: remove the scheduling-event reason, leaving P3 Pending. Can you still
name insufficient capacity as the cause? No. Pending can cover several setup
stages. Inspect scheduling and container/image events before selecting a cause.
A status summary narrows the investigation without supplying every explanation.

### 4) **Common confusion**

A cluster is not necessarily several physical servers, and a Pod is not necessarily
one container. Replicated Pods do not imply replicated data. A Service exposes a
network boundary; it does not by itself create the application instances behind it.

A controller attempts reconciliation rather than promising instant convergence.
Likewise, replacing a Pod is not restoring every piece of application state.
A StatefulSet identity or a successful container restart still needs a data and
recovery design when the application depends on retained information.

### 5) **Performance note**

Scheduling and control loops consume resources, while placement and configured
resource availability influence workload behavior. More desired replicas can add
no usable capacity if they remain Pending, and replicas sharing a bottleneck may
not increase useful throughput. The packet measures neither orchestration overhead
nor application speed. It provides placement and eligibility facts only.

### 6) **Mentor note**

Ask the learner to count physical hosts, worker nodes, desired Pods and eligible
endpoints separately. Then reveal P2's changed readiness and ask which answers
change. A sound explanation updates only the endpoint count and keeps shared
hardware and unverified client outcomes visible. Removing P3's event reason tests
whether the learner can stop at a status without inventing its cause.
