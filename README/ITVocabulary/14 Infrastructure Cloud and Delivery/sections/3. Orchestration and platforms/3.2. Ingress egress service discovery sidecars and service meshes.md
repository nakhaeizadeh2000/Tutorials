## 3.2. Ingress egress service discovery sidecars and service meshes

“Put it behind ingress” may mean incoming traffic, a Kubernetes API object or a
particular proxy installation. Those meanings are related, but they are not
interchangeable. Identify the boundary, the configuration object and the software
that implements the route.

Read the previous orchestration lesson and earlier network-intermediary vocabulary.
Kubernetes references use its 1.37 documentation checked 2026-10-20; Istio examples
name architectural modes rather than prescribe an installation. All traffic
records below are fictional, not live requests or a deployed mesh.

### 1) **Identify traffic direction and distinguish route intent from implementation**

**Ingress** means traffic entering a named boundary; **egress** means traffic
leaving it. A request from application A to application B is egress from A and
ingress to B. If both are inside one cluster, that call need not cross the cluster's
external boundary. Always say which application, network or cluster is meant.

**North-south traffic** commonly describes communication across an environment's
external boundary. **East-west traffic** commonly describes communication between
its internal components. These are diagram conventions, not compass directions
or universally identical security zones. State the chosen boundary in the legend.

A capitalized Kubernetes **Ingress** is an API object specifying HTTP or HTTPS
routing, commonly by host and path, to backends. An **Ingress controller** is the
software that implements relevant Ingress configuration. Kubernetes's
[Ingress guide](https://kubernetes.io/docs/concepts/services-networking/ingress/)
explicitly distinguishes the object from its controller: creating only the object
does not create a functioning entry path. External reachability also depends on
the rest of the network, naming and application arrangement.

The Ingress API is frozen for further development, but remains generally available;
the Kubernetes project states it has no plans to remove it. Its guide recommends
**Gateway API** for newer capabilities. Gateway API is a family of Kubernetes
extension APIs for network routing, not another spelling of an IP default gateway.
Its actual capabilities depend on the resources and implementation being used.
Recognizing both names is more useful than treating “frozen” as “already removed.”

An **egress gateway** is a designated component through which selected outbound
traffic is routed. Its name does not prove all outbound paths use it or that every
destination is permitted. An inbound HTTP route and outbound-access policy answer
different questions. Reuse the earlier firewall, proxy and TLS lessons when
reviewing the actual controls and protected endpoints.

### 2) **Separate discovery helper placement and mesh traffic roles**

**Service discovery** finds the current access information for a named service.
It can use DNS, a platform API or another registry mechanism. Discovery answers
where or how to contact something; it does not prove that contact succeeds, the
caller is authorized or the requested business action completes.

For a normal Kubernetes ClusterIP Service, cluster DNS can resolve the Service's
name to its virtual address. A headless Service has a different answer shape;
Kubernetes's [service DNS guide](https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/)
distinguishes those cases. A Service can remain the named access boundary while
its backend Pods change. Do not hard-code a single Pod address just because one
lookup or inspection found it during development.

A **sidecar** is a supporting component deployed alongside an application instance.
In a Kubernetes Pod, a sidecar container can supply proxying, log handling or another
helper function. A sidecar is not necessarily a proxy or a mesh. It shares the
Pod's placement boundary, but it need not be the main application process.

Kubernetes has native lifecycle support for sidecar containers, stable since
**1.33**, using restartable init containers that continue after startup. Its
[sidecar documentation](https://kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/)
distinguishes that mechanism from ordinary init containers, which complete startup
work, and from ordinary multi-container arrangements. The architectural word
sidecar predates that API feature; a diagram's helper label does not prove which
lifecycle mechanism was configured.

A **service mesh** supplies infrastructure for communication between selected
application services, with capabilities such as traffic policy, protected
connections and communication telemetry. In a proxy-based mesh, its **data plane**
handles application traffic, while its **control plane** configures and coordinates
that handling. These describe mesh roles, which are distinct from the Kubernetes
control plane's management of cluster objects.

Sidecar placement is one arrangement, not the definition of every mesh. Istio's
[data-plane comparison](https://istio.io/latest/docs/overview/dataplane-modes/)
describes both sidecar proxies and an **ambient** mode with node-level proxies
and optional additional proxies for application-protocol features. Different
placement changes resource, identity and traffic-handling boundaries. It does
not by itself establish better security, lower cost or complete feature equivalence.

A mesh can apply a communication policy without knowing the application's entire
business authorization rule. A permitted connection from a reporting service does
not automatically authorize that service to read any workshop roster. Likewise,
network retries need the existing operation-identity and side-effect reasoning;
adding a proxy does not make every repeated write safe.

### 3) **Trace a request across boundaries and vary the evidence**

Read this **fictional packet**. “Ingress route” means the Kubernetes object; arrows
below describe logical request paths, not a wire trace.

| Supplied fact | What it establishes |
|---|---|
| External browser calls the report entry address | Intended ingress to cluster W, and north-south traffic under this diagram's convention |
| Ingress route maps report host/path to Service R | Route intent; no implementing controller or reachable proxy is yet established |
| Inside W, frontend F resolves normal ClusterIP Service R to its virtual address | Service discovery result for this lookup; not a successful report request |
| F calls R inside W | Egress from F and ingress to R; east-west traffic under the chosen cluster boundary |
| Each report Pod contains an application container and a log-forwarding helper | Sidecar pattern for log handling; no mesh proxy or mesh policy is supplied |
| R calls an external delivery API through gateway G | Stated egress path for that call; other outbound paths are unspecified |
| Report permission checks and recipient delivery | No results supplied |

The packet contains ingress, egress, discovery and a sidecar without demonstrating
a working public route or a service mesh. The log helper's co-location does not
turn it into a network proxy. The observed DNS answer also supplies no missing
application permission or recipient-delivery evidence.

Add only a later report showing that an installed controller accepted the Ingress
route and an external synthetic request completed its expected report response.
That supports the tested entry path and response under those conditions. It does
not prove every outbound call uses G, that all roster permissions are correct or
that delivery to an actual recipient occurred.

Now consider an independent variation: replace the log helper with a configured
mesh proxy and supply evidence that F-to-R traffic passed through the intended
mesh policy. This establishes that communication arrangement for the checked
path. It still does not establish R's business authorization or safe duplicate
handling at the external delivery API.

Practice: another proposal says “there are no per-Pod proxy sidecars, therefore
there is no service mesh.” Is that conclusion supported? No. Ask whether another
data-plane arrangement, such as node-level proxies, implements the mesh. If none
is supplied, leave mesh participation unverified rather than infer its absence
solely from one missing implementation pattern.

### 4) **Common confusion**

Ingress direction is broader than Kubernetes Ingress, which specifically describes
a routing API object. A gateway's presence is also broader than a proved policy:
traffic can bypass an intended gateway unless the design and controls prevent it.

Service discovery is not load balancing, authentication or health verification,
though a platform can combine those facilities. A sidecar is a placement pattern;
a mesh is a communication arrangement. Neither term alone establishes what data
was exposed or which application outcome was checked.

### 5) **Performance note**

Proxies and discovery lookups can add processing, memory use or network work;
caching and connection reuse change what occurs per request. The cost depends on
placement, protocols, policies and workload. Comparing a sidecar arrangement with
an ambient arrangement requires equivalent features and stated measurement
conditions. No proxy, discovery, latency, throughput or resource benchmark was run
for this lesson, and no application requires a mesh merely to satisfy these names.

### 6) **Mentor note**

Ask the learner to mark ingress and egress at F, R and the cluster boundary for
the same internal call. Then ask what the log sidecar proves about network policy.
A sound answer distinguishes direction, discovery, route implementation and
helper purpose. Use the no-sidecar variation to test whether the learner confuses
one product arrangement with the entire architectural category.
