## 1.1. On-premises hosted public private hybrid and multicloud

A server can belong to a company while sitting in someone else's data center.
An application can use a public cloud while keeping its data private. These are
ordinary combinations once location, ownership, service responsibility and cloud
deployment models are treated as different questions.

Read the earlier operating-system, network and security vocabulary first. This
lesson classifies constructed arrangements; it requires no provider account,
subscription, installation or infrastructure change.

### 1) **Separate a machine's location from ownership and operation**

**On-premises**, often shortened to **on-prem**, describes infrastructure at the
organization's own site or facilities in the stated discussion. It does not by
itself specify whether employees or a contractor maintain the equipment, whether
the organization owns every component, or whether the setup offers cloud services.
**Off-premises** describes infrastructure elsewhere relative to that organization.
State whose premises are meant: the same facility can be the provider's premises
and off-premises for its customer.

**Hosting** means providing an environment in which software or services run.
“Hosted” is broad: it might describe a rented server, a managed application or
an organization's own hosting operation. Ask where it runs, who provides it and
who operates each layer. A website's domain registration and DNS hosting also do
not identify the machine or party that serves its application requests.

**Colocation** provides a useful counterexample to “off-site means someone else's
servers.” A customer can place its own hardware in a provider's data-center space.
Equinix's [colocation documentation](https://docs.equinix.com/colocation/)
describes that arrangement. The facility can supply space and related services
while hardware ownership and operating-system duties have another owner.
Contracts and selected services determine the actual division; the word alone
does not settle every maintenance or access obligation.

A **data center** is a facility housing computing and supporting infrastructure.
A **host** can mean a machine or execution environment, as earlier lessons explain.
Neither word inherently means public cloud. Keep physical placement separate from
the software roles of client, server and application backend.

### 2) **Read cloud deployment labels through their defined scope**

**Cloud computing** describes a service/resource model rather than merely “a server
on the internet.” NIST's [cloud definition](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-145.pdf)
identifies on-demand self-service, network access, resource pooling, rapid elasticity
and measured service. A remote machine's address alone does not establish those
capabilities. Measured use also does not imply that every service has the same
billing contract or unlimited available capacity.

A **public cloud** offers its cloud infrastructure for general use by customers.
Public describes the service/deployment model, not permission for everyone to read
each customer's data. A provider can offer isolated customer resources and private
network connections within that model. Making an object publicly readable changes
its access configuration; it does not create the definition of public cloud.

A **private cloud** is provisioned for exclusive use by one organization, potentially
serving several of its business units. It can be on or off that organization's
premises and can be operated by the organization, a third party or a combination.
A private IP address or a private account on a public cloud does not alone turn
the provider's cloud into a private cloud. A dedicated ordinary server also needs
the relevant cloud capabilities before the cloud classification is established.

NIST additionally describes **community cloud** for a specified group of organizations
with shared concerns. These deployment labels answer who the infrastructure is
provisioned to serve. They do not establish application authorization, legal
compliance or a universally best security model.

**Hybrid cloud** connects distinct cloud infrastructures through an arrangement
supporting data or application portability in NIST's definition. In common
industry usage, “hybrid” also describes integrated on-premises and public-cloud
environments, even when the local environment is traditional infrastructure.
Make that usage explicit rather than silently assuming every on-site server is
a private cloud. A diagram with two boxes and a network link does not establish
that an application can move between them or recover across them.

**Multicloud** commonly means an organization uses services from more than one
cloud provider. Google's [multicloud explanation](https://cloud.google.com/learn/what-is-multicloud)
illustrates provider diversity and acknowledges variation in usage. State whether
the claim concerns the whole organization, one application or a particular
recovery design. Two unrelated applications on two providers can satisfy an
organization-level description without providing failover for either application.

Hybrid and multicloud can overlap: an organization can connect its private cloud
to public-cloud services from two providers. Conversely, two regions from one
provider do not establish provider diversity. The labels alone do not guarantee
portability, synchronized data or freedom from dependencies on one provider's API.
The specific design must support those outcomes.

### 3) **Classify concrete arrangements without inventing guarantees**

Read these **independent fictional arrangements**:

| Arrangement | Supplied facts | Supported description |
|---|---|---|
| A | Company-owned servers in its office; manually assigned fixed resources; no self-service pool or elasticity supplied | On-premises infrastructure; cloud capabilities are not established |
| B | Application uses a general-public cloud provider's resources; its records and network access are restricted | Public-cloud hosting with the stated private access configuration |
| C | Dedicated cloud infrastructure serves only one organization; the contracted provider operates it at the provider's site | Off-premises private cloud under the supplied exclusive-use/cloud facts |
| D | C is integrated with B using supplied technology that enables data/application portability between the distinct clouds | Hybrid-cloud arrangement under the supplied definition; no recovery test stated |
| E | The organization runs its catalog on provider P and an unrelated analytics application on provider Q | Multicloud at organization scope; no same-application failover demonstrated |

A distinguishes physical placement from a cloud model. B distinguishes a public
service offering from public data. C separates exclusive organizational use from
hardware location and operator identity. D supplies an integration fact beyond
merely owning two subscriptions. E supplies provider diversity without claiming
that either workload runs on both providers.

Now change only B's object-access rule so an exported file becomes readable by
anyone who reaches its address. Its cloud deployment label remains public cloud.
Its data-exposure situation changed and needs a security assessment; the label
was never proof that such exposure was intended or acceptable. Likewise, changing
C's operator would not alone change its exclusive-use deployment classification.

Practice: replace C in D with A, retaining only a VPN connection and no statement
of cloud capabilities or portability. Can you retain the same NIST-based hybrid-
cloud conclusion? No. You now have a connection between traditional on-site
infrastructure and a public cloud, with the stronger cloud-composition/portability
facts absent. “Hybrid IT” or a clearly defined broader hybrid usage may describe
the intention, but the tunnel alone proves neither cloud capabilities nor movement
of the application. Ask which actual integration the design supports.

When reviewing a proposal, record location, hardware/resource ownership, operator,
consumer scope, integration and the particular workload separately. Then evaluate
requirements such as availability, data handling and cost with their own evidence.
These classifications guide questions; they are not purchasing recommendations
or proof that any arrangement meets those requirements.

### 4) **Common confusion**

Public cloud is not the same as a public database, private cloud is not the same
as a private subnet, and on-premises is not the same as self-managed. “Hosted”
needs its provider and responsibility scope. A service can combine several of
these descriptions without contradiction.

Multiple providers also do not automatically mean redundant service. If one
application depends on a component that exists only at P, owning an unrelated
subscription at Q does not show that the application survives P's failure.
Recovery needs a concrete data, identity, dependency and execution design.

### 5) **Performance note**

Location, network paths, service characteristics, resource allocation and workload
can affect latency and throughput. Public/private/hybrid labels supply none of
those measurements. A nearby office server is not inherently faster for every
user, and a second provider does not automatically add usable capacity.

No provider benchmark, network probe, migration, cost comparison or failover test
was performed. The fictional classifications do not rank these arrangements by
speed, expense or reliability.

### 6) **Mentor note**

Have the learner fill separate columns for location, owner, operator and consumer
scope before choosing a label. Then change B's file permission and ask which
column changed. A sound answer revises data access without redefining public
cloud. Use E to test whether they can distinguish provider diversity from an
application's demonstrated recovery capability.
