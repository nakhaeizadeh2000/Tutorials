## 1.2. IaaS PaaS SaaS managed services and shared responsibility

A provider can patch a database engine while the customer still chooses who may
read its records. “The database is managed” does not answer both questions. Start
with the capability being supplied, then assign each relevant task explicitly.

This lesson builds on the hosting and security vocabulary. Its arrangements are
fictional reading exercises; no subscription, cloud account or deployment is needed.

### 1) **Distinguish infrastructure platform and application capabilities**

**Infrastructure as a Service**, or **IaaS**, supplies fundamental computing
resources on which a consumer can run software, including operating systems and
applications. A typical example is provisioned virtual machines with storage and
networking. The provider operates the underlying infrastructure; the consumer
controls the guest operating system and deployed application within the service's
limits. A **guest operating system** is the operating system inside a virtual
machine, distinct from the machinery supporting it.

**Platform as a Service**, or **PaaS**, supplies an application-hosting platform.
The consumer deploys an application using supported languages, libraries and tools,
while the provider operates underlying infrastructure and operating systems. The
consumer still controls the deployed application and relevant settings. Supported
runtime versions, extension mechanisms and access boundaries depend on the service.

**Software as a Service**, or **SaaS**, supplies the provider's application for
customers to use, through a user interface or program interface. The consumer
configures the permitted application settings rather than operating its underlying
stack. Hosted email is a familiar example. SaaS does not require a browser-only
interface or mean that the customer's users and data need no administration.

These distinctions follow the service-model definitions in
[NIST SP 800-145](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-145.pdf).
They classify the supplied capability and control boundary. They do not form a
universal product ranking. A single organization can consume all three models,
and a provider supplying SaaS can itself consume infrastructure from another provider.

Keep the service-model question separate from the preceding lesson's deployment
models. “Public” describes a cloud deployment arrangement; “PaaS” describes a
service capability. Neither word alone says which workshop records an employee
is allowed to read.

### 2) **Name managed tasks and shared responsibilities precisely**

A **managed service** delegates specified operational tasks to a provider. The
term needs an object and scope: operating-system updates, database-engine patching,
backup capture, monitoring or another named activity. **Self-managed** means the
consumer operates the specified component itself. Both terms are relative to a
boundary; self-managing an application does not mean owning its building.

A **managed service provider**, often abbreviated **MSP**, is an organization
performing agreed management services. It might operate a customer's IaaS guest
system. That extra arrangement changes the task assignment without automatically
changing the underlying cloud product into SaaS. Ask which provider is meant if
infrastructure and management come from different companies.

A **shared responsibility model** describes how provider and customer duties are
divided or coordinated. “Shared” does not mean half the work each, or that either
party can assume the other completed an unassigned task. For example, the provider
may supply an access-control mechanism, while the customer chooses the permitted
users and configures the relevant rules.

[AWS's explanation](https://aws.amazon.com/compliance/shared-responsibility-model/)
distinguishes customer-managed guest systems on EC2 from more abstracted services
whose infrastructure and operating systems AWS operates. It still assigns data
and permission tasks to customers. These are scoped provider examples, not rules
for every product bearing the same label.

[Microsoft's responsibility guide](https://learn.microsoft.com/en-us/azure/security/fundamentals/shared-responsibility)
also distinguishes service models and retained customer configuration and identity
duties. It explicitly describes its responsibility terminology as governance
guidance rather than a replacement for contractual terms. Read the actual service
documentation and agreement when assigning work. A general diagram cannot settle
all obligations of a particular service, configuration or jurisdiction.

Distinguish **performing an operation**, **deciding its policy** and **checking its
outcome**. Provider-managed backup capture does not by itself select the customer's
required recovery point or prove that an application can resume from those copies.
Use the existing recovery lesson for capture and restoration mechanics. The new
question here is who performs and verifies each part.

### 3) **Read a responsibility packet and expose unassigned work**

Consider these three independent, fictional workshop arrangements:

| Arrangement | Supplied capability | Explicit task division |
|---|---|---|
| A | Cloud virtual machines on which the workshop team installs its own operating system and application | Infrastructure provider maintains physical hosts; workshop team patches the guest system and application |
| B | Cloud application platform receiving the team's application | Platform provider maintains the operating system and supplied runtime; team maintains its application code, dependencies and access configuration |
| C | Ready-made cloud booking application | Application provider maintains its application stack; customer administrator assigns workshop users and the application's permitted access settings |

A illustrates IaaS, B PaaS and C SaaS under the supplied facts. B's provider-managed
runtime does not patch a library packaged inside the team's own application unless
that duty is included. C's provider-operated application does not decide every
customer-specific user assignment. Identify the actual component before assigning
its update or permission task.

Add this **contract excerpt for B only**:

| Activity | Stated owner or evidence |
|---|---|
| Produce a daily database backup and retain it for seven days | Provider, as an included managed database service |
| Choose which workshop staff may read private rosters | Customer administrator |
| Apply the chosen roster permissions | Customer team using the supplied controls |
| Verify that the application can resume with an acceptable restored dataset | No owner assigned and no result supplied |
| Most recent backup job | Reported successful; restored contents and application recovery untested |

The last two rows expose a responsibility and evidence gap. They do not prove
that the backup is corrupt. Assign an owner for recovery requirements and the
rehearsal, identify needed provider support, and agree what the outcome must show.
“Fully managed” on a brochure does not fill those rows with a passing result.

Now change only A: a separate MSP is contracted to patch the guest system. The
cloud infrastructure capability is still IaaS. The task moves to the MSP under
that agreement, and the customer needs a way to confirm its completion and handle
exceptions. Do not silently move application updates if the agreement names only
the guest operating system.

Practice: B's new provider report says the operating system was updated yesterday.
Can the team close a finding about an outdated library bundled in its application?
No. The supplied assignment leaves that component with the team, and an OS update
is not evidence that the application artifact changed. A component-specific
update and adoption check would address the actual gap.

### 4) **Common confusion**

PaaS is not a promise that the provider writes the customer's business logic.
SaaS is not a promise that every user assignment or integration is correct.
“Managed database” names a management scope, not automatic ownership of every
query, data-retention choice and restoration outcome.

A task can also require contributions from both parties without becoming vague.
The customer can request a restore while the provider operates the restoration
mechanism, and the customer then checks whether the recovered application meets
its needs. State each action and its evidence rather than one unexplained shared cell.

### 5) **Performance note**

Delegating operations can change available tuning controls, supported resource
choices and the work needed to maintain a service. It does not establish lower
latency, greater capacity or lower total cost. The relevant limits, workload and
measurement boundary still need inspection. The three fictional arrangements
include no measurements, cost comparison or recovery-duration result.

### 6) **Mentor note**

Ask the learner who updates B's supplied runtime and who updates a library bundled
with its application. Then ask whether a successful backup job proves recovery.
A sound answer identifies the component, its assigned operator and the additional
outcome evidence needed. Give credit for an explicit unassigned task rather than
a confident guess from the service label.
