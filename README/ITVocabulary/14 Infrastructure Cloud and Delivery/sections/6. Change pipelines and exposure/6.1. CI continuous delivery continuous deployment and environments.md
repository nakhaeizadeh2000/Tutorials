## 6.1. CI continuous delivery continuous deployment and environments

“The CD pipeline is green” leaves two questions unanswered: which meaning of CD
is intended, and what actually reached production? A workflow can check code,
prepare a deployable artifact and wait for a release decision without performing
an automatic production deployment.

Read build, Git and quality-evidence vocabulary first. The pipeline records below
are fictional. No hosted automation, repository workflow or deployment is created.

### 1) **Distinguish integration practice from an automation service**

**Continuous integration**, or **CI**, is a development practice of frequently
integrating changes into a shared codebase and checking the combined result.
Martin Fowler's [CI explanation](https://martinfowler.com/articles/continuousIntegration.html)
emphasizes frequent mainline integration and automated build/testing feedback.
**Mainline** here means the shared integration line, not necessarily a branch
literally named `main`.

A **CI service** runs configured work, often after a repository event. A **runner**
or **agent** is an execution environment for that work. A **job** groups configured
steps; a **stage** groups work into a broader workflow phase under the tool's
conventions. These names vary by product. A failed job needs its actual command,
version, inputs and output, not a diagnosis from the stage's title.

A service can run checks on a long-lived feature branch. Those checks are useful,
but their existence does not establish that colleagues' changes are frequently
combined in a shared mainline. Conversely, the project's chosen integration
practice is not defined by which vendor hosts the runner.

A build prepares outputs; tests check selected behavior; neither is automatically
a production deployment. “Green” means the configured completion conditions passed
for the identified run. It does not establish that omitted checks ran, that every
dependency was real or that the tested revision matches the currently proposed one.
The testing domain owns those evidence limits.

A **delivery pipeline** connects preparation, verification and deployment-related
activities through defined dependencies and gates. Not every stage must be strictly
sequential; independent checks can run in parallel. A later stage still needs the
outputs and required results on which it depends. Read the workflow's actual graph
and artifact identities rather than assume one list of tool names proves that flow.

### 2) **Separate deployability from automatic production deployment**

**Continuous delivery** is the discipline of keeping software deployable through
repeatable preparation, verification and deployment capabilities. It aims to make
production deployment a deliberate, routine action when needed. A human or business
decision can still determine when to use that capability.

**Continuous deployment** additionally makes production deployment automatic for
changes that pass the applicable pipeline conditions. This does not mean knowingly
deploying failed checks or that every team must use identical conditions. Spell
out the trigger, gates and production action in the actual system.

Fowler's [delivery/deployment distinction](https://martinfowler.com/bliki/ContinuousDelivery.html)
separates the ability to deploy routinely from doing so automatically. Continuous
delivery does not require a particular environment literally named acceptance,
a fixed number of pipeline stages or deploying every change to every user at once.
Deployment, release and user exposure get their fuller distinction in the next lesson.

Both practices are abbreviated **CD**. **CI/CD** can therefore mean integration
with continuous delivery or with continuous deployment. Expand the phrase in a
report. The CNCF glossary uses a narrower
[acceptance-environment framing](https://glossary.cncf.io/continuous-delivery/)
for delivery; that is a useful example of terminology variation, not a reason to
assume a universally required stage name. State the intended capability and flow.

A **deployment environment** is an operating context for a version of the system.
Common conventions include these roles:

| Environment name | Usual purpose | What the name alone does not prove |
|---|---|---|
| Development | Build and investigate changes | That it uses only one engineer's laptop |
| Test | Exercise selected checks | That all dependencies or data match production |
| Staging or preproduction | Rehearse relevant production-like behavior | Identical load, topology, permissions or external services |
| Production | Serve the intended operational users or business workload | That every feature is enabled for every user |

An organization can use different names, several test contexts or temporary
**preview environments** for selected changes. State the actual scope. Git
**staging** prepares a commit snapshot; a deployment staging environment hosts
software. These are different meanings of the same word.

**Environment parity** means matching relevant characteristics across environments.
It does not require copying private production data into every test system.
Identify the behaviors that need representative configuration, dependencies,
permissions and workload, and use appropriate controlled data. A production-like
screen or identical image digest does not establish all of those conditions.

**Promotion** commonly means advancing a selected artifact or version through the
organization's delivery process. Some systems reuse an exact artifact; others
rebuild. Record which happened. If a rebuild produces different content, earlier
checks do not automatically establish that the new artifact behaves identically.
Configuration differences can also change behavior even when the image stays fixed.

### 3) **Trace checks deployability and a production action separately**

Read these **independent fictional arrangements**:

| Arrangement | Supplied behavior | Supported conclusion |
|---|---|---|
| A | Team members frequently integrate in a shared mainline; automated build and selected tests run on the combined revision | CI practice is supplied; no production delivery capability is stated |
| B | A's practice plus a repeatable verified route for deploying a selected artifact to production; an authorized person chooses when to start that route | Continuous delivery under the stated deployability facts; automatic production deployment is not supplied |
| C | A's practice plus an automated route that deploys each qualifying change to production when required conditions pass | Continuous deployment under the stated automated-production facts |

Now inspect this **candidate-specific packet for B**:

| Record | Supplied observation |
|---|---|
| Candidate | Source C9 produced image digest D9 |
| Checks | Configured source and application checks passed for C9/D9 in test |
| Staging | D9 deployed and the stated export case passed with a simulated notification provider |
| Production | D8 is still running; manual production action for D9 has not started |
| Environment difference | Production uses the real notification provider; no D9 integration result for it is supplied |

The recorded test and staging work does not mean D9 reached production. It also
does not prove that D9 works with the real notification provider. The broad B
arrangement states a delivery capability; this particular packet still leaves
that integration claim without evidence. Do not turn a practice label into a
substitute for candidate-specific checks.

Change only the Production row by supplying a completed deployment and
inventory showing D9 running there after the manual action. D9 is now deployed
under the stated observation. That individual manual action still does not turn
B's workflow into continuous deployment, and it does not retroactively make the
simulated staging notification a real delivery.

Practice: the check badge instead belongs to C8/D8, while the candidate remains
C9/D9. Can it certify the candidate's configured checks? No. Request results
applicable to the candidate. A green historical run and the word latest do not
supply that alignment.

### 4) **Common confusion**

A CI product is not the whole integration practice, and continuous delivery is
not the same as continuously deploying into production. A manual release decision
can coexist with a highly automated delivery route. CD should be expanded wherever
the actual production behavior matters.

An environment name is not a test result. Staging can differ from production,
and a passed simulated interaction remains simulated. An artifact's promotion
also does not prove it was rebuilt, or that rebuilding preserved its bytes.

### 5) **Performance note**

Pipeline duration affects feedback and delivery waiting, while runners consume
compute and may contend for dependencies. Parallel jobs can shorten some waits
but can also compete for resources or violate required ordering if configured
incorrectly. A pipeline label does not change application latency. No runner,
workflow-duration, production-load or delivery-speed benchmark was run here.

### 6) **Mentor note**

Ask the learner what is currently running in production before revealing any
pipeline labels. Then show the A–C flows and ask where the production decision
occurs. A sound answer distinguishes integration, deployability and automatic
production action, and keeps the simulated provider and candidate identity visible.
Use C8/D8 to test whether they can reject a green but inapplicable result.
