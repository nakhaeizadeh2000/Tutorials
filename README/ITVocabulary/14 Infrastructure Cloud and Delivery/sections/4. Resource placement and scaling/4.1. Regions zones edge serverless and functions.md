## 4.1. Regions zones edge serverless and functions

An application can serve a response near a user while its database remains in a
distant region. A provider can operate its servers while the application team
still owns permissions, dependencies and recovery requirements. Placement and
execution-management labels answer different questions.

Read hosting, shared responsibility and workload placement first. Product examples
use AWS and Cloudflare documentation checked 2026-10-20. The fictional arrangement
below requires no account, deployment, cloud purchase or network experiment.

### 1) **Locate regions zones and edge work without inferring complete coverage**

A cloud **region** is a provider-defined geographic service area. An **availability
zone**, often **AZ**, is a provider-defined location or group of facilities within
a region, designed to separate relevant infrastructure failures. Names, boundaries
and supported services depend on the provider. A zone is not automatically one
building, a country, a time zone or an independent provider.

AWS's [regions and zones guide](https://docs.aws.amazon.com/global-infrastructure/latest/regions/aws-regions-availability-zones.html)
distinguishes geographic regions and zones containing one or more data centers.
Use that as a scoped example, not a universal topology or a promise that separate
zones cannot share any failure. Two instances in one zone and two instances in
different zones have different placement descriptions; neither alone proves the
application meets its availability requirements.

A **multi-zone** arrangement uses multiple zones; a **multi-region** arrangement
uses multiple regions. State which workload and dependencies are present in each.
A second region containing a static image is not necessarily a second operating
copy of the booking system. A **regional service** has a relevant region-scoped
resource or operation boundary; a **global service** has some cross-region or
global service scope. Check which parts are global rather than assuming every
resource, data copy and operation shares one boundary.

**Edge computing** places selected computation near a relevant source, user or
network boundary instead of requiring all work at one centralized location.
An **edge location** can host request processing or cached delivery; it need not
have every service available in a cloud region. “Near” is relative to a path and
workload, not proof that the nearest building processed a given request.

A content delivery network can serve cached resources from distributed locations.
An edge function can execute custom request handling there. Those roles can
coexist, but caching and running code are different acts. If edge code waits for
a database in one region, that backend dependency remains part of the full request.
An edge deployment label alone establishes neither low end-to-end latency nor
where all data is stored or processed.

### 2) **Separate server management from application execution and responsibility**

In hosted cloud usage, **serverless** commonly means a service abstracts specified
server provisioning and operations from its consumer. Physical machines and
execution environments still exist. The application team still has duties such
as supplying code, configuring access, understanding limits and handling outcomes.
Use the shared-responsibility lesson for the division, rather than interpreting
the name as “no operations.”

Serverless is broader than one function product. **Functions as a Service**, or
**FaaS**, commonly runs consumer-supplied code through a provider-managed invocation
model. **Backend as a Service**, or **BaaS**, supplies backend capabilities such
as managed data or identity services. Mike Roberts's original
[serverless architecture discussion](https://martinfowler.com/articles/serverless.html)
introduces those two uses and the retained operational concerns. Its 2018 platform
limits and maturity judgments require current provider evidence.

A platform **function** is a deployed code unit under that platform's contract.
It can contain many ordinary language functions. A **handler** is the entry code
called for a defined event or request, and an **invocation** is one execution
request under the platform model. A **trigger** connects an event source or
request mechanism to that invocation. Receiving the trigger is not necessarily
proof that an external business effect completed.

AWS's current [Lambda overview](https://docs.aws.amazon.com/lambda/latest/dg/welcome.html)
distinguishes event functions, web functions and managed microVM environments.
An event-handler model is therefore not the entire meaning of serverless compute.
The relevant product still defines execution lifetime, concurrency, networking,
supported runtimes, packaging and billing conditions. Do not generalize an old
product limit or one-request-at-a-time model to every current serverless service.

An **execution environment** is the runtime context in which the code operates.
Some platforms reuse an initialized environment across invocations. Lambda's
[lifecycle guide](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)
describes reuse; Cloudflare's [Workers runtime explanation](https://developers.cloudflare.com/workers/reference/how-workers-works/)
describes isolates and the absence of a guarantee that two requests use the same
instance. Cloudflare also illustrates that serverless execution need not create
a separate VM for every function invocation.

Reuse does not make process-local memory a durable application database. A value
left in one environment may be absent in another or lost when that environment
ends. Conversely, an environment is not necessarily fresh for every request.
Keep request-specific information within its intended scope, and use an appropriate
retained-state service when the application needs durable shared facts.

“Serverless” also has a distinct embedded-database meaning: SQLite uses it to mean
there is no separate database server process. That existing architecture owner
explains why the same word can describe a local library and a remotely operated
cloud service without making their deployment diagrams identical.

### 3) **Read a mixed placement and function packet**

Consider this **fictional arrangement**, whose names are not actual provider regions:

| Component | Supplied placement or behavior |
|---|---|
| Booking API | Instances in zones A and B within region R1 |
| Booking database | Only R1 is supplied; no R2 recovery copy or operating database is specified |
| Edge request handler | Runs at distributed edge locations; every booking lookup calls the R1 API |
| Report function | Provider-managed event handler; receives a booking event and requests a report write |
| Function state | Uses a process-local counter; environment reuse and retirement are possible |
| Image copy | Report image also stored in R2; no running report instance there is supplied |
| Operations | Customer team owns application permissions and checks; no recovery rehearsal or latency measurement supplied |

The API is multi-zone in R1. The application is not demonstrated to operate in R2
merely because one image is stored there. The edge handler changes where part of
the request executes, while the required booking lookup retains its R1 dependency.
Provider management of the report environment leaves the named application duties
with the customer team.

The function's process-local counter is also insufficient evidence of a global
report count. Another execution environment can start with a different counter,
and retirement can discard the local value. A reused environment can retain it
for a later invocation. Neither a guaranteed reset nor durable continuity follows
from the word function.

Change only the edge handler so a stated class of public, immutable static files
is served from an already populated edge cache without calling R1. Those particular
requests now have a different dependency path. Booking lookups still require R1.
Do not extend a static-file result to private, changing booking data or all requests.

Practice: a later record says the report function's handler returned successfully,
but its external writer only acknowledged acceptance and completion was not checked.
Was the report definitely stored? No. The invocation result and external write's
business outcome have different boundaries. Request completion evidence for the
specific operation rather than treating serverless execution as an end-to-end guarantee.

### 4) **Common confusion**

A region is not a time zone, and several zones are not several providers. Edge
placement is not an assertion that every dependency moved to the edge. A global
service name also does not prove worldwide data replication or an automatic
cross-region recovery design.

Serverless does not mean no servers, no limits, no retained responsibilities or
necessarily FaaS. A function is not necessarily a tiny source function or a fresh
process. “Stateless” application design means required continuity is handled
appropriately; it does not prove that no memory or external state exists.

### 5) **Performance note**

Placement can change network distance and dependency waiting. Initializing an
execution environment can add work compared with reusing one, while initialization
and reuse policies vary. Calling a distant database from edge code can preserve a
substantial remote wait. None of these labels supplies a measured startup time,
response percentile, capacity ceiling or cost advantage. No deployment, latency,
cold-start or cost experiment was performed for this packet.

### 6) **Mentor note**

Ask the learner to draw only the dependencies of one booking lookup, then those
of the changed static-file request. A sound answer changes one path without
relocating the database by implication. Follow with the process-local counter:
the learner should explain both possible reuse and possible loss, and identify
what durable shared counting would still require.
