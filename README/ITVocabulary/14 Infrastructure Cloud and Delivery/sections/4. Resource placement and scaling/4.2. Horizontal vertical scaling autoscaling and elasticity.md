## 4.2. Horizontal vertical scaling autoscaling and elasticity

A platform increases the desired replica count from two to four, but the two new
Pods remain Pending. The scaling policy acted; useful running capacity has not
yet doubled. Name what changed, what became ready and which work the application
can actually complete.

Read resource quantities, workload placement and failure-flow vocabulary first.
Kubernetes examples use 1.37 documentation checked 2026-10-20. The numbers below
are an explicitly simplified hypothetical model, not measurements of a deployed
application or a recommendation for a production scaling policy.

### 1) **Distinguish changing instance size from changing instance count**

**Vertical scaling** changes resources assigned to an instance or execution unit.
**Scale up** commonly means increasing that allocation; **scale down** means
reducing it. Replacing a VM with a larger memory/CPU configuration is one example.
A container resource adjustment is another context. Whether the change requires
replacement, restart or can happen in place depends on the platform and resource.
Do not define vertical scaling as always requiring downtime or never requiring it.

**Horizontal scaling** changes the number of instances or managed units.
**Scale out** commonly adds them; **scale in** removes them. Increasing a report
worker pool from two to three workers is horizontal scaling. Up/down are sometimes
used loosely for any increase/decrease, so state the actual count or allocation
when the distinction matters.

Changing one VM from two virtual CPUs and 4 GiB RAM to four virtual CPUs and 8 GiB
RAM is a vertical resource change. Creating a second VM with the original allocation
is a horizontal count change. Neither description establishes identical physical
hardware, twice the useful throughput or the same total operating cost.

**Scalability** is the ability to handle growth under stated requirements and
resource assumptions. Say whether the growth concerns requests, stored data,
concurrent users or another quantity. Adding resources is a mechanism; maintaining
the required outcome as load grows is the property to demonstrate.

The Twelve-Factor App's original [process-model guidance](https://12factor.net/concurrency)
uses separate web and worker process types to explain scaling work independently.
The important design question is which work can be divided among instances.
Shared state, per-instance sessions and a serialized dependency can constrain
that division. Starting more processes is not proof that all application work
is independently partitionable.

### 2) **Separate automatic adjustments from elastic application behavior**

**Autoscaling** automatically adjusts a defined resource or instance target using
rules or other decision logic. A **reactive** policy responds to observed signals;
a **scheduled** policy acts at specified times; a **predictive** policy uses a
forecast. A schedule can prepare capacity for expected demand without measuring
the current request rate. Automatic therefore does not always mean reactive.

A policy needs inputs, permitted ranges and an action. For example, a fictional
policy might increase desired report-worker count when its queue signal crosses
a configured threshold, up to four workers. That is a desired-count decision.
Provisioning, image retrieval, startup and readiness still need to succeed before
new workers become useful.

**Elasticity** describes adapting supplied resources to changing demand, including
releasing resources when less is needed. NIST's [cloud definition](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-145.pdf) includes rapid
elasticity and says automatic adjustment occurs in some cases. Elasticity and
autoscaling are related but not synonyms: a manually requested adjustment can
use elastic infrastructure, and an automatic policy can react poorly or hit a
limit. Neither term means infinite capacity or a zero-delay response.

In Kubernetes, a **HorizontalPodAutoscaler**, or **HPA**, adjusts a scalable
workload's desired replica count from supported metrics. Its
[horizontal autoscaling guide](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)
distinguishes that count change from vertical resource adjustment. It does not
itself turn a full worker node into a larger machine or guarantee room for the
requested Pods.

**Node autoscaling** separately provisions or consolidates execution nodes.
Kubernetes's [node autoscaling guide](https://kubernetes.io/docs/concepts/cluster-administration/node-autoscaling/)
explains both scheduling constraints and limits such as provider capacity and
configuration. Combining the mechanisms still needs a compatible policy and
successful actions. Raising the Pod target is not evidence that the nodes were
created or that the workload became Ready.

**Scale-in** also needs lifecycle handling: stopping an instance can interrupt
in-progress work or discard instance-local state. Determine whether work must
finish, be transferred or safely retried before removal. The earlier delivery
and retry lessons own those guarantees; scaling does not eliminate them.

A metric's **lookback window** selects which observations are considered. A
**cooldown** can delay another scaling action after an earlier one, while a
**stabilization window** can prevent reacting immediately to every changing
recommendation. Implementations define these mechanisms differently. Microsoft's
[autoscaling guidance](https://learn.microsoft.com/en-us/azure/architecture/best-practices/auto-scaling)
distinguishes its observation window and cooldown. Read the specific controller's
rules rather than assume one universal timer or scale-in algorithm.

**Flapping** is repeated movement between opposing adjustments, such as adding
and removing instances as a signal crosses nearby thresholds. Account for
measurement and startup delays, and evaluate signals against the actual workload.
CPU alone may miss a downstream wait. Avoid copying a threshold from another
application without checking what it measures and whether the adjustment helps.

### 3) **Compare requested resources with a bounded capacity model**

Consider this **hypothetical steady-state model**, not an observed benchmark.
Every report request needs one worker operation and one operation on a shared
storage service. A ready worker can perform at most 20 such operations per second
under the model. Work divides perfectly across workers, but storage can complete
at most 50 report operations per second in total. Ignore startup, queueing details,
retries and all other overhead for this deliberately optimistic bound.

| Ready workers | Ideal worker bound | Bound including shared storage |
|---|---|---|
| 2 | 40 reports/s | At most 40 reports/s |
| 3 | 60 reports/s | At most 50 reports/s |
| 4 | 80 reports/s | At most 50 reports/s |

The last column is the smaller of the worker bound and the shared storage bound.
It is a ceiling under the stated assumptions, not a predicted observed rate.
Four workers cannot establish 80 completed reports per second when each report
still requires the storage operation. Adding workers may merely move or intensify
the bottleneck.

Now distinguish two fictional records. At 10:00 the autoscaler requests four
workers, but only two are Ready and the other two are Pending. The model still
has the two-ready-worker bound. At 10:02 all four are Ready; the worker bound grows,
while the unchanged shared storage still caps this model at 50. A successful
adjustment and a successful business-performance outcome need separate evidence.

For an independent vertical-change proposal, increase memory per worker without
supplying a changed per-worker operation bound. Can you replace 20 with 40?
No. More memory may address a particular resource need, but this packet supplies
no new useful-work measurement or model establishing that speedup.

Practice: a later record changes storage's modeled bound from 50 to 100 reports/s
and keeps four workers Ready. What is the new optimistic bound? The smaller of
80 and 100 is 80 reports/s. The arithmetic changes because the limiting assumptions
changed; it is still not a load test or proof of sustained throughput.

### 4) **Common confusion**

More requested replicas are not more ready instances, and more ready instances
are not automatically more useful end-to-end capacity. Autoscaling a frontend
does not necessarily scale its database, external API or network allowance.

A resource limit, a concurrency limit and an autoscaling maximum are also different
controls. One bounds resource use, one bounds active work and one bounds a scaling
target. An automatic maximum of four does not imply four instances are always
running, nor does it certify the safe load for those instances.

### 5) **Performance note**

The arithmetic above bounds a synthetic workload; it measures nothing. Real scaling
can add coordination, connection and storage contention, and provisioning takes
time. Removing resources also changes available headroom and interruption risks.
Measure completed work and user-relevant outcomes under the intended demand and
failure conditions before claiming a scaling benefit. No benchmark, controller
experiment, memory/CPU resize or cost comparison was performed here.

### 6) **Mentor note**

Have the learner identify whether a proposed change affects instance count,
per-instance resources, a policy target or an observed outcome. Then reveal the
storage bound after they calculate the worker bound. A strong answer revises the
conclusion without treating the arithmetic as a measurement. Remove the Ready
observations to test whether they can distinguish a policy decision from usable capacity.
