## 7.1. Read a platform diagram and release plan

A diagram with two application boxes, a managed database and an automated pipeline
can look convincing while leaving important delivery questions unanswered. Follow
a particular user operation through its placements and dependencies, then connect
the release plan to the artifacts and responsibilities it actually describes.

This is an integrated reading exercise. Every system, requirement and observation
below is fictional; no application, cloud service or deployment was run.

### 1) **Recover scope placement and responsibility from the diagram packet**

The team wants workshop registration to continue if one physical application host
fails. Its backend uses NestJS with the Fastify adapter. Framework names identify
the application vehicle; they do not establish placement, access or recovery.

The following is an **informal deployment view**, not a complete C4 diagram.
Provider Q's region R1 contains zones A and B. The request arrows mean required
application interactions, not successful live probes:

| Relationship | Intended operation |
|---|---|
| Browser → public entry E | Submit a registration |
| E → either ready API Pod | Forward the registration request |
| API Pod → database DB | Complete the required registration data operation |
| Backup process → retained copy BK | Capture selected DB history for recovery |

Read the placement and duty records alongside those arrows:

| Element | Supplied placement or responsibility |
|---|---|
| API Pods P1 and P2 | Both Ready; on VM nodes N1 and N2 respectively |
| VM nodes N1 and N2 | Both on physical host H-A in zone A, region R1 |
| DB | Managed database in zone B, region R1; every registration needs it; no fallback path supplied |
| BK | Nightly retained database copy in region R2; no restore or usable-application rehearsal supplied |
| Provider Q | Operates physical infrastructure and DB engine patching under this packet's service agreement |
| Application team | Owns API code, runtime configuration, authorization policy and release decisions |
| Recovery responsibility | No person or service is assigned to validate BK or coordinate application recovery |

Simon Brown's [diagram review questions](https://c4model.com/diagrams/checklist)
help establish scope, element meanings and labeled relationship directions. Here,
reading the arrows without the placement table would hide the shared physical host.
Reading the diagram without the duty table would hide the recovery responsibility
gap. A service label does not fill either gap.

The two Pods supply two running application instances under the recorded readiness
criteria. They do not satisfy the stated one-physical-host-failure requirement:
both depend on H-A. DB is another required dependency in the registration flow.
A DB failure can prevent registration even if both Pods remain Ready. The provider
operating the engine does not itself establish successful registration or recovery.

Microsoft's [failure mode analysis guidance](https://learn.microsoft.com/en-us/azure/well-architected/reliability/failure-mode-analysis)
likewise traces individual flows through internal and external dependencies. Use
that flow discipline here; do not infer universal failure probabilities or a
particular architecture recommendation from this small packet.

### 2) **Compare the release plan with current artifacts and outcomes**

The delivery proposal says:

> Our two-node cluster is highly available. Autoscaling and the R2 backup make it
> multi-region. Green CI means D18 is ready. We will canary it to 2% and roll back
> instantly if anything fails.

Its evidence is more specific:

| Record | Supplied fact |
|---|---|
| Scaling | Controller requests four API Pods under load; only P1/P2 are Ready; the other two are Pending with insufficient-node-capacity events |
| Candidate | Source C18 produced image D18; its configured test checks passed |
| Staging | D18's registration case passed using a simulated DB; the supplied real-DB integration result belongs to D17 |
| Production | D17 is running; D18's manual production action has not started |
| Exposure plan | Enable the new registration path for 2% of accounts after placement; no evaluation criteria or adoption observations supplied |
| Data change | D18 will remove an old field that D17 needs; no compatible return path supplied |

A useful review separates each claim from its supporting or missing evidence:

| Claim | Defensible reading |
|---|---|
| Two-node availability | Distinct VM nodes share one physical failure boundary; the stated requirement is unmet by this placement |
| Autoscaling | A desired count is recorded, but additional ready capacity is not supplied |
| Multi-region | The backup is in R2; the registration application and DB are recorded only in R1 |
| Green candidate | C18/D18 checks passed in their stated scope; the simulated DB and D17 integration do not verify D18 against the real DB |
| Canary | Limited exposure is planned, but its evaluation and actual implementation remain unspecified |
| Instant rollback | No recovery duration or compatible D17 data procedure is established |

The backup's location is useful information about a copy. It is not a second
operating registration system. Similarly, the 2% account plan does not establish
2% traffic or limit the effect of a shared-data migration. The earlier rollout
lesson owns these exposure and recovery distinctions; apply them to the actual
shared DB rather than repeat their definitions.

Avoid replacing the proposal with “everything is broken.” The record establishes
a placement conflict with a requirement and several evidence gaps. It does not
establish a failed D18 production deployment, because that action has not occurred.
A proposed correction also remains a proposal until its outcome is observed.

### 3) **Write a review handoff and update it when evidence changes**

A technical handoff could say:

> P1 and P2 both depend on H-A, so this placement cannot continue registration
> after H-A fails as required. The application team and infrastructure operator
> need to resolve placement and assess the required DB path. D18 has test and
> simulated-DB staging evidence; its real-DB integration and production deployment
> remain unverified. Name a recovery owner, define the canary evaluation and
> establish a compatible data return or correction procedure before relying on
> the stated recovery claim.

For the product stakeholder, preserve the same facts with less mechanism detail:

> The current application copies share the machine whose failure they must survive.
> The new version is still awaiting production deployment, and one important data
> integration check applies to the previous version. We also need an assigned
> recovery owner and evidence for the proposed recovery process. The off-site copy
> and rollout plan alone do not establish continuity or a recovery time.

Practice: change only N2's placement to a different physical host H-B in zone B,
still in R1. The common application-host dependency is now removed for N1/N2.
This improves the placement fact relevant to H-A's failure. It does not demonstrate
traffic failover, adequate surviving capacity, DB availability, R2 application
recovery or candidate compatibility. Zone B now contains N2 and DB; keep that
shared zone visible when analyzing a different failure. Do not report a performed
failure test from a revised diagram.

In an interview, ask whether adding another Pod on H-A meets the physical-host
requirement. A reasoned answer identifies the unchanged failure boundary and asks
about surviving service capacity and the required data path. Repeating “replicas
provide high availability” does not answer this scenario.

### 4) **Common confusion**

A diagram can describe intended architecture, observed placement or a mixture.
State which facts come from which records and when they were observed. A box
count does not reveal physical independence, and a planned controller action is
not an extra running instance.

Responsibility and evidence are also separate. Assigning someone to recovery
removes the unassigned-work gap; it does not prove the restore succeeded. Passing
a candidate's simulated interaction does not replace its missing real integration.

### 5) **Performance note**

More desired replicas cannot supply extra serving capacity while placement remains
blocked. After placement changes, the surviving instances and shared DB still
need capacity evidence for the required workload. No traffic volumes, service
rates or failure measurements are supplied, so neither the 2% plan nor the diagram
supports a throughput, latency or recovery-time estimate.

### 6) **Mentor note**

Give the learner only the relationship table, then reveal placement and duties.
Ask which earlier conclusions need revision. A strong review follows registration
end to end, distinguishes the specific requirement conflict from missing evidence,
and updates only the affected claims when N2 moves. Assess the quality of the
handoff and its next questions, rather than the number of platform terms used.
