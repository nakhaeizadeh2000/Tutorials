## 5.2. Infrastructure as code configuration management and drift

The repository says three workers. A tool's saved record says three. The current
platform has five after an emergency change. Those are three sources of information
about one resource, not three interchangeable versions of the truth. Reconcile
the intended configuration, tool records and actual observations before changing it.

Read Git, configuration and desired-state vocabulary first. Terraform and Ansible
appear as product examples from documentation checked 2026-10-20. The packet below
is fictional and contains no runnable configuration or instruction to modify infrastructure.

### 1) **Distinguish infrastructure definitions from configuration activities**

**Infrastructure as code**, or **IaC**, defines infrastructure through code or
machine-readable definitions that can be reviewed, versioned and used by tools.
Those definitions can describe resources such as machines, networks and storage.
IaC is an approach, not the name of one file format, provider or product.

Martin Fowler's original [IaC explanation](https://www.martinfowler.com/bliki/InfrastructureAsCode.html)
connects definitions with software-engineering practices. Version history helps
review intended changes, but does not automatically record every out-of-band
operation or prove that rebuilding the environment gives identical behavior.
Relevant provider versions, inputs, permissions and retained data also matter.

**Provisioning** creates or makes resources available for use. **Configuration
management**, in this infrastructure context, maintains settings and software
arrangements against an intended setup. Creating a machine, ensuring a required
package is present and tracking a configuration baseline are related activities,
but they are not identical changes.

The boundaries overlap across tools. Ansible can manage configuration and also
provision some resources; Terraform can manage many resource types through
providers. Avoid teaching “tool A only makes machines, tool B only edits files”
as a universal rule. Identify the particular resource and operation in the workflow.

An **imperative definition** specifies actions to perform. A **declarative definition**
states an intended result for a tool to realize. Both can participate in IaC.
A source-controlled sequence that appends a line on every run may produce duplicates;
a state-oriented operation that ensures the required line is present can avoid
that repeated effect under its documented conditions.

This relates to **idempotency**: repeating the relevant operation has the same
intended effect as performing it once, within its stated scope. Ansible's
[module introduction](https://docs.ansible.com/projects/ansible/latest/module_plugin_guide/modules_intro.html)
says modules should avoid changes when the desired state already matches. That
is a design expectation to check for the selected module and task, not proof that
every command, script or complete playbook is automatically idempotent. Output,
execution cost and external side effects can still need separate analysis.

### 2) **Separate desired state tool state plans and drift**

A **configuration baseline** is the agreed reference setup for a stated scope.
The **desired state** is the intended state a definition or controller expresses.
**Actual state** is what the managed system currently has or does, established
through appropriate observation. “Actual” still needs a time, resource and method;
a stale inventory is not a live observation merely because its heading says actual.

**Configuration drift** is divergence from an expected or recorded configuration.
A manual console edit can create it, but a detected difference alone does not
prove an attack or an unauthorized action. The change might have been an approved
emergency adjustment whose durable definitions were not updated yet. Establish
the reason and applicable policy before deciding whether to retain or reverse it.

Terraform **state** is a tool record mapping configured resource instances to real
objects and retaining relevant metadata. Its [state documentation](https://developer.hashicorp.com/terraform/language/state)
distinguishes those bindings from the configuration itself. State is not the same
thing as a live platform inventory, a Git commit or a backup of the application's
business data. A tool can know the identity of a database without retaining all
its reservation records.

A **refresh** observes supported remote resource information to update or inform
the tool's view. A **plan** previews proposed resource actions for a particular
configuration, inputs and observations. **Apply** carries out the selected resource
changes under the tool's rules. Terraform's [plan reference](https://developer.hashicorp.com/terraform/cli/commands/plan)
distinguishes planning from applying those changes. Reading a plan that proposes
removing two workers does not establish that either worker has already stopped.

Terraform also has a refresh-only mode whose goal is updating its state and outputs
to reflect external changes. A refresh-only proposal to record five existing
workers is different from a normal resource-change proposal to return to three.
Neither by itself rewrites the source configuration to declare five. Be explicit
about the mode and which object is changing.

Drift detection also has coverage limits: a tool can compare only resources and
attributes it manages or observes under the relevant settings and permissions.
A report finding no difference in tracked instance count does not certify every
network rule, application file or data record. GitOps adds a continuous pulling
and reconciliation model; IaC stored in Git does not automatically supply that
control loop.

Tool state and saved plans may contain sensitive values even when a terminal view
hides them. Terraform's plan reference explicitly identifies that saved-artifact
risk. Use the documented state backend and access controls for the selected tool;
versioning infrastructure definitions is not an instruction to publish state,
plan files or secrets alongside them.

### 3) **Reconcile an emergency-change packet before selecting a correction**

Read this **fictional packet**. It uses simplified worker-count records, not an
actual Terraform resource schema or plan output.

| Record | Supplied fact |
|---|---|
| Reviewed definition C7 | Desired report worker count is three |
| Earlier tool record | Three managed workers recorded at 09:00 |
| Emergency change | Authorized operator increases actual count to five at 09:30 to handle a temporary event |
| Live inspection | Five workers exist at 10:00; all five are currently processing work |
| Normal resource plan | Observes five and proposes removing two to match C7 |
| Application recovery copy | No booking-data backup or restore result supplied |
| Current operational decision | Whether the temporary extra workers are still needed has not been decided |

The current difference is known and its supplied cause is authorized. The source
and older tool record have not kept up with that change. The plan identifies one
possible reconciliation toward C7, but it has not established that removing busy
workers is presently acceptable or that the removal was performed.

If the organization deliberately retains five, update the intended definition
through its change process and verify the resulting plan and actual state. If it
returns to three, coordinate unfinished work and confirm the resulting service
outcome. These are alternative decisions, not a recommendation to choose either
without the missing operational requirement.

Now add only a refresh-only result recording five workers. The tool's record
becomes more current. C7 still declares three, and no supplied resource action
has reduced the live count. Do not confuse improved inventory knowledge with
changed desired state or completed infrastructure work.

Practice: replace the worker-count difference with an untracked application file
edited on one machine. A count-only comparison reports no difference. Does it
prove that the application configuration matches its baseline? No. That comparison
did not inspect the changed file. Ask which mechanism owns and checks it instead
of extending one tool's coverage to the entire environment.

### 4) **Common confusion**

A configuration file, a tool state snapshot, a plan and a running system are
different artifacts or conditions. A committed change is not an applied change,
a successful refresh is not a desired-state edit, and an infrastructure state
file is not a database backup.

Drift need not be malicious or automatically wrong, and an apparently clean report
need not be complete. Reconciliation should preserve a deliberate, reviewed
intent and address operational consequences. Blindly restoring an older declaration
can remove a still-needed emergency adjustment.

### 5) **Performance note**

Reading resource state, computing plans and applying changes consume tool and
provider work and can encounter API limits. A repeated idempotent check can still
perform requests even if it changes nothing. A configuration change can affect
application resources or availability, but the existence of IaC does not establish
a runtime speedup or cheaper operation. No provider comparison, plan timing,
rebuild, worker-removal or performance experiment was run for this packet.

### 6) **Mentor note**

Give the learner the three count records without timestamps and ask which they
would trust. Then reveal the times and authorized emergency action. A sound answer
separates intended policy from observation rather than silently choosing the
largest or newest number as the desired state. Use refresh-only to test whether
they can explain a knowledge change without claiming a resource change.
