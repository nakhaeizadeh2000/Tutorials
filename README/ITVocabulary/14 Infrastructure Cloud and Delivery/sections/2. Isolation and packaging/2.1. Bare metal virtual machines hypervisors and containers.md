## 2.1. Bare metal virtual machines hypervisors and containers

“Three containers” does not mean three physical machines, and “two virtual
machines” does not prove two independent pieces of hardware. Read the resource
boundaries before judging what can run together or fail together.

This lesson uses a conventional hardware VM and Linux process-container model.
Other products can combine these mechanisms. The examples are static arrangements;
no virtualization software, elevated permissions or container runtime is required.

### 1) **Locate hardware guests and the virtualization boundary**

**Bare metal** refers to physical-machine use without an intervening hardware VM
for the specified operating environment. A bare-metal server can still run an
operating system, drivers and applications. The label does not mean “no software,”
“no administrator” or automatically “on-premises.” A provider can supply physical
machines as a service.

**Virtualization** introduces an abstraction of resources. Here, a hardware
**virtual machine**, or **VM**, presents a machine environment to a guest operating
system. A **hypervisor**, also called a **virtual machine monitor** or **VMM**,
manages virtual-machine execution and access to underlying resources. The **host**
supplies the supporting environment; a **guest** runs within the virtual machine.
The words can recur at different levels if virtualization is nested, so name the
particular host and guest when reading a diagram.

In the conventional VM arrangement, each guest runs its own kernel. Several VMs
can share one physical host's processors, memory and storage resources. An assigned
**virtual CPU**, or **vCPU**, is a virtual processing resource presented to a guest;
its count does not automatically establish dedicated physical cores or a measured
amount of useful application work.

A **type 1** or **bare-metal hypervisor** operates directly at the hardware level.
A **type 2** or **hosted hypervisor** operates on a conventional host operating
system. [Red Hat's virtualization explanation](https://www.redhat.com/en/topics/virtualization/what-is-virtualization)
introduces those categories. Real implementations can blur a simple two-box
picture, so use the product's architecture for detailed boundaries. Calling a
hypervisor bare-metal does not mean its guests also run without virtualization.

This infrastructure VM meaning differs from the language-execution VM introduced
in the runtime lesson. Both describe virtual execution models, but a language VM
does not necessarily boot an independent guest operating-system kernel.

### 2) **Distinguish process containers from separate guest kernels**

A **container**, in this Linux process-isolation discussion, runs application
processes within configured resource and visibility boundaries. Containers using
one host kernel share that kernel rather than each booting a separate guest
kernel. The packaged files can include a runtime, libraries and user-space tools;
those files are not a separately running kernel.

A **container runtime** is software involved in creating and running containerized
processes. A surrounding tool such as Docker also provides other management and
packaging facilities. The distinction matters because “Docker” can name a product,
a command interface or an environment containing several components.

Linux **namespaces** give processes scoped views of particular resources, such as
process identifiers, network resources or mount points. The
[Linux namespace manual](https://man7.org/linux/man-pages/man7/namespaces.7.html)
explains this visibility mechanism. A **control group**, or **cgroup**, groups
processes for resource accounting and configured controls such as limits. A
separate view and a resource limit answer different questions. An isolated process
list does not establish a fixed memory allowance.

Julia Evans's [original container investigation](https://jvns.ca/blog/2016/10/10/what-even-is-a-container/) contrasts those two mechanisms
through visible process views and constrained resources. The useful question is
“which kernel and which controls apply?” Her historical administrative commands
are not needed for this lesson. Docker's current
[resource-control documentation](https://docs.docker.com/engine/containers/resource_constraints/)
states that containers have no resource constraints by default at that layer.
Other surrounding policies can impose limits; inspect effective settings instead
of assuming isolation supplies a quota.

Containers and VMs can coexist. A VM can run a Linux kernel supporting several
containers. In that case, those containers share the VM's kernel, not a separate
kernel belonging to each container. Docker Desktop for Linux explicitly
[uses a VM](https://docs.docker.com/desktop/setup/install/linux/), illustrating why
“containers always directly use my laptop's OS kernel” is too broad.

**Isolation** means separation at a named boundary, not a universal security or
failure guarantee. Privileges, shared mounts, networking, kernel exposure and
resource controls affect what is actually separated. A directory deliberately
shared with a container is not made inaccessible merely by using a container.
Separate kernels also do not prove immunity to a hypervisor or shared-hardware
failure. Use the security lesson for policy and defense questions.

### 3) **Trace a mixed arrangement and vary one boundary**

Read this **fictional layout**, whose facts are stipulated rather than observed:

| Layer | Supplied arrangement |
|---|---|
| Physical machine H | One hardware host with a hypervisor |
| VM A | Guest kernel K-A; runs two Linux process containers, web and worker |
| VM B | Separate guest kernel K-B; runs a reporting application |
| Container files | Web and worker have different application/library files |
| Resource policy | No container-level CPU or memory cap is configured; no other caps are supplied in the packet |
| Shared data | Both containers are deliberately given access to one export directory |

There is one physical host, two VM guest kernels and two containerized workloads
in A. Web and worker share K-A despite their different library files. Reporting
uses K-B. None of these counts proves how many cores are reserved or whether the
hardware can sustain the workload.

If K-A fails so VM A's processes stop, both web and worker lose their execution
environment. B's separate kernel is a distinct boundary, but the packet supplies
no proof about its state or user-visible service during that event. If H fails
and both VMs stop, their different guest kernels do not provide hardware redundancy.

Do not interpret the absent container caps as unlimited available hardware or
as proof that the application already exhausted memory. It means this packet
supplies no such per-container allowance. Likewise, separate application files do
not prevent both processes from modifying the explicitly shared export directory.
A review should identify the relevant rule and effective controls before claiming
that a workload cannot affect another.

Change only worker's placement: move it into VM B under K-B, retaining its shared
export access. Web and worker now use separate guest kernels, while H remains a
shared physical dependency and the shared-data access remains. This strengthens
the kernel-separation description; it does not establish a complete security,
availability or performance result.

Practice: instead keep worker in A, but configure a memory limit for it. Did it
become a VM? No. One resource-control condition changed; worker still runs as
containerized processes under K-A. Its exact allocation and failure behavior need
the relevant settings and observations. A limit is not a reservation or proof
that every other resource is constrained.

### 4) **Common confusion**

A container is not defined by being a small VM. A small VM can still have its own
guest kernel, while a large container can still share a kernel. Size does not
identify the isolation mechanism. A filesystem containing an operating-system
user-space distribution also does not prove a separate kernel booted.

Two containers, two VMs and two physical hosts are different counts. A diagram
must show their relationships before those counts support a failure analysis.
“Host” without a level can conceal the difference between a container's immediate
Linux environment and the physical machine underneath it.

### 5) **Performance note**

Sharing a kernel avoids a separate guest kernel for each process container, but
that structural difference does not establish a universal speed or cost ranking.
Workload, storage/network paths, scheduling, configured limits and VM overhead all
matter. A VM can also run many applications. The fictional layout has no startup,
throughput, memory-overhead or interference measurement; none is inferred from names.

### 6) **Mentor note**

Ask the learner to mark the kernel used by each workload before counting machines.
Then change a memory limit and ask which boundary moved. A sound answer separates
resource policy from kernel ownership. Finally, point to the shared directory and
ask why different container files do not establish independent data access.
