## 2.2. Images layers registries tags and digests

Two deployments can request the same image tag and receive different content at
different times. Conversely, two containers created from one image can produce
different results because their inputs and settings differ. Separate packaged
content, its reference and the running instance.

Read the container lesson and earlier artifact-evidence vocabulary first. This
lesson uses Docker terminology and OCI Image Specification 1.1.1 concepts, checked
2026-10-20. The examples are constructed records, not commands to pull or run images.

### 1) **Separate packaged images from instances and filesystem layers**

A **container image** packages filesystem content and configuration used to create
a container. It is an artifact, not a running application. Creating two containers
from the same image creates separate instances with their own execution state.
The image also does not supply every external condition: compatible execution
support, permissions, configuration, network dependencies and data can still matter.

An **image layer** describes filesystem changes, such as added, modified or removed
files. Layers are applied in order to form the intended filesystem view. A **base
image** supplies an existing starting point that another image can extend. Docker's
[image introduction](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/)
describes packaged content and layers; its portability language still needs the
execution conditions from the preceding lesson.

For a small fictional image, layer L1 adds a runtime and `/app/message.txt`
containing `hello`. L2 replaces that file with `welcome` and adds application code.
The composed view has `welcome` at that path. L2 is a change on top of L1, not a
second running machine. These layer labels stand for content, not measured sizes
or real filesystem archives.

An image's addressed content is immutable: changing the packaged content produces
a different content object. Docker commonly adds a container-specific **writable
layer** for filesystem changes made by that instance, leaving the underlying image
layers unchanged. Its [layer explanation](https://docs.docker.com/get-started/docker-concepts/building-images/understanding-image-layers/)
distinguishes those changes. Writing a temporary file inside a container therefore
does not automatically rebuild or publish its source image. Mounted storage can
have its own lifetime and sharing rules; do not assume every changed file belongs
to that writable layer.

A **Dockerfile** is a build recipe describing instructions used to prepare an
image. It is not the built image or a complete record of all resolved build inputs.
If a recipe refers to a changing base-image tag, the same recipe text can select
a different base later. A **build context** is the input set made available to the
builder under its rules; it is not automatically the running container's filesystem.
These terms orient artifact reading here; detailed build syntax belongs to Docker study.

### 2) **Read registry references and identify the hashed object**

A **container registry** stores and distributes image-related content and metadata.
An image **repository** groups named content within that registry. This use of
repository differs from a Git source repository; one can hold source history
while another distributes built images.

Consider the **illustrative reference**, not a runnable command:
`registry.example.test/workshops/report:stable`. The hostname identifies the
registry location in this example; `workshops/report` identifies its repository;
`stable` is the **image tag**, a human-readable reference. The reserved `.test`
name is fictional and not a registry the reader should contact.

Tags can be reassigned unless an applicable registry policy prevents it. A tag
that resembles a version number does not inherently make the mapping immutable.
`latest` is also a name, not a protocol guarantee that it identifies the newest,
most secure or compatible content. Read the publisher's tagging policy and the
actual resolution record.

An **image digest** is a content identifier computed with a named hash algorithm
for a particular object. A reference by digest uses `@` followed by the digest,
for example the syntax `repository@sha256:<complete hexadecimal digest>`. This is
placeholder notation, not an actual retrievable reference. A digest check compares
the addressed bytes with an expected identifier; it is not a publisher signature
or an application behavior test.

An **image manifest** describes a particular image by referencing its configuration
and layers. An **image index**, also called a **manifest list** in Docker usage,
can reference multiple manifests, including platform-specific variants. The
[OCI manifest](https://github.com/opencontainers/image-spec/blob/v1.1.1/manifest.md)
and [index](https://github.com/opencontainers/image-spec/blob/v1.1.1/image-index.md)
definitions establish these different objects. An index digest identifies the
index; a selected platform manifest has its own digest. Record which object was
hashed before comparing two reported values.

This matters when one tag supports both `linux/amd64` and `linux/arm64`. Those
labels identify operating-system and processor-architecture targets. The same
index can select different platform-specific manifests. Different digest strings
in an index report and a platform report are not automatically a mismatch or a
changed release. Check the descriptor relationship and selected platform.

### 3) **Trace a moving tag and a running instance separately**

Read this **fictional timeline**. D-A and D-B stand for different complete manifest
digests for the same platform, not actual SHA-256 values.

| Time | Supplied observation |
|---|---|
| 09:00 | Registry tag `report:stable` resolves to manifest D-A |
| 09:05 | Container C1 is created from D-A; its inventory records that manifest |
| 10:00 | Publisher reassigns `report:stable` to D-B after an application change |
| 10:05 | A fresh retrieval resolves the tag to D-B and creates C2 from D-B |
| 10:10 | Inspection still identifies C1's original image as D-A; no replacement of C1 occurred |

The tag text stayed the same while its registry mapping changed. C1 did not
replace itself merely because the publisher changed the tag. C2 uses different
content under the explicitly supplied fresh-retrieval facts. Do not infer a
particular tool's cache or pull policy when those facts are absent.

Using a trusted D-A digest reference can hold that content selection fixed while
it remains available and accessible. It also continues selecting that older
content; a later fix in D-B does not silently enter the pinned image. An update
process must deliberately assess and adopt the new content. Chainguard's original
[update discussion](https://edu.chainguard.dev/chainguard/containers/security-and-compliance/updating-containers/considerations-for-image-updates/)
usefully raises both moving tags and update decisions. Its broad reproducibility
language should be narrowed to the content actually identified.

Now give two new containers the same D-A image, but supply one with a different
configuration value and a changed external dataset. Equal image identity does
not imply equal outputs. The runtime inputs and data remain separate evidence.
Likewise, a digest bound to a known image does not prove the image has no vulnerable
component, or that its publisher is accepted by the team's trust policy.

Practice: replace the timeline's 10:05 retrieval and C2 inventory rows with only
“deployment file still says `report:stable`.” Can you conclude D-B is running?
No. You know the requested reference text, not its effective resolution or the
running instance's image identity. Request that evidence before diagnosing which
build's behavior was observed.

### 4) **Common confusion**

An image, a tag, a manifest digest and a container identifier name different
things. A container identifier does not itself identify every input or mutable
file the application used. A Git tag and an image tag also belong to different
reference systems even when their text matches.

“Immutable image” and “mutable tag” are compatible statements: immutable content
can have a name whose mapping changes. “Pinned by digest” needs the object and
platform scope, and still leaves an update responsibility. Neither pinning nor
retrieval is a substitute for the earlier provenance and behavior checks.

### 5) **Performance note**

Reusable image layers can avoid repeating some storage or transfer when the
relevant content is already available. A different tag does not by itself mean
all layers changed, and an available image does not remove application startup
work. Compressed download size, extracted storage and running-process memory are
separate quantities. No layer-sharing, download, startup or memory benchmark was run;
the timeline supplies content identity only.

### 6) **Mentor note**

Ask which object each identifier names, then cover the C2 inventory row. A strong
answer stops short of claiming what is running. Next keep the image digest fixed
and vary an external input; the learner should preserve content identity while
withdrawing an unsupported identical-behavior claim. Finally ask who will assess
and adopt D-B, so fixed selection is not confused with automatic maintenance.
