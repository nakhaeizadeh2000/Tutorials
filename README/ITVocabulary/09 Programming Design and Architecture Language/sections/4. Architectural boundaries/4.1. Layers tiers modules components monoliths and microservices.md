## 4.1. Layers tiers modules components monoliths and microservices

A diagram has six boxes labeled “modules,” deployed on three machines. Is it
layered, three-tier or microservices? Box counts alone cannot answer. Logical
responsibilities, execution locations and independent deployment are different
boundaries. State which view a diagram represents before interpreting it.

This lesson uses constructed design/deployment cards for a NestJS application
with the Fastify adapter. It requires the earlier process, API and dependency
lessons, but no framework installation. The cards are static descriptions, not
observations of a deployed system.

### 1) **Separate logical organization from deployment placement**

A **layer** groups responsibilities and establishes dependency rules within a
design. For example, an HTTP handling layer translates requests, application
logic coordinates a booking use case, and a data-access layer implements storage
operations. A layer is not automatically a process or a machine. Several layers
can execute in one application process.

A **tier** identifies a physical execution/deployment separation in the architectural
view being used. A browser, an application-server tier and a separate database
tier form a familiar three-tier view. A tier can contain multiple instances;
“three servers” does not necessarily mean “three tiers.” Microsoft's
[N-tier architecture guide](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/n-tier)
distinguishes logical layers from physical tiers. Confirm what a particular team
means, especially when virtual machines and containers share underlying hardware.

For an original example, suppose one NestJS application process contains HTTP
controllers, booking application logic and PostgreSQL access adapters. It runs
on a server separate from the database server. Its three logical groups are
inside one application tier; the database is another tier. If a diagram also
includes the browser, it can show three tiers overall. Specify the scope rather
than treating the same backend-only picture as a contradictory count.

Layering rules also vary. In **closed layering**, calls go through the adjacent
layer; **open layering** permits skipping intermediate layers under the specified
rules. Those terms describe allowed dependencies, not measured traffic. The
preceding DIP lesson explains how a storage implementation can depend on a
policy-facing contract even when runtime calls go toward storage. Draw source
and runtime arrows separately when that distinction matters.

### 2) **Distinguish modules and components from independent services**

The earlier tools lesson owns language **module** vocabulary. In architecture
conversations, a module can also mean a cohesive design unit larger than one source
file. Ask whether “module” refers to a language mechanism, framework metadata or
a conceptual boundary.

A **Nest module** groups controllers/providers and describes imports and exported
providers for framework assembly. Nest's [module guide](https://docs.nestjs.com/modules)
explains those relationships. Creating `BookingsModule` and `ReportsModule` does
not give them separate processes, HTTP servers or independent deployments.
An exported provider is also not automatically a public network endpoint.

A **component** is a software unit considered through its responsibility and
interface, but the expected boundary depends on the model. Some teams use it
for an internal group of collaborating code. Fowler's
[component discussion](https://martinfowler.com/bliki/SoftwareComponent.html)
uses a stricter replaceable/upgradeable-unit meaning and distinguishes libraries
from out-of-process services. State the intended meaning before inferring that
any box called a component can be deployed independently. A UI component is
another context; it need not be an independently operated network service.

A **monolith** is an application built/deployed as one unit within the stated
scope. It can contain many cohesive modules. A **modular monolith** emphasizes
maintained internal boundaries while retaining that combined deployment. These
labels do not mean one source file, no interfaces or poor design.

A **microservices architecture** divides application capabilities into collaborating
services intended to be independently deployable, with explicit interaction
contracts. James Lewis and Martin Fowler's [original article](https://martinfowler.com/articles/microservices.html)
describes this style and its trade-offs rather than imposing a formal size quota.
A service can have multiple runtime instances or supporting processes. “Micro”
does not establish a line count, team size or one-table limit.

An application's use of a separate database, external email provider or payment
API does not alone make its own backend microservices. Those are dependencies;
identify which application capabilities the team develops and deploys separately.
Likewise, a class named `BookingService` can be an in-process object.

### 3) **Read a boundary claim against concrete change evidence**

Compare these constructed packets. A deployment unit means software selected
and placed into operation together; later delivery vocabulary develops that
process in detail.

| Packet | Stated evidence | Supported interpretation |
|---|---|---|
| A | Booking and reporting modules ship in one backend artifact; three identical backend instances run behind a load balancer | One backend deployment unit with three instances; still a monolith within this scope |
| B | Same deployment as A, but booking/report code expose supported internal interfaces and avoid each other's internal storage details | A modular-monolith design is described; deployment has not become independently separated |
| C | Bookings and reporting have separate service deployments; reporting consumes a supported booking API and can update while bookings stays deployed under its compatible contract | Evidence of service separation and an independent change boundary; neither speed nor failure isolation follows automatically |
| D | Two processes run on different machines, but every reporting change requires deploying a matching booking version at the same time | Physical separation is established; the claimed independent change boundary is not established for those changes |

A has more running backend processes than a single-instance deployment, but those
processes are replicas of the same unit. Splitting its code into twenty directories
would not change that fact. B adds a meaningful internal design claim. Verify
actual dependency use before treating the modular label as evidence that boundaries
are respected.

C still needs API compatibility. A change that breaks the booking API can require
consumer coordination even in a service architecture. D is sometimes described
as a **distributed monolith**: separate processes with changes so coupled that
teams operate them as one coordinated system. That is a diagnosis to investigate,
not a conclusion based only on seeing a shared database or repository. Ask which
specific dependency forces the joint change.

Practice: in A, a report's language changes. Must every backend instance in the
system become a new microservice? No. A new combined artifact can update the
existing backend deployment. Now change the requirement: reporting must scale and
release on a separate schedule with a compatible booking-data contract. A separate
reporting service becomes a candidate. It still needs data access/ownership,
operations and failure decisions. The new requirement changes the trade-off; it
does not prove the implementation works.

Fowler's [Monolith First discussion](https://martinfowler.com/bliki/MonolithFirst.html)
explains the cost of managing services and the difficulty of discovering boundaries
early. Treat its first-hand experience as a reason to examine context, not as a
universal ban on starting with services or a guarantee that any monolith can later
be split cheaply. Preserve a clear change boundary whichever deployment choice
fits the actual requirements.

### 4) **Common confusion**

A network layer, an application layer and a compiler optimization tier use similar
words in different models. They cannot be counted together as one architecture
stack. An “application service” also needs context: object responsibility, deployed
capability and OS-managed background process are different meanings.

Separating processes does not remove semantic coupling. Two APIs can still require
lockstep field changes, and an internal module boundary can sometimes contain
change better than a poorly chosen network boundary. Conversely, one repository
can hold several independently deployable services. Repository layout is not the
deployment contract.

### 5) **Performance note**

Moving an in-process collaboration across a network introduces transport and
serialization work and new failure paths. Separate deployment can allow different
capacity choices for different workloads, but it establishes no automatic speed,
cost or reliability improvement. Extra tiers that only forward calls can add
work without a corresponding requirement benefit. Our packets supply neither
measured durations nor workload/capacity results. Compare the actual call path,
resource use and required outcomes before claiming one architecture scales better.

### 6) **Mentor note**

Ask the learner to mark three things on packet A: logical responsibilities,
deployment unit and running instances. Then compare B and C and ask which boundary
changed in each. A sound answer does not count directories or machines as services;
it identifies the supported contracts and the evidence needed to release one
capability while preserving its consumers. Require an arrow legend before using
a diagram to explain dependency direction.
