## 4.2. Clean hexagonal DDD CQRS and event sourcing

A proposal says, “Use Clean Architecture with DDD, CQRS and event sourcing.” Those
names answer different questions. They can be combined, but one does not require
all the others. Ask which dependency, modeling, read/write or history requirement
each choice addresses.

Read the earlier dependency-direction, deployment and database lessons. The
examples below are constructed architecture and history cards for a NestJS
application using Fastify. They are not runnable framework configuration or an
event-store implementation.

### 1) **Recognize policy boundaries in Clean and hexagonal architecture**

**Clean Architecture** separates policy from mechanisms using an inward source-
dependency rule: application/business policy should not depend on outer framework,
UI or database details. A **use case** represents an application action and the
coordination needed to accomplish it, such as requesting a booking under the
application's rules. Robert Martin's [original explanation](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)
distinguishes source dependencies from control flow and explicitly says its
circles are schematic, rather than a mandatory count.

The earlier `BookingPolicy` and policy-facing `BookingReader` contract illustrate
the idea. An adapter converts database results into application values; the policy
does not import a driver-specific row type. A `domain` directory alone establishes
no such boundary. Inspect the actual dependencies and the values crossing them.

**Hexagonal Architecture**, also called **Ports and Adapters**, emphasizes the
application's inside/outside boundary. A **port** describes a purposeful interaction
contract. An **adapter** connects that contract to a particular technology.
An inbound adapter drives an application operation; an outbound adapter implements
an interaction the application needs. Cockburn's [original 2005 article](https://alistair.cockburn.us/hexagonal-architecture)
explains this symmetry and why the hexagon does not require six ports.

In our constructed example, a Nest HTTP controller translates an incoming request
into a booking action. A PostgreSQL adapter supplies the booking-read capability.
A test driver could invoke that action without HTTP, and an in-memory reader
could supply controlled data. Those replacements help isolate policy checks;
they do not test the real HTTP mapping or PostgreSQL behavior. Nest's Fastify
adapter is a concrete HTTP-platform integration, while “adapter” here describes
a more general architectural role.

Clean and hexagonal architecture share separation goals, with different organizing
emphases. Neither name dictates deployment as microservices. A single modular
application can use these boundaries. Nor does a replaceable database adapter
prove two databases have interchangeable transaction or query guarantees.

### 2) **Place DDD around shared understanding and an explicit model boundary**

**Domain-Driven Design**, or **DDD**, focuses software design on understanding the
problem domain through collaboration between domain practitioners and developers.
A model selects concepts and relationships useful for solving those problems.
For a workshop system, “confirmed booking” should mean a rule both the people
running workshops and the software can explain.

An **ubiquitous language** connects that model to discussion, documentation and
code within a **bounded context**, the boundary in which the model and its meanings
apply. Eric Evans's [DDD Reference](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf),
Definitions and “Putting the Model to Work,” establishes these concepts. The
reference summarizes a larger approach; reading its term list alone is not a
complete modeling process.

Consider a constructed disagreement. Workshop staff say a “customer” is a person
attending a session. Billing staff say a “customer” is the organization receiving
the invoice. Forcing one global `Customer` object can blur participant identity
and billing responsibility. Explicitly scoped models can keep the two meanings
coherent and define the mapping when they interact.

A bounded context is a model boundary, not automatically a microservice, database
or folder. DDD also does not mean merely naming classes `Entity` and `Repository`.
The next modeling lesson develops the object terms. Here the key question is
whether the model captures agreed rules and where those meanings apply.

### 3) **Separate read/write models from an authoritative event history**

**CQRS** means **Command Query Responsibility Segregation**. It separates the model
used to change information from the model used to read it. A **command** expresses
an intended action; a **query** asks for information. For example, `CancelBooking`
requests a change, while a workshop summary asks for active-booking totals.
The request can be rejected; its name does not mean it already happened.

Fowler's [CQRS discussion](https://martinfowler.com/bliki/CQRS.html) describes
separate models and notes that they can share one database or use separate stores.
CQRS does not require two databases, a message broker or event sourcing. Merely
putting `read` and `write` methods in different files does not explain what the
models separate or why. A simple CRUD model may serve the requirement more clearly.

**Event sourcing** records the relevant state changes as an authoritative ordered
event history from which the current state can be reconstructed. An **event**
records something that happened, such as `BookingCancelled`. A **projection**
derives a representation from that history, such as a workshop summary. Microsoft's
[event-sourcing guide](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)
distinguishes the event store, derived views and the additional concurrency,
versioning and replay obligations.

Here is an original static history. Assume no booking exists initially, all events
are valid, and their stored sequence is the application order. For this exercise,
a cancellation removes that booking's active seats. All facts shown have been
retained; this is not a delivery trace.

| Stored sequence | Recorded fact | Active seats after applying it |
|---|---|---|
| 1 | Booking r17 confirmed for 2 seats | 2 |
| 2 | Booking r18 confirmed for 3 seats | 5 |
| 3 | Booking r17 cancelled | 3 |

The current total is 3. Reconstructing through sequence 2 gives 5. A current table
containing only r18 can answer the current total but does not alone explain r17's
history. An ordinary audit log may provide useful history, yet its existence does
not establish that all required state can be reconstructed from it. Inspect the
authoritative record and the reconstruction contract.

Now suppose a separately updated summary projection has applied only through
sequence 2. Its 5-seat result is behind the authoritative history. Ask which
sequence it has applied before claiming the cancellation failed. If the projection
is updated in the same transaction as the history, a different visibility contract
may apply. CQRS/event sourcing names alone do not choose either arrangement.

Compare these distinct choices:

| Design card | What is established |
|---|---|
| Separate booking-command model and report-query model share current-state tables | CQRS is described; no authoritative event history is established |
| Authoritative events rebuild booking state, with one model serving changes and reads | Event sourcing is described; separate CQRS models are not required by that fact |
| Separate command model appends authoritative events; a query model derives summaries | Both CQRS and event sourcing are described; update timing still needs a contract |
| Current-state table is updated and a message is published afterward | Event publication is described; reconstruction from authoritative events is not established |

A name does not solve failure coordination. For the last card, what if the table
update succeeds and message publication fails? The earlier transaction lesson
explains why an external effect does not automatically belong to the database
transaction. A production design must address that boundary; declaring “event
sourcing” does not supply the missing guarantee.

### 4) **Common confusion**

A port in Ports and Adapters is an interaction boundary, not a TCP port number.
DDD's domain is the problem area, not a DNS name. These are contextual meanings,
so preserve the surrounding nouns when speaking to a mixed audience.

An event store and a message broker serve different roles: authoritative retained
history and message distribution need separate contracts. One product may support
several roles, but neither “we publish events” nor “we have a queue” proves event
sourcing. Similarly, DDD, Clean and hexagonal design do not require CQRS everywhere.
Select each choice for the problem it addresses.

Replay also must distinguish reconstruction from new external actions. Rebuilding
a summary must not casually resend every historical email. Fowler's historical
[event-sourcing draft](https://martinfowler.com/eaaDev/EventSourcing.html#ExternalUpdates)
highlights that failure mode; it is not a current framework implementation recipe.

### 5) **Performance note**

Replaying a long history performs work proportional to the events processed under
the chosen handler cost model. Stored derived state or a snapshot can reduce
repeated reconstruction work, while adding storage and maintenance obligations.
A snapshot represents state at a known history position; its correctness and
remaining events must be accounted for. This is related to, but not proof of,
a tested recovery backup.

Separate read models can support query-specific representations, but asynchronous
updates can introduce lag. Added mapping boundaries also perform work. None of
these names guarantees faster writes, fewer conflicts or lower latency. The card
establishes only arithmetic and stated sequencing; no runtime timing is measured.

### 6) **Mentor note**

Ask the learner which question each name answers: dependencies, interaction
boundaries, domain understanding, read/write models or authoritative history.
Then give them only the fourth design card and ask whether event sourcing is
proved. A sound answer identifies the missing authority/reconstruction evidence
and the table/message failure boundary. For the delayed summary, require its
applied history position before diagnosing a failed business action.
