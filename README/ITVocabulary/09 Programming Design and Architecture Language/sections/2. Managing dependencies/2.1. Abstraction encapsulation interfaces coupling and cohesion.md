## 2.1. Abstraction encapsulation interfaces coupling and cohesion

A proposal says, “Add more abstractions to reduce coupling.” More files and
interfaces do not establish that result. Ask which detail callers currently know,
which change should stay local, and which behavior the proposed boundary promises.
This lesson gives those questions precise names.

Read the previous programming-style lesson for classes, methods and state. The
small collection example uses CPython 3.14.4 on Linux x86_64, without external
dependencies. It demonstrates an in-process ownership boundary, not a database
reservation system or a security sandbox.

### 1) **Name the operation contract and the detail it hides**

An **abstraction** presents the aspects relevant to a task while leaving other
details out of the working model. “Add this participant to the roster” describes
an operation without requiring a caller to manipulate list positions. The
abstraction is useful when its simpler contract gives the caller enough information
to use it correctly.

An **interface** is the boundary through which a component is used: its available
operations and their agreed behavior. The implementation performs them. This is
broader than a language's `interface` keyword. A function, object or remote API
can expose an interface. A declaration that names only inputs and return types
may leave important behavior unspecified.

For a roster, our proposed interface is:

| Operation | Contract |
|---|---|
| `add(id)` | For a string participant ID, add it if absent; repeating the ID leaves one occurrence |
| `members()` | Return an immutable snapshot of the IDs, in order of first addition |

A caller can depend on uniqueness, order and snapshot behavior. The internal
list name is not part of that contract. An implementation could use another
representation if it preserved these observations. **Representation independence**
is this ability for callers to rely on the abstraction while the representation
changes. MIT's [abstract-data-type reading](https://web.mit.edu/6.031/www/fa21/classes/10-abstract-data-types/)
connects that freedom to specifying operations clearly. A replacement returning
arbitrary order would break our contract even if it still removed duplicates.

**Indirection** adds a route between a caller and the work, such as a forwarding
function. It can support an abstraction, but an extra wrapper that exposes every
internal list operation may hide no useful decision. Name the reduced knowledge
or protected rule before calling another layer an improvement.

### 2) **Protect the owner’s rules across the exposed interface**

**Encapsulation** groups responsibility and controls interaction with internal
state. **Information hiding** keeps implementation decisions from becoming client
obligations. The ideas overlap: controlled operations can protect an invariant
and leave the storage choice replaceable. They do not require every piece of
information to be inaccessible.

Our roster should own the uniqueness rule. A public getter returning its live
internal list would allow a caller to append duplicates without using `add`.
Putting the list behind a method would not fix that leak. Fowler's
[Encapsulated Collection](https://martinfowler.com/bliki/EncapsulatedCollection.html)
explains this bypass and discusses views and copies. The right returned form
depends on whether callers need a snapshot, live observation or controlled mutation.

Save `roster_boundary.py` and run `python3 roster_boundary.py`. `_ids` indicates
internal state by Python naming convention; it does not enforce private access.
`tuple` builds an immutable sequence. Because these elements are ordinary strings,
this snapshot exposes no mutable participant objects. The example catches the
attempt to append to a tuple so execution can continue.

```python
class Roster:
    def __init__(self):
        self._ids = []

    def add(self, participant_id):
        if participant_id not in self._ids:
            self._ids.append(participant_id)

    def members(self):
        return tuple(self._ids)

roster = Roster()
roster.add("p1")
roster.add("p1")
snapshot = roster.members()
print("After repeated add:", roster.members())
try:
    snapshot.append("p1")
    print("View mutation accepted")
except AttributeError:
    print("View mutation rejected")
print("After attempted mutation:", roster.members())
roster.add("p2")
print("Earlier snapshot:", snapshot)
print("Current members:", roster.members())
```

Observed output:

```text
After repeated add: ('p1',)
View mutation rejected
After attempted mutation: ('p1',)
Earlier snapshot: ('p1',)
Current members: ('p1', 'p2')
```

The repeated `add` preserves one occurrence. The snapshot cannot append, and it
retains its earlier contents after a later addition. The comma in `('p1',)` is
Python's notation for a one-element tuple.

Now change only `return tuple(self._ids)` to `return self._ids`. The returned
value would be the actual mutable list: the append succeeds, the roster contains
two `p1` entries, and the previously returned reference also sees later additions.
That violates both uniqueness protection and the promised snapshot semantics.
Returning a fresh list would isolate its structure but would still fail our
explicit immutable-result promise. The contract determines the appropriate repair.

This example relies on clients respecting `_ids` as internal. Python's
[private-variable discussion](https://docs.python.org/3.14/tutorial/classes.html#private-variables)
explains its conventions and name-mangling limits. Other languages provide different
access controls. Neither an underscore nor an inaccessible field establishes a
complete security boundary, and a method can still expose mutable state indirectly.

### 3) **Assess dependencies and responsibility through a concrete change**

**Coupling** concerns dependencies between parts and how changes or assumptions
connect them. A caller relying on `_ids` being a list is coupled to that detail.
A caller using `members()` is still coupled to the published order and snapshot
contract. Useful software has dependencies; the goal is to make the necessary
ones understandable and contain unnecessary change effects.

**Cohesion** concerns how closely the contents of a unit serve its responsibility.
A roster containing membership operations has a coherent purpose. Adding unrelated
image resizing and exchange-rate retrieval because “they are all helpers” makes
that purpose harder to explain. Class size alone does not establish cohesion.
The [CS 3100 changeability lesson](https://neu-pdi.github.io/CS3100-Spring-2026/lecture-notes/l7-design-for-change/)
uses hypothetical changes to make both terms concrete.

Consider this constructed design card, independent of the executed Python example:

| Stated fact | Consequence for a proposed storage change |
|---|---|
| The attendee screen calls `members()` and needs first-addition order | Preserve that order even if storage changes |
| A report reads `_ids` and sorts that list in place | It depends on representation and changes the owner's order |
| Roster operations enforce membership rules; a separate exporter formats text | The responsibilities have an explainable division |
| Both use one `Utility` object that also handles unrelated currency conversions | Shared placement alone supplies no membership-related purpose |

A sound improvement moves the report onto a supported observation operation and
sorts its own result when it needs a different presentation order. It does not
merely rename `_ids` or add a forwarding class. If order requirements themselves
change, that is an interface change to discuss with consumers.

Keeping related data and behavior together can help, but “never ask for data” is
too broad. Fowler's [Tell Don't Ask discussion](https://martinfowler.com/bliki/TellDontAsk.html)
explicitly recognizes useful query operations and competing design concerns.
Our `members()` observation is intentional. Review the responsibility and contract
rather than banning every getter or splitting every operation into another class.

### 4) **Common confusion**

Encapsulation here concerns program responsibilities and state access. Network
encapsulation means carrying one protocol unit within another; the shared word
does not imply the same mechanism. Likewise, a general interface is not limited
to a TypeScript declaration, and that declaration does not supply a runtime
validator or automatically enforce a business rule.

Reducing the number of imports does not by itself establish lower coupling.
Callers can depend on a shared field's meaning, an undocumented order or a global
configuration value without a conspicuous import. Name the actual dependency and
the change that would expose it.

### 5) **Performance note**

The snapshot copies n references for n IDs, so its construction and additional
reference storage grow linearly. The objects referenced are not recursively
copied. Here the IDs are immutable strings; mutable elements would need further
ownership reasoning. The list membership check also scans candidates. A different
representation could change that cost, but it must preserve the specified order
and observations. No timing was measured. Adding an interface alone establishes
no speedup, and avoiding a necessary copy by exposing mutable state changes the
behavioral contract.

### 6) **Mentor note**

Ask which change each boundary allows: storage replacement, a new sort order or
a new membership rule. Then ask what a caller may observe and mutate. A sound
answer distinguishes a representation change from a contract change, identifies
the leaking reference, and gives a responsibility-based reason for a split.
“High cohesion and low coupling” becomes useful only when the learner can explain
those concrete consequences.
