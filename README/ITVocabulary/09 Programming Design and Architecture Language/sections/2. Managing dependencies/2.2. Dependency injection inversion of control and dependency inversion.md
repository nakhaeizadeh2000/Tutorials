## 2.2. Dependency injection inversion of control and dependency inversion

“These classes use DI, so the architecture is inverted” combines three different
claims. Who supplies a collaborator? Who decides when application code runs?
Which source-level contracts does the policy depend on? Answer those questions
separately before judging the design.

Read the preceding abstraction and interface lesson. The artifacts here are
constructed design descriptions, not executable configuration. The application
context is NestJS with the Fastify adapter; no framework installation is required
to interpret it. Framework provider mechanics remain deeper study.

### 1) **Separate supplying dependencies from controlling execution**

A **dependency** is something a component needs; the earlier tools lesson introduced
the general term. A booking policy might need a collaborator that reads existing
bookings. **Dependency injection**, or **DI**, supplies that collaborator from
outside the consumer instead of making the consumer select and construct its
implementation internally.

With **constructor injection**, the collaborator arrives when the consumer is
created. Setter or property injection supplies it through another supported
initialization path. Required constructor arguments make required dependencies
visible at construction. A later setter may be appropriate when the lifecycle
requires it, but the allowed partially initialized states then need a contract.

A **composition root** is the place where the application assembles its concrete
collaborators. Manual assembly can create a reader and pass it to a policy.
A **DI container** automates resolution and assembly from registrations. DI does
not require a container or decorators. A **service locator** instead lets a
consumer request a collaborator from a registry during its work. Injecting the
locator still leaves that lookup inside the consumer. Fowler's original
[injection article](https://martinfowler.com/articles/injection.html) distinguishes
these arrangements and emphasizes separating configuration from use.

**Inversion of control**, or **IoC**, describes a control relationship in which
another coordinating mechanism invokes supplied behavior or manages an aspect
that the application would otherwise direct. A framework selecting and invoking
a registered request handler is an example. The relevant question is which
control moved: handler invocation, object assembly or another lifecycle step.
Fowler's [IoC explanation](https://martinfowler.com/bliki/InversionOfControl.html)
distinguishes the broader idea from containers. IoC can occur without DI: a
framework can invoke a handler that constructs all its own dependencies.

### 2) **Read source dependencies separately from runtime calls**

The **Dependency Inversion Principle**, or **DIP**, concerns dependency direction.
High-level policy should rely on suitable abstractions rather than detailed
mechanisms; the mechanisms should conform to those abstractions. “High-level”
here means policy, such as deciding booking eligibility. “Low-level” means a
mechanism, such as fetching rows with a particular database driver. These are
roles in this discussion, not ranks of developer importance.

Robert C. Martin's [original DIP paper](https://www.cs.utexas.edu/~downing/papers/DIP-1996.pdf)
explains the policy/detail distinction with replaceable readers and writers.
Its discussion also recognizes abstraction outside class inheritance. Applying
DIP does not require making an interface for every function or wrapping every
stable library operation.

Consider this original design packet:

| Part | Stated responsibility and dependency |
|---|---|
| `BookingPolicy` | Decides eligibility using a supplied `BookingReader` contract; imports no database-driver types |
| `BookingReader` | Policy-owned contract: find bookings for a workshop, returning application booking values with stated absence/error behavior |
| `PgBookingReader` | Implements that contract using a PostgreSQL access layer; maps database results into the required application values |
| Assembly configuration | Chooses `PgBookingReader` and supplies it when constructing `BookingPolicy` |
| HTTP controller | Calls the policy when Nest routes a request to it, using the application's Fastify HTTP adapter |

The source-dependency sketch below is static. Its arrows mean “depends on the
named source contract,” not “a request travels here”:

```text
BookingPolicy ----> BookingReader contract <---- PgBookingReader
```

The policy can be understood without knowing the adapter's SQL row representation.
The adapter knows the contract it must satisfy. A different reader could replace
it if it preserved that contract. Merely naming a contract `IBookingReader` while
returning a driver-specific connection object would retain a dependency on that
detail through the abstraction itself.

A runtime call sketch answers a different question. Here arrows mean “invokes”:

```text
Controller -> BookingPolicy -> selected reader instance -> data access
```

The policy still calls the reader at runtime. Dependency inversion does not mean
the database must call the policy, or that requests reverse direction. The
assembly configuration knows the selected concrete implementation; hiding that
choice from policy code does not make it disappear from the application.

### 3) **Classify a wiring claim and its remaining obligations**

In our NestJS context, a **provider token** identifies a registration; **resolution**
finds the corresponding value or constructs it under the configured rules.
A provider binding may choose a class, an existing value or a factory. A factory
is a function that creates the provided value. A TypeScript interface erases and
cannot itself be the runtime token; a runtime value such as a shared symbol can
identify a binding for that contract. Nest's
[custom-provider guide](https://docs.nestjs.com/fundamentals/custom-providers)
explains those concrete mechanisms.

The [Fastify adapter guide](https://docs.nestjs.com/techniques/performance) explains
the HTTP integration choice. That adapter does not determine whether the policy's
source dependencies follow DIP. HTTP adaptation and provider resolution are
separate responsibilities.

Practice with four variants of the packet. “Established” means established by
the stated design, not by an executed application test:

| Variant | Classification and reason |
|---|---|
| Policy creates `PgBookingReader` internally and exposes a controller handler to Nest | Framework handler invocation demonstrates IoC; the reader is not injected, and policy retains the concrete dependency |
| Assembly passes a concrete `PgBookingReader` to a policy whose source imports and relies on driver-specific operations | Constructor DI is present; that alone does not establish the desired policy/detail inversion |
| Assembly passes a reader satisfying the policy-owned `BookingReader` contract, with source dependencies as sketched | DI and the described DIP boundary are present; no automatic container is required |
| Policy calls a global registry to request its reader each time | Service-location behavior is present; inspect the registry dependency and returned contract separately |

For the third variant, replacing the reader in an isolated policy test could
help observe eligibility decisions without a database. That would not verify
SQL mapping, transaction behavior or the real framework's wiring. A replacement
must satisfy behavior as well as member names. A reader returning an empty list
on every database error could silently change the policy's decisions even though
its method shape looks compatible.

Provider **scope** describes a reuse/lifetime boundary. “Singleton” must name the
container or application context within which an instance is shared. A registration
label does not prove that an old consumer receives a later replacement, and
sharing one mutable instance requires appropriate state ownership. Full framework
scope rules belong to Nest's documentation and the existing TypeScript teaching
container, whose deliberately limited behavior must not be mistaken for Nest's.

### 4) **Common confusion**

DI supplies a dependency; DIP judges the policy/detail relationship; IoC identifies
transferred control. They can support one another, but finding one does not prove
all three. Likewise, a DI token is a runtime identity for wiring, not an API
credential, authorization decision or data validator.

A constructor with many dependencies makes the situation visible; it does not
by itself prove poor design or supply a universal threshold for splitting a class.
Inspect whether those collaborators serve one coherent responsibility. Moving
them behind a generic locator can conceal the same problem.

### 5) **Performance note**

Injection says where a collaborator comes from, not how fast its operations run.
Container resolution and construction perform work; reusing an instance retains
that instance and its reachable state. Resolving or creating expensive clients
for each operation can add work, while inappropriate sharing can violate lifecycle
requirements. Ask when construction happens and which lifetime is correct before
measuring. These static sketches establish no startup, request-latency, database
throughput or framework-versus-manual speed result.

### 6) **Mentor note**

Give the learner the second variant and ask whether passing the dependency already
proves DIP. A useful answer inspects the consumer's source contract and identifies
the retained driver detail. Then ask them to draw separate source and call arrows.
They should explain how the policy can call the concrete runtime object while
depending on an abstraction in source, and name the integration checks still needed.
