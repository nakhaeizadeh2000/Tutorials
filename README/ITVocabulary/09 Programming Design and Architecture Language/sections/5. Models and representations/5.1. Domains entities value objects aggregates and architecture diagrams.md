## 5.1. Domains entities value objects aggregates and architecture diagrams

A box labeled `Booking` can mean a domain concept, a database table, an in-memory
object or a deployed service. These are different models. Before interpreting a
box or choosing a class, ask what distinction the model needs and which question
the drawing answers.

Read the previous DDD, contract and deployment lessons. The records, aggregate
rules and diagrams below are original constructed examples, not a deployed system
or a full implementation of Domain-Driven Design.

### 1) **Distinguish domain identity from equal values and memory identity**

A **domain** is the problem area to which software is applied, such as workshop
booking. A **domain model** selects concepts, rules and relationships useful for
that area. It is not a complete copy of reality. The preceding lesson owns DDD's
shared language and bounded contexts; here we identify distinctions inside a model.

An **entity** is distinguished by continuity of identity across changes. A booking
can remain the same booking when its contact name or status changes. Its identifier
helps express that continuity, but the domain must define what the identifier
identifies. Eric Evans's [DDD Reference](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf),
“Entities,” makes identity primary over a snapshot of attributes.

Use this original record card:

| Observation | Identity interpretation under this booking model |
|---|---|
| Booking r17 initially has contact Mina and 2 seats | One booking identified as r17 |
| r17's contact is corrected to Sara | Still r17; the attribute changed |
| r18 has the same contact and seat count as r17 | A different booking because its booking identity differs |
| A second process loads another representation of r17 | Another representation can refer to the same domain booking |

A **value object** represents a meaning determined by its values, without a separate
conceptual identity to track. For example, two `SeatSelection(2, "standard")` values
can mean the same selection in a model where count and seat category determine
equality. `SeatSelection(2, "premium")` differs. An immutable design replaces the
selection when it changes, rather than mutating shared value state. Fowler's
[value-object discussion](https://martinfowler.com/bliki/ValueObject.html) explains
how the desired equality differs from a language's default object comparison.

Domain identity and runtime object identity must not be collapsed. Two JavaScript
objects loaded for r17 need not compare equal with `===`; that operator does not
implement the booking identity rule. Likewise, creating a class named `ValueObject`
does not automatically supply value-based equality. The language-specific identity
lesson remains the owner of those mechanics.

Classification depends on purpose. A seat selection can be a value within a booking;
a particular physical seat with a maintenance history can be an entity in another
model. Adding a database surrogate key to store a value does not by itself change
what the value means in the domain. ORM vocabulary may also call a mapped table
class an entity; clarify that product usage before assuming full DDD semantics.

### 2) **Read an aggregate as a rule-enforcement boundary**

An **aggregate** groups related domain objects within a boundary for consistent
changes. Its **aggregate root** is the entity through which outside code requests
changes to that aggregate. The root is responsible for preserving the group's
invariants. Evans's “Aggregates” reference and Microsoft's
[domain-validation explanation](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-model-layer-validations)
connect this boundary to enforcing rules across state transitions.

Consider this deliberately limited booking-request model:

| Part | Meaning in this constructed model |
|---|---|
| `BookingRequest` root | Identified request owning the changes to its seat selections |
| Seat selections | Value objects describing count and category |
| Local invariant | The total requested seats must be between 1 and 4 |
| Supported change | Add or replace selections through the root, which checks the resulting total |

A request currently has selections of 2 standard seats and 1 premium seat, totaling
3. Adding 2 more would produce 5, so the proposed change must be rejected or
revised under this model. If outside code can append directly to the internal
selection list and skip the check, the aggregate boundary is not actually enforced.
Drawing a surrounding rectangle does not supply that enforcement.

This local rule says nothing about the workshop's remaining capacity across all
requests. Two individually valid three-seat requests could exceed a five-seat
workshop. That is a separate coordination/invariant question. A production design
must choose the owner and the transactional/concurrency mechanism that preserves
it; naming each request an aggregate is not a solution to that wider rule.

An aggregate is not every object reachable by following references. Putting every
booking, customer, invoice and workshop into one giant aggregate can expand the
work and contention of every change. A boundary should follow required consistency
and responsibility, with explicit treatment for facts outside it. It is also not
a service, a database shard, a SQL aggregate function such as `SUM`, or a requirement
to deploy one process per root.

### 3) **Select a diagram view and read its claims within that scope**

An **architecture diagram** represents selected aspects of a system. It needs a
purpose, scope, element meanings and relationship meanings. The drawing can document
an intended design or an observed deployment; identify which before treating it
as evidence about running software.

**UML**, the **Unified Modeling Language**, is a standardized modeling language
for structure and behavior. A class view can describe types and relationships;
a sequence view can describe interactions over time. OMG's
[UML entry point](https://www.omg.org/uml/) links the specification, whose current
formal page lists 2.5.1. Naming UML does not establish that an informal box sketch
follows its notation or that the implementation matches the model.

**C4** organizes architecture views through **Context, Containers, Components and
Code**. Simon Brown's [official model overview](https://c4model.com/) introduces
these levels. They answer different questions:

| View | Question for the workshop system |
|---|---|
| System context | Who uses the workshop system, and which external systems does it interact with? |
| Container | Which applications and data stores collaborate inside the system boundary? |
| Component | Which groups of functionality collaborate inside one selected container? |
| Code | Which code elements implement a selected part? |

A [C4 container](https://c4model.com/abstractions/container) means an application
or data store, not specifically a Docker container. A
[C4 component](https://c4model.com/abstractions/component) is related functionality
behind an interface inside a container; it is not a separately deployable unit
in that model. This is a concrete example of why the earlier component lesson
requires context. Deployment placement and running replicas need a deployment
view rather than assumptions from the logical box count.

Here is an **informal runtime interaction sketch**, not formal UML or a complete
C4 diagram. Its title is “Workshop booking read path.” Arrows mean “initiates the
labeled interaction”; responses are omitted. Database access is a simplified role
label, not a complete driver/connection trace.

```text
Participant (person)
  -- HTTPS request --> Workshop API (NestJS with Fastify)
                         -- SQL query --> Booking database (PostgreSQL)
```

This sketch identifies roles, technologies and an intended interaction path. It
does not show instance counts, the domain aggregate, transaction boundaries,
authorization decisions, timeouts or measured latency. Those omissions are limits
of the view, not evidence that the system has no such behavior.

Practice: a reviewer says the three pictured elements prove three microservices,
strong consistency and a 50-millisecond response. None follows. The person is not
a service; an application and data store are different element types. The arrow
does not define isolation or the whole operation's atomicity. No time measurement
is shown. Ask for the appropriate deployment, data-contract and measurement evidence.

Now add a note that the API has three replicas. This changes known instance count,
not the number of domain aggregates or independently deployable capabilities.
If an unlabeled arrow replaces the SQL query label, even the interaction mechanism
becomes unspecified. C4's [review checklist](https://c4model.com/diagrams/checklist)
is useful for checking scope, element types, legends and relationship labels.

### 4) **Common confusion**

A domain in this modeling discussion is not a DNS domain name. A domain model is
also not an AI model or simply a database schema. The representations can relate,
but the word alone does not establish their purpose or boundaries.

An entity's identity is a domain distinction, not necessarily a memory address.
An aggregate's consistency boundary must be implemented through controlled changes
and appropriate storage coordination; drawing a root icon does not make concurrent
updates safe. Keep the local invariant separate from claims about other aggregates.

### 5) **Performance note**

Model names and diagram symbols have no direct runtime performance effect. Their
implementation can matter: loading a huge object graph, copying large values or
coordinating many updates can add work and contention. A smaller aggregate is not
automatically better if it leaves a required invariant unprotected. A diagram can
help locate interactions to measure, but arrow count is not latency and a container
box supplies no resource limit. No runtime or load measurement was performed here.

### 6) **Mentor note**

Ask whether correcting r17's contact creates a new booking, whether equal seat
selections need distinct identity, and which operation protects the four-seat
limit. Then ask what still protects workshop capacity across requests. A sound
answer distinguishes identity, value equality, local ownership and wider coordination.
For a diagram, require its question, view, element types and arrow meaning before
accepting a conclusion about deployment or guarantees.
