## 6.1. Review a proposal that hides decisions behind pattern names

A design proposal should explain how a system meets its requirements and what it
costs to change or operate. Names such as Clean Architecture and CQRS can shorten
that explanation once their boundaries are clear. They cannot supply the missing
reasoning. A **design proposal review** connects each claimed benefit to a concrete
requirement, mechanism, consequence and piece of evidence.

This exercise integrates the preceding design lessons. Its workshop booking
application uses NestJS with the Fastify adapter. All requirements, inspection
results and proposed changes below are constructed teaching artifacts. No actual
application or production review is being reported.

### 1) **Expand the names into requirements and boundaries**

The proposal says:

> Our Clean, functional microservices use dependency injection and DDD. CQRS and
> event sourcing make every report correct. Three service instances make totals
> constant time. Deduplicating equal bookings follows value-object design. The
> accompanying refactor raises the minimum booking from one seat to two.

The product requirements are more concrete. A participant can book one or more
seats. Two separate bookings must remain separately identifiable even when their
contact and seat values match. Staff need to see which bookings contribute to a
report, and a proposed delay in report updates needs their agreement. No report
latency target, immediate-read requirement or reason for independent service
releases has yet been supplied.

Start by asking what each design choice is meant to accomplish:

| Proposed benefit | Boundary or decision to inspect |
|---|---|
| Policy independent of database details | Source contracts used by booking policy and its adapters |
| Independently changeable services | Built artifacts, compatible interfaces and deployment units |
| Predictable report calculation | Inputs, effects, authoritative data and report update path |
| Correct identity handling | Booking identity versus values used to compare a selection |
| Safe internal restructuring | Required behavior before and after the change |
| Bounded calculation work | Operation, input size and counted work |

A useful answer may reject an unnecessary mechanism while preserving its goal.
For example, if reports have no independent deployment need, keeping them in the
same application can remain a candidate. Their internal responsibility boundary
still matters. If a separate read model is needed, explain the query it serves
and the additional update and freshness obligations.

Fowler's [discussion of writing patterns](https://martinfowler.com/articles/writingPatterns.html)
connects a named recurring solution to its applicability and alternatives. Apply
that discipline here: ask what problem triggers the choice and what evidence
would make another choice preferable.

### 2) **Separate established facts from unsupported conclusions**

The supplied inspection packet says:

| Artifact | Established fact in this fictional packet |
|---|---|
| Source inspection | `BookingPolicy` imports and uses a driver-specific `PgConnection`; a container passes the connection into its constructor |
| Deployment description | Bookings and Reports are modules in one built application artifact, deployed in three identical running instances |
| Calculation inspection | Each report calculation visits every one of its n input booking rows, once per row; each visit performs bounded work in the stated model |
| Effect inspection | The report formatter writes a `display_label` into the caller's supplied booking records |
| Identity sample | r17 and r18 are distinct bookings with the same contact and seat values; the proposed comparison merges them |
| Model inspection | GET and POST handlers use the same booking model; no separate read model is described |
| Storage description | Current booking rows are authoritative; an event is published afterward, with no authoritative replayable event history defined |
| Change description | The proposed validator rejects one-seat bookings; the only supplied check result is a successful compilation |

Constructor injection is present. The policy still depends directly on the
particular database mechanism, so the stated policy/detail independence is not
established by the container. Ask whether the requirement calls for a policy-owned
reader contract returning application values, and what behavior that contract
must preserve. Simply renaming `PgConnection` to `IPgConnection` would not remove
the driver-specific obligation.

The backend application is deployed as one unit with three instances. That is a
replicated monolith in this stated scope, not evidence of three independently
deployable application services. Whether its modules have well-maintained internal
boundaries remains a separate inspection question. A diagram with three boxes
would not overturn the artifact and deployment facts. The C4
[review checklist](https://c4model.com/diagrams/checklist) asks for an explicit view,
scope and relationship meanings; it does not turn box counts into service counts.

For the report operation, the packet specifies n bounded visits, giving linear
work, Θ(n), under that cost model. Three application instances do not make one
such calculation constant time. The formatter also has an observable effect on
caller-owned records. Calling the surrounding code functional does not make this
operation pure. Decide whether mutation is part of its intended contract; if the
report should leave booking records unchanged, producing separate display values
is a candidate repair.

The proposed equality rule conflicts with the stated booking identities. Keeping
r17 and r18 distinct is a product requirement even when their attributes match.
Value equality can still be useful for a seat-selection value within each
booking. It is the meaning of the modeled thing that decides which comparison
is appropriate.

Separate GET and POST handlers alone do not establish CQRS model separation.
Publishing an event after updating authoritative current rows does not establish
event sourcing. Ask where report inputs come from and how publication failure
is handled. If publication fails after the booking change, which record allows
the reporting path to catch up? The packet supplies no answer. Do not describe
that missing mechanism as a demonstrated live delivery failure, or prescribe
an entire event-sourced replacement before establishing the actual need.

Finally, rejecting one seat changes supported behavior. It contradicts the stated
requirement and cannot be justified merely as a refactor. If the product owner
intentionally changes that requirement, record the behavior and compatibility
change explicitly. Compilation does not demonstrate that existing one-seat
behavior was preserved.

### 3) **Request discriminating evidence and give usable feedback**

A technical review can say:

> The container supplies dependencies, while booking policy still uses a concrete
> driver contract. The backend is one deployment unit with three instances. The
> shown report scans n rows and mutates supplied records. Its proposed comparison
> merges bookings that the requirements keep distinct. Separate read/write models
> and authoritative event history have not been shown. The minimum-seat change
> conflicts with the current requirement. Please resolve those contracts and show
> checks for the affected behavior before asserting the proposed benefits.

For a product collaborator: “The proposal changes which bookings are allowed and
could combine two separate bookings in a report. We need to preserve those rules
or agree on explicit changes. We also need to decide how current a report must be
and what happens when its update fails. The architecture names do not answer
those questions.” This keeps the consequences intelligible without hiding the
uncertainties.

Choose checks that distinguish the disputed outcomes. A case with r17 and r18
sharing attributes checks identity preservation. A one-seat before/after case
checks the changed acceptance boundary. A report call followed by inspection of
its original input checks the mutation contract. Reviewing the policy's imported
and returned types checks its source dependency. A separate integration exercise
would be needed for database mapping and real report publication. These are
proposed checks, not tests executed in this lesson.

Now remove only the source-inspection row. You may still say that DI does not
prove dependency inversion, but you may no longer assert that this policy
actually imports `PgConnection`. The conclusion becomes unverified. Alternatively,
replace the deployment row with evidence that Reports is a separate artifact and
can be compatibly updated while Bookings keeps its deployed version. That supports
independent deployment for that change. It changes neither the report's linear
scan nor the missing authoritative event history.

For interview practice, answer “Which pattern would fix this proposal?” A strong
answer first selects a concrete requirement and demonstrated conflict. For
example, preserving booking identity addresses the merger without requiring a
new deployment style. It then explains a candidate change, a consequence and an
observation that could show the change failed. Reciting every pattern in the
proposal does not meet that reasoning goal.

### 4) **Common confusion**

Using a term imprecisely does not prove that its associated technique is always
inappropriate. An independently released reporting service or a separate read
model may be justified after requirements and costs are known. Equally, correcting
the terminology alone does not repair the one-seat rejection or merged identity.
Distinguish a naming correction, a behavior defect and an unverified mechanism.

Review the artifact supplied rather than inventing a missing implementation.
Here current rows are explicitly authoritative. If a later design makes event
history authoritative and demonstrates reconstruction, reevaluate that claim
against the new evidence instead of treating the earlier conclusion as permanent.

### 5) **Performance note**

This packet establishes counted report work under an explicit model, not elapsed
latency or total system capacity. Data retrieval, sorting, serialization and
contention could add other costs. More instances might serve more independent
requests under suitable conditions, while shared dependencies could limit the
result. No workload measurements are supplied. Ask for the actual operation,
data size, concurrency and measurement boundary before promising a speedup.

### 6) **Mentor note**

Ask the learner to pair one review sentence with its supporting packet row and
its user-visible consequence. Then remove the row and have them revise the
sentence. A sound answer preserves uncertainty and proposes a check that could
change their conclusion. Give feedback on that reasoning before debating which
architecture name the team should use.
