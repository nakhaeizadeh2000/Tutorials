## 1.1. Algorithms data structures complexity and invariants

“Use a better algorithm” needs a problem and a correctness requirement. “Use a
hash map” names an organization choice, but still needs operations and a workload.
This lesson gives you the language to interpret those suggestions without treating
an asymptotic label as a measured speed or a proof that the result is correct.

Read the earlier software, data-model and measurement lessons. The complete small
example uses CPython 3.14.4 on Linux x86_64 with no external dependencies. It is
an observation of values and counted comparisons, not a benchmark.

### 1) **Separate a procedure from the structures it operates on**

An **algorithm** is a specified procedure for solving a problem: given allowed
inputs, it follows defined steps to produce a required result. An implementation
expresses the procedure in executable code. A problem may admit several correct
outputs, and randomized algorithms can make choices during execution; “algorithm”
does not imply that every implementation always follows one fixed path.

A **data structure** organizes data and supports operations on it. The organization
and operations matter together. A sequence supports positions, while a key/value
map supports access by key. Two implementations can support similar operations
with different costs. MIT's [introductory algorithms notes](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-spring-2020/477c78e0af2df61fa205bcc6cb613ceb_MIT6_006S20_lec1.pdf)
separate the problem, algorithm, correctness, efficiency and data-structure interface.
Those distinctions remain useful without adopting that course's full formal model.

| Term | Organizing idea | Example operation |
|---|---|---|
| Sequence or list | Items have positions | Read the item at position i |
| Set | Distinct members under a defined equality rule | Test membership |
| Map or dictionary | Keys identify associated values | Retrieve a value by key |
| Stack | Last added is first removed, or LIFO | Push an item, then pop the top |
| Queue | First added is first removed, or FIFO | Enqueue an item, then dequeue the oldest |
| Tree | Hierarchical parent/child relationships in the stated rooted model | Visit a subtree |
| Graph | Nodes connected by edges | Follow a connection or find a path |

**LIFO** means last-in, first-out; **FIFO** means first-in, first-out. These identify
removal policies, not particular hardware containers. Python's
[data-structure tutorial](https://docs.python.org/3.14/tutorial/datastructures.html)
shows a list used as a stack and a deque used for queue operations. A **deque**,
or double-ended queue, supports adding and removing at either end. Exact ordering,
equality and costs still depend on the implementation and operation.

An array is a storage/sequence representation, but language arrays differ.
JavaScript arrays have their own property and length semantics; do not import a
fixed contiguous C-array model into every language. Likewise, a database graph
model and an in-memory graph can describe related relationships while exposing
different operations, persistence and guarantees.

### 2) **Count work while preserving the search contract**

**Linear search** checks items in sequence until it finds a match or exhausts the
input. Here the contract is “return the first matching zero-based position, or
None if absent, together with the number of equality comparisons.” The input is
a finite list of ordinary integers that is not changed during the call.

Save `search_cost.py` and run `python3 search_cost.py` in its folder. `enumerate`
provides positions and values, `return` ends the function and `None` indicates
absence. `range(n)` supplies integers from zero through n minus one.

```python
def locate(values, target):
    comparisons = 0
    for position, value in enumerate(values):
        comparisons += 1
        if value == target:
            return position, comparisons
    return None, comparisons

values = [7, 3, 7, 9]
for target in (7, 9, 4):
    print("Target", target, "result", locate(values, target))
print("Empty:", locate([], 7))
for size in (10, 100):
    print("Missing in", size, "items:", locate(list(range(size)), -1))
```

Observed output:

```text
Target 7 result (0, 1)
Target 9 result (3, 4)
Target 4 result (None, 4)
Empty: (None, 0)
Missing in 10 items: (None, 10)
Missing in 100 items: (None, 100)
```

The first 7 occurs at position zero, so one comparison suffices. Finding the last
item or proving 4 absent takes four comparisons for this list. The empty list
requires none. The larger missing-target cases count every input item. These
observations check the example; the loop's structure explains why the missing
case scales with list length.

An **invariant** is a condition intended to remain true, introduced in the data
domain. A **loop invariant** holds at a specified repeated point in a loop. Here,
before each comparison, all earlier positions have been checked and do not match.
Initially there are no earlier positions. After a failed comparison, that position
joins the checked prefix. A match is therefore the first match; if the loop ends,
no position matches. The finite unchecked suffix also shrinks, explaining termination.

Now move the final `return None, comparisons` inside the loop after the `if`.
The changed algorithm would stop after the first nonmatch and miss 9. That breaks
the contract even though it performs fewer comparisons. “It does less work” is
not a correctness argument. Harvard's [search teaching](https://cs50.harvard.edu/x/notes/3/)
also contrasts sequential search with dividing a suitably ordered search space.

### 3) **Read complexity with an operation case and cost model**

**Time complexity** describes how computational work grows with input size under
a specified model; **space complexity** concerns memory growth. State what n means,
which operation is counted and whether the claim concerns worst, best, expected
or another case. Here n is the number of list elements and the counted operation
is one integer equality comparison.

**Big O** describes an asymptotic upper bound, ignoring fixed multiplicative
constants and lower-order terms. It does not itself mean “worst case”; you can
bound different case functions. **Big Omega** describes a lower bound and
**Big Theta** a tight asymptotic bound. They are not synonyms for best case and
“best equals worst.” The [MIT notes](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-spring-2020/477c78e0af2df61fa205bcc6cb613ceb_MIT6_006S20_lec1.pdf)
identify those bound roles. Formal proofs belong to deeper algorithm study.

| Common growth label | Meaning in a stated model |
|---|---|
| O(1), constant | Bound does not grow with n |
| O(log n), logarithmic | Growth like the number of repeated constant-factor reductions |
| O(n), linear | Bound proportional to n |
| O(n log n) | Combined linear and logarithmic growth |
| O(n²), quadratic | Bound proportional to the square of n |

Our missing-target search uses exactly n comparisons, hence a tight linear count.
The successful first-item case uses one for a nonempty list. The function keeps
only a fixed number of working values, so its auxiliary state is constant-sized
under this element/word model. The input list itself still contains n items.
The example's list construction and printed output are outside that search count.

**Binary search** repeatedly discards part of a search space using an ordering
condition. On an appropriately sorted random-access sequence it needs logarithmically
many comparisons in the worst case. Sorting or maintaining the sequence is separate
work. Python's [bisect performance notes](https://docs.python.org/3.14/library/bisect.html#performance-notes)
make a useful distinction: logarithmic location does not make insertion into a
list logarithmic, because shifting items can dominate. Name the full operation.

Practice: “The lookup is O(1), so every request finishes in one millisecond.” What
is unsupported? A growth bound is not a duration, and the request can include
other work. Ask for the implementation assumptions, input-size definition and
actual request measurement. Constants, comparison cost, memory and I/O matter.

### 4) **Common confusion**

An algorithm name alone does not establish its prerequisites. Binary search needs
an appropriate ordering; Dijkstra's shortest-path algorithm has graph/weight
conditions that a bare “graph” label does not specify. Ask for the applicable
contract before borrowing a complexity statement.

An invariant is also not automatically a runtime assertion. Reasoning can establish
a maintained property without executing a check at every step. Assertions can test
selected states, but a few passing inputs do not prove every allowed execution.
The existing JavaScript defensive-pattern lesson owns assertion/error mechanics.

### 5) **Performance note**

The comparison counts expose growth for one operation; they measure no elapsed
time. A more suitable structure can reduce search work while adding construction,
update or memory costs. Evaluate the full workload. Even an asymptotically better
algorithm can be slower for a particular small input and implementation. Preserve
correctness and measure equivalent outcomes before claiming a practical speedup.

### 6) **Mentor note**

Ask a learner to state the search contract, explain the empty and duplicate cases,
and identify the maintained prefix property. Then propose the early-return error.
A sound answer rejects its lower comparison count because it changes the result.
For a complexity claim, require n, operation, case and assumptions before a growth
label, followed by the separate evidence needed for a real duration claim.
