## 1.2. Imperative declarative functional and object-oriented styles

A review says, “Make the booking calculation functional.” Before changing code,
ask what should improve: visible data flow, isolation from changing state, or
something else. A style name describes an approach to organizing computation.
It does not replace a result contract or establish that a program is correct.

The preceding lesson supplies algorithm and cost vocabulary. This example uses
CPython 3.14.4 on Linux x86_64, with no external dependencies. It compares a small
calculation; it is not an application backend or a performance benchmark.

### 1) **Distinguish explicit steps from a stated result**

**Imperative programming** expresses computation through commands and explicit
control flow, often updating variables as execution proceeds. A loop that starts
with a total of zero, checks each booking and adds approved seats is imperative.
**Procedural programming** organizes work into procedures or functions; those
procedures can contain imperative steps. Merely putting a loop in a function does
not make the approach functional in the sense discussed below.

**Declarative programming** emphasizes the result or relationships required and
leaves more execution choices to an implementation. For example, a SQL query
specifying a sum over approved bookings leaves access-plan selection to the
engine. The earlier query lesson explains that distinction between the logical
question and the physical plan. Declarative does not mean “no steps happen.”
The steps exist beneath the interface you chose.

These are useful descriptions of a particular expression, component or language
facility. They are not exclusive boxes into which every entire program fits.
Python's [Functional Programming HOWTO](https://docs.python.org/3.14/howto/functional.html)
introduces several approaches and shows how a language can support a mixture.
A declarative SQL query can sit inside an imperative application workflow.

### 2) **Identify data flow objects and effects**

**Functional programming** organizes computation around functions and the flow of
values between them. A **pure function**, under its stated input model, produces
a result determined by its inputs and has no externally observable side effects.
A **side effect** includes writing output, changing shared data or sending a
request. Reading a changing clock can make a result depend on something beyond
its explicit arguments even if the function writes nothing. Both dependencies
and effects matter when reasoning about purity.

**Object-oriented programming**, or **OOP**, organizes responsibilities around
objects with associated state and behavior. A **method** is an operation associated
with an object. A class can define the state and methods for its instances.
Inheritance is one possible relationship between classes; adding an inheritance
tree is not necessary to demonstrate this object-oriented organization. Python's
[class tutorial](https://docs.python.org/3.14/tutorial/classes.html#class-objects)
explains instance initialization, attributes and methods used in the next example.

You can combine these choices. An object method can delegate a calculation to a
pure function, while an outer workflow saves the answer. Pure calculations make
input/output cases easier to isolate from files, clocks and other services. A
method can keep operations near the state they concern. Neither arrangement
ensures sensible responsibilities: a huge function and an object doing unrelated
jobs can both be difficult to understand.

### 3) **Compare the same calculation without changing its contract**

Our contract is: for a finite collection of `(status, seats)` pairs, sum seats
whose status is exactly `approved`. Assume ordinary strings and nonnegative
integers, with no input changes during calculation. This is a metric calculation;
it does not check workshop capacity or reserve seats.

Save `programming_styles.py` and run `python3 programming_styles.py`. A Python
`def` defines a function; `return` supplies its result. The expression `x if test
else 0` chooses between two values. `sum` adds the supplied values. The expression
inside its parentheses produces one value per input pair without first building
a list of those results.

`class Booking` defines our instance shape. `__init__` initializes a newly created
instance, and `self` names that instance in its methods. Calling
`booking.counted_seats()` supplies that instance to the method. The fields here
are directly accessible; this example makes no claim of enforced data hiding.

```python
def imperative_total(rows):
    total = 0
    for status, seats in rows:
        if status == "approved":
            total += seats
    return total

def contribution(status, seats):
    return seats if status == "approved" else 0

def functional_total(rows):
    return sum(contribution(status, seats) for status, seats in rows)

class Booking:
    def __init__(self, status, seats):
        self.status = status
        self.seats = seats

    def counted_seats(self):
        return contribution(self.status, self.seats)

rows = (("approved", 2), ("cancelled", 1), ("approved", 3))
bookings = [Booking(status, seats) for status, seats in rows]
print("Explicit loop:", imperative_total(rows))
print("Value flow:", functional_total(rows))
print("Objects and methods:", sum(b.counted_seats() for b in bookings))
print("Repeated calculation:", functional_total(rows))
print("Empty input:", functional_total(()))
bookings[0].status = "cancelled"
print("After object change:", sum(b.counted_seats() for b in bookings))
print("Original pairs:", functional_total(rows))
```

Observed output:

```text
Explicit loop: 5
Value flow: 5
Objects and methods: 5
Repeated calculation: 5
Empty input: 0
After object change: 3
Original pairs: 5
```

The first three lines compute the same sum, 2 + 3. The loop makes accumulation
explicit; the value-flow expression names a per-row calculation and an aggregate.
The object version associates the operation with each booking and reuses the
same function. Its aggregation expression also has a functional flavor. These
are overlapping design choices, rather than four incompatible languages.

Changing one object's status changes the object-based input, so its later answer
is 3. The original tuple pairs still represent the original facts and yield 5.
Repeated invocation is predictable only with the relevant inputs held fixed.
The empty input yields the additive starting value zero.

Updating `total` inside `imperative_total` changes private working state; it does
not modify the caller's rows or shared data. For this ordinary input model, that
function also has a pure input/output contract. Conversely, a short expression
that calls a function which emails every booking has effects. Recognize behavior
by inspecting dependencies and operations, not by counting loops or parentheses.
The `print` calls in our demonstration deliberately perform output outside the
calculation functions.

Practice: a reviewer proposes moving a database write into `contribution` because
“functional code should do everything in one expression.” Explain the consequence.
The returned number would no longer describe everything the call does; repeated
calculation could repeat writes. Keep the calculation and the intended write
boundary clear. Choosing the write's transactional and retry behavior requires
the relevant database/API contract, not a style slogan.

### 4) **Common confusion**

A language that supports classes can also support standalone functions and loops.
A class declaration is not proof of good OOP, and using `map` is not proof of
purity: its supplied operation may mutate shared state. Likewise, pure functions
can return objects. “Functional versus object-oriented” is too coarse to describe
our method delegating to `contribution`.

Declarative also does not mean shorter or automatically easier to read. An opaque
chain can hide intermediate meanings. Use a named intermediate result when it
makes the contract easier to explain; use an explicit loop when its changing
state and early exits are the clearer expression of the task.

### 5) **Performance note**

All three initial totals examine every supplied booking in this example. The
object demonstration additionally constructs a list of instances. The generator
expressions avoid a separate list of numeric contributions, but the original
input and the booking objects still occupy memory. A style name alone establishes
no elapsed-time ranking or automatic parallel execution. Compare equivalent
outputs, input preparation, allocations and effects before measuring a speed claim.
The previous lesson owns growth bounds and measurement scope.

### 6) **Mentor note**

Ask the learner to identify the inputs and visible effects of each function, then
explain why the local accumulator does not change the caller's data. Next change
an object's status and ask whether the input stayed the same. A sound answer can
identify imperative steps, value flow and object-associated behavior in one
program, and justify a change through a concrete benefit instead of declaring
one paradigm universally superior.
