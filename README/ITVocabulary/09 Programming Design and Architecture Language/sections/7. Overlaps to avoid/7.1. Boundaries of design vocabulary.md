## 7.1. Boundaries of design vocabulary

Understanding a design term lets you ask a more precise question. Implementing
that design requires additional decisions and evidence. This domain has supplied
small observations and constructed reviews so you can distinguish those tasks.
Use the following routes to deepen a particular question without collecting more
pattern names as a substitute for practice.

### 1) **Keep each design question with its conceptual owner**

Return to an owner when a discussion depends on its distinction. A brief reminder
is enough in a report; reproduce the example only when the new problem changes
something material.

| Question in a review | Existing explanation and boundary |
|---|---|
| What grows as input size grows? | [Algorithms and complexity](<../1. Reasoning about programs/1.1. Algorithms data structures complexity and invariants.md>) explains operation, case and cost model; a duration needs a measurement |
| Does this calculation change its inputs? | [Programming styles and effects](<../1. Reasoning about programs/1.2. Imperative declarative functional and object-oriented styles.md>) distinguishes value flow, object responsibilities and observable effects |
| What behavior must survive a representation change? | [Abstraction and encapsulation](<../2. Managing dependencies/2.1. Abstraction encapsulation interfaces coupling and cohesion.md>) owns the behavioral interface and controlled-access distinction |
| Who supplies a dependency, and what does policy depend on? | [DI, IoC and DIP](<../2. Managing dependencies/2.2. Dependency injection inversion of control and dependency inversion.md>) separates assembly, control and source dependencies |
| Is this shared knowledge or merely similar code? | [Principles and patterns](<../3. Principles and refactoring/3.1. SOLID DRY KISS YAGNI patterns and antipatterns.md>) turns DRY and other principles into contextual questions |
| Is behavior intentionally changing? | [Refactoring and replacement](<../3. Principles and refactoring/3.2. Refactoring rewrites technical debt and legacy systems.md>) separates preservation, modernization and future burden |
| What can be deployed or changed independently? | [Architecture boundaries](<../4. Architectural boundaries/4.1. Layers tiers modules components monoliths and microservices.md>) separates logical structure, physical placement and compatible deployment |
| Which data is authoritative, and which model serves reads? | [Clean, hexagonal, DDD, CQRS and event sourcing](<../4. Architectural boundaries/4.2. Clean hexagonal DDD CQRS and event sourcing.md>) separates policy, model, read/write and history decisions |
| What identity or consistency boundary does this box mean? | [Models and diagrams](<../5. Models and representations/5.1. Domains entities value objects aggregates and architecture diagrams.md>) separates domain identity, values, aggregates and diagram views |
| How do I turn the proposal into useful feedback? | [Applied design review](<../6. Applied design review/6.1. Review a proposal that hides decisions behind pattern names.md>) integrates requirements, facts, uncertainty and proposed checks |

The same word may lead elsewhere in another context. A network port belongs to
the network domain; an application port in hexagonal architecture is an interaction
contract. A SQL aggregate calculation is not a DDD aggregate. Clarifying the
subject prevents a technically correct explanation from answering the wrong
question.

### 2) **Choose deeper study from the missing implementation skill**

Algorithm Design is the planned route for designing and proving algorithms beyond
the bounded examples here. Design Patterns develops recurring solutions and their
implementation trade-offs. Clean Architecture & DDD develops policy and model
boundaries in applications. Microservices and System Design develop service
coordination and wider system trade-offs. These are planned subject tracks, not
additional lessons published by this domain.

Framework mechanics also have their own evidence. A declaration that the system
uses DI is not an implementation of provider lifetime, startup wiring or an adapter.
The existing [TypeScript DI lesson](<../../../../TypeScript/14 Decorators and Metadata/sections/3. Patterns in Practice/3.3. Dependency injection with decorators.md>) supplies a runnable, deliberately bounded teaching container.
It does not reproduce every NestJS behavior. Application-oriented backend study
in this curriculum uses NestJS with Fastify; foundational runtime and framework
tracks teach their own subjects directly.

Keep language mechanics with their owners. For example, [JavaScript identity and
copying](<../../../../JavaScript/03 Values Types and Coercion/sections/1. The value model/1.2. Immutability identity and copying how primitives and objects differ.md>) explains reference identity; the booking model decides whether two values
represent the same booking. Likewise, [database transactions](<../../../08 Databases Storage and Data Pipelines/sections/4. Transactional behavior/4.1. Transactions ACID isolation locks and deadlocks.md>) explain storage and concurrency scope; naming an aggregate does not configure
that scope. Use those links to answer a concrete mechanism question rather than
assuming all identity or consistency terminology has one owner.

The next approved vocabulary domain develops concurrency, messaging and distributed
guarantees. Delivery mechanisms, failure handling and ordering need their own
precise scope. Event sourcing and microservice labels do not supply those guarantees.
No unpublished lesson link is needed to understand this boundary.

### 3) **Hand off a mixed design claim without losing the requirement**

Consider this constructed message:

> Each booking is an aggregate in a Clean microservice. Therefore two application
> instances cannot oversell a workshop, replacing the database needs no checks,
> and moving to functional code makes the report constant time.

A useful response begins with the requirement: “Accepted bookings across both
instances must not exceed workshop capacity.” Ask which owner and coordinated
operation preserve that rule across different booking roots. Local checks within
each booking cannot alone establish the shared capacity guarantee.

Next identify the replacement contract. Which policy values, errors, ordering and
transactional outcomes must the new adapter preserve? A policy boundary can reduce
which code needs changing. It does not eliminate storage mapping and integration
checks. Finally, ask which report operation and input size are meant. A functional
form can still scan every row. Its style alone establishes no growth bound or
measured latency.

A technical handoff names those three independent gaps. A product handoff can say:
“We need evidence that shared capacity remains protected, that the replacement
preserves required outcomes, and that the report meets its agreed performance
target.” The term explanations stay at their canonical owners; the handoff carries
the requirement and missing evidence.

Practice: add a verified concurrent booking check for the stated two-instance,
one-workshop case. That adds evidence for that scenario's capacity outcome. It
still does not verify the replacement adapter or the report. A strong answer says
which scope improved and which questions remain open; it does not keep demanding
the same evidence after it has been supplied.

### 4) **Common confusion**

A vocabulary boundary is not a ban on examples or interdisciplinary reasoning.
A small complete example can expose a distinction. A full scheduler, event store
or framework integration introduces additional contracts that deserve their own
teaching sequence and verification.

Similarly, finishing this domain does not establish implementation mastery in
all its named architectures. You should now be able to explain a proposal, locate
a conflict and ask for relevant evidence. Building and operating the system is a
further practical outcome.

### 5) **Performance note**

Study routes and terminology have no direct runtime cost. Implementations of the
named choices can change computation, copying, communication and contention.
Choose the operation and workload before selecting a measurement. A domain model
or diagram can help locate that operation, but neither replaces a profiler,
benchmark or production observation. No performance experiment is supplied here.

### 6) **Mentor note**

Ask the learner to turn one vague claim into a requirement, a conceptual owner
and a concrete next observation. Then change only one piece of evidence. A sound
handoff updates the relevant conclusion and leaves unrelated claims separate.
Use this exercise to select the learner's next practical study task; avoid assigning
an entire framework course when the actual gap is understanding equality.
