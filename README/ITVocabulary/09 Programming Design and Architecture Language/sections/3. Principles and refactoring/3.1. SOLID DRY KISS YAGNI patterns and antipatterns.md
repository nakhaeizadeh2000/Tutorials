## 3.1. SOLID DRY KISS YAGNI patterns and antipatterns

“Make it SOLID and DRY” is not yet actionable review feedback. A useful review
names a responsibility, dependency or duplicated decision, explains its consequence,
and proposes a change with a cost. This lesson turns common design slogans into
questions you can apply to a concrete proposal.

Read the preceding abstraction and dependency-inversion lessons. Examples here
are constructed design and requirement cards. They are not executable programs
or demonstrations that one architecture is universally best.

### 1) **Interpret the five SOLID principles through their intended boundaries**

**SOLID** names five object-oriented design principles. They concern responsibilities,
extension and dependencies, rather than prescribing a number of classes or a
framework. The expansions below identify different review questions.

| Principle | Meaning and a concrete question |
|---|---|
| **S — Single Responsibility Principle (SRP)** | Group behavior around a coherent responsibility and reason for change. Should a booking-eligibility rule change require editing invoice presentation? |
| **O — Open-Closed Principle (OCP)** | Support a useful kind of extension through a stable boundary instead of repeatedly changing established consumers. Can another booking reader satisfy the existing reader contract? |
| **L — Liskov Substitution Principle (LSP)** | A subtype must preserve the behavioral expectations clients rely on when used in place of its base type. Does the replacement preserve the promised results, conditions and failure behavior? |
| **I — Interface Segregation Principle (ISP)** | Avoid making consumers depend on operations they do not need. Can a reporting consumer depend on booking reads without also requiring deletion operations? |
| **D — Dependency Inversion Principle (DIP)** | Keep policy dependent on suitable abstractions, with detailed mechanisms conforming to them. Does eligibility depend on a policy-facing reader contract or on driver-specific connection operations? |

The existing [dependency-inversion lesson](<../2. Managing dependencies/2.2. Dependency injection inversion of control and dependency inversion.md>)
explains D fully, including why injection alone does not prove it. Steven Zeil's
[original SOLID course lesson](https://www.cs.odu.edu/~zeil/cs330/latest/Public/solid/index.html)
introduces the five principles and contrasts type compatibility with expected
behavior. Treat them as design reasoning, not mechanical pass/fail labels.

SRP's “reason to change” is easy to misread as “one method per class.” A cohesive
membership component may need add, remove and observe operations. Robert Martin's
[SRP explanation](https://blog.cleancoder.com/uncle-bob/2014/05/08/SingleReponsibilityPrinciple.html)
connects responsibility to the business concerns requesting changes. Identify
those concerns before splitting code. One person making two unrelated requests
does not make the requests one responsibility.

OCP also does not forbid bug fixes or all edits to existing code. Select the
extension boundary worth preserving. Trying to anticipate every possible future
change adds machinery without establishing that those variations will be needed.
A function parameter or composed collaborator may provide the extension; class
inheritance is not the only mechanism.

For substitution, suppose a reader contract says “return an empty collection only
when the workshop has no bookings; report storage failures distinctly.” A replacement
that converts every database failure into an empty collection changes that contract.
A client could conclude there are no bookings when storage is unavailable. Matching
method names and return shapes does not repair the behavioral difference. For
actual subtyping, this is the kind of reasoning LSP demands; the same contract
question is useful when replacing injected collaborators without an inheritance tree.

ISP does not require every interface to contain exactly one method. A reporting
view may coherently need several read operations. Keep its dependency appropriate
to that use instead of exposing unrelated capabilities or fragmenting the contract
until using it becomes awkward.

### 2) **Distinguish duplicated knowledge from similar-looking text**

**DRY** means **Don't Repeat Yourself**. Its central concern is repeated knowledge:
representing the same decision in several places invites disagreement when it
changes. The Pragmatic Programmers' [published tips](https://pragprog.com/tips/)
frame DRY around an authoritative representation of knowledge. This is broader
than finding identical character sequences.

Consider this original requirement card:

| Requirement owner | Current rule | Approved change |
|---|---|---|
| Refund policy | Refund applications are allowed within 14 days | Change the refund window to 7 days |
| Invitation policy | Invitations expire after 14 days | Keep invitation expiry at 14 days |

A developer combines both values into `DEFAULT_WINDOW_DAYS = 14` because the text
is duplicated. Changing that shared value to 7 would also shorten invitations,
contradicting the second row. The repeated number was coincidence; the two rules
can change independently. Separate names tied to their actual meanings make that
independence visible.

Now change the evidence: both the UI help text and server validation describe the
same refund window. Maintaining independent refund-window constants can make the
UI promise 14 while the server accepts only 7. That is duplicated knowledge. A
shared authoritative policy value, or generated help content derived from that
value, can keep the representations aligned. A real distribution mechanism still
needs compatibility and update reasoning; naming one constant does not synchronize
already deployed clients automatically.

A useful extraction shares a real concept. A general helper full of flags for
unrelated refund and invitation exceptions may reduce repeated lines while adding
coupling. Explain which fact should change together and which facts should remain
independent before claiming DRY requires the merge.

### 3) **Use simplicity and pattern names to justify a specific decision**

**KISS** is commonly expanded as “Keep it simple, stupid”; “Keep it simple and
straightforward” expresses the same practical aim without directing an insult at
a colleague. Prefer a design whose behavior and necessary moving parts are easy
to understand. Simple does not mean shortest source or fewest error checks.
Omitting a required storage-failure outcome makes the contract weaker, even if
the function becomes shorter.

**YAGNI** means **You Aren't Gonna Need It**. It challenges implementing speculative
capabilities before they are needed. Fowler's [YAGNI discussion](https://martinfowler.com/bliki/Yagni.html)
explains the cost of building and carrying unused functionality and distinguishes
it from work that keeps code changeable. YAGNI does not excuse ignoring today's
requirements or removing the checks needed to preserve them.

A **design pattern** describes a recurring solution structure, its applicable
problem and context, and its consequences. An **antipattern** describes a recurring
approach that tends to produce harmful consequences in the stated context, with
a route toward improvement. These names compress a discussion; they do not replace
it. Fowler's [pattern-writing article](https://martinfowler.com/articles/writingPatterns.html)
explains why recurrence, a concrete solution and the reasoning about its use matter.
A pattern is not necessarily a library or code you can paste unchanged.

Practice with this constructed proposal for a NestJS application using Fastify:

> We need one current refund policy and an exported refund report. Create a plugin
> platform for twenty hypothetical future policy providers. Put refund decisions,
> invitation expiry and report formatting in one universal service to stay DRY.
> A substitute reader will return no bookings whenever the database fails so the
> application stays simple. Call the design SOLID.

A reasoned response identifies three distinct problems. The plugin platform has
no stated current variation that justifies its complexity; defer it or provide
concrete requirements and a cheaper extension option. The universal service merges
independent rules and presentation responsibilities; share the actual refund-policy
knowledge while keeping invitation and report changes understandable. Finally,
empty-on-storage-error violates the stated reader contract; preserve that distinction
rather than calling suppressed failure “simple.”

If two real refund-policy variants become required, the extension judgment changes.
A **Strategy** arrangement supplies interchangeable policy behavior behind a common
contract. It can fit that variation, including through functions or objects, but
requires defining selection and compatible behavior. A one-policy implementation
need not add a strategy registry merely to claim the pattern. Full pattern
implementations remain the dedicated Design Patterns track's future work.

### 4) **Common confusion**

Similar-looking code can encode different knowledge, and different-looking code
can repeat the same policy. DRY is therefore a question about meaning and change,
not a ban on repeated syntax. A fixed “extract after exactly three copies” rule
cannot establish whether those copies should remain one decision.

SOLID and YAGNI can pull a proposal in different directions. A useful extension
boundary supports demonstrated change; a speculative platform has costs today.
Resolve the tension using actual requirements, replacement contracts and change
costs. Neither slogan overrides the need for a working, understandable design.

Calling a colleague's solution an antipattern without explaining the context and
consequence teaches little. Describe the observed coupling or failure, then the
proposed repair. Names such as “god object” usually point to accumulated unrelated
responsibilities; line count alone does not prove that diagnosis.

### 5) **Performance note**

These principles establish no direct runtime speed ranking. Sharing code does
not automatically reduce the amount of work performed, and a general plugin path
may introduce construction, lookup or retention work. Conversely, a necessary
abstraction can hide an efficient implementation. State the actual operations
and measure equivalent behavior before asserting a speedup. Development/change
costs are also relevant, but this static proposal includes no measured maintenance
or execution times.

### 6) **Mentor note**

Ask the learner to repair one review comment by naming the affected rule, the
change that exposes the problem, and a concrete alternative. The refund/invitation
example should reveal whether they distinguish shared knowledge from equal values.
Then add a required second policy and ask what changed in their YAGNI/OCP judgment.
A sound explanation revises the decision when the evidence changes and preserves
the reader's behavioral contract throughout.
