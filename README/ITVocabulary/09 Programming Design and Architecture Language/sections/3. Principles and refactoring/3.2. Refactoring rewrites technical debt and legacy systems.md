## 3.2. Refactoring rewrites technical debt and legacy systems

A ticket says, “Refactor the legacy booking system and remove the debt.” That
could mean reorganizing a function, changing a rule, replacing an application or
upgrading an unsupported dependency. Those actions have different contracts and
verification needs. Ask what changes, what must remain observable, and which
future difficulty the work addresses.

This lesson builds on design boundaries and behavior contracts. The complete
small example uses CPython 3.14.4 on Linux x86_64, without external dependencies.
The larger application scenarios are explicitly constructed reading exercises.

### 1) **Separate behavior-preserving restructuring from a changed requirement**

**Refactoring** changes internal software structure while preserving its observable
behavior. It proceeds through transformations intended to keep the software working.
Fowler's [refactoring definition](https://refactoring.com/) distinguishes this
technique from the broader activity of restructuring. “Cleanup” is not sufficient
evidence: deleting an apparently unused operation can change an external effect.

Observable behavior depends on the contract. It may include returned values,
errors, data changes and external interactions. Specify that boundary before
claiming preservation. Keeping the happy-path response while changing failures
or persistent data is not automatically equivalent.

Here is an original extraction example. The contract accepts ordinary integer
seat counts, returns a label for positive counts and raises `ValueError` with the
stated message for zero or negative counts. Boolean values and other types are
outside this small example's allowed input model.

Save `refactor_contract.py` and run `python3 refactor_contract.py`. `raise` produces
the error; `try`/`except` records it so all cases run. `observe` turns each returned
value or expected error into a comparable pair. The extracted validator names
an existing rule; it does not introduce a new acceptance condition.

```python
def original_label(seats):
    if seats < 1:
        raise ValueError("positive seats required")
    suffix = "seat" if seats == 1 else "seats"
    return f"{seats} {suffix}"

def require_positive(seats):
    if seats < 1:
        raise ValueError("positive seats required")

def extracted_label(seats):
    require_positive(seats)
    suffix = "seat" if seats == 1 else "seats"
    return f"{seats} {suffix}"

def observe(operation, seats):
    try:
        return "value", operation(seats)
    except ValueError as error:
        return "error", str(error)

for seats in (-1, 0, 1, 2):
    before = observe(original_label, seats)
    after = observe(extracted_label, seats)
    print(seats, after, before == after)
```

Observed output:

```text
-1 ('error', 'positive seats required') True
0 ('error', 'positive seats required') True
1 ('value', '1 seat') True
2 ('value', '2 seats') True
```

These observations compare a negative, zero, singular and plural case. The source
also shows the same condition, message and label construction under the stated
integer model. The four observations are not a proof covering arbitrary objects,
custom comparison methods or every possible application side effect.

Now change the extracted validator to reject `seats <= 1`. The one-seat case
would change from a label to an error. That is a changed rule, whether intended
or accidental. If the new requirement is “at least two seats,” classify it as a
behavior change and verify that requirement separately. If no such change is
intended, it is a regression to repair, rather than a refactoring success.

### 2) **Describe the future cost behind a debt claim**

**Technical debt** is a metaphor for technical decisions or deficiencies that
make later work harder. The **principal** is the work needed to address the
underlying issue; **interest** is the extra effort or recurring burden caused
while it remains. These are explanatory roles, not automatically monetary amounts
or fixed financial interest rates.

Ward Cunningham's [1992 experience report](https://c2.com/doc/oopsla92.html)
connects shipping an immature implementation with the later need to consolidate
understanding. It is a historical first-hand account, not evidence that object-
oriented software always makes change cheap. Fowler's later
[technical-debt discussion](https://martinfowler.com/bliki/TechnicalDebt.html)
uses the metaphor to compare ongoing change difficulty with remediation effort.

For example, suppose a constructed refund system stores the same policy rule in
three independent locations. Every policy change requires finding and updating
all three, and one location was missed during the last change. That is a specific
burden and failure mechanism. “The files look old” does not establish the same
claim. A useful debt record names the affected work, evidence, proposed remedy,
owner and condition that makes addressing it worthwhile.

Debt can be deliberate, such as accepting a temporary compatibility adapter with
a recorded removal condition. It can also be discovered when new requirements
reveal a poor boundary. Fowler's [debt quadrant](https://martinfowler.com/bliki/TechnicalDebtQuadrant.html)
separates deliberate/inadvertent from prudent/reckless as reasoning dimensions.
They are not labels that establish someone's competence or prove an estimate.

A bug describes incorrect behavior; a debt item describes an ongoing technical
burden. They can be related without being identical. A missing feature is also
not automatically debt. Prioritize using actual change frequency, user impact,
support constraints and repair risk. A frequently changed area can justify
attention sooner than an ugly but isolated area, while a serious support or
security obligation must not be dismissed merely because its code rarely changes.

### 3) **Judge replacement and legacy claims without an age shortcut**

A **rewrite** replaces an implementation, often across a substantial boundary.
It may aim to preserve existing behavior or intentionally change it. The word
alone says little about migration, compatibility or delivery strategy. A replacement
can contain individual refactorings, but a large replacement effort is not evidence
of a sequence of small verified behavior-preserving steps.

A **legacy system** is an existing system inherited or retained under historical
constraints. Teams also use legacy to emphasize unsupported technology, missing
checks or difficult change; clarify the intended meaning. Existing systems may
contain valuable business rules, integrations and operational knowledge. Age
alone establishes neither poor quality nor a need for replacement.

**Modernization** changes a system to meet current needs or constraints. It can
include upgrades, restructuring, replacement and revised operations. “Modern” is
a goal needing specifics, such as a supported runtime or a verifiable change
boundary. A new language or framework does not establish those outcomes by itself.

The **Strangler Fig** approach replaces selected behavior gradually while old
and new parts coexist. Fowler's [updated explanation](https://martinfowler.com/bliki/StranglerFigApplication.html)
discusses incremental replacement and the temporary architecture it can require.
This is an alternative to one large cutover, not a guarantee of low risk or a
requirement to introduce microservices. Data ownership, routing and retirement
of temporary paths still need deliberate decisions.

Practice with this constructed change packet:

| Proposed work | What to call it and what remains to establish |
|---|---|
| Extract a pure refund calculation into a helper, preserving inputs, outputs and errors | A proposed refactoring; compare the relevant behavior after the actual transformation |
| Change the refund window from 14 days to 7 | A changed business requirement; establish its intended acceptance and compatibility |
| Replace an old exporter with a new implementation | A rewrite/replacement; specify preserved behavior, intentional differences and consumer migration |
| Remove two obsolete copies of the refund rule so future changes have one authoritative owner | A debt-reduction goal; preserve required behavior and verify how remaining consumers obtain the rule |

A colleague wants to combine all four into “a small cleanup.” Explain why that
hides risk. Failures could come from restructuring, the new policy or replacement
compatibility. A clearer plan identifies the behavior-preserving work, the intended
behavior change and the replacement boundary separately, with evidence for each.
That does not require a universal number of commits or a complete freeze on changes;
it makes the work's claims reviewable.

If packet evidence only says “the new exporter compiles,” replacement compatibility
is still unknown. Compilation does not show the same file content, errors or data
selection. Identify representative outputs and failure cases to compare, including
any intended differences. Those proposed checks have not been executed here.

### 4) **Common confusion**

A characterization check records existing behavior to help detect unintended
change. Existing behavior may include defects, so the recorded result is not
automatically the desired specification. Decide deliberately which observations
to preserve and which to change under a separate requirement.

A semantic rename tool can help restructure code, but a tool's “refactor” action
is not a compatibility certificate. External consumers and string-named protocols
may sit outside its edit set. Likewise, replacing unsupported technology does not
automatically fix confusing responsibilities in the new implementation.

### 5) **Performance note**

The extracted validator adds a function call in the source; this lesson measures
no elapsed time or interpreter optimization. Its purpose is to expose a rule
without changing the defined label/error behavior. A performance optimization
has its own evidence requirement: compare equivalent outcomes on a stated workload.
Debt “interest” here concerns future engineering burden, which is different from
CPU time, storage latency or a measured service slowdown.

### 6) **Mentor note**

Ask the learner to identify the observer and the behavior promised to stay fixed.
Then introduce the one-seat failure and ask whether the change is still a successful
refactoring. A sound answer depends on the requirement, not the edit's size. For
legacy/debt discussions, require one concrete obstacle, its consequence and the
evidence that would justify restructuring or replacement. Avoid assigning blame
from an old design that may have served different constraints.
