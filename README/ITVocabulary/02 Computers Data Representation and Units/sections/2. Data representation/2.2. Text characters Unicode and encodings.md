## 2.2. Text characters Unicode and encodings

A form allows ten characters, a database field allows ten bytes, and a program
reports that an emoji has length two. Those statements can describe different
counts rather than contradicting each other. The missing question is: which
representation or unit is being counted?

Read bits/bytes and byte order first. This lesson separates text concepts from
language-specific string operations. Its complete Python observation needs no
third-party packages, and the supplied output makes the distinctions visible
even if you do not run it.

### 1) **Distinguish a displayed character from code points and code units**

**Unicode** assigns numbers called **code points** and defines properties and
text-processing rules for a large repertoire of characters. A code point is
written with `U+` and hexadecimal digits, such as `U+0041` for Latin capital A.
That notation identifies the code point; it is not itself the stored byte sequence.

The everyday word **character** can mean what a person perceives as one text
element. It need not correspond to one code point. For example, an e followed
by a combining acute accent can appear as é. The base and accent use two code
points while forming one combined text element in this example.

A **grapheme cluster** is a programmatically determined text segment used as a
practical approximation to a user-perceived character. It can contain multiple
code points. Unicode's [text segmentation annex](https://www.unicode.org/reports/tr29/)
explains both that approximation and the possibility of language/context-specific
tailoring. Counting grapheme clusters is therefore different from counting bytes
and is not a complete theory of human writing or visual appearance.

A **code unit** is a fixed-size unit of an encoding form. UTF-8 uses eight-bit
units, UTF-16 uses sixteen-bit units, and UTF-32 uses thirty-two-bit units. One
code point can require more than one code unit in UTF-8 or UTF-16. The number
in UTF-16 is not a promise that every visible character fits in sixteen bits.

### 2) **Separate text from the bytes used to exchange it**

A **character encoding** defines a representation for text. **Encoding** produces
the representation, often bytes for storage or transfer; **decoding** interprets
that representation as text. A receiver must use the intended encoding, not
guess from how a few familiar letters happen to appear.

UTF expands as Unicode Transformation Format. For valid text, **UTF-8** represents
a code point using one to four bytes. **UTF-16** uses one or two sixteen-bit code
units; **UTF-32** uses one thirty-two-bit unit per code point. None of these
statements makes one visible text element equal to one byte or one code point.
See Unicode's [encoding FAQ](https://www.unicode.org/faq/utf_bom.html).

**ASCII**, expanded as American Standard Code for Information Interchange, is a
much smaller character repertoire/encoding. UTF-8 preserves the ASCII range's
byte values, which helps familiar English text look unsurprising. That does not
extend ASCII to every language or make every byte sequence valid UTF-8.

Two representations can also be **canonically equivalent** without having the
same code-point sequence. Precomposed é (`U+00E9`) and e plus combining acute
(`U+0065 U+0301`) are an example. **Normalization** transforms text according to
defined equivalence rules. NFC, Normalization Form C, uses canonical composition.
Unicode's [normalization annex](https://www.unicode.org/reports/tr15/) defines the
forms and their intended equivalences.

Choose a normalization policy for the task rather than blindly changing all
data. A human-name comparison and preserving the exact bytes of a signed
document have different requirements. Normalization is neither spelling correction
nor a guarantee that every visually similar string becomes equal.

### 3) **Observe distinct counts and decoding failures in a complete example**

Tested environment: **Python 3.14.4 on Linux x86_64**, Unicode database 16.0.0.
Save the following as `text_counts.py` and run `python3 text_counts.py` in the
same folder. `unicodedata` is part of Python's standard library; install nothing.
The quoted escape sequences specify the exact characters without requiring a
particular keyboard layout.

```python
import unicodedata

print("Unicode database:", unicodedata.unidata_version)
samples = ["A", "\u00e9", "e\u0301", "\U0001f600"]
for text in samples:
    points = " ".join(f"U+{ord(ch):04X}" for ch in text)
    print(points, "| code points:", len(text),
          "| UTF-8 bytes:", len(text.encode("utf-8")),
          "| UTF-16 units:", len(text.encode("utf-16-le")) // 2)

print("raw equal:", samples[1] == samples[2])
print("NFC equal:", unicodedata.normalize("NFC", samples[1]) ==
      unicodedata.normalize("NFC", samples[2]))
try:
    b"\xff".decode("utf-8")
except UnicodeDecodeError:
    print("invalid UTF-8 rejected")
```

Observed output:

```text
Unicode database: 16.0.0
U+0041 | code points: 1 | UTF-8 bytes: 1 | UTF-16 units: 1
U+00E9 | code points: 1 | UTF-8 bytes: 2 | UTF-16 units: 1
U+0065 U+0301 | code points: 2 | UTF-8 bytes: 3 | UTF-16 units: 2
U+1F600 | code points: 1 | UTF-8 bytes: 4 | UTF-16 units: 2
raw equal: False
NFC equal: True
invalid UTF-8 rejected
```

The loop visits the four strings. `ord` obtains each code point, and the
formatting expression displays it in hexadecimal. In this Python example,
`len(text)` counts code points, while `len(text.encode("utf-8"))` counts the
encoded bytes. Dividing the explicit little-endian UTF-16 byte count by two
counts its sixteen-bit units. That codec emits no leading byte-order mark, so
the count does not include one. The experiment does not count grapheme clusters
or measure font rendering.

The two é representations compare unequal as raw code-point sequences and
equal after the selected normalization. Finally, `FF` alone is not a valid
UTF-8 sequence. The default strict decoder raises `UnicodeDecodeError`, which
the example catches. Python's [Unicode HOWTO](https://docs.python.org/3.14/howto/unicode.html)
explains the text/bytes boundary and decoding behavior. Silently discarding
decoding errors would hide missing data rather than establish the correct encoding.

Practice: would a one-byte UTF-8 limit accept the smiling-face sample? No: its
single code point requires four UTF-8 bytes in the observed example. A one-code-point
limit and a one-byte limit are different requirements, even before considering
multi-code-point grapheme clusters.

### 4) **Common confusion**

"Unicode" and "UTF-8" are not interchangeable answers to an encoding question.
Unicode text can be represented in several ways. Name the actual encoding when
exchanging bytes, and state which unit a length limit counts.

An escape such as `\u00e9` in source text is also not the same thing as the
UTF-8 bytes for é. The language interprets that escape to construct a string;
encoding the resulting string is a separate operation. Displayed symbols,
source notation, code points and bytes occupy different roles.

### 5) **Performance note**

The examples demonstrate that equal-looking text can have different byte counts.
Storage and transfer limits should therefore be measured in the encoding actually
used. Encoding, normalization and segmentation also perform work; do not repeatedly
transform large text merely to obtain an unrelated property. Their costs depend
on data and implementation. These tiny examples verify semantics, not a universal
speed ranking between Unicode encodings or libraries.

### 6) **Mentor note**

Ask which count supports a storage limit, which supports a language's indexing
operation and which approximates a user's editing action. Then show the two é
rows and ask why direct comparison differs. A sound answer names the representation
and intended equivalence instead of calling one string corrupted or claiming
that Python's length rule applies to every language.
