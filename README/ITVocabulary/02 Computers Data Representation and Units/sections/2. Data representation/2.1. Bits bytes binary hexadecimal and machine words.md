## 2.1. Bits bytes binary hexadecimal and machine words

A diagnostic tool displays `41`; another shows `01000001`; a third shows `65`.
Those displays can represent the same value in different number bases. But a
sequence of bits does not, by itself, tell you whether the program intends a
number, text, a flag or part of something larger.

This lesson uses small values and an optional complete Python experiment. You
need the preceding distinction between hardware resources and their descriptions,
not a mathematics or programming course. Each example's interpretation is stated.

### 1) **Read bits and bytes as patterns with a declared interpretation**

A **bit**, short for binary digit, has two possible values, written 0 and 1.
In this track's modern byte-oriented examples, a **byte** contains eight bits.
The word **octet** explicitly means an eight-bit group, a useful term when a
protocol must avoid historical ambiguity about byte sizes.

Eight bits allow 256 distinct patterns: each of eight positions has two choices,
so the number of combinations is two multiplied by itself eight times. Under an
**unsigned integer** interpretation, the patterns represent whole numbers from
0 through 255. Unsigned means that this interpretation has no negative values.

The same eight bits can be interpreted another way. Under an eight-bit signed
two's-complement integer interpretation, the patterns represent -128 through
127. For example, all eight bits set to 1 represent 255 as unsigned and -1 as
signed two's complement. The pattern did not change; its interpretation did.
Signed simply means negative values can be represented; the actual encoding
still needs to be specified.

This distinction prevents a common diagnostic error: reading a byte display as
though every file or message must be a list of unsigned numbers. A file format
or contract tells you what the bytes mean. An arbitrary byte is not automatically
a complete character or a whole application value.

### 2) **Translate number bases without changing the underlying value**

**Decimal** uses ten digits and place values based on powers of ten. **Binary**
uses 0 and 1 with place values based on powers of two. **Hexadecimal**, often
shortened to hex, uses sixteen digits: 0–9 followed by A–F for values ten through
fifteen. Letter case does not change a hexadecimal digit's value.

| Base | Display of decimal 65 | How the value is obtained |
|---|---|---|
| Decimal | `65` | Six tens plus five ones. |
| Binary | `01000001` | One sixty-four plus one one; the other positions contribute zero. |
| Hexadecimal | `41` | Four sixteens plus one one. |

One hex digit covers four bits, so two hex digits display one byte conveniently.
For example, binary `11111111` is hex `FF` and unsigned decimal 255. Prefixes such
as `0b` for binary and `0x` for hexadecimal identify notation in many programming
languages and tools. They are not extra bits stored in the numerical value.

Leading zeros can preserve the displayed width of a field. `00000001` and `1`
have the same unsigned numerical value, but the first display makes an eight-bit
field visible. Padding text is different from allocating or changing the field's
actual representation in memory.

### 3) **Ask about width signedness and byte order before interpreting a field**

A **machine word** refers to a unit associated with an architecture or interface,
but its size must be checked in that context. A 64-bit machine does not make
every value or API type 64 bits. For a concrete counterexample, the Windows
[data-type reference](https://learn.microsoft.com/en-us/windows/win32/winprog/windows-data-types)
defines its type named `WORD` as a 16-bit unsigned integer. An interface's defined
name wins over a guess based on the computer's marketing description.

**Endianness** is the byte-order convention for a multi-byte representation.
For the two bytes `01 02`, a big-endian unsigned interpretation places the more
significant byte first: one times 256 plus two, giving 258. Little-endian places
the less significant byte first: one plus two times 256, giving 513. It is about
byte order here, not reversing the bits within each byte.

The following experiment is tested with **Python 3.14.4 on Linux x86_64** and
uses no packages or imports. Save it as `byte_patterns.py` and run
`python3 byte_patterns.py` from the same folder. `print` displays values;
`format` produces a chosen notation. `bytes` constructs a byte sequence and
`int.from_bytes` interprets it with the stated order and signedness.

```python
value = 65
print("decimal:", value)
print("binary:", format(value, "08b"))
print("hex:", format(value, "02x"))

data = bytes([1, 2])
print("big:", int.from_bytes(data, "big"))
print("little:", int.from_bytes(data, "little"))
print("unsigned ff:", int.from_bytes(b"\xff", "big"))
print("signed ff:", int.from_bytes(b"\xff", "big", signed=True))

try:
    (256).to_bytes(1, "big")
except OverflowError:
    print("overflow: 256 does not fit in one unsigned byte")
```

Observed output:

```text
decimal: 65
binary: 01000001
hex: 41
big: 258
little: 513
unsigned ff: 255
signed ff: -1
overflow: 256 does not fit in one unsigned byte
```

In the formatting strings, `b` selects binary and `x` selects lowercase hex.
The `08` and `02` request zero-padded minimum display widths. They do not limit
the integer's allowed size. Python's ordinary integer can hold 256; converting
it into a single unsigned byte fails because that representation ends at 255.
The `try`/`except` block catches this intentional failure and prints a stable
explanation instead of terminating the example.

The behavior follows Python's
[integer byte-conversion reference](https://docs.python.org/3.14/library/stdtypes.html#int.from_bytes)
and [format documentation](https://docs.python.org/3.14/library/functions.html#format).
Other languages can reject, wrap or otherwise handle out-of-range conversions
under different rules. Do not infer their behavior from this Python example.

Practice: interpreting `01 00` as a two-byte unsigned integer produces 256 in
big-endian order and 1 in little-endian order. Explain the calculation before
changing a parser. A disagreement can mean mismatched representation assumptions,
not corrupted bytes.

### 4) **Common confusion**

Hexadecimal is a display notation, not encryption and not inherently compression.
Writing a byte as two hex characters makes it easier for a person to inspect,
but storing those characters as text is a different representation with its own
encoding cost. The value and the way it is written are different questions.

A 32-bit or 64-bit label also does not settle every width, alignment or byte-order
rule used by a program. Read the field's contract. A byte order can be explicitly
defined by a file or protocol regardless of the host machine's native convention.

### 5) **Performance note**

Formatting a value for display is additional work and creates text, while an
actual byte sequence has its own storage size. Two hex digits describe eight
bits mathematically; that does not mean text rendering is free or uses one byte.
For performance questions, distinguish the in-memory value, its serialized bytes
and diagnostic text. This tiny experiment verifies interpretation, not conversion
throughput or a universal advantage for a particular number base.

### 6) **Mentor note**

Give a learner `FF` and ask for its value. A careful answer first asks for the
base, field width and signedness. Then provide the two-byte pattern `01 02` and
ask what byte-order information is still needed. The goal is to expose missing
representation assumptions, not reward mental arithmetic performed on an
unstated contract.
