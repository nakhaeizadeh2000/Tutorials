## 1.1. Hardware software firmware and drivers

A camera is connected, its indicator lights up, but the meeting application
shows no picture. Is this a hardware problem, a software problem, or something
else? Those labels help organize an investigation, but the symptom alone does
not identify a cause.

This lesson introduces four related terms through a constructed device report.
No hardware purchase, installation or update is needed. You only need the first
domain's habit of distinguishing an observation from a proposed explanation.

### 1) **Distinguish physical components from the instructions they execute**

**Hardware** means the physical components of a computing system: chips, a camera
sensor, a keyboard, a screen, cables and storage devices. **Software** includes
programs and the instructions and associated material that make them work. A
meeting application is software; the camera sensor is hardware.

Software is stored and executed using physical hardware. That does not erase
the distinction. Replacing a storage device changes a physical component;
installing a different application changes the software stored on it. You can
change software while retaining the same device, or replace a failed device
while reinstalling the same software.

An **operating system**, often shortened to OS, manages computing resources and
provides services that applications use. Windows, Linux and macOS are examples
of operating-system families. For now, distinguish the OS from an application
running on it; later lessons explain OS responsibilities in more depth.

### 2) **Locate firmware and drivers within the software picture**

**Firmware** is software closely tied to a device's low-level operation. It may
initialize components, control a device's behavior or participate in starting
the system. It is often stored in non-volatile device memory, which retains its
contents without normal operating power. Firmware is not a physical component
halfway between hardware and software: it is software with a particular role.

A **device driver** is software participating in communication between an OS
and a device. Applications can use OS-provided operations instead of each
implementing the device's detailed communication rules. The driver may be
supplied with the OS rather than installed separately. Microsoft's
[driver introduction](https://learn.microsoft.com/en-us/windows-hardware/drivers/gettingstarted/what-is-a-driver-)
also explains that real systems can have several driver layers, and some drivers
do not correspond directly to one physical device. The simple picture is an
orientation, not a complete universal architecture.

| Part in a simplified camera setup | Classification | Role |
|---|---|---|
| Camera sensor and electronics | Hardware | Capture light and provide physical device capabilities. |
| Device control program | Firmware | Operate device-specific functions. |
| Camera-related OS driver | Software, specifically a driver | Participate in access to the camera through the OS. |
| Meeting application | Application software | Request camera data and present it in a meeting. |

Firmware and drivers are therefore kinds of software, not mutually exclusive
alternatives to software. A download page may list "software," "drivers" and
"firmware" in separate product categories for convenience. Read each package's
purpose instead of assuming the headings define disjoint technical categories.
Device manufacturer Plugable's
[first-hand support explanation](https://plugable.com/blogs/news/hardware-software-drivers-and-firmware-explained)
uses connected-device examples to distinguish those roles.

### 3) **Interpret boot and update descriptions without collapsing the layers**

**Booting** is the process of starting a computing system toward a running
environment. A **bootloader** is a program involved in loading or starting a
subsequent stage, often an operating system. Boot firmware and bootloaders can
participate in that sequence; their exact division depends on the platform.
Device firmware can also operate long after startup, so firmware does not mean
only the code used before the OS starts.

Firmware is not necessarily immutable. For a concrete primary example,
Raspberry Pi publishes an
[EEPROM bootloader repository](https://github.com/raspberrypi/rpi-eeprom)
containing firmware images and update tooling for specified board families.
Here, EEPROM names a kind of electrically erasable programmable read-only memory.
The historical read-only wording does not mean this particular memory can never
be rewritten. This example establishes that some firmware can be updated; it
does not establish that every device supports the same update process.

Now inspect this fictional report:

```text
Device: Camera A, hardware revision 2
Device firmware: 1.6
OS driver: 4.2
Meeting application: 8.1
Observation: camera indicator is on; application reports no image
```

The numbers identify different components' versions, not stages on one common
version scale. A driver update changes a different part from a device-firmware
update. An application update does not, by that fact alone, replace the camera's
electronics or firmware.

Practice: classify the change "application 8.1 was replaced by 8.2; firmware
still reports 1.6." It is an application-software change, with no reported change
to the firmware version. The record does not prove the camera is faulty, that
the driver is correct, or that the update fixed the missing image. Ask what
behavior was observed after the change before making those claims.

### 4) **Common confusion**

"The device powers on" does not establish that its entire hardware/software path
works. The indicator is one observation, not a complete test of capture, access
permissions, drivers and application behavior. Conversely, an application error
does not prove the physical device is damaged.

Nor does every device need a vendor installer. An appropriate driver can already
be provided by the OS. The existence of a separate download is not the definition
of a driver, and installing every available package is not a diagnosis.

### 5) **Performance note**

Physical capabilities and software behavior both influence performance. Firmware
or driver changes can alter device behavior, but their category or newer version
number does not predict a speedup. Identify the operation, versions and conditions
and compare observed results. The fictional camera report contains no performance
measurements, so no throughput or latency conclusion is justified.

### 6) **Mentor note**

Ask a learner to label each row of the camera report and name which part changes
when its version changes. Then ask why a lit indicator does not settle the cause
of the missing picture. A sound explanation separates physical capability,
device control, OS integration and application behavior without asserting that
every real device has exactly four isolated layers.
