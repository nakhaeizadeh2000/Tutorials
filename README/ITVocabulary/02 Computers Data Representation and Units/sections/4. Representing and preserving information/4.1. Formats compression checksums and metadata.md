## 4.1. Formats compression checksums and metadata

A teammate renamed a file to `report.gz`, another says it became smaller, and a
third says its checksum changed. These statements answer different questions.
The name suggests a format, size describes a quantity, and a checksum summarizes
specified bytes. None of those statements alone establishes that the report is
valid or came from the expected author.

Read the earlier byte and text lessons first. This lesson uses a small optional
Python experiment, with no downloaded files or external packages.

### 1) **Distinguish a format from its name and metadata**

A **file format** defines rules for representing information: how a reader should
interpret the stored sequence. A filename **extension**, such as `.gz`, is a naming
convention. Renaming arbitrary bytes does not transform them into the suggested
format. A reader must still recognize and validate the actual representation.

**Metadata** describes data or its context. A filename, modification time, image
width or author field can be metadata. Its location depends on the system: some
metadata lives inside the file, while other metadata is recorded separately.
Changing an embedded description changes the file's bytes even when the main
content remains equivalent for a particular task.

For a concrete format, gzip has a header, compressed data and a trailer. The
header can contain an original filename and modification time; its trailer
includes a check value for the uncompressed bytes. These are format-defined
fields, not assumptions based on the `.gz` suffix. See the
[gzip format specification](https://www.rfc-editor.org/rfc/rfc1952.html#section-2.3.1).

Ask what “the same file” means in a discussion. It might mean identical bytes,
the same decoded text, or the same visible image. Those are different comparison
rules. An updated author field could change a whole-file digest without changing
the report's numerical results. Conversely, equal-looking text need not have
identical encoded bytes, as the earlier Unicode example demonstrated.

### 2) **Separate lossless compression from other transformations**

**Compression** seeks a representation that uses less space. **Lossless compression**
permits exact recovery of the original data. **Lossy compression** discards some
information under a chosen quality model, so recovery need not reproduce every
original detail. State which data is being preserved. An image format can preserve
its pixel data while a separate editing operation has already removed metadata.
The [PNG specification's lossless definition](https://www.w3.org/TR/png-3/#dfn-lossless)
provides a precise bit-for-bit criterion for the compression operation.

Compressing is not guaranteed to shrink every input. The representation itself
has overhead, and an input may contain little useful redundancy. Do not add a
compression step merely because the filename contains “backup.” Compare actual
sizes and establish whether exact restoration is required.

This complete example was tested on **Python 3.14.4, Linux x86_64**. Save it as
`representations.py` and run `python3 representations.py` in that folder. It uses
standard-library `gzip` for compression and `hashlib` for SHA-256 digests. A digest
is a computed summary of input bytes, introduced further in the next section.
The `b` prefix creates bytes, `len` counts them, and `==` compares two values.

```python
import gzip
import hashlib

payload = b"order=paid\n" * 100
packed = gzip.compress(payload, compresslevel=9, mtime=0)
print("Original bytes:", len(payload))
print("Compressed bytes:", len(packed))
print("Exact round trip:", gzip.decompress(packed) == payload)
print("Tiny input sizes:", len(b"A"), len(gzip.compress(b"A", compresslevel=9, mtime=0)))
print("Compressed digest equals original:",
      hashlib.sha256(packed).digest() == hashlib.sha256(payload).digest())
changed = payload.replace(b"paid", b"void", 1)
print("Changed digest equals original:",
      hashlib.sha256(changed).digest() == hashlib.sha256(payload).digest())
try:
    gzip.decompress(b"not gzip")
except gzip.BadGzipFile:
    print("Invalid gzip rejected")
```

Observed output in that environment:

```text
Original bytes: 1100
Compressed bytes: 41
Exact round trip: True
Tiny input sizes: 1 21
Compressed digest equals original: False
Changed digest equals original: False
Invalid gzip rejected
```

The repeated line compresses well; the one-byte input grows because the complete
representation needs additional structure. Decompression restores the repeated
payload exactly. `mtime=0` omits the current timestamp from the gzip header; the
compression level is explicit too. Other compressor versions may produce different
compressed bytes or sizes while preserving the round trip. Python documents these
options and the possible invalid-input exceptions in its
[gzip reference](https://docs.python.org/3.14/library/gzip.html). The caught failure
here concerns this deliberately invalid header, not every possible damaged stream.

### 3) **Use checksums as evidence of a defined byte sequence**

A **checksum** is a computed check value used to help detect changes or errors.
CRC means **cyclic redundancy check**; gzip includes a CRC-32 of its uncompressed
data. A **hash function** maps input data to a digest; SHA-256 is a cryptographic
hash algorithm often used for file comparisons. “Checksum” is also used loosely
for published hash digests, so ask which algorithm and input were used.

Python's [hashlib reference](https://docs.python.org/3.14/library/hashlib.html)
distinguishes a byte-valued `digest()` from `hexdigest()`, a hexadecimal text
display of the digest. The experiment compares digests of bytes directly. The
compressed representation has a different digest from the original; changing one
occurrence of `paid` also changes the observed digest. Neither result identifies
the cause of an unexpected mismatch. You must first check that both parties
hashed the same representation using the same algorithm.

Matching check values are evidence within that comparison, not a proof of who
created the data. Different inputs can share a finite-sized check value, and a
party able to replace a download might also replace an untrusted published hash.
An ordinary check value alone provides no authenticated connection to an author.
Encryption, signatures and trust have separate roles, taught later in this track.

Practice: a sender hashes the original report, while the recipient hashes its
gzip file. They obtain different values. Is corruption established? No. They
compared different byte sequences. First agree whether to compare the transferred
gzip bytes or the recovered report bytes, then compare the relevant values.
A mismatch after that correction still requires investigation.

### 4) **Common confusion**

“Binary file” and “compressed file” are not synonyms. Text is stored as bytes too;
compression is a particular transformation. Similarly, an extension is a clue
for choosing a reader, not proof of valid contents. The experiment rejected bytes
because they failed the gzip reader's checks, regardless of any possible name.

Lossless recovery is also different from confidentiality. Anyone with the usual
decompressor can recover this example's text; it contains no secret key or access
control. A smaller representation does not make the information private.

### 5) **Performance note**

Compression exchanges processing work and memory for a potentially smaller stored
or transferred representation. The benefit depends on the data and the limiting
resource. These byte counts establish sizes for two inputs, not compression
throughput or end-to-end transfer time. This bounded example holds everything in
memory; it is not a prescription for loading arbitrarily large files at once.

### 6) **Mentor note**

Ask a learner to mark which bytes are counted, restored and hashed at each line.
Then propose changing only an embedded timestamp. A sound explanation separates
the unchanged recovered content from the possibly changed packaged bytes, and
asks which comparison the requirement actually promises.
