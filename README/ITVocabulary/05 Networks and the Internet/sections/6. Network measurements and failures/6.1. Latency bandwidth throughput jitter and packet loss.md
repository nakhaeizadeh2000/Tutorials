## 6.1. Latency bandwidth throughput jitter and packet loss

A link is labeled 100 Mbit/s, a file transfer achieves 34 Mbit/s, and a probe
reports 30 ms. These values do not contradict one another. They describe different
quantities and may describe different paths, intervals and traffic. “The network
is slow” loses those useful distinctions.

Read the units, packet and transport lessons first. The complete Python example
uses **synthetic inputs**. It verifies arithmetic; it is not a speed test of this
computer, an ISP or a remote service.

### 1) **Separate elapsed delay from capacity and observed rate**

Network **latency** is elapsed delay between specified events. A **one-way delay**
concerns movement from one observation point to another in a stated direction.
A **round-trip time** (**RTT**) concerns an outward-and-return observation. State
whether the method includes a reply generator's processing time; different probe
methods and tools can include different work.

Do not divide every RTT by two and report it as a measured one-way delay. Paths
and queueing can differ by direction. In a constructed case with 10 ms outward,
20 ms return and negligible turnaround, RTT is 30 ms; neither direction took
15 ms. One-way timestamps across machines also require suitable clock handling.
[RFC 7679](https://www.rfc-editor.org/rfc/rfc7679.html)
explains how clock synchronization error contributes to one-way measurement error.
A negative computed delay can reveal a measurement problem rather than a packet
moving backward in time.

**Bandwidth** is overloaded. In many network reports it means information-carrying
**capacity**, expressed in bits per second. In other technical contexts it can
refer to a frequency range. **Throughput** is an observed rate: a counted amount
divided by an observation interval at a stated boundary. A nominal link capacity
is not a promise that an application's useful data arrives at that rate.
[RFC 5136](https://www.rfc-editor.org/rfc/rfc5136.html)
distinguishes physical/link quantities from IP-layer capacity, usage and available
capacity. Ask which meaning a specification or chart uses.

Several factors can separate a link label from an application observation:
other users share capacity, protocol metadata consumes space, retransmission can
repeat data, endpoints may produce or consume slowly, and the path may contain
a more restrictive link. Do not identify a specific bottleneck merely by noticing
a difference. Establish the actual traffic and observation boundary first.

For a transfer report, distinguish application payload bytes from protocol bytes
or all observed wire traffic. “8 MiB arrived in 2 seconds” requires deciding which
bytes and whether the interval includes setup and waiting. A request's response
time can additionally include server processing. That is not automatically the
network-only delay.

### 2) **Specify how variation and loss were counted**

Network **jitter** usually refers to variation in delay, but several metrics use
that word. [RFC 3393](https://www.rfc-editor.org/rfc/rfc3393.html#section-1.1)
explains this ambiguity and defines a selected-packet difference in one-way delay.
A report should identify the calculation, sample and units rather than treating
“jitter 5” as a complete measurement.

For fictional one-way delays of 10, 12, 11 and 40 ms, successive signed differences
are `+2`, `-1` and `+29` ms. A negative difference means the later packet in that
pair had a smaller delay; it is not a negative travel time. The maximum-minus-
minimum delay would instead be 30 ms. These are different summaries of the same
sample. Do not interchange either with an unnamed tool's jitter value.

**Packet loss** concerns packets not delivered under a specified observation
rule. A **loss ratio** divides the counted lost packets by the relevant sent
population. If 5 of 100 selected test packets are not received by the declared
threshold, the measured loss ratio for that population is 5%. It is not a
universal five-percent loss rate for every application and future interval.

A receiver must distinguish a very late packet from a packet counted as lost.
[RFC 7680](https://www.rfc-editor.org/rfc/rfc7680.html#section-2.8)
requires reporting the loss threshold and measurement context; it also discusses
instrument errors. Dropping a packet in the measurement tool can look like network
loss. A request timeout is weaker evidence still: it does not by itself identify
whether the request, response, processing or some other stage failed.

### 3) **Calculate a scoped report from synthetic observations**

Save `network_quantities.py` and run `python3 network_quantities.py`. Tested:
**CPython 3.14.4 on Linux x86_64**, standard library only. `Fraction` represents
exact ratios; formatting then chooses the displayed decimal precision. The delay
values are supplied observations for this exercise, not clock readings.

```python
from fractions import Fraction

payload_bytes = 8 * 2**20
seconds = 2
bit_rate = Fraction(payload_bytes * 8, seconds)
print(f"Payload rate Mbit/s: {float(bit_rate / 10**6):.6f}")
print(f"Payload rate MB/s: {payload_bytes / seconds / 10**6:.6f}")
sent, missing_by_threshold = 100, 5
print(f"Selected-packet loss percent: {100 * missing_by_threshold / sent:.1f}")
delays_ms = [10, 12, 11, 40]
changes = [later - earlier for earlier, later in zip(delays_ms, delays_ms[1:])]
print("Successive signed delay differences ms:", changes)
print("Delay range ms:", max(delays_ms) - min(delays_ms))
```

Observed calculation output:

```text
Payload rate Mbit/s: 33.554432
Payload rate MB/s: 4.194304
Selected-packet loss percent: 5.0
Successive signed delay differences ms: [2, -1, 29]
Delay range ms: 30
```

The bit and byte rates describe the same counted payload. The different displayed
numbers do not indicate different performance: one byte is eight bits. The
packet-loss population and the four-delay sample are separate synthetic inputs;
this program does not infer that the lost packets caused the 40 ms observation.
It also does not establish that the two-second interval or 8 MiB quantity ever
occurred on a live path.

Practice: someone compares this 33.554432 Mbit/s payload rate with a 100 Mbit/s
link label and says the link lost two-thirds of its packets. The explained answer
rejects that inference. A throughput/capacity ratio is not a packet-loss ratio.
Loss requires its own sent/delivered observations and classification rule.
Return to the measurement boundary and possible limiting resources instead.

A useful report specifies source/destination context, direction, protocol/test
traffic, packet or payload size, interval, result units and method. For delay
or loss, include relevant clock/threshold assumptions. The exact detail depends
on the question; collect enough to compare like with like instead of pasting
unrelated speed-test screenshots.

### 4) **Common confusion**

High capacity can coexist with high latency. A path can carry many bits per second
while each exchange still takes a long time. Many small sequential request/response
steps can therefore feel slow despite a favorable large-transfer rate.

Low observed loss for one probe type does not prove loss-free application traffic.
Protocols, packet sizes, direction, scheduling and policy can differ. Likewise,
a reported timeout is not automatically a measured lost packet.

### 5) **Performance note**

These terms directly describe performance dimensions, but selecting a metric is
not identifying a cause. More bandwidth does not automatically remove server
processing delay, and a mean does not describe every observation. The code checks
units and summaries only; it neither loads a network nor measures latency,
throughput, variation or loss from a real endpoint.

### 6) **Mentor note**

Ask a learner to name the numerator, denominator and population behind each
number. Then ask why 30 ms range differs from the three signed variations.
A strong answer states the calculation and limits before proposing a network
change, and rejects packet-loss conclusions drawn only from a low transfer rate.
