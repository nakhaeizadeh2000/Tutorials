## 3.1. Domains hostnames DNS resolvers and records

A domain registration succeeds, but the website still fails. Another user sees
a different address for the same name. Neither observation means DNS is a single
broken directory. Registration, authoritative data, resolution caches and the
application reached through an address are separate parts of the story.

Read IP addressing first. All names and records in the worked cards below are
fictional. Names under `.test` use the testing namespace described in
[RFC 6761](https://www.rfc-editor.org/rfc/rfc6761.html#section-6.2);
no public DNS queries or account changes are needed for these exercises.

### 1) **Separate a hierarchical name from registration and hosting**

**DNS** means **Domain Name System**. It organizes names and typed information
in a distributed hierarchy. In `api.shop.example.test`, the dot-separated pieces
are **labels**. `api.shop.example.test` is a **subdomain** of
`shop.example.test`; compare whole labels, not arbitrary text suffixes.
A **top-level domain**, or **TLD**, is directly below the root in the naming
hierarchy. The name of a domain is not itself its website's content.

A **fully qualified domain name** (**FQDN**) supplies the full name in the DNS
hierarchy. The explicit form `api.shop.example.test.` ends with a dot for the
root. A short name like `api` needs context to determine the intended full name.
**Hostname** often means a domain name used for a host, but systems also use it
for a short local name. Clarify the expected form when a configuration field says
“hostname.” [RFC 9499](https://www.rfc-editor.org/rfc/rfc9499.html#section-2)
records these terminology distinctions.

A **DNS zone** is an administered portion of the namespace. Delegation can place
a child portion under different authority; one domain subtree is not necessarily
one zone. DNS server responsibilities follow those authority boundaries rather
than assuming one server knows all names.

**Registration** establishes a name registration under the relevant registry's
rules, commonly through a **registrar**. **DNS hosting** serves the name's DNS
data. **Web hosting** runs the service that produces the site's responses. One
provider may sell all three, but purchasing one does not logically supply every
other component. ICANN's [domain-name explanation](https://www.icann.org/resources/pages/about-domain-names-2018-08-30-en)
explicitly separates the registered name from a functioning website or email
service. Do not tell someone that renewing a registration necessarily repairs
an application's configuration or an unreachable host.

### 2) **Follow a naming question through resolver and authority roles**

A **resolver** obtains DNS information for a query. A **stub resolver** depends
on another resolver to complete the work. A **recursive resolver** pursues the
answer for its client, possibly answering from its cache or asking other servers.
An **authoritative DNS server** answers from its knowledge of a zone. These are
roles; the words “DNS server” alone do not identify which role a report means.
[RFC 9499's server and client terminology](https://www.rfc-editor.org/rfc/rfc9499.html#section-6)
provides the scoped definitions.

A DNS question includes the name and requested record type, with a class such
as Internet (`IN`). Asking for an IPv4 address record is a different question
from asking for mail routing information. In a simplified uncached lookup,
the client's resolver can pursue referrals from root authority toward the relevant
TLD and the target zone's authority. A **referral** identifies authority to ask
next. The browser does not have to contact every authority itself.
[RFC 1034](https://www.rfc-editor.org/rfc/rfc1034.html#section-4.3.1)
distinguishes recursive answers from referral-following behavior.

For the fictional `api.shop.example.test` question, picture the responsibility
flow as client → selected recursive resolver → relevant authorities → answer
back to the client. This is a teaching path, not a claim about a publicly delegated
`.test` hierarchy. A local testing arrangement could serve that namespace itself.

A **DNS cache** stores information for reuse. **TTL** means **time to live**;
in DNS it governs the record's cache-use interval in seconds. A cached answer
can avoid asking the authority again on every lookup. A record update is therefore
not a broadcast that instantly overwrites every existing cache. Do not promise
“the whole Internet refreshes exactly at this second” from one TTL. The relevant
record, previously cached value, resolver behavior and client context matter.

Julia Evans's original [DNS update investigation](https://jvns.ca/blog/how-updating-dns-works/)
shows why comparing an authority with a recursive answer is more informative
than treating “DNS propagation” as one unexplained timer. Its recorded observations
are historical examples, not current addresses or timing guarantees for your service.

### 3) **Read record types and a cache discrepancy as scoped evidence**

A **resource record** attaches typed data to an owner name. The following table
is a conceptual selection, not a complete DNS record inventory or configuration
file. The [original DNS record specification](https://www.rfc-editor.org/rfc/rfc1035.html#section-3.2.2)
and [IPv6 DNS extension](https://www.rfc-editor.org/rfc/rfc3596.html#section-2.1)
anchor the listed types.

| Type | What its data means | What it does not mean |
|---|---|---|
| `A` | An IPv4 address for the name | A successful connection or application response |
| `AAAA` | An IPv6 address for the name | Proof that the client's IPv6 path works |
| `CNAME` | The canonical target name for an alias | An HTTP redirect to another page |
| `NS` | A name server associated with zone authority/delegation | The address of the website itself |
| `TXT` | Text strings used by a specified consumer/protocol | A universal command or an automatic access grant |

Mail-related DNS records receive their own explanation next. Here, distinguish
the question's type before interpreting its answer. A name can have multiple
address records. An alias names another DNS name, whose relevant records still
need resolution; it is not the same thing as storing a literal IP address in
an address record.

Read this **constructed report**, using documentation-only IPv4 addresses:

```text
Question: api.shop.example.test. IN A
Authority answer: 192.0.2.20, configured TTL 300 seconds
Resolver R answer: 192.0.2.10, remaining TTL 90 seconds
Additional evidence: R cached the previous record before the authority update.
```

The explained answer is that R's older cached answer can account for this
particular difference. A configured TTL at the authority and a remaining TTL
on a cached response describe different moments in a record's use. Changing the
new record's TTL does not retroactively rewrite R's existing cached lifetime.
No record in this card proves that either address runs a working application.

Remove the additional-evidence line and the conclusion becomes weaker. Cache
state is a candidate explanation, but different authority configuration, query
sources or intended views might matter too. Record the exact question, responding
server, answer, time and relevant network context before asserting a cause.
Do not change a machine's resolver simply to make two screenshots agree; that
changes the observation context and may select different policy or internal names.

### 4) **Common confusion**

A successful DNS response is not a successful website request. It supplies naming
information; connecting to and using the selected service is further work. A
registration record likewise does not prove that an `A` or `AAAA` record exists
for every desired subdomain.

DNS TTL and an IP packet's Hop Limit are unrelated controls despite both being
associated with lifetime language. One governs cached naming information; the
other constrains packet forwarding. Preserve the protocol qualifier when using
an overloaded abbreviation.

### 5) **Performance note**

Cached naming information can avoid repeated lookup work. Shorter cache intervals
can increase the frequency of fresh queries, while longer reuse can retain older
answers for longer. This is a trade-off within a real configuration, not proof
that the shortest TTL always makes an application faster. The cards measure no
query latency, cache-hit rate or actual update convergence.

### 6) **Mentor note**

Ask the learner which actor can serve an old cached answer and which actor holds
the current zone data. Then ask whether either actor serves the website's page.
A good answer distinguishes resolver, authority and application, identifies the
record type, and lowers its certainty when the cache-history evidence is removed.
