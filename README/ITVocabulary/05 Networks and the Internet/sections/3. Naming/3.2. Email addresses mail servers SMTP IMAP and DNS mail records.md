## 3.2. Email addresses mail servers SMTP IMAP and DNS mail records

“The domain has mail records, so this message is authentic and delivered” combines
several unsupported conclusions. Routing information, transport acceptance,
mailbox access and domain validation answer different questions. A useful email
report identifies the particular address, hop and check involved.

Read the DNS lesson first. Every address and result card below is fictional under
`.test`. They are reading exercises: no messages are sent, mailboxes accessed,
credentials entered or DNS records published.

### 1) **Separate an email address from the identities used in transit**

An **email address**, such as `support@shop.example.test`, normally has a
**local part** (`support`) and a **domain part** (`shop.example.test`). The receiving
system assigns the local part's meaning. It might select a mailbox, alias or
application workflow; it need not name one human user. Do not apply one provider's
rules for ignoring dots or suffixes to every domain. The
[SMTP address model](https://www.rfc-editor.org/rfc/rfc5321.html#section-2.3.11)
reserves local-part interpretation for the relevant receiving system.

A **display name** is human-readable text associated with a mailbox in message
headers. In `Shop Support <support@shop.example.test>`, “Shop Support” is the
display name. That visible label alone proves neither domain control nor the
identity of a human author.

The message's **From header field** identifies its claimed author mailbox or
mailboxes under the [message-format specification](https://www.rfc-editor.org/rfc/rfc5322.html#section-3.6.2).
The **SMTP envelope** separately supplies sender and recipient information for
transport. Envelope `MAIL FROM` and `RCPT TO` roles are not simply copies of the
visible From and To header fields. For example, a delivery provider can use its
own return address for processing delivery failures while carrying the customer's
claimed author address in the message.

When someone says “sender,” ask whether they mean the human-readable name, message
From address, envelope sender, connecting system or signing domain. Preserving
that distinction is essential to understanding the validation mechanisms below.
A copied screenshot of a display name cannot answer all of those questions.

### 2) **Trace submission relay and mailbox access as different tasks**

**SMTP** means **Simple Mail Transfer Protocol**. It carries mail between systems.
**Submission** introduces a message into the delivery system; **relay** forwards
it toward another mail system. [RFC 6409](https://www.rfc-editor.org/rfc/rfc6409.html)
separates submission from relay so their policies can differ. A **mail server**
can perform several roles; the label alone does not reveal which role failed.

**IMAP**, the **Internet Message Access Protocol**, lets a client access and
manage messages and mailboxes on a server. The versioned baseline here is
[IMAP4rev2, RFC 9051](https://www.rfc-editor.org/rfc/rfc9051.html), which explicitly
distinguishes mailbox access from posting mail. A client might use IMAP to read
stored messages and a submission service to send new ones. Reading an old message
successfully therefore does not test the outgoing submission path. Some products
use other access interfaces; “email works” still needs a specific operation.

Here is a conceptual path, not a live protocol transcript:

```text
sender's client -> submission service -> relay/destination mail service -> mailbox
recipient's client <------------------- mailbox access through IMAP
```

Several roles may run in one service, and real paths can include more relays.
An acknowledgement at one handoff is evidence about that handoff, not proof that
the recipient read the message. Ask what “delivered” means in the product's report:
accepted for onward handling, placed in a mailbox, or some other recorded event.

DNS helps locate receiving mail systems. An **MX record**, for **mail exchange**,
names a mail server and a preference value for a domain. Lower numbers indicate
higher preference among its MX records. Its target is a name whose address must
be obtained; MX is not an instruction to open a user's IMAP mailbox. SMTP's
[mail-routing rules](https://www.rfc-editor.org/rfc/rfc5321.html#section-5)
explain that lookup and its fallback conditions.

Consider the fictional records `shop.example.test MX 10 mx1.shop.example.test`
and `shop.example.test MX 20 mx2.shop.example.test`. The first has the preferred
value; the second can provide another delivery candidate. This is a conceptual
card, not pasteable zone-file syntax or a guarantee of failover. Publishing two
names does not establish their independent operation, current reachability or
acceptance of the local part `support`. Likewise, a working website address does
not establish a working mail path for the same domain.

### 3) **Read domain validation claims without promising safe content**

**SPF**, the **Sender Policy Framework**, lets a domain publish which sending
hosts are authorized to use its domain in specified SMTP identities. The check
uses the connecting IP and the relevant envelope/HELO identity, rather than
simply validating the visible From address. Its policy is published through DNS
TXT data. [RFC 7208](https://www.rfc-editor.org/rfc/rfc7208.html)
defines that authorization check. An SPF pass alone does not establish that the
claimed author domain in the message matches the validated domain.

**DKIM**, **DomainKeys Identified Mail**, associates a signing domain with selected
message content through a cryptographic signature. A verifier uses the published
public key to check that signature. The
[DKIM specification](https://www.rfc-editor.org/rfc/rfc6376.html)
distinguishes the signer from the purported author and defines DNS TXT key lookup.
A signature provides scoped evidence under that mechanism; it neither encrypts
the message nor proves that every claimed author personally wrote it.

**DMARC** expands to **Domain-based Message Authentication, Reporting, and
Conformance**. It relates successful SPF or DKIM domain validation to the message's
**Author Domain**, the domain in its From field, through **alignment**. Strict
alignment requires identical domains; relaxed alignment uses a defined
organizational-domain relationship. A domain publishes policy preferences and
reporting requests in DNS TXT data. The **current core reference is RFC 9989
(May 2026)**, which obsoletes RFCs 7489 and 9091. See its
[overview and alignment rules](https://www.rfc-editor.org/rfc/rfc9989.html#section-4).
This initial curriculum teaches the current baseline directly.

Use this **constructed assessment card**. Assume the stated valid DMARC policy
and strict alignment; no other successful checks exist:

| Evidence | Value |
|---|---|
| Message Author Domain | `shop.example.test` |
| SPF result and authenticated domain | pass, `mailer.example.test` |
| DKIM result and signing domain | pass, `shop.example.test` |

The explained answer is that the SPF domain does not strictly align, while the
validated DKIM domain does. DMARC can pass through that aligned DKIM result;
it does not require both SPF and DKIM to pass with alignment. Change DKIM to
failure while preserving this unaligned SPF result, and this card no longer
provides an aligned successful identifier.

That conclusion concerns domain use. It does not prove a human identity, the
truth of an invoice, harmless attachments or safe links. A domain's handling
preference also does not compel every recipient system to make identical local
filtering decisions. Request the receiver's actual result rather than assuming
that merely publishing a policy makes every message safe or guarantees inbox
placement. This lesson does not configure mail authentication or prescribe a
production policy.

### 4) **Common confusion**

MX, SPF and DKIM are not three alternative ways to find the recipient's mailbox.
MX supports routing; SPF checks sending-host authorization for a domain identity;
DKIM verifies a signing-domain association. DMARC adds the author-domain alignment
and policy context. None is a user's mailbox password.

Transport protection and domain validation also differ. Signing a message is not
encrypting its contents, and protected transport alone does not validate all
claimed author information. The protected-connection lesson develops that separate
boundary later in this domain.

### 5) **Performance note**

Mail delivery can involve queues, retries and multiple handoffs. A short client
submission time is not the recipient's end-to-end delivery time. DNS lookups and
signature checks perform additional work, but their names alone provide no timing
estimate. No delivery latency, authentication throughput or inbox-placement test
was performed for these cards.

### 6) **Mentor note**

Ask a learner to identify the exact domain each check validated before announcing
“authenticated.” Then change only the DKIM domain in the card and ask whether the
strict-alignment conclusion survives. A strong answer follows the identities,
separates transport from mailbox access and refuses to infer content safety from
a domain-validation result.
