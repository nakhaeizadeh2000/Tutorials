## 5.1. Proxies reverse proxies VPNs firewalls and load balancers

An architecture labels one box “gateway,” “reverse proxy,” “firewall” and “load
balancer.” This can be a legitimate combination of roles, or vague wording hiding
important decisions. Determine which traffic it receives, what it forwards and
which rule it applies before counting boxes or promising protection.

Read interfaces, routes and socket endpoints first. The examples are constructed
path and status cards. They install no gateway, configure no VPN and change no
access rules.

### 1) **Classify a proxy by the side and protocol it serves**

A network **proxy** is an intermediary that forwards communication on behalf of
another participant. Context determines its protocol and role. For **HTTP**, the
**Hypertext Transfer Protocol** used for web request/response communication, a
**forward proxy** is typically selected by the client or its configuration to
forward requests toward destinations. A company browser configuration might
select a common proxy for certain external requests.

A **reverse proxy** receives requests as the service's outward-facing server,
then forwards them toward other servers. The client can use the service address
without choosing that intermediary as its general outgoing proxy. HTTP's
[intermediary definitions](https://www.rfc-editor.org/rfc/rfc9110.html#section-3.7)
call this role a gateway. That use of “gateway” differs from the IP next-hop
meaning in the routing lesson.

Compare these conceptual paths:

```text
Forward proxy: browser -> organization's chosen proxy -> destination service
Reverse proxy: client -> service's public-facing proxy -> internal application
```

“Reverse” does not mean that responses travel backward while ordinary proxies
only carry requests. Both arrangements can carry requests and responses. The
useful distinction concerns which side's service the intermediary represents.
A product can serve different roles for different traffic.

A **load balancer** distributes traffic among selected destinations under a
selection policy. A reverse proxy can also load-balance, but it could forward to
only one destination. A transport-level balancer and an HTTP-aware balancer
observe different information; the name alone does not specify how routing
choices are made. Here **backend** means the destination service or pool behind
the intermediary, not necessarily a separate development team or one machine.

Do not infer equal traffic from the word “balance.” Policy might use weights,
connection counts or affinity to keep related work together. Ask what is selected:
a connection, an HTTP request, or another unit? That choice changes what the
intermediary can distribute. Detailed configuration belongs to the relevant
infrastructure subject, not this vocabulary comparison.

### 2) **Separate private connectivity from traffic policy**

A **VPN** is a **virtual private network**: logical private connectivity built
over underlying networks. A **tunnel** carries communication within an enclosing
protocol or connection. Many remote-access VPNs protect tunneled traffic with
cryptography. The actual protocol and configuration determine the protection
boundary; “VPN” is not one universal implementation.

For a concrete example, [WireGuard's conceptual overview](https://www.wireguard.com/)
describes an interface carrying IP packets protected and encapsulated over UDP.
Which destinations use that interface depends on the configured network path
and peer rules. A company VPN intended for internal destinations does not,
by its name alone, route every external browsing request through that company.
Other VPN technologies have their own mechanisms; NIST's
[IPsec VPN guide overview](https://csrc.nist.gov/pubs/sp/800/77/r1/final)
provides another explicitly scoped family.

Ask where the tunnel begins and ends. Traffic leaving its far endpoint continues
under the protections and policies of the next path. A VPN connection therefore
does not establish that every later hop is protected, that the destination
application is trustworthy or that a user is anonymous to all observers.
Network access can also succeed while an application still denies access to a
particular account or record.

A **firewall** is a device or program controlling network traffic according to
policy. It can operate on a host or between networks, rather than requiring a
separate physical appliance. NIST's
[firewall-policy publication](https://csrc.nist.gov/pubs/sp/800/41/r1/final)
defines that traffic-control role. A rule permitting one address/protocol/port
combination does not necessarily permit a different combination.

Firewall policy differs from application permission. Allowing a connection to
reach the application does not decide whether the caller may export customer
data. A VPN can create a path, a firewall can constrain that path, and the
application can make its own access decision. Treat these as related questions
with separate evidence.

### 3) **Trace the failed hop and the evidence behind a health claim**

Read this **fictional design and observation card**:

```text
Client -> edge E -> either application A or application B
E receives public HTTP requests and selects A or B.
E also applies configured network traffic rules.
A periodic probe establishes a TCP connection to A and then closes it.
That probe passes; the client's export request fails.
```

Classify E and explain whether the observations contradict each other.

The explained answer identifies reverse-proxy and load-balancer roles: E presents
the service interface and selects a destination. Its traffic-rule behavior also
performs a firewall role as stated. These responsibilities could share a product;
three labels do not require three independent devices or failure boundaries.
Nothing in the card establishes a VPN or a client-selected forward proxy.

A **health check** is a defined probe or observation used to assess a condition.
Here it tests TCP connection establishment to A. It does not exercise the export
operation, B's behavior or the complete client path. HAProxy's
[health-check documentation](https://www.haproxy.com/documentation/haproxy-configuration-tutorials/reliability/health-checks/)
illustrates the distinction between connection probes and application request
checks. “Healthy” needs the check definition and result, not just a green symbol.

The passing probe and failed export can therefore coexist. Ask whether E received
the client request, which destination it selected, and what that destination
reported. Preserve the relevant times and request identity. If only B fails,
A's probe supplies little direct evidence about B. If the export requires a
resource the probe never accesses, the check's scope does not cover that dependency.
Do not disable the firewall or bypass the proxy merely to remove a visible error;
first identify the failing boundary and intended policy.

A clearer claim is: “E's configured TCP probe to A passed at the recorded time.
The export request through E failed, and its selected destination/result still
need to be correlated.” This states what is known without declaring the entire
service healthy or inventing a blocked-packet diagnosis.

### 4) **Common confusion**

A network proxy is not a JavaScript `Proxy` object. The latter intercepts object
operations within its language semantics; this lesson concerns communication
participants. Use the qualified name when discussing both in one system.

NAT, firewalling and proxying also differ. Address translation changes addressing
information, a firewall enforces traffic policy, and a proxy participates in
forwarding communication. A gateway device may combine them, but observing one
role does not establish the others.

### 5) **Performance note**

An intermediary can add processing, buffering and another path segment. It can
also reuse resources or distribute work. Net benefit depends on the actual traffic
and bottleneck; another box is neither inherently faster nor inherently slower.
Probe traffic also performs work and measures only its chosen condition. No VPN
encryption cost, proxy latency or load-distribution benchmark was performed here.

### 6) **Mentor note**

Ask the learner to label each role using a sentence from the card, then identify
which claim the probe actually supports. A strong answer distinguishes the chosen
destination, check scope and application outcome. Replace “TCP probe” with a
complete successful export and ask what additional evidence that would provide,
while retaining the limits concerning B and other traffic.
