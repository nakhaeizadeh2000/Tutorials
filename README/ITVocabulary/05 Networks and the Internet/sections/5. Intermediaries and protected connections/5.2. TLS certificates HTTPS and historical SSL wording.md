## 5.2. TLS certificates HTTPS and historical SSL wording

A service has a certificate, yet its client rejects the connection. Another
service presents HTTPS at its edge but forwards plaintext to the application.
These are understandable situations once you distinguish a certificate, peer
verification and the endpoints of a protected channel.

Read DNS, transport and reverse-proxy roles first. All certificate and path cards
below are constructed. No public site is tested, certificate issued, trust store
changed or validation bypassed.

### 1) **Identify the channel and protocol behind protected-connection language**

**TLS** means **Transport Layer Security**. It establishes a protected channel
between communicating peers. Its goals include confidentiality against network
observers, detection of tampering and authentication under the chosen mechanism.
A **TLS handshake** negotiates parameters and establishes the cryptographic
material used for the connection. [TLS 1.3, RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html#section-1)
defines these roles. Protection has endpoints; it is not a label for every stage
of a system's data lifecycle.

**HTTPS** means HTTP used with the secure-origin/channel requirements associated
with the `https` scheme. It does not replace HTTP's application meaning with an
entirely different business protocol. The scheme specifies how the client should
reach and verify that origin under HTTP's rules. The application still needs to
handle its requests correctly. QUIC integrates TLS differently from HTTP over a
TCP/TLS connection; revisit the transport owner for that distinction instead of
assuming every HTTPS exchange has the same wire arrangement.

**SSL**, **Secure Sockets Layer**, is historical protocol terminology. Products
and teams still say “SSL certificate” when they mean a certificate used for TLS.
Ask for the actual negotiated protocol and version; the label does not prove
that obsolete SSL is in use. [RFC 7568](https://www.rfc-editor.org/rfc/rfc7568.html)
prohibits SSL 3.0, and [RFC 8996](https://www.rfc-editor.org/rfc/rfc8996.html)
deprecates TLS 1.0 and 1.1. Do not enable them to follow an old screenshot.

TLS 1.3 is the modern versioned baseline here. TLS 1.2 remains covered by the
configuration requirements in [BCP 195's RFC 9325](https://www.rfc-editor.org/rfc/rfc9325.html#section-3.1.1),
which prefers negotiating TLS 1.3 when supported. A report must name the actual
version and relevant configuration rather than infer safety from “TLS enabled.”
This vocabulary lesson does not provide a cipher-suite deployment recipe.

### 2) **Separate a certificate binding from successful service identity verification**

In certificate-based TLS, a **certificate** supplies a signed binding involving
identity information and a **public key**. A public key is information used in
cryptographic verification; it is distinct from the secret private key held by
its corresponding party. The later security domain develops those mechanisms.
Merely receiving the certificate is not the whole verification process.

A **certification authority**, or **CA**, issues certificates under its validation
policy. Let's Encrypt's original [issuance explanation](https://letsencrypt.org/how-it-works/)
shows a concrete domain-control validation process followed by certificate
issuance for a requested public key. Such domain validation does not certify
that every page, invoice or download from that domain is honest.

A **certificate chain** supports validation toward a configured **trust anchor**,
the trusted starting information for the client's validation process.
[RFC 5280's path-validation model](https://www.rfc-editor.org/rfc/rfc5280.html#section-6)
checks the binding under that trust and other constraints. Different clients can
have different trusted anchors and policies. A chain can fail validation because
the necessary trust relationship or intermediate information is missing; a
certificate's presence alone does not establish acceptance by every client.

The client must also check that the presented identity is appropriate for the
service it intended to reach. **SAN**, **subject alternative name**, is the
certificate extension carrying identifiers such as DNS names and IP addresses.
The current [service-identity specification, RFC 9525](https://www.rfc-editor.org/rfc/rfc9525.html),
uses those typed identifiers and separates matching them from other certificate
checks. A DNS name and an IP address are different identifier types, not
interchangeable text fields.

Read this **fictional verification card**:

| Check context | Evidence |
|---|---|
| Intended DNS identity | `api.shop.example.test` |
| Presented DNS SAN | Only `catalog.shop.example.test` |
| Certificate chain | Passes this client's configured path checks |
| Validity period | Passes the check at the recorded time |

The explained answer is a name mismatch. The successful path/time checks do not
supply the missing `api.shop.example.test` identity. Changing the application's
expected identity to whatever the server happens to present would discard the
question verification was meant to answer. Confirm the intended endpoint and
its configured certificate/route instead. A successful TLS handshake is also
not evidence that an arbitrary caller is authorized to export data.

**Mutual TLS**, or **mTLS**, authenticates both sides under the configured TLS
mechanism, often using client and server certificates. This adds peer identity
evidence; application policy still determines what each identified peer may do.
Do not treat mTLS as a universal replacement for every application permission.

### 3) **Mark protection boundaries across an intermediary**

**TLS termination** identifies where a TLS connection ends and protected data is
decrypted for processing. A reverse proxy terminating TLS is an endpoint of that
connection. HTTP's [intermediary and secure-origin rules](https://www.rfc-editor.org/rfc/rfc9110.html#section-4.2.2)
help distinguish that outward service from subsequent connections.

Consider these **constructed arrangements**, with no other channel protection:

```text
A: client == TLS == edge proxy -- plaintext HTTP -- application
B: client == TLS == edge proxy == separate TLS == application
```

Arrangement A protects the client-to-edge channel, not the plaintext edge-to-
application channel. Arrangement B protects two distinct channels. The edge
processes plaintext between them and must establish the intended identity/trust
for its backend connection. “HTTPS outside” does not by itself establish either
backend arrangement or end-to-end secrecy from the edge.

Neither diagram says how logs, database rows or backups are protected. TLS protects
communication in its channel; storage protection and application disclosure have
other boundaries. Similarly, a valid connection to a maliciously chosen domain
can be protected while delivering harmful instructions. Authentication to the
chosen name does not establish that the user chose the right service.

Practice: “The edge has a current certificate, therefore internal traffic and
stored customer data are encrypted.” The answer rejects both inferences. Ask
which connection is negotiated and verified for the backend, then separately
ask how stored data is protected. Do not invent those mechanisms from the edge's
certificate status.

### 4) **Common confusion**

Encryption and successful identity verification are related but distinct. Skipping
verification can leave encrypted communication with the wrong peer. A warning is
therefore evidence to investigate, not a nuisance removed by declaring every
certificate acceptable.

A certificate's expiration is also not a complete description of its fitness.
Name, chain, intended use and applicable client policy matter. Conversely, a
certificate error is not automatically a DNS error: name resolution may succeed
before a later verification step fails.

### 5) **Performance note**

Handshake work, cryptographic processing and connection reuse affect cost and
latency. Their actual impact depends on the protocol version, implementation,
traffic and reuse pattern. The presence of TLS alone supplies no fixed slowdown,
and disabling verification is not a sound performance conclusion. No handshake,
certificate-validation or encrypted-throughput benchmark was performed here.

### 6) **Mentor note**

Ask the learner to circle every TLS endpoint in A and B, then identify which actor
can read application data at the edge. Follow with the mismatch card: a strong
answer states why passing chain validation does not prove the intended service
identity and proposes investigation that preserves verification.
