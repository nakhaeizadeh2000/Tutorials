## 2.1. Packets frames protocols and network layers

A network diagram labels one box “Ethernet,” another “IP” and another “application.”
These do not have to be three separate machines. They describe different
responsibilities and representations in the communication path. The same carried
data can appear inside several surrounding protocol units.

Read the network-scope lesson first. The examples below are constructed diagrams
and report cards, not real packet captures. They explain vocabulary before any
packet-analysis tool or router setup is required.

### 1) **Separate a protocol rule from the unit carrying data**

A **protocol** defines rules for communication: how participants represent,
interpret and respond to information. Its name does not describe a physical cable
or one particular software package. Two implementations can communicate when they
follow the relevant compatible rules and other required conditions hold.

A **packet** is a unit of network data, but usage varies. People may use the word
loosely for captured traffic. “IP packet” is more precise: it identifies the
protocol whose unit is being discussed. A **datagram** is also a protocol-scoped
unit; an IP datagram and a UDP datagram are different surrounding structures.
Always establish what the speaker is counting before comparing packet sizes or
loss reports. [RFC 1122's terminology](https://www.rfc-editor.org/rfc/rfc1122.html#section-1.3.3)
distinguishes IP datagrams, packets and link frames in its Internet-host model.

A **header** contains control information before the carried content. A **payload**
is the content carried by a surrounding unit. Some formats also have a **trailer**
after it. These are relative roles: content that is payload for one protocol may
include the header of another. A payload is not necessarily plain application
text, and headers are not necessarily human-readable lines.

A **frame** is a transmission unit of a link protocol. **Encapsulation** means
carrying one protocol unit inside another. For example, IPv4 datagrams can be
carried inside Ethernet frames; [RFC 894](https://www.rfc-editor.org/rfc/rfc894.html)
defines that specific arrangement. The Ethernet frame is not placed inside the
IP packet in this example. Reversing the nesting reverses the explanation of
which metadata serves which part of delivery.

```text
Ethernet frame
  Ethernet header
  IP packet
    IP header
    transport information and carried data
  Ethernet trailer
```

This is a conceptual nesting picture, not a byte-accurate frame specification.
It omits field sizes and many possible arrangements. The carried transport and
application details will receive their own lessons. You need not understand every
field to recognize the difference between a frame and its contained IP packet.

### 2) **Use layers as a map of responsibilities**

A **layer** groups communication responsibilities. The Internet-suite model in
[RFC 1122](https://www.rfc-editor.org/rfc/rfc1122.html#section-1.1.3)
describes application, transport, internet and link layers. Use this small map
to choose a question rather than memorize a count:

| Responsibility | Question to ask |
|---|---|
| Application | What does this exchange mean for the task? |
| Transport | What communication service do the applications use? |
| Internet | How are IP packets addressed and forwarded across networks? |
| Link | How is a unit carried on this connected network? |

The **OSI model**, short for **Open Systems Interconnection**, is another reference
model. Its numbered terms appear in documentation: “layer 2” commonly refers to
link behavior, “layer 3” to network/IP behavior, “layer 4” to transport behavior
and “layer 7” to application behavior in this context. Those numbers belong to
that model, not the row numbers of the table above.

Julia Evans's original [OSI and TCP/IP discussion](https://jvns.ca/blog/2021/05/11/what-s-the-osi-model-/)
explains the teaching problem with forcing every Internet mechanism into a neat
numbered slot. Ask which protocol and operation a claim means. An “application
layer” label does not imply a particular application protocol, and a “layer 7
balancer” label alone does not specify its behavior for every possible protocol.

A conceptual layer need not be a separate process, machine or software module.
Likewise, each conceptual layer need not contribute one visible header to every
packet. Diagrams that include physical transmission as a separate teaching layer
can look different from the table while discussing the same communication path.
First read the model's legend; do not declare a diagram wrong solely because its
box count differs.

### 3) **Trace an encapsulated packet across a forwarding step**

A **MAC address** is a **media access control address** used in local-link
communication such as Ethernet. The [ARP specification](https://www.rfc-editor.org/rfc/rfc826.html)
illustrates the distinction between protocol addresses and Ethernet addresses.
An IP address has a different role in addressing
across the network path. The next lesson develops IP addresses and routing; here
we compare the two scopes without doing address arithmetic.

Use this fictional two-link path with Ethernet on each link:

```text
host A -- link 1 -- router R -- link 2 -- host B
```

Assume the router forwards the packet directly toward B on link 2, with no address
translation, tunneling or fragmentation. A **hop** is one forwarding step along
the path. For the unit A sends, the relevant comparison is:

| Observation point | Local frame destination | Carried IP destination |
|---|---|---|
| A sends on link 1 | R's receiving link interface | B's IP address |
| R sends on link 2 | B's link interface | B's IP address |

The explained result is a different local delivery target at the next link while
the intended IP destination remains B under these assumptions. The router does
not simply send the original incoming frame unchanged onto the next link. Do not
claim that every byte of the carried IP packet is unchanged either: forwarding
can update protocol fields. IPv6's **Hop Limit**, for example, is decremented
when forwarding, as specified in [RFC 8200 section 3](https://www.rfc-editor.org/rfc/rfc8200.html#section-3).
This prevents an unqualified “identical packet at every point” inference.

Practice: a report says “the frame destination was the router, so the request
must be addressed to the router's application.” Explain the mistake. The answer
separates local frame delivery from the carried packet's destination and from
the eventual application operation. A local next step is not necessarily the
final intended recipient. The card illustrates those responsibilities; it does
not establish an actual route, traffic policy or successful application response.

### 4) **Common confusion**

A packet is not inherently one complete file or one complete request. Application
data can span units, and protocol boundaries need not match the user's conceptual
record boundaries. Before saying “one packet was lost,” establish the protocol,
observation point and measurement method.

“Encapsulation” here also differs from a programming-language access boundary.
Both involve surrounding something, but private fields and Ethernet payloads
have different mechanisms and guarantees. Use the qualified term when context
could support either meaning.

### 5) **Performance note**

Protocol metadata consumes space alongside carried data, so payload bytes and
all transmitted bytes are different quantities. The exact overhead depends on
the actual protocols and representation; this simplified diagram provides no
fixed percentage. Layer count alone also does not establish software overhead
or throughput. No packet-rate, latency or processing-cost benchmark is performed.

### 6) **Mentor note**

Ask the learner to draw a boundary around the frame, then around the IP packet
inside it. Change the local link in the card and ask which addressing question
changes. A strong answer names the model and protocol, preserves the stated
assumptions and avoids turning layer shorthand into a universal implementation.
