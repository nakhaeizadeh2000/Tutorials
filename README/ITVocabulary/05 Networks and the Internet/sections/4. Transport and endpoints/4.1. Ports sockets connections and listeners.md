## 4.1. Ports sockets connections and listeners

“The server is on port 8000” leaves out the address, transport protocol and
network context. “It is listening” also differs from “this client connected and
completed its task.” Naming those boundaries makes connection reports useful.

Read IP addressing and processes first. The complete example uses only local
IPv4 loopback. It exposes no listener on external interfaces and contacts no
remote machine. TCP's delivery guarantees are developed in the next lesson.

### 1) **Identify an endpoint with its protocol address and port context**

A transport **port** is a numeric identifier used by a protocol such as TCP or
UDP to distinguish communication endpoints. It is not a physical connector.
An IP address alone does not identify the desired application interaction:
`127.0.0.1` with TCP port 8000 and the same address with UDP port 8000 describe
different protocol endpoints. Linux's
[IP socket address reference](https://man7.org/linux/man-pages/man7/ip.7.html)
explains the address/port combination and that ports belong to protocols above IP.

A **socket** is a communication endpoint exposed to a program through an OS API.
The program uses it to send, receive and manage communication. A **socket address**
has a format determined by its **address family**. An IPv4 socket commonly uses
an IP address and port; that is not the only possible socket family. **Unix domain
sockets** support local interprocess communication, with local names rather than
an Internet address/port pair. See the
[Linux local-socket reference](https://man7.org/linux/man-pages/man7/unix.7.html).
A socket is therefore not simply a permanent synonym for “IP plus port.”

For TCP, a **connection** relates local and remote endpoints. The local and remote
addresses and ports distinguish connections within the relevant network context.
A server can have several connections targeting its same listening address and
port. It does not need a new public server port for every accepted client.
A client commonly receives a temporary **ephemeral port** selected by the OS;
its value is not a durable user or process identity.

A **listener** is a socket prepared to accept incoming connection attempts.
**Binding** associates a socket with a local address; **accepting** obtains a
socket for an incoming connection. The
[Linux socket overview](https://man7.org/linux/man-pages/man7/socket.7.html)
distinguishes `bind`, `listen`, `connect` and `accept`. These are operation roles,
not four different network services.

### 2) **Observe a listener and its accepted connection separately**

Save `local_connection.py` and run `python3 local_connection.py`. Tested:
**CPython 3.14.4 on Linux x86_64**, standard library only. The example creates one
listener and one client in the same process. A worker thread accepts and sends a
fixed short greeting while the main thread receives it.

```python
import socket
from threading import Thread

observed = {}
with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as listener:
    listener.settimeout(3)
    listener.bind(("127.0.0.1", 0))
    listener.listen(1)
    address = listener.getsockname()

    def serve_once():
        connection, _ = listener.accept()
        with connection:
            connection.settimeout(3)
            observed["same_port"] = connection.getsockname()[1] == address[1]
            observed["different_socket"] = connection is not listener
            connection.sendall(b"ready\n")

    worker = Thread(target=serve_once)
    worker.start()
    with socket.create_connection(address, timeout=3) as client:
        with client.makefile("rb") as incoming:
            greeting = incoming.readline(32)
    worker.join(timeout=4)
    if worker.is_alive():
        raise RuntimeError("Local worker did not finish")
    assert greeting == b"ready\n"
    print("OS selected a port:", address[1] > 0)
    print("Accepted socket keeps server port:", observed["same_port"])
    print("Accepted socket differs from listener:", observed["different_socket"])
    print("Greeting:", greeting.decode("ascii").strip())
```

Observed output:

```text
OS selected a port: True
Accepted socket keeps server port: True
Accepted socket differs from listener: True
Greeting: ready
```

`AF_INET` selects IPv4; `SOCK_STREAM` selects the stream socket used for TCP here.
Binding loopback port `0` asks the OS to choose an available local port. That
request is different from choosing a fixed service port of zero. `getsockname`
reads the selected address, and the client connects to it. The assertion checks
the actual greeting rather than inferring success from the ability to connect.

`accept` returns a new socket for the connection. The original listener and this
socket differ, although the accepted socket uses the server's same local port.
MIT's original [socket teaching material](https://web.mit.edu/6.031/www/sp21/classes/24-sockets-networking/)
explains why the physical-plug analogy breaks at this point: accepting a connection
does not consume the listener and turn it into that one connected socket.
This example accepts only once; it is not a production multi-client server.

The fixed greeting ends with a newline. `makefile("rb")` exposes a binary reader,
and `readline(32)` reads through the line boundary with a size bound. We do not
assume that one send operation corresponds to one receive operation. Python's
[socket reference](https://docs.python.org/3.14/library/socket.html)
documents these operations. Timeouts make failures visible; after a timeout this
example exits and discards the reader rather than reusing its potentially
inconsistent buffer. Context managers close the reader and socket resources.

If local socket creation is denied by your execution environment, record that
limitation instead of claiming the expected exchange occurred. This run tests
neither external routing nor another machine's access policy.

### 3) **Read listening and connection claims without inferring service health**

The local binding matters. Binding specifically to loopback differs from a
**wildcard bind**, which accepts any local address in the specified address
family under the platform's rules. On Linux IPv4, `0.0.0.0` has that wildcard
meaning for binding. It is not a literal public destination that a remote client
can use to identify your machine. Neither binding choice alone describes every
firewall or application-access decision.

Practice with this fictional report:

```text
Service report: listening on IPv4 127.0.0.1:8000
Client: a different physical machine
Claim: remote access must work because port 8000 is listening
```

The explained answer identifies a scope mismatch. This listener is bound to the
server's loopback context; a different machine's `127.0.0.1` refers to itself.
The report supplies no externally reachable listener address. It does not justify
blindly widening the bind: first establish whether remote access is intended and
which interface and policy should permit it.

Now suppose a client does connect. That establishes transport connection success
for that attempt, not a successful export, valid authentication or healthy database.
The tiny greeting assertion tests one additional application outcome; a production
health claim would need its own defined task and evidence. A port convention
can suggest a protocol but does not prove which program is actually serving it.

### 4) **Common confusion**

A socket listener is not a JavaScript event listener, even though both wait for
something to happen. This page owns OS communication endpoints; language callback
registration belongs to its language/platform owner.

A listening socket also differs from an accepted connection. Closing a connection
need not mean the listener stopped accepting other clients. Conversely, the
presence of a listener does not prove that the application will process every
accepted connection successfully.

### 5) **Performance note**

Each connection can require OS and application resources. A listening port count
therefore does not describe the number of live connections or their memory cost.
The loopback greeting is a correctness observation with bounded data; its timeout
values are failure bounds, not measured latency or capacity targets. No connection-
rate, concurrency or external-network benchmark was performed.

### 6) **Mentor note**

Ask the learner to draw the listener, client socket and accepted socket separately,
then label which two exchange the greeting. A strong answer preserves the listener's
local port, identifies both connection endpoints and explains why loopback success
cannot establish access from another machine.
