## 4.2. TCP UDP QUIC and protocol guarantees

“We use a reliable transport, therefore the order was saved exactly once” crosses
an evidence boundary. Transport protocols can provide valuable delivery properties
without knowing what an order is. Name the unit, ordering scope and completion
condition before repeating a guarantee.

Read packets and socket endpoints first. This lesson uses constructed traces and
comparison exercises, not packet-loss experiments or protocol benchmarks.

### 1) **Read TCP reliability at the byte-stream boundary**

**TCP**, the **Transmission Control Protocol**, provides a reliable, ordered
**byte stream** between its endpoints. The stream carries bytes without preserving
the application's write-call or message boundaries. Loss detection and
**retransmission**, sending replacement data after inferred loss, contribute to
its reliability. See [RFC 9293's key concepts](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2).
TCP can also fail when the communication cannot continue; “reliable” is not a
promise of eventual delivery through every permanent outage.

For a fictional sender writing `AB` and then `CD`, the receiver's byte stream
contains `ABCD` when those bytes are delivered. Reads could return `A` then `BCD`,
`AB` then `CD`, or all four bytes together. Those are different read boundaries,
not reordered application bytes. The application needs its own framing rule,
such as newline-delimited records or explicit lengths, to recover messages.
The prior loopback lesson used a bounded line reader for that reason.

Do not equate TCP acknowledgement with application processing. A receiving
transport can acknowledge bytes before a program validates or stores their
meaning. TCP itself also does not supply message-content encryption or validate
every claimed application identity. Those properties require the appropriate
additional mechanisms and checks.

### 2) **Interpret UDP without assuming every application above it is unreliable**

**UDP**, the **User Datagram Protocol**, carries separate datagrams. It does not
itself provide reliable delivery, ordered delivery or duplicate suppression.
[RFC 768](https://www.rfc-editor.org/rfc/rfc768.html)
defines its basic service. If an application sends updates numbered 10 and 11,
UDP alone does not establish that both arrive, arrive once, or arrive in that
order. An application can use sequence numbers and policy to reject stale data,
but the policy is additional behavior, not a new guarantee hidden in UDP's name.

Choosing datagrams can fit information whose usefulness expires, such as a
frequently replaced position update. That does not mean every application using
UDP should ignore losses or that a late transaction can safely be discarded.
Specify which data can be lost, how the application notices and what outcome is
required. A file-transfer design over UDP may add reliability above it.

UDP also provides no inherent congestion control. Sending without regard to
available path capacity can harm the application and other traffic. The
[UDP usage guidelines](https://www.rfc-editor.org/rfc/rfc8085.html#section-3.1)
require appropriate behavior above UDP. “No TCP handshake” is not permission to
send unlimited traffic, nor evidence that the whole application has no handshake.

### 3) **Locate QUIC streams and datagrams above UDP**

**QUIC** is a transport protocol carried over UDP. Its own mechanisms add a
connection, reliable streams and congestion control; UDP underneath does not
remove those properties. A QUIC **stream** carries ordered bytes, and
**multiplexing** allows multiple logical streams in one connection. Ordering is
within each stream, not one promised total application-event order across all
streams. [RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html)
defines QUIC version 1; [RFC 9369](https://www.rfc-editor.org/rfc/rfc9369.html)
also standardizes QUIC version 2. A product's supported version and features
still need verification.

QUIC integrates TLS cryptographic setup and packet protection, described in
[RFC 9001](https://www.rfc-editor.org/rfc/rfc9001.html).
Recognize that protected transport is built into this protocol design; the next
protected-connection lesson explains certificates and identity checks. Protection
does not make every application operation valid or authorize every caller.

**Head-of-line blocking** describes later work waiting behind earlier missing
or unfinished work. QUIC avoids transport ordering blockage across unrelated
streams when only one stream's data is lost. It does not remove every wait:
affected data in that stream still needs recovery, and streams still share
connection resources. If a lost packet contains data from several streams,
several can be affected. Do not turn “independent streams” into “loss has no cost.”

The standardized [QUIC DATAGRAM extension](https://www.rfc-editor.org/rfc/rfc9221.html)
adds application datagrams without requiring retransmission. Support must be
advertised through the extension's transport parameter before such datagrams
are sent. This is separate from reliable stream data, not a change making every
QUIC stream unreliable. Ask which service and extension a claim actually uses.

### 4) **Challenge a guarantee using a concrete failure timeline**

Read this **fictional timeline**, which separates transport and application events:

| Step | Recorded event |
|---|---|
| 1 | Client sends bytes representing “create order.” |
| 2 | Receiving transport acknowledges those bytes. |
| 3 | Server application fails before storing the order. |
| 4 | Client has no application completion response. |

The answer to “was the order saved?” is **no in this stated card**, because step 3
explicitly establishes the failure before storage. The transport acknowledgement
does not override that evidence. In a real report lacking step 3, the storage
outcome would be unknown; an acknowledgement alone would not settle it either.

Now change step 3: the order is stored, but the response never reaches the client.
Repeating the operation could create a second order unless the application
contract handles repetition. The transport name does not define that contract.
Later API and distributed-systems vocabulary develops safe repetition and effect
guarantees. Here the useful action is to ask what the acknowledgement means and
how the application identifies a completed or repeated operation.

Use this compact comparison to review a claim:

| Service | Unit and ordering scope | Additional question |
|---|---|---|
| TCP | Ordered byte stream | How are application records delimited and completed? |
| UDP | Separate datagrams, without its own delivery/order guarantee | What policy handles loss, duplicates, order and congestion? |
| QUIC streams | Reliable ordered bytes within each stream | Which streams and application dependencies are involved? |
| QUIC DATAGRAM extension | Datagrams without required retransmission | Was support negotiated, and which losses are acceptable? |

This is a guide to questions, not a protocol-selection benchmark. A design should
choose behavior appropriate to its requirements, deployment constraints and
supported implementations, then verify the resulting application contract.

### 5) **Common confusion**

Reliable transport does not mean exactly one business effect. Transport sequence
numbers identify transport data, not an application's durable order identity.
Likewise, QUIC running over UDP does not mean it inherits only UDP's bare service:
encapsulation permits a higher protocol to add mechanisms.

“Ordered” also needs a scope. Bytes within one stream, datagrams observed on a
path, and user-visible events across independent streams are different orders.
A log sorted by display time does not create a protocol guarantee.

### 6) **Performance note**

Recovery, handshakes, buffering and congestion response affect delay and resource
use. Independent streams can avoid one kind of waiting while still sharing capacity.
Neither “UDP is faster” nor “QUIC always wins” follows from the protocol labels.
State workload, network conditions, implementation and measured outcome before
comparing performance. No loss simulation, handshake timing or throughput run is
claimed here.

### 7) **Mentor note**

Ask the learner to label the unit acknowledged at step 2 and the business state
missing at step 4. Then remove the application-failure evidence and ask how the
answer changes. A strong answer distinguishes known failure from unknown outcome,
keeps ordering scoped and asks for an application-level contract instead of
promoting a transport property into a business promise.
