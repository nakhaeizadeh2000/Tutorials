## 7.1. Describe a name connection or timeout failure

“The network is down” might mean that a name did not resolve, a connection was
refused, a certificate did not match or an application did not respond before a
deadline. These require different next questions. A useful report says what was
attempted and which outcome was actually observed.

This lesson synthesizes the network domain. The cards use fictional `.test` names
and documentation addresses. They are static exercises, not logs from executed
requests or instructions to probe a real system.

### 1) **Record the attempted path and the last established outcome**

Start with the user's task: for example, requesting an export through a service
name. Then identify the relevant context: client/process, time, network view,
resolver, selected address, transport and port. Include a proxy or VPN only if
evidence shows it participates. A diagram of intended connectivity does not
prove the request followed that path.

For a **new TCP/TLS connection** in these cards, distinguish the following checks:

| Observation | What it can establish for that attempt |
|---|---|
| DNS answer for the stated question | Naming information from the queried context |
| Successful TCP connection | Connection establishment to the selected endpoint |
| Successful TLS/service verification | The required protected-channel checks passed |
| Application completion response | The stated application reported its defined outcome |

This is a diagnostic sequence for the chosen scenario, not a universal packet
trace. A reused connection, local name override, proxy or QUIC session can change
which steps happen locally and when. Record the actual arrangement. Even the last
row needs a response contract: receiving any text is not proof of a completed
export or durable business effect.

Identify the **last established outcome**, not merely the last line printed. A
client may log an intended destination before any connection exists. A server's
“request received” message may precede a later failed operation. Correlate records
for the same attempt and state what each observer can know.

### 2) **Compare four failure cards without inventing a root cause**

Assume these are **four independent attempts**, each on a new connection. The
card records no aliases in the DNS name-error case. Later stages are not attempted
unless stated; no fallback destination exists.

| Card | Recorded evidence |
|---|---|
| A | Query `api.shop.example.test IN A` to resolver R returns `NXDOMAIN`; no connection attempt. |
| B | DNS returns `192.0.2.20`; TCP connection to that address on port 443 reports refusal. |
| C | TCP connects; TLS path/time checks pass; intended `api.shop.example.test` does not match the certificate's sole `catalog.shop.example.test` DNS SAN; client stops. |
| D | TCP and required TLS checks pass; application request is sent; no completion response is observed before its configured 2-second deadline. |

Before reading the answer, write each card's failed observation boundary and a
question that could distinguish explanations.

**A is a naming result.** `NXDOMAIN` means a DNS name error, not a generic timeout.
Under this no-alias card, the response says the queried name does not exist in
that naming context. [RFC 2308](https://www.rfc-editor.org/rfc/rfc2308.html#section-2.1)
distinguishes name errors from a response lacking data of the requested type.
Ask whether the intended name, resolver/view and authoritative configuration agree.
Do not conclude that the organization's entire registered domain is unregistered
or that its application process stopped. An old negative cache entry can also
matter; investigate the actual answer rather than repeatedly changing the name.

**B is a connection failure.** The address was obtained, but this connection was
not established. Linux's [connect reference](https://man7.org/linux/man-pages/man2/connect.2.html)
describes `ECONNREFUSED` for a stream attempt finding no listener at the remote
address. In a real multi-component path, identify the source of the refusal and
whether the selected endpoint is the intended one. Request listener/bind/policy
evidence for that context; the card does not establish a bad password or failed
TLS name check. It also does not prove that every service on the machine is down.

**C is service-identity verification failure.** TCP establishment and valid
path/time checks do not make the different DNS name match. Confirm which
certificate and route the intended service should present. Disabling verification
would change the security requirement rather than establish that the service
met it. This card states the client stopped before the application request.

**D is a deadline observation.** A **timeout** occurs when the required completion
was not observed by a specified deadline. Here it is an application-response
wait, not the earlier TCP connection or DNS lookup. Request evidence showing
whether the relevant server received, processed and completed the operation.
The response might be delayed, absent or lost; the operation's effect remains
unknown in this card. Neither the word “timeout” nor the two-second value proves
packet loss or identifies a failed component.

Changing D to “TCP connect timed out before the application request was sent”
changes the boundary and next questions. Ask which operation the timer covers,
when it starts and what counts as completion. A single generic timeout message
cannot substitute for that contract.

### 3) **Write a useful handoff and justify the next observation**

For D, a weak handoff says: “DNS is fine, network is slow, retry it and increase
the timeout.” This invents a cause from a missing response. It can also repeat
an effect if the server already completed the request.

A stronger answer is: “For the recorded attempt, this client resolved the service,
established TCP and passed the required TLS checks. It sent the application
request but observed no completion response before the configured 2-second
response deadline. Server receipt and completion remain unknown. Correlate this
attempt with the relevant edge and application records before deciding whether
repetition or a deadline change is appropriate.”

A **request identifier** is a value used to associate records for an attempt or
operation. Its format and propagation depend on the system; do not assume every
hop recorded it correctly. If it is available, preserve it with relevant times
and context. Avoid dumping passwords, tokens or entire private payloads into the
report. The earlier configuration lesson explains redacted evidence collection.

Choose the next observation by its ability to distinguish explanations. For D,
a correlated server-completion record changes what can be inferred about a missing
client response. For C, packet-throughput numbers are less directly useful than
the actual expected/presented identities. For A, probing the application's port
without a confirmed intended address answers a different question.

Interview practice: “What does a successful ping prove about an HTTPS export?”
A sound answer asks what that ping measured and identifies the additional
connection, identity and application checks. A reply to one kind of probe is not
a successful export. No ping run is part of this exercise.

### 4) **Common confusion**

A symptom category is not a root cause. A timeout classifies an observation;
a particular firewall rule, stalled handler or failed dependency would be an
explanation requiring more evidence. One failing destination also does not show
that every external or internal destination fails.

“No error in this log” is not proof that the attempt succeeded. The observer might
not cover the failing stage, the records might concern another request, or the
required outcome might never have been recorded. State the evidence gap.

### 5) **Performance note**

Increasing a deadline permits longer waiting; it does not make the operation faster
or add network capacity. A too-short deadline can reject useful work, while a long
wait can hold resources. Select it against the operation's requirements and actual
measurements. These cards provide no timing distribution or tuning recommendation.

### 6) **Mentor note**

Give the learner only the short word “timeout,” then gradually reveal D's preceding
steps. A strong explanation becomes more specific as evidence arrives without
claiming a cause prematurely. Require a next question and predicted discriminating
result, then ask how the answer changes if the connection was reused through a
proxy rather than newly established directly.
