## 6.1. Boundaries of testing and debugging vocabulary

This domain teaches how to read quality evidence and communicate a failure. It
also includes small local observations so the vocabulary has an observable meaning.
It does not turn a vocabulary learner into the designer of a complete application
test strategy. Use the following routes to deepen the specific question you need
to answer.

### 1) **Keep each quality question with its conceptual owner**

| Question | Canonical explanation in this domain | What the explanation does not establish by itself |
|---|---|---|
| Was this an exception, a defect or a regression? | [Errors and observed failures](<../1. Faults and evidence/1.1. Errors defects bugs failures exceptions and regressions.md>) | A unique cause, or earlier working behavior without evidence |
| What requirement or user purpose was evaluated? | [Verification and acceptance](<../1. Faults and evidence/1.2. Verification validation QA QC and acceptance.md>) | Acceptance of every user task or department approval |
| Which real parts interacted? | [Test scope and boundaries](<../2. Test scope and intent/2.1. Unit component integration system end-to-end and contract tests.md>) | Provider or workflow behavior excluded by substitutes |
| Why was the case selected and how was it investigated? | [Test objectives and exploration](<../2. Test scope and intent/2.2. Functional non-functional regression smoke and exploratory testing.md>) | An actual run merely because a plan exists |
| What condition did the arrangement check? | [Assertions and doubles](<../3. Test arrangements and limits/3.1. Assertions fixtures test doubles mocks stubs spies and fakes.md>) | Real delivery from a recorded local call |
| What does a percentage or passing retry mean? | [Coverage and unreliable signals](<../3. Test arrangements and limits/3.2. Coverage flaky tests false positives and false negatives.md>) | Correctness, a fixed intermittent cause or universal coverage of requirements |
| What observation distinguishes explanations? | [Reproduction and debugging](<../4. Investigation language/4.1. Reproduction hypotheses stack traces breakpoints and root causes.md>) | The complete history or organizational cause from one traceback |
| Can someone attempt the same failure? | [Issue reporting](<../5. Applied reporting and review/5.1. Write a reproducible issue with expected and actual behavior.md>) | A verified reduction that nobody actually tried |
| Does the candidate meet the claimed quality criteria? | [Candidate quality review](<../5. Applied reporting and review/5.2. Challenge a tested-and-production-ready claim.md>) | The whole release decision from a bounded packet |

Return to these owners for full explanations. In another domain, a short reminder
and a precise link are usually enough; add the new security, delivery or operational
application rather than repeating this entire vocabulary.

### 2) **Distinguish language mechanics from full testing and operational practice**

JavaScript's [error and debugging domain](<../../../../JavaScript/15 Error Handling and Debugging/README.md>)
owns language-specific error propagation and host debugging tools. Its
[testing and tooling domain](<../../../../JavaScript/20 Testing and Tooling Essentials/README.md>)
owns language-specific assertion and runner examples. Consult version-matched
primary documentation for the actual runtime and tool you execute. A vocabulary
page naming a breakpoint or mock does not replace that setup or verify a tool's
current flags.

TypeScript's [Testing Types domain](<../../../../TypeScript/17 Testing Types/README.md>)
owns compile-time probes, typed doubles and public declaration-consumer checks.
The distinction matters: checking a declared return type does not execute the
function, and executing a correct value case does not establish that a public
type stayed precise. Its
[boundary lesson](<../../../../TypeScript/17 Testing Types/sections/7. Overlaps to avoid/7.1. Boundaries what is covered elsewhere.md>)
provides the detailed route between those contracts. Do not relabel a compiler
result as a runtime integration test.

The root curriculum's broader Testing track is still planned. It will own full
automation methodology and application testing with the user's chosen Playwright
vehicle. This domain does not impose a second framework choice, a test-level quota
or a complete hosted pipeline. Its Python examples are self-contained vocabulary
observations, not a replacement backend framework or Testing curriculum.

Application context continues to use NestJS with the Fastify adapter. A real
adapter, database or message-provider check needs the relevant implementation
setup and evidence. For a missing import or permission failure, the
[environment diagnosis owner](<../../../04 Operating Systems Files and Environments/sections/5. Applied diagnosis/5.1. Explain works-on-my-machine and resource failures.md>)
helps compare execution conditions. For compatibility and candidate identity, use
[release evidence reading](<../../../11 Version Control Releases and Dependencies/sections/5. Applied change reading/5.1. Read a pull request release note and dependency update.md>).
Detailed security assessment, load measurement, incident response and delivery
operations require their own subject expertise; the later approved vocabulary
domains introduce those words without making them unexplained prerequisites here.

### 3) **Route a mixed claim without discarding useful evidence**

Consider this **constructed handoff**, not a tool run:

> “The TypeScript probe passes, the browser check sees total 2 from a prepared
> response, and the notification spy recorded one call. Therefore the production
> report and delivered notification are tested. The real report sometimes times
> out, but its stack mentions the HTTP client, so increase that timeout.”

A supported reply separates the responsibilities:

> The type probe supports its selected static contract. The browser result checks
> client behavior against prepared data. The spy supports one local interaction.
> None supplies the missing real report-to-notification delivery evidence. Keep
> those results, identify the real path and candidate to evaluate, and record the
> timeout's conditions, expected completion and observations before choosing a
> correction. A frame mentioning the HTTP client locates part of the observed path;
> it does not establish that the configured deadline is the underlying defect.

For the next investigation, ask whether the report request reached the service,
whether its work completed and what the client actually waited for. The
[timeout and retry owner](<../../../10 Concurrency Messaging and Distributed Systems/sections/4. Failure and flow control/4.1. Timeouts retries backoff jitter and circuit breakers.md>)
explains the unknown-outcome and repeated-effect questions; language stacks do
not settle them. Do not send a beginner into an unbuilt operations course just to
explain why a missing response is not proof of no effect.

Now add evidence that one identified report was persisted and one identified
notification reached the intended synthetic recipient through the real path on
the candidate. This strengthens that stated end-to-end observation. It does not
explain the intermittent timeout or establish all inputs, failure recovery and
capacity. A good handoff updates the particular supported claim while keeping
those separate questions visible.

### 4) **Common confusion**

A domain boundary is an ownership and depth decision, not a prohibition on useful
small examples. The local debugger example makes frames and hypotheses concrete;
it does not claim to implement a debugging platform. Similarly, a conceptual
contract-testing comparison can be useful before someone installs a tool.

Evidence boundaries also survive a change of language. A type-compatible fake,
a Python recording object and an intercepted browser response each need a stated
behavioral scope. Their names and implementation languages do not turn substitutions
into observations of a real external effect.

### 5) **Performance note**

This routing page has no direct runtime performance effect. Useful vocabulary can
help select the right measurement, but it cannot supply one. A quicker static gate,
a passing substitute test or a changed timeout is not a measured improvement to
the real service. No benchmark, load test or incident timing was performed here.

### 6) **Mentor note**

Have the learner assign each handoff clause to a contract and owner before choosing
a tool. Add the recipient evidence and ask exactly which conclusion changes.
Reward preservation of the valid local and static results alongside the missing
real-boundary questions. Choosing the next subject from a demonstrated gap is
more useful than memorizing another list of test acronyms.
