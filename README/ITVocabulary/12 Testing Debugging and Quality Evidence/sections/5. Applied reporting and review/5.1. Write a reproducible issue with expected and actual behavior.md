## 5.1. Write a reproducible issue with expected and actual behavior

“CSV export is broken; fix the cache” supplies a symptom category and a guessed
solution, but no way to attempt the same failure. A useful issue preserves what
was observed and gives the next investigator enough context to compare it with
the relevant requirement. You do not need to discover the cause before reporting.

### 1) **Turn a complaint into a reproducible comparison**

An **issue report** records a problem or work item in a form that others can
investigate and track. An issue may concern a defect, a question or a requested
feature; its presence in a tracker does not establish a diagnosis. For a suspected
bug, identify the action, starting state, expected behavior, actual behavior and
relevant environment. Link the expectation to an agreed rule or explain why you
believe it applies. “I prefer a different layout” and “the agreed keyboard path
cannot reach Submit” are different claims requiring different evaluation.

A useful title describes the observed trigger and outcome. “Export includes
pending seats while the Approved filter is selected” is more informative than
“Export broken” or “Cache invalidation defect.” The first names the reproducible
behavior without selecting an unverified cause. The
[Mozilla bug-writing guide](https://bugzilla.mozilla.org/page.cgi?id=bug-writing.html)
uses precise steps, distinct expected and actual results, and separation of facts
from speculation. Its tracker fields, title-length suggestions and platform
procedures are local conventions, not requirements for every project.

Use the relevant environment details rather than dumping everything available.
A build identifier distinguishes application revisions; a browser/runtime version,
operating system, configuration or dependency can distinguish execution conditions.
Include an initial dataset or state when the result depends on it. Replacing
customer content with synthetic data is helpful only if the replacement still
preserves the behavior; say whether you verified that reduction.

### 2) **Write a complete report from a bounded evidence packet**

The following is a **fictional evidence packet and writing exercise**, not a
reproduction executed against an application for this tutorial:

| Available evidence | Detail |
|---|---|
| Agreed rule R-14 | The CSV includes only rows matching the selected status filter |
| Application | Browser report client, build `demo-42`; service build `api-18` |
| Recorded environment | Chrome 151 on a Linux desktop; no other client tested |
| Starting state | Fresh synthetic report `example-a`; exactly two rows: approved with 2 seats, pending with 3 seats |
| Action | Select Approved, then choose Download CSV after the table shows the filtered result |
| Observations | Table shows the approved row and total 2; downloaded CSV includes both rows and total 5 |
| Repeat attempts | Three fresh-report attempts produced the same mismatch |
| Diagnosis evidence | No request/response capture, source inspection or cache investigation |
| Impact and workaround | CSV disagrees with the selected view; manually removing the pending row gives the intended data in this tiny example |

A report derived from that packet can read:

> **Title:** Download CSV includes pending row with Approved filter selected
>
> **Context:** Client `demo-42`, service `api-18`, Chrome 151 on a Linux desktop.
> This was observed with synthetic data; other clients and builds are untested.
>
> **Setup:** Create a fresh report containing exactly two rows: `row-a`, status
> approved, seats 2; `row-b`, status pending, seats 3. Begin with both rows visible.
>
> **Steps:** Select Approved. Confirm that the table displays only `row-a` and
> total 2. Choose Download CSV. Open the downloaded file and inspect its rows
> and total.
>
> **Expected:** Under agreed rule R-14, the CSV contains `row-a` only and total 2.
>
> **Actual:** The table remains filtered to `row-a`, but the CSV contains `row-a`
> and `row-b` with total 5. The mismatch occurred in three of three fresh-report
> attempts in the stated environment.
>
> **Impact:** Someone using the file receives data outside the chosen filter.
> Manually removing `row-b` works for this two-row example; that does not establish
> a safe general workaround for larger reports or every export format.
>
> **Evidence and uncertainty:** The synthetic row contents and CSV observation
> are recorded above. There is no request capture or source inspection, and the
> cause and responsible component remain unconfirmed. The original cache theory
> is a hypothesis. Next, compare the selected filter, outgoing export request and
> returned content to narrow the failed boundary.

Every fact in the report comes from the packet or gives the synthetic rows names
for readable steps. The title does not claim that the display filter failed: the
display is correct in the packet. Selecting Approved before downloading is a
necessary condition; omitting it would change the question. “Click export” alone
would not identify whether to export the whole report or the filtered view.

The report also distinguishes **frequency** from prevalence. Three of three attempts
in this setup do not show that every user, browser or report is affected. Likewise,
there is no earlier working-build observation, so do not call this a newly introduced
regression merely because someone noticed it today.

### 3) **Refine the report when evidence or expectations change**

Now remove R-14 as a variation. The mismatch still deserves investigation, but the
report can no longer establish a violation of that agreed export rule. State the
observed difference and ask whether export is intended to use the current filter.
Do not silently convert a product-design question into a confirmed implementation
defect. Keep the distinction between the requested outcome and known requirements.

Next, change the attempt record to “one mismatch in five attempts.” Preserve the
unsuccessful reproduction attempts too, including relevant changed conditions.
Do not write “always.” Compare whether selection, data readiness or initial state
differs; those are proposed investigations, not established causes. The preceding
debugging lesson owns the full hypothesis-and-experiment reasoning.

An attachment should answer a question. Exact error text, a small synthetic input,
a relevant trace excerpt or the mismatched file can be useful. A screenshot can
show the selected filter and display; it may not show the CSV contents or service
result. A request trace may contain credentials, cookies or personal data. Review
what you share, remove sensitive values, and identify meaningful omissions without
altering the structure needed to explain the failure. Link the existing secret
and redaction owner for the detailed distinction.

When another person tries the steps, record their build, conditions and outcome.
If they cannot reproduce, compare that evidence with the original setup. Julia
Evans's [useful-question guidance](https://jvns.ca/blog/2021/10/21/how-to-get-useful-answers-to-your-questions/)
supports giving current understanding and the missing fact. Help the recipient
identify the difference rather than demanding that a beginner prove the cause.
For separate symptoms, use the project's reporting convention and cross-link
related reports; do not assume they share a cause because they appear together.

Practice: rewrite “Backend cache broken on all devices after the last release.”
A supported answer is: “In the recorded Chrome/Linux setup on `demo-42`/`api-18`,
CSV output includes the pending row despite Approved selection, in three fresh
attempts. Other devices, earlier releases and the cause are untested.” The
improvement is accurate scope and a concrete comparison, not extra jargon.

### 4) **Common confusion**

“Expected” is not synonymous with “the result I wanted.” Explain the rule, user need
or documentation behind it and preserve uncertainty where that reference is missing.
A report can still be valuable before the team decides whether it is a bug.

A minimal reproduction is also not permission to remove essential state. If the
mismatch occurs only after editing a saved report, replacing it with a new report
may lose the failure. Keep the original conditions and label any reduced example's
actual verification. Never describe an untried simplification as reproduced.

### 5) **Performance note**

Precise steps can reduce repeated investigation work, but writing the report does
not directly change application speed. A slowness report needs the operation,
start/end observations, environment and relevant workload; a screenshot alone
supplies no latency measurement. This packet establishes a content mismatch and
contains no measured export duration or performance comparison.

### 6) **Mentor note**

Have the learner mark the report's facts, expectation, hypothesis and proposed
next observation. Remove R-14, then ask them to revise only the claims that depend
on it. A good revision keeps the reproducible mismatch while requesting the missing
product decision. Next, change the repeat count and check that their frequency
statement changes without inventing a cause or platform-wide conclusion.
