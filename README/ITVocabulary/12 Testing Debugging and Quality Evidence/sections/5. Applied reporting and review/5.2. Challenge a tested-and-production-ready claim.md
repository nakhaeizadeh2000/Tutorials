## 5.2. Challenge a tested-and-production-ready claim

“The build is tested and production-ready” is a conclusion that needs a subject,
criteria and evidence. A test result can be valid within its arrangement while
leaving a release requirement unanswered. Review the actual artifact, behavior
and conditions before deciding what the result supports.

### 1) **Align each quality claim with an artifact and an expectation**

This is an **original fictional release-review exercise**. The application uses
NestJS with the Fastify adapter, a browser client and a report database. No backend
or browser tests were executed for this exercise. The named tests and outcomes
belong to the constructed packet below.

The team's criterion for this release requires the filtered CSV rule R-14 to pass
on the release candidate and requires a real database-path check for that candidate.
Other operational criteria exist outside this packet; it cannot establish the
whole release decision. These are stated local requirements, not a universal
mandatory test inventory for every product.

| Packet item | Recorded evidence |
|---|---|
| Proposed candidate | Source H12, artifact A12; build completed successfully |
| Success claim | “All 92 cases passed; 90% coverage; E2E and integration covered; production-ready” |
| Run summary for H12 | 89 cases passed initially; 3 failed initially and passed on retry; logs retained |
| Coverage report for H12 | 90 of 100 included statements executed; 10 additional administrative statements excluded |
| Calculation checks for H12 | Local calculations; some assertions check only that a returned total is numeric |
| H12 browser suite labeled E2E | Real page interactions; every report API response intercepted with prepared data; no real API or database request |
| Real database integration result | Correct query result against the real driver and test database, but for H11; no H12 result supplied |
| R-14 export issue on H12 | Approved table shows only the 2-seat approved row; CSV includes that row and the 3-seat pending row; issue remains unresolved |
| Acceptance and capacity | No intended-user acceptance outcome or representative-load result supplied |

Start with the candidate and its actual version. A successful build establishes
that the configured build completed; it does not automatically establish every
runtime requirement. The H11 integration result remains useful evidence about
H11. To use it for H12, explain what changed and provide an appropriate argument
or updated check. Do not quietly relabel the old run as a candidate result.

The source-to-running-configuration distinction matters beyond test code. Google's
original [Testing for Reliability chapter](https://sre.google/sre-book/testing-reliability/)
describes how a valid isolated result can differ from an operationally relevant
configuration. The point here is evidence alignment, not importing Google's entire
release process or its historical infrastructure.

### 2) **Distinguish a supported result from a detected problem or missing evidence**

A worked assessment separates three situations: a supported bounded observation,
contrary evidence, and an unanswered question. Missing evidence is not proof that
the feature is broken. A known requirement violation is stronger than a missing
check, and should not disappear into a generic “needs more tests” comment.

| Claim | Assessment from this packet | Useful follow-up |
|---|---|---|
| The candidate builds | Supported by the A12 build record | Keep the build configuration and candidate identity with the result |
| All 92 passed on their first attempt | Contradicted: three passed only after retry | Preserve initial failures and investigate their conditions |
| 90% means 90% of requirements are correct | Unsupported: this report counts included statement execution | Inspect assertions, exclusions and uncovered behavior against requirements |
| The browser suite exercises the deployed report API | Contradicted by the intercepted-response arrangement | Evaluate the real boundary separately with candidate-specific evidence |
| The driver/database path passed on H12 | Unestablished: supplied result is H11 | Check the relevant H12 path or justify why prior evidence applies |
| R-14 passes on H12 | Contradicted by the recorded CSV mismatch | Investigate and correct the reported case, then check it on the candidate |
| The workload is within required capacity | Unestablished: no suitable workload result supplied | Define the required workload and measurement boundary before evaluation |

The number-only assertion can accept both required total 2 and incorrect total 5.
That does not invalidate every calculation test; it identifies a particular weak
condition. Likewise, browser tests with prepared responses can check useful client
behavior. They leave real request handling and persistence outside their scope,
regardless of the suite's E2E label. Use the existing assertion and test-boundary
owners for the full distinctions rather than changing the suite name into proof.

Ninety of 100 included statements is 90% under that report. Including the 10
excluded, unexecuted administrative statements in this same statement inventory
would yield 90/110, about 81.82%. This calculation explains the scope difference;
it does not establish whether those exclusions are justified. Ask why they exist
and what evidence covers the relevant risk. The coverage owner explains why a
percentage cannot evaluate assertion quality or absent implementation.

For the retry record, “92 cases eventually passed, with 3 passing only on retry”
preserves the evidence better than “92 clean passes.” It is not 95 independently
specified cases. The first failures require investigation; the packet does not
show whether they were test defects, application races or environmental problems.
Do not classify them automatically as false positives.

### 3) **Write a useful decision handoff and update it as evidence changes**

A technical handoff can read:

> Candidate A12 from H12 builds, and all 92 selected cases eventually passed,
> including three after initial failures. The browser suite checks client behavior
> against prepared responses. The supplied real-database result is for H11, so
> candidate database-path evidence remains unresolved. The known H12 CSV mismatch
> violates the release's R-14 criterion. Investigate that case and the three initial
> failures, then align correction and database results with the candidate. The
> packet does not establish user acceptance or representative-load behavior.

For a stakeholder, retain the practical implication without requiring test jargon:

> The candidate can be built, and several selected checks passed. The export still
> includes data outside the chosen filter, which conflicts with this release's
> agreed rule. The supplied checks do not yet establish the candidate's database
> path or the whole release's readiness. The team needs a verified correction and
> the remaining evidence required by its release criteria before making that claim.

Now add a controlled variation: H12 receives a passing real-database result, and
the team investigates the CSV defect, fixes it in source H13 and builds A13.
Those facts resolve the old H12 database evidence gap and identify a new candidate.
They do not make A13's CSV case pass without an actual result, nor automatically
transfer every H12 observation to H13. Compare changes and record applicable new
results or a justified reuse argument. An approval on an older artifact is also
not automatically an approval on the changed candidate.

For an interview, ask: “Would you ship this release?” A strong answer starts with
the supplied local criteria and the known R-14 failure. It asks which remaining
risks the authorized release owner must evaluate, rather than inventing one
universal test count or personally assuming decision authority. If the requirement
changes through an agreed decision, record the new expectation and its consequences;
do not rewrite the test simply to turn a known failure green.

### 4) **Common confusion**

A green job can mean that its configured completion conditions were satisfied.
It does not explain whether a case was skipped, retried, weakened or run against
substitutes. Read the arrangement and detailed outcomes before broadening the claim.

“Tested” is also not a permanent attribute of a component name. A source revision,
artifact, input, state and environment define what was evaluated. Conversely,
asking for evidence does not require rerunning every possible check after every
edit. Judge applicability and relevant risk, and explain any reuse of prior results.

### 5) **Performance note**

No representative-load result appears in this packet. Passing small functional
checks and observing a fast substitute do not measure real dependency latency,
contention or capacity. Define the workload, population, environment and start/end
boundary for the actual performance question. The arithmetic above concerns coverage
scope only; no build, test-duration or throughput benchmark was performed here.

### 6) **Mentor note**

Ask the learner to assign each conclusion to a packet row and classify it as
supported, contradicted or unanswered. Then introduce A13 and ask which evidence
still applies. Reward a targeted next check and a reason for reuse, not a demand
for an arbitrary larger test suite. The learner should preserve the known export
failure separately from the unverified capacity and acceptance questions.
