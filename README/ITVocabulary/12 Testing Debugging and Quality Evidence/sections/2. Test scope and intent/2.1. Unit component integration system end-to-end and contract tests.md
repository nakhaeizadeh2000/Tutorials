## 2.1. Unit component integration system end-to-end and contract tests

A test report says “end-to-end passed,” but the browser's API request was replaced
with a prepared response. Another says “unit tests passed,” yet exercises several
real objects together. Before deciding whether either report is misleading, ask
what the test actually exercised and which boundary the team intended the label
to describe.

Read the preceding quality-evidence lessons. This page uses constructed test
arrangements, not executable tests or real test-run results. The backend context
is NestJS with the Fastify adapter; no framework setup is needed to follow it.

### 1) **Define the tested boundary before assigning a level name**

The **system under test**, often **SUT**, is the software boundary being evaluated.
A **test level** organizes evaluation around a scope such as a component or a
whole system. Names are useful shorthand, but their local meaning needs a shared
boundary and objective.

A **unit test** commonly checks a small unit of behavior. The unit might be a
function, class or cooperating group, rather than exactly one file. **Component
testing** can be a synonym: ISTQB uses component and unit together. Other teams
use component for a larger independently testable part, such as a service or UI
component. State which convention you use. Neither filename nor framework name
can settle it.

**Integration testing** evaluates interfaces and interactions between parts.
**Component integration** can concern parts within a system; **system integration**
can concern separate systems or external services. A narrow repository-to-database
check exercises a real integration without requiring a browser or the entire
application. If that database is replaced with a programmed response, the check
no longer exercises that real storage boundary.

**System testing** evaluates the overall behavior of the system within its stated
scope. It can include functional and other quality concerns, and some outside
systems may be simulated. An **end-to-end test**, or **E2E test**, follows a workflow
across specified starting and ending points. Often those points are user action
and resulting application state, but “end-to-end” needs the actual endpoints and
substitutions named. It does not automatically include every third party or prove
production readiness.

The [ISTQB syllabus](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf),
section 2.2.1, supplies one explicit level taxonomy. Martin Fowler's
[unit](https://martinfowler.com/bliki/UnitTest.html) and
[integration](https://martinfowler.com/bliki/IntegrationTest.html) discussions explain
why other teams draw different boundaries. His “solitary” tests replace a unit's
collaborators; “sociable” tests retain some real collaborators. Use those distinctions
to clarify a discussion, not to force every team's vocabulary into one naming rule.

### 2) **Trace which real collaborations each arrangement exercises**

Read these independent fictional arrangements for a report feature. A **substitute**
here means code supplying a prepared response in place of a real dependency; the
later test-double lesson explains the named varieties.

| Arrangement | Real software exercised | Explicitly outside this arrangement |
|---|---|---|
| A: call the seat-total function and compare its return | Local calculation on supplied rows | HTTP, database, browser, email |
| B: call the real report repository against a fresh database | Repository, database driver and database operations | Service routing, browser, email |
| C: submit an HTTP request to the running report API | Fastify request handling, Nest application logic, repository and database | Browser and real email service; email call receives a prepared success |
| D: operate the report page and check its displayed result | Browser page and UI code | API call is intercepted and answered with prepared JSON |
| E: operate the page, submit to the real API and inspect persisted report state | Browser, API, application and database | Email uses a substitute; no recipient mailbox is inspected |

A is a clear small-unit example. B is a narrow integration check at the storage
boundary. C checks more integrated application behavior; a team may call it API
integration or service component testing. The table is more informative than
settling that naming debate.

D can be valuable UI evidence, but it cannot show that the page successfully
integrated with the real report API. The response never came from that API. E
covers the stated user-action-to-persisted-report path and can be described as
E2E for that scope. It cannot establish actual email delivery. Replacing an external
dependency changes the claim a test supports; it does not make all remaining
observations worthless.

Playwright's [best practices](https://playwright.dev/docs/best-practices#avoid-testing-third-party-dependencies)
show controlled responses for third-party dependencies. Such control can make an
application check more predictable. Preserve the substitution in the reported
scope, and obtain separate real-boundary evidence when that integration is the
question. No Playwright code or browser session was run for this table.

Practice: replace B's database with a simple in-memory map implementing the same
repository operations. What evidence is lost? The revised arrangement may check
its caller's behavior against that substitute, but no longer exercises the real
driver, SQL, database constraints or storage configuration. “Both store values”
does not establish that the implementations behave identically. The exact revised
boundary determines whether the team calls it unit or component testing.

### 3) **Distinguish interface-contract evidence from a complete workflow**

A **contract test** evaluates an agreed interaction at a boundary, such as an
API request and response or a produced message. The purpose is compatibility of
the relevant participants or conformance of an implementation to a documented
contract. It is not synonymous with every check of business behavior.

Consider a client that sends a report request and reads a numeric `approvedSeats`
field. A local client check receives a prepared response containing that field.
It supplies evidence that the client can use that response; it does not establish
that the real provider produces it.

In one **consumer-driven contract** approach, the consumer's exercised expectations
are recorded, and a separate provider verification checks the real provider against
those interactions under controlled preconditions. The [Pact introduction](https://docs.pact.io/)
and [consumer/provider walkthrough](https://docs.pact.io/getting_started/how_pact_works)
explain this split. These are conceptual examples, not an instruction to install
a contract-testing tool. Both the consumer evidence and corresponding provider
verification must apply to the versions and interactions being considered.

A provider check against an API specification is also called contract testing
in some teams. It can find documentation/implementation disagreement, but alone
does not show that a particular client sends the right request or uses the response
correctly. Reading a schema file without executing the participants establishes
still less. State the checked contract and participant versions explicitly.

Contract checks also have limits. Verifying a required numeric field does not
show that every total is calculated correctly. Separately executed participant
checks do not exercise the complete deployed network path or report-to-email
workflow. Add evidence for the distinct risk rather than turning “contract passed”
into a universal integration guarantee.

### 4) **Common confusion**

Test level, purpose and execution tool are different dimensions. A browser can
exercise a narrow UI with its API substituted or a broad application workflow.
An HTTP request can exercise one API boundary without any user interface. The
presence of a browser, subprocess or real JSON parser does not by itself establish
end-to-end scope.

“Integration passed” is also incomplete without naming the integrated parts. A
prepared provider response can be appropriate for a client check while leaving
real-provider compatibility unverified. Describe that limitation directly instead
of declaring every substitute-based check either complete or useless.

### 5) **Performance note**

Wider arrangements can add process startup, network, database and browser work,
as well as more state to manage. Narrow checks often give quicker, more localized
feedback, while broader checks can expose wiring or environment problems that
narrow ones omit. These are trade-offs, not fixed duration classes or a prescribed
percentage of tests at each level. Measure execution and investigation cost for
the actual suite, and retain evidence for important boundaries. The table provides
no timing benchmark or universal test-pyramid ratio.

### 6) **Mentor note**

Ask a learner to draw the real path in D and E and mark the substituted edge.
Then ask which arrangement supports the claim “the customer received the email.”
The answer is none: no real mailbox delivery was checked. For contract testing,
remove the provider-verification record and expect the compatibility conclusion
to weaken. Strong answers name the remaining useful evidence and the missing
boundary before proposing another test or arguing about level names.
