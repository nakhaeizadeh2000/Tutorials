## 2.2. Functional non-functional regression smoke and exploratory testing

“We ran functional tests, so we did not run regression tests” assumes that those
labels describe exclusive buckets. They often describe different dimensions.
One check can evaluate a function, protect against a regression and be included
in a small smoke suite at the same time.

Start with the previous lesson's real-versus-substituted boundaries. This lesson
adds purpose and approach to that scope. The examples are constructed evaluation
plans and records; no test execution or performance measurement is claimed.

### 1) **Separate the tested scope from the quality question and execution method**

A **functional test** evaluates what the software does, such as calculating a
required total or rejecting an invalid request. A **non-functional test** evaluates
a quality characteristic such as performance or usability under stated conditions.
For example, one report check can evaluate both the returned total and completion
within a specified duration. The requirement and observation determine the claim.

These purposes can apply at several scopes. A small calculation can have a
performance concern; a complete system can have a functional correctness concern.
Non-functional does not mean “only after integration,” and functional does not
mean “only through a browser.” The [ISTQB CTFL 4.0.1 syllabus](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf),
section 2.2.2, describes the distinction and its application across levels. Its
quality categories are a useful reference, not a reason to avoid stating the
specific quality question in plain language.

Execution method is another dimension. A person can carry out prescribed checks;
an automated tool can execute checks and record results. Neither method alone
establishes the test's level, quality objective or adequacy. A **test case** describes
a particular situation with relevant preconditions, inputs or actions and expected
results. A **test suite** groups cases for a purpose. A **test run** is an actual
execution of a selection in an identified environment and version. A suite existing
in a repository is not evidence that it ran.

### 2) **Distinguish change protection from a preliminary smoke check**

The earlier regression lesson owns the before/after distinction: **regression
testing** looks for adverse consequences of a change. **Confirmation testing**
checks that a particular reported problem has been corrected; teams also commonly
call that retesting. The two purposes can overlap in the cases they execute,
but confirming one correction does not establish that other behavior was preserved.

A **smoke test** or smoke suite provides a preliminary check of important basic
capabilities before relying on a build or proceeding to more detailed evaluation.
A service starting is one possible check; a critical report workflow may be another.
The selected purpose and critical paths matter more than a fixed number of cases
or a universal time limit. Microsoft's [test-type guidance](https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/testing-strategy-test-types)
uses smoke testing to establish basic functionality before further testing.

Passing a smoke suite does not imply a complete regression evaluation or release
acceptance. If the suite exercises login and report creation, it may tell you
nothing about a large export or restore workflow. Name what passed and what remains
unperformed instead of translating “smoke passed” into “all features work.”

| Create a report through the UI and verify the persisted seat total; retain it across releases and include it in the team's quick build check | Functional, regression when used after changes, and smoke when selected for that suite; its E2E scope still needs the real path named |

These are plans, not passing outcomes. For the first check, changing its suite tag
from smoke to regression does not change the application components it exercises.
For the second, collecting duration data without comparing it to the required
bound does not supply the planned pass/fail evaluation. For the third, running
only valid-input requests would not confirm the reported zero-seat correction.

### 3) **Use exploration to turn observations into the next useful experiment**

**Exploratory testing** connects learning, test design, execution and evaluation:
what a tester observes can change which experiment they perform next. It is not
synonymous with random clicking, an absence of preparation or undocumented results.
A **test charter** can state the mission and limits of a session while leaving
room to follow evidence. Tools and automated checks can support that investigation.

Satisfice's original [exploratory-testing explanation](https://www.satisfice.com/exploratory-testing)
emphasizes learning that influences testing. ISTQB section 4.4.2 also describes
focused exploration and optional session-based charters. The teaching point is
the feedback between observation and the next question, not a universal rule that
every session has the same length or paperwork.

Here is a fictional charter: “Investigate whether changing report filters can
leave displayed totals inconsistent with the selected filter. Use synthetic data;
record the sequence, selected filter and visible result. Do not send real emails.”
The tester starts with approved-only records, then switches to pending-only. The
label changes but the displayed total remains the approved value. They next
inspect the response record and repeat the switch after a reload to distinguish
stale UI state from a different server result. Those follow-up choices come from
the observation; they were not an arbitrary tour of the interface.

This narrative describes an investigation, not a verified diagnosis. An unchanged
number alone might reflect coincidentally equal totals, so the synthetic inputs
must make the expected results distinguishable. A reproducible sequence with those
inputs can become a prescribed regression case after the behavior and requirement
are understood. Preserve what was observed separately from the proposed cause.

Practice: the response record contains the correct pending total while the screen
still shows the earlier approved total. Which hypothesis gains support? A problem
between receiving that response and displaying it becomes a stronger direction
for investigation. The record does not uniquely identify a particular UI defect.
If the response record is removed, do not keep the same confidence about a UI-only
cause. The next observation should help separate the remaining possibilities.

### 4) **Common confusion**

Functional, regression and smoke are not three mandatory separate copies of a
check. They can describe its quality objective, change-related purpose and selection
for a preliminary suite. Count unique executed cases and their actual coverage
rather than inflating results by counting every label as another execution.

Exploratory work can be disciplined and evidence-producing, while a long scripted
suite can omit important questions. Prescribed and adaptive work can support each
other: a repeatable check preserves a discovered example, and further exploration
can challenge assumptions that the repeatable check leaves untouched.

### 5) **Performance note**

A performance test measures application behavior under a workload; the time spent
running a test suite is a different cost. A quick smoke check cannot stand in for
a required sustained workload merely because both have a time-related name. Keep
setup, application observation, environment and pass criteria explicit. This lesson's
100-request/two-second rule is fictional and has not been executed; no speedup,
capacity claim or recommended universal threshold follows from it.

### 6) **Mentor note**

Ask a learner to label the first planned check by scope, purpose, execution method
and run status. They should notice that the method and actual result were not
supplied, rather than guess them from the E2E or smoke label. Then ask them to
choose the next observation in the filter investigation and explain how each
possible result would affect their hypothesis. Reward a discriminating experiment
and clear evidence, not an arbitrary number of cases or a preferred testing label.
