## 4.1. Reproduction hypotheses stack traces breakpoints and root causes

A report ends with `ZeroDivisionError`. The arithmetic line identifies where this
execution could not continue; it does not tell you what the product should do with
an empty report. Debugging connects the observed failure, the relevant expectation
and the conditions that produced it.

### 1) **Separate a reproducible symptom from a proposed explanation**

**Debugging** investigates and corrects a software problem. Testing can expose a
failure or evaluate a correction; debugging asks how it happened. A **symptom** is
an observed manifestation, such as a crash or an incorrect total. A **hypothesis**
is a proposed explanation that observations or experiments can support or challenge.
Write “the report crashes for this empty input” separately from “the data loader
must be broken.” The first can be observed before the second is established.

A **reproduction** is a procedure that produces the relevant behavior under stated
conditions. A **minimal reproduction** removes unrelated parts while preserving
that behavior. Minimal does not mean shortest at any cost: removing the competing
worker may remove the race you need to investigate. Record exact inputs, relevant
versions, configuration, initial state, steps, expected behavior and actual outcome.
For intermittent behavior, record attempts and conditions rather than promising
that a single recipe always fails.

Julia Evans's original [debugging discussion](https://jvns.ca/blog/2019/06/23/a-few-debugging-resources/)
connects reproduction with experiments that check assumptions. Use a discriminating
question: if the loader returned the wrong type, what would you observe before
calling the calculation? Change one relevant condition where feasible so the
result can distinguish explanations. Changing the dependency version, input and
implementation together may hide which change mattered.

### 2) **Read a traceback and inspect a paused frame**

This complete example runs on **CPython 3.14.4, Linux x86_64**, a pinned local
runtime. Current Python 3.15 reference documentation was consulted; it is not the
executed version. No packages are needed. The product rule for this example is:
for a nonempty list of ordinary positive integer seat counts, show their arithmetic
mean; for an empty list, show `no data`. The calculation helper's intended input
is nonempty. The report below deliberately omits the empty-case handling.

Save `report_debug.py` and run `python3 report_debug.py`. This is an intentional
failure in a local program; it changes no files and contacts no service.

```python
def average(seats):
    return sum(seats) / len(seats)


def render_report(seats):
    return average(seats)


print(render_report([]))
```

The process exits unsuccessfully with `ZeroDivisionError: division by zero`.
Its traceback identifies the module call on line 9, `render_report` on line 6,
and `average` on line 2. File paths and diagnostic highlighting depend on the
runtime and location. This is Python's “most recent call last” presentation:
read the final exception description, then follow the recorded frames to see
how execution reached it. Python's [exception tutorial](https://docs.python.org/3.15/tutorial/errors.html)
explains this traceback context. Other languages and tools may order frames
differently or include separately reconstructed asynchronous context.

A **stack trace** describes recorded call frames at a particular observation;
a Python exception **traceback** records the frames associated with that exception.
It is not a complete history of every earlier call or every state change. Source
locations must match the running artifact; generated or transformed code may need
**source maps**, which relate generated positions to their original source.
Language-specific stack and source-map mechanics remain with their owners.

A **debugger** can pause execution and inspect state. A **breakpoint** specifies a
place or condition at which to stop. A **conditional breakpoint** stops when its
condition holds. While paused, a **frame** supplies the local context for inspection.
A **watch expression** is an expression a debugger reevaluates to observe a value;
evaluating an expression can call code or change state, so it is not automatically
passive. Start with simple variable and length inspection here.

For the same file, run `python3 -m pdb report_debug.py`. Python's built-in debugger
starts paused. Enter these debugger commands, one per line; do not include a
`(Pdb)` prompt as input:

```text
break 2
continue
p seats
p len(seats)
p sum(seats)
where
quit
```

`break 2` sets a line breakpoint. `continue` runs to it, before the division.
The three inspection results are `[]`, `0` and `0`. `where` shows the call path
through the module and `render_report` into `average`, along with debugger machinery.
`quit` ends this debugging session before the failing division is executed. These
commands were actually run for this lesson; they do not repair the program.

The empty list and zero divisor challenge the wrong-type hypothesis. They support
a narrower explanation: the report calls a nonempty-only helper with an empty
list. You still need the stated product rule to decide how to correct that path.
An empty input is not automatically bad data; this example explicitly allows it.

Common stepping names describe how execution resumes. **Step into** follows a
called function where supported; **step over** runs the call and seeks the next
stop in the current frame; **step out** resumes toward the current function's
return. Exceptions, other breakpoints and tool rules can interrupt that intent.
Stepping executes code; it does not skip the call's effects. The current
[`pdb` reference](https://docs.python.org/3.15/library/pdb.html) documents Python's
`step`, `next`, `return`, breakpoint and inspection behavior.

### 3) **Connect a correction to causal evidence and its limits**

For the controlled correction, add an empty-list check inside `render_report`
before its existing return. When `not seats` is true, return the string `no data`;
otherwise retain the call to `average`. In this input model, an empty list is
false in a condition. The corrected empty case prints `no data` and exits
successfully. Changing only the final input to `[2, 4]` prints `3.0`. Both corrected
cases were executed. The helper is unchanged because its documented input remains
nonempty; this is one responsibility choice, not a universal guard-placement rule.

The sequence establishes more than a guessed cause: the same empty input reaches
zero division in the original, the paused frame confirms that input, and a targeted
change handles that case while retaining one nonempty example. It does not prove
all possible input types, other callers or an entire application are correct.

A **root cause** is an underlying causal explanation at a defined investigation
scope. Teams sometimes use it for the immediate faulty logic and sometimes for
conditions that allowed the fault to reach users. Name that scope. Here, the missing
empty-case handling explains the local requirement failure. Why it was omitted,
why review did not catch it, and whether production ever received this input are
unanswered. A list of **contributing factors** may be more useful than inventing
one deepest cause or blaming the person whose change appears in history.

A **workaround** changes how the problem is encountered, such as manually avoiding
empty reports. A **mitigation** reduces its impact, such as containing the failed
report so other work remains available. A **fix** or correction addresses the
identified fault. Those labels depend on scope: hiding the error dialog without
providing `no data` does not fulfill this report requirement.

Practice: suppose the failure disappears only while stepping. Is it disproved?
No. The debugger changes timing and possibly scheduling. Preserve the unpaused
observations and investigate with an observation method suited to that behavior.
This is a reasoning variation, not a race reproduced by this sequential example.

### 4) **Common confusion**

The last application frame is a starting point, not an automatic root-cause answer.
A helper can correctly reject an input that its caller should never supply.
Conversely, moving the crash into a handler does not by itself satisfy a user need.
Compare the behavior with the contract at each boundary.

“Cannot reproduce” describes the investigator's current result. It does not prove
that the original observation was false. Compare versions, initial state, inputs
and execution conditions before closing the gap with a guessed explanation.

### 5) **Performance note**

Pausing stops relevant execution and can hold resources while other participants
continue. Logging, tracing and expression evaluation can also change timing and
work performed. Do not use this paused run as an ordinary response-time measurement.
The example demonstrates a calculation failure, not a measured bottleneck or
concurrency defect; no overhead or performance improvement was measured.

### 6) **Mentor note**

Ask the learner to state the symptom, two competing hypotheses and one observation
that distinguishes them before editing. Have them explain each traceback frame,
then decide which boundary should own empty-case handling under the supplied rule.
A strong answer distinguishes the reproduced local cause from uninvestigated
release or organizational factors, and checks the original failing case after
making the targeted correction.
