## 3.1. Assertions fixtures test doubles mocks stubs spies and fakes

A passing test says the notification service was called with a total of 5. Did a
real notification arrive? If the service was replaced by a recording object, the
test establishes a local interaction, not external delivery. Understanding the
arrangement is essential to interpreting the assertion.

Read the earlier test-boundary lesson first. This page uses a complete local Python
example to make the arrangement and its limits observable. It requires no testing
framework, service account or network access.

### 1) **Identify the prepared situation and the condition being checked**

A test **assertion** compares an observation with an expected condition and reports
a failure when the condition does not hold. It can concern a returned value,
visible state, exception or interaction. An assertion does not establish anything
it does not inspect. Checking that a result exists is weaker than checking its
required value when that value matters.

This is different from a TypeScript **type assertion**, which instructs the checker
and does not add an ordinary runtime check. “Assertion” also appears in runtime
design-by-contract discussions. Name the mechanism and the claim; the same word
does not imply the same evidence in every context.

A **fixture** is the prepared data, state or resources that a test needs. Depending
on the tool, the term can also refer to the setup and cleanup mechanism that
provides those resources. A JSON file can contain fixture data, but a fixture need
not be a file or a substitute. A fresh real database can be part of a fixture.
Playwright's [fixture guide](https://playwright.dev/docs/test-fixtures) illustrates
resources with explicit setup and teardown; that tool-specific mechanism is not
a requirement for the small example below.

An **Arrange–Act–Assert** description makes the reasoning visible: establish the
situation, perform the action, then evaluate the relevant observations. Include
cleanup when resources or temporary replacements need it. This is a useful reading
sequence, not a rule that every test has exactly three lines, one function call
or one assertion.

### 2) **Choose a substitute by its role rather than its library name**

A **test double** replaces a real collaborator for a testing purpose. These common
names follow the vocabulary popularized by Martin Fowler from Gerard Meszaros's
work in [Test Double](https://martinfowler.com/bliki/TestDouble.html):

| Role | What it contributes to an arrangement | Example |
|---|---|---|
| Dummy | Fills a required position but is not used on this path | An unused reporter argument |
| Stub | Supplies prepared answers or failures | A notifier that always returns `accepted` |
| Spy | Records interactions for later inspection | A notifier that records the submitted totals |
| Mock | Carries expectations about interactions that are verified | An object expecting one notification with total 5 |
| Fake | Supplies a working, simplified implementation | An in-memory report store supporting save and lookup |

These describe roles, not rigid product classes. One object can supply a prepared
answer and record calls, serving both stub and spy purposes. “Mock” is also often
used loosely for any substitute. Python's current
[`unittest.mock` introduction](https://docs.python.org/3.15/library/unittest.mock.html)
describes a `Mock` object that can provide return values and record interactions;
the class name does not settle which role a particular arrangement uses. No library
API is needed or executed in this lesson.

A fake store implements some behavior, but it does not automatically reproduce
a real database's query language, transactions or constraints. Likewise, a stub's
prepared success is not evidence that a real service accepts the request. Retain
real-boundary checks for the integration questions that these substitutes leave
open. The previous contract-testing lesson explains one way to compare participant
expectations with actual provider behavior.

### 3) **Run a recording collaborator and test what it establishes**

Tested environment: **CPython 3.14.4 on Linux x86_64**, a pinned local runtime.
The current Python 3.15 documentation was consulted for the terminology comparison,
not claimed as the executed version. Save `recorded_notice.py` and run
`python3 recorded_notice.py`. No packages or imports are required.

The local contract is simple: for a list of ordinary positive integer seat counts,
submit their sum to the supplied notifier exactly once and return its receipt.
This deliberately omits input validation and external transport. `class` defines
an object type, `__init__` prepares each new instance, and `self.calls` is that
instance's recorded list. `append` adds one item.

```python
class RecordingNotifier:
    def __init__(self):
        self.calls = []

    def send(self, total):
        self.calls.append(total)
        return "accepted"


def send_summary(seat_counts, notifier):
    total = sum(seat_counts)
    return notifier.send(total)


seat_counts = [2, 3]
notifier = RecordingNotifier()
receipt = send_summary(seat_counts, notifier)
print("Receipt:", receipt)
print("Recorded totals:", notifier.calls)
if receipt != "accepted" or notifier.calls != [5]:
    raise AssertionError("unexpected summary interaction")
print("Local expectation passed")
```

Observed output:

```text
Receipt: accepted
Recorded totals: [5]
Local expectation passed
```

The fixture includes the two input counts and a fresh recording notifier. The
action calls `send_summary`. The final condition checks the receipt and the complete
recorded list. `[5]` means one recorded call with total 5; it excludes both no call
and two recorded calls. The explicit `if` and `raise AssertionError` implement
this example's test assertion without relying on Python's optionally disabled
`assert` statement.

The notifier supplies a prepared receipt and records calls, so it acts as both
stub and spy. The receipt came from that object. There is no real notification
transport, remote acceptance or recipient delivery in the program. Calling the
final line “email delivery passed” would overstate the result.

For a controlled failure, change only `notifier.send(total)` to
`notifier.send(total + 1)`. The receipt remains `accepted`, but the recorded list
becomes `[6]`. In the executed variation, the check raises
`AssertionError: unexpected summary interaction`, the process exits unsuccessfully,
and the final passing line is absent. Restore the original expression afterward.
This contrast shows why checking only the prepared success receipt would miss
a wrong outgoing total.

Practice: imagine the code submits total 5 twice. Would checking only that the
list contains 5 establish the contract? No. That weaker condition ignores the
exactly-once local-call requirement. The existing equality with `[5]` checks both
the expected argument and call count. This is a local interaction contract, not
the distributed exactly-once guarantee taught earlier.

### 4) **Common confusion**

A spy observing a method call does not prove the remote effect occurred. If the
real notifier performs retries or remote writes, those behaviors are outside this
recording object's implementation. Conversely, the local interaction check is
still useful: the deliberately wrong total causes it to fail.

Overly detailed interaction expectations can also tie tests to incidental internal
steps. Check a call count or order when it is part of the behavior you need to
preserve, as in this example, rather than requiring every helper invocation to
remain unchanged. A passing test against a substitute that always agrees with
incorrect behavior can supply false confidence; assess both the expectation and
the substitute's fidelity.

### 5) **Performance note**

Replacing a network or database dependency can remove real I/O and setup work,
which changes both test cost and what was exercised. The recording list itself
uses memory proportional to its retained calls; long runs may need bounded
observation or cleanup. No timing comparison was performed here. “Fake” or “mock”
is not a performance guarantee, and a fast substitute cannot establish the real
integration's latency or capacity.

### 6) **Mentor note**

Ask the learner to identify the fixture, action, assertion and replacement boundary,
then explain why the receipt alone is insufficient. Run the wrong-total variation
and ask which observation exposes the problem. Next, propose a real notifier that
returns `accepted` but cannot deliver a message. They should preserve the local
check's value while asking for separate transport and delivery evidence, rather
than changing its passing line into a broader success claim.
