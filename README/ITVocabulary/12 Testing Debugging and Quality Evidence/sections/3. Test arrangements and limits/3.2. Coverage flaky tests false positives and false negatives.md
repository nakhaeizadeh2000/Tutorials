## 3.2. Coverage flaky tests false positives and false negatives

“Coverage is 90%, and the failed test passed on retry.” That sentence contains two
observations, neither of which establishes that the feature is correct. The first
needs a denominator; the second needs an investigation of why the outcomes differed.
Read the preceding assertion and test-boundary lessons before this page.

### 1) **Read coverage as a scoped execution measurement**

**Coverage** describes how much of a specified set was exercised. Code coverage
usually records execution, while requirements coverage may record which stated
requirements have corresponding tests. These are different sets. A requirement
linked to a planned case has not necessarily been exercised in an actual run.

For code coverage, name the criterion before interpreting the percentage:

| Criterion | Typical question | Important limitation |
|---|---|---|
| Statement or line | Which counted statements or source lines executed? | Executing a line does not establish its result was checked correctly |
| Branch | Which counted decision outcomes or control-flow transitions executed? | Exercising both directions does not exercise every input or combination |
| Function | Which counted functions were entered? | Entering a function does not check every behavior inside it |

Tools differ in their counting rules and treatment of generated code, mappings,
exception paths and exclusions. Read the report's definitions. For example,
[Coverage.py's branch documentation](https://coverage.readthedocs.io/en/latest/branch.html)
explains its source-to-destination transitions and how exclusions can change the
possible branches. This is a concrete tool model, not a universal branch algorithm.

Consider this **constructed report**, not output from a coverage tool run here:

| Report scope | Exercised statements | Counted statements | Coverage |
|---|---:|---:|---:|
| Whole application | 100 | 120 | 83.33% rounded |
| Report feature within it | 20 | 40 | 50% |
| Other application code | 80 | 80 | 100% |

The whole percentage hides the feature's larger gap. Now exclude the feature's
20 unexecuted statements without changing the tests. The remaining application
scope becomes 100/100, or 100%. The excluded behavior did not acquire evidence;
the denominator changed. An exclusion can be justified, but its reason and scope
must remain visible. Excluding difficult behavior solely to pass a gate conceals
the gap the metric was meant to expose.

Coverage also cannot see behavior that was never implemented. If a required
permission check is absent from the source, executing every existing statement
does not add that check. Review requirements, assertions and actual integration
boundaries alongside execution gaps. Google's original
[coverage discussion](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html)
likewise treats coverage as an incomplete signal and emphasizes examining specific
gaps. Its numerical guidelines are organizational context, not universal targets.

### 2) **Define the positive signal before classifying a mistaken result**

For the following discussion, a **positive** means “this check reports a defect.”
A **false positive** reports a problem when the behavior actually meets the
relevant expectation. A **false negative** misses a real problem. Some tools use
“positive” to mean a successful outcome instead, so establish the convention first.
Neither label can be assigned from the red or green color alone: compare the signal
with the actual behavior and the relevant requirement.

This **fictional assessment** uses a report requirement that approved rows count
toward the total and pending rows do not. Approved seats are 2 and pending seats
are 3, so the required total is 2.

| Actual implementation and observation | Automated check | Interpretation under our convention |
|---|---|---|
| Incorrect total 5 | Checks only that the result is a number; passes | False negative for this selection defect |
| Correct total 2 | Incorrectly expects 5; fails | False positive for a product defect; the expectation is wrong |
| Incorrect total 5 | Expects the required 2; fails | True positive: the check detects the defect |
| Correct total 2 | Expects 2; passes | True negative for this case; other behavior remains unexamined |

An **oracle** is the reference or mechanism used to decide what outcome is expected.
It might be an agreed rule, trusted independent calculation or comparison with an
accepted model. Copying the implementation's formula into the expected-result
calculation can repeat the same mistake. In this case, use the independent approved-
only rule to explain 2. An oracle can itself be incomplete or mistaken.

Change only the weak number check in the first row to an equality with 2. It now
exposes the wrong total. No new source line needs to execute for the assertion to
become more discriminating. This is why identical execution coverage can accompany
very different defect-detection evidence. These rows are worked reasoning, not
executed tests or a measured false-positive rate.

### 3) **Interpret intermittent outcomes without erasing the first failure**

A **flaky test** produces inconsistent pass/fail outcomes across runs when the
intended tested behavior and relevant setup are expected to remain the same.
“Same source revision” is useful context, but it does not prove identical state,
scheduling, dependencies or resource availability. An intermittent application
race can be a real defect; flakiness does not automatically mean the test is wrong.

In this **constructed run history**, all attempts use source revision H7 and the
same case: display the pending total after changing a filter.

| Attempt | Result | Available evidence |
|---|---|---|
| Initial | Failed | Label changed; old total still visible when checked |
| Retry | Passed | Pending total visible when checked |
| Later fresh run | Failed | Old total visible again |

This supports an intermittent outcome. It does not identify whether the application
failed to update, the test observed too early, shared state interfered or another
condition changed. Preserve the first failure's trace, setup and observation.
Compare readiness and state rather than adding an arbitrary delay and assuming
the cause is fixed. A longer delay can hide a product timing defect or merely move
the intermittent boundary.

A **retry** is another attempt. It can recover a useful result while leaving the
initial failure unexplained. Playwright's current
[retry reporting](https://playwright.dev/docs/test-retries) explicitly distinguishes
a first-attempt pass from failure followed by a passing retry. This page runs no
Playwright tests and prescribes no retry count.

**Quarantine** commonly means separating an unreliable check from a trusted gate
while it is investigated. That can protect usable feedback, but it reduces the
gate's protection unless equivalent evidence remains. Record the affected behavior,
owner, investigation and restoration criteria. Fowler's original
[non-determinism article](https://martinfowler.com/articles/nonDeterminism.html)
connects isolation, asynchronous behavior and neglected quarantine; it does not
make one policy appropriate for every release risk.

Practice: remove the later fresh failure from the history. Can you say the retry
fixed the cause? No. You have one failure and one passing retry, with no recorded
correction. Add evidence that a readiness check now waits for the pending response
and then checks the displayed value. This strengthens the arrangement's rationale,
but actual reruns and investigation are still needed to assess the change.

### 4) **Common confusion**

100% code coverage means the counted execution criterion was satisfied within its
scope. It does not mean every requirement, input, state or expected result was
checked. Conversely, a missing branch is useful information; the metric's limits
do not make the uncovered path irrelevant.

A flaky failure and a false positive are different descriptions. The first concerns
inconsistent outcomes; the second concerns whether a defect signal is mistaken.
If a race causes the displayed value to violate its requirement, a failing check
can be a true positive even when a retry passes. Investigate before dismissing it.

### 5) **Performance note**

Coverage collection and reporting can add work; its amount depends on the tool,
workload and instrumentation. A timing observed during instrumentation is not
necessarily an uninstrumented baseline. Retrying a whole expensive test repeats
setup and workload, and can increase contention for other tests. No coverage
overhead, flake probability or timing improvement was measured in this lesson.

### 6) **Mentor note**

Give the learner the report and run history without their conclusions. Ask which
scope produces each percentage, what excluding the 20 statements changes, and why
the weak assertion misses 5. Then ask whether the passing retry explains the first
failure. A sound answer preserves the observations, names an investigation that
could distinguish causes, and avoids promising correctness from either metric.
