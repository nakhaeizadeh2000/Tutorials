## 1.1. Errors defects bugs failures exceptions and regressions

A report returns the wrong total without throwing an exception. Another request
raises an exception because it correctly rejects invalid input. Calling both
“an error” hides the distinction between an unwanted result and the mechanism
used to communicate an outcome.

This domain starts with faults and evidence before comparing checks and testing
practices. You need the earlier program and contract vocabulary. The small example
introduces the Python syntax it uses; no testing framework is required.

### 1) **Separate a mistake from a defect and an observed failure**

In a common testing convention, an **error** is a human mistake. A **defect**, also
called a **fault** or **bug** in that convention, is a problem in a work product
such as code, a requirement or a build configuration. A **failure** is observed
behavior that does not meet the relevant expectation. The distinction is useful:
the mistake is an action or judgment, the defect is in an artifact, and the failure
occurs under particular conditions.

Suppose the agreed report rule is “count seats only for approved reservations.”
A developer mistakenly decides all reservations should count. Removing the status
filter introduces a code defect. Running that code with a pending reservation
then produces an incorrect total: an observed failure. Running it with approved
reservations only may hide the defect because both calculations agree.

The [ISTQB CTFL 4.0.1 syllabus](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf),
section 1.2.3, uses this distinction and emphasizes that a defect need not cause
a failure in every execution. It also recognizes failures arising from environmental
conditions. A failed operation alone therefore does not identify a particular
human mistake or establish that application source code is its cause.

Team language is less uniform. “Error” can mean a runtime exception, an error
message, an incorrect value or a failed request. “Bug” can include concerns about
usefulness even when a written specification is satisfied. James Bach's original
[What Testers Find](https://www.satisfice.com/blog/archives/572) distinguishes product
problems, risks, testing difficulties and surprising observations. It is a useful
reminder that finding value-threatening behavior is broader than counting thrown
exceptions or deviations from a document. Ask which convention is in use, and
state the actual problem before debating the label.

### 2) **Observe a wrong result and a correctly handled exception separately**

An **exception** is a language mechanism for signaling and propagating a condition
outside the ordinary return path. Depending on handling and context, it may be
caught, propagated or lead to termination. A **crash** describes an abnormal
termination outcome; an exception does not necessarily crash a process.
Python's current [errors and exceptions tutorial](https://docs.python.org/3.15/tutorial/errors.html)
explains raising and handling. The broader JavaScript exception hierarchy belongs
to the linked language lesson.

Tested environment: **CPython 3.14.4 on Linux x86_64**, explicitly a pinned local
runtime rather than the current Python release. The relevant exception behavior
is also documented in the Python 3.15 reference checked on **2026-10-19**.
Save this complete example as `failure_words.py` and run
`python3 failure_words.py`. It uses only the standard language, with no packages.

Input rows are pairs of status and seat count. In this exercise, statuses are
`approved` or `pending`, and seats must be ordinary positive integers. The report
must sum approved seats; empty input must total zero. Each `def` defines a function;
`for` visits the pairs; `sum` totals selected values. `type(seats) is int` excludes
booleans as counts. The validation helper is shared so that the reporting difference
comes from selection rather than different input rules.

```python
def validate(rows):
    for status, seats in rows:
        if type(seats) is not int or seats <= 0:
            raise ValueError("seats must be a positive integer")


def report_v1(rows):
    validate(rows)
    return sum(seats for status, seats in rows if status == "approved")


def report_v2(rows):
    validate(rows)
    return sum(seats for status, seats in rows)


mixed = [("approved", 2), ("pending", 3)]
print("Earlier mixed result:", report_v1(mixed))
print("Changed mixed result:", report_v2(mixed))
print("Approved-only changed result:", report_v2([("approved", 2)]))
try:
    report_v2([("approved", 0)])
except ValueError:
    print("Invalid count rejected: ValueError handled")
print("Program continued")
```

Observed output:

```text
Earlier mixed result: 2
Changed mixed result: 5
Approved-only changed result: 2
Invalid count rejected: ValueError handled
Program continued
```

For the mixed input, the required total is 2. The changed function returns 5
because it includes the pending row's 3 seats. It raises no exception for that
wrong result. For approved-only input it returns the required 2 despite containing
the same missing-filter defect.

The zero-count call follows a different path. `raise` signals the specified invalid
input with `ValueError`; `except` handles that particular exception, and the final
line shows continued execution. Under this example's contract, that rejection is
expected behavior, not evidence that the report has a zero-count bug. An application
that promises a user-friendly rejection could still fail its broader contract if
it exposed an unexplained crash instead. Specify the observation boundary.

### 3) **Identify a regression from a change and a preserved expectation**

A **regression** is an adverse change to behavior that previously worked as
required. In the example, `report_v1` returns the required mixed-input result,
and the changed `report_v2` fails the same unchanged rule for the same input.
That provides a concrete regression comparison. The two functions are illustrative
before/after versions in one file, not historical production releases.

A changed result alone does not prove a regression. If the agreed requirement
changes to include pending reservations, a new result of 5 can be intentional.
If the requirement remains the same but there is no evidence of an earlier working
state, the current failure can still be reported without claiming it is new.
Record the version, input, environment and expected behavior before assigning a
regression label.

**Regression testing** checks for adverse consequences of changes, including effects
outside the directly edited behavior. It differs from merely confirming that a
specific reported defect was fixed; the detailed test-purpose comparison comes
later in this domain. Passing one repaired example does not establish an absence
of other regressions.

Practice: restore the `if status == "approved"` condition in `report_v2` and rerun.
Its mixed result becomes 2; the approved-only result and invalid-input handling
stay as shown. That checks this correction for these inputs. It does not establish
behavior for malformed row shapes, unknown statuses or an entire reporting service;
those are outside the example's stated input model and run.

### 4) **Common confusion**

A failure is not required before a defect can be found. Reviewing the missing
filter against the stated rule can reveal the code problem before running it.
Conversely, observing a discrepancy does not uniquely locate a defect: the expected
result, test input or environment could also need investigation.

“Handled” does not mean “correct.” Silently catching an exception and returning
a believable but incorrect total could conceal a failure. Here the handled
exception is correct because the rejection is explicitly required, not merely
because a handler exists. Keep bug count, exception count and failure count as
different observations rather than treating them as interchangeable measurements.

### 5) **Performance note**

A performance regression is an adverse performance change relative to a stated
baseline, workload, environment and measurement. It need not throw an exception
or produce an incorrect numeric result. These runs compare values and control
flow; they contain no latency or throughput measurements. Exception-handling costs
are runtime- and workload-dependent, so their presence alone does not establish
a performance problem or justify hiding a required rejection.

### 6) **Mentor note**

Ask the learner to locate the defect before running the program, then identify
which output demonstrates a failure. Ask why the approved-only output does not
remove the defect, and why the caught `ValueError` is expected. Finally, remove
the earlier-version observation and ask them to revise “regression” into a current
failure claim with missing history. A sound explanation separates evidence,
expectation and causal hypothesis without assigning blame to an unknown person.
