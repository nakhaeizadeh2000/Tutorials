## 1.2. Explain a change request and release narrative

“The green build is a safe patch; roll back if needed.” A release explanation
must connect the requested outcome to consumers, checks, exposure and recovery.
A reassuring adjective cannot supply those connections.

### 1) **Trace a requirement into a consumer-visible change**

Continue the fictional museum import setting, using this independent change packet.
No build, check or rollout was performed for the lesson.

| Record | Supplied information |
|---|---|
| Need | Researchers must distinguish queued, processing, failed and succeeded jobs |
| Existing contract | API returns `status: done` after import; notebook N1 requires that exact value |
| Candidate | Service S2 replaces `done` with `succeeded`; no compatibility alias |
| Label | Proposed service release 2.4.1 under an explicitly adopted SemVer public-API policy |
| Dependencies | Notebook N2 handles the new status but is not deployed |
| Checks | Unit checks pass; one staging import with N2 succeeds; no N1/S2 compatibility result |
| Placement | S2 deployed to one production replica; feature exposure disabled; no production import result |
| Data change | Candidate can write new normalized records; S1's ability to read them is unverified |
| Ownership | Lin owns rollout; Noor owns compatibility checks; Ivo decides acceptance |

The requirement describes observable job outcomes. It does not require removing
the old value immediately. Under the supplied contract, N1's reliance on `done`
makes the replacement a consumer-visible compatibility issue. The [SemVer owner](<../../../11 Version Control Releases and Dependencies/sections/3. Versions and compatibility/3.1. SemVer compatibility breaking changes and deprecation.md>)
explains the full scheme; the [2.0.0 specification](https://semver.org/)
requires an incompatible public-API change to receive a major increment in its
version-1+ rules. The proposed patch label conflicts with the stated policy.
Changing the number alone would not make N1 handle the new value.

Ask for a transition design or coordinated consumer migration and evidence for the
supported combinations. N2 existing in a repository does not establish its deployment.
Nor does one successful N2 staging case establish N1/S2 compatibility.

### 2) **Separate delivery and recovery evidence**

S2's deployment to one replica and disabled exposure describe different states.
The [delivery owner](<../../../14 Infrastructure Cloud and Delivery/sections/6. Change pipelines and exposure/6.2. Builds releases deployments rollouts rollbacks and feature flags.md>) owns these distinctions.
This packet supplies placement evidence, not an observed successful production
import or proof that every path is disabled. Read the flag's actual scope before
calling the candidate unreachable.

Rollback also has a boundary. Restoring S1 executable code would not necessarily
undo S2's written data, external effects or schema changes. Here new-record
readability is unverified. Before describing rollback as a reliable recovery plan,
identify the data states involved and obtain suitable compatibility/recovery evidence.
A flag can stop new exposure while leaving existing jobs to complete or fail;
its effect needs an explicit rule.

A useful readiness table separates the supplied states:

| Question | Current reading |
|---|---|
| Is a candidate built? | S2 exists with recorded passing unit checks |
| Does one new-client path work in staging? | One N2 import case is recorded successful |
| Is the old-client pairing verified? | No result supplied; explicit status contract conflicts |
| Is candidate code placed in production? | One replica, exposure stated disabled |
| Is production task success established? | No import result supplied |
| Can old code recover all new data? | Unverified |
| Who can accept the release? | Ivo; no acceptance supplied |

Do not combine these into a single green “ready” label. Some are established
facts, some contrary evidence and some unanswered questions.

### 3) **Write two accurate release explanations**

For a technical teammate:

> S2 changes the promised `done` value to `succeeded`, conflicting with N1 and the
> proposed SemVer patch signal. N2 passes one staging import, but N2 is not deployed
> and no N1/S2 check is supplied. S2 is on one production replica with exposure
> stated disabled. Noor owns compatibility evidence; Lin owns rollout. Verify S1
> reading new records before claiming rollback coverage. Ivo's acceptance is pending.

For a research stakeholder:

> The candidate adds clearer import outcomes, but current notebook compatibility
> remains unresolved. A new-notebook staging example succeeded; that is not evidence
> of a successful production rollout. Lin and Noor own rollout and compatibility
> follow-up, and Ivo has not accepted release. Recovery for newly written records
> still needs evidence before enabling the change.

Both preserve the same evidence. The stakeholder version explains the consequence
without requiring SemVer syntax. Neither blames the test owner or invents a schedule.

Variation: N2 is deployed to every supported client and documented support for N1
has ended through an authorized change. Reassess the consumer population; the prior
N1 obligation may no longer apply. Still verify new data recovery and release
acceptance. Separately, disabling exposure after one import does not undo that
import's recorded changes. Review its actual outcome and recovery needs.

### 4) **Common confusion**

Passing checks, satisfying requirements and accepting release are related but
separate. A patch label communicates a policy obligation rather than enforcing
compatibility. Deployment and exposure also differ, and neither automatically
provides a completed recovery procedure.

### 5) **Performance note**

No latency or throughput evidence is supplied. A status rename does not demonstrate
faster imports; a canary placement does not establish representative load behavior.
If timing bounds are requirements, include them in checks under a stated workload.

### 6) **Mentor note**

Ask the learner which old consumer demonstrates breakage and which observation
would support the rollback claim. Then change only the supported-client population.
A strong answer revises that obligation while retaining unrelated recovery and
acceptance questions.
