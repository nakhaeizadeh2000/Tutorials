## 1.1. Annotate an unfamiliar architecture proposal

A museum proposes a service for importing field-station observations. You have
not worked on it before. The task is to annotate what its proposal establishes,
what remains assumed and what evidence would change your assessment. Recognizing
a queue or database icon is only the beginning.

### 1) **Read purpose and boundaries before guarantees**

The [C4 diagram review checklist](https://c4model.com/diagrams/checklist) starts with
scope, element meaning and relationship labels. Use those questions on any sketch
without pretending an informal drawing follows formal notation. The existing
[architecture-model lesson](<../../../09 Programming Design and Architecture Language/sections/5. Models and representations/5.1. Domains entities value objects aggregates and architecture diagrams.md>) owns the
full distinction among model, deployment and observed behavior.

For an unfamiliar proposal, identify whether the artifact describes intended or
running behavior, who uses it and what a successful task means. Separate people,
applications, data stores and deployment instances. Then trace one action through
its boundaries. An omitted control is a question, not proof that it is absent.

### 2) **Annotate a cross-domain proposal**

This original fictional design packet is complete for the exercise; it describes
intent rather than a deployed system. No implementation is required.

| Artifact | Supplied statement |
|---|---|
| User outcome | Authorized researchers submit observations and later see whether each import succeeded |
| Client | Field notebook application sends an HTTPS import request with a researcher credential |
| API | NestJS with Fastify adapter validates input, checks the researcher's project permission, records a job and returns its identifier |
| Background path | API publishes the job identifier to a queue; a worker reads the uploaded object and writes normalized records |
| Data | Metadata database and object store; proposal does not specify coordination between job recording and publishing |
| Read path | Notebook requests job status; a replica is proposed for reads |
| Operations | Logs and an alert are proposed; no service target or recovery evidence |
| Summary | “HTTPS makes submissions authorized; queued means imported; replicas guarantee immediate status and backup; cloud means no operations” |

Annotate the summary at each boundary:

| Boundary | What the packet establishes | What it does not establish |
|---|---|---|
| Protected transport | HTTPS is proposed | Resource authorization from HTTPS alone |
| API permission | A project check is intended | Verified enforcement for each caller/project |
| Job response | Identifier for recorded work | Worker completion or normalized records |
| Record then publish | Two intended activities | Atomic coordination or recovery from partial failure |
| Worker delivery | A consumer is proposed | Duplicate-safe processing or a delivery guarantee |
| Replica read | A read copy is proposed | Immediate visibility of the latest worker update |
| Operations | Proposed telemetry | An SLO, successful restoration or elimination of operator duties |

The most immediate semantic correction is queued versus imported. The stated
user outcome requires a later result, so the response and status path need a
contract defining accepted, processing, failed and succeeded states. Those states
are proposed review questions, not new facts added to the packet.

The two-step record/publish path creates a coordination question: what happens if
recording succeeds but publishing fails? Ask how the system detects and repairs
that state, rather than declaring a named distributed pattern already implemented.
Likewise, a repeated delivery needs an operation identity and processing rule;
“queue” alone establishes neither losslessness nor exactly-once business effects.

A replica is not automatically a backup and may lag the write being queried.
Request the relevant consistency and recovery contract. Cloud placement also leaves
application permissions, configuration, observation and recovery responsibilities
to be identified. These are different gaps, not a reason to replace every design
choice before investigating.

### 3) **Prioritize review questions**

A useful annotation can conclude:

> This is a proposed asynchronous import design. Acceptance and worker completion
> are separate, and the required status outcome remains underspecified. First define
> the job-state contract and record/publish recovery. Confirm project authorization
> and duplicate handling, then specify read visibility, service indicators and recovery
> responsibilities. No measured speed or availability guarantee is supplied.

Priorities depend on the decision. For a permissions review, the caller/project
matrix comes first. For an operations handoff, recovery and status evidence may
be the immediate need. Explain that priority rather than reciting every acronym.

Variation: a supplied test now confirms one accepted job reached normalized records
and status succeeded. Credit that end-to-end case in its conditions. It does not
establish all authorization cases, record/publish failure recovery or immediate
replica visibility. Next remove the arrow labels: now even which participant
initiates each operation becomes unclear. Ask for the legend before tracing further.

### 4) **Common confusion**

A diagram is evidence about a described model, not automatic proof of deployment
or runtime guarantees. An accepted request, acknowledged message and successful
import are distinct outcomes. The familiar word “backup” also cannot be inferred
from the presence of any second copy.

### 5) **Performance note**

Asynchrony can move work outside a request while increasing time to final completion.
A short acceptance response does not establish a fast import. Measure acceptance
and completion at their own boundaries, with workload and errors. No service or
load experiment was run for this proposal.

### 6) **Mentor note**

Ask the learner for five annotations and one priority justified by the user outcome.
Then supply the one successful job trace. A strong response credits the evidence
without erasing other gaps and explains why the next observation is discriminating.
