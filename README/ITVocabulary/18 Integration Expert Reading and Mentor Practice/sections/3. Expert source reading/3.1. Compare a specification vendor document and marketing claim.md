## 3.1. Compare a specification vendor document and marketing claim

A colleague combines three links into one claim: “The managed queue is reliable,
so an HTTP 202 response guarantees our import completed.” All three sources can
be useful while that conclusion remains unsupported. Read their subjects before
ranking their authority.

### 1) **Identify authority subject and time**

A specification can define protocol meaning. Vendor documentation can describe a
product or recommended design under particular conditions. A product page can
communicate intended benefits and point toward detailed documentation and service
terms. None automatically supplies measurements of your application.

Use this source record, checked on 2026-10-21. These are actual pages; the museum
conclusion and exercise below are constructed.

| Source | Identity and time | Question it can help answer |
|---|---|---|
| [RFC 9110, section 15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3) | HTTP Semantics, published June 2022; fixed RFC publication | What does 202 Accepted mean? |
| [Azure asynchronous request-reply pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/asynchronous-request-reply) | Living architecture guidance, last updated 2026-03-30; retrieved 2026-10-21 | How can a design report acceptance and later status? |
| [Azure Service Bus product page](https://azure.microsoft.com/en-us/products/service-bus) | Living product presentation, retrieved 2026-10-21; no release version stated in the selected passage | What benefits does this product advertise? |

A retrieval date is not a publication date or product version. Record a displayed
revision when one exists, and leave it unknown when it does not. RFC publications
also have errata and status/update relationships worth checking for implementation
work. The earlier [document-reading owner](<../../../01 Reading and Using Technical Language/sections/2. Reading technical documents/2.1. Guides references specifications and release notes.md>)
explains source purposes; here you must compare their actual claims.

### 2) **Compare sources without flattening their claims**

RFC 9110 says 202 indicates acceptance for processing while processing is incomplete.
It leaves open whether the request will ultimately be acted on. That directly
contradicts treating this status as proof of completed import. The protocol gives
a response meaning, not a service-specific state machine or success guarantee.

The Azure architecture pattern describes returning an acceptance response and
providing a way to obtain later status. This is design guidance for separating
request acceptance from long-running work, not evidence that the museum system
implements those steps correctly. Its sample headers, status endpoint and backend
choices also should not be recast as universal requirements for every 202 response.

The Service Bus page promotes reliable messaging and asynchronous integration.
Those are claims about a messaging service's intended benefits. They do not turn
an unrelated API status into completed business processing, demonstrate the museum's
worker behavior or establish its end-to-end latency. For a real service selection,
follow the product's precise delivery, configuration, limit and service-term
references for the chosen offering. This exercise makes no purchase recommendation.

There is no need to call the sources contradictory. They address different layers.
The invalid step is silently moving a general messaging benefit into an HTTP
completion guarantee, then into a specific application's observed outcome.

### 3) **Write a sourced conclusion with open questions**

A defensible review can say:

> RFC 9110's 202 semantics establish acceptance with processing incomplete, not import
> success. Azure's pattern illustrates later status reporting, while the Service Bus
> page describes messaging benefits. Neither shows what our worker committed or how
> our API reports failure. Identify our accepted/status contract, message and job
> identity, delivery configuration and observed processing outcomes before making an
> end-to-end completion claim.

Now add a museum API contract, revision 3, stating that202 returns a job identifier
and a status URL. This supplies an application-specific promise consistent with
the protocol. It does not prove the implementation returns either value correctly
or that a particular job succeeded. Add an observed response and a later successful
job record to establish those separate boundaries in that case.

Practice a second claim: “The vendor pattern mentions scaling, therefore our import
will finish within 100 milliseconds.” A supported answer asks which operation the
number measures, which workload/configuration applies and where an applicable
bound or measurement is established. An introductory example duration in architecture
guidance is not an application's service-level objective or measured processing time.

Your source comparison should retain exact sections, scope, versions/dates and
unresolved questions. A long bibliography with no claim-to-source mapping is less
useful than three well-matched references and a precise limitation.

### 4) **Common confusion**

“Official” does not mean one page answers every question. A normative statement
can define a conforming behavior without proving a deployed implementation conforms.
A marketing page can accurately describe a product benefit while failing to support
a stronger claim invented by a reader. Evaluate the inference, not just the source brand.

### 5) **Performance note**

Acceptance latency and final processing duration are different measures. Neither
source type supplies a universal speed result, and no application benchmark was
performed here. Follow any actual performance claim to its workload, method,
configuration, measurements and limits before applying it elsewhere.

### 6) **Mentor note**

Ask the learner to attach each clause of the original claim to one source and
mark the unsupported transitions. Then provide the revision 3 contract and one
successful job. A good answer credits local promises and observations without
promoting them to universal reliability or timing guarantees.
