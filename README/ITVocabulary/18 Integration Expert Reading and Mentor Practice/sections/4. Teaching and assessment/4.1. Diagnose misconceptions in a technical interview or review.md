## 4.1. Diagnose misconceptions in a technical interview or review

A candidate expands every acronym but says a successful login proves access to
all records. Another forgets an expansion but correctly traces the resource
permission boundary. Which answer demonstrates the outcome you intended to assess?
Make that outcome explicit before judging performance.

### 1) **Elicit reasoning before judging knowledge**

Ask a question with enough context to have a defensible answer. “Is this system
reliable?” has no indicator, target or evidence. “Does this successful probe establish
that the stated import task met its target?” can reveal a specific reasoning gap
when you supply the probe and target.

[Carnegie Mellon's prior-knowledge guidance](https://www.cmu.edu/teaching/designteach/teach/priorknowledge.html)
encourages finding what learners already understand and where prerequisites are
missing. Use the answer to choose feedback. A request for a definition may indicate
an unfamiliar name; a wrong causal explanation may reveal a deeper misconception.
Do not infer inability, dishonesty or a job level from a single word or accent.

Permit clarification and state whether resources are allowed. For vocabulary
interpretation, looking up a protocol detail can be appropriate if the learner
then matches it to the artifact accurately. A memorization test and a review task
measure different things. Explain which you are conducting.

### 2) **Diagnose and repair a specific mental model**

Use these independent original fictional interview cards. No system behavior was
tested for them.

| Card | Evidence and learner answer | Likely reasoning gap to investigate |
|---|---|---|
| Access | A user authenticates; no record permission supplied. “They can read every project” | Identity confused with authorization |
| Import | API returns 202; no worker result. “All records are imported” | Acceptance confused with completion |
| Model | 95 routine/5 urgent cases; classifier flags none. “95% accuracy means urgent routing is good” | Aggregate correctness confused with positive-case detection |
| Release | Candidate deployed to one replica, exposure disabled. “Every user has the new feature” | Placement confused with exposure and population |

For the access card, ask what operation and resource the evidence permits. A model
answer is: “Authentication establishes identity under the stated mechanism; it
does not establish permission for every project. We need the caller/action/resource
rule and enforcement evidence.” If the learner merely forgot the term authorization
but gives this explanation, credit the reasoning.

Give feedback that repairs the inference: “You correctly identified a successful
login. The step from identity to all-project access has no permission evidence.
Consider one account allowed only project A: what would justify reading B?” This
is more useful than “Wrong, memorize authentication versus authorization.” Link
its [full owner](<../../../13 Security Identity and Privacy/sections/2. Identity and access/2.1. Identification authentication authorization and accounting.md>) for the underlying distinction.

For import, the model answer identifies accepted processing and asks for job status
or completion evidence. For urgent routing, the all-negative classifier misses all
five urgent cases: recall is zero despite 95% accuracy. For release, deployment
records placement; the actual flag scope and exposure evidence are needed. Each
answer identifies a missing boundary without inventing failure.

Now change only the access card: supply a policy permitting this caller to read
project B and a trace confirming that operation. Credit B access in that case;
all-project permission still does not follow. A learner who repeats “never trust
login” without incorporating the added evidence has memorized a warning rather
than repaired the model.

### 3) **Assess explanations with explicit criteria**

A **rubric** states what is assessed and describes evidence of different achievement
levels. [Carnegie Mellon's rubric guidance](https://www.cmu.edu/teaching/assessment/assesslearning/rubrics.html)
connects criteria, descriptions and performance levels. The following is an original
practice rubric, not a validated hiring instrument or universal seniority scale.

| Criterion | Needs another attempt | Adequate for this task | Strong transfer |
|---|---|---|---|
| Meaning in context | Expands names but merges boundaries | Explains the relevant distinction | Resolves an ambiguous meaning from the artifact |
| Evidence | Invents results or universal guarantees | Preserves supplied observations and unknowns | Selects evidence that could distinguish alternatives |
| Explanation | Gives a verdict without a reason | Connects observation to conclusion | Explains why a changed condition changes one conclusion |
| Feedback | Labels the person or recites a slogan | Names the incorrect inference and repair | Checks the learner's revised reasoning constructively |

Use each criterion separately. Do not average excellent terminology with fabricated
results and call the evidence dimension adequate. An answer can be strong in one
area and need another attempt in another. Record the specific revision needed,
such as “retain the successful login but withdraw all-project permission.”

Practice a follow-up for the model card: ask which five cases must appear in the
recall denominator. A sound answer identifies actual urgent cases and explains zero
detected out of five. Requiring only the acronym TP would miss the learning goal.
A second attempt with a changed positive class can assess transfer; state the new
convention clearly rather than using a trick.

### 4) **Common confusion**

A misconception is an incorrect model of a relationship, not any pause or unfamiliar
term. A technically correct answer can also be poorly explained. Diagnose those
separately so feedback addresses the actual gap. One short exercise does not prove
or disprove a person's overall engineering competence.

### 5) **Performance note**

Interview fluency does not measure application performance. For a speed claim,
ask for operation, workload and measurement evidence; do not reward a confident
optimization slogan. No learner study, hiring assessment or runtime benchmark was
executed here.

### 6) **Mentor note**

Have two reviewers independently assess an explanation using the practice rubric,
then compare the evidence behind any disagreement. Revise ambiguous criteria before
blaming the learner. Repeat with one changed card to see whether feedback changed
the reasoning rather than only the remembered wording.
