## 4.2. Build and teach a team glossary with canonical owners

A team glossary says “token: security; model: AI; done: shipped.” It is short, but
it will mislead readers of a parser trace, domain diagram or staging update. A
useful glossary maps a scoped meaning to its explanation and evidence rather than
forcing every occurrence of a word into one definition.

### 1) **Design entries around meaning and context**

A **canonical owner** is the primary full explanation for a scoped concept. Aliases
and related lessons point to that owner instead of repeating it. Ownership here
concerns teaching content, not authority over a production service. A word may
have several owners when its meanings genuinely differ.

An entry needs a recognizable term, context, brief meaning, precise owner and any
important local convention or source status. Not every entry needs a large template.
Choose enough information to prevent the actual confusion. An acronym's expansion
is useful navigation, but cannot replace an explanation of its role.

For example, “token” can mean an identity credential or an LLM tokenizer unit.
Keep those entries separate and use the sentence's context to select the meaning.
Likewise, “model” in a domain diagram and a fitted predictor refer to different
representations. The track's alphabetical term lookup is navigation; its linked
leaves remain the explanations.

### 2) **Resolve competing meanings without duplication**

Use this original fictional onboarding packet for the museum team:

| Local artifact | What a new teammate needs to understand |
|---|---|
| Security note | Researcher credential grants access only under project permission rules |
| AI draft note | Prompt budget counts tokens under the chosen tokenizer |
| Domain sketch | Observation entity keeps its identity when a description is corrected |
| Team policy P2 | “Done” means required checks and review complete; release acceptance is separate |
| Release note | Import job “succeeded” means normalized records committed under API contract revision 3 |

A small worked glossary can route those meanings:

| Entry | Brief context reminder | Full explanation or local authority |
|---|---|---|
| Access token | Credential in the identity discussion, not a unit of text | [Identity tokens](<../../../13 Security Identity and Privacy/sections/2. Identity and access/2.2. Principals credentials sessions tokens roles and permissions.md>) plus the applicable identity reference |
| LLM token | Tokenizer-specific input/output unit | [Model context](<../../../17 AI Machine Learning and Model Terminology/sections/3. Generative systems/3.1. Foundation models LLMs tokens prompts context windows and embeddings.md>) plus the selected model/tokenizer reference |
| Domain entity | Continuity of domain identity across attribute changes | [Domain identity](<../../../09 Programming Design and Architecture Language/sections/5. Models and representations/5.1. Domains entities value objects aggregates and architecture diagrams.md>) |
| Done, team P2 | Required checks/review complete in this team's stated policy | P2 is supplied fictional local authority; [completion vocabulary](<../../../16 Teams Product Work and Professional Communication/sections/4. Planning and progress/4.2. Dependencies blockers scope creep Definition of Done and handoffs.md>) explains the general distinction |
| Succeeded, import API revision 3 | Stated job-state outcome, separate from team completion | Supplied fictional API contract; [API contracts](<../../../07 APIs Protocols and Integration/sections/1. Interfaces and contracts/1.1. APIs endpoints routes operations and contracts.md>) explains the contract boundary |

The last two are not invented universal definitions. In an actual glossary, link
the real maintained policy/contract and record its status. Do not fabricate a policy
URL for this exercise. The exact revision matters: a later contract could change
which records are covered, while the general vocabulary stays useful.

A copied full definition in every onboarding document creates several places to
repair. Prefer one full owner with a contextual reminder and precise link. If
owners disagree, compare their scopes and authority. A team can decide a local
label, but that does not rewrite an external protocol or erase another valid
meaning. Preserve superseded records where history matters and direct current
readers to the adopted explanation.

### 3) **Teach and maintain the glossary**

A junior explains: “The API says succeeded, so the feature is done and released.
Tokens are how the AI authenticates.” Start by acknowledging the valid observation:
the API state says something about the job. Then repair the unsupported transitions:

> In revision 3, succeeded describes the job's normalized-record commit. P2 separately
> defines team completion, and release acceptance is another decision. Which evidence
> would show those two outcomes? Also, the prompt note counts LLM tokenizer units;
> the security note uses a credential meaning. Let's identify which note each token
> occurrence belongs to before explaining it.

This feedback targets the inference rather than the person. [Google's audience guidance](https://developers.google.com/tech-writing/one/audience)
supports adapting detail to the reader's task and familiarity. Use the previous
[assessment lesson](<4.1. Diagnose misconceptions in a technical interview or review.md>) for criteria and
changed-condition feedback rather than duplicating its rubric.

Now ask for a brief explanation to a researcher: “The import job succeeded under
its recorded data rule. That does not by itself announce a released feature.” For
an engineer, retain revision 3, the commit boundary and the policy distinction.
Both versions preserve meaning while changing detail.

Practice maintenance: P3 explicitly adds release acceptance to the team's definition
of done. Update that local entry and link the adopted P3, preserving P2 history.
Do not change the API's succeeded entry unless its own contract changes. Then give
the learner a new sentence, “The tokenizer used more tokens after the language
changed.” A sound explanation selects the representation meaning without mentioning
login. This tests use of context, not recall of the table order.

### 4) **Common confusion**

One canonical explanation per meaning does not require one meaning per spelling.
Nor does a glossary owner automatically decide local product policy. A short
reminder should help select the right explanation; it should not become a second,
slightly different full lesson that quietly drifts out of date.

### 5) **Performance note**

Glossary navigation has no direct runtime effect. Clarifying token meanings can
prevent a bad cost estimate, but a definition does not measure model use. Similarly,
changing the word done changes no deployment, data or latency by itself.

### 6) **Mentor note**

Ask the learner to produce three scoped entries and correct the junior's explanation
without copying entire owner lessons. Supply P3 afterward. Assess whether they update
only the local completion meaning, preserve history and still interpret the new
tokenizer sentence correctly. No team training was conducted for this lesson.
