## 2.1. Reconstruct an incident from conflicting messages

One person says “DNS is down,” another says “the API is fine,” and the user sees
“import failed.” They may describe different clients, times and operations. A useful
incident account reconciles those scopes before declaring one speaker wrong.

### 1) **Align observations before proposing causes**

Record who observed what, where, when and with which operation identity. A client
clock and service clock need an alignment basis before their displayed times become
a reliable ordering. A job identifier may join records about one import; a similar
timestamp alone may not. The existing [telemetry owner](<../../../15 Performance Observability and Reliability/sections/3. Telemetry and investigation/3.2. Logs metrics traces spans correlation and cardinality.md>)
explains correlation rather than treating it as causal proof.

[Google's troubleshooting chapter](https://sre.google/sre-book/effective-troubleshooting/)
connects observations, system understanding and hypotheses. It also separates
restoration from complete explanation. Here you will choose evidence, not operate
a real service or run diagnostic commands.

### 2) **Reconstruct a bounded incident account**

All records below are original fiction. Times are UTC and stipulated as aligned
unless explicitly marked otherwise. No real network, database or service was used.

| Time and source | Supplied observation |
|---|---|
| 12:00 notebook A | Its resolver returns a temporary lookup failure for `imports.example.invalid`; no connection attempt for this operation |
| 12:01 notebook B | Using a cached address, it connects to the intended API and completes TLS validation |
| 12:01 API | B's operation R7 passes its project permission check; a job row J7 commits; response is not observed by B |
| 12:02 notebook B | R7 times out waiting for response; UI displays “import failed” |
| 12:03 worker | J7 processing is recorded successful; write result contains 12 normalized records |
| 12:03 status service | A read replica returns J7 as queued; replica visibility delay for this update is recorded |
| 12:04 monitor | Successful health probes to one API endpoint; no end-to-end import or resolver coverage |
| Chat | “DNS down everywhere”; “health green, no incident”; “timeout proves nothing was saved”; “queued means the worker failed” |

The reserved `.invalid` name is a fictional identifier; do not attempt to resolve it.
Notebook A's observation stops at naming for that operation. It does not establish
a global resolver outage. B's cached address makes its successful connection
compatible with A's lookup failure. They did not exercise the same naming path.

B's connection and TLS validation establish those stages for its operation. They
are not proof of universal reachability or permission; the packet separately supplies
R7's successful project check. R7's timeout is an observation about the response
boundary. The committed J7 row contradicts “nothing was saved.”

The worker record supports processing success and 12 normalized records for J7.
The replica's queued result is stale relative to that recorded success, with an
explicit visibility delay supplied. It does not show worker failure. The health
probe covers one endpoint and omits the failed naming/status paths, so green health
can coexist with user-visible failure. The [incident owner](<../../../15 Performance Observability and Reliability/sections/6. Incident operations/6.1. Alerts incidents severity priority mitigation and remediation.md>)
explains why a monitor's state does not alone decide service impact or severity.

A defensible account is:

> Notebook A could not resolve the import host at 12:00. B reached the API via a
> cached address at 12:01; R7 passed its stated permission check and committed J7,
> but B did not observe a response and timed out. J7 later recorded processing
> success with 12 records. A replica still reported queued with recorded visibility
> delay. The health probe did not cover the naming or full import/status path.
> The causes of the lookup failure and missing response, broader impact and current
> recovery remain unresolved.

This preserves both failures and successes. It does not collapse all symptoms
into one cause or claim that eventual worker success gave B a successful user experience.

### 3) **Choose a discriminating next check**

For A, compare the affected resolver path and a relevant alternative under authorized
conditions; record time, client and answers. That can distinguish a client/resolver
scope from a wider naming issue. For R7, correlate response handling and connection
records with its operation identity rather than retrying the import as a diagnostic.
For J7, inspect the authoritative status and replica visibility evidence to assess
what the notebook should show after this observed state.

These are proposed investigations, not results or commands executed here. If
restoration is urgent, the responsible responders must choose actions with their
operational context, preserving evidence and controlling consequences. This lesson
supplies no authority or procedure to restart systems or bypass permission checks.

Variation: remove the J7 commit and worker records. B's timeout now leaves the
business outcome unknown; it does not prove success or failure. Ask for the operation
record before considering repeat submission. Next remove the stipulated clock
alignment. Preserve displayed timestamps while qualifying cross-source ordering;
the records cannot justify the same precise timeline without another alignment basis.

Practice: write a two-sentence stakeholder update. One supported answer is: “Some
clients cannot begin imports, while a separate submitted job completed but its user
saw a timeout and stale status. The scope, causes and recovery are not yet established;
responders need naming, response and authoritative-status evidence.” Do not claim
all users are affected or assign a severity number without the local criteria.

### 4) **Common confusion**

A correlation identifier helps join records; it does not explain why a response
was missing. A timed-out request may have committed work. A successful worker does
not establish a successful client response, and a stale status read is not automatic
evidence that the original write failed.

### 5) **Performance note**

Timeout configuration, response latency, processing duration and replica visibility
lag are different quantities. The packet's minute-resolution records do not provide
precise latency distributions or a bottleneck profile. No load or recovery-time
measurement was performed.

### 6) **Mentor note**

Ask the learner to label the last established boundary for A, R7, J7 and the probe.
Then remove commit records or clock alignment. Assess whether they narrow only
the dependent conclusions and choose an observation that could distinguish causes.
A confident one-cause story without that evidence should not pass.
