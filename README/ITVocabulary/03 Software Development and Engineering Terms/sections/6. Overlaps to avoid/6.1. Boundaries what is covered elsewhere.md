## 6.1. Boundaries: what is covered elsewhere

This domain names engineering work — changes, reviews, shipping, and code health. It deliberately stops at these borders:

1. **Git mechanics** (commands, branching strategies like GitFlow/trunk-based, rebasing how-to, hooks) — the future Git track owns the tool; this domain owns one line per word ([1.1](<../1. Change words/1.1. Repo branch commit and merge.md>)).
2. **CI/CD pipelines and DevOps practice** (writing workflows, runners, secrets, progressive delivery operation) — [Domain 06 Security Cloud and DevOps Vocabulary](<../../../06 Security Cloud and DevOps Vocabulary/README.md>). The *words* (build, pipeline, canary) stay here ([2.1](<../2. Ship words/2.1. Build test release and deploy.md>)); operating them lives there.
3. **Testing depth** (writing unit/integration/e2e suites, mocking, coverage strategy) — the future Testing track; this domain names the test levels and their cost-per-catch only.
4. **Agile process vocabulary** (sprints, velocity, story points, roles) — [Domain 07 Teamwork Agile and Interview Vocabulary](<../../../07 Teamwork Agile and Interview Vocabulary/README.md>); review-turnaround as a metric is mentioned here ([1.2](<../1. Change words/1.2. Pull request review and conflicts.md>)), process ownership lives there.
5. **Environments and infrastructure** (localhost/staging/prod, cloud failure boundaries) — [Domain 02](<../../../02 Hardware Infrastructure and Platforms/README.md>); releases travel through those environments, defined there not here.

If you find yourself writing `git` commands, YAML pipelines, or test code inside this domain — stop; name the concept in one line, link the neighbor that owns the practice, and move on.
