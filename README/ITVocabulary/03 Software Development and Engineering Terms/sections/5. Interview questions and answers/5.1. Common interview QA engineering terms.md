## 5.1. Common interview Q&A: engineering terms

### 1) **Git vs GitHub**

*The opener that filters bluffing — answer in one contrast sentence.*

- **Q**: "What's the difference between Git and GitHub?"
- **Model answer**: "Git is the distributed version-control tool on my machine — repos, branches, commits, merges. GitHub is a hosting platform *for* Git repos, adding pull requests, reviews, CI, and issue tracking. I commit with Git; I collaborate on GitHub." (from [1.1](<../1. Change words/1.1. Repo branch commit and merge.md>))
- **What they are really testing**: whether your mental model separates tool from platform — follow-ups ("what happens when GitHub is down?") reward people who know local Git keeps working.

### 2) **Merge vs rebase**

*Vocabulary-level answer with honesty markers — name the trade, defer the mechanics.*

- **Q**: "Merge or rebase — which do you prefer?"
- **Model answer**: "Merge commits preserve true history — branches and all — at the cost of noise; rebasing replays my commits onto the tip for a linear story, at the cost of rewriting history, so never on shared branches. I follow the team's convention: rebase private feature branches, merge to main. The command-level details I'd verify in the docs rather than recite."
- **What they are really testing**: judgment over trivia — "it depends on branch-sharing" outscores any absolute rule, and the honesty marker ("I'd verify") reads as seniority, not weakness.

### 3) **CI/CD in one paragraph — plus rapid-fire drills**

*What the letters promise.*

- **Q**: "What does CI/CD mean in practice?"
- **Model answer**: "CI — every merge to main builds and tests automatically, so integration happens daily instead of release-week. CD is delivery (an artifact is always releasable; a human releases) or deployment (releases go out automatically). Our pipeline: commit → build → unit → integration → staging → prod, with flags separating deploy from release." (from [2.1](<../2. Ship words/2.1. Build test release and deploy.md>))
- **Rapid-fire drills** (one line each):
  - *Commit?* — "Atomic snapshot with a why-message — the currency of collaboration."
  - *Pull request?* — "A merge proposal with its conversation — diff, checks, review, approval."
  - *Deploy vs release?* — "Deploy lands bits somewhere; release puts functionality in users' hands."
  - *Tech debt?* — "A shortcut with carrying cost — deliberate ones get tickets, accidental ones get discovered."
  - *Refactor?* — "Restructuring with behavior proven unchanged — green tests before and after."
  - *LGTM / nit?* — "Approval vs trivia-level comment the author may take or leave."

### 4) **Common confusion**

- "I must pick a side on merge-vs-rebase" — interviewers reward convention-awareness ("depends on sharing, team decides") over zealotry.
- "CI/CD answers need tool names" — Jenkins/GitHub Actions name-dropping without the concept scores zero; the paragraph above with zero tool names scores full.
- "Vocabulary answers should be exhaustive" — three crisp sentences beat ten hedged ones; offer depth ("happy to go deeper on any") instead of dumping it.

### 5) **Mentor note**

Drill candidates on *force-labeling* under pressure: after each answer, ask "was that blocking or a nit?" The habit transfers directly to review quality — engineers who qualify their statements in interviews write qualified, mergeable review comments on the job.
