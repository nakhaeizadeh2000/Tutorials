## 1.1. Repo, branch, commit, and merge

### 1) **Repo holds history, branch holds a line of work**

**Definitions** — A *repo* (repository) is a project plus its full change history — every version that ever existed, browsable. A *branch* is a parallel line of work: an independent draft of the future that diverges from `main` and later reunites with it.

- **What problem it solves**: without these words, teams describe changes as files ("I edited checkout.js") instead of as history ("my `coupon-discount` branch, three commits ahead of main"). Files describe *state*; branches describe *intent over time* — and intent is what reviewers review.
- **Modern guidance** — name the branch for the work, not the author: `feat/coupon-discount`, `fix/login-timeout`. Short-lived, single-purpose branches merge in days; a branch older than a sprint is a second codebase wearing a costume — rebase or split it before it rots.

```text
# Bad: state-talk (no history, no intent)
"I changed checkout.js and utils.js — can you look?"

# Good: history-talk (work unit is named and placed)
"PR from feat/coupon-discount — 3 commits on top of main,
 touches checkout + utils. Review the branch, not the files."
```

### 2) **Commit is a snapshot with a message**

A *commit* freezes the project at one moment — a complete, revertable snapshot — with a *message* explaining why. Commits are the currency of collaboration: small, atomic (one logical change), and message-led.

- **Why it matters (maintainability, debugging)**: future debugging reads history, not code — `git blame` and `bisect` walk commits to find which change broke what. A commit titled "fix stuff" touching twelve files is a dead end for every future investigator, including its author in three months.
- **Modern guidance** — one logical change per commit, message in imperative mood ("add coupon validation", not "added" or "adds"), body explaining *why* when the reason isn't obvious. Squash noise ("wip", "typo") before merging so public history reads like decisions, not keystrokes.

### 3) **Merge unites lines of work**

*Merging* combines branches back together. The three names you will hear: *fast-forward* (no divergence — main simply advances), *merge commit* (an explicit union node preserving both histories), *rebase* (replay your commits onto the new tip for a linear story).

- **What problem it solves**: every team argues about history shape eventually, and the argument is really about trade-offs — merge commits preserve truth (what actually happened, branches and all) at the cost of noise; rebasing buys a clean linear story at the cost of rewriting history (never on shared branches).
- **Modern guidance** — naming level only here: know what each word promises so you can follow the team's convention discussion. How to execute them — commands, conflict flows, branch strategies — belongs to the future Git track, linked from [6.1](<../6. Overlaps to avoid/6.1. Boundaries what is covered elsewhere.md>), not taught here.

### 4) **Common confusion**

- "Repo means GitHub project" — the repo is the history store (local `.git` included); GitHub is one *host* for repos, not the repo itself.
- "Commit means save" — saving is private and continuous; committing is publishing a history entry colleagues will read — different bar, different message.
- "main vs master" — `main` is the current conventional default branch name; `master` is its retired predecessor. Same role, new name — update scripts and habits accordingly.

### 5) **Mentor note**

Review commit messages before code: a week of "rewrite this message to say why" teaches change-thinking faster than any branching lecture. Juniors who write good messages start making atomic commits unprompted — the message bar drags the change discipline up behind it.
