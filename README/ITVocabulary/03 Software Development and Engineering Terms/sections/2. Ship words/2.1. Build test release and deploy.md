## 2.1. Build, test, release, and deploy

### 1) **Build turns source into runnable**

**Definitions** — *Build* transforms source into an *artifact* (the runnable output: binary, bundle, container image). *Compile* (language → machine code), *bundle* (many modules → few files), *package/image* (app + dependencies → shippable unit) are the three build flavors you will hear.

- **What problem it solves**: "just run the code" stops working the moment more than one machine is involved — every environment needs the identical artifact, built once, promoted unchanged. "Works from source on my laptop" is not an artifact; the build makes the thing environments can actually share.
- **Modern guidance** — build once, deploy many: the artifact tested on staging must be bit-identical to the one reaching prod (same hash, same tag). Rebuilding per environment reintroduces exactly the drift staging exists to eliminate.

```text
# Bad: artifact-free shipping (each environment gets a surprise)
"Deploy main to prod — Jenkins rebuilds it there, should be fine."

# Good: one artifact, promoted unchanged
"Image api:2.14.1 (sha:9f3c…) green on staging — promoting
 the same digest to prod. No rebuild between environments."
```

### 2) **Test gates the pipeline**

*Unit* tests check one function in isolation (fast, many); *integration* tests check pieces together (API + DB); *e2e* (end-to-end) tests drive the real system like a user (slow, few, brittle). The *pipeline* runs them in that order — cheap gates first.

- **Why it matters (correctness, velocity)**: the test pyramid exists because each level has a different cost-per-catch — units catch logic slips in seconds, e2e catches wiring failures in minutes. Teams with only e2e wait 40 minutes to learn a typo; teams with only units learn their wiring is broken from users.
- **Modern guidance** — name the level in every test discussion ("this needs an integration test — units can't see the query"), keep the pipeline's cheap gates fast enough to run per-commit, and treat flaky tests as broken gates: quarantine or fix within the sprint, never normalize red.

### 3) **Release decides, deploy executes**

*Deploy* lands bits somewhere (staging, prod, a canary slice). *Release* makes functionality available to users. *Feature flags* split the two — deploy dark, release by flipping; *canary*/*blue-green* are release shapes (fraction of users first, or parallel environments with a cutover).

- **Why it matters (risk, honesty)**: conflating the words hides risk — "deployed Friday" sounds done while users see nothing (unreleased) or everyone sees an untested change (released without canary). Separating them gives teams independent levers: deploy often (small, safe), release deliberately (measured, reversible).
- **Modern guidance** — announce releases, not deploys ("releasing coupons to 5% — watching error budget, full rollout tomorrow"); keep every release reversible within minutes (flag flip, instant rollback). If reverting takes longer than a coffee, the release process — not the code — is the risk.

### 4) **Common confusion**

- "CI/CD means automatic deploys to prod" — CI (continuous integration: merge + test often) is near-universal; CD splits into *delivery* (artifact always releasable, human releases) vs *deployment* (automatic). Know which your team practices before promising either.
- "More e2e means more safety" — past a point, e2e suites buy flakiness, not safety; confidence comes from the pyramid balance, not the top layer's size.
- "Deploy equals release" — flags, canaries, and staged rollouts exist precisely because the industry learned to separate them.

### 5) **Mentor note**

Draw the team's actual path — commit → build → unit → integration → staging deploy → e2e → prod deploy → release — on one whiteboard, with owners and minutes per stage. Juniors who see the whole conveyor stop asking "is it done?" (meaningless mid-pipe) and start asking "which stage?" — the vocabulary installs the mental model, which installs the patience for process.
