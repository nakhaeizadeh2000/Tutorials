## 3.1. Refactor, tech debt, legacy, and cleanup

### 1) **Refactor changes shape, not behavior**

**Definition** — *Refactoring* restructures code without changing what it does: rename, extract function, split module — same inputs, same outputs, better shape. Verified by running the unchanged test suite before and after: green → green means refactor; red → red means you broke it; no tests means you cannot prove it was a refactor at all.

- **What problem it solves**: codebases rot by accretion — each feature bolts onto the last one's shape until change becomes excavation work. Refactoring repays that friction continuously, keeping the code's shape aligned with what it actually does now rather than what it did three pivots ago.
- **Modern guidance** — refactor in the same breath as touching code (boy-scout rule: leave the campsite cleaner), in small behavior-preserving steps, never mixed into feature PRs. A PR that "adds coupons and refactors checkout" is two reviews wearing one title — split them so the refactor reviews as pure shape-change.

```text
# Bad: shape-change disguised (reviewers can't verify behavior)
PR "add coupon expiry" also renames 40 functions and moves
 6 files — behavior diff hidden inside the noise.

# Good: refactor separated and provable
PR 1 "refactor: extract pricing module (no behavior change,
 tests green before+after)". PR 2 "feat: coupon expiry
 on the new module". Each reviews in minutes.
```

### 2) **Tech debt is borrowed time with interest**

*Tech debt* is a shortcut taken now, paid later with *interest* — every future change near the shortcut costs extra. *Deliberate* debt ("ship Friday, clean up ticket DEBT-44 Monday") is a tool; *accidental* debt (unknown unknowns, skill gaps, deadline panic) is a discovery.

- **Why it matters (velocity, morale)**: unnamed debt compounds silently until the team moves at half speed and nobody can say why. Named debt with tickets, owners, and interest estimates becomes plannable work — "checkout debt costs ~2 days per feature; pay down in Q4" is a business conversation; "the code sucks" is a feeling.
- **Modern guidance** — log every deliberate shortcut as a debt ticket at the moment of taking it (what, why, estimated interest), budget ~20% of capacity for paydown, and never let debt tickets age without re-triage — stale debt entries are how teams normalize the swamp.

### 3) **Legacy means inherited, not bad**

*Legacy code* is code inherited without its context — authors gone, reasons unrecorded, tests thin. It usually *works* (it survived production); what it lacks is a living theory of itself. *Cleanup* (dead-code removal, dependency pruning) and *rewrite* (rebuild from scratch) are the two responses — with opposite risk profiles.

- **History in one paragraph**: every generation calls the previous one's stack "legacy" — mainframes, then client-server, then monoliths, now early microservices. The word tracks *distance from current fashion*, not quality; contempt for legacy is how teams volunteer for rewrites that reintroduce the bugs the legacy had already fixed.
- **Modern guidance** — respect-then-characterize: cover legacy with characterization tests (record what it does), change behind those tests, prefer strangler-fig migration (new system gradually replaces old at the edges) over big-bang rewrite. Rewrite only when the platform itself is unmaintainable — and budget double, because the second-system effect is real.

### 4) **Common confusion**

- "Refactor means improve the code" — improvement without behavior-preservation proof is rewriting; the discipline (green→green) is the definition, not the aspiration.
- "Tech debt is just bad code" — bad code with no shortcut history is just bad code; debt implies a *borrowing decision* (or discovery) plus carrying cost — track it like one.
- "Legacy should be rewritten" — working legacy encodes years of fixed bugs; rewrites discard that knowledge. Strangle, don't nuke.

### 5) **Mentor note**

Normalize debt-talk in planning: ask "what shortcut are we taking, and what's the ticket?" at every estimate review. Juniors trained to name debt out loud stop hiding shortcuts (which is where accidental debt breeds) and start pricing them — turning the team's most taboo topic into ordinary backlog math within a quarter.
