## 1.1. Protocol, packet, and address

### 1) **Protocol is the agreed manners**

**Definition** — A *protocol* is a set of rules both ends of a conversation follow so bits become meaning: who speaks first, what each message looks like, what happens on errors. *TCP* (reliable, ordered delivery), *UDP* (fast, fire-and-forget), and *IP* (addressing and routing) are the three names underneath nearly everything.

- **What problem it solves**: without shared rules, two programs exchanging bytes hear noise. Protocols turn that noise into guarantees you can build on — "TCP delivers every byte, in order" lets application developers stop thinking about lost packets entirely.
- **Modern guidance** — reach for the name that matches the need: TCP for correctness (files, APIs, pages), UDP where lateness beats loss (live video, games, DNS itself). Saying "we use UDP because freshness matters more than completeness" is a design rationale in one sentence.

```text
# Bad: protocol-blind (hides the real trade-off)
"The stream glitches — let's increase the buffer."

# Good: protocol named, trade-off visible
"Stream runs over TCP — retransmits stall live playback.
 Glitches are head-of-line blocking, not capacity.
 Fix: switch to UDP-based transport or accept the delay."
```

### 2) **Packet is the envelope**

A *packet* bundles data with its delivery info: a *header* (source, destination, sequence) plus a *payload* (your bytes). Networks cap packet size (*MTU*), so big things travel as many small packets, reassembled at the far end.

- **Why it matters (debugging, performance)**: "packet loss" (envelopes vanishing — congested or faulty links) and "fragmentation" (oversized packets split and slow) are the two words behind most "the network is flaky" mysteries. Loss asks for retransmission or a better path; chronic loss asks for the provider, with numbers attached.
- **Modern guidance** — quote loss as a rate over time ("0.8% loss to db-primary over 10 min"), never as a feeling. And keep payloads comfortably under common MTUs (~1,400 bytes for VPN-tunneled paths) when you control message size — preventing fragmentation beats diagnosing it.

### 3) **Address tells where, port tells whom**

An *IP address* names a machine on a network (`203.0.113.7`, or IPv6's longer form); a *port* names the program on that machine (`:443` HTTPS, `:5432` Postgres). Together they are the complete delivery address: where, plus whom.

- **What problem it solves**: "can't reach the service" splits instantly once the address is two-part — wrong IP means routing/DNS trouble; right IP with refused port means the program isn't listening (down, misconfigured, firewalled). One address, two diagnoses, zero guessing.
- **Modern guidance** — report both halves always ("`db-primary:5432` refuses connections; host pings fine") and learn the famous ports cold (80/443 web, 22 SSH, 5432 Postgres, 6379 Redis, 27017 Mongo). "Connection refused on the right port" is the most informative six words in network debugging.

### 4) **Common confusion**

- "Protocol means HTTP" — HTTP is one application protocol riding atop TCP/IP; the word covers every layer's rulebook, not just the web's.
- "More bandwidth fixes packet loss" — loss is envelopes vanishing, not a narrow pipe; a fatter pipe with the same faulty link loses the same fraction.
- "IP address identifies a person" — it identifies a network attachment point, often shared (NAT) or rotated (DHCP); attribution needs far more than an address.

### 5) **Mentor note**

Teach juniors the three-question network triage: *which protocol* (what guarantees hold?), *what do the packets say* (loss rate? size?), *which half of the address fails* (where vs whom)? Three answers locate virtually every connectivity ticket — install the reflex with real `ping`/`curl` output, not diagrams.
