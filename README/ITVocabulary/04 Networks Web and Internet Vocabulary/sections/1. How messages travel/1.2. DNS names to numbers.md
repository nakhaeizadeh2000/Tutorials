## 1.2. DNS: names to numbers

### 1) **DNS is the internet's phone book**

**Definition** — *DNS* (Domain Name System) translates human names (`api.example.com`) into IP numbers machines route to. Resolution walks a hierarchy: your *resolver* asks root → top-level domain (`.com`) → authoritative server for the zone, caching each answer along the way.

- **What problem it solves**: humans remember names, routers need numbers, and both change independently — DNS is the indirection layer letting either move without breaking the other. New server IP? Update one record; every name pointing at it follows silently.
- **Modern guidance** — when "the site is down for some users", check DNS before code: stale caches, expired domains, and mis-edited records produce exactly the partial-outage pattern that looks like application failure. `dig`/`nslookup` output belongs in the first five minutes of any reachability investigation.

```text
# Bad: DNS-blind (blames the app for a naming failure)
"Prod is down — roll back the release! (For users whose
 resolvers still hold the OLD record pointing at the
 decommissioned IP. The release is innocent.)"

# Good: DNS checked first, blast radius visible
"api.example.com resolves to the new IP (93.184…) from here,
 but 1.1.1.1 still serves the old A record (TTL 3600, expires
 in ~40 min). Partial outage, self-healing — hold the rollback."
```

### 2) **Records are entry types**

An *A record* maps a name to an IPv4 address (AAAA for IPv6); a *CNAME* aliases one name to another ("www → apex"); an *MX* record routes mail. Each answers a different question — address, alias, mail-exchange.

- **What problem it solves**: record types are the vocabulary of every DNS change request — "point staging at the new cluster" means editing an A record; "www should follow the apex" means a CNAME. Naming the record type turns vague tickets into executable edits.
- **Modern guidance** — prefer CNAMEs for things that move (services behind load balancers, SaaS endpoints) and A records for stable apexes; keep TTLs short (300s) before planned moves, long (hours) in steady state. The TTL is part of the change plan, not an afterthought — set it *before* migration day.

### 3) **Cache and TTL explain staleness**

*TTL* (time-to-live) tells resolvers how long to cache an answer. "DNS propagation delay" is mostly cache expiry, not travel time — the new record is live everywhere instantly; old answers linger until their TTL dies at each cache.

- **Why it matters (incidents, launches)**: every DNS change has two phases — instant publication plus TTL-long convergence. Teams that forget the second phase announce migrations as done while half the planet still resolves the old address, then debug phantom "it works for me" splits for hours.
- **Modern guidance** — plan changes as publish-then-wait: lower TTL days ahead, change the record, wait out the old TTL, verify from multiple resolvers/geographies, then restore TTL. Announce completion after convergence, never after publication.

### 4) **Common confusion**

- "DNS propagates slowly" — publication is instant; caches expire on TTL schedule. Lower TTLs *before* you need speed.
- "CNAME at the apex is fine" — bare domains traditionally can't be CNAMEs (it conflicts with other required records); providers offer alias/ANAME workarounds — know which yours uses.
- "DNS is only for websites" — service discovery, mail routing, verification tokens (SPF/DKIM), and VPN endpoints all ride DNS; "DNS issue" can break email while the site stays green.

### 5) **Mentor note**

Make juniors resolve names by hand until boring: `dig +trace` one domain, read the delegation chain aloud. Anyone who has watched a resolver climb root → TLD → authoritative will never again say "DNS is down, the internet is broken" — they will say which level failed, which is the difference between a ticket and a tantrum.
