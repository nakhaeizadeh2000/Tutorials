## 4.1. Networking vocabulary checklist (mental models mentors insist on)

### 1) **Name the leg**

DNS, connection, or server work — in every slowness or reachability report (from [1.1](<../1. How messages travel/1.1. Protocol packet and address.md>), [1.2](<../1. How messages travel/1.2. DNS names to numbers.md>)).

- **Check yourself**: "DNS resolves in 20ms, TCP connects in 40ms, server takes 1.7s" — three legs, one culprit, zero debate. Reports without leg timings invite three teams to blame each other for a week.
- **Bad habit to break**: "the network is slow" — the single most expensive sentence in debugging; it names no leg, aims no fix, and pages everyone.

### 2) **Name the speed word correctly**

Latency vs bandwidth — with numbers, every time (from [2.2](<../2. Web talk/2.2. Latency vs bandwidth and timeouts.md>)).

- **Check yourself**: "p99 latency 1.8s, bandwidth 80% idle" — delay problem, not width problem. Any proposal mentioning the wrong axis gets returned for re-measurement before discussion.
- **Bad habit to break**: buying bandwidth for latency problems (and vice versa) — the industry's most reliably wasted purchase order.

### 3) **Name the outcome class**

2xx/4xx/5xx — whose fault before whose fix (from [2.1](<../2. Web talk/2.1. HTTP requests verbs and status codes.md>)).

- **Check yourself**: "POST /charges → 422, caller omitted email" — caller fault, caller fix, no incident. "→ 500 since 14:20" — owner fault, owner paged. First digit first, details after.
- **Bad habit to break**: reading bodies before classes — ten minutes of JSON archaeology to learn what the first digit said in one glance.

### 4) **Common confusion**

- "Checklists are for outages only" — the same three names (leg, speed word, outcome class) accelerate everyday debugging, code review of networking code, and interview answers alike.
- "This much precision takes too long" — three nouns add seconds to a report and subtract hours from the investigation; the ROI is absurd.

### 5) **Mentor note**

Reject leg-free, unit-free, class-free network reports the way linters reject unused variables — automatically and without apology. A team that cannot describe a failure in leg + speed-word + outcome-class cannot fix it faster than by luck, and luck is not a process.
