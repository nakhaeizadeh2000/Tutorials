## 6.1. Boundaries: what is covered elsewhere

This domain names network conversations — messages, names, requests, and speed. It deliberately stops at these borders:

1. **Packet/socket mechanics** (TCP handshakes, TLS negotiation, raw sockets, packet capture analysis) — future Networks/System tracks own the machinery; this domain owns the envelope vocabulary ([1.1](<../1. How messages travel/1.1. Protocol packet and address.md>)).
2. **API design depth** (REST resource modeling, GraphQL schemas, auth schemes like OAuth2 flows) — the future API Design track; verbs and status codes stay here as words ([2.1](<../2. Web talk/2.1. HTTP requests verbs and status codes.md>)), designing with them lives there.
3. **Ops networking in practice** (configuring load balancers, CDN rules, firewall policies, observability) — [Domain 06 Security Cloud and DevOps Vocabulary](<../../../LOG.md>) (planned; curriculum in this track's LOG — link upgraded to the domain README when it lands) and future Cloud tracks; the vocabulary seeds (region, instance, timeout) are planted in Domains 02 and 04.
4. **Data formats on the wire** (JSON, encodings, serialization trade-offs) — Domain 05 Data Databases and AI Vocabulary (planned, see LOG) for data words; byte/unit foundations stay in [Domain 01](<../../../01 Core IT Concepts and Professional Jargon/README.md>).
5. **Environments and deployment** (where requests land — localhost/staging/prod) — [Domain 02](<../../../02 Hardware Infrastructure and Platforms/README.md>); this domain names the trip, Domain 02 names the destinations.

If you find yourself configuring a load balancer, modeling an API, or reading packet captures inside this domain — stop; name the concept in one line, link the neighbor that owns the practice, and move on.
