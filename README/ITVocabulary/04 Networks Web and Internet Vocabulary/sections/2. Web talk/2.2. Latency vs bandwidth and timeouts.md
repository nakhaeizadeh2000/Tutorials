## 2.2. Latency vs bandwidth, timeouts

### 1) **Latency is delay, bandwidth is width**

**Definitions** — *Latency* is how long one round-trip takes (milliseconds — distance + hops + processing). *Bandwidth* is how much data fits per second (Mb/s — pipe width). A video call needs low latency (freshness); a backup needs high bandwidth (volume); neither substitutes for the other.

- **What problem it solves**: "the network is slow" prescribes nothing — upgrading bandwidth for a latency problem (chatty protocol, distant region) spends money to keep the exact same delay. Naming the right speed word aims the fix: latency problems move work closer (region, cache, fewer round-trips); bandwidth problems widen the pipe (or shrink the payload).
- **Modern guidance** — measure both, quote both: "p99 latency 1.8s to ap-south (chatty: 14 sequential calls), bandwidth 900 Mb/s spare". The moment both numbers sit side by side, the fix usually announces itself — and "slow" retires from your vocabulary.

```text
# Bad: speed-word soup (prescribes the wrong purchase)
"App feels slow — upgrade our bandwidth."

# Good: delay vs width separated, fix aimed
"Bandwidth 80% idle; latency 1.8s from 14 sequential API calls.
 Fix: batch the calls (fewer trips), not a fatter pipe."
```

### 2) **Timeout bounds the wait**

A *timeout* caps how long you wait for an answer before giving up — per attempt, per connection phase, per whole operation. Without one, a hung dependency hangs you: threads pile up, queues grow, and one slow downstream cascades into your outage.

- **Why it matters (resilience, correctness)**: timeouts convert unbounded failure into bounded failure — "payment calls fail fast after 3s" instead of "checkout threads exhaust and everything 503s". Every cascading outage postmortem contains a missing or infinite timeout somewhere in the chain.
- **Modern guidance** — set timeouts at every boundary (connect, read, total), sized from measured p99s plus headroom — never copied from examples. Too short amputates healthy-but-slow calls; too long lets failures cascade; "no timeout" is always wrong, in every language, at every layer.

### 3) **Retry and backoff handle failure**

*Retry* re-attempts a failed call; *backoff* spaces attempts increasingly (1s, 2s, 4s…); *jitter* randomizes the spacing so fleets don't pulse together. Retry only what is safe to repeat (idempotent verbs, or guarded by idempotency keys) — otherwise retries manufacture duplicates.

- **Why it hurts when rude (thundering herds)**: a fleet retrying instantly and simultaneously turns one failure into a self-inflicted DDoS — the recovering service drowns in synchronized retry waves just as it gasps back up. Backoff + jitter converts that hammering into a gentle ramp the service can absorb.
- **Modern guidance** — retry with a budget (max attempts + total deadline), back off exponentially with jitter, and never retry 4xx (caller fault — repeating the same wrong call is just load with extra steps). Log every retry at debug, alert when retry *rate* climbs — rising retries are the earliest warning of downstream trouble.

### 4) **Common confusion**

- "High bandwidth means low latency" — a cargo plane has enormous bandwidth and terrible latency; a motorcycle courier is the reverse. Different axes, different fixes.
- "Timeouts cause failures" — timeouts *reveal* failures boundedly; the failure already happened, the timeout just refuses to wait forever for recovery.
- "Retrying always helps" — retries help transient faults on idempotent operations; they amplify overloads, duplicate non-idempotent writes, and mask root causes when unbounded.

### 5) **Mentor note**

Ban "slow" from incident vocabulary the way you ban "broken": require latency-number + bandwidth-number + which-leg before theories. Juniors trained to open with "1.8s p99, pipe idle, 14 sequential calls" debug like seniors within months — because the measurement habit *is* the senior habit, and the words are just its handle.
