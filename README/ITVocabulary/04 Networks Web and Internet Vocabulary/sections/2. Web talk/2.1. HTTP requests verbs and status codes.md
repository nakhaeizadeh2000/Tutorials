## 2.1. HTTP: requests, verbs, and status codes

### 1) **Request asks, response answers**

**Definition** — *HTTP* (Hypertext Transfer Protocol) is the web's conversation format: a *request* (method + URL + headers, optional body) earns a *response* (status code + headers, optional body). *HTTPS* is HTTP inside a TLS-encrypted channel — same conversation, sealed envelope.

- **What problem it solves**: every web interaction — page loads, API calls, webhooks — is this shape. Reading one request/response pair (browser DevTools → Network tab) demystifies any integration: what was actually asked, what actually came back, and where the two diverge from expectations.
- **Modern guidance** — debug with the pair, not with guesses: reproduce, open the Network tab, read method/URL/status/body in that order. Most "API is broken" tickets die at this step — the request was malformed, and the server answered correctly.

```text
# Bad: pair-blind (argues about vibes)
"The login API is broken — it just doesn't work."

# Good: pair quoted (fault locates itself)
"POST /sessions → 422, body: {\"error\": \"email_required\"}.
 Client omitted the field — server behaved. Fix the form."
```

### 2) **Verbs say the intent**

*GET* reads (no side effects promised); *POST* submits (creates/acts — general-purpose write); *PUT* replaces a whole resource; *PATCH* modifies part of one; *DELETE* removes. *Idempotent* verbs (GET, PUT, DELETE) can repeat safely; POST generally cannot — retrying it may double-create.

- **Why it matters (correctness, API sanity)**: the verb is a contract about repeatability — infrastructure *acts* on it (browsers retry idempotent requests; caches serve GETs; crawlers follow them). A "GET that deletes" is a landmine: prefetched by browsers, cached by CDNs, re-triggered by retries — deleting things on behalf of anyone who merely looked.
- **Modern guidance** — match verb to intent on every endpoint you touch: reads are GET, partial updates PATCH, full replacements PUT, destruction DELETE, actions-that-aren't-resources POST. And never retry a POST blindly — use idempotency keys (see Domain 01's decode example) or confirm-then-act.

### 3) **Status codes say the outcome class**

The first digit classifies: *2xx* success (200 OK, 201 Created, 204 No Content); *3xx* redirection (go look over there — 301 permanent, 302/307 temporary); *4xx* client fault (400 bad request, 401 unauthenticated, 403 forbidden, 404 not found); *5xx* server fault (500 internal, 502 bad gateway, 503 unavailable).

- **Why it matters (fault attribution)**: the first digit answers "whose fix?" before anyone reads the body — 4xx means the caller must change; 5xx means the owner must wake up. Misclassified codes (200 with an error body, 500 for bad input) corrupt every dashboard, alert, and retry policy downstream.
- **Modern guidance** — read one digit, then the specific code, then the body — in that order, out loud, in incident calls. And when building: return the honest class (422/400 for caller faults, never 200-with-error, never 500-for-validation) — your status codes are other teams' alerting logic.

### 4) **Common confusion**

- "404 means the server is down" — 404 means the server answered and lacks that resource; a down server gives connection errors or 5xx, never 404.
- "401 vs 403" — 401 = unknown identity (authenticate!); 403 = known identity, denied (authorize differently or stop asking). The numbers encode the fix.
- "HTTPS makes a site trustworthy" — it makes the channel private and the endpoint authenticated-as-the-cert-holder; phishing sites have valid certificates too.

### 5) **Mentor note**

Run live DevTools readings: break an endpoint deliberately, have juniors narrate method → URL → status class → body before touching code. Two sessions of "read the pair first" kills the most common junior reflex — editing code before reading the conversation — which is responsible for an outsized share of wasted debugging hours.
