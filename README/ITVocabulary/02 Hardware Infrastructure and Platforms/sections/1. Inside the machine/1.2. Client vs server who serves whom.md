## 1.2. Client vs server (who serves whom)

### 1) **Roles, not machines**

**Definitions** — The *client* asks (initiates requests); the *server* answers (holds resources and responds). These are *roles in an interaction*, not kinds of hardware — your laptop is a client when it fetches a page and a server when it runs `localhost:3000` for a colleague.

- **What problem it solves**: beginners picture two species of computer ("client machines" vs "server machines") and then drown in setups where one box plays both roles. The role framing dissolves the confusion: ask "who initiates, who responds *in this exchange*?" and every architecture diagram reads correctly.
- **Modern guidance** — always qualify the role with the exchange: "the browser (client) asks our API (server), which becomes a client of Postgres (server)". Chained roles are the normal case in microservice systems — naming each hop prevents the "wait, which service calls which?" spiral.

```text
# Bad: machine-thinking (breaks on the first real diagram)
"Is the API gateway a client or a server? It must be one."

# Good: role-per-exchange (handles chains naturally)
"Gateway ← app: gateway is server. Gateway → auth service:
 gateway is client. Same box, two roles, one line each."
```

### 2) **Frontend vs backend follows the split**

*Frontend* is the client-side presentation (what users see and touch — browser UI, mobile screens). *Backend* is the server-side truth and rules (APIs, databases, business logic). *Full-stack* means working across both.

- **History in one paragraph**: the split hardened as browsers got capable — logic migrated client-ward (SPAs) then partially back (server components, edge rendering), but the vocabulary stayed: frontend = near the user, backend = near the data. Every framework debate of the last decade is an argument about where on this line a given piece of work should sit.
- **Modern guidance** — place responsibilities by trust, not convenience: validation, pricing, and permissions live on the backend because clients are user-controlled and therefore untrustworthy; the frontend mirrors them for speed and UX, never as the authority. "The frontend enforces it" is not enforcement — it is a suggestion with styling.

### 3) **The request round-trip in one paragraph**

Client sends a *request* (method + address + payload) over the network; the server does *work* (auth, logic, data access) and returns a *response* (status + payload). Latency is the round-trip time; everything slow in distributed systems is this loop, repeated and nested.

- **Why it matters (debugging, interviews)**: this paragraph is the skeleton key for half of professional vocabulary — timeout (no response in time), retry (send again), cache (skip the trip), load balancer (pick which server), 500 (server failed doing the work). Each term is one modification of the round-trip story; learn the story once, decode dozens of terms free.
- **Modern guidance** — narrate any failure as a round-trip sentence: "client sent X, server did Y, response was Z after N ms". Support tickets, incident reports, and interview answers all accept this shape — it tells the listener exactly which leg to investigate.

### 4) **Common confusion**

- "Server means a big computer in a datacenter" — "server" equally means the *program* (Nginx, Postgres) answering requests; "the server is down" usually refers to the program, not the box.
- "Frontend is easy, backend is hard" — they fail differently (state/UX complexity vs data/scale complexity); seniority exists on both sides of the line.
- "Client-server is outdated (everything is peer-to-peer/cloud now)" — the roles persist inside every new topology; even P2P nodes alternate client/server per exchange.

### 5) **Mentor note**

Test understanding with role-flipping, not definitions: "in `npm install`, who is client?" (npm CLI), "and the registry?" (server) — "now who serves the tarball bytes?" (still registry-as-server, or CDN edge). Anyone who answers three flips without hesitation owns the concept; anyone reciting "client asks, server answers" without mapping it to real tools does not — drill with tools, not flashcards.
