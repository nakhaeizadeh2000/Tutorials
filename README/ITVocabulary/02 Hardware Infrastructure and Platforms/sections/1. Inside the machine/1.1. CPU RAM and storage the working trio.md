## 1.1. CPU, RAM, and storage (the working trio)

### 1) **CPU computes, RAM holds the working set, storage keeps everything**

**Definitions** — The *CPU* (Central Processing Unit) executes instructions — billions of simple operations per second across *cores* (independent execution units). *RAM* (Random-Access Memory) holds the data programs are actively using — fast, volatile (contents vanish on power loss). *Storage* (SSD/HDD) keeps everything persistently — slower than RAM, but surviving restarts.

- **What problem it solves**: "the app is slow" is unactionable until you know which member of the trio is saturated. Each one has different symptoms and different fixes — more cores, more RAM, faster disk — and upgrading the wrong one burns budget for zero gain.
- **Modern guidance** — think in the speed-vs-capacity ladder: CPU registers → cache → RAM → SSD → HDD → network. Each step down is ~10–100x slower and ~10x cheaper per byte. Data your program touches constantly must live as high on the ladder as it fits; everything else sinks downward.

```text
# Bad: trio-blind (prescribes the wrong upgrade)
"The app is slow — let's double the CPU."

# Good: each member named with its symptom
"p95 latency spikes correlate with RAM at 98% (swap storm),
 CPU idle at 30%, disk I/O flat. Memory-bound, not CPU-bound —
 add RAM (or cut the working set), not cores."
```

### 2) **Bottleneck vocabulary**

*CPU-bound* means the processor is the limit (heavy compute: video encoding, ML inference). *Memory-bound* means RAM size or bandwidth is the limit (large datasets, leaks, swap storms). *I/O-bound* means waiting dominates — disk reads or network responses, with the CPU idle.

- **Why it matters (performance, money)**: the bottleneck word *is* the diagnosis and the prescription in one. "I/O-bound on Postgres reads" points at queries and indexes; "CPU-bound on JSON serialization" points at payload shape or a faster parser. Teams that name the bottleneck class in the first sentence fix things in hours; teams that debate "slow" in the abstract fix things in sprints.
- **Modern guidance** — measure-don't-guess framing: one dashboard glance (CPU %, memory %, I/O wait %) before uttering any bottleneck word. The vocabulary earns its power only when attached to numbers — otherwise "CPU-bound" is just a confident-sounding guess.

### 3) **Specs decode to behavior**

*Cores/threads*: more cores = more truly-parallel work (a 4-core box runs ~4 heavy threads at once; hyper-threading adds ~30%, not 2x). *GB RAM*: the ceiling on your working set — exceed it and the OS swaps to disk, collapsing speed 100x. *SSD vs HDD*: solid-state vs spinning disk — SSDs serve random reads ~100x faster, which is why "still on HDD" explains whole classes of slowness.

- **What problem it solves**: spec sheets and cloud instance pickers are written in exactly these words ("4 vCPU, 16 GB RAM, SSD"). Decoding them predicts behavior before paying: Will this box hold my dataset in RAM? Can it run my test suite in parallel? Is disk even a factor?
- **Modern guidance** — translate every spec into a prediction out loud: "16 GB RAM holds our 8 GB working set with headroom; 4 cores match our 4-worker design; SSD makes startup I/O negligible." If you cannot state the prediction, you are shopping, not engineering.

### 4) **Common confusion**

- "More GHz means proportionally faster" — clock speed stopped scaling that way circa 2005; core count, cache, and memory bandwidth dominate modern performance.
- "RAM and storage are both memory" — RAM is volatile working memory; storage persists. "Out of memory" (RAM) and "disk full" (storage) are different failures with different fixes — conflating them pages the wrong runbook.
- "Swap makes RAM limits harmless" — swap (disk used as overflow RAM) keeps processes alive but at disk speed; a swapping production box is effectively down for latency-sensitive traffic.

### 5) **Mentor note**

Make juniors report all three numbers with every "slow" claim — CPU %, RAM %, I/O wait — before allowing theories. Two weeks of this ritual and bottleneck vocabulary becomes reflex; skip it and you get a team that upgrades CPUs to fix memory leaks, which is the most expensive possible way to learn the trio.
