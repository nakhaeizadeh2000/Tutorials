## 5.1. Common interview Q&A: infrastructure vocabulary

### 1) **Client vs server**

*Roles-not-machines answer with a round-trip sentence.*

- **Q**: "Explain client-server architecture."
- **Model answer**: "Client and server are roles, not machines: the client initiates requests, the server responds. A browser (client) asks an API (server), which itself becomes a client of the database. Frontend is the client-side presentation; backend is the server-side truth — validation and permissions live on the backend because clients are user-controlled." Then offer the round-trip: request → work → response (from [1.2](<../1. Inside the machine/1.2. Client vs server who serves whom.md>)).
- **What they are really testing**: whether you can trace one request end to end without hand-waving any hop — the gateway follow-up ("is it client or server?") separates role-thinkers from machine-thinkers instantly.

### 2) **What happens when you visit a URL**

*The beloved mega-question — answered as vocabulary choreography, mechanics linked out.*

- **Q**: "What happens when you type google.com and press Enter?"
- **Model answer** (vocabulary layer — name every actor, defer every mechanism): "The browser (client) resolves the name via DNS, opens a connection to a server (likely behind a load balancer), sends an HTTP request; the server does its work — possibly as a client of caches and databases — and returns a response the browser renders. Slow legs show up as latency; failures surface per leg: DNS, connection, server 5xx." Each underlined word is a pointer to a deeper domain — say so: "DNS mechanics live in our Networks domain; I'm narrating the choreography here."
- **What they are really testing**: breadth with honesty — can you name all ten actors while admitting which ones you'd need docs for? Candidates who fake depth on all ten fail; candidates who name ten and deep-dive two pass.

### 3) **Staging vs production — plus rapid-fire drills**

*Why both exist — the one-paragraph answer.*

- **Q**: "Why do teams maintain staging alongside production?"
- **Model answer**: "Production serves real users, so every release rehearses on staging first — same shape and services, fake data. Staging catches environment gaps localhost can't show: real service topology, migrations, flags. Localhost proves the code runs; staging proves the release behaves; production is the only verdict that counts." (from [2.1](<../2. Where code lives and runs/2.1. Localhost staging and production environments.md>))
- **Rapid-fire drills** (one line each):
  - *CPU vs RAM vs storage?* — "CPU computes, RAM holds the working set (volatile), storage persists — ladder of speed vs capacity."
  - *CPU-bound vs I/O-bound?* — "Processor saturated vs waiting on disk/network with CPU idle — different fixes."
  - *Region vs zone?* — "Geographic area vs isolated datacenter inside it — multi-zone is the cheapest real resilience."
  - *Managed service?* — "Provider operates it (patches, backups, failover) — you trade control for freedom from the pager."
  - *VM vs container?* — "VM emulates a whole machine with its OS; container packages one app sharing the host kernel."

### 4) **Common confusion**

- "The URL question wants the full protocol trace" — at vocabulary level it wants *actor coverage with mechanism pointers*; reciting TCP handshakes while forgetting DNS exists scores worse than naming everything and deferring two.
- "Staging questions are junior questions" — they test release discipline thinking, which staff engineers get wrong often enough that interviewers keep asking.
- "Rapid-fire means rushed" — one calm line per term beats three hedged ones; precision reads as seniority.

### 5) **Mentor note**

Run mock interviews where the candidate must answer *then point*: every term they use must be followed by "which lives in domain X" or "whose mechanics I'd look up". This trains the exact skill the URL mega-question tests — breadth with honest depth-markers — and it doubles as a tour of the track itself.
