## 6.1. Boundaries: what is covered elsewhere

This domain names infrastructure — what each word points to in machines, roles, environments, and clouds. It deliberately stops at these borders:

1. **Networks deep vocab** (DNS, HTTP, TCP, latency vs bandwidth, load balancing mechanics) — [Domain 04 Networks Web and Internet Vocabulary](<../../../LOG.md>) (planned; curriculum recorded in this track's LOG — link to be upgraded to the domain README when it lands). The round-trip story stays here ([1.2](<../1. Inside the machine/1.2. Client vs server who serves whom.md>)); how packets move does not.
2. **How servers, VMs, and containers work** (processes, images, orchestration, Linux administration) — future Linux, Docker, and Cloud tracks own the mechanics; this domain owns one line per word ([2.2](<../2. Where code lives and runs/2.2. Cloud words region zone instance and managed.md>)).
3. **Software-engineering terms** (repo, branch, CI/CD, deploy pipelines, agile process) — Domain 03 Software Development and Engineering Terms and Domain 06 Security Cloud and DevOps Vocabulary (planned, see LOG); "shipped" as a word stays in Domain 01, pipelines live there.
4. **Data and AI vocabulary** (schema, query, embedding, token) — Domain 05 (planned, see LOG); storage *hardware* (SSD/HDD) is named here ([1.1](<../1. Inside the machine/1.1. CPU RAM and storage the working trio.md>)), data *systems* are not.
5. **Core concepts and meeting language** (layers, units, acronyms, standups) — [Domain 01](<../../../01 Core IT Concepts and Professional Jargon/README.md>); this domain assumes that vocabulary and builds upward from it.

If you find yourself explaining how virtualization, orchestration, or a protocol *works* inside this domain — stop; keep the one-line name, link the neighbor that owns the mechanism, and move on.
