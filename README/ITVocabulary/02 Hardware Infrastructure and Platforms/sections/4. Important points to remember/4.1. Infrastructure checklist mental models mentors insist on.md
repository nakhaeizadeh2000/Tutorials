## 4.1. Infrastructure checklist (mental models mentors insist on)

### 1) **Name the bottleneck class**

CPU-bound, memory-bound, or I/O-bound — before any fix, with numbers attached (from [1.1](<../1. Inside the machine/1.1. CPU RAM and storage the working trio.md>)).

- **Check yourself**: every "slow" report carries CPU %, RAM %, and I/O-wait. No numbers, no bottleneck word — "I/O-bound" without `iostat` output is a guess wearing a lab coat.
- **Bad habit to break**: upgrading the wrong resource (new CPUs for a memory leak) — the most expensive possible way to avoid one dashboard glance.

### 2) **Name the environment**

Localhost, staging, or production — in every claim, every ticket, every deploy verb (from [2.1](<../2. Where code lives and runs/2.1. Localhost staging and production environments.md>)).

- **Check yourself**: "deployed to staging, green with seed v3" — not "deployed". "Reproduces on staging, not on localhost" — not "reproduces". The environment noun disqualifies half of all wrong theories on arrival.
- **Bad habit to break**: environment-free verbs that let localhost evidence authorize production conclusions.

### 3) **Name the failure boundary**

Zone, region, single-box — in every resilience claim (from [2.2](<../2. Where code lives and runs/2.2. Cloud words region zone instance and managed.md>)).

- **Check yourself**: "multi-zone in one region (survives datacenter loss, not regional)" — not "highly available". Every availability adjective must cash out into a named boundary and a named survivor scenario, or it is marketing.
- **Bad habit to break**: "runs in the cloud, so it's resilient" — the cloud is rented hardware with extra steps; resilience is a design you can draw, not a property you inherit.

### 4) **Common confusion**

- "Checklists slow me down" — they slow down the *first* incident report by two minutes and accelerate every subsequent one by hours; net velocity is strongly positive.
- "Seniors don't need this" — seniors need it most: their confident-sounding guesses get believed without evidence, so their unforced errors cost more.

### 5) **Mentor note**

Enforce the triple-name rule in code review and incident review alike: bottleneck class + environment + failure boundary, or the report goes back. A month of returned reports rewrites team reflexes permanently — juniors trained this way write incident updates that read like senior ones, because the structure *is* the seniority.
