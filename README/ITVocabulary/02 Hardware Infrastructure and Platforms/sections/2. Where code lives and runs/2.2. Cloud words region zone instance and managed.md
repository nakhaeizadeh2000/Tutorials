## 2.2. Cloud words: region, zone, instance, and managed

### 1) **Region and zone are failure boundaries**

**Definitions** — A *region* is a provider's geographic area (e.g., `eu-central-1`, roughly "Frankfurt and surroundings"). A *zone* (availability zone) is one isolated datacenter — own power, cooling, network — inside a region. Regions hold data near users and inside legal borders; zones survive each other's fires.

- **What problem it solves**: "deploy it in the cloud" says nothing about blast radius. Region/zone vocabulary turns resilience from vibes into arithmetic: single-zone = one fire away from down; multi-zone = survives a datacenter loss; multi-region = survives a regional catastrophe (at multi-region cost and complexity).
- **Modern guidance** — default to multi-zone inside one region (the cheapest real resilience: providers replicate managed data across zones nearly free); go multi-region only when downtime math or data-residency law demands it. And put users' data in their legal region *first* — GDPR fines dwarf hosting bills.

```text
# Bad: boundary-blind (resilience theater)
"We're highly available — everything runs in the cloud."

# Good: boundaries named, promise sized
"API runs in 3 zones of eu-central-1 (survives a datacenter loss).
 Single-region by design: RPO/RTO accepted, residency in the EU."
```

### 2) **Instance, VM, and container in one line each**

An *instance* is one rented machine (virtual or physical) from a provider — the billing atom of compute. A *VM* (virtual machine) emulates a whole computer, OS included, on shared hardware. A *container* packages one app with its dependencies, sharing the host's kernel — lighter than a VM, isolated enough for most purposes.

- **What problem it solves**: job posts, incident threads, and architecture docs use all three interchangeably, and they are not interchangeable — "restart the instance" (provider-level, minutes, new IP maybe) vs "restart the container" (seconds, same host) have different blast radii. One line each keeps the words from blurring under pressure.
- **Modern guidance** — naming level only here (this is a vocabulary track): instance = rented box, VM = box-emulator, container = app-package. How virtualization and orchestration *work* belongs to the future Linux/Docker/Cloud tracks — using the names correctly today is what unblocks you in every cloud console and doc page.

### 3) **Managed means "they operate it"**

A *managed service* (managed Postgres, managed Kubernetes, serverless functions) trades control for freedom from on-call burden: the provider patches, backs up, fails over — you configure, pay the markup, and accept their limits.

- **Why it matters (money and sleep)**: self-hosting looks cheaper until you price the pager: patching CVEs at midnight, sizing disks before they fill, testing restores nobody tested. Managed shifts that labor to the provider's bill — usually the right trade for small teams, sometimes the wrong one at scale (when the markup exceeds an ops hire).
- **Modern guidance** — default to managed for undifferentiated heavylifting (databases, queues, TLS, backups); self-host only what is your competitive edge or breaks the managed limits (exotic extensions, cost cliffs, compliance oddities). Revisit the decision yearly — the correct answer moves as you grow.

### 4) **Common confusion**

- "Region vs zone vs datacenter" — zone ≈ isolated datacenter; region = cluster of zones; providers avoid promising exact building counts, so reason in zones, not buildings.
- "Serverless means no servers" — it means no servers *you manage*; your code still runs on instances somewhere, billed per invocation instead of per hour.
- "Multi-region is strictly better" — it multiplies consistency, deployment, and debugging complexity; most outages it "prevents" never threatened single-region-multi-zone setups in the first place.

### 5) **Mentor note**

Give every junior the one-line map exercise for your own system: "our API runs as containers on N instances across X zones of region Y; Postgres is managed with multi-zone failover." If they cannot produce that sentence in week two, your onboarding teaches tools but not terrain — and terrain is what they will navigate at 3 AM.
