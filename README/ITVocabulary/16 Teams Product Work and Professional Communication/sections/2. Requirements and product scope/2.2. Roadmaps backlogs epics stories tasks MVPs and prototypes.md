## 2.2. Roadmaps backlogs epics stories tasks MVPs and prototypes

A roadmap says “simpler workshop follow-up,” a tracker contains twelve tasks, and
a demo looks finished. These artifacts answer different questions. Direction is
not implementation, and implementation activity is not evidence that the intended
users can complete the task in production. Read the purpose before the status label.

### 1) **Distinguish product direction from work decomposition**

A **roadmap** communicates intended direction, outcomes and broad sequencing over
time. It may use dates, horizons such as now/next/later, or themes. Establish whether
a date is an ambition, forecast or binding commitment. A roadmap can change as
teams learn; that does not erase an explicit customer commitment that also exists.

A **backlog** records work awaiting attention under some process. In Scrum, the
**Product Backlog** is an evolving ordered list of product work; see the
[2020 guide's artifact definition](https://scrumguides.org/scrum-guide.html#product-backlog).
A generic team's backlog can include ideas, defects, research and maintenance.
An entry is not automatically approved, scheduled or promised. “In the backlog”
needs an ordering, scope and decision context before it means “coming next.”

An **epic** groups a substantial body of related work. A **user story** briefly
expresses a user's goal or valuable capability and supports discussion and acceptance
criteria. A **task** describes work to perform, such as implementing a filter or
reviewing a draft. Teams and tools use different hierarchies: a task may sit under
a story or alongside stories within an epic. Atlassian's [epic explanation](https://www.atlassian.com/agile/project-management/epics/)
illustrates decomposition; its tool vocabulary is not a universal hierarchy.

For example, the roadmap outcome is “coordinators can contact pending attendees.”
An epic groups follow-up improvements. A story says “As a coordinator, I need the
pending contacts for my selected workshop so I can follow up before it starts.”
Tasks might implement selection, inspect permission rules and evaluate the complete
workflow. Completing only the selection task does not fulfill the story.

The familiar role/goal/benefit sentence is a useful prompt, not an obligatory
incantation. “As a developer, I want a new column” still needs the reason and its
relationship to a user outcome. Agile Alliance's [story discussion](https://agilealliance.org/glossary/user-stories/)
emphasizes the evolving shared understanding beyond a card. A story title alone
does not define all behavior, and Scrum does not require every item to use that template.

### 2) **Choose a learning artifact for the uncertainty**

A **prototype** represents selected aspects of a possible design so people can
explore and evaluate them. It can be a sketch, clickable mockup or working code.
Its **fidelity** is how closely the relevant appearance, interaction or behavior
resembles the intended product. Visual fidelity does not establish data fidelity,
security or production operation. State the dimensions actually represented.

A **proof of concept**, or **PoC**, investigates whether an approach can work under
specified conditions. For example, can the intended identity provider supply the
needed group information in a controlled integration? That bounded result does
not establish that users understand the resulting screen or that operations can
support it. The terms prototype and PoC can overlap; name the question being tested.

A **minimum viable product**, or **MVP**, is a bounded product offering used to
learn about a product hypothesis. In its Lean Startup framing, the point is useful
learning about customers, not merely deleting features. Agile Alliance's
[MVP explanation](https://agilealliance.org/glossary/mvp/)
highlights learning and the danger of emphasizing minimum while neglecting viability.
Specify the hypothesis, intended users, observation and decision the evidence will
inform. “First release” is a broader local usage; clarify it rather than assuming
an experiment was conducted.

For example, a manually assisted follow-up service might test whether coordinators
will use a daily pending-contact list. It can deliver value and learning without
establishing that an automated exporter scales. An MVP is not permission to omit
protections required for the data and activity it actually handles.

A **production deliverable** must satisfy its real operating, support and quality
requirements. The UK government's [prototype guidance](https://www.gov.uk/service-manual/design/making-prototypes)
explicitly distinguishes exploration code from production standards. Apply that
boundary to the evidence; do not treat a realistic screen as proof that prototype
code can simply be copied into a live service. Some artifacts can evolve into
production implementations, but readiness requires the appropriate additional work.

### 3) **Read a polished demonstration without overstating progress**

This fictional packet concerns workshop follow-up:

| Artifact | Supplied evidence | Limit |
|---|---|---|
| Roadmap | “Improve follow-up next quarter,” marked tentative | No committed delivery date |
| Backlog | Epic E3 with story S8 for the pending-contact workflow | Selection for implementation not recorded |
| Prototype P2 | Clickable screen uses prepared W1 contacts; three coordinators find the intended list during a walkthrough | No live data, permissions or large-input check |
| PoC C1 | A separate controlled adapter retrieves the expected group field from the selected provider | No evidence it is connected to P2 |
| Task board | “Create button” is complete; access review and export generation remain open | Story completion not established |
| Proposed MVP | Offer a manually prepared list to a bounded pilot group and observe whether they use it | Proposal only; no pilot results |

A precise update is: “The prototype supports the checked list-finding interaction,
and a separate PoC supports the provider-field feasibility case. The integrated
workflow remains incomplete. The pilot is proposed, and the roadmap date is tentative.”
Calling this “MVP launched and story done” would promote a proposal and separate
artifacts into an outcome the packet never established.

Practice: add an actual recorded pilot in which the intended coordinators use the
manually prepared list. That supplies behavior evidence for the bounded offering.
It still does not prove that P2 has live authorization or that automated generation
meets load requirements. If the walkthrough evidence is removed instead, usability
of the prototype becomes unverified; a polished image cannot fill the gap.

### 4) **Common confusion**

A task is not an operating-system task, and a product prototype is not JavaScript's
prototype object mechanism. Context selects the meaning. A backlog is also not
necessarily a queue of requests executing in a service.

An MVP can contain substantial manual work, while a prototype can contain working
code. The label alone does not determine deployment, quality or learning. Ask who
used what, under which conditions, and what decision the evidence supports.

### 5) **Performance note**

An epic size or completed-task count does not measure software throughput. A
prototype using fixed data omits retrieval, authorization and other potential
costs. A PoC timing can establish only its measured path and conditions. No pilot,
load, adapter or user-speed measurement was executed here; all packet records are
constructed. Vocabulary helps choose the next evaluation, not predict its result.

### 6) **Mentor note**

Present the attractive prototype screenshot description before revealing the
packet. Ask what makes it “done.” A strong answer first requests its intended
purpose, then separates visual interaction, integration feasibility, actual customer
learning and production readiness. Add the pilot result and check that only the
corresponding learning claim strengthens.
