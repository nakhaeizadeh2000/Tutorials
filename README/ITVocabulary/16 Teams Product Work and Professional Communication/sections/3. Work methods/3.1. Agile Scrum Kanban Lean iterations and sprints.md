## 3.1. Agile Scrum Kanban Lean iterations and sprints

“We are Agile because we have a daily meeting and a board.” The meeting and board
are visible artifacts. They do not show whether people learn from working outcomes,
adapt plans or finish useful work. This lesson helps you ask about those behaviors
without prescribing one process for every organization.

### 1) **Separate adaptive values from a named framework**

**Agile** refers to a family of approaches associated with adaptive development,
collaboration and feedback. The original [Agile Manifesto](https://agilemanifesto.org/)
states preferences among values while explicitly retaining value in the other
items. It does not reject plans, contracts, tools or documentation. Its
[principles](https://agilemanifesto.org/principles.html)
emphasize working outcomes, sustainable development, technical quality and reflection.
These are a historical statement of intent, not evidence that adopting a label
causes better results in a particular team.

For example, a team can document a decision so future maintainers understand why
an export excludes approved bookings. That documentation supports delivery and
operation. Producing a large document while postponing all user feedback is a
different working pattern. “Working software matters” does not mean “leave the
on-call engineer without instructions.” Choose documentation for an actual purpose.

**Scrum** is a specific framework. Its [2020 guide](https://scrumguides.org/scrum-guide.html)
defines Developers, Product Owner and Scrum Master accountabilities, events and
artifacts. The PO/backlog accountability already has an owner in this domain.
Recognize that framework responsibilities are different from a company's job titles.
Scrum is one approach compatible with adaptive development; Agile is not another
name for Scrum.

### 2) **Distinguish timeboxed learning from managed flow**

An **iteration** is a repeated development or learning cycle. It can revise a design
based on what was learned. An **increment** adds usable capability. These ideas
can overlap: refine a confusing selection flow while adding an export feature.
Repeatedly holding meetings without learning or adding usable capability does
not demonstrate those outcomes.

A **Sprint** is Scrum's timebox of one month or less. Within it, people plan toward
a **Sprint Goal**, inspect progress and adapt. **Sprint Planning** establishes the
purpose and plan; the **Daily Scrum** inspects progress toward that goal. A
**Sprint Review** inspects the product outcome with stakeholders and informs next
steps; a **Sprint Retrospective** examines how the team works and what to improve.
A Sprint ending is not proof that all selected items were finished or that a
production deployment occurred. Scrum allows release before the review; it does
not define the review as a mandatory release gate.

**Kanban**, in the [May 2025 Kanban Guide](https://kanbanguides.org/the-kanban-guide/2025.5/),
concerns the flow of value through a defined workflow. Establish work items,
start/finish boundaries, states and movement policies, then manage and improve
that flow. **Work in progress**, or **WIP**, consists of started but unfinished
items. Explicit controls govern how much work is admitted; a board alone does
not establish this management. Pulling new work when capacity is available differs
from assigning every available idea immediately.

For example, if a local policy permits three active items across implementation
and review, two items being implemented plus one waiting for review already use
those three places. Moving the waiting item to a hidden “parking” list does not
finish it. State exception policies and investigate what prevents completion.
Kanban can supplement a team's other approach; the names need not be rival departments.

**Lean** thinking and practice focus on needed value, the work producing it and
learning how to reduce waste. The [Lean Enterprise Institute introduction](https://www.lean.org/explore-lean/what-is-lean/)
connects customer problems, experimentation and respect for people. Do not reduce
Lean to removing staff or maximizing everyone's utilization. Repeatedly entering
the same export request can be waste worth investigating; a necessary security
review is not waste merely because it does not add a visible button. Judge the
purpose and consequences before removing work.

### 3) **Evaluate a process claim from observed work**

Read these fictional records. The team calls its approach “Scrum with Kanban flow
controls”; that label is a claim to investigate, not a certification.

| Record | Supplied information |
|---|---|
| Goal | During a two-week Sprint, enable coordinators to retrieve pending contacts for their selected workshop |
| Local workflow | Started at implementation; finished only after implementation and required review; active WIP control is three |
| Board snapshot | A is being implemented, B is waiting for review, C is being implemented |
| Proposed action | Start D because “B is not being coded, so there are only two active items” |
| Outcome | The Sprint ends with A usable and reviewed; B and C remain unfinished |
| Reflection | Team proposes reserving review capacity and observing item completion and age next Sprint |

A, B and C are all started and unfinished under the supplied boundaries. The
proposed D would exceed the local control unless an applicable explicit exception
permits it. Waiting for review is part of the workflow. The purpose of the control
is not satisfied by relabeling that waiting time.

A's usable result supports a completed addition within its recorded scope. The
calendar ending does not complete B or C. Nor does the packet establish whether A
alone achieved the full goal: identify the capability it actually supplies.
The reflection proposes an improvement; it has no observed effect yet.

A useful response is: “Our active count is three including review waiting. Rather
than start D under the current rule, clarify review capacity and how to help finish
existing work. At the next inspection, compare the actual completed outcomes and
waiting items; don't report the proposed change as an improvement already achieved.”

Practice: add evidence that B passes its required review and meets the finish rule.
WIP falls to two, so the supplied control can allow another item to start. That
change establishes capacity under this policy, not guaranteed shorter cycle time
or an obligation to start D ahead of every other item. Ordering and priorities
still matter.

### 4) **Common confusion**

A daily status meeting is not automatically Scrum's Daily Scrum, and a column-based
board is not the whole Kanban strategy. Use the intended purpose and behavior,
not a renamed calendar invitation, to interpret a practice.

Adapting to change does not mean changing every commitment without discussion.
Keep the goal, quality requirements, contractual duties and new evidence visible.
Likewise, an iteration does not have to be a Sprint: Sprint has a framework meaning,
while iteration is broader.

### 5) **Performance note**

Work-method names have no direct effect on program execution speed. WIP controls
can change waiting and coordination, but the outcome depends on the actual workflow,
variation and capacity. Counting more started items is not proof of more delivered
value. The snapshot checks only the local count; no productivity, cycle-time,
delivery-rate or application-performance experiment was run here.

### 6) **Mentor note**

Ask the learner to explain why B counts without saying “because the board says so.”
They should refer to the start and finish rules. Then ask what evidence would show
that reserving review capacity helped. A strong answer needs comparable outcomes
and conditions, not just a new meeting, fewer columns or the word Lean.
