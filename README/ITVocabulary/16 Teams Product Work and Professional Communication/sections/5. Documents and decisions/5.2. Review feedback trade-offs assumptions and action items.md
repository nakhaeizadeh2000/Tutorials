## 5.2. Review feedback trade-offs assumptions and action items

“This design is bad; use a cache.” The comment identifies neither the requirement
being missed nor why the suggested mechanism helps. Professional review turns a
concern into reasoning the author and decision owner can inspect. It can be direct
without guessing another person's motives or demanding a preferred implementation.

### 1) **Write feedback that identifies evidence and consequence**

**Review feedback** evaluates a work product or proposal. Name the object and
location, describe the observation, connect it to a consequence or requirement,
and state the requested next step. A **clarification** asks for missing meaning
or evidence; it is different from an established defect. A **suggestion** offers
an option, while a required correction addresses an applicable unmet condition.

Google's original [code-review comment guidance](https://google.github.io/eng-practices/review/reviewer/comments.html)
recommends explaining reasoning, discussing the work and making comment intent
clear. These habits also help proposal reviews. Its particular code-review process
and “Nit” label are not universal policy. If labels are used, agree their meaning:
a minor wording suggestion should not silently carry the same blocking authority
as a confirmed data-scope violation.

Compare these comments about the same fictional export:

| Weak feedback | More useful feedback |
|---|---|
| This is obviously careless | The example file includes W2 although the selection rule permits W1 only. Please correct the selection and retain a check for both workshops |
| Performance is terrible | I see no duration result for the required input size. Please identify the measured version and workload; speed remains unverified |
| Use a cache | If repeated unchanged reads dominate, caching might reduce source work. We need the permitted data age and workload evidence before choosing it |
| Rename this immediately | Optional wording: pendingCount may clarify the value's meaning; I have not identified a behavioral failure |

The first repair states a supported mismatch. The second asks for evidence rather
than inventing a slow measurement. The third states a conditional option. The
fourth marks a preference. Courtesy does not require weakening a clear correctness
finding into an ambiguous “maybe”; explain its evidence and consequence plainly.

### 2) **Explain an option choice with assumptions and trade-offs**

A **trade-off** is a choice among competing consequences. A cache can introduce
memory, refresh and invalidation work in exchange for avoiding some repeated
source work. Whether that exchange is useful depends on the operation, freshness
rule and observed workload. “There are trade-offs” is not an explanation until
those consequences and conditions are named.

An **assumption** is a premise treated as true in some reasoning. “The caller
accepts results up to five minutes old” is an assumption if no requirement or
agreement establishes it. Record who can confirm it and what happens if it fails.
A **hypothesis** proposes an explanation, such as repeated source reads causing
the delay; an **observation** supplies a recorded result. An assumption need not
be a causal hypothesis, and none becomes evidence merely because it appears in a table.

**Decision rationale** connects the chosen option to requirements, evidence,
alternatives and known limitations. NASA's [decision-analysis guidance](https://www.nasa.gov/reference/6-8-decision-analysis/)
emphasizes alternatives, criteria and uncertainty, with effort appropriate to the
decision. You do not need a weighted matrix for every naming question. Conversely,
adding numerical scores to unsupported guesses does not make a consequential
architecture choice objective.

Some conditions are mandatory boundaries; others allow preference trade-offs.
If every selected-workshop export must exclude other workshops, a faster option
that includes them fails that requirement. It does not become acceptable merely
because a convenience score outweighs privacy in an arbitrary table. Reconcile
an actual requirement change with its authority rather than hiding it in scoring.

### 3) **Turn disagreement into a decision and verifiable follow-up**

Read this constructed review packet:

| Record | Supplied information |
|---|---|
| Required result | Pending-contact list must reflect all accepted updates before the export begins, for its selected workshop |
| Proposal A | Read the authoritative source for each export |
| Proposal B | Reuse a result for five minutes with no invalidation or source validation |
| Supplied timeline | At 09:00 B stores a pending booking; cancellation is accepted at 09:01; export begins at 09:02 and B returns the old pending record |
| Performance evidence | Neither proposal has measured representative export durations |
| Review | “A is slow and not scalable. B is best practice. We assume five-minute freshness is fine” |
| Authority | Ada owns product criteria; Jo owns implementation follow-up |

B's supplied timeline conflicts with the explicit required result. The five-minute
premise is not an innocent missing detail: it contradicts that rule. Neither A's
slowness nor B's speed or scalability is established. A may meet the data rule
without meeting some future performance criterion; the packet does not decide that.

A useful review says: “At 09:02 B returns the booking canceled at 09:01, contrary
to the accepted-update rule. Please revise the reuse design or ask Ada to decide
an explicit freshness change. Neither proposal has representative timing evidence,
so keep the speed comparison open.” This identifies the consequence without
calling the author careless or declaring every cache unsuitable.

A proposed **action item** should have an owner, outcome and acceptance evidence.
For Jo, one item can be: “Produce a candidate preserving the accepted-update rule
and selected-workshop boundary; record the candidate and check a cancellation
between initial retrieval and later export. Include the relevant access/selection
cases and report any freshness guarantee still unverified.” A separate item can
resolve the workload and timing criteria with Ada before comparing performance.
The earlier incident-learning lesson owns the full general action-item explanation.

Do not close Jo's first item merely because a revised diagram was uploaded. The
stated candidate check remains part of its completion. Equally, a corrected
cancellation case does not prove every concurrent history or all access rules.
Keep remaining limitations attached to the evidence.

Practice: Ada explicitly changes the requirement to permit up to five-minute-old
results under a defined policy. The original timeline may then comply with that
new rule; retain the revision and conditions. B still has no demonstrated speedup.
If instead the timeline is removed, B's design still raises a credible requirements
concern, but the supplied observed-output violation is no longer established.

### 4) **Common confusion**

Disagreement is not automatically a conflict between personalities. Two readers
may be using different requirements or evidence. First recover the shared question.
An explanation of why an option was chosen can resolve a misunderstanding without
making the option universally best.

An action request is not an action result. “Investigate scalability” also lacks a
clear stopping condition. Name the workload or missing decision so the owner can
produce evidence that answers a bounded question.

### 5) **Performance note**

A review comment changes no runtime behavior by itself. A suggested cache may
reduce some source operations while adding lookup, memory and freshness-management
costs. Those costs and outcomes need measurement under the selected policy. No
cache, source read, cancellation, candidate check or performance comparison was
executed here. The times are fictional logical ordering, not a measured benchmark.

### 6) **Mentor note**

Ask the learner to classify each sentence of the weak review as observation,
assumption, unsupported conclusion or suggestion. Then change only Ada's rule.
A sound answer revises the compliance judgment while keeping the performance
claim open. Ask which artifact would close each proposed action item and why an
uploaded diagram alone cannot supply the specified runtime evidence.
