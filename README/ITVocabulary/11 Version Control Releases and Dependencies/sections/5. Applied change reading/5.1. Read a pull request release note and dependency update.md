## 5.1. Read a pull request release note and dependency update

“Approved minor update; tests are green; the package is signed, so it is ready”
combines several claims whose evidence may refer to different versions. Read the
change, dependency selection and verification records together before deciding
what the sentence actually establishes.

This is a constructed review exercise for a reporting application using NestJS
with the Fastify adapter. No framework knowledge is needed. `H1` and `H2` label
application commits; `A1` and `A2` label different archive digests. They are not
real commit IDs or digest values. No application checks were run for this packet.

### 1) **Align the proposal and release notes with the relevant versions**

Read the following fictional change packet. Each row provides a stated fact for
this exercise; it is not evidence from a real repository or package publisher.

| Artifact | Supplied information |
|---|---|
| SDK's version policy | Adopts SemVer 2.0.0 for its public API |
| SDK 2.4.2 public contract | A report input must contain the numeric field `seats` |
| SDK 2.5.0 release notes | `seats` is removed; input must now contain `quantity`; `seats` alone is rejected |
| Application PR target and state | Proposes merging `report-update` into `main`; PR is still open |
| Review and test record | Reviewer approved application commit `H1`; tests passed there with SDK 2.4.2 |
| Current PR head | `H2`, which also changes the lock selection to SDK 2.5.0 and adapts the report caller to send `quantity` |
| Current-head verification | No test or approval record for `H2` is supplied |

Start with the concrete behavior change. A caller using the documented `seats`
input loses that accepted input in 2.5.0. Under the publisher's stated SemVer
contract, this is a breaking public-API change despite the minor-version label.
[SemVer's major-change rule](https://semver.org/spec/v2.0.0.html#spec-item-8)
explains the conflict. The release number cannot override the explicitly described
change. If the old input were undocumented internal behavior instead, you would
need to establish its contract status before reaching the same conclusion.

The application change at `H2` may be a sensible adaptation to the new SDK input,
but the packet does not establish that it works. Approval and tests at `H1`
concern an earlier application commit and earlier dependency selection. The PR's
open state also does not establish integration into `main` or deployment.

Avoid the opposite overclaim too: no test record is not proof of a failing test.
The correct statement is that verification of the current proposal is missing
from the supplied evidence. Ask for it with the current commit and dependency
selection identified.

### 2) **Trace selected contents and supporting evidence through the update**

The packet continues with these records:

| Artifact | Supplied information |
|---|---|
| Application manifest | SDK range remains `^2.4.0` across `H1` and `H2` |
| Lockfile diff | SDK selection changes from 2.4.2 to 2.5.0; its transitive formatter changes from 1.7.2 to 1.8.0 |
| Build installation record | The `H2` build records SDK 2.5.0 and formatter 1.8.0 |
| SDK provenance report | For archive `A2`, expected signer, source, builder and parameters pass the stated policy checks |
| SBOM report | Its subject is archive `A1`, an earlier SDK artifact |
| License and offering note | The exact covered SDK component retains MIT terms; the vendor now offers paid support |
| Support note | The SDK's 2.x line remains maintained; the packet gives no fix or compatibility guarantee for this application |

The unchanged manifest did not freeze the dependency contents. The range admits
2.5.0 in this example, and the lockfile diff names a concrete selection change.
It also identifies a transitive update, so “only the direct SDK changed” misstates
the record. The installation row adds evidence about that build's contents; it
does not supply a report-execution result.

The provenance result concerns `A2`. The inventory concerns `A1`; it cannot settle
the component inventory of `A2`. Ask for the appropriate artifact-bound SBOM and
its generation scope. Do not relabel the missing inventory as either verified
contents or proven malicious contents. The earlier artifact lesson explains the
separate subject, trust and policy checks in full.

Paid support does not turn the stated MIT-covered component into proprietary
software. Conversely, the MIT terms for that component do not automatically
establish the terms of every transitive dependency or separate service contract.
Keep the exact component and intended use attached to a license-review question.
Maintenance of 2.x is another independent fact: it cannot supply the missing
`H2` compatibility result or undo the documented input removal.

### 3) **Write a review handoff that preserves what is known and unknown**

A useful technical handoff could say:

> H2 adapts the caller to SDK 2.5.0 and changes the lock selection, including the
> formatter. The SDK notes remove a previously public input despite a minor-version
> release. The supplied approval and passing tests cover H1 with SDK 2.4.2. Please
> review and check H2 with its selected dependencies, provide the inventory for A2,
> and clarify the publisher's compatibility notice before making the release decision.

For a product teammate, keep the implication and next evidence clear:

> The proposal changes the reporting integration. Its latest version still needs
> the relevant check results and matching component record; the earlier approval
> covers a different version. Paid vendor support is a separate offering and does
> not resolve those missing results.

Neither handoff invents a broken report, compromised package or authorized
production rollout. In a real review, assign the requested follow-up to the person
responsible for the relevant evidence and state what result would answer it.
“Investigate dependencies” is less useful than identifying `H2`, SDK 2.5.0 and
archive `A2`.

Practice: add a test record at `H2` that builds with the selected versions and
successfully checks the application's report inputs and results. What changes?
Those specific checks now have supporting evidence for the current proposal.
They do not fix the upstream SemVer discrepancy, make the old SBOM apply to `A2`,
or prove every production workload. If instead the PR head moves to `H3`, locate
which evidence applies to that new state before reusing the previous conclusion.

### 4) **Common confusion**

A passing check is about the state and scope it exercised. A current green badge
without its commit and dependency context can conceal the version mismatch in
this packet. A signature result is similarly about its subject and policy, not
an interchangeable substitute for application tests or an inventory.

An update can be admitted by a version range while violating the publisher's
compatibility promise. Range matching, release-policy conformance and actual
consumer compatibility answer different questions. Treat their disagreement as
information to resolve instead of choosing whichever label supports a preferred
outcome.

### 5) **Performance note**

Neither the minor version nor the new formatter version predicts report latency.
The packet contains no timing evidence. If the release notes claim a speedup,
identify the workload, versions, measurement boundary and comparison before
repeating it. Keep installation or build duration separate from the time users
wait for a report. Repeating a performance claim from a signed release note
verifies neither its measurement nor its applicability to this application.

### 6) **Mentor note**

Ask a learner to attach every approval, check and inventory to its subject before
offering a verdict. In an interview, ask why the unchanged range, minor version,
maintained line and valid provenance do not establish a successful upgrade. A
strong answer uses the packet's concrete mismatches and asks for discriminating
evidence. Then add the `H2` check record and expect a narrower, more positive
conclusion for the checked behavior rather than an unchanged blanket rejection.
