## 1.2. Branches tags remotes forks and clones

A teammate says, “It is on main in my fork, and my clone is up to date.” Before
looking for a missing change, identify which repository and which reference each
phrase describes. The same branch name can refer to different commits in two
repositories, and a local record of another repository can be out of date.

Read the repository, staging and commit lesson first. Git reference documentation
and GitHub's fork terminology were checked 2026-10-19. The history tables below
are constructed examples. C1, C2 and C3 are short teaching labels for commit
objects, not actual Git object IDs or commands to run.

### 1) **Distinguish moving branch names from labeled versions**

A **reference**, often **ref**, gives an object or another reference a name. A
**branch** describes a line of development whose current **tip** is identified by
a branch reference. Normal commits on that checked-out branch move its tip to
the new commit. Other branch references need not move with it. Git's
[branch reference](https://git-scm.com/docs/git-branch) distinguishes creating a
branch from switching the working tree to it.

Suppose `main` and `report-fix` both initially point to C1. A new commit C2 has
parent C1 and is made on `report-fix`. Now `report-fix` points to C2 and `main`
still points to C1. Both lines include the shared C1 history. Creating the second
name did not create a second independent copy of every project file or require
a second repository.

**HEAD** supplies the current checkout context. In an ordinary attached checkout,
it refers to the current branch, which identifies its current commit. With a
**detached HEAD**, it refers directly to a commit rather than a branch. That
changes which reference would advance on a new commit; it does not mean the
existing commit was erased. A new repository can also have an unborn branch
before its first commit, as the [Git glossary](https://git-scm.com/docs/gitglossary#def_HEAD)
explains. Avoid the universal shortcut “HEAD is always a branch name.”

A **tag** labels an object, commonly a commit chosen as a version point. A
**lightweight tag** is a direct reference. An **annotated tag** refers through a
tag object containing a message, tagger and date, with an optional signature.
Git's [tag reference](https://git-scm.com/docs/git-tag) explains this distinction.
Tags normally remain at the chosen version rather than advancing on each new
commit, but a tag name can be deliberately replaced. Do not confuse a stable
naming convention with an immutable commit object's identity.

For example, tag `v1.0.0` can label C1 while `main` later points to C3. Asking to
inspect the tag and asking to inspect current main are different requests.
The tag alone does not prove that a package was published, an artifact matches
that source, or a production service runs it. Those need their own records.

### 2) **Separate another repository from your local record of it**

A **clone** is a repository created from another repository. In an ordinary
non-bare clone, Git also checks out a working tree and configures a **remote**,
a named connection description for another repository. `origin` is the usual
initial remote name, not a special globally authoritative server. Names and
configuration can differ; Git's [clone reference](https://git-scm.com/docs/git-clone)
describes the ordinary setup and its options.

A remote can identify a repository on the same computer or one reached through
a network URL. Its configuration does not prove that the destination is reachable,
that your credentials allow writing there, or that every local commit has been
sent. A repository can have more than one remote. Git's
[remote reference](https://git-scm.com/docs/git-remote) describes configuring them
and updating their remote-tracking references.

A **remote-tracking branch**, such as `origin/main`, is a local reference recording
a known state of a branch from that remote. It is not a live view of the server's
current branch. A **fetch** obtains selected objects and updates relevant local
references according to configuration, as the
[fetch reference](https://git-scm.com/docs/git-fetch) specifies. It does not, by itself in this ordinary
setup, advance your local `main` or combine its work with the fetched history.

Use this original two-repository packet. The team repository's `main` initially
points to C1. Bob makes an ordinary clone with remote name `origin`. Later the
team creates C2 with parent C1. Bob then successfully fetches the team branch;
he performs no merge, rebase, reset or local commit in this packet.

| Time | Team repository `main` | Bob's local `origin/main` | Bob's local `main` |
|---|---|---|---|
| After clone | C1 | C1 | C1 |
| After the team's new commit, before Bob fetches | C2 | C1 | C1 |
| After Bob's stated fetch | C2 | C2 | C1 |

Before fetching, Bob's local `main` equals his local `origin/main`, yet both are
behind the team's actual C2. A local comparison cannot reveal a server update
that has not been learned. After fetching, the new C2 object and reference are
available locally while Bob's branch remains at C1. “Downloaded” and “integrated
into my branch” are separate events.

A **push** requests updates to references in another repository and sends needed
objects. The [push reference](https://git-scm.com/docs/git-push) describes that
remote-update operation. Its success, target and included references matter. Merely creating a
local commit does not perform that request. Here no push occurred, and no
hosting-service workflow or credentials are needed to interpret the table.

“Tracking” also appears in the phrase “a local branch tracks another branch.”
That is configured integration/comparison information, not an automatic continuous
synchronization process. The original
[Git terminology investigation](https://jvns.ca/blog/2023/11/01/confusing-git-terminology/)
identifies this overloaded wording. The following collaboration lesson develops
upstream and integration language rather than requiring a full workflow here.

### 3) **Distinguish a hosted fork from a branch and a local clone**

In GitHub's usage, a **fork** is a separate repository connected to another
repository through the hosting platform's relationship. It has its own branches
and collaboration space under the platform's permission rules. A branch remains
inside one repository. GitHub's [fork reference](https://docs.github.com/en/pull-requests/reference/forks)
makes the repository boundary explicit; “separate” does not mean every visibility
or permission policy is independent of the original.

A common arrangement has three repositories: the team's hosted repository, Bob's
hosted fork and Bob's local clone of that fork. The local clone's `origin` can
point to Bob's fork, while another configured remote points to the team. In a
different arrangement, `origin` points directly to the team. Inspect configuration
before interpreting “I pushed to origin.” A successful update to Bob's fork is
not automatically an update to the team's repository.

A fork does not automatically accept Bob's future changes into the original.
Likewise, a local clone is not automatically registered as a hosted fork. The
word “fork” also has a broader project meaning: a continuing development effort
that diverges from another project. Clarify whether the discussion concerns a
hosting relationship, a repository copy or a separate maintained project.

Practice: Bob says, “I committed the fix, created tag v1.0.0 and pushed my fork.
The team and production therefore have the fix.” The first statements need their
actual target and result evidence, but even if true they do not establish the
last sentence. Check which commit the tag resolves to, which references the push
updated, whether the team's repository accepted the change, and which source and
artifact a deployment used. A version-shaped name does not fill those gaps.

Change one fact: the team now verifies its `main` at C2, containing the fix. That
supports the source-history claim for the team. Production deployment remains
unverified. Evidence about one repository does not update every other boundary.

### 4) **Common confusion**

`main` names a branch in a particular repository. Two repositories can both have
that name while pointing to different commits. Conversely, several branch or tag
names in one repository can identify the same commit. Always pair the name with
its repository and relevant observation time.

A source archive download is not necessarily a Git clone: it may contain files
without history, references or remote configuration. A clone can also be shallow
or partial, limiting the history or objects obtained. Do not treat every copy
called a clone as a complete backup of repository history, hosted issues, external
artifacts and all working-tree files.

### 5) **Performance note**

A branch reference need not duplicate the whole working tree or object history.
Cloning and fetching can instead incur object transfer, storage and checkout work;
options that omit history or objects can change later access requirements. The
number of branch names alone is not a useful transfer-size estimate. These tables
measure no network cost, clone duration, storage use or branch-switch latency.

### 6) **Mentor note**

Give the learner the table before Bob's fetch and ask whether equality of his two
local references proves equality with the team's server. Then reveal the fetch
and ask which reference moved. For a fork, have them name all three repositories
and the destination of origin before interpreting a push. A sound answer follows
references and evidence rather than assuming a name identifies one universal copy.
