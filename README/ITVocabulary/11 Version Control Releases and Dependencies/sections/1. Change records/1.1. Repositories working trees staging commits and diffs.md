## 1.1. Repositories working trees staging commits and diffs

You save a corrected file, make a commit and discover that the correction is
missing from history. Saving, staging and committing are three different actions.
Git can simultaneously retain one committed version, prepare another version for
the next commit, and leave a third version in the file you are editing.

This lesson introduces those records before full collaboration workflows. The
example was run with Git 2.53.0 and Bash 5.3.9 on Linux x86_64. Current Git 2.56
reference semantics were checked 2026-10-19; the tested binary is explicitly the
older version, not a claim to have run the current release.

### 1) **Separate recorded history from editable and proposed contents**

**Version control** records versions and relationships so people can inspect and
combine changes. **Git** is a version-control system. A Git **repository** contains
its object database, references and associated metadata; in ordinary project
conversation, “repo” also commonly means the whole checkout. Ask which meaning
matters when discussing a copy or a missing file.

A **working tree** is the checked-out file/directory view you edit. It can include
tracked and untracked files. Git's repository metadata is commonly reached through
`.git`; that path can be a directory or a file pointing elsewhere, so do not use
its visible shape as the definition of a repository. A bare repository can have
history without a working tree. These distinctions are described in Git's
[glossary](https://git-scm.com/docs/gitglossary).

The **index**, also called the **staging area**, prepares the next snapshot.
**Staging** a file records selected contents there. It is not a continuing promise
to include whatever that file contains when you eventually commit. Git's
[`add` reference](https://git-scm.com/docs/git-add) explains both whole-file and
partial-change staging. Here we use whole files only.

A **commit** is a recorded snapshot with metadata and parent relationships. A
**commit ID** identifies that commit object. Parents connect the history: an
initial commit has none, an ordinary following commit has one, and a merge commit
can have multiple parents. Git's current
[data-model guide](https://git-scm.com/docs/gitdatamodel) distinguishes immutable
objects from references to them. An edit or an amended record does not mutate an
existing commit object into different contents under the same ID.

The snapshot describes the versioned tree, not necessarily every file on disk.
Untracked files and later unstaged edits need not be included. A commit message
such as “Fix report” is an explanation supplied by a person, not evidence that a
test passed, a server deployed or another repository received the commit.

### 2) **Observe three versions of one file**

Use a new, empty example folder outside your existing project checkouts, and run
these commands there. They create one local repository and its `note.txt`; they
contact no hosting service. The example assumes ordinary Git text handling without
custom content filters. `printf` writes the stated line; `cat` prints the current
file. Run the block in Bash with Git installed.

`init` creates the repository, naming its initial branch `main`. A branch is a
named line of history, developed in the next lesson. `add` stages the named path.
The first `commit` records the one-seat file. Its `-c` options supply synthetic
identity and disable signing/hooks for this demonstration command only; they do
not change global configuration. `-m` supplies the message, and `--quiet` suppresses
routine setup/commit messages. `--` separates command options from file paths.

```bash
git init --quiet --initial-branch=main --template=
printf 'Seats: 1\n' > note.txt
git add -- note.txt
git -c user.name='Vocabulary Demo' -c user.email='demo@example.test' \
  -c commit.gpgsign=false -c core.hooksPath=/dev/null \
  commit --quiet -m 'Record first note'
printf 'Seats: 2\n' > note.txt
git add -- note.txt
printf 'Seats: 3\n' > note.txt
git status --short
git show HEAD:note.txt
git show :note.txt
cat note.txt
git diff --cached --numstat -- note.txt
git diff --numstat -- note.txt
```

Observed output; the final two rows have tab-separated fields:

```text
MM note.txt
Seats: 1
Seats: 2
Seats: 3
1	1	note.txt
1	1	note.txt
```

`HEAD` identifies the current commit in this ordinary checkout. `git show
HEAD:note.txt` reads that commit's file, and `git show :note.txt` reads the index's
file in this no-conflict example. The results establish three distinct states:

| Location | Contents | How it got there |
|---|---|---|
| Current commit | `Seats: 1` | First staging followed by commit |
| Index | `Seats: 2` | Second staging |
| Working tree | `Seats: 3` | Later file edit, not staged |

Git's [short-status reference](https://git-scm.com/docs/git-status#_short_format)
uses two status columns for this ordinary tracked-file case. The first `M` means
the index differs from the current commit; the second means the working-tree file
differs from the index. The file is both staged and modified. There is no
contradiction and Git has not forgotten the third edit.

A plain commit without additional path or automatic-staging options would record
the two-seat staged version. The three-seat edit would remain on disk outside
that commit. Git's [recording-changes chapter](https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository)
explains this staged-then-edited case. Checking the file in your editor alone is
therefore insufficient to inspect what the next plain commit will contain.

Variation: in a fresh run, insert one more `git add -- note.txt` immediately before
`git status --short`. Now status is `M  note.txt`, and both the index and file show
three seats. The final unstaged diff is empty. Staging copied the later contents;
it did not change the existing one-seat commit. This variation demonstrates why
the timing of staging matters.

### 3) **Name both sides of a diff and the evidence still missing**

A **diff** describes differences between selected inputs. A **patch** commonly
means a textual representation of changes that a tool can inspect or apply; it
is not itself the same record as a commit. Commits carry snapshots and history
relationships, while a diff depends on which two versions are compared.

In the example, `git diff --cached` compares the index with the current commit.
`--staged` is a synonym for this option. Plain `git diff` compares working-tree
changes with the index. The [diff reference](https://git-scm.com/docs/git-diff)
also provides commit-to-commit and other comparisons; never interpret “the diff”
without knowing its endpoints. These commands' `--numstat` option reports added
and deleted text-line counts and the path. A replacement of one line produces
one addition and one deletion in each comparison here.

For the first comparison, the change is one seat to two. For the second, it is
two to three. Identical numerical summaries do not mean identical contents.
Likewise, an empty unstaged diff in the variation does not mean the index matches
the old commit: the staged difference still exists. Use the relevant comparison
rather than inferring a clean checkout from one empty output.

A **tracked file** has an entry in Git's index; an **untracked file** is outside
that tracked set. An **ignored file** matches applicable ignore rules and can be
omitted from ordinary untracked reporting. Ignoring does not remove an already
tracked file from history. “Clean” usually means no reported pending changes in
the compared checkout, not that the program is correct or that ignored local
files cannot affect a run.

Julia Evans's original [Git terminology investigation](https://jvns.ca/blog/2023/11/01/confusing-git-terminology/)
shows how index, staged and cached wording can obscure this model. Treat that as
an aid to reading the command, not a rule that every option with one of those
words has identical behavior. Her later
[documentation-contribution account](https://jvns.ca/blog/2026/01/08/a-data-model-for-git/)
connects the newer data-model guide with questions from actual readers.

Practice: “My editor shows three seats, so my teammate will receive three when I
commit.” What is missing? First inspect the staged contents and exact commit
operation. In the original run, a plain commit records two. Then establish how
the teammate obtains that recorded commit; local recording alone does not show
sharing. Do not change files or rewrite history merely to answer that question.

### 4) **Common confusion**

Saving an editor buffer writes working-tree contents; staging prepares selected
contents; committing records a snapshot. They need not contain the same version.
Calling all three “saved” hides the evidence needed to recover a missing change.

Git's index is not a database query index or a book's topic index. Likewise, a
Git commit records version history, while a database commit accepts transactional
changes under a separate contract. A Git commit does not roll back an external
service action or prove persistent application data is valid.

### 5) **Performance note**

A snapshot model does not imply that Git physically duplicates every unchanged
file for every commit. Existing objects can be reused and storage representation
can be compressed. Repository size, changed content, filesystem checks and diff
work affect cost; a one-line count is not a performance measurement. This tiny
run measures version contents and status only, with no commit-speed, storage-size
or large-repository benchmark.

### 6) **Mentor note**

Ask the learner to predict all three seat values before revealing the output.
Then add the final staging operation and ask which value changes location and
which old record stays the same. A sound answer distinguishes editor state,
proposed snapshot and recorded history. For a diff, require both endpoints before
accepting “nothing changed” or “this is what was committed.”
