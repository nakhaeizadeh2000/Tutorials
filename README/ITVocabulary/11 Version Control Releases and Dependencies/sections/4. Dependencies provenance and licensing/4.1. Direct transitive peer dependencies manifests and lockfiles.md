## 4.1. Direct transitive peer dependencies manifests and lockfiles

“The dependency did not change” can mean that a declaration stayed the same, that
an exact selected version stayed the same, or that a running program loaded the
same files. Those statements need different evidence. A package name in a manifest
cannot establish all three.

Start with the earlier package and module lesson and this domain's compatibility
lesson. This page uses npm 12 documentation checked on **2026-10-19** as a concrete
example of package-manager terminology. The records below are invented reading
artifacts; no package installation is required or claimed.

### 1) **Read dependency roles relative to a particular project**

A **direct dependency** is declared by the project under discussion. A **transitive
dependency** is reached through another dependency. These describe relationships,
not permanent categories attached to a package name. If an application declares
both a reporting library and a formatting library, while reporting also requires
formatting, formatting is reached by both a direct and an indirect path.

A **dependency graph** records these requirements as connections between components.
It can contain multiple versions of a package; a list of distinct names loses
that information. A **development dependency** supports work such as building or
checking the project. That purpose does not prove its code or generated output
is absent from a delivered application.

Read this complete, fictional `package.json` manifest as data. The names identify
invented packages, not downloads to try:

```json
{
  "name": "report-demo",
  "version": "1.0.0",
  "private": true,
  "dependencies": {
    "report-sdk": "^2.4.0",
    "report-plugin": "1.0.3"
  },
  "devDependencies": {
    "quality-checker": "3.1.0"
  }
}
```

The application directly declares `report-sdk` and `report-plugin`, plus the
checker for development work. For this exercise, the SDK's metadata also declares
`format-core`, which the application does not declare. Relative to the application,
`format-core` is transitive. Relative to the SDK, it is direct.

The plugin's metadata declares the SDK as a **peer dependency**: it describes a
compatible host with which the plugin is intended to operate. This relationship
matters when the application supplies a host and expects a plugin to work with
that host. A private, unrelated copy inside the plugin does not by itself establish
that relationship. Domenic Denicola's original [peer-dependency explanation](https://nodejs.org/en/blog/npm/peer-dependencies)
develops this motivation; its historical npm installation behavior is not today's
contract.

In current npm, ordinary peers are installed by default; optional peers and
configuration require separate attention. An **optional dependency** can be absent
under the manager's applicable rules, and application code must handle the absence
if it needs to continue. These are distinct roles, rather than synonyms for
“unimportant.” See npm's [manifest fields](https://docs.npmjs.com/cli/v12/configuring-npm/package-json/)
for the concrete declarations and conditions.

### 2) **Separate requested constraints from resolved and installed versions**

A **manifest** describes a project and its requirements. A **version range** allows
a set of versions under a manager's matching rules. In this example, `^2.4.0`
admits both normal versions `2.4.2` and `2.6.0`; it does not name one exact installed
version. Do not extrapolate that example into the rules for every zero-major or
pre-release range. An exact declaration such as `1.0.3` is often called a **pin**.
Pinning a direct dependency alone does not select all of its transitive versions.

**Resolution** selects concrete dependencies subject to requirements and manager
policy. **Installation** makes the selected contents available in an environment.
Configuration can influence both stages. For example, npm 12 supports root
`overrides` for existing dependency selections and `packageExtensions` for repairs
to dependency metadata; raw upstream declarations are not necessarily the entire
resolution input.

A **lockfile** records concrete resolution information so later work can reuse
selected inputs rather than choose afresh from ranges. npm's
[`package-lock.json` documentation](https://docs.npmjs.com/cli/v12/configuring-npm/package-lock-json/)
explains its recorded dependency tree and reviewable change history. A lockfile
change can therefore matter even when the application's manifest is unchanged.
Review both artifacts together when reviewing an update. In npm 12, the older
`npm-shrinkwrap.json` file is no longer read or written; historical instructions
that treat it as an alternative need a version check.

The **installed dependency tree** describes what is actually present for a given
environment. It need not contain every locked entry. npm's
[`omit` contract](https://docs.npmjs.com/cli/v12/commands/npm-ci/#omit) explicitly
allows categories to remain resolved in the lockfile while absent from disk.
Conversely, an existing directory is not evidence that the intended installation
job produced it or that a running process loaded those files.

Keeping reviewed lockfiles supports repeatable dependency selection. It does not
alone establish identical build outputs across operating systems, toolchains and
configuration, or successful application behavior. Record the relevant environment
and verify the outcome that matters.

### 3) **Diagnose a disagreement without inventing its cause**

Read the following constructed observations. They concern the same project copy
and the root installation location of `report-sdk` at the stated inspection time.
The table summarizes records; it is not a generated npm lockfile or command trace.

| Evidence | Recorded value |
|---|---|
| Application manifest | `report-sdk` requested as `^2.4.0` |
| Checked-in lockfile | That dependency selected as `2.4.2` |
| Inspected installed package metadata | Root installed copy reports `2.6.0` |
| Process that generated yesterday's report | Its loaded dependency was not recorded |

The manifest permits both observed version numbers. It therefore cannot settle
which exact version was installed. The lock and the inspected root copy disagree,
but the table does not explain why. A different command, configuration, project
state or subsequent modification remains a hypothesis. Yesterday's running code
is also unestablished: today's directory inspection cannot supply missing history.

A useful handoff says: “The reviewed lock selects SDK 2.4.2, while this copy's root
installation reports 2.6.0. Please identify the installation command, manager
version, working directory, configuration and artifact used by the report job.”
Deleting the lockfile immediately would remove relevant evidence and can select
other versions; first establish the intended inputs and the mismatch's origin.

As one bounded product example, npm 12's [`npm ci` contract](https://docs.npmjs.com/cli/v12/commands/npm-ci/)
requires a lockfile and fails rather than updating it to reconcile a manifest
mismatch. That documented behavior is not proof that this fictional job ran that
command. No npm command was executed for this exercise.

Practice: remove the installed-metadata row. Can you still say the installation
is wrong? No. You know the declared range and locked selection, but lack the
observation needed to compare them with installed contents. Adding a successful
installation log would provide more evidence about that job; it still would not
prove the report used the intended files or produced correct results.

### 4) **Common confusion**

“Peer” does not mean “the manager never installs it.” That claim often comes from
older npm behavior. Read the current manager's contract and the specific optional
peer and configuration settings before interpreting an installation result.

“Development” also does not mean “cannot affect production.” A development-time
compiler can change the produced application. Classify the role first, then trace
which inputs contributed to the artifact and which code the runtime loads.

A lockfile is neither the manifest's spelling repeated nor a census of a running
process. Each answers a different question. Keeping these questions separate makes
an unchanged manifest and changed behavior a useful investigation, not a paradox.

### 5) **Performance note**

Dependency work has several costs: resolving metadata, obtaining contents,
installing them, building outputs and loading or executing code. Lock information
can avoid some repeated resolution work, but neither a locked-entry count nor a
manifest's number of direct dependencies predicts download size, startup time or
request latency. Omitted development tools and unused packaged files make those
counts especially different from runtime work. This lesson measures none of those
costs; inspect and measure the stage relevant to the claim.

### 6) **Mentor note**

Ask the learner to draw application → SDK → formatter, then add application →
plugin and the plugin's peer requirement on the SDK. They should explain which
relationships are direct from each viewpoint and why the host relationship needs
its own compatibility evidence. Next, show only the manifest and ask for the exact
running SDK version. A sound answer requests additional evidence rather than
guessing from the range. Use the removed-row practice to test that discipline.
