## 3.1. SemVer compatibility breaking changes and deprecation

A dependency changes from 2.4.3 to 2.4.4. Does that prove your application can
upgrade without problems? The number can communicate a compatibility contract,
but you must first know whether the project adopts that contract and what public
interface it covers. Then inspect what the actual update does.

This lesson uses Semantic Versioning 2.0.0 and source explanations checked
2026-10-19. All release and booking examples are constructed reading exercises;
no package update or application compatibility test is reported.

### 1) **Read the version scheme and its declared interface**

**Semantic Versioning**, or **SemVer**, assigns meaning to version changes relative
to a declared public API. For a normal version `MAJOR.MINOR.PATCH`, the three
components are nonnegative integers without leading zeroes. Under the version-1+
contract, an incompatible public-API change requires a major increment, compatible
new functionality a minor increment, and compatible bug fixes a patch increment.
A minor increment resets patch to zero; a major increment resets both lower
components. The [SemVer 2.0.0 specification](https://semver.org/spec/v2.0.0.html)
defines these rules and requires released version contents to remain unchanged.

A **major version**, **minor version** and **patch version** therefore describe
positions and their adopted change rules, not the amount of code edited. One
removed field can be breaking; a large private implementation replacement can
preserve the public contract. A project using date-based labels or another
policy does not acquire SemVer promises merely by displaying periods and numbers.

For example, a hypothetical booking SDK at 2.4.3 declares a function that returns
the total seats in approved bookings, returning zero for an empty input. It also
declares its supported inputs and error behavior. That public contract is the
comparison point, not the current folder layout or a screenshot of one result.
The [API-contract owner](<../../../07 APIs Protocols and Integration/sections/1. Interfaces and contracts/1.1. APIs endpoints routes operations and contracts.md>)
explains the interface boundary in detail.

**Version precedence** is comparison order, not a decimal fraction: `2.10.0`
follows `2.9.0`. A hyphen introduces a **pre-release identifier**, such as
`3.0.0-rc.1`, which precedes normal `3.0.0`. A plus sign introduces **build metadata**;
`3.0.0+build.7` and `3.0.0+build.8` have equal SemVer precedence. That does not mean
their names or build records are identical. Major-zero `0.y.z` has no stable
public-API promise under SemVer's initial-development rules. A leading `v` can
be an ecosystem's tag convention rather than part of the core SemVer string.

Go's [module-version guide](https://go.dev/doc/modules/version-numbers) supplies
a concrete ecosystem applying version components and pre-release labels. Its
Go-specific paths and pseudo-versions are separate tool behavior, not syntax to
copy into every package manager. Release lifecycle labels receive their own
explanation in the following lesson.

### 2) **Judge compatibility from a consumer's required behavior**

**Backward compatibility** means that the newer component preserves the relevant
contract for consumers of the older interface. State the environment and covered
behavior. A **breaking change** violates that compatibility boundary, potentially
requiring a consumer change. **Forward compatibility** instead concerns an older
consumer or component handling relevant newer inputs or counterparts. Neither
phrase means every possible old/new pairing works.

Read this fictional release review. The SDK explicitly adopts SemVer after 1.0.0.
Each row is an independent candidate change from 2.4.3, not one cumulative release:

| Candidate change | Compatibility reasoning | Appropriate signal under the stated policy |
|---|---|---|
| Fix an internal empty-input defect so the documented result is zero; preserve the declared API | Restores promised behavior without introducing an incompatible API change | A patch, such as 2.4.4 |
| Add a separately named report function while preserving all existing calls and results | Compatible new public functionality | A minor, such as 2.5.0 |
| Rename required response field `seats` to `quantity` and stop returning `seats` | An old consumer reading the promised field loses it | A major, such as 3.0.0 |
| Keep the old function working but mark its public use deprecated | Removal has not happened; the deprecation must be communicated | A minor increment under SemVer, with migration guidance |

Calling the field rename a cleanup or bug fix does not change its public effect.
Publishing that change as 2.4.4 would conflict with the stated versioning contract.
Conversely, a major increase does not prove that your particular application uses
the changed API. Inspect the relevant change and consumer before declaring that
all users must edit their code.

“Additive” also needs a use case. A newly added optional argument might preserve
direct calls while changing a callable type another program assigns or implements.
Go's original [module-compatibility article](https://go.dev/blog/module-compatibility)
shows exactly that distinction with a variadic function extension. The general
question is which supported uses must remain valid; adding a feature is not an
automatic compatibility proof across all interfaces and languages.

For a message format, an old consumer that rejects unknown fields may reject a
new response field. Another consumer explicitly permitting extensions may accept
it. To judge the change, inspect the actual schema and extension contract rather
than assuming that all optional additions are harmless. A new producer accepting
old requests and an old reader accepting new responses are different directions.

SemVer states obligations; it cannot prevent an implementation defect or discover
every consumer dependence. Hynek Schlawack's original
[compatibility critique](https://hynek.me/articles/semver-will-not-save-you/)
highlights unintended breakage and the difference between maintainer intent and
application outcomes. Use that warning to inspect release notes and relevant
integration evidence, not to erase the value of a declared versioning contract
or treat all upgrades as equally risky.

In the empty-input row, a consumer might have built a workaround around the old
error. Investigate that reliance when checking the update. It does not turn every
possible dependence on an undocumented defect into the declared API. Keep the
promised contract, observed behavior and your application's assumptions visible.

### 3) **Separate deprecation and support from actual removal**

**Deprecation** discourages continued use under a project's policy; it is not
removal. The earlier [status-language owner](<../../../01 Reading and Using Technical Language/sections/2. Reading technical documents/2.2. Requirements guarantees defaults and support status.md>)
explains that boundary. Here SemVer adds a versioning consequence: marking public
functionality deprecated requires a minor increment in the version-1+ scheme.
Removing that functionality later is an incompatible change, requiring a major
increment under that contract.

A **migration guide** explains how consumers adapt. It should identify changed
inputs, outputs and behavior, not merely announce “use the new version.” Suppose
2.5.0 deprecates `totalSeats` in favor of `approvedSeatTotal`, while both continue
to return the same documented value. A guide can name that substitution and any
real differences. It cannot silently replace a total with a booking count, which
answers another question.

A **breaking-change notice** identifies the affected contract and adaptation.
For the `seats` rename, include the old/new field, the version boundary and how
readers handle a transition. Whether old and new deployed components must coexist
is an additional integration requirement. Changing a version number does not
perform the migration or establish that every running client was updated.

Practice: “The old function is deprecated in 2.5.0, so it is removed now, every
2.x release is unsupported, and the upgrade is safe because it is minor.” None
of those three conclusions follows. The stated deprecation does not remove the
function; maintenance dates come from the project's support policy; and actual
consumer compatibility still needs evidence. A precise note records the new
preferred function, the old behavior still available, any announced removal
version and the checks actually performed. Leave missing dates unknown.

Version identity also has a subject. A library's 2.5.0, a service's API `v1` and
a repository tag can identify different artifacts and contracts. Link the release
record to the actual dependency or deployed interface before comparing numbers.
A release label alone supplies no support duration, security assessment or
production-readiness result.

### 4) **Common confusion**

A “patch” can mean a version component or a textual change representation. The
[Git lesson](<../1. Change records/1.1. Repositories working trees staging commits and diffs.md>)
owns the latter. A large patch file is not automatically a major version change,
and a small edit can break a public contract.

Likewise, stable API promises and defect-free execution differ. Ignoring a
publisher's explicit breaking-change notice because your code still compiles can
miss a changed value meaning or runtime interaction. Conversely, counting a new
major number as proof that every old operation fails exaggerates the evidence.

### 5) **Performance note**

A major, minor or patch number has no direct speed or memory effect. A compatible
implementation can still have performance differences, and a claimed optimization
needs its own workload and measurement boundary. If a cost or latency bound is
part of the declared public contract, include it in the compatibility assessment.
No upgrade, throughput or latency benchmark was run for these release cards.

### 6) **Mentor note**

Ask the learner to defend the release signal for the field rename by naming an
old consumer that would fail. Then change the contract to explicitly permit an
added field and ask which direction of compatibility is being considered. For a
deprecation note, require separate answers about current availability, announced
removal and maintenance dates. A strong answer reads the policy and evidence
rather than rewarding memorized major/minor/patch expansions.
