## 3.2. Alpha beta release candidates stable LTS and EOL

A download can be newer without being a final release. A final release can be
outside maintenance, and an older release line can still receive fixes. Read
release readiness, compatibility and maintenance as separate claims before
interpreting “latest supported version.”

This lesson builds on the preceding SemVer and earlier status-language lessons.
Publisher examples were checked **2026-10-19**. The exercise's report SDK and its
dates are fictional; the Node.js and Python examples are dated source readings,
not runtime installations or upgrade recommendations.

### 1) **Read release readiness from the publisher's own criteria**

**Alpha** commonly labels early testing releases whose features or behavior can
still change substantially. **Beta** commonly labels a later testing phase, often
with more settled features. A **release candidate**, or **RC**, is a proposed
candidate for the final release, subject to the project's remaining checks and
fix policy. Those conventions are useful orientation, not universal definitions
of feature completeness, audience size or remaining defect counts.

For a concrete policy, Python's [development-cycle guide](https://devguide.python.org/developer-workflow/development-cycle/)
allows feature development during alpha, freezes new features at the first beta,
and restricts RC changes to reviewed fixes appropriate before final release.
The goal of no code changes between RC and final is not a guarantee that the
candidate has no serious defects or that every project uses Python's rules.
Do not apply that feature-freeze criterion to a different product's beta without
reading its policy.

**Final**, **stable** and **general availability**, often **GA**, indicate release
status under a publisher's criteria. They do not promise zero defects, every
platform supported, or compatibility with every integration. GA is especially
common in service/product announcements; ask which feature, region or platform
the announcement covers. A publisher can make one feature generally available
while another feature in the same product remains preview.

A **release channel** groups releases for an intended audience or policy, such
as stable, beta or nightly. A **nightly build** is typically produced frequently
from ongoing development; its name does not establish a release review outcome.
A “latest” selector may mean latest in one channel rather than highest among
all labels. Check that channel and the exact resolved artifact before reporting
the version tested.

The [SemVer owner](<3.1. SemVer compatibility breaking changes and deprecation.md>)
explains pre-release ordering. A candidate such as `4.0.0-rc.1` is not the same
version identifier as final `4.0.0`. A local run on one does not become evidence
of running the other because the names look similar. Likewise, Python's `rc1`
spelling follows Python's version convention; do not demand identical suffix
syntax across ecosystems.

### 2) **Separate a release line's maintenance from an installed patch**

A **release line** is a maintained family of versions, such as a major or
major/minor branch under the project's policy. **Long-term support**, or **LTS**,
usually names a longer maintenance commitment for a selected line. It needs an
owner, supported changes, platforms and end date. There is no universal LTS
length or guarantee that every feature remains unchanged.

Node.js's [release working-group schedule](https://github.com/nodejs/Release)
distinguishes **Current**, **Active LTS** and **Maintenance LTS**. Active LTS
admits changes audited for that line; maintenance focuses on critical bug and
security fixes with limited discretionary changes. In the schedule read on
2026-10-19, 24.x is Active LTS, 22.x is Maintenance LTS and 26.x is Current.
The schedule lists 24.x maintenance starting 2026-10-20 and 26.x Active LTS
starting 2026-10-28, and explicitly allows date changes. Planned transitions
are not already-completed transitions.

The separate [Node.js releases page](https://nodejs.org/en/about/previous-releases)
also announces a changed annual cycle starting with 27. Therefore, extending the
historical odd/even rule indefinitely would misread the published direction.
This is an announced schedule policy, not a claim that a future release or its
LTS transition has already occurred. Look up the applicable line and observation
date rather than deriving all future support from number parity.

Python's [version-status table](https://devguide.python.org/versions/) uses
feature, bugfix, security and end-of-life states rather than labeling every
supported branch LTS. On the same check date, 3.15 and 3.14 are in bugfix status,
3.13 is in security status, and 3.10 is end-of-life. Several lines can receive
maintenance simultaneously while admitting different categories of changes.
These are branch policies, not a claim that any arbitrary old patch in the family
contains subsequent corrections.

An installed `2.8.1` and a maintained `2.x` line are different subjects. The line
can still receive updates while that installation lacks later fixes. Conversely,
a newer major line's existence does not itself end maintenance of the older
line. Read the release record for the exact artifact and the support policy for
the line; neither one replaces the other.

**End of life**, or **EOL**, means the specified publisher's maintenance commitment
has ended under its policy. The program may still launch, and historical downloads
may remain available. “It runs” does not establish continued fixes. A separate
vendor or service can offer another support arrangement, but its scope must be
established separately rather than attributed to the original project.

### 3) **Interpret a release matrix without inventing a recommendation**

This constructed report-SDK policy is deliberately different from the real
publisher examples. Read it as a complete exercise card:

| Report SDK label | Stated status | Stated maintenance scope |
|---|---|---|
| 2.8.1 | Final; line 2.x designated LTS | Critical fixes through 2027-06-30, with later 2.x patches published separately |
| 3.1.0 | Final; line 3.x designated Current | Feature and bug updates through 2027-01-31 |
| 4.0.0-rc.1 | Candidate in preview channel | Evaluation only; final date and maintenance period not announced |

A teammate says, “Choose 4 because it is latest and stable. Otherwise choose 3,
because a higher major has longer support. Our 2.8.1 installation is fully fixed
because 2.x is LTS.” What can the card support?

Version 4's listed artifact is a candidate in preview, not the card's final
release. Versions 2.8.1 and 3.1.0 are both final. The listed 2.x maintenance window
ends later than 3.x, so highest major does not imply longest support. However,
the card does not say which later 2.x patches exist or whether the installed
2.8.1 includes them. It also supplies no application-compatibility evidence for
moving between major versions.

A precise response is: “The preview artifact is 4.0.0-rc.1. The card lists final
releases on both 2.x and 3.x, with different support scopes and dates. We need the
exact available patches, platform requirements and our integration results before
choosing an upgrade.” The [version-compatibility lesson](<3.1. SemVer compatibility breaking changes and deprecation.md>)
owns that last assessment; this card does not perform it.

Now add evidence that the installed artifact is 2.8.4, with a release note naming
a particular fix. You can strengthen the exact-version and included-fix statement.
You still cannot claim all defects are fixed, that every dependency is supported,
or that 3.1.0 was tested successfully. Changing one row's evidence does not settle
the entire system's readiness.

### 4) **Common confusion**

A release status applies to a specified artifact or line; a feature status can
apply to only one API inside it. A stable runtime can include experimental APIs,
and a maintained runtime does not establish maintenance of every library used
with it. Name the subject before repeating the label.

**Deprecated** also differs from EOL. Deprecation can discourage one feature
while its containing release remains maintained. EOL concerns the stated release
or product's maintenance boundary. The earlier
[status-language lesson](<../../../01 Reading and Using Technical Language/sections/2. Reading technical documents/2.2. Requirements guarantees defaults and support status.md>)
keeps availability, recommendation and maintenance meanings distinct.

### 5) **Performance note**

Alpha, stable, LTS and EOL do not directly specify speed or resource use.
Different releases can change performance, but a status label does not measure
the workload. Maintenance windows influence planning and compatibility work, not
automatically request latency. These tables contain no benchmark or capacity
result, and a preview build's newer number is no evidence of a speed benefit.

### 6) **Mentor note**

Ask the learner to name the subject, policy owner, observation date and promised
change scope for one row. Then move the observation date across a scheduled
transition and require a fresh source check rather than an assumed transition.
For the fictional card, ask which final line has the later end date and what is
still unknown about an old installed patch. A sound answer separates readiness,
maintenance and actual artifact evidence.
