## 2.1. Merges rebases conflicts and pull requests

Two branches can each be reasonable in isolation while their combined behavior
is wrong. Git's ability to combine text, a reviewer's approval and a completed
integration record answer different questions. Read the proposed change, its
history and its verification evidence separately.

This lesson assumes the preceding commit and reference vocabulary. Its histories,
configuration edits and review packet are constructed, not executed Git operations.
Current Git and GitHub explanations were checked 2026-10-19.

### 1) **Distinguish joining histories from replaying changes on a new base**

A **merge** integrates development histories. A **merge commit** records a
combined result with multiple parents. In a **fast-forward**, the current branch
reference can advance to an existing descendant commit without a new merge commit.
Git's [merge reference](https://git-scm.com/docs/git-merge) distinguishes these
outcomes. “Merged” does not always mean “a new two-parent commit was created.”

Use this fictional history: C1 is shared; `main` advances to C2 with parent C1;
`report-fix` independently advances to F1 with parent C1. The branches have
**diverged**: each has a commit outside the other's ancestry. A normal two-parent
merge can create M1 with parents C2 and F1. It retains both original histories
and records their chosen combined snapshot. No branch name needs to disappear.

A **rebase** instead replays selected changes onto another starting point. In
this simple example, replaying F1's change onto C2 creates F2 with parent C2, and
`report-fix` moves to F2. F1 and F2 are different commit objects because their
recorded parents differ, even if the intended report fix is the same. This is
**history rewriting** from the branch's perspective, not in-place mutation of F1.
The [rebase reference](https://git-scm.com/docs/git-rebase) describes replay and
its conflict behavior; options and already-applied changes can alter which commits
are replayed in real workflows.

| Operation in this example | Resulting parent relationships | What stays unproven |
|---|---|---|
| Two-parent merge | M1 has parents C2 and F1 | Combined behavior meets requirements |
| Rebase report-fix onto main | F2 has parent C2; C2 has parent C1 | Replayed behavior preserves the intended fix |
| Later fast-forward main from C2 to F2 | main now names existing F2 | A deployment or runtime check occurred |

Pro Git's [rebasing chapter](https://git-scm.com/book/en/v2/Git-Branching-Rebasing)
compares integration histories through a concrete example. Its matching final
snapshots are an example, not a guarantee that every merge resolution and rebase
resolution produces identical files. Prefer the history shape that fits the team's
collaboration and review contract. A linear-looking history is not inherently
proof of a more correct program.

Rewriting commits that collaborators already use can leave them working from
superseded IDs and require coordinated recovery or integration. Agree on the
shared-history policy before doing that work. Conversely, a merge commit can
preserve a branching decision useful for later inspection. These are collaboration
trade-offs, not a universal command preference or a force-push recipe.

A **pull** in Git fetches and then attempts to integrate the selected remote work
into the current branch under the configured policy. It can use fast-forward,
merge or rebase behavior, or refuse the attempted integration. Git's
[pull reference](https://git-scm.com/docs/git-pull) explains the distinction from
fetching alone. A pull request, introduced below, is a separate collaboration
artifact; creating one does not run a local `git pull` for every reviewer.

### 2) **Separate unresolved text from incorrect combined behavior**

A **merge conflict** means Git cannot automatically reconcile a particular
combination under the selected operation and strategy. It can involve content,
deletions or other path changes. It does not prove that either contributor made
a mistake or that one whole branch must be discarded.

Consider one constructed configuration field, measured in accepted requests per
minute. The common version has `request_limit: 100`. Main changes it to 120 to
admit more work. The topic branch changes the same field to 80 to protect a
constrained dependency. The packet says Git reports a conflict. A **conflict
resolution** must establish the agreed policy and resulting contents. Choosing
120 because it is larger or 80 because it is “ours” does not supply that policy.
Ask which workload and dependency contract the release is meant to support.

Conflict markers in text display competing versions; deleting the markers alone
does not establish a correct resolution. Git's rebase documentation also explains
that “ours” and “theirs” follow operation roles, which can feel reversed while
rebasing: the so-far rebased series starts from the new base, while the replayed
work is on the other side. Inspect the actual versions and operation instead of
interpreting those words as everyday ownership labels.

Now consider a different packet with no textual conflict. Main changes an API's
accepted path from `/report` to `/reports` and updates its existing caller. The
topic branch adds a new caller in another file that still uses `/report`. The
packet explicitly says the merged service no longer accepts the old path. Git
combines the text successfully, but the new caller requests an unsupported path.
This is a **semantic conflict** in the combined behavior, even without a reported
text conflict.

The next check must exercise that caller against the resulting interface, not
merely search for conflict markers. A successful compile may help with some
contracts but need not detect a wrong string path. “Resolved,” “merged cleanly”
and “verified behavior” must therefore remain separate statements.

### 3) **Read the review artifact and its integration direction**

A **pull request**, or **PR**, proposes and discusses integrating changes. In
GitHub's terminology, the **base branch** is the target and the **head branch**
contains the proposed work. The repositories may differ when a fork contributes.
GitHub's [pull-request reference](https://docs.github.com/en/pull-requests/reference/pull-requests)
and [creation guide](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request)
make that direction explicit. A PR is a hosting collaboration feature, not a
commit object shared by every Git implementation.

The **author** proposes the change. A **reviewer** evaluates it and gives feedback;
an **approval** records that reviewer's decision under the platform and repository
rules. GitHub’s [review reference](https://docs.github.com/en/pull-requests/reference/pull-request-reviews)
explains review outcomes. Approving, merging and deploying are separate actions. A check result must
also identify what revision and cases it exercised. An earlier approval does not
by itself demonstrate that a later changed head received the same inspection.
Whether approvals are dismissed or further approvals are required is a repository
policy question, not a universal rule inferred from the word approved.

**Upstream** has several contextual meanings. A project's upstream repository is
an earlier source of development, such as the team repository from which Bob
forked. A branch's configured **upstream branch** instead supplies comparison and
integration information. Bob's local `report-fix` might track his fork's
`origin/report-fix`, while his project's upstream is the team's repository.
An optional remote literally named `upstream` is another naming convention.
The pull reference's upstream section describes the configured branch relationship.

**Downstream** describes a recipient or dependent relative to a named source.
Bob's maintained derivative can be downstream of the team project; an application
using a library can be downstream of that library. It is not the name of one
mandatory Git remote. Clarify which change direction the discussion concerns.

Practice packet: PR 42 proposes head `report-fix` into base `main`. A reviewer
approves head H1. The author later adds H2 containing the new old-path caller.
Only H1's check result is supplied; the PR remains open and no merge is recorded.
Can the status update say “the fix is reviewed, tested, merged and live”?

A supported update is: “H1 received approval and the supplied checks. The current
head H2 needs evidence for its changed caller and applicable review requirements.
The request remains open, with integration and deployment unverified.” The string
path check above is a candidate, not an executed test in this lesson. Adding a
verified merge record would establish that integration action, while production
still needs its deployment evidence.

### 4) **Common confusion**

A conflict is a request for a decision, not a vote about whose work is valuable.
The intended combined result can require parts of both changes or a different
implementation. A tool accepting the resolution says nothing by itself about the
business policy chosen for the request limit.

A remote-tracking comparison, PR target and deployment destination are different
boundaries. “Upstream is updated” must identify which repository or configured
branch relationship and which revision. Likewise, a reviewer can comment without
approving, and an approval does not move the base branch by itself.

### 5) **Performance note**

Merging and rebasing perform history and content work whose cost depends on the
repository and selected changes. A shorter-looking log does not prove faster
application execution. The important runtime consequence in these packets is a
potentially incompatible caller or changed admission policy; no resulting latency
or capacity was measured. Include appropriate behavior checks after integration
rather than treating the absence of text conflicts as a performance result.

### 6) **Mentor note**

Ask the learner to draw the parent relationships for M1 and F2, then explain why
F2 needs a new ID. Give them the conflict-free path change and ask which user
operation could fail. Finally change the PR head from H1 to H2 and require a
status update that preserves the older evidence without applying it automatically
to new work. A sound answer separates history, decision, verification and delivery.
