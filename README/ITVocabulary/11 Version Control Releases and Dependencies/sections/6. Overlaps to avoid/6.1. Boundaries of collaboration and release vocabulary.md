## 6.1. Boundaries of collaboration and release vocabulary

A branch, release number, lockfile and verification report can all identify useful
parts of a change. None substitutes for the complete workflow that produces,
checks and delivers software. Use this domain to understand what a record means;
choose deeper study from the operation or decision you actually need to perform.

### 2) **Choose implementation study from the operation and evidence needed**

Full Git workflows belong to the planned **Git & GitHub** track. That includes
choosing collaboration policies, recovering mistaken operations and managing
shared history. Recognizing “rebase” here is insufficient reason to rewrite a
shared branch. The correct action depends on actual references, working contents,
collaborators and recovery needs. This domain supplies interpretation, not a
universal command sequence for every repository.

Package resolution, publishing and runtime loading have their own mechanics.
Existing [JavaScript modules](<../../../../JavaScript/14 Modules and Code Organization/README.md>)
teach language-level imports and package entry points. The earlier
[package/module distinction](<../../../03 Software Execution and Developer Tools/sections/3. Tools and interfaces/3.2. Packages modules dependencies and package managers.md>)
explains why installing a distribution and loading a module are different acts.
A manager's full resolver, workspace or publication procedure needs that manager's
current documentation and the project's configuration; it should not be inferred
from this vocabulary example.

Producing a build, placing software in an environment and exposing changed behavior
to users are delivery concerns. Later infrastructure/delivery vocabulary and the
planned **DevOps** and **Production Toolchain** tracks develop those boundaries.
A Git tag alone cannot establish what a service is running. If a change also
modifies stored data, the existing [migration lesson](<../../../08 Databases Storage and Data Pipelines/sections/2. Relational and document language/2.2. Schemas constraints normalization and migrations.md>)
explains why returning source files to an earlier state does not itself restore
lost information or coordinate readers and writers.

Security implementation and risk assessment also extend beyond recognizing a
signature or SBOM. Origin checks do not settle credential exposure, application
permissions or vulnerability impact. Legal conclusions need the exact terms,
covered components and intended use. Route these decisions to their appropriate
technical or license-review owner. Keep a question concrete enough that the owner
can assess it rather than attaching an unexplained “secure” or “approved” label.

These deeper routes are learning guidance. Planned tracks are not assumed to be
published prerequisites for understanding the current lesson.

### 3) **Turn a mixed rollback request into separate, answerable questions**

Read this constructed handoff:

> The update failed. Reset the branch to yesterday's tag, restore the old lock,
> and we will have rolled back production. The older package was signed, so no
> further questions are needed.

The accompanying facts are narrower: yesterday's tag identifies application
commit `C4`; the running service's artifact is unrecorded; an earlier lock selects
SDK 2.4.2; the service also performs a data migration during its startup process.
No recovery action has been performed in this exercise.

A useful response separates the records and desired outcome:

> C4 identifies a recorded application state, and the earlier lock identifies
> a dependency selection. We still need the running artifact and deployment state,
> the intended recovery target, and the migration's effect on stored data. Please
> identify the service and data recovery owners before choosing the workflow.
> The older signature result needs its own subject and policy; it does not show
> that the earlier application can read the present data.

This does not prescribe resetting a shared branch or assert that a rollback is
impossible. It identifies missing evidence that could change the action. History
management, dependency selection, operational recovery and data compatibility are
different responsibilities even when one person handles several of them.

Practice: add a verified service record showing that the current instance runs
artifact `A6`, and a recovery rehearsal showing that `A4`, built from `C4` with
the selected dependencies, reads a copy of the current migrated data correctly.
The running-state question is now answered for that instance, and the stated
read path has useful recovery evidence. You still need to establish the actual
recovery procedure and its scope, including relevant writers and other instances.
A successful rehearsal is evidence about what it exercised, not proof that every
operational step has already happened.

### 4) **Common confusion**

A concept's owner and a team's responsible person are different meanings of
“owner.” The table routes an explanation; the handoff assigns or discovers who
can make and carry out a real decision. A documentation link cannot supply that
person's authority or evidence.

Likewise, “return to an old commit” and “restore the service's earlier behavior”
are different outcomes. The former identifies source history; the latter depends
on built contents, environment and state. Ask which outcome is required before
proposing a workflow.

### 5) **Performance note**

Correct classification has no direct effect on identical program instructions.
It can reduce investigation work by directing attention to the appropriate
record or stage. A source rollback does not establish that latency will return
to an earlier value if data, configuration or traffic differ. Measure the relevant
running workload after an actual change; this static handoff contains no timing
or recovery-duration experiment.

### 6) **Mentor note**

Ask the learner to mark every claim in the rollback request as a history,
dependency, artifact, runtime or data question, then name its next evidence source.
They should preserve the user's recovery goal while resisting an unsupported
command prescription. Add the rehearsal record and ask which uncertainty it
removes. A strong answer updates that part of the explanation and retains the
remaining operational questions without repeating every definition in this domain.
