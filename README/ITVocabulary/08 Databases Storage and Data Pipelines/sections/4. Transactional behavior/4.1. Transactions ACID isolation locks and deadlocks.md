## 4.1. Transactions ACID isolation locks and deadlocks

A booking operation may need to reduce available capacity and add a reservation.
Keeping only one change would leave the data inconsistent with the intended
operation. A database transaction supplies a boundary for related database work;
it does not automatically include an email, payment service or browser response.

Read the preceding schema, query and access-layer lessons. The complete example
runs on SQLite 3.54.1, Linux x86_64. PostgreSQL 18 provides explicitly scoped
isolation and lock examples, checked 2026-10-18.

### 1) **State the transaction boundary and the four ACID properties**

A **transaction** groups database work under defined completion and concurrency
rules. **Commit** accepts the transaction's database changes; **rollback** discards
its uncommitted changes within the database's transactional scope. PostgreSQL's
[transaction tutorial](https://www.postgresql.org/docs/18/tutorial-transactions.html)
illustrates grouping several updates with `BEGIN` and `COMMIT`, or cancelling with
`ROLLBACK`. Client libraries can also manage transaction boundaries.

**ACID** expands to **atomicity, consistency, isolation and durability**. SQLite's
[transactional overview](https://sqlite.org/transactional.html) uses this vocabulary.
Each letter addresses a different question:

| Property | Meaning to establish | What it does not establish by itself |
|---|---|---|
| Atomicity | Transactional changes are accepted as a unit or discarded | Every external effect belongs to that unit |
| Consistency | Declared invariants remain satisfied through correctly defined operations | The database invents missing business rules |
| Isolation | Concurrent transactions interact according to specified visibility and conflict rules | Every isolation level behaves as one serial execution |
| Durability | Accepted changes persist under the stated storage and failure assumptions | Survival of every possible storage loss or deletion |

An **invariant** is a condition intended to remain true, such as nonnegative
remaining capacity. The application and database rules must actually express and
preserve it. A transaction that atomically writes a negative value is still wrong
if the intended rule forbids that value and no mechanism prevented it.

Durability also needs the configured product and storage contract. PostgreSQL's
[reliability discussion](https://www.postgresql.org/docs/18/wal-reliability.html)
explains persistence and cache assumptions. SQLite's
[atomic-commit account](https://sqlite.org/atomiccommit.html#hardware_assumptions)
also makes hardware assumptions explicit. An in-memory demonstration cannot prove
survival of a process exit or power failure.

### 2) **Observe discarded and committed changes in a bounded example**

Use the SQLite executable from the query lesson. Save `transaction_reading.sql`
beside it and run `./sqlite3 :memory: < transaction_reading.sql` in that folder.
This creates its own temporary database with one workshop and no bookings.
The two `SELECT` expressions report remaining capacity and booking count.

```sql
.bail on
.headers off
.mode list
CREATE TABLE workshops (
  workshop_id TEXT PRIMARY KEY,
  remaining INTEGER NOT NULL CHECK (remaining >= 0)
);
CREATE TABLE bookings (booking_id TEXT PRIMARY KEY, workshop_id TEXT NOT NULL);
INSERT INTO workshops VALUES ('w4', 2);
BEGIN;
UPDATE workshops SET remaining = remaining - 1 WHERE workshop_id = 'w4';
INSERT INTO bookings VALUES ('r17', 'w4');
SELECT remaining, (SELECT count(*) FROM bookings) FROM workshops;
ROLLBACK;
SELECT remaining, (SELECT count(*) FROM bookings) FROM workshops;
BEGIN;
UPDATE workshops SET remaining = remaining - 1 WHERE workshop_id = 'w4';
INSERT INTO bookings VALUES ('r17', 'w4');
COMMIT;
SELECT remaining, (SELECT count(*) FROM bookings) FROM workshops;
```

Observed output:

```text
1|1
2|0
1|1
```

The first transaction can read its own pending changes: one remaining place and
one booking. Rolling back restores two places and no bookings. The second
transaction performs the same changes and commits; the final query sees one place
and one booking. This is one connection, so it does not demonstrate what a second
concurrent reader sees. SQLite documents that
[connection distinction](https://sqlite.org/isolation.html).

The example deliberately rolls back. It does not claim that every statement error
automatically rolls back every surrounding transaction in every driver. Its schema
also does not implement a full booking system: there is no foreign key here, no
permission decision and no multi-connection overbooking test. Read the scope of
the demonstrated behavior instead of treating the short script as a production
reservation algorithm.

### 3) **Distinguish visibility lock waiting and deadlock recovery**

An **isolation level** states the allowed interactions among concurrent transactions.
A **dirty read** observes another transaction's uncommitted change. A
**nonrepeatable read** sees a previously read value change after another transaction
commits. A **phantom read** observes a changed set of rows satisfying a repeated
query. These are different phenomena, not alternate names for any stale screen.

[PostgreSQL's isolation guide](https://www.postgresql.org/docs/18/transaction-iso.html)
describes Read Uncommitted, Read Committed, Repeatable Read and Serializable.
PostgreSQL implements stronger behavior than some standard minima: its requested
Read Uncommitted behaves as Read Committed, and its Repeatable Read prevents
phantoms. At its default Read Committed level, successive ordinary queries in
one transaction can see different newly committed data. A **serializable** execution
has the effect of transactions running one at a time in some order; implementations
can overlap work and abort a conflicting transaction. The application must handle
such failures, rather than assuming serializable means “no retries needed.”

A **lock** controls conflicting access to a resource. A **lock wait** occurs when
an operation must wait for a conflicting holder. Locks differ by scope and mode;
a row lock does not necessarily block ordinary readers. A **deadlock** is a cycle
of dependencies that prevents the participants from proceeding without intervention.
For this constructed exclusive-lock timeline, each transaction holds its first
resource until it ends:

| Step | Transaction A | Transaction B |
|---|---|---|
| 1 | Holds workshop w4 | Holds workshop w5 |
| 2 | Requests w5 and waits for B | Requests w4 and waits for A |

Both cannot obtain their requested resource while the other continues holding it.
If B requested nothing from A, A's wait alone would not establish that cycle.
[PostgreSQL's locking guide](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-DEADLOCKS)
explains detection and aborting a participant. The exact victim is not a useful
application guarantee. Consistent acquisition order can avoid this particular
cycle, but the application still needs scoped error/retry handling.

SQLite's write coordination is different: normally one writer at a time per
database, with visibility affected by connection and journal settings. Do not
interpret every busy response as this PostgreSQL-style two-resource deadlock.
Likewise, an HTTP timeout is an observation deadline, not proof that a transaction
aborted. It may have committed before the response was lost.

### 4) **Common confusion**

ACID consistency concerns valid database states and rules. Distributed consistency
concerns observations across operations or copies; the shared word does not make
those guarantees interchangeable. Neither meaning promises that a human entered
the true workshop details.

A transaction is also not necessarily one query or one web request. Several
statements can share one transaction, and one request can use several transactions.
Rolling back database changes does not unsend an email already delivered outside
the transaction's scope. Design that coordination explicitly.

### 5) **Performance note**

Transactions can hold locks and other resources while open. Unnecessary waiting
inside one, such as waiting for a person to confirm a screen, can delay conflicting
work. Stronger concurrency guarantees may involve coordination, monitoring or
aborted work; the cost depends on the product and workload. The memory-only example
measures no commit I/O, contention, deadlock frequency or crash recovery. Use the
actual transaction boundary and required guarantees when assessing costs.

### 6) **Mentor note**

Ask a learner to draw a box around the two database changes and leave the email
and browser response outside it. Then remove B's request for w4 from the lock
card. A sound answer explains why database rollback cannot retract the email and
why the revised card establishes a wait without proving a deadlock. Ask what new
evidence would establish the transaction's outcome after a timeout.
