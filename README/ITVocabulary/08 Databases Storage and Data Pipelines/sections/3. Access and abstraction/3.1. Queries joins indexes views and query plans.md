## 3.1. Queries joins indexes views and query plans

“Add an index” is not a complete explanation of a slow report. First identify the
question, the rows it should return and the work the engine plans to perform.
An index offers an access path; it does not repair a wrong question.

Read the table/key and schema lessons first. The small local example below uses
SQLite 3.54.1, the stable download checked 2026-10-18, on Linux x86_64. PostgreSQL
18 documentation supplies additional explicitly labeled plan/view distinctions.

### 1) **Separate a query its matching rule and its result**

A **query** requests a database operation or information. In everyday SQL use,
“query” often means a retrieval statement; some tools use it more broadly for
statements that change data too. Name the operation when its effects matter.
A **result set** is the collection of rows returned by a retrieval.

A **join** combines rows according to a relationship expressed by the query.
An **inner join** returns matching pairs. A **left outer join** also retains
unmatched left-side rows, using nulls for the missing right-side values. A
**cross join** returns every pair. The
[PostgreSQL join tutorial](https://www.postgresql.org/docs/18/tutorial-join.html)
explains these distinctions. The logical pairs describe the result, not a
requirement that every engine compare every possible pair during execution.

In the example, three bookings refer to two people. Joining on matching person
identifiers returns three booking/name pairs. Leaving out that identity condition
and requesting all pairs returns six combinations. Faster access to those six
wrong combinations would not make the report correct. A foreign key is also not
required to write a join; the query's condition determines which values match.

### 2) **Observe an index and a named query in a complete local example**

A **database index** is an additional structure supporting access to data, for
example locating bookings by workshop rather than inspecting every booking.
The engine can choose whether to use it. PostgreSQL's
[index introduction](https://www.postgresql.org/docs/18/indexes-intro.html)
explains both that choice and the need to maintain indexes when data changes.
An index need not impose uniqueness unless that particular index's rule does so.

An ordinary **view** gives a name to a query and presents its result as a
relation. It is not inherently a stored copy of that result. PostgreSQL's
[view tutorial](https://www.postgresql.org/docs/18/tutorial-views.html)
illustrates this interface. A **materialized view** stores the derived result;
PostgreSQL [refreshes it explicitly](https://www.postgresql.org/docs/18/rules-materializedviews.html).
Its stored data may lag behind the source. Refresh behavior is a product contract,
not something established merely by naming a view.

For the runnable example, obtain the **SQLite tools 3.54.1** appropriate to your
platform from the [official download page](https://sqlite.org/download.html).
Extract the command-line program. On the tested Linux setup, place the executable
`sqlite3` and the following file `booking_queries.sql` in the same example folder.
The program is separate from Python's bundled SQLite library. No server or external
package is needed. Run `./sqlite3 :memory: < booking_queries.sql` from that folder.
`:memory:` keeps this database in memory; it disappears when the program exits.

The initial statements create the two tables and insert their records. `SELECT`
chooses output columns, `ON` states the matching rule and `ORDER BY` orders the
output. `AS b` and `AS p` are short names for the two tables. `count(*)` counts
result rows. Dot-prefixed lines control the SQLite shell: stop on errors, hide
column headings, separate fields with `|`, and print section labels. They are not
portable SQL statements; see the [SQLite CLI guide](https://sqlite.org/cli.html).

```sql
.bail on
.headers off
.mode list
CREATE TABLE people (person_id TEXT PRIMARY KEY, display_name TEXT NOT NULL);
CREATE TABLE bookings (
  booking_id TEXT PRIMARY KEY,
  person_id TEXT NOT NULL,
  workshop_id TEXT NOT NULL
);
INSERT INTO people VALUES ('p1', 'Mina'), ('p2', 'Reza');
INSERT INTO bookings VALUES ('r17', 'p1', 'w4'), ('r18', 'p1', 'w5'), ('r19', 'p2', 'w4');
.print Joined bookings
SELECT b.booking_id, p.display_name
FROM bookings AS b JOIN people AS p ON b.person_id = p.person_id
ORDER BY b.booking_id;
.print All pairs without the identity condition
SELECT count(*) FROM bookings CROSS JOIN people;
.print Before the workshop index
EXPLAIN QUERY PLAN SELECT booking_id FROM bookings WHERE workshop_id = 'w4';
CREATE INDEX bookings_workshop_idx ON bookings(workshop_id);
.print After the workshop index
EXPLAIN QUERY PLAN SELECT booking_id FROM bookings WHERE workshop_id = 'w4';
CREATE VIEW booking_names AS
SELECT b.booking_id, p.display_name
FROM bookings AS b JOIN people AS p ON b.person_id = p.person_id;
UPDATE people SET display_name = 'Sara' WHERE person_id = 'p1';
.print View after the name change
SELECT booking_id, display_name FROM booking_names WHERE booking_id = 'r17';
```

Observed full output in that environment:

```text
Joined bookings
r17|Mina
r18|Mina
r19|Reza
All pairs without the identity condition
6
Before the workshop index
QUERY PLAN
`--SCAN bookings
After the workshop index
QUERY PLAN
`--SEARCH bookings USING INDEX bookings_workshop_idx (workshop_id=?)
View after the name change
r17|Sara
```

The two plan descriptions concern the same workshop filter, before and after the
index exists. This run selected a table scan first and an index search afterward.
The name change then updates the source person. Reading the ordinary view returns
Sara; it did not freeze Mina's name when the view was created. That is a visibility
observation in this simple session, not a full concurrency or freshness guarantee.

### 3) **Interpret a plan as evidence about a specific execution strategy**

A **query plan**, or **execution plan**, describes how an engine intends to obtain
the result: accesses, filtering, joins, sorting and other operations. A **planner**
or **optimizer** chooses among supported strategies using its information and
estimates. It does not promise the globally best strategy for every condition.

SQLite's [EXPLAIN QUERY PLAN guide](https://sqlite.org/eqp.html) describes `SCAN`
and `SEARCH`. Here the first visits the table, while the second uses the named
index for the workshop condition. The `?` describes the condition's value position;
it does not mean the literal workshop identifier was lost. Exact plan text is
version-dependent and is not a stable application interface.

A plan is not itself a measured duration. In PostgreSQL's
[EXPLAIN guide](https://www.postgresql.org/docs/18/using-explain.html), estimated
`cost` uses planner units, and estimated `rows` concerns emitted rows rather than
necessarily all inspected rows. `EXPLAIN ANALYZE` actually executes its statement
to collect observations. Do not add that option to an arbitrary write merely
because plain plan inspection seemed read-only. SQLite's command in this example
is different; PostgreSQL's option and output must not be silently substituted.

Practice: the team shows the second plan and says “the report is now twice as
fast.” What has been established? This run chose an index path. No elapsed-time
comparison or representative report workload was measured. Request those results,
and verify that the returned records still answer the intended question.

### 4) **Common confusion**

A join combines records into a result; it does not merge the source tables into
one stored table. Its result can have more rows than either input, depending on
the matching rule. The six-pair result is expected for a cross join, but would be
a mistake if the requirement was one correct person per booking.

A view's name also says nothing by itself about authorization or query cost.
An ordinary view, a materialized result and a cached API response have distinct
update and access rules. Inspect the mechanism and its contract.

### 5) **Performance note**

Indexes consume space and require maintenance during changes. Their benefit depends
on the query and data distribution; a scan can be sensible for a tiny table or
when much of the data is required. The three-row run demonstrates selected plans,
not a meaningful speed benchmark. Adding indexes everywhere can increase write
work without helping the relevant reads. Measure the actual workload after checking
correctness, and retain the plan, versions and dataset context with the result.

### 6) **Mentor note**

Ask a learner to predict the joined row count before discussing the index. Then
ask what changes after the name update and what the plan cannot tell them about
elapsed time. A sound explanation separates logical results, source visibility,
access strategy and measurements. If they say “the index fixed it,” ask which of
those four claims they observed.
