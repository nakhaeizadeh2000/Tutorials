## 3.2. SQL CRUD ORMs query builders and drivers

A team says “the ORM saved the booking.” That statement leaves several questions:
which database operation ran, which values it received, what it changed and how
the application learned the outcome. Distinguish the operation's purpose from the
language and software layers used to perform it.

Read the preceding query and schema lessons. The complete local SQL example uses
SQLite 3.54.1 on Linux x86_64. Library examples identify roles from documentation
checked 2026-10-18; no application framework or ORM installation is required.

### 1) **Distinguish an operation category from the SQL language**

**CRUD** expands to **create, read, update and delete**. These are broad data-operation
categories. Creating a booking adds a record; reading retrieves it; updating changes
it; deleting removes it under the application's rules. CRUD does not specify
permissions, transaction boundaries or whether deletion must erase every copy.

**SQL** expands to **Structured Query Language**. It is a language family used to
define and work with data, not the name of one database server. Products implement
particular SQL capabilities and dialects. PostgreSQL's
[SQL language guide](https://www.postgresql.org/docs/18/sql.html)
separates definition, manipulation, retrieval and other facilities. Learning a
few SQL verbs is not evidence that every statement is portable across products.

| Intent for a booking record | Typical SQL statement |
|---|---|
| Create the record | `INSERT` |
| Read records | `SELECT` |
| Update records | `UPDATE` |
| Delete records | `DELETE` |

`CREATE TABLE` instead defines a storage structure. The shared English word
“create” does not make it equivalent to CRUD's create-a-record operation.
**DDL**, data definition language, names structure-related statements; **DML**,
data manipulation language, names data operations. Classifications of retrieval
vary: some teaching materials call `SELECT` **DQL**, data query language, while
others include it in broader data manipulation. State the statement's behavior
instead of arguing from an unexplained classification acronym. For example,
[Oracle’s statement classification](https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/Types-of-SQL-Statements.html)
includes retrieval in DML; its transaction/DDL behavior is specific to that product.

Using the SQLite executable obtained in the previous lesson, save this as
`crud_reading.sql` in the same example folder. Run
`./sqlite3 :memory: < crud_reading.sql`. All records exist only in that temporary
in-memory database. `WHERE` selects the affected record, and `changes()` reports
rows affected by the most recent completed data-changing statement in this example,
as defined in the [SQLite function reference](https://sqlite.org/lang_corefunc.html#changes).

```sql
.bail on
.headers off
.mode list
CREATE TABLE bookings (booking_id TEXT PRIMARY KEY, seats INTEGER NOT NULL);
INSERT INTO bookings VALUES ('r17', 2);
SELECT booking_id, seats FROM bookings;
UPDATE bookings SET seats = 3 WHERE booking_id = 'r17';
SELECT booking_id, seats FROM bookings;
UPDATE bookings SET seats = 4 WHERE booking_id = 'missing';
SELECT changes();
DELETE FROM bookings WHERE booking_id = 'r17';
SELECT count(*) FROM bookings;
```

Observed output:

```text
r17|2
r17|3
0
0
```

The first two lines show the created record and its updated seats. The third
shows that the attempted update of `missing` affected no row. It did not fail with
a syntax error; it also did not create a booking. The final line counts zero
remaining rows after deletion. Neither zero has the same meaning merely because
its printed numeral matches the other. A database success result must still be
interpreted against the intended operation and affected-row expectations.

### 2) **Locate mapping construction and communication responsibilities**

An **ORM**, or **object-relational mapper**, maps between application objects/models
and relational data and offers operations through an application-language API.
It may include relationship loading, change tracking or migration facilities;
the exact set is product-specific. TypeORM's
[getting-started guide](https://typeorm.io/docs/getting-started/)
illustrates entities and mapped columns. An entity class describes the mapping;
its mere presence in a source file does not prove the live table was created or
that a particular call persisted a record.

A **query builder** offers a programming interface for constructing queries.
It can help compose selected columns, conditions and joins without manually
assembling SQL strings. Kysely's [introduction](https://www.kysely.dev/docs/intro)
provides a TypeScript-oriented example of that role. An ORM may also expose a
query builder. These are capabilities that can coexist, rather than exclusive
labels for every product.

A **database driver** supplies application access to a database through a supported
interface or protocol. For a server database it handles communicating requests and
results; an embedded engine may instead be called through a local library.
[node-postgres](https://node-postgres.com/) is a concrete PostgreSQL access library.
This driver meaning differs from an operating-system device driver.

A possible responsibility path is application operation → ORM or query builder →
driver → database engine → returned result. Some stacks combine or omit layers;
inspect the actual stack. SQL text is an instruction representation along that
path, not another service that runs beside the database. The ORM still relies on
the database's behavior for constraints and transactions.

A **parameterized query** supplies data values separately from the query's structure.
The node-postgres [query guide](https://node-postgres.com/features/queries)
shows text and values passed separately. This helps prevent values being treated
as SQL syntax. A value parameter is not a universal placeholder for a table or
column name; identifier handling needs its own supported design. An ORM label
alone cannot establish how raw or dynamically constructed queries were handled.

### 3) **Review an access-layer claim with concrete outcome evidence**

A constructed report says: “The typed ORM call completed successfully, so the
booking is valid, authorized and fast.” Translate the claim into separate checks.
What operation was requested? Which record matched? What does the tool's result
mean? Which database rules ran? Which application access decision was performed?
What workload and timing were measured?

The zero-row update above is a useful counterexample: a completed statement can
leave the intended record unchanged because it did not match. A type-checked query
can also use a stale description of a deployed schema. Type checking helps within
its declared assumptions; it does not observe the database's current state.

Another constructed screen lists 20 bookings, then performs one extra person
lookup for each. This is the **N+1 query pattern**: one initial query plus N related
queries, here 21 database calls. A single convenient application call or property
access can hide such work, depending on the library's loading behavior. TypeORM’s
[performance guide](https://typeorm.io/docs/performance-optimization/introduction/)
identifies this as a relevant access-pattern problem. Request
the emitted operations and their conditions before proposing a join, batch read
or other repair. Those alternatives must preserve the required data and limits.

Practice: replace the ORM with handwritten SQL while keeping the same 21 requests.
Has the N+1 pattern been removed? No. The request pattern is unchanged. Likewise,
introducing an ORM does not inherently create N+1; it is a behavior of a particular
access path, not a consequence established by the acronym.

### 4) **Common confusion**

CRUD is not a strict mapping to HTTP methods. An HTTP operation can perform several
database operations, no database access at all, or work that completes later.
Interpret the API contract and the data operation at their separate boundaries.

“Raw SQL” means SQL supplied directly rather than wholly through a higher-level
query interface. It can still use value parameters and a driver. “Raw” does not
necessarily mean concatenated untrusted input, and a builder does not guarantee
that every escape hatch is used correctly.

### 5) **Performance note**

Access layers can introduce construction, mapping and data-transfer work, but the
number and shape of database operations often matter more than the abstraction's
name. Twenty-one small calls and one combined retrieval have different trade-offs,
including transferred data and work at the engine. This lesson counts a constructed
pattern; it measures no ORM or driver overhead. The local CRUD run verifies values
and affected counts, not server latency, authorization or production throughput.

### 6) **Mentor note**

Ask a learner to annotate a reported “save” with intent, emitted operation,
parameters, matching identity and observed result. Then show the two zero outputs
and ask what each counts. A sound explanation distinguishes statement completion
from the requested business outcome and can locate a problem without assuming
that replacing an access library automatically fixes it.
