## 5.2. Backups snapshots replication sharding and restores

Two database machines do not necessarily provide two recoverable versions of
yesterday's data. A replica may receive a bad deletion, a snapshot may omit needed
state, and a backup may exist without a working restoration procedure. State what
each copy contains, when it was captured and which failure it can address.

Read the storage and transaction lessons first. Product examples use PostgreSQL
18, MongoDB's current manual and SQLite 3.54.1, checked 2026-10-18. The runnable
exercise changes only a new demonstration database and its local backup file.

### 1) **Distinguish recovery copies from point-in-time capture mechanisms**

A **backup** is retained data and associated information intended to support
recovery. **Restore** means loading retained material into a usable target;
**recovery** is the broader return to an acceptable state, potentially including
log replay, checks and restoring application operation. A job marked successful
is evidence about that job, not proof of the whole recovery outcome.

A **snapshot** captures a resource's state at a particular point under a product's
rules. A **full backup** covers the selected scope, while an **incremental backup**
retains changes relative to earlier material. A snapshot may use incremental
storage internally. Amazon's [EBS snapshot guide](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-snapshots.html)
provides one such example. Snapshot therefore does not mean “a physically separate,
complete copy of every byte,” nor does its name establish application consistency.

Database files can depend on buffered changes, logs and several volumes.
[PostgreSQL's filesystem-backup guide](https://www.postgresql.org/docs/18/backup-file.html)
explains why casually copying a running data directory or selected table files
can be unusable, and distinguishes a consistent snapshot procedure. Follow the
engine's supported capture method; a filesystem copy is not automatically a
valid database backup.

A **logical backup** records logical objects and data in a restorable form, such
as a database dump. A **physical backup** preserves the database's storage
representation and required supporting state. Compatibility and restore granularity
differ by mechanism. PostgreSQL's [backup overview](https://www.postgresql.org/docs/18/backup.html)
separates dumps, filesystem backups and continuous archiving.

**Point-in-time recovery**, or **PITR**, reconstructs state at a chosen supported
point. PostgreSQL's [continuous archiving](https://www.postgresql.org/docs/18/continuous-archiving.html)
combines a suitable base backup with the required continuous write-ahead log,
or **WAL**, history. A log fragment or unrelated export does not supply that chain.
“Every second is recoverable” needs evidence that the required history actually
exists and can be replayed.

### 2) **Separate replication from dividing a dataset into shards**

**Replication** maintains copies of data through a defined transfer/apply process.
A **replica** is one such copy. A **primary** commonly accepts writes in a
primary/replica design, while a **standby** is maintained to support a later takeover;
product roles and permitted reads/writes differ. A **failover** changes service to
another participant after failure or a deliberate switch.

**Replication lag** is delay between relevant stages, such as source commit and
replica application. Specify which stages and measurement are meant. PostgreSQL's
[standby guide](https://www.postgresql.org/docs/18/warm-standby.html)
describes asynchronous streaming by default and synchronous modes with different
acknowledgment conditions. “Synchronous” needs the required participants and the
acknowledged stage, not an assumption that every copy is immediately readable.

Replication can support availability, but a replica following changes can also
receive an accidental deletion. It is not automatically retained history from
before that deletion. Delayed copies and additional retention mechanisms have
specific contracts; do not assume them from the word replica.

**Sharding** divides data across separately managed portions called **shards**.
A **shard key** helps decide placement or routing. One shard can hold workshops
w1–w50 while another holds w51–w100 in a constructed range-based design. These
are different portions, not two complete copies. Replication can be applied
within each shard: MongoDB's [sharding guide](https://www.mongodb.com/docs/manual/sharding/)
explicitly describes shards containing subsets and deployed as replica sets.
Replication and sharding can coexist and solve different questions.

If one shard is unavailable, operations needing its data may fail even while
another shard responds. “Half the machines work” does not establish that a report
covering every workshop is complete. Ask which data and dependencies the operation
needs.

### 3) **Verify what a restored copy actually contains**

Use a new, otherwise empty example folder. Copy the SQLite 3.54.1 executable from
the query lesson into it and save this file as `restore_reading.sql`. The script
creates `recovery-demo.db` as a backup artifact; that name must not already be
present. Run `./sqlite3 :memory: < restore_reading.sql` in that folder. The working
database is in memory. `.backup` writes its current contents to a file, and
`.restore` replaces the current demonstration database's contents from that file.
These are [SQLite shell commands](https://sqlite.org/cli.html), not generic SQL.

```sql
.bail on
.headers off
.mode list
CREATE TABLE bookings (booking_id TEXT PRIMARY KEY);
INSERT INTO bookings VALUES ('r17');
.backup recovery-demo.db
INSERT INTO bookings VALUES ('r18');
SELECT count(*) FROM bookings;
DELETE FROM bookings;
SELECT count(*) FROM bookings;
.restore recovery-demo.db
SELECT booking_id FROM bookings ORDER BY booking_id;
```

Observed output:

```text
2
0
r17
```

The live database first contains two bookings and then none after the deliberate
deletion. Restoration recovers `r17`, which existed when the backup was made.
`r18` was accepted afterward and is absent from that backup. A successful restore
therefore does not imply recovery of every later operation. The created backup
file remains available for inspection; no existing application database is involved.

As a historical case, GitLab's original
[January 2017 outage postmortem](https://about.gitlab.com/blog/postmortem-of-database-outage-of-january-31/)
reports failed backup production, unusable primary/secondary data and recovery
from an earlier snapshot. It illustrates why capture, retained contents and
restoration must be checked separately. Its versions, infrastructure and timings
are historical evidence, not a current GitLab architecture or recovery-time promise.

Practice: a constructed packet says a 09:00 backup contains `r17`, a 09:30 write
adds `r18`, and a 10:00 deletion reaches the primary and its replica. No later
backup or log history is available. Can the replica supply the old records?
Not from the stated current contents. Can the 09:00 backup recover `r18`? No.
It predates that write. Recoverable history must be established explicitly.

### 4) **Common confusion**

A live replica, an incremental snapshot and a logical export can all be called
“copies” while containing different state and requiring different supporting
material. List the recovery target and prerequisites, including permissions and
necessary keys, before treating one as interchangeable with another.

A backup's age, retained scope and restore duration are separate quantities.
“One backup per day” alone specifies neither how much accepted data could be lost
nor how long the application will take to resume. Failed jobs, capture boundaries
and later log history can change the answer.

### 5) **Performance note**

Capturing, transferring and restoring data consume processing, storage and I/O.
Incremental capture can reduce copied changes but add restore dependencies.
Synchronous acknowledgment can add waiting; asynchronous replication can leave a
data-loss window under relevant failures. Sharding can distribute work while
adding routing and cross-shard coordination. This tiny restore run measures
contents only, not production recovery time, lag, durability or scalability.

### 6) **Mentor note**

Give a learner a list of copies without saying which is a backup. Ask what each
contains after a deletion and how it would produce the requested recovery target.
A sound answer distinguishes history from current duplication and demands a
restoration result with checked contents. Then add `r18` after capture and ask why
“restore succeeded” is still an incomplete business outcome.
