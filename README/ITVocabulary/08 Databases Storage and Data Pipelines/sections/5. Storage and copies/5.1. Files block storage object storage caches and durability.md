## 5.1. Files block storage object storage caches and durability

“Stored in the cloud” does not explain how an application addresses its data,
which copy is authoritative or what loss the system can survive. Separate the
access interface from the role of the copy and its retention guarantees.

The earlier file/path lesson owns filesystem basics; the transaction lesson owns
ACID durability. This page applies those ideas to storage descriptions. Examples
are constructed reading cards, with product documentation checked 2026-10-18.

### 1) **Identify the interface exposed to the consumer**

**File storage** exposes files through filesystem operations and names organized
in directories. The filesystem can be local or supplied over a network. The
consumer might open a named file, read a range and modify part of it. Exact sharing,
locking and durability behavior depends on the filesystem and deployment.

**Block storage** exposes addressable storage blocks, often through a device-like
**volume**. A filesystem can use that volume to organize files. The database then
reads its files through that filesystem. These are layers of one path, rather
than evidence that the same deployment must be exclusively “file” or “block.”
Amazon's [EBS volume guide](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-volumes.html)
provides a concrete block-device example; no cloud account is needed here.

**Object storage** exposes stored objects through an object-oriented storage API.
Here “object” means stored content with identifying information and metadata, not
necessarily an application-language object instance. A consumer retrieves an
object by its key within the service's container or namespace. A **blob**, short
for binary large object, often means opaque content handled as a unit; vendors
use the word in specific product models too.

In Amazon S3, a **bucket** is a storage container and an **object key** identifies
an object within it, with version identity relevant when versioning is enabled.
For a general purpose bucket, `exports/workshop-w4.json` is the full key; the slash
can support a folder-like presentation without being an operating-system path.
See the [S3 overview](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)
and [object-key guide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-keys.html).
S3 also has specialized bucket types. Do not universalize one bucket model or a
filesystem analogy across every storage product.

| Constructed operation | Interface being used |
|---|---|
| Open `/reports/today.json` in the process's filesystem | File access |
| Read blocks from an attached volume | Block access |
| Retrieve key `reports/today.json` from bucket `workshop-exports` through its API | Object access |

The similar names in the first and third rows do not imply identical operations.
A storage gateway or mount can translate between interfaces, but that translation
needs its own supported behavior. Renaming a local file is not automatically the
same operation as changing a remote object key. Nor is object storage restricted
to unstructured information: a stored JSON export can contain structured records.

### 2) **Separate a cache role from memory location and persistence**

A **cache** keeps data or computed results for reuse so a consumer can avoid
repeating some work. In this application, an **authoritative copy**, or **source
of truth**, is the copy designated to decide the relevant fact. Authority is a
system responsibility, not an automatic property of a filename or product.
A cache can be on disk, in memory, local to a process or accessed over a network.
Location alone does not identify its role.

Suppose PostgreSQL holds the accepted booking status, and Redis keeps a reusable
copy for the status screen. That Redis value is a cache under this design. If the
system instead accepts unique booking records only into Redis, those values are
not disposable merely because the product is often used for caching.

**Eviction** removes entries under a capacity or selection policy. **Expiration**
makes entries cease to be usable or present after a lifetime rule. The policies
have different triggers. Redis's [eviction reference](https://redis.io/docs/latest/develop/reference/eviction/)
includes policies that remove keys under memory pressure and `noeviction`, which
can reject new data-changing commands instead. A claim that a store is a cache
must explain what happens when an entry disappears or a write is rejected.

**Persistence** retains data beyond a particular execution lifetime through a
storage mechanism. Redis's [persistence guide](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)
describes snapshot, append-only and disabled-persistence configurations. Thus
“Redis means nothing is persisted” is wrong, but “Redis means every accepted write
survives a crash” is also unsupported without the actual configuration and failure
scope. Persisting cache entries does not by itself make them authoritative or fresh.

### 3) **Read retention and recovery claims against a concrete failure**

Recall that **durability** concerns retention of accepted data under stated failure
assumptions. **Availability** concerns being able to use the service when needed.
A preserved object can be temporarily inaccessible; a responding service can have
lost a previously accepted value. These are different observations.

This constructed workshop packet states the roles explicitly:

| Component | Contract in this example |
|---|---|
| Booking database | Authoritative accepted reservation status |
| Status cache | Reusable status copy, permitted to be discarded and refilled from the database |
| Object export | Report generated from database values recorded at 09:00 UTC |
| Client screen | May display the export until its input is refreshed |

At 09:10, a restart empties the cache, while the database remains accessible and
intact. Has the reservation necessarily been lost? No. The stated authoritative
copy remains. A refill can obtain its value, but the application still needs a
working refill path; the table does not prove that implementation.

Now change only one fact: the last accepted reservation existed solely in the
cache and had not reached any recoverable authoritative store. Calling the value
“cached” no longer establishes that it is rebuildable. Identify which system
accepted the operation, what it acknowledged and where the required information
was retained. A product label cannot supply the missing record.

Finally, the 09:00 export remains readable at 09:20 but lacks a 09:15 cancellation.
Its continued storage demonstrates neither current booking state nor a failed
durability mechanism. It represents an earlier collection. Even a storage service
with strong read-after-write behavior cannot update an export that the application
has not regenerated. Amazon S3's scoped
[consistency description](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel)
is an example of why access consistency and report freshness must be separated.

Practice: someone proposes deleting the database because the object export is
“durable.” What evidence is missing? Establish whether the export contains all
required data, which point in time it represents, how later accepted writes are
retained, and whether the application can recover and operate from it. Durability
of a selected artifact does not establish completeness for a different purpose.

### 4) **Common confusion**

File, block and object describe interfaces and organization. Cache describes a
reuse role. Durable describes a retention property under a contract. They belong
to different questions and can apply within the same system.

A storage label also does not imply a consistency model or a universal speed
ranking. Some older comparisons describe every object store as eventually
consistent. Current product behavior must be checked for the actual operation
and container type; do not transfer that historical generalization blindly.

### 5) **Performance note**

A cache hit can avoid source work, while a miss adds a lookup and possible refill.
Eviction, serialization, network access and refresh can change the costs. A block
interface can support small updates, but the full application path and storage
contract determine the outcome. No timing or durability experiment is run here.
Compare the required reads/writes, sizes, reuse, failure scope and measured costs
instead of selecting an interface because a table calls it “fast.”

### 6) **Mentor note**

Ask a learner to label each packet row with interface, authority, lifetime and
rebuild source. Then remove the authoritative record. A sound answer changes the
loss conclusion even though the cache product name remains the same. Ask which
observation distinguishes a missing value, an inaccessible service and an old
export; those require different investigations.
