## 8.1. Boundaries of data vocabulary

You can now ask which data a statement concerns, how the system represents it,
which operation runs and what evidence supports a guarantee. The next learning
step should follow the question you need to answer. Knowing the correct storage
label alone does not establish that you can design, administer or recover the system.

This page closes the data domain with owner routes and a worked handoff. It does
not add database setup, a new product baseline or another implementation syllabus.

### 1) **Route a meaning question to its existing owner**

### 2) **Choose deeper study from the task and its required evidence**

Reading a query result is different from designing a query-tuning experiment.
Database implementation study must address the actual engine, schema, data,
execution plans, statistics and representative workload. The small SQLite examples
here establish specific local outcomes; they do not compare production engines
or certify a capacity design.

Schema design needs requirements about identity, relationships, historical meaning
and valid transitions. Formal normalization, constraints and migration rollout
belong to deeper database-design work. A normal-form label should follow that
reasoning, not replace it. The root curriculum includes planned **Databases** and
**Database Design** tracks for those goals; those tracks are not yet published.

Access-library implementation needs the selected driver or ORM's actual version,
query behavior, mapping, connection and transaction contracts. The planned **ORM**
track is that deeper route. Language type mechanics remain in TypeScript, while
JavaScript owns its parsing and value semantics. A typed declaration does not
prove live data conforms to it.

Cache implementation needs authority, keys, freshness, capacity, refill and failure
behavior. The planned **Redis** track can develop product mechanics. Do not infer
those choices from this domain's recognition example. Recovery administration
similarly needs a supported capture procedure, protected retained material,
restoration environment and observed recovery outcomes. “We know what PITR means”
is not a restore rehearsal.

Later vocabulary domains develop general concurrency, distributed observations,
security and service-level objectives. This domain's transaction, copy and pipeline
examples provide their data context; they do not implement consensus, identity
policies or a complete reliability program. Future study names are guidance,
not links to absent lessons or permission to claim those skills already verified.

### 3) **Turn a mixed data promise into a focused learning handoff**

A constructed teammate says:

> The ORM returns JSON from our document-shaped rows. We will put a copy in Redis,
> replicate it and use CDC for analytics. That makes the system schemaless, fast
> and recoverable, so no further database work is needed.

A useful response preserves the proposed components while separating the decisions.
JSON identifies a representation, and document-shaped values do not alone identify
the whole database model. Request the actual stored structures and access path.
An ORM identifies mapping capabilities, not which operations or constraints ran.
Ask which values remain authoritative after the Redis copy is lost and how the
copy becomes current after a change.

Replication then needs its participants, copied scope and acknowledgment rules.
It does not establish a retained version before an unwanted change. Recovery needs
its target state, supporting material and a checked restoration. CDC identifies
capture; the analytics consumer must still apply and interpret changes correctly.
A proposed speed improvement needs an equivalent workload and actual measurement.

For a technical teammate, the handoff could be: “Show one booking's stored shape,
query and result, then trace its update into Redis and the report. Identify the
authoritative record, copied scope, last applied change and retained recovery
history. Use those artifacts to choose the required implementation checks.”

For a product collaborator: “These components may support the design, but we still
need to verify that a recorded booking remains correct, appears in reports at the
required time and can be recovered after the agreed failures. The current diagram
does not provide those outcomes by itself.”

Practice: now the team supplies a successful isolated restore containing the
required bookings through a stated cutoff. What changes? Recovery has concrete
evidence for that tested scope. It does not establish cache freshness, every later
write or the proposed speedup. Revise the specific claim supported by the new
result and leave independent questions open.

### 4) **Common confusion**

Choosing a deeper study route does not mean the current domain's definitions were
incomplete. The vocabulary outcome is to interpret a claim and identify the needed
artifact. Implementation mastery additionally requires building, testing and
operating the actual mechanism under its requirements.

Conversely, a new question is not automatically a reason to create another copy of
the same definition. Use the owner table for meanings. Add the new application,
conditions or failure evidence where the new question belongs.

### 5) **Performance note**

Routing terminology and learning goals has no direct runtime effect. Its practical
benefit is choosing the relevant investigation: query count, an engine plan,
cache misses, ingestion progress and restore work concern different paths.
This handoff measures none of them. A product or architecture label cannot stand
in for an observation at the actual performance boundary.

### 6) **Mentor note**

Ask the learner to select one unresolved claim from the mixed proposal, name its
owner and request one discriminating artifact. Then ask what competence would be
needed to change the implementation. A sound answer separates understanding the
claim, collecting evidence and safely carrying out the deeper work. Avoid rewarding
a recommendation that merely adds more named components.
