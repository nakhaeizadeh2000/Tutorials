## 2.2. Schemas constraints normalization and migrations

A field can exist, have the expected type and still contain the wrong fact. A
schema describes structure, a constraint restricts allowed data, normalization
examines how facts depend on one another, and a migration changes a deployed
structure or its data. Use these terms for different parts of a change review.

Read the preceding keys and relationships lesson. This page uses constructed
artifacts and a proposed change sequence; no production migration is performed.
Product details use PostgreSQL 18 and MongoDB's current manual, checked 2026-10-18.

### 1) **Identify structure rules and their enforcement boundary**

A **database schema** can mean the structure of a database: its tables, columns,
types and rules. There is also a narrower namespace meaning. In PostgreSQL,
`booking.reservations` can identify table `reservations` inside named schema
`booking`. A database can contain multiple such schemas. The
[PostgreSQL schema guide](https://www.postgresql.org/docs/18/ddl-schemas.html)
explains that organization. “Change the schema” could mean altering a table's
structure; it need not mean creating another namespace.

A **constraint** is an enforced restriction on allowed data. In a PostgreSQL
example, `NOT NULL` excludes null values and `CHECK (seats > 0)` requires a
positive non-null seat count when combined with that null restriction. `CHECK`
alone can pass when its result is unknown because of null. A default merely
supplies an omitted value; it does not prohibit a supplied bad value. See the
[constraint reference](https://www.postgresql.org/docs/18/ddl-constraints.html).
The preceding lesson owns primary and foreign keys; they are particular rules,
not a substitute for all other validation.

A document database can have validation rules too. MongoDB's
[schema validation guide](https://www.mongodb.com/docs/manual/core/schema-validation/)
describes allowed types and ranges, configurable treatment of existing documents,
and rejection versus warning behavior. “We added a validator” therefore needs
its actual coverage and enforcement settings. An API schema, an application's
checks and a database constraint occupy different boundaries, even when they
express similar requirements.

In a constructed booking rule, `seats` must be an integer from one to four. A
record with `seats=0` violates that rule. A record with `seats=2` can satisfy it
while referring to a workshop with no remaining places. The range check does not
claim to enforce availability across bookings.

### 2) **Explain duplicated facts through their change consequences**

**Normalization** organizes relational structures using dependencies between facts
to reduce problematic redundancy and modification anomalies. **Normal forms** are
specific criteria used to assess such structures. Memorizing a form's number
does not establish that the model captures the application's meaning. This lesson
teaches the diagnostic vocabulary, rather than the formal decomposition algorithms.

Consider an illustrative design with these rows:

| booking_id | workshop_id | current_workshop_title |
|---|---|---|
| r17 | w4 | Intro to Networks |
| r18 | w4 | Intro to Networks |

The stated business rule is that each workshop has one current title. Thus
`workshop_id` determines that title, independently of the booking. Storing it in
every booking makes a rename require multiple coordinated edits. Updating only
`r17` produces two different supposed current titles for `w4`: an **update anomaly**.
If workshop facts can be stored only inside booking rows, adding a workshop with
no booking exposes an **insert anomaly**, and deleting its final booking can
remove its only stored title, a **delete anomaly**.

A proposed repair puts the current title in `workshops(workshop_id, title)` and
keeps `workshop_id` in each booking. Changing that workshop's title then has one
owner. This is the kind of reasoning developed in Aalto's
[normalization lesson](https://opencs.aalto.fi/en/courses/databases/part-8/4-normalization).
The exact dependencies must come from the requirements; a small sample with no
conflict is not proof that a dependency is universally required.

Now change the field's meaning to `title_shown_when_booked`. An old title may be
intentional historical evidence. Removing every repeated title would erase that
meaning. **Denormalization** deliberately introduces redundant or precombined data,
often to serve particular reads. It needs a policy for changes and acceptable
staleness; “fewer tables” alone is not a justification. Historical facts and copies
of a current fact must first be distinguished by meaning.

### 3) **Read a migration as a change with preconditions and evidence**

A **database migration** is a controlled change that moves a database from one
expected state to another. A **schema migration** changes structures or rules;
a **data migration** moves or transforms values. One change may need both.
Migration files, the record of applied changes and the database's actual state
are distinct evidence. Having a file named `add_contact_name` does not prove it
ran successfully on the intended database.

Sadalage and Fowler's original
[Evolutionary Database Design](https://martinfowler.com/articles/evodb.html)
describes capturing changes as testable artifacts and tracking their application
and order. Its concrete tooling and team process are examples, rather than a
requirement that every migration system use the same filenames or workflow.

Suppose a constructed application renames document field `contact_name` to
`booker_name`, while older application instances may still run. A proposal that
only changes new writes leaves old documents and old readers unresolved. Review
this explicit sequence:

| Proposed step | Evidence or decision needed |
|---|---|
| Allow readers to understand both field shapes | Defined precedence if both exist, and checked old/new examples |
| Coordinate writes during the transition | Which writers remain active and which fields they maintain |
| Backfill old documents | Transformation rule, progress, retry behavior and conflict handling |
| Remove old-field support | Evidence that affected data and active consumers no longer require it |

**Backfill** means populating or transforming previously stored records, rather
than only changing future writes. The table is a review outline, not a universally
safe executable migration. It leaves concurrency, deployment coordination and
failure recovery to the implementation design.

Practice: the report says “the new column exists, so migration is complete.” What
is missing? The structural step does not prove that historical values were filled,
that consumers agree on their meaning, or that the required constraints are now
enforced. Ask for those completion criteria. A **rollback** attempts to return to
an earlier state, but dropping a field after deleting its values cannot recreate
the lost information merely because the tool offers a reverse command.

### 4) **Common confusion**

“Schemaless” does not mean application code can understand every possible record.
A reader expecting `contact_name` still fails to find it after an unexplained
rename. Structure may be implicit in code even when a database accepts both shapes.

Normalization here is a data-design concept. It differs from Unicode normalization
or rescaling numbers. Similarly, a successful schema change does not prove that a
business rule was preserved for every existing record and concurrent operation.

### 5) **Performance note**

Reducing repeated current facts can reduce coordinated update work, while readers
may need to combine separate records. Deliberate redundant representations can
shift that work toward writes or refresh jobs. Migrations can also scan or rewrite
existing data and contend with ordinary use. None of these names guarantees a
speedup or a zero-downtime change. Evaluate the actual operations, dataset and
product behavior; this page runs no migration or performance experiment.

### 6) **Mentor note**

Ask whether a repeated workshop title means “current title” or “title at booking
time” before suggesting a repair. Then ask a learner to name the allowed states
before, during and after the contact-field change. A sound review identifies data,
readers, writers and enforcement separately, and defines completion through
observed state rather than the presence of a migration file.
