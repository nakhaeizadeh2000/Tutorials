## 2.1. Tables rows columns documents fields keys and relationships

A booking says that Mina reserved a place in a workshop. To interpret its storage
model, identify the booking's own identity, the details recorded about it and the
references connecting it to the person and workshop. The same displayed names
are not necessarily the same identity.

Read the preceding model comparison first. The following tables and JSON are
constructed data artifacts for reading; they are not database commands. PostgreSQL
18 and MongoDB's current manual anchor the scoped terminology, checked 2026-10-18.

### 1) **Read records attributes and nested documents**

A relational **table** is a named collection of **rows** described by named
**columns**. A row records values for one entry, and a column identifies an
attribute across those entries. “Record” often means a row, but can also mean a
document or another system's stored entry; ask which representation is intended.
PostgreSQL's [concepts page](https://www.postgresql.org/docs/18/tutorial-concepts.html)
introduces these terms and warns that displayed row order is not an inherent SQL
guarantee. Row number two in a screenshot is not a durable record identifier.

Our illustrative `people` table is:

| person_id | display_name |
|---|---|
| p1 | Mina |
| p2 | Mina |

Our `bookings` table is:

| booking_id | person_id | workshop_id | seats |
|---|---|---|---|
| r17 | p1 | w4 | 2 |
| r18 | p1 | w5 | 1 |
| r19 | p2 | w4 | 1 |

Two people have the same display name. The table explicitly gives them different
identifiers. The booking `r17` belongs to `p1`, and `seats` is a numerical attribute
of that booking. A row's shape does not tell us every business rule: for example,
whether the booker must attend or whether another booking by `p1` is allowed.

A **document** records named **fields** and their values; fields can contain nested
objects or lists. A **collection** groups documents in MongoDB terminology. The
following JSON illustrates a booking document shape. It is not a MongoDB shell
session or a complete account of BSON's additional data types.

```json
{
  "_id": "r17",
  "person_id": "p1",
  "workshop_id": "w4",
  "seats": 2,
  "contact": {"display_name": "Mina"},
  "attendee_names": ["Mina", "Reza"]
}
```

`contact` is a field whose value is an embedded document, and `display_name` is a
field inside it. `attendee_names` contains a list of two strings. A field is a
named part, while a document is the containing record. The same word “field” is
sometimes used for a table column or one form input, so specify the context.
MongoDB's [document reference](https://www.mongodb.com/docs/manual/core/document/)
describes field/value pairs and the `_id` identity of documents in a standard
collection. Its special collection types and uniqueness scope need their own
rules; do not assume every document system behaves identically.

### 2) **Distinguish identifiers keys and enforced references**

A **key** identifies or locates something within a stated scope. A key in a
key-value store, a JSON object's field name and a relational key are related uses
of the word, but they are not interchangeable contracts.

In a relational table, a **primary key** is the selected column or combination of
columns used to identify rows uniquely. PostgreSQL requires its values to be
unique and non-null; **null** represents a missing or unknown value in this SQL
context. A **composite key** uses several columns together. A combination such as
`(workshop_id, seat_number)` can identify a seat while neither part is unique alone.
A table can have one declared primary key and other uniqueness rules. See
[PostgreSQL's primary-key definition](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-PRIMARY-KEYS).
Naming a column `id` is not itself a declaration of any of these rules.

In our example, the design chooses `people.person_id` and `bookings.booking_id`
as primary keys. A **foreign key** is a declared rule connecting referring values
to an allowed referenced key. If `bookings.person_id` is declared as a non-null
foreign key to `people.person_id`, every booking must refer to an existing person
under that rule. This maintains **referential integrity** for that reference.
The [PostgreSQL foreign-key tutorial](https://www.postgresql.org/docs/18/tutorial-fk.html)
shows an insertion rejected because its referenced record does not exist.

Now change `r19` to refer to `p9`, which is absent from `people`. With that rule
enforced, the proposed value violates it. Without a database constraint, a column
called `person_id` does not automatically prevent the bad reference. Application
code might perform a check, but the name alone proves neither that check nor its
correctness under concurrent changes.

Similarly, the JSON field `"person_id": "p1"` is a reference by application meaning.
Those characters do not automatically establish a database-enforced foreign key.
An **embedded** contact stores details inside the booking; a **reference** points
to another record by identity. If Mina changes her name, decide whether the booking
should retain the name recorded at booking time or show the person's current name.
That meaning determines whether unchanged embedded text is history or stale data.

### 3) **Explain relationship counts and diagnose a broken model claim**

A **relationship** associates entries. **Cardinality**, in this modeling context,
describes how many entries can participate on each side. It is also used elsewhere
for a count of distinct values, so include the context.

A **one-to-many relationship** allows one person to have many bookings, while each
booking belongs to one person in this design. The example has two bookings for
`p1`. A **one-to-one relationship** allows at most one associated entry on each
side; whether participation is mandatory is a separate rule. A **many-to-many
relationship** permits several entries on both sides, such as people attending
several workshops and workshops admitting several people.

A **junction table**, also called a link or association table, can represent that
last relationship. For example, `attendance(person_id, workshop_id)` records pairs.
If the design prohibits duplicate attendance, the pair can be a composite primary
key. `p1/w4` and `p1/w5` then differ, while a second `p1/w4` repeats the same pair.
MongoDB's [modeling guide](https://www.mongodb.com/docs/manual/data-modeling/#document-relationships)
illustrates the same relationship categories and embedded/reference choices in a
document context. Relationship meaning is not limited to relational databases.

A constructed review says: “Every column ending in `_id` is a foreign key, so the
model cannot contain invalid bookings.” This overstates both the mechanism and
the outcome. Request the actual declared rules and their enforcement state.
Even an enforced person reference does not establish that `seats` is positive,
the workshop is open or the booker has permission. Each requirement needs its
own relevant rule or operation.

Practice: change the display name of `p1` to Sara. Does `r17` now belong to `p2`,
whose name remains Mina? No. The booking refers to `p1`, not to whichever person
currently displays a matching name. A model that uses names as identifiers would
need explicit uniqueness and change rules; human names do not supply those
properties automatically.

### 4) **Common confusion**

A primary key identifies a row; it does not have to be an auto-incrementing integer
or reveal the row's business meaning. Composite identifiers also need their full
scope. Seat `12` in workshop `w4` need not be the same seat assignment as `12` in `w5`.

Repeated display names are not necessarily duplicate people. Conversely, two
records with different technical IDs could describe the same real-world person.
Technical uniqueness and business duplicate detection answer different questions.

### 5) **Performance note**

Embedding data can let one read obtain related details, while references can keep
shared details in one place. Either choice changes the work needed for particular
reads and updates. The small artifacts establish identity and structure, not
latency or storage efficiency. Constraints and indexes can also have operational
costs; knowing a key's meaning does not prove that every lookup or write is fast.

### 6) **Mentor note**

Ask a learner to circle one record's identity, underline its attributes and draw
its references. Then give two people the same name and remove a referenced person.
A sound explanation preserves identity, identifies the potentially broken link,
and asks for the enforcement rule instead of diagnosing from column names alone.
For cardinality, require both the maximum count and whether absence is permitted.
