## 1.1. Data datasets databases and database management systems

“The database changed” might mean that someone edited a reservation, installed a
new software version, or replaced an exported report. Those are different changes
with different consequences. Start by naming the information, its collection and
the software responsible for managing it.

The earlier representation, file and API lessons supply the prerequisites. This
page is a reading exercise: it requires no database installation. Product examples
use PostgreSQL 18 documentation and SQLite's embedded architecture, checked
2026-10-18; they are not reports of a running database in this lesson.

### 1) **Separate information collections and management software**

**Data** is represented information that software can store or process. The value
`2` becomes useful reservation data when its context tells us it means two seats,
rather than two seconds or an identifier. Representations and units still matter;
the database label does not supply that missing meaning.

A **dataset** is a collection of data considered together for a purpose. “Approved
reservations for this workshop as recorded at 09:00 UTC” identifies a useful scope.
Its exported values might be available in JSON and in CSV, a text format using
separated fields and records. Two formats need not mean two different underlying
collections. Check which fields, selection rules and observation time they represent.
The W3C's [DCAT 3 overview](https://www.w3.org/TR/vocab-dcat-3/#vocabulary-overview)
provides a formal cataloging example that separates a dataset from its accessible
representations. You do not need its metadata language to use this distinction.

A **database** is an organized collection of data, maintained for access and use.
It can contain several related collections and support ongoing changes. A dataset
can be extracted from a database, span several sources or exist independently as
files. The terms overlap in ordinary use; neither is defined by an arbitrary size
threshold or a requirement to fit in exactly one file.

A **database management system**, abbreviated **DBMS**, is software that manages
databases and their operations. It provides ways to define, read and change data
under the rules it implements. PostgreSQL is a DBMS product; `booking_demo` can be
the name of one database it manages. PostgreSQL's
[concepts tutorial](https://www.postgresql.org/docs/18/tutorial-concepts.html)
uses tables as its concrete organization. Other database models exist, so “all
databases are spreadsheets” is an unreliable mental model.

| Name in a reservation discussion | What it identifies |
|---|---|
| Reservation `r17` has two seats | Data with application meaning |
| Approved reservations recorded at 09:00 UTC | A scoped dataset |
| `booking_demo` | A named database in this example |
| PostgreSQL 18 | The DBMS product and its major version |
| `approved-0900.json` | A file containing one export representation |

Editing `r17` changes data. Updating the DBMS changes software. Reformatting an
export may change its bytes without changing the reservation facts it represents.
Specify the object of the change before deciding whether consumers need a new
report, a software compatibility check or a correction to the stored information.

### 2) **Identify the client engine and server roles**

A **database client** is software requesting database operations. It might be a
command-line tool, a graphical administration application or an application
backend. A backend can be a server to a browser and a client to a database in the
same workflow. These words describe interaction roles.

A **database engine** is the machinery that performs database operations. Vendors
sometimes use “engine” and “DBMS” broadly for the same product; elsewhere an engine
is a component inside a larger system. Name the product and responsibility rather
than assuming that every use of the word denotes an independently installed server.

In PostgreSQL's client/server architecture, the **database server** accepts client
connections and manages database operations and files. Clients and the server can
run on different computers. A GUI on your laptop is therefore not the database
itself, and its view of local files need not match the server's filesystem. See the
[PostgreSQL architecture tutorial](https://www.postgresql.org/docs/18/tutorial-arch.html).
Here, “server” names software providing the service; people may also use it for
the computer hosting that software, so clarify which failed.

An **embedded database** uses an engine inside the application process. SQLite
illustrates this arrangement: the library accesses database files without a separate
database server process between it and the files. The application still uses
database software; a filename alone does not perform the operations. SQLite calls
this [serverless](https://sqlite.org/serverless.html) in its architectural sense.
A hosted product described as serverless may instead have provider-operated servers.
Those uses of the label require different diagrams.

Neither arrangement is automatically correct for every application. At this stage,
the useful question is “which component handles the database operation?” Choosing,
administering or tuning that component requires requirements beyond the vocabulary.

### 3) **Read a data report without blaming the wrong object**

This constructed packet states all times on the same day in UTC. It is an artifact
classification exercise, not an observed database session.

| Evidence | Stated observation |
|---|---|
| System inventory | PostgreSQL 18 manages the named database `booking_demo` |
| Export record | At 09:00, export `approved-0900.json` contained `r17`, approved, two seats |
| Change record | At 09:05, `r17` was changed to cancelled in `booking_demo` |
| Report input | At 09:10, the report read the unchanged 09:00 export |
| Report output | The report displayed `r17` as approved |

A colleague concludes: “PostgreSQL is broken because the database still says
approved.” The packet supports a narrower explanation. The report read a file
representing an earlier dataset; it did not read the current database in the
stated observation. The file's old value does not contradict the later database
change. Whether the report ought to refresh is a product requirement, not a fact
deduced from the DBMS name.

A useful handoff is: “The 09:10 report used the 09:00 export. The change record says
`r17` became cancelled at 09:05. Please establish the report's freshness requirement
and whether its input should be regenerated or read through the current service.”
This identifies both the evidence and the decision needed. Reinstalling the DBMS
would not address the stated old-file input.

Now remove the export record's time and the report-input evidence. Can we still
establish the same cause? No. Ask which source the report actually read, when that
source was produced and whether the selection rules match. A database connection
error would be different evidence again: it says an attempted access failed, not
that the stored reservation necessarily disappeared.

For a final distinction, suppose the inventory instead says “SQLite library in the
report process, database file `booking.sqlite`.” There is no separate PostgreSQL
server to restart in that described path. Identify the application's file access
and embedded engine before investigating. A stopped process and a missing database
file are different conditions even though either might be reported as “database down.”

### 4) **Common confusion**

A database product logo, a named database and a client window can all be casually
called “the database.” That shorthand works only while everyone shares the same
context. In a failure report, name the product/version, the intended database or
file, the requesting application and the observed operation.

A dataset is also not necessarily a frozen export. A team can maintain an evolving
dataset; the time boundary in this example is explicit. Calling something a
“snapshot” in conversation does not by itself establish a transactional guarantee
about how it was captured. Preserve the collection and timing assumptions.

### 5) **Performance note**

The labels data, dataset and database have no direct speed effect. Costs arise
from the actual work and path: reading an export, performing a database operation
or communicating with a separate server can involve different processing and I/O.
This lesson measures none of them. An embedded/client-server distinction identifies
a boundary; it does not rank the two systems for an unspecified workload.

### 6) **Mentor note**

Ask a learner to classify four changes: cancelling `r17`, generating a new export,
upgrading PostgreSQL and closing the GUI. A sound answer identifies data change,
new representation, software change and client lifecycle respectively. Then remove
one row of the packet and ask which conclusion becomes uncertain. Reward the
ability to request missing evidence, not just expansion of DBMS.
