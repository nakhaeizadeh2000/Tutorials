## 1.2. Relational document key-value graph and time-series models

A reservation system can organize people, bookings and room temperatures in
several ways. A model name tells you how information is represented and accessed.
It does not settle whether a write survives a failure, whether concurrent updates
are safe, or whether a particular question will be fast.

Read the preceding data/DBMS distinction first. This lesson compares illustrative
models, not five installed products or an implementation benchmark. Product
capabilities below were checked against their documentation on 2026-10-18.

### 1) **Recognize what each model makes explicit**

A **data model** describes the structures used to organize information and the
relationships those structures express. The word can also mean an application's
specific design: “our booking model.” Clarify whether a discussion concerns a
family of representations or one application's choices within that family.

| Model | Main organization | Example question |
|---|---|---|
| Relational | Named tables of rows and columns, with relationships expressed through values | Which bookings belong to each workshop? |
| Document | Structured documents containing named fields and potentially nested data | What details belong in this booking's document? |
| Key-value | A key identifies an associated value | What value is stored under `booking:r17`? |
| Graph | Nodes and explicit connections, with details depending on the graph model | Which attendees are connected through shared workshops? |
| Time-series | Observations associated with times and identifying dimensions | How did room temperature change during the workshop? |

A **relational database** organizes data using relations, commonly presented as
tables. A relational DBMS, or **RDBMS**, manages that model. “Relational” refers to
relations, not a promise that other models cannot represent relationships.
PostgreSQL's [concepts tutorial](https://www.postgresql.org/docs/18/tutorial-concepts.html)
supplies the table/row/column orientation. A display order is not an inherent
ordering guarantee for rows.

A **document database** treats structured documents as important units. A document
is data with named fields, rather than necessarily a word-processing file. For
example, a booking can include a nested contact object and a list of attendee
names. MongoDB groups documents in collections, supports embedded and referenced
relationships, and permits documents to vary in structure unless validation rules
restrict them. Its [data-modeling guide](https://www.mongodb.com/docs/manual/data-modeling/)
also emphasizes access patterns. Flexible structure still needs a design.

In a **key-value model**, the key is the name used to retrieve or modify the
associated value. Think of `booking:r17` selecting one stored booking value.
The value might be bytes or a richer supported structure; key-value does not mean
“only plain text.” Redis's [keyspace guide](https://redis.io/docs/latest/develop/using-commands/keyspace/)
provides a concrete key/value example. Its
[data-type overview](https://redis.io/docs/latest/develop/data-types/) shows why
“Redis is only a string cache” is too narrow a product description.

A **graph database** organizes information around nodes and connections. A node
might represent an attendee, with a connection to the workshop they booked.
Neo4j's **property graph** attaches properties to nodes and relationships and gives
relationships a direction and type. Those are properties of that graph model;
other graph models need their own definitions. Read its
[graph concepts](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/)
for the scoped terminology. Graph here means connected data, not a chart drawing.

A **time series** is a sequence of observations associated with times. A
**time-series database** emphasizes storing and working with such data. A temperature
observation needs a time, value, unit and sensor identity to answer the intended
question. InfluxDB 3 Core describes its data using databases, tables, timestamps,
tags for identifying context and fields for values. That
[current product model](https://docs.influxdata.com/influxdb3/core/write-data/best-practices/schema-design/)
uses tables too. A time-series label and a tabular representation can coexist.

### 2) **Separate model labels from product guarantees**

**NoSQL** is an umbrella label used for several database families beyond the
traditional relational/SQL-centered category. It is often glossed as “not only
SQL.” Treat the label as a starting point for questions, not a precise guarantee
shared by every product. Document, key-value and graph databases differ from one
another. NoSQL does not mean no relationships, no structure or no transactions.

A **transaction** groups database work under defined guarantees, developed later
in this domain. For this comparison, the key fact is that MongoDB's
[transaction documentation](https://www.mongodb.com/docs/manual/core/transactions/)
explicitly supports multi-document transactions with configuration-dependent
behavior. Thus “NoSQL means transactions are impossible” is already disproved by
a concrete counterexample; the product's exact supported deployment and settings
still matter.

The categories are also not exclusive product boxes. PostgreSQL supports JSON
values in table columns through its [JSON types](https://www.postgresql.org/docs/18/datatype-json.html).
Receiving JSON from a database therefore does not prove it is a document-only
product. Likewise, adding a timestamp column to a table does not demonstrate
specialized time-series storage or a retention policy.

Separate three questions in a proposal: what structure represents the information,
what operations the product supports, and what guarantees the configured deployment
provides. An answer to one cannot silently stand in for all three. In particular,
“schemaless” usually concerns how structure is declared or enforced. Code that
expects a field still has an expectation even if the database permits its absence.
Full schema and migration terminology follows in the next section.

### 3) **Translate a workload into questions before choosing labels**

Consider these constructed requirements for a workshop application:

1. Show one reservation and its contact details by reservation identifier.
2. List every workshop with the number of confirmed reservations.
3. Find chains of attendees connected through shared workshops.
4. Compute the average temperature for each room over five-minute intervals.

A document-shaped booking is a natural representation to discuss for the first
screen. A key lookup also describes how that screen locates its booking. These
observations are compatible: the access pattern and the value's structure name
different aspects of the same work.

The second question needs related bookings and workshops to be combined and
counted. A relational representation makes those collections explicit, but that
is not proof that only a relational product can answer it. The third foregrounds
connections and traversal, so a graph model is useful language for expressing the
question. The fourth foregrounds time windows and grouping by room, motivating
time-series terminology. None of these sketches establishes the fastest system.

A weak proposal says: “Use NoSQL; it will scale and cannot have schema problems.”
A useful revision says: “The reservation screen reads a document by identifier.
We also need cross-workshop counts and changes to contact fields. Show how the
candidate product supports those operations and handles old and new document
shapes. State the data volume, concurrent work and failure requirements before
claiming a performance or recovery benefit.”

Practice: if the proposal now adds “our relational database returns a JSON booking,”
what contradiction has appeared? None. The result format does not identify the
stored model, and relational products can support JSON data. Ask about the actual
tables, document fields and retrieval operation. You need those artifacts to
understand the design; the response's braces alone are insufficient evidence.

### 4) **Common confusion**

“Relational” is not a synonym for “all fields are scalar text,” and “document” is
not a synonym for “no links between records.” Both can represent connected
information. Their representation and supported operations differ, so a design
must explain where each relationship lives and how changes remain coherent.

A time-series point also is not identified by a timestamp alone in every product.
Two sensors can observe different values at the same instant. Preserve the
identifying dimensions and product rules instead of assuming one global record
per clock tick.

### 5) **Performance note**

A data model influences the work needed for a particular question. Reading one
nested booking differs from combining many bookings or traversing connections.
Products can add indexes and specialized operations, so the model's name cannot
predict their measured cost. This lesson makes no timing or scalability comparison.
A useful evaluation specifies the operations, dataset, write rate, supported
features and failure requirements before measuring candidates.

### 6) **Mentor note**

Give a learner the four requirements without product names and ask them to mark
identities, nested details, connections and time windows. Then introduce a new
report that combines workshops. A sound explanation revisits the access needs
instead of declaring the first model universally best or replacing one product
with four products merely because four patterns were named.
