## 7.1. Read a data design and recovery claim

A proposal can use correct database words while connecting them through unsupported
guarantees. “Typed, transactional, replicated and backed up” still needs an object,
operation, time and failure scope for each claim. This exercise integrates the
preceding lessons through one constructed workshop system.

Read the earlier data-model, schema, access, transaction, storage and pipeline
owners first. Every observation below is fictional. No actual service, recovery
procedure or production readiness assessment is being reported.

### 1) **Translate the proposal into separate responsibilities and promises**

The proposal reads:

> PostgreSQL stores the bookings. The typed access layer makes all values valid.
> Contact fields are flexible, so renames need no migration. Each booking is ACID,
> which guarantees its confirmation email. A replica and daily backup mean no
> accepted booking can be lost. CDC makes the dashboard immediately current.

The product requirements are explicit: a confirmed booking must have a valid
workshop reference and positive seats; the application must not exceed capacity;
confirmation email status must be reported separately; recovery must identify
which accepted bookings can be reconstructed. No numerical recovery deadline or
maximum report delay is supplied.

Break the proposal apart before evaluating it:

| Claim boundary | Relevant evidence |
|---|---|
| Stored booking rules | Actual database constraints and application operations |
| Typed access layer | What the checked model describes, plus actual database results |
| Contact-field change | Existing records and active reader/writer expectations |
| Transaction | Included statements, completion result and concurrency settings |
| Email | Separate delivery outcome and its relation to database work |
| Recovery copies | Capture times, retained contents, history and restore results |
| Dashboard | Source/capture/application/summary/display progress |

These are evidence requests, not a requirement to use a particular database or
framework. A role name identifies where to investigate; it does not prove that
the requirement was implemented.

### 2) **Trace observations to supported conclusions**

The constructed packet contains these facts, all on one day in UTC:

| Artifact | Established fact |
|---|---|
| Schema inspection | Booking has a non-null workshop reference with an enforced foreign key and a positive-seat rule; no capacity rule is shown |
| Contact sample | Stored r17 still has `contact_name`; the new reader reads only `booker_name` |
| Capture record | At 09:00, the recovery backup contains r17 and no r18 |
| Booking transaction | At 09:10, r18 insertion and the corresponding capacity reduction commit together |
| Email record | r18's confirmation email delivery fails after that commit |
| Analytics record | r18's change is captured at 09:10:02; last verified applied input for the dashboard is 09:00 |
| Deletion record | At 09:20, both the primary and following replica have applied deletion of r18 |
| Recovery inventory | No later backup or usable log history is available |
| Isolated restore result | Restoring the 09:00 backup produces r17, without r18 |

First evaluate validity. The shown rules establish a valid referenced workshop
and positive seat count for accepted rows under those rules. They do not establish
capacity protection. Ask for the operation and concurrency mechanism that prevents
overbooking the remaining places. A generated type declaration cannot fill that
gap or prove deployed constraints match its assumptions.

Next evaluate the rename. The sample and new reader disagree on the field name.
Allowing flexible document content does not repair that reader. Ask how the active
readers handle old and new shapes, how writers transition and whether stored data
needs transformation. An example showing both names is useful only if their
precedence and meaning are defined. “Schemaless” does not eliminate this contract.

The booking transaction did commit both database changes. The failed email is a
separate outcome. Saying “the booking rolled back because the email failed”
contradicts the packet's commit evidence. A useful report is: “r18 is recorded and
capacity is reduced; confirmation delivery failed.” Further coordination depends
on the product's intended handling of undelivered confirmation. Do not blindly
repeat the booking operation to repair email delivery.

For analytics, the source commit and capture are established, while application
after 09:00 is not. The dashboard's missing r18 is compatible with its verified
input time. We cannot yet distinguish a delayed consumer, failed transformation
or old presentation input. Obtain the applied source position and the specific
summary read by the dashboard. A CDC product label does not establish those stages.

Finally, the replica reflects the deletion. The retained backup and its restored
contents predate r18. Under the stated inventory, r18 cannot be reconstructed from
those artifacts. Do not claim an impossible recovery merely because a restore
command completed successfully. The earlier
[backup and restore lesson](<../5. Storage and copies/5.2. Backups snapshots replication sharding and restores.md>)
provides the mechanism and a real local demonstration; this packet remains fiction.
GitLab's [historical incident account](https://about.gitlab.com/blog/postmortem-of-database-outage-of-january-31/)
also distinguishes expected backups from available recoverable state.

### 3) **Choose discriminating checks and write a concrete handoff**

A technical handoff can state:

> The shown constraints cover reference existence and positive seats, with capacity
> protection still unverified. The new contact reader does not handle the supplied
> old record shape. r18's database changes committed, while email delivery failed.
> Dashboard application after 09:00 is unverified. The tested 09:00 backup restores
> r17 but predates r18, and the replica has applied r18's deletion. Identify the
> capacity mechanism, contact transition, delivery recovery and required retained
> history before describing this design as complete.

For a product collaborator, preserve the consequences with fewer implementation
terms: “The booking was recorded, but its email failed. The report has not been
verified against the latest booking changes. The available recovery copy cannot
restore the later booking in this scenario. We also need to confirm how capacity
is protected and how older contact records remain readable.”

Select the next check to resolve one uncertainty. Comparing an old contact record
with the deployed reader tests a compatibility hypothesis. Inspecting the last
applied analytics position tests a different stage. Timing an indexed query does
not answer either question. A recovery rehearsal should check required records
and application use in an isolated target, not overwrite the live system merely
to discover whether the backup is usable.

Change one packet row: add independently verified retained history sufficient to
replay through 09:15, with a tested successful restore to that point. The earlier
“r18 cannot be recovered from the available artifacts” conclusion no longer holds.
The replica alone still does not supply that history; the new evidence does.
Now remove the isolated restore result instead. You can still see that the backup
predates r18, but you must leave the backup's actual usability unverified.

For interview practice, explain why “ACID and replicas guarantee no data loss” is
too broad. A strong answer names the transaction, acknowledgment, configured
persistence, replication stage, failure type and required historical recovery.
It separates missing evidence from a demonstrated failure. Merely expanding ACID
or prescribing more servers does not meet the reasoning goal.

### 4) **Common confusion**

A missing guarantee is not automatically a proven defect. The packet establishes
a field-reader mismatch and a failed email, but it leaves the capacity mechanism
unverified rather than showing overbooking. State that distinction clearly.

A successful local restore also is not evidence for every future recovery. Here
its contents and capture time support a specific conclusion. Newer data, changed
versions, different permissions or missing supporting material require their own
checks against the actual intended recovery target.

### 5) **Performance note**

This packet contains no measured durations or load. An index, replica, CDC stream
or warehouse label cannot establish that the booking path or report is fast.
First define the operation, data scope, acceptable freshness and success outcome.
Then measure the corresponding path. Recovery speed and recovered contents are
separate outcomes; a quickly restored incomplete dataset does not satisfy a
requirement for later accepted records.

### 6) **Mentor note**

Ask a learner to mark every handoff sentence as observation, supported inference,
unresolved question or proposed action. Remove one supporting row and require the
appropriate sentence to become less certain. A sound review offers a check that
could distinguish explanations and keeps the user-visible consequence intelligible
without hiding it behind technical labels.
