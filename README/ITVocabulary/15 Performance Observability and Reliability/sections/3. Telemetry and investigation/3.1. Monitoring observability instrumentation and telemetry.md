## 3.1. Monitoring observability instrumentation and telemetry

A dashboard can report successful HTTP responses while a user asks whether their
registration was actually stored. If the collected evidence covers only request
acceptance, the dashboard cannot answer the storage question. Start with the
question, then inspect which observations exist and how they reached the report.

This lesson uses fictional telemetry records, not a deployed monitoring system.
Detailed log, metric and trace structures belong to the next lesson.

### 1) **Separate an activity a capability and the data supporting it**

**Monitoring** is the ongoing collection and examination of system observations
for purposes such as tracking behavior, detecting conditions and assessing service
health. An explicit check might count failed responses or test a registration
workflow. State what it actually observes: a process responding on a health route
is weaker evidence than a successful business operation through required dependencies.

**Observability**, in this software context, is the ability to investigate and
understand a system's behavior from available observations. It concerns questions
the evidence lets you answer, including questions not anticipated when a dashboard
was designed. It is not established by purchasing a product called an observability
platform or by possessing three particular data types.

**Telemetry** is data emitted or collected about system behavior. Logs, numerical
metrics and request traces are common forms, with different detail and aggregation.
OpenTelemetry's primary [observability primer](https://opentelemetry.io/docs/concepts/observability-primer/)
connects the ability to investigate with emitted evidence. That evidence still has
coverage, retention and interpretation limits. No finite instrumentation guarantees
an answer to every possible future question.

Charity Majors's original [discussion of observability definitions](https://charity.wtf/p/observability-is-a-many-splendored-thing)
challenges treating a collection of tools as the capability itself and emphasizes
exploring request context. Apply that question-first reasoning without assuming
that monitoring and investigation occupy mutually exclusive products. Existing
observations can support both activities, and insufficient observations can require
additional instrumentation. Calling the system observable does not recreate an
unrecorded event.

### 2) **Trace instrumentation collection and interpretation separately**

**Instrumentation** supplies observation points or measurement behavior. A developer
might explicitly record when a registration transaction commits. Automatic or
**zero-code instrumentation** can observe supported framework, library or runtime
boundaries without adding the same calls manually to application source. It does
not automatically know every business meaning or cover every dependency.

OpenTelemetry's [instrumentation overview](https://opentelemetry.io/docs/concepts/instrumentation/)
describes code-based and zero-code approaches as complementary. A generic HTTP
instrument can observe a response while missing the later work that response
accepted. Put business evidence at the relevant operation and give its fields
clear meanings; do not rename “handler started” to “registration saved.”

A simplified **telemetry pipeline** has several distinct responsibilities:

| Responsibility | Example question |
|---|---|
| Emit or collect an observation | Did the relevant component record the event or measurement? |
| Receive, process and export data | Was the data accepted, transformed and sent to its intended destination? |
| Store and retain it in a backend | Is it available for the relevant period and scope? |
| Query and interpret it | Does the report select the right service, version, operation and outcome? |

An **exporter** sends telemetry to a destination. A **collector** receives and may
process and export telemetry. The OpenTelemetry [Collector introduction](https://opentelemetry.io/docs/collector/)
provides that concrete role. It is distinct from the analysis or storage backend,
and some configurations send directly from an application to a backend. A collector
is not mandatory merely because a diagram contains the word telemetry.

Data can be absent because an event was not instrumented, because it was filtered
or lost, because retention ended, or because the query selects another scope.
Investigate those boundaries before interpreting “no matching record” as “the
operation never happened.” Conversely, an emitted success label is only as useful
as the behavior its instrumentation actually observes.

State the relevant implementation status too. OpenTelemetry includes different
signals, language implementations and collector components with their own support
and stability. A project name alone does not establish that every selected part
is stable or configured correctly. This lesson introduces roles without installing
an SDK, agent, collector or backend.

### 3) **Answer a business question from a limited telemetry packet**

Read these **constructed records** for request r7 in a NestJS application using
the Fastify adapter. A worker performs the database write after request acceptance.

| Record | Supplied evidence |
|---|---|
| Client response | HTTP 202 Accepted for r7 |
| Monitoring chart | 99% of the selected API responses are 2xx during its window |
| Instrumentation | API middleware observes HTTP responses; the worker can emit commit or failure records tied to the request identifier |
| Pipeline setting | Worker export is disabled; the chart and search backend receive API telemetry only |
| Search result | API acceptance record for r7; no worker record in that backend |

The chart answers a response-class question for its selected population. It does
not show whether r7 was stored. The missing worker record also does not establish
a failed write: the supplied transport configuration explains why that backend
has no worker evidence. The actual write outcome remains unknown in this packet.

A useful handoff says:

> We have request-acceptance evidence for r7. The report covers API response classes,
> and worker observations are not exported to this backend. We need evidence for
> the database operation, with request identity and outcome semantics checked, and
> we need to verify the observation path before using this report for that question.

In a **separate variation**, worker export is enabled and its delivery path is
verified. A worker record linked to r7, emitted only after the database transaction's
commit acknowledgment, is delivered to the backend. This supports the stated acknowledged commit for that operation.
It does not show a subsequent user notification, correct content in every field,
all future durability conditions or equivalent evidence for other requests. More
specific observation strengthens a specific claim.

Practice: change only the search query to select another deployment version. An
empty result from that query would describe its selected scope; it would not revoke
the r7 evidence in the correct scope. Include version and component context in
investigation notes so later readers can reproduce the question being asked.

### 4) **Common confusion**

Instrumentation produces or collects observations; exporting, retaining and querying
them are other responsibilities. “We added logging” does not establish that the
intended backend received the relevant event, and “the collector is running” does
not establish that the application emitted it.

Monitoring can reveal a symptom and support investigation. Observability describes
the useful investigative capability, rather than a rule that existing monitoring
data can never answer an unfamiliar question. Check the actual evidence and question.

### 5) **Performance note**

Instrumentation, encoding, transfer, processing, indexing and retention consume
resources. More fields or more observations can improve investigation while adding
cost and possible sensitive-data exposure. Collect relevant evidence under its
purpose and access rules; indiscriminately recording every request body is not a
universal improvement. No instrumentation overhead, collector throughput, backend
cost or application latency was measured in this exercise.

### 6) **Mentor note**

Ask what the 99% chart can answer before asking what happened to r7. Then reveal
the disabled worker exporter. A sound answer identifies an evidence-path gap without
inventing a failed write. Add the commit acknowledgment record and ask which claim
becomes supported. Evaluate whether the learner can name a useful observation,
its meaning and its delivery path instead of simply requesting “more logs.”
