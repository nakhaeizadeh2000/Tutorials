## 3.2. Logs metrics traces spans correlation and cardinality

An error chart identifies a rising count, a log records a timeout, and a trace
shows related operations. These artifacts can complement one another, but they
retain different information. Ask which artifact supports the particular claim
instead of treating every signal as a full record of the request.

The previous lesson owns instrumentation and the observation pipeline. The
artifacts below are fictional, with simplified identifiers and one service clock.
They are not OpenTelemetry wire payloads or results of a running backend.

### 1) **Choose the artifact from the observation needed**

A **log** records an event or message, commonly with a timestamp, component,
severity and contextual fields. A **structured log** separates named fields so
tools can filter them without guessing their meaning from free text. Structure
helps interpretation; it does not establish that a label such as saved was emitted
at the correct point or that the logging path retained every event.

A **metric** represents a numerical measurement with time and associated dimensions.
Metrics commonly aggregate many operations. A **counter** accumulates counted
activity; its reporting must account for resets and the chosen cumulative or
interval representation. A **gauge** describes a current value such as occupied
slots. A histogram retains a distribution representation, as explained in the
percentile lesson. A count of errors needs a matching request population to become
an error fraction.

OpenTelemetry's [metric concepts](https://opentelemetry.io/docs/concepts/signals/metrics/)
distinguish instruments and aggregation. Reading a counter value of 10,000 as
10,000 requests per second loses its time basis. A gauge reading of 8 occupied
slots is also not a count of 8 new requests during that second.

A **trace** associates recorded operations in a request or related workflow. A
**span** represents a particular operation, usually with start/end time, identity,
attributes and context linking it to related spans. A **root span** has no parent
within its trace; a **child span** records a related sub-operation under a parent.
Links can associate spans beyond one parent-child relationship, including
asynchronous work. A trace can cross processes when the needed context propagates.

A **trace ID** identifies the trace; a **span ID** identifies an operation within
that context. A team's **request ID** can be a separate identifier with its own
rules. OpenTelemetry's [trace explanation](https://opentelemetry.io/docs/concepts/signals/traces/)
connects spans, propagated context, attributes and links. A distributed trace is
different from an exception stack trace: the latter records call frames at an
observation, rather than the instrumented workflow across components.

### 2) **Correlate recorded operations without inventing missing ones**

**Correlation** associates relevant observations, often through shared identifiers
and context. Request identity, component, version and observation time can help
relate a log to a trace. **Context propagation** carries needed association data
across an operation boundary. It does not happen merely because two services use
the same tracing product.

Here is a **simplified structured log**. Identifiers T7 and P1 are explanatory
labels, not valid protocol identifiers. Under this packet's logging contract,
policy_timeout is emitted when this client observes its policy-call deadline.

```json
{"elapsed_ms":30,"service":"api","event":"policy_timeout","request_id":"r7","trace_id":"T7","span_id":"P1"}
```

The accompanying **client-side trace fragment** for T7 uses one clock:

| Span label | Operation | Parent | Start ms | End ms |
|---|---|---|---|---|
| A1 | API request r7 | None | 0 | 40 |
| D1 | Database client operation | A1 | 5 | 35 |
| P1 | Policy-service client operation | A1 | 10 | 30 |

The log can be associated with P1 under the supplied identity rules. It records a
client-observed timeout, not a proven policy-server failure or unique network
cause. No remote-internal spans are supplied. The local database operation spans
30 ms and the policy operation spans 20 ms, but they overlap. Adding 30 + 20 does
not give the API's 40 ms elapsed time. A trace may also omit uninstrumented work.

A metric chart counting all API failures during the interval can show whether this
condition is common in its population; it does not automatically identify r7 or
prove that every failure shares its cause. Conversely, this single trace does not
establish a service-wide percentile or failure rate.

**Sampling** selects some observations for recording or retention under a policy.
Missing spans can also reflect disabled instrumentation, export problems or query
scope. A trace view is therefore a view of recorded evidence, not proof of every
operation performed. Match the data's coverage and collection policy to the claim.

Practice: remove request_id, trace_id and span_id from the log while leaving its
time and service. It is now weaker evidence for an association with this request:
nearby time alone may match several concurrent requests. Request the missing
context or an independent association before attaching that event to P1.

### 3) **Account for dimensions and cardinality before adding identifiers**

An **attribute** is a named contextual value. In a metrics system, **labels** or
**dimensions** partition observations by values such as service, route or outcome.
A **time series** records observations over time for a defined metric identity and
label set. Exact identity rules depend on the data model.

**Cardinality** counts distinct values or combinations under a stated scope.
It differs from **dimensionality**, the number of attributes available to describe
an observation. One request_id dimension can have thousands of distinct values;
several fixed dimensions may produce far fewer observed combinations.

Consider an **unconstrained classroom metrics mapping** with 10,000 requests.
Each request is counted once. There are 3 services, 2 route categories and 4 outcome
categories, and all 3 × 2 × 4 = 24 combinations occur. With only these labels,
there are 24 distinct metric series. Add a globally unique request ID to every
request's metric labels: now there are 10,000 observed distinct series, one for
each request. The 24 original combinations are not an extra multiplier because
each unique request belongs to only one of them in this example.

Prometheus's [label guidance](https://prometheus.io/docs/practices/naming/)
explains how unique label combinations create series. OpenTelemetry also documents
cardinality limits and overflow aggregation, where measurement values can be
retained while detail in attributes is reduced. Check the actual SDK/backend and
query behavior; our classroom count assumes no such limit or overflow processing.
A bounded total does not guarantee every requested per-attribute breakdown exists.

Detailed identifiers can be useful for investigating individual requests in logs
or traces. This does not make them suitable as unconstrained metric labels. Choose
fields and their storage model for the question, cost, retention and access needs.
Do not copy sensitive payloads or credentials into every signal to make it “richer.”
The earlier observability lesson's question-first approach and privacy owners
retain those judgment boundaries.

### 4) **Common confusion**

A distributed trace is not an exception stack trace, and child-span durations do
not generally add up to a parent's duration. Overlap, gaps, different clocks and
missing operations affect interpretation. This example deliberately uses one clock
to isolate overlap rather than a clock-synchronization problem.

A matching ID supports association under its generation and propagation rules.
It is not a causal proof or an authorization credential. A high-cardinality value
also has different cost implications as a metric label, searchable log field or
trace attribute; avoid one blanket rule for every signal.

### 5) **Performance note**

Event volume affects log transport and retention; attribute combinations affect
metric aggregation and storage; spans, attributes and retention affect trace cost.
Sampling or limits can reduce some costs while reducing investigative detail.
No fixed cost multiplier follows from the 24-to-10,000 example, and no telemetry
backend, sample policy, storage bill or application overhead was measured here.

### 6) **Mentor note**

Ask the learner to connect the log to its span, calculate the two child durations
and explain why their sum exceeds the API interval. Then propose adding request IDs
to the counter labels. A sound answer preserves per-request investigative value
while explaining the 10,000 distinct combinations and choosing an appropriate
representation instead of treating every available field as a metric dimension.
