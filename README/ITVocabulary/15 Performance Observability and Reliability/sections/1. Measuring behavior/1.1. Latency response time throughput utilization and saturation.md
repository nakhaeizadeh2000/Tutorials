## 1.1. Latency response time throughput utilization and saturation

A report says “requests are slow, but CPU is only 20%.” That is possible: requests
can wait for a database connection while the CPU has little work to execute.
Response time, completed work and resource use answer different questions. Name
the operation and observation boundary before interpreting the number.

Earlier units explain durations and network measurements. Here the new question
is a service operation's behavior and its required resources. All numbers below
are synthetic; no service or load generator is measured.

### 1) **State which time and work rate a report measures**

**Latency** is elapsed delay between specified events. In service discussions,
**response time** often means elapsed time from a request's start to its observed
completion. Teams and tools use latency for different subintervals, so the label
alone does not settle whether it includes queueing, processing, network transfer
or the complete user interaction. A time to first response byte also differs from
time to receive the complete response.

Suppose a single service clock records a request accepted at 4.0 seconds, removed
from a queue at 6.0, and completed at 6.1. For these explicitly defined boundaries,
queue wait is 2.0 seconds and subsequent service time is 0.1 seconds. The service's
acceptance-to-completion response time is 2.1 seconds. The browser may have observed
additional time outside this interval. Do not call the entire 2.1 seconds CPU time
or a measured network delay.

**Throughput** is completed work per time at a stated boundary. It might count
responses, successful registrations, processed messages or bytes. Identify the
unit and which outcomes qualify. **Arrival rate** counts work entering that
boundary; **completion rate** counts work leaving it as completed. These rates can
differ while work accumulates or drains. Concurrent outstanding requests are a
count at a time, rather than a per-second rate.

A successful business outcome needs a suitable rule. An HTTP response can count
as completed while reporting an error, and a 200 response can carry the wrong
result. Google's original [monitoring discussion](https://sre.google/sre-book/monitoring-distributed-systems/)
distinguishes successful and failed request timing and treats traffic and errors
as separate observations. Faster errors can change a combined latency summary
without improving successful task completion.

### 2) **Separate resource use from excess waiting work**

**Utilization** describes resource use under a defined accounting model. State the
resource, interval and denominator. Common examples include:

| Resource and model | Utilization observation | Important boundary |
|---|---|---|
| One CPU, time-based model | Busy CPU time divided by available observation time | Host, process and allocated-capacity denominators can differ |
| Memory capacity | Used amount divided by the defined usable capacity | “Used” may include different kinds of retained or reusable memory |
| Connection pool | Occupied slots divided by configured slots | An occupied connection need not be actively executing a query |

Do not compare “CPU 200%” and “CPU 50%” without the tools' conventions. A tool may
count multiples of one CPU while another normalizes to several CPUs. A long average
can also hide short busy intervals or an imbalance across resources.

**Saturation**, in the resource sense used here, is excess work that a resource
cannot currently service, often visible as waiting work. A pool can have all slots
occupied and additional requests queued even while the application CPU is mostly
idle. High utilization and saturation are related questions, not interchangeable
numbers. Busy time for a device that supports parallel work is also not necessarily
a percentage of its maximum possible throughput.

Brendan Gregg's original [USE Method](https://www.brendangregg.com/usemethod.html)
examines utilization, saturation and errors per resource and explains how interval
averaging can hide bursts. Google's golden-signals discussion uses saturation more
broadly for constrained capacity or fullness. Read the actual metric definition:
a chart called saturation may show a queue, occupancy or a predictive warning.
Neither source supplies one universal “good CPU percentage” for every workload.

Use these observations to select an investigation. A waiting-connection count
makes the pool and its downstream work relevant. It does not by itself establish
that enlarging the pool is safe: more concurrent work can increase load on the
same database. The earlier flow-control and scaling lessons own those mechanisms.

### 3) **Calculate rates and preserve the unresolved cause**

Read this **constructed ten-second packet**. Initially no requests are outstanding.
All arrivals are counted once; none are dropped or retried inside this model.

| Observation | Supplied value |
|---|---|
| Arrived during the interval | 100 requests |
| Completed during the interval | 90 responses: 85 successful registrations and 5 reported failures |
| At the interval end | 10 outstanding: 8 waiting for a DB pool slot and 2 using a slot |
| Application CPU model | One CPU with 2 busy CPU-seconds during the 10-second interval |
| Pool snapshot at the interval end | Both of its 2 slots occupied |
| One separate request trace | Accepted at 4.0, dequeued at 6.0, completed at 6.1 on the same service clock |

The arrival rate is 10 requests/second, completed-response throughput is 9/second,
and successful-registration throughput is 8.5/second. The conservation check is
100 arrivals − 90 completions = 10 outstanding under the stated initial state.
CPU utilization for this model is 20%. The pool snapshot shows 100% occupancy
and 8 waiting requests at that instant; it does not show that those values held
throughout all ten seconds.

The trace's 2.1-second response time includes 2 seconds of queueing. This helps
explain how slow requests and low CPU can coexist. It does not identify why the
slots stayed occupied or establish a complete system bottleneck diagnosis. Ask
about slot holding, database work and the relevant time intervals before choosing
a change. The single trace does not describe every request's response time.

Practice: change only the final 10 outstanding requests into 10 completed timeout
responses by the end of the same interval. Completed-response throughput becomes
100/10 = 10/second, but successful registrations remain 85/10 = 8.5/second. The
higher completion count is not evidence of more useful completed registrations.
This changed packet has zero outstanding requests at the endpoint; do not retain
the earlier queue snapshot as if both endpoint states occurred together.

### 4) **Common confusion**

Requests per second and simultaneous requests measure different quantities.
Likewise, a low CPU average does not rule out another saturated resource or a
short CPU burst hidden by that average. Name the resource and time scope instead
of calling the whole machine “only 20% busy.”

Service time and response time also need explicit definitions. Here service time
begins after dequeueing. A dashboard may use another boundary; preserve its actual
definition when comparing reports.

### 5) **Performance note**

These terms directly describe performance dimensions, but a metric is not a
remedy. Reducing queue wait could reduce the traced response time if other costs
stay fixed; adding CPU has no demonstrated effect on that wait in this packet.
Increasing completed failures can raise response throughput without improving
useful outcomes. The arithmetic is checked separately; no latency, utilization,
pool, capacity or throughput benchmark was performed.

### 6) **Mentor note**

Ask the learner to write units beside 100, 10, 9, 8.5 and 20%. Then ask which
observation supports saturation and which only shows occupancy. A sound answer
keeps the snapshot separate from interval averages, identifies the 2-second wait
and explains why the timeout variation improves a counter without improving the
business result. Ask for the next distinguishing observation, not a guessed resize.
