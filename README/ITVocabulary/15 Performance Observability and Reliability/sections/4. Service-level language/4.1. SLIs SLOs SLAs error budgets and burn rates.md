## 4.1. SLIs SLOs SLAs error budgets and burn rates

“99.9% reliable” is incomplete until the operation, measurement and time window
are defined. It may refer to successful requests, usable time, fresh data or a
contract with exclusions. Separate the observation from the target and agreement
before calculating whether a service met its objective.

The prior measurement and telemetry lessons explain populations and evidence
limits. All service records and targets in this lesson are fictional. No actual
service agreement, availability report or contractual entitlement is assessed.

### 1) **Separate an indicator a target and an agreement**

A **service level indicator**, or **SLI**, is a quantitative measure of a service
property. Examples include the fraction of eligible requests returning correct
results within a stated duration, or the fraction of records processed before a
deadline. State the operation, qualifying population, good-outcome rule, measurement
point and observation window. An internal CPU percentage can inform investigation
without directly measuring a user's successful task.

A **service level objective**, or **SLO**, sets a target for a defined indicator
over its stated window. For example, “at least 99.9% of eligible lookups return the
correct result within 200 ms at the API measurement boundary over 28 days.” The
SLI reports what was observed; the SLO states the desired threshold. A target is
not proof that the system achieved it.

A **service level agreement**, or **SLA**, records agreed service expectations and
the consequences specified for meeting or missing them. Consequences can include
service credits, but the actual terms determine the scope and conditions. An
internal objective is not automatically a customer agreement. Google's original
[service-level terminology](https://sre.google/sre-book/service-level-objectives/)
separates indicators, objectives and agreements through those purposes.

| Question | Relevant object |
|---|---|
| What does our measured good-request fraction equal? | SLI result |
| What fraction are we aiming to provide, over which window? | SLO |
| What have the parties agreed, including applicable consequences? | SLA |

Measurement implementation matters. A server-side count cannot observe every
request that failed before reaching the server. A probe can exercise a path without
representing every user's context. Google's [SLO implementation guidance](https://sre.google/workbook/implementing-slos/)
distinguishes the intended service property from the mechanism used to measure it.
Keep that coverage visible, and define handling of missing data rather than silently
counting it as success.

### 2) **Calculate allowed bad outcomes and the rate of spending them**

For an SLO expressed as a good-event fraction, an **error budget** is the allowed
bad-event fraction: 1 minus the target. At a 99.9% objective, the allowed fraction
is 0.1%, or 0.001. “Error” here includes anything failing the stated good-event
rule, such as a correct but too-late response. It is not limited to HTTP 5xx codes.

For a completed window containing N eligible events, multiply N by the allowed
fraction to obtain the allowed bad-event count. Compare the observed bad count
with that allowance. A negative remaining value means the objective's budget has
been exceeded; it does not make the events disappear. Fractional allowances and
rounding need an explicit reporting convention when event counts are small.

An **error budget policy** describes how a team uses that evidence for decisions,
such as prioritizing reliability work or changing release conditions. It is not
a universal rule that every exhausted budget stops every change. Fixes and other
exceptions need the team's actual policy. A budget is also not permission to
ignore harmful outcomes merely because a numerical allowance remains.

**Burn rate** compares the observed bad-event fraction with the fraction allowed
by the SLO. For this ratio convention:

- Burn rate 1 means the observed fraction equals the allowed fraction.
- Burn rate 5 means it is five times that allowance.
- Burn rate 0 means no bad events were observed in the chosen, nonempty population.

Google's [burn-rate explanation](https://sre.google/workbook/alerting-on-slos/)
connects this ratio to spending the budget. Always report the short observation
window as well as the SLO window. Converting burn into a predicted exhaustion time
requires assumptions about future demand, outcomes, window movement and remaining
budget. A ratio alone is not a measured future deadline.

A **time-based** objective instead defines good and bad time under a particular
measurement rule. In a separate idealized 28-day binary-time model, 0.1% of elapsed
time is 40.32 minutes. That is not a conversion of a request-event budget into
permitted outage minutes: request volume can vary, and the measurement models
have different denominators.

### 3) **Read a passing window with a concerning short-window rate**

Use this **constructed completed report**. The SLI covers received API lookups;
it does not cover requests that failed before the API observation boundary. The
packet's eligibility and good-outcome classifications are supplied as complete
for that boundary, with no missing observations.

| Item | Supplied value |
|---|---|
| Objective | At least 99.9% good eligible lookups in a fixed 28-day window |
| Good rule | Correct result within 200 ms at the defined API boundary |
| Eligible lookups in the full window | 1,000,000 |
| Good lookups in the full window | 999,200 |
| Bad lookups in the full window | 800 |
| Last ten minutes of that window | 10,000 eligible lookups, 50 bad |
| Customer agreement | No SLA terms supplied |

The full-window SLI is 999,200 / 1,000,000 = 99.92%, meeting the stated 99.9% SLO.
The allowance is 0.001 × 1,000,000 = 1,000 bad events. With 800 used, 200 remain,
which is 20% of that allowance. This is an event budget for this completed window,
not 200 minutes or a reserve guaranteed for the next window.

The last ten minutes have a bad fraction of 50 / 10,000 = 0.5%. Its burn rate is
0.5% / 0.1% = 5. A passing full-window report can therefore coexist with a short
interval that spends budget faster relative to the objective. The policy and
additional observations determine the response; neither “the month passed, ignore
it” nor “burn 5 proves a five-minute outage” follows from these numbers.

We also cannot calculate a service credit or establish contractual compliance:
the packet supplies no agreement terms. Even a customer document using 99.9% could
use another operation, window, boundary or exclusion rule.

Practice: change only the collector query so it counts responses within 200 ms
without checking result correctness. A fast wrong result can now qualify in the
query while failing the stated good rule. The implementation no longer measures
the intended SLI. Correct the measurement definition and evidence before treating
a more favorable number as improved service.

### 4) **Common confusion**

SLI, SLO and SLA are not three names for the same percentage. The indicator's
measurement, objective's target and agreement's conditions can differ. A process
being up also does not establish correct, timely user results.

An error budget needs its denominator. A request-based allowance cannot be turned
into minutes without a separate model. A short-window burn rate also does not
replace the full-window result or guarantee future demand and failures.

### 5) **Performance note**

A latency threshold can be part of a good-event definition, connecting performance
to an operational objective. Measurement resolution, incomplete coverage and data
processing cost affect what the report can establish. Choosing 200 ms in this
fiction does not make it an appropriate target for every service. Only arithmetic
was checked; no SLI collection, alert rule, SLO compliance measurement or service
performance test was executed.

### 6) **Mentor note**

Ask the learner to identify numerator, denominator, target and windows before doing
any division. Then ask how 99.92% passing and burn rate 5 can both be correct. A
sound answer keeps the two windows and event populations distinct, explains the
200-event remainder and refuses to invent SLA consequences or outage minutes.
Use the fast-wrong-result variation to test whether they review the good rule,
rather than accepting every larger percentage.
