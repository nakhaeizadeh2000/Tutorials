## 4.1. Data vocabulary checklist (mental models mentors insist on)

### 1) **Name the shape**

Structured vs unstructured — before picking any tool, store, or query (from [1.1](<../1. Data words/1.1. Data vs information structured vs unstructured.md>)).

- **Check yourself**: "support tickets as JSON with fixed fields (structured) plus raw bodies in object storage (unstructured)" — two shapes, two stores, decided up front. Shape-first prevents the millisecond-query-on-PDFs disaster class.
- **Bad habit to break**: choosing the database before describing the data — the most common source of year-two regret migrations.

### 2) **Name the question**

What query, what answer, who consumes it — before touching the store (from [1.2](<../1. Data words/1.2. Database table query and index.md>)).

- **Check yourself**: "hourly failure reasons for support (dashboard), paged on spike doubling" — question, consumer, trigger. Collection without this sentence is hoarding with extra steps.
- **Bad habit to break**: "log everything, we'll figure it out" — petabytes of liability generating zero decisions.

### 3) **Name the cost**

Tokens, index writes, inference latency — data is never free (from [2.1](<../2. AI words/2.1. Model token and prompt.md>), [2.2](<../2. AI words/2.2. Training vs inference and hallucination.md>)).

- **Check yourself**: "feature costs ~400 tokens/call at 2k calls/day ≈ $X/month; evals green at 4.3/5" — priced and measured. Every index ("+5% write overhead") and every model call gets the same two-line accounting.
- **Bad habit to break**: shipping AI features without token budgets — finance discovers them first, and that meeting is never fun.

### 4) **Common confusion**

- "Checklists kill data exploration" — exploration is *asking new questions*, which the checklist accelerates (shape known, store known, cost known) — it kills only blind hoarding.
- "Cost-naming is premature optimization" — optimization is tinkering; pricing is planning. Nobody calls a project budget premature.

### 5) **Mentor note**

Add shape/question/cost to the design-doc template as three required lines. Reviews then check vocabulary instead of excavating intent — and juniors internalize that data work *starts* with words (what shape, what question, what cost) long before it touches stores or models.
