## 1.2. Database, table, query, and index

### 1) **Database stores, table organizes, query asks**

**Definitions** — A *database* is a system for storing and retrieving data durably (Postgres, MongoDB, Redis). A *table* (or *collection*) organizes records into rows with shared shape. A *query* asks a question in the store's language and gets matching records back.

- **What problem it solves**: beginners treat "the database" as a magic box and "slow app" as one symptom. The three nouns split it: is the *store* unhealthy (disk, connections), the *organization* wrong (missing tables, bad schema), or the *question* expensive (unindexed full scan)? Each points at a different owner and fix.
- **Modern guidance** — report database trouble with all three: "query X on table charges (Postgres primary) scans 4M rows — missing index on created_at". Store + shape + question in one line; any DBA (or future you) starts fixing instead of investigating.

```text
# Bad: box-talk (one symptom, no split)
"The database is slow — we need a bigger instance."

# Good: store/shape/question split (fix aims itself)
"Store healthy (CPU 20%, connections fine); question slow:
 SELECT on charges scans 4M rows, no index on created_at.
 Fix: add the index (~minutes), not a bigger box."
```

### 2) **SQL vs NoSQL is a shape choice**

*SQL* (relational: Postgres, MySQL) stores tables with enforced schemas and relations — consistency and joins are the product. *NoSQL* (document, key-value, wide-column: MongoDB, Redis, Cassandra) trades schema rigidity for flexibility and scale-shape — nested documents, blazing key lookups, horizontal growth.

- **History in one paragraph**: relational ruled for decades because business data *is* relational (orders have customers have payments). The 2010s web-scale wave (loose shapes, huge writes, global distribution) birthed NoSQL's Cambrian explosion — then the industry relearned that most apps still want joins, and modern Postgres absorbed half the document use-case. Fashion cycles; the shape question stays.
- **Modern guidance** — choose by access pattern, not hype: relational by default (your data almost certainly relates); document stores for genuinely shape-shifting records; key-value for cache/session speed; specialized engines (search, graph, time-series) when their query shape dominates. "NoSQL for scale we don't have" is the most common regret migration in both directions.

### 3) **Index buys read speed with write cost**

An *index* is a lookup structure (usually a B-tree) that finds rows without scanning — the book's back pages: topic → page numbers. Every index accelerates matching reads and taxes every write (each insert/update maintains each index) plus storage.

- **Why it matters (performance, correctness)**: missing indexes are the #1 cause of "database slow" — a full scan on a million-row table where an index would touch dozens. But index-everything backfires symmetrically: write-heavy tables drown in index maintenance, and unused indexes are pure cost. The vocabulary *is* the trade-off statement.
- **Modern guidance** — index the questions you actually ask (foreign keys, frequent WHERE/ORDER columns — verify with slow-query logs, not guesses), and audit yearly: drop indexes no query uses. Quote both sides when proposing one: "speeds the hourly report 40x, adds ~5% write overhead on charges".

### 4) **Common confusion**

- "NoSQL means no schema" — it means *flexible/enforced-elsewhere* schema; schemaless stores still need application-level shape discipline, or they become swamps with faster writes.
- "Indexes always help" — they help reads they match and hurt all writes; an index nobody's query uses is a tax with no benefit.
- "The ORM removes the need to know this" — ORMs generate queries, and generated queries scan just as happily; "N+1", "missing index", and "full scan" all survive the abstraction — they just hide in prettier code.

### 5) **Mentor note**

Make juniors read one slow-query plan (`EXPLAIN`) before allowing any "database is slow" claim — the plan names scan-vs-index, row counts, and cost in the database's own words. One guided reading session converts "magic box" thinkers into "store/shape/question" thinkers permanently; it is the highest-ROI thirty minutes in backend onboarding.
