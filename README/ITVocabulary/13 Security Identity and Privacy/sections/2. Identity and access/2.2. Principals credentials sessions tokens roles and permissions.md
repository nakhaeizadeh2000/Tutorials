## 2.2. Principals credentials sessions tokens roles and permissions

A browser still displays a staff name, but an API rejects its request. Elsewhere,
a background worker can export a report without any person currently signed in.
To interpret either situation, identify the actor, presented evidence, accepted
identity context and permission for the actual operation.

### 1) **Identify the principal and the authority relevant to this request**

A **principal** is an entity represented in a security decision, such as a user
account, service or device. Ask which principal is acting in this system, rather
than assuming every request comes directly from a human. A service can act under
its own identity or on behalf of another subject; identify that relationship
instead of replacing both with the word “user.”

A **credential** commonly means material or evidence used to establish identity
or access authority. Passwords, keys, certificates and tokens appear in different
credential contexts, with different verification rules. Some standards define
credential more narrowly, so name the actual artifact and protocol. A public
username selects an identity but does not by itself prove control of it. The
previous authentication lesson owns the full claim-versus-evidence distinction.

A **permission** concerns an allowed operation on a resource in context. A **role**
is a named grouping of responsibilities or permissions under a system's model.
Being called `report-reader` does not specify all permissions without the role's
actual policy. A role named `admin` in one application is not automatically an
administrator in the database, operating system or another organization.

Use a concrete policy statement: “Assigned staff may read the roster of their
assigned workshop.” This carries both an operation and resource relationship.
“Staff may read rosters” could accidentally imply every roster. The
[OWASP authorization guide](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)
frames decisions through users, resources and operations. Detailed role-based,
attribute-based and least-privilege designs belong to their later security lesson;
this page establishes the terms needed to read them.

### 2) **Separate session continuity from token representation and validity**

An **authenticated session** lets an application maintain an accepted authentication
context across interactions. A **session identifier** can refer to server-maintained
state; a session secret or proof can bind the client to that context. The exact
mechanism and lifetime are part of the design. The earlier browser-state lesson
owns cookies, page sessions and storage: a cookie can carry a session identifier,
but a cookie, `sessionStorage` and a server's session are not equivalent things.

A **security token** represents information or authority interpreted under a
particular security protocol. An **access token** is used for access to protected
resources. A **bearer token** can be used by a party possessing it without separate
proof of possession of a cryptographic key. This property does not make every
arbitrary presented string valid: the recipient still needs to accept the token
under the applicable rules. [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750.html)
defines the OAuth bearer-token model. Not every security token is a bearer token.

A token can be **opaque** to a client, which treats it as an uninterpreted value,
or carry structured information. **JWT** expands to **JSON Web Token**. It is a
claims format, not a synonym for login, a session or every access token. A **claim**
is an asserted piece of information. An **issuer** makes those assertions; a
**subject** is the entity the relevant claims concern; an **audience** identifies
the intended recipient or recipients under the protocol. A **scope** describes
an access range or capability in its protocol's terms, not an automatic grant to
every resource with a similar name.

[RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html) defines JWT claims and
representations. JWTs can use signatures, message authentication codes or encryption
under their formats; the JWT label alone does not promise encrypted claims or
confidential contents. Reading decoded text is not verification of a token's
origin, cryptographic protection or intended use. The
[JWT best-current-practice document](https://www.rfc-editor.org/rfc/rfc8725.html)
adds validation guidance, including issuer/subject and audience checks. This is
vocabulary orientation, not a complete token-validator implementation or library
configuration. Cryptographic mechanisms and identity protocols have later owners.

**Expiration** ends validity according to a time rule. **Revocation** withdraws
validity or authority before its otherwise permitted end, according to the actual
system's mechanism. A cryptographic signature does not itself consult a changed
permission assignment or guarantee immediate revocation. Interpret the recipient's
validation and policy, not just a timestamp or a readable role claim.

Logout also needs a named boundary. NIST's current
[session-management guidance](https://pages.nist.gov/800-63-4/sp800-63b/session/)
distinguishes an authentication session from access and refresh tokens that can
remain valid after that session ends. It also distinguishes sessions at different
federated participants. Do not infer “all API authority ended everywhere” merely
because one page returned to a signed-out view.

### 3) **Trace a human session and a worker request separately**

Read this **fictional policy and evidence packet**. Names such as `token-a` are
labels, not real secrets or syntactically valid JWT examples. The report service
context is NestJS with the Fastify adapter; no authentication system runs here.

| Artifact or rule | Stated meaning |
|---|---|
| Staff principal `staff-a` | Assigned to workshop W1; role `report-reader` permits roster reads only for assigned workshops |
| Worker principal `export-worker` | Permitted to write generated public catalog files; not permitted to read restricted rosters |
| Browser session S1 | Authenticated context for `staff-a`; the browser application ends S1 on logout |
| Access token `token-a` | Issued for `staff-a`, audience report API, scope roster-read; expires at 10:00 |
| API validation and policy | Token accepted before expiry under the configured checks; workshop assignment is checked for each roster operation; S1 logout does not revoke this token |
| At 09:00 | API accepts `token-a`; W1 roster request allowed, W2 roster request denied |
| At 09:05 | Browser logs out of S1 and shows signed-out state |
| At 09:06 | A recorded API request with `token-a` still passes token validation and is allowed for W1 |
| Worker observation | A request under `export-worker` can write a public catalog file without using S1 |

The 09:00 outcomes apply the resource relationship, not just the role name. Token
validation succeeds for both requests, but W2 access is denied by the separate
workshop rule. This is useful evidence of distinct token acceptance and resource
permission decisions in the packet, not a universal claim that every API checks
a live assignment on every request.

The 09:06 result follows the supplied lifetime and logout policy. It does not prove
that logout failed to end S1, or that this design satisfies the product's intended
logout requirement. If the requirement is to end all that user's API access on
logout, the recorded behavior would expose a gap in this design. First state
which session, token and recipient the requirement covers.

The worker acts under a different principal with different authority. It does
not inherit `staff-a`'s roster permissions merely because it supports the same
application. Likewise, a successful public-file write does not establish authority
to read a private roster or proof that a human is present.

Now change the policy: logout revokes `token-a`, and the report API receives and
enforces that revocation before the 09:06 request. The changed request should be
rejected under that stated contract. Documenting revocation alone is not evidence
of that enforcement. The original observations remain evidence about the original
policy; they do not verify the changed mechanism.

Practice: remove the API's stated workshop rule. Can you still conclude that a
roster-read scope limits access to W1? No. You need the actual resource authorization
contract and result. A token's high-level capability label does not silently add
an assignment rule absent from the stated policy.

### 4) **Common confusion**

A signed token is not automatically encrypted, a decoded claim is not automatically
trusted, and a role string is not the complete access policy. Do not use a browser's
visible name as a substitute for the service's accepted principal and authority.

An authentication session, an access token and a separate service's session can
have different lifetimes. “Logged out” must identify which context ended and what
other authority was invalidated. This distinction explains an investigation; it
does not prescribe one storage, token or revocation design for every application.

### 5) **Performance note**

A token lookup, local cryptographic validation, policy query and revocation check
perform different work. Their relative costs depend on implementation, cache state,
network conditions and workload. “Stateless” does not mean no policy data or zero
revocation cost, and a JWT is not a measured speed improvement by name. No token,
session or permission benchmark was executed here.

### 6) **Mentor note**

Ask the learner to draw a plain list of principal, credential/token, session,
recipient and operation for the 09:06 request. Then ask why the worker's successful
write says nothing about a staff roster read. A strong answer traces authority
through the stated rules, preserves the logout requirement question and asks for
actual enforcement evidence before calling a policy change complete.
