## 8.1. Read a security finding and identity diagram

A review says “SSO, passkeys, HTTPS and signed tokens make the roster secure.”
A finding reports that an instructor received another workshop's roster. The
mechanisms and the finding can both be real: strong authentication does not
supply a missing resource-permission check. Read each claim at its own boundary.

This synthesis uses concepts already taught in this domain. The following system,
records and findings are entirely constructed. No application, credential, person
or production incident was tested. The backend context remains NestJS with the
Fastify adapter.

### 1) **Annotate roles artifacts and protection boundaries before judging the claim**

Read this **informal relationship sketch**:

```text
Corporate identity provider -- OIDC identity relationship --> App A
Ada's browser -- TLS; access token for report API --> Report API
Catalog worker -- workload credential --> Report API
Report API -- roster retrieval --> Roster store
Catalog worker -- catalog-file writes --> Export store
```

The arrows describe intended relationships, not a complete wire-protocol sequence,
verified deployment or complete access-control inventory. They do not imply that
an OIDC ID token is used as the report API's access token. App A is the OIDC
relying party; the Report API is a protected-resource service. The browser and
worker can represent different principals even though they call the same service.
The token issuer and full token-acquisition path are outside this sketch.

Start by marking which party accepts each artifact, which principal it represents
and which resource operation is intended. A workload credential is not evidence
that Ada is present. TLS on the browser/API arrow describes that channel; it
says nothing here about the store connections, files at rest or who may read an
export. An intended write arrow also does not prove that a particular worker
created every file found in the destination.

C4's [diagram-review checklist](https://c4model.com/diagrams/checklist) asks for
scope, a legend and meaningful relationship directions. Apply those questions
without calling this informal sketch a verified C4 model. The
[Threat Modeling Manifesto](https://www.threatmodelingmanifesto.org/) similarly
uses representations to identify concerns and evaluate responses. A diagram is
an aid to asking questions, not a certificate that the answers are satisfactory.

### 2) **Connect the finding to policy and observations without inventing impact**

Use this **fictional requirement and evidence packet**:

| Record | Supplied fact |
|---|---|
| Roster policy | Instructors may read only their currently assigned workshop's private roster |
| Worker policy | Catalog worker is a separate principal; its approved job is public-catalog writes, with no private-roster authority |
| Login evidence | App A accepted the corporate OIDC identity for Ada; the recorded passkey event included accepted cryptographic and required trusted user-verification evidence |
| API identity evidence | The API's configured checks accepted the access token for the report API and mapped it to Ada; no token forgery is reported |
| Trusted assignment | Ada is assigned W1 and has no assignment or exception for W2 |
| Finding F-17 | An authorized synthetic review records the API returning W2's private roster to Ada's request |
| Privacy policy and file evidence | Contact records must be disposed of 30 days after workshop end, with no exception here; an identifiable contact CSV remains in the shared export folder at day 31 |
| Assessment scope | The supplied assessment examined App A's login control; it did not examine the Report API's roster authorization or export-file handling |

F-17 supports a resource-authorization mismatch under the supplied policy. It
does not show that Ada's identity was forged or that the passkey verification
failed. Authentication accepted a principal; the service then permitted a
forbidden object-level result. The [authorization owner](<../5. Access control and defense/5.1. Least privilege RBAC ABAC defense in depth and zero trust.md>)
explains why the subject/action/resource relationship remains necessary.

The private roster's confidentiality is the relevant property in that finding.
One returned synthetic roster does not establish the total scope of production
exposure, a malicious actor, data modification, outage or a jurisdiction-specific
breach classification. Preserve those questions instead of inventing impact from
the security label. The vulnerability/incident owner supplies that distinction.

The passkey and token observations remain positive evidence for their stated
checks. They do not erase F-17, and F-17 does not automatically refute those
observations. Nor does a signed token prove that its holder is assigned to W2.
Treat the accepted identity and the failed permission boundary separately.

The day-31 CSV is a separate retention problem under the packet's policy. Its
presence does not show which process created it, whether an outsider downloaded
it or whether the roster response produced that export. An arrow in the sketch
cannot supply the missing causal record. Access restrictions or encryption also
would not establish that retaining this copy satisfies its disposal rule.

Finally, the login assessment does not cover the API or export questions. Its
scope remains useful and limited. [Assessment scope and assurance](<../7. Privacy and governance language/7.2. Policies controls audits compliance and assurance.md>)
explains why unexamined controls cannot inherit a passing result from a neighbor.

### 3) **Write an evidence-based handoff and revise it when facts change**

A technical handoff could say:

> The supplied login and API records accept Ada's identity, but F-17 records the
> Report API returning W2's private roster although Ada is assigned only W1.
> Investigate resource-specific authorization and its enforcement on this path.
> Separately, the identifiable day-31 CSV conflicts with the stated retention
> rule; identify its lifecycle and disposal evidence. The login-control assessment
> does not cover either boundary. Production extent, actor intent and any link
> between the response and CSV remain unestablished.

For a product stakeholder, preserve the consequences with less mechanism detail:

> The review found a roster-permission failure and a separate overdue contact-data
> copy under our stated rules. Successful sign-in checks do not resolve either
> issue. We need owners, corrective actions and evidence for the affected API and
> file lifecycle. The packet does not establish the extent of production impact.

Propose follow-up evidence that distinguishes the issues: the permission decision
for this principal/resource, a correction verified against allowed and forbidden
workshops, and the CSV's contents, ownership and disposal history. These are
proposals. This lesson has not run those checks or confirmed remediation.

Now remove the trusted-assignment row and the policy's W1/W2 restriction, retaining
only the returned W2 roster. You can still report what was returned, but you cannot
retain the same established policy-violation conclusion. Obtain the actual
permission rule and assignment. The mere fact that a workshop is called W2 does
not prove it was forbidden to Ada.

Practice: instead retain the original policy and add an authorized post-change
check showing Ada can read W1 and is denied W2. What changes? The new evidence
supports the correction for those checked operations at that time. The earlier
failure remains historical evidence. The CSV, untested alternate routes, production
extent and assessment scope do not become resolved by that one access check.

Interview reasoning: “Should we replace SSO to fix this?” A sound answer first
asks which mechanism failed. The supplied case points to resource authorization;
replacing sign-in does not itself add that rule. This does not prove the wider
SSO design needs no review, but the packet supplies no causal basis for treating
it as the fix for F-17.

### 4) **Common confusion**

Identity providers, relying parties, APIs and workers are roles, not automatically
one shared identity or session. An ID token, access token and workload credential
also have different purposes. A diagram label cannot replace evidence of their
validation, recipients or permissions.

A valid protection at one boundary is compatible with a defect at another.
Avoid both “everything is secure because login passed” and “every mechanism is
broken because one roster was returned.” State the specific positive evidence,
negative result and unresolved questions.

### 5) **Performance note**

The sketch supplies no request rate, latency distribution, policy-query cost or
key-service measurement. A proposed permission correction needs its own behavior
and performance evidence in the real implementation. Removing a required resource
check is not a behavior-preserving speed optimization.

No login, passkey, token, roster request, file operation, production assessment
or benchmark ran here. The diagram and timestamps are static reasoning inputs.

### 6) **Mentor note**

Ask the learner to highlight every handoff clause and point to its supporting
packet row. Then remove assignment evidence and require a weaker conclusion.
A strong answer retains the return observation while withdrawing the established
permission violation. In the correction variation, it updates only the tested
access boundary and leaves the unrelated CSV issue open.
