## 6.2. CVE CWE CVSS advisories patching and supply chain failures

A scanner finds a dependency, an advisory gives it a severe rating, and a pull
request updates its version. These are useful records, but they do not establish
the same fact. A vulnerability identifier is not a severity score, a score is not
proof of this application's exposure, and a merged update is not a deployed fix.

Read the earlier vulnerability, dependency-record and artifact-evidence lessons
first. This lesson interprets a fictional advisory and application inventory;
no current vulnerability, package update or incident is investigated here.

### 1) **Distinguish identifiers weakness types and severity assessments**

**CVE** expands to **Common Vulnerabilities and Exposures**. A **CVE ID** provides
a common identifier for a specific vulnerability record so different reports can
refer to the same issue. The record's description and references matter; the
identifier alone does not specify which of your systems is affected. It also does
not encode severity, proof of exploitation or a remediation deadline.

**CWE**, **Common Weakness Enumeration**, describes weakness types in software
and hardware. One underlying weakness type can lead to vulnerabilities in many
products. The [CWE project's explanation](https://cwe.mitre.org/about/faq.html)
distinguishes that type from a particular vulnerability identified through CVE.
A weakness such as missing authorization is a class of problem; an advisory about
one affected product/version is a more specific record. Neither vocabulary is a
complete inventory of every vulnerability that could exist in an application.

**CVSS**, **Common Vulnerability Scoring System**, communicates vulnerability
characteristics and severity. A numerical score needs its **CVSS version**, metric
values and assessment context. The **vector string** records the selected metric
values in a defined textual form. Keep that vector and its source with the score
so another reader can understand the assessment rather than guessing its inputs.

The current [CVSS 4.0 specification](https://www.first.org/cvss/v4.0/specification-document)
organizes metrics into these groups:

| Group | What it contributes |
|---|---|
| Base | Intrinsic vulnerability characteristics assessed independently of a particular consumer environment |
| Threat | Relevant characteristics that can change over time, including exploitation maturity |
| Environmental | Characteristics and requirements specific to the consumer's environment |
| Supplemental | Additional context that does not change the standard numerical score |

The score range is 0.0–10.0. A high Base score does not mean a corresponding
percentage chance that your service will be compromised. FIRST's
[user guide](https://www.first.org/cvss/v4.0/user-guide.html#CVSS-Base-Score-CVSS-B-Measures-Severity-not-Risk)
explicitly distinguishes Base severity from risk. Threat and environmental
assessment add context, but the resulting number is still not a complete account
of the organization's assets, obligations and priorities. Record the assessment
date, source, version and metric groups; do not mix a 3.1 Base score and a 4.0
contextual assessment as though their labels and inputs were identical.

### 2) **Read an advisory through the actual software supply chain**

A **security advisory** communicates a security issue and relevant details, often
including affected products and versions, triggering conditions, mitigations,
fixed releases and references. It can be updated as evidence changes. Read the
publisher's actual affected range and prerequisites rather than deciding exposure
from a package name or a screenshot of a score.

**Exposure** asks whether the relevant vulnerable component and conditions occur
in the system being assessed. Presence, execution, reachable input and applicable
configuration are separate questions. A scanner's version match can be a useful
lead or a confirmed component match without proving that an exploit occurred.
Conversely, missing reachability evidence is not proof that the component is safe.
State what the current inspection actually establishes.

A **software supply chain** includes the dependencies, tools, build processes,
distribution and updates through which software reaches a consumer. A failure
can involve vulnerable dependencies, malicious package contents, compromised
build tooling or an inappropriate distribution source. An attack is one possible
cause; the broader failure category is not limited to deliberate attacks.
[OWASP Top 10:2025's supply-chain category](https://top10.owasp.org/2025/A03_2025-Software_Supply_Chain_Failures/)
explicitly extends beyond merely using known vulnerable components.

A component inventory or **SBOM** helps locate what is in a specified artifact.
**Provenance** helps describe how that artifact was produced. Neither proves
that all code is harmless, every component is listed or every relevant advisory
is known. The earlier release-evidence lesson owns those distinctions. Use the
inventory to connect this advisory to the actual installed or running subject;
do not silently substitute an SBOM from a different build.

**Patching** applies a corrective software change, update or upgrade. A
**mitigation** reduces a relevant exposure or effect without necessarily replacing
the underlying vulnerable code. Disabling an affected feature can be a proposed
mitigation, but its effectiveness needs evidence that the feature is disabled
and that alternate paths do not preserve the stated problem.

NIST's [patch-management guidance](https://csrc.nist.gov/pubs/sp/800/40/r4/final)
includes identifying, prioritizing, acquiring, installing and verifying changes.
That sequence explains why “the fix exists,” “the dependency file changed” and
“the running service uses the corrected artifact” are separate milestones. A
security fix can also affect compatibility or operations. Evaluate and verify
the relevant change rather than assuming either that every upgrade is safe or
that operational caution justifies leaving an issue without ownership.

### 3) **Trace a fictional advisory from inventory to deployment**

This **constructed packet** concerns an invented library called `WorkshopFormat`.
Names `ADV-DEMO` and `ISSUE-DEMO` are explanatory labels, not real advisory IDs
or valid CVE identifiers. The backend context is NestJS with the Fastify adapter;
the library and application below are not installed or executed.

| Record | Supplied fact |
|---|---|
| Advisory ADV-DEMO | WorkshopFormat 1.8.0 is affected when its optional HTML preview receives untrusted comments; 1.8.1 contains the described correction |
| Assessment | The publisher supplies a CVSS 4.0 Base assessment; no assessment of this application's environment is supplied |
| Running artifact A12 | Its inspected inventory contains WorkshopFormat 1.8.0 |
| Feature evidence | No reliable record of whether preview is enabled or which inputs reach it |
| Dependency update | A merged change selects 1.8.1; a new artifact A13 was produced |
| Deployment observation | The inspected production instance is still running A12 |
| Exploitation evidence | None supplied for this application |

A12 contains the stated affected version. The packet does not establish whether
the advisory's preview/input conditions are met, nor whether exploitation occurred.
Record that gap and investigate it. Do not downgrade the unknown conditions into
“not affected” or upgrade the component match into “already compromised.”

The update changes the selected version and produces A13. Production's observed
A12 identity shows that this instance has not adopted that new artifact. A merged
pull request therefore does not establish deployment of the correction. Request
A13's actual component evidence, relevant behavior checks and deployment evidence
for the intended instances. These are follow-up needs, not tests already performed.

Now add one fact: a trusted configuration and request-path inspection confirms
that A12's preview is enabled and accepts untrusted attendee comments through
the affected path. The known exposure is stronger because the triggering
conditions are established. This still supplies no observed exploit or complete
incident history. The Base assessment did not change merely because the consumer
learned more about its own environment.

Practice: remove the running-artifact row, leaving only the source lockfile and
A13's build record. Can you conclude that production runs either version? No.
The source selection and produced artifact need a connection to the actual
production process. Recover that identity before calling the patch installed.
A planned release or an available image is not that missing observation.

A useful handoff distinguishes the issue identifier, affected-component match,
triggering conditions, severity source, known effects, proposed response, owner
and verification status. Priority then considers the actual risk context and
response constraints. This vocabulary lesson prescribes no universal patch
interval, risk score or authority to accept an unresolved issue.

### 4) **Common confusion**

CVE identifies a vulnerability, CWE classifies a weakness type, and CVSS describes
an assessment. None is a count of production compromises. “No CVEs found” means
only that a particular check found none within its inputs, method and knowledge;
it does not prove an absence of unknown flaws, malicious code or configuration
problems.

An updated manifest, corrected artifact and corrected running system also have
different subjects. A workaround can reduce exposure while the old component
remains present. State that mitigation and its limits instead of relabeling the
component itself as patched.

### 5) **Performance note**

Scanning inventories, rebuilding artifacts, testing compatibility and deploying
updates consume resources. A patch can change runtime behavior or cost, and a
mitigation may disable useful functionality. None of those effects can be inferred
from CVE digits, a severity number or a patch-version label. No package, scan,
compatibility check, deployment or performance measurement ran for this packet.

### 6) **Mentor note**

Give the learner the packet without the conclusions. Ask which
one supports component presence, triggering conditions and actual deployment.
Then remove the running identity and require them to narrow the claim. A strong
answer keeps missing evidence separate from both an observed compromise and
proof of safety, and names the next fact needed to verify the chosen response.
