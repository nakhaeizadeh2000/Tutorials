## 6.1. Injection XSS CSRF SSRF and broken access control

A report says “input caused a security failure.” That could mean data became
instructions, a browser made an unwanted authenticated request, a server fetched
an inappropriate destination, or an account received a forbidden record. These
are different boundaries. Naming the boundary helps the next reviewer ask for
the right evidence and avoid proposing an unrelated fix.

This is vocabulary education using safe, constructed findings. No attack payload,
exploit command, target service or attack execution is provided. Read the API,
browser and access-control vocabulary first.

### 1) **Distinguish data becoming instructions from an unwanted browser action**

**Injection** occurs when untrusted input is interpreted as instructions or
structure in a context where it should remain data. **SQL injection** concerns
the database query context; command injection concerns a command interpreter.
A suspicious-looking string is not proof that the interpreter executed it.
Trace the value to its actual use and distinguish a possible weakness from a
confirmed behavior.

For SQL parameter values, a properly used parameterized interface separates data
from query structure. This addresses a different problem from checking that a
booking's seat count is positive. **Input validation** checks an application's
allowed values; a value can satisfy a length rule while still being handled
unsafely in a query. The [OWASP injection guide](https://cheatsheetseries.owasp.org/cheatsheets/Injection_Prevention_Cheat_Sheet.html#defense-option-1-prepared-statements-with-parameterized-queries)
explains the separation. Dynamic identifiers and query construction have other
requirements; an ORM or stored procedure name alone does not verify correct use.
The earlier database-access lesson owns parameter terminology and access layers.

**Cross-site scripting**, or **XSS**, concerns untrusted content executing in a
browser's application context. Despite its historical name, two different sites
need not be involved in every XSS case. A comment intended as text could become
active content when an application inserts it into an executable context.
Possible effects depend on the page's authority and protections; “XSS” alone
does not prove every cookie was readable or every account compromised.

**Output encoding** represents data appropriately for its destination context so
it is treated as data. HTML text, an attribute and a URL component are different
contexts; one generic “escape” operation is not automatically correct for all.
When intentionally accepting rich HTML, **HTML sanitization** removes disallowed
constructs according to a suitable policy and implementation. Encoding all markup
as text and allowing selected HTML serve different product requirements.
The [OWASP XSS guide](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)
explains these choices and dangerous contexts where inserting untrusted content
should be avoided. Base64 is not a substitute: after decoding, the original
untrusted content still needs handling appropriate to where it is used.

**Cross-site request forgery**, or **CSRF**, concerns inducing a victim's browser
to send an unwanted request using authority the target application accepts.
A common setting involves session cookies automatically accompanying an eligible
request. The attacker need not know the cookie or read the response for a
state-changing request to cause harm. Which cookies actually accompany a request
still depends on browser and cookie rules; they are not sent to every destination.

The [OWASP CSRF guide](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
connects protection to the client and authentication mechanism. Relevant defenses
can include validated anti-CSRF tokens, origin checks or request metadata, with
appropriate framework integration. A role check can establish that the victim's
account may perform the operation while failing to establish that this request
represents the victim's intended action. “The user was logged in” does not resolve
that distinction. Neither does a CORS error automatically prevent the request;
the earlier CORS lesson owns the send-versus-response-read boundary.

### 2) **Locate the server request and the missing resource permission**

**Server-side request forgery**, or **SSRF**, abuses an application's ability to
make requests on behalf of supplied input. For example, a preview service may
fetch a user-selected destination using the server's network position and
credentials. If that input can redirect the service toward an unintended internal
resource, the server's request boundary is the concern. It is different from
making the user's browser submit an action with its session cookie.

The [OWASP SSRF guide](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html#context)
uses server-fetch and callback scenarios and distinguishes applications with a
fixed set of permitted destinations from broader fetchers. Parsing a URL or
verifying its syntax does not establish that the resolved destination, redirect
or actual connection is permitted. Destination controls and network egress
restrictions address different parts of that path. This page does not supply a
complete URL-filtering algorithm or a list of targets to probe.

**Broken access control** occurs when the enforced permissions fail to restrict
an operation as the policy requires. An authenticated instructor reading another
instructor's restricted roster is an example if the policy permits only assigned
workshops. The problem can exist with entirely ordinary input and no injection.
A hard-to-guess record identifier is not the missing authorization rule.

Reports may call an object-reference variant **IDOR**, insecure direct object
reference, or discuss **BOLA**, broken object level authorization, in API contexts.
Read the described object and operation; the label alone does not establish the
extent of exposure. [OWASP's authorization guide](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)
requires resource-specific checks. The preceding access-control lesson owns the
policy model and least-privilege reasoning; this section identifies the failure
category rather than repeating its request matrix.

These categories can overlap. XSS is a kind of injection into a browser context,
and a server-request flaw can cross an authorization boundary too. Classify the
mechanism actually described without assuming that a report must fit exactly
one exclusive box or that one fix addresses every related weakness.

### 3) **Read five findings at their supplied evidence levels**

The following are **independent fictional findings** from an authorized review
of synthetic workshop data. They are not records of tests executed for this
lesson. Each row supplies a mechanism and outcome for interpretation; no attack
syntax is needed to understand the distinction.

| Finding | Supplied observation | Main boundary to investigate |
|---|---|---|
| A | A search value is joined into SQL structure; review evidence shows the database interprets part of that value as query syntax | SQL injection: input crossed from data into query structure |
| B | An attendee comment intended as text is inserted as active page content; supplied browser evidence records its execution in the application context | XSS: untrusted content became browser-executed content |
| C | An unrelated site induces a browser request with an eligible session cookie; the target changes the user's email without its intended request-origin defense | CSRF: authenticated browser authority accompanied an unwanted request |
| D | A preview URL causes the backend fetcher to retrieve a restricted internal service outside its permitted destinations | SSRF: the server was induced to make an unintended request |
| E | An instructor assigned only W1 receives W2's restricted roster; the stated policy prohibits this | Broken access control: the operation violated the subject/resource rule |

A's parameterization question does not answer C's request-intent problem. C can
succeed without injecting script into the target page. D uses the server's request
capability, while C uses the browser's accepted authority. E requires no special
query syntax or executable comment: the forbidden resource result is the failure.

Now remove A's interpretation evidence. Retain only “the search input contained
punctuation and the service returned an error.” That is insufficient to establish
SQL injection or its cause. Request evidence about construction and interpretation;
keep the error observation without promoting it to a confirmed exploit.

Practice: add to E that the response failed the browser's CORS sharing check,
but the supplied server record still confirms the forbidden W2 roster response
to that caller. Did the authorization defect disappear? No. The response-read
restriction does not supply the missing resource check. Whether the browser page
could read those bytes is a separate question from what the server permitted and
returned. Do not generalize this row into a claim about every non-browser or
network observer; retain the actual caller and evidence.

A useful handoff names the subject, input source, interpreter or request maker,
resource, expected rule, observed effect and remaining uncertainty. It also states
the version and environment when they matter. A category label helps organize
that investigation; it does not provide its missing facts or remediation proof.

### 4) **Common confusion**

XSS and CSRF are not interchangeable abbreviations. One describes injected
browser execution; the other can involve a normal request made with the victim's
authority. SSRF changes which participant makes the induced request again.
Authentication alone does not prevent any of these categories in every design.

“Sanitized,” “encoded” and “validated” need a context and rule. A Base64 decoder,
an HTML sanitizer and a positive-integer check perform different jobs. Hiding an
object's ID, using HTTPS or seeing a browser CORS error likewise does not establish
authorization for that object.

### 5) **Performance note**

Input checks, context-specific output handling, permission evaluation and outbound
request restrictions add different work. Request limits can also constrain resource
consumption from fetchers. Their costs depend on actual implementation and inputs;
these vulnerability names supply no speed estimate or license to skip a required
check as an optimization.

No exploit, browser execution, database request, outbound connection or performance
experiment was performed here. The supplied findings demonstrate how to reason
from a fictional report, not how fast a mitigation runs or whether it is complete.

### 6) **Mentor note**

Ask the learner to underline who interprets or sends something in each finding.
Then replace A with the weaker error-only evidence and require a narrower claim.
A strong explanation separates a clue, a confirmed mechanism and its impact,
and proposes a check that addresses the identified boundary. It does not claim
that one generic input filter, login system or network appliance solves all five.
