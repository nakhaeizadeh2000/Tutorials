## 4.1. Encoding hashing encryption and digital signatures

A report is Base64-encoded, a download has a hash, and a message is signed. These
operations answer different questions. Changing how bytes look does not establish
who supplied them, and verifying their source does not necessarily hide their
contents. Start with the property the application needs.

Read the earlier byte/encoding and checksum explanations first. This lesson adds
the security purpose and key relationships; it does not repeat Unicode mechanics
or the release-provenance workflow.

### 1) **Separate representation and byte comparison from confidentiality**

**Encoding** represents information under a defined scheme. The earlier text
lesson explains character encodings such as UTF-8. **Base64** instead represents
arbitrary bytes using a restricted text alphabet, useful when a surrounding format
expects text. A decoder needs the appropriate scheme, not a secret decryption key.
Base64 and Base64url have different alphabet rules; the surrounding protocol must
specify its variant and padding requirements.

A Base64 value can look unfamiliar while exposing all the original bytes to an
ordinary decoder. Encoding a password before putting it in a public report still
reveals the password. [RFC 4648's security discussion](https://www.rfc-editor.org/rfc/rfc4648.html#section-12)
explicitly warns about this confidentiality mistake. Neither the absence of
readable words nor successful decoding establishes encryption or authenticity.

A **cryptographic hash function** computes a digest from input bytes. SHA-256,
for example, produces a 256-bit digest. **Hexadecimal** is one way to display those
digest bytes; displaying a digest in Base64 would change its representation, not
turn hashing into encryption. An ordinary unkeyed hash needs no secret key.

For a suitable cryptographic hash, finding an input for a given digest or finding
colliding inputs should be computationally infeasible under the intended security
conditions. A **collision** means different inputs produce the same digest.
Finite-sized digests cannot give every possible input its own unique output.
“Hard to find a collision” is therefore different from “collisions cannot exist.”

Hashing has no decryption operation that restores the original report. Nevertheless,
a small, predictable input can be guessed and its digest compared. Hashing a field
containing only `yes` or `no` does not make its value confidential. Password storage
needs an appropriate salted password-hashing scheme and cost settings; this lesson's
plain SHA-256 comparison is not a password-storage design. The
[Python hash reference's key-derivation discussion](https://docs.python.org/3.15/library/hashlib.html#key-derivation)
explains that different purpose. Algorithm choice and configuration require their
own assessment; a function being available in a library is not a security endorsement.

### 2) **Identify what a key adds to protection and verification**

**Encryption** transforms **plaintext**, the input to be protected, into
**ciphertext** under a cryptographic scheme. **Decryption** recovers plaintext
using the required key material and parameters. Plaintext can be a binary file;
it need not be human-readable text. Encryption's confidentiality goal concerns
who can recover the information under the scheme's assumptions.

Symmetric encryption uses a shared secret key. Public-key encryption uses a
public/private key relationship, with private decryption material kept secret.
The next lesson develops those roles and key management. Neither “encrypted” nor
“uses a public key” establishes correct implementation, key protection or
permission to access the decrypted report.

Confidentiality and detection of unauthorized changes need separate attention.
**Authenticated encryption** combines encryption with an integrity/authenticity
check under its key and usage rules. Do not infer that every encryption mode
provides this property. OWASP's [storage guide](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html#cipher-modes)
distinguishes these modes and their requirements. Use established maintained
implementations; inventing a transformation or combining primitives casually can
leave the intended property absent. This vocabulary page provides no encryption
construction or production parameter recipe.

A **message authentication code**, or **MAC**, is a keyed check of a message.
**HMAC** is a standard construction using a cryptographic hash and a shared secret
key. A verifier computes and compares the expected tag. Someone who knows the
shared key can also generate tags, so a valid MAC does not distinguish between
two parties who both possess that key. It does not hide the message or by itself
establish freshness. Reusing an unchanged authenticated message can still require
application-level replay checks.

A **digital signature** uses a private signing key and a corresponding public
verification key. Verification checks the signature against the signed data;
it does not require giving every verifier the private signing key. For a concrete
scheme, [RFC 8032's signing and verification procedures](https://www.rfc-editor.org/rfc/rfc8032.html#section-5.1.6)
use those distinct inputs. Signing is not a universal synonym for “encrypting a
hash with the private key.” Different schemes have their own defined operations.

A signature supports integrity and origin evidence under the relevant algorithm,
key and trust assumptions. [NIST's Digital Signature Standard](https://csrc.nist.gov/pubs/fips/186-5/final)
describes that purpose. A public verification key still needs a trustworthy
association with the expected signer. Validating a signature from an unexpected
key does not establish the intended publisher. Signing a public notice also does
not make the notice secret or its assertions true. The release-evidence lesson
owns the full artifact-versus-statement-versus-acceptance comparison.

| Operation | Key relationship | Main question addressed | What the name alone does not establish |
|---|---|---|---|
| Base64 encoding | No secret key | How are bytes represented as text? | Confidentiality or trusted origin |
| Unkeyed cryptographic hashing | No secret key | What digest corresponds to these bytes? | An authenticated sender or recovery of the input |
| Encryption | Required encryption/decryption key material | Who can recover the protected plaintext? | Every integrity, permission or key-protection property |
| HMAC | Shared secret for generation and verification | Does this tag match this message under this key? | Which shared-key holder generated it or whether it is new |
| Digital signature | Private signing key; public verification key | Does this signature verify for this data and key? | Secrecy, trusted identity from an unknown key, or truth of the signed claim |

### 3) **Observe encoding a value and checking a changed message**

This complete local experiment uses only Python's standard library. It was tested
on **CPython 3.14.4, Linux x86_64**, a pinned environment; current Python 3.15
[Base64](https://docs.python.org/3.15/library/base64.html) and
[HMAC](https://docs.python.org/3.15/library/hmac.html) references document the relevant
operations. Save it as `protection_roles.py` and run `python3 protection_roles.py`.
No service, account or downloaded data is involved.

The `b` prefix creates bytes. `digest()` returns digest bytes; `hexdigest()` returns
a hexadecimal display. The key below is deliberately public demonstration data.
It provides no protection against a reader of this page and must not be adopted
as an application secret.

```python
import base64
import hashlib
import hmac

message = b"roster=2"
changed = b"roster=3"
encoded = base64.b64encode(message)
print("Encoded:", encoded.decode("ascii"))
print("Recovered:", base64.b64decode(encoded).decode("ascii"))
print("Digest bytes and hex characters:", len(hashlib.sha256(message).digest()),
      len(hashlib.sha256(message).hexdigest()))
print("Changed bytes match digest:",
      hashlib.sha256(changed).digest() == hashlib.sha256(message).digest())

key = b"public-demonstration-key-not-a-secret"
tag = hmac.digest(key, message, "sha256")
print("Original message matches tag:",
      hmac.compare_digest(tag, hmac.digest(key, message, "sha256")))
print("Changed message matches original tag:",
      hmac.compare_digest(tag, hmac.digest(key, changed, "sha256")))
```

Observed output:

```text
Encoded: cm9zdGVyPTI=
Recovered: roster=2
Digest bytes and hex characters: 32 64
Changed bytes match digest: False
Original message matches tag: True
Changed message matches original tag: False
```

The decoder recovers the report without a key. The digest has 32 bytes even though
its hexadecimal display has 64 characters. Both comparisons notice this selected
message change. The MAC comparison also depends on its key; the ordinary hash
comparison does not. `compare_digest` avoids content-based short-circuit comparison
for tags, as the HMAC reference recommends; this is not a measurement or promise
that every surrounding operation is immune to timing leaks.

Practice: a party can replace the report and its untrusted ordinary hash, but
cannot obtain the secret key in a separate, correctly implemented HMAC arrangement.
Why does replacing the hash not authenticate the new report? The party can simply
hash the replacement. Generating an accepted MAC for changed contents requires
the protected key under the arrangement's assumptions. Now remove the secret-key
condition and use the public key string from this page. Anyone reading it can
compute a matching tag. The mechanism's name did not repair key disclosure.

That practice is a constructed reasoning exercise. The local run demonstrates
selected encoding, digest and MAC behavior; it does not demonstrate secure key
distribution, cryptographic security, encryption or digital-signature verification.

### 4) **Common confusion**

A hash table's hashing role and a cryptographic hash's security properties are
different questions. Likewise, a CRC can help detect accidental corruption without
providing the adversarial properties expected of a cryptographic mechanism.
A file and an accompanying replaceable checksum do not become trusted together.

“Decrypt the hash” usually hides the wrong model. Guessing an input, decoding a
hexadecimal display and decrypting ciphertext are different operations. A signed
or MAC-protected message can remain readable, and a repeated valid message may
still be inappropriate for a later action.

### 5) **Performance note**

Encoding changes size as well as consuming computation. Standard padded Base64
uses four output characters for each group of up to three input bytes; this
8-byte example becomes 12 ASCII characters. Hashing and MAC generation process
the input, while signature and encryption costs depend on scheme, parameters,
message handling and implementation. The experiment measures none of their speeds.

Password-hashing cost is intentionally tunable to make guessing more expensive.
Treating maximum verification speed as its only goal would undermine that purpose.
Choosing actual settings requires the security and capacity context; this page
supplies no universal latency or work-factor target.

### 6) **Mentor note**

Ask the learner to identify who can decode, decrypt, generate a MAC or verify a
signature in a stated arrangement. Then give them a new public key from the same
untrusted message and ask whether verification establishes the intended publisher.
A sound answer separates mathematical verification from trusted key association.
Finally, disclose a formerly secret MAC key and require them to revise the origin
claim without pretending that changing Base64 alphabets restores secrecy.
