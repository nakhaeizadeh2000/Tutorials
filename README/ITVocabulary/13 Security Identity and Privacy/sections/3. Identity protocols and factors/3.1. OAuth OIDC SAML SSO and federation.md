## 3.1. OAuth OIDC SAML SSO and federation

“Use SSO with OAuth” combines an experience, an authorization framework and an
unstated identity protocol. It may describe a reasonable design, but it does not
yet identify what each participant trusts or which token each recipient accepts.
Start with the purpose of the exchange, then name its roles and artifacts.

### 1) **Distinguish delegated access from an authentication layer**

**OAuth 2.0** is an authorization framework. It lets a client obtain limited access
to a protected resource under the relevant authorization arrangement. For example,
a scheduling application can obtain permission to read a calendar without asking
the user to give that application their calendar-service password. Some OAuth
arrangements concern a client acting on its own behalf; not every access token
represents a currently present human.

In the delegated calendar example, the **resource owner** authorizes access,
the **client** is the scheduling application, the **authorization server** issues
the access token, and the **resource server** is the protected calendar API. These
are roles: one deployment may combine some of them. The token and permission
owner from the preceding lesson explains why valid access still needs a resource
and operation scope.

OAuth alone does not define a general sign-in identity assertion to the client.
**OpenID Connect**, abbreviated **OIDC**, adds an identity layer on OAuth 2.0.
An **OpenID Provider**, or **OP**, authenticates the end user and supplies identity
claims under the protocol; the application relying on that result is a **relying
party**, or **RP**, and an OAuth client in that exchange.

An **ID token** carries claims about the user's authentication and potentially
other identity information for that client. An **access token** serves protected-
resource access. They are different artifacts with different intended recipients
and validation rules. A calendar API accepting an access token does not establish
that the application correctly validated an ID token for its own login. An ID
token for the scheduling client is not automatically a calendar access credential.

The [OIDC Core 1.0 specification incorporating errata set 2](https://openid.net/specs/openid-connect-core-1_0.html)
(Final, December 15, 2023) defines this identity layer and JWT-based ID token.
Aaron Parecki's original [OAuth 2.0 Simplified explanation](https://www.oauth.com/oauth2-servers/openid-connect/)
compares the delegation and identity questions. Interpret that distinction as the
protocol's contract; it does not mean no deployment can ever obtain identity
information through an additional, explicitly defined service.

Current OAuth security guidance includes
[RFC 9700](https://datatracker.ietf.org/doc/html/rfc9700), published January 2025.
In authorization-code flows, **PKCE** means **Proof Key for Code Exchange** and
helps bind the code exchange to the initiating transaction. An **authorization
code** is an intermediate value exchanged at the token endpoint, not the access
token presented to the resource API. The current guidance requires PKCE for
public clients and recommends it for confidential clients. Old examples using
password grants or front-channel access-token issuance are not default templates:
the password grant must not be used under that guidance, and implicit-grant use
is discouraged subject to its stated protections. This page explains vocabulary;
it is not a complete secure flow implementation or configuration recipe.

### 2) **Separate federation protocols from the single-sign-on experience**

**Federation** lets separately administered parties rely on identity assertions
through an established trust arrangement. An **identity provider**, or **IdP**,
supplies identity assertions; a relying service evaluates them under its policy.
A trusted assertion still needs an intended recipient, subject mapping, validity
and relevant checks. It does not automatically grant the subject every local role.
NIST's [current federation guideline](https://pages.nist.gov/800-63-4/sp800-63c.html)
describes assertions and separately administered relying parties. Trust needs an
explicit scope; merely sharing a vendor or email-domain spelling is not a complete
federation configuration.

**SAML** expands to **Security Assertion Markup Language**. SAML 2.0 defines
XML-encoded assertions and associated protocols. An assertion contains statements
made by an asserting party; authentication and attributes are common identity-use
contexts. In SAML web sign-in, the application is commonly called a **service
provider**, or **SP**, relying on an IdP. The [SAML 2.0 Core standard](https://docs.oasis-open.org/security/saml/v2.0/saml-core-2.0-os.pdf)
defines assertions and processing; its March 2005 publication date is not a reason
to copy historical cryptographic settings into a current deployment. Bindings and
profiles specify how particular exchanges and use cases operate.

**Single sign-on**, or **SSO**, is the experience or capability of accessing
multiple participating applications using an established authentication context
without independently repeating the full sign-in for each one. OIDC and SAML
can support that experience. SSO is not one token format or a promise of no further
prompts: expiry, step-up requirements and application policy can require more
authentication. One shared password manually typed into several applications is
not the same interaction as this federated SSO example.

Federation and SSO are related but different questions. The first concerns
cross-party trust and assertions; the second concerns sign-in continuity across
applications. Federated participants can still prompt again. Conversely, a set
of applications can provide a shared sign-in experience within one administrative
system without the same cross-organization federation arrangement.

### 3) **Read a two-application sign-in and delegated-API story**

This **fictional architecture packet** describes no live login or token exchange.
A staff user uses the corporate identity service and two applications:

| Participant | Stated role and trust |
|---|---|
| Corporate identity service | OIDC provider for App A; SAML IdP for App B; calendar authorization server in this scenario |
| App A, workshop portal | OIDC RP/client; accepts appropriately validated ID tokens issued for App A and creates its own session |
| App B, support portal | SAML SP; accepts appropriately validated SAML assertions issued for App B and creates its own session |
| Calendar API | Resource server accepting appropriate access tokens for permitted calendar operations |
| User's experience | After corporate sign-in, visits to A and B need no new credential prompt in the observed sequence |
| Portal permissions | Workshop access is decided from App A's own assignment policy |
| Logout rule | App A logout ends A's session; no coordinated termination of the identity-service or App B sessions is configured |

The observed sequence supports an SSO experience for those applications under
those conditions. The identity service performs several roles, but App A's ID
token, App B's SAML assertion and the calendar access token remain different
artifacts. Nothing in the packet permits sending one indiscriminately to every
recipient. The actual validation and transport mechanics are not implemented here.

A user accepted by the corporate IdP may still lack a workshop assignment in A.
That is an authorization question, not proof that federated authentication failed.
Likewise, logging out of A does not end B's or the IdP's context under the stated
rule. The previous session lesson and NIST's session guidance explain why those
boundaries need explicit coordination rather than inference from an SSO label.

A useful handoff is:

> App A uses OIDC for its sign-in identity result, App B uses a SAML federation
> arrangement, and the calendar API uses an access token for delegated resource
> access. The stated sequence gives an SSO experience, while local workshop
> permissions and session termination remain separate. Confirm the intended
> recipient and validation contract for each artifact, and the required logout scope.

Now remove the no-new-prompt observation while retaining the configurations.
The packet still describes federation arrangements, but it no longer demonstrates
that the user experienced prompt-free access in that sequence. Add a product
requirement for logout everywhere: the current local-only rule would leave a
requirement gap. A proposed coordinated-logout design still needs its own
implementation and evaluation; do not call that requirement fulfilled by changing
the diagram's label.

### 4) **Common confusion**

OIDC is not a new name for OAuth, and a JWT is not automatically an OIDC ID token.
Identify the protocol, token purpose and recipient. A successful API access
result alone does not establish a secure application login or a verified legal
identity for the user.

SSO does not mean every application grants identical permissions, shares one
session or accepts the same credential. The same corporate identity can map to
different application roles and independently managed sessions. A login button's
brand is not enough to identify those arrangements.

### 5) **Performance note**

Federated sign-in can involve redirects, network exchanges and token or assertion
validation. Reusing an authentication context can reduce repeated interaction,
but response time and dependency availability still depend on the actual flow.
No universal OIDC-versus-SAML speed ranking follows from JSON versus XML, and no
login latency or availability measurement was performed in this exercise.

### 6) **Mentor note**

Ask the learner to name the recipient and purpose of all three artifacts before
asking them to expand an acronym. Then remove the observed prompt-free sequence
and require a narrower claim. A strong answer preserves federation configuration,
withdraws the observed SSO claim, and keeps workshop permission and logout scope
separate from successful corporate authentication.
