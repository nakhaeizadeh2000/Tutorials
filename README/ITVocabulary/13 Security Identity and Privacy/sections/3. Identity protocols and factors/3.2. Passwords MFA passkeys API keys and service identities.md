## 3.2. Passwords MFA passkeys API keys and service identities

A login asks for two secrets, a passkey uses one approval gesture, and a worker
calls an API with a key. Counting prompts does not tell you how many authentication
factors were used, which identity was established or what the caller may do.
Compare the mechanism and its evidence before interpreting the label.

### 1) **Count distinct factors rather than fields or gestures**

A **password** or memorized **passphrase** is a knowledge-based authentication
secret. An **authentication factor** concerns the category of evidence: something
you know, something you have or something you are. **Multi-factor authentication**,
or **MFA**, combines distinct factors; **two-factor authentication**, or **2FA**,
uses two. Two passwords, or a password and another memorized PIN, do not become
two factor categories merely because they occupy separate fields.

A **one-time password**, or **OTP**, is an authenticator output intended for limited
use rather than a reusable account password. Its purpose and generating mechanism
matter: an application-generated code can demonstrate control of an authenticator.
A code remains phishable if a user can be tricked into entering it at an impostor
that relays it to the real verifier. **Phishing resistance** concerns preventing
that authentication misuse through the protocol's binding, not merely making a
code short-lived or displaying a reassuring prompt.

Current [NIST authenticator guidance](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/)
distinguishes these mechanisms and explains why manually entered OTP and out-of-band
outputs are not considered phishing-resistant. MFA can improve protection without
making every method equally resistant to phishing. A protected authentication
mechanism also does not establish that every recovery path, session or later
application permission is secure.

### 2) **Interpret a passkey through its cryptographic and local checks**

A **passkey** is a FIDO credential for passwordless authentication using a
cryptographic key pair. The service registers public-key information; an
authenticator uses the corresponding private key to produce a proof for the
sign-in exchange. This avoids sending a reusable account password to the service.
The [FIDO passkey explanation](https://fidoalliance.org/passkeys/) distinguishes
**synced passkeys**, available through a provider's synchronization arrangements,
from **device-bound passkeys**, retained on a particular authenticator. A hardware
security key is one possible authenticator, not the only place a passkey can live.

A local fingerprint, face check, device PIN or password may authorize use of that
credential. In this passkey interaction, local biometric verification does not
mean the website receives the fingerprint or face image. The service receives
protocol evidence. Do not generalize that statement to a different application
that explicitly uploads an image for a separate identity-proofing task.

**User presence** and **user verification** are different. A touch can show that
someone is interacting; a PIN or biometric check can locally verify the user
under the authenticator's model. A passkey arrangement can provide multiple factors
through possession of the authenticator and appropriate local verification.
One gesture can therefore participate in MFA, while two knowledge fields remain
one factor category. A screenshot of a prompt alone does not establish that
verification occurred or that the relying party accepted the required evidence.

**WebAuthn** is the web API and associated public-key credential model used in
these interactions. The [WebAuthn Level 3 Recommendation](https://www.w3.org/TR/webauthn-3/)
was published August 25, 2026. It distinguishes presence from verification and
scopes credentials through the relying-party identifier and origin rules. Those
bindings support resistance to ordinary impostor-site phishing; they do not
promise immunity to every endpoint compromise or recovery attack. Availability
of specific features still depends on the actual browser, authenticator and
service implementation. No browser capability or registration was tested here.

### 3) **Distinguish human authentication from API and workload identity**

An **API key** is a credential-like value an API accepts under its own contract.
It may identify a project for quota or billing, authorize a capability, or be bound
to a service identity. The name alone does not tell you which. Current
[Google Cloud API-key documentation](https://docs.cloud.google.com/docs/authentication/api-keys)
distinguishes standard keys, which associate a request with a project without
authenticating a principal, from service-account-bound authorization keys. This
product distinction is a counterexample to both “every API key authenticates a
user” and “no API key can represent a service account.” It is not a recommendation
to deploy that product's long-lived authorization keys.

A **service identity** represents a service or workload in security decisions.
A **service account** is an account used for that non-human context. A **workload**
is a running application or compute task here. Different systems can provide
short-lived credentials, cryptographic proofs or other mechanisms; a service
account does not inherently require a human password or a permanently stored
private-key file. Google's [service-account overview](https://docs.cloud.google.com/iam/docs/service-account-overview)
provides one concrete distinction between the account, its permissions and its
credential options. Product role names and defaults remain scoped to that product.

Read these **independent fictional arrangements**, not executed authentication tests:

| Arrangement | Supported interpretation | Unsupported shortcut |
|---|---|---|
| Staff login accepts a password and a separately memorized PIN | Two knowledge secrets | Calling it two distinct factors from the field count |
| Staff login accepts a password plus proof from an OTP authenticator | Knowledge plus the stated authenticator-control evidence | Assuming the OTP cannot be relayed to an impostor |
| Passkey sign-in verifies the cryptographic response and required trusted local user-verification evidence | Authenticator control plus the stated local verification under this policy | Requiring a second visible prompt before it can count as MFA |
| API contract says key identifies project P for quota only | Project association for that API | Attributing the request to a signed-in staff user |
| Export worker obtains a short-lived credential for its service account | Workload acts under that service identity and its permissions | Treating token issuance as authority over every roster |

For the passkey row, the verification and trust conditions are supplied facts in
the constructed arrangement; they were not inferred from a button's appearance.
For the worker row, ask which resources and actions the account is permitted to
access. Credential strength and least privilege answer different questions.

Now change only the worker's account policy to permit public catalog writes but
not restricted roster reads. A valid credential can still lead to a denied roster
request. That does not imply an authentication failure. If a service accidentally
uses a shared human account instead, the resulting identity and attribution change;
calling the process a worker does not silently create a separate service principal.

Practice: remove the trusted local-verification evidence from the passkey row,
leaving only “a security key was touched.” Can you still establish the MFA claim?
No. You need the authenticator, protocol and relying-party evidence relevant to
verification; presence alone does not establish that additional factor. Retain
whatever cryptographic authentication the remaining evidence actually supports.

### 4) **Common confusion**

Passwordless, MFA and phishing-resistant are different properties. They can overlap,
but none of those words alone establishes every other property. A passkey need not
be a physical USB key, and a synced credential is not automatically device-bound.
Ask about enrollment, recovery, verification and supported environments in context.

An API key, service account and access token are also different objects. The key
may be one credential, the account is a principal with authority, and a token may
carry or reference a limited access grant. A successful human sign-in does not
prove which of those a later background request actually uses.

### 5) **Performance note**

Password verification, OTP checks, public-key verification and credential retrieval
perform different work. Interaction time, network exchanges and recovery effort
also affect the user's experience. Factor count and token names do not provide
comparable latency numbers. No timing, cryptographic benchmark, sign-in-success
rate or workload-credential measurement was performed in this lesson.

### 6) **Mentor note**

Have the learner identify evidence for each factor and principal before counting
prompts. Remove the passkey verification fact and require a narrower claim. Then
ask why restricting the worker's roster permission does not weaken or strengthen
its credential's cryptographic proof. A sound answer separates authentication,
authorization and recovery questions instead of choosing one universally safe label.
