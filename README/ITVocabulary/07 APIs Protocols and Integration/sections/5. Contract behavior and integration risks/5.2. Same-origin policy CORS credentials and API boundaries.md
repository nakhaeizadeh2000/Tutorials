## 5.2. Same-origin policy CORS credentials and API boundaries

A command-line client can receive an API response that a browser page cannot read.
That does not prove the API is unavailable or that the browser's request had no
server-side effect. Browser response access, network reachability and application
permission are separate boundaries.

### 1) **Locate the browser policy and the application access decision**

The **same-origin policy** restricts interactions between different origins in
the browser. For ordinary HTTP addresses, origin compares scheme, full host and
effective port; the previous [address lesson](<../1. Interfaces and contracts/1.2. Resources representations URIs URLs and origins.md>)
owns that comparison. A page at `https://app.example.com` and an API at
`https://api.example.com` are cross-origin even when the same organization owns both.

The policy is not “no cross-origin traffic.” Navigation, embedding and some writes
can cross origins under their applicable rules, while script access to response
data is restricted. The [same-origin policy guide](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy#cross-origin_network_access)
distinguishes those interactions. A form being able to submit does not mean its
page can freely read another origin's responses.

**CORS**, or **Cross-Origin Resource Sharing**, is an HTTP-header mechanism for
sharing responses across origins under browser rules. **Origin** is the request
field describing the initiating origin in these interactions.
**Access-Control-Allow-Origin** is a response field indicating the origin allowed
to read the response through CORS, or a permitted wildcard. It is not a request
header the page can add to grant itself access. The
[header reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Access-Control-Allow-Origin)
explains its server-response role.

A configured allowed origin is not the same as an authenticated user. In minimum
terms, **authentication** establishes identity evidence; **authorization** decides
whether the actor may perform this action on this resource. Detailed identity
mechanisms belong to the later security domain. The server must still make its
application access decisions. A non-browser HTTP client is not constrained by a
page's same-origin policy, and an Origin value is not a secret proving identity.

### 2) **Read the preflight actual request and credential mode separately**

A **CORS preflight** is an OPTIONS request checking whether the proposed cross-origin
request's method and headers are permitted under the CORS protocol. Some requests
can proceed without that preliminary exchange. “Simple request” is a common older
label for the limited method/header arrangements that do not require a preflight;
it does not mean harmless business behavior. The
[MDN CORS guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)
compares these paths.

For example, a normal cross-origin fetch using a POST with
`Content-Type: application/json` requires a preflight unless an applicable cached
permission avoids a new exchange. GET with a non-safelisted custom request header
can require one too. **Safelisted** means included in the protocol's limited
method/header/value allowances, not approved as safe by a security audit.

Here are **constructed selected-field excerpts**, not captured traffic or commands.
Assume a CORS fetch from the app origin to the API origin, credentials mode `omit`,
no applicable preflight cache entry and no unrelated policy/network failure.
The planned actual method is POST. The browser's preflight includes:

```http
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, x-client-label
```

These fields describe a future actual request. They do not contain the reservation
body. A successful preflight response could have status 204 with these fields:

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers: content-type, x-client-label
```

**Access-Control-Allow-Methods** and **Access-Control-Allow-Headers** concern CORS
permission for the proposed request. A bare `204` without the necessary matching
fields is insufficient. A generic HTTP `Allow` header is not a substitute for
these fields. After a successful preflight, the actual response still needs its
applicable CORS fields for the page to read it. The
[Fetch standard's CORS protocol](https://fetch.spec.whatwg.org/#http-cors-protocol)
defines these separate checks. Preflight success is not approval of a reservation.

**Credentials mode** is a browser request setting governing credential handling.
For fetch, `same-origin` is the default, `omit` excludes browser-managed credentials,
and `include` allows their cross-origin use under applicable rules. Cookies are
one example; HTTP authentication and TLS client certificates also belong to this
context. The [credentials reference](https://developer.mozilla.org/en-US/docs/Web/API/Request/credentials)
introduces these settings. `include` cannot manufacture a login, override cookie
scope/SameSite rules or defeat browser third-party-cookie restrictions.

For credentials mode `include`, response sharing requires an explicit allowed
origin and `Access-Control-Allow-Credentials: true`; the literal value is
case-sensitive. `Access-Control-Allow-Origin: *` is not the credentialed-sharing
form, even if the credentials flag is present. These are response-access rules,
not a guarantee that the browser actually had an eligible cookie to send. Do not
infer the request's credential mode solely from whether one Cookie field was seen.

### 3) **Diagnose a CORS report without inventing the business outcome**

Read these **independent fictional cards**. Their observations are stated evidence,
not a live browser test:

| Card | Stated evidence | Supported conclusion |
|---|---|---|
| A | A no-preflight POST was sent; server records the requested change; actual response lacks matching CORS fields | The change occurred, but the page cannot read that response through CORS |
| B | A required preflight fails its CORS check; browser trace shows the planned POST was never sent | This attempt stopped before that POST; no conclusion about other attempts follows |
| C | Preflight succeeds; actual POST returns a readable 403 with correct CORS fields and an explicit application denial | CORS response sharing works; the application denied this action |

For A, blindly retrying the write can repeat its effect. Consult the operation's
repetition contract first. For B, changing response-body parsing will not repair
the preflight mismatch. Compare the initiating origin, requested method/header
names and preflight response. For C, adding more CORS origins will not establish
the missing application permission. Identify the denial and intended actor instead.

Remove A's server record: whether the change occurred becomes unknown. The browser
access failure alone does not restore certainty. Similarly, “works in a command-line
client” verifies only that client's path, credentials and response handling. It
does not test browser CORS enforcement or prove both clients sent the same request.
A useful report includes both origins, credential mode, preflight/actual distinction
and relevant fields, with secrets removed.

Do not treat `mode: "no-cors"` as a way to read a blocked cross-origin JSON API.
It restricts available request features and gives an **opaque response** for this
cross-origin use: its body and headers are unavailable to the page. The
[request-mode reference](https://developer.mozilla.org/en-US/docs/Web/API/Request/mode)
explains the distinction. A repair needs the intended API/browser contract, not
an opaque result that merely hides the useful evidence.

### 4) **Common confusion**

CORS is not a firewall, a login mechanism or a complete defense against unwanted
cross-site actions. Restricting response reads does not generally prevent every
cross-origin request from being sent. Safe HTTP method semantics and CORS
safelisting are also different concepts: GET's intended read-only meaning is not
the complete rule for whether its headers trigger preflight.

Same-site and same-origin are different comparisons. Moving from one subdomain
to another can preserve the former and change the latter. Do not loosen a response
sharing policy merely because two addresses look similar or an error says CORS.

### 5) **Performance note**

An uncached preflight adds a request/response exchange before the actual request.
Preflight permission caching can reduce repeated exchanges under its own rules;
it is distinct from caching an application's response body. A response that varies
its allowed origin also needs correct cache variation; the existing Vary lesson
owns that model. This lesson makes no timing measurement or universal browser
cache-duration claim. Removing a needed access boundary to save an exchange is
not a measured optimization.

### 6) **Mentor note**

Ask where each card stopped: before the actual request, after server processing,
or at an application denial visible to the page. A strong answer cites the
specific observation rather than translating every CORS report into “server never
received it.” Then ask what disappears when A's server record is removed. The
learner should preserve an unknown effect and check repetition semantics before
suggesting a retry.
