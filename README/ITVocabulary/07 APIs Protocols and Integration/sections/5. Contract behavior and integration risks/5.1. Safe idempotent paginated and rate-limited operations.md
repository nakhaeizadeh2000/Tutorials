## 5.1. Safe idempotent paginated and rate-limited operations

A timed-out request may already have changed server state. A second request may
repeat that change, retrieve a different result or be rejected by a limit.
Words such as safe, idempotent and paginated answer different questions; combine
them only after identifying the particular operation and contract.

### 1) **Separate read-only intent repeatable effects and repeatable results**

In HTTP, a **safe method** has essentially read-only requested semantics. Logging
a retrieval does not make GET unsafe in this sense. **Idempotent** means repeating
identical requests has the same intended server effect as one request. It does
not require identical response bytes or status codes. The
[HTTP method-property definitions](https://www.rfc-editor.org/rfc/rfc9110.html#name-common-method-properties)
make these distinctions.

| Method group | Safe semantics? | Idempotent semantics? |
|---|---|---|
| GET, HEAD, OPTIONS, TRACE | Yes | Yes |
| QUERY | Yes | Yes |
| PUT, DELETE | No | Yes |
| POST, PATCH | No general safety guarantee | No general idempotency guarantee; a specific operation can supply one |

QUERY's properties are defined by [RFC 10008](https://datatracker.ietf.org/doc/html/rfc10008),
published June 2026. Its support still depends on the actual path. These are
protocol semantics, not evidence that a particular implementation follows them.
A GET that approves a reservation when merely fetched violates the safe-method
expectation; changing the URL wording does not repair that behavior.

For a **constructed example**, suppose PUT sets a particular preference resource
to `{"language":"fr"}`. Repeating the same request asks for the same replacement.
The first response might report creation and a later response report replacement.
That difference does not defeat idempotency. A GET of current availability can
also return different bodies as availability changes while remaining safe and
idempotent. Thus neither property promises a frozen result.

A **retry** is another attempt after a failure or uncertain result. Before
repeating a write, establish its repetition semantics. An **idempotency key** is
an operation identifier used by a cooperating service to recognize repeated
attempts of one intended operation. It is not a universal feature created by
adding an arbitrary header. Scope, retention, matching parameters and behavior
for simultaneous attempts belong to the service contract.

Brandur Leach's [original failure analysis](https://stripe.com/blog/idempotency)
illustrates the lost-response problem and operation identifiers. For current
provider-specific limits, [PayPal's idempotency reference](https://developer.paypal.com/api/rest/reference/idempotency/)
explicitly requires supported APIs and stored request IDs; its header name and
response behavior are not universal HTTP rules. A new identifier for every retry
would identify new operations instead of preserving one operation's identity.
Reusing one identifier for unrelated user intentions is the opposite mistake.

Consider this **fictional contract card**:

| Item | Explicit contract or observation |
|---|---|
| Operation | POST creates a reservation |
| Repetition rule | Same account, same operation ID and same content within one hour reuse the first completed result |
| First attempt | Client receives no response |
| Client intention | Still wants the same reservation, not a second one |

The missing response leaves the first outcome unknown. Under this stated rule,
a retry of the same intention must preserve the operation ID and content within
the stated scope. Inventing a new ID loses the supplied protection. The rule says
nothing about simultaneous in-flight attempts, partial processing or recovery
after the hour: ask for those cases instead of claiming universal exactly-once
execution. Waiting until a rate limit clears does not fill those gaps.

### 2) **Read pagination as a continuation contract**

**Pagination** divides a collection result into pages. A **page size** bounds the
number of returned items under the API's rules. **Offset pagination** skips a
specified number of results. A **cursor** or **page token** represents where to
continue. Its meaning can be opaque: pass it back as documented rather than
editing its internals. A returned **next link** can package the next request URL.
These names do not by themselves establish a stable snapshot of the collection.

Google's [AIP-158 pagination guidance](https://google.aip.dev/158) supplies one
concrete contract: opaque continuation tokens and an explicit end marker matter;
a short or even empty page need not mean the collection has ended. Keep filter
and ordering parameters consistent with the token's contract. Its particular
field names and defaults are Google's design conventions, not requirements for
every API.

Trace this **constructed offset example**, with the listed order fixed for each
individual request but no snapshot preserved across requests:

| Step | Current ordered IDs | Request and result |
|---|---|---|
| First request | a, b, c, d | Skip 0, take 2 → a, b |
| Insert at front | x, a, b, c, d | No request yet |
| Second request | x, a, b, c, d | Skip 2, take 2 → b, c |

`b` appears in both pages because insertion moved its position. Concatenating
the pages as though they were one unchanged list gives a misleading result.
Removing `a` instead of inserting `x` would produce `d` alone at offset 2, missing
`c` across the two retrieved pages. These are consequences of the stated model,
not a claim that every pagination design has that behavior.

A cursor can avoid some position-shift problems, but “cursor-based” still does
not prove snapshot isolation, no duplicates or permanent token validity. Read the
service's ordering, update and expiry rules. Treat a token as continuation data;
its possession alone is not evidence of access permission.

### 3) **Interpret rate limits with the relevant scope and clock**

A **rate limit** constrains admitted work over time. A **quota** is an allowance
under a stated accounting policy, such as requests per day. The scope may be an
account, client IP, endpoint or shared resource. Some limits count weighted work
rather than one unit per request. A concurrency limit constrains simultaneously
active work, a different dimension from requests per minute.

`429 Too Many Requests` reports rate limiting. [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)
does not prescribe one universal counting identity or algorithm. **Retry-After**
can state delay seconds or an HTTP date; `Retry-After: 30` means seconds, not an
epoch timestamp. The [field definition](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after)
explains those forms. Read reset fields under their own contract: an epoch-based
reset time and a relative wait are different quantities.

[GitHub's rate-limit reference](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
illustrates separate primary and secondary limits, response metadata and `403`
or `429` outcomes. A remaining primary allowance does not prove every other
limit permits a request. Product limits and field names are not universal HTTP
constants; retrieve the applicable current contract when diagnosing a real client.

For practice, a fictional API permits 60 requests per minute **per account**.
Two clients for the same account each make 40 requests in that minute. Their
combined 80 exceeds that allowance; two devices do not create two account budgets.
If a response then asks for a 30-second wait, respect that interval and the
operation's retry contract. It is not a promise that the next attempt will succeed.
Bound attempts and handle the failed operation explicitly rather than spinning
in an immediate retry loop that adds more rejected traffic.

### 4) **Common confusion**

Safe does not mean free of security risk or cost. Idempotent does not mean no
state change, one execution, or identical output. A method's standard semantics
and an application's actual behavior can disagree; preserve both as evidence
when reporting a defect.

A short page does not universally mean finished. A token does not universally
mean snapshot. A `429` does not define how a previous timed-out write ended.
These conclusions require separate parts of the contract.

### 5) **Performance note**

Smaller pages can reduce per-response size while increasing request count to
traverse a collection. Larger pages may increase transfer and memory costs.
Retries consume capacity even when the intended effect is idempotent; duplicate
recognition and retained operation results also require resources. The offset
trace and account example demonstrate logic and arithmetic only. They establish
no database query cost, optimal page size or measured rate-limit implementation.

### 6) **Mentor note**

Give the learner a DELETE response followed by a different response to the same
DELETE, then ask whether that alone disproves idempotency. A strong answer asks
about intended effects instead of comparing only status codes. Follow with the
reservation card and have them identify which values must stay the same and
which missing concurrency/recovery rules prevent a broader guarantee.
