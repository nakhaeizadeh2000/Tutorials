## 4.1. Polling webhooks SSE and WebSocket

A reservation status can reach a browser through repeated requests, an open event
stream or a two-way message channel. A provider can also notify another server
through a webhook. “Push” does not identify which path was used or what happens
when the recipient disconnects. Draw the participants before naming the pattern.

### 1) **Identify who initiates each exchange and where updates arrive**

**Polling** means checking repeatedly for new information. With **short polling**,
a client sends a request, receives the available result and checks again later.
With **long polling**, the server can hold a request pending until an update or a
defined timeout, then the client normally issues another request. A new request
does not necessarily require a new transport connection. The original operator
analysis in [RFC 6202](https://www.rfc-editor.org/rfc/rfc6202.html#section-2.1)
explains this difference; its 2011 deployment limits are not universal current
browser limits.

A **webhook** is a configured callback interaction: a provider sends an event
notification to a receiver's endpoint, commonly through an HTTP request. The
receiver needs a reachable endpoint under the provider's requirements. A browser
page does not automatically receive that server's webhook. The receiver might
update stored state, after which the page learns the result through another path.
[GitHub's webhook introduction](https://docs.github.com/en/webhooks/about-webhooks)
is a concrete provider example of subscription, callback URL and event payload.

**SSE** means **server-sent events**. A client opens an HTTP request and the server
sends a sequence of text events in its response using `text/event-stream`. The
browser's **EventSource** API manages this receive stream. Application events
travel from server to client on that stream; client actions can use separate
requests. **WebSocket** provides a two-way message channel after its opening
handshake. **Full duplex** means both sides can send messages on the established
channel; it does not promise simultaneous processing of all those messages.
The [SSE guide](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)
and [WebSocket API overview](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)
introduce these different communication arrangements.

| Pattern | Initiator and update path | Useful question |
|---|---|---|
| Short polling | Consumer requests snapshots or changes repeatedly | How old can the displayed result become between checks? |
| Long polling | Consumer requests; provider delays a complete response | What ends the wait and starts the next request? |
| Webhook | Provider requests the configured receiving endpoint | What confirms receipt, and what is the retry policy? |
| SSE | Consumer opens a request; provider streams events in the response | What can be recovered after a disconnect? |
| WebSocket | Client opens a channel; both sides exchange messages | Which application message types and recovery rules are agreed? |

A channel may carry snapshots of current state or notifications about changes.
Those are different contracts. Polling a current snapshot can reveal the final
status while missing intermediate transitions; an event feed also needs a
retention/recovery contract to establish whether every transition is available.

### 2) **Read event framing and distinguish a library from its transport**

This is a **constructed SSE response-content excerpt**, not a command, complete
HTTP response or captured stream. The empty line after the data line terminates
the event block. SSE content is UTF-8 text; the JSON inside `data` is an application
choice rather than an SSE requirement.

```text
id: update-17
event: reservation-status
data: {"id":"r17","status":"approved"}

```

`event` names the dispatched event type. `data` supplies its text. `id` sets the
last event identifier; it is not automatically the reservation identifier. Here
`update-17` identifies an update and `r17` identifies a reservation. A browser can
send its nonempty last event identifier in `Last-Event-ID` when reestablishing the
connection. The [HTML standard](https://html.spec.whatwg.org/multipage/server-sent-events.html#the-last-event-id-header)
defines that mechanism and event framing.

Reconnection is not the same as replay. To recover missing updates, the service
must interpret that identifier and have an applicable history or snapshot policy.
An ID alone cannot recreate data the service no longer retains. Likewise, receiving
an event does not prove a user saw it or that a downstream side effect completed.

**Socket.IO** is a library and application protocol, not another spelling of
WebSocket. Its 4.x documentation lists HTTP long-polling, WebSocket and WebTransport
as possible underlying transports. Selection depends on capabilities and
configuration. Its own packet metadata means a plain WebSocket client does not
therefore speak the Socket.IO protocol. The [Socket.IO introduction](https://socket.io/docs/v4/)
explains the distinction and additional facilities such as reconnection and
acknowledgements. These facilities still need their actual application contract;
a successful transport switch is not proof of durable message processing.

When a report says “the socket disconnected,” ask whether it means an OS socket,
a WebSocket connection or a Socket.IO session. Each names a different boundary.
The earlier OS/network lesson owns the general socket meaning.

### 3) **Diagnose delivery and freshness claims from a timeline**

Read this **fictional evidence card**. It describes separate paths in a reservation
system, not a test that ran:

| Time | Observation or explicit contract |
|---|---|
| 0 | Browser polls the receiver's status endpoint and displays pending |
| 1 | Provider changes the reservation to approved |
| 1.1 | Provider sends a webhook to the receiver, which stores approved |
| 1.2 | Receiver returns its documented receipt response to the provider |
| 5 | Browser's next poll retrieves approved and updates the display |

The webhook delivery and browser freshness are different paths. The receiver had
the update at 1.1, while the browser did not request a new result until 5. Calling
the whole system “instant because it uses webhooks” hides that delay. A clearer
statement is that the provider notified the receiver, and the browser observed
the new status on its next poll. The card supplies no claim about every user's
latency or about intermediate status transitions.

Now remove the receipt observation. Was the notification processed? The stated
stored-state observation still establishes this particular receiver update, but
the provider's receipt knowledge becomes unknown. If the provider retries after
an unobserved response, the receiver could see the notification again. Whether it
actually retries depends on its contract. For example,
[GitHub documents no automatic redelivery of failed deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries).
Do not copy another provider's retry schedule into a generic webhook definition.

For a second variation, the browser uses SSE but disconnects before the approved
event. “EventSource reconnected” establishes a new receive opportunity, not that
the missing update was replayed. Ask for the last received ID, server recovery
behavior and evidence of the displayed state. The same missing-history question
applies to a reconnected WebSocket channel unless the application supplies recovery.

### 4) **Common confusion**

One-way event delivery does not make the whole application read-only. An SSE feed
can coexist with ordinary HTTP writes. Two-way WebSocket capability does not mean
every application needs it, and a webhook endpoint is a receiving server interface,
not automatically a user's notification surface.

“Real time” is often informal product wording. Ask for a concrete delay boundary
and target. It does not promise a hard deadline, no loss or exactly one processing
of each event. Repeated delivery, recovery and business effects need explicit rules.

### 5) **Performance note**

For a simplified steady-state model, 100 clients each making one poll every five
seconds produce an average of 20 requests per second, excluding retries and other
traffic. Shortening the interval to one second gives 100 requests per second.
Synchronized clients can still create bursts rather than evenly spaced traffic.
These are arithmetic estimates, not measured server capacity.

Persistent receive channels reduce repeated request setup but retain connection
state and may buffer messages. Slow consumers and intermediary timeouts still
matter. Compare actual update frequency, delay needs, open connections and message
volume before choosing a pattern. No universal connection count or speed ranking
is established by these examples.

### 6) **Mentor note**

Ask the learner to draw two arrows for the card: provider to receiver, then browser
to receiver and its response. The drawing should explain why webhook receipt at
1.2 does not mean the page changed then. Follow with the disconnect variation:
a strong answer asks where missed updates come from instead of treating reconnect
as a recovery guarantee.
