## 2.1. Requests responses methods headers status codes and bodies

A response can successfully report that a reservation is still pending. HTTP
success and completion of the user's business goal are different conclusions.
Read the request's action, response status, metadata and application content
together before announcing what happened.

### 1) **Annotate the two messages in an exchange**

A **request** asks a server to handle an operation. A **response** reports an HTTP
result and can carry application data. A **method**, also called a **verb**, expresses
the request's intended action. A **status code** is the three-digit response result.
A **header field** carries named metadata. A **body** carries message data when
permitted; not every message has one. The
[MDN message guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Messages)
uses HTTP/1.1's readable structure to introduce these parts.

Here are **constructed HTTP/1.1 reading views**, not captured traffic and not
commands to send. A real HTTP/1.1 message uses CRLF line endings. The blank line
separates the field section from any body. The response body below is the single
31-byte UTF-8 JSON text shown, without a trailing newline in its declared content.
JSON is a structured text format; its full format/validation vocabulary comes later.

```http
GET /reservations/r17 HTTP/1.1
Host: api.example.com:8443
Accept: application/json

```

```http
HTTP/1.1 200 OK
Date: Sun, 18 Oct 2026 12:00:00 GMT
Content-Type: application/json
Content-Length: 31

{"id":"r17","status":"pending"}
```

The **request line** gives method `GET`, request target `/reservations/r17` and
version. `Host` identifies the requested authority in this example. `Accept` states
a response-format preference. This request contains no body. The **status line**
gives version, code `200` and a human-readable **reason phrase**, `OK`. Reason
phrases are not application state or a reliable machine decision key.

`Content-Type` identifies the response content's **media type**, here
`application/json`. `Content-Length` in this particular response gives its content
length in bytes. The property `status` inside the JSON body belongs to the application
contract; it is separate from the HTTP status code. HTTP's named fields and the
body's field names are also different namespaces.

HTTP field names are case-insensitive, while field values follow their own rules.
Do not lowercase every value merely because names can be compared without case.
The [header reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers)
introduces request, response and representation metadata. Complete framing rules
and intermediary handling are protocol details beyond this vocabulary exercise.

HTTP/2 and HTTP/3 preserve shared HTTP semantics with different encodings/framing.
A developer tool can show a readable view without that view being literal wire
bytes. In particular, do not write `HTTP/2 200 OK` as though it were HTTP/1.1's text
status line on an HTTP/2 connection. The next lesson develops version terminology.

### 2) **Read the method as intent rather than a CRUD nickname**

The following methods are worth recognizing. Their protocol semantics constrain
an application, while the particular resource and data contract supply the
remaining meaning. This table is an orientation, not a complete implementation
or permission policy.

| Method | Intended operation |
|---|---|
| `GET` | Retrieve a selected representation |
| `HEAD` | Like GET, but with no response content; useful metadata can still be returned |
| `POST` | Ask the target to process submitted content under its own defined behavior |
| `PUT` | Create or replace the target's state with the supplied representation |
| `PATCH` | Apply modifications described by a patch document |
| `DELETE` | Remove the target's association with its current functionality; not a promise to erase every underlying copy |
| `OPTIONS` | Request communication options for the target |
| `CONNECT` | Establish a tunnel |
| `TRACE` | Request a diagnostic loopback of the request path |
| `QUERY` | Request safe query processing with defined request content |

The [method reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Methods)
is useful for lookup. [RFC 5789](https://datatracker.ietf.org/doc/html/rfc5789)
defines PATCH's modification-document model. A patch is not necessarily “one
JSON object containing whichever fields changed”; the agreed patch format matters.
POST is also not a synonym for record creation, and PUT is not limited to updating
an already existing object. Method names alone do not reveal database operations.

**QUERY** is now standardized by
[RFC 10008](https://datatracker.ietf.org/doc/html/rfc10008), published June 2026.
It supports safe, idempotent processing of query content rather than overloading
GET content with an assumed universal meaning. Safe concerns requested read-only
semantics; idempotent concerns the intended effect of repetition. The later
operation-guarantee lesson develops those properties and their limits. QUERY is
a method, distinct from the URL's query component after `?`. A published method
does not prove support in a given server, intermediary or client tool.

Some methods allow meaningful request content while others have no generally
defined semantics for it. “Our client can send bytes” does not establish that all
servers and intermediaries will interpret them as intended. Use the method and
format the actual contract supports; full behavior comes from
[HTTP semantics](https://www.rfc-editor.org/rfc/rfc9110.html#name-methods), not a
rule that every action must fit a database create/read/update/delete nickname.

### 3) **Interpret status content and missing responses separately**

The first digit gives a status **class**:

| Class | Reading orientation |
|---|---|
| `1xx` | Informational/interim response |
| `2xx` | Successful handling under the method/status semantics |
| `3xx` | Redirection-related handling, including cache validation results |
| `4xx` | A reported client-error condition |
| `5xx` | A reported server-error condition |

These classes describe the response, not which team's code caused the incident.
A client receiving an error can be correct, and a server implementation can issue
a misleading code. Preserve the evidence instead of assigning blame from its
first digit.

Recognize a few common meanings. `200 OK` indicates success under the method's
semantics. `201 Created` reports resource creation. `202 Accepted` means accepted
for processing without establishing completed processing or its eventual success.
`204 No Content` reports success without response content; do not require a JSON
body in every successful response. `304 Not Modified` is used in conditional
retrieval and has no response content; it is not a new representation payload.
The [status reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status)
provides a lookup route; read the relevant definition and conditions rather than
memorizing every code.

For failures, `400` indicates a perceived bad request, `401` a lack of valid
required authentication credentials, `403` refusal and `404` no current target
representation found or unwillingness to disclose one. `409` indicates conflict
with current state. `429` reports rate limiting. `500` is an unexpected server
condition, while `502` and `504` concern a gateway's upstream response/timeout and
`503` indicates temporary unavailability. The detailed cause and recovery policy
still need application and environment evidence.

Return to the constructed GET. It successfully retrieves a representation of
reservation `r17`. Under the previous lesson's contract, pending means recorded
but not approved. The correct user message preserves that state. It must not say
“Approved” merely because the HTTP code is `200`. If the body instead disagrees
with the documented contract, investigate the mismatch rather than discarding
the contract or blindly trusting a UI label.

Now consider two **fictional variations**. First, an operation returns `202` and
an agreed job identifier. That supports acceptance for processing; the caller
needs the documented completion-observation mechanism. Second, a connection fails
before any HTTP response arrives. There is no HTTP status code to interpret.
Do not invent a `500` or assume a timed-out write had no effect; the absence of a
received result is a different evidence boundary.

### 4) **Common confusion**

`Accept` states a preference about what the client can receive; `Content-Type`
describes the content being sent. Putting `Accept: application/json` in a request
does not make arbitrary request-body bytes valid JSON or force every error response
to have that format.

A body is not synonymous with JSON, and a successful response need not have a body.
The response's HTTP code, the application's `status` field and a transport result
are three different observations. Label each when handing off an integration issue.

### 5) **Performance note**

Headers and content add transferred bytes, and serialization/processing can add
work. No status code or verb establishes the cost of an operation: GET may trigger
expensive processing and a short error may arrive after a long wait. The 31-byte
body length checks representation size only; it excludes headers, framing and
transport overhead. This lesson supplies no measured request latency or throughput.

### 6) **Mentor note**

Ask the learner to circle the HTTP code and the body status separately, then explain
the user-facing result. Follow with the `202`, `204` and no-response variations.
A strong answer changes the inference for each case, avoids unconditional JSON
parsing and preserves an unknown application outcome when the response is missing.
