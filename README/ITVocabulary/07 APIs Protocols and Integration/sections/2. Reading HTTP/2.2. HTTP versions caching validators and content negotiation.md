## 2.2. HTTP versions caching validators and content negotiation

A browser can reuse a response correctly even though the server has changed since
that response was generated. “Fresh” is a cache-policy judgment. It is not proof
that the cached representation equals the server's state at this instant. Keep
protocol version, reuse policy and representation selection as separate questions.

The protocol references here are HTTP semantics and caching from June 2022,
with HTTP/2 and HTTP/3 defined by RFC 9113 and RFC 9114. Checked 2026-10-18;
these are standards baselines, not a claim that every client implements every feature.

### 1) **Recognize shared semantics across different HTTP versions**

The previous lesson's methods, status codes and representation vocabulary carry
across HTTP versions. The version changes how those messages travel. An API's
business version, such as `/v2/reservations`, is an independent contract label.

| Protocol | What to recognize |
|---|---|
| HTTP/1.1 | Textual start lines and fields, with defined body framing, commonly over TCP |
| HTTP/2 | Binary frames and interleaved exchanges on streams within a TCP connection; compressed field blocks |
| HTTP/3 | HTTP mapped onto QUIC streams, with QUIC carried over UDP |

A **frame** here is a version-specific protocol unit, different from the Ethernet
frame in the network lesson. **Multiplexing** lets multiple logical exchanges share
a connection. HTTP/2 does not remove TCP's transport head-of-line blocking.
HTTP/3 changes that transport relationship; it does not remove every reason an
application might wait. See the originating [HTTP/2](https://www.rfc-editor.org/rfc/rfc9113.html)
and [HTTP/3](https://www.rfc-editor.org/rfc/rfc9114.html) specifications for those mappings.

A path can use HTTP/3 between browser and reverse proxy, then HTTP/1.1 between
proxy and application. “The request used HTTP/3” therefore needs an observed hop.
An `https` URL alone does not identify HTTP/1.1, HTTP/2 or HTTP/3, and a readable
DevTools view does not establish literal wire encoding. Shared semantics and
version scope are explained in [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#name-protocol-version).

### 2) **Read cache storage freshness and reuse as separate decisions**

An **HTTP cache** stores responses for possible reuse. A **private cache**, such as
a browser's HTTP cache, serves one user. A **shared cache** serves multiple users.
A **CDN**, or **content delivery network**, distributes content delivery across
servers and can provide shared caching. Naming the cache matters: a response
missing from a browser cache might still be available at a CDN. The
[MDN caching guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)
compares these locations before explaining freshness and validation.

**Cache-Control** carries directives. Here are unqualified **response** directives,
not a complete configuration recipe:

| Directive | Interpretation |
|---|---|
| `max-age=60` | A 60-second freshness lifetime, subject to other applicable rules |
| `no-cache` | Storage can be allowed; successful validation is required before reuse for another request |
| `no-store` | Do not store the immediate request/response or reuse this response |
| `private` | A shared cache must not store the response; a private cache may, subject to other constraints |

**Fresh** means current age is less than freshness lifetime; **stale** means it no
longer meets that test. `Age` reports an estimated age in seconds since generation
or successful origin validation. `Expires` supplies an absolute expiry time;
it is not a command to delete a local file. These distinctions come from
[HTTP caching](https://httpwg.org/specs/rfc9111.html#freshness). Storage permission,
freshness and whether a response matches this request are separate checks.

Consider this **constructed reading exercise**, not captured traffic. An eligible
stored response for one public timetable has these selected response fields:

```http
Cache-Control: max-age=60
ETag: "timetable-1"
```

Assume its calculated current age is zero at time 0. There are no other reuse
restrictions, invalidations or selection differences in this example.

| Time in seconds | Stated event | What the cache can conclude |
|---|---|---|
| 0 | Store timetable 1 | Fresh under the stated policy |
| 20 | Origin changes to timetable 2 | The cache has not learned that change |
| 30 | Another matching request arrives | Timetable 1 is still fresh and may be reused |
| 60 | Another matching request arrives | Timetable 1 is now stale; ordinary fresh reuse no longer applies |

At time 30, “fresh” and “latest origin content” give different answers. At time
60, stale does not mean corrupted or automatically deleted. Validation can make
a stored response usable again. Conversely, a freshness lifetime does not force
an already displayed page to refresh at its expiry boundary.

Some policies deliberately permit bounded stale service. **stale-while-revalidate**
allows a limited stale response while validation is attempted in the background;
**stale-if-error** allows bounded stale use for eligible error conditions. They
are extensions described by [RFC 5861](https://www.rfc-editor.org/rfc/rfc5861.html),
not unconditional defaults or new definitions of “fresh.” Read the full applicable
policy and implementation support before interpreting a stale response as a defect.

### 3) **Trace validators and negotiated representations**

A **validator** supplies evidence for comparing a selected representation with a
previous one. **ETag**, short for entity tag, is an opaque quoted identifier.
The client must not assume it is a content hash or a sortable revision number.
A tag prefixed `W/` is weak: it can support semantic equivalence without promising
byte-for-byte identity. Strong and weak comparison have different uses; see
[HTTP validator semantics](https://www.rfc-editor.org/rfc/rfc9110.html#name-validator-fields).

For an ordinary conditional GET, the client can send the stored tag in
`If-None-Match`. This selected-field excerpt is illustrative, not a whole request:

```http
If-None-Match: "timetable-1"
```

If the selected representation still matches, `304 Not Modified` carries no new
response content. The cache updates applicable metadata and reuses its suitable
stored body. It must not replace that body with an empty timetable. If the current
tag differs in this example, a normal successful retrieval returns `200` with
timetable 2 and its new tag. The MDN guide's
[validation walkthrough](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching#validation)
compares these outcomes. Under our timeline, the change at time 20 leads to the
second result. In a variation with no origin change, validation can return `304`.

`Last-Modified` is a timestamp validator, commonly paired with `If-Modified-Since`.
It has different precision and maintenance limits from an entity tag. Neither
mechanism promises the resource cannot change again immediately after validation.

**Content negotiation** selects a representation using the interaction's stated
preferences and available variants. The server can offer English and French
content at one URL. A request's `Accept`, `Accept-Language` and `Accept-Encoding`
express preferences about media type, language and content coding. Selected
response metadata describes what was sent: for example `Content-Type`,
`Content-Language` and `Content-Encoding`. A preference is not proof that the
chosen representation satisfies it. The [negotiation guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Content_negotiation)
explains the server-selection model and its limits.

Suppose a constructed response for `Accept-Language: en` includes
`Content-Language: en` and `Vary: Accept-Language`. **Vary** tells a cache that the
named request field participates in matching stored responses to later requests.
A later French preference cannot simply use this English variant as the same
matching cached response. `Vary` does not grant access or establish identity.
Omitting a relevant selection field can cause a cache to reuse the wrong variant;
inspect both selection policy and the actual fields rather than clearing caches
and declaring the issue solved.

### 4) **Common confusion**

`no-cache` does not mean “never store,” and `private` does not mean “encrypted.”
For a response that may be retained but must be checked before reuse, validation
is the relevant distinction. For one that must not be retained in HTTP caches,
`no-store` expresses the storage restriction. Neither directive is a complete
privacy guarantee or a way to control malicious recipients.

A `304` concerns the conditional request and selected representation, not every
resource on the server. An HTTP version is also not an application release number.
Ask which contract, representation, cache and hop the claim describes.

### 5) **Performance note**

Eligible fresh reuse can avoid an upstream request. Validation can avoid sending
the representation body again, but still requires communication and server work.
Variant selection can divide reuse across many stored representations. These are
cost mechanisms, not measured speedups: this lesson has no live cache or protocol
benchmark. Compare latency and transferred bytes for the same workload and cache
state before attributing a change to HTTP/3 or caching alone.

### 6) **Mentor note**

Ask whether timetable 1 at time 30 is fresh, then whether it is current origin
content. The correct answers are yes and no under the stated timeline. Remove
the time-20 evidence: freshness is still established, but latest-state equality
is now unknown. Follow with the no-change `304` variation and ask where the
visible body comes from. A sound explanation identifies the stored body rather
than inventing content inside the `304` response.
