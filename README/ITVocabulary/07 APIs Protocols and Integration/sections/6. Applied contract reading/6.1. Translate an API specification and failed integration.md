## 6.1. Translate an API specification and failed integration

A report says, “The API is broken: success means approved, the SDK is typed, and
CORS says the request failed.” That sentence combines different contracts and
observations. This exercise asks you to trace them without turning uncertainty
into a diagnosis. All artifacts below are constructed; no reservation service
or deployed integration was tested.

### 1) **Translate a description into actions representations and missing promises**

Use this **OpenAPI 3.2.1-style description fragment**, written as JSON. It is not
a standalone complete OpenAPI document: top-level metadata and other operations
are deliberately outside the excerpt. The [OpenAPI specification](https://spec.openapis.org/oas/v3.2.1.html)
defines how path, parameter, operation and response descriptions fit together.
Reading this excerpt is not evidence that a live implementation obeys it.

```json
{
  "paths": {
    "/reservations/{id}": {
      "get": {
        "parameters": [
          {"name": "id", "in": "path", "required": true,
           "schema": {"type": "string"}}
        ],
        "responses": {
          "200": {
            "description": "A selected reservation representation",
            "content": {
              "application/json": {
                "schema": {
                  "type": "object",
                  "required": ["id", "status"],
                  "properties": {
                    "id": {"type": "string"},
                    "status": {"type": "string",
                               "enum": ["pending", "approved"]}
                  }
                }
              }
            }
          }
        }
      }
    }
  }
}
```

Additional fictional product documentation says **pending** means recorded but
awaiting approval, while **approved** means approval was granted. The service base
is `https://api.example.com`; the browser app is `https://app.example.com`.
A separate creation operation uses POST `/reservations`; its accepted response is
202. The packet does not provide its full request schema, completion deadline or
repetition contract.

Before reading the answer, translate the GET for a teammate. A suitable version is:
“To retrieve reservation r17, send GET to `/reservations/r17` at the documented
base. A described 200 result contains JSON with string `id` and `status` properties.
The listed status values are pending and approved. Read the status value to know
which business state is represented.”

`{id}` is a path placeholder, not braces to send literally for r17. **enum** here
restricts a value to the listed choices, as explained by the
[enumerated-values reference](https://json-schema.org/understanding-json-schema/reference/enum). The required list states that both
properties must be present; listing a property without requiring it would not
establish presence. This fragment does not forbid additional properties. It also
does not promise every request succeeds, define all errors or supply an access
policy. The creation note establishes acceptance wording, not immediate approval.

### 2) **Trace the failure packet to its last established boundary**

The reporter provides these independent fictional cases:

| Case | Evidence |
|---|---|
| A: status display | A GET response is readable to the browser, HTTP 200 with body `{"id":"r17","status":"pending"}`. The UI displays Approved solely because the code is 200. |
| B: freshness | A browser stores pending at calculated age zero with `max-age=60`; origin changes to approved at time 20; matching fresh reuse at time 30 still supplies pending. No invalidation or other reuse restriction applies. |
| C: creation uncertainty | The browser sends a POST not requiring preflight. Its response fails CORS sharing. There is no server processing record or usable response available in the packet. |
| D: typed client | An SDK build passes. A later actual response contains `{"id":"r17","status":7}`. The report provides no runtime validation evidence. |

For **A**, the content agrees with the described pending state. The UI's mapping
from HTTP 200 to business approval is wrong under the supplied product definitions.
The packet does not establish a defective backend approval rule. Ask the UI to
interpret the represented status and handle unexpected content explicitly.

For **B**, fresh cache reuse and latest origin state differ. The reader has evidence
of the origin's change, but the cache has no new validation. The old result may
still be reusable under the stated policy. Investigate the product's acceptable
staleness and the intended response policy before calling the cache noncompliant.
“Show the latest state after approval” needs a defined observation/revalidation
path; an HTTP version number does not supply one.

For **C**, CORS sharing failed after the request was sent. The business effect is
unknown. Obtain a trustworthy operation result or use the documented repetition
contract before another creation attempt. Neither “it definitely failed” nor
“it definitely created a reservation” follows from this card. Adding a new request
ID without an agreed operation-identity rule supplies no duplicate protection.

For **D**, the numeric status conflicts with this described string/enum contract.
A passing SDK build does not validate a received payload. Check the actual service
version, description and runtime boundary handling. A mismatch could arise from a
wrong environment, incompatible deployment or defective implementation; the packet
does not identify which. Do not silently coerce `7` to a string and call the
integration repaired.

Now vary C: a required preflight fails, and a browser trace confirms the actual
POST was not sent. This attempt stopped earlier, so it cannot have created through
that POST. Other attempts remain separate evidence. This change demonstrates why
“CORS error” alone is too little information for an operation-outcome claim.

### 3) **Write a useful handoff and justify the next check**

A useful handoff separates observation, interpretation and next evidence. For C:

> The browser sent the creation POST to the API origin, but could not read its
> response because CORS sharing failed. We have no evidence of the business result.
> Before retrying creation, establish the original operation's outcome or obtain
> its repetition contract. Separately compare the actual response's CORS fields
> with the app origin and request credential mode.

This statement keeps two investigations visible. Repairing response sharing will
help future browser access; it does not retroactively establish the first result.
Record the actual client/service versions and correlate the relevant attempt,
removing credentials from shared artifacts. Do not attach unrelated traffic and
assume it describes the same operation.

For interview practice, answer: **“The payload matches the schema. What remains?”**
A good answer distinguishes structural agreement from business permission,
current inventory, completion and freshness. None is automatically established
by a shape check. **“Would switching to gRPC fix C?”** A good answer first names
the observed browser boundary and desired behavior. A protocol/framework change
is not evidence about the already uncertain creation or a substitute for its
contract. Implementing another interface would be a separate design decision.

To assess your answer, require a specific request, target, stated observation,
applicable rule and unknown. Reject claims that a generated client proves server
behavior, every successful code means approved or every CORS failure prevents
transmission. Prefer one next observation that distinguishes plausible explanations
over a broad instruction to “check everything.”

### 4) **Common confusion**

A description's schema is a statement about allowed data, not proof an executing
validator ran. A single matching response also does not verify the whole service.
Conversely, a mismatch identifies a contract discrepancy without necessarily
identifying the responsible deployment or team.

An error shown to a browser user and the server's operation outcome can disagree.
Preserve the uncertainty until relevant evidence resolves it; repeated attempts
can make that evidence harder to interpret if they create separate operations.

### 5) **Performance note**

Case B contains a declared freshness model, not a latency experiment. The packet
contains no response-time distribution, throughput sample or before/after load
evidence. Caching, retries, validation and interface changes can affect cost,
but these cards cannot quantify it. A useful performance follow-up would define
the same client task, cache state and measurement boundary before comparison.

### 6) **Mentor note**

Ask the learner to give the last proven fact for each case before proposing a
repair. A should end at a represented pending state, B at eligible cached reuse,
C at unknown processing after transmission, and D at a description/data mismatch.
Then remove one decisive row or change the preflight evidence. Their conclusion
should change only where the evidence changed; this is stronger evidence of
understanding than memorizing status codes.
