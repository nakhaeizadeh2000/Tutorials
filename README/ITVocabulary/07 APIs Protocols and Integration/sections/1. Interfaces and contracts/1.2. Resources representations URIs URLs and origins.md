## 1.2. Resources representations URIs URLs and origins

An address identifies what a client wants to interact with. The returned data is a
representation of that target, not the address itself. Meanwhile, a browser may
compare addresses by origin or site for different purposes. Those comparisons
need more precision than “same domain.”

### 1) **Separate the resource its identifier and its representation**

In HTTP, a **resource** is the target of an interaction: a reservation, collection,
report or another concept exposed through the interface. It need not be a disk
file or one database row. A **representation** communicates information about a
resource's state in a particular form, together with relevant metadata. The same
reservation could have an HTML presentation for a person and a structured data
presentation for another program. Their bytes can differ while referring to the
same application concept.

[HTTP semantics sections 3.1–3.2](https://www.rfc-editor.org/rfc/rfc9110.html#name-resources)
define this separation. “The resource changed” and “we received a different
representation” therefore need context. A localized label or formatting change
can change representation bytes without changing the reservation's accepted date.
Conversely, an identifier can remain stable while the represented state changes.
Do not treat a resource address as a promise of immutable content.

A **URI**, **Uniform Resource Identifier**, identifies a resource under an agreed
scheme. A **URL**, **Uniform Resource Locator**, additionally provides an access
mechanism/location. These are the
[RFC 3986 terminology distinctions](https://www.rfc-editor.org/rfc/rfc3986.html#section-1.1.3);
web platform documents commonly use URL throughout. Neither word guarantees that
a target exists, is currently reachable or permits your requested action. The
method and application contract still matter.

A **URI reference** can be absolute or relative to a base. For example, the path
reference `/reservations/r17` needs a base location to determine its full address.
Do not copy a relative path into an unrelated environment and assume it still
identifies the same service. A base in test and a base in production can make the
same path refer to different deployments.

### 2) **Read an address by components without making a request**

Use this fictional example address. It is inspected as text only; no service is
contacted. Save as `address_parts.py` and run `python3 address_parts.py`. Checked on
Python 3.14.4/Linux x86_64, 2026-10-18, with only the standard library.

```python
from urllib.parse import urlsplit

address = "https://api.example.com:8443/reservations/r17?view=summary#details"
parts = urlsplit(address)

print("Scheme:", parts.scheme)
print("Host:", parts.hostname)
print("Port:", parts.port)
print("Path:", parts.path)
print("Query:", parts.query)
print("Fragment:", parts.fragment)
```

Observed output:

```text
Scheme: https
Host: api.example.com
Port: 8443
Path: /reservations/r17
Query: view=summary
Fragment: details
```

The **scheme** is `https`. The **authority** in this example is the host and explicit
port, `api.example.com:8443`. The **path** identifies the target within that context;
it is not evidence of a filesystem directory. The **query** is additional address
data introduced by `?`; the contract decides what `view=summary` means. The
**fragment**, introduced by `#`, identifies a client-side target or interpretation.
The fragment is not sent as part of this URL's normal HTTP request target. Client
code can still read it and explicitly communicate information later.
[MDN's URI component reference](https://developer.mozilla.org/en-US/docs/Web/URI/Reference)
explains these boundaries. In particular, a fragment change is not a new query
parameter received automatically by the server.

**Percent-encoding** represents data bytes using `%` and two hexadecimal digits,
such as `%20` for a space byte. Encoding a separator and leaving it as a structural
separator can change interpretation. Do not implement arbitrary decoding or URL
construction by guessing which punctuation is harmless. Encoding is a representation
mechanism, not encryption or validation of the requested action.

The [Python parser reference](https://docs.python.org/3.14/library/urllib.parse.html#urllib.parse.urlsplit)
defines this split operation and explicitly warns that it is not input validation
or complete conformance to a browser's URL parser. This exercise establishes how
this well-formed literal is split. It proves no DNS resolution, connection,
permission or application behavior.

### 3) **Compare origins and sites using their intended boundaries**

For ordinary HTTP(S) addresses, an **origin** combines scheme, full host and effective
port. **Same-origin** means these match; **cross-origin** means they do not. The
path, query and fragment do not participate in this comparison. An omitted default
HTTPS port is effectively 443; merely writing `:443` does not create another origin.
The [MDN origin explanation](https://developer.mozilla.org/en-US/docs/Glossary/Origin)
shows these comparisons. Other URL schemes and sandboxed documents can use different
origin rules, so do not apply this simple tuple model to every possible URL.

A browser **site** comparison is broader. In the schemeful same-site context used
here, it combines the scheme with the **registrable domain**. A **public suffix**
is a suffix under which separate parties can register names, as recorded in the
Public Suffix List; it need not be a single final label. A registrable domain adds
the name immediately before the applicable public suffix. For `api.example.com`,
the example's registrable domain is `example.com`. Different subdomains can be
same-site while remaining cross-origin.

[MDN's site explanation](https://developer.mozilla.org/en-US/docs/Glossary/Site)
and Eiji Kitamura's original
[same-site versus same-origin guide](https://web.dev/articles/same-site-same-origin)
explain why neither “same company” nor “last two labels” is a sufficient general
algorithm. In this site comparison, ports do not distinguish sites; schemes do.
Older material may use a schemeless definition, so read the mechanism's actual
meaning rather than silently applying old terminology.

Compare each address below with `https://api.example.com/reservations`:

| Other address | Origin relationship | Schemeful site relationship |
|---|---|---|
| `https://api.example.com:443/help?lang=en` | Same-origin | Same-site |
| `https://api.example.com:8443/help` | Cross-origin: different port | Same-site |
| `https://www.example.com/help` | Cross-origin: different host | Same-site |
| `http://api.example.com/help` | Cross-origin: different scheme | Cross-site |
| `https://api.example.org/help` | Cross-origin: different host | Cross-site |

These are address comparisons, not successful requests or permission decisions.
Knowing that two addresses are same-site does not establish that a browser script
may read every response from both. The later CORS lesson uses these distinctions;
no browser-access configuration is implied by this table.

As practice, change only `#details` to `#history` in the example literal. The origin
and schemeful site are unchanged. Now change only the port from 8443 to 9443: the
origin changes, while the schemeful site remains the same. The changed address
still does not tell you whether any service listens there.

### 4) **Common confusion**

A resource is not its filename, URL string or one particular response body. The
identifier selects a target; a representation communicates state under the
operation's semantics. A different URL also need not mean a different physical
server, because mappings and intermediaries can vary.

Origin and site are not synonyms. Sharing the `example.com` parent does not make
`api.example.com` and `www.example.com` same-origin. Use the full scheme/host/port
comparison for origin and the applicable site rule for a site question. Neither
label alone establishes organizational trust or user authorization.

### 5) **Performance note**

Address structure can influence routing and representation selection, but a short
URL is not evidence of a fast operation. The returned representation's size and
processing may differ between formats, yet this exercise measures neither. Its
parser performs local text processing only. It is not a request-latency benchmark
or proof that changing a query avoids server work.

### 6) **Mentor note**

Ask the learner to annotate the literal, then explain why changing only its path
can preserve origin while selecting a different target. Follow with the subdomain
and port rows. A sound answer distinguishes address comparison from browser access
policy and from actual service reachability, without using the vague phrase
“same domain” to answer all three questions.
