## 1.1. APIs endpoints routes operations and contracts

A teammate sends `/reservations` and says, “Here is the API.” The path is useful,
but it does not tell you which action to request, what data to supply or what
success means. An address, an operation and a contract answer different questions.
This domain builds on the software, network and client vocabulary without requiring
a backend framework or a deployed service.

### 1) **Distinguish an interface from its implementation and consumers**

An **API**, **application programming interface**, describes how software can use
capabilities supplied by other software. A local library function and a browser
interface are APIs too; not every API is a web address. The earlier
[programs and libraries owner](<../../../03 Software Execution and Developer Tools/sections/1. Software categories/1.1. Programs applications libraries frameworks and SDKs.md>)
introduces that general meaning. Here we focus on interfaces between communicating
applications.

The **provider** supplies the capability; the **consumer** uses it. An **API call**
is an invocation of an exposed operation. For a remote HTTP API, that normally
involves sending a request and interpreting the response under its contract.
**HTTP** means **Hypertext Transfer Protocol**; its message and method semantics
are developed later in this domain. No actual call is made by merely displaying
an address in a document.

An **interface** is the usable boundary. The **implementation** is the code and
supporting behavior behind it. Several implementations can aim to provide the
same interface, and one implementation can expose several interfaces. Documentation
can describe the boundary without revealing the internal database tables or source
layout. Conversely, inspecting source does not replace knowing which behavior
consumers are promised.

A **public API** commonly means an interface offered to outside consumers, while
an **internal API** serves consumers within a stated organization or system.
These are audience/exposure labels. Public does not necessarily mean free,
unrestricted or available without credentials; internal does not automatically
mean trusted or undocumented. Clarify the intended audience and access contract.

### 2) **Identify the address operation and routing rule**

An **endpoint** in HTTP API discussions often means an exposed address, or a specific
method-and-address combination. Teams use both meanings. Include the method and
location when precision matters instead of arguing from an unqualified endpoint
count. This differs from a transport endpoint described by protocol, address and
port: several HTTP operations can use the same transport service.

A **method** expresses the requested HTTP action, such as `GET` for retrieval.
A **path** is the location component after the host portion in the simple examples
here. A **path template** has a variable part, such as `/reservations/{id}`; replacing
`{id}` with `r17` gives a concrete path. The template itself is a description,
not the literal identifier of every reservation. Full address components belong
to the next lesson.

An **operation** is a particular exposed action and its behavior. In OpenAPI's HTTP
model, operations are described for methods on paths. Thus `GET /reservations` and
`POST /reservations` can describe different operations at one path. Here `POST`
submits a reservation request; do not infer every POST in every API creates a
record without reading its contract. The
[OpenAPI path/operation tutorial](https://learn.openapis.org/specification/paths.html)
shows the separation of path-level information and individual operations.

A server **route** is a rule mapping an incoming request to handling behavior,
often based on method and path. A **handler** is the code selected to handle that
request. Frameworks may organize handlers into controllers, which group related
request handling. For example,
[NestJS's controller introduction](https://docs.nestjs.com/controllers)
explains routing as selecting request handling. These are implementation concepts;
the public contract does not necessarily expose the controller's class name or
folder path. No NestJS setup or adapter behavior is needed for this reading task.

This route is also distinct from an IP forwarding route or a UI navigation route.
Context identifies the boundary. A proxy can map a public path to a different
internal path; an address in a consumer document need not match a source filename.
State which side of that mapping you are discussing.

### 3) **Read the contract beyond a successful example**

An **API contract** states how provider and consumer interactions are meant to
work: operations, accepted input, output meaning, error conditions and relevant
constraints. A field's **shape** describes its structure and value types; its
**semantics** describes what those values mean. The string `status` needs documented
meanings, not merely a declaration that it is text.

Use this **fictional contract card**, written as explanatory text rather than an
OpenAPI document or runnable server configuration:

```text
Provider: the booking service in a test scenario; no real service address.
GET /reservations/{id}: return the stored reservation, or a documented not-found
result when it does not exist. The consumer supplies the reservation identifier.
POST /reservations: submit roomId and date. The service checks access and current
availability. Accepted requests return a reservation identifier and status pending.
Pending means the request is recorded but approval has not completed.
Unavailable rooms produce a documented conflict result instead of a reservation.
This excerpt makes no repeat-submission or completion-time guarantee.
```

There are two operations in this card, on two path templates. A concrete GET might
refer to `/reservations/r17`; POST refers to the collection path. Neither the path
name nor receipt of a response alone establishes that approval completed. The card
explicitly defines accepted/pending as recorded but not yet approved. A consumer
showing “Approved” immediately would misrepresent that declared result.

Now vary the excerpt: remove the sentence defining pending. You still know the
field's name and possible label, but its business meaning is unspecified. Ask for
that meaning before implementing the user message. Likewise, the excerpt does not
say what a repeated POST does or how long approval takes. A happy-path example
must not be promoted into a missing guarantee.

An **API specification** is an artifact describing the interface. An **API reference**
helps a reader look up its operations and details. **OpenAPI** is a standard for
describing HTTP APIs; **OAS** expands to **OpenAPI Specification**. The current
[OpenAPI 3.2.1 specification](https://spec.openapis.org/oas/v3.2.1.html), published
2026-09-10 and checked 2026-10-18, describes paths, operations, inputs and responses.
This description version is separate from a service's own product/API version.
Tool compatibility still needs checking for the particular feature set used.

**Swagger** is a name associated with API tooling and the specification's history;
it is often used informally for a generated documentation UI. Ask whether “update
Swagger” means changing the description, regenerating a UI or changing server
behavior. An attractive reference page does not prove a deployed implementation
conforms to its description. A generated client or a checked type also does not
establish that every received value meets the runtime contract.

### 4) **Common confusion**

Endpoint, route and operation can be colloquial synonyms, but the questions remain
different: where is the capability exposed, which action is requested and how does
the implementation choose code? State method, location and intended result when
those distinctions affect a report.

A specification's completeness and the service's correctness are also separate.
A missing error description is a contract gap; an implementation returning a result
contrary to a clear description is a behavior mismatch. Investigate the actual
version and evidence before deciding which artifact needs changing.

### 5) **Performance note**

Documenting a contract has no direct effect on request latency. Route selection,
input handling, application work and communication may contribute costs, but
counting endpoints or choosing a specification format does not measure them. The
card provides no response-time guarantee or benchmark. A performance contract
would need its own operation, workload, measurement boundary and conditions.

### 6) **Mentor note**

Ask what the consumer may show after POST returns pending, then remove the pending
definition. A strong answer initially explains the recorded/not-approved state
and subsequently requests the missing semantics. Follow by asking whether the
same path can have multiple operations and why a documentation screenshot cannot
prove a successful live integration.
