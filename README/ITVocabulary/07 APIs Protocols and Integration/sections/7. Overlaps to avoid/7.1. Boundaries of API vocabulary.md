## 7.1. Boundaries of API vocabulary

Being able to annotate an exchange is a useful skill. It does not establish that
you can implement a secure, compatible service or operate its dependencies.
Use this domain to identify the contract and the missing evidence, then route the
detailed question to its owner. A precise learning boundary prevents an unfamiliar
term from turning every diagnosis into an entire framework course.

### 1) **Route interpretation questions to their existing conceptual owners**

The following routes revisit full explanations. Use their specific examples when
you need the meaning, rather than creating a second definition in each API note.

| Question | Existing owner and boundary |
|---|---|
| Is this an endpoint, operation, routing rule or description? | [Interface and contract](<../1. Interfaces and contracts/1.1. APIs endpoints routes operations and contracts.md>) identifies the role; it does not implement the route. |
| What identifies the resource, and which addresses share an origin? | [Resources and addresses](<../1. Interfaces and contracts/1.2. Resources representations URIs URLs and origins.md>) separates identification and comparison from reachability. |
| What do method, status and content establish? | [HTTP messages](<../2. Reading HTTP/2.1. Requests responses methods headers status codes and bodies.md>) owns result interpretation, including standardized QUERY. |
| Is the response fresh, validated or a selected variant? | [Version and caching vocabulary](<../2. Reading HTTP/2.2. HTTP versions caching validators and content negotiation.md>) owns HTTP reuse policy and representation matching. |
| What kind of interface is REST, GraphQL, gRPC or SOAP? | [Styles and technologies](<../3. Styles formats and schemas/3.1. REST RPC GraphQL gRPC and SOAP.md>) distinguishes categories and contract artifacts. |
| Did bytes parse and satisfy a data rule? | [Payloads and schemas](<../3. Styles formats and schemas/3.2. Payloads JSON XML YAML Protobuf and schemas.md>) separates syntax, structure and business acceptance. |
| Who initiates updates, and what follows a disconnect? | [Interaction patterns](<../4. Interaction patterns/4.1. Polling webhooks SSE and WebSocket.md>) identifies polling, callback and stream paths. |
| What does repetition, continuation or a limit promise? | [Operation behavior](<../5. Contract behavior and integration risks/5.1. Safe idempotent paginated and rate-limited operations.md>) owns scoped API interpretation, not a production resilience algorithm. |
| Can browser code read the response, and was the request sent? | [CORS boundaries](<../5. Contract behavior and integration risks/5.2. Same-origin policy CORS credentials and API boundaries.md>) separates browser sharing from application permission. |
| How should these observations become a diagnosis? | [Integrated contract reading](<../6. Applied contract reading/6.1. Translate an API specification and failed integration.md>) supplies a complete worked evidence packet. |

A source can use a narrower or looser meaning than another source. Preserve the
actual contract's scope in your notes. For example, a team's “endpoint” may mean
a URL or a method/URL pair; record which one rather than silently treating the two
as identical. The earlier language domain owns that general ambiguity habit.

### 2) **Choose implementation and deeper guarantees as separate learning goals**

Language-specific serialization remains with
[JavaScript data exchange](<../../../../JavaScript/16 JSON Serialization and Data Exchange/sections/5. Beyond JSON structuredClone and data exchange/5.2. Data exchange patterns APIs NDJSON binary and base64.md>).
TypeScript's [static versus runtime boundary](<../../../../TypeScript/01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.2. Static checking vs runtime reality trust but verify.md>)
explains why a declared type does not check an actual response. Those owners can
develop the mechanisms without repeating every general HTTP definition here.

A browser failure before an HTTP response may need the earlier
[network diagnosis route](<../../../05 Networks and the Internet/sections/7. Applied diagnosis/7.1. Describe a name connection or timeout failure.md>).
Do not explain it solely by a JSON schema or CORS label. Conversely, a returned
contract mismatch is not evidence that DNS failed.

For deeper study, separate these intended outcomes:

- Implementing routes, request validation, error handling and protocol-specific
  clients belongs to API Design and the relevant backend/platform tracks. Framework
  mechanics are part of that implementation goal, not a prerequisite for reading
  the messages in this domain.
- Coordinating workers, retaining operation identity and recovering partial effects
  requires the later concurrency/distributed-systems vocabulary and its specialist
  implementation study. The word idempotent alone does not supply those mechanisms.
- Establishing identity, access rules and protection against unwanted actions
  requires the later security vocabulary and detailed security engineering.
  CORS sharing permission alone does not resolve that problem.
- Choosing database operations or proving recovery and durability requires data
  and reliability study. An API's successful response is evidence only under its
  stated application contract.

These are future learning routes in the approved curriculum and root plan, not
links to unpublished lessons or a claim that those implementation tracks exist.
The next vocabulary domain develops databases and data paths, using this domain's
contract-reading skills rather than requiring a running backend.

### 3) **Turn a mixed guarantee claim into a focused handoff**

Read this **constructed proposal**:

> Our gRPC service uses Protobuf and a typed client, so all received values are
> business-valid. Every creation retry gets a new operation ID. A browser can read
> the response because its origin is allowed, so permission to create is covered.

A useful review separates three claims. First, identify the message definition,
actual decoding/checks and business rule. A typed client does not establish current
inventory or the actor's authority. Second, ask for the repetition contract and
the identity of one user intention. New IDs on every attempt do not preserve an
operation ID for duplicate recognition under a contract that requires reuse.
Third, identify the actual authorization decision; browser response access is a
different boundary.

A clear handoff could say:

> The interface names describe the proposed communication and data tooling. We
> still need the executed business checks and action-permission rule. For retries,
> specify how attempts of the same creation are identified, retained and recovered.
> Keep browser response sharing as a separate policy with its own evidence.

This does not demand replacing gRPC or Protobuf. It identifies the missing contracts
and mechanisms. If the author adds a documented retry rule, inspect its account,
operation, content and retention scope; that improves the retry claim without
proving the business-validity or permission claims. Each conclusion changes only
when its own evidence changes.

For practice, rewrite the proposal in one sentence for a product teammate. A good
answer might be: “The proposed communication tools do not yet demonstrate correct
reservation decisions, duplicate handling or access checks; those behaviors need
explicit rules and verification.” The answer need not recite every acronym to
preserve the actual concern.

### 4) **Common confusion**

A vocabulary owner is the place that explains a concept, not necessarily the team
that operates a production component. Route learning by topic; route an actual
incident by the observed system and agreed responsibility.

Naming a deeper subject does not mean every reader must finish it before using
this domain. You can accurately report “sent request, unreadable response, unknown
effect” now, while recognizing that implementing recovery needs further study.

### 5) **Performance note**

The ownership map has no direct runtime effect. Its practical value is avoiding
misdirected investigation and unsupported claims. Choosing a transport, schema
library or retry design can affect operational cost, but this routing exercise
measures none of them. Carry any performance question to its actual workload and
measurement boundary instead of inferring speed from an interface label.

### 6) **Mentor note**

Ask the learner to choose one owner for each sentence of the proposal and write
one evidence question for it. A strong answer routes format/type, repetition and
access claims separately and explains why one new document does not prove all
three. Have them translate the review for a teammate who needs the decision,
not an acronym inventory.
