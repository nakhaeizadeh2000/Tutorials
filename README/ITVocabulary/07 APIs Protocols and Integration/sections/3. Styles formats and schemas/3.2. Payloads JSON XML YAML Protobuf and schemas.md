## 3.2. Payloads JSON XML YAML Protobuf and schemas

A service can receive valid JSON that violates its reservation contract.
`{"seats":"2"}` parses, but a contract expecting an integer need not accept the
string `"2"`. Separate the representation, the operation that reads it and the
rules that make it acceptable for this application.

### 1) **Follow data from a value to a transmitted representation**

A **payload** is the content carried at a stated protocol boundary. In an HTTP
exchange, people often mean the application content in the body. Be specific:
a packet's payload can contain the HTTP message, while the HTTP body contains
application data. The [network unit lesson](<../../../05 Networks and the Internet/sections/2. Moving and addressing data/2.1. Packets frames protocols and network layers.md>)
owns that nesting model.

**Serialization** converts structured values into a representation suitable for
storage or transmission. **Deserialization** reconstructs values from that
representation. **Parsing** interprets syntax to produce a structured result;
these operations often overlap in a library's API. An **encoder/decoder** or
**codec** implements a particular conversion. The word encoding needs context:
JSON serialization, UTF-8 text encoding and gzip compression are different steps.

For a constructed HTTP request, an application may serialize a seat count into
JSON text, encode that text as UTF-8 bytes and send those bytes as content with
`Content-Type: application/json`. HTTP carries the message; JSON describes the
data representation; UTF-8 maps its text to bytes. Changing to HTTP/3 does not
turn JSON into Protobuf. Changing the content label without converting the bytes
does not convert the format either.

### 2) **Recognize formats without confusing their data and definition files**

| Format | Expansion or name | Useful recognition and limit |
|---|---|---|
| JSON | JavaScript Object Notation | Text values such as objects, arrays, strings, numbers, booleans and null; not executable JavaScript |
| XML | Extensible Markup Language | Marked-up document structure with elements and attributes; well-formed syntax alone does not establish application validity |
| YAML | YAML Ain't Markup Language | A data serialization language with mappings, sequences and scalars; block indentation can express structure |
| Protobuf | Protocol Buffers | Typed message definitions and serialization tooling; `.proto` source is different from a serialized binary message |

[JSON's standard](https://www.rfc-editor.org/rfc/rfc8259.html) describes a
language-independent format. An object member name is a string; numbers and
strings are distinct. A JSON text need not be an object: `null` and `42` are also
JSON values. Native language objects can have capabilities that JSON cannot
represent directly. JavaScript's full parsing/stringifying mechanics remain in
its existing track.

The [XML 1.0 specification](https://www.w3.org/TR/xml/) distinguishes well-formed
structure from additional validity constraints. Tags such as `<seats>2</seats>`
do not, by spelling alone, establish that the application has validated a positive
integer. XML is not inherently SOAP; SOAP defines an additional messaging contract.

[YAML 1.2.2](https://yaml.org/spec/1.2.2/) describes a representation model and tag
resolution as well as visible syntax. A **scalar** is a single value, contrasted
with a collection. This illustrative YAML fragment uses a mapping and an integer
under the usual Core schema; it is a reading artifact, not a configuration to apply:

```yaml
reservation:
  id: "r17"
  seats: 2
```

Indentation nests `id` and `seats` under `reservation`. Quoting `"2"` instead would
express a string here. When troubleshooting conversion, state the parser version
and schema/settings; do not assume every YAML loader applies identical resolution
rules. YAML's tag-resolution meaning of **schema** also differs from a complete
application validation schema.

The [Protobuf overview](https://protobuf.dev/overview/) separates definitions,
generated code, libraries and serialized data. A **field number** identifies a
message field; it is not that field's value. The project now also uses **Editions**
to select behavior defaults; its [Editions overview](https://protobuf.dev/editions/overview/)
lists 2024 as the latest released edition when checked 2026-10-18. An edition year
is not a compiler package version or proof of every tool's support.

This **illustrative definition**, not an executed compiler example, describes
fields and their numbers:

```proto
edition = "2024";

message Reservation {
  string id = 1;
  uint32 seats = 2;
}
```

`1` identifies `id`; `2` identifies `seats`. Neither assigns a reservation ID or
seat count. A serialized message contains values interpreted with its message
definition. Do not rename the definition file to `.bin` and call that serialization.
A successful decode still does not establish a business rule such as “at least
one seat,” nor permission to reserve it.

### 3) **Distinguish parsing schema checks and business acceptance**

An **application schema** describes expected structure and constraints, such as
required fields, value types and allowed ranges. **Schema validation** checks an
instance against those rules. **JSON Schema** is a specific schema technology,
distinct from JSON itself. Its [introductory guide](https://json-schema.org/understanding-json-schema/about)
explains why knowing the outer format is insufficient. A schema still cannot
establish every fact about the outside world: available seats can change after a
structurally valid request is constructed.

Run this complete offline example with **CPython 3.14.4**, standard library only.
Save it as `payload_checks.py` and run `python3 payload_checks.py`. No service or
account is needed. `matches_contract` is a small handwritten check for this
example, not a JSON Schema implementation or a production security validator.
The example contract requires exactly one property, `seats`, holding a Python
integer from 1 through 4 after JSON decoding.

```python
import json


def matches_contract(value):
    return (
        type(value) is dict
        and set(value) == {"seats"}
        and type(value["seats"]) is int
        and 1 <= value["seats"] <= 4
    )


samples = [
    ("integer", '{"seats":2}'),
    ("string", '{"seats":"2"}'),
    ("boolean", '{"seats":true}'),
    ("zero", '{"seats":0}'),
    ("broken", '{"seats":'),
]
for label, text in samples:
    try:
        value = json.loads(text)
    except json.JSONDecodeError:
        print(label, "syntax error")
    else:
        print(label, "parsed; contract", matches_contract(value))
```

Expected output:

```text
integer parsed; contract True
string parsed; contract False
boolean parsed; contract False
zero parsed; contract False
broken syntax error
```

`json.loads` parses the text. The helper separately checks the decoded value.
Short-circuiting `and` prevents the later property access when the earlier shape
check fails. `type(...) is int` deliberately excludes booleans, which Python
otherwise treats as an integer subtype. The malformed input reaches the caught
syntax error; the string, boolean and zero inputs pass parsing but fail the
specific contract. The [Python JSON reference](https://docs.python.org/3.14/library/json.html)
documents the decoder and error behavior. This observes the supplied samples,
not universal strict JSON conformance for every possible input.

For practice, change the integer input to `{"seats":5}`. It should still parse but
fail the range check. If `{"seats":2}` passes, can the service promise two seats
are available? No. That needs current business-state and access decisions at the
operation boundary. Parsing and structural acceptance do not prove those facts.

### 4) **Common confusion**

A JSON `null`, a missing property and an empty string are different representations.
The application contract decides which, if any, are acceptable. Converting every
unexpected value to a string can hide the mismatch rather than repair it.

“Schema validated” needs the actual schema, dialect and validator settings.
Likewise, an example payload is evidence of one shape, not an exhaustive contract.
A Protobuf definition and a YAML document can both be text files while serving
different roles; inspect their intended consumer before classifying the artifact.

### 5) **Performance note**

Serialization, decoding and validation require work and memory. Text versus binary
alone does not establish cost: value distribution, field selection, encoding,
compression and library behavior matter. Protobuf messages are not automatically
compressed, and smaller wire size does not prove lower total request latency.
The executed example checks correctness distinctions only; no format benchmark
or large-input memory test is claimed.

### 6) **Mentor note**

Ask why the string case reaches the contract check but the broken case does not.
Then ask what a passing integer result proves about inventory. A sound answer
names three boundaries: syntactic interpretation, this local shape/range contract
and the separate decision against current application state. Have the learner
point to the responsible check rather than merely recite “validate input.”
