## 3.1. REST RPC GraphQL gRPC and SOAP

“Which protocol is better: REST or GraphQL?” mixes categories and hides the task.
First identify what the name describes. Then ask how this particular interface
represents actions, chooses data and communicates failures. One application can
expose more than one kind of interface to different consumers.

### 1) **Separate architectural style interaction model and concrete technology**

**REST** expands to **Representational State Transfer**. It is an architectural
style: constraints on how components interact. In Fielding's original model,
client/server separation, stateless interaction, caching, a uniform interface and
layers work together; code on demand is optional. **Stateless** here concerns
request context: the server does not rely on stored conversational session context
to interpret the next request. It does not prohibit storing reservations or other
resource state.

A **uniform interface** includes identifying resources, manipulating representations,
self-descriptive messages and using hypermedia to guide application state. Here,
**hypermedia** means representations can convey links or controls for possible
next interactions, interpreted using agreed meanings. A JSON body and a plural
URL alone do not demonstrate all these constraints. Read the
[original REST derivation](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm)
for the reasoning. Teams often use “REST API” more loosely for resource-oriented
HTTP APIs; clarify the claimed properties rather than turning naming into an argument.

**RPC** means **remote procedure call**. The interface presents named procedures
or methods to invoke remotely, with parameters and results. “Call
`GetReservation(r17)`” emphasizes the operation; “retrieve the representation of
`/reservations/r17`” emphasizes an addressable resource under a common method.
RPC is a family of interaction models, not one serialization format. An RPC can
use HTTP; HTTP usage alone does not establish a REST design.

Martin Nally's original [REST/RPC discussion](https://cloud.google.com/blog/products/application-development/rest-vs-rpc-what-problems-are-you-trying-to-solve-with-your-apis)
is useful for comparing procedure-oriented and resource-oriented interfaces and
asking which integration problem matters. Its efficiency preferences are design
judgments, not evidence that one family is always faster or easier to change.

| Name | Category to recognize | What still needs clarification |
|---|---|---|
| REST | Architectural style | Which constraints the actual interface follows |
| RPC | Remote operation model | Procedure contract, encoding and failure semantics |
| GraphQL | API query language, type system and execution model | Exposed fields, execution rules and transport arrangement |
| gRPC | A concrete RPC framework/ecosystem | Service definition, supported methods and client/platform capabilities |
| SOAP | An extensible messaging protocol/framework | Version, binding, application messages and extensions |

The category is a starting point for reading, not a ranking. “Our system uses
HTTP, JSON and RPC-style operations” can be a more useful description than an
unsupported claim of REST conformance.

### 2) **Recognize the contract artifacts behind GraphQL gRPC and SOAP**

**GraphQL** exposes a schema of types and fields and executes operations against
it. A schema describes the exposed structure and rules; it does not mean every
client can access every field. A **query** requests data, a **mutation** expresses
an operation intended to change data, and a **subscription** supports a stream of
results over time. The originating [mutation](https://graphql.org/learn/mutations/)
and [subscription](https://graphql.org/learn/subscriptions/) guides distinguish
these operation kinds. The particular schema and implementation define their business
meaning. The [GraphQL introduction](https://graphql.org/learn/introduction/)
shows field selection and explains that GraphQL is independent of a specific
database. It is not a way to send arbitrary SQL directly to storage.

This **constructed GraphQL reading fragment** assumes the service schema exposes
`reservation(id: ...)` with `id` and `status` fields. It is not a runnable service
or an observed response:

```graphql
query ReservationSummary {
  reservation(id: "r17") {
    id
    status
  }
}
```

`ReservationSummary` names this client operation. The nested selection asks for
two exposed fields. It does not request every reservation attribute, establish
permission to read them, or reveal how many backend calls execution requires.
Adding an unknown field should be evaluated against the schema; its presence in
a client's source code does not add it to the service contract.

**gRPC** supplies machinery for remote methods. A service definition describes the
methods and input/output messages. An **IDL**, or **interface definition language**,
is a language used to express that contract. gRPC commonly uses Protocol Buffers
for the IDL and message serialization. A generated **client stub** is local code
that prepares the remote call; calling it does not turn network failure into an
ordinary local function result. See the [gRPC introduction](https://grpc.io/docs/what-is-grpc/introduction/).

Recognize **unary** calls with one request and one response, **server streaming**
with multiple response messages, **client streaming** with multiple request
messages, and **bidirectional streaming** with streams in both directions.
The [gRPC core concepts](https://grpc.io/docs/what-is-grpc/core-concepts/)
separate these shapes. A generated method signature alone does not establish its
business effects, deadline policy or safe retry behavior. Protobuf is a format
and contract technology; it is not another name for gRPC.

**SOAP 1.2** defines a structured messaging framework using XML technologies.
An **envelope** contains the message, with an optional SOAP header and a required
SOAP body. A **fault** reports a SOAP-level failure. A **binding** specifies how
the messaging framework uses an underlying protocol, such as HTTP. SOAP is not
limited to one transport or to RPC-style interactions. The
[SOAP 1.2 specification](https://www.w3.org/TR/soap12-part1/)
explains these boundaries; security and reliability extensions are additional
contracts, not automatic properties of every SOAP message. SOAP was historically
expanded as Simple Object Access Protocol; SOAP 1.2 treats the name as a name,
not an acronym to expand into its current definition.

### 3) **Compare interfaces without inventing guarantees**

Consider three **fictional interface notes** for the same reservation system:

| Note | Supported reading | Unsupported inference |
|---|---|---|
| A: GET `/reservations/r17` returns a JSON representation | An HTTP resource retrieval with JSON content | Complete REST constraints follow from this one example |
| B: `ReservationService.GetReservation` is a unary gRPC method | One request and one response under its service contract | The network cannot fail because a client stub was generated |
| C: The GraphQL fragment above selects `id` and `status` | The client selects two fields exposed by the assumed schema | Only two database reads occur, or every result is authorized |

The useful next question for A is which constraints and representation controls
the provider documents. For B, ask how failures and unknown outcomes are represented.
For C, ask which execution and access rules apply. If A instead documents a named
`ApproveReservation` procedure carried over HTTP, describing that interaction as
RPC-style explains more than assuming every HTTP endpoint is RESTful.

When comparing a candidate design, state the consumer tasks, available clients,
required message shapes and compatibility obligations first. Then compare actual
contracts and measured behavior. A label supplies neither the user's requirements
nor evidence that the implementation meets them.

### 4) **Common confusion**

REST does not require JSON, and XML content alone does not make a message SOAP.
GraphQL's graph of exposed fields does not require a graph database. A gRPC method
and a GraphQL operation can both use underlying HTTP arrangements while exposing
different application contracts.

“Stateless” also does not mean “no data changes.” A server can persist a reservation
while requiring each request to carry its own interpretation context. Distinguish
stored resource data from the conversational dependency being discussed.

### 5) **Performance note**

Field selection can reduce returned data while execution still performs substantial
work. Small RPC calls can become expensive if a task needs many network round trips.
Resource reuse depends on the actual cache policy. These are questions to measure,
not a universal performance order among REST, GraphQL, gRPC and SOAP. The examples
here inspect interface descriptions; no service throughput or payload benchmark
has been run.

### 6) **Mentor note**

Ask the learner to explain note B to someone who knows local functions but not
RPC. A strong explanation includes the remote boundary and possible failure,
not only the generated method name. Then give note A without its JSON claim:
the retrieval remains HTTP, while the representation format is now unknown.
This tests whether the learner separates interaction meaning from encoding.
