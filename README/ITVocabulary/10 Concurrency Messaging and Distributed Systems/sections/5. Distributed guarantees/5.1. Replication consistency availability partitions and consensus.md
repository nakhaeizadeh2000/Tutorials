## 5.1. Replication consistency availability partitions and consensus

Two machines hold copies of the same booking status. One accepts a change, but
the other cannot hear from it. What may the second machine tell a reader? The
answer depends on the operation's contract, not simply on having replicas.

Read the data-copy, transaction and timeout lessons first. This lesson uses
constructed histories, not a deployed database or consensus test. Sources checked
2026-10-19 establish conceptual models; no product label supplies all these
properties automatically.

### 1) **Separate copied state from the observations a contract permits**

**Replication** maintains copies through a transfer and application process.
Its storage roles and acknowledgment stages are explained in the
[data-copy lesson](<../../../08 Databases Storage and Data Pipelines/sections/5. Storage and copies/5.2. Backups snapshots replication sharding and restores.md>).
Here the new question is **consistency**: which combinations of operations and
observed results are allowed? An operation history records invocations and
responses, including their ordering. Ask which object, readers, writers and
operation types the model covers.

For a simple read/write object, **linearizability** means each operation appears
to occur at one instant between its invocation and response, respecting real-time
order. If a write finishes before a read starts, that read must follow the write
in the apparent order. The object's own rules determine the result. With no
intervening write, reading an earlier value would violate this contract.
[Jepsen's linearizability explanation](https://jepsen.io/consistency/models/linearizable)
also emphasizes that the scope of an object can vary. A guarantee for one booking
key does not automatically cover an operation changing several keys.

“Strong consistency” is too loose to substitute for that definition. Request the
named model and covered operations. Nor is distributed consistency the same as
[ACID consistency](<../../../08 Databases Storage and Data Pipelines/sections/4. Transactional behavior/4.1. Transactions ACID isolation locks and deadlocks.md>):
preserving a booking invariant and deciding what a later reader may see are
separate questions.

**Eventual consistency** promises convergence under its assumptions: after
updates stop and required communication and recovery can proceed, replicas
ultimately agree on the resolved state. Concurrent conflicting updates also need
a resolution rule. The word “eventual” alone gives no fixed convergence deadline
and does not promise that a writer immediately reads its own accepted change.
**Read-your-writes** is an additional observation guarantee for that writer within
a defined scope. Werner Vogels's original
[eventual-consistency article](https://www.allthingsdistributed.com/2008/12/eventually_consistent.html)
separates these client observations. Its 2008 product descriptions are historical,
not current service contracts.

For example, changing a profile label and seeing the old label briefly can be
permitted by one contract. That does not establish that the same contract suits
admitting a booking against shared capacity. Decide what the operation needs;
“eventual” does not mean arbitrary permanent corruption is acceptable.

### 2) **Read a partition timeline before applying CAP terminology**

A **network partition** prevents communication between groups of participants
that may still be running. It differs from deliberately partitioning a dataset
into shards. A timeout alone cannot establish whether a message was lost,
delayed, or blocked by a particular fault.

Consider this fictional read/write register, a single stored value named `status`.
It starts as `pending`. The packet explicitly provides this order:

| Step | Given observation |
|---|---|
| 1 | A and B both hold `pending`. |
| 2 | Communication between A and B stops and stays unavailable. Clients can still reach each side. |
| 3 | A accepts `write(confirmed)` and returns success to its client. |
| 4 | After that success, another client starts `read()` through B. |
| 5 | B returns its local value, `pending`. No other write occurred. |

The returned value in step 5 violates the stated linearizable-register contract.
The successful write precedes the later read, and no later write restores
`pending`. This conclusion uses the packet's completed-operation order, not a
comparison of possibly inaccurate server timestamps.

Change one condition: start the read while the write is still in progress. The
operations now overlap. An old value can be consistent with linearizability if
the read is placed before the write in the apparent order. That one result alone
therefore no longer establishes a violation. Timing is part of the claim.

**CAP** names consistency, availability and partition tolerance. In the relevant
read/write model, C is linearizability. A requires every request to a nonfailed
participant eventually to receive the operation's response; it is not an uptime
percentage or a bounded-latency promise. P admits communication failures that
can keep groups separated. Under that fault model, C and A cannot both be
guaranteed for this shared object. Gilbert and Lynch's
[Perspectives on the CAP Theorem, section 2](https://groups.csail.mit.edu/tds/papers/Gilbert/Brewer2.pdf)
states the model and explains the information a separated reader lacks.

B cannot discover A's new value from a permanently silent link. Waiting
indefinitely or refusing the read can preserve the consistency contract, but
fails CAP availability for that operation. Returning an error is useful failure
reporting; it does not count as successfully answering the requested register
read. Returning the stale value permits progress under a weaker contract.

“Pick any two” hides the fault assumption. Selecting a product label cannot
prevent the link from failing. State the response policy during separation,
including which operations stop and which may return weaker results. Different
operations can have different policies; a cached public description and a capacity
reservation need not make the same choice.

### 3) **Distinguish consensus decisions from a replica count**

**Consensus** is agreement on a proposed value under specified validity,
agreement and progress conditions. Repeated agreement can establish a shared log
order for a replicated state machine, where copies apply agreed operations.
**Raft** and **Paxos** are names to recognize in this context, not interchangeable
configuration switches or proofs that every application operation is correct.

A **quorum** is a set of participants sufficient for a protocol decision. In a
fixed three-voter Raft group, a majority is two. A **leader** coordinates relevant
protocol work; **leader election** selects that role through protocol rules.
A missed heartbeat by itself does not establish that another server has ceased
to hold authority. The original
[Raft paper, sections 2 and 5](https://raft.github.io/raft.pdf)
explains majority-based progress and election/log restrictions under its
non-Byzantine crash-failure model. Byzantine faults include participants behaving
arbitrarily; this is a different assumption from merely stopping and recovering.

Use this constructed decision card, with fixed voters A, B and C. It concerns new
log entries requiring a majority, not every possible cached read:

| Connectivity | What the count establishes |
|---|---|
| A and B communicate; C is isolated | A/B contain two voters. This side can support progress if election, timing, storage and client-access conditions also hold. |
| A, B and C are all separated | Each group has one voter. No group can form the required majority for a new entry. |
| C alone declares itself leader | The declaration does not supply a majority or permission to commit conflicting entries. |

An intersection between majorities helps protocols carry decisions forward, but
counting two copies is not the whole safety argument. Election, log and membership
rules still matter. Raft even distinguishes an older entry being present on a
majority from the conditions needed to commit it. Do not turn a useful counting
exercise into a new consensus algorithm.

Google SRE's original
[critical-state chapter](https://sre.google/sre-book/managing-critical-state/)
connects consensus with coordination failures and operational costs. Its cases
motivate checking authority and failure assumptions, rather than inferring
correctness from the number of healthy processes.

Practice: a proposal says, “Three replicas and consensus mean all clients always
see the latest booking and all writes always succeed.” Give a precise review.
Three replicas alone establish neither promise. Ask which reads use the agreed
state and how their authority is verified, what write completion acknowledges,
and what happens when a client can reach only the isolated voter. Consensus
safety can be preserved while that client's write makes no progress. A separate
lagging read path can also weaken the user-visible contract. Inspect that path
before claiming linearizability for the whole API.

### 4) **Common confusion**

“Consistent” does not mean every physical copy changes at the same instant.
Linearizability constrains observable operation histories; an implementation may
keep lagging copies from answering particular reads. Conversely, showing equal
values at one moment does not prove all future histories meet a model.

A majority of running machines is not necessarily a communicating quorum. Two
healthy voters on separated networks cannot exchange the messages needed for
their protocol decision. Likewise, safety and progress differ: refusing a new
write can avoid a conflicting decision while leaving the requested work undone.

### 5) **Performance note**

Consensus-based replication can require communication and storage work before
an operation completes. Quorum placement and slow required responses affect that
path; adding replicas does not automatically reduce latency or multiply write
capacity. A weaker read contract may permit another path, but its actual cost
still depends on implementation and workload. These histories establish no
latency, convergence-time or availability measurement. Specify the operation and
failure case before comparing costs.

### 6) **Mentor note**

First ask the learner why `pending` is wrong in the non-overlapping timeline.
Then move the read earlier. A sound explanation changes with the operation order
and does not merely repeat “replication lag.” Next separate all three voters and
ask whether a refusal disproves consensus safety. The learner should distinguish
preserving an agreed decision from guaranteeing progress, and name the missing
assumptions behind an “always available” claim.
