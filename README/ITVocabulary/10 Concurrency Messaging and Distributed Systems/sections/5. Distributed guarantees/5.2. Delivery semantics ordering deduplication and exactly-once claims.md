## 5.2. Delivery semantics ordering deduplication and exactly-once claims

A booking event reaches a report consumer. The consumer adds two seats to the
report, then stops before acknowledging the delivery. If the event arrives again,
should the report add two more? Receiving a repeated message and producing a
repeated business effect are different events.

Read the message-lifecycle and transaction lessons first. Product references were
checked 2026-10-19. The SQLite example is a local observation; the broker and email
failure timelines are constructed, not live integration tests.

### 1) **Name what is counted and where the guarantee ends**

**Delivery semantics** describe allowed delivery outcomes under a contract and
failure model. A **redelivery** presents an earlier message again. Distinguish
publication into a broker, delivery to a consumer, execution of a handler, and
committed effects visible to another participant.

| Label | Meaning at the named boundary | What it does not establish |
|---|---|---|
| **At-most-once** | Zero or one occurrence; omissions are possible | Every accepted input produced its required result |
| **At-least-once** | One or more occurrences under the contract's recovery assumptions | Repeated attempts cannot duplicate an effect |
| **Exactly-once** | One occurrence or one reflected result, as precisely defined by the contract | The handler ran once, or every external action happened once |

An at-least-once promise needs retention, retry and recovery assumptions. It is
not protection against permanent loss of every copy, abandonment of a failed
consumer, or every imaginable outage. **End-to-end** also needs named endpoints:
from an accepted source record to which externally observable result?

Use this fictional packet. Event `e17` represents two seats added to a report.
The report starts at zero. A delivery runs an unconditional addition, the database
commit succeeds, the acknowledgment is not recorded, and the broker redelivers
`e17`. Running the addition again makes the report four. The second delivery is
compatible with at-least-once delivery, while the business report is wrong for
one event. The [acknowledgment lesson](<../3. Messages and streams/3.2. Streams batches consumers acknowledgments and dead-letter queues.md>)
owns the receipt/processing distinction; the new issue is repeated effects.

Moving acknowledgment before the database commit creates another gap: a stop
between them can leave no report change and no normal redelivery. Reordering two
independent steps does not make them atomic. A review must inspect the recovery
contract across that boundary.

### 2) **Observe deduplication by identity within one transaction**

**Deduplication** recognizes repeated instances of the same logical input and
suppresses selected repeated work or effects. **Idempotent processing** preserves
the intended outcome when the same operation is repeated. Deduplication is one
way to obtain that property; some operations already have it. An **idempotent
consumer** preserves that intended outcome across repeated inputs. The
[API idempotency lesson](<../../../07 APIs Protocols and Integration/sections/5. Contract behavior and integration risks/5.1. Safe idempotent paginated and rate-limited operations.md>)
explains operation identity and scope in requests.

For this report, use an event ID agreed with the producer. The consumer must
record that identity and its database effect in the same transaction. Recording
only a marker before applying the effect can suppress work that never succeeded;
recording it later leaves a repetition gap. Chris Richardson's original
[idempotent-consumer explanation](https://microservices.io/post/microservices/patterns/2020/10/16/idempotent-consumer.html)
connects the failure gap with atomic message-ID tracking. Other designs exist;
a separate marker table is not a requirement for every storage system.

Use the SQLite 3.54.1 executable from the query lesson in a new example folder.
Save this complete file as `deduplicate_report.sql` and run
`./sqlite3 :memory: < deduplicate_report.sql`. It uses one connection, one report
row and one consumer's retained event identities. Each distinct event in this
small input adds exactly two seats. No broker is connected.

```sql
.bail on
.headers off
.mode list
CREATE TABLE applied_events (event_id TEXT PRIMARY KEY);
CREATE TABLE report (total INTEGER NOT NULL);
INSERT INTO report VALUES (0);

BEGIN;
INSERT INTO applied_events VALUES ('e17')
  ON CONFLICT(event_id) DO NOTHING;
UPDATE report SET total = total + 2 WHERE changes() = 1;
COMMIT;
SELECT total FROM report;

BEGIN;
INSERT INTO applied_events VALUES ('e17')
  ON CONFLICT(event_id) DO NOTHING;
UPDATE report SET total = total + 2 WHERE changes() = 1;
COMMIT;
SELECT total FROM report;

BEGIN;
INSERT INTO applied_events VALUES ('e18')
  ON CONFLICT(event_id) DO NOTHING;
UPDATE report SET total = total + 2 WHERE changes() = 1;
COMMIT;
SELECT total FROM report;
```

Observed output:

```text
2
2
4
```

The first insert stores `e17`. SQLite's
[`ON CONFLICT ... DO NOTHING`](https://sqlite.org/lang_upsert.html)
skips an insert that conflicts with the named uniqueness rule. Its
[`changes()` function](https://sqlite.org/lang_corefunc.html#changes)
reports the immediately preceding completed data-changing statement's row count
in this example. After the new event insert that count is one, so the guarded
update adds two. After the duplicate insert it is zero, so the report stays two.
The new identity `e18` is accepted and makes the report four. Do not insert another
data-changing statement between the ID insertion and this guard: it would change
what the count means.

The two distinct events happen to carry the same amount. Treating equal payloads
as duplicates would incorrectly discard `e18`. Conversely, assigning a new ID to
every retry would stop this table from recognizing the repeated `e17`. The example
assumes stable IDs and matching content on redelivery. A production contract must
also handle an ID reused with conflicting content and scope identities across
independent consumers; this tiny table does not implement those checks.

Try two independent variations, starting from a fresh in-memory database each
time. Remove the three `WHERE changes() = 1` guards: output becomes `2, 4, 6`,
because every attempted delivery adds seats. Alternatively, keep the guards and
replace only the first `COMMIT` with `ROLLBACK`: output becomes `0, 2, 4`. The
rollback discards both the first marker and its report addition, allowing the
later attempt at `e17` to apply. This is deliberate rollback, not an observed
crash-recovery test.

The final total does not prove exactly-once delivery or handler execution. It
shows a repeated ID producing one committed report addition in this local
sequence. Deleting old markers, losing the database, changing IDs or bypassing
this transaction changes the protection. No email, HTTP request or other external
action is covered by this database transaction.

### 3) **Read ordering and exactly-once claims at their actual boundary**

**Ordering** must name its scope and stage. Publication order, log order, delivery
order, processing completion and external-effect order can differ. **Per-key
ordering** covers one key's sequence; it does not establish a global order over
all keys. A partition's offset orders its own log, not the real-world occurrence
time of every event.

Suppose two different events set a booking to `confirmed` and then `cancelled`.
Worker A receives confirmation first but runs slowly. Worker B applies cancellation
first; A later overwrites it with confirmation. There was no duplicate ID, yet
the final state violates the required update order. Deduplication alone does not
repair this. A consumer needs an appropriate ordering or version-check contract.
RabbitMQ's [queue-ordering guide](https://www.rabbitmq.com/docs/queues#message-ordering)
distinguishes single-channel enqueue order from interleaved publishers, priorities
and redeliveries. Even ordered delivery does not force concurrent handlers to
complete in that order.

Kafka's [4.3 delivery-semantics design](https://kafka.apache.org/43/design/design/#message-delivery-semantics)
explains how a Kafka transaction can coordinate consumed offsets with output
records between Kafka topics. Consumers' transaction visibility settings matter.
It separately identifies coordination with output stored in another system as
an additional requirement. That is a meaningful exactly-once scope, not permission
to assume an arbitrary email or remote database call joined the transaction.

As another scoped example, Amazon SQS's
[FIFO exactly-once-processing page](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/FIFO-queues-exactly-once-processing.html)
describes deduplicating repeated `SendMessage` attempts within a five-minute
interval. Read the stated action, ID and interval rather than expanding the page
title into a universal application-effect guarantee.

Practice: an email provider accepts a send, the worker stops before recording its
local sent marker, and the input returns. Does the SQLite technique above prove
that another send is safe? No. The external send and local marker have an unresolved
coordination gap. A useful review asks about provider-supported operation identity,
its retention and retry contract, or reconciliation evidence. Merely renaming a
local flag `sent_once` does not settle the remote outcome. Removing the provider's
acceptance evidence also changes the diagnosis to an unknown send outcome.

### 4) **Common confusion**

“Once per message” needs a message identity. A booking ID can have many legitimate
updates, while one update can have many delivery attempts. Using only the booking
ID as the duplicate key could suppress a later cancellation. A transport-generated
ID that changes on retry can fail in the opposite direction.

FIFO means first in, first out at a defined queue boundary. It does not mean
exactly once, and it does not make the oldest worker finish first. Similarly,
processing a record more than once can still produce one reflected result under
an appropriate coordinated output contract. Count observable effects separately
from attempts.

### 5) **Performance note**

Retaining identities uses storage and checking them adds work. Atomic output
coordination can add commit and contention costs; serializing an ordered sequence
can restrict parallel progress for that sequence. Removing markers to save space
also shortens the scope of duplicate recognition. Choose retention against the
actual replay/retry contract, not an unexplained universal time limit. This
in-memory example measures contents only, with no broker throughput, commit
latency or storage-durability benchmark.

### 6) **Mentor note**

Give the learner two event IDs with equal payloads and two attempts with one ID.
Ask which should change the report, then require a predicted total before the run.
Next move an email send outside the transaction and ask what new failure window
appears. A sound answer names the committed effect, identity and retention scope,
and does not claim that a transaction or broker setting covers an unrelated
external service.
