## 6.1. Explain an ambiguous distributed-system promise

“Async, replicated and exactly once” can describe several mechanisms while leaving
the user-visible outcome unspecified. A useful **distributed-system claim review**
connects each promise to an operation, a failure case, an observation and a clear
limit. This exercise asks you to make that connection across the preceding lessons.

The workshop service uses NestJS with the Fastify adapter. Every requirement,
relative time and diagnostic fact below is a constructed teaching artifact. No
application, broker or partition experiment was run for this packet.

### 1) **Expand the promise into operations and required outcomes**

The proposal says:

> Our async workers run in parallel. Three replicas make every booking read
> current and every write available. Publisher confirms prove successful report
> processing. Retrying after a timeout is safe because messaging is exactly once.
> A bounded queue supplies backpressure, and a healthy breaker probe means all
> previous work has recovered.

The stated requirements are more precise. After a booking-status write returns
success, a later status read must reflect that write unless another write changes
it. Each distinct accepted event must contribute its seats to the report once.
Email submission is tracked separately; the team must distinguish provider
acceptance from delivery to a recipient. No numerical latency target or promise
that every partitioned client can write has been agreed.

Before diagnosing anything, split the proposal into review questions:

| Claimed benefit | Boundary to inspect |
|---|---|
| Parallel worker execution | Actual simultaneous computation, not just overlapping task lifetimes |
| Current reads | Covered object, completed-write order and actual read path |
| Available writes | Client reachability, communicating participants and failure policy |
| Completed report processing | Committed output and progress evidence for the same event |
| Safe retry | Logical identity, repeated effect and remote-outcome evidence |
| Backpressure | Feedback that actually changes upstream production |
| Recovery | Previously incomplete operations and their required outputs |

This does not require selecting a technology first. It requires deciding what an
observer should be able to establish. For example, “all writes available” is not
a useful substitute for agreeing how an isolated client's attempt is handled.

### 2) **Trace a supplied failure packet without extending its evidence**

The diagnostic packet supplies the following facts. Times are relative positions
on one stipulated timeline, not independently sampled machine clocks. Booking
status starts as `pending`; the report starts at zero.

| Position | Given fact |
|---|---|
| Work trace | Tasks X and Y overlap in lifetime and yield on the same event-loop thread. No simultaneous CPU-execution observation is supplied. |
| 50 ms | Fixed voters A, B and C separate into communicating A/B and isolated C. The read/write object uses a majority protocol for new writes. |
| 80 ms | A/B complete the status write `confirmed`; the write client receives success. No later status write occurs. |
| 90 ms | A publisher confirm records broker acceptance of report event e17, which adds two seats. |
| 100 ms | A separate caller waiting for the report result reaches its deadline without that result. |
| 120 ms | The report consumer commits an unconditional two-seat addition for e17. It stores no duplicate marker. |
| 125–130 ms | The consumer connection ends before its acknowledgment is recorded. Redelivery of e17 runs the addition again and commits. The report is now four. |
| 140 ms | A status read starts through C and returns its unchanged local `pending`. C also refuses a new write because it cannot form the required majority. |
| Separate email attempt | The provider records acceptance of one send. The worker stops before its local sent marker is saved. No recipient-delivery evidence is supplied. |
| Overload inspection | A queue limit is configured, but a wrapper continues accepting upstream work into an uncapped in-memory list when the queue fills. |
| Later breaker trial | One allowed trial call succeeds. No reconciliation of the earlier report or email is recorded. |

The task trace supports concurrent lifetimes. It does not establish parallel CPU
execution. A pending task can let another task run on the same thread; that is the
[work-and-time distinction](<../1. Work and time/1.2. Concurrency parallelism scheduling and event loops.md>),
not a performance result.

The 140 ms read violates the stated current-status requirement: the confirmed
write completed before this read started, and no later write changed it. The
isolated C write refusal, however, does not prove that the majority protocol's
safety failed. It records lack of progress for that client under the stated
separation. [Linearizability and CAP](<../5. Distributed guarantees/5.1. Replication consistency availability partitions and consensus.md>)
explain those distinct questions; [Jepsen's model](https://jepsen.io/consistency/models/linearizable)
anchors the completed-before-start ordering condition.

At 90 ms the report effect is not established. RabbitMQ's
[acknowledgment guide](https://www.rabbitmq.com/docs/confirms) separates publisher
confirmation from consumer handling. Here the packet later establishes something
stronger and different: e17 actually caused two committed additions. The result
four conflicts with the one-contribution requirement. This is a known duplicate
effect in the supplied fiction, not merely a hypothetical risk inferred from
having retries.

At the 100 ms deadline, that caller has not received the required report result.
The deadline alone says nothing about a later commit. The later diagnostic rows
establish the two additions; they do not mean the caller already knew that at
100 ms. Keep the observer and observation time explicit when proposing a retry.

The email record establishes provider acceptance of one send, while the local
marker is missing. It establishes neither recipient delivery nor that a repeat
send will be suppressed. The [delivery-semantics lesson](<../5. Distributed guarantees/5.2. Delivery semantics ordering deduplication and exactly-once claims.md>)
owns the external-action gap. Treating the report's database transaction as proof
of email behavior would cross a different boundary.

Finally, the bounded queue does not bound the wrapper's list or regulate its
source. The memory obligation has moved. The successful breaker trial establishes
that one trial's result, not correction of the total or resolution of the earlier
send. Neither signal supplies the missing business recovery evidence.

### 3) **Rewrite the contract and request evidence that could change it**

A technical handoff can say:

> The trace shows concurrent same-thread tasks, with parallel execution unverified.
> The status read through C violates the stipulated completed-write requirement.
> C's write is refused while isolated from a majority. Event e17 has two committed
> report additions, so the total needs reconciliation and the repeated-event path
> needs correction. The separate caller timed out before receiving its result.
> One email submission was accepted, with recipient delivery and repeat-send
> handling unverified. The wrapper retains unbounded pending work, and one
> successful breaker trial does not establish recovery of those earlier outcomes.

For a product collaborator: “A confirmed booking can still appear pending on the
shown read path. The report counted the same event twice. One email submission
was accepted, but we have not established receipt or what a repeat attempt would
do. An isolated client cannot submit the shown write. We need explicit handling
for those cases before promising the proposed behavior.”

A corrected design proposal should state its intended behavior before claiming
it has been implemented. For this scenario, candidates include routing required
current-status reads through an appropriate verified path, coordinating report
identity tracking with its database effect, preserving operation identity across
retries, and regulating or refusing upstream work instead of accumulating an
uncapped list. Each candidate needs its own failure checks. Choosing a particular
consensus implementation or rewriting the whole service is outside this exercise.

Request a repeated-e17 case and a distinct-e18 case with checked report contents.
For current-status reads, request a completed write followed by a read through each
allowed route, including the isolated route and its specified refusal behavior.
For email, inspect the provider's actual repeat-request contract and reconcile the
accepted attempt before assuming a new one is harmless. For overload, inspect
all pending-work locations and whether upstream admission actually changes. These
are proposed checks, not tests executed against this fictional service.

Vary the evidence deliberately. Remove the 120–130 ms output records. You can
still say a publisher confirm does not prove report completion, but you cannot
assert that this report actually reached four. Alternatively, change the 140 ms
read to overlap the unfinished write. Returning `pending` alone then no longer
establishes a linearizability violation. Neither variation resolves the email
coordination gap or the uncapped list.

Interview prompt: “Which guarantee does this system have?” A strong answer first
selects an operation and observer. It then names a supported property or
contradicted requirement, its packet evidence and its limits. It can explain why
one rejected write and one stale read deserve different judgments. A single
system-wide label earns no credit without that reasoning.

### 4) **Common confusion**

A supported diagnosis and a candidate correction are different kinds of statement.
The packet establishes duplicate report additions; it does not establish that a
proposed deduplication patch has been implemented, tested under crash or retained
long enough for replay. Future behavior stays an intended contract until checked.

A mechanism can be useful without satisfying every promise. The queue can bound
its own contents while the wrapper remains unbounded. The breaker can successfully
admit a trial while earlier accepted work remains unresolved. Describe the exact
scope rather than declaring either mechanism universally useless or sufficient.

### 5) **Performance note**

Overlapping task lifetimes, three replicas and one successful probe provide no
throughput or tail-latency measurement. The uncapped list identifies a potential
memory-growth path, but the packet contains no measured growth rate. Duplicate
report additions establish a correctness defect, not its total load cost. Define
workload, observation interval and completion boundary before comparing a repair's
latency or capacity. No timing benchmark accompanies these fictional milliseconds.

### 6) **Mentor note**

Have the learner underline every factual clause in their handoff and point to its
packet row. Remove the duplicate-effect evidence and ask for a revised sentence;
then move the read earlier. A sound answer weakens only the affected conclusion.
Give feedback on those evidence changes before asking for more architecture
names. The learner should also distinguish what the waiting caller knew then
from what a later investigation established.
