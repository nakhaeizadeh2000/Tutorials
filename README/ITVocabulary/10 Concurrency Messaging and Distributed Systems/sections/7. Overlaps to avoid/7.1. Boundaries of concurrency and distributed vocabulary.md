## 7.1. Boundaries of concurrency and distributed vocabulary

Knowing that a call is asynchronous, a message is acknowledged or a replica is
current helps you ask the next question. It does not implement a scheduler,
consumer recovery protocol or agreement algorithm. Keep the vocabulary owner
separate from the implementation evidence needed for a particular system.

This closing lesson routes the domain's concepts to their detailed explanations
and appropriate further study. Its handoff exercise is constructed; no service
change or restart test is reported.

### 1) **Return to the owner of the specific guarantee**

Use the table to choose the question before choosing the tool. Each linked leaf
already exists and teaches its distinction fully.

| Question | Conceptual owner | Boundary to preserve |
|---|---|---|
| Who can proceed while a result is pending? | [Synchronous, asynchronous and blocking](<../1. Work and time/1.1. Synchronous asynchronous blocking and non-blocking.md>) | Caller behavior does not describe every worker resource |
| Did work overlap or actually execute simultaneously? | [Concurrency and scheduling](<../1. Work and time/1.2. Concurrency parallelism scheduling and event loops.md>) | Task lifetimes do not prove parallel computation |
| Which compound operation must stay together? | [Shared state and coordination](<../2. Coordination and hazards/2.1. Shared state atomicity races locks and deadlocks.md>) | An in-process lock has a participant and lifetime scope |
| Is this a request, an occurrence or a delivery route? | [Messages and subscriptions](<../3. Messages and streams/3.1. Commands events messages queues brokers and pub-sub.md>) | Semantic intent differs from routing and retention |
| What does the completion signal establish? | [Acknowledgments and checkpoints](<../3. Messages and streams/3.2. Streams batches consumers acknowledgments and dead-letter queues.md>) | Received input and applied output differ |
| What does a waiting limit or trial result reveal? | [Timeouts, retries and breakers](<../4. Failure and flow control/4.1. Timeouts retries backoff jitter and circuit breakers.md>) | Unknown outcomes and unresolved earlier work remain possible |
| Where does excess work wait or get refused? | [Flow control](<../4. Failure and flow control/4.2. Backpressure buffering throttling and load shedding.md>) | One bounded buffer does not regulate the whole path |
| What may a reader observe during separation? | [Consistency and consensus](<../5. Distributed guarantees/5.1. Replication consistency availability partitions and consensus.md>) | Agreement safety and client progress differ |
| Which repeated effects and orders are allowed? | [Delivery semantics](<../5. Distributed guarantees/5.2. Delivery semantics ordering deduplication and exactly-once claims.md>) | Identity, output coordination and external actions need explicit scope |

An overloaded word can lead to the wrong owner. A JavaScript job queue, a database
transaction and a broker queue are not interchangeable atomicity mechanisms.
Similarly, partition can mean a communication fault, a dataset portion or a log's
ordered subdivision. Use the surrounding operation and product contract to choose
the relevant meaning; do not merge the definitions because the spelling matches.

For type relationships between asynchronous results, use the existing

For database transactions, isolation and accepted-state rules, use the existing

### 3) **Hand off a mixed runtime and recovery question**

A fictional request says:

> Convert the report callback to a Promise so it never blocks, then add a mutex
> so duplicate events cannot change the report after restart. Prove recovery by
> showing the process is running again.

Separate three missing contracts. Promise composition determines how the caller
receives completion and failure; it does not by itself move synchronous work off
an occupied execution resource. The async/blocking and JavaScript owners answer
that first question. Ask which operation and resource actually wait.

A local mutex coordinates participating work within its scope. The request's
restart and duplicate-effect goal instead needs stable input identity and a
retained, appropriately coordinated output record. Route that investigation to
the delivery-semantics and transaction owners; do not reteach their whole example
inside a Promise lesson. Ask which state survives replacement of the process and
how it relates to the committed report change.

A running replacement process establishes neither the report contents nor the
status of every earlier event. Request those outputs and progress records for
the affected inputs. The acknowledgment owner supplies the reading distinction;
implementation recovery needs its actual storage and broker evidence.

A useful handoff is: “Please separate caller completion from execution-resource
blocking, and separate local exclusion from retained duplicate handling. Show how
the same logical event is recognized after restart and verify the required report
result. Process startup is one observation, with business recovery still unverified.”

Now add a scoped result: after a deliberate restart, replaying e17 leaves the
checked report total unchanged, while distinct e18 contributes once. This supports
those tested cases. It does not establish all crash points, lost-history behavior,
external email actions or a performance improvement. More precise evidence
changes the answer without changing which conceptual owner explains it.

### 4) **Common confusion**

A small executable illustration is useful evidence of its stated behavior; it
need not become a complete production service. The task-lock example observes a
lost update, while the SQL example observes retained identity within its local
sequence. Neither silently verifies the other's wider failure scope.

Likewise, an implementation gap is not a reason to repeat an entire foundational
lesson in every later domain. Give the contextual reminder needed for the current
sentence, link its exact owner and develop the new application. If a term appears
to have two owners, first check whether its meanings differ.

### 5) **Performance note**

Choosing a documentation owner has no direct runtime effect. The benefit is asking
for the correct evidence: an event-loop trace, storage result or load measurement
answers different questions. A Promise conversion, local lock or process restart
has no speed benefit established by this handoff. Measure the actual operation
and resource after its correctness and recovery contract is defined.

### 6) **Mentor note**

Ask the learner to select one question from the request and identify its owner,
needed artifact and remaining uncertainty. Accept a short contextual explanation
with a precise route; reject an acronym list or an unrelated implementation.
Then add the scoped restart/replay result and ask exactly which conclusion became
stronger. Good teaching makes the evidence boundary visible without implying
that vocabulary fluency alone demonstrates production mastery.
