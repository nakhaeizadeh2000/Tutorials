## 2.1. Shared state atomicity races locks and deadlocks

Two tasks can each read the same old value, calculate a replacement and overwrite
one another's changes. They need not execute at exactly the same instant. A
suspension between reading and writing is enough to expose the problem.

Read the preceding task/scheduling lesson and the earlier database transaction
lesson. Here we examine in-process coordination; a lock in one application
instance does not protect independent instances or a shared database automatically.

### 1) **Name the shared state and the operation that must stay together**

**Shared state** is state accessible to more than one relevant participant.
**Shared mutable state** can also change. A participant's private local variable
can contain an old observation of that shared state, even while another participant
changes the authoritative value.

A **race condition** occurs when correctness depends on the relative order or timing
of concurrent events and an allowed ordering can violate the required result.
Consider two completed increments of a counter initially zero:

| Step | Task A | Task B | Shared count |
|---|---|---|---|
| 1 | Reads 0 into its local value | | 0 |
| 2 | | Reads 0 into its local value | 0 |
| 3 | Writes local value plus 1 | | 1 |
| 4 | | Writes its local value plus 1 | 1 |

Both operations finished, but the required final count is 2. This is a **lost
update**. MIT's [concurrency reading](https://web.mit.edu/6.031/www/fa21/classes/21-concurrency/)
uses interleavings to explain why correct-looking individual steps can combine
into an incorrect operation. The table above is a constructed schedule, not a
claim about CPU instruction order.

An **atomic operation**, in this concurrency context, is indivisible with respect
to the specified competing observations or operations. Name that scope: protecting
one assignment does not make the whole read–calculate–write sequence atomic.
The database lesson's ACID atomicity addresses accepting or discarding transactional
changes as a unit; it must not be silently substituted for this concurrent-operation
boundary or for a database isolation guarantee.

A **data race** has a more specific definition in a language's memory model. For
example, the [Go memory model](https://go.dev/ref/mem) defines conflicting memory
accesses and their required synchronization ordering. A higher-level race condition
can exist even when individual memory accesses are safely ordered. The single-loop
example below demonstrates an application race across suspension; it does not
claim to run a language memory-model race detector.

### 2) **Observe a lost update and protect the complete critical section**

A **critical section** is code that accesses state under an exclusion discipline.
**Mutual exclusion** permits only one participating operation in the protected
section at a time. A **mutex**, short for mutual exclusion, is a lock used to
provide that control. All conflicting participants must use the same appropriate
lock, and the protected region must cover the required operation.

Tested environment: **CPython 3.14.4 on Linux x86_64**, standard library only.
Current Python 3.15 [asyncio lock documentation](https://docs.python.org/3.15/library/asyncio-sync.html#asyncio.Lock)
retains the task-lock contract used here. Save `lost_update.py` and run
`python3 lost_update.py`.

```python
import asyncio

async def increment(state):
    old = state["count"]
    await asyncio.sleep(0)
    state["count"] = old + 1

async def run_pair(protected):
    state = {"count": 0}
    lock = asyncio.Lock()

    async def job():
        if protected:
            async with lock:
                await increment(state)
        else:
            await increment(state)

    async with asyncio.TaskGroup() as group:
        group.create_task(job(), eager_start=False)
        group.create_task(job(), eager_start=False)
    return state["count"]

async def main():
    print("Unprotected:", await run_pair(False))
    print("Protected:", await run_pair(True))

asyncio.run(main())
```

Observed output:

```text
Unprotected: 1
Protected: 2
```

The dictionary is the shared state for a pair; each call to `increment` has its
own `old` local value. In the unprotected run, both jobs read zero before their
yields resume. They then both write one, producing the table's lost update.
The explicit yield makes this particular failure observable without hoping for
a rare thread schedule.

In the protected run, the first job acquires the shared lock before reading.
It retains the lock while its task yields. The other job can get a turn but
cannot enter that same critical section yet. After the first job writes one and
leaves the `async with` block, the next job can read one and eventually write two.
The context manager releases the lock when leaving the protected block, including
exceptional exits; release does not roll back state changes already made.

This `asyncio.Lock` coordinates cooperating tasks using it. It is not a thread-safe
lock or a distributed lock. The example has one loop and no database. It proves
neither a deployment-wide booking invariant nor protection for code that ignores
the lock.

Practice: move the read of `old` and its yield outside the protected section,
leaving only the assignment locked. Both jobs can again save zero, then take turns
writing one. The writes are mutually excluded, but the required compound operation
is not. The correct boundary follows the invariant rather than the smallest line
that changes a value.

### 3) **Distinguish exclusion from progress and wider coordination**

A **deadlock** prevents participants from progressing because they depend on one
another in a cycle. The database lesson owns the full two-resource lock example.
A different constructed cycle can occur with one task lock:

| Participant | Holds or needs |
|---|---|
| Task A | Holds lock L and awaits task B's completion before releasing L |
| Task B | Must acquire L before it can finish |

A cannot release until B finishes, and B cannot finish until A releases. This
card assumes no cancellation, timeout or other intervention. It is not executed
as a deliberately hanging program. Revise the dependency so A does not await work
that requires the lock it holds. Merely adding more worker capacity does not
remove this cycle. MIT's [mutual-exclusion reading](https://web.mit.edu/6.031/www/fa21/classes/23-mutual-exclusion/)
explains why exclusion and progress are separate concerns.

A **safety** property excludes an unwanted outcome, such as losing an accepted
increment. A **liveness** property requires desired progress eventually to occur
under the stated assumptions. A lock can help with the first while an incorrect
wait relationship breaks the second. A long wait alone does not prove deadlock;
identify the dependency preventing progress. **Starvation** instead describes
work indefinitely failing to obtain the opportunity or resource it needs while
other work can continue. Fairness and progress guarantees depend on the scheduler
and primitive; do not infer them from the generic word lock.

Other approaches can avoid sharing mutable state or give one owner the whole
operation. An owner accepting “increment” can make a stronger boundary than clients
sending independent “read” and “write” requests. Message passing alone still does
not make a check and later update indivisible. For a workshop shared across
application instances, select coordination at the actual authoritative boundary;
an in-memory mutex in each instance does not combine them into one lock.

### 4) **Common confusion**

“Single-threaded” does not imply “free from application races.” Our jobs interleave
at a deliberate await. Likewise, thread-safe individual methods do not automatically
make a sequence of calls safe as a compound operation. Ask what can happen between
the read and its dependent change.

A lock also does not confer authorization, validate the business rule or persist
state after a crash. It controls a specified access relationship. Different locks,
ignored locks or a lock with the wrong scope cannot establish the intended rule.

### 5) **Performance note**

Conflicting work waits for the protected section, so unnecessary slow work while
holding a lock can increase contention. A section that is too narrow can still
be incorrect. First preserve the required invariant, then reduce unnecessary
protected work without moving dependent observations outside the boundary.
These tiny runs show an outcome difference, not lock overhead, contention under
load, fairness or throughput. A globally shared lock may serialize more work than
needed; choosing finer boundaries also requires reasoning about cross-boundary rules.

### 6) **Mentor note**

Ask the learner to mark both private `old` values and the one shared dictionary.
Then move the read outside the lock and require an explicit failing schedule.
A sound answer explains why locking only writes is insufficient. For the deadlock
card, require both dependency arrows before accepting the diagnosis, and have the
learner name the scope an in-process repair would still leave unprotected.
