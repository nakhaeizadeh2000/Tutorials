## 1.2. Concurrency parallelism scheduling and event loops

Two operations can both be unfinished without executing instructions at the same
instant. Distinguishing those situations helps you interpret “parallel requests,”
worker counts and event-loop claims. Start with the preceding distinction between
a waiting task and an occupied execution thread.

### 1) **Distinguish overlapping work from simultaneous execution**

**Concurrency** concerns work whose lifetimes can overlap and whose progress must
be organized together. **Parallelism** concerns computations actually executing
at the same time. An application can have concurrent tasks on one execution
thread, switching among their steps. With suitable resources and implementation,
concurrent work can also execute in parallel.

Andrew Gerrand's [Go project explanation](https://go.dev/blog/waza-talk), introducing
Rob Pike's talk, distinguishes concurrent program structure from simultaneous
execution. Its “processes” are independently executing activities in that discussion,
not a requirement that every activity be a separate operating-system process.
No Go knowledge is needed for the distinction.

Consider two constructed schedules. `A1` and `A2` are steps of A; `B1` and `B2`
are steps of B. Each column is one illustrative interval, not a measured duration.

| Schedule | First interval | Second | Third | Fourth |
|---|---|---|---|---|
| One execution resource, sequential operations | A1 | A2 | B1 | B2 |
| One resource, interleaved operations | A1 | B1 | A2 | B2 |
| Two resources, simultaneous work possible | Resource 1: A1; resource 2: B1 | Resource 1: A2; resource 2: B2 | Finished | Finished |

In the middle row, B starts before A completes. Their lifetimes overlap, but only
one listed step executes at a time. The last row describes parallel execution.
Having two available resources would permit such a schedule; their existence
alone would not prove it happened.

An outstanding network request may overlap another request while JavaScript
callbacks still execute one at a time on a particular event-loop thread. Specify
whether “parallel” refers to remote work, CPU execution or merely outstanding
operations. A count of open connections does not answer all three questions.

### 2) **Identify what a scheduler and event loop can run**

A **scheduler** selects which eligible work gets execution resources and when.
An operating-system scheduler deals with threads; a runtime can separately
schedule tasks onto those threads. A task being ready means it can proceed under
that scheduler's conditions. A task waiting for input is different from ready work
that has not yet received a turn.

With **preemptive scheduling**, a scheduler can interrupt execution to run other
work without that work explicitly yielding at that moment. With **cooperative
scheduling**, work gives control back at supported suspension or yield points.
These describe a scheduling relationship, not an entire machine: cooperatively
scheduled tasks can run within a thread that the operating system preempts.

An **event loop** coordinates callbacks, ready tasks and observations such as I/O
readiness or timers. The exact queues, phases and fairness rules belong to the
runtime. Python's [asyncio development guide](https://docs.python.org/3.15/library/asyncio-dev.html#concurrency-and-multithreading)
describes one loop running its tasks and callbacks in its thread. Long computation
or a blocking call in that thread can delay the other work assigned to that loop.

This does not mean all asynchronous systems have one thread, or that every task
has its own thread. A program may have several loops, worker threads or processes.
Draw those execution boundaries before attributing a bottleneck or guarantee to
“the event loop.”

### 3) **Observe interleaving without claiming a CPU speedup**

Tested environment: **CPython 3.14.4 on Linux x86_64**, standard library only.
Current Python 3.15 documentation retains these task, task-group and yield
contracts; the executable observation below is explicitly from 3.14.4.
Save `task_progress.py` and run `python3 task_progress.py`.

```python
import asyncio
import threading

async def stepper(name, trace, threads):
    threads.add(threading.get_ident())
    trace.append(name + "1")
    await asyncio.sleep(0)
    trace.append(name + "2")

async def main():
    sequential = []
    concurrent = []
    threads = set()
    await stepper("A", sequential, threads)
    await stepper("B", sequential, threads)
    async with asyncio.TaskGroup() as group:
        group.create_task(stepper("A", concurrent, threads), eager_start=False)
        group.create_task(stepper("B", concurrent, threads), eager_start=False)
    print("Sequential:", " ".join(sequential))
    print("Concurrent:", " ".join(concurrent))
    print("Stepper thread identities:", len(threads))

asyncio.run(main())
```

Observed output:

```text
Sequential: A1 A2 B1 B2
Concurrent: A1 B1 A2 B2
Stepper thread identities: 1
```

A trace is a list recording the order of steps. A set records distinct observed
thread identities. The sequential calls await A's completion before beginning B,
so A's internal yield does not itself start B. In the group, both tasks are
scheduled before the group waits for their completion. `eager_start=False` makes
the delayed scheduling choice explicit. Each task appends its first marker and
then yields through `asyncio.sleep(0)`, allowing the other to progress.

The [task reference](https://docs.python.org/3.15/library/asyncio-task.html) documents
task creation, task-group completion and the explicit zero-delay yield. The group
keeps this pair's lifetime inside its block; both have completed before we print.
The trace is the observed schedule in this declared environment, not a universal
ordering rule for other schedulers or task factories. One thread identity means
these stepper executions used the same thread; it does not inventory every thread
in the process or measure work performed elsewhere.

Remove only `await asyncio.sleep(0)` from `stepper` and run again. The concurrent
trace becomes `A1 A2 B1 B2` in this setup. Both tasks were arranged together, but
each task's body now completes without a suspension point. Writing `async def`
did not force its steps to interleave. The preceding lesson also shows why an
already-satisfied awaitable need not yield.

### 4) **Common confusion**

Concurrent design can support parallel execution, but a concurrent API does not
prove simultaneous CPU work. Conversely, independent synchronous calls on different
threads or machines can run in parallel. Classify the actual boundary rather than
equating synchronous with single-threaded and asynchronous with parallel.

One event-loop thread also does not make every multi-step application operation
atomic. Another task can change shared state while the first task is suspended.
The next coordination lesson examines that case. Run-to-completion between yield
points is a narrower claim than “this application cannot race.”

### 5) **Performance note**

Interleaving can let useful work proceed during another operation's wait. It does
not reduce the computation in A1 or A2. Parallel execution may reduce elapsed time
for suitable independent work, with limits from available resources, dependencies,
coordination and shared bottlenecks. Creating more runnable work can instead add
queueing and memory use. The trace example measures neither durations nor resource
utilization; it establishes ordering and observed thread identity only.

### 6) **Mentor note**

Give the learner the middle schedule and ask whether B progressed before A finished,
and whether two steps executed simultaneously. Then remove the yield in the code.
A sound prediction distinguishes task lifetime, execution turns and hardware
parallelism. Ask which extra observation would support an actual speedup claim;
a different log order alone is insufficient.
