## 1.1. Synchronous asynchronous blocking and non-blocking

“The operation is async, so nothing waits” confuses a result dependency with an
execution resource. A booking report still needs its data before calculating a
total. The important questions are how completion reaches the caller and what
other work can proceed while that result is unavailable.

Read the process/thread and API-contract vocabulary first. These terms have
context-dependent uses; this lesson identifies the boundary rather than imposing
one universal naming convention on every language or standard.

### 1) **Separate completion order from an occupied execution resource**

A **synchronous** call, in ordinary direct-call usage, completes its operation or
reports failure before the caller continues past that call. Adding two already
available numbers is synchronous and may finish quickly. A synchronous file read
can instead wait for storage. Synchronous does not itself mean slow.

An **asynchronous** interface separates initiating or arranging work from receiving
its eventual completion. A callback, future, promise or message can carry that
completion. A **callback** is supplied behavior invoked by another operation;
not all callbacks are asynchronous. A collection's mapping callback may run
entirely before the mapping call returns.

**Blocking** here means that a specified execution resource, commonly the calling
thread, cannot proceed with other work while it waits for an operation or condition.
A **non-blocking** I/O attempt does not wait for readiness: if progress is unavailable
now, it returns an appropriate outcome so the caller can do something else. It
need not arrange a later completion notification. Python's
[socket mode documentation](https://docs.python.org/3.15/library/socket.html#notes-on-socket-timeouts)
provides a concrete distinction between blocking, non-blocking and timeout modes.

These questions are related but different:

| Constructed operation | What completes, and who can proceed? |
|---|---|
| Direct addition of two integers | The result is returned in the call; no external readiness wait is needed |
| Blocking receive with no available data | The calling thread waits for data, an error or its configured limit |
| Non-blocking receive with no available data | This attempt reports that it cannot proceed now; the caller retains control |
| Start work, then later receive a completion callback | Initiation and completion are separated; inspect work before return and callback execution separately |
| Suspend a task awaiting a result | That task's continuation waits, while its scheduler may run other work on the thread |

Some communities call the last case synchronous-looking or even synchronous
composition because dependent steps retain their order. For example, Android's
[async API guidelines](https://android.googlesource.com/platform/developers/docs/+/cf79849224405677e8d3a7bb5f42c420e2f60fc3/api-guidelines/async.md)
explicitly distinguish suspending functions from thread blocking. State what waits
and what remains available instead of trying to settle the issue from a keyword.

### 2) **Observe an unavailable result and a suspended task separately**

Tested environment: **CPython 3.14.4, Linux x86_64**, standard library only.
The cited current Python 3.15 reference describes the same socket, event and
callback contracts used here; this run does not claim Python 3.15 execution.
Save `waiting_boundaries.py` and run `python3 waiting_boundaries.py`.

```python
import asyncio
import socket
import threading

reader, writer = socket.socketpair()
with reader, writer:
    reader.setblocking(False)
    try:
        reader.recv(1)
    except BlockingIOError:
        print("Receive attempt: no data now")
    writer.sendall(b"x")
    print("Later receive:", reader.recv(1).decode("ascii"))

async def main():
    ready = asyncio.Event()
    owner_thread = threading.get_ident()

    def signal_ready():
        print("Callback on same thread:",
              threading.get_ident() == owner_thread)
        ready.set()

    asyncio.get_running_loop().call_soon(signal_ready)
    print("Task before wait")
    await ready.wait()
    print("Task after signal")

asyncio.run(main())
```

Observed output:

```text
Receive attempt: no data now
Later receive: x
Task before wait
Callback on same thread: True
Task after signal
```

`socketpair()` creates two connected local endpoints, not an internet listener.
The reader has no data on its first attempt. Its non-blocking mode produces the
caught `BlockingIOError`, rather than waiting for a writer. The program then sends
one byte through the other endpoint and receives it. This example deliberately
performs another attempt after supplying data; the first attempt did not register
a callback or promise to deliver that byte later. Both endpoints close when the
`with` block ends.

`async def` declares a coroutine function, whose execution can suspend. `asyncio.run`
runs the top-level coroutine. An `asyncio.Event` starts unset; its
[wait operation](https://docs.python.org/3.15/library/asyncio-sync.html#asyncio.Event)
suspends the awaiting task until the flag is set. It is an in-process coordination
flag, distinct from a stored business event such as “booking confirmed.”

`call_soon` arranges the ordinary `signal_ready` callback for a later loop turn,
as documented by the [callback scheduler](https://docs.python.org/3.15/library/asyncio-eventloop.html#asyncio.loop.call_soon).
The task prints its before line, then waits on the unset event. That suspension
allows the queued callback to run on the same thread. The callback sets the flag;
the waiting task can then resume. Its continuation waited, but its thread was
available to perform the callback. No extra worker thread is created by this code.

Change one condition: set `ready` before calling `await ready.wait()`. Now the wait
can complete without suspension. The after line appears before the queued callback.
Therefore an `await` expression is not a promise that another operation must get
a turn; the awaitable's state and contract matter. This variation is a local
ordering observation, not a measured scheduling guarantee for every async API.

### 3) **Read an async claim across the full operation**

A fictional export interface returns a job identifier before the export finishes.
That establishes a split between acceptance and completion at that interface.
It does not tell you whether preparing the request blocked a thread, whether a
worker blocks on storage, or how the caller learns that the job failed. Ask for
those boundaries separately.

An asynchronous wrapper can move blocking work to a worker thread. The caller's
thread may then remain available, while the worker still waits. That can be a
useful arrangement, but a finite worker pool can fill. Conversely, declaring a
function `async` does not transform a blocking call or long computation inside it
into cooperative work. Inspect the actual operations it invokes.

For a task awaiting booking data, preserving the dependency is correct: it cannot
calculate a valid total from data it has not received. The design question is
which other independent work should progress during that wait. Error reporting,
cancellation and ownership of outstanding work still need contracts; “fire and
forget” does not establish successful completion.

Practice: a report says “the caller received a job ID immediately, but all ten
workers were waiting for database connections.” Is that contradictory? No. The
caller interface can report acceptance before completion while worker resources
are blocked. Inspect connection limits and worker activity before deciding whether
more asynchronous calls would improve the situation. The report is constructed;
no export or database workload was executed here.

### 4) **Common confusion**

A suspended task and a blocked thread are different units. Name the unit in the
sentence “it waits.” A synchronous function can be brief, and an asynchronous
operation can take a long time or perform blocking work internally.

Non-blocking also does not mean zero elapsed time or no possible CPU use. Repeating
an unavailable receive in a tight loop can consume CPU while accomplishing little.
Readiness notification and completion notification are different contracts. In
concurrent-algorithm literature, non-blocking can additionally mean a formal
progress property; that is not what socket mode alone promises.

### 5) **Performance note**

Allowing other work during I/O waits can improve utilization or responsiveness
when independent work exists. It does not make the underlying read faster or
remove limits in storage and worker pools. An event loop can itself wait for
external events when there is no ready work; that is different from a handler
preventing already-ready work from running. The example records ordering and
availability, not latency, throughput, CPU utilization or a parallel speedup.

### 6) **Mentor note**

Ask the learner to mark the moment when the first receive ends, the task suspends,
the callback runs and the task resumes. Then ask why the callback can run without
a second thread. A sound answer distinguishes the attempted operation, the logical
task and the execution thread, and explains why the already-set variation changes
the order.
