## 3.1. Commands events messages queues brokers and pub-sub

“Send the booking event to a queue” mixes the meaning of information with the
mechanism moving it. Start by asking whether the sender requests an action or
announces a fact. Then identify who should receive a copy and what the messaging
system actually promises.

The earlier design lesson introduced commands and events. This lesson adds their
communication roles and routing boundaries. All booking packets and delivery
allocations below are constructed; no broker or backend application is deployed.

### 1) **Separate a message envelope from its intended meaning**

A **message** is a unit of communicated information under a messaging contract.
Its **body** carries application data, while an **envelope** or accompanying
metadata can identify type, destination, message identity or other handling details.
The exact fields depend on the protocol and application contract. JSON is one
possible body representation; it does not make the message an event.

A **command message** carries a request to perform an action. An **event message**
communicates something that happened. These are semantic roles, not necessarily
different transport-level types. Hohpe and Woolf's originating pattern excerpts
for [command messages](https://www.enterpriseintegrationpatterns.com/patterns/messaging/CommandMessage.html)
and [event messages](https://www.enterpriseintegrationpatterns.com/patterns/messaging/EventMessage.html)
distinguish the requested action from notification of an occurrence.

For the workshop application, compare these fictional contracts:

| Message | Agreed meaning | What receipt alone does not establish |
|---|---|---|
| `ConfirmBooking`, request c17, booking r17 | Ask the booking owner to confirm r17 under its rules | That capacity was available or confirmation succeeded |
| `BookingConfirmed`, event e17, booking r17 | Announce that the producer recorded r17 as confirmed | That every report or email consumer has processed it |
| `BookingSummary`, response s17, active seats 3 | Supply a summary value for a stated query/input scope | That it is a new instruction or a full historical record |

The words in the type field are useful only because the contracts define them.
Calling an unperformed instruction `BookingConfirmed` does not turn it into a
fact. Likewise, receiving a claimed fact does not independently validate its
source or truth. Ask which component is authorized to announce that state and
which evidence supports the claim.

A message identifier is also distinct from a booking identifier. Two different
facts about r17 can have different event IDs. Repeated transmission of the same
fact may retain its event identity under the contract. Later delivery reasoning
uses that distinction; the spelling of an ID alone provides no deduplication.

### 2) **Distinguish distribution roles from storage and processing guarantees**

A **producer** creates or sends messages; a **publisher** sends into a publication
mechanism. A **consumer** receives messages for processing. One application can
perform both roles in different interactions. These are roles, not requirements
for a separate process per role.

A **message broker** mediates communication between producers and consumers. It
can route, buffer or retain messages according to its product and configuration.
A **message queue** holds messages for consumption under a queue contract. The
earlier data-structure queue explains the basic collection idea; a broker queue
adds delivery, resource and lifecycle rules. The word queue alone supplies no
universal durability, ordering or successful-processing guarantee.

With **competing consumers**, workers share a delivery source to distribute work.
A **work queue** commonly uses this arrangement so one selected worker handles a
particular delivery. With **publish–subscribe**, abbreviated **pub-sub**, publication
is routed to interested subscriptions. A **subscription** records interest under
the system's routing and delivery rules. Independent subscriptions can each receive
the same published information, while workers inside one subscription may share
its work. Inspect the subscription boundary before counting recipients.

A **topic** is a named publication or routing grouping whose meaning is product-
specific. It may identify retained records, a subject hierarchy or a routing
pattern. Do not assume that every product's topic is a queue, one subscriber or
an authoritative event store.

RabbitMQ provides a concrete routing example. In its AMQP 0-9-1 model, an
**exchange** routes published messages to queues through **bindings**, the declared
routing relationships. A fanout exchange routes to its bound queues. The official
[work-queue tutorial](https://www.rabbitmq.com/tutorials/tutorial-two-javascript)
and [publish–subscribe tutorial](https://www.rabbitmq.com/tutorials/tutorial-three-javascript)
contrast shared-queue workers with separate receiving queues. These are product
roles, not a universal architecture every broker must implement.

### 3) **Trace copies and competing workers in a concrete topology**

Staff require both the report updater and the email sender to receive each
booking-confirmed fact. The following static packet assumes two valid publications,
e17 and e18; all named queues and bindings exist before publication; no failures,
redelivery, expiration or filtering occur. The allocations are stipulated examples,
not promises about a broker's worker-selection policy.

| Arrangement | Constructed delivery allocation | Requirement interpretation |
|---|---|---|
| Report and Email compete on one shared queue | Report gets e17; Email gets e18 | Work was divided; neither function received both facts |
| One report queue and one email queue each receive both publications | Report queue: e17,e18; Email queue: e17,e18 | Both functions have their own intended input copies |
| The report queue has workers R1 and R2; the email queue has E1 | R1 gets e17; R2 gets e18; E1 gets e17,e18 | Reporting work is shared inside its function; email retains its own input stream |

The third arrangement creates four intended queue deliveries across the two
functional destinations, not six deliveries merely because three worker processes
exist. R1 and R2 are two workers for one logical reporting responsibility. Whether
their processing is correct, ordered or complete remains a separate question.

Now remove the email queue and binding before e17 is published, then create them
before e18. In the RabbitMQ fanout arrangement described here, the missing binding
did not route e17 to that later queue. Creating a subscription afterward is not
proof of historical replay. A retained-history service could offer a different
contract, which must be named and checked rather than inferred from pub-sub.

A useful handoff is: “Reports and email need independent subscription inputs;
report workers can share the reporting queue. Verify binding lifetime, retention
and processing outcomes separately.” Avoid “add another consumer so both services
get every event” until the shared versus independent subscription arrangement
is clear.

### 4) **Common confusion**

Commands can be carried by the same broker technology as events. Event names
conventionally describe facts and command names describe actions, but grammar
is not delivery semantics. A producer sending a message also does not establish
that a consumer accepted or completed the business operation.

Publishing events is not automatically event sourcing. A distribution queue can
remove acknowledged messages; authoritative reconstructable history has a separate
contract. Nor does adding a broker automatically make the application microservices:
deployment and responsibility boundaries still need their own evidence.

### 5) **Performance note**

Competing workers can increase processing capacity when work and dependencies
permit it. Independent subscription copies add deliveries, buffering and processing
work. If a consumer cannot keep up, its backlog can grow under the configured
retention and capacity rules. A broker can decouple when producers and consumers
run without making either operation free or infinitely scalable. This packet
establishes copy allocation only; it supplies no throughput, latency or storage
measurement and no guaranteed worker speedup.

### 6) **Mentor note**

Give the learner two workers and one queue, then ask whether both functions
receive both events. Require them to draw the subscription boundaries before
answering. Next change a command into an announced fact without changing its
transport. A sound answer changes the semantic interpretation while keeping
routing and delivery guarantees as separate questions.
