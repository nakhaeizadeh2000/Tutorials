## 5.1. Review an AI feature proposal without capability hype

A useful AI review begins with the intended user outcome. Model size, agent labels
and a polished demonstration are context; they do not decide whether a feature
meets the actual task. This exercise integrates the preceding lessons without
requiring an ML implementation.

### 1) **Extract task data and responsibility**

Read this original fictional proposal packet. All measurements are stipulated
records for analysis; this lesson runs no model or application.

| Artifact | Supplied information |
|---|---|
| User need | Support staff need current, tenant-permitted manual passages to draft answers |
| Proposed feature | Retrieve passages, generate a draft, require staff approval before sending |
| Data | Ten selected English questions from one tenant; current manuals stored, but index revision not recorded |
| Result | Nine drafts contain a citation marker; one lacks one |
| Reviewed draft | Cites an older manual and gives its superseded refund rule |
| Permissions | Caller login checked; no resource/tenant enforcement evidence |
| Tool | Submission tool advertised; intended feature scope is draft-only |
| Resources | No serving latency, review-effort or cost observations |
| Summary | “90% accurate autonomous support, always current, secure and cheaper than staff” |

First identify the actors and action. Staff approve drafts; this is not evidence
of autonomous customer support. The stated need includes current and permitted
sources, so retrieval relevance alone is insufficient. A login identifies a caller;
it does not establish permission for every retrieved resource. The advertised
submission tool adds a capability question that must be reconciled with draft-only scope.

### 2) **Evaluate claims against the packet**

Use the established owners rather than restating their mechanisms:

| Claim | Supported interpretation | Missing evidence or decision |
|---|---|---|
| 90% accurate | Nine of ten selected drafts meet the marker check | Reviewed factual/source criteria and representative evaluation |
| Always current | Manuals are stored; a stale draft is recorded | Index revision, source selection and response support |
| Autonomous | Feature proposes staff approval | Exact control path and permitted actions |
| Secure | Login is checked | Resource/tenant authorization and relevant adversarial checks |
| Cheaper | No resource comparison supplied | Serving, integration, review, recovery and other scoped costs |

The [evaluation owner](<../4. Applications and limitations/4.2. Hallucinations evaluations benchmarks guardrails and prompt injection.md>) explains why marker
presence cannot stand in for factual accuracy. The [retrieval owner](<../3. Generative systems/3.2. Retrieval RAG grounding fine-tuning and quantization.md>)
separates storage, index, context and source support. The [agent owner](<../4. Applications and limitations/4.1. Agents workflows tool calling and model context protocols.md>)
separates available tools from permitted execution. Each exposes a different gap;
one benchmark score cannot close them all.

A recorded stale answer is direct negative evidence for the blanket currentness
claim. The other gaps are absence of evidence in the packet, not proof that every
permission control is absent or that the system can never be economical. Phrase
those conclusions differently. “No authorization evidence supplied” is more accurate
than “all tenant data was leaked.”

### 3) **Write a bounded recommendation**

A review can read:

> The proposal addresses staff drafting, with human approval before sending. The
> supplied result is 90% citation-marker success on ten selected English questions,
> not measured factual accuracy. One reviewed draft uses a superseded rule. Before
> assessing deployment readiness, identify the actual source/index revisions, check
> source support and currentness, and obtain resource-level permission evidence.
> Keep tool execution consistent with draft-only scope. Define representative tasks,
> acceptable errors and the ownership of review, escalation and rollback. Cost and
> latency comparisons remain unmeasured.

This is a recommendation to gather evidence, not a hidden approval to deploy.
A **pilot** is a limited trial under stated conditions. Calling something a pilot
does not remove access requirements or guarantee that its results generalize.
A concrete pilot proposal would name included users/data/actions, success criteria,
stop conditions, responsible owners and how errors reach human support.

For this packet, useful evaluation cases include a current-rule question, an obsolete
passage competing with a current one, no authorized supporting passage, and a
question belonging to another tenant. Grade the desired outcome in each: a supported
current draft, a controlled inability to answer or an enforced permission boundary.
Human review needs its own criteria and evidence; “a person will catch mistakes”
is not a measured control.

Practice a variation: add a verified trace showing cross-tenant retrieval is denied.
Credit that result for its caller/resource/operation and stated setup. Do not upgrade
it to factual accuracy, fresh indexing, all-case security or lower cost. Next add
three acceptable drafts. Without the full selection method and new denominator,
“now 100%” is still unsupported.

### 4) **Common confusion**

Rejecting hype is not rejecting a useful feature. The packet can motivate a narrower
staff-assistance trial while failing to establish autonomous service readiness.
Keep the decision proportional to the evidence and task. A model benchmark from
another environment neither supplies nor invalidates this missing application evidence.

### 5) **Performance note**

End-to-end cost includes retrieval, generation, review, retries and recovery at the
chosen boundary. A shorter generated answer may still require more human correction.
The packet supplies no measured comparison; do not infer savings from model quality
or a lower advertised token price alone.

### 6) **Mentor note**

Give the learner the summary first and then the packet. Require them to revise five
claims with distinct evidence limits and propose one case that could change a
specific conclusion. Assess whether their recommendation retains the real user
need without inventing failures, completed tests or deployment authorization.
