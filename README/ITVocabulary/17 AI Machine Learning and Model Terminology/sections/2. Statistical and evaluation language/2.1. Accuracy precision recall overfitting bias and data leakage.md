## 2.1. Accuracy precision recall overfitting bias and data leakage

“Accuracy is 95%” can describe a classifier that misses every urgent request.
To interpret a score, first identify the task, reference labels, population and
cost of each error. Then inspect what was counted.

### 1) **Calculate task-specific classification measures**

For this original fictional assessment, **positive** means a message needs urgent
routing according to reviewed reference labels. A true positive (TP) is flagged
and urgent; a false positive (FP) is flagged but not urgent. A false negative (FN)
is urgent but missed; a true negative (TN) is correctly left unflagged. The general
[false-signal lesson](<../../../12 Testing Debugging and Quality Evidence/sections/3. Test arrangements and limits/3.2. Coverage flaky tests false positives and false negatives.md>) owns these concepts;
this lesson applies them to model metrics.

| Prediction | Reference urgent | Reference not urgent |
|---|---:|---:|
| Flag urgent | 3 TP | 2 FP |
| Do not flag | 2 FN | 93 TN |

There are 100 examples, five actually urgent and five predicted urgent.
**Accuracy** is the fraction correct: (3 + 93) / 100 = 96%.
**Precision** asks how many flagged examples are actually urgent: 3 / (3 + 2) = 60%.
**Recall** asks how many actual urgent examples were flagged: 3 / (3 + 2) = 60%.
They happen to match here; their denominators represent different sets.
[Google's classification metrics](https://developers.google.com/machine-learning/crash-course/classification/accuracy-precision-recall)
defines these measures and discusses class imbalance and error costs.

Now flag one additional actually urgent message and leave everything else unchanged.
TP becomes 4 and FN 1; FP stays 2 and TN 93. Accuracy is 97%, precision 4/6 (about
66.7%) and recall 4/5 (80%). The different denominators now produce different values.
A system flagging nothing would instead have 95% accuracy and zero recall on these
five urgent examples. Its precision has a zero denominator; report that it is
undefined here or state the reporting convention, rather than inventing 100%.

A **threshold** can convert a numerical score into a classification. Changing it
changes the decision rule and can trade missed cases against unnecessary review.
Not every pair of changes improves both precision and recall as our deliberately
chosen variation did. Include the threshold and reference-label process in a report.

### 2) **Distinguish fitting and evidence failures**

**Overfitting** means fitting particular available examples or noise in ways that
do not generalize adequately. High training scores and lower independent scores
can raise that concern; a gap alone does not establish its cause. Population shifts,
label differences and preparation errors also deserve investigation.

**Bias** needs context. It can mean a model's built-in assumptions, a statistical
systematic error, skew in data collection or harmful disparities across people.
These meanings are related questions, not interchangeable diagnoses. Ask which
population, measurement and consequence the speaker means. An aggregate score can
hide uneven performance without identifying why the difference exists.

**Data leakage** lets information influence model building or evaluation that
should not be available for the stated prediction/evaluation task. Examples include
using a later resolution code to route an arriving ticket, fitting preprocessing
on held-out data, or splitting near-duplicate messages across training and evaluation
so that supposed novelty is compromised. The [scikit-learn pitfalls discussion](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)
shows why preparation belongs inside the separation too. A pipeline can help enforce
correct fitting boundaries; its mere presence does not detect every leakage path.

Leakage can make a score optimistic even when the proposed model is simple. It is
not just another name for overfitting or unauthorized disclosure. Data privacy and
ML evaluation separation are different concerns that can coexist.

### 3) **Challenge a quality score**

A proposal reports the first matrix as “96% reliable for all customer support.”
Its packet says the 100 cases came from one team's archived messages, duplicates
were not checked and the final resolution code was an input. This supports the
arithmetic for those supplied labels, not the broad capability claim. The unavailable
input and possible overlap undermine the proposed evidence. The narrow source also
leaves other teams, languages and current traffic unestablished.

Ask for a split matching the intended prediction time and grouping, input availability,
label review, population coverage and a decision threshold chosen under an appropriate
evaluation design. Name error costs: missing urgent cases and sending routine cases
to scarce reviewers have different consequences. The appropriate release criterion
is a product and risk decision, not whichever metric looks highest.

Removing the later code fixes one identified input defect in the design. It does
not produce a new measured score, remove possible duplicates or establish an
acceptable urgent-case recall. Keep the old result with its limitation rather than
silently carrying 96% over to a changed model or dataset.

### 4) **Common confusion**

Precision is not the same as the number of decimal places. Recall is not a model's
ability to remember a conversation. Accuracy does not mean every output is 96%
correct. Each metric summarizes a defined collection under reference labels and a
decision rule, and its interpretation depends on that collection.

### 5) **Performance note**

ML “performance” may mean predictive quality or computational speed. State which.
Higher recall can increase downstream review work; it does not automatically change
inference latency. Our counts establish neither production quality nor resource cost.

### 6) **Mentor note**

Hide the percentages and ask the learner to explain each denominator before
calculating it. Then supply the extra true positive and the no-flags baseline.
A sound answer handles undefined precision explicitly and challenges the population
claim independently of whether the arithmetic is correct.
