## 3.1. Foundation models LLMs tokens prompts context windows and embeddings

“The LLM remembers our entire knowledge base because it has a large context
window.” This combines model training, supplied input and application storage.
A larger capacity does not establish what information was actually present or
correctly used in one response.

### 1) **Separate model families from applications**

A **foundation model** is trained on broad data and can be adapted to downstream
tasks. The originating [Stanford report](https://crfm.stanford.edu/report.html)
introduced the term to emphasize a broadly reusable but incomplete foundation.
It includes more than language models, and does not mean a model works well for
every task without evaluation.

A **large language model (LLM)** models language at scale and can be used for tasks
such as generation, classification or extraction. Many generate text by predicting
successive tokens conditional on context. “Large” has no single enduring size
threshold. A chat product combines a model with instructions, storage, tools and
other application behavior. Do not attribute every product capability to its
underlying model or treat fluent output as evidence of factual correctness.

### 2) **Read model input and representation limits**

A **token** is a unit used by a particular tokenizer/model representation. Text
tokens may correspond to words, word parts, punctuation or other encoded pieces.
Token counts depend on the tokenizer and content; one token is not universally
one word or a fixed number of characters. [Hugging Face's tokenization explanation](https://huggingface.co/docs/transformers/tokenizer_summary)
shows why word pieces can differ by vocabulary. Security access tokens and lexical
tokens in programming are different uses of the same word.

A **prompt** is input supplied to guide a response. An application may construct
it from instructions, a user message, selected conversation history, retrieved
passages and tool results. The visible chat message may be only part of what the
model receives. Conversely, the application's saved history need not all be included
in the current model call.

The **context window** is a model-specific capacity for the information processed
in a request and, under its counting rules, generation. Input and output limits,
reasoning accounting, truncation and service behavior require the current model/API
reference. [Anthropic's context documentation](https://platform.claude.com/docs/en/build-with-claude/context-windows)
is a concrete example of provider-specific accounting; no numerical product limit
is adopted here as universal. Capacity is not a guarantee of equally effective use
of every included detail or persistent memory across calls.

An **embedding** represents an item as numbers in a learned space. A retrieval
system can compare compatible query and document embeddings to find candidates.
[Google's embedding-space lesson](https://developers.google.com/machine-learning/crash-course/embeddings/embedding-space)
explains representations in terms of distances and relationships. Similarity depends
on model, representation and comparison method. A nearby vector is not proof that
a passage answers the question, is true or is authorized for this caller.

### 3) **Inspect a context claim**

Consider an original fictional reading packet. Its token counts are stipulated
for a toy model, not measured using a real tokenizer.

| Item | Supplied information |
|---|---|
| Toy request budget | 100 units shared by supplied input and maximum generated output |
| Instructions and question | 20 units |
| Selected passages | 50 units: documents A and B |
| Reserved output | 30 units |
| Saved application store | Documents A, B and C; C contains the revised refund rule |
| Retrieval | A and B were selected by embedding similarity; C was not selected |
| Claim | “All saved documents fit, so the answer applies the revised rule” |

The stipulated request uses 20 + 50 + 30 = 100 units. Only A and B were supplied;
C's presence in storage does not place its revised rule in the context. The packet
therefore cannot support the claim that this response applied C. Even if the model
happened to produce the revised answer, that alone would not establish its provenance.

Adding C requires revising the request budget or other content under the toy rule.
Suppose C uses 15 units. The unchanged request would require 115, exceeding the
stipulated capacity. A larger toy budget could resolve the capacity conflict while
still leaving retrieval relevance and answer correctness to assess. Actual providers
may reject, truncate or use other documented behavior; this arithmetic does not
predict which behavior a real service takes.

Now supply C and remove B within a suitable budget. The input contains the revised
rule, but the response still needs checking against it. “Included” and “used
correctly” remain different evidence claims. Later retrieval and evaluation lessons
show how to keep those boundaries visible.

### 4) **Common confusion**

An embedding is not an encrypted copy with an automatic access guarantee. A context
window is not a database, a durable conversation memory or a factual-knowledge
certificate. Distinguish what was trained into parameters, what was supplied now
and what the application can retrieve separately.

### 5) **Performance note**

Input length, output length, model, batching and hardware affect serving cost and
latency. Token count is not a complete speed model, and a larger advertised window
does not establish lower cost or better retrieval. The toy arithmetic measures no
real tokenizer, model latency, retrieval quality or memory consumption.

### 6) **Mentor note**

Ask the learner to mark storage, selected input and generated output as separate
sets. Add C without changing the budget, then enlarge only the budget. A good
answer resolves the arithmetic separately from whether the revised rule was found
and followed. Do not reward invented vendor limit numbers.
