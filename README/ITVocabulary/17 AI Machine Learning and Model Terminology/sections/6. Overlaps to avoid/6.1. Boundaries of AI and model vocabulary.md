## 6.1. Boundaries of AI and model vocabulary

You can identify a leaky evaluation without knowing how to train a neural network.
You can also recognize a RAG design without having implemented safe retrieval.
This domain develops the first kind of competence: interpreting claims, locating
boundaries and requesting evidence. Implementation requires additional study and
verified practice.

### 1) **Separate interpretation from implementation competence**

The [model/task lesson](<../1. Models tasks and data/1.1. AI machine learning deep learning models and algorithms.md>) distinguishes fields,
methods, fitted artifacts and application components. The [data-use lesson](<../1. Models tasks and data/1.2. Features labels datasets training validation and inference.md>)
tracks fitting, selection and prediction. Those outcomes let you detect the wrong
kind of evidence without pretending to know a vendor's hidden training process.

The [metrics lesson](<../2. Statistical and evaluation language/2.1. Accuracy precision recall overfitting bias and data leakage.md>) gives exact denominators
for a small classification case. The [uncertainty lesson](<../2. Statistical and evaluation language/2.2. Correlation causation confidence and uncertainty in model claims.md>)
separates association, causal effects, intervals and model scores. This is not a
statistics course: choosing a valid sampling design, causal identification method
or interval estimator needs the relevant assumptions and specialist work.

Generative-system lessons distinguish [context](<../3. Generative systems/3.1. Foundation models LLMs tokens prompts context windows and embeddings.md>),
[adaptation and retrieval](<../3. Generative systems/3.2. Retrieval RAG grounding fine-tuning and quantization.md>) and [tool execution](<../4. Applications and limitations/4.1. Agents workflows tool calling and model context protocols.md>).
They do not provide a full tokenizer, training stack, search engine or agent runtime.
Likewise, reading [protective-control claims](<../4. Applications and limitations/4.2. Hallucinations evaluations benchmarks guardrails and prompt injection.md>)
is not certification that a deployed system resists attacks.

### 2) **Route deeper questions precisely**

| Actual question | Existing vocabulary owner | Next kind of work |
|---|---|---|
| Why is 96% accuracy missing urgent cases? | Classification metrics | Error analysis, labels and task-specific evaluation |
| Which split matches future tickets? | Data roles and leakage | Temporal/grouped evaluation design and data provenance |
| Does the feature cause faster handling? | Causal claims | Experimental or observational causal study under justified assumptions |
| How do we fit the model? | Training and parameters | ML algorithms, optimization, data preparation and reproducible training |
| How do we retrieve only authorized passages? | Retrieval plus security owners | Application architecture, resource permissions and verified enforcement |
| Why is a tool result uncertain after timeout? | Agent execution plus retry owner | Distributed operation identity, recovery and idempotency implementation |
| Is quantization faster here? | Quantization plus measurement owner | Representative hardware/workload/quality comparison |

These are directions, not a requirement to master every specialty before asking
a useful question. Start with the demonstrated gap. Model training and application
security are different learning goals even when one feature needs both.

For changing APIs and protocols, use version-matched originating documentation.
The MCP lesson anchors its baseline to the current stable revision consulted for
this domain; later protocol changes need an incremental update rather than silently
changing what an older artifact meant. A vendor article is also evidence for its
specified arrangement, not universal model behavior.

### 3) **State a defensible handoff**

Read this constructed message: “We trained the model by uploading new manuals.
It has MCP, a guardrail and 95% confidence, so it can approve refunds reliably.”
No further records are supplied.

A useful handoff says: “Please identify whether upload updated storage, retrieval
or learned parameters; the actual model/application/protocol versions; and what the
95% value measures. Approval needs its own authority and verified action outcome.
Describe the guardrail's enforcement boundary and task evaluation, including wrong
or unsupported answers and permitted actions. Name the owners of those checks
and recovery.”

This handoff does not assert the model is untrained, the service is insecure or
refunds failed. It identifies unsupported inferences. If the next record shows an
index update, credit retrieval preparation while retaining the other unknowns.
If it instead shows an authorized completed refund, credit that specific action
while retaining the general reliability and score questions.

The progression from recognizing a term to judging a claim is the outcome. The
next domain asks you to apply it alongside networking, data, delivery and team
language in unfamiliar artifacts, without repeating the full definitions.

### 4) **Common confusion**

A vocabulary boundary does not make terminology shallow or useless. Correctly
separating a proposal, permission and observed outcome can prevent a serious review
mistake. The limit is treating that interpretation as proof that you can implement
or validate every underlying mechanism.

### 5) **Performance note**

This page changes no executable system. “Model performance” still needs a quality
or resource meaning and an explicit measurement boundary. Ask for both when a
proposal trades task quality against latency or cost; no such trade-off was
measured in this lesson.

### 6) **Mentor note**

Ask the learner to choose the single most consequential gap for a stated decision:
review a draft, authorize a refund, or compare hosting cost. Their first question
should change with the decision. A strong explanation routes deeper work precisely
and avoids both blanket approval and invented failure.
