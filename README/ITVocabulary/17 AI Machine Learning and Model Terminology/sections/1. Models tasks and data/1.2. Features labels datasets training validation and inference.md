## 1.2. Features labels datasets training validation and inference

“The model learned from today's request” may mean a parameter update, or merely
that the request was supplied as input. Those are different operations. Read what
data did, not just which file or API method contained it.

### 1) **Identify inputs targets and dataset roles**

A **feature** is an input attribute or representation used for a task. A **label**
is the target value in a supervised example. For support routing, message text
can be an input and the reviewed routing category its label. “Feature” here does
not mean a product capability, and “label” does not mean any arbitrary metadata
field. A ticket identifier is not automatically a useful predictive feature.

A **dataset** is a collection of examples, with its selection and preparation
history. The general [dataset owner](<../../../08 Databases Storage and Data Pipelines/sections/1. Databases and models/1.1. Data datasets databases and database management systems.md>) explains the broader
term. In ML, ask what population the examples represent, when inputs were available
and how targets were obtained. Human labels can be inconsistent or mistaken;
recorded categories are not automatically perfect truth.

**Parameters** are learned model values, such as fitted weights. A **hyperparameter**
controls model structure or the learning procedure, such as a selected tree-depth
limit. Choosing a setting by looking at evaluation results is still a choice
influenced by those data, even if an engineer makes it manually.

### 2) **Trace fitting selection and prediction**

**Training** fits model parameters using the training data. A **validation set**
guides model or hyperparameter selection. A **test set** provides held-out evidence
for evaluating the selected result under a stated design. Repeatedly selecting
changes using a “test” file makes that file part of selection in substance; its
name cannot preserve independence.

**Inference** uses a model to produce an output for an input. It need not update
parameters. Evaluation often runs inference on examples whose reference labels
are available to the evaluator but withheld from the prediction input. Production
inference is not the only setting where inference occurs. The input preparation
used at prediction time also needs to match the fitted model's expectations.
[Google's supervised-learning explanation](https://developers.google.com/machine-learning/intro-to-ml/supervised)
introduces the feature/label and training/inference relationship.

Consider a fixed classifier version C2. It receives text, returns “access” and
logs the result. Nothing in that sequence establishes learning. A separate
process might later review outcomes and fit C3. **Online learning** can update a
model from arriving data, but a logging or personalization claim alone does not
show such updates. Ask which values change, under what procedure and controls.

### 3) **Inspect a data-use packet**

This original fictional packet describes a proposed routing experiment; it is
not an executed training run.

| Stage | Recorded data use |
|---|---|
| Source | Last year's messages from one English-speaking support team |
| Inputs | Message text plus a “final resolution code” entered after staff finish the case |
| Train file | Used to fit C2 |
| Validation file | Used to choose among depth settings |
| Test file | Compared C2/C3/C4, then selected C4 because it scored highest |
| Deployment proposal | Route a new message immediately on arrival, before resolution |

The validation file guides a setting. The so-called test file also influences
selection, so its reported score is not independent final evidence for the
selected C4. A new evaluation design needs to preserve genuinely held-out evidence;
simply renaming the same file does not repair its past use.

The resolution code is unavailable at the proposed prediction time. Feeding it
to the model gives the experiment information the actual routing task lacks.
This is a data-leakage concern, developed fully in the next lesson. Separately,
one team's English messages do not establish coverage of all teams or languages.
More rows of the same narrow kind need not fill that gap.

A supported rewrite says: “C4 was selected using both named validation and test
results. Independent final evaluation remains outstanding. Remove or redesign
the unavailable input and assess the intended population before interpreting
routing quality.” The [scikit-learn pitfalls guide](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)
explains why evaluation data must not influence fitting or selection. It is an
implementation reference, not a command sequence executed here.

Now remove the resolution code and keep only arrival-time text. That resolves
the identified unavailable-input defect in the proposal. It does not repair
test reuse or establish multilingual coverage. Alternatively, rename the test
file “validation”: the label becomes more honest, while independent evaluation
is still missing. Follow changes through each separate concern.

### 4) **Common confusion**

Training, validation and test describe roles in an evaluation design, not inherent
properties of files. Terminology also varies across tools and research fields.
Explain actual use when names conflict. A prediction can be checked against a
label without that label becoming an input or updating model parameters.

### 5) **Performance note**

Fitting and inference can have very different resource costs. Batch size, input
representation, hardware and model shape matter. Preparing data can also dominate
end-to-end latency. This packet specifies data roles, not timings or a demonstrated
benefit from a training method.

### 6) **Mentor note**

Ask the learner to draw arrows from each dataset to parameter fitting, setting
selection or final measurement. Then remove only the resolution code. A good
explanation repairs one arrow while retaining the other evidence gaps. Do not
require knowledge of a specific ML library to reason about data use.
