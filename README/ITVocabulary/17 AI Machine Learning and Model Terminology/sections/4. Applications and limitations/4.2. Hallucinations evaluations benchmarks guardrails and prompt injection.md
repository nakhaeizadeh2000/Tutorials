## 4.2. Hallucinations evaluations benchmarks guardrails and prompt injection

“The benchmark passed, so the guarded agent cannot hallucinate or leak data.”
A measured task result, a protective mechanism and a universal guarantee are
three different claims. Read what was tested and which boundary was enforced.

### 1) **Classify unsupported output and evaluation evidence**

A **hallucination** is generated content presented as factual despite lacking
support or conflicting with evidence. Inventing a manual section is one example.
The term does not establish deliberate deception, a particular internal cause
or that every surprising answer is wrong. [Google's generative glossary](https://developers.google.com/machine-learning/glossary/generative#hallucination)
uses it for plausible but factually incorrect output. Keep the specific error
and reference evidence rather than letting the label replace diagnosis.

An **evaluation**, often shortened to **eval**, defines a task, environment,
outputs or outcomes to inspect, and grading criteria. A **grader** judges specified
aspects using code, people, models or a combination. A **benchmark** supplies a
specified collection and procedure for comparison. Its score belongs to that
setup: model version, prompts, tools, datasets, attempts, constraints and grader.
[Anthropic's evaluation account](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
separates a task, trial, trace, grader and environmental outcome. An agent saying
“completed” is evidence of its statement, not the completed business action.

Check the reference criteria too. A grader checking only that an answer contains
a citation marker can pass a fabricated citation. A model grader can also make
mistakes. Compare representative judgments with an independently reviewed standard,
inspect disagreements and report limitations. A leaderboard rank cannot substitute
for evidence on the intended users and actions.

### 2) **Locate protective controls and their limits**

A **guardrail** is a control intended to constrain behavior or reduce a stated
risk. It may be an input filter, output check, permission restriction, tool boundary,
human review or another mechanism. The word names no universal algorithm. Ask
what it checks, where it runs and what happens when it rejects or is unavailable.
A prompt asking for care is different from code preventing an unauthorized operation.

**Prompt injection** occurs when input crosses an intended instruction boundary
and influences model behavior inappropriately. Direct input and indirectly retrieved
content can both be involved. An external manual should supply task data, not
become authority to change the application's permissions. [OWASP's prompt-injection guide](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)
distinguishes direct and indirect sources and explains why RAG or fine-tuning does
not eliminate the risk. No malicious payload is needed for this vocabulary exercise.

Retain application-level authorization and least privilege even when model behavior
is uncertain. An output validator can reject malformed JSON while accepting a
well-formed forbidden action. A citation check can help assess source support while
failing to enforce tenant access. Controls answer different questions and need
evidence at their actual enforcement points.

### 3) **Read a bounded evaluation report**

This original fictional packet supplies invented grading records, not evaluation
results produced here.

| Item | Supplied record |
|---|---|
| Collection | Ten handpicked English manual questions |
| Pass rule | Answer contains a bracketed citation marker |
| Results | Nine pass; one fails |
| Reviewed example | “Refunds last 60 days [M8]”; supplied M8 says 14 days |
| Protection | JSON format validator; no tenant permission evidence supplied |
| Indirect content | Retrieved text asks the application to change its operating instructions; no action trace supplied |
| Claim | “90% factual accuracy; injection caused a data breach; protected for every tenant” |

Nine of ten pass the marker rule: 90% marker-check success on selected cases.
The record does not establish factual accuracy. The reviewed answer contradicts
M8 despite its marker. Regrade against the intended criteria, preserving the old
measurement's identity rather than quietly relabeling it.

The retrieved text raises a prompt-injection concern, but without an action or
disclosure trace the packet does not establish a successful breach. The format
validator also supplies no tenant authorization evidence. Avoid both extremes:
claiming safety from the validator and claiming a breach from suspicious input alone.

Now add a trace showing the host rejected an attempted unauthorized tool action
before service contact. That supports this control's successful rejection in this
case. It does not prove all injection attempts fail or fix the false refund answer.
Next, replace the grader with a checked reference comparison and obtain new results.
Only those new results support the revised criterion; do not carry over nine passes.

### 4) **Common confusion**

A refusal and an incorrect answer are different outcomes. A benchmark failure
can reflect a real system defect, an unsuitable task or a broken grader. Likewise,
a hallucination need not involve prompt injection, and attempted injection need
not produce hallucination or a successful unauthorized action.

### 5) **Performance note**

Controls and repeated evaluation trials consume resources. Report latency and
cost beside task quality under the same setup when comparing options. The packet's
90% says nothing about speed, and this lesson runs no benchmark or control test.

### 6) **Mentor note**

Ask the learner to write the narrowest supported result for the grader, factual
answer, suspected injection and validator separately. Then add the rejection trace.
A strong revision credits the observed rejection without upgrading it to universal
protection or ignoring the factual contradiction.
