## 4.1. Agents workflows tool calling and model context protocols

“The agent called a tool, so the refund is complete.” A model may have generated
a proposed call, the host may have rejected it, or a service may have accepted a
job that is still pending. Trace control and execution separately.

### 1) **Identify control and execution responsibilities**

An **AI workflow** arranges model and tool steps, often along predefined code paths.
An **agent** commonly uses model outputs to choose steps or tools dynamically.
Definitions vary: some products call any assisted automation an agent.
[Anthropic's original engineering account](https://www.anthropic.com/engineering/building-effective-agents)
makes this control-path distinction explicitly. It is useful vocabulary rather
than a universal naming rule or proof that a dynamic system is better.

A **tool** exposes a capability such as looking up a case or submitting a request.
**Tool calling** produces or handles a structured request for that capability.
The model can choose a name and arguments; application code, a provider-managed
runtime or another service performs execution. Read which participant actually
runs the operation and which credentials it uses.

An **agent loop** repeatedly obtains a proposed step, applies controls, executes
permitted work, observes results and decides what follows. A stopping condition,
budget, unavailable tool or human decision can end the loop. “Autonomous” needs a
scope: permitted actions, duration, oversight and recovery. It does not mean the
system has unrestricted authority or reliably reaches every goal.

### 2) **Read integration protocol claims**

**Model Context Protocol (MCP)** standardizes communication between applications
and providers of context or tools. In the [2026-07-28 specification](https://modelcontextprotocol.io/specification/2026-07-28),
a **host** is the application using integrations, a **client** is its connector,
and a **server** provides capabilities. Resources, prompt templates and tools
serve different purposes. Exposing a resource is not executing a business action.

MCP is an interface protocol, not a model, complete agent framework or guarantee
that every advertised tool is available and authorized. Read the implemented
protocol revision, capabilities, optional extensions and transport requirements
when assessing compatibility. A server's name or a conforming message does not
prove its output is correct or its requested action appropriate.

Keep application permission separate from interface validity. Arguments can match
a schema while naming a refund the caller may not approve. Authorization, user
intent, tenant boundaries and appropriate confirmation belong in the actual
system design. The earlier security and API lessons own those mechanisms.

### 3) **Trace a proposed tool action**

Use this original fictional trace, not a real tool invocation:

| Stage | Supplied record |
|---|---|
| Goal | Staff member asks for a draft refund recommendation for case K8 |
| Model output | Requests `submit_refund` for K8 |
| Host rule | This task permits reading and drafting only; submission requires separate authority |
| Host outcome | Rejects the call before contacting the refund service |
| Final text | “Refund complete” |

The generated tool request exists, but no service submission occurred. It also
exceeds the stated draft-only task. The final claim contradicts the supplied trace.
A correct summary is: “The proposed submission was rejected; no refund was submitted.
The requested draft still needs to be produced.” Protocol support would not change
the task's permitted scope.

Now vary the packet: submission is authorized and the service returns “job J4
accepted.” That establishes acceptance of a job, not completed payment. The next
appropriate observation is the job's documented outcome. A model's confident
completion sentence cannot fill that gap.

Finally, suppose the service times out after receiving the request. Without
further evidence, the outcome is uncertain; it is not automatically a rejection.
A repeat call can have consequences, so use the existing [retry/idempotency owner](<../../../07 APIs Protocols and Integration/sections/5. Contract behavior and integration risks/5.1. Safe idempotent paginated and rate-limited operations.md>)
for the full distinction. The vocabulary task is to preserve uncertainty and ask
which operation identity and result can be checked, not invent a retry algorithm.

A useful review asks who selects actions, enforces permissions, executes operations,
records outcomes and owns recovery. A model, host and server may each contribute;
none of their labels answers all five questions.

### 4) **Common confusion**

A tool-call argument is a proposal or request, not evidence of execution. A successful
transport or protocol response also need not mean the user's intended business
outcome happened. A tool result can contain untrusted content; being delivered
through an integration does not turn that content into application policy.

### 5) **Performance note**

Repeated model calls and remote actions add latency, cost and possible waiting.
A dynamic loop may use more steps than a fixed workflow. Compare task success,
retries and actual resource use rather than claiming agents or MCP are inherently
faster. No loop, remote request or benchmark ran for this trace.

### 6) **Mentor note**

Have the learner identify the last established boundary in all three variants:
rejected proposal, accepted job and uncertain timeout. Ask for a completion
statement and next observation for each. A strong answer preserves authority and
outcome separately without adding a reflexive retry.
