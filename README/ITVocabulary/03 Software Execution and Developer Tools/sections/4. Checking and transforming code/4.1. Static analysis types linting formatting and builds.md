## 4.1. Static analysis types linting formatting and builds

“The build is green” is useful only when you know what ran. A formatter might
accept the layout while a type checker rejects an argument. A build might produce
files without running application tests. Separate the tools' purposes before
interpreting the result.

Read the preceding compilation and artifact lessons. This page teaches the
meaning and limits of checks, rather than prescribing a language tool configuration.

### 1) **Distinguish structural checks from observed application behavior**

**Static analysis** examines code or a representation of it without executing the
application workload being analyzed. The analysis tool itself runs; “static” does
not mean no software executes anywhere. A syntax check can identify malformed
language constructs. A type checker can reason about permitted values and operations
under a type system and its assumptions.

A **type** describes a category or constraint on values. A **type annotation**
records a declared type in source. **Static type checking** evaluates relevant
relationships before the application operation runs. **Runtime checking** observes
or enforces a condition during execution. Different languages and tools combine
these responsibilities differently. Do not infer runtime enforcement merely from
a type-looking label in source.

For a concrete observation, Python documents that its runtime does not enforce
function and variable annotations in the [typing reference](https://docs.python.org/3.14/library/typing.html).
Tested environment: **CPython 3.14.4 on Linux x86_64**. Save `annotation_observation.py`
and run `python3 annotation_observation.py`; no imports or packages are required.
The string argument is deliberately inconsistent with the annotation.

```python
def twice(value: int) -> int:
    return value * 2

print("Integer input:", twice(21))
print("String input:", twice("go"))
```

Observed output:

```text
Integer input: 42
String input: gogo
```

`int` expresses the intended integer contract for the argument and return value.
The interpreter nevertheless runs both calls; multiplying the string repeats it.
We ran Python, not a separate type checker. The observation establishes that these
annotations did not reject this input during this execution. It does not establish
that a configured static checker would accept the program.

For type-checker assumptions, trusted assertions and runtime validation in
TypeScript, use the [existing checked-contract lesson](<../../../../TypeScript/01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.2. Static checking vs runtime reality trust but verify.md>).
This vocabulary distinction is a prerequisite for reading that evidence correctly,
not a replacement for the language's type-system instruction.

### 2) **Separate lint rules from source formatting**

**Linting** checks code against selected rules. Rules may identify suspicious
operations, unused definitions, project conventions or style issues. ESLint's
[core concepts](https://eslint.org/docs/latest/use/core-concepts/) describes rules
and their configuration. A pass means the selected analysis reported no applicable
violations under that setup; it does not mean every possible bug was checked.
Ignored files, disabled rules and analysis assumptions affect the scope.

A source **formatter** rewrites presentation according to its rules, such as
line layout and spacing. [Prettier's introduction](https://prettier.io/docs/)
explains its source-reprinting approach. This is useful for consistent layout,
but it does not decide whether an invoice calculation matches the business rule.
Do not describe a successful formatting check as a successful application test.

The roles can overlap at the edges. A linter may enforce layout rules, while an
editor can run both lint and format tools. Also, a linter's **report formatter**
may mean the component that renders diagnostics, rather than a tool rewriting
source. Clarify the input and output when “formatter” is ambiguous.

### 3) **Read a build result as the result of its configured steps**

A **build** is a process that prepares software outputs from its inputs. It can
include compilation, source transforms, generated code, resource copying, bundling
or packaging. A **bundler** combines an application's code and resource graph into
delivery outputs. A build may include checks or tests, but the name “build” does
not guarantee that any particular check ran.

Here is a constructed result card, not observed output from a real project:

| Step | Reported result | Supported conclusion |
|---|---|---|
| Format selected source files | Passed | Those files matched that formatter's configured expectations |
| Analyze selected rules | Passed | Those rules reported no violations in their analysis scope |
| Produce delivery archive | Passed | That configured production step reported success |
| Execute application scenarios | Not run | No scenario execution evidence is supplied |

A poor status update is “Everything works.” A precise one is “Formatting, the
selected analysis rules and archive production passed; application scenarios were
not run.” The second statement keeps the useful evidence while exposing the
remaining question. A file left over from an earlier build is also not proof that
the latest build succeeded; associate results with the inputs and run that produced
them.

Practice: the runtime example printed `gogo`, while a fictional report says
“formatting passed.” Is that inconsistent? No. Formatting concerns presentation,
while the observed call exposes a mismatch with the intended type contract.
Ask which check was configured to enforce that contract and whether it ran.

### 4) **Common confusion**

“No diagnostics” does not mean “no defects.” The tool may have checked a limited
set of files or trusted declarations that do not match actual inputs. Conversely,
a diagnostic can describe a deliberate project convention rather than a runtime
failure. Read its rule and context before deciding what correction is appropriate.

A build output is not necessarily checked output. A transform, checker and test
runner can be independent steps. Describe their actual results separately rather
than borrowing confidence from a single green label.

### 5) **Performance note**

Static checks and formatting add development or build work; they do not ordinarily
become application operations merely because they ran beforehand. Generated output
and runtime validation can have separate execution costs. This lesson measures
none of those costs. To investigate a slow build, time the actual stages and
preserve their checking scope instead of disabling an unspecified “slow tool.”

### 6) **Mentor note**

Ask a learner to rewrite the result card as a status update with no unsupported
claim. Then ask which additional evidence would support the integer-only contract
at a runtime boundary. A sound answer separates annotations, static analysis and
actual input validation, rather than adding another generic “build passed” badge.
