## 3.2. Packages modules dependencies and package managers

“Install the package, then import the module” describes two different actions.
Installation makes a distribution available in an environment; importing asks a
language implementation to load code. The installed project's name and the name
used in source do not always match.

Read the library and execution-environment lessons first. The example below
uses only two local files; no downloads, registry account or package manager
installation is required.

### 1) **Distinguish code organization from distribution units**

A **module** is a unit of code with a defined identity and access boundary in its
language ecosystem. For this Python example, a `.py` file supplies an importable
module. Other languages define module boundaries differently; do not turn “one
file” into a universal definition of the word.

A **package** often describes a unit organized for distribution and installation,
including code, metadata and possibly other files. Metadata describes the package,
such as its name and requirements. A package can supply multiple modules; an
application can also use local modules that were never downloaded separately.
The package/module distinction therefore differs from library/application roles.

Python adds another important meaning: an **import package** is a special module
that can contain submodules, while a **distribution package** is an installable
project or distribution file. The [Python Packaging User Guide](https://packaging.python.org/en/latest/discussions/distribution-package-vs-import-package/)
explains the naming relationship: the Pillow distribution supplies the `PIL`
import package. This is an illustration of that documented relationship, not an
instruction to install either name.

Do not guess a download from an unfamiliar import spelling. Consult the project's
installation instructions to identify its intended distribution and environment.
A coincidentally matching registry name is insufficient evidence that it supplies
the code the application expects.

### 2) **Trace a local dependency without confusing import and installation**

A **dependency** is something a component relies on. In code discussions this can
mean another module, library or package needed to build, check or run software.
Name the stage: a compiler can be needed for a build without being part of the
running application. This lesson introduces the relationship; version resolution,
lockfiles and direct/transitive dependency categories belong to the later release
and dependency domain.

Tested environment: **CPython 3.14.4 on Linux x86_64**. Create a new folder and save
the following two files in it. No external packages are used.

`lesson_math.py` defines a reusable operation:

```python
def double(value):
    return value * 2
```

`report.py` imports that operation and uses it:

```python
from lesson_math import double

print("Report result:", double(21))
```

From that folder, run `python3 report.py`. Observed output:

```text
Report result: 42
```

The `def` statement defines a function; its indented `return` produces the result
for its caller. The import makes `double` available to the report. The dependency
relationship is report → lesson_math, while the function call uses the library-like
capability. No installation occurred. Python's [modules tutorial](https://docs.python.org/3.14/tutorial/modules.html)
describes this file-based reuse and importing names from a module.

For a controlled failure, place a copy of `report.py` alone in a second empty
folder and run it there in a fresh Python process with no `PYTHONPATH` override.
In the tested clean environment it exits unsuccessfully with
`ModuleNotFoundError: No module named 'lesson_math'`. The required local module
is unavailable to that run. Restore the two files together for the passing case.
Installing an unrelated registry project is not the appropriate repair for this
missing local file.

### 3) **Identify the package manager and the environment it manages**

A **package manager** helps obtain, install, update or remove packages and track
their declared requirements, according to that ecosystem's rules. It is a tool,
not the same thing as the package contents or the language import mechanism.
A **registry** or package index is a service or collection from which packages
can be discovered and obtained; it is distinct from the client tool using it.

For comparison, npm's [package documentation](https://docs.npmjs.com/about-packages-and-modules/)
describes packages using `package.json` metadata. That is an npm convention,
not a rule that every Python or operating-system package must follow. Read each
manager's contract rather than borrowing another ecosystem's file names.

A constructed status note says: “The editor extension is installed, and a package
installation succeeded.” What remains unknown? Which package manager ran, which
distribution it installed, which environment received it, and whether the intended
runtime can load its modules. An editor extension and a runtime dependency serve
different roles. A successful installation also does not establish that the
application executed correctly or that the dependency is suitable for every use.

Practice: a colleague says a module must be downloaded because the application
imports it. The explained answer is that imports can refer to local code or
standard-library code as well as separately installed distributions. Identify
the module's owner and the intended setup before choosing an installation action.

### 4) **Common confusion**

A library is a reusable capability; a package is an organization or distribution
boundary; a module is a code unit under the language's rules. A single project
can play all three roles. Their names and counts need not align one to one.

An import failure also does not uniquely diagnose “package not installed.” The
example fails because a local file is missing from the new run's environment.
A name, path or environment mismatch can require a different repair.

### 5) **Performance note**

Dependencies can add download, installation, loading and execution work, but the
number of package names alone does not quantify those costs. Some packages contain
large data; others supply little executed code. This example verifies reuse and
a missing-module failure, not import timing, bundle size or package-manager speed.
Measure the stage and actual contents relevant to the application.

### 6) **Mentor note**

Ask a learner to label the example's module, callable capability and dependency
arrow, then explain why no download was needed. Show an unfamiliar import name
and ask how to find its intended owner. A good answer consults the project's
setup rather than treating a guessed registry name as proof.
