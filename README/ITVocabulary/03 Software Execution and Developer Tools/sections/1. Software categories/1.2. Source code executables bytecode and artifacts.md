## 1.2. Source code executables bytecode and artifacts

A build finishes and produces a program, a type declaration and a test report.
All three can be useful outputs, but only some contain executable behavior.
Calling every output “the binary” hides what the next step actually needs.

Read the preceding software-category lesson first. This lesson distinguishes
forms of code and delivery outputs; the following section explains transformation
and execution techniques in more depth.

### 1) **Distinguish source text from execution representations**

**Source code** expresses instructions in a programming language, commonly in
text files that people edit. It can also be generated by another tool. A generated
JavaScript file can be an output of one step and source input to a later step;
“source” does not necessarily mean handwritten.

**Machine code** contains instructions for a processor architecture. An
**executable file** is arranged so that a suitable system or runtime can load and
run its program. A native executable typically includes more than instruction
bytes: it also has format information and data needed for loading. Its CPU
architecture, operating-system conventions and other requirements matter.
Do not promise that a native executable runs on every machine with enough RAM.

**Bytecode** is an instruction representation for a virtual execution machine,
rather than directly the native processor's instruction set. A **virtual machine**
in this context is software that provides an execution model for those instructions.
It is a different meaning from a whole virtualized computer used for hosting.
The executing implementation may interpret bytecode or translate it further.

For a specific example, CPython compiles Python source into a code object with
bytecode used by its interpreter. The official [dis documentation](https://docs.python.org/3.14/library/dis.html)
explicitly treats CPython bytecode as an implementation detail that can change
between releases. Do not infer compatibility with another implementation or Python
version from the word “bytecode.”

### 2) **Observe that preparing code is different from executing it**

Tested environment: **CPython 3.14.4 on Linux x86_64**. Save this complete example
as `code_forms.py` and run `python3 code_forms.py`. It needs no imports or packages.
It compiles and executes only the fixed source string shown here.

```python
source = 'print("Result:", 6 * 7)'
print("Source type:", type(source).__name__)
code = compile(source, "<lesson>", "exec")
print("Compiled type:", type(code).__name__)
print("Before execution")
exec(code)
print("After execution")
```

Observed output:

```text
Source type: str
Compiled type: code
Before execution
Result: 42
After execution
```

`source` is text. `compile` prepares a code object; `"<lesson>"` supplies a
recognizable diagnostic filename, not an output path. The `"exec"` mode says the
input contains statements. `type(...).__name__` displays the kind of object.
The multiplication's printed result appears only when `exec(code)` executes the
prepared code, after “Before execution.” No executable file or saved bytecode
file is created by this example.

These operations are documented in Python's [built-in functions reference](https://docs.python.org/3.14/builtins/functions.html#compile).
Successful preparation does not prove that executing the program will achieve
its intended outcome. Changing the fixed source to a syntactically valid operation
that fails at runtime would preserve that distinction. Do not adapt this experiment
into executing untrusted input; `exec` runs code rather than validating ordinary data.

### 3) **Identify artifacts by their producer and intended consumer**

An **artifact** is an output or retained work product. In a build discussion,
it often means a file or collection produced by the development process. The
term does not require machine code, nor does it prove that the output passed tests.
For a concrete platform convention, GitHub documents
[workflow artifacts](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts)
as retained workflow outputs, including test results and log files as well as binaries.

Consider this constructed inventory, not files generated by the Python example:

| Output | Intended use | What its existence alone does not prove |
|---|---|---|
| Native application executable | Load and run on its supported target | Compatibility with every machine or correctness of every operation |
| Generated JavaScript | Execute in its intended JavaScript environment | Availability of every host capability it uses |
| TypeScript declaration | Describe a programming interface to a type checker | Presence of a matching executable implementation |
| Test report | Record results of the checks it actually describes | Coverage of unperformed cases |
| Compressed delivery archive | Carry a collection to a later step | That every member is itself executable |

The [TypeScript declaration lesson](<../../../../TypeScript/12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.1. Authoring d.ts public API surface.md>)
owns declaration generation and consumer behavior. Here the essential distinction
is that a type description and a runtime implementation serve different consumers.
No TypeScript toolchain is needed to understand that boundary.

Practice: “The artifact uploaded, therefore the application ran.” What is missing?
Upload establishes that some output was stored, assuming the report is accurate.
Ask which artifact was uploaded, which execution step ran, on what target, and
what it observed. A test report can be uploaded even when the application test
failed; reading its contents is a separate evidence step.

### 4) **Common confusion**

“Binary” can mean non-text data generally, or shorthand for a built executable.
An image is binary data but is not thereby a native program. Clarify which use
is intended before choosing a tool or diagnosing a launch failure.

“Compiled” also does not necessarily mean “ready to run directly on this CPU.”
This example produced an in-memory CPython code object. Other pipelines produce
native executables, intermediate objects or another language's source.

### 5) **Performance note**

Representations can change loading, storage and preparation costs, but their
names alone do not establish a faster program. Bytecode may avoid repeating
some preparation; native code still has loading and runtime requirements.
This example observes order and object types, not preparation speed or steady
execution performance. Compare the same workload and environment before making
a performance claim about a representation.

### 6) **Mentor note**

Ask the learner to label each output with its next consumer: processor/system
loader, language implementation, type checker or human reviewer. Then ask which
step would need to run to support a claim about behavior. A sound explanation
separates “produced,” “accepted by the next tool” and “executed with an observed result.”
