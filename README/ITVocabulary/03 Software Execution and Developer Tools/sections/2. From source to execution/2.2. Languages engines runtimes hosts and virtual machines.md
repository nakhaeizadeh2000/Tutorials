## 2.2. Languages engines runtimes hosts and virtual machines

“The language supports it” and “our application can use it here” are different
claims. A language defines behavior, an implementation executes it, and the
surrounding environment supplies capabilities and restrictions. You need these
layers to explain a failure without blaming the wrong component.

Read the preceding code-form and execution-technique lessons. This page owns
the general vocabulary; JavaScript's detailed engine and host mechanics remain
in its existing language track.

### 1) **Separate a language definition from an executing implementation**

A **programming language** defines how programs are expressed and what their
constructs mean. An **implementation** provides machinery that accepts and
executes programs according to some version of that language. It can contain
compilers, interpreters and supporting libraries. Python and CPython therefore
name different things: the language and a particular implementation.

An **engine** commonly names the execution machinery for a language or another
specialized task. A JavaScript engine executes JavaScript; a database engine
processes database operations. The word needs its subject. It does not always
name a standalone application that includes every facility an application needs.

The V8 project's [embedding guide](https://v8.dev/docs/embed) illustrates this
boundary: an application can embed the JavaScript engine and expose additional
application operations to the executed code. That guide is written for C++
implementers; we use its component relationship here, without building V8 or
requiring C++ as a prerequisite.

### 2) **Distinguish runtime host and virtual-machine meanings**

A **runtime environment** provides the machinery and services needed while a
program executes. Depending on the ecosystem, “runtime” can include language
execution, libraries, memory management and platform interfaces. It can also
mean the execution phase itself: a “runtime failure” is a failure while running,
rather than the name of another installed product.

A **host** is the environment or application in which something executes. In
JavaScript discussions it may mean a browser or another embedding application.
In infrastructure discussions a host may instead mean a computer running a
workload. Ask what is hosted and which boundary is being discussed.
Node.js describes itself as a JavaScript runtime in its official
[project overview](https://nodejs.org/en/about); that identifies a software role,
not another source language or an application framework.

| Statement | Meaning to clarify |
|---|---|
| The host provides file access | Which embedding environment, API and permissions? |
| The runtime version changed | Which installed implementation and version? |
| The error occurred at runtime | Which operation executed, and what failed? |
| The application runs in a VM | A language execution machine or a virtualized computer? |

A **virtual machine**, or **VM**, can describe an abstract execution machine
with its own instruction model, as in the preceding bytecode lesson. The
[Java Virtual Machine specification, section 1.2](https://docs.oracle.com/javase/specs/jvms/se25/html/jvms-1.html#jvms-1.2)
describes such a machine without requiring one particular implementation
technology. A VM does not inherently mean “an interpreter only.”

The same abbreviation is used for a virtualized computer that can run an
operating system. That infrastructure meaning will be developed later in this
track. A Java application running on a JVM might itself be inside an infrastructure
VM. Those are two different boundaries, not redundant descriptions of one layer.

### 3) **Collect identity evidence without treating it as a capability test**

Tested environment: **CPython 3.14.4, Linux x86_64**. Save `execution_identity.py`
and run `python3 execution_identity.py` in the same folder. It imports only
standard-library modules; it reads metadata and makes no configuration changes.

```python
import platform
import sys

print("Language version:", platform.python_version())
print("Implementation:", sys.implementation.name)
print("Operating-system platform:", sys.platform)
```

Observed output:

```text
Language version: 3.14.4
Implementation: cpython
Operating-system platform: linux
```

The version and implementation fields answer separate questions even though
CPython's release numbering normally aligns them. Python documents the
implementation identifier in its [sys reference](https://docs.python.org/3.14/library/sys.html#sys.implementation).
The last line reports an operating-system platform label; it does not identify
every detail of the machine or prove an operation is permitted.

Suppose a constructed application report says: “Python 3.14 is present, therefore
the application can write this output file.” Version evidence alone cannot
establish file permissions, destination availability or installed third-party
libraries. Record the implementation and platform, then test the specific
capability through its documented interface in the intended environment.
A permission failure does not by itself imply that Python's language definition
is broken.

This also refines portability claims. Code can use ordinary language constructs
while depending on an unavailable platform API or external library. A clear
compatibility statement names the supported implementations, versions and
required capabilities rather than relying only on a language logo.

### 4) **Common confusion**

“Engine,” “runtime” and “host” are useful roles, not universally disjoint product
categories. One application can embed an engine, provide runtime services and
act as a host. Draw the responsibilities first; attach the publisher's names
second. Avoid a rigid equation that claims every ecosystem packages them alike.

A VM label alone also does not prove isolation, security or portability. Those
properties depend on the actual implementation, configuration and contract.
The JVM example establishes an instruction-model meaning, not a promise that
untrusted programs cannot cause harm.

### 5) **Performance note**

An implementation, configuration or host can affect execution costs and available
resources. The language name alone cannot predict those costs. The example only
reads identity fields; it benchmarks no engine or VM. A useful comparison needs
the same workload, relevant versions and stated environment constraints.

### 6) **Mentor note**

Ask a learner to explain a missing capability using four blanks: language,
implementation, host, and required operation. Then ask whether “runtime” names a
component or a phase in the original report. A sound answer identifies the layer
and the next evidence needed without assuming that naming the layer fixes it.
