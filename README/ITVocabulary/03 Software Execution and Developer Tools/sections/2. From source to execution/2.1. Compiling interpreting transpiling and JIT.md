## 2.1. Compiling interpreting transpiling and JIT

“Python is interpreted, so it has no compiler.” “The TypeScript compiler made
an executable for the CPU.” Both statements collapse several different steps.
Describe what consumes the code, what it produces and when that work happens.
Those questions are more useful than placing every language in one permanent box.

Read the [code forms lesson](<../1. Software categories/1.2. Source code executables bytecode and artifacts.md>)
first. It introduces source, machine code, bytecode and the difference between
preparing code and executing it.

### 1) **Describe compilation and interpretation as implementation steps**

**Compilation** translates code into another representation. The result might be
machine code, bytecode or another language's source. A **compiler** performs that
translation. The word alone does not specify the output or guarantee correctness
of the program's intended behavior.

**Interpretation** executes the operations described by a representation using an
interpreter. That representation can already be the output of compilation.
For example, CPython's documented source-to-bytecode path combines a compiler and
an interpreter; see the [Python bytecode glossary entry](https://docs.python.org/3.14/glossary.html#term-bytecode).
Calling this implementation “interpreted” does not remove its compilation step.

**Ahead-of-time**, often abbreviated **AOT**, places compilation before the
execution phase being discussed. State the boundary: a deployment build might
compile code before a user launches the application. It can still leave work for
the loader or runtime. A language's specification and a particular implementation's
pipeline are different things.

| Better description | Question it answers |
|---|---|
| This compiler emits native code for this target | What representation and target are produced? |
| This implementation compiles source to bytecode and interprets it | How are preparation and execution combined? |
| This build emits JavaScript before delivery | What happens before the target runtime receives code? |

### 2) **Distinguish source transformation from runtime capabilities**

**Transpilation** usually means source-to-source compilation, such as translating
supported TypeScript syntax into JavaScript. It is not the opposite of compilation;
it names a kind of translation. Teams may use “compile” and “transpile” differently,
so ask for the actual inputs, outputs and enabled checks.

The [TypeScript handbook's erased-types explanation](https://www.typescriptlang.org/docs/handbook/typescript-from-scratch.html#erased-types)
explains that type information is removed from emitted JavaScript. That does not
turn a type annotation into a runtime input check. A transform and a type-checking
step can also be separate tools; the later static-analysis lesson distinguishes
what each establishes.

A **polyfill** supplies an implementation of a missing runtime API, commonly
installed into the expected global location. Rewriting syntax does not by itself
supply every operation that code calls. If a transform leaves a call to an
unavailable library or host function, execution can still fail. Detailed
[JavaScript transpilation and polyfills](<../../../../JavaScript/01 Fundamentals and Mental Model/sections/3. Running JavaScript today/3.4. Transpilation polyfills and baseline strategy.md>)
belong to their existing owner; the vocabulary here identifies the two jobs.

### 3) **Place JIT and failures on the execution timeline**

**JIT** means **just-in-time compilation**: compilation occurs during execution,
often translating selected code to native instructions. An implementation can
start with interpretation and later compile some code; not every function must
follow an identical path. JIT is an implementation technique, not a separate
source language or a promise of one universal speedup.

Configuration matters too. The V8 team's original
[JIT-less V8 article](https://v8.dev/blog/jitless), published in 2019 for V8 7.4,
describes an interpreter-oriented mode and its measured trade-offs. It is a
concrete counterexample to assuming that a language name fixes one execution
strategy. Its historical benchmark numbers are not predictions for your machine
or a statement of today's default configuration.

This complete failure-stage observation was tested on **CPython 3.14.4, Linux
x86_64**. Save `failure_stages.py` and run `python3 failure_stages.py`; no imports
or packages are needed. The two source strings are fixed demonstration inputs.

```python
try:
    compile("1 +", "<invalid>", "eval")
except SyntaxError:
    print("Invalid expression: preparation failed")

code = compile("1 / 0", "<valid>", "eval")
print("Division expression: preparation passed")
try:
    eval(code)
except ZeroDivisionError:
    print("Division expression: execution failed")
```

Observed output:

```text
Invalid expression: preparation failed
Division expression: preparation passed
Division expression: execution failed
```

`"eval"` selects a single expression. The incomplete expression cannot be
prepared. The division expression is valid Python syntax, but its execution
raises an exception. These are CPython observations; other languages can define
division by zero differently. `eval` executes code, so this demonstration is
not a method for accepting untrusted text as data.

Practice: “A source transform passed, so every operation is supported on the
target.” What must be checked? Identify the emitted representation, the target's
syntax and API support, any required helpers or libraries, and actual execution
evidence. Passing one translation step establishes only that step's result.

### 4) **Common confusion**

Interpreted execution does not mean reading source text afresh for each operation.
Compilation does not necessarily mean native machine code. Both misconceptions
come from treating familiar tool arrangements as definitions of all languages.
Name the actual implementation and transformation instead.

JIT also differs from transpilation: one describes compilation timing during
execution; the other describes a source-to-source relationship. A pipeline can
use both at different stages.

### 5) **Performance note**

Compilation consumes time and memory; a runtime may spend that work to improve
later execution. Short-lived and long-running workloads can experience different
trade-offs. This lesson measures no compile duration, warmup or execution speed.
Do not rank languages from these labels or transfer V8's 2019 benchmark results
to an unrelated current workload.

### 6) **Mentor note**

Ask a learner to draw input → transformation → output → execution for a named
implementation. Then place each observed failure on that path. A strong answer
allows compilation and interpretation to coexist and explains why successful
preparation leaves runtime questions unanswered.
