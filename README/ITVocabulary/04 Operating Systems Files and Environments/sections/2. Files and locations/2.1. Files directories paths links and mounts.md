## 2.1. Files directories paths links and mounts

A program finds `notes.txt` when launched from one folder and fails from another.
Two names can refer to the same file, while one unchanged path can expose different
contents after a filesystem is mounted. A path is a lookup instruction in a
particular environment, not a permanent global identity for data.

Read the OS and process lessons first. Concrete path and link observations below
use Linux; other operating systems and filesystems have their own naming rules.
No mount, disk format or administrator operation is performed.

### 1) **Resolve a location from its starting point and path components**

A **file** is an object exposed through a filesystem; ordinary files commonly
hold bytes such as text or program data. A **directory**, commonly called a
**folder**, organizes named entries. A **filesystem** supplies the organization
and operations through which those objects are accessed. Not every filesystem
entry is an ordinary stored document: directories, links and device interfaces
can have different behavior.

A **path** describes a location through named components. On Linux, an
**absolute path** starts with `/`, the root of the process's filesystem view.
A **relative path** needs a starting directory. Ordinary relative file access
commonly starts from the process's **current working directory**, or **CWD**.
An application can deliberately choose another base, so check its documented
rule for a configuration path. See Linux's
[path resolution reference](https://man7.org/linux/man-pages/man7/path_resolution.7.html).

Consider these constructed Linux lookups with no intervening links or mounts:

| Working directory | Relative path | Intended location |
|---|---|---|
| `/work/project` | `notes.txt` | `/work/project/notes.txt` |
| `/work` | `notes.txt` | `/work/notes.txt` |
| `/work/project` | `../notes.txt` | `/work/notes.txt` |

`.` names the current directory and `..` its parent in this model. The first two
rows explain the launch-location failure: the same relative spelling starts
elsewhere. A source file's directory is not automatically the running process's
working directory. Record both when investigating a missing configuration file.
Do not assume that replacing every path with an absolute path solves deployment;
the target still needs the intended filesystem view and access.

### 2) **Distinguish a second name from a copy or a symbolic target**

A **hard link** is another directory entry for the same underlying file object.
It is not an independent copy. On the Linux filesystems considered here, hard
links to ordinary files stay within one filesystem. A **symbolic link**, or
**symlink**, instead stores a path to a target. It can refer across filesystem
boundaries, and its target need not currently exist. A link whose target path
does not resolve is often called a **dangling** or **broken link**. Linux's
[link-handling manual](https://man7.org/linux/man-pages/man7/symlink.7.html)
explains these distinctions.

Tested environment: **CPython 3.14.4 on Linux x86_64**, on a filesystem supporting
both link types. Save `file_names.py` and run `python3 file_names.py`. It uses only
the standard library and changes files exclusively inside its own automatically
cleaned temporary directory.

```python
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as folder:
    base = Path(folder)
    target = base / "notes.txt"
    target.write_text("hello", encoding="utf-8")
    alias = base / "alias.txt"
    alias.symlink_to("notes.txt")
    hard = base / "hard.txt"
    hard.hardlink_to(target)
    print("Symbolic link reaches same file:", alias.samefile(target))
    print("Hard link reaches same file:", hard.samefile(target))
    target.rename(base / "renamed.txt")
    print("Symbolic link still exists as a link:", alias.is_symlink())
    print("Symbolic link reaches an existing target:", alias.exists())
    print("Hard link text after rename:", hard.read_text(encoding="utf-8"))
```

Observed output:

```text
Symbolic link reaches same file: True
Hard link reaches same file: True
Symbolic link still exists as a link: True
Symbolic link reaches an existing target: False
Hard link text after rename: hello
```

`Path` represents a path; `/` joins a base with a child name in this API. The
`with` block keeps all operations inside the lifetime of the temporary directory.
Python's [pathlib reference](https://docs.python.org/3.14/library/pathlib.html)
documents the link, comparison and rename operations used here.

The symlink's relative `notes.txt` target is interpreted from the link's containing
directory. Initially both link names reach the original file. Renaming `notes.txt`
to `renamed.txt` leaves the symlink's stored path unchanged, so that path stops
resolving. `is_symlink()` can still identify the link itself; `exists()` follows
its target in this example. The hard link still names the underlying object.
Neither link was an independent backup of the text.

The example does not establish identical support on every filesystem or on
Windows, where link creation and path conventions can differ. If link creation
is unavailable, that condition must be recorded rather than reporting the
expected result as a local observation.

### 3) **Include mounts and the process view in a location claim**

A **mount** attaches a filesystem or filesystem view at a location called a
**mount point**. Linux's [mount manual](https://man7.org/linux/man-pages/man8/mount.8.html)
describes how a mounted filesystem becomes visible through a directory. The
underlying content previously visible there can be hidden by the mount without
being deleted. The storage might be local, remote or supplied virtually; a
normal-looking path does not identify the backing device by itself.

Imagine a constructed deployment where `/data` should expose a mounted dataset.
If that mount is absent, `/data` might still be an ordinary directory with different
contents. A “directory exists” check alone cannot establish that the expected
dataset is available. Ask what is mounted and what view the running process sees.
This is an evidence question, not an instruction to mount or unmount anything.

Practice: two programs report different contents for `/data/config.txt`. Does one
have to be lying? No. They may run on different machines or see different filesystem
views. First establish the machine, process view, mount state and relevant time.
Then compare the actual objects. An absolute path removes one starting-directory
ambiguity; it does not create a universal file identity.

### 4) **Common confusion**

A folder is not necessarily a disk, and a mount point is not necessarily a separate
physical drive. A filesystem view can join several resources into one hierarchy.
Likewise, “the link exists” and “the target exists” are distinct checks, as the
observed dangling symlink shows.

A hard link is also not a safety copy. Because both names refer to the same object,
changing its contents through either name is not independent preservation of an
older version. Backups and restoration have different goals.

### 5) **Performance note**

A path's spelling does not tell you its storage latency. Local, network-backed
and virtual filesystems can perform different work behind similar names. Links
also do not guarantee a speedup or a complete duplicated copy. This experiment
observes names and identity, not lookup timing, disk throughput or backup cost.

### 6) **Mentor note**

Ask a learner to predict both link results before the rename, then distinguish
checking the link from following it afterward. For a missing configuration report,
require the working directory and the path's interpretation rule before suggesting
a path edit. A sound answer includes the filesystem view when an absolute path
still disagrees across environments.
