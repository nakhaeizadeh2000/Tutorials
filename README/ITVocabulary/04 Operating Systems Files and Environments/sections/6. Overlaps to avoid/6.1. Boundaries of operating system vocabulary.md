## 6.1. Boundaries of operating system vocabulary

You can now ask which process attempted an operation, where it looked, which
identity and configuration applied, and how its outcome was reported. These
questions make execution descriptions intelligible. They do not replace the
engineering needed to administer the machine or implement its operating system.

This closing lesson routes questions to the explanation that owns them. The
handoff exercise is constructed text, not a system inspection or repair.

### 1) **Keep interpretation separate from system administration**

Recognizing a term helps identify the next evidence question. Administration
changes an operating environment: it can involve accounts, access rules, services,
filesystems and resource policies. OS internals study explains mechanisms such
as scheduling and memory mapping. Those are distinct next learning tasks.

| Question | What this domain establishes | What deeper work must establish |
|---|---|---|
| “Is this an OS API or a system call?” | Locate the application/kernel boundary and state the trace's scope. | Implement or analyze the particular OS mechanism. |
| “Which process is the service?” | Separate managed activity from one running instance. | Configure supervision, startup, shutdown and recovery policy. |
| “Why is the file missing?” | Check path base, target and filesystem view. | Provision storage and manage mounts correctly for the deployment. |
| “Why is access denied?” | Identify actor, operation, resource and applicable policy evidence. | Design and apply access rules for real accounts and workloads. |
| “What limit was reached?” | Name resource, usage measure, scope and reported failure. | Select a justified resource policy and verify its effects. |

The repository's planned Linux & Shell and Operating Systems & System Fundamentals
tracks are appropriate future study for administration and internals respectively.
They are not published prerequisites or live links here. If you need a concrete
procedure now, consult the manual for the actual platform/version and establish
what change the task requires. A vocabulary exercise does not itself supply an
operational change plan.

Avoid turning a definition into a repair instruction. Knowing that a mount can
hide earlier directory contents does not tell you which filesystem should be
attached, whether workloads are using it or what recovery process applies.
Likewise, a permission error does not justify granting every actor more access.
The missing context is part of the work, not an inconvenience to ignore.

### 2) **Send language and delivery questions to their actual owners**

A language runtime uses OS resources, but its concepts do not map one-to-one onto
OS counters. A garbage collector determines language-object reachability under
its implementation. The OS manages the process's mappings and residency. Use the
[JavaScript memory model](<../../../../JavaScript/18 Memory Management and GC/sections/1. Memory model/1.1. Heap stack execution contexts and references how values live.md>)
for that language's lifetime reasoning; use this domain's measurement distinctions
when interpreting a process report. Do not reproduce an entire garbage-collection
lesson under “heap,” or infer an object leak solely from a large address space.

The same boundary applies to execution. Knowing that a process contains threads
does not predict a language's callback order. JavaScript's
[async domain](<../../../../JavaScript/13 Async Event Loop and Promises/README.md>)
owns that scheduling detail. General concurrency vocabulary appears later in
this track; it will compare progress and waiting across interfaces without
replacing language semantics.

Keep these additional routes precise:

- For which interpreter, module or build artifact actually ran, return to
  [toolchain diagnosis](<../../../03 Software Execution and Developer Tools/sections/5. Applied diagnosis/5.1. Read a toolchain diagram and classify a failure.md>).
- For how a relative name locates a file, use the
  [path owner](<../2. Files and locations/2.1. Files directories paths links and mounts.md>).
- For which configuration source wins, use the application's documented contract
  and the [configuration distinction](<../3. Configuration and access/3.2. Environment variables configuration and secrets.md>).
  Process inheritance does not prescribe application precedence.
- For whether an API caller may read a business record, investigate application
  authorization. OS file permission vocabulary alone does not explain that policy.

Later approved infrastructure and security domains will introduce delivery,
isolation and identity terminology. Their detailed implementation belongs in the
corresponding subject tracks. A future topic is a learning route, not evidence
that its mechanism has already been taught or configured.

### 3) **Write a handoff that preserves the unresolved question**

Practice with this fictional message:

> “The service restarted, its PID changed, the new process has the same environment,
> and heap memory is still high. Give it more RAM and mark the leak fixed.”

Write an answer before reading the explanation. Which observations are useful,
which words need clarification, and what conclusion is unsupported?

The explained answer preserves the restart/PID report as evidence of a different
running instance in the stated observation context. It asks what “same environment”
means: deployed settings, selected process variables or the entire machine context?
It asks which “heap” counter was recorded, with its value, unit, tool, workload
and time. It does not repeat secret values in a shared handoff.

The proposed leak diagnosis is unsupported. A high value alone does not establish
unintended retention, and a capacity increase is not proof of a corrected lifecycle.
Route object-retention investigation to the runtime memory owner and resource
policy to the responsible operational work. If a temporary capacity change is
chosen for a separate reason, report its observed effect separately from evidence
of a durable correction. No restart, memory change or leak repair was performed
by reading this exercise.

A concise handoff could say: “Confirm the new process identity and effective
nonsecret settings. Identify the reported memory counter and compare the same
workload over time. We have a high-value report, not yet evidence of a leak or
of a repair. The next investigation depends on whether the counter describes
runtime allocations or OS residency.” This gives a teammate an answerable task.

### 4) **Common confusion**

An overlap boundary does not mean that related systems are independent. Runtime
allocation can affect process resource use, and access rules can affect file
operations. The boundary identifies where the complete explanation belongs so
that the same concept does not acquire conflicting definitions across lessons.

A service restart is also not proof of a fixed defect. It may replace an instance
while leaving the triggering condition intact. Preserve the distinction between
an action, an observed result and a causal explanation.

### 5) **Performance note**

Routing a question to its owner has no direct execution-speed effect. Its practical
value is selecting the relevant measurement before changing resources. A runtime
counter and an OS counter may both be useful while answering different questions.
This lesson measures neither memory behavior nor service recovery performance.

### 6) **Mentor note**

Ask the learner to turn the fictional message into two work items: one that
clarifies evidence and one that could investigate a mechanism after clarification.
A strong answer avoids inventing a root cause, names the appropriate owner and
states what result would support the eventual conclusion. Memorizing OS nouns
without that boundary awareness is not yet diagnostic competence.
