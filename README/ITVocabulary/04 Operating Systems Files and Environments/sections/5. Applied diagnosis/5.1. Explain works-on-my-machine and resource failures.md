## 5.1. Explain works-on-my-machine and resource failures

“It works on my machine” describes an observation in one environment. It does not
identify why another run differs. The useful next step is to make the comparison
specific enough that someone can reproduce it, rather than assigning blame to a
machine, developer or operating system.

This synthesis uses the earlier OS lessons. All report cards below are
**constructed reading exercises**, not observations from a deployed application.
They require no commands, account changes or resource exhaustion.

### 1) **Turn a machine comparison into specific evidence questions**

Start with the operation: which input should produce which output? A successful
startup is not the same outcome as a completed export. Then identify the running
artifact and its context. Two people can have identical source text while running
different builds, dependency sets or interpreters.

Use the following questions selectively. Request the evidence relevant to the
failing operation, not a dump of every system setting.

| Dimension | Concrete question | Why the distinction matters |
|---|---|---|
| Artifact and input | Which output artifact and input were actually used? | Matching repository names do not establish matching bytes. |
| Runtime | Which implementation and version launched it? | An installed version is not necessarily the selected version. |
| Location | What was the working directory and how was the path interpreted? | Relative paths may select another location. |
| Access | Which process identity attempted which operation on which object? | A developer's interactive access does not establish service access. |
| Configuration | Which documented source supplied the effective nonsecret setting? | A default or file on disk may not be the selected value. |
| Resources | What usage, limit and failure were recorded for that process at that time? | Machine totals do not describe every process restriction. |
| Outcome | What were the result, diagnostics and completion status? | A printed line alone does not establish completion. |

Each dimension has its full explanation in an earlier owner. This page teaches
how to combine the questions into a diagnosis. Julia Evans's
[debugging discussion](https://jvns.ca/blog/2019/06/23/a-few-debugging-resources/)
provides useful practice in checking assumptions and testing a focused guess.
Use experiments to discriminate explanations; avoid treating a familiar error
message as proof of its most familiar cause.

### 2) **Diagnose the constructed report without changing every variable**

An export tool is documented to read `settings.json` relative to its working
directory. Here is the fictional comparison, with no links or mounts affecting
the stated paths:

| Evidence | Run A | Run B |
|---|---|---|
| Export artifact and input | Same recorded checksums | Same recorded checksums |
| Interpreter | CPython 3.14.4 | CPython 3.14.4 |
| Working directory | `/srv/export` | `/srv` |
| Configuration file | `/srv/export/settings.json` present | `/srv/export/settings.json` present |
| Attempted open | `/srv/export/settings.json` | `/srv/settings.json` |
| Result | Expected export completed, status 0 | Missing-file error, status 2 |

Before reading on, identify the strongest explanation and one targeted test.

The explained answer is a **location mismatch**: Run B resolves the relative
configuration name from a different base. The file's presence under `/srv/export`
does not contradict its absence at the attempted location. Matching interpreters
and artifacts make those differences less useful initial guesses for this card;
they do not prove universal compatibility of the application.

A suitable test launches the same artifact and input with the documented working
directory while preserving the other relevant conditions. Alternatively, if the
tool supports an explicit configuration path, test that documented interface.
Do not invent an unsupported option. If the rerun completes with the expected
output, record which condition changed and what outcome was observed. The result
supports this explanation for the reproduced case, not every deployment.

Changing the interpreter, permissions, configuration contents and working directory
at once may produce a passing run but leaves the causal explanation unclear.
Giving the process broader permissions is especially unhelpful here: no denial
was reported, and broader access does not place a file at the missing location.
A copied configuration file might hide the launch error and later diverge from
the intended source. Prefer a deliberate launch/configuration contract.

A useful handoff says: “Run B attempted `/srv/settings.json` because its working
directory was `/srv`; the documented base is `/srv/export`. Test the launch base
with the same artifact and input. Access and resource-limit changes are not
supported by this evidence.” Status 2 belongs to this fictional tool's contract;
it is not a universal missing-file code.

### 3) **Interpret resource failure with its actual boundary**

A **resource limit** restricts resource use for a stated scope. It differs from
the installed capacity of the whole machine. On Linux, process resource limits
include a currently enforced **soft limit** and a **hard limit** that bounds it.
The [getrlimit reference](https://man7.org/linux/man-pages/man2/getrlimit.2.html)
defines each resource separately. Its `RLIMIT_NOFILE` restricts the descriptor
number range a process can open; exceeding it produces `EMFILE`. That is not a
statement that the disk has run out of bytes.

Consider a separate fictional report: a worker cannot open another file and
records `EMFILE`; free storage remains available. The appropriate questions concern
that worker's effective descriptor limit and live resource lifecycle. Does it
close completed files? Does the intended workload legitimately require more
simultaneous open resources? A larger limit may accommodate justified demand;
it may also postpone failure from a growing accumulation. The error alone does
not choose between those explanations or authorize changing a shared policy.

Likewise, “killed” is not a complete out-of-memory diagnosis. A signal result
identifies a termination mechanism under its reporting API. Establish the sender
or relevant system evidence before attributing a cause. Request the relevant
memory measure and scope; virtual address space, resident memory and traced
allocations are different quantities. Do not intentionally exhaust a shared
machine to reproduce a resource failure.

### 4) **Common confusion**

“Same environment” often means only “same OS name.” A useful comparison lists
the relevant variables rather than hiding them behind that label. Conversely,
a difference is a candidate explanation, not automatically the cause. Show how
it could produce the symptom and design a test that distinguishes it.

A run that succeeds as a different account is not proof that the intended account
needs unrestricted privileges. It changes the actor and possibly other context.
Preserve those distinctions in the report.

### 5) **Performance note**

A resource failure and slow execution can share pressure on a resource, but neither
label establishes the other. A descriptor-limit refusal can occur while storage
capacity remains plentiful. Record workload, usage, limit and timing separately.
This lesson performs no workload, throughput or resource-pressure benchmark.

### 6) **Mentor note**

Ask the learner to defend the next test using one row of the card. A good answer
names the predicted difference in behavior and the conditions to hold steady.
Then remove the attempted-open row: certainty should fall, and the next step
should become observation of the selected location rather than a claimed fix.
This tests reasoning under incomplete evidence instead of memorized troubleshooting.
