## 4.2. Standard streams pipes exit codes and signals

A command prints useful-looking text and then fails. Another writes a warning
but succeeds. A third ends because it receives a termination signal. To interpret
these outcomes, separate data streams, diagnostic streams and process completion
information instead of judging success from visible text alone.

Read the process, terminal and system-call lessons first. Concrete examples use
Linux and Python; no unrelated running process is signaled or stopped.

### 1) **Separate input output and diagnostic channels**

A **stream** carries a sequence of data. The three conventional **standard streams**
for command-line programs are **standard input** (`stdin`), **standard output**
(`stdout`) and **standard error** (`stderr`). Their usual roles are input data,
ordinary results and diagnostics. The names describe channels, not fixed physical
devices or automatic truth judgments.

In a terminal session, stdout and stderr may both appear in the same window.
They remain distinct streams and can be redirected to different destinations.
Stdin may come from a terminal, a file or another process. Python exposes its
stream objects in the [sys reference](https://docs.python.org/3.14/library/sys.html#sys.stdin).

Do not infer failure merely because stderr contains text: a tool may place progress
or warnings there. Conversely, a tool can write partial results to stdout before
failing. Interpret the documented completion status and the operation's required
outcome alongside the data, rather than relying on a channel's name.

### 2) **Trace data through a pipe without merging the other evidence**

A **pipe** connects a writer and a reader through a byte-stream channel. Linux's
[pipe overview](https://man7.org/linux/man-pages/man7/pipe.7.html)
describes its read and write ends. It is not a saved file containing a complete
message, and it does not inherently define application record boundaries.
The programs must agree whether their data uses lines, lengths or another format.

Tested environment for this small shell observation: **Bash 5.3.9 and CPython
3.14.4 on Linux x86_64**. Run this complete command at a Bash prompt:

```bash
printf 'item=42\n' | python3 -c 'import sys; print(sys.stdin.read().upper(), end="")'
```

Observed output:

```text
ITEM=42
```

`printf` produces a line on stdout. Bash's `|` connects that output to Python's
stdin. The fixed Python source reads the input, converts its letters to uppercase
and prints without adding another newline. This ordinary pipe connection does
not also merge stderr into the data stream. Other shells or explicit redirections
can select different arrangements.

When a pipeline fails, identify the status of the relevant stages and the shell's
configured policy for the overall result. A final command accepting input does
not, by itself, establish that the earlier producer completed successfully.
Avoid treating “a pipeline printed something” as a complete correctness check.

### 3) **Distinguish a program exit from signal termination**

An **exit status**, often called an **exit code**, records a process completion
result for its parent. Zero conventionally indicates success; nonzero meanings
are tool-specific. For example, a search utility may use one nonzero status for
no matches and another for a processing error. Read that tool's contract rather
than assuming all nonzero statuses mean identical failures.

A **signal** is an OS notification delivered to a process or thread under the
platform's rules. The Linux [signal overview](https://man7.org/linux/man-pages/man7/signal.7.html)
identifies `SIGTERM` as a termination signal with a default terminating action.
Handling can depend on the program and signal; sending a termination request
alone is not proof of completed cleanup or a successful application outcome.

Save this complete example as `process_outcomes.py` and run
`python3 process_outcomes.py`. Tested environment: **CPython 3.14.4 on Linux x86_64**;
all modules are standard library. The second fresh child deliberately sends
SIGTERM only to itself. The parent remains running to inspect the result.

```python
import subprocess
import sys
import signal

source = 'import sys; print("item=42"); print("notice", file=sys.stderr); sys.exit(3)'
result = subprocess.run(
    [sys.executable, "-c", source], capture_output=True, text=True)
print("stdout:", repr(result.stdout))
print("stderr:", repr(result.stderr))
print("Exit status:", result.returncode)

signal_source = 'import os, signal; os.kill(os.getpid(), signal.SIGTERM)'
terminated = subprocess.run(
    [sys.executable, "-c", signal_source], capture_output=True, text=True)
print("Terminated by SIGTERM:", terminated.returncode == -signal.SIGTERM)
```

Observed output:

```text
stdout: 'item=42\n'
stderr: 'notice\n'
Exit status: 3
Terminated by SIGTERM: True
```

The first child produces both streams and deliberately exits with status 3.
`repr` displays their newline characters visibly. `capture_output=True` keeps
the streams separate for inspection; `text=True` returns text values.
The [subprocess result contract](https://docs.python.org/3.14/library/subprocess.html#subprocess.CompletedProcess)
explains that Python represents POSIX signal termination as a negative signal
number. We compare against the symbolic signal value rather than assuming a
universal numeric SIGTERM constant.

That negative representation belongs to this API. A shell can present signal
termination differently, so do not paste Python's return-code interpretation
into every tool's exit-code table. The child's stdout text also does not make
its deliberate status 3 a success. This complete observation distinguishes
successful execution of our inspecting parent from the outcomes it inspected.

Practice: “There was no stderr, therefore the export succeeded.” The explained
answer asks for its completion status and intended output evidence. Empty stderr
is only an observation about a channel, not proof that all work completed.

### 4) **Common confusion**

An application exception, an ordinary exit status and an OS signal are different
mechanisms. A runtime may translate one event into another result, but that
translation is part of its documented behavior. Identify the reporting layer
before interpreting the number or message.

Standard output is not necessarily a screen, and standard error is not itself
a failure flag. Keep data separate from diagnostics when another program must
parse it; an unexpected progress line in the data channel can invalidate otherwise
useful output.

### 5) **Performance note**

Pipes have finite capacity, and writers/readers can wait for one another. Buffering
can also delay when output becomes visible. This does not mean the application
has stopped making progress. Capturing all output into memory, as this bounded
example does, is unsuitable for arbitrarily large output. No pipe throughput,
buffering latency or process-startup benchmark was performed here.

### 6) **Mentor note**

Ask a learner to label input, result data, diagnostics and completion status in
the example. Then ask which process succeeded and which deliberately failed.
A strong answer distinguishes the parent inspection from each child outcome and
states the API-specific signal representation without turning it into a universal
exit-code convention.
