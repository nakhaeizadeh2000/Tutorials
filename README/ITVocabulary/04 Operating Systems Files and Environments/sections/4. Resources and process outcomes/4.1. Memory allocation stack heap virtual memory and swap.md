## 4.1. Memory allocation stack heap virtual memory and swap

A dashboard shows several gigabytes of virtual memory, much less resident memory,
and a separate runtime heap value. These figures can describe different things
without contradicting one another. Before diagnosing a leak or buying RAM, identify
which quantity each tool measures and which resource is actually limited.

Read the RAM, process and OS lessons first. This page introduces measurement and
resource vocabulary; language-specific object lifetime and garbage-collector
mechanics remain with their detailed owners.

### 1) **Separate allocation call state and object lifetime**

**Allocation** makes storage available for data or execution state under an
allocator's rules. It does not necessarily mean a new physical RAM request for
every source-level object; an allocator may reuse storage it already manages.
**Deallocation** makes storage available for reuse under that management scheme.
It need not immediately reduce a process's operating-system memory figure.

A **call stack** models active function calls and the state needed to resume
callers. A **stack frame** is the state associated with an invocation in that
model. A **heap** commonly refers to storage managed for dynamically allocated
data whose lifetime need not match one active function call. These are useful
roles, not a universal diagram locating every language value in physical memory.

For a concrete caution, the [Go FAQ's stack/heap discussion](https://go.dev/doc/faq#stack_or_heap)
explains that storage placement is chosen by the implementation. This supports
rejecting the slogan “local variables are always on the stack.” It does not make
Go's allocation rules the rules for Python or JavaScript.

A function can finish while data it created remains needed elsewhere. Automatic
memory management can reclaim storage when its own lifetime rules permit; the
language/runtime determines those rules. The [JavaScript memory-model owner](<../../../../JavaScript/18 Memory Management and GC/sections/1. Memory model/1.1. Heap stack execution contexts and references how values live.md>)
connects references and object lifetime. Use that owner for JavaScript reasoning
rather than copying a generic stack/heap picture into a language guarantee.

### 2) **Distinguish virtual addresses resident RAM and swap**

**Virtual memory** gives a program an address-space abstraction instead of direct
ownership of one continuous physical RAM region. An **address space** is the range
of addresses the program can use under its execution model. On the common Linux
systems discussed here, mappings connect virtual pages with physical memory or
other backing. A **page** is a unit used for that memory management; its size
depends on the platform.

The Linux kernel's [virtual-memory primer](https://docs.kernel.org/admin-guide/mm/concepts.html#virtual-memory-primer)
explains address translation, demand paging, protection and sharing. Virtual
memory is therefore broader than “RAM plus disk.” A large reserved virtual region
does not by itself establish that an equally large amount of RAM is resident.

**Resident memory** is memory currently present in physical RAM for the measured
mapping/process scope. **RSS**, or **resident set size**, is a common process
measurement. It differs from virtual size and from the subset a language allocator
reports. Some resident mappings can also be shared, so casually adding process
RSS values can misrepresent unique physical use.

Linux's [process status reference](https://man7.org/linux/man-pages/man5/proc_pid_status.5.html)
distinguishes `VmSize`, `VmRSS` and `VmSwap` and explicitly cautions that some of
these accounting values are approximate. A report must name its source and
meaning rather than presenting every field as an exact interchangeable byte count.

**Swap** is backing space the OS can use for some memory pages, commonly through
a swap file or device; Linux documents those forms in [swapon](https://man7.org/linux/man-pages/man2/swapon.2.html).
Moving pages between resident memory and backing involves additional work and
can affect latency. Swap does not mean the program has unlimited usable memory,
and lack of active swap does not mean virtual memory is absent. We do not change
swap configuration or force memory pressure in this lesson.

### 3) **Observe a scoped allocation counter without confusing it with RSS**

Tested environment: **CPython 3.14.4 on Linux x86_64**. Save `allocation_scope.py`
and run `python3 allocation_scope.py`. It uses the standard-library `tracemalloc`
module and a bounded one-million-byte payload.

```python
import tracemalloc

tracemalloc.start()
before, _ = tracemalloc.get_traced_memory()
payload = bytearray(1_000_000)
with_payload, peak = tracemalloc.get_traced_memory()
del payload
after, _ = tracemalloc.get_traced_memory()
print("Tracked growth at least payload bytes:", with_payload - before >= 1_000_000)
print("Peak at least current at sample:", peak >= with_payload)
print("Tracked bytes fall after deletion:", after < with_payload)
tracemalloc.stop()
```

Observed output:

```text
Tracked growth at least payload bytes: True
Peak at least current at sample: True
Tracked bytes fall after deletion: True
```

`bytearray` creates a mutable byte buffer. `tracemalloc` reports current and peak
sizes of the memory blocks it traces, documented in its
[allocation reference](https://docs.python.org/3.14/library/tracemalloc.html).
We compare values instead of promising identical bookkeeping byte counts across
runtime builds. `_` marks a returned value that the example does not need.

In this CPython run, traced allocations increased while the buffer existed and
fell after the last `payload` reference was removed. That is an observation of
this counter and lifetime arrangement, not a universal promise about deletion
in every implementation. We did not measure RSS, virtual reservations, swap
activity or a return of physical memory to the OS. Tracing also starts at the
explicit start call, so it does not inventory all prior runtime allocations.

Practice: a fictional runtime heap counter falls, but a process RSS display
remains stable. Does that prove the deallocation failed? No. The counters have
different scopes, and an allocator can retain storage for reuse. Ask which data
remains live, which allocator and process figures are being compared, and what
repeated observations show before declaring a leak.

### 4) **Common confusion**

Stack overflow, a runtime heap limit and an OS memory limit are different failure
contexts. A machine can have free RAM while a particular process or runtime has
reached another limit. Identify the actual failure report and configured scope;
do not repair every memory-related problem by increasing an unrelated limit.

“Freeing an object” also does not mean wiping every copy of its bytes or ensuring
that no other reference remains. Object lifetime, allocator reuse, OS accounting
and confidential-data erasure are different questions.

### 5) **Performance note**

Allocation, reuse, reclamation and page movement can contribute different costs.
A high allocation rate and a large retained working set are not the same problem.
This experiment observes a scoped size change; it measures neither allocation
speed nor collection pauses or paging latency. Choose the actual workload and
counter before recommending pooling, more swap or a different runtime limit.

### 6) **Mentor note**

Give a learner three labels—runtime traced bytes, resident memory and virtual
size—and ask which claim each can support. Then ask whether the observed buffer
deletion proves RSS fell. A sound answer names the unmeasured boundary and uses
a language-specific lifetime explanation only where it applies.
