## 3.1. Users groups permissions privileges and ownership

A report file is named `public.txt`, but a background service cannot read it.
The name does not grant access. An operating system evaluates the requesting
process's identity, the requested operation and applicable access rules. Reading
those rules requires separating a person, an account, a running process and a
file's recorded owner.

Read the process and filesystem lessons first. The concrete model here is Linux
with ordinary Unix permission bits; it is not a universal access-control model
for every operating system or application.

### 1) **Identify the actor and the resource before interpreting access**

A **user account** is an identity recognized by a system. It may represent a person
or a service rather than a human currently logged in. A **group** collects
identities for access-management purposes. On Linux, user and group identities
are represented by numeric IDs, commonly called **UID** and **GID**. Names are
human-readable labels associated with those identities.

Processes carry credentials used for access decisions, so a service can have
different access from the person who launched or configured it. The Linux
[credentials manual](https://man7.org/linux/man-pages/man7/credentials.7.html)
describes real, effective, filesystem and supplementary identities. For this
introductory model, the key question is which identity the actual operation uses;
we do not assume that a login name alone answers every access check.

**Ownership** records which user and group own a file under the filesystem's
model. It is metadata, not an assertion that the named person wrote every byte
or that all other accounts are excluded. **Permission** describes allowed
operations under a rule. **Privilege** describes authority to perform particular
restricted actions or override some ordinary restrictions. Administrator or root
access can affect decisions, but it does not make every operation universally
possible in every environment.

### 2) **Read Unix permission bits without treating them as the whole policy**

For an ordinary Linux file, the basic permission classes are owner, group and
other. In each class, **read**, **write** and **execute** are commonly written
`r`, `w` and `x`. A missing permission is displayed as `-`. The
[inode reference](https://man7.org/linux/man-pages/man7/inode.7.html)
documents the file ownership and mode fields behind these displays.

| Ordinary-file mode | Owner | Group | Other |
|---|---|---|---|
| `rw-r-----`, often written `640` | read and write | read | none |
| `rw-------`, often written `600` | read and write | none | none |

The numeric representation uses octal, base eight. Within each class, read
contributes 4, write 2 and execute 1; adding them gives the digit. Thus 6 means
4 + 2. A leading Python `0o` declares octal notation; it is not another permission.

Directory permissions have related but different meanings. Read concerns listing
entries; execute/search concerns traversing the directory to reach a named entry;
write concerns modifying directory entries, subject to other checks. A readable
file can still be unreachable without search permission on a directory in its
path. Linux's [path-resolution reference](https://man7.org/linux/man-pages/man7/path_resolution.7.html)
explains that traversal requirement. Removing a name also concerns its containing
directory, so a file's write bit alone does not decide every deletion question.

Tested environment: **CPython 3.14.4 on Linux x86_64**. Save `permission_bits.py`
and run `python3 permission_bits.py`. It uses the standard library and changes
only a newly created file inside an automatically cleaned temporary directory.

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import stat

with TemporaryDirectory() as folder:
    path = Path(folder) / "report.txt"
    path.write_text("example", encoding="utf-8")
    path.chmod(0o640)
    mode = stat.S_IMODE(path.stat().st_mode)
    print("Mode:", oct(mode))
    print("Owner read bit:", bool(mode & stat.S_IRUSR))
    print("Group write bit:", bool(mode & stat.S_IWGRP))
    print("Other read bit:", bool(mode & stat.S_IROTH))
```

Observed output:

```text
Mode: 0o640
Owner read bit: True
Group write bit: False
Other read bit: False
```

`chmod` sets the new file's mode. `stat()` reads metadata; `S_IMODE` extracts its
mode bits, and `&` checks whether a named bit is set. Python's
[stat reference](https://docs.python.org/3.14/library/stat.html)
defines those operations and constants. This is an actual metadata observation,
not an attempted access by separate user accounts. It does not prove which
accounts can open the file under every additional policy.

### 3) **Diagnose a denied operation without widening access blindly**

Use this constructed basic-permission scenario. The file has owner Alice, group
Reports and mode `640`. Bob's requesting process is not the owner but belongs to
Reports; Cara's process is neither. Assume no extra ACLs, special privileges or
other restrictions, and allow all necessary directory traversal.

Under that model Alice may read and write, Bob may read, and Cara receives no
access through these bits. Bob cannot write by borrowing Alice's owner bits.
Changing the filename to `everyone.txt` changes none of those permissions.

Now remove the assumption that traversal is allowed. Bob's file read bit is no
longer sufficient evidence that opening the full path succeeds. Similarly, an
**ACL**, or **access control list**, can express more specific user/group access
rules than the basic display alone reveals. The Linux
[ACL manual](https://man7.org/linux/man-pages/man5/acl.5.html)
explains that extended model. Other policies and resource conditions can also
matter; the numeric mode is a starting point, not a complete diagnosis.

A poor repair is “grant everyone all permissions” or “run everything as an
administrator” without identifying the denied operation. Such changes widen the
authority available to unrelated code and can conceal the actual configuration
mistake. A focused next step is to identify the service's process identity, exact
path, attempted operation, relevant directory access and applicable policy. Then
choose the smallest justified change and verify the intended operation as that
identity. This page does not perform that administrative change.

### 4) **Common confusion**

File owner, process owner and application-level “document owner” need not be the
same identity or even the same kind of concept. A web application can maintain
its own access rules in addition to OS file access. Determine which layer denied
the operation before changing filesystem permissions.

“Read-only” also needs an object and scope. Lacking permission to modify file
contents differs from lacking permission to remove its directory entry. The
exact operation and applicable rules matter more than a loose adjective.

### 5) **Performance note**

Permission rules primarily govern access, not data throughput. Giving broader
permissions is not an established performance optimization. Access checks and
policy mechanisms can contribute work, but this example measures no overhead.
Repeated denied operations can waste work or produce errors; first correct the
access contract rather than treating a permission label as a speed setting.

### 6) **Mentor note**

Ask a learner to solve the Alice/Bob/Cara scenario and then remove one assumption:
Bob's group membership, directory traversal or the absence of an ACL. A strong
answer changes only the conclusion that the altered evidence affects and asks
for the actual process identity before prescribing an administrative command.
