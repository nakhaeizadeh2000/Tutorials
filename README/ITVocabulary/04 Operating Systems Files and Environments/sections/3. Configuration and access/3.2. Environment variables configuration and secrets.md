## 3.2. Environment variables configuration and secrets

“The environment is production” might name a deployed system. “The environment
contains `REPORT_MODE`” refers to a process's named values. These meanings connect,
but they are not identical. A deployment label does not prove which values a
particular running process actually received.

Read the process and access lessons first. The example uses only synthetic,
non-secret settings and a short-lived child process. It never prints your real
process environment or reads a credential store.

### 1) **Distinguish deployment context from process configuration**

**Configuration** supplies settings that affect how software operates. It can come
from files, command arguments, process environment variables or a service. Which
source wins when several specify a value is the application's **precedence** rule;
there is no universal order shared by all tools.

An **environment variable** is a named value supplied through a process environment.
In the Python interface used here, names and values are strings. Starting a child
process ordinarily passes an environment based on its parent's, but a launcher
can supply an explicit mapping instead. Python documents that choice in its
[subprocess reference](https://docs.python.org/3.14/library/subprocess.html).
A value changed in one process is not a global edit to every running process.

A **deployment environment**, such as development, staging or production, names
a context in which the application is operated. Its configuration can differ
from another context, but the friendly name alone does not establish its database,
permissions or process settings. The original [Twelve-Factor configuration chapter](https://12factor.net/config)
by Adam Wiggins motivates separating settings that vary between deployments from
application code. That is a design approach, not proof that every setting belongs
in an environment variable or that this storage mechanism protects secrets.

A file conventionally named `.env` can be an input to a loader that supplies
settings. The name alone does not cause every OS or program to load it. Identify
the tool, file selection and loading time before assuming that editing such a
file changed an already-running service.

### 2) **Parse named values according to an explicit contract**

Tested environment: **CPython 3.14.4 on Linux x86_64**. Save `process_config.py`
and run `python3 process_config.py`. It uses standard-library modules only. The
child receives the explicit synthetic mapping rather than the parent's normal
inherited environment, which is sufficient for this tested executable on Linux.
This minimal mapping is not a portable recipe for launching arbitrary programs.

```python
import subprocess
import sys

configuration = {"LESSON_MODE": "demo", "LESSON_ENABLED": "false"}
child_source = """import os
raw = os.environ['LESSON_ENABLED']
if raw not in {'true', 'false'}:
    raise ValueError('LESSON_ENABLED must be true or false')
print('Child mode:', os.environ['LESSON_MODE'])
print('Nonempty text is truthy:', bool(raw))
print('Parsed enabled flag:', raw == 'true')
os.environ['LESSON_MODE'] = 'changed-in-child'
"""
output = subprocess.check_output(
    [sys.executable, "-c", child_source], env=configuration, text=True)
print(output, end="")
print("Parent configuration:", configuration["LESSON_MODE"])
```

Observed output:

```text
Child mode: demo
Nonempty text is truthy: True
Parsed enabled flag: False
Parent configuration: demo
```

The dictionary supplies names and text values for the child. Inside that child,
`os.environ` exposes its process environment, as the
[Python OS reference](https://docs.python.org/3.14/library/os.html#os.environ)
describes. The fixed child source accepts exactly `true` or `false`; comparison
with `true` then produces a Boolean. The nonempty string `false` is truthy in
Python, so `bool(raw)` would be the wrong parser for this contract.

The child's change to its own `LESSON_MODE` does not mutate the parent's supplied
configuration dictionary. The final line observes that dictionary, not a list of
the parent's real environment variables. Each process's scope matters.

For a controlled invalid-input case, change the synthetic `LESSON_ENABLED` value
to `perhaps` and rerun. In the tested environment the child raises the stated
`ValueError`; `check_output` then raises `CalledProcessError` in the parent and
the command exits unsuccessfully. Restore `false` for the passing case. Do not
silently turn an unrecognized setting into a convenient default unless the
configuration contract deliberately specifies that behavior.

### 3) **Distinguish secret delivery from secret protection**

A **secret** is a value whose confidentiality matters, such as a password or a
private authentication credential. Some configuration is secret; a display theme
or a public port setting usually is not. The word “configuration” therefore does
not establish whether a value can be shared safely.

Environment variables are a delivery mechanism, not encryption or an access-control
policy. Diagnostic output, inherited settings and other inspection mechanisms can
expose values depending on the environment and permissions. OWASP's
[secrets-management guidance](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)
discusses environment/log exposure and managed delivery alternatives. Read those
as mechanisms and conditions, not a claim that every process can read every other
process's environment.

A **secret manager** supplies controlled storage and access for secrets, with
capabilities depending on its actual product and setup. Storing a reference to
a secret also differs from storing the secret value itself. Full credential,
rotation and deployment design belong to later security and infrastructure lessons.

Consider a constructed support request: “Paste the complete environment so we can
find why the mode is wrong.” A better request asks for the non-secret mode name,
its selected source, the process/start time and whether required secret settings
are present, without their values. If an output must be shared, **redaction**
removes sensitive content from that output. A label such as `[REDACTED]` is useful
only if the actual value has really been removed from the shared artifact.

### 4) **Common confusion**

An environment value that looks like a number or Boolean is still text until the
application interprets it. Missing, empty and invalid values are also different
cases; the application must define its response. The example deliberately accepts
a narrow vocabulary rather than relying on truthiness.

Changing a launcher, shell or configuration file also does not prove that an
existing process reread its settings. Ask whether the application reads once at
startup, reloads through a defined mechanism or queries another source later.
Verify the actual process and effective setting while withholding secret values.

### 5) **Performance note**

Reading a local named value and fetching a remote secret involve different work.
Whether configuration is parsed once or repeatedly also changes its cost and
update behavior. This lesson measures neither access latency nor reload overhead.
Do not introduce a cache or repeated remote fetch from the word “configuration”
alone; establish the application's freshness and failure requirements first.

### 6) **Mentor note**

Ask a learner to explain why `false` produces two different Boolean results in
the output, then identify exactly what the parent line observes. Finally, have
them rewrite the support request with the smallest non-secret evidence needed.
A sound answer preserves configuration source and process scope without exposing
an entire environment or claiming that a secret-manager label guarantees safety.
