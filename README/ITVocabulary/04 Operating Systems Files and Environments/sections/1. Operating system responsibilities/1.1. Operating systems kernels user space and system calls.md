## 1.1. Operating systems kernels user space and system calls

A program wants to display text, read a file or start another program. Those
operations depend on services beyond ordinary arithmetic in the language. The
operating system manages shared resources and supplies interfaces through which
programs request work. Understanding that boundary helps you distinguish a
language error from an operating-system operation that failed.

Read the preceding hardware and execution domains first. The optional trace below
is specifically for Linux; it is not a claim that every operating system uses
identical interfaces or internal organization.

### 1) **Locate the kernel within the operating-system picture**

An **operating system**, often shortened to **OS**, manages resources and provides
services for programs: execution, memory, files and device access are common
responsibilities. The **kernel** is its core privileged component. A complete
operating-system environment also contains tools and supporting software outside
the kernel. A shell is therefore not the whole OS, and the kernel is not the
same thing as a graphical desktop.

OpenStax's [fundamental OS concepts](https://openstax.org/books/introduction-computer-science/pages/6-2-fundamental-os-concepts)
uses resource and application-service relationships to introduce these
responsibilities. Different OS designs organize the components differently;
this lesson uses Linux for the concrete boundary rather than presenting one
diagram as every system's architecture.

On Linux, **user space** is the ordinary execution environment for applications
and many supporting programs, outside kernel execution. **Kernel space** refers
to the kernel's privileged execution and memory context. These terms describe
execution/protection boundaries, not whether a person is currently using a
keyboard. A background program can run in user space, and an administrator's
application does not become kernel code merely because its user has more access.

### 2) **Distinguish an application API from a system-call boundary**

A **system call** requests a service through an entry point into the kernel.
Applications generally reach that boundary through runtime or library interfaces.
The Linux [system-call introduction](https://man7.org/linux/man-pages/man2/intro.2.html)
explains that C library wrappers commonly perform the steps needed to enter the
kernel and translate results for their callers.

A conceptual path is application → runtime/library API → system-call boundary →
kernel service → result. It is a responsibility model, not a promise that every
source-level function call maps to exactly one system call. A library can perform
work locally, combine requests, or make several requests for one higher-level
operation. The result can also be failure, for example when a requested file is
unavailable or access is denied.

This is why “the function exists” and “the operation succeeded” remain separate.
A file-reading API can exist in the runtime while the intended file cannot be
opened in the current environment. Record the actual operation and result before
concluding that the language implementation is defective.

### 3) **Observe one Linux system call in a bounded example**

Tested environment: **CPython 3.14.4 and strace 6.19 on Linux x86_64**. `strace`
is a Linux diagnostic tool that records selected system-call interactions.
If it is unavailable or tracing is restricted in your environment, you can read
the observed trace below; do not report a local trace as performed.

Save this complete file as `os_boundary.py` in a new folder:

```python
import os

os.write(1, b"Boundary reached\n")
```

The number `1` identifies standard output, the running program's usual output
destination. Here it is a small example of a **file descriptor**, a number used
to refer to an open I/O resource. **I/O** means input/output. The `b` prefix creates
bytes and `\n` ends the line. Python documents `os.write` in its
[OS interface reference](https://docs.python.org/3.14/library/os.html#os.write).
Use of this low-level interface makes the observed request easy to identify;
it is not a recommendation to replace ordinary application text output with it.

From that folder, run this command at your shell prompt:

```bash
strace -e trace=write -o calls.txt python3 os_boundary.py
```

`-e trace=write` selects the `write` system call for display; `-o calls.txt` saves
the trace separately from the program's standard output. These options are
documented in the [strace manual](https://man7.org/linux/man-pages/man1/strace.1.html).
The program displayed:

```text
Boundary reached
```

Open `calls.txt` in your editor. The observed trace contained these lines;
spacing may differ by tool version:

```text
write(1, "Boundary reached\n", 17)      = 17
+++ exited with 0 +++
```

The request specifies descriptor 1 and 17 bytes. The returned 17 records that
this write accepted all 17 bytes in this run. The final line records normal process
exit with status zero. This trace is direct evidence of the selected kernel
interaction, rather than an inference from the Python function's name.

The filter hides other kinds of system calls, including startup work. Do not
conclude that Python required only one system call in total. Nor does this output
prove the text was saved durably to a disk: standard output can point to different
resources. General stream and descriptor behavior receives a later lesson.

### 4) **Common confusion**

User space does not mean “unimportant,” “interactive” or “owned by an ordinary
human user.” Many essential services run there. Kernel privileges and application
access rights are related boundaries, but they are not identical concepts.

An API call also need not be a raw system call. Use the documented interface
and observed trace to establish a particular relationship; do not label every
imported function an operating-system entry point.

### 5) **Performance note**

A high-level operation may include library work, kernel work and waiting for a
resource. Its duration cannot be attributed to the kernel simply because a system
call appears in its path. Tracing adds diagnostic work and can change timing;
this run records behavior, not normal execution speed. No per-call cost or
cross-OS performance comparison is claimed.

### 6) **Mentor note**

Ask a learner to identify which part of the conceptual path the Python API and
the trace line describe. Then ask whether a missing file would mean the API is
missing. A sound answer separates capability, request, access conditions and
observed outcome, while keeping the Linux-specific evidence scoped to Linux.
