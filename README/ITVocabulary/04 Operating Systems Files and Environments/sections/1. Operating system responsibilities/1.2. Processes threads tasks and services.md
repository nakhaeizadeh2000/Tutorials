## 1.2. Processes threads tasks and services

An application is “running twice,” a process has “eight threads,” and a service
has “restarted.” These descriptions concern different boundaries. To investigate
a failure or resource limit, identify the running instance, its execution units
and the mechanism managing its lifecycle.

Read the preceding OS-boundary lesson and the earlier program/runtime vocabulary.
The example creates one short-lived thread and one child process; it does not
install, restart or stop an operating-system service.

### 1) **Separate a program from its running instances and threads**

A **process** is a running instance of a program with an execution context and
resources managed by the operating system. The same program can have multiple
process instances, each with its own identity and state. A source file or executable
on disk is not itself that running instance.

A **thread** is a thread of execution within a process. Multiple threads in one
process share important process resources while retaining their own execution
state. The Linux/POSIX [pthreads manual](https://man7.org/linux/man-pages/man7/pthreads.7.html)
describes shared process identity and memory alongside per-thread state. Separate
processes normally have separate address spaces, though programs can arrange
communication or explicit shared memory. Isolation is not a claim that processes
can never affect one another.

A **PID** is a process identifier. A thread has an identifier too, whose meaning
depends on the interface reporting it. Neither is a CPU-core number. An OS can
schedule different threads on available execution resources over time; counting
threads does not establish how many are simultaneously executing instructions.
Do not use an old numeric identifier as a permanent application identity, because
identifiers can be reused after an instance ends.

### 2) **Observe the process boundary independently of thread identity**

Tested environment: **CPython 3.14.4 on Linux x86_64**. Save `execution_units.py`
and run `python3 execution_units.py`. All imports are standard library; there
are no external commands beyond the running Python executable itself.

```python
import os
import subprocess
import sys
import threading

main_pid = os.getpid()
main_thread = threading.get_ident()

def worker():
    print("Thread shares process:", os.getpid() == main_pid)
    print("Different thread identity:", threading.get_ident() != main_thread)

thread = threading.Thread(target=worker)
thread.start()
thread.join()
child_pid = int(subprocess.check_output(
    [sys.executable, "-c", "import os; print(os.getpid())"], text=True))
print("Child has different process:", child_pid != main_pid)
```

Observed output:

```text
Thread shares process: True
Different thread identity: True
Child has different process: True
```

The main program records its process and Python thread identities. `Thread` names
the operation to run; `start()` begins it in another thread, and `join()` waits
for that thread to finish. The worker reports the same process identity and a
different thread identity. The [threading reference](https://docs.python.org/3.14/library/threading.html)
documents these operations; Python's thread identifier need not be the same
numeric value as an operating-system-native thread identifier.

Next, `sys.executable` selects the current Python executable for a new child
process. Its `-c` option executes the fixed short source string. The
[subprocess check_output operation](https://docs.python.org/3.14/library/subprocess.html#subprocess.check_output)
returns the child's output, which `int` converts from text into a number. The
child's PID differs from the still-running parent's PID. We print comparisons
so the expected result does not depend on machine-specific identifier values.

This establishes distinct identities in the declared environment. It does not
benchmark process creation, show simultaneous CPU execution or test communication
between arbitrary processes.

### 3) **Read task and service labels in their management context**

A **task** can mean a unit of work in a scheduler, a language's asynchronous
operation or an item on a team's board. Do not assume it always means a separate
process or thread. Ask which subsystem defines the task and how it executes.
Later concurrency lessons develop those execution relationships.

An operating-system **service** is a managed software activity intended to supply
a capability. A **service manager** controls lifecycle operations such as starting,
stopping and tracking it. The service may involve a main process and additional
workers. Some services perform a short operation and finish rather than remaining
running indefinitely.

For one concrete convention, systemd describes `.service` units and their managed
process behavior in [systemd.service](https://man7.org/linux/man-pages/man5/systemd.service.5.html).
Restart behavior depends on configuration and conditions; the word “service” does
not promise that every exit automatically restarts. This is terminology reading,
not instructions to change your machine's service configuration.

A **daemon** commonly means an unattended background program in Unix-like usage.
The term does not establish that the process runs with administrator privileges.
Also, Python's “daemon thread” is a separate, specifically documented thread
shutdown property; it is not an operating-system service manager.

Practice: a fictional report says the “export service” restarted and its PID
changed, but its service name stayed the same. Is that contradictory? No. A
stable managed-service identity can refer to a new process instance after a
restart. Ask which manager, process instance and observation time the report
concerns before deciding whether the application is currently healthy.

### 4) **Common confusion**

One application need not equal one process, and one process need not equal one
thread. A browser or server can use several processes, and a process can use
several threads. State the actual arrangement rather than deriving it from the
application's name.

“Running” also does not necessarily mean using a CPU at this instant. A live
process or thread may be waiting for work or another event. A manager reporting
a service as active is different evidence from a successful user operation.

### 5) **Performance note**

Threads and processes consume resources and may spend time waiting or coordinating.
Neither more threads nor more processes guarantees greater throughput. Their
costs and benefits depend on the workload, implementation and available resources.
The example records identity relationships and waits for completion; it measures
no creation overhead, memory use, parallel speedup or service availability.

### 6) **Mentor note**

Ask a learner to draw two processes, with two threads inside one of them. Mark
which identifiers and resources belong to each boundary. Then add a managed
service name and replace its process after a fictional restart. A sound answer
preserves the management identity while changing the running-instance identity.
