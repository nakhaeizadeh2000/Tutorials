## 1.1. Terms jargon abbreviations and acronyms

Imagine receiving this message on your first day:

> The API is ready. Ask QA to run the smoke test before the rollout.

You recognize the letters, but you cannot yet tell what work to do. Looking up
each expansion helps only a little. You also need to know what the words refer
to in this situation. This lesson develops that habit before introducing the
specialist topics themselves. No software installation or programming is needed.

### 1) **Distinguish a technical meaning from its written form**

A **term** is a word or phrase used for a particular concept. In ordinary speech,
"memory" can mean a person's recollection. In a computer discussion, it can refer
to a resource that holds information used by running programs. The word is
familiar; the relevant meaning still needs to be learned.

**Jargon** is language shared by a particular group. Some jargon names a precise
technical concept. Some is an informal shortcut, such as "ship it" for making a
change available. It can help experienced teammates communicate quickly, but
becomes a barrier when the audience does not share the meaning. Google's
[jargon guidance](https://developers.google.com/style/jargon) recommends defining
necessary jargon or replacing it with more specific language.

An **abbreviation** is a shortened written or spoken form. An **acronym** is
formed from initial letters and pronounced as a word; an **initialism** is spoken
letter by letter. People often use "acronym" as an umbrella label for both.
That naming variation rarely matters as much as understanding the concept.
See the distinction in Google's
[abbreviation guide](https://developers.google.com/style/abbreviations).

| Expression | What kind of expression is it? | What is still missing? |
|---|---|---|
| application programming interface, or API | A technical phrase and its abbreviation; API is usually spoken letter by letter. | What operations can another program request, and under what rules? |
| random-access memory, or RAM | A technical phrase and an acronym commonly spoken as a word. | Which memory resource is meant and what the program needs it for. |
| smoke test | Jargon for a small check of important basic behavior. | Which checks this team actually runs. |
| ship it | Informal workplace shorthand. | Whether the speaker means approval, deployment or availability to users. |

These categories overlap. API is both a technical term and an abbreviation.
Calling something jargon does not establish whether its meaning is precise,
whether it is useful, or whether this audience already understands it.

### 2) **Turn an expansion into a usable explanation**

An **expansion** gives the words represented by an abbreviation. An explanation
connects those words to a task or observable example. For this introductory
scenario, an API is a defined way for software to request operations from other
software. A weather application might request the forecast from a weather
service instead of collecting every measurement itself. The interface specifies
how to make that request and how to interpret the result.

That example gives you something to reason about. Expanding API alone does not
tell you which requests the team's software supports, whether anyone tested
them, or whether customers can use them yet. Those are separate questions.

In the opening message, QA means **quality assurance**. The speaker may be using
it informally for colleagues who perform testing. A **rollout** makes a change
available to its intended users, possibly in stages. For now, these are enough
to ask a useful question:

> Which basic checks should the testers run, and which result lets us proceed
> with making this change available?

You have not mastered APIs, testing or delivery. You have identified the task
and the missing information without pretending that the initials answered it.

### 3) **Choose language that fits the reader and the task**

When a teammate already knows a term, repeatedly expanding it can interrupt the
discussion. When a newcomer does not, an unexplained abbreviation can conceal
the entire instruction. Introduce the relevant meaning once, then use a
consistent short form. Expand unfamiliar initials, but also explain unfamiliar
words in the expansion.

Consider the constructed instruction "Send the payload to the API." A payload
is the data being sent for the operation in this example. For a newcomer, a
clearer instruction is "Send the address data using the application's documented
interface." For an experienced API reader, specifying the actual operation and
data fields would be more useful than replacing every technical word.

Practice: explain "The API accepts a payload" without using either API or
payload. One possible answer is "Other software can submit data using the
documented request format." This answer identifies the actors and action.
It leaves unanswered which format and operation are supported, so a good follow-up
asks for their documentation rather than inventing them.

### 4) **Common confusion**

Not knowing an abbreviation does not prove that someone lacks the underlying
skill. A person may already understand a concept under another name or may be
new to the team's shorthand. Ask for the meaning and then discuss the actual
task. Conversely, reciting the expansion does not demonstrate practical
understanding: ask for a concrete example and a consequence.

Another trap is treating a local nickname as an industry definition. A team may
call one particular group "QA"; that does not make quality assurance universally
synonymous with that group's testing activities. Keep the local use visible.

### 5) **Performance note**

Choosing an acronym instead of its full phrase has no direct effect on the speed
of a running program. The relevant cost here is communication: an ambiguous
instruction can send someone toward the wrong check or operation. Clear wording
helps people identify what to inspect; it does not itself establish that the
software is fast or correct. No runtime benchmark is relevant to this distinction.

### 6) **Mentor note**

Ask a learner to explain the opening message to a person joining the team today.
A sound answer identifies software requesting an operation, people checking
behavior and a change becoming available. It also asks what "ready" means.
If the learner only expands initials, ask them to describe one concrete action.
If they ask for the test criteria, treat that as useful reasoning, not ignorance.
