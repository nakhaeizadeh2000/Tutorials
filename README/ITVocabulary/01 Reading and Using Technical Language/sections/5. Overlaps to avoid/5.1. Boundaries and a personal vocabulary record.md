## 5.1. Boundaries and a personal vocabulary record

You can now question a vague statement and choose a useful document. The next
challenge is remembering what you learned without collecting a dictionary of
unconnected expansions. A small vocabulary record helps if it preserves context,
evidence and the next question, rather than just accumulating words.

This leaf closes the domain. It explains where its instruction stops and how
to route a new question. The record below is a constructed writing exercise;
you can keep your own in ordinary notes without installing a special tool.

### 1) **Keep interpretation here and detailed mechanisms with their owners**

This domain owns reading habits: distinguishing a term from its expansion,
resolving context, selecting documents, interpreting requirement/status wording,
asking a focused question and preserving evidence in a rewrite. It introduces
specialist terms only far enough to make those tasks understandable.

The boundary depends on the question you are answering:

| Question | Appropriate next step |
|---|---|
| What does client mean in this message? | Use this domain's context and clarification methods. |
| Which operations does this particular interface accept? | Read the matching interface reference; vocabulary alone cannot supply the contract. |
| Why is a JavaScript host API unavailable in another runtime? | Use the existing [engines runtimes and hosts lesson](<../../../../JavaScript/01 Fundamentals and Mental Model/sections/1. What JavaScript is/1.2. Engines runtimes and hosts V8 SpiderMonkey JavaScriptCore Node Deno Bun.md>). |
| How do JavaScript promises propagate a failure through a chain? | Use the existing [promise-chaining lesson](<../../../../JavaScript/13 Async Event Loop and Promises/sections/3. Promises core/3.2. Chaining then catch finally and error propagation.md>). |
| How do we configure a production delivery pipeline or enforce access rules? | Learn the relevant delivery or security implementation topic; a familiar name is not an implementation plan. |

Later domains in this track introduce specialist vocabulary in a deliberate
order. Their lessons appear in the [track index](<../../../README.md>) as they
become available. Dedicated implementation tracks may still be planned; a future
track's name should not be mistaken for an available prerequisite. Start with
what you can understand and state the missing context honestly.

### 2) **Record meaning and evidence rather than just an expansion**

A useful entry answers four practical questions: what was the expression, what
did it mean here, what evidence supports that interpretation, and where should
you go for the full explanation? Add an unresolved question when the available
evidence does not settle something important.

Here is a completed entry for the fictional FieldNotes situation:

| Field | Example entry |
|---|---|
| Expression | client |
| Context | The constructed FieldNotes/OrdersTest report in the earlier context lesson. |
| Meaning here | FieldNotes, the application making the order-label request. |
| Concrete use | FieldNotes requests a label from the Orders application installed as OrdersTest. |
| Evidence | The follow-up explicitly names FieldNotes as the requesting application. |
| Boundary | This entry does not define every use of client or establish why a request fails. |
| Full explanation | The [context lesson](<../1. Words in context/1.2. Overloaded words and ambiguous abbreviations.md>) owns word ambiguity; the application's contract needs its own reference. |
| Still unknown | Which request and result caused the original reported failure. |

The entry works without inventing an expansion: client is already a word.
For an initialism, include the expansion if it helps, then keep the same context
and evidence fields. For a changing API or support policy, also record the
relevant version and the date you checked the source. That date describes your
evidence, not a promise that the information will remain true indefinitely.

Julia Evans describes building a small dictionary while learning unfamiliar
project terms in [How to ask good questions](https://jvns.ca/blog/good-questions/).
The value here is orientation: names and relationships make the next question
easier to formulate. Your record can be short; a complete encyclopedia is not
needed before participating in a discussion.

### 3) **Revisit entries when their context changes**

Suppose another teammate says "the client renewed the service contract." Do not
replace the FieldNotes entry with "client means customer" and erase the earlier
context. Add the customer context or distinguish the two uses. A vocabulary
record should help you select a meaning, not force one meaning onto every message.

When your understanding changes, correct the entry and preserve the distinction
that caused confusion. If a document update changes a feature's status, record
the new source/version instead of leaving an old label as timeless advice.
Use links to the full owner explanation so every personal reminder does not
become a second, gradually diverging lesson.

Practice: create an entry for stable using the
[status lesson](<../2. Reading technical documents/2.2. Requirements guarantees defaults and support status.md>).
A sound entry names the publisher and policy, explains the relevant compatibility
meaning briefly, links the policy and lists availability on your target platform
as a separate question. An entry saying "stable means safe and fast everywhere"
fails because it replaces scoped evidence with unestablished promises.

### 4) **Common confusion**

A glossary is a navigation aid, not proof that the reader can implement every
concept it names. Being able to explain a queue, database or interface is a
valuable starting point. Operating one correctly requires additional design,
testing and practical experience.

Nor does linking an owner remove the need for a short local explanation. A reader
should understand the current sentence without following a long chain of links.
Give the minimum context here and use the link for the genuinely deeper question.

### 5) **Performance note**

Keeping vocabulary notes has no direct effect on program runtime. The practical
cost is maintaining reliable information: copying a long technical explanation
creates another place that can become stale. A brief reminder with a precise
owner link reduces duplicated maintenance. That is an information-management
trade-off, not a measured improvement in application latency or memory use.

### 6) **Mentor note**

Review one learner entry by changing its context. Ask whether its definition
still applies and what new evidence would be needed. Then ask the learner to
teach the distinction with an example. A sound record helps them revise their
explanation; it should not encourage defending an old expansion after its scope
has stopped fitting the situation.
