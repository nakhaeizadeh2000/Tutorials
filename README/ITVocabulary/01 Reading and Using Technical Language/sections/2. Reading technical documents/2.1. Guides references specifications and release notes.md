## 2.1. Guides references specifications and release notes

You need to change a program's waiting time. A tutorial demonstrates one value,
a reference lists an option, a protocol specification discusses timing rules,
and release notes announce a changed default. Which page answers your question?

All four can be useful, but for different reasons. This lesson teaches a reading
route, using constructed documents rather than a real program to configure.
You need no installation. The goal is to choose evidence for a question and
recognize what that evidence leaves unresolved.

### 1) **Choose a document by the question it can answer**

**Documentation** is information that helps people understand, use or maintain a
system. A site's labels are helpful clues rather than a universal classification.
A page called "guide" may mix instructions and explanation; inspect its purpose.

| Need | Useful document | What to expect |
|---|---|---|
| Learn a small task for the first time. | Tutorial | A guided sequence with a manageable example and outcome. |
| Complete a task you already understand. | How-to guide | A focused procedure with stated prerequisites. |
| Look up a setting or operation. | Reference | Names, allowed values, meanings and conditions. |
| Understand why a design works this way. | Explanation | Concepts, causes, alternatives and trade-offs. |
| Establish defined behavior or interoperability rules. | Specification | Precise requirements within a declared scope. |
| Understand what changed between releases. | Release notes or changelog | Version-specific additions, fixes, removals and compatibility information. |

**Interoperability** means that different implementations can work together under
the relevant rules. A **release** is a named published version of software or
another deliverable. A **changelog** records changes, often across several releases;
release notes may select and explain the changes important to readers.

The first four document purposes follow the user-needs distinction in
[Diátaxis](https://diataxis.fr/). It is a useful reading lens, not a rule that
every publisher must use those four headings or keep every page in one category.
Specifications and release records answer additional questions about requirements
and change over time.

### 2) **Separate an example from a requirement or guarantee**

Suppose a fictional reference says:

> `waitSeconds` is a non-negative number of seconds. When omitted, it is 20.

A tutorial for the same fictional tool uses `waitSeconds = 5`. Its example shows
one choice. It does not change the reference's documented default to five seconds.
Nor does the sentence establish that an operation will always finish within five
seconds: you would need the option's actual behavior and relevant conditions.

A **default** is the value or behavior selected when no applicable override is
provided. A **requirement** states what must hold in its scope. A **guarantee**
promises an outcome under particular conditions. These are different kinds of
statement. A recommended setting is not automatically a requirement, and an
observed successful example is not automatically a guarantee.

Specifications can contain explanatory examples as well as requirements. Look
for the document's own conventions for **normative** material, which defines
requirements or conformance, and **informative** material, which aids explanation.
Do not infer the distinction from whether a paragraph contains code.

**RFC** is the historical title Request for Comments in the Internet document
series. An RFC is not automatically an Internet Standard: the series includes
Informational, Experimental and other statuses. Check the document status and
which documents update or replace it. The IETF's
[RFC overview](https://www.ietf.org/process/rfcs/) explains those distinctions.
An internal company proposal called an RFC can use the same initials with a
different publication process.

### 3) **Follow a versioned reading route and preserve uncertainty**

For the waiting-time task, start by identifying the program and installed version.
Use a guide if you need the procedure, then the matching reference to understand
the option. Read release notes for the versions crossed by an upgrade. Consult a
specification when your question concerns behavior it actually defines.

Imagine fictional version 3.0 release notes say the default changed from 20 to
10 seconds. A version 2.4 installation does not acquire that default merely
because its user opened the current documentation. Conversely, an old tutorial
can still teach a sound concept while giving an obsolete option name. Preserve
the useful explanation, then verify the version-sensitive instruction.

When sources disagree, identify whether they describe the same version, platform,
configuration and scope. An implementation can also have a defect or a documented
deviation. A specification tells you the intended contract within its scope;
an observation tells you what occurred in the tested conditions. Investigate the
disagreement rather than discarding either kind of evidence automatically.

Practice: you know how to edit the configuration but need to learn whether
`waitSeconds = 0` is allowed in fictional version 2.4. Choose the first document
and explain why. A version-matched reference is the best first choice because
the question concerns an allowed value. If the reference does not state what zero
does, report that gap; neither a tutorial's positive example nor "non-negative"
alone establishes whether zero means no wait, no limit or something else.

### 4) **Common confusion**

"Official" identifies a source's relationship to a project, not a promise that
every sentence is current, complete or applicable to your installation. Check
the selected version and the statement's conditions. A useful third-party
explanation can help you understand an idea while the project's own reference
establishes the implementation-specific behavior you need to verify.

Likewise, "specification" is a document purpose, not proof of adoption by every
product. A vendor can implement only a declared subset or a particular edition.
Ask what actually claims conformance to which rules.

### 5) **Performance note**

Choosing a document type has no direct runtime effect. Applying an option from
the wrong version can affect waiting, resource use or error behavior, but the
effect depends on that option's semantics. Do not turn a tutorial's timing
example into a benchmark. Record the version, operation and measurement conditions
before comparing results.

### 6) **Mentor note**

Ask a learner to find the sentence supporting a proposed configuration change.
Then ask whether it is an example, recommendation, default, requirement or measured
result. A strong answer names both the evidence and its version/scope. If the
learner points to a successful tutorial run, ask what additional evidence would
establish behavior for the proposed setting and installed version.
