## 2.2. Requirements guarantees defaults and support status

"The client should retry. The option is stable and enabled by default." Does
this mean retrying is required, every request succeeds, and every installation
has the option enabled? None of those conclusions follows without more context.

This lesson distinguishes three questions: what a document requires, what
behavior it promises, and what a publisher says about a feature's lifecycle.
The examples are fictional text to interpret; there is no program to install.
Use the previous lesson's distinction between a reference and a specification.

### 1) **Read requirement levels within the document that defines them**

A requirement is a rule within a stated scope. In Internet specifications using
**BCP 14**, a particular set of uppercase words carries defined requirement levels.
BCP means Best Current Practice; BCP 14 includes
[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119.html) and its clarification,
[RFC 8174](https://www.rfc-editor.org/rfc/rfc8174.html).

| Keyword in that convention | Interpretation |
|---|---|
| MUST or REQUIRED | Conformance requires this behavior when its stated conditions apply. |
| MUST NOT | Conformance prohibits this behavior in its stated scope. |
| SHOULD or RECOMMENDED | There can be justified exceptions, but their implications must be understood and weighed. |
| SHOULD NOT | There can be justified reasons to do it, with the consequences understood and weighed. |
| MAY or OPTIONAL | The feature or behavior is permitted rather than required; other applicable rules still apply. |

Check the document's convention rather than assigning special force to capitals
everywhere. RFC 8174 also makes clear that requirements can be normative without
using those keywords. Lowercase wording is interpreted as ordinary English under
that convention; it does not automatically make the whole sentence irrelevant.

Consider this constructed specification excerpt, which explicitly adopts BCP 14:

```text
When a request contains an unknown field, the receiver MUST reject the request.
The receiver SHOULD include a human-readable explanation.
The sender MAY include an optional note field.
```

If an unknown field is present, rejection is required by this fictional contract.
Omitting the explanation needs a justified exception to the recommendation.
The note field is optional, but that does not make every arbitrary field valid.
The permitted option and the unknown-field rule address different cases.

Notice the condition in the first sentence. It does not require rejecting every
request. A useful reading names the actor, triggering condition and required
behavior together. Dropping any one of them can reverse the meaning.

### 2) **Keep guarantees distinct from defaults and observations**

A guarantee is a promise within conditions and limits. "If the service accepts
an order, it assigns an order identifier" promises a relationship between
acceptance and an identifier. It does not promise that every submitted order is
accepted, that acceptance takes one second or that a later payment succeeds.

A default, as introduced in the
[document-reading lesson](<2.1. Guides references specifications and release notes.md>),
is what is selected without an applicable override. Suppose a fictional reference
says retries default to two attempts. An administrator can explicitly configure
one attempt. Knowing the default does not tell you the effective setting of that
installation. Ask which configuration sources and overrides actually apply.

An **observation** records what happened in a particular case. If three requests
succeeded in a local check, you observed three successes. You have not established
a promise for all requests. If observed behavior contradicts a documented
guarantee under its stated conditions, preserve the inputs, versions and result
so the discrepancy can be investigated.

Practice: "Requests with a valid identifier MUST return its stored label" does
not tell you what happens for an invalid identifier. A sound answer records the
gap and looks for another clause. Treating the unspecified case as success,
rejection or a crash would add behavior absent from the sentence.

### 3) **Interpret lifecycle and support labels as scoped policies**

**Experimental** and **preview** usually warn that a feature is still being
evaluated or can change under the publisher's stated policy. **Stable** typically
signals an intended compatibility level. These labels do not share one universal
definition across projects, and stable does not mean defect-free.

For a concrete publisher-specific example, Node.js documents its own
[stability index](https://nodejs.org/api/documentation.html#stability-index).
Its experimental category does not carry the same compatibility policy as its
stable category. Its legacy category is also distinct from deprecated. Read the
selected Node version's policy rather than transplanting those meanings to an
unrelated product.

**Deprecated** commonly means the publisher no longer recommends new use, while
the feature may still work for compatibility. It does not by itself announce a
removal date. **Removed** states that an implementation no longer supplies the
feature in the relevant version. **Obsolete** is less consistent: MDN explains
that it historically distinguished obsolete from deprecated but no longer uses
obsolete as a separate status label. See
[MDN's own status conventions](https://developer.mozilla.org/en-US/docs/MDN/Writing_guidelines/Experimental_deprecated_obsolete).

**Supported** also needs a subject and scope. A platform can support an operation
while its release line no longer receives maintenance from the publisher. A team
can support a browser in its product while one feature needs a fallback there.
Ask whether support means availability, compatibility testing, maintenance or a
service commitment, then find the relevant policy.

For a fictional release note saying "The old option is deprecated in 4.0," the
justified conclusion is that new use is discouraged under that project's policy.
You still need the migration guidance, effective replacement behavior and any
removal schedule. "Delete it immediately" and "it will work forever" both go
beyond the statement.

### 4) **Common confusion**

Optional does not mean unimportant or unconstrained. A feature can be optional
to implement but have strict requirements once selected. Likewise, enabled by
default does not mean mandatory: a default describes selection, while a rule
describes permitted behavior.

Another trap is reading "stable" as "available everywhere." The status of a
design, one implementation's compatibility policy and the installations your
users run are different facts. Establish each one separately.

### 5) **Performance note**

These labels do not directly make a program faster. They affect which behavior
you can responsibly assume. A default retry count can influence waiting and work
performed, but a stable/deprecated label alone predicts neither cost nor speed.
Measure the effective configuration and operation; do not use lifecycle status
as performance evidence.

### 6) **Mentor note**

Give a learner one conditional MUST and an optional feature with its own rule.
Ask which actor must do what when the option is absent and when it is present.
Then add a deprecation notice without a removal date. A sound answer preserves
the conditions, follows the option's applicable rules and explicitly leaves
the removal date unknown. This tests interpretation rather than keyword recall.
