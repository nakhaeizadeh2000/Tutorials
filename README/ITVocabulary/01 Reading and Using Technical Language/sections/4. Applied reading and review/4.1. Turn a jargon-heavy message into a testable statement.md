## 4.1. Turn a jargon-heavy message into a testable statement

This exercise combines the domain's vocabulary and reading habits. The following
message and evidence are constructed for practice; they are not results from a
real application or a test you have run.

> Client green in test. Stable API passed QA. Ready to ship; should be fast.

The sentence is short, but several readers could act on different meanings.
Your task is to rewrite it without inventing confidence, failures or requirements.
No programming is required. Try the exercise before reading the worked answer.

### 1) **Separate ambiguous wording from the evidence actually supplied**

Use this fictional evidence card:

| Item | Available information |
|---|---|
| Requesting program | FieldNotes, version 2.4 |
| Receiving program and installation | Orders, installed as OrdersTest |
| Operation | Request the stored label for an order identifier. |
| First observation | Identifier 101: expected `Lamp`; received `Lamp`. |
| Second observation | Identifier 102: expected `Book`; received `Book`. |
| Missing-identifier requirement | The fictional contract requires a `not found` result when an identifier is absent. |
| Missing-identifier check | Not performed in this record. |
| Timing information | No response-time measurements were recorded. |
| Production availability | Not checked; no release decision is recorded. |
| Stable status | A publisher labels the interface stable under its compatibility policy. |

The word **green** is informal status shorthand, often suggesting that some
check passed. It needs the check's name and result. QA could refer to people,
activities or a team label. "Ready" needs a named decision and criteria.
The earlier lessons explain these distinctions; the new work is applying them
together to a single piece of evidence.

Write down which phrases are ambiguous and which are unsupported conclusions.
Client and test need concrete names. "Passed QA" exaggerates the two observations
unless the intended scope is stated. "Should be fast" is an expectation with no
measurement here. Stable status does not supply the missing performance evidence.

### 2) **Produce a scoped statement and an actionable next question**

One sound rewrite is:

> In OrdersTest, FieldNotes 2.4 received the expected labels for order identifiers
> 101 and 102 in the recorded checks. The missing-identifier case required by
> the contract has not been checked in this record. No timing measurements or
> production-release decision are recorded. Which remaining checks and acceptance
> criteria apply before the release decision?

The rewrite names the actors, installation, inputs and observed outcomes.
It also distinguishes three missing things: a behavior check, a measurement and
a decision. It does not claim that the missing-identifier behavior is broken.
It says the supplied evidence does not establish that behavior.

A **testable statement** describes a claim clearly enough to compare it with
relevant evidence. A future check of an absent identifier needs a known absent
identifier, the contract's expected `not found` result and the actual result.
The present record supplies only the requirement and the missing check. Ask for
the missing input and execution evidence rather than writing "error handling
passed" to make the report look finished.

NASA's [requirement-writing checklist](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/)
similarly emphasizes clear terms, stated assumptions and criteria for verification.
That is useful guidance for precise wording here; this exercise does not import
NASA's entire requirements process into an ordinary team status update.

For a stakeholder who only needs release status, a shorter faithful version is:

> Two recorded order-label checks matched expectations in the test installation.
> A required missing-order check remains unverified, and the release decision is
> still open. Response time has not been measured.

This version omits identifiers because they are not needed for that audience's
immediate decision. Keep the detailed evidence available to whoever investigates
or reproduces the checks. Adapting the detail does not authorize changing the
certainty of the claim.

### 3) **Review the rewrite for hidden additions and useful omissions**

Compare a draft against the evidence card, sentence by sentence. Ask whether each
statement is an observation, a rule, an assumption, a proposed action or an open
question. A claim about the application's behavior should not silently become
a claim about every installation or future request.

Three tempting rewrites fail for different reasons:

| Draft | Why it exceeds or distorts the evidence |
|---|---|
| The API works, so release it. | Two cases do not establish every relevant outcome or the release criteria. |
| The missing-order behavior fails. | The case was not performed; absence of evidence is not an observed failure. |
| OrdersTest is fast because the API is stable. | Compatibility status supplies neither measurements nor a performance target. |

An interview question can test this reasoning: "What would convince you that
this message supports a release decision?" A strong answer asks for the applicable
criteria and evidence covering them, including the stated missing behavior.
It does not prescribe an arbitrary number of tests or pretend that testing can
establish every property for all possible inputs.

Practice variation: someone proposes adding "Every request returns within one
second." What is missing? The card provides no timing evidence, definition of
which requests count or conditions under which a timing promise would hold.
You can propose a performance question, but cannot honestly report that universal
claim as a checked fact.

### 4) **Common confusion**

Precise wording need not remove all uncertainty. "The record does not include
this check" can be more accurate and useful than either "passed" or "failed."
The purpose is to make a decision's evidence and gaps visible.

Nor does every status message need every technical detail. The evidence card
and the stakeholder summary serve different purposes. Preserve the link between
them so that brevity does not erase qualifications or prevent investigation.

### 5) **Performance note**

The communication exercise has no direct runtime effect. Its performance lesson
is about evidence: a successful functional result does not establish response
time. A useful performance investigation identifies the operation, workload,
environment, measurement boundary and target before drawing conclusions. Here,
the correct timing conclusion is simply that no measurements were supplied.

### 6) **Mentor note**

Ask a learner to highlight every factual claim in their rewrite and point to its
supporting card entry. Then remove one entry and ask which sentence must change.
This reveals whether the learner follows evidence or merely writes authoritative
phrases. Give credit for leaving an important question open and for distinguishing
unverified behavior from an observed failure.
