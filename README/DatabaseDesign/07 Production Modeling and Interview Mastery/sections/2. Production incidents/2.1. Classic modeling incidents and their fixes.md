# 2.1. Classic modeling incidents and their fixes

## 1. The orphan storm (dropped FKs meeting buggy writers — Domains 01 and 04)

**Definition** — the incident: orphan rows accumulating silently after FKs were dropped "for performance" (or never created — the schema coasted on application validation), then a buggy writer (bulk import, race window, missed validation path) inserts thousands referencing nonexistent parents. Discovery: defensive `WHERE x IS NOT NULL` clauses multiplying per query (symptom — queries defending against impossible states); a dashboard counting "unknown" customers (symptom — orphans surfaced as business entities); or a JOIN silently dropping rows (symptom — INNER JOIN excluding orphans, totals drifting from source counts). Root cause always structural (unenforced reference), never writer-local (any writer eventually errs — backfills, consoles, races, bugs — the five horsemen of application-only integrity).

**What problem it solves (by cataloging)** — orphan storms recur because each generation rediscovers them (new team, new service, same "FKs are slow" blog post — the cycle from [Domain 04 §1.1](<../../../04 Relationships at Scale/sections/1. Foreign keys at volume/1.1. Foreign keys that survive traffic.md>)). The catalog entry converts rediscovery to reference ("orphan storm — see 04/1.1 ledger, 01/2.2 writer-windows — fix: restore FKs phased (05/1.1), sweep orphans (quarantine → assign-or-purge, certificated), add CI FK audit"). Postmortems citing catalog entries close faster (diagnosis pre-written — verify, don't derive); prevention cites the same entry (review ritual from [1.2](<../1. Track synthesis/1.2. Design review as a practice.md>) — FK lines enforced per PR).

**Modern guidance** — the fix sequence (runbook-shaped, phased per [Domain 05 §1.1](<../../../05 Evolution Growth and Partitioning/sections/1. Schema evolution/1.1. Expand and contract migrations.md>)): (1) **stop the bleeding** (fix writers — validation paths, race windows — orphans stop accumulating *before* cleanup, else cleanup chases inflow); (2) **quarantine** (identify orphans — anti-join query — move to quarantine table or flag — deletes nothing yet, reversibility preserved); (3) **adjudicate** (per orphan class: reassignable (parent typo'd — point at true parent), deletable (genuinely meaningless — purge with certificate), ambiguous (business decides — ticketed, SLA'd)); (4) **restore enforcement** (ADD CONSTRAINT phased — NOT VALID then VALIDATE on clean history — FKs return, CI audit prevents recurrence); (5) **register** (postmortem → trigger: unindexed/unconstrained-FK count alerted at zero-tolerance — [Domain 04 §4.1](<../../../04 Relationships at Scale/sections/4. Mentor checklist/4.1. Relationship review checklist mentors insist on.md>)'s automation). Order matters (bleeding → quarantine → adjudicate → enforce → register — cleanup before enforcement re-breaks writers; enforcement before adjudication blocks legitimate edge cases).

```sql
-- GOOD: the fix sequence as SQL — quarantine, adjudicate, enforce (runbook excerpt).
-- (1) Identify: SELECT l.id FROM order_lines l LEFT JOIN orders o ON o.id = l.order_id
--     WHERE o.id IS NULL;  (anti-join — orphans enumerated, counted, sampled)
-- (2) Quarantine: CREATE TABLE orphan_lines AS SELECT ... (reversible — nothing deleted);
-- (3) Adjudicate per class (reassign / purge-with-certificate / ticket ambiguity);
-- (4) Enforce phased: ALTER TABLE order_lines ADD CONSTRAINT ... FOREIGN KEY ... NOT VALID;
--     then VALIDATE after cleanup (05/1.1 discipline — no blocking rewrite);
-- (5) Register: CI FK audit (zero bare FKs) + postmortem trigger. Storm closed, recurrence barred.
```

```sql
-- BAD: the panic fix — delete first, enforce never, learn nothing.
-- DELETE FROM order_lines WHERE order_id NOT IN (SELECT id FROM orders);  -- 2M rows, one
-- statement (locks, bloat, lag — heroic delete incident wearing orphan cleanup);
-- ambiguous orphans destroyed with reassignable ones (revenue history damaged permanently);
-- writers unfixed (inflow continues — storm resumes within weeks); FKs unrestored
-- ("we'll add them later" — later never scheduled); postmortem absent (rediscovery
-- scheduled for next team, next service, next blog post). Panic as procedure, recurrence guaranteed.
```

**Common confusion** — *"orphans are a data-quality issue, not modeling."* Data quality *executes* cleanup; modeling *prevents* recurrence (FKs restored, CI auditing, writers fixed — structural responses to structural causes). Quality teams sweeping orphans quarterly while FKs stay dropped treat symptoms permanently (sweeps as operations — toil scheduled forever); modelers restoring enforcement cure structurally (sweeps unneeded — orphans impossible). Both roles matter; neither substitutes (sweep without enforcement recurs; enforcement without sweep leaves history dirty). Model cures; quality verifies cure held — sequence, not substitution.

**Performance note** — orphan economics: storms cost engineering quarters (quarantine + adjudication + enforcement + postmortem — multi-week projects with business stakeholders for ambiguous classes); prevention costs an index + constraint per FK (microseconds per write — [Domain 04 §1.1](<../../../04 Relationships at Scale/sections/1. Foreign keys at volume/1.1. Foreign keys that survive traffic.md>)'s ledger — cheapest insurance in relational modeling). Cleanup queries cost anti-join scans (full child scans — one-time, off-peak, acceptable); panic deletes cost heroic rewrites (locks + bloat + lag — [Domain 05](<../../../05 Evolution Growth and Partitioning/README.md>) physics). Prevention pennies, storms quarters — the ledger that ends "FKs are slow" permanently (stated finally — the debate's tombstone, track complete).

**Mentor note** — teach orphan storms as *the* FK parable (every junior hears it once — ideally in training (this catalog), never in production (on-call discovering orphans at 3 a.m.)). The parable structure (dropped FKs → buggy writer → silent accumulation → defensive queries → discovery → phased fix → CI prevention) sticks permanently — juniors who've internalized the arc defend FKs unprompted for careers. Tell it early (onboarding week one — with the anti-join query runnable on staging data); reference it per FK debate ("storm risk?" — two words ending re-litigation). Parables prevent; ledgers convince; both retained.

## 2. The ceiling collision (unbounded nests meeting physics — Domains 02 and 03)

**Definition** — the incident: a document/array/table growing unboundedly until it hits a physical limit — MongoDB 16MB document ceiling (nested event streams, activity feeds, comment arrays — [Domain 03 §2.1](<../../../03 Document Modeling for Scale/sections/2. Embed or reference/2.1. Embed when together.md>)'s growth bombs), PostgreSQL TOAST/row limits on wide rows (unbounded JSONB accumulations — [Domain 02 §1.2](<../../../02 Normalization Deep Dive/sections/1. Dependencies and atomicity/1.2. First normal form atomic values.md>)'s arrays-as-junctions), or operational ceilings (single-partition hot spots, oversized rows breaking replication packets). Discovery: writes failing at the limit (hard errors — inserts rejected — functionality breaking, not degrading); reads degrading toward it (multi-MB documents transferred per title render — latency climbing months before collision); migrations forced under deadline (split streams out *now* — physics scheduling the project, terms dictated by the ceiling, not the team).

**What problem it solves (by cataloging)** — ceiling collisions recur because growth feels linear until limits (teams watching averages miss maximums — mean document 4KB, max 15.9MB — dashboards green on means, red on maxes nobody gauges). The catalog entry converts surprise to schedule ("ceiling collision — see 03/2.1 bound audits, 02/1.2 array conditions, 05/2.1 growth math — fix: bucket/split migration under expand/contract, gauges from birth"). Postmortems citing the entry close faster (bound audit missing — named precisely); prevention cites bound audits per nested structure ([Domain 03 §4.1](<../../../03 Document Modeling for Scale/sections/4. Mentor checklist/4.1. Document modeling checklist mentors insist on.md>) — cap/rate/breaker per array, review-enforced). Gauges on maximums (not means) catch collisions quarters early — the monitoring lesson embedded in the modeling one.

**Modern guidance** — the fix sequence: (1) **relieve** (stop the growth — rate-limit appends, redirect new writes to split structures — collision halted before migration, else migration chases inflow — same bleeding-first order as orphan storms); (2) **migrate under expand/contract** (new bucketed/split shape alongside — dual-write during cutover — backfill history chunked — readers switched — old shape dropped — [Domain 05 §1.1](<../../../05 Evolution Growth and Partitioning/sections/1. Schema evolution/1.1. Expand and contract migrations.md>) for relational, [Domain 03 §3.2](<../../../03 Document Modeling for Scale/sections/3. Patterns and change/3.2. Versioning and shape migration.md>) lazy/eager for documents); (3) **gauge maximums** (max-document-size, max-array-length, max-row-width — alerted at 70% of limits — means retired from capacity dashboards wherever maximums govern); (4) **register** (bound audits mandatory per nested structure going forward — review template updated — postmortem trigger: "unbounded growth scheduled by physics again — never"). Relief before migration (chasing inflow fails); gauges with migration (unmonitored splits re-collide in new shapes).

```sql
-- GOOD: relief then migration — inflow halted, shape split, maximums gauged (runbook excerpt).
-- (1) Relief: rate-limit event appends (shed load) + redirect new writes to buckets_new
--     (dual-write begins — old shape frozen growing, new shape receiving).
-- (2) Migrate: backfill history into buckets chunked (throttled, resumable — 05/1.1);
--     readers switched to buckets; old nested shape dropped (witnessed zero refs).
-- (3) Gauges: max bucket size + max array length alerted at 70% limits (means retired).
-- (4) Register: bound audits per nested structure (review-enforced — 03/4.1 template).
-- Physics met on schedule; terms dictated by team. Collision closed, recurrence barred.
```

```sql
-- BAD: the deadline migration — physics scheduling, terms dictated, quality sacrificed.
-- (Growth unrelieved — migration chasing inflow (backfill rerun thrice — moving target).
-- Shape rushed (buckets sized by panic, not predicates — re-migration within a year).
-- Gauges unadded (maximums still unmonitored — next collision already growing, invisibly).
-- Register absent ("we'll add bound audits later" — later unscheduled, rhythm unprotected).
-- Migrated under ceiling pressure: slower (chasing), worse (rushed shapes), blind (ungauged).
-- Deadline migrations cost triple (chase + rush + blindness) — relief-first costs once.
```

**Common confusion** — *"bigger limits would prevent this (raise the ceiling)."* Limits move, physics remains (16MB → 64MB delays collision by growth-months, never prevents — unbounded growth meets every ceiling eventually; TOAST tuning, row-size knobs — same delay, same destiny). "Raise the limit" treats symptoms (capacity) while causes persist (unboundedness undesigned — no bound audit, no bucket, no gauges). Bounded shapes survive any limit (buckets work at 1MB or 1GB ceilings — design independent of constants); unbounded shapes die at every limit (migration per ceiling raise — recurring tax on undesigned growth). Design boundedness; ignore limit values — limits change, unboundedness kills across all of them.

**Performance note** — collision economics: relief costs throttling (shed load briefly — availability dip, bounded, communicated); deadline migration costs triple (chase + rush + blindness above — quarters of drag); gauged prevention costs bound audits (minutes per structure at design) + maximum gauges (trivial queries, dashboarded). Unbounded growth's performance degrades *before* collision (multi-MB transfers per read — latency climbing months early — the early warning unheeded without maximum gauges). Gauges catch degradation quarters before collision — prevention window wide open for teams measuring maximums; shut for teams averaging means.

**Mentor note** — teach "gauge maximums, not means" (juniors monitoring means learn the lesson in one incident (green means, red maxes — collision "unexpected" despite months of growth signals); maximum gauges thereafter permanent habit (size, length, width maximums on every unbounded structure — dashboarded from birth). The means/maxims distinction generalizes (p99 vs mean latency, max vs average queue depth, hottest vs average partition — extremes govern incidents, averages govern reports). Extremes page; averages report — monitor extremes, report averages, never confuse the two.

## 3. The fiction dashboard (fan-out sums meeting finance — Domains 02 and 04)

**Definition** — the incident: reporting queries joining independent one-to-many children multiply rows (orders × lines × events — [Domain 04 §3.1](<../../../04 Relationships at Scale/sections/3. Skew and hot relationships/3.1. Hot keys and skew.md>)'s fan-out rule violated), sums computed over products (revenue 5×'d, counts 10×'d — fiction presented with decimal precision), finance reconciling against inflated numbers (weeks of mistrust — "the database is wrong" — credibility damaged past the fix). Discovery: sums exceeding plausible totals (revenue > Σ payments — division by fan-out reveals it — the sum-consistency assertion from 04/3.1 catching it automatically where present); business questioning numbers (finance's spreadsheet disagreeing with the dashboard — manual reconciliation exposing multiplicative error); new fan added (shipments joined in — fiction multiplier changing silently — previously-"correct" dashboard drifting without code changes to its logic).

**What problem it solves (by cataloging)** — fan-out fictions recur because they look correct (queries return numbers, dashboards render, decimals reassure — wrongness invisible without independent totals to compare against). The catalog entry converts invisible-wrong to checkable ("fiction dashboard — see 04/3.1 split rule, 02/2.2 independence diagnosis — fix: split queries aggregating independently, add sum-consistency assertions, backfill corrections with announcements"). Postmortems citing the entry close faster (fan-out named — split prescribed — assertions added); prevention cites review reflex ("two one-to-many children in one query — flag on sight" — [Domain 04 §4.1](<../../../04 Relationships at Scale/sections/4. Mentor checklist/4.1. Relationship review checklist mentors insist on.md>)). Fiction requires the absence of cross-checks; assertions make absence impossible.

**Modern guidance** — the fix sequence: (1) **freeze** (mark dashboard untrusted — banner, not silent fix — decisions made on fiction need revisiting (finance notified with corrected numbers + error bounds — trust repaired by transparency, never by quiet correction)); (2) **split** (each fan aggregated independently — lines query, events query, shipments query — assembled in code — 04/3.1's rule applied — corrected numbers verified against independent totals (payments ledger — ground truth outside the fan-out)); (3) **assert** (sum-consistency assertions deployed — revenue ≈ Σ payments within tolerance — alerting on divergence — fiction detectable automatically forever after); (4) **register** (review reflex enforced — two-fans-one-query flagged structurally (linter where feasible — JOIN-count heuristics + fan-out shape detection); postmortem trigger: "unasserted sums" swept quarterly — every reporting query either asserted or ticketed). Freeze before fix (fictional decisions compound while queries run); assert with fix (unasserted corrections re-fiction silently).

```sql
-- GOOD: freeze, split, assert — fiction contained, corrections verified (runbook excerpt).
-- (1) Freeze: dashboard bannered untrusted (finance notified — corrected numbers + bounds).
-- (2) Split: revenue from lines ONLY (SELECT order_id, sum(qty*price) ... GROUP BY 1);
--     events counted separately (SELECT count(*) ... — independent query, independent truth).
--     Verified vs payments ledger (ground truth outside fans — agreement required, not hoped).
-- (3) Assert: revenue ≈ Σ payments ±0.1% (alerting — divergence pages, fiction impossible silently).
-- (4) Register: two-fans-one-query flagged in review (reflex enforced — 04/4.1); unasserted
--     sums swept quarterly (asserted or ticketed — no silent sums remain).
```

```sql
-- BAD: the quiet correction — fiction fixed silently, trust unrepaired, recurrence unscheduled.
-- (Query fixed without banner — finance decisions made on fiction unrevisited (budgets set,
-- bonuses computed — fiction compounding into compensation). No assertions added ("fixed now" —
-- next fan (shipments) re-fictions silently within quarters). No review reflex (two-fan queries
-- merging weekly — each a future fiction). Trust unrepaired (finance learned dashboards lie —
-- spreadsheets forever after — the dashboard's credibility death, unappealing, permanent).)
-- Silent fixes repair numbers; announced fixes repair trust; assertions prevent recurrence.
-- All three required; silence delivers none.
```

**Common confusion** — *"DISTINCT would have prevented this."* (Asked and answered in [Domain 04 §3.1](<../../../04 Relationships at Scale/sections/3. Skew and hot relationships/3.1. Hot keys and skew.md>); restated for the incident catalog: DISTINCT repairs counts, not sums (revenue still multiplied), not transfer (products still shipped), not future metrics (each new aggregate a new trap). Incident-grade prevention is structural (split queries — cause removed) plus asserted (sum-consistency — recurrence detected) — DISTINCT is per-query symptom-trimming (one weed per query, root spreading). Causes over symptoms — split, assert, register.

**Performance note** — fiction economics: split queries cost round trips (pipelined — negligible) while saving combinatorial transfer (50× rows unshipped — the performance *improvement* wearing a correctness fix — splits pay twice: truth + speed); assertions cost one comparison query per dashboard refresh (trivial — bounded, indexed totals compared); unasserted fiction costs finance trust (unbounded — credibility unrecoverable past repeated incidents — dashboards abandoned for spreadsheets, permanently). Split-and-assert is cheaper *and* truer — the rare fix improving both axes simultaneously (truth with speed — adopt immediately, assert permanently).

**Mentor note** — teach fiction dashboards as *the* fan-out parable (twin of orphan storms for constraints: juniors hearing it once spot two-fan queries forever — "lines × events = 50 rows, sums fictional" — the multiplication table from 04/3.1 performed live cements it). Parable pair (storms for integrity, fictions for aggregation — two stories covering the track's twin failure families) told in onboarding week one, referenced per reporting PR ("fan-out check?" — two words ending re-litigation). Stories prevent; assertions detect; parables stick — all three, always.
