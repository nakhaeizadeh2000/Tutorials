# 2.2. From incidents to prevention

## 1. Postmortems name missing artifacts (which checklist, record, or trigger would have caught it)

**Definition** — the modeling postmortem: blameless incident review whose output is *named missing artifacts* — which review line unasked (FK index? bound audit? skew note?), which record unwritten (denormalization ledger? migration phase? retention policy?), which trigger unset (partition threshold? purge window? relay lag alert?) — each mapped to the track leaf that prescribes it. "Human error" and "be careful" are banned outputs (moral judgments, not artifacts — unrepeatable, unimprovable); missing-artifact lists are the only acceptable finding (concrete, assignable, verifiable — the incident converted to checklist deltas).

**What problem it solves** — the moral postmortem ("engineer should have caught it" — blame without artifact (same engineer catches next time by luck, misses by workload — humans don't scale as controls); "process failed" without naming which line (vague improvement theater — "strengthen reviews" — unmeasurable, unenforced, forgotten by next quarter)). Artifact-naming converts incidents to improvements mechanically (missing FK-index line → CI linter added; missing bound audit → review template updated; missing trigger → gauge dashboarded with owner). Postmortems producing artifact deltas improve systems; postmortems producing judgments degrade culture (blame suppresses reporting — incidents hidden, learning stopped — the opposite of reliability).

**Modern guidance** — the postmortem template (run within a week, owners present, blameless facilitated): *timeline* (what happened, when — facts, no interpretations); *missing artifacts* (checklist lines unasked? records unwritten? triggers unset? — each mapped to track leaves — the findings section, consisting entirely of artifact names + leaf links); *deltas* (template updates, linter additions, gauge dashboards, register entries — assigned with dates — improvements as tickets, never intentions); *sharing* (story-bank entry written — next promise — team learns without re-experiencing). Facilitation rule: every "should have" sentence rewritten as artifact ("should have caught the missing index" → "FK-index CI line absent — added"). Language shapes learning; artifacts shape systems.

```sql
-- GOOD: the postmortem output — artifacts named, deltas ticketed, story banked.
-- Incident: flagship member-list timeouts (2M members, reverse index absent).
-- Missing artifacts: junction reverse-index line unasked (04/4.1 — template present,
-- line skipped); skew note absent (04/2.1 audit unrun — celebrity unexamined);
-- depth gauge unset (no oldest-page metric — degradation invisible pre-incident).
-- Deltas: CI junction-both-ways check (ticket #101, owner platform, due Friday);
-- skew-note review gate (template updated); member-list p99 gauge + alert (dashboarded).
-- Story banked (next promise): "flagship timeouts" told at onboarding henceforth.
```

```sql
-- BAD: the moral postmortem — judgments rendered, artifacts unnamed, recurrence scheduled.
-- "Engineer should have indexed both directions. Team must be more careful with
-- celebrity features. Process needs strengthening." (Which checklist line? Unnamed —
-- template unupdated. Which trigger? Unset — gauges unbuilt. Which record? Unwritten —
-- register empty. Story banked? Unwritten — next hire re-discovers via identical incident.)
-- Judgments without artifacts; intentions without tickets; learning without record.
-- Blame assigned; system unchanged; recurrence certain (same gaps, new quarter).
```

**Common confusion** — *"blameless means no accountability."* Blameless means *system* accountability (artifacts assigned to owners with dates — stronger accountability than blame: verifiable completion vs felt guilt) instead of *personal* accountability theater (blame assigned, system unchanged — accountability performed, learning prevented). Owners own deltas (linter built? gauge dashboarded? template updated? — checkable); nobody owns guilt (uncheckable, unproductive, reporting-suppressing). Accountability for artifacts, blamelessness for humans — both maximal, never traded.

**Performance note** — postmortem economics: artifact postmortems cost hours (facilitated session + delta tickets — bounded, scheduled); moral postmortems cost culture (reporting suppressed — incidents hidden longer, discovered worse — MTTR growing invisibly); unexamined incidents cost recurrence (same gaps, new quarters — full incident price repaid per recurrence). Deltas compound (each postmortem's linters/gauges/templates prevent classes, not instances — prevention ROI growing per incident *declining*); blame compounds negatively (each moral postmortem suppressing the reports that would have triggered artifact postmortems). Artifact culture pays compound interest; blame culture charges it.

**Mentor note** — facilitate first postmortems visibly well (seniors modeling artifact-naming teach more than any process doc — "which leaf prescribes it?" asked per finding, links collected live). Ban "should have/be careful" in real time (rewrite aloud — facilitation as teaching: every moral sentence converted to artifact sentence publicly demonstrates the habit). Teams experiencing one good artifact postmortem demand them thereafter (learning palpable — deltas ticketed, systems visibly improving); teams experiencing moral ones avoid postmortems entirely (learning absent — process resented). Facilitate excellently once; culture follows.

## 2. Prevention is scheduled (triggers, audits, and drills from every incident — never hoped)

**Definition** — the scheduling rule: every postmortem delta gets a calendar entry (trigger thresholds monitored from date X; audit sweeps recurring quarterly from date Y; drills rehearsed monthly from date Z) — prevention *scheduled* (owned, dated, recurring) versus prevention *hoped* ("we'll watch for this" — unwatched; "team knows now" — turnover erases; "won't happen again" — famous last words, statistically). Scheduled prevention is verifiable (did the audit run? did the drill happen? did the trigger fire-or-hold?) — hoped prevention is indistinguishable from forgetting (no evidence either way — absence of incidents attributed to improvement, actually luck, until luck expires).

**What problem it solves** — the action-item graveyard (postmortem notes listing improvements, nobody scheduling, all forgotten within a quarter — "strengthen FK reviews" without CI ticket, owner, or date — intention decaying to zero within weeks); and the drill-less team (procedures documented, never rehearsed — relay-restart runbook untested (fails when needed — stale commands, changed topology); kill drills undrilled (switches decorative — [Domain 06 §3.1](<../../../06 Modeling for Operations/sections/3. Runtime configuration/3.1. Feature flags and config storage.md>)); backup restores untested (rumors, not capabilities)). Scheduling converts intentions to events (calendar entries with owners — executed or visibly skipped, never silently forgotten); drills convert documentation to capability (rehearsed procedures working under pressure — tested, not hoped).

**Modern guidance** — the scheduling contract per delta: *triggers* (threshold + gauge + owner + start-date — monitored from the date, firing or holding visibly — unmonitored triggers are hopes with thresholds); *audits* (register sweeps, flag reviews, version-budget checks — quarterly from date X — calendar invites sent during the postmortem, owners attending); *drills* (relay restarts, kill flips, restore tests, claim-query failures — monthly-to-quarterly per criticality — rehearsed with notes (what broke in rehearsal? — fixed before incidents); *verification* (deltas confirmed complete — linter merged? gauge dashboarded? template updated? — postmortem re-opened until deltas land, never closed on intentions). Postmortem status: OPEN until deltas complete (tracking issue, reviewed weekly — closure on evidence, never on meeting adjournment).

```sql
-- GOOD: prevention scheduled — calendar entries, owners, verification (excerpt).
-- Trigger: junction reverse-index CI check (ticket #101, owner platform, lands Friday;
-- postmortem stays OPEN until merged — closure on evidence).
-- Audit: skew-note gate added to review template (effective immediately; quarterly
-- sweep verifies compliance — first sweep date set: 2026-12-15, owner on call).
-- Drill: relay-restart rehearsal monthly from Nov (runbook tested — gaps fixed same day).
-- Verification: postmortem OPEN (weekly review — closes when all deltas evidence-complete).
```

```sql
-- BAD: prevention hoped — intentions minuted, nothing scheduled.
-- "Action items: strengthen reviews, watch flagship growth, consider gauges."
-- (Tickets? None filed — intentions in meeting notes (unread thereafter). Owners?
-- Unassigned — everybody's job is nobody's. Dates? Absent — "soon" decaying to never.
-- Verification? None — postmortem closed at adjournment (learning celebrated, systems
-- unchanged). Next quarter: identical incident, identical action items, identical hopes.
-- Hoped prevention is forgotten prevention with better minutes. Schedule or surrender.)
```

**Common confusion** — *"scheduling prevention is bureaucratic overhead."* (Asked and answered per-tempo; restated finally for postmortem deltas.) Scheduled deltas cost calendar entries + verification minutes (bounded, visible); hoped deltas cost recurrence (full incident price per repeat — unbounded, certain). "Overhead" framing counts scheduling seconds while ignoring recurrence quarters — full ledger favors scheduling by orders of magnitude, eighth and final restatement across the track (counted: each domain's version plus this synthesis — the lesson compounding deliberately, track complete).

**Performance note** — scheduled-prevention economics close the track's prevention argument finally: triggers firing early convert incidents to tickets (cheap, calm, scheduled responses); audits sweeping quarterly convert decay to maintenance (boring, effective, calendared); drills rehearsing convert procedures to capabilities (working under pressure — tested, not hoped). Unscheduled equivalents convert tickets to incidents (expensive, panicked, paged), maintenance to archaeology (heroic, resented, incomplete), procedures to documentation (untested, failing when needed). Schedule converts cost centers to routines — the operations maturity arc complete, track closed.

**Mentor note** — teach "ticketed or it didn't happen" (juniors leaving postmortems with tickets (numbers, owners, dates) learn improvement-as-workflow; juniors leaving with intentions learn improvement-as-theater). Review postmortem openness weekly (OPEN postmortems listed — deltas progressing? blocked? — attention sustained until evidence-complete). Close postmortems on evidence publicly ("deltas landed — linter merged, gauge live, template updated — closing with thanks" — closure celebrated as improvement delivered, not meeting ended). Ticketed deltas, evidenced closure, celebrated improvement — culture in three habits.

## 3. Incident stories teach (the story bank habit — war stories per domain, told early)

**Definition** — the story bank: a living collection of team (and track-catalog) incidents told as narratives (situation → surprise → diagnosis → fix → prevention — five beats, five minutes) — three war stories per domain minimum (orphan storms, ceiling collisions, fiction dashboards from [2.1](<2.1. Classic modeling incidents and their fixes.md>) seeding the bank; team incidents added post-postmortem), told to every junior early (onboarding week one — stories before schemas: consequences felt before rules learned), retold per relevant review ("storm risk?" — two words invoking the full parable). Stories are compressed experience (years of incidents in minutes of narrative — the highest-bandwidth teaching medium in engineering).

**What problem it solves** — rule amnesia (checklists followed mechanically — lines checked without comprehension — judgment absent where rules end (novel situations ungoverned — "the template didn't cover it" — correct, templates never cover everything; judgment covers the rest, judgment needs stories)); and experience bottlenecks (seniors' judgment locked in seniors' heads — juniors repeating incidents seniors survived a decade prior — organizational learning rate capped at mentorship bandwidth). Stories transfer judgment (not just rules — *why* rules exist, felt through consequences — comprehension surviving where compliance fades); banks scale transfer (written once, told infinitely — mentorship bandwidth multiplied — juniors learning from incidents they never experienced, seniors teaching without repeating).

**Modern guidance** — the bank habit (build once, tell always): *collect* (postmortem → story-bank entry — five beats, anonymized where sensitive (blameless extends to storytelling — systems, never persons), linked to home-domain leaves); *curate* (three per domain minimum — best-told retained, duplicates merged, outdated retired (fixed systems' stories kept as history — "how we learned FK discipline" — heritage, not clutter)); *tell early* (onboarding week one — storms/fictions/collisions before schemas — consequences first, rules as their names); *invoke per review* ("storm risk? fiction check? ceiling dated?" — two-word invocations carrying full parables — review shorthand with narrative backing); *refresh* (new incidents added post-postmortem — bank living, never finished — stale banks (untouched yearly) signal incident-free luck or report-suppression — investigate which, celebrate or fix accordingly).

```sql
-- GOOD: the bank living — collected, curated, told early, invoked per review (excerpt).
-- Bank: orphan-storm-2024 (FKs dropped for benchmarks → buggy import → 2M orphans →
-- phased fix + CI audit — told onboarding day 2); fiction-Q2 (lines×events sums 5×'d →
-- finance mistrust → split + assertions — invoked per reporting PR: "fiction check?");
-- ceiling-2025 (nested ticks → 16MB → deadline buckets — invoked per nested array:
-- "ceiling dated?"). Told early (consequences before rules); invoked briefly (shorthand
-- with backing); refreshed post-incident (living, never finished).
```

```sql
-- BAD: the unbanked team — incidents experienced, learning evaporated.
-- Storm 2024 (fixed heroically — postmortem skipped ("too busy") — knowledge in two
-- heads, both departed 2025). Fiction Q2 (fixed silently — finance never told why numbers
-- changed — trust unrepaired, assertions unadded — re-fictioned Q4, larger). Ceiling 2025
-- (migrated under deadline — bound audits unmandated — next nest growing unbounded *now*,
-- invisibly). Juniors repeating all three (unheard stories can't prevent); seniors tired
-- of re-teaching (unbanked knowledge re-taught per hire, degrading per retelling —
-- telephone game with incidents). Experienced thrice, learned never. Evaporation itemized.
```

**Common confusion** — *"stories are anecdotes, not engineering."* Anecdotes *illustrate*; parables *transfer judgment* (rules + consequences + emotion — comprehended, retained, applied — cognitive science on narrative memory vs list memory, consistently one-sided). Checklists govern known situations (complete, verifiable — keep them); stories govern judgment (novel situations, trade-off feel, consequence imagination — irreducible to lines). Engineers need both (lists for completeness, narratives for wisdom — the track's pedagogy pairing checklists (§4s) with war stories (§5s) per domain deliberately). Dismissing stories keeps lists and loses wisdom — complete reviews, hollow judgment.

**Performance note** — story economics: banking costs minutes per incident (five beats written post-postmortem — hot context, cheapest capture); telling costs minutes per junior (onboarding hour covering the bank — highest-bandwidth teaching available); invoking costs seconds per review (two-word shorthand — comprehension compressed); unbanked incidents cost recurrence (full incident price per repeat — quarters each). Bank ROI exceeds 1000× on first prevented repeat (minutes banked vs quarters repeated — the track's steepest return curve, stated finally). Stories compound (each telling slightly better — narrators improving); incidents without banks repeat identically (unlearned lessons, full price, every time).

**Mentor note** — become the team's storyteller-in-chief (seniors telling parables well teach more than any documentation — narrative craft as mentorship skill: five beats, vivid consequences, named artifacts, linked leaves — practiced deliberately, performed naturally). Collect others' stories (juniors' incidents banked with credit — storytelling democratized, bank diversified); retire stale ones (fixed systems' stories kept as heritage — "how we learned" — pride, not clutter). Storytelling leadership compounds mentorship (one telling reaches all listeners — bandwidth seniors can't match 1:1). Tell stories; bank them; invoke briefly; teach narrators — culture in four verbs, track complete.
