# 6.1. Boundaries what is covered elsewhere

## 1. This track ends at design (usage, code, systems beyond — the edges)

**Definition** — the track's outer boundary, stated finally: Database Design teaches *decisions that outlive code* (entities, dependencies, forms, documents, relationships, evolution, operations shapes — seven domains, complete). Beyond its edges: **usage** (operating databases — SQL fluency, EXPLAIN tuning, backup execution, monitoring operation — [Databases track](<../../../../Databases/README.md>)); **code** (mapping shapes into programs — repositories, ODMs/ORMs, worker frameworks, flag SDKs — [DesignPatterns 06](<../../../../DesignPatterns/06 Modern Patterns and Anti-Patterns/README.md>) + ORM track (textual forward — unbuilt)); **systems** (topology, distribution, infrastructure — sharding operations, broker topologies, cluster management — SystemDesign/Microservices/DevOps tracks (textual forwards — unbuilt or sibling-owned)). Edges crisp, crossings linked, repetitions zero — the DRY contract honored at track scale, complete.

**What problem it solves** — track sprawl in both directions (design track absorbing EXPLAIN tutorials (usage without a design question), broker topologies (infrastructure without a modeling decision), ODM mappings (consumption without shape authority) — each absorption diluting the track's thesis (decisions outliving code) with mechanics belonging elsewhere); and track timidity (design refusing adjacent necessities — capacity numbers without measurement functions? triggers without monitoring? — edges drawn so sharply the track starves its own procedures). Edges placed where decisions end (design) and execution begins (usage/code/systems) — procedures referenced across edges (measurement functions linked, monitoring assumed, mappings consumed), mechanics never re-taught. Crisp edges, rich crossings — bounded completeness, track complete.

**Modern guidance** — the edge map (decision → execution, per neighbor): shapes → SQL fluency (write/operate them — Databases 01–03); triggers → monitoring operation (dashboards/alerts/runbooks executing — Databases 06–07); outbox/job/flag shapes → code mappings (repositories/workers/SDKs consuming — Patterns 06, ORM textual); partition/shard keys → topology operation (resharding, rebalancing — SystemDesign textual); audit/retention shapes → compliance operation (legal processes consuming certificates — outside all tracks — one line per DRY). Design reviews cite edges ("execution per Databases 06 runbook — linked"); execution reviews cite designs ("shape per DatabaseDesign 05/2.2 — linked"). Bilateral boundaries (each side referencing the other — stated in both tracks' boundary leaves — rot slower than unilateral claims, verified at every closeout).

**Common confusion** — *"boundaries mean isolation (tracks never interact)."* Boundaries mean *ownership* (each concept one home — DRY at repo scale), crossings mean *interaction* (links everywhere concepts meet — references dense, repetitions zero). Isolated tracks duplicate (same concept taught thrice, drifting); interacting tracks reference (taught once, linked widely — closeouts verifying links track-wide: 600+ and counting). Ownership without interaction is silos; interaction without ownership is duplication. Both, always: owned concepts, linked crossings — the repo's architecture in one sentence, track complete.

**Performance note** — none specific — track-edge performance mechanics (tuning, topologies, SDK overhead) live beyond edges by design. Performance delivered at design time across seven domains; tuning succeeding at execution time across neighbor tracks. Decide upstream; tune downstream — the track's final performance sentence, complete.

**Mentor note** — teach edges as graduation ("you now know where design ends — usage/code/systems beyond, each with its track — learning continues, directed"). Edges orient graduates (next tracks named per interest — operators to Databases 06–07, mappers to Patterns/ORM, scalers to SystemDesign — directed autonomy, not abandonment). Graduates leaving with edge maps learn continuously (directed); graduates leaving without them stall (finished curriculum, unknown next — momentum lost). Map edges; direct onward; graduate completely — mentorship's closing act, track complete.

## 2. Siblings consume this track (ORM mappings, API shapes, microservice boundaries — downstream)

**Definition** — the downstream boundary: sibling tracks consume Database Design outputs without re-teaching them — ORM track maps shapes to mappers (entities → models, relationships → associations, inheritance → strategies — consumption, never redefinition); API tracks shape responses from aggregates (endpoints serving documents/entities designed here — response envelopes referencing, not remodeling); Microservices/CleanArchitecture tracks draw boundaries informed by aggregates (consistency boundaries informing service boundaries — [Domain 03 §1.1](<../../../03 Document Modeling for Scale/sections/1. Aggregates and access/1.1. Aggregates the unit of document modeling.md>)'s invariants constraining service cuts — downstream, never repeated). Consumption flows one way (design constrains code — never reverse — the track's standing rule, sixth restatement across domains, final at track scale).

**What problem it solves** — upstream inversion at track scale (ORM-first modeling ("how will Prisma represent this?" — mapper limitations dictating entities); API-first shaping ("REST needs nested JSON" — response formats dictating aggregates); service-first boundaries ("one service per table" — deployment topology dictating consistency). Each inversion models for consumers, not for domains — schemas serving mappers/endpoints/services inherit their limitations as defects (unmappable junctions become missing entities; unnestable responses become merged aggregates; per-table services become distributed monoliths with cross-service FKs unenforceable). Design upstream (domains constrain); consume downstream (code adapts — friction informative, never vetoing). Direction enforced at track scale — inversions fail architecture review, not just schema review.

**Modern guidance** — the consumption map (producer → consumer, linked one-way): entities/relationships → ORM models/associations (mappers project shapes — friction (unmappable composite keys? inheritance strategies?) resolved mapping-side first, shape-side second with ADR — never mapper-dictated); aggregates/documents → API response shapes (endpoints serve designed units — envelope/pagination added downstream — response needs never reshape aggregates (chips/subsets serve screens without merging lifecycles — [Domain 03](<../../../03 Document Modeling for Scale/README.md>) consumed correctly)); consistency boundaries → service boundaries (services owning aggregates whole — cross-service references eventual (sagas/outbox — [Domain 06 §2.1](<../../../06 Modeling for Operations/sections/2. Coordination out of the database/2.1. Outbox tables designed for relay.md>) consumed) — split aggregates across services never (distributed consistency without boundary — the microservices failure mode starting in modeling). Consume downstream; constrain upstream; link one-way.

```sql
-- GOOD: consumption downstream — shapes constraining code, links one-way (excerpt).
-- ORM maps users/orders/memberships (associations follow FKs — mapper friction resolved
-- mapping-side (custom types, composite-key support) — shapes unchanged, ADRs filed).
-- API serves order aggregates (envelope + keyset pagination downstream — aggregate unmerged).
-- Services own aggregates whole (orders service owns order aggregate — cross-service refs
-- via outbox events (06/2.1 consumed) — eventual, contracted). Upstream constrains;
-- downstream adapts; links flow one way. Architecture directed.
```

```sql
-- BAD: upstream inversion — consumers dictating shapes, defects inheriting limitations.
-- "Prisma can't map composite keys — use surrogate everywhere" (mapper dictating identity —
-- junction invariants weakened track-wide for tool convenience). "API needs nested users
-- with orders — embed customers in orders" (response format merging lifecycles — GDPR
-- archaeology scheduled). "One service per table" (topology dictating consistency —
-- orders split across three services — cross-service transactions impossible — sagas
-- everywhere compensating for boundaries that shouldn't exist). Consumers designing;
-- domains suffering; limitations inheriting. Inversion itemized; direction violated.
```

**Common confusion** — *"greenfield services should design data and code together."* Together, yes — with direction (domains constrain code: aggregates inform service cuts; shapes inform models; invariants inform APIs — co-design with upstream authority, not negotiation among equals). "Together" without direction negotiates (mapper convenience trading against integrity — trades integrity loses eventually, always); "together" with direction collaborates (code informing shapes with usage reality — feedback valued, authority clear — friction resolved mapping-side first). Co-design directed (upstream constrains, downstream informs); never negotiated (peers trading integrity for convenience). Direction dignifies collaboration; absence corrupts it into compromise.

**Performance note** — none specific — consumer performance (ORM hydration, API serialization, service latency) lives downstream by design. This track's downstream contribution, stated finally: shapely data serving fast consumers (bounded documents hydrating cheaply, indexed relationships joining fast, gauge-serving tables observable natively — consumer performance inherited from shape quality). Consumer tuning atop unshaped data (N+1 over reference-spaghetti, hydration of unbounded nests, polling of ungauged queues) is remediation, not optimization — shaped upstream prevents it structurally. Shape well; consume cheaply — the downstream dividend, track complete.

**Mentor note** — teach "who consumes this shape?" per design (juniors naming ORM endpoints/services per table discover downstream implications early — shapes designed consumable (bounded, indexed, gauged) versus shapes designed in vacuum (correct, unusable — mappers choking, endpoints assembling, services splitting)). Consumer-awareness without consumer-submission (shapes serving consumers while constraining them — hospitality with authority — the senior posture toward downstream). Aware, not submissive — hospitable, never inverted. Posture taught per design; direction held per career.

## 3. The method travels (new stores, new frameworks — lenses transfer, shapes adapt)

**Definition** — the graduation thesis: this track teaches *lenses*, not just shapes — dependency arrows (any store with relationships), access catalogs (any store with queries), bound audits (any store with growth), priced copies (any store with hot paths), phased evolution (any store with live traffic), gauge-serving operations (any store with on-call). New stores (graph? time-series? vector? — future engines, same questions: what determines what? what reads together? what grows unbounded? what copies hot? how does it change? who operates?) yield to the same lenses with adapted shapes (edges for relationships, rollups for series, payloads for vectors — shapes novel, lenses permanent). Graduation, not goodbye — lenses traveling beyond every shape taught here.

**What problem it solves** — the track's terminal risk: graduates fluent in seven domains' shapes but blind to eighth-store novelty ("we adopted X — none of the track applies!" — shapes differing, lenses unrecognized — relearning from zero, repeating all seven domains' mistakes in the new engine). Lens-transfer prevents it (arrows drawn on graph edges — dependencies persist; catalogs listed for vector queries — access persists; bound audits on series cardinality — growth persists; copy ledgers for cached embeddings — hot paths persist; phased migrations for schema-full stores — evolution persists; gauges on pipelines — operations persist). Shapes adapt per engine (edges ≠ FKs — but dependencies are dependencies); lenses persist per thinking (questions outliving engines — careers outliving stacks).

**Modern guidance** — the transfer procedure (new store, same lenses): (1) *dependencies* (what determines what? — draw arrows — any store relating data has dependencies — graph edges, series tags, vector metadata — arrows first, always); (2) *access* (what reads together? — catalog queries — any store serving reads has hot paths — embed/colocate/cache accordingly); (3) *bounds* (what grows unbounded? — audit caps/rates/breakers — any store accumulating has ceilings — physical or economic); (4) *copies* (what's hot? — price copies per read:write ratios — any store caching has ledgers); (5) *evolution* (how does it change live? — phase or version per grain — any live store evolves); (6) *operations* (who operates? — gauges, owners, runbooks — any production store pages). Six lenses, any engine, shapes adapted locally. Lenses permanent; shapes provisional; graduates traveling.

**Common confusion** — *"new paradigms need new methods (unlearning required)."* Paradigms change shapes (tables → documents → edges → series → vectors — genuine novelty per engine); methods persist across paradigms (dependencies/access/bounds/copies/evolution/operations — questions engines can't obsolete, only re-dress). "Unlearn relational!" discards lenses with shapes (overcorrection — document generation repeating normalization mistakes expensively attests); "apply relational everywhere!" discards shape novelty (under-correction — reference-spaghetti in document stores attests). Transfer lenses, adapt shapes — neither discard nor impose — the graduated posture toward every new engine, forever.

**Performance note** — none specific — new-engine performance mechanics live with new engines (unlearnable here, correctly). Lens-transfer *is* the performance strategy for novelty (bound audits preventing first-generation ceiling collisions; access catalogs preventing first-generation fan-out; copy ledgers preventing first-generation cache stampedes — each lens preventing its incident class in the new engine *before* local scar tissue forms). Transferred lenses outperform local experience initially (decades of relational/document scar tissue applied day one in graph/vector land — unfair advantage, earned across this track). Travel lenses; skip scars; perform veteran on day one.

**Mentor note** — teach transfer explicitly as graduation ("take arrows/catalogs/bounds/copies/phases/gauges to your next engine — report back what adapted" — graduates as lens missionaries, track's influence compounding across stacks). Collect transfer stories (graph-arrows anecdotes, vector-catalog wins — banked beside incident stories ([2.2](<../2. Production incidents/2.2. From incidents to prevention.md>)) — proof lenses travel, motivation for next cohorts). Graduates returning with transfer stories teach stronger than any curriculum (lived lens-travel, narrated peer-to-peer — pedagogy compounding beyond mentors). Send equipped; welcome back stories; compound influence — mentorship's final act, track complete.
