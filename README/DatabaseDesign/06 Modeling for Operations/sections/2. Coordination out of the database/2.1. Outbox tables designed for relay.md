# 2.1. Outbox tables designed for relay

## 1. The pattern lives in Databases 05 (atomic record, relay, idempotent consume — linked, not repeated)

**Definition** — the transactional outbox in one paragraph (full treatment in [Databases 05 §3.1](<../../../../Databases/05 Transactions Consistency and Integrity/sections/3. Distribution/3.1. Distributed honesty 2PC and sagas.md>), linked per DRY, never restated): business write + event intent commit in *one local transaction* (both-or-neither recorded — the dual-write failure eliminated structurally); a relay process publishes outbox rows to the broker (marks relayed — at-least-once delivery, honestly); consumers handle idempotently (keys dedup — repeats converge). Exactly-once *effects* from at-least-once *delivery* plus transactional *recording* — three boring parts, one honest system.

**What problem it solves (by reference)** — dual-write failures (DB committed/broker crashed = state changed, nobody notified; broker-first ordering = phantom events for rolled-back work) made "write DB + publish event" the most incident-dense two lines in backend code. The pattern's division of labor: Databases 05 owns *why and how it works* (atomicity argument, relay process, idempotent consumers, runnable mechanics); this leaf owns *what the table looks like* (columns, ordering, relay surface, purge) — the schema half the pattern needs and no pattern doc fully specifies. Read Databases 05 first if the pattern is new; read here for the table.

**Modern guidance** — the reading order is load-bearing: pattern-illiterate teams designing outbox tables optimize the wrong thing (payload richness over relay orderability; clever partitioning over purge discipline). Databases 05 first (pattern + mechanics, one leaf), then this leaf (table shape), then relay implementation (your language's worker idioms — consumption side, outside both tracks). Cross-link, don't cross-teach — each leaf owns its half, both halves referenced from both sides.

**Common confusion** — *"outbox needs a message broker to be useful."* The table is useful brokerless (audit log of intent — "what did we mean to publish?" answerable; testing seam — assert recorded intents without brokers; replay source — republish history after consumer outages). Brokers deliver; tables record — recording has standalone value (observability, testability, replayability) even before any relay exists. Design the table first (this leaf); attach the broker when the consumer arrives (relay is an addition, not a prerequisite).

**Performance note** — none specific — outbox write cost (one extra row per business transaction — same-transaction INSERT, microseconds) and relay read cost (indexed unrelayed scan — next promise's partial index) are priced with the table design, not the pattern. Pattern-level performance (relay lag, consumer throughput, broker topology) touches Databases 05–06 (linked, not repeated). Table half here, pattern half there — performance ledgers split at the same boundary, each complete on its side.

**Mentor note** — teach "pattern there, table here" explicitly (juniors sent to Databases 05 first return with pattern fluency, then design tables that serve relays they've understood — order matters; table-first learners optimize payloads while misunderstanding delivery). Reading-order discipline ("05/3.1, then 06/2.1 here, then implement") is curriculum sequencing doing its job — sequences teach, piles confuse. Assign the order; check the sequence; review the table last.

## 2. Design the relay surface (ordered cursors, payload contracts, relayed-at marking)

**Definition** — the relay surface: the table shape + access pattern the relay process consumes — monotonic sequence (BIGINT identity — global order, gap-tolerant: relays handle gaps from rolled-back transactions, never assume contiguity), payload contract (JSONB with event name + versioned schema — consumers parse by (event, version), never by hope), relayed-at marking (NULL = pending — partial index serves the relay scan; timestamp when published — lag measurable per row), aggregate identity (aggregate + aggregate_id — ordering per aggregate where needed, debugging per entity always).

**What problem it solves** — the unrelayable outbox: UUID PKs without order (relay can't sequence — "which rows are new?" answered by timestamps with collision/precision pathologies); TEXT payloads without contracts (consumers parsing free-form strings — new producers breaking old consumers silently); no relayed marking (republish-everything on relay restart — duplicates flooding, or published-flags without timestamps — lag unmeasurable); missing aggregate identity ("which entity's events lag?" — unanswerable, debugging by full-table scan). Relay surfaces designed for writers (convenient INSERTs) instead of relays (ordered scans + contracts + lag math) — the table serves its hardest reader last. Design relay-first: the relay is the table's dominant reader by frequency and fragility.

**Modern guidance** — the table contract (verified shapes on PostgreSQL 16.15): `seq BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` (monotonic cursor — relay tracks max-relayed-seq, crash-resumes without gaps-or-duplicates ambiguity... duplicates still possible (at-least-once) — cursor prevents *re-scans*, idempotency prevents *re-effects*); `WHERE relayed_at IS NULL` partial index on (seq) (relay scan serves pending only — table grows, scan stays small); payload `(event TEXT, event_version INT, payload JSONB)` (contract per event+version — consumers switch on the pair, producers version bumps); `aggregate, aggregate_id` (per-entity ordering + debugging — "lag for order-7?" answerable); `occurred_at` (business time — lag = now - occurred_at per row, dashboarded). Relay claim pattern: `SELECT ... WHERE relayed_at IS NULL ORDER BY seq LIMIT n FOR UPDATE SKIP LOCKED` (concurrent relays without coordination — verified below; lock mechanics touch Databases 05).

```sql
-- GOOD: the relay surface — ordered, contracted, lag-measurable (verified PG 16.15).
CREATE TABLE outbox (
  seq          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- relay cursor (monotonic)
  aggregate    TEXT NOT NULL,          -- 'order' (per-entity debugging + ordering)
  aggregate_id TEXT NOT NULL,          -- 'o1'
  event        TEXT NOT NULL,          -- 'paid' (consumers switch on event+version)
  event_version INT NOT NULL DEFAULT 1,
  payload      JSONB NOT NULL,         -- contracted per event+version
  occurred_at  TIMESTAMPTZ NOT NULL DEFAULT now(),   -- lag math: now - occurred_at
  relayed_at   TIMESTAMPTZ             -- NULL = pending (partial index serves relay)
);
CREATE INDEX outbox_relay_idx ON outbox (seq) WHERE relayed_at IS NULL;
-- Relay claim (concurrent relays, no coordination — verified):
-- SELECT seq FROM outbox WHERE relayed_at IS NULL ORDER BY seq LIMIT 100 FOR UPDATE SKIP LOCKED;
-- Publish batch → UPDATE outbox SET relayed_at = now() WHERE seq = ANY($1);
```

```sql
-- BAD: the writer-designed outbox — convenient INSERTs, unservable relay.
CREATE TABLE outbox_bad (
  id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),  -- unordered: "what's new?" unanswerable
  payload TEXT NOT NULL,                               -- free-form: consumers parse hopefully
  done    BOOLEAN NOT NULL DEFAULT false               -- published flag: no timestamps (lag
  -- unmeasurable), no aggregate (debugging by scan), no version (consumers switch on vibes).
  -- Relay: full-table scan per poll (no partial index — done=false rows mixed with history);
  -- restart republishes ambiguously (no cursor — gaps vs lag indistinguishable);
  -- consumer breaks on producer changes silently (no contract — hope as integration).
  -- Convenient to write, impossible to relay. Writers served; system failed.
);
```

**Common confusion** — *"gaps in seq (rolled-back transactions) break relay cursors."* Gap-tolerant relays track max-*relayed* (not max-*seen* — rolled-back seqs never relay, cursor advances past published rows only; pending gaps re-polled until published-or-forever-pending — abandoned gaps bounded by polling, never blocking). Alternatively gapless schemes (pgq-style ticket counters — complexity for aesthetics). Gaps are normal (aborted transactions exist); tolerance is one clause (WHERE relayed_at IS NULL — gaps included naturally). Design for gaps; never prevent them (preventing needs serialization — throughput suicide for aesthetics).

**Performance note** — relay economics: pending-scan cost O(unrelayed) via partial index (small while relay keeps up — lag visible as scan growth, self-alarming); claim cost one indexed range + row locks (SKIP LOCKED skips contended rows — concurrent relays scale linearly to relay count); marking cost one UPDATE per batch (batched ANY($1) — single statement per batch, not per row). Relay lag (now - occurred_at of oldest pending — dashboarded, alerted — the outbox's vital sign) decomposes into publish latency + backlog (backlog growing → relay under-provisioned or broker down — distinct responses, same gauge). Gauges, not hopes — relay health measured per row-timestamp.

**Mentor note** — teach "design for the relay" as reader-first modeling (same habit as [Domain 03](<../../../03 Document Modeling for Scale/sections/1. Aggregates and access/1.2. Access patterns drive document shape.md>)'s access-first shaping — dominant reader shapes the table; here the relay is dominant by fragility if not frequency). Juniors designing for writers (convenient INSERT shapes) produce unrelayable tables confidently — redirect with "show me the relay query" (unwritable relay query = undesigned table, sent back). Relay query first, table second — reader-driven design once more, operations edition.

## 3. Purge relayed rows routinely (at-least-once needs at-most-once storage)

**Definition** — outbox retention: relayed rows (relayed_at set, consumed downstream) purge on schedule — retention window (7–30 days typical — replay/debug window, not archive), batched deletes (1.1... [Domain 05 §3.1](<../../../05 Evolution Growth and Partitioning/sections/3. Lifecycle and retention/3.1. Archival and lifecycle tiers.md>)'s purge discipline — chunked, hold-free (outbox rows carry no legal holds normally — verify per domain), certificated), verified below (`DELETE WHERE relayed_at < now() - interval`). Unpurged outboxes grow unboundedly (every business transaction appends — the fastest-growing table by design — unpurged = the table eating the database it serves).

**What problem it solves** — the fossil outbox: relayed rows retained "for debugging" indefinitely (table billions of rows — relay scans slowing (partial index still small, but autovacuum choking on dead weight, backups swelling, pg_class groaning); "debugging" unexercised (nobody queried 2-year-old relayed rows — ever); purge attempted eventually as heroic DELETE (locks, bloat, lag — [Domain 05 §3.1](<../../../05 Evolution Growth and Partitioning/sections/3. Lifecycle and retention/3.1. Archival and lifecycle tiers.md>)'s heroic-purge incident, outbox edition). Retention windows bound all three (storage proportional to window × rate — priced; purges routine (small, frequent, boring); debugging served within window (recent rows queryable — old rows' questions answered by consumer-side logs, not the outbox).

**Modern guidance** — the retention contract (recorded beside the table): *window* (relayed rows kept N days — replay/debug needs, sized from incident history — "when did we last need >7-day-old relayed rows?" — answer sets the window); *purge job* (daily batch DELETE by relayed_at — chunked 10k, off-peak — boring, monitored, alerted on failure); *pre-purge verification* (consumer lag within window — no consumer behind the purge horizon — lag gauge gates the job structurally: purge only rows older than max-consumer-lag + margin); *cold exception* (regulated events archived before purge — [Domain 05 §3.1](<../../../05 Evolution Growth and Partitioning/sections/3. Lifecycle and retention/3.1. Archival and lifecycle tiers.md>) tiers consume the exception — policy cited, not vibed). Unrelayed rows never purge (pending = undelivered promise — age irrelevant, delivery everything — purge predicates always include relayed_at IS NOT NULL... precisely: relayed_at older than window).

```sql
-- GOOD: retention as routine — windowed, gated, boring (verified PG 16.15 shapes).
-- Daily job (lag-gated: purge only behind slowest consumer + margin):
DELETE FROM outbox WHERE relayed_at < now() - interval '7 days';
-- (Chunked 10k with keyset cursor in production — 05/3.1 batching; lag gauge gates:
--  max consumer lag 2 days → 7-day window holds 5-day margin. Margin monitored.)
-- Regulated exception: financial events copy to cold tier pre-purge (policy cited) —
-- then purge identically. Window recorded: ADR-052 (7d: replay needs + incident history).
```

```sql
-- BAD: the fossil outbox — retained everything, purged never, heroically eventually.
-- 4B relayed rows (every transaction since 2023 — "debugging"); relay scans slowing
-- (partial index fine, but autovacuum never finishing — bloat everywhere); backups
-- 80% outbox (restore RTO dominated by replayed history nobody reads); heroic purge
-- attempted Q3 (single DELETE 3B rows — locks, lag, killed at 60% — zero progress).
-- Debugging served never (2-year-old rows queried: zero times, verified post-mortem).
-- Retained for nobody, billed to everybody, purged heroically. Retention unowned, itemized.
```

**Common confusion** — *"purging relayed rows loses the audit trail."* Audit trails live in audit/history tables ([1.1](<../1. History and deletion/1.1. Audit trails that answer questions.md>) — actor-attached, question-driven, retention-policied) — not in delivery infrastructure (outbox rows record *intent to publish*, consumed downstream — downstream systems own effects history; replay needs bound the window). Conflating delivery log with audit trail retains infrastructure exhaust as compliance evidence (unindexed for audit questions, unscoped for retention policy — expensive, noncompliant). Audit in mirrors, delivery in outbox, retention per purpose — three tools, three windows, zero conflation.

**Performance note** — purge economics: windowed purges cost minutes daily (small batches, off-peak — boring); fossil purges cost quarters (heroic deletes, vacuum storms, backup RTO dominated by exhaust). Partial index stays small either way (pending-only — relay performance decoupled from retention — the design's saving grace: relay survives fossilization, everything else doesn't). Storage proportional to window × rate (7d × 1M/day × 500B ≈ 3.5GB — priced once, monitored always). Windows with math beat retention with hope — price per window, monitor per gauge.

**Mentor note** — teach "who reads 30-day-old relayed rows?" (answer: nobody, verified by query logs — the window question that sets retention empirically). Juniors proposing long windows from caution learn measurement beats caution (incident history shows max replay age — window = max + margin, recorded). Caution unmeasured retains forever; caution measured retains optimally. Ask for the oldest replay incident's date — the window follows arithmetically. Evidence-sized windows, never anxiety-sized.
