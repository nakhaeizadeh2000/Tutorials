# 2.2. Job tables and queues in the database

## 1. Claim-work with SKIP LOCKED (concurrent workers without coordination)

**Definition** — the claim pattern: workers fetch pending jobs with `SELECT ... WHERE status='pending' ORDER BY run_after, id LIMIT n FOR UPDATE SKIP LOCKED` (verified below on PostgreSQL 16.15) — each worker locks and skips rows locked by others, so N concurrent workers divide the queue without coordination, without a broker, without duplicates. The partial index `(run_after, id) WHERE status='pending'` serves the claim scan (pending-only — table grows, scan stays small — same shape as the outbox relay index from [2.1](<2.1. Outbox tables designed for relay.md>)).

**What problem it solves** — the broker-or-bust assumption (background work "needs" Redis/RabbitMQ/SQS — new infrastructure, new failure modes, new bills — for workloads the database already serves: scheduled emails, report generation, webhook retries, cleanup jobs at units-to-hundreds per minute). Claim-work tables handle moderate throughput with transactional guarantees brokers can't offer (claim + business-write in one transaction — job claimed and effect recorded atomically; broker acknowledgments are separate-phase and raceable). Start in the database (zero new infrastructure, observable via SQL, backed up with everything else); graduate deliberately (third promise names the exit).

**Modern guidance** — the table contract (verified shapes): `status` with CHECK (`pending/claimed/done/failed` — closed vocabulary, no free-text drift); `run_after` (scheduling + backoff in one column — retries set future run_after, scheduled jobs set it at creation); `attempts` (retry counting — max-attempts policy enforced structurally or by worker convention, recorded); coherence CHECK (`(status='claimed') = (claimed_by IS NOT NULL)` — verified rejection below: claimed-without-claimer impossible); claim index partial on pending (relay-scan economics — pending set small while workers keep up); claim-then-work in one transaction per batch (SELECT FOR UPDATE SKIP LOCKED + UPDATE to claimed — atomic handoff, crash-safe: uncommitted claims roll back to pending automatically).

```sql
-- GOOD: the queue in a table — claimed concurrently, ordered fairly (verified PG 16.15).
CREATE TABLE jobs (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  kind       TEXT NOT NULL,          -- 'email', 'report', 'webhook' (workers switch on kind)
  payload    JSONB NOT NULL,         -- contracted per kind (like outbox events — 2.1)
  status     TEXT NOT NULL DEFAULT 'pending'
             CHECK (status IN ('pending', 'claimed', 'done', 'failed')),
  attempts   INT NOT NULL DEFAULT 0,
  run_after  TIMESTAMPTZ NOT NULL DEFAULT now(),   -- schedule + backoff in one column
  claimed_by TEXT,
  claimed_at TIMESTAMPTZ,
  CONSTRAINT jobs_claim_coherent CHECK ((status = 'claimed') = (claimed_by IS NOT NULL))
);
CREATE INDEX jobs_claim_idx ON jobs (run_after, id) WHERE status = 'pending';
-- Claim (N workers, no coordination — verified): SELECT id FROM jobs
-- WHERE status='pending' AND run_after <= now() ORDER BY run_after, id LIMIT 1
-- FOR UPDATE SKIP LOCKED; → UPDATE jobs SET status='claimed', claimed_by='w1',
-- claimed_at=now(), attempts=attempts+1 WHERE id=$1; (same transaction — atomic handoff)
-- Incoherent claim rejected structurally (verified): status='claimed', claimed_by NULL → ERROR.
```

```sql
-- BAD: status strings without machinery — a jobs table cosplaying as a queue.
CREATE TABLE jobs_bad (
  id      BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  payload TEXT NOT NULL,
  status  TEXT NOT NULL DEFAULT 'pending',   -- free text: 'Pending', 'PENDING', 'in-progress'
  -- (no CHECK — vocabulary drifts per writer); no run_after (scheduling = polling sleep
  -- in code); no attempts (retries infinite or absent — poison jobs loop forever);
  -- no claim index (workers full-scan per poll); claim by SELECT-then-UPDATE (race:
  -- two workers claim one job — double-send, double-charge — the race SKIP LOCKED closes).
  -- A table named queue with none of queue semantics. Hope as infrastructure.
);
```

**Common confusion** — *"SKIP LOCKED loses jobs (skipped rows never run)." Skipped rows are locked, not lost (locks held by live workers doing the work — skipped this poll, completed by the holder; crashed holders roll back — rows return to pending automatically — crash-safety by transactionality, the broker-ack race eliminated structurally). Starvation needs pathological lock-holding (worker claiming thousands without committing — batch limits bound it — LIMIT n per claim, commits per batch). Skipped ≠ dropped — skipped means *claimed elsewhere, progressing*; the pending set drains as workers commit. Monitor depth (pending count + oldest pending age — gauges from [4.1](<../4. Mentor checklist/4.1. Operations-modeling checklist mentors insist on.md>)), not skips.

**Performance note** — claim economics: pending-scan O(pending) via partial index (small while workers keep up — depth growth self-alarms via gauges); claim locks per batch (row locks held briefly — workers scale linearly to CPU/connection budget); no broker round trips (local transaction — microseconds vs network milliseconds per claim). Throughput ceiling: single-table claim rate (thousands/minute comfortably — connection-bound, not lock-bound with SKIP LOCKED); beyond → partitioned job tables by kind (parallel claim streams) then brokers (third promise). Measure claim latency (poll-to-claim time) — the queue's vital sign, dashboarded from day one.

**Mentor note** — teach "claim, don't poll-and-pray" (juniors writing SELECT-then-UPDATE learn the race by demonstration: two shells, same pending row, both claim — double-execution visible in seconds — then SKIP LOCKED fixes it observably). Races demonstrated beat races described — the two-shell exercise takes five minutes and vaccinates against check-then-act permanently (the habit transfers to every concurrent mutation: outbox claims, seat bookings, inventory decrements). Demonstrate races; prescribe locking; review for both.

## 2. State machines, not status strings (transitions constrained, retries counted)

**Definition** — the discipline: job status is a *state machine* (pending → claimed → done/failed; failed → pending via retry with backoff; claimed → pending via lease expiry for crashed workers) with legal transitions constrained structurally where cheap (coherence CHECKs — promise 1's shape; valid-transition triggers where strictness pays — `OLD.status/new.status` pair whitelists) and retries counted explicitly (attempts + max_attempts policy + exponential run_after backoff — poison jobs park in failed after N attempts, never loop forever). Strings drift; machines transition — one governed, the other hoped.

**What problem it solves** — the string-status decay trio: *illegal transitions* (pending → done skipping claim — work "completed" never attempted; done → pending resurrections — duplicate effects; failed rows manually flipped without reset attempts — retry counts lying); *infinite poison* (failing job retried forever — error budget burned on deterministic failure, queue head blocked (FIFO) or workers saturated (parallel) — one bad payload DoSing the queue); *orphaned claims* (worker crashes mid-job — claimed_by a corpse, claimed_at aging, job neither progressing nor eligible — invisible stall, discovered by customer complaint). Machines with counters convert all three to structure (illegal = rejected, poison = parked, orphans = expired by lease).

**Modern guidance** — the machine contract: states closed-vocabulary CHECK (four states — additions versioned deliberately, never improvised); transitions guarded (coherence CHECK minimum — claimed ⟺ claimer; transition trigger where strictness justified — whitelist (pending→claimed, claimed→done/failed, failed→pending, claimed→pending-on-expiry) — trigger cost weighed against bug cost: strict on money-moving jobs, coherence-only on idempotent notifications); retries bounded (max_attempts per kind — 5 default, recorded; backoff `run_after = now() + attempts^2 * interval` — exponential, capped; poison parks in failed with error payload retained — dead-letter by status, alerted); leases bounded (claimed rows expire after N minutes without heartbeat — sweeper resets to pending, attempts incremented — crash recovery automatic, invisible stalls impossible by construction).

```sql
-- GOOD: transitions governed, retries bounded, orphans expiring (PostgreSQL 16.15 shapes).
-- Retry with backoff (worker path — attempts counted, schedule pushed):
-- UPDATE jobs SET status='pending', run_after = now() + (attempts * attempts || ' minutes')::interval
-- WHERE id=$1 AND status='failed' AND attempts < 5;  -- bounded: poison parks after 5
-- Lease expiry (sweeper path — crashed workers' jobs return automatically):
-- UPDATE jobs SET status='pending', claimed_by=NULL WHERE status='claimed'
-- AND claimed_at < now() - interval '10 minutes';  -- orphans impossible past lease
-- Dead-letter: status='failed' AND attempts>=5 (alerted, error payload retained — inspected, never looped).
```

```sql
-- BAD: strings with hope — transitions ungoverned, retries unbounded, orphans eternal.
-- UPDATE jobs SET status='done' WHERE id=$1;  -- from any state (pending→done: work unattempted).
-- Retry: UPDATE jobs SET status='pending' WHERE status='failed';  -- attempts uncounted
-- (poison job #4417: failing 6 months, retried 2M times — workers saturated, error budget ash).
-- Crashed worker: claimed rows aging (claimed_by='dead-w3', 2024) — neither progressing
-- nor eligible — stall visible only via customer complaint ("my email never arrived").
-- Strings drift, poison loops, orphans accumulate. Hope as infrastructure, thrice over.
```

**Common confusion** — *"transition triggers are over-engineering."* Trigger strictness is priced per job kind (money-moving: strict whitelist — illegal transitions are correctness incidents; idempotent notifications: coherence CHECK suffices — worst case a duplicate send, idempotency-absorbed). "Over-engineering" describes strictness exceeding bug cost — measure bug cost first (duplicate charge vs duplicate email — orders apart). Calibrate strictness to blast radius: strict where money moves, coherent where duplicates absorb, strings nowhere. Calibration, not maximalism — the engineering judgment interviews probe ([5.1](<../5. Interview QA/5.1. Common interview QA operations modeling.md>)).

**Performance note** — machine economics: transition guards cost trigger/CHECK evaluation per write (microseconds — constant); lease sweeper costs one indexed range UPDATE per sweep interval (pending-expired scan — partial index on (status, claimed_at) keeps it small — sweeps minutely, cheaply); dead-letter retention costs storage per poison job (tiny — alerted, inspected, deleted after postmortem — dead letters are evidence with expiry, not archives). Unbounded retries cost workers (saturation — throughput zero for real work); orphaned claims cost latency infinity (jobs never completing — unbounded tail). Bounded machines: constant overhead, finite tails — the only queue shape with both properties.

**Mentor note** — teach "draw the machine" before "name the statuses" (juniors sketching states as circles with arrows spot missing transitions instantly — "how does claimed become pending on crash?" unanswerable from a status list, obvious from a diagram with a lease edge). State diagrams fit index cards; cards review faster than DDL (review the diagram, approve the machine, then check the DDL implements it). Diagram-first for machines, same as screens-first for documents ([Domain 03](<../../../03 Document Modeling for Scale/sections/1. Aggregates and access/1.2. Access patterns drive document shape.md>)) — pictures before structures, permanently.

## 3. Know when to leave the database (rate, fan-out, and ordering limits — graduate deliberately)

**Definition** — the graduation rule: database queues serve to measured limits — rate (thousands/minute per table — connection- and lock-bound), fan-out (one queue feeding bounded workers — broadcast to thousands of consumers needs pub-sub topology, not polling), ordering (per-key FIFO via claim order — global strict ordering across workers unachievable without serialization killing throughput). Exceeding any limit *by measurement* (gauges trending, not vibes forecasting) triggers graduation: dedicated brokers (SQS/RabbitMQ/Kafka per need — at-least-once + ordering + fan-out properties matched to workload, not fashion), with the table retained as audit/schedule source where useful (jobs recorded in DB, dispatched via broker — belt and suspenders for money-moving work).

**What problem it solves** — the two queue failures: *premature graduation* (brokers adopted for 10 jobs/minute — infrastructure without load: deployment topology, monitoring, dead-letter config, SDK upgrades — all operated for throughput the database serves in its sleep; complexity without customers) and *overdue graduation* (database queue at 50k/minute — connections saturated by polling, lock contention on claim index, relay lag growing unboundedly — "just add workers" adding connections that worsen contention — the queue past its physics, heroics instead of graduation). Limits measured (claim latency, pending depth, lock waits — gauged from day one per promise 1) make graduation scheduled (trigger reached → migrate deliberately) instead of hoped or panicked.

**Modern guidance** — the graduation triggers (recorded beside the table from birth): *rate* (claim latency p99 >Xs or pending depth growing unboundedly at max workers → broker evaluation); *fan-out* (one event → N>100 consumers routinely → pub-sub topology — polling N workers per event is fan-out by accident); *ordering* (global FIFO demanded across parallel workers → broker with partitioning (Kafka-style keyed order) — database FIFO serializes (one claim stream — throughput = 1/claim-latency — the denial of parallelism). Graduate by property needed (ordering → Kafka-like; fan-out → pub-sub; rate → SQS-like work queues — matched, never fashionable). Migration path: dual-publish during cutover (DB + broker — expand/contract from [Domain 05 §1.1](<../../../05 Evolution Growth and Partitioning/sections/1. Schema evolution/1.1. Expand and contract migrations.md>) applies to queues too), drain DB queue, retire pollers — boring, reversible, witnessed.

```sql
-- GOOD: triggers recorded from birth — graduation scheduled, not hoped or panicked.
-- jobs table (email/report/webhook kinds): current 200/min, p99 claim 40ms.
-- Triggers: claim p99 >500ms sustained → evaluate broker; pending depth >100k →
-- partitioned job tables by kind (intermediate step — parallel claim streams, still DB);
-- fan-out need (one event → 500 consumers) → pub-sub directly (polling can't fan out).
-- Current: DB queue correct (200/min ≪ limits). Revisit: quarterly with gauges.
-- Graduation path on file (dual-publish → drain → retire — boring by design).
```

```sql
-- BAD: the unmeasured extremes — broker on day one, or database forever.
-- Day-one Kafka (10 jobs/min — 3 brokers, ZooKeeper/KRaft, schema registry, exactly-once
-- config debates — operated for throughput a cron job serves; complexity without load).
-- Or: database queue at 80k/min (connections 90% polling, claim locks contending, pending
-- depth months-deep — "add workers" worsening contention — physics ignored, heroics
-- scheduled). Premature graduation wastes operations; overdue graduation wastes incidents.
-- Gauges decide; fashions don't. Unmeasured either way is unengineering.
```

**Common confusion** — *"real systems use brokers — DB queues are toys."* Scale defines "real" (thousands/minute sustained is real production for most teams — served well in-DB with transactional guarantees brokers can't offer; millions/minute with fan-out is broker territory — matched deliberately). Dismissing DB queues categorically confuses fashion with physics — physics has gauges (claim latency, depth, lock waits), fashion has slogans ("web-scale"). Gauges hire; slogans posture. Serve current load correctly; graduate on triggers — the only queue philosophy with both properties.

**Performance note** — graduation economics: DB queue marginal cost ≈ zero (existing connections, existing backups, SQL observability — operated already); broker marginal cost = topology + monitoring + SDK + dead-letter ops (fixed cost regardless of throughput — justified past triggers, wasteful before). Intermediate step (partitioned job tables by kind — parallel claim streams, still zero new infrastructure) doubles headroom before brokers — most teams never pass it. Price fixed broker ops against measured DB headroom — graduate when headroom expires on schedule, quarter(s) ahead, never during the spike that proved the need.

**Mentor note** — teach "gauges before brokers" (juniors proposing queues name the three gauges first — claim latency, pending depth, lock waits — then the triggers, then the table; brokers proposed only past triggers with numbers). Gauge-first queue design generalizes (every scaling decision starts instrumented — capacity from [Domain 05 §2.1](<../../../05 Evolution Growth and Partitioning/sections/2. Growth and capacity/2.1. Capacity modeling with measured triggers.md>) applied to queues). Review queue PRs gauge-first ("show me the triggers" — missing triggers fail review structurally). Instrumented proposals; triggered graduations; boring queues — the operations maturity arc in one habit.
