# 1.2. Soft deletes done deliberately

## 1. deleted_at is a lifecycle state (visible, reversible — with a purge path)

**Definition** — soft delete: rows retire via `deleted_at` timestamp (NULL = live) instead of DELETE — reads filter (`WHERE deleted_at IS NULL`), writes revive (clear the stamp), purges hard-delete after a window ([Domain 05 §3.1](<../../../05 Evolution Growth and Partitioning/sections/3. Lifecycle and retention/3.1. Archival and lifecycle tiers.md>)). The stamp is a *lifecycle state* (like status transitions — governed, queried, transitioned deliberately), not a trash flag (invisible, permanent, unowned). States have transitions (delete → restore → purge), owners, and queries; flags have none of these — design states, never flags.

**What problem it solves** — the hard-delete duo it replaces (accidental DELETE unrecoverable without backup surgery — losing interim writes; GDPR "delete my data" executed as hard DELETE destroying history finance/regulatory needs — erasure vs retention conflict unmediated) and the soft-delete duo it disciplines (flag-columns nobody filters — "deleted" rows surfacing in lists, counts, and FK traversals; flags without purge paths — tombstones accumulating forever, tables 40% dead rows, vacuum choking on undead weight). Deliberate soft-delete keeps reversibility (restore path real) with finality scheduled (purge path real) — both designed, neither hoped.

**Modern guidance** — the soft-delete contract per table: (a) *filter discipline* (all live-reads predicate `deleted_at IS NULL` — views for the dominant reads (`active_users` — named, not ad-hoc WHEREs scattered — so the filter lives once); FK traversals consider deleted parents explicitly — RESTRICT vs CASCADE vs SET NULL re-examined with tombstones present ([Domain 04 §1.1](<../../../04 Relationships at Scale/sections/1. Foreign keys at volume/1.1. Foreign keys that survive traffic.md>))); (b) *restore path* (clear stamp + revalidate uniqueness — next promise's partial index makes restore safe); (c) *purge path* (hard DELETE after N days — Domain 05 §3.1 batching + certificates — tombstones have funerals scheduled, not accumulating); (d) *uniqueness story* (next promise — partial unique indexes, decided per table, never defaulted).

```sql
-- GOOD: lifecycle state with filter, restore, and purge paths (verified PG 16.15).
CREATE TABLE users (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email      TEXT NOT NULL,
  deleted_at TIMESTAMPTZ   -- NULL = live; timestamp = retired (when, for retention math)
);
CREATE UNIQUE INDEX users_email_live_uidx ON users (email) WHERE deleted_at IS NULL;
-- Live reads: WHERE deleted_at IS NULL (or active_users view — filter lives once).
-- Restore: UPDATE users SET deleted_at = NULL WHERE id = $1 (partial index revalidates).
-- Purge: hard DELETE WHERE deleted_at < now() - '90 days' (batched, certificated — 05/3.1).
```

```sql
-- BAD: the trash flag — invisible, permanent, unowned.
CREATE TABLE users_bad (
  id      BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email   TEXT UNIQUE NOT NULL,   -- full UNIQUE: deleted emails block reuse forever
  deleted BOOLEAN NOT NULL DEFAULT false   -- flag: no when (retention uncomputable),
  -- no purge path (tombstones forever), filters scattered (half the queries forget
  -- WHERE NOT deleted — dead rows in lists, counts, reports). Restore? UPDATE flag
  -- (revalidates nothing — UNIQUE still held by older tombstones: restore fails
  -- mysteriously). Flag without lifecycle: invisible state, permanent weight.
);
```

**Common confusion** — *"soft-delete means never losing data."* Soft-delete means *reversible within the window* (restore path real for N days) and *purged after* (tombstones die on schedule — storage reclaimed, uniqueness freed, retention honored). "Never lose data" is archival ([Domain 05 §3.1](<../../../05 Evolution Growth and Partitioning/sections/3. Lifecycle and retention/3.1. Archival and lifecycle tiers.md>) — cold tiers, legal holds); soft-delete is operational undo with expiry. Conflating them retains tombstones forever ("just in case" — the dearest two words in storage) or purges live-today rows under archival assumptions. Undo window ≠ archive; stamp ≠ history — three distinct tools (soft-delete, history mirrors from 1.1, cold tiers from 05/3.1), each owned separately.

**Performance note** — tombstone economics: live queries filter tombstones per read (partial index `WHERE deleted_at IS NULL` keeps live access point-fast — full-table scans skip dead weight structurally); tables accrue dead rows between purges (bloat proportional to delete rate × purge interval — purge cadence sized from delete velocity, not calendar comfort); UNIQUE semantics need partial indexes (next promise — full UNIQUEs on soft-deleted tables are restore-breaking bugs, not constraints). Purge cadence is the performance lever (weekly purges keep tombstones <5%; yearly purges keep 40% dead weight — vacuum, backups, and scans all bill the difference).

**Mentor note** — teach "who filters, who purges, who restores?" per soft-deleted table (three roles, three answers — filter owner (view vs convention), purge schedule (job + cadence), restore procedure (documented, tested — unrestored restores are theoretical)). Juniors answering all three design lifecycles; answering one design flags. The trio generalizes (every state machine reviews by transitions-in, transitions-out, and terminal states — lifecycle thinking once more, operations edition).

## 2. Uniqueness survives soft deletion (partial unique indexes — the constraint that outlives the row)

**Definition** — the technique: `CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL` — uniqueness enforced among live rows only (verified above: delete + re-insert same email succeeds). Deleted rows release their uniqueness claims (emails reusable — new account with a recycled address works); restored rows revalidate (conflicting live claimant blocks restore — correct: two live rows can't share it). Full UNIQUE constraints on soft-deleted tables are the bug this replaces (tombstones holding uniqueness hostage — restores failing, reuse blocked, "deleted" data constraining live operations indefinitely).

**What problem it solves** — the tombstone-hostage trio: *reuse blocked* (user deletes account, re-registers — "email taken" by their own tombstone — support ticket, manual purge, bad experience); *restore failing* (admin restores a row whose email a newer row claimed — full UNIQUE rejects — restore path broken exactly when needed); *phantom conflicts* (bulk import colliding with ancient tombstones — thousands of "duplicate" errors against dead rows). Partial unique indexes resolve all three structurally (live-set uniqueness — the only set that matters operationally; tombstones unconstrained — correctly, they're gone).

**Modern guidance** — convert every UNIQUE on a soft-deleted table to partial (`WHERE deleted_at IS NULL`) in the same migration that adds the stamp (same PR — inseparable changes; full UNIQUE + deleted_at is a contradiction shipped). Audit existing tables once (UNIQUE constraints on stamped tables without predicates — each a hostage incident scheduled). Edge cases decided explicitly: *restore-vs-claimant* (newer live row wins — restore rejected with clear error, admin reassigns — policy, not bug); *multi-column uniques* (partial predicates apply identically — `(tenant_id, slug) WHERE deleted_at IS NULL`); *FK targets* (referencing soft-deleted rows — allowed structurally; readers filter — policy per relationship, recorded).

```sql
-- GOOD: live-set uniqueness — tombstones release claims, restores revalidate (verified PG 16.15).
CREATE UNIQUE INDEX users_email_live_uidx ON users (email) WHERE deleted_at IS NULL;
-- Delete row 1 (stamp it) → INSERT same email succeeds (verified above: second INSERT 0 1).
-- Restore row 1 while row 2 lives → UNIQUE violation (correct: one live claimant allowed).
-- Audit query for hostages elsewhere: constraints on stamped tables lacking predicates.
```

```sql
-- BAD: full UNIQUE on stamped tables — tombstones holding live operations hostage.
CREATE TABLE users_bad2 (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email      TEXT UNIQUE NOT NULL,   -- full constraint: tombstones included
  deleted_at TIMESTAMPTZ
);
-- Re-register after delete: "email taken" (by your own tombstone — support ticket).
-- Restore admin action: violates (newer claimant exists — restore path broken).
-- Bulk import: collides with 2019 tombstones (thousands of phantom duplicates).
-- The constraint protects nothing live and obstructs everything attempted. Hostage, itemized.
```

**Common confusion** — *"partial indexes are exotic — avoid cleverness."* Partial unique indexes are standard PostgreSQL (documented, planner-supported, decade-stable — as-of-September-2026 unremarkable), and the alternative (full UNIQUE + tombstones) is objectively broken (three failure modes above, all structural). "Exotic" describes unfamiliarity, not risk — unfamiliarity cures with one code review, hostage incidents recur per tombstone. Standard tool, correct application — cleverness is using the wrong constraint confidently.

**Performance note** — partial indexes are *smaller* than full ones (live rows only — tombstones excluded — index shrinks as deletes accumulate, the rare structure that improves with age) and *faster* for live queries (fewer entries, shallower tree — live lookups point-fast; tombstone-excluded scans skip dead weight structurally). Full UNIQUEs on stamped tables pay full size for hostage semantics — worse on both axes (bigger index, broken restores). Smaller, faster, correct — the trifecta that ends the "exotic" objection permanently.

**Mentor note** — teach the delete-then-reinsert test (verified above — juniors running it watch reuse succeed and *feel* partial uniqueness work; the two INSERTs with one UPDATE between demonstrate more than any definition). Make it the soft-delete acceptance test (every stamped table ships with the test: insert → delete → reinsert same key → succeeds; restore-while-claimed → fails clearly). Tests encode the semantics; semantics survive hires. Acceptance-test the lifecycle, not just the columns.

## 3. Soft-delete is not archival (operational undo vs lifecycle tier — different tools, owners, rhythms)

**Definition** — the separation: soft-delete serves *operational undo* (days-to-weeks reversibility for user/admin actions — owned by product engineering, transitions fast, purge scheduled); archival serves *lifecycle obligation* (months-to-years retention for legal/tax/history — owned by data/compliance, tiers by temperature, purges certificated — [Domain 05 §3.1](<../../../05 Evolution Growth and Partitioning/sections/3. Lifecycle and retention/3.1. Archival and lifecycle tiers.md>)). Undo windows measure in days (restore path hot, support-operated); retention windows measure in years (cold tiers, legal-signed). Different horizons, different owners, different rhythms — one stamp cannot serve both without corrupting both.

**What problem it solves** — the conflation duo: *tombstones as archive* ("we keep deleted rows forever — that's our history" — tombstones without audit metadata (no actor, no reason, no version chain — 1.1's questions unanswerable), without retention policy (forever by default — priced nowhere), without tiering (hot-table bloat — performance billed daily for legal value); and *archive as undo* ("restore from cold storage" for yesterday's accidental delete — hours-long restore for a one-row undo — support tickets aging while dumps download). Undo needs speed (live-table stamp, instant restore); archive needs durability (cold tiers, legal holds, certificates). Speed and durability live in different structures — conflated, each fails the other's requirements.

**Modern guidance** — the division per deleted row (both, sequenced): *undo window* (deleted_at stamped — restorable instantly by support — days-to-weeks per product policy — purge job hard-deletes after); *archival decision at purge time* (purge job consults retention: obligation → cold tier first (copy, verify, certificate), then hard-delete; no obligation → hard-delete with certificate). Tombstones never *are* the archive (no actor metadata, no tiering, no legal holds — three absences disqualifying); archives never *serve* undo (restore latency disqualifying). Sequence: stamp → (restore? done) → purge-window → (obligation? archive : delete) → certificate. Five states, two owners (product for undo, data/compliance for archive), one purge job consulting both.

```sql
-- GOOD: undo then archive-or-delete — sequenced, owned, certificated.
-- Day 0: UPDATE users SET deleted_at = now() WHERE id = $1;  (undo window opens — support restores)
-- Day 30 (purge job): obligation? → copy to cold tier (verify counts) → hard DELETE + certificate.
--                      no obligation? → hard DELETE + certificate (lighter).
-- Support restore (day 5): UPDATE users SET deleted_at = NULL WHERE id = $1 (partial index revalidates).
-- Audit history (1.1 mirror): every transition recorded (stamp, restore, purge — actors attached).
```

```sql
-- BAD: the eternal tombstone — undo without expiry, archive without structure.
-- UPDATE users SET deleted = true WHERE id = $1;  -- then: nothing. No purge job
-- (tombstones accumulate — 40% dead weight by year 3). No archive decision (legal
-- history in hot tables — discovery scans production; retention unpriced). No actor
-- metadata (who deleted? when? why? — unanswerable). Restore path: UPDATE flag
-- (works — the one functioning piece, preserving dead weight for its sake).
-- Undo permanent, archive absent, performance billed daily. Conflation, itemized.
```

**Common confusion** — *"deleted data must be kept for legal reasons — so never purge."* Legal holds preserve *specific* data under *specific* matters (scoped, signed, released — [Domain 05 §3.1](<../../../05 Evolution Growth and Partitioning/sections/3. Lifecycle and retention/3.1. Archival and lifecycle tiers.md>)'s hold table) — never "everything forever just in case" (unscoped retention is discovery liability, not compliance — opposing counsel reads your tombstones too). Purge *through* holds (jobs consult hold table — scoped windows survive, everything else dies on schedule). "Legal says keep" names a scope and signer, or it's anxiety wearing a suit — ask for both, purge the rest.

**Performance note** — separation economics: undo windows cost tombstone weight briefly (days-to-weeks of dead rows — bounded, purged); eternal tombstones cost permanently (40% tables — vacuum/backups/scans billing dead weight forever; partial indexes shrinking helpfully but heap still bloated). Archival costs cold pennies (object storage — priced per GB, retrieved yearly-or-never); hot-tombstone "archival" costs RAM-priced storage daily. Undo brief, archive cold, purge scheduled — each horizon priced in its tier, total minimal. Conflation prices everything at hot-tier rates indefinitely — the dearest lifecycle failure, billed monthly.

**Mentor note** — teach "undo or archive?" per deleted row (juniors classifying restores-vs-obligations place every deletion correctly — support-ticket restores are undo; tax-year records are archive; most rows are neither (purge on schedule)). The classification question generalizes (every retained byte answers "for whom, until when, at what tier?" — lifecycle thinking once more, operations edition). Review deletions by classification (undo window? obligation? neither → purge date?) — unclassified deletions default to purge-scheduled, never forever.
