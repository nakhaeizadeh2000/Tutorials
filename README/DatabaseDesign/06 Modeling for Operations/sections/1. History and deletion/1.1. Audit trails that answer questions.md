# 1.1. Audit trails that answer questions

## 1. History tables mirror entities (who changed what when — append-only)

**Definition** — a history table is an append-only mirror of an entity table plus change metadata (changed_by, changed_at, operation) — every INSERT/UPDATE/DELETE on the entity appends a version row, typically via trigger. The live table answers "what is true now"; the history table answers "what was true then, who changed it, and in what order." History is written by the database (triggers fire regardless of writer — application, console, backfill), not by application goodwill.

**What problem it solves / history** — the unanswerable incident: "customer's balance changed unexpectedly — who, when, from what?" Without history: application logs sampled (maybe), backups diffed (hourly granularity, painful), guilty writer unknown (five services touch balances). With history: one query (all versions of row X ordered — actor, timestamp, before/after). Pre-trigger eras faked this with application audit calls (forgotten on new writers, bypassed by consoles, raced under concurrency); database triggers close every path structurally — the writer cannot opt out because the writer doesn't participate.

**Modern guidance** — mirror per audited entity (history table per entity, not one global audit log — per-entity mirrors query naturally: "history of account X" is one indexed lookup; global logs need filtering per question); capture via AFTER ROW triggers (verified below — INSERT/UPDATE/DELETE all covered, OLD+NEW both available); include actor + timestamp + operation on every row (changed_by from session context — `SET app.user_id` plumbed per request, current_user otherwise — anonymous actors are audit holes, close them); history tables append-only by convention + REVOKE (no UPDATE/DELETE grants for application roles — immutability enforced, not hoped). Audit what regulators, support, and incident response ask about (money, identity, permissions, configuration) — not everything (audit-all is write amplification without readers — next promise scopes it).

```sql
-- GOOD: history by trigger — every writer covered, no opt-out (verified PG 16.15).
CREATE TABLE accounts (
  id      BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  balance NUMERIC(12, 2) NOT NULL
);

CREATE TABLE accounts_history (
  hid        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  id         BIGINT NOT NULL,   -- the entity row versioned (indexed below)
  balance    NUMERIC(12, 2) NOT NULL,
  changed_by TEXT NOT NULL,     -- actor: SET app.user_id per request (else current_user)
  changed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  op         CHAR(1) NOT NULL   -- I/U/D (first letter of TG_OP)
);
CREATE INDEX accounts_history_id_idx ON accounts_history (id, changed_at);

CREATE OR REPLACE FUNCTION audit_accounts() RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO accounts_history (id, balance, changed_by, op)
  VALUES (COALESCE(NEW.id, OLD.id), COALESCE(NEW.balance, OLD.balance),
          current_setting('app.user_id', true), substring(TG_OP, 1, 1));
  RETURN COALESCE(NEW, OLD);
END $$;

CREATE TRIGGER accounts_trg AFTER INSERT OR UPDATE OR DELETE ON accounts
  FOR EACH ROW EXECUTE FUNCTION audit_accounts();
-- "Balance history of account 7": SELECT * FROM accounts_history WHERE id = 7 ORDER BY hid;
-- Backfills, consoles, admin scripts: all trigger, all recorded. No exceptions exist.
```

```sql
-- BAD: application audit calls — coverage by convention, holes by construction.
-- app.updateBalance(id, amount); audit.log("balance changed", id);  -- two calls:
-- new writer forgets the second (coverage decays per hire); console UPDATE bypasses
-- entirely (no application involved); concurrent updates interleave logs ambiguously
-- (ordering by log timestamp ≠ commit order — history lies about sequence).
-- "Who changed it?" → shrug + log-grep + backup-diff archaeology. Coverage hoped, holes certain.
```

**Common confusion** — *"triggers are hidden logic — application code is clearer."* Audit triggers are *infrastructure*, not business logic (they record, never decide — no branching on values, no side effects beyond the history row). Hidden-business-logic (price calculations in triggers — genuinely bad) and visible-infrastructure (audit capture — genuinely good) differ in kind: one decides silently, the other records universally. Judge triggers by what they do (record vs decide), not where they live — blanket trigger bans trade universal coverage for visible holes.

**Performance note** — trigger audit costs one extra row-write per mutation (heap + index maintenance on the history table — roughly doubles write cost for audited tables; history indexes sized for entity+time lookups, not global scans). Scope controls cost (audit money/identity/permissions/config — high-value entities; skip telemetry/counters/caches — high-volume, low-question). History tables grow monotonically (write-only — partition by time from birth ([Domain 05 §2.2](<../../../05 Evolution Growth and Partitioning/sections/2. Growth and capacity/2.2. Partitioning keys that prune.md>) applies: monthly pieces, DETACH to warm per retention) — unpartitioned history becomes the unvacuumable giant within a year.

**Mentor note** — teach "which tables would you subpoena?" (juniors listing money/identity/permissions/config discover audit scope themselves — the question converts vague "audit important things" to concrete table lists). Then ask "who writes to them besides the app?" (backfills, consoles, jobs — the trigger's justification in one question). Two questions, audit scope + mechanism decided — juniors design coverage completely on the first try thereafter.

## 2. Effective dating for state over time (valid-from/valid-to ranges — history without triggers)

**Definition** — effective dating (slowly-changing-dimension type 2, in warehouse vocabulary): state rows carry validity ranges (`valid_from`, `valid_to` — NULL valid_to = current) instead of mutating in place — changes close the old row (set valid_to) and open a new one. Point-in-time queries become range predicates (`WHERE $t BETWEEN valid_from AND COALESCE(valid_to, 'infinity')`); full history is the table itself (no mirror needed); corrections are new rows (never UPDATEs — the past is immutable, superseded not rewritten).

**What problem it solves** — the trigger-history gap for *state semantics*: trigger mirrors answer "what changed" (row versions) but not "what was effective" cleanly (a price entered today effective next quarter — changed_at ≠ valid_from; backdated corrections — history order ≠ effective order). Effective dating models validity as data (ranges queryable, overlapping ranges constrainable via exclusion — the no-double-truth guarantee triggers can't express). Slowly-changing reference data (prices, tax rules, tiers, contracts, org assignments) needs effective ranges; trigger history records system events. Different questions, different shapes — validity vs occurrence, both legitimate, rarely interchangeable.

**Modern guidance** — choose per question asked: "what did the system record, in what order?" → trigger history (promise 1 — occurrence-ordered, writer-covering); "what was true for business purposes at time T?" → effective dating (validity-ordered, queryable per instant). Effective-date mechanics: close-then-open in one transaction (UPDATE old SET valid_to + INSERT new — atomic, never half-dated); exclusion constraint preventing overlaps (`EXCLUDE USING gist (entity WITH =, daterange(valid_from, valid_to) WITH &&)` — double-truth impossible structurally — Databases 02 mechanics); current-row view (`WHERE valid_to IS NULL` — convenience, indexed partial). Corrections as new rows with backdated ranges (past superseded, never mutated — audit reads both versions with their effective spans).

```sql
-- GOOD: validity as data — point-in-time queries, overlap-proof (PostgreSQL 16.15 shapes).
CREATE TABLE prices (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  sku        TEXT NOT NULL,
  price      NUMERIC(10, 2) NOT NULL,
  valid_from DATE NOT NULL,
  valid_to   DATE,   -- NULL = currently effective
  EXCLUDE USING gist (sku WITH =, daterange(valid_from, COALESCE(valid_to, 'infinity')) WITH &&)
  -- double-truth impossible: no two rows same sku with overlapping validity. Structural.
);
-- "Price of X on 2025-03-15": WHERE sku=$1 AND daterange(valid_from, COALESCE(valid_to,'infinity')) @> DATE '2025-03-15';
-- Change: close old (SET valid_to) + open new — one transaction, history preserved, past immutable.
```

```sql
-- BAD: mutation with a timestamp column — history overwritten, validity unqueryable.
CREATE TABLE prices_bad (
  sku        TEXT PRIMARY KEY,
  price      NUMERIC(10, 2) NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()   -- "history": the latest write wins,
  -- previous prices gone (overwritten — Q1 revenue unexplainable); future prices
  -- unrepresentable (effective-next-quarter needs a row that lies until then);
  -- backdated corrections rewrite the past (audit reads fiction). One row per truth
  -- is one truth total — history requires rows plural, validity requires ranges.
);
```

**Common confusion** — *effective dating versus trigger history: pick one?* Complementary, frequently coexisting: effective-dated tables *also* get trigger mirrors where occurrence-order matters (who entered the backdated correction, and when — validity says what was effective, history says who recorded it). Validity answers business-time questions; triggers answer system-time questions; bitemporal designs name both explicitly (valid-time + transaction-time — vocabulary for the interview, procedure above for the work). Pick per question; combine where both questions are asked (prices: both — money always deserves both).

**Performance note** — range predicates need GiST (exclusion + `@>` containment queries index via GiST — B-trees serve equality on current rows; historical range scans need the range index — size it per query pattern). Current-row partial index (`WHERE valid_to IS NULL` — small, hot — the dominant operational read stays point-fast while history stays queryable). History growth is append-only (closed rows accumulate — partition by valid_from range yearly — same lifecycle as trigger history, same [Domain 05](<../../../05 Evolution Growth and Partitioning/sections/2. Growth and capacity/2.2. Partitioning keys that prune.md>) procedures).

**Mentor note** — teach "valid-time vs transaction-time" as vocabulary with the two shapes attached (effective ranges vs trigger mirrors — juniors naming both times place every history requirement correctly on first hearing). The bitemporal word earns interview marks; the shape selection earns production correctness — teach the word *through* the shapes (validity question → ranges; occurrence question → triggers), never as definition-first. Questions first, vocabulary as their names — the track's standing pedagogy.

## 3. Audit for questions, not compliance theater (design from the question list)

**Definition** — the scoping rule: audit tables exist for enumerated questions ("which support agent refunded order X?", "what was the approved limit before change Y?", "who disabled the flag during the incident?") — each audited entity traces to 1+ questions, each question traces to readers (support, finance, incident response, regulators). Unaudited entities need no justification (default: unaudited); audited entities need questions (no question → no mirror — "might need it" is compliance theater with write-amplification billing).

**What problem it solves** — the two audit failures: *audit-everything* (mirrors on all tables including telemetry/counters/sessions — write load doubled system-wide, history storage dwarfing live data, zero readers for 90% of mirrors — cost without questions) and *audit-nothing-until-subpoena* (incident/regulatory/audit request arriving at unmirrored tables — reconstruct-from-backups archaeology under deadline, answers approximate, credibility damaged). Question-driven scoping lands between: audited where questions exist (money, identity, permissions, config, contracts), unaudited where none do (counters, caches, telemetry, sessions) — each decision recorded with its questions, revisited when questions change (new regulation → new mirrors, phased like any migration — [Domain 05 §1.1](<../../../05 Evolution Growth and Partitioning/sections/1. Schema evolution/1.1. Expand and contract migrations.md>)).

**Modern guidance** — the audit register (one row per audited entity): *entity, questions (numbered, with readers), mechanism (trigger mirror vs effective dating vs both), retention (history kept how long — [Domain 05 §3.1](<../../../05 Evolution Growth and Partitioning/sections/3. Lifecycle and retention/3.1. Archival and lifecycle tiers.md>) consumes this), owner*. Review triggers: new entity with money/identity/permissions/config semantics → audit question asked automatically; new regulation → register swept for gaps; yearly audit of the audit (mirrors unread in 12 months → candidate for removal — audit has its own lifecycle, priced like everything else). Readers named per question (support dashboard queries history how? — unqueried mirrors are write-only memory, candidate removal regardless of age).

```sql
-- GOOD: the audit register — questions, mechanisms, retention, owners (excerpt).
-- accounts: Q1 "balance disputes" (support reads history by id); Q2 "fraud review"
--   (risk scans changed_by patterns). Mechanism: trigger mirror (occurrence-ordered).
--   Retention: 7yr (tax basis cited, CFO signed). Owner: ledger team.
-- prices: Q3 "historical revenue explainability" (finance point-in-time). Mechanism:
--   effective dating (validity-ordered) + trigger mirror (entry-order). Retention: 10yr.
-- telemetry_events: NO questions → unaudited (stated, dated — revisit on regulation).
```

```sql
-- BAD: audit by anxiety — mirrors everywhere, questions nowhere.
-- 47 history tables (every entity mirrored "just in case" — write load +85% fleet-wide,
-- history storage 3× live data, vacuum struggling on append-only giants).
-- Readers: none named (support unaware mirrors exist; queries written ad hoc per incident,
-- each reinventing "history of X" SQL). Yearly cost: six figures in storage + write
-- overhead. Questions answerable in theory, asked never in practice. Theater with billing.
```

**Common confusion** — *"regulations require auditing everything."* Regulations require answering *specific* questions (transaction records, access logs, consent trails, data-processing registers — enumerated per framework, scoped per article). "Audit everything" over-collects (GDPR data-minimization *violated* by indiscriminate history — the regulation cited for auditing forbids the over-collection done in its name). Read the articles, enumerate their questions, mirror those entities — compliance is question-driven by law, not anxiety-driven by audit. Scope from the text, never from fear.

**Performance note** — audit scoping is write-performance policy (mirrors double audited-table write cost — scoping decides *which* tables pay; unscoped audit-everything taxes the fleet's hottest tables equally with its coldest). Retention bounds history growth (7yr partitions DETACHed per [Domain 05](<../../../05 Evolution Growth and Partitioning/sections/2. Growth and capacity/2.2. Partitioning keys that prune.md>) — mirrors partitioned from birth, never retrofitted). Reader queries stay point-shaped (entity+time indexes — history read occasionally, written constantly — index for reads, tolerate writes). Price audit per entity (write ×2 + storage × history) — the register carries costs beside questions, ledger complete.

**Mentor note** — teach "name the reader" per audit proposal (juniors proposing mirrors name who queries them, how, how often — unnamed readers mean unasked questions, unasked questions mean theater). The reader test kills more unjustified mirrors than any cost argument (costs debated; absent readers indefensible). Review audit PRs reader-first ("who reads this history?" — silence fails review), mechanism second, retention third. Readers justify mirrors; mirrors serve readers; theater serves neither.
