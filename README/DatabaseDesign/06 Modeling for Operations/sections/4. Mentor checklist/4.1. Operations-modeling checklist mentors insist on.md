# 4.1. Operations-modeling checklist mentors insist on

## 1. Every destructive path is reversible (soft windows, audit coverage, purge certificates)

**Definition** — the review's first pass over destructive operations: for each delete/purge/drop path in the PR, the author states reversibility (soft window with restore procedure? backup coverage with tested RTO? audit mirror recording transitions? purge certificate proving compliance?) — irreversible-by-default paths fail review structurally. Destruction without undo is data loss scheduled; destruction with designed reversibility is operations. The checklist asks per path, not per table — paths differ within tables (user-requested erasure vs retention purge vs cascade side-effect — three reversibilities, three answers).

**What problem it solves** — irreversible-by-default merges (hard DELETE endpoints without soft windows — support unable to restore yesterday's accident; purge jobs without certificates — compliance unprovable; cascade policies nobody traced to tombstones — [Domain 04 §1.1](<../../../04 Relationships at Scale/sections/1. Foreign keys at volume/1.1. Foreign keys that survive traffic.md>)'s blast radius meeting no undo). Each merges calmly (code correct, tests green — destruction untested by definition, reversibility unasked by habit) and fails irreversibly (the failure mode from which no rollback exists — restore-from-backup losing interim writes, or worse, unrestorable). Reversibility review converts "can delete" (capability) to "can undelete" (operations) before merge — the only moment the question is cheap.

**Modern guidance** — the reversibility lines per destructive path: soft window stated (deleted_at + restore procedure + purge date — [1.2](<../1. History and deletion/1.2. Soft deletes done deliberately.md>) — or explicit "no window because X," signed); audit coverage named (trigger mirror recording transitions with actors — [1.1](<../1. History and deletion/1.1. Audit trails that answer questions.md>) — or explicit gap with owner); purge certificate planned (counts, windows, holds, signer — [Domain 05 §3.1](<../../../05 Evolution Growth and Partitioning/sections/3. Lifecycle and retention/3.1. Archival and lifecycle tiers.md>) — or regulatory exception cited); cascade traced (dependent tombstones/purges enumerated — Domain 04 policies re-examined with deletion present). Missing line → request changes; explicit "none because X, signed Y" passes (stated absence with owner beats unstated absence always).

```sql
-- GOOD: the reversibility review artifact — every path undoable or signed-irreversible.
-- Path: user account deletion. Soft window: deleted_at + 30d restore (support-operated) ✓.
-- Audit: accounts_history mirror records stamp/restore/purge with actors ✓.
-- Purge: day-30 batch, hold-checked, certificated (05/3.1) ✓. Cascades: orders RESTRICT
-- (history preserved — erasure anonymizes instead — policy cited) ✓.
-- Irreversible exception: none (all paths reversible or signed). Verdict: approve destruction.
```

```sql
-- BAD: the capability review — deletion possible, undo unasked.
-- Path: "DELETE /users/:id → hard delete." (Soft window? Unasked — support restores via
-- backup surgery (hours, interim-write loss). Audit? Unasked — who deleted whom when:
-- application logs, maybe, sampled. Purge certificate? Unasked — GDPR proof: absence
-- presented as evidence. Cascades? Unasked — orders cascade-deleted with accounts
-- (history destroyed with the actor — finance reconciles against void).)
-- Capability approved; operations absent; irreversibility scheduled. Review covered code;
-- production grades undo. Different subjects — the review chose wrong.
```

**Common confusion** — *"reversibility review slows down deletes."* Reversible deletes ship at identical velocity (soft window + audit + purge path designed once per table, reused per delete — the design amortizes to zero marginal cost); irreversible deletes ship incidents (backup restores, compliance findings, support escalations — quarters of drag per event). "Slows down" counts design minutes while ignoring incident quarters — the full ledger favors reversibility by orders of magnitude. Fast deletes of unrecoverable data are fast borrowing against future velocity — debt with legal interest.

**Performance note** — reversibility review is upstream performance work (same argument as every checklist leaf in this track, sixth restatement): soft windows cost tombstone weight briefly (bounded, purged — 1.2's economics); audit mirrors cost write ×2 on scoped tables (1.1's ledger); purge certificates cost rows (trivial). Unreviewed destruction costs backup RTO (hours + interim loss), vacuum storms (heroic purges), and compliance fines (priced by regulators). Transitional costs amortize at purge; incident costs compound per event. Design undo; bill rarely.

**Mentor note** — automate the checkable half (CI: DELETE endpoints without soft-window annotation flagged; purge jobs without certificate writes flagged; stamped tables without partial unique indexes flagged — linters for lifecycle, same as 05/4.1's migration linters), review the judgment half (window lengths, audit scope, exception signatures). Juniors learn fastest from instant automation feedback (red build: "destructive path without reversibility statement") plus human exception discussion. Machines check presence; mentors check proportion — split accordingly, sixth domain running, permanent value.

Audit trails that answer questions.md>); purge certificates in [Domain 05 §3.1](<../../../05 Evolution Growth and Partitioning/sections/3. Lifecycle and retention/3.1. ## 2. Every async handoff is observable (outbox lag, queue depth, relay health — gauges, not hopes)

**Definition** — the review's second pass over asynchronous paths (outbox relays, job workers, scheduled purges, flag syncs): each handoff arrives with its gauges (lag, depth, age, error rate — dashboarded), its alerts (thresholds with owners — firing to humans, not dashboards), and its runbook pointer (lag growing → procedure X; depth exploding → procedure Y). Ungauged handoffs fail review structurally — "the relay runs every minute" describes schedule, not health; health is measured (lag now? depth now? errors now?) or unknown. Unknown async paths are outages queued.

**What problem it solves** — silent-stall merges (outbox relay crashed Tuesday — discovered Friday via customer complaints ("my order never shipped") — lag unmeasured, alerts absent, runbook nonexistent); depth-blind queues (pending depth months-deep — workers saturated long before anyone looked — gauges would have fired at 10× normal, nobody defined normal); unowned relays (relay process running on a forgotten VM — owner departed, restarts manual, monitoring never configured — infrastructure by accident). Each merges working (relay runs, workers poll — green at deploy) and decays invisibly (no gauges → no alerts → no response → incident-by-customer). Observability review converts decay to signal before customers do.

**Modern guidance** — the observability lines per handoff: gauges named (outbox: oldest-unrelayed lag + pending count; jobs: pending depth + oldest-pending age + failed count; purges: last-run timestamp + rows processed; flag syncs: last-sync + staleness) — all dashboarded from birth; alerts set (lag >X → page owner; depth >Y → ticket queue; age >Z → escalate — thresholds from capacity math ([Domain 05 §2.1](<../../../05 Evolution Growth and Partitioning/sections/2. Growth and capacity/2.1. Capacity modeling with measured triggers.md>)), not round numbers); runbooks pointed (lag procedure, depth procedure, dead-letter procedure — linked, rehearsed or referenced); ownership assigned (relay owner, queue owner — humans paged, teams reviewing). Missing gauge → request changes; gauge without alert → request alert; alert without runbook → request runbook. Chain complete or merge blocked.

```sql
-- GOOD: the observability review artifact — gauges, alerts, runbooks, owners.
-- Outbox relay: lag gauge (oldest unrelayed occurred_at — alert >5min, owner platform,
-- runbook: relay-restart + broker-check linked). Jobs: depth + oldest-age gauges
-- (alert depth >10k / age >30min, owner workers team, runbook: scale-workers + poison-check).
-- Purge: last-run + rows gauges (alert >26h since run, owner data, runbook: manual-run).
-- Verdict: handoffs observable — approve async paths.
```

```sql
-- BAD: the schedule review — cadence stated, health unknown.
-- "Relay runs every minute (cron)." (Lag now? Unmeasured — crashed Tuesday, silent till
-- Friday. Depth? Ungauged — months-deep before discovery. Alerts? Absent — customers
-- alerted us. Runbook? Nonexistent — Friday's fix improvised under pressure.)
-- "Workers poll jobs." (Poison jobs? Uncounted — #4417 looping since spring. Orphaned
-- claims? Unaged — dead-w3's jobs pending eternally.) Cadence approved; health unknown;
-- incidents queued. Schedules aren't observability — gauges are.
```

**Common confusion** — *"monitoring is ops' job after merge."* Gauges designed post-merge measure what exists (retrofitted metrics on uninstrumented paths — lag unmeasurable without occurred_at columns, depth unqueryable without status indexes — the table from [2.1](<../2. Coordination out of the database/2.1. Outbox tables designed for relay.md>)/[2.2](<../2. Coordination out of the database/2.2. Job tables and queues in the database.md>) either serves gauges or doesn't). Post-merge observability discovers the table can't answer ("when did this become pending?" — unrecorded — gauge impossible without migration). Design gauges with tables (occurred_at, status, claimed_at — observability columns, not overhead); operate gauges after merge (ops owns dashboards/alerts — interface, not handoff). Table serves gauges; gauges serve on-call — co-designed, never retrofitted.

**Performance note** — gauge economics: gauge queries cost indexed point-lookups (lag = one ordered scan head — microseconds; depth = one count on partial index — fast while pending set small — gauges priced like features, cheap); alert evaluation costs monitoring-system cycles (trivial — thresholds on existing metrics); unobserved incidents cost customer trust + war rooms (unbounded — the most expensive line in operations). Gauges are the cheapest insurance in async systems — microseconds per poll preventing quarters per incident. Instrument everything async; alert ruthlessly; runbook calmly.

**Mentor note** — teach "what's the gauge?" per async path (juniors answering with lag/depth/age triples design observable systems on first hearing; answering "the cron runs" learn the distinction in one question). Gauge-first async design generalizes (every handoff — queues, relays, webhooks, syncs — gets gauges before code: lag, depth, errors, age — the universal async vital signs). Review async PRs gauge-first ("show me the gauges" — missing gauges fail structurally); praise gauged handoffs publicly ("great lag gauge with owner"). Praise gauges; gauge praise's effect on incidents avoided.

## 3. Every runtime switch is owned (flags with owners and expiry — switches, not sediment)

**Definition** — the review's closing act over runtime configuration: every flag/config row merged arrives with owner (accountable team — paged when the flag misbehaves, responsible for progression), expiry (rollout-complete estimate — firing review, not auto-delete), rollout plan (percentages/cohorts over time — progression tracked), and retirement path (consolidation PR shape — removal witnessed by zero references) — or permanent declaration (kill switches, entitlements — "permanent by design, yearly review" — stated, never drifted). Ownerless, expiryless flags fail review structurally — sediment scheduled at birth, declined at review.

**What problem it solves** — sediment merges (flags without owners (departed authors — progression unowned, retirement unowned — fossilization certain); without expiry (immortal by omission — 340-flag matrices years later); without plans (percentages static — rollouts stalled silently, half the users on old behavior indefinitely); kill switches undrilled (incident response via pipeline anyway — switches decorative). Each merges trivially (one row — "just a flag") and accumulates permanently (rows never die without lifecycle — evaluation matrices growing, dead branches rotting, incident misreads compounding). Lifecycle review converts trivial merges to managed instruments (born with owners, progressing on plan, retiring on evidence) — rows with funerals, not sediment.

**Modern guidance** — the flag review lines: owner named ("team-payments — progression + retirement accountable" — team, not individual (individuals depart; teams persist)); expiry dated ("2026-12-31 — rollout-complete estimate + margin — fires review"); plan tracked ("25%→50%→100% Oct–Dec — stalls investigated, not shrugged"); retirement shaped ("consolidation PR removes references, behavior unconditional, row deleted last — witnessed"); permanent declared where applicable ("kill_payments: permanent by design, yearly review — stated, never defaulted"). Quarterly flag audit calendared (stale-flag review — 30 minutes, tickets filed — ritual from [3.1](<../3. Runtime configuration/3.1. Feature flags and config storage.md>)). Missing owner/expiry → request changes; "temporary" without date → permanent by another name (rejected vocabulary — temporary has a date or it's sediment).

```sql
-- GOOD: the flag review artifact — owned, expiring, planned, retiring-or-permanent.
-- new_checkout: owner team-payments ✓, expires 2026-12-31 ✓, plan 25→50→100 ✓,
-- retirement: consolidation PR shape agreed ✓. kill_payments: PERMANENT declared,
-- yearly review calendared ✓. Stale audit: quarterly ritual on calendar ✓.
-- Verdict: switches owned — approve flags.
```

```sql
-- BAD: the row review — columns checked, lifecycle unasked.
-- new_checkout: enabled=true, rollout 25% (owner? unasked — author departing next month.
-- Expiry? unset — immortal by omission. Plan? none — 25% indefinitely (half the users
-- on old behavior — unexamined). Retirement? unmentioned — sediment scheduled.)
-- The review approved a row; production inherits sediment. Lifecycle unasked, forever owned
-- by nobody. Trivial merge, permanent accumulation. Review covered columns; time graded lifecycle.
```

**Common confusion** — *"flag lifecycle is process overhead for simple toggles."* Simple toggles grow targeting (boolean today, cohorts tomorrow, percentages next quarter — simple is temporary); simple toggles outlive authors (owner departs — progression orphaned); simple toggles skip retirement (one-line removal feared — unknown behavior + unknown owner = hands off). Lifecycle costs one owner-line + one expiry-date at birth (seconds); sediment costs comprehension permanently (evaluation matrices only growing). Seconds now vs comprehension forever — the cheapest lifecycle in software, declined most often. Price seconds against forever; choose seconds.

**Performance note** — flag-lifecycle review is comprehension-performance (evaluation matrices staying small — fast incident reads ("which flags matter?" — answerable in seconds, not archaeology); dead branches removed — coverage honest, maintenance focused). Sediment taxes every incident (flag archaeology under time pressure — misreads, wrong kills, hesitant rollbacks) and every onboarding (matrices unexplained — new hires learning fossilized behavior as current). Lifecycle review keeps matrices live (every flag progressing or declared-eternal — comprehension constant regardless of flag count). Comprehension is operational performance — review it like latency.

**Mentor note** — model flag ownership on your own flags first (the track's standing lesson, sixth domain: authority's example teaches — senior's flag with owner/expiry/plan/retirement teaches more than any lifecycle mandate). Praise owned flags ("great expiry with plan") louder than clever targeting — teams optimize for praised behavior, and clever unowned flags have had enough admirers. Quarterly audits attended by seniors (presence signals priority — rituals seniors skip die within two quarters). Attend, praise, bury dead flags together — culture in three verbs.
