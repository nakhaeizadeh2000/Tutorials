# 3.1. Feature flags and config storage

## 1. Flags are rows, not branches (deploys stop gating releases)

**Definition** — feature flags as data: a flags table (name, enabled, rollout rules, owner, expiry) evaluated at runtime — releases ship dormant (flag off), activate by row update (no deploy), roll back by row update (instant, no pipeline). Deploys deliver *code*; flags deliver *behavior* — decoupled release trains (merge anytime, activate on schedule, kill on incident). Branches gate merges; flags gate users — version control handles the former, the database the latter.

**What problem it solves / history** — the deploy-coupled release: features merging to main going live immediately (half-tested code serving production — release trains held hostage by the slowest review); rollbacks requiring redeploys (broken feature reverted via pipeline — minutes-to-hours of bad behavior serving while CI rebuilds, plus the revert's own risk); long-lived feature branches (diverging for weeks — merge conflicts growing, integration tested never until the big bang). Flags decouple all three (merge anytime — dormant by default; activate on schedule — row update; kill instantly — row update beats pipeline by orders of magnitude). Trunk-based development with flags replaced branch-per-feature across the industry — version-free practice, as-of-September-2026 standard.

**Modern guidance** — the flag contract per flag (verified shapes below): `name` PK (stable identifier — code references by name, never by id); `enabled` (master switch — sole decider when targeting absent); targeting (`rollout_pct` 0–100 CHECKed + `cohorts` array — percentage and cohort gates, combinable); `kill` (emergency switch — evaluated first, bypasses everything — incident response in one UPDATE); `owner` (team accountable — flags without owners fossilize — third promise); `expires_on` (stale-flag hygiene — dated at creation); `updated_at` (audit of who changed behavior when — flag flips are production changes, logged like deploys). Evaluation order fixed: kill → enabled → targeting (documented, tested per flag — evaluation semantics versioned with the flag consumer, never improvised per call site).

```sql
-- GOOD: flags as rows — releases without deploys, rollbacks without pipelines (verified PG 16.15).
CREATE TABLE feature_flags (
  name        TEXT PRIMARY KEY,   -- stable: code references names, never ids
  enabled     BOOLEAN NOT NULL DEFAULT false,
  rollout_pct INT NOT NULL DEFAULT 0 CHECK (rollout_pct BETWEEN 0 AND 100),
  cohorts     TEXT[] NOT NULL DEFAULT '{}',   -- '{"beta","staff"}' (overlap operator below)
  kill        BOOLEAN NOT NULL DEFAULT false, -- emergency: evaluated first, bypasses all
  owner       TEXT NOT NULL,                  -- accountable team (fossil prevention — promise 3)
  expires_on  DATE,                           -- stale-flag hygiene (dated at creation)
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- Evaluate (kill → enabled → targeting — fixed order, tested per flag):
-- SELECT name FROM feature_flags WHERE kill = false AND enabled
-- AND (rollout_pct = 100 OR cohorts && '{beta}');  -- percentage OR cohort gate
```

```sql
-- BAD: flags as branches/config-files — releases coupled to deploys, rollbacks to pipelines.
-- feature/new-checkout branch (3 weeks diverging — merge conflicts compounding; untested
-- with main until the big bang). config/prod.yaml: new_checkout: true (deploy to flip —
-- pipeline minutes; rollback = revert + rebuild + redeploy — incident window tripled).
-- env var per flag (host-divergent values — canary hosts disagreeing silently; no audit
-- of who flipped what when). Branches gate merges (version control's job); runtime
-- behavior needs runtime storage (the database's job). Coupled, undebuggable, slow.
```

**Common confusion** — *"flags are just booleans — a config file suffices."* Booleans suffice for on/off; production flags need targeting (percentages, cohorts — gradual rollouts, not flag-days), kill switches (incident response faster than pipelines), ownership (fossil prevention), expiry (hygiene), and audit (who flipped behavior when — production-change accountability). Config files serve static configuration (ports, timeouts — deployed with code, correctly); flags serve *runtime behavior decisions* (who sees what — changed independently of deploys, audited independently). Static vs runtime — different storage, different lifecycle, never conflated.

**Performance note** — flag-read economics: flags read per request (hot path — cache aggressively: in-memory refresh every N seconds, never per-request queries at scale — cache stampede guarded by jittered refresh); evaluation local (boolean + array-overlap on cached rows — microseconds, zero I/O); kill-switch latency bounded by refresh interval (5–30s typical — incident response in seconds, not pipeline-minutes). Stale-cache risk priced (refresh interval = maximum kill latency — stated, monitored — interval breaches alert). Cache the flags, audit the flips, bound the staleness — hot-path safe by construction.

**Mentor note** — teach "would you deploy to turn this off at 3 a.m.?" (the flag-or-config test — juniors answering honestly sort runtime decisions (flags — killable without pipelines) from static config (files — deployed with code) on first hearing). The 3 a.m. framing converts abstract decoupling to incident reality (pipelines feel fast at noon, glacial during outages — design for the outage clock, not the demo clock). Every runtime behavior decision gets the test; every "yes" becomes a flag row with owner and expiry. Test once per decision, benefit per incident.

## 2. Targeting rules stay queryable (percentages, cohorts, kill switches — evaluation without deploys)

**Definition** — targeting as data: rollout rules stored queryably (percentage integers, cohort arrays, per-entity overrides) — evaluable in SQL for analysis ("who sees the flag?" — cohort membership queries, rollout coverage counts) and in code for requests (deterministic hash(user) < pct — stable per user across requests — plus cohort lookup). Kill switches as rows (kill=true bypasses all targeting — incident response in one UPDATE, audited). Queryable rules serve operators (coverage analysis) and code (request evaluation) from one source — no duplicated logic drifting between dashboard and application.

**What problem it solves** — the opaque rollout: percentage logic embedded in code constants (coverage unqueryable — "who sees it?" answered by code reading, not SQL; rollout changes need deploys — defeating flags' purpose); cohort lists in spreadsheets (targeting decided outside the system — applied manually, drift inevitable — spreadsheet says beta, code says beta-plus-friends); kill switches as code pushes (incident response via pipeline — minutes of bad behavior while CI runs — the exact failure flags exist to prevent). Queryable rules convert rollouts from code behavior to data analysis (coverage counted, cohorts listed, kills flipped — all in SQL, all audited, none deployed).

**Modern guidance** — the targeting contract: *percentages* deterministic (hash(user_id + flag) mod 100 < pct — stable per user per flag — no sticky storage needed for the common case; sticky overrides table for exceptions — per-user pins surviving percentage changes); *cohorts* as arrays (overlap operator — `cohorts && '{beta}'` — indexed via GIN where cohort queries run hot — cohort membership managed as data (user_cohorts table or attribute), never hardcoded); *kills* as first-evaluated rows (kill=true short-circuits — tested per flag (kill drill: flip kill, verify behavior dies within refresh interval — rehearsed, not hoped); *overrides* as rows (per-entity pins — support tooling flips individuals — audited like all flag writes). Analysis queries shipped with the flag (coverage count, cohort listing — operators answer "who sees it?" without code access).

```sql
-- GOOD: targeting queryable — coverage counted, cohorts listed, kills drilled (verified PG 16.15 shapes).
-- Coverage analysis (operators, no code access): how many flags target beta?
-- SELECT name, rollout_pct FROM feature_flags WHERE cohorts && '{beta}';  (GIN-indexable)
-- Kill drill (rehearsed per flag): UPDATE feature_flags SET kill = true WHERE name = $1;
-- → behavior dies within refresh interval (verified per flag — drill recorded, not hoped).
-- Per-user pin (support override): separate flag_overrides(user_id, flag, forced_state)
-- table (audited, expirable — pins without expiry become permanent targeting sediment).
```

```sql
-- BAD: targeting in code constants and spreadsheets — unqueryable, undeployable-fast, undrilled.
-- if (user.id % 100 < 25) { newCheckout(); }  // percentage in code (deploy to change —
-- flags' purpose defeated; coverage unqueryable — "who sees it?" needs code archaeology).
-- cohorts.xlsx (targeting decided outside the system — applied by hand-editing code lists;
-- drift guaranteed: spreadsheet v7 vs code v12, nobody reconciling). Kill: redeploy
-- previous version (pipeline minutes — incident window tripled; kill switch absent where
-- most needed). Targeting outside the database is targeting outside audit, analysis, and speed.
```

**Common confusion** — *"percentage rollouts need sticky storage per user."* Deterministic hashing (hash(user+flag) — stable across requests, sessions, deploys — no storage) covers the common case (percentage cohorts stable without state); sticky tables cover exceptions (pinned users surviving percentage *changes* — hash remaps on pct change by design (modulo boundaries shift) — pins preserve individuals across changes). Hash-first (stateless, free), pins-for-exceptions (stateful, audited, expirable) — storage where semantics demand (pins), math where statelessness suffices (percentages). Sticky-everything is state without need; hash-only ignores pin realities — both, each where fit.

**Performance note** — targeting economics: hash evaluation O(1) per request (microseconds — no I/O on cached flags); cohort overlap O(cohorts) array scan (tiny arrays — negligible; GIN serves analytical cohort queries, not request path); pins lookup one indexed row (per-request only where pins exist — absent-pins fast-path: skip lookup when user has no pins — cached pin-set per request, usually empty). Kill evaluation first (short-circuit — incident path fastest by construction — kill checks precede all other logic, always). Microsecond evaluations, cached flags, drilled kills — targeting costs nothing measurable, saves incidents measurably.

**Mentor note** — teach "query the rollout" (juniors writing coverage SQL — "show me beta coverage" answered in psql, not code review — discover targeting as data analysts do). Operators answering rollout questions without engineers is organizational leverage (support/sales/product self-serve targeting analysis — fewer interruptions, faster answers). Queryable targeting democratizes releases; code-embedded targeting gatekeeps them behind deploys and developers. Democratize deliberately — queryability is a team-performance feature, not just a technical one.

## 3. Flag lifecycle is managed (stale flags retire — flags without owners become permanent branches)

**Definition** — flag lifecycle: flags are born (creation with owner + expiry + rollout plan), live (targeting adjusted during rollout — percentages climbing, cohorts widening), retire (rollout complete → code paths consolidated → flag row deleted — the flag's death certificate: removal PR linked, behavior now unconditional). Permanent flags (kill switches, entitlements, ops toggles — intentionally immortal) are declared permanent at birth (different lifecycle: reviewed, never retired — the exception stated, not drifted into). Lifecycle unmanaged = flags accumulating (hundreds of stale flags — evaluation matrices no one understands, dead code paths untested, "temporary" 2021 experiment still gating).

**What problem it solves** — flag sediment: stale flags fossilizing (rollout finished 2023, flag still evaluated — dead code paths rotting (untested branches — coverage lies), evaluation matrices confusing (which flags matter? — archaeology per incident), cleanup feared (removing unknown-behavior flags risks breakage — so nobody removes — accumulation accelerates). Sediment converts flags from release tools to legacy code (branches that happen to live in rows — the long-lived feature branches flags were invented to kill, reincarnated as data). Lifecycle management (expiry at birth, retirement as rollout's final step, permanent-declared exceptions) keeps the flag set live: every flag either progressing or declared-eternal, none drifting.

**Modern guidance** — the lifecycle contract per flag (stated at creation): *owner* (team — accountable for progression AND retirement — ownerless flags fossilize by default); *expiry* (date — rollout-complete estimate + margin — expiry fires review, not auto-delete (auto-deleting behavior gates is flag-day automation — review decides: retire or extend with reason)); *rollout plan* (percentages/cohorts over time — 10% → 50% → 100% dated — progression tracked, stalls investigated); *retirement* (code consolidation PR — flag references removed, behavior unconditional — flag row deleted last, witnessed by zero code references — same grep-before-drop sacrament as [Domain 05 §1.1](<../../../05 Evolution Growth and Partitioning/sections/1. Schema evolution/1.1. Expand and contract migrations.md>)); *permanent declaration* (kill switches, entitlements — "permanent by design, reviewed yearly" — stated, never defaulted — permanent-by-drift is sediment with seniority).

```sql
-- GOOD: lifecycle managed — expiry fires review, retirement witnessed, permanents declared.
-- Flag new_checkout: owner team-payments, expires 2026-12-31, plan 25%→50%→100% (Oct–Dec).
-- Expiry review (Dec 31): rollout 100% stable 6 weeks → retire (consolidation PR #8912:
-- flag references removed, behavior unconditional; code search zero hits → row deleted).
-- Flag kill_payments: PERMANENT by design (incident switch — yearly review, never retire).
-- Stale-flag audit (quarterly): SELECT name, owner, expires_on FROM feature_flags
-- WHERE expires_on < now() AND name NOT IN (permanent set) → retirement tickets filed.
```

```sql
-- BAD: flag sediment — born without lifecycle, living forever, understood by none.
-- 340 flags (12 owned — owners departed; 200 expired-ignoring (no expiry set — immortal
-- by omission); 47 referencing deleted code paths (flag evaluates, nothing branches —
-- pure overhead + confusion); 3 kill switches nobody drilled (incident response via
-- pipeline anyway — switches decorative). Evaluation matrix: unknowable (which flags
-- matter? — archaeology). Cleanup: feared (unknown behavior + unknown owners = hands off).
-- Sediment: branches reincarnated as rows, legacy code wearing runtime storage.
```

**Common confusion** — *"cleaning flags risks breakage — leave them."* Retirement risk is managed (consolidation PR reviewed like any code change — behavior unconditional, tests covering both paths pre-consolidation — removal witnessed by zero references — same safety as any deletion), while sediment risk is certain (dead branches untested — coverage fiction; evaluation confusion — incident-time misreads; matrix growth — every new flag harder to reason about). Managed risk (reviewed removal) beats certain decay (permanent sediment) — "leave them" trades a reviewable PR for unreviewable accumulation. Retire deliberately; fear correctly.

**Performance note** — sediment economics: stale flags cost evaluation time per request (hundreds of cached evaluations — microseconds each, compounding — flag-matrix evaluation growing with sediment, never with value); dead code paths cost coverage lies + maintenance confusion (untested branches — bugs hiding where tests claim coverage); cleanup costs one consolidation PR per flag (reviewed, tested — bounded, scheduled). Retire-per-flag costs hours quarterly; sediment costs comprehension permanently (incident misreads under time pressure — the bill arriving at 3 a.m. with interest). Retire routinely; comprehend always.

**Mentor note** — teach "flags are branches with owners and funerals" (juniors hearing the branch analogy place flags correctly — trunk-based industry practice, lifecycle included — and remember funerals (retirement as rollout's final step, not optional hygiene). Quarterly flag audits as team ritual (stale-flag review meeting — 30 minutes, tickets filed, owners assigned — boring, effective). Rituals beat reminders (calendar > conscience — expiry dates fire reviews automatically; conscience-dependent cleanup never happens). Calendar the audit; bury the dead flags; keep the kill switches sharp.
