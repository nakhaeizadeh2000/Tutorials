# 5.1. Common interview QA operations modeling

## 1. Design reliable notifications live (outbox narration — table, relay, idempotency, purge)

**Definition** — the exercise: *"order paid — notify the customer reliably, exactly once in effect"* (the interview staple). The graded artifact is outbox narration end-to-end: atomic recording (business + outbox rows, one transaction — dual-write failure named and eliminated), relay surface (ordered seq, contracted payload, relayed-at marking, partial index — table designed for its relay), idempotent consumption (keys dedup — repeats converge — [Domain 01 §2.2](<../../../01 Modeling Foundations and Mental Model/sections/2. Identity and keys/2.2. Identity at scale.md>)), purge windows (relayed rows retained 7–30 days, lag-gated). Pattern referenced ([Databases 05 §3.1](<../../../../Databases/05 Transactions Consistency and Integrity/sections/3. Distribution/3.1. Distributed honesty 2PC and sagas.md>) by name — never re-taught), table designed live, delivery honestly at-least-once throughout.

**What problem it solves** — notification questions filter for distributed honesty (most candidates propose dual-write ("save order, then publish event") — the most incident-dense two lines in backend code, unrecognized; or "exactly-once delivery" — the impossible promise, believed). Interviewers listen for the impossibility acknowledged ("exactly-once delivery doesn't exist — exactly-once *effects* via idempotency, stated plainly") and the atomicity placed correctly (recording transactional — delivery retried — effects deduplicated — three properties, three mechanisms, no conflation). Honesty about impossibility + precision about mechanisms = the senior signal; "we'd use Kafka exactly-once" = the vocabulary signal (Kafka's EOS is transactional-scope, not end-to-end — believed, not understood).

**Modern guidance** — the five-minute shape: (1) *kill dual-write* (1 min — name the failure (committed-unpublished + published-uncommitted — both directions, both production-frequent) before proposing anything — diagnosis before prescription, graded); (2) *atomic record* (1 min — "order + outbox rows, one transaction — both-or-neither recorded — single-system guarantee, no coordination"); (3) *relay surface* (2 min — "seq cursor, JSONB contract per event+version, relayed_at + partial index, aggregate identity — relay scans pending only, lag dashboarded"); (4) *consume + purge* (1 min — "idempotency keys dedup (repeats converge); purge relayed past 7d lag-gated (retention window, not forever)"). Impossibility stated ("at-least-once delivery, exactly-once effects — the honest contract") — interviewers promoting honesty over magic, always.

```sql
-- GOOD (whiteboard narration, paid-order notification — 5 min):
-- "Dual-write dies both directions (committed-unpublished: paid-unshipped, discovered by
-- customers; published-uncommitted: phantom events for rolled-back work). So: one
-- transaction records order + outbox row (seq identity, event+version contract, payload).
-- Relay polls WHERE relayed_at IS NULL ORDER BY seq (partial index — pending-only scan),
-- publishes, marks relayed (at-least-once, honestly). Consumers dedup by idempotency key
-- (repeats converge — exactly-once effects, never promised delivery). Purge relayed past
-- 7d, lag-gated (retention window with margin). Pattern: Databases 05/3.1 (referenced);
-- table: seq/contract/marking/purge (designed here, live)."
CREATE TABLE outbox (
  seq BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, aggregate TEXT NOT NULL,
  aggregate_id TEXT NOT NULL, event TEXT NOT NULL, event_version INT NOT NULL DEFAULT 1,
  payload JSONB NOT NULL, occurred_at TIMESTAMPTZ NOT NULL DEFAULT now(), relayed_at TIMESTAMPTZ
);
```

```sql
-- BAD (whiteboard): the hopeful two-liner — incidents scheduled, impossibility unacknowledged.
-- INSERT INTO orders ...; publish("order_paid", ...);  -- (DB commits, broker crashes:
-- paid-unshipped, customer-discovered. Broker-first: phantom events for rolled-back work.
-- "Exactly once"? Delivery unpromised-but-assumed; duplicates unhandled (no idempotency
-- keys — double-notifications, double-charges downstream). Relay? None (dual-write has
-- no relay — failures are permanent, not retried). Purge? N/A (no outbox exists).
-- Two lines, four failure modes, zero honesty. Hope as integration, live on whiteboard.)
```

**Common confusion** — *"the interviewer wants Kafka/RabbitMQ specifics."* Brokers are interchangeable delivery (SQS/Rabbit/Kafka — properties matched to workload, all at-least-once at heart); the interview grades *honesty architecture* (dual-write killed, atomicity placed, idempotency named, purge windowed) — broker-agnostic, correct across all of them. Candidates reciting broker features while dual-writing fail; candidates narrating outbox with "any broker" pass. Architecture over products — always, especially under vendor questioning ("which broker?" — "any at-least-once; the table carries the guarantees, the broker carries bytes").

**Performance note** — volunteer relay economics unprompted ("relay scan pending-only via partial index — microseconds while caught up; lag gauge oldest-unrelayed — alert 5min; purge 7d window ≈ rate × 7 days storage — priced"). Economics with gauges signal operations maturity alongside design correctness — interviewers noting both promote faster (correctness gets hired, operability gets leveled). Gauges named per handoff (lag, depth, age) — the observability reflex from [4.1](<../4. Mentor checklist/4.1. Operations-modeling checklist mentors insist on.md>), performed live.

**Mentor note** — drill as impossibility-first narration ("exactly-once delivery is impossible — here's the honest assembly" — candidates leading with impossibility frame everything after as engineering, not magic). Grade the order (dual-write killed *before* outbox proposed? — diagnosis-first candidates diagnose every problem first, a career habit forming in interviews). Three timed rounds transform magic-believers into honesty-architects — the single most valuable interview transformation in distributed systems, rehearsed in five-minute increments.

## 2. Background work without a broker (job-table design under questioning)

**Definition** — the follow-up: *"no Kafka/RabbitMQ — run welcome emails in the database"* (the constraint interview). The graded skill is claim-work design under questioning: status machine (pending/claimed/done/failed — transitions governed), claim query (SKIP LOCKED, ordered, partial-indexed — written live, correctly), retry bounds (attempts, backoff, poison parking), lease expiry (crashed workers' jobs return — orphans impossible), graduation triggers (rate/fan-out/ordering limits named with numbers). Constraint accepted (no broker lamented — "with these tools" attitude graded), queue derived (table + machine + gauges, complete), exit named (triggers, not forever).

**What problem it solves** — broker-default thinking (background work "requires" infrastructure — candidates unable to design within constraints reveal tool-dependence, not engineering; interviewers constraining brokers deliberately probe first-principles queueing: atomicity, coordination-freedom, retry economics — all answerable in SQL). Candidates designing complete job tables under constraint show they understand queues (claims, leases, poison, gauges); candidates stalled without brokers show they operate queues (configured, monitored, depended-upon). Understanding hires anywhere; dependence hires where brokers exist. Interviews prefer anywhere.

**Modern guidance** — the five-minute shape: (1) *table* (1 min — "jobs: kind, payload, status-CHECK, attempts, run_after, claimed_by/at, coherence CHECK — machine, not strings"); (2) *claim* (2 min — write the query live: "SELECT ... WHERE pending AND run_after<=now ORDER BY run_after,id LIMIT n FOR UPDATE SKIP LOCKED — concurrent workers, no coordination; partial index serves pending-only" — writing it correctly *is* the senior filter (SKIP LOCKED named, ordering stated, index partial — three details, all graded)); (3) *retries + leases* (1 min — "bounded attempts with exponential run_after, poison parks in failed alerted; lease sweeper resets stale claims — orphans impossible past lease"); (4) *gauges + graduation* (1 min — "depth + oldest-age gauges, alert thresholds; graduate past rate/fan-out/ordering triggers — named numbers"). Constraint embraced, queue complete, exit priced — five minutes, hired.

```sql
-- GOOD (whiteboard, welcome emails — 5 min, query written live):
-- "Table: kind/payload/status-CHECK/attempts/run_after/claimed_by (+coherence CHECK).
-- Claim (the senior filter — written, not described): SELECT id FROM jobs WHERE
-- status='pending' AND run_after <= now() ORDER BY run_after, id LIMIT 10
-- FOR UPDATE SKIP LOCKED — workers divide without coordination. Then UPDATE to claimed
-- (same txn — atomic handoff; crashes roll back to pending automatically).
-- Retries bounded (5 attempts, exponential backoff, poison parks alerted); leases expire
-- (10-min sweeper — orphans impossible). Gauges: depth + oldest-age, alerted. Graduate
-- past rate/fan-out/ordering triggers (named numbers — brokers on triggers, never by default)."
```

```sql
-- BAD (whiteboard): the poll-and-pray — status strings, racing claims, infinite retries.
-- SELECT id FROM jobs WHERE status='pending' LIMIT 10;  -- (FOR UPDATE? Missing —
-- workers race claims (double-sends). SKIP LOCKED? Missing — workers block each other.
-- ORDER? Missing — starvation unexamined. Partial index? Missing — full scans per poll.)
-- UPDATE jobs SET status='done' WHERE id=$1;  -- (claimed state? Skipped — work unattempted
-- completable. Attempts? Uncounted — poison job #4417 looping since spring.)
-- Constraint accepted ("no broker, fine") — queue fundamentals declined with it.
-- Tool-dependence revealed: operates queues, doesn't understand them.
```

**Common confusion** — *"claim queries are too advanced for interviews."* SKIP LOCKED is one clause (documented, stable, decade-old — as-of-September-2026 unremarkable), and interviewers ask constraints precisely to see clause-level precision ("write the claim" separates describers from implementers — describers say "workers coordinate somehow"; implementers write FOR UPDATE SKIP LOCKED). Clause precision is implementer evidence — the most compact senior signal in SQL interviews (one clause, nine words, complete coordination story). Learn the clause; write it live; hired.

**Performance note** — volunteer claim economics ("pending-scan via partial index — small while workers keep up; locks per batch brief — workers scale to connection budget; depth gauge oldest-pending-age — alert 30min"). Economics with gauges (same pattern as promise 1 — design correctness + operations maturity, both noted). Throughput ceiling stated ("thousands/minute comfortably — connection-bound; partitioned tables, then brokers past triggers — graduated, never hoped"). Ceilings with exits — the complete queue answer in one extra sentence, expert depth for free.

**Mentor note** — drill claim-query writing (blank whiteboard, "claim 10 jobs for 5 concurrent workers" — 90 seconds, graded: SKIP LOCKED present? ordering stated? partial index mentioned? coherence considered?). Writing beats describing 10-to-1 in interviews (written queries prove implementation; described queries prove vocabulary). Three writing drills convert describers to implementers — the highest-ROI interview prep in SQL-land (one clause, nine words, career-changing precision). Write, don't describe — drill it until automatic.

## 3. Audit and deletion under pressure (history vs soft-delete vs purge — the judgment call)

**Definition** — the closer: *"a user demands deletion, finance needs history, support needs undo — design it"* (the three-way tension interview). The graded skill is *tool separation under pressure*: audit mirrors for history (regulators/finance read versions — 1.1), soft-delete for undo (support restores within window — 1.2), purge with certificates for erasure (GDPR executed, holds checked, proof retained — [Domain 05 §3.1](<../../../05 Evolution Growth and Partitioning/sections/3. Lifecycle and retention/3.1. Archival and lifecycle tiers.md>)) — three tools, three owners, three horizons, sequenced per deletion (stamp → window → obligation-check → archive-or-purge → certificate). Conflation under pressure (tombstones-as-archive, purge-as-undo, mirrors-as-erasure-proof) fails; separation passes.

**What problem it solves** — pressure collapses distinctions (candidates choosing one tool for three needs: "soft-delete everything" (tombstones as history — no actors, no versions — finance unserved; as erasure — data retained, GDPR violated — legal unserved; as undo — the one fit, lonely); or "hard-delete everything" (undo impossible — support unserved; history destroyed — finance unserved; erasure complete — the one fit, lonely)). Interviewers apply pressure deliberately (three stakeholders, conflicting needs — watching whether distinctions hold or collapse). Held distinctions under conflicting demands = senior judgment performing live; collapsed tools = junior simplification under stress.

**Modern guidance** — the ninety-second shape: (1) separate aloud ("three needs, three tools: undo → soft-delete 30d window (support restores); history → audit mirror (finance reads versions, actors attached); erasure → purge with holds-check + certificate (legal signed, proof retained)"); (2) sequence ("stamp day 0 → restore-window 30d → obligation-check (legal hold? archive first) → purge + certificate"); (3) conflicts resolved ("GDPR vs tax-retention: erasure anonymizes live (pseudonymize), history retains anonymized versions (utility without identity) — conflict mediated, not wished away; holds override schedules structurally (purge jobs check hold table — spoliation impossible by query structure)"); (4) Tombstone≠archive stated ("stamps serve undo (days), tiers serve obligation (years) — horizons differ 100×, tools differ accordingly"). Separation narrated, conflicts mediated, horizons quantified — judgment performing, not freezing.

```sql
-- GOOD (spoken, deletion-request scenario — 90 seconds, distinctions held):
-- "Three tools: soft-delete stamps undo (30d window — support restores instantly);
-- audit mirror keeps history (finance reads versions with actors — deletion recorded
-- as a transition, not an absence); purge executes erasure (holds checked structurally,
-- certificate retained — GDPR proof). Sequence: stamp → window → hold-check →
-- archive-if-obligated → purge + certificate. Conflicts: tax history vs erasure →
-- anonymize live, retain anonymized versions (utility without identity — mediated).
-- Tombstones ≠ archive (days vs years — different tools, different owners)."
```

```sql
-- BAD (spoken): the single-tool collapse — pressure freezing distinctions.
-- "Soft-delete everything — set deleted flag, keep forever." (Undo? Yes (the one fit).
-- History? No actors/versions (finance unserved). Erasure? Violated (data retained —
-- GDPR unserved, fines scheduled). Purge? Never (tombstones accumulate — performance
-- billed daily). One tool, three needs, one served. Or the mirror: "hard-delete
-- everything" (erasure served; undo/history destroyed — two stakeholders unserved).
-- Pressure collapsed three tools into one; the interview grades the collapse, not the tool.
```

**Common confusion** — *"anonymization satisfies both history and erasure."* Anonymization (irreversible identity-stripping) satisfies erasure (no personal data remains — GDPR content) AND statistical history (aggregates computable — finance utility) — but NOT audit history (who did what — identity *is* the audit content — anonymized actors unanswerable) and NOT support undo (anonymized rows unrestorable to persons). Anonymization mediates two needs (erasure + statistics), not all four (audit + undo need identity preserved somewhere — holds, mirrors with access controls, legal-scoped retention). Partial mediation stated precisely beats total mediation claimed vaguely — name which needs each technique serves, never all.

**Performance note** — close with horizon economics ("undo window: tombstone weight days-bounded (purged); audit mirrors: write ×2 scoped tables, partitioned yearly; purge batches: off-peak chunks with certificates; anonymization: one-time compute per row at purge — each horizon priced in its tier, total minimal"). Horizon-priced operations signal cost-awareness alongside judgment (correctness gets hired, cost-awareness gets leveled — the track's standing close). Four tools, four horizons, four prices — the complete answer in one extra breath.

**Mentor note** — teach "separate before sequencing" (juniors listing three tools before ordering them hold distinctions under pressure; juniors sequencing one tool collapse elegantly). Drill as stakeholder triads (support/finance/legal demands stated together — 90 seconds, tools assigned per demand, conflicts mediated aloud): pressure rehearsed beats pressure improvised (interviews and incidents share the shape — conflicting stakeholders, finite time, distinctions required). Rehearse triads monthly; perform calmly always — pressure-handling is trained, never innate.
