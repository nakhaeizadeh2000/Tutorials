# 6.1. Boundaries what is covered elsewhere

## 1. Transaction mechanics live in Databases 05 (atomicity, outbox pattern, sagas — linked, not repeated)

**Definition** — outward boundary: how the engine *guarantees* what this domain *shapes*. Single-system atomicity (the outbox's recording half), SKIP LOCKED semantics (the claim's locking half), saga compensation (the cross-system alternative), isolation levels (what concurrent relays/workers observe) — all engine behavior owned by [Databases 05](<../../../../Databases/05 Transactions Consistency and Integrity/README.md>), flagship leaf [3.1 Distributed honesty](<../../../../Databases/05 Transactions Consistency and Integrity/sections/3. Distribution/3.1. Distributed honesty 2PC and sagas.md>) (2PC/saga/outbox mechanics with runnable code). Domain 06 names the tables (outbox columns, job machines, flag rows); Databases 05 teaches the guarantees underneath.

**What problem it solves** — duplicated coverage rot (two outbox explanations drifting — one updating relay semantics, one fossilizing table shapes beside stale pattern text) and misplaced coverage confusion (isolation levels taught beside flag schemas suggests they're one decision — they're two: what guarantee (there), then what shape (here)). Single source of truth per PROMPT.md §5: pattern/mechanics in Databases 05, table/machine/flag design here — each concept one home, links between, drift impossible by construction (stale links fail loudly at verification; stale copies fail silently in production — prefer loud failures, always).

**Modern guidance** — the crossing map, by need: outbox pattern + relay + consumer mechanics → [Databases 05 §3.1](<../../../../Databases/05 Transactions Consistency and Integrity/sections/3. Distribution/3.1. Distributed honesty 2PC and sagas.md>); ACID guarantees and isolation behavior → [Databases 05 §1](<../../../../Databases/05 Transactions Consistency and Integrity/sections/1. Guarantees/1.1. ACID that holds.md>); constraint mechanics (exclusion, CHECK execution) → [Databases 05 §2](<../../../../Databases/05 Transactions Consistency and Integrity/sections/2. Mechanisms/2.2. Constraints as integrity.md>); idempotency keys (consumer dedup) → [Domain 01 §2.2](<../../../01 Modeling Foundations and Mental Model/sections/2. Identity and keys/2.2. Identity at scale.md>); full orientation → [Databases track index](<../../../../Databases/README.md>). Inbound, Databases 05's boundary leaf defers operations-modeling depth here — pattern there, tables here, each owning its half (stated in both directions — bilateral boundaries rot slower than unilateral claims).

**Common confusion** — *"this track assumes transactions — where do I learn them?"* (Asked in every boundary leaf; restated for direct arrivals landing here.) Databases 05, in order (guarantees → mechanisms → distribution), then return here for table shapes. The tracks compose: Databases makes you operational, Database Design makes you deliberate — guarantees are operational, shapes are deliberate, both required, each owned. Either order works; skipping either half doesn't.

**Performance note** — none specific — performance mechanics (lock monitoring, contention measurement, isolation overhead) are Databases 05–06 territory by design. This domain's performance contribution is upstream: claim indexes that keep relay scans small, partial uniques that keep live access fast, bounded machines with finite tails, cached flags with microsecond evaluation — decisions that make the mechanics' job possible. Unshaped async paths can't be tuned, only survived — shape correctly here; measure calmly there.

**Mentor note** — same navigation discipline as every boundary leaf in this track (sixth restatement, permanent value): mechanics questions get links, not lessons — then the *why* of the boundary. Learners who navigate the map become autonomous; mentors who re-teach across boundaries train dependency. The boundary is curriculum, not convenience — final restatement, same habit, track complete.

**Cross-links** — the map above is the complete outward set for transaction mechanics; backup/monitoring neighbors and application patterns follow.

## 2. Backup and monitoring live in Databases 06–07 (restore mechanics, alerting — neighbors, not repeats)

**Definition** — outward boundary: operating what this domain shapes — backup/restore mechanics (pg_dump strategies, point-in-time recovery, restore testing — [Databases 06](<../../../../Databases/06 Performance Backup and Operations/README.md>)), monitoring and alerting infrastructure (metric collection, dashboards, paging — Databases 06), production data synthesis (API contracts, keyset pagination, review practice — [Databases 07](<../../../../Databases/07 Production Data Use and Interview Mastery/README.md>)). Domain 06 designs gauge-serving tables (occurred_at, status, claimed_at — observability columns, not overhead); neighbors operate the gauges (dashboards, alerts, runbooks). Tables serve gauges; gauges serve on-call — co-designed ([4.1](<../4. Mentor checklist/4.1. Operations-modeling checklist mentors insist on.md>)), never retrofitted.

**What problem it solves** — scope creep in both directions (operations domain absorbing backup tutorials — mechanics without a design question; monitoring runbooks absorbing table design — procedures without modeling context). The interface is crisp: Domain 06 outputs *gauge-serving shapes + triggerable procedures* (lag measurable, depth queryable, purges certificated); neighbors output *operating capability* (backups restoring, alerts firing, on-call responding). Shapes without capability are documentation; capability without shapes is improvisation on uninstrumented tables. Both halves, each owned, interfacing at gauges and runbooks — the same design/operate interface as [Domain 05 §6](<../../../05 Evolution Growth and Partitioning/sections/6. Boundaries/6.1. Boundaries what is covered elsewhere.md>), operations edition.

**Modern guidance** — the neighbor map: backup/restore mechanics and point-in-time recovery → Databases 06; performance operations (EXPLAIN, index maintenance, vacuum behavior for history/job/outbox tables) → Databases 06; production data use (API envelopes, keyset pagination serving job/outbox reads, review synthesis) → Databases 07; keyset mechanics specifically → [Databases 07 §2.2](<../../../../Databases/07 Production Data Use and Interview Mastery/sections/2. Review and design/2.2. Data API contracts.md>); on-call judgment and capacity behavior → Databases 07 + NodeJS 07 (outside both tracks — one line per DRY). Gauge columns designed here (occurred_at everywhere, status machines queryable, claimed_at/relayed_at timestamps) are the interface contract — neighbors assume them present; tables missing them fail operating review (returned to this domain for reshaping, not worked around).

**Common confusion** — *"gauges are monitoring config, not modeling."* Gauge-serving columns are modeling (occurred_at on outbox rows, claimed_at on jobs, status machines queryable — shaped at table creation, unaddable later without migrations); gauge dashboards are monitoring (thresholds, alerts, runbooks — configured post-merge, operated continuously). Unshaped tables can't be gauged (lag unmeasurable without timestamps — monitoring discovers the gap, modeling fixes it a migration later). Shape first (here), monitor second (there) — order matters; retrofits cost migrations that foresight priced at zero.

**Performance note** — none specific — operations performance (backup windows, alert latency, restore RTO) is neighbors' territory by design. This domain's operations contribution is upstream, restated finally: gauge-serving shapes, bounded machines, priced triggers, executable procedures — operability delivered at design time. The interface working as designed, track complete.

**Mentor note** — teach the design/operate interface explicitly ("who runs this gauge at 3 a.m.?" — asked per handoff, answered with team names — gauges without operators are decoration). Juniors designing gauges with operators named learn operational empathy early (procedures written for tired humans — abort signals clear, verification simple, rollback named). The empathy test (would *you* run this half-asleep?) applies to every runbook-adjacent design — sixth domain, same question, permanent habit. Design for the tired; operate rested.

## 3. Application patterns live in DesignPatterns 06 (repository seam, pub-sub — outside this track)

**Definition** — outward boundary (unchanged across all six domains — ODMs/ORMs/repositories consume shapes, never define them): how code *talks to* operations tables — repository patterns over job/outbox/flag tables, pub-sub consumption of relayed events, ODM mappings of audit/history shapes — is owned elsewhere ([DesignPatterns 06](<../../../../DesignPatterns/06 Modern Patterns and Anti-Patterns/README.md>) — repository seam, pub-sub and event sourcing; ORM track — planned sibling, textual forward, target unbuilt, no dead link by design). Shapes defined here; consumed there. Influence flows one way: modeling decisions constrain code structure, never the reverse — sixth restatement, same rule, track complete.

**What problem it solves** — consumer-first operations modeling ("how will the worker framework poll this?" — framework polling semantics dictating job tables; "how does the ODM map history mirrors?" — mapper limitations flattening audit shapes; "which broker SDK?" — SDK choice preceding outbox design). Consumers serve shapes; shapes serve workloads — inverting the dependency models for tools, not for operations (framework upgrades reshaping tables; ODM migrations redefining audit; broker switches re-architecting relays). Decide shapes here (workload-derived, gauge-serving, bounded); map them there (adapters absorb tool friction — friction is information, not veto — stated six times because violated six times as often).

**Modern guidance** — the consumption map: repository seam and testability over operations tables → DesignPatterns 06 (assumes sound shapes underneath — repositories over claim-work tables, test doubles over flag tables); pub-sub consumption of relayed events (broker topology, consumer groups, SDK specifics) → DesignPatterns 06 §2.2 pub-sub (linked, not repeated); ODM/ORM mappings of audit/history/flag shapes → ORM track (textual forward — unbuilt); worker-framework specifics (BullMQ/Sidekiq/Celery topologies) → outside all tracks (tooling, not modeling — one line per DRY). When mapping friction appears, change mapping first, shape second, record which and why (ADR habit from [Domain 01 §4](<../../../01 Modeling Foundations and Mental Model/sections/4. Mentor checklist/4.1. Modeling checklist mentors insist on.md>)) — six domains, one habit, permanent value.

**Common confusion** — *"the worker framework needs its own tables — use theirs."* Framework-owned tables (framework-managed schema, versioned by the framework, migrated on upgrade — opaque to modeling review) vs application-owned job tables (this domain's shapes — reviewed, gauged, bounded). Framework tables serve framework upgrades (convenient, coupled — upgrade reshapes your operations data); application tables serve operations (reviewed, owned — coupled to nothing but workload). Prefer application-owned for domain-significant work (money-moving jobs, audited relays — owned shapes, reviewable); accept framework-owned for incidental work (cache warming, best-effort notifications — convenience wins where stakes are low). Stakes decide ownership — high stakes, owned tables; low stakes, convenience. Decide per workload, never by default.

**Performance note** — consumption performance (worker throughput, ODM hydration, SDK overhead) is the consumers' territory — owned outside this track, all six domains. But note the direction (sixth restatement, same truth): most consumption pathologies trace to unshaped operations tables (unbounded job tables the framework scans whole, unindexed flag tables read per request, mirrorless audit queried via full history scans). Good shaping here prevents performance work there — the cheapest worker optimization is a well-indexed job table; the cheapest ODM optimization is a bounded flag set. Shape first; consume cheaply.

**Mentor note** — teach the dependency direction as architecture (same sentence as Domain 01 §6, sixth and final stating): "the database outlives every framework." Worker frameworks turn over every 3–5 years; well-shaped operations tables serve for decades. Juniors internalizing this stop asking "how does tool X want it?" and start asking "what does operations need?" — the senior transition in one sentence, now in its operations translation, track complete. Six domains, one sentence, permanent career value.
