# 4.1. Document modeling checklist mentors insist on

## 1. Draw boundaries before documents (invariants and lifecycles first — JSON second)

**Definition** — the review's first pass: before any document shape is examined, the author states aggregates (boundaries + owning invariants) and lifecycles (born/archived/deleted with what). The JSON is reviewed *against* the boundaries — nesting inside them, references across them — never on its own elegance. Boundaries unstated → review stops; shapes without boundaries are decoration.

**What problem it solves** — JSON-first reviews approve beautiful documents with merged lifecycles (customers nested in orders — "but the fetch is so clean!") and reject sound references as "extra queries." Boundary-first ordering forces the structural verdict before the aesthetic one — the lifecycle merge gets caught while it's still a PR comment, not a GDPR-erasure archaeology project. Same discipline as [Domain 02 §4.1](<../../../02 Normalization Deep Dive/sections/4. Mentor checklist/4.1. Normalization review checklist mentors insist on.md>)'s dependencies-first ordering, document flavor.

**Modern guidance** — the review template, filled per aggregate: (a) boundary named + invariants listed ("order aggregate: total==Σlines, status ordered"); (b) lifecycle trio answered (born/archived/deleted with what); (c) cross-boundary connections listed as references (with extended-reference upgrades justified per [2.2](<../2. Embed or reference/2.2. Reference when apart.md>)'s three conditions). Authors fill it; reviewers verify boundaries before reading JSON. Empty template → request changes without reading further.

```json
// GOOD: the review artifact — boundaries stated, JSON judged against them.
// Aggregate: order {invariants: total==sum(lines), status ordered; lifecycle:
// born-with lines, archived-with lines, deleted-with lines}.
// Cross-boundary: customerId ref (customer lifecycle independent — outlives orders);
// product refs by sku + frozen snapshots (catalog independent).
// Verdict: boundaries sound — proceed to nesting/pattern review.
{ "review": "boundaries-first", "aggregates": ["order"], "references": ["customerId", "sku"] }
```

```json
// BAD: the review that admired JSON — boundaries never asked, merge never caught.
// "Clean document! Customer nested for locality, products nested for convenience.
// Ship it." (Customer lifecycle merged into orders — erasure archaeology scheduled.
// Products nested — reprice fan-out scheduled. The review praised the fetch and
// approved two time-bombs. Boundaries unasked, consequences unbilled.)
{ "review": "json-first", "verdict": "lgtm", "boundaries": "unexamined" }
```

**Common confusion** — *"small features don't need boundary ceremonies."* Small features grow: the MVP order document (customer nested "temporarily") becomes the production shape its successor inherits — temporary merges fossilize exactly like temporary copies ([Domain 02 §3.1](<../../../02 Normalization Deep Dive/sections/3. Judgment/3.1. Deliberate denormalization with priced trade-offs.md>)'s fossilization warning, document edition). Boundary statements cost three lines; fossilized merges cost migrations. Size of feature, size of ceremony — both small, both non-optional.

**Performance note** — boundary review is upstream performance work (same argument as dependency review): every lifecycle merge removed is fan-out writes avoided; every unjustified reference questioned is assembly examined. Aggregates reviewed this way rarely need heroic re-sharding later — their write units were reasoned about before their queries.

**Mentor note** — run the template on the team's *existing* collections as training (same exercise as 02/4.1): boundaries drawn retrospectively, merges found (there will be several), each finding converted to either a record ("known merge, tolerated until X") or a migration ticket. The findings advertise the template better than any mandate — "it found our two lifecycle merges in an hour."

## 2. Show the query catalog (no shape without its reads listed, counted, and freshness-stated)

**Definition** — the review's second pass: every document shape arrives with its query catalog ([1.2](<../1. Aggregates and access/1.2. Access patterns drive document shape.md>)) — reads listed with per-day frequencies, result shapes, and freshness contracts; writes listed with rates and concurrency. Reviewers check shape-against-catalog (dominant reads one-fetch? hot writes isolated? staleness contracts honored?) — shapes without catalogs are guesses, and guesses don't merge.

**What problem it solves** — uncatalogued shapes optimize imagined workloads (the "flexible" universal document serving no measured query) while missing real ones (the 800k/day screen assembling four fetches — nobody listed it, so nobody shaped for it). The catalog forces workload honesty: frequencies expose the dominant path (shaped first), freshness exposes copy eligibility (stated, not discovered), write rates expose vetoes (priced before nesting). Reviews without catalogs debate taste; reviews with catalogs check arithmetic.

**Modern guidance** — the catalog bar: every read entry needs all three (frequency, shape, freshness — missing freshness defaults to real-time, the strictest contract, until stated); every write entry needs rate + concurrency (single vs multi-writer decides vetoes). Top-five entries by frequency × cost must map to shapes explicitly ("Q1 → embedded lines, one fetch"). Stale entries flagged (catalogs older than the feature's last change get re-measured — "still 800k/day?" asked yearly). No catalog → request changes; partial catalog → review only the covered paths, flag the rest as unreviewed risk.

```json
// GOOD: shape traced to catalog — every nest and link answers to an entry.
// Q1 order-screen 800k/day realtime → embedded lines (one fetch). Q2 history 50k/day
// → subset (names without lines). W1 place-order 100k/day single-writer → atomic unit.
// W2 view-tick 1M/day multi-writer → veto: counters apart (no nest). Verdict: each
// shape line-traces to a catalog line — approve.
{ "catalogCoverage": "Q1→embed, Q2→subset, W1→atomic, W2→veto", "uncovered": "none" }
```

```json
// BAD: the catalog-free shape — nesting by intuition, priced by nobody.
// "Orders embed lines and customer chips; views nested for locality."
// Which read wants chips? (Unlisted.) What writes views, how often? (Unlisted.)
// Freshness of chips? (Unstated — dashboard or finance?) Every decision unexamined;
// the review can only judge JSON aesthetics. Verdict: request changes — catalog first.
{ "catalogCoverage": "none", "verdict": "aesthetics-only" }
```

**Common confusion** — *"catalogs are waterfall documentation that rots."* Catalogs rot only if unmaintained — same as schemas, tests, and every living artifact. The maintenance is trivial (re-measure top entries per feature change; yearly audit otherwise) and the alternative is designing blind. "Docs rot" argues for living documents with owners, not for designing without workload knowledge — the knowledge exists (production serves it daily); the catalog merely writes it down.

**Performance note** — catalog review *is* capacity review in miniature (1.2's transfer arithmetic applied per shape): reviewers summing top-five budgets validate the feature's data-plane cost before code ships. Shapes whose budgets exceed capacity get reshaped in review (cheap) instead of re-architected in production (dear). The catalog turns performance from a tuning phase into a modeling input — where it belongs.

**Mentor note** — teach juniors to *volunteer* catalogs (same lesson as 02/4.1's volunteered anomaly stories): "reads are X at Y/day realtime; writes Z at W/day multi-writer — shape follows." Volunteered catalogs signal senior thinking louder than correct JSON — they show the author models workload, not structure. Praise volunteered catalogs publicly; the team imitates what gets praised.

## 3. Price every nest and link (growth math and contention story per boundary)

**Definition** — the review's closing act: every embedded array carries its bound audit (cap, rate, 10× breaker — [2.1](<../2. Embed or reference/2.1. Embed when together.md>)); every reference carries its assembly cost (who fetches, how often — [1.2](<../1. Aggregates and access/1.2. Access patterns drive document shape.md>)); every copy carries its conditions (snapshot vs chip, sync policy — [2.1](<../2. Embed or reference/2.1. Embed when together.md>)/[2.2](<../2. Embed or reference/2.2. Reference when apart.md>)). Unpriced nests/links/copies don't merge — pricing is the review's exit criterion, not its decoration.

**What problem it solves** — the unpriced middle: nests without bounds (ceiling migrations scheduled by physics), references without assembly accounting (dominant screens quietly assembling), copies without policies (stale chips served as truth). Each is a cost adopted without a ledger — and ledgers are what separate design from drift. Pricing converts every structural choice into a budgeted line with a revisit trigger; unbudgeted lines compound into the "why is everything slow/fragile?" archaeology of year three.

**Modern guidance** — the pricing format, one line per nest/link/copy in the PR: "lines[]: cap ≤50 policy, ~3 avg, 10×→50KB — nest approved." / "customerId ref: assembled on profile screen only (5k/day) — bare ref approved." / "customerChip: name-only, rename events, nightly sync, dashboard-grade — chip approved." Plus the register habit (blessed structures listed, dated, revisit-triggered — same as [Domain 02 §4.1](<../../../02 Normalization Deep Dive/sections/4. Mentor checklist/4.1. Normalization review checklist mentors insist on.md>)'s blessing register, document edition). Yearly re-pricing is calendared — traffic shifts invalidate old prices silently otherwise.

```json
// GOOD: the priced boundary — every structure budgeted, every budget dated.
// lines[]: ≤50/order policy, ~3 avg, 10×→50KB — nest. views: 1M/day multi-writer —
// veto, apart (day-docs). customerChip: name-only, rename-rare, nightly sync — chip.
// versions: v3 current, v2 lazy-adapted (budget 2). Revisit: 2027-09 or 10× traffic.
// The boundary now has a birthday, a budget, and a review date.
{ "pricing": "complete", "revisit": "2027-09", "register": "ADR-034" }
```

```json
// BAD: the unpriced merge — "lgtm" on structures nobody budgeted.
// lines[]: unbounded? (Unasked.) views nested: writers? (Uncounted.) chips: sync?
// (Nonexistent.) versions: how many live? (Unknown.) The PR ships three time-bombs
// and a drift collection with a clean diff. "Temporary" nests fossilize; unpriced
// links surprise; unversioned shapes accumulate. The pricing would have cost sentences.
{ "pricing": "none", "verdict": "lgtm", "futures": "three incidents" }
```

**Common confusion** — *"pricing is bureaucracy that slows shipping."* (Asked and answered in 02/4.1; restated for arrivals landing here: one line per structure, written while context is hot, versus archaeology under incident pressure while cold.) Document structures fossilize faster than relational ones (no migration linter forces revisits; schemaless means silent) — pricing is *more* necessary here, not less. The sentence-per-structure habit is the cheapest insurance in document work.

**Performance note** — the register doubles as the scaling plan: yearly re-pricing ("still 800k/day? views now 5M/day — veto holding? chips synced?") catches structures whose rent outgrew savings before users notice. Priced structures with triggers turn document modeling from permanent fixtures into leased decisions — returned, renegotiated, or renewed on schedule.

**Mentor note** — model pricing on your own PRs first (same lesson as every checklist leaf in this track: authority's example teaches, mandates nag). A senior's priced nest ("cap ≤50, breaker at 500 — approved self") teaches more than a wiki on review culture. Praise priced structures ("great bound audit") louder than you praise clever ones — teams optimize for praised behavior, and clever unpriced nests are liabilities with admirers.
