# 2.1. Embed when together

## 1. Contained lifecycle embeds (lives and dies with the parent)

**Definition** — the first embed rule: nest data whose entire existence unfolds inside the parent's — created only with it, meaningless without it, deleted with it. Order lines, addresses on an account, preferences on a profile, items on an invoice. Contained lifecycle is the *strongest* embed signal because it eliminates every divergence failure at once: no orphan copies, no cross-document staleness, no independent evolution to track.

**What problem it solves** — the reference-everything reflex (often imported from relational habit): lines in their own collection joined per order read, addresses versioned apart from accounts — paying assembly cost per read for independence nobody needs. Referenced children of a contained lifecycle buy nothing (no independent readers, no independent writers) and cost a fetch per assembly plus consistency windows the single document would close. Nesting contained children is not denormalization — it is the lifecycle's honest shape.

**Modern guidance** — apply [1.1's lifecycle test](<../1. Aggregates and access/1.1. Aggregates the unit of document modeling.md>) per candidate child: born-with, archived-with, deleted-with the parent (2-of-3 "together" → embed). Then confirm no *independent* readers (nobody queries lines without their order) and no *independent* writers (nobody edits a line outside order context — returns/refunds edit the order). Lifecycle + access agreement → nest without further ceremony; either disagreeing → [2.2](<2.2. Reference when apart.md>).

```json
// GOOD: lines contained — born, read, archived, and deleted with the order.
// No independent line readers exist (lines render inside the order screen);
// no independent line writers exist (refunds edit the order aggregate).
// Single-document atomicity covers every mutation the business performs.
{
  "_id": "ord_1042",
  "status": "placed",
  "lines": [
    { "sku": "book-a", "qty": 2, "price": "9.99" },
    { "sku": "book-b", "qty": 1, "price": "24.50" }
  ],
  "total": "44.48"
}
```

```json
// BAD: contained children referenced apart — independence modeled where none exists.
// Every order screen assembles lines per order (fetch fan-out on the dominant read);
// every order write coordinates two collections (lines + orders — the race window
// single-document atomicity would close). Ceremony without a beneficiary.
{ "_id": "ord_1042", "status": "placed", "total": "44.48" }
// + lines collection: { "_id": "l1", "orderId": "ord_1042", "sku": "book-a", ... }
// Crash between order + line writes: the order exists with no lines — impossible nested.
```

**Common confusion** — *"embedding duplicates data."* Nesting contained children duplicates *nothing* — one fact, one home, inside its only parent. Duplication means the same fact in two places (products copied per order — independent lifecycle, genuinely duplicated). Lines inside their sole order are stored once. "Don't duplicate" argues against shared-truth copies, never against contained nesting — conflating them reference-splits data with a single natural home.

**Performance note** — contained nesting is the cheapest consistent shape available: one fetch serves the dominant read (no assembly — [1.2's one-screen rule](<../1. Aggregates and access/1.2. Access patterns drive document shape.md>) satisfied structurally), one write mutates the unit (atomic — no coordination). The performance case needs no numbers beyond the alternative's: every referenced child adds a round trip per read and a race window per write, permanently.

**Mentor note** — teach contained-lifecycle as the *default nest*: juniors should reach for embedding first for lines/items/addresses/preferences and justify references, not the reverse. The burden runs embed-first here (unlike keys, where surrogate-first ruled) because document stores optimize the nested unit — defaults follow the engine's grain, and the engine's grain is the document.

## 2. Bounded small and slow-growing (tens of elements, known ceiling — growth math before production)

**Definition** — the second embed rule: nest only lists with a known, small bound — tens of elements, stable domains (order lines per order, addresses per user, statuses per workflow). "Bounded" means a business rule caps it (max lines per order, max addresses per account) or the domain does (statuses are enumerable); "slow-growing" means additions are business events (new address), not system ticks (page views, sensor readings, log lines).

**What problem it solves** — unbounded embedding (activity feeds, event streams, comment threads nested "for locality") grows until the document hits the 16MB ceiling in production — the failure Databases 03 leaf 2.1 documents with growth math, linked not repeated here. The rule's value is *before* that math: boundedness is checkable at design time from business rules alone ("can an order hold 10,000 lines?" — the business says no → nest freely). Growth math confirms; boundedness decides.

**Modern guidance** — the bound audit per nested list: (a) name the cap (business rule or domain size — "≤50 lines/order policy," "≤5 addresses/account"); (b) name the growth rate (events per day per parent — 2 addresses/year vs 10k views/day); (c) name the breaker (what happens at 10× — still small, or ceiling math required?). Cap named + rate slow → embed. Either missing → measure ([Databases 03 ceiling math](<../../../../Databases/03 MongoDB Deep Dive/sections/2. Modeling and speed/2.1. Embed versus reference.md>)) or split ([bucket pattern in 3.1](<../3. Patterns and change/3.1. Schema patterns that scale.md>) for streams, [2.2](<2.2. Reference when apart.md>) for shared growth).

```json
// GOOD: bounded by policy, slow by domain — the audit passes in three lines.
// Cap: ≤50 lines/order (business policy). Rate: ~3 lines avg, set at placement.
// Breaker at 10×: 500 small lines ≈ 50KB — two orders of magnitude under ceiling.
{
  "_id": "ord_1042",
  "lines": [
    { "sku": "book-a", "qty": 2, "price": "9.99" },
    { "sku": "book-b", "qty": 1, "price": "24.50" }
  ]
}
```

```json
// BAD: unbounded by nature — views accumulate per tick, forever, in the read document.
// Rate: 1k/day and climbing. Breaker: 16MB in ~2 years at current growth — then a
// production migration under load (split streams out, backfill buckets, dual-write).
// The "locality" saved one fetch per read and bought a ceiling collision on schedule.
{
  "_id": "art_7",
  "title": "Sharding 101",
  "views": [
    { "at": "2026-09-01T10:00:00Z", "by": "u_1" },
    "... 400,000 more entries ..."
  ]
}
```

**Common confusion** — *"we'll cap it later if it grows."* Later means a live migration: new bucket/stream shape, backfill of history, dual-write cutover — under traffic, against the ceiling's deadline. Caps are design-time business questions ("max lines per order?") answered in an afternoon; migrations are production surgeries scheduled in quarters. Ask early; the business always has an answer (and if it doesn't, *that* is the signal — unbounded until proven otherwise).

**Performance note** — bounded embeds keep documents cache-resident and rewrites cheap (whole-document rewrite per update is trivial at KB sizes — the 1.2 veto's amplification math only bites at scale). The performance argument for nesting (one fetch, no assembly) holds exactly while boundedness does — growth erodes both (larger transfers, costlier rewrites). Boundedness isn't just safety; it's the precondition for the nest's performance case.

**Mentor note** — make juniors write the three-line bound audit (cap, rate, 10× breaker) beside every nested array in review. Three lines that take a minute and prevent ceiling migrations worth quarters. Authors who can't name the cap haven't asked the business — send them to ask, not to guess. The audit habit is capacity planning at its smallest useful scale.

## 3. Snapshot semantics intended (point-in-time copy is the correct duplication)

**Definition** — the third embed rule: nest copies whose *staleness is the point* — historical records that must freeze while the world moves on. Line items snapshot name+price at order time (repricing must not rewrite history); invoice copies freeze tax rules; audit entries freeze state. Snapshot nesting is duplication *by requirement*: the copy's divergence from current truth isn't rot — it's the record.

**What problem it solves** — the two symmetric history failures: *live references for history* (order lines pointing at the product catalog — reprice rewrites invoices, history becomes fiction) and *snapshot paranoia* (refusing all copies — every historical read joins against long-deleted catalog rows, or fails). Snapshots resolve it structurally: history nests frozen, catalog evolves referenced, and the two never confuse because their semantics differ by design (frozen vs current), not by accident.

**Modern guidance** — mark every nested copy with its semantics at write time: field names that say frozen (`priceAtOrder`, `nameAtOrder` — from 1.1's GOOD example — never bare `price` beside a live catalog), and a rule: snapshots are written once (at the event) and never updated (updates to "fix" history are a separate audited event, not a mutation). Review check: any nested field that mirrors a live entity without an `At/Event` marker fails — ambiguous copies become wrong copies within a year.

```json
// GOOD: frozen by naming — history reads need no catalog, catalog evolution can't touch it.
// priceAtOrder/nameAtOrder: written once at placement, never updated. The product
// catalog holds current truth (referenced by sku for navigation); the order holds
// history. Both correct simultaneously — semantics differ by construction.
{
  "_id": "ord_1042",
  "lines": [
    { "sku": "book-a", "nameAtOrder": "Book A", "priceAtOrder": "9.99", "qty": 2 }
  ],
  "total": "44.48"
}
```

```json
// BAD: live-linked history — the past rewrites whenever the catalog moves.
// Reprice book-a to 12.99: every historical order now reports fiction (revenue
// restated upward by a catalog edit!). Or the mirror failure: catalog row deleted,
// historical lines dangle (sku points nowhere — history unreadable without archives).
{
  "_id": "ord_1042",
  "lines": [{ "sku": "book-a", "qty": 2 }]
}
// + products collection (CURRENT truth): { "sku": "book-a", "price": "12.99" }
// Order total 19.98 vs recomputed 25.98 — which is true? Neither, reliably.
```

**Common confusion** — *"snapshots violate single source of truth."* Truth is temporal: current price (catalog — one home) and historical price (order snapshot — one home *per event*) are different facts about different times. Single-source means one home per fact, not one home per value-string. "9.99" appears twice (catalog history + order snapshot) as two facts — the confusion dissolves once time is part of the fact's identity.

**Performance note** — snapshots make historical reads self-contained (no catalog join for invoices, reports, audits — the dominant history access is one fetch). The cost is storage (copies per event — small fields, priced once) against the alternative's join load per historical read plus the integrity risk. History reads outnumber history writes by orders of magnitude — snapshots are the rare duplication that pays on both correctness and speed.

**Mentor note** — teach the `At/Event` naming convention as team law with one counterexample kept handy (the repriced-invoice incident, real or constructed). Juniors adopt frozen-naming instantly once they've seen history rewritten by a catalog edit — the story does what the rule cannot: make staleness-as-correctness *feel* right. Keep the story in onboarding.
