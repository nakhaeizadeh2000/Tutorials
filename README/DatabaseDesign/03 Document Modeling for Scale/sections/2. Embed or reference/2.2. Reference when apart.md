# 2.2. Reference when apart

## 1. Shared truth links (one catalog, many readers — updates propagate by reading current)

**Definition** — the first reference rule: entities read by many aggregates and owned by one writer live in their own collection, linked by id. Product catalogs, user profiles, tax tables, configuration — *shared truth* (one current version, many observers). Updates happen once at the source; every reference reads current on fetch. No copies, no fan-out, no divergence — by construction rather than by maintenance.

**What problem it solves** — the duplicated-catalog failure: product details nested per order (2.1's BAD shape) turn every reprice into a multi-million-document rewrite — partial failures leave price soup (same sku, three prices, all "current"), and no query can answer "the price" without choosing a copy. References collapse the question: the catalog holds the price; orders hold history snapshots ([2.1](<2.1. Embed when together.md>)) plus the sku link. Current-truth reads assemble; historical reads don't need to.

**Modern guidance** — the shared-truth test per candidate: *readers many, writers one* (catalog team owns products; every order reads them) → own collection + bare id references. Confirm no dominant screen needs the shared fields in one fetch ([1.2](<../1. Aggregates and access/1.2. Access patterns drive document shape.md>)) — if one does, extended reference (third promise), not embedding. Confirm the link direction: dependents hold the id (order → product), never the reverse (products don't list their orders — unbounded by definition).

```json
// GOOD: one catalog, linked — reprice is one write, every reader current.
// Products owned by the catalog team; orders reference by sku; history snapshots
// frozen per line (2.1). Three lifecycles, three homes, zero fan-out.
{ "_id": "prod_book-a", "sku": "book-a", "name": "Book A", "price": "12.99", "active": true }
{ "_id": "ord_1042", "lines": [{ "sku": "book-a", "priceAtOrder": "9.99", "qty": 2 }] }
```

```json
// BAD: shared truth nested per reader — the catalog edit that touches millions.
// Reprice book-a: rewrite every order containing it (millions of documents, partial
// failure = price soup). Discontinue it: history or catalog? Both break. The nest
// saved one assembly per read and billed unbounded fan-out per write — backwards
// at any reader:writer ratio above trivial.
{
  "_id": "ord_1042",
  "lines": [{ "product": { "sku": "book-a", "name": "Book A", "price": "9.99" }, "qty": 2 }]
}
```

**Common confusion** — *"references are just foreign keys without enforcement."* Structurally similar, semantically poorer — and that's honest: document stores don't enforce cross-document integrity (no FK constraints across collections in the relational sense). The reference is a *navigational* contract maintained by writers, not a *guarantee* maintained by the engine. Design accordingly: tolerate dangling links (deleted products referenced by history — expected, handled by snapshot fields), never assume them away. The engine's silence is a design input, not an oversight.

**Performance note** — reference assembly costs one indexed id lookup per link (fast, point queries — the cheap join shape) against nested copies' zero-lookup reads. The comparison that matters is write-side: one catalog write vs N-copy fan-out. Reader:writer ratios decide — 1000:1 read-heavy with stable truth still favors references (cheap assembly, zero maintenance); extended reference (third promise) trims the assembly where a dominant screen demands it. Count both sides before choosing.

**Mentor note** — teach "readers many, writers one" as the reference reflex: juniors chanting it place catalogs, profiles, and configs correctly on the first try. The failure to correct is the reverse reflex ("nest everything read together") applied to shared truth — diagnose by asking "who else reads this, and who writes it?" Two questions, correct placement, every time.

## 2. Unbounded or independently hot (streams, threads, counters — growth without ceiling)

**Definition** — the second reference rule: data that grows without bound (event streams, comment threads, audit logs) or burns hot independently (counters, live tallies, session state) lives outside the parent aggregate — in its own documents (buckets, [3.1](<../3. Patterns and change/3.1. Schema patterns that scale.md>)) or its own collection, linked back by parent id. The parent stays bounded and cache-cool; the growth lives where growth is cheap (appends, not rewrites).

**What problem it solves** — the two embedding time-bombs from [1.2](<../1. Aggregates and access/1.2. Access patterns drive document shape.md>) and [2.1](<2.1. Embed when together.md>): *growth bombs* (nested streams swelling toward 16MB — migration under ceiling pressure) and *heat bombs* (hot counters nested in the system's most-read document — contention serializing every concurrent writer, rewrite amplification per tick). Both share a root cause: coupling an unbounded/hot lifecycle to a bounded/cool aggregate. Separation defuses both structurally — no policy, no monitoring threshold, no heroics.

**Modern guidance** — the separation shapes: *streams* → bucket documents keyed by (parent, window) with parent id back-link ([3.1](<../3. Patterns and change/3.1. Schema patterns that scale.md>)'s bucket pattern); *threads* (comments, replies) → own documents with parent id (paginated independently — the screen never wants all 40k); *counters* → separate counter documents per (entity, window) (daily granularity from 1.2's GOOD example). Parent holds at most a summary (count, latest-N cache) with stated staleness — never the stream itself.

```json
// GOOD: growth lives apart — parent bounded, stream append-only, heat isolated.
// Article: stable, cache-hot, rewritten on edits only. Views: per-day documents,
// appended/incremented freely — 1M views/day touches small day-documents, never
// the article body. Comments: own documents, paginated — the screen fetches page 1,
// not all 40,000.
{ "_id": "art_7", "title": "Sharding 101", "body": "...", "commentCount": 40213 }
{ "_id": "art_7_views_2026-09-28", "articleId": "art_7", "count": 1042031 }
{ "_id": "c_9001", "articleId": "art_7", "authorId": "u_9", "text": "..." }
```

```json
// BAD: growth and heat nested in the parent — two time-bombs, one document.
// Views array: +1k entries/day toward the ceiling (migration scheduled by physics).
// views counter field: every view rewrites the article (contention + amplification).
// comments array: 40k entries shipped to every reader of the title. The "simple"
// single document concentrates every scaling failure the domain contains.
{
  "_id": "art_7",
  "title": "Sharding 101",
  "body": "...",
  "views": 1042031,
  "viewLog": ["... 400,000 entries ..."],
  "comments": ["... 40,000 entries ..."]
}
```

**Common confusion** — *"separate documents mean losing atomicity."* Correct — and priced: cross-document writes aren't atomic (single-document atomicity is the aggregate's superpower, [1.1](<../1. Aggregates and access/1.1. Aggregates the unit of document modeling.md>)). The separation is chosen *because* the data doesn't need joint atomicity (views don't need transactional consistency with the article body — approximate counts are fine; comments don't need atomicity with the article — orphans on concurrent delete are handled by policy). Atomicity surrendered where unneeded is simplification, not loss — surrender it where needed and it's a bug. Know which.

**Performance note** — heat isolation is queuing theory again ([1.2](<../1. Aggregates and access/1.2. Access patterns drive document shape.md>)): concurrent increments to one document serialize (throughput = 1/write-latency); per-day counter documents parallelize across days and shard keys. Growth isolation is transfer economics:bounded parents stay cache-resident (KBs per fetch); stream-bearing parents bloat every read (MBs per title render). Separate early — the split is cheap at design, dear under ceiling pressure.

**Mentor note** — the time-bomb framing teaches urgency honestly: "this nest has a date with the ceiling — name it." Juniors asked to date the collision (growth rate → 16MB ÷ rate = months remaining) either prove boundedness or discover unboundedness themselves. Dating collisions converts abstract growth warnings into calendar events — and calendar events get prioritized.

## 3. Extended reference for the middle (copy small stable fields, link the rest)

**Definition** — the extended reference pattern (official MongoDB pattern): store the id *plus* a small set of frequently-read, rarely-changed fields from the referenced entity — `customerId` + `customerName`, `sku` + `productName`. Reads get one-fetch locality for the common case; the link preserves access to full current truth; updates to copied fields propagate by policy (or are accepted stale where semantics allow).

**What problem it solves** — the bare-reference tax on dominant screens (order list needing customer names — N+1 assembly per render) versus the full-embed fan-out (nesting whole customers — lifecycle merge). Extended reference is the engineered middle: copy *only* what the screen renders (name, never email/city/preferences), link the rest. The copy is small (bounded staleness blast radius), stable (name changes are rare events, not ticks), and explicitly second-class (readers needing truth follow the id).

**Modern guidance** — three conditions, all required: (a) *small* (1–3 scalar fields — chips, not profiles); (b) *stable* (changes are rare business events — renames, reprices — never ticks or streams); (c) *tolerant* (stale copies acceptable within a stated window, or refreshed by named policy — change-data-capture job, write-through hook, periodic sync). Document all three per extended reference; violate any → bare reference (stability/tolerance fail) or rethink the boundary (smallness fails — the "chip" is a profile in disguise).

```json
// GOOD: the chip — name for the screen, id for the truth, policy for the gap.
// Copied: name only (small, stable — renames are rare events).
// Policy: rename propagates via nightly sync job (tolerance: 24h, dashboard-grade;
// profile screen always reads the customer aggregate — truth one hop away).
{
  "_id": "ord_1042",
  "customerChip": { "customerId": "cus_101", "name": "Ann" },
  "lines": [{ "sku": "book-a", "qty": 2, "price": "9.99" }]
}
```

```json
// BAD: the chip grown into a profile — "extended" without bound, stale without policy.
// Email, city, tier, preferences copied (not small); email changes often (not stable);
// no sync exists (not tolerated — downstream fraud checks read the copy as truth!).
// The middle ground without conditions is the worst of both: fan-out on change AND
// staleness presented as fact. Conditions or bare reference — no middle without rules.
{
  "_id": "ord_1042",
  "customer": {
    "customerId": "cus_101",
    "name": "Ann",
    "email": "a@x.io",
    "city": "Berlin",
    "tier": "gold",
    "preferences": { "...": "..." }
  }
}
```

**Common confusion** — *extended reference versus snapshot (2.1): same thing?* Mirror images: snapshots freeze history (must *not* update — divergence is correctness); extended references cache current truth (must update *eventually* — divergence is tolerated staleness with a policy). Same shape (copied fields + id), opposite maintenance (never touch vs sync on schedule), opposite failure (updating a snapshot destroys history; never syncing a chip serves fiction). Name which one every copy is — confusion between them is a bug class.

**Performance note** — chips eliminate the dominant assembly (one fetch for the list screen — the 800k/day path from 1.2's catalog) at the price of a sync job (rare-event fan-out — renames touch thousands of chips, nightly, offline). The economics mirror [Domain 02 §3.1](<../../../02 Normalization Deep Dive/sections/3. Judgment/3.1. Deliberate denormalization with priced trade-offs.md>)'s copy pricing (read savings × frequency vs write rent × rarity) — same ledger, document store. Price per chip; drop chips whose screens cooled.

**Mentor note** — teach the snapshot-vs-chip distinction as *the* document-modeling judgment call: same shape, opposite maintenance, and choosing wrong fails silently (stale chip served as history, frozen snapshot "synced" into fiction). Juniors who can classify every copied field as snapshot or chip have mastered document duplication — which is most of document modeling's hard part.
