# 1.1. Aggregates the unit of document modeling

## 1. Boundaries are consistency decisions (what must change atomically belongs together)

**Definition** — an aggregate is the consistency boundary: the cluster of data that must change as one unit or not at all. The boundary is drawn by *invariants* (rules spanning multiple pieces — "order total always equals the sum of its lines," "a booking never exceeds capacity"), not by topic similarity. Everything inside one aggregate updates in a single atomic write; everything across aggregates is eventually consistent by design.

**What problem it solves / history** — relational modeling taught entity-first thinking (tables per noun, joins at read time), and document beginners import it directly: seventeen collections mirroring seventeen tables, assembled per screen with application joins — N+1 in document clothing, the exact failure Databases 03 leaf 2.1 diagnoses. Aggregates invert the question: not "what things exist?" but "what must stay consistent together?" The answer is usually *fewer, larger* units than the entity list suggests — and each one becomes a document (or a small document family).

**Modern guidance** — find aggregates by hunting invariants: list every rule of the form "X must always agree with Y." Each invariant's span is an aggregate candidate (total↔lines → order aggregate; balance↔ledger → account aggregate). Rules that span candidates ("a customer's credit limit spans their orders") are cross-aggregate by definition — they get sagas, checks, or tolerance, never a bigger document. One invariant, one boundary, one write unit.

```json
// GOOD: the order aggregate — every invariant inside changes in one atomic write.
// Invariants: total == sum(lines); status transitions are ordered; lines never
// outlive the order. All three hold trivially: one document, one write.
{
  "_id": "ord_1042",
  "customerId": "cus_101",
  "status": "placed",
  "lines": [
    { "sku": "book-a", "qty": 2, "price": "9.99" },
    { "sku": "book-b", "qty": 1, "price": "24.50" }
  ],
  "total": "44.48",
  "placedAt": "2026-09-28T10:00:00Z"
}
```

```json
// BAD: the same data split across three collections with no invariant owner.
// Total vs lines vs status now agree by convention — every writer (app, backfill,
// console) must maintain what one document would guarantee. The "flexibility"
// of separate collections is three race windows wearing a schema.
{ "_id": "ord_1042", "customerId": "cus_101", "status": "placed" }
// + order_lines collection: { "orderId": "ord_1042", "sku": "book-a", ... }
// + order_totals collection: { "orderId": "ord_1042", "total": "44.48" }
// Crash between the three writes: status placed, lines missing, total stale.
```

**Common confusion** — *"aggregate" means "big document."* Size is a side effect; consistency is the criterion. A two-field document can be an aggregate (a feature flag with its rollout rules — one invariant, one unit); a 15MB document can span three aggregates glued by topic (user + their orders + their support tickets — three lifecycles, three writers, one rewrite tax). Judge boundaries by invariants, measure size separately ([1.2](<1.2. Access patterns drive document shape.md>) prices size; Databases 03 leaf 2.1 owns the ceiling math).

**Performance note** — aggregate writes are single-document atomic (one write unit, no coordination) — the cheapest consistent write a distributed store offers. Cross-aggregate writes need application coordination (sagas, outbox, reconciliation jobs — Domain 06 forward) at 10–100x the complexity. Every invariant placed *inside* a boundary is coordination avoided forever; every invariant stranded *across* boundaries is a distributed-systems problem adopted permanently. Boundaries are the highest-leverage performance decision in document modeling — made before any query runs.

**Mentor note** — teach invariants before JSON: hand juniors a feature spec and ask "what must always agree?" before any document is drawn. Juniors list entities; redirect to rules ("total matches lines — where does that rule *live*?"). Three such exercises and juniors stop drawing collections first — the single most valuable habit transfer from relational keys ([Domain 01](<../../../01 Modeling Foundations and Mental Model/sections/2. Identity and keys/2.1. Surrogate versus natural keys.md>)'s "constraints are the design" is this leaf's ancestor).

## 2. Lifecycle tests the boundary (created, archived, and deleted together — one aggregate)

**Definition** — the lifecycle test: if A cannot be born without B, cannot be meaningfully archived without B, and must die with B, they share an aggregate. Order lines fail independence on all three (no orphan lines, archive with the order, cascade on delete); products pass it (exist before any order, survive every order, delete on catalog policy alone). Lifecycle is the observable shadow of invariants — easier to check in a review than abstract rules.

**What problem it solves** — invariant-hunting is abstract for juniors; lifecycle questions are concrete ("can a line exist without its order?" — no, everywhere, always). The test converts boundary disputes into answerable questions with business stakeholders: "when we delete a user, what must vanish?" (sessions, preferences — same aggregate family) "and what must survive?" (their orders — tax law says so — different aggregate). Stakeholders answer lifecycle fluently; the answers draw boundaries for free.

**Modern guidance** — run the three questions per candidate child: *born together?* (line created only within an order → inside); *archived together?* (old orders archive with lines → inside); *deleted together?* (order purge takes lines → inside). Two of three "together" → embed inside the aggregate; two of three "apart" → separate aggregate with a reference. The 2-of-3 rule handles the awkward middle (reviews live forever but die with the product? — born-apart, archived-mixed, deleted-together → separate aggregate, reference, cascade policy named).

```json
// GOOD: lines live and die with the order — one lifecycle, one document family.
// Archive policy: "orders older than 7 years move to cold storage WITH their lines."
// Delete policy: "order purge deletes lines." No orphan lines exist by construction.
{
  "_id": "ord_1043",
  "customerId": "cus_102",
  "status": "fulfilled",
  "lines": [{ "sku": "book-c", "qty": 1, "price": "12.00" }],
  "total": "12.00"
}
```

```json
// BAD: products nested per order — independent lifecycle entombed in another aggregate.
// Product "book-c" repriced: N order documents rewrite (stale copies diverge).
// Product discontinued: history rewrites or detaches — both wrong (history must freeze,
// catalog must evolve — one shape cannot do both). Lifecycle mismatch, guaranteed rot.
{
  "_id": "ord_1044",
  "lines": [{ "product": { "sku": "book-c", "name": "Foo", "price": "12.00" }, "qty": 1 }]
}
```

**Common confusion** — *"cascade delete is a database feature, so boundaries don't matter."* Cascades implement a boundary decision; they don't make it. The decision ("lines die with orders; orders don't die with customers") precedes the mechanism (cascade, TTL, purge job) — and different mechanisms serve different lifecycles (legal hold ≠ cascade). Lifecycle first, mechanism second, always.

**Performance note** — lifecycle-aligned aggregates make archival trivial (move/delete whole documents, no orphan scans) and keep working sets hot (live orders without tombstoned children bloating them). Lifecycle-mismatched nesting bloats every read (dead product data shipped per order) and every write (repricing fans out). Archive/delete economics are modeled at design time or paid at 3 a.m. — the lifecycle test is capacity planning in disguise (Domain 05 forward).

**Mentor note** — the stakeholder-interview drill: juniors practice asking "born/archived/deleted with what?" until the three questions feel natural. The skill transfers beyond documents (relational cascade policies, event retention, cache invalidation all answer lifecycle questions). Review boundary PRs by re-asking the trio — authors who answer instantly modeled well; hesitation locates the unexamined boundary.

## 3. Reference across aggregates (links between consistency units, never nesting across them)

**Definition** — the boundary rule: aggregates connect by *reference* (store the other's id), never by nesting. `order.customerId` links aggregates; embedding the customer inside the order merges lifecycles that diverge (customers outlive orders; repricing/reprofiling fans out). Nesting is for *inside* a boundary; references are for *between* them — the rule has no exceptions, only patterns that make references cheaper ([2.2](<../2. Embed or reference/2.2. Reference when apart.md>)'s extended reference).

**What problem it solves** — theOffline seductive merge: "one fetch gets everything!" nests customers into orders, products into lines, authors into books — and each merge couples an independent lifecycle to someone else's write path. The failures arrive slowly then suddenly: profile edits rewrite history (or fork it inconsistently), catalog reprice touches millions of documents, a GDPR erasure must hunt embedded copies across collections. References keep each aggregate's writers to its own owners — blast radius contained by construction.

**Modern guidance** — default every cross-aggregate connection to a bare id reference; upgrade to extended reference (small stable copied fields + id) only where reads prove the need ([2.2](<../2. Embed or reference/2.2. Reference when apart.md>) prices it). Name the owning side: the reference lives on the dependent (order holds customerId — orders need customers, not vice versa). Enforce at review: any nested object with an independent lifecycle fails — split to reference, no matter how convenient the fetch.

```json
// GOOD: aggregates linked, lifecycles independent — each writer owns its documents.
// Order references the customer (id only); product referenced by sku; history frozen
// per line (name+price snapshot — snapshot semantics, THIRD promise of 2.1, intended).
{
  "_id": "ord_1045",
  "customerId": "cus_101",
  "lines": [
    { "sku": "book-a", "nameAtOrder": "Book A", "priceAtOrder": "9.99", "qty": 2 }
  ],
  "total": "19.98"
}
// Customer reprofiles: zero order documents touched. Product repriced: history intact.
```

```json
// BAD: the customer nested inside the order — two lifecycles, one document.
// cus_101 changes email: rewrite every historical order (or fork: profile says X,
// invoices say Y — pick your incident). GDPR erasure: hunt copies across millions
// of order documents. The "convenient fetch" bills monthly, forever.
{
  "_id": "ord_1046",
  "customer": { "id": "cus_101", "email": "a@x.io", "city": "Berlin" },
  "lines": [{ "sku": "book-a", "qty": 2 }]
}
```

**Common confusion** — *"but the join is expensive — $lookup on every order read!"* The read cost is real and priced in [1.2](<1.2. Access patterns drive document shape.md>) (dominant reads earn extended-reference copies; rare reads accept assembly). What's *not* acceptable is deleting the boundary to dodge the join — that's trading a measured read cost for an unmeasured consistency liability. Price the join; keep the boundary.

**Performance note** — reference reads cost assembly (application join or `$lookup` — Databases 03 mechanics), but reference *writes* stay O(1) per aggregate while nested-copy writes fan out O(N) per lifecycle event. Read-heavy + stable-reference topologies favor assembly (reads are indexed id lookups — fast); write-heavy shared entities *demand* references (fan-out is unbounded). Count writers per entity before counting readers — writers decide boundaries, readers shape within them.

**Mentor note** — the blast-radius question ends nesting debates: "who rewrites how many documents when this changes?" Juniors defending a nest must answer with a number; numbers above one aggregate's size lose. Teach the question as the review closer for every embedded object — asked three times, it becomes the author's self-check before review exists.
