# 1.2. Access patterns drive document shape

## 1. List queries before drawing shapes (frequency, shape, and freshness per query)

**Definition** — the query catalog: every read and write the feature needs, each annotated with frequency (per day), result shape (what fields, what nesting), and freshness (real-time vs minutes-old). The catalog is the schema's spec — documents are shaped to serve it, and shapes without a catalog entry are guesses. No catalog, no schema; the rule is absolute for new aggregates, advisory for trivial ones.

**What problem it solves / history** — schema-first document design (entities nested by topic elegance) produces shapes no query wants: the profile document embedding order history because "users have orders" — while the only reader is the auth service (needs id + role) and orders render elsewhere (needs the aggregate from [1.1](<1.1. Aggregates the unit of document modeling.md>)). Every field fetched-but-unused is transfer tax; every assembly-per-read is latency chosen blindly. The catalog makes both visible before the first document exists.

**Modern guidance** — the catalog format, per query: *name, frequency, fields, freshness, writer alongside*. Five to fifteen entries cover most features; rank by frequency × cost (a 1M/day read shapes nesting; a 10/day admin export accepts assembly). Freshness splits truth from copies (real-time → aggregate read; minutes-old → precomputed copy, [Domain 02 §3.1](<../../../02 Normalization Deep Dive/sections/3. Judgment/3.1. Deliberate denormalization with priced trade-offs.md>)'s record discipline applies unchanged). Revisit per feature — catalogs rot as features grow, and rot shows as "why is this embedded?" mysteries.

```json
// GOOD: the catalog first — three entries that shape everything below.
// Q1 order-screen: 800k/day, needs order+lines+total, real-time → embed lines (done in 1.1).
// Q2 customer-history: 50k/day, needs order ids+totals+dates (NOT lines) → subset pattern (3.1).
// Q3 dashboard-revenue: 1k/day, needs daily sums, 5-min stale OK → computed pattern (3.1).
// W1 place-order: 100k/day, writes one aggregate → single-document atomic, no contention.
// The shapes below are DERIVED — each line traces to a catalog entry.
{
  "catalog": [
    { "q": "Q1 order-screen", "freqPerDay": 800000, "freshness": "realtime", "shape": "aggregate" },
    { "q": "Q2 customer-history", "freqPerDay": 50000, "freshness": "realtime", "shape": "subset" },
    { "q": "Q3 dashboard-revenue", "freqPerDay": 1000, "freshness": "5min", "shape": "computed" },
    { "q": "W1 place-order", "freqPerDay": 100000, "freshness": "realtime", "shape": "one-aggregate-write" }
  ]
}
```

```json
// BAD: shapes without a catalog — nesting by topic, priced by nobody.
// "Users have orders, orders have lines, lines reference products — nest it all?"
// Which read wants the user WITH their full order history? (None — auth wants id+role.)
// Which write tolerates the rewrite? (None — repricing fans out.) Every nest is a guess;
// production will grade guesses as incidents. The document below serves no listed query
// because no query was ever listed.
{ "_id": "cus_101", "profile": "...", "orderHistory": ["<2MB of nobody's-read>" ] }
```

**Common confusion** — *"access-first means reads dictate everything."* Reads dominate shaping (they outnumber writes 10–1000×), but writes *veto* (third promise): a shape perfect for reads that serializes all writers is a denial-of-service designed in. Catalog both, rank reads first, veto by writes — the ordering matters and the veto is real.

**Performance note** — the catalog is a load model in miniature: frequency × document size = transfer budget per query; freshness = copy eligibility. Summing the top five entries estimates the feature's data-plane cost before code exists — the cheapest capacity conversation a team can have (Domain 05 forward formalizes it). Catalogs that skip numbers ("frequent," "occasional") produce shapes with the same precision as their inputs — demand per-day figures.

**Mentor note** — make "show me the catalog" the first review question for every document shape, asked before any JSON is read. Juniors learn that shapes are downstream of workload; seniors who skip catalogs get the same question regardless of rank. Two reviews of this form and authors arrive with catalogs pre-written — the review teaches the method by repetition.

## 2. One screen one fetch (the dominant read path decides nesting)

**Definition** — the shaping heuristic: the query serving the dominant screen (highest frequency × user visibility) should complete in one document fetch. Nest what that screen renders together; accept assembly (second fetch, `$lookup`) for everything else. "One screen" is literal — sketch the UI, circle the data region, that region is the fetch unit.

**What problem it solves** — fetch fan-out per render (order screen assembling order + lines + products + customer across four round trips — latency additive per hop, failure modes multiplicative). Each hop adds p99; each hop can fail independently; each hop needs its own cache story. One-fetch screens have one latency number and one failure mode — operability follows shape. The heuristic converts "fast page" from a tuning goal into a modeling outcome.

**Modern guidance** — sketch-first procedure: (1) draw the screen's data regions; (2) map each region to aggregates ([1.1](<1.1. Aggregates the unit of document modeling.md>)) — one region per aggregate is the honest case; (3) regions sharing one aggregate → nest (already inside); regions spanning aggregates → extended reference or second fetch, chosen by frequency ([2.2](<../2. Embed or reference/2.2. Reference when apart.md>)). Never merge aggregates to satisfy the sketch — the sketch shapes *within* boundaries, never across them.

```json
// GOOD: the order screen's fetch — one aggregate, everything the screen renders.
// Regions: header (status/total) + lines table + customer chip (name only — extended
// reference copied at order time per snapshot rules). One fetch, one latency number.
{
  "_id": "ord_1042",
  "status": "placed",
  "total": "44.48",
  "customerChip": { "customerId": "cus_101", "name": "Ann" },
  "lines": [
    { "sku": "book-a", "qty": 2, "price": "9.99" },
    { "sku": "book-b", "qty": 1, "price": "24.50" }
  ]
}
```

```json
// BAD: the screen assembled from four fetches — latency additive, failures multiplicative.
// fetch order → fetch lines (orderId) → fetch each product (N skus) → fetch customer.
// p99 = p99(order) + p99(lines) + max(p99(products)) + p99(customer) — and any hop's
// cache miss cascades. The "flexible" normalized-documents shape bills per render,
// forever, at the highest-traffic screen in the system.
{ "_id": "ord_1042", "customerId": "cus_101", "lineIds": ["l1", "l2"] }
```

**Common confusion** — *"one fetch means embed everything the screen shows."* The screen shows customer data — but the customer *aggregate* stays referenced (boundary rule from 1.1); the screen gets a *chip* (extended reference) or a second fetch, not a nested customer. One-fetch serves regions, not aggregates — chips and subsets ([3.1](<../3. Patterns and change/3.1. Schema patterns that scale.md>)) bridge the gap without merging lifecycles. Sketch within boundaries.

**Performance note** — quantify the heuristic once: four-hop assembly at 2ms/hop median is 8ms median but ~25ms p99 (tail multiplication — independent failure/timing per hop); one 4KB fetch is ~2ms at both. At 800k/day, the tail difference is the support-ticket difference. One-fetch isn't dogma (rare screens assemble fine) — it's arithmetic applied to the dominant path.

**Mentor note** — the screen-sketch exercise is the fastest document-modeling lesson: juniors sketching UIs before JSON produce access-shaped documents on the first try. Keep a "screens first" wall rule for one quarter — teams internalize it, then the rule can retire. The sketch habit outlives every specific schema decision.

## 3. Write paths veto reads (hot writers split what readers would nest)

**Definition** — the veto rule: where a write path's contention or volume breaks a read-shaped nest, the writes win and readers accept assembly. Concretely: counters incremented thousands of times per second don't nest in the read aggregate (every increment rewrites it — contention + write amplification); unbounded event streams don't embed (growth without ceiling); multi-writer shared subdocuments split (concurrent edits conflict per document). Reads propose, writes dispose.

**What problem it solves** — read-shaped disasters: the "helpful" embedded view-counter turning every page view into a full-document rewrite (contention serializes readers' writes, p99 explodes under load); the embedded activity feed growing 10k entries/day (document swells, then hits the ceiling in production — Databases 03 leaf 2.1's growth math, linked); the shared cart edited by two devices (last-writer-wins eats items). Each nested-read convenience adopted a write liability nobody priced — the veto prices it at design time.

**Modern guidance** — audit every nest against its write path: *frequency* (writes/sec per document — hundreds+ splits counters out), *concurrency* (multiple writers per document — devices, services, users — splits shared state out), *growth* (unbounded appends — splits streams out). The split shapes: counters → separate counter documents (or computed rollups, [3.1](<../3. Patterns and change/3.1. Schema patterns that scale.md>)); streams → bucket pattern ([3.1](<../3. Patterns and change/3.1. Schema patterns that scale.md>)); shared edits → own aggregate with references. Readers of the split data accept a second fetch — the catalog ([promise 1](#1-list-queries-before-drawing-shapes-frequency-shape-and-freshness-per-query)) records which reads pay it.

```json
// GOOD: the veto applied — page reads the article aggregate; views live apart.
// Article document: read-shaped, rarely rewritten (edits are editorial events).
// View counter: separate document, incremented freely — zero contention with reads,
// zero rewrite of the article body per view. Q-screen assembles two fetches for the
// one screen that shows both; every other reader pays nothing.
{ "_id": "art_7", "title": "Sharding 101", "body": "...", "authorId": "u_3" }
{ "_id": "art_7_views", "articleId": "art_7", "count": 1042031, "day": "2026-09-28" }
```

```json
// BAD: the veto ignored — counter nested in the read aggregate.
// Every view rewrites the whole article document: write amplification (KBs per +1),
// write contention (concurrent views serialize on one document), cache churn
// (the hot read document invalidated per view). At 1k views/sec the "simple nest"
// is a self-inflicted write bottleneck on the system's most-read document.
{ "_id": "art_7", "title": "Sharding 101", "body": "...", "views": 1042031 }
```

**Common confusion** — *"writes vetoing reads means pessimizing the common case."* The common case is *reads of rarely-written data* (articles, orders, profiles) — nesting stands there. The veto fires only where writes are hot, concurrent, or unbounded — a minority of nests with majority of incident potential. Vetoes are rare, surgical, and load-bearing: exactly the decisions worth a senior's attention.

**Performance note** — contention math, briefly: single-document writes serialize (one writer at a time per document — lock + oplog ordering); N concurrent increments to one document queue, latency grows linearly with concurrency, throughput caps at single-write latency. Separate counter documents (or sharded counters — Domain 05 forward) parallelize. The veto is queuing theory applied at design time — measure write concurrency per document the way you'd measure queue depth.

**Mentor note** — teach "count the writers" alongside "draw the screen": every nest gets a writer count written beside it in review. Juniors count readers naturally (screens are visible); writers hide (jobs, devices, webhooks, other services). The review question "who writes this, how often, concurrently?" surfaces the hidden half — asked per nest, it becomes the author's pre-review habit within weeks.
