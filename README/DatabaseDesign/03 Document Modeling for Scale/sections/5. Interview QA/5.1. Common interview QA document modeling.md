# 5.1. Common interview QA document modeling

## 1. Design a document schema live (access-first narration)

**Definition** — the exercise: *"design the document schema for X"* (food delivery, ride-sharing, blogging). The graded artifact is access-first narration: queries listed before shapes, boundaries before JSON, trade-offs priced before conclusions. Candidates who draw documents first fail even with good shapes (ungradeable decisions); candidates who narrate catalog → boundaries → shapes pass even with imperfect JSON (method visible, fixable).

**What problem it solves** — relational transplants (seventeen collections mirroring seventeen tables — the failure 1.1 names) and embed-everything fashion ("joins are legacy" — the failure Databases 03 leaf 2.1 names) both stem from skipping access analysis. Interviewers probe document design because it reveals whether the candidate models *workload* (queries, frequencies, writers) or *fashion* (what the last blog post recommended). Narration makes the distinction audible within minutes.

**Modern guidance** — the fifteen-minute shape (same skeleton as [Domain 01 §5](<../../../01 Modeling Foundations and Mental Model/sections/5. Interview QA/5.1. Common interview QA modeling foundations.md>), document flavor): (1) *catalog* (3 min — "what screens? how often? what freshness? who writes, how fast?" — ask before drawing); (2) *boundaries* (4 min — invariants and lifecycles out loud: "total matches lines — one aggregate; restaurant shared across orders — reference"); (3) *shapes* (5 min — nest within boundaries per the dominant fetch, chips for cross-boundary screens, buckets for streams); (4) *prices and gaps* (3 min — bound audits, version field, "minimum-cardinality unenforced, owned by app"). Narrate assumptions; write the version field unprompted — it signals production experience instantly.

```json
// GOOD (whiteboard narration, food delivery — 15 min):
// "Catalog first: order-tracking screen (500k/day realtime — order+items+status, one
// fetch); restaurant page (200k/day — menu needed, realtime); courier writes location
// (10/sec per courier — hot, independent). Boundaries: order aggregate (total==lines);
// restaurant shared truth (many orders, one menu — reference); courier location stream
// (unbounded ticks — veto: apart, bucketed). Shapes: order embeds lines + restaurant
// chip (name only, menu changes are rare events, nightly sync tolerated); menu items
// referenced by id (shared, evolving); courier ticks in 5-min buckets. Prices: lines
// ≤30 policy; chips name-only; schemaVersion 1 stamped day one. Gap: courier-order
// assignment consistency is app-side saga (cross-aggregate by definition)."
// Sketched JSON follows the narration — every nest traces to a catalog line.
{
  "_id": "order_555",
  "schemaVersion": 1,
  "status": "preparing",
  "restaurantChip": { "restaurantId": "r_12", "name": "Noodle House" },
  "lines": [{ "itemId": "m_3", "nameAtOrder": "Ramen", "priceAtOrder": "11.50", "qty": 2 }],
  "total": "23.00"
}
```

```json
// BAD (whiteboard): silent documents — ungradeable decisions, unasked workload.
// { restaurant with full nested menu + all historical orders + courier locations }
// (Boundaries unasked — menu lifecycle merged into orders; ticks nested — heat bomb;
// no catalog, no prices, no version. The interviewer learned the candidate draws
// JSON confidently and models nothing.)
{ "_id": "r_12", "menu": ["..."], "orders": ["...all history..."], "couriers": ["...ticks..."] }
```

**Common confusion** — *"document interviews want Mongo syntax."* Syntax is checkable in minutes and rarely graded; *decisions* are graded over the full session. Candidates reciting operators while nesting courier ticks fail; candidates sketching plain JSON while vetoing hot writes pass. If syntax anxiety strikes, narrate shapes in JSON-with-comments (this domain's convention) and say so — interviewers grade the boundary, not the bracket.

**Performance note** — the scale note (same 2-minute slot as every QA leaf in this track): name the hot structure and its growth ("courier ticks: 10/sec × 500 couriers — buckets sized 5-min, ~3k entries, sealed immutable; order lines bounded ≤30 — no ceiling math needed"). One growth sentence per unbounded structure — the expert signal that separates shapers from drawers.

**Mentor note** — mock monthly with rotating domains (delivery, social, IoT, logistics) so candidates practice *method*, not memorized schemas — same prescription as Domains 01–02. Grade the four phases separately (catalog stated? boundaries named? prices given? version stamped?) — phase scores diagnose precisely ("great shapes, never prices" → drill pricing). The version-field habit deserves its own checkbox: candidates who stamp v1 unprompted have shipped; those who don't, haven't.

## 2. Embed versus reference under pressure (the rule stack)

**Definition** — the follow-up: *"would you embed or reference X?"* The failing answers are absolute ("embed for speed" — fashion; "reference for integrity" — transplant). The passing answer is the *rule stack*, applied in order: lifecycle (contained → embed), boundedness (bounded + slow → embed), snapshot intent (history → embed frozen), shared truth (many readers one writer → reference), unbounded/heat (streams/counters → apart), with extended reference as the priced middle for dominant screens. Rules recited *as applied* to X — not as a list, as a verdict with reasoning.

**What problem it solves** — interviewers ask this because production asks it weekly and juniors answer tribally ("my last team embedded everything"). The stack separates engineers who *decide* (rules + prices) from engineers who *default* (habits + hopes). Each rule eliminates a class; the surviving shape is derived, not preferred — derivation narrated live is unmistakable senior signal.

**Modern guidance** — the ninety-second shape: (1) lifecycle verdict first ("lines die with orders — contained, embed-leaning"); (2) bound check ("≤30 policy, slow — embed holds"); (3) sharing check ("products shared across orders — reference, snapshots frozen"); (4) the middle only if a screen demands ("order list needs names — chip, name-only, nightly sync"); (5) what would flip it ("if lines grew unbounded — streams, not lines — buckets"). Five beats, each a rule applied, ending with the falsifier — candidates who state what would change their answer show they reason, not recite.

```json
// GOOD (spoken over the order-lines example, 90 seconds):
// "Lifecycle: lines die with orders — contained, embed-leaning. Bound: ≤30 policy,
// slow — embed holds. Sharing: products shared — reference by sku, snapshot name
// and price frozen at order time. Screen tax: order list needs product names —
// snapshot already carries them, no chip needed. Flip conditions: lines unbounded
// (configurators, not orders) → buckets; products per-order-custom (designs) →
// contained, embed fully. Current shape follows from current rules."
{
  "_id": "ord_1042",
  "lines": [{ "sku": "book-a", "nameAtOrder": "Book A", "priceAtOrder": "9.99", "qty": 2 }]
}
```

```json
// BAD (spoken): the fashionable absolute — confident, unpriced, wrong somewhere.
// "Embed everything — one fetch, no joins, that's the Mongo way." (Customer nested?
// Products nested? Ticks nested? The absolute holds until the first shared lifecycle,
// then fails everywhere at once. Or the mirror: "Reference everything — integrity
// matters." Seventeen collections, four fetches per screen, N+1 in document clothing.
// Absolutes are fashion statements; stacks are engineering.)
{ "strategy": "always-embed", "failures": "scheduled" }
```

**Common confusion** — *"the interviewer wants one answer."* They want a *derivation*: rules applied in order to a verdict, with flip conditions. "Embed, because lifecycle+bound+snapshot all point there — and here's what would flip it" is an answer; "embed" is a guess with good diction. Derivations survive follow-ups ("what if lines were unbounded?"); guesses collapse at the first one.

**Performance note** — volunteer the price with the verdict ("embed saves 800k assemblies/day; bound audit caps the risk at 50KB worst-case"). Prices generalize across every embed/reference question ever asked — candidates who price answer variants (counters, feeds, catalogs) without new preparation. Same ratio reasoning as [Domain 02's QA](<../../../02 Normalization Deep Dive/sections/5. Interview QA/5.1. Common interview QA normalization.md>): readers decide, writers veto, numbers settle.

**Mentor note** — drill as rapid-fire verdicts: name ten nest/reference candidates (lines, products, views, comments, addresses, sessions, menus, ticks, chips, histories), ninety seconds total, rule-plus-verdict each. Speed forces stack internalization — deliberation is for design reviews, reflex is for interviews (and for the 3 a.m. "can we nest this?" Slack message, where the same reflex serves production directly).

## 3. Scale the schema tenfold (buckets, subsets, versions as scale answers)

**Definition** — the closer: *"your schema works — now 10× the data. What breaks first?"* The graded skill is *ordered* failure prediction in document terms: which nest hits its bound first, which reference fans out, which unversioned shape blocks migration — each answered with the pattern that absorbs it (buckets for streams, subsets for bloat, versions for drift). Same "three deep, then stop" discipline as Domains 01–02, document vocabulary.

**What problem it solves** — day-one document shapes carry hidden ceilings (nested arrays with linear growth, unversioned shapes with silent drift, hot documents with serial writes) that 10× traffic converts to incidents. The question separates shapes with *priced headroom* (bound audits, version budgets, bucket windows) from shapes with *hoped headroom* ("Mongo scales horizontally" — the cluster scales; the 16MB document does not). Headroom priced in documents beats headroom assumed in infrastructure.

**Modern guidance** — answer in failure order, three deep: (1) *growth* ("views array hits 16MB at current rate in ~8 months — bucket by day now, not then; priced: one migration vs scheduled ceiling collision"); (2) *heat* ("order document rewrites per view-tick serialize at 10× — counters already apart (veto applied), verify day-doc contention at new rate"); (3) *drift* ("three live versions at 10× team size — version budget enforced at 2, eager rewrite for v1 before the team doubles"). Close with today's one change (usually: bucket the fastest stream, stamp versions if missing) — restraint graded over redesign, same as every 10× answer in this track.

```json
// GOOD (narrated 10× on the food-delivery schema): ordered, priced, restrained.
// "First: courier ticks — 10× couriers × 10/sec = unbucketed growth; buckets already
// 5-min (~3k entries), sealed immutable — holds to 100×, no action. Second: order
// lines bound ≤30 — 10× orders is count growth, not size growth; no ceiling risk.
// Third: restaurant chips — rename fan-out grows 10× (nightly sync window stretches);
// trigger: sync exceeding window → change-stream-driven sync (mechanics) or bare refs.
// Today's change: stamp schemaVersion (missing — drift starts silently) and bucket
// ticks if not yet (the one migration I refuse to run under ceiling pressure)."
// Verdict: two holds, one trigger, one action — the senior shape.
{ "_id": "order_555", "schemaVersion": 1, "restaurantChip": { "restaurantId": "r_12", "name": "Noodle House" } }
```

```json
// BAD: scale theater — infrastructure answers to modeling questions.
// "We'd shard... everything? Add replicas? Move to... a bigger cluster?"
// (No named first bottleneck, no bound audit referenced, no version budget —
// the answers cost more than the problem and fix none of it. The 16MB document
// doesn't care how many shards you own.)
{ "strategy": "more-hardware", "ceilings": "unexamined" }
```

**Common confusion** — *"document scale answers mean sharding."* (Same theater warning as Domain 02's 10× leaf, document edition.) At 10×, answers are still modeling: buckets, subsets, versions, vetoes. Sharding is the 100× answer — reaching for it at 10× signals resume-driven design. Interviewers asking 10× want headroom thinking with document vocabulary, not topology theater.

**Performance note** — every 10× answer needs a *measured trigger* ("bucket when daily ticks exceed 50k," "subset when parent exceeds 16KB hot," "rewrite when versions exceed budget 2") — triggers turn anxiety into runbooks, same as Domain 02. Untriggered scale plans are procrastination in the other direction. Document triggers deserve the same dashboard a relational team gives row counts: ceiling proximity is a metric, not a feeling.

**Mentor note** — teach "three deep, then stop" identically across all three domains (01 relational, 02 normalization, 03 documents) — the discipline is track-level, the vocabulary per-domain. Juniors drilled in one domain transfer the shape to others; interviewers encountering it three times in one loop promote. Reflex over recall, ordering over completeness — drill until it's the candidate's native incident-response shape too, because production demands exactly this ordering under worse pressure.
