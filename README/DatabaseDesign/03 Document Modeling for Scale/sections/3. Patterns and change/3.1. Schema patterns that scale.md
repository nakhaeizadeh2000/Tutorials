# 3.1. Schema patterns that scale

## 1. Bucket the unbounded (fixed-size time/count buckets turn streams into bounded documents)

**Definition** — the bucket pattern (official MongoDB pattern): partition an unbounded sequence into fixed-size documents — one per (entity, window) — each holding up to N entries, then a new bucket. Sensor readings per hour, views per day, events per thousand. The stream's unboundedness is converted into a bounded *count of bounded documents*: each bucket small, indexed, and independently readable; the whole stream paginated by bucket, never loaded whole.

**What problem it solves** — the growth bomb from [2.1](<../2. Embed or reference/2.1. Embed when together.md>) and [2.2](<../2. Embed or reference/2.2. Reference when apart.md>): nested streams swelling toward 16MB, or per-event documents exploding collection counts (10M tiny documents — index bloat, working-set churn). Buckets sit between: documents few enough to index cleanly, small enough to stay cache-hot, appendable without rewriting history (only the *current* bucket mutates; sealed buckets are immutable). Growth becomes a document count, and document counts scale horizontally.

**Modern guidance** — size buckets by read-write balance: *time windows* (hour/day) where recency dominates reads (dashboards want today — one bucket fetch); *count windows* (500–1000 entries) where uniformity matters (even document sizes, predictable transfer). Bucket key: `(entityId, windowStart)` with a compound index — range queries over windows stay ordered. Seal policy: buckets close on window end (immutable after — no late-write contention); late data goes to an overflow bucket or the current one by documented rule. Precompute per-bucket rollups (count, sum, min/max) so range aggregations sum buckets, never scan entries.

```json
// GOOD: the sensor stream as hourly buckets — bounded documents, countable growth.
// Bucket key (sensorId, hour) — compound index. Entries capped at 360 (one per 10s).
// Rollups precomputed: daily sums read 24 buckets, never 86k entries.
// Late reading (clock skew): overflow rule — lands in current open bucket, flagged.
{
  "_id": "sen_9_2026-09-28T10",
  "sensorId": "sen_9",
  "hour": "2026-09-28T10:00:00Z",
  "count": 360,
  "avgTemp": "21.4",
  "readings": [
    { "at": "2026-09-28T10:00:10Z", "temp": "21.2" },
    { "at": "2026-09-28T10:00:20Z", "temp": "21.5" }
  ]
}
```

```json
// BAD: the stream as one document per reading — 86k documents/day/sensor, index bloat.
// Collection count explodes (10k sensors → 860M docs/day); working set churns;
// "today's average" scans 86k index entries per sensor. The per-event document has
// no reader (nobody fetches reading #41,203 alone) — granularity without a consumer.
{ "_id": "r_1", "sensorId": "sen_9", "at": "2026-09-28T10:00:10Z", "temp": "21.2" }
// ... 85,999 siblings per day. Or the mirror failure: all nested in one document
// (2.1's BAD) — ceiling collision on schedule. Buckets or per-event; never the extremes.
```

**Common confusion** — *"buckets are just sharding by time."* Related mechanics, different level: sharding distributes documents across machines (operations topology); buckets shape documents within a collection (modeling). Buckets work unsharded (small deployments get bounded reads without any cluster); sharding works unbucketed (distributes whatever shape exists). Combine both at scale (bucket + shard key on entity — Domain 05 forward); confuse neither with the other.

**Performance note** — bucket economics: writes touch only the open bucket (one hot document per entity — contention bounded by entity count, not event rate); reads fetch whole buckets (KBs per window — sequential, cache-friendly); rollups turn O(entries) aggregations into O(buckets) (24 hourly buckets vs 86k readings — 3,500× fewer units scanned). Size buckets so the hot read (today's dashboard) fits few fetches and the hot write (current events) touches one document.

**Mentor note** — teach buckets as "pagination for writes": juniors understand read pagination (pages of results); buckets are the write-side twin (pages of history, filled over time). The analogy lands instantly — then generalize: every unbounded sequence in the system (logs, events, versions, ledgers) wants a paging strategy, and "we'll paginate reads later" is half the design. Paging is a modeling decision, not a UI one.

## 2. Subset the working set (hot fields in the parent, full body referenced)

**Definition** — the subset pattern (official MongoDB pattern): split an entity's fields by access temperature — the hot subset (titles, statuses, counts, chips — what lists and screens render) stays in the parent document; the cold bulk (bodies, histories, blobs — fetched rarely, large) moves to a referenced document. The 90% fetch stays one small document; the 10% fetch pays one assembly for data it actually wants.

**What problem it solves** — the bloated-parent tax: article documents carrying full bodies + 40k comment *metadata* + revision history on every title render (KBs fetched for bytes needed — transfer waste × 800k reads/day); or the inverse over-split (title in a separate collection from body — assembly on *every* read including the dominant one). The subset draws the line by temperature, not topic: hot together, cold apart, each fetch sized to its consumer.

**Modern guidance** — the temperature audit per field: *fetched with the parent in >80% of reads* → stays (title, status, count, chip); *fetched alone or rarely* → moves (body, full history, attachments). The cold document links back by parent id (one-to-one, named `..._details` or `..._body`); the parent may hold a staleness marker (bodyUpdatedAt — readers decide freshness). Boundary case (fetched 50/50): keep together until measured — splits are cheap to add later, assemblies are forever once split. Re-audit per feature: temperatures shift as screens evolve.

```json
// GOOD: the 90% fetch is one small document — body fetched only when opened.
// Parent (hot): title, status, counts — ~300 bytes per list row, 800k/day.
// Body (cold): full text + revisions — fetched on open (~5% of list views).
// commentCount maintained (counter discipline from 1.2); comments live apart (2.2).
{ "_id": "art_7", "title": "Sharding 101", "status": "published", "commentCount": 40213, "bodyUpdatedAt": "2026-09-20T08:00:00Z" }
{ "_id": "art_7_body", "articleId": "art_7", "body": "...full text...", "revisions": 14 }
```

```json
// BAD: everything together — every list render ships bodies nobody opened.
// 800k/day × 40KB bodies = 32GB/day transfer for titles. Or the mirror: title split
// to its own collection (assembly per EVERY read — including the 90% that wants both
// title and status together). Temperature-blind splits tax one side permanently.
{
  "_id": "art_7",
  "title": "Sharding 101",
  "status": "published",
  "body": "...40KB nobody opened...",
  "revisionHistory": ["...14 full revisions..."]
}
```

**Common confusion** — *subset versus extended reference (2.2): same pattern?* Same shape family (hot copy + cold truth), different direction: extended reference copies *another aggregate's* fields into the reader (cross-boundary); subset splits *one entity's* fields by temperature (within an aggregate family). Subset children share the parent's lifecycle (archive together — 1.1's test passes); extended-reference targets live independently. Classify by lifecycle: together → subset; apart → extended reference.

**Performance note** — subset economics are transfer arithmetic: parent size × hot frequency vs assembly cost × cold frequency. 300B × 800k/day = 240MB/day hot path; +40KB × 40k opens = 1.6GB/day cold path, paid only by openers. Unsplit: 40KB × 800k = 32GB/day — 13× the transfer for identical information. Run these numbers per entity once; the pattern justifies itself wherever hot/cold ratios exceed ~5:1.

**Mentor note** — teach temperature as a *measured* property, not a guessed one: access logs (or analytics events) rank fields by fetch frequency before any split. Juniors guessing temperatures split wrong ("body feels important" — to authors, not readers); one week of fetch counts settles every subset debate with data. "Show me the fetch counts" is the subset review question — asked twice, it becomes the author's pre-work.

## 3. Compute once read many (precomputed rollups for expensive aggregations)

**Definition** — the computed pattern (official MongoDB pattern): maintain precomputed aggregation results (totals, counts, averages, leaderboards) in dedicated documents, updated on write or schedule — trading write-time computation for read-time triviality. The dashboard reads one document; the writes maintain it. Same economics as [Domain 02 §3.1](<../../../02 Normalization Deep Dive/sections/3. Judgment/3.1. Deliberate denormalization with priced trade-offs.md>)'s materialized copies — the document-store expression of the same ledger.

**What problem it solves** — aggregation pipelines over millions of documents per page load (daily revenue across all orders — full scan + group, seconds per render, linear in history growth). Caching helps transiently (cache misses still scan; invalidation races); read replicas help partially (same scan, different machine). Precomputation changes the complexity: O(history) per render becomes O(1) document fetch + O(1) incremental maintenance per write. History growth stops punishing readers — the rollup absorbs it.

**Modern guidance** — the computed checklist (same six fields as 02/3.1's record, document flavor): (1) *rollup defined* (daily revenue = Σ totals by day); (2) *maintenance path* (write-time increment on order placement vs scheduled recompute — write-time for real-time needs, scheduled for tolerant ones); (3) *staleness stated* (real-time vs 5-min vs daily — per consumer); (4) *rebuild path* (full recompute from source aggregates — required, tested, or the rollup is unrecoverable truth); (5) *granularity* (daily buckets compose into weekly/monthly — store the finest grain consumers need, never coarser); (6) *revisit trigger* (volume or consumer change). Missing (4) fails review absolutely — unrebuildable rollups are liabilities, not optimizations.

```json
// GOOD: the rollup document — O(1) dashboard fetch, incrementally maintained.
// Granularity: daily (composes to weeks/months by summation).
// Maintenance: incremented on order placement (write-time, real-time consumers).
// Rebuild: sum(order.totals) GROUP BY day from orders — tested quarterly.
// Staleness: zero for today (write-time); intraday corrections replay same path.
{
  "_id": "rev_2026-09-28",
  "day": "2026-09-28",
  "orderCount": 48210,
  "gross": "1042031.55",
  "byTier": { "gold": "402115.00", "standard": "639916.55" }
}
```

```json
// BAD: the dashboard aggregating raw history per render — O(history) per page load.
// db.orders.aggregate([{$group: {_id: "$day", gross: {$sum: "$total"}}}]) — full scan,
// seconds per render, growing with every order ever placed. Cache in front: misses
// still scan; race windows serve stale as fresh (unstated staleness — the defect
// 02/3.1 names). The pipeline is correct and unshippable past thousands of orders.
{ "_id": "dashboard_query", "pipeline": "scan-all-orders-every-render" }
```

**Common confusion** — *"precomputation is premature optimization."* Optimization without measurement is premature; precomputation *with* a measured O(history) hot path is engineering. The distinguishing question: "show me the render latency vs history growth curve." Linear-and-climbing justifies the rollup; flat-and-fast doesn't. Curves, not slogans — the same measure-don't-guess framing as every performance claim in this track.

**Performance note** — maintenance-path choice is the performance decision: write-time increments add microseconds per write (constant — scales with write rate, trivially parallel across day-documents); scheduled recomputes cost O(window) per run (fine for tolerant consumers, wasteful for real-time). Hot-write + real-time-read topologies need write-time (or change streams — Databases mechanics); tolerant reads take schedules. Match path to freshness contract — mismatch in either direction wastes (over-fresh compute burned, under-fresh readers starved).

**Mentor note** — teach the rebuild drill before the rollup ships: "delete the rollup collection — now restore it." Teams that rehearse recovery trust precomputation; teams that can't rebuild fear their own optimization (correctly — unrebuildable state is a liability). The drill takes an hour, validates path (4), and converts the rollup from clever to dependable. No drill, no ship.
