# 3.2. Versioning and shape migration

## 1. Every document carries its version (implicit shapes become explicit contracts)

**Definition** — the schema-versioning pattern (official MongoDB pattern): a `schemaVersion` field (integer, starting at 1) on every document, incremented whenever the shape changes. Schemaless storage means shapes drift silently (v1 orders beside v3 orders, readers guessing); the version field converts drift into inventory — queries can count versions, code can branch on them, migrations can target them. One integer, total shape visibility.

**What problem it solves** — the silent-drift failure: three years of feature work produce five undocumented shapes in one collection; a new reader handles the latest, corrupts the oldest (missing fields read as nulls, renamed fields read as absent); debugging means sampling documents by age and reverse-engineering history. Versioned documents answer "what shapes exist?" with a group-by (one aggregation — Databases 03 mechanics) instead of archaeology — and every reader states which versions it supports, turning silent corruption into explicit errors.

**Modern guidance** — version from day one (v1 on the first document — retrofitting versions onto drifted history is the archaeology the field prevents); bump on any shape change (added/renamed/restructured fields — additive-only changes still bump, so readers can distinguish "field absent by age" from "field absent by error"); never reuse numbers. Readers declare supported versions (strict: reject unknown; tolerant: adapt known-old — next promise prices the choice). Enforce by review: PRs changing document shapes bump the version, update the reader matrix, or fail.

```json
// GOOD: versions explicit — inventory by aggregation, readers branch deliberately.
// v1 (2024): { customerId, lines[] } — no totals, no chips.
// v2 (2025): + total, + customerChip. v3 (2026): + status history, lines gain priceAtOrder.
// "How many v1 orders remain?" — GROUP BY schemaVersion. Answerable in seconds.
{ "_id": "ord_1042", "schemaVersion": 3, "customerId": "cus_101", "status": "placed", "lines": [{ "sku": "book-a", "qty": 2, "priceAtOrder": "9.99" }], "total": "19.98" }
```

```json
// BAD: five shapes, zero versions — every reader guesses, oldest data rots silently.
// 2024 order: { customerId, lines } (no total — total computed... or missing?).
// 2025 order: { customerId, lines, total } (same collection, different contract).
// Reader code: if (doc.total === undefined) doctrine — nulls from age confused with
// nulls from error, renames undetectable, migration targets uncountable. The collection
// holds history no query can reliably read — write-only memory at scale.
{ "_id": "ord_0001", "customerId": "cus_001", "lines": [{ "sku": "book-z", "qty": 1 }] }
```

**Common confusion** — *"versioning is only for public APIs."* Stored data outlives every API version (documents persist for years; API versions turn over quarterly) — unversioned storage is an unversioned API with no deprecation policy. The version field is cheaper than any API versioning scheme (one integer vs header negotiation) and more durable (survives every rewrite). Version storage first; APIs inherit the discipline.

**Performance note** — versioning costs one small integer per document (bytes, negligible) plus reader branching (one switch — trivial). It *saves* performance work: version-targeted migrations (rewrite only v1s — indexed query on schemaVersion) instead of full-collection scans; version-aware readers skip adaptation for current shapes (fast path unbranched). The integer pays rent from the first migration.

**Mentor note** — teach "v1 on day one" as professionalism, not pessimism: juniors hear versioning as planning-to-fail; reframe as planning-to-evolve (shapes *will* change — the only question is whether the change is inventoried). Teams adopting day-one versioning never pay the retrofit tax; teams deferring it pay archaeology plus backfill-versioning (inferring versions from field presence — heuristic, lossy). Day one is the cheapest version ever stamped.

## 2. Migrate lazily or eagerly — priced (read-time adaptation vs batch rewrite)

**Definition** — the two migration strategies for versioned shapes: *lazy* (read-time adaptation — readers handle old versions in code, documents upgrade on next write) and *eager* (batch rewrite — a job converts all old documents now). Lazy spreads cost over time (no big-bang) but carries reader complexity permanently (until versions die); eager pays upfront (one job, tested, monitored) but demands downtime tolerance or dual-read windows. The choice is economic, never stylistic.

**What problem it solves** — the unmigrated middle: teams that neither adapt readers (old documents corrupt new code) nor rewrite (old versions accumulate — five shapes, readers guessing, back to promise 1's BAD). Or the reflexive big-bang (rewriting 500M documents for a cosmetic rename — hours of write load, oplog pressure, rollback complexity — for zero business value). Pricing picks correctly: cosmetic change on cold history → lazy (or never); breaking change on hot paths → eager with dual-read; legal/regulatory shape → eager with deadline.

**Modern guidance** — the pricing inputs: (a) *old-version read rate* (hot v1s read daily → adapt or rewrite soon; cold v1s untouched for a year → lazy forever is fine); (b) *rewrite cost* (document count × write cost + oplog + index churn — measured on a sample, extrapolated); (c) *reader complexity budget* (each supported version is a code path with tests — count paths, cap at 2–3 live versions); (d) *deadline* (regulatory/compliance shapes have one — economics bow to law). Rule of thumb: ≤2 live versions with lazy adaptation is the steady state; eager jobs fire when versions exceed budget or deadlines demand.

```json
// GOOD: the priced decision, recorded — lazy with a version budget, eager trigger named.
// Change: v2 → v3 (lines gain priceAtOrder; total stays). Old-version reads: v2 hot
// (60% of history reads — recent orders), v1 cold (<1% — pre-2025, rarely opened).
// Decision: lazy adaptation for v2 (reader computes priceAtOrder = price fallback,
// one code path, tested) + eager rewrite for v1 ONLY (cold but corruptible —
// backfill priceAtOrder from catalog archives, one batch job, deadline none).
// Budget: max 2 live versions (v2+v3); v1 rewrite job closes the third.
// Record: ADR-033, trigger "v4 ships → re-price v2".
{
  "migrationRecord": "ADR-033",
  "change": "v2 to v3",
  "strategy": "lazy-v2 plus eager-v1-backfill",
  "versionBudget": 2,
  "revisit": "when v4 ships"
}
```

```json
// BAD: the unpriced extremes — big-bang rewrite for cosmetics, or permanent drift.
// "Rewrite all 500M documents this weekend for the rename" (eager without pricing:
// oplog storm, replica lag, rollback plan: hope). Or: "readers handle all versions"
// (lazy without budget: 5 live versions, 5 code paths, tests nobody runs — reader
// complexity growing while history nobody reads stays ancient). Both skip the ledger;
// both bill later at incident rates.
{ "migrationStrategy": "hope", "versions": "all of them, forever" }
```

**Common confusion** — *"lazy means never migrating."* Lazy means migrating *on touch* (documents upgrade when written — hot documents converge fast, cold ones linger harmlessly). Never-migrating is unversioned drift (promise 1's BAD) — no adaptation code, no budget, no record. Lazy-with-budget converges the hot set and documents the cold; never-migrating converges nothing and documents nothing. The adaptation code is the difference — count its paths.

**Performance note** — eager rewrites are the heaviest routine write load a cluster sees (full-collection rewrite — oplog flooding, replica lag, cache eviction); throttle (batches with sleeps), schedule (low-traffic windows), and monitor lag as the abort signal. Lazy adaptation costs per-read branching (microseconds) plus eventual write-upgrades (amortized). Price rewrite wall-time from sample batches (time 10k, extrapolate, add 50% — samples lie optimistically); price lazy as reader-path count × test maintenance. Numbers pick; gut doesn't.

**Mentor note** — teach migration as *budget management* (versions alive, paths maintained, deadlines pending) rather than heroics (weekend rewrites). Juniors romanticize big-bangs; seniors maintain budgets. The version-budget number (≤2–3 live) on a dashboard somewhere — reviewed quarterly — prevents both drift and heroics structurally. Boring migrations are successful migrations; review for boredom.

## 3. Polymorphism needs a discriminator (one collection, several shapes)

**Definition** — polymorphic storage: one collection holding several document shapes (vehicles: cars with doors, bikes with gears, boats with hulls) distinguished by a *discriminator* field (`kind: "car"`) plus the schemaVersion. The discriminator makes the implicit explicit — queries filter by kind, readers branch by kind, indexes serve per-kind patterns. Without it: shape-sniffing (field presence heuristics — lossy, brittle); with it: a declared union, queryable and validatable.

**What problem it solves** — the two polymorphic failures: *separate collections per subtype* (cars/bikes/boats collections — "all vehicles" queries fan out per collection, new subtypes need new collections + query changes, shared logic duplicates) and *undiscriminated soup* (one collection, shapes distinguished by vibes — "has doors ⇒ car, probably" — breaking the day a boat gets doors, i.e., a cabin). The discriminator is the middle that holds: one collection (unified queries), declared kinds (reliable branching), per-kind validation (schema rules per discriminator value).

**Modern guidance** — discriminate when subtypes share identity and query patterns (all vehicles listed, searched, owned together) but differ in attributes (kind-specific fields). The discriminator contract: (a) *required* (every document carries kind — enforced by validation); (b) *immutable* (kind never changes — a car doesn't become a boat; reclassification is delete+insert, audited); (c) *versioned alongside* (kind + schemaVersion jointly identify the shape — readers branch on the pair). Shared fields stay top-level (id, owner, createdAt); kind-specific fields nest under a kind-named subdocument (clean branching, clean validation).

```json
// GOOD: declared union — queries filter by kind, readers branch reliably.
// Shared: _id, kind, owner, createdAt (queried across kinds). Specific: details
// subdocument per kind (validated per kind — car rules never touch boats).
// "All vehicles of owner X" — one query. "Cars with 4 doors" — kind + field.
{ "_id": "v_1", "kind": "car", "schemaVersion": 2, "ownerId": "u_3", "details": { "doors": 4, "fuel": "electric" } }
{ "_id": "v_2", "kind": "boat", "schemaVersion": 2, "ownerId": "u_3", "details": { "hull": "catamaran", "berths": 6 } }
```

```json
// BAD: shape-sniffing soup — kinds implicit, branching heuristic, validation impossible.
// Car? (has doors — or is it a van? a cabin-boat?). Validation rules can't target
// "cars" (no car set exists — only documents that happen to have doors). New subtype
// (e-bike with... doors? no — with a battery cars also have?) breaks every heuristic.
// Queries branch on accidents of field presence — the schema equivalent of type-sniffing.
{ "_id": "v_1", "ownerId": "u_3", "doors": 4, "fuel": "electric" }
{ "_id": "v_2", "ownerId": "u_3", "hull": "catamaran", "berths": 6 }
```

**Common confusion** — *"discriminators are relational thinking (a type column)."* Type columns in relational tables and discriminators in documents solve the same information problem (which shape is this?) with different enforcement (CHECK vs validation rules) — convergent evolution, not borrowed thinking. The document version adds nesting freedom (kind-specific subdocuments validated independently — cleaner than nullable-column sprawl). Same question, better-shaped answer.

**Performance note** — discriminators index well (`{ownerId, kind}` serves per-owner-per-kind listings; `{kind}` alone serves fleet reports) — polymorphic queries stay point-shaped, never scans. The anti-pattern's cost is reader-side (field-presence branching per document — CPU per row, unindexable intent). One indexed field beats a thousand heuristics — discriminators are performance features wearing modeling clothes.

**Mentor note** — teach "name the kind" as the polymorphism reflex: any collection where juniors say "documents *mostly* look like X" needs a discriminator before the second shape lands. The *mostly* is the tell — unspoken unions become soup within a year. Review question: "what kinds live here, and where is it written?" Unwritten answer → request changes. Kinds are contracts; contracts are written.
