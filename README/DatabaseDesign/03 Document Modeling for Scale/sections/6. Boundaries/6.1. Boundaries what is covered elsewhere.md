# 6.1. Boundaries what is covered elsewhere

## 1. Relational discipline lives in Domains 01–02 (the lenses documents bend)

**Definition** — inbound boundary: Domains 01 ([Modeling Foundations](<../../../01 Modeling Foundations and Mental Model/README.md>)) and 02 ([Normalization Deep Dive](<../../../02 Normalization Deep Dive/README.md>)) teach the relational discipline this domain deliberately bends: entities and lifecycles (01 §1), key strategy (01 §2), dependency analysis (02 §1), normal forms through 5NF (02 §2), priced denormalization (02 §3). Documents don't abolish these lenses — embedding *is* controlled denormalization, aggregates *are* consistency boundaries around entities, snapshots *are* frozen dependencies. The relational theory transfers; only the shapes change.

**What problem it solves** — document modelers without relational foundations make two symmetric errors: *transplanting* (normalizing documents into reference-spaghetti — 1.1's BAD) and *ignoring* (embedding without bound audits, copying without snapshot/chip classification — every failure in §2). Both come from missing lenses, not missing syntax. Domains 01–02 supply the lenses (dependency arrows, anomaly vocabulary, copy ledgers); this domain supplies the document shapes they evaluate. Neither half works alone — the track's sequencing (relational first, documents third) is load-bearing.

**Modern guidance** — the crossing map backward: lifecycle and cascade thinking → [Domain 01 §1/§4](<../../../01 Modeling Foundations and Mental Model/sections/1. What modeling means/1.2. Entities relationships and cardinality.md>); key and identity strategy (candidate keys behind `_id` design) → [Domain 01 §2](<../../../01 Modeling Foundations and Mental Model/sections/2. Identity and keys/2.1. Surrogate versus natural keys.md>); dependency and anomaly vocabulary → [Domain 02 §1](<../../../02 Normalization Deep Dive/sections/1. Dependencies and atomicity/1.1. Functional dependencies the one idea behind every normal form.md>); copy-pricing ledgers and decision records → [Domain 02 §3.1](<../../../02 Normalization Deep Dive/sections/3. Judgment/3.1. Deliberate denormalization with priced trade-offs.md>); review-blessing ritual → [Domain 02 §4.1](<../../../02 Normalization Deep Dive/sections/4. Mentor checklist/4.1. Normalization review checklist mentors insist on.md>). Readers arriving here without 01–02 should detour for 01 §1–§2 and 02 §1/§3.1 at minimum — aggregates assume lifecycles, copies assume ledgers.

**Common confusion** — *"document modeling replaces normalization."* (Asked across all three domains' boundary leaves; restated for arrivals landing here directly.) Normalization eliminates dependency defects; document modeling shapes access units — different optimizers, both valid, each incomplete without the other. Designers who "replace" one with the other produce reference-spaghetti or unbounded nests respectively. Replace nothing; sequence everything: dependencies first (02), access second (03), translation last.

**Performance note** — none specific — this domain's performance content (bound audits, transfer arithmetic, refresh policies, veto math) stands on its own; Domains 01–02 contribute upstream shape economics (write amplification removed, join shapes priced). Joined across three domains: model entities (01), sharpen formally (02), shape documents (03) — each layer cheaper to operate than the last's unexamined defaults.

**Mentor note** — diagnose by failure direction (track-wide habit): reference-spaghetti → missing aggregate lens, send to 03 §1; unbounded nests → missing bound audits, keep here §2; stale copies served as truth → missing snapshot/chip classification, drill 2.1 vs 2.2; "flexible" soup → missing versioning, send to 3.2. Prescribe by direction, not seniority — and run the combined drill (model one feature relationally *then* documentally, narrating each translation choice) as the three-domain graduation test.

**Cross-links** — the map above is the complete inbound set; forward and outward boundaries follow.

## 2. Mechanics live in Databases 03 (query syntax, ceiling math, write units — linked, not repeated)

**Definition** — outward boundary: how the engine *executes* what this domain *decides*. Aggregates name write units; Databases 03 teaches their atomicity mechanics. Bound audits name ceilings; Databases 03 teaches the growth math that measures them. Extended references name chips; Databases 03 teaches the `$lookup`/projection syntax that assembles them. Neither track repeats the other — decision rules here, execution mechanics there, links between.

**What problem it solves** — duplicated coverage rots (two ceiling-math explanations drifting apart), and misplaced coverage confuses (operator syntax taught beside aggregate theory suggests they're one decision — they're two: what boundary, then how to query it). Single source of truth per PROMPT.md §5: each concept has one home; this leaf maps the crossings so readers never wonder and writers never paste.

**Modern guidance** — the crossing map, by need: embed-vs-reference read-locality lens + 16MB ceiling math + snapshot-vs-truth framing → [Databases 03 leaf 2.1](<../../../../Databases/03 MongoDB Deep Dive/sections/2. Modeling and speed/2.1. Embed versus reference.md>); query operators, projections, aggregation pipelines → [Databases 03 §1](<../../../../Databases/03 MongoDB Deep Dive/sections/1. Query depth/1.2. Query operators and projections.md>); write atomicity, ids, idempotency → [Databases 03 §3](<../../../../Databases/03 MongoDB Deep Dive/sections/3. Writes/3.1. Writes ids and idempotency.md>); full orientation → [Databases track index](<../../../../Databases/README.md>) and [Databases 03 index](<../../../../Databases/03 MongoDB Deep Dive/README.md>). Inbound, Databases 03's boundary leaf defers modeling depth here — each track owning its side. Live-engine verification gap (no mongoprobe this session — kernel incompatibility, recorded in [LOG.md](<../../../LOG.md>)) is covered by this division: mechanics claims stay linked, design claims stay engine-free.

**Common confusion** — *"this track assumes Mongo — where do I learn it?"* (Asked in every boundary leaf; restated for direct arrivals.) Databases 03, in order, then return here. The tracks compose: Databases makes you operational, Database Design makes you deliberate — operational-first is the common path, deliberate-first the ambitious one. Either order works; skipping either half doesn't.

**Performance note** — none specific — performance mechanics (index selection for chips, `$lookup` planning, write-concern tuning) are Databases 03/06 territory by design. This domain's performance contribution is upstream: bounded, priced, versioned shapes cost less to operate than shapes that cannot state their own guarantees — same upstream argument as Domains 01–02, document expression.

**Mentor note** — same navigation discipline as every boundary leaf in this track: mechanics questions get links, not lessons — then the *why* of the boundary. Learners who navigate the map become autonomous; mentors who re-teach across boundaries train dependency. The boundary is curriculum, not convenience — third restatement, same habit, permanent value.

**Cross-links** — the map above is the complete outward set for mechanisms; code-mapping boundary (unchanged across domains) next.

## 3. Code mapping lives outside this track (ODMs and repositories consume shapes — they do not define them)

**Definition** — outward boundary (unchanged from [Domain 01 §6](<../../../01 Modeling Foundations and Mental Model/sections/6. Boundaries/6.1. Boundaries what is covered elsewhere.md>) and [Domain 02 §6](<../../../02 Normalization Deep Dive/sections/6. Boundaries/6.1. Boundaries what is covered elsewhere.md>), restated per the boundary-leaf contract): how code *talks to* document shapes — ODM schemas (Mongoose and kin), repository patterns, migration frameworks — is owned elsewhere and never re-taught here. Shapes are defined in this track; consumed everywhere else. Influence flows one way: modeling decisions constrain code structure, never the reverse.

**What problem it solves** — ODM-first modeling ("how will Mongoose populate this?") inverts the dependency twice over: the schema starts serving the mapper (population paths dictate references — the 1.1 BAD shape with library branding), and mapper limitations become schema defects (discriminators the ODM handles poorly get flattened into soup — 3.2's BAD by tooling). Decide the shape here; map it there — friction at the mapping layer is *information* (the model said something the tool dislikes), not a veto. Same rule as relational, document edition — stated thrice because violated thrice as often (ODMs feel more "native" to documents, so their gravity is stronger).

**Modern guidance** — the consumption map: repository seam and testability → [DesignPatterns 06](<../../../../DesignPatterns/06 Modern Patterns and Anti-Patterns/README.md>) (assumes sound shapes underneath); ODM usage → the ORM track (planned sibling per root README — textual forward, target unbuilt, no dead link by design); schema-validation enforcement (JSON Schema validators as the mapper-independent contract) → Databases 03 mechanics (linked, not repeated). When mapping friction appears, change the mapping first, the shape second, record which and why (ADR habit from [Domain 01 §4](<../../../01 Modeling Foundations and Mental Model/sections/4. Mentor checklist/4.1. Modeling checklist mentors insist on.md>)) — and prefer validators over ODM enforcement for cross-service contracts (validators live with the data, ODMs live with one service).

**Common confusion** — *"the ODM schema IS the document design."* The ODM schema is one consumer's view — typed, convenient, and incomplete (no bound audits, no version budgets, no catalog traces). Teams that mistake the Mongoose model for the design lose every decision the ODM can't express (why this nest? what bound? which version?) — and rediscover them during incidents. The design lives in this domain's artifacts (boundaries, catalogs, prices, versions); the ODM model is their projection into code. Projection, not source.

**Performance note** — ODM overhead (hydration, change tracking, population N+1) is *consumption* performance — owned by the ORM/Patterns side. But note the direction (same as Domain 01 §6, document edition): most consumption pathologies trace to unmodeled shapes (unbounded arrays the ODM hydrates whole, missing discriminators forcing client-side branching, absent subsets shipping bodies per list). Good shaping here prevents performance work there — the cheapest ODM optimization is a well-bounded document.

**Mentor note** — teach the dependency direction as architecture (same sentence as Domain 01 §6, worth its third stating): "the database outlives every framework." ODMs turn over every 3–5 years; well-shaped document families serve for decades. Juniors who internalize this stop asking "how does tool X want it?" and start asking "what does the workload need?" — the senior transition in one sentence, now in its document translation.

Boundaries what is covered elsewhere.md>); denormalization twin in [Domain 02 §6](<../../../02 Normalization Deep Dive/sections/6. Boundaries/6.1. Boundaries what is covered elsewhere.md>).
