# 1.2. First normal form atomic values

## 1. One cell one fact (no lists, no comma-strings, no repeating groups hiding in columns)

**Definition** — first normal form: every cell holds one atomic value, and no repeating groups (phone1/phone2/phone3, or a `tags` column holding `"a,b,c"`). "Atomic" means indivisible *for the queries you run* — a name is atomic until you need first/last separately; an address is atomic until you filter by city. Atomicity is defined by use, not by type.

**What problem it solves / history** — pre-relational systems stored repeating groups natively (COBOL occurs-clauses, hierarchical segments); Codd's 1NF abolished them because every repeated group reintroduces the anomalies from [1.1](<1.1. Functional dependencies the one idea behind every normal form.md>) in miniature: adding a fourth phone needs a migration, "customers with phone X" scans three columns, and `phone2` means "second phone" in one row and "spare phone" in the next. 1NF is the floor every later form stands on — unrepeat the groups before reasoning about dependencies.

**Modern guidance** — the mechanical test: would any query need to look *inside* this cell, or count *across* these columns? If yes, split: repeating columns → child table (one row per value, position column if order matters); comma-strings → child table or native array (third promise). Apply at design time, not when the fourth phone arrives.

```sql
-- GOOD: one phone per row — the fourth phone is an INSERT, and every phone is queryable.
CREATE TABLE customers (
  id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name TEXT NOT NULL
);

CREATE TABLE customer_phones (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id),
  phone       TEXT NOT NULL,
  position    INT NOT NULL DEFAULT 0,   -- order preserved without repeating columns
  UNIQUE (customer_id, phone)            -- the same number twice is a data entry error
);
```

```sql
-- BAD: the repeating group — three columns for an unbounded list.
CREATE TABLE customers_bad (
  id     BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name   TEXT NOT NULL,
  phone1 TEXT,   -- NULL means "no phone" or "unknown"? Undecided, per row.
  phone2 TEXT,   -- the fourth phone needs ALTER TABLE + backfill + app changes
  phone3 TEXT    -- "find customer by phone" checks three columns, forever
);
```

**Common confusion** — *"1NF bans all multi-valued storage."* 1NF bans *unstructured* multi-values the engine cannot see into. A native array with operators, a JSONB document with a GIN index — these are queryable structures with their own trade-offs (third promise), not repeating groups. The rule targets invisibility, not plurality.

**Performance note** — repeating columns defeat indexing three times over: no single index covers "any phone," statistics fragment across columns, and every lookup is a three-way OR. The child table needs one index on `(phone)` and the lookups become point queries — 1NF compliance is routinely the largest search-performance win available, for zero tuning effort.

**Mentor note** — the code-smell tell juniors can apply today: numbered column names (`value1`, `extra2`, `note3`) are repeating groups wearing a disguise. Teach "grep your schema for trailing digits" as a self-review step — it catches 1NF violations before they reach review, and the habit generalizes to all naming smells ([Domain 01 §4](<../../../01 Modeling Foundations and Mental Model/sections/4. Mentor checklist/4.1. Modeling checklist mentors insist on.md>)).

## 2. Atomicity is queryability (what the database cannot see inside, it cannot index, join, or constrain)

**Definition** — a value is atomic *relative to the workload*: city is atomic if you never filter by it, composite the day a "customers per city" report appears. The 1NF question is never "is this value simple?" but "will any query, constraint, or join need its parts?" Design for the parts you can foresee; split when foresight runs out.

**What problem it solves** — the two classic non-atomic traps: *comma-strings* (`tags = 'vip,beta,emea'` — "all beta customers" becomes `LIKE '%beta%'`, matching `alphabet` too) and *packed addresses* (`address = '12 Main St, Berlin'` — city reports need string surgery per row). Both store multiple facts per cell, so the engine can neither index the parts (no B-tree into a substring) nor constrain them (no CHECK on "the second element") nor join on them. Every workaround (LIKE scans, regex extracts, application-side splits) is O(N) forever.

**Modern guidance** — split on first foreseeable need: tags → junction table (they will gain metadata — `tagged_at`, `tagged_by` — within a year, always); address parts you filter by → columns (`city`, `postal_code`), parts you only display → one column (YAGNI for the rest). The rule is asymmetric: splitting early costs one join; unsplitting later costs a migration with string parsing under load. When in doubt, split the part you *query*, keep whole the part you *display*.

```sql
-- GOOD: tags as rows — "all beta customers" is an indexed equality, and tags can grow metadata.
CREATE TABLE tags (
  id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name TEXT UNIQUE NOT NULL
);

CREATE TABLE customer_tags (
  customer_id BIGINT NOT NULL REFERENCES customers (id),
  tag_id      BIGINT NOT NULL REFERENCES tags (id),
  tagged_at   TIMESTAMPTZ NOT NULL DEFAULT now(),  -- metadata the string could never hold
  PRIMARY KEY (customer_id, tag_id)
);
-- SELECT customer_id FROM customer_tags WHERE tag_id = $beta;  -- index, milliseconds
```

```sql
-- BAD: the comma-string — unindexable, unjoinable, unconstranable, and lying in wait.
CREATE TABLE customers_bad2 (
  id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name TEXT NOT NULL,
  tags TEXT NOT NULL DEFAULT ''   -- 'vip,beta,emea'
);
-- SELECT ... WHERE tags LIKE '%beta%';   -- full scan + false positives ('alphabet')
-- No FK to a tags table, no UNIQUE per tag, no tagged_at — three features impossible.
```

**Common confusion** — *"but the application splits the string fine."* Application-side splitting works for display and dies for querying: the database still scans every row, still cannot join, still cannot enforce. "The app handles it" confuses *reading* a value with *reasoning over* a column — 1NF governs the latter.

**Performance note** — quantify once and the debate ends: `LIKE '%x%'` over 10M rows is seconds per query, every time, unindexable by B-trees (trigram indexes help substrings but never joins or constraints). The junction table turns it into microseconds. When someone defends the string, ask for the row count at which seconds-per-query becomes acceptable — the answer is always "we'll migrate before that," which concedes the point.

**Mentor note** — make juniors write the "queryability audit" for each TEXT column in review: "will we filter/join/constrain inside this?" Three audits that answer "display only" teach restraint (not everything needs splitting); one that answers "filter" and gets split teaches the rule. The audit habit matters more than any single verdict.

## 3. Arrays are the deliberate exception (PostgreSQL arrays have operators — but they still cost normal-form guarantees)

**Definition** — PostgreSQL native arrays (`TEXT[]`, `INT[]`) with operators (`&&` overlap, `@>` contains, `ANY`) are *structured* multi-values: the engine sees inside, indexes them (GIN), and constrains elements (CHECK on `cardinality()`). They violate 1NF's letter while honoring its spirit (queryability) — which makes them a deliberate, priced exception rather than a loophole.

**What problem it solves** — some lists are genuinely value-like: a week's opening-hours flags, a fixed set of locale fallbacks, denormalized tag caches kept consistent by triggers. Exploding these into junction tables buys formalism at the price of join tax on every read — for lists that never gain metadata and never join, the junction is ceremony. Arrays serve the narrow band where the list is queried (operators + GIN cover it) but never related.

**Modern guidance** — arrays only under three simultaneous conditions, all documented: (a) elements never gain attributes of their own (no `tagged_at` coming — if it might, junction now); (b) elements never join to another table (no FK semantics needed); (c) element count stays small and bounded (dozens, not thousands — GIN bloat and update-rewrite costs grow with size). Violate any condition later → migrate to junction (expand/contract, Domain 05 forward). Default junction; justify array — the same burden-of-proof shape as [Domain 01's key rule](<../../../01 Modeling Foundations and Mental Model/sections/2. Identity and keys/2.1. Surrogate versus natural keys.md>).

```sql
-- GOOD: the narrow exception — bounded, attributeless, join-free, indexed, constrained.
CREATE TABLE locales (
  id        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  code      TEXT UNIQUE NOT NULL,
  fallbacks TEXT[] NOT NULL DEFAULT '{}',           -- e.g. '{de-AT,de,en}' — display order
  CONSTRAINT fallbacks_bounded CHECK (cardinality(fallbacks) <= 5)
);
CREATE INDEX locales_fallbacks_gin ON locales USING GIN (fallbacks);
-- "which locales fall back to German?" — indexed overlap query:
-- SELECT code FROM locales WHERE fallbacks && '{de}';
```

```sql
-- BAD: arrays as junction replacement — elements that clearly want to relate.
CREATE TABLE orders_bad3 (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  book_ids BIGINT[] NOT NULL   -- books exist as entities! No FK, no quantity per line,
                               -- no line lifecycle — the hidden entity from Domain 01,
                               -- entombed where constraints cannot reach it
);
-- "all orders containing book X" works (ANY + GIN) — but referential integrity,
-- per-line quantities, and line refunds are all impossible. Queryable is not enough;
-- related data needs relationships.
```

**Common confusion** — *"arrays are just as good as junction tables now that GIN exists."* GIN covers lookup, not integrity (no FK from array elements), not attributes (no per-element columns), not set semantics under concurrency (whole-array rewrite per UPDATE — two concurrent appends conflict where junction INSERTs would not). Operators solve querying; only tables solve relating.

**Performance note** — arrays rewrite whole on UPDATE (a 100-element array append rewrites all 100 — TOAST-amplified at large sizes), and GIN indexes are slower to update than B-trees (pending-list mechanics — Databases 02 territory). Small, rarely-updated arrays: negligible. Large, hot arrays: a write-amplification trap. Size and churn decide — measure both before committing.

**Mentor note** — teach arrays as "denormalization with training wheels": all the shortcut benefits, a migration path to junction tables when conditions break, and three written conditions to check yearly. Juniors learn that exceptions need *narrower* rules than defaults, not looser ones — a lesson that transfers to every "it depends" in engineering.
