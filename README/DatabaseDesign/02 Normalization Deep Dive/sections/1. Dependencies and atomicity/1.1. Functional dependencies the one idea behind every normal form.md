# 1.1. Functional dependencies the one idea behind every normal form

## 1. Dependency is determination (if knowing A always tells you B, A determines B)

**Definition** — a functional dependency `A → B` means: within this table, knowing A's value always tells you B's value. `order_id → customer_id` (one order has one customer). `customer_id → customer_city` (one customer lives in one city — today). It is a statement about the business, not the data sample — "always" means in every legal state, not just current rows.

**What problem it solves / history** — before Codd (1971), schema design was folklore: experienced designers "felt" that storing the city on every order row was wrong but could not say why beyond "duplication." Functional dependencies turned the feeling into a testable claim: `customer_id → city` holds inside an orders table, so the city is a fact about the customer stored where it does not belong. Every normal form (1.2 through 2.2) is one sentence about which dependencies may live where.

**Modern guidance** — write dependencies before drawing tables: for each candidate table, list `A → B` sentences from the business rules. The sentences come from stakeholders ("can a customer have two cities?" — no → `customer_id → city`), never from samples (two Berlin rows prove nothing). If stakeholders cannot answer, the dependency is undecided — record it as a gap ([3.1 in Domain 01](<../../../01 Modeling Foundations and Mental Model/sections/3. First design moves/3.1. From requirements to tables.md>)'s gap-list habit), not as a guess.

```sql
-- GOOD: the dependency customer_id → city lives in exactly one place.
CREATE TABLE customers (
  id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- id → every column
  city TEXT NOT NULL                                     -- customer_id → city, once
);

CREATE TABLE orders (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id)  -- no city here: nothing to disagree
);
```

```sql
-- BAD: customer_id → city asserted on every order row — N copies of one fact.
CREATE TABLE orders_bad (
  order_id      BIGINT PRIMARY KEY,       -- order_id → everything (fine)
  customer_id   BIGINT NOT NULL,          -- customer_id → customer_city (repeated!)
  customer_city TEXT NOT NULL             -- the same fact, copied per order
);
-- Two rows, customer 101, 'Berlin' twice: which copy is true? Both. Until one changes.
```

**Common confusion** — *"dependencies are just unique constraints."* Uniqueness is one dependency shape (`UNIQUE(email)` means email → row). But most dependencies are not unique: `customer_id → city` allows thousands of customers per city. Thinking only in uniques misses the dependencies that actually drive normalization — determination is wider than identification.

**Performance note** — naming dependencies has no runtime cost; it pays at review time (a reviewer who sees `customer_id → city` inside orders spots the anomaly before migration) and at incident time ("which copy won?" is answered by design, not archaeology). Dependency literacy is the cheapest correctness tool in this domain.

**Mentor note** — teach the arrow notation on a whiteboard before any normal-form number: `order_id → customer`, `customer → city`, therefore `order_id → city` (transitivity preview). Juniors who can draw three arrows already understand 3NF's motivation — the numbers later are just names for arrow patterns. Notation first, nomenclature second.

## 2. Keys are minimal determiners (a key determines the whole row and nothing smaller does)

**Definition** — a *superkey* is any column set determining the whole row; a *candidate key* is a minimal one (no subset suffices); the *primary key* is the candidate you chose. Minimality matters: `{order_id, customer_id}` determines an order row, but `order_id` alone does — so the pair is a superkey, not a candidate key, and treating it as identifying invites 2NF violations (next leaf's territory — preview, not repeat).

**What problem it solves** — key confusion produces two symmetric defects: *oversized keys* (composite PKs carrying columns that determine nothing — every FK referencing them drags dead weight) and *undersized identity* (a "key" that does not determine the row — duplicates that no constraint catches). Minimality is the test that rejects both: can anything be removed and still determine the row? If yes, remove it.

**Modern guidance** — for each table, enumerate candidate keys explicitly during design (usually 1–2: the surrogate PK plus a natural UNIQUE). The [Domain 01 default](<../../../01 Modeling Foundations and Mental Model/sections/2. Identity and keys/2.1. Surrogate versus natural keys.md>) (surrogate PK, naturals UNIQUE beside it) already yields this: the surrogate is one candidate key, each UNIQUE another. Write them down — normal-form definitions speak in "key" and "non-key" attributes, and you cannot apply what you have not named.

```sql
-- GOOD: candidate keys named — id (chosen PK) and email (alternate key, enforced).
CREATE TABLE customers (
  id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- candidate key 1 (chosen)
  email TEXT UNIQUE NOT NULL,                             -- candidate key 2 (alternate)
  city  TEXT NOT NULL                                     -- non-key attribute
);
-- "Non-key attribute" now has meaning: city is neither key — every NF rule about
-- non-key columns applies to exactly this column.
```

```sql
-- BAD: no key named at all — nothing determines the row, so anything (duplicates
-- included) is permitted and no normal-form reasoning can even start.
CREATE TABLE customers_bad (
  id    BIGINT,   -- not a key: duplicates allowed
  email TEXT,     -- not unique: the "identifier" identifies nothing
  city  TEXT
);
```

**Common confusion** — *"primary key" and "candidate key" are synonyms in practice.* The PK is one candidate among (potentially) several — and normal forms care about *all* of them (BCNF especially: a dependency onto a non-chosen candidate still matters). Teams that name only the PK reason about half their keys.

**Performance note** — each candidate key buys an index (PK + each UNIQUE) — enforcement and lookup in one structure. The cost is write-time index maintenance per key; the discipline is justifying each UNIQUE by a business dependency, not adding "just in case" uniques that tax every INSERT.

**Mentor note** — the one-question drill: point at any table and ask "what are the candidate keys?" Hesitation means the designer never enumerated them — send them back to list dependencies first. Fluency here predicts fluency in every later normal-form discussion.

## 3. Anomalies are dependency symptoms (update, insert, and delete anomalies all mean one fact lives in two places)

**Definition** — three failure shapes, one cause: **update anomaly** (one fact in N rows — changing it needs N writes, and partial writes leave contradictions); **insert anomaly** (a fact cannot be recorded without an unrelated row — a new customer with no orders has nowhere to live); **delete anomaly** (deleting the last carrier row destroys an unrelated fact — deleting the final Berlin order deletes "customer 101 lives in Berlin"). All three mean a dependency lives where its determiner is not the key.

**What problem it solves** — anomalies convert abstract dependency talk into production consequences: the update anomaly is a data-corruption incident (two cities for one customer — which ships?); the insert anomaly is a missing-feature ticket ("we can't onboard suppliers without POs" becomes a schema change); the delete anomaly is silent data loss. Naming the three gives teams a shared incident vocabulary — "this bug was an update anomaly" diagnoses and prescribes at once.

**Modern guidance** — use anomalies as the design-time test: for every repeated fact, narrate all three ("to change it I touch N rows; to add a customer without orders I… can't; to delete the last order I lose…"). If any narration hurts, the dependency is misplaced — split the table now (2.1 shows the splits). Anomalies are the *why* behind every normal form: 2NF/3NF/BCNF each eliminate one dependency shape that causes them.

```sql
-- GOOD: each anomaly narrated against the split design — all three absent.
-- Update: customer moves → one UPDATE on customers. Insert: new customer → one INSERT,
--   no order needed. Delete: last order deleted → customer row (and city) survives.
UPDATE customers SET city = 'Munich' WHERE id = 101;   -- one row, always consistent
INSERT INTO customers (email, city) VALUES ('new@x.io', 'Paris');  -- no order required
DELETE FROM orders WHERE id = 7;                        -- customer 101's city untouched
```

```sql
-- BAD: the same three operations against orders_bad — each one injures.
UPDATE orders_bad SET customer_city = 'Munich' WHERE customer_id = 101;
-- update anomaly: touched 2 rows today, 2M rows at scale — partial failure = contradiction
INSERT INTO orders_bad (order_id, customer_id, customer_city) VALUES (3, 102, 'Paris');
-- insert anomaly: customer 102 cannot exist without fabricating an order for them
DELETE FROM orders_bad WHERE order_id = 2;
-- delete anomaly: if that was 101's last order, "101 lives in Berlin" is gone forever
```

**Common confusion** — *"anomalies are theoretical — applications handle consistency."* Applications handle the happy path; anomalies strike on the paths applications forget (backfills, admin consoles, bulk imports, race windows — the idempotency lesson from [Domain 01](<../../../01 Modeling Foundations and Mental Model/sections/2. Identity and keys/2.2. Identity at scale.md>) generalizes: constraints close windows code leaves open). Every anomaly class has a production-incident archetype; "theoretical" ends at the first one.

**Performance note** — the update anomaly is also a write-amplification problem: changing one fact costs N row writes plus N index updates at scale — the normalized single-row UPDATE is O(1) against the anomaly's O(N). Normalization is routinely a write-performance improvement disguised as correctness work; price it that way when justifying splits to skeptics.

**Mentor note** — teach anomalies through incident postmortems, real or constructed: "customer saw two different cities on invoice vs profile — root cause: update anomaly, fix: split table + backfill + UNIQUE." Juniors remember stories, not definitions; three war stories (one per anomaly) stick longer than any textbook chapter. Collect your team's.
