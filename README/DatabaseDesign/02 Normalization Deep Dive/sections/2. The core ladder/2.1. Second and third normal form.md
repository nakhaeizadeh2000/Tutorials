# 2.1. Second and third normal form

## 1. 2NF kills partial dependency (no non-key column may depend on part of a composite key)

**Definition** — second normal form: the table is in 1NF, and every non-key attribute depends on the *whole* key, not part of it. Partial dependency can only exist where keys are composite — `{student_id, course_id} → instructor` is partial because `course_id → instructor` alone (the instructor teaches the course regardless of who enrolls). The fix is mechanical: move the partially-dependent attribute to a table keyed by the part it actually depends on.

**What problem it solves** — the enrollment-table classic: `(student_id, course_id, grade, instructor)` stores the instructor per enrollment — the instructor changes (sabbatical replacement) and N enrollment rows must update (update anomaly); a new course with no students cannot record its instructor (insert anomaly); the last student dropping deletes who teaches it (delete anomaly). All three from [1.1](<../1.%20Dependencies%20and%20atomicity/1.1.%20Functional%20dependencies%20the%20one%20idea%20behind%20every%20normal%20form.md>), all three gone after one split.

**Modern guidance** — audit every composite key (junction tables, natural composite PKs): for each non-key column, ask "does this need *both* key parts, or just one?" Grade needs both (a grade is awarded to a student *in* a course — keep). Instructor needs one (move to courses). The question takes thirty seconds per column and is the entire 2NF review — no other procedure exists.

```sql
-- GOOD: instructor depends on course_id — so it lives in courses, keyed by course_id.
CREATE TABLE courses (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  instructor TEXT NOT NULL   -- course_id → instructor, whole key, one home
);

CREATE TABLE enrollments (
  student_id BIGINT NOT NULL REFERENCES students (id),
  course_id  BIGINT NOT NULL REFERENCES courses (id),
  grade      CHAR(1) NOT NULL CHECK (grade IN ('A','B','C','D','F')),
  -- grade needs BOTH parts (awarded to this student in this course) — stays
  PRIMARY KEY (student_id, course_id)
);
-- Instructor change: one UPDATE on courses. New course, no students: INSERT into courses.
```

```sql
-- BAD: instructor rides along per enrollment — partial dependency, three anomalies.
CREATE TABLE enrollments_bad (
  student_id BIGINT NOT NULL,
  course_id  BIGINT NOT NULL,
  grade      CHAR(1) NOT NULL,
  instructor TEXT NOT NULL,   -- depends on course_id alone — copied per student
  PRIMARY KEY (student_id, course_id)
);
-- Instructor replacement: UPDATE N rows (partial failure = two instructors for one course).
-- New course, zero enrollments: instructor has nowhere to live.
```

**Common confusion** — *"surrogate keys make 2NF automatic."* Mostly true and dangerously soothing: single-column surrogate PKs *cannot* have partial dependencies (no parts to be partial on) — which is why surrogate-default teams ([Domain 01](<../../../01 Modeling Foundations and Mental Model/sections/2. Identity and keys/2.1. Surrogate versus natural keys.md>)) rarely meet 2NF violations. But composite keys survive in junctions and legacy schemas, and "2NF is automatic" becomes "I never learned to spot partial dependency" — until the legacy table arrives. Know the rule even where the default hides it.

**Performance note** — the 2NF split replaces N-column duplication with a join — and the join is on a PK lookup (indexed by definition), the cheapest join shape that exists. The anomaly it removes (N-row updates) was O(enrollments); the join it adds is O(1) per row. Splits like this are performance improvements that happen to be taught as correctness.

**Mentor note** — teach 2NF as "the thirty-second question" (does this column need both key parts?), not as a definition to memorize. Juniors who can ask the question audit any composite key on sight; juniors who memorized "no partial dependency" freeze on real schemas. Procedure over phrasing — drill on the team's own junction tables.

## 2. 3NF kills transitive dependency (no non-key column may depend on another non-key column)

**Definition** — third normal form: in 1NF, with no partial dependencies (2NF), and no non-key attribute depends on another non-key attribute. The chain `order_id → customer_id → city` is transitive: city depends on the key *through* a non-key column. The fix is the same surgery one level deeper: move the transitively-dependent attribute to a table keyed by its actual determiner (customers).

**What problem it solves** — the orders-with-city classic from 1.1's BAD example, now named: `orders(order_id, customer_id, customer_city)` — customer moves, N order rows update; customer without orders cannot exist; last order deleted, city knowledge lost. 3NF violations are the most common real-world anomaly source precisely because transitive chains *look* innocent (each column seems to describe the row) — the dependency lens is the only reliable detector, which is why 1.1 precedes this leaf.

**Modern guidance** — the review procedure: for each non-key column, trace its determiner — "does this describe the key, or does it describe *another column*?" City describes the customer, not the order → move. Postal code describes the city → further move (cities table) *if* you query by it and it has its own lifecycle — otherwise document the chain as accepted (third promise's territory: not every transitive chain earns a table). Trace determiners, not vibes.

```sql
-- GOOD: the chain order_id → customer_id → city is cut — city lives with its determiner.
CREATE TABLE customers (
  id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  city TEXT NOT NULL   -- customer_id → city: determiner is the key here
);

CREATE TABLE orders (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id)  -- chain stops: join recovers city
);
-- Move: one UPDATE. Customer without orders: INSERT into customers. Last order gone: city survives.
```

```sql
-- BAD: the transitive chain poured into one table — 1.1's anomaly trio, formalized.
CREATE TABLE orders_bad (
  id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id   BIGINT NOT NULL,
  customer_city TEXT NOT NULL   -- depends on customer_id (non-key), not on id (key)
);
```

**Common confusion** — *2NF and 3NF are "basically the same thing."* They eliminate structurally different defects (partial vs transitive), and the confusion matters because the *detector* differs: 2NF asks "which key part?" (only composite keys at risk), 3NF asks "which column?" (every table at risk). Collapsing them leaves teams checking one shape and missing the other — usually the transitive one, which hides better.

**Performance note** — 3NF splits are the joins developers most want to denormalize away ("joining customers for every order list!") — and the denormalization is sometimes right ([3.1](<../3. Judgment/3.1. Deliberate denormalization with priced trade-offs.md>) prices it). Default split: the FK join is PK-indexed and the anomaly removed is O(N) writes. The join costs microseconds; the anomaly costs incidents — split first, shortcut deliberately later, never accidentally now.

**Mentor note** — the whiteboard exercise that teaches 3NF permanently: draw `order → customer → city` as arrows, then ask "which arrow crosses a table boundary?" Juniors see the middle arrow trapped inside orders — the visual makes transitivity obvious in a way definitions never do. Arrows first (1.1's notation lesson compounds here), verdicts second.

## 3. Most production schemas stop here (3NF is the working default — know what higher forms buy before climbing)

**Definition** — a standing team convention: design to 3NF by default; climb to BCNF/4NF only for diagnosed defects, and treat 5NF as vocabulary. 3NF eliminates every anomaly class that occurs routinely (partial, transitive, repeating); higher forms address overlapping-candidate-key edge cases (BCNF) and independent multi-facts (4NF) that most domains never grow.

**What problem it solves** — two failure modes at once: *under-normalization* (1NF/2NF schemas with live anomalies — the incidents this domain prevents) and *over-normalization* (every transitive chain split into its own table regardless of lifecycle — join sprawl where twelve tables assemble one screen, each join a latency and comprehension tax). The 3NF default with named exceptions steers between them: correct enough to be anomaly-free, coarse enough to stay readable.

**Modern guidance** — encode it as review policy: "3NF unless (a) a diagnosed BCNF/4NF defect, or (b) a priced denormalization record ([3.1](<../3. Judgment/3.1. Deliberate denormalization with priced trade-offs.md>))." New tables arrive 3NF-shaped; deviations carry justification. Revisit yearly: tables that grew new dependency shapes (a column that became multi-valued, a second determiner that appeared) get re-audited — normalization is a property maintained, not a ceremony performed once.

```sql
-- GOOD: the working default — bookstore from Domain 01, audited: 1NF (no groups),
-- 2NF (single-column surrogates throughout; junction PKs carry no non-key columns),
-- 3NF (city/price/grade each live with their determiner). Anomalies: none known.
-- Higher forms: no overlapping candidate keys (BCNF vacuous), no independent
-- multi-facts per entity (4NF vacuous) — climbing buys nothing today. Recorded, dated.
```

```sql
-- BAD (over-normalized): the transitive chain split past its lifecycle —
-- cities barely queried, yet every order list joins three tables to name one.
orders → customers → cities → regions   -- four tables for "who ordered from where"
-- Each join is cheap; the twelve-join screen they compose is not — latency,
-- planner fragility, and a schema only its author navigates. 3NF permits cities
-- inside customers (city has no independent lifecycle here); splitting anyway
-- is formalism without a defect.
```

**Common confusion** — *"higher normal form always means better design."* Normal forms are defect-eliminators, not quality scores: each form removes one dependency shape. With no instance of the shape, the form is vacuous — climbing higher changes nothing except table count (up) and readability (down). "What defect does this split remove?" is the only question; silence is the answer "none — stop."

**Performance note** — the join budget is real but routinely overstated: PK-join chains of 3–5 tables resolve in microseconds on indexed keys; pain starts past ~8–10 joins per query or with fan-out multiplication (joining two independent one-to-many children explodes rows — a 4NF-shaped problem wearing a performance costume, diagnosed properly in 2.2). Count joins before fearing them; split fans out before joining them.

**Mentor note** — teach "stop at 3NF" as engineering judgment, not laziness: the senior move is knowing which defects you *don't* have. Juniors climb to 5NF from anxiety; seniors hold 3NF from diagnosis. Review praise for restraint ("good — no BCNF defect here, stopping is correct") teaches the stopping rule faster than any lecture on higher forms.
