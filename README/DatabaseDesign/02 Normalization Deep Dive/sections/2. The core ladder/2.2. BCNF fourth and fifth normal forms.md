# 2.2. BCNF fourth and fifth normal forms

## 1. BCNF closes the 3NF loophole (every determiner must be a key)

**Definition** — Boyce–Codd normal form (1974): for every non-trivial dependency `A → B`, A must be a superkey. 3NF's version has an escape clause (B may be part of *some* key); BCNF removes it. The loophole needs overlapping candidate keys to matter — the classic: enrollments keyed `{student, course}` *and* `{student, instructor}`, with `instructor → course` (each instructor teaches exactly one course) where instructor alone is no key. 3NF holds (course is key-adjacent); the anomaly lives on (instructor's course repeated per student).

**What problem it solves** — the rare-but-real residue: instructor reassigned to a new course → N enrollment rows update (update anomaly survived 3NF); a new instructor with no students has nowhere to record their course (insert anomaly); last student drops, course assignment lost (delete anomaly). Same trio as [1.1](<../1.%20Dependencies%20and%20atomicity/1.1.%20Functional%20dependencies%20the%20one%20idea%20behind%20every%20normal%20form.md>), wearing a key-overlap disguise. The fix mirrors 2NF/3NF surgery: move `instructor → course` to its own table keyed by instructor.

**Modern guidance** — suspect BCNF only where candidate keys overlap (two keys sharing columns) — which in surrogate-default schemas is nearly nowhere ([2.1](<2.1.%20Second%20and%20third%20normal%20form.md>)'s soothing truth, with the same warning: legacy natural-key tables overlap routinely). Diagnostic: list all candidate keys; for each dependency, check the determiner is a superkey. Determiner-not-a-key → split to a table keyed by the determiner. Thirty seconds once keys are enumerated — which is why [1.1's key-naming drill](<../1.%20Dependencies%20and%20atomicity/1.1.%20Functional%20dependencies%20the%20one%20idea%20behind%20every%20normal%20form.md>) precedes all of this.

```sql
-- GOOD: instructor → course lives keyed by instructor — the anomaly cannot form.
CREATE TABLE taught_by (
  instructor TEXT PRIMARY KEY,   -- the determiner IS the key: BCNF by construction
  course     TEXT NOT NULL
);

CREATE TABLE enrollments (
  student_id BIGINT NOT NULL REFERENCES students (id),
  instructor TEXT NOT NULL REFERENCES taught_by (instructor),
  grade      CHAR(1) NOT NULL,
  PRIMARY KEY (student_id, instructor)  -- course recovered by join, always consistent
);
-- Reassignment: one UPDATE on taught_by. New instructor, no students: INSERT there.
```

```sql
-- BAD: 3NF-passing, BCNF-failing — instructor → course asserted per enrollment.
CREATE TABLE enrollments_bad (
  student_id BIGINT NOT NULL,
  course     TEXT NOT NULL,
  instructor TEXT NOT NULL,
  PRIMARY KEY (student_id, course)   -- candidate key 2: {student_id, instructor} overlaps
  -- instructor → course, instructor not a key: reassignment updates N rows
);
```

**Common confusion** — *"3NF and BCNF are interchangeable in practice."* They coincide wherever keys do not overlap — i.e., nearly every surrogate-key schema, which is why practitioners conflate them harmlessly for years. The confusion bites exactly once: the legacy table with two overlapping natural keys, where "but it's 3NF!" defends a live anomaly. Know the difference for that day; coast on the coincidence every other day.

**Performance note** — BCNF splits behave like 2NF/3NF splits (PK-indexed join replaces O(N) anomaly writes). No distinct performance story — which is itself the point: higher forms cost the same cheap join shape while removing rarer defects. The price of climbing is readability (more tables), never speed.

**Mentor note** — teach BCNF as a detective story, not a definition: present the BAD table ("it's 3NF — find the anomaly anyway"). Juniors who hunt the instructor-reassignment scenario discover the loophole themselves; the definition then names what they found. One worked mystery beats ten recitations of "every determiner a superkey."

## 2. 4NF kills multivalued dependency (independent multi-facts about one thing belong apart)

**Definition** — fourth normal form (Fagin, 1977): no non-trivial *multivalued* dependencies. `person →→ skill` means: a person's skill set is independent of anything else in the row — knowing the person tells you their skills, but skills pair freely with the row's other facts. The violation: `(person, skill, language)` storing every skill×language combination — Amy's 3 skills and 2 languages need 6 rows, and adding a skill needs 2 inserts (one per language). Independent facts multiplied together.

**What problem it solves** — the combination explosion: row count becomes the *product* of independent fact counts, so single-fact changes cost fan-out writes (add a language → one row per existing skill), and the table asserts false pairings (row "Amy/SQL/French" suggests SQL relates to French — it does not). 4NF splits independent multi-facts into separate tables (`person_skills`, `person_languages`), each holding one fact type with its own lifecycle.

**Modern guidance** — the detector question: "if I list all of X's A's, does the list change when B changes?" Amy's skills don't change when she learns a language → independent → separate tables. Contrast genuine pairing (order *lines*: book+quantity *do* pair — the line is one fact, not two; no 4NF issue). Independence is the whole test: paired facts stay, independent facts split. Suspect 4NF wherever one entity accumulates two unbounded lists in one table.

```sql
-- GOOD: one fact type per table — adding a skill is one INSERT, languages untouched.
CREATE TABLE person_skills (
  person TEXT NOT NULL,
  skill  TEXT NOT NULL,
  PRIMARY KEY (person, skill)
);

CREATE TABLE person_languages (
  person   TEXT NOT NULL,
  language TEXT NOT NULL,
  PRIMARY KEY (person, language)
);
-- Amy: 3 skill rows + 2 language rows = 5 rows, each a true fact.
-- New language: 1 INSERT. New skill: 1 INSERT. No pairings asserted, none maintained.
```

```sql
-- BAD: the cross product — 3 skills × 2 languages = 6 rows of diminishing truth.
CREATE TABLE person_facts_bad (
  person   TEXT NOT NULL,
  skill    TEXT NOT NULL,
  language TEXT NOT NULL,
  PRIMARY KEY (person, skill, language)
);
-- Amy learns Korean: 3 INSERTs (one per skill). Drops SQL: 2 DELETEs.
-- Every row implies skill↔language pairing that does not exist.
```

**Common confusion** — *4NF is "3NF for multiple values."* Related but distinct: 3NF governs *which column determines which* (functional chains); 4NF governs *whether two fact lists vary independently* (multivalued pairing). A table can be 3NF-clean and 4NF-violating (the BAD table above has no transitive chain — its defect is pairing, not determination). Different detector question, different split — learn both questions, not one blur.

**Performance note** — the cross product is a storage *and* write tax (product-sized rows, fan-out writes) plus a read trap: joining two independent one-to-many children of one parent multiplies rows (the fan-out from [2.1's third promise](<2.1.%20Second%20and%20third%20normal%20form.md>)) — a performance-costume 4NF violation. Splitting fixes storage, writes, and the join trap at once; the price is two queries (or two joins) instead of one, each honest.

**Mentor note** — the independence question ("does list A change when B changes?") is the portable skill — it diagnoses 4NF, designs document boundaries (Domain 03 forward), and scopes API responses. Drill it on the team's own wide tables; every "huh, those really are independent" is a latent split found before it becomes a migration.

**Cross-links** — fan-out joins as performance symptom in [2.1](<2.1.%20Second%20and%20third%20normal%20form.md>); independent-lists reasoning reused for document embedding decisions in Domain 03 (forward — unbuilt).

## 3. 5NF is join dependency (know it exists, recognize it once a decade)

**Definition** — fifth normal form (Fagin, 1979): every non-trivial *join dependency* is implied by the keys. Concretely: if a table can be losslessly decomposed into three or more projections (supplier–part–project: "supplier S supplies part P to project J") yet no two-way split preserves all constraints, the three-way fact is genuine and the table is 5NF *by staying whole*. Paradoxically, 5NF usually means *don't split further* — it certifies the three-way table as irreducible.

**What problem it solves (rarely)** — the over-decomposition trap: a well-meaning designer splits supplier-part-project into three binary tables (supplies-part, supplies-project, part-project) and discovers spurious pairings (supplier S "supplies" part P to projects they never touched — the binary tables can't express the three-way constraint). 5NF names the shape where the whole is truer than any parts: three-way business facts (supplier×part×project, doctor×patient×treatment-protocol) that only hold jointly.

**Modern guidance** — recognition, not procedure: if a three-column relationship resists every two-way split (each split either loses constraints or invents false pairings), stop splitting — the table is the model, document the join dependency in one sentence, move on. You will apply this judgment a handful of times in a career; the value is entirely in *not* breaking what shouldn't split. Never reach for 5NF proactively; let irreducible three-way facts announce themselves through failed decompositions.

```sql
-- GOOD: the irreducible three-way fact — kept whole, documented, constrained jointly.
CREATE TABLE supply (
  supplier TEXT NOT NULL,
  part     TEXT NOT NULL,
  project  TEXT NOT NULL,
  PRIMARY KEY (supplier, part, project)
  -- the composite PK IS the enforcement: the only legal state is the set of true triples.
  -- join dependency recorded, not split: "S supplies P to J" holds only jointly.
  -- A two-way split (supplier_parts + supplier_projects) would invent pairings
  -- (S supplies P to EVERY project of S) — false. The whole stays.
);
-- Design note (the deliverable): "supply is 5NF-whole: binary decompositions tried
-- 2026-09, both invented false pairings. Do not split without re-proving."
```

```sql
-- BAD: the reflexive three-way split — binary tables asserting facts nobody stated.
CREATE TABLE supplier_parts_bad    (supplier TEXT NOT NULL, part TEXT NOT NULL, PRIMARY KEY (supplier, part));
CREATE TABLE supplier_projects_bad (supplier TEXT NOT NULL, project TEXT NOT NULL, PRIMARY KEY (supplier, project));
-- Joining them claims "S supplies P to J" for every J of S — including projects S never
-- sent P to. The split manufactured data. (When the pairings ARE true independently,
-- this split is correct — that is 4NF's case, not this one. Independence decides.)
```

**Common confusion** — *"5NF means split into the smallest possible tables."* The opposite: 5NF tells you when to *stop*. The normal-form ladder is not a splitting contest — each form removes one defect shape, and 5NF's shape (harmful join dependency) is absent precisely when the three-way table is honest. "Further normalized" is not "further split"; read the defect, not the direction.

**Performance note** — three-way tables join in three directions; index all three rotations you query (`(supplier, part)`, `(supplier, project)`, `(part, project)` as needed — composite leading-column rules from Databases 02 apply). The honest whole is cheaper than the dishonest split plus compensating application logic that re-imposes the lost constraint per query.

**Mentor note** — teach 5NF as a story ("the split that manufactured data"), never as a definition first. One anecdote inoculates against over-decomposition forever; the formalism (`⋈-dependency implied by keys`) serves only readers who will publish, not practitioners who will model. Vocabulary for interviews, judgment for work — label which is which.
