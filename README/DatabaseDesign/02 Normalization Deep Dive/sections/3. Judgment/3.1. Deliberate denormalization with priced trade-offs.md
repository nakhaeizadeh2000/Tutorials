# 3.1. Deliberate denormalization with priced trade-offs

## 1. Normalize first, denormalize deliberately (you cannot price a shortcut you never measured)

**Definition** — denormalization is reintroducing controlled redundancy into a normalized schema for measured benefit: a cached count, a copied name, a precomputed total. *Deliberate* is the load-bearing word — the normalized shape exists first (designed, reviewed), the shortcut is added second (measured, recorded), and the normalized source of truth remains queryable so the copy can be rebuilt and audited.

**What problem it solves / history** — every production schema eventually meets the query that normalization punishes: the dashboard aggregating millions of lines per page load, the order list joining five tables for one screen, the report scanning history the normalized shape spreads wide. The naive responses are binary — suffer the query, or corrupt the model "temporarily" (permanently). Deliberate denormalization is the third way: keep the truth normalized, maintain a documented copy for the hot path, and price the maintenance honestly.

**Modern guidance** — the sequence is non-negotiable: (1) build normalized (2.1's default); (2) measure the hot query (EXPLAIN, production timings — Databases 02/06 mechanics); (3) prove the shortcut fixes it (before/after numbers, not hopes); (4) record the decision (second promise); (5) automate consistency (trigger, application write-through, or materialized view — third promise). Shortcuts taken in any other order are anomalies with good intentions — and good intentions don't survive the first inconsistent read.

```sql
-- GOOD: truth normalized, hot-path copy maintained — both shapes present, roles clear.
CREATE TABLE orders (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id),
  placed_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE order_lines (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id BIGINT NOT NULL REFERENCES orders (id),
  quantity INT NOT NULL CHECK (quantity > 0),
  price    NUMERIC(10, 2) NOT NULL CHECK (price >= 0)
);
-- The dashboard's per-order total: maintained as a materialized view (third promise),
-- NOT as a total column on orders — the copy has an owner (the database), a refresh
-- policy, and a rebuild path. The normalized lines remain the truth.
```

```sql
-- BAD: the shortcut first — a total column with no owner, no policy, no record.
CREATE TABLE orders_bad (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL,
  total       NUMERIC(12, 2) NOT NULL DEFAULT 0  -- who updates this? When? What if they forget?
);
-- Every line INSERT/UPDATE/DELETE must remember the column — across all writers,
-- backfills, and admin scripts. The first forgotten path invents money.
```

**Common confusion** — *"denormalization means normalization was wrong."* No — it means the workload has a hot path the general shape serves expensively. The normalized schema is still correct (and still the truth, rebuild source, and audit trail); the copy is a performance structure wearing a business costume. Teams that feel guilty about copies under-maintain them; teams that feel proud over-copy. Both emotions are wrong — copies are priced infrastructure, neither sin nor virtue.

**Performance note** — price both sides before deciding: shortcut savings (hot query before/after — milliseconds × executions/day) versus shortcut rent (write amplification per line change, refresh cost, storage, staleness window). Most denormalizations pay rent on every write to save on some reads — profitable only when read:write ratios justify it (dashboards: yes; OLTP order creation: usually no). The ratio is measured, never assumed.

**Mentor note** — teach "normalize first" as professional ethics, not pedagogy: juniors who denormalize from day one never learn what the copy costs (they've never seen the truth-only shape run). Seniors who demand the normalized baseline aren't gatekeeping — they're ensuring the shortcut's price is denominated against reality. Require the baseline measurement in every denormalization review.

## 2. Every shortcut gets a decision record (what was copied, what breaks, who keeps it consistent)

**Definition** — a denormalization decision record: a dated, attributed note stating the copied fact, the shortcut shape, the measured justification, the consistency mechanism, the staleness tolerance, and the revisit trigger. It lives beside the schema (migration comment, ADR, or schema COMMENT) — where the next hire finds it before touching either copy.

**What problem it solves** — undocumented copies rot asymmetrically: the writer who knew the maintenance rule leaves; successors see two sources for one fact, trust the wrong one, and "fix" consistency by deleting the maintenance job ("why does this trigger exist?"). Or worse — nobody knows the copy is stale-tolerant, so a report reads it as truth and finance reconciles against fiction. The record converts tribal maintenance into scheduled engineering.

**Modern guidance** — six fields, no more, no fewer: (1) *copied fact* (order total = Σ lines); (2) *shortcut shape* (materialized view `order_totals`, CONCURRENTLY refreshed); (3) *justification with numbers* ("dashboard p95 2.1s → 40ms at 50k orders/day, measured 2026-09"); (4) *consistency mechanism* (refresh job, owner named); (5) *staleness tolerance* ("5 minutes — dashboard-only, never finance"); (6) *revisit trigger* ("1M orders/day or finance adoption — then synchronous trigger or drop the copy"). Field 6 is the most skipped and most valuable: shortcuts without expiry become permanent fixtures nobody re-prices.

```sql
-- GOOD: the record travels with the schema — found in psql, not in departed-Slack.
COMMENT ON MATERIALIZED VIEW order_totals IS
  'DENORMALIZATION RECORD (ADR-021, 2026-09): per-order total = sum(lines).
   Justification: dashboard p95 2.1s → 40ms at 50k orders/day.
   Mechanism: refresh job every 5 min (owner: platform team).
   Staleness: 5 min tolerated — dashboard only, NEVER finance (finance reads lines).
   Revisit: 1M orders/day or finance adoption → synchronous trigger or drop copy.';
```

```sql
-- BAD: the copy exists, the reasoning evaporated — archaeology required.
-- (A materialized view with no comment, a total column with no ADR, a trigger
--  whose purpose died with its author. The next hire faces two sources of truth
--  and zero guidance — and will choose wrong exactly when it matters.)
```

**Common confusion** — *"small copies don't need records."* Small copies grow: the dashboard total gets adopted by finance ("it's right there!"), the tolerated staleness becomes a reconciliation gap, the missing record becomes a missing defense. Record cost is one paragraph; the incident it prevents is a quarter-end. Size of copy, size of record — both small, both non-optional.

**Performance note** — field 5 (staleness tolerance) is a performance parameter in disguise: tighter tolerance means more frequent refreshes (more write load); looser means cheaper maintenance. Stating it explicitly lets the team tune refresh cost against business need instead of refreshing "as often as possible" (waste) or "when someone complains" (incident).

**Mentor note** — review denormalization PRs by reading the record first, code second: missing field → request changes before discussing implementation. Juniors learn that justification precedes mechanism; seniors model it by writing records for their own shortcuts (especially theirs — authority without records teaches that rules are for others).

## 3. Materialized views are honest denormalization (the database maintains the copy)

**Definition** — a materialized view stores a query's result as a table-like object, refreshed on policy (`REFRESH MATERIALIZED VIEW`, with `CONCURRENTLY` for lock-free refreshes given a unique index). The copy's maintenance is declarative (the view *definition*) and mechanical (the refresh *job*) — no application code stands between truth and copy, so no forgotten path can desynchronize them beyond the stated staleness window.

**What problem it solves** — application-maintained copies (triggers hand-written per table, write-through logic in three services, total columns updated "wherever lines change") desynchronize through enumeration failure: the maintainer lists every write path, and the list is always incomplete (backfill scripts, new services, admin consoles). Materialized views eliminate enumeration — the refresh recomputes from truth wholesale, so *every* write path is covered by construction, including ones that don't exist yet.

**Modern guidance** — prefer materialized views for aggregate/read-model copies (totals, counts, rollups, leaderboards); reserve triggers/write-through for row-level copies needing sub-refresh latency (a customer's current balance, an order's live status). Refresh policy follows staleness tolerance (second promise's field 5): `CONCURRENTLY` on a schedule for dashboard-grade freshness (needs a UNIQUE index — verified below); plain refresh in maintenance windows for daily-grade. Monitor refresh duration as a first-class metric — a refresh slower than its interval is a silent staleness breach.

```sql
-- GOOD: the copy maintains itself — definition checked in, refresh scheduled, rebuild trivial.
CREATE MATERIALIZED VIEW order_totals AS
  SELECT order_id, sum(quantity * price) AS total
  FROM order_lines
  GROUP BY order_id;

CREATE UNIQUE INDEX order_totals_uidx ON order_totals (order_id);
-- Scheduled: REFRESH MATERIALIZED VIEW CONCURRENTLY order_totals;  -- no read locks
-- Rebuild from truth: full REFRESH (non-concurrent) any time — the lines never lie.
-- Staleness: bounded by the schedule — stated in the record, never discovered.
```

```sql
-- BAD: application write-through — every line mutation must remember the total,
-- in every service, script, and console, forever.
-- INSERT INTO order_lines ...; UPDATE orders SET total = total + $x WHERE id = $o;
-- Backfill Tuesday: 2M historical lines loaded, totals untouched — dashboard now
-- reports fiction with full confidence. The refresh that would have fixed it
-- doesn't exist, because the copy has no owner but "everyone" (i.e., no one).
```

**Common confusion** — *"materialized views are always stale, so they're always wrong."* Staleness is a *specified* property (field 5), not a defect — dashboard-grade consumers tolerate minutes; finance-grade consumers read truth. "Wrong" means "violates its contract"; a 5-minute view read at minute 3 is correct. The defect is unstated staleness (application copies with unknown lag), not bounded staleness with a stated window.

**Performance note** — CONCURRENTLY costs more per refresh (diff + apply vs rebuild) but never blocks readers — the right default for anything user-facing. Watch the crossover: refresh duration approaching the interval means the copy no longer meets its staleness contract — responses in ascending desperation: plain refresh in low-traffic windows, incremental strategies (pg_ivm-style, version-dependent — check support as of your PostgreSQL), or promoting the copy to trigger-maintained synchronous truth-adjacent. Measure refresh duration; alert on it.

**Mentor note** — frame the choice as ownership, not technology: "who maintains this copy when you're on holiday?" Materialized view: the database, on schedule. Trigger: the trigger, on every write. Application: whoever remembers, hopefully. Juniors who answer the holiday question choose correctly without memorizing any comparison table — ownership reasoning transfers to caches, replicas, and every other copy in the system.
