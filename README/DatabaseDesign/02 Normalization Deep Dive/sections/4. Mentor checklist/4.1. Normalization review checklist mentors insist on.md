# 4.1. Normalization review checklist mentors insist on

## 1. Read every table as dependencies (list what determines what before approving any schema)

**Definition** — the review's first pass: for each table in the PR, write the dependency sentences (`order_id → customer_id`, `customer_id → city`) before looking at any query, index, or application code. The schema is approved or rejected on the sentences — everything else is commentary. A table whose dependencies the reviewer cannot list in two minutes is not ready, whatever the migration looks like.

**What problem it solves** — reviews that start from DDL syntax ("missing semicolon," "wrong type") approve anomalous schemas with perfect formatting, while reviews that start from queries ("will this be slow?") optimize shapes that shouldn't exist. Dependencies-first ordering forces the structural verdict before the cosmetic and performance ones — catching the misplaced `customer_city` while it's still a PR comment, not a backfill ticket.

**Modern guidance** — the review template, filled per table: (a) candidate keys named; (b) each non-key column's determiner stated; (c) normal form claimed (1NF/2NF/3NF/higher — with the loophole checked for BCNF where keys overlap); (d) violations listed with records ([3.1](<../3. Judgment/3.1. Deliberate denormalization with priced trade-offs.md>)). Authors fill it; reviewers verify it. Empty template → request changes without reading further — the discipline is the review.

```sql
-- GOOD: the review artifact for orders — four lines that decide everything.
-- Table orders(id PK, customer_id FK NOT NULL, placed_at):
--   (a) keys: {id} (sole candidate — surrogate default).
--   (b) determiners: id → customer_id, id → placed_at. No partial (single-column key),
--       no transitive (both describe the order event itself).
--   (c) claimed: 3NF. (d) violations: none.
-- Verdict: approve structure; proceed to indexes/queries.
```

```sql
-- BAD: the review that never happened — approved on syntax, anomalous on arrival.
-- Table orders_bad(id PK, customer_id, customer_city, promo_name):
--   (nobody asked) customer_city → determiner customer_id (non-key): 3NF violation, live.
--   (nobody asked) promo_name → determiner promo_code? No promo_code column at all —
--     the name floats without its key: even the dependency is unstatable.
-- Verdict that should have been: request changes, split customers + promotions out.
```

**Common confusion** — *"this slows reviews to a crawl."* The template takes minutes per table and prevents backfill migrations that take days — the highest-ROI minutes in schema work. Reviews feel slower for two weeks (learning the questions), then faster permanently (anomalies stop arriving disguised as features). Measure review latency if skeptics persist; the numbers side with dependencies.

**Performance note** — dependency review is upstream performance work: every anomaly removed is O(N) writes avoided, every unjustified split questioned is join tax examined. The checklist's performance value compounds — schemas reviewed this way rarely need heroic tuning later, because their shapes were reasoned about before their queries.

**Mentor note** — run the template on the team's *existing* schema as a training exercise before enforcing it on PRs: each table audited, dependencies listed, violations found (there will be several — every legacy schema has them). The findings become the team's first denormalization records (write them!) and the template's best advertisement: "it found our three anomalies in an hour."

## 2. Demand the anomaly story (for each redundancy: show the update path that keeps copies consistent)

**Definition** — for every duplicated fact the review finds (or the author admits), the author narrates the anomaly trio: the exact UPDATE path (which rows, which transaction, what partial failure leaves behind), the INSERT path (how the fact is born without its carriers), and the DELETE path (how the fact survives its last carrier). Vague answers ("the app handles it") fail; named mechanisms (trigger X, job Y, view Z with refresh policy) pass.

**What problem it solves** — redundancies defended by hand-waving ("we'll keep them in sync") desynchronize on the first forgotten path — and the forgetting is structural: no author enumerates backfills, consoles, and future services. The anomaly story forces enumeration *now*, when the redundancy is still a proposal: unlistable paths become visible as risk, and visible risk gets a mechanism (or gets rejected). Stories are load tests for maintenance claims.

**Modern guidance** — the three questions, asked verbatim in review: (1) "Customer moves — show me the UPDATE. All rows? One transaction? What does a crash mid-way leave?" (2) "New customer, no orders — where does the city live until the first order?" (3) "Last order deleted — who preserves the city, and where?" Acceptable answers name constraints, jobs, or views with policies; "the service layer" alone is insufficient (which service? which method? what about the console?). Record accepted stories beside the denormalization record ([3.1](<../3. Judgment/3.1. Deliberate denormalization with priced trade-offs.md>)).

```sql
-- GOOD: the story with named mechanisms — reviewable, testable, ownable.
-- Redundancy: order_totals.total copies sum(order_lines).
-- (1) UPDATE path: none needed — REFRESH CONCURRENTLY every 5 min recomputes wholesale;
--     crash mid-refresh leaves the previous complete snapshot (atomic swap).
-- (2) INSERT path: new orders appear in totals at next refresh — 5-min window, documented.
-- (3) DELETE path: deleted orders vanish at next refresh — same window.
-- Verdict: story holds — mechanisms named, windows bounded, owner assigned.
```

```sql
-- BAD: the story that isn't — "the app" as universal solvent.
-- Redundancy: orders_bad.total mirrors lines.
-- (1) "The order service updates it." Which method? The bulk-import script? The admin
--     console's manual line edit? The data-fix migration last Tuesday? Silence.
-- (2) "It's DEFAULT 0 until lines exist." So every new order reports total 0 as fact?
-- (3) "Deletes... do we delete lines?" Unknown. The story has no ending because the
--     design has no owner. Verdict: request changes — name mechanisms or drop the copy.
```

**Common confusion** — *"telling stories doesn't scale — big schemas need automation."* The story *selects* the automation: unmaintainable-by-narration redundancies get materialized views (self-maintaining); narratable ones get their mechanism blessed. Stories don't replace automation — they audit whether the automation covers reality. Skipping them automates the happy path and schedules the incident.

**Performance note** — anomaly stories surface write amplification early ("every line change rewrites the total" — quantified per story) — the pricing input [3.1](<../3. Judgment/3.1. Deliberate denormalization with priced trade-offs.md>) demands. Stories told at review time are load estimates; stories told at incident time are postmortems. Same content, vastly different cost.

**Mentor note** — teach juniors to *volunteer* the story before being asked: "the redundancy here is X; update path Y; insert Z; delete W." Volunteered stories signal senior thinking louder than any correct schema — they show the author models maintenance, not just structure. Praise volunteered stories publicly; the team imitates what gets praised.

## 3. Bless each violation in writing (unnamed denormalization is debt; named denormalization is design)

**Definition** — the review's closing act: every accepted deviation from 3NF gets its blessing recorded — approver, date, denormalization record link, revisit trigger — in the PR itself. Unblessed violations (merged silently, "we'll document later") are tech debt by definition: cost without a ledger. Blessed violations are design: cost with a ledger, an owner, and an expiry.

**What problem it solves** — the "temporary" copy that became load-bearing: merged without record during a launch crunch, discovered two years later serving finance from a dashboard-tolerance refresh, untouchable because nobody knows what depends on it. Blessings prevent fossilization — the revisit trigger fires, someone re-prices, the copy is kept, fixed, or dropped *on schedule* instead of during an audit panic. Records are how temporary stays temporary.

**Modern guidance** — the blessing format, one comment per violation in the merging PR: "Blessed: `order_totals` MV (ADR-021) — approver @senior, 2026-09, revisit at 1M orders/day or finance adoption." Plus a tracking habit: blessed violations listed in a discoverable register (ADRs indexed, schema COMMENTs greppable — `COMMENT ... 'DENORMALIZATION RECORD'` prefix from 3.1 makes them findable). Yearly review of the register is a calendar event, not an intention — intentions don't survive roadmap pressure.

```sql
-- GOOD: the blessing — visible, attributed, expiring.
-- PR comment: "Blessed: order_totals MV (ADR-021) — @senior 2026-09.
--  Revisit: 1M orders/day or finance adoption. Register: ADR-021 indexed under
--  'denormalization'. Next audit: 2027-09 (calendar invite sent)."
-- The copy now has a birthday and a review date — it cannot fossilize unnoticed.
```

```sql
-- BAD: the silent merge — "temporary" with no half-life.
-- PR comment: "lgtm" (the total column ships with no record, no approver, no trigger).
-- Two years later: finance reconciles against it, the dashboard team owns the refresh
-- nobody scheduled, and removing it breaks three downstream extracts nobody mapped.
-- "Temporary" lasted longer than most employees. The blessing would have cost a sentence.
```

**Common confusion** — *"blessings are bureaucracy that slows shipping."* One sentence per violation, written while context is hot, versus archaeology under audit pressure while context is cold. Bureaucracy is cost without benefit; blessings are the cheapest insurance in schema work — the teams that skip them don't ship faster, they debug longer.

**Performance note** — the register doubles as a performance-review input: yearly re-pricing ("still 50k orders/day? refresh still 5-min?") catches copies whose rent outgrew their savings (traffic shifted, hot query cooled). Blessings with triggers turn denormalization from permanent fixtures into leased performance — returned when the lease expires.

**Mentor note** — model blessings on your own PRs first, especially senior-authored shortcuts ("blessing my own copy — ADR linked, revisit set"). Juniors imitate authority: a senior's blessing teaches the ritual; a senior's silent merge teaches that rituals are for others. The register's authority comes from its most senior entries, not its strictest enforcement.
