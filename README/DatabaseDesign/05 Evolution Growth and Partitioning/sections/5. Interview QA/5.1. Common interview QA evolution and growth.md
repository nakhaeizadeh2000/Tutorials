# 5.1. Common interview QA evolution and growth

## 1. Migrate a live table on a whiteboard (expand-contract narration)

**Definition** — the exercise: *"add a non-nullable email to 50M users with zero downtime"* (the interview staple). The graded artifact is phased narration: expand (nullable add — old code safe), migrate (dual-write + chunked backfill + reader switch + parity proof), contract (drop old — grep-witnessed) — each phase with its rollback, each deploy safe against both neighbors. Candidates narrating phases pass; candidates writing one ALTER fail even with correct syntax (syntax was never the subject — coexistence was).

**What problem it solves** — migration questions filter for production experience withouch requiring it (students can learn phases; only production teaches flag-day pain — the question distinguishes studied procedure from assumed atomicity). Interviewers listen for phase vocabulary (expand/migrate/contract), coexistence reasoning (old writers? new readers? stragglers?), and rollback per phase (each phase independently reversible — except contract, verified first). Vocabulary + coexistence + rollback = the senior signal; single-statement answers = the hope signal.

**Modern guidance** — the five-minute shape: (1) *expand* (1 min — "nullable add, old code ignores, rollback = drop column"); (2) *dual-write + backfill* (2 min — "new code writes both, history chunked 5k with lag throttle, sample-timed wall-time +50%"); (3) *switch + verify* (1 min — "readers to new, parity counts + samples, stragglers named — cron, BI, cached plans"); (4) *contract* (1 min — "old writes stopped, one-cycle freeze, grep zero, drop witnessed — no rollback past verification, stated"). Stragglers named unprompted (the expert tell — interviewers note who remembers cron workers and BI extracts without prompting). Rollback stated per phase (calm reversibility, designed — not "we'd roll back," but how, per phase).

```sql
-- GOOD (whiteboard narration, 50M users — 5 min):
-- "Expand: ADD COLUMN email TEXT nullable — old INSERTs safe, rollback DROP COLUMN.
--  Dual-write new code (both shapes), backfill 5k chunks keyset-ordered, lag-throttled,
--  wall-time from 10k-sample +50%. Switch readers with COALESCE fallback (ticketed
--  removal), parity: zero-NULL count + samples. Stragglers: cron v3, BI extract v9 —
--  bounded, verified. Contract: stop old writes, freeze one cycle, grep zero, DROP.
--  Verification precedes contract — contracted shapes don't return."
ALTER TABLE users ADD COLUMN email TEXT;  -- phase 1: additive, both versions safe
```

```sql
-- BAD (whiteboard): the single statement — correct syntax, failed interview.
ALTER TABLE users ADD COLUMN email TEXT NOT NULL;  -- (50M-row rewrite mid-deploy?
-- Old writers failing fleet-wide? Backfill where? Stragglers who? Rollback how?)
-- "Then update the code." The migration assumed atomicity; the system deploys
-- incrementally; the interviewer heard hope where phases belong. Syntax: A+.
-- Engineering: not hired.
```

**Common confusion** — *"small tables in interviews don't need phases."* Interviewers choosing 50M rows chose deliberately (phases required — the number is the test); candidates waiving phases for "small" tables miss that the number *is* the scenario. Even at small scale, narrating phases shows procedure (graded) while single statements show syntax (ungraded). Scale waives nothing in interviews — the scenario's number answers the waiver preemptively. Phase the 50M; mention you'd phase smaller too (habit signal, bonus marks).

**Performance note** — volunteer backfill math unprompted ("5k chunks, 2s per chunk sampled → 50M rows ≈ 6 hours +50% → overnight window with lag abort at 5s" — estimation live, assumptions stated). Interviewers grading performance awareness note estimators vs hopers instantly — the sample-extrapolate-margin reflex in one sentence signals production backfill experience (or well-studied procedure — indistinguishable live, hired either way).

**Mentor note** — drill as timed narration (5 minutes, phases + stragglers + rollback — graded separately: phases named? coexistence both directions? stragglers volunteered? rollback per phase?). Candidates reliably fix narration in three timed rounds (same prescription as all QA leaves — time them, grade phases, watch procedure replace syntax-focus). The straggler habit deserves its own checkbox: volunteered stragglers predict offers better than correct DDL.

## 2. Partition for a workload (key choice derived from queries — pruning demonstrated)

**Definition** — the follow-up: *"this events table hits 500M rows — partition it."* The graded skill is key derivation from predicates (not from data): dominant queries listed first (recency ranges? tenant equality? point lookups?), key matched to predicates (RANGE/time, LIST/tenant, HASH/id-spread), pruning demonstrated per pattern (EXPLAIN-verified, or narrated precisely enough to convince), grain budgeted (pieces/year × horizon ≤ low hundreds), count justified. Key-from-queries is the senior order; key-from-data ("hash by id, obviously") is the hope order.

**What problem it solves** — partitioning questions filter for workload thinking (most candidates know partition *types* as vocabulary; few derive keys from predicates live). Interviewers vary the workload deliberately ("time-series events" then "multi-tenant orders" then "uniform sessions") watching whether the key *changes* (RANGE → LIST → HASH across scenarios — adaptivity graded, same as [Domain 04 §5.1](<../../../04 Relationships at Scale/sections/5. Interview QA/5.1. Common interview QA relationships at scale.md>)'s hierarchy triplets). Static keys across varying workloads signal fashion; derived keys signal engineering.

**Modern guidance** — the ninety-second shape per scenario: (1) predicates first ("dominant queries? recency ranges — 800k/day; point lookups rare" — asked, or stated from the scenario); (2) key derived ("RANGE by month on occurred_at — prunes recency to 1–2 pieces"); (3) pruning demonstrated ("EXPLAIN shows September predicate touching September piece only — verified pattern, recorded per table"); (4) grain budgeted ("monthly × 10yr = 120 pieces — budget 500, trigger 300; automation creates ahead"); (5) what would flip it ("tenant-isolation requirement → LIST subpartition; uniform point-load → HASH — triggers named"). Five beats, derivation audible, adaptivity across scenarios the pass criterion.

```
-- GOOD (spoken, events scenario, 90 seconds):
-- "Predicates: recency ranges dominate (800k/day), point lookups rare. Key: RANGE
-- by month on occurred_at — September queries prune to September piece (EXPLAIN
-- verified — single-partition plan). Grain: monthly × 10yr = 120 pieces (budget 500).
-- PK includes occurred_at (uniqueness across pieces required). Flip: tenant-isolation
-- demand → LIST subpartition; uniform point-load → HASH. Maintenance per piece
-- (VACUUM minutes), archival DETACHes monthly (retention-aligned grain)."
```

```
-- BAD (spoken): the data-derived key — partitioning the column, not the workload.
-- "Hash-partition by id — even spread, no hotspots." (Predicates? Unasked — recency
-- queries fan out to ALL partitions (id hash says nothing about time); pruning zero;
-- costs fully paid (planning × N, maintenance × N), benefits never collected. Even
-- spread of the wrong key is evenly-distributed waste. The workload asked time;
-- the answer gave hash. Question unheard, decoration delivered.)
```

**Common confusion** — *"partitioning is advanced — juniors shouldn't need it."* Key derivation is predicate thinking (which queries constrain what — the catalog habit from [Domain 03](<../../../03 Document Modeling for Scale/sections/1. Aggregates and access/1.2. Access patterns drive document shape.md>)), not advanced machinery — juniors deriving keys from predicates outscore seniors reciting types. Interviews grade derivation at every level; "advanced" describes the machinery (DETACH mechanics, planner behavior — Databases 02), never the key choice. Choose keys early in careers; operate pieces with seniority.

**Performance note** — volunteer the pruning number ("500M rows → 20M September piece — 25× less I/O per recency query; planning overhead per query negligible at 120 pieces") — quantified pruning beats asserted pruning in every scorecard. Numbers with EXPLAIN backing ("single-partition plan, verified pattern") signal procedure over vocabulary — the expert tell in ninety seconds. Quantify, verify, state — the performance-answer shape, partitioning edition.

**Mentor note** — drill as scenario triplets (time-series / multi-tenant / uniform-sessions — same sitting, three keys, one procedure — twin of 04/5.1's hierarchy triplets): adaptivity trained explicitly, verdict-switching graded ("did the key change across scenarios?" — switching correct is pass; consistency across workloads is failure). Fashion is consistent; engineering adapts — train adaptation, grade switching, hire switchers.

## 3. Capacity-plan a feature (rows-per-day math live — headroom priced, triggers named)

**Definition** — the estimation exercise: *"how much storage will this feature need in a year?"* (the staff-level filter). The graded artifact is live arithmetic: rates sourced (asked or stated with source — "50k orders/day measured, +8%/mo forecast"), widths measured (not guessed — "420B/row weighed via pg_total_relation_size"), math shown (width × count × indexes × overhead — the [2.1](<../2. Growth and capacity/2.1. Capacity modeling with measured triggers.md>) spreadsheet compressed to two minutes), triggers named (partition/archive/upgrade at numbers with owners). Arithmetic with sources beats adjectives with confidence at every level.

**What problem it solves** — estimation questions filter for quantitative judgment (the staff/senior divider — most candidates describe ("it'll grow"), few compute ("27M rows × 420B × 2.4 × 1.2 = 33GB, 7% of budget")). Interviewers listen for sourced rates (measured > forecast > guessed — precision stated honestly), measured widths (weighed, not column-guessed), and trigger discipline (numbers with owners, not "later"). Computation live, assumptions labeled, headroom priced — the complete senior estimation shape in under three minutes.

**Modern guidance** — the three-minute shape: (1) *rates* (30s — "orders 50k/day measured prod, lines ×3, events 2M/day roadmap — sources stated, dates attached"); (2) *widths* (30s — "420B/row weighed (pg_total_relation_size ÷ count) — measured, not summed from types"); (3) *math* (60s — "50k × 540d = 27M rows × 420B = 11GB heap × 2.4 idx × 1.2 overhead ≈ 33GB — 7% of 500GB budget"); (4) *triggers* (60s — "partition orders at 80M (platform), archive events >13mo (data), RAM review at 70% working set — owners named, quarterly re-derivation calendared"). Unknowns bounded ("returns unlaunched — excluded with re-measure date, not zeroed silently"). Four beats, numbers throughout, triggers closing — estimation as performance, arithmetic as evidence.

```sql
-- GOOD (spoken with live math, 3 min — the staff shape):
-- "Rates: 50k orders/day measured (prod, Sept), +8%/mo forecast Q4 — sources stated.
--  Widths: 420B/row weighed — measured via pg_total_relation_size, not type-summed.
--  Math: 50k × 540 days = 27M rows × 420B ≈ 11GB heap × 2.4 indexes × 1.2 overhead
--  ≈ 33GB — 7% of the 500GB budget. Triggers: partition at 80M rows (platform owns),
--  archive events past 13 months (data owns), RAM review at 70% (monthly gauge).
--  Unknowns: returns unlaunched — excluded, re-measure dated week-2 post-launch."
```

```sql
-- BAD (spoken): the adjectives estimate — confident, sourceless, triggerless.
-- "It should scale fine — Postgres handles billions of rows. We'll monitor and
-- optimize as needed." (Rates? Unasked. Widths? Unguessed. Math? Absent. Triggers?
-- "Monitor" uninstrumented. Every sentence defers quantification to a future that
-- arrives as incidents. Confidence without arithmetic is optimism with a title —
-- titles don't page, but unmodeled growth does.)
```

**Common confusion** — *"estimation interviews want exact answers."* They want *honest arithmetic*: sourced rates (precision labeled), measured widths (method stated), explicit margins (+50% on samples, +20% overhead — margins named, not hidden), bounded unknowns (excluded with re-measure dates, never zeroed). "≈33GB ±40%, sources attached" beats "33GB exactly" (false precision — interviewers distrust round certainty) and beats "no idea" equally. Ranges with sources hire; precision without sources postures; silence fails.

**Performance note** — close with the residency angle ("33GB total, hot working set ~8GB — resident in 64GB RAM with 8× headroom; cliff date from growth math: month 30 at current rates — calendared review month 24") — RAM-headroom thinking unprompted signals the performance awareness that separates senior estimators from junior calculators. Totals answer storage; residency answers speed; both in one close — the complete answer in one extra sentence.

**Mentor note** — teach estimation as Fermi-with-sources (round numbers, explicit margins, stated unknowns — juniors practicing live math discover arithmetic is performable, not just reviewable). Drill weekly with rotating features (orders/events/uploads/sessions — same four beats, fresh numbers): speed builds confidence, sources build honesty, triggers build completeness. Estimators are made by repetition — three timed rounds convert "bad at math" juniors into measured seniors. Math out loud, sources attached, triggers named — hire that candidate (or become them).
