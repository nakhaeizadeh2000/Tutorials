# 6.1. Boundaries what is covered elsewhere

## 1. Migration mechanics live in Databases 02 (DDL safety, CONCURRENTLY, locks — linked, not repeated)

**Definition** — outward boundary: how the engine *executes* what this domain *sequences*. Expand/contract names the phases; Databases 02 ([Postgres Deep Dive](<../../../../Databases/02 Postgres Deep Dive/README.md>)) teaches the DDL safety underneath — `CONCURRENTLY` index builds, lock behavior per statement type, transaction discipline for migrations, constraint mechanics (`NOT VALID` + `VALIDATE` execution). Backfill batching names chunking; Databases 02/05 teach the lock and transaction behavior that sizes chunks. Neither track repeats the other — procedure here, machinery there, links between.

**What problem it solves** — duplicated coverage rot (two `CONCURRENTLY` explanations drifting apart — one current, one stale, readers trusting the wrong one) and misplaced coverage confusion (lock mechanics taught beside phase sequencing suggests they're one decision — they're two: what order (here), then how heavy each step (there)). Single source of truth per PROMPT.md §5: each concept has one home; this leaf maps the crossings so readers never wonder and writers never paste.

**Modern guidance** — the crossing map, by need: constraint/index DDL, `CONCURRENTLY` builds, and migration-safe DDL patterns → [Databases 02](<../../../../Databases/02 Postgres Deep Dive/README.md>); transactions, lock queues, and long-transaction behavior (backfill chunk sizing, purge batching physics) → [Databases 05](<../../../../Databases/05 Transactions Consistency and Integrity/README.md>); keyset mechanics (backfill cursors, never OFFSET) → [Databases 07 §2.2](<../../../../Databases/07 Production Data Use and Interview Mastery/sections/2. Review and design/2.2. Data API contracts.md>); EXPLAIN and size measurement (`pg_*_size` family) → [Databases 02/06](<../../../../Databases/06 Performance Backup and Operations/README.md>); full orientation → [Databases track index](<../../../../Databases/README.md>). Inbound, Databases boundary leaves defer evolution depth here — each track owning its side.

**Common confusion** — *"this track assumes migrations — where do I learn to run them?"* (Asked in every boundary leaf; restated for direct arrivals.) Databases 02 for DDL safety and constraint mechanics, 05 for transaction behavior — in order, then return here for sequencing. The tracks compose: Databases makes you operational, Database Design makes you deliberate — phases are deliberate, locks are operational, both required, each owned. Either order works; skipping either half doesn't.

**Performance note** — none specific — performance mechanics (lock monitoring, lag alerting, size-measurement functions) are Databases 02/05/06 territory by design. This domain's performance contribution is upstream: phased migrations distribute load across deploys, chunked backfills bound lag, budgeted grains bound planning — decisions that make the mechanics' job possible. Unphased migrations can't be tuned, only survived — decide correctly here; execute calmly there.

**Mentor note** — same navigation discipline as every boundary leaf in this track (fifth restatement, permanent value): mechanics questions get links, not lessons — then the *why* of the boundary. Learners who navigate the map become autonomous; mentors who re-teach across boundaries train dependency. The boundary is curriculum, not convenience.

**Cross-links** — the map above is the complete outward set for mechanisms; versioning twin and operations neighbors follow.

## 2. Versioning discipline lives in Domain 03 (schemaVersion, lazy/eager — the document twin)

**Definition** — sibling boundary: [Domain 03 §3.2](<../../../03 Document Modeling for Scale/sections/3. Patterns and change/3.2. Versioning and shape migration.md>) owns versioning and shape migration for documents (schemaVersion fields, lazy-vs-eager economics, discriminators); Domain 05 owns expand/contract and compatibility for relational schemas. Same problem (shapes change under live traffic), mirrored solutions (versioned adaptation vs phased deploy — both avoid flag-days; budgets vs phases — both bound transitions). Neither domain repeats the other — the twin is linked wherever the lesson transfers, restated never.

**What problem it solves** — twin confusion (applying document versioning to relational schemas — version columns on rows instead of phased DDL — or relational phasing to documents — three-deploy ceremonies for schemaless shapes readers could adapt to). Each store evolves in its grain: relational evolution is *deployed* (schema states versioned by migration, code coexists by compatibility windows); document evolution is *read* (shapes versioned per document, readers adapt). Cross-applying grains wastes (phases for schemaless flexibility) or breaks (versions without enforcement where constraints could hold). Twins linked, grains respected, solutions matched to stores.

**Modern guidance** — the transfer map (lesson → twin): version budgets (≤2–3 live versions) ↔ phase discipline (expand/migrate/contract — both bound concurrent shapes); lazy adaptation economics ↔ backfill economics (on-touch convergence vs batched rewrite — same ledger, different grain); eager triggers ↔ contract verification (budgets exceeded → rewrite; references zero → drop — both close transitions on evidence); discriminator contracts ↔ compatibility taxonomy (declared shapes vs classified changes — both make implicit explicit). Learn both twins; apply per store; cite across — cross-citations ("per 03/3.2 version budgets, this contract phase closes two versions") model integrated thinking.

**Common confusion** — *"one evolution discipline should cover both stores."* The shared principles (no flag-days, bound transitions, verify before finalize) are store-free — stated identically in both domains. The *procedures* differ irreconcilably (DDL phases need deploy coordination; document adaptation needs reader branching — different actors, different rhythms, different verification). Principles shared, procedures per store — unifying procedures breaks both; sharing principles strengthens both. Link principles; own procedures.

**Performance note** — none specific beyond §§1–3's own economics — the twin point *is* performance-relevant though: correctly-grained evolution minimizes transition load (phased DDL distributes rewrites; lazy adaptation amortizes upgrades) while cross-grained evolution maximizes it (big-bang rewrites for documents that could adapt; per-row versioning where constraints could enforce). Grain-matched evolution is cheapest by construction — match first, optimize never needed.

**Mentor note** — teach twins as "same problem, mirrored solutions" (juniors learning both grains reason about evolution structurally — flag-day avoidance as principle, procedures as store-fitting instances). The transfer question ("how would 03/3.2 handle this relational change?") trains analogical thinking — seniors answer fluently, juniors learn by attempting. Analogies across stores are the expert habit forming early — encourage the attempts, correct the grains.

Versioning and shape migration.md>); lazy/eager economics referenced from [1.1](<../1. Schema evolution/1.1. Expand and contract migrations.md>) and [1.2](<../1. Schema evolution/1.2. ## 3. Operations live in Databases 06–07 and Domain 06 (backup, monitoring, on-call — neighbors, not repeats)

**Definition** — forward + outward boundary: operating the evolved, partitioned, tiered schema — backups and restores, monitoring and alerting, on-call modeling judgment — belongs to neighbors. [Databases 06](<../../../../Databases/06 Performance Backup and Operations/README.md>) owns backup mechanics and performance operations; [Databases 07](<../../../../Databases/07 Production Data Use and Interview Mastery/README.md>) owns production data use and interview synthesis; Domain 06 (Modeling for Operations — unbuilt) will own operation-shaped modeling (observability schemas, audit trails, feature-flag storage, job tables). Domain 05 designs for operability (triggers with owners, runbooks referenced, procedures rehearsed); neighbors operate — design/operate interface, not overlap.

**What problem it solves** — scope creep in both directions (evolution domain absorbing backup tutorials — mechanics without a design question; operations runbooks absorbing schema design — procedures without modeling context). The interface is crisp: Domain 05 outputs *triggerable procedures* (partition at 80M rows — how, step by step, rehearsed); neighbors output *operating capability* (backups that restore, alerts that fire, on-call that responds). Procedures without capability are documentation; capability without procedures is improvisation. Both halves, each owned, interfacing at triggers and runbooks.

**Modern guidance** — the neighbor map: backup/restore mechanics (pg_dump strategies, point-in-time recovery, restore testing) → Databases 06; monitoring, alerting, and production operations → Databases 06–07; cold-storage restore procedures (object dumps back to queryable — the cold tier's other direction) → Databases 06 mechanics + 3.1's policy (jointly — policy here, machinery there); operation-shaped schemas (audit tables, outbox pattern, job queues in tables, flag storage) → Domain 06 (forward — unbuilt; textual, no dead link by design). Full curriculum in [LOG.md](<../../../LOG.md>).

**Common confusion** — *"runbooks belong with procedures."* Runbooks live closest to their executors (on-call engineers — Databases 06–07 territory); procedures live closest to their designers (modelers — this domain). Cross-linking beats co-locating (procedure references runbook; runbook references procedure — each maintained by its owners, neither rotting in the other's repo). Colocated runbooks rot when schemas evolve (owners differ); linked runbooks evolve with both sides. Link across the interface; maintain per owner.

**Performance note** — none specific — operations performance (backup windows, alert latency, restore RTO) is neighbors' territory by design. This domain's operations contribution is upstream: triggerable, rehearsed, owned procedures that on-call can execute (partition splits, archival jobs, purge batches — each with abort signals and verification). Executable procedures are operability delivered at design time — the interface working as designed.

**Mentor note** — teach the design/operate interface explicitly ("who runs this procedure at 3 a.m.?" — asked per trigger, answered with team names — procedures without operators are fiction). Juniors designing triggers with operators named learn operational empathy early (procedures written for tired humans — abort signals clear, verification simple, rollback named). Review procedures from the on-call chair (would *you* run this half-asleep? — the empathy test every runbook-adjacent design should pass). Design for the tired; operate rested.
