# 1.2. Backward-compatible discipline

## 1. Old and new code coexist (every migration ships while both versions run)

**Definition** — the deploy assumption: during any migration, old code (pre-deploy) and new code (post-deploy) run simultaneously — rolling deploys, canary traffic, replica-lagging readers, retry-queued workers holding old binaries for hours. Backward-compatible discipline means every schema state serves both code versions: new schema tolerates old writers (nullable additions, defaults covering new NOT NULLs eventually), old schema tolerates new readers (new code reads old shapes until migration completes — dual-read windows, never flag-day assumptions).

**What problem it solves** — the rolling-deploy breakage: migration adding a NOT NULL column without default ships while old app servers still INSERT without it (constraint violations spike mid-rollout — half the fleet erroring, the dashboard red during "successful" deploys); or new code deployed expecting backfilled data while the backfill runs (NULLs where totals were assumed — new code crashes on old rows). Both share a root cause: assuming atomic code+schema cutover in a system that deploys incrementally by design. Compatibility windows (old↔new both live, both served) remove the assumption structurally.

**Modern guidance** — the coexistence checklist per migration: (a) *old writers vs new schema* (new columns nullable or defaulted — old INSERTs succeed; new constraints NOT VALID initially — old rows tolerated); (b) *new readers vs old rows* (new code handles unbackfilled NULLs — COALESCE, fallbacks, dual-read — until backfill completes); (c) *stragglers named* (retry queues, cron workers, cached plans, BI extracts — each with its version lag bounded and its compatibility verified, not hoped). Deploy order follows: expand schema → deploy tolerant code → backfill → tighten constraints → deploy assuming code → contract. Six steps, each safe against both neighbors.

```sql
-- GOOD: coexistence by construction — each state serves both code versions.
-- State A (expand): email nullable — old code INSERTs (ignores it) ✓, new code writes it ✓.
-- State B (migrated): backfill complete, email SET NOT NULL — old code still INSERTs?
-- Only if old code supplies email (it doesn't) → old code retired BEFORE tightening.
-- Order honored: tighten constraints only after old writers are gone (deploy tracking,
-- not hope). New readers handle NULL emails until backfill done (COALESCE fallback).
ALTER TABLE users ADD COLUMN email TEXT;  -- State A: both versions safe (verified PG 16.15)
```

```sql
-- BAD: flag-day assumption — atomic cutover in an incremental system.
ALTER TABLE users ADD COLUMN email TEXT NOT NULL;  -- no default, history unbackfilled:
-- old app servers INSERTing without email → constraint violations fleet-wide mid-rollout.
-- New code assuming emails present → crashes on unbackfilled rows.
-- Rollback: which side? Both broken differently. The migration assumed a cutover;
-- the deploy pipeline never promised one. Assumption vs architecture — architecture wins.
```

**Common confusion** — *"blue-green deploys make this unnecessary."* Blue-green swaps traffic atomically *between* environments — but stragglers persist across the cut (in-flight transactions on old code, retry queues with old payloads, replica lag serving old reads, workers mid-job). "Atomic" describes the router, not the system — every cutover has a tail, and tails run old code against new schema (or vice versa). Compatibility windows shrink with blue-green (minutes, not hours) but never vanish — discipline lightens, never lifts.

**Performance note** — coexistence costs are transitional (nullable columns briefly, dual-writes during migration, tolerant readers with COALESCE branches — all removed at contract) against flag-day costs that are permanent when they fail (violation spikes mid-deploy — error budgets burned; emergency rollbacks — deploys frozen for days; data repair — engineer-weeks). Transitional costs amortize to zero at contract; incident costs compound into process scar tissue ("no deploys on Fridays" — the organizational interest on one flag-day). Price accordingly.

**Mentor note** — teach "who runs old code right now?" as the migration design question (juniors answering: canary holdouts, retry queues, cron, cached plans, BI — the straggler inventory). Teams maintaining a straggler list (versions live, lag bounds, compatibility verified per migration) deploy calmly; teams discovering stragglers mid-migration discover them as incidents. Inventory beats discovery — the list lives beside the deploy docs, reviewed per migration, never assumed empty.

## 2. Additive changes are safe, breaking changes expand first (the compatibility taxonomy)

**Definition** — the taxonomy: **safe-additive** changes ship directly (new nullable columns, new tables, new indexes CONCURRENTLY, new CHECKs NOT VALID, widening a type — old code ignores additions, old rows tolerate them); **breaking** changes enter expand/contract (renames, drops, type narrowings, new NOT NULLs without defaults, constraint tightening, splitting/merging tables — anything old code or old rows could violate). Classification precedes procedure: safe ships, breaking phases — misclassified changes are incidents wearing the wrong checklist.

**What problem it solves** — the two misclassification failures: *breaking shipped as safe* (NOT NULL without default on a live table — old writers fail instantly; type narrowing truncating history — silent corruption; DROP COLUMN with dashboard references — BI breaks Monday) and *safe shipped as breaking* (three-phase ceremony for a nullable audit column — weeks of process for a zero-risk addition; teams trained that "migrations are heavy" start batching schema changes into flag-days — the ceremony backfires into coupling). Correct classification keeps safe changes light (velocity preserved) and breaking changes phased (safety preserved) — both properties, no trade between them.

**Modern guidance** — the classification test per DDL statement: "can old code run unchanged against the new schema, AND can new code run unchanged against old rows?" Both yes → safe-additive, ship directly (still reviewed, still off-peak for large tables — light, not reckless). Either no → breaking, expand/contract ([1.1](<1.1. Expand and contract migrations.md>)). Tricky cases decided conservatively (type widening usually safe — except application length validations now mismatched; new defaults safe — except old code explicitly inserting NULLs expecting NULLs; index additions safe-query-wise — but build load needs CONCURRENTLY — Databases 02 mechanics). When unsure: phase it — over-caution costs days, under-caution costs incidents.

```sql
-- GOOD: classified correctly — additive ships, breaking phases (verified PG 16.15).
-- SAFE (ship directly): new nullable column, new table, CONCURRENTLY index.
ALTER TABLE users ADD COLUMN status TEXT NOT NULL DEFAULT 'active';  -- defaulted: old INSERTs safe
ALTER TABLE users ADD COLUMN meta JSONB;                             -- nullable: old code ignores
-- BREAKING (expand first): rename, drop, tighten, narrow.
-- ALTER TABLE users RENAME COLUMN name TO email;      -- NO: expand/contract (1.1 promise 3)
-- ALTER TABLE users DROP COLUMN legacy_contact;       -- NO: contract phase only (grep first)
-- ALTER TABLE users ALTER COLUMN status SET NOT NULL; -- NO (without default): expand first
```

```sql
-- BAD: misclassified both directions — incidents and ceremony-swamps together.
ALTER TABLE users ADD COLUMN email TEXT NOT NULL;           -- breaking shipped as safe:
-- old writers fail fleet-wide (no default, history NULL). Incident within the hour.
ALTER TABLE users ADD COLUMN audit_note TEXT;               -- safe shipped as breaking:
-- three-phase plan, two weeks, four deploys — for a nullable note column. The team
-- learns migrations are "heavy" and starts batching changes into quarterly flag-days.
-- One misclassification causes incidents; the other causes the process that causes them.
```

**Common confusion** — *"NOT NULL with a default is always safe."* Usually — with two caveats: (a) old code explicitly inserting NULL (expecting NULL semantics — now gets the default — behavior change disguised as schema change; audit callers first); (b) large-table rewrite cost (PostgreSQL 11+ skips rewrites for defaults — version-labeled as-of-September-2026 standard — but older engines and some constraint forms still rewrite; verify per version, per statement — Databases 02 mechanics). "Usually safe" with named caveats beats "always safe" with incidents — taxonomy entries carry footnotes, not blind trust.

**Performance note** — classification has performance teeth: safe-additive DDL is instant or CONCURRENTLY-built (no blocking rewrites — deploy anytime); breaking changes phased distribute load (1.1's economics). Misclassified-breaking ships blocking rewrites into deploy windows (ALTER rewriting 50M rows mid-deploy — locks, lag, timeouts — the "quick migration" that pages). The taxonomy isn't paperwork — it's load scheduling disguised as caution. Classify fast, deploy calmly.

**Mentor note** — teach classification as a two-question drill ("old code unchanged? old rows tolerated?") run per DDL statement in review — thirty seconds per statement, verdict safe/breaking/unsure (unsure → phase). Juniors drilling verdicts classify correctly within weeks; the drill generalizes to API versioning, config changes, and every compatibility question thereafter. Compatibility thinking is a career skill wearing a migration checklist — teach the skill through the checklist.

## 3. Readers tolerate, writers conform (Postel across deploys)

**Definition** — Postel's law applied to schema evolution: readers are liberal (new code handles old rows — missing columns, unbackfilled NULLs, legacy enum values — via COALESCE, fallbacks, version branches), writers are conservative (all writers emit the new shape promptly — dual-write during transition, new-shape-only after). Tolerance is temporary (until contract — old shapes die on schedule); conformance is prompt (writers migrate first — readers can't tolerate what writers won't stop producing). The asymmetry is the whole discipline: strict outputs, generous inputs, both versioned, both temporary.

**What problem it solves** — the intolerant reader (new code assuming backfilled data — crashes on NULL emails mid-migration; new dashboards dividing by new columns — divide-by-NULL gaps during rollout) and the nonconforming writer (legacy importer still writing old shapes months later — contract blocked indefinitely; third-party webhook payloads in v1 format — tolerance permanent, tech debt institutionalized). Intolerant readers convert migrations into flag-days (every reader must cut over atomically — impossible with stragglers); nonconforming writers convert transitions into limbo (dual shapes forever — the "temporary" compatibility layer outliving its authors). Tolerance windows readers; conformance deadlines writers.

**Modern guidance** — the tolerance/conformance contract per migration: *readers* list tolerated old shapes with expiry (NULL emails tolerated until backfill +1 release — COALESCE fallback, ticketed removal; legacy enum values mapped until contract — mapping table in code, tested); *writers* list conformance deadlines (application dual-write starts deploy N, old-shape writes end deploy N+1 — enforced by dropping old write paths, not by asking nicely; external writers notified with format-change lead time — versioned payloads, sunset headers where applicable). Contract phase verifies both (no old-shape reads in code search; no old-shape writes in logs) before dropping tolerance. Tolerance without expiry is permission; conformance without deadline is suggestion.

```sql
-- GOOD: tolerance in readers (COALESCE), conformance in writers (dual-write → new-only).
-- Reader during migration (tolerant, ticketed removal at contract):
-- SELECT COALESCE(email, lower(name) || '@x.io') AS email FROM users;
-- Writer during migration (conformant, dual-shape then new-only):
-- INSERT INTO users (name, email) VALUES ($1, $2);  -- both shapes from deploy N
-- Contract verification: SELECT count(*) FROM users WHERE email IS NULL; → 0 (backfill done)
-- + code search zero COALESCE-email fallbacks remaining → tolerance removed with shape.
```

```sql
-- BAD: intolerant readers, nonconforming writers — the migration that never ends.
-- Reader: SELECT email FROM users;  -- crashes on unbackfilled NULLs (no tolerance —
-- every NULL row is an exception, exceptions spike mid-migration, rollback "fixes" it
-- by abandoning progress). Writer: legacy importer INSERTs name-only (no conformance —
-- new NULLs appear post-backfill; contract blocked; tolerance made permanent).
-- Readers demand, writers ignore — the transition limps forever, dual shapes forever,
-- "temporary" compatibility code celebrating its second birthday in production.
```

**Common confusion** — *"tolerant readers hide data problems."* Tolerance with expiry and tickets surfaces problems on schedule (fallback usage logged — "COALESCE-email hit 0.3% of reads, declining" — the metric proves convergence); tolerance without either hides them permanently (silent fallbacks, unmonitored). The difference isn't tolerance-vs-strictness — it's instrumented-temporary vs silent-permanent. Log fallback hits, ticket tolerance removal, contract on zero — tolerance as a monitored bridge, never as a rug for sweeping.

**Performance note** — tolerance costs per-read branching (COALESCE/fallback evaluation — microseconds, plus index-visibility nuances — fallback expressions may bypass indexes on unbackfilled shapes; acceptable transiently, removed at contract) against intolerance costs (crashes, rollbacks, abandoned migrations — orders of magnitude dearer). Conformance costs writer coordination (dual-write payload, deadline enforcement — organizational work, not compute). Both costs expire at contract — transitional by design, which is exactly why contract must ship (uncontracted tolerance is permanent tax without representation).

**Mentor note** — teach "tolerance ticketed, conformance deadlined" as the migration social contract (juniors writing fallbacks open removal tickets in the same PR — tolerance born with expiry; juniors owning writers set conformance dates with the team — deadlines social, not solo). The social half (tickets, dates, owners) matters more than the SQL half — migrations fail on coordination, never on syntax. Review the tickets alongside the DDL; approve people-plans with schema-plans, never separately.
