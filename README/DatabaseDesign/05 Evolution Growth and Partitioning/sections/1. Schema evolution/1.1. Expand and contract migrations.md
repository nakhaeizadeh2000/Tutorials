# 1.1. Expand and contract migrations

## 1. Never rewrite in one deploy (expand, migrate, contract — three phases, zero downtime)

**Definition** — the expand/contract pattern: every breaking schema change ships as three compatible phases across separate deploys — **expand** (add the new shape alongside the old, nullable/unused — old code unaffected), **migrate** (dual-write both shapes, backfill history in batches, switch readers), **contract** (drop the old shape once nothing references it). Each phase is backward-compatible alone; only the sequence breaks compatibility safely. One-deploy rewrites (ALTER + code swap together) couple schema and code releases — rollback of either strands the other.

**What problem it solves / history** — the coupled-deploy outage: code expecting the new column ships before the migration runs (crash loop on missing column), or the migration runs before code ships (NOT NULL without default breaks old INSERTs) — ordering two systems (deploy pipeline + migration runner) that nobody synchronized. Expand/contract decouples them structurally: each deploy is safe against both schema states, each schema state serves both code versions. The pattern emerged from continuous-delivery practice (Fowler's evolutionary database design lineage — version-free procedure) and is now the industry default for live systems — junior teams discover it during their first failed Friday deploy.

**Modern guidance** — the phase checklist per breaking change: **expand** (additive DDL only — new nullable columns, new tables, new indexes CONCURRENTLY — Databases 02 mechanics; deploy; old code ignores additions by construction); **migrate** (dual-write in application code — write old + new; backfill history chunked/throttled/resumable — next promise; switch readers to new shape — deploy; verify parity — counts match, spot-checks pass); **contract** (remove old writes, then old reads, then old DDL — three sub-steps, each deployed; the old column dies last, witnessed by zero references in code search). Rollback per phase (expand rolls back by dropping additions; migrate by switching readers back; contract by... nothing — contracted shapes don't return, which is why verification precedes it).

```sql
-- GOOD: the three phases as DDL — each safe alone, breaking only in sequence.
-- EXPAND (deploy 1): additive only — old code unaffected (ignores email).
ALTER TABLE users ADD COLUMN email TEXT;  -- nullable: old INSERTs keep working

-- MIGRATE (deploy 2): backfill history, then constrain (verified PostgreSQL 16.15).
UPDATE users SET email = lower(name) || '@x.io' WHERE email IS NULL;  -- chunked in prod
ALTER TABLE users ALTER COLUMN email SET NOT NULL;  -- safe: no NULLs remain
-- Readers switched to email; parity verified (counts match); dual-write removed.

-- CONTRACT (deploy 3): old shape removed — code search shows zero references first.
-- ALTER TABLE users DROP COLUMN legacy_contact;  -- last rites, witnessed
```

```sql
-- BAD: the one-deploy rewrite — schema and code coupled, rollback stranded.
-- Deploy ships code reading users.email WITH migration adding it NOT NULL immediately:
ALTER TABLE users ADD COLUMN email TEXT NOT NULL;  -- blocks on 50M-row rewrite AND
-- breaks old code mid-deploy (INSERTs without email fail between migration and code).
-- Rollback code → new column orphaned. Rollback migration → new code crashes.
-- Friday evening, two systems, zero safe direction. The coupled deploy, itemized.
```

**Common confusion** — *"small tables don't need phases."* Small tables grow (every 50M-row table was young once — the unphased habit formed on small tables executes on large ones), and phase discipline costs little on small tables (three quick deploys) while training the reflex for large ones. "Small now" waivers expire exactly where unphased migrations hurt most (junctions, events, logs — [Domain 04](<../../../04 Relationships at Scale/README.md>)'s fastest growers). Phase always; the habit is the asset, the table size merely today's excuse.

**Performance note** — phased migrations distribute load across deploys (expand: instant DDL; migrate: throttled backfill — next promise prices it; contract: instant DDL) instead of concentrating it in one blocking rewrite (single ALTER rewriting 50M rows — locks, bloat, replica lag, all at once, during the deploy window). Total work is comparable; peak impact differs by orders of magnitude — phases trade calendar time (days between phases) for safety margin (each phase independently safe). The slow migration is the fast incident avoided.

**Mentor note** — teach "which phase is this?" as the migration review opener (every schema PR labeled expand/migrate/contract — unlabeled PRs fail review structurally, before content). Juniors labeling phases learn the pattern by repetition; seniors skipping labels get the same question regardless of rank. Three reviews of enforced labeling and authors arrive pre-labeled — the review teaches the method by insistence, same pedagogy as every checklist in this track.

## 2. Backfills are batch jobs (chunked, throttled, resumable — measured, never hoped)

**Definition** — the backfill discipline: populating new shapes from history runs as a controlled batch job — fixed chunk sizes (1k–10k rows per batch — small enough to avoid long locks, large enough to finish), throttling (sleeps between chunks — replica lag is the throttle signal), resumability (progress tracked — `WHERE id > $last` cursors, never OFFSET — reruns continue, never restart), and measured wall-time (sample batch timed, extrapolated +50% — samples lie optimistically). Backfills are migrations' longest phase; undisciplined ones are outages wearing a maintenance window.

**What problem it solves** — the heroic backfill: single UPDATE over 50M rows (one statement, one transaction — locks held for the duration, bloat from 50M dead tuples at once, replica lag spiking, rollback segment groaning; killed halfway → zero progress, all cost), or the unthrottled loop (chunks without sleeps — replicas lagging behind writes, read-your-write violations on followers, cascade of timeouts). Both share a root cause: treating history-population as a query instead of a job. Jobs have chunking, pacing, checkpoints, and abort signals; queries have none — backfills need all four.

**Modern guidance** — the backfill template (same shape every time): (a) *chunk key* (monotonic id or timestamp — `WHERE id > $last ORDER BY id LIMIT 5000` — keyset, never OFFSET — [Databases 07 §2.2](<../../../../Databases/07 Production Data Use and Interview Mastery/sections/2. Review and design/2.2. Data API contracts.md>) mechanics); (b) *idempotency* (re-runnable chunks — SET is idempotent by construction; derived values recomputed identically — reruns safe by design, per 03/3.2's rewrite discipline); (c) *throttle* (sleep calibrated to replica lag — lag >Xs → pause; progress logged per chunk — ETA visible); (d) *abort signal* (lag threshold, error rate, business-hours guard — named before starting, honored automatically); (e) *verification* (counts old-vs-new, checksums sampled — parity proven, not assumed — contract phase waits on it).

```sql
-- GOOD: the backfill as a job — chunked, ordered, resumable, verifiable.
-- Chunk (repeat with $last advancing; 5k rows; sleep calibrated to replica lag):
UPDATE users SET email = lower(name) || '@x.io'
WHERE id > $last_processed_id AND email IS NULL
ORDER BY id LIMIT 5000;
-- Progress: max(id) processed logged per chunk (rerun continues from cursor).
-- Throttle: pg_sleep calibrated — replica lag >5s pauses the loop (abort signal).
-- Verify before contract: SELECT count(*) FROM users WHERE email IS NULL;  -- must be 0
-- + spot-check sampled rows (derived values match recomputation — idempotent by design).
```

```sql
-- BAD: the heroic backfill — one statement, one transaction, zero controls.
UPDATE users SET email = lower(name) || '@x.io';  -- 50M rows, one transaction:
-- locks held for the duration (writes queue behind); 50M dead tuples at once (bloat +
-- vacuum storm); replicas lagging minutes (stale reads cascade); killed at 80% →
-- zero progress, all cost, retry from scratch. No chunks, no throttle, no cursor,
-- no verification — a query cosplaying as a job, failing as an outage.
```

**Common confusion** — *"backfills run off-hours, so controls don't matter."* Off-hours reduce contention; they don't grant atomicity (killed jobs still roll back fully — progress lost), prevent lag (replicas still follow 50M writes), or verify correctness (wrong derivation at 3 a.m. is still wrong at 9 a.m. — just 50M rows wronger). Night windows shrink blast radius; discipline removes it. "Off-hours" is scheduling; chunking/throttling/verification is engineering — schedule *and* engineer, never either alone.

**Performance note** — backfill economics: chunk size trades lock-hold (smaller = shorter locks, friendlier) against total wall-time (smaller = more round trips, slower) — 1k–10k rows per chunk is the usual sweet region (locks sub-second, throughput acceptable); throttle trades job duration (slower with sleeps) against replica health (lag bounded — followers stay readable); verification trades minutes now (counts + samples) against rollback quarters later. Measure the sample batch, extrapolate +50%, schedule the window from the number — backfill duration estimated, never hoped.

**Mentor note** — teach "time 10k, extrapolate, add half" as the backfill estimation reflex (juniors estimating "a few minutes" for 50M rows learn humility via arithmetic — 10k in 2s → 50M in ~3 hours +50% → schedule 4.5, announce 6). Estimation errors are the #1 backfill incident cause (windows exceeded, traffic arriving mid-job) — the reflex converts hope to schedule in one sentence. Rehearse on staging with production-sized samples; staging lies smaller, production bills larger.

## 3. Renames are add-and-drop (no RENAME under traffic — alias, migrate, drop)

**Definition** — the rename rule: column/table renames ship as add (new name alongside old) → dual-write + backfill (both populated) → readers switched → old dropped — never as `RENAME COLUMN` under traffic. RENAME is instant in DDL terms but breaking in deploy terms (old code referencing the old name crashes between migration and code deploy — the coupled-deploy failure from promise 1, concentrated in one statement). Renames are the most underestimated breaking change: trivial in development ("just rename it"), hazardous in production (every reader, writer, report, and dashboard references the old name *somewhere*).

**What problem it solves** — the rename outage and its slower twin, rename drift: *outage* (RENAME deployed with code swap — old replicas/code/Dashboards querying the old name fail; BI extracts break silently; the rollback renames back, breaking the new code — no safe direction, same shape as promise 1's BAD); *drift* (rename "completed" in schema while five readers still use the old name via views/aliases nobody mapped — half-migrated vocabulary, new hires learning two names for one column). Add-and-drop converts renames from flag-days to phases: old name works throughout, new name adopted incrementally, old dropped when code search proves zero references.

**Modern guidance** — the rename sequence (four deploys, each safe): (1) **add** new column + dual-write (application writes both; backfill old→new for history); (2) **switch** readers to new (deploy; verify parity — old-vs-new reads compared, sampled); (3) **stop** old writes (deploy; old column frozen — any writer still targeting it errors visibly, surfacing missed callers); (4) **drop** old column (code search zero hits + one release cycle of frozen-old observation — drop ships only after the freeze proves no readers remain). Views as aliases where the engine supports cheap renaming-safe layers — but aliases are transition aids with expiry, not permanent vocabulary (two names forever is drift institutionalized — drop date recorded at add time).

```sql
-- GOOD: rename as phases — old works throughout, new adopted incrementally, drop witnessed.
-- (1) ADD + dual-write: ALTER TABLE users ADD COLUMN email TEXT; app writes name+email; backfill.
-- (2) SWITCH readers to email; parity verified (old vs new compared on samples).
-- (3) STOP old writes: application drops name writes; freeze observed one release cycle.
-- (4) DROP witnessed: code search zero hits for legacy name + freeze clean → drop ships.
ALTER TABLE users DROP COLUMN legacy_contact;  -- last rites: referenced nowhere, proven
```

```sql
-- BAD: the flag-day rename — instant DDL, distributed breakage.
ALTER TABLE users RENAME COLUMN name TO email;  -- old code, old dashboards, BI extracts,
-- replica-lagging readers, cached query plans: all referencing 'name', all failing at
-- various times after the deploy. Rollback renames back — new code fails instead.
-- The statement took milliseconds; the incident took the weekend. Renames are never
-- "just" renames under traffic — they're vocabulary changes across every consumer.
```

**Common confusion** — *"views/triggers make renames transparent — just alias."* Aliases (views, compatibility triggers, ORM field mappings) smooth the transition *during* phases — they don't replace phases (alias without drop-date is permanent dual vocabulary — drift; alias without dual-write leaves writers split). Aliases are scaffolding with a removal ticket filed at erection — useful, temporary, dated. Permanent aliases are renames that never finished — the drift twin wearing a solution costume.

**Performance note** — rename-phase costs: dual-write doubles write payload per row during transition (bytes, not statements — negligible for scalar columns; priced for wide ones); backfill moves history once (next-promise... promise 2's discipline applies — chunked, throttled); frozen-old observation costs one release cycle of calendar time (not compute — patience, the scarcest migration resource). Total compute trivial; total calendar weeks. Renames are cheap in machines, dear in coordination — schedule accordingly, never "squeeze in" a rename with a feature deploy.

**Mentor note** — teach "grep before drop" as the contract-phase sacrament (code search, dashboard search, BI extract search, *then* drop — the witnessing habit from [Domain 02 §4.1](<../../../02 Normalization Deep Dive/sections/4. Mentor checklist/4.1. Normalization review checklist mentors insist on.md>)'s blessings, migration edition). Juniors dropping after schema-only checks orphan invisible consumers (the CEO's spreadsheet, the auditor's extract — always something); seniors grep widely, wait a cycle, drop calmly. The drop ships when evidence — not confidence — says zero references.
