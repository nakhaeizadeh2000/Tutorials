# 4.1. Evolution review checklist mentors insist on

## 1. Every migration is expand-compatible (old code runs against new schema — stated, not hoped)

**Definition** — the review's first pass over schema changes: for each migration PR, the author states the phase (expand/migrate/contract — [1.1](<../1. Schema evolution/1.1. Expand and contract migrations.md>)), the compatibility verdict (old writers vs new schema: safe how? new readers vs old rows: tolerant how? — [1.2](<../1. Schema evolution/1.2. Backward-compatible discipline.md>)), and the rollback per phase (expand rolls back by dropping additions; migrate by switching readers; contract doesn't — verification precedes it). Unlabeled migrations fail review structurally — content unexamined until phases stated.

**What problem it solves** — phase-blind merges (NOT NULL without default sailing through a types-focused review — old writers failing fleet-wide mid-rollout; renames approved as "simple DDL" — dashboards breaking Monday; backfills merged without chunking — the heroic UPDATE locking production). Each is a compatibility question unasked at the last calm moment — review is that moment; the checklist asks structurally (phase? compatibility both directions? rollback?) so no migration merges on DDL aesthetics alone. Calm questions now, or incident questions later — same questions, worse lighting.

**Modern guidance** — the migration review lines: phase named ("expand: additive email column" / "migrate: dual-write + backfill, 5k chunks, lag throttle" / "contract: drop legacy_contact, grep zero + one-cycle freeze witnessed"); compatibility both directions stated ("old writers: nullable → safe ✓; new readers: COALESCE fallback, ticket #123 removal ✓; stragglers: cron v3.2 bounded, BI extract v9 verified ✓"); rollback named ("expand: DROP COLUMN; migrate: reader switch-back + dual-write resume; contract: N/A — verification attached"); backfill/rename sub-discipline referenced (chunking plan? rename at phase 1 of 4 with drop date?). Missing line → request changes; the template grows one row per migration — phases first, queries never (migrations have no queries to tune — only compatibility to prove).

```sql
-- GOOD: the migration review artifact — phased, compatible both ways, rollback named.
-- Phase: EXPAND (additive email TEXT nullable). Old writers: safe (ignore it) ✓.
-- New readers: N/A yet (no readers added this phase) ✓. Stragglers: cron v3.2 INSERTs
-- name-only — safe under nullable ✓ (verified against straggler list). Rollback:
-- DROP COLUMN email (instant, safe). Verdict: approve expand.
```

```sql
-- BAD: the aesthetics review — types checked, compatibility unexamined.
-- "ALTER looks fine. +1." (Phase? Unasked — it's a bare ADD NOT NULL: breaking shipped
-- as safe. Old writers? Unasked — fleet fails mid-rollout. Rollback? Unasked — both
-- directions broken differently by the time anyone asks.) The review approved syntax;
-- production graded compatibility. Different subjects, different outcomes — the review
-- covered the wrong one.
```

**Common confusion** — *"small migrations don't need the ceremony."* Small migrations train the reflex used on large ones (phase-labeling a nullable column today is practice for phasing a table split next quarter); and "small" misjudges impact routinely (one-line NOT NULL on a 50M-row table — small diff, large locks, fleet-wide writer failures). Ceremony scales with risk, but the *labeling* habit doesn't scale at all — it's constant, tiny, and universal. Label always; phase by risk; the habit is the asset.

**Performance note** — migration review is upstream performance work (same argument as every checklist leaf in this track, fifth restatement): phased migrations distribute load across deploys (no blocking rewrites in windows); chunked backfills bound lag (replicas stay readable); witnessed contracts prevent repair migrations (the most expensive kind — written under incident pressure, executed without rehearsal). Review minutes convert to outage-hours avoided at the usual rate — highest-ROI minutes in schema work, permanently true.

**Mentor note** — automate the checkable half (CI linter: ADD NOT NULL without default fails the build; DROP COLUMN without referenced-grep evidence fails; RENAME COLUMN fails outright — "expand/contract only"), review the judgment half (phase correctness, compatibility reasoning, backfill sizing). Juniors learn fastest from instant automation feedback (red build with the rule linked) plus human phase discussion. Machines check shape; mentors check sequence — split accordingly, same as [Domain 04 §4.1](<../../../04 Relationships at Scale/sections/4. Mentor checklist/4.1. Relationship review checklist mentors insist on.md>)'s structure/judgment split.

**Cross-links** — expand/contract in [1.1](<../1. Schema evolution/1.1. Expand and contract migrations.md>); compatibility taxonomy in [1.2](<../1. Schema evolution/1.2. Backward-compatible discipline.md>); automation/judgment split twin in [Domain 04 §4.1](<../../../04 Relationships at Scale/sections/4. Mentor checklist/4.1. ## 2. Every growth claim is measured (rates sourced, math shown, triggers set)

**Definition** — the review's second pass over growth-facing changes (new tables, new indexes, new features with storage implications): the author shows rates (rows/day with source + date — [2.1](<../2. Growth and capacity/2.1. Capacity modeling with measured triggers.md>)), math (width × count × indexes × overhead — the spreadsheet, or its relevant row), and triggers (metric → threshold → response → owner — set or explicitly deferred with reason). Growth claims without all three ("should scale fine," "plenty of headroom," "we'll partition later") fail review as unmeasured — adjectives aren't arithmetic, intentions aren't triggers.

**What problem it solves** — hope-shaped growth merges (unmeasured rates → undersized budgets → disk-full pages; unmodeled widths → RAM cliffs → mystery slowness; untriggered "laters" → emergency re-partitioning under load). Each merges calmly (the PR looks fine — tables, indexes, code all correct) and fails eventually (volume arrives on schedule; the schedule was never consulted). The measured-growth gate converts "eventually" to dates (spreadsheet says month 14 — trigger fires month 11 — response windowed) — failures become tickets with owners instead of pages without context.

**Modern guidance** — the growth review lines per new table/feature: rates ("orders 50k/day measured prod 2026-09, +8%/mo forecast Q4" — sourced, dated); math ("420B/row × 27M rows/18mo × 2.4 idx × 1.2 = 33GB — 7% of budget" — shown, not asserted); triggers ("partition at 80M rows → procedure 2.2, owner platform; archive events >13mo → procedure 3.1, owner data" — set with owners, or deferred with reason + re-ask date). Indexes proposed update the multiplier (new index → capacity impact stated — index review includes storage now). "Unknown" rates accepted with expiry (unlaunched feature — re-measure week 2 post-launch — bounded ignorance, ticketed re-ask). No numbers → request changes; numbers without sources → request sources; sources without dates → request dates.

```sql
-- GOOD: the growth review artifact — sourced rates, shown math, set triggers.
-- Rates: orders 50k/day (prod measured 2026-09), lines ×3.0, events 2M/day (roadmap).
-- Math: widest table 420B/row × 18mo horizon = 33GB (7% budget) — headroom comfortable.
-- Triggers: partition orders at 80M (2.2, platform); archive events >13mo (3.1, data).
-- Indexes: +1 on orders (multiplier 2.4→2.6 — budget updated). Verdict: approve with triggers.
```

```sql
-- BAD: the adjectives review — correct schema, unmeasured future.
-- "Tables look good. Should handle growth." (Rates? Unasked — 50k vs 500k/day changes
-- everything. Math? Unshown — 420B vs 4KB widths change it 10×. Triggers? Unset —
-- "later" unscheduled.) The schema serves today impeccably and expires undated —
-- growth arrives as surprise despite being forecastable from day one. Adjectives approved;
-- arithmetic absent; incidents scheduled (dateless, as usual).
```

**Common confusion** — *"growth review slows feature shipping."* Growth review costs minutes per table (rates looked up, math one spreadsheet row, triggers one line each) against unmodeled growth costing quarters (emergency projects, outage remediation, re-architecture under load). "Slows shipping" counts review minutes while ignoring incident quarters — the full ledger favors measurement by orders of magnitude. Fast shipping of unmeasured schemas is fast borrowing against future velocity — debt with volume-indexed interest.

**Performance note** — growth review *is* performance review at the schema level (same argument as 2.1: residency cliffs, index depth, vacuum load — all size functions decided here). Reviewers summing top-table budgets validate the feature's data-plane cost before code ships — performance tuned at modeling time, not firefighting time. The growth gate turns performance from a tuning phase into a modeling input — where it belongs, fifth domain running, permanent value.

**Mentor note** — teach "show me the spreadsheet row" per table (juniors arriving with rates/math/triggers pre-computed signal senior thinking louder than correct DDL — they model futures, not just structures). Praise measured growth publicly ("great trigger set — month-11 firing with 3-month window"); the team imitates praised behavior. Volunteered numbers beat requested numbers (faster reviews, better morale) — praise creates volunteers, mandates create compliance theater. Praise measurers; measure praise's effect quarterly.

## 3. Every retention rule is owned (policy named, job scheduled, legal signed — or data stays forever by default)

**Definition** — the review's closing act over data lifecycle: every table (or category) arrives with its retention stated — tiers + durations ([3.1](<../3. Lifecycle and retention/3.1. Archival and lifecycle tiers.md>)), legal basis cited, owner + signer named, purge/archive job linked or ticketed. Tables without retention statements default to *retain forever, priced visibly* ("unclassified — retained at hot-tier cost pending classification ticket #456") — the default stated aloud so its cost motivates classification faster than any mandate. Retention unowned is liability unassigned; liability unassigned compounds.

**What problem it solves** — the lifecycle vacuum at merge time (tables born without retention — dying never, by default — storage compounding, discovery liability growing, purge projects launching years later under regulatory deadlines); and the policy-less purge (deletion code merged without hold-checks, certificates, or signers — spoliation scheduled as a feature). Both enter production silently (no error, no alert — absence of policy is invisible until audit or disk-full). The owned-retention gate makes lifecycle visible at birth: policy or priced-forever-default, job or ticket, signer or escalation — every table, every review, no invisible defaults.

**Modern guidance** — the retention review lines per table/category: policy ("events: hot 3mo → warm 10mo → cold to 13mo → purge; basis product-need + privacy review, signer CPO" — named, cited, signed); job ("purge job linked — batched, hold-checked, certificated — or ticket #789 with date" — scheduled or ticketed, never vague); holds ("legal_holds consulted structurally — new categories registered in hold scope on creation"); default ("unclassified user_uploads — retained forever at $X/mo, classification ticket #456 due Q1" — priced default, expiry dated). Yearly retention review with legal (laws change, promises expire, categories drift — calendared, owners present). No policy → priced-forever (stated, ticketed) — never silent-forever.

```sql
-- GOOD: the retention review artifact — policy, job, holds, default — all owned.
-- events: hot 3mo → warm 10mo → cold 13mo → purge (basis cited, CPO signed 2026-06).
-- Job: purge-events linked (batched 10k, hold-checked, certificates retained) ✓.
-- Holds: category registered in legal_holds scope ✓. New table user_uploads:
--   policy pending → priced-forever default ($X/mo, ticket #456, due Q1) — stated, not silent.
-- Verdict: approve with classification ticket blocking Q1 (not this merge — dated debt, owned).
```

```sql
-- BAD: the lifecycle-blind merge — born to live forever, purged by courage eventually.
-- New table uploads: (retention? unasked — forever by default, silently). Purge endpoint
-- "delete old uploads": (holds? unchecked — no hold table exists. Certificates? none —
-- prove what?). Five years later: 800TB unclassified (storage line item, discovery
-- nightmare) + a purge project under regulatory deadline (spoliation risk, war room).
-- Birth without lifecycle is forever by default; forever is the dearest retention policy —
-- priced nowhere, paid everywhere.
```

**Common confusion** — *"retention review is legal's job, not engineering's."* Legal owns *policy content* (durations, bases, signatures); engineering owns *policy existence* (asking, encoding, jobbing — the register, the hold table, the purge discipline). Unasked legal doesn't volunteer (they don't know the table exists); unencoded policy doesn't execute (jobs need predicates). Engineering initiates (new table → "retention?" asked at review), legal decides (durations + signatures), engineering implements (jobs + holds + certificates). Interface, not handoff — same joint ownership as capacity ([2.1](<../2. Growth and capacity/2.1. Capacity modeling with measured triggers.md>)). Ask; don't assume legal's silence is consent.

**Performance note** — retention review is storage-performance review (tiered data keeps hot sets resident — the p99 cliff avoided by policy, not by hardware; unclassified forever-data bloats backups, vacuums, and working sets — every unowned table taxes operations silently). Owned retention with tiering is the cheapest performance work available (evicting cold data beats provisioning RAM — dollars vs discipline, discipline winning). Price forever-defaults visibly — nothing motivates classification like a monthly dollar figure beside "unclassified."

**Mentor note** — model retention ownership on your own tables first (the track's standing lesson, fifth domain: authority's example teaches). A senior's retention note ("my table: hot 6mo → cold 2yr → purge, legal signed, job linked") teaches more than any policy wiki. Praise owned lifecycles ("great hold coverage") louder than clever schemas — teams optimize for praised behavior, and unowned forever-tables have had enough silent approvers. Praise owners; ownership spreads.
