# 3.1. Archival and lifecycle tiers

## 1. Hot warm cold by access (live rows hot, recent history warm, legal history cold)

**Definition** — lifecycle tiers: data placed by access temperature — **hot** (live working set — indexed, cached, on fast storage, fully queryable), **warm** (recent history — queryable but slower: detached partitions, read replicas, compressed tables — accessed weekly, not per-request), **cold** (legal/audit history — restorable, not queryable: object storage dumps, offline archives — accessed yearly or never, retained for obligation). Tiers are access promises with storage prices: hot costs RAM and fast disk per GB; cold costs pennies per GB plus restore hours.

**What problem it solves** — the single-tier giant: all history hot (500M-row events with 2019 rows in RAM-priced storage, indexed, vacuumed, backed up nightly — 90% of cost serving 1% of reads), or the panic purge (disk-full Friday → DELETE 300M rows ungracefully — hours of locks, bloat, replica lag, plus the legal discovery request Monday for exactly the purged window). Tiering converts binary keep/delete into graduated economics: each byte pays the tier its access justifies, moves on schedule (not in panic), with legal sign-off preceding every destructive transition.

**Modern guidance** — the tiering procedure per table (from 2.1's growth inventory): (a) classify by access (hot: per-request reads/writes — live partitions; warm: analytical/recency reads — detached recent partitions, compressed, on slower storage or replicas; cold: obligation-only — restorable dumps with tested restores); (b) set tier boundaries in time (hot <3mo, warm 3–13mo, cold >13mo — example; boundaries from access logs + retention policy, never round numbers); (c) automate transitions (DETACH to warm monthly — verified below; dump to cold quarterly — restore-tested); (d) price each tier (hot $/GB-fast, cold $/GB-object — the spreadsheet from 2.1 extended — tiering justified in dollars, not aesthetics).

```sql
-- GOOD: tiering as DDL rhythm — detach monthly, dump quarterly, restore-tested (verified PG 16.15).
-- HOT: events_2026_09 (live partition — indexed, cached, vacuumed normally).
-- WARM (monthly job): ALTER TABLE events DETACH PARTITION events_2026_06;
--   detached piece stays queryable (attached on demand), compressed, slower storage.
-- COLD (quarterly job): CREATE TABLE cold_2026_q1 (LIKE events_archive INCLUDING ALL);
--   INSERT INTO cold_2026_q1 SELECT * FROM detached_piece; verify counts; dump to object
--   storage; restore-test sampled quarters yearly (untested archives are rumors).
ALTER TABLE dd_log DETACH PARTITION dd_log_old;  -- milliseconds, metadata-only (verified)
```

```sql
-- BAD: the single-tier giant — all history hot, then panic-purged.
-- 500M rows: 2019 events indexed/vacuumed/backed-up nightly (90% cost, 1% reads).
-- Disk-full Friday: DELETE FROM events WHERE occurred_at < '2024-01-01';  -- 300M rows,
-- one statement: hours of locks, bloat storm, replica lag cascade. Monday: legal asks
-- for Q3-2023 records (purged Friday, unrecoverable — no cold tier existed). Cost maximized
-- before (hot everything), obligations violated after (nothing retained). Both failures,
-- one cause: no tiers.
```

**Common confusion** — *"archival means deleting old data."* Archival means *relocating* by temperature (hot→warm→cold — queryability degrading gracefully, recoverability preserved); deletion is the *final* transition (cold→gone — after retention expires, legally signed, reversibly windowed — next promise). Conflating them purges what should tier (legal history deleted with yesterday's logs) or tiers what should purge (garbage retained in cold storage forever — "cheap" pennies compounding into real money plus discovery liability). Relocate first, delete last, sign always.

**Performance note** — tiering economics: hot tier sized for RAM residency (working set in memory — the p99 cliff from 2.1 avoided by evicting cold); warm tier sized for maintenance sanity (detached pieces VACUUMed rarely, excluded from nightly backups — backup windows shrink with hot size, not total size); cold tier priced in object-storage pennies (retrieval hours acceptable — obligation reads, not user reads). Backup-window math alone justifies tiering (nightly backup of hot 50GB vs full 2TB — hours vs overnight-failure) — price it per backup run, not per byte.

**Mentor note** — teach "which tier is this row in?" per table (juniors answering from access logs design temperature-first; guessing from age designs calendar-first — age correlates with temperature usually, but viral-old-rows and dead-young-rows break the correlation). Temperature measured (access counts), tiers assigned (policy), transitions automated (schedule) — the lifecycle habit in three clauses. Review tables by tier assignment the way code reviews check types: every table, every review, "tiers?" asked aloud.

## 2. Retention is a business rule (legal holds, tax years, user promises — policy first)

**Definition** — retention policy: per data category, how long it lives in each tier and when (and whether) it dies — stated by legal/product (tax records 7–10 years by jurisdiction; user content until account deletion + grace; telemetry 13 months; security logs per compliance framework), signed by owners, encoded in jobs. Policy precedes mechanism (purge jobs implement policy; they never invent it), and absence of policy defaults to *retain forever* (storage bills + discovery liability compounding silently — the most expensive default in data management, chosen by inaction everywhere).

**What problem it solves** — the policy vacuum duo: *purge paralysis* ("can we delete 2021 events?" — legal unasked, product unsure, engineering blocked — 5-year-old telemetry retained at hot-tier prices indefinitely, nobody empowered to decide) and *rogue purging* ("cleanup script" deleting user content under active legal hold — spoliation liability; or GDPR erasure executed against backups without a tested story — "deleted" everywhere except the restore that resurrects it). Policy converts both to procedure: named categories, signed durations, owned jobs — decisions made by authorized humans on schedule, never by engineers guessing under disk pressure.

**Modern guidance** — the retention register (one row per category): *category* (orders, events, user content, logs, backups); *tiers + durations* (hot 3mo → warm 10mo → cold 7yr → delete); *legal basis* (tax code §X, GDPR Art. 17, contract §Y — cited, not vibed); *owner + signer* (product/legal names — signatures dated); *job* (purge/archive procedure linked — 3.1's promise-3 discipline); *holds process* (litigation hold suspends purges — mechanism named: hold flag table checked by every purge job — holds override schedules structurally, never by email). Review yearly with legal present (laws change; promises expire; categories drift). No policy → retain (stated default, priced visibly — "unclassified data retained at $X/mo pending classification" motivates classification faster than any mandate).

```sql
-- GOOD: policy encoded with holds overriding schedules structurally.
-- Retention register: events (hot 3mo → warm 10mo → cold to 13mo → purge; basis: product
-- analytics need + privacy review 2026-06, signer: CPO; owner: data team).
CREATE TABLE legal_holds (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  scope      TEXT NOT NULL,   -- 'events:2024-q3' — category + window (purge jobs check)
  reason     TEXT NOT NULL,
  placed_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  released_at TIMESTAMPTZ      -- NULL = active: purge jobs skip scoped windows, structurally
);
-- Purge job predicate: ... AND NOT EXISTS (SELECT 1 FROM legal_holds WHERE scope matches
-- AND released_at IS NULL);  -- holds override by query structure, never by memory.
```

```sql
-- BAD: the policy vacuum — purges by courage, retention by inertia.
-- "Can we delete 2021 events?" (Legal: "not sure, check." Product: "maybe needed."
-- Engineering: retains — $X/mo indefinitely, discovery liability compounding.)
-- "Cleanup" deletes user uploads under active litigation (hold existed... in someone's
-- inbox — the purge job checks no hold table because none exists). Paralysis and
-- spoliation from one vacuum: no register, no signer, no hold mechanism. Policy absent;
-- consequences present, billed quarterly and in court respectively.
```

**Common confusion** — *"retention is just DELETE WHERE old."* Deletion is the final mechanical step of a legal-business-technical chain (policy → sign-off → hold-check → batch → verify → audit-log). "Just delete" skips holds (spoliation), verification (partial purges presenting as complete — auditors sample), and audit trails (proving deletion happened — GDPR accountability requires evidence of erasure, not just absence). Purge jobs produce *deletion certificates* (counts, windows, hold-checks passed, timestamps — retained themselves) — deletion you can't prove didn't happen compliantly.

**Performance note** — retention economics: unclassified retention bills hot-tier prices for cold-value data (the single largest waste in most database budgets — found by tiering audits, fixed by policy); rogue purges bill in bloat (mass DELETEs fragment — purge discipline from promise 3 applies: batched, off-peak, vacuumed after); legal noncompliance bills in fines (priced by regulators, not engineers — GDPR percentages of revenue dwarf any storage line). Policy pays three ways (storage, bloat-avoidance, fine-avoidance) — the highest-ROI document most teams never write.

**Mentor note** — teach "who signed this deletion?" per purge (juniors asking learn that deletion is an authorized act, not a technical one — the mindset shift from "can I?" (technically yes) to "may I?" (legally signed)). Pair juniors with legal/product for one retention review — the cross-functional conversation teaches domain gravity no schema drill conveys (tax years, litigation holds, user promises — real stakes, real signatures). Engineers who've sat retention reviews purge carefully forever after — one meeting, permanent caution.

## 3. Purge with the same discipline as migrate (batched, monitored, reversible-windowed)

**Definition** — purge discipline: deletions at volume follow the backfill template ([1.1](<../1. Schema evolution/1.1. Expand and contract migrations.md>)'s batching — chunked, throttled, resumable) plus deletion-specific guards: hold-checks (legal_holds consulted per batch — promises above), reversibility windows (soft-delete or delayed-hard-delete — purged rows recoverable for N days before finality), verification (counts pre/post, samples confirmed gone *and* confirmed complete — partial purges are the silent failure), and audit certificates (deletion evidence retained — counts, windows, signers, timestamps).

**What problem it solves** — the heroic purge (single DELETE of 300M rows — hours of locks, bloat storm, replica lag, vacuum backlog — plus irreversibility: wrong predicate discovered post-commit restores from backup, i.e., from hours ago, losing interim writes) and the incomplete purge (predicate missing a partition — old pieces detached-but-never-dropped, "deleted" data queryable via forgotten pieces; or timezone-window gaps — rows outside the assumed bounds surviving silently). Purge incidents share backfill physics (volume + locks + lag) plus deletion's unique irreversibility (migrate-wrong can re-migrate; purge-wrong restores from backup). Discipline converts both to routine.

**Modern guidance** — the purge template (per category, per window): (a) *scope query* (exact predicate — partition-bounded where partitioned — DETACH preferred over DELETE for whole pieces: milliseconds vs hours); (b) *hold check* (legal_holds consulted — structural, per batch); (c) *soft window* (deleted_at stamped or piece quarantined N days — restorable; hard purge after window + verification); (d) *batches* (10k–100k rows per chunk for DELETE purges — 1.1's chunking; sleeps on replica lag); (e) *verify both directions* (gone: sample old keys return nothing; complete: count of survivors in window is zero — absence proven both ways); (f) *certificate* (audit row: window, counts, holds-checked, signer, timestamp — retained permanently — proof of compliant deletion).

```sql
-- GOOD: purge as a job — scoped, held-checked, batched, verified both ways (verified PG 16.15 shapes).
-- Whole pieces first (metadata, preferred): ALTER TABLE events DETACH PARTITION events_2024_01;
--   quarantine piece 30 days (restorable), then DROP (finality witnessed).
-- Row purges where pieces mix (batched, hold-checked):
DELETE FROM events WHERE id IN (
  SELECT id FROM events
  WHERE occurred_at < '2024-01-01' AND deleted_at IS NULL
  ORDER BY id LIMIT 10000
);  -- chunk; sleep on lag; repeat from cursor. Hold-check predicate ANDed per batch.
-- Verify: SELECT count(*) FROM events WHERE occurred_at < '2024-01-01'; → 0 (complete)
-- + sampled old keys return nothing (gone) + certificate row written (proof).
```

```sql
-- BAD: the heroic purge — one statement, no holds, no window, no proof.
DELETE FROM events WHERE occurred_at < '2024-01-01';  -- 300M rows, one transaction:
-- locks for hours (writes queue, then time out, then retry-storm); bloat tsunami
-- (300M dead tuples — vacuum choking for days); replicas lagging hours (stale reads
-- cascade); legal hold on Q4-2023 violated (no hold table consulted — spoliation);
-- wrong-year rows included (predicate timezone bug — discovered post-commit, unrestorable
-- without backup surgery losing interim writes). No certificate (prove what, exactly?).
-- Deletion without discipline is data loss with extra steps.
```

**Common confusion** — *"DETACH makes purge discipline unnecessary."* DETACH removes *locking/bloat* pain (metadata operation — the mechanical win) but not *correctness* pain (wrong piece detached = data loss at metadata speed — faster mistakes, not fewer; holds still unchecked; verification still required; certificates still owed). DETACH is the preferred *mechanism*; discipline is the required *procedure* — mechanism without procedure fails faster and more completely. Detach carefully, verify always, certificate permanently.

**Performance note** — purge economics: DETACH (milliseconds — preferred wherever pieces align with windows — partition grain designed for retention from [2.2](<../2. Growth and capacity/2.2. Partitioning keys that prune.md>) pays here); batched DELETE (minutes-to-hours wall-time, throttled — replica lag bounded, locks sub-second per chunk); post-purge VACUUM (reclaim space — schedule after large purges; bloat unvacuumed is space unbought). Certificate storage trivial (rows per purge — permanent, tiny). Wrong-predicate restores priced in backup RTO (hours + interim-write loss — the number that justifies every verification step above).

**Mentor note** — teach "verify both directions" as the purge sacrament (gone *and* complete — juniors verifying one direction learn the other from the incident that finds it: survivors discovered in audit (incomplete) or needed rows missing (over-purge)). Pair first purges with senior witnessing (second eyes on scope predicate + hold check — the buddy system for irreversible operations). Irreversible operations deserve ceremony proportional to irreversibility — purges rank just below schema drops, and the culture should feel it.
