# 2.2. Partitioning keys that prune

## 1. Partition by query predicate (time, tenant, hash — pruning decides)

**Definition** — partitioning splits one logical table into physical pieces (range by time, list by tenant/region, hash by id) with the query planner skipping irrelevant pieces (*pruning* — verified above: September predicate touched only the September partition). The partition key is chosen from query predicates, not from data aesthetics: the key that appears in WHERE clauses prunes; keys absent from queries are expensive decoration (planning overhead per partition, zero skipped).

**What problem it solves** — the unpartitioned giant: 500M-row events table where every recency query scans history (indexes deepening, vacuum struggling, autovacuum never finishing a pass, backups swelling, deletes fragmenting) — or the mispartitioned giant (hash-partitioned by id for time-range queries — every query fans out to all partitions, planning time × N, pruning zero). Partitioning converts table-size problems into partition-count arithmetic: queries touch relevant pieces, maintenance operates per piece (VACUUM/REINDEX/DETACH per partition — small, fast, online), archival detaches pieces (3.1's procedure) instead of deleting rows.

**Modern guidance** — the key-selection procedure (run once per giant, recorded): (a) list the dominant predicates (time ranges? tenant equality? id lookups?) — from the query catalog habit ([Domain 03 §1.2](<../../../03 Document Modeling for Scale/sections/1. Aggregates and access/1.2. Access patterns drive document shape.md>)); (b) match key type (time predicates → RANGE by month/quarter; tenant predicates → LIST by tenant/region; uniform point lookups, no range pattern → HASH by id — spread without pruning claims); (c) verify pruning (EXPLAIN shows only relevant partitions — checked per query pattern, not assumed — the verification step teams skip and regret). Mixed predicates (time + tenant) → subpartition or leading-key choice by dominance (time usually wins — recency queries outnumber tenant sweeps; tenant-then-time where tenancy isolates legally).

```sql
-- GOOD: key from predicates — recency queries prune, maintenance per piece (verified PG 16.15).
CREATE TABLE events (
  id          BIGINT GENERATED ALWAYS AS IDENTITY,
  occurred_at TIMESTAMPTZ NOT NULL,
  payload     JSONB,
  PRIMARY KEY (id, occurred_at)   -- partition key in PK (required for uniqueness across pieces)
) PARTITION BY RANGE (occurred_at);

CREATE TABLE events_2026_09 PARTITION OF events
  FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
-- EXPLAIN SELECT ... WHERE occurred_at >= '2026-09-10' AND occurred_at < '2026-09-20';
-- → Seq Scan on events_2026_09 ONLY (October pruned — verified above, not asserted).
-- Maintenance: VACUUM/REINDEX per piece; archival: DETACH old pieces (3.1).
```

```sql
-- BAD: key from aesthetics — hash by id for time-range workloads (pruning zero).
CREATE TABLE events_bad (
  id      BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  occurred_at TIMESTAMPTZ NOT NULL,
  payload JSONB
) PARTITION BY HASH (id);
-- Every recency query fans out to ALL partitions (id hash says nothing about time):
-- planning × N, execution × N, maintenance × N — partitioning's costs without its
-- benefit. The key decorates; the workload suffers. Predicate-less keys are overhead.
```

**Common confusion** — *"partitioning makes queries faster."* Partitioning makes *prunable* queries touch less data (faster) and *unprunable* queries touch more planning (slower — planning time grows with partition count). Net effect depends entirely on predicate coverage: recency-predicated workloads speed up dramatically; ad-hoc analytics across all history slow marginally (planning per piece). "Faster" is predicate-conditional — verify per query pattern (EXPLAIN per pattern, recorded), never assume globally.

**Performance note** — partition economics: pruning converts O(table) scans to O(relevant pieces) (500M rows → 20M September piece — 25× less I/O per recency query); maintenance converts table operations to piece operations (VACUUM September: minutes vs hours; REINDEX: per piece, online-friendly); planning costs O(pieces) per query (hundreds of partitions: measurable planning overhead — the count budget from promise 3). Archival becomes metadata (DETACH — milliseconds — vs DELETE millions — hours): the lifecycle payoff that alone justifies partitioning time-series tables.

**Mentor note** — teach "show me the EXPLAIN" as the partitioning proof ritual (juniors claiming pruning demonstrate it per query pattern — one EXPLAIN per dominant predicate, checked into the design record). Unverified pruning claims are the partitioning version of untested backups — believed until needed, absent when needed. Proof per pattern, recorded per table — the ritual takes minutes and prevents the most expensive partitioning failure (believed-but-absent pruning discovered at scale).

## 2. Keys must appear in queries (unpruned partitions are expensive decoration)

**Definition** — the pruning contract: a partition key pays for itself only where queries constrain it. Time-partitioned tables queried by time prune (the common case — recency dominates); the same tables queried by user_id alone scan all pieces (no time predicate — nothing to prune on). Every query pattern gets a pruning verdict (prunes / scans-all / partially prunes) — patterns scanning all pieces at volume need either predicate changes (add time bounds — application change, often free) or secondary partitioning (tenant subpartitions where tenancy isolates).

**What problem it solves** — the decoration partition: tables partitioned "for scale" on keys their queries never constrain (tenant-partitioned tables queried globally per dashboard — every dashboard query fans out; time-partitioned tables queried by id lookups — point queries planning across hundreds of pieces). Costs paid fully (planning overhead, manageability, DDL complexity per piece) for benefit zero (nothing pruned, ever). Pruning verdicts per pattern expose decoration before adoption: unpruned patterns either gain predicates (cheapest fix — bound the time range in application code) or the key changes (partition by what queries constrain, not by what data suggests).

**Modern guidance** — the pruning audit per table (three columns: query pattern, predicate present?, verdict): dominant patterns must prune (recency queries on time-partitioned events — yes; tenant dashboards on tenant-partitioned data — yes); rare patterns may scan (yearly compliance export touching all pieces — acceptable, scheduled, off-peak); point lookups need key-inclusive access paths (id lookups on time-partitioned tables — include time bounds where known, accept fan-out where not — point queries fan out cheaply: N partition probes, each indexed — affordable, unlike scans). Fix order for unpruned dominants: add predicates first (free), subpartition second (structural), rekey last (migration — [1.1](<../1. Schema evolution/1.1. Expand and contract migrations.md>)'s discipline applies to partition keys too).

```sql
-- GOOD: pruning audited per pattern — dominants prune, rares scheduled, points affordable.
-- Pattern A (dashboard recency, 800k/day): WHERE occurred_at >= now() - '7 days' → prunes
--   to 1 piece (verified EXPLAIN — recorded). Pattern B (yearly export, 12/year):
--   scans all pieces — scheduled off-peak, acceptable (rare × slow beats common × slow).
-- Pattern C (point lookup by id): fans out N probes — each indexed, microseconds;
--   affordable (probes ≠ scans — fan-out cost counted, found trivial).
```

```sql
-- BAD: decoration audited never — partitioned for scale, queried against the key.
-- Tenant-partitioned orders queried per global dashboard (no tenant predicate — ever):
-- every render fans out to all tenant pieces (planning × N, execution × N, slowest
-- piece sets latency). Time-partitioned events queried by payload contents (no time
-- bounds — full-history JSONB scans per search). Partitioning adopted, predicates
-- ignored — costs fully paid, benefits never collected. Decoration, itemized.
```

**Common confusion** — *"global secondary indexes fix unpruned queries."* PostgreSQL has no global indexes on partitioned tables (each partition indexes itself — N local indexes, not one global) — cross-partition queries consult N indexes (planning + probing per piece). Local indexes serve pruned queries beautifully and unpruned queries expensively; no index type rescues a predicate-less pattern. Predicates prune; indexes accelerate pruned access — different jobs, both required, neither substituting. (Version-labeled as-of-September-2026: global indexes remain absent in PostgreSQL partitioned tables.)

**Performance note** — pruning math: pruned query cost ≈ pieces-touched × per-piece cost (1 piece ≈ unpartitioned-table-of-that-size performance — partitioning preserves speed while bounding size); unpruned cost ≈ N pieces × (planning + probing) (N=200: planning alone milliseconds before execution — measurable, sometimes dominant for fast queries). The ratio decides key fitness: dominant-pruned → fit; dominant-unpruned → rekey or repredicate. Count predicates before counting partitions — fitness is workload-relative, never absolute.

**Mentor note** — teach "which predicate prunes this?" per partitioned table (juniors answering instantly design predicate-first; hesitation locates decoration). The question generalizes beyond partitioning (index selection, shard keys, bucket windows — every distribution decision answers "what constrains it?"). Distribution literacy starts here: data placed by predicate, queried by predicate, verified by EXPLAIN. Three clauses, one habit, every scale decision thereafter.

## 3. Partition count is a budget (hundreds, not thousands — planning, locks, manageability)

**Definition** — the count budget: partition totals stay in the low hundreds per table (monthly pieces ≈ 12/year — a decade is 120; tenant pieces ≈ tenant count — fine to hundreds). Thousands of partitions degrade planning (per-piece planning time × N — slow queries before execution), locking (DDL touching parent locks children — fan-out), and manageability (DETACH/REINDEX/VACUUM per piece × N — operational toil scaling with count). Budgets are set per table with growth math (pieces/year × horizon ≤ budget) and enforced by grain choice (monthly vs daily vs yearly — grain is the budget lever).

**What problem it solves** — the partition explosion duo: *over-fine grain* (daily partitions "for precision" — 3,650 pieces per decade — planning overhead dominating fast queries, autovacuum never completing a cycle across pieces, pg_class bloat from thousands of relations) and *under-fine grain* (yearly pieces for hot recency queries — 50GB pieces, maintenance back to table-scale, archival too coarse for retention windows). Grain mismatched to workload in either direction bills permanently (too many: planning + toil; too few: maintenance + archival pain). Budgeted grain matches piece size to operations (pieces sized for VACUUM-in-minutes, DETACH-per-retention-window, planning-in-microseconds).

**Modern guidance** — the grain procedure: (a) size pieces by maintenance (VACUUM/REINDEX comfortable in minutes — tens of GB max per piece at typical hardware — measure, don't guess); (b) size pieces by retention (DETACH granularity matching archival windows — monthly retention → monthly pieces — 3.1's procedure consumes what grain produces); (c) count the horizon (pieces/year × retention years ≤ low hundreds — else coarsen grain or shorten retention); (d) default-forward (new pieces auto-created — pg_partman-style automation or scheduled DDL — manual piece creation is toil scheduled as incidents when forgotten). Subpartitioning only for two-dimensional dominance (tenant × time where both isolate — rare; each level multiplies counts — budget both).

```sql
-- GOOD: budgeted grain — monthly pieces, decade horizon, automated creation.
-- Grain: monthly (VACUUM minutes per piece; DETACH matches 13-month retention — 3.1).
-- Horizon: 10 years × 12 = 120 pieces (budget ≤500 — headroom 4×, trigger at 300).
-- Automation: scheduled DDL creates next quarter's pieces (forgotten creation = failed
-- INSERTs at month boundary — the outage automation prevents; monitor piece-ahead count).
CREATE TABLE events_2026_10 PARTITION OF events
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');  -- created ahead, monitored
```

```sql
-- BAD: grain unbudgeted — daily pieces for a decade of mild queries.
-- 3,650 partitions: planning overhead per query (milliseconds before execution —
-- dominating fast point queries); autovacuum cycling endlessly (never finishing all
-- pieces — bloat accumulating everywhere); pg_dump/pg_class groaning (thousands of
-- relations to enumerate); DDL on parent fanning out (locks × 3,650 — deploys freeze).
-- Precision nobody needed (daily DETACH for yearly retention?) billing everybody daily.
```

**Common confusion** — *"more partitions means more parallelism."* Partition-wise joins/aggregates parallelize across pieces (real benefit — version-dependent, check planner behavior as-of your PostgreSQL), but parallelism gains saturate (dozens of workers max — hundreds of pieces queue, not parallelize) while planning/toil costs grow unboundedly with count. Parallelism argues for *enough* pieces (match worker counts, not exceed them 100×); budgets argue against *excess*. Enough, not more — parallelism saturates, overhead doesn't.

**Performance note** — count economics: planning time ≈ linear in pieces (measured per version — verify on yours: EXPLAIN a point query at 50 vs 500 pieces, plot it once); lock fan-out ≈ pieces touched per DDL (parent DDL ripples — schedule accordingly); autovacuum coverage ≈ workers ÷ pieces (thousands of pieces starve each — bloat everywhere, slowly). The budget number (low hundreds) balances pruning granularity against all three — derived from measurements, round only in presentation. Budgets with math beat budgets with vibes — plot once, budget forever (re-plot per major version).

**Mentor note** — teach "count the pieces in ten years" per partitioned table (juniors multiplying grain × horizon catch explosions before creation — "daily × 10 years = 3,650 — too many, monthly" — in seconds). The ten-year question generalizes (retention windows, version budgets, trigger horizons — every scale decision has a horizon; unexamined horizons expire as incidents). Horizons first, grains second, budgets always — the capacity habit in miniature, same as [2.1](<2.1. Capacity modeling with measured triggers.md>)'s spreadsheet at table scale.
