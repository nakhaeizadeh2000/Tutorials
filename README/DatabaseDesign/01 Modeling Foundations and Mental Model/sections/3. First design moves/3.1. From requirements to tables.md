# 3.1. From requirements to tables

The worked method, end to end. Requirements paragraph (invented, deliberately ordinary):

> *"A bookstore sells books online. Customers register with an email and place orders; each order contains one or more books with quantities. Books have an ISBN, a title, a price, and one or more authors. Authors have names."*

What follows is the method from the three questions ([1.1](<../1. What modeling means/1.1. What data modeling is and is not.md>)), applied mechanically. All DDL below executed on PostgreSQL 16.15.

## 1. Nouns become tables (the requirements paragraph already lists your entities)

**Definition** — underline every noun phrase in the requirements; each candidate entity passes the lifecycle test from [1.2](<../1. What modeling means/1.2. Entities relationships and cardinality.md>): independent identity, independent lifecycle. Surviving nouns are tables; the rest are columns or someone else's problem.

**Applied** — nouns: *bookstore* (the system itself — not a table), *customers* (identity: email; lifecycle: register, order — entity), *orders* (identity: order number; lifecycle: placed, fulfilled — entity), *books* (identity: ISBN; lifecycle: published, priced — entity), *authors* (identity: name... weak, needs a surrogate — entity), *quantities* (a number on a line — column), *emails* (identifier of customer — column), *ISBN/title/price/names* (attributes — columns).

**Modern guidance** — run the test out loud for each noun, especially the tempting non-entities: "can a quantity exist without its line?" No → column (on the line entity, which the verbs will reveal next). "Can an author exist without a book?" Yes (new author, first book next month) → entity. The discipline is discarding nouns, not collecting them.

```sql
-- GOOD: four entities, each with identity — authors included despite having
-- only a name today (biographies arrive next quarter; the entity was real anyway).
CREATE TABLE customers (
  id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email TEXT UNIQUE NOT NULL
);

CREATE TABLE authors (
  id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name TEXT NOT NULL
);

CREATE TABLE books (
  id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  isbn  TEXT UNIQUE NOT NULL,
  title TEXT NOT NULL,
  price NUMERIC(10, 2) NOT NULL CHECK (price >= 0)
);
-- orders + lines arrive with the verbs (next section) — entities first, relationships second
```

```sql
-- BAD: every noun kept, none tested — quantities and emails promoted to tables
-- they cannot sustain (no identity, no lifecycle), while the real entities wait.
CREATE TABLE quantities (id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, qty INT);
CREATE TABLE emails (id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, email TEXT);
-- The schema now has tables for numbers and strings, and joins for everything.
```

**Common confusion** — *"the requirements mention X, so X is a table."* Requirements mention attributes, roles, and system names too. The noun list is candidates, not conclusions — the lifecycle test is the election. Skipping the test produces schemas with tables for adjectives.

**Performance note** — phantom tables (quantities, emails above) cost a join on every query that touches their parent — permanent join tax for entities that never needed independence. Each rejected noun saves a join forever; noun-discipline is performance work disguised as pedantry.

**Mentor note** — run this as a team exercise: hand juniors a requirements paragraph and five minutes, then compare noun lists. Disagreements ("is *shipment* an entity?") are the lesson — they surface lifecycle thinking faster than lectures. Collect the team's discarded nouns; they make excellent review anecdotes.

**Cross-links** — attribute-vs-entity at scale (when a column grows into a table under load) is Domain 05 evolution (forward — unbuilt).

## 2. Verbs become relationships (each verb hides a cardinality decision)

**Definition** — circle every verb connecting two nouns; each verb is a relationship with a cardinality to decide: *place* (customers→orders), *contain* (orders→books, with quantities — a line entity hiding in the verb), *write* (authors→books). The verb's fine print ("one or more") is the cardinality sentence from [1.2](<../1. What modeling means/1.2. Entities relationships and cardinality.md>).

**Applied** — *customers place orders*: one customer, many orders; an order belongs to exactly one customer → FK `orders.customer_id` NOT NULL. *Orders contain books with quantities*: an order has many lines, each line names one book and a quantity → `order_lines` entity (it has lifecycle: added, refunded per line — the verb concealed an entity). *Authors write books*, "one or more" both ways → many-to-many → junction `book_authors` with composite PK.

**Modern guidance** — interrogate every verb for its plural: "can an order contain the same book twice?" (separate lines vs quantity merge — business call, model either, record it). "Can a book exist with no author?" (corporate publications — yes → junction rows optional, book independent). Verbs without asked plurals are the cardinality bets from 1.2, unpriced.

```sql
-- GOOD: every verb translated — relationships enforced, hidden entity (lines) surfaced.
CREATE TABLE orders (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id),  -- "place": N orders, 1 customer
  placed_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE order_lines (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id BIGINT NOT NULL REFERENCES orders (id),   -- "contain": the hidden entity
  book_id  BIGINT NOT NULL REFERENCES books (id),
  quantity INT NOT NULL CHECK (quantity > 0)
);

CREATE TABLE book_authors (
  book_id   BIGINT NOT NULL REFERENCES books (id),     -- "write": N-to-N
  author_id BIGINT NOT NULL REFERENCES authors (id),
  PRIMARY KEY (book_id, author_id)
);
```

```sql
-- BAD: verbs unmodeled — books folded into the order as an array, authorship as text.
-- "Which orders contain book X?" / "all books by author Y?" are now unanswerable in SQL.
CREATE TABLE orders_bad (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id),
  book_ids    BIGINT[] NOT NULL,   -- the verb "contain", entombed in an array
  author_names TEXT NOT NULL       -- the verb "write", entombed in a string
);
```

**Common confusion** — *"the junction table has no id column — is that allowed?"* Yes, and preferred here: the composite PK *is* the identity ("this author wrote this book" occurs once). A surrogate id on a pure junction adds nothing and weakens the duplicate protection — reach back to [2.1](<../2. Identity and keys/2.1. Surrogate versus natural keys.md>)'s rule: default surrogate, *justify* natural — the composite key here is justified in one sentence.

**Performance note** — `order_lines` will dwarf every other table (rows = orders × lines) — the schema's hot center. Its FKs need indexes (PostgreSQL doesn't auto-index FKs — Databases 02), and its growth rate drives capacity planning (Domain 05 forward). Verb analysis already told you which table to watch: the one every verb feeds.

**Mentor note** — teach "find the hidden entity in the verb" as a puzzle: *enrollments* hide in "students take courses," *lines* hide in "orders contain books," *memberships* hide in "users join teams." Juniors who collect three such discoveries start seeing entities everywhere — which is exactly the skill.

**Cross-links** — junction tables at scale (growth, partitioning, hot keys) deepen in Domain 04 relationships at scale (forward — unbuilt).

## 3. Constraints are the design (NOT NULL, UNIQUE, and FKs are modeling sentences)

**Definition** — the final pass: translate every business rule that survived nouns and verbs into constraints, and read the schema back as English. "Each order contains one or more books" → enforced how? (CHECK or application count — record which.) "ISBNs are unique" → UNIQUE. "Prices are never negative" → CHECK. "Lines always point at real books" → FK. A rule with no constraint is a wish.

**Applied** — walk the bookstore rules: emails identify customers → UNIQUE (done in entities). ISBN unique → UNIQUE. Price ≥ 0 → CHECK. Quantity ≥ 1 ("one or more") → CHECK. Every line's book/order real → FKs. Every order has a customer → NOT NULL + FK. Author names required → NOT NULL. What resists constraints: "an order contains *one or more* books" (minimum-cardinality needs a trigger or application check — *record the gap explicitly* rather than pretending the schema covers it).

**Modern guidance** — finish with two artifacts: (a) the DDL, every constraint a translated sentence; (b) the gap list — rules the schema cannot express (minimum cardinalities, cross-row invariants, temporal rules) with their enforcement owner named (trigger, application, batch job). The gap list is a design deliverable, not an apology — reviewers bless it or challenge it, but nobody discovers it in production.

```sql
-- GOOD: the complete bookstore — read it as English, rule by rule.
CREATE TABLE customers (
  id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email TEXT UNIQUE NOT NULL             -- "emails identify customers"
);

CREATE TABLE authors (
  id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name TEXT NOT NULL                     -- "every author has a name"
);

CREATE TABLE books (
  id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  isbn  TEXT UNIQUE NOT NULL,            -- "ISBNs are unique"
  title TEXT NOT NULL,
  price NUMERIC(10, 2) NOT NULL CHECK (price >= 0)   -- "prices are never negative"
);

CREATE TABLE book_authors (
  book_id   BIGINT NOT NULL REFERENCES books (id),
  author_id BIGINT NOT NULL REFERENCES authors (id),
  PRIMARY KEY (book_id, author_id)       -- "no duplicate authorship"
);

CREATE TABLE orders (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id),  -- "every order has a customer"
  placed_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE order_lines (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id BIGINT NOT NULL REFERENCES orders (id),  -- "lines point at real orders/books"
  book_id  BIGINT NOT NULL REFERENCES books (id),
  quantity INT NOT NULL CHECK (quantity > 0)        -- "one or more" (per line)
);
-- GAP LIST (rules the schema cannot express — owners named):
-- G1 "an order has ≥1 line": application check at checkout (owner: orders service).
-- G2 "price at order time is frozen": order_lines.unit_price snapshot (deferred —
--    Domain 05 evolution; today's prices are current-price by documented decision).
```

```sql
-- BAD: same tables, wishes instead of sentences — no CHECK, no UNIQUE, nullable FKs.
CREATE TABLE books_bad (
  id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  isbn  TEXT,                 -- duplicates welcome
  title TEXT,
  price NUMERIC(10, 2)        -- negative prices welcome
);
-- Every rule now lives in application code paths — all of them, under every race.
```

**Common confusion** — *"CHECK constraints are just validation duplication."* Validation guides input; CHECKs bound the data against every writer (backfills, admin consoles, future services, bugs). The price rule above survives a bulk-import script that never saw the signup form — that is the difference, and it is worth restating every time.

**Performance note** — CHECKs and FKs cost microseconds per write and pay back in reads (planner constraints) and incidents avoided (no cleanup migrations for impossible states). The gap list has its own performance clause: G1's application check needs a transaction around order creation — name the isolation requirement now (Databases 04 owns the mechanics), not during the incident.

**Mentor note** — require the gap list in every design doc review. Juniors resist ("it admits incompleteness"); reframe: the gap list is what makes the design *complete* — known unknowns with owners beat unknown unknowns every time. Seniors model this by writing their own gaps first.
