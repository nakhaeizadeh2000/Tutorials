# 4.1. Modeling checklist mentors insist on

## 1. Every table earns its name (singular nouns, no tbl_ prefixes, junction tables say what they join)

**Definition** — table names are the schema's user interface: `customers`, `orders`, `order_lines`, `book_authors`. The convention: singular nouns (`customer`, not `customers`? or plural — *pick one*, document it, enforce it), no Hungarian prefixes (`tbl_`, `dim_`, ` tbl` — the catalog already knows they are tables), junction tables named from both sides (`book_authors`, never `mapping_table_3`).

**What problem it solves** — inconsistent naming is a daily tax: every query starts with "was it `user` or `users`?", every join guesses junction names, every new hire learns by failing. Worse, vague names hide vague thinking — a table called `data`, `info`, `records`, or `general` is an unmodeled entity with a nameplate. Naming reviews catch modeling gaps before DDL does.

**Modern guidance** — lint names in review with three rejections: (a) *meaningless* (`data`, `info`, `misc`, `temp` without a dated expiry comment) — rename to the entity; (b) *prefixed* (`tbl_orders`) — strip; (c) *lying* (`active_users` as a table instead of a view/query — snapshots rot; name tables for what they *store*, views for what they *select*). Junction tables: `a_b` alphabetical or domain-ordered — consistency over cleverness.

```sql
-- GOOD: names narrate the domain — a stranger reads the catalog like a paragraph.
customers, authors, books, book_authors, orders, order_lines, payments
-- Junction tables say what they join; line tables say whose lines they are.
```

```sql
-- BAD: the catalog as a puzzle — prefixes, plurals mixed, junctions anonymous.
tbl_customers, author (singular here, plural there), data, mapping_table_3,
active_users_snapshot_2024_FINAL  -- a table pretending to be a query result
```

**Common confusion** — *"singular vs plural is bikeshedding."* The choice is arbitrary; the *consistency* is not. Mixed conventions break every generic tool (repository bases, admin UIs, code generators assume one rule). Bikeshedding is arguing for an hour; professionalism is writing the rule down in five minutes and moving on.

**Performance note** — naming has no runtime cost and enormous *incident-response* value: at 3 a.m., `order_lines` is found in seconds while `mapping_table_3` requires archaeology. Name for the on-call engineer who has never seen this schema — readability under stress is performance of the team.

**Mentor note** — make naming the *first* review comment and the *kindest* one: "suggest `book_authors` — junctions read better named from both sides." Juniors learn conventions fastest through naming feedback because it is concrete, frequent, and never personal. Save architectural objections for below the naming line.

## 2. Every relationship is drawn both ways (if you cannot state the reverse rule, you have not modeled it)

**Definition** — for each relationship, state both directions as sentences: "a customer places *many* orders" **and** "an order belongs to *exactly one* customer." The reverse sentence is where missing NOT NULLs, missing junction tables, and wrong cardinalities hide — forward sentences describe intent, reverse sentences expose enforcement.

**What problem it solves** — forward-only modeling produces the classic defects: "users have roles" modeled (FK added) while "a role has many users, and deleting a role does *what* to them?" unasked — until a delete cascades (or is blocked) in production. The reverse question forces `ON DELETE` policy, nullability, and cardinality to be decided rather than defaulted.

**Modern guidance** — the review ritual: for every FK in a PR, the author writes both sentences plus the delete rule ("orders deleted → lines CASCADE; customers deleted → BLOCKED while orders exist"). Reviewers verify sentence against constraint and delete policy against business rule. Three lines per FK in the PR description; five minutes per review; orphan-row and surprise-cascade incidents approach zero.

```sql
-- GOOD: both directions stated, delete policy explicit — the PR description writes itself.
-- Forward: "a customer places many orders."
-- Reverse: "an order belongs to exactly one customer; deleting a customer with
--           orders is blocked (business rule: history is immutable)."
customer_id BIGINT NOT NULL REFERENCES customers (id) ON DELETE RESTRICT
-- Forward: "an order has many lines."
-- Reverse: "a line belongs to exactly one order; lines die with their order."
order_id BIGINT NOT NULL REFERENCES orders (id) ON DELETE CASCADE
```

```sql
-- BAD: forward-only — the FK exists but the reverse was never asked.
-- What deletes what? The default (NO ACTION) answers at runtime, in production.
customer_id BIGINT REFERENCES customers (id)  -- nullable: reverse sentence missing
                                               -- ("must every order have a customer?")
                                               -- delete rule missing: surprise someday
```

**Common confusion** — *"`ON DELETE` choices are DBA trivia."* They are business rules wearing SQL syntax: CASCADE means "children are meaningless without the parent" (lines without orders — true); RESTRICT means "history outlives the actor" (orders outlive... well, the business decides); SET NULL means "the connection was optional all along." Each choice narrates the domain — trivia never did that.

**Performance note** — CASCADE deletes on huge child tables (millions of lines) are *slow, locking operations* — the reverse sentence must include volume awareness ("deleting a ten-year customer cascades 2M lines — use soft-delete + batch purge instead," owned operationally by Domain 06 forward). The relationship review is where that bomb gets spotted, years before it detonates.

**Mentor note** — teach juniors to *read schemas backwards*: pick any FK and recite the reverse sentence plus delete behavior. Five minutes of this exercise on the existing schema reliably surfaces two or three unasked questions — which become the team's first relationship-review wins and the habit's best advertisement.

## 3. Every key choice is written down (the next hire should find the why, not re-derive it)

**Definition** — key decisions (surrogate vs natural per [2.1](<../2.%20Identity%20and%20keys/2.1.%20Surrogate%20versus%20natural%20keys.md>), sequence vs UUID per [2.2](<2.2.%20Identity%20at%20scale.md>), composite vs surrogate on junctions) get a one-line rationale recorded where the next hire looks: migration comment, design doc, or schema comment — never just the author's memory.

**What problem it solves** — six months later, "why is this UUID?" has three possible answers (multi-writer need, cargo-cult, or copy-paste) with three different correct responses (keep, migrate, standardize) — and no way to distinguish them without the author, who left. Undocumented decisions get re-litigated or, worse, "fixed" into regressions by well-meaning successors.

**Modern guidance** — the cheapest record is a SQL comment on the column or table (`COMMENT ON COLUMN device_events.id IS 'UUIDv4: offline devices mint ids; see ADR-014';`), backed by an ADR (Architecture Decision Record) for cross-table policies ("all PKs BIGINT identity except device_events — ADR-014"). Rule of thumb: column comment for the *what*, ADR for the *why*. Review checks: new key type → comment present; new policy → ADR linked.

```sql
-- GOOD: the why travels with the schema — found by the next hire in psql, not in Slack history.
CREATE TABLE device_events (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),  -- offline minting; ADR-014
  ...
);
COMMENT ON TABLE device_events IS 'Multi-writer ingest; UUID per ADR-014 (2026-09). Revisit if ingest centralizes.';

-- GOOD: policy-level record (ADR-014, one paragraph):
-- "PKs default BIGINT identity (cheap, ordered). Exception: device_events uses UUIDv4
--  because field devices mint ids offline. Revisit: if ingest centralizes, migrate to
--  identity (cost: backfill + FK rewrite — priced, not feared)."
```

```sql
-- BAD: the decision evaporates — the schema shows what, nobody knows why.
CREATE TABLE device_events (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),  -- (no comment, no ADR)
  ...
);
-- Successor, 2027: "UUIDs are slow, migrate to BIGINT?" — re-derives the offline
-- requirement the hard way (field-device outage) because the why was never written.
```

**Common confusion** — *"comments rot; code is truth."* Stale comments are a real risk — which is why the comment states the *reason* (stable: "offline minting") not the *mechanism* (volatile: syntax). Reasons rot slower than code changes; dated comments ("ADR-014, 2026-09") let readers judge freshness. The alternative — no record — rots instantly.

**Performance note** — documentation has no query cost; its performance value is in *preventing* expensive re-derivations (wrong-way migrations, load-test rediscoveries). One prevented key-strategy migration funds a decade of column comments.

**Mentor note** — model this by writing your own whys first, especially on senior-authored schemas ("I chose this in 2024 because…"). Juniors imitate what seniors do, not what checklists say — a senior's column comment teaches more than a wiki page about documentation culture. Review praise for good whys ("great ADR link") reinforces faster than any mandate.
