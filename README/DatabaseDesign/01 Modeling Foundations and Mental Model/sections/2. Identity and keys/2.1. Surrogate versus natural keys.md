# 2.1. Surrogate versus natural keys

## 1. Natural keys describe (emails and slugs mean something — and meaning changes)

**Definition** — a natural key is a primary key drawn from the business domain itself: an email, a country code, a slug, an ISBN. It identifies a row *by describing it* — the key's value carries meaning a human can read.

**What problem it solves / history** — natural keys are the oldest modeling instinct: before auto-increment existed, keys *had* to be meaningful (ledger numbers, license plates). They read beautifully in raw data (`WHERE country = 'DE'` needs no join) and they prevent a whole class of duplication by construction — two rows cannot share the "same" email if the email *is* the key.

**Modern guidance** — use natural keys as *identifiers of convenience*, not as *anchors of relationship*. The failure mode is always change: people change emails, companies rebrand slugs, countries split (Sudan/SS), ISBNs get reassigned. Every natural key is a business fact, and business facts change — when the key changes, every foreign key pointing at it must cascade, and cascading primary-key updates across millions of rows is the migration nobody wants to run. Rule: natural values get UNIQUE constraints (still enforced, still queryable); relationships point elsewhere.

```sql
-- GOOD: the natural value is protected (UNIQUE) but nothing depends on it.
-- Renaming the slug is one UPDATE to one row.
CREATE TABLE accounts (
  id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email TEXT UNIQUE NOT NULL,   -- natural identifier, enforced — but not referenced
  slug  TEXT UNIQUE NOT NULL    -- rename-safe: no FK points here
);
```

```sql
-- BAD: the slug IS the primary key — every referencing table stores it.
-- A rebrand now cascades across the whole database.
CREATE TABLE accounts_bad (
  slug TEXT PRIMARY KEY  -- "acme" → "acme-inc" rewrites every FK in the system
);

CREATE TABLE invoices_bad (
  id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  account_slug TEXT NOT NULL REFERENCES accounts_bad (slug)  -- coupled to a name
);
```

**Common confusion** — *"UNIQUE is the same as PRIMARY KEY, so this is just style."* Nearly — but PKs are the conventional FK target, cannot be NULL, and most tooling (ORMs, replication, admin UIs) assumes a single immutable PK. UNIQUE gives the enforcement without the coupling. Style with consequences.

**Performance note** — natural PKs are usually *wider* (TEXT vs BIGINT): wider keys bloat every index that includes them, including all referencing FK indexes. A BIGINT FK is 8 bytes; a slug FK is 8 + string length on every row of every child table. At scale this is real storage and cache pressure — another quiet vote for narrow surrogates.

**Mentor note** — juniors propose natural keys because sample data never changes ("emails are unique, right?"). Counter with one question: "what happens when it changes?" — then tell the country-split story (Sudan → Sudan + South Sudan, 2011; every `country CHAR(2)` PK in the world noticed). One historical anecdote ends the debate permanently.

## 2. Surrogate keys identify (a meaningless id survives renames, merges, and regulation)

**Definition** — a surrogate key is a system-generated identifier with no business meaning: a sequence (`GENERATED ... AS IDENTITY`), a UUID, a Snowflake-style id. It identifies the row and nothing else — which is exactly why it never needs to change.

**What problem it solves** — three change-events kill natural keys and leave surrogates untouched: **renames** (slug/email change → one UPDATE, zero FK churn); **merges** (two duplicate customer rows merge → surviving id wins, children re-point once); **regulation** (GDPR erasure of the email → the id stays, history stays consistent, the person is gone). Meaningless identifiers are *stable* identifiers, and stability is what FK graphs need.

**Modern guidance** — default to `BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` on PostgreSQL (as of September 2026 — the modern spelling; `SERIAL` is legacy). It is narrow (8 bytes), ordered (index-friendly inserts), and human-debuggable (small numbers in logs). Reach for UUIDs only when generation must be distributed (multi-writer, offline clients) — the trade is covered in 2.2, not here.

```sql
-- GOOD: merges are bookkeeping, not surgery.
-- Two duplicate customers (ids 101, 202) merge into 101:
-- children re-point once, history intact, no key ever changed meaning.
CREATE TABLE customers (
  id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email TEXT UNIQUE NOT NULL
);

CREATE TABLE orders (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id)
);
-- merge: UPDATE orders SET customer_id = 101 WHERE customer_id = 202;
--        DELETE FROM customers WHERE id = 202;
```

```sql
-- BAD: no surrogate, email is the anchor — GDPR erasure ("delete my email")
-- now means deleting the identity every order points at, or keeping data
-- the user asked to delete. The model fights the regulation.
CREATE TABLE customers_bad (
  email TEXT PRIMARY KEY  -- erasure and identity are the same column: pick one
);
```

**Common confusion** — *"surrogate keys are wasteful — an extra column for nothing."* Eight bytes per row buys: rename-safety, merge-safety, regulation-safety, narrow FKs, and stable ORM/repository identity. That is the cheapest insurance in schema design. The "waste" framing counts bytes and ignores migrations.

**Performance note** — monotonically increasing BIGINTs insert at the B-tree's right edge (page splits amortized, cache-hot); random UUIDs scatter inserts across the index (every insert a cold page — 2.2 quantifies this). Default ordered unless distribution forces otherwise.

**Mentor note** — make "default surrogate, justify natural" a review rule with the burden of proof stated: anyone proposing a natural PK writes the change-story ("when X changes we will…"). Most proposals die at that sentence — which is the rule working.

## 3. Default surrogate, justify natural (the burden of proof runs one way)

**Definition** — a team convention: every table gets a surrogate PK unless a written justification shows a natural key is stable *forever* (truly immutable, short, fixed-alphabet values — ISO currency codes are the textbook survivor). The convention exists so key choice is a decision with a record, not an accident of who wrote the migration.

**What problem it solves** — without a default, key style varies per author and per month: half the schema on slugs, half on sequences, joins mixing TEXT and BIGINT, merges that touch twelve tables. A default buys uniformity; the escape hatch (justified naturals) buys honesty for the rare genuine case.

**Modern guidance** — encode the default in review, not in hope: a checklist item ("surrogate PK? if natural, where is the justification?") plus a migration template with the identity column pre-filled. Genuine natural-PK survivors: ISO currency/language codes, fixed enumerations owned by standards bodies — values that change on decade timescales with global announcements. Everything your business invents (slugs, usernames, emails) fails the test.

```sql
-- GOOD: the rare justified natural — small, fixed, externally standardized.
-- (Even here many teams still surrogate; the point is the bar, not the verdict.)
CREATE TABLE currencies (
  code CHAR(3) PRIMARY KEY,      -- ISO 4217: 'USD', 'EUR' — stable for decades
  name TEXT NOT NULL
);

-- GOOD: the everyday default — surrogate PK, natural values UNIQUE beside it.
CREATE TABLE products (
  id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  sku  TEXT UNIQUE NOT NULL,     -- business identifier, changeable, unreferenced
  name TEXT NOT NULL
);
```

```sql
-- BAD: mixed conventions with no record — which style is "ours"? Nobody knows.
CREATE TABLE a_things (slug TEXT PRIMARY KEY, ...);       -- author 1, natural
CREATE TABLE b_things (id BIGINT GENERATED ... , ...);    -- author 2, surrogate
-- joins now cast, merges now special-case, onboarding now apologizes
```

**Common confusion** — *"conventions stifle senior judgment."* Conventions *record* senior judgment so juniors inherit it. The escape hatch is the respect for judgment; the default is the delivery mechanism. Seniors who resist defaults usually object to *bad* defaults — fix the default, don't abolish defaulting.

**Performance note** — uniformity pays in tooling: one key type means one pagination pattern, one repository base, one backup/restore assumption. Mixed key types multiply every generic utility by the number of styles — a maintainability cost that compounds faster than any byte count.

**Mentor note** — teach this leaf as a worked review: present a PR with a natural PK and let the junior discover the change-story is missing. Finding the gap themselves teaches the convention better than any rule document — then point at the checklist so the lesson sticks.
