# 2.2. Identity at scale

## 1. Sequences bottleneck writers (a single counter is a single point of contention)

**Definition** — a sequence (`GENERATED ... AS IDENTITY`) hands out ids from one central counter. Every INSERT takes a brief lock on that counter — invisible at hundreds of writes per second, a serialization point at tens of thousands, and unworkable across independent writers (multiple primaries, edge devices, offline clients) that cannot reach the counter at all.

**What problem it solves (by naming it)** — teams discover this ceiling during their first real traffic spike: write throughput plateaus while CPU sits idle, and the profile points at sequence contention (WAL-amplified on replicas, worse with `CACHE 1` defaults in some setups). Naming the bottleneck *before* it bites is the difference between a planned key migration and a 3 a.m. one. Most applications never reach this ceiling — the point is knowing where it is.

**Modern guidance** — stay on sequences until evidence (not anxiety) says otherwise: single-primary PostgreSQL handles thousands of sequenced inserts per second without distress. When the ceiling approaches, the moves in ascending desperation are: larger sequence `CACHE`, separate sequences per partition/shard, then abandoning central generation (UUIDs below). Never pre-optimize to UUIDs "for scale" — random ids charge their price (next promise) from day one while the sequence ceiling may never arrive.

```sql
-- GOOD: sequences until the workload says otherwise — ordered, narrow, debuggable.
CREATE TABLE events (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  payload    JSONB NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- Scale signal to watch: INSERT throughput plateauing with idle CPU + lock waits
-- on the sequence — measured in pg_stat_activity, not guessed in planning.
```

```sql
-- BAD: abandoning sequences on day one for imagined scale.
-- Every insert below now pays the scatter price (next section) to solve a
-- contention problem the workload does not have and may never have.
CREATE TABLE events_bad (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),  -- "web scale" on day one, 40 users
  payload JSONB NOT NULL
);
```

**Common confusion** — *"sequences have gaps, so they are broken."* Gaps (from rollbacks, caching, failover) are inherent to high-performance sequences — ids are unique and ordered-ish, never gapless. Gapless numbering (invoice sequences, ticket numbers) is a *business* requirement needing its own mechanism (separate counter table with serialization you accept deliberately) — never the primary key's job.

**Performance note** — sequence contention scales with writer count, not table size: 10 writers × 1k inserts/s is fine; 500 connection-pool writers hammering one counter is not. The bottleneck is lock acquisitions per second on a single object — frame it that way when reading profiles, and confirm with measurement before migrating key strategies.

**Mentor note** — this is the canonical premature-scaling lesson: juniors reach for distributed ids because conference talks scared them; seniors ask "how many writes per second, measured?" Teach the question, not the answer — the workload decides, and workloads change (which is why the migration path matters more than the initial choice).

**Cross-links** — sharded/partitioned sequences belong to Domain 05 evolution (forward — unbuilt); measuring contention (pg_stat_activity, EXPLAIN) is Databases usage territory (linked, not repeated).

## 2. UUIDs distribute generation (random ids buy insert parallelism at the price of index locality)

**Definition** — UUIDv4 (`gen_random_uuid()` — built into PostgreSQL since v13, no extension needed) lets *any* writer mint a globally unique id with no coordination: app servers, edge devices, offline clients. Uniqueness without communication is the entire value proposition — everything else about UUIDs is cost.

**What problem it solves** — multi-writer topologies cannot share a counter: active-active regions, offline-first mobile clients syncing later, bulk import pipelines running in parallel. UUIDs (or Snowflake-style ordered ids) remove the coordination round-trip from the write path — generation happens in the client, insertion just lands.

**Modern guidance** — choose by topology: single primary → sequences (2.1's default stands). Multiple independent writers → UUIDv7 (time-ordered, as of the September 2026 era the maturing choice — check your PostgreSQL version's support; v4 random otherwise) for the best balance: distributed generation *with* index locality. UUIDv4 random only where v7 is unavailable — and eyes open about the scatter cost below.

```sql
-- GOOD: client-generated identity for a multi-writer world — no counter round-trip.
CREATE TABLE device_events (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  device_id  TEXT NOT NULL,
  payload    JSONB NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- Any device mints ids offline; sync is INSERTs, never coordination.
```

```sql
-- BAD: UUID primary key AND a sequence-style access pattern expected.
-- Range scans ("latest 100 events") over random UUIDs cannot use the PK order —
-- the model bought distribution it does not use and paid locality it needed.
-- Rule: if you always ORDER BY created_at, the UUID PK is pure cost; use a
-- sequence PK plus created_at index, or UUIDv7 whose order matches time.
```

**Common confusion** — *"UUIDs are unguessable, so they are secure."* Unpredictability is a side effect, not access control — never expose raw UUID PKs as authorization ("knowing the id means access"). And the reverse confusion: UUIDs are *not* more collision-prone than sequences in practice (122 random bits); collisions are a theoretical, not operational, concern.

**Performance note** — the scatter price, concretely: random UUIDs insert at random B-tree positions → every INSERT touches a cold page (more I/O, worse cache hit rates, ~2–4x slower bulk loads than sequential ids in published benchmarks — verify on your hardware), indexes fragment faster, and each key is 16 bytes vs 8 (every referencing FK index doubles its key width). UUIDv7 restores locality (time-ordered → right-edge inserts like sequences) while keeping distributed generation — which is why it is the modern default for new multi-writer designs.

**Mentor note** — draw the two-axis trade on a whiteboard: *generation* (central vs distributed) × *locality* (ordered vs random). Sequences: central + ordered. UUIDv4: distributed + random. UUIDv7: distributed + ordered. Juniors who can place any id scheme on those axes will never choose blindly again.

**Cross-links** — time-ordered id schemes at sharded scale (Snowflake, ULID) resurface in Domain 05 (forward — unbuilt); UUID storage/index mechanics touch Databases 02 (linked, not repeated).

## 3. Idempotency keys are business identity (client-supplied keys turn retries into safe no-ops)

**Definition** — an idempotency key is a client-supplied unique token (per operation, e.g. per checkout attempt) stored in a UNIQUE column. Retries resend the same key; the database's uniqueness guarantee turns the retry into a no-op (or a return of the original result) instead of a duplicate charge, order, or booking.

**What problem it solves** — networks fail after the server commits but before the client hears back — the client cannot distinguish "lost request" from "lost response," so it retries, and without idempotency the retry double-executes. This is the #1 source of duplicate charges in payment systems and duplicate orders in commerce. Application-level dedup checks race; a UNIQUE constraint does not.

**Modern guidance** — model idempotency explicitly for every mutating operation that money, inventory, or external side effects touch: a `TEXT UNIQUE NOT NULL` column (client-generated, UUID or hash), a status column distinguishing *in-progress* from *complete* (so concurrent retries wait rather than duplicate), and response reuse (return the original result on key conflict, don't error). Scope keys per operation type, expire them on a documented schedule.

```sql
-- GOOD: the retry path is a constraint tribunals, not application hope.
CREATE TABLE payments (
  id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  idempotency_key TEXT UNIQUE NOT NULL,   -- client-supplied per checkout attempt
  status          TEXT NOT NULL DEFAULT 'pending'
                         CHECK (status IN ('pending', 'succeeded', 'failed')),
  amount          NUMERIC(12, 2) NOT NULL
);
-- Attempt 1: INSERT ... → pending → charge → UPDATE succeeded.
-- Retry (same key): INSERT conflicts → SELECT existing → return original result.
-- No window exists where two charges can happen — the constraint closes it.
```

```sql
-- BAD: dedup by "checking first" — a race dressed as a safeguard.
-- Two concurrent retries both SELECT (no row yet), both INSERT, both charge.
-- SELECT ... WHERE idempotency_key = $1;  -- nothing found (yet)
-- INSERT ...;                              -- twice, concurrently: duplicates
```

**Common confusion** — *"idempotency keys are the primary key."* No — the surrogate PK still anchors relationships; the idempotency key is a *business* UNIQUE beside it (same pattern as 2.1's slug: enforced, unreferenced, changeable-by-policy). Conflating them couples retry-scoping to row identity — keys expire, PKs must not.

**Performance note** — the UNIQUE index on the key is small, hot, and exactly the lookup the retry path needs — this constraint pays for itself on first use. Expiry (DELETE old keys) needs a `created_at`-ordered cleanup job; size the schedule so the index stays memory-resident.

**Mentor note** — teach retries as a modeling problem, not a networking problem: "the network will duplicate your request — where in the schema does the duplicate die?" Juniors who answer "in the code" haven't finished; the answer is "in a UNIQUE constraint." This reframe generalizes to every at-least-once system (queues, webhooks, sync).

**Cross-links** — the status-machine around payments (pending → succeeded) is application state-machine design, outside this track; exactly-once *processing* semantics (outbox pattern) belong to operations-heavy Domain 06 (forward — unbuilt).
