# 6.1. Boundaries what is covered elsewhere

## 1. Mechanics live in Databases (constraints, indexes, migrations, transactions — linked, not repeated)

**Definition** — this track teaches *decisions*; the [Databases track](<../../../../Databases/README.md>) teaches *mechanisms*. The boundary: if it is about what to decide (which key, which cardinality, which rules), it lives here; if it is about how the engine executes it (constraint syntax variants, index types, migration tooling, isolation levels), it lives there. Neither track repeats the other — links cross the boundary instead.

**What problem it solves** — duplicated coverage rots: two explanations of FK syntax drift apart, and readers trust neither. Single-source-of-truth (PROMPT.md §5) means each concept has exactly one home, and this leaf is the map of where the neighbors live — so readers never wonder "was that covered?" and writers never paste.

**Modern guidance** — the crossing map, by need: writing the DDL → Databases 01–02 (SQL, constraints, migrations, review); choosing/fixing indexes → Databases 02 (index mechanics — this track states *which* columns need indexes, never *how* B-trees work); embedding vs referencing in Mongo → Databases 03 (mechanics; the *decision rule* for documents is Domain 03 of this track, forward — unbuilt); race-safe enforcement → Databases 04 (transactions, locking); operating the result → Databases 05–07 (observability, access, production). Inbound, the Databases track's Domain 07 forwards point here for modeling depth — the tracks reference each other, each owning its side.

- Constraint/index/migration mechanics → [Databases 02](<../../../../Databases/02 Postgres Deep Dive/README.md>)
- Document shape mechanics → [Databases 03](<../../../../Databases/03 MongoDB Deep Dive/README.md>)
- Transactions, locking, race-safe rules → [Databases 05](<../../../../Databases/05 Transactions Consistency and Integrity/README.md>)
- Observability, access, production operation → [Databases 06–07](<../../../../Databases/06 Performance Backup and Operations/README.md>)
- Full track orientation → [Databases track index](<../../../../Databases/README.md>)

**Common confusion** — *"this track assumes SQL — where do I learn it?"* Databases 01–02, in order, then return here. The tracks compose: Databases makes you operational, Database Design makes you deliberate. Either order works; operational-first is the common path.

**Performance note** — none specific — performance mechanics (EXPLAIN, index selection, contention measurement) are Databases 02/04/05 territory by design. This track's performance contribution is upstream: shapes whose worst case can be reasoned about (1.1) cost less to operate than shapes that cannot.

**Mentor note** — when a learner asks a mechanics question here ("how do I create a partial index?"), answer with the link, not the lesson — then note *why* the boundary exists. Teaching learners to navigate the map is part of teaching the subject; mentors who re-teach across boundaries train dependency instead of autonomy.

**Cross-links** — the map above is the complete outbound set for mechanisms; the remaining two promises cover the inbound/future boundaries.

## 2. Normal forms live in Domain 02 (this domain names the questions; the next domain sharpens the answers)

**Definition** — forward boundary: Domain 01 teaches *what to ask* (entities, keys, relationships, constraints); Domain 02 (Normalization Deep Dive — unbuilt) teaches the *formal sharpening* (1NF through 5NF, functional dependencies, denormalization judgment). This domain deliberately stops at working intuition; the next domain makes it rigorous.

**What problem it solves** — premature formalism kills momentum: leading with functional dependencies before learners have modeled anything produces students who can define 3NF and cannot design a schema. The sequencing (intuition → method → formalism → scale) means every normal form lands on experience the reader already has — "oh, *that's* what the order_lines split was."

**Modern guidance** — after this domain, readers can model correctly by habit; Domain 02 gives them the vocabulary to *prove* it and the judgment to *violate* it deliberately (denormalization with priced trade-offs). Do not skip ahead seeking rigor — and do not treat this domain as "the easy version"; working intuition is the harder half, formalism is notation for what you already feel.

- Domain 02 (forward — unbuilt): 1NF→5NF with worked violations, dependency analysis, denormalization decision records.
- Domains 03–07 (forward — unbuilt, full list in [LOG.md](<../../../LOG.md>)): document modeling, relationships at scale, evolution, operations modeling, production mastery.

**Common confusion** — *"I already know normal forms — can I skip Domain 01?"* Knowing the definitions is not the skill; the skill is reaching for the right shape under time pressure with stakeholders watching. If the whiteboard exercise in [5.1](<../5. Interview QA/5.1. Common interview QA modeling foundations.md>) feels effortless, skip freely — otherwise the intuition work here pays first.

**Performance note** — normalization's performance story (join cost vs anomaly cost, deliberate denormalization) belongs to Domain 02 — this leaf states the boundary and stops, per DRY.

**Mentor note** — use the formalism gap diagnostically: juniors who model well but cannot name the normal form need vocabulary (send to 02 when built); juniors who recite forms but model poorly need *this* domain again. The failure direction tells you which medicine — mentors prescribe by direction, not by seniority.

**Cross-links** — Domain 02 forward (unbuilt — textual, no dead link by design); the method this domain taught in [3.1](<../3. First design moves/3.1. From requirements to tables.md>).

## 3. Code mapping lives outside this track (repositories and ORMs consume models — they do not define them)

**Definition** — outward boundary: how code *talks to* the model — repository patterns, ORM mappings, migration frameworks, query builders — is owned elsewhere and never re-taught here. The model is defined in this track; consumed everywhere else. Influence flows one way: modeling decisions constrain code structure, never the reverse.

**What problem it solves** — framework-first modeling ("how will Prisma/TypeORM represent this?") inverts the dependency: the schema starts serving the mapper instead of the business. Teams that model for their ORM inherit its limitations as schema defects (junction tables the ORM cannot express become missing entities; inheritance mapping dictates table shapes). Decide the model here; map it there — friction at the mapping layer is *information* (the model said something the tool dislikes), not a veto.

**Modern guidance** — the consumption map: repository seam and testability → [DesignPatterns 06](<../../../../DesignPatterns/06 Modern Patterns and Anti-Patterns/README.md>) (assumes a sound model underneath); ORM/query-builder usage → the ORM track (planned sibling per root README — textual forward, target unbuilt, no dead link by design); TypeScript data-layer typing → TSTrack/TSNode as applicable. When mapping friction appears, change the mapping first, the model second, and record which you changed and why (ADR habit from [4.1](<../4. Mentor checklist/4.1. Modeling checklist mentors insist on.md>)).

**Common confusion** — *"the ORM needs an id column on every table — including junctions."* Tool defaults are not modeling rules: a surrogate on a pure junction weakens duplicate protection (1.2's composite PK discussion). Configure the mapper around the model (composite keys are mappable in every serious ORM); never remodel around the mapper's defaults.

**Performance note** — N+1 queries, lazy-loading storms, and repository chatter are *consumption* performance — owned by the ORM/Patterns side. But note the direction: most consumption pathologies trace to unmodeled relationships (missing FKs the mapper cannot follow, blobs it cannot query). Good modeling here prevents performance work there — the cheapest query optimization is a well-shaped schema.

**Mentor note** — teach the dependency direction as architecture: "the database outlives every framework." Frameworks turn over every 3–5 years; well-modeled schemas serve for decades. Juniors who internalize this stop asking "how does tool X want it?" and start asking "what does the business need?" — which is the senior transition in one sentence.

**Cross-links** — repository seam in DesignPatterns 06; the checklist habit (record mapping-vs-model decisions) in [4.1](<../4. Mentor checklist/4.1. Modeling checklist mentors insist on.md>).
