# 1.1. What data modeling is and is not

## 1. Model before mechanism (a schema is a decision record, not a migration artifact)

**Definition** — data modeling is the practice of deciding *what exists* in a system, *how those things relate*, and *what must stay true about them* — before choosing indexes, queries, or storage engines. The schema (tables, columns, constraints) is the written record of those decisions.

**What problem it solves** — most production database pain is not slow queries; it is shapes that cannot express the business anymore. A `users` table that grew an `address2`, an `address3`, and a `notes` column holding JSON is not a query problem — it is a modeling problem that no index can fix. Modeling exists so that change arrives as a migration, not a rewrite.

**Modern guidance** — model first on paper (or a whiteboard), in nouns and verbs, with no database open. Open the database only to *record* decisions you already made. As of the September 2026 era this advice is tool-independent: ER diagrams, `dbdiagram.io`-style DSLs, or plain bullet lists all work — the artifact that matters is the decisions, not the drawing.

```sql
-- GOOD: every line below is a decision, not a default.
-- "Customers exist; emails identify them; orders belong to exactly one customer."
CREATE TABLE customers (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email       TEXT UNIQUE NOT NULL,   -- identity decision: email identifies a customer
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE orders (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id),  -- relationship decision
  placed_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

```sql
-- BAD: the shape mirrors a signup form, not the business.
-- Which column identifies the customer? Can one customer have two emails?
-- The schema answers nothing because no decision was made.
CREATE TABLE app_data (
  id     BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  field1 TEXT,
  field2 TEXT,
  extra  TEXT  -- "we'll figure it out later" is not a model
);
```

**Common confusion** — *"modeling" is not "drawing ER diagrams."* Diagrams are documentation of a model, not the model itself. A team with a perfect diagram nobody decided anything from has no model; a team with three bullet points everyone builds against has one.

**Performance note** — modeling mistakes are the most expensive performance problems because they resist local fixes. A missing index costs one migration; a missing entity (orders folded into customers as arrays) costs a redesign plus a data migration under load. Measure-don't-guess starts *before* measurement: choose shapes whose worst case you can reason about.

**Mentor note** — teach juniors to narrate decisions out loud during design reviews: "I chose X because the business rule is Y." Review the *because*, not the SQL. Seniors who skip this produce schemas only they understand — which is the same as schemas nobody understands.

**Cross-links** — the mechanics of expressing these decisions (constraint syntax, migration workflow) live in the [Databases track](<../../../../Databases/README.md>); how constraints fail in production is catalogued there. What follows in this domain turns the three questions into method.

## 2. Usage versus design (running queries is a different skill than choosing shapes)

**Definition** — *usage* is operating a database: writing SQL, creating indexes, tuning queries, running migrations. *Design* is choosing what the database holds and why. One person can do both, but they are different skills with different failure modes: bad usage is slow; bad design is wrong.

**What problem it solves / history** — tutorials (including most SQL courses) teach usage: SELECT, JOIN, GROUP BY. Graduates can query anything and design nothing — so real schemas get designed by accident, one migration at a time, each optimizing for the feature at hand. This track exists because that gap is where production outages are born.

**Modern guidance** — keep the two practices on separate checklists. A design review asks: *what exists, how does it relate, what must stay true?* A usage review asks: *is it indexed, is the plan sane, is the migration safe?* Never let "but the query works" close a design review — working queries against a wrong shape are technical debt with interest.

```sql
-- GOOD: design question first ("can an order exist without a customer?"),
-- answered in the schema — NOT NULL encodes the business rule.
customer_id BIGINT NOT NULL REFERENCES customers (id)

-- BAD: usage patch over a design hole ("just LEFT JOIN, customers might be missing").
-- Every query now defends against a state the business says cannot happen.
-- SELECT ... FROM orders LEFT JOIN customers ...  -- why is this LEFT?
```

**Common confusion** — *"the ORM handles the design."* ORMs map objects to tables; they consume a model, they do not create one. An ORM over an unmodeled schema produces nicely-named access to a mess — repositories included (the repository seam is owned by [DesignPatterns 06](<../../../../DesignPatterns/06 Modern Patterns and Anti-Patterns/README.md>), which assumes the model underneath is sound).

**Performance note** — usage-level tuning has a ceiling set by design. The fastest possible query against a shape that forces full scans of unrelated rows is still slow. When tuning stops helping, the bottleneck moved up a level: stop tuning, start remodeling.

**Mentor note** — in interviews and reviews, separate the two explicitly: "this is a usage concern, parked; the design question is…". Juniors conflate them and argue past seniors. Naming the level ends the confusion.

**Cross-links** — usage mastery (index mechanics, EXPLAIN, transaction behavior) is the Databases track's job — see its overviews; this track links there instead of re-teaching.

## 3. The three questions (what exists, how it relates, what must stay true)

**Definition** — every modeling decision answers three questions: **(1) What exists?** → entities (tables). **(2) How does it relate?** → relationships and cardinality (foreign keys, junction tables). **(3) What must stay true?** → constraints (NOT NULL, UNIQUE, CHECK, FK). If a design discussion is not answering one of these, it is not a design discussion.

**What problem it solves** — design meetings drift: types, indexes, naming, framework features, all at once. The three questions are a forcing function — they sequence the conversation (existence before relationship before rules) and expose what is undecided. "We don't know yet" is a valid answer to question 2; shipping without answering it is not.

**Modern guidance** — run every new feature through the three questions in order, in writing, before any DDL. One sentence each is enough for simple features; the discipline is the point, not the length.

```sql
-- GOOD: the three answers, recorded as DDL for "customers place orders".
-- (1) EXISTS: customers, orders.
-- (2) RELATES: an order belongs to exactly one customer (customer_id + FK).
-- (3) STAYS TRUE: email identifies a customer (UNIQUE); every order has a customer (NOT NULL + FK).
CREATE TABLE customers (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email       TEXT UNIQUE NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE orders (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id),
  placed_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

```sql
-- BAD: question 3 unanswered — nothing must stay true, so nothing does.
CREATE TABLE orders (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT,            -- nullable: orphan orders are now possible
  customer_email TEXT            -- duplicated: which source is true?
  -- no FK, no UNIQUE, no NOT NULL: the schema permits every inconsistency
);
```

**Common confusion** — *question 3 is "validation," so it belongs in the application.* Application validation and database constraints answer different questions: validation guides users toward correct input; constraints guarantee the data stays correct when validation is bypassed, buggy, or raced. Defense in depth, not duplication — constraint mechanics live in Databases 02, which this leaf does not repeat.

**Performance note** — question-3 answers are free performance: UNIQUE and FK constraints create the indexes the queries will need anyway, and NOT NULL lets the planner reason more tightly. Constraints pay rent twice — correctness and speed.

**Mentor note** — make "which of the three questions are we answering?" the house phrase of design reviews. Juniors learn to structure thought; seniors stop re-litigating settled questions; the log of answers becomes onboarding documentation for free.
