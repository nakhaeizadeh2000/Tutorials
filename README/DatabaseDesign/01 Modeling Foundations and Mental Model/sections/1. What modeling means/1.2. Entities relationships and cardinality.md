# 1.2. Entities relationships and cardinality

## 1. Entities carry identity (if two rows can be confused, the entity is underspecified)

**Definition** — an entity is a distinct thing the business tracks (customer, order, course) that deserves its own table *because it has its own identity and lifecycle*. The test is confusion: if two rows could describe the same real thing and nobody could tell, the entity is underspecified — something that needs identifying has been folded into something else.

**What problem it solves** — the classic junior schema stores the world in two giant tables (`users` with 40 columns, `data` with the rest) because "we might need it." Queries then distinguish entities by convention (`WHERE type = 'order'`), and every convention is a bug waiting for a new hire who never learned it. Explicit entities make the database state what the business means.

**Modern guidance** — one entity, one table, one primary key — decided by lifecycle, not by size. Two litmus tests: (a) *independent lifecycle* — can an order exist, change, and be deleted on its own schedule? Then it is an entity, not a column. (b) *independent identity* — does the business point at it and say "that one"? Then it needs a key of its own.

```sql
-- GOOD: order items are entities — they have identity (line 3 of order 42)
-- and lifecycle (added, refunded individually).
CREATE TABLE order_items (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id   BIGINT NOT NULL REFERENCES orders (id),
  sku        TEXT NOT NULL,
  quantity   INT NOT NULL CHECK (quantity > 0),
  unit_price NUMERIC(12, 2) NOT NULL
);
```

```sql
-- BAD: items folded into the order as a text blob — no identity, no lifecycle,
-- no constraints, no queries ("find all orders containing sku X" is now string surgery).
CREATE TABLE orders_bad (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id),
  items      TEXT NOT NULL  -- "sku:qty,sku:qty,..." — the database cannot see inside
);
```

**Common confusion** — *"small things don't deserve tables."* Table-worthiness is not about size; a two-column junction table (below) is smaller than most columns and more important than most tables. The question is never "how big" — it is "does it have identity and rules of its own."

**Performance note** — folded entities (arrays, blobs, CSV columns) defeat the planner: no statistics inside the blob, no index into it, every query a full scan plus parsing. Splitting entities out is routinely a 10–100x query improvement — not from tuning, from letting the database see the data.

**Mentor note** — when a junior proposes a blob/array column, ask "what will we need to find *inside* this in a year?" Juniors optimize for write-convenience (one INSERT); seniors optimize for read-reality (a thousand future queries). The question teaches lifecycle thinking in one sentence.

## 2. Relationships carry rules (one-to-many is a constraint choice, not a drawing convention)

**Definition** — a relationship is a business rule about how entities connect, recorded as constraints: a foreign key says "this row must point at a real row there"; NOT NULL says "the connection is mandatory"; UNIQUE on the FK says "at most one here points there" (one-to-one). The diagram line means nothing — the constraints mean everything.

**What problem it solves** — ER diagrams routinely show relationships the schema never enforces: the drawing says "orders belong to customers" while the schema has a nullable `customer_id` with no FK. Then orphan rows accumulate, every query grows defensive `WHERE customer_id IS NOT NULL` clauses, and "the diagram lied" becomes tribal knowledge. Enforced relationships keep the drawing and the data identical.

**Modern guidance** — for every relationship, write the rule in one sentence, then translate it to constraints mechanically: *mandatory* → NOT NULL; *must reference a real row* → FOREIGN KEY; *at most one* → UNIQUE; *many-to-many* → junction table with a composite key (below). If a sentence cannot be written, the relationship is unmodeled — go ask the business.

```sql
-- GOOD: "a student enrolls in many courses; a course has many students;
-- the same student cannot enroll twice" — every clause is a constraint.
CREATE TABLE students (id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE courses  (id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, title TEXT NOT NULL);

CREATE TABLE enrollments (
  student_id BIGINT NOT NULL REFERENCES students (id),
  course_id  BIGINT NOT NULL REFERENCES courses (id),
  enrolled_on DATE NOT NULL DEFAULT CURRENT_DATE,
  PRIMARY KEY (student_id, course_id)  -- "cannot enroll twice", enforced by the database
);
```

```sql
-- BAD: the relationship exists only in application code (and in a diagram somewhere).
-- Nothing stops duplicates, orphans, or half-written pairs.
CREATE TABLE enrollments_bad (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  student_id BIGINT,   -- nullable, no FK: may point nowhere
  course_id  BIGINT    -- nullable, no FK: duplicates welcome
);
```

**Common confusion** — *"foreign keys are slow, so real systems skip them."* FK checks cost one indexed lookup on write — measurable in benchmarks, invisible in production next to network and I/O. What FKs buy (no orphans, optimizer knowledge, self-documenting joins) dwarfs the cost. Systems that skip FKs do it for online-schema-change operability at extreme scale — a deliberate trade with compensating application checks, never a default. (Constraint mechanics and their costs are owned by Databases 02 — linked, not repeated.)

**Performance note** — FK columns are join columns: index them (PostgreSQL does not auto-index FKs — a usage fact from Databases 02 worth restating here because it bites modelers). The composite PK on a junction table serves both directions' uniqueness; add a second index on `(course_id, student_id)` when traversing from the other side.

**Mentor note** — teach the sentence-first habit: no FK gets written without its English sentence in the PR description. Reviewers check sentence against constraint — "mandatory" with a nullable column fails review. This single habit eliminates most orphan-row incidents.

## 3. Cardinality is a bet on the future (model the cheaper direction to change)

**Definition** — cardinality (one-to-one, one-to-many, many-to-many) states how many rows *may* connect. Every cardinality choice is a bet: "a user has one profile" bets the business will never need two. Bets are fine — unpriced bets are not. The design skill is choosing the cardinality whose *wrongness is cheapest*.

**What problem it solves / history** — schemas ossify around day-one cardinality: `users.profile_photo_url` (one photo — until galleries), `orders.address` (one address — until split shipments), `employees.manager_id` (one manager — until matrix orgs). Each wrong bet required a migration under load plus backfill plus application surgery. The cost was never the column; it was the bet nobody priced.

**Modern guidance** — when uncertain, model the *more general* cardinality if its cost today is small: a separate `profile_photos` table costs one join and survives galleries; a single column saves one join and dies at the second photo. Concretely: one-to-one today with any chance of one-to-many tomorrow → separate table now (the join is cheap, the migration later is not). Many-to-many that is "really" one-to-many today → junction table only if the business direction is genuinely ambiguous; otherwise YAGNI applies — over-generalizing every relationship is its own disease (join sprawl, unclear ownership).

```sql
-- GOOD: photos modeled one-to-many from the start — the second photo is an INSERT, not a migration.
CREATE TABLE users (id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, name TEXT NOT NULL);

CREATE TABLE profile_photos (
  id      BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users (id),
  url     TEXT NOT NULL,
  position INT NOT NULL DEFAULT 0
);
-- Today's rule ("one photo shown") is a query (ORDER BY position LIMIT 1),
-- not a shape — rules change cheaper than shapes.
```

```sql
-- BAD: the bet ("exactly one photo forever") poured into concrete.
-- The gallery feature now needs: new table + backfill + dual-write + cutover.
ALTER TABLE users ADD COLUMN photo_url TEXT;  -- cheap today, expensive tomorrow
```

**Common confusion** — *"we'll just migrate when we get there."* Migrations under load with live traffic are the most dangerous routine operation in database work (migration safety is Databases 02's territory). Pricing a bet means pricing *that* migration — downtime risk, backfill time at 10x rows, dual-write complexity — against one join today. Usually the join wins.

**Performance note** — generality costs joins; specificity costs migrations. One extra join on an indexed FK is microseconds — price it honestly against the migration you are avoiding. But audit generality yearly: tables created "just in case" that stayed one-to-one for three years are join tax without benefit — collapse them (expand/contract in reverse, owned by Domain 05 forward).

**Mentor note** — teach juniors to write the bet down: "CARDINALITY BET: users→photos is 1-N because galleries are on the roadmap; revisit 2027." Dated, attributed bets turn future arguments ("who decided this?") into scheduled reviews. Seniors who bet silently create mysteries; mentors create records.
