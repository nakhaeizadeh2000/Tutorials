# 2.1. Junction tables at scale

## 1. Index both directions (composite PK serves one traversal — the reverse needs its own)

**Definition** — the rule: every junction table carries two indexes — the composite PRIMARY KEY `(a, b)` serving a→b traversal ("groups of user X"), plus an explicit reverse index `(b, a)` serving b→a ("members of group Y"). The PK's leading column orders one direction; the reverse direction without its index scans (or sorts without help) — at junction tables' characteristic sizes (millions to billions of rows), the missing direction is the slow page, the timed-out report, the incident.

**What problem it solves** — the one-direction junction: `(user_id, group_id)` PK built for "my groups" page, then "group members" admin screen seq-scans 200M membership rows per render (or abuses the PK's second column with a skip-scan the planner may or may not choose). Junction tables are queried both ways by nature (both sides own screens — members list *and* groups list) — single-direction indexing serves half the product. The reverse index costs one B-tree (storage + write maintenance, priced once); the missing one costs per-query scans forever.

**Modern guidance** — create both indexes in the founding migration (same PR as the junction — never "when the admin screen is slow"). Order the PK by the dominant traversal (more "my groups" reads → `(user_id, group_id)` leading user_id; analytics by group → reversed). Covering bonus: INCLUDE frequently-selected junction attributes in the reverse index (`(group_id, user_id) INCLUDE (joined_at, role)` — index-only scans for member lists, PostgreSQL 11+ — as-of-September-2026 standard). Review rule: junction PR without two indexes fails — the reviewer names the unserved direction out loud.

```sql
-- GOOD: both traversals indexed — "my groups" and "group members" are both point queries.
CREATE TABLE memberships (
  user_id   BIGINT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  group_id  BIGINT NOT NULL REFERENCES groups (id) ON DELETE CASCADE,
  joined_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  role      TEXT NOT NULL DEFAULT 'member',
  PRIMARY KEY (user_id, group_id)   -- "groups of user X": leading user_id
);
CREATE INDEX memberships_reverse_idx ON memberships (group_id, user_id)
  INCLUDE (joined_at, role);   -- "members of group Y": leading group_id + covering
-- Both directions: indexed point lookups, no scans, no planner gambling.
```

```sql
-- BAD: PK-only junction — half the product unindexed.
CREATE TABLE memberships_bad (
  user_id  BIGINT NOT NULL REFERENCES users (id),
  group_id BIGINT NOT NULL REFERENCES groups (id),
  PRIMARY KEY (user_id, group_id)   -- "my groups": fast. "group members": 200M-row scan.
  -- The admin screen, the moderation queue, the group analytics export — all scan.
  -- "We'll add it when slow" = adding it during the incident (CONCURRENTLY racing locks).
);
```

**Common confusion** — *"the composite PK's second column is indexed too."* Partially — B-trees serve leading-column predicates efficiently; second-column-only predicates get skip-scans *at the planner's discretion* (helpful sometimes, unreliable at scale, never covering). "Sometimes fast" is not an index strategy — the reverse direction deserves a structure designed for it, not a structure that occasionally helps. Explicit beats incidental, always.

**Performance note** — junction economics at scale: two indexes double index-maintenance per INSERT (still microseconds — B-tree inserts amortized) and roughly double junction storage (keys are narrow BIGINTs — priced once, cheap per row). Against: per-query full/skip scans of hundred-million-row tables (seconds per render, uncacheable at cardinality). The ledger favors two indexes from row one — junctions are the fastest-growing tables in social/grouped domains (rows = users × memberships), so "small now" expires fastest here.

**Mentor note** — teach "name the unserved direction" as the junction review closer: author states both traversals and their indexes before approval. Juniors learn bidirectional thinking (every relationship reads both ways — [Domain 01 §4](<../../../01 Modeling Foundations and Mental Model/sections/4. Mentor checklist/4.1. Modeling checklist mentors insist on.md>)'s both-ways rule, scale edition); seniors catch the PK-ordering choice (dominant direction leads). One question, both lessons, every junction PR.

## 2. Junctions grow attributes (today's enrolled_on becomes tomorrow's status)

**Definition** — the growth law: pure link junctions (two FKs, nothing else) accumulate attributes over time — `enrolled_at`, then `role`, then `status`, then `expires_at`, then `invited_by`. Each attribute describes the *membership*, not either endpoint (role is per user-per-group, not per user). Junctions are entities in chrysalis: born as links, matured into first-class rows with lifecycles, validations, and histories of their own.

**What problem it solves** — the attribute homeless crisis: membership status with nowhere to live gets folded onto users ("status per group... in a JSON column on users" — 1NF violation from [Domain 02](<../../../02 Normalization Deep Dive/sections/1. Dependencies and atomicity/1.2. First normal form atomic values.md>)) or onto groups ("member statuses array" — unbounded growth from [Domain 03](<../../../03 Document Modeling for Scale/sections/2. Embed or reference/2.1. Embed when together.md>)), or spawns a *second* junction shadowing the first (memberships + membership_statuses — dual sources of membership truth, diverging immediately). Attributes belong on the relationship row that already exists — the junction designed with room to grow receives them; the junction designed as "just two ids" resists them until something breaks.

**Modern guidance** — found junctions with a surrogate-friendly posture even when starting pure: composite PK for the link invariant (verified above), plus `created_at`-style audit columns from day one (they're free and always wanted), plus a review question per feature ("does anything describe this membership?"). When attributes arrive: add columns while the junction stays link-shaped (≤3–4 attributes, all membership-scoped); promote to surrogate PK + full entity (its own id, its own lifecycle, its own history table) when attributes gain lifecycles of their own (status transitions need auditing → membership_events; approvals need workflow → membership_requests). Promotion criteria written down, not felt.

```sql
-- GOOD: the junction with room — link invariant plus audit columns, promotion-ready.
CREATE TABLE memberships (
  user_id   BIGINT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  group_id  BIGINT NOT NULL REFERENCES groups (id) ON DELETE CASCADE,
  joined_at TIMESTAMPTZ NOT NULL DEFAULT now(),   -- day-one audit: always wanted
  role      TEXT NOT NULL DEFAULT 'member',       -- first attribute: membership-scoped
  status    TEXT NOT NULL DEFAULT 'active',       -- second: still link-shaped
  PRIMARY KEY (user_id, group_id)
);
-- Promotion trigger (recorded): "status transitions need history → membership_events
-- table + surrogate PK. Until then: link-shaped with attributes, no ceremony."
```

```sql
-- BAD: attributes exiled — the junction stayed "pure" while reality moved on.
CREATE TABLE memberships_bad (
  user_id  BIGINT NOT NULL REFERENCES users (id),
  group_id BIGINT NOT NULL REFERENCES groups (id),
  PRIMARY KEY (user_id, group_id)   -- "just two ids" — then role/status/expiry arrived...
);
-- ...and landed in a JSON blob on users (unqueryable), a parallel statuses table
-- (dual truth), and three application enums disagreeing. Purity preserved; design lost.
```

**Common confusion** — *"junctions with attributes violate normalization."* Attributes depending on the full composite key (role depends on user+group jointly — neither alone determines it) are 2NF-clean by definition ([Domain 02 §2.1](<../../../02 Normalization Deep Dive/sections/2. The core ladder/2.1. Second and third normal form.md>)'s thirty-second question: needs both key parts → stays). Normalization governs *placement*, not *count* — membership-scoped attributes on the membership row are the form's demand, not its violation. "Pure junctions" is aesthetic, not normal.

**Performance note** — attribute growth widens junction rows (storage per row grows — priced once, narrow types stay cheap) and enriches covering indexes (INCLUDE the hot attributes — member lists stay index-only). The performance trap is *promotion done late*: auditing via triggers bolted onto link-shaped junctions (row-version soup) instead of proper event tables. Promote on the recorded trigger, not two years later — late promotion migrates history under load; timely promotion designs it in.

**Mentor note** — teach "junctions are larval entities" (the metaphor sticks): today's link is tomorrow's workflow object. Juniors designing junctions ask "what will this membership need in a year?" — role, status, expiry, invitation, history — and leave room (or promote early for the obviously-growing). The question generalizes: every link table is audited for future entity-hood at creation. Foresight as a review question, not a personality trait.

## 3. Hot pairs skew everything (celebrity memberships unbalance partitions and caches)

**Definition** — junction skew preview (full treatment in [3.1](<../3. Skew and hot relationships/3.1. Hot keys and skew.md>)): a tiny fraction of junction rows cluster on celebrity keys (a million users in one group; one user in ten thousand groups). Skew breaks every average-based assumption — partition balance (one partition holds the celebrity's rows), cache efficiency (celebrity rows evict everything else), and query latency (celebrity traversals scan millions while medians scan dozens). Junctions concentrate skew because they multiply entities: skew in either endpoint compounds in the link table.

**What problem it solves** — the average-tested junction: load tests with uniform memberships pass (p99 fine at 100 rows/traversal), production celebrity groups time out ("group members" for the 2M-member flagship — full traversal per render, cache poisoned per fetch, replicas lagging on the celebrity's writes). Skew is invisible to uniform testing and dominant in production — naming it at design time converts "unexpected" incidents into priced mitigations (separate query paths for hot keys, count caches, async member-list builds — [3.1](<../3. Skew and hot relationships/3.1. Hot keys and skew.md>)'s toolkit).

**Modern guidance** — the skew audit per junction (three questions): (a) *can one key collect disproportionate rows?* (open groups, celebrity follows, default-tenants — yes unless capped); (b) *what breaks first?* (member-list renders, count queries, partition balance — name it); (c) *what's the mitigation?* (capped membership, cached counts with tolerance, hot-key query path with pagination/cursors, async exports — priced per [3.1](<../3. Skew and hot relationships/3.1. Hot keys and skew.md>)). Caps where the business allows (max members per group — the cheapest skew control ever invented); caches where reads dominate; separate paths where celebrities are first-class (they usually are — the business *wants* flagships).

```sql
-- GOOD: skew named with mitigation — the celebrity path designed, not discovered.
CREATE TABLE memberships (
  user_id   BIGINT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  group_id  BIGINT NOT NULL REFERENCES groups (id) ON DELETE CASCADE,
  joined_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, group_id)
);
CREATE INDEX memberships_reverse_idx ON memberships (group_id, user_id);
-- SKEW NOTE (recorded): flagship groups may exceed 1M members. Mitigations: member
-- counts served from cached counter (5-min tolerance, dashboard-grade); member lists
-- keyset-paginated (no OFFSET — Databases 02 mechanics); groups capped at 5M by policy
-- (business-approved); celebrity-group reads routed to replica (hot-row isolation).
```

```sql
-- BAD: skew unexamined — uniform assumptions poured into schema and queries.
-- SELECT ... FROM memberships WHERE group_id = $flagship ORDER BY joined_at
-- OFFSET 500000 LIMIT 50;   -- deep OFFSET over millions: seconds per page, growing.
-- SELECT count(*) FROM memberships WHERE group_id = $flagship;  -- per render: full count.
-- No caps, no caches, no pagination discipline — the flagship's success is the query's
-- failure, discovered at the worst moment (launch day, press coverage, traffic spike).
```

**Common confusion** — *"skew is an operations problem, not a modeling problem."* Operations mitigates skew (caches, replicas, rate limits); modeling *creates or prevents* the skew surface (caps prevent, counters cache by design, pagination discipline shapes queries). Unmodeled skew arrives in operations as an emergency ("the flagship launched, everything's slow"); modeled skew arrives as a ticket ("implement the recorded mitigation — trigger reached"). Same work, scheduled vs panicked — the design half decides which.

**Performance note** — skew math briefly: uniform junctions scale linearly (2× rows → 2× cost, predictable); skewed junctions scale by the hottest key (one key's rows dominate partitions, caches, and p99). OFFSET pagination degrades linearly with depth (page N scans N rows — keyset pagination costs constant per page — Databases 02 mechanics). Count queries over hot keys are full traversals per render (cache with tolerance or precompute — [Domain 02 §3.1](<../../../02 Normalization Deep Dive/sections/3. Judgment/3.1. Deliberate denormalization with priced trade-offs.md>)'s ledger applies). Numbers per junction, recorded — skew priced is skew managed.

**Mentor note** — teach "who is the celebrity?" per junction (every social/grouped domain has one — flagship group, default tenant, system user, viral post). Juniors asked to name the celebrity and its row count answer with business knowledge they already have; the follow-up ("what breaks when it 10×s?") writes the mitigation. Celebrity-naming converts domain gossip into capacity planning — the most fun review question in this track, and among the most valuable.
