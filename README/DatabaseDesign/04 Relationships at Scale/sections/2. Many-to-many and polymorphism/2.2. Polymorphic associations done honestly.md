# 2.2. Polymorphic associations done honestly

## 1. Nullable-FK exclusive arcs (one FK per target, CHECK exactly-one-set)

**Definition** — the exclusive arc: a table referencing N possible parents carries N nullable FK columns plus a CHECK enforcing exactly one is set (`(a IS NOT NULL)::int + (b IS NOT NULL)::int = 1` — verified above on PostgreSQL 16.15). Comments on posts *or* images: `post_id`, `image_id`, one set, enforced by the engine. Each arc is a real FK (indexed, joinable, cascade-policy-bearing); the exclusivity is a real CHECK (no zero-parent orphans, no two-parent ambiguity).

**What problem it solves** — polymorphic needs are genuine (comments, likes, attachments, audit events target many entity types) and the dishonest solutions fail structurally: the type-plus-id string pair (next promise's BAD — unconstrainable) or N separate comment tables (query fan-out per "all comments," shared logic duplicated, new target types need new tables + query changes). Exclusive arcs keep one table (unified queries) with enforced integrity (each arc a true FK) — honesty at the price of one CHECK and N columns, scaling to a handful of targets.

**Modern guidance** — use exclusive arcs for 2–4 target types with shared child logic (comments rendered uniformly, likes counted uniformly). Per arc: non-null FK + index ([1.1](<../1. Foreign keys at volume/1.1. Foreign keys that survive traffic.md>) — N arcs need N indexes, priced upfront) + delete policy per target (post deleted → its comments CASCADE; image deleted → hers CASCADE — policies may differ per arc, recorded). The CHECK names all arcs (adding a target alters the CHECK — migration-visible, review-visible, never silent). Beyond ~4 targets the arc table widens uncomfortably → supertype pattern (next promise) or reconsider whether the children are truly uniform.

```sql
-- GOOD: polymorphism with integrity — each arc enforced, exclusivity enforced.
CREATE TABLE comments (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  post_id  BIGINT REFERENCES posts (id) ON DELETE CASCADE,
  image_id BIGINT REFERENCES images (id) ON DELETE CASCADE,
  body     TEXT NOT NULL,
  CONSTRAINT comments_exactly_one_target CHECK (
    (post_id IS NOT NULL)::int + (image_id IS NOT NULL)::int = 1
  )
);
CREATE INDEX comments_post_idx ON comments (post_id);    -- each arc indexed
CREATE INDEX comments_image_idx ON comments (image_id);  -- (partial WHERE NOT NULL optional)
-- "All comments by user X": one table. "Comments on post Y": indexed arc. New target
-- (videos): new column + CHECK rewrite + index — migration-visible by design.
```

```sql
-- BAD: arcs without exclusivity — nullable FKs with no CHECK, ambiguity by default.
CREATE TABLE comments_bad (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  post_id  BIGINT REFERENCES posts (id),
  image_id BIGINT REFERENCES images (id),
  body     TEXT NOT NULL   -- both NULL: orphan comment (on nothing). Both set: on what?
  -- Readers guess (COALESCE chains), writers err (application "ensures" — raced),
  -- analytics double-count (both-set rows appear in two rollups). The arcs exist;
  -- the exclusivity — the entire point — was left as an exercise for every query.
);
```

**Common confusion** — *"CHECK constraints can't express this cleanly."* The boolean-cast sum idiom (`(x IS NOT NULL)::int + ... = 1`) is idiomatic PostgreSQL — readable, enforced per row, cheap (constant-time predicate). Alternatives (trigger functions, exclusion gymnastics) overcomplicate; the CHECK is the clean expression. Portability caveat (honest): the cast idiom is Postgres-flavored — other engines spell it with CASE; the *pattern* (exclusive arc + exactly-one enforcement) ports everywhere, syntax adapts.

**Performance note** — arc economics: N indexes (one per arc — write maintenance × N, priced upfront) + CHECK per write (constant predicate — negligible) against unified queries (one table for "all comments" — no fan-out) and indexed per-arc traversal (each direction served). Sparse arcs waste little (NULLs store cheaply — one null bitmap bit per column); mostly-NULL arc #5 of 6 suggests the target count outgrew the pattern → supertype. Count NULL ratios yearly — sparsity trends trigger the migration before width becomes absurd.

**Mentor note** — teach "count the targets" as the pattern selector: 2–4 uniform targets → exclusive arcs; 5+ or divergent logic → supertype; genuinely open-ended ("comment on anything, including future types") → supertype with registry, never string pairs. Juniors asked "how many targets, growing how fast?" select correctly without memorizing pattern names — target-count is observable, pattern names are vocabulary. Vocabulary follows verdicts.

## 2. Supertype tables for shared identity (one id space, subtype specifics apart)

**Definition** — the supertype (class-table-inheritance done relationally): a parent table holding shared identity (`media: id, kind, owner, created_at`) plus one subtype table per kind (`photos: media_id PK+FK, resolution`; `videos: media_id PK+FK, duration`) whose PK doubles as the FK to the supertype (1-to-1 enforced structurally — a subtype row *is* its supertype row, extended). Shared queries hit the supertype (all media of owner X — one table); kind-specific queries join (photos with resolution — PK join, the cheapest shape); integrity holds throughout (no dangling subtypes — FK; no kind confusion — CHECK on `kind`).

**What problem it solves** — wide exclusive arcs (6+ targets — arc table mostly NULLs, CHECK a paragraph, indexes × N) and divergent child logic (photos need resolution validation, videos need duration workflows — uniform comment-table logic doesn't apply). Supertypes scale target counts without widening (new kind = new table + kind value — no ALTER on shared structures) and honor divergence (per-subtype constraints, policies, lifecycles — each subtype its own design space). The price is joins (supertype + subtype per full read — PK joins, cheap) and insert ceremony (two rows per entity — same transaction, or the subtype dangles... which the FK prevents anyway).

**Modern guidance** — choose supertype when targets exceed ~4, diverge in attributes/behavior, or grow unpredictably ("comment on anything" — open-ended by requirement). Enforce kind-subtype agreement (CHECK on supertype `kind` + application/trigger guarantee that a `kind='photo'` row has exactly one photos row — the one integrity point the structure alone can't close; name its owner explicitly). Read patterns: shared listings from supertype alone (fast, narrow); detail pages join the subtype (PK lookup); cross-subtype analytics from supertype + kind filter (no fan-out). Insert helper (function or repository method — one place creating both rows transactionally — never ad-hoc double INSERTs scattered per caller).

```sql
-- GOOD: shared identity, divergent specifics — queries unite, integrity holds.
CREATE TABLE media (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  kind       TEXT NOT NULL CHECK (kind IN ('photo', 'video')),  -- discriminator, enforced
  owner_id   BIGINT NOT NULL REFERENCES users (id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE photos (
  media_id   BIGINT PRIMARY KEY REFERENCES media (id) ON DELETE CASCADE,
  resolution TEXT NOT NULL   -- PK doubling as FK: 1-to-1 structural, no extra id
);

CREATE TABLE videos (
  media_id   BIGINT PRIMARY KEY REFERENCES media (id) ON DELETE CASCADE,
  duration_s INT NOT NULL CHECK (duration_s > 0)
);
-- "All media of owner X": SELECT FROM media WHERE owner_id — one narrow table.
-- "Photo with resolution": media ⋈ photos on PK — cheapest join shape that exists.
```

```sql
-- BAD: single-table inheritance sprawl — all subtypes, one table, NULLs everywhere.
CREATE TABLE media_bad (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  kind       TEXT NOT NULL,
  resolution TEXT,        -- NULL for videos (meaningless column per row)
  duration_s INT,         -- NULL for photos (ditto)
  codec      TEXT,        -- NULL for photos (ditto — third kind widens further)
  artist     TEXT         -- NULL for videos... every kind adds NULLs for all others
  -- Constraints per kind impossible (resolution required IFF kind=photo — CHECK soup);
  -- new kinds ALTER the shared table (migration contention on the hottest table);
  -- rows bloat with inapplicable columns (storage + cache tax per row, forever).
);
```

**Common confusion** — *supertype versus exclusive arc: which is "more normalized"?* Both are dependency-clean when done right (arc exclusivity via CHECK, subtype agreement via kind discipline) — the choice is about *growth shape*, not purity: fixed few targets → arcs (fewer tables, unified children); growing/divergent targets → supertype (new kinds without ALTERs, per-kind design space). "More normalized" is the wrong axis — both satisfy the forms; they differ in evolution cost. Choose by future, not by form.

**Performance note** — supertype join economics: shared listings touch one narrow table (fast — the hot query stays single-table); detail reads add one PK join (microseconds — PK-on-PK, the cheapest join); subtype-specific filters join then filter (or filter the subtype first — planner handles both). Insert ceremony costs two row writes per entity (one transaction — atomicity preserved, the FK guarantees no dangles). Against: single-table sprawl's NULL bloat (storage + cache per row) and ALTER contention (migrations on the shared hot table). Joins priced in microseconds beat ALTERs priced in outages.

**Mentor note** — teach the kind-agreement gap explicitly ("the structure can't close it — who does?"): juniors who can name the unenforced invariant *and its owner* (trigger, repository method, review checklist) design honestly; juniors who believe "FKs handle everything" ship the gap as a bug. Every pattern has an honesty boundary — supertype's is kind agreement. Name boundaries, assign owners, review both.

## 3. Never the type-plus-id string pair (unconstrainable, unjoinable — the anti-pattern)

**Definition** — the dishonest polymorphic shape: `target_type TEXT` + `target_id BIGINT` (or worse, TEXT) with no FK (can't reference N tables), no CHECK reaching across tables, no join the planner can serve (dynamic table per row — queries branch in application code). It stores a *pointer without a contract*: readers resolve by convention (`if type='post' query posts...`), writers insert by hope, and the database — the integrity engine — sees two opaque columns signifying nothing.

**What problem it solves (by naming it)** — this anti-pattern is ubiquitous (Rails' `commentable_type/commentable_id` made it idiomatic; audit/event tables copy it reflexively) precisely because it's *easy to write*: one table, no ALTERs for new targets, application code switches on type. Naming its cost honestly is the intervention: every "flexibility" cited is a constraint declined, and declined constraints bill quarterly. Engineers who've only seen the pattern never price it — this promise is the price tag.

**Modern guidance** — the migration path (for the thousand existing instances): (a) count targets — 2–4 uniform → exclusive arcs (this leaf, first promise); 5+/divergent/open → supertype (second promise); (b) backfill under the new structure (populate arcs/supertype rows from type+id pairs — the pairs parse deterministically *if* history is clean; quarantine unparsable rows visibly, never silently); (c) dual-write during cutover (new writes populate both shapes — expand/contract, Domain 05 forward), then drop the pair columns. Greenfield rule absolute: type+id pairs fail review on sight — the reviewer needn't ask questions, only point at this leaf.

-- GOOD: (either honest shape — arcs for few, supertype for many; arcs shown.)
-- The migration target for every type+id pair in the system. Integrity enforced,

```sql
-- BAD: the string pair — flexibility that defeats the database.
CREATE TABLE comments_bad (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  target_type TEXT NOT NULL,   -- 'post', 'image', 'video', 'typo-squat' (unenforced!)
  target_id   BIGINT NOT NULL, -- references... whichever table target_type names today
  body        TEXT NOT NULL
);
-- No FK possible (N targets, one column) → orphans accumulate silently.
-- No join plannable (table per row) → "comments with their targets" is N+1 in code.
-- Typo in target_type ('posts') → rows pointing nowhere, discovered never (or in audit).
-- New target type → zero migrations (the cited "benefit") and zero integrity (the price).
-- GROUP BY target_type counts strings, not relationships — analytics on vibes.
```

**Common confusion** — *"but Rails/Django do it this way."* Frameworks optimize for getting started (zero-migration polymorphism ships the demo); they don't optimize for year three (orphan sweeps, unjoinable analytics, typo'd types). Framework idioms are starting defaults, not design verdicts — outgrow them deliberately when targets stabilize (usually by v2). "The framework does it" answers how to start, never whether to continue.

**Performance note** — pair-query economics: per-target queries need type-filtered scans (no FK index into a dynamic table — each target's rows found by filtering, not seeking); unified queries ("recent comments with targets") are application N+1 (one query per type present — latency additive per type, failure modes multiplicative). Honest shapes convert both to indexed seeks (arcs) or single-table scans (supertype). The pair's "no migration" savings fund permanent per-query taxes — the worst trade in this leaf, itemized.

**Mentor note** — keep one production anecdote ready (orphan-sweep cron, typo'd type outage, unjoinable audit — every senior has one; borrow if needed): juniors defending pairs ("but flexible!") convert on contact with consequences, never on contact with theory. The anecdote does what the CHECK-vs-string argument cannot — make integrity *feel* expensive to decline. Theory names the price; stories collect it.
