# 4.1. Relationship review checklist mentors insist on

## 1. Every FK earns its index and policy (no bare foreign keys)

**Definition** — the review's first pass over relationships: for each FOREIGN KEY in the PR, the author states its index (name, or the legacy-audit ticket if backfilling) and its delete policy with both lenses (domain correctness + volume safety — [1.1](<../1. Foreign keys at volume/1.1. Foreign keys that survive traffic.md>)). A bare FK (no index, default policy) fails review structurally — the reviewer needn't examine queries, data, or intent; the relationship is unfit for traffic by inspection.

**What problem it solves** — bare-FK drift: constraints merged for correctness ("references work in dev") without traffic fitness (no index — parent writes scan; default policy — deletes surprise). Each bare FK is a scheduled incident with an unknown date — the review converts unknown-date to known-ticket (index added now, policy chosen now) or known-risk (legacy exception with owner and deadline — never silent). Reviews that check data types but skip FK fitness approve schemas that pass tests and fail launches.

**Modern guidance** — the FK review line, per constraint: "FK orders.customer_id → customers(id): index orders_customer_id_idx ✓; policy RESTRICT (history immutable; erasure is ticketed workflow; application pre-checks) ✓; write cost: one lookup per insert (priced) ✓." Self-FKs included (parent_id indexed? roots NULL or sentinel — stated?). Cross-shard FKs flagged (unenforceable — compensating checks named per 1.1's exception, all three conditions documented). Missing line → request changes; the template from [Domain 02 §4.1](<../../../02 Normalization Deep Dive/sections/4. Mentor checklist/4.1. Normalization review checklist mentors insist on.md>) grows one row per FK — dependencies first, relationships second, queries last.

```sql
-- GOOD: the FK review artifact — three relationships, each earning its place.
-- FK orders.customer_id → customers: index ✓ / RESTRICT (history; erasure ticketed) ✓.
-- FK order_lines.order_id → orders: index ✓ / CASCADE (lines meaningless alone;
--   volume: thousands max — single statement safe) ✓.
-- FK employees.manager_id → employees: index ✓ / RESTRICT (reassign before delete;
--   roots NULL by convention, documented) ✓. Verdict: approve relationships.
```

```sql
-- BAD: the review that checked types — FKs present, fitness unexamined.
-- FK orders.customer_id → customers (index? unasked — parent deletes will scan 50M rows).
-- FK lines.order_id → orders (policy? default NO ACTION — order deletes fail at runtime).
-- FK comments.target... (which table? type+id pair — the reviewer never reached 2.2's
-- anti-pattern, having approved the JSON aesthetics two comments ago).
-- Verdict that should have been: request changes — three bare FKs, one dishonest pair.
```

**Common confusion** — *"small tables don't need FK indexes."* Small tables grow (every 50M-row table was once empty — the index absent at growth's inflection point is the incident's precondition), and index cost on small tables is trivial (tiny B-tree, negligible maintenance). "Small now" expires fastest exactly where growth surprises most (junctions, events, logs — the tables nobody watches). No waivers by size — waivers by *measured immutability* only (static seed tables, enumerated in review, revisited never because never changing — the one honest exception).

**Performance note** — FK review is upstream performance work (same argument as every checklist leaf in this track): each index approved removes future scans; each policy approved removes future lock incidents; each write cost priced removes future "FKs are slow" relitigation. Review minutes convert to outage-hours avoided at the track's usual exchange rate — the highest-ROI minutes in schema work, fourth restatement, permanent truth.

**Mentor note** — automate the checkable half (CI query: unindexed FKs fail the build — the audit query from 1.1 as a migration linter; CHECK-less nullable arc pairs flagged), review the judgment half (policies, volumes, exceptions). Juniors learn fastest from instant automation feedback (red build: "FK without index") plus human policy discussion (why RESTRICT here?). Machines check structure; mentors check judgment — split the review accordingly and both halves improve.

## 2. Every junction is traversed both ways (both directions indexed and narrated)

**Definition** — the review's second pass: for each junction table, the author narrates both traversals (a→b and b→a — who reads which, how often) and names both indexes (composite PK direction + reverse). Junctions traversed one way in review get used both ways in production (both sides own screens — always); the unnarrated direction arrives as the slow page, the timed-out export, the incident. Both directions narrated and indexed, or the junction doesn't merge.

**What problem it solves** — single-direction junctions (PK serving "my groups," admin's "group members" scanning — [2.1](<../2. Many-to-many and polymorphism/2.1. Junction tables at scale.md>)'s BAD, merged because review examined one screen). Screens multiply after merge (moderation queues, analytics exports, member search — each a new traversal of the same junction, each unindexed direction a new incident). The both-ways narration forces the author to enumerate *future* traversals ("who else will read this junction?") — junction readers grow monotonically; indexing both directions at birth covers readers not yet conceived.

**Modern guidance** — the junction review lines: direction A (query, frequency, index — "my groups, 500k/day, PK leading user_id ✓"); direction B (query, frequency, index — "group members, 50k/day, reverse (group_id, user_id) INCLUDE role ✓"); growth attributes (today's columns + promotion trigger — "role/status present; membership_events trigger recorded ✓"); skew note (celebrity candidate? mitigation? — "flagship capped 5M, counts cached ✓"). Four lines per junction; missing line → request changes. The reviewer re-asks [Domain 01 §4](<../../../01 Modeling Foundations and Mental Model/sections/4. Mentor checklist/4.1. Modeling checklist mentors insist on.md>)'s reverse sentence at scale ("state the reverse rule *and its index*").

```sql
-- GOOD: the junction review artifact — both ways, growth, skew, all narrated.
-- memberships(user_id, group_id): A "my groups" 500k/day → PK ✓; B "members" 50k/day →
-- reverse INCLUDE(role) ✓; attributes role/status (link-shaped; events trigger set) ✓;
-- skew: flagship capped, counts cached, keyset pages ✓. Verdict: approve junction.
```

```sql
-- BAD: the single-screen review — direction B unasked, growth unexamined, skew unknown.
-- memberships(user_id, group_id): A "my groups" → PK ✓. B: (unasked — admin screen ships
-- next quarter, scans 200M rows on arrival). Attributes: (unasked — role lands in JSON
-- on users). Skew: (unasked — flagship launches at press event, timeouts live on air).
-- The review approved a quarter of a junction; production billed the remaining three.
```

**Common confusion** — *"YAGNI — index the second direction when needed."* Second directions are needed with certainty (both sides own screens — a structural property of many-to-many, not a feature forecast) and cheap at birth (empty-table index builds instantly, no CONCURRENTLY needed, no lock contention). YAGNI governs speculative *features*; bidirectional traversal is *certain* usage — "when needed" means "during the incident." Certainty discounted is risk mispriced; index both at birth.

**Performance note** — birth-indexing economics: empty-table CREATE INDEX is instantaneous (no scans, no locks worth naming); retrofitted indexes need CONCURRENTLY (slower builds, disk I/O under load, replication lag monitoring — Databases 02 mechanics). The same index costs seconds at birth, hours under traffic. "Later" multiplies cost by orders of magnitude while the unindexed direction bills per query meanwhile — birth-indexing is the rare decision that's cheaper *and* safer *and* faster. No trade-off; just do it.

**Mentor note** — teach "junctions are read twice" as reflex (same family as "every FK earns its index"): juniors internalizing bidirectional traversal design symmetric junctions by habit — PK ordered by dominant direction, reverse covering the other, both narrated without prompting. Review praise for volunteered direction-B narration ("great — you covered admin reads preemptively") reinforces faster than any mandate. Praise symmetry; symmetry compounds.

## 3. Every hot relationship is named (skew identified, mitigation priced, revisit dated)

**Definition** — the review's closing act: every relationship with skew potential arrives with its celebrity named, ordered failures listed, mitigations priced with triggers, and revisit dated — [3.1](<../3. Skew and hot relationships/3.1. Hot keys and skew.md>)'s audit as a merge requirement. Unnamed hot relationships (junctions without celebrity analysis, counters without contention notes, hierarchies without depth bounds) don't merge — "no celebrities" is itself a claim requiring the business answer ("largest group asked: 200 members, capped — no skew surface"), never a default assumption.

**What problem it solves** — hope-shaped merges (uniform load tests passing, celebrities unasked, mitigations unplanned — the launch-spike incident scheduled by optimism). Named skew converts optimism to schedule: caps enforced before flagships (not after timeouts), counters split before serialization (not after lock pileups), keysets adopted before OFFSET collapse (not after deep-page complaints). The review is the last calm moment before production — calm moments are for pre-commitments; war rooms are for executing them.

**Modern guidance** — the skew review lines per hot candidate: celebrity named with counts ("flagship: 2M members, +10k/day"); breaks-first ordered ("counts → lists → partitions"); mitigations with triggers ("cached counts, 5-min; keyset pages; replica routing at CPU-skew>30%"); revisit dated ("2027-09 or 5M members — calendar invite, not intention"). Plus the negative claim where applicable ("no skew surface: groups capped at 50 by business rule — asked 2026-09, recorded"). Register alongside denormalization blessings ([Domain 02 §4.1](<../../../02 Normalization Deep Dive/sections/4. Mentor checklist/4.1. Normalization review checklist mentors insist on.md>)) — one blessings register for all priced deviations, relational and document alike.

```sql
-- GOOD: the skew review artifact — named, ordered, triggered, dated.
-- memberships skew: flagship 2M/+10k/day; breaks-first counts→lists→partitions;
-- mitigations cached-counts/keysets/replica-rule with triggers; revisit 2027-09.
-- like_counts: single-row (rate 100/day — no split; trigger: lock waits >0 → shard).
-- Verdict: skew budgeted — approve with register entry ADR-041.
```

```sql
-- BAD: the hope-shaped merge — skew unasked, mitigations absent, dates none.
-- memberships: (celebrity? unasked). like_counts: single row ("fine for now" —
-- now ending at virality). Pagination: OFFSET ("we'll fix if slow" — slow arriving
-- as timeouts, fix as hotfix). The merge ships three unpriced bets with no ledger;
-- production collects — with interest, during the launch, on camera.
```

**Common confusion** — *"skew review is premature optimization."* Optimization without measurement is premature; skew review *is* measurement (celebrity counts from business answers, triggers from capacity math, mitigations from priced options). "Premature" describes unmeasured work — the skew audit measures first (counts, rates, break-order) and mitigates on triggers. Unmeasured hope ships incidents; measured pre-commitment ships launches. The audit is the opposite of premature — it's the earliest mature decision available.

**Performance note** — the register doubles as the scaling runbook (same argument as every blessings register in this track): yearly re-pricing catches celebrities outgrowing mitigations (flagship at 4M — triggers approaching — split counters *before* serialization, not after). Skew budgeted with triggers turns scaling from emergency response into scheduled maintenance — the track's closing argument for every priced structure, restated here for relationships: pre-commit calmly, execute automatically, launch boringly.

**Mentor note** — model skew-naming on your own PRs first (the track's standing lesson, fourth domain running: authority's example teaches, mandates nag). A senior's skew note ("flagship candidate: 2M, mitigations priced, revisit dated — blessing requested") teaches more than any checklist mandate. Praise named skew ("great celebrity analysis") louder than clever queries — teams optimize for praised behavior, and unpriced hope has had enough admirers.
