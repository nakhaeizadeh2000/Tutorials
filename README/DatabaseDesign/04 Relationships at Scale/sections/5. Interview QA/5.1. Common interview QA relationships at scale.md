# 5.1. Common interview QA relationships at scale

## 1. Model followers or friends live (the social-graph whiteboard)

**Definition** — the exercise: *"design follows/friends for X users"* (the interview staple). The graded artifact is scale-aware narration: directed vs undirected stated first (follows: one row per direction, asymmetric; friends: mutuality modeled how — two rows or one with state?), junction shaped with both indexes ([2.1](<../2. Many-to-many and polymorphism/2.1. Junction tables at scale.md>)), celebrity named with mitigation ([3.1](<../3. Skew and hot relationships/3.1. Hot keys and skew.md>)) — all before any query is discussed. Candidates modeling tables pass junior loops; candidates modeling *direction, junctions, and celebrities* pass senior ones.

**What problem it solves** — the undirected muddle (follows modeled symmetric "because friendship" — then blocking, requests, and asymmetric celebrities need re-architecture), the unindexed junction (follower lists scanning — the admin screen of shame, live in the interview), and the celebrity omission (no mention of viral accounts — the interviewer hears hope, not engineering). Social graphs concentrate every relationship-scale decision in one exercise — direction, junctions, skew, fan-out (timelines!) — which is why interviewers love it and candidates should prepare exactly this shape.

**Modern guidance** — the fifteen-minute shape: (1) *direction* (2 min — "follows directed (A→B ≠ B→A); friends = mutual follows + state, or single row with status — pick one, state the queries each serves"); (2) *junction* (5 min — composite PK ordered by dominant traversal, reverse index, attributes with promotion trigger — narrate both directions' screens); (3) *celebrity* (4 min — "viral accounts: follower counts cached, lists keyset-paginated, timelines fan-out-on-write for celebrities vs fan-out-on-read for normals — priced split"); (4) *timelines* (4 min — the fan-out kicker: "celebrity posts push to follower caches (write amplification, bounded by celebrity count); normal posts assemble on read (read cost, bounded by followee count) — hybrid by follower count, trigger recorded"). Direction → junction → celebrity → timeline: the senior order.

```sql
-- GOOD (whiteboard narration, follows — 15 min):
-- "Directed: follows(follower, followee) — asymmetric by nature. Junction: PK
-- (follower, followee) for 'who I follow' + reverse (followee, follower) for
-- 'followers' — both indexed at birth. Celebrity: viral accounts cached counts
-- (tolerance stated), follower lists keyset-paginated. Timelines: hybrid — post
-- fan-out-on-write for authors under 10k followers (bounded amplification),
-- fan-out-on-read above (bounded assembly); trigger recorded, not hoped."
CREATE TABLE follows (
  follower_id BIGINT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  followee_id BIGINT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (follower_id, followee_id),
  CONSTRAINT no_self_follow CHECK (follower_id <> followee_id)
);
CREATE INDEX follows_reverse_idx ON follows (followee_id, follower_id);
```

```sql
-- BAD (whiteboard): the undirected assumption — symmetric tables, silent celebrities.
CREATE TABLE friendships_bad (
  user_a BIGINT NOT NULL REFERENCES users (id),
  user_b BIGINT NOT NULL REFERENCES users (id),
  PRIMARY KEY (user_a, user_b)   -- direction? requests? blocks?all unasked.
  -- No reverse index (follower lists scan). No celebrity plan (viral = incident).
  -- No timeline story (the actual hard problem — unmentioned). Tables drawn; nothing modeled.
);
```

**Common confusion** — *"friends are just mutual follows — same table."* Mutual-follows-as-friends needs the mutuality query per check (two rows exist? — double lookup) and request/block states need somewhere (pending? blocked? — attributes on the junction or a state column — a design decision, not a detail). "Just" hides three decisions (representation, state, transition rules) — interviewers asking "friends" after "follows" probe exactly whether the candidate re-examines direction or coasts on it. Re-examine aloud — the coasting is audible.

**Performance note** — the timeline split is the performance answer interviewers wait for: fan-out-on-write costs O(followers) per post (bounded for normals — hundreds of cache writes, trivial) but explodes for celebrities (millions per post — write storms); fan-out-on-read costs O(followees) per timeline render (bounded for most — hundreds of assembly reads) but punishes power-users following thousands. Hybrid by follower count bounds both — the threshold (10k? 100k?) recorded with re-measure trigger. Numbers with triggers: hired.

**Mentor note** — drill social graphs as the relationship-scale capstone (same monthly-mock prescription as all QA leaves): direction stated in 30 seconds, junction both-ways in 2 minutes, celebrity with mitigation in 2 minutes, timeline hybrid in 3 minutes. Time each phase separately — candidates reliably discover their phase gap ("great junctions, never mention celebrities") and fix it in three rounds. Phase-timed drills beat whole-exercise repeats for diagnosis.

## 2. Hierarchies under questioning (adjacency vs closure vs nested — the trade-off answer)

**Definition** — the follow-up: *"how would you model a category tree / org chart / comment threads?"* The failing answers pick by fashion ("nested sets — elegant") or by single-axis reasoning ("adjacency — simple"). The passing answer runs [1.2](<../1. Foreign keys at volume/1.2. Self-references and hierarchies.md>)'s three questions live (depth bounded? reads hot? moves frequent?) and derives the shape — default adjacency, disqualify with workload, niche shapes by ratio. Derivation narrated, disqualifiers stated, revisit trigger named.

**What problem it solves** — hierarchy questions filter for ratio thinking (the rarest junior skill — most candidates know encodings as vocabulary, few as workload responses). Interviewers vary the workload deliberately ("shallow menu" then "unbounded threads" then "read-only taxonomy") watching whether the answer *changes* — fashion answers don't (nested sets for everything); ratio answers do (adjacency → closure → nested sets across the three scenarios). Adaptivity is the signal; encodings are the props.

**Modern guidance** — the ninety-second shape per scenario: (1) ask the three questions out loud ("depth? read heat? move rate?" — asking is graded; assumptions stated beat assumptions hidden); (2) derive ("bounded + rare moves → adjacency, default stands" / "unbounded + hot reads → closure, triples maintained in-transaction" / "read-only deep → nested sets, batch rebuilt"); (3) price the rejected ("closure's triple maintenance wasted here — moves rare, reads shallow" — rejected options priced, not ignored); (4) trigger ("revisit if threads go unbounded — recorded"). Three scenarios, same procedure, different verdicts — the procedure is the answer, verdicts are its outputs.

```
-- GOOD (spoken, category tree scenario, 90 seconds):
-- "Depth? Bounded — categories max 4 levels by policy. Reads? Moderate — browsed,
-- not per-request hot. Moves? Admin-rare. Verdict: adjacency — parent_id self-FK,
-- indexed, roots NULL by convention. Rejected: closure (triple maintenance for
-- reads that don't need it — wasted writes); nested sets (move rewrites for moves
-- that barely happen — risk without benefit). Trigger: threads-style unbounded
-- growth → closure. The default stands because the workload lets it."
```

```
-- BAD (spoken): the fashionable absolute — encoding first, workload never.
-- "Nested sets — lft/rgt ranges, subtree reads are beautiful range queries."
-- (Depth? Unasked. Moves? Unasked — daily reorgs rewrite half the table, discovered
-- never in the interview, discovered quarterly in production. The elegance answered
-- a question nobody asked; the workload asked three that went unanswered.)
```

**Common confusion** — *"knowing all four encodings is the point."* Vocabulary without selection is trivia — interviewers can read Wikipedia too. The point is *matching*: workload in, shape out, with priced rejections. Candidates reciting four encodings with no selection procedure score below candidates knowing two with a working procedure. Procedures hire; catalogs decorate.

**Performance note** — volunteer move-cost numbers unprompted ("adjacency move: 1 row; nested-sets move: range rewrite — O(affected ranges); closure move: triple maintenance O(subtree)") — move economics decide more hierarchy selections than read latency (reads differ by constant factors; moves differ by complexity classes). Complexity-class answers ("O(1) vs O(subtree) moves") signal expert depth in one sentence — the cheapest expert signal in this interview.

**Mentor note** — drill as scenario triplets (shallow menu / hot threads / frozen taxonomy — same sitting, three verdicts, one procedure): adaptivity trained explicitly beats adaptivity hoped for. Grade verdict-switching ("did the answer change across scenarios?" — switching correct is the pass criterion; consistency across different workloads is the failure mode). Fashion is consistent; engineering adapts — train the adaptation, grade the switching.

## 3. What breaks at ten million rows (ordered failure prediction for relationships)

**Definition** — the closer: *"your schema works — now ten million rows per table. What breaks first?"* The relationship-scale edition: unindexed FKs (parent writes scanning), single-direction junctions (reverse traversals timing out), OFFSET pagination over celebrities (deep pages crawling), single-row counters serializing (viral increments queueing), fan-out joins multiplying (dashboards fictionalizing). Ordered three-deep with triggers — the track's fourth telling of "three deep, then stop" (Domains 01–03 each have theirs; vocabulary per domain, discipline track-wide).

**What problem it solves** — relationship failures at volume are *selective* (flagships time out while medians stay green — "mostly fine" dashboards during incidents) and *structural* (missing indexes, unexamined skew, fan-out queries — not tunable, only remodelable). The 10M question separates engineers who modeled for volume (indexes at birth, celebrities named, fans split) from engineers who modeled for correctness and hoped about volume. Hope is audible in these answers — ordered failures with triggers are its opposite, equally audible.

**Modern guidance** — answer in failure order, three deep: (1) *missing indexes surface* ("unindexed FKs: parent writes start scanning at millions — audit query in CI catches them; junction reverse directions time out — birth-indexed, verified"); (2) *skew activates* ("flagship traversals dominate p99 — cached counts fire, keysets hold, replica routing triggers at CPU-skew"); (3) *fan-out fictions appear* ("dashboards joining lines × events drift from truth as volumes grow — sum-consistency assertions catch them; split queries already in place"). Close with today's one change (usually: run the unindexed-FK audit, or name the unexamined celebrity) — restraint over redesign, same as every 10M answer in this track.

```sql
-- GOOD (narrated 10M on the bookstore+junction schema): ordered, triggered, restrained.
-- "First: FK audit — any bare FKs start scanning at millions; CI lints them, legacy
-- ones get CONCURRENTLY indexes this quarter. Second: membership junctions — flagship
-- traversals dominate p99; cached counts + keysets already recorded, replica trigger
-- set at CPU-skew 30%. Third: reporting fan-out — lines × events dashboards drift;
-- sum-consistency assertions added this sprint. Today's change: run the FK audit
-- (one query, one afternoon) — the cheapest of the three, and the one most likely
-- to find something."
```

```sql
-- BAD: scale theater, relationship edition — topology answers to modeling questions.
-- "We'd shard by... user? Add read replicas? Cache everything in Redis?"
-- (Which FK scans first? Unasked. Which junction skews? Unnamed. Which dashboard
-- fictions? Undetected. Infrastructure answers to structural questions — cost without
-- diagnosis, motion without movement. The unindexed FK doesn't care about your shards.)
```

**Common confusion** — *"ten million rows needs distributed answers."* (Same theater warning, fourth domain running — repetition intentional: the most common senior-loop failure mode deserves its standing rebuttal.) At 10M rows, answers are still modeling: indexes, celebrities, fan-out splits — single-machine PostgreSQL handles 10M rows per table routinely with correct shapes. Distributed answers at 10M signal resume-driven design; structural answers signal production experience. Structure first, topology at 100× — the track's standing ratio.

**Performance note** — every 10M answer needs a *measured trigger* (same as Domains 02–03: "CONCURRENTLY when audit finds bare FKs," "replica routing at CPU-skew 30%," "counter sharding at lock-waits >0") — triggers turn anxiety into runbooks. Relationship triggers deserve the same dashboard as row counts and ceiling proximity: unindexed-FK count (should read zero), celebrity traversal p99 (trending, not spiking), sum-consistency assertions (green). Metrics, not feelings — fourth restatement, permanent value.

**Mentor note** — teach "three deep, then stop" identically across all four domains now (01 relational bets, 02 normalization defects, 03 document ceilings, 04 relationship volume) — the discipline is fully track-level, vocabulary per-domain. Candidates drilled in all four transfer the shape to unseen domains (and to production incidents, where the same ordering under worse pressure saves quarters). Drill until reflex; grade ordering over completeness; promote order-makers.
