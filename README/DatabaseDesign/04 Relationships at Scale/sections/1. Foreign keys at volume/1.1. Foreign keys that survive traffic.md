# 1.1. Foreign keys that survive traffic

## 1. Index every foreign key (unindexed FKs lock whole tables on parent writes)

**Definition** — the rule: every FOREIGN KEY column gets its own index, explicitly, at creation time. PostgreSQL does not auto-index FKs (unlike some databases) — the constraint checks correctness without an index, but every parent-side write (UPDATE/DELETE on the referenced row) must then scan the *entire* child table for orphans-in-waiting, taking restrictive locks while it scans. At ten rows nobody notices; at ten million the parent table freezes per delete.

**What problem it solves** — the classic production freeze: deleting (or updating the PK of) one customer blocks while PostgreSQL seq-scans 50M order rows confirming no reference — holding locks that queue every concurrent order write behind it. The incident reads as "database hung," the cause is a missing 30-second index, and the fix ships during the outage it should have prevented. FK indexes are the cheapest outage insurance in relational modeling — enforcement already paid for the constraint; the index pays for the traffic.

**Modern guidance** — create the FK index in the same migration as the FK (same PR, same review — never "later"). Name it predictably (`orders_customer_id_idx` — greppable in `\di` output and in lock-monitoring queries). Audit legacy tables once: query `pg_constraint` left-joined against `pg_index` for FKs with no covering index — every hit is a scheduled incident; schedule the `CREATE INDEX CONCURRENTLY` (non-blocking build — Databases 02 mechanics) before traffic finds it. Review rule: FK without index fails review, no exceptions, no "small table" waivers (small tables grow).

```sql
-- GOOD: constraint plus index, same migration — correctness and traffic-safety together.
CREATE TABLE orders (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id) ON DELETE RESTRICT,
  placed_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX orders_customer_id_idx ON orders (customer_id);
-- Parent delete: indexed orphan-check (microseconds) + RESTRICT verdict — no scan, no freeze.
```

```sql
-- BAD: the bare FK — correct at review, catastrophic at volume.
CREATE TABLE orders_bad (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id)  -- no index: parent UPDATE/DELETE
  -- seq-scans this whole table under lock. "We'll add it when slow" means adding it
  -- during the incident, with CONCURRENTLY racing the very locks it would prevent.
);
```

**Common confusion** — *"the PK index covers the join, so we're fine."* The PK index serves child→parent lookups (join order lines to their order — fast). The missing index serves parent→child checks (delete this customer — scan all orders — slow) *and* the reverse join direction. Two directions, two index needs; the PK covers one. "Joins are fast" (true, via PK) coexists with "deletes freeze" (true, via missing FK index) — different operations, different structures.

**Performance note** — FK checks cost one indexed lookup per write (microseconds — the price of enforcement, paid gladly); unindexed FK checks cost a sequential scan per parent write (seconds-to-minutes at scale — the price of omission, paid in outages). The index itself costs write-time maintenance (one more B-tree per INSERT — negligible next to the row write) and storage (8 bytes × rows — priced once). Every ledger favors indexing; the only losing move is deferral.

**Mentor note** — teach the audit query, not just the rule: juniors who can *find* unindexed FKs (`pg_constraint` ⨝ `pg_index` gap query — Databases 02 owns the SQL) fix legacy schemas independently; juniors who only memorized "index FKs" write good new tables atop rotten old ones. Run the audit together on the team's schema in week one — the hits found become the quarter's easiest reliability wins and the rule's permanent advertisement.

## 2. Delete policy is a business rule (CASCADE, RESTRICT, and SET NULL narrate the domain)

**Definition** — `ON DELETE` policy states what a row's death means for its dependents: CASCADE (children die with the parent — lines without orders are meaningless), RESTRICT (death blocked while dependents exist — history outlives actors), SET NULL (the connection was optional — the child survives, orphaned by design). Each choice narrates the domain from [Domain 01 §4](<../../../01 Modeling Foundations and Mental Model/sections/4. Mentor checklist/4.1. Modeling checklist mentors insist on.md>); at volume each also narrates the *blast radius* (CASCADE on a ten-year customer touches millions of rows — the operation, not just the rule, needs designing).

**What problem it solves** — default-policy incidents: NO ACTION (the default) answering delete questions at runtime ("why can't I delete this vendor?" — because 2M dependent rows, discovered in production); accidental CASCADE (a cleanup script deleting a parent nobody knew had children — the ORM's `cascade: true` default meeting a production parent); and the volume surprise (RESTRICT blocking a GDPR erasure the business promised — legal commitment vs schema refusal, resolved in a war room). Policies decided at design time are business rules; policies defaulted are runtime surprises with business consequences.

**Modern guidance** — choose per relationship with both lenses: *domain lens* (what should happen — lines CASCADE, orders RESTRICT, optional links SET NULL) and *volume lens* (what *can* happen in one statement — CASCADE over millions of rows needs batching, RESTRICT over hot parents needs pre-checks in application code to fail fast with a good error). Write both in the PR ("lines CASCADE — max thousands per order, single statement safe" / "customers RESTRICT — erasure is a ticketed workflow, application pre-checks first"). Volume lens revisited yearly: today's safe CASCADE is tomorrow's ten-million-row statement.

```sql
-- GOOD: policies narrated in both lenses — domain correctness plus volume safety.
CREATE TABLE order_lines (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id BIGINT NOT NULL REFERENCES orders (id) ON DELETE CASCADE,
  -- domain: lines meaningless without orders. volume: thousands max per order —
  -- single-statement CASCADE safe. Revisit if bulk-order feature lands.
  quantity INT NOT NULL CHECK (quantity > 0)
);

CREATE TABLE orders (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id) ON DELETE RESTRICT,
  -- domain: history immutable — orders outlive account closure. volume: erasure is a
  -- ticketed multi-step workflow (anonymize, archive, then delete) — RESTRICT is the
-- backstop, application pre-checks give the human-readable error first.
  placed_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

```sql
-- BAD: defaults everywhere — the schema abstains, production decides.
CREATE TABLE order_lines_bad (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id BIGINT NOT NULL REFERENCES orders (id)  -- default NO ACTION: deleting an
  -- order with lines fails at runtime (support ticket), and nobody chose that — the
  -- database defaulted, the business never approved, the user meets the error raw.
);
```

**Common confusion** — *"ON DELETE is DBA trivia — the ORM handles cascades."* ORM cascades run in application code (N+1 deletes, race windows, no atomicity across the set); database CASCADE runs in one statement (atomic, but all-or-nothing at volume). Different semantics, different failure modes — and the ORM's cascade *plus* the database default can double-delete or conflict. Choose the layer deliberately (database for integrity-sized sets, application workflows for human-sized processes with approvals), record which, never both silently.

**Performance note** — CASCADE volume is the blast-radius number: rows touched = parent count × children per parent, in one transaction (locks held throughout — long transactions bloat, block vacuum, risk deadlock). Thousands: fine. Millions: batch the purge (application loop with limits + sleeps — Domain 06 operations) or soft-delete + background purge. The policy states intent; the volume decides execution — reviewer checks both, always.

**Mentor note** — teach delete policy through GDPR/retention stories (legal deadlines meeting schema refusals — every company has one): juniors who've traced an erasure request through CASCADE/RESTRICT chains understand policies as business commitments, not SQL options. Keep the team's erasure runbook beside the schema docs — each RESTRICT should link to the workflow that honors it, each CASCADE to the volume note that bounds it.

## 3. FK write cost is priced, not feared (one indexed lookup per write — keep FKs)

**Definition** — the standing verdict on "are foreign keys slow?": each FK costs one indexed PK lookup on the referenced table per write (microseconds, constant) plus a shared lock held briefly. What FKs buy (no orphans ever, optimizer join knowledge, self-documenting schema, free reverse-direction documentation) dwarfs the cost at every scale short of extreme write-sharding — where even then the trade is explicit (drop FKs *with compensating application checks*, never by default).

**What problem it solves / history** — the periodic "drop all FKs for performance" movement (early-2010s NoSQL-adjacent advice, revived per hype cycle): teams strip constraints for benchmark numbers, then pay in orphans (defensive `WHERE x IS NOT NULL` clauses multiplying per query), incident archaeology ("which service wrote the orphan?"), and reconciliation jobs (nightly orphan sweeps — the constraint reimplemented badly, in batch, daily). The benchmark won microseconds per write; production pays engineers per quarter. Priced once, the trade never favors dropping — until genuine sharding arrives, and then it's priced again, not defaulted.

**Modern guidance** — keep every FK that names a real business invariant (which is nearly all of them — undeleted-adjacent designs from Domain 01 name invariants, not conveniences). The narrow exception, all conditions required: (a) cross-shard references the engine cannot enforce (shards hold different tables — FK syntax can't span them); (b) compensating checks named (application validation + async reconciliation job, both owned); (c) online-schema-change operability genuinely blocked (FKs complicate some zero-downtime migration tooling — measured, not rumored). Document all three per dropped FK; re-audit when topology changes (resharding back together can restore enforceability — reclaim it).

```sql
-- GOOD: the invariant enforced where the engine can see it — orphans impossible by construction.
CREATE TABLE order_lines (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id BIGINT NOT NULL REFERENCES orders (id) ON DELETE CASCADE,
  book_id  BIGINT NOT NULL REFERENCES books (id)
);
-- Write cost: two indexed lookups (~microseconds). Benefit ledger: zero orphan rows
-- ever, zero defensive NULL filters, zero reconciliation jobs, optimizer trusts joins.
```

```sql
-- BAD: FKs dropped for benchmark aesthetics — integrity reimplemented in hope.
CREATE TABLE order_lines_bad (
  id       BIGINT PRIMARY KEY,
  order_id BIGINT NOT NULL,   -- "references orders (trust us)"
  book_id  BIGINT NOT NULL    -- "references books (trust us harder)"
);
-- Saved: microseconds per write. Bought: orphan rows from every buggy writer/backfill/
-- race; IS NOT NULL filters in every query; a nightly orphan-sweep job (the FK,
-- reimplemented in cron, eventually consistent, paging someone at 3 a.m.).
```

**Common confusion** — *"our ORM validates references, so FKs duplicate."* ORM validation races (check-then-insert across concurrent writers — both check, both insert, one orphaned when the parent deletes between), misses non-ORM writers (backfills, consoles, future services in other languages), and evaporates on bugs (one missed validation path, permanent orphans). Constraints close windows code leaves open — the idempotency lesson from [Domain 01](<../../../01 Modeling Foundations and Mental Model/sections/2. Identity and keys/2.2. Identity at scale.md>) generalizes: uniqueness closed retry windows; FKs close writer windows. Same principle, same verdict.

**Performance note** — the complete FK price list, honestly stated: per-write indexed lookup (µs) + brief shared lock on the parent row (contention only under concurrent writes to the *same parent* — hot-parent skew, [3.1](<../3. Skew and hot relationships/3.1. Hot keys and skew.md>) prices it) + index storage/maintenance (bytes per row, amortized). Against: orphan incidents (engineer-days each), defensive query clauses (readability + planner noise per query), reconciliation infrastructure (jobs, dashboards, pages). Run the ledger once per schema — it reads the same every time until sharding.

**Mentor note** — end the "FKs are slow" debate permanently with one measurement: `EXPLAIN ANALYZE` on an FK-checked INSERT (lookup visible, microseconds) beside the incident count from the orphan era (or the industry's). Juniors trust numbers over elders; seniors citing numbers instead of authority teach measurement culture alongside the verdict. The debate ends; the habit (price, don't fear) transfers to every "X is slow" claim thereafter.
