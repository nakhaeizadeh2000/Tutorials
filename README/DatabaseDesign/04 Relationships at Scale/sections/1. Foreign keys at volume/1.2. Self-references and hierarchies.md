# 1.2. Self-references and hierarchies

## 1. Adjacency lists for shallow trees (parent_id self-FK — trivial writes, recursive reads)

**Definition** — the adjacency list: each row holds `parent_id` referencing its own table's PK (NULL for roots). Writes are trivial (INSERT with a parent, MOVE with one UPDATE); reads recurse (`WITH RECURSIVE` — verified below on PostgreSQL 16.15). The shape suits shallow, slow-changing trees: org charts, category trees, threaded comments under a depth cap — hierarchies where depth stays single-digit and moves are administrative events, not ticks.

**What problem it solves / history** — hierarchies predate every fancy encoding: the org chart is a parent pointer, and adjacency lists model it with zero ceremony (one column, one self-FK, one index). The failure it avoids is premature encoding — closure tables and nested sets adopted for five-level category trees, tripling write paths for recursion nobody runs. Adjacency is the default every hierarchy must disqualify before complicating: simple writes, honest reads, understood by every hire on day one.

**Modern guidance** — default adjacency when depth is bounded (≤5 by policy or domain — categories, orgs, menus) and moves are rare (admin actions, not user ticks). Guardrails: NOT NULL policy decided (roots: NULL parent vs sentinel root row — pick one, document it; NULL is conventional), the self-FK indexed ([1.1](<1.1. Foreign keys that survive traffic.md>)'s rule applies to self references equally — unindexed parent_id punishes subtree deletes identically), and a depth CHECK or trigger where the bound is load-bearing (threads capped at N levels — enforce, don't hope). Disqualify toward closure when reads recurse per request at depth or frequency that hurts (third promise prices it).

```sql
-- GOOD: the org chart as parent pointers — writes trivial, reads recursive, all honest.
CREATE TABLE employees (
  id        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  manager_id BIGINT REFERENCES employees (id) ON DELETE RESTRICT,  -- NULL = top brass
  name      TEXT NOT NULL
);
CREATE INDEX employees_manager_idx ON employees (manager_id);  -- self-FK, same rule

-- Subtree read: recursion in one query (verified PostgreSQL 16.15).
WITH RECURSIVE reports AS (
  SELECT id, manager_id, name, 1 AS depth FROM employees WHERE id = 1
  UNION ALL
  SELECT e.id, e.manager_id, e.name, r.depth + 1
  FROM employees e JOIN reports r ON e.manager_id = r.id
)
SELECT * FROM reports;
```

```sql
-- BAD: adjacency assumed infinite — deep, hot, recursive reads per request.
-- 50-level comment threads read via 50-iteration recursion on every page view;
-- each level a nested-loop step, p99 linear in depth, frequency 800k/day.
-- Depth unbounded + reads hot = adjacency disqualified (closure or path below).
-- The shape isn't wrong — the workload outgrew the default, unnoticed.
```

**Common confusion** — *"recursive CTEs are slow, so adjacency is slow."* Recursion cost scales with depth × breadth of the traversed subtree, not with table size — shallow subtrees recurse in milliseconds regardless of millions of unrelated rows (the CTE walks relationships, not tables). "CTEs are slow" confuses traversal cost (bounded by subtree) with scan cost (bounded by nothing). Measure subtree reads before blaming recursion — shallow trees never need another shape.

**Performance note** — adjacency write cost is O(1) (one parent pointer); subtree-read cost is O(subtree) per query (each level a join step — indexed parent_id keeps steps cheap); move cost is O(1) (one UPDATE — the spanning advantage over nested sets, whose moves rewrite ranges). The ledger favors adjacency wherever writes/move simplicity outweighs deep-read frequency — i.e., most administrative hierarchies. Price moves explicitly: reparenting a subtree under adjacency is one row; under nested sets it's a range rewrite (third promise).

**Mentor note** — teach "default adjacency, disqualify with workload" (not "choose among four encodings"): juniors presented four options freeze or fashion-pick; juniors given a default plus disqualifiers (depth >5? reads hot? moves frequent?) decide correctly in minutes. Defaults with exit criteria beat catalogs of options — the same default-first pedagogy as surrogate keys ([Domain 01](<../../../01 Modeling Foundations and Mental Model/sections/2. Identity and keys/2.1. Surrogate versus natural keys.md>)) and 3NF ([Domain 02](<../../../02 Normalization Deep Dive/sections/2. The core ladder/2.1. Second and third normal form.md>)).

## 2. Closure tables for deep queries (ancestor/descendant pairs materialized)

**Definition** — the closure table: a companion table storing every (ancestor, descendant, depth) triple — the transitive closure of the parent relation. Subtree reads become single indexed lookups (`WHERE ancestor = X` — no recursion); depth filters are predicates (`depth <= 2`); moves update the affected triples (more writes than adjacency, bounded by subtree size). The shape suits deep or hot-read hierarchies: unbounded threads, permission trees evaluated per request, catalogs browsed by subtree.

**What problem it solves** — recursion-per-request at depth or frequency: 50-level threads read 800k/day (adjacency's O(depth) per read × hot path = latency budget burned on traversal); permission checks walking ancestors per API call (auth latency linear in org depth — the security tax nobody priced). Closure converts traversal into lookup: reads O(matching rows) with zero recursion, at the price of write-time triple maintenance ( fan-out per move, priced below). Reads dominate → materialize the traversal once, read it forever.

**Modern guidance** — adopt closure when subtree/descendant queries are hot (per-request or per-render) or depth is unbounded (threads, nested tasks, referral chains). Maintain triples with triggers or application writes in the same transaction (never eventual — a torn closure lies structurally, worse than slowness). Include self-pairs (ancestor = descendant, depth 0 — simplifies "node plus subtree" queries to one predicate) and index both columns (`(ancestor)`, `(descendant)` — both traversal directions, same rule as [2.1](<../2. Many-to-many and polymorphism/2.1. Junction tables at scale.md>)'s junction indexing). Depth column enables level-capped reads without recursion.

```sql
-- GOOD: traversal materialized — subtree reads are lookups, moves maintain triples.
CREATE TABLE categories (
  id        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  parent_id BIGINT REFERENCES categories (id),
  name      TEXT NOT NULL
);

CREATE TABLE category_closure (
  ancestor   BIGINT NOT NULL REFERENCES categories (id) ON DELETE CASCADE,
  descendant BIGINT NOT NULL REFERENCES categories (id) ON DELETE CASCADE,
  depth      INT NOT NULL CHECK (depth >= 0),
  PRIMARY KEY (ancestor, descendant)
);
CREATE INDEX closure_descendant_idx ON category_closure (descendant);  -- upward traversal

-- Subtree (verified shape on PostgreSQL 16.15): one indexed lookup, zero recursion.
-- SELECT descendant FROM category_closure WHERE ancestor = 1 AND depth <= 3;
-- Ancestors of a node: SELECT ancestor FROM category_closure WHERE descendant = 42;
```

```sql
-- BAD: closure maintained eventually ("a job rebuilds it nightly") — structural lying.
-- Daytime moves invisible to subtree reads (new nodes missing, moved nodes doubled);
-- permission checks against stale closure authorize wrong subtrees (security incident
-- wearing a performance optimization). Torn derived state is worse than slow truth —
-- maintain in-transaction or don't materialize. Eventual closure is eventual correctness.
```

**Common confusion** — *closure tables duplicate the parent_id (denormalized — bad?).* The closure stores *derived* facts (transitive reachability), not duplicated base facts — same category as materialized views ([Domain 02 §3.1](<../../../02 Normalization Deep Dive/sections/3. Judgment/3.1. Deliberate denormalization with priced trade-offs.md>)) and computed rollups ([Domain 03 §3.1](<../../../03 Document Modeling for Scale/sections/3. Patterns and change/3.1. Schema patterns that scale.md>)): maintained copies with rebuild paths (recompute from parent_id anytime), justified by hot reads. Derived-and-maintained is design; duplicated-and-hoped is debt — the maintenance transaction is the difference.

**Performance note** — closure economics: reads O(subtree rows) single-lookup (vs O(depth) recursive steps — wins grow with depth and frequency); writes O(subtree) triple maintenance per move (vs adjacency O(1) — loses on move-heavy workloads). Break-even: read-heavy deep trees favor closure overwhelmingly (1000 reads per move amortizes any triple cost); write-heavy shallow trees keep adjacency. Storage: triples ≈ nodes × avg-depth (deep narrow trees multiply — price per hierarchy, not per table).

**Mentor note** — teach closure as "the join table for trees" (learners knowing junctions from [2.1](<../2. Many-to-many and polymorphism/2.1. Junction tables at scale.md>) grasp ancestor/descendant pairs instantly — same composite-PK shape, same both-directions indexing). Analogies to owned concepts beat fresh definitions: closure isn't a fourth hierarchy encoding to memorize, it's junctions applied to self-reference. One analogy, permanent comprehension.

**Cross-links** — junction indexing twin in [2.1](<../2. Many-to-many and polymorphism/2.1. Junction tables at scale.md>); materialized-copy discipline in [Domain 02 §3.1](<../../../02 Normalization Deep Dive/sections/3. Judgment/3.1. Deliberate denormalization with priced trade-offs.md>).

## 3. Match the shape to the depth (paths, nested sets, and ltree have their niches)

**Definition** — the remaining encodings, each with its honest niche: *path strings* (`/1/4/12/` — prefix queries via LIKE, human-readable, string-length capped); *nested sets* (lft/rgt ranges — subtree reads as range predicates, moves rewrite ranges); *ltree* (PostgreSQL contrib extension, verified 1.2 on dbprobe — path type with operators and GiST indexes, paths as first-class values). None is the default; each wins a specific read/write ratio the first two shapes serve poorly.

**What problem it solves** — encoding debates settled by fashion ("nested sets are elegant" — until the first subtree move rewrites 2M ranges under lock) or by default-sticking (adjacency recursion at 50 levels hot — the disqualified default nobody revisited). The niche map ends both: paths for readable, shallow, rarely-moved trees (config, menus — debuggable in raw rows); nested sets for read-almost-only deep trees (product taxonomies rebuilt nightly — moves are batch events, reads are everything); ltree where Postgres-native path operators earn their extension (label trees, permission paths with `<@` containment queries).

**Modern guidance** — the selection procedure (run once per hierarchy, recorded): (1) depth bounded ≤5 + moves rare → adjacency (default stands); (2) reads hot/recursive or depth unbounded → closure; (3) reads overwhelmingly dominate + moves are batch → nested sets; (4) human-readable paths required + Postgres → ltree/paths. Record the choice with its disqualifiers ("adjacency chosen: depth ≤4 policy, moves admin-only; revisit if threads go unbounded"). Revisit triggers, not revisits — hierarchies outgrow shapes silently otherwise.

```sql
-- GOOD: ltree where paths are queried natively (verified: ltree 1.2 on dbprobe).
CREATE EXTENSION IF NOT EXISTS ltree;

CREATE TABLE topics (
  id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  path LTREE NOT NULL,   -- 'science.physics.quantum' — readable, queryable
  name TEXT NOT NULL
);
CREATE INDEX topics_path_idx ON topics USING GIST (path);
-- Subtree: WHERE path <@ 'science.physics' (containment — GiST-indexed, no recursion).
-- Depth: nlevel(path). Moves: rewrite the moved subtree's paths (priced per move).
```

```sql
-- BAD: nested sets for a move-heavy tree — elegance with a rewrite tax.
-- lft/rgt ranges: subtree reads are beautiful range predicates...
-- ...until reparenting a mid-size subtree rewrites half the table's ranges in one
-- statement (locks, bloat, replica lag — per MOVE, at user-tick frequency).
-- Catalogs rebuilt nightly: perfect fit. Org charts with daily reorgs: scheduled pain.
-- The encoding serves the read ratio it was chosen for — chosen for the wrong ratio here.
```

**Common confusion** — *"more sophisticated encoding means better modeling."* Sophistication serves ratios, not quality: nested sets on a 3-level menu is ceremony (adjacency reads it in one join); adjacency on a 50-level hot thread is negligence (recursion per render). "Best" is ratio-relative — the selection procedure above asks workload questions, never elegance questions. Elegance unpriced is fashion; the niche map prices every option.

**Performance note** — move-cost comparison (the deciding number most teams skip): adjacency O(1), ltree/paths O(subtree), closure O(subtree triples), nested sets O(table-range). Read-cost: adjacency O(depth steps), all others O(subtree lookup). Moves-frequent + reads-rare is adjacency's fortress; moves-never + reads-hot is nested sets'; everything mixed is closure's or ltree's. Count moves per day before choosing — the number nobody measures and everybody needs.

**Mentor note** — teach the niche map as "three questions" (depth bounded? reads hot? moves frequent?) — juniors answering three questions choose correctly without memorizing four encodings. Questions over catalogs, same pedagogy as every selection in this track (keys, forms, patterns). The map fits on an index card; the card belongs in onboarding beside the schema docs.
