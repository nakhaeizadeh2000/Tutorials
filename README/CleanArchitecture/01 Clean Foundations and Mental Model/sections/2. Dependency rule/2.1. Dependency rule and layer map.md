# 2.1. Dependency rule and layer map

## 1. Dependencies point inward (outer knowing inner — inner ignorant — rule enforcing)

**Definition** — the dependency rule (Martin 2017, the one rule breaking which breaks the architecture): source-code dependencies pointing only inward — outer layers knowing inner layers, inner layers ignorant of outer layers (outer knowing inner — adapters importing ports (use cases owning (entities deciding (knowledge flowing inward — power staying central); inner ignorant (entities importing nothing — use cases importing entities-only (frameworks unknown — databases unheard (ignorance keeping — leverage holding); rule enforcing (arrows proving — violations failing (direction owning — coupling declining).

**What problem it solves** — the outward-knowledge trio: *inner importing outer* (entities importing ORM — use cases importing HTTP (vendors owning — policy obeying (direction reversing — leverage inverting (swaps rewriting — upgrades fearing); *abstractions owned outward* (interfaces living in adapters — policy implementing details (tail wagging — dog obeying (inversion missing — DIP violating); *direction hoping* (arrows unreviewed — imports ungrepped (erosion scheduling — big-balling arriving (discipline decaying — rewrites looming). Inward arrows converting hope to enforcement (outer knowing — inner ignoring (ports owned inward — adapters implementing (direction proving — coupling declining); reviewers tracing imports per feature (inward proving → verifiable; outward → returned).

**Modern guidance** — the direction lines per dependency (review-enforced): *outer knowing inner* (adapters importing ports — controllers calling use cases (knowledge flowing inward — power staying central (composition serving — structure funding); *inner ignorant* (entities importing nothing — use cases importing entities-only (frameworks unknown — databases unheard (ignorance keeping — leverage holding (swapability earning — fear declining); *rule enforcing* (arrows proving — violations failing (direction owning — coupling declining (enforcement funding — erosion ending).

```typescript
// GOOD: direction holding — adapter importing the port, policy ignorant of the adapter (compiled + run live).
interface OrderStore { // port owned inward — the use case's file declaring, details obeying
  save(total: number): void;
  total(): number;
}
class PlaceOrder { // inner ignorant — entities-only imports, adapters unheard
  constructor(private readonly store: OrderStore) {}
  execute(total: number): number { this.store.save(total); return this.store.total(); }
}
class MemoryStore implements OrderStore { // outer knowing inner — adapter importing the port
  private sum = 0;
  save(total: number): void { this.sum += total; }
  total(): number { return this.sum; }
}
class LoggingStore implements OrderStore { // second outer — direction holding under swap
  constructor(private readonly inner: OrderStore) {}
  save(total: number): void { this.inner.save(total); }
  total(): number { return this.inner.total(); }
}
const a = new PlaceOrder(new MemoryStore()).execute(10);
const b = new PlaceOrder(new LoggingStore(new MemoryStore())).execute(10);
console.log(a === 10 && b === 10 ? 'direction holds' : 'direction broken');
```

```typescript
// // inside place-order.use-case.ts:
// import { PgStore } from '../adapters/pg-store.adapter'; // inner knowing outer — vendors owning, policy obeying.
// import { Request } from 'express'; // transports owning — tests heavying, swaps rewriting.
// class PlaceOrder { constructor(private readonly store: PgStore) {} } // concrete depending — fakes declining, DIP violating.
// } // Own ports inward: use cases declaring, adapters implementing.)
```

**Common confusion** — *"dependency inversion means no dependencies (isolation absoluting)."* Inversion flipping ownership (policy declaring — details implementing (arrows pointing inward — knowledge flowing centrally (inversion funding — swapability earning); dependencies remaining (use cases calling entities — adapters implementing ports (composition serving — structure funding (depending owning — isolation declining). "No dependencies" describing isolation (imports banning — composition refusing); inversion describing direction (owners flipping — arrows pointing inward). Invert ownership (ports declaring inward — adapters implementing outward); keep depending (composition serving — structure funding).

**Performance note** — direction economics: pointing costing interface ownership (ports declaring — adapters implementing (direction holding — swapability earning); reversed equivalents costing rewrites (vendors dictating — migrations fearing (upgrades breaking — leverage inverting). Point cheaply (imports — inward); reverse never (vendors — rewrites).

**Mentor note** — teach "arrows point inward" (juniors tracing one import arrow per dependency design direction-held code on first hearing; outward imports interrogated ("which port?" — direction demanding per edge). Point one arrow once (outer knowing — inner ignoring tangible (reversal ending — leverage proving permanently). Know outward; ignore inward — directional discipline in three habits, reviewed per dependency.

## 2. Four layers mapped (entities → use cases → adapters → frameworks — each owning one job)

**Definition** — the four concentric layers (innermost first): entities deciding enterprise rules (invariants guarding — logic homing (policy owning — frameworks ignoring); use cases orchestrating application flow (intents owning — ports calling (flow proving — details deferring); interface adapters translating (controllers shaping — presenters formatting (translation owning — deciding declining); frameworks and drivers serving (NestJS wiring — databases persisting (details plugging — policy obeying). Each owning one job (single reason changing — axes separating (ownership proving — ripple declining).

| Layer | Owns | May import | Never imports |
|---|---|---|---|
| Entities | enterprise rules, invariants | nothing (or stdlib tools) | frameworks, ORM, HTTP |
| Use cases | application flow, ports | entities | adapters, frameworks |
| Adapters | translation, persistence | ports, use-case boundaries | framework internals |
| Frameworks | wiring, serving, driving | adapters (via DI) | nothing inward (they are the edge) |

**What problem it solves** — the layer-collapse trio: *jobs mixing* (totals computed in SQL — auth decided in JSX (ownership missing — changes rippling (edits multiplying — reviews guessing (consistency failing — trust eroding); *layers skipping* (controllers querying — entities emailing (shortcuts billing — direction breaking (convenience charging — rewrites scheduling); *names lying* (services deciding nothing — managers managing no one (vocabulary decaying — onboarding guessing (language blurring — design hoping). Mapped layers converting mixing to ownership (each owning one job — imports proving (axes separating — ripples declining); reviewers placing every class in exactly one ring (mapping proving → verifiable; mixing → returned).

**Modern guidance** — the mapping lines per class (review-enforced): *entities deciding* (invariants guarding — logic homing (policy owning — frameworks ignoring (deciding proving — scattering ending); *use cases orchestrating* (intents owning — ports calling (flow proving — details deferring (orchestrating owning — collapsing declining); *adapters translating* (controllers shaping — presenters formatting (translation owning — deciding declining (translating proving — leaking ending); *frameworks serving* (NestJS wiring — databases persisting (details plugging — policy obeying (serving proving — dictating declining).

```typescript
// GOOD: layers mapping — entity → use case → adapter → controller-shape, each owning one job (compiled + run live).
class Order { // LAYER 1 entities — enterprise rules, imports nothing
  constructor(readonly total: number) {
    if (total <= 0) throw new Error('total must be positive');
  }
}
interface OrderStore { // LAYER 2 port — use cases declaring, adapters implementing
  save(total: number): void;
  total(): number;
}
class PlaceOrder { // LAYER 2 use cases — application flow, entities-only imports
  constructor(private readonly store: OrderStore) {}
  execute(total: number): number {
    const order = new Order(total);
    this.store.save(order.total);
    return this.store.total();
  }
}
class MemoryStore implements OrderStore { // LAYER 3 adapters — translation owning, deciding declining
  private sum = 0;
  save(total: number): void { this.sum += total; }
  total(): number { return this.sum; }
}
function ordersController(place: PlaceOrder): string { // LAYER 3 edge — shaping owning, deciding declining
  return JSON.stringify({ total: place.execute(7) });
}
const body = ordersController(new PlaceOrder(new MemoryStore())); // LAYER 4 wiring — composing, never deciding
console.log(body === '{"total":7}' ? 'layers map' : 'layers collapse');
```

**Common confusion** — *"more rings means cleaner (layers multiplying)."* Rings serving direction (arrows pointing inward — knowledge flowing centrally (separation proving — coupling declining (rings funding — direction holding); count following jobs (intents grouping — axes separating (ownership proving — ripple declining (count earning — ceremony declining). "More rings" describing ceremony (files multiplying — comprehension taxing); mapping describing ownership (jobs homing — axes separating). Map jobs (ownership proving — ripple declining); multiply never (ceremony billing — comprehension taxing).

**Performance note** — mapping economics: owning costing one placement decision per class (rings assigning — jobs homing (ownership proving — ripple declining); collapsed equivalents costing ripples (changes multiplying — reviews guessing (consistency failing — trust eroding). Place cheaply (classes — rings); collapse never (mixing — ripples).

**Mentor note** — teach "every class has one ring" (juniors placing one class per ring design honestly-mapped layers on first hearing; ringless classes interrogated ("which layer?" — mapping demanding per class). Map one class once (jobs homing — ownership proving tangible (mixing ending — ripple declining permanently). Own one job; import inward — mapping discipline in three habits, reviewed per class.

## 3. Violations detected mechanically (import graphs proving — lint rules guarding — reviews catching)

**Definition** — mechanical enforcement: the dependency rule checked by tools, not hope (import graphs proving — edges asserting (direction holding — erosion detecting (proving owning — hoping ending); lint rules guarding (boundaries declaring — violations failing (CI gating — merges blocking (guarding proving — decay preventing); reviews catching (arrows tracing — exceptions justifying (humans judging — tools proving (catching funding — discipline holding).

**What problem it solves** — the erosion trio: *rules decaying* (arrows reversing file by file — shortcuts accumulating (discipline fading — big-balling arriving (decay scheduling — rewrites looming); *reviews missing* (humans skimming — imports unexamined (violations landing — direction blurring (hope funding — enforcement absenting); *exceptions sprawling* (one shortcut citing precedent — precedents multiplying (erosion compounding — rules hollowing (precedent owning — discipline ending). Mechanical detection converting decay to gates (graphs proving — lint guarding (CI blocking — erosion detecting); reviewers reading gate output, not hunting imports (detecting proving → verifiable; hoping → returned).

**Modern guidance** — the detection lines per repo (review-enforced): *import graphs proving* (edges listing — ranks comparing (direction asserting — violations naming (proving owning — hoping ending (evidence funding — discipline holding); *lint rules guarding* (boundaries declaring — no-restricted-imports firing (CI gating — merges blocking (guarding proving — decay preventing (automation owning — fatigue declining); *reviews catching* (arrows tracing — exceptions justifying (humans judging — tools proving (catching funding — discipline holding (judgment serving — automation grounding).

```typescript
// GOOD: violations detecting — layer ranks asserting direction, planted breach caught (compiled + run live).
type Edge = [from: string, to: string];
const rank: Record<string, number> = { entities: 0, usecases: 1, adapters: 2, frameworks: 3 }; // inward = lower rank
function violations(edges: Edge[]): Edge[] { // checker owning — direction asserting, hope ending
  return edges.filter(([from, to]) => (rank[from] ?? 9) < (rank[to] ?? 9)); // outward edge = violation
}
const clean: Edge[] = [['adapters', 'usecases'], ['usecases', 'entities'], ['frameworks', 'adapters']];
const dirty: Edge[] = [...clean, ['usecases', 'frameworks']]; // planted breach — shortcut billing, direction breaking
const caught = violations(dirty);
console.log(violations(clean).length === 0 && caught.length === 1 ? 'rule holds' : 'checker broken');
```

```typescript
// BAD: enforcement hoping — no gates, exceptions sprawling (real erosion shape).
// // "just this once" import (shortcuts accumulating — discipline fading — big-balling arriving).
// // No CI gate (violations landing — direction blurring — hope funding).
// // Reviews skimming imports (humans missing — erosion compounding). Gate mechanically; justify exceptions.)
```

**Common confusion** — *"tooling replaces review judgment (gates deciding)."* Tools proving direction (edges asserting — violations naming (evidence funding — discipline holding (proving serving — hoping ending); judgment placing exceptions (shortcuts pricing — contexts weighing (trade-offs owning — honesty funding (judging serving — automation grounding). "Replacing" describing abdication (humans skipping — context ignoring); tooling describing evidence (gates proving — reviewers judging). Prove with tools (graphs asserting — violations naming); judge with humans (exceptions pricing — contexts weighing).

**Performance note** — detection economics: gating costing one lint rule (boundaries declaring — violations failing (CI blocking — decay preventing); uneroded equivalents costing rewrites (shortcuts accumulating — big-balling arriving (decay scheduling — rewrites looming). Gate cheaply (rules — CI); hope never (erosion — rewrites).

**Mentor note** — teach "the gate proves the rule" (juniors running one graph check per commit design erosion-proof repos on first hearing; unexamined imports interrogated ("gate green?" — detection demanding per merge). Detect one violation once (edges asserting — breaches naming tangible (decay ending — direction proving permanently). Graph imports; gate merges — detection discipline in three habits, reviewed per repo.
