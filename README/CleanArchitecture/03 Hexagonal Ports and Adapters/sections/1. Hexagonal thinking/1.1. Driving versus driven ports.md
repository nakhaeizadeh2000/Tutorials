# 1.1. Driving versus driven ports

## 1. Sides differing (driving commanding — driven serving — symmetry holding)

**Definition** — the two sides: driving (primary) ports commanded BY actors (users commanding — CLIs invoking (tests driving — schedulers triggering (commanding owning — flows starting); driven (secondary) ports commanded BY the app (stores persisting — mails sending (clocks timing — queues publishing (serving funding — details plugging); symmetry holding — both sides interfacing, neither concreting (doors bordering — app centering (holding proving — coupling declining).

**What problem it solves** — the one-sided trio: *driving-only thinking* (controllers porting — repositories concreting (vendors owning — policy obeying (half-hexagons building — swaps rewriting (thinking blinding — symmetry breaking); *sides confusing* (stores commanding — use cases serving (arrows reversing — leverage inverting (confusing charging — direction breaking); *needs unowned* (adapters declaring — consumers obeying (tail wagging — dog following (unowned billing — dictating inviting). Differing sides converting half to whole (driving facing actors — driven facing details (ports bordering — app centering); reviewers naming both sides per feature (differing proving → verifiable; one-sided → returned).

**Modern guidance** — the differing lines per feature (review-enforced): *driving commanding* (users commanding — CLIs invoking (tests driving — schedulers triggering (commanding owning — flows starting (actors owning — app serving); *driven serving* (stores persisting — mails sending (clocks timing — queues publishing (serving funding — details plugging (app owning — vendors obeying); *symmetry holding* (doors bordering — app centering (interfaces facing — concrete absenting (holding proving — coupling declining (balance owning — bias ending).

```typescript
// GOOD: sides differing — driving port commanded by actors, driven port commanded by the app (compiled + run live).
interface RegisterMember { // DRIVING port — actors commanding, app offering
  register(name: string): string;
}
interface MemberStore { // DRIVEN port — app commanding, details serving
  save(name: string): void;
  count(): number;
}
class Registry implements RegisterMember { // core deciding — both sides interfacing, neither concreting
  constructor(private readonly store: MemberStore) {}
  register(name: string): string {
    if (name.length === 0) throw new Error('name required');
    this.store.save(name); // driven serving — app commanding, details plugging
    return `member:${name}`;
  }
}
class MemoryStore implements MemberStore {
  private names: string[] = [];
  save(name: string): void { this.names.push(name); }
  count(): number { return this.names.length; }
}
const store = new MemoryStore();
const driving: RegisterMember = new Registry(store); // driving commanding — actors invoking, flows starting
const out = driving.register('ada');
console.log(out === 'member:ada' && store.count() === 1 ? 'sides differ' : 'hexagon halves');
```

```typescript
// BAD: sides halving — controllers porting, repositories concreting (real half-hexagon shape).
// class Registry { constructor(private readonly pg: PgStore) {} } // vendors owning — policy obeying, swaps rewriting.
// // No driving port (actors unmamed — flows unowned — symmetry breaking). Name both sides; interface both.)
```

**Common confusion** — *"driving means controllers (HTTP owning)."* Controllers adapting actors (HTTP shaping — requests translating (transports serving — handlers assuming (adapting funding — commanding declining); driving naming actors (users commanding — CLIs invoking (tests driving — schedulers triggering (naming owning — flows starting). "Controllers" describing adapters (transports shaping — frameworks declining); driving describing sides (actors commanding — ports offering). Adapt actors (adapters translating — frameworks declining); name sides (driving commanding — driven serving).

**Performance note** — differing economics: naming costing two interfaces (driving facing — driven facing (ports bordering — app centering); halved equivalents costing rewrites (vendors owning — swaps rewriting (thinking blinding — symmetry breaking). Name cheaply (ports — sides); halve never (concrete — rewrites).

**Mentor note** — teach "name both sides" (juniors interfacing one driving + one driven port per feature design symmetry-held hexagons on first hearing; concreted sides interrogated ("which port?" — differing demanding per side). Differ one feature once (driving commanding — driven serving tangible (halving ending — symmetry proving permanently). Command driving; serve driven — differing discipline in three habits, reviewed per feature.

## 2. Ports facing (interfaces bordering — app centering — outside plugging)

**Definition** — port facing: boundary interfaces ringing the app, each facing its outside (interfaces bordering — doors stating (app centering — outside plugging (facing proving — leaking declining); app centering — decisions homing (rules guarding — flows composing (centering funding — scattering ending); outside plugging — actors commanding (vendors serving (details deferring — cores ignoring (plugging owning — dictating declining).

**What problem it solves** — the misfaced trio: *adapters owning* (interfaces living outward — consumers obeying (tail wagging — dog following (owning inverting — leverage reversing (misplacing billing — direction breaking); *ports leaking* (shapes traveling — vendors dictating (contracts coupling — swaps rewriting (leaking charging — exposure scheduling); *centers hollowing* (logic drifting — rules scattering (decisions missing — ownership blurring (hollowing costing — trust eroding). Facing ports converting misfacing to centering (consumers owning — doors bordering (app deciding — outside plugging); reviewers tracing each interface to its owning side per port (facing proving → verifiable; misfacing → returned).

**Modern guidance** — the facing lines per port (review-enforced): *interfaces bordering* (doors stating — app centering (outside plugging — leaking declining (bordering proving — scattering ending (facing owning — misfacing refusing); *app centering* (decisions homing — rules guarding (flows composing — cores ignoring (centering funding — hollowing ending (decisions proving — drifting declining); *outside plugging* (actors commanding — vendors serving (details deferring — cores ignoring (plugging owning — dictating declining (swapping earning — fear ending).

```typescript
// GOOD: ports facing — consumer-owned doors ringing the app, outsides plugging (compiled + run live).
interface Greeter { // DRIVING door — app offering, actors commanding
  greet(name: string): string;
}
interface Clock { // DRIVEN door — app needing, details serving
  now(): number;
}
class DayGreeter implements Greeter { // center deciding — doors bordering, outsides plugging
  constructor(private readonly clock: Clock) {}
  greet(name: string): string {
    const hour = new Date(this.clock.now()).getUTCHours();
    return hour < 12 ? `morning:${name}` : `day:${name}`;
  }
}
const fixed: Clock = { now: () => Date.UTC(2026, 0, 1, 8) }; // driven plugging — fake sliding, suites headlessing
const driving: Greeter = new DayGreeter(fixed); // driving plugging — actors commanding, flows starting
console.log(driving.greet('ada') === 'morning:ada' ? 'ports face' : 'doors misface');
```

**Common confusion** — *"facing means public APIs (surfaces exposing)."* APIs exposing endpoints (routes serving — clients calling (surfaces owning — contracts versioning (exposing funding — hiding declining); facing bordering apps (doors stating — outsides plugging (consumers owning — details deferring (facing proving — leaking declining). "APIs" describing surfaces (endpoints exposing — traffic serving); facing describing ownership (consumers owning — doors bordering). Expose APIs (surfaces serving — clients calling); face ports (consumers owning — app centering).

**Performance note** — facing economics: bordering costing owned doors (consumers owning — app centering (outsides plugging — leaking declining); misfaced equivalents costing inversion (adapters owning — cores obeying (tail wagging — leverage reversing). Face cheaply (doors — ports); misface never (adapters — inversion).

**Mentor note** — teach "consumers own their doors" (juniors bordering one port per side design face-correct hexagons on first hearing; adapter-owned interfaces interrogated ("which consumer?" — facing demanding per port). Face one port once (doors bordering — app centering tangible (misfacing ending — ownership proving permanently). Border interfaces; center app — facing discipline in three habits, reviewed per port.

## 3. Cockburn grounding (hexagon naming — symmetry proving — lockstep declining)

**Definition** — Cockburn grounding (Alistair Cockburn, 2005, "Hexagonal Architecture"): the app drawn as a hexagon with symmetric doors left and right, delaying technology decisions (hexagon naming — doors picturing (symmetry showing — vendors deferring (naming funding — bias declining); symmetry proving — driving equaling driven (sides balancing — neither ruling (proving owning — halving declining); lockstep declining — parties unblocking (availability keeping — throughput earning (declining proving — blocking ending).

**What problem it solves** — the vendor-first trio: *frameworks picturing* (diagrams centering vendors — boxes naming products (bias owning — policy whispering (picturing billing — direction breaking); *symmetry unproven* (driving concreting — driven interfacing (halves building — swaps rewriting (unproven charging — balance missing); *decisions earlying* (vendors choosing — migrations fearing (lockstep scheduling — leverage inverting (early costing — options dying). Grounded hexagons converting vendor-first to symmetry (doors picturing — vendors deferring (decisions delaying — options keeping); reviewers drawing sides before naming products per feature (grounding proving → verifiable; vendor-first → returned).

**Modern guidance** — the grounding lines per drawing (review-enforced): *hexagon naming* (doors picturing — vendors deferring (symmetry showing — bias declining (naming funding — vendor-first ending (pictures owning — products waiting); *symmetry proving* (driving equaling — driven balancing (sides interfacing — concrete absenting (proving owning — halving declining (balance funding — bias ending); *lockstep declining* (parties unblocking — availability keeping (throughput earning — blocking ending (declining proving — coordinating refusing).

```typescript
// GOOD: symmetry proving — one core driven by two actors through one driving port (compiled + run live).
interface Adder { // driving door — app offering, actors commanding
  add(a: number, b: number): number;
}
class Sum implements Adder { // center deciding — vendors deferred, options kept
  add(a: number, b: number): number { return a + b; }
}
function cliActor(port: Adder, args: string[]): number { // actor one — CLI commanding, core ignoring
  return port.add(Number(args[0]), Number(args[1]));
}
function testActor(port: Adder): number { // actor two — tests driving, core ignoring
  return port.add(20, 22);
}
const core: Adder = new Sum();
console.log(cliActor(core, ['20', '22']) === 42 && testActor(core) === 42 ? 'symmetry proves' : 'vendors first');
```

**Common confusion** — *"hexagon means six adapters (geometry counting)."* Hexagon picturing symmetry (doors showing — vendors deferring (pictures serving — bias declining (picturing funding — counting refusing); adapters numbering by sides (actors commanding — vendors serving (counts following — geometry ignoring (numbering earning — picturing declining). "Six" describing geometry (sides counting — doors picturing); hexagon describing equality (driving balancing — driven matching). Picture symmetry (doors showing — bias declining); count adapters (sides serving — needs stating).

**Performance note** — grounding economics: picturing costing one drawing (doors showing — vendors deferring (decisions delaying — options keeping); vendor-first equivalents costing lock-in (migrations fearing — leverage inverting (decisions earlying — options dying). Picture cheaply (hexagons — doors); vendor never (products — lock-in).

**Mentor note** — teach "draw sides before products" (juniors picturing one hexagon per feature design vendor-deferred symmetry on first hearing; product-centered diagrams interrogated ("where are the doors?" — grounding demanding per drawing). Ground one hexagon once (symmetry proving — vendors deferring tangible (bias ending — options proving kept permanently). Name doors; defer vendors — grounding discipline in three habits, reviewed per feature.
