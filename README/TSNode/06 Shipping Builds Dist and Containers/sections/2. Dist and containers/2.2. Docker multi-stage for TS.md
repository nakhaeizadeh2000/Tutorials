# 2.2. Docker multi-stage for TS

The TypeScript service image: builder compiling, runtime executing, non-root user, and mapped traces inside a `src/`-less container. Junior read: copy the Dockerfile shape, build, run. Expert read: why each stage carries what it carries, and what the in-container mapped trace proves about the whole pipeline.

## 1) Builder compiles, runtime executes

### 1) **Definition** (the two-stage split)

*Builder*: full toolchain (`node:24-alpine` + `npm install` with devDeps + `tsc -p`) producing `dist/`. *Runtime*: bare platform (`node:24-alpine` + `npm install --omit=dev` + `COPY --from=builder dist/`) executing `node dist/`. Stages share nothing but the artifact directory: toolchain never enters production (no compiler to exploit, no types to bloat), sources never enter production (positions travel in maps — verified below).

### What problem it solves (history)

Single-stage TS images (toolchain + sources + hook in production) combined every shipping anti-pattern: slow cold starts (compile at boot), version drift (container compiling differently than CI checked), bloated attack surface (compiler + test fixtures + dev configs shippable), and hook-in-production incidents (the boundary [01/4.1](<../../../01 Execution Foundations and Mental Model/sections/4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>) drew, violated per deploy). Multi-stage splits the lifecycle where it belongs: compile-time inputs in builder, run-time inputs in runtime, never mixed.

### Modern guidance

As of September 2026: `node:24-alpine` bases (Active LTS, minimal surface — pin minor, renovate deliberately); builder `COPY` order optimized for caching (manifest first for dep-layer hits, sources after, config with sources); runtime copies `dist/` + manifest only (plus production `node_modules` via `--omit=dev`); `.dockerignore` excluding everything the stages don't name (`node_modules`, `dist`, logs — context hygiene). Verify per image (build + run + mapped throw — the trio below, every Dockerfile change).

### Runnable example (good — the Dockerfile, built and run, verified)

```dockerfile
FROM node:24-alpine AS builder
WORKDIR /app
COPY package.json ./
RUN npm install --no-audit --no-fund
COPY tsconfig.build.json ./
COPY src ./src
RUN npx tsc -p tsconfig.build.json

FROM node:24-alpine AS runtime
ENV NODE_ENV=production
WORKDIR /app
COPY package.json ./
RUN npm install --omit=dev --no-audit --no-fund && npm cache clean --force
COPY --from=builder /app/dist ./dist
USER node
CMD ["node", "--enable-source-maps", "dist/main.js"]
```

```bash
docker build -t ship-probe ./ship
# naming to docker.io/library/ship-probe:latest done
docker run --rm ship-probe
# hello ship
docker images ship-probe --format "{{.Size}}"
# 245MB
```

Verified (Docker v29.7.2, daemon local): builder compiled (after the `TS5083`/`TS2580` fixes from [1.1](<../1. Build configs/1.1. The build tsconfig.md>) — self-contained config, `@types/node` present), runtime executes as `USER node` with production env, image 245MB. `CMD` carries `--enable-source-maps` (file-map observability — the artifact twin of hook defaults, per [05/3.1](<../../../05 Debugging Sourcemaps and Profiling TypeScript/sections/3. Production triage/3.1. Triage order for TS services.md>)).

### Common confusion

- **"one stage is simpler"** — one stage is *shorter* (fewer lines) and *worse* on every axis that matters (size, surface, determinism, boot). Simplicity worth optimizing is conceptual (two stages, two jobs — clearer than one stage doing both); line-count simplicity that ships compilers to production is the expensive kind.
- **"COPY . covers everything"** — `COPY .` defeats layer caching (any file change busts every layer below) and ships context filth (credentials-adjacent files, git history, local `dist/`). Explicit `COPY` per stage (manifest → config+sources → artifact) caches maximally and ships minimally — the Dockerfile equivalent of narrow `include`.

### Performance note

Image size prices every deploy (245MB here: pull time, registry storage, extraction CPU — per replica, per rollout). Layer ordering prices rebuilds (manifest-first: dep changes rebuild all, source changes rebuild little — the common case fast). `npm cache clean` and `--omit=dev` each shave tens of MB (verified pattern — measure yours with `docker images` per change, the one-line audit).

### Mentor note

Require `docker build + run + mapped-throw` proof with every Dockerfile PR (the trio above — build green, output correct, trace mapped): image changes verified like code changes (executed, not eyeballed). Mentees ship their first traced container and never fear multi-stage again — the Dockerfile demystifies into two jobs with a contract between them.

## 2) Non-root, production env, pinned base

### 2) **Definition** (the hardening trio)

`USER node` (Alpine's unprivileged user — the process can't rewrite its own image, bind privileged ports, or escalate trivially), `ENV NODE_ENV=production` (dependency behavior switch — dev warnings off, prod optimizations on, conditional dev code paths excluded), pinned base (`node:24-alpine` exact-ish tag — renovate-bot range, not `latest` — reproducible layers, auditable CVEs). Three lines, three attack/correctness classes closed.

### What problem it solves (history)

Root-by-default containers (276 CVEs-turned-incidents industry-wide involved container escape or overwrite paths eased by root) plus `latest`-tag drift (Tuesday's rebuild pulling a new major — behavior changing with zero repo diff) plus ambient `NODE_ENV` (dev-mode servers in production — verbose, slow, leaky). The trio is the industry's settled answer, encoded per-Dockerfile rather than per-cluster (defense at the artifact, not just the orchestrator).

### Modern guidance

Every production Dockerfile: `USER` (non-root — `node` for Node images, dedicated users for custom bases), `NODE_ENV=production` (set in image, overridable per environment — never absent), pinned base minor (`24-alpine` minimum precision; patch-float for CVE fixes via rebuilds, major-bump as deliberate PRs). Lint the trio in CI (hadolint or equivalent — `DL3002` no-root-warning, unpinned-tag rules — automation over memory).

### Runnable example (good — the trio, in place, verified running)

```dockerfile
FROM node:24-alpine AS runtime
ENV NODE_ENV=production
WORKDIR /app
# ... installs, artifact copy ...
USER node
CMD ["node", "--enable-source-maps", "dist/main.js"]
```

```bash
docker run --rm ship-probe
# hello ship   (as uid=1000(node), NODE_ENV=production — verified executing)
```

The verified run above executed under these three lines (non-root user, prod env, pinned `24-alpine`): hardening that costs nothing at runtime (same syscalls, constrained identity) and pays at audit time (every control present, none bolted on later).

### Common confusion

- **"`USER node` breaks file writes"** — non-root breaks *unowned* writes (logs/tmp/cache dirs need ownership set — `chown` in builder or volume mounts at runtime). Owned paths work identically — the breakage teaches correct ownership (writable paths declared, not assumed), which production needed anyway.
- **"pinning blocks security updates"** — pinning *schedules* them (renovate PRs bumping the tag with full CI — updates reviewed, tested, attributable). `latest` doesn't update faster (it updates *opaquely* — new bytes with no diff, no tests, no owner). Pinned + automated beats floating + hoped, on security most of all.

### Performance note

Trio cost at runtime: zero measurable (identity check per syscall is kernel noise; env lookup per access is cached; pinned layers pull identically). Trio value at audit/incident time: bounded blast radius (non-root), deterministic behavior (pinned), correct mode (prod env). Free at runtime, priceless at review — the cheapest hardening in shipping.

### Mentor note

The trio belongs in every Dockerfile review checklist (three checkboxes, thirty seconds): non-root? prod env? pinned base? Mentees internalize container hygiene faster through review repetition than through policy docs — checklists beat charters (enforced per diff, not per quarter).

## 3) Mapped traces inside the image

### 3) **Definition** (positions without sources)

Container stack traces name authored positions (`/app/src/app.ts:6:9`) though `src/` was never copied into the runtime image: positions travel in co-shipped `.js.map` files (`sources: ['../src/app.ts']`), resolved by `--enable-source-maps` at throw time. Source *text* display falls back (no `sourcesContent` embedded here — context snippet shows `dist/` text), but positions — the triage currency — map exactly. Observability without sources on disk: the minimal-image promise kept fully.

### What problem it solves (history)

"Maps need sources beside them" folklore shipped `src/` into production images (defeating minimal-image goals) or dropped maps entirely (blind production — the incident class [05/3.1](<../../../05 Debugging Sourcemaps and Profiling TypeScript/sections/3. Production triage/3.1. Triage order for TS services.md>) exists to prevent). Position-mapping without sources proves the middle path: triage-grade observability (file:line per frame) at zero source-shipping cost.

### Modern guidance

Assert in-container mapping per image build (mapped-throw smoke: `--boom`-style fixture or fault-injection endpoint, positions asserted — the deploy gate from [4.1](<../4. Important points to remember/4.1. Shipping checklist habits mentors insist on.md>)); treat source-context display as nice-to-have (embed `sourcesContent` where text matters — costs bytes per map, pays in triage readability); never ship `src/` for observability alone (positions suffice — verified below; sources serve editors, not incidents).

### Runnable example (good — mapped positions, srcless image, verified)

```bash
docker run --rm ship-probe node --enable-source-maps dist/main.js --boom
# /app/dist/app.js:9
#     throw new Error("dist-boom");
#           ^
# Error: dist-boom
#     at fail (/app/src/app.ts:6:9)
#     at Object.<anonymous> (/app/src/main.ts:4:7)
#     at Module._compile (node:internal/modules/cjs/loader:1929:14)
```

Verified inside the running container: frames name `/app/src/*.ts` positions (authored, exact — 6:9) while the image holds no `src/` directory (only `dist/` + manifest + prod deps). Context snippet falls back to `dist/` text (no `sourcesContent` embedded in these maps — observed, not asserted as default); positions — what triage spends — map fully.

### Common confusion

- **"unreadable without sources"** — positions locate uniquely (file:line → editor/IDE at the exact defect — the 99% triage need); source *text* inline saves one editor jump (the 1% convenience). Conflating the two ships megabytes of sources to save seconds of navigation — price the convenience before paying it.
- **"maps in images leak code"** — maps carry *positions* (+ optionally `sourcesContent` text — opt-in per emit config). Position-only maps leak structure (file names, line counts — internal services: irrelevant; public images: weigh per audience). `sourcesContent` is the knob (on for debuggability, off for exposure) — decide per image, default thoughtfully.

### Performance note

In-image map cost: disk bytes (maps ≈ 30–50% of `js` size here — 1.3MB profile earlier suggests scale awareness; measure per service) + throw-time remap (microseconds per frame — incidents only). No steady-state cost (maps idle until thrown). Ship maps always for services (observability wins); strip for size-obsessed edge artifacts deliberately (documented, measured, rare).

### Mentor note

Demo the srcless mapped trace live (container throw, `.ts` positions, no `src/` aboard — `docker exec ls` proving absence): the disbelief ("but the sources aren't there!") converting to understanding ("positions travel in maps") is the single most effective sourcemap lesson available. Run it per onboarding cohort; watch the mental models update in real time.
