# 2.1. dist layout that deploys

The `dist/` tree as a deployment contract: `rootDir`-shaped mirroring, runtime-only file selection, and `package.json` pointing at the artifact. Junior read: four files, mirrored tree, `node dist/` runs. Expert read: what travels (and what must not), and how the manifest flips the repo's execution contract from sources to artifacts.

## 1) `rootDir` shapes the tree

### 1) **Definition** (the declared tree shape)

`rootDir: src` declares the compilation root: outputs mirror inputs (`src/app.ts` → `dist/app.js`, `src/main.ts` → `dist/main.js`), and any file outside the root fails the build loudly instead of warping the tree. The `dist/` layout is therefore *derived and predictable*: entry at `dist/main.js`, siblings beside it, depth preserved — deploy scripts, Docker `CMD`s, and profilers address stable paths.

### What problem it solves (history)

Undeclared roots produced layout-by-accident (a stray file outside `src/` nested everything under `dist/src/` — deploys addressing `dist/main.js` broke silently; or scattered roots flattened oddly — imports resolving differently in `dist/` than in sources). Declared `rootDir` converts layout from emergent to contractual: the tree shape is a build input, reviewed like one, failing loudly on violation instead of warping quietly.

### Modern guidance

Set `rootDir` in every build config (even single-dir services — the declaration documents intent and guards against future strays); keep one source root per deployable (monorepo packages: one root each — roots follow deployment topology per [1.1](<../1. Build configs/1.1. The build tsconfig.md>) part 2); assert the tree in the gate (inventory listing, exact file set — [1.2](<../1. Build configs/1.2. Emit verification.md>) gate 2).

### Runnable example (good — the mirrored tree, verified)

```bash
find ship/dist -type f | sort
# ship/dist/app.js
# ship/dist/app.js.map
# ship/dist/main.js
# ship/dist/main.js.map
```

Four files, mirrored depth, no `src/` nesting inside `dist/` (the `rootDir` contract holding), no strays. Entry address: `dist/main.js` — stable across builds, addressing what Docker `CMD`, profilers, and smoke tests all point at.

### Common confusion

- **"`rootDir` defaults sanely"** — default is the *common path* of inputs (emergent from whatever `include` catches — a test file in `include` silently re-roots the tree to `dist/src/...`). Emergent layout is the failure mode `rootDir` exists to prevent — declare it, don't inherit it.
- **"nested dist/ is harmless"** — nested trees break every address (Docker `CMD`, `main` field, profiler paths, smoke assertions — all written against the flat contract). One undeclared root poisons every downstream address simultaneously — the blast radius of a "harmless" default.

### Performance note

No runtime dimension (layout is addressing, not execution). The cost axis is deploy reliability (stable addresses → scriptable deploys; warped trees → per-deploy path archaeology). `rootDir` costs one line; warped-tree incidents cost a deploy window each. Addressing certainty is operational performance.

### Mentor note

Show the warped tree once (temporarily add a root-external file, emit, display `dist/src/...`) — the horror demonstrates `rootDir`'s value more efficiently than any explanation. Then restore and declare: lessons involving revenant directories stick (reuse the ghost-file pedagogy from [1.2](<../1. Build configs/1.2. Emit verification.md>) part 3).

## 2) Only runtime files travel

### 2) **Definition** (the artifact file set)

`dist/` carries runtime files: compiled `.js` (executed), co-shipped `.js.map` (observed — [05/3.1](<../../../05 Debugging Sourcemaps and Profiling TypeScript/sections/3. Production triage/3.1. Triage order for TS services.md>) parity), and for libraries `.d.ts` (+ maps). It never carries sources (`.ts` — unneeded at runtime; maps reference them by position), tests, configs, or dev tooling. Each audience priced: services need `js`+`map`; libraries add declarations; nobody needs sources on disk (positions travel in maps — verified in-container in [2.2](<./2.2. Docker multi-stage for TS.md>)).

### What problem it solves (history)

Fat artifacts (whole-repo copies "just in case" — sources, tests, tsconfigs, READMEs in production images) bloated transfers, widened attack surfaces (test fixtures with credentials, dev configs with secrets), and confused triage (which file actually executes? — three candidates per module). Minimal artifacts answer unambiguously: `dist/*.js` executes, `dist/*.js.map` observes, nothing else exists to confuse.

### Modern guidance

Services: `js` + `map` only (assert via inventory gate — exact set, no extras); libraries: add `.d.ts` (+ `declarationMap` — TS 12/3.1 owns the contract); sources: excluded (positions suffice — the in-container proof in [2.2](<./2.2. Docker multi-stage for TS.md>)); secrets/tests/configs: excluded structurally (never rely on "we don't read them" — absent files can't leak). `.dockerignore` + `files` field + gate inventory enforce the set three ways (build context, publish scope, verification).

### Runnable example (good — the minimal set, verified)

```bash
find ship/dist -type f | sort
# ship/dist/app.js       (executes)
# ship/dist/app.js.map   (observes)
# ship/dist/main.js      (entry — executes)
# ship/dist/main.js.map  (observes)
# (.ts: absent — correct. tests: absent — correct. tsconfig: absent — correct.)
```

### Common confusion

- **"ship sources for debuggability"** — positions (in maps) debug; sources on disk add nothing the map lacks (verified: container traces name `/app/src/app.ts:6:9` with no `src/` present). Source *text* display needs `sourcesContent`/resolution — nice, not necessary; positions are necessary, and maps carry them. Ship maps, skip sources.
- **"declarations help service debugging"** — declarations help *type-consumers* (none for services — no importer reads service `.d.ts`). Hovers in production debugging read maps, not declarations. Service `.d.ts` is unread weight with build-time cost — libraries differ (contracts are their product).

### Performance note

Artifact size directly prices transfers (registry push/pull per deploy — megabytes × frequency), attack surface (files present are files exploitable), and cold starts (fewer files, faster layer extraction). Minimal sets are faster, safer, and clearer simultaneously — the rare triple win. Measure image size per change (245MB baseline here — regressions visible, attributable).

### Mentor note

Audit any production image with `find` (or dive/equivalent): every non-`js`/`map` file justifies itself aloud (test fixture? dev config? stray source? — each a finding with a removal). Teams auditing quarterly keep images lean permanently; teams never auditing accumulate archaeology (layers of "just in case" spanning years).

## 3) `package.json` points at the artifact

### 3) **Definition** (the manifest flip)

The manifest declares artifact execution: `main: dist/main.js` (entry address), `scripts.start: node dist/main.js` (or service entry — the production command), `scripts.build` producing it, `files` scoping published scope (libraries), engines declaring the runtime floor. The flip (scripts from `./src/*.ts`-via-hook to `dist/*.js`-via-node) is the textual moment the repo's execution contract changes from sources to artifacts.

### What problem it solves (history)

Manifests pointing at sources (`"main": "src/index.ts"`, start scripts invoking ts-node) shipped repos that *required the toolchain to run* (production installing `typescript`, compiling at boot — slow, flaky, version-sensitive) or *failed outright* (hook absent in prod images — `Unknown file extension` at container start, the most embarrassing deploy failure: the app never ran once). Manifest flip makes artifacts runnable by bare Node — the only runtime production guarantees.

### Modern guidance

`main` names the artifact entry (never sources — consumers import built output); `start` runs `node dist/` (flags: `--enable-source-maps` for file-map observability — the artifact twin of hook defaults); `build` precedes it in every pipeline (`prepublishOnly`/`prepack` for libraries, explicit build jobs for services); `engines` pins the Node floor the artifact targets (24 era: `"node": ">=20"` or tighter — matches the base image, verified compatible). Review manifest diffs touching `main`/`start` as deployment changes (they redirect production execution — the highest-blast-radius lines in the file).

### Runnable example (good — the flipped manifest, verified running)

```jsonc
// ship/package.json — scripts name the artifact contract
{
  "name": "ship-probe",
  "main": "dist/main.js",
  "scripts": {
    "build": "tsc -p tsconfig.build.json",
    "start": "node dist/main.js"
  }
}
```

```bash
node ship/dist/main.js
# hello ship
```

Verified: bare Node (no hook, no flags, no toolchain) executes the artifact — the production guarantee in one command. Contrast S1's hook-absent failure (`Unknown file extension .ts` — the exact incident this flip prevents): artifacts run where hooks were never installed, by construction.

### Common confusion

- **"`main` should point at sources for monorepos"** — workspace *development* resolves sources (project references, loader hooks — dev-time conveniences); published/consumed packages resolve artifacts (`main`/`exports` naming `dist/` — TS 12/3.3 owns the maps). Dev-time source resolution and manifest artifact addresses coexist (different consumers, different fields) — conflating them ships dev conveniences as public contracts.
- **"start scripts need ts-node for maps"** — maps work without the hook (`--enable-source-maps` + co-shipped `.js.map` — verified artifact twin in [1.2](<../1. Build configs/1.2. Emit verification.md>) part 2). Hook-in-production for observability is the most expensive misunderstanding in this domain (full toolchain to reproduce what one flag does).

### Performance note

Bare-Node artifact start: zero compile, deterministic bytes (fastest boot of every option per [01/1.1](<../../../01 Execution Foundations and Mental Model/sections/1. Execution identity and setup/1.1. What ts-node is and is not.md>)'s leaderboard, plus replica-identical). Hook-in-production start: slowest boot + per-machine variance + toolchain image weight. The manifest flip is worth seconds per boot, megabytes per image, and incidents per year — priced thrice, paid once (one `main` line).

### Mentor note

Grep every repo's `start` script in the shipping audit (`ts-node`/`tsx`/`.ts` in `start` = finding with the ladder attached — [01/2.1](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>) numbers end the debate). The audit takes a minute per repo; each violation found prevents a production toolchain incident. Highest-ROI grep in this track.
