# 4.1. Shipping checklist (habits mentors insist on)

The three habits that keep shipping boring: no hook in production (grep-proven), maps with artifacts (gate-proven), images run before they ship (smoke-proven). Junior read: three assertions, all green, then deploy. Expert read: what each assertion excludes, and why checklist gates belong in CI rather than in release-day memory.

## 1) No hook in production

### 1) **Definition** (the boundary grep)

Production `start` scripts invoke bare Node on artifacts (`node dist/main.js` — no `ts-node`, no `tsx`, no `.ts` entry): asserted mechanically (`grep` on the manifest — exit 70 names violations), reviewed culturally (hook-in-`start` fails review with the ladder attached — [01/2.1](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>) numbers end the debate). The boundary from [01/4.1](<../../../01 Execution Foundations and Mental Model/sections/4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>) enforced as text search, not tribal knowledge.

### What problem it solves (history)

Hook-in-production creep (dev script copied to `start` "temporarily," Dockerfile `CMD` invoking ts-node for "observability," orchestrator commands with loader flags nobody remembers adding) arrived without diffs announcing it — each instance discovered via slow boots, version incidents, or toolchain CVEs in production images. The grep converts creep into a CI failure: undeclared production toolchains block the merge, attributed to the diff that introduced them.

### Modern guidance

Assert per repo (stage 70: `start` matches `node dist/` shape, rejects hook tokens — the gate below); audit per quarter (all `start`/`serve`/`prod` scripts across the org — violations ticketed with ladder numbers, fixed within the sprint); exempt explicitly (the rare measured exception — tiny internal tool with numbers in a comment — allowlisted by path, never by silence). Exceptions documented beat exceptions discovered.

### Runnable example (good — the assertion, verified)

```bash
#!/bin/bash
# shipping checklist gate: no hook in start + maps ship + image runs
grep -q '"start": "node dist/' ship/package.json || exit 70
! grep -q 'ts-node\|tsx\|\.ts"' ship/package.json <<<"$(grep '"start"' ship/package.json)" || exit 70
[ -f ship/dist/main.js.map ] || exit 71
docker run --rm ship-probe 2>&1 | grep -q "hello ship" || exit 72
echo SHIP-CHECK-GREEN
```

```bash
./gate7.sh; echo "exit=$?"
# SHIP-CHECK-GREEN
# exit=0
```

Verified: manifest declares artifact execution (stage 70 green), maps co-ship (stage 71), container smoke prints (stage 72). Three assertions, three boundary guarantees, one script — the shipping twin of gates 1–6, same exit-code narration.

### Common confusion

- **"dev and start should match"** — they should *rhyme* (same entry, same config family) not *match* (hook vs artifact — different executors by design). Matching executors across environments is precisely the hook-in-production creep; rhyming executors (dev hook, prod artifact, shared config base) is the practice. Rhyme, don't replicate.
- **"grep is too naive"** — naive is the point (text search catches `ts-node`, `tsx`, `.ts` in start scripts regardless of author intent — no AST, no config parsing, no false negatives from cleverness). Sophisticated checks follow (image inspection, SBOM audit); the grep is the floor, not the ceiling — floors catch the most, cheapest.

### Performance note

Gate cost: three greps + one container run (seconds, image-cached) — the cheapest deploy gate after version prints. Hook-in-production cost: slowest boots + toolchain images + version incidents (priced thrice in [2.1](<../2. Dist and containers/2.1. dist layout that deploys.md>) part 3). Asymmetric trade funds the gate permanently — cheapest stage, highest blast-radius exclusion.

### Mentor note

The `start`-script grep belongs in every repo's CI within the hour of reading this (one line, immediate value): existing violations surface as named findings (fix with ladder numbers attached), future violations block at PR. Mentees learn the boundary fastest when CI enforces it before humans explain it — automation teaches, mentors reinforce.

## 2) Maps ship with artifacts

### 2) **Definition** (the observability invariant)

Every shipped artifact carries its maps (`.js.map` beside `.js` — asserted via file existence, stage 71) and every production Node runs flagged (`--enable-source-maps` in `CMD`/start — asserted via manifest inspection): blind production is thereby a *detectable* state (gate red) rather than a *discovered* state (3 a.m. stack of `dist` positions). Observability ships; it never "gets added later."

### What problem it solves (history)

Map-stripping optimizations ("save space," "hide sources," "faster deploys" — each plausible, each blinding) accumulated until incident stacks named generated positions exclusively — triage degraded to guessing while the maps that would have named lines sat ungenerated in build logs. The invariant (maps co-ship, always) removes the optimization's victim (on-call readability) from the tradeoff table permanently.

### Modern guidance

Assert co-shipping per build (stage 71: every `.js` has its `.map` — loop over `dist/`, not just the entry); assert the flag per image/manifest (`CMD`/start contains `--enable-source-maps` — grep stage alongside 70); verify positions per deploy (throw-fixture smoke against staging — mapped `.ts` frames or the deploy blocks, per [05/3.1](<../../../05 Debugging Sourcemaps and Profiling TypeScript/sections/3. Production triage/3.1. Triage order for TS services.md>) parity). Three assertions, three pipeline moments (build, image, deploy) — coverage across the map lifecycle.

### Runnable example (good — the co-shipping proof, verified)

```bash
find ship/dist -type f | sort
# ship/dist/app.js
# ship/dist/app.js.map    ← co-shipped (stage 71 asserts this pairing per file)
# ship/dist/main.js
# ship/dist/main.js.map

node --enable-source-maps ship/dist/main.js --boom 2>&1 | grep "at fail"
#     at fail (/tmp/tsprobe/ship/src/app.ts:6:9)   ← positions, not dist lines
```

### Common confusion

- **"maps double image size"** — maps add ~30–50% of `js` bytes (measured proportion, not doubling — and `js` is itself a fraction of image layers dominated by the Node base). Size objections price against the 245MB baseline here (maps: kilobytes; base: hundreds of MB) — proportionality check before optimization, always.
- **"internal services don't need maps"** — internal services need maps *most* (highest deploy frequency × least triage ceremony = fastest blind-incident accumulation). Public exposure arguments (sourcesContent caution per [2.2](<../2. Dist and containers/2.2. Docker multi-stage for TS.md>) part 3) scope *content*, never *positions*. Positions always; text per audience.

### Performance note

Map costs: disk bytes (measured above), throw-time remap (microseconds per frame — incidents only), zero steady-state (maps idle until thrown). Benefit: every production throw triageable (minutes vs hours per incident). The cost/benefit Asymmetry is the domain's largest after the hook boundary — fund maps unconditionally, debate only `sourcesContent`.

### Mentor note

Frame map-shipping as on-call empathy ("the 3 a.m. version of you will thank the 3 p.m. version") — engineers ship maps for their future selves, not for compliance. Teams internalizing temporal empathy maintain observability without enforcement; teams needing enforcement get the gate (stage 71 doesn't care about your philosophy — red is red).

## 3) Every image runs before it ships

### 3) **Definition** (the smoke contract)

Built images boot and answer before registries accept them: container smoke (run → expect output → mapped throw → exit codes) executes post-build, pre-push — red blocks the push mechanically. Untested images (built, pushed, first-run-in-production) are lottery tickets with layers; smoked images are verified artifacts with receipts.

### What problem it solves (history)

"Builds green, fails at sea" (untested images failing on first orchestrator boot — missing env, wrong CMD, unbound ports, broken entry — discovered per environment, debugged per pager) wasted the most expensive debugging context (production-shaped, time-pressured) on the cheapest verifiable properties (does it boot? does it answer?). Smoke moves first-boot earlier (CI, calm) from later (prod, paged).

### Modern guidance

Smoke every image (boot + expected output + mapped throw + exit codes — the four assertions, sub-minute combined); smoke against production-shaped config (env, ports, mounts mirrored — smoke passing on toy config proves toy readiness only); block pushes on smoke red (registry accepts verified images — unverified pushes fail the pipeline, attributed to the Dockerfile diff that broke them).

### Runnable example (good — the smoke, verified)

```bash
docker run --rm ship-probe 2>&1 | grep -q "hello ship" || exit 72   # boots + answers
docker run --rm ship-probe node --enable-source-maps dist/main.js --boom 2>&1 | grep -q "at fail (.*/app/src/app.ts"
# mapped throw inside the image (stage 72 extended — boot, behavior, AND observability smoked)
```

Verified both (this session): boot prints, throw maps — the image proven runnable *and* observable before any registry sees it. Stage 72 in gate7 covers boot+behavior; extend per service (health endpoint, readiness probe, signal handling — same pattern, more assertions).

### Common confusion

- **"CI smoke duplicates staging"** — smoke proves the *image* (artifact integrity — boots, answers, maps); staging proves the *deployment* (env, networking, data, scale). Different subjects (bytes vs systems), different moments (pre-push vs post-deploy) — complementary gates, never substitutes. Skip either and its subject goes unverified.
- **"smoke slows the pipeline"** — smoke costs one container boot + one throw (seconds, image-cached) against first-boot-in-prod failures (minutes-to-hours, paged, customer-visible). Pipeline seconds vs incident hours — the cheapest insurance in shipping after the grep.

### Performance note

Smoke runtime: container start (seconds, image-cached layers) + assertions (milliseconds) — per build, negligible beside image build minutes. Unsmoked-image cost: production first-boot failures (orchestrator backoff loops, pager storms, rollback windows — priced in downtime, not compute). Insure per build; collect per incident avoided.

### Mentor note

The smoke graduation exercise: break an image four ways (wrong CMD, missing env, dropped maps, broken entry) and watch stage-72 variants fire per breakage — each exit naming its failure. Thirty minutes, four breakages, complete shipping literacy. Mentees completing it review Dockerfile PRs with runtime eyes permanently.
