# 3.1. CI gates for TS services

The merged pipeline: typecheck, tests, emit, artifact probes, and image build — ordered so each stage gates the next, failures named by stage. Junior read: copy the workflow shape, keep it green. Expert read: why order is load-bearing (cheap checks first, artifacts last), and what "verified, never assumed" costs per merge (seconds) versus saves per incident (hours).

## 1) Gates 1–6 merged into one pipeline

### 1) **Definition** (the unified pre-flight)

Gates 1–5 (execution pin/probe/checker; config winner/pairs/aliases; hook trace/order; workflow suite/REPL/receipt; observability maps/profiles) plus gate 6 (shipping: exists/mapped/runs/traces) run as one CI workflow in dependency order — fast checks first (seconds), builds middle (emit), artifact probes last (image). Pedagogy split them across five sessions ([02/4.1](<../../../02 Configuration and tsconfig for Execution/sections/4. Important points to remember/4.1. Config checklist habits mentors insist on.md>)'s unification rule); operations merges them into a single required status.

### What problem it solves (history)

Gate sprawl (six scripts run by hand, in whatever order the responder remembers, skipping the slow ones under deadline) degrades to gate theater — files existing, nobody running them, incidents arriving through ungated stages. The merged workflow (one file, ordered steps, required status blocking merge) converts documentation into enforcement: unrun gates block the merge mechanically, not socially.

### Modern guidance

One workflow file per deployable (`.github/workflows/verify.yml` shape below — jobs mirror the gates, steps mirror the stages); required status on protected branches (merge blocked on red — no override culture for gate failures); local reproduction of every step (each CI step runnable locally verbatim — "fails only in CI" means environment drift, fixed by containerizing the step, never by weakening it).

### Runnable example (good — the workflow, validated)

```yaml
name: ts-service
on: [push, pull_request]
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 24, cache: npm }
      - run: npm ci
      - run: npx tsc --noEmit -p tsconfig.json
      - run: npm test
      - run: npm run build
      - run: ./gate6.sh
      - run: docker build -t app:${{ github.sha }} .
```

Validated: parses as YAML (8 steps, structure confirmed via `yaml.safe_load` — shape-checked, not just eyeballed). Order reads cheap-to-dear: install → check → test → emit → probe → image. Each step gates the next (checker red blocks tests? — arguably tests could precede types; the ordering rule in part 2 settles it: fastest signal first).

### Common confusion

- **"one mega-job is simpler"** — one *workflow* (unified status), multiple *jobs* where parallelism helps (typecheck || tests || lint concurrently; build after all green; probes after build). Unity of status, parallelism of execution — matrix the independent, sequence the dependent. The example compresses to one job for clarity; scale splits it by dependency, never by taste.
- **"gates slow merges"** — gates *pace* merges (minutes of verification per merge against hours of incident per escape). Slow is unparallelized, uncached full rebuilds per push (fix with caching + scoping, per TS 19) — gate count is rarely the bottleneck; measure step durations before blaming gates (the slowest step earns optimization, not the gate concept).

### Performance note

Pipeline runtime budget: install (cached: seconds) + check (incremental: seconds) + tests (suite-bound: tens of seconds) + build (emit: seconds) + probes (sub-second) + image (layer-cached: seconds-to-minutes on dep change). Total: single-digit minutes typical, dominated by tests and image layers — optimize those (parallel jobs, layer order), never by deleting verification stages.

### Mentor note

Review pipeline PRs for ordering violations first (slow-before-fast? artifact-before-check? image-before-probes?) — order is the highest-leverage review axis (wrong order wastes machine time per run and human time per failure). Then for local-reproducibility (each step runnable verbatim locally — steps that only run in CI are un-debuggable by authors, the worst property a check can have).

## 2) Build-gate-build order

### 2) **Definition** (the dependency sequence)

Typecheck → tests → emit → artifact probes → image build: each stage consumes the previous stage's verified output (checked sources → tested behavior → emitted bytes → probed artifact → shipped image). Reordering (image before probes, emit before tests) spends expensive stages on unverified inputs — minutes burned per failure that an earlier cheap stage would have caught in seconds.

### What problem it solves (history)

Optimistic pipelines (build image first, "test in parallel," probe never) produced the costliest failure shape: ten-minute image builds invalidated by thirty-second type errors discovered after — machine time wasted per run, human time wasted per triage ("is it the code or the image?"). Dependency order makes cheap stages fail fast (seconds) and expensive stages run rarely-on-green (amortized correctness).

### Modern guidance

Order rule: pure verification (typecheck, lint) → behavioral verification (tests) → derivation (emit) → artifact verification (probes, smoke) → packaging (image) → deploy. Parallelize within independence bands (lint || typecheck || unit tests — no shared outputs); sequence across dependence (nothing consumes unverified inputs). Image builds last among verifications (most expensive, most downstream — invalidated by anything upstream).

### Runnable example (good — the order with costs attached)

```yaml
# dependency order, cheapest first (verified shape from part 1):
- run: npx tsc --noEmit -p tsconfig.json   # seconds — gates everything below
- run: npm test                             # tens of seconds — gates emission
- run: npm run build                        # seconds — produces the artifact
- run: ./gate6.sh                           # sub-second — probes the artifact
- run: docker build -t app:${{ github.sha }} .  # minutes-if-cold — packages the proven
```

```yaml
# bad: image first (verified pattern smell — minutes spent before seconds decide)
- run: docker build -t app:${{ github.sha }} .  # 4 min…
- run: npx tsc --noEmit -p tsconfig.json        # …invalidated in 20s by a type error
```

Why it hurts, priced: 4 minutes of build + push per run invalidated by a 20-second check placed after — multiplied by pushes per day per developer. Order the stages by cost-ascending and the waste disappears structurally (no discipline required once the file encodes it).

### Common confusion

- **"parallel everything for speed"** — parallelize *independent* stages (typecheck || lint || unit-tests — disjoint inputs/outputs); dependent stages serialize by definition (probes need artifacts; images need probes). Parallelizing dependence isn't speed (it's races — probes asserting half-built artifacts, flaky by construction). Dependency first, parallelism second.
- **"fail-fast flag replaces ordering"** — `fail-fast` stops *matrices* on first red (useful, orthogonal); ordering decides *what runs before what fails* (cost structure). Both: order cheap-first AND fail fast — complementary controls, neither substituting the other.

### Performance note

Pipeline economics per merge: ordered cost = Σ(stages until first red, usually green → all stages) vs unordered worst-case (expensive stages always run). Expected savings ≈ P(early-red) × (expensive-stage cost) — on red-prone branches (feature work), substantial; on green main, identical. Order for the red case (that's when cost matters); green runs cost the same either way.

### Mentor note

Audit pipelines by printing step durations (CI exposes per-step timing — sort descending, optimize the top): the slowest *verification* step earns engineering (caching, scoping, parallel splits); the slowest *packaging* step earns Dockerfile work (layer order per [2.2](<../2. Dist and containers/2.2. Docker multi-stage for TS.md>)). Never optimize by deleting stages (verification removed is incidents purchased — price honestly).

## 3) Artifacts verified, never assumed

### 3) **Definition** (gate6 in the pipeline)

`gate6.sh` (stages 60–63: artifact exists, maps co-shipped, entry runs, throw maps) executes post-build, pre-image (or post-image against the container — both, ideally): exists (file present — build produced), mapped (co-shipped `.js.map` — observability intact), runs (entry prints — execution intact), traces (throw names `.ts` — parity intact). Four assertions, one script, blocking status — the artifact twin of every earlier gate.

### What problem it solves (history)

"Build passed, ship it" assumed artifacts from exit codes (tsc 0 ≠ layout right ≠ entry runs ≠ maps ship — [1.2](<../1. Build configs/1.2. Emit verification.md>) part 1's four exclusions). Assumed artifacts produced the deployment incident catalog (nested trees, broken entries, blind production — each "impossible, the build passed"). Verified artifacts close the catalog: every assumed property asserted, every assertion blocking.

### Modern guidance

Gate the artifact in CI (gate6 post-build — red blocks image/push); gate the image too (container smoke: boot + mapped throw + exit codes per [2.2](<../2. Dist and containers/2.2. Docker multi-stage for TS.md>) — image-layer regressions caught distinctly from build regressions); gate on schedule as well (nightly artifact probes catch toolchain drift — compiler minors, base-image updates — between code changes). Three gates, three moments (build, image, time) — coverage across the artifact lifecycle.

### Runnable example (good — gate6, verified green)

```bash
#!/bin/bash
# shipping gate: artifact exists + maps co-shipped + runs + traces map
[ -f ship/dist/main.js ] || exit 60
[ -f ship/dist/main.js.map ] || exit 61
node ship/dist/main.js | grep -q "hello ship" || exit 62
node --enable-source-maps ship/dist/main.js --boom 2>&1 | grep -q "at fail (.*/ship/src/app.ts:6:9)" || exit 63
echo SHIP-GREEN
```

```bash
./gate6.sh; echo "exit=$?"
# SHIP-GREEN
# exit=0
```

Verified: all four stages green (exists, mapped, runs, traces — the complete artifact contract in one script). In CI this runs post-`npm run build`, pre-`docker build` (artifact proven before packaging) — plus the container smoke post-build (mapped throw inside the image — [2.2](<../2. Dist and containers/2.2. Docker multi-stage for TS.md>) part 3 verified the shape).

### Common confusion

- **"build exit 0 implies shippable"** — implies *compilable* (one of four properties — layout, execution, mapping unverified). The implication chain developers assume (compiles → correct tree → runs → observes) breaks at every arrow in practice (nested trees compile; broken entries compile; mapless builds compile). Assert each arrow; assume none.
- **"smoke tests replace artifact gates"** — smoke tests assert *behavior* (endpoints respond); artifact gates assert *structure* (files exist, maps ship, traces name). Behavior-green + structure-red ships working code nobody can observe (the next incident goes blind). Both gates, both green — behavior proves function, structure proves operability.

### Performance note

Gate6 cost per build: file checks (milliseconds) + entry run (cold start, sub-second) + throw probe (milliseconds) — sub-second total, the cheapest pipeline stage after version prints. Unverified-artifact cost: deployment incidents (hours with misdirection, per occurrence). Cheapest stage, highest leverage — fund it first, cut it never.

### Mentor note

The gate6 graduation exercise: break an artifact four ways (delete entry, drop maps, break entry, strip flag) and watch stages 60–63 fire in order — each exit code naming its breakage. Thirty minutes, four failures, complete artifact literacy. Mentees completing it review build PRs with structural eyes permanently.
