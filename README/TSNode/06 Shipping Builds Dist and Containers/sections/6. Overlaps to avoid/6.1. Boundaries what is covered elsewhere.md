# 6.1. Boundaries: what is covered elsewhere

Where this domain stops and who owns the rest — the DRY map for shipping. Junior read: if your question isn't answered here, this page names the page that answers it. Expert read: the service-artifact vs library-package vs orchestration split that keeps shipping knowledge in exactly one place per question.

## 1) Emit, publish, and orchestration mechanics (neighbor tracks own the machinery)

### 1) **Definition** (the artifact/mechanics split)

*How compilation stages work, how declarations publish, how packages attain health, how builds scale, how containers orchestrate* are machinery — owned by neighboring tracks, assumed here, never restated. This domain owns the *service artifact*: build delta, dist layout, map shipping, service image, CI gates. Machinery questions go outward; artifact questions stay here.

### Common confusion

- **"this domain should explain declarations"** — services deliberately skip them ([1.1](<../1. Build configs/1.1. The build tsconfig.md>) part 1 priced the skip); libraries follow TS 12. Explaining here duplicates one home or contradicts the other — link per audience (service → skip with reason; library → TS 12 with contract).
- **"shipping without orchestration is incomplete"** — images are the handoff (built + smoked + pushed here; scheduled + scaled + policied there). Completeness at the handoff means verified artifacts with receipts — orchestration consumes receipts, never re-verifies builds. Handoff discipline beats end-to-end sprawl.

### Mentor note

Teach mentees to read this page as a router: "machinery" questions go outward (TS 01/12/16/19, NodeJS 06, Docker), "artifact" questions stay here. The distinction resolves half of all shipping debates before they start — most are machinery-questions asked in artifact-rooms ("how does `composite` work?" during a "what goes in `dist/`?" decision), or the reverse.

What remains is *judgment*: selecting architectures under constraints, reviewing Node+TS systems, narrating full-system traces, and the interview that synthesizes all seven domains. Each gets its full treatment exactly once, in Domain 07; mentions here stay one line plus a forward pointer (textual until it lands, live link after).

### Common confusion

- **"textual forwards are dead links"** — deliberate placeholders (domain name + LOG pointer, never a `<path>` link), retired to live links when Domain 07 lands. The rule: no angle-bracket link may point at a nonexistent file — verified by sweep after every unit this session.

## 3) Development-side mechanics (neighbor domains own the ends)

### 3) **Definition** (the ships-what-they-built boundary)

Shipping consumes *developed* (01: hooks/modes; 02: configs; 03: loaders; 04: loops/suites), *mapped* (05: traces/profiles), and *gated* (all: green builds) inputs — this domain owns none of those ends, only their convergence into artifacts. Questions about what's shipped go here; questions about what's built go back; questions about evidence go to 05. Gates 1–7 embody the boundary: each asserts one layer's shippability.

### Common confusion

- **"a shipping bug is a build bug"** — shipping fails in artifact vocabulary (missing files, unmapped traces, hook in `start`, unsmoked images); builds fail in compiler vocabulary (`TS5xxx`, emit errors, layout breaks). Debug the artifact first (gates 60–72 name the property), the build second (emit gates name the cause) — the layer that failed names the half.
- **"this track replaces its prerequisites"** — it assumes them (declared in every domain's `## 0. Prerequisites`). Artifacts compile scoped sources through composed loaders in gated loops — readers without 01–05 misattribute every shipping failure upward. Ship atop foundations, never instead of them.

### Mentor note

The one-sentence router for shipping: "Machinery questions go outward (TS/NodeJS/Docker tracks), construction questions go back (01–05), *artifact* questions stay here." Builds/images/gates — the shipping layer with its own craft, its own checklist, its own interview.
