# 1.2. Emit verification

Proving the build before it ships: clean emit, file inventory, entry execution, and the throw-fixture parity probe. Junior read: four commands, all green, then ship. Expert read: what each check excludes, and why stale `dist/` is a deployment defect with a one-line prevention.

## 1) Emit is a checklist, not a hope

### 1) **Definition** (the four-gate emit)

Clean typecheck-emit (`tsc -p` exit 0) → file inventory (`js` + `map` present, `.ts` absent, tree mirrored) → entry executes (`node dist/main.js` prints) → fixture maps (throw names `.ts` under `--enable-source-maps`). Each gate excludes a failure class (type errors, layout breaks, runtime breakage, map loss); all four green means the artifact is shippable — evidenced, not hoped.

### What problem it solves (history)

"Build passed" once meant "tsc exited 0" — and artifacts shipped with wrong trees (`dist/src/` nesting), missing maps (blind production), and untested entries (broken on first request). Each class survived because no gate named it. The four-gate emit names all four: typecheck, layout, execution, mapping — the complete artifact contract in four commands.

### Modern guidance

Run all four gates per build (locally pre-push, in CI per merge — the build job fails on any red); script them (`"build:verify"` beside `"build"` — gates live with the build, not in runbooks); extend per pipeline (declaration check for libraries, size budgets for bundles — same pattern, more gates). A build passing fewer than four gates ships on hope for the unchecked classes.

### Runnable example (good — all four gates, verified)

```bash
./node_modules/.bin/tsc -p ship/tsconfig.build.json && echo EMIT-OK
# (exit 0 — gate 1: clean emit)

find ship/dist -type f | sort
# ship/dist/app.js
# ship/dist/app.js.map
# ship/dist/main.js
# ship/dist/main.js.map
# (gate 2: js+map, no .ts, mirrored tree)

node ship/dist/main.js
# hello ship
# (gate 3: entry executes)

node --enable-source-maps ship/dist/main.js --boom 2>&1 | grep "at fail"
#     at fail (/tmp/tsprobe/ship/src/app.ts:6:9)
# (gate 4: mapped .ts frames from the artifact — parity probe from 05/3.1, fulfilled)
```

Verified end to end: emit clean, four files exactly, entry prints, throw maps to authored positions. Gate 4's positions (`src/app.ts:6:9` vs unmapped `dist/app.js:9:11` — verified pair, genuinely different numbers) prove the maps aren't decorative: without them, triage reads line 9 of generated code; with them, line 6 of authored source.

### Common confusion

- **"tsc exit 0 suffices"** — exit 0 proves *compilation*, not *layout* (nesting), *execution* (runtime), or *mapping* (observability). Each subsequent gate caught real incident classes (nested trees deployed, broken entries shipped, blind production). Four gates, four exclusions — sufficiency is conjunctive.
- **"verify once per repo"** — verify per *build* (emit varies with sources, configs, and compiler versions — yesterday's green proves yesterday's tree). Gates automate (seconds per build); trust expires per emit. Per-build verification is the point of automation.

### Performance note

Four-gate cost per build: emit (seconds) + inventory/execution/fixture (sub-second combined) — dominated by compilation you'd pay anyway. Manual verification (ssh, run, eyeball — minutes, skipped under pressure) vs gated verification (seconds, always) — automation converts a skipped rite into an enforced invariant for less time than one manual run.

### Mentor note

Make the four gates the definition of "builds cleanly" for the team (PR template: emit/inventory/execution/mapping checkboxes, each with its command). Mentees internalize artifact discipline when "green build" means four evidences, not one exit code — vocabulary shapes verification, verification shapes artifacts.

## 2) Parity probe against `dist/`

### 2) **Definition** (the artifact twin of the hook fixture)

The same throw fixture from [05/4.1](<../../../05 Debugging Sourcemaps and Profiling TypeScript/sections/3. Production triage/3.1. Triage order for TS services.md>)'s gate (deliberate throw, fixed file/line) executed against `dist/` under `--enable-source-maps`, asserting authored `.ts` frames: mapped means the artifact pipeline (build maps, co-shipping, flag) holds end to end; unmapped means a stage regressed — failing the build instead of blinding production. Hook fixture proves dev observability; artifact fixture proves prod observability — twins, both gated.

### What problem it solves (history)

Artifact observability decayed silently (maps dropped from images to "save space," flags lost in script rewrites, build configs forked without `sourceMap`) — each plausible alone, collectively blinding production while dev traces stayed perfect. The parity probe (same fixture, both executions) detects divergence: dev-mapped + prod-unmapped names the artifact pipeline specifically, with the fixture diff as evidence.

### Modern guidance

Assert parity per build (hook fixture + artifact fixture, same file/line expectations modulo transport — inline vs file maps name identically); run artifact probes in staging deploy jobs (post-build smoke: boot + throw + mapped-frames assertion — the deploy gate from [4.1](<../4. Important points to remember/4.1. Shipping checklist habits mentors insist on.md>)); fail closed on mismatch (unmapped artifact = broken pipeline = blocked deploy — never "ship now, fix maps later").

### Runnable example (good — the twin probes, verified pair)

```bash
# hook twin (verified S5): inline maps, no flags
./node_modules/.bin/ts-node --transpile-only --project dbg/tsconfig.json ./dbg/trace.ts 2>&1 | grep "at boom"
#     at boom (/tmp/tsprobe/dbg/trace.ts:2:9)

# artifact twin (verified this session): file maps + flag
node --enable-source-maps ship/dist/main.js --boom 2>&1 | grep "at fail"
#     at fail (/tmp/tsprobe/ship/src/app.ts:6:9)

# and the control (no flag — proves the flag's load-bearing role here):
node ship/dist/main.js --boom 2>&1 | grep "at fail"
#     at fail (/tmp/tsprobe/ship/dist/app.js:9:11)
```

Three runs, complete story: hook maps flagless (bundled support), artifact maps flagged (file transport needs the flag), unflagged artifact names generated positions (line 9 vs 6 — genuinely different triage). The twins agree on positions; they differ only in transport — parity verified, not assumed.

### Common confusion

- **"one probe covers both executions"** — transports differ (inline vs file), flags differ (none vs `--enable-source-maps`), failure modes differ (hook support vs co-shipping). One probe covers one transport; twins cover the pipeline. Halved coverage fails exactly the uncovered half — in production, at night.
- **"parity probes duplicate unit tests"** — unit tests assert *behavior* (values, flows); parity probes assert *observability* (positions, attribution). Orthogonal concerns, orthogonal fixtures — behavior-green + observability-red ships working code nobody can debug. Both gates, both green, always.

### Performance note

Twin-probe cost per build: two throws (milliseconds) + grep assertions (free) — the cheapest gates in the pipeline after version prints. Unmapped-production cost: blind incidents (hours with misdirection, per occurrence). Asymmetry funds the twins permanently — cheapest stages, highest leverage.

### Mentor note

Teach parity as "same fixture, both worlds" (one throw file shape, hook run + artifact run, positions compared). Mentees who internalize twins stop asking "does observability work?" (singular, vague) and start asking "mapped here *and* there?" (plural, checkable) — the question upgrade is the skill upgrade.

## 3) Stale `dist/` never ships

### 3) **Definition** (the freshness invariant)

`dist/` is gitignored, cleaned before emit (`rm -rf dist/` or `tsc -b --clean` semantics), and rebuilt per pipeline run — never committed, never patched, never incrementally overlaid across builds. Stale artifacts (yesterday's `dist/` with today's version tag) deploy deleted code paths and resurrect fixed bugs — the freshness invariant (build output derives *only* from current sources + current config) excludes the entire class.

### What problem it solves (history)

Committed `dist/` (early Node practice, "deploy what you tested" taken literally) rotted desync-first: sources fixed, artifacts stale, deploys carrying both versions' behaviors unpredictably. Incremental-overlaid builds (emit without clean) left orphaned files (deleted sources still executing — ghost routes serving removed handlers). Clean-rebuild-per-pipeline ended both: output as pure function of inputs, every time.

### Modern guidance

`.gitignore` lists `dist/` (and `*.tsbuildinfo` unless intentionally cached — cache discipline per TS 19); build scripts clean first (`"prebuild": "rm -rf dist"` — npm lifecycle, automatic); pipelines never cache `dist/` across runs (cache `node_modules` and tsbuildinfo where valid — never outputs); deploy jobs assert freshness (newest `dist/` mtime newer than pipeline start — cheap timestamp check in the gate).

### Runnable example (good — clean, emit, verify freshness)

```bash
rm -rf ship/dist && ./node_modules/.bin/tsc -p ship/tsconfig.build.json && ls ship/dist
# app.js  app.js.map  main.js  main.js.map   (only current sources emit)
node ship/dist/main.js
# hello ship
```

```bash
# bad: overlay emit without clean (deleted sources persist as ghosts)
# (src/old-route.ts deleted last sprint — without clean, dist/old-route.js still serves)
```

Why it hurts, specifically: ghost files execute (deleted routes serving, removed middleware running — behavior from unreviewed past), version tags lie (artifact claims v2.3, contains v2.1 paths), rollbacks confuse (which files belong to which version? — unanswerable post-hoc). Fix: clean-first always (one `rm`, total freshness) — the cheapest invariant in shipping.

### Common confusion

- **"clean slows builds"** — clean deletes outputs (milliseconds of `rm`); emit re-derives everything anyway (full transpile per build — incremental emit is `tsc -b`'s job with tsbuildinfo, a different mechanism from dirty `dist/`). Clean-first full builds trade seconds for certainty — incremental caching (tsbuildinfo, layer caches) recovers speed without sacrificing freshness.
- **"committed dist/ aids debugging"** — committed dist aids *confusion* (which commit's sources produced this dist? — unverifiable post-hoc). Debuggability comes from maps + tags (positions + versions, both verifiable), never from checking in build outputs. Version the inputs, gate the outputs, ignore the middle.

### Performance note

Clean-rebuild cost: full emit per build (seconds on service trees — the correct price of certainty). Layer caching (Docker `COPY` ordering per [2.2](<../2. Dist and containers/2.2. Docker multi-stage for TS.md>)) recovers most of it across unchanged sources (cache hits skip reinstall + recompile). Freshness and speed compose via caching — never via dirty outputs.

### Mentor note

The ghost-file demo converts skeptics permanently: delete a source, emit without clean, execute the ghost. One revenant route serving from beyond deletion ends "clean is optional" talk forever — horror is an underrated teaching tool (use sparingly, remember fondly).
