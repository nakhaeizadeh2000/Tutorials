# 1.1. The build tsconfig

The emission delta: `outDir`/`rootDir`/`sourceMap`/`declaration` shaped for artifacts, self-contained inside the build context, with types present where the builder compiles. Junior read: copy the shape, build cleanly. Expert read: why `extends` across a Docker boundary fails, and why the builder needs types the runtime never loads.

## 1) One delta for emission

### 1) **Definition** (the build context)

The build tsconfig extends the repo base and overrides exactly what emission needs: `outDir: dist` (artifacts land outside sources), `rootDir: src` (tree shape declared — stray files outside `src/` fail loudly instead of warping `dist/`), `sourceMap: true` (co-shipped maps per [05/3.1](<../../../05 Debugging Sourcemaps and Profiling TypeScript/sections/3. Production triage/3.1. Triage order for TS services.md>)), `declaration: false` (services ship behavior, not contracts — libraries differ, see TS 12/3.1), `noEmit: false` (the one context where emit happens — every other tsconfig in the repo says `noEmit` or nothing).

### What problem it solves (history)

Single-config repos emitted with editor settings (no `outDir` — `.js` beside `.ts`, imports resolving to stale emit, `git status` permanently dirty) or checker settings (`noEmit: true` inherited — builds producing nothing, silently). The dedicated delta separates the only context that writes files from every context that reads them: emission is a decision with a file, not a flag remembered at deploy o'clock.

### Modern guidance

One `tsconfig.build.json` per deployable (services: one; monorepo packages: one each, extending the root base); `include: ["src"]` narrow (tests, scripts, and config fixtures never enter artifacts); `exclude: ["**/*.test.ts"]` where tests co-locate (belt-and-suspenders beside `include` — defense in depth for layout). Build script: `"build": "tsc -p tsconfig.build.json"` (explicit `-p` — never bare `tsc`, whose discovery depends on CWD).

### Runnable example (good — the delta, verified emitting)

```jsonc
// ship/tsconfig.build.json — self-contained (part 2 explains why not extends)
{
  "compilerOptions": {
    "target": "es2022",
    "module": "commonjs",
    "strict": true,
    "esModuleInterop": true,
    "outDir": "dist",
    "rootDir": "src",
    "sourceMap": true,
    "declaration": false,
    "noEmit": false,
    "types": ["node"]
  },
  "include": ["src"]
}
```

```bash
./node_modules/.bin/tsc -p ship/tsconfig.build.json && find ship/dist -type f | sort
# ship/dist/app.js
# ship/dist/app.js.map
# ship/dist/main.js
# ship/dist/main.js.map
```

Verified: clean emit, mirrored tree (`src/` → `dist/` file-for-file), maps co-shipped, zero declarations (services need none). `rootDir` earns its keep silently here — remove it and a stray file outside `src/` would nest the whole tree one level deeper (the classic `dist/src/...` surprise, prevented by declaration).

### Common confusion

- **"`declaration: true` for services"** — declarations serve *consumers* (libraries importing your types — TS 12/3.1 owns the contract). Services have no type-consumers (only operators running `node dist/`) — emitting `.d.ts` for services ships unread files that slow the build. Libraries: `declaration` + `declarationMap` on; services: off, deliberately.
- **"build extends the app config"** — build extends the *base* ([02/1.1](<../../../02 Configuration and tsconfig for Execution/sections/1. Config architecture/1.1. Base and delta tsconfigs.md>)), like every delta. App configs carry runner concerns (`ts-node` object, test `include`s) that emission must not inherit — siblings under the base, never parent-child.

### Performance note

Emit cost per build: full transpile + map generation (seconds on service trees — the one context where paying it is correct). `declaration: false` saves the declaration pass (~5–10% per TS 01/3.1's measurement, cited not re-measured); narrow `include` saves file discovery. Build-time economics favor completeness over speed (builds run per merge, not per save — correctness of output beats seconds of emit).

### Mentor note

Review build configs against the dev configs they sit beside: every key must justify its divergence (outDir/rootDir/sourceMap: emission needs; noEmit:false: only here; test-only flags: absent). Deltas that mirror without reason get merged; divergences without comments get questioned. The build file is small — its review should be exacting, not casual.

## 2) Self-contained inside the build context

### 2) **Definition** (the context-boundary rule)

Build configs must resolve *inside* every context that builds them — local shells, CI runners, Docker build stages. `extends: ../tsconfig.json` resolves against the filesystem, so any context receiving only a subtree (Docker `COPY`, sparse checkouts, package-scoped CI) breaks the chain: `TS5083: Cannot read file`. Self-containment (inline options, or extends pointing *within* the copied tree) makes the build location-independent.

### What problem it solves (history)

`extends` chains assume the whole repo travels together — true locally, false in every build optimization (Docker layer caching copies `package.json` first; monorepo CI checks out packages; release branches vendor subtrees). Each optimization met the same `TS5083` at 2 a.m., fixed by duplicating three options under deadline pressure. Self-containment declares independence upfront: the build file carries what the build needs, everywhere it builds.

### Modern guidance

Build configs: inline the emission options (or extend a base *copied alongside* — `COPY tsconfig.base.json` beside it, relative path intact). Never extend upward out of the build context (`../` in a build file is a finding until proven copied). Verify per context (local `tsc -p` *and* container build — the pair, not either): contexts differ, each earns its proof.

### Runnable example (good — the failure, then the fix, both verified)

```bash
# ship/tsconfig.build.json with "extends": "../tsconfig.json", built in Docker (context = ship/):
# #12 [builder 7/7] RUN npx tsc -p tsconfig.build.json
# #12 1.466 error TS5083: Cannot read file '/tsconfig.json'.
```

Verified live (Docker buildx): the extends escaped the context (`/app/../tsconfig.json` = `/tsconfig.json` — outside the image entirely). Fix applied in-probe: inline the six emission options, rebuild — green. The error names the missing file absolutely (`/tsconfig.json` — the escape made visible); read it literally and the fix writes itself.

### Runnable example (bad — the deadline duplication)

```jsonc
// bad: 2 a.m. fix — full option copy with no record of the divergence
{ "compilerOptions": { /* 40 lines copied from base, already drifting */ } }
// six months later: base enables exactOptionalPropertyTypes, build doesn't —
// checked locally, fails in container (or vice versa). Two truths, one incident.
```

Why it hurts: duplication without provenance (which lines mirror the base? which diverge deliberately?) — drift invisible until it bites across contexts. Fix: extend *within* the context (copy the base file into the image/context alongside) or inline minimally *with a comment naming the base* (`// mirrors tsconfig.base.json: target/module/strict — keep in sync`). Provenance or parity-checking (`--showConfig` diffed per context in CI) — never silent copies.

### Common confusion

- **"extends always works in Docker"** — extends works iff the base travels (multi-`COPY` Dockerfiles, monorepo-aware contexts). The failure isn't extends (fine mechanism) but *context packing* (what travels). Audit `COPY` lines beside `extends` lines — the pair must agree, file by file.
- **"one base for all contexts"** — one base per *travel unit* (repo root for local/CI-full; package base for package builds; inline for Docker subtrees). Bases follow deployment topology, not org charts — contexts that ship separately configure separately.

### Performance note

Self-containment costs option-duplication bytes (or one extra `COPY` layer — negligible) against cross-context build failures (each worth an incident + a deadline patch). `COPY` granularity also affects layer caching (base file changes bust fewer layers than inlined churn — the Dockerfile in [2.2](<../2. Dist and containers/2.2. Docker multi-stage for TS.md>) orders copies to exploit this).

### Mentor note

Teach `TS5083` as "the build file points outside its world" — one sentence that resolves every extends-across-context failure on sight. Mentees graduate from build-config confusion when they reflexively ask "what travels with this file?" before "what does this file say?" — context first, content second.

## 3) Types present where the builder compiles

### 3) **Definition** (builder-scope dependencies)

The builder compiles (typechecks + emits), so it needs everything compilation consumes: `typescript` itself plus `@types/*` for every untyped import the tree touches (`process`, `Buffer`, `__dirname` need `@types/node`). These are *build* dependencies (`devDependencies` suffices — installed in builder stages, omitted in runtime). Missing types fail the build with `TS2580`-class errors; present-but-unshipped types cost nothing at runtime.

### What problem it solves (history)

`--omit=dev` enthusiasm deleted `@types/node` from install scopes ("types aren't runtime!") — then builder stages (installing with the same flags) failed to compile the very code the image exists to run. Types aren't runtime *code*, but they are build-time *inputs*: omission scope must distinguish compile-time from run-time, and the line runs between stages, not packages.

### Modern guidance

`@types/*` in `devDependencies`, always (never `dependencies` — shipping type packages to production images bloats without function); builder stages install *with* devDeps (`npm install` / `npm ci` full); runtime stages install `--omit=dev` (verified below — types absent, execution unaffected). `types: ["node"]` (or scoped lists) in build configs where global-type pollution matters (narrower than `@types` auto-inclusion — explicit over ambient, per [02/1.1](<../../../02 Configuration and tsconfig for Execution/sections/1. Config architecture/1.1. Base and delta tsconfigs.md>)'s replacement-not-merge warning).

### Runnable example (good — the failure, then the fix, both verified)

```bash
# builder WITHOUT @types/node (verified live in Docker buildx):
# src/main.ts(3,5): error TS2580: Cannot find name 'process'.
#   Do you need to install type definitions for node?
#   Try `npm i --save-dev @types/node`.
```

```jsonc
// package.json — types as devDeps (build inputs, not runtime cargo)
{ "devDependencies": { "typescript": "5.9.3", "@types/node": "24.10.1" } }
```

```dockerfile
# builder: full install (types present — compiles)
RUN npm install --no-audit --no-fund
# runtime: prod-only install (types absent — executes; verified: hello ship prints)
RUN npm install --omit=dev --no-audit --no-fund && npm cache clean --force
```

Verified end to end: builder failed without the types (compiler's own suggestion quoted verbatim — read diagnostics literally, per [02/4.1](<../../../02 Configuration and tsconfig for Execution/sections/4. Important points to remember/4.1. Config checklist habits mentors insist on.md>)), passed with them; runtime image (types omitted) executes identically. The compiler tells you what to install; the stages decide where it lives.

### Common confusion

- **"@types in dependencies is safer"** — safer for nothing (runtime never imports types — erasure deleted them; bundlers never bundle them) and costlier (larger images, slower installs, wider audit surface). `devDependencies` is the semantically correct scope — safety through correctness, not through shipping more.
- **"skipLibCheck replaces @types"** — `skipLibCheck` skips *checking* declaration files (faster builds, fewer third-party type errors); it doesn't *provide* missing ones (`TS2580` fires with or without it — the names must exist to be referenced, checked or not). Orthogonal flags, complementary roles — enable both, confuse neither.

### Performance note

Types cost build time (parsing `.d.ts` trees — `@types/node` is large; `types: [...]` scoping trims it) and zero runtime (erased + omitted). `skipLibCheck: true` in build configs (faster, safe for services — library *authors* keep it strict per TS 12) — measure `time tsc -p` with/without on your tree; keep the faster printout with the commit.

### Mentor note

The two-error onboarding for builder types (`TS5083` extends-escape + `TS2580` missing-types — both verified this session) makes the perfect build-config exercise: break a working Docker build each way, read the diagnostics, fix each in place. Mentees completing both unaided own build contexts; the diagnostics taught them, not you.
