# 5.1. Common interview QA: shipping

Canonical answers for the three shipping questions every TypeScript-on-Node interview asks, plus rapid-fire drills. Junior read: memorize the diagnoses with their numbers. Expert read: each answer pairs the judgment with its *verified reproduction* from this domain — costs priced, failures quoted, proofs green.

## 1) "Why not run ts-node in production?" — answer with numbers

### 1) **Definition** (the priced-boundary screen)

"Why does production run `dist/` instead of ts-node?" — screens for economic reasoning over dogma: hires quote the ladder (full 1.247s → transpile-only 0.427s → SWC 0.228s on 60 files, artifact faster still at zero compile), determinism (byte-identical replicas vs per-boot compilation variance), and blast radius (type errors as build rejections vs runtime outages). Preachers ("best practice says") fail; pricers pass.

### What problem it solves (hiring signal)

Production-runtime choice is the highest-blast-radius judgment in TypeScript operations (every deploy, every replica, every boot) — engineers deciding by fashion import fashion's failure modes (slow cold starts, toolchain CVEs, version incidents). The question predicts whether runtime choices will be measured or mimicked on this hire's watch.

### Modern guidance

Answer in three prices (startup: ladder numbers + zero-compile artifacts; determinism: identical bytes across replicas — cacheable, signable, diffable; failure timing: type errors fail builds, never pages), close with the measured exception (tiny internal tools with numbers in a comment — the rule proving judgment, not absolutism). Cite the boundary ([01/4.1](<../../../01 Execution Foundations and Mental Model/sections/4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>)) as decided, the numbers as deciding.

### Runnable example (good — the prices, quoted)

```bash
# startup (verified S1, 60-file tree): full 1.247s → transpile-only 0.427s → swc 0.228s → artifact ~0.05s (no compile)
# determinism: docker run --rm ship-probe → hello ship (identical bytes, every replica — verified this session)
# failure timing: TS2322 in build → red CI (cheap); TS2322 at container boot → paged outage (dear)
```

A hire leads with numbers, follows with blast radius, volunteers the exception — economics before architecture. Interviewers: ask "when *would* you?" (tiny tool, measured, commented) — absolutists fail the follow-up regardless of the main answer's polish.

### Common confusion (in candidates)

- **"transpile-only in prod is fine"** — faster than full, still per-boot compilation with per-machine variance plus the full toolchain image (compiler CVEs in production, slowest cold start of the artifact family). Fine is comparative (vs full mode) not absolute (vs artifacts) — candidates stopping at comparative reveal satisficing instincts.
- **"containers make it reproducible"** — containers reproduce *files*, not *behavior-at-boot* (compile-per-boot still varies by CPU/throttle/cache state across nodes). Determinism requires identical *bytes executed*, not identical *images built* — artifacts deliver both, hooks deliver one.

### Performance note

The numbers *are* the answer (ladder + zero-compile, quoted above, re-measured per repo). Strongest form: "seconds per boot × replicas × restarts = fleet tax; artifacts zero it; the exception needs its own arithmetic in a comment." Fleet-scale multiplication converts local slowness into organizational cost — senior candidates multiply unprompted.

### Mentor note

Mock with "defend ts-node in production" (steelman the wrong position — tiny tool, measured, commented): mentees who can argue both sides choose correctly per context; mentees who can only recite the rule apply it absolutely (including where the exception fits). Judgment training requires losing an argument gracefully — stage the loss deliberately.

## 2) "Docker build fails on extends" — diagnose it

### 2) **Definition** (the context-boundary screen)

`TS5083: Cannot read file '/tsconfig.json'` inside `docker build` — screens for context thinking: hires read the absolute path literally (extends escaped the build context — `/app/../` = `/`), name the fix (inline options or `COPY` the base alongside), and state the rule (build files resolve inside every context that builds them). Path-readers pass in seconds; config-theorists debug for hours.

### What problem it solves (hiring signal)

Docker builds fail opaquely to developers who think in repo terms (paths relative to the project) while the builder thinks in context terms (paths relative to `COPY`d files) — the mismatch class behind most "works locally, fails in Docker" incidents. The question measures context-awareness directly: which filesystem does this command see?

### Modern guidance

Answer by reading the error (`/tsconfig.json` absolute = escaped context — the escape made visible), fix by containment (inline emission options or co-`COPY` the base — verified green rebuild this session), prevent by pairing (`COPY` lines audited beside `extends` lines — the pair must agree, file by file). Generalize unprompted (sparse checkouts, package-scoped CI — same escape, same rule): context thinking transfers everywhere.

### Runnable example (good — the failure and fix, quoted verbatim)

```bash
# #12 [builder 7/7] RUN npx tsc -p tsconfig.build.json
# #12 1.466 error TS5083: Cannot read file '/tsconfig.json'.
# src/main.ts(3,5): error TS2580: Cannot find name 'process'. [...]
```

Verified live (Docker buildx, this session): two errors, two lessons (context escape + builder-scope types — [1.1](<../1. Build configs/1.1. The build tsconfig.md>) parts 2–3). A hire reads `/tsconfig.json` and says "escaped — the context ships `ship/`, the extends points above it" before proposing anything; the interviewer scores the reading, the fix is trivial after.

### Common confusion (in candidates)

- **"COPY the root tsconfig"** — half-right (works, but drags context scope upward — cache granularity worsens, unrelated files travel). Strong candidates prefer self-containment (inline or co-located base) and name the caching trade; `COPY ..` advocates reveal context-indifference (the disease presenting as cure).
- **"TS2580 means install @types globally"** — global types fix the local build while the Dockerfile stays broken (environments differ — the fix must land in the *build context*: devDeps + builder install). Candidates fixing the observed environment instead of the failing one fail the screen regardless of eventual success.

### Performance note

No performance content (correctness incident) — candidates mentioning layer caching here earn bonus relevance (fewer layers invalidated by self-contained configs — the [2.2](<../2. Dist and containers/2.2. Docker multi-stage for TS.md>) connection, volunteered not required). Priced dimension is build reliability (context-complete configs build everywhere) — say exactly that; stop.

### Mentor note

Rehearse with the raw buildx output on screen and Dockerfiles covered: "diagnose from this alone." Graduates point at `/tsconfig.json` within seconds ("escaped context"); near-misses edit compiler options. The exercise trains literal error-reading under pressure — the transferable skill beneath the specific failure.

## 3) "How do you know the artifact works?" — trace the proof (plus rapid-fire)

### 3) **Definition** (the proof-tracing screen)

"Prove this artifact deploys" — screens for verification thinking: hires enumerate gates 60–63 (exists, mapped, runs, traces) plus container smoke (boot, behavior, observability) with the commands that assert each, quoting green outputs. Assertion-reciters ("we have CI") fail partially; proof-tracers (commands + outputs + exit codes) pass fully.

### What problem it solves (hiring signal)

"Build passed, ship it" culture ships exit-code confidence (compiles ≠ correct tree ≠ runs ≠ observes — [1.2](<../1. Build configs/1.2. Emit verification.md>) part 1's four exclusions). Engineers who enumerate artifact proofs gate deployments on evidence; engineers who cite build-green gate on hope. The question predicts deploy-incident rates directly.

### Modern guidance

Answer as a gate walk (60 exists → 61 mapped → 62 runs → 63 traces → container smoke → push), each with its command and expected output (quoted below, verified this session); name the blockers (any red blocks push — mechanically, not socially); extend per service (health endpoints, readiness, signals — same pattern, more assertions). Proof ends at push (verified images ship; unverified pushes fail the pipeline).

### Runnable example (good — the walk, quoted green)

```bash
./gate6.sh; echo "exit=$?"
# SHIP-GREEN
# exit=0
docker run --rm ship-probe
# hello ship
docker run --rm ship-probe node --enable-source-maps dist/main.js --boom 2>&1 | grep "at fail"
#     at fail (/app/src/app.ts:6:9)
```

Exists, runs, traces-mapped (inside the image, srcless) — the complete artifact proof in three commands. A hire walks all three unprompted; the interviewer hears verification thinking, not tool recitation. Follow-up ("maps missing in prod?"): stage 61/63 red → block push → co-ship maps ([4.1](<../4. Important points to remember/4.1. Shipping checklist habits mentors insist on.md>) part 2).

### Rapid-fire drills (with answers)

1. **Start script runs `ts-node` — verdict?** Finding (stage 70 — flip to `node dist/` with ladder numbers attached) ([4.1](<../4. Important points to remember/4.1. Shipping checklist habits mentors insist on.md>)).
2. **`dist/` committed to git — verdict?** Finding (stale-artifact class — gitignore + clean-first; version inputs, gate outputs) ([1.2](<../1. Build configs/1.2. Emit verification.md>)).
3. **No `.map` beside emitted `.js` — verdict?** Finding (stage 61 — blind production; co-ship or block) ([4.1](<../4. Important points to remember/4.1. Shipping checklist habits mentors insist on.md>)).
4. **Image never run pre-push — verdict?** Finding (smoke red-by-absence — boot+throw before registry, always) ([4.1](<../4. Important points to remember/4.1. Shipping checklist habits mentors insist on.md>)).
5. **CI builds image before typecheck — verdict?** Reorder (cheap-first dependency order — minutes wasted per red run otherwise) ([3.1](<../3. CI gates/3.1. CI gates for TS services.md>)).
6. **Prod trace names `dist/` lines — fix?** Co-ship maps + `--enable-source-maps` (artifact parity — same skills, file transport) ([1.2](<../1. Build configs/1.2. Emit verification.md>)).

### Common confusion (in candidates)

- **"CI green means shippable"** — CI green means *checked stages passed* (coverage = stages present, not stages conceivable — missing map-gate greens blindly). Candidates asking "which gates?" before celebrating green show verification thinking; celebrators show hope. Always ask which gates.
- **"smoke tests prove artifacts"** — smoke proves *behavior* (endpoints answer); gates prove *structure* (files/maps/traces present). Behavior-green + structure-red ships working code nobody can observe — both green, always ([3.1](<../3. CI gates/3.1. CI gates for TS services.md>) part 3).

### Performance note

Proof cost per build (gates + smoke: seconds-to-a-minute, image-cached) vs unverified-deploy cost (first-boot failures, blind incidents — priced in downtime). Candidates pricing proof against downtime (not against "pipeline speed") calibrate correctly; pipeline-speed worriers optimize the wrong denominator (minutes vs outages).

### Mentor note

Timed rapid-fire (ten seconds each, autopsy misses against this domain): six-for-six is graduation — and the quarterly shipping-readiness quiz. Drills 1–4 are binary verdicts (finding/not) — hesitation reveals uninternalized invariants; drill them until instantaneous.
