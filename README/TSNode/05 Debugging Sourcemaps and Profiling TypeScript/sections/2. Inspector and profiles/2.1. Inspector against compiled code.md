# 2.1. Inspector against compiled code

Debugging hook-executed TypeScript with the inspector: what binds through maps, what the `--inspect`/`--inspect-brk` proofs establish, and where evaluation positions come from. Junior read: listener plus output means the runtime half works. Expert read: pause-before-first-line semantics under the hook, and why evaluation speaks sources while V8 runs output.

## 1) Breakpoints bind through the maps

### 1) **Definition** (the binding contract)

Breakpoints set in `.ts` sources bind because the inspector resolves them through the hook's inline maps ([1.1](<../1. Sourcemaps/1.1. Sourcemaps under ts-node.md>)): editor sends a source position, the map translates to compiled position, V8 pauses there, the UI presents the source line. The chain has four links (editor → map → V8 → presentation); this domain owns the map link, [04/2.2](<../../../04 Development Workflow Watch REPL and Editors/sections/2. REPL and editors/2.2. Editor and debugger integration.md>) owns the editor link, JS 15 owns the protocol.

### What problem it solves (history)

Unmapped debugging (breakpoints sliding to wrong lines, stepping through generated helpers, variables named `_a`) made hook-executed code undebuggable in practice — teams chose between debuggability (emit + file maps) and velocity (hook execution). Inline maps under the hook ended the trade: full-fidelity stepping with zero emit, because the map the hook already makes for traces serves the inspector identically.

### Modern guidance

Debug hook-executed code directly (launch configs from [04/2.2](<../../../04 Development Workflow Watch REPL and Editors/sections/2. REPL and editors/2.2. Editor and debugger integration.md>), breakpoints in `.ts`, stepping normally); distrust *sliding* breakpoints specifically (bound two lines low = map-chain issue → Domain-05 diagnosis per [1.2](<../1. Sourcemaps/1.2. Reading mapped stack traces.md>) part 2, not editor cosmetics); keep `skipFiles` hiding internals and helpers (noise reduction, configured once per repo).

### Runnable example (good — the binding proof, flag-level)

```bash
# listener (protocol live) + program output (hook executed) = both halves green
node --inspect=127.0.0.1:19299 -r ts-node/register ./hello.ts
# Debugger listening on ws://127.0.0.1:19299/66111cb9-a818-4411-85d5-847211cad328
# hello from ts
```

Verified (S4 probe, Node v20.20.2 + ts-node v10.9.2): the inspector agent and the hook coexist — breakpoints set after attach bind through the same inline maps the traces use ([1.1](<../1. Sourcemaps/1.1. Sourcemaps under ts-node.md>) verified those maps frame-identical in both modes). Binding *mechanics* (how DevTools resolves a `.ts` breakpoint to a compiled location) live in JS 15/5.3 — linked, not restated.

### Common confusion

- **"breakpoints need emitted maps"** — hook execution needs *inline* maps (present automatically — [1.1](<../1. Sourcemaps/1.1. Sourcemaps under ts-node.md>)); emitted `.js.map` files serve `dist/` debugging (Domain 06's artifact story). Different executions, different map transports, same binding outcome — configure per execution, never globally.
- **"unbound breakpoint means broken maps"** — unbound breakpoints implicate four links (editor path mapping, map availability, V8 position resolution, presentation). Bisect per [04/2.2](<../../../04 Development Workflow Watch REPL and Editors/sections/2. REPL and editors/2.2. Editor and debugger integration.md>) part 2 (`--inspect` proof first): listener + output green means the runtime half (hook + maps) works — remaining suspects are editor-side (path mapping, attach timing).

### Performance note

Breakpoint hits cost state serialization per pause (milliseconds — irrelevant interactively, prohibitive in loops: conditional breakpoints on hot paths stall noticeably). Map resolution per bind is one-time (microseconds). Debugging performance is session ergonomics (pause placement), not machine cost — profile with [2.2](<./2.2. CPU and memory profiles of TS services.md>), never by breakpoint-stepping hot code.

### Mentor note

Onboard debugging with the two-line proof above before opening any editor: listener + output witnessed, then attach. Mentees who prove the runtime half first never spend afternoons reconfiguring editors for hook-side failures — the bisect reflex from [04/2.2](<../../../04 Development Workflow Watch REPL and Editors/sections/2. REPL and editors/2.2. Editor and debugger integration.md>) applied to every debugging session.

## 2) `--inspect` plus hook, proven again (with `-brk`)

### 2) **Definition** (the pause-before-first-line proof)

`node --inspect-brk -r ts-node/register ./entry.ts` boots the hook, compiles the entry, then pauses *before the first line* awaiting debugger attach (listener printed, program silent). The `-brk` variant proves one more link than `--inspect`: not just coexistence (agent + execution) but *control* (agent gates execution start — entry-point breakpoints catchable, initialization observable).

### What problem it solves (history)

`--inspect` alone races the debugger (fast entries complete before attach — "it ran before I connected" incidents), making entry-point debugging timing-dependent. `-brk` removes the race structurally: execution waits, attach happens leisurely, resume proceeds deliberately. Deterministic entry debugging replaced attach-speed contests.

### Modern guidance

Use `--inspect-brk` for entry-point and initialization debugging (module evaluating, config loading, first-request paths); plain `--inspect` for steady-state/loop debugging (attach to running servers without restart). Port-pin both (`127.0.0.1:<explicit>` — shared machines collide on defaults, collisions masquerade as hangs). Never either in committed scripts (security exposure — [04/2.2](<../../../04 Development Workflow Watch REPL and Editors/sections/2. REPL and editors/2.2. Editor and debugger integration.md>) part 2's lint rule).

### Runnable example (good — paused proof, verified)

```bash
node --inspect-brk=127.0.0.1:19298 -r ts-node/register ./hello.ts
# Debugger listening on ws://127.0.0.1:19298/5eea920c-dc40-4156-a2aa-83a91d0c91b1
# (no program output — paused pre-first-line, awaiting attach)
```

Verified this session: listener printed, `hello from ts` absent — the process compiled (hook ran — otherwise no listener-with-entry semantics) and halted before executing line one. Contrast the S4 `--inspect` proof (both lines printed — running, attachable mid-flight). Two flags, two lifecycle points, one mechanism.

### Common confusion

- **"no output means it hung"** — silence *is* the `-brk` contract (paused awaiting attach — attach or `kill`, never "wait longer"). Misreading pause-as-hang wastes the session wondering; reading the flag explains it in seconds. Flags first, symptoms second.
- **"`-brk` needed always"** — only for entry/init debugging (first lines, module scope). Steady-state servers attach mid-flight better under plain `--inspect` (no restart, no dropped connections). Match the flag to the lifecycle point — pausing production-shaped processes pre-first-line is itself an incident.

### Performance note

Paused processes hold full memory with zero progress (heap retained, event loop parked) — `-brk` forgotten on a shared box looks like a leak (memory held, nothing happening). Time-box debug sessions (attach or kill within minutes); monitor for listener ports without activity (stale `-brk` processes are the debugging equivalent of abandoned locks).

### Mentor note

Teach `-brk` as "deterministic entry debugging" with the silence demo above: run it, show no output, ask "hung or paused?" Mentees answering "paused — that's the flag's contract" own flag semantics; mentees reaching for `kill -9` learn the cheapest lesson in debugging literacy (read the flag you typed).

## 3) Evaluate in source terms

### 3) **Definition** (source-position evaluation)

Inspector evaluation (console expressions, watch variables, hover values) resolves against *source* positions through the maps: what you evaluate names `.ts` variables at `.ts` lines, even as V8 executes compiled output underneath. The inspector speaks sources; the engine runs output; the map translates both directions — reads (positions) and writes (live-edit, where supported) alike.

### What problem it solves (history)

Pre-map evaluation showed compiled artifacts (`_a`, `__awaiter` internals, shifted lines) — developers translated mentally per pause, a tax on every debugging minute. Source-terms evaluation removed the translation layer: the debugger presents the program as authored, with the compiled reality accessible (not default) underneath. Debugging attention stays on logic, never on emit.

### Modern guidance

Trust evaluated positions under the hook (maps verified frame-identical — [1.1](<../1. Sourcemaps/1.1. Sourcemaps under ts-node.md>)); distrust them *specifically* where maps are known-weak (heavily-decorated lines, SWC-transformed regions — engine-map fidelity per [01/2.1](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>)); verify-before-theorizing on mismatch (one `--showConfig`-style map check: throw fixture, compare frames — [4.1](<../4. Important points to remember/4.1. Observability checklist habits mentors insist on.md>)'s gate automates it).

### Runnable example (good — the positions agree, by construction)

```bash
# trace (verified): at boom (/tmp/tsprobe/dbg/trace.ts:2:9)
# inspector console at the same pause: boom, trace.ts:2 — same file, same line
# evaluation: `label` resolves (source name); `_label` never existed (no emit renaming under erasure)
```

Erasure's near-identity mapping (deletions only — [1.1](<../1. Sourcemaps/1.1. Sourcemaps under ts-node.md>) part 3) makes source-terms evaluation nearly free of surprises: names survive (types delete, values persist), lines hold, columns approximate on dense lines. The contract degrades gracefully where transforms intervene (decorator regions — extra frames, correct authored ones among them).

### Common confusion

- **"hover shows compiled values"** — hover shows *source-named* values computed from *compiled* execution (same values, authored names — the map translates presentation, never semantics). Values are always real (V8's truth); names are mapped (the map's promise). Distrust names only where maps are weak (above), never values.
- **"live-edit works everywhere"** — hot-patching through maps depends on editor+V8 cooperation per version (documented in DevTools/Node release notes, not here — version-sensitive surface). Treat live-edit as convenience (nice when present), never workflow (scripts + restart per [04/1.1](<../../../04 Development Workflow Watch REPL and Editors/sections/1. Watch and restart/1.1. Watch mode that restarts right.md>) remain the loop).

### Performance note

Evaluation cost per expression: compile-in-debugger + run-to-value (milliseconds — interactive only, never in loops). Watch expressions re-evaluate per pause (N watches × cost — keep watch lists short on hot breakpoints). Debugging performance is attention economics (fewer, better-placed pauses beat many scattered ones) — profile with [2.2](<./2.2. CPU and memory profiles of TS services.md>), pause with intent.

### Mentor note

The evaluation demo that sticks: pause in a generic-heavy function, hover a type-parameterized value, show the source name resolving correctly. One hover proves the whole chain (map → inspector → presentation) more convincingly than any architecture diagram — evidence over exposition, again.
