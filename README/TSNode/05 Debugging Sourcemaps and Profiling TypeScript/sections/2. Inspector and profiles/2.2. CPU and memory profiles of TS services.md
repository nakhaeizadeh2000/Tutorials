# 2.2. CPU and memory profiles of TS services

Profiling hook-executed TypeScript: `--cpu-prof` flames attributed to `.ts`, `--heap-prof` allocation stories per source, and the flame-first discipline transferred unchanged. Junior read: two flags, open in DevTools, read the widest boxes. Expert read: what `.ts` attribution proves about the pipeline, and where TS-specific allocation hides.

## 1) `--cpu-prof` attributes to `.ts`

### 1) **Definition** (source-attributed sampling)

`node --cpu-prof --cpu-prof-dir <dir> --cpu-prof-name <file> -r ts-node/register ./entry.ts` samples the V8 stack at 1kHz through hook execution and writes a `.cpuprofile` whose frames name `.ts` URLs (`file:///…/busy.ts`, function `hot`) — attribution flowing through the same inline maps as traces ([1.1](<../1. Sourcemaps/1.1. Sourcemaps under ts-node.md>)). Open in DevTools Performance or Speedscope; read flames in source terms.

### What problem it solves (history)

Profile attribution through transpile pipelines historically named generated code (frames into `busy.js:1:48392` — unmappable without co-shipped maps), forcing TS teams to profile `dist/` builds (stale, unrepresentative of dev) or squint at minified flames. Hook execution with inline maps profiles the *running sources directly*: the flame you read is the code you wrote, no map-chasing step.

### Modern guidance

Profile the path that matters (a hot route, a batch job, boot itself — never the idle process); keep sampling at defaults (1kHz overview, then zoom); read self-time (where time goes) not total (who called). `.ts` attribution is automatic under the hook — no flags beyond the profiler's own, no map plumbing. Flame-first discipline (hypothesis → profile → shape-fix → re-profile) transfers verbatim from [NodeJS 06/1.2](<../../../../NodeJS/06 Debugging Configuring and Shipping/sections/1. Debugging and profiling/1.2. CPU and memory profiles with action.md>) — assumed here, applied to sources.

### Runnable example (good — profiled, attributed, valid, verified)

```typescript
// dbg/busy.ts — CPU-bound, typed
function hot(n: number): number {
  let s = 0;
  for (let i = 0; i < n; i++) { s += Math.sqrt(i); }
  return s;
}
console.log("hot:", Math.floor(hot(2000000)));
```

```bash
TS_NODE_PROJECT=dbg/tsconfig.json node --cpu-prof --cpu-prof-dir dbg/prof --cpu-prof-name busy.cpuprofile -r ts-node/register ./dbg/busy.ts
# hot: 1885617375
# dbg/prof/busy.cpuprofile — 1.3MB, 5940 nodes, valid JSON
```

```python
import json; d = json.load(open('dbg/prof/busy.cpuprofile'))
# nodes: 5940 — parses, complete
# 'hot' frames: 8 — the function, named
# urls containing 'busy': {'file:///tmp/tsprobe/dbg/busy.ts'} — sources, not output
```

Verified: program output correct, profile valid JSON, `hot` frames present, URLs naming the `.ts` file. The profiler flags compose with hook flags transparently (profiler owns sampling, hook owns compilation — orthogonal stages, one command).

### Common confusion

- **"profiles need emitted code"** — profiles need *executing* code with *attribution*; the hook provides both (runs sources, maps frames). Emitted-code profiles add staleness (profiled bytes ≠ current sources on dirty trees) for zero attribution gain. Profile what you run; run what you profile.
- **"1kHz misses fast functions"** — sampling misses sub-millisecond *individual calls* but captures hot *paths* (statistical guarantee over time — the flame's wide boxes are real regardless of rate). Narrow-but-tall surprises are sampling noise; wide boxes are signal — read accordingly.

### Performance note

Profiler overhead at 1kHz: low single-digit percent (sampling, not instrumentation) — safe for staging, acceptable briefly in production (prefer short captures: 30–60s windows around the scenario, not always-on). `.cpuprofile` size scales with duration × graph size (1.3MB here for seconds — plan disk for long captures; `--cpu-prof-dir` to scratch, never the repo).

### Mentor note

Require a profile with every "it's slow" report (no flame, no triage — the rule from NodeJS 06, applied): hypothesis stated, profile attached, widest box named. Mentees graduate from performance folklore ("maybe the loop?") to performance evidence ("`hot` self-time 62%") the week the rule lands — flames end opinion-based optimization permanently.

## 2) `--heap-prof` writes alongside

### 2) **Definition** (allocation story per source)

`node --heap-prof --heap-prof-dir <dir> --heap-prof-name <file>` samples allocations (not just CPU) through hook execution, writing a `.heapprofile` openable in DevTools Memory view: which stacks allocate, how much survives, where retained paths root — attributed to `.ts` sources identically (same map pipeline). CPU asks *where time goes*; heap asks *what survives* — different questions, same command shape.

### What problem it solves (history)

TS-service leaks hid behind compilation (allocation attributed to generated code — unmappable without maps; helper closures from downlevel emit misattributed to user functions). Source-attributed heap profiles name the retaining stacks as authored: the closure, the cache, the listener list — leak triage in source terms from the first opening.

### Modern guidance

Heap-profile on symptom (growing RSS across requests/batches — never speculatively); capture short windows around the leaking operation (before/after snapshots compared — retained-path deltas name the leak class); read retained size (what survives GC — the leak), not allocated size (churn is normal — nursery behavior per JS 18). V8 sampling heap profiler overhead is higher than CPU (allocation tracking per sample — brief captures, staging first).

### Runnable example (good — same shape, second artifact, verified)

```bash
TS_NODE_PROJECT=dbg/tsconfig.json node --heap-prof --heap-prof-dir dbg/prof --heap-prof-name busy.heapprofile -r ts-node/register ./dbg/busy.ts
# hot: 1885617375
# dbg/prof/ → busy.cpuprofile + busy.heapprofile (both artifacts, one run each)
```

Verified: program output identical, `.heapprofile` written beside the CPU profile. Same flags pattern (profiler + dir + name + hook + entry) — learn one shape, operate both profilers. Open both in DevTools (Performance for CPU, Memory for heap); correlate (hot CPU + growing retained = the leak doing work — the highest-signal combination).

### Common confusion

- **"heap-prof replaces heap snapshots"** — sampling profiler (statistical allocation story over time) vs snapshots (exact retained graph at an instant): snapshots identify *what* leaks (retained paths), profiles identify *when/where* it allocates (temporal story). Leak workflow uses both (profile to locate the operation, snapshot-diff to name the retainer) — complementary instruments, not substitutes.
- **"TS allocates more than JS"** — type annotations allocate nothing (erased — [1.1](<../1. Sourcemaps/1.1. Sourcemaps under ts-node.md>) part 3); downlevel helpers allocate marginally (part of emit, measurable, rarely dominant). Heap differences between equivalent TS/JS are noise beside architecture (caching, listeners, closures) — profile the design, never the language.

### Performance note

Heap-prof overhead exceeds cpu-prof (per-allocation sampling cost — keep captures short, staging-first, never production-always). Artifact sizes grow with allocation volume (busy loops write megabytes per minute — dir to scratch, rotate aggressively). Snapshot diffs (DevTools compare) cost analyst time, not machine time — budget the reading, not just the capture.

### Mentor note

Pair every heap profile with its CPU twin (same run shape, both artifacts — as above): CPU-hot + heap-growing pinpoints "leak doing work" (caches filling with computed values); CPU-cold + heap-growing pinpoints "leak at rest" (listeners, timers, registries). The pair classifies leaks before a single retained path is read — triage by combination, then zoom.

## 3) Flame-first discipline transfers unchanged

### 3) **Definition** (the method, rehomed)

Hypothesis ("route X is slow") → profile route X under load (not the idle process) → read self-time (widest boxes — where time goes; deopt markers — shape problems) → fix the shape (monomorphic callsites, packed arrays, moved work) → re-profile proving it (before/after numbers — the receipt). Every clause transfers verbatim from NodeJS 06/1.2 to hook-executed TypeScript; the only delta is attribution (frames name `.ts` — free, automatic, verified).

### What problem it solves (history)

TS teams reinvented profiling workflows (custom harnesses, emit-then-profile rituals, "can't profile TS directly" folklore) for a solved problem — the method cares about stacks and samples, never about source language. Transferring the discipline unchanged (instead of rebuilding it) saves the reinvention and inherits the receipts format (before/after numbers or it didn't happen).

### Modern guidance

Profile TS services exactly like JS services (same flags, same viewers, same reading rules — the `.ts` attribution is a presentation upgrade, not a method change); keep profiles out of the repo (scratch dirs, short captures, attached to reports not commits); re-profile after every fix (the receipt is the practice — unfixed-by-numbers means unproven). Type-specific shape fixes (decorator density, enum-fuelled megamorphism, barrel re-export chains) ride the standard method — new smells, same loop.

### Runnable example (good — the loop, TS-flavored)

```bash
# 1. hypothesis: hot() dominates the batch path
# 2. profile: --cpu-prof on the batch entry (verified above — hot frames present)
# 3. read: widest box = hot self-time (Math.sqrt loop — expected, arithmetic-bound)
# 4. fix (illustrative): memoize/hoist/reduce calls per the shape found
# 5. re-profile: before/after self-time delta quoted in the commit
```

### Common confusion

- **"TS needs TS-specific profiling tools"** — V8 profiles executing code (language-agnostic below the map); maps translate presentation (language-aware above it). The toolchain is shared (Node flags, DevTools, Speedscope); only attribution is TS-flavored — and it's automatic. Toolchain FOMO wastes evaluation cycles; the standard tools already name your sources.
- **"profiles in CI gate performance"** — profiles diagnose; *benchmarks* gate (stable workloads, statistical thresholds — JS 19 owns the methodology). CI-stored profiles rot (unread artifacts); CI-run benchmarks with regression thresholds endure. Profile to understand, benchmark to enforce — different instruments, different jobs.

### Performance note

Method cost: one profiled run per hypothesis (seconds) + reading time (minutes) + fix verification run — against days of intuition-led optimization that optimizes cold code. The receipt requirement (before/after numbers in the commit) is the highest-ROI process in performance work: unmeasured "fixes" that regressed are caught by their own missing numbers.

### Mentor note

The profile-review ritual: every perf PR attaches before/after flames (or self-time deltas) with the widest box named. No attachment, no approval — the rule converts optimization from opinion to evidence within a quarter. Mentees learn to *enjoy* being wrong ("hypothesis disproven by flame" beats "fix shipped on hunch" — celebrate the disproof publicly).
