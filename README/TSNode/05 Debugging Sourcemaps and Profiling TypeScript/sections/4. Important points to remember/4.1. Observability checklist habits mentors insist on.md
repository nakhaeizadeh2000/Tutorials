# 4.1. Observability checklist (habits mentors insist on)

The three habits that keep TypeScript observability boring: mapped-frame assertions, rehearsed profiling, and posted triage order. Junior read: extend the gate with three observability stages. Expert read: which pipeline regression each stage catches, and why observability gates belong in CI rather than in on-call heroics.

## 1) Traces name `.ts` or the pipeline is broken

### 1) **Definition** (the mapping assertion)

CI throws a fixture and asserts `.ts` frames (`at boom (…/trace.ts:2:9)` — file, line, column as authored): mapped means the pipeline (engine maps, hook registers, remapper runs) holds end to end; unmapped means a stage regressed — failing the build instead of confusing on-call. The fixture is the canary for the entire observability chain: traces, breakpoints, and profiles all depend on the same maps.

### What problem it solves (history)

Map regressions arrived silently (transpiler swap, loader change, flag edit — each plausibly unrelated to observability) and surfaced at 3 a.m. as unreadable incident stacks — the pipeline broke in daylight, the bill came at night. The fixture moves detection to merge time (red build, named cause, author present) from incident time (blind on-call, absent author).

### Modern guidance

One throw fixture per repo (deliberate `throw`, fixed file/line — brittle-by-design: line moves fail the assertion, forcing fixture updates that re-verify mapping); asserted in CI (exit 50 names mapping failure distinctly from all other stages); extended per pipeline (custom loaders/transformers each earn a fixture proving *their* output maps — compositional coverage for compositional pipelines).

### Runnable example (good — the mapping stage in the gate)

```bash
#!/bin/bash
# observability gate: mapped frames + attributable profile
./node_modules/.bin/ts-node --transpile-only --project dbg/tsconfig.json ./dbg/trace.ts 2>&1 | grep -q "at boom (.*/dbg/trace.ts:2:9)" || exit 50
TS_NODE_PROJECT=dbg/tsconfig.json timeout 60 node --cpu-prof --cpu-prof-dir dbg/prof --cpu-prof-name gate.cpuprofile -r ts-node/register ./dbg/busy.ts >/dev/null 2>&1 || exit 51
python3 -c "import json,sys; d=json.load(open('dbg/prof/gate.cpuprofile')); sys.exit(0 if any('busy.ts' in n['callFrame'].get('url','') for n in d['nodes']) else 1)" || exit 52
echo OBSERVE-GREEN
```

```bash
./gate5.sh; echo "exit=$?"
# OBSERVE-GREEN
# exit=0
```

Verified: stage 50 asserts mapped frames (regex on the throw output), stage 51 profiles the busy path, stage 52 asserts `.ts` attribution inside the profile JSON. Three stages, three pipeline guarantees, one script — the observability twin of gates 1–4, same exit-code narration.

### Common confusion

- **"fixture line moves break CI spuriously"** — the breakage is the *signal* (line moved without fixture update = mapping unverified for the new shape — re-verify deliberately, then update). Brittle fixtures fail *usefully* (forcing re-proof); silent fixtures fail *never* (proving nothing). Prefer useful brittleness.
- **"one fixture covers all entries"** — mapping is per-pipeline (CJS hook, ESM loader, custom transforms each map independently — a green CJS fixture says nothing about the loader door). Fixture per execution path (each door, each custom hook, each engine) — coverage follows composition.

### Performance note

Gate cost: one throw (milliseconds) + one profiled run (seconds, busy-path only) — scheduled per merge (mapping regressions arrive via dependency/config diffs, not per commit). Fixture maintenance (line updates on fixture edits): seconds per change. Pipeline-blind incidents: hours with misdirection — the asymmetry funds the gate permanently.

### Mentor note

Require the mapping fixture in every repo's first observability PR ("prove traces name sources before building anything atop them") — traces, breakpoints, profiles, and triage all assume it. Mentees who gate maps first never debug unmapped; mentees who skip it debug unmapped at 3 a.m. Order matters; enforce it.

## 2) Profiles exist before incidents

### 2) **Definition** (rehearsed profiling)

Profile commands exist pinned (flags, dirs, names — reviewable), output dirs exist and rotate (scratch, never the repo), and the team has run them (each responder profiled the hot path at least once, calm). Rehearsed profiling means incidents meet operators, not tourists: flags known, viewers openable, flames readable — practiced in daylight, executed paged.

### What problem it solves (history)

First-time profilers under pager pressure (flag syntax guessed, output dirs missing, DevTools import forgotten, flame illiteracy) convert incidents into tutorials — learning curves billed at outage rates. Rehearsal moves the learning to game-days (cheap, calm, repeatable): the incident then executes a practiced motion, not a first attempt.

### Modern guidance

Pin profile commands beside run scripts (`profile:cpu`, `profile:heap` — full flag sets, scratch dirs); rehearse quarterly (game-day: profile the hot path, read the widest box, name the shape fix — even with no incident); keep one recent baseline profile per service (known-good flame to diff against — regressions visible as shape changes, not just numbers). Baselines age (re-capture per release — stale baselines mislead like stale maps).

### Runnable example (good — the rehearsed pair, verified)

```bash
# pinned, rehearsed, verified this session (both artifacts, one shape):
TS_NODE_PROJECT=dbg/tsconfig.json node --cpu-prof --cpu-prof-dir dbg/prof --cpu-prof-name busy.cpuprofile -r ts-node/register ./dbg/busy.ts
# hot: 1885617375 — 5940 nodes, hot frames, busy.ts URLs
TS_NODE_PROJECT=dbg/tsconfig.json node --heap-prof --heap-prof-dir dbg/prof --heap-prof-name busy.heapprofile -r ts-node/register ./dbg/busy.ts
# hot: 1885617375 — allocation story beside the CPU story
```

### Common confusion

- **"profiling in staging suffices unrehearsed"** — staging access *during* incidents is itself contested (permissions, load shape, data parity) — rehearsal covers access paths too (who can profile where, credentials ready, dirs writable). Unrehearsed staging profiling fails on logistics before methodology.
- **"baselines replace gates"** — baselines *inform* triage (diff against known-good); gates *enforce* invariants (mapped frames, suite green). Different instruments (reference vs assertion) — baselines age gracefully (re-capture), gates fail loudly (fix now). Both, never either/or.

### Performance note

Rehearsal cost: one game-day per quarter (hours, team-wide) + baseline storage (megabytes, rotating). Unrehearsed incident profiling: first-profile latency (tens of minutes) + misread flames (wrong fixes shipped under pressure — negative progress). The game-day is the cheapest performance insurance a team buys — price it against one bad hotfix, not against zero.

### Mentor note

Run the game-day personally the first time (lead the profile, narrate the reading, model the receipt): mentees imitate the lead's calm before they internalize the method. Second game-day, hand the keyboard over (narrate while they drive); third, observe silently. Graduated operators profile without being asked — the habit outlives the teacher.

## 3) Triage order posted, not remembered

### 3) **Definition** (runbook over recall)

The triage order ([3.1](<../3. Production triage/3.1. Triage order for TS services.md>): logs → profiles → hooks, unmapped short-circuit) lives on the runbook page (linked from alerts, printed for war rooms), not in responders' memories. Posted order executes under pressure; remembered order degrades with adrenaline (familiar layers first, evidence never). Paper beats recall at 3 a.m. — always has, always will.

### What problem it solves (history)

Unposted orders fragment per responder (each debugs their comfort layer first — hooks for hook people, config for config people), so multi-responder incidents duplicate work (three people profiling while nobody reads the stack) and miss stages (maps unchecked by all). Posted order synchronizes strangers: first responder reads stage 1 aloud, second prepares stage 2, third holds stage 3 — parallel without collision.

### Modern guidance

One runbook page per service family (order, gate commands, fixture locations, escalation pivots — the [3.1](<../3. Production triage/3.1. Triage order for TS services.md>) narrative compressed to commands); linked from every alert (pagerduty/opsgenie annotations carry the URL — discovery under pressure is a solved problem when the link ships with the page); rehearsed per quarter (game-day executes the page end to end — pages rot, rehearsals refresh).

### Runnable example (good — the page, compressed)

```markdown
# TS-service triage (order matters — do not skip stages)
1. Logs: capture mapped stack → first authored frame = suspect.
   Unmapped authored frame? STOP — fix maps ([05/1.2]), resume here after.
2. Profiles: resource-shaped? `--cpu-prof`/`--heap-prof` pinned cmds → widest box.
3. Hooks: loading evidence only (wrong file? missing trace? order smell?) → swap/pin per [03/1.1].
Gates: ./gate5.sh (50 maps / 51 profiles / 52 attribution). Escalation: "stacks untrusted" pivot call.
```

### Common confusion

- **"runbooks replace judgment"** — runbooks replace *recall*, not judgment (stages execute in order; interpretation stays human — a weird profile still needs a reader). Posted order handles the routine 80% identically every time; judgment handles the novel 20% with full attention (freed from sequencing overhead).
- **"posting is bureaucratic"** — posting costs one page (written once, rehearsed quarterly); remembering costs per incident per responder (re-derivation under adrenaline, fragmented across the team). Bureaucracy is process without payoff; the runbook's payoff is synchronized strangers closing incidents in order.

### Performance note

Posted-order cost: page maintenance (minutes per quarter) + rehearsal (game-day, shared with profiling practice). Unposted-order cost: duplicated stages (N responders × overlapping work) + missed stages (maps unchecked → hours of false-position triage). Synchronization is operational performance — the team as a parallel machine, orchestrated by paper.

### Mentor note

Review incident timelines against the posted order (stage skipped? pivot announced? gate green before theorizing?) — retrospectives that audit *sequence adherence* improve future incidents more than root-cause deep-dives alone. Process review compounds (every incident sharpens the order); cause review terminates (one bug understood). Do both; lead with sequence.
