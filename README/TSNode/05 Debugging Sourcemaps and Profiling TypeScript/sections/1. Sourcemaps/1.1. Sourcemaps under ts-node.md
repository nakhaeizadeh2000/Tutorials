# 1.1. Sourcemaps under ts-node

How stack traces name `.ts` files: the bundled remapping support, why no flags are needed, and where Node's own `--enable-source-maps` fits (redundantly). Junior read: throws show your source lines, always. Expert read: which package performs the remap, what transpile-only preserves, and the flag interaction matrix.

## 1) Maps ride along automatically

### 1) **Definition** (the bundled remap)

ts-node depends on `@cspotcode/source-map-support` (verified in the probe tree: nested under `ts-node@10.9.2`), which hooks stack-trace generation: every frame's compiled position is translated through the inline map the hook emits per file, so `Error.stack` names `trace.ts:2:9` instead of eval-machine gibberish. No flag, no config, no `source-map-support` install of your own — the runner ships its cartographer.

### What problem it solves (history)

Unmapped hook traces named generated code (line numbers into concatenated eval output — unactionable), forcing teams to install and wire `source-map-support` themselves with version-matched fragility. Bundling the support (matching the compiler ts-node drives) removed the second dependency and its mismatch class: traces map correctly because the mapper and the emitter share a version by construction.

### Modern guidance

Rely on the bundled maps for all hook-executed code (dev, scripts, tests, watch loops — everywhere ts-node compiles); never install a parallel `source-map-support` (competing remappers double-translate positions — the classic "off by N lines" corruption); verify mapping per repo once (throw fixture asserting `.ts` frames — the checklist in [4.1](<../4. Important points to remember/4.1. Observability checklist habits mentors insist on.md>) automates it).

### Runnable example (good — mapped frames, both modes, no flags)

```typescript
// dbg/trace.ts — throws deliberately
function boom(): never {
  throw new Error("mapped?");
}

export function run(): void {
  boom();
}

run();
```

```bash
./node_modules/.bin/ts-node --project dbg/tsconfig.json ./dbg/trace.ts
# /tmp/tsprobe/dbg/trace.ts:2
#   throw new Error("mapped?");
#         ^
# Error: mapped?
#     at boom (/tmp/tsprobe/dbg/trace.ts:2:9)
#     at run (/tmp/tsprobe/dbg/trace.ts:6:3)

./node_modules/.bin/ts-node --transpile-only --project dbg/tsconfig.json ./dbg/trace.ts
# (identical mapped frames — at boom (.../trace.ts:2:9), at run (.../trace.ts:6:3))
```

Verified on ts-node v10.9.2 + TS 5.9.3: full and transpile-only traces identical, both naming authored file/line/column with source context. Dependency proof: `npm ls` shows `@cspotcode/source-map-support@0.8.1` deduped under ts-node — the remapper, named.

### Common confusion

- **"maps need `sourceMap: true`"** — the probe tsconfig sets it, but hook traces map *regardless* (ts-node emits inline maps per file for its own pipeline — the `sourceMap` flag governs *emit-to-disk*, a Domain 06 concern). Don't cargo-cult emit flags into execution configs expecting trace changes.
- **"transpile-only degrades mapping"** — erasure preserves line fidelity (deletions don't shift lines the way transforms can) — verified identical above. Checking never owned mapping; skipping it changes nothing about positions.

### Performance note

Remap cost per thrown stack: one map lookup per frame (microseconds — maps cached per file after first throw). Hot-path exception handling (exceptions-as-control-flow, already an anti-pattern) pays remap per throw — but the fix is throwing less, never unmapping. Normal error rates: unmeasurable.

### Mentor note

Demonstrate mapping by throwing deliberately in front of mentees (the fixture above, both modes, same output) — then ask "which package did that?" (`npm ls` reveals it). Engineers who know the remapper exists debug unmapped frames as *pipeline* failures (part of [1.2](<./1.2. Reading mapped stack traces.md>)) instead of mysteries.

## 2) `--enable-source-maps` is redundant-but-harmless

### 2) **Definition** (the two remappers)

Node's `--enable-source-maps` remaps stacks through `sourceMappingURL`-referenced maps (emitted `.js.map` files, bundler outputs); ts-node's bundled support remaps hook-compiled frames through inline maps. Under the hook, ts-node's remapper already translated every frame — Node's flag finds nothing left to translate (idempotent overlap, not conflict).

### What problem it solves (history, inverted — the confusion it prevents)

Teams migrating JS services (flag present in every script) to ts-node asked whether to keep it; teams reading Node docs wondered why hook traces map *without* it. Both questions dissolve: the flag governs Node's remapper (file-based maps), ts-node ships its own (inline maps) — overlapping coverage, zero interference, keep-or-drop both defensible.

### Modern guidance

Keep `--enable-source-maps` in scripts that also execute emitted/bundled code (mixed pipelines: hook for sources, `dist/` for artifacts — one flag covering the file-based half); drop it where ts-node compiles everything (no behavioral change — verified identical output below). Never *depend* on it for hook traces (the bundled support is the guarantee; the flag is belt-and-suspenders for the file-based remainder).

### Runnable example (good — flag changes nothing under the hook, verified)

```bash
node --enable-source-maps -r ts-node/register ./dbg/trace.ts
# /tmp/tsprobe/dbg/trace.ts:2
#   throw new Error("mapped?");
#         ^
# Error: mapped?
#     at boom (/tmp/tsprobe/dbg/trace.ts:2:9)
```

Byte-comparable to the flagless run (same file, line, column, context) — the flag added zero translations because none remained. Harmless to keep (future emitted frames in the same process still benefit), pointless to require (hook traces never needed it).

### Common confusion

- **"the flag double-translates"** — remappers are idempotent over already-mapped frames (mapped positions carry no further mapping to apply — second pass is a no-op, not a corruption). Double-*installation* of competing `source-map-support` copies corrupts; the Node flag plus ts-node's bundled support cooperates. Different failure classes — don't conflate them.
- **"future Node defaults change this"** — if Node ever defaults `--enable-source-maps` on (discussed upstream, per JS 15), hook traces stay identical (nothing left to translate). Default-flips affect file-based pipelines; inline-mapped hook output is already at the end state.

### Performance note

Flag cost under the hook: map-cache initialization Node performs regardless of hits (microseconds at boot) — unmeasurable beside compilation. Keep-or-drop decides nothing performance-wise; decide on coverage grounds (mixed pipelines keep, pure-hook drops or keeps freely).

### Mentor note

Use the flag question as a layering quiz: "which remapper handles hook frames? which handles `dist/` frames?" Mentees answering "bundled / Node flag" own the two-remapper model; mentees answering "the flag does everything" get the verified pair above (identical output, flag on/off) — evidence beats assertion, again.

## 3) Transpile-only maps identically

### 3) **Definition** (erasure preserves positions)

Transpile-only deletes type annotations without moving code (erasure, not transformation): line N in source remains line N in output, columns shift only by deleted annotation widths on the same line. The inline map is therefore near-identity — and mapped traces match full-mode traces frame-for-frame (verified identical above). Checking never participated in positioning.

### What problem it solves (history)

Early fast-execution paths (Babel-strip pipelines, naive transpilers) *did* shift lines (helper injection, statement rewriting), teaching a generation that "fast means unmappable." TypeScript's isolated transpile preserves layout closely enough that the folk belief is now wrong — but beliefs outlive their causes, so the identical-traces proof exists to retire it per repo.

### Modern guidance

Trust transpile-only traces exactly as full-mode traces (same maps, same fidelity — the mode split from [01/2.1](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>) has no observability dimension). Investigate *column* drift on heavily-annotated single lines (deleted types shift same-line columns — rarely material, occasionally confusing in dense generics); line numbers — the triage currency — never drift under erasure.

### Runnable example (good — the identity proof, quoted)

```bash
# full mode:     at boom (/tmp/tsprobe/dbg/trace.ts:2:9) / at run (/tmp/tsprobe/dbg/trace.ts:6:3)
# transpile-only: at boom (/tmp/tsprobe/dbg/trace.ts:2:9) / at run (/tmp/tsprobe/dbg/trace.ts:6:3)
# (verified outputs, both modes — frame-identical)
```

### Common confusion

- **"SWC/esbuild maps differ"** — third-party transpilers emit their own maps (same inline mechanism, different generator) — fidelity equivalent for erasable sources, occasionally divergent on heavy transforms (decorator lowering reorders). Map *problems* under `--swc` implicate the engine's map, not the mode — route accordingly (engine docs, not mode debates).
- **"decorators break mapping"** — legacy decorator emit *adds* helper frames (visible as extra stack entries — noise, not misattribution). Noisy ≠ wrong: the authored frames still name correctly; helpers are skipped by eye (or `skipFiles` in launch configs — [04/2.2](<../../../04 Development Workflow Watch REPL and Editors/sections/2. REPL and editors/2.2. Editor and debugger integration.md>)).

### Performance note

No performance dimension (map generation is a fixed fraction of transpile, paid identically in both modes — microseconds per file). The folk belief ("fast = unmappable") cost teams real checker-latency (full mode retained "for better traces" — paying seconds per run for zero fidelity gain). Retire the belief with the proof above; keep the seconds.

### Mentor note

When a team runs full mode "so stack traces stay accurate," show the identical pair and switch the loop to transpile-only the same day — with the checker moved to its own clock (the three-clocks wiring from [01/4.1](<../../../01 Execution Foundations and Mental Model/sections/4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>)). One demonstration, permanent latency win, zero observability cost.
