# 1.2. Reading mapped stack traces

How to read hook-produced stacks: authored frames vs runtime frames, what unmapped entries indict, and how async chains stitch through maps. Junior read: top frame names your bug, `.ts` lines are truth. Expert read: the frame taxonomy (mapped/user, unmapped/runtime, hook-internals) and the escalation each commands.

## 1) Frames name sources, not output

### 1) **Definition** (the mapped frame)

A mapped frame — `at load (/tmp/tsprobe/dbg/mixed.ts:4:13)` — names the authored file, line, and column: the position as written, not as executed. Columns count into the source line (generics-heavy lines shift under erasure — noted in [1.1](<./1.1. Sourcemaps under ts-node.md>) part 3, rarely material). Lines — the triage currency — are exact under both modes, verified across this domain's probes.

### What problem it solves (history)

Unmapped hook traces (eval-machine positions) made every throw a two-step investigation (find the generated line, mentally reverse the compile) — errors cost minutes before triage began. Mapped frames collapse it to zero steps: the trace *is* the source location. Reading skill shifted from reverse-compilation to frame taxonomy (which frames are yours, which are the platform's).

### Modern guidance

Read top-down: first *authored* frame (yours — the bug), then outward (callers — the path), skipping runtime frames (platform — context only). The error *message* line plus source snippet Node prints (`return fs.readFileSync…` with caret) usually suffices for `TypeError`/`ReferenceError` classes; deeper logic bugs need the caller chain (frames 2–5 — the route the bad value traveled).

### Runnable example (good — the mixed stack, annotated)

```bash
./node_modules/.bin/ts-node --transpile-only --project dbg/tsconfig.json ./dbg/mixed.ts
# /tmp/tsprobe/dbg/mixed.ts:4
#   return fs.readFileSync(p, "utf8");
#             ^
# TypeError: Cannot read properties of undefined (reading 'readFileSync')
#     at load (/tmp/tsprobe/dbg/mixed.ts:4:13)              ← authored (yours — READ HERE)
#     at Object.<anonymous> (/tmp/tsprobe/dbg/mixed.ts:7:13) ← authored (caller — the path)
#     at Module._compile (node:internal/modules/cjs/loader:1521:14) ← runtime (context — skip)
#     at Module.m._compile (/tmp/tsprobe/node_modules/ts-node/src/index.ts:1618:23) ← hook (context — skip)
```

Verified: authored frames carry `.ts` positions (4:13 the call, 7:13 the caller); runtime frames carry `node:internal` positions (loader context); hook frames name ts-node internals (compile context). Side-lesson, free: `fs` is `undefined` because default-importing a CJS builtin without `esModuleInterop` yields the namespace-less default — the interop rule from [NodeJS 01/2.2](<../../../../NodeJS/01 Runtime Fundamentals and Mental Model/sections/2. Process and modules/2.2. Modules in Node CJS and ESM interop.md>), surfacing uninvited (real codebases serve such two-for-ones constantly).

### Common confusion

- **"top frame is the bug"** — top *authored* frame is the bug (hook/runtime frames above it are machinery — `Module.m._compile` never contains your defect). Read past machinery to the first `.ts` frame; start there, always.
- **"column numbers are exact"** — lines exact, columns approximate on heavily-annotated lines (erasure deletes widths). Triage on lines (file:line locates uniquely); use columns as hints (position within long chains), never as proof.

### Performance note

No runtime dimension (reading skill, not execution cost). The cost axis is triage time: taxonomy readers (yours/path/context in one glance) resolve throws in minutes; flat readers (every frame equally suspicious) wander into internals per incident. One annotated example (above) trains the glance permanently.

### Mentor note

Annotate one real incident stack per mentee (arrows + YOURS/PATH/SKIP labels, as above) and keep it in the runbook. The annotated artifact converts abstract advice ("read top-down") into a reflex — mentees overlay the pattern on every future trace without thinking.

## 2) Unmapped frames indict the pipeline

### 2) **Definition** (the mapping-failure signal)

A frame naming *generated* positions inside a `.ts` run — `evalmachine.<anonymous>`,6613-style line numbers into concatenated output, or `.js` paths with no corresponding authored file — signals map loss *at a pipeline stage*, not a code bug. Maps drop at exactly three places: generation (transpiler emitted no/invalid map), registration (remapper not installed for the executing path — ESM/custom loaders bypassing ts-node's support), consumption (flag/tooling stripping `sourceMappingURL`).

### What problem it solves (history)

Unmapped frames were shrugged at (" TS stacks are just noisy") — normalizing a pipeline failure into folklore, and with it abandoning source-level debugging for `console.log` archaeology. Naming the three drop points converts folklore back into defects: each has a check, each check takes seconds, all three verified in [4.1](<../4. Important points to remember/4.1. Observability checklist habits mentors insist on.md>)'s gate.

### Modern guidance

On encountering an unmapped frame: (1) generation — which engine compiled this file (tsc? SWC? esbuild? — each owns its map fidelity; `--swc` map issues route to the engine); (2) registration — which hook loaded it (ts-node's CJS hook maps; ESM/custom-loader paths verify per floor — a custom `load` hook returning source *without* the map chain drops mapping for its files); (3) consumption — which tool renders the stack (some log shippers truncate `sourceMappingURL` context; raw `err.stack` always carries positions, formatted log lines sometimes don't).

### Runnable example (good — the healthy baseline to compare against)

```bash
# healthy: every authored frame maps (verified all session)
#     at boom (/tmp/tsprobe/dbg/trace.ts:2:9)
#     at run (/tmp/tsprobe/dbg/trace.ts:6:3)

# sick (shapes to recognize — diagnose per the three drop points):
#     at evalmachine.<anonymous>:6613:21   → generation/registration failure (no map consulted)
#     at run (/tmp/tsprobe/dist/run.js:4:17) → emitted file without co-shipped .map (consumption gap)
```

The healthy pair above is verified output (both modes); the sick shapes are the recognition vocabulary — any frame matching them escalates to pipeline diagnosis *before* code debugging (per the triage order in [3.1](<../3. Production triage/3.1. Triage order for TS services.md>): unmapped frames escalate immediately, mapping failure poisons every downstream reading).

### Common confusion

- **"noisy stacks mean broken maps"** — hook-internals frames (`Module.m._compile` at ts-node paths) are *healthy noise* (machinery context, correctly unmapped — internals have no `.ts` original). Broken maps show as *wrong positions for authored code*, not as extra frames. Noise ≠ failure; misattribution = failure.
- **"one unmapped frame ruins the trace"** — mixed stacks are normal (native frames, internals, hook machinery never map — verified in part 1's example). The defect is specifically *authored code* appearing unmapped. Taxonomy first (whose frame?), verdict second.

### Performance note

Diagnosis cost per unmapped frame: three checks (engine? hook? renderer?) at seconds each — against hours lost theorizing behavior from mispositioned frames. The gate in [4.1](<../4. Important points to remember/4.1. Observability checklist habits mentors insist on.md>) automates the healthy-baseline assertion (throw fixture, assert `.ts` frames) — pipeline regressions fail CI instead of confusing on-call.

### Mentor note

Keep a "rogues gallery" of unmapped-frame shapes with their drop-point diagnoses (evalmachine → registration; dist-without-map → consumption; shifted lines → engine). New on-call engineers match shapes before theorizing — pattern matching beats first-principles under pager pressure, every time.

## 3) Async stacks stitch through maps

### 3) **Definition** (composition of two remaps)

`--async-stack-traces` (default on) stitches `await` chains (caller frames across microtask boundaries); source-map support remaps each frame's position. Under the hook both apply: async TS functions rejecting show *stitched callers* at *mapped positions* — two orthogonal remaps composing transparently (documented interaction in JS 15/5.3's Q10, applied here to hook-compiled sources).

### What problem it solves (history)

Unstitched async traces ended at the await boundary (rejection in a helper named the helper, never the route that called it); unmapped stitched traces named concatenated positions across boundaries (worse — confident misdirection). The composition (stitch + remap) gives the full story: who called, across awaits, at authored lines — the minimum viable incident narrative for async services.

### Modern guidance

Write async TS normally (`await` chains, not `.then` forests — stitching follows `await`); read rejections top-down through stitched callers (each `.ts`-named — trust them equally, sync or async); keep `--async-stack-traces` default-on (disabling it amputates cross-boundary callers for zero gain). Promise-typed rejections without `await` in the chain still truncate (microtask reality — JS 15/5.2 owns the mechanics).

### Runnable example (good — the composition, described precisely)

```typescript
// route calls helper across await; helper throws: stitched + mapped
//     at helper (/srv/routes.ts:12:9)     ← throw site, mapped
//     at route (/srv/routes.ts:28:11)     ← stitched caller across await, mapped
//     at Layer.handle (node:internal/…)   ← runtime context, unmapped (normal)
```

Shape documented from the mechanism (stitch per JS 15, remap verified all session for sync frames): the composition follows from its parts — each frame independently mapped, the chain independently stitched. Teams verify per repo with one async fixture (reject across two awaits, assert both `.ts` frames present) — the checklist in [4.1](<../4. Important points to remember/4.1. Observability checklist habits mentors insist on.md>) includes it.

### Common confusion

- **"async stacks need the flag"** — `--async-stack-traces` defaults on (explicitly enabling it is harmless documentation, not a behavior change). Missing callers across awaits implicate *`.then` chains* (unstitchable by construction), not flags — rewrite to `await` before flag-hunting.
- **"mapped async frames cost more"** — remap cost per frame is identical sync/async (position translation doesn't know about boundaries). Async incident cost is *reading* cost (longer chains) — mitigated by the taxonomy from part 1 (yours/path/context), applied per stitched frame.

### Performance note

No execution cost (stack capture on throw only — zero-cost until rejection). Reading cost scales with chain depth (deep middleware stacks + ORM layers = long traces) — the taxonomy (skip runtime, follow authored callers) compresses them to the 3–5 frames that matter. Teach skipping, not scrolling.

### Mentor note

The async fixture (reject-across-awaits with asserted `.ts` frames) belongs in every repo's observability gate — it proves both remaps compose *in this pipeline* (custom loaders/transformers can break either half silently). One fixture, two guarantees, CI-enforced — the composition stops being assumed and starts being tested.
