# 3.1. Triage order for TS services

The incident order for hook-executed TypeScript: mapped logs first, profiles second, hook mechanics last — with unmapped frames short-circuiting everything and artifacts inheriting the method. Junior read: follow the order, don't skip steps. Expert read: why each stage exonerates a layer, and what each stage's failure commands next.

## 1) Logs first, profiles second, hooks last

### 1) **Definition** (the layer-exonerating sequence)

*Stage 1 — logs*: mapped stack (which `.ts` frame threw? — [1.2](<../1. Sourcemaps/1.2. Reading mapped stack traces.md>) taxonomy) exonerates or indicts code. *Stage 2 — profiles*: CPU/heap on the failing path (shape problem or volume problem? — [2.2](<../2. Inspector and profiles/2.2. CPU and memory profiles of TS services.md>) discipline) exonerates or indicts resources. *Stage 3 — hooks*: only when stages 1–2 implicate loading (wrong file executed, map missing, order suspect — Domains 02–03 mechanics). Each stage can close the incident; no stage is skipped to reach a later one.

### What problem it solves (history)

Cross-layer debugging (tuning the hook for a logic bug, profiling for a typo, re-reading config for a leak) wastes the incident's first hour reliably — every layer *can* explain any symptom vaguely, so undisciplined triage picks the most familiar layer instead of the indicted one. The order forces evidence per layer before moving: logs name code, profiles name resources, remainder names loading — what remains after exoneration is the suspect.

### Modern guidance

Runbook order, posted not remembered: (1) capture the mapped stack (first authored frame = prime suspect; unmapped = escalate per part 2, skipping the sequence); (2) reproduce under profiler if resource-shaped (slowness, growth, pressure — hypothesis first, per NodeJS 06); (3) inspect hook/config mechanics only with loading evidence (wrong file, missing map, order smell — trace lines and receipts decide). Close at the earliest exonerating stage — most incidents end at stage 1 (a `.ts` line number *is* the diagnosis).

### Runnable example (good — the order applied to this domain's own failures)

```bash
# incident: "hks: hooked-paths" never prints, Cannot find package '@app/util'
# stage 1 (logs): trace ABSENT — no [hook:resolve] line → not a mapping bug (mapper never saw it)
#   → skip code debugging entirely (nothing wrong with util.ts — verified in isolation)
# stage 2 (profiles): not resource-shaped (boot failure, not slowness) → skip
# stage 3 (hooks): order suspect → swap flags → trace present → prints. Closed at stage 3.
# total: one swap test, minutes — versus the config/specifier rabbit holes skipped
```

The S3 order investigation, replayed as triage: each stage's evidence (absent trace, non-resource shape, order hypothesis) routed past two wrong layers to the right one. The order works because stages *exclude* — exclusion is faster than search.

### Common confusion

- **"start with the most likely cause"** — likelihood without evidence is familiarity bias (hook experts blame hooks for typos; config experts blame pairs for leaks). The order replaces prior probabilities with staged evidence — slower to start, faster to close, always.
- **"skip logs for performance incidents"** — slowness still throws breadcrumbs (timeout errors with stacks, pressure warnings with origins — mapped, named, free). Stage 1 costs seconds and occasionally closes perf incidents outright (a stack pointing at the accidental `await`-in-loop beats a profile to the same conclusion by an hour).

### Performance note

Triage speed compounds per stage skipped correctly (each exoneration eliminates a layer's worth of investigation — minutes to hours). The order's cost is discipline (resisting the familiar layer); its payoff is mean-time-to-diagnosis (staged evidence converges monotonically — every reading narrows, never widens).

### Mentor note

Run incident game-days with the order enforced (stage-1 evidence required before stage-2 tooling touches the system): participants feel the slowdown of discipline once, then the speedup of convergence thereafter. The runbook page carries the order; the game-day carries the conviction. Both required; neither sufficient alone.

## 2) Unmapped frames escalate immediately

### 2) **Definition** (the short-circuit rule)

Any authored-code frame appearing unmapped (evalmachine positions, wrong-file attributions, shifted lines beyond erasure tolerance) suspends the normal order: mapping failure poisons logs (stage 1 unreadable), profiles (stage 2 unattributable), and judgment (every reading suspect) — fix the map pipeline first ([1.2](<../1. Sourcemaps/1.2. Reading mapped stack traces.md>) part 2's three drop points), then resume triage from stage 1 with trustworthy evidence.

### What problem it solves (history)

Teams triaged from mispositioned stacks for hours (fixing the wrong lines, profiling the wrong functions — every conclusion drawn from false positions, all motion, no progress) because "noisy TS stacks" folklore normalized the corruption. The short-circuit rule reclassifies unmapped frames from *noise* to *blocker*: triage halts, pipeline heals, then triage restarts on truth.

### Modern guidance

Detect via the gate (throw fixture asserting `.ts` frames — [4.1](<../4. Important points to remember/4.1. Observability checklist habits mentors insist on.md>) automates it, failing CI on pipeline regression); diagnose via the three drop points (engine? hook? renderer? — seconds each); resume only after the fixture greens. During live incidents: one unmapped authored frame → stop theorizing behavior, start diagnosing maps — announce the pivot explicitly ("stacks untrusted, fixing maps first") so the team follows.

### Runnable example (good — the pivot, narrated)

```bash
# incident stack shows: at evalmachine.<anonymous>:6613:21  (authored code expected)
# pivot announced: "stacks untrusted — maps before behavior"
# drop-point sweep: engine (tsc? SWC? — same as last green) → hook (custom load added Tuesday — SUSPECT)
#   → load hook returns source without map chain (envelope rebuilt, not spread — [03/2.2](<../../../03 ESM CJS and Loader Hooks Deep Dive/sections/2. Custom hooks/2.2. Authoring a load hook.md>) part 2's bad pattern, live)
# fix: spread envelope → fixture greens → resume triage at stage 1 (mapped, trustworthy)
```

Constructed from this track's verified pieces (envelope rule from 03/2.2, drop points from 1.2, gate from 4.1): the pivot narrative shows how the rules compose under pressure — each citation a decision, each decision evidenced. Real incidents rhyme with this shape; the runbook carries the verse.

### Common confusion

- **"one bad frame, continue anyway"** — a single mispositioned authored frame invalidates *positional* reasoning globally (which other frames lie? — unknowable without the pipeline fixed). Healthy noise (internals, hook machinery — correctly unmapped) continues fine; *authored* misattribution halts everything. Taxonomy first ([1.2](<../1. Sourcemaps/1.2. Reading mapped stack traces.md>) part 1), pivot second.
- **"escalate means page someone"** — escalate means *reorder* (maps before behavior — same responders, different sequence). Paging the map owner helps (hook authors know their envelope discipline); paging up the hierarchy doesn't. Escalation is technical (sequence change), not organizational (rank change).

### Performance note

Pivot cost: minutes (three drop-point checks) against hours of false-position triage (every conclusion suspect, most wrong). The gate amortizes it to zero (CI catches pipeline regressions pre-merge — incidents never meet unmapped frames). Prevention (gate) beats pivot (discipline) beats folklore (hours) — invest in that order.

### Mentor note

Drill the pivot call explicitly ("stacks untrusted" — said aloud, incident channel, timestamped): teams that announce pivots follow them; teams that think pivots privately fragment (half the room still theorizing behavior). Incident communication is a skill with a script — write the script down, rehearse it calm, execute it paged.

## 3) Artifacts profile like sources

### 3) **Definition** (production parity of method)

Production runs artifacts (`dist/` + shipped maps — Domain 06), not hooks — but the triage method transfers unchanged: mapped stacks (via co-shipped `.js.map` + `--enable-source-maps`), attributed profiles (same flags against `node dist/`), same three stages, same short-circuit rule. The execution differs (emit vs hook); the observability contract doesn't (source-named evidence everywhere).

### What problem it solves (history)

"Works in dev, blind in prod" (rich hook traces locally, minified positions in production — two observability regimes, on-call fluent in neither under pressure) trained teams to fear production incidents specifically. Artifact+map parity unifies the regimes: the same reading skills, the same gate shapes, the same runbook — dev practice transfers to prod directly because the evidence looks identical.

### Modern guidance

Ship maps with artifacts (`.js.map` beside `.js`, `sourceMap: true` in build configs — Domain 06 owns the mechanics); run production Node with `--enable-source-maps` (the flag's home turf — file-based maps, per JS 15); profile production-shaped load in staging with identical flags (prod parity per NodeJS 06). The dev/prod evidence gap closes to zero by construction — verify with the same throw fixture against `dist/` (mapped `.ts` frames or the pipeline is broken there too).

### Runnable example (good — the parity check, described)

```bash
# staging parity probe (shape — Domain 06 owns the build producing dist/):
node --enable-source-maps ./dist/trace.js
# at boom (/srv/src/trace.ts:2:9)   ← emitted code, shipped maps, same authored positions
```

Parity means the S-dev reading skills (taxonomy, drop points, order) apply unmodified to prod evidence — one skill set, both regimes. The probe belongs in deploy pipelines (post-deploy smoke asserting mapped frames from `dist/`) — the artifact twin of [4.1](<../4. Important points to remember/4.1. Observability checklist habits mentors insist on.md>)'s hook fixture.

### Common confusion

- **"hook observability doesn't transfer"** — stages, taxonomy, and order transfer verbatim (this leaf); only map *transport* differs (inline under hook, files under emit — [1.1](<../1. Sourcemaps/1.1. Sourcemaps under ts-node.md>) parts 1–2). Transport is plumbing; method is skill — plumbers differ per regime, skills carry over.
- **"shipping maps leaks sources"** — maps reference sources (consumers navigate *if* sources ship/ sourcemapped — TS 12/3.1's declarationMap wisdom, same shape). Internal services: ship freely (observability wins); public artifacts: weigh exposure (private symbol maps, access-gated) — the decision is per audience, never a reason to fly blind in prod.

### Performance note

Artifact profiling costs what hook profiling costs (same flags, same sampling) minus compile variance (deterministic bytes — cleaner baselines, tighter before/after deltas). Staging parity runs cost one deploy-shaped rehearsal per pipeline change — against prod incidents triaged with dev skills (minutes vs hours). Parity pays per incident, forever.

### Mentor note

Require staging evidence in incident reviews ("show me the mapped staging stack") alongside production timelines — teams practicing parity produce both reflexively; teams without it produce timelines with unmappable positions attached. Review artifacts shape future behavior: ask for mapped evidence, get mapped pipelines.
