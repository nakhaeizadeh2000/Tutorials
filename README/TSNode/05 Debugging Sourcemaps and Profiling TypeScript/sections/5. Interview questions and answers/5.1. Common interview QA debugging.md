# 5.1. Common interview QA: debugging

Canonical answers for the three observability questions every TypeScript-on-Node interview asks, plus rapid-fire drills. Junior read: memorize the diagnoses. Expert read: each answer pairs the symptom with its *verified reproduction* from this domain — evidence first, conclusion as confirmation.

## 1) "Stack shows compiled JS, not TS" — diagnose it

### 1) **Definition** (the map-pipeline screen)

Authored code appearing at generated positions (evalmachine lines, `dist/` lines without source context) — screens for pipeline thinking: hires enumerate the three drop points (generation? registration? consumption? — [1.2](<../1. Sourcemaps/1.2. Reading mapped stack traces.md>) part 2) and check each in seconds, instead of debugging code from false positions. Symptom readers fail; pipeline readers pass.

### What problem it solves (hiring signal)

Unmapped stacks are the observability incident that corrupts all downstream judgment (every conclusion drawn from false positions is suspect) — engineers who recognize pipeline failure on sight halt and repair; engineers who don't theorize behavior for hours. The question predicts incident competence directly: evidence triage under corrupted evidence.

### Modern guidance

Answer as a checklist with the verified baseline: healthy hook traces name `trace.ts:2:9`-style positions in both modes without flags (quoted verbatim); deviations route by drop point (engine maps? hook registration? renderer truncation?); the gate fixture ([4.1](<../4. Important points to remember/4.1. Observability checklist habits mentors insist on.md>) stage 50) proves the pipeline per repo. End unprompted with the short-circuit rule ([3.1](<../3. Production triage/3.1. Triage order for TS services.md>) part 2 — maps before behavior): process knowledge, not just diagnosis.

### Runnable example (good — healthy vs sick, quoted)

```bash
# healthy (verified both modes): authored positions, source context
#     at boom (/tmp/tsprobe/dbg/trace.ts:2:9)
#     at run (/tmp/tsprobe/dbg/trace.ts:6:3)

# sick shapes (recognition vocabulary):
#     at evalmachine.<anonymous>:6613:21  → generation/registration (no map consulted)
#     at run (/tmp/tsprobe/dist/run.js:4:17) → emitted without co-shipped .map (consumption)
```

A hire narrates which drop point each sick shape indicts *before* proposing fixes; the interviewer scores the routing, not the remedy (remedies are lookups once routed). Follow-up ("hook-internals frames present?"): healthy noise (correctly unmapped machinery — [1.2](<../1. Sourcemaps/1.2. Reading mapped stack traces.md>) part 1), not signal.

### Common confusion (in candidates)

- **"add --enable-source-maps"** — yellow flag as a *first* move: harmless under the hook (verified no-op) but fixes nothing when the drop is generation/registration-side. Strong candidates diagnose the drop point first, prescribe second; flag-first candidates prescribe before diagnosing.
- **"TS stacks are just noisy"** — red flag: folklore normalizing pipeline failure (the attitude this domain exists to retire). Noisy-internals tolerance is fine; authored-misattribution tolerance is disqualifying-adjacent — the distinction is the screen.

### Performance note

No performance content (correctness incident) — candidates mentioning overhead here are filling air. The priced dimension is triage corruption (false positions → false conclusions → wrong fixes shipped). Say exactly that; stop.

### Mentor note

Rehearse with sick-shape flashcards (three shapes, three drop points, thirty seconds): recognition speed is the skill (pattern matching under pager pressure beats first-principles every time). Graduates match-then-route without pausing; near-misses theorize code from evalmachine lines — correct the layer, not the person.

## 2) "Production is slow — profile what, how?" — answer with discipline

### 2) **Definition** (the flame-first screen)

"Service is slow, what do you do?" — screens for hypothesis-driven profiling: hires state a hypothesis first (which path? under what load?), profile that path (`--cpu-prof` on the entry, short capture), read self-time (widest boxes), fix shapes, re-profile with numbers. Tool-namers ("I'd use clinic/0x") without hypotheses fail; method-followers pass with any tooling.

### What problem it solves (hiring signal)

Performance work without discipline optimizes cold code (days spent, nothing improved) or ships regressions disguised as fixes (no before/after numbers). The flame-first method (NodeJS 06's discipline, transferred in [2.2](<../2. Inspector and profiles/2.2. CPU and memory profiles of TS services.md>) part 3) is the only reliable converter of effort into latency — the question measures whether the candidate owns the converter.

### Modern guidance

Answer in method order with the verified proof: flags compose with the hook transparently (`--cpu-prof --cpu-prof-dir --cpu-prof-name` + `-r` — verified 5940-node valid profile attributed to `busy.ts` with `hot` frames); viewers read `.ts` flames directly (no map-chasing); heap profiles pair for growth symptoms (CPU-hot + heap-growing = leak doing work); receipts close every fix (before/after self-time in the commit — unmeasured "fixes" are hunches). Type-specific smells volunteered (decorator density, barrel megamorphism) show depth; method shows competence — both scored.

### Runnable example (good — the proof, quoted)

```bash
TS_NODE_PROJECT=dbg/tsconfig.json node --cpu-prof --cpu-prof-dir dbg/prof --cpu-prof-name busy.cpuprofile -r ts-node/register ./dbg/busy.ts
# hot: 1885617375 — program correct, profile valid (5940 nodes),
# 'hot' frames present, urls: {file:///tmp/tsprobe/dbg/busy.ts}
```

A hire quotes attribution as the payoff ("frames name my sources — no map step") and pairs heap for growth ("same shape, `.heapprofile` beside it"); the interviewer hears toolchain fluency plus method discipline in one breath. Follow-up ("profile production directly?"): brief captures in staging, never always-on in prod (sampling overhead + artifact volume — [2.2](<../2. Inspector and profiles/2.2. CPU and memory profiles of TS services.md>) part 1).

### Common confusion (in candidates)

- **"profile the idle server for a baseline"** — red flag (NodeJS 06's canonical bad: idle profiles show event-loop wait, not work — baselines come from known-good *load*, never idleness). Method literacy tested in one sentence.
- **"TS needs special profiling tools"** — yellow flag: V8 profiles executing code (language-agnostic); maps translate presentation (automatic). Toolchain FOMO wastes evaluation cycles — the standard tools already name sources ([2.2](<../2. Inspector and profiles/2.2. CPU and memory profiles of TS services.md>) part 3).

### Performance note

The numbers *are* the answer (5940 nodes, `hot` frames, `.ts` URLs — quoted above; re-measured per repo). Strongest form: method order + proof quote + receipt requirement ("before/after in the commit or it didn't happen"). Evidence volunteered with sources beats evidence extracted; ranges beat points.

### Mentor note

Mock with "the batch path takes twice its budget" — demand hypothesis + flag command + reading plan before any fix talk. Mentees graduate when profiling precedes prescription without prompting — the discipline outlives every tool (flags change yearly; hypothesis-profile-fix-receipt never does).

## 3) "Who owns a wrong line number?" — layer attribution (plus rapid-fire)

### 3) **Definition** (the ownership screen)

"A trace names the wrong line — checker? hook? maps? editor? whose bug?" — screens for layer attribution: hires route by evidence (reproduce under the other mode? compare emit? check the gate fixture?) and assign ownership per layer (engine maps, hook registers, renderer truncates, editor presents). Single-owner answers ("the sourcemaps are broken") fail the attribution; routed answers pass.

### What problem it solves (hiring signal)

Wrong-position reports bounce between teams (compiler people, hook people, editor people — each unable to reproduce in isolation) until someone attributes by layer with evidence. The question predicts cross-team debugging effectiveness: owners route, tourists bounce. Every org has the bouncing version of this incident quarterly; hires should be the routing version.

### Modern guidance

Answer as a decision tree: same wrongness in both modes? (yes → engine maps; no → mode-specific path) / wrong in file but right in REPL? (entry config vs CWD discovery — [04/2.1](<../../../04 Development Workflow Watch REPL and Editors/sections/2. REPL and editors/2.1. The ts-node REPL.md>)) / wrong only under custom loader? (envelope discipline — [03/2.2](<../../../03 ESM CJS and Loader Hooks Deep Dive/sections/2. Custom hooks/2.2. Authoring a load hook.md>) part 2) / wrong only in log shipper? (renderer truncation — raw `err.stack` decides). Each branch ends in an owner *and* a verification (fixture, swap, raw output) — attribution with proof, never blame with confidence.

### Runnable example (good — the tree, walked on this domain's evidence)

```bash
# symptom: at run (.../trace.ts:9:3), authored call at :6
# branch 1 — both modes? transpile-only shows :6:3, full shows :9:3 → mode-specific path (checker-influenced emit)
# branch 2 — custom loader in play? yes (added Tuesday) → envelope suspect ([03/2.2] spread rule)
# branch 3 — raw err.stack vs shipped line? raw correct → renderer truncates (shipper drops context)
# (constructed walk — the method, not an incident: attribution by elimination with a check per branch)
```

### Rapid-fire drills (with answers)

1. **Hook traces map without flags — which package?** `@cspotcode/source-map-support` bundled under ts-node (verified via `npm ls`) ([1.1](<../1. Sourcemaps/1.1. Sourcemaps under ts-node.md>)).
2. **Transpile-only traces differ from full — true?** False (verified frame-identical — erasure preserves positions) ([1.1](<../1. Sourcemaps/1.1. Sourcemaps under ts-node.md>)).
3. **`--inspect-brk` silence — hung or paused?** Paused pre-first-line (verified: listener without output — attach or kill) ([2.1](<../2. Inspector and profiles/2.1. Inspector against compiled code.md>)).
4. **Gate exits 50 vs 51 vs 52 — meaning?** 50: unmapped frames (pipeline); 51: profile failed (path/flags); 52: unattributed profile (map gap in profiler) ([4.1](<../4. Important points to remember/4.1. Observability checklist habits mentors insist on.md>)).
5. **Heap grows, CPU cold — leak class?** At rest (listeners/timers/registries — snapshot-diff names the retainer; profile locates weakly) ([2.2](<../2. Inspector and profiles/2.2. CPU and memory profiles of TS services.md>)).
6. **Prod stack names `dist/` lines — fix?** Ship `.js.map` + `--enable-source-maps` (artifact parity — same reading skills, file transport) ([3.1](<../3. Production triage/3.1. Triage order for TS services.md>)).

### Common confusion (in candidates)

- **"the hook owns all mapping"** — hook owns *hook-executed* mapping (inline); emit owns *artifact* mapping (files); renderer owns *presentation* (truncation). Three owners, three verifications — single-owner answers skip two checks and usually blame the wrong layer.
- **"positions are always exact"** — lines exact (erasure), columns approximate (deleted widths), decorators noisy (helper frames). Precision claims per axis (line/column/frame) separate calibrated engineers from folklore carriers.

### Performance note

Attribution speed compounds per correct routing (right owner, first try — minutes) vs bounce latency (wrong owners serially — days across teams). The decision tree above is the accelerator: evidence per branch, owner per outcome, verification per claim. Routing skill is organizational performance.

### Mentor note

Timed rapid-fire (ten seconds each, autopsy misses against this domain): six-for-six is graduation — and the quarterly team health-check. Drills 3 and 4 separate evidence-tracers (pause semantics, exit-code narration) from reconfigurers; ask those first when time is short.
