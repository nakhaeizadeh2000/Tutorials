# 6.1. Boundaries: what is covered elsewhere

Where this domain stops and who owns the rest — the DRY map for observability. Junior read: if your question isn't answered here, this page names the page that answers it. Expert read: the layer-vs-mechanics split that keeps measurement knowledge in exactly one place per question.

## 1) Map, inspector, heap, and service mechanics (neighbor tracks own the machinery)

### 1) **Definition** (the layer/mechanics split)

*How source maps work, how the inspector protocol behaves, how V8 allocates and collects, how flamegraphs read, how services triage* are machinery — owned by neighboring tracks, assumed here, never restated. This domain owns the *TypeScript layer*: ts-node's bundled remap, mapped TS traces, inspector against hooked code, `.ts`-attributed profiles, TS-service triage order.

### Common confusion

- **"this domain should explain flamegraphs"** — explaining them here duplicates JS 19/NodeJS 06 in a third place, and triplicates drift. One-line mention plus link is the policy — DRY is correctness, not tidiness.
- **"layer without mechanics is shallow"** — the layer is where TS incidents live (unmapped authored frames, unattributed profiles, mode-specific map gaps) and mechanics can't see them (protocol-correct but source-blind). Depth here is measured in attributions, not internals.

### Mentor note

Teach mentees to read this page as a router: "machinery" questions go outward (JS 15/18/19, NodeJS 06), "attribution" questions stay here. The distinction resolves half of all observability debates before they start — most are machinery-questions asked in attribution-rooms ("how does sampling work?" during a "which frame is mine?" incident), or the reverse.

## 3) Config, hooks, workflow, and interview mechanics (neighbor domains own the ends)

### 3) **Definition** (the observing-everything boundary)

Observability watches *configured hooks* (01–03: modes, scopes, loaders) running in *daily loops* (04: watch, REPL, suites) — this domain owns neither end, only their evidence: traces, profiles, triage. Questions about what's observed go outward/backward; questions about the evidence stay here. The gate scripts (1–5) embody the boundary: each asserts one layer's observables.

### The assignments (with the exact targets)

- Modes, hooks, loaders, gates 1–3 → [01 Execution Foundations](<../../../01 Execution Foundations and Mental Model/README.md>), [02 Configuration](<../../../02 Configuration and tsconfig for Execution/README.md>), [03 Loader Hooks](<../../../03 ESM CJS and Loader Hooks Deep Dive/README.md>). Observability assumes all of them; their construction lives there.

### Common confusion

- **"an observability bug is a hook bug"** — observability fails in evidence vocabulary (unmapped frames, unattributed profiles, silent gates); hooks fail in chain vocabulary (`ERR_LOADER_CHAIN_INCOMPLETE`, missing traces, order throws). Debug the evidence first (fixture: which stage?), the hook second (trace present?) — the layer that failed names the half, per the stage-ordering habit.
- **"this track replaces its prerequisites"** — it assumes them (declared in every domain's `## 0. Prerequisites`). Maps name hook output; hooks compile scoped sources; scopes live in configs — readers without 01–04 read those first. Observability atop missing foundations misattributes everything.

### Mentor note

The one-sentence router for observability: "Machinery questions go outward (JS/NodeJS tracks), construction questions go back (01–04), *evidence* questions stay here." Traces/profiles/triage/gates — the evidence layer with its own craft, its own checklist, its own interview.
