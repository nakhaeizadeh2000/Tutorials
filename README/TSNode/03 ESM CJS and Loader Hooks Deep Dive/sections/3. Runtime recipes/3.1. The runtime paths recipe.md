# 3.1. The runtime paths recipe

The complete alias-without-packages implementation: explicit-extension checker mapping plus a resolve-hook runtime half, ordered mapper-before-compiler — fulfilling the forwards from [01/3.1](<../../../01 Execution Foundations and Mental Model/sections/3. Loading model/3.1. Loading TypeScript under CJS and ESM.md>) and [02/3.1](<../../../02 Configuration and tsconfig for Execution/sections/3. Paths runtime/3.1. paths and baseUrl that run.md>). Junior read: four files, two commands, aliases that execute. Expert read: why each ingredient is load-bearing, and the three closings priced against each other.

## 1) Checker mapping in, hook mapping out

### 1) **Definition** (the recipe's two halves)

*Checker half*: `paths` mapping the alias to an *explicit file* (`"@app/*": ["src/lib/*.ts"]` — extension included because ESM-mode checkers don't probe extensions, as the `TS2307` trace proved). *Runtime half*: a resolve hook mapping the same alias to the same file URL with `shortCircuit: true` ([2.1](<../2. Custom hooks/2.1. Authoring a resolve hook.md>)'s contract). Both halves name the same files; neither half knows the other exists; the entry works because both agree.

### What problem it solves (history)

[02/3.1](<../../../02 Configuration and tsconfig for Execution/sections/3. Paths runtime/3.1. paths and baseUrl that run.md>) closed the checker/runtime gap two ways (bridge package, erasure). The recipe is the third closing — no new dependency, no spelling change: the mapping the checker reads, re-implemented as the ten-line hook the runtime needs. Teams that can't add packages (locked installs, vendored trees) or won't rename imports get aliases that execute with stdlib-only machinery.

### Modern guidance

One hooks file per repo (`hooks/aliases.mjs` — shared by every entry), one `paths` entry per alias family (explicit extensions under ESM pairs, extensionless under CJS pairs — the checker half follows the pair's spelling rules), mapper flags on every aliased entry's command (order per [1.1](<../1. Hook pipeline/1.1. resolve and load the two-stage pipeline.md>) part 3, pinned in scripts). The recipe replaces `tsconfig-paths` where hook authorship is already in-house; it doesn't obsolete the package (fifteen aliases with regex families still favor the maintained implementation — build-vs-buy per mapping complexity).

### Runnable example (good — the four files, end to end)

```jsonc
// hks/tsconfig.json — checker half (explicit .ts: ESM mode probes nothing)
{ "compilerOptions": {
    "target": "es2022", "module": "NodeNext", "moduleResolution": "NodeNext",
    "strict": true, "baseUrl": ".", "paths": { "@app/*": ["src/lib/*.ts"] } },
  "include": ["src"] }
```

```typescript
// hks/src/main.ts — the alias, unchanged from the failing version
import { p } from "@app/util";
console.log("hks:", p());
```

```javascript
// hks/hooks.mjs — runtime half ([2.1](<../2. Custom hooks/2.1. Authoring a resolve hook.md>) contract)
if (specifier.startsWith('@app/')) {
  const file = path.join(LIB, specifier.slice('@app/'.length) + '.ts');
  return { url: pathToFileURL(file).href, shortCircuit: true };
}
```

```bash
./node_modules/.bin/tsc --noEmit --project hks/tsconfig.json && echo HKS-CHECK-OK
# HKS-CHECK-OK
TS_NODE_PROJECT=hks/tsconfig.json node --loader ts-node/esm --loader ./hks/hooks.mjs ./hks/src/main.ts
# [hook:resolve] @app/util -> /tmp/tsprobe/hks/src/lib/util.ts
# hks: hooked-paths
```

Verified end to end on Node v20.20.2 + ts-node v10.9.2: checker green (after the explicit-extension fix — the extensionless mapping died `TS2307`, diagnosed via `--traceResolution`), runtime green (trace + output). Four files, no new dependency, both resolvers agreeing.

### Common confusion

- **"the hook duplicates tsconfig-paths"** — it re-implements one mapping family (prefix → directory + extension) in ten lines; tsconfig-paths implements the full `paths` grammar (wildcards, fallbacks, conditions) maintained across releases. Recipe for one family, package for many — the boundary is mapping complexity, not philosophy.
- **"checker mapping and hook mapping can differ"** — they must agree *exactly* (same alias → same file), or the green check vouches for code the runtime never loads (or vice versa). Single source of truth would be ideal (generate one from the other — a build step Domain 06 could own); until then, change both in the same commit, verified by the two commands above run back-to-back.

### Performance note

Recipe overhead per aliased import: one prefix match + path join (microseconds) in resolve, zero in load (file URL flows into ts-node's normal pipeline). Cheaper than the bridge package (no extra dependency walk, no pattern-list scan) — though both vanish beside compilation. The performance argument for the recipe is dependency surface (stdlib-only), not speed.

### Mentor note

Assign the recipe as the capstone exercise for this domain: checker mapping (fix the `TS2307` first — trace included), hook mapping (contract from [2.1](<../2. Custom hooks/2.1. Authoring a resolve hook.md>)), order (swap until it prints — [1.1](<../1. Hook pipeline/1.1. resolve and load the two-stage pipeline.md>) part 3), all three verified live. Mentees completing it unaided own hooks; mentees needing hints reveal exactly which part to re-teach.

## 2) Mapper before compiler on the command line

### 2) **Definition** (the order pin)

Multi-loader invocations list the compiler first and mappers after (`--loader ts-node/esm --loader ./hooks.mjs`), so execution runs mappers → compiler → default (last-listed runs first — derived from the verified pair in [1.1](<../1. Hook pipeline/1.1. resolve and load the two-stage pipeline.md>)). The order is pinned in scripts, launch configs, and docs — flag sequence is load-bearing configuration, not cosmetic arrangement.

### What problem it solves (history)

Default intuition ("my hook listed first runs first") produces the reversed arrangement, which fails `Cannot find package` with the mapper demonstrably correct in isolation — the composes-alone-breaks-together mystery of [1.1](<../1. Hook pipeline/1.1. resolve and load the two-stage pipeline.md>) part 3. Pinning the verified order (plus the comment stating execution sequence) converts a derived-twice-per-incident fact into a recorded decision.

### Modern guidance

Every multi-loader command carries an order comment (`# runs: hooks.mjs → ts-node/esm → default`); every such command is verified by the swap test on toolchain upgrades (ten seconds: reverse, record, restore). Programmatic equivalents order identically (`register()` call sequence follows the same LIFO rule — mapper registered last runs first). Reviewers check flag order the way they check import order: mechanically, every time.

### Runnable example (good — the pinned command)

```bash
# package.json — order pinned, execution documented, trace proving it
{ "scripts": {
    "dev": "node --loader ts-node/esm --loader ./hooks/aliases.mjs ./src/main.ts"
    # runs: aliases.mjs (maps) → ts-node/esm (compiles) → default (loads)
} }
```

```bash
# verification: trace present means the mapper ran first
# [hook:resolve] @app/util -> /tmp/tsprobe/hks/src/lib/util.ts
# hks: hooked-paths
```

### Runnable example (bad — the tidied command)

```bash
# bad: "consistent flag ordering" applied by a well-meaning formatter —
# project hooks first, vendor second (reads naturally, runs broken)
node --loader ./hooks/aliases.mjs --loader ts-node/esm ./src/main.ts
# Error: Cannot find package '@app/util' ...
```

Verified failing (this session): natural reading order is reverse-execution order. The tidier "fixes" the arrangement into failure with zero functional diff — the most dangerous commit shape (looks like hygiene, behaves like sabotage). Fix: the order comment (mechanical protection) plus the trace assertion in the gate (part of [4.1](<../4. Important points to remember/4.1. Hooks checklist habits mentors insist on.md>)).

Why it hurts: failure vocabulary (`Cannot find package` — resolution) misdirects from the cause (sequence) toward specifiers and configs — every responder debugs the wrong half first. Fix the order, then fix the process that allowed reordering (comment + gate + review rule, all three).

### Common confusion

- **"one order works everywhere"** — order semantics are version-sensitive (chain-overhaul majors re-derive them — the v20 derivation above expires when the floor moves). The *practice* (pin + comment + swap-test on upgrade) is universal; the *arrangement* is per-toolchain. Never copy flag order between Node majors without re-verifying.
- **"programmatic registration avoids ordering"** — `register()` calls nest by the same LIFO rule (later call = outer = first) — same derivation needed, same pin required (call-sequence comment). No registration form escapes order; flags just make it visible.

### Performance note

Order has no performance content (same links, same work). Its cost is diagnostic when wrong and zero when pinned — the cheapest reliability practice in this domain (one comment) against the most misdirected failure (package-blaming for sequence causes).

### Mentor note

Include flag order in the team's "never tidy" list beside import side-effect order and CSS cascade order — sequences where arrangement *is* semantics. Mentees internalize it via the swap exercise (both orders, one prints) — derived knowledge survives; memorized rules get "cleaned up."

## 3) One recipe, every aliased entry

### 3) **Definition** (the convergence rule)

All aliased entries in a repo share one hooks file (or one hooks directory with a single registration point): new aliases extend the mapping table, never spawn new hook files. The recipe converges — N aliases, one implementation, one order pin, one trace format — instead of fragmenting per package, per team, per quarter.

### What problem it solves (history)

Per-package hook files drift exactly like per-package configs once did ([02/1.1](<../../../02 Configuration and tsconfig for Execution/sections/1. Config architecture/1.1. Base and delta tsconfigs.md>)'s extends lesson, one level down): three mappers with three trace formats, two order pins, one stale mapping nobody owns. Convergence applies the base-and-delta economics to hooks: shared table (base), per-entry pins (deltas), zero copies.

### Modern guidance

Structure: `hooks/aliases.mjs` (table + resolve), `hooks/transforms.mjs` (load transforms, if any), `hooks/register.mjs` (preload importing both — one `--import` for all entries). Mapping table data-driven (prefix → directory + extension rule, iterated — not one `if` per alias). New alias = one table row + checker `paths` row, same commit, both commands verified. Workers/children inherit via `NODE_OPTIONS=--import` (preload form travels in env where `--loader` chains tangle).

### Runnable example (good — the table, not the ifs)

```javascript
// hooks/aliases.mjs — data-driven: N aliases, one code path
import { pathToFileURL, fileURLToPath } from 'node:url';
import path from 'node:path';
const base = fileURLToPath(import.meta.url + '/..');
const TABLE = [
  ['@app/', './src/lib/', '.ts'],     // prefix → dir + extension rule
  ['@shared/', './packages/shared/src/', '.ts'],
];
export async function resolve(specifier, context, nextResolve) {
  for (const [prefix, dir, ext] of TABLE) {
    if (specifier.startsWith(prefix)) {
      const file = path.join(base, dir, specifier.slice(prefix.length) + ext);
      console.error(`[hook:resolve] ${specifier} -> ${file}`);
      return { url: pathToFileURL(file).href, shortCircuit: true };
    }
  }
  return nextResolve(specifier, context);
}
```

Shape verified (single-alias version executed all session; table generalization is iteration over the proven path — new rows verified by the same two commands as part 1, per row). Table reviewable in diffs; behavior uniform across aliases by construction.

### Runnable example (bad — hook sprawl)

```javascript
// bad: packages/api/hooks.mjs, packages/web/hooks.mjs, scripts/hooks.mjs —
// three mappers, two trace formats, one stale (@old/ still mapped, package deleted)
```

Why it hurts: mapping truth fragments (which file maps `@app/`? — answer varies by entry), fixes land in one copy (the other two rot), traces diverge (grep patterns per package). Fix: converge (one file, table-driven) and delete the copies — the migration is mechanical (merge tables, unify traces, re-pin orders) and auditable via the gate's per-entry trace assertion.

### Common confusion

- **"per-package hooks match per-package configs"** — configs scope *behavior per package* (different pairs legitimately); hook mappings declare *repo-wide spelling* (aliases mean the same everywhere or they mean nothing). Different scoping needs: configs diverge by package, mappings converge by repo. Conflating them fragments the vocabulary the config scoping was meant to serve.
- **"the table needs a DSL"** — prefix/dir/extension rows cover every alias family this track has met (exact-file overrides: one more column, same loop). DSLs arrive when conditions, versions, or environments enter mappings — until then, data beats language (readable in review, grepable in incidents).

### Performance note

Table scan per specifier: N prefix checks (nanoseconds × rows — hundreds of rows before measurability). Delegation silence for non-matches keeps the common path free. Convergence even *saves* hook-module loads (one file Parsed once vs N files) — trivially, but directionally right: unity is cheaper at every scale.

### Mentor note

Review new hook files with one question: "why isn't this a row in the shared table?" Valid answers (different stage, different lifecycle, genuinely conflicting semantics) are rare and interesting; invalid answers ("our package is special") reveal the sprawl instinct early. The shared table is infrastructure; treat additions like schema migrations (reviewed, tested per row, announced).
