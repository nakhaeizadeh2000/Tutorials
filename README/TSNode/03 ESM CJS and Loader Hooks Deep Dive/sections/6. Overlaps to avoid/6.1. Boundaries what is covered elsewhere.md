# 6.1. Boundaries: what is covered elsewhere

Where this domain stops and who owns the rest — the DRY map for hooks. Junior read: if your question isn't answered here, this page names the page that answers it. Expert read: the authorship-vs-contract split that keeps platform knowledge in exactly one place per question.

## 1) Hook API semantics and stability (Node.js docs own the contract)

### 1) **Definition** (the authorship/contract split)

*Signatures, accepted types, chaining rules, stability flags, deprecation schedules* are platform contract — owned by Node's `node:module` documentation, assumed here, never restated. This domain owns *authorship*: matching narrowly, decoding defensively, spreading envelopes, ordering deliberately, tracing sufficiently. Contract questions go to the docs; craft questions stay here.

### The assignments (with the exact targets)

- Hook signatures, formats, chaining, stability table → Node.js `node:module` docs (see LOG research notes — v26.10.0 semantics; local floor v20 executes the async subset only).
- ESM system mechanics (format determination, `type` field, conditional exports) → [NodeJS 01/2.2. Modules in Node](<../../../../NodeJS/01 Runtime Fundamentals and Mental Model/sections/2. Process and modules/2.2. Modules in Node CJS and ESM interop.md>). Hooks *customize* the system; the system lives there.
- Module forms and specifier grammar → [TypeScript 12: Modules and Declaration Files](<../../../../TypeScript/12 Modules Namespaces and Declaration Files/README.md>). Hooks rewrite specifiers; the grammar lives there.
- ts-node's own loader implementation (how ts-node/esm compiles, its resolve passthrough) → ts-node "How it works" docs (see LOG research notes). This domain *composes around* ts-node's loader; its internals live there.
- Hook operation (doors, config scoping, mode interplay) → [01 Execution Foundations](<../../../01 Execution Foundations and Mental Model/README.md>) + [02 Configuration](<../../../02 Configuration and tsconfig for Execution/README.md>) (this track). This domain assumes all of it.

### Common confusion

- **"this domain should specify the hook signatures"** — signatures are version-sensitive contract (sync family didn't exist two majors ago; async deprecates now). Restating them here guarantees stale copies; linking guarantees current ones. Authorship patterns (match/map/delegate) survive majors; signatures don't.
- **"reading Node docs replaces this domain"** — docs specify the contract; this domain teaches the craft (order derivation, trace discipline, tax accounting, recipe convergence). Contract without craft produces correct-but-broken hooks (valid signatures, wrong order, silent threads). Both halves required.

### Mentor note

Teach mentees the two-bookmark rule: Node docs open for *signatures*, this domain open for *decisions*. Debugging starts at the decision bookmark (order? scope? shape?) and ends at the contract bookmark (exact field names) — direction matters, and novices reliably walk it backwards.

## 3) Config and runtime mechanics (neighbor domains own the ends)

### 3) **Definition** (the middle-layer boundary)

Hooks sit *between* configuration (which file governs, which pair compiles — Domains 01–02) and runtime (what Node does with the loaded module — Node.js track). This domain owns the middle: specifier-to-URL, URL-to-source, order, traces. Questions resolving upward ("which config?") go to 01–02; questions resolving downward ("what executes?") go to Node.js; questions about the passage stay here.

### The assignments (with the exact targets)

- Config architecture, pairs, specifiers, paths bridges → [01 Execution Foundations](<../../../01 Execution Foundations and Mental Model/README.md>) + [02 Configuration](<../../../02 Configuration and tsconfig for Execution/README.md>). The recipe *assumes* explicit-extension checker mappings and scoped pairs; their construction lives there.
- Workers, processes, clustering (hook inheritance across threads) → [NodeJS 05: Child Processes and Workers](<../../../../NodeJS/05 Child Processes Workers and Clustering/README.md>). Sync hooks' non-inheritance and preload-via-`execArgv` patterns execute there; the constraint is declared here ([1.2](<../1. Hook pipeline/1.2. register versus loader flags versus registerHooks.md>) part 2).
- Sourcemap/inspector mechanics (flags, DevTools workflow) → [JavaScript 15/5.3. Source maps workflow](<../../../../JavaScript/15 Error Handling and Debugging/sections/5. Debugging toolkit/5.3. Source maps Node inspector DevTools workflow and flags.md>). [Domain 05](<../../../05 Debugging Sourcemaps and Profiling TypeScript/README.md>) *applies* them to hooked/compiled output; the mechanics live there.

### Common confusion

- **"a hook bug is a config bug"** — hooks consume config (pairs, scopes) but fail in chain vocabulary (`ERR_LOADER_CHAIN_INCOMPLETE`, `Cannot find package`, missing traces). Debug the chain first (stages, order, trace), the config second (`--showConfig`) — the stage that failed names the half, per [1.1](<../1. Hook pipeline/1.1. resolve and load the two-stage pipeline.md>).
- **"this track replaces the Node.js track"** — it assumes it (declared in every domain's `## 0. Prerequisites`). Loaders customize Node's pipeline; understanding the pipeline precedes customizing it — readers without the Node module model read NodeJS 01/05 first.

### Mentor note

The one-sentence router for hooks: "Config questions go left (01–02), engine questions go right (Node.js), *passage* questions stay here." Resolve/load/order/trace — the middle layer with its own craft, its own checklist, its own interview.
