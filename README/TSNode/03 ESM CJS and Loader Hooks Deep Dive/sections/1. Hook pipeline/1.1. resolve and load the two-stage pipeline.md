# 1.1. resolve and load: the two-stage pipeline

Node's ESM loading is two stages — `resolve` (specifier → URL) then `load` (URL → source) — with user hooks chaining at each stage. Junior read: two functions, two jobs, in that order always. Expert read: the isolation proof that resolve runs without load, and why chain position becomes semantics when a link resolves eagerly.

## 1) resolve names the URL, load fetches the source

### 1) **Definition** (the two jobs)

`resolve(specifier, context, nextResolve)` answers *where*: it takes the import string plus the importing module's URL and returns an absolute URL (plus an optional format hint). `load(url, context, nextLoad)` answers *what*: it takes that URL and returns the source for Node to evaluate (plus the final format). Custom hooks implement either or both; default hooks do both when no customization intervenes. ts-node's ESM loader is a `load`-stage participant (compiling `.ts` sources) riding on default resolution — [01/3.1](<../../../01 Execution Foundations and Mental Model/sections/3. Loading model/3.1. Loading TypeScript under CJS and ESM.md>) operated it; this leaf opens it.

### What problem it solves (history)

Pre-hook Node resolved and loaded as one inseparable motion — teaching it a new specifier shape (aliases), a new source language (TypeScript), or a new origin (HTTPS) meant patching Node itself. Splitting the pipeline into two hookable stages (stabilized across Node 16→20 for async hooks, extended in-thread in 22.15+/23.5+) turned every such need into user code: match in `resolve`, transform in `load`, compose by chaining.

### Modern guidance

Debug in stage order, always: resolution failure (`Cannot find package`, `ERR_MODULE_NOT_FOUND`) means the `resolve` chain never produced a URL — look at specifiers and mappings, never at source transforms. Load failure (`ERR_UNKNOWN_FILE_EXTENSION`, `SyntaxError` at evaluate) means resolution succeeded and the bytes were wrong — look at formats and transforms, never at specifiers. The stage that failed names the half of the pipeline to inspect; crossing stages doubles every debugging session.

### Runnable example (good — resolve proven running without load)

```javascript
// hks/hooks.mjs — resolve-only hook: maps, never loads
import { pathToFileURL, fileURLToPath } from 'node:url';
import path from 'node:path';
const LIB = fileURLToPath(new URL('./src/lib/', import.meta.url));
export async function resolve(specifier, context, nextResolve) {
  if (specifier.startsWith('@app/')) {
    const file = path.join(LIB, specifier.slice('@app/'.length) + '.ts');
    console.error(`[hook:resolve] ${specifier} -> ${file}`);
    return { url: pathToFileURL(file).href, shortCircuit: true };
  }
  return nextResolve(specifier, context);
}
```

```bash
node --loader ./hks/hooks.mjs ./hks/iso.mjs
# [hook:resolve] @app/util -> /tmp/tsprobe/hks/src/lib/util.ts
# TypeError [ERR_UNKNOWN_FILE_EXTENSION]: Unknown file extension ".ts"
```

Verified on Node v20.20.2: the resolve hook fires (trace printed), produces the `.ts` URL, ends the resolve chain — and then `load` fails because no compiler participates. The failure is the proof: resolve completed *independently* of load. Add `--loader ts-node/esm` after it and the same URL compiles and prints (the recipe in [3.1](<../3. Runtime recipes/3.1. The runtime paths recipe.md>)).

### Runnable example (bad — one hook doing both jobs blindly)

```javascript
// bad: resolve hook that also reads and compiles (pseudo-pattern)
export async function resolve(specifier, context, nextResolve) {
  const url = (await nextResolve(specifier, context)).url;
  const source = await compileSomehow(url);   // resolve stage doing load's job
  cacheSomewhere(url, source);
  return { url, shortCircuit: true };
}
```

Why it hurts: stage confusion breaks chaining (downstream `load` hooks never see the source path they expect — caches disagree, formats mismatch), doubles I/O (read once here, read again in load), and defeats `shortCircuit` semantics (ending resolve early starves legitimate downstream resolvers). Fix: resolve returns URLs; load returns sources — each stage its job, composition preserved.

### Common confusion

- **"resolve returns the module"** — resolve returns a *URL string* (plus optional hints); no code is read, no format decided finally. The `load` hook "ultimately responsible for the final format" even when resolve hints one (per Node docs) — hints advise, loaders decide.
- **"ts-node/esm is a resolve hook"** — primarily a *load* participant (compilation) with a thin resolve passthrough (`.ts` extension handling, `.js`→`.ts` remap per "How it works"). Knowing which stage a link actually works in predicts how it composes — thin-resolve links compose anywhere, eager-resolve links demand position (part 3).

### Performance note

Resolve runs per specifier (cheap string work + maybe filesystem probes); load runs per module (I/O + transform). Custom resolve hooks add microseconds per import — invisible against compilation milliseconds. The performance rule is about *placement*, not speed: resolving eagerly (hitting disk in resolve) duplicates the load stage's I/O; mapping strings (no I/O) keeps resolve free. Map in resolve, read in load.

### Mentor note

Teach the split with the isolated failure above: run resolve-only, watch load fail, ask "which stage worked?" Anyone who answers "resolve — the trace proves it" owns the model; anyone who says "the hook is broken" conflates the stages. Five minutes, one command, permanent mental model.

## 2) Chains nest last-in-first-out

### 2) **Definition** (delegation or termination)

Every hook receives `nextX` — the subsequent link's hook, ending at Node's default. A link either *delegates* (`return nextResolve(specifier, context)`, optionally with modified arguments) or *terminates* (`return { url, shortCircuit: true }`). Returning a value without calling `nextX` and without `shortCircuit: true` throws — the chain defends itself against accidental breaks. Multiple registrations nest LIFO: for `register()` calls, later-registered runs first; each link sees the chain downstream of itself.

### What problem it solves (history)

Single-loader Node (`--loader` one file) forced monolithic hooks: alias mapping, TS compilation, and instrumentation fused in one module, unorderable and untestable in isolation. Chaining (Node 16.12+) decomposed them: ts-node compiles, your hook maps, the tracer instruments — each link developed, tested, and ordered independently, composed on the command line.

### Modern guidance

One concern per hook file (mapper maps, transformer transforms, tracer traces), composed explicitly per entry. Unrelated hooks share nothing (async family: separate thread, message channels for coordination — per docs; sync family: shared realm, still prefer explicit channels). Deregister sync hooks when their job ends (`hooks.deregister()` — async `register()` has no equivalent; process-lifetime commitment).

### Runnable example (good — mapper plus compiler, each delegating correctly)

```bash
# hooks.mjs resolve: maps @app/* (shortCircuit), delegates everything else (nextResolve)
# ts-node/esm: compiles .ts (load), passes everything else through
TS_NODE_PROJECT=hks/tsconfig.json node --loader ts-node/esm --loader ./hks/hooks.mjs ./hks/src/main.ts
# [hook:resolve] @app/util -> /tmp/tsprobe/hks/src/lib/util.ts
# hks: hooked-paths
```

Verified on Node v20.20.2 (chain-order semantics are version-sensitive across the loader overhaul — re-verify the pair on every Node major bump; the swap test takes ten seconds): the mapped specifier short-circuits resolve at the mapper; every other specifier (`node:…`, relative `./…`) delegates down to ts-node's resolve then default. The `.ts` URL flows into the load chain where ts-node compiles. Two files, two jobs, one output.

### Runnable example (bad — the swallowing link)

```javascript
// bad: returns a URL without shortCircuit (chain violation)
export async function resolve(specifier, context, nextResolve) {
  if (specifier.startsWith('@app/')) {
    return { url: pathToFileURL(mapped).href };  // no shortCircuit, no nextResolve
  }
  return nextResolve(specifier, context);
}
// Node throws: a hook that returns without calling nextX or shortCircuit
// is an accidental break until proven intentional
```

Why it hurts: the chain cannot distinguish "I handled it" from "I forgot to delegate" — so it treats both as errors, loudly. The throw is the guardrail working: `shortCircuit: true` is the author *declaring* termination. Fix: add the flag (three words) and the "error" becomes the design.

### Common confusion

- **"shortCircuit means skip remaining hooks"** — it means *end this stage's chain intentionally* (remaining downstream links don't run for this specifier/URL). Legitimate for terminal mappings (alias → file); wrong for observations (tracers must delegate, never terminate — a tracing hook with shortCircuit blinds every link below it).
- **"LIFO means last flag wins"** — LIFO orders *execution*, not *authority*: every link still runs (unless short-circuited upstream), each transforming or delegating in turn. "Wins" is the wrong verb — links don't compete, they nest.

### Performance note

Chain depth costs one function call per link per stage (nanoseconds) — depth is free. What costs is *work duplicated across links* (two links hitting disk for the same file, three links parsing the same source). Profile hook overhead per-link (timestamp at entry/exit during development) and keep each link's work disjoint: resolve maps strings, load reads once, transforms compose by spreading `...result`.

### Mentor note

Review every custom hook for the two-line contract: "delegates via nextX OR terminates via shortCircuit — show me which." Hooks failing the review don't run correctly by accident; they throw by design. The contract fits on a sticky note; enforce it like a type signature.

## 3) Position matters when links resolve eagerly

### 3) **Definition** (order as semantics)

Chaining theory says order shouldn't matter (every link delegates what it doesn't handle) — practice says otherwise when a link *resolves eagerly*: ts-node/esm's resolve attempts default resolution on the original specifier instead of delegating unknowns first, so an unmapped alias dies inside ts-node's link before reaching the mapper below it. Mapper-before-compiler on the command line is therefore not style but semantics.

### What problem it solves (history, inverted — the surprise it explains)

Teams chaining "ts-node first, ours second" (reading LIFO as "ours wins") met `Cannot find package '@app/util'` with the mapper demonstrably correct in isolation — the classic composes-alone-breaks-together mystery. The cause is architectural, not buggy: eager links consume specifiers they can't handle instead of passing them down. Position encodes the assumption "my link sees the original specifier" — true only upstream of eager links.

### Modern guidance

Order rule: *mappers and rewriters before compilers and instruments* — specifier-to-specifier links first, source-producing links last. Verify order empirically per toolchain (swap the flags, record which arrangement prints — arrangements are facts about link implementations, not opinions). Pin the working order in scripts and launch configs (flag order is reviewable; "it worked when I typed it" is not).

### Runnable example (good — both orders, verified, one prints)

```bash
# mapper BEFORE compiler: mapper rewrites, ts-node compiles the file URL
TS_NODE_PROJECT=hks/tsconfig.json node --loader ts-node/esm --loader ./hks/hooks.mjs ./hks/src/main.ts
# [hook:resolve] @app/util -> /tmp/tsprobe/hks/src/lib/util.ts
# hks: hooked-paths
```

Wait — read carefully: `--loader ts-node/esm --loader ./hks/hooks.mjs` prints, i.e. with these `--loader` flags the *first-listed runs last*?? Empirically: listing ts-node/esm first and hooks.mjs second works. So `--loader` flag order is *reverse* of execution (last flag = outermost = runs first) — consistent with LIFO nesting. The mapper (listed last) runs first, rewrites, compiler sees the file URL. The mental model holds: execution runs outermost-first; list compiler first, mappers later; execution then proceeds mappers → compiler.

### Runnable example (bad — the intuitive order, verified failing)

```bash
# mapper listed FIRST (intuition: "mine runs first") — actually runs LAST:
TS_NODE_PROJECT=hks/tsconfig.json node --loader ./hks/hooks.mjs --loader ts-node/esm ./hks/src/main.ts
# Error: Cannot find package '@app/util' imported from /tmp/tsprobe/hks/src/main.ts
```

Verified: ts-node/esm (listed second, running first) attempts the raw alias, default resolution fails, the mapper below never sees the specifier. Same files, same flags, reversed — one prints, one throws. Flag order is load-bearing; comments in `package.json` scripts should state the rule ("mappers list last, run first") so the next editor doesn't "tidy" it into failure.

Why it hurts: the failure blames the *package* (`Cannot find package` — a resolution vocabulary) for what is actually an *ordering* decision — misdirection toward specifiers and configs instead of flag sequence. Fix: list mappers after compilers; verify by swapping once and recording the working arrangement beside the script.

### Common confusion

- **"LIFO contradicts the working order"** — no: LIFO describes nesting (last-registered = outermost = runs first), and `--loader` flags register in listed order… then execute outermost-first, i.e. *last-listed runs first*. The verified pair above is LIFO behaving exactly as documented — intuition ("listed first runs first") is what contradicts it.
- **"programmatic register() composes differently"** — same LIFO rule (`register(foo); register(bar)` → bar outermost, runs first — per docs; verified pattern: the S2 probe's `register()` + flag composition printed correctly). One rule, all registration forms — learn it once.

### Performance note

Order has zero performance content (same links, same work, different sequence) — its cost is purely diagnostic when wrong (misdirected debugging toward packages and specifiers). The cheapest ordering practice: a one-line comment above every multi-loader invocation stating execution order ("runs: hooks.mjs → ts-node/esm → default"). Thirty characters preventing a thirty-minute misdiagnosis.

### Mentor note

Teach flag order with the swap exercise: run both arrangements, watch one print and one throw, derive LIFO from evidence rather than asserting it. Mentees who *derive* LIFO ("last-listed runs first, because the working order proves it") retain it; mentees who memorize it reverse it under pressure — usually while "tidying" a script.
