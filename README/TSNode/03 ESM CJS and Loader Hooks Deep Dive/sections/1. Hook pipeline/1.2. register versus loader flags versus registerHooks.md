# 1.2. register() versus loader flags versus registerHooks

Three ways to install hooks — `--loader`/`--import` flags, programmatic `register()`, and sync `registerHooks()` — one chain underneath. Junior read: three spellings, same result, pick by who launches the process. Expert read: the thread tax that separates them, the availability matrix per Node major, and the deprecation already moving beneath `register()`.

## 1) Three registrations, one chain

### 1) **Definition** (the installation forms)

*Flags*: `--loader ./hooks.mjs` (async family) or `--import ./preload.mjs` (a module that itself calls `register()`/`registerHooks()`) install hooks before application code loads — owning every entry including workers-by-default. *Programmatic*: `register('./hooks.mjs', import.meta.url)` inside the entry, with affected modules loaded via dynamic `import()` after (static imports evaluate before the call — same trap as [02/1.2](<../../../02 Configuration and tsconfig for Execution/sections/1. Config architecture/1.2. Monorepo configs and project scoping.md>)'s entry/config ordering). *Sync*: `registerHooks({ resolve, load })` installs in-thread functions directly — no hook module, no thread hop. All three feed the same chain semantics from [1.1](<./1.1. resolve and load the two-stage pipeline.md>).

### What problem it solves (history)

Each form exists because the launcher differs: flags serve terminals and scripts (visible, reviewable); programmatic serves libraries and harnesses (already running JS, unlocking TS imports from inside); `registerHooks` serves performance (in-thread, added v23.5/v22.15 when the async thread tax proved structural). One chain, three doors — the same triad shape as [01/1.2](<../../../01 Execution Foundations and Mental Model/sections/1. Execution identity and setup/1.2. Installing and running your first TypeScript file.md>)'s CLI/register/programmatic, one level down.

### Modern guidance

Terminals and npm scripts → flags (`--import` preload preferred over `--loader`: no deprecation warning, and preload files compose registrations explicitly). In-process harnesses → programmatic `register()` (then dynamic `import()` — never static imports of customized modules in the registering file). New code on supported floors → `registerHooks()` (sync, deregisterable). ts-node's own loader stays a `--loader ts-node/esm` flag (or its `register()`-form successor per Node's warning) — your hooks compose *around* it, never inside it.

### Runnable example (good — all three forms, same output)

```bash
# form 1 — flags: mapper hook + compiler hook composed on the command line
TS_NODE_PROJECT=hks/tsconfig.json node --loader ts-node/esm --loader ./hks/hooks.mjs ./hks/src/main.ts
# [hook:resolve] @app/util -> /tmp/tsprobe/hks/src/lib/util.ts
# hks: hooked-paths

# form 2 — programmatic: entry registers, then dynamically imports
# hks/prog.mjs: register("./hooks.mjs", import.meta.url) + await import("@app/util")
TS_NODE_PROJECT=hks/tsconfig.json node --loader ts-node/esm ./hks/prog.mjs
# [hook:resolve] @app/util -> /tmp/tsprobe/hks/src/lib/util.ts
# prog: hooked-paths

# form 3 — --import preload: registration before any application code
# hks/preload.mjs: register("./hooks.mjs", import.meta.url)
TS_NODE_PROJECT=hks/tsconfig.json node --import ./hks/preload.mjs --loader ts-node/esm ./hks/src/main.ts
# [hook:resolve] @app/util -> /tmp/tsprobe/hks/src/lib/util.ts
# hks: hooked-paths
```

All three verified on Node v20.20.2 + ts-node v10.9.2: identical mapping trace, identical output. The chain doesn't care how links arrived — only their order (mapper listed to run first — [1.1](<./1.1. resolve and load the two-stage pipeline.md>) part 3).

### Common confusion

- **"programmatic register() covers the entry's own static imports"** — never: static imports evaluate before any entry code runs, including the `register()` call (verified pattern in Node docs; same class as the config-before-entry rule). Customized modules load dynamically-after, or the entry itself launches behind a flag. Static-first is the most common programmatic-registration failure.
- **"`--loader` and `--import` are interchangeable"** — `--loader` installs a hook module directly (with the ExperimentalWarning steering toward `register()`); `--import` runs an arbitrary preload module (which may register hooks, set globals, configure tracing). Preloads compose (multiple `--import`s, explicit order); `--loader` chains (LIFO nesting). Prefer preloads for new wiring — they read as code, not flags.

### Performance note

Registration cost is one module load per hook file (once per process) — noise. The performance content lives in part 2 (thread tax per *hook invocation*, not per registration). Choose forms by launcher and lifecycle (deregisterable sync vs process-lifetime async), never by imagined startup deltas — all three cost the same single-digit milliseconds.

### Mentor note

Quiz door selection with one question (same as [01/1.2](<../../../01 Execution Foundations and Mental Model/sections/1. Execution identity and setup/1.2. Installing and running your first TypeScript file.md>), one level down): "who starts the process — you, a tool, or running code?" (you → flags; a tool → flags in its config or env; running code → programmatic). Mentees answering in one breath stop cargo-culting registration forms into the wrong launcher.

## 2) Async hooks pay the thread tax

### 2) **Definition** (the loader-thread caveats)

`module.register()`/`--loader` hooks run on a dedicated loader thread, not the application thread: no shared globals (coordination via `MessageChannel` + `data`/`transferList` through `initialize`), no effect on `createRequire` graphs or on `require()` calls inside the registering module, and CommonJS customization gaps (child modules of hook-processed CJS may bypass hooks; double-loading with monkey-patching hazards) — all documented in Node's async-hooks caveats. `registerHooks()` runs in-thread, same realm: plain function calls, shared state, no tax.

### What problem it solves (history, inverted — the cost it explains)

The async family's caveats read as arbitrary restrictions until the threading model explains them: separate thread ⇒ structured-clone-only communication ⇒ no globals; loader-thread evaluation order ⇒ registering-module blind spots; CJS's synchronous `require` graph ⇒ async interception gaps. Every caveat is the thread tax itemized. The sync family exists to abolish the tax where the platform allows (ESM-first flows, modern floors).

### Modern guidance

New hooks on Node ≥22.15/23.5: `registerHooks()` by default (simpler mental model, deregisterable, testable as plain functions). Async family where required (older floors, ts-node/esm itself, CJS-heavy graphs needing its specific coverage): design for the thread from day one — no globals assumed, `initialize` + message ports for coordination, integration tests asserting the CJS paths explicitly. Mixed chains (sync links + async links): sync runs first, then async — order your links accordingly (mappers sync-first where possible).

### Runnable example (good — proving which family you're in)

```bash
node -e "const m = require('node:module'); console.log('registerHooks:', typeof m.registerHooks, '| register:', typeof m.register)"
# registerHooks: undefined | register: function   (Node v20.20.2)
```

Verified: the floor check every hook file's header comment should encode. On v20 only the async family exists — every probe in this domain runs there (same family as ts-node/esm, so composition findings transfer). On ≥22.15 the sync family appears; on ≥25.9 the async family deprecates (part 3). Floors decide families; families decide design constraints.

### Runnable example (bad — globals across the thread boundary)

```javascript
// bad: async hook reading application-thread state
let mappingTable = {};
export function setMappings(t) { mappingTable = t; }  // called from app thread: SILENTLY INEFFECTIVE
export async function resolve(specifier, context, nextResolve) {
  if (mappingTable[specifier]) { /* never fires — hook sees its own thread's {} */ }
  return nextResolve(specifier, context);
}
```

Why it hurts: silence (no error — the hook runs correctly against an empty table), misattribution (mappings "ignored" → debugging the mapping logic instead of the thread boundary), and the fix requires architecture (ports + `initialize` data), not a patch. Fix: pass mappings via `register(hooks, { data })` → `initialize`, or hoist the table into the hook module's own scope (loaded once on the loader thread — module-level constants *are* shared, they just live there).

### Common confusion

- **"sync hooks are always better"** — where available, usually; but sync hooks don't inherit into workers by default (preload via `--import`/`--require` + `execArgv` inheritance covers it — per docs), and the ecosystem (ts-node/esm included) still ships async. "Better" is floor- and graph-dependent; the tax analysis decides per repo, not per fashion.
- **"the thread tax affects ts-node users"** — indirectly: ts-node/esm's async nature is why mapping hooks must precede it (eager link, [1.1](<./1.1. resolve and load the two-stage pipeline.md>) part 3) and why hook files stay dependency-free (loader-thread imports resolve through the very chain being built — keep hook modules lean: `node:` + `path` only).

### Performance note

Thread tax per hook invocation: structured-clone round-trips for coordination, cross-thread dispatch latency per resolve/load — microseconds that multiply by graph size (thousands of modules × two stages). Sync hooks collapse this to function-call cost. Measure on your graph (`--cpu-prof` boot profiles attribute loader-thread time separately) before rewriting working async hooks — the tax is real but rarely dominant beside compilation.

### Mentor note

Teach the thread with the globals exercise: set a global in the app, read it in an async hook, watch it arrive empty. One failed expectation, permanently calibrated intuition — cheaper than reading the caveats list twice. Then show the `initialize` + port pattern as the legitimate channel: constraints first, tools second.

## 3) Deprecation moves beneath you

### 3) **Definition** (the Stability-0 status)

As of the Node v26.10.0 documentation (current in the September 2026 era): `module.register()` is Stability 0 — Deprecated (deprecated v25.9.0, runtime deprecation DEP0205 enforced from v26), directing users to `module.registerHooks()`; sync hooks graduated to Release Candidate (v25.4/v24.13.1). The async family isn't removed — deprecated means "plan the migration," with runtime warnings marking every register() call on new floors.

### What problem it solves (history — why the platform moved)

A decade of async-only customization accumulated the caveats of part 2 as permanent tax; sync hooks (asked for since workers made threads visible) finally give the common cases an in-thread path. Deprecation is the platform collecting the debt: new code writes sync, old code migrates on its own schedule, warnings (not removals) enforce the direction.

### Modern guidance

Write `registerHooks()`-first with an async fallback where floors demand it: feature-detect (`typeof require('node:module').registerHooks`), branch once in a shared `hooks-entry` module, and keep hook *logic* (match/map/transform functions) family-agnostic so the migration swaps registration, not behavior. Pin the deprecation state per Node major in comments (`// register() path: remove when floor ≥ 22.15`) — deprecation timelines are the rarest documented tech debt, literally dated by the platform.

### Runnable example (good — the floor check as code)

```javascript
// bad (DO NOT COPY — trap demonstration): async fn inside registerHooks
const { registerHooks } = require('node:module');
const { matchAlias, mapToFile } = require('./alias-logic.cjs'); // family-agnostic
if (typeof registerHooks === 'function') {
  registerHooks({
    async resolve(specifier, context, nextResolve) { /* NEVER resolves in-thread */ }
  });
}
```

Why it fails: sync hooks must be *synchronous* functions — an async fn returns a promise the chain cannot await in-thread, so the mapping silently never applies (worse than throwing: silent). The honest version branches fully:

```javascript
// hooks-entry.cjs — correct: sync functions for registerHooks, async module for register()
const mod = require('node:module');
if (typeof mod.registerHooks === 'function') {
  mod.registerHooks({
    resolve(specifier, context, nextResolve) {
      if (specifier.startsWith('@app/')) {
        const { pathToFileURL } = require('node:url');
        return { url: pathToFileURL(mapToFile(specifier)).href, shortCircuit: true };
      }
      return nextResolve(specifier, context);
    }
  });
} else {
  mod.register('./hooks-async.mjs', require('node:url').pathToFileURL(__filename));
}
```

Untested-on-this-floor note, stated plainly: the sync branch above is written against the v26.10.0 documented contract but *cannot execute* on this session's Node v20.20.2 (`registerHooks: undefined` — verified); the async branch is the verified path (every probe in this domain). Migrating teams re-verify the sync branch on their floor before deleting the fallback — documented-shape code still earns its probe.

### Common confusion

- **"deprecated means removed"** — deprecated means *warned*: `register()`-based loaders (ts-node/esm included) keep working while warnings accumulate. Migration urgency is proportional to warning volume in your logs, not to the word "deprecated" — plan by quarters, panic never.
- **"sync hooks cover CJS identically"** — sync documentation explicitly extends to CJS graphs (in-thread interception reaches `require()` paths the async thread missed) — one of the migration's genuine payoffs, and a migration test to write: assert previously-bypassed CJS children now intercept.

### Performance note

Migration dividend: thread-tax removal per invocation (part 2's microseconds × graph size) plus deregistration (sync hooks release cleanly — long-lived processes with phased loading reclaim hook overhead; async hooks persist for process lifetime). Price the migration with a boot profile before/after; keep the printout with the commit that deletes the fallback.

### Mentor note

Track platform deprecations as dated tickets, not background anxiety: "register() DEP0205 — re-evaluate at Node 26 floor" with the version, the replacement, and the probe to re-run. Mentees learn platform citizenship from watching deprecations handled as scheduled work — the opposite of both panic-migration and ostrich-floor-pinning.
