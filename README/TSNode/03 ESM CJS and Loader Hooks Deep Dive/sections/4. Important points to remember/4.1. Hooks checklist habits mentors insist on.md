# 4.1. Hooks checklist (habits mentors insist on)

The three habits that keep custom hooks boring: trace evidence per mapping, pinned order per command, and explicit async-tax accounting. Junior read: extend the gate with two hook stages. Expert read: which incident each stage names, and why hook checks belong in CI rather than in developers' memories of flag order.

## 1) Trace proves the mapping

### 1) **Definition** (the evidence habit for hooks)

No loader debugging proceeds past the hook trace: `[hook:resolve] @app/util -> /…/util.ts` on stderr per mapping, asserted mechanically in the gate (exit 30 names its absence). [2.1](<../2. Custom hooks/2.1. Authoring a resolve hook.md>) established tracing as authorship discipline; this habit makes it operational evidence — quoted in bug reports, asserted in CI, grepped in incidents.

### What problem it solves (history)

Loader failures without traces produce narrative debugging ("I think the hook runs…", "the flags look right…") — descriptions of belief, not evidence. With traces, the same failures produce two decisive readings: trace present + wrong output = mapping bug (fix the table); trace absent = order/scope bug (fix flags/pins). The trace converts every loader incident into a two-branch decision tree before any human theorizes.

### Modern guidance

Gate stage 30 asserts the trace line per aliased entry (regex on stderr: `hook:resolve.*<alias>`); stage 31 asserts the program output. Bug template fields for loader failures: command + trace output + `--showConfig` (config half) — three evidences, zero narratives. Keep mapping traces committed and always-on (one line per rewrite); gate verbose full-chain tracing behind `HOOK_TRACE` for development only.

### Runnable example (good — the hook stages in the gate)

```bash
#!/bin/bash
# hooks gate: trace evidence + order pin, non-zero names the stage
OUT=$(TS_NODE_PROJECT=hks/tsconfig.json node --loader ts-node/esm --loader ./hks/hooks.mjs ./hks/src/main.ts 2>&1)
echo "$OUT" | grep -q "hook:resolve.*@app/util" || exit 30
echo "$OUT" | grep -q "hks: hooked-paths" || exit 31
echo HOOKS-GREEN
```

```bash
./gate3.sh; echo "exit=$?"
# HOOKS-GREEN
# exit=0
```

Verified: green on the pinned order. Reverse the flags and re-run — exit 30 fires (trace absent: the mapper never saw the specifier), naming the order failure without a human reading flag sequences. The gate stages compose with gates 1–2 (execution + config + hooks = the full pre-flight; merge into one script per [02/4.1](<../../../02 Configuration and tsconfig for Execution/sections/4. Important points to remember/4.1. Config checklist habits mentors insist on.md>)).

### Common confusion

- **"trace assertion is brittle"** — it asserts the hook's *contract* (this specifier maps to this file), not its formatting (regex on alias + arrow, tolerant of path prefixes). Contract assertions are the opposite of brittle — they break exactly when behavior changes, which is when you want breakage.
- **"stderr tracing pollutes logs"** — one line per mapped import at boot (dozens, namespaced, greppable) against log volumes in the millions. Pollution is a property of *verbose* tracing (every specifier, every link) — which stays behind `HOOK_TRACE`, off by default, as [2.1](<../2. Custom hooks/2.1. Authoring a resolve hook.md>) prescribed.

### Performance note

Two greps per gate run (milliseconds) over captured output — the cheapest stages in any gate script. Unconditional execution (not failure-only) is what makes the *next* failure debuggable: evidence collected routinely, consulted exceptionally.

### Mentor note

Pair with the pin check into a single loader pre-flight (trace + output + order-comment presence — the third via `grep -c "runs:" package.json`, if you formalize order comments). Onboard mentees by breaking the order deliberately and letting exit 30 teach [1.1](<../1. Hook pipeline/1.1. resolve and load the two-stage pipeline.md>) part 3 faster than any lecture.

## 2) Order pinned on every command

### 2) **Definition** (flag sequence as configuration)

Every multi-loader invocation pins its flag order in a reviewable artifact (script, launch config, documented command) with an execution-order comment (`# runs: aliases.mjs → ts-node/esm → default`). Order is configuration with semantics ([1.1](<../1. Hook pipeline/1.1. resolve and load the two-stage pipeline.md>) part 3 proved it); unpinned order is unreviewed configuration — drift waiting for a tidy-up commit.

### What problem it solves (history)

Reordered-by-hygiene failures (formatter, well-meaning contributor, "consistent flag sorting" lint) are loader incidents with zero functional diff — invisible in review, embarrassing in retrospect. Pinned order with comments converts reordering from silent sabotage into a visible diff against a stated rule: reviewers see the comment, the diff contradicts it, the commit gets questioned.

### Modern guidance

Comment every multi-loader command (execution order, outside-in); forbid flag-sorting lints on loader command lines (document the exemption with the verified pair as justification); re-verify order on every Node major bump (swap test, ten seconds — arrangement expires with toolchains). Programmatic registrations get call-sequence comments identically (LIFO applies to `register()` ordering too).

### Runnable example (good — the pin, the comment, the proof)

```jsonc
// package.json — order pinned and self-documenting
{ "scripts": {
    "dev": "node --loader ts-node/esm --loader ./hooks/aliases.mjs ./src/main.ts"
    // runs: aliases.mjs (maps) → ts-node/esm (compiles) → default (loads).
    // DO NOT REORDER (verified pair: reversed flags fail Cannot-find-package).
} }
```

```bash
# proof the pin holds (gate stage 30 doubles as the order assertion):
./gate3.sh; echo "exit=$?"
# HOOKS-GREEN — trace present means the mapper ran first
```

### Runnable example (bad — the sortable command)

```bash
# bad: no comment, alphabetical flags (reads clean, runs broken on this toolchain)
node --loader ./hooks/aliases.mjs --loader ts-node/esm ./src/main.ts
# Error: Cannot find package '@app/util' ...
```

Verified failing (this session, twice): alphabetical is reverse-execution here. The failure vocabulary (`Cannot find package`) misdirects toward specifiers — only the pin (and the trace assertion backing it) routes responders to sequence first. Fix the order, then fix the process (comment + gate + the lint exemption, all three).

### Common confusion

- **"comments rot"** — comments *describing intent* rot; comments *stating verifiable facts* get verified (the gate asserts the trace the comment predicts — comment and gate check each other). Rot-proof commenting means asserting the claim elsewhere, which stage 30 does.
- **"one order per repo suffices"** — order is per *command* (different entries compose different link sets: workers add tracers, tests add mocks). Each multi-loader command pins its own order; shared preload files ([3.1](<../3. Runtime recipes/3.1. The runtime paths recipe.md>) part 3's convergence) reduce the count, never the requirement.

### Performance note

Comments cost bytes; gate assertions cost milliseconds; reorder incidents cost hours with misdirection multipliers. The most asymmetric trade in this domain — one line preventing the most misdiagnosed failure class. Pin everything, verify on upgrade, never tidy blindly.

### Mentor note

Add flag order to the team's "never tidy" list (beside import side-effect order and CSS cascade) with the verified pair linked as justification. Newcomers encounter the list during onboarding; the list prevents the incident before the instinct forms. Cultural defenses beat technical ones for hygiene-shaped failures.

## 3) Async tax acknowledged

### 3) **Definition** (the constraints checklist)

Every async-family hook ships with its taxes declared: no shared globals (coordination via ports/`initialize` data), loader-thread module scope (lean hook modules: `node:` + `path` only), CJS coverage asserted by test (bypass paths probed, not assumed), process-lifetime persistence (no deregistration — phased loading designs accordingly). Declared constraints are design inputs; undeclared ones are incidents.

### What problem it solves (history)

Async hooks fail in ways that look like *logic* bugs (empty tables, missed modules, stale state) but are *topology* bugs (wrong thread, bypassed graph, persisted registration). Checklisting the taxes at authorship converts topology surprises into reviewed decisions: "globals unavailable — mappings live in-module" is a design line, not a 2 a.m. discovery.

### Modern guidance

Hook-file header comment enumerates the taxes it accepts (thread, scope, lifetime, CJS coverage) with the floor that imposes them (`// async family (Node 20 floor): no shared globals; mappings in-module; CJS children asserted in test/hooks-cjs.test.mjs`). Migration ticket dated per deprecation (`register()` → `registerHooks()` at floor ≥22.15 — [1.2](<../1. Hook pipeline/1.2. register versus loader flags versus registerHooks.md>) part 3). New hook PRs answer four questions (shared state? module scope? CJS paths? deregistration need?) before merge — the async-tax review, five minutes.

### Runnable example (good — the header that prevents incidents)

```javascript
// hooks/aliases.mjs — header (verified constraints, this domain's probes)
// Family: async (module.register/--loader — Node 20 floor; registerHooks at ≥22.15).
// Taxes accepted: (1) no shared globals — TABLE lives in-module;
// (2) lean imports only (node:url, node:path — loader-thread resolution);
// (3) CJS children coverage: N/A (ESM-only repo — asserted by absence of require());
// (4) process-lifetime registration (no deregister — single-phase boot).
// Migration: re-evaluate sync family when floor reaches 22.15 (ticket #…).
```

### Runnable example (bad — the unconstrained hook)

```javascript
// bad: no header, app-thread assumptions throughout
import { settings } from '../src/settings.js';  // app module in loader thread: chain-dependent
export async function resolve(specifier, context, nextResolve) {
  if (settings.aliases[specifier]) { /* works iff settings loads before the hook needs it — ordering luck */ }
  return nextResolve(specifier, context);
}
```

Why it hurts: app-module imports inside hook files resolve *through the chain under construction* (circular dependency by architecture: the hook needs the app it helps load). Works on lucky orderings, breaks on refactors — the failure arrives as "mappings ignored," debugged as logic, caused by topology. Fix: in-module table (self-contained hook files — the recipe's shape from [3.1](<../3. Runtime recipes/3.1. The runtime paths recipe.md>)), settings injected via `initialize` data if genuinely dynamic.

### Common confusion

- **"lean hook modules are premature minimalism"** — every non-`node:` import in a hook file is a module loaded on the loader thread through the nascent chain (failure modes multiply per import: version skew, side effects, ordering). Leanness is correctness insurance with a performance bonus, not aesthetic restraint.
- **"the checklist is bureaucracy"** — four questions, five minutes, per hook PR — against topology incidents measured in hours with misdirection. The checklist's cost is fixed and tiny; its payoff is the incident that never files. Bureaucracy is process without payoff; this is process *as* payoff.

### Performance note

Tax accounting has no runtime cost (comments and review minutes) — its performance dividend is avoiding the *wrong* optimizations (caching across threads, shared-state shortcuts that corrupt). Teams that acknowledge the thread design for message-passing from the start; teams that don't retrofit it after corruption. Direction matters more than speed here.

### Mentor note

The graduation review for this domain: hand the mentee an unconstrained hook (app imports, shared globals, no trace) and the four questions. Thirty minutes to a header-commented, self-contained, traced hook with a gate stage — each change citing its leaf. Fluency demonstrated, topology internalized, incidents prepaid.
