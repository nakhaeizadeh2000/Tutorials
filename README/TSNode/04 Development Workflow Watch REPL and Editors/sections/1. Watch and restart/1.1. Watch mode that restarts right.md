# 1.1. Watch mode that restarts right

`node --watch` composed with the ts-node hook: run, bounce, re-run — with the entry's whole graph watched and transpile-only inside. Junior read: one flag, restarts included. Expert read: what the watcher actually observes (graph, not file), and why the mode rule from 01 is load-bearing here of all places.

## 1) `node --watch` plus the hook

### 1) **Definition** (stdlib restart, hook-compiled)

`node --watch <entry>` re-executes the entry when watched files change; `-r ts-node/register` (or `NODE_OPTIONS`) installs the hook inside each fresh process. Composition is mechanical — the watcher restarts Node, Node installs the hook, the hook compiles — no plugin, no config file, one flag plus one hook. Watch *primitives* live in [JS 01/3.2](<../../../../JavaScript/01 Fundamentals and Mental Model/sections/3. Running JavaScript today/3.2. Node.js essentials running files REPL and version discipline.md>); this leaf owns the hook inside them.

### What problem it solves (history)

Save-and-rerun-by-hand (the `↑ Enter` loop) capped iteration speed and broke flow state; external restarters added dependencies for a platform capability (`--watch` stabilizing across Node 18→22). Composing the stdlib watcher with the register hook gives the loop with zero new packages: the two flags you already know, combined.

### Modern guidance

Dev scripts use `node --watch` + hook registration + `TS_NODE_PROJECT` scoping (never `--project` — it isn't a Node flag, see part 3's verified failure). One loop per entry; shared entries share the command shape. `--watch` is development-only (never in CI/start scripts — a watcher that never exits is a hung pipeline, per TS 19's mode-per-workflow rule linked in [01/4.1](<../../../01 Execution Foundations and Mental Model/sections/4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>)).

### Runnable example (good — boot, bounce, new output)

```typescript
// wf/srv.ts + wf/helper.ts (hook-compiled, graph of two)
import { v } from "./helper";
console.log("srv:", v());
```

```bash
TS_NODE_PROJECT=wf/tsconfig.json node --watch -r ts-node/register ./wf/srv.ts
# srv: 1
# Completed running './wf/srv.ts'
# (edit wf/helper.ts: return 1 → return 3)
# Restarting './wf/srv.ts'
# srv: 3
```

Verified on Node v20.20.2 + ts-node v10.9.2: initial run prints, helper edit triggers `Restarting`, re-run prints the new value. The single-file variant from research (edit entry itself: `watch-run:` → `Restarting` → `watch-run2: 42`) behaves identically — entry or dependency, the loop bounces.

### Common confusion

- **"`--watch` re-compiles incrementally"** — it *restarts the process* (fresh hook, fresh compile of the graph — no in-memory incremental state). Restarts cost full cold start per save (the mode ladder from [01/2.1](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>) prices each bounce: transpile-only keeps bounces sub-second).
- **"watch observes the entry file"** — it observes the entry's *graph* (verified: editing `helper.ts` bounced `srv.ts`). Save in a leaf, watch the root bounce — the loop covers refactors, not just the file you stare at.

### Performance note

Bounce cost = cold start (hook compile of the graph, per save). On the 60-file probe tree from [01/2.1](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>): ~1.2s full-mode bounces vs ~0.4s transpile-only — hundreds of saves per day make the mode choice a felt difference in flow. Measure your tree's bounce (`time` one boot), multiply by saves, choose the mode with arithmetic.

### Mentor note

Onboard with the bounce exercise: boot the loop, edit a *dependency* (not the entry), watch the server follow. Mentees who see the graph bounce stop restarting manually "to be safe" — trust in the loop is built by watching it follow a helper edit, once.

## 2) Watch the entry's whole graph

### 2) **Definition** (graph observation)

The watcher tracks files the entry *loads* (requires/imports resolved through the hook), not just the entry path: helper edits, shared-lib edits, and config-adjacent source edits all bounce the loop. Observation follows the module graph dynamically — files enter observation when imported, leave when the graph drops them (restart rebuilds the graph fresh).

### What problem it solves (history)

File-watchers that observe one path (early `--watch` iterations, naive `fs.watch` scripts) missed dependency edits — the server ran stale helpers while the author stared at fresh sources, producing "but I saved!" incidents. Graph observation closed the staleness class: any loaded file's save bounces the world that loaded it.

### Modern guidance

Trust but verify per repo: boot the loop, touch each *category* of dependency (helper, shared package, aliased module via the [03/3.1](<../../../03 ESM CJS and Loader Hooks Deep Dive/sections/3. Runtime recipes/3.1. The runtime paths recipe.md>) recipe), confirm each bounces. Generated files (emit outputs, codegen targets) deserve ignore rules where supported — bouncing on your own build's exhaust is a feedback loop in the bad sense (emit → bounce → emit).

### Runnable example (good — the category sweep, verified core)

```bash
# verified this session: helper edit bounces the server with new output
# srv: 1  →  (edit wf/helper.ts)  →  Restarting './wf/srv.ts'  →  srv: 3
```

Extend the sweep per repo: aliased helper (recipe hook in the loop — mapper flags compose on the watch command identically), JSON data file (watched as a loaded module — bounce confirmed the same way), `.ts` under ESM loader door (`--loader` flags compose with `--watch` — verify per floor, flag-order rules from [03/1.1](<../../../03 ESM CJS and Loader Hooks Deep Dive/sections/1. Hook pipeline/1.1. resolve and load the two-stage pipeline.md>) still apply).

### Common confusion

- **"watched files list is static"** — dynamic per graph (conditional imports, lazy `import()` branches enter observation when first loaded). A file saved *before* its first import never bounced anything — then bounces after. "It didn't restart" sometimes means "it wasn't loaded yet," not "watch is broken."
- **"node_modules changes bounce"** — dependencies inside `node_modules` generally don't trigger (watchers scope to the project graph; `node_modules` churn would bounce constantly). Editing linked packages (`npm link`, workspaces) *does* bounce when resolved as project files — verify per setup, don't assume either way.

### Performance note

Graph observation costs one watcher per loaded file (OS handles, dozens-to-hundreds — noise) plus restart cost per save (cold start, priced in part 1). The cost that matters is *false bounces* (generated files, log outputs inside watched dirs): each steals a cold start and breaks flow. Ignore-list hygiene (`--watch-ignore` patterns where supported, generated outputs outside watched roots) pays per save, forever.

### Mentor note

The "touch every category" sweep makes an excellent pairing exercise: mentee touches, mentor predicts bounce-or-not, both watch. Wrong predictions reveal model gaps (conditional branches, linked packages, generated exhaust) faster than any documentation — three minutes, permanent calibration.

## 3) Transpile-only inside every loop

### 3) **Definition** (the loop-mode rule)

Watch loops execute transpile-only (or equivalent unchecked execution) — never full-mode checking. The checker runs beside the loop (`tsc --noEmit --watch` in a second terminal, editor diagnostics inline, CI gate at merge — the three clocks from [01/4.1](<../../../01 Execution Foundations and Mental Model/sections/4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>)), never inside the bounce path. Each bounce pays compilation only; checking rides its own schedule.

### What problem it solves (history)

Full-mode watch loops paid whole-program checking per save (seconds per bounce on real trees), training developers to save rarely (giant diffs per bounce, defeating the loop's purpose) or to disable checking entirely (fast loop, type errors as staging surprises — the coupled-schedule failure from [01/2.1](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>)). Mode-per-clock restored both virtues: sub-second bounces *and* complete verification.

### Modern guidance

Every watch/dev script transpile-only by default (`-r ts-node/register` + `TS_NODE_TRANSPILE_ONLY=true`, or CLI `--transpile-only`, or transpile-only-first restarter config); every repo pairs it with a visible type clock (`dev:types` script, documented beside `dev`); every merge gates on the cold checker. A full-mode watch loop in a repo is a review finding with the ladder numbers attached — until measured otherwise, which it never is.

### Runnable example (good — the loop command, fully composed)

```bash
# the complete dev-loop invocation: watcher + hook + mode + scope, all explicit
TS_NODE_PROJECT=wf/tsconfig.json TS_NODE_TRANSPILE_ONLY=true \
  node --watch -r ts-node/register ./wf/srv.ts
```

```bash
# bad: the same loop in full mode (default when transpileOnly unset)
TS_NODE_PROJECT=wf/tsconfig.json node --watch -r ts-node/register ./wf/srv.ts
# each bounce pays the checker — seconds per save on real trees
```

And the flag that isn't: `--project` after `node` dies before anything runs (verified live this session):

```bash
node --watch -r ts-node/register --project wf/tsconfig.json ./wf/srv.ts
# node: bad option: --project
```

`--project` belongs to the ts-node CLI (which parses it); bare `node` rejects unknown flags before the hook loads. Under `-r`/loader doors, scope travels via `TS_NODE_PROJECT` (or the tsconfig discovery walk) — doors differ, and the flag set differs with them ([01/1.2](<../../../01 Execution Foundations and Mental Model/sections/1. Execution identity and setup/1.2. Installing and running your first TypeScript file.md>)'s door discipline, applied).

### Common confusion

- **"transpile-only watch hides type errors"** — it defers them to the adjacent clock (watch-mode `tsc`, editor, CI) — hidden from the bounce, visible beside it. Hiding would mean *nowhere*; deferring means *elsewhere on purpose*. The distinction is the whole practice.
- **"one terminal is simpler"** — one terminal coupling two clocks is simpler to *start* and slower forever after (every save waits on checks). Two terminals (loop + types) is simpler to *sustain* — optimize for the thousand saves, not the first boot.

### Performance note

Loop economics: bounce latency × saves per day = flow tax. Transpile-only minimizes the first factor (sub-second on most trees); the second factor is fixed by work habits. Full mode multiplies the tax 3× (measured ladder) for zero loop benefit (checker output scrolls past, unread, per bounce). Arithmetic, not taste.

### Mentor note

Make the mode visible: require watch scripts to name their mode (`--transpile-only` flag or `TS_NODE_TRANSPILE_ONLY` in env, printed in the script itself). Invisible modes drift (someone "simplifies" the script, full mode returns, bounces triple overnight). Named modes survive refactors; the name is the guardrail.
