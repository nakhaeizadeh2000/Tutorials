# 1.2. Nodemon and restarter discipline compared

When the stdlib watcher isn't enough — nodemon's extension watchlist (and its classic `.ts` miss), the three-restarter decision rule, and pinning restart commands like configuration. Junior read: nodemon needs `-e ts`, always. Expert read: process-model differences that decide among restarters, and why ts-node-dev stays documented-but-uninstalled here.

## 1) Nodemon watches extensions, not intentions

### 1) **Definition** (the extension watchlist)

Nodemon restarts on changes to files matching its watched extensions (`-e` list, defaulting to JS-family: `js,mjs,cjs,json` and friends — notably *not* `ts`). A TypeScript entry edited under default settings runs once, prints `clean exit - waiting for changes before restart`, and never bounces: the watcher observes extensions, the sources aren't among them, silence follows. `-e ts` (usually `-e ts,json`) enrolls TypeScript sources; then edits bounce as expected.

### What problem it solves (history, inverted — the trap it sets)

Nodemon predates TypeScript's dominance; its defaults encode a JS era. The `--exec ts-node …` composition *looks* complete (TypeScript runs — first boot prints), which is exactly why the missing restart surprises: execution works, observation doesn't, and the two arrive through different mechanisms (exec vs watchlist) that no single glance covers. The trap is set by partial success.

### Modern guidance

Every nodemon+ts-node invocation names extensions explicitly (`-e ts,json` minimum — config files change too), the exec line names the hook composition (`--exec ts-node --transpile-only --project …` or `-r` variant), and both live in `package.json` scripts (never tribal CLI memory). Verify per repo with the edit test from [1.1](<./1.1. Watch mode that restarts right.md>): boot, edit a dependency, watch the bounce — before trusting any loop.

### Runnable example (good — the miss, then the fix, both verified)

```bash
# WITHOUT -e ts: runs once, then waits forever (nodemon 3.1.14)
./node_modules/.bin/nodemon --exec ./node_modules/.bin/ts-node --transpile-only --project wf/tsconfig.json ./wf/nd.ts
# [nodemon] starting `.../ts-node ...`
# nd-run: 2
# [nodemon] clean exit - waiting for changes before restart
# (edit wf/nd.ts → …nothing. No "restarting due to changes". Silence.)

# WITH -e ts: edit → bounce → new output
./node_modules/.bin/nodemon -e ts --exec ./node_modules/.bin/ts-node --transpile-only --project wf/tsconfig.json ./wf/nd.ts
# [nodemon] watching path(s): *.*
# [nodemon] watching extensions: ts
# [nodemon] starting `.../ts-node ...`
# nd-run: 3
# [nodemon] restarting due to changes...
# [nodemon] starting `.../ts-node ...`
# nd-run: 4
```

Verified: same binary, same entry, same edit — the only delta is the watchlist. The `watching extensions: ts` line is the receipt (quote it in bug reports); its absence is the diagnosis. Note `watching path(s): *.*` — nodemon observes broadly by path, narrowly by extension: path breadth misleads ("it watches everything!"), extension narrowness decides.

### Common confusion

- **"nodemon is broken with ts-node"** — nodemon is *unconfigured* for ts-node (defaults predate the pairing). One flag completes it — "broken" diagnoses that survive a one-flag fix were never breakage, only defaults.
- **"`--exec ts-node` vs config file"** — `nodemon.json` (`{ "exec": "…", "ext": "ts,json", "watch": […] }`) beats long CLI lines for the same reason tsconfig beats flags ([02/1.1](<../../../02 Configuration and tsconfig for Execution/sections/1. Config architecture/1.1. Base and delta tsconfigs.md>)): reviewable, diffable, shared. CLI for experiments, file for the repo.

### Performance note

Nodemon overhead per bounce: process respawn + full cold start (same as `node --watch` — both restart processes; neither is incremental). Watchlist breadth affects *scan* cost on huge trees (path `*.*` with thousands of files: use `watch`/`ignore` to scope) — extension narrowness affects *correctness* (this leaf). Scope paths for speed, enroll extensions for function.

### Mentor note

The extension miss is the ideal onboarding bug: reproducible in two commands, diagnosed in one log line (`watching extensions:`), fixed in one flag, prevented forever by scripts. Walk every mentee through the miss-then-fix sequence live — the habit it installs ("read the watcher's receipt lines") generalizes to every file-watching tool they will ever meet.

## 2) Three restarters, one decision rule

### 2) **Definition** (the process-model comparison)

`node --watch` (stdlib: restarts the process on graph changes, zero dependencies), nodemon (mature watcher: configurable paths/ext/delays, exec-arbitrary, process-per-restart), ts-node-dev (in-process restarter: shares the TypeScript compiler between restarts, `--respawn`/`--transpile-only`/`--ignore-watch` — faster bounces, same-process state risks). All three restart; they differ in *what survives the bounce* (nothing / nothing / compiler instance) and *what they observe* (graph / paths+ext / dependency graph via require cache).

### What problem it solves (history)

Restarters multiplied because each optimizes a different pain: stdlib minimizes dependencies, nodemon maximizes configurability (delays, ignores, exec hooks, legacy floors), ts-node-dev minimizes bounce latency (compiler reuse across restarts — meaningful on thousand-file trees where cold start dominates). No single winner exists because the pains differ per repo: small service (any), giant monorepo package (compiler reuse), exotic pipeline (nodemon exec).

### Modern guidance

Decision rule, in order: (1) default to `node --watch` (stdlib, zero surface, graph-aware — verified all session); (2) reach for nodemon when the loop needs what stdlib lacks (restart delays for cascading saves, exec pipelines, ignore granularity, pre-v18 floors); (3) reach for ts-node-dev only with measured cold-start pain *and* acceptance of same-process restart semantics (state leakage across bounces is the price of compiler reuse). Revisit per year, not per mood — restarter churn re-breaks every pinned command for zero loop gain.

As of September 2026, with explicit honesty: ts-node-dev was *not installed in this session's probe* (its install tree timed out under tool limits — SIGTERM on the installer, not a registry failure), so its row below is documented from its public CLI contract (`--respawn`, `--transpile-only`, `--ignore-watch`, `--clear`), not executed. The rule still holds: adopt on measured bounce pain with the semantics eyes-open, never on README promises.

### Runnable example (good — the comparison with receipts where executed)

| Restarter | Restart trigger (verified) | Bounce model | Needs for TS |
|---|---|---|---|
| `node --watch` | graph save → `Restarting` (verified: entry + dependency) | fresh process, cold start | hook flags (`-r`/loader) + scope env |
| nodemon | ext-listed save → `restarting due to changes` (verified with `-e ts`) | fresh process, cold start | `-e ts` + `--exec` composition |
| ts-node-dev | dependency save → respawn (documented) | compiler reused, faster | `--transpile-only` recommended; semantics per its docs |

```bash
# the two verified loop commands, side by side:
TS_NODE_PROJECT=wf/tsconfig.json node --watch -r ts-node/register ./wf/srv.ts
./node_modules/.bin/nodemon -e ts,json --exec ./node_modules/.bin/ts-node --transpile-only --project wf/tsconfig.json ./wf/srv.ts
```

### Runnable example (bad — restarter polygamy)

```jsonc
// bad: three restarters across scripts (each documented "temporarily")
{ "scripts": {
    "dev": "node --watch -r ts-node/register ./src/server.ts",
    "dev:fast": "ts-node-dev --transpile-only ./src/server.ts",
    "dev:old": "nodemon --exec ts-node ./src/server.ts" } }
// behavior differs per script (modes, ext lists, state leakage) —
// "works on dev:fast, breaks on dev" incidents with no code diff
```

Why it hurts: restart semantics become per-script variables (state leakage here, full cold start there, unchecked without `-e ts`), so loop behavior can't be reasoned about repo-wide — and the "temporary" scripts outlive every intention. Fix: one restarter per repo (the decision rule picks it), others deleted, choice recorded beside the script with its reason.

### Common confusion

- **"ts-node-dev is always faster"** — faster *bounces* (compiler reuse) with *riskier* restarts (same-process state: singletons, timers, module cache subtleties across respawns). Speed measured per tree; risk accepted per team — both halves of the sentence required before adopting.
- **"nodemon exec distinguishes CJS/ESM"** — exec composes with either door (`-r` hook or `--loader` flags inside the exec string — loader flag-order rules from [03/1.1](<../../../03 ESM CJS and Loader Hooks Deep Dive/sections/1. Hook pipeline/1.1. resolve and load the two-stage pipeline.md>) apply verbatim inside `--exec`). Doors compose through restarters transparently; restarters never fix door errors.

### Performance note

Bounce-latency ranking on large trees (direction stable, magnitudes per tree): ts-node-dev (compiler reused) < transpile-only fresh process (`node --watch`/nodemon, tied — same cold start) < full-mode fresh process (checker per bounce — never). Measure your tree's cold start once; if bounces feel slow, the fix order is mode first (full→transpile-only, 3×), restarter second (fresh→reused, marginal), hardware never.

### Mentor note

Forbid restarter debates without numbers: "adopt X" proposals must attach the tree's measured cold start and the bounce count per day. Nine of ten proposals evaporate at the arithmetic (sub-second bounces need no optimizer); the tenth arrives with evidence and gets approved in minutes. Numbers end fashion cycles.

## 3) Restart commands are pinned like any config

### 3) **Definition** (scripts as configuration)

Restart invocations live in `package.json` scripts (or `nodemon.json`/equivalent), complete with exec line, extension list, project scope, and mode — the full composition, reviewable in diffs, executable by every teammate identically. A restart command typed from memory is unpinned configuration with extra steps; a restart command in scripts is infrastructure.

### What problem it solves (history)

Tribal CLI memory ("I run nodemon with some flags… I think `-e ts`?") produced per-developer loop behavior: different modes, different ext lists, different scopes — "works on my loop" incidents mirroring the global-install era from [01/1.2](<../../../01 Execution Foundations and Mental Model/sections/1. Execution identity and setup/1.2. Installing and running your first TypeScript file.md>). Pinning (like lockfiles, like tsconfig) converts behavior from memory into artifact.

### Modern guidance

Every loop command names all four slots (restarter + exec/hook + mode + scope): `"dev": "nodemon -e ts,json --exec \"ts-node --transpile-only --project tsconfig.dev.json\" ./src/server.ts"` — or the `node --watch` equivalent with env. Order comments where loaders compose (mapper-before-compiler, per [03/1.1](<../../../03 ESM CJS and Loader Hooks Deep Dive/sections/1. Hook pipeline/1.1. resolve and load the two-stage pipeline.md>)). CI asserts the *existence* of pinned loops (script presence check — cheap) while humans assert their *correctness* (edit test per loop, per [1.1](<./1.1. Watch mode that restarts right.md>)).

### Runnable example (good — the pinned quartet)

```jsonc
{
  "scripts": {
    // restarter + hook + mode + scope — all four slots, zero memory required
    "dev": "TS_NODE_PROJECT=tsconfig.dev.json node --watch -r ts-node/register ./src/server.ts",
    "dev:alt": "nodemon -e ts,json --exec \"ts-node --transpile-only --project tsconfig.dev.json\" ./src/server.ts",
    "dev:types": "tsc --noEmit --watch"
  }
}
```

### Runnable example (bad — the remembered command)

```bash
# bad: loop behavior reconstructed per terminal from memory
nodemon --exec ts-node src/server.ts
# missing: -e ts (never restarts on sources!), --transpile-only (full-mode bounces),
# --project (wrong-config roulette) — three omissions, zero errors, one confused developer
```

Why it hurts, specifically: each omission fails *silently* (no restart, slow bounce, wrong pair — none announce themselves as flag problems), so the developer debugs code, config, and toolchain before suspecting the command line they typed themselves. Pinned commands fail loudly or not at all — the omissions become diffs, and diffs get reviewed.

### Common confusion

- **"scripts are documentation enough"** — scripts *are* the loop (executable truth), documentation *describes* it (prose approximation). Both, in that hierarchy: script first (runs identically everywhere), prose second (explains the why — the decision rule from part 2, the order from [03/1.1](<../../../03 ESM CJS and Loader Hooks Deep Dive/sections/1. Hook pipeline/1.1. resolve and load the two-stage pipeline.md>)).
- **"pinning prevents experimentation"** — pin the default loop; experiment on branches (new restarter? new flags? — branch, measure, merge or discard). Pinned defaults *enable* experimentation (a known-good baseline to compare against) instead of preventing it.

### Performance note

Pinned loops cost nothing at runtime (same commands, written down) and save the setup tax per developer per repo (minutes) plus the misconfiguration incidents per year (hours). The highest-ROI lines in `package.json` after `typecheck` — four slots, complete composition, zero memory.

### Mentor note

Audit any repo's loops in sixty seconds: read `scripts`, check four slots per loop command, run the edit test on each. Missing slots are findings with fixes attached (add the flag, pin the scope, name the mode) — the audit converts loop folklore into infrastructure before lunch.
