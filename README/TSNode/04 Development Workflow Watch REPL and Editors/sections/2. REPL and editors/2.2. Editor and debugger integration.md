# 2.2. Editor and debugger integration

Wiring editors and debuggers to TypeScript-through-the-hook: launch configs that execute (not just attach), the `--inspect` proof that works without any editor, and the boundary where mechanics belong to other tracks. Junior read: copy the launch.json, set breakpoints in `.ts`. Expert read: why `runtimeExecutable` beats `program`-with-wrapper, and what `--inspect` proves before the editor opens.

## 1) Launch configs execute, not just attach

### 1) **Definition** (the wiring shape)

A TypeScript debug configuration launches Node *with the hook installed* (`runtimeExecutable: node` + `runtimeArgs: [-r ts-node/register]` or loader equivalents), scoped (`TS_NODE_PROJECT`) and moded (`TS_NODE_TRANSPILE_ONLY`) via env — so breakpoints set in `.ts` sources bind through ts-node's sourcemaps (Domain 05 owns the maps; this leaf owns the config that activates them). Attaching to an already-running process is the fallback; launching through the hook is the practice.

### What problem it solves (history)

`program: ts-node` launch configs (executing the ts-node binary as the "program") broke argument passing, env layering, and loader composition — the debugger owned a process whose flags it couldn't fully express. `runtimeExecutable: node` + `runtimeArgs` restored the full invocation surface: every CLI/hook/loader form from [01/1.2](<../../../01 Execution Foundations and Mental Model/sections/1. Execution identity and setup/1.2. Installing and running your first TypeScript file.md>) expressible, debuggable identically.

### Modern guidance

One launch config per entry (checked into `.vscode/launch.json`, reviewed like scripts): hook form matching the npm script's door (CJS entries `-r`, ESM entries loader flags in `runtimeArgs`), `TS_NODE_PROJECT` pinned (debugger CWDs differ from terminals — scope explicitly per [02/1.2](<../../../02 Configuration and tsconfig for Execution/sections/1. Config architecture/1.2. Monorepo configs and project scoping.md>)), transpile-only for session speed (full-mode breakpoints wait on the checker per restart — the loop-mode rule from [1.1](<../1. Watch and restart/1.1. Watch mode that restarts right.md>) applies to debug sessions equally).

### Runnable example (good — the config, validated)

```jsonc
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Debug TS via hook",
      "type": "node",
      "request": "launch",
      "runtimeExecutable": "node",
      "runtimeArgs": ["-r", "ts-node/register"],
      "args": ["${workspaceFolder}/src/server.ts"],
      "env": {
        "TS_NODE_PROJECT": "${workspaceFolder}/tsconfig.json",
        "TS_NODE_TRANSPILE_ONLY": "true"
      },
      "console": "integratedTerminal",
      "skipFiles": ["<node_internals>/**"]
    }
  ]
}
```

Validated: parsed as JSON (`JSON-OK: Debug TS via hook`), every slot filled (hook, scope, mode — the composition from [1.1](<../1. Watch and restart/1.1. Watch mode that restarts right.md>) part 3, debugger-expressed). ESM variant swaps `runtimeArgs` to the loader flags (`--loader ts-node/esm` + mapper flags in verified order — [03/1.1](<../../../03 ESM CJS and Loader Hooks Deep Dive/sections/1. Hook pipeline/1.1. resolve and load the two-stage pipeline.md>) part 3 travels into the editor).

### Common confusion

- **"`console: integratedTerminal` is cosmetic"** — it decides stdio routing (debug console vs terminal: stdin interactivity, color support, TTY detection by the program). REPL-ish debugging and `readline` flows need the terminal; log-only flows suit the console. Cosmetic-looking, behavior-bearing — set deliberately.
- **"launch configs replace scripts"** — they *duplicate* the invocation (same doors, same flags, same env) in a second syntax. Duplication drifts (script gains `--project`, config doesn't) — audit launch configs beside scripts on every invocation change, or generate one from the other (tasks that echo the dev script).

### Performance note

Debug-session startup = cold start + inspector handshake (transpile-only keeps it near loop latency; full mode adds the checker per launch). `skipFiles` isn't performance (it's noise reduction — internals hidden from stepping), but stepping *speed* perceptibly improves when the debugger skips compiled-helper frames. Session cost is human (breakpoint discipline), not machine.

### Mentor note

Require every debuggable entry to ship its launch config (same PR as the entry — "runnable" includes "debuggable"). Mentees inheriting repos should debug before reading: breakpoints in `main.ts`, step twice, narrate the hook's invisible presence (sources shown, JS executed — the sourcemap story Domain 05 will tell). Debugging-first onboarding beats reading-first for runtime code.

## 2) `--inspect` proves the wiring without the editor

### 2) **Definition** (the editor-independent proof)

`node --inspect -r ts-node/register ./entry.ts` boots the program through the hook with the inspector agent listening (`Debugger listening on ws://…`) — proving hook+debugger coexistence with zero editor involvement. If this prints both lines (listener + program output), any launch-config failure is editor configuration, not runtime incompatibility. Bisect first, configure second.

### What problem it solves (history)

"Breakpoints don't bind" reports conflated three layers (hook compilation, sourcemap emission, editor attachment) into one symptom — debugging the editor while the hook was misconfigured, or vice versa, for hours. The `--inspect` proof isolates the runtime half in one command: listener + output means the runtime half works, and only the editor half remains suspect.

### Modern guidance

Run the proof before writing any launch config (new repo, new entry, new Node major — thirty seconds that partitions all future failures). `--inspect-brk` variant for entry-point breakpoints (breaks before first line — attach, then resume). Port-pin in shared environments (`--inspect=127.0.0.1:<port>` — never default-port on shared dev servers; collisions masquerade as hangs).

### Runnable example (good — both lines, verified)

```bash
node --inspect=127.0.0.1:19299 -r ts-node/register ./hello.ts
# Debugger listening on ws://127.0.0.1:19299/66111cb9-a818-4411-85d5-847211cad328
# hello from ts
```

Verified on Node v20.20.2 + ts-node v10.9.2: inspector agent up (WebSocket URL printed) *and* hook-compiled program output on the next line. The two lines are the whole proof: debugging protocol live, TypeScript executing — every layer below the editor confirmed working.

### Common confusion

- **"no listener line means ts-node broke inspect"** — listener absence means the *flag* didn't reach Node (flag ordering: `--inspect` before `-r` and entry — Node parses its own flags left-to-right; misplaced flags after the entry belong to the program). Hook and inspector compose orthogonally — order the flags, don't blame the tools.
- **"`--inspect` in npm scripts is harmless"** — a listening inspector in shared/staging environments is a security exposure (debugger attach = code execution). `--inspect` belongs in launch configs and manual probes, never in committed scripts (lint for it: `grep -r --inspect package.json .vscode` in CI).

### Performance note

Inspector agent costs a paused-nothing thread plus protocol overhead per breakpoint hit (microseconds idle, milliseconds per pause for state serialization) — negligible for development, unacceptable at production scale (never `--inspect` production; profiles come from Domain 05's sampling tools, not live debugging).

### Mentor note

Teach the bisect reflex with the two-line proof: "listener?" (runtime half) then "editor attaches?" (editor half). Mentees who bisect solve debug-wiring failures in minutes; mentees who reconfigure blindly solve them eventually, expensively. The proof command belongs in the team runbook beside the gates.

## 3) Mechanics live elsewhere

### 3) **Definition** (the wiring/mechanics split)

*Wiring* (this leaf: launch configs, `--inspect` composition, hook+debugger coexistence) vs *mechanics* (elsewhere: inspector protocol internals, breakpoint resolution, sourcemap generation/consumption, profiling). Wiring answers "how do I debug this entry?"; mechanics answers "how does debugging work?". Different questions, different homes, linked not duplicated.

### What problem it solves (history)

Workflow docs that re-teach inspector internals rot (protocol versions move; the copy doesn't) and bloat (fifty pages where five suffice). The split keeps this leaf evergreen (wiring shapes change slowly — `runtimeExecutable` has been stable for years) while mechanics evolve in their single homes (updated by the engineers who operate them).

### Modern guidance

Debug-TypeScript questions route by layer: entry won't boot under debugger → this leaf (wiring); breakpoints land wrong → Domain 05 (sourcemaps); stepping behaves oddly → JS 15 (protocol); production incident → NodeJS 06 (service debugging). Four layers, four homes, zero overlap — the router from [4.1](<../4. Important points to remember/4.1. Workflow checklist habits mentors insist on.md>) extended to debugging.

### Runnable example (good — routing three failures)

```bash
# "launch config errors before main" → wiring (this leaf): check runtimeArgs order, env pins
# "breakpoint binds two lines low" → sourcemaps (Domain 05): map chain inspection
# "works in terminal, not in editor" → CWD/scope (02/1.2): debugger CWD differs — pin TS_NODE_PROJECT
```

### Common confusion

- **"one debugging guide suffices"** — one *router* suffices (this part); guides multiply by layer (each owned where it evolves). Centralized mechanics rot; centralized routing endures — organize pointers, not copies.
- **"Domain 05 makes this leaf obsolete"** — Domain 05 deepens the *map* half; this leaf remains the *wiring* reference (configs, flags, proofs). Complementary by design — the track's layering, not its redundancy.

### Performance note

No runtime dimension (documentation architecture). The cost axis is maintenance: unowned copies rot at the speed of platform change (inspector flags move yearly); owned singles update in place. DRY is a performance practice for teams (search once, find truth) wearing an aesthetics costume.

### Mentor note

Enforce the split in review: debugging PRs touching mechanics get redirected to the owning track ("great find — file it against JS 15/NodeJS 06, link from here"); PRs touching wiring land here. Mentees learn contribution routing alongside debugging — the repo's structure teaches the platform's structure.
