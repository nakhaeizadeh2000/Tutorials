# 2.1. The ts-node REPL

The TypeScript REPL: piped evaluation that runs and exits, interactive exploration with project config, and the promotion rule to files. Junior read: pipe two-liners, get answers. Expert read: how the REPL shares (and differs from) script execution — stdin naming, error reporting, and exit behavior.

## 1) Pipe evaluates, terminal explores

### 1) **Definition** (the two REPL shapes)

*Piped*: stdin carries the program (`printf '…' | ts-node`), evaluated once, process exits — scripting with TypeScript syntax. *Interactive*: bare `ts-node` on a TTY opens the read-eval-print loop (multiline-aware, completion-assisted, project-configured) — exploration with immediate feedback. Same compiler, same config discovery, different lifecycles: one-shot vs session.

### What problem it solves (history)

One-off TypeScript questions ("does this type error?", "what does this emit?") previously needed a scratch file plus a compile step — ceremony exceeding the question. Piped evaluation collapses it to one shell line; the interactive loop extends it to follow-ups (each answer suggesting the next probe) without file churn. The REPL is the cheapest possible TypeScript execution: no files, no scripts, no cleanup.

### Modern guidance

Pipes for deterministic probes (verifications, gate checks, doc examples — stdin text is the program, reviewable in history); interactive for exploration (API shape discovery, error-message reading, "what if" chains). Both honor the project tsconfig (discovery from CWD — run from the repo root or pin `TS_NODE_PROJECT`, same as scripts). Anything reused twice becomes a file ([1.2](<../1. Watch and restart/1.2. Nodemon and restarter discipline compared.md>)'s promotion economics apply to REPL transcripts too).

### Runnable example (good — piped probes, both modes)

```bash
printf 'const s: string = "repl-pipe";\nconsole.log(s.toUpperCase());\n' | ./node_modules/.bin/ts-node --transpile-only
# REPL-PIPE
# (exit 0 — evaluated, printed, exited)
```

```bash
printf 'const x: number = "nope";\n' | ./node_modules/.bin/ts-node
# [stdin].ts(1,7): error TS2322: Type 'string' is not assignable to type 'number'.
# (exit 0 — reported, not crashed)

printf 'const x: number = "nope";\nconsole.log("still:", x);\n' | ./node_modules/.bin/ts-node --transpile-only
# still: nope
```

Verified on ts-node v10.9.2: full-mode REPL names the virtual file `[stdin].ts` with line/column diagnostics and *continues* (exit 0 — the loop survives errors by design); transpile-only erases and runs. The `[stdin].ts` filename is the tell: piped programs are compiled as a virtual module under the active project — config, strictness, and all.

### Common confusion

- **"REPL exit code signals success"** — piped full-mode exits 0 *despite* the diagnostic (verified above — the error printed, exit stayed zero). Never gate on REPL exit codes; gate on output content (`grep -q "error TS"` inverts the check) or use `tsc --noEmit` for verdicts. Exit-zero-with-errors is loop-friendly behavior, not a pass signal.
- **"REPL ignores tsconfig"** — discovery runs identically (CWD walk per [02/1.2](<../../../02 Configuration and tsconfig for Execution/sections/1. Config architecture/1.2. Monorepo configs and project scoping.md>)); strictness, pairs, and `ts-node` options all apply. A REPL answering differently from scripts means different *directories*, not different *tools* — `pwd` before theorizing.

### Performance note

REPL boot costs one compiler startup (same cold start as scripts, ~0.4s transpile-only on small trees) — per *session* for interactive (amortized across inputs), per *invocation* for pipes (each pipe pays full boot). Pipe-heavy automation (dozens of probes in a script) should batch into fewer invocations or graduate to files — boot-per-line is the slowest possible automation.

### Mentor note

Teach piped REPL as the verification tool for every claim in review ("prove the type error" → one pipe, diagnostic quoted). Mentees who reach for pipes instead of scratch files iterate faster and leave evidence in shell history. Interactive sessions stay ephemeral by rule: anything worth keeping gets promoted to a file before the terminal closes.

## 2) REPL shares the project config

### 2) **Definition** (no-entry discovery)

Without an entrypoint script, ts-node searches for tsconfig from `--cwd`/`process.cwd()` (per official Configuration docs — the `--cwdMode`-without-entry rule). Practically: the REPL compiles under the nearest config *above the launch directory*. Same project, same strictness, same `ts-node` object (transpileOnly included) — the REPL is a script with stdin as its source, nothing more.

### What problem it solves (history)

Pre-discovery REPLs compiled under defaults (or required explicit flags), so interactive answers disagreed with script behavior — same input, different strictness, "but the REPL said" incidents. Unified discovery (REPL = entryless script) guarantees the loop and the file agree: the answer explored interactively is the answer scripts produce.

### Modern guidance

Launch REPLs from the package root (nearest config = the package's own — no surprises); pin with `TS_NODE_PROJECT` when exploring cross-package behavior (monorepo root shell, package questions — explicit scope per [02/1.2](<../../../02 Configuration and tsconfig for Execution/sections/1. Config architecture/1.2. Monorepo configs and project scoping.md>)); mirror the script mode (transpile-only REPL for exploration speed, full-mode REPL when hunting type errors interactively — the diagnostic above only fires in full mode).

### Runnable example (good — same diagnostic both doors)

```bash
# script door (verified S1): full mode gates with TS2322
./node_modules/.bin/ts-node ./loose.ts 2>&1 | head -2
# TSError: ⨯ Unable to compile TypeScript:

# REPL door (verified this session): same error, virtual filename, loop survives
printf 'const x: number = "nope";\n' | ./node_modules/.bin/ts-node 2>&1 | head -1
# [stdin].ts(1,7): error TS2322: Type 'string' is not assignable to type 'number'.
```

Same checker, same rule, two filenames (`loose.ts` vs `[stdin].ts`) — the REPL disagrees with scripts about nothing except where the bytes came from. That agreement is the feature: explore in the loop, trust in the file.

### Common confusion

- **"REPL transpile-only is the default"** — the REPL defaults to the *config* (full unless `transpileOnly` set — the diagnostic above fired on defaults). Interactive type-error hunting *wants* full mode (diagnostics inline); interactive API exploration *wants* transpile-only (no checker latency per line). Set deliberately per session purpose — the default serves neither perfectly.
- **"multiline paste just works"** — the REPL is line-oriented with paste heuristics (`.editor` mode for blocks in interactive use; pipes bypass the issue entirely — another reason pipes suit automation). Pasted blocks misbehaving interactively is a REPL UX edge, never a language fact — verify via file before concluding.

### Performance note

Interactive latency per line: parse + (full mode) check + eval — milliseconds for expressions, noticeable for declarations pulling heavy types. Transpile-only REPL keeps every line sub-second on large projects (checker skipped per line — the mode economics from [01/2.1](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>) applied per keystroke). Slow REPL lines mean full mode on a big program — switch modes, not tools.

### Mentor note

Pair REPL exploration with file promotion explicitly: "explore three lines, then write the file." Mentees who live in the REPL accumulate unverifiable knowledge (transcripts scroll away); mentees who promote accumulate tests and scripts. The REPL is a scratchpad with a compiler — treat it like one (disposable by design).

## 3) Scripts outgrow the REPL fast

### 3) **Definition** (the promotion rule)

Two uses, then a file: any piped probe repeated, any interactive transcript worth keeping, any multi-line exploration with dependencies — promoted to a script under the project's tsconfig, runnable via the loop commands from [1.1](<../1. Watch and restart/1.1. Watch mode that restarts right.md>). The REPL answers questions; files preserve answers. Promotion is the moment an answer becomes infrastructure.

### What problem it solves (history)

Transcript knowledge rots (scrollback lost, shell history per-machine, no review, no CI) — teams re-deriving the same answers quarterly because nobody promoted the probe that found them. The promotion rule converts exploration into artifacts at the cheapest moment (while the answer is on screen): paste transcript to file, add assertions, commit. Verification probes from this track's own gates (`gate*.sh` in S1–S3 logs) all began as REPL-grade one-liners.

### Modern guidance

Keep a `scratch/` (gitignored) for sub-file probes and promote deliberately: probe → scratch file → asserted script → committed tooling, each step when the previous proves its worth. Document the promotion in commit messages ("promoted from REPL probe: verifies X") — provenance tells future readers why the script exists. Never commit REPL transcripts as documentation (unrunnable prose rots; committed scripts run in CI).

### Runnable example (good — probe to gate stage)

```bash
# step 1 — probe (REPL pipe, this session):
printf 'const s: string = "repl-pipe";\nconsole.log(s.toUpperCase());\n' | ./node_modules/.bin/ts-node --transpile-only
# REPL-PIPE

# step 2 — promote (gate stage, S1/S2 pattern):
./node_modules/.bin/ts-node --transpile-only ./hello.ts | grep -q "hello from" || exit 11
```

The same bytes, first as exploration, then as assertion — promotion adds the verdict (`grep -q`, exit code) the probe lacked. Every gate stage in this track's history followed this path; the pattern generalizes to all team tooling.

### Common confusion

- **"REPL history is documentation"** — history is per-machine, unreviewed, and unrunnable as a suite. Documentation is committed, reviewed, and executed (or explicitly marked illustrative). Promote or lose it — there is no third fate for knowledge.
- **"small probes don't need files"** — small probes need files the *second* time they run. First run: REPL. Second run: file. The rule counts executions, not lines — a two-liner run weekly belongs in scripts more than a fifty-liner run once.

### Performance note

Promotion costs one file creation (seconds) against re-derivation per quarter (hours across the team). The REPL-to-file pipeline is the highest-leverage documentation practice in this domain: every promoted probe becomes a regression test, a gate stage, or a runnable example — artifacts that pay per use.

### Mentor note

Review mentees' shells, not just their commits: frequent re-typed probes are promotion candidates the mentee hasn't recognized. "File that" is the highest-value two-word review comment in workflow mentoring — it converts ephemeral expertise into team assets, one probe at a time.
