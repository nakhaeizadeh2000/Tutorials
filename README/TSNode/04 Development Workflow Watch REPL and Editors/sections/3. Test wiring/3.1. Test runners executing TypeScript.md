# 3.1. Test runners executing TypeScript

Running `node --test` (and friends) against TypeScript sources through the hook: the wiring, the test-tree delta, and the one-runner rule. Junior read: flags in one place, TAP out. Expert read: why test trees need their own tsconfig delta, and how watchers, workers, and loaders compose inside test processes.

## 1) `node --test` plus the hook

### 1) **Definition** (the stdlib combination)

`node --test` discovers and runs test files (TAP output, subprocess isolation per file); `-r ts-node/register` (or loader flags) compiles `.ts` test sources on import. Combined: `node --test -r ts-node/register ./tests/` executes TypeScript tests with zero test-framework dependencies — runner mechanics from [JS 20](<../../../../JavaScript/20 Testing and Tooling Essentials/README.md>) (assumed: `describe`/`it`/`test`, hooks, mocks), hook wiring from [01/1.2](<../../../01 Execution Foundations and Mental Model/sections/1. Execution identity and setup/1.2. Installing and running your first TypeScript file.md>), test semantics unchanged by the language of the file.

### What problem it solves (history)

TypeScript test execution once required framework transforms (jest+ts-jest, vitest pipelines, mocha+register recipes) — each coupling the suite to a runner's compiler integration. The stdlib combination decouples them: Node runs the tests, the hook compiles the sources, and migrating frameworks (or staying stdlib) never re-touches compilation. Tests assert behavior; the hook is invisible to assertions.

### Modern guidance

Default to `node --test` + hook for unit/integration suites (stdlib, TAP-parseable, CI-native); reach for framework runners (vitest/jest) only for their differentiators (DOM, snapshots-at-scale, UI) — never merely "to run TypeScript" (the hook already does that). Test command pinned in scripts with scope env (`TS_NODE_PROJECT` pointing at the test delta — part 2); coverage via the runner's native V8 support (JS 20 owns the mechanics).

### Runnable example (good — TAP green on `.ts`, verified)

```typescript
// wf/tests/helper.test.ts — plain node:test, TypeScript spelling
import test from "node:test";
import assert from "node:assert/strict";
import { help } from "../../cjs/helper";

test("hook compiles the helper", () => {
  assert.equal(help(), "helped");
});
```

```bash
TS_NODE_PROJECT=wf/tsconfig.json node --test -r ts-node/register ./wf/tests/helper.test.ts
# TAP version 13
# # Subtest: hook compiles the helper
# ok 1 - hook compiles the helper
#   ---
#   duration_ms: 1.301822
```

Verified on Node v20.20.2 + ts-node v10.9.2: discovery finds the `.ts` file, the hook compiles (helper imported across directories), TAP reports green. The test asserts *behavior* (`helped`) — compilation is the silent precondition, exactly as it should be.

### Common confusion

- **"tests need transpile-only"** — test suites are the *best* transpile-only case (hundreds of files, rerun constantly — full mode multiplies suite time by the checker factor from [01/2.1](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>)). Type errors gate via `typecheck` in CI (same pipeline, separate job) — suites stay fast, merges stay sound.
- **"one test file per tsconfig"** — one test *delta* per suite (the `include` covers `tests/` + referenced sources — part 2), not per file. Scoping is per *tree*, matching how the runner discovers (directory walk, not file list).

### Performance note

Suite startup = hook compile of the test graph (transpile-only: milliseconds per file — the 0.427s sixty-file rung from [01/2.1](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>) is the shape). Per-test overhead of the hook: zero after import (compiled modules cache normally). Watch-mode suites (`--test --watch` + hook) pay cold start per save-bounce — same loop economics as [1.1](<../1. Watch and restart/1.1. Watch mode that restarts right.md>), same transpile-only prescription.

### Mentor note

New suites start stdlib+hook until a framework differentiator is named in writing (DOM/snapshot/UI need). "Everyone uses vitest" is fashion; "we need component snapshots" is architecture — demand the sentence before the dependency. Most service suites never outgrow `node --test`; the ones that do migrate with compilation untouched (the hook doesn't care which runner imports).

## 2) Test trees get their own delta

### 2) **Definition** (the suite-scoped tsconfig)

Test sources compile under a dedicated delta (`tsconfig.test.json` or test-scoped config): `include` covering tests + referenced sources, `esModuleInterop`/`allowSyntheticDefaults` as the test style requires, `types: ["node"]` (or `@types` scope for the suite), `noEmit` (tests execute, never emit). The delta extends the base ([02/1.1](<../../../02 Configuration and tsconfig for Execution/sections/1. Config architecture/1.1. Base and delta tsconfigs.md>)) and diverges only where tests differ — which is always at least the `include`.

### What problem it solves (history)

Tests compiled under the app config inherit app constraints (`include: ["src"]` excluding tests — files unchecked; strict emit settings irrelevant to execution; missing test-only libs) — producing suites that run but never typecheck (or typecheck the wrong file set). The dedicated delta makes the suite a first-class compilation target: checked completely, executed identically, configured explicitly.

### Modern guidance

Every suite owns its delta (checked in, extended from base, `include` = tests + sources-under-test); `TS_NODE_PROJECT` in test scripts points at it (never the app config — app `include` excludes the tests by design); CI runs `tsc --noEmit -p <test-delta>` as the suite's type gate (the program the hook executes is the program the checker verifies — parity by construction).

### Runnable example (good — the delta that unblocked the suite, verified)

```jsonc
// wf/tsconfig.json — test delta (extends nothing here; names everything)
{ "compilerOptions": {
    "target": "es2022", "module": "commonjs", "strict": true,
    "esModuleInterop": true },
  "include": ["tests", "../cjs"] }
```

```bash
# WITHOUT esModuleInterop (app-style config): full-mode hook refuses the suite
# wf/tests/helper.test.ts(1,8): error TS1259: Module '"node:test"'
#   can only be default-imported using the 'esModuleInterop' flag
# WITH the delta: TAP green (verified above)
TS_NODE_PROJECT=wf/tsconfig.json node --test -r ts-node/register ./wf/tests/helper.test.ts
# ok 1 - hook compiles the helper
```

Verified: the `TS1259` fired under the app-flavored config (full-mode check doing its job — the error is correct behavior, not breakage), and the delta's single added flag (`esModuleInterop`) resolves it. Test style (default imports from CJS builtins) *is* a compiler concern — the delta is where style meets execution.

### Common confusion

- **"`esModuleInterop` changes runtime behavior"** — it changes *emit helpers* (`__importDefault` wrappers) with identical observable behavior for well-formed imports; under ts-node it changes what the checker *accepts*. The flag's test-suite role is permissive (accept the import style tests use), not behavioral — runtime assertions pass identically either way.
- **"transpile-only suites don't need the delta"** — transpile-only skips *checking*, not *resolution*: `include`/paths/pairs still govern what the hook compiles (wrong `include` → files outside the program → subtly different emit). The delta serves execution too — scope is not a check-time luxury.

### Performance note

Delta cost: one more config file read per test boot (microseconds) + checker time over the test tree in CI (seconds, incremental locally). Suite-type-gate runtime scales with test count (linear, checker-bound) — project references ([TS 19](<../../../../TypeScript/19 Performance Project References and Scaling/README.md>)) partition app vs suite programs at monorepo scale. Small repos: one delta, full check, done.

### Mentor note

Review new suites for the delta first (exists? extends base? include covers tests+sources? `TS_NODE_PROJECT` wired in scripts?) — before reading a single test. Suite infrastructure decides whether the tests mean anything (unchecked tests assert runtime only; unscoped suites compile under accidents). Infrastructure review precedes content review, always.

## 3) One runner per repo, wired once

### 3) **Definition** (the single-wiring rule)

One test runner per repo, its TypeScript wiring declared exactly once (script + delta + scope env), inherited by every suite invocation (watch, CI, workers spawning tests, editors running single files). Duplicate wirings (mocha config *and* node --test flags *and* editor settings, disagreeing) are the test-world twin of restarter polygamy ([1.2](<../1. Watch and restart/1.2. Nodemon and restarter discipline compared.md>) part 2).

### What problem it solves (history)

Runner accretion (jest legacy + vitest pilot + node --test experiment, all wired, none removed) leaves suites whose behavior depends on *which* command ran them (different transforms, different globals, different module handling) — "green here, red there" with no code diff. Single wiring makes test behavior a repo property, not an invocation lottery.

### Modern guidance

Declare the runner in one script (`"test": "node --test -r ts-node/register ./tests/"` with `TS_NODE_PROJECT` — full composition visible); editors reuse it (VS Code test integration points at the same command); CI runs it verbatim (no CI-specific flags — divergence between local and CI test commands is a finding); watch variants derive (`--test --watch` adds one flag to the declared command, never a second wiring).

### Runnable example (good — the single declaration)

```jsonc
{ "scripts": {
    "test": "TS_NODE_PROJECT=tsconfig.test.json node --test -r ts-node/register ./tests/",
    "test:watch": "TS_NODE_PROJECT=tsconfig.test.json node --test --watch -r ts-node/register ./tests/",
    "test:types": "tsc --noEmit -p tsconfig.test.json"
} }
```

Execution (fast loop), types (adjacent clock), watch (derived, not duplicated) — the three clocks from [01/4.1](<../../../01 Execution Foundations and Mental Model/sections/4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>) expressed for suites. Every suite run in the repo flows through these three lines.

### Common confusion

- **"editors need separate test wiring"** — editors need the *same* wiring exposed (test-controller settings referencing the declared script, not parallel flags). Separate editor wiring drifts (flags added to scripts, not settings) — point editors at scripts, never around them.
- **"CI needs extra test flags"** — CI needs *fewer* (same command, plus reporters/coverage the runner owns natively). CI-specific transforms or loaders mean local runs don't reproduce CI — the cardinal test-wiring sin. Identical commands, environment-provided secrets only.

### Performance note

Single wiring has no runtime cost (same commands, one declaration) and compounding human savings (one behavior to learn, one failure vocabulary, one upgrade path). Multi-runner repos pay per-suite cognitive tax plus cross-runner flake taxonomy (each runner flakes differently — triage multiplies). Unity is operational performance.

### Mentor note

Audit test wiring by counting runners (one = healthy; two = migration in progress with a dated removal ticket, or a finding; three+ = archaeology). Then run the full suite three ways (script, editor, CI-equivalent env) and diff outcomes — identical results prove the wiring; any divergence is the audit's deliverable, filed before lunch.
