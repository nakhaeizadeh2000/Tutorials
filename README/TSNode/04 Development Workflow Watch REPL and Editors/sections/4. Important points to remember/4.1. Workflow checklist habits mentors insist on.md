# 4.1. Workflow checklist (habits mentors insist on)

The three habits that keep the daily loop boring: proven restarts, composed doors, and clock-split feedback. Junior read: extend the gate with three workflow stages. Expert read: which incident each stage names, and why loop behavior belongs in CI assertions rather than developer memory.

## 1) Restart proven per entry

### 1) **Definition** (the bounce rite)

No watch loop is trusted until its bounce is observed: boot the entry, edit it *and* a dependency, watch both restarts print new output. The rite runs per entry (each loop command proven), per restarter change (swapping watchers re-proves), and per major bump (watch semantics drift across versions — re-verify the pair). Trusted loops are witnessed loops; everything else is hope with a config file.

### What problem it solves (history)

Unproven loops fail in the worst way (silently stale: nodemon without `-e ts` running yesterday's code while sources change — verified all session) — and the failure presents as *code* misbehavior (stale output blamed on logic) rather than *loop* misbehavior. The rite converts loop trust from assumption to observation: one edit, one bounce, one new output — witnessed, then relied upon.

### Modern guidance

Prove loops on creation and on change (new entry, new restarter, new flags, new major — the rite takes thirty seconds and expires on each); record the proof shape in the repo (which file edited, which output changed — beside the script, as a comment or doc line); automate the re-proof where valuable (CI job editing a fixture and asserting the bounce — the gate pattern extended to time).

### Runnable example (good — the rite, recorded)

```bash
# proof record (wf/srv.ts loop): edit dependency, observe bounce with NEW value
# srv: 1  →  (edit wf/helper.ts: return 1 → return 3)  →  Restarting './wf/srv.ts'  →  srv: 3
```

```bash
# the negative proof that motivates the rite (nodemon, default exts):
# nd-run: 2 → (edit wf/nd.ts) → [nodemon] clean exit - waiting for changes before restart
# ...silence. No bounce. Stale code running. (Fixed with -e ts — [1.2](<../1. Watch and restart/1.2. Nodemon and restarter discipline compared.md>))
```

Both verified this session: the positive rite (stdlib watcher, entry + dependency) and the negative rite (nodemon defaults, silent staleness). New loops get the positive rite before first use; suspect loops get the negative check first (edit → silence? — loop guilty until proven bouncing).

### Common confusion

- **"booting proves the loop"** — booting proves *execution* (hook, config, entry all work — valuable, insufficient). Only a *change* proves the loop (observation wired, restart armed, graph followed). Boot-green + changeuntested loops are exactly the ones that go stale quietly.
- **"one proof covers all entries"** — observation is per-graph (each entry loads different files; ext lists differ per restarter invocation). Prove per loop command, not per restarter binary — the unit of trust is the command, matching the unit of pinning ([1.2](<../1. Watch and restart/1.2. Nodemon and restarter discipline compared.md>) part 3).

### Performance note

Rite cost: two boots + two edits (a minute, once per loop per change-event). Stale-loop cost: debugging phantom behavior (code accused, loop guilty) measured in hours per incident — with misdirection multipliers (stale output looks exactly like logic bugs). The most asymmetric trade in this domain after flag pinning.

### Mentor note

Make the rite the first task for every new entry ("before you code, prove the loop bounces with a new value"). Mentees internalize loop-skepticism early — every subsequent "but I saved!" moment resolves to the rite instead of despair. Thirty seconds of rite prevents hours of phantom debugging per developer per year.

## 2) Doors composed, never assumed

### 2) **Definition** (the full-composition rule)

Every loop/test/debug command composes all its doors visibly: restarter flags + hook flags + mode + scope (+ loader order where ESM participates). No slot inherited from ambient state (shell env, editor defaults, CWD luck) in committed commands — ambient slots are unreviewable, undiffable, and the first casualty of machine changes. Composition complete on screen, or it doesn't exist.

### What problem it solves (history)

Ambient-slot commands ("works in my terminal" — carrying `NODE_OPTIONS`, shell aliases, editor-injected env invisible to the repo) fail on every other machine with zero diff to inspect — the failure has no artifact, only absence. Full composition moves every slot into reviewable text (scripts, launch configs, CI env blocks), where absence becomes visible and changes become diffs.

### Modern guidance

Audit every loop/test/debug command for the slots (restarter? hook? mode? scope? loader order?): each slot either explicit in text or deliberately ambient with a comment naming the provider (`# scope via ambient TS_NODE_PROJECT (direnv .envrc) — do not rely on CWD`). Deliberate ambient beats accidental ambient — the comment converts luck into decision. [2.2](<../2. REPL and editors/2.2. Editor and debugger integration.md>)'s launch.json models the shape (env block explicit); scripts mirror it.

### Runnable example (good — the slot audit, applied)

```bash
# audit: TS_NODE_PROJECT=wf/tsconfig.json node --watch -r ts-node/register ./wf/srv.ts
#   restarter: node --watch ✓ explicit
#   hook: -r ts-node/register ✓ explicit
#   mode: (absent — full-mode default! finding: add TS_NODE_TRANSPILE_ONLY or --transpile-only)
#   scope: TS_NODE_PROJECT ✓ explicit
# verdict: 3/4 explicit — mode slot repaired before pinning
```

The audit above catches a real omission in this session's own early probe commands (mode unset — full-mode bounces). Complete composition is verified slot by slot, not felt as a whole — the audit is the instrument, the four slots are the scale.

### Runnable example (bad — the ambient loop)

```bash
# bad: developer shell carries NODE_OPTIONS="-r ts-node/register", runs:
node --watch ./src/server.ts
# works — until CI (no NODE_OPTIONS), colleague (different alias), container (clean env).
# Three environments, one invisible slot, zero diffs explaining the divergence.
```

Why it hurts: environment-coupled behavior with no artifact (the slot lives in dotfiles, not the repo) — divergence without evidence, the hardest class to triage ("works for me" × N machines). Fix: move the slot into text (script env prefix) or name it deliberately (comment + `.envrc` committed) — ambient always, accidental never.

### Common confusion

- **"env prefixes clutter scripts"** — prefixes *are* the composition (mode + scope visible per command — the alternative is invisible coupling). Clutter is aesthetic; coupling is structural — optimize scripts for auditability (slot-complete), not brevity.
- **"launch configs centralize this"** — configs centralize *debug* composition; scripts centralize *loop/test* composition. Both complete, both reviewed, neither substituting the other (the duplication is deliberate — debuggers and terminals evolve separately; audit both on invocation changes).

### Performance note

Composition audits cost minutes per command (slot checklist, once) against ambient-slot incidents (hours with misdirection, per occurrence). The audit belongs in PR review for command-touching diffs (new script? new launch config? — four slots checked before approval). Review-time minutes vs incident-time hours, every time.

### Mentor note

Teach the four-slot chant (restarter-hook-mode-scope) until mentees recite it per command unprompted. Commands passing the chant get approved; commands failing it get the missing slot named in review. Two weeks of chanting converts a team from ambient to explicit permanently.

## 3) Feedback split by clock

### 3) **Definition** (the workflow gate)

Execution (suite green), exploration (REPL probe), and configuration (winner receipt) assert as separate gate stages (exits 40/41/42) — the three clocks from [01/4.1](<../../../01 Execution Foundations and Mental Model/sections/4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>) extended to workflow: instant (REPL), repeatable (suite), structural (config). Each stage names its clock's failure without implicating the others.

### What problem it solves (history)

Monolithic workflow checks ("run the tests" as the only signal) conflate clocks (suite red: code? config? runner wiring?) — triage starts blind. Split stages isolate: suite-green-but-REPL-red means wiring (config/scope, not code); REPL-green-but-suite-red means test-tree specifics (delta, not the hook); config-stage red means structure (winner/pair, not behavior). Isolation is triage speed.

### Modern guidance

Gate the workflow per repo (suite + probe + receipt stages, exit-coded, CI-run); run the fast stages locally per change (REPL probe: seconds; suite: tens of seconds; receipt: sub-second); reserve full gates for merges (all stages, all clocks). Merge gates 1–4 (execution, config, hooks, workflow) into the one pre-flight per [02/4.1](<../../../02 Configuration and tsconfig for Execution/sections/4. Important points to remember/4.1. Config checklist habits mentors insist on.md>)'s unification rule — pedagogy splits, operations unifies.

### Runnable example (good — the workflow gate, verified)

```bash
#!/bin/bash
# workflow gate: suite green + REPL probe + test-delta winner
TS_NODE_PROJECT=wf/tsconfig.json timeout 30 node --test -r ts-node/register ./wf/tests/helper.test.ts 2>&1 | grep -q "^ok 1" || exit 40
printf 'const s: string = "g4";\nconsole.log(s);\n' | ./node_modules/.bin/ts-node --transpile-only 2>&1 | grep -q "g4" || exit 41
./node_modules/.bin/ts-node --showConfig --project wf/tsconfig.json 2>/dev/null | grep -q '"project"' || exit 42
echo WORKFLOW-GREEN
```

```bash
./gate4.sh; echo "exit=$?"
# WORKFLOW-GREEN
# exit=0
```

Verified: all three stages green (suite TAP, REPL pipe, config receipt) — the workflow equivalent of gates 1–3, same exit-code narration. Combined pre-flight across all four gates: twelve stages, twelve names, zero ambiguity about which clock failed.

### Common confusion

- **"four gates are gate bloat"** — four teaching files, one merged script in repos (unification rule — [02/4.1](<../../../02 Configuration and tsconfig for Execution/sections/4. Important points to remember/4.1. Config checklist habits mentors insist on.md>)). Bloat is unmerged process (four scripts run by hand); merged gates are one command with twelve names. Split to teach, merge to operate.
- **"workflow gates replace the rite"** — gates assert *state* (suite green now); the rite proves *liveness* (edits bounce). Rite for loops (temporal, witnessed), gates for everything stateless. Both, per part 1 — liveness can't be gated, only witnessed.

### Performance note

Workflow gate runtime: suite-dominated (tens of seconds on real trees; sub-second otherwise) — schedule per change locally for fast stages (probe + receipt), per merge for the suite. Rite cost stays manual (a minute per loop-change-event — liveness witnessed, never fully automatable by nature). Price each by its clock; never merge clocks to save scheduling thought.

### Mentor note

The graduation exercise for this domain: hand the mentee an unwired repo (no scripts, no delta, no launch config) and the four gate scripts. One hour to green-everywhere: pinned loops, proven bounces, wired tests, configured editor — each artifact citing its leaf. Fluency demonstrated, workflow internalized, incidents prepaid for the team.
