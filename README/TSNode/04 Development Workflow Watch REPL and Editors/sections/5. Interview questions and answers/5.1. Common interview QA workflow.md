# 5.1. Common interview QA: workflow

Canonical answers for the three workflow questions every TypeScript-on-Node interview asks, plus rapid-fire drills. Junior read: memorize the diagnoses. Expert read: each answer runs the evidence (receipt lines, ladders, wirings) before the conclusion — prediction first, output as confirmation.

## 1) "Nodemon ignores .ts changes" — diagnose it

### 1) **Definition** (the watchlist screen)

Entry runs once under nodemon, edits never bounce — screens for extension-watchlist reasoning: hires ask for the `watching extensions:` receipt line before anything else (absent `ts` = diagnosis complete), prescribe `-e ts,json`, and prevent with pinned scripts. Fix-without-evidence candidates ("restart it", "reinstall nodemon") fail the screen regardless of eventual success.

### What problem it solves (hiring signal)

Silent staleness (running yesterday's code while editing today's) is the workflow incident most often misdiagnosed as logic failure — the candidate's first instinct (loop vs code) predicts triage direction on every future "but I saved!" report. Evidence-first loop debugging is the single highest-leverage workflow habit; the question measures exactly it.

### Modern guidance

Answer in three beats with the verified pair: receipt (`watching extensions:` missing `ts` — evidence), fix (`-e ts,json` — one flag), prevention (pinned script + edit-test rite — [4.1](<../4. Important points to remember/4.1. Workflow checklist habits mentors insist on.md>)). The `watching path(s): *.*` red herring named unprompted (broad paths mislead; narrow extensions decide) signals genuine familiarity over rehearsal.

### Runnable example (good — the diagnosis live)

```bash
# symptom: runs once, edits silent
# nd-run: 2
# [nodemon] clean exit - waiting for changes before restart

# diagnosis (one log line, present in every nodemon boot):
# (no "watching extensions: ts" line — or extensions listing without ts)

# fix + proof:
./node_modules/.bin/nodemon -e ts --exec ./node_modules/.bin/ts-node --transpile-only --project wf/tsconfig.json ./wf/nd.ts
# [nodemon] watching extensions: ts
# [nodemon] restarting due to changes...
# nd-run: 4
```

Verified both (nodemon 3.1.14): silence without the flag, bounce with it. A hire narrates "receipt first" before touching flags; the interviewer watches the order of operations, not the outcome — outcome is guaranteed once the receipt is read.

### Common confusion (in candidates)

- **"nodemon doesn't support TypeScript"** — red flag: it executes TypeScript fine (first boot prints); it doesn't *observe* `.ts` by default. Support-vs-observe confusion reveals the candidate never separated execution from watching — the stage error from [03/1.1](<../../../03 ESM CJS and Loader Hooks Deep Dive/sections/1. Hook pipeline/1.1. resolve and load the two-stage pipeline.md>), one level up.
- **"switch to node --watch"** — yellow flag as a *first* move: valid alternative, wrong diagnostic order (fix the configured tool before auditioning replacements — otherwise every tool gets one incident before replacement, forever). Strong candidates fix, then compare.

### Performance note

No performance content (correctness incident, not speed) — candidates mentioning bounce latency here are filling air. The priced dimension is staleness duration (edits unobserved per session) and its prevention cost (one flag + one rite). Say exactly that; stop.

### Mentor note

Rehearse with the silent log on screen and flags covered: "diagnose from this output alone." Graduates point at the missing extensions line within seconds; near-misses propose restarts and reinstalls. The exercise trains receipt-reading under pressure — the transferable skill beneath the specific gotcha.

## 2) "Dev loop is slow" — profile the loop

### 2) **Definition** (the measurement-sequence screen)

"Bounces take seconds" — screens for ordered optimization: hires measure cold start first (`time` one boot), then apply the sequence (mode → restarter → tree) with the ladder numbers (full ~3× transpile-only; restarter marginal; tree structure last). Tool-first candidates ("switch to X") fail; measurement-first candidates pass before naming any tool.

### What problem it solves (hiring signal)

Loop slowness is the highest-frequency developer-experience complaint, and undisciplined fixes (restarter churn, hardware requests, framework migrations) cost more than the slowness. The measurement sequence converts complaints into arithmetic — and arithmetic into the cheapest effective fix, usually a mode flag. The question predicts whether performance work will be evidence-driven.

### Modern guidance

Answer as a procedure, not a prescription: (1) `time` the cold boot (one number, current tree); (2) if full mode, switch to transpile-only (expect ~3× — verified ladder [01/2.1](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>): 1.247s → 0.427s on 60 files); (3) if still slow, evaluate restarter reuse (ts-node-dev class) against state-leakage acceptance; (4) if still slow, profile the tree (giant barrels, decorator density, transformer load). Each step measured before the next is taken — no skipping, no combining.

### Runnable example (good — the sequence with this track's numbers)

```bash
# step 1 — measure (60-file probe tree, ts-node v10.9.2):
time ./node_modules/.bin/ts-node --project big/tsconfig.json ./big/src/main.ts
# real 0m1.247s   (full mode — the complaint, quantified)
time ./node_modules/.bin/ts-node --transpile-only --project big/tsconfig.json ./big/src/main.ts
# real 0m0.427s   (transpile-only — step-2 fix, ~3x)
```

A hire quotes the shape ("checker removal ~3×, SWC ~2× further, measured on 60 files — yours will differ, direction won't") plus the procedure; a reciter quotes a number without a tree. Interviewers: ask "what do you measure first?" — the answer ("cold boot, `time`, current tree") outranks any tool name.

### Common confusion (in candidates)

- **"faster restarter fixes slow loops"** — restarter swaps change respawn mechanics, not compile cost (fresh-process restarters tie — same cold start; reuse models help marginally). Mode dominates 10:1 — candidates leading with restarters optimize the margin while the checker bills the bulk.
- **"hardware fixes slow loops"** — cold start is compiler-bound single-threaded parsing (more cores don't parse faster — workers help suites, not boots). Candidates prescribing hardware reveal they never profiled; candidates prescribing mode reveal they did.

### Performance note

The numbers *are* the answer here (ladder quoted above, re-measured per repo). Strongest form: "measure yours with two `time` commands, expect the checker to dominate, fix mode first" — procedure plus prior (3×) plus humility (your tree differs). Numbers volunteered with sources beat numbers recited; ranges beat points.

### Mentor note

Mock with "the loop takes four seconds and the team is unhappy" — demand the measurement plan before any prescription. Mentees graduate when step 1 is always `time`, step 2 always mode, and tools enter at step 3 with deltas attached. Fashion-proof performance judgment in three steps.

## 3) "How do tests run TypeScript here?" — trace the wiring (plus rapid-fire)

### 3) **Definition** (the wiring-trace screen)

"Walk me through this repo's test execution" — screens for compositional reasoning: hires name runner + hook + delta + scope in one breath (`node --test`, `-r ts-node/register`, test tsconfig, `TS_NODE_PROJECT` — with the file each lives in), then prove it (TAP line quoted, delta shown, gate referenced). Component namers pass partially; composers pass fully.

### What problem it solves (hiring signal)

Test wiring is the most-forked infrastructure in TypeScript repos (framework + transform + config + editor, each half-migrated) — engineers who can *trace* a working wiring can *repair* a broken one and *review* a proposed one. The question predicts test-infrastructure ownership, the least glamorous and most load-bearing kind.

### Modern guidance

Answer as a trace (command → hook → delta → TAP), cite the single wiring (script name, delta file, scope env — no alternatives mentioned unless asked), and name the gates (suite green + types green, separate jobs). Follow-ups welcomed ("ESM suite?" — loader door + flag order ([03/1.1](<../../../03 ESM CJS and Loader Hooks Deep Dive/sections/1. Hook pipeline/1.1. resolve and load the two-stage pipeline.md>)); "watch?" — `--test --watch` derivation, same wiring).

### Runnable example (good — the trace, quoted)

```bash
TS_NODE_PROJECT=wf/tsconfig.json node --test -r ts-node/register ./wf/tests/helper.test.ts
# TAP version 13
# # Subtest: hook compiles the helper
# ok 1 - hook compiles the helper
```

"The `test` script composes `node --test` (runner, stdlib) with `-r ts-node/register` (hook, CJS door), scoped by `TS_NODE_PROJECT` to the test delta (which adds `esModuleInterop` the app config lacks — verified `TS1259` without it), reporting TAP green; types gate separately via `tsc --noEmit -p` on the same delta." One breath, four components, one proof — the complete answer.

### Rapid-fire drills (with answers)

1. **nodemon runs once, never bounces on `.ts` — fix?** `-e ts,json` (extension watchlist — receipt line proves it) ([1.2](<../1. Watch and restart/1.2. Nodemon and restarter discipline compared.md>)).
2. **`node: bad option: --project` — meaning?** ts-node flag given to Node (doors differ — scope via `TS_NODE_PROJECT`/discovery under `-r`) ([1.1](<../1. Watch and restart/1.1. Watch mode that restarts right.md>)).
3. **Piped REPL exits nonzero — worry?** No: full-mode pipes exit 0 *with* diagnostics printed (verified) — gate on output content, never the code ([2.1](<../2. REPL and editors/2.1. The ts-node REPL.md>)).
4. **Breakpoints don't bind in `.ts` — bisect?** `--inspect` proof first (listener+output = runtime half green → editor suspect; absent = wiring) ([2.2](<../2. REPL and editors/2.2. Editor and debugger integration.md>)).
5. **Suite fails `TS1259` under the hook — fix?** Test delta with `esModuleInterop` (style-meets-execution — app config deliberately lacks it) ([3.1](<../3. Test wiring/3.1. Test runners executing TypeScript.md>)).
6. **Gate exits 40 vs 41 vs 42 — meaning?** 40: suite red (code/tree); 41: REPL probe red (wiring/scope); 42: no config winner (structure) ([4.1](<../4. Important points to remember/4.1. Workflow checklist habits mentors insist on.md>)).

### Common confusion (in candidates)

- **"tests prove the hook works"** — tests prove *behavior through* the hook (assertions on values); hook health is proven by *dedicated* stages (trace lines, receipts, gates). Green suites with broken traces are luck, not health — candidates conflating the two skip the wiring review that matters.
- **"one test command suffices everywhere"** — suites, watch, debug, and CI share the wiring but differ in flags (derived variants, one declaration — [3.1](<../3. Test wiring/3.1. Test runners executing TypeScript.md>) part 3). Candidates reciting one command for all contexts reveal single-context experience; follow-ups ("under watch? under the debugger?") complete the screen.

### Performance note

Wiring-trace answers need no numbers (composition question, not speed) — except the loop-latency follow-up, which routes to part 2's ladder. Candidates volunteering the mode factor unprompted ("transpile-only keeps suites fast — measured 3×") show cross-part integration; the screen rewards it.

### Mentor note

Timed rapid-fire (ten seconds each, autopsy misses against this domain): six-for-six is graduation — and the quarterly team health-check. Drills 2 and 4 separate evidence-tracers (flag vocabulary, bisect reflex) from reconfigurers; ask those first when time is short.
