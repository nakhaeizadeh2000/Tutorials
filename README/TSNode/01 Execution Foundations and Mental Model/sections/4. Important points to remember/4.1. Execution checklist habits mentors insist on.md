# 4.1. Execution checklist (habits mentors insist on)

The three habits that keep TypeScript execution boring: pin-and-probe the runner, measure before shipping the hook, and schedule checking where it gates. Junior read: a copy-paste gate script. Expert read: why each line exists, which incident it prevents, and the exit-code contract supervisors rely on.

## 1) Pin it, scope it, probe it

### 1) **Definition** (the pre-flight triad)

*Pin it*: `typescript` + `ts-node` in `devDependencies`, lockfile committed, `--version` asserted. *Scope it*: the entry file resolves its tsconfig by upward search — verify *which* config (wrong-package inheritance compiled ESM as CJS live in [3.1](<../3. Loading model/3.1. Loading TypeScript under CJS and ESM.md>)). *Probe it*: a two-line erasable file runs through the hook before any real work starts.

### What problem it solves (history)

Every failure autopsied in this domain shared one trait: an assumption nobody checked. The 7.0.2 boot crash (unpinned peer), the `TS5109` (missing config), the `exports` crash (wrong config scope), the bare-`node` deploy (missing hook) — each is a 30-second probe finding that arrived as a multi-hour incident instead. The triad exists because execution assumptions rot on every bump, move, and refactor.

### Modern guidance

Run the triad after setup, after every runner/compiler/Node bump, and after moving entry files between packages. Automate the version-print half in CI (asserts the pin even where the hook never executes); keep the probe file (`hello.ts`-class, erasable-only) in the repo's contributing guide next to the three commands from [1.2](<../1. Execution identity and setup/1.2. Installing and running your first TypeScript file.md>).

### Runnable example (good — the gate script)

```bash
#!/bin/bash
# execution gate: pin + probe + checker, non-zero on any drift
./node_modules/.bin/ts-node --version >/dev/null || exit 10
./node_modules/.bin/ts-node --transpile-only ./hello.ts | grep -q "hello from" || exit 11
./node_modules/.bin/tsc --noEmit --project big/tsconfig.json || exit 12
echo GATE-GREEN
```

```bash
./gate.sh; echo "exit=$?"
# GATE-GREEN
# exit=0
```

Verified on the probe tree (ts-node v10.9.2 + TS 5.9.3): green on the clean tree. Plant the `loose.ts` type error from [1.1](<../1. Execution identity and setup/1.1. What ts-node is and is not.md>) into the project and re-run — exit `12`, the checker stage naming the culprit. Distinct exit codes per stage (10 pin, 11 probe, 12 checker) tell the on-call engineer *which* assumption rotted before they open a log.

### Runnable example (bad — the vibes-based pre-flight)

```bash
# bad: "it ran yesterday" as the entire execution strategy
./node_modules/.bin/ts-node ./src/server.ts   # after a TS bump, a move, a refactor…
# TSError at boot — now debug runner AND app together, under time pressure
```

Why it hurts: couples runner diagnosis with application diagnosis at the worst moment (deploy, demo, incident). The gate separates them for the price of one script and three seconds.

### Common confusion

- **"the gate duplicates CI"** — CI checks the *artifact*; the gate checks the *hook*. Different executors, different configs, different failures — the gate belongs where `.ts` runs directly (laptops, script jobs, hook-based environments), CI belongs where merges land.
- **"`--version` asserts nothing"** — it asserts the pin resolves (single copy, bootable binary — the 7.0.2 crash died exactly here, at boot, before any flag parsing). Cheap line, highest signal per character in the script.

### Performance note

Three seconds per gate run, triggered on bump/move — against multi-hour hook-vs-app ambiguity per incident. Automate it (postinstall or a `predev` script) and the cost drops to zero human seconds; the payoff stays step-function.

### Mentor note

Review rule: any repo executing `.ts` directly without a gate script (or equivalent CI job) gets a checklist finding, not a suggestion. Onboard mentees by breaking the probe deliberately (hide the tsconfig, plant a type error, bump nothing) and letting the gate's exit code teach the triad — failure-driven onboarding sticks.

## 2) Never ship the hook unmeasured

### 2) **Definition** (the production boundary)

Development runs the hook (fast feedback); production runs an artifact (`tsc` emit → `node dist/`, or a bundled equivalent). The boundary is crossed deliberately, with startup numbers on both sides — never by pointing a process manager at `ts-node` because the dev script was closer.

### What problem it solves (history)

`ts-node` in production start commands was once common advice, and it produced a failure class: cold containers paying full typecheck at boot (healthcheck timeouts before first request), type errors becoming runtime outages instead of build rejections, and per-boot compilation variance across replicas. Artifacts fail identically everywhere or nowhere — hooks fail per machine, per boot.

### Modern guidance

As of September 2026: `start` scripts execute `node dist/` (or the bundled output); `dev` scripts execute the hook; Docker multi-stage builds compile in the builder and copy only `dist/` + production deps. The measured ladder from [2.1](<../2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>) (1.247s → 0.427s → 0.228s on 60 files) is the *dev-loop* argument — production's argument is stronger (zero compile at boot, deterministic bytes). Shipping mechanics (build configs, dist layout, containers) are owned by [Domain 06](<../../../06 Shipping Builds Dist and Containers/README.md>) — this leaf owns the *decision*.

### Runnable example (good — the honest pair)

```jsonc
// package.json — dev runs the hook, prod runs the artifact
{
  "scripts": {
    "dev": "ts-node --transpile-only ./src/server.ts",
    "build": "tsc -p tsconfig.build.json",
    "start": "node ./dist/server.js",
    "typecheck": "tsc --noEmit"
  }
}
```

```bash
./node_modules/.bin/tsc -p tsconfig.build.json && node ./dist/server.js
# (boots with zero compilation — every replica identical)
```

### Runnable example (bad — the hook in production)

```bash
# bad: start script from [1.1](<../1. Execution identity and setup/1.1. What ts-node is and is not.md>), repeated because it keeps happening
"scripts": { "start": "ts-node ./src/server.ts" }
```

Why it hurts, priced: slowest cold start of every option (full checker per import, per replica, per restart); healthcheck races on scale-up (new replicas serve late or get killed pre-ready); error timing inverted (a type error pages on-call instead of failing the build). The one exception that proves the rule — tiny internal tools where the artifact pipeline costs more than it saves — must be a *measured* exception with the numbers in a comment, never a default.

### Common confusion

- **"transpile-only in prod is fine, it's fast"** — faster than full mode, still per-boot compilation with per-machine variance (plus the entire `devDependencies` tree, including the compiler, inside the production image). Artifacts are smaller, faster, and auditable — the image that runs is the image that was tested.
- **"serverless needs the hook"** — serverless needs *small cold starts*, which argues *against* the hook (compile on every cold boot). Bundle (esbuild/SWC) or emit ahead; the hook is the slowest possible cold start.

### Performance note

Production startup ranking (same tree, direction stable): artifact ≈ stripping > `tsx` > transpile-only > full mode — and only the artifact is *byte-identical* across replicas (cacheable, signable, diffable). The determinism dividend exceeds the speed dividend: identical bytes mean the tested thing is the running thing.

### Mentor note

Make the boundary a merge rule: any `start`/`serve`/`prod` script containing `ts-node` (or `tsx`, or `.ts` entry under bare Node below the stripping floor) fails review until the author attaches measured justification. Juniors learn fastest from the container exercise: build both images, compare sizes and cold starts — the numbers end the debate permanently.

## 3) Checking runs on its own schedule

### 3) **Definition** (the two-track cadence)

Execution iterates at human speed (save → rerun, sub-second); checking runs at pipeline speed (watch-mode `tsc --noEmit` in the editor, required gate in CI). Neither waits on the other during development; both must agree at merge. The schedule — not the tool — is the practice.

### What problem it solves (history)

Coupled schedules forced a false choice: wait on checks per rerun (slow loop, developers disabling checks to cope) or skip checks entirely (fast loop, type errors as staging surprises). The cadence split keeps both virtues: instant feedback *and* complete verification, each on its natural clock.

### Modern guidance

Three clocks: editor (`tsc --watch` or language-server diagnostics — instant, approximate), pre-push/CI (`tsc --noEmit` over the full program — complete, blocking), and the hook itself (checks nothing in transpile-only — by design). Full-mode ts-node is *not* one of the clocks (subset checking with runner diagnostics — covers neither speed nor completeness). Enforce the CI clock as a required merge gate; the rest is ergonomics.

### Runnable example (good — the schedule wired)

```jsonc
// package.json — each clock named, each clock scheduled
{
  "scripts": {
    "dev": "ts-node --transpile-only ./src/server.ts",
    "dev:types": "tsc --noEmit --watch",
    "typecheck": "tsc --noEmit",
    "prepush": "npm run typecheck"
  }
}
```

```bash
# terminal 1: instant reruns (checker never blocks the loop)
npm run dev
# terminal 2: inline type feedback (watch-mode, incremental)
npm run dev:types
# CI: the gate (exit non-zero blocks the merge — verified exit 12 above)
npm run typecheck
```

### Runnable example (bad — one clock for both jobs)

```bash
# bad: full-mode ts-node as the only "checking" in the loop
"scripts": { "dev": "ts-node ./src/server.ts" }
# slow reruns AND subset diagnostics — pays the checker's cost,
# receives half the checker's value, CI gate absent
```

Why it hurts: worst of both worlds quantified in [2.1](<../2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>) (full-mode startup cost) and [2.2](<../2. Modes and configuration/2.2. The tsconfig that executes.md>) (subset vs program checking). Fix: split the clocks — the three lines above cost minutes to add and pay back daily.

### Common confusion

- **"watch-mode `tsc` plus transpile-only duplicates work"** — they compile separately, yes, and that is the point: each optimizes its own axis (speed vs completeness) instead of compromising both. Shared nothing, blocked never — duplication of *compute* in exchange for decoupling of *schedules*.
- **"CI-only checking suffices"** — CI catches errors at merge latency (minutes to hours after authoring); watch-mode catches them at authoring latency (seconds). Both clocks earn their keep — CI for the merge guarantee, watch for the author.

### Performance note

Watch-mode checking is incremental (only changed files re-resolve — seconds on thousand-file trees where cold `tsc --noEmit` takes tens of seconds). Price the CI clock once (cold check duration → pipeline budget); price the dev clock never (incremental cost is noise). Scaling the checker further (references, composite) is owned by TypeScript 19 — linked, not repeated.

### Mentor note

Ask mentees to draw their repo's two clocks (who runs what, when, blocking whom) on a whiteboard. Missing clocks are visible instantly — no clock runs the checker (no `typecheck` anywhere), or one clock does double duty (full-mode dev). The drawing exercise converts abstract advice into a concrete wiring diff.
