# 6.1. Boundaries: what is covered elsewhere

Where this domain stops and who owns the rest — the DRY map for the whole track. Junior read: if your question isn't answered here, this page names the page that answers it. Expert read: the single-source-of-truth assignments that keep seven domains from re-teaching each other.

## 1) Language and pipeline theory (TypeScript track owns the what)

### 1) **Definition** (the theory boundary)

*Why* TypeScript erases, *which* syntax erases, *how* the pipelines compare, *what* each compiler flag means, and *how* the language server works are language knowledge — owned by the TypeScript track, assumed here, never restated. This domain owns only the *running*: invoking ts-node, scoping its config, choosing its mode, wiring its gates.

### Common confusion

- **"this domain should explain erasable syntax fully"** — explaining it here duplicates the inventory in two places, and duplicates drift (one place updates, the other lies). One-line mention plus link is the entire policy — DRY is a correctness practice, not tidiness.
- **"boundaries mean shallow coverage"** — boundaries mean *placed* coverage: this domain goes deeper than anywhere else on hooks, modes, gates, and loading precisely because it refuses to spend pages on theory owned elsewhere.

### Mentor note

## 3) Runtime mechanics (Node.js track owns the engine room)

### 3) **Definition** (the runtime boundary)

What happens *after* compilation — event-loop phases, process lifecycle, CJS/ESM resolution inside Node, workers, sockets, diagnostics — is runtime knowledge owned by the Node.js track. ts-node compiles *to* that runtime; it never changes it. A scheduling bug under ts-node is a Node bug with TypeScript spelling, diagnosed with Node tools.

### The assignments (with the exact targets)

- Process model, globals, lifecycle, CJS/ESM interop → [NodeJS 01: Runtime Fundamentals](<../../../../NodeJS/01 Runtime Fundamentals and Mental Model/README.md>). [3.1](<../3. Loading model/3.1. Loading TypeScript under CJS and ESM.md>) teaches ts-node's *hooks into* these systems; the systems themselves live there.
- Packages, lockfiles, `node_modules` resolution → [NodeJS 02: Packages and Layout](<../../../../NodeJS/02 Packages Scripts and Project Layout/README.md>). [1.2](<../1. Execution identity and setup/1.2. Installing and running your first TypeScript file.md>) pins the runner; package mechanics live there.
- Service debugging (inspector, profiles, shipping) → [NodeJS 06: Debugging, Configuring, Shipping](<../../../../NodeJS/06 Debugging Configuring and Shipping/README.md>). Domain 05 will teach the *TypeScript layer* (sourcemaps, TS-aware profiles); the service mechanics live there.

### Common confusion

- **"a ts-node stack trace is a ts-node problem"** — traces point at compiled output plus sourcemaps; the *behavior* in the trace is Node's (timers, sockets, workers unchanged by the hook). Debug the runtime with runtime tools; fix the map with Domain 05's tools. Conflating the two layers doubles every debugging session.
- **"this track replaces Node.js 01"** — it assumes it. Readers arriving without the Node runtime model should read NodeJS 01 first (declared in this domain's `## 0. Prerequisites`) — the hook model makes no sense atop a missing runtime model.

### Mentor note

The one-sentence router for mentees: "TypeScript questions go left (TypeScript track), Node questions go right (Node.js track), *running-TypeScript-on-Node* questions stay here." Three tracks, no overlap, every question housed — that sentence is worth more than any single leaf.
