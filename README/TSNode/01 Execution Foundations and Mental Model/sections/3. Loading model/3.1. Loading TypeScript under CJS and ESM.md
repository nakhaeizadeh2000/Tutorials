# 3.1. Loading TypeScript under CJS and ESM

How ts-node feeds TypeScript into Node's two module systems — the require hook for CJS, the loader hook for ESM — and why Node's resolution rules (extensions, `package.json` `type`, config scope) still decide everything before compilation starts. Junior read: CJS just works; ESM needs three things to agree. Expert read: the exact failure each disagreement produces, all reproduced live.

## 1) CJS via require hook

### 1) **Definition** (extending what require understands)

Under CommonJS, ts-node patches `require.extensions` (via `-r ts-node/register` or the CLI, which registers the same hook): when Node resolves a `.ts` file, the hook compiles it with the project tsconfig and hands JavaScript back to the normal CJS pipeline — synchronous, cached in `require.cache`, invisible downstream. Required files cannot tell they were ever TypeScript.

### What problem it solves (history)

CJS is synchronous and extension-driven, so teaching it one more extension was a small, stable patch — the reason ts-node's CJS path matured years before ESM existed and remains the lowest-friction door. Monorepo tools, test runners, and config files (`webpack.config.ts`, `eslint.config.ts`) all ride this hook without knowing it.

### Modern guidance

CJS services: keep `"module": "commonjs"`, enter through the CLI or `-r ts-node/register`, and write imports exactly as NodeJS 01/2.2 teaches (extensionless relative paths resolve — the hook changes *compilation*, never *resolution*). Transpile-only for iteration, full mode for one-shots — the mode split from [2.1](<../2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>) applies unchanged.

### Runnable example (good — extensionless CJS chain through the hook)

```typescript
// cjs/helper.ts
export function help(): string { return "helped"; }

// cjs/main.ts — extensionless, exactly as in JS
import { help } from "./helper";
console.log("cjs:", help());
```

```bash
./node_modules/.bin/ts-node --transpile-only --project cjs/tsconfig.json ./cjs/main.ts
# cjs: helped
```

Verified (ts-node v10.9.2, `module: commonjs`): extensionless specifier resolves, hook compiles, CJS cache holds the result. The same chain through `node -r ts-node/register` behaves identically — door differs, pipeline doesn't.

### Common confusion

- **"the hook makes `require` asynchronous"** — never: CJS stays synchronous end to end (top-level `await` in a `.ts` file under CJS is a compile error, not a feature). Async entry points mean ESM — different door, below.
- **"compiled output is cached on disk"** — the CJS cache is in-memory per process (plus ts-node's optional on-disk transpile cache, a startup optimization, not a build artifact). Every process boot recompiles — the reason cold-start numbers from [2.1](<../2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>) matter.

### Performance note

Require-hook overhead per file is one transpile plus one CJS wrap — the 0.427s sixty-file measurement from [2.1](<../2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>) *is* this hook's cost profile. Circular imports cost the same half-initialized-exports dance as JS (the hook doesn't fix cycles — it inherits them).

### Mentor note

Teach CJS loading as "Node unchanged, one extension added": any mentee fluent in `require` resolution already knows 90% of this path. Spend the saved time on ESM below — that is where the misconceptions live.

## 2) ESM via loader hook

### 2) **Definition** (teaching the ESM pipeline a new format)

Native ESM resolves and loads asynchronously through a hook chain (`resolve` → `load`). ts-node's ESM entry (`--loader ts-node/esm`, modern form `--import` + `register()`) appends a link that compiles `.ts` during `load` and returns JavaScript with the correct `format`. Three slots must agree: `package.json` `type` (or `.mts`/`.cts` extensions) names the format, the tsconfig `module`/`moduleResolution` pair emits it, and the loader flag installs the hook.

### What problem it solves (history)

ESM's pipeline was designed closed (known extensions, known formats) — TypeScript arrived as a foreign format with no seat. The loader hook is that seat: without it, `Unknown file extension ".ts"` (reproduced in [2.2](<../2. Modes and configuration/2.2. The tsconfig that executes.md>)); with it, ESM graphs import `.ts` natively, top-level `await` included.

### Modern guidance

As of September 2026: prefer the `register()` form Node's warning steers toward (`--import 'data:...register("ts-node/esm"...)'`) over bare `--loader` (still works, deprecation-warning attached — verified live on Node v20.20.2 this session). Scope config explicitly (`TS_NODE_PROJECT` or Climatching `--project` where the CLI owns the process) — the upward search starts at the *entry file*, and a monorepo entry easily inherits the wrong package's pair. Full ESM specifier discipline (extensions, `type`, `allowImportingTs`/`rewriteRelativeImportExtensions` on TS 5.7+) is owned by TypeScript 12/01-3.2 and linked, not restated.

### Runnable example (good — all three slots agreeing)

```typescript
// esm/helper.ts + esm/entry.ts (package type: module, NodeNext pair)
import { help } from "./helper.js";
console.log("esm:", help());
```

```bash
TS_NODE_PROJECT=esm/tsconfig.json node --loader ts-node/esm ./esm/entry.ts
# esm: helped-esm
```

Verified: `.js`-suffixed specifier (NodeNext ESM rule), `type: module`, scoped config — prints. Note the specifier says `.js` while the file on disk is `helper.ts`: under NodeNext, TypeScript resolves `.js` → `.ts` deliberately (the mapping TypeScript 22 documents for `rewriteRelativeImportExtensions`).

### Runnable example (bad — two disagreements, two autopsies)

```bash
# bad 1: right loader, wrong config scope (root commonjs tsconfig inherited)
node --loader ts-node/esm ./esm/entry.ts
# ReferenceError: exports is not defined in ES module scope
```

Why it hurts: CJS emit landed inside an ES module scope — the error blames `exports` (a *symptom* three layers from the cause: config scope). Fix: scope the project (`TS_NODE_PROJECT`) so the ESM pair compiles the entry. Config scope is a loading concern, not a style preference.

```bash
# bad 2: extensionless specifier under ESM
# esm/bad-entry.ts: import { help } from "./helper";
TS_NODE_PROJECT=esm/tsconfig.json node --loader ts-node/esm ./esm/bad-entry.ts
# (uncaught exception — ESM resolution refuses extensionless relatives)
```

Why it hurts: the identical import works under CJS (verified above: `cjs: helped`) and dies under ESM — the hook compiles, but *resolution runs first* and resolution is Node's, not ts-node's. Fix: explicit extensions under ESM, always (lint it: the rule belongs in the review checklist, [4.1](<../4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>)).

### Common confusion

- **"ts-node ESM is slower than CJS"** — marginally (async pipeline stages vs sync require), but the measured gap is noise beside the mode gap from [2.1](<../2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>) (checker vs no-checker dwarfs hook-vs-loader). Choose the system by package architecture, never by startup folklore.
- **"`--loader` is stable API"** — Node still prints `ExperimentalWarning` for `--experimental-loader` on v20.20.2 and steers to `register()`. Pin the invocation form per Node major and re-check on upgrade — loader API is the fastest-moving surface in this domain.

### Performance note

Loader-hook cost per module is one async round-trip plus transpile — parallelizable across the graph (ESM's structural advantage: independent branches compile concurrently where CJS serializes). On wide graphs ESM loading can *beat* CJS wall-clock despite costlier per-module work — measure graph shape (`--cpu-prof` on boot, or simply `time` both systems on your entry) before theorizing.

### Mentor note

Teach ESM loading as a three-slot checklist (format signal, compiler pair, hook flag) and make mentees diagnose bad-1/bad-2 blind: cover the answers, show the error, ask "which slot disagrees?" Fluency here is the difference between a five-minute fix and a lost afternoon — it is also exactly what interviewers probe ([5.1](<../5. Interview questions and answers/5.1. Common interview QA execution foundations.md>)).

## 3) Extension and specifier rules still apply

### 3) **Definition** (resolution runs before compilation)

ts-node compiles *after* Node resolves: the specifier in the `import`/`require` statement must satisfy Node's resolver (or TypeScript's `moduleResolution` mirroring it) exactly as written. The hook never rewrites specifiers (except the documented `.ts`↔`.js` mapping under `allowImportingTs`/`rewriteRelativeImportExtensions`, TS 5.7+); getting the path wrong fails identically with or without ts-node installed.

### What problem it solves

Conflating "TypeScript can't find my module" (resolution) with "ts-node can't compile my module" (transpilation) sends debugging down the wrong half of the pipeline — tsconfig `paths` edited when the fix was a missing extension, loader flags debated when the fix was `package.json` `type`. The boundary ("resolve first, compile second") assigns every failure to its half in seconds.

### Modern guidance

Debug in pipeline order: (1) does bare-Node resolution accept the specifier? (`node --check` on the emitted shape, or resolve-tracing); (2) only then, does the hook compile it? Portability rule: write specifiers the *strictest* consumer accepts (explicit extensions, `type`-consistent) and every runner — ts-node CJS/ESM, `tsx`, stripping — resolves them identically. That discipline is what makes sources runner-portable, the property [2.2](<../2. Modes and configuration/2.2. The tsconfig that executes.md>)'s strictness section exists to guarantee.

### Runnable example (good — one import, two systems, both green)

```bash
# CJS: extensionless resolves (verified above)
./node_modules/.bin/ts-node --transpile-only --project cjs/tsconfig.json ./cjs/main.ts
# cjs: helped

# ESM: explicit .js specifier resolves to the .ts file (verified above)
TS_NODE_PROJECT=esm/tsconfig.json node --loader ts-node/esm ./esm/entry.ts
# esm: helped-esm
```

Same intent, system-correct spelling each time. A codebase mixing both systems (dual packages, migration periods) carries both spellings deliberately — uniformity across systems is the actual bug (bad-2 above is what it compiles to).

### Runnable example (bad — blaming the hook for a resolution failure)

```bash
# bad: "fixed" by switching runners instead of fixing the specifier
# ./esm/bad-entry.ts fails under ts-node loader →
#   try tsx → same failure → try stripping → same failure →
#   afternoon lost; the specifier was extensionless all along
```

Why it hurts: runner-swapping as a diagnostic multiplies variables (three runners' quirks) while the constant — the specifier — sits unexamined. Fix: reproduce under bare `node` first (strip the hook from the experiment); if bare Node fails too, the hook was never the suspect.

### Common confusion

- **"`paths`/`baseUrl` fix runtime resolution"** — they fix the *checker's* resolution (and the editor's); at run time, bare Node still needs real files at the written paths (or a resolver that honors the mapping — owned by bundlers and [Domain 03's `paths` recipe](<../../../03 ESM CJS and Loader Hooks Deep Dive/sections/3. Runtime recipes/3.1. The runtime paths recipe.md>)). `paths` without runtime support is the most common "typechecks, crashes" shape in TypeScript-on-Node.
- **"allowImportingTs means write `.ts` in imports"** — the flag *permits* `.ts` specifiers where the emitter rewrites them (TS 5.7+ `rewriteRelativeImportExtensions`); without the rewrite paired, `.ts` specifiers crash every runner except the checker. Pair or perish — and keep the pair in the same tsconfig the runner reads.

### Performance note

Resolution cost is per-import filesystem probing (extension search order, `node_modules` walk) — identical under ts-node and bare Node, and the reason explicit extensions are *faster* as well as safer (fewer probes per specifier). On huge graphs the probe count dominates cold start measurably — explicitness is a performance practice wearing a correctness costume.

### Mentor note

Institutionalize "bare-Node-first" as the team's module-debugging liturgy: any import failure gets 60 seconds under `node` (or `node --check`) before ts-node enters the conversation. Print it on the onboarding page; it halves module-debugging time within a month.
