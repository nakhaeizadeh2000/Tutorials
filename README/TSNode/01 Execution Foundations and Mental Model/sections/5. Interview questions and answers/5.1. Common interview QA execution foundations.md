# 5.1. Common interview QA: execution foundations

Canonical answers for the three execution questions every Node+TypeScript interview asks, plus rapid-fire drills. Junior read: memorize the layer sentences. Expert read: each answer contains a *priced judgment* (numbers from this domain's probes) and a *diagnostic trace* (an error from this domain, autopsied live) — that is what distinguishes a senior answer from a recited one.

## 1) "How does ts-node run TypeScript?" — answer in layers

### 1) **Definition** (the precision screen)

The question screens for the hook model from [1.1](<../1. Execution identity and setup/1.1. What ts-node is and is not.md>): candidates who say "it runs TypeScript" stop at layer one; hires walk all three — hook (loader registration on `require`/ESM pipeline), compile (TypeScript transpiler per import, tsconfig-governed), execute (plain JavaScript on V8; types never reach the engine).

### What problem it solves (hiring signal)

Teams running TypeScript-on-Node debug boot failures weekly (config scope, mode confusion, loader mismatches — this domain's entire catalog). A candidate with the layered model diagnoses them in minutes; one without re-derives the model per incident. The question predicts on-call performance directly.

### Modern guidance

Answer in layers, each with its evidence: layer 1 (hook — evidence: bare `node hello.ts` throws `SyntaxError` on the annotation, ts-node prints); layer 2 (modes — evidence: `TS2322` gates full mode, transpile-only prints `runs: not a number`); layer 3 (config — evidence: missing tsconfig kills both modes differently, `Unknown file extension` vs `TS5109`). All three evidences verified in this domain's probes (ts-node v10.9.2 + TS 5.9.3). End with the boundary: production runs artifacts, the hook develops them ([4.1](<../4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>)).

### Runnable example (good — the 60-second live trace)

```bash
# the candidate narrates each line BEFORE running it:
./node_modules/.bin/ts-node ./hello.ts        # hook compiles, prints
node ./hello.ts 2>&1 | head -2                # no hook: annotation is a SyntaxError
./node_modules/.bin/ts-node --transpile-only ./loose.ts   # gate open: runs
./node_modules/.bin/ts-node ./loose.ts 2>&1 | head -2     # gate shut: TS2322
```

```bash
# verified outputs, in order:
# hello from ts
# const label: string = "ts";  (+ SyntaxError caret)
# runs: not a number
# TSError: ⨯ Unable to compile TypeScript:  (+ TS2322)
```

A hire narrates the *mechanism* per line (hook presence, gate state) before the output confirms it. A reciter describes outputs after the fact. Interviewers: ask "what would change under `--transpile-only`?" before running line 4 — prediction separates models from memories.

### Common confusion (in candidates)

- **"ts-node type-checks, so no `tsc` needed"** — red flag: full mode checks the imported subset with runner diagnostics. Strong candidates name `tsc --noEmit` as the merge gate unprompted ([2.1](<../2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>)).
- **"the hook is only for dev"** — yellow flag: true by default, but script jobs, CLIs, and hook-based test environments run it legitimately. Strong candidates ask *where* before judging.

### Performance note

Interviewers who ask "how much does the hook cost?" expect the shape, not the number: per-import transpile, checker-dominated cold start, ~3× mode gap on real trees (1.247s → 0.427s measured in [2.1](<../2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>)). Candidates quoting the shape plus "measure yours" outscore candidates quoting any single number.

### Mentor note

Rehearse mentees with the four-line trace above until narration precedes output fluently. The drill doubles as the onboarding handshake from [1.2](<../1. Execution identity and setup/1.2. Installing and running your first TypeScript file.md>) — interview prep and team practice in one exercise.

## 2) Transpile-only versus typecheck: which and why?

### 2) **Definition** (the latency judgment question)

The interviewer grants a scenario (dev server, CI pipeline, production deploy, one-off script) and the candidate places checking and execution on schedules — transpile-only vs full mode, `tsc --noEmit` placement, SWC candidacy. Scored on *constraint response*: same candidate must answer differently per scenario, with the delta priced.

### What problem it solves (hiring signal)

Mode choice is the highest-frequency judgment in TypeScript-on-Node operations (every repo, every environment). Candidates with one answer for all scenarios ("always transpile-only", "always full check") will misconfigure exactly the environments they haven't considered. The question exposes single-answer thinking in ninety seconds.

### Modern guidance

Canonical matrix (as of September 2026): dev loop → transpile-only + watch-mode `tsc` (instant reruns, inline feedback); CI → `tsc --noEmit` required gate (complete program check); production → artifact, no hook (deterministic bytes); one-off script → full mode (one command, both jobs, negligible cost). SWC iff transpile-only misses budget *and* the delta is measured ([2.1](<../2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>) ladder: 1.247s → 0.427s → 0.228s). Candidates should volunteer the matrix before being walked through it.

### Runnable example (good — scenario answers with teeth)

```bash
# scenario: "dev server, 300 files, checker already in CI"
# answer: transpile-only (checker-bound seconds removed from every restart),
# plus `tsc --noEmit --watch` beside it — evidence: the 60-file 3× gap

# scenario: "production deploy"
# answer: neither mode — `tsc -p tsconfig.build.json && node dist/`
# evidence: per-boot compile variance + healthcheck races ([4.1](<../4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>))

# scenario: "the gate script exits 12 on a clean-looking tree"
# answer: stage 12 is the checker — a type error exists somewhere in the
# program (verified: planted TS2322 → exit 12). Read the tsc output, not the app logs.
```

### Common confusion (in candidates)

- **"transpile-only is unsafe"** — incomplete without "unless `tsc --noEmit` gates merges." Safety is a property of the *pipeline* (two tracks), never of the *flag*. Candidates who locate safety in CI score; candidates who locate it in the runner flag don't.
- **"SWC replaces the checker"** — disqualifying-adjacent: SWC never typechecks. Any answer pairing `--swc` with checker removal fails the question regardless of other strengths.

### Performance note

Strong candidates quantify with the domain's ladder (order-of-magnitude: checker removal ~3×, SWC ~2× further, all on 60 files) and hedge correctly ("your tree, your numbers — one `time` each"). Numbers volunteered with sources beat numbers recited; ranges beat points.

### Mentor note

Mock-interview this question with scenario cards (dev/CI/prod/script/suite) and demand a different answer per card with a price attached. Mentees graduate when no card takes longer than thirty seconds — speed here reflects compiled judgment, not memorization.

## 3) ts-node vs tsx vs native stripping (plus rapid-fire)

### 3) **Definition** (the runner judgment question)

"How do you run TypeScript, and when ts-node?" — scored as a constraint table: rows (tsc-emit, ts-node full, ts-node transpile-only, `tsx`, stripping), columns (checks? / non-erasable? / startup / needs install?). Full marks require *ts-node's niche stated positively* (compiler-faithful execution, optional checking, transformers, REPL, deep tsconfig integration) — not merely "slower tsx".

### What problem it solves (hiring signal)

Runner churn is constant (stripping matured across Node 22→24, `tsx` dominates mindshare) and teams need engineers who choose by constraint, not fashion. Candidates who default to one runner for every job will standardize the wrong tool the quarter after hiring. The table answer predicts tooling leadership.

### Modern guidance

As of September 2026: erasable-only sources (`erasableSyntaxOnly`) so every runner accepts them; develop via a fast JIT (measure `tsx` vs transpile-only on your tree); gate with `tsc --noEmit`; ship artifacts; keep ts-node where its compiler hooks earn it (transformers, API, REPL). The survey itself lives in [TypeScript 01/3.2](<../../../../TypeScript/01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>) — candidates should cite it as the reference, not reproduce it from memory.

### Runnable example (good — the table, filled)

| Runner | Checks? | Non-erasable? | Startup (60 files) | Install? |
|---|---|---|---|---|
| `tsc` + `node dist/` | yes (at build) | yes | fastest at boot (no compile) | compiler only |
| ts-node full | yes (per import) | yes | slowest (1.247s) | ts-node + TS |
| ts-node transpile-only | no | yes | mid (0.427s) | ts-node + TS |
| ts-node `--swc` | no | yes | fast (0.228s) | + @swc/core |
| `tsx` | no | yes (esbuild) | fast | tsx |
| stripping (Node v22.18+) | no | **no** (refuses) | fastest (delete-only) | none (built in) |

Timings verified this domain; `tsx`/stripping rows documented from official sources (single source of truth in TypeScript 01/3.2 — this table *applies* it to ts-node's row, never restates the survey). The killer follow-up: "your tree has three `enum`s and must run flagless on Node 24?" — answer: strip the enums (erasable idioms) or drop stripping; ts-node/`tsx` accept them either way.

### Rapid-fire drills (with answers)

1. **`TS5109` on boot — cause?** Half a `module`/`moduleResolution` pair (or missing tsconfig defaulting into NodeNext). Fix: set the pair together ([2.2](<../2. Modes and configuration/2.2. The tsconfig that executes.md>)).
2. **`exports is not defined in ES module scope` — cause?** CJS emit loaded as ESM — wrong config scope (root commonjs config inherited by an ESM entry). Fix: `TS_NODE_PROJECT` scoping ([3.1](<../3. Loading model/3.1. Loading TypeScript under CJS and ESM.md>)).
3. **Extensionless import works in CJS, dies in ESM — why?** Resolution runs before compilation; ESM requires explicit extensions, CJS doesn't. Fix the specifier, not the runner ([3.1](<../3. Loading model/3.1. Loading TypeScript under CJS and ESM.md>)).
4. **`erasableSyntaxOnly` on, `enum` still runs under transpile-only — broken?** No: the flag gates the checker, never the runner. The CI gate (missing) is the bug, not the flag ([2.2](<../2. Modes and configuration/2.2. The tsconfig that executes.md>)).
5. **ts-node 10 + TypeScript 7 — safe upgrade?** No (verified boot crash, peer incompat). Pin, test the matrix, read the peer range ([1.2](<../1. Execution identity and setup/1.2. Installing and running your first TypeScript file.md>)).
6. **Dev loop slow on 300 files — first lever?** Mode, not tool: full → transpile-only (checker-bound seconds), then SWC iff still over budget — each rung measured ([2.1](<../2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>)).

### Common confusion (in candidates)

- **"stripping replaces ts-node"** — only for erasable-only sources on new-enough Node (local v20 in this domain has no stripping at all). Version-gated, syntax-gated — candidates stating both gates pass; either gate omitted is a flag.
- **"one runner for everything"** — the single most expensive sentence in this interview. Environments differ (loop vs gate vs artifact); the answer must differ with them.

### Performance note

Interview numbers need only shape + source: "checker removal ~3×, SWC ~2× further, measured on 60 files with `time` — yours will differ, direction won't." Candidates who say "measure yours" unprompted signal seniority more reliably than any memorized figure.

### Mentor note

Run rapid-fire as a timed game (10 seconds per answer, then autopsy the misses against this domain's leaves). Six-for-six under time pressure is the graduation bar — and the same six questions make an excellent team health-check quiz quarterly.
