# 2.1. Transpile-only versus full typechecking

ts-node's two execution modes — full typechecking per import versus strip-and-run — plus the third-party-transpiler escalator for when the compiler itself is the bottleneck. Junior read: `--transpile-only` makes startup fast; `tsc --noEmit` keeps it honest. Expert read: measured numbers on a 60-file tree, the exact failure each mode catches, and when SWC earns its extra dependency.

## 1) Two modes, one default to question

### 1) **Definition** (the gate on the hook)

Full mode (the default) runs the TypeScript checker on every file the hook compiles and refuses to execute on type errors. Transpile-only (`--transpile-only`, `TS_NODE_TRANSPILE_ONLY=true`, or the `ts-node-transpile-only` binary) transpiles each file in isolation — types deleted, never examined — and runs whatever remains. Same hook from [1.1. What ts-node is and is not](<../1. Execution identity and setup/1.1. What ts-node is and is not.md>); different gate.

### What problem it solves (history)

Full checking made every run pay for whole-program reasoning at import time: servers with hundreds of files started in many seconds, editors' save-and-rerun loop stalled, and errors surfaced twice (ts-node at boot, `tsc` in CI). Transpile-only — added as a first-class flag precisely for this pain — moved checking out of the hot path while keeping the same hook, same tsconfig, same output for correct code.

### Modern guidance

Question the default per environment: full mode for one-file scripts (checking inline costs nothing measurable); transpile-only everywhere a human waits on startup (dev servers, watch loops, test suites). As of September 2026 the community default has settled — transpile-only to run, `tsc --noEmit` to gate — and full mode in a large service's start script is a review finding until measured otherwise.

### Runnable example (good — same tree, both modes, priced)

```bash
# 60-file generated tree, ts-node v10.9.2 + TypeScript 5.9.3:
./node_modules/.bin/ts-node --project big/tsconfig.json ./big/src/main.ts
# mods: 60 first: {"id":0,"name":"m0","tags":["a","b"]}
# real 0m1.247s

./node_modules/.bin/ts-node --transpile-only --project big/tsconfig.json ./big/src/main.ts
# mods: 60 first: {"id":0,"name":"m0","tags":["a","b"]}
# real 0m0.427s
```

Verified: identical output, ~3× startup gap — the checker's share, priced in seconds on one machine. And the gate behaves as [1.1](<../1. Execution identity and setup/1.1. What ts-node is and is not.md>) promised: a `TS2322` file aborts full mode and sails through transpile-only.

### Runnable example (bad — full mode as the dev-loop default)

```bash
# bad: every save-and-rerun pays the full check on a 300-file service
"scripts": { "dev": "ts-node ./src/server.ts" }
```

Why it hurts: latency (seconds per restart, hundreds of restarts per day per developer), duplication (CI's `tsc --noEmit` reports the same errors with file-and-line context anyway), and misleading blame ("the app is slow to start" misdiagnosed when the runner is the cost). Fix: `"dev": "ts-node --transpile-only ./src/server.ts"` plus a parallel `tsc --noEmit --watch` for inline feedback.

### Common confusion

- **"transpile-only skips parsing"** — it parses fully (syntax errors still abort: `TSError` on malformed code) and transpiles per file; it skips only *type resolution*. A missing bracket fails in both modes; a wrong type fails in one.
- **"`--transpile-only` changes emit"** — for correct code the emitted JavaScript is identical (same compiler, same transpile pass — only the check pass is dropped). The flag changes *gating*, never *output*.

### Performance note

The 1.247s → 0.427s measurement above is the shape, not the number: gap scales with file count, `strict` surface, and decorator/transformer load; it shrinks to noise under ~10 files. Measure yours with `time` on both modes before standardizing — one command each, same tree, cold cache (`rm -rf` any `.tsbuildinfo` first so the full run cannot cheat).

### Mentor note

Run the two timings live in front of the mentee and ask *before* revealing: "which output differs?" (Neither — that is the point.) The lesson that sticks: modes differ in *error timing*, never in *correct-code behavior*. Anyone choosing a mode without timing both is guessing.

## 2) Separate checking from running

### 2) **Definition** (the two-track pipeline)

Execution (`ts-node --transpile-only`, `tsx`, stripping) optimizes for feedback speed; checking (`tsc --noEmit`) optimizes for error completeness. The pipeline runs them as separate tracks: the runner never gates on types, the checker gates merges — each scheduled where its cost hurts least.

### What problem it solves

Coupled mode forced one schedule on two concerns: developers waited on checks during iteration, or — flipped the other way — transpile-only repos with no checker anywhere shipped type errors to production. Separation gives each concern its natural cadence: instant reruns locally, complete verification at merge.

### Modern guidance

Wire it thrice: `dev` script runs transpile-only; editor/CI runs `tsc --noEmit` (with `--watch` locally for inline feedback); merge gates require the checker green. The checker that matters is the project-wide program (`tsc -p tsconfig.json`), never the hook's per-import subset — full-mode ts-node checks only what gets imported.

### Runnable example (good — the checker catches what the runner skips)

```bash
# loose.ts content placed inside the project: runner silent, checker loud
./node_modules/.bin/ts-node --transpile-only ./big/src/main.ts
# (runs — no per-import complaint about other files)

./node_modules/.bin/tsc --noEmit --project big/tsconfig.json
# big/src/loose-check.ts(1,7): error TS2322: Type 'string' is not assignable to type 'number'.
```

Verified: transpile-only executes without comment; `tsc --noEmit` reports `TS2322` with file, line, and column. On the clean tree the same command prints nothing and exits 0 (`CLEAN-OK` in this session's probe) — silence is the pass signal, teach mentees to read it as such.

### Runnable example (bad — transpile-only with no checker anywhere)

```jsonc
// bad: package.json scripts with fast execution and zero verification
{ "scripts": { "dev": "ts-node --transpile-only ./src/server.ts", "build": "tsc -p tsconfig.build.json" } }
// "build" emits — but nothing ever runs the checker over the dev tree,
// so a type error surfaces as a wrong runtime value in staging, not red CI
```

Why it hurts: emit without `--noEmit`-style gating checks only *emittability*, and transpile-only execution checks nothing — the error in `loose.ts` (`runs: not a number`, verified in [1.1](<../1. Execution identity and setup/1.1. What ts-node is and is not.md>)) ships as behavior, not as a diagnostic. Fix: a `typecheck` script (`tsc --noEmit`) wired into CI as a required gate.

### Common confusion

- **"`tsc` emit in build covers checking"** — emit typechecks as a side effect, but builds often scope to subsets (`include: ["src"]` vs tests, configs, scripts) and developers skip reading build warnings. An explicit `typecheck` script over the full program is the gate; the build is a beneficiary.
- **"full-mode ts-node is the checker"** — it checks the imported subset with runner-flavored diagnostics (no project-wide unused checks, no declaration-emit errors). Gating merges on it is gating on a sample.

### Performance note

`tsc --noEmit` on the 60-file probe tree completes in well under a second — but it scales superlinearly past thousands of files (project references and incremental builds, owned by TypeScript 19, linked below). Schedule accordingly: watch-mode locally (incremental, cheap), full cold check in CI (complete, priced once per merge).

### Mentor note

Review rule: any repo whose scripts contain `transpile-only` (or `tsx`, or stripping) without a `typecheck` script wired to CI gets a blocking comment. The check takes one line of JSON; its absence is the highest-severity cheap finding in this domain.

## 3) SWC when the compiler is the bottleneck

### 3) **Definition** (the third-party transpiler door)

ts-node delegates per-file transpilation to a faster engine — `--swc` (backed by `@swc/core`, Rust) instead of the TypeScript transpiler — while keeping ts-node's hooks, tsconfig parsing, and CLI. Checking still belongs to `tsc --noEmit`; SWC only makes the strip step faster.

### What problem it solves

On large trees even transpile-only spends its startup inside the TypeScript transpiler (parsing + isolated emit per file, single-threaded JS). SWC's Rust parser cuts that remainder — the last mechanical slice of startup after checking is removed. It exists for the services where 0.4s is still too slow: giant monorepo packages, CLI tools graded on cold start, test suites spawning hundreds of workers.

### Modern guidance

Reach for `--swc` only after measuring transpile-only and finding the *transpiler* (not the checker) dominant: if full→transpile-only saved seconds, you were checker-bound and SWC buys little; if transpile-only still misses your budget, SWC is the next lever. Cost of the lever: an extra native dependency (`@swc/core` platform binaries), divergence risk on exotic emit (verify output parity on your tree), and one more version to pin.

### Runnable example (good — the full ladder, one tree)

```bash
# same 60-file tree, same machine — the complete ranking, verified:
./node_modules/.bin/ts-node --project big/tsconfig.json ./big/src/main.ts
# real 0m1.247s   (full: checker + TypeScript transpile)

./node_modules/.bin/ts-node --transpile-only --project big/tsconfig.json ./big/src/main.ts
# real 0m0.427s   (TypeScript transpile, no check)

./node_modules/.bin/ts-node --swc --project big/tsconfig.json ./big/src/main.ts
# real 0m0.228s   (SWC transpile, no check)
```

Verified on `@swc/core` latest (4 packages added, native binary included): identical program output all three rungs, monotonic speedup 1.247s → 0.427s → 0.228s. Note the combination that does *not* exist: `--swc` never checks — pairing it with full mode is a contradiction, and ts-node resolves it by transpiling (flags compose mechanically, semantics stay transpile-only).

### Runnable example (bad — SWC before measuring)

```bash
# bad: adopting the native dependency on a 12-file service
npm i -D @swc/core   # platform binaries in the lockfile for a 0.05s win
```

Why it hurts: dependency surface (native binaries per platform, install flakiness on exotic CI images) against unmeasured gain — the 12-file service saves tens of milliseconds it never felt. Fix: adopt on numbers (transpile-only misses budget → try `--swc` → keep iff the delta matters), never on fashion.

### Common confusion

- **"SWC typechecks faster"** — SWC never typechecks (it parses syntax, not types). `--swc` without `tsc --noEmit` in CI is transpile-only with extra steps — same gate requirement, faster strip.
- **"SWC emit always equals tsc emit"** — behaviorally identical for standard syntax at matched `target`, but exotic paths (custom transformers, `const enum` inlining semantics, decorator flavors) can diverge. Parity-check on your tree (`tsc` emit vs `--swc` run, diff the behavior-critical outputs) before standardizing.

### Performance note

SWC's edge is parse-bound throughput (Rust tokenizer, parallelizable) — expect roughly 2× over TypeScript transpile on file count, less on small trees where process spawn dominates (all three rungs converge under ~10 files: measure, watch the floor). The ceiling: native stripping (delete-only, no parse-transform at all) beats every transpiler on erasable-only sources — the leaderboard from [1.1](<../1. Execution identity and setup/1.1. What ts-node is and is not.md>) still applies.

### Mentor note

Teach the ladder, not the tool: full → transpile-only → SWC is a *measurement sequence* (remove the checker, then accelerate the strip), each rung justified by the previous rung's profile. Mentees who jump to SWC first optimize a cost they never located; make them produce all three timings for their repo before approving the dependency.
