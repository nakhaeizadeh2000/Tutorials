# 2.2. The tsconfig that executes

How ts-node reads `tsconfig.json`, which `module`/`target` pairs actually run, and which strictness flags keep one source tree acceptable to every runner. Junior read: three fields, one file, no more `TS5109`. Expert read: what the defaults do when the file is missing, and why `erasableSyntaxOnly` gates the checker but never the runner.

## 1) ts-node reads your tsconfig

### 1) **Definition** (automatic parsing with Node-aware defaults)

ts-node locates `tsconfig.json` upward from the entry file (or `--project` / `TS_NODE_PROJECT` override it), parses `compilerOptions`, and fills unset fields with defaults matched to your Node version. Flags live in one file — the CLI stays bare, the shebang stays portable, and every door from [1.2. Installing and running](<../1. Execution identity and setup/1.2. Installing and running your first TypeScript file.md>) shares one configuration.

### What problem it solves (history)

Pre-config runners took behavior from flags, env vars, and tribal knowledge simultaneously — the same file compiled differently per invocation, and "works via CLI, breaks via `-r`" was a weekly occurrence. Automatic config parsing made the file the single source of truth: change the compiler behavior once, every door follows.

### Modern guidance

Keep exactly one execution tsconfig per runtime context (app, tests, scripts each extend a shared base — never copy flags), pass `--project` only where the entry file's upward search lands wrong (monorepo packages, out-of-tree scripts), and inspect the effective result with `tsc --showConfig` whenever behavior surprises you. This session's probe tsconfig is the minimal honest shape:

```jsonc
{
  "compilerOptions": { "target": "es2022", "module": "commonjs", "strict": true }
}
```

Effective expansion verified via `tsc --showConfig` (`strict` blooms into `noImplicitAny`, `strictNullChecks`, `strictPropertyInitialization`, … — the flags you set versus the flags that run are different lists; `--showConfig` shows the second).

### Runnable example (good — the file present, everything works)

```bash
./node_modules/.bin/ts-node ./hello.ts
# hello from ts
```

### Runnable example (bad — the file missing, two different deaths)

```bash
mv tsconfig.json tsconfig.hidden

./node_modules/.bin/ts-node ./hello.ts
# TypeError: Unknown file extension ".ts" for /tmp/tsprobe/hello.ts

./node_modules/.bin/ts-node --transpile-only ./hello.ts
# TSError: ⨯ Unable to compile TypeScript:
# error TS5109: Option 'moduleResolution' must be set to 'NodeNext'
# (or left unspecified) when option 'module' is set to 'NodeNext'.
```

Both verified live (ts-node v10.9.2, no tsconfig on disk): full mode cannot even determine the module format without config guidance, and transpile-only dies on the defaulted `module: NodeNext` pairing. Restore the file — both commands print. The lesson: "no tsconfig" never means "safe defaults"; it means *ts-node's* defaults, which encode a NodeNext bet your tree may not take.

Why it hurts: the failures blame the *code* (extension errors, option errors) while the cause is a *missing file* — and the file goes missing exactly during refactors (moved entry points, new packages, Docker contexts that copy `src/` without the config). Fix: the handshake from [1.2](<../1. Execution identity and setup/1.2. Installing and running your first TypeScript file.md>) after every move, and `--project` pinned in scripts whose entry lives outside the config's subtree.

### Common confusion

- **"`ts-node` ignores tsconfig in transpile-only"** — false: the `TS5109` above fired *in transpile-only*. Mode drops the check pass, never the config parse. Options still decide module format, target downleveling, and transformer wiring in every mode.
- **"one tsconfig serves editor, runner, and build"** — one *base* serves all three; each consumer extends with deltas (editor: `noEmit` + watch; runner: execution module pair; build: `outDir` + declarations). Single file for everything forces someone's context to lie — usually the runner's.

### Performance note

Config *size* costs nothing at run time (parsed once per process); config *wrongness* costs everything (full re-diagnosis per boot failure, multiplied by developers). The measurable investment is one `tsc --showConfig` review per quarter — minutes against the hours a drifted `module`/`target` pair burns.

### Mentor note

When a mentee's ts-node failure mentions extensions, options, or formats, forbid touching source until `tsc --showConfig -p` output is on screen. Nine of ten such failures evaporate at the sight of the effective config — teach the reflex, not the individual error codes.

## 2) Module and target pairs that run

### 2) **Definition** (the pairing contract)

`module` decides what the compiled output *is* (CommonJS `require`/`exports` vs ESM `import`/`export`); `target` decides how *modern* it may stay (which syntax survives vs downlevels). ts-node additionally needs the pair to match the *loader door*: CJS output through the require hook, ESM output through the loader hook. Three slots — output shape, language level, entry door — must agree.

### What problem it solves

Mismatched triples produce the genre's most confusing errors: ESM output fed to `require()` (`Must use import`), CJS output under `--loader ts-node/esm` (format complaints), downleveled output hiding runtime behavior the source promised. The pairing contract turns "which flags?" into a lookup: name the door, the pair follows.

### Modern guidance

As of September 2026, two sanctioned pairs cover nearly everything: CJS services — `"module": "commonjs", "target": "es2022"` through the require hook (this session's verified probe shape); ESM services — `"module": "NodeNext", "moduleResolution": "NodeNext"` with matching `package.json` `type` through the loader hook (owned in full by [3.1. Loading TypeScript under CJS and ESM](<../3. Loading model/3.1. Loading TypeScript under CJS and ESM.md>)). Set both fields explicitly — the `TS5109` above is what "half a pair" compiles to. `target` below `es2020` on a modern Node buys nothing (Node runs the modern syntax natively) while obscuring stack traces and sourcemaps.

### Runnable example (good — the CJS pair, verified end to end)

```jsonc
// tsconfig.json — CJS service pair
{ "compilerOptions": { "target": "es2022", "module": "commonjs", "strict": true } }
```

```bash
./node_modules/.bin/ts-node ./hello.ts          # hello from ts
node -r ts-node/register ./hello.ts             # hello from ts — same pair, hook door
./node_modules/.bin/tsc --noEmit -p tsconfig.json  # silent — checker agrees
```

### Runnable example (bad — half a pair)

```jsonc
// bad: module named, resolution betrayed (or absent entirely)
{ "compilerOptions": { "module": "NodeNext" } }
```

```bash
./node_modules/.bin/ts-node --transpile-only ./hello.ts
# error TS5109: Option 'moduleResolution' must be set to 'NodeNext' ...
```

Why it hurts: the error reads as compiler pedantry but means "you named the output shape without naming how imports resolve" — and under full mode the same half-pair can *run the wrong files* (resolution falling back where you cannot see it) instead of failing loudly. Fix: always set the pair together; copy neither field alone between projects.

### Common confusion

- **"`target` should match the oldest supported Node"** — `target` should match the oldest Node you *execute on*, and ts-node executes on *your* Node. Downleveling for a Node 16 that never runs this code pays transform cost and readability for zero compatibility. The floor is the runtime in the Dockerfile, not the README badge.
- **"ESM is just `module: NodeNext`"** — the flag is one third of ESM (file extensions, `package.json` `type`, specifier discipline complete it). The remaining two thirds live in [3.1](<../3. Loading model/3.1. Loading TypeScript under CJS and ESM.md>) — this leaf refuses to half-teach them.

### Performance note

`target` too low costs real startup: downleveled helpers (`__awaiter`, `__spreadArray`) allocate and wrap where native syntax would not, on every import, every boot. On the 60-file probe tree from [2.1](<./2.1. Transpile-only versus full typechecking.md>), raising `target` to the runtime's level is free performance — no code change, less emit. Measure `time` before and after a target bump; keep the faster printout in the commit message.

### Mentor note

Make pair selection a two-question drill: "which door loads the entry?" (require → commonjs; loader → NodeNext) and "which Node runs it?" (target answers). Mentees who recite flags without naming the door will produce half-pairs forever; the drill fixes the ordering.

## 3) Strictness that survives execution

### 3) **Definition** (flags every runner accepts)

`strict: true` (and its bloom: `noImplicitAny`, `strictNullChecks`, …) constrains *checking*, never *execution* — strict code runs under every runner unchanged. `erasableSyntaxOnly` (TypeScript 5.8+) goes further: it *rejects non-erasable syntax at check time* (`enum`, parameter properties, runtime namespaces), guaranteeing the same sources also survive native stripping. Strictness is a promise about sources; erasability is a promise about runners.

### What problem it solves

Teams standardizing on fast runners (stripping, `tsx`) discovered sources that only the full compiler accepted — an `enum` committed casually, a parameter property in a constructor — and each one detonated on the runners that cannot generate code. `erasableSyntaxOnly` fails those files at `tsc` time, where the author sits, instead of at stripping time, where the on-call engineer sits.

### Modern guidance

New services: `"strict": true` plus `"erasableSyntaxOnly": true`, so one tree runs under ts-node (both modes), `tsx`, and flagless stripping on Node v22.18.0+. Legacy trees: enable the flag, fix the flagged sites (the compiler lists every one — migration, not archaeology), and only then advertise runner freedom. The erasable inventory itself — *which* constructs erase — is owned by [TypeScript 01/3.3](<../../../../TypeScript/01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>) and is not restated here.

### Runnable example (good — the flag gates the checker)

```bash
# erase/legacy.ts: enum Status { Pending, Done }
./node_modules/.bin/tsc --noEmit --project erase/tsconfig.json
# erase/legacy.ts(1,6): error TS1294: This syntax is not allowed
# when 'erasableSyntaxOnly' is enabled.
```

Verified on TypeScript 5.9.3: the checker names the file, line, and rule. Fix the source (union type over the enum), the error evaporates, and the file runs under *every* runner — that universality is the flag's entire payoff.

### Runnable example (bad — assuming the flag gates the runner)

```bash
# bad: believing erasableSyntaxOnly protects execution
./node_modules/.bin/ts-node --transpile-only --project erase/tsconfig.json ./erase/legacy.ts
# 0   (runs! the enum transpiles — the flag never fired)
```

Verified live — and this is the expert-grade nuance: `erasableSyntaxOnly` is a *check-time* rejection. Transpile-only ts-node transpiles the `enum` happily (it is still the TypeScript compiler, generating code as always) and prints `0`. The flag protects stripping-era Node from ever *receiving* such files — via CI failing the author — not by teaching runners to refuse them. Teams that enable the flag but never run the checker gain nothing: the guard without the gate is decoration.

Why it hurts: false confidence ("we enabled the flag, so stripping is safe") followed by a stripping `SyntaxError` in production from a file the checker never saw. Fix: flag plus `tsc --noEmit` gate in CI — the pair from [2.1](<./2.1. Transpile-only versus full typechecking.md>), applied to erasability.

### Common confusion

- **"`strict` slows execution"** — strictness evaporates with the types (zero emit difference for the annotations it constrains). Strict code can even run *faster* under stripping: fewer exotic constructs survive review, so fewer files need transform paths.
- **"erasable-only sources lose expressiveness"** — the banned list is small (`enum`, parameter properties, runtime namespaces, a few aliases) and each has an erasable idiom (unions, explicit assignments, `import type`). The inventory with migrations lives in TypeScript 01/3.3 — linked, not repeated.

### Performance note

Erasable-only trees unlock the fastest execution rung (native stripping: delete-only, no transform — see the leaderboard in [1.1](<../1. Execution identity and setup/1.1. What ts-node is and is not.md>)). The flag's performance value is therefore *optional speed*: pay nothing today (ts-node runs the same sources identically), keep the fastest runner available tomorrow. One boolean, one future option.

### Mentor note

Demo the bad example live: enable the flag, run transpile-only, watch the `enum` execute — then ask "so what did the flag do?" The silence that follows is the lesson: flags constrain *checkers*, runners *transpile*. Mentees who internalize that sentence stop expecting config to do execution's job.
