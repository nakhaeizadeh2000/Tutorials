# 1.2. Installing and running your first TypeScript file

Installing ts-node as a pinned project dependency and running a first `.ts` file three ways — CLI, require hook, and programmatic registration. Junior read: copy these four commands and TypeScript runs. Expert read: *which* invocation owns each use case, and why the global-install shortcut corrupts every one of them.

## 1) Install once, pin with the project

### 1) **Definition** (the dev-dependency contract)

ts-node and `typescript` ship as `devDependencies`, versions locked by the lockfile. The runner is project infrastructure, like the test framework — same version on every machine, invisible to production installs (`npm ci --omit=dev` drops it from the artifact).

### What problem it solves (history)

Global installs (`npm i -g ts-node`) were the early norm, and they produced the classic drift: laptop A ran ts-node 8 with TS 3.x, CI ran 9 with 4.x, and identical sources compiled differently. Failures ("works locally, red in CI") traced to invisible version gaps, not code. Pinning moved the runner into the repo, where the lockfile governs it.

### Modern guidance

As of September 2026 (ts-node 10.9.x, TypeScript 5.9 era): `npm i -D typescript ts-node`, commit the lockfile, never install globally. This session's own probe caught the current edge of the same lesson — ts-node 10.9.2 crashes at boot under TypeScript 7.0.2 (`TypeError` reading `fileExists` in `configuration.js`) and works pinned to 5.9.3. Unpinned runners break silently across majors; pinned runners break loudly at install time, where fixes are cheap.

### Runnable example (good — pinned install with proof)

```bash
npm i -D typescript ts-node
npm ls ts-node typescript
# tsprobe@1.0.0 /tmp/tsprobe
# ├─┬ ts-node@10.9.2
# │ └── typescript@5.9.3 deduped
# └── typescript@5.9.3
```

Verified install: 21 packages, one tree, `ts-node --version` → `v10.9.2`, `tsc --version` → `Version 5.9.3`. `npm ls` is the handshake — it proves the runner and the compiler resolve to one copy each (a duplicated `typescript` nested under ts-node is the smell that precedes phantom type errors).

### Runnable example (bad — the global shortcut)

```bash
# bad: no repo record, no lockfile entry, version = whatever the laptop has
npm i -g ts-node
ts-node ./hello.ts   # runs today, someone else's 8.x/7.x combo tomorrow
```

Why it hurts: correctness (compiler version decides which syntax compiles), reproducibility (CI cannot `npm ci` what `package.json` never names), and debuggability (first question on any failure — "which ts-node?" — has no answer). Globals are for editors, never for runners.

### Common confusion

- **"ts-node bundles TypeScript"** — it depends on it as a peer: `npm ls` above shows `typescript@5.9.3 deduped` *under* ts-node. Installing ts-node without `typescript` in the tree compiles nothing. Always install both names.
- **"latest of both is safest"** — latest-unpinned is how this session found the 7.0.2 boot crash. Pin first, upgrade deliberately (`npm outdated` → bump → full test + `tsc --noEmit`), never by accident.

### Performance note

Install size is trivial (tens of packages) against the alternative cost: one unpinned-runner incident burns more engineer-hours than a decade of lockfile updates. The measurable number is install reproducibility — `rm -rf node_modules && npm ci && ts-node --version` must print the same version on every machine, every time.

### Mentor note

Make pinning a merge gate, not advice: CI runs `npm ci` (lockfile-strict) so an unpinned runner fails at install, not at 2 a.m. Teach mentees to read `npm ls` output the way they read test results — duplicated compilers and missing peers are findings, not trivia.

## 2) Run three ways, know which you used

### 2) **Definition** (the three invocations)

ts-node's own docs name three doors into the same hook: the **CLI** (`ts-node script.ts` — owns terminals and npm scripts), the **require hook** (`node -r ts-node/register script.ts` — owns tools that launch Node themselves: test runners, debuggers, `NODE_OPTIONS` injection), and **programmatic registration** (`require('ts-node').register({...})` then `require()` — owns libraries and harnesses that must compile TS from inside JS).

### What problem it solves

Each door exists because the caller differs: a human types the CLI; a test runner spawns `node` and only accepts flags; a build harness is already JS and needs one `require()` to unlock TS imports. One door cannot serve all three — the register flag exists precisely for processes you do not start.

### Modern guidance

Scripts and `package.json` entries use the CLI; editor debuggers, `NODE_OPTIONS`, and child processes use `-r ts-node/register`; in-process harnesses use programmatic `register()`. ESM entry points use the loader door instead (`--loader ts-node/esm`) — owned by [3.1. Loading TypeScript under CJS and ESM](<../3. Loading model/3.1. Loading TypeScript under CJS and ESM.md>), not this leaf.

### Runnable example (good — all three doors, same output)

```typescript
// hello.ts (same file as 1.1)
const label: string = "ts";
console.log("hello from", label);
```

```bash
# door 1 — CLI: owns terminals and npm scripts
./node_modules/.bin/ts-node ./hello.ts
# hello from ts

# door 2 — require hook: owns tools that launch node themselves
node -r ts-node/register ./hello.ts
# hello from ts
```

```javascript
// door 3 — programmatic: owns in-process harnesses (plain .js entry)
require('ts-node').register({ transpileOnly: true });
require('./hello.ts');
// hello from ts
```

All three verified on ts-node v10.9.2 + TypeScript 5.9.3 with an explicit `tsconfig.json` (`module: commonjs`, `target: es2022`, `strict: true`) — without it, this session's probe failed with `TS5109`, the lesson [2.2](<../2. Modes and configuration/2.2. The tsconfig that executes.md>) exists to teach. One-liners for probes: `ts-node -e 'const n: number = 41; console.log(n + 1)'` prints `42`; `ts-node -p -e '"hook:" + (40 + 2)'` prints `hook:42` — note `-p` rides with `-e`, never alone (bare `-p` is parsed as a script path and dies in module resolution — caught live in this session's probe).

### Common confusion

- **"`-r ts-node/register` and the CLI are the same"** — same hook, different owner: the CLI parses ts-node flags (`--transpile-only`, `--esm`); the `-r` form accepts only Node flags plus `NODE_OPTIONS`, with ts-node options coming from `tsconfig.json` or `TS_NODE_*` env vars. Flags after `node -r ...` belong to Node, not ts-node.
- **"shebang scripts need CLI flags inline"** — portable shebangs (`#!/usr/bin/env ts-node`) read options from `tsconfig.json`; inline flags need `env -S` and break across platforms. Config over command line — always.

### Performance note

Door choice has no runtime cost difference (identical hook, identical compile) — the cost axis is *startup attribution*: the CLI adds one process spawn you can `time` directly; `-r` hides inside the host tool's spawn (profile the host, not ts-node). Measure the door you ship, not the door you type.

### Mentor note

Drill door selection as a one-question quiz: "who starts the Node process — you, a tool, or running JS?" (you → CLI; a tool → `-r`/loader; running JS → programmatic). Mentees who answer in one breath stop cargo-culting flags into the wrong door.

## 3) Verify the run teaches the hook

### 3) **Definition** (the handshake habit)

Every new checkout proves its runner before any real work: pinned versions print, a probe file runs through the hook, and the failure mode without the hook is demonstrated once — so the team shares one mental model of what executes their TypeScript.

### What problem it solves

Runner assumptions rot: a lockfile bump, a Node major, a deleted tsconfig silently change what `ts-node` does (or whether it boots at all — this session collected three such failures in one probe). A 30-second handshake after setup changes turns "it broke mysteriously" into "the handshake names the breakage."

### Modern guidance

Keep a `hello.ts`-class probe (erasable-only, two lines, prints) plus a three-command handshake in the contributing guide: `ts-node --version` (pin), `ts-node ./probe.ts` (hook), `node ./probe.ts` (fails without the hook — proves the model). Re-run after every runner/compiler/Node bump. The failure catalog this handshake detects — peer-incompat crashes, missing-tsconfig `TS5109`, ESM/CJS mismatches — is rehearsed with fixes in [4.1. Execution checklist](<../4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>).

### Runnable example (good — the 30-second handshake)

```bash
./node_modules/.bin/ts-node --version   # v10.9.2 — the pin speaks
./node_modules/.bin/ts-node ./hello.ts  # hello from ts — the hook works
node ./hello.ts 2>&1 | head -2
# const label: string = "ts";
#       ^^^^^
# (fails without the hook — the model holds)
```

### Runnable example (bad — assuming the green terminal)

```bash
# bad: first run is the real server, first failure is a production-shaped mystery
./node_modules/.bin/ts-node ./src/server.ts
# TSError / TS5109 / MODULE_NOT_FOUND — now debug the runner AND the app at once
```

Why it hurts: runner failures and application failures present identically (a stack trace at boot) but fix differently (config vs code). The handshake separates the variables before they can combine.

### Common confusion

- **"CI passing means the runner is fine"** — CI usually runs the *artifact* (`tsc` + `node dist/`), never the hook. The handshake belongs where the hook runs: laptops, script jobs, and any environment executing `.ts` directly.
- **"one handshake per repo lifetime"** — the handshake expires on every runner/compiler/Node version change. Re-run on bump; automate the version-print half in CI (`ts-node --version` asserts the pin even where the hook never runs).

### Performance note

Thirty seconds of handshake versus hours of hook-vs-app ambiguity per incident — the highest-ROI commands in this domain. Cost is linear in discipline (run on bump), payoff is step-function (each caught drift saves a debugging session).

### Mentor note

Onboard every mentee with the handshake live: watch them run all three commands and narrate what each proves. Anyone who can explain why the third command *must* fail understands the hook model; anyone who cannot will misdiagnose the next boot failure.
