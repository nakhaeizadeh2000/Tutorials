# 1.1. What ts-node is and is not

ts-node is a TypeScript execution engine for Node.js: it hooks Node's module loading so `.ts` files compile at import time and run without a separate build step. Junior read: `ts-node hello.ts` runs TypeScript the way `node hello.js` runs JavaScript. Expert read: the hook, the compiler instance behind it, and the mode flags decide your startup latency, your error timing, and whether production should ever see this tool.

## 1) A hook, not a runtime

### 1) **Definition** (the hook model)

ts-node does not replace Node.js — it *registers* on Node's loader (`require` hook for CJS, ESM loader for ESM) and compiles each `.ts` file to JavaScript at the moment it is imported. V8 still executes plain JavaScript; the TypeScript never reaches the engine. Mental model: `node` + a just-in-time `tsc` attached to `require`.

### What problem it solves (history)

Before load-time hooks, every TypeScript run needed two steps: `tsc` emit, then `node dist/`. Scripts, CLIs, and test bootstraps paid a full build for a one-off run, and repos accumulated `prepublish`-style glue to keep `dist/` fresh. ts-node collapsed the two steps into one command — at the price of paying compilation on every import, on every run.

### Modern guidance

Reach for ts-node when the *developer loop* is the bottleneck (scripts, CLIs, test setup, local servers) — as of September 2026 (ts-node 10.9.x, TypeScript 5.9 stable) that is still its home ground. Do not treat it as a production server runtime by default: an artifact built once (`tsc` emit, then `node dist/`) starts faster and fails identically on every machine. The production decision is priced in [2.1. Transpile-only versus full typechecking](<../2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>) and [6.1. Boundaries](<../6. Overlaps to avoid/6.1. Boundaries what is covered elsewhere.md>).

### Runnable example (good — the hook fires on import)

```typescript
// hello.ts — erasable-only source: annotations delete cleanly
const label: string = "ts";
console.log("hello from", label);
```

```bash
./node_modules/.bin/ts-node ./hello.ts
# hello from ts
```

Verified on ts-node v10.9.2 + TypeScript 5.9.3: annotation stripped at import, program prints. The same file under bare Node (v20.20.2, no stripping support) fails — proving the hook, not the runtime, did the work:

```bash
node ./hello.ts
# /tmp/tsprobe/hello.ts:1
# const label: string = "ts";
#       ^^^^^
# (SyntaxError — Node parses the annotation as code)
```

### Runnable example (bad — assuming the runtime understands TypeScript)

```bash
# bad: committing a `node server.ts` start script and discovering
# in staging that only ts-node was ever in the loop
node ./server.ts   # SyntaxError on the first annotation, deploy red
```

Why it hurts: the failure appears only where the hook is absent (CI, Docker, a colleague's laptop) — green-here-red-there, the most expensive failure class. Fix: every `node *.ts` invocation must resolve to a hook (`ts-node`), a prebuilt artifact (`node dist/`), or a stripping-capable Node (v22.18.0+, erasable-only sources) — decided explicitly, never by accident.

### Common confusion

- **"ts-node runs TypeScript"** — precisely, it *compiles* TypeScript to JavaScript at import time and Node runs the result. The distinction matters the moment a stack trace, a sourcemap, or a startup profile disagrees with your source (sourcemap mechanics → [Domain 05](<../../../05 Debugging Sourcemaps and Profiling TypeScript/README.md>)).
- **"no tsconfig needed"** — ts-node parses `tsconfig.json` automatically and defaults the rest to your Node version. Missing config does not mean default-safe: this session's own probe failed with `TS5109` (module/NodeNext mismatch) until an explicit `module: commonjs` landed — config is load-bearing, full story in [2.2. The tsconfig that executes](<../2. Modes and configuration/2.2. The tsconfig that executes.md>).

### Performance note

Hook cost is per-import compilation: cold start grows with file count, warm runs pay nothing extra (CJS cache holds compiled output). Measure, don't guess: `time ts-node src/app.ts` versus `time ts-node --transpile-only src/app.ts` on your repo — the gap is the typechecker's share of startup, and it decides whether [2.1](<../2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>) matters to you.

### Mentor note

Teach the hook model with the two-command demo above (`ts-node` prints, `node` throws) before any flag talk. Review checklist item: every repo running `.ts` directly must name its hook in `package.json` scripts — `ts-node`, `tsx`, or a Node version floor for stripping. "It works on my machine" is a hook-presence claim; make it explicit.

## 2) Transpile on import, optionally check

### 2) **Definition** (the two modes)

Every import through ts-node takes one of two paths: *full mode* typechecks the file and refuses to run on type errors; *transpile-only* (`--transpile-only`, `ts-node-transpile-only`) strips types without checking and runs whatever remains. Same hook, different gate.

### What problem it solves

Full checking on every import made large servers slow to start and double-reported errors CI already caught (`tsc --noEmit` failing, then ts-node failing again on boot). Transpile-only splits the concerns: the runner optimizes for feedback speed, the checker runs where failures gate merges.

### Modern guidance

Default to transpile-only for execution plus `tsc --noEmit` in CI — as of the TypeScript 5.9 era this is the standard split (execution never waits on the checker; errors still block merges). Keep full mode for small scripts where one command should do both jobs. Mode mechanics, SWC escalation, and the CI pairing are owned by [2.1. Transpile-only versus full typechecking](<../2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>).

### Runnable example (good — the gate behaves as advertised)

```typescript
// loose.ts — a type error that erases cleanly
const x: number = "not a number";
console.log("runs:", x);
```

```bash
./node_modules/.bin/ts-node ./loose.ts
# TSError: ⨯ Unable to compile TypeScript:
# loose.ts(1,7): error TS2322: Type 'string' is not assignable to type 'number'.

./node_modules/.bin/ts-node --transpile-only ./loose.ts
# runs: not a number
```

Verified on ts-node v10.9.2 + TypeScript 5.9.3: full mode gates on `TS2322`; transpile-only erases the annotation and runs. Neither mode invents runtime safety — the string flows through in both worlds; only the *timing* of the complaint differs.

### Common confusion

- **"transpile-only is unsafe"** — it is *unchecked at run time*, not unchecked: `tsc --noEmit` in CI sees the same errors. Unsafe is running transpile-only with no checker anywhere in the pipeline.
- **"full mode replaces `tsc`"** — full mode checks only files pulled through the hook (no cross-file program guarantees like `noEmit` over the whole project). The checker that gates merges is `tsc`, never the runner.

### Performance note

Typechecking dominates cold start on annotation-heavy trees: expect transpile-only to start a mid-size server a multiple faster (measure yours — one `time` each, same machine, same tree). The gap widens with `strict` on and decorator-heavy files; it narrows to noise on ten-file scripts, where full mode's simplicity wins.

### Mentor note

Make the split tangible: run both commands above in front of the mentee and point at where each error surfaces (terminal now vs CI later). Review rule: any `ts-node` (non-transpile-only) in `package.json` scripts of a 50+-file service is a startup-latency finding until measured.

## 3) One runner among several

### 3) **Definition** (the honest leaderboard)

Four ways run `.ts` on Node, different trade-offs: `tsc` emit + `node dist/` (faithful, slowest loop), ts-node (checks-or-strips via the real compiler, slowest start of the JITs), `tsx` (esbuild transpile, fast start, no checking), native stripping (Node v22.18.0+ runs erasable-only sources flagless, zero transform). ts-node's niche: compiler-faithful execution with optional checking and deep tsconfig integration.

### What problem it solves (why several runners exist)

No single runner dominates all axes: checking fidelity (ts-node full, `tsc`), startup speed (stripping, `tsx`), transform power for non-erasable syntax (ts-node, `tsx`, `tsc` — stripping refuses `enum`/parameter-properties outright). The leaderboard exists so each environment picks its axis: dev loop, CI gate, or production artifact.

### Modern guidance

As of September 2026: new services default to erasable-only sources (`erasableSyntaxOnly`) so *every* runner accepts them, develop via a fast JIT (`tsx` or ts-node transpile-only — measure both), gate with `tsc --noEmit`, ship compiled artifacts. Keep ts-node full mode where its compiler hooks earn their keep (custom transformers, API integration, REPL) — that is what the alternatives cannot do. The full comparison with numbers lives where it belongs — [3.2. Executing TypeScript](<../../../../TypeScript/01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>) — and is not re-argued here.

### Runnable example (good — choosing by constraint, not habit)

```bash
# local script, one file, want checking inline: ts-node full mode
./node_modules/.bin/ts-node ./hello.ts
# hello from ts

# dev server, 300 files, checker already in CI: transpile-only
./node_modules/.bin/ts-node --transpile-only ./server.ts

# production: never the hook — build once, run the artifact
./node_modules/.bin/tsc -p tsconfig.build.json && node ./dist/server.js
```

### Runnable example (bad — one runner for every job)

```bash
# bad: ts-node full mode as the production start command
"scripts": { "start": "ts-node ./src/server.ts" }
```

Why it hurts: every deploy pays full typecheck at boot (slowest start), a cold container can time out its healthcheck before serving, and a type error becomes a *runtime* outage instead of a *build* rejection. Production runs artifacts; runners develop them.

### Common confusion

- **"`tsx` and ts-node are interchangeable"** — `tsx` (esbuild) transpiles non-erasable `enum`/`namespace` that stripping rejects and starts faster; ts-node (real compiler) typechecks optionally and honors transformer plugins. Same command shape, different engines — pick by constraint.
- **"native stripping replaces ts-node"** — only for erasable-only sources on Node v22.18.0+ (local v20.20.2 in this session has no stripping at all — version-gated, check `node --version` before assuming). Non-erasable syntax, custom transformers, and REPL-driven flows keep ts-node relevant.

### Performance note

Order-of-magnitude startup ranking on a real tree (measure yours; direction is stable): stripping ≈ fastest (delete-only), `tsx` next (esbuild, cached), ts-node transpile-only next (TypeScript transpiler, no check), ts-node full slowest (full checker per import). The ranking flips for *correctness feedback*: only full mode and `tsc` tell you about type errors at all.

### Mentor note

Teach runner choice as a constraint table (rows: runners; columns: checks? / non-erasable? / startup / needs install?) and make the mentee fill it for their service. Interviewers probe exactly this judgment — the canonical answer is rehearsed in [5.1. Common interview QA](<../5. Interview questions and answers/5.1. Common interview QA execution foundations.md>).
