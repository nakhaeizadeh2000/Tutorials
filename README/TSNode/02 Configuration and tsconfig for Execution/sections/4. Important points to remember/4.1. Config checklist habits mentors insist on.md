# 4.1. Config checklist (habits mentors insist on)

The three habits that keep multi-file, multi-package configuration boring: evidence before theory, proven scope per entry, and complete pairs with bridged paths. Junior read: extend the gate script with three config stages. Expert read: which incident each stage names, and why config checks belong in CI rather than memory.

## 1) Show the config before theorizing

### 1) **Definition** (the evidence-first reflex)

No config dispute proceeds past `--showConfig`: the effective merged configuration (winner file, extends merge, `ts-node` object, injected defaults) printed before any source is read, any flag debated, or any runner blamed. [1.1](<../1. Config architecture/1.1. Base and delta tsconfigs.md>) established the command; this habit makes it reflex.

### What problem it solves (history)

Config debugging without evidence runs on merge-simulation: engineers reasoning about `extends` precedence, `types` replacement, and override layers in their heads — wrong often enough that this track's own probes surprised their author three times (injected `sourceMap`/`outDir`, resolved `project` path, NodeNext-by-default). Evidence replaces simulation; simulation was never good at it.

### Modern guidance

Every ts-node failure gets `--showConfig --project <it>` as step zero (after the pin check from [01/4.1](<../../../01 Execution Foundations and Mental Model/sections/4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>), before everything else). Bug template fields: command + `--showConfig` + `ts-node -vv` — no evidence, no triage. CI emits `--showConfig` as an artifact on config-touching diffs so green-here-red-there divergences arrive pre-diagnosed.

### Runnable example (good — the config stage in the gate)

```bash
#!/bin/bash
# config gate: winner receipt + pair completeness + alias execution
PROJ="${1:-tsconfig.json}"
./node_modules/.bin/ts-node --showConfig --project "$PROJ" 2>/dev/null | grep -q '"project"' || exit 20
./node_modules/.bin/tsc --noEmit --project "$PROJ" || exit 21
./node_modules/.bin/ts-node --transpile-only -r tsconfig-paths/register --project pw/tsconfig.json ./pw/src/main.ts | grep -q "pw: paths" || exit 22
echo CONFIG-GREEN
```

```bash
./gate2.sh pw/tsconfig.json; echo "exit=$?"
# CONFIG-GREEN
# exit=0

./gate2.sh mono/pkg-a/run.ts >/dev/null 2>&1; echo "bad-project exit=$?"
# bad-project exit=20
```

Verified: green on a real project (exit 0), stage-20 refusal when handed an entry path instead of a config (the `--project`-takes-config rule from [1.2](<../1. Config architecture/1.2. Monorepo configs and project scoping.md>), enforced mechanically). Exit codes narrate the failure: 20 no-winner, 21 checker, 22 alias-execution.

### Common confusion

- **"showConfig output is stable"** — it expires on every config edit, move, upgrade, and environment change (yesterday's receipt describes yesterday's tree). Re-run per incident; the gate re-runs per execution. Cached evidence is another word for assumption.
- **"grep -q hides the evidence"** — the gate asserts; humans inspect. When a stage fails, re-run its command *without* the grep and read the output — the gate routes attention, then gets out of the way.

### Performance note

One sub-second boot per gate run (no user code compiled) — the cheapest stage in either gate script. Run it unconditionally (not only on failure): unconditional evidence is what makes the *next* failure debuggable in minutes instead of hours.

### Mentor note

Pair this habit with the pin check from [01/4.1](<../../../01 Execution Foundations and Mental Model/sections/4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>) into a single pre-flight: versions, winner, checker, aliases. Four stages, four exit codes, one script — onboarding becomes "run the gate, read the exit code," and config fluency follows from repetition, not lectures.

## 2) Scope proven per entry

### 2) **Definition** (inheritance assumed guilty)

Every executable entry proves its governing config: the walk's winner is *shown* (`--showConfig` receipt), not assumed from directory layout. New entries, moved entries, and monorepo-boundary entries get explicit pins (`--project`/`TS_NODE_PROJECT`) unless the receipt demonstrates the walk already terminates correctly. Trust, but verify — per entry, per move.

### What problem it solves (history)

Location-dependent behavior is the monorepo tax: entries work until reorganization changes what the walk finds, then fail in the previous package's voice weeks later. Proven scope converts the tax into a receipt — moves that change the winner break the gate (missing pin, changed receipt) instead of silently recompiling under new rules.

### Modern guidance

CI asserts scope for every entry point: a job (or gate loop) running `--showConfig --project` per package entry and comparing the winner path against a checked-in expectation. New packages copy the pin pattern from siblings (delta config + scoped script), never the hope that the walk "probably finds the right one." Reorganization diffs include receipt updates — scope changes reviewable like code changes.

### Runnable example (good — receipts per entry, scripted)

```bash
# every entry names its governor; the gate loops them
for entry in ./cfg/app/run.ts ./cjs/main.ts ./pw/src/main.ts; do
  ./node_modules/.bin/ts-node --showConfig --project "$(dirname "$entry")/tsconfig.json" 2>/dev/null \
    | grep -q '"project"' && echo "SCOPED: $entry" || echo "UNSCOPED: $entry"
done
```

Entries with sibling configs scope cleanly; entries without (like `mono/pkg-a/run.ts`, inheriting root) print their inherited winner — also fine, *once recorded*. The point is never "local config everywhere" but "known winner everywhere": inheritance is legitimate when receipted, dangerous when assumed.

### Runnable example (bad — scope by convention)

```bash
# bad: "all entries sit beside their configs" (undocumented, unenforced)
# — the next contributor nests a script one level deeper for tidiness,
# the walk terminates one level higher, the pair changes, nothing announces it
```

Why it hurts: conventions without checks decay (every repo's directory tidiness evolves), and scope decay is silent until boot. Fix: receipt the convention (gate loop above) so decay fails loudly at the commit that causes it, attributed correctly.

### Common confusion

- **"one receipt per repo suffices"** — the walk is per-entry (starts at the entrypoint, per official docs). One receipt proves one entry; N entries need N receipts. The loop above costs one boot per entry — linear, cheap, complete.
- **"pinned entries don't need receipts"** — pins rot too (renamed configs, moved projects — the pin points at air, the walk resumes silently underneath). Receipt the *winner*, not the pin: `--showConfig` shows what governed, regardless of how it was chosen.

### Performance note

N boots for N entries (sub-second each, no user compilation) — run per CI invocation on config-touching diffs, nightly otherwise. Human cost of unscoped entries (cross-package misconfiguration incidents) exceeds the machine cost by orders of magnitude at any team size above one.

### Mentor note

Assign new monorepo contributors the "scope safari": receipt every entry in the repo, record winners, flag surprises. The exercise teaches the walk, the pins, and the repo layout simultaneously — and every surprise found is a latent incident converted to a ticket before it pages.

## 3) Pairs complete, paths bridged

### 3) **Definition** (the merge-time config contract)

No merge lands with a half-pair (`module` without `moduleResolution`, accept without rewrite) or an unbridged alias (`paths` without a runtime half): the gate's stages 21 (checker over the program) and 22 (aliased entry *executed*, not merely checked) enforce both. Config review checks the deltas; the gate checks the consequences.

### What problem it solves (history)

Reviewers read configs; configs lie by omission (a missing half is invisible in a diff that only shows what's present). The gate reads consequences: checker output (catches type errors *and* unknown options like `TS5023`), executed aliases (catches the checker/runtime gap), exit codes (name the stage). Diffs declare intent; gates verify reality — both halves required.

### Modern guidance

Required CI jobs for hook-executed repos: `typecheck` (`tsc --noEmit`, full program), `config-gate` (winner receipts + alias execution, exit-coded), and the execution smoke (every entry boots under its pin — the [01/4.1](<../../../01 Execution Foundations and Mental Model/sections/4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>) gate extended). Half-pair and half-flag diffs fail at stage 21 *with the compiler's own message attached*; unbridged aliases fail at stage 22 *with the entry named*. No human needs to memorize the matrix ([2.1](<../2. Module pairs and specifiers/2.1. The module pair matrix for execution.md>)) to enforce it — the gate knows.

### Runnable example (good — the full gate, both scripts)

```bash
./gate.sh; echo "exec exit=$?"       # 01/4.1: pin + probe + checker
# GATE-GREEN
# exec exit=0
./gate2.sh pw/tsconfig.json; echo "config exit=$?"
# CONFIG-GREEN
# config exit=0
```

Verified back-to-back on the probe tree: execution green *and* config green — pin, probe, checker, winner, aliases, all receipted. Plant the `loose.ts` error → stage 12/21 fires; plant an unbridged alias → stage 22 fires; hide the tsconfig → stage 20/10 fires. Every failure in this track's catalog has a stage that names it.

### Runnable example (bad — review-only config governance)

```bash
# bad: "we review tsconfig diffs carefully" (and run no config gate)
# — the half-pair lands Friday (reviewer missed the absent half),
# deploys Monday (hook reads what review skimmed), pages Tuesday
```

Why it hurts: absence is unreviewable at scale (no diff hunk marks a missing `moduleResolution`), while consequences are perfectly checkable (the compiler *says* TS5109; the runtime *says* MODULE_NOT_FOUND). Governance by gate beats governance by vigilance — vigilance tires, gates don't.

### Common confusion

- **"gates replace review"** — gates replace *vigilance*, not judgment: reviewers still decide whether the alias is justified ([3.1](<../3. Paths runtime/3.1. paths and baseUrl that run.md>) part 3), whether the pair suits the architecture ([2.1](<../2. Module pairs and specifiers/2.1. The module pair matrix for execution.md>)). Gates enforce completeness; humans decide fitness.
- **"two gates are one too many"** — merge them freely (one script, six stages, distinct exits). This track keeps two files for teaching (execution vs configuration concerns); repos should keep one gate with both halves. Pedagogy splits; operations unifies.

### Performance note

Full gate (both scripts): seconds per run, dominated by the checker stage on large trees (incremental/watch locally, cold in CI). Schedule accordingly: smoke stages per execution, checker per merge — the cadence split from [01/4.1](<../../../01 Execution Foundations and Mental Model/sections/4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>) part 3 applies unchanged.

### Mentor note

The graduation exercise for this domain: hand the mentee a repo with three planted config faults (half-pair, unbridged alias, wrong-scope entry) and the gate scripts. Thirty minutes, three exit codes, three fixes — each fix must cite the leaf that owns it. Fluency demonstrated, not described.
