# 6.1. Boundaries: what is covered elsewhere

Where this domain stops and who owns the rest — the DRY map for configuration. Junior read: if your question isn't answered here, this page names the page that answers it. Expert read: the single-source-of-truth assignments that keep config knowledge in exactly one place per question.

## 1) Flag semantics and release history (TypeScript track owns the meaning)

### 1) **Definition** (the meaning boundary)

*What* each compiler option means, *when* it shipped, and *how* flags interact inside the checker are language knowledge — owned by the TypeScript track, assumed here, never redefined. This domain owns only the *wiring*: which files carry which flags, which entry each file governs, and how the runner reads them.

### The assignments (with the exact targets)

- Flag semantics (every `compilerOptions` field, checker interactions) → [TypeScript 13: Configuration and Compiler Options](<../../../../TypeScript/13 Configuration and Compiler Options/README.md>). All five config leaves link there instead of redefining.
- Release history (`rewriteRelativeImportExtensions` shipment scope, 5.7 change group) → [TypeScript 22 Update 5.7](<../../../../TypeScript/22 Update TypeScript 5.7/README.md>). [2.2](<../2. Module pairs and specifiers/2.2. allowImportingTsExtensions and extension rewriting.md>) operates the flag; its history lives there.
- Module forms and specifier discipline (import/export grammar, `import type` trio) → [TypeScript 12: Modules and Declaration Files](<../../../../TypeScript/12 Modules Namespaces and Declaration Files/README.md>). [2.1](<../2. Module pairs and specifiers/2.1. The module pair matrix for execution.md>) maps forms to doors; the forms live there.
- Execution foundations (hook model, modes, loading, gates) → [01 Execution Foundations](<../../../01 Execution Foundations and Mental Model/README.md>) (this track). This domain assumes all of it — modes behind the `ts-node` object, loading behind the scoping, gates behind the checklist.

### Common confusion

- **"this domain should explain what `strict` does"** — explaining it here duplicates TypeScript 13 in a second place, and duplicates drift. One-line mention plus link is the policy — DRY is correctness, not tidiness.
- **"wiring without semantics is shallow"** — wiring is where execution lives: the same flag means one thing to the checker and causes one behavior in the runner, and this domain owns the causal half. Depth here is measured in autopsies, not definitions.

### Mentor note

Teach mentees to read this page as a router: "meaning" questions go to TypeScript 13, "wiring" questions stay here. The distinction resolves half of all config debates before they start — most are meaning-questions asked in wiring-rooms, or the reverse.

### Common confusion

- **"textual forwards are dead links"** — deliberate placeholders (domain name + LOG pointer, never a `<path>` link), retired to live links as each domain lands. The rule: no angle-bracket link may point at a nonexistent file — verified by sweep after every unit this session.
- **"config should preview loaders"** — previews duplicate; config *assumes-forward*. [3.1](<../3. Paths runtime/3.1. paths and baseUrl that run.md>) names the Domain 03 recipe once and moves on — the recipe teaches, this domain doesn't pre-teach.

## 3) Runtime mechanics (neighbor tracks own the engine room)

### 3) **Definition** (the runtime boundary)

What happens *after* config and compilation — package installation, `node_modules` resolution inside Node, service debugging, sourcemap consumption — is neighboring-track knowledge. This domain configures the TypeScript on-ramp; the engine room belongs to the tracks that own it.

### The assignments (with the exact targets)

- Package mechanics (lockfiles, `node_modules` walk, binaries) → [NodeJS 02: Packages and Layout](<../../../../NodeJS/02 Packages Scripts and Project Layout/README.md>). [01/1.2](<../../../01 Execution Foundations and Mental Model/sections/1. Execution identity and setup/1.2. Installing and running your first TypeScript file.md>) pins the runner; package mechanics live there.
- Service debugging and shipping (inspector, profiles, containers, healthchecks) → [NodeJS 06: Debugging, Configuring, Shipping](<../../../../NodeJS/06 Debugging Configuring and Shipping/README.md>). Domain 05 will teach the *TypeScript layer* (sourcemaps, TS-aware profiles); service mechanics live there.
- Sourcemap/inspector mechanics (flags, DevTools workflow, `--enable-source-maps`) → [JavaScript 15/5.3. Source maps workflow](<../../../../JavaScript/15 Error Handling and Debugging/sections/5. Debugging toolkit/5.3. Source maps Node inspector DevTools workflow and flags.md>). Domain 05 will *apply* them to compiled output; the mechanics live there.

### Common confusion

- **"a config bug is a runtime bug"** — config decides *what compiles and how it loads*; the runtime decides *what happens after*. `MODULE_NOT_FOUND` on an alias is a config-scope failure with runtime vocabulary — the boundary ("resolve the mapping, then debug the behavior") assigns each half in seconds.
- **"this track replaces its prerequisites"** — it assumes them ([01 Execution Foundations](<../../../01 Execution Foundations and Mental Model/README.md>) + TypeScript 13). Readers arriving without the hook model or flag semantics should read those first — config architecture makes no sense atop missing foundations.

### Mentor note

The one-sentence router: "Meaning questions go to TypeScript 13, engine questions go to Node.js, *which-file-governs-which-entry* questions stay here." Three homes, no overlap, every question housed.
