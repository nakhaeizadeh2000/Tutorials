# 2.1. The module pair matrix for execution

Every executable `module`/`moduleResolution` combination ts-node meets in practice — which door each pair needs, which half-pairs die how, and why the matrix replaces memory. Junior read: look up your door, copy the pair. Expert read: the failure each wrong cell produces, all reproduced in this track's probes.

## 1) Name the door, the pair follows

### 1) **Definition** (the lookup table)

`module` chooses the emit shape, `moduleResolution` chooses the import spelling the checker accepts, and the *door* (require hook vs loader hook) chooses which shapes can load. The matrix below is the complete execution-relevant set as of September 2026 (TypeScript 5.9, ts-node 10.9.x, Node 20–26): sanctioned pairs run; everything else is a diagnosed failure, not a mystery.

### What problem it solves (history)

`module` accepts a dozen values (`commonjs`, `esnext`, `nodenext`, `node16`, `bundler`, …) interacting with three doors and two resolution algorithms — memorization fails somewhere around the fourth combination, and the failure lands as `TS5109`, `Unknown file extension`, or silent wrong-file. The matrix converts recall into lookup: find the door, read the pair.

### Modern guidance

Two sanctioned pairs cover nearly all services: `"module": "commonjs"` (+ default `node` resolution) through the require hook, and `"module": "NodeNext"` + `"moduleResolution": "NodeNext"` through the loader hook with matching `package.json` `type`. Set both fields explicitly in every config (the base from [1.1](<../1. Config architecture/1.1. Base and delta tsconfigs.md>) is the place). Everything outside the matrix needs a written reason and a reviewer.

### Runnable example (good — the matrix, with receipts)

| `module` | `moduleResolution` | Door | Verdict |
|---|---|---|---|
| `commonjs` | `node` (default) | CLI / `-r register` | runs (verified S1 + S2: `cjs: helped`, `extends: delta`) |
| `NodeNext` | `NodeNext` | `--loader ts-node/esm` + matching `type` | runs (verified S1: `esm: helped-esm`) |
| `esnext` | `node` | require hook | **dies** (verified below) |
| `NodeNext` (half) | unset | any | **dies** `TS5109` (verified S1: missing-config default) |
| `bundler` | `bundler` | require hook | checker-only spelling — runtime gap (see part 3 + [3.1](<../3. Paths runtime/3.1. paths and baseUrl that run.md>)) |

```bash
# the esnext cell, verified:
./node_modules/.bin/ts-node --transpile-only --project mx/tsconfig.json ./mx/run.ts
# TypeError: Unknown file extension ".ts" for /tmp/tsprobe/mx/run.ts
```

`module: esnext` emits ESM shape; the require hook loads CJS — Node's own format detection rejects the entry before ts-node compiles a line. Same error family as the missing-config death in [01/2.2](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.2. The tsconfig that executes.md>), same lesson: the pair must name a door that accepts its shape.

### Common confusion

- **"`moduleResolution` is a typechecker concern"** — it decides which *spellings* the checker accepts (`.js`-suffixed for NodeNext, extensionless for `node`), and ts-node executes sources written in those spellings. Wrong resolution setting, right runtime: the checker waves through imports the loader then refuses (autopsied in [01/3.1](<../../../01 Execution Foundations and Mental Model/sections/3. Loading model/3.1. Loading TypeScript under CJS and ESM.md>) bad-2).
- **"NodeNext vs node16 matters for execution"** — both select Node's real resolution with version-gated details; for *running* code they behave identically in the common cases. Pick `NodeNext` (tracks the running Node) and stop deliberating — the pair matters, the flavor doesn't.

### Performance note

The pair has no steady-state cost difference worth measuring (emit shape affects helper allocation marginally; the mode gap from [01/2.1](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>) dwarfs it 10×). Choose pairs by door correctness, then forget performance until a profile names the emit.

### Mentor note

Print the matrix on the team wiki and require every new tsconfig to cite its row. Mentees graduate from pair confusion the day lookup replaces memory — and reviewers gain a one-line check ("which matrix row?") that catches every half-pair at diff time.

## 2) Half-pairs fail loudly or worse

### 2) **Definition** (the incomplete contract)

A half-pair names the output shape without the resolution to match (`module: NodeNext` alone), or the resolution without the shape it serves. TypeScript 5.x answers half-pairs with `TS5109` *when it detects them* — and with silent fallback behavior when it doesn't (resolution quietly degrading to a default the author never chose).

### What problem it solves (history)

`TS5109` (module/NodeNext mismatch) was introduced precisely because silent fallback burned teams: code resolving under one algorithm in the editor and another at runtime, imports landing on different files per tool. The loud failure is the *good* outcome — it names the missing half. The bad outcome is the pair that typechecks, runs, and resolves differently in two places.

### Modern guidance

Complete every pair in the base config (both fields, same file, same commit), and treat any `TS5109` as a five-second fix (add the matching `moduleResolution`), never a research project. Audit for the silent kind with `--showConfig` (effective pair printed) plus a resolution probe: import one aliased and one relative module per system and confirm the loaded paths (`require.resolve` / `--experimental-print-required-tla`… in practice, a smoke test importing every alias).

### Runnable example (good — the loud failure, fixed in one line)

```bash
# half-pair: { "compilerOptions": { "module": "NodeNext" } }
./node_modules/.bin/ts-node --transpile-only ./hello.ts
# error TS5109: Option 'moduleResolution' must be set to 'NodeNext'
# (or left unspecified) when option 'module' is set to 'NodeNext'.
```

Verified S1 (missing-config default bet) and re-verified conceptually S2: the fix is the second half — `"moduleResolution": "NodeNext"` beside it. One line, zero ambiguity, the compiler literally dictating the repair.

### Runnable example (bad — silencing instead of completing)

```bash
# bad: TS5109 "fixed" by downgrading the shape instead of completing the pair
{ "compilerOptions": { "module": "commonjs" } }   # was NodeNext-intended
# the error vanishes — and so does the ESM architecture the package wanted
```

Why it hurts: the error was *correct* (the tree wanted Node semantics); the fix deleted the intent instead of completing it. ESM packages silently become CJS, top-level await breaks downstream, loader wiring rots — all because a diagnostic was treated as noise. Fix the pair toward the architecture, never away from the error.

### Common confusion

- **"`TS5109` is ts-node pedantry"** — it fires from `tsc` identically (checker-level validation, mode-independent — verified in transpile-only). Blaming the runner delays the one-line fix by exactly the time spent switching runners to "prove" it.
- **"leaving `moduleResolution` unset is safer"** — unset means *defaulted*, and defaults encode bets (the S1 missing-config death ran on defaults). Explicit beats absent: two fields, both named, no bets.

### Performance note

Half-pairs cost nothing at runtime (they fail before running, or degrade silently at resolve time — microseconds either way). Their cost is entirely human: misdiagnosis cycles per incident. The cheapest performance practice in this leaf is also the simplest — complete pairs eliminate an entire failure class for zero runtime cost.

### Mentor note

Use `TS5109` as the canonical "read the error" teaching moment: the message names the option, the required value, and the alternative — the complete repair in one sentence. Mentees who learn to obey precise diagnostics here obey them everywhere; the habit transfers to every compiler they will ever meet.

## 3) ESM output needs the loader door

### 3) **Definition** (shape/door agreement)

ESM-shaped emit (`esnext`, `NodeNext` under `type: module`, `nodenext`) can only enter Node through the ESM pipeline — the loader hook (`--loader ts-node/esm` / `register()`), which compiles during `load` with the correct `format`. The require hook (`-r ts-node/register`, CLI-in-CJS-mode) speaks CJS exclusively: ESM shape through it dies at format detection, before compilation, every time.

### What problem it solves (history)

Mixed-shape repos (CJS packages beside ESM packages, migrations mid-flight) constantly feed one door the other's shape — the CLI defaults to require-hook behavior, so ESM entries fail until the loader flag is added. The rule "shape names the door" ends the guessing: read the emit, pick the flag, no third option.

### Modern guidance

ESM entries always launch with the loader flag (plus `TS_NODE_PROJECT` scoping from [1.2](<../1. Config architecture/1.2. Monorepo configs and project scoping.md>)); CJS entries always launch bare or `-r`. Encode the door in the package's scripts (not in runbooks): `"dev": "node --loader ts-node/esm ./src/entry.ts"` vs `"dev": "ts-node --transpile-only ./src/server.ts"` — the command line *is* the shape declaration.

### Runnable example (good — shape matched to door)

```bash
# ESM shape + loader door (verified S1):
TS_NODE_PROJECT=esm/tsconfig.json node --loader ts-node/esm ./esm/entry.ts
# esm: helped-esm

# CJS shape + require door (verified S1+S2):
./node_modules/.bin/ts-node --transpile-only --project cjs/tsconfig.json ./cjs/main.ts
# cjs: helped
```

### Runnable example (bad — ESM shape, CJS door)

```bash
# bad: esnext emit through the require hook (verified this session)
./node_modules/.bin/ts-node --transpile-only --project mx/tsconfig.json ./mx/run.ts
# TypeError: Unknown file extension ".ts" for /tmp/tsprobe/mx/run.ts
```

Why it hurts: the error mentions extensions (a *resolution* vocabulary) for what is actually a *shape/door* mismatch — misdirection that sends debugging toward specifiers and configs instead of the invocation. Fix: read shape first (`--showConfig` → `module`), then match the door. Extension errors on ESM-shaped output are door errors until proven otherwise.

### Common confusion

- **"the CLI auto-detects ESM"** — the CLI follows the *config's* shape and the *package's* type; with `esnext` emit and no loader flag there is nothing to detect *with*. Auto-detection would require loading to know the format before the hook that teaches formats runs — circular by construction.
- **"`.mts` fixes the door"** — `.mts` fixes the *format signal* (always ESM regardless of `type`), which helps resolution pick correctly — but the hook flag is still required to *compile* the TypeScript. Signal and hook are independent slots; filling one never fills the other.

### Performance note

Door mismatch costs a failed boot (seconds) plus misdirected debugging (hours) — the most expensive cell in the matrix per occurrence. Correct doors cost nothing extra (loader vs require overhead is noise beside mode choice). Matrix lookup before invocation: free. Autopsy after: dear.

### Mentor note

Drill shape→door as a reflex: show a `module` value, demand the invocation in under five seconds (`commonjs` → bare CLI; `esnext`/`NodeNext` → loader flag + scope). Five values, five answers, no hesitation — the drill takes ten minutes and prevents the most misdirected debugging sessions in this track.
