# 2.2. allowImportingTsExtensions and extension rewriting

Writing `.ts` extensions in import specifiers — the flag that permits it, the rewrite that ships it, and the exact name that gates both. Junior read: two flags, one config, `.ts` in source becomes `.js` in output. Expert read: why the wrong name dies `TS5023`, and why ts-node runs the unrewritten source while Node never could.

## 1) Write `.ts`, ship `.js`

### 1) **Definition** (the 5.0/5.7 pair)

`allowImportingTsExtensions` (TypeScript 5.0+) permits `.ts`/`.mts`/`.cts` extensions in relative import specifiers where the checker previously rejected them; `rewriteRelativeImportExtensions` (TypeScript 5.7+, documented in the TS 5.7 release notes this track links) rewrites those extensions to their `.js`/`.mjs`/`.cjs` counterparts at emit. Together: sources name the real file, outputs name the runnable file, one tree serves checkers, emitters, and runners.

### What problem it solves (history)

NodeNext discipline demands explicit extensions, but source files are `.ts` while only `.js` (post-emit) is runnable — so authors wrote `.js` specifiers pointing at files that don't exist on disk (correct, but unreadable to newcomers and unnavigable to naive tooling). The pair resolves the lie: write the file that exists, ship the specifier that runs. ts-node additionally runs the unrewritten source directly (verified below), closing the loop for hook-based execution.

### Modern guidance

ESM services that want self-describing imports: enable both flags in the same tsconfig the runner reads, write `.ts` extensions in relative imports, and keep the classic `.js`-specifier style everywhere else (mixed conventions per file are worse than either convention uniformly). Requires `noEmit` or `emitDeclarationOnly`… no — requires only the pair; but note the constraint the compiler enforces: rewriting applies to *relative* imports, and ambient/bare specifiers stay untouched.

### Runnable example (good — the triple, verified)

```typescript
// ait/src/main.ts — names the file that exists
import { g } from "./helper.ts";
console.log("ait:", g());
```

```bash
./node_modules/.bin/tsc --noEmit --project ait/tsconfig.json && echo AIT-CHECK-OK
# AIT-CHECK-OK

./node_modules/.bin/tsc -p ait/tsconfig.emit.json && cat ait/dist/main.js
# import { g } from "./helper.js";
# console.log("ait:", g());

TS_NODE_PROJECT=ait/tsconfig.json node --loader ts-node/esm ./ait/src/main.ts 2>/dev/null
# ait: ait
```

Verified on TypeScript 5.9.3 + ts-node v10.9.2: checker accepts, emitter rewrites `.ts`→`.js`, loader runs the unrewritten source. Three tools, one convention, zero contradictions.

### Common confusion

- **"the rewrite fixes runtime resolution"** — the rewrite fixes *emitted* code; ts-node never emits to disk, so under the hook the *loader* resolves the `.ts` specifier directly (it knows the mapping). Bare Node on unrewritten sources still fails — the pair is a checker/emitter contract, and the hook honors it by understanding both spellings.
- **"works for bare/package imports"** — rewriting covers *relative* imports only. `@app/util`-style bare specifiers keep their spelling through emit (and keep their runtime gap — owned by [3.1](<../3. Paths runtime/3.1. paths and baseUrl that run.md>)).

### Performance note

Zero runtime cost (spelling only — emit bytes differ by one character per specifier). The payoff is human: imports name existing files, so go-to-definition, new-hire navigation, and naive grep all work without a mental `.js`→`.ts` translation layer. Tooling that resolves `.ts` specifiers natively (ts-node's loader, bundlers) pays nothing; tooling that doesn't (bare Node) was never in the audience.

### Mentor note

Adopt per-service, never per-file: grep the tree for mixed `.js`/`.ts` relative specifiers during review — a mixed tree forces every reader to know which convention each file follows, defeating the purpose. The migration is mechanical (rewrite specifiers, enable the pair, run the matrix from [2.1](<./2.1. The module pair matrix for execution.md>)) and makes a good first-week task.

## 2) The flag name is the trap

### 2) **Definition** (the rename that never happened)

The flag is `allowImportingTsExtensions` — full name, no abbreviation. `allowImportingTs` (the "obvious" shortening) is not a flag in any TypeScript release through 5.9: the compiler answers it with `error TS5023: Unknown compiler option`. The trap is set by plausibility — the wrong name looks more natural than the right one.

### What problem it solves (history, inverted)

This part exists because documentation-by-memory fails exactly here: blog posts abbreviate, chatbots shorten, and the author's fingers type the short form unbidden. `TS5023` is the compiler defending its vocabulary — unknown options abort before anything else runs, which (perversely) makes this the *loudest* failure in the domain: total boot refusal over one identifier.

### Modern guidance

Copy the flag name from `tsc --showConfig` acceptance, never from prose: add the flag, run `--showConfig`, confirm it echoes back. Any guide (including this one) is a pointer; the compiler's option parser is the authority. When `TS5023` names an option, the fix is orthographic — diff the identifier character by character against the handbook, don't reason about semantics.

### Runnable example (good — the wrong name, caught live)

```bash
printf '{\n  "compilerOptions": { "allowImportingTs": true, "noEmit": true }\n}\n' > ait/mini.json
./node_modules/.bin/tsc --showConfig -p ait/mini.json
# ait/mini.json(2,24): error TS5023: Unknown compiler option 'allowImportingTs'.
```

Verified on TypeScript 5.9.3: this session's own probe authored the wrong name from memory and the compiler refused it — the finding survived into the leaf deliberately. The corrected file (`allowImportingTsExtensions`) echoes its merged form instead of erroring.

### Runnable example (bad — "fixing" the error by removing the flag)

```bash
# bad: TS5023 → delete the flag → checker now rejects .ts specifiers →
# rewrite the imports back to .js → the whole convention quietly dies
```

Why it hurts: the error was orthographic (one identifier), but the "fix" deletes the feature (the convention, the emit rewrite, the loader compatibility). Total blast radius from one misread diagnostic. Fix the spelling, keep the feature — in that order, always.

### Common confusion

- **"TS5023 means my TS is too old"** — sometimes (genuinely new flags on old compilers), but *here* 5.9.3 rejects it: newness is not the axis, existence is. Check the name first (docs search), the version second (`tsc --version`) — the order matters because the common case is the typo, not the toolchain.
- **"the IDE accepted it"** — editors validate against JSON schemas that may lag or diverge from the installed compiler. The compiler's parser outranks every schema, every linter, every memory — `--showConfig` is the vote that counts.

### Performance note

Zero runtime dimension (config rejected before compilation starts). The cost axis is authoring time: one minute per `TS5023` when the habit is "diff the identifier," unbounded when the habit is "reinstall the toolchain and ask chat." Habits have performance profiles too.

### Mentor note

Keep a running "hall of typos" for the team (`allowImportingTs`, `moduleResoltuion`, `esModuleInterop` casing…) with the exact diagnostic each produces. Newcomers hit one within weeks; the hall turns a confusing refusal into a five-second lookup. This leaf's verified example is entry one.

## 3) Pair or perish

### 3) **Definition** (the conjunction contract)

Accept-without-rewrite is a trap; rewrite-without-accept is a different trap. `allowImportingTsExtensions` without `rewriteRelativeImportExtensions`: sources import `.ts`, emit keeps `.ts`, every runner but the checker crashes on the specifier. `rewriteRelativeImportExtensions` without the accept flag: the compiler rejects the `.ts` spelling before rewriting anything. Both flags, same config, the config the runner reads — or neither.

### What problem it solves (history)

The flags shipped two years apart (accept in 5.0, rewrite in 5.7), so a generation of configs carries the first without the second — written when rewrite didn't exist, never completed after it landed. Those configs typecheck green and crash red on every runner: the exact "typechecks but crashes" shape interviewers probe ([5.1](<../5. Interview questions and answers/5.1. Common interview QA configuration.md>)) and [3.1](<../3. Paths runtime/3.1. paths and baseUrl that run.md>) generalizes.

### Modern guidance

Enable the pair atomically (one commit, both flags, plus a specifier grep proving the tree uses the spelling), and lint the conjunction in review: any config containing one flag without the other fails the checklist ([4.1](<../4. Important points to remember/4.1. Config checklist habits mentors insist on.md>)). The pair lives in the *runner-read* config — a build-only tsconfig carrying the rewrite while the runner reads a sibling without it reproduces the crash with extra steps.

### Runnable example (good — the pair complete, all three tools agree)

```bash
# ait/tsconfig.json carries BOTH flags (verified triple from part 1):
./node_modules/.bin/tsc --noEmit --project ait/tsconfig.json && echo CHECK-OK
# CHECK-OK
./node_modules/.bin/tsc -p ait/tsconfig.emit.json && grep 'from' ait/dist/main.js
# import { g } from "./helper.js";
TS_NODE_PROJECT=ait/tsconfig.json node --loader ts-node/esm ./ait/src/main.ts 2>/dev/null
# ait: ait
```

### Runnable example (bad — accept without rewrite)

```jsonc
// bad: the 5.0-era config, never completed after 5.7
{ "compilerOptions": { "allowImportingTsExtensions": true, "noEmit": false } }
// checker: green (.ts spelling permitted) —
// emit: ./helper.ts specifier preserved → node: Cannot find module './helper.ts'
```

Why it hurts: the green check actively vouches for sources no runner can execute — confidence inverted, exactly backwards from a gate's purpose. The crash arrives at boot (loud) or, under bundlers that resolve `.ts`, never (divergent) — either way the config lied. Fix: add the rewrite flag in the same file, same commit, verified by reading the emitted specifier.

### Common confusion

- **"noEmit configs don't need the rewrite"** — the *checker* doesn't, but the config is shared with emitters and readers (build tsconfig extends it, ts-node reads it, editors mirror it). The pair belongs in the base ([1.1](<../1. Config architecture/1.1. Base and delta tsconfigs.md>)) so every consumer inherits the conjunction, not the fragment.
- **"ts-node needs neither flag"** — ts-node's loader resolves `.ts` specifiers regardless (verified: it ran the unrewritten source). True — and irrelevant: the flags exist for the *other* tools in the pipeline (tsc, bundlers, stripping-era Node). Runner tolerance never excuses pipeline incoherence.

### Performance note

No runtime cost (emit-time string rewrite, once per build). The cost of incompleteness is measured in boot crashes per deploy — the most expensive unit in this domain. Atomic adoption (both flags, one commit, one verification triple) is the cheapest possible insurance.

### Mentor note

Teach flag pairs as *conjunctions to be completed*, not items to be collected: every flag learned gets the question "what completes it?" (`allowImportingTsExtensions` → rewrite; `module: NodeNext` → resolution; `paths` → runtime bridge). Mentees who ask the completion question unprompted stop filing half-configs within a month.
