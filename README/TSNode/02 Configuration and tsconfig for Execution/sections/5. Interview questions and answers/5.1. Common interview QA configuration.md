# 5.1. Common interview QA: configuration

Canonical answers for the three config questions every TypeScript-on-Node interview asks, plus rapid-fire drills. Junior read: memorize the autopsy sentences. Expert read: each answer pairs the diagnostic with its *verified reproduction* from this domain — mechanism, evidence, and fix in thirty seconds.

## 1) "TS5109 on boot" — autopsy it

### 1) **Definition** (the half-pair screen)

`error TS5109: Option 'moduleResolution' must be set to 'NodeNext' when option 'module' is set to 'NodeNext'` screens for pair completion from [2.1](<../2. Module pairs and specifiers/2.1. The module pair matrix for execution.md>): candidates who "try flipping flags until it boots" fail; hires read the diagnostic (it names the option, the required value, and the alternative) and complete the pair in one line.

### What problem it solves (hiring signal)

Half-pairs are the most common config fault in the wild (defaults, copies, and refactors all produce them), and the fix is trivial *iff* the candidate reads diagnostics literally. The question predicts whether config incidents take thirty seconds or thirty minutes on this hire's watch.

### Modern guidance

Answer in three beats: quote the diagnostic (proves you read it), name the missing half (`moduleResolution: NodeNext` beside `module: NodeNext` — or the reverse downgrade, rejected: complete toward the architecture, never away from the error), and state where it lands (the base config's pair, same file, same commit). End with prevention: the gate's checker stage ([4.1](<../4. Important points to remember/4.1. Config checklist habits mentors insist on.md>)) catches half-pairs pre-merge, so humans never should.

### Runnable example (good — the autopsy live)

```bash
# half-pair config: { "compilerOptions": { "module": "NodeNext" } }
./node_modules/.bin/ts-node --transpile-only ./hello.ts
# error TS5109: Option 'moduleResolution' must be set to 'NodeNext' ...
```

Verified S1 (missing-config default bet) and S2 (matrix cell): the candidate narrates *before* running — "transpile-only still parses config, the defaulted module is NodeNext without resolution, expect TS5109" — then the output confirms. Prediction first, confirmation second: that ordering is what interviewers score.

### Common confusion (in candidates)

- **"it's a ts-node bug"** — red flag: `TS5109` fires from `tsc` identically (verified in transpile-only, which skips checking but never config parsing). Blaming the runner reveals the candidate never learned which stage owns options.
- **"delete the module line"** — yellow flag: silences the diagnostic by deleting intent (the ESM architecture the package wanted). Strong candidates complete the pair; weak ones negotiate with the error.

### Performance note

Thirty-second fix when read literally; unbounded when "researched" (reinstalls, runner swaps, forum dives). Interviewers asking "how long should this take?" expect "under a minute, most of it typing" — calibration about diagnostic trust, not speed.

### Mentor note

Rehearse with the error text on screen and the keyboard covered: no running, just reading — "what's the fix?" Mentees graduate when the answer comes from the message alone. The habit (read diagnostics as instructions) transfers to every tool they will ever debug.

## 2) "Typechecks but crashes on import" — autopsy it

### 2) **Definition** (the two-resolver screen)

Green `tsc`, red boot on the first import — screens for the checker/runtime split from [3.1](<../3. Paths runtime/3.1. paths and baseUrl that run.md>): hires name the two resolvers (checker reads `paths`, Node doesn't) before touching anything; the rest debug the application for an hour first.

### What problem it solves (hiring signal)

This shape is the most common TypeScript-on-Node production incident (green CI vouching for unrunnable code), so the answer predicts incident response directly. Candidates who say "paths needs a runtime half" in the first minute will resolve the page in ten; candidates who start in application logs will resolve it after the bridge is suggested to them.

### Modern guidance

Answer in pipeline order: reproduce under the hook (`MODULE_NOT_FOUND` naming the alias — evidence), explain the split (checker maps, runtime doesn't — mechanism), offer both closings (bridge with `tsconfig-paths` where aliases earn it, erase to relatives where they don't — judgment). Verified triple from [3.1](<../3. Paths runtime/3.1. paths and baseUrl that run.md>): `PATHS-CHECK-OK`, `Cannot find module '@app/util'`, `pw: paths` after `-r tsconfig-paths/register`.

### Runnable example (good — the three-command proof)

```bash
./node_modules/.bin/tsc --noEmit --project pw/tsconfig.json && echo CHECK-OK
# CHECK-OK
./node_modules/.bin/ts-node --transpile-only --project pw/tsconfig.json ./pw/src/main.ts
# Error: Cannot find module '@app/util'
./node_modules/.bin/ts-node --transpile-only -r tsconfig-paths/register --project pw/tsconfig.json ./pw/src/main.ts
# pw: paths
```

A hire narrates the *verdict each command must produce* before running (green check, red boot, green bridge) — the interviewer watches prediction, not output. Follow-up ("workers spawn bare — where does the bridge go?"): `NODE_OPTIONS` env level, or the alias gets erased — per-door wiring leaks where processes multiply.

### Common confusion (in candidates)

- **"add the alias to more configs"** — red flag: the mapping exists (checker proves it); what’s missing is runtime support. More mapping fixes nothing — the candidate debugs the informed resolver instead of the ignorant one.
- **"switch to tsx/bundler"** — yellow flag: different tools with their own `paths` stories (bundlers resolve at build; the gap merely moves). Strong candidates fix the pipeline in place before auditioning replacements.

### Performance note

Bridge cost (hash lookup per import) is unmeasurable beside compilation — candidates citing performance against the bridge reveal premature optimization instincts. The priced answer: "free at runtime, one package + one flag of surface; erasure when the alias doesn't earn it." Economics, not benchmarks.

### Mentor note

Mock this question with the three commands ready but unrun, and demand predictions first ("what does each print, and why?"). Mentees graduate when all three predictions land — the predictions *are* the model, the outputs merely confirm it.

## 3) "Unknown option allowImportingTs" — autopsy it (plus rapid-fire)

### 3) **Definition** (the vocabulary screen)

`error TS5023: Unknown compiler option 'allowImportingTs'` screens for evidence-over-memory: the wrong name is *more* plausible than the right one (`allowImportingTsExtensions`), so candidates who trust fingers over parsers fail loudly at boot. Hires diff the identifier against the compiler (`--showConfig` acceptance) instead of defending their memory.

### What problem it solves (hiring signal)

Config vocabulary errors are weekly occurrences (abbreviated blog flags, shortened chat answers, confident typos), and the fix is orthographic — thirty seconds for the evidence-driven, unbounded for the memory-defenders (who reinstall toolchains and question versions). The question measures the cheapest high-frequency habit in this domain.

### Modern guidance

Answer: the flag is `allowImportingTsExtensions` (verified `TS5023` on 5.9.3 this session — the author's own memory bug, kept as material), paired atomically with `rewriteRelativeImportExtensions` (accept without rewrite crashes every runner but the checker — [2.2](<../2. Module pairs and specifiers/2.2. allowImportingTsExtensions and extension rewriting.md>) part 3). Habit stated unprompted: "I copy flag names from `--showConfig` acceptance, never from prose" — that sentence scores independently of the answer.

### Runnable example (good — wrong name, right reflex)

```bash
./node_modules/.bin/tsc --showConfig -p ait/mini.json
# ait/mini.json(2,24): error TS5023: Unknown compiler option 'allowImportingTs'.
```

Verified: thirty seconds from diagnostic to corrected config (full name, pair completed, triple re-verified: check + emit rewrite + loader run). The candidate who narrates "orthographic, not semantic — diff the identifier" before fixing demonstrates the reflex; the candidate who reaches for version tables demonstrates its absence.

### Rapid-fire drills (with answers)

1. **Entry inherits the wrong package's pair — first command?** `--showConfig` (receipt the winner) — then pin with `--project`/`TS_NODE_PROJECT` ([1.2](<../1. Config architecture/1.2. Monorepo configs and project scoping.md>)).
2. **`esnext` emit through CLI fails `Unknown file extension` — cause?** Shape/door mismatch (ESM shape, require door) — relaunch via the loader door ([2.1](<../2. Module pairs and specifiers/2.1. The module pair matrix for execution.md>)).
3. **`.ts` specifier accepted by tsc, crashes Node — missing what?** The rewrite half (`rewriteRelativeImportExtensions`) — accept without rewrite is the trap ([2.2](<../2. Module pairs and specifiers/2.2. allowImportingTsExtensions and extension rewriting.md>)).
4. **Gate exits 20 — meaning?** No config winner (`--project` handed an entry path, or no file on the walk) — receipt stage ([4.1](<../4. Important points to remember/4.1. Config checklist habits mentors insist on.md>)).
5. **Gate exits 22 — meaning?** Unbridged alias (checker passed, aliased entry didn't execute) — bridge or erase ([3.1](<../3. Paths runtime/3.1. paths and baseUrl that run.md>)).
6. **New package, no tsconfig — behavior?** Newest-`@tsconfig/bases` bet, silent — write the three-line config before the first run ([1.2](<../1. Config architecture/1.2. Monorepo configs and project scoping.md>)).

### Common confusion (in candidates)

- **"TS5023 means upgrade TypeScript"** — sometimes true, here false (5.9.3 rejects it — existence axis, not version axis). Candidates who check the name first (docs) and version second (`tsc --version`) order correctly; reversers burn time on every typo.
- **"the IDE accepted the flag"** — schemas diverge from parsers; the compiler outranks all of them. Candidates citing `--showConfig` as the vote that counts pass; schema-trusters wobble.

### Performance note

Thirty seconds per vocabulary fault with the diff-the-identifier habit; unbounded without it. Teams feel this as onboarding drag (newcomers hit one within weeks) — the hall-of-typos practice from [2.2](<../2. Module pairs and specifiers/2.2. allowImportingTsExtensions and extension rewriting.md>) converts it to a five-second lookup permanently.

### Mentor note

Run rapid-fire timed (ten seconds per answer, autopsy misses against this domain's leaves). Six-for-six is the graduation bar — and the same six make a quarterly team health-check. Interviewers: drill 4 vs 5 (exit 20 vs 22) separates gate-users from gate-tourists.
