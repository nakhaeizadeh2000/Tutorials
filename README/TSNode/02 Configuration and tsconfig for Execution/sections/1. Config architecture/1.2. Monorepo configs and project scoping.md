# 1.2. Monorepo configs and project scoping

Which `tsconfig.json` governs an entry point — the upward search, explicit scoping per package, and what the defaults do when no file exists. Junior read: every entry must resolve to exactly one config; verify with `--showConfig`. Expert read: the search starts at the entry (not the CWD), and the wrong winner fails in the other package's voice.

## 1) Upward search starts at the entry

### 1) **Definition** (tsc search rules, inherited)

ts-node locates configuration with the same search behavior as `tsc`: upward from the *entrypoint script* (or `--cwd` in `--cwdMode`/REPL, where no entry exists). The first `tsconfig.json` found walking toward the filesystem root governs the run — its `module` pair, its strictness, its `ts-node` object. No file found → newest `@tsconfig/bases` defaults for your Node+TS (per official docs).

### What problem it solves (history)

Single-package repos never notice the search (one config, found immediately). Monorepos notice it constantly: `packages/api/run.ts` inherits `packages/api/tsconfig.json` while `scripts/run.ts` inherits the root one — different pairs, different modes, same command shape. The search rule explains why identical invocations behave differently per directory, and it has done so since ts-node adopted tsc's resolution.

### Modern guidance

Give every executable package its own tsconfig (even a three-line delta extending the root base from [1.1](<./1.1. Base and delta tsconfigs.md>)) so the search terminates locally and deliberately. Scripts outside packages either get their own config or an explicit `--project` pin — never the accident of whatever the walk finds. Verify the winner per entry with bare `--showConfig` (prints the resolved `project` path — verified below).

### Runnable example (good — nested entry inherits root, visibly)

```bash
# mono/pkg-a/run.ts exists; mono/pkg-a/tsconfig.json does NOT
./node_modules/.bin/ts-node --showConfig 2>&1 | grep '"project"'
#     "project": "/tmp/tsprobe/tsconfig.json"

./node_modules/.bin/ts-node ./mono/pkg-a/run.ts
# mono: scoped
```

Verified: the walk from `mono/pkg-a/` finds no local file, terminates at the root config, and the entry runs under the root's `commonjs` pair. The `project` line is the receipt — quote it in bug reports instead of describing directory layouts in prose.

### Runnable example (bad — assuming the CWD decides)

```bash
# bad: running from packages/api and assuming its tsconfig governs
# (the entry lives in scripts/ — the walk starts there, not here)
cd packages/api && ts-node ../../scripts/migrate.ts
# governs: scripts/tsconfig.json (or root) — NOT packages/api/tsconfig.json
```

Why it hurts: the failure speaks in the wrong package's voice (api's pair expected, scripts' pair applied — `TS5109` here, silent wrong-file there), and the debugger re-runs from a different CWD with a *different* winner. Fix: scope explicitly (part 2) or co-locate entries with their configs — never navigate-and-hope.

### Common confusion

- **"`--project` takes the entry"** — it takes a *config path*: `--showConfig --project mono/pkg-a/run.ts` dies with `TSError` (verified live — the flag resolves a project file, not an entry). Entry on the command line, config behind `--project`, never swapped.
- **"REPL uses the entry's config"** — the REPL has no entry, so the search falls back to `--cwd`/`process.cwd()`. Different launch directories, different REPL behavior — pin with `--project` in REPL-bound workflows or stop being surprised.

### Performance note

The search is a few `stat` calls per boot (noise) — until a networked filesystem or a 30-level-deep container path makes it measurable. `--project` skips the walk entirely: pin it in hot paths (watch loops, workers) and the cost drops to zero while the determinism win stays.

### Mentor note

Teach the walk physically: `find <entry-dir> -maxdepth 4 -name tsconfig.json` before any scoping debate. Mentees who list the *candidates* before arguing the *winner* resolve monorepo config fights in minutes; the rest argue about ghosts.

## 2) Scope explicitly per package

### 2) **Definition** (two pins, same effect)

`--project <path>` (CLI flag, where the CLI owns the process) and `TS_NODE_PROJECT=<path>` (env var, where tools spawn Node themselves) both override the upward search with an explicit config file. Same mechanism the loader door uses (`TS_NODE_PROJECT` scoped the ESM run in [01/3.1](<../../../01 Execution Foundations and Mental Model/sections/3. Loading model/3.1. Loading TypeScript under CJS and ESM.md>)) — applied here to package scoping.

### What problem it solves (history)

Implicit search makes behavior a function of *file location*: move an entry across packages and its compiler pair changes without a single edited line. Explicit scoping makes behavior a function of *declaration*: the script, the launch config, or the env names the project, and moves change nothing until the declaration changes. Location-independent behavior is what lets monorepos refactor safely.

### Modern guidance

npm scripts use `--project` (visible in `package.json`, reviewable in diffs); spawned processes, debuggers, and loaders use `TS_NODE_PROJECT` (flows through env where flags cannot); the `ts-node.project` key inside config covers programmatic registration. One rule: any entry whose walk *could* terminate anywhere but its own config gets a pin — "could" evaluated by listing candidates, not by hoping.

### Runnable example (good — the pin changes behavior, both forms)

```typescript
// loose.ts — the TS2322 file from 01/1.1 (root config: full mode)
const x: number = "not a number";
```

```bash
./node_modules/.bin/ts-node ./loose.ts 2>&1 | head -2
# TSError: ⨯ Unable to compile TypeScript:   (root config: full check gates)

./node_modules/.bin/ts-node --project cfg/app/tsconfig.json ./loose.ts
# runs: not a number                        (pinned config: transpileOnly)

TS_NODE_PROJECT=cfg/app/tsconfig.json ./node_modules/.bin/ts-node ./loose.ts
# runs: not a number                        (env pin: identical effect)
```

Verified: same file, same binary, three behaviors — governed entirely by which config won. The pin is not a hint; it is the *entire* difference between a gate and a run.

### Runnable example (bad — the unpinned monorepo script)

```jsonc
// bad: packages/api/package.json — works until the entry moves
{ "scripts": { "migrate": "ts-node ../../scripts/migrate.ts" } }
// the entry's walk terminates at scripts/tsconfig.json TODAY —
// after the next reorganization it terminates elsewhere, silently
```

Why it hurts: reorganization (the most routine monorepo operation) becomes a compiler-behavior change with no diff marking it — failures arrive weeks later, blamed on the code that moved rather than the config that changed underneath it. Fix: `"migrate": "ts-node --project ../../scripts/tsconfig.json ../../scripts/migrate.ts"` — the pin survives every move that preserves the relative layout, and breaks loudly (missing file) otherwise.

### Common confusion

- **"`--project` and `TS_NODE_PROJECT` conflict"** — precedence is defined (explicit flag beats env beats search); setting both is redundant, not contradictory. Pick the form the *launcher* supports (CLI → flag, spawned → env) and set exactly one.
- **"pinning duplicates the walk's answer"** — today, yes; the pin pays off on the day the layout changes. Like type annotations, explicit scope is insurance against future edits, not a description of the present.

### Performance note

Pinned projects skip the upward walk (a handful of syscalls) — negligible per run, meaningful per *watch loop iteration* and per *worker spawn* at scale. The real performance win is human: pinned entries never trigger cross-package misconfiguration incidents, each worth hours.

### Mentor note

Review rule: any npm script whose entry path crosses a package boundary without `--project` gets a scoping comment. Mentees internalize the rule fastest by breaking it once: move an unpinned entry, watch the behavior change with zero diffs, then add the pin and repeat — the lesson is the contrast.

## 3) Defaults are a bet, not a promise

### 3) **Definition** (the newest-bases fallback)

No `tsconfig.json` found anywhere on the walk → ts-node uses the newest recommended defaults from `@tsconfig/bases` compatible with your Node and TypeScript (recent pairings: `@tsconfig/node16`-class). The fallback encodes a bet — modern module settings, strict-ish checking — placed without consulting your tree.

### What problem it solves (history)

Early ts-node *required* a config file; missing files failed opaquely at boot. The bundled-defaults fallback (shipped with the `@tsconfig/bases` integration) turned a hard failure into a working run — at the cost of hiding the absence. Scripts "just work" until the day the bet mismatches the tree, which is exactly the failure [01/2.2](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.2. The tsconfig that executes.md>) autopsied: full mode `Unknown file extension`, transpile-only `TS5109`.

### Modern guidance

Treat a defaulted run as a *diagnostic signal*, not a state: if `--showConfig` reveals no `project` file (defaults in use), write the three-line config from [01/2.2](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.2. The tsconfig that executes.md>) before anything else. Extend a bundled base explicitly (`"extends": "ts-node/node16/tsconfig.json"`, per official docs) when you genuinely want the recommendation — inherited deliberately, with a name and a version, rather than received silently from the fallback.

### Runnable example (good — naming the inheritance)

```jsonc
// tsconfig.json — the fallback's bet, stated explicitly and pinned
{
  "extends": "ts-node/node16/tsconfig.json",
  "compilerOptions": { "strict": true }
}
```

```bash
./node_modules/.bin/ts-node --showConfig 2>&1 | grep '"project"'
#     "project": "/tmp/tsprobe/tsconfig.json"   (a file won — no fallback)
```

Explicit `extends` converts the silent bet into a declared dependency: upgrades to ts-node re-resolve the named base (visible in `--showConfig`), and readers see the inheritance instead of inferring it. Verified: with a file present, `project` names it; without one, defaults apply unnamed.

### Runnable example (bad — building on the unnamed default)

```bash
# bad: repo with no tsconfig.json, ts-node "working fine"
# — until a ts-node minor bumps the bundled base (module NodeNext, say),
# and every entry'semit changes with zero repo diffs
```

Why it hurts: the behavior changelog lives in *ts-node's* release notes, not the repo's — upgrades become behavior changes nobody reviewed, and bisection points at the ts-node version rather than any decision. Fix: the three-line config (or an explicit `extends`) — three lines that convert "whatever the runner thinks" into "what the repo declares."

### Common confusion

- **"defaults match `tsc` behavior"** — `tsc` *requires* files and has no equivalent fallback; an unconfigured `tsc` fails where unconfigured ts-node runs. The tools disagree by design here — another reason the runner needs its own declared config rather than borrowing assumptions from the checker.
- **"older TypeScript gets the same defaults"** — incompatible older compilers receive an *older* default configuration (per docs). Same repo, different TS majors, different silent behavior — the pin from [01/1.2](<../../../01 Execution Foundations and Mental Model/sections/1. Execution identity and setup/1.2. Installing and running your first TypeScript file.md>) is what makes the fallback deterministic per machine.

### Performance note

Default configurations target modern Node (`es2022`-class emit) — on a current runtime that is the *fast* choice (no downlevel helpers). The performance risk of defaults is not speed but *surprise*: a base bump changing emit characteristics mid-upgrade. Pin the base name; the speed takes care of itself.

### Mentor note

The thirty-second audit for any repo: `ls tsconfig*.json` — zero results means the fallback governs, and the fix is the smallest possible config commit. Teach mentees to run the audit on every repo they join before trusting a single green run.
