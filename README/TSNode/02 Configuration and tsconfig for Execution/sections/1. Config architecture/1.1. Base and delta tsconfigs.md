# 1.1. Base and delta tsconfigs

One shared base config plus per-consumer deltas via `extends`, the `ts-node` object for runner-only options, and `--showConfig` as the argument-ender. Junior read: write flags once, inherit everywhere. Expert read: which layer owns which override, and the exact moment copied configs become a liability.

## 1) One base, deltas per consumer

### 1) **Definition** (the extends chain)

`tsconfig.json` supports `extends`: a child file inherits every field of its base and overrides listed keys. The architecture: one `tsconfig.base.json` holds the project truth (`target`, `module`, `strict`), and each consumer — app, tests, scripts, build — extends it with a delta (its `include`, its runner tweaks, its emit settings). Flags are written once and read many times.

### What problem it solves (history)

Copied configs were the norm: five `tsconfig.json` files with near-identical `compilerOptions`, drifting one field at a time until the test tree typechecked under rules the app tree rejected (or vice versa). Every drift arrived as a mystery ("green here, red there") because no file declared the relationship. `extends` makes the relationship the structure — deltas are visible, bases are single.

### Modern guidance

As of September 2026: one base per repo (or per workspace root), one delta per execution context, deltas limited to what differs (never restate the base). This session's probe shape is the minimal honest form:

```jsonc
// cfg/tsconfig.base.json — the single truth
{ "compilerOptions": { "target": "es2022", "module": "commonjs", "strict": true } }

// cfg/app/tsconfig.json — the delta: scope + runner mode only
{
  "extends": "../tsconfig.base.json",
  "compilerOptions": { "types": [] },
  "ts-node": { "transpileOnly": true }
}
```

### Runnable example (good — the base propagates)

```bash
./node_modules/.bin/ts-node --project cfg/app/tsconfig.json ./cfg/app/run.ts
# extends: delta
```

And the propagation that justifies the pattern — edit *only the base*, re-inspect the app:

```bash
# cfg/tsconfig.base.json: "target": "es2022" → "es2023"
./node_modules/.bin/ts-node --showConfig --project cfg/app/tsconfig.json | grep '"target"'
#     "target": "es2023",
```

Verified: the app's effective config changes with zero app-file edits. One edit, every consumer — that is the entire economic argument for `extends`, demonstrated rather than asserted. (Base restored to `es2022` after the probe; the run above still prints.)

### Runnable example (bad — the copied pair)

```jsonc
// bad: tsconfig.app.json and tsconfig.tests.json, identical today
{ "compilerOptions": { "target": "es2022", "module": "commonjs", "strict": true } }
// six months later: tests bumped target for a lib, app didn't —
// a lib API typechecks in tests, fails in the app. No file records the fork.
```

Why it hurts: drift is silent (no error marks the divergence point), blame is diffuse (which copy is "right"?), and repair requires a human diff of files that were never meant to differ. Fix: delete one copy, `extends` the other — the fork becomes a visible delta or disappears.

### Common confusion

- **"`extends` merges arrays"** — it *replaces* them (`include`, `exclude`, `types` overwrite wholesale; only `compilerOptions` keys merge). The probe delta sets `"types": []` knowing it replaces, not appends — deltas that assume merging inherit nothing and declare confusion.
- **"relative `extends` paths are fragile"** — they resolve relative to the *extending file*, deterministically. Fragility comes from moving files without updating the pointer — caught instantly by `--showConfig` failing to find the base, the loudest possible signal.

### Performance note

Config layering costs one extra file read per process boot (microseconds, once) — against the hours a drifted pair burns per incident. The measurable practice: `tsc --showConfig -p <each-delta>` in CI, diffed against checked-in expectations if you are ambitious, eyeballed if you are not. Minutes per quarter, incidents prevented per year.

### Mentor note

Onboard repos with the propagation demo above: change the base, show every consumer's effective config move. Mentees who watch one edit steer five contexts stop copying configs the same day. Review rule: any new `tsconfig*.json` that duplicates more than three `compilerOptions` keys from a sibling gets an "extends, don't copy" comment.

## 2) The ts-node object inside the config

### 2) **Definition** (runner options where flags cannot reach)

ts-node reads a `"ts-node"` object from the same `tsconfig.json`, using camelCase programmatic names: `transpileOnly`, `files`, `project`, `cwd`, plus a `compilerOptions` sub-object whose entries override the file's own `compilerOptions` *only inside ts-node*. It exists for one reason: CLI flags cannot reach every door (require-hook `-r`, shebangs, loaders), but the config file reaches all of them — verified in [01/1.2](<../../../01 Execution Foundations and Mental Model/sections/1. Execution identity and setup/1.2. Installing and running your first TypeScript file.md>).

### What problem it solves (history)

Before the `ts-node` object, runner behavior split across invocations: the npm script said `--transpile-only`, the debugger config didn't, the shebang couldn't — same sources, three behaviors. Centralizing runner options in the config (the file every door already reads) collapsed the behaviors to one, overridable per delta.

### Modern guidance

Put runner-affecting options in the `ts-node` object (mode, file scope, project path), compiler-affecting options in `compilerOptions`, and ts-node-only compiler *deviations* in `ts-node.compilerOptions` (e.g., the runner tolerates looser `types` while the build stays strict). The probe delta above is the canonical minimal use: `"ts-node": { "transpileOnly": true }` — every door inherits transpile-only without a flag in sight.

### Runnable example (good — the object governs all doors)

```bash
./node_modules/.bin/ts-node --showConfig --project cfg/app/tsconfig.json
# {
#   "ts-node": {
#     "transpileOnly": true,
#     "cwd": "/tmp/tsprobe",
#     "projectSearchDir": "/tmp/tsprobe",
#     "project": "/tmp/tsprobe/cfg/app/tsconfig.json"
#   },
#   "compilerOptions": {
#     "target": "es2022",
#     "module": "commonjs",
#     "strict": true,
#     "types": [],
#     ...plus ts-node-injected run defaults (sourceMap, outDir ./.ts-node)...
```

Verified on ts-node v10.9.2: the object surfaces verbatim (plus resolved paths), base and delta merge beneath it, and injected run defaults append after. Note what `--showConfig` proves beyond the merge: *which project file won* (`projectSearchDir` → `project`) — the scoping question [1.2](<./1.2. Monorepo configs and project scoping.md>) owns.

### Runnable example (bad — flags scattered per door)

```bash
# bad: behavior lives in invocations, config is decorative
"scripts": {
  "dev": "ts-node --transpile-only ./src/server.ts",
  "debug": "ts-node ./src/server.ts",
  "worker": "node -r ts-node/register ./src/worker.ts"
}
# dev skips checks, debug typechecks, worker does whatever the config says —
# three doors, two behaviors, zero files declaring the difference
```

Why it hurts: behavior varies by *how you started the process*, so bug reports must include the exact command line to be reproducible — and the debugger door (which accepts no ts-node flags at all) can never match the CLI door. Fix: `"ts-node": { "transpileOnly": true }` in config, bare commands everywhere.

### Common confusion

- **"`ts-node.compilerOptions` vs `compilerOptions`"** — the former overrides the latter *only under ts-node* (documented use: runner/build divergence from one file). Divergence is a loaded gun: every override is a way the runner disagrees with the build. Prefer zero overrides; justify each survivor in a comment.
- **"the object replaces CLI flags"** — flags still win per-invocation (explicit beats configured). The object sets the default every door shares; flags handle the exception. Defaults in config, exceptions on command lines — never the reverse.

### Performance note

`files: true` (load all `include`d files at boot) trades startup time for global-declaration availability; default lazy-loading trades the reverse. The `--showConfig` output names your setting — if boot is slow and `files` is true, you are paying to parse files the entry never imports. Measure with it on and off (`time` both); keep the faster printout.

### Mentor note

Audit any repo's runner behavior by reading exactly one place: the `ts-node` object. If behavior requires reading `package.json` scripts *plus* launch configs *plus* env vars, the config is decorative and the doors disagree — consolidate first, debug second.

## 3) `--showConfig` ends arguments

### 3) **Definition** (the evidence command)

`ts-node --showConfig` (optionally with `--project`) prints the effective configuration ts-node will use: merged `extends`, resolved paths, the `ts-node` object, and injected run defaults. `tsc --showConfig -p` does the same for the checker. Together they replace every "what config is active?" debate with output.

### What problem it solves (history)

Config disputes were settled by reading files and reasoning about merges — humans simulating `extends` chains, `types` replacement, and override precedence in their heads, usually wrongly (this session's probe output alone contains three surprises: injected `sourceMap`, `outDir ./.ts-node`, resolved `project` path). `--showConfig` moves the merge from heads to stdout, where it can be quoted, diffed, and pasted into bug reports.

### Modern guidance

Run it before theorizing, always: entry misbehaving → `--showConfig --project <it>` first, source second. Require its output in every "ts-node ignores my config" bug report (template it: command + `--showConfig` + `ts-node -vv` versions). Diff it across environments when green-here-red-there strikes (`--showConfig` on laptop vs CI — the divergence is usually `projectSearchDir`, i.e. scoping, i.e. [1.2](<./1.2. Monorepo configs and project scoping.md>)).

### Runnable example (good — evidence over memory)

```bash
./node_modules/.bin/ts-node --showConfig --project cfg/app/tsconfig.json 2>&1 | grep -E '"target"|"transpileOnly"|"project"'
#     "transpileOnly": true,
#     "project": "/tmp/tsprobe/cfg/app/tsconfig.json"
#     "target": "es2022",
```

Three lines settle three disputes: the mode (transpile-only, from the delta's `ts-node` object), the winning file (absolute path — no guessing which config governed), the effective target (merged from base). Verified output, quoted verbatim.

### Runnable example (bad — reasoning about merges unaided)

```bash
# bad: "the app config sets commonjs, so the app runs commonjs"
# (the app config extends a base that sets NodeNext; the delta never
#  mentions module — unaided reasoning picks the wrong winner)
```

Why it hurts: merge precedence (`extends` base loses to delta, `ts-node.compilerOptions` beats both under the runner) is exactly complex enough to defeat memory and exactly simple enough to feel obvious — the worst combination. Every wrong guess costs a debug cycle; `--showConfig` costs a second.

### Common confusion

- **"`--showConfig` shows what tsc uses"** — it shows what *ts-node* uses (note the injected `sourceMap`/`outDir` run defaults — tsc never sees those). Pair it with `tsc --showConfig -p` when the dispute is checker-vs-runner; each tool speaks for itself.
- **"once per repo lifetime"** — the output expires on every config edit, move, upgrade, and environment change. Re-run per incident; automate per pipeline (emit it as a CI artifact on config-touching diffs and half of all "works locally" mysteries become self-solving).

### Performance note

One process boot to print (sub-second, no compilation of user code) — the cheapest diagnostic in this domain by two orders of magnitude. Cost of skipping it: human merge-simulation at engineer rates, usually wrong, always slow.

### Mentor note

Make `--showConfig` output a required field in the team's bug template for *any* ts-node failure (alongside versions from `ts-node -vv`). Mentees graduate from config confusion the week the template lands — evidence habits beat config knowledge, because configs change and the habit doesn't.
