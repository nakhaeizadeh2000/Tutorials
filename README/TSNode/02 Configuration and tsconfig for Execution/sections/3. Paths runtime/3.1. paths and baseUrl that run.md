# 3.1. paths and baseUrl that run

Why `paths`/`baseUrl` aliases typecheck green and crash red — and the two ways to close the gap (bridge the runtime, or erase the need). Junior read: aliases need a runtime half; here are both fixes. Expert read: which fix survives bundlers, workers, and stripping-era Node, priced honestly.

## 1) Checker maps, runtime doesn't

### 1) **Definition** (the two-resolver split)

`paths` + `baseUrl` teach the *checker* (and the editor) to resolve `@app/util` → `src/lib/util` — a compile-time mapping with zero emit. Node's resolver never reads `tsconfig.json` (Amaro ignores it entirely, per Node docs), so at run time `@app/util` resolves as a *bare package specifier* — searched in `node_modules`, not found, `MODULE_NOT_FOUND`. One mapping, two resolvers, only one of them informed.

### What problem it solves (history, inverted — the problem it *creates*)

Aliases were adopted for readability (relative `../../../lib/util` ladders are write-only code), and the checker endorsed them — green CI, clean editor, confident authors. Then execution disagreed: the first aliased import at boot crashed the process. The shape "typechecks but crashes" is the most common TypeScript-on-Node production incident precisely because the green check vouches for code no runner can load.

### Modern guidance

Treat every `paths` entry as *debt with two repayment options* (part 2: bridge; part 3: erase). New services: prefer relative specifiers until aliases earn their keep (three-plus levels of `../` on heavily-shared imports — the readability threshold); adopt aliases with the bridge wired the same commit the first alias lands. Existing alias trees: bridge first (one line), then decide per alias whether the readability still justifies the machinery.

### Runnable example (good — the gap, demonstrated)

```jsonc
// pw/tsconfig.json — checker fully informed
{ "compilerOptions": {
    "target": "es2022", "module": "commonjs", "strict": true,
    "baseUrl": ".", "paths": { "@app/*": ["src/lib/*"] } } }
```

```typescript
// pw/src/main.ts
import { p } from "@app/util";
console.log("pw:", p());
```

```bash
./node_modules/.bin/tsc --noEmit --project pw/tsconfig.json && echo PATHS-CHECK-OK
# PATHS-CHECK-OK

./node_modules/.bin/ts-node --transpile-only --project pw/tsconfig.json ./pw/src/main.ts
# Error: Cannot find module '@app/util'
# Require stack:
# - /tmp/tsprobe/pw/src/main.ts
```

Verified: checker green, hook red — same file, same config, two resolvers. The `Require stack` names the entry (resolution failed *there*, at run time), while the checker stays silent — the signature of every paths incident: green check, red boot, no overlap in the evidence.

### Common confusion

- **"ts-node should honor `paths`"** — ts-node compiles; it does not resolve (resolution is Node's, per [01/3.1](<../../../01 Execution Foundations and Mental Model/sections/3. Loading model/3.1. Loading TypeScript under CJS and ESM.md>)'s resolve-before-compile rule). Expecting the hook to remap specifiers mistakes which pipeline stage owns paths — the mapping must reach the *resolver*, not the *compiler*.
- **"it works in the editor so it runs"** — the editor runs the checker, not the code. Editor-green is evidence about types; boot is evidence about modules. Different evidences, different tools — conflating them is the incident.

### Performance note

The gap has no runtime cost profile (it fails, fast, at first import) — its cost is incident-shaped: green CI invites the alias deeper into the tree before the first execution attempt, so the eventual crash implicates more files. Shrink the blast radius by executing aliased entries *before* merging (the gate from [01/4.1](<../../../01 Execution Foundations and Mental Model/sections/4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>) runs the hook — extend it to aliased entries first).

### Mentor note

Demo the gap live exactly as above (check passes → run crashes) and watch the room: every engineer who has shipped TypeScript recognizes the shape instantly. The lesson that sticks is the sentence "the checker is not the runtime" — repeat it until the team says it back unprompted.

## 2) Bridge with tsconfig-paths

### 2) **Definition** (the runtime-side mapping)

`tsconfig-paths` reads the same `paths`/`baseUrl` and patches Node's resolver at boot (`-r tsconfig-paths/register`), so the runtime maps what the checker maps. One flag on the invocation, zero source changes: the alias keeps its spelling, both resolvers agree, the gap closes mechanically.

### What problem it solves (history)

Before the bridge, teams closed the gap by hand: build-time rewriters, post-emit sed scripts, custom loaders per package — each a private resolver reimplementing `paths` with its own bugs. `tsconfig-paths` standardized the bridge to a single maintained package reading the canonical file: the mapping declared once (tsconfig), honored twice (checker natively, runtime via the hook).

### Modern guidance

Alias trees that must stay aliases: `-r tsconfig-paths/register` on every door that executes them (CLI `-r` flag composes with `-r ts-node/register`: `-r ts-node/register -r tsconfig-paths/register`), pinned as a devDependency, and the combination asserted in the gate (an aliased probe file that must print). Workers/child processes inherit via `NODE_OPTIONS` (both `-r` flags travel in env). Production artifacts: prefer build-time path rewriting (emit already-resolved relatives) over shipping the bridge — artifacts shouldn't resolve at boot what the build could settle.

### Runnable example (good — the one-line fix, verified)

```bash
./node_modules/.bin/ts-node --transpile-only \
  -r tsconfig-paths/register \
  --project pw/tsconfig.json ./pw/src/main.ts
# pw: paths
```

Verified (tsconfig-paths latest, 5 packages added): identical sources, identical config — the resolver now maps `@app/util` → `src/lib/util.ts` before the hook compiles. Checker and runtime agree; the incident class evaporates for this tree.

### Runnable example (bad — the bridge wired in one door only)

```bash
# bad: package.json covers the CLI door, workers spawn bare
"scripts": { "dev": "ts-node -r tsconfig-paths/register ./src/server.ts" }
// src/worker.ts spawns child processes running aliased entries —
// children inherit plain node, no -r flags, MODULE_NOT_FOUND at 3 a.m.
```

Why it hurts: resolver patches are per-process (each `node` needs its own `-r`), so door-by-door wiring leaks exactly where processes multiply (workers, children, test runners spawning servers). Fix: `NODE_OPTIONS="-r ts-node/register -r tsconfig-paths/register"` at the environment level for hook-executed fleets — one declaration, every process — or eliminate the alias (part 3).

### Common confusion

- **"tsconfig-paths slows resolution"** — one mapping lookup per aliased import (hash lookup, microseconds); unaliased specifiers short-circuit untouched. Unmeasurable on any profile that also compiles TypeScript — the bridge is free beside the hook.
- **"the bridge fixes bundlers too"** — bundlers resolve at build time with their own `paths` support (usually native); the bridge targets *hook-executed* code (ts-node, loaders, REPL). Mismatched fix for bundled artifacts — know which pipeline executes before wiring.

### Performance note

Bridge overhead: a `paths`-pattern match per import specifier (regex/microseconds) — invisible against transpile milliseconds. The performance argument for erasure (part 3) is therefore *not* speed but surface: fewer packages, fewer flags, fewer doors to wire. Keep the bridge where aliases earn it; erase where they don't.

### Mentor note

Review rule: any `paths` entry without a wired runtime half (bridge flag, build rewrite, or erasure commit) fails review — the checker alone is half a feature. Ask authors to demonstrate the aliased entry *running*, not merely checking, before approving the alias. The demo takes ten seconds; the incident it prevents takes a night.

## 3) Or erase the need

### 3) **Definition** (aliases as opt-in complexity)

Every alias is machinery: a `paths` entry (checker), a bridge flag (runtime), per-door wiring (workers/env), and a reviewer who must know both halves. Erasure deletes the alias in favor of relative specifiers — zero mapping, zero bridge, both resolvers agreeing trivially because nothing is remapped. The need disappears; the gap disappears with it.

### What problem it solves (history)

Alias adoption outpaced alias justification: trees with two-level depth gained `@app/*` because "clean imports" sounded senior, then paid bridge-wiring on every door forever. Erasure reverses uneconomic adoption — the imports get slightly longer (`../../lib/util`), and an entire failure class plus its wiring leave the repo. Relative specifiers are the default the ecosystem debugs for free.

### Modern guidance

Default to relative; alias by exception with a written threshold (e.g., shared packages imported 3+ levels deep across 5+ consumers — the shape where relatives genuinely rot). Revisit per quarter: aliases whose consumer count shrank get erased back. The day stripping-era Node runs your services, relatives work with zero configuration on every runner — aliases still need their bridge story per runner. Portability favors the boring spelling.

### Runnable example (good — the same program, no machinery)

```typescript
// pw/src/erased.ts — erased: names the file, no mapping anywhere
import { p } from "./lib/util";
console.log("pw:", p());
```

```bash
./node_modules/.bin/tsc --noEmit --project pw/tsconfig.json && echo ERASED-CHECK-OK
# ERASED-CHECK-OK
./node_modules/.bin/ts-node --transpile-only --project pw/tsconfig.json ./pw/src/erased.ts
# pw: paths
```

Verified: both green with the `paths` entry untouched-but-unused (delete it next — dead mapping is worse than none: it invites the next author to use it). No `-r` flag, no extra package, works under `tsx`, stripping, and bare emit identically — runner-portability for free.

### Runnable example (bad — alias theater)

```jsonc
// bad: one alias, one consumer, full machinery
{ "compilerOptions": { "baseUrl": ".", "paths": { "@app/*": ["src/lib/*"] } } }
// a single import uses @app/util — the repo pays checker mapping +
// runtime bridge + door wiring to shorten one specifier by twelve characters
```

Why it hurts: fixed machinery cost against negligible readability gain — and every new door (worker, script, REPL) re-pays the wiring. Fix: erase the alias (relative import), delete the mapping, remove the bridge flag. Machinery should scale with consumers, never precede them.

### Common confusion

- **"relative imports don't scale"** — they scale to any depth; they *uglify* past ~3 levels. Ugliness is a style problem (fixed by moving files closer, the real design smell the ladder exposes); unresolvable aliases are an execution problem. Prefer the style problem — it never pages.
- **"erasure forbids all aliases"** — erasure forbids *unjustified* aliases. Deep shared packages with dozens of consumers justify the machinery (bridge wired once, readability daily). The rule is economic, not aesthetic: machinery ∝ consumers.

### Performance note

Erased imports resolve fastest (direct relative probe, no pattern matching) — though the delta is unmeasurable beside compilation. The real performance win is operational: zero bridge packages in the install graph, zero flags per door, zero alias incidents per year. Boring is fast *to run as a team*.

### Mentor note

Frame the alias debate as budgets, not taste: each alias costs one bridge + N door wirings + permanent reviewer load; it earns readability per consumer. Make authors state the consumer count when proposing an alias — the number usually settles the debate before taste enters. Erasure is the default; aliases are purchases.
