# 1.1. Selecting architectures under constraints

Choosing how TypeScript executes in production — hook, artifact, or native stripping — from constraints (traffic, team, SLOs) instead of habit. Junior read: list the inputs before naming the runner. Expert read: the decision tree that makes boring win, and the ADR that makes the decision replayable.

## 1) Constraints first, runners second

### 1) **Definition** (the inputs-before-outputs rule)

Traffic shape (rps, payload sizes, latency SLO), team size (who operates the pipeline), and platform floor (Node version, container vs serverless) are the *inputs*; the execution strategy — ts-node hook in dev, `tsc` artifact in prod, stripping where the floor allows — is the *output*. Name the inputs in writing; derive the runner from them. Never the reverse.

### What problem it solves (history)

Runner-first teams standardized one executor everywhere (ts-node in prod "for consistency," stripping on a v20 floor "for speed") and met the failure each mismatch owns: per-boot compile variance, healthcheck races, `SyntaxError` on non-erasable syntax at 2 a.m. Constraint-first ordering prevents the mismatch class: the floor disqualifies stripping before anyone depends on it, the SLO disqualifies hook-in-prod before the Dockerfile is written.

### Modern guidance

As of September 2026 (Node.js 24 Active LTS, 22 Maintenance LTS, 26 Current; TypeScript 5.9 stable): decide per environment, not per repo — dev loop runs the hook (fast feedback, [01/2.1](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>)), production runs artifacts (`tsc` emit → `node dist/`, [06/1.2](<../../../06 Shipping Builds Dist and Containers/sections/1. Build configs/1.2. Emit verification.md>)), stripping only where the floor (v22.18.0+) and erasable-only sources both hold ([01/1.1](<../../../01 Execution Foundations and Mental Model/sections/1. Execution identity and setup/1.1. What ts-node is and is not.md>) part 3). Write the three inputs at the top of the design doc; the runner choice falls out.

### Runnable example (good — the arithmetic that sizes the decision)

```bash
node -e "const rps=200, lat=0.25; console.log('coresNeeded:', Math.ceil(rps*lat))"
# coresNeeded: 50
```

Verified this session: 200 rps × 0.25s mean hold = 50 concurrent slots (Little's law) — the input number every runner decision divides by. Fifty slots on burstable single-core containers argues artifacts (zero compile per boot, deterministic bytes); fifty slots on a four-core box argues nothing about runners (capacity is orthogonal — the point: size first, then choose, never choose to avoid sizing).

### Runnable example (bad — runner-first design)

```markdown
# bad: design doc opening line
"We will run ts-node in production for consistency with development."
```

Why it hurts: consistency of *command* purchased with inconsistency of *guarantees* (per-boot compile, per-machine variance, toolchain in the image — [01/4.1](<../../../01 Execution Foundations and Mental Model/sections/4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>) part 2 priced all three). Fix: open with constraints (traffic, SLO, floor, team) and let the tree below decide — consistency belongs at the config base ([02/1.1](<../../../02 Configuration and tsconfig for Execution/sections/1. Config architecture/1.1. Base and delta tsconfigs.md>)), not the production entrypoint.

### Common confusion

- **"one runner simplifies operations"** — one runner per *environment* simplifies (dev hook, prod artifact — each optimal, each pinned); one runner across environments complicates (dev pays prod's ceremony or prod pays dev's variance). Uniformity is a property of contracts (same config base, same gates), not of binaries.
- **"serverless changes the answer"** — serverless sharpens the inputs (cold-start SLO dominates, per-invocation billing) and the tree still decides (artifacts or bundled emit — never the hook; cold compile per invocation is the slowest possible start). Different inputs, same method — constraints first, always.

### Performance note

Architecture performance is decided here (hook-per-boot vs zero-compile changes fleet cold-start by seconds × replicas × restarts — [06/5.1](<../../../06 Shipping Builds Dist and Containers/sections/5. Interview questions and answers/5.1. Common interview QA shipping.md>) part 1 priced it). Measure the chosen shape once chosen (`time` cold boot on the artifact, healthcheck latency at scale-up); keep the numbers with the ADR (part 3) — decisions without numbers decay into folklore by the next quarter.

### Mentor note

Reject design docs that open with the runner choice ("we use X") and demand the constraints section first ("traffic T, SLO S, floor F, team N — therefore X"). Two review cycles of this and teams self-correct permanently — the document structure teaches the thinking order better than any lecture on architecture.

## 2) Boring wins ties

### 2) **Definition** (the novelty budget)

Between two architectures meeting the SLOs, choose the one with fewer moving parts (no custom loader where `tsconfig-paths` suffices, no transformer where erasure suffices, no new runner where the current one measures fine). Novelty is budgeted: each exotic component must justify its existence against the boring alternative with numbers, and the budget resets per decision — never "we already have three custom pieces, one more is free."

### What problem it solves (history)

Resume-driven architecture (custom hooks for mappable aliases, SWC before measuring transpile-only, ESM migration for a CJS service with no ESM consumers) accumulated failure modes no incident ever needed: loader-order mysteries, engine-map divergences, interop traps — each adopted for elegance, each paid in on-call hours. Boring-wins converts elegance from default to defendant: justify or remove.

### Modern guidance

Count moving parts per proposal (runners, hooks, transformers, bridges, custom resolvers — list them); challenge each with "what breaks if we delete it?" (nothing measurable → delete); spend novelty only where boring demonstrably fails (measured gap, not theorized elegance — the SWC rule from [01/2.1](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>): adopt on numbers, never on fashion). Re-audit yearly (boring alternatives improve — stripping matured across Node 22→24 and retired whole hook setups legitimately).

### Runnable example (good — the deletion test, applied)

```markdown
# proposal: custom resolve hook for @app/* (3 aliases, one team, CJS service)
# deletion test: replace with relative imports (erasure per [02/3.1])
# result: hook file, order pin, trace wiring, gate stages — all deleted; suite green
# verdict: boring wins — recipe kept documented ([03/3.1]) for the day aliases earn it
```

```markdown
# bad: novelty retained without measurement
"Keep the SWC transpiler — it's faster." (transpile-only bounce: 0.4s; SWC: 0.2s;
# nobody measured, nobody felt 0.2s, native dep in the lockfile forever)
```

Why it hurts: unmeasured novelty compounds (each exotic piece interacts with every future piece — loader × transformer × bridge failure surfaces multiply, debuggability divides). Fix: the deletion test per component, yearly — architecture as gardening (prune or justify), never as monument.

### Common confusion

- **"boring means outdated"** — boring means *fewest parts meeting SLOs with margin* (a 2026 boring stack: erasable sources, transpile-only dev, `tsc` artifacts, Node 24 — thoroughly modern, zero exotic). Outdated means failing SLOs or drowning in toil — different axis entirely. Conflating them lets novelty pose as progress.
- **"budgeting novelty slows innovation"** — budgeting *directs* it (spend where boring demonstrably fails — the constraint that earns the experiment gets the experiment). Undirected novelty spends everywhere and learns nowhere (no measurement, no comparison). Budgets accelerate learning by forcing comparison.

### Performance note

Boring architectures profile cleanly (fewer layers between symptom and cause — mapped traces, standard flames, no hook-thread attribution puzzles). Exotic pieces each add diagnostic surface (loader order? transformer divergence? bridge staleness?) — triage time grows with part count even when steady-state performance ties. Boring is operational performance wearing a simplicity costume.

### Mentor note

Keep a team novelty ledger (component, justification, measurement, review date — one table): additions append rows, yearly reviews prune them. Mentees proposing additions learn to argue in ledger terms (numbers, not adjectives); reviewers gain a memory longer than the quarter. Ledgers turn taste into governance without bureaucracy.

## 3) Decisions recorded

### 3) **Definition** (the ADR habit)

Architecture Decision Records: one short document per crossroads — context (constraints at decision time), options (with prices), verdict (what and why), review date (when to re-examine). Stored beside the code (``docs/adr/``), linked from the configs they govern, re-read on every relevant change. Judgment replayable by strangers, years later.

### What problem it solves (history)

Oral-tradition architecture ("we tried stripping once, it broke something") decayed into superstition (prohibitions nobody could explain, preferences nobody could defend) — new engineers either obeyed blindly (boring calcified into outdated) or violated blindly (relearning old incidents at full price). ADRs convert tradition into evidence: the breakage named, the context dated, the re-examination scheduled.

### Modern guidance

Write ADRs for runner choices, mode defaults, restarter picks, hook adoptions, map-shipping policies, and image strategies (every judgment in domains 01–06 that could surprise a newcomer); review on schedule (dates fire — re-examine with fresh numbers, keep or reverse explicitly); link from code (tsconfig comments, Dockerfile comments, script comments point at the ADR — decisions discoverable where they're questioned).

### Runnable example (good — the ADR skeleton, filled)

```markdown
# ADR-004: Production runs tsc artifacts, not ts-node (2026-09-24)
# Context: 200 rps, p99 250ms SLO, Node 24 floor, team of 5.
# Options: (a) ts-node transpile-only in prod — 0.4s/boot variance, toolchain image;
#   (b) tsc emit + node dist/ — ~0.05s boot, deterministic bytes; (c) stripping — floor
#   allows but 3 enums remain (migration pending, ADR-005).
# Verdict: (b) — numbers in [01/2.1], image proof in [06/2.2], gate6 enforces.
# Review: 2027-03 (re-examine stripping post enum-migration).
```

### Runnable example (bad — the unrecorded reversal)

```markdown
# bad: silent migration (no ADR, no date, no prices)
# commit: "switch prod to tsx for speed" — boot delta unmeasured, map pipeline
# unverified, gate stages still asserting ts-node traces. Green CI, blind prod.
```

Why it hurts: unverdictable change (no context to review, no numbers to compare, no date to revisit — the team can't distinguish improvement from drift), gate skew (assertions proving the old shape pass vacuously or fail confusingly), and re-incident risk (the old decision's reasons unknown, its failure modes re-enter unopposed). Fix: revert-or-record (revert now, or write the ADR with numbers and re-land).

### Common confusion

- **"ADRs are bureaucracy"** — bureaucracy is process without payoff; ADRs pay at every onboarding (read, don't interview), every incident (context in minutes), every revisit (numbers to compare). Five-paragraph documents with expiration dates — the lightest governance that works.
- **"code comments suffice"** — comments explain *what/why locally* (one flag, one line); ADRs explain *what/why globally* (system direction, rejected alternatives, review schedule). Comments point at ADRs; ADRs don't fit in comments. Both, layered — never either/or.

### Performance note

ADR cost: thirty minutes to write, ten to review, five per revisit — against re-decision costs (hours per re-litigation) and re-incident costs (full price per repeated mistake). The cheapest architectural performance practice: decide once, record, revisit on schedule instead of on fire.

### Mentor note

Require an ADR with every architecture PR (no record, no merge — the rule that builds the habit in a quarter). Review ADRs, not just code: context complete? options priced? verdict falsifiable? date set? Mentees writing their first three ADRs learn judgment faster than a year of implementation — deciding explicitly is the skill.
