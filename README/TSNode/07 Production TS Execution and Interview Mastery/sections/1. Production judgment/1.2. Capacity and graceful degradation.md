# 1.2. Capacity and graceful degradation

Sizing TypeScript services from numbers and shedding load gracefully when numbers are exceeded. Junior read: multiply before provisioning; degrade before collapsing. Expert read: where compile cost enters capacity math, and why limits are designed, not discovered.

## 1) Capacity from numbers

### 1) **Definition** (budgets × traffic = resources)

Per-request budgets (CPU ms, memory MB, connection hold time) multiplied by traffic (rps, concurrency) derive cores, memory, and connection pools — with explicit headroom (N+1 instances minimum, burst margin per SLO). TS-specific inputs: cold-start seconds per boot (hook vs artifact — the ladder from [01/2.1](<../../../01 Execution Foundations and Mental Model/sections/2. Modes and configuration/2.1. Transpile-only versus full typechecking.md>)) feeding scale-up latency, and checker-off-boot proving steady-state costs exclude compilation.

### What problem it solves (history)

Vibes-based provisioning ("three replicas should do it" — for every service, every load) produced twin failures: idle over-provision (money burned quietly) and cliff under-provision (noon traffic collapsing a service sized for midnight — the incident [5.1](<../5. Interview questions and answers/5.1. Common interview QA judgment synthesis.md>) rehearses). Arithmetic replaces vibes: slots from Little's law, instances from slots-per-box, memory from measured RSS plus headroom.

### Modern guidance

Size per service (budgets measured on the artifact — never the hook; hook boots cost more and vary — capacity math on hook numbers provisions variance, not capacity); headroom explicit (burst factor × N+1 — written in the ADR from [1.1](<./1.1. Selecting architectures under constraints.md>), reviewed with traffic deltas); re-size on evidence (profile deltas, traffic growth, emit changes — numbers expire, re-measure per quarter).

### Runnable example (good — the sizing arithmetic, verified)

```bash
node -e "const rps=500, p99=0.2, mem=256; const slots=Math.ceil(rps*p99); console.log('slots:', slots, '| instances(50 slots each):', Math.ceil(slots/50), '| mem/instance MB:', mem);"
# slots: 100 | instances(50 slots each): 2 | mem/instance MB: 256
```

Verified this session: 500 rps × 0.2s hold = 100 concurrent slots → 2 instances at 50 slots each (+1 headroom = 3 deployed). Memory per instance measured from artifact RSS (never hook boot — hook compile inflates RSS transiently; provision steady-state, alarm the transient).

### Runnable example (bad — vibes provisioning)

```markdown
# bad: capacity section of the design doc, complete
"Replicas: 3 (standard)."
```

Why it hurts: unpriced capacity can't be reviewed (is 3 enough? too many? — unanswerable), can't be alarmed (no thresholds derived — alerts fire on symptoms, never on approach), and can't scale (traffic doubles — double what?). Fix: the arithmetic above, three lines, every number sourced (budgets measured, traffic projected, headroom explicit).

### Common confusion

- **"autoscaling replaces sizing"** — autoscaling reacts to thresholds sizing defines (target CPU/concurrency/latency — all derived from budgets) with scale-up latency sizing must cover (cold starts × instance count — artifact boots measured, hook boots disqualifying). Unsized autoscaling oscillates (thrashing on noise) or lags (cold starts exceeding SLO before warm). Size first, scale second — autoscalers execute arithmetic, they don't invent it.
- **"load tests give capacity"** — load tests *validate* arithmetic (confirm slots, find the real bottleneck — usually downstream, not compute) — they don't replace it (untargeted load-testing without expected numbers produces graphs without verdicts). Predict (arithmetic), then test (confirm or learn), never test blind.

### Performance note

Capacity math costs one profiling session per service per quarter (budgets measured under representative load — the [05/2.2](<../../../05 Debugging Sourcemaps and Profiling TypeScript/sections/2. Inspector and profiles/2.2. CPU and memory profiles of TS services.md>) discipline applied) against continuous over-provision (money) or cliff incidents (downtime). The highest-ROI arithmetic in operations: three lines preventing both tails.

### Mentor note

Demand the three numbers (slots, instances+headroom, mem) in every production-readiness review — no numbers, no launch. Mentees learn capacity thinking fastest by sizing their own dev service first (small numbers, same method): predict, deploy, watch the dashboards confirm. Arithmetic habit formed small transfers large.

## 2) Degrade by layers

### 2) **Definition** (graceful-worse over failed-best)

Overload sheds in layers: timeouts bound waits (no unbounded holds), caches absorb repeats (stale-while-revalidate beats origin collapse), static fallbacks serve last (degraded content beats errors), queues buffer bursts (backpressure per [NodeJS 01](<../../../../NodeJS/01 Runtime Fundamentals and Mental Model/README.md>) pool mechanics — linked, not restated). Each layer sacrifices quality to preserve availability — in that order, by design, tested per layer.

### What problem it solves (history)

All-or-nothing services (full fidelity or 500s — no middle gears) collapsed completely under partial overload (one slow dependency → queued exhaustion → total outage — the incident with the steepest regret gradient: 90% servable, 0% served). Layered degradation converts cliffs into slopes: worse answers, sustained availability, recovery without restart.

### Modern guidance

Timeout every outbound hop (p99 × small factor — never unbounded; TS `AbortSignal.timeout` per call); cache the repeatable (routes, configs, typecheck-adjacent metadata — stale briefly beats absent totally); serve static fallbacks (health, landing, cached pages — last gear, always available); queue with bounds (finite queues + defined overflow — drop or degrade explicitly, never grow unboundedly). Test each layer by fault injection (slow dependency, dead cache, full queue — per layer, per quarter).

### Runnable example (good — the layer table, priced)

```markdown
# degradation layers (outermost sheds first):
# L1 timeouts: upstream p99 200ms → timeout 600ms (3× — transient-tolerant, outage-bounded)
# L2 cache: 60s TTL on hot routes → origin survives cache-death for minutes, not seconds
# L3 static: /health + landing static → always 200, even with everything downstream dark
# L4 bounded queues: 1000 deep, overflow → 429 + Retry-After (explicit, client-actionable)
```

```markdown
# bad: unbounded everything (the default that collapses)
# no timeouts (waits forever) + no cache (origin per request) + no fallback (500s) +
# unbounded queue (memory grows until OOM-kill). Four absences, one outage shape.
```

Why it hurts: unbounded systems fail *maximally* (every resource exhausts simultaneously — no partial survival, no fast recovery, restart required). Each missing layer converts a slope back into a cliff; all four missing guarantees the cliff. Fix: layers outermost-first (timeouts today — cheapest, highest leverage — then inward).

### Common confusion

- **"degradation means worse code"** — degradation means *designed* worse-behavior (explicit fallback paths, tested, documented — engineering); collapse means *undesigned* worse-behavior (500s, timeouts, OOMs — accident). Designed-worse preserves trust (status page: "degraded, recovering"); accidental-worse destroys it. The difference is intention, tested.
- **"timeouts cause failures"** — timeouts *convert* unbounded waits (cascading) into bounded errors (retryable, countable, alarmable). A timed-out hop is a known state with a known remedy (retry/fallback/shed); a hung hop is an unknown state consuming a slot forever. Timeouts manufacture failure visibility — visibility is the prerequisite of grace.

### Performance note

Degradation layers cost steady-state little (timeout timers, cache memory, fallback bytes — all measured in single-digit percent) and overload everything (availability sustained at 10× the cliff load — the curve flattens instead of falling). Load-test the layers (fault injection per layer — the only honest measurement; untested fallbacks are wishes, not gears).

### Mentor note

Game-day per layer (kill the cache, slow the upstream, flood the queue — observe the gear engage): teams that watched degradation work trust it under pager pressure; teams that merely configured it bypass it ("just restart" — the cliff reflex). One game-day per layer per year sustains the trust; skipped years quietly return the team to cliff-shaped instincts.

## 3) Limits everywhere, discovers nowhere

### 3) **Definition** (bounded-by-design resources)

Every resource carries an explicit bound: request bodies (capped per [NodeJS 04](<../../../../NodeJS/04 Events Networking and HTTP/README.md>) bare-server discipline — linked), queues (finite with overflow policy), caches (TTL + max entries), connections (pool caps), event listeners (budgets per [NodeJS 04](<../../../../NodeJS/04 Events Networking and HTTP/README.md>)), hook chains (finite links). Exhaustion is a designed state (429/503 + remedy headers) — never a discovery (OOM, EMFILE, hang).

### What problem it solves (history)

Unbounded-resource incidents (uncapped upload → OOM, unbounded listener growth → warning-then-leak, infinite retry → self-DDoS) share one trait: the limit was discovered in production at 3 a.m. instead of designed in review at 3 p.m. Bounds convert discoveries into rejections (cheap, countable, alarmable) — the cheapest reliability transformation available: one constant per resource.

### Modern guidance

Bound per resource (body bytes, queue depth, cache entries/TTL, pool size, retry count with backoff caps, payload sizes); overflow explicitly (429 + `Retry-After` for rate, 503 for unavailable, drop-oldest/newest per queue semantics — documented per endpoint); alarm on approach (80% thresholds — pages before cliffs, never at them). Review new code for unbounded growth (arrays appended per request, maps keyed per user, listeners per connection — the three unbounded shapes, challenged on sight).

### Runnable example (good — the bounds list, auditable)

```markdown
# resource bounds (audited per review):
# body: 1MB cap (413 beyond) — per [NodeJS 04] trio discipline
# queue: 1000 deep → 429 + Retry-After: 30 on overflow
# cache: 10k entries, 60s TTL — bounded memory, fresh enough
# listeners: ≤20 per emitter (budget from [NodeJS 04]) — growth beyond is a leak ticket
# retries: 3, backoff capped at 5s — no retry storms, ever
```

### Runnable example (bad — the unbounded service)

```javascript
// bad: three unbounded shapes in twelve lines
const seen = [];                    // grows per request, forever (leak by design)
emitter.on("data", handler);        // per-connection, never removed (leak by pattern)
await fetch(url);                   // no timeout, no retry cap (hang + storm by default)
```

Why it hurts: each unbounded shape is a timed incident (memory, handles, slots — exhaustion scheduled, date TBD). Combined, they guarantee the 3 a.m. page and maximize its blast radius (all resources exhausting together — the maximally-correlated failure). Fix: bound each (cap, remove, timeout) — three lines, three incidents prepaid.

### Common confusion

- **"bounds reject legitimate traffic"** — bounds reject *unbounded* traffic (the 1GB upload, the 1M-deep queue — never legitimate at those magnitudes); legitimate peaks fit designed bounds with headroom (part 1's arithmetic sizes the bounds). Rejected-at-bound traffic gets actionable errors (429/413 + remedies); accepted-beyond-bound traffic gets collapse. Bounds protect legitimacy by shedding excess.
- **"Node handles backpressure automatically"** — streams exert backpressure *when used as streams* (piped, paused, drained — [NodeJS 03](<../../../../NodeJS/03 Files Streams and Buffers/README.md>) owns the mechanics); buffered-everything code opts out (accumulate-then-process has no pressure signal — unbounded by construction). Bounds are the application-level backpressure for non-stream paths — design them wherever streams don't flow.

### Performance note

Bounds cost nothing steady-state (comparisons per operation — noise) and cap worst-case everything (memory, handles, latency tails — the p99 story is a bounds story: unbounded queues *are* tail latency). Tail-latency work without bounds review optimizes the servable while the unservable grows — bound first, optimize second.

### Mentor note

The unbounded-shape hunt makes excellent review training (three shapes, twelve lines, find them all): mentees completing it review production code with bounds-eyes permanently. Add the shapes to the review checklist ([2.1](<../2. Review and design/2.1. Reviewing Node+TS code.md>) part 1 carries them as gate items) — checklist beats memory, again.
