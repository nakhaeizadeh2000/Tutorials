# 5.1. Common interview QA: judgment and synthesis

Canonical answers for the three capstone questions every senior TypeScript-on-Node interview asks, plus rapid-fire drills across all seven domains. Junior read: memorize the narrations. Expert read: each answer synthesizes verified receipts from 01–06 — systems, incidents, and teaching, priced and standarded throughout.

## 1) Design a TS service, execution edition

### 1) **Definition** (the systems screen)

"Design a TypeScript service handling 500 rps with p99 250ms" — screens for constraint-first execution design: hires open with inputs (traffic, SLO, floor, team — [1.1](<../1. Production judgment/1.1. Selecting architectures under constraints.md>)), size from arithmetic (100 slots → 3 instances — [1.2](<../1. Production judgment/1.2. Capacity and graceful degradation.md>)), choose runners per environment (hook dev, artifact prod), wire configs/loaders/maps/gates per domain, and close with the ADR shape (verdict + numbers + review date).

### What problem it solves (hiring signal)

Systems answers reveal architectural judgment wholesale (constraints handled? capacity priced? failure designed? observability shipped?) — the single highest-signal interview hour available. Candidates narrating end-to-end with numbers predict production ownership; candidates reciting components predict integration tickets. The screen hires owners, not assemblers.

### Modern guidance

Answer as a walk: constraints → capacity → runners → configs → loaders → loops → maps → artifacts → gates → ADRs (seven domains in traversal order — the [3.1](<../3. Full-system synthesis/3.1. One request every layer.md>) narration applied to a green field). Quote receipts per choice (ladder numbers, sizing arithmetic, gate stages — all verified this track); name the boring alternative rejected per exotic kept (novelty budgeted — [1.1](<../1. Production judgment/1.1. Selecting architectures under constraints.md>) part 2); close with review posture (gates-first, priced, failure-approved — [2.1](<../2. Review and design/2.1. Reviewing Node+TS code.md>)).

### Runnable example (good — the answer skeleton, filled)

```markdown
# "500 rps, p99 250ms, Node 24 floor, team of 5, TS service"
# constraints: 100 slots → 3 instances (2+1), 256MB RSS each ([1.2] arithmetic, verified)
# runners: transpile-only dev (0.4s bounces), tsc artifacts prod (~0.05s boot, deterministic)
# configs: base + build/test deltas, TS_NODE_PROJECT per entry ([02])
# loaders: none custom (erased aliases — boring wins; recipe documented if needed)
# loops: node --watch dev, node --test suites, launch.json debug ([04])
# maps: bundled inline dev, co-shipped file maps + flag prod ([05])
# artifacts: dist + maps, multi-stage image 245MB-class, USER node ([06])
# gates: 1–7 green blocking merge; ADR-004 records this with review date ([1.1])
```

A hire narrates this in five minutes with numbers; the interviewer hears seven domains compiled into one decision. Follow-up ("traffic 10×s overnight?"): capacity arithmetic re-run (1000 slots → instances + headroom), degradation layers engaged ([1.2](<../1. Production judgment/1.2. Capacity and graceful degradation.md>) part 2), autoscale thresholds from budgets — scaling as arithmetic, not panic.

### Common confusion (in candidates)

- **"starts with the framework"** — red flag: framework choice is application architecture (their tracks); execution design is runtime architecture (this track). Starting with Express/Fastify answers a different interview — redirect kindly ("frameworks aside — how does the TypeScript execute here?").
- **"one environment, one runner"** — yellow flag: dev/prod runner split is the track's load-bearing judgment ([01/4.1](<../../../01 Execution Foundations and Mental Model/sections/4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>)). Single-runner answers get the ladder quoted back at them ("price hook-in-prod cold starts at 500 rps, then we'll talk").

### Performance note

Design answers need numbers (slots, boots, bytes, budgets — quoted above, re-derived per scenario); ranges beat points ("50–100 slots" honest vs "exactly 73" fabricated); sources beat memory ("S1 ladder" cited vs "I recall"). Numbers volunteered with provenance outscore numbers recited; humility about variance outscores false precision.

### Mentor note

Mock the systems question monthly (new constraints each time — traffic shapes, floors, teams varied): mentees graduate when every answer opens with inputs, prices every choice, and closes with an ADR shape — five minutes, no tooling, pure judgment. The mock doubles as architecture training (constraints-first thinking transfers to every design review).

## 2) "Your TS service falls over at noon" — debug it live

### 2) **Definition** (the incident screen)

"Traffic spikes, p99 blows, errors climb — walk me through it" — screens for staged triage under pressure: hires execute [05/3.1](<../../../05 Debugging Sourcemaps and Profiling TypeScript/sections/3. Production triage/3.1. Triage order for TS services.md>) live (logs: first authored frame; profiles: widest box; hooks: only with loading evidence), announce pivots ("stacks untrusted — maps first"), and close with receipts (profile delta, gate green, ADR updated). Random-layer responders fail; staged responders pass before the fix lands.

### What problem it solves (hiring signal)

Incident response is the least trainable-on-the-job skill that matters most at 3 a.m. (everyone learns eventually; the team pays tuition per incident until they do). Simulated incidents measure the pre-trained state: staged evidence-gathering, pivot discipline, receipt-backed fixes — the exact behaviors correlating with short MTTR in production postmortems.

### Modern guidance

Answer in stages with narration ("first I'd capture the mapped stack — first authored frame is suspect one; unmapped → pivot to maps before theorizing…"), profile the hot path on hypothesis (never blind — [05/2.2](<../../../05 Debugging Sourcemaps and Profiling TypeScript/sections/2. Inspector and profiles/2.2. CPU and memory profiles of TS services.md>) discipline quoted), fix shapes not symptoms (monomorphic, bounded, degraded — [1.2](<../1. Production judgment/1.2. Capacity and graceful degradation.md>) layers engaged), and close the loop (receipt profile, gate green, runbook updated — incidents prepaid going forward).

### Runnable example (good — the staged narration, compressed)

```markdown
# "noon spike, p99 4s (SLO 250ms), 5xx climbing"
# stage 1 (logs): mapped stack → first authored frame: payment route awaiting unbounded upstream (no timeout — [1.2] violation named in seconds)
# stage 2 (profiles): --cpu-prof on the route → widest box: await queue, slots exhausted (capacity math confirms: 100 slots, 400 queued)
# stage 3 (hooks): no loading evidence (traces present, maps green) → skipped correctly
# fix: 600ms timeout + bounded queue (1000, 429 beyond) + cache on hot route → p99 180ms (receipt profile attached)
# close: bounds added to review gates, ADR updated, game-day scheduled for the layer
```

### Common confusion (in candidates)

- **"scale up first"** — yellow flag as a *first* move: scaling buys headroom (valid mitigation — do it in parallel via autoscale/runbook) but diagnoses nothing (root cause unaddressed — the spike returns with the bill). Strong candidates mitigate *and* diagnose concurrently (scale to survive, stage to understand — two tracks, stated explicitly).
- **"restart the service"** — red flag as diagnosis: restarts clear evidence (profiles lost, stacks gone, queues drained — the crime scene cleaned before forensics). Restart to *mitigate* (documented, timestamped); never to *investigate* (evidence first — logs captured, profiles taken, then restart if needed).

### Performance note

Incident answers need the receipt habit (before/after profiles quoted — "p99 4s → 180ms, flame attached" — falsifiable, transferable); postmortem quality predicted by staging discipline (staged responders write timelines with evidence per stage; random responders write narratives with conclusions per hunch). Hire the stagers; train the rest with game-days ([4.1](<../4. Important points to remember/4.1. Mastery checklist habits mentors insist on.md>) part 2's rehearsal).

### Mentor note

Run live-fire mocks (broken service, candidate screensharing, narrate-while-diagnosing): score staging (logs→profiles→hooks order held?), pivots (unmapped announced?), receipts (fix evidenced?). Graduates hold order under simulated pressure; near-misses layer-hop (coach with the game-day prescription — [4.1](<../4. Important points to remember/4.1. Mastery checklist habits mentors insist on.md>) part 2). Pressure reveals training; training removes pressure.

## 3) Teach ts-node in five minutes (plus rapid-fire)

### 3) **Definition** (the mentoring screen)

"Teach me ts-node — five minutes, whiteboard" — screens for compiled, transferable understanding: hires narrate hook-not-runtime (one demo: prints under ts-node, throws under node), modes (full gates/TTS2322, transpile-only runs — one file, both commands), config (one tsconfig, `--showConfig` proof), and close with the boundary (artifacts in prod — one sentence). Five minutes, three demos, zero jargon unexplained — teaching *is* the mastery proof ([4.1](<../4. Important points to remember/4.1. Mastery checklist habits mentors insist on.md>) part 3).

### What problem it solves (hiring signal)

Senior hires teach constantly (onboarding, reviews, incidents — knowledge transfer is the job above a level); teaching skill predicts multiplier impact directly (narrators grow teams; hoarders bottleneck them). The five-minute lesson compresses pedagogy into an observable: structure (simple→deep), evidence (demos, not claims), responsiveness (questions routed, not deflected).

### Modern guidance

Teach in traversal order (hook → modes → config → boundary — the [3.1](<../3. Full-system synthesis/3.1. One request every layer.md>) narration compressed to four beats); demo per beat (prints/throws, gates/runs, `--showConfig`, ladder — every claim witnessed); invite interruption (questions routed to domains — "great question — that's [03]'s loader order, thirty seconds?" — responsiveness scored). Close with the one sentence that matters ("TypeScript executes via hooks in dev, artifacts in prod — everything else is configuration of that split").

### Runnable example (good — the four-beat lesson, timed)

```markdown
# beat 1 (hook, 1 min): ts-node hello.ts prints / node hello.ts throws — the hook, witnessed
# beat 2 (modes, 1 min): loose.ts gates full / runs transpile-only — error timing, not safety
# beat 3 (config, 1 min): --showConfig names the winner — evidence over memory
# beat 4 (boundary, 1 min): tsc + node dist/ — production runs artifacts (ladder quoted)
# close (1 min): questions — each routed to its domain, live
```

All four demos verified across S1–S6 (prints, gates, receipts, ladders — this track's probe corpus). A hire teaching this cold demonstrates retention; the interviewer learns ts-node *and* evaluates simultaneously — the lesson is the assessment.

### Rapid-fire drills (with answers — all seven domains)

1. **Hook vs runtime in one sentence?** Hook compiles at import, V8 runs the output ([01/1.1](<../../../01 Execution Foundations and Mental Model/sections/1. Execution identity and setup/1.1. What ts-node is and is not.md>)).
2. **`TS5109` on boot — fix?** Complete the pair (`moduleResolution: NodeNext` — [02/2.1](<../../../02 Configuration and tsconfig for Execution/sections/2. Module pairs and specifiers/2.1. The module pair matrix for execution.md>)).
3. **Reversed loader flags break — why?** Eager link consumes first; mapper must run first — list compiler first ([03/1.1](<../../../03 ESM CJS and Loader Hooks Deep Dive/sections/1. Hook pipeline/1.1. resolve and load the two-stage pipeline.md>)).
4. **Nodemon ignores `.ts` — fix?** `-e ts,json` (extension watchlist — receipt line proves it) ([04/1.2](<../../../04 Development Workflow Watch REPL and Editors/sections/1. Watch and restart/1.2. Nodemon and restarter discipline compared.md>)).
5. **Trace names `dist/` lines in prod — fix?** Co-ship maps + `--enable-source-maps` (artifact parity) ([05/3.1](<../../../05 Debugging Sourcemaps and Profiling TypeScript/sections/3. Production triage/3.1. Triage order for TS services.md>)).
6. **Start script runs ts-node — verdict?** Finding (stage 70 — flip to `node dist/`) ([06/4.1](<../../../06 Shipping Builds Dist and Containers/sections/4. Important points to remember/4.1. Shipping checklist habits mentors insist on.md>)).
7. **Capacity for 500 rps × 0.2s — answer?** 100 slots → 3 instances (2+1) ([1.2](<../1. Production judgment/1.2. Capacity and graceful degradation.md>) — verified arithmetic).

### Common confusion (in candidates)

- **"teaching means covering everything"** — teaching means *routing* everything (four beats live, every question routed to its domain — coverage via pointers, not recitation). Completists run overtime listing flags; teachers finish early with questions answered. Brevity with pointers outscores exhaustive recitation.
- **"rapid-fire tests trivia"** — rapid-fire tests *compiled judgment* (ten seconds permits retrieval, never derivation — answers present iff the model is compiled). Trivia fails under follow-up ("why?" breaks reciters); judgment survives it (every drill above routes to a leaf with the full story). Drill, then probe — the pair separates cleanly.

### Performance note

Teaching answers need timing (four beats, five minutes — pace evidenced); rapid-fire needs instantaneity (ten seconds per drill — retrieval, not reasoning). Candidates managing the clock unprompted signal seniority more reliably than any single answer (time-awareness is the meta-skill: paced lessons, snappy drills, conversational follow-ups).

### Mentor note

The five-minute lesson is the onboarding gift every senior owes (record once, replay per hire — then live-teach quarterly to keep it sharp). Timed rapid-fire runs the quarterly health-check (seven drills, seventy seconds, team-wide gaps surfaced). Teaching infrastructure compounds: lessons recorded, drills repeated, gaps closed — mastery scaled beyond individuals.
