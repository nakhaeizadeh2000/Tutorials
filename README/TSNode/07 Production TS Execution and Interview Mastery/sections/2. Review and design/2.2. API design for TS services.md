# 2.2. API design for TS services

Designing service boundaries in TypeScript: explicit contracts, types that serve consumers, and failures naming remedies. Junior read: envelope every response, type every boundary. Expert read: where erasable-only sources meet API evolution, and why remedy-bearing errors cut support load measurably.

## 1) Contracts explicit

### 1) **Definition** (the boundary promise)

Every endpoint declares statuses (2xx/4xx/5xx per outcome), shapes (request/response schemas — typed, validated at runtime), errors (codes, not just messages), versioning (path or header — planned before v2), and breaking-change policy (announced, migrated, then removed). The contract is written (OpenAPI or equivalent), reviewed (like code), and tested (contract tests asserting shapes — not just status 200).

### What problem it solves (history)

Implicit contracts (200-with-error-body, shape-by-example, version-by-surprise) coupled every consumer to implementation accidents: a renamed field breaking three clients, an undocumented 429 crashing a retry-less caller, a "minor" change paging integrators. Explicit contracts convert integration from archaeology (read the handler, guess the shape) to engineering (read the spec, code to it, test against it).

### Modern guidance

Envelope responses uniformly (`{ ok, data } | { ok: false, error: { code, remedy } }` — verified below); validate at runtime (schemas enforced at the boundary — types erase, validators persist: the type-vs-validation split from TS 02, linked); version explicitly (never rename/remove without a version bump + migration window); document remedies per error (part 3's rule, previewed here).

### Runnable example (good — the envelope, verified)

```typescript
// api.ts — uniform envelope, erasable-only (runs under every runner)
type Envelope<T> = { ok: true; data: T } | { ok: false; error: { code: string; remedy: string } };
function ok<T>(data: T): Envelope<T> { return { ok: true, data }; }
function fail(code: string, remedy: string): Envelope<never> { return { ok: false, error: { code, remedy } }; }
console.log(JSON.stringify(ok({ id: 7 })));
console.log(JSON.stringify(fail("RATE_LIMITED", "Retry after 30s")));
```

```bash
./node_modules/.bin/ts-node --transpile-only api.ts
# {"ok":true,"data":{"id":7}}
# {"ok":false,"error":{"code":"RATE_LIMITED","remedy":"Retry after 30s"}}
```

Verified this session (ts-node v10.9.2): success and failure share one shape (clients branch on `ok`, never on status-text-sniffing); errors carry machine-readable codes plus human-actionable remedies (part 3's contract, demonstrated early).

### Common confusion

- **"TypeScript types are the contract"** — types describe compile-time shapes (erased at runtime — callers in other languages never see them); contracts describe runtime behavior (statuses, codes, versions — enforced by validators and tests). Types *generate* contracts (derive OpenAPI from types — single source) but never *substitute* for them (unvalidated types are wishes at the boundary).
- **"versioning can wait for v2"** — unversioned v1 *is* the versioning decision (every change is breaking by default — no path/header to evolve under). Version from day one (cost: one path segment; benefit: every future change has somewhere to go but breaking). Retrofit versioning is a migration; initial versioning is a prefix.

### Performance note

Envelope overhead per response: one discriminant field + uniform serialization (bytes, single-digit percent on small payloads — negligible beside I/O). Validation overhead per request (schema parse — microseconds-to-milliseconds by payload size): measure hot paths, skip validation only with benchmarks proving safety (unvalidated boundaries accept garbage at full speed — fast wrongness). Contract costs are linear and visible; contract absences cost incidents.

### Mentor note

Review API PRs contract-first (spec diff before handler diff — shapes, codes, versions decided before implementation reviewed): implementation follows contract, never precedes it. Mentees designing APIs start with the envelope + error table (one page), then handlers — contract-driven development, one page at a time.

## 2) Types serve the boundary

### 2) **Definition** (consumer-facing type design)

Public types are designed for consumers (minimal, stable, documented — the surface from TS 12/3.1), generated from sources (`declaration: true` + `declarationMap` for libraries — derivation, not hand-sync), and erasable where execution demands it (services: `erasableSyntaxOnly`-clean sources running under every runner — [01/3.3-equivalent discipline via 02/2.2](<../../../02 Configuration and tsconfig for Execution/sections/2. Module pairs and specifiers/2.2. allowImportingTsExtensions and extension rewriting.md>)). Internals stay internal (unexported — never leaking through the contract).

### What problem it solves (history)

Leaky type surfaces (every internal helper exported "for tests," barrel re-exports of implementation details, hand-synced `.d.ts` drifting from sources) coupled consumers to internals (refactors breaking clients, `any`-infection across codebases — TS 12/5.1's promise-4 shape) and bloated check times (consumers checking implementation-shaped declarations). Designed surfaces (curated exports, generated declarations) decouple: internals move, contracts hold.

### Modern guidance

Services: erasable-only sources (every runner executes — the universality payoff from [02/2.2](<../../../02 Configuration and tsconfig for Execution/sections/2. Module pairs and specifiers/2.2. allowImportingTsExtensions and extension rewriting.md>)); libraries: generated declarations + maps (reviewed diffs per PR — API evolution visible); both: export lists curated (public surface reviewed deliberately — additions need justification, removals need versions). Envelope types shared (one `Envelope<T>` definition, published or vendored — clients and servers branch identically).

### Runnable example (good — erasable envelope, universal execution)

```bash
# api.ts above is erasable-only (type aliases + functions — no enum, no namespaces):
./node_modules/.bin/tsc --noEmit --project <with-erasableSyntaxOnly> api.ts  # clean (no TS1294)
# → runs under ts-node (verified), tsx, AND flagless stripping (v22.18+) — one file, every runner
```

```typescript
// bad: non-erasable contract (enum in the boundary — stripping refuses, runners diverge)
// enum Status { Pending, Done }  // TS1294 under erasableSyntaxOnly — the flag earning its keep
type Status = "pending" | "done"; // erasable idiom — every runner, zero cost
```

Why the idiom wins: union literals erase to nothing (zero runtime, zero emit, universal execution); enums emit code (runtime cost + runner restrictions + checker exceptions). Boundary types deserve the most portable spelling — they cross the most runners.

### Common confusion

- **"rich domain types belong in the API"** — rich types belong *behind* the API (branded types, invariants, state machines — server-side power); wire types stay *narrow* (JSON-shaped, versioned, documented — client-side stability). Mapping between them (parse, don't cast — validators at the boundary) is the design work. Leaking domain richness onto the wire couples every consumer to every invariant change.
- **"declarationMap is optional"** — TS 12/3.1's verdict stands (navigation reaches sources — developer-experience infrastructure). For libraries especially: consumers debugging into `.d.ts` stubs instead of sources file support tickets instead of reading code. Maps convert tickets into self-service.

### Performance note

Erasable boundary types cost zero runtime (erased — the whole point) and minimal check time (aliases resolve fast; deep generic webs resolve slowly — keep wire types shallow: unions, objects, arrays — the fast shapes). Declaration emit adds build seconds (libraries pay willingly — consumer check-time savings dwarf it); services skip it (no consumers — [06/1.1](<../../../06 Shipping Builds Dist and Containers/sections/1. Build configs/1.1. The build tsconfig.md>) priced the skip).

### Mentor note

Teach boundary design with the envelope exercise (design `Envelope<T>` + three error codes with remedies for a toy route — thirty minutes): every subsequent API discussion references the exercise ("where's the envelope? what are the codes?"). One exercise, permanent lens — boundaries designed, not accreted.

## 3) Failures name remedies

### 3) **Definition** (actionable error contract)

Every error response carries: stable `code` (machine-branchable — `RATE_LIMITED`, not "Too many requests"), human `message` (what happened), `remedy` (what to do — "Retry after 30s," "Reduce batch to ≤100," "See runbook X"), and `retryable` where applicable (boolean — callers decide programmatically, never by message-sniffing). Errors without remedies are complaints; errors with remedies are interfaces.

### What problem it solves (history)

Remedy-less errors (500 "Internal error," 429 without `Retry-After`, timeouts without guidance) converted every failure into a support ticket (humans bridging the remedy gap — reading code, asking engineers, waiting) — support load scaling with failure rate instead of with novelty. Remedy-bearing errors convert repeats into self-service (first occurrence: ticket + remedy added; subsequent: clients follow the remedy — support load scaling with novelty only).

### Modern guidance

Codify per error (table: code → status → remedy → retryable — reviewed like API shapes); quote limits in the error (`Retry-After: 30`, "limit 100/60s" — numbers from [1.2](<../1. Production judgment/1.2. Capacity and graceful degradation.md>) part 3's bounds, surfaced to callers); link runbooks for operational errors (deploy/config incidents need human paths — URL in the error, not in tribal memory); test remedies (assert `remedy` field presence per error code — contract tests covering the interface, not just the happy shape).

### Runnable example (good — remedies verified above)

```bash
# from the verified probe: {"ok":false,"error":{"code":"RATE_LIMITED","remedy":"Retry after 30s"}}
# caller branches on code (machine), follows remedy (human), no ticket filed (team) — the full payoff in one line
```

```jsonc
// bad: message-only errors (the support-ticket generator)
{ "error": "Something went wrong" }       // code? remedy? retryable? — all absent, ticket certain
{ "error": "Rate limit exceeded" }        // code absent (message-sniffing required), remedy absent, Retry-After absent
```

Why it hurts, priced: each remedy-less error costs one support interaction (minutes-to-hours × failure rate — recurring failures charging full price every occurrence). Remedies amortize (written once, served per failure — support load collapsing to novel errors only). The error table is support-load engineering, not documentation polish.

### Common confusion

- **"remedies leak internals"** — remedies describe *caller action* (retry, reduce, wait, contact — external vocabulary), never *system internals* (stack traces, query shapes, hostnames — redacted). Actionable ≠ transparent: "retry after 30s" helps without exposing; stack traces expose without helping. Remedy outward, investigate inward.
- **"codes freeze the API"** — codes *version* with the API (new codes added freely — additive, non-breaking; removals versioned — same policy as fields). Uncoded messages freeze harder (clients sniffing text break on rewording — every copy-edit a breaking change). Codes liberate wording; messages without codes imprison it.

### Performance note

Remedy fields cost bytes per error (tens of bytes — errors are rare paths; payload cost negligible). Retryable flags save thundering herds (non-retryable errors shed load — callers back off correctly instead of hammering; retry storms are unbounded-error consequences — [1.2](<../1. Production judgment/1.2. Capacity and graceful degradation.md>) part 3's caps enforced by clients reading flags). Error design is load-shedding design wearing an API costume.

### Mentor note

Audit any API's errors in ten minutes (list codes, check remedies, verify retryable flags — gaps filed as findings with support-ticket counts attached): the audit converts abstract "better errors" into counted load (N tickets/month answerable by remedies). Teams seeing the count prioritize the table immediately — support metrics sell error design better than any style argument.
