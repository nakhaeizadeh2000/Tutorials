# 2.1. Reviewing Node+TS code

The gates-first review order for TypeScript-on-Node: mechanical findings before taste, priced numbers before approval, failure paths before happy paths. Junior read: run the greps before opining on style. Expert read: why review order determines incident rates, and what "approve" certifies beyond the diff.

## 1) Gates before taste

### 1) **Definition** (the mechanical-first order)

Review in layers: gates (hook in `start`? half-pair? unbridged alias? unmapped trace? — grep + gate scripts decide), then correctness (logic, types, boundaries), then taste (naming, structure, elegance). Mechanical findings block; correctness findings discuss; taste findings suggest. Order enforced per PR, not per mood.

### What problem it solves (history)

Taste-first reviews (naming debates atop hook-in-production start scripts, elegance discourse over unmapped traces) approved structurally broken code with polished prose — incidents shipped beautifully formatted. Gates-first ordering inverts the waste: machines judge machines (greps, gates, typecheckers — instant, objective), humans judge what machines can't (design, trade-offs, readability).

### Modern guidance

Every PR touching execution paths runs gates 1–7 (or the merged pre-flight — green required, stage numbers quoted on red); reviewers open with the gate output (red → request changes with the stage number, no further reading until green); taste comments wait for green (style on red code is churn — the code will change anyway). Gate lists live in [01/4.1](<../../../01 Execution Foundations and Mental Model/sections/4. Important points to remember/4.1. Execution checklist habits mentors insist on.md>) through [06/4.1](<../../../06 Shipping Builds Dist and Containers/sections/4. Important points to remember/4.1. Shipping checklist habits mentors insist on.md>) — six checklists, one review order.

### Runnable example (good — the mechanical review, verified)

```bash
grep '"start"' ship/package.json
# "scripts": { "build": "tsc -p tsconfig.build.json", "start": "node dist/main.js" },
grep -c "ts-node" ship/package.json || echo "no-ts-node-in-manifest"
# no-ts-node-in-manifest
./gate7.sh
# SHIP-CHECK-GREEN
```

Verified this session: manifest executes artifacts (no hook tokens), checklist gate green — the mechanical review of a shipping surface in three commands. A reviewer pasting this output approves the *structure*; logic review follows on green, never before.

### Runnable example (bad — the taste-first review)

```markdown
# bad: review comment thread on a PR whose start runs ts-node in production
# "Nit: rename `srv` to `server` for clarity." (3 replies, resolved)
# "Consider async/await here instead of .then." (approved after change)
# — merged with hook-in-prod, unmapped traces, no smoke. Beautiful incident, incoming.
```

Why it hurts: review attention is finite (each taste thread spends the reviewer's budget); mechanical defects survive politeness (nobody wants to be the "gates person" after three naming threads); incidents inherit the polish (well-named variables in unmapped stacks). Fix: gates first as policy (template enforces: gate output pasted before human review begins — no output, no review).

### Common confusion

- **"gates replace reviewers"** — gates replace *vigilance*, not judgment (mechanical properties checked; design decisions still human — [1.1](<../1. Production judgment/1.1. Selecting architectures under constraints.md>)'s ADRs need readers, not runners). Reviewers freed from grep-work spend attention on architecture — gates upgrade review, never automate it away.
- **"small PRs skip gates"** — small PRs skip *slow* gates never (gate7: seconds; typecheck: seconds — cheap gates run always); large suites gate per schedule (full profiles per merge, not per push — cost-proportioned, per [04/4.1](<../../../04 Development Workflow Watch REPL and Editors/sections/4. Important points to remember/4.1. Workflow checklist habits mentors insist on.md>) part 3's clock split). Size scales scheduling, never exemption.

### Performance note

Review throughput rises when machines go first (mechanical red in seconds vs human-found-in-days; taste discussion only on green code that survives). Review *quality* rises simultaneously (attention unspent on greppable defects concentrates on design). Gates-first is review performance (faster merges, fewer escapes) wearing a process costume.

### Mentor note

Enforce with PR templates (gate-output section first, human-review sections after — structure beats exhortation): contributors paste green outputs before requesting review; reviewers check the paste before reading code. Two quarters of template-enforced order and teams internalize it (templates teach until habits form, then guard the habit).

## 2) Ask for the numbers

### 2) **Definition** (the priced-constant rule)

Every constant in the diff justifies itself with a number: pool sizes (measured concurrency), timeouts (p99 multiples), caps (arithmetic from [1.2](<../1. Production judgment/1.2. Capacity and graceful degradation.md>)), cache TTLs (staleness budgets), retry counts (blast-radius math). Unpriced numbers get challenged ("sized from what?") — not out of hostility, but because unpriced constants are guesses wearing literal syntax.

### What problem it solves (history)

Magic-constant production (timeout 30s "seems safe," pool 10 "default," retries 5 "standard" — each unmeasured, each load-bearing) failed mysteriously at scale (30s timeouts cascading, 10-pools starving, 5-retries storming) with no diagnostic trail (which constant? sized for what load?). Priced constants fail diagnosably (threshold known, arithmetic attached, deviation measurable) — and get resized correctly on first evidence instead of third incident.

### Modern guidance

Challenge every unexplained literal in execution paths (timeouts, sizes, counts, TTLs, ports, versions — "source?" per number); accept measurements, derivations, and explicit guesses-with-review-dates (honest estimates beat silent defaults — "guess, revisit March" is honorable); record prices beside the constant (comment with the arithmetic or ADR link — prices live with code, not in chat history).

### Runnable example (good — priced vs unpriced, contrasted)

```typescript
// good: every number sourced
const TIMEOUT_MS = 600; // upstream p99 200ms × 3 (measured 2026-09, dashboard X)
const POOL_SIZE = 10; // 100 slots / 10 per connection (sizing in [1.2], ADR-004)
const RETRIES = 2; // blast radius: 3× traffic worst case, within headroom (ADR-004)
```

```typescript
// bad: literals without lineage
const TIMEOUT_MS = 30000; // (nothing — 30s of cascading hang per slow upstream)
const POOL_SIZE = 10; // (nothing — default-shaped, load-unshaped)
const RETRIES = 5; // (nothing — 6× amplification, storms at the second failure)
```

Why it hurts: unpriced numbers resist tuning (change 30s to what? — no model answers) and hide coupling (timeout × retries × pool = worst-case load multiplier — unknowable without prices). Fix: price on introduction (three comments, one minute) or on first challenge (reviewer asks once, author measures, comment lands with the fix).

### Common confusion

- **"asking slows reviews"** — asking *accelerates* reviews over time (priced codebases answer before asked — comments carry prices; unpriced codebases re-litigate per PR). First month slower (habit forming); every month after faster (evidence accumulated). Invest the month.
- **"estimates don't count as prices"** — dated estimates count fully ("guess 600ms, revisit March" — falsifiable, scheduled, honest). What doesn't count: silence (no number to revisit, no date to revisit on). Falsifiability is the standard, not accuracy — wrong fast beats vague forever.

### Performance note

Priced constants are performance documentation (timeouts bound tails, pools bound concurrency, TTLs bound staleness — the p99 story told per constant). Unpriced constants are performance debt (tails unexplained, capacity unplanned, incidents undiagnosable). Review-time pricing converts debt to documentation at one comment per number — the cheapest performance practice after bounding.

### Mentor note

Model the question kindly ("help me understand the 600 — measured or estimated?") until the team asks it of itself — tone determines adoption (curiosity spreads, interrogation stalls). Celebrate first pricings publicly (the comment that sourced a timeout is a team asset — say so). Culture first, checklist second, gates last — in that order, always.

## 3) Approve the failure paths

### 3) **Definition** (happy-paths-necessary-insufficient)

Approval certifies failure behavior, not just feature behavior: errors routed (typed, mapped, actionable), drains sequenced (SIGTERM → drain → exit 0 — [NodeJS 01](<../../../../NodeJS/01 Runtime Fundamentals and Mental Model/README.md>) lifecycle, linked), maps shipped (traces name `.ts` — [05/4.1](<../../../05 Debugging Sourcemaps and Profiling TypeScript/sections/4. Important points to remember/4.1. Observability checklist habits mentors insist on.md>) stage 50), rollouts smoked (boot + throw + exit codes — [06/4.1](<../../../06 Shipping Builds Dist and Containers/sections/4. Important points to remember/4.1. Shipping checklist habits mentors insist on.md>) stages 70–72). Happy paths necessary; failure paths decisive — merge when both convince.

### What problem it solves (history)

Happy-path approvals (demo works, tests green, screenshots lovely) shipped services whose first error was also their first untested path (unmapped stacks, undrained deploys, unhandled rejections killing the process — the incident catalog of [05/3.1](<../../../05 Debugging Sourcemaps and Profiling TypeScript/sections/3. Production triage/3.1. Triage order for TS services.md>)). Failure-path review converts first-errors from incidents into handled cases (routed, mapped, drained — each verified pre-merge, each boring in production).

### Modern guidance

Per PR: name the failure modes changed (new throw? new dependency? new path? — author lists them in the description); prove each handled (test asserting the route, gate asserting the map, drain asserted by signal test — evidence per mode); approve only when failures convince equally (reviewer asks "show me it failing correctly" — the demo that matters). Failure coverage tracked like test coverage (modes enumerated, each evidenced — gaps explicit, never accidental).

### Runnable example (good — failure-path review checklist, applied)

```markdown
# PR review (failure paths): new payment route
# - throw paths: 3 new throws → all typed, all tested (assert rejects with code) ✓
# - traces: fixture still maps (gate stage 50 green post-change) ✓
# - drain: SIGTERM during in-flight payment → completes then exits 0 (tested) ✓
# - rollout: canary + mapped-throw smoke in staging (gate6 pattern) ✓
# verdict: failures approved — happy path was already convincing.
```

```markdown
# bad: happy-path-only approval
# "Tested manually, works. Screenshots attached." (failures: unlisted, untested,
# unmapped — the next incident's agenda, pre-approved)
```

Why it hurts: unreviewed failure paths activate in production (that's where untested paths execute — Murphy's law with a pager), and each costs more there (diagnosis without maps, recovery without drains, rollback without smoke). Fix: failure-path section in the PR template (author fills, reviewer verifies — structure, again, beating exhortation).

### Common confusion

- **"failure review doubles review time"** — failure review *front-loads* incident time (minutes in review vs hours paged — same work, cheaper venue, calmer participants). Total engineering time falls (fewer incidents, faster triage when they come — mapped, drained, routed by construction). Pay in review or pay in incidents, with interest.
- **"small changes can't fail interestingly"** — small changes fail in foreign paths (one-line import → loader-order break per [03/1.1](<../../../03 ESM CJS and Loader Hooks Deep Dive/sections/1. Hook pipeline/1.1. resolve and load the two-stage pipeline.md>); one-flag change → map loss per [05/1.2](<../../../05 Debugging Sourcemaps and Profiling TypeScript/sections/1. Sourcemaps/1.2. Reading mapped stack traces.md>)). Interesting failures hide in boring diffs — review the blast radius, not the diff size.

### Performance note

Failure-path review costs minutes per PR (modes listed, evidence linked) against incident hours per escape (diagnosis + fix + retro + trust repair). The highest-leverage review minutes available: each approved failure path is an incident that arrives handled (boring page, known remedy) instead of novel (confusing page, cold diagnosis).

### Mentor note

Pair-review failure paths with juniors explicitly ("let's list what can fail here" — before reading what succeeds): the habit forms fastest as a spoken ritual (senior models enumeration, junior internalizes the lens). Three sessions of spoken failure-listing and juniors review failure-first unprompted — the lens transfers permanently.
