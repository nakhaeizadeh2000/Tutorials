- **What problem it solves**: capstone bloat (mechanics re-derived in synthesis leaves — copies drifting at the track's summit; the longest leaves teaching the least new). Reference discipline keeps the capstone lean (links per technique — judgment per leaf; new content only where assembly creates insight). Readers navigate by need (mechanics rusty — the link names the refresher; judgment ready — the leaf delivers).
- **Modern guidance** — when a capstone question reduces to mechanics, link out in one line (never re-derive — "pairs: [02/2.1]" then continue with the judgment). When a 01–06 reader arrives here, the prerequisites (domain index §0) tell them what's assumed — no surprise dependencies. Propose mechanics corrections upstream (errors in 01–06 fixed there — never patched by local restatement, least of all here).

## 2) **Frameworks and platform**

**Definition** — this track stops at the execution layer's edge deliberately: request routing, middleware, validation, ORMs, and app architecture → the framework tracks (Express for minimal, Fastify for speed, NestJS for enterprise — each executes TypeScript via the mechanics here; this track's domains are the foundation they assume). Runtimes beyond Node, clouds, vendors, and platform certifications → platform docs (AWS, containers, Kubernetes — venues, not execution). Production judgment here is execution judgment (TS-on-Node-shaped); platform judgment lives on platforms.

- **Why it matters (scope)**: track sprawl (framework tutorials inside an execution track — competing with dedicated tracks, losing to both; platform guides aging with vendor APIs — unmaintainable beside execution stability). Clean edges learn faster (execution complete here — frameworks next with mechanics assumed; platforms referenced, never re-taught). Each venue authoritative in its own track (updates land once — DRY across the repo, not just the track).
- **Modern guidance** — finish execution before frameworks (this track complete — mechanics assumed downstream; framework code then reads as automation, not magic). Reference platforms, never re-teach (links to current docs — versions drift; local copies rot). Judge execution questions here (hook-vs-artifact trade-offs — the track's home turf; platform trade-offs — home turf elsewhere).

## 3) **Words and careers**

**Definition** — meeting vocabulary (what to *call* these things — transpile-only, loader chain, sourcemap attribution as professional language) → the [IT Vocabulary track](<../../../../ITVocabulary/README.md>) (naming owned there; mechanism owned here). Growth beyond TS-Node (staff engineering, system design at scale, mentoring as craft) → the mentor paths later in this repo (System Design, Mentor Capstone — named as next steps when those tracks land; see root README mentor-path order). This track graduates engineers fluent in TS execution (hirable, promotable, on-callable); careers continue elsewhere, referenced here.

- **Why it matters (growth)**: vocabulary poverty (correct mechanics, unintelligible meetings — influence capped by language; words learned alongside, interviews and incidents both graded on clarity). Track-terminal thinking (TS-Node complete — learning stops; runtimes evolve, systems widen; graduation is commencement, not conclusion). Referenced next steps keep momentum (System Design for scale — Mentor Capstone for craft; paths named, not hidden).
- **Modern guidance** — borrow vocabulary deliberately (IT Vocabulary for review/incident phrasing — precise words make precise diagnoses). Name the next track per engineer (scale-hungry → System Design track when it lands; craft-hungry → Mentor Capstone; framework-hungry → Express/Fastify/NestJS tracks — guidance, not gates). Keep career questions out of execution reviews (promotion packets cite impact — built on these mechanics; mechanics enable, impact argues).
