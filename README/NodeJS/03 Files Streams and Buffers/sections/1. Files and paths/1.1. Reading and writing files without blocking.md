## 1.1. Reading and writing files without blocking

### 1) **Promises first, sync almost never**

**Definition** — `fs/promises` is the default file API (every operation returns a promise — executed on the pool, never the loop; `await` at call sites, errors as rejections). Synchronous `fs.*Sync` blocks the JS thread for the whole operation (the loop frozen — every concurrent client waits; leaf 3.1 of Domain 01 priced exactly this). The rule: async everywhere a loop exists (servers, CLIs doing real work); sync only where no loop exists yet (boot-time config, one-shot scripts).

- **What problem it solves**: sync-in-server latency (one `readFileSync` per request at 100 rps — each blocks milliseconds; the loop serializes all of them; p99 explodes while CPU idles). The failure reads as "slow disk" — the cause is the API choice, not the hardware. Async moves the wait to the pool (loop free — thousands of concurrent file ops, one thread scheduling). Same disk, different universe.
- **Modern guidance** — import from `node:fs/promises` by default (the promise surface first; callbacks legacy, sync exceptional). Reserve `*Sync` for boot (config load before listen — bounded, once, documented with a comment). Never sync per-request (review rule: `Sync` in a handler is a defect until proven boot-only). Handle rejections at the boundary (missing files are `ENOENT` — expected input, not exceptional crash; catch and route).

```javascript
// GOOD: pool-executed reads, loop free — runs on node v20.20.2
import { readFile, writeFile } from 'node:fs/promises';
await writeFile('/tmp/nodeprobe/hello.txt', 'hello files\n'); // pool thread writes (loop schedules on)
const text = await readFile('/tmp/nodeprobe/hello.txt', 'utf8'); // encoding named (bytes → string, explicit)
console.log('read back:', JSON.stringify(text)); // "hello files\n" (round trip, async throughout)
// BAD: `const text = readFileSync(path)` inside a request handler ("simpler control flow") —
// every request freezes the loop for disk latency; concurrency collapses to one-at-a-disk-speed
```

### 2) **Flags and modes are contracts**

**Definition** — open flags declare intent to the OS: `r` (read — fails if absent), `w` (write — creates or truncates), `a` (append — creates or seeks to end), `wx` (exclusive create — fails with `EEXIST` if present). Modes set permissions (`0o644` — owner writes, world reads). Flags prevent whole bug classes (`wx` makes create-if-absent atomic — no check-then-act race; `a` makes concurrent appends safe — no interleaved truncation). Intent stated once, enforced by the kernel.

- **Why it matters (correctness)**: check-then-act races (exists? then write — two processes interleave; both see absent, both write, one clobbers). Truncation accidents (`w` on a path meant to append — existing data destroyed; the flag was the only guard and nobody set it). Permission surprises (world-writable secrets — mode default inherited from umask, never chosen). Flags move these from code discipline (fallible) to kernel enforcement (reliable).
- **Modern guidance** — default `w` for outputs you own (truncation intended — stated), `a` for logs (append-only — concurrent writers safe), `wx` for lockfiles and first-writes (exclusivity atomic — races impossible). Pass flags explicitly in `writeFile` options (`{ flag: 'wx' }` — visible at the call site, reviewable). Set modes for secrets (`0o600` — owner-only; checked in review like any credential handling).

```javascript
// GOOD: exclusivity enforced by the kernel — verified on node v20.20.2 (first wins, second EEXIST)
import { writeFile } from 'node:fs/promises';
await writeFile('/tmp/nodeprobe/once.txt', 'first', { flag: 'wx' }).catch(() => {}); // idempotent fixture
try { await writeFile('/tmp/nodeprobe/once.txt', 'second', { flag: 'wx' }); console.log('overwrote (unexpected!)'); }
catch (err) { console.log('exclusive guard held:', err.code); } // EEXIST (atomic — no race window)
// BAD: `if (!existsSync(p)) writeFileSync(p, data)` ("same thing, readable") —
// TOCTOU race: two processes pass the check, one clobbers; `wx` closes the window the check opens
```

### 3) **Big files stream, small files read**

**Definition** — the size rule: whole-read (`readFile` — entire file in memory) for config-sized inputs (kilobytes — convenience free); streaming (leaf 2.1 — constant memory regardless of size) past the memory comfort line (megabytes and up — or whenever size is attacker-controlled). The threshold isn't a number, it's a question: "what's the largest this input can be, and can I hold twice that?" (twice — input plus output buffers). Unbounded reads of bounded memory are OOM incidents with a paper trail.

- **Why it hurts when missing (reliability)**: OOM kills on large inputs (log file grows to gigabytes — nightly report reads it whole; container limit hit; orchestrator kills mid-write — partial outputs, lost work). Attacker-controlled sizes (upload endpoints reading whole bodies — a 10 GB "avatar" kills the worker; streams with limits bound the damage). The failure arrives as resource exhaustion — the cause is an API choice three layers up.
- **Modern guidance** — read whole below ~10 MB known-good (configs, fixtures, templates — convenience justified). Stream above, or whenever size is untrusted (uploads, logs, exports — pipeline with byte caps). Cap what you read (`Content-Length` checked before buffering; stream `destroy()` past the cap — bounded by construction). Measure the line (RSS per input class in staging — the number that sets the policy, not folklore).

```javascript
// GOOD: size decides the API — runs on node v20.20.2 (small whole, large chunked)
import { readFile, stat } from 'node:fs/promises';
const SMALL_LIMIT = 10 * 1024 * 1024; // 10 MB comfort line (policy, not folklore — documented here)
const info = await stat('/tmp/nodeprobe/hello.txt'); // metadata first (leaf 1.2's rule)
const data = info.size < SMALL_LIMIT
  ? await readFile('/tmp/nodeprobe/hello.txt', 'utf8') // small: whole-read convenience
  : 'TOO BIG — stream it (leaf 2.1)'; // large: pipeline, constant memory
console.log('decision:', JSON.stringify(data).slice(0, 30));
// BAD: `await readFile(upload.path)` on user uploads ("works in dev") —
// dev uploads are kilobytes; attacker uploads are gigabytes; the OOM arrives with a ransom note
```

### 4) **Common confusion**

- "`fs/promises` is slower than callbacks" — same pool, same syscalls (promise wrapping costs nanoseconds beside disk milliseconds; benchmark the disk, never the wrapper). Ergonomics free at these ratios.
- "`wx` works across networks" — atomicity is filesystem-scoped (local FS: atomic; NFS/S3: advisory or emulated — distributed exclusivity needs coordination, not flags). Know your filesystem's promises.
- "Sync is fine at low traffic" — sync blocks *all* traffic during the call (one slow disk stall pauses every concurrent request — low traffic means rare pauses, not absent ones; latency spikes, not averages). Loop-blocking is never traffic-gated.
- "Encoding defaults are safe" — absent encoding returns `Buffer` (correct — bytes first; assuming utf8 strings corrupts binary silently — name the encoding or handle bytes). Defaults are byte-honest; callers must choose.

### 5) **Performance note**

File API costs are syscall costs, priced per operation: whole-reads cost memory ×2 (input plus string decode — the number that OOMs); streams cost per-chunk overhead (negligible beside I/O — chunk size tunes throughput, 64 KB default sane); sync calls cost loop time (the only API choice that taxes *other* requests — priced in leaf 01/3.1's lag probe). Flags/modes cost nothing (kernel-side — free correctness). Optimize by API selection (size rule above — the decision that dominates), then by concurrency (parallel reads for independent files — pool absorbs them), never by sync-vs-async microbenchmarks (identical syscalls, different threads).

### 6) **Mentor note**

Teach async-first as loop respect ("every sync call borrows the loop from all concurrent users — name the borrower" until `Sync` in handlers *looks* wrong). Demo the `wx` race live (two processes, same path — one wins, one `EEXIST`; then the exists-check version — both pass, one clobbers; atomicity felt). Drill the size rule (hand students a 5 GB fixture path — "read it or stream it? — decide before coding"). Watch for the sync-habitual ("simpler" — fix with the p99 question: "simpler for whom? — every concurrent user pays") and the whole-reader ("uploads too" — fix with the avatar-attack story). Review check: promises by default, sync boot-only with comments, flags explicit, size rule applied, juniors stat before reading.
