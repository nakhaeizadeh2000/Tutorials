## 2.2. Backpressure and stream errors

### 1) **Backpressure is the contract**

**Definition** — backpressure is the protocol keeping fast producers from drowning slow consumers: `writable.write(chunk)` returns `false` when the internal buffer passes `highWaterMark` (stop writing — resume on the `drain` event); readable pauses when unconsumed (data queues to the mark, then the source throttles); `pipeline`/`for await` honor it automatically (no manual checks — the machinery yields). Memory stays bounded by protocol, not by hope: buffer size ≈ mark × stages, regardless of producer speed.

- **What problem it solves**: unbounded buffering OOMs (a fast file read piped to a slow socket without backpressure — gigabytes queue in memory; the process dies holding data it already "handled"). The failure reads as resource exhaustion — the cause is a skipped protocol (manual `data`→`write` loops ignoring return values — the classic `.on('data', c => out.write(c))` memory bomb). Honored backpressure converts speed mismatch into pacing (producer waits — throughput matches the slowest stage, memory stays flat).
- **Modern guidance** — never ignore `write()`'s return (false → await `drain` — three lines; the contract in full). Prefer `pipeline`/`for await` (backpressure built in — manual loops only where staging demands). Size `highWaterMark` deliberately (default 16 KB — larger for throughput, smaller for latency; tuned per workload, measured per change). Test with mismatched speeds (fast generator, 10 ms-delayed consumer — assert flat memory, not just correct output).

```javascript
// GOOD: the contract honored manually — runs on node v20.20.2 (false observed, drain awaited)
import { Writable } from 'node:stream';
const slow = new Writable({ highWaterMark: 10, write(_c, _e, cb) { setTimeout(cb, 5); } }); // 5ms per chunk (slower than producer)
const ok = slow.write(Buffer.alloc(64)); // 64 bytes vs 10-byte mark (buffer exceeded immediately)
console.log('write returned:', ok); // false (STOP — protocol speaking)
if (!ok) await new Promise((res) => slow.once('drain', res)); // resume on drain (paced, bounded)
console.log('drained — producer paced to consumer');
// BAD: `src.on('data', (c) => out.write(c))` ("direct piping") —
// return value ignored: fast disk + slow socket = gigabytes queued; the OOM with a one-line cause
```

### 2) **Errors destroy, then clean**

**Definition** — stream errors are terminal for the stream (an `error` event with no listener throws — crashing the process; a failed stage poisons its neighbors — half-written state downstream). The discipline: `pipeline` destroys every stage on any failure (automatic teardown — descriptors freed, partial outputs abandoned), manual chains destroy explicitly (`stream.destroy(err)` — propagate, then clean), and `error` listeners exist on every bare stream (no unguarded emitters — unhandled stream errors are process crashes wearing event clothes).

- **Why it hurts when missing (reliability, resources)**: unhandled `error` crashes (socket reset mid-upload — no listener — process dies on a routine network event; the incident is a missing three-line handler). Partial outputs masquerade as complete (failed middle, un-torn-down destination — truncated file served as whole; checksums catch it downstream, users catch it first). Leaked stages accumulate (undestroyed files/sockets per failure — EMFILE under sustained errors; the outage that follows the outage).
- **Modern guidance** — `pipeline` for chains (teardown automatic — one catch, all destroyed; leaf 2.1's rule, enforced here). `destroy(err)` for manual topologies (分支 topologies pipeline can't express — destroy propagates the cause; half-states cleaned). Listener on every bare stream (constructed Readable/Writable gets an `error` handler at construction — review rule, no exceptions). Assert truncation impossible (output checksums or atomic renames — consumers never read partial results).

```javascript
// GOOD: failure tears down everything — runs on node v20.20.2 (rejected, destroyed, no leak)
import { pipeline } from 'node:stream/promises'; import { Readable, Transform } from 'node:stream';
let destroyed = false;
const fragile = Readable.from(['ok', 'ok']); // source (two chunks, then end)
const killer = new Transform({ transform(_c, _e, cb) { cb(new Error('midstream failure')); } });
killer.on('close', () => { destroyed = true; }); // close observed (teardown happened)
await pipeline(fragile, killer, async function* (src) { for await (const _ of src); }).catch((e) => console.log('rejected:', e.message, '| stage closed:', destroyed));
// BAD: `src.pipe(mid).pipe(dst)` with a single `.on('error')` on dst ("handled") —
// mid's errors never reach dst's handler: unhandled throw, leaked src, partial dst — handled nowhere
```

### 3) **Flowing vs paused, chosen**

**Definition** — Readables have two modes: paused (default — data waits until read: `read()`, `for await`, or `resume()` pull it) and flowing (`data` listeners push chunks as fast as produced — no pull, no pause, no backpressure signal to slow down). The choice is load-bearing: flowing mode with a slow handler replays the memory bomb (chunks arrive regardless — queue grows); paused + `for await` applies backpressure per iteration (consumer pace governs producer). Choose paused unless a reason names flowing (legacy `data` APIs, event-style fan-out with bounded sources).

- **Why it matters (liveness)**: accidental flowing (attaching `data` "just to log" — mode flips to flowing; the logger becomes the consumer; slow downstream drowns). Unpausable producers (flowing sockets can't be slowed by the app — only `pause()` re-asserts control; unpausable-by-default code discovers this under load). The mode flip is silent (no warning on attaching `data` — behavior changes, logs don't mention it). Explicit mode choice makes the flip visible.
- **Modern guidance** — default to `for await` consumption (paused with backpressure — the safe shape; mode never flips accidentally). Attach `data` only deliberately (bounded sources, logging taps that ignore pacing needs — commented with the reason). Call `pause()`/`resume()` explicitly around mode transitions (backpressure asserted by name — reviewers see the protocol). Never mix `data` and `for await` on one stream (mode fights — pick the consumer, commit to it).

```javascript
// GOOD: paused consumption with pacing — runs on node v20.20.2 (3 chunks, consumer-paced, bounded)
import { Readable } from 'node:stream';
const paced = Readable.from(['x'.repeat(100), 'y'.repeat(100), 'z'.repeat(100)]); // paused by default (waits)
let total = 0; for await (const chunk of paced) { total += chunk.length; await new Promise((r) => setTimeout(r, 10)); } // 10ms work per chunk (producer paced)
console.log('consumed paused:', total, 'bytes (backpressure per iteration — producer waited)');
// BAD: `stream.on('data', async (c) => { await slowWork(c); })` ("async handler handles pacing") —
// flowing mode ignores handler speed: chunks queue unboundedly while awaits pend; concurrency explodes, memory follows
```

### 4) **Common confusion**

- "Backpressure only matters for huge data" — pacing matters wherever speeds differ (slow DB writes behind fast file reads — megabytes queue in seconds; small services OOM on modest files at bad ratios). Ratios, not absolutes.
- "`drain` fires per write" — `drain` fires when the buffer empties below the mark (once per saturation episode — awaiting it in a loop without re-checking stalls; the pattern is write→false→await-drain→resume). Episodes, not writes.
- "Destroying loses data" — destroying abandons *failed* flows (error already terminal — undestroyed stages hold corrupt partials, not precious data; completed flows end, never destroy). Teardown preserves correctness; hoarding preserves garbage.
- "Flowing is faster than paused" — identical throughput ceiling (both move chunks at producer/consumer pace; flowing skips pull overhead measured in nanoseconds — the "speed" is skipped safety). Pace equal, safety not.

### 5) **Performance note**

Backpressure *is* memory performance: honored protocol bounds memory to marks × stages (flat under any speed ratio — the guarantee); violated protocol grows memory to producer-speed × incident-duration (unbounded — the OOM). `highWaterMark` tunes the throughput/latency trade (larger: fewer syscalls, more burst memory; smaller: snappier pause response, more overhead — measure per workload, defaults sane). `destroy()` frees descriptors immediately (failed-flow resources recycled — EMFILE avoided under error storms). Optimize memory by protocol compliance (automatic with `pipeline`/`for await` — the free win), throughput by mark sizing (measured), descriptor churn by fast teardown (destroy on first failure — never linger).

### 6) **Mentor note**

Teach backpressure as plumbing ("producer faucet, consumer drain, mark as overflow line — draw it" until unbounded `data→write` loops *look* flooded). Demo the bomb safely (fast generator + 50 ms consumer, manual loop ignoring returns — RSS climbs; then `pipeline` — flat; memory graphs teach faster than words). Demo the hang (bare `.pipe` with failing middle — silence; then `pipeline` — rejection; errors felt). Drill mode awareness ("attaching `data` flips what?" — flowing, unpausable, unpressured — recited before coding). Watch for the return-ignorer ("write returns what?" — fix with the drain drill) and the async-data-handler ("await paces it" — fix with the queue-growth demo). Review check: returns checked or machinery used, destroy paths present, modes chosen, juniors pace producers before blaming memory.
