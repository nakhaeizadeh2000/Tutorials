## 2.1. Readable, writable, and transform

### 1) **Streams are uniform I/O**

**Definition** — streams are Node's single interface for chunked data: Readable (data source — files, sockets, stdin; push or pull chunks), Writable (data sink — files, sockets, stdout; `write()` + `end()`), Duplex (both — sockets), Transform (both with processing — compress, parse, encrypt in flight). Same events (`data`/`end`/`error`), same errors, same backpressure (leaf 2.2) — whether the bytes come from disk, network, or a generator. Learn the interface once; every I/O source obeys it.

- **What problem it solves**: per-source I/O dialects (file code unlike socket code unlike stdin code — three error styles, three chunk shapes, three test doubles). The uniform interface collapses them (one pipeline shape handles all three — test with in-memory streams, deploy against files and sockets unchanged). Composition follows uniformity (any readable feeds any writable through any transform — Lego semantics for bytes).
- **Modern guidance** — program to the interface (functions accept Readables, return Writables — sources interchangeable; tests inject `Readable.from([...])`, production passes file/network streams). Prefer `node:stream/promises` entry points (`pipeline`, `finished` — promise surfaces composing with async code). Build sources with `Readable.from` (iterables become streams in one call — generators as data factories, no subclassing).

```javascript
// GOOD: one interface, three sources — runs on node v20.20.2 (same consumer, any producer)
import { Readable } from 'node:stream';
async function countChunks(source) { let n = 0, bytes = 0; for await (const chunk of source) { n++; bytes += chunk.length; } return { n, bytes }; }
console.log('memory source:', await countChunks(Readable.from(['ab', 'cde']))); // { n: 2, bytes: 5 } (test double)
const { createReadStream } = await import('node:fs');
console.log('file source:', await countChunks(createReadStream('/tmp/nodeprobe/hello.txt'))); // same consumer (production)
// BAD: `body.on('data')` handlers hand-rolled per source ("fewer abstractions") —
// three dialects, three error styles, untestable without real sockets; uniformity is leverage
```

### 2) **Pipeline over pipe**

**Definition** — `pipeline()` (from `stream/promises`) connects stages with full lifecycle management: errors in any stage abort all stages (propagation — one failure tears down the chain), all streams destroyed on completion (cleanup — no dangling file descriptors), completion as a promise (composition with async control flow). Bare `.pipe()` chains none of this (source errors never reach the destination — silent hangs; failed middles leak handles). The rule is absolute: `pipeline` in production, `.pipe` in throwaway demos (and even then, think twice).

- **Why it hurts when missing (reliability, resources)**: silent pipeline hangs (transform throws — destination waits forever; request never resolves; timeouts fire instead of errors — diagnosis starts three layers from the cause). Leaked descriptors (failed stages never destroyed — EMFILE under sustained failures; the process dies of success-handling). Unawaited completion (response sent before flush — truncated downloads reported as client bugs). `pipeline` converts all three into one awaited promise with one catch.
- **Modern guidance** — always `pipeline` stage chains (import from `stream/promises` — awaited, errors caught once at the end). Never bare-`.pipe` across failure domains (files, networks, user input — every real source fails eventually). Destroy explicitly on early exit (`controller.abort()` / `stream.destroy()` — partial downloads abandoned, descriptors freed). Test the failure path (a failing transform in the middle — assert rejection propagates and descriptors close; the test that earns `pipeline`).

```javascript
// GOOD: lifecycle managed, errors propagated — runs on node v20.20.2 (copied bytes match, failure rejects)
import { pipeline } from 'node:stream/promises'; import { Transform } from 'node:stream';
import { createReadStream, createWriteStream } from 'node:fs'; import { readFile } from 'node:fs/promises';
const upper = new Transform({ transform(chunk, _enc, cb) { cb(null, chunk.toString().toUpperCase()); } });
await pipeline(createReadStream('/tmp/nodeprobe/hello.txt'), upper, createWriteStream('/tmp/nodeprobe/upper.txt'));
console.log('pipelined:', JSON.stringify(await readFile('/tmp/nodeprobe/upper.txt', 'utf8'))); // "HELLO FILES\n"
const boom = new Transform({ transform(_c, _e, cb) { cb(new Error('stage failed')); } });
await pipeline(createReadStream('/tmp/nodeprobe/hello.txt'), boom, createWriteStream('/tmp/nodeprobe/never.txt')).catch((e) => console.log('propagated:', e.message)); // stage failed (one catch, all torn down)
// BAD: `src.pipe(upper).pipe(dst)` ("classic pattern") —
// transform errors never reach dst: hangs, leaks, truncated files — the classics, still shipping
```

### 3) **Transform in the middle**

**Definition** — Transform stages process chunks in flight (map: uppercase, parse, encrypt — one chunk in, chunks out; flush: emit remainders at end — partial lines, final blocks). This makes pipelines data factories (read → decompress → parse → validate → write — each stage single-purpose, independently testable). Stages stay small (one job per transform — SRP for bytes), pipelines read as sentences (source, verbs, sink — the data story in one `pipeline` call).

- **Why it matters (maintainability)**: monolithic stream handlers rot (one 200-line `data` callback parsing, validating, and writing — untestable without fixtures, undebuggable without logging every branch). Staged pipelines test per stage (feed chunks to one transform — assert outputs; stages compose by construction). Reuse follows stages (the gunzip stage serves logs, backups, and uploads — written once, pipelined thrice).
- **Modern guidance** — one job per transform (parse *or* validate — never both; stages named for the job). Push multiple outputs where natural (`this.push()` per record — line splitters emit per line; object mode carries records, not buffers). Handle `flush` for remainders (partial final chunk — trailing line without newline, padding block; unflushed remainders silently truncate). Keep transforms synchronous where possible (CPU per chunk small — heavy work chunks the loop; leaf 3.1 of Domain 01 prices it; workers await in Domain 05).

```javascript
// GOOD: staged, testable, sentence-readable — runs on node v20.20.2 (3 lines in, 3 records out)
import { pipeline, Readable } from 'node:stream'; import { Transform } from 'node:stream';
const split = new Transform({ readableObjectMode: true, transform(chunk, _e, cb) { for (const line of chunk.toString().split('\n')) if (line) this.push({ line }); cb(); } });
const seen = []; await new Promise((res, rej) => pipeline(Readable.from(['a\nb', '\nc\n']), split, async function* (src) { for await (const r of src) seen.push(r); }, (err) => err ? rej(err) : res()));
console.log('records:', JSON.stringify(seen)); // [{"line":"a"},{"line":"b"},{"line":"c"}] (split across chunk seams)
// BAD: 200-line `data` handler parsing + validating + writing ("one pass, efficient") —
// efficient at runtime, bankrupt at review: untestable stages, undebuggable branches, unreusable whole
```

### 4) **Common confusion**

- "`.pipe` returns the destination, so chaining is composition" — chaining without lifecycle (errors unpropagated, cleanup manual — composition of data flow, abandonment of failure flow). `pipeline` composes both flows.
- "Object mode is slower, avoid it" — object mode trades buffer copies for allocation (records vs bytes — parse once into objects, downstream stages skip re-parsing; measure the pipeline, not the mode). Clarity first, benchmarks second.
- "Transforms must be classes" — `Transform` instances suffice (constructor with `transform`/`flush` — subclass only for reuse across modules; factories returning configured instances cover most cases). Instances compose; classes publish.
- "`for await` replaces pipelines" — `for await` consumes (one stream read conveniently); `pipeline` connects (stages with managed lifecycle). Consumption vs connection — different jobs, both kept.

### 5) **Performance note**

Stream costs are per-chunk overhead plus lifecycle: chunk size tunes throughput (default 16 KB readable / 64 KB fs — larger chunks fewer syscalls; measure with your payload, not defaults worship). `pipeline` adds negligible management cost (one promise + destroy calls — invisible beside I/O). Object mode allocates per record (GC pressure at millions of records/s — batch or stay binary at extremes; typical services never reach them). Backpressure violations cost memory (unbounded buffering — leaf 2.2; the performance failure that matters). Optimize chunk sizing by measurement (throughput vs latency per workload), lifecycle by default (`pipeline` always — free reliability), memory by protocol (backpressure honored — leaf 2.2).

### 6) **Mentor note**

Teach uniformity first ("same consumer, three sources — swap them live" until students reach for `Readable.from` in tests unprompted). Demo the `.pipe` hang (failing middle, bare pipe — destination waits; then `pipeline` — rejection in hand; the lifecycle lesson in two runs). Drill stage-splitting (hand a monolithic handler — "cut into three transforms, test each"; composition observed). Watch for the piper (bare `.pipe` in production — fix with "show me the error path" — there isn't one) and the monolithist ("one pass" — fix with "test the middle third alone" — silence follows). Review check: `pipeline` everywhere, one job per transform, sources injectable, failure paths tested, juniors consume with `for await` and connect with `pipeline`.
