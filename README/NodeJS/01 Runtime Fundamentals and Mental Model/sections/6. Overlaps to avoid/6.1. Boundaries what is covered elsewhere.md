## 6.1. Boundaries: what is covered elsewhere

### 1) **Language mechanics**

**Definition** — this domain owns *runtime behavior* (which box runs what, which phase schedules what, which process owns what); the *language* lives next door. Promise combinators, microtask plumbing, and async/await grammar → [JavaScript 13: Async Event Loop and Promises](<../../../../JavaScript/13 Async Event Loop and Promises/README.md>) (this domain's leaf 3.1 assumes its microtask mechanics and prices them in phases). Module keywords as grammar (`import`/`export` forms, live-binding semantics) → [JavaScript 14: Modules and Code Organization](<../../../../JavaScript/14 Modules and Code Organization/README.md>) (this domain's leaf 2.2 assumes the syntax and owns Node's resolution). Syntax questions go there; scheduling questions stay here.

- **What problem it solves**: double-teaching (promise states re-explained per track — drift between copies within a year; `export` forms redefined per domain — subtle contradictions accumulate). Single source of truth keeps every copy fresh (one definition, many links — updates land once). Readers navigate faster too (grammar confusion routes to JS 13/14 in one click — no runtime leaf wastes pages re-deriving microtasks).
- **Modern guidance** — when a question reduces to grammar, link out in one line (never re-derive — "microtask mechanics: [JS 13]" then continue with the runtime point). When a JS-track reader arrives here, the prerequisites (domain index §0) tell them what's assumed — no surprise dependencies. Propose language-side corrections upstream (errors in JS 13/14 fixed there — never patched by local restatement).

### 2) **Deeper runtime topics**

**Definition** — this domain is the map, not the territory: each runtime area below gets its full treatment in its own domain (planned, see LOG — full coverage lands with those domains). Packages, scripts, and project layout → Domain 02 (what `npm install` builds, how `package.json` scripts orchestrate, where files live). Files, streams, and buffers → Domain 03 (the pool's main customers — reading, transforming, and backpressuring bytes). Events, networking, and HTTP → Domain 04 (emitters, sockets, bare servers — the runtime's public face). Child processes, workers, and clustering → Domain 05 (cores via processes — the answer to layer 4 of leaf 5.1). Debugging, configuring, and shipping → Domain 06 (inspect, env, deploys — runtime literacy in production).

- **Why it matters (maintainability)**: map-first learning prevents premature depth (streams before the loop model — backpressure without phases is incantation; workers before the process model — threads without lifecycle is hazard). Each domain assumes this one (process, loader, phases — the vocabulary every later leaf speaks). Skipping ahead borrows confusion at interest; the map makes the territory cheap.
- **Modern guidance** — read in `NN` order (on-disk prefixes are curriculum order — 01 before 02, always). Treat textual forwards as promises, not placeholders (each names its owning domain — when the domain lands, links upgrade; until then, the name scopes the question). Record cross-domain fixes at the boundary (a phases error found while writing streams gets fixed in 01/3.1 and linked — never duplicated into 03).

### 3) **Frameworks and vocabulary**

**Definition** — structure above the runtime and words about the runtime live elsewhere. Request routing, middleware, validation, and app architecture → the framework tracks (Express for minimal, Fastify for speed, NestJS for enterprise — each owns its layer above `node:http`; this track's Domain 04 stops at bare servers deliberately — frameworks compose on top, never inside). Professional vocabulary (what to *call* these things in reviews, incidents, and interviews — event loop, backpressure, graceful shutdown as meeting words) → the [IT Vocabulary track](<../../../../ITVocabulary/README.md>) (naming owned there; mechanism owned here).

- **Why it matters (operations, communication)**: layer confusion misroutes learning (Express middleware studied to understand phases — framework code *uses* the loop without *teaching* it; incident words improvised per team — "the thing hung" instead of "poll starved" — diagnosis slows to the speed of vocabulary). Clean layers learn faster (runtime first, framework second, words alongside — each in its venue).
- **Modern guidance** — build one bare `node:http` service before any framework (Domain 04's exercise — the runtime earns its intuition first; frameworks then read as conveniences, not magic). Borrow vocabulary deliberately (IT Vocabulary for review/incident phrasing — precise words make precise diagnoses). Keep framework questions out of runtime reviews (slow route? reproduce on bare `http` first — leaf 1.1's layer rule, applied to learning).
