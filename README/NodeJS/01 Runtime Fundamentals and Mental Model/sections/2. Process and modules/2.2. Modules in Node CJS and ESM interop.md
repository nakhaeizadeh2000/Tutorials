## 2.2. Modules in Node: CJS and ESM interop

### 1) **Two systems, one resolver**

**Definition** — Node loads code through two module systems sharing one resolution algorithm: CommonJS (`require()` — synchronous, returns the export object *now*; results cached per resolved path, so the second `require` returns the same object) and ESM (`import` — asynchronous-capable and statically analyzable; bindings live, hoisted, and strict by default). Same files on disk, different loading semantics: CJS executes like function calls (order = call order, cycles return partial objects); ESM links before executing (order = graph order, cycles get live bindings).

- **What problem it solves**: loader confusion is silent-behavior territory (`require` of an ESM-only package throws `ERR_REQUIRE_ESM` — the most common post-2022 backend error; top-level `await` valid in ESM, syntax error in CJS — same line, different fate; duplicated state from dual-package loads — a CJS copy *and* an ESM copy of one library, singletons split in two). Knowing which system runs a file predicts all three before they happen.
- **Modern guidance** — write ESM for new code (`import`/`export` — static analysis enables tree-shaking, top-level await, and succeeds where the ecosystem is going), keep CJS where the ecosystem still lives it (configs, legacy internals — migrate at boundaries, not in panics). Never mix loaders in one file (`require` in ESM needs `createRequire` — point 3; `import()` in CJS works but returns a promise — async boundary wherever it appears). Decide per package, document at the boundary.

```javascript
// GOOD: each system used as designed — verified on node v20.20.2
// cjs: const config = require('./config.cjs'); // sync — value in hand on the next line
// esm: import { summarize } from './lib.mjs';  // static — analyzable, tree-shakable, top-level await allowed
const a = require('node:util'); const b = require('node:util');
console.log('CJS cached identity:', a === b); // true — one object per resolved path (singletons ride this)
```

```javascript
// GOOD: dynamic import as the deliberate async boundary — runs on node v20.20.2
const mode = process.env.PARSER ?? 'fast';
const parser = await import(mode === 'fast' ? './fast.mjs' : './slow.mjs').catch(() => ({ default: null }));
console.log('loaded parser:', parser.default !== null || 'fallback');
// BAD: `require(variable)` with computed paths everywhere ("flexible") —
// bundlers can't trace it, caches split per spelling, cycles return half-built objects silently
```

### 2) **File-to-module mapping rules**

**Definition** — Node decides *which system* interprets a `.js` file by the nearest parent `package.json` `"type"` field (`"type": "module"` → `.js` is ESM; absent/`"commonjs"` → `.js` is CJS), with explicit overrides (`.mjs` always ESM, `.cjs` always CJS, `.json` importable with attributes). Resolution walks up (bare specifiers → `node_modules` upward; relative specifiers → path-joined; `node:` specifiers → builtins, never the disk). The mapping is deterministic — every surprise traces to a `type` field nobody read.

- **Why it matters (correctness)**: the `.js`-means-what problem (`SyntaxError: Cannot use import statement` — file written as ESM, nearest `type` says CJS; or `__dirname is not defined` — file written as CJS, nearest `type` says module). Extension-less relative imports (`./lib` without `.js` — works in CJS and bundlers, fails in pure ESM — the strictest system wins at runtime). Dual-package hazard (a dependency shipping both `main` and `exports` conditions resolving differently per importer — two instances, one pretending to be a singleton).
- **Modern guidance** — set `"type"` explicitly in every package (no absent-field roulette — `"module"` for new work). Always write extensions in ESM relative imports (`./lib.js`, not `./lib` — the one spelling every loader accepts). Use `.mjs`/`.cjs` as escape hatches at mixed boundaries (a CJS config inside an ESM package is `config.cjs` — intent in the filename, no reader needs the `type` graph). Check `exports` maps when singletons split (dual `require`/`import` conditions — align them or dedupe the dependency).

```bash
# GOOD: the mapping is inspectable — nearest type decides (verified on node v20.20.2)
mkdir -p /tmp/nodeprobe/esmpkg && printf '{"type":"module"}' > /tmp/nodeprobe/esmpkg/package.json
printf "export const kind = 'esm';\n" > /tmp/nodeprobe/esmpkg/lib.js
node --input-type=module -e "import { kind } from '/tmp/nodeprobe/esmpkg/lib.js'; console.log('.js under type:module is', kind)"
node -e "console.log('same .js under type:commonjs would throw on import syntax — mapping, not magic')"
# BAD: extensionless `./lib` imports in ESM ("works in my bundler") —
# bundlers resolve leniently, Node ESM strictly: green in dev, red in production
```

### 3) **Interop without surprises**

**Definition** — the boundary toolkit for mixed codebases: importing CJS from ESM (`import pkg from 'cjs-lib'` — the whole `module.exports` becomes the *default* export; named imports are best-effort static guesses, reliable only for statically analyzable shapes), requiring ESM from CJS (not allowed synchronously — `import()` async-only; `createRequire` builds a `require` inside ESM for the reverse trip), and JSON modules (`import data from './x.json' with { type: 'json' }` — attributes required, never bare).

- **Why it hurts when missing (correctness)**: the default-export trap (`import { connect } from 'cjs-lib'` silently `undefined` — the export lives on `default`, named destructuring finds nothing, failure surfaces far downstream as "connect is not a function"). The `__dirname`-in-ESM crash (CJS idiom pasted into ESM — every migrated file trips once; leaf 2.1 owns the replacement). `require(esm)` throws `ERR_REQUIRE_ESM` (synchronous brain meeting asynchronous modules — restructure to async or stay CJS at that boundary).
- **Modern guidance** — default-import CJS, then destructure (`import pkg from 'cjs-lib'; const { connect } = pkg;` — one spelling that always works, regardless of static analyzability). Reach ESM from CJS via top-level `import()` (async boundary made visible — callers see the promise). Use `createRequire` for the unavoidable reverse (data files, computed paths in ESM — quarantined to one helper module, never scattered). Prefer `node:` builtins in both systems (identical specifiers — one less interop axis).

```javascript
// GOOD: default-import CJS then destructure + createRequire quarantined — runs on node v20.20.2
import { createRequire } from 'node:module'; // the sanctioned reverse bridge (ESM -> CJS)
import fsDefault from 'node:fs'; // builtin CJS via default import (whole exports object)
const { readFileSync } = fsDefault; // destructure after — always works (no static guessing)
const require = createRequire(import.meta.url); // one quarantined require (data/config only)
console.log('interop ok:', typeof readFileSync === 'function' && typeof require === 'function');
// BAD: `import { readFileSync } from 'node:fs'` relied on everywhere from CJS packages ("shorter") —
// named-from-CJS is best-effort: green for analyzable shapes, undefined for computed exports, red at 3 AM
```

### 4) **Common confusion**

- "`require` and `import` are interchangeable syntax" — different loaders (sync-cached-executing vs linked-live-strict — timing, cycles, and top-level await all differ). Syntax is the surface; loading is the substance.
- "Named imports from CJS always work" — best-effort static analysis (Node guesses names from simple shapes; computed `exports[x] = ...` defeats it — default-import-then-destructure never guesses). Trust `default`, verify nameds.
- "Adding `.js` extensions is ugly/optional" — mandatory in pure ESM (the strictness the whole ecosystem converges on — bundlers already accept them; write once, run everywhere). Ugly beats broken.
- "`type: module` converts everything automatically" — it reinterprets `.js` (CJS idioms inside — `__dirname`, `require`, `module.exports` — all break simultaneously; `.cjs` hatches the stragglers). Migration is per-file work with per-file errors; the flag just declares intent.

### 5) **Performance note**

Loader choices cost at startup, rarely at runtime: ESM's link-before-execute adds parse-and-link overhead per cold start (measurable in serverless — hundreds of modules link serially; bundle or snapshot for cold paths), while CJS's sync `require` blocks the loop per call (top-level requires serialize boot — lazy-require hot paths only if profiling proves boot matters; it rarely does for long-lived servers). Runtime cost after load is identical (both compile to the same V8 code — function call overhead indistinguishable). Optimize loading for startup latency (fewer, statically analyzable modules — ESM wins), never for request throughput (loaders retire after boot).

### 6) **Mentor note**

Teach resolution before syntax ("which system runs this file? — answer from `type` + extension before reading a line" until students check the mapping first). Demo each failure live (`ERR_REQUIRE_ESM`, `__dirname`-in-ESM, extensionless import — three errors, three lessons, ten minutes). Drill the default-import habit (review rule: named-from-CJS must justify itself; default-then-destructure is the default). Watch for the syntax-thinker ("just style" — fix with the cycle demo: partial CJS object vs live ESM binding) and the extension-skipper ("bundler handles it" — fix with pure-Node runtime: red on arrival). Review check: `type` explicit, extensions present, CJS consumed via default, bridges quarantined, juniors predict the loader before running.
