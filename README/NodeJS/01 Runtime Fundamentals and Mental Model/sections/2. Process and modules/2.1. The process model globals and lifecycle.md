## 2.1. The process model, globals, and lifecycle

### 1) **One process, owned explicitly**

**Definition** — every Node program is one OS process with three explicit contracts: inputs (`process.argv` — CLI arguments after the script path; `process.stdin` — piped data), configuration (`process.env` — environment strings, never secrets in code), and outcomes (`process.exitCode` — the integer supervisors and CI read). Nothing implicit: the process starts from a command, reads its world from declared channels, and reports success or failure as a number.

- **What problem it solves**: implicit process handling fails at 3 AM (hardcoded ports colliding in staging — argv/env ignored; secrets committed because "env is hassle" — leaked credentials; `process.exit(1)` mid-flight truncating flushed logs — outcomes unsignaled). Explicit contracts make behavior reproducible (same argv + same env = same run) and failures routable (exit code names the failure class — supervisors restart on 1, page on 2, ignore 0).
- **Modern guidance** — parse argv with a tiny parser (built-in `node:util` `parseArgs` — no dependency for flags; `--port 3000` defaults declared beside usage). Read env with validation at boot (fail fast on missing `DATABASE_URL` — crash in line 10 with a named error, not line 10,000 with `undefined`). Set `process.exitCode` instead of calling `process.exit()` (lets the loop drain — pending writes flush; `exit()` murders them — leaf point 3 prices this).

```javascript
// GOOD: argv + env + exitCode as declared contracts — runs on node v20.20.2
import { parseArgs } from 'node:util';
const { values } = parseArgs({ options: { port: { type: 'string', default: '3000' } } });
const port = Number(values.port); // input: declared, defaulted, typed at the edge
const db = process.env.DATABASE_URL; // config: environment-owned, never hardcoded
if (!db) { console.error('missing DATABASE_URL'); process.exitCode = 1; } // outcome: numbered, drain-safe
else { console.log(`would listen on ${port} with db configured`); }
// BAD: `const port = 3000; const db = 'postgres://...'` ("fewer moving parts") —
// staging collides, secrets leak, every environment runs the developer's laptop values
```

### 2) **Globals are runtime services**

**Definition** — Node injects a small set of globals because every program needs them without importing: timers (`setTimeout`, `setInterval` — loop-bound, leaf 3.1), paths (`__dirname`/`__filename` in CJS — the *file's* directory; `process.cwd()` — the *launch* directory; different questions, different answers), binary data (`Buffer` — bytes before strings), and module scope (`exports`, `require`, `module` in CJS; `import.meta` in ESM). Each global is a service with a contract — learn the contract, not just the name.

- **Why it matters (correctness)**: the classic `__dirname` vs `cwd()` swap (config resolved relative to launch dir — works from repo root, breaks from anywhere else; tests pass, production `./config.json` not found). ESM removes `__dirname` entirely (`import.meta.url` + `fileURLToPath` — the migration every converted codebase trips on once). Timer globals assumed to be browser timers (Node returns `Timeout` objects with `.unref()` — unref'd timers don't hold the process open; browser code has no such concept).
- **Modern guidance** — resolve files from the module, never from cwd (`new URL('./config.json', import.meta.url)` in ESM — launch-directory-proof; `path.join(__dirname, ...)` in CJS). Use `.unref()` for housekeeping timers (metrics flush must not hold a dying process open — ref'd handles keep the loop alive, point 3). Prefer explicit imports where a global has one (`node:buffer`, `node:timers` — readability over keystrokes; globals stay for the truly universal).

```javascript
// GOOD: module-relative resolution + unref'd housekeeping — runs on node v20.20.2
import { readFileSync } from 'node:fs';
const configPath = new URL('./config.json', import.meta.url); // file's dir — launch-proof
const timer = setInterval(() => console.log('heartbeat'), 60_000); // housekeeping
timer.unref(); // must not hold the process open (ref'd handles block natural exit)
console.log('config at', configPath.pathname, '| cwd is', process.cwd()); // different answers, both visible
// BAD: `readFileSync('./config.json')` ("shorter") —
// resolves against cwd: green from repo root, red from everywhere else (cron, systemd, Docker WORKDIR)
```

### 3) **Lifecycle ends on purpose**

**Definition** — a Node process exits *naturally* when the event loop drains (no pending timers, sockets, or handles — work finished, goodbye) or *forcibly* via `process.exit(code)` / signals (SIGTERM from orchestrators, SIGINT from Ctrl-C). Natural exit returns `process.exitCode` (default 0); forced exit skips the loop (pending writes lost, `finally` runs but async cleanup doesn't). Production rule: end naturally with a numbered code; handle signals to get there gracefully.

- **Why it hurts when missing (correctness, data loss)**: `process.exit(0)` after `console.log` in a piped process (stdout truncated — the write was still queued; success reported, data lost). Unhandled SIGTERM in containers (orchestrator waits, then SIGKILLs mid-request — in-flight writes corrupt; graceful window wasted). `exit` event handlers doing async work (the `exit` event is synchronous-only — promises never resolve; cleanup silently skipped, resources leak per restart).
- **Modern guidance** — never call `process.exit()` in libraries (set `process.exitCode`, return — the application owns death). Handle SIGTERM/SIGINT once at the top (stop accepting, finish in-flight with a timeout, then exit — the graceful-shutdown trio; orchestrators grant seconds, use them). Do async cleanup in signal handlers, sync-only in `exit` (flush logs in the handler — `process.on('exit')` may only run sync code; anything awaiting there is fiction).

```javascript
// GOOD: graceful shutdown with numbered outcome — runs on node v20.20.2 (exit code 0, flushed)
let server = { close: (cb) => cb() }; // stand-in (Domain 04 owns http — see 01/6.1 boundaries for the live map)
process.on('SIGTERM', () => { // orchestrator asks us to die politely
  console.log('SIGTERM: draining'); // sync-safe logging (flushed before natural exit)
  server.close(() => { process.exitCode = 0; }); // finish, then number the outcome
});
process.on('exit', (code) => { console.log(`exit:${code} (sync only here — no awaits)`); });
setTimeout(() => console.log('work done, loop drains naturally'), 50); // no forced exit anywhere
// BAD: `process.exit(0)` right after logging ("we're done anyway") —
// queued stdout/stderr truncated, in-flight requests severed, exit code lies about completeness
```

### 4) **Common confusion**

- "`process.env` values are typed" — always strings (`PORT=3000` arrives as `'3000'` — `Number()` at the edge; `ENABLED=false` is truthy — compare explicitly). Validate-and-coerce at boot, once.
- "`__dirname` works everywhere" — CJS-only (ESM uses `import.meta.url`; workers have their own paths — [Domain 05](<../../../05 Child Processes Workers and Clustering/README.md>)). Know which module system you're standing in (leaf 2.2).
- "`process.exit()` flushes stdio" — it doesn't (queued writes die; piped output truncates — the classic "missing last log line"). Set `exitCode`, let the loop drain.
- "Signals need frameworks to handle" — `process.on('SIGTERM')` is three lines (shown above — no dependency; orchestrators speak signals, your process should answer). Graceful shutdown is runtime literacy, not framework magic.

### 5) **Performance note**

Process-model choices cost at the margins that matter at scale: boot-time env validation (milliseconds once — versus hours debugging `undefined` mid-request; always worth it), `exit()`-truncated telemetry (lost tail logs per deploy — observability gaps exactly when deploys are riskiest; drain-safe exits preserve them), unref'd vs ref'd timers (a forgotten 60s `setInterval` holds every worker process open — orchestrator SIGKILLs pile up; `.unref()` is free). None of these show in microbenchmarks; all show in incident reviews. Optimize the lifecycle for debuggability (complete logs, numbered exits, graceful drains — the evidence incidents need).

### 6) **Mentor note**

Teach the process as a contract diagram (inputs → program → numbered outcome — draw it before any code; students should place argv/env/exitCode on it unprompted). Demo the cwd trap live (run the same script from two directories — one green, one red; the lesson sticks). Drill graceful shutdown as a kata (SIGTERM the example process — watch it drain and number its exit; then show the `process.exit()` truncation with piped output). Watch for the hardcoder ("env is hassle" — fix with the leaked-secret story) and the exiter (`process.exit()` sprinkled in helpers — fix with "who owns death?" — only main does). Review check: argv parsed, env validated at boot, exitCode numbered, signals handled, no `exit()` outside main, juniors probe `process` instead of assuming.
