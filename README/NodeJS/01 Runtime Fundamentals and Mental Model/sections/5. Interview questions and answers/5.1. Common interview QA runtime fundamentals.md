## 5.1. Common interview QA: runtime fundamentals

### 1) **"Is Node single-threaded?" — answer in layers**

**Definition** — the precision screen: the answer is layered, and interviewers listen for the layers. Layer 1 (your JavaScript runs on one thread — no data races in application code, one call stack). Layer 2 (libuv owns a thread pool beneath it — fs, DNS, crypto parallelize off-thread; `UV_THREADPOOL_SIZE` sizes it). Layer 3 (the OS parallelizes I/O underneath that — epoll/kqueue serve thousands of idle sockets with no threads at all). Layer 4 (multi-core comes from multi-process — cluster and workers, [Domain 05](<../../../05 Child Processes Workers and Clustering/README.md>)). One sentence per layer; the single-threaded slogan retired after layer 1.

- **What problem it solves**: slogan answers fail follow-ups ("then how does it handle 10k connections?" — the candidate who said "single-threaded" has nowhere to go; the layered candidate points at the pool, then the kernel). Interviewers escalate until slogans break (blocking-JS scenario → pool-saturation scenario → multi-core scenario — each needs a different layer). Layers also diagnose production (leaf 1.1's "which box is slow?" is this answer applied to incidents — the interview skill and the on-call skill are one skill).
- **Modern guidance** — lead with the precise sentence ("one JS thread, a libuv pool beneath, the kernel beneath that, processes for cores" — fifteen words, all four layers). Attach a number per layer (pool default 4 — shows operational awareness; 10k idle connections per process — shows scale sense). Close with the consequence (CPU blocks everyone — chunk or move it; I/O scales — that's the runtime's bargain). Never say "single-threaded" without the layers that redeem it.

```javascript
// GOOD: the layered answer as runnable evidence — runs on node v20.20.2
import { cpus } from 'node:os';
console.log('layer 1 — JS threads here:', 1); // your code: one stack, no races
console.log('layer 2 — pool threads:', process.env.UV_THREADPOOL_SIZE ?? 4); // libuv: default 4
console.log('layer 3 — idle sockets: kernel-handled (no threads per connection)');
console.log('layer 4 — cores available:', cpus().length, '(one process each — see 01/6.1 boundaries for the live map)');
// BAD: "yes, single-threaded" (full answer — confident, wrong-shaped) —
// collapses four layers into a slogan; every follow-up ("then how…?") starts from rubble
```

### 2) **CJS vs ESM: which and why?**

**Definition** — the judgment question: interviewers want the trade, not the tribe. CJS (`require` — synchronous, cached, dynamic paths; cycles yield partial objects; the ecosystem's legacy majority). ESM (`import` — static, analyzable, live bindings; top-level await; cycles safe; the ecosystem's direction). The decision factors: package age (dependencies still CJS-majority at the edges — interop unavoidable), loading needs (sync config loads favor CJS; tree-shaking and static analysis favor ESM), team trajectory (new code ESM — the ecosystem converges there; migrate at boundaries, leaf 2.2).

- **Why it matters (correctness)**: tribe answers mishandle boundaries (ESM-only codebase meeting a CJS-only dependency — `ERR_REQUIRE_ESM` in production; "always CJS" meeting top-level-await needs — async factories wrapping everything). Judgment answers name the interop rules (default-import CJS then destructure — leaf 2.2; `createRequire` quarantined; `.mjs`/`.cjs` hatches). The interviewer is really asking "have you survived a mixed codebase?" — the rules prove it.
- **Modern guidance** — state the default then price the exceptions ("new code ESM for static analysis and trajectory; CJS at legacy boundaries with default-import discipline — interop rules from leaf 2.2, not ad-hoc"). Name the three failure modes unprompted (`ERR_REQUIRE_ESM`, named-from-CJS `undefined`, extensionless ESM imports — listing them signals production mileage). Mention `type` + extensions as the mapping (nearest `package.json` decides — shows you read the resolver, not just the syntax).

```javascript
// GOOD: judgment with receipts — runs on node v20.20.2
import pkg from 'node:fs'; // CJS builtin consumed the disciplined way (default, then destructure)
const { readFileSync } = pkg; // no static guessing (leaf 2.2's rule, cited live)
console.log('interop rule holds:', typeof readFileSync === 'function');
// spoken close: "ESM by default, CJS at boundaries, default-import discipline throughout —
//  the mapping (type + extension) decides, the rules (leaf 2.2) govern"
// BAD: "ESM because it's modern" (taste as argument — no trade, no boundary plan, no failure modes) —
// modern-everywhere meets the first CJS-only dependency and discovers interop at 3 AM
```

### 3) **Order this program's output**

**Definition** — the trace screen: candidates read a scheduling snippet aloud and predict the print order. The tested mechanics: sync first (call stack drains before anything), `nextTick` before promises (between-phases queue precedes microtasks), promises before timers (microtasks drain per turn), timers before immediates in main context (timers phase precedes check), immediates before timers in I/O context (check follows poll — leaf 3.1). Tracing aloud reveals the mental model (phase names used correctly) or its absence ("um, timeout first?").

- **Why it matters (liveness)**: tracers debug production ordering (why did the log line print after the response? — phase literacy; why did the server go deaf? — starvation literacy). Non-tracers cargo-cult deferrals (`setTimeout(0)` sprinkled as "async" — ordering assumed, races shipped). The whiteboard trace is the on-call diagnosis in miniature — same queues, smaller stakes.
- **Modern guidance** — narrate by queue, not by gut ("sync, then nextTick queue, then promise microtasks, then timers phase, then check — main context" — mechanism per line, never vibes). State the context dependence unprompted ("in main; inside I/O, immediate would win — leaf 3.1's deterministic case"). Practice the starvation variant too ("recursive nextTick prints forever, immediates never — liveness, not just order" — the follow-up interviewers love).

```javascript
// GOOD: the canonical trace — verify by running, then narrate (output below, node v20.20.2)
console.log('A: sync');
process.nextTick(() => console.log('B: nextTick'));
Promise.resolve().then(() => console.log('C: promise'));
setTimeout(() => console.log('D: timer'), 0);
setImmediate(() => console.log('E: immediate'));
// observed: A, B, C, D, E (main context — timers phase precedes check)
// narration: "A drains the stack; B jumps the phases; C clears microtasks;
//  D wins the phase race in main; E waits for check —
//  inside readFile's callback, E would beat D deterministically"
// BAD: memorizing A-B-C-D-E ("the answer is ABCDE" — recited, not derived) —
// the follow-up changes one line (wrap in readFile) and the recital breaks; mechanisms transfer, mnemonics don't
```

Rapid-fire drills (one sentence each — mechanism named, no essays): "timer late by 300 ms?" — loop blocked, the excess is JS-box time (leaf 3.1's proof). "`UV_THREADPOOL_SIZE=1` effect?" — pool serializes: crypto/DNS queue, loop stays healthy (wrong box to blame). "Recursive `setImmediate` vs `nextTick`?" — immediate yields per turn (alive), nextTick starves poll (deaf). "`.js` under no `type`?" — CJS (absent means commonjs; pin it explicitly anyway). "Exit code of a drained process?" — `process.exitCode`, default 0 (numbered, not forced — leaf 2.1). "Where do `fetch` globals come from?" — undici bundled with the runtime (versioned in `process.versions` — probe, don't assume).

### 4) **Common confusion**

- "Interview answers differ from production answers" — the layers *are* the runbook (single-threaded-layers diagnoses incidents; phase-tracing debugs ordering; interop rules fix 3 AM errors). Studying "interview Node" separately from "real Node" doubles the work and halves each half.
- "Tracing is trivia, not engineering" — tracing is *compressed* engineering (five lines exercising four queues — the densest possible check of scheduling literacy; engineers who trace correctly schedule correctly). Trivia is uncorrelated; traces correlate.
- " Judgment questions have right answers (ESM always)" — judgment questions have *priced* answers (ESM default with boundary costs named beats ESM-always with costs discovered). Interviewers score the pricing, not the pick.
- "Rapid-fire rewards memorization" — rapid-fire rewards *mechanism compression* (each one-liner derives from a box or phase — reciters fail the variant, derivors pass it). Compress mechanisms, not sentences.

### 5) **Performance note**

Interview performance is runtime performance retold: the layered answer prices boxes (which box saturates first under *your* workload — the senior follow-up); the CJS/ESM judgment prices startup (cold-start linking vs boot-require serialization — serverless cares); the trace prices tail latency (phase yields bound p99 — scheduling literacy *is* latency literacy). Candidates who connect each answer to a number (pool size, lag probe, cold-start budget) signal production ownership — the trait senior loops actually hire for. Mechanisms plus measurements, always.

### 6) **Mentor note**

Teach interview prep as production prep ("every question here is an incident in a suit" — map each to its leaf: layers→1.1, versions→1.2, exits→2.1, interop→2.2, phases→3.1). Drill traces aloud (whiteboard, no running — narration graded on queue-names-per-line; then run to verify — the loop closes). Drill variants, not answers (change main→I/O context, bounded→unbounded recursion — derivors adapt, reciters collapse; adapt publicly). Watch for the sloganist ("single-threaded", "ESM modern" — fix with "which layer?/priced how?") and the memorizer (ABCDE recited — fix with the readFile variant). Review check: layers with numbers, judgment with prices, traces with mechanisms, rapid-fire derived, juniors narrate before running.
