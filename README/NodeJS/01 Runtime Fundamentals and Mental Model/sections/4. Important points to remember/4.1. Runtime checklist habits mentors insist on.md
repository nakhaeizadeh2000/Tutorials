## 4.1. Runtime checklist (habits mentors insist on)

### 1) **Pin it, print it, probe it**

**Definition** — the boot discipline that prevents the entire drift class: *pin* the version (`.nvmrc` + `engines` — leaf 1.2), *print* what actually runs (`process.version` logged at startup — the pin verified, not assumed), *probe* the assumptions (feature presence, OpenSSL line, platform globals — leaf 1.2's handshake, automated). Three verbs, five seconds, zero "works on my machine".

- **Why it matters (maintainability)**: unprobed boots fail far from causes (a missing global blamed on application code — actually a stale base image; a new syntax error on CI only — actually the matrix testing an unpinned line). The startup log line is the cheapest observability in backend work (every incident starts with "which runtime?" — answered before anyone asks). Probes are onboarding too (each assert teaches one runtime fact — juniors learn the platform by reading the boot sequence).
- **Modern guidance** — assert the major at boot (compare `process.versions.node` against the documented floor — crash in line 10 with a named error, not line 10,000 with a syntax mystery). Log version + LTS codename on every start (`v24.11.0 (Krypton)` in the first log line — grep-able across fleets). Run the handshake in CI before tests (environment failures fail the *setup* step — never masquerade as test failures).

```javascript
// GOOD: boot asserts its own runtime — runs on node v20.20.2 (prints v20.20.2 / Iron)
const [major] = process.versions.node.split('.').map(Number);
if (major < 20) { console.error(`requires node >= 20, running ${process.version}`); process.exitCode = 1; }
else { console.log(`boot on ${process.version} (LTS ${process.release.lts ?? 'none'}) — floor checked, codename printed`); }
// BAD: no boot line, no floor ("the Dockerfile handles it") —
// base-image drift surfaces as mystery syntax errors; the runtime never introduces itself
```

### 2) **Exit codes are API**

**Definition** — the process's last word is a number, and supervisors read it: `0` clean (work done, loop drained — restart nothing), `1` general failure (uncaught error, missing config — restart or alert per policy), domain codes above (usage errors, unhealthy dependencies — routed differently by orchestrators and CI). The mapping is documented beside the code (README section or `--help` output — operators read docs, not sources).

- **Why it hurts when missing (correctness, operations)**: exit-zero-on-failure (a crashed worker reporting success — orchestrator scales nothing, alerts fire on symptoms minutes later; CI greens a broken build — deploys ship the failure). Exit-nonzero-on-success (a healthy cron reporting `1` — pagers wake humans for completed work; trust in alerts erodes per false page). Unnumbered deaths (`process.exit()` with no code audit — every call site invents its own semantics; operators can't route what isn't specified).
- **Modern guidance** — set `process.exitCode`, never call `process.exit()` outside fatal boot paths (drain-safe — leaf 2.1; pending telemetry flushes, logs complete). Reserve codes deliberately (`0` clean, `1` failure, `2` misuse — the sysexits-inspired trio covers most services; document any beyond). Test the codes (spawn the CLI in tests, assert `exitCode` per scenario — the contract under test, not just the happy path).

```javascript
// GOOD: numbered outcomes per scenario — verified on node v20.20.2 (exit 0 / exit 2)
// cli.mjs: const cmd = process.argv[2];
// if (!cmd) { console.error('usage: cli <cmd>'); process.exitCode = 2; } // misuse — distinct from failure
// else if (cmd === 'run') { console.log('running'); process.exitCode = 0; } // clean — drained, numbered
// BAD: `process.exit(1)` inside a helper on any error ("fail fast") —
// murders queued logs, skips graceful drains, and conflates misuse with failure in one number
```

### 3) **Schedule with phase awareness**

**Definition** — every deferral names its queue deliberately: `setImmediate` for "after I/O" follow-ups (check phase — yields to the loop), `process.nextTick` only for bounded API-contract deferrals (between phases — never recursive), timers for actual deadlines (with lateness tolerated — timers fire no earlier than asked, leaf 3.1), and workers for CPU (off the loop entirely — Domain 05, planned, see LOG). The review question per deferral: "which phase, and what happens if it recurses?"

- **Why it matters (liveness)**: phase-blind scheduling degrades under load first (works in tests, starves in production — `nextTick` recursion fine at 10 rps, deaf at 10k; `setTimeout(0)` chains drifting seconds behind under pool pressure). Liveness bugs are load-activated (invisible in CI, total in incidents — the worst discovery venue). Phase-aware code behaves identically at 1 rps and 10k (yields scale; starvation doesn't).
- **Modern guidance** — default soon-queue is `setImmediate` (safe under recursion — liveness preserved by construction). Cap every recursive pattern (counter, budget, or drain-check — unbounded soon-work is a bug wearing an optimization costume). Add the lag probe to long-lived processes (10-line interval measuring drift — the liveness instrument; alert on drift, not just on errors). Review deferrals like allocations (each `nextTick` justifies priority-over-liveness in a comment — unjustified ones become `setImmediate`).

```javascript
// GOOD: chunked CPU with yields + lag witness — runs on node v20.20.2 (finishes, exits clean — witness never holds it)
const lag = setInterval(() => { const t = Date.now(); setImmediate(() => console.log('loop lag ms:', Date.now() - t - 1)); }, 500);
lag.unref(); // witness only — never holds the process open (leaf 2.1)
let i = 0; (function chunk() { // 10k items in slices of 1k, yielding between
  const stop = Math.min(i + 1000, 10000); while (i < stop) i++;
  if (i < 10000) setImmediate(chunk); else console.log('chunked 10k with yields — loop stayed alive');
})();
// BAD: `while (i < 10000000) i++` inline per request ("simpler than chunking") —
// loop blocked for seconds per request; every concurrent client waits; lag probe screams, users leave
```

### 4) **Common confusion**

- "Checklists are for juniors" — checklists are for *load* (experts skip steps under pressure exactly when steps matter — aviation and surgery learned this; runtimes qualify). Seniority writes the checklist; everyone runs it.
- "Exit codes don't matter behind orchestrators" — orchestrators *are* exit-code readers (restart policies keyed on codes — `0` vs `1` decides backoff vs alert; Kubernetes, systemd, CI all route on numbers). Behind orchestrators, codes matter more, not less.
- "One `setTimeout(0)` chain is harmless" — harmless unloaded (tests green), harmful saturated (each link waits a full loop turn — chains stretch linearly with load; chunking with `setImmediate` has identical shape with bounded lag). Load changes the verdict.
- "Boot probes slow down deploys" — five milliseconds of asserts (versus hours of archaeology per drift incident — the cheapest insurance in the service; slow deploys come from images and migrations, never from version prints).

### 5) **Performance note**

Checklist items are performance *enablers*, not costs: pinned versions let V8 upgrades compound (free JIT gains per LTS line — leaf 1.2); numbered exits preserve tail telemetry (complete logs per deploy — profiling data exactly when performance work starts); phase-aware scheduling holds p99 under load (yields bound tail latency — the number users feel); lag probes detect regressions per deploy (drift history as a performance gate). Total runtime cost: microseconds per boot, one interval per process. Total incident cost avoided: the category of outages this domain exists to prevent. Measure the avoided class (drift incidents/quarter, starvation pages/quarter — both should read zero).

### 6) **Mentor note**

Teach the checklist as a pre-flight ritual ("read it aloud before first deploy" — ritual beats reminder; students should recite pin-print-probe unprompted). Demo each failure once (drifted version, truncated log, starved loop — three scars, permanent habits). Drill graceful shutdown as a kata (SIGTERM the example — watch it drain and number; leaf 2.1's exercise). Watch for the checklist-skipper ("I know this" — fix with the load question: "at 3 AM under page, which step do you skip first? — that's why it's written") and the over-pinner (exact-patch pins blocking security updates — fix with line-ranges: pin the line, float the patch). Review check: version pinned and printed, exits numbered and tested, deferrals phase-named, lag probe present, juniors run the handshake before debugging.
