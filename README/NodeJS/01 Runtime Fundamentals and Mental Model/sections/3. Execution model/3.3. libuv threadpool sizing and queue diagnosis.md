## 3.3. libuv threadpool sizing and queue diagnosis

### 1) **Which work uses the pool**

**Definition** — the pool from [3.1](<./3.1. The Node event loop phases in practice.md>) serves exactly the work the OS offers no async handle for: async `fs` operations, `dns.lookup` (OS `getaddrinfo` — blocking by nature), async `crypto` (`pbkdf2`, `scrypt`, `randomFill` — CPU on pool threads), and async `zlib` (compress/decompress streams off-thread). Everything else bypasses it: TCP/UDP sockets ride kernel readiness (`epoll`/`kqueue` — thousands of idle connections, zero threads), and `dns.resolve` sends DNS packets directly (c-ares, no pool thread — the lookup-vs-resolve split from [Domain 04/2.2](<../../../04 Events Networking and HTTP/sections/2. Networking/2.2. DNS and connection behavior.md>)). Misplacing work on this map misdiagnoses every queue behind it.

- **What problem it solves**: pool-blind scaling (logins hashing with `pbkdf2` at 500k iterations on 4 pool threads — 8 logins/sec ceiling with a healthy loop; the fix is workers or lighter KDF, never a bigger event loop). The mirror bug is pool-theft (CPU compute parked on pool threads — I/O queueing behind arithmetic; workers from [Domain 05/2.1](<../../../05 Child Processes Workers and Clustering/sections/2. Worker threads/2.1. Messaging and transfer.md>) exist precisely so compute never rents I/O's crew).
- **Modern guidance** — route by the map (file/DNS-crypto/zlib bursts → pool, expect queueing; sockets → kernel, expect fan-out; sustained CPU → workers, expect isolation). Prefer `dns.resolve` over `lookup` in request paths where records suffice (no pool slot consumed — one fewer queue under burst). Keep sync variants (`pbkdf2Sync`, `readFileSync`) off request paths entirely (they run on the JS thread — the worst box, blocking everything).

```javascript
// GOOD: the pool map proven in two runs — verified on node v20.20.2 (4 threads ~70–95 ms, 1 thread ~265 ms)
const { pbkdf2 } = require('node:crypto'); // pool work: 4 hashes, 100k iterations each
console.time('4x pbkdf2');
let done = 0;
for (let i = 0; i < 4; i++) {
  pbkdf2('pw', 'salt', 100000, 64, 'sha512', () => { // default pool (4): all four overlap
    if (++done === 4) console.timeEnd('4x pbkdf2'); // ~70–95 ms — parallel
  });
}
// Rerun with UV_THREADPOOL_SIZE=1 node ... — same script ~265 ms: serialized, loop healthy throughout
// BAD: `scrypt(password, salt, 64)` awaited inline per signup on pool threads ("async means non-blocking") —
// async means off-loop, not off-queue: 4 threads × 200 ms = 20 signups/sec ceiling, then queue explosion
```

### 2) **Size start-only from measurement**

**Definition** — `UV_THREADPOOL_SIZE` is read once at process startup (environment variable before `node` starts — exporting it mid-process changes nothing; the pool never resizes under a running loop). Default 4. Raising it shortens the queue for pool-bound services (crypto/zlib-heavy APIs — threads cheap, queueing expensive); lowering to 1 serializes pool work (a debugging shape — proves pool-vs-loop attribution, never a production shape). The ceiling is core count (threads beyond cores add context-switch tax — the queue moves from libuv to the scheduler). This sizes the *queue*, never the *loop* (blocked JS ignores thread count — [3.1's](<./3.1. The Node event loop phases in practice.md>) confusion entry).

- **Why it matters (capacity)**: the one-line capacity lever (an auth service at pool saturation — `UV_THREADPOOL_SIZE=8` on an 8-core box doubles crypto throughput with zero code change; the alternative is a rewrite for a queue). The mis-set lever (size 32 on 4 cores — throughput flat, tail latency worse; the incident review reads "we scaled threads, not cores").
- **Modern guidance** — set it in the deployment manifest (Dockerfile `ENV`, systemd unit, orchestrator env — versioned with the service, never shell folklore). Start from measurement (pool latency p99 under load → size up while p99 falls; stop when flat or at core count — evidence picks the number). Document the number with its reason (`UV_THREADPOOL_SIZE=8 # auth: pbkdf2-bound, 8 cores, p99 180→60 ms` — the next engineer inherits the measurement, not the magic). Never size above core count in production (oversubscription just moves the queue — workers or caching next).

```javascript
// GOOD: sizing from evidence, not hope — run under load, read p99, set once at startup
// Dockerfile (or compose/systemd env — versioned, reviewable):
// ENV UV_THREADPOOL_SIZE=8 # auth service: pbkdf2-bound, 8 cores, pool p99 180ms -> 60ms measured 2026-09
// BAD: `UV_THREADPOOL_SIZE=64` on a 4-core container ("more threads, more speed") —
// 64 threads contend for 4 cores: throughput flat, p99 worse, and the loop-blind dashboard blames Node
```

```bash
# GOOD: the attribution run — same script, two pool sizes, one conclusion
node pool-probe.js # 4x pbkdf2: ~70–95 ms (parallel — pool healthy at 4)
UV_THREADPOOL_SIZE=1 node pool-probe.js # 4x pbkdf2: ~265 ms (serialized — pool-bound, loop innocent)
```

### 3) **Diagnose the box before prescribing**

**Definition** — two probes, two boxes, no guessing (the [3.1](<./3.1. The Node event loop phases in practice.md>) rule made operational): a loop-lag probe (a 1 s `setInterval` measuring drift — drift means the JS thread is blocked) plus a pool-latency histogram (timing on pool ops — `pbkdf2`/`readFile` durations under load). Clean lag + slow pool ops = pool saturated (size the pool, cache, or move on). Lagged interval + fast pool ops = loop blocked (chunk, delegate, or worker — pool size irrelevant). Both slow = overloaded host (neither knob — capacity or shed, [Domain 07/1.2](<../../../07 Production Node Use and Interview Mastery/sections/1. Production judgment/1.2. Capacity and graceful degradation.md>)). Flame profiles that name the box live in [Domain 06/1.2](<../../../06 Debugging Configuring and Shipping/sections/1. Debugging and profiling/1.2. CPU and memory profiles with action.md>).

- **Why it matters (incidents)**: the 3 AM attribution (p99 tripled — lag probe flat, pool p99 spiking: pool box, size up and go back to sleep; lag probe drifting, pool flat: loop box, find the regex, stay up). Probes turn the war room from debate ("is Node slow?") into reading ("lag 0 ms, pool p99 400 ms — pool").
- **Modern guidance** — ship the lag probe by default (10 lines, unref'd witness per [3.2](<./3.2. Timers handles ref unref and process lifetime.md>) — drift history per deploy). Histogram pool ops at the call site (duration on crypto/fs ops — the saturation signal). Graph both on one dashboard (lag + pool p99 side by side — the box named at a glance). Prove before sizing (no probe, no pool change — tuning without instruments is superstition with syntax).

```javascript
// GOOD: the two-probe witness — verified on node v20.20.2 (drift single-digit ms idle, pool 4x ~70 ms)
const start = Date.now();
let ticks = 0;
const lag = setInterval(() => { // loop-lag probe: drift = JS thread blocked
  ticks++;
  const drift = Date.now() - start - ticks * 1000;
  if (ticks === 2) { console.log('loop drift ms:', drift, '(~0 idle; hundreds = blocked loop)'); clearInterval(lag); }
}, 1000);
// NOTE: production probes add lag.unref() per leaf 3.2 (witness only) — omitted here so the demo ticks before exiting
const { pbkdf2 } = require('node:crypto');
console.time('pool 4x'); // pool-latency probe: queue depth made visible
let n = 0;
for (let i = 0; i < 4; i++) pbkdf2('pw', 'salt', 100000, 64, 'sha512', () => { if (++n === 4) console.timeEnd('pool 4x'); });
// BAD: raising UV_THREADPOOL_SIZE because "p99 is high" with no lag probe ("threads are cheap") —
// loop-bound p99 ignores thread count: pool grows, latency stays, the deploy changes nothing but the manifest
```

### 4) **Common confusion**

- "`UV_THREADPOOL_SIZE` can be set per request" — no (read once at startup — mid-process `process.env` writes change nothing; per-request shaping belongs to queues and worker pools, not the env).
- "Sockets consume pool threads" — no (sockets ride kernel readiness — 10k idle connections cost no threads; only fs/DNS-lookup/crypto/zlib queue on the pool).
- "`dns.lookup` and `dns.resolve` cost the same" — no (lookup blocks a pool thread per call via `getaddrinfo`; resolve sends packets via c-ares — under DNS burst the difference is the queue).
- "Bigger pool fixes slow endpoints" — only pool-bound endpoints (clean lag + slow pool ops; loop-bound slowness needs chunking/workers — [3.1's](<./3.1. The Node event loop phases in practice.md>) box rule, measured not guessed).

### 5) **Performance note**

Pool costs are queue costs, priced per burst: 4 threads × 70 ms crypto = ~57 ops/sec ceiling (each extra concurrent request waits — p99 climbs linearly past saturation); sizing to 8 on 8 cores doubles the ceiling (queue halves — until cores saturate, then flat). Oversubscription costs context switches (threads > cores — scheduler thrash, p99 worse than a smaller pool). Measure-don't-guess framing: histogram pool-op latency first (p99 under representative load — the saturation signal), size second (up while p99 falls, stop at flat or core count), re-measure third (the receipt — p99 before/after in the deploy note). Pool tuning without the histogram is superstition with an env var.

### 6) **Mentor note**

Teach the map before the knob ("place each API: pool, kernel, or worker?" until students route `readFile` to pool and sockets to kernel unprompted). Demo the serialization live (same script at pool 4 vs pool 1 — 92 ms vs 267 ms on the wall clock; the queue made visible in two runs). Demo the probes together (lag flat + pool slow = name the box aloud — diagnosis as narration). Watch for the thread-maximalist ("set it to 64 everywhere" — fix with the oversubscription run: flat throughput, worse p99) and the box-blind ("slow is slow" — fix with the two-probe dashboard: lag vs pool p99 side by side). Review check: pool-bound claims carry p99 receipts, pool size versioned with its reason, compute on workers never on pool threads, lag probe present, juniors place APIs on the map before sizing.
