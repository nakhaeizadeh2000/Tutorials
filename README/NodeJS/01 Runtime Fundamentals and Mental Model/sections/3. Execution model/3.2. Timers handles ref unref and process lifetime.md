## 3.2. Timers handles, ref unref, and process lifetime

### 1) **Handles are lifetime votes**

**Definition** — every `setTimeout`/`setInterval`/`setImmediate` returns a handle object (`Timeout`/`Immediate`) that votes on whether the process stays alive: ref'd (the default — `hasRef()` true) keeps the loop running; unref'd (`timeout.unref()` — `hasRef()` false) is a witness that never blocks natural exit. The exit rule from [3.1](<./3.1. The Node event loop phases in practice.md>) is exact: between loop iterations Node checks for waiting I/O or ref'd timers, and shuts down cleanly when none remain — an unref'd 60-second interval exits in milliseconds, a ref'd one holds the process for the full minute. Timer callback mechanics (clamping, delay minimums) live in [JavaScript 13/2.1](<../../../../JavaScript/13 Async Event Loop and Promises/sections/2. Timers and scheduling/2.1. Timers setTimeout setInterval setImmediate and Node phases.md>); this leaf owns the *lifetime* half — which handles hold the door open.

- **What problem it solves**: deploy-hanging housekeeping (a metrics-flush `setInterval(30000)` left ref'd in every worker — orchestrator sends SIGTERM, the loop never drains, SIGKILL follows 30 s later, in-flight requests severed; the fix is seven characters — `.unref()` — but only lifetime literacy finds it). The symmetric bug is premature exit (a fire-and-forget `setTimeout(cleanup, 5000).unref()` with nothing else pending — the process exits before the callback, the cleanup never runs, nobody notices until the disk fills).
- **Modern guidance** — default ref'd stays for foreground work (request timeouts, response deadlines — the work the process exists to do). Unref every background-only handle (metrics flushes, cache sweeps, lag-probe witnesses — `timer.unref()` at creation, asserted with `hasRef()` in tests). Re-arm deliberately (`timeout.ref()` only after a prior `unref` — calling `ref()` on an already-ref'd handle is a no-op, not a count). Audit rule: each `setInterval` in a server must have either a `clearInterval` on the same scope or an `unref()` with a comment naming why it outlives requests.

```javascript
// GOOD: foreground ref'd, background unref'd — verified on node v20.20.2 (exits at once, not after 5 s)
const keepalive = setTimeout(() => console.log('foreground work'), 100);
console.log('foreground hasRef:', keepalive.hasRef()); // true — holds the loop (correct: work pending)
const housekeeping = setInterval(() => {}, 5000);
housekeeping.unref(); // background only — must never hold a dying process open
console.log('housekeeping hasRef:', housekeeping.hasRef()); // false — witness, exits cleanly
clearInterval(housekeeping); // same-scope teardown (audit rule: clear or unref-with-reason, here both)
// BAD: `setInterval(flushMetrics, 30000)` with no unref and no clear ("it runs in the background") —
// background holds every deploy: SIGTERM waits, orchestrator SIGKILLs, in-flight requests cut mid-response
```

### 2) **refresh, close, and clear without realloc**

**Definition** — handles carry three lifecycle verbs beyond ref/unref: `clearTimeout`/`clearInterval`/`clearImmediate` cancel the schedule (callback never fires); `timeout.close()` is the legacy alias of cancel (prefer `clearTimeout` — same effect, current name); `timeout.refresh()` resets the start clock to now and reschedules for the original duration *without allocating a new handle* (an idle-killer pattern: activity calls `refresh()`, silence lets the callback fire). `Immediate`/`Timeout` handles add `[Symbol.dispose]` (explicit cancel — call the method directly since Node 20.5+, or via the `using` keyword on Node 22+). Delay clamping (`NaN`/`<1`/`>2147483647` → `1`) is language mechanics — [JavaScript 13/2.1](<../../../../JavaScript/13 Async Event Loop and Promises/sections/2. Timers and scheduling/2.1. Timers setTimeout setInterval setImmediate and Node phases.md>).

- **Why it matters (correctness, allocations)**: refresh-vs-recreate is the idle-timeout shape (each request calls `idle.refresh()` — one handle per connection, zero churn; recreating per request allocates a handle per request — GC pressure linear in traffic). Calling `refresh()` on an already-fired timer *reactivates* it (documented, surprising — a "dead" handle starts firing again; guard with `hasRef()`/state or `close()` first when reactivation is wrong).
- **Modern guidance** — idle timeouts via `refresh` (one handle, refreshed on activity — the connection-idle pattern). One-shot cancellation via `clearTimeout` (never `close()` in new code — legacy name, same wire). Scope-bound immediates via `using` + `Symbol.dispose` where the codebase uses explicit resources (otherwise `clearImmediate` in the same scope). Never `refresh()` a timer you meant to kill (close first, then decide — reactivation by accident schedules work nobody owns).

```javascript
// GOOD: one handle, refreshed on activity — verified on node v20.20.2 (fired at ~300 ms, not 200 ms)
const start = Date.now();
const idle = setTimeout(() => console.log('idle fired after ms:', Date.now() - start), 200);
setTimeout(() => idle.refresh(), 100); // activity at 100 ms — clock restarts, fires at ~300 ms (both ref'd: demo holds the loop)
// GOOD: dispose cancels without new syntax — verified on node v20.20.2 (never fires)
const guard = setImmediate(() => console.log('never fires — disposed'));
guard[Symbol.dispose](); // explicit cancel (the `using` keyword form needs Node 22+; the method works since 20.5)
// BAD: `idle = setTimeout(onIdle, 200)` recreated per request ("refresh is confusing") —
// one allocation per request plus a clear per prior handle; under 10k rps the timer churn shows in GC profiles
```

### 3) **Shutdown interplay**

**Definition** — lifetime votes compose with the graceful-shutdown sequence from [2.1](<../2. Process and modules/2.1. The process model globals and lifecycle.md>): SIGTERM → stop accepting → drain in-flight → numbered exit. Unref'd housekeeping drops out of the drain automatically (nothing to wait for — the sequence only counts ref'd work). Ref'd work must be closed or awaited before the numbered exit (otherwise the drain hangs on its own deadline — the deploy budget from [Domain 06/3.1](<../../../06 Debugging Configuring and Shipping/sections/3. Shipping/3.1. Containers healthchecks graceful deploys.md>)). The promises timer API (`node:timers/promises`) takes the vote as an option (`{ ref: false }` — unref'd from birth; `{ signal }` — `AbortSignal` cancels into `AbortError`).

- **Why it matters (operations)**: the drain that never drains (a ref'd 30 s poll interval inside a server that "shuts down gracefully" — the 2 s deploy budget from Domain 06 fires first, `exitCode = 1` forced, the graceful path never tested clean). Unref'd-by-default promises (`setTimeout(100, value, { ref: false })` for background sleeps — never a drain participant) plus signal-cancelled foreground sleeps (`{ signal }` wired to the shutdown `AbortController` — sleeps abort when the drain starts).
- **Modern guidance** — housekeeping promises always `{ ref: false }` (background sleeps never join the drain). Foreground delays always `{ signal }` (shutdown aborts the sleep — the drain proceeds without waiting out the clock). Keep one shutdown `AbortController` per process (abort on SIGTERM — every foreground timer observes the same signal). Test the exit (spawn the service, SIGTERM it, assert exit 0 within budget — the drain asserted, not hoped).

```javascript
// GOOD: shutdown-aware sleeps — verified on node v20.20.2 (aborted sleep rejects AbortError, unref'd sleep never holds exit)
const { setTimeout: sleep } = require('node:timers/promises');
const ac = new AbortController();
async function main() {
  const bg = sleep(5000, 'bg', { ref: false }); // background — never holds the loop
  bg.then(() => console.log('bg done'), () => console.log('bg cancelled'));
  const fg = sleep(5000, 'fg', { signal: ac.signal }); // foreground — abortable by shutdown
  fg.then(() => console.log('fg done'), (e) => console.log('fg aborted:', e.name)); // AbortError
  setImmediate(() => ac.abort()); // simulated SIGTERM — drain starts, foreground sleep aborts
}
main();
// BAD: `await sleep(30000)` with no signal and default ref inside a SIGTERM handler ("wait out the retry") —
// the drain waits 30 s, the 2 s deploy budget forces exit 1, graceful shutdown exists only in the README
```

### 4) **Common confusion**

- "`unref` cancels the timer" — no (cancel is `clearTimeout`/`close`/`dispose`; `unref` only withdraws the lifetime vote — the callback still fires if the process stays alive for other reasons). Witness versus cancelled: different axes.
- "`ref()` stacks" — no (ref-counting does not exist — `ref()` after `ref()` is a no-op; `hasRef()` is boolean, not a counter. Pair each `unref` with at most one `ref`).
- "`refresh()` only works on pending timers" — no (refresh on a fired timer *reactivates* it — documented re-arm; close-then-decide when reactivation is unintended).
- "Promises timers can't be unref'd" — they can (`{ ref: false }` at creation — the option form of `unref()`; plus `{ signal }` for cancellation — votes and abort composed in one call).

### 5) **Performance note**

Handle costs are allocation costs, priced per creation: one `Timeout` object + one queue entry per `setTimeout` (microseconds — thousands concurrent fine; millions per minute pooled or hierarchically scheduled). `refresh()` avoids the reallocation (idle-timeout connections refresh in place — zero churn under sustained traffic). Unref'd handles cost nothing at exit (no drain participation — deploy latency flat). Measure-don't-guess framing: count live handles under load first (`process._getActiveHandles().length` in diagnostics — the number to graph), convert churn to refresh second (realloc rate drops), unref the background third (exit latency measured per deploy). Lifetime tuning without handle counts is superstition with syntax.

### 6) **Mentor note**

Teach votes before verbs ("does this handle keep the process alive?" before "which cancel spelling" — students reach for `hasRef()` unprompted). Demo the exit live (ref'd 5 s timer blocks the runner; `unref()` it and rerun — instant exit; vote priced in seconds). Demo refresh with timestamps (set 200, refresh at 100, read ~300 — the clock visibly restarts). Watch for the background-hold ("interval without unref or clear" — fix with the deploy story: SIGTERM, 30 s hang, SIGKILL) and the unref-and-hope ("unref'd the only work, callback never ran" — fix with the vote rule: unref'd witnesses need ref'd company). Review check: every interval has clear-or-unref-with-reason, idle timeouts refresh instead of recreate, promises sleeps carry `ref`/`signal` deliberately, shutdown path tested with SIGTERM-to-exit-0.
