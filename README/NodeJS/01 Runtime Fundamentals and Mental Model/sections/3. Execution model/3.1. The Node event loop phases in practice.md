## 3.1. The Node event loop phases in practice

### 1) **Phases order real callbacks**

**Definition** — the event loop is libuv's repeating itinerary, and every callback waits in exactly one stop: timers (expired `setTimeout`/`setInterval`), pending callbacks (deferred system callbacks), idle/prepare (internal), poll (I/O completions — files, sockets; where the loop *waits*), check (`setImmediate`), close callbacks (socket `close` handlers). Each iteration runs each phase's queue in order — so *where* a callback waits decides *when* it runs relative to others. Language-level promise mechanics live in [JavaScript 13](<../../../../JavaScript/13 Async Event Loop and Promises/README.md>); this leaf owns Node's *phase scheduling* — which queue, which order, which production consequence.

- **What problem it solves**: phase-blind code misorders work (`setTimeout(0)` assumed "next" — actually timers phase, which loses to `setImmediate` inside I/O; cleanup in the wrong phase delaying the next poll — latency added per iteration, invisible in unit tests). Ordering bugs are environment-sensitive (pass in scripts, flip under load — phases depend on *where the loop is* when you schedule). Phase literacy turns "flaky timing" into "readable schedule".
- **Modern guidance** — learn the two orderings that matter (main-module context: timers before immediates — both scheduled from sync code race by loop position; I/O context: immediates always beat `setTimeout(0)` — check runs before the next timers pass, deterministic). Schedule I/O follow-ups with `setImmediate` (runs right after poll — the phase your completion just left). Never depend on cross-phase races for correctness (same-phase FIFO is contract; cross-phase timing is weather — synchronize with promises, not phases).

```javascript
// GOOD: I/O-context ordering is deterministic — verified on node v20.20.2 (immediate always first)
const fs = require('node:fs');
fs.readFile(__filename, () => { // inside poll phase (I/O completion)
  setTimeout(() => console.log('2nd: timeout (next timers pass)'), 0);
  setImmediate(() => console.log('1st: immediate (check runs first)'));
});
// BAD: `setTimeout(fn, 0)` as "run next" everywhere ("zero means immediate") —
// zero means "next timers phase", which loses to check-phase immediates from I/O —
// "next" assumed, second place delivered, ordering bugs shipped
```

### 2) **`process.nextTick` vs `setImmediate`**

**Definition** — two "run soon" queues with opposite contracts: `process.nextTick` runs *between* phases (after the current operation, before the loop continues — highest priority, drains fully before anything else), `setImmediate` runs *in* the check phase (after poll — yields to I/O first). Consequence: recursive `nextTick` starves the loop (I/O never served — the server stops answering); recursive `setImmediate` yields per iteration (I/O served between turns — the server stays alive). Priority versus liveness, chosen per call.

- **Why it matters (correctness, liveness)**: `nextTick` recursion is a self-inflicted denial of service (each turn queues another — poll never runs, sockets pile up, health checks fail; the process looks alive and answers nothing). Framework internals use `nextTick` for *bounded* work (a handful of deferrals — safe); application code copying the idiom unboundedly inherits the starvation. The fix is one word (`setImmediate` — same "soon", with breathing room), but only phase literacy finds it.
- **Modern guidance** — default to `setImmediate` for "run soon" (yields to I/O — safe under recursion, correct under load). Reserve `nextTick` for *API-contract* cases (emitting errors after construction — `EventEmitter` constructors deferring `error` so callers can subscribe; stream internals — bounded, few, framework-owned). Cap any recursive deferral (counter or queue-drain check — unbounded soon-queues are bugs regardless of which queue). Audit for `nextTick` in hot paths during review (each occurrence must justify priority over liveness).

```javascript
// GOOD: priority where owed, yield everywhere else — verified on node v20.20.2
console.log('1st: sync');
process.nextTick(() => console.log('2nd: nextTick (between phases, before promises)'));
Promise.resolve().then(() => console.log('3rd: promise microtask'));
setTimeout(() => console.log('4th: timer (timers phase, main context)'), 0);
setImmediate(() => console.log('5th: immediate (check phase, main context)'));
// bounded nextTick: exactly N turns, then yield (starvation impossible by construction)
function drain(items, i = 0) {
  if (i >= items.length) return;
  process.nextTick(() => { items[i](); drain(items, i + 1); }); // bounded — terminates
}
// BAD: `function poll() { process.nextTick(poll); }` ("responsive polling") —
// loop never reaches poll phase: sockets starve, server deaf, CPU pinned at 100% doing nothing useful
```

### 3) **The pool behind the loop**

**Definition** — libuv's thread pool (default 4 threads, `UV_THREADPOOL_SIZE` at process start) executes what the loop must not: file I/O, DNS lookups, `crypto`/`zlib` work, and anything the OS offers no async handle for. The loop queues; threads work; completions return via poll. Two distinct failure modes: *blocked loop* (JS thread busy — nothing scheduled, everything late) versus *saturated pool* (threads busy — queued work waits, loop itself healthy). Diagnose the box (leaf 1.1) before prescribing.

- **What problem it solves**: misattributed slowness (slow `pbkdf2` blamed on "Node is slow" — actually 4 pool threads serializing CPU-bound crypto; slow requests blamed on the database — actually a 300 ms regex blocking the loop for everyone). Each mode has its own instrument (loop lag probes for the JS thread — a 1s interval measuring drift; latency histograms under pool load for saturation) and its own remedy (chunk/move CPU off the loop; size the pool or cache for saturation). Wrong box, wrong fix, second incident.
- **Modern guidance** — keep CPU off the loop (chunk long work with `setImmediate` turns — yields between slices; move heavy compute to worker threads — Domain 05, planned, see LOG). Size the pool from measurement (`UV_THREADPOOL_SIZE` up for crypto/zlib-heavy services — threads are cheap, queueing is not; never above core count — oversubscription just moves the queue). Prove the box with a lag probe (interval drift = loop blocked; clean probe + slow pool ops = pool saturated — two numbers, correct diagnosis).

```javascript
// GOOD: the blocked-loop proof in ten lines — verified on node v20.20.2 (timer ~300ms, not 100ms)
const start = Date.now();
setTimeout(() => console.log('timer fired after ms:', Date.now() - start, '(100 expected — excess is blocked loop)'), 100);
const burnUntil = Date.now() + 300; while (Date.now() < burnUntil); // BLOCKS the loop (demo only — never ship this)
// GOOD: pool parallelism observed — 4 crypto ops share 4 threads (verified, ~equal wall time)
const { pbkdf2 } = require('node:crypto');
console.time('4x pbkdf2 on pool');
let done = 0; for (let i = 0; i < 4; i++) pbkdf2('pw', 'salt', 1000, 64, 'sha512', () => { if (++done === 4) console.timeEnd('4x pbkdf2 on pool'); });
// BAD: `pbkdf2` with 500k iterations inline per login request ("bcrypt-equivalent security") —
// 4 threads × 500 ms = 8 logins/sec ceiling; queue explodes, loop healthy, everyone blames the wrong box
```

### 4) **Common confusion**

- "`setTimeout(0)` and `setImmediate` are the same" — same in main-module scripts by accident of loop position (order varies run to run); different inside I/O always (immediate wins — deterministic). Same-looking, contract-different.
- "Microtasks are just faster phases" — microtasks (`nextTick` queue, promise queue) drain *between* phases, not *as* phases (a `nextTick` flood prevents phase advance entirely — no phase can do that to another). Between versus within: starvation lives in the gap.
- "Bigger `UV_THREADPOOL_SIZE` is always better" — helps pool-bound work (crypto/zlib/DNS/file — queue shortens); does nothing for loop-bound work (blocked JS ignores thread count) and oversubscription thrashes (threads > cores = context-switch tax). Measure the box, then size.
- "The loop guarantees timer punctuality" — timers fire *no earlier than* the delay (overload pushes them late — the 100 ms timer firing at 400 ms above is contract, not bug). Deadlines need design (tolerances + lag probes), not `setTimeout` faith.

### 5) **Performance note**

Phase costs are queue costs, priced per iteration: a poll phase holding 10k socket completions (fine — that's the job) versus a timers phase holding 10k expired 1 ms intervals (churn — coalesce or back off); `nextTick` depth per turn (bounded handfuls free; unbounded recursion infinite); pool queue depth under load (the number to graph — pool latency p99 is the saturation signal). Measure-don't-guess framing: add a loop-lag probe first (10 lines — drift history per deploy), graph pool latency second (histogram on crypto/fs ops), resize third (pool size, chunking, or workers — evidence picks). Phase tuning without probes is superstition with syntax.

### 6) **Mentor note**

Teach phases as an itinerary ("walk the loop: timers, pending, poll, check, close — place each API on a stop" until students route `setImmediate` to check unprompted). Demo ordering live (run the I/O-context snippet — immediate-first every time; then the main-context race — order varies; determinism vs weather in one terminal). Demo starvation safely (bounded `nextTick` drain vs a capped 100-turn recursive version with a counter and its loop-lag readout — priority priced in latency). Watch for the zero-timer ("`setTimeout 0` means next" — fix with the I/O-context demo) and the pool-blind ("slow equals slow loop" — fix with the two-probe diagnosis: lag clean + pool slow = pool box). Review check: soon-work yields via `setImmediate`, `nextTick` bounded and justified, CPU chunked or moved, lag probe present, juniors trace callback order before running.
