## 1.2. Installing, managing, and pinning versions

### 1) **One Node per project, pinned**

**Definition** — version drift (laptop runs 22, CI runs 20, production runs 24 — same code, three behaviors) ends at the repo boundary: each project pins its Node in `.nvmrc` (or `.node-version` — read by nvm, fnm, volta, and CI setup-node alike) *and* in `package.json` `engines` (enforced at install time). The pin is a contract: every environment runs the version the code was written against, or refuses loudly.

- **What problem it solves**: unpinned projects fail mysteriously across machines (`Array.fromAsync` exists on 22+ but throws on 20 — "works on my machine" as a version gap; native addons compiled against one ABI crashing on another; lockfile churn from mixed npm versions). Debugging starts with "which node?" — pinned repos answer in one file read. The cost of pinning (one line, one file) versus the cost of drift (hours per incident, multiplied by every contributor and pipeline).
- **Modern guidance** — use a manager, never the OS package (nvm for compatibility, fnm for speed, volta for project-automatic switching — any beats `apt install nodejs`, which trails LTS by months and needs sudo per upgrade). Commit `.nvmrc` with the full semver you tested (`24.11.0`, not `24` — majors drift within lines). Set `"engines": {"node": ">=24 <25"}` *and* `"engineStrict": true` (or `.npmrc` `engine-strict=true` — refusal beats warning; warnings scroll past, refusals stop pipelines).

```bash
# GOOD: pinned and enforced — verify with the probes below
cat .nvmrc            # 24.11.0 (exact — every shell/CI resolves identically)
node --version        # v24.11.0 (matches .nvmrc — or the manager switches first)
npm ls -g --depth=0  # global surface audited (few globals — project tools stay local)
```

```jsonc
// GOOD: package.json refuses wrong runtimes (complete as-shown — paste into package.json)
{
  "engines": { "node": ">=24 <25" }, // LTS line contract (as of September 2026: 24 Active LTS)
  "engineStrict": true               // install fails loudly on mismatch — no silent drift
}
// BAD: no .nvmrc, no engines ("latest everywhere, freedom") —
// CI upgrades silently, production lags, contributors debug each other's versions
```

### 2) **LTS lines, not latest hype**

**Definition** — Node ships on two cadences: Current (a new major every 6 months — features first, support for ~6 months) and LTS (even majors promoted each October — Active for 18 months with features backported, then Maintenance for 12 months with security only). Production rides LTS (stability + security windows you can plan around); experiments ride Current (feature previews you can afford to break). Odd majors never become LTS — they are stepping stones, not destinations.

- **Why it matters (maintainability)**: Current-line production inherits churn (breaking V8/undici upgrades mid-year — dependency recompiles, addon rebuilds, surprise deprecations) and short support (security patches stop months after release — unpatched servers or forced upgrades on someone else's schedule). LTS-line production inherits calendars (end-of-life dates published years ahead — upgrades planned in quarters, not weekends). The trade is novelty versus plannability — backends choose plannability.
- **Modern guidance** — standardize on the Active LTS for services (as of September 2026: Node.js 24 Active LTS, 22 Maintenance LTS, 26 Current — new services start on 24, existing 22s plan migration before Maintenance ends). Track EOL dates, not release hype ([nodejs.org/en/about/previous-releases](https://nodejs.org/en/about/previous-releases) — calendar in planning docs, upgrades as scheduled work). Preview Current in CI matrices only (test on 26, ship on 24 — future-proof without future-risk).

```javascript
// GOOD: the runtime reports its own support story — runs on node v20.20.2
console.log(process.version); // local runtime answers first (never assume the pin held)
console.log(process.release.lts); // 'Iron' on v20 (LTS codename) — undefined means non-LTS
// maintenance check: compare process.version against the published EOL calendar —
// a one-line probe in CI beats discovering EOL during an incident
// BAD: "we run whatever the Docker base image shipped" ("pinning is bureaucracy") —
// base-image bumps become unreviewed runtime upgrades with production as the test suite
```

### 3) **Verify the install teaches the runtime**

**Definition** — every install ends with probes, not assumptions: `node --version` (binary answers), `process.versions` (every embedded component answers — v8, uv, zlib, openssl, undici), and `node -e` one-liners (behavior answers — feature presence checked live). New machine, new container, new CI image: probe first, code second. Verification is onboarding (each probe teaches one runtime fact) and insurance (each probe catches one drift class).

- **What problem it solves**: assumed installs rot silently (stale `node` shadowing the manager's via `PATH` order — `which node` disagrees with the pin; partial upgrades leaving npm from another line; containers caching a base layer two majors old). Failures surface far from causes (a missing `fetch` global blamed on code, actually Node 16 in the image). Five seconds of probes collapses hours of archaeology — the cheapest debugging in backend work.
- **Modern guidance** — probe the trio on every new environment (`which node` → location; `node --version` → line; `node -p "process.versions"` → components). Assert security-critical components (OpenSSL version for TLS work — `process.versions.openssl`; undici for fetch behavior — `process.versions.undici`). Script the probes into setup docs (copy-paste block in the repo README — every contributor runs the same five lines; CI runs them before tests).

```bash
# GOOD: the five-line environment handshake — verified on node v20.20.2
which node                       # location first (shadowing caught here, not in stack traces)
node --version                   # v20.20.2 here (compare against .nvmrc — match or switch)
node -p "process.versions.v8"    # 11.3.244.8-node.38 (engine answers — feature support derivable)
node -p "process.versions.openssl" # 3.0.19 here (TLS stack answers — audit-relevant)
node -e "console.log(typeof fetch)" # function on 18+ (behavior answers — globals probed, not assumed)
# BAD: `node server.js` as the first command on a new machine ("it'll error if wrong") —
# errors arrive as app failures, causes hide three layers down; probe the runtime, then run the app
```

### 4) **Common confusion**

- "nvm and fnm and volta — just pick latest Node instead" — managers solve *multi-project* reality (client A on 22, client B on 24 — one machine, two contracts). Latest-everywhere works for zero or one projects; professionals carry several.
- "Odd versions are fine for production" — odd majors get ~6 months of life and no LTS promotion (23 was born to die — production on odd lines buys forced upgrades). Even lines for servers, odd lines for previews.
- "`engines` is enough without `.nvmrc`" — different tools read different files (npm/yarn read `engines`; shells/CI read `.nvmrc`/`.node-version`; humans read both). Belt and suspenders: pin in both, they cost one line each.
- "Docker makes pinning redundant" — Docker *is* a pin (the `FROM node:24` line) that drifts when written loosely (`:latest`, `:24` floating patch — rebuilds change runtimes). Pin digests or exact tags; the image line is `.nvmrc` with more syntax.

### 5) **Performance note**

Version choice *is* a performance decision with receipts: each LTS line ships a newer V8 (JIT improvements compound — typical server workloads gain single-digit percent per major, free with the upgrade) and a newer undici/llhttp stack (fetch and HTTP parse paths speed measurably). But upgrades also move costs (new V8 deoptimizes old trick-code —
 microbenchmark-shaped code regresses; native addons recompile — deploy pipelines lengthen once). Measure per line (benchmark the service on 22 vs 24 in staging — adopt on numbers, not release notes), never per anecdote.

### 6) **Mentor note**

Teach pinning as the first backend habit ("before your first route: `.nvmrc`, `engines`, five probes" — environment discipline precedes code). Demo drift live (run the same snippet under two Nodes via the manager — different output, one lesson). Drill the LTS calendar (ask "which line, which phase, when EOL?" until Active/Maintenance/Current answers come unprompted). Watch for the latest-chaser ("but 26 has—" — fix with the support-window question: "who patches it in March?") and the probe-skipper (straight to `node server.js` — fix by requiring the handshake block in setup docs). Review check: `.nvmrc` exact, `engines` enforced, EOL date known, probes run before debugging, juniors pin before coding.
