## 1.1. What Node.js is and is not

### 1) **V8 plus libuv plus bindings**

**Definition** — Node.js is three pieces composed: V8 (Google's JavaScript engine — parses and JIT-compiles your JS on a single thread), libuv (the C library owning the event loop and a thread pool — timers, I/O polling, and off-thread work), and Node bindings (C++/JS glue exposing OS services — `fs`, `net`, `crypto` — to JavaScript). One thread runs *your* code; a small pool (default 4 threads) does blocking work *for* it; the loop shuttles completions back. Every production diagnosis starts from this model: slow JS blocks everything, slow I/O merely queues.

- **What problem it solves**: before Node (as of the pre-2009 era), JavaScript lived only in browsers — server work meant another language, and I/O meant one-thread-per-connection servers that paid a thread stack per idle client. Node showed evented I/O with non-blocking APIs could serve thousands of concurrent connections from one JS thread — the pool absorbs the blocking parts (file reads, DNS, crypto) while JS stays free to schedule. One language end-to-end, and connection counts decoupled from thread counts.
- **Modern guidance** — draw the three boxes before debugging anything (JS thread → loop → pool; ask "which box is slow?" first). Keep the JS box non-blocking (CPU work chunked or moved — leaf 3.1 prices the loop; workers live in Domain 05 — planned, see LOG). Treat pool saturation as a queue, not a crash (tune `UV_THREADPOOL_SIZE` only after measuring — bigger pools help crypto/zlib, never help blocked JS).

```javascript
// GOOD: ask each box what it is — verified on node v20.20.2
console.log(process.versions.v8); // V8 engine version (the JS box)
console.log(process.versions.uv); // libuv version (the loop + pool box)
console.log(typeof process.binding); // 'function' — the bindings box exists (internal API, observe don't use)
// BAD: "node is single-threaded, so nothing runs in parallel" —
// the pool (fs, DNS, crypto) and the OS (sockets) parallelize beneath your single JS thread
```

### 2) **Server-side JS without the browser**

**Definition** — Node runs the *language* without the *platform*: no `window`, no `document`, no DOM or `fetch`-as-browser-API — instead files (`fs`), sockets (`net`), processes (`process`, `child_process`), and OS details (`os`, `path`). The swap defines backend work: programs read from disks and networks instead of pages, and answer many clients instead of one user. Same syntax as frontend JS; disjoint standard library.

- **Why it matters (correctness)**: browser-shaped assumptions crash on boot (`document is not defined` — the most common first-hour Node error; `localStorage` missing; `alert` absent). Code shared between frontend and backend must depend only on the intersection (pure language — strings, arrays, JSON) or inject the platform (pass `fetch`/`fs` in — never import the wrong world). The boundary is explicit: if it touches a page, it cannot run here; if it touches a disk, it cannot run there.
- **Modern guidance** — guard shared code by capability, not by runtime sniffing (`typeof document === 'undefined'` branches rot — inject dependencies instead). Reach for `node:`-prefixed imports (`node:fs`, `node:path` — unambiguous built-ins, no dependency confusion with npm names). Verify platform claims with a one-liner before assuming (`node -e "console.log(typeof window)"` prints `undefined` — the runtime tells you what world you're in).

```javascript
// GOOD: capability-free shared code + node: imports at the boundary — runs on node v20.20.2
import { readFile } from 'node:fs/promises'; // unambiguous builtin (not an npm package)
export function summarize(text) { return text.split('\n').length; } // pure language — runs anywhere
const lines = summarize(await readFile('LOG.md', 'utf8')); // platform touch isolated at the edge
console.log('lines:', lines);
// BAD: top-level `document.title = 'x'` in a server module ("it worked in the browser") —
// ReferenceError on boot; platform code never crosses worlds unguarded
```

### 3) **Node is not a framework**

**Definition** — Node is a *runtime*: it schedules callbacks and exposes I/O — it does not route URLs, validate bodies, or structure apps. Frameworks (Express, Fastify, NestJS — own tracks later in this repo) live *above* Node and own request/response ergonomics; Node owns the loop, the loader, and the syscalls beneath. Confusing the layers misattributes failures (a slow route is framework/app code *or* a blocked loop — different boxes, different fixes).

- **Why it matters (maintainability)**: runtime-vs-framework confusion produces wrong remedies (adding middleware to fix pool saturation; upgrading Express to fix a blocked event loop; blaming Node for an N+1 query). Each layer has its own instruments (`node --inspect` and loop-lag probes for the runtime — Domain 06, planned, see LOG; route timing and validation errors for the framework — framework tracks). Name the layer before reaching for the fix.
- **Modern guidance** — learn the runtime first (this track — `http` bare server in [Domain 04/3.1](<../../../04 Events Networking and HTTP/sections/3. HTTP without frameworks/3.1. Bare nodehttp servers and clients.md>), before any framework), then add exactly one framework per service (Express for minimal, Fastify for speed, NestJS for enterprise — their tracks decide). Keep framework code off the hot path's diagnosis (reproduce slowness against bare `node:http` — if it persists, the runtime/app is slow, not the framework).

```javascript
// GOOD: bare node:http proves the runtime layer works — runs on node v20.20.2
import http from 'node:http';
const server = http.createServer((req, res) => { res.end('ok'); }); // no framework — runtime only
server.listen(0, () => { console.log('listening on', server.address().port); server.close(); });
// BAD: "our API is slow, let's switch frameworks" (before measuring) —
// unmeasured rewrites migrate the slowness; instrument the layer, then decide
```

### 4) **Common confusion**

- "Node is single-threaded so it can't use multiple cores" — one *JS* thread per process; the pool parallelizes beneath it, and multi-core comes from multi-process (cluster/workers — Domain 05). Cores via processes, not threads.
- "Node is best for everything backend" — best for I/O-bound fan-out (many idle connections, little per-request CPU); a poor default for CPU-bound work (video encoding, ML inference — blocked loop, see leaf 3.1). Match the runtime to the workload.
- "V8 version equals Node version" — V8 ships *inside* Node (`process.versions.v8` trails Chrome's V8 by integration lag); engine features arrive with Node releases, not browser releases. Check `process.versions`, never assume.
- "require/import is just style" — they are different loaders with different timing (sync-cached vs async-static — leaf 2.2 owns the rules). Style debates hide loading semantics; learn the semantics.

### 5) **Performance note**

The three-box model *is* the performance model: JS-box time blocks all clients (1 ms of regex per request at 1k rps = saturated — measure with loop-lag probes, leaf 3.1), pool-box time queues per thread (4 default threads × slow crypto = head-of-line delay — size after measuring), OS-box time scales with the kernel (epoll/kqueue handle idle connections cheaply — the free lunch evented I/O buys). Allocate optimization accordingly: profile the JS thread first (flame graphs — Domain 06), pool second (latency histograms under load), framework last (it rarely dominates).

### 6) **Mentor note**

Teach the boxes before any API ("draw V8, libuv, bindings — point at which box each new API lives in" until students place `fs.readFile` in the pool and `Array.map` in JS unprompted). Demo the browser/API swap live (`node -e "console.log(typeof window, typeof process)"` — two worlds in one line). Drill layer-naming on every bug ("runtime, framework, or app? — name it before fixing"). Watch for the single-thread absolutist ("nothing parallel" — fix with a pool demo: parallel `crypto.pbkdf2` timings) and the framework-first learner (Express before `http` — fix with the bare-server exercise above). Review check: three boxes drawable, platform boundary respected, layer named per failure, juniors probe `process.versions` instead of guessing.
