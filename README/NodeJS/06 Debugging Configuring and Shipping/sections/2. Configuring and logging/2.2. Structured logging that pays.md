## 2.2. Structured logging that pays

### 1) **JSON lines with context**

**Definition** — structured logs are JSON lines (one object per line — `level`, `msg`, `time`, plus context: `reqId`, `route`, `durationMs`; machine-parseable — grep by field, join across services, aggregate in dashboards). `console` serves development (human-readable, immediate); structured serves production (pino/winston/bunyan — levels, serializers, transports; chosen once, used everywhere). Context rides every line (request id propagated — async context or explicit passing; without it, concurrent requests interleave untraceably).

- **What problem it solves**: text-log archaeology (freeform messages — unparseable at scale; "error occurred" without which request, which user, which deploy; incidents reconstructed from vibes). Interleaved concurrency (100 concurrent requests logging identically — unattributable lines; reqId joins each line to its exchange). Level-less noise (everything `console.log` — alerts unfilterable; levels route: debug dev-only, info always, warn paging-adjacent, error paging).
- **Modern guidance** — log JSON in production (one line, one object — stdout collected by the platform; files rotated, never infinite). Carry reqId always (generated at ingress — propagated through calls; every line attributable; sampled traces join on it). Level deliberately (debug off in prod — noise gated; warn/error with action attached — every error names the remedy or the runbook). Prefer pino for hot paths (fastest JSON serialization — overhead measured in nanoseconds; the logger never the bottleneck).

```javascript
// GOOD: one line, all context, machine-parseable — runs on node v20.20.2 (valid JSON, fields present)
function log(level, msg, ctx = {}) { process.stdout.write(JSON.stringify({ level, msg, time: new Date().toISOString(), pid: process.pid, ...ctx }) + '\n'); } // JSON lines (stdout — platform collects)
log('info', 'request completed', { reqId: 'r-42', route: 'POST /upload', durationMs: 31, status: 200 }); // context rides along (joinable, aggregatable)
const parsed = JSON.parse('{"level":"info","msg":"request completed","reqId":"r-42"}'); // downstream shape (grep by field — jq '. | select(.reqId=="r-42")')
console.log('parseable:', parsed.reqId === 'r-42' && parsed.level === 'info'); // true (machines read what humans skim)
// BAD: `console.log('upload done for ' + user + ' in ' + ms + 'ms')` ("readable") —
// readable once, unparseable forever: no levels, no ids, no joins — archaeology at scale
```

### 2) **Log at boundaries, not in loops**

**Definition** — log placement discipline: boundaries emit (request in/out with ids and durations — the exchange recorded; errors with cause chains — the failure recorded; deploy markers — version lines at boot; dependency calls at warn+ — slow/failing externals visible), interiors stay quiet (loops log at debug or sampled — hot paths silent by default; per-iteration info is a throughput tax and a storage flood). Signal over noise (every production line answers "what happened to whom, how long, what now?" — lines failing the test don't ship).

- **Why it matters (operations, cost)**: log floods (per-chunk info in a stream pipeline — GBs per hour; storage billed, signal drowned; hot-path logging slowing the path itself — observer overhead). Missing boundaries (no request-out line — latency unmeasurable per route; no deploy marker — which version served this error unknown; incidents missing both ends of the story). Noisy levels (info for trivia — alerts unfilterable; warn for routine — pager fatigue; level discipline is alert discipline).
- **Modern guidance** — boundaries always (ingress/egress per request — ids + durations; errors with `cause` — chains preserved; boot/shutdown markers — version + config floor logged). Interiors sampled or debug (1-in-1000 hot-path traces — representative without flood; debug gated by env — silent in prod). Budget log volume (bytes/request estimated — storage priced; high-volume endpoints sampled; floods alarmed like any metric).

```javascript
// GOOD: boundaries recorded, interior sampled — runs on node v20.20.2 (2 boundary lines, 0 flood)
function log(level, msg, ctx = {}) { process.stdout.write(JSON.stringify({ level, msg, ...ctx }) + '\n'); }
log('info', 'request in', { reqId: 'r-7', route: 'GET /data' }); // boundary: ingress (who, where)
let sampled = 0; for (let i = 0; i < 10000; i++) { if (i % 1000 === 0) { sampled++; /* log('debug', 'chunk', { i }) — dev only */ } } // interior: silent (sampled in real code, off here)
log('info', 'request out', { reqId: 'r-7', status: 200, durationMs: 12 }); // boundary: egress (outcome, latency)
console.log('interior lines emitted:', 0, '| boundary lines:', 2, '(signal over noise — loops quiet, edges loud)');
// BAD: `on('data', c => console.log('got chunk', c.length))` ("visibility") —
// 10k lines per file, GBs per day, signal zero — visibility theater with a storage bill
```

### 3) **Drain on shutdown**

**Definition** — async log transports buffer (pino destinations, network shippers — writes queued for throughput; process exit truncates the queue — tail logs lost exactly when deploys are riskiest). Drain discipline: SIGTERM handler flushes first (`logger.flush()` awaited — leaf 2.1 of Domain 01's graceful trio; shutdown order: stop accepting → finish in-flight → flush logs → exit), sync writes for the final lines (exit-path logging synchronous — `fs.writeSync` for the last word; async after drain-begins is fiction), transport errors surfaced (failed flush logged to stderr — lost telemetry announced, not silent).

- **Why it hurts when missing (observability)**: truncated deploy evidence (last lines before restart missing — the error that caused the deploy never recorded; post-mortems start blind). Silent shipper failures (network transport down — logs dropped without alarm; monitoring the monitor skipped). Unordered shutdown (exit before flush — `process.exit()` murdering queued telemetry; leaf 2.1 of Domain 01 priced this generally, applied here specifically).
- **Modern guidance** — flush before exit (shutdown sequence ends with drain — awaited, timed out, logged; exit codes set after flush — numbered outcomes with complete evidence). Sync the finale (last lines via sync writes — guaranteed present; async transports closed first). Test the shutdown (SIGTERM the service in staging — assert tail lines present; the test earning every drain). Monitor the monitor (transport health metric — shipper failures page like any outage).

```javascript
// GOOD: drain before death — runs on node v20.20.2 (flushed lines present, exit numbered)
const fs = require('node:fs'); const LOG = '/tmp/nodeprobe/drain.log'; fs.writeFileSync(LOG, ''); // transport stand-in (buffered writer below)
let queue = []; const ship = (line) => queue.push(line); // async transport (buffered — throughput over immediacy)
async function flush() { const batch = queue; queue = []; if (batch.length) await fs.promises.appendFile(LOG, batch.join('\n') + '\n'); } // drain (awaited — evidence before exit)
ship(JSON.stringify({ level: 'info', msg: 'serving' })); ship(JSON.stringify({ level: 'info', msg: 'SIGTERM draining' }));
await flush(); // shutdown order: stop → finish → FLUSH → exit (drain before death)
const lines = fs.readFileSync(LOG, 'utf8').trim().split('\n');
console.log('tail preserved:', lines.length === 2 && JSON.parse(lines[1]).msg === 'SIGTERM draining'); // true (evidence complete)
process.exitCode = 0; // numbered after flush (outcomes with complete evidence)
// BAD: `process.on('SIGTERM', () => process.exit(0))` with buffered transport ("fast shutdown") —
// fast and blind: queued telemetry murdered; incidents without tail logs; speed at evidence's expense
```

### 4) **Common confusion**

- "More logs equal more observability" — observability equals *answerable questions* (unstructured volume answers none; structured boundaries answer most; floods drown the answers they contain). Signal, not volume.
- "console.log is fine in production" — `console` is unleveled, unshaped, synchronous-ish (fine for CLIs and boot lines; services need levels, JSON, transports; the migration is one logger module). CLIs yes, services structured.
- "Sampling loses important errors" — sampling gates *volume*, never *errors* (errors always logged — sampling applies to routine flow; warn+ bypass samplers by contract). Errors complete, routine representative.
- "Flushing slows shutdown" — flushes take milliseconds (queued lines small — bounded by volume discipline; timeout caps the wait; truncated evidence costs incidents, flush costs microseconds). Drain always, timeout sanely.

### 5) **Performance note**

Logging costs are serialization + I/O, priced per line: JSON stringify microseconds (pino faster than `JSON.stringify` — hot paths measured; the logger rarely the bottleneck — profile before blaming). Sync writes block (boot/finale only — loop impact zero elsewhere; async transports buffer — throughput preserved). Volume costs storage + attention (bytes/request × traffic — priced; floods cost both money and signal). Transports cost connections (shippers pooled — failures monitored; localhost-first, network-second). Optimize volume first (boundaries + sampling — the dominant cost), serialization second (pino where measured), transports always monitored (shipper health — the meta-metric).

### 6) **Mentor note**

Teach logging as evidence design ("which questions must production answer? — lines written to answer them" until unanswerable logs *look* unfinished). Demo the flood (per-chunk logging for 10k chunks — volume observed; then boundaries-only — signal observed; noise priced). Demo the truncation (buffered transport + `process.exit` — tail missing; then drain-first — complete; evidence felt). Drill reqId propagation ("trace r-42 end to end — which lines join?" — attribution exercised). Watch for the chatterbox ("visibility" — fix with the storage bill: bytes/request × traffic) and the exit-murderer (fast shutdown — fix with "where are the tail logs?"). Review check: JSON with context, boundaries loud + loops quiet, drains awaited, juniors join lines by reqId before guessing.
