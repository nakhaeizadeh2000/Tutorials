## 1.2. CPU and memory profiles with action

### 1) **Profile CPU, then deoptimize the hot**

**Definition** — CPU profiling (`--cpu-prof` — V8 samples the stack periodically; `.cpuprofile` opened in DevTools flame view; `--cpu-prof-name`/`--cpu-prof-dir` control output) turns "slow" into a location (widest flame boxes — where time goes; V8 deopt markers — polymorphic callsites, megamorphic loads, sparse arrays). The discipline: hypothesis first ("route X is slow" — profile route X under load, not the idle process), flame second (read the boxes — self-time, not total), change third (fix the shape — monomorphic callsites, packed arrays, moved work), re-profile proving it (before/after numbers — the receipt).

- **What problem it solves**: blind optimization (rewriting readable code for imagined hotspots — unmeasured, often pessimizing; "V8 likes" folklore applied where profiles never pointed). Deopt blindness (megamorphic callsite eating 30% — invisible in source, blazing in flame; fixed by stabilizing shapes — one-line change, double-digit win). Unproven fixes (optimized, deployed, "feels faster" — no before/after; feelings aren't benchmarks).
- **Modern guidance** — profile under production-shaped load (staging traffic replay — idle profiles lie; hot paths appear under concurrency). Read self-time (boxes wide by own work — total-time wide includes children; optimize leaves, not trunks). Fix shapes first (stable object shapes — monomorphic; packed arrays — no holes; small functions — inlinable; the V8 greatest hits). Re-profile every fix (before/after on the same load — receipts in the commit; unreceipted optimization reverted on suspicion).

```bash
# GOOD: profile captured under load, file produced — verified on node v20.20.2 (.cpuprofile written)
mkdir -p /tmp/nodeprobe/prof && printf 'let s = 0; for (let i = 0; i < 5e7; i++) s += Math.sqrt(i);\nconsole.log("sum:", s > 0);\n' > /tmp/nodeprobe/prof/busy.cjs
node --cpu-prof --cpu-prof-dir /tmp/nodeprobe/prof --cpu-prof-name hot.cpuprofile /tmp/nodeprobe/prof/busy.cjs
ls /tmp/nodeprobe/prof/hot.cpuprofile # exists (open in DevTools → flame → widest boxes first)
# hypothesis → flame → shape fix → re-profile (the loop; profiles without hypotheses are souvenirs)
# BAD: `--cpu-prof` on an idle server ("baseline") —
# idle flames show the event loop waiting; hot paths appear under load — profile the traffic, not the silence
```

### 2) **Snapshot heaps, diff the growth**

**Definition** — heap snapshots (`v8.getHeapSnapshot()` — full heap to a stream; `--heapsnapshot-signal` — on-demand via SIGUSR2; DevTools compare view — snapshot A vs B, retained size deltas named). The discipline: baseline at steady state (warm, settled — not mid-startup), exercise the suspect flow (repeat the leak-candidate N times — growth per iteration isolated), snapshot again (delta shows retainers — constructor names, paths to GC roots; the leak's address). Heap mechanics (shapes, generations, GC roots) live in [JavaScript 18](<../../../../JavaScript/18 Memory Management and GC/README.md>); this leaf owns the *service* procedure — when to snapshot, what to diff, what to change.

- **Why it matters (operations)**: slow-burn OOMs (memory climbing weekly — restarts masking; snapshots diffed across days name the retainer — cache without bounds, listener without off, timer without clear). Misattributed growth (RSS up — heap or native? snapshot sizes the JS heap; remainder is native/buffers — different tools per side). Unproven leak fixes ("maybe fixed" deploys — growth re-measured post-fix; flat lines, not hope).
- **Modern guidance** — snapshot at steady state (warmed, settled — startup allocation excluded; deltas meaningful). Drive the suspect flow in isolation (N iterations, snapshot between — per-iteration growth quantified; one variable at a time). Read retained paths (who holds whom to roots — the fix location; shallow size misleads, retained convicts). Verify flat post-fix (same procedure — growth zero across iterations; the receipt closing the incident).

```javascript
// GOOD: snapshot written, sized, parsed — runs on node v20.20.2 (file exists, megabytes, valid JSON start)
const v8 = require('node:v8'); const fs = require('node:fs');
const snap = '/tmp/nodeprobe/heap.heapsnapshot'; const out = fs.createWriteStream(snap);
v8.getHeapSnapshot().pipe(out).on('finish', () => { // stream to disk (heaps are big — never buffered whole)
  const fd = fs.openSync(snap, 'r'); const head = Buffer.alloc(15); fs.readSync(fd, head, 0, 15, 0); fs.closeSync(fd); // first bytes only (header check, not full read)
  console.log('snapshot bytes:', fs.statSync(snap).size > 1e6 ? '>1MB (real heap captured)' : 'tiny?!', '| starts:', JSON.stringify(head.toString()));
});
// procedure: baseline → exercise suspect × N → snapshot → diff in DevTools (retainers named, fix verified flat)
// BAD: single snapshot stared at ("big objects!") —
// one snapshot shows size, never growth; leaks live in deltas — snapshot twice, diff always
```

### 3) **Every profile ends in a change**

**Definition** — the profiling contract: no profile without a hypothesis (named suspect — "upload route p99"; named question — "where do the 2.4 s go?"), no finding without an action (shape fix, moved work, bounded cache — committed, not filed), no action without a re-profile (same load, same procedure — before/after numbers in the commit message). Profiles are expensive attention (engineer-hours reading flames) — spent only against decisions. Souvenir profiles (captured, admired, unactioned) are waste with file extensions.

- **Why it matters (economics)**: profile theater (flames in slide decks — no commits follow; performance acknowledged, never addressed). Unreceipted changes (optimized without before/after — regressions indistinguishable from wins; future readers can't tell improvement from churn). Hypothesis-free fishing (profiles trawled for "anything slow" — noise optimized, signal missed; questions focus, trawling diffuses).
- **Modern guidance** — write the hypothesis first (one line in the ticket — suspect + question; profiles answering unstated questions answer nothing). Commit the receipt (before/after numbers + procedure — future debuggers replay, not reinvent). Timebox the fishing (30 minutes trawling maximum — then state a hypothesis or stop; attention budgeted like compute). Close the loop publicly (incident notes name profile → change → re-profile — the record teaching the org).

```javascript
// GOOD: hypothesis, action, receipt — runs on node v20.20.2 (numbers, same procedure, committed story)
// hypothesis: "string building in the hot loop dominates" — profile → flame shows += at 40% self-time
let t = Date.now(); let s = ''; for (let i = 0; i < 20000; i++) s += 'x'; const plusMs = Date.now() - t; // before (+= shape)
t = Date.now(); const parts = []; for (let i = 0; i < 20000; i++) parts.push('x'); const joinMs = Date.now() - t + 0.001; const j = parts.join(''); // after (join shape)
console.log(`before: ${plusMs}ms (+=) | after-shape: ${joinMs.toFixed(1)}ms (join) | same length: ${s.length === j.length}`); // receipt (procedure replayable — modern V8 often ties; the method, not the winner, is the point)
// BAD: "optimized string building" with no numbers ("faster now") —
// faster how much, measured how, replayable where? Receipts or it didn't happen
```

### 4) **Common confusion**

- "Flame width equals function cost" — total-time width includes children (self-time is the function's own work — optimize leaves with wide self-time; wide trunks delegate blame downward). Leaves, not trunks.
- "One snapshot proves the leak" — deltas prove leaks (single snapshots show occupancy — growth needs two points; baseline discipline, not snapshot enthusiasm). Twice, diffed.
- "Deopts mean V8 is broken" — deopts mean shapes shifted (polymorphism introduced — code changed promises mid-loop; fix the shapes, thank the marker; deopt counters guide, never accuse). Markers, not malfunctions.
- "Profiling overhead invalidates results" — sampling overhead ~1–2% (shapes preserved — relative widths trustworthy; absolute times scaled; compare profiles relatively, never nanosecond-litigate). Relative truth.

### 5) **Performance note**

Profiling costs are attention + overhead, priced per session: sampling ~1–2% CPU (production-safe briefly — always-on profiling budgeted in capacity; snapshots stop-the-world seconds for large heaps — staging or off-peak, never mid-peak blind). Report/heap files cost disk megabytes (rotated — retention policy, not accumulation). Re-profile runs cost staging time (same load twice — the receipt's price; cheaper than unproven deploys). Optimize attention first (hypotheses before profiles — engineer-hours dominate all), overhead second (off-peak snapshots — user impact zero), receipts always (before/after in commits — future profiling starts from evidence).

### 6) **Mentor note**

Teach profiling as hypothesis-testing ("state the suspect and the question before capturing" until trawling *looks* wasteful). Demo the flame reading (widest self-time box — "what shape feeds it?" — monomorphism fix live; before/after numbers in the same session). Demo the diff (two snapshots, one leak loop between — retainer named; fix; flat re-proof). Drill receipts ("no numbers, no merge" for perf claims — culture encoded in review). Watch for the trawler ("anything slow?" — fix with "state the hypothesis") and the feeler ("faster now" — fix with "replayable procedure?"). Review check: hypotheses stated, flames read by self-time, deltas diffed, receipts committed, juniors profile under load, never idle.
