## 3.1. Containers, healthchecks, graceful deploys

### 1) **Images layered by change rate**

**Definition** — Dockerfiles ordered slowest-changing first (base image → toolchain → dependencies → source — each layer cached until its inputs change; dependency installs cached across deploys; source copied last — rebuilds take seconds). Lockfiles inside the image (`npm ci` — frozen trees shipped, never negotiated at build; `NODE_ENV=production` — dev deps omitted). Non-root user (dropped privileges — compromised processes contained; rootless by policy, not by hope).

- **What problem it solves**: slow rebuilds (source-first Dockerfiles — every deploy reinstalls everything; minutes per build, CI queues behind). Drifting images (unlocked installs at build — Tuesday's image differs from Monday's; same tag, different tree; rollbacks rolling dice). Root-by-default (compromised app with host-adjacent privilege — container escape blast radius; dropped privileges contain). Layering converts builds from minutes to seconds and images from snowflakes to artifacts.
- **Modern guidance** — copy manifests first, source last (`package.json` + lock → `npm ci` → copy source — cache hit until deps change). Pin base digests (tag + digest — base-image drift ends; rebuilds reproducible months later). Run as non-root (`USER node` — the official image ships one; file ownership set at copy — permission errors caught at build, not at 3 AM). Ignore ruthlessly (`.dockerignore` — node_modules, git, fixtures excluded; context small, builds fast, secrets unshipped).

```dockerfile
# GOOD: cached layers, frozen tree, dropped privileges (complete as-shown — build with: docker build -t svc .)
FROM node:24-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
FROM node:24-slim
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY --chown=node:node src/ ./src/
COPY --chown=node:node package.json ./
USER node
EXPOSE 3000
HEALTHCHECK --interval=10s --timeout=3s CMD node -e "fetch('http://127.0.0.1:3000/health').then(r=>{if(!r.ok)process.exit(1)})"
CMD ["node", "src/index.js"]
# BAD: `FROM node:latest / COPY . . / RUN npm install / CMD npm start` ("works locally") —
# unpinned base, unignored context, unlocked install, root user, dev deps shipped — five gaps, one file
```

### 2) **Healthchecks gate traffic**

**Definition** — two probes with different jobs: liveness (process alive — restart if failing; cheap, local) vs readiness (ready for traffic — route away while failing; checks dependencies). Orchestrators act on verdicts (unready → no traffic; unlively → restart; startup grace — slow boots not killed mid-warmup). The endpoint is honest (checks what serving needs — DB reachable, not just socket open; shallow `/health` lies under dependency outage — deep `/ready` tells truth).

- **Why it matters (operations)**: traffic to unready (deploying pods receiving requests mid-boot — 500s during every rollout; readiness gates eliminate deploy errors entirely). Dead-but-routed (wedged process with open socket — liveness shallow, traffic black-holed; deep checks catch wedges). Missing startup grace (slow cold start killed at 10 s — crash-looping healthy code; grace periods sized from measured boot, not hope).
- **Modern guidance** — split liveness/readiness (alive cheap — always; ready deep — dependencies checked; different failures, different actions). Fail closed on dependency loss (unready, not degraded-guessing — load sheds to healthy; degraded modes explicit, never accidental). Size grace from measurements (p99 boot time × 2 — cold starts survive; grace in config, reviewed per deploy). Test probes in staging (kill the DB — readiness flips; wedge the loop — liveness flips; verdicts observed, not assumed).

```javascript
// GOOD: honest probes, split verdicts — runs on node v20.20.2 (ready→200, unready→503, live→200)
const http = require('node:http');
let dbUp = true; // dependency state (checked by readiness — truth, not socket-openness)
const server = http.createServer((req, res) => {
  if (req.url === '/live') { res.end('alive'); return; } // liveness (cheap — process breathing?)
  if (req.url === '/ready') { if (dbUp) res.end('ready'); else { res.writeHead(503); res.end('no-db'); } return; } // readiness (deep — can we serve?)
  res.end('app');
}).listen(0, '127.0.0.1', async () => {
  const port = server.address().port; const get = (p) => new Promise((res) => http.get({ port, host: '127.0.0.1', path: p }, (r) => { let b = ''; r.on('data', (c) => b += c); r.on('end', () => res(`${r.statusCode}:${b}`)); }));
  console.log(await get('/ready'), '|', await get('/live')); // 200:ready | 200:alive (both green)
  dbUp = false; console.log('db down:', await get('/ready'), '| live still:', await get('/live')); server.close(); // 503:no-db | 200:alive (split verdicts — shed, don't restart)
});
// BAD: single `/health` returning 200 unconditionally ("orchestrator needs something") —
// traffic routed to wedged and depless alike; probes that can't fail are decorations
```

### 3) **Deploys drain, never drop**

**Definition** — graceful shutdown sequence (SIGTERM received → stop accepting (server.close — existing connections drain, new refused) → finish in-flight (outstanding requests complete within budget) → flush telemetry (logs/metrics drained — leaf 2.2) → exit numbered (code 0 — orchestrator proceeds to next pod)). Orchestrators grant seconds (`terminationGracePeriodSeconds` — budget configured, not defaulted; rollout sequencing — replacements ready before predecessors die). Dropped deploys are 500s with a deploy SHA attached (every rollout an incident without drains).

- **Why it hurts when missing (reliability)**: connection severing (SIGTERM → instant exit — in-flight requests cut; clients retry thundering; every deploy a mini-outage). Unready replacements (old dies before new ready — readiness gates, point 2, prevent; rollout order matters as much as drains). Telemetry gaps (exit before flush — deploy evidence truncated; leaf 2.2 priced generally, applied at rollout).
- **Modern guidance** — implement the sequence exactly (close → drain → flush → exit — order fixed; timeouts per stage — budgets from SLOs; numbered exit last). Size grace periods (p99 drain time × 2 + flush — configured per service; defaults kill slow drainers). Roll ready-first (new pods ready before old stop — surge configured; zero-downtime by sequence). Test rollouts in staging (deploy under load — zero 500s asserted; the test earning every sequence).

```javascript
// GOOD: the sequence, exactly — runs on node v20.20.2 (in-flight completes, then exit 0)
const http = require('node:http');
const server = http.createServer((req, res) => setTimeout(() => res.end('done-slow'), 150)); // slow request (in-flight during SIGTERM)
server.listen(0, '127.0.0.1', () => {
  const port = server.address().port;
  http.get(`http://127.0.0.1:${port}/`, { headers: { connection: 'close' } }, (r) => { let b = ''; r.on('data', (c) => b += c); r.on('end', () => console.log('in-flight survived:', b === 'done-slow')); }); // started pre-SIGTERM (close header: server keep-alive would otherwise hold the socket past the demo — production drains wait it out under budget)
  setTimeout(() => process.emit('SIGTERM'), 20); // the orchestrator speaks (20ms in — mid-flight)
});
process.on('SIGTERM', () => { server.close(() => { console.log('drained — exiting 0 (no drops)'); process.exitCode = 0; }); // stop accepting → in-flight finishes → numbered exit
  setTimeout(() => { console.log('drain budget exceeded — forcing'); process.exitCode = 1; }, 2000).unref(); }); // budget (drains terminate; hangs don't)
// BAD: default SIGTERM handling with 5s grace ("Kubernetes handles it") —
// default kills mid-flight; grace unconfigured; drains unimplemented — the platform provides time, code must use it
```

### 4) **Common confusion**

- "Dockerfile order doesn't matter with caching" — order *is* caching (changed layers invalidate below — source-first rebuilds everything per deploy; manifests-first rebuilds deps only on dep change). Slowest-changing first, always.
- "One healthcheck suffices" — liveness ≠ readiness (restart vs shed — different failures, different actions; one probe conflates; wedged-but-alive needs split verdicts). Two probes, two jobs.
- "Graceful shutdown is the orchestrator's job" — orchestrators grant *time* (code performs the sequence — close, drain, flush, exit; unimplemented handlers waste granted seconds). Time granted; sequence coded.
- "`latest` tags are fine internally" — floating tags drift rebuilds (same tag, different base — CVE posture unknowable; digests pin — reproducible months later). Pin everything shippable.

### 5) **Performance note**

Shipping costs are build time + rollout safety, priced per deploy: layered builds cache to seconds (deps unchanged — source-only rebuilds; unlayered minutes per deploy — CI queues behind). Healthchecks cost a request per interval (negligible — cheap endpoints; deep readiness slightly more — worth every microsecond). Graceful drains cost seconds per rollout (in-flight completing — zero 500s; the cheapest reliability there is). Non-root costs nothing (flag-level — security free). Optimize build caching first (layer order — the minutes lever), rollout sequencing second (ready-first — the errors lever), grace budgets always (drain time — the drops lever).

### 6) **Mentor note**

Teach shipping as sequence ("close, drain, flush, exit — recite per service" until instant-exit *looks* violent). Demo the drop (SIGTERM mid-flight without handler — request severed; then sequenced — completes; drains felt). Demo the split verdict (DB killed — readiness 503, liveness 200; shed vs restart observed). Drill layer order ("why is source last?" — cache invalidation explained per line). Watch for the default-accepter ("platform handles it" — fix with "show me the handler" — absent) and the single-prober ("one /health" — fix with "wedged-but-listening?"). Review check: layers ordered, probes split, drains sequenced, grace sized, juniors test rollouts under load before declaring done.
