## 6.1. Boundaries: what is covered elsewhere

### 1) **Streams and bytes**

**Definition** — this domain owns the *conversation* (events, sockets, HTTP exchanges); the *data path* underneath lives in [Domain 03](<../../../03 Files Streams and Buffers/README.md>) and is assumed, never re-taught. Pipeline lifecycle and teardown → [Domain 03/2.1](<../../../03 Files Streams and Buffers/sections/2. Streams and pipelines/2.1. Readable writable and transform.md>) (socket relays pipeline identically — no socket-specific lifecycle invented here). Backpressure protocol → [Domain 03/2.2](<../../../03 Files Streams and Buffers/sections/2. Streams and pipelines/2.2. Backpressure and stream errors.md>) (fast senders paced the same over TCP — no network-specific pacing invented here). Binary framing → [Domain 03/3.1](<../../../03 Files Streams and Buffers/sections/3. Binary data/3.1. Buffers encodings and binary truth.md>) (wire parsing by spec — no socket-specific framing invented here). Data questions route in one line.

- **What problem it solves**: double-teaching (backpressure re-explained per socket leaf — copies drifting; framing re-derived per protocol — contradictions accumulating). Single source of truth keeps every copy fresh (one definition, many links — updates land once). Readers navigate faster too (pacing confusion routes to 03/2.2 in one click — no HTTP leaf wastes pages re-deriving drain).
- **Modern guidance** — when a question reduces to streams or bytes, link out in one line (never re-derive — "pacing: [03/2.2]" then continue with the conversation point). When a Domain 03 reader arrives here, the prerequisites (domain index §0) tell them what's assumed — no surprise dependencies. Propose data-path corrections upstream (errors in 03 fixed there — never patched by local restatement).

### 2) **Design and testing depth**

**Definition** — this domain owns runtime *use* (subscribe, dial, serve); *design judgment* and *test technique* live in their own tracks. Observer pattern as design (subject/observer roles, push/pull, decoupling economics) → [Design Patterns 04/2.1](<../../../../DesignPatterns/04 Behavioral Patterns Command and Control/sections/2. Requests and notifications/2.1. Observer subscribe and notify.md>) (this domain's emitters assume the pattern — never re-justify it). Testing emitters and async timing (fake timers, determinism, flake hygiene) → [JavaScript 20/4.1](<../../../../JavaScript/20 Testing and Tooling Essentials/sections/4. Async timing and flake control/4.1. Testing promises async await event emitters and rejections.md>) (this domain's probes assume testability — never re-teach it). Use questions stay here; design and test questions route out.

- **Why it matters (maintainability)**: the use/design/test split prevents misplaced depth (pattern trade-offs re-argued in a socket leaf — stale within a refactor; timer-mocking re-derived in an emitter leaf — two copies, one rots). Each side links the other (emitter misuse rooted in pattern confusion routes precisely — "decoupling economics: [Patterns 04/2.1]" — instead of guessing). Boundaries make all three sides shorter and more accurate.
- **Modern guidance** — use here, design and test there (an emitter question about *coupling* routes to Patterns; about *flaky timing* routes to JS 20; about *API behavior* stays). Quote the boundary in reviews ("use-side fix" vs "design-side fix" vs "test-side fix" — different venues, different owners). Keep this domain's pattern coverage consumer-shaped (owned emitters, documented surfaces — leaf 1.2; decoupling economics — Patterns 04/2.1).

### 3) **Frameworks and deeper Node**

**Definition** — this domain stops at bare `node:http` deliberately: request routing, middleware, validation, and app architecture → the framework tracks (Express for minimal, Fastify for speed, NestJS for enterprise — each composes atop bare mechanics; this domain's leaf 3.1 is the foundation they assume). Remaining runtime depth: child processes, workers, and clustering → [Domain 05](<../../../05 Child Processes Workers and Clustering/README.md>) (cores via processes — parallelism beyond the loop); debugging, configuring, and shipping → [Domain 06](<../../../06 Debugging Configuring and Shipping/README.md>) (inspect, env, deploys — conversation observability in production); production synthesis and interviews → [Domain 07](<../../../07 Production Node Use and Interview Mastery/README.md>) (the track's capstone). Each owned there (planned, see LOG — full coverage lands with those domains).

- **Why it matters (operations)**: layer confusion misroutes learning (Express middleware studied to understand sockets — framework code *uses* emitters without *teaching* them; worker threads reached for before socket tuning — parallelism before pacing). Clean layers learn faster (bare servers, then frameworks; sockets, then workers — each in its venue, each assumed by the next).
- **Modern guidance** — read in `NN` order (on-disk prefixes are curriculum order — 04 before 05, always). Treat textual forwards as promises, not placeholders (each names its owning domain — when the domain lands, links upgrade; until then, the name scopes the question). Record cross-domain fixes at the boundary (an emitter bug found while writing workers gets fixed in 04/1.1 and linked — never duplicated into 05).
