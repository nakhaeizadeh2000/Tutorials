## 1.2. Event patterns beyond basics

### 1) **Once and prepended order**

**Definition** — ordering tools for intent: `once()` subscribes single-fire (initialization, first-connection, handshake completion — auto-removed after firing; never-fired `once` still leaks, scope cleanup applies), `prependListener()`/`prependOnceListener()` insert at the front (middleware-style ordering — auth before handler, validation before processing), `listenerCount()`/`eventNames()` introspect (budgets enforced programmatically — the tripwire as code). Order declared in API calls, never in comments hoping readers comply.

- **What problem it solves**: ordering-by-luck (auth registered after the handler it guards — works until someone reorders imports; one-time setup with `on` + manual flag — flags forgotten, setup runs twice, connections double). Explicit ordering survives refactors (prepend states priority — immune to registration shuffling); `once` retires flags (single-fire by construction — no boolean to forget). Introspection makes budgets testable (count asserted in tests — growth caught before production).
- **Modern guidance** — `once` for single-fire by nature (handshakes, first-ready, one-shot migrations — nature, not discipline). `prepend` for guard-before-action (validation, auth, circuit checks — priority stated, not hoped). Assert counts in tests for high-volume emitters (listenerCount after setup — expected number encoded; drift fails the test, not the quarter). Remove never-fired `once` on teardown (scope cleanup covers both — `off` the reference regardless).

```javascript
// GOOD: order stated, single-fire constructed — runs on node v20.20.2
const { EventEmitter } = require('node:events');
const bus = new EventEmitter(); const order = [];
bus.on('req', () => order.push('handler')); // registered first (runs second — priority elsewhere)
bus.prependListener('req', () => order.push('guard')); // priority stated (runs first, always)
bus.once('boot', () => order.push('boot-once')); // single-fire (second emit silent)
bus.emit('boot'); bus.emit('boot'); bus.emit('req');
console.log(order.join(' | '), '| listeners:', bus.listenerCount('req')); // boot-once | guard | handler | listeners: 2 (guard + handler)
// BAD: `let booted = false; on('boot', () => { if (!booted) { booted = true; ... } })` ("explicit control") —
// flags forgotten, copied, inverted; `once` retires the whole category
```

### 2) **Async listeners decoupled**

**Definition** — `emit` never awaits (async listeners *start* synchronously during emission, then race independently — completion order unordered, errors escaping to unhandled rejections, not to the emitter's `error` channel). The decoupling is total: emission finished ≠ handling finished (post-emit code runs before handlers complete); handler errors bypass `error` listeners (async throw → rejection — the emitter never sees it). Async handlers need explicit capture (try/catch inside → route to `error` manually, or handler wrappers doing it uniformly).

- **Why it matters (correctness)**: awaited-emit assumptions (post-emit assertions on handler side effects — racing, flaky; "emit then read the result" — result pending). Lost async errors (unhandled rejections crashing modern Node — the throw that bypassed every `error` listener; silent in older defaults — failures vanishing). Ordering illusions (two async handlers assumed sequential — concurrent; shared-state mutations interleaving). Emission synchrony misleads exactly where handlers go async.
- **Modern guidance** — never depend on handler completion post-emit (emit is notification, not invocation — results via callbacks/promises the handler resolves, not via emit's return). Wrap async handlers uniformly (a helper try/catching into `emitter.emit('error', e)` — one wrapper, every handler; or per-handler try/catch where classification differs). Handle rejections at the process level as backstop (`unhandledRejection` logging — the net beneath the net; leaf 2.1 of Domain 01's discipline, applied). Prefer explicit task queues for ordered async work (emitters notify, queues sequence — different tools).

```javascript
// GOOD: decoupling observed, errors captured — runs on node v20.20.2 (emit-first, routed-error, exit 0)
const { EventEmitter } = require('node:events');
const bus = new EventEmitter(); const seq = [];
bus.on('work', async (x) => { try { await new Promise((r) => setTimeout(r, 30)); if (x < 0) throw new Error('bad input'); seq.push(`done:${x}`); } catch (e) { bus.emit('error', e); } });
bus.on('error', (e) => seq.push(`routed:${e.message}`)); // async errors routed manually (emitter never sees them)
bus.emit('work', 1); bus.emit('work', -1); seq.push('emit-returned'); // emission done, handlers pending
setTimeout(() => console.log(seq.join(' | ')), 80); // emit-returned | done:1 | routed:bad input (decoupled, captured)
// BAD: `emit('save', doc); assert(savedToDb(doc))` ("emit is synchronous, so handlers ran") —
// sync dispatch, async handlers: assertion races the handler; green sometimes, red under load
```

### 3) **Emitters as boundaries**

**Definition** — module-owned emitters with documented surfaces: internal events stay internal (state-change notifications consumed within the module — no external subscribers assumed), public events documented like API (names, payload shapes, error semantics — the emitter as interface), cross-module flow via explicit channels (returned emitters, injected buses — never globals). The Observer pattern's design discipline lives in [Patterns 04/2.1](<../../../../DesignPatterns/04 Behavioral Patterns Command and Control/sections/2. Requests and notifications/2.1. Observer subscribe and notify.md>); this point is its runtime enforcement — who may subscribe to what, decided per module.

- **Why it matters (maintainability)**: global-bus spaghetti (everything emits everything — subscribers unknown, ordering accidental; renaming an event breaks silent consumers three packages away; debugging via grep across the repo). Undocumented payloads (shape changed — consumers crash on missing fields; no contract to check against). Leaked internals (refactor renames an internal event — external code subscribed; encapsulation broken by notification). Boundaries make events reviewable (surface listed, subscribers known, renames safe).
- **Modern guidance** — return or inject emitters, never globalize (module creates, caller subscribes — ownership visible; shared buses passed explicitly, documented). Document the event surface (README section per public emitter — names, payloads, error channel; changes reviewed like API changes). Keep internal events private (symbol-named or closure-scoped where truly internal — subscription impossible by construction). Prefer return values/promises over events for 1:1 flows (events serve 1:N notification — request/response over emitters is coupling in disguise).

```javascript
// GOOD: owned emitter, documented surface — runs on node v20.20.2
const { EventEmitter } = require('node:events');
function createQueue() { const bus = new EventEmitter(); bus.on('error', () => {}); // owned (not global)
  let n = 0; return { push(x) { n++; bus.emit('item', x); }, // public: 'item' (payload: the item)
    size: () => n, onItem: (fn) => bus.on('item', fn) }; } // surface minimal (subscribe via method, internals hidden)
const q = createQueue(); const got = []; q.onItem((x) => got.push(x)); q.push('a'); q.push('b');
console.log('received:', got.join(','), '| size:', q.size()); // a,b | 2 (boundary respected, surface tiny)
// BAD: `global.bus = new EventEmitter()` ("easy cross-module events") —
// subscribers unknowable, renames ungreppable, payloads uncontracted — the bus to nowhere good
```

### 4) **Common confusion**

- "`emit` waits for async listeners" — dispatch sync, handlers decoupled (post-emit code precedes handler completion — always; awaiting needs explicit promises, not emission). Notification, not invocation.
- "`once` + `emit` = request/response" — 1:1 over events is disguised coupling (no timeout, no correlation, no backpressure — promises/queues serve request/response; events serve broadcast). Shape matches purpose.
- "Prepend fixes all ordering" — prepend orders *registration priority*, not *async completion* (two prepended async handlers still race; ordering dispatch ≠ ordering results). Priority stated, results still concurrent.
- "Private emitters can't leak" — closure emitters leak via subscribers (external `on` without `off` pins the closure — ownership of cleanup stays with the subscriber; document removal, enforce budgets). Privacy bounds surface, not retention.

### 5) **Performance note**

Advanced patterns cost nothing structural (prepend is array unshift — registration-time; `once` wraps once — dispatch identical; introspection iterates listeners — test-time only). Async decoupling costs coordination (unawaited handlers need capture wrappers — lines, not cycles; unhandled rejections cost crashes — the expensive kind). Boundary discipline costs indirection (method-wrapped subscription — one call deep; documented surfaces — reading time repaid in refactor safety). Optimize handler work (the payload, always), never dispatch mechanics (nanoseconds beside handler milliseconds); optimize coupling (boundaries reduce blast radius — the incident cost that dwarfs cycles).

### 6) **Mentor note**

Teach ordering as declaration ("show me where priority lives — in calls or in hope?" until `prepend` answers guard-before-action). Demo decoupling live (emit with slow async handler, push post-emit marker — marker first, every time; then the assertion-race version — flaky on demand; notification vs invocation in one terminal). Drill error capture (async handler throwing unguarded — unhandled rejection; then wrapped — routed; the bypass felt). Watch for the emit-awaiter ("handlers ran" — fix with the marker demo) and the global-buser ("easy" — fix with "name all subscribers" — silence follows). Review check: single-fire constructed, guards prepended, async captured, emitters owned, juniors narrate dispatch-vs-completion before asserting.
