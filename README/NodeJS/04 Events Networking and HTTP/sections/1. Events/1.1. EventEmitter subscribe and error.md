## 1.1. EventEmitter subscribe and error

### 1) **Subscribe, emit, clean up**

**Definition** — `EventEmitter` is Node's in-process notification bus: `on(name, fn)` subscribes (ordered — listeners run in registration order), `emit(name, ...args)` notifies (synchronous — every listener runs before `emit` returns; no awaiting, no queueing), `off`/`removeListener` unsubscribes (ownership released — references dropped, GC allowed). The Observer *design* lives in [Design Patterns 04/2.1](<../../../../DesignPatterns/04 Behavioral Patterns Command and Control/sections/2. Requests and notifications/2.1. Observer subscribe and notify.md>); this leaf owns the *runtime mechanics* — timing, ordering, and cleanup of Node's emitter.

- **What problem it solves**: decoupled notification without polling (request lifecycle events, progress reports, plugin hooks — producers emit without knowing consumers; consumers react without owning producers). Synchronous emission keeps causality readable (emit → all reactions complete → continue — stack-traceable, debuggable). Explicit cleanup prevents the slowest leak class (forgotten listeners pinning whole object graphs — servers growing per request until OOM).
- **Modern guidance** — subscribe with named functions where removal matters (anonymous listeners can't be `off`'d — `off` needs the same reference). Emit with the payload consumers need (event name + data args — no reaching back into producer state). Clean up symmetrically (every `on` in setup has an `off` in teardown — connection-scoped listeners die with the connection; review pairs them like braces).

```javascript
// GOOD: ordered, synchronous, cleaned — runs on node v20.20.2
const { EventEmitter } = require('node:events');
const bus = new EventEmitter(); const order = [];
const a = (x) => order.push(`a:${x}`); bus.on('job', a); // named (removable later)
bus.once('job', (x) => order.push(`once:${x}`)); // single-fire (auto-removed after first)
bus.emit('job', 1); bus.emit('job', 2); // synchronous (both emissions fully reacted before next line)
bus.off('job', a); bus.emit('job', 3); // unsubscribed (no reaction — cleanup honored)
console.log(order.join(' | ')); // a:1 | once:1 | a:2 (ordered, once-fired, cleaned)
// BAD: anonymous `on` per request with no `off` ("GC handles it") —
// emitter holds the closure; closure holds the request; requests accumulate — the leak that graphs beautifully
```

### 2) **Errors are terminal events**

**Definition** — `error` is the emitter's reserved channel: emitting `error` with no listener throws (the error escapes as an exception — crashing the process if uncaught); with a listener, it routes (centralized failure handling per emitter). This makes error-silent emitters impossible by construction (unlike rejected promises without handlers — emitters refuse to swallow). Every emitter gets an `error` listener at construction — the rule with no exceptions.

- **Why it hurts when missing (reliability)**: routine crashes on routine events (socket reset — `error` emitted; no listener — process dies on a normal network occurrence; the incident is a missing three-line handler). Swallowed failures in custom emitters (domain errors emitted as data events — consumers never check; corruption flows downstream as success). The `error` contract converts both into routed, logged, handled failures — boring by design.
- **Modern guidance** — attach `error` at construction (before any operation can emit — race-free; factory functions wire it before returning). Route, don't just log (emitter errors classify: retryable → retry queue; fatal → shutdown path — leaf 2.1 of Domain 01's exit discipline, applied). Test the error path (emit `error` in tests — assert routing, assert no throw; the test earning every listener).

```javascript
// GOOD: error routed, process alive — verified on node v20.20.2 (exit 0 with listener, exit 1 without)
const { EventEmitter } = require('node:events');
const guarded = new EventEmitter(); guarded.on('error', (e) => console.log('routed:', e.message)); // listener first
guarded.emit('error', new Error('socket reset (routine)')); // handled (no throw — boring reliability)
// Equivalent unguarded emitter crashes: `node -e "require('node:events').EventEmitter"` + emit error, no listener → throws, exit 1
// BAD: `.on('data', ...)` with no `.on('error', ...)` ("errors are rare") —
// rare × connection-count = routine; unguarded emitters convert routine networks into crashes
```

### 3) **Leaks warned, not prevented**

**Definition** — Node warns (not errors) past 10 listeners on one event (`MaxListenersExceededWarning` — a tripwire, not a wall): legitimate fan-out exceeds it (broadcast buses with dozens of subscribers — `setMaxListeners(n)` documents the budget), and leaks exceed it silently-growing (per-request listeners never removed — the count climbs per connection; the warning names the event and the count). The warning is a review prompt: budget legitimate growth, fix unbounded growth.

- **Why it matters (operations)**: listener leaks grow with traffic (each connection adds, none remove — memory climbs linearly with requests; the graph every on-call engineer recognizes too late). The default-10 tripwire catches them early (first warning in staging — investigated in minutes; ignored warnings in production — OOM in weeks). Budgets document intent (`setMaxListeners(50)` with a comment — fifty expected, fifty-first investigated).
- **Modern guidance** — keep the default where unexamined (10 trips early — the tripwire working). Set explicit budgets where fan-out is designed (`setMaxListeners` with a comment naming the expected count — documented growth). Investigate every warning as a leak until proven fan-out (count vs connections correlated — linear growth is the leak signature; flat is fan-out). Prefer `once`/scoped listeners for per-unit work (auto-cleanup — the leak class retired by API choice).

```bash
# GOOD: tripwire observed, budget set — verified on node v20.20.2 (warning printed, then silenced by budget)
node -e "const e = new (require('node:events'))(); e.on('x', () => {}); e.on('x', () => {}); e.setMaxListeners(1); e.on('x', () => {});" 2>&1 | head -2 # MaxListenersExceededWarning (tripwire fires)
node -e "const e = new (require('node:events'))(); e.setMaxListeners(50); console.log('budget:', e.getMaxListeners());" # 50 (documented growth — comment why in real code)
# BAD: `emitter.setMaxListeners(0)` globally ("warnings are noise") —
# the tripwire disabled project-wide; leaks grow silently; the OOM arrives without its early warning
```

### 4) **Common confusion**

- "Emit is async" — `emit` is fully synchronous (all listeners complete before return — ordering guaranteed, errors propagate to the emitter's try/catch; async listeners *start* synchronously and race after). Sync dispatch, async handlers — different clocks.
- "`once` prevents leaks" — `once` auto-removes *after firing* (never-fired `once` leaks like `on` — connection-scoped single-fire events that never occur accumulate; scope cleanup still required). Fired-once cleaned; unfired identical to `on`.
- "More listeners slow emission linearly — avoid emitters" — dispatch cost is a function call per listener (nanoseconds — the bottleneck is always handler work, never dispatch; profile handlers, never the bus). Plumbing free, payloads priced.
- "`error` listener makes failures silent" — listener *routes* (log + classify + act — silence is a handler choice, not a contract outcome; unhandled throws loudly). Routing beats both swallowing and crashing.

### 5) **Performance note**

Emitter costs are dispatch costs, priced per emit: listener calls at function-call speed (nanoseconds each — thousands of listeners still sub-millisecond; the budget question is memory, never CPU). Argument passing by reference (no copies — large payloads cheap; mutation shared — document ownership). Leak cost is retention (pinned closures × traffic — the only emitter cost that ever mattered; tripwire + budgets retire it). Optimize by scoping (connection listeners die with connections — retention bounded), budgeting (maxListeners documented — growth reviewed), and handler profiling (slow handlers, not slow buses) — never by avoiding emitters (the alternative is polling or coupling, both worse).

### 6) **Mentor note**

Teach emitters as contracts ("subscribe, emit, clean up — recite per emitter" until `off` appears beside every `on` unprompted). Demo synchronicity live (emit with three listeners pushing to an array — order printed; then an async listener — started-sync, finished-later; two clocks in one terminal). Demo the crash (unguarded `error` emit — process dies; then guarded — routed; three lines preventing an outage). Drill leak recognition (per-request `on` without `off` — count climbs; tripwire fires; budget-vs-fix decision). Watch for the anonymous-subscriber ("GC handles it" — fix with the retention graph) and the tripwire-muter (`setMaxListeners(0)` — fix with "which leak will you miss first?"). Review check: errors listened at construction, cleanups paired, budgets documented, juniors predict emission order before running.
