## 2.2. DNS and connection behavior

### 1) **Lookup before connect**

**Definition** — name resolution precedes every dial, via two APIs with different contracts: `dns.lookup()` (OS resolution — `/etc/hosts`, NSS, then DNS; honors search domains and `verbatim` ordering; what `net.connect('localhost')` uses internally) versus `dns.resolve*()` (direct DNS records — A/AAAA/MX/TXT bypassing hosts; what service discovery and verification need). Dual-stack reality: `localhost` may resolve to `::1` first (IPv6 — refused when the server bound IPv4-only; the classic "works with 127.0.0.1, fails with localhost"). Resolution fails independently of connection (DNS down ≠ service down — classify before retrying).

- **What problem it solves**: localhost-vs-127.0.0.1 mysteries (server on IPv4, client resolving IPv6 first — `ECONNREFUSED` on a running service; fixed by binding dual-stack or resolving explicitly, never by "restarting"). Hosts-file surprises (staging overrides in `/etc/hosts` — `lookup` honors, `resolve` ignores; debugging with the wrong one denies the override exists). DNS-failure misclassification (resolve fails — retrying the *connection* hammers a healthy service for a DNS problem; classify the layer, back off the right one).
- **Modern guidance** — resolve explicitly where families matter (`lookup(host, { family: 4 })` for IPv4-only estates — determinism over versatility; `verbatim: true` preserving resolver order where configured). Bind dual-stack by default (`::` with `ipv6Only: false` — both families served; single-family binding is a documented exception). Separate DNS errors from dial errors (resolve step distinct — different metric, different alert, different backoff).

```javascript
// GOOD: resolution interrogated before dialing — runs on node v20.20.2 (localhost → loopback, family named)
const dns = require('node:dns').promises;
const v4 = await dns.lookup('localhost', { family: 4 }); // OS path, IPv4 pinned (deterministic for v4 estates)
console.log('localhost v4:', v4.address); // 127.0.0.1 (no network needed — hosts/NSS answer)
try { await dns.lookup('nonexistent.invalid'); } catch (e) { console.log('DNS fails distinctly:', e.code); } // ENOTFOUND (classify: resolution, not connection)
// BAD: `connect('localhost')` + "connection refused??" (family unexamined) —
// server on 127.0.0.1, resolver offering ::1 first; the fix is binding or family, never volume
```

### 2) **Retries with backoff, timeouts always**

**Definition** — every dial carries two policies: a deadline (timeout — no unbounded connects; `ETIMEDOUT`/`abort` past budget; hanging dials are leaked intent) and a retry schedule (exponential backoff with jitter — 100 ms → 200 ms → 400 ms + random spread; jitter desynchronizes thundering herds; max attempts or max elapsed — retries terminate). Retryable classified (refused/reset/timeout — transient; auth/validation — permanent, never retried). Unbounded retries are a self-inflicted DDoS (outage + retry storm = extended outage).

- **Why it matters (operations)**: retry storms amplify outages (every client retrying instantly — 10× load on a recovering service; jittered backoff spreads the wave; caps bound the multiple). Hanging dials accumulate (no timeout — descriptors held per attempt; slow-burn exhaustion under partial outages). Permanent-error retries waste and confuse (401 retried 5× — logs full of expected failures; auth failures fail fast, loudly, once).
- **Modern guidance** — timeout every dial (connect timeout 3–10 s typical — budget from dependency SLOs, not hope). Back off exponentially with jitter (base × 2^n + random — herd desynchronized; cap attempts (3–5) or elapsed (30 s) — retries terminate, pages fire instead). Retry transient only (`ECONNREFUSED`/`ETIMEDOUT`/`ECONNRESET` — yes; `EACCES`/auth/validation — no, fail fast). Log attempts with cause (attempt n/m + error code — retry visibility in incidents, not mystery load).

```javascript
// GOOD: bounded retries, jittered, timed — runs on node v20.20.2 (3 attempts, ~70ms total, then surfaces)
async function dial(port, { attempts = 3, base = 10 } = {}) {
  const net = require('node:net'); let last;
  for (let i = 0; i < attempts; i++) {
    try { await new Promise((res, rej) => { const s = net.connect(port, '127.0.0.1'); s.on('error', rej);
      s.setTimeout(500); s.on('timeout', () => rej(new Error('ETIMEDOUT-ish'))); s.on('connect', () => { s.end(); res(); }); }); return `connected attempt ${i + 1}`; }
    catch (e) { last = e; await new Promise((r) => setTimeout(r, base * 2 ** i + Math.random() * base)); } // backoff + jitter (herd-safe)
  } throw last; // terminate (cap reached — page, don't loop)
}
console.log(await dial(1).catch((e) => `surfaced after cap: ${e.code ?? e.message}`)); // port 1 refused (fast-fail, bounded)
// BAD: `while (true) { try { connect() } catch { await sleep(1000) } }` ("resilient client") —
// unbounded fixed-interval retries: herd-synchronized, outage-amplifying, pager-silent — resilience theater
```

### 3) **Keep-alive and pooling preview**

**Definition** — connection reuse economics: establishing TCP (+TLS) costs handshakes (milliseconds per connection — latency tax per request if redialed); keep-alive reuses (socket held past one response — subsequent requests skip handshakes); agents pool (N sockets shared across requests — concurrency without redial; `maxSockets` bounds the pool; idle eviction reaps). HTTP agents (`http.Agent`/`undici.Agent`) implement the policy; the application sets the numbers from capacity math (pool × services < server connection budget). Full pooling mastery rides with production HTTP — previewed here, practiced in 3.1 and Domain 06.

- **Why it matters (performance)**: redial-per-request latency (TLS handshake per API call — hundreds of ms serial; pooled — amortized to zero; the p99 difference between architectures). Ephemeral-port exhaustion (short-lived client bursts — TIME_WAIT accumulates; pools reuse — ports survive). Unbounded pools (default `maxSockets: Infinity` in some clients — burst opens thousands; server `maxConnections` sheds; client caps prevent self-inflicted refusal).
- **Modern guidance** — pool by default for repeated origins (agents with `keepAlive: true` — reuse across requests; idle timeout below server's (client 50 s vs server 60 s — client closes first, no race). Cap pools explicitly (`maxSockets` from concurrency needs — burst bounded; queueing visible in metrics, not in refused connections). Measure reuse (socket `reusedSocket` flag / agent stats — pooling verified, not assumed; redial rate graphed per deploy).

```javascript
// GOOD: pooled client, capped, verified — runs on node v20.20.2 (first dials, second reuses)
const http = require('node:http');
const agent = new http.Agent({ keepAlive: true, maxSockets: 10, timeout: 50000 }); // reuse + cap + client-closes-first
const server = http.createServer((req, res) => res.end('ok')).listen(0, '127.0.0.1', async () => {
  const port = server.address().port;
  const get = () => new Promise((res, rej) => { const rq = http.get({ port, host: '127.0.0.1', agent }, (rs) => { rs.resume(); rs.on('end', () => res(rq.reusedSocket)); }); rq.on('error', rej); }); // reusedSocket lives on the request, not the response
  console.log('first reused:', await get()); // false (handshake paid)
  console.log('second reused:', await get()); // true (no redial — economics observed)
  server.close(); agent.destroy();
});
// BAD: `http.get` per request with default agent and no cap ("simple client") —
// redial latency per call, port churn per burst; simplicity at the wrong layer
```

### 4) **Common confusion**

- "`lookup` and `resolve` are interchangeable" — OS path vs DNS-direct (hosts/search-domains honored vs ignored; different failure modes; different debugging). Resolve the question first: name or record?
- "Retries should be instant for speed" — instant retries synchronize herds (all clients hammer the recovering instant — backoff+jitter desynchronizes; speed of *recovery*, not of *retry*). Fast retries slow recoveries.
- "Timeouts can be long, failures are rare" — rare × connections = routine (long timeouts hold descriptors through every partial outage; budgets from SLOs, not optimism). Timeouts are capacity policy.
- "Pooling is an optimization for later" — pooling is architecture (redial latency shapes p99 from day one; retrofit changes connection behavior under load — set the agent before the first deploy). Later never comes; pools now.

### 5) **Performance note**

Connection behavior costs handshake latency and descriptor budgets: DNS lookup cached per process (milliseconds once — cache TTLs honored; resolve-per-request is the wasteful shape). Handshakes cost RTTs (TCP 1 + TLS 1–2 — pooling amortizes to zero across requests; redial-per-request pays per call — the architectural number). Backoff delays recovery traffic (bounded — caps terminate; unbounded retries cost more than any outage they "survive"). Pool sizing trades burst against budget (larger pools absorb bursts, consume server connections — capacity math both sides). Optimize handshake amortization first (pools — the p99 lever), retry boundedness second (caps — the outage lever), DNS caching third (TTL-respecting — the steady-state lever).

### 6) **Mentor note**

Teach resolution before dialing ("which family answers localhost here? — print it" until `lookup` precedes `connect` in every debug). Demo the herd (ten clients, fixed-interval retry against a downed port — synchronized hammering observed; then jittered — spread; backoff felt in logs). Demo reuse (first vs second request timing + `reusedSocket` — handshake cost seen once, then gone). Drill classification ("retry or fail fast? — name the code" for refused/timeout/reset vs auth/validation). Watch for the instant-retrier ("speed" — fix with the herd demo) and the timeless-dialer ("rare" — fix with descriptor math: timeout × conns < budget). Review check: families explicit, dials timed, retries bounded+jittered, pools capped, juniors classify before retrying.
