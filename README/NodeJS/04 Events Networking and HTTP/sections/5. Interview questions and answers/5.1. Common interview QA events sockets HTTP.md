## 5.1. Common interview QA: events, sockets, HTTP

### 1) **"10k connections, one process" — how?**

**Definition** — the C10K screen: candidates explain idle-connection economics. The answer: one loop multiplexes (epoll/kqueue — kernel waits on all sockets; JS wakes per event; no thread per connection), state stays tiny per socket (closures + small buffers — ~KBs each; 10k idles ≈ tens of MB), work never blocks (pool for I/O, workers for CPU — the loop always returns to poll). The interviewer listens for "no thread per connection" in the first sentence and per-connection budgets in the second. Follow-ups scale the numbers (100k — descriptor tuning; TLS — handshake CPU; chatty — loop saturation).

- **What problem it solves**: thread-per-connection instincts (10k threads × MB stacks — gigabytes of stacks, context-switch collapse; the architecture that caps at thousands). Evented multiplexing inverts the cost (connections cheap — CPU per message the only scaling variable; idle is nearly free). The answer also diagnoses production (connection-count alerts routed to fd budgets and per-conn state — not to thread pools that don't exist).
- **Modern guidance** — lead with multiplexing ("kernel waits, loop wakes — one thread, N sockets"). Budget per connection ("KBs of state — counted, capped via maxConnections + timeouts"). Name the ceilings honestly (descriptors — `ulimit`; TLS handshakes — CPU; chatty fan-out — loop time; each a number, each tunable). Demo at small scale (200 concurrent echoes below — same shape as 10k, smaller ceiling).

```javascript
// GOOD: 200 concurrent echoes, one process — runs on node v20.20.2 (200/200 answered, loop never blocked)
const net = require('node:net');
const server = net.createServer((s) => { s.on('data', (c) => s.write(c)); s.on('error', () => {}); }).listen(0, '127.0.0.1', async () => {
  const port = server.address().port; const one = () => new Promise((res) => { const c = net.connect(port, '127.0.0.1'); c.on('error', () => res(false)); c.on('connect', () => c.write('q')); c.on('data', (d) => { res(d.toString() === 'q'); c.end(); }); });
  const results = await Promise.all(Array.from({ length: 200 }, one)); // 200 concurrent (same shape as 10k)
  console.log('answered:', results.filter(Boolean).length, '/ 200 (multiplexed — no threads)');
  server.close();
});
// narration: "10k identical — raise ulimit, budget state, time idles; the loop doesn't care about the count"
// BAD: "Node handles it automatically" (magic as answer — no multiplexing, no budgets, no ceilings) —
// automatic until descriptors run out; economics stated, not hoped
```

### 2) **Emitter leak warning: diagnose it**

**Definition** — the listener trace: candidates narrate the diagnosis when `MaxListenersExceededWarning` fires. The steps: read the warning (event name + count + emitter — the what and where), correlate with load (count growing per request/connection — leak; flat at high count — fan-out), find the subscriber (who calls `.on` without matching `.off` — per-connection handlers the classic), fix by ownership (scope cleanup to the lifecycle — connection close removes its listeners; or `once` where single-fire). Prevention stated last (budgets + count assertions in tests — the class retired).

- **Why it matters (operations)**: leaks grow with traffic (warning in staging ignored — OOM in production weeks later; the graph every on-call recognizes too late). Misdiagnosis wastes the fix (raising `maxListeners` on a true leak — tripwire muted, growth continues; scoping fixes leaks, budgets document fan-out — different remedies, correctly routed). The interviewer is really asking "have you read this warning at 3 AM, and what did you do?"
- **Modern guidance** — reproduce first (per-connection `on` in a loop — warning fires deterministically; the demo below). Correlate before fixing (count vs connections — linear is leak, flat is fan-out). Fix by lifecycle (teardown removes — `close`/`finish` handlers `off` what setup `on`'d). Budget deliberate fan-out (`setMaxListeners` + comment — documented growth, tripwire intact for the rest).

```javascript
// GOOD: leak reproduced, then fixed — runs on node v20.20.2 (warning fires, scoped version silent)
const { EventEmitter } = require('node:events');
const leaky = new EventEmitter(); leaky.setMaxListeners(5); // low tripwire (audible fast)
for (let i = 0; i < 7; i++) leaky.on('tick', () => {}); // per-unit subscribes, none removed (the leak shape)
console.log('leaky count:', leaky.listenerCount('tick'), '(warning above — growth unbounded)');
const scoped = new EventEmitter(); const sub = () => {}; scoped.on('tick', sub); scoped.off('tick', sub); // lifecycle-paired (setup/teardown symmetric)
console.log('scoped count:', scoped.listenerCount('tick'), '(paired — flat forever)');
// fix narrated: "move the off into the connection-close handler; assert the count in tests"
// BAD: "raise the limit" as the whole fix (tripwire muted — leak continues to OOM, quietly) —
// limits document fan-out; lifecycles fix leaks; confusing them schedules the outage
```

### 3) **Slow POST, huge body: handle it**

**Definition** — the streaming-receive trace: candidates design a big-upload endpoint under adversarial conditions. The expected shape: stream the body (never buffer whole — chunks to disk via pipeline), cap the bytes (policy per endpoint — 413 + destroy past it), bound the time (request timeout — slowloris paced, not indulged), verify integrity (checksum/hash compared — truncation detected). Numbers named (cap bytes, timeout seconds, disk path). The interviewer escalates (10 GB? — same shape; gzip bomb? — decompressed-size cap; stalled sender? — idle timeout reaps).

- **Why it matters (security, reliability)**: unbounded uploads OOM (whole-read on attacker sizes — the avatar-attack over HTTP); uncapped time ties up slots (slowloris — connections held open at trickle; timeouts reap); unverified writes corrupt silently (truncated uploads stored as complete — checksums catch, customers otherwise). The trace is the endpoint design review in miniature — same threats, smaller stakes.
- **Modern guidance** — stream to disk (`pipeline(req, createWriteStream(tmp))` — constant memory; rename on success only — partials never served). Cap bytes and seconds (413 past size policy; 408/440 past time policy — both enforced, both logged). Verify before accepting (hash compare — integrity proved; parse after complete — 400 on malformed). Consume or destroy always (sockets recycle only when drained — pooling economics preserved).

```javascript
// GOOD: capped receive with verdicts — runs on node v20.20.2 (200:ok:11, 413 oversize)
const http = require('node:http');
const CAP = 64; // policy (stated — 64 bytes here, megabytes in production with the same shape)
const server = http.createServer((req, res) => { let bytes = 0; const chunks = [];
  req.on('data', (c) => { bytes += c.length; if (bytes > CAP) { res.writeHead(413); res.end('oversize'); req.destroy(); } else chunks.push(c); });
  req.on('end', () => res.end(`ok:${bytes}`)); req.on('error', () => {}); });
server.listen(0, '127.0.0.1', async () => {
  const port = server.address().port; const post = (b) => new Promise((res) => { const r = http.request({ port, host: '127.0.0.1', method: 'POST', agent: false }, (r2) => { let d = ''; r2.on('data', (c) => d += c); r2.on('end', () => res(`${r2.statusCode}:${d}`)); }); r.on('error', () => res('reaped')); r.end(b); });
  console.log(await post('hello world'), '|', await post('x'.repeat(200))); server.close(); // 200:ok:11 | 413:oversize
});
// narration: "10 GB identical — pipeline to disk, same cap shape, timeout added; gzip bombs capped post-decompression"
// BAD: "buffer it, check length, then save" (cap after buffering — OOM precedes the check) —
// order matters: count during, destroy past, never buffer-then-judge
```

Rapid-fire drills (one sentence each — mechanism named): "Unref'd socket?" — doesn't hold the loop (server convinces, process still exits — `unref` for outbound dials). "`server.close()` with live conns?" — stops accepting, drains existing (graceful — in-flight completes, new refused). "HTTP/1.1 keep-alive default?" — yes (sockets reuse unless closed — pooling works because persistence is default). "Emit with zero listeners?" — returns false, nothing happens (no error — silence by design; `error` the sole exception). "Socket `data` as strings?" — Buffers (bytes first — `setEncoding` only when the view is proven). "DNS fails, connect retries?" — classify first (resolution vs dial — back off the right layer).

### 4) **Common confusion**

- "C10K needs async everything" — C10K needs *non-blocking multiplexing* (sync boot fine; sync per-request fatal — the distinction is loop-time, not syntax). Block the loop never; block at boot freely.
- "Leak warnings are tuning knobs" — warnings are *diagnoses* (tune documented fan-out; fix unbounded growth — the warning can't tell them apart, the correlation can). Knobs document; lifecycles cure.
- "Big uploads need big memory" — big uploads need *disk + caps* (memory flat by construction — buffering is the bug, streaming the fix; gzip bombs need post-decompression caps — same shape, deeper). Memory constant, always.
- "Interview networking differs from real networking" — the trace *is* the design review (C10K answer sizes production; leak answer debugs staging; upload answer ships the endpoint). Study shippable shapes, not recitals.

### 5) **Performance note**

Interview conversation answers price real costs: multiplexing removes per-connection threads (10k idles ≈ tens of MB — the headline economics); listener budgets prevent retention growth (pinned closures × traffic — the only emitter cost that mattered); caps bound memory per request (cap × concurrency — capacity plannable); keep-alive amortizes handshakes (reuse verified — leaf 2.2's true). Candidates connecting each answer to a number (descriptors, bytes, timeouts) signal production ownership — the trait senior loops hire for. Mechanisms plus measurements, always.

### 6) **Mentor note**

Teach interview prep as incident prep ("every question here is a 3 AM page in a suit" — map each to its leaf: scale→2.1, leaks→1.1, uploads→3.1, dials→2.2). Drill the 200-echo demo live (same shape as 10k — scale the narrative, not the code). Drill leak diagnosis as story (warning → correlate → subscriber → lifecycle → budget — five beats, told in order). Drill uploads adversarially (oversize, malformed, stalled — three attackers, one shape). Watch for the magician ("automatically" — fix with "how many descriptors?") and the muter ("raise the limit" — fix with "leak or fan-out? — correlate first"). Review check: scale budgeted, leaks storied, uploads capped, rapid-fire derived, juniors multiplex before threading.
