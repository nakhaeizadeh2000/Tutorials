## 1.1. package.json as install and load contract

### 1) **One manifest, three audiences**

**Definition** — `package.json` is read by three different consumers, and each field answers one of them: humans read `name`/`version`/`description`/`license` (identity — what is this, may I use it); npm reads `dependencies`/`devDependencies`/`scripts`/`bin` (operations — what to install, what to run); Node reads `type`/`exports`/`main`/`engines` (loading — how to interpret and whether to refuse). A complete manifest serves all three; an incomplete one taxes whoever was forgotten (humans guess, npm drifts, Node misloads).

- **What problem it solves**: audience-blind manifests fail at distance (no `engines` — installs succeed on wrong Nodes, failures surface as app bugs; no `exports` — deep imports reach into internals, upgrades break consumers silently; no `description`/`license` — adoption and compliance stall on questions the manifest should answer). Each missing field moves its cost downstream (support questions, incident archaeology, legal review). Completeness is front-loaded cheapness.
- **Modern guidance** — fill all three audiences at creation (`npm init` answers, then review every section — no field left default-unknown). Treat the manifest as code (reviewed in PRs — dependency and `exports` changes get the same scrutiny as source changes; `git diff package.json` read before every merge). Keep generated sections honest (lockfiles committed beside it — leaf 1.2; `packageManager` field pinning the manager itself — corepack-enforced, drift ends at the toolchain too).

```jsonc
// GOOD: all three audiences served (complete as-shown — npm 10.8.2 reads every field below)
{
  "name": "@acme/service", "version": "1.4.0", "description": "Billing edge service",
  "license": "Apache-2.0", "type": "module", // humans: identity — Node: ESM mapping (leaf 2.2 of Domain 01)
  "exports": { ".": "./src/index.js" }, // Node: public surface (deep imports refused — point 2)
  "engines": { "node": ">=20 <23" }, // npm: runtime floor declared (enforced via .npmrc engine-strict — point 3)
  "scripts": { "start": "node src/index.js", "test": "node --test" }, // npm: workflows (leaf 2.1)
  "packageManager": "npm@10.8.2" // toolchain pinned (corepack activates exactly this npm)
}
// BAD: `{ "name": "x", "dependencies": {...} }` ("we'll add fields when needed") —
// Node guesses CJS, npm installs anywhere, humans ask in chat what this package is
```

### 2) **Fields that decide loading**

**Definition** — four fields steer the loader before a line of code runs: `type` (`.js` means ESM or CJS — [Domain 01/2.2](<../../../01 Runtime Fundamentals and Mental Model/sections/2. Process and modules/2.2. Modules in Node CJS and ESM interop.md>) for the full mapping), `exports` (the public surface map — subpaths listed load, unlisted throw `ERR_PACKAGE_PATH_NOT_EXPORTED`), `main` (the legacy entry — used only when `exports` is absent; presence of `exports` retires `main` for modern Node), `engines` (the runtime floor — advisory unless enforced, point 3). Misconfigured, these four produce the errors developers blame on code (`Cannot use import statement`, `__dirname is not defined`, path-not-exported walls).

- **Why it matters (correctness)**: loading fields are silent architects (a missing `type` flips every `.js` file's meaning — one absent line, whole-package reinterpretation; an absent `exports` exposes internals — consumers deep-import `./src/util.js`, then break on refactors they were never promised). Encapsulation at the manifest level (`exports` as the API boundary — internal files reorganize freely behind a stable map). The loader reads the contract first; code second.
- **Modern guidance** — set `type` explicitly, always (no absent-field roulette — `"module"` for new work). Define `exports` for every published package (`"."` at minimum — unlisted subpaths throw by design; the error is the encapsulation working). Prefer `exports` over `main` (modern Node consults `exports` first — `main` remains for legacy consumers only). Probe the contract (`npm pkg get type exports engines` — the manifest interrogated, never assumed).

```bash
# GOOD: the manifest interrogated — verified with npm 10.8.2
mkdir -p /tmp/nodeprobe/pkg && printf '{"name":"demo","version":"1.0.0","type":"module","exports":{".":"./index.js"},"engines":{"node":">=20"}}' > /tmp/nodeprobe/pkg/package.json
npm pkg get name version type --prefix /tmp/nodeprobe/pkg # three fields answer (identity + mapping)
npm pkg get exports --prefix /tmp/nodeprobe/pkg          # public surface printed (deep imports judged here)
node -e "const m = require('/tmp/nodeprobe/pkg/package.json'); console.log('node reads engines:', m.engines.node)"
# BAD: editing fields by rumor ("someone said exports breaks jest") —
# loader behavior verified by probes in seconds; rumor-driven manifests rot for quarters
```

### 3) **Contracts enforced, not wished**

**Definition** — advisory fields wish; enforced fields contract. `engines` without enforcement prints a warning nobody reads (pipelines scroll past; installs complete on wrong Nodes — verified: manifest `engineStrict` alone still exits 0 on npm 10). Enforcement is one line in `.npmrc`: `engine-strict=true` (installs abort with `notsup` on mismatch, exit 1 — refusal, not advice). Declare in the manifest, enforce in `.npmrc`. Same principle for names and versions (validated at publish — invalid names rejected; `npm pkg fix` repairs mechanics). Contracts fail loudly at install time or not at all.

- **Why it hurts when missing (correctness, operations)**: unenforced `engines` greenlights drift (CI installs on Node 18 against an `engines: >=20` wish — optional chaining fine, `Array.fromAsync` throwing; the failure reads as an app bug, the cause is an ignored warning three steps earlier). Loud refusal collapses the distance (install aborts naming the mismatch — fix the environment, not the code). Warnings are documentation; errors are contracts.
- **Modern guidance** — declare in the manifest, enforce in `.npmrc` (`engines` names the floor; `engine-strict=true` refuses the mismatch — verified: manifest-only strictness still exits 0 on npm 10). Prove refusal once per project (a mismatched install attempted deliberately — watch `notsup`, exit 1; the contract demonstrated, not assumed). Pass `--engine-strict` in CI flags too (warnings promoted to errors where drift costs most).

```bash
# GOOD: refusal demonstrated — verified with npm 10.8.2 (notsup, exit 1)
mkdir -p /tmp/nodeprobe/future && printf '{"name":"future","version":"1.0.0","engines":{"node":">=99"}}' > /tmp/nodeprobe/future/package.json
printf 'engine-strict=true\n' > /tmp/nodeprobe/future/.npmrc # enforcement lives here (manifest alone only warns)
npm install --prefix /tmp/nodeprobe/future --dry-run # npm error notsup ... Required: {"node":">=99"} (refusal, not advice)
# BAD: `"engines": { "node": ">=20" }` with no strictness ("the warning is enough") —
# warnings scroll past in CI logs; the wrong Node installs, the app fails, archaeology begins
```

### 4) **Common confusion**

- "`main` and `exports` are the same" — `exports` wins when present (modern Node never consults `main` for mapped subpaths; `main` serves legacy resolvers only). Both set means two audiences; `exports`-only means one modern contract.
- "`engines` blocks installs by default" — advisory by default (warning only — enforcement is opt-in via strict flags; the field wishes until configured). Set the field *and* the strictness.
- "`packageManager` is redundant with `.nvmrc`" — different pins (`.nvmrc` pins Node — leaf 1.2 of Domain 01; `packageManager` pins npm/pnpm/yarn — the installer itself drifts too). Two tools, two pins.
- "Private packages need no metadata" — private packages need *more* (no registry page documents them — the manifest is the only documentation; future-you is the audience most taxed by sparseness). Interior quality shows in manifests.

### 5) **Performance note**

Manifest design costs nothing at runtime (parsed once per process start — microseconds; `exports` maps resolve in nanoseconds beside I/O). It pays at install time (complete manifests install deterministically — no re-resolves, no version negotiations; `engineStrict` aborts in seconds instead of failing in production hours later) and at scale (encapsulated `exports` let internals refactor without consumer coordination — the coordination cost dwarfs every nanosecond the loader ever spends). Optimize the manifest for install determinism and refactor freedom — never for parse speed (unmeasurable beside the first `require`).

### 6) **Mentor note**

Teach the manifest as three contracts ("who reads this field? — name the audience per line" until students sort fields into human/npm/Node unprompted). Demo refusal live (the `>=99` install — `EBADENGINE` in three seconds; enforcement understood forever). Drill `exports` as encapsulation (deep-import a listed vs unlisted subpath — one loads, one throws by design; boundaries felt, not just read). Watch for the minimalist ("fewer fields, less to maintain" — fix with the drift invoice: every missing field bills downstream) and the rumor-editor (fields changed on hearsay — fix with `npm pkg get` probes: verify in seconds). Review check: all three audiences served, `type` explicit, `exports` mapped, engines enforced, juniors interrogate manifests before editing them.
