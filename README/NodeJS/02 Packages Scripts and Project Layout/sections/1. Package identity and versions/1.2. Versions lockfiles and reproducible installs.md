## 1.2. Versions, lockfiles, and reproducible installs

### 1) **Semver ranges are promises**

**Definition** — every dependency version is a promise about compatible change: `MAJOR.MINOR.PATCH` (breaking.feature.fix — [semver](https://semver.org/)); ranges state how much change you accept (`1.2.3` exact — this and only this; `~1.2.3` — patch-level trust, `1.2.x`; `^1.2.3` — minor-level trust, `1.x` without breaking). npm's default (`^`) trusts maintainers to never break minorly — a social promise with a technical syntax. Each range prices risk per dependency (exact = zero surprise, manual upgrades; caret = automatic fixes, occasional breakage invoices).

- **What problem it solves**: unpriced ranges fail at distance (`^` on a 0.x dependency — minor *is* major below 1.0, breakage arrives as a "patch" Tuesday; floating ranges in libraries — your consumers inherit version negotiations you never tested; exact-everywhere in apps — security patches wait for human upgrades that never come). The failure reads as "the ecosystem broke" — the cause is a promise nobody priced. Ranges declared deliberately turn ecosystem motion into scheduled work.
- **Modern guidance** — default `^` for applications with lockfiles (motion absorbed by the lock — point 2; upgrades deliberate via `npm update <pkg>`). Pin exact for 0.x dependencies and native addons (breakage-prone surface — precision over convenience). Use `~` for infrastructure-adjacent deps (types, linters — patch trust, minor review). Libraries keep ranges wide and test the matrix (consumers resolve — your CI proves the span, not a point).

```bash
# GOOD: ranges interrogated, not assumed — verified with npm 10.8.2 (registry reachable)
npm view semver version # latest published (the ^ target your installs float toward)
node -e "console.log('^1.2.3 lets 1.9.0 in, keeps 2.0.0 out (minor trust, major wall)')"
# BAD: `"some-lib": "*"` ("always latest, always fresh") —
# every install negotiates anew; breakage arrives unannounced, unreproducible, untraceable to a decision
```

### 2) **Lockfiles freeze the tree**

**Definition** — `package.json` declares *intent* (ranges — what change is acceptable); `package-lock.json` records *resolution* (exact versions + integrity hashes for every transitive node — what actually installed). Committed locks make installs deterministic (same tree on every machine); `npm ci` enforces them (deletes `node_modules`, installs exactly the lock — aborts on manifest/lock mismatch instead of re-resolving). Intent evolves deliberately (`npm install <pkg>` re-resolves and rewrites the lock — reviewed in PRs); reproduction never negotiates.

- **Why it matters (correctness, security)**: unlocked installs drift per machine and per day (Monday's tree differs from Friday's — "works on my machine" as a calendar function; transitive breakage without any direct change — your diff empty, your build red). Integrity hashes close the supply-chain gap (each tarball verified against the lock — tampered registries and proxies detected, not trusted). The lockfile is the only artifact that says what ran in production — everything else is aspiration.
- **Modern guidance** — commit the lockfile for applications (always — no exceptions; `.gitignore`d locks are a reproducibility hole). Use `npm ci` in every pipeline (frozen installs — mismatch aborts loudly; `npm install` in CI re-resolves silently). Review lock diffs like code (unexpected major bumps, new transitive authors, removed integrity fields — supply-chain review per PR). Never hand-edit the lock (re-resolve via npm commands — hand edits corrupt the integrity chain).

```bash
# GOOD: frozen tree demonstrated end to end — verified with npm 10.8.2
mkdir -p /tmp/nodeprobe/repro && printf '{"name":"repro","version":"1.0.0"}' > /tmp/nodeprobe/repro/package.json
npm install --prefix /tmp/nodeprobe/repro semver@7 2>&1 | tail -1 # intent recorded (^7), resolution frozen
node -p "require('/tmp/nodeprobe/repro/package-lock.json').packages['node_modules/semver'].version" # locked exact
rm -rf /tmp/nodeprobe/repro/node_modules && npm ci --prefix /tmp/nodeprobe/repro 2>&1 | tail -1 # wipe + frozen reinstall
npm ls semver --prefix /tmp/nodeprobe/repro # identical tree restored (reproduce, don't renegotiate)
# BAD: `npm install` in CI ("ci is just faster install") —
# re-resolution per run: green Monday, red Friday, empty diff — the calendar as a dependency
```

### 3) **Reproduce means verify**

**Definition** — a reproduced tree is verified, not assumed: `npm ls` (the installed tree printed — phantom and deduped nodes visible), `npm explain <pkg>` (why a version installed — which parent demanded it, which range allowed it), `npm audit` (known vulnerabilities in the frozen tree — fix availability included). Verification runs at install time (post-`ci` checks in pipelines) and at review time (lock diffs interrogated per PR). Trust installed — after evidence, never before.

- **Why it hurts when missing (security, debuggability)**: unverified trees harbor duplicates (three copies of a vulnerable transitive — patched once, exploitable twice; `npm ls` would have shown all three). Unexplained versions confuse upgrades (`npm update` moves a transitive nobody owns — `explain` names the demanding parent first). Unaudited trees ship known CVEs (audit databases list the advisory with a fix version — shipping without checking is negligence with a paper trail). Each tool answers one question in seconds; skipping all three answers nothing ever.
- **Modern guidance** — print the tree after `ci` (`npm ls --omit=dev` in pipelines — production surface visible per run). Explain before upgrading (`npm explain` names the constraint chain — bump the parent, not the transitive). Audit on schedule, fix on evidence (`npm audit` weekly in CI — fix versions applied deliberately, not panicked; `audit fix` reviewed, never blind). Record the evidence (pipeline logs keep tree + audit output — incidents start from the recorded tree, not a fresh guess).

```bash
# GOOD: the tree interrogated — verified with npm 10.8.2 (against the frozen repro above)
npm ls semver --prefix /tmp/nodeprobe/repro # who installed what, deduped and nested
npm explain semver --prefix /tmp/nodeprobe/repro # why this version (parent chain + ranges named)
node -p "require('/tmp/nodeprobe/repro/package-lock.json').packages['node_modules/semver'].integrity.slice(0, 20)" # hash recorded (tamper-evident)
# BAD: shipping the tree no one printed ("install succeeded, ship it") —
# duplicates, advisories, and phantom parents ride along unseen; incidents discover them instead
```

### 4) **Common confusion**

- "`^` means compatible, always" — caret trusts *maintainers'* discipline (0.x treats minor as major — `^0.2.3` admits breakage; humans break contracts, syntax can't prevent it). Caret is trust with syntax, not proof.
- "`npm ci` is just faster `npm install`" — different contracts (`ci` installs the lock exactly and aborts on mismatch; `install` re-resolves and rewrites). Speed is a side effect; frozen-vs-fluid is the substance.
- "Lockfiles are generated, don't review them" — generated *and* load-bearing (the lock names every transitive author and version — supply-chain review happens here or nowhere). Review the diff, not the whole file (unexpected majors, new authors — the signal in the noise).
- "Dev dependencies don't need locking" — one lock covers all (dev tools run in CI with production privileges — a compromised linter exfiltrates from the pipeline; `omit=dev` at deploy, audit everything always). Attackers read your `.gitignore` too.

### 5) **Performance note**

Version strategy costs at install time, pays at debug time: locked `ci` installs beat re-resolving installs (no metadata negotiation — faster *and* deterministic; the rare case where faster is also safer). Exact-pinned trees skip range math (microseconds — irrelevant beside download time; pin for risk, never for speed). Audit adds seconds per pipeline run (versus incident-weeks per shipped CVE — the cheapest security in backend work). Deduped trees shrink `node_modules` (fewer copies — faster containers, smaller images; `npm dedupe` measured, not ritual). Optimize installs for determinism first (frozen trees), speed second (caching, registries mirrors) — never the reverse (fast-but-fluid is Monday-green-Friday-red).

### 6) **Mentor note**

Teach ranges as promises ("what change does `^` accept from a stranger? — price it aloud" until caret-on-0.x *looks* wrong). Demo drift live (install unlocked Monday, install Friday — diff the trees; the calendar as a dependency, visible). Drill `explain` before every upgrade ("which parent demands it? — name the chain before bumping"). Watch for the star-pinner (`"*"` everywhere — fix with the breakage invoice: unannounced, unreproducible) and the lock-ignorer (lock gitignored — fix with the Monday/Friday demo). Review check: ranges priced, lock committed, `ci` in pipelines, tree printed, audit scheduled, juniors explain before upgrading.
