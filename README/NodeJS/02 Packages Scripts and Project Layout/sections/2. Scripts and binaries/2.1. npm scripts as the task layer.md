## 2.1. npm scripts as the task layer

### 1) **Scripts are the project's CLI**

**Definition** — `scripts` maps names to shell commands, and npm runs them with the project's environment (`npm run <name>` — exact command from the manifest; `npm start`/`npm test` — shorthand for the two canonical workflows). The scripts table is the project's command surface: onboarding reads it instead of asking in chat, CI calls it instead of embedding shell, contributors extend it instead of documenting tribal one-liners. Every repeated command earns a name; unnamed repetition is process debt.

- **What problem it solves**: tribal commands rot (the deploy one-liner lives in one engineer's history — they leave, it dies; CI embeds shell that drifts from local practice — green locally, red remotely, same intent; README commands bit-rot (flags change, docs don't — copy-paste fails, trust erodes). Named scripts fix the command in version control (reviewed, tested, runnable identically everywhere). The manifest becomes executable documentation — read it, run it, believe it.
- **Modern guidance** — name every workflow (`dev`, `start`, `test`, `lint`, `build` — the canonical five; custom names for the rest, verbs not nouns). Keep `start` production-shaped (`node src/index.js` — what the platform runs; `dev` may watch/reload, `start` must not). Never hide required env inside scripts (reference `process.env` with boot validation — leaf 2.1 of Domain 01; scripts compose commands, secrets stay environmental).

```bash
# GOOD: the project's CLI, listed and runnable — verified with npm 10.8.2
mkdir -p /tmp/nodeprobe/scripts && printf '{"name":"demo","version":"1.0.0","scripts":{"hello":"node -e \\"console.log(1987)\\"","test":"node --test"}}' > /tmp/nodeprobe/scripts/package.json
npm run --prefix /tmp/nodeprobe/scripts # lists every script (the CLI surface, self-documenting)
npm run hello --prefix /tmp/nodeprobe/scripts # runs exactly the stored command (no tribal memory)
# BAD: `./deploy.sh` in chat history + CI yaml with different flags ("scripts are ceremony") —
# two sources of truth, zero reviews, onboarding by archaeology
```

### 2) **Lifecycle and env wiring**

**Definition** — npm runs more than the named command: `pre<name>`/`post<name>` hooks bracket it (migrations before start, cleanup after build — ordered automatically), `node_modules/.bin` joins `PATH` (dependency binaries invocable by bare name inside scripts — no global installs, no relative paths), and `npm_package_*` env vars carry manifest fields in (`npm_package_version` — version-stamping builds without re-declaration). The wiring is the feature: scripts behave identically on every machine because npm builds the same execution room each time.

- **Why it matters (correctness)**: unwired commands depend on ambient machines (global `vitest` version differs per laptop — same script, different runner; `./node_modules/.bin/vitest` hardcoded — breaks on Windows, breaks on pnpm layouts; version re-declared in three files — release bumps miss one). npm's room removes the ambient (bins resolved locally, hooks ordered declaratively, metadata injected). "Works on my machine" is usually "my machine had the global" — the room ends that class.
- **Modern guidance** — call bins by bare name in scripts (`vitest run`, not paths or globals — resolution local and portable). Use `pre`/`post` for ordered pairs (prebuild cleans, posttest reports — ordering declared, not remembered). Read metadata from env (`$npm_package_version` in sh, `%npm_package_version%` on Windows — or cross-env for sanity; single source in the manifest). Inspect the room when confused (`npm run env` prints the execution environment — `PATH` with `.bin` visible, variables listed).

```bash
# GOOD: hooks ordered + room inspected — verified with npm 10.8.2
printf '{"name":"demo","version":"1.0.0","scripts":{"prehello":"node -e \\"console.log(1986)\\"","hello":"node -e \\"console.log(1987)\\""}}' > /tmp/nodeprobe/scripts/package.json
npm run hello --prefix /tmp/nodeprobe/scripts # prehello runs first (1986), then hello (1987) — ordering declared
npm run env --prefix /tmp/nodeprobe/scripts 2>/dev/null | grep -o "[^ ]*\.bin[^ ]*" | head -1 # .bin on PATH (bins by bare name)
# BAD: `pretest` that secretly deploys ("convenient ordering") —
# lifecycle hooks must be unsurprising: setup/teardown of the named workflow, never side quests
```

### 3) **Composition over runners**

**Definition** — scripts compose with shell operators and delegation before they need a task runner: `&&` chains sequence (fail-fast — first failure stops the chain, exit code propagates), `&` with `wait` parallels where safe (independent checks concurrently), delegation to files scales (complex logic lives in `scripts/*.mjs` invoked by one-line names — testable, lintable, reviewable). Task runners (gulp, grunt descendants, `npm-run-all2`) enter only when composition strains (cross-platform parallelism, file watching matrices). Composition first, dependencies later.

- **Why it matters (maintainability)**: premature runners tax every contributor (plugin APIs to learn, versions to pin, configs to debug — for what `&&` already does). Uncomposed scripts duplicate (lint flags repeated in five scripts — one flag change, five edits; extract to a shared script or file). Overlong one-liners rot (200-character chains untestable — delegation to a file buys tests and stack traces). The ladder: chain, then delegate, then (rarely) adopt a runner — each rung earned by pain, not fashion.
- **Modern guidance** — chain with `&&` for sequences (fail-fast default — errors stop the line, CI reds honestly). Delegate past one line of logic (`"migrate": "node scripts/migrate.mjs"` — the file tested, the name stable). Quote for the lowest common shell (sh-compatible quoting — Windows runs scripts via sh emulation; exotic bashisms break contributors). Adopt a runner only with measured pain (parallel + watch + matrix needs coinciding — one need is solved by composition).

```bash
# GOOD: chained, fail-fast, delegating — verified with npm 10.8.2
printf '{"name":"demo","version":"1.0.0","scripts":{"check":"node -e \\"process.exit(0)\\"","verify":"npm run check --prefix /tmp/nodeprobe/scripts && node -e \\"console.log(1988)\\""}}' > /tmp/nodeprobe/scripts/package.json
npm run verify --prefix /tmp/nodeprobe/scripts # check passes, 1988 prints (chain short-circuits on failure — try exit(1))
# BAD: `"test": "node --test test/a.js && node --test test/b.js && node --test test/c.js && ..."` (twelve chains inline) —
# past three links, delegate: one `test-all.mjs` with real control flow, real errors, real tests
```

### 4) **Common confusion**

- "`npm start` runs `node .`" — runs the `start` script *if defined* (else falls back to `node server.js` legacy — define `start` explicitly; implicit fallbacks surprise). Explicit beats inherited.
- "Scripts need bash" — scripts run via sh (plus npm's `script-shell` config — bashisms break on minimal images and Windows; write portable chains or set the shell deliberately). Portability is a choice, not an accident.
- "`pre`/`post` run for every script" — only for the named workflow (`prehello` brackets `hello` — no global hooks; shared setup belongs in a composed first link, not in lifecycle magic). Scoped, not ambient.
- "More scripts means better DX" — named *workflows*, not named *commands* (five canonical plus real workflows; thirty micro-scripts scatter understanding — compose inside, name outside). Names are API; APIs stay small.

### 5) **Performance note**

Scripts cost process spawns (each `npm run` adds a shell + npm wrapper — tens of milliseconds; chains of dozens add seconds to workflows — delegate hot loops to files, keep scripts as entry points). `.bin` shims add an exec hop (negligible beside test suites; measure suites, never shims). `pre`/`post` double the spawn count per workflow (fine for CI — correctness over milliseconds; noticeable only in watch-loop inner cycles — call the tool directly there). Optimize the *workflow's* wall time (parallelize independent checks — the minutes that matter), never the *spawn* overhead (milliseconds nobody feels). Scripts are coordination; coordination costs are paid in clarity currency.

### 6) **Mentor note**

Teach scripts as executable documentation ("new hire runs `npm run` with no other instructions — what do they learn?" until manifests read as CLIs). Demo the room live (`npm run env` — point at `.bin` on `PATH`; run a bare bin name — ambient-machine thinking ends). Drill hook ordering (add `pre`/`post`, predict the sequence, run — declared order observed). Watch for the globalist (global CLIs in scripts — fix with "which version runs on CI?") and the inliner (200-char chains — fix with "test that chain" — delegation follows). Review check: five canonical names present, bins bare, hooks unsurprising, chains fail-fast, logic delegated, juniors onboard from `npm run` alone.
