## 2.2. Binaries, npx, and executed packages

### 1) **`bin` turns packages into commands**

**Definition** — the `bin` manifest field maps command names to files (`{ "cowsay": "./cli.js" }` — install creates `node_modules/.bin/cowsay`, a shim with a node shebang pointing at the file). The shim is what makes bare-name invocation work (inside scripts via npm's `PATH` room — leaf 2.1; directly via `./node_modules/.bin/<name>`). No `bin` field, no command — libraries stay importable-only by default, executables opt in explicitly.

- **What problem it solves**: unrunnable tools (a test runner installed but invocable only by deep path — contributors guess, CI hardcodes; global installs papering over the gap — versions drift per machine). The `bin` contract standardizes execution (installed → invocable — same spelling on every machine). Missing-bin confusion also debugs quickly (`ls node_modules/.bin` — the command exists or it doesn't; no PATH archaeology).
- **Modern guidance** — depend, then invoke by bare name in scripts (leaf 2.1's room resolves `.bin` — never hardcode the path, never global-install the tool). Inspect `.bin` when commands go missing (`ls` the dir — absent shim means absent/incompatible install, not ambient failure). Declare `bin` for your own CLIs (one name per entry file — quoted in docs beside `npx <pkg>` usage).

```bash
# GOOD: installed → invocable, same spelling everywhere — verified with npm 10.8.2
mkdir -p /tmp/nodeprobe/bins && printf '{"name":"bins","version":"1.0.0"}' > /tmp/nodeprobe/bins/package.json
npm install --prefix /tmp/nodeprobe/bins cowsay@1.6.0 2>&1 | tail -1 # bin field ships the command
ls /tmp/nodeprobe/bins/node_modules/.bin/ | head -3 # shim exists (cowsay among them)
/tmp/nodeprobe/bins/node_modules/.bin/cowsay "shim works" # executed via shim (shebang → node)
# BAD: `npx cowsay` in CI scripts ("always fresh") —
# fresh means unpinned: registry motion re-resolves per run; pin in devDependencies, invoke bare
```

### 2) **`npx` executes without installing**

**Definition** — `npx` (and `npm exec`) runs a package's binary without adding it to your project: one-shot scaffolders (`create-*` CLIs — run once, never depended on), version-pinned exec (`npx -p cowsay@1.6.0 cowsay hi` — exact version, no install), and ad-hoc tools (migrations, codemods — used rarely, owned by no project). Resolution order: local `.bin` first (project wins when present), then cache/registry (fetched when absent). Convenience with a supply-chain price: every unpinned exec trusts the registry at run time.

- **Why it matters (correctness, security)**: unpinned execs drift per run (Tuesday's scaffolder differs from Monday's — generated projects differ by weekday; compromised registry responses execute immediately — no lockfile, no review, no hash check). The price is invisible until it invoices (a hijacked one-shot running with your credentials and cwd). Pinned exec (`-p pkg@version`) restores determinism; local installs restore reviewability. Convenience chosen with eyes open.
- **Modern guidance** — prefer local installs for repeated use (anything run twice belongs in `devDependencies` — reviewed, locked, invocable bare). Pin every exec (`-p <pkg>@<version>` — exact, quoted in docs/runbooks; `--yes` only in non-interactive pipelines — prompts exist to confirm fetches). Reserve bare `npx <pkg>` for interactive one-shots (scaffolding on your laptop — observed, discardable; never in CI — pipelines execute only pinned artifacts).

```bash
# GOOD: one-shot without project pollution — verified with npm 10.8.2 (empty dir stays empty)
mkdir -p /tmp/nodeprobe/oneshot && npm exec --yes --prefix /tmp/nodeprobe/oneshot --package=cowsay@1.6.0 -- cowsay "no install" # fetched to cache, not to cwd
ls /tmp/nodeprobe/oneshot # package.json absent, node_modules absent (nothing installed, command ran)
# BAD: `npx some-scaffolder` inside a Dockerfile ("fewer layers") —
# every build re-resolves: unreproducible images, unreviewed code executing as root at build time
```

### 3) **Global installs are the exception**

**Definition** — global installs (`npm install -g`) place commands outside any project (one version system-wide — shared by everything, owned by nothing). Legitimate residents: exactly the tools that operate *across* projects and carry no project state (the package manager itself, corepack shims, maybe a process manager). Everything else installs locally (per-project versions — two clients on two lines coexist; lockfiles review tools like code). Globals are ambient machinery — and ambient is what leaf 2.1's room exists to eliminate.

- **Why it hurts when missing (maintainability, security)**: global-version coupling (project A needs vitest 1, project B needs vitest 2 — one global serves neither; upgrades coordinated across unrelated repos — or more often, never). Privilege creep (global installs historically needed sudo — root-owned files in userland; even user-scoped globals bypass project review — unaudited code on every `PATH`). The exception list stays short because each entry taxes every project on the machine.
- **Modern guidance** — audit globals quarterly (`npm ls -g --depth=0` — each entry justifies its residence; unjustified entries uninstall). Prefer corepack for manager pinning (`corepack enable` — shims per `packageManager` field, no global npm-version coupling). Use `npx -p` for cross-project one-shots (pinned exec without residence — convenience without tenancy). Never `sudo npm install -g` (root-owned `node_modules` breaks future non-root updates — fix the prefix, not the privilege).

```bash
# GOOD: globals audited — verified with npm 10.8.2 (short list, each entry residence-justified)
npm ls -g --depth=0 # every global named (belongs across projects, or uninstall it)
node -p "process.env.npm_config_prefix ?? '(default prefix)'" # where globals live (known location, no sudo mysteries)
# BAD: `sudo npm i -g left-pad lodash express vitest` ("toolbox") —
# root-owned packages, unpinned versions, every project inheriting one engineer's afternoon
```

### 4) **Common confusion**

- "`npx` always uses the latest" — local `.bin` wins first (`npx vitest` runs the project's pinned vitest when installed — registry only when absent; the shadowing surprises users expecting freshness). Locality before novelty.
- "Shims work everywhere identically" — shebang + `PATH` semantics differ (Windows uses `.cmd` shims — quoting and signal behavior vary; pnpm uses isolated layouts — deep-path assumptions break). Bare names in scripts (portable); direct `.bin` paths (diagnostic only).
- "Caching makes unpinned exec safe" — cache keys include the unresolved range (re-resolves per TTL/policy — freshness leaks back in; only exact pins freeze). Cache is speed, pins are safety.
- "`npm exec` and `npx` differ fundamentally" — same engine, different UX (`npm exec` flags explicit, `npx` terse; `--package` vs `-p` — pick one spelling per repo). One documented spelling per project.

### 5) **Performance note**

Binary strategy costs at install/fetch time, never at runtime (shims add one exec hop — microseconds beside test suites; `npx` fetches seconds on first run, cached after — pin + warm the cache in CI images). Global tools skip per-project installs (disk saved — irrelevant beside image sizes; consistency lost — the actual currency). Local `.bin` invocation adds zero overhead versus direct paths (same file executed — the shim resolves once per spawn). Optimize for determinism (pinned locals — reproducible commands), then for fetch latency (registry mirrors, cache warming) — never by reaching for globals (saved seconds, spent quarters).

### 6) **Mentor note**

Teach execution as a ladder ("installed-local beats pinned-exec beats bare-npx beats global — climb down only with reason" until students default to `devDependencies`). Demo the shim live (`ls .bin`, `cat` a shim — the shebang demystified in ten seconds). Demo pollution-free exec (the empty-dir `npm exec` — nothing installed, command ran; then the Dockerfile warning — same convenience, different stakes). Watch for the globalist ("global toolbox" — fix with the two-clients-two-versions scenario) and the fresh-exec ("always latest in CI" — fix with the weekday-scaffolder story). Review check: tools local and pinned, execs versioned, globals audited, juniors invoke bare names without knowing why it works (then learn why).
