## 3.1. node_modules resolution and project layout

### 1) **The lookup walk, stated plainly**

**Definition** — Node resolves every specifier by rule, in order: relative specifiers (`./x`, `../x` — joined to the importing file's path, extension rules per loader — [Domain 01/2.2](<../../../01 Runtime Fundamentals and Mental Model/sections/2. Process and modules/2.2. Modules in Node CJS and ESM interop.md>)); bare specifiers (`lodash` — walk upward from the importing file, checking each level's `node_modules`, first match wins); `node:` specifiers (`node:fs` — builtins, never the disk). The walk is deterministic (same tree, same answer — reproducibility's foundation) and visible (`require.resolve()` prints the verdict — resolution interrogated, never assumed).

- **What problem it solves**: resolution-by-folklore (deep relative chains `../../../../lib` — moves break six files; bare imports working "by magic" — the walk invisible until it fails; `node:` confused with bare names — a dependency shadowing a builtin, or vice versa). Stating the walk turns magic into mechanics (every resolved path traceable to a rule; every failure mappable to a step). Debuggers read the walk; guessers read stack traces.
- **Modern guidance** — resolve relatively within a package (sibling files by path — explicit, move-detectable), barely across packages (dependencies by name — versioned, locked). Use `node:` for all builtins (unambiguous — no dependency can shadow `node:fs`). Print resolutions when confused (`require.resolve('<spec>')` from the importing directory — the walk's verdict in one line; `resolve.paths()` shows every level consulted).

```javascript
// GOOD: the upward walk observed — verified on node v20.20.2 (sub/ has no node_modules of its own)
const fs = require('node:fs'); const Module = require('node:module');
fs.mkdirSync('/tmp/nodeprobe/walk/node_modules/a', { recursive: true });
fs.writeFileSync('/tmp/nodeprobe/walk/node_modules/a/package.json', '{"name":"a","version":"1.0.0","main":"index.js"}');
fs.writeFileSync('/tmp/nodeprobe/walk/node_modules/a/index.js', 'module.exports = "found-upward";');
fs.mkdirSync('/tmp/nodeprobe/walk/sub', { recursive: true });
const reqFromSub = Module.createRequire('/tmp/nodeprobe/walk/sub/fake.js'); // resolve as if from sub/
console.log('bare-style upward hit:', reqFromSub('a')); // found-upward (walk climbed past empty sub/)
// BAD: `require('../../../../lib/util')` chains ("explicit is good") —
// explicit paths, implicit coupling: every move breaks importers; alias or restructure past two levels
```

### 2) **Layout conventions that scale**

**Definition** — the community-converged shape of a Node project: `src/` (owned code — the package's own modules), `test/` or co-located `*.test.js` (proof — beside or beneath, never mixed into shipped files), `scripts/` (project automation — leaf 2.1's delegates), top-level manifests (`package.json`, lockfile, configs — the contracts), and strict separation of app vs lib (apps: `src/index.js` boots a process; libs: `src/index.js` exports an API — booting code never ships in libraries, importable code never assumes a process). Conventions scale because every hire already knows them.

- **Why it matters (maintainability)**: bespoke layouts tax every reader (where do tests live? which file boots? — questions answered per repo instead of never asked). Mixed app/lib modules break consumers (a library importing its own CLI — side effects on require; an app exporting internals — encapsulation by accident). Shipped test fixtures bloat installs (`files` field or `.npmignore` uncurated — consumers download your fixtures). Convention is shared vocabulary — deviation needs a reason stated in the README.
- **Modern guidance** — start conventional (`src/`, `test/`, `scripts/` — boring on purpose; boring scales). Separate entry points (`"exports"` maps lib surface — leaf 1.1; a distinct `bin` entry boots the CLI — leaf 2.2; neither imports the other). Curate shipped files (`files: ["src/"]` whitelist — consumers receive the surface, not the scaffolding). Document deviations once (nonstandard layout explained at the repo root — the tax paid visibly, not discovered).

```bash
# GOOD: conventional shape, stated and shipped lean — the boring layout as commands
mkdir -p /tmp/nodeprobe/layout/src /tmp/nodeprobe/layout/test /tmp/nodeprobe/layout/scripts
printf '{"name":"layout","version":"1.0.0","files":["src/"]}' > /tmp/nodeprobe/layout/package.json
printf 'export {};\n' > /tmp/nodeprobe/layout/src/index.js # owned code (shipped — files whitelist)
printf "import test from 'node:test';\n" > /tmp/nodeprobe/layout/test/index.test.js # proof (never shipped)
printf "console.log('migrate');\n" > /tmp/nodeprobe/layout/scripts/migrate.mjs # automation (delegated)
find /tmp/nodeprobe/layout -type f | sort # manifest up top, three dirs each with its role
# BAD: `lib/`, `app/`, `source/`, `helpers2/` across four services ("organic growth") —
# every repo a dialect; every hire a translator; every move a migration
```

### 3) **Hoisting, phantoms, and ghosts**

**Definition** — npm flattens dependency trees (hoisting — transitive deps lifted to top-level `node_modules` when versions allow; disk saved, duplicates minimized), which creates two specters: phantom dependencies (packages your code imports but never declared — resolving today via a hoisted transitive, breaking tomorrow when the parent upgrades), and ghosts (stale entries — removed deps lingering in `node_modules` because installs add but rarely prune without `ci`/dedupe). Both resolve *today* and betray *later* — the worst failure shape.

- **Why it hurts when missing (correctness, reproducibility)**: phantom breakage without diffs (parent bumps its dep — your undeclared import vanishes; your code unchanged, your build red — the calendar as adversary again). Ghost divergence (local `node_modules` richer than a fresh install — green locally, red in CI; "delete node_modules and reinstall" as ritual instead of `ci` as policy). Hoisting also duplicates silently (conflicting ranges nest copies — three versions of one lib, singletons split — `npm ls <pkg>` exposes the copies).
- **Modern guidance** — declare everything imported (every bare specifier in your code appears in `dependencies` — lint it: `depcheck` or `eslint-plugin-import` with no-extraneous rules). Prefer `npm ci` over `npm install` for clean states (prunes ghosts by construction — wipe-and-freeze, not accumulate). Inspect duplicates deliberately (`npm ls <pkg>` — copies named; `npm dedupe` consolidates where ranges allow). Consider strict layouts for large monorepos (pnpm-style isolation — phantoms impossible by construction; npm's `install-strategy` notes the trade — adopted with eyes open).

```bash
# GOOD: phantom caught red-handed — verified with npm 10.8.2 (resolves, undeclared, doomed)
node -e "console.log('phantom resolves today:', require('/tmp/nodeprobe/bins/node_modules/string-width/index.js') ? 'yes' : 'no')" # hoisted transitive of cowsay
node -p "Object.keys(require('/tmp/nodeprobe/bins/package.json').dependencies ?? {}).includes('string-width')" # false (used, never declared)
npm ls string-width --prefix /tmp/nodeprobe/bins # nested under cowsay (borrowed, not owned — declare it or drop it)
# BAD: `require('string-width')` bare in app code ("it resolves, ship it") —
# resolves until cowsay's next major drops it; then your diff is empty and your build is red
```

### 4) **Common confusion**

- "Hoisting means one copy always" — hoisting deduplicates *compatible* ranges (conflicting majors nest — `npm ls` shows the copies; singletons split across copies — state bugs with no code cause). One copy is the common case, never the promise.
- "`npm install` cleans up removals" — installs add, rarely prune (removed deps linger as ghosts — fresh CI differs from veteran laptops; `ci` wipes, `install` accumulates). Clean states come from `ci`, not from hope.
- "Phantoms are harmless if tests pass" — tests pass against *today's* hoist (parent upgrades re-hoist — breakage without diffs; lockfiles freeze versions, not hoist shapes). Declared-or-absent, no third state.
- "Deep nesting is always bad" — nesting is version honesty (conflicting ranges *must* coexist — nesting expresses it; forced flattening would lie about versions). Judge duplicates by count and cause, not by depth.

### 5) **Performance note**

Layout choices cost at install and cold-start: flattened trees install faster (fewer directories — marginal) but resolve ambiguously (phantoms — correctness first); nested duplicates multiply disk and parse time (three copies parsed per boot — measurable in serverless cold starts; `dedupe` where ranges allow). `files`-whitelisted publishes shrink downloads (fixtures excluded — install seconds saved per consumer, multiplied by every install everywhere). `node_modules` size dominates container layers (cache the install layer separately — Dockerfile ordering by change frequency). Optimize installs for determinism (frozen + declared), images for layering (deps cached, source last) — never for tree cleverness (exotic layouts save seconds, cost quarters).

### 6) **Mentor note**

Teach resolution as a walk ("trace this import upward aloud — name each level" until students climb past empty dirs unprompted). Demo the phantom live (the `string-width` catch above — resolves, undeclared, doomed; three commands, permanent habit). Drill `require.resolve` as the first diagnostic ("don't guess where it loads from — print it"). Watch for the deep-relativist (`../../../../` chains — fix with "what breaks when this file moves?") and the phantom-farmer ("it resolves" — fix with "who declares it?"). Review check: imports declared, resolutions printed not guessed, entries separated, shipped files curated, juniors trace the walk before blaming code.
