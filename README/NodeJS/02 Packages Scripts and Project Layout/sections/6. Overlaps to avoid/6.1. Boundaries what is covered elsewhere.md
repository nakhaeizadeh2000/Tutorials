## 6.1. Boundaries: what is covered elsewhere

### 1) **Runtime mechanics**

**Definition** — this domain owns *arrival* (how code lands on disk and how commands find it); *execution* lives in [Domain 01](<../../../01 Runtime Fundamentals and Mental Model/README.md>). Loader mapping rules (which system interprets a file) → [Domain 01/2.2](<../../../01 Runtime Fundamentals and Mental Model/sections/2. Process and modules/2.2. Modules in Node CJS and ESM interop.md>) (this domain's leaves assume the mapping and build packaging on top). Process lifecycle and exit contracts → [Domain 01/2.1](<../../../01 Runtime Fundamentals and Mental Model/sections/2. Process and modules/2.1. The process model globals and lifecycle.md>) (scripts exit by its rules; gates number outcomes by them). Scheduling and phases → [Domain 01/3.1](<../../../01 Runtime Fundamentals and Mental Model/sections/3. Execution model/3.1. The Node event loop phases in practice.md>) (never re-derived here). Execution questions go there; arrival questions stay here.

- **What problem it solves**: double-teaching (loader semantics re-explained per packaging leaf — copies drifting within a year; exit-code rules restated per gate — subtle contradictions accumulating). Single source of truth keeps every copy fresh (one definition, many links — updates land once). Readers navigate faster too (mapping confusion routes to 01/2.2 in one click — no packaging leaf wastes pages re-deriving `type`).
- **Modern guidance** — when a question reduces to execution, link out in one line (never re-derive — "loader mapping: [01/2.2]" then continue with the packaging point). When a Domain 01 reader arrives here, the prerequisites (domain index §0) tell them what's assumed — no surprise dependencies. Propose execution-side corrections upstream (errors in 01/2.2 fixed there — never patched by local restatement).

### 2) **Publishing and tooling depth**

**Definition** — this domain owns *consuming* (installing, resolving, running dependencies); *authoring and publishing* live in the TypeScript track. Package health and publish checks (publint, attw — is your package consumable?) → [TypeScript 16/2.3](<../../../../TypeScript/16 Tooling Language Server and Ecosystem/sections/2. Lint Format and Checks/2.3. publint attw and package health checks.md>). Version management and upgrade playbooks → [TypeScript 16/3.3](<../../../../TypeScript/16 Tooling Language Server and Ecosystem/sections/3. Debugging and Ecosystem/3.3. Version management and upgrade playbooks.md>). Publishing types (`exports` maps, `typesVersions`) → [TypeScript 12/3.3](<../../../../TypeScript/12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>). Consuming questions stay here; authoring questions go there.

- **Why it matters (maintainability)**: the author/consumer split prevents misplaced depth (publint rules re-derived in a consuming leaf — stale within a release; upgrade playbooks duplicated — two copies, one rots). Each side links the other (consumers hitting publish-side breakage route precisely — "your `exports` map excludes this subpath — [TS 12/3.3]" — instead of guessing). Boundaries make both sides shorter and both more accurate.
- **Modern guidance** — consume here, author there (a packaging question about *your* dependencies stays; about *your* published surface routes to TS 12/16). Quote the boundary in reviews ("consuming-side fix" vs "publishing-side fix" — different repos, different owners). Keep this domain's `exports` coverage consumer-shaped (what unlisted subpaths do to importers — leaf 1.1; how to author maps — TS 12/3.3).

### 3) **Deeper Node topics**

**Definition** — this domain is the map's second page, not the remaining territory: each area below gets its full treatment in its own domain (planned, see LOG — full coverage lands with those domains). Files, streams, and buffers → [Domain 03](<../../../03 Files Streams and Buffers/README.md>) (the pool's main customers — reading, transforming, backpressuring bytes). Events, networking, and HTTP → Domain 04 (emitters, sockets, bare servers — the runtime's public face). Child processes, workers, and clustering → Domain 05 (cores via processes — parallelism beyond the pool). Debugging, configuring, and shipping → Domain 06 (inspect, env, deploys — runtime literacy in production). Production synthesis and interviews → Domain 07 (the track's capstone).

- **Why it matters (operations)**: map-first learning prevents premature depth (streams before packaging — backpressure without installs is incantation; workers before resolution — threads without modules is hazard). Each domain assumes 01–02 (runtime vocabulary + packaging discipline — the language every later leaf speaks). Skipping ahead borrows confusion at interest; the map makes the territory cheap.
- **Modern guidance** — read in `NN` order (on-disk prefixes are curriculum order — 02 before 03, always). Treat textual forwards as promises, not placeholders (each names its owning domain — when the domain lands, links upgrade; until then, the name scopes the question). Record cross-domain fixes at the boundary (a resolution error found while writing streams gets fixed in 02/3.1 and linked — never duplicated into 03).
