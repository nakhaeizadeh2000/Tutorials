## 1.1. Selecting architectures under constraints

### 1) **Constraints first, patterns second**

**Definition** — architecture selection starts from inputs, never from preferences: traffic shape (rps, payload sizes, connection counts — measured or estimated with ranges), team shape (headcount, on-call burden, hiring — complexity budget), SLOs (latency percentiles, availability targets, recovery objectives — the contract). Outputs follow (cluster for fan-out — [Domain 05/3.1](<../../../05 Child Processes Workers and Clustering/sections/3. Multi-core servers/3.1. cluster for multi-core servers.md>); worker pools for CPU — [Domain 05/2.1](<../../../05 Child Processes Workers and Clustering/sections/2. Worker threads/2.1. Messaging and transfer.md>); frameworks per team shape — their tracks). Patterns answer constraints; preferences answer nothing.

- **What problem it solves**: resume-driven architecture (Kubernetes for a cron job — operational burden without traffic; microservices for three engineers — coordination overhead without scale; event sourcing for CRUD — complexity without audit need). Each mismatch bills daily (toil, cognitive load, incident surface) while serving no constraint. Constraint-first selection spends complexity where traffic demands (evidence per component — every moving part justified by a number).
- **Modern guidance** — write constraints before components (traffic ranges, team count, SLOs — one page; components proposed against it). Derive capacity from arithmetic (per-request budgets × traffic — cores, memory, connections; headroom explicit — [1.2. Capacity](<../1. Production judgment/1.2. Capacity and graceful degradation.md>)). Challenge every default (cluster? workers? framework? queue? — each earns its place against a constraint; unchallenged defaults accumulate). Revisit per order of magnitude (10× traffic re-runs the selection — yesterday's shape expires).

```javascript
// GOOD: constraints in, architecture out — runs on node v20.20.2 (routes stated, arithmetic shown)
function select({ rps, cpuMs, team, p99 }) {
  const coreMsPerSec = 1000; const coresNeeded = Math.ceil((rps * cpuMs) / coreMsPerSec); // capacity arithmetic (per-request budgets × traffic)
  const shape = cpuMs > 10 ? 'cluster + worker pool' : 'clustered node:http/Fastify'; // CPU-priced (off-loop past 10ms — Domain 05)
  const teamNote = team < 4 ? 'monolith-first (coordination budget small)' : 'services where bounded contexts demand'; // team-priced (complexity budget)
  return { coresNeeded, shape, teamNote, p99Budget: p99 };
}
console.log(JSON.stringify(select({ rps: 500, cpuMs: 40, team: 3, p99: 300 }))); // {"coresNeeded":20,"shape":"cluster + worker pool",...} (numbers, not tastes)
// BAD: "we use microservices" (identity as architecture — unpriced, unchallenged, unrevisitable) —
// patterns without constraints are fashion; fashion bills daily
```

### 2) **Boring wins ties**

**Definition** — among architectures meeting SLOs, choose the fewest moving parts (boring technology — battle-tested, well-understood, hireable; novelty budgeted — one experiment per system maximum, isolated, reversible). Boring compounds (known failure modes — runbooks exist; known hiring pool — onboarding fast; known limits — capacity math trusted). Novelty compounds the other way (unknown failures at 3 AM — no runbook; unknown limits — capacity guessed; unknown hiring — bus factor one).

- **Why it matters (operations)**: novelty incidents (unproven queue semantics — message loss discovered in production; exotic database — corruption without tooling; custom framework — maintainer departure ends support). Each novel component multiplies on-call burden (new failure modes × new runbooks × new expertise — small teams drown fastest). Boring fails boringly (known modes, existing playbooks, searchable errors — incidents routine, not existential).
- **Modern guidance** — count moving parts (databases, queues, services, vendors — fewer wins ties; each part justified against a constraint). Budget one novelty per system (experiment isolated — blast radius contained; reversible — rollback path tested; reviewed hardest). Prefer managed where undifferentiated (queues, stores, DNS — bought reliability beats built toil; build only the differentiating core). Revisit novelty at maturity (proven experiments graduate — unproven ones retire; novelty budget renewed, never accumulated).

```javascript
// GOOD: novelty budgeted, boring defaulted — runs on node v20.20.2 (parts counted, verdict stated)
const parts = ['node:http service', 'postgres (managed)', 'redis (managed)', 'experimental queue']; // moving parts (listed — count them)
const novel = parts.filter((p) => p.startsWith('experimental'));
console.log('moving parts:', parts.length, '| novel:', novel.length, novel.length <= 1 ? '(budget respected — one experiment, isolated)' : '(OVER BUDGET — cut or isolate)'); // 4 | 1 (boring wins ties)
// BAD: "event-driven microservices on the edge with CRDTs" for a form backend ("modern stack") —
// modernity unpriced: five novelties, zero runbooks, bus factor one — boring would have shipped in a week
```

### 3) **Decisions recorded**

**Definition** — Architecture Decision Records (one markdown file per crossroads — context, options considered, verdict, consequences, review date; stored beside code — versioned with it; short — one page, not a thesis). ADRs convert judgment into organizational memory (future engineers replay reasoning — not just results; revisits scheduled — verdicts expire with constraints; alternatives preserved — rejected options with reasons, not rumors). Unrecorded decisions evaporate (reasons leave with authors — re-litigation per hire; constraints shift silently — architecture frozen by forgetting).

- **Why it matters (maintainability)**: re-litigation cycles (new hire questions the monolith — no record of why; debate restarts from zero; quarters burn). Silent drift (constraints changed — verdict stale; nobody re-runs selection; architecture serves expired inputs). Oral tradition (decisions in chat history — unsearchable, unreviewed, bit-rotting; ADRs versioned, reviewable, greppable).
- **Modern guidance** — write ADRs at crossroads (framework choice, state strategy, parallelism shape — decided once, recorded once). Keep them short (context/options/verdict/consequences/review — five headings, one page; length discourages writing). Review on schedule (verdict dates — constraints re-checked; expired verdicts re-decided with new numbers). Link from code (config comments reference ADR numbers — reasoning one hop from implementation).

```markdown
<!-- GOOD: ADR-004 as complete-as-shown (copy to docs/adr/004-cluster.md — judgment replayable) -->
# ADR-004: Cluster with external sessions

- Verdict: cluster N=cores, sessions external ([Domain 05/3.1](<../../../05 Child Processes Workers and Clustering/sections/3. Multi-core servers/3.1. cluster for multi-core servers.md>) mechanics assumed)
```

### 4) **Common confusion**

- "Best practice means always" — practices priced per constraint (cluster for fan-out — wasteful for crons; workers for CPU — overhead for 1 ms tasks; best *given inputs*, never absolute). Context decides, slogans don't.
- "Boring means outdated" — boring means *proven* (recent boring exists — current LTS, managed services; outdated means unpatched — different axis entirely). Proven vs patched, not new vs old.
- "ADRs are bureaucracy" — ADRs are *memory* (one page per crossroads — cheaper than one re-litigation; bureaucracy blocks, records accelerate). Write to remember, not to comply.
- "Constraints stifle innovation" — constraints *fund* innovation (novelty budget explicit — experiments isolated and reversible; unconstrained novelty funds incidents). Budgets enable; blank checks endanger.

### 5) **Performance note**

Selection costs are capacity arithmetic, priced per deploy: right-sized cores (budgets × traffic — neither idle overspend nor saturated cliff; headroom explicit — 30–50% typical). Boring stacks perform predictably (known profiles — capacity math trusted; novel stacks profiled post-hoc — surprises billed). ADR overhead is writing time (one page per crossroads — minutes; re-litigation costs quarters). Optimize constraint accuracy first (traffic ranges measured — wrong inputs, wrong architecture), component count second (fewest meeting SLOs — boring wins), novelty last (one budgeted experiment — isolated, reversible).

### 6) **Mentor note**

Teach constraints-before-components ("state the traffic, team, and SLOs before naming anything" until pattern-first answers *sound* hollow). Demo the arithmetic live (500 rps × 40 ms — 20 cores on the whiteboard; then the monolith question — team of 3 decides; numbers routing). Drill ADR writing (one crossroads, one page, five headings — reviewed for brevity; re-litigation roleplay with and without the record). Watch for the fashionist ("modern stack" — fix with "which constraint needs it?") and the documentarian (ten-page ADRs — fix with "one page or it won't be read"). Review check: constraints stated, arithmetic shown, parts counted, novelty budgeted, decisions recorded, juniors route before reaching.
