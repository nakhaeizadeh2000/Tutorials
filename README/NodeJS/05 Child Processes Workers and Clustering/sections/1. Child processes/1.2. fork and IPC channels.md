## 1.2. fork and IPC channels

### 1) **fork is Node-to-Node**

**Definition** — `fork(modulePath)` spawns a Node subprocess with a built-in IPC channel (`child.send(msg)` / `process.on('message')` — JSON-structured messaging; `child.on('message')` the reverse). Both ends run the same runtime (shared language, shared stdlib versions — no serialization dialects), communicating as peers (parent delegates, child reports — request/response or fire-and-forget per message shape). fork suits CPU-adjacent delegation and isolation (crash in the child doesn't crash the parent — blast radius contained).

- **What problem it solves**: in-process crashes (a native segfault or OOM in a parser — whole service dies; forked parser dies alone, parent respawns — availability preserved). Blocking delegation without threads (heavy compute moved off the loop — parent schedules, child computes; simpler mental model than workers for coarse tasks). Privilege separation (child with fewer rights — file access scoped; compromise contained by process boundary).
- **Modern guidance** — fork coarse tasks (seconds of work, few messages — channel overhead per message, not per byte; chatty protocols belong in threads — leaf 2.1). Keep children stateless (inputs per message — respawn safe; stateful children complicate restarts — externalize or replicate). Guard the channel (`error`/`disconnect` listeners — dead children detected, not hoped alive; orphaned sends throw — handle, don't assume).

```javascript
// GOOD: delegate and report, same runtime both ends — runs on node v20.20.2 (41 + 1 = 42)
const { fork } = require('node:child_process'); const { writeFileSync } = require('node:fs');
writeFileSync('/tmp/nodeprobe/adder.cjs', `process.on('message', ({ a, b }) => process.send({ sum: a + b }));`); // child: compute + report
const child = fork('/tmp/nodeprobe/adder.cjs'); child.on('error', () => {}); // guarded channel (dead child detected)
child.on('message', ({ sum }) => { console.log('delegated sum:', sum === 42); child.kill(); }); // 42 (off-loop compute, structured reply)
child.send({ a: 41, b: 1 }); // delegate (JSON-structured — no dialects, same runtime)
// BAD: `fork` per request ("parallelism!") —
// fork costs milliseconds + megabytes each; per-request forking is process-per-request with extra steps — pool or thread it
```

### 2) **Channels carry protocol, not dumps**

**Definition** — IPC messages follow envelopes (`{ type, payload, id }` — type routes, payload carries, id correlates request/response; versioned — `{ v: 1 }` for evolution). Validation at receipt (shape-checked before use — malformed messages rejected with cause; a crashing parser fed by IPC is still a crash). Fire-and-forget vs request/response chosen per message (notifications need no reply — no correlation overhead; queries need ids — timeouts on unanswered, orphans on dead children).

- **Why it matters (correctness)**: schemaless drift (parent sends v2, child parses v1 — silent misreads; envelopes versioned — mismatch rejected loudly). Uncorrelated replies (two concurrent queries — responses unattributable; ids correlate; timeouts bound the wait). Unvalidated trust (child input treated as safe — compromised/misbehaving children inject; validate at every receipt — boundaries, not vibes).
- **Modern guidance** — envelope every message (`type`-first dispatch — switch on type, never on shape-sniffing). Correlate queries (id per request — pending map with timeouts; late replies dropped, not misapplied). Validate on receipt (both ends — cheap JSON-schema or manual guards; invalid → logged rejection, never thrown crash). Version the envelope (v field — mixed-version fleets during rollouts; old shapes supported or explicitly refused).

```javascript
// GOOD: enveloped, correlated, validated — runs on node v20.20.2 (echo:42, v1 accepted)
const { fork } = require('node:child_process'); const { writeFileSync } = require('node:fs');
writeFileSync('/tmp/nodeprobe/echoer.cjs', `process.on('message', (m) => { if (m && m.v === 1 && m.type === 'echo') process.send({ v: 1, id: m.id, type: 'echoed', payload: m.payload }); });`); // validate then reply (shape-checked, version-gated)
const child = fork('/tmp/nodeprobe/echoer.cjs'); child.on('error', () => {});
child.on('message', (m) => { console.log('enveloped:', m.v === 1 && m.id === 7 && m.payload === 42); child.kill(); }); // v1, correlated, validated
child.send({ v: 1, id: 7, type: 'echo', payload: 42 }); // envelope (type routes, id correlates, v evolves)
// BAD: `send(hugeObjectWithFunctions)` ("it worked locally") —
// functions don't serialize (silently dropped); Dates become strings; class instances become plain — channel carries JSON, nothing more
```

### 3) **Death supervised, restarts bounded**

**Definition** — supervised children: exits classified (code 0 — done, no restart; expected codes — task-failed, retry per policy; unexpected/signal — crash, respawn), respawns bounded (counter with window — 5 restarts in 60 s, then stop and page; unbounded respawn feeds crash loops — CPU burned, logs flooded, pager silent), death always logged (exit code + signal + uptime — the telemetry incidents need). Supervision is a loop (watch → classify → act), not a hope (children monitored, never assumed alive).

- **Why it hurts when missing (operations)**: crash loops unattended (child dies on boot config — respawned instantly, forever; CPU pinned, logs rotating, service effectively down with green supervisor). Silent deaths (no exit logging — "it just stopped" — uptime unknown, cause unknown; forensics start from zero). Zombie fleets (reparented strays per deploy — accumulating across releases; boxes filling with the undead).
- **Modern guidance** — classify before respawning (expected → policy retry; crash → bounded respawn; clean → release). Bound with windowed counters (N per T — exceeded means systemic, page the human; backoff between attempts — thundering contained). Log every death (code, signal, uptime, attempt — the record incidents read). Prefer orchestrators for fleets (systemd/K8s restart policies — battle-tested supervision; hand-rolled for libraries, platforms for services).

```javascript
// GOOD: classified, bounded, logged — runs on node v20.20.2 (2 crashes, then paged — loop starved, not fed)
const { fork } = require('node:child_process'); const { writeFileSync } = require('node:fs');
writeFileSync('/tmp/nodeprobe/crasher.cjs', `throw new Error('boot bug');`); // crashes immediately (the systemic kind)
let attempts = 0; const MAX = 2; const deaths = [];
function launch() { const c = fork('/tmp/nodeprobe/crasher.cjs'); const born = Date.now(); c.on('error', () => {});
  c.on('exit', (code, signal) => { attempts++; deaths.push(`${code ?? signal}@${Date.now() - born}ms`); // logged (code, uptime — forensics ready)
    if (attempts <= MAX) { console.log(`crash ${attempts}/${MAX} — respawning`); launch(); } // bounded (then stop)
    else console.log('cap hit — PAGING (not respawning):', deaths.join(', ')); }); } // systemic → human (loop starved)
launch();
// BAD: `child.on('exit', () => fork(script))` ("self-healing") —
// boot-bug children respawned forever: CPU pinned, logs flooded, service down with a healing narrative
```

### 4) **Common confusion**

- "fork shares memory with the parent" — separate processes (memory isolated — messages cloned through the channel; sharing needs workers + SharedArrayBuffer — leaf 2.2; fork's isolation *is* the feature). Clone, don't share.
- "send() is synchronous delivery" — send queues (backpressure on full channels — `send` returns false when saturated; large payloads chunked; receipt unordered across rapid sends? No — ordered per channel, but processing async). Queued, ordered, async.
- "Killing the parent kills forked children" — orphans adopted (same as spawn — leaf 1.1; supervision must kill the tree; disconnect first — `child.disconnect()` closes the channel, child exits when done). Trees killed deliberately.
- "IPC is fast enough for bulk data" — channels serialize JSON (bulk through stdio streams or shared memory — messages for control, streams for cargo; megabyte messages stall the channel). Control by message, cargo by stream.

### 5) **Performance note**

fork costs are process costs with channel overhead: spawn latency milliseconds + megabytes (pool/reuse for frequent tasks — fork per coarse job, never per request). Message throughput thousands/sec for small envelopes (JSON serialize/parse per message — bulk data via streams/shared memory, not messages; channel stalls past ~MB payloads). Supervision costs a watcher per child (negligible — counters and timers; crash-loop logging bounded by the cap). Optimize granularity first (coarse tasks — seconds of work per fork amortizes launch), message size second (small envelopes — cargo by stream), respawn policy always (bounded — crash loops cost more than any task they "save").

### 6) **Mentor note**

Teach fork as isolation with a phone line ("separate houses, JSON letters — draw the boundary" until shared-memory assumptions *look* wrong). Demo the crash contained (child throws — parent alive, respawns bounded; then in-process equivalent — all dead; isolation felt). Demo the envelope (unversioned mismatch — silent misread; then enveloped — loud rejection; protocol felt). Drill supervision ("exit 1, SIGKILL, code 0 — respawn, page, or release?" — three deaths, three remedies). Watch for the forker (fork-per-request — fix with launch-cost math: ms + MB × rps) and the unbounder ("self-healing" infinite — fix with the crash-loop story: pinned CPU, silent pager). Review check: tasks coarse, messages enveloped, receipts validated, deaths classified, respawns bounded, juniors supervise before delegating.
