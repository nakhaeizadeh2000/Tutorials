## 5.1. Common interview QA: processes, workers, cluster

### 1) **"CPU-bound task in Node?" — route it**

**Definition** — the offload screen: candidates route a CPU-heavy job (password hashing, image processing, report generation) through the decision tree. The expected answer: measure the loop cost first (lag probe — leaf 3.1 of Domain 01; past ~10 ms per task, move it), then worker pool (bounded to cores — results messaged back; leaf 2.1), processes only for isolation needs (crash-prone native — leaf 1.2), never the pool threads (libuv's crew serves I/O — compute steals I/O capacity). Numbers named (task ms, core count, pool size). The interviewer listens for "measure first" before "workers".

- **What problem it solves**: loop-blocked CPU in production (report endpoint freezing all concurrent users — the p99 cliff; moved to workers — flat latency). Pool-thread theft (crypto on libuv threads — I/O starving behind compute; workforce separation routes correctly). Premature parallelism (workers for 1 ms tasks — overhead without benefit; the tree keeps small work on the loop). Routing is architecture at small scale — every CPU call site answers it.
- **Modern guidance** — lead with measurement ("lag probe first — move past ~10 ms"; evidence, not instinct). Route by tree (leaf 3.1's procedure — trust-priced, CPU-priced, fan-out-priced). Name the pool numbers (cores counted, size stated, queue visible). Mention the failure handling (worker errors classified — supervision, leaf 1.2's loop applied to threads).

```javascript
// GOOD: measured, routed, pooled — runs on node v20.20.2 as ESM (hash off-loop, loop free)
import { Worker } from 'node:worker_threads'; import { writeFileSync } from 'node:fs';
writeFileSync('/tmp/nodeprobe/hasher.cjs', `const { parentPort } = require('node:worker_threads'); const { pbkdf2Sync } = require('node:crypto'); parentPort.on('message', (pw) => parentPort.postMessage(pbkdf2Sync(pw, 'salt', 10000, 32, 'sha512').toString('hex').slice(0, 16)));`); // CPU isolated (10k rounds off-loop)
const w = new Worker('/tmp/nodeprobe/hasher.cjs'); w.on('error', () => {});
w.postMessage('s3cret'); console.log('hash prefix:', await new Promise((res) => w.once('message', res)), '| loop never blocked'); await w.terminate();
// narration: "10 ms measured → worker pool of cores-1 → messaged results → supervised exits"
// BAD: "put it in a worker" (reflex without measurement — 1 ms tasks pooled, overhead unbilled) —
// reflexes skip the probe; probes precede pools
```

### 2) **Worker vs child process: which and why?**

**Definition** — the isolation judgment: candidates compare memory models, startup costs, and failure radii. Workers (threads, one process — shared-nothing by default, messaging cheap, startup light; crash takes all threads — fate shared). Child processes (separate processes — memory isolated, startup ms + MBs, crash contained — fate split). The decision factors: trust (untrusted → processes), granularity (fine tasks → workers, coarse → either), failure blast radius (acceptable shared fate → workers; contained → processes). Priced per workload, never per preference.

- **Why it matters (architecture)**: misrouted isolation fails characteristically (native parser in a worker — segfault kills all threads; chatty coordination over fork IPC — serialization dominates; per-request forks — launch overhead per call). Each misroute bills differently (total crashes, slow coordination, launch latency). The judgment answer names the trade before choosing — interviewers score the pricing.
- **Modern guidance** — state the memory model first ("workers: isolates, messaged; processes: separate, channeled" — the foundation). Price startup (workers lighter — pools for hot paths; fork heavier — coarse jobs). Name the blast radius ("who dies with whom?" — shared fate vs contained). Default workers for trusted CPU, processes for untrusted/crashy (the split in one breath).

```javascript
// GOOD: judgment with receipts — runs on node v20.20.2 (both isolated per model, receipts printed)
const { Worker } = require('node:worker_threads'); const { fork } = require('node:child_process'); const { writeFileSync } = require('node:fs');
writeFileSync('/tmp/nodeprobe/whoami.cjs', `require('node:worker_threads').parentPort.postMessage('thread:' + require('node:worker_threads').threadId);`); // worker identity (thread in process)
writeFileSync('/tmp/nodeprobe/whoami2.cjs', `process.send('process:' + process.pid);`); // process identity (own pid)
const w = new Worker('/tmp/nodeprobe/whoami.cjs');
console.log('worker:', await new Promise((res) => w.once('message', res)), '| main pid:', process.pid, '(thread ≠ process — shared fate)'); await w.terminate();
const c = fork('/tmp/nodeprobe/whoami2.cjs');
console.log('child:', await new Promise((res) => c.once('message', res)), '| main pid:', process.pid, '(own pid — contained fate)'); c.kill();
// spoken close: "threads share fate, processes contain it — trust and granularity decide"
// BAD: "workers are lighter, always use workers" (one metric — startup weight blind to blast radius) —
// lighter and shared-fate: native crashes take all threads; weight isn't the only price
```

### 3) **Cluster with sessions: design it**

**Definition** — the state trace: candidates design session handling under cluster (stateless workers + external store — any worker serves any request; session id in signed cookie — tamper-evident; store read per request — Redis/database; rolling restarts safe — workers disposable). The anti-design named (in-memory Map — logout roulette; sticky routing — imbalance + refork amnesia). The interviewer escalates (store down? — fail-closed vs stale-cache policy; cookie size? — id only, never payload; rotation? — versioned secrets). Externalized state answers every escalation; local state answers none.

- **Why it matters (operations)**: stateful-cluster bugs deploy on schedule (in-memory sessions + first cluster rollout = random logouts — the classic; sticky affinity + uneven clients = hot workers; refork + local rate limits = collective drift). Each traces to worker-local state under shared-port routing. Externalization retires the class (refork-safe, balance-free, rollout-proof).
- **Modern guidance** — externalize first (store-backed sessions — the design in one sentence). Sign the id (tamper-evident cookies — trust verified, not assumed). Keep workers disposable (kill -9 test — no loss beyond in-flight; the litmus). Version the format (rolling old+new workers — schemas compatible or explicitly gated).

```javascript
// GOOD: external sessions, disposable workers — runs on node v20.20.2 (both workers, one truth)
const cluster = require('node:cluster'); const http = require('node:http'); const os = require('node:os'); const fs = require('node:fs');
const PORT = 41238; const STORE = '/tmp/nodeprobe/sessions.json'; // external truth (any worker, survives refork)
if (cluster.isPrimary) { fs.writeFileSync(STORE, '{}');
  for (let i = 0; i < Math.min(2, os.availableParallelism()); i++) cluster.fork();
  setTimeout(async () => { const get = (p) => new Promise((res) => http.get(`http://127.0.0.1:${PORT}${p}`, (r) => { let b = ''; r.on('data', (c) => b += c); r.on('end', () => res(b)); }));
    await get('/login?id=u1'); const me1 = await get('/me?id=u1'); const me2 = await get('/me?id=u1');
    console.log('session reads back:', me1.startsWith('hello-u1') && me2.startsWith('hello-u1') ? 'consistent (any worker, one truth)' : 'MISMATCH'); // same user, possibly different workers, one answer
    for (const id in cluster.workers) cluster.workers[id].kill('SIGTERM'); setTimeout(() => process.exit(0), 300); }, 800);
} else { http.createServer((req, res) => { const url = new URL(req.url, 'http://x'); const store = JSON.parse(fs.readFileSync(STORE, 'utf8'));
    if (url.pathname === '/login') { store[url.searchParams.get('id')] = 'hello-' + url.searchParams.get('id'); fs.writeFileSync(STORE, JSON.stringify(store)); res.end('logged'); }
    else res.end(`${store[url.searchParams.get('id')] ?? 'no-session'}-from-${process.pid}`); }).listen(PORT, '127.0.0.1'); } // worker id appended (proves routing varies, answer doesn't)
// BAD: `const sessions = new Map()` + cluster ("works with 1 worker") —
// works until the second worker: routing varies, memory doesn't follow — logout roulette deals again
```

Rapid-fire drills (one sentence each — mechanism named): "`exec` on 50 MB output?" — killed past maxBuffer (stream with spawn — buffer caps, not hopes). "Unfilled `allocUnsafe` on a socket?" — disclosure (pool garbage on the wire — fill-then-freeze same tick). "Fork per request?" — ms + MB each (pools or workers for hot paths — fork coarse only). "`once` never firing?" — still leaks (unfired equals `on` — scope cleanup regardless). "Shared counter exact?" — Atomics only (bare `++` loses updates — races silent). "Primary serving traffic?" — supervise, don't serve (deaths need a responsive watcher). "Cluster + in-memory rate limit?" — collective drift (per-worker buckets reset on refork — externalize).

### 4) **Common confusion**

- "Interview parallelism answers differ from real ones" — the tree *is* the runbook (offload decisions in incidents; supervision in on-call; externalization in deploys — every answer here runs in production). Study shippable shapes, not recitals.
- "More parallelism always helps CPU" — helps to core count (past it, context churn; measured knees, not multiplied threads — leaf 4.1's demo). Cores bound compute; hope doesn't.
- "Cluster solves CPU-bound servers" — cluster multiplies loops (I/O fan-out scales; per-request CPU still blocks each worker's loop — CPU tasks need workers *inside* clustered processes; shapes compose). Fan-out × offload, not either.
- "Sessions just need stickiness" — stickiness postpones externalization (imbalance + refork amnesia remain; sticky accepted only protocol-bound with priced imbalance). Externalize first, affinitize almost-never.

### 5) **Performance note**

Interview parallelism answers price real costs: worker offload trades isolate overhead for loop freedom (measured ms vs blocked loop — the headline trade); transfer trades bookkeeping for bandwidth (bulk constant-time — the cargo answer); cluster trades memory × N for throughput ×N on I/O-bound (capacity math per box); external sessions trade a store round-trip for refork safety (microseconds beside correctness). Candidates connecting each answer to a number (task ms, pool size, store latency) signal production ownership — the trait senior loops hire for. Mechanisms plus measurements, always.

### 6) **Mentor note**

Teach interview prep as incident prep ("every question here is a 3 AM page in a suit" — map each to its leaf: offload→2.1, isolation→1.2, cluster→3.1, sharing→2.2, spawn→1.1). Drill the tree aloud with variants (untrusted + CPU-heavy — process containing workers? fan-out + sessions — cluster with store; derivors compose, reciters freeze). Drill supervision stories (death classified, cap paged — narrated in order). Watch for the reflex-pooler ("workers!" before measurement — fix with "how many ms?") and the stickifier ("affinity" — fix with "kill -9 a worker mid-session"). Review check: workloads routed, isolation priced, sessions external, rapid-fire derived, juniors measure before parallelizing.
