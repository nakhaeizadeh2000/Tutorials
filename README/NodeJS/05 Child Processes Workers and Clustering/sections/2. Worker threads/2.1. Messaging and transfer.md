## 2.1. Messaging and transfer

### 1) **Workers run JS in parallel**

**Definition** — `worker_threads` run JavaScript on separate threads in one process (each worker its own V8 isolate — no shared heap, no data races by default; `new Worker(file)` + `postMessage`/`on('message')` ports both directions). Unlike the pool (libuv's fixed crew for I/O), workers run *your* JS in parallel (CPU-bound loops off the loop — the event loop schedules while workers compute). Unlike fork (separate processes), workers share the process (lighter startup, structured-clone messaging, optional shared memory — leaf 2.2).

- **What problem it solves**: loop-blocked CPU (image hashing per upload — 200 ms of JS freezing every concurrent request; moved to a worker — loop free, latency flat). Process-heavy parallelism (fork per task — ms + MB each; workers start lighter, message faster — fine-grained parallelism affordable). Pool misuse (crypto on the loop's pool threads — saturating I/O capacity with compute; workers separate the workforces — I/O pool for I/O, workers for CPU).
- **Modern guidance** — move CPU off the loop past ~10 ms per task (measure first — leaf 3.1 of Domain 01's lag probe decides; migrate on evidence, not instinct). Keep workers task-scoped (compute in, result out — stateless handlers; stateful workers complicate restarts and scaling). Handle worker errors and exits (nonzero exit → classify like any child — leaf 1.2's supervision, applied to threads).

```javascript
// GOOD: loop free while workers compute — runs on node v20.20.2 as ESM (sum correct, loop responsive)
import { Worker } from 'node:worker_threads'; import { writeFileSync } from 'node:fs';
writeFileSync('/tmp/nodeprobe/summer.cjs', `const { parentPort } = require('node:worker_threads'); parentPort.on('message', (n) => { let s = 0; for (let i = 1; i <= n; i++) s += i; parentPort.postMessage(s); });`); // isolate (own heap, own thread)
const w = new Worker('/tmp/nodeprobe/summer.cjs'); w.on('error', () => {});
const t = Date.now(); w.postMessage(1e7); // heavy loop off-loaded (main thread schedules on)
const lag = setInterval(() => {}, 50); // loop witness (fires freely — unblocked)
const sum = await new Promise((res) => w.once('message', res)); clearInterval(lag); await w.terminate();
console.log('off-loop sum:', sum === 50000005000000, '| loop stayed free'); // true (50M computed beside the loop, not on it)
// BAD: `for (let i = 1; i <= 1e9; i++) ...` in a request handler ("simple math") —
// simple math at 10 rps saturates the loop; workers parallelize what handlers must not serialize
```

### 2) **Transfer beats copy**

**Definition** — messages cross isolates by structured clone (copied — safe, priced per byte; large buffers duplicated per message) or by transfer (`transferList: [buffer]` — ownership moved, zero-copy; sender detached after sending — use-after-transfer throws). The economics: small control messages clone freely (envelopes — negligible); bulk cargo transfers (megabyte buffers — copied once is once too often at throughput). Detachment enforces single ownership (no aliasing across threads — the data race that can't happen).

- **Why it matters (performance, correctness)**: clone-per-message bandwidth (10 MB image cloned per worker dispatch — GC churn, latency linear in size; transferred — constant time regardless). Use-after-transfer throws (`DOMException` on detached access — loud, immediate; the ownership made visible). Neutering surprises (transferred `ArrayBuffer` length reads 0 sender-side — by design; code reading it after sending is the bug).
- **Modern guidance** — clone control, transfer cargo (small messages plain; buffers via transferList — the rule in one breath). Size the message before choosing (KBs clone — MBs transfer; measured, not felt). Never touch after transfer (send is the last use — restructure producers to relinquish; detached access throws by design, not by accident). Prefer pools over per-task workers where transfer setup repeats (amortize — point 3).

```javascript
// GOOD: zero-copy handoff, ownership moved — runs on node v20.20.2 as ESM (filled, transferred, detached)
import { Worker } from 'node:worker_threads'; import { writeFileSync } from 'node:fs';
writeFileSync('/tmp/nodeprobe/taker.cjs', `const { parentPort } = require('node:worker_threads'); parentPort.on('message', (buf) => parentPort.postMessage(buf[0] + buf[buf.length - 1]));`); // reads transferred bytes
const buf = Buffer.alloc(1024); buf.fill(7); // cargo (1 KB — transfer shape identical at 1 GB)
const w = new Worker('/tmp/nodeprobe/taker.cjs'); w.on('error', () => {});
w.postMessage(buf, [buf.buffer]); // transferList (ownership moves — zero copy)
console.log('sender detached:', buf.buffer.byteLength === 0); // true (single ownership — use-after-transfer would throw)
console.log('worker read ends:', (await new Promise((res) => w.once('message', res))) === 14); await w.terminate(); // 7+7 (bytes arrived intact)
// BAD: `postMessage(hugeBuffer)` without transferList ("it arrives either way") —
// arrives copied: megabytes duplicated per dispatch, GC churning; transfer moves, clone duplicates
```

### 3) **Pools size the parallelism**

**Definition** — worker pools bound concurrency to cores (N workers for N cores — CPU-bound tasks parallelize to core count, no further; queue feeds tasks, results return via promises; `os.availableParallelism()` sizes the pool). Unbounded workers thrash (100 threads on 6 cores — context-switch overhead, memory per isolate, throughput *below* pooled). Pool discipline: fixed size, FIFO queue, per-task timeouts, worker recycling on errors (crashed workers replaced — supervision, leaf 1.2's loop applied).

- **Why it matters (performance)**: oversubscription collapse (threads ≫ cores — scheduler churn dominates; measured throughput drops past ~2× cores for CPU work; the "more is faster" fallacy with graphs). Unbounded growth (worker per request — isolates accumulate under burst; memory per isolate × burst = OOM; pools bound the multiple). Idle waste (pool sized once — cores added later unused; size at boot from `availableParallelism`, re-read on scaling events).
- **Modern guidance** — size pools to cores (`availableParallelism()` — minus one for the loop on mixed servers; exact for compute fleets). Queue, don't spawn (pending FIFO — backpressure visible as queue depth; depth graphed, alarmed). Timeout tasks (hung workers replaced — stuck compute detected, not awaited forever). Recycle on error (crashed worker → fresh isolate — state reset by construction; stateless handlers make this free).

```javascript
// GOOD: 2 workers, 4 tasks, bounded — runs on node v20.20.2 as ESM (all correct, max 2 concurrent)
import { Worker } from 'node:worker_threads'; import os from 'node:os'; import { writeFileSync } from 'node:fs';
writeFileSync('/tmp/nodeprobe/double.cjs', `const { parentPort } = require('node:worker_threads'); parentPort.on('message', ({ id, n }) => parentPort.postMessage({ id, r: n * 2 }));`); // id echoes (replies attributable)
const SIZE = Math.min(2, os.availableParallelism()); // bounded by cores (2 here — never unbounded)
let seq = 0; const pool = Array.from({ length: SIZE }, () => { const w = new Worker('/tmp/nodeprobe/double.cjs'); w.on('error', () => {}); // ONE dispatcher per worker (once-per-task would all fire on the next reply — once means removed-after, not queued)
  const pending = new Map(); w.on('message', ({ id, r }) => { pending.get(id)(r); pending.delete(id); }); // replies routed by id (attribution, not arrival order)
  return { run: (n) => new Promise((res) => { const id = ++seq; pending.set(id, res); w.postMessage({ id, n }); }), stop: () => w.terminate() }; });
let next = 0; const run = (n) => pool[next++ % pool.length].run(n); // round-robin across pool (queue visible as pending size)
console.log('pooled:', JSON.stringify(await Promise.all([1, 2, 3, 4].map(run))) === '[2,4,6,8]'); // true (4 tasks, 2 workers, attributed)
await Promise.all(pool.map((p) => p.stop())); console.log('pool size was:', SIZE, '| cores:', os.availableParallelism());
// BAD: `new Worker(...)` per request ("elastic parallelism") —
// isolates per request: memory × burst, startup × latency; elasticity without bounds is just unbounded
```

### 4) **Common confusion**

- "Workers share memory by default" — isolates by default (separate heaps — messages cloned; sharing needs `SharedArrayBuffer` + opt-in — leaf 2.2; default isolation *is* the safety). Clone first, share deliberately.
- "More workers than cores helps I/O" — workers serve CPU (I/O already multiplexes on the loop + pool — worker-per-connection wastes isolates; threads for compute, loop for I/O). Right workforce per workload.
- "Transfer is always faster" — transfer wins past copy cost (tiny messages clone cheaper than transfer bookkeeping — threshold in KBs, measured; control clones, cargo transfers). Sized choice, not dogma.
- "Terminated workers clean everything" — terminate stops the thread (pending messages dropped — in-flight tasks lost; graceful drain before terminate — results collected, then freed). Drain, then terminate.

### 5) **Performance note**

Worker costs are isolate + message costs, priced per task: startup milliseconds + MBs (pool amortizes — spawn rarely, reuse always); structured clone bandwidth-bound (GB/s memory copies — fine for control, priced for cargo; transfer constant-time — the bulk answer); oversubscription taxed in context switches (throughput peaks near core count — measured per workload, never assumed). Pool queues add scheduling latency (microseconds — invisible beside compute milliseconds). Optimize granularity first (coarse tasks amortize startup), cargo path second (transfer bulk — clone control), pool size always (cores ± loop — measured peak, not max threads).

### 6) **Mentor note**

Teach workers as CPU off-ramps ("loop free while workers compute — watch the witness fire" until offloading *looks* obvious past 10 ms). Demo the blocked loop first (heavy loop inline — lag probe screams; then worker version — silent; evidence before remedy). Demo transfer (clone vs transfer timings on 10 MB — linear vs flat; ownership felt via detachment). Drill pool sizing ("how many workers? — count cores aloud"; unbounded version's thrash under burst). Watch for the inliner ("simple math" in handlers — fix with the lag probe) and the spawner (worker-per-request — fix with isolate-cost math: MB × rps). Review check: CPU measured before moving, cargo transferred, pools bounded to cores, workers supervised, juniors message before sharing.
