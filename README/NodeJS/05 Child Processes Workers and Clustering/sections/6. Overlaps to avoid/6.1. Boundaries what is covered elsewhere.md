## 6.1. Boundaries: what is covered elsewhere

### 1) **Loop and pool execution**

**Definition** — this domain owns the *escape hatches* (processes, threads, cores); the *loop they relieve* lives in [Domain 01](<../../../01 Runtime Fundamentals and Mental Model/README.md>) and is assumed, never re-taught. Three-box model and pool-vs-loop diagnosis → [Domain 01/1.1](<../../../01 Runtime Fundamentals and Mental Model/sections/1. Runtime identity and setup/1.1. What Node.js is and is not.md>) (which box is slow decides whether parallelism helps at all). Phase scheduling and nextTick discipline → [Domain 01/3.1](<../../../01 Runtime Fundamentals and Mental Model/sections/3. Execution model/3.1. The Node event loop phases in practice.md>) (lag probes measure before offloading — no probe, no pool). Process lifecycle and exit codes → [Domain 01/2.1](<../../../01 Runtime Fundamentals and Mental Model/sections/2. Process and modules/2.1. The process model globals and lifecycle.md>) (children exit by its rules). Diagnosis questions route in one line.

- **What problem it solves**: double-teaching (loop mechanics re-explained per worker leaf — copies drifting; exit codes restated per supervisor — contradictions accumulating). Single source of truth keeps every copy fresh (one definition, many links — updates land once). Readers navigate faster too (blocking confusion routes to 01/3.1 in one click — no parallelism leaf wastes pages re-deriving phases).
- **Modern guidance** — when a question reduces to execution, link out in one line (never re-derive — "lag pricing: [01/3.1]" then continue with the parallelism point). When a Domain 01 reader arrives here, the prerequisites (domain index §0) tell them what's assumed — no surprise dependencies. Propose execution-side corrections upstream (errors in 01 fixed there — never patched by local restatement).

### 2) **Streams and messaging patterns**

**Definition** — this domain owns process/thread *mechanics* (spawn, message, share, fork); *stream plumbing* and *design shapes* live elsewhere. Pipeline lifecycle, backpressure, and byte framing (child stdio pipelined — same interface, new venue) → [Domain 03](<../../../03 Files Streams and Buffers/README.md>) (assumed throughout — never re-derived). Observer/mediator coordination shapes (who notifies whom, hub topologies) → the [Design Patterns track](<../../../../DesignPatterns/README.md>) (channels here carry bytes; patterns there carry intent). Plumbing and shape questions route out in one line.

- **Why it matters (maintainability)**: the mechanics/plumbing/pattern split prevents misplaced depth (backpressure re-derived per stdio pipe — stale within a release; mediator topologies re-justified per fork tree — two copies, one rots). Each side links the other (supervision trees shaped by mediator thinking route precisely — "coordination: [Patterns]" — instead of guessing). Boundaries make all three sides shorter and more accurate.
- **Modern guidance** — mechanics here, plumbing and patterns there (a stdio question about *pacing* routes to 03; about *topology* routes to Patterns; about *launch* stays). Quote the boundary in reviews ("mechanics-side" vs "plumbing-side" vs "pattern-side" — different venues, different owners). Keep this domain's channel coverage control-shaped (envelopes, ids, timeouts — leaves 1.2/2.1; byte movement — 03).

### 3) **Debugging and production**

**Definition** — this domain launches and supervises parallelism; *observing* it and *shipping* it live in the remaining domains (planned, see LOG — full coverage lands with those domains). Debugging workers and processes (`node --inspect` per worker, profiling parallel code) → Domain 06 (inspect, env, deploys — parallelism observability in production). Production synthesis and interviews → Domain 07 (the track's capstone — when all seven domains combine under load). Each owned there; launching questions stay here.

- **Why it matters (operations)**: launch/observe/ship confusion misroutes learning (workers spawned before knowing how to profile them — blind parallelism; clusters shipped before inspectable — undebuggable fleets). Clean order learns faster (launch, then observe, then ship — each in its venue, each assumed by the next).
- **Modern guidance** — read in `NN` order (on-disk prefixes are curriculum order — 05 before 06, always). Treat textual forwards as promises, not placeholders (each names its owning domain — when the domain lands, links upgrade; until then, the name scopes the question). Record cross-domain fixes at the boundary (a worker bug found while debugging gets fixed in 05/2.1 and linked — never duplicated into 06).
