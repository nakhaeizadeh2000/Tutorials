## 6.1. Common interview QA arrays tuples and collections

Answer collection questions by naming a contract, demonstrating the relevant operation and stating its limit. These questions test reasoning about data and evidence; they are not a hiring rubric or a claim that remembering one container rule predicts engineering ability.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence under its filename. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`; run `node dist/FILE.js`. Activate negatives individually with those flags and --noEmit instead of --outDir dist.

### 1) **When does a tuple express more than a union array?**

A tuple gives particular positions types and required presence, while (string | number)[] describes an open list of either kind of value. A tuple is useful when the positions have roles, including a homogeneous numeric range. A fresh malformed tuple and a literal out-of-range index are rejected. Mutable tuple array methods can still change its length, so do not claim all pushes beyond arity fail. [Tuple contracts](<../2. Tuple Types/2.1. Fixed arity tuples labels and optional elements.md>) owns that limit.

Predict each observation in contracts.ts before compiling. Later questions refer back to the same program.

```typescript
type Pair = [host: string, port: number];
const pair: Pair = ["db", 5432];
// const swapped: Pair = [5432, "db"]; // TS2322
// console.log(pair[2]); // TS2493
pair.push("debug");
console.log(pair.length, pair.join(","));
const source = ["Ada"];
const view: readonly string[] = source;
source.push("Lin");
const draft = [...view];
draft.push("New");
console.log(view.join(","), draft.join(","), Object.isFrozen(view));
// const reverseAssignment: string[] = view; // TS4104
const byName = new Map<string, number>([["__proto__", 1]]);
const dictionary: Record<string, unknown> = { __proto__: null };
dictionary["__proto__"] = 1;
console.log(byName.get("__proto__"), dictionary["__proto__"], Object.hasOwn(dictionary, "__proto__"));
type Key = "a" | "b";
const complete: Record<Key, number> = { a: 1, b: 2 };
const incomplete = new Map<Key, number>();
console.log(complete.b, incomplete.get("b"));
// const missing: Record<Key, number> = { a: 1 }; // TS2741
const empty: string[] = [];
const first = empty[0];
console.log(first === undefined ? "missing" : first.toUpperCase());
// const guaranteed: string = empty[0]; // TS2322 with noUncheckedIndexedAccess

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type StaticLength = Expect<Equal<Pair["length"], 2>>;
type MissingRead = Expect<Equal<typeof first, string | undefined>>;
```

The output is `3 db,5432,debug`, `Ada,Lin Ada,Lin,New false`, `1 1 true`, `2 undefined`, then `missing`; both probes compile. The first line deliberately contrasts the tuple's static length type with an accepted mutable push. The other observations separate a shared readonly view, an independent outer draft, two dictionary representations, finite required properties and a possibly missing array read.

### 2) **Why can a mutable array flow into a readonly array view?**

The mutable array supplies the reads the readonly contract needs. A readonly array does not supply ordinary push, sort or writable index operations required by a mutable array contract, so the reverse assignment fails. Copy when a genuinely independent mutable outer array is needed. This is an assignment/capability distinction, not proof that TypeScript enforces invariance for every mutable element relationship.

In contracts.ts, view changes after source.push because they share one array. The view is also unfrozen. Readonly cannot revoke another alias or make nested mutable objects immutable. The draft has an independent outer array, but object elements would still need their own copy policy. [Readonly arrays](<../1. Array Types/1.2. Readonly arrays and mutable vs frozen arrays.md>) explains those cases in full.

### 3) **How can a filter narrow without a written is annotation?**

A suitable comparison callback can acquire an inferred predicate, so the narrowing overload can produce a more specific element array. An explicit boolean return type can hide that stronger signature. Boolean itself does not become a general null-exclusion predicate. Also inspect data policy: truthiness removes the empty string and zero, which may be valid values. [The primary inferred-predicate notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-5.html#inferred-type-predicates) explain the conditions; the [array-method owner](<../1. Array Types/1.3. Array methods map filter reduce typed precisely.md>) provides the broader contrasts.

Save as selection.ts.

```typescript
const values: (string | null)[] = ["", "Ada", null];
const inferred = values.filter(value => value !== null);
const booleanOnly = values.filter((value): boolean => value !== null);
const truthy = values.filter(Boolean);
console.log(inferred.length, inferred.join("|"), truthy.length);
// booleanOnly.map(value => value.toUpperCase()); // TS18047
// truthy.map(value => value.toUpperCase()); // TS18047
const mixed: (number | string)[] = [1, "Ada"];
const found = mixed.find(value => typeof value === "string");
console.log(found?.toUpperCase() ?? "missing");
// found.toUpperCase(); // TS18048

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Inferred = Expect<Equal<typeof inferred, string[]>>;
type BooleanOnly = Expect<Equal<typeof booleanOnly, (string | null)[]>>;
type Truthy = Expect<Equal<typeof truthy, (string | null)[]>>;
type Found = Expect<Equal<typeof found, string | undefined>>;
```

The output is `2 |Ada 1`, then `ADA`; all four probes compile. Find can narrow the matched type too, but still returns undefined when there is no match. A handwritten predicate must also be correct; its signature is a claim the checker can trust, not an automatic verification of its body.

### 4) **How would you choose Record, Map or an object dictionary?**

Ask whether keys must be complete, what key identity means, how missing entries are represented and what operations/transport are needed. A finite Record requires named properties. A Map with the same finite key type can still be empty. Map is useful for entry iteration, dynamic membership and identity keys; a null-prototype object with deliberate own-property/value checks is also a valid string dictionary, as contracts.ts demonstrates.

A Map instance has a prototype, while its entries occupy a separate namespace managed by set/get/has. An ordinary numeric assignment to the inherited __proto__ setter is ignored on the demonstrated runtime; that observation alone is not proof of global prototype pollution. Numeric object properties coerce to string keys, symbol properties have different enumeration/JSON behavior, and fromEntries is not a universal lossless Map codec. Use [Record versus Map](<../3. Collections and Selection/3.2. Record vs Map indexed access vs hashed keys.md>) for the tested selection table and [worked collection APIs](<../3. Collections and Selection/3.1. Map and Set typing generics over collections.md>) for actual presence, conversion and supported features.

### 5) **What changes when noUncheckedIndexedAccess is enabled?**

It makes ordinary potentially missing array/index-signature reads include undefined; required tuple slots and declared finite properties can remain present. It is separate from strict. In contracts.ts, empty[0] requires an absence policy while complete.b remains number. A tuple's static guarantees still have the mutable-method limits shown in question 1.

The flag adds no runtime check and does not change emitted JavaScript. A non-null assertion can suppress a diagnostic without making a value exist. Investigate each new error and choose an appropriate read check or a stronger justified contract; do not count diagnostics as verified production incidents or mechanically append assertions. The [index-flag pitfalls](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by collection misunderstandings.md>) execute both flag settings and the asserted-read failure.

### 6) **Common confusion**

Array and tuple syntax describe static contracts rather than runtime validation. Readonly does not mean independent or frozen, and a finite Map key type does not require finite completeness. A narrowing filter can be inferred, but its condition still executes and may remove values the application intended to keep.

Type precision and semantic correctness are different. A function returning a number can compute the wrong number, and a complete guard table can contain the wrong decision. Explain the admitted operation and the actual tested outcome rather than offering one universal container rule.

### 7) **Performance note**

Types, readonly modifiers and index-option checks erase. Pushes, copies, membership operations, filtering and string methods remain. Their cost depends on the actual work and input. No universal Map hash complexity, array-versus-tuple checker formula, review productivity result or “highest yield” ranking was measured. Use the operation and workload when discussing performance.

### 8) **Mentor note**

Ask for a counterexample after each answer: an accepted tuple push, a changed readonly view, an inferred predicate, an empty finite-key Map or an asserted missing read. A sound explanation states why the counterexample is allowed and what additional mechanism would meet the intended requirement.

For practice, implement firstString(values: readonly unknown[]): string | undefined using find with a typeof comparison. Verify that [1, "", "Ada"] returns the empty string, [] returns undefined and [{ name: "Ada" }, 2] also returns undefined. Replacing the comparison with Boolean must fail the declared return contract because an arbitrary truthy unknown is not proved to be a string. A second variant that finds only nonempty strings could compile, but fails this exercise's earliest-string policy. Test both type and value requirements.
