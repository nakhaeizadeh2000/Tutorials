## 6.1. Common interview QA — arrays, tuples and collections

### 1) **When is `[string, number]` preferable to `(string | number)[]`?** (arity + position vs open list)

**Definition** — `[string, number]` promises exactly two elements in exactly that order (arity + position contracts); `(string | number)[]` promises any count in any order (element contract only). Prefer the tuple when length is fixed and positions carry meaning (pairs, entries, coordinates, protocol frames); prefer the array when length varies or elements are interchangeable (lists, lines, tags).

**What problem it solves / history** — interviewers ask this to test contract thinking: candidates answering "tuples for pairs" describe habit; candidates adding "arity errors, position types, push-beyond-arity rejected" describe *which guarantees* each shape provides — and therefore predict the swap/overflow bugs the wrong choice permits.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), answer with the one-sentence test ("fixed count + mixed meaning → tuple; open count or uniform meaning → array") plus the failure each prevents (swapped positions compile under arrays; unbounded growth errors under tuples). Full treatment in [2.1. Fixed arity tuples](<../2. Tuple Types/2.1. Fixed arity tuples labels and optional elements.md>) + [3.3. Choosing](<../3. Collections and Selection/3.3. Choosing Array Tuple ReadonlyArray and readonly tuples.md>).

**Runnable example** — contracts compared (`tsc --strict`):

```typescript
type Pair = [host: string, port: number];
const p: Pair = ["db", 5432];
console.log(p[0].toUpperCase(), p[1].toFixed(0)); // DB 5432
// const swapped: Pair = [5432, "db"]; // error TS2322 — positions enforced
const list: (string | number)[] = [5432, "db"]; // compiles — no positions to enforce
console.log(list.length); // 2 — length is all arrays promise
```

**Common confusion** — "tuples are just short arrays" — tuples add arity + position *contracts* (compile-time rejections arrays never produce) — same emit, different proofs. "single-type tuples are pointless" — `[id: string]` still enforces arity-1 and labels — niche but honest.

**Performance note** — identical emit (plain arrays); tuple checks cost O(arity) per literal (tiny) — contract strength is free at runtime.

**Mentor note** — strong answers volunteer the *failure prevented* (swap compiles under arrays) unprompted — probe with "what bug does each choice permit?" when candidates stop at definitions. Hiring signal: contract-first reasoning predicts API-design quality.

**Cross-links** — fixed arity → [2.1. Fixed arity tuples](<../2. Tuple Types/2.1. Fixed arity tuples labels and optional elements.md>); choosing → [3.3. Choosing](<../3. Collections and Selection/3.3. Choosing Array Tuple ReadonlyArray and readonly tuples.md>).

### 2) **Why does `readonly string[]` accept `string[]` but not the reverse?** (read-covariance, write-invariance)

**Definition** — mutable → readonly flows (a mutable list satisfies every read a readonly consumer needs: iteration, indexing, `length`, `map`); readonly → mutable errors (readonly cannot satisfy future writes: `push`, index-write, `sort`). Capability narrows (fewer methods) while admission widens (more sources) — the array instance of use-site variance from 02/3.1.

**What problem it solves / history** — one-direction flow lets APIs accept every caller's list while guaranteeing non-mutation — callers pass freely (`string[]`, tuples, literals), implementations stay constrained. The reverse ban is what makes the guarantee trustworthy: no silent path converts a frozen snapshot back into a mutable alias without an explicit, reviewable copy.

**Modern guidance** — as of TypeScript 5.9 era, answer with the capability sentence ("reads need less than writes promise") plus the copy-not-cast escape (`[...ro]`). Full treatment in [1.2. Readonly arrays](<../1. Array Types/1.2. Readonly arrays and mutable vs frozen arrays.md>).

**Runnable example** — direction enforced (`tsc --strict`):

```typescript
function readAll(xs: readonly string[]): number { return xs.length; }
const m: string[] = ["a"];
console.log(readAll(m), readAll(["l"] as const)); // 1 1 — both flow in
// function writeAll(xs: string[]): void { xs.push("x"); }
// const ro: readonly string[] = ["a"];
// writeAll(ro); // error TS2345 — readonly cannot satisfy future writes
const copy: string[] = [...m]; // escape via copy, never cast
console.log(copy.length); // 1
```

**Common confusion** — "readonly accepts fewer values" — accepts *more* (every mutable list plus tuples/literals); *does* less (no mutation) — admission widens as capability narrows. "tuples don't flow into readonly arrays" — tuples are array subtypes — `readonly ["a"]` satisfies `readonly string[]` (fixed length is a stronger promise, still compatible).

**Performance note** — zero runtime delta (erased modifier); copies (`[...ro]`) cost O(n) at explicit boundaries — the only runtime content, budgeted and visible.

**Mentor note** — ask "which direction flows, and what operation would break if the reverse did?" (`push` on a frozen tuple) — mechanism (write-invariance) over memorization. Follow-up: "how do you escape?" (copy — and why not cast: aliasing).

**Cross-links** — readonly lifecycle → [1.2. Readonly arrays](<../1. Array Types/1.2. Readonly arrays and mutable vs frozen arrays.md>); variance rules → [3.1. Variance](<../../../02 The Type System Core/sections/3. Soundness and variance/3.1. Covariance contravariance and invariance who varies which way.md>).

### 3) **How does `filter` narrow with an `is` predicate — and why not with `Boolean`?** (predicate vs truthiness overloads)

**Definition** — `filter<S extends T>(p: (x: T) => x is S): S[]` is a *narrowing overload*: the callback's `is` return teaches the checker the output element type (`string[]` from `(string|null)[]`). `filter(Boolean)` calls the `(x: T) => unknown` overload (truthiness, no type information) — output keeps the input element type. Narrowing requires a *declared* predicate; truthiness functions return `boolean`, which proves nothing about *which* members survive.

**What problem it solves / history** — `filter(Boolean)` folklore ("it removes nulls, and types follow") compiled in value terms (nulls do vanish at runtime) while types stayed wide (`(string|null)[]` — downstream `toUpperCase` erroring correctly on a now-impossible `null`). The `is`-predicate overload aligns the type with the runtime: survivors proven, downstream casts deleted.

**Modern guidance** — as of TypeScript 5.9 era, write `is`-predicates for every narrowing filter (`isString`, `isDefined`, `isNonNull` — project-wide shared guards); never rely on `Boolean` for type narrowing (runtime-fine, type-blind). Full treatment in [1.3. Array methods](<../1. Array Types/1.3. Array methods map filter reduce typed precisely.md>).

**Runnable example** — predicate narrows, Boolean doesn't (`tsc --strict`):

```typescript
const xs: (string | null)[] = ["a", null];
const isS = (x: string | null): x is string => x !== null;
const narrowed: string[] = xs.filter(isS); // string[] — predicate taught the checker
console.log(narrowed.map((s) => s.toUpperCase()).join(",")); // A
const wide = xs.filter(Boolean); // (string | null)[] — truthiness proves no types
// wide.map((s) => s.toUpperCase()); // error TS18048 — correctly still nullable
console.log(wide.length); // 1 — runtime filtered, types honest about the gap
```

**Common confusion** — "`Boolean` is a type guard" — returns `boolean` (a value), not a predicate (a type claim) — the stdlib has no `filter(Boolean)` narrowing overload for general unions. "custom `is` predicates validate" — predicates *assert* (caller trusts the implementation) — a lying predicate (`x is string` returning true for numbers) corrupts downstream soundly-typed code; test predicates like any logic. "narrowing works for `find` too" — `find` returns `T | undefined` regardless (absence orthogonal to narrowing) — combine (`find` + predicate still yields `S | undefined`).

**Performance note** — predicate vs `Boolean` identical emit (one callback per element); the dividend is deleted downstream assertions/casts, not speed.

**Mentor note** — hover both results (`string[]` vs `(string|null)[]`) — the tooltip pair teaches overload-driven narrowing faster than any explanation. Exercise: convert three `filter(Boolean)` sites to shared `is`-guards and delete the downstream `!` assertions — assertion count is the precision dividend.

**Cross-links** — predicates → [3.3. Custom narrowers](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.3. Custom narrowers predicates asserts and type guards on unions.md>); methods → [1.3. Array methods](<../1. Array Types/1.3. Array methods map filter reduce typed precisely.md>).

### 4) **`Record<K, V>` vs `Map<K, V>` — which for dynamic user-supplied keys, and why?** (known-serializable vs hashed-dynamic)

**Definition** — dynamic user-supplied keys → `Map`: clean key space (no prototype pollution), typed key kinds (no stringification surprises), `V | undefined` reads (absence honest), deletion-friendly internals. `Record` serves finite, string, JSON-needing, stable key sets — user input fails all four conditions, so `Map` wins before any further analysis.

**What problem it solves / history** — user-keyed `Record<string, …>` shipped prototype-pollution vulnerabilities (`"__proto__"` assignments), stringification bugs (`1` vs `"1"` same slot), and `undefined`-lies on missing keys — each a security-or-correctness incident with types green. Interviewers probe this to test security-aware container choice, not just API recall.

**Modern guidance** — as of TypeScript 5.9 era, answer with pollution first (security), stringification second (correctness), absence-honesty third (types) — then the four-question table. Full treatment in [3.2. Record vs Map](<../3. Collections and Selection/3.2. Record vs Map indexed access vs hashed keys.md>).

**Runnable example** — pollution class avoided structurally (`tsc --strict`):

```typescript
const sessions = new Map<string, number>();
console.log(sessions.get("__proto__") ?? "absent"); // absent — clean key space, honest read
const reg: Record<string, number> = {};
reg["__proto__"] = 1; // prototype shadow — value stored nowhere visible
console.log(Object.keys(reg).length); // 0 — pollution, typed green
```

**Common confusion** — "`Object.create(null)` suffices" — fixes pollution only (stringification, undefined-lies, missing `size`/iteration guarantees remain) — `Map` wins on four axes, not one. "`Map` can't cross JSON" — `Object.fromEntries` at the boundary (one explicit line) — serialization is a boundary concern, not a storage one.

**Performance note** — `Map` O(1) amortized with higher constants; delete-heavy user-keyed workloads strongly favor it (no hidden-class transitions) — workload shape decides, as always.

**Mentor note** — the `"__proto__"` demo (`Object.keys` showing 0) converts faster than any threat model. Hiring signal: pollution-first answers think adversarially; API-only answers think syntactically.

**Cross-links** — decision table → [3.2. Record vs Map](<../3. Collections and Selection/3.2. Record vs Map indexed access vs hashed keys.md>); Map typing → [3.1. Map and Set](<../3. Collections and Selection/3.1. Map and Set typing generics over collections.md>).

### 5) **What does `noUncheckedIndexedAccess` change — and what breaks when you enable it?** (index honesty + migration)

**Definition** — the flag adds `| undefined` to every *open* index read (`arr[i]: T` → `T | undefined`; `dict[k]: V` → `V | undefined`); fixed tuple positions stay non-optional (arity proves presence). Enabling surfaces dozens of latent crashes as narrow-or-error sites — each fixed with `?.`/`??`/early-return, never `!`. The highest-yield single flag flip in collection-heavy codebases.

**What problem it solves / history** — default indexing lies (`users[0]: User` on empty pages — the 5.1 promise-4 incident class) with `strict: true` fully green — the last adjacent hole most codebases leave open. The flag closes it: presence becomes unignorable at every `[i]`/`[key]` read, converting a runtime-crash class into compile-time narrowing discipline.

**Modern guidance** — as of TypeScript 5.9 era, enable in every strict tsconfig; triage the resulting errors as a latent-incident backlog (each a crash that hadn't happened *yet*); fix with narrowing only (`!` migrations preserve every crash while silencing the flag). Full treatment in [5.1. Production bugs](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by collection misunderstandings.md>) promise 4 + [13 Configuration](<../13 Configuration and Compiler Options/README.md>) (textual forward).

**Runnable example** — flag converts crashes to narrows (`tsc --strict`):

```typescript
interface U5 { name: string; }
function first(users: U5[]): string {
  return users[0]?.name ?? "anonymous"; // honest under the flag; harmless without it
}
console.log(first([]), first([{ name: "ada" }])); // anonymous ada
// without the flag users[0].name compiles AND throws on [] — the lie this flag deletes
```

**Common confusion** — "the flag breaks valid code" — reveals unhandled absence in valid-*looking* code — breakage is diagnosis; `?.` fixes are one line each. "tuples need the same treatment" — fixed positions prove presence by arity (`pair[0]` on `[A, B]` stays `A`) — open indexing is the hole, not positions. "`!` migrates faster" — redistributes the lie per site (every crash preserved, flag silenced) — slower *and* dishonest.

**Performance note** — zero emit delta (pure check-time `| undefined`); narrowing branches (`?.`) cost one check each vs unbounded `TypeError`s — highest-ROI flag by post-mortem count.

**Mentor note** — enable Friday, triage Monday (dozens of errors = latent-incident backlog, prioritized free). Rule: `!` on indexed reads fails review; narrowing is the only accepted fix.
