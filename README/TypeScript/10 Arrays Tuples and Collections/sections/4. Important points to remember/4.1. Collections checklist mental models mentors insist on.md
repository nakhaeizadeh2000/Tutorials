## 4.1. Collections checklist — mental models mentors insist on

### 1) **Arrays for lists, tuples for slots, Maps for dynamic keys** (container follows data shape)

**Definition** — the selection instinct in one line per shape: open same-type sequences → `T[]`; fixed-arity mixed slots → tuples; finite key sets → `Record`/interfaces; dynamic/user keys → `Map`; membership registries → `Set`. Shape-first thinking (what *is* the data?) before API thinking (what do I *do* with it?) — the container follows the shape, methods follow the container.

**What problem it solves / history** — habit-containers (`Record<string, unknown>` for everything keyed, `any[]` for everything listed, parallel arrays for pairs) produced all four 5.1 incident classes — each a shape/container mismatch compiling silently. Shape-first selection deletes the mismatch at declaration: the data's own answers (how many? same type? keyed? mutated?) pick a container that cannot express the bug.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), run the shape questions ([3.3. Choosing](<../3. Collections and Selection/3.3. Choosing Array Tuple ReadonlyArray and readonly tuples.md>) + [3.2. Record vs Map](<../3. Collections and Selection/3.2. Record vs Map indexed access vs hashed keys.md>)) on every new collection declaration; re-run when answers change. See promises 2–4 for the lifecycle, literal, and review halves of the checklist.

**Runnable example** — shape picks honestly (good vs bad, `tsc --strict`):

```typescript
// good — each shape gets its container: tuple slots, array list, Map registry
type CfgPair = [key: string, value: string]; // fixed 2, mixed → tuple
const tags: string[] = ["a", "b"]; // open, same → array
const byId = new Map<string, number>(); // dynamic keys → Map
byId.set("u1", 1);
const [k, v]: CfgPair = ["host", "h"];
console.log(k.toUpperCase(), tags.length, byId.get("u1")?.toFixed(0)); // HOST 2 1

// bad — one habit-container (array) for all three shapes
const pairBad: (string | number)[] = ["host", "h"]; // positions unchecked
// fix — CfgPair/tags/byId: shape-first selection per declaration
console.log(pairBad.length); // 2 — compiles with zero contracts
```

**Common confusion** — "selection is premature optimization" — selection is *correctness* (arity, absence, pollution proofs), with performance as a side effect — nothing premature about it. "shapes change, so selection rots" — re-run the questions on change (that's the discipline); habit-containers rot *without* signaling, selected ones signal via type errors when answers change.

**Performance note** — correct containers dominate micro-optimizations (O(1) vs O(n), zero vs N copies) — selection *is* the performance review for collections.

**Mentor note** — whiteboard the five shapes with one example each and ask the team to route them — calibration in ten minutes. Review stamp: every new collection declaration carries its shape answers or it doesn't merge.

### 2) **Readonly at boundaries, mutable inside** (freeze published snapshots; build locally)

**Definition** — lifecycle half of the checklist: builders accumulate mutably (local scope, `push` legal); parameters, snapshots, and returns publish as `readonly` (mutation scoped out by signature); escape to mutable only via explicit copy. Never `as`-away freezing — copies are reviewable, casts are aliasing bugs with documentation.

**What problem it solves / history** — shared-mutation incidents (sorted leaderboards, pushed frames, reordered inputs — 1.2/1.3's demos and 5.1's promises) all share one root: mutable-typed publication. Readonly-at-boundaries makes each such incident a compile error at authorship instead of a data-corruption report in production — the freeze point moves from vigilance to signature.

**Modern guidance** — as of TypeScript 5.9 era, default every exported/shared collection type to `readonly`; keep mutability for function-local builders; convert with spread/`toSorted`/`Object.freeze` at publication. See [1.2. Readonly arrays](<../1. Array Types/1.2. Readonly arrays and mutable vs frozen arrays.md>) for the full lifecycle treatment.

**Runnable example** — freeze point in the signature (good vs bad, `tsc --strict`):

```typescript
// good — builder mutable, publication readonly: lifecycle split by signature
function top2(xs: readonly number[]): readonly number[] {
  return xs.toSorted((a, b) => b - a).slice(0, 2); // derive, never mutate input
}
const board2 = [3, 1, 2];
console.log(top2(board2).join(","), board2.join(",")); // 3,2 3,1,2 — input intact

// bad — mutable publication invites post-publication mutation
function top2Bad(xs: number[]): number[] { return xs.sort((a, b) => b - a).slice(0, 2); }
console.log(top2Bad(board2).join(","), board2.join(",")); // 3,2 3,2 — input reordered
// fix — readonly parameter + toSorted return: non-mutation by construction
```

**Common confusion** — "readonly inconveniences consumers" — one spread per genuine mutation need vs unbounded hidden aliasing — the inconvenience *is* the protection. "builders should be readonly too" — accumulation is mutation; freeze at publication, not during construction.

**Performance note** — signature freezing costs nothing (erased); boundary copies cost O(n) each (budgeted, explicit); aliasing bugs cost unbounded debugging — lifecycle split is performance-positive by construction.

**Mentor note** — "who owns this array after `return`?" — the one review question covering this entire promise. Exercise: convert three published collections to `readonly` and fix each implementation error with copies — the error sites are the mutation audit.

### 3) **Literals narrow at the source** (`as const` tables keep exhaustiveness alive)

**Definition** — precision half of the checklist: curated tables (routes, methods, statuses) declared `as const` (+ `satisfies` contracts); working sets derived (`typeof t[number]`); helpers widen receivers (never narrow sources); exhaustiveness consumes the literals downstream. One widened joint collapses the chain — probe joints with literal hovers in review.

**What problem it solves / history** — widened tables (stringly routes, `string[]` methods, `Record<string>` handlers) killed exhaustiveness silently — new variants shipped without branch requirements, exactly the 5.1 promise-3/4 class. Source-narrowing keeps every downstream switch honest: add a variant, the compiler lists the unhandled branches.

**Modern guidance** — as of TypeScript 5.9 era, `as const` + `satisfies` every curated table; derive (never list) working sets; return `M` (never `string`) at pipeline joints. See [2.2. as const tuples](<../2. Tuple Types/2.2. as const tuples literal inference and readonly.md>) + [3.3. Literal preservation](<../../../09 Utility Types and Type Transformations/sections/3. Transformations in Practice/3.3. satisfies and as const preserving literals through transforms.md>) (in 09).

**Runnable example** — narrow source, honest switches (good vs bad, `tsc --strict`):

```typescript
// good — as const source: derived union stays literal, switches stay exhaustive
const OPS = ["read", "write"] as const;
type Op = (typeof OPS)[number]; // "read" | "write"
function runOp(o: Op): number { return o === "read" ? 1 : 2; }
console.log(runOp("read")); // 1 — every variant handled, provably

// bad — widened source: switches prove nothing
const looseOps: string[] = ["read", "write"];
function runBad(o: string): number { return 0; } // no literals, no exhaustiveness
// fix — as const at the source; derive the union; exhaust downstream
console.log(runBad("anything")); // 0 — compiles for every typo
```

**Common confusion** — "literals everywhere slow checks" — curated tables (tens of members) check fast; generated sets (thousands) need explicit strategy — narrow curated, annotate generated. "widening is harmless with tests" — tests cover listed cases; exhaustiveness covers *unlisted* ones (the next variant) — different guarantees, both needed.

**Performance note** — narrow unions check per member (fast for curated sets); collapsed `string` checks trivially but proves nothing — precision costs linear member checks and buys incident prevention.

**Mentor note** — add a variant to each table and count the new errors (narrow: N helpful errors; wide: zero) — the blast-radius comparison sells source-narrowing permanently. Gate: curated tables without `as const` fail review.

### 4) **Probe arity and element types in review** (hover declarations, not usages)

**Definition** — review habit completing the checklist: hover every new collection *declaration* and read arity (`[]` vs tuple vs `readonly`), element types (narrow? `any`? `unknown`?), and key kinds (`string` vs union vs `Map`) — before reading any usage. Usages inherit declaration precision (or imprecision); auditing declarations audits the whole downstream for free.

**What problem it solves / history** — usage-side reviews (`x.toUpperCase()` looks fine) missed declaration-side rot (`string[]` where a tuple belonged, `Record<string>` where a union belonged) — each a latent incident invisible at every use site. Declaration-hovering inverts the leverage: one hover per declaration verifies every downstream use simultaneously.

**Modern guidance** — as of TypeScript 5.9 era, review collections declaration-first: hover the type, ask the stamp questions (shape? keys? lifecycle? literals?), then skim usages for consistency. Flag `any[]`, bare `[]`, `Record<string, unknown>`, and de-consted tables on sight — each a declaration-side defect with a known fix.

**Runnable example** — declaration hover predicts downstream (good vs bad, `tsc --strict`):

```typescript
// good — declaration hover tells the whole story: tuple arity + literals + readonly
const CFG = ["prod", 3] as const; // readonly ["prod", 3] — hover once, trust everywhere
type C0 = (typeof CFG)[0]; // "prod" — derived narrowly
console.log(CFG[1].toFixed(0), "prod" as C0); // 3 prod

// bad — usage looks fine, declaration hides the rot
const cfgBad: (string | number)[] = ["prod", 3]; // hover: open, mixed, mutable — three smells
console.log(cfgBad[0]); // prod — usage innocent, declaration guilty on all three counts
// fix — hover declarations in review; usages follow declarations, never lead them
```

**Common confusion** — "hovering is not real review" — hover-reading *is* type review (the checker computed the answers; the reviewer just reads them) — logic review follows, type review leads. "declaration discipline slows feature work" — thirty seconds per declaration vs incident post-mortems — the highest-leverage review seconds in typed codebases.

**Performance note** — declaration review scales O(declarations); usage review scales O(usages) — declarations ≪ usages in every codebase, so declaration-first is asymptotically cheaper reviewing *and* produces stronger guarantees.

**Mentor note** — run one review declaration-first, out loud, with hovers — the team sees latent bugs surface before logic discussion begins. Make "hover the declaration" the first checklist item for collection PRs, not an afterthought.
