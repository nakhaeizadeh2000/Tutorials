## 4.1. Collections checklist mental models mentors insist on

Review a collection by asking what each contract establishes and what evidence is still needed. Types can reject malformed construction, unsupported writes and missing finite handlers. Runtime behavior still determines which values are selected, whether empty input works, whether aliases change data and whether a result actually meets its intended meaning.

### 1) **Choose roles, sequence and key semantics**

A batch is an open sequence of work items. Each work item has an operation and its numeric inputs in two positional roles, so a readonly tuple is useful inside that sequence. A finite Record requires a handler for each admitted operation. A Map can accumulate observed operation counts, while a Set reports distinct operations without representing repeated work items. These choices answer different questions; using a Set for the work list would change repetition semantics.

Use [collection selection](<../3. Collections and Selection/3.3. Choosing Array Tuple ReadonlyArray and readonly tuples.md>) for the full shape/capability reasoning and [Record versus Map](<../3. Collections and Selection/3.2. Record vs Map indexed access vs hashed keys.md>) for completeness, properties and entry identity. A homogeneous tuple is valid, a union array can be intentional, and a dynamic object dictionary is not automatically a defect.

### 2) **State the mutation and coverage requirements explicitly**

The runner below only reads its inputs, so it accepts readonly work items and readonly numeric arrays. A private mutable output array makes accumulation straightforward; publishing it as readonly rejects ordinary writes through that returned view. There is no runtime freeze requirement here, and the result is not frozen. A stronger independent/frozen snapshot policy belongs to the selection lesson's worked example.

The operation table is a const tuple and its element union supplies the handler keys. The Record contract makes missing coverage an error. A get-versus-everything-else ternary would not acquire that property merely because its parameter is a literal union. Likewise, no type annotation verifies that a handler computes the intended arithmetic.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save the fence as batch.ts. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist batch.ts`; run `node dist/batch.js`. Activate negatives individually with those flags and --noEmit instead of --outDir dist.

```typescript
const OPS = ["sum", "count"] as const;
type Op = (typeof OPS)[number];
type WorkItem = readonly [op: Op, values: readonly number[]];
type Result = readonly [op: Op, value: number];
const handlers: Record<Op, (values: readonly number[]) => number> = {
  sum: values => values.reduce((total, value) => total + value, 0),
  count: values => values.length,
};
function runBatch(items: readonly WorkItem[]): readonly Result[] {
  const output: Result[] = [];
  for (const [op, values] of items) {
    // values.push(9); // TS2339
    output.push([op, handlers[op](values)]);
  }
  return output;
}
const tasks: readonly WorkItem[] = [["sum", [0, 2]], ["count", []], ["sum", [3]]];
const results = runBatch(tasks);
console.log(results.map(([op, value]) => op + ":" + value).join(","));
console.log(tasks.map(([, values]) => values.length).join(","), Object.isFrozen(results));
const observed = new Map<Op, number>();
const initialCount = observed.get("count");
console.log(initialCount ?? "not observed");
for (const [op] of tasks) observed.set(op, (observed.get(op) ?? 0) + 1);
const distinct = new Set(tasks.map(([op]) => op));
console.log(results.length, distinct.size, observed.get("sum"));
const first = results[0];
if (first !== undefined) console.log(first[0], first[1].toFixed(0));
console.log(runBatch([]).length, handlers.sum([]), handlers.count([]));
// results.push(["sum", 9]); // TS2339
// results[0][1].toFixed(0); // TS2532
// const invalid: WorkItem = ["sum", ["x"]]; // TS2322
// const short: WorkItem = ["sum"]; // TS2322
// const typo: Op = "unknown"; // TS2322
// const missing: typeof handlers = { sum: values => values.length }; // TS2741

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Operations = Expect<Equal<Op, "sum" | "count">>;
type TwoRoles = Expect<Equal<WorkItem["length"], 2>>;
type OpenResults = Expect<Equal<typeof results["length"], number>>;
type InitiallyMissing = Expect<Equal<typeof initialCount, number | undefined>>;
```

The output is `sum:2,count:0,sum:3`, `2,0,1 false`, `not observed`, `3 2 2`, `sum 2`, then `0 0 0`; all four live probes compile. The repeated sum work item remains in the results, while the Set reports two distinct operations. The finite-key Map initially lacks count; its key type did not establish coverage. The result view is readonly and actually unfrozen. The input lengths remain unchanged in this implementation.

### 3) **Trace presence, empty cases and callback meaning**

A returned readonly Result[] can still be empty, so a numeric read needs an absence policy. The guard checks the extracted first value before using its tuple positions. The runner's empty batch returns an empty array; its sum handler deliberately uses zero as the empty reduction result. Those are separate choices from the shapes of Result and WorkItem.

Follow actual callback behavior. Count returns a length; sum accumulates values. Both share the same callable type, so replacing sum with values.length would compile while changing the result of the first task from 2 to 2 coincidentally. The third sum task, [3], distinguishes those implementations: its correct result is 3 rather than 1. Choose data that exposes a wrong algorithm instead of relying on type probes alone. [Array methods](<../1. Array Types/1.3. Array methods map filter reduce typed precisely.md>) owns callback inference, filters, reductions and copying operations in detail.

### 4) **Require evidence for the claim being reviewed**

Inspect declarations for the intended relationships, then inspect operations and run meaningful examples. An accepted declaration does not certify arithmetic, source independence, runtime integrity, input validation or every later use. Compile-time negatives demonstrate rejection; executed outcomes demonstrate the selected runtime behavior. Editor hovers can help inspect types, but this example uses live type probes and compilation rather than claiming an editor session occurred.

For changes, retain a small set of cases that discriminate the intended behavior: a repeated operation, zero, an empty batch, an empty numeric input, a missing first result and a newly added operation. Route broader external parsing or unknown-value checks to their existing owners instead of treating a local type annotation as validation.

### 5) **Common confusion**

Readonly controls operations through a view; it does not imply frozen output. A Map with finite key parameters can still lack entries, while a finite Record's required-property contract supplies completeness at construction. Literal preservation helps express coverage but needs an actual exhaustive contract or branch check.

An inferred or annotated type can be correct while the calculation is wrong. More compiler errors after changing a declaration are not automatically a count of production bugs, and an error-free hover is not proof of the intended behavior. Explain what each check observes.

### 6) **Performance note**

The runner executes handlers, traverses work items and allocates an output array and result tuples. Set/Map construction and string formatting also perform runtime work. Type aliases, readonly modifiers and live type probes erase. No asymptotic review-cost claim, fixed container crossover, checker-cache guarantee or benchmark supports this checklist. If processing cost matters, measure realistic work items and handlers, not a type spelling or a review stamp.

### 7) **Mentor note**

Ask why the first sum case alone would fail to expose a length-based implementation, then use the third case to make the wrong result visible. Have the learner distinguish three results from two distinct operations and explain why initiallyMissing includes undefined even though Op is finite. This tests semantics, key presence and static contracts together.

For practice, add product to OPS and update the Operations probe, initially leaving handlers unchanged. Expect TS2741 for the missing product handler. Implement product with a reduction initialized to one, add a [product, [2, 3]] work item and verify product:6. Also call handlers.product([]) and require 1. An implementation initialized to zero has the right type but fails the arithmetic cases; verify that counterexample before fixing it. Adding the literal alone does not implement the operation.
