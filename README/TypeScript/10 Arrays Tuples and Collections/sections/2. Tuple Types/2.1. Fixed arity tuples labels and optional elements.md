## 2.1. Fixed arity tuples labels and optional elements

A tuple assigns meaning and types to positions: an entry can contain a string key followed by a numeric count. This catches many construction and access mistakes that an open union array permits. A tuple is still a JavaScript array, however, and its static length contract does not make a mutable value immune to array mutation.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence under its filename. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`; run `node dist/FILE.js`. Activate negatives individually using those flags with --noEmit instead of --outDir dist.

### 1) **Position checking and the mutable-length limit**

A required two-position tuple checks a fresh value's two slots and exposes a literal length type. A literal index outside those slots is rejected. An ordinary union array instead describes an open list whose elements may have either type. The [primary tuple guide](https://www.typescriptlang.org/docs/handbook/2/objects.html#tuple-types) explains the positional contract; it is not runtime validation of an external array.

Save as positions.ts.

```typescript
type Entry = [key: string, count: number];
const entry: Entry = ["users", 42];
console.log(entry[0].toUpperCase(), entry[1].toFixed(0));
// const swapped: Entry = [42, "users"]; // TS2322
// const short: Entry = ["users"]; // TS2322
// const long: Entry = ["users", 42, "extra"]; // TS2322
// console.log(entry[2]); // TS2493
const openList: (string | number)[] = [42, "users", "extra"];
console.log(openList.length);
const pushedLength = entry.push("extra");
const declaredLength: 2 = entry.length;
console.log(pushedLength, declaredLength, entry.join(","));
// entry.push(true); // TS2345: push checks the admitted element union, not exact final arity
const vulnerable: Entry = ["jobs", 2];
vulnerable.pop();
try { console.log(vulnerable[1].toFixed(0)); }
catch (error) { console.log("missing required slot", error instanceof TypeError); }
const protectedView: readonly [string, number] = ["jobs", 2];
// protectedView.push("extra"); // TS2339
// protectedView[1] = 3; // TS2540
console.log(protectedView.join(","));

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type FixedLength = Expect<Equal<Entry["length"], 2>>;
type FirstSlot = Expect<Equal<Entry[0], string>>;
type Elements = Expect<Equal<Entry[number], string | number>>;
```

The output is `USERS 42`, `3`, `3 3 users,42,extra`, `missing required slot true`, then `jobs,2`; three probes compile. Push accepted another admitted element and pop removed a required one. The checker still treats entry.length as 2 and vulnerable[1] as number, even though these mutations made those assumptions false at runtime. No assertion was needed to demonstrate the limitation.

Readonly tuples block these ordinary writes through their own view. They still do not freeze the array or revoke a mutable alias, as the [readonly owner](<../1. Array Types/1.2. Readonly arrays and mutable vs frozen arrays.md>) demonstrates. For a protocol frame or fixed return shape, prefer controlled construction and a readonly consumer contract; validate unknown external data separately.

### 2) **Labels explain positions without enforcing their meaning**

Labels make a positional type easier to understand, especially when adjacent values have the same primitive type. They do not become runtime properties, constrain destructuring variable names or distinguish otherwise identical tuple types. If accidentally swapping same-typed values is unacceptable, labels alone cannot prevent it; consider named object fields or a more specific value contract.

Save as labels.ts.

```typescript
type Point3D = [x: number, y: number, z: number];
function makePoint(): Point3D { return [1, 2, 3]; }
function distance([x, y, z]: Point3D): number { return Math.hypot(x, y, z); }
console.log(distance(makePoint()).toFixed(2));
type PersonLocation = [name: string, city: string];
type CityPerson = [city: string, name: string];
const person: PersonLocation = ["Ada", "London"];
const relabeled: CityPerson = person;
const [arbitraryFirst, arbitrarySecond] = relabeled;
console.log(arbitraryFirst, arbitrarySecond, Object.hasOwn(person, "name"));
const swapped: PersonLocation = ["London", "Ada"];
console.log(swapped.join(","));
type MixedLabels = [name: string, number];
const mixedLabels: MixedLabels = ["Ada", 36];
console.log(mixedLabels.join(","));

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type LabelsIgnored = Expect<Equal<PersonLocation, CityPerson>>;
type MixedCompatible = Expect<Equal<MixedLabels, [string, number]>>;
```

The output is `3.74`, `Ada London false`, `London,Ada`, then `Ada,36`; both probes compile. MakePoint is implemented, so the program does not rely on an ambient function that disappears at runtime. Relabeling did not reorder the actual values, and swapping two strings remains type-correct despite changing their meaning.

Labels were introduced in TypeScript 4.0. [TypeScript 5.2 lifted the all-or-nothing labeling restriction](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-2.html#named-and-anonymous-tuple-elements), so the mixed-labeled type is valid on this baseline. Labels support tooling and documentation; no editor interaction or specific tooltip rendering is part of this executed example.

### 3) **Optional positions, open rests and meaningful alternatives**

An optional position admits omission, so its read can be undefined and the tuple's length can be a union of literal lengths. Under exactOptionalPropertyTypes, omission differs from explicitly supplying undefined unless the position's value type includes undefined. An open rest admits zero or more values of its element type and gives the overall length type number.

Save as variable-shapes.ts.

```typescript
type MaybeEntry = [key: string, count?: number];
const omitted: MaybeEntry = ["jobs"];
const complete: MaybeEntry = ["jobs", 2];
const [key, count = 0] = omitted;
console.log(key, count, omitted.length, complete.length);
// const noHead: MaybeEntry = []; // TS2322
// const explicitUndefined: MaybeEntry = ["jobs", undefined]; // TS2322 with exactOptionalPropertyTypes
const admitsUndefined: [key: string, count?: number | undefined] = ["jobs", undefined];
console.log(admitsUndefined.length);
type Batch = [label: string, ...values: number[]];
const batch: Batch = ["jobs", 1, 2];
const emptyBatch: Batch = ["jobs"];
console.log(batch.join(","), emptyBatch.length);
// const wrongRest: Batch = ["jobs", "one"]; // TS2322
type Middle = [start: string, ...values: number[], end: boolean];
const middle: Middle = ["jobs", 1, 2, true];
const noMiddle: Middle = ["jobs", false];
console.log(middle.join(","), noMiddle.join(","));
type OptionalThenRest = [label?: string, ...values: number[]];
const valid: OptionalThenRest = [];
console.log(valid.length);
// type BadOrder = [label?: string, count: number]; // TS1257
// type BadAfterRest = [...values: number[], end?: boolean]; // TS1266
type Result = [ok: true, value: number] | [ok: false, error: string];
function describe(result: Result): string {
  return result[0] ? result[1].toFixed(0) : result[1].toUpperCase();
}
console.log(describe([true, 2]), describe([false, "oops"]));

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type PossibleLengths = Expect<Equal<MaybeEntry["length"], 1 | 2>>;
type OptionalRead = Expect<Equal<MaybeEntry[1], number | undefined>>;
type OpenLength = Expect<Equal<Batch["length"], number>>;
```

The output is `jobs 0 1 2`, `2`, `jobs,1,2 1`, `jobs,1,2,true jobs,false`, `0`, then `2 OOPS`; three probes compile. The optional position has no required element after it, but it can precede an open rest. A required final element can follow a suitable rest when no preceding optional position conflicts with that shape. Invalid combinations have separate diagnostics; “everything after a rest is illegal” is not the rule.

The Result union preserves a relationship between its tag and payload. Replacing it with [boolean, number | string] would lose that relationship. A union of tuple alternatives is therefore useful rather than inherently a bad practice. The [union narrowing owner](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.3. Custom narrowers predicates asserts and type guards on unions.md>) owns the wider reasoning. Function rest signatures and generic tuple composition belong to the linked function/generic owners rather than requiring a second implementation here.

### 4) **Common confusion**

A fixed tuple length is a static contract, not an unchangeable runtime array length. Assignment and literal-index checking are stronger than the available mutable array methods' arity guarantees. A label also names an intended role without creating a runtime field or rejecting same-typed swaps.

An optional element is not a required element whose value includes undefined: omission changes possible length. An open rest also differs from a fixed generic tuple spread; inspect the actual resulting shape before predicting its length or admitted values.

### 5) **Performance note**

Tuple types and labels erase. Runtime array allocation, pushes, pops, destructuring, Math.hypot and string operations remain. A tuple annotation performs no validation or special storage conversion. There is no measured checker-cost formula, allocation equivalence with objects or tooltip-based productivity result here. Choose positional or named data for its meaning and evaluate actual runtime work separately when needed.

### 6) **Mentor note**

Ask which operations the compiler rejects before running positions.ts: construction with three fields, reading literal index 2, pushing a string, and popping the count. The surprising accepted mutations should prompt a precise explanation of the contract's limit, rather than abandoning positional checking altogether.

For practice, implement entryFor(key: string, count: number): readonly [key: string, count: number] by returning a fresh two-element literal without assertions. Verify the two values, then activate a caller push and confirm TS2339. A reversed or three-element return must fail construction checking. Object.isFrozen on the successful result should still be false: the exercise requires a readonly consumer view, not runtime freezing. Explain which additional operation would enforce that separate requirement.
