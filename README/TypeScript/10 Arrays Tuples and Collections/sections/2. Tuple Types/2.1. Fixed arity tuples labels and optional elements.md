## 2.1. Fixed-arity tuples — labels and optional elements

### 1) **Fixed arity, heterogeneous slots** (length and per-position types checked)

**Definition** — `[string, number]` is a 2-tuple: exactly two elements, first a `string`, second a `number`. Arity errors (`push` a third, assign a 1-tuple) fail at compile time; each position reads with its own type (`pair[0].toUpperCase()`, `pair[1].toFixed()`). Tuples are arrays structurally (methods, iteration, spread all work) with length *and* position contracts layered on.

**What problem it solves / history** — heterogeneous pairs as `(string | number)[]` lost both contracts: positions interchangeable (name/age swapped silently), arity unenforced (3-element "pair" compiled) — every consumer re-validated what the type should have guaranteed. Tuples (since TS 1.x, labels since 4.0) make pairs, triples, and key-value entries self-describing: the shape *is* the validation.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), default heterogeneous fixed groups to tuples (coordinates, entries, multi-returns, `[state, setState]` shapes) and open mixed lists to unions (`(string | number)[]` only when length genuinely varies). Destructure at the boundary (`const [name, age] = pair`) so positions become names immediately.

**Runnable example** — arity and position enforced (good vs bad, `tsc --strict`):

```typescript
// good — pair contract: positions typed, arity fixed
type Entry = [key: string, count: number];
const e: Entry = ["users", 42];
console.log(e[0].toUpperCase(), e[1].toFixed(0)); // USERS 42
const [k, c] = e; // string, number — destructured to names at the boundary
console.log(k, c); // users 42

// good — entries() bridge: Object/Map iteration yields tuples natively
const m = new Map<string, number>([["a", 1]]);
for (const [key, val] of m) console.log(key.toUpperCase(), val.toFixed(0)); // A 1

// bad — union array loses position and arity
const bad: (string | number)[] = ["users", 42];
const swapped: (string | number)[] = [42, "users"]; // compiles — position contract gone
const triple: (string | number)[] = ["a", 1, "extra"]; // compiles — arity contract gone
// fix — Entry tuple: swapped and triple both error at the declaration
// const fix1: Entry = [42, "users"]; // error TS2322 — positions enforced
console.log(bad.length, swapped.length, triple.length); // 2 2 3 — unchecked shapes
```

**Common confusion** — "tuples reject array methods" — `push` beyond arity errors, but `map`/`slice`/iteration all work (returning *array*-typed results — the tuple contract doesn't survive mapping; re-annotate when arity must persist). "`[string, number]` accepts `[]`" — no (length mismatch errors) — only *optional-element* tuples (promise 3) accept shorter. "labels affect assignability" — documentation-only (`[key: string]` ≡ `[string]`) — labels guide readers and tooltips, never the checker.

**Performance note** — tuples check per position (O(arity), tiny) and emit plain arrays — zero runtime shape. Destructuring costs nothing extra (same element reads, named bindings). Prefer tuples over single-field interfaces for internal pairs (no allocation difference, less declaration overhead).

**Mentor note** — swap the pair live (`[42, "users"]`) and read TS2322 — position enforcement in one error. Then show the union-array version compiling the same swap — the contrast sells tuples in under a minute. Review gate: heterogeneous arrays with stable arity must become tuples.

### 2) **Labeled elements** (documentation in the type)

**Definition** — `[name: string, age: number]` labels each position: tooltips show `name:`/`age:` instead of `0:`/`1:`, call-site hints name arguments, and apply/spread order documents itself. Labels are erased (no runtime footprint) and ignored by assignability (`[name: string]` ≡ `[label: string]` ≡ `[string]`).

**What problem it solves / history** — unlabeled multi-same-type tuples (`[string, string, string]` — host/port/path? or path/host/port?) forced readers to find the constructor to learn positions — and constructors lived far from uses. Labels (TS 4.0) put the documentation *in* the type: every hover, tooltip, and error message names the slots, so positions survive the distance between declaration and call site.

**Modern guidance** — as of TypeScript 5.9 era, label every tuple with 2+ same-typed positions or 3+ positions total (`[host: string, port: number]`, `[x: number, y: number, z: number]`); single distinctive pairs (`[string, number]`) may stay bare. Label rest elements too (`...rest: string[]` reads better than `...string[]` in signatures).

**Runnable example** — labels guide, never constrain (good vs bad, `tsc --strict`):

```typescript
// good — labels name same-typed positions: order readable at every use
type Point3D = [x: number, y: number, z: number];
const p: Point3D = [1, 2, 3];
console.log(p[0].toFixed(0), p[2].toFixed(0)); // 1 3 — hover shows x/y/z, not 0/1/2
function dist([x, y, z]: Point3D): number { return Math.hypot(x, y, z); }
console.log(dist(p).toFixed(2)); // 3.74

// good — labels are assignability-transparent: differently-labeled twins interchange
type A = [first: string, second: string];
type B = [a: string, b: string];
const ab: A = ["x", "y"];
const bb: B = ab; // ok — labels ignored by the checker
console.log(bb[0]); // x

// bad — unlabeled same-type triple: positions learnable only from the constructor
type P3 = [number, number, number];
declare function makeP3(): P3; // which is x? readers must find the implementation
// fix — Point3D: the type itself answers "which position is which"
console.log(makeP3()[1].toFixed(0));
```

**Common confusion** — "labels enforce names at destructuring" — `const [width, height] = p` (renamed freely) — labels guide tooltips, never bind identifiers. "differently-labeled tuples are incompatible" — fully transparent (`A` ≡ `B` above) — relabel freely when crossing API boundaries. "labels cost emit" — erased entirely; hover-only documentation with zero bytes.

**Performance note** — zero check/emit cost (labels vanish before checking completes — pure display metadata). The performance content is human: labeled positions remove constructor-hunting from reviews.

**Mentor note** — hover `Point3D` vs `P3` side by side (`x/y/z` vs `0/1/2`) — the tooltip *is* the lesson. Exercise: take the repo's most-confusing unlabeled tuple and label it — count the call sites that become self-explanatory. Lint: consider `@typescript-eslint` naming conventions for tuple labels on public APIs.

### 3) **Optional and rest elements** (varying arity with checked tails)

**Definition** — trailing positions may be optional (`[string, number?]` accepts length 1–2); rest elements (`[string, ...number[]]`, `[...T, last: string]`) splice variable middles/tails with checked element types. Optional elements must trail required ones (`[string?, number]` errors); rest composition follows 08/3.3's concat rules at value level.

**What problem it solves / history** — overloads-per-arity (`f(a)`, `f(a, b)`, `f(a, b, c)`) for functions with trailing options collapsed into one tuple-typed rest (`...args: [a: A, b?: B]`) — arity enforced *and* documented in a single signature. Optional tuple elements (TS 3.0+) plus labeled rest (4.0) replaced most 2–4-arity overload sets with one rest type.

**Modern guidance** — as of TypeScript 5.9 era, model trailing-option signatures as labeled tuple rests (`...args: [url: string, init?: RequestInit]`) instead of overloads; model composed sequences with spread (`[...Head, last: T]`) instead of unions of tuple shapes. Keep optionals trailing; keep rests labeled; destructure with defaults (`const [a, b = 0] = pair`) at consumption.

**Runnable example** — arity varies, checking persists (good vs bad, `tsc --strict`):

```typescript
// good — optional tail: length 1–2, positions still typed
type MaybePair = [name: string, age?: number];
const p1: MaybePair = ["ada"];
const p2: MaybePair = ["ada", 36];
console.log(p1.length, p2[1] ?? "unknown"); // 1 36 — optional reads as number | undefined

// good — labeled tuple rest replaces overloads-per-arity
function fetch2(...[url, init]: [url: string, init?: { method: string }]): string {
  return `${init?.method ?? "GET"} ${url}`;
}
console.log(fetch2("/a"), fetch2("/b", { method: "POST" })); // GET /a POST /b
// fetch2(); // error TS2554 — Expected 1-2 arguments (arity enforced, documented)

// bad — union of tuple shapes instead of optional/rest composition
type PairOrSingle = [string, number] | [string]; // works but forks every consumer switch
function headBad(p: PairOrSingle): string { return p[0]; }
// fix — MaybePair: one shape, optional tail, no consumer fork
console.log(headBad(["x", 1])); // x
```

**Common confusion** — "`[string, number?]` accepts `[]`" — min length 1 (required head) — `[]` errors; all-optional (`[string?, number?]`) accepts `[]`. "optional elements may precede required" — `TS1257`: required after optional errors — order optionals last, always. "rest elements break arity" — `[...T, last]` *computes* arity from `T` (fixed when `T` is fixed) — rest composes, `any[]` dissolves; different tools (see 08/3.3).

**Performance note** — optional/rest tuples check per position like fixed ones (O(arity)) — no overhead vs unions of shapes, and far better error messages (one arity error vs forked-branch mismatches).

**Mentor note** — the `fetch2` hover (`[url: string, init?: …]`) replaces a 3-overload list in one line — show both and ask which documents arity better. Exercise: collapse one overload-per-arity set in the codebase to a labeled tuple rest and delete the overloads — count deleted lines as ROI.
