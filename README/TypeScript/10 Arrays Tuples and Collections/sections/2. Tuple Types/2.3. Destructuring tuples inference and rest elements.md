## 2.3. Destructuring tuples — inference and rest elements

### 1) **Positional destructuring** (bindings get slot types; mismatches error)

**Definition** — `const [name, age] = pair` binds each position to its slot type (`name: string`, `age: number` — no annotations needed); too many bindings (`const [a, b, c] = pair` on a 2-tuple) error, too few are fine (prefix binding). Defaults fill `undefined` slots (`const [a, b = 0] = maybePair`); renaming is free (bindings are fresh identifiers, not label references).

**What problem it solves / history** — indexed access (`pair[0]`, `pair[1]`) scattered magic positions through consumers — readers counted indices, refactors renumbered them silently, and swapped positions compiled identically. Destructuring at the boundary converts positions to names once: downstream code reads `name`/`age` (self-documenting, rename-safe), and arity changes error at the binding, not at the twentieth `pair[1]`.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), destructure tuples at function entries and return sites (`const [user, err] = load()`); index (`pair[0]`) only inside generic tuple utilities where positions are computed. Provide defaults for optional slots (`b = 0`); annotate the binding when the source is wide (`const [a, b]: [string, number] = loose`).

**Runnable example** — names at the boundary (good vs bad, `tsc --strict`):

```typescript
// good — destructure once: positions become names for the whole scope
function load(): [user: string, code: number] { return ["ada", 200]; }
const [user, code] = load(); // string, number — inferred per slot
console.log(user.toUpperCase(), code.toFixed(0)); // ADA 200
// const [a, b, c] = load(); // error TS2493 — tuple too short for 3 bindings (arity enforced)

// good — defaults cover optional slots honestly
type Maybe = [name: string, age?: number];
function greet([name, age = 0]: Maybe): string { return `${name} (${age})`; }
console.log(greet(["lin"]), greet(["ada", 36])); // lin (0) ada (36)

// bad — indexed access scatters magic positions through the consumer
const r = load();
console.log(r[0].toUpperCase(), r[1].toFixed(0)); // works — but every r[1] re-asks "which slot?"
// fix — destructure at the boundary: one positional read, infinite named uses
```

**Common confusion** — "destructuring copies the tuple" — binds references (no allocation; elements shared) — copy explicitly (`[...t]`) when independence matters. "labels constrain binding names" — labels are display-only; `const [u, c] = load()` renames freely. "defaults change the tuple type" — defaults apply to the *binding* (`age: number` after `= 0`), never the source (still `number | undefined` in the tuple) — narrowing at the binding, not the declaration.

**Performance note** — destructuring emits plain element reads (identical to indexing — zero overhead); defaults compile to `??`-ish initialization per slot (one branch per defaulted binding — negligible). Prefer destructuring over repeated indexing for both readability *and* JIT-friendliness (named locals optimize better than repeated property loads in long functions).

**Mentor note** — ban `pair[0]`/`pair[1]` beyond utility internals in review — every indexed access is a rename waiting to break. Exercise: convert one indexed-access consumer to destructured bindings and count the magic numbers deleted — readability ROI in one diff.

### 2) **Rest in destructuring** (tuple-aware rest types vs array rest)

**Definition** — `const [head, ...tail] = xs` types `tail` from the source: tuple source → tuple rest (`[1, "a", true]` gives `head: number`, `tail: [string, boolean]`); array source → array rest (`string[]` gives `head: string`, `tail: string[]`). The rest binding preserves tuple-ness when the source has it — precise tails without manual slicing types.

**What problem it solves / history** — `slice(1)`-typed tails (`string[]` regardless of source arity) discarded the very precision tuples were declared for — a `[status, payload, meta]` triple destructured via indices kept types, but any rest-based helper (`skipFirst`) flattened to arrays. Tuple-aware rest keeps the tail typed: `tail` of a triple is a pair, provably, with per-position types intact.

**Modern guidance** — as of TypeScript 5.9 era, destructure-with-rest for head/tail splitting (`const [first, ...rest] = rows`); annotate the rest when the source is wide (`const [h, ...t]: [string, ...number[]] = mixed`). In generic helpers, capture rest with `<T extends unknown[]>` (see 08/3.3) rather than re-slicing — forwarding preserves what slicing flattens.

**Runnable example** — tails keep tuple precision (good vs bad, `tsc --strict`):

```typescript
// good — tuple rest: tail keeps positions and types
const triple: [code: number, body: string, cached: boolean] = [200, "ok", true];
const [code, ...rest] = triple; // code: number, rest: [string, boolean]
console.log(code.toFixed(0), rest[0]?.toUpperCase()); // 200 OK

// good — array rest stays array-typed (honest about open length)
const list: string[] = ["a", "b", "c"];
const [first, ...others] = list; // first: string, others: string[]
console.log(first.toUpperCase(), others.length); // A 2

// bad — slice-typed tails flatten tuple precision to arrays
const flat: string[] = [triple[1], String(triple[2])]; // manual rebuild, types hand-threaded
// fix — const [s, ...r] = triple: the checker threads positions automatically
console.log(flat.join(",")); // ok,true — rebuilt by hand what rest infers
```

**Common confusion** — "rest always yields `T[]`" — yields tuple-rest for tuple sources (positions preserved) — only array sources give plain arrays. "destructured rest allocates differently" — identical emit to `slice` (one new array) — the difference is purely static precision. "skipping middle positions works positionally" — destructuring skips via holes (`const [, second] = t`) — holes are explicit; rest only takes the *tail*.

**Performance note** — rest destructuring allocates one array (like `slice`) — O(tail) per split. In hot loops over large tuples, index directly (`t[0]`) instead of rest-splitting per iteration — same guidance as array slicing, unchanged by precision.

**Mentor note** — hover `rest` (`[string, boolean]`) vs a sliced rebuild (`string[]`) — precision preserved vs flattened in one tooltip pair. Exercise: type a `skipFirst` helper generically (`<T extends unknown[]>([_, ...r]: T): [...r: T]`… via function rest capture) — connects this leaf to 08/3.3's forwarding.

### 3) **Destructuring function returns** (tuples for multi-returns vs options objects)

**Definition** — multi-value returns come in two shapes: *tuples* (`[data, error]` — positional, best for 2 fixed values with a conventional order) and *options objects* (`{ data, error }` — named, best for 3+ values or optional members). Tuples destructure positionally (`const [d, e] = load()`); objects destructure by name (`const { data } = load()`). The choice is positional-convention vs self-description.

**What problem it solves / history** — out-params and parallel arrays (`results[i]` with `errors[i]`) scattered paired values across structures that drifted out of sync (lengths diverging silently). Tuple returns co-locate the pair per call (`[data, err]` per invocation — the Go/Rust shape, typed); object returns name each member for wider shapes. Both beat parallel structures by keeping paired values adjacent.

**Modern guidance** — as of TypeScript 5.9 era, return tuples for exactly-2 conventional pairs (`[value, error]`, `[state, setState]`, `[key, val]`); return labeled tuples for 2–3 positional values with stable order; return objects for 3+ values, optional members, or evolving shapes (adding a field never breaks object destructuring; adding a tuple slot renumbers positions). Label tuple returns (`[user: string, code: number]`) so tooltips document the convention.

**Runnable example** — pairs adjacent, shapes honest (good vs bad, `tsc --strict`):

```typescript
// good — tuple pair: conventional order, labeled, destructured at the call
function parseNum(input: string): [value: number, err: string | null] {
  const n = Number(input);
  return Number.isNaN(n) ? [NaN, "not a number"] : [n, null];
}
const [val, err] = parseNum("42");
console.log(err ?? val.toFixed(0)); // 42 — pair adjacent per call, narrowed by err check

// good — object return for evolving shapes (fields added without renumbering)
function loadUser(id: string): { user: string; cached: boolean; tookMs?: number } {
  return { user: id, cached: false };
}
const { user } = loadUser("u1");
console.log(user.toUpperCase()); // U1

// bad — parallel arrays drift out of sync silently
const ids = ["u1", "u2"];
const errs: (string | null)[] = [null]; // lengths diverged — no type links them
// fix — pairs per call ([value, err][]) or objects: adjacency enforced by the type
const pairs: [string, string | null][] = [["u1", null], ["u2", "timeout"]];
console.log(pairs.length, errs.length); // 2 1 — drift visible only because pairs co-locate
```

**Common confusion** — "tuples scale to N returns" — past 3 positions, order becomes tribal knowledge — objects scale, tuples don't; the threshold is conventional (2–3), not technical. "labeled returns enforce names" — labels document; destructuring renames freely (`const [v] = …`) — convention, not contract. "error-tuples replace throw" — `[value, null]` vs throw is an API-design choice (local handling vs call-stack unwinding) — tuples don't settle it; team convention does.

**Performance note** — tuple returns allocate one small array per call (same as object literals — one allocation either way); destructuring adds no extra allocation. In ultra-hot paths returning pairs millions of times, out-param objects or indexed writes avoid per-call allocation — measure before contorting APIs.

**Mentor note** — ask "what happens when we add a third return?" for tuple vs object designs — renumbering vs additive extension decides the shape upfront. Exercise: evolve one 2-tuple return to 3 values both ways (append slot vs add field) and count broken call sites — objects win by zero, which is the lesson.
