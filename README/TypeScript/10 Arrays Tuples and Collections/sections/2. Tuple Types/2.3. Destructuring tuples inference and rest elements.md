## 2.3. Destructuring tuples inference and rest elements

Destructuring gives local names to values taken from an iterable. A tuple source supplies positional type information, while an ordinary array may be empty and gives weaker presence guarantees. Follow what is bound, what defaults replace, and whether a rest binding constructs a new outer array.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence under its filename. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`; run `node dist/FILE.js`. Activate negatives individually using --noEmit instead of --outDir dist with those flags.

### 1) **Bind positions and default only undefined**

A required tuple slot supplies its position's type. Fewer bindings can read a prefix; a literal binding beyond a fixed tuple's known end is rejected. A default supplies a binding value when the extracted value is undefined, but does not update the source. Null does not trigger that default. The [runtime destructuring reference](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Destructuring#default_value) documents this distinction and rest behavior.

Save as bindings.ts.

```typescript
function load(): [user: string, code: number] { return ["Ada", 200]; }
const [user, code] = load();
console.log(user.toUpperCase(), code.toFixed(0));
// const [a, b, c] = load(); // TS2493
const optional: [name: string, count?: number] = ["Ada"];
const [label, count = 0] = optional;
console.log(label, count, optional.length, optional[1]);
const nullable: readonly [number | null] = [null];
const [keptNull = 0] = nullable;
console.log(keptNull, keptNull ?? 0);
const empty: string[] = [];
const [first = "guest"] = empty;
console.log(first, empty.length);
const [unguarded] = empty;
// unguarded.toUpperCase(); // TS18048 with noUncheckedIndexedAccess
const altered: [number, number] = [1, 2];
altered[Symbol.iterator] = () => [9, 8][Symbol.iterator]();
const [iteratedFirst, iteratedSecond] = altered;
console.log(altered[0], iteratedFirst, iteratedSecond);

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Name = Expect<Equal<typeof user, string>>;
type Count = Expect<Equal<typeof count, number>>;
type OptionalSource = Expect<Equal<typeof optional[1], number | undefined>>;
type OpenRead = Expect<Equal<typeof unguarded, string | undefined>>;
```

The output is `ADA 200`, `Ada 0 1 undefined`, `null 0`, `guest 0`, then `1 9 8`; four probes compile. The default changed the local count, not the tuple's length or missing slot. Keeping null differs from applying ?? afterward. Destructuring also consumes the iterator: the deliberately changed array iterator yields 9 and 8 while direct index 0 still contains 1. Thus array destructuring is not universally identical to repeated indexed reads.

Destructure when the local names clarify a stable positional convention. Direct indexing remains appropriate for a tag check, a selected slot or an algorithm that works in positions. Annotating a binding cannot turn an arbitrary open array into a validated fixed tuple.

### 2) **Rest creates a fresh outer tail and can preserve tuple positions**

When the source has a fixed tuple shape, rest can infer the remaining positions as another tuple. A readonly source still produces a mutable rest array: its outer value is new. Referenced objects inside that new array are shared unless separately copied. Slicing a tuple instead generally returns an array of its element union, which does not identify a particular positional tail.

Save as tails.ts.

```typescript
const triple: readonly [code: number, body: string, cached: boolean] = [200, "ok", true];
const [code, ...tail] = triple;
tail[0] = "edited";
console.log(code, tail[0].toUpperCase(), triple[1], Object.is(tail, triple));
// tail[1] = "yes"; // TS2322
const sliced = triple.slice(1);
console.log(sliced.join(","));
// sliced[0].toUpperCase(); // TS2532 and TS2339: possible absence and a union element
const rows: readonly [id: number, row: { name: string }] = [1, { name: "Ada" }];
const [, ...rowTail] = rows;
rowTail[0].name = "Lin";
console.log(rows[1].name, Object.is(rowTail[0], rows[1]));
const list: string[] = ["a", "b", "c"];
const [head, ...others] = list;
console.log(head?.toUpperCase() ?? "missing", others.join(","));
// const [...all, last] = list; // TS2462: rest must be last in a binding pattern

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type TupleTail = Expect<Equal<typeof tail, [string, boolean]>>;
type Sliced = Expect<Equal<typeof sliced, (string | number | boolean)[]>>;
type ArrayTail = Expect<Equal<typeof others, string[]>>;
type ArrayHead = Expect<Equal<typeof head, string | undefined>>;
```

The output is `200 EDITED ok false`, `ok,true`, `Lin true`, then `A b,c`; four probes compile. Changing the tail's string slot did not change the original outer tuple. Editing the shared row did change the original row. The slice did not gain a string-at-index-zero contract merely because its runtime first element is a string in this example.

Rest in a binding pattern must be last. That syntax rule differs from a rest element in a tuple type, where suitable middle rest shapes are legal. Generic head/tail implementations belong to [variadic tuple generics](<../../../08 Generics Deep Dive/sections/3. Variance and Advanced Generic Patterns/3.3. Variadic tuple generics pipe concat and rest capture.md>); a type-only Tail transformation would not perform this runtime allocation.

### 3) **Return related values with an actual relationship**

A return like [number, string | null] does not tell the checker that a particular error value proves something about the number. Use a union of tagged alternatives when the relationship matters. Const destructuring can preserve that correlation so a tag check narrows its companion payload. The [primary control-flow notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-6.html#control-flow-analysis-for-destructured-discriminated-unions) explain the binding conditions; they are not a promise that every reassigned or separately extracted variable stays correlated.

Save as returns.ts.

```typescript
type ParseResult = readonly [ok: true, value: number] | readonly [ok: false, error: string];
function parseFinite(input: string): ParseResult {
  const value = Number(input);
  return input.trim() !== "" && Number.isFinite(value) ? [true, value] : [false, "not finite"];
}
function describe(input: string): string {
  const [ok, payload] = parseFinite(input);
  return ok ? payload.toFixed(1) : payload.toUpperCase();
}
console.log(describe("42"), describe("bad"), describe(""));
// function mutableBindings(result: ParseResult): string { let [ok, payload] = result; return ok ? payload.toFixed(1) : payload.toUpperCase(); } // TS2339
function tupleV1(): [user: string, code: number] { return ["Ada", 200]; }
function tupleV2(): [user: string, code: number, cached: boolean] { return ["Ada", 200, false]; }
const [firstUser, firstCode] = tupleV1();
const [sameUser, sameCode] = tupleV2();
console.log(firstUser, firstCode, sameUser, sameCode);
function objectV2(): { user: string; code: number; cached: boolean } { return { user: "Ada", code: 200, cached: false }; }
const { user, code } = objectV2();
console.log(user, code);
// const [fixedPair]: [[string, number]] = [tupleV2()]; // TS2322: an exact old tuple contract is different from a prefix binding
```

The output is `42.0 NOT FINITE NOT FINITE`, `Ada 200 Ada 200`, then `Ada 200`. The parser's documented policy rejects blank input and nonfinite conversions; it is a local example rather than a general numeric grammar or a framework integration. The success branch actually narrows payload to number, while the failure branch permits the string operation. The mutable let-destructured variant lacks the same correlation and is rejected.

Appending a return position does not renumber an existing prefix binding. Both tuple and object consumers above keep working after the shown additive extension, while assigning a larger tuple to an exact old tuple type can fail. Choose positional conventions or named fields for their meaning, stability and evolution needs, rather than a universal two-versus-three-field cutoff or a claim that one form never breaks consumers.

### 4) **Common confusion**

A default removes undefined from that binding according to its expression; it neither fills the source nor removes null automatically. Ordinary array heads can still be missing under noUncheckedIndexedAccess even when a nearby example happens to use a nonempty literal.

Rest constructs a fresh outer array, but ordinary bindings to objects keep their references. Readonly source positions do not imply a readonly rest result. A tuple type's middle rest syntax also does not make a middle rest binding pattern legal.

### 5) **Performance note**

Types erase, while iterator consumption, defaults, rest allocation, conversion and string operations remain. Rest collects remaining values into a new array; a custom iterator can perform additional work. No universal equivalence with slice, zero-cost destructuring claim, JIT advantage or object-versus-tuple allocation benchmark was established. Use the clearest appropriate access pattern and measure actual hot code before changing an API for speed.

### 6) **Mentor note**

Ask the learner to identify which values were copied and which references were shared in tails.ts, then contrast keptNull with the later ?? result. For returned alternatives, have them explain why the const-bound tag narrows payload and why merely pairing unrelated unions would not.

For practice, implement countFrom(input: readonly [count?: number | null | undefined]): number | null. Use a destructuring default of zero. Verify [], [undefined], [null] and [0] return 0, 0, null and 0, respectively, without changing any source array. A solution using count ?? 0 should compile but fail the null-preservation criterion. Explain this as a choice of data policy, not a preference for one punctuation style.
