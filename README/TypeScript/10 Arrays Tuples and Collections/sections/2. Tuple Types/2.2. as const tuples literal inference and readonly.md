## 2.2. as const tuples literal inference and readonly

A const assertion on an array literal can preserve both its positional shape and literal values. This is useful when an ordered runtime table also defines a finite set of admitted values. The assertion does not validate unknown data, freeze the array or force every consumer to handle future additions.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence under its filename. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`; run `node dist/FILE.js`. Activate negatives individually with those flags and --noEmit instead of --outDir dist.

### 1) **Preserve a literal tuple at the expression**

The same literal can have an open array contract, a readonly literal tuple contract or an explicitly chosen broader positional contract. Const assertions preserve information in the literal expression; they cannot recover literal values that an earlier variable's type has already widened. They also do not recursively change every referenced value's type. The [primary const-assertion notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-4.html#const-assertions) explain these boundaries.

Save as literal-source.ts.

```typescript
const loose = ["get", 200];
const precise = ["get", 200] as const;
const positional: readonly [method: string, status: number] = ["get", 200];
console.log(loose.join(","), precise.join(","), positional.join(","));
console.log(Object.isFrozen(precise));
// precise.push("post"); // TS2339
// precise[0] = "get"; // TS2540
// const retroactive = loose as const; // TS1355
const shared = [1, 2];
const withReference = [shared] as const;
withReference[0].push(3);
console.log(shared.join(","));
const nestedLiteral = [[1, 2]] as const;
// nestedLiteral[0].push(3); // TS2339
console.log(nestedLiteral[0].join(","), Object.isFrozen(nestedLiteral[0]));

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Loose = Expect<Equal<typeof loose, (string | number)[]>>;
type Precise = Expect<Equal<typeof precise, readonly ["get", 200]>>;
type Positional = Expect<Equal<typeof positional, readonly [string, number]>>;
type Referenced = Expect<Equal<typeof withReference[0], number[]>>;
type NestedLiteral = Expect<Equal<typeof nestedLiteral[0], readonly [1, 2]>>;
```

The output is `get,200 get,200 get,200`, `false`, `1,2,3`, then `1,2 false`; five probes compile. The nested literal has a readonly tuple type, while the existing shared variable remains a mutable number[]. Neither is frozen by as const. Use an explicit tuple annotation when positions matter but future values should remain broad; do not add literal constraints merely because they are available.

### 2) **Derive membership and make coverage an explicit contract**

Indexing a tuple's type with number yields its element union. That union describes membership, while iteration order and duplicates remain runtime properties of the source tuple. Keyof the tuple is a different query: it includes array keys such as length, rather than producing the element values.

Save as membership.ts.

```typescript
const METHODS = Object.freeze(["get", "post"] as const);
type Method = (typeof METHODS)[number];
const handlers: Record<Method, () => string> = {
  get: () => "G",
  post: () => "P",
};
function dispatch(method: Method): string { return handlers[method](); }
const searchable: readonly string[] = METHODS;
function isMethod(value: unknown): value is Method {
  return typeof value === "string" && searchable.includes(value);
}
console.log(METHODS.map(dispatch).join(","));
for (const candidate of ["get", "delete", 42]) {
  console.log(isMethod(candidate) ? dispatch(candidate) : "invalid");
}
// dispatch("delete"); // TS2345
const repeated = ["get", "post", "get"] as const;
console.log(repeated.length, new Set(repeated).size);
const arrayKey: keyof typeof METHODS = "length";
console.log(arrayKey);
const STATUSES = ["idle", "loading", "done"] as const;
type Status = (typeof STATUSES)[number];
function next(status: Status): Status {
  const candidate = STATUSES[(STATUSES.indexOf(status) + 1) % STATUSES.length];
  if (candidate === undefined) throw new Error("missing status");
  return candidate;
}
console.log(STATUSES.map(next).join(","));

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Members = Expect<Equal<Method, "get" | "post">>;
type DuplicatesDoNotExpandUnion = Expect<Equal<typeof repeated[number], "get" | "post">>;
```

The output is `G,P`, `G`, `invalid`, `invalid`, `3 2`, `length`, then `loading,done,idle`; both probes compile. The explicit Record contract requires a handler for each Method. If delete is added to METHODS, the missing handlers.delete is rejected. A function that merely returns G for get and P for everything else would still compile after that addition; deriving a union does not automatically make arbitrary logic exhaustive.

The runtime isMethod function actually checks membership. Its table is frozen here so ordinary runtime writes cannot expand the accepted membership beyond the declared tuple. This is a deliberate integrity policy, distinct from the const assertion. The searchable view admits a general string to includes without changing the source's type or casting its result. Next performs an actual index check before returning; no assertion hides a possible undefined expression.

A derived union avoids manually copying this finite table's members into a second type declaration. It does not establish uniqueness, preserve order inside the union, validate independent tables or prevent unsafe interop from violating assumptions. [Indexed queries](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.3. Type queries on objects keyof indexed access and typeof capture.md>) owns the underlying type operations.

### 3) **Admit readonly readers and deliberately widen drafts**

A function that only reads strings can accept readonly string[] and work with mutable arrays, readonly arrays and const tuples. A function that must mutate needs a different contract. Create a copy when a draft must be independent, then choose whether its elements should retain the source's literal union or admit arbitrary strings. “Never widen the source or copy” is not a sound rule for mutable state.

Save as consumers.ts.

```typescript
const METHODS = ["get", "post"] as const;
function count(values: readonly string[]): number { return values.length; }
console.log(count(METHODS), count(["other"]), count([]));
function append(values: string[], value: string): void { values.push(value); }
// append(METHODS, "delete"); // TS4104: readonly input cannot supply a mutable parameter
const narrowDraft = [...METHODS];
// narrowDraft.push("delete"); // TS2345: still a get | post element contract
const broadDraft: string[] = [...METHODS];
append(broadDraft, "delete");
console.log(broadDraft.join(","), METHODS.join(","), Object.is(broadDraft, METHODS));
type AllowedMethod = "get" | "post";
const checked = ["get", "post"] as const satisfies readonly AllowedMethod[];
// const typo = ["gett"] as const satisfies readonly AllowedMethod[]; // TS2820
console.log(checked.join(","));
```

The output is `2 1 0`, `get,post,delete get,post false`, then `get,post`. BroadDraft intentionally widens its element contract and has independent outer identity. That serves an editable list without weakening the source table. The checked declaration catches a source typo against a separately defined domain contract; satisfies does not perform runtime validation. [Literal-preserving transforms](<../../../09 Utility Types and Type Transformations/sections/3. Transformations in Practice/3.3. satisfies and as const preserving literals through transforms.md>) covers contextual effects and the legal operator order.

### 4) **Common confusion**

Const binding, const assertion, readonly view and freezing are different decisions. Preserving literal positions can be useful, but it does not guarantee deep runtime immutability or every desired consumer invariant. A repeated tuple entry still iterates twice even though the derived union includes its literal only once.

A mutable parameter is not automatically a defect: append genuinely needs to write. Changing such a parameter to readonly would require changing its behavior. Readonly admission is appropriate for readers, while copying and an explicit broader element type can be appropriate for editable drafts.

### 5) **Performance note**

Const assertions, indexed-access types and satisfies checks erase. Freeze, includes, map, Set construction, indexOf and spreading remain real operations. A fresh draft copies references into a new outer array; literal preservation does not perform that copy. No “computed once” checker cache guarantee, literal-count threshold or universal checking-speed benefit was established. Use a finite table because it models the domain, then measure real workloads if checking or runtime costs become significant.
