## 2.2. `as const` tuples — literal inference and readonly

### 1) **`as const` tuple inference** (literals plus readonly plus arity in one assertion)

**Definition** — `["get", 200] as const` infers `readonly ["get", 200]`: each element narrowed to its literal (`"get"`, not `string`), the array frozen to `readonly`, and the tuple arity fixed (length 2, positions typed). Three guarantees — literal precision, non-mutation, fixed shape — from one eight-character assertion, all erased at emit.

**What problem it solves / history** — route/status tables (`["get", "post"]` widening to `string[]`, losing exhaustiveness; mutable tables accepting pushes that broke arity-indexed lookups) needed three separate declarations (literal union + readonly + tuple) that drifted independently. `as const` (TS 3.4) fuses all three at the value: the table *is* the type source, and `typeof table[number]` derives every downstream set from it.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), declare curated tables (routes, methods, statuses, permissions) as `as const` tuples/objects at module scope; derive working types (`typeof t[number]`, `keyof typeof t`) instead of re-listing. Pair with `satisfies` contracts for typo-checking (see [3.3. Literal preservation](<../../../09 Utility Types and Type Transformations/sections/3. Transformations in Practice/3.3. satisfies and as const preserving literals through transforms.md>) in 09).

**Runnable example** — table as type source (good vs bad, `tsc --strict`):

```typescript
// good — as const: literals + readonly + arity; typeof derives the working set
const METHODS = ["get", "post"] as const;
type Method = (typeof METHODS)[number]; // "get" | "post" — derived, never listed
function handle(m: Method): string { return m === "get" ? "G" : "P"; }
console.log(handle("get")); // G
// METHODS.push("delete"); // error TS2339 — arity/readonly enforced at the source

// bad — widened table: exhaustiveness dead on arrival
const loose = ["get", "post"]; // string[] — literals widened at declaration
type LMethod = (typeof loose)[number]; // string — derived set is "any string"
function handleBad(m: string): string { return m; } // no literals to exhaust over
// fix — as const at the source: narrow once, derive everywhere
console.log(handleBad("anything-compiles")); // anything-compiles — the cost of widening
```

**Common confusion** — "`as const` freezes at runtime" — narrows the *type* only; runtime still mutable (pair with `Object.freeze` when enforcement matters — see 1.2 promise 3). "`readonly ["get"]` accepts `["get"]` writes" — nothing accepts writes to readonly (push/index-write absent) — readonly-ness travels with the type, not the assertion site. "`as const` on huge arrays is free" — every element becomes a literal instantiation (10k rows → 10k literal types — see 09/3.3 size guidance; const-assert curated tables, type-annotate datasets).

**Performance note** — literal instantiations cache per element (small tables trivial); the derived union (`[number]` indexed access) computes once. Check cost grows with table size — curated tables (tens) free, generated lists (thousands) need explicit `string` element types instead.

**Mentor note** — hover `METHODS` (`readonly ["get", "post"]`) vs `loose` (`string[]`) — three guarantees visible in one tooltip vs none. Exercise: add `"delete"` to `METHODS` and watch `handle` demand a branch (exhaustiveness re-armed by propagation); add it to `loose` and watch nothing happen. Review gate: curated string tables without `as const` fail review.

### 2) **Literal tuples as derived sets** (unions, keys, and exhaustiveness from ordered data)

**Definition** — `T[number]` over a tuple yields the element union (`["a","b"][number]` → `"a" | "b"`); mapped/indexed derivation (`keyof`, `Partial`, template tables) consumes ordered sources the same way. The tuple is the *single* source: order for runtime (iteration, indexing), union for types (exhaustiveness, parameters) — one declaration serving both worlds without duplication.

**What problem it solves / history** — parallel declarations (a runtime array *plus* a hand-listed union — `const MS = ["get","post"]; type M = "get" | "post"`) drifted on every edit (array gains `"delete"`, union forgets it — handlers untyped but runtime-present). Indexed derivation (`typeof MS[number]`) deletes the second declaration: the union *is* the array's type projection, so drift is impossible by construction.

**Modern guidance** — as of TypeScript 5.9 era, derive every working set from its source table (`Method = typeof METHODS[number]`, `Route = typeof ROUTES[number]`, handler keys from event tuples) — never list a union that mirrors a runtime table. When order doesn't matter, still prefer tuple sources (indexable, iterable, free union via `[number]`) over bare unions plus separate arrays.

**Runnable example** — one source, both worlds (good vs bad, `tsc --strict`):

```typescript
// good — tuple serves runtime order AND type union from one declaration
const STATUSES = ["idle", "loading", "done"] as const;
type Status = (typeof STATUSES)[number]; // "idle" | "loading" | "done"
function next(s: Status): Status {
  const i = (STATUSES as readonly string[]).indexOf(s);
  return STATUSES[(i + 1) % STATUSES.length] as Status;
}
console.log(next("idle")); // loading — runtime order + type union, same source

// bad — parallel declarations drift
const STATUSES2 = ["idle", "loading", "done"];
type Status2 = "idle" | "loading" | "done"; // mirrors STATUSES2 today...
// STATUSES2.push("archived") compiles (mutable string[]); Status2 silently lacks it — drift
// fix — as const + typeof [number]: the union cannot drift from the table
console.log(STATUSES2.length); // 3 — runtime grew, type didn't (the drift)
```

**Common confusion** — "`[number]` only works on tuples" — works on any array/tuple (`string[][number]` is `string`) — tuples just yield *literal* unions when const-asserted. "derived unions preserve order" — unions are unordered sets (`"done" | "idle"` ≡ `"idle" | "done"`) — order lives in the tuple (iteration/indexing), membership in the union — use each where it belongs. "indexing needs the tuple type imported" — `typeof table[number]` works from the *value* — no type import required, value-to-type projection in one expression.

**Performance note** — indexed access caches per (tuple, index) pair — one computation per derived set. The union's size drives downstream check cost (exhaustive switches over 200 statuses check 200 branches) — curated tables keep switches fast; generated sets need explicit testing strategy.

**Mentor note** — push to the runtime array and ask "did the union change?" (no — drift demonstrated), then convert to `as const` + derived and repeat (union follows — drift impossible). Exercise: find one mirrored array+union pair in the codebase and delete the union — count call sites that keep compiling (all of them, now derived).

### 3) **When `as const` over-narrows** (widen the parameter, not the argument)

**Definition** — `readonly ["get"]` passed to `(xs: string[]) => …` errors (readonly → mutable banned); passed to `(xs: string)`-shaped generics it instantiates literally (sometimes *too* narrow — a helper meant for any string now returns `"get"`-specific types). The fix direction is uniform: widen the *receiving* side (mutable/readonly-tolerant parameters, `string` returns) — never strip the source's precision with casts or mutable re-declarations.

**What problem it solves / history** — const-asserted arguments broke loosely-typed helpers (`process(METHODS)` erroring on `string[]` params; `wrap("lit")` returning `"lit"`-branded wrappers that poisoned downstream unions) — teams "fixed" it by de-consting sources (losing exhaustiveness everywhere) instead of widening the one helper. Parameter-side widening (`readonly string[]`, explicit `string` returns) preserves source precision for every other consumer while admitting the helper.

**Modern guidance** — as of TypeScript 5.9 era, type helpers to *admit* readonly/literal inputs (`xs: readonly string[]`, `T` unconstrained with `string` return) and keep sources const-asserted — precision lives at declarations, tolerance at receivers. When a generic over-narrows (`identity("get")` → `"get"` where `string` was wanted), annotate the call (`identity<string>("get")`) or the return — never widen the source.

**Runnable example** — widen receivers, keep sources narrow (good vs bad, `tsc --strict`):

```typescript
// good — tolerant parameter admits every source shape
function count(xs: readonly string[]): number { return xs.length; }
const lit = ["a", "b"] as const; // readonly ["a", "b"]
console.log(count(lit), count(["x"]), count([])); // 2 1 0 — all admitted, none widened

// good — explicit return widens where the API promises string, not literal
function label<T>(x: T): string { return String(x); } // return string (not T): widening by design
const l: string = label("get"); // string — downstream unions unaffected
console.log(l.toUpperCase()); // GET

// bad — de-consting the source to satisfy one narrow helper
const src = ["get", "post"]; // string[] — precision deleted for ALL consumers...
function needMutable(xs: string[]): number { return xs.length; }
console.log(needMutable(src)); // 2 — works, but exhaustiveness died everywhere else
// fix — needMutable(xs: readonly string[]): source stays as const, helper admits it
```

**Common confusion** — "readonly inputs complicate helpers" — one keyword (`readonly`) admits mutable, tuple, and const sources alike — *less* constrained, not more. "generic over-narrowing is inference failing" — inference succeeding *too well* (`"get"` is the precise answer) — the API, not the solver, decides whether precision or widening serves callers. "casts at the call site are equivalent" — `lit as string[]` works once and rots (every new call site re-casts); widening the parameter fixes all call sites permanently.

**Performance note** — tolerant parameters change nothing at check cost (same element checks, wider admission); const sources keep downstream switches narrow (fewer members = faster checks) — widen-receivers is the performance-positive direction too.

**Mentor note** — the direction rule ("widen receivers, never narrow sources") fits a review stamp — violations are one-line diffs in the wrong file. Exercise: find one de-consted source, restore `as const`, widen the complaining helper instead — count how many *other* call sites regain exhaustiveness (the blast radius of the original de-consting, reversed).
