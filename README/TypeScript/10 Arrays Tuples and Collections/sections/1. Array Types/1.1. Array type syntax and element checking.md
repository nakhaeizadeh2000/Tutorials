## 1.1. Array type syntax and element checking

An array type describes an open collection and the operations its elements support. It can reject a wrong literal or push, but it does not validate external data or guarantee that every numeric position exists. Choose the element contract independently from the way the array is allocated.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence under its filename. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`; run `node dist/FILE.js`. Activate commented negatives individually and use the same flags with --noEmit instead of --outDir dist.

### 1) **Two spellings and meaningful parentheses**

String[] and Array<string> describe the same mutable array type. The [primary array guide](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#arrays) documents both. Choose a readable spelling; a team's style rule may make that consistent, but neither spelling adds methods, validates values or creates a different runtime container. Parentheses, in contrast, can change the type being expressed.

Save as syntax.ts.

```typescript
const names: string[] = ["Ada"];
const genericNames: Array<string> = names;
const sameNames: string[] = genericNames;
genericNames.push("Lin");
console.log(names === sameNames, names.join(","));
const mixed: (string | number)[] = ["a", 1];
let scalarOrNumbers: string | number[] = "a";
console.log(scalarOrNumbers, mixed.join(","));
scalarOrNumbers = [1, 2];
console.log(scalarOrNumbers.length);
// scalarOrNumbers = ["a"]; // TS2322: string[] is neither a string nor number[]
const callbacks: Array<() => string> = [() => "hello"];
const parenthesized: (() => string)[] = callbacks;
const makeNames: () => string[] = () => ["Ada", "Lin"];
console.log(parenthesized.map(callback => callback()).join(","), makeNames().join(","));
// const wrong: (() => string)[] = makeNames; // TS2322: a function is not an array of functions

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type SameArray = Expect<Equal<string[], Array<string>>>;
type MixedElement = Expect<Equal<typeof mixed[number], string | number>>;
```

The output is `true Ada,Lin`, `a a,1`, `2`, then `hello Ada,Lin`; both live type probes compile. Assignment created aliases, so pushing through genericNames changed names too. The spelling did not make a copy. In the union example, parentheses put the union inside the element position; without them, the union permits a scalar string or an array of numbers. Likewise, an array of callbacks differs from one callback returning an array.

### 2) **Check writes and narrow dynamic elements**

An explicit element type is useful for state whose intended invariant should remain stable. A mixed literal can instead infer a union element type when both kinds of values are intended. Neither choice runs a validator. Any bypasses useful checks, while unknown requires evidence before a string operation.

Save as elements.ts.

```typescript
const ids: string[] = [];
ids.push("u1");
// ids.push(42); // TS2345
// const wrongIds: string[] = ["u1", 42]; // TS2322
console.log(ids.join(","));
const mixed = ["a", 1];
console.log(mixed.map(value => typeof value === "string" ? value.toUpperCase() : value.toFixed(1)).join(","));
const loose: any[] = ["a"];
loose.push(42);
try {
  loose.map(value => value.toUpperCase());
} catch (error) {
  console.log("unchecked failure", error instanceof TypeError);
}
const incoming: unknown[] = ["a", 42];
console.log(incoming.map(value => typeof value === "string" ? value.toUpperCase() : "not a string").join(","));
// incoming.map(value => value.toUpperCase()); // TS18046: unknown requires evidence
```

The output is `u1`, `A,1.0`, `unchecked failure true`, then `A,not a string`. The wrong value entered loose at the push, but the failure appeared later in the mapper. Catching this intentional failure lets the rest of the demonstration run. Unknown does not automatically validate the payload either: this mapper implements a specific rule for each value. The [unknown owner](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>) covers evidence at dynamic boundaries.

### 3) **Empty contexts and allocated holes**

Do not apply one empty-array inference rule to every position. Under these flags an object property's uncontextualized [] can infer never[], while an explicit property type establishes a useful intended contract. A const assertion on [] produces an empty readonly tuple. Evolving locals and generic arguments have additional context-sensitive behavior; the [inference owner](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.2. Type inference widening and contextual typing.md>) demonstrates them fully.

Array construction raises a separate runtime question. The [Array constructor documentation](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/Array#array_constructor_with_a_single_parameter) explains that one numeric argument supplies length and creates empty slots. A string element annotation does not initialize those slots.

Save as construction.ts.

```typescript
const untypedState = { jobs: [] };
// untypedState.jobs.push("job-1"); // TS2345: this property's element type is never
const state: { jobs: string[] } = { jobs: [] };
state.jobs.push("job-1");
const emptyTuple = [] as const;
// emptyTuple.push("job-1"); // TS2339: readonly empty tuple has no push
console.log(state.jobs.join(","), untypedState.jobs.length, emptyTuple.length);
const allocated = new Array<string>(2);
console.log(allocated.length, 0 in allocated, allocated[0]);
// const first: string = allocated[0]; // TS2322 with noUncheckedIndexedAccess
// allocated[0].toUpperCase(); // TS2532 with noUncheckedIndexedAccess
const initialized = Array.from({ length: 2 }, (_, index) => "job-" + index);
console.log(initialized.length, 0 in initialized, initialized.join(","));
console.log(initialized[0]?.toUpperCase());

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type EmptyProperty = Expect<Equal<typeof untypedState.jobs, never[]>>;
type EmptyTuple = Expect<Equal<typeof emptyTuple, readonly []>>;
type AllocatedRead = Expect<Equal<typeof allocated[0], string>>;
```

The output is `job-1 0 0`, `2 false undefined`, `2 true job-0,job-1`, then `JOB-0`. The last type probe uses an indexed-access type, which describes the array's declared element type. The actual allocated[0] expression can still be undefined and is checked accordingly by noUncheckedIndexedAccess. The flag does not add slots or runtime checks. Disabling it permits the commented direct method call, which then throws TypeError on the missing value. Array.from here performs real initialization; it is not a compiler-speed workaround.

Never is assignable to other types. The rejected property push fails in the opposite direction: an ordinary string is not assignable to never. A never[] need not mean the program is invalid, but this state needs an explicit string element contract before ordinary writes.

### 4) **Common confusion**

An element type is not a presence guarantee. An empty string[] is valid, a positive length can coexist with holes, and an out-of-range read can yield undefined. Tuples add positional contracts, but their mutation limits need separate examination rather than a blanket claim that every length-changing operation is forbidden.

A const array binding can still be mutated. Readonly changes the available static operations; it is a separate choice from the two mutable array spellings and from actual freezing. Narrowing unknown values is also a separate runtime operation from declaring an array's type.

### 5) **Performance note**

Array type syntax and annotations erase; they add no runtime validation or allocation. Pushes, mapping, Array construction and Array.from remain real operations. Array.from in the example calls a mapper to fill positions, whereas the numeric constructor leaves holes. Choose from the required data, not an unsupported checking-time formula or a claim that one spelling parses faster. No benchmark or review-speed measurement was performed here.

### 6) **Mentor note**

Ask the learner to predict both length and slot presence before running construction.ts. Then ask which operation first introduced the bad value in elements.ts and which operation observed the failure. A sound answer separates allocation, element contracts and dynamic evidence.

For practice, implement appendName(target: string[], value: unknown): boolean. Append and return true only for a string; otherwise return false. A typeof check should narrow value before push, without an assertion. Calling it with 42 and then Ada must print false, true and leave only Ada in the target. Removing the narrowing should produce TS2345 at the push. The boolean is the chosen acceptance policy, not proof that arbitrary objects or nested arrays were validated.
