## 1.1. Array type syntax and element checking

### 1) **Two spellings, one type** (`T[]` vs `Array<T>` — style, not semantics)

**Definition** — `string[]` and `Array<string>` name the identical type: a mutable, ordered list of `string`. The checker, emit, and assignability treat them interchangeably — `Array<string>` is not "more generic" and `T[]` is not "simpler-checked." Teams pick one for readability and lint it.

**What problem it solves / history** — mixed-spelling codebases (`string[]` beside `Array<string>` beside `ReadonlyArray<string>`) forced readers to pause on every declaration wondering whether the spelling signaled a different type — it never did. One enforced spelling removes the pause: the `array-type` lint rule (consistent spelling) exists precisely because the choice is pure style.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), default to `T[]` for simple element types (`string[]`, `User[]`) and allow `Array<T>` where `T[]` nests unreadably (`Array<string | number>[]` vs `(string | number)[][]` — the former parses faster). Lint it (`@typescript-eslint/array-type` with `default: "array"`) so the codebase never mixes. All array syntax erases (see [2.1. Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)).

**Runnable example** — identical types, one enforced style (good vs bad, `tsc --strict`):

```typescript
// good — one spelling per codebase (T[] here); nesting uses Array<> where clearer
const names: string[] = ["ada", "lin"];
const matrix: Array<string[]> = [["a"], ["b", "c"]]; // Array<> avoids ]] nesting noise
console.log(names[0]?.toUpperCase(), matrix[1]?.length); // ADA 2

// good — generic containers compose with either spelling identically
interface Pager<T> { items: T[]; total: number; }
const pg: Pager<string> = { items: ["a"], total: 1 };
console.log(pg.items.length); // 1

// bad — mixed spellings force readers to diff identical types
const a: string[] = ["x"];
const b: Array<string> = a; // legal (same type!) — but the reader paused to verify
// fix — pick T[] (or Array<>) once, lint it, never mix
console.log(b[0]?.toUpperCase()); // X
```

**Common confusion** — "`Array<string>` supports more methods" — identical interface (`Array<T>`) backs both spellings — method sets cannot differ. "`readonly string[]` is a third spelling of the same" — `readonly` changes assignability (see [1.2. Readonly arrays](<./1.2. Readonly arrays and mutable vs frozen arrays.md>)) — spelling vs modifier differ. "linting style is bikeshedding" — inconsistent spelling measurably slows reviews (every mixed declaration re-asks "same type?") — lint once, never ask again.

**Performance note** — zero check or emit difference between spellings — the same `Array<T>` reference type resolves either way. The performance content is human: consistent spelling removes per-declaration verification from reviews.

**Mentor note** — show `string[]` and `Array<string>` side by side, ask "which methods differ?" (none), then enable the lint rule live — style debates end with automation, not meetings. Review gate: mixed-spelling files fail lint before human review begins.

### 2) **Element checking per position** (every element verified against `T`)

**Definition** — `const xs: number[] = [1, 2, 3]` checks *each* element against `number`; a heterogeneous literal `["a", 1]` against `string[]` errors on `1` (or infers `(string | number)[]` when unannotated — the checker unions the element types rather than picking one). Length is unchecked (arrays are open-ended); element type is total.

**What problem it solves / history** — untyped arrays (`any[]` by habit, or JS-migrated code with no annotations) pushed element-type errors to usage sites (`xs.map(x => x.toFixed())` failing far from the bad push) — each error pointed at the reader, never the writer. Element checking moves the error to the *literal or push* that introduced the wrong-typed value: write-side precision instead of read-side forensics.

**Modern guidance** — as of TypeScript 5.9 era, annotate collection state (`const ids: string[] = []`) so pushes check at the write; let literals infer when heterogeneous *intentionally* (`["a", 1]` → `(string | number)[]`), and annotate when the inference would union accidentally (mixed literal meant as `string[]` with a stray number — the annotation catches the stray). Prefer `unknown[]` + narrowing over `any[]` for genuinely dynamic payloads.

**Runnable example** — errors at the write, not the read (good vs bad, `tsc --strict`):

```typescript
// good — annotated state: bad push errors where written
const ids: string[] = [];
ids.push("u1");
// ids.push(42); // error TS2345 — caught at the push, not at a later .toUpperCase
console.log(ids.length); // 1

// good — heterogeneous literal infers a union element type honestly
const mixed = ["a", 1]; // (string | number)[] — both members usable with narrowing
console.log(typeof mixed[0]); // string

// bad — any[] defers every element error to usage sites
const loose: any[] = ["a"];
loose.push(42);
console.log(loose.map((x) => x.toUpperCase())); // compiles — crashes on 42 at runtime
// fix — string[] (or unknown[] + narrowing): the push, not the map, is checked
const strict: unknown[] = ["a", 42];
console.log(strict.length); // 2 — reads narrow per element instead of trusting all
```

**Common confusion** — "arrays check length" — never (that's tuples — see [2.1. Fixed arity tuples](<../2. Tuple Types/2.1. Fixed arity tuples labels and optional elements.md>)); `string[]` of length 0 and length 1000 share the type. "heterogeneous literal picks the first type" — the checker *unions* (`(string | number)[]`), never picks — each element keeps its type until narrowed. "`unknown[]` is just `any[]` with extra steps" — `unknown[]` forces per-element narrowing at reads; `any[]` disables it — opposite safety postures.

**Performance note** — element checking is O(elements) at literal/push sites, cached per array type afterward — literals of thousands of elements (generated fixtures) check once at declaration. Prefer building large arrays with `Array.from({length}, map)` (one checked mapper) over thousand-element literals (thousand element checks).

**Mentor note** — uncomment the bad `push(42)` and read TS2345 together — "error at the write" is the sentence that converts `any[]` users. Exercise: migrate one `any[]` state field to `unknown[]` and fix each resulting read error with narrowing — the error count *is* the bug list the `any` was hiding.

### 3) **Empty arrays and `never[]`** (no evidence → `never` element, annotate or seed)

**Definition** — `const xs = []` infers `never[]` under `strict` (`noImplicitAny`): with zero elements the checker has no evidence for the element type, so it picks `never` (assignable to nothing) rather than guessing. The array is then unusable until annotated (`const xs: string[] = []`) or evolved (`const xs = ["seed"]`).

**What problem it solves / history** — pre-`strict` code widened `[]` to `any[]` silently — every later push compiled and every later read was unchecked (the `any`-infection vector behind countless "how did a number get into my string list?" incidents). `never[]` flips the default to *unusable-until-specified*: the declaration errors on first use (`push("a")` onto `never[]` fails) instead of infecting downstream.

**Modern guidance** — as of TypeScript 5.9 era, always annotate empty-collection state (`const queue: Job[] = []`, `const seen = new Set<string>()`) — treat bare `[]` as a declaration smell in review. Seed from data where the type should follow the data (`const [first] = rows` patterns); annotate where the type leads the data (state fields, accumulators).

**Runnable example** — `never[]` forces the annotation (good vs bad, `tsc --strict`):

```typescript
// good — annotated: pushes checked from the first write
const queue: string[] = [];
queue.push("job-1");
console.log(queue[0]?.toUpperCase()); // JOB-1

// bad — bare [] infers never[]: every use errors until specified
const bad = []; // never[] — evolving-array inference (only literal push patterns evolve it)
// bad.push("x"); // error TS2345 — never[] accepts nothing (the forcing function working)
// fix — annotate: const bad: string[] = [] (or seed: const bad = ["x"])
function drain(q: string[]): number { return q.length; }
console.log(drain(queue)); // 1
```

**Common confusion** — "`never[]` is a bug in inference" — the honest answer to zero evidence (not `any[]`'s lie, not a guessed `string[]`) — the error message *is* the feature. "evolving arrays fix this automatically" — evolving inference (`let xs = []; xs.push("a")` → `string[]`) applies only to narrow literal patterns and collapses under most real code — annotate instead of relying on evolution. "`const xs: never[]` is useful" — almost never written by hand; `never[]` appears as an *inferred signal*, not a declared intent.

**Performance note** — `never[]` checks fastest (no element type to verify) — but its uses all error, so the "saving" is illusory. Annotated empty arrays cost one element-type registration — negligible; the real cost avoided is downstream `any`-infection forensics.

**Mentor note** — hover bare `[]` (`never[]`) vs annotated (`string[]`) side by side and ask "which one can be pushed to?" — the error that follows teaches evidence-based inference in thirty seconds. Review gate: bare `[]`/`new Set()`/`new Map()` without type arguments fail review.
