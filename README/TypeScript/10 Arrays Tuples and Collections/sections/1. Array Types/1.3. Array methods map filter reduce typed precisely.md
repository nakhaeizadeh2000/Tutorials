## 1.3. Array methods — `map`/`filter`/`reduce` typed precisely

### 1) **`map`/`filter`/`find` precision** (mapper return becomes element type)

**Definition** — `users.map(u => u.id)` types as `string[]` (mapper return threaded per element); `xs.find(p)` returns `T | undefined` (absence is the honest type); `filter` with a predicate (`x is T`) *narrows* the element type, while `filter(Boolean)` / truthiness callbacks keep the wide type. Method precision follows the callback's type — precise callbacks, precise results.

**What problem it solves / history** — loosely-typed callbacks (`any`-returning mappers, `Boolean` filters) laundered precision mid-chain: `mixed.filter(Boolean)` stayed `(string | number | null)[]` in older lib typings (no narrowing without a predicate), so downstream `toUpperCase` needed casts that hid real nulls. Predicate overloads (`filter<S extends T>(p: (x: T) => x is S): S[]`) made narrowing the default for well-typed callbacks — precision flows when the callback declares it.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), write callbacks with precise returns (predicates `is` for filters, narrow mappers for maps) and read chain hovers after each link — the inferred element type at each step is the review surface. Prefer `find` + undefined-narrowing over `filter(...)[0]` (length-1 arrays lie about presence).

**Runnable example** — precision follows the callback (good vs bad, `tsc --strict`):

```typescript
// good — predicate narrows: nulls proven gone, downstream needs no cast
const mixed: (string | null)[] = ["a", null, "b"];
const isStr = (x: string | null): x is string => x !== null;
const clean: string[] = mixed.filter(isStr); // string[] — narrowed by the predicate
console.log(clean.map((s) => s.toUpperCase()).join(",")); // A,B

// good — find returns T | undefined: absence handled, not indexed away
const hit = clean.find((s) => s.startsWith("A")); // string | undefined
console.log(hit?.toLowerCase() ?? "missing"); // a

// bad — Boolean filter keeps the wide type (no predicate, no narrowing)
const stillWide = mixed.filter(Boolean); // (string | null)[] — truthiness is not a type guard
// stillWide.map((s) => s.toUpperCase()); // error TS18048 — s possibly null (correctly!)
// fix — isStr predicate: declare the narrowing so filter can apply it
const fixed = mixed.filter(isStr).map((s) => s.toUpperCase());
console.log(fixed.join(",")); // A,B
```

**Common confusion** — "`filter(Boolean)` narrows nulls" — `Boolean` returns `boolean`, not a predicate — the stdlib has no `filter(Boolean)` narrowing overload (a `filter(isNonNull)` predicate is the fix; newer libs narrow `filter(Boolean)` only for specific falsy-union shapes — never rely on it). "`find` returns `T`" — `T | undefined` (empty match is normal) — indexing `[0]` after filter has the same honesty problem; prefer `find`. "map callbacks receive checked indexes" — the index param is `number` (not a literal) — per-position precision needs tuples, not arrays.

**Performance note** — predicate narrowing is check-time only (zero emit delta vs `Boolean`); chains allocate per link (filter creates an array, map creates another) — fuse hot loops (`for..of` with narrowing) past measured thresholds, keep chains elsewhere for readability.

**Mentor note** — hover each chain link (`mixed.filter(…)` → `string[]`? or wide?) before and after the predicate fix — chain-hover reading is the review skill for every collection pipeline. Exercise: convert three `filter(Boolean)` call sites to predicates and delete the downstream non-null assertions they required — assertion count is the precision dividend.

### 2) **`reduce` accumulator threading** (initial value fixes the accumulator)

**Definition** — `xs.reduce((acc, x) => …, init)` types the accumulator from `init` (no `init` → accumulator starts as `T`, first element consumed as seed — and errors on empty arrays' type, `T` with no fallback). The callback must return the accumulator type every iteration; a branch returning a different shape widens or errors — threading discipline enforced per step.

**What problem it solves / history** — `reduce` without `init` on possibly-empty arrays produced `T`-typed results from zero iterations (runtime `TypeError: Reduce of empty array with no initial value` with a confident `T` type) — the signature promised a value the runtime couldn't deliver. Always-`init` plus accumulator-typed callbacks make the empty case a value (`init` returned) with a checked type instead of a throw with a lie.

**Modern guidance** — as of TypeScript 5.9 era, always pass `init` (typed as the accumulator, not necessarily the element — `Record<string, number>` accumulators over `User[]` are the norm), annotate the accumulator when the callback branches (`<Record<string, number>>{}` seeds read better than inference puzzles), and prefer `map`/`filter`/`find`/`some` for single-purpose passes — `reduce` earns its complexity only for genuine accumulation (grouping, summing with conditions, building maps).

**Runnable example** — init fixes the accumulator (good vs bad, `tsc --strict`):

```typescript
// good — init types the accumulator; empty input returns init, not a throw
interface Sale { region: string; amount: number; }
function byRegion(sales: Sale[]): Record<string, number> {
  return sales.reduce<Record<string, number>>((acc, s) => {
    acc[s.region] = (acc[s.region] ?? 0) + s.amount;
    return acc;
  }, {});
}
console.log(byRegion([])); // {} — honest empty, typed Record<string, number>
console.log(byRegion([{ region: "eu", amount: 5 }]).eu); // 5

// bad — no init: accumulator seeded from first element, empty array throws at runtime
function sumBad(xs: number[]): number {
  return xs.reduce((a, b) => a + b); // compiles — throws TypeError on [] at runtime
}
// sumBad([]); // TypeError: Reduce of empty array with no initial value
// fix — reduce((a, b) => a + b, 0): init covers empty AND fixes the accumulator type
const sumOk = (xs: number[]): number => xs.reduce((a, b) => a + b, 0);
console.log(sumOk([]), sumOk([1, 2])); // 0 3
```

**Common confusion** — "accumulator must match element type" — independent (`Record` accumulator over `Sale[]` elements is idiomatic) — `init` declares the accumulator; elements feed it. "explicit generic `<Record<…>>` is redundant with `init`" — `init` usually suffices for inference (`{}` widens to `{}`… actually `{}` infers `{}` — the explicit parameter documents intent and survives callback-branch widening — prefer explicit on multi-branch reducers). "`reduce` replaces loops" — `for..of` with early `break`/`continue` outperforms and out-reads `reduce` with flag variables — reduce for accumulation, loops for control flow.

**Performance note** — `reduce` allocates nothing beyond the accumulator (single pass, O(n)) — the cost question is readability-per-branch, not speed; multi-branch reducers with spread-per-iteration (`{...acc, [k]: v}` — O(n²) copies) are the real perf trap — mutate the accumulator object per step instead.

**Mentor note** — run `sumBad([])` and read the `TypeError` next to its confident `number` return type — signature-vs-runtime mismatch in one throw. Rule: `reduce` without `init` fails review unconditionally; multi-branch reducers get explicit accumulator generics.

### 3) **Mutating vs non-mutating methods** (typing the difference)

**Definition** — mutating methods (`sort`, `splice`, `push`, `reverse`, `fill`) change the array in place *and* return it (or a removed slice) — typed on `T[]` only, absent from `readonly T[]`. Copying counterparts (`toSorted`, `toReversed`, `toSpliced`, `slice`, `concat`, `map`, `filter` — ES2023+) return new arrays and exist on readonly too. The type system encodes the mutation contract: availability *is* documentation.

**What problem it solves / history** — `sorted = items.sort()` looked like a pure derivation but aliased and reordered the input (the 1.2 `totalBad` incident class) — readers couldn't distinguish derivation from mutation without reading bodies. Copying methods (ES2023, lib `es2023`) plus readonly availability make the distinction *syntactic*: `toSorted` cannot alias by construction; `sort` on a `readonly` parameter doesn't compile — mutation requires a mutable-typed receiver.

**Modern guidance** — as of TypeScript 5.9 era (target `es2023`+ for the `toX` methods, else polyfill), derive with copying methods (`toSorted`, `toSpliced`, `slice`) on shared/readonly data; mutate (`sort`, `splice`) only on locally-owned builders. When a function sorts its input, take `readonly` and return `toSorted` — signature proves non-mutation; when it must mutate, take mutable and document why the caller surrenders the order.

**Runnable example** — derivation vs mutation by construction (good vs bad, `tsc --strict`):

```typescript
// good — toSorted derives; input provably untouched (readonly even forbids sort)
function top3(scores: readonly number[]): number[] {
  // scores.sort(); // error TS2339 — sort absent on readonly (contract enforced)
  return scores.toSorted((a, b) => b - a).slice(0, 3);
}
const board = [3, 1, 2, 5];
console.log(top3(board).join(","), board.join(",")); // 5,3,2 3,1,2 — input order kept

// bad — sort derives nothing: aliases and reorders the caller's list
function top3Bad(scores: number[]): number[] {
  return scores.sort((a, b) => b - a).slice(0, 3); // compiles — board reordered behind caller
}
console.log(top3Bad(board).join(","), board.join(",")); // 5,3,2 5,3,2 — input destroyed
// fix — readonly parameter + toSorted: non-mutation by signature AND by method
```

**Common confusion** — "`toSorted` is just slower `sort`" — same O(n log n) algorithm; one extra O(n) copy — the copy *is* the feature (aliasing eliminated). "`slice` before `sort` equals `toSorted`" — `slice().sort()` works but reads as two operations with an interim mutable; `toSorted` states derivation in one name — prefer the vocabulary. "readonly arrays lack needed methods" — readonly keeps every non-mutating method (`map`, `slice`, `toSorted`, iteration) — only the seven mutators are absent, which is exactly the point.

**Performance note** — copying methods allocate O(n) per call (the derivation price) — fine at boundaries, wasteful in tight loops over huge arrays (sort a local mutable copy there, or sort indices). `splice` vs `toSpliced` share the O(n) shift cost — copying adds one allocation, not algorithmic overhead.

**Mentor note** — the before/after `board.join(",")` comparison (`3,1,2` vs `5,3,2`) is the aliasing demo that ends "sort returns a new array" myths permanently. Lint: flag `.sort(` on parameters (prefer `toSorted` or document ownership transfer); review any mutating method on non-local arrays as a defect.
