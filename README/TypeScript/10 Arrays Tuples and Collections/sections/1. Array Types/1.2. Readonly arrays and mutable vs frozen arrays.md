## 1.2. Readonly arrays — mutable vs frozen arrays

### 1) **`readonly T[]` / `ReadonlyArray<T>`** (compile-time freeze on lists)

**Definition** — `readonly string[]` (equivalently `ReadonlyArray<string>`) is the array type minus every mutating member: no `push`/`pop`/`splice`/index-write; reads (`length`, indexing, iteration, `map`) all remain. Like 04/1.2's `readonly` properties, it is a *checker* promise — emit is an ordinary array unless `Object.freeze` also runs.

**What problem it solves / history** — shared-list mutation (a callee `sort`ing or `push`ing a caller's array) was invisible in signatures — `process(items: string[])` *permits* mutation whether or not it *performs* it, so every caller had to read the implementation to know their list survived. `readonly` parameters advertise non-mutation in the signature: `process(items: readonly string[])` *cannot* mutate — callers verify by reading one annotation, and violating implementations fail at the method call, not in a downstream test.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), default parameters, return snapshots, and shared state to `readonly T[]`; keep `T[]` for locally-built accumulators. Spell it `readonly T[]` (reads left-to-right with the declaration; `ReadonlyArray<T>` only where `readonly` prefix nests poorly). Never `as`-away readonly at call sites — copy (`[...xs]`) when mutation is genuinely needed.

**Runnable example** — freeze advertised in the signature (good vs bad, `tsc --strict`):

```typescript
// good — readonly parameter: implementation cannot mutate, callers need not audit it
function total(xs: readonly number[]): number {
  // xs.push(4); // error TS2339 — push does not exist on readonly (caught at authorship)
  return xs.reduce((a, b) => a + b, 0);
}
const shared = [1, 2, 3];
console.log(total(shared), shared.length); // 6 3 — caller's list provably intact

// good — copy to mutate: the boundary is explicit, not hidden
function extended(xs: readonly string[], extra: string): string[] {
  return [...xs, extra]; // new array — shared input untouched by construction
}
console.log(extended(["a"], "b").length); // 2

// bad — mutable parameter permits silent input mutation
function totalBad(xs: number[]): number {
  xs.sort((a, b) => b - a); // compiles — caller's order destroyed as a side effect
  return xs[0] ?? 0;
}
const order = [3, 1, 2];
console.log(totalBad(order), order[0]); // 3 3 — input reordered behind the caller's back
// fix — readonly parameter (plus toSorted when a sorted copy is needed)
```

**Common confusion** — "`readonly` freezes at runtime" — checker-only; a determined `as` cast or JS caller still mutates — pair with `Object.freeze` (next promise) when runtime matters. "`readonly string[]` accepts fewer values" — accepts *more* (every `string[]` flows in); it *does* less (no mutation) — assignability widens while capability narrows. "methods returning new arrays need mutable input" — `map`/`filter`/`slice` exist on readonly arrays and return mutable results — reading never requires mutability.

**Performance note** — zero runtime cost (erased modifier); check cost identical to mutable. The *performance* win is aliasing clarity: readonly signatures let reviewers rule out mutation-driven re-renders/recomputations without reading bodies — fewer defensive copies (`[...xs]` everywhere "just in case") once signatures advertise.

**Mentor note** — uncomment the `push` line and read TS2339 together — "the signature protects the caller from the implementation" inverts the usual direction of type errors and sticks. Exercise: convert three shared-list parameters to `readonly` and fix each resulting implementation error with copies — the error sites *are* the mutation audit. Review gate: exported functions taking mutable array parameters must justify why.

### 2) **Mutable assignable to readonly** (read-covariance, write-invariance)

**Definition** — `const ro: readonly string[] = mutable` compiles (a mutable list satisfies every read a readonly consumer needs); `const m: string[] = ro` errors (readonly cannot satisfy future writes). Direction: mutable → readonly flows; readonly → mutable requires a copy. This is use-site covariance for reads with invariance for writes — the array instance of 02/3.1's variance rules.

**What problem it solves / history** — one-direction flow lets APIs *widen* what they accept without weakening what they promise: `render(items: readonly Item[])` accepts every caller's list (mutable state, literals, tuples) while guaranteeing non-mutation — callers pass freely, implementations stay constrained. The reverse ban (`readonly` → mutable) is what makes the guarantee trustworthy: no laundering path exists without an explicit, reviewable copy.

**Modern guidance** — as of TypeScript 5.9 era, accept `readonly` in every read-only position (parameters, snapshot fields, return types of getters); produce mutable only from builders/factories (and freeze on publication when the value escapes). When a readonly input must become mutable locally, copy at the boundary (`const work = [...input]`) — one line, visible in review, never `as`.

**Runnable example** — flow direction enforced (good vs bad, `tsc --strict`):

```typescript
// good — every list kind flows into readonly consumers
function render(items: readonly string[]): string { return items.join(","); }
const mutable = ["a", "b"];
const tuple = ["x", "y"] as const; // readonly ["x", "y"] — flows in too
console.log(render(mutable), render(tuple), render(["lit"])); // a,b x,y lit

// good — readonly to mutable via explicit copy (reviewable, honest)
function ownIt(items: readonly string[]): string[] { return [...items]; }
console.log(ownIt(tuple).length); // 2 — new mutable array, source untouched

// bad — readonly to mutable via cast hides the aliasing
function ownBad(items: readonly string[]): string[] {
  return items as string[]; // compiles — but mutating the result mutates the caller's tuple
}
const src = ["a"];
const aliased = ownBad(src);
aliased.push("MUTATED");
console.log(src.length); // 2 — caller's list changed through the "copy"
// fix — [...items]: the copy is one line; the cast is a shared-mutation bug
```

**Common confusion** — "tuples aren't arrays so they won't flow in" — tuples *are* arrays structurally (fixed-length `Array` subtypes) — `readonly ["x","y"]` satisfies `readonly string[]` (see [2.1. Fixed arity tuples](<../2. Tuple Types/2.1. Fixed arity tuples labels and optional elements.md>)). "copying on every boundary is wasteful" — copies cost O(n) at explicit, auditable points; hidden aliasing costs unbounded debugging — copy at trust boundaries, alias within them. "`as const` arrays are a different universe" — `readonly [literal]` flows into `readonly T[]` like any tuple — one lattice, not two.

**Performance note** — the copy (`[...xs]`) is the only runtime cost in this leaf — O(n) allocation per boundary crossing. Budget it: copy at module/API boundaries (rare, large clarity win); alias freely *within* a function (no check or runtime cost for passing readonly references around).

**Mentor note** — the `ownBad` demo (caller's `src` growing through the "copy") is the aliasing lesson that sticks — run it, gasp, then fix with spread. Ask "who owns this array?" at every boundary in review — readonly answers "the caller", mutable answers "whoever holds it", casts answer "nobody knows."

### 3) **`as const` arrays and runtime freezing** (checker promise vs value guarantee)

**Definition** — `["a", "b"] as const` infers `readonly ["a", "b"]` (literal elements + readonly + tuple arity — three guarantees in one assertion); `Object.freeze([...])` shallow-freezes the *value* at runtime (mutations throw in strict mode / silently fail otherwise). The first convinces `tsc`, the second convinces the runtime — production boundaries that matter need both, applied in that order (narrow, then freeze).

**What problem it solves / history** — checker-only freezing left a hole every JS-interop boundary could drive through: a `readonly string[]` passed to untyped code (or a lying `as` cast) mutated freely at runtime while the types claimed frozen — caught only when downstream reads saw impossible values. The `as const` + `Object.freeze` pair closes both worlds: literals for exhaustiveness, freezing for enforcement, each verifying the other.

**Modern guidance** — as of TypeScript 5.9 era, publish shared tables as `as const` *plus* `Object.freeze` at module scope (config, routes, permissions); consume them as `readonly` types. Remember `freeze` is shallow (nested arrays/objects stay mutable — deep-freeze or `DeepReadonly` types for nested structures, see [3.1. Deep transforms](<../../../09 Utility Types and Type Transformations/sections/3. Transformations in Practice/3.1. Deep transforms DeepPartial DeepReadonly and the budget.md>) in 09).

**Runnable example** — both worlds frozen (good vs bad, `tsc --strict`):

```typescript
// good — as const narrows (checker), freeze enforces (runtime): the pair
const ROUTES = Object.freeze(["/a", "/b"] as const);
type Route = (typeof ROUTES)[number]; // "/a" | "/b" — derived set for exhaustiveness
function serve(r: Route): string { return r === "/a" ? "A" : "B"; }
console.log(serve("/a")); // A
// ROUTES.push("/c"); // error TS2339 — frozen at check time too

// bad — checker-only freeze mutates through interop
const loose: readonly string[] = ["x"];
(loose as string[]).push("MUTATED"); // compiles via cast — runtime array grew
console.log(loose.length); // 2 — the "frozen" list changed
// fix — Object.freeze at publication: casts can lie to tsc, not to the runtime
const hard = Object.freeze(["x"] as const);
// (hard as string[]).push("y"); // throws TypeError at runtime — enforcement, not promise
console.log(hard.length); // 1
```

**Common confusion** — "`Object.freeze` narrows the type" — returns `readonly T[]` (shallow) — narrowing *literals* still needs `as const` (`freeze(["a"])` gives `readonly string[]`, not `readonly ["a"]` — freeze after asserting, not instead). "frozen arrays are deeply immutable" — shallow: `freeze([{a: 1}])` still allows `arr[0].a = 2` — deep structures need recursive freezing (runtime) + `DeepReadonly` (types). "freeze hurts performance" — one-time O(n) at publication; reads unaffected — freezing hot paths costs nothing after startup.

**Performance note** — `Object.freeze` is a single O(n) publication cost; element access on frozen arrays optimizes identically in JITs (shapes stable). `as const` costs check-time literal instantiations (one per element — trivial for curated tables; avoid const-asserting 10k-row datasets — see 09/3.3's size guidance).

**Mentor note** — mutate a checker-only-frozen list through a cast live, then through `Object.freeze` (throw) — promise-vs-guarantee in two runs. Rule: publish with both, consume as `readonly`, and never accept "frozen" claims without naming which world enforces them.
