## 1.2. Readonly arrays and mutable vs frozen arrays

A readonly array is a view that allows reads and omits the array's ordinary write operations. It does not create a snapshot or freeze a value. Separate three questions: which operations this reference permits, which other references share the value, and whether runtime integrity has been enforced.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence under its filename. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`; run `node dist/FILE.js`. Activate negatives individually with the same flags and --noEmit in place of --outDir dist.

### 1) **Readonly restricts this array view**

ReadonlyArray<T> and readonly T[] express the same contract. Push, sort, splice and index replacement are unavailable through that view. Read operations such as map and slice remain available and can produce new mutable arrays. Use a readonly parameter when the implementation needs to read the collection; this communicates intent and catches ordinary writes through that parameter. The [primary ReadonlyArray guide](https://www.typescriptlang.org/docs/handbook/2/objects.html#the-readonlyarray-type) documents those operations and assignment direction.

Save as views.ts.

```typescript
function total(values: readonly number[]): number {
  // values.push(4); // TS2339
  // values[0] = 4; // TS2542
  return values.reduce((sum, value) => sum + value, 0);
}
const source = [1, 2];
const view: ReadonlyArray<number> = source;
console.log(total(view), Object.isFrozen(view));
source.push(3);
console.log(view.join(","));
const doubled = view.map(value => value * 2);
doubled.push(8);
console.log(doubled.join(","), view.length);
const rows: readonly { name: string }[] = [{ name: "Ada" }];
for (const row of rows) row.name = "Lin";
console.log(rows.map(row => row.name).join(","));
// rows.push({ name: "New" }); // TS2339
function observe(values: readonly number[], effect: () => void): number {
  effect();
  return values.length;
}
console.log(observe(view, () => source.push(4)), view.length);
```

The output is `3 false`, `1,2,3`, `2,4,6,8 3`, `Lin`, then `4 4`. Source and view share the array, and the callback can reach source independently of the readonly parameter. The mutable row object is also reachable through a readonly outer array. These are accepted operations without assertions; the signature does not prove global immutability or unchanged contents across arbitrary callbacks.

### 2) **Assignment direction and shallow copies**

A mutable array supplies the reads a readonly consumer needs. The reverse assignment fails because a readonly contract does not supply the required write methods. Copying with spread creates a new outer array when a local mutable collection is needed; its referenced element objects remain shared.

Do not confuse that assignment rule with a claim that TypeScript enforces invariance on all mutable arrays. It permits some unsafe widening between different element types. The [variance owner](<../../../02 The Type System Core/sections/3. Soundness and variance/3.1. Covariance contravariance and invariance who varies which way.md>) explains why reading and writing the same generic type require careful reasoning.

Save as sharing.ts.

```typescript
const tuple = ["x", "y"] as const;
function render(values: readonly string[]): string { return values.join(","); }
console.log(render(tuple), render(["a"]));
// const mutable: string[] = tuple; // TS4104
const copied = [...tuple];
copied.reverse();
console.log(copied.join(","), tuple.join(","), Object.is(copied, tuple));
const source = [{ name: "Ada" }];
const objectCopy = [...source];
for (const row of objectCopy) row.name = "Lin";
console.log(source.map(row => row.name).join(","), objectCopy === source);
interface Animal { name: string }
interface Cat extends Animal { meow(): string }
const cats: Cat[] = [{ name: "Mira", meow: () => "meow" }];
const animals: Animal[] = cats;
animals.push({ name: "Other" });
try {
  console.log(cats.map(cat => cat.meow()).join(","));
} catch (error) {
  console.log("mutable widening", error instanceof TypeError);
}
const readOnlyAnimals: readonly Animal[] = cats;
// readOnlyAnimals.push({ name: "Other" }); // TS2339
console.log(readOnlyAnimals.length);
```

The output is `x,y a`, `y,x x,y false`, `Lin false`, `mutable widening true`, then `2`. The outer copies have independent identity, while the object copy still refers to the same row. The mutable Animal[] alias admits an Animal without meow and corrupts the assumption behind the Cat[] read. A readonly Animal[] view blocks that push through itself; it does not repair an already corrupted source or revoke another mutable alias.

Choose copying when independent outer collection changes are required. Choose a projection or deeper copy policy when shared element objects would violate the intended snapshot. An annotation alone proves neither ownership nor exclusivity.

### 3) **Runtime freezing and literal inference are separate choices**

Object.freeze executes and returns the same object with its own properties protected. Its enforcement is shallow; element objects are separate values. As const instead affects inferred literal/readonly types and erases. Use the combination when both literal precision and actual outer-array integrity are requirements. Neither a universal pairing nor a special publication order is needed for every array API.

Save as integrity.ts.

```typescript
const literals = ["/a", "/b"] as const;
console.log(Object.isFrozen(literals));
const source = ["x"];
const frozen = Object.freeze(source);
console.log(frozen === source, Object.isFrozen(frozen));
try {
  source.push("y");
} catch (error) {
  console.log("frozen write", error instanceof TypeError);
}
console.log(source.join(","));
const nested = Object.freeze([{ name: "Ada" }]);
for (const row of nested) row.name = "Lin";
console.log(nested.map(row => row.name).join(","), Object.isFrozen(nested[0]));
const precise = Object.freeze(["/a", "/b"] as const);
const broad = Object.freeze(["/a", "/b"]);
// precise.push("/c"); // TS2339
// precise[0] = "/a"; // TS2540
// const admitted: typeof precise[number] = "/c"; // TS2322
console.log(precise.join(","), broad.join(","));

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type LiteralTuple = Expect<Equal<typeof literals, readonly ["/a", "/b"]>>;
type FrozenTuple = Expect<Equal<typeof precise, readonly ["/a", "/b"]>>;
type FrozenArray = Expect<Equal<typeof broad, readonly string[]>>;
```

The output is `false`, `true true`, `frozen write true`, `x`, `Lin false`, then `/a,/b /a,/b`; all three probes compile. Freezing source did not copy it or change the old variable's static type, but the actual old-alias push fails at runtime. The nested name remains writable. The [freeze documentation](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/freeze#freezing_arrays) explains runtime enforcement and shallow scope. A mapped DeepReadonly type also erases; it cannot recursively freeze values.

### 4) **Common confusion**

Readonly is neither const binding nor runtime freeze. A const binding prevents rebinding, a readonly array view rejects its own ordinary writes, and Object.freeze enforces restrictions on the actual outer object. Literal preservation is a fourth concern: it can help derive a finite union, but unnecessary narrow values can make intended updates awkward.

Readonly does not mean an independent snapshot. A source push changes its readonly view, a shallow copy shares object elements, and a frozen outer array still permits changes inside an unfrozen element. Name the exact boundary before describing data as immutable.

### 5) **Performance note**

Readonly modifiers and const assertions erase. Copying and mapping allocate new outer arrays and perform work over the values they process; freezing is another actual runtime operation. None of these operations is caused automatically by a readonly signature. No JIT equivalence, freeze timing, checker-speed benefit or threshold for large literal tables was measured. Choose the needed independence/integrity policy and measure it on the relevant workload when cost matters.

### 6) **Mentor note**

Ask the learner to draw which variables point to the same outer array and which element objects remain shared. Have them predict the source-alias push, the copied row edit and the frozen old-alias failure separately. An explanation that merely says readonly means safe misses the controlling reference and runtime operation.

For practice, implement snapshotNames(rows: readonly { name: string }[]): readonly string[]. Map the names into a fresh array, then freeze that array. Changing an original row's name afterward must leave the snapshot unchanged; Object.isFrozen(snapshot) must be true and Reflect.set(snapshot, "0", "changed") must return false. Mapping to strings deliberately removes shared row objects. Returning rows.map without freezing meets the static return type but fails the runtime-integrity criterion. No assertion is needed.
