## 5.1. Real production bugs caused by collection misunderstandings

### 1) **`as`-cast array push overflowed a fixed protocol frame** (tuple-typed frame built as `string[]`; 4th field shipped to hardware)

**Definition** — a hardware protocol frame typed `[kind: string, len: number]` was *built* as `string[]` ("easier pushes") with an `as Frame` cast at the end — the cast silenced arity checking, a 4th debug field slipped into one frame, and the device parsed the extra bytes as the next frame's header (cascading desync across the batch).

**What problem it solves / history** — builder-side convenience (`string[]` + pushes + terminal cast) vs tuple-side honesty (fixed slots, arity errors at the push) — the cast chose convenience and deleted the exact check (arity) the protocol needed. Building *as the tuple* (typed accumulator or tuple literal) keeps every push arity-checked; the cast kept none.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), build fixed-arity values as their tuple type from the first statement (`const frame: Frame = [kind, len]` — pushes beyond arity error immediately); ban `as` casts on collection construction (casts *conclude* checking; construction *needs* it). When arity varies during build, accumulate honestly (`(string|number)[]`) and validate into the tuple once (`assertFrame(parts)` predicate) — cast never.

**Runnable example** — arity checked at the push, not the cast (good vs bad, `tsc --strict`):

```typescript
// bad — string[] builder + terminal cast: arity unchecked until hardware complains
type Frame = [kind: string, len: number];
function buildBad(kind: string, len: number, debug?: string): Frame {
  const parts: (string | number)[] = [kind, len];
  if (debug) parts.push(debug); // compiles — arity invisible to string[]
  return parts as Frame; // cast silences the 3-element lie (2 slots promised)
}
console.log(buildBad("data", 4, "x").length); // 3 — overflow shipped inside a Frame type

// good — tuple-typed from the first statement: overflow errors at the push
function build(kind: string, len: number): Frame {
  const frame: Frame = [kind, len];
  // frame.push("x"); // error TS2345 — arity enforced where written
  return frame;
}
console.log(build("data", 4).length); // 2 — contract holds end to end
```

**Common confusion** — "the cast is safe because we checked" — the cast *replaced* checking (no assertion ran; `as` never validates) — checked means a predicate/guard ran, cast means trust without evidence. "builder ergonomics need loose types" — tuple-typed builders (`const f: Frame = [k, l]`) are equally ergonomic for fixed arity — looseness serves *varying* arity only. "hardware caught it, types are redundant" — hardware caught it after shipping; types catch it before committing — different cost centers by orders of magnitude.

**Performance note** — tuple-typed construction emits identical arrays (zero delta); the cast version cost a hardware desync + batch recall — arity checking is the highest-ROI check in protocol code, bar none.

**Mentor note** — grep `as Frame`-shaped terminal casts on builders quarterly — each is an arity check deleted for convenience. Exercise: rebuild one cast-constructed tuple as tuple-typed-from-first-statement and count the new arity errors (each a shipped-overflow candidate). Gate: `as` on collection construction fails review unconditionally.

### 2) **Mutated shared `sort` reordered a cached leaderboard** (in-place sort on a published array; every reader saw the mutation)

**Definition** — a `top(n)` helper `sort`ed the cached leaderboard array in place and sliced — every caller holding the cache reference saw their "insertion-ordered" list reorder behind their backs; a concurrently-rendered full table flickered between orders on each `top()` call. The signature (`top(board: Score[]): Score[]`) permitted mutation; the implementation performed it; no type recorded either fact.

**What problem it solves / history** — in-place derivation (`sort`/`reverse`/`splice` on shared inputs) is the aliasing incident behind 1.2/1.3's demos — this instance reached production because the helper *looked* pure (returned a new slice — of a mutated source). `readonly` parameters + copying methods (`toSorted`) make purity structural: the helper *cannot* alias-mutate regardless of what future edits add to its body.

**Modern guidance** — as of TypeScript 5.9 era, take shared inputs as `readonly`, derive with `toSorted`/`toSpliced`/`slice`, and return new arrays — purity by signature, not by discipline. When mutation is genuinely wanted (local sort of a local buffer), own the buffer (construct it in the function) so no alias exists to corrupt.

**Runnable example** — purity by signature (good vs bad, `tsc --strict`):

```typescript
// bad — in-place sort on shared cache: every reader's order corrupted per call
interface Score { name: string; pts: number; }
const cache: Score[] = [{ name: "a", pts: 1 }, { name: "b", pts: 9 }];
function topBad(n: number): Score[] {
  return cache.sort((x, y) => y.pts - x.pts).slice(0, n); // mutates cache, returns a slice of it
}
console.log(topBad(1)[0]?.name, cache[0]?.name); // b b — cache order destroyed (was a-first)

// good — readonly snapshot + toSorted: readers provably unaffected
const cache2: readonly Score[] = [{ name: "a", pts: 1 }, { name: "b", pts: 9 }];
function topN(n: number): Score[] {
  return cache2.toSorted((x, y) => y.pts - x.pts).slice(0, n); // derivation, not mutation
}
console.log(topN(1)[0]?.name, cache2[0]?.name); // b a — source order kept
// cache2.sort; // error TS2339 — sort absent on readonly (cannot regress to mutation)
```

**Common confusion** — "slice-after-sort copies safely" — `slice` copies the *mutated* order (too late — source already reordered); copy-then-sort (`slice().sort()`) or `toSorted` (sort-into-copy) — order of operations is the whole bug. "small caches don't matter" — aliasing corrupts regardless of size; small caches just corrupt *faster* (every reader sees every mutation). "freezing the cache fixes it" — `Object.freeze` throws on mutation (detection) but `readonly` + `toSorted` *prevents* the mutation path from compiling (prevention) — prefer prevention, add freezing for interop.

**Performance note** — `toSorted` allocates O(n) per call (the derivation price) — leaderboard-sized arrays trivial; hot-path sorts over huge buffers should sort a local mutable copy (owned, no alias) — same method choice, owned input.

**Mentor note** — log `cache[0]` before/after `topBad` — the corrupted order is the aliasing lesson no slide conveys. Lint: mutating methods (`.sort(`, `.splice(`, `.reverse(`) on parameters fail review unless the parameter is locally-owned-and-mutable by construction.

### 3) **`Record<string, Handler>` swallowed a missing route** (stringly table accepted absence; unauthenticated path shipped)

**Definition** — an auth-middleware table typed `Record<string, Handler>` (string keys, shared handler type) accepted a route registration missing its guard — absence compiled (any string key optional-absent), the path served unauthenticated for a release, and the post-mortem found the table *could not have* caught it: its type described "some strings map to handlers", not "these routes map to these guards."

**What problem it solves / history** — stringly tables trade all three finite-key guarantees (typo-rejection, absence-detection, literal preservation — see [3.2. Record vs Map](<../3. Collections and Selection/3.2. Record vs Map indexed access vs hashed keys.md>) promise 1) for construction convenience. `Record<RouteKey, Guard>` restores them: missing guards error TS2741, typo'd paths error TS2353, template-derived keys stay literal — the table becomes a proof of coverage, not a bag of handlers.

**Modern guidance** — as of TypeScript 5.9 era, type binding tables over finite unions (`Record<Route, Guard>`, derived via template literals from method+path factors); assert completeness at registration (exhaustive builder or `satisfies` + `keyof` check); consume through exhaustive switches so new routes demand guards. String-keyed tables survive only for genuinely open registries (plugins, user extensions) — with per-entry validation, not blind trust.

**Runnable example** — finite table proves coverage (good vs bad, `tsc --strict`):

```typescript
// good — finite table: missing guard errors at registration, not after shipping
type Route3 = "/a" | "/b";
type Guard = (token: string) => boolean;
const guards: Record<Route3, Guard> = {
  "/a": (t) => t.length > 0,
  "/b": () => true,
};
console.log(guards["/a"]("tok")); // true — every route has a guard, provably
// const missing: Record<Route3, Guard> = { "/a": (t) => t.length > 0 }; // error TS2741 — /b unguarded

// bad — stringly table: absence invisible, typos welcome
const looseGuards: Record<string, Guard> = { "/a": (t) => t.length > 0 }; // /b missing — compiles
// looseGuards["/b"]?.("tok"); // undefined at runtime — unauthenticated path served
// fix — Record<Route3, Guard>: coverage is a type error away, not an incident away
console.log(Object.keys(looseGuards).length); // 1 — one guard where two were required
```

**Common confusion** — "partial tables are sometimes intended" — then type `Partial<Record<Route, Guard>>` (absence *explicit* and handled per read) — `Record<string, …>` makes absence *implicit* everywhere. "guards validated at runtime anyway" — runtime validation without the table type still permits *forgotten* routes (nothing enumerates what to validate) — the finite type *is* the enumeration. "template-derived keys overcomplicate" — `` `GET ${Path}` `` derivation (see [09/3.2](<../../../09 Utility Types and Type Transformations/sections/3. Transformations in Practice/3.2. Template literal composition Capitalize handlers and routes.md>)) composes with `Record` — derivation *feeds* finite tables, not replaces them.

**Performance note** — finite tables check per key (O(routes), cached once) — hundreds of routes trivial; the incident cost (unauthenticated serving) dwarfs any check-time consideration by definition.

**Mentor note** — delete one guard from each table and compare errors (TS2741 vs silence) — coverage-proof vs coverage-theater in one deletion. Gate: `Record<string, Handler/Guard>` over knowable-finite route sets fails review; finite `Record` + exhaustive consumption is the required shape.

### 4) **`noUncheckedIndexedAccess` off — `users[0]` typed non-optional and crashed** (index access assumed present; empty page threw)

**Definition** — with `noUncheckedIndexedAccess` off (the default), `users[0]` types as `User` (not `User | undefined`) and `dict[key]` as `V` — every index read asserts presence the runtime never promised. An empty search page (`users = []`) rendered `users[0].name` — `TypeError: Cannot read properties of undefined` with a confident non-optional type, green CI, no `strict` violation (the flag that would have caught it was never enabled).

**What problem it solves / history** — index signatures and array indexing are the last `strict`-adjacent hole most codebases leave open: `strict: true` without `noUncheckedIndexedAccess` still lies on every `[i]`/`[key]` read. Enabling the flag (`T` → `T | undefined` on index reads) converts the entire class into narrow-or-error at every read — the single highest-yield flag flip in collection-heavy codebases, routinely surfacing dozens of latent crashes on first enable.

**Modern guidance** — as of TypeScript 5.9 era, enable `noUncheckedIndexedAccess` in every strict tsconfig (see [13 Configuration](<../../../13 Configuration and Compiler Options/README.md>) textual forward); narrow every indexed read (`?.`/`??`/early-return — the same discipline as `Map.get`); destructure tuples (positions, not indexes) where arity is known. Expect dozens of new errors on first enable — each a latent crash; fix with narrowing, never with `!` (mass `!`-adding re-lies at every site).

**Runnable example** — flag converts crashes to narrows (good vs bad, `tsc --strict`):

```typescript
// good — with the flag: users[0] is User | undefined, empty page handled
interface U { name: string; }
function firstName(users: U[]): string {
  return users[0]?.name ?? "anonymous"; // narrows the honest undefined
}
console.log(firstName([]), firstName([{ name: "ada" }])); // anonymous ada

// bad — without the flag: users[0] types User, empty page throws
function firstNameBad(users: U[]): string {
  // return users[0].name; // compiles under default flags — throws on [] at runtime
  return users.length > 0 ? (users[0] as U).name : "anonymous"; // manual length check + cast (the pre-flag pattern)
}
// fix — enable noUncheckedIndexedAccess: the ?. above becomes REQUIRED, not stylistic
console.log(firstNameBad([])); // anonymous — correct result via manual discipline the flag automates
```

**Common confusion** — "the flag breaks valid code" — it *reveals* unhandled absence in valid-looking code — breakage is diagnosis, and `?.`/`??` fixes are one line each. "`!` restores the old behavior cheaply" — `!` re-asserts presence per site (the exact lie, redistributed) — mass-`!` migrations preserve every crash while silencing the flag. "tuples are affected identically" — fixed positions (`tuple[0]` on `[A, B]`) stay non-optional (arity proves presence); only *open* indexing gains `undefined` — tuples dodge the flag by construction (another reason to prefer them for fixed shapes).

**Performance note** — zero emit/runtime delta (pure check-time `| undefined`) — the "cost" is narrowing branches per indexed read (one `?.` each — negligible) versus production `TypeError`s (unbounded). Highest-ROI flag in the collection space by post-mortem count.

**Mentor note** — enable the flag on a Friday afternoon and triage Monday (dozens of errors, each a crash that never happened yet) — the error list *is* the latent-incident backlog, prioritized for free. Rule: `!` on indexed reads fails review; narrowing is the only accepted fix.
