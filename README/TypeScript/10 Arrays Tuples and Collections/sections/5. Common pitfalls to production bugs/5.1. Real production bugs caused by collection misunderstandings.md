## 5.1. Real production bugs caused by collection misunderstandings

These local reproductions show failure patterns that matter in application code. They are not sourced accounts of a particular hardware outage, security release or CI failure. For each, identify the operation that permits the bad state, observe the consequence, then test the narrower repair and its limits.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence under its filename. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2023,dom --outDir dist FILE.ts`; run `node dist/FILE.js`. Activate commented negatives separately using those flags with --noEmit instead of --outDir dist. The ES2023 declarations expose copying methods that actually run on this Node version.

### 1) **A tuple contract does not block every mutable length change**

A mutable tuple can accept a pushed value from its element union. Merely replacing a loose array builder with a mutable tuple therefore does not make overflow impossible. For locally constructed fixed data, return a checked tuple literal through a readonly contract. For unknown input, actually check its shape and value requirements.

Save as frame.ts.

```typescript
type MutableFrame = [kind: string, length: number];
type Frame = readonly [kind: string, length: number];
const mutable: MutableFrame = ["data", 4];
mutable.push("debug");
console.log(mutable.length, mutable.join(","));
function build(kind: string, length: number): Frame { return [kind, length]; }
const built = build("data", 4);
console.log(built.length, Object.isFrozen(built));
// built.push("debug"); // TS2339
// const long: Frame = ["data", 4, "debug"]; // TS2322
function parseFrame(input: unknown): Frame {
  if (!Array.isArray(input) || input.length !== 2) throw new Error("invalid frame");
  const kind: unknown = input[0];
  const length: unknown = input[1];
  if (typeof kind !== "string" || typeof length !== "number" || !Number.isSafeInteger(length) || length < 0) {
    throw new Error("invalid frame");
  }
  return Object.freeze([kind, length] as const);
}
console.log(parseFrame(["data", 4]).join(","));
for (const input of [["data", 4, "debug"], new Array(2), ["data", -1], ["data", "4"]]) {
  try { parseFrame(input); } catch (error) { console.log(error instanceof Error ? error.message : "unexpected"); }
}
```

The output is `3 data,4,debug`, `2 false`, `data,4`, followed by four `invalid frame` lines. The readonly return is still unfrozen, while parseFrame deliberately freezes the fresh outer tuple after checking two readable values. Its policy rejects holes, extra fields, negative lengths and a string length. The parser does not establish any real wire encoding or device protocol behavior. A tuple assertion would not execute these checks; [tuple limits](<../2. Tuple Types/2.1. Fixed arity tuples labels and optional elements.md>) owns the static distinction.

### 2) **A new slice can still follow an in-place mutation**

Sort changes its receiver before slice creates the result. Another reference to the source therefore observes a reordered array even though the function returns a fresh slice. To preserve source order, use a copying sort or copy before sorting. A new outer array still shares its element objects unless those are separately projected.

Save as leaderboard.ts.

```typescript
interface Score { name: string; points: number }
const cache: Score[] = [{ name: "a", points: 1 }, { name: "b", points: 9 }];
function topBad(values: Score[]): Score[] { return values.sort((a, b) => b.points - a.points).slice(0, 1); }
console.log(topBad(cache).map(row => row.name).join(","), cache.map(row => row.name).join(","));
const source: Score[] = [{ name: "a", points: 1 }, { name: "b", points: 9 }];
function topScores(values: readonly Score[]): Score[] {
  // values.sort(); // TS2339
  return values.toSorted((a, b) => b.points - a.points).slice(0, 1);
}
const selected = topScores(source);
console.log(selected.map(row => row.name).join(","), source.map(row => row.name).join(","));
console.log(Object.is(selected[0], source[1]));
const independent = source.toSorted((a, b) => b.points - a.points).map(row => ({ ...row }));
for (const row of independent) row.points += 1;
console.log(independent.map(row => row.points).join(","), source.map(row => row.points).join(","));
```

The output is `b b,a`, `b a,b`, `true`, then `10,2 1,9`. The copying sort preserves the source's outer order. Object.is exposes the remaining shared row reference. The explicit row copies serve the separate requirement that edits to the derived rows should not change the source. A readonly signature catches ordinary writes through that view; it is not proof of global purity across other aliases or callbacks. [Readonly boundaries](<../1. Array Types/1.2. Readonly arrays and mutable vs frozen arrays.md>) covers those limits.

### 3) **Missing-handler policy differs from complete and correct guards**

An open registry can legitimately lack a key. Whether that absence permits or rejects an operation is application logic, not a behavior caused by Record<string, Guard>. A finite Record can require each named guard, but a supplied guard can still implement the wrong decision. This local example makes both distinctions observable; it is not an HTTP integration or an authentication system.

Save as guards.ts.

```typescript
type Route = "/a" | "/b";
type Guard = (token: string) => boolean;
const partial: Record<string, Guard> = { "/a": token => token.length > 0 };
function missingAllows(path: string, token: string): boolean {
  return partial[path]?.(token) ?? true;
}
function missingDenies(path: string, token: string): boolean {
  const guard = partial[path];
  return guard === undefined ? false : guard(token);
}
console.log(missingAllows("/b", ""), missingDenies("/b", ""));
const guards: Record<Route, Guard> = {
  "/a": token => token.length > 0,
  "/b": token => token === "staff",
};
console.log(guards["/a"](""), guards["/b"]("other"), guards["/b"]("staff"));
// const missing: Record<Route, Guard> = { "/a": token => token.length > 0 }; // TS2741
const wrongPolicy: Record<Route, Guard> = { "/a": () => true, "/b": () => true };
console.log(wrongPolicy["/b"](""));
// guards["/c"]("staff"); // TS7053
```

The output is `true false`, `false false true`, then `true`. The first helper explicitly chose true for a missing entry; the second chose false. The finite table requires both routes, while wrongPolicy still satisfies the exact same callable contract and admits an empty token. Test the decision rule as well as coverage. Actual external route/token parsing and application integration remain separate work. [Record versus Map](<../3. Collections and Selection/3.2. Record vs Map indexed access vs hashed keys.md>) owns finite coverage and open-entry semantics.

### 4) **An index flag does not add runtime checks or prove every read**

NoUncheckedIndexedAccess makes ordinary potentially missing array/index-signature reads include undefined. Required tuple slots and declared finite properties have different contracts. The [primary option reference](https://www.typescriptlang.org/tsconfig/noUncheckedIndexedAccess.html) shows that declared existing fields remain present. The option is separate from strict and does not change emitted JavaScript.

Save as first.ts.

```typescript
interface User { name: string }
function firstName(users: readonly User[]): string {
  const first = users[0];
  return first === undefined ? "anonymous" : first.name;
}
function assertedFirst(users: readonly User[]): string { return users[0]!.name; }
// function bareFirst(users: readonly User[]): string { return users[0].name; } // TS2532 with noUncheckedIndexedAccess
console.log(firstName([]), firstName([{ name: "Ada" }]));
try { assertedFirst([]); }
catch (error) { console.log("asserted missing read", error instanceof TypeError); }
const fixed: readonly [name: string] = ["Ada"];
const finite: Record<"ready", string> = { ready: "yes" };
console.log(fixed[0].toUpperCase(), finite["ready"].toUpperCase());

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type FixedRead = Expect<Equal<typeof fixed[0], string>>;
type FiniteRead = Expect<Equal<typeof finite["ready"], string>>;
```

The output is `anonymous Ada`, `asserted missing read true`, then `ADA YES`; both probes compile. The assertion silences absence checking and leaves an actual crashing read. Activating bareFirst is rejected with the option enabled; without it, the same body compiles and an empty call throws. The flag does not require exactly ?. or ?? as a fix: checking the extracted value is equally valid. A new diagnostic signals an obligation to investigate, not proof of one known production crash per error.

### 5) **Common confusion**

A fixed tuple annotation does not close every mutable array-method hole, and a readonly return does not freeze its value. A fresh outer collection does not imply independent objects inside it. Name the guarantee the particular construction or copy actually establishes.

Handler presence is distinct from handler behavior. A finite table can contain a function that always returns true, and an open table can safely handle missing entries according to its chosen policy. Index flags expose absence concerns but cannot validate runtime input, prevent every assertion or correct the decision logic.

### 6) **Performance note**

Annotations and index-option changes erase. Parsing, checks, sorting, copying and callbacks still execute. Preserving source order and independent row edits here requires actual copies chosen for those requirements. No hardware recall cost, production frequency, universal compiler saving, JIT result or “highest yield” ranking was measured. Judge the failure policy first, then measure relevant runtime work if it affects the design.

### 7) **Mentor note**

Ask the learner to locate the line that introduces each failure: push, sort, missing-entry fallback or an asserted read. Then ask what the repaired variant still does not promise. A sound answer can say that copying sort preserves outer order while sharing row objects, or that finite guard coverage leaves the guard's decision unproved.

For practice, add /c to Route in guards.ts. Both finite tables must first fail for the missing property; the open partial registry remains valid. Add /c: token => token === editor to the complete guards table and choose an explicit policy for wrongPolicy too. Update the old /c negative because that call is now admitted. Verify the complete table rejects an empty token, rejects staff and accepts editor for /c. Adding () => true has the right function type but fails those decisions. Record the observed results rather than describing this local test as a deployed route check.
