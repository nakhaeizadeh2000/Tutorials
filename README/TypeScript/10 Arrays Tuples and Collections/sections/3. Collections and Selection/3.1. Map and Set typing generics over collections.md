## 3.1. Map and Set typing — generics over collections

A Map relates each key to a value; a Set tracks membership of values. Their generic arguments constrain writes and describe reads, while runtime equality, absence and conversion rules determine what the collections actually contain. Start with a deliberate element contract, then account for missing entries and representation changes.

Examples use TypeScript 7.0.2 and Node 20.20.2, verified 2026-10-13. Save the first four named files in a new directory without tsconfig.json. Run `tsc --strict --target es2022 --module commonjs --lib es2022,esnext.collection,dom --outDir out FILE.ts`. For maps, sets and entries, run `node out/FILE.js`. The upsert program needs the separate polyfill setup in part 4. The two iterator-helper files in part 5 use their separately stated library and Node 22 runtime commands. For a rejection, uncomment only the indicated line and use the same compiler flags with `--noEmit` instead of `--outDir out`.

### 1) **Map contracts, inference and absent reads**

Map<string, Account> checks both arguments of set and gives get the result Account | undefined. Store the result and narrow that value before reading balance. A has call answers a membership question; its boolean signature does not narrow the result of a separate get call.

Save `maps.ts`:

```typescript
export {};
interface Account { id: string; balance: number }
const ledger = new Map<string, Account>();
ledger.set("a1", { id: "a1", balance: 100 });
function balanceOf(id: string): string {
  const account = ledger.get(id);
  return account === undefined ? "missing" : account.balance.toFixed(2);
}
console.log("balances:", balanceOf("a1"), balanceOf("absent"));
// ledger.set(42, { id: "x", balance: 1 }); // TS2345: key contract.
// ledger.set("bad", { id: "x", balance: "one" }); // TS2322: value contract.
if (ledger.has("a1")) {
  const separateRead = ledger.get("a1");
  // console.log(separateRead.balance); // TS18048: has did not narrow get.
  console.log("membership read:", separateRead?.balance);
}
const inferred = new Map([["apple", 2], ["pear", 3]]);
console.log("entry-inferred:", inferred.get("apple"));
const unchecked = new Map();
unchecked.set(1, "two"); unchecked.set("other", 3);
type IsAny<T> = 0 extends (1 & T) ? true : false;
type Expect<T extends true> = T;
const uncheckedRead = unchecked.get(1);
type BareRead = Expect<IsAny<typeof uncheckedRead>>;
console.log("bare value:", uncheckedRead);
```

The output is `balances: 100.00 missing`, `membership read: 100`, `entry-inferred: 2` and `bare value: two`. Activate the wrong key, wrong value or unguarded separateRead individually to observe TS2345, TS2322 or TS18048.

Entries can supply construction-time inference, so explicit type arguments are useful without being mandatory for every seeded map. Bare new Map(), however, uses the no-argument Map<any, any> overload in this compiler. The live IsAny assertion confirms its unchecked read. It does not acquire a precise contract from the first set call. The compiler's installed lib.es2015.collection.d.ts is the primary signature source for these distinctions.

An open object dictionary also needs honest absence handling, usually through a guarded read and the [index-access option](<../../../13 Configuration and Compiler Options/sections/3. Modules Emit and Projects/3.3. noUncheckedIndexedAccess and exactOptionalPropertyTypes.md>). The [Record-versus-Map owner](<./3.2. Record vs Map indexed access vs hashed keys.md>) compares representations. Neither container parses malformed external values; [runtime validation](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>) establishes their element contracts.

### 2) **Set membership, equality and typed iteration**

Set<string> rejects non-string writes. Spreading a set creates an array of its elements; it does not change the set's membership responsibilities. Equality remains a runtime property, including object identity and the treatment of NaN and signed zero.

Save `sets.ts`:

```typescript
export {};
const seen = new Set<string>();
function visit(id: string): string {
  if (seen.has(id)) return "repeat";
  seen.add(id);
  return "first";
}
console.log("visits:", visit("a"), visit("a"), seen.size);
// seen.add(1); // TS2345: element contract.
const ids = ["a", "b", "a", "c"];
const unique: string[] = [...new Set(ids)];
console.log("unique:", unique.join(","));
const one = { id: 1 };
const objects = new Set([one, one, { id: 1 }]);
console.log("object identities:", objects.size);
const numbers = new Set([NaN, NaN, 0, -0]);
console.log("number equality:", numbers.size);
```

The output is `visits: first repeat 1`, `unique: a,b,c`, `object identities: 2` and `number equality: 2`. Uncomment seen.add(1) to observe TS2345. Reusing one object reference deduplicates it; a new object with the same id remains distinct. The numbers collapse repeated NaN and the two signed zeros. The [collection specification](https://tc39.es/ecma262/multipage/keyed-collections.html) defines those runtime key/equality operations.

A generic element type does not count distinct elements or validate a business identity. If objects should deduplicate by their id field, choose an explicit key policy, often a Map keyed by that field. Retain arrays when duplicate values are meaningful, and distinguish membership from a separately published [readonly array view](<../1. Array Types/1.2. Readonly arrays and mutable vs frozen arrays.md>).

### 3) **Entries, snapshots and object/JSON conversion**

Map construction consumes key/value pairs. A readonly tuple entry contract lets the checker reject a mistyped seed. Materializing entries into an array takes a snapshot of the entries rather than a live subscription to later map writes. If values are objects, copying entries alone does not deep-clone those objects.

Save `entries.ts`:

```typescript
export {};
const seed: readonly (readonly [string, number])[] = [["apple", 2], ["pear", 3]];
const prices = new Map<string, number>(seed);
// const invalid = new Map<string, number>([["apple", "two"]]); // TS2769.
const snapshot: [string, number][] = [...prices.entries()];
prices.set("apple", 4);
console.log("snapshot versus map:", snapshot[0]?.[1], prices.get("apple"));

const token = Symbol("token");
const mixed = new Map<PropertyKey, number>([[1, 10], ["1", 11], [token, 20]]);
const object = Object.fromEntries(mixed);
console.log("converted:", mixed.size, object["1"], Reflect.get(object, token));
console.log("own symbol:", Object.hasOwn(object, token), Reflect.ownKeys(object).length);
console.log("json:", JSON.stringify(object));
```

The output is `snapshot versus map: 2 4`, `converted: 3 11 20`, `own symbol: true 2` and `json: {"1":11}`. Uncomment invalid to observe TS2769 for a string supplied as the numeric value.

The Map distinguishes numeric 1 and string "1". Object conversion maps both to the same string property, so the later entry wins here. It preserves the symbol property; JSON serialization subsequently omits it. The [Object.fromEntries algorithm](https://tc39.es/ecma262/multipage/fundamental-objects.html#sec-object.fromentries) uses property-key conversion. Reflect.get observes the symbol value because this library's inferred fromEntries result does not expose that exact symbol index directly. A static index declaration and runtime key preservation are separate questions.

Choose a deliberate conversion policy at a [JSON boundary](<../../../../JavaScript/16 JSON Serialization and Data Exchange/README.md>): reject or encode unsupported key kinds, and account for collisions. Do not assert that a conversion retains every Map key identity. [Tuple contracts](<../2. Tuple Types/2.1. Fixed arity tuples labels and optional elements.md>) own the pair-shape mechanics.

### 4) **Worked get-or-insert methods and support conditions**

getOrInsert receives a value. JavaScript evaluates a supplied fresh() call before entering the method, even on a hit. getOrInsertComputed receives a callback and calls it for a missing key, supplying that key. Both return an existing entry without replacing it, including an existing undefined value.

The [current TC39 upsert repository](https://github.com/tc39/proposal-upsert) reports Stage 4 as checked 2026-10-13. TypeScript 6.0 introduced the esnext collection declarations, described in its [release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html). The compiler's lib setting supplies types rather than implementations. These methods were absent natively on tested Node 20.20.2 and 22.18.0; the following actual run uses core-js 3.45.1.

In the example directory, run `npm install --ignore-scripts --save-exact core-js@3.45.1`. Save `upsert.ts`, compile it with the flags above, then run `node --require core-js/actual/map/get-or-insert --require core-js/actual/map/get-or-insert-computed out/upsert.js`. Both preloads occur before the program uses Map.prototype. This setup was installed and executed in a scratch project, separate from the tutorial repository.

```typescript
export {};
const counts = new Map<string, number>();
let eagerCalls = 0;
function fresh(): number { eagerCalls++; return 7; }
console.log("eager values:", counts.getOrInsert("eager", fresh()), counts.getOrInsert("eager", fresh()), eagerCalls);
let lazyCalls = 0;
function compute(key: string): number { lazyCalls++; return key.length; }
console.log("lazy values:", counts.getOrInsertComputed("lazy", compute), counts.getOrInsertComputed("lazy", compute), lazyCalls);
// counts.getOrInsert("wrong", compute); // TS2345: a value is required.
// counts.getOrInsertComputed("wrong", 7); // TS2345: a callback is required.

const optional = new Map<string, number | undefined>([["present", undefined]]);
let optionalCalls = 0;
const stored = optional.getOrInsertComputed("present", () => { optionalCalls++; return 9; });
console.log("stored undefined:", optional.has("present"), stored, optionalCalls);
try {
  counts.getOrInsertComputed("failure", () => { throw new Error("factory failed"); });
} catch (error) {
  console.log("factory failure:", error instanceof Error, counts.has("failure"));
}
```

The output is `eager values: 7 7 2`, `lazy values: 4 4 1`, `stored undefined: true undefined 0` and `factory failure: true false`. Both eager argument expressions run, while the computed miss runs once. The existing undefined entry counts as present, so its callback never runs. The throwing callback propagates its error without inserting that missing entry in this case.

Activate either wrong-method argument separately to observe TS2345. Run the compiled file on the tested Node 20 without the preloads to observe TypeError: getOrInsert is not a function. That failure diagnoses runtime support, despite a passing type check. Inspect your deployment runtime's actual support rather than infer it from a lib label or Stage 4 status. A compatible implementation or an ordinary has/get/set helper is a bounded fallback; these APIs do not supply general asynchronous locking.

As an exercise, change fresh to build an expensive value and predict the two hit/miss call counts before running it. Then replace the stored undefined entry with an absent key. The computed callback now runs and supplies 9. That change is about key presence, rather than whether get returned a truthy value.

### 5) **Typed iterator helpers over collections**

The iterator returned by Map.values can filter, map and take values before materializing an array. Those transformations are lazy: creating the pipeline does not yet visit the values. A terminal operation such as toArray drives consumption. The synchronous helper APIs are standardized; their [TC39 repository](https://github.com/tc39/proposal-iterator-helpers) records Stage 4 and explains that async helpers are a separate proposal. Do not assume an async iterator has these synchronous methods.

TypeScript's general Iterator interface describes the next protocol. IteratorObject describes iterator objects carrying the built-in helper surface when the appropriate declarations are included; collection iterators use specific subtypes such as MapIterator. A hand-written object can implement next without inheriting the runtime helpers. Iterator.from adapts such an iterator or an iterable to the helper surface. The [5.6 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-6.html#iterator-helper-methods) explain the typing distinction and stricter built-in completion checks.

For this section, save `helpers.ts` and `limits.ts` below. Use TypeScript 7.0.2 with `tsc --strict --erasableSyntaxOnly --target es2022 --module commonjs --lib es2025,dom --outDir out FILE.ts`. This compiler's es2025 library includes es2025.iterator. Run the emitted file with `npm exec --yes --package=node@22.18.0 -- node out/FILE.js`. Both files also ran directly as source on that Node version. The same helper program fails on tested Node 20.20.2 without an implementation: helper methods are absent despite the accepted declarations. No polyfill is needed for the tested Node 22 runs.

```typescript
export {};
const data = new Map<string, number | undefined>([["a", 2], ["b", undefined], ["c", 4], ["d", 6]]);
const values: MapIterator<number | undefined> = data.values();
let visited = 0;
let mapped = 0;
const selected = values
  .filter((value): value is number => { visited++; return value !== undefined; })
  .map(value => { mapped++; return value * 10; })
  .take(2);
console.log("before:", visited, mapped); // before: 0 0
const result = selected.toArray();
console.log("result:", result.join(","), visited, mapped); // result: 20,40 3 2
console.log("reuse:", selected.toArray().length); // reuse: 0: consumed helper

type Equal<X, Y> = (<T>() => T extends X ? 1 : 2) extends
  (<T>() => T extends Y ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type MappedResult = Expect<Equal<typeof result, number[]>>;
const empty = new Map<string, number>().values().next();
type EmptyValue = Expect<Equal<typeof empty.value, number | undefined>>;
// empty.value.toFixed(); // TS18048: built-in iterator can be done
console.log("completed:", empty.done, empty.value); // completed: true undefined
const first = data.values().next();
if (!first.done && first.value !== undefined) console.log("first:", first.value.toFixed(1)); // first: 2.0

let cursor = 0;
const raw: Iterator<number, undefined, undefined> = {
  next() {
    return cursor < 2 ? { done: false, value: ++cursor } : { done: true, value: undefined };
  },
};
// raw.map(value => value * 2); // TS2339: general next protocol has no map method
const adapted = Iterator.from(raw).map(value => value.toFixed(1)).toArray();
type AdaptedResult = Expect<Equal<typeof adapted, string[]>>;
console.log("adapted:", adapted.join(",")); // adapted: 1.0,2.0
console.log("set:", Iterator.from(new Set(["b", "a", "b"])).toArray().join(",")); // set: b,a
```

The predicate excludes undefined, so map receives number and the result becomes number[]. Three source values were visited to produce two retained outputs. Calling toArray again does not restart the consumed helper. Request a fresh values iterator when you need a new pass. The raw adapter example preserves the numeric yield contract and maps it to strings; a protocol annotation alone would not install the methods on raw.

Under strictBuiltinIteratorReturn, which strict enables, a built-in iterator's completion value can be undefined. Check done before reading a yielded value; if the element contract itself contains undefined, check that separately too. This is independent of Map.get's absent-entry union. Uncomment either negative access to see the diagnostic. The library permits the helper calls only when its declarations are selected; it does not supply the runtime implementation.

Save `limits.ts`:

```typescript
export {};
let produced = 0;
let closed = 0;
function* source(): Generator<number, void, void> {
  try {
    for (let value = 0; value < 5; value++) { produced++; yield value; }
  } finally { closed++; }
}
const noMatches = source().filter(value => value > 99).take(1).toArray();
console.log("output limit:", noMatches.length, produced, closed); // output limit: 0 5 1
produced = 0;
closed = 0;
const inputLimited = source().take(3).filter(value => value > 99).toArray();
console.log("input limit:", inputLimited.length, produced, closed); // input limit: 0 3 1
```

A take after filter limits matching outputs, so the first pipeline examines all five finite inputs when no match exists. With an unbounded source that never matches, that ordering could keep pulling forever. Placing take before filter bounds the number of inputs pulled instead. It may therefore return fewer matching results. Select the limit's position from the requirement: cap work on the source, or seek a target number of matches. The finally outputs also show cleanup on finite completion and on the bounded generator's early closure in this fixture.

This section demonstrates selected helper operations rather than an exhaustive catalog. Use arrays when repeated traversal, indexing or a materialized snapshot is the intended contract; use an iterator pipeline when consuming a sequence once suits the operation. toArray still materializes the result, and lazy processing does not imply universally faster execution or bounded memory in an arbitrary source. It changes when and how much of this source is consumed. Plain for-of remains a fallback on runtimes without helpers when the required transformation can be written as a loop.

### 6) **Common confusion**

A has boolean is not a checker assertion connecting every later get to the same key. Bare Map construction is unchecked here, whereas explicit arguments or entries can establish a useful contract. Object.fromEntries preserves symbol properties that JSON may omit. Finally, a factory passed to getOrInsert is itself a value; only the computed method invokes a factory for an absent entry. A next protocol and an iterable contract do not by themselves install helper methods. A consumed helper is not a replayable collection, and a limit on matching outputs is different from a limit on input visits.

### 7) **Performance note**

The specification requires average sublinear access for Map and Set; it does not promise a particular hash-table implementation or universal constant-time ranking against objects. Entry materialization and array spread copy collection contents. Eager fresh() work occurs on hits as well as misses, while the observed computed example avoids that factory work on hits. These call counts are evidence about execution, not a measured latency improvement. The helper fixture likewise observes skipped mapper work and early input closure; toArray allocates its result and the original Map remains in memory. No lazy-versus-array timing or memory benchmark was run. No container-speed benchmark, size threshold or checker-speed comparison was run; measure the actual workload before changing representation for performance.

### 8) **Mentor note**

Ask which writes the ledger checks, what its missing read returns and why the separate get remains optional after has. Then predict the helper visit counts and move take across filter. A sound review explains which limit bounds source work before recommending that ordering.
