## 3.1. `Map` and `Set` typing — generics over collections

### 1) **`Map<K, V>` per-key precision** (has/get/set threaded through key and value types)

**Definition** — `new Map<string, User>()` fixes key type `K` and value type `V` per instance: `set` requires `(K, V)`, `get` returns `V | undefined` (honest absence — the key may be missing), `has` narrows (with assertion-style guards in recent libs). Unlike index signatures (which return `V` and lie about missing keys), `Map` types absence into every read.

**What problem it solves / history** — dictionary objects (`{ [k: string]: User }`) typed `users[id]` as `User` even for absent ids — `undefined` at runtime with a confident type (the 5.1 `noUncheckedIndexedAccess` incident class). `Map`'s `get: (k: K) => V | undefined` makes absence unignorable: every read narrows (`?? default`, early return) or errors — the container, not the flag, enforces honesty.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), default dynamic-keyed state to `Map` (caches, registries, memo tables); keep `Record` for fixed key sets (see [3.2. Record vs Map](<./3.2. Record vs Map indexed access vs hashed keys.md>)). Always annotate construction (`new Map<string, User>()` — bare `new Map()` infers `Map<unknown, unknown>` and poisons every method). Narrow every `get` — `??`, `if`, or throw — never `!`.

**Runnable example** — absence typed into every read (good vs bad, `tsc --strict`):

```typescript
// good — annotated Map: keys and values checked, absence narrowed per read
interface Acct { id: string; balance: number; }
const ledger = new Map<string, Acct>();
ledger.set("a1", { id: "a1", balance: 100 });
// ledger.set(42, { id: "x", balance: 1 }); // error TS2345 — K is string, not number
const found = ledger.get("a1")?.balance.toFixed(2) ?? "missing";
console.log(found); // 100.00 — ?. narrows the V | undefined honestly

// good — has-then-get narrows without a second lookup type-hole
function balanceOf(known: Map<string, Acct>, id: string): string {
  if (!known.has(id)) return "unknown account";
  return (known.get(id)?.balance ?? 0).toFixed(2); // get re-narrowed after has
}
console.log(balanceOf(ledger, "a1"), balanceOf(ledger, "zz")); // 100.00 unknown account

// bad — dictionary object lies about missing keys
const dict: Record<string, Acct> = {};
const d = dict["ghost"]; // Acct — confident type, undefined value (without noUncheckedIndexedAccess)
// console.log(d.balance.toFixed(2)); // TypeError at runtime — the lie compiled
// fix — Map.get's V | undefined: absence in the type, handled at every read
console.log("dict-shape-kept-for-fixed-keys-only");
```

**Common confusion** — "`has` narrows `get` automatically" — control-flow does *not* link `has(k)` to `get(k)` (separate calls — the checker can't prove same-key stability across arbitrary code) — re-narrow `get` explicitly (`?.`/`??`) even after `has`. "`new Map()` infers from first `set`" — construction-time inference only (`new Map([["a", 1]])` works from entries); bare `new Map()` is `Map<unknown, unknown>` permanently — annotate at construction. "Map iteration is untyped" — `for (const [k, v] of map)` destructures `[K, V]` tuples natively (see [2.1. Fixed arity tuples](<../2. Tuple Types/2.1. Fixed arity tuples labels and optional elements.md>)).

**Performance note** — `Map` hashing costs O(1) amortized per op with higher constants than object property access (shape-optimized) — faster for frequent add/delete churn (no shape transitions), marginally slower for tiny fixed dictionaries. Choose by mutation pattern (see 3.2), not microbenchmarks; type cost identical either way.

**Mentor note** — hover `ledger.get("x")` (`Acct | undefined`) vs `dict["ghost"]` (`Acct`) — honesty-vs-lie in two tooltips is the whole `Map` pitch. Exercise: convert one `Record<string, T>` cache to `Map` and fix each resulting `| undefined` — the fix sites *are* the unhandled-absence bugs. Review gate: `!` after `.get(` must justify why absence is impossible.

### 2) **`Set<T>` membership typing** (one element type, iteration yields `T`)

**Definition** — `new Set<string>()` holds unique `T` values: `add` requires `T`, `has` tests membership, iteration/`forEach` yields `T` (never `undefined` — membership was proven by iteration itself). Deduplication is reference/value-equality at runtime (`SameValueZero`); the type tracks element kind, not uniqueness proof.

**What problem it solves / history** — dedup-by-array (`[...new Set(xs)]` untyped, or manual `includes` checks O(n) per element with `any[]` accumulators) scattered uniqueness logic that types never verified — duplicates re-entered through untyped pushes. `Set<T>` centralizes membership: construction dedupes, `has` gates, iteration yields proven members — the uniqueness invariant lives in the container, checked at every method.

**Modern guidance** — as of TypeScript 5.9 era, use `Set` for visited/seen registries, tag collections, and dedup passes (`[...new Set(ids)]` typed `T[]` out); keep arrays for ordered duplicates-allowed data (leaderboards, logs). Annotate construction (`new Set<string>()`); spread back to arrays for indexed/mapped consumption (`[...set].map(...)`).

**Runnable example** — membership centralized (good vs bad, `tsc --strict`):

```typescript
// good — seen-registry: membership proven by the container
const seen = new Set<string>();
function visit(id: string): string {
  if (seen.has(id)) return "repeat";
  seen.add(id);
  return "first";
}
console.log(visit("a"), visit("a"), seen.size); // first repeat 1 — dedup by construction

// good — dedup pass stays typed end to end
const ids = ["a", "b", "a", "c"];
const unique: string[] = [...new Set(ids)]; // spread Set → array, T preserved
console.log(unique.join(",")); // a,b,c — order of first appearance, typed string[]

// bad — manual includes-dedup on any[] accumulators
const acc: any[] = [];
for (const id of ids) if (!acc.includes(id)) acc.push(id); // O(n²), untyped throughout
// fix — Set<string>: O(1) membership + typed iteration + spread back to T[]
console.log(acc.length); // 3 — correct result, unverified types
```

**Common confusion** — "`Set` proves uniqueness statically" — types track *element kind* (`T`), not *cardinality* — `Set<string>` may still hold one element twice across time (add same twice = one entry — runtime dedupes, types don't count). "object elements dedupe by shape" — `Set` uses reference equality for objects (two `{id:1}` literals are distinct members) — dedupe objects by key (`Map<id, Obj>`) instead. "spread loses the set" — `[...set]` is a *new array* for indexed consumption; the set retains membership duties — convert at consumption boundaries, not before.

**Performance note** — `Set.has` O(1) vs `includes` O(n) — the asymptotic win is real for registries past hundreds of members; spread-to-array costs O(n) once per consumption — dedupe-then-spread beats includes-loops whenever membership tests repeat.

**Mentor note** — benchmark `includes`-loop vs `Set` on 10k ids live (seconds vs milliseconds) — the container choice becomes visceral, not theoretical. Exercise: convert one `any[]`-accumulator dedup to `Set<T>` + spread and delete the `any` — typed *and* faster in one diff.

### 3) **Constructing from entries** (tuple-typed entries bridge arrays into maps)

**Definition** — `new Map<string, number>([["a", 1], ["b", 2]])` constructs from `[K, V]` tuple entries; `Object.fromEntries(tupleArray)` converts back to a `Record`. Entries are the interchange format: arrays of pairs flow into `Map`s (construction), out of `Map`s (`[...map.entries()]`, `Object.entries(obj)`), and through tuple utilities (`Head`, mapped filters) — typed end to end when entries are tuples, flattened when plain arrays.

**What problem it solves / history** — bootstrap data (seed users, config pairs, test fixtures) lived as object literals (untyped keys) or `any[][]` pairs that `new Map()` accepted without checking — mistyped entries (`["a", "not-a-number"]` into `Map<string, number>`) compiled and poisoned every later `get`. Tuple-typed entries check each pair at construction: keys against `K`, values against `V`, arity per entry — seed data verified like any other code.

**Modern guidance** — as of TypeScript 5.9 era, seed maps from `as const` or explicitly-typed tuple arrays (`[["a", 1]] as [string, number][]` or `satisfies`); convert maps to objects via `Object.fromEntries` only at JSON boundaries (key type must extend `string` — numeric/symbol keys need explicit mapping). Prefer `Map` construction from entries over imperative `set` loops for static seeds (one checked literal vs N unchecked statements).

**Runnable example** — seeds checked per pair (good vs bad, `tsc --strict`):

```typescript
// good — tuple entries: each pair checked against K and V at construction
const prices = new Map<string, number>([["apple", 2], ["pear", 3]]);
console.log(prices.get("apple")?.toFixed(2) ?? "missing"); // 2.00
// new Map<string, number>([["apple", "two"]]); // error TS2345 — value mistyped per entry

// good — entries bridge: map → tuples → object at the JSON boundary
const pairs: [string, number][] = [...prices.entries()]; // [K, V][] — tuple-typed
const obj: Record<string, number> = Object.fromEntries(pairs); // back to object for JSON
console.log(obj.apple?.toFixed(0) ?? "missing", JSON.stringify(obj).length > 2); // 2 true

// bad — any[][] seeds poison every later get
const loosePairs: any[][] = [["apple", "two"]]; // compiles — value mistyped, unchecked
const looseMap = new Map<string, number>(loosePairs as [string, number][]); // cast launders it
console.log(looseMap.get("apple")); // "two" at runtime, number in types — the laundering
// fix — tuple-typed entries: no cast, each pair checked where written
```

**Common confusion** — "`Object.entries` returns tuples" — returns `[string, T][]` (keys widened to `string` — a *known* precision loss; `as const` sources + `Object.entries` still widen keys — re-narrow via the source union when exact keys matter). "`fromEntries` inverts exactly" — inverts *string-keyed* maps to `Record<string, V>`; numeric keys stringify, symbol keys drop — lossy at non-string keys by JSON semantics. "entries arrays are maps" — arrays snapshot (stale after map mutation); entries *transfer*, references *track* — construct from entries, subscribe via the map.

**Performance note** — construction from N entries is O(N) inserts (same as N `set` calls, one statement); `[...map.entries()]` snapshots O(N) — iterate the map directly in hot paths instead of snapshotting per loop.

**Mentor note** — mistype one seed value and read the per-entry TS2345 — "seed data is code" lands when the checker audits fixtures. Exercise: convert one `set`-loop bootstrap to an entries literal and count the statements deleted — construction beats accumulation for static data.
