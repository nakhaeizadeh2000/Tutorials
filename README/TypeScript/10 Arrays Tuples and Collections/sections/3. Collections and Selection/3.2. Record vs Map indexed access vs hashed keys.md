## 3.2. `Record` vs `Map` — indexed access vs hashed keys

### 1) **`Record<K, V>` for fixed key sets** (known keys, literal syntax, JSON-serializable)

**Definition** — `Record<"a" | "b", Handler>` is a *fresh* mapped object type: exactly the listed keys, each with value type `V`, constructible as an object literal, serializable via `JSON.stringify` with no conversion. [04/1.2](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) introduced the shape; [09/1.1](<../../../09 Utility Types and Type Transformations/sections/1. Mapped Types/1.1. Mapped type fundamentals homomorphic mapping over keys.md>) proved the mechanic — this leaf owns the *selection*: when `Record` (not `Map`, not index signatures) is the honest container.

**What problem it solves / history** — `Record<string, Handler>` for *fixed* handler sets (three known events) accepted typos (`onClik`), tolerated absence (missing `onKeydown` compiled), and widened template-derived keys back to `string` (see [09/3.3](<../../../09 Utility Types and Type Transformations/sections/3. Transformations in Practice/3.3. satisfies and as const preserving literals through transforms.md>) promise 3's route collapse) — every fixed-set benefit surrendered to one over-broad key type. `Record<Union, V>` restores all three: typos error, absence errors, derived keys stay literal.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), reach for `Record` when keys are a known finite set (config sections, handler tables, locale bundles): `Record<Event, Handler>` with the union curated, literals constructed as object literals, absence caught by TS2741. Never `Record<string, …>` where a finite union exists — the `string` key is the typo-and-absence hole.

**Runnable example** — finite keys enforced (good vs bad, `tsc --strict`):

```typescript
// good — finite key set: typos error, absence errors, literals preserved
type Ev3 = "click" | "keydown";
type Handlers3 = Record<Ev3, (at: number) => void>;
const h3: Handlers3 = { click: (at) => console.log(at), keydown: (at) => console.log(at) };
h3.click(5); // 5 logged
// const missing: Handlers3 = { click: (at) => console.log(at) }; // error TS2741 — keydown missing
// const typo: Handlers3 = { click: (at) => console.log(at), keydown: (at) => console.log(at), clik: (at) => console.log(at) }; // error TS2353 — excess key caught

// bad — string-keyed Record surrenders all three guarantees
const loose3: Record<string, (at: number) => void> = { clik: (at) => console.log(at) }; // typo compiles, keydown absence invisible
// fix — Record<Ev3, …>: the key union (not string) is the contract
console.log(Object.keys(h3).length); // 2 — exactly the curated set
```

**Common confusion** — "`Record` with a union iterates like mapped types" — `Record<K, V>` *is* `{ [P in K]: V }` (non-homomorphic fresh shape — no modifier memory, explicit modifiers rule). "`Record<string, V>` validates JSON" — it types the *shape* (string keys, V values) — malformed JSON still parses into it via `as`; validate with schemas, then annotate `Record`. "finite Records can't grow" — extend the *union* (`Ev3 | "scroll"`), never widen to `string` — growth stays curated and checked.

**Performance note** — `Record<Union, V>` instantiates per key (O(keys), cached once) — curated sets trivial; `Record<string, V>` is one instantiation (cheapest, least checking) — the cost/precision trade is explicit: pay per-key checks for typo/absence proofs.

**Mentor note** — delete one key from `h3` and misspell another — TS2741 + TS2353 in the same object is the "finite keys enforced" demo that converts `Record<string>` users. Exercise: find one `Record<string, …>` over a knowable-finite set and replace with the union — count the new errors (each is a latent typo/absence bug).

### 2) **`Map` for dynamic keys** (unknown-at-compile-time, non-string, churn-heavy)

**Definition** — `Map<K, V>` owns three territories `Record` cannot serve: keys unknown until runtime (user ids, cache tags), non-string keys (object identities, numbers without stringification), and high-churn membership (frequent add/delete without shape-transition costs). Iteration order is insertion-guaranteed; `size` is O(1); `get` stays `V | undefined` — dynamic honesty in every method.

**What problem it solves / history** — dynamic registries modeled as `Record<string, T>` suffered three failures: user-supplied keys collided with prototype members (`"constructor"`, `"__proto__"` — the pollution class), numeric keys stringified silently (`map[1]` vs `map["1"]` — same slot, two spellings), and delete-heavy churn deoptimized hidden classes (V8 shape transitions on every `delete`). `Map` eliminates all three structurally: clean key space, typed key kinds, deletion-friendly internals.

**Modern guidance** — as of TypeScript 5.9 era, default caches/registries/memo tables/indexes to `Map` unless *all four* Record-conditions hold (keys finite + string + JSON-needed + low churn — next promise's table). Never use plain objects for user-supplied keys (prototype pollution is a security bug, not a style nit — `Object.create(null)` only when `Map` is genuinely unavailable).

**Runnable example** — dynamic keys without pollution or stringification (good vs bad, `tsc --strict`):

```typescript
// good — user-supplied keys live in a clean, typed key space
const sessions = new Map<string, number>();
function touch(id: string): number {
  const n = (sessions.get(id) ?? 0) + 1;
  sessions.set(id, n);
  return n;
}
console.log(touch("constructor"), touch("constructor"), sessions.size); // 1 2 1 — no pollution
// sessions.set("__proto__" as string, 9); // works safely — Map has no prototype chain to poison

// bad — plain-object registry collides with the prototype
const reg: Record<string, number> = {};
const evil = "__proto__";
reg[evil] = 1; // silently targets the prototype (or throws in strict assignment) — pollution class
console.log(reg[evil], Object.keys(reg).length); // 1 0 — value stored NOWHERE visible (prototype shadow)
// fix — Map<string, number>: user keys can never reach Object.prototype
```

**Common confusion** — "`Object.create(null)` equals `Map`" — null-prototype objects fix pollution but keep stringification (`obj[1]` ≡ `obj["1"]`), keep `undefined`-lies on missing keys (without `noUncheckedIndexedAccess`), and lack `size`/iteration guarantees — `Map` wins on three axes, not one. "`Map` can't be JSON-serialized" — `Object.fromEntries(map)` at the boundary (string keys) — one conversion line, explicit and reviewable. "small maps are slower" — constant-factor differences vanish against the pollution/churn correctness wins — measure at scale, choose by key-kind.

**Performance note** — `Map` add/delete/get O(1) amortized with higher constants than monomorphic property access; delete-heavy workloads strongly favor `Map` (no hidden-class transitions); tiny fixed dictionaries favor objects. The decision input is workload shape (next promise), not microbenchmarks.

**Mentor note** — run the `"__proto__"` demo live (`Object.keys` showing 0 after assignment) — prototype pollution made visceral in two lines. Security framing converts where performance framing doesn't: user-keyed plain objects are vulnerabilities with types. Review gate: `Record<string, …>` fed by user input fails review.

### 3) **Choosing by four questions** (keys known? strings? JSON? churn?)

**Definition** — the decision table: (1) keys known at compile time? No → `Map`. (2) keys non-string? → `Map`. (3) JSON round-trip required? → `Record`/object (or `Map` + `fromEntries` at the boundary). (4) frequent add/delete? → `Map`; stable shape? → `Record`/interface. First "Map" answer wins; `Record` only when all four favor objects. Interfaces beat `Record` for fixed heterogeneous shapes (per-key value types differ).

**What problem it solves / history** — container choice by habit (`Record` everywhere because "objects are simpler"; `Map` everywhere because "safer") produced both incident classes in this domain's pitfalls (5.1 promises 3–4): stringly tables swallowing absence, object registries polluted by user keys. Four questions asked in order route every declaration to the honest container *before* the incident, in review, in thirty seconds.

**Modern guidance** — as of TypeScript 5.9 era, stamp the table on the contributing guide and require the answers for new collection state (one comment line: `// Map: dynamic user keys, high churn`). Revisit when answers change (fixed set becomes dynamic → migrate `Record` → `Map` with the `get`-narrowing fixes counted as the migration's test plan).

**Runnable example** — four questions, four containers (good vs bad, `tsc --strict`):

```typescript
// good — each container chosen by its answers
interface Flags { dark: boolean; beta: boolean } // fixed heterogeneous → interface (per-key types)
type Handlers4 = Record<"click" | "key", () => void>; // fixed homogeneous → Record
const cache = new Map<string, string[]>(); // dynamic keys + churn → Map
const order: string[] = []; // ordered duplicates-allowed → Array
const h4: Handlers4 = { click: () => console.log("c"), key: () => console.log("k") };
h4.click(); // c — finite keys enforced
console.log(cache.size, order.length, Object.keys(h4).length); // 0 0 2

// bad — one container for all four jobs
const everything: Record<string, unknown> = {}; // fixed, dynamic, ordered, keyed — all flattened to unknown
// fix — ask the four questions per declaration; unknown-valued Records answer none of them
```

**Common confusion** — "interfaces and Records interchange" — interfaces allow per-key types + declaration merging + `extends`; `Record<K, V>` forces homogeneous values — heterogeneous fixed shapes want interfaces (see [1.3. Interfaces vs aliases](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.3. Interfaces vs type aliases when to use which.md>)). "arrays answer keyed questions" — arrays answer *ordered* questions; keyed lookup by scan is O(n) plus untyped absence — different data structure, different domain promise. "the table is overkill for small code" — four questions take thirty seconds and prevent both incident classes — cheapest review habit in this domain.

**Performance note** — correct-container choice dominates all micro-optimizations in this space (O(1) vs O(n) lookup, zero vs N defensive copies, shape-stable vs transition-thrashed) — the table *is* the performance guidance; benchmark only after choosing correctly.

**Mentor note** — run new collection declarations through the table out loud in reviews for a month — the team internalizes it, then the stamp suffices. Exercise: re-decide five existing `Record<string, unknown>` declarations with the table — most migrate (to unions, `Map`, or interfaces), each migration deleting an incident vector.
