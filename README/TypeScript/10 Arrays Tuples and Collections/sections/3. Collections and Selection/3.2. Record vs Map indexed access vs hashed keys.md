## 3.2. Record vs Map indexed access vs hashed keys

Record describes an object type; Map constructs a runtime collection. Choose from the key semantics, presence guarantees and operations the application needs. A finite Record can require named properties, while a Map offers a separate entry space and identity-based object keys. Neither choice validates incoming values or automatically provides a lossless JSON format.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence under its filename. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`; run `node dist/FILE.js`. Activate negatives individually with those flags and --noEmit instead of --outDir dist.

### 1) **Finite required keys do not mean exact runtime contents**

Record<K, V> constructs properties for the admitted key type K, each with value type V. For a finite key union, every required key must be supplied. A fresh object literal also gets excess-property checking. A compatible wider object can still be assigned to that view with extra runtime properties intact. The [primary Record reference](https://www.typescriptlang.org/docs/handbook/utility-types.html#recordkeys-type) documents the utility; [mapped types](<../../../09 Utility Types and Type Transformations/sections/1. Mapped Types/1.1. Mapped type fundamentals homomorphic mapping over keys.md>) owns its mechanics.

Save as finite.ts.

```typescript
type EventName = "click" | "keydown";
type Handlers = Record<EventName, () => string>;
const handlers: Handlers = { click: () => "C", keydown: () => "K" };
console.log(handlers.click(), handlers.keydown());
// const missing: Handlers = { click: () => "C" }; // TS2741
// const typo: Handlers = { click: () => "C", keydown: () => "K", clik: () => "X" }; // TS2561
const wider = { click: () => "C", keydown: () => "K", scroll: () => "S" };
const view: Handlers = wider;
console.log(Object.keys(view).join(","), JSON.stringify(view));
// view.scroll(); // TS2339: the static view does not expose this extra key
const symbol = Symbol("metadata");
const keyed: Record<1 | typeof symbol, string> = { 1: "one", [symbol]: "hidden" };
console.log(keyed[1], keyed[symbol], Reflect.ownKeys(keyed).length, JSON.stringify(keyed));
// const invalidKey: Record<object, string> = {}; // TS2344
const finiteMap = new Map<EventName, string>();
console.log(finiteMap.size, finiteMap.get("click"));

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type StaticKeys = Expect<Equal<keyof Handlers, EventName>>;
type PropertyKeys = Expect<Equal<keyof typeof keyed, 1 | typeof symbol>>;
```

The output is `C K`, `click,keydown,scroll {}`, `one hidden 2 {"1":"one"}`, then `0 undefined`; both probes compile. The wider object kept scroll, and JSON omitted its function-valued properties. The numeric property becomes a JSON string key; the symbol property is omitted. Record is not limited to string-literal keys and says nothing by itself about JSON suitability.

A Map whose key type is a finite union still can be empty. Its key parameter checks supplied keys; it does not require one entry for every union member. Choose a finite Record when complete coverage is part of the static contract, or check a Map's completeness separately. Heterogeneous fixed fields can use an interface or object alias; a common V in Record need not preserve a distinct value type for each key.

### 2) **Separate own properties, prototypes and Map entries**

An ordinary object's inherited properties can be mistaken for dictionary entries. Its legacy __proto__ accessor also behaves differently from an own data property. The [accessor reference](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/proto#description) specifies that a non-object, non-null assigned value is ignored. Assigning an object can change that receiver's prototype; it is not the same as changing Object.prototype for every object.

Save as keys.ts. This deliberately observes the legacy accessor on a local object; ordinary application code should not use it as a prototype-management API.

```typescript
const ordinary: Record<string, unknown> = {};
console.log(typeof ordinary["constructor"], Object.hasOwn(ordinary, "constructor"));
ordinary["__proto__"] = 1;
console.log(Object.hasOwn(ordinary, "__proto__"), Object.getPrototypeOf(ordinary) === Object.prototype);
ordinary["__proto__"] = { inherited: 7 };
console.log(ordinary["inherited"], Object.hasOwn(ordinary, "inherited"), Object.hasOwn(Object.prototype, "inherited"));
const dictionary: Record<string, unknown> = { __proto__: null };
dictionary["__proto__"] = 1;
dictionary["constructor"] = 2;
console.log(dictionary["__proto__"], Object.hasOwn(dictionary, "__proto__"), Object.getPrototypeOf(dictionary) === null);
const entries = new Map<string, number | undefined>();
entries.set("__proto__", 1);
entries.set("constructor", 2);
entries.set("present", undefined);
console.log(entries.get("__proto__"), entries.get("constructor"), entries.size, Object.getPrototypeOf(entries) === Map.prototype);
console.log(entries.has("present"), entries.get("present"), entries.has("missing"), entries.get("missing"));
const value = entries.get("constructor");
console.log(value === undefined ? "missing" : value.toFixed(0));
// if (entries.has("constructor")) entries.get("constructor").toFixed(0); // TS2532
const person = { id: "u1" };
const byIdentity = new Map<object, string>([[person, "Ada"]]);
console.log(byIdentity.get(person), byIdentity.get({ id: "u1" }));
const counts: Record<string, number> = {};
const missingCount = counts["missing"];
// missingCount.toFixed(0); // TS18048
console.log(missingCount ?? 0);
```

The output is `function false`, `false true`, `7 false false`, `1 true true`, `1 2 3 true`, `true undefined false undefined`, `2`, `Ada undefined`, then `0`. The ordinary object's numeric __proto__ assignment did not store 1 or throw here. Its later object assignment changed only that local receiver's inheritance. The null-prototype dictionary stores the same text as an own data key. This object-literal prototype syntax is distinct from invoking the inherited legacy accessor.

A Map instance still has a prototype. Its set/get/has methods manage entries separately from those object properties, so an entry named constructor or __proto__ does not invoke the object's inherited property setter. Use those methods rather than bracket properties on the Map instance. These observations identify concrete hazards; they do not prove that every object dictionary is vulnerable or that changing containers validates values.

The stored undefined entry differs from an absent entry. Has reports that distinction, while a separate get result still requires its own value check in TypeScript. The [worked Map/Set owner](<./3.1. Map and Set typing generics over collections.md>) covers these method contracts and current collection features in depth. For an object dictionary, distinguish own presence from inherited values and narrow unknown values before using them. NoUncheckedIndexedAccess makes the ordinary missing count read include undefined; the flag does not alter the runtime object.

### 3) **Choose the data contract and an explicit transport policy**

Dynamic string keys can be represented by an object dictionary or a Map. A finite key set can also use either, but their coverage guarantees differ. Non-string object keys require Map when identity must survive; numeric and symbol property keys have distinct object semantics. JSON is an additional boundary, not a reason to assume either representation always round-trips.

| Requirement | Useful choice or question |
|---|---|
| Every key in a finite union must exist | A finite Record supplies required properties; a Map needs a separate completeness check. |
| Fields have different meanings or value types | An interface or object alias can name those individual fields. |
| Object keys must retain identity | Map supports identity keys; an ordinary object property cannot use an object identity as a property key. |
| Dynamic string dictionary | Compare Map operations with a deliberate object prototype and own-property policy. |
| Ordered entry iteration and direct size | Map supplies an iterable entry API and size; object enumeration needs a chosen key subset. |
| JSON transport | Specify supported key/value types and conversions; test collisions and omitted values. |
| Frequent updates or performance sensitivity | Measure the actual workload, including conversion and iteration costs. |

Save as transport.ts.

```typescript
const mixed = new Map<number | string, string>([[1, "numeric"], ["1", "text"]]);
const object = Object.fromEntries(mixed);
console.log(mixed.size, Object.keys(object).length, JSON.stringify(object));
console.log(JSON.stringify(mixed));
console.log(JSON.stringify([...mixed]));
const strings = new Map<string, number>([["Ada", 2], ["Lin", 1]]);
const objectPayload = Object.fromEntries(strings);
console.log(JSON.stringify(objectPayload));
interface Config { host: string; retries: number }
const config: Config = { host: "localhost", retries: 2 };
console.log(JSON.stringify(config));
// strings.set(1, 3); // TS2345
```

The output is `2 1 {"1":"text"}`, `{}`, `[[1,"numeric"],["1","text"]]`, `{"Ada":2,"Lin":1}`, then `{"host":"localhost","retries":2}`. The entry-array encoding preserves this example's numeric-versus-string key distinction, while fromEntries collapses both to one object property. The string/number payload and named config have deliberately JSON-compatible values in this example. Encoding entry arrays still does not preserve arbitrary object identity, functions or every possible Map value through JSON. A receiver needs a decoding and validation policy too; a type assertion on JSON.parse would not supply one.

### 4) **Common confusion**

Finite Record means required typed properties, not an exact runtime key set. A narrower view does not delete wider object's data, and fresh excess-property checking is not a runtime filter. Record<string, unknown> can be an honest dynamic boundary type when its values are inspected; it is not inherently a failed design.

Map's entry namespace is separate from its instance properties. It is useful for dictionary behavior, but does not automatically enforce finite completeness, validate payloads or serialize entries. An object with a deliberate null prototype and own-property handling is a valid string dictionary choice, not merely a fallback for environments without Map.

### 5) **Performance note**

Record types erase; object and Map operations remain. The [Map reference's specification discussion](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Map#description) describes average sublinear access, not a required hash-table implementation or universal constant-time promise. [Zheng Hao's original object-versus-Map experiments](https://www.zhenghao.io/posts/object-vs-map) show why key distributions and measurement conditions matter; their 2022 timings were not rerun or adopted as current results here. No universal deletion/JIT claim, crossover size or checker-cache formula supports this lesson. Include required conversions and iteration in an application benchmark when speed affects the decision.

### 6) **Mentor note**

Ask which requirement is established by each mechanism: finite required keys, own-property presence, value narrowing, identity lookup or transport encoding. Have the learner explain why view still has scroll and why JSON.stringify(view) omits all the handlers. A sound container choice names the needed contract rather than repeating “dynamic means Map” as a ban on other representations.

For practice, add scroll to EventName in finite.ts while initially leaving handlers unchanged. Expect TS2741 for the missing handler; wider already has scroll and remains compatible. Add scroll: () => S to handlers and verify its new call prints S. Update the old view.scroll negative because it is now admitted. Explain why merely constructing an empty Map<EventName, string> still would not prove all three entries exist.
