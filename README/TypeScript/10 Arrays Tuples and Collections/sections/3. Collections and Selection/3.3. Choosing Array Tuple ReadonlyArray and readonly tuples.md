## 3.3. Choosing Array Tuple ReadonlyArray and readonly tuples

Choose a collection contract from the meaning of the data and the operations a consumer needs. A list of rows can be open-ended, while a minimum/maximum pair has two positional roles even though both values are numbers. Readonly capability, independent copies and runtime integrity are additional decisions; no single array annotation establishes all three.

### 1) **Choose meaningful positions or an open sequence**

Use an array when each element plays the same role and the collection can have an open number of elements. Use a tuple when particular positions have distinct roles or required presence. The types need not differ: readonly [min: number, max: number] is useful precisely because both numbers could otherwise be confused. Optional and rest tuples can model variable shapes too; “known length and mixed types only” is an incomplete selection rule.

The [tuple owner](<../2. Tuple Types/2.1. Fixed arity tuples labels and optional elements.md>) covers construction and mutable-method limits. Labels document roles without preventing a same-typed swap. Prefer named object fields when those roles are easier to understand by name or evolve independently. Arrays and tuples are both runtime arrays; neither choice automatically changes indexing into a search or validates incoming values.

### 2) **Choose capabilities, independence and runtime integrity separately**

A readonly input admits ordinary mutable arrays as well as readonly sources. A private mutable builder can accumulate results before returning a readonly view. Returning that builder does not freeze it; copying is needed only when the required independence calls for it. An editable result can legitimately be mutable when that is the API's purpose.

For the worked example, define a stronger snapshot requirement: later edits to the caller's row objects must not change the snapshot, and its own rows, range and containers must reject runtime writes. Because each row contains only a string and a number, copying these two fields separates the values needed here. Freeze each copied row, the row array, the numeric range and the result object explicitly. This is a policy for this finite shape, not a general deep-freeze utility. The [readonly owner](<../1. Array Types/1.2. Readonly arrays and mutable vs frozen arrays.md>) and [runtime freeze reference](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/freeze#deep_freezing) explain why a single outer freeze would be insufficient for object elements.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save the fence as snapshot.ts. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist snapshot.ts`; run `node dist/snapshot.js`. Activate negatives individually and use those flags with --noEmit instead of --outDir dist.

```typescript
interface Row { id: string; score: number }
type ScoreRange = readonly [min: number, max: number];
interface ScoreSnapshot {
  readonly rows: readonly Readonly<Row>[];
  readonly range: ScoreRange | null;
}
function buildSnapshot(input: readonly Row[]): ScoreSnapshot {
  const owned: Readonly<Row>[] = [];
  let lower: number | undefined;
  let upper: number | undefined;
  for (const row of input) {
    if (!Number.isFinite(row.score)) throw new Error("score must be finite");
    owned.push(Object.freeze({ id: row.id, score: row.score }));
    lower = lower === undefined ? row.score : Math.min(lower, row.score);
    upper = upper === undefined ? row.score : Math.max(upper, row.score);
  }
  const range: ScoreRange | null = lower === undefined || upper === undefined
    ? null : Object.freeze([lower, upper] as const);
  return Object.freeze({ rows: Object.freeze(owned), range });
}
const source: Row[] = [{ id: "Ada", score: 2 }, { id: "Lin", score: 5 }];
const snapshot = buildSnapshot(source);
for (const row of source) if (row.id === "Ada") row.score = 99;
source.push({ id: "New", score: 7 });
console.log(source.map(row => row.score).join(","), snapshot.rows.map(row => row.score).join(","));
console.log(snapshot.range?.join(",") ?? "empty");
console.log(Object.isFrozen(snapshot), Object.isFrozen(snapshot.rows), Object.isFrozen(snapshot.rows[0]), Object.isFrozen(snapshot.range));
console.log(Reflect.set(snapshot.rows, "0", { id: "X", score: 0 }));
if (snapshot.range !== null) console.log(Reflect.set(snapshot.range, "0", 0));
const firstRow = snapshot.rows[0];
if (firstRow !== undefined) console.log(Reflect.set(firstRow, "score", 0));
// snapshot.rows.push({ id: "X", score: 0 }); // TS2339
// for (const row of snapshot.rows) row.score = 0; // TS2540
// if (snapshot.range !== null) snapshot.range[0] = 0; // TS2540
const draft: Row[] = snapshot.rows.map(row => ({ ...row }));
for (const row of draft) row.score += 10;
console.log(draft.map(row => row.score).join(","), snapshot.rows.map(row => row.score).join(","));
const empty = buildSnapshot([]);
console.log(empty.rows.length, empty.range);
try { buildSnapshot([{ id: "Bad", score: Infinity }]); }
catch (error) { console.log(error instanceof Error ? error.message : "unexpected"); }
const scores = source.map(row => row.score);
// const arbitraryRange: ScoreRange = scores; // TS2322: an open array does not prove two required slots
// const shortRange: ScoreRange = [1]; // TS2322

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type RangeLength = Expect<Equal<ScoreRange["length"], 2>>;
type OpenRows = Expect<Equal<ScoreSnapshot["rows"]["length"], number>>;
type OpenScores = Expect<Equal<typeof scores, number[]>>;
```

The output is `99,5,7 2,5`, `2,5`, `true true true true`, `false`, `false`, `false`, `12,15 2,5`, `0 null`, then `score must be finite`; three live probes compile. Source changes do not affect the copied snapshot fields. Reflect.set observes actual write rejection without pretending an annotation runs a check. The editable draft copies the row objects again, so its score updates do not affect the snapshot either.

The range tuple has two numbers with distinct roles; the rows array allows any length, including zero. Null explicitly represents an absent range. Infinity is a valid JavaScript number and a valid number-typed value, so the finite-score requirement needs a runtime test. The function accepts an already typed row collection; it is not a parser for arbitrary unknown JSON, sparse arrays or hostile getters. [Runtime boundary parsing](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>) owns establishing those external shape guarantees.

### 3) **Review the requirement that each choice establishes**

Use a few concrete questions instead of requiring a stamp on every declaration. Do consumers need a sequence or roles at particular positions? Must they write through this reference? Can another alias still change a supposedly stable result? Which runtime values need copying or integrity enforcement? In the example, those answers justify an open readonly row list, a two-position readonly numeric tuple, copied scalar row fields and explicit freezing at each relevant level.

If access is by identity or named key rather than position, use the [Record-versus-Map selection lesson](<./3.2. Record vs Map indexed access vs hashed keys.md>). Required finite coverage, key semantics and transport policy still need separate decisions. An array remains a valid representation when iteration is the task, and an object remains useful when named fields communicate the result better. Choose the contract that serves the task rather than declaring the strictest type automatically best.

### 4) **Common confusion**

A tuple can have homogeneous element types, and an array can contain a union. The key distinction is the role and presence of positions, not a requirement for mixed primitives. Readonly type syntax does not create ownership, copy a source or freeze a builder on return.

A copy can be shallow, and runtime freeze is shallow too. The example meets its stated snapshot requirement by explicitly copying the only row fields and freezing all relevant objects it constructs. Adding a nested mutable field would require revisiting that policy rather than assuming the current implementation had become a general solution.

### 5) **Performance note**

The type choices erase. This implementation traverses the provided rows, creates copied row objects and an outer array, and freezes its output objects. The later draft performs another explicit copy. These are real costs chosen for the snapshot requirement. No tuple-versus-array checker advantage, runtime index speedup, publication threshold or JIT result was measured. If independence or runtime integrity is unnecessary for another API, it can choose a cheaper policy honestly; measure the relevant implementation before optimizing.

### 6) **Mentor note**

Ask the learner to remove one operation at a time: the per-row copy, the row freeze, the outer-array freeze or the range's tuple contract. Require them to predict which source edit, runtime write or malformed assignment would then be admitted. This connects each mechanism to an observable requirement instead of treating readonly as a general safety stamp.

For practice, add a readonly count: number property to ScoreSnapshot. First change only the interface and confirm the builder fails because its return lacks count. Then compute count from owned.length when constructing the result. Verify that the two-row snapshot reports 2 and the empty snapshot reports 0, even after source grows to three rows. Do not assert the result into the new type; the value must actually contain the property. Explain why a stored initial count is a snapshot observation, while source.length later answers a different question.
