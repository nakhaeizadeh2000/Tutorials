## 3.3. Choosing — `Array`, `Tuple`, `ReadonlyArray`, and readonly tuples

### 1) **Array vs tuple** (open list vs fixed slots — the one-sentence test)

**Definition** — unknown length + same element type → array (`string[]`); fixed arity + per-position types → tuple (`[string, number]`). The test answers in one sentence per declaration ("do I know how many, and are they different?") — yes/yes → tuple; anything else → array (possibly union-elemented). Readonly variants follow the same test (see promise 2).

**What problem it solves / history** — arity-known data modeled as arrays (`[host, port]` as `string[]` — ports parsed per use, positions unchecked) and open lists modeled as tuples (`[string, string, …]`-aspirations that couldn't express "N more") both compiled while checking nothing. The sentence routes each declaration before it ships: tuples where the shape is the contract, arrays where growth is the contract.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), ask the sentence at every collection declaration; destructure tuples and iterate arrays (matching consumption to shape); convert when answers change (pair grows a third slot → tuple gains a position; fixed set becomes dynamic → tuple becomes array). When torn, prefer the stricter (tuple) — loosening later is additive, tightening breaks consumers.

**Runnable example** — sentence routes each declaration (good vs bad, `tsc --strict`):

```typescript
// good — tuple where shape is the contract, array where growth is
type HostPort = [host: string, port: number]; // fixed 2, mixed → tuple
const hp: HostPort = ["db", 5432];
console.log(hp[0].toUpperCase(), hp[1].toFixed(0)); // DB 5432
const tags: string[] = ["a", "b"]; // open length, same type → array
console.log(tags.map((t) => t.toUpperCase()).join(",")); // A,B

// bad — array where shape is the contract: positions and arity unchecked
const hpBad: (string | number)[] = ["db", 5432];
const swapped: (string | number)[] = [5432, "db"]; // compiles — contract gone
console.log(swapped.length); // 2 — same length, wrong positions, no error
// fix — HostPort: the sentence ("fixed 2, mixed types") answered tuple
// const fix: HostPort = [5432, "db"]; // error TS2322 — positions enforced
```

**Common confusion** — "single-element tuples are pointless" — `[id: string]` still enforces arity-1 + labels + readonly-tuple flow (niche but honest — single slots with contracts). "unions of tuples cover open lists" — `[A] | [A, A] | [A, A, A]` enumerates arities (finite) — open-ended growth needs arrays (or rest-element tuples ` [A, ...A[]]` — the honest hybrid). "the sentence ignores readonly" — readonly is the *second* question (promise 2) — shape first, mutability second, always in that order.

**Performance note** — shape choice has zero runtime delta (both emit arrays); check cost favors tuples at small arity (per-position, cached) vs arrays (per-element at literals). The performance content is downstream: tuple positions enable O(1) indexed reads with literal types; arrays need scans/searches.

**Mentor note** — run the sentence out loud for five declarations in review ("how many? same type?") — the team internalizes the routing within a week. Exercise: find one `(string | number)[]` with stable arity and convert to a tuple — count the new position errors (each a latent swap bug).

### 2) **Mutable vs readonly** (builders mutate locally; published data freezes)

**Definition** — second question after shape: mutated after creation? Locally-built and consumed → mutable (`T[]`, `[A, B]`); shared, published, or cross-boundary → readonly (`readonly T[]`, `readonly [A, B]`). Mutable flows into readonly (widening admission); readonly escapes to mutable only via copy. Builders accumulate mutably and freeze on `return` (`as const`, `Object.freeze`, or readonly-typed publication).

**What problem it solves / history** — uniformly-mutable collections (every list `T[]`, every pair `[A, B]`) let callees mutate caller state anywhere (the 1.2/1.3 `sort` incidents) — safety required whole-program audits. Uniformly-readonly collections swung too far (builders fought the type at every `push`). Split by lifecycle — mutable inside, readonly outside — localizes mutation to the construction scope where it belongs and is reviewable.

**Modern guidance** — as of TypeScript 5.9 era, declare builders mutable (`const out: string[] = []`), parameters/snapshots/returns readonly (`items: readonly T[]`), and convert at the boundary (`return [...out]`, `return out as const` where literals serve). Lint exported mutable collection state (`no-mutable-export` custom rule or review convention) — publication is the freeze point.

**Runnable example** — lifecycle split (good vs bad, `tsc --strict`):

```typescript
// good — mutable inside, readonly outside: mutation scoped to construction
function evens(upto: number): readonly number[] {
  const out: number[] = []; // mutable builder — pushes legal here
  for (let i = 0; i <= upto; i += 2) out.push(i);
  return out; // mutable flows into readonly — frozen by signature
}
const e = evens(6);
console.log(e.join(",")); // 0,2,4,6
// e.push(8); // error TS2339 — published as readonly (mutation scoped out)

// bad — uniformly mutable: publication invites caller-side mutation
function evensBad(upto: number): number[] {
  const out: number[] = [];
  for (let i = 0; i <= upto; i += 2) out.push(i);
  return out;
}
const eb = evensBad(6);
eb.push(999); // compiles — consumer mutates the "result" (aliasing the builder's array)
console.log(eb.length); // 5 — published data changed post-publication
// fix — readonly return: the freeze point is the signature, not reviewer vigilance
```

**Common confusion** — "readonly returns inconvenience consumers" — consumers needing mutation copy once (`[...e]`) — one explicit line vs unbounded hidden aliasing; the inconvenience is the feature. "builders should be readonly throughout" — accumulation *is* mutation (`push` per element) — readonly builders fight every append; freeze at publication, not during construction. "tuples can't be readonly" — `readonly [A, B]` (and `as const` inference) — same lifecycle split, fixed arity.

**Performance note** — freeze-at-publication costs nothing extra (signature-only; the builder array transfers by reference into readonly type). Copy-on-escape (`[...out]`) costs O(n) per publication — budget at API boundaries (rare), alias within scopes (free).

**Mentor note** — the `eb.push(999)` post-publication mutation is the lifecycle demo — "who owns this array after `return`?" has exactly one honest answer (nobody mutates it). Review stamp: "mutable inside? readonly outside? freeze point named?" — three yeses, merge.

### 3) **Review stamp** (three questions routing every collection declaration)

**Definition** — the stamp: (1) length known + types mixed? → tuple, else array; (2) keys involved? → 3.2's four-question table (`Record`/`Map`/interface); (3) mutated after creation? → mutable iff locally-built-and-consumed, else readonly. Three answers, one container — applied to every new collection declaration in review, thirty seconds each.

**What problem it solves / history** — container choice by habit produced all four incident classes in 5.1 (protocol-frame overflow, shared-sort mutation, stringly-table absence, unchecked index crash) — each a declaration the stamp would have rerouted. Stamps work because they move the decision *earlier* (declaration, with three questions) from *later* (incident, with a post-mortem): same thinking, different timing, opposite cost.

**Modern guidance** — as of TypeScript 5.9 era, print the stamp in the contributing guide; require answers (one comment line on non-obvious declarations: `// tuple: fixed 2, mixed; readonly: published`); re-stamp when answers change (fixed set goes dynamic, local list gets published). Combine with 3.2's table for keyed data — six questions total covering every container in the language.

**Runnable example** — stamp applied to three declarations (good vs bad, `tsc --strict`):

```typescript
// good — stamped: tuple (fixed/mixed/readonly) + array (open/same/mutable) + Map (dynamic keys)
type Frame = readonly [kind: string, len: number]; // Q1 tuple, Q3 readonly (protocol: fixed + published)
const frame: Frame = ["data", 4];
const scratch: number[] = []; // Q1 array (open/same), Q3 mutable (local builder)
scratch.push(1);
const reg2 = new Map<string, number>(); // Q2 table → Map (dynamic keys)
console.log(frame[1].toFixed(0), scratch.length, reg2.size); // 4 1 0

// bad — unstamped: array for a frame (arity unchecked), mutable for published (aliasing open)
const frameBad: (string | number)[] = ["data", 4]; // Q1 said tuple — ignored
// fix — stamp every declaration: shape (Q1), keys (Q2 table), lifecycle (Q3)
console.log(frameBad.length); // 2 — compiles with zero contracts
```

**Common confusion** — "stamps slow reviews" — thirty seconds per declaration vs hours per incident — the stamp is the highest-ROI review habit in this domain. "obvious declarations don't need it" — obvious *today* (fixed pair) rots *tomorrow* (third slot added as array push instead of tuple position) — stamp on creation, re-stamp on change. "six questions overlap" — Q1–Q3 route ordered data, 3.2's four route keyed data — disjoint inputs, shared discipline.

**Performance note** — correct-container choice dominates micro-optimizations (O(1) vs O(n), zero vs N copies) — the stamp *is* the performance review for collections; benchmark only correctly-chosen containers.

**Mentor note** — stamp five existing declarations together in one review session — the team calibrates on real code, and the two that migrate prove the stamp's value immediately. Make the stamp a checklist comment template, not folklore: `// Q1:? Q2:? Q3:?` on every new collection state.
