## 7.1. Boundaries — what is covered elsewhere

### 1) **Function-level rest, overloads, and generic forwarding** (signatures, capture, pipes) — [05 Functions and Callable Types](<../../../05 Functions and Callable Types/README.md>) + [08 Generics Deep Dive](<../../../08 Generics Deep Dive/README.md>)

**Definition** — tuple rest on signatures (`...args: [url, init?]`), overloads-per-arity, per-call inference, and `<T extends unknown[]>` forwarding with concat/pipe composition live in 05/2.3 and 08/3.3 — this domain *consumed* those mechanics (labeled rests, `[...T, last]`, entry tuples) without re-teaching them.

**What problem it solves / history** — 05 owns "how do I type this signature?"; 08 owns "how do parameters forward?"; 10 owns "what are these collection types?" — three layers (signature, forwarding, type) composed at use sites instead of repeated per domain.

**Modern guidance** — for signature/rest/overload questions start at [2.3. Rest and tuples](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.3. Rest parameters tuple types and variadic composition.md>); for forwarding/concat/pipe questions go to [3.3. Variadic tuples](<../../../08 Generics Deep Dive/sections/3. Variance and Advanced Generic Patterns/3.3. Variadic tuple generics pipe concat and rest capture.md>); for the types themselves stay here.

**Runnable example** — three layers, one call (`tsc --strict`):

```typescript
// 10: the tuple type; 05: the rest signature; 08: the forwarding capture
type Args = [url: string, init?: { method: string }]; // 10 owns this shape
function call(...[url, init]: Args): string { return `${init?.method ?? "GET"} ${url}`; } // 05 owns the rest
function fwd<T extends unknown[]>(fn: (...args: T) => string, ...args: T): string { return fn(...args); } // 08 owns the capture
console.log(fwd(call, "/a")); // GET /a — three domains, one honest call
```

**Common confusion** — "10 replaces 05/2.3" — 10 *uses* tuple rests; 05 *defines* signature rest semantics (arity errors, `this`, overloads) — definition vs application differ.

**Performance note** — no overlap means no duplicated guidance — signatures (05), forwarding (08), and types (10) each measure their own costs.

**Mentor note** — route "how do I type this callback's rest?" to 05, "how do I forward it?" to 08, "array or tuple?" here — the question's verb picks the domain.

**Cross-links** — rest signatures → [2.3. Rest and tuples](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.3. Rest parameters tuple types and variadic composition.md>); forwarding → [3.3. Variadic tuples](<../../../08 Generics Deep Dive/sections/3. Variance and Advanced Generic Patterns/3.3. Variadic tuple generics pipe concat and rest capture.md>).

### 2) **Mapped/conditional transforms over collections** (`Partial`, `Exclude`, `DeepPartial`, `Awaited`) — [09 Utility Types and Type Transformations](<../../../09 Utility Types and Type Transformations/README.md>)

**Definition** — the transform catalog over element/key sets (`Partial<User[]>`, `Exclude<Status, …>`, `DeepPartial<Config>`, `Awaited<Promise<T>[]>` semantics) lives in 09 — this domain supplied the *inputs* (arrays, tuples, Maps the transforms consume) without building the catalog.

**What problem it solves / history** — 09's `Head`/`Tail`/`ElemOf` examples borrow tuple inputs; 10's tables derive unions transforms consume — inputs and transforms compose across the boundary instead of either domain owning both halves.

**Modern guidance** — choose the container here (shape? keys? lifecycle?), transform it with 09 (map/filter/extract/derive) — selection before transformation, always. For `Head`/`Tail`/`Awaited`-over-tuples start at [2.3. infer pipelines](<../../../09 Utility Types and Type Transformations/sections/2. Conditional Types/2.3. infer pipelines ReturnType Parameters Awaited.md>).

**Runnable example** — 10 selects, 09 transforms (`tsc --strict`):

```typescript
// 10: tuple source with literals; 09: indexed derivation into a working set
const STATUSES = ["idle", "done"] as const; // 10 owns the source shape
type Open = Exclude<(typeof STATUSES)[number], "done">; // 09 owns the filter: "idle"
const o: Open = "idle";
console.log(o.toUpperCase()); // IDLE — selection (10) then transformation (09)
```

**Common confusion** — "transforms belong with containers" — transforms operate over *any* input kind (objects, unions, tuples) — housing them per-container would duplicate the catalog N times; one catalog (09) serving all inputs (04/07/10) is the DRY shape.

**Performance note** — selection cost (10) plus transform cost (09) compose additively — both cached per instantiation; no double-counting when layers stay separate.

**Mentor note** — tell students "you can now *hold* collections (10) and *compute* over them (09)" — holding vs computing is the two-domain story in one sentence.

**Cross-links** — utility home → [09 Utility Types](<../../../09 Utility Types and Type Transformations/README.md>); infer pipelines → [2.3. infer pipelines](<../../../09 Utility Types and Type Transformations/sections/2. Conditional Types/2.3. infer pipelines ReturnType Parameters Awaited.md>).

### 3) **Object-type composition and literal basics** (`&` vs `extends`, literals, `as const`, `satisfies`) — [04 Objects, Interfaces and Type Aliases](<../../../04 Objects Interfaces and Type Aliases/README.md>) + [03 Basic Types and Annotations](<../../../03 Basic Types and Annotations/README.md>)

**Definition** — shape composition (`&` vs `extends`, merging, `keyof`/`T[K]`), literal types, widening, and the `as const`/`satisfies` pair live in 04/03 — this domain applied them (tuples of object types, literal tuples, const-asserted tables with contracts) without re-teaching.

**What problem it solves / history** — collections *contain* shapes and literals; the rules governing contents (freshness, widening, literal preservation) belong to the content domains — 10 links per use instead of restating per collection kind.

**Modern guidance** — design element shapes in 04 (freshness-safe, queried correctly), declare literal sources narrowly in 03 (`as const`), then collect them here — contents before containers, always.

**Runnable example** — 04 shape + 03 literals, collected here (`tsc --strict`):

```typescript
// 04: element shape; 03: literal source; 10: the collection holding both
interface Item { sku: string; qty: number; } // 04 owns shape rules
const SKUS = ["a1", "b2"] as const; // 03 owns literal narrowing
const stock: Record<(typeof SKUS)[number], Item> = { a1: { sku: "a1", qty: 3 }, b2: { sku: "b2", qty: 0 } };
console.log(stock.a1.qty.toFixed(0)); // 3 — contents (04/03) collected (10)
```

**Common confusion** — "collections need no shape rules" — freshness, `readonly`, and widening all still apply *inside* every element — containers add a layer, they do not replace the content layer.

**Performance note** — content checks (04/03) and container checks (10) compose additively — keep element shapes small *and* collections cached.

**Mentor note** — review collections in two passes (contents per 04/03, container per 10) — mixed passes miss one layer's bugs.

**Cross-links** — object model → [04 Objects](<../../../04 Objects Interfaces and Type Aliases/README.md>); literals → [3.3. Literal types](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>).

### 4) **Union algebra and narrowing over elements** (distributivity, discriminants, exhaustiveness) — [07 Unions, Intersections and Narrowing](<../../../07 Unions Intersections and Narrowing/README.md>)

**Definition** — `|`/`&` set algebra, discriminated-union design, and control-flow narrowing (`typeof`/`in`/`never`-sink exhaustiveness, predicates) live in 07 — this domain held unions *in* collections (element unions, entry unions, status tables) and narrowed them with 07's guards without re-teaching either.

**What problem it solves / history** — `(A | B)[]` processing needs both layers (collection iteration from 10, member narrowing from 07) — each domain owns its layer so `for (const x of xs) if ("a" in x)` reads as composition, not duplication.

**Modern guidance** — hold alternatives in collections here (element unions, optional slots), discriminate and exhaust them with 07 (guards, switches, `never` sinks) — holding vs handling, in that order.

**Runnable example** — 10 holds, 07 handles (`tsc --strict`):

```typescript
// 10: element union held in an array; 07: discriminant narrowed per element
type Shape = { kind: "c"; r: number } | { kind: "s"; s: number };
function areas(shapes: readonly Shape[]): number[] {
  return shapes.map((sh) => sh.kind === "c" ? Math.PI * sh.r ** 2 : sh.s ** 2); // 07 narrowing inside 10 iteration
}
console.log(areas([{ kind: "s", s: 2 }])[0]?.toFixed(0)); // 4 — held (10), handled (07)
```

**Common confusion** — "element narrowing belongs to 10" — narrowing *values* is control-flow analysis (07) regardless of container; 10 owns holding/iterating them — related, not identical.

**Performance note** — element-union switches cost O(members) per element (fine for small unions); filter-then-map (narrow the array first with a predicate) beats per-element branching in hot loops.

**Mentor note** — teach the pipeline order explicitly (hold → narrow → consume) — students who sequence the two domains stop building filters before modeling the union.

**Cross-links** — unions/narrowing → [07 Unions](<../../../07 Unions Intersections and Narrowing/README.md>); predicates → [3.3. Custom narrowers](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.3. Custom narrowers predicates asserts and type guards on unions.md>).

### 5) **Compiler strictness flags** (`strict`, `noUncheckedIndexedAccess`, `--erasableSyntaxOnly`) — [13 Configuration and Compiler Options](<../13 Configuration and Compiler Options/README.md>) (textual forward)

**Definition** — `strict` (surfacing `unknown`/`never[]` fallbacks), `noUncheckedIndexedAccess` (honest index reads — this domain's highest-yield flag), and `--erasableSyntaxOnly`/`isolatedDeclarations` (array/tuple syntax passes) live in 13 — this domain verified every fence under `strict` without owning the flags.

**What problem it solves / history** — flag semantics belong with the compiler-options reference (13), not scattered across 20 domains — one home keeps `tsconfig` advice consistent as defaults evolve through TS 5.x into 6.0.

**Modern guidance** — develop collections under `strict` + `noUncheckedIndexedAccess` (all examples verified so, 5.1 promise 4 demonstrates the payoff); take flag questions to 13 when it lands — until then, per-leaf verification notes are authoritative.

**Runnable example** — flags change what the same collection reports (`tsc --strict`):

```typescript
// noUncheckedIndexedAccess ON: open index reads gain undefined (tuples exempt by arity)
function head<T>(xs: readonly T[]): T | undefined { return xs[0]; } // honest under the flag
console.log(head([]) ?? "empty", head([7])?.toFixed(0)); // empty 7
```

**Common confusion** — "collections need special flags" — they need `strict` + `noUncheckedIndexedAccess` (like everything needs `strict`) plus nothing else; `--erasableSyntaxOnly` already passes for all array/tuple syntax.

**Performance note** — flags add check-time precision at zero emit cost — the selection guidance here (cache, scope, name) assumes both flags on.

**Mentor note** — standardize team `tsconfig` on `strict` + `noUncheckedIndexedAccess` before teaching collections — unstrict collections teach `any`-shaped habits that strictness later punishes.
