## 4.1. Unions intersections narrowing checklist — mental models mentors insist on

Use this checklist when reviewing a union handler or composed contract. Each question asks for concrete evidence: an accepted value, a rejected operation, an executed branch or a deliberate fallback. The full mechanisms live in the linked owners; the cache-command example applies them together.

### 1) **Check which inputs the union actually allows**

State the valid alternatives before selecting a guard. A read command needs a key; a write command needs a key and value. A shared literal `mode` connects the write value with the write operation. That relationship matters even with two alternatives; there is no variant-count threshold for choosing a tag.

A structural union accepts values satisfying at least one alternative, potentially both when the contracts overlap. Distinct tags separate the tag values, but do not seal the object against additional keys. Decide whether extra data is harmless or forbidden, rather than assuming the union prohibits it. Use [union membership](<../1. Union Types/1.1. Union fundamentals member access and the common property rule.md>), [tagged representation](<../1. Union Types/1.2. Discriminated unions the tagged pattern that scales.md>) and [forbidden-field modeling](<../2. Intersection Types/2.2. The never trap conflicting intersections and impossible states.md>) for the respective questions.

### 2) **Check the evidence before each operation**

Read a shared key directly. Before using the write-only value, establish the write branch. The guard should match the required semantics: tag equality identifies this command's operation, whereas `in` would ask about property presence, including inherited properties. A cast can conceal a missing proof and produce an undefined read.

Narrowing follows control flow, not just the braces surrounding a condition. After the read branch returns, the continuation can be the write branch. Inspect the remaining paths instead of claiming that every narrowing disappears at the end of an if block. [Built-in narrowers](<../3. Control Flow Narrowing/3.1. Built-in narrowers typeof instanceof in and equality.md>) and [control-flow exhaustiveness](<../3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>) own those rules. If a reusable predicate supplies the evidence, verify its false case too using [custom guards](<../3. Control Flow Narrowing/3.3. Custom narrowers predicates asserts and type guards on unions.md>).

### 3) **Check whether composition requires both contracts**

Every queued command also requires an audit identifier. Intersect that common requirement with the union rather than making audit metadata another alternative. The resulting type describes one value; it does not perform a runtime merge. Use an actual constructor expression to establish its fields.

A conflicting literal discriminant can reduce an entire intersection to `never`; an ordinary field conflict can leave an impossible property. An accepted alias alone does not prove a value exists. [Intersection fundamentals](<../2. Intersection Types/2.1. Intersection fundamentals merging object shapes.md>) and [the never trap](<../2. Intersection Types/2.2. The never trap conflicting intersections and impossible states.md>) own those distinctions. Also avoid replacing intersection with `Extract` by assumption: [distribution and filtering](<../2. Intersection Types/2.3. Unions and intersections distributive behavior and primitive intersections.md>) explains where their results differ.

### 4) **Check what adding an alternative should require**

If a new command needs new behavior, keep an exhaustiveness sink at the point where no declared alternatives should remain. Adding a variant must then fail until its behavior is implemented. This is useful for a small local workflow as well as a public API; visibility alone does not decide the policy.

A permissive fallback is appropriate only when ignoring the remaining inputs is intentional. A bare never assignment can check static coverage, while a throwing helper also defines a runtime unexpected-path outcome. The declaration and helper code do not disappear merely because the annotation erases. Input parsing, the handled payload's validity and runtime fallback remain separate concerns; see [exhaustiveness](<../3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>) and [boundary parsing](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>).

The following review drill was verified with TypeScript 7.0.2 and Node.js 20.20.2. Save as `review.ts`; compile with `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist review.ts`; run `node dist/review.js`. For each negative, activate one commented line and recheck with the same flags plus `--noEmit` instead of `--outDir dist`.

```typescript
type ReadCommand = { mode: "read"; key: string };
type WriteCommand = { mode: "write"; key: string; value: string };
type Command = ReadCommand | WriteCommand;
type Queued = Command & { auditId: string };
function queue(command: Command, auditId: string): Queued {
  return { ...command, auditId };
}
function assertNever(_value: never): never { throw new Error("Unhandled command"); }
function run(command: Queued, cache: Map<string, string>): string {
  const key: string = command.key; // Common requirement.
  switch (command.mode) {
    case "read": return `${command.auditId}:read ${key}=${cache.get(key) ?? "missing"}`;
    case "write": cache.set(key, command.value); return `${command.auditId}:write ${key}`;
    default: return assertNever(command);
  }
}
function payload(command: Command): string {
  if (command.mode === "read") return "no payload";
  return command.value.toUpperCase(); // Read path returned; write remains here.
}
const cache = new Map<string, string>();
const jobs: Queued[] = [
  queue({ mode: "read", key: "name" }, "a1"),
  queue({ mode: "write", key: "name", value: "Ada" }, "a2"),
  queue({ mode: "read", key: "name" }, "a3"),
];
for (const job of jobs) console.log(run(job, cache), payload(job));

function assumedPayload(command: Command): string {
  return (command as WriteCommand).value.toUpperCase(); // Deliberately unsound.
}
try { assumedPayload({ mode: "read", key: "name" }); }
catch (error) { console.log(error instanceof TypeError ? "cast: TypeError" : "unexpected error"); }
const richerRead = { mode: "read" as const, key: "name", value: "extra data" };
const acceptedRead: Command = richerRead; // Structural extra data does not change the mode.
console.log(payload(acceptedRead));
// const missingValue: Command = { mode: "write", key: "name" }; // TS2322
// const missingAudit: Queued = { mode: "read", key: "name" }; // TS2322
// function unsafe(command: Command) { return command.value; } // TS2339
```

The output is:

```text
a1:read name=missing no payload
a2:write name ADA
a3:read name=Ada no payload
cast: TypeError
no payload
```

The read/write behavior is observable, the write-only payload is used after a real guard, and each queued input contains the audit field. The richer read value demonstrates structural openness without changing the handler's selected mode. The unsafe assertion fails on a legitimate read input.

For the extension check, change `Command` to `ReadCommand | WriteCommand | { mode: "delete"; key: string }`. Without editing the handlers, `assertNever(command)` fails with TS2345 and `payload`'s remaining value read fails with TS2339. Implement the delete behavior and decide what payload reporting should mean for it. These are useful review signals; adding `as never` or casting the remaining command to WriteCommand would suppress them.

### 5) **Common confusion**

Safe common reads do not imply that every member's operations have compatible callable signatures. Nor does a union mean that an object has exactly one alternative's listed fields. Review the actual operation and the input contract; the common-property slogan is a starting question, not an exact-object guarantee.

A tag check does not require a const assertion or satisfies when an existing declared union already has the needed literal tags. Conversely, a broad flat property such as `mode: "read" | "write"` does not automatically connect an optional value to write mode. Representation and expression-level precision are separate review questions.

### 6) **Performance note**

The type composition and annotations erase. The spread in queue creates a new object, while tag comparisons, map reads/writes and the throwing helper remain JavaScript. These examples establish no dispatch-size threshold or checker-cost formula. A tag can serve a semantic need even for two variants; choosing it from an unmeasured speed claim would obscure that need.

### 7) **Mentor note**

Ask the reviewer to identify the evidence behind each of the four checklist questions in review.ts. A strong answer names the accepted fixtures, the narrowing path, the simultaneous audit requirement and the failing extension check. Require an explanation of the richer read fixture and the unsafe cast's runtime consequence as well.

For the delete exercise, a suitable implementation deletes the requested key and defines an explicit no-payload response. Verify read-after-delete and deletion of a missing key, then confirm that the sink remains. This tests an actual behavior change rather than completion of a formatting checklist.
