## 4.1. Unions, intersections, narrowing — checklist (mental models mentors insist on)

### 1) **Unions are checked by what is common — narrow first** (only shared members survive without a guard)

**Definition** — `A | B` exposes only the *intersection of its members' keys* (common properties) until you narrow — `if (x.kind === "a")` or `if ("x" in x)` proves the member — then exclusive members appear in that narrowed branch. The rule is the default safety gate — the checker blocks `u.exclusive` because `u` might be the member that lacks it.

**What problem it solves / history** — exposed-everything unions produced unchecked `undefined` reads — `string | { items: string[] }` read `items` on a `string` because the checker had no proof otherwise. The common-property gate (since TS 1.6) flipped the default to "prove which branch" — identical reasoning to `strictNullChecks` forcing `if (x !== null)` before `x.length`.

**Modern guidance** — as of TypeScript 5.9 era, never widen past the gate with `as` or `(x as A).field` — narrow with a runtime proof. For two-member primitive unions prefer `typeof`; for object unions prefer `in` or discriminant equality (`x.kind === "literal"`). The exclusive member is available *only* inside the narrowed block — exit the block and the type re-wide to `A|B` again.

**Runnable example** — gated access vs narrow-then-access (good vs bad, `tsc --strict`):

```typescript
type Circle = { kind: "circle"; radius: number; tag: string };
type Square = { kind: "square"; side: number; tag: string };
type Shape = Circle | Square;

function describe(shape: Shape): string {
  // good — common property always safe
  console.log(shape.tag); // both have tag

  // good — narrow then access exclusive
  if (shape.kind === "circle") return `r ${shape.radius}`; // narrowed to Circle
  return `s ${shape.side}`; // narrowed to Square
}
console.log(describe({ kind: "circle", radius: 2, tag: "geo" })); // r 2

// bad — widening past gate with cast
function describeBad(shape: Shape): string {
  return `${(shape as Circle).radius}`; // compiles even when shape is Square — wrong radius read
}
// fix — narrow first as above
```

**Common confusion** — "`shape.radius` is `number | undefined` so an if is not needed" — `radius` is *not* optional on the union — it is *absent* on Square — no `| undefined` synthesis — narrow, do not optional-chain around the gate. "`as` is narrowing" — `as` asserts without a runtime proof — exclusion is widening the current value is precisely what `typeof`/`in`/`===` proves.

**Performance note** — common-property gate is O(members × properties) per site — checker-only — zero emit. Runtime cost is the proving branch (`===`/`in`/`typeof`) — one equality per narrowing — trivial.

**Mentor note** — have students attempt `u.a` on `type U = { a: number } | { b: number }` — error TS2339 teaches the gate — fix with `if ("a" in u)` and show autocomplete narrows. Require this narrative in PRs that add union handlers.

### 2) **Tag unions when variants grow** (a `kind` literal scales better than `in` chains)

**Definition** — a *discriminated* union gives every member the same literal key with a distinct literal value — `kind: "circle" | "square" | "triangle"` — the checker splits on `switch(kind)` and exhaustive handling becomes proof — `in` chains degrade as variant count grows and when overlapping keys prevent the split.

**What problem it solves / history** — three object shapes where two share `width/height` cannot be split via `in` — `width` exists on both — `kind` disambiguates cheaply — one equality check per branch. As Redux/XState proved, adding a tagged variant to a union and letting `switch(kind)` plus `assertNever` guard every consumer scales horizontally without growing an inheritance tree (see [2.2. Abstract classes](<../../../06 Classes and Object-Oriented Types/sections/2. Inheritance and Polymorphism/2.2. Abstract classes and members when abstract beats interface.md>)).

**Modern guidance** — as of TypeScript 5.9 era, add a discriminant when the union reaches 3+ non-primitive members or when members overlap on every key except a tag — keep the discriminant top-level (flat `kind`, not `meta.kind.tag`). Derive the tag union from an `as const` source so the literal set and the runtime collection stay in sync (see [3.3. Literal types](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>)).

**Runnable example** — `kind` at scale vs `in` chain (good vs bad, `tsc --strict`):

```typescript
type Evt =
  | { kind: "click"; x: number; y: number }
  | { kind: "keydown"; key: string }
  | { kind: "scroll"; delta: number };

function handle(evt: Evt): string {
  switch (evt.kind) {
    case "click": return `click ${evt.x},${evt.y}`;
    case "keydown": return `key ${evt.key}`;
    case "scroll": return `scroll ${evt.delta}`;
  }
}
console.log(handle({ kind: "keydown", key: "Enter" })); // key Enter

// bad — in chain for 8 variants reads as ladder with subtle overlap risk
type Untagged = { radius: number } | { side: number } | { base: number; height: number };
// function classify(shape: Untagged): string { if ("radius" in shape) … else if ("side" in shape) … }
```

**Common confusion** — "every union needs `kind`" — `string | null` or `string | number` splits via `typeof`/`!== null` — tagging only scales object-shaped multi-variant unions. "`kind` must be `string`" — `kind` must be *narrow* literal — `kind: string` never splits; `kind: "circle" | "square"` does.

**Performance note** — one discriminant string per value — trivial. Dispatch cost is `switch(kind)` (engine jump-table optimization for 8+ literals) vs linear `in` chain — `switch` wins at scale. Checker cost identical.

**Mentor note** — extend an 8-variant event example with a new literal and show `never` sink (see [3.2](<../3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>)) failing — fixes must add the `case` — `in`-ladder has no such invariant.

### 3) **Intersections for composition, unions for alternatives** (if both, use `&`; if either, use `|`)

**Definition** — `A & B` asserts a value satisfies *both* shapes (augmentation, mixin, branding) — `type Audited<T> = T & { auditId: string }`; `A | B` asserts a value satisfies *either* shape (alternatives, modes) — `type Event = Click | Key`. Conflating them hides the modeling error with `never`: mixing discriminants via `&` builds `kind: never`, mixing co-present fields via `|` enables an illegal alternative.

**What problem it solves / history** — `FlatOptional = { mode: "a"|"b"; x?: number; y?: string }` conflated alternative with co-presence — `mode:"a"` without `x` compiled and failed inside the handler — discriminated union alternatives and intersected co-present fields separate the concerns explicitly (see [2.2. Impossible-state modeling](<../../2. Intersection Types/2.2. The never trap conflicting intersections and impossible states.md>)).

**Modern guidance** — as of TypeScript 5.9 era, ask "must a value have *both* slices or *one*?" — `&` for both (augment an already-decided shape with timestamps/brands), `|` for either (choose a branch/mode/variant). Hover every new composite — if an overlapped `kind` hovers as `never`, the operator choice was wrong — fix the operator, not the `as` silence.

**Runnable example** — operator choice signals intent (good vs bad, `tsc --strict`):

```typescript
type HasId = { id: string };
type User = HasId & { name: string }; // & — both — augmentation
const u: User = { id: "1", name: "Ada" };

type Click = { kind: "click"; x: number };
type Key = { kind: "keydown"; key: string };
type Evt = Click | Key; // | — either — alternative
const evt: Evt = { kind: "click", x: 1 }; // either active

// bad — chose & for alternatives → kind is never
type Confused = { kind: "click"; x: number } & { kind: "keydown"; key: string }; // kind never
// const c: Confused = { kind: "click", x: 1, key: "a" }; // error — Confused unreachable
// fix — union above (Evt) — either click or keydown, not both
```

**Common confusion** — "`&` merges values at runtime" — `&` asserts *both* type slices on one value — runtime merges are spread/`Object.assign` — `&` only asserts overlap — mismatch on literal discriminants collapses to `never` (see [2.2](<../../2. Intersection Types/2.2. The never trap conflicting intersections and impossible states.md>)). "`A | B` with overlapping keys is the same as `A & B`" — overlapping keys on `|` create an *either* over the union — no value carries both sets — `&` means a single value carries both — fundamentally different optionality models.

**Performance note** — both `&` and `|` erase — zero emit. Picking the right operator prevents hallucinated `never` traces and entanglement per PR that would require follow-up remaps — no runtime measure needed.

**Mentor note** — ask students: "must a value have `auditId` *and* base shape?" — answer `"&"` — vs "must a shape be a circle *or* a square?" — answer `"|"` — reduce the mistake to whether the answer satisfies both or either.

### 4) **Prove exhaustiveness with `never`** (every public union-typed switch/reducer gets a `never` sink)

**Definition** — after narrowing all known union members, assign the remaining value to `never` (or `return assertNever(value)`) — `default: return assertNever(shape);` inside `switch(kind)` — the checker errs iff a member remains — adding a Variant to the union without handling it blocks CI.

**What problem it solves / history** — `default: break` / `default: return staleState` swallowed new variants — the new `Shape` kind or `Action` type shipped with no error and stale state during the handler — `never` turns the omission into a compile error that the PR adding the Variant must fix (see [1.3 exhaustive hook preview](<../../1. Union Types/1.3. Literal unions enums vs unions and exhaustiveness preview.md>)).

**Modern guidance** — as of TypeScript 5.9 era, add a `never` sink to every `switch`/`if/else` over a *public* discriminated union or literal set whose members may grow — `Shape`, `Action`, `Status`, `Feature`. Use `function assertNever(x: never): never { throw new Error("Unexpected " + JSON.stringify(x)); }` at `default:` and import it everywhere. Skip the sink only for closed local splits (`string|number` within one function) where the set is clearly not growing — annotate the skip with a literal comment explaining "closed."

**Runnable example** — sink gates the next Variant PR (good vs bad, `tsc --strict`):

```typescript
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; side: number };

function assertNever(x: never): never { throw new Error(`Unexpected ${JSON.stringify(x)}`); }

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2;
    case "square": return shape.side ** 2;
    default: return assertNever(shape); // exhaustive — miss "triangle" stops the PR
  }
}

// bad — default returns valid value → new Variant swallowed
function areaBad(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2;
    case "square": return shape.side ** 2;
    default: return 0; // stale 0 when Shape gains new kind — no error issued
  }
}
```

**Common confusion** — "`default: break` is enough" — `break` leaves unhandled Variant to merge as valid path after `switch`; exhaustiveness requires `never` assigned from that merged path — `break` then `assertNever` outside switch also works but tail return is simpler. "`never` is a value returned" — you *assign* trailing narrowed type to `never`; return `never` is achieved by `assertNever` throwing — the `never` typed helper signals unreachable, not a tangible value.

**Performance note** — `never` assignments erase; `assertNever` emits only one `throw` helper — never taken on exhaustive success — zero cost on normal path.

Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>) for the branching story.
