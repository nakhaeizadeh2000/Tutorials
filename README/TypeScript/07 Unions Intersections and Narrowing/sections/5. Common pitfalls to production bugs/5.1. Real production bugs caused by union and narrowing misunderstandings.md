## 5.1. Real production bugs caused by union and narrowing misunderstandings

These are small, local reproductions of failure patterns that matter in application code, not claims about documented customer incidents. Each isolates what the type system rejected or trusted, the observable consequence and a repair. Use the linked owners for the full mechanism.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent TypeScript fence under its filename, compile with `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then run `node dist/FILE.js`. Activate each commented negative separately and check with the same flags plus `--noEmit` instead of `--outDir dist`.

### 1) **A shared-key check concealed the wrong mutation**

Both checkout and modal cards have a preview. Testing for that required shared key supplies no evidence that a card has a checkout URL. A cast can then permit the wrong write. The repair must also preserve the operation's meaning: updating a checkout URL must not replace an unrelated modal identifier.

Save as `cards.ts`.

```typescript
type Checkout = { preview: string; checkoutUrl: string };
type Modal = { preview: string; modalId: string };
type Untagged = Checkout | Modal;
function wrongUpdate(card: Untagged, url: string): void {
  if ("preview" in card) {
    // card.checkoutUrl = url; // TS2339: shared preview did not select Checkout
    (card as Checkout).checkoutUrl = url; // Deliberate bypass.
  }
}
const leaked: Modal = { preview: "sale", modalId: "m1" };
wrongUpdate(leaked, "/pay");
console.log("leaked:", leaked.modalId, Object.hasOwn(leaked, "checkoutUrl"));

type CheckoutCard = Checkout & { kind: "checkout" };
type ModalCard = Modal & { kind: "modal" };
type Card = CheckoutCard | ModalCard;
function updateCheckout(card: Card, url: string): void {
  const isCheckout = card.kind === "checkout";
  if (isCheckout) card.checkoutUrl = url; // The const condition retains this refinement.
}
const modal: ModalCard = { kind: "modal", preview: "sale", modalId: "m1" };
const checkout: CheckoutCard = { kind: "checkout", preview: "sale", checkoutUrl: "/old" };
updateCheckout(modal, "/pay"); updateCheckout(checkout, "/pay");
console.log("fixed:", modal.modalId, Object.hasOwn(modal, "checkoutUrl"), checkout.checkoutUrl);
function aliasBefore(card: Card): string {
  const alias = card;
  if (card.kind === "checkout") {
    // return alias.checkoutUrl; // TS2339: this separate alias was not refined by the original's guard
    const narrowed = card;
    return narrowed.checkoutUrl;
  }
  return card.modalId;
}
console.log(aliasBefore(checkout), aliasBefore(modal));
```

The output is `leaked: m1 true`, `fixed: m1 false /pay`, then `/pay m1`. The bad write adds a checkout field to the modal. The repaired operation updates only checkout cards and leaves the modal ID unchanged.

Do not generalize this into “aliases always lose narrowing.” The const condition above works on the unmodified parameter, while the separate object alias demonstrates a different relationship. [TypeScript 4.4](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-4.html#control-flow-analysis-of-aliased-conditions-and-discriminants) documents aliased-condition analysis. [Built-in narrowing](<../3. Control Flow Narrowing/3.1. Built-in narrowers typeof instanceof in and equality.md>) owns optional/shared/inherited-key distinctions; [tagged unions](<../1. Union Types/1.2. Discriminated unions the tagged pattern that scales.md>) owns representation choices. An exclusive-key check may also be appropriate when the producer's untagged contract already supplies that distinction.

### 2) **An impossible intersection was mistaken for runtime dispatch control**

Purchase and view are alternatives. Intersecting their incompatible tags reduces the entire type to `never`. That blocks ordinary construction and property access. It does not unregister a handler, remove emitted code or prevent a value forced through an assertion from reaching a function.

Save as `impossible.ts`.

```typescript
type Purchase = { kind: "purchase"; sku: string };
type View = { kind: "view"; id: string };
type BadInput = Purchase & View;
type Expect<T extends true> = T;
type WholeIsNever = Expect<[BadInput] extends [never] ? true : false>;
// const bad: BadInput = { kind: "purchase", sku: "A", id: "1" }; // TS2322
// function sibling(input: BadInput) { return input.sku; } // TS2339: whole type is never
function mistakenlyTyped(_input: BadInput): string { return "handler ran"; }
const forced = { kind: "purchase", sku: "A" } as unknown as BadInput;
console.log(mistakenlyTyped(forced)); // The function still executes.

type UserEvent = Purchase | View;
function handle(event: UserEvent): string {
  switch (event.kind) {
    case "purchase": return `purchase ${event.sku}`;
    case "view": return `view ${event.id}`;
    default: { const complete: never = event; throw new Error("Unhandled event"); }
  }
}
console.log(handle({ kind: "purchase", sku: "A" }), handle({ kind: "view", id: "v1" }));
```

The output is `handler ran`, then `purchase A view v1`. Repair the modeling operator and check real fixtures. Do not use an ambient declaration or cast as evidence that a valid intersection fixture exists. The [never-trap owner](<../2. Intersection Types/2.2. The never trap conflicting intersections and impossible states.md>) demonstrates safe type-level probes and retained ambient reads; [intersection fundamentals](<../2. Intersection Types/2.1. Intersection fundamentals merging object shapes.md>) distinguishes ordinary field conflicts and interface diagnostics. Here the error is a wrong contract, not automatic runtime suppression.

### 3) **A permissive fallback mislabeled a new status**

A fallback returning an ordinary success label can make an unhandled status look valid. The code still returns string on every path, so a missing-return check cannot expose that policy error. A never sink makes a remaining declared status a compiler error instead.

Save as `statuses.ts`.

```typescript
type APIStatus = "success" | "pending" | "failed" | "retrying";
function assertNever(_value: never): never { throw new Error("Unhandled status"); }
function wrongSummary(status: APIStatus): string {
  switch (status) {
    case "success": return "ok";
    case "pending": return "waiting";
    case "failed": return "error";
    default: return "ok";
  }
}
function summary(status: APIStatus): string {
  switch (status) {
    case "success": return "ok";
    case "pending": return "waiting";
    case "failed": return "error";
    case "retrying": return "waiting for retry";
    default: return assertNever(status);
  }
}
for (const status of ["success", "pending", "failed", "retrying"] as const) {
  console.log(status, wrongSummary(status), summary(status));
}
```

The lines are `success ok ok`, `pending waiting waiting`, `failed error error`, then `retrying ok waiting for retry`. To expose the omission statically, remove `summary`'s retrying case: TS2345 identifies the remaining status at `assertNever`. Add `| "confirming"` to `APIStatus` instead and the same sink rejects the new member, while wrongSummary still accepts it.

Choose a fallback deliberately for handlers that are meant to ignore unrelated inputs. This summarizer needs behavior for every status, so treating retry as success violates its contract. [Exhaustiveness](<../3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>) owns the full static-coverage/runtime-fallback distinction. External status strings still need parsing before this handler; the union annotation does not validate the wire format.

### 4) **A published boolean omitted the caller's narrowing contract**

A correct boolean selection can be useful without being a predicate. The problem arises when a consumer expects a type refinement that the published signature does not advertise, then adds casts to compensate. Eligible unannotated functions can infer predicates on the current baseline; requiring every reusable guard to spell `is` is outdated.

Save as `published.ts`.

```typescript
function booleanPresent(value: string | null): boolean { return value !== null; }
function explicitPresent(value: string | null): value is string { return value !== null; }
const inferredPresent = (value: string | null) => value !== null;
const inputs: (string | null)[] = ["", "Ada", null];
const plain = inputs.filter(booleanPresent);
const explicit = inputs.filter(explicitPresent);
const inferred = inputs.filter(inferredPresent);
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Plain = Expect<Equal<typeof plain, (string | null)[]>>;
type Explicit = Expect<Equal<typeof explicit, string[]>>;
type Inferred = Expect<Equal<typeof inferred, string[]>>;
// plain.map(value => value.toUpperCase()); // TS18047: published boolean supplied no refinement
console.log(plain.length, explicit.map(value => value.length).join(","), inferred.map(value => value.length).join(","));
```

The output is `2 0,3 0,3`. Runtime selection is correct in all three cases and preserves the empty string. Only two signatures advertise the non-nullish type relationship. Publish an honest predicate when consumers need that relationship, retain boolean for a selection rule, or use a direct local check. Do not mechanically rewrite every boolean-returning function to a predicate: an extra business condition can invalidate its false-case claim.

[Custom guards](<../3. Control Flow Narrowing/3.3. Custom narrowers predicates asserts and type guards on unions.md>) owns the partial-selection failure and assertion alternative; [callable guards](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.3. Type guards predicates asserts and satisfies on functions.md>) owns inferred-signature conditions. The [primary 5.5 explanation](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-5.html#inferred-type-predicates) supports the inference used here.

### 5) **Common confusion**

A runtime misbehavior needs an executed path. An impossible alias alone does not demonstrate a silenced handler, and a missing narrowing signature alone does not prove that the function returns the wrong boolean. The reproductions distinguish the compiler's rejected operation, a deliberate checking bypass and the actual resulting behavior.

A repair must preserve domain meaning as well as compile. Assigning a URL to modalId would satisfy its string annotation but still update the wrong concept. Check the preserved values and changed values, not just whether both branches contain an assignment.

### 6) **Performance note**

The type signatures erase; mutation, guards, filters and handler calls remain. In particular, a forced never input does not suppress the function call. These cases measure correctness outcomes, not guard speed or checker complexity. The important operational distinction is whether a path reports an unexpected state, returns a misleading success or writes unintended data; timing claims would require a separate workload and measurement.

### 7) **Mentor note**

For each failure, ask for the trigger, the missing evidence, the observed consequence and the smallest repair that preserves the intended operation. Have the learner activate the rejected line before examining the cast that concealed it. Then run both a formerly failing fixture and an unaffected fixture against the repair.

For a regression exercise, add confirming to the status set and implement a waiting-for-confirmation label. The sink should fail before the repair, every existing status should keep its label afterward, and confirming should receive its explicit label. This is a behavior requirement, not permission to erase the compiler error with a cast or generic success fallback.
