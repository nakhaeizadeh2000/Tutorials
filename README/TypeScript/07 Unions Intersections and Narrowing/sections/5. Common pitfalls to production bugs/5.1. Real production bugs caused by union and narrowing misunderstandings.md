## 5.1. Real production bugs caused by union and narrowing misunderstandings

### 1) **`in` check without discriminant caused alias narrowing to misfire** (common property narrowed the wrong branch and mutated the wrong shape)

**Definition** — an `in` guard (`"shared" in x`) narrows `x` only when the checked key is *exclusive* to one member — when both members share the same property (e.g., both have `preview?: string`), the `in` check does not split — and aliasing `x` before narrowing loses the narrowed proof after the assignment.

**What problem it solves / history** — a production patch where `type Card = { preview: string; checkoutUrl: string } | { preview: string; modalId: string }` used `if ("preview" in card)` to isolate the first branch — but both branches have `preview`, so the guard kept both members — then mutating `checkoutUrl` on what might have been `modalId` wrote to a field that did not belong to that variant — runtime produced a phantom `checkoutUrl` entry on the wrong card type and broke downstream lookup.

**Modern guidance** — as of TypeScript 5.9 era, never rely on `in` over a *common* key — add a `kind` discriminant for any union where a key appears on every branch — `type CheckoutCard = { kind: "checkout"; preview: string; checkoutUrl: string }`. When `in` is used over an exclusive key, narrow first and bind the aliased variable *inside* the narrowed block — not before — so reassignment does not escape the proof.

**Runnable example** — common `in` that fails to split, fixed with `kind` (good vs bad, `tsc --strict`):

```typescript
// bad — 'in' over common key does not isolate branch — wrong mutation stays unsplit
type Checkout = { preview: string; checkoutUrl: string };
type Modal = { preview: string; modalId: string };
type CardBad = Checkout | Modal;

function mutateBad(card: CardBad, url: string): void {
  if ("preview" in card) {
    // 'preview' is on both members — narrowing does not refine Checkout vs Modal
    // card is still CardBad — touching checkoutUrl might be touching Modal
    (card as Checkout).checkoutUrl = url; // compiles via cast, wrong when card is Modal
  }
}
const modalBad: CardBad = { preview: "sale", modalId: "m1" };
mutateBad(modalBad, "https://pay.example.com");
console.log(modalBad); // { preview: 'sale', modalId: 'm1', checkoutUrl: 'https://...' } — wrong shape leaked

// good — discriminant-carrying union; equality on kind splits correctly
type CheckoutGood = { kind: "checkout"; preview: string; checkoutUrl: string };
type ModalGood = { kind: "modal"; preview: string; modalId: string };
type Card = CheckoutGood | ModalGood;

function mutate(card: Card, url: string): void {
  if (card.kind === "checkout") {
    card.checkoutUrl = url; // narrowed to CheckoutGood — only that branch carries checkoutUrl
  } else {
    card.modalId = url; // narrowed to ModalGood
  }
}
const modal: Card = { kind: "modal", preview: "sale", modalId: "m1" };
mutate(modal, "https://pay.example.com");
console.log(modal); // { kind: 'modal', preview: 'sale', modalId: 'https://...' } — correct branch mutated
```

**Common confusion** — "`in` proves a *value* is there" — `in` proves *key presence*, not member identity — if every member has `preview`, `"preview" in card` proves nothing about which branch. "Casting after `in` is still narrowing" — `as Checkout` inside the block silences the checker but does not carry the proof after the condition — any reassignment before narrowing loses the connection — bind after guard.

**Performance note** — discriminant read is one property + `===`; shared-key `in` is one prototype-key check — runtime indistinguishable — the bug cost is that a misfire writes a phantom key into a JSON payload that a consumer reads — far exceeds guard style choice.

**Mentor note** — ask "which key proves which branch?" — answer is an *exclusive* key or `kind` — ask after a code snippet that uses `in` over a common field — trace the two call sites that passed `page.checkoutUrl` into a modal to reproduce the payload leak — show fix via refactor to `kind`.

### 2) **Conflicting intersection collapsed to `never` and silenced a handler** (dead branch never ran; no error until new variant shipped)

**Definition** — `type HandlerInput = Circle & Square` yields `kind: never` — the composite is impossible to construct — a handler typed for `HandlerInput` is typed with `never` on the discriminant, so its branch logic is unreachable (dead code) — the build passes, but the live code never invokes that handler as it matches no real payload, and a new variant's handler was silently omitted because the signature consumed the old impossible composite.

**What problem it solves / history** — an ingestion service typed a runtime union incorrectly as `type UserEvent = Purchase & View` (both were alternatives) — every `switch` on `event.kind` had discriminants collapsed to `never` inside `UserEvent`, handlers for purchase and view compiled due to cast-laundering, but when `"refund"` variant arrived, the handler registry still used the old `UserEvent` type — refund was never registered and fell through to default stale cart — users saw missing refund entries in their history.

**Modern guidance** — as of TypeScript 5.9 era, treat hovering `never` on a freshly defined `A & B` as a red flag — search for `|` where `&` was written when the two sides were meant to be alternative branches — pick `|`. Hover every new composite and demand that no property reads `never`; silence requires union alternatives — a trailing construction probe (`declare const probe: T`) that type-checks with a `kind:"a"` literal fails immediately when the composite collapses to `never` (see [2.2 early-detection](<../../2. Intersection Types/2.2. The never trap conflicting intersections and impossible states.md>)).

**Runnable example** — never-collapsed handler and fixed union handler (good vs bad, `tsc --strict`):

```typescript
type Purchase = { kind: "purchase"; sku: string };
type View = { kind: "view"; id: string };
type BadRegistry = Purchase & View; // kind never — handler typed over this is dead branch logic
// const bad: BadRegistry = { kind: "purchase", sku: "A", id: "1" }; // error TS2322: "purchase" not assignable to never

// good — alternative union, registry remains live, new variant extends the union, not a collapsed intersect
type UserEvent = Purchase | View;
function handle(event: UserEvent): string {
  switch (event.kind) {
    case "purchase": return `purchase ${event.sku}`;
    case "view": return `view ${event.id}`;
  }
}
handle({ kind: "purchase", sku: "A" });
handle({ kind: "view", id: "v1" });

type Purchase2 = Purchase;
type Refund = { kind: "refund"; sku: string; reason: string };
type AllEvents = UserEvent | Refund;
function handleAll(event: AllEvents): string {
  switch (event.kind) {
    case "purchase": return `purchase ${event.sku}`;
    case "view": return `view ${event.id}`;
    case "refund": return `refund ${event.sku}`;
  }
}
console.log(handleAll({ kind: "refund", sku: "A", reason: "broken" })); // refund A

// bad — kept the old & registry, refund path never reachable
function handleAllBad(event: AllEvents): string {
  // a handler that still thinks its argument is BadRegistry typed dead branch, not refund
  return "silenced"; // dead branch never exercised — refund return never produced
}
```

**Common confusion** — "`never` on kind means whole type empty" — siblings survive (`sku`, `id`), but `kind` can never be satisfied — handler silently dead — lecture price. "The type line should have errored" — `type Bad = A & B` never errors alone — laziness is deliberate — only construction proves conflict — probe or `interface extends` surfaces.

**Performance note** — `never` collapse is checker-only — zero emit — no runtime cost — but handler silencing produced a customer-facing missing-history regression without compile signal — far exceeds misfire cost.

**Mentor note** — drill hovers after any intersecting composite: point out `never`, ask "what runtime value could be both?" — answer none → fix. Use `interface Conf extends A, B {}` to demonstrate early TS2430 reporting alternative (see [2.1](<../../2. Intersection Types/2.1. Intersection fundamentals merging object shapes.md>)).

### 3) **Exhaustiveness without `never` let a new API status fall through `default: break`** (reducer returned stale state; no compile error)

**Definition** — reducer `switch` over `APIStatus` had `default: break` / `default: return existingState` that swallowed a new variant (`"retrying"`) — `statusSummary("retrying")` fell to the default and returned the fallback branch, never exercising the specialized retry state for the UI — `never` sink would have blocked the PR adding the variant until the handler registered the case.

**What problem it solves / history** — growing API status machine where product added `"pending_confirmation"` — response now carried it — the summarizer still had `default: return { label: "ok", color: "green" }` and rendered the confirmation page with green-ok styling instead of amber awaiting — user shipped tricked into believing confirmation succeeded — downstream relied on unprotected default rather than the exhaustiveness contract.

**Modern guidance** — as of TypeScript 5.9 era, every `switch(kind)` over an exported discriminated union or literal set that may grow gets `default: return assertNever(value)` — never `default: break` — `assertNever` forces the PR adding the variant to add the case or CI fails — missing-case bugs become unshippable at PR gate, not post-ship triage.

**Runnable example** — missing `retrying` without never falls through (good vs bad, `tsc --strict`):

```typescript
type APIStatus = "success" | "pending" | "failed" | "retrying";
function assertNever(x: never): never { throw new Error(`Unexpected ${JSON.stringify(x)}`); }

// bad — missing case fell through default with stale return
function statusSummaryBad(status: APIStatus): string {
  switch (status) {
    case "success": return "ok";
    case "pending": return "waiting";
    case "failed": return "error";
    default: return "ok"; // when 'retrying' added to APIStatus, it silently became 'ok' — no compile error
  }
}
console.log(statusSummaryBad("retrying")); // ok — wrong, should be waiting for retry

// good — exhaustive sink gates the new variant
function statusSummary(status: APIStatus): string {
  switch (status) {
    case "success": return "ok";
    case "pending": return "waiting";
    case "failed": return "error";
    case "retrying": return "retrying…";
    default: return assertNever(status); // if 'retrying' were not cased, this line would error and block PR
  }
}
console.log(statusSummary("retrying")); // retrying… — explicit handling required

// good — if/else variant with trailing assert
function summaryElse(s: APIStatus): string {
  if (s === "success") return "ok";
  if (s === "pending") return "waiting";
  if (s === "failed") return "error";
  if (s === "retrying") return "retrying…";
  const _e: never = s; // proves no member remains
  return assertNever(_e);
}
```

**Common confusion** — "`default: break` is enough" — `break` leaves the merged path open — missing variant inherits whatever lies after `switch` — silent regression — `assertNever` converts the path into a compile error. "`never` is a value returned" — you assign remaining narrowed type to `never`; `assertNever` returns `never` via `throw` — you do not construct or return a value.

**Performance note** — `assertNever` is never-executed under exhaustiveness — one throw helper — zero cost on normal path — wins by preventing missing-case regression plus the debugging/triage of a shipped bug at production latency.

**Mentor note** — extend `APIStatus` with `"confirming"` without updating `statusSummaryBad` to illustrate missing error — then show `statusSummary` with sink blocks PR — students experience the PR gate vs shipped bug — test.

### 4) **Predicate returned `boolean` instead of `x is T` so narrowing never happened downstream** (guard looked correct; the checker never narrowed)

**Definition** — call-site narrowing requires `x is T` tag on the return type — `function isCircle(s: Shape): boolean` checks the same condition as `shape is Circle` version but never narrows callers — every branch after `if (isCircle(shape))` must still cast `shape as Circle` to recover `radius`.

**What problem it solves / history** — shared validator library exported `isValidEmail(v: string | null): boolean` — pagination util downstream had `if (isValidEmail(email)) send(email)` but checker still forced `as string` — new validation branch inside predicate added `"email" in v` path but downstream missed the second narrowing because `boolean` returned never communicated the proof — handler shipped with hidden `as` that crumbled on masked custom email type.

**Modern guidance** — as of TypeScript 5.9 era, write predicates with `param is Member` return for union guards reused across sites — keep the body sound (throw/else branch covers complement) and pair with `asserts` only when fallthrough must throw. Keep predicates single-purpose: asserting multiple predicates at once breaks the branching contract for `if/else` chains — one predicate per member, or discriminate directly with `kind ===`.

**Runnable example** — predicate without `is` blocks callers, fixed narrow propagates (good vs bad, `tsc --strict`):

```typescript
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Shape = Circle | Square;

// bad — returns boolean, not narrowed checker proof
function checkCircleBad(shape: Shape): boolean {
  return shape.kind === "circle";
}
function areaBad(shape: Shape): number {
  if (checkCircleBad(shape)) {
    // shape still Shape — not narrowed — must cast
    return Math.PI * (shape as Circle).radius ** 2; // hidden cast laziness
  }
  return (shape as Square).side ** 2;
}

// good — returns predicate, caller narrowed automatically
function isCircle(shape: Shape): shape is Circle {
  return shape.kind === "circle";
}
function area(shape: Shape): number {
  if (isCircle(shape)) return Math.PI * shape.radius ** 2; // narrowed to Circle — radius available
  return shape.side ** 2; // narrowed to Square
}
console.log(area({ kind: "circle", radius: 3 })); // 28.27...

// good — assertion variant for invariant path, no if wrapper
function assertIsCircle(s: Shape): asserts s is Circle {
  if (s.kind !== "circle") throw new Error(`Expected circle, got ${s.kind}`);
}
function radiusOf(shape: Shape): number {
  assertIsCircle(shape);
  return shape.radius; // narrowed after call returns
}
console.log(radiusOf({ kind: "circle", radius: 2 })); // 2
```

**Common confusion** — "boolean return narrows, just implicitly" — only `x is T` narrows callers — `boolean` leaves caller type unchanged — require cast/extra `if`. "`asserts` does the same" — `assert` returns `void` and narrows post-call; `predicate` returns `boolean` and narrows both branches — use `assert` when non-member should throw instead of reaching else.

**Performance note** — predicates emit as plain functions checking property equality — identical runtime to inline `if (x.kind==="a")` — reusable check without extra cost. Checker cost per predicate call is one narrowing walk — trivial; sharing predicates eliminates re-duplicated branching logic in `switch`.

**Mentor note** — show diff: `function isCircle(...): boolean` vs `function isCircle(...): shape is Circle` — diff is two words in the return type — impact is whether every `if (isCircle(...))` block retains narrowing — exercise: review shared validators and grep `): boolean` — ask whether those predicate-shaped functions should be `is T` — fix two across codebase.
