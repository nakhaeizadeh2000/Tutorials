## 2.1. Intersection fundamentals — merging object shapes

### 1) **What `A & B` means** (set intersection — a value is both — the composition glue)

**Definition** — `type C = A & B` is the set intersection of `A` and `B` — a value of `C` satisfies *both* `A` and `B` simultaneously. For object types that means every required property from both sides must be present: `{ a: string } & { b: number }` is `{ a: string; b: number }`. For unions of objects, `&` distributes narrowing; for primitives, `&` often collapses to `never` (see [2.2. The never trap](<./2.2. The never trap conflicting intersections and impossible states.md>)).

**What problem it solves / history** — class inheritance modeled "both" via `class C extends A, B` (JavaScript only supports single `extends`), and mixin helpers copied properties at runtime with no checker proof. Intersections (added with unions in TS 1.4) reified "both" as a type — `Timestamped<T> = T & { createdAt: Date }` and `WithId = Entity & { id: string }` became checkable compositions without an inheritance chain. Like unions, `&` erases — zero emit — and scales to stacking (see [2.3. Unions and intersections distributive behavior](<./2.3. Unions and intersections distributive behavior and primitive intersections.md>)).

**Modern guidance** — as of TypeScript 5.9 era, use `&` for *composition* — "add fields to a shape" — `type User = Person & { role: Role }`, `type Audited<T> = T & { audit: AuditTrail }`. Compose at the type level, not via class extends, when the composite is data without shared construction logic. Prefer `&` on object shapes and literal-aware forms; avoid `&` mixing unrelated primitives (it becomes `never` silently).

**Runnable example** — intersection as composition (good vs bad, `tsc --strict`):

```typescript
// good — intersection merges object shapes; merged hover shows both sides
type HasId = { id: string };
type HasName = { name: string };
type User = HasId & HasName; // { id: string; name: string }
const user: User = { id: "42", name: "Ada" };
console.log(user.id, user.name); // 42 Ada

// good — stacking intersections via factory (the T & Audit pattern)
type Timestamped = { createdAt: Date; updatedAt: Date };
type Auditable<T> = T & Timestamped; // add audit to any shape
function withTimestamps<T extends object>(obj: T): Auditable<T> {
  const now = new Date();
  return { ...obj, createdAt: now, updatedAt: now };
}
const audited = withTimestamps({ id: "1", title: "Post" });
console.log(audited.id, audited.createdAt.toISOString().length > 0); // true

// good — branded composition (the approved intersection for nominal safety)
type Brand<Tag extends string> = { __brand: Tag };
type UserId = string & Brand<"UserId">; // primitive & brand still composes
function makeUserId(raw: string): UserId { return raw as UserId; }
console.log(makeUserId("u1"));

// bad — intersection of incompatible primitives is never (no value can be both)
type Impossible = string & number; // never — no value satisfies both
// const x: Impossible = "hi"; // error TS2322: string not assignable to never
// fix — pick union (|) for alternatives, intersection (&) only for overlapping object sets
type Either = string | number; // either, not both
const y: Either = "hi"; // ok

// good — compatible overlap merges narrowly
type A = { kind: "a"; value: string };
type B = { common: number };
type AB = A & B; // { kind: "a"; value: string; common: number }
const ab: AB = { kind: "a", value: "x", common: 1 };
console.log(ab.kind, ab.common); // a 1
```

**Common confusion** — "`&` merges values at runtime" — `&` does not merge objects at runtime — it asserts that a single *value* satisfies both type shapes — spreading `{ ...a, ...b }` is the runtime merge, `A & B` is its type. "`A & B` is always larger than `A`" — for object types it is *larger* (more requirements), but for primitives it can be `never` — intersection's size depends on overlap, not on operator alone. "`extends` is the same as `&` for classes" — for `interface C extends A, B` and `type C = A & B` the *shape* often matches, but error messages and conflict handling diverge (see [2.1. Intersection vs extends](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>)).

**Performance note** — `&` erases — zero emit, no helper, no wrapper. Checker cost is O(members × properties) per intersection — merging 4 object types each with 10 keys walks ~40 keys — cheap. For large intersections built via `type Big = A & B & C & D & …`, the hover type can become very long — prefer a named intermediate (`type WithAudit = T & Timestamped`) over an inline 8-way `&` to keep hovers readable and diagnostics fast.

**Mentor note** — ask students to read the hover on `User = HasId & HasName` — they expect `HasId & HasName` to stay as-is — show that the hover expands to `{ id: string; name: string }` — teaches that `&` on objects *is* property accumulation, not a deferred generic. Contrast with `string & number` hovering as `never` — why object merges succeed and primitive merges collapse.

### 2) **Merging object types** (`{a: string} & {b: number}` → `{a: string; b: number}` — reading the hover)

**Definition** — `&` on two object types concatenates their required members — `{ a: string } & { b: number; c?: boolean }` yields `{ a: string; b: number; c?: boolean }` — overlapping keys that are *compatible* merge to their intersection, overlapping keys that *conflict* collapse to `never` on that key (see [2.2](<./2.2. The never trap conflicting intersections and impossible states.md>)). The resulting type is checked structurally (see [1.1. Structural assignability](<../../../02 The Type System Core/sections/1. Structural typing/1.1. Structural assignability shape not name.md>)) — any value assignable to *both* sides satisfies the intersection.

**What problem it solves / history** — `Object.assign({}, a, b)` and `{ ...a, ...b }` have always merged data at runtime — the checker needed a type for the merge result without requiring a new interface per combination. `A & B` fills that role — `type Merged = A & B` is the type of `merge(a,b)` when the merge keeps both sets of keys — composable, inspectable in hovers, and erasable without emit.

**Modern guidance** — as of TypeScript 5.9 era, use `&` to type merges *where the result really has both sets of keys* — API augmentation (`Base & { extra: string }`), plugin extension (`Config & PluginConfig`), and audit/metadata layering (`T & Timestamps`). When merging overlapping keys, ensure the overlapping type narrows, not conflicts — `{ role: string } & { role: "admin" | "viewer" }` narrows to `"admin" | "viewer"` — `{ role: "admin" } & { role: "editor" }` collapses to `never` on `role`. Keep overlapping merges explicit in review comments.

**Runnable example** — compatible merge vs conflict (good vs bad, `tsc --strict`):

```typescript
// good — compatible overlap narrows
type Base = { role: string };
type Narrowed = Base & { role: "admin" | "viewer" }; // role is "admin"|"viewer"
const n: Narrowed = { role: "admin" }; // ok
// const badRole: Narrowed = { role: "editor" }; // error TS2322

// good — disjoint parts compose into one shape
type Click = { kind: "click"; x: number; y: number };
type Audited = { auditId: string; ts: number };
type AuditedClick = Click & Audited; // { kind: "click"; x,y; auditId, ts }
const evt: AuditedClick = { kind: "click", x: 1, y: 2, auditId: "a1", ts: Date.now() };
console.log(evt.kind, evt.auditId); // click a1

// good — spread is the runtime dual of &
function merge<A extends object, B extends object>(a: A, b: B): A & B {
  return { ...a, ...b } as A & B;
}
const merged = merge({ id: "1" }, { name: "Ada" }); // { id: string } & { name: string }
console.log(merged.id, merged.name); // 1 Ada

// bad — conflicting discriminant merge collapses to never
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Confused = Circle & Square; // { kind: never; ... } — whole hover is never for kind
// const c: Confused = { kind: "circle", radius: 2, side: 4 }; // error TS2322: kind "circle" not assignable to never
// fix — use union (|) for alternatives, & only for co-present fields

// good — object & index signature widens exactness intentionally
type Strict = { id: string };
type Loose = Strict & Record<string, unknown>; // id plus any extras
const loose: Loose = { id: "1", extra: 42 }; // ok — extra allowed via index signature
console.log(louseId(loose)); // helper to show id preserved
function louseId(x: Loose): string { return x.id; }
```

**Common confusion** — "hover shows `never`, so the whole type is empty" — only the *conflicting property* becomes `never`; siblings survive — `({ kind: "a" } & { kind: "b" } & { id: string })` hovers with `kind: never` but `id: string` still present — the branch is impossible to construct, not absent. "`A & B` is like spread order" — spread order determines *which value wins* at runtime when keys collide; `&` on conflicts yields `never` regardless of order — the runtime merge and the type merge diverge on collisions — reason about collisions explicitly. "Mixin should `extend`, not `&`" — for data, either is readable; for error quality and `interface` merges, `extends` traces conflict earlier (see [2.1. Intersection vs extends](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>)).

**Performance note** — object-merge intersection is checker-only — spread `{ ...a, ...b }` allocates one new object at runtime (O(keys) copy), the `&` type adds zero. Checker cost scales with total key count — a 4-way intersection with 10 keys each is ~40 key walks per site — still fast. For very wide intersections (20+ `&` operands) the hover grows and diagnostic paths lengthen — alias intermediate intersections (`type Mid = A & B; type Big = Mid & C & D`) to keep hovers and `--extendedDiagnostics` traces readable.

**Mentor note** — demo the hover split: present `{ a: string } & { b: number; c?: boolean }` and ask what the hover shows — answer is `{ a: string; b: number; c?: boolean }` — then mutate to conflicting `{ kind: "a" } & { kind: "b" }` and show `never` — ask why `kind` never appears — because no runtime string can be both `"a"` and `"b"`.

### 3) **Intersections vs `extends`** (when `type C = A & B` and `interface C extends A, B` diverge)

**Definition** — `interface C extends A, B { extra: string }` and `type C = A & B & { extra: string }` often describe the same *shape* — both require `A`'s members, `B`'s members, and `extra`. Differences surface on conflicts and diagnostics: `extends` reports *at the interface declaration* which key conflicts (`interface C extends A { x: string }` where `A` already has `x: number` → `TS2430`), while `A & B` defers the conflict to the *use site* as `never` on the key and may stay silent until someone constructs a value.

**What problem it solves / history** — `interface` `extends` predates `&` as the composition mechanism — it modeled inheritance chains with declaration merging and early conflict reporting. `type` `&` added lightweight, non-nominal composition for any shape — object, primitive, union — without merging. Choosing between them is choosing *when* you want the conflict reported and *how* the hover reads.

**Modern guidance** — as of TypeScript 5.9 era, prefer `interface extends` for *named, public, augmentable contracts* — the error site is the `interface` line, not a distant `const c: A & B = { … }`. Prefer `type &` for *ad-hoc, local, or primitive-involving compositions* — `Branded<T> = T & { __brand: Tag }`, `Audited<T> = T & Timestamps`, or `type Mixed = string & { trimmed: true }` (see [1.3. Interfaces vs type aliases](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.3. Interfaces vs type aliases when to use which.md>)). Never mix them to hide a conflict — a conflicting `extends` must be fixed at the `interface`, a conflicting `&` that hovers as `never` must be fixed at the composition, not with `as`.

**Runnable example** — error timing differs (good vs bad, `tsc --strict`):

```typescript
// good — interface extends reports conflict early at declaration
interface HasNumber { value: number; }
interface HasString { value: string; }
// interface ConflictExtends extends HasNumber, HasString {} // error TS2430: value incompatibility reported HERE

// good — type intersection defers conflict to usage (never on value)
type HasNumberT = { value: number };
type HasStringT = { value: string };
type ConflictViaAnd = HasNumberT & HasStringT; // { value: never }
const x: ConflictViaAnd = { value: "hi" as never }; // construct impossible; never signals bug
// const y: ConflictViaAnd = { value: 42 }; // error — 42 not assignable to never

// good — choose extends for public contract so team sees error at the boundary
interface Timestamped { createdAt: Date; }
interface Named { name: string; }
interface AuditedUser extends Timestamped, Named { id: string; } // clean, reported at interface
const auditedUser: AuditedUser = { name: "Ada", id: "1", createdAt: new Date() };
console.log(auditedUser.name);

// good — choose & for ad-hoc local composition
type Local = { id: string } & { tag: "local" }; // local, no interface needed
const local: Local = { id: "42", tag: "local" };
console.log(local.tag); // local

// bad — conflicting & hidden with 'as' silences never
type Bad = { kind: "a" } & { kind: "b" }; // { kind: never }
const bad = { kind: "a" } as unknown as Bad; // compiles, but kind is never — downstream never branches
// fix — use | for alternatives, not & for exclusive kinds
type Good = { kind: "a"; a: number } | { kind: "b"; b: number };
const good: Good = { kind: "a", a: 1 }; // ok
```

**Common confusion** — "type `A & B` and `interface extends` are interchangeable" — shapes often match, diagnostics do not — `extends` fails at the `interface`, `&` fails at the value — choose by *where* you want the error. "`&` is always better because it works for everything" — `&` on classes can mean something different from `extends` on instances (see [2.1. Extends implements](<../../../06 Classes and Object-Oriented Types/sections/2. Inheritance and Polymorphism/2.1. Extends implements and structural class compatibility.md>)); keeping `extends` for declared contracts makes ownership clearer. "I can `as` past the `never` conflict" — `as unknown as NeverIntersection` silences the checker but the `never` branch remains impossible to satisfy — callers that narrow on the conflicting discriminant still enter dead code at runtime.

**Performance note** — `interface extends` and `type &` both erase — zero emit. Diagnostics cost differs: `extends`冲突 detection is O(members) at the `interface` declaration (early); `&` conflict as `never` is cheap until a value is assigned, then the assignment walk also costs O(members). Early reporting (`extends`) shortens the error trace (one line vs one value site plus hover) — use it when the error should block the PR that *declares* the composite, not the PR that *uses* it once.

**Mentor note** — exercise: give two interfaces with conflicting `value: number` vs `value: string`, ask to predict whether `interface C extends A,B` compiles and whether `type C = A & B` hover shows `never` — answer is both encode the same conflict, only the locus differs. Review gate: forbid `as unknown as T` to silence `never` on intersections — require `|` vs `&` fix instead.
