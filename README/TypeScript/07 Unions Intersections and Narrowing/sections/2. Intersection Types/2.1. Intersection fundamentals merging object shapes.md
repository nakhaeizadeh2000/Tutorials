## 2.1. Intersection fundamentals — merging object shapes

### 1) **An intersection requires one value to satisfy both operands**

`A & B` describes values meeting both requirements. For compatible object contracts, this can mean a value needs both id and name. Adding requirements narrows the set of acceptable values even though it gives a consumer more known members to use. It does not allocate, merge or modify an object.

Use TypeScript **7.0.2** and Node **20.20.2**, verified 2026-10-15. Save each named program in a fresh directory without tsconfig.json. Build with `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then execute `node dist/FILE.js`. For a commented negative, activate only that line in a separate copy and replace `--outDir dist` with `--noEmit`. Intentional runtime failures are caught.

Save `requirements.ts`:

```typescript
export {};
type HasId = { id: string };
type HasName = { name: string };
type User = HasId & HasName;
const user: User = { id: "u1", name: "Ada" };
const idView: HasId = user;
const nameView: HasName = user;
console.log(user.id, user.name, idView === user && nameView === user);
type NarrowRole = { role: string } & { role: "admin" | "viewer" };
const role: NarrowRole = { role: "admin" };
console.log(role.role);
// const missing: User = { id: "u2" }; // TS2322: both requirements must be met.
// const wrongRole: NarrowRole = { role: "editor" }; // TS2322.
```

Build and execution exit 0; output is `u1 Ada true`, then `admin`. The two typed views refer to the same object. Its initializer created the fields; the intersection only checks the contract. The compatible role overlap narrows the permitted values rather than choosing whichever operand appears last. The [structural owner](<../../../02 The Type System Core/sections/1. Structural typing/1.1. Structural assignability shape not name.md>) explains member compatibility.

Intersection types arrived in TypeScript 1.6, as documented in the [original release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-1-6.html#intersection-types). Their old generic helper is historical teaching material, not proof that every modern generic object merge preserves its advertised intersection. The next two parts examine that limit.

### 2) **Conflicts can affect one member or reduce the whole type**

A required property cannot simultaneously hold an ordinary string and number. In the Plain intersection below, value is never while the surrounding contract still has id:string. Conflicting literal discriminants instead reduce Tagged itself to never. This distinction matters when diagnosing a member-access error rather than merely reading a compact editor display.

Save `conflicts.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Plain = { value: string; id: string } & { value: number };
type Field = Expect<Equal<Plain["value"], never>>;
type Sibling = Expect<Equal<Plain["id"], string>>;
type StillObject = Expect<Equal<[Plain] extends [never] ? true : false, false>>;
type Tagged = { kind: "a"; id: string } & { kind: "b" };
type WholeType = Expect<Equal<Tagged, never>>;
// const plain: Plain = { value: 42, id: "u1" }; // TS2322: impossible required value.
// function read(value: Tagged): string { return value.id; } // TS2339: Tagged is never.
console.log("checked ordinary conflict and whole-type reduction");
```

The four live type assertions pass and the program prints its confirmation. Activating each negative separately produces the stated rejection, exit 1. A sibling type remaining visible on Plain does not provide an ordinary initializer for its impossible required value. Conversely, Tagged has no usable sibling access after whole-type reduction. The [primary 3.9 notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-9.html#intersections-reduced-by-discriminant-properties) describe the discriminant reduction.

Optional conflicts require separate presence reasoning: two incompatible optional values can still permit omission. The [object-composition owner](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>) verifies the read/write distinction under both exact-optional settings. [Impossible states](<./2.2. The never trap conflicting intersections and impossible states.md>) develops those consequences. Do not silence a conflict with an assertion and then treat an apparently unreachable branch as a runtime guarantee.

### 3) **Object spread overwrites; an intersection requires both contracts**

Object spread creates a result from copied properties, with later properties replacing earlier ones of the same key. Intersection has no such replacement rule. Generic spread inference can approximate its result as an intersection, which does not make an overwritten contract true. Removing a cast alone is insufficient in the following accepted helpers.

Save `spread.ts`:

```typescript
export {};
function unsafeMerge<A extends object, B extends object>(a: A, b: B): A & B {
  return { ...a, ...b }; // Accepted even without an assertion.
}
const merged = unsafeMerge({ value: "text" }, { value: 123 });
const impossible: never = merged.value;
const claimedString: string = merged.value;
console.log("merge:", impossible, typeof merged.value);
try { claimedString.toUpperCase(); }
catch (error: unknown) { console.log(error instanceof TypeError ? "string call: TypeError" : "unexpected"); }
type Times = { createdAt: Date; updatedAt: Date };
function unsafeStamp<T extends object>(input: T): T & Times {
  const now = new Date("2026-10-15T00:00:00Z");
  return { ...input, createdAt: now, updatedAt: now };
}
const stamped = unsafeStamp({ id: "p1", createdAt: "old" });
const oldContract: string = stamped.createdAt;
console.log("stamp:", stamped.id, Object.prototype.toString.call(stamped.createdAt));
try { oldContract.toUpperCase(); }
catch (error: unknown) { console.log(error instanceof TypeError ? "old field: TypeError" : "unexpected"); }

type Post = { id: string; title: string; createdAt?: string };
type StampedPost = Omit<Post, keyof Times> & Times;
function stampPost(post: Post, now: Date): StampedPost {
  return { id: post.id, title: post.title, createdAt: now, updatedAt: now };
}
const post = stampPost({ id: "p2", title: "Post", createdAt: "old" }, new Date("2026-10-15T00:00:00Z"));
console.log("explicit:", post.id, post.createdAt.toISOString(), post.createdAt === post.updatedAt);
// const wrongTime: string = post.createdAt; // TS2322: the replacement contract is Date.
```

Output is `merge: 123 number`, `string call: TypeError`, `stamp: p1 [object Date]`, `old field: TypeError`, then `explicit: p2 2026-10-15T00:00:00.000Z true`. The impossible static field still has a runtime value because the generic spread did not actually enforce both contracts. Since never is assignable to string, the first accepted assignment can carry that wrong runtime value into a string operation. The timestamp helper similarly replaces the original string with a Date while advertising the original requirement too.

The [primary generic-spread notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-2.html#generic-spread-expressions-in-object-literals) distinguish generic intersection inference from concrete rightmost-property overwrite. The original [generic-spread report and discussion](https://github.com/microsoft/TypeScript/issues/50559) expose the same practical misconception; the executions above establish current behavior.

The bounded remedy chooses an explicit Post contract and deliberately replaces its old timestamps. Omit describes the removed type requirements; the initializer supplies the actual selected fields. It does not claim to copy every arbitrary object's prototype, non-enumerable members or generic extension fields. For a real merge API, decide which keys may collide, which value wins and which properties must actually be retained. Test that policy. Use [branding](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>) for evidence boundaries rather than inventing a runtime brand through a type assertion.

### 4) **Interface heritage checks compatibility at the declaration**

Compatible interface heritage and intersections can describe the same requirements. With conflicting parents, heritage reports the incompatible declaration; an intersection can remain a type expression and fail when a value or member is used. Neither operator chooses a collision policy for runtime data.

Save `heritage.ts`:

```typescript
export {};
interface HasId { id: string }
interface HasName { name: string }
interface PublicUser extends HasId, HasName { label: string }
type LocalUser = HasId & HasName & { label: string };
const user: PublicUser = { id: "u1", name: "Ada", label: "admin" };
const local: LocalUser = user;
console.log("same contract:", local === user, local.label);
interface NumberValue { value: number }
interface StringValue { value: string }
// interface Conflict extends NumberValue, StringValue {} // TS2320: incompatible multiple parents.
// interface Replacement extends NumberValue { value: string } // TS2430: incompatible replacement.
```

This prints `same contract: true admin`. The two negatives fail at their declarations with the distinct stated diagnostics. Prefer heritage when its explicit parent compatibility check and interface capabilities fit; prefer an intersection when the type expression represents the intended conjunction, including union or primitive operands. Neither is universally more readable or faster. Legal utility heritage, optional conflicts and detailed declaration choices belong in [object composition](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>) and [interfaces versus aliases](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.3. Interfaces vs type aliases when to use which.md>).

### 5) **Common confusion**

More required members means fewer acceptable values, not a larger set of values. Intersections do not copy fields, reopen declarations or implement last-write-wins merging. A conflicting ordinary required property and conflicting literal tags can simplify differently. Accepted generic spread inference is not proof that its runtime result meets every intersected requirement, and a field typed never does not make an incorrectly typed emitted value vanish.

### 6) **Performance note**

The intersection, interfaces, Omit result and equality probes erase. The spreads, object initializers, Date allocation and method calls remain. Naming an intermediate may help humans understand an error, but it does not establish a fixed speedup or operand-count limit. This lesson measured no key-walk formula, editor hover latency or runtime merge benchmark. Use the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) for a demonstrated checker concern, and measure executing data-copy work separately.

### 7) **Mentor note**

Ask the learner why user can supply both HasId and HasName without creating another object. Then compare Plain's value/id types with Tagged's whole-type reduction and require the relevant diagnostic rather than an assumed hover layout.

For the generic helper, predict the runtime value before inspecting its inferred intersection. A sound answer identifies the overwrite, the accepted never-to-string assignment and the eventual failing method call. Have the learner state the bounded stampPost policy and explain why an arbitrary-object merge needs a stronger, separately verified contract. Finish with the two heritage errors: they describe declaration compatibility, not runtime copying.
