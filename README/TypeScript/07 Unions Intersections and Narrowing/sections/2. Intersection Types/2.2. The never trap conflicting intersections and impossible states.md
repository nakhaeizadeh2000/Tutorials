## 2.2. The never trap — conflicting intersections and impossible states

An impossible intersection can expose a modeling mistake; an optional `never` property can deliberately exclude an unwanted field. The useful question is which contract you intended and where the checker demonstrates it. A type alias being accepted does not prove that a matching value exists.

Examples were verified with TypeScript 7.0.2 and Node.js 20.20.2. Save each TypeScript fence under its stated filename in a scratch directory. Except for the explicitly identified flag comparison, compile each independently with `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then run `node dist/FILE.js`. Commented negative lines are alternatives: activate one at a time and check with the same flags plus `--noEmit` instead of `--outDir dist`.

### 1) **Conflicting property trap**

The [preceding lesson](<./2.1. Intersection fundamentals merging object shapes.md>) distinguishes two outcomes. An ordinary `string`/`number` field conflict can leave an object type with an impossible field. Conflicting discriminants such as `kind: "circle"` and `kind: "square"` reduce the entire intersection to `never`. This whole-type reduction was documented in [TypeScript 3.9](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-9.html#intersections-reduced-by-discriminant-properties). Consequently, accessing a sibling such as `radius` also fails; it does not remain a usable part of that type.

Save as `conflicts.ts`. `Expect<T extends true>` makes a false type-level result a compiler error. The square brackets test the whole type, as explained in part 3.

```typescript
type Expect<T extends true> = T;
type IsNever<T> = [T] extends [never] ? true : false;
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Both = Circle & Square; // This alias is accepted; Both is never.
type Ordinary = { value: string; id: string } & { value: number };
type TaggedIsEmpty = Expect<IsNever<Both>>;
type OrdinaryIsNotNever = Expect<IsNever<Ordinary> extends false ? true : false>;
type FieldIsEmpty = Expect<IsNever<Ordinary["value"]>>;

function fromBottom(value: never): string {
  return value; // Accepted: never is assignable to string.
} // No call: we have not manufactured a never value.
// function readRadius(value: Both) { return value.radius; } // TS2339
// const impossible: Both = { kind: "circle", radius: 1, side: 2 }; // TS2322
// const wrongDirection: never = "circle"; // TS2322

const shape: Circle | Square = { kind: "circle", radius: 2 };
console.log(shape.kind, shape.radius);
```

The output is `circle 2`. The `never` parameter can flow to `string`; assigning an ordinary string to `never` fails. Confusing these directions makes an exhaustiveness check hard to explain. The accepted aliases above describe impossible requirements, while the union repairs the intended choice between shapes. For declaration-site conflict reporting, multiple interface heritage reports TS2320 in the example in [object composition](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>).

### 2) **Impossible-state modeling**

A tag makes alternatives distinguishable. It does not seal each object against every additional key. A fresh email literal containing `phone` is rejected by excess-property checking, but a richer existing object can satisfy the email branch structurally. Add `phone?: never` only when that field's presence is itself an invalid combination. [Freshness](<../../../02 The Type System Core/sections/1. Structural typing/1.2. Excess property checks and freshness.md>) explains the general assignment rule.

Save as `contacts.ts`.

```typescript
type Contact =
  | { kind: "email"; email: string }
  | { kind: "phone"; phone: string };
const mixed = { kind: "email" as const, email: "ada@example.com", phone: "555" };
const ordinary: Contact = mixed; // Accepted: extra fields can exist.
console.log(ordinary.kind, Object.hasOwn(ordinary, "phone"));
// const fresh: Contact = { kind: "email", email: "ada@example.com", phone: "555" }; // TS2353

type StrictContact =
  | { kind: "email"; email: string; phone?: never }
  | { kind: "phone"; phone: string; email?: never };
// const forbidden: StrictContact = mixed; // TS2322, even through a variable
// const missing: StrictContact = { kind: "email" }; // TS2322
function destination(contact: StrictContact): string {
  return contact.kind === "email" ? contact.email : contact.phone;
}
console.log(destination({ kind: "phone", phone: "555" }));

type LooseContact = { kind: "email" | "phone"; email?: string; phone?: string };
function looseDestination(contact: LooseContact): string {
  const address = contact.kind === "email" ? contact.email : contact.phone;
  if (address === undefined) throw new Error("missing address");
  return address;
}
try {
  looseDestination({ kind: "email" }); // Accepted, but the requested data is absent.
} catch (error) {
  console.log(error instanceof Error ? error.message : "unexpected error");
}
```

The output is `email true`, `555`, then `missing address`. The strict contract requires matching data and rejects the other concrete contact field. The flat contract requires the handler to account for missing data. Choose from those requirements; do not add forbidden fields merely to make every union look identical.

The optional-property flag affects what counts as a forbidden write. Save the next file as `optional.ts`. First compile it with the earlier command **omitting `--exactOptionalPropertyTypes`**, and run it. Then compile it with that option enabled and `--noEmit`: the `present` initializer is rejected with TS2375.

```typescript
type EmailOnly = { email: string; phone?: never };
const absent: EmailOnly = { email: "ada@example.com" };
const present: EmailOnly = { email: "ada@example.com", phone: undefined };
const read: undefined = absent.phone;
console.log(Object.hasOwn(absent, "phone"), Object.hasOwn(present, "phone"), read);
```

Without the flag, the output is `false true undefined`: the key can be present with `undefined`. With the flag, omit the `present` declaration and its use to obtain a valid absent-key example. Reading the optional property still yields `undefined`. This absence-versus-value distinction is the point of [exact optional property types](https://www.typescriptlang.org/tsconfig/exactOptionalPropertyTypes.html). Dan Vanderkam's [optional-never article](https://effectivetypescript.com/2021/11/11/optional-never/) develops the structural-assignment problem and this caveat; the examples here check both modes on the declared compiler. These are static contracts, so external data still needs [runtime validation](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.1. Hand-rolled schemas parse validate narrow.md>).

### 3) **Detecting the trap early**

Use a construction attempt when you want to prove that an intended fixture satisfies the contract. Use a type-level assertion when you want to pin a particular reduction. Neither an ambient declaration nor a cast establishes that such a fixture exists.

Save as `detection.ts`.

```typescript
type Expect<T extends true> = T;
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type BadCheck<T> = T extends never ? true : false;
type IsNever<T> = [T] extends [never] ? true : false;
type Whole = { kind: "a"; x: number } & { kind: "b"; y: number };
type Field = { value: string; id: string } & { value: number };
type BadResult = Expect<Equal<BadCheck<never>, never>>;
type WholeResult = Expect<Equal<IsNever<Whole>, true>>;
type ObjectResult = Expect<Equal<IsNever<Field>, false>>;
type FieldResult = Expect<Equal<IsNever<Field["value"]>, true>>;
type SurvivingField = Expect<Equal<Field["id"], string>>;
// type IntendedPossible = Expect<Equal<IsNever<Whole>, false>>; // TS2344
console.log("whole-type and individual-field checks passed");
```

The output confirms that the file ran after its five assertions compiled. `BadCheck<never>` produces `never`, because the conditional distributes over the empty union. Wrapping the input avoids that distribution and returns `true`. This checks whether the **whole** type is `never`; it does not inspect every property for you. `Field` and `Field["value"]` deliberately give different answers. The full transformation mechanism belongs to [conditional types](<../../../09 Utility Types and Type Transformations/sections/2. Conditional Types/2.1. Conditional fundamentals distributive law and never branches.md>); test-utility design belongs to [type assertions in tests](<../../../17 Testing Types/sections/1. Type Assertions in Tests/1.1. Expect Equal and compile-time type assertions.md>).

An empty `assertPossible` body cannot validate anything. Nor does `never` delete runtime handlers or protect a retained read of an erased ambient name. Save as `runtime.ts`; both failures are controlled observations rather than instructions for application validation.

```typescript
type A = { kind: "a"; x: number };
type B = { kind: "b"; y: number };
type AB = A & B;
function assertPossible<T>(_value: T): void {} // No test, throw or validation.
const hidden = { kind: "a", x: 1 } as unknown as AB; // Deliberately false claim.
assertPossible<AB>(hidden);
console.log("empty helper returned");
function handleA(value: A): void {
  if (value.kind === "a") console.log("handler ran", value.x);
}
handleA(hidden); // never is assignable to A; the runtime object is still there.

declare const missingProof: AB; // Erased; creates no runtime binding.
try {
  void missingProof; // This expression remains in JavaScript.
} catch (error) {
  console.log(error instanceof ReferenceError ? "ReferenceError" : "unexpected error");
}
```

The output is `empty helper returned`, `handler ran 1`, then `ReferenceError`. Inspect `dist/runtime.js`: the declaration disappears and `void missingProof` remains. A type-only probe is a `type` declaration such as `WholeResult` above, with no expression reading an absent binding. Use a real fixture or an actual throwing validator when runtime evidence is required.

### 4) **Common confusion**

A forbidden optional key is not a required key of type `never`. Requiring that key would make a normal finite fixture impossible; optionality permits its absence. The exact-optional flag decides whether an explicit `undefined` write also qualifies. Separately, a required ordinary conflict can make an object uninhabitable without reducing the whole object type to `never`; checking only `IsNever<Object>` misses that case.

A successful build containing an unused impossible alias proves only that the declaration is accepted. Casting a fixture to that alias removes precisely the construction evidence you were trying to collect. Examine the diagnostic at the operation being tested, rather than treating a hover description as a runtime guarantee.

### 5) **Performance note**

The intersection, conditional aliases and optional-property annotations erase; they add no runtime validation or automatic branch removal. Real tag comparisons, presence checks, function calls and throws remain. The controlled runtime example demonstrates that difference, without measuring their cost. No timing or checker-complexity conclusion follows from these small probes; investigate a measured checker slowdown through the [diagnostics and traces owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>).

### 6) **Mentor note**

Ask a learner to predict three independent results: whether the alias declaration is accepted, whether a concrete initializer is accepted, and what emitted JavaScript does after a deliberate cast. A sound explanation keeps those results separate. Then ask them to reject `mixed` through a variable and explain why `phone?: never` changes that assignment. Finally, remove the exact-optional flag and have them predict the presence check before running it.

For a repair exercise, remodel `{ mode: "preset" | "custom"; preset?: string; custom?: string }` so the selected value is required and the other key is forbidden. Two tagged branches, each requiring its matching `string` and declaring the other field `?: never`, satisfy that requirement under the exact-optional flag. Test a valid fixture for each branch, a missing value, a mixed variable and a present-undefined key.
