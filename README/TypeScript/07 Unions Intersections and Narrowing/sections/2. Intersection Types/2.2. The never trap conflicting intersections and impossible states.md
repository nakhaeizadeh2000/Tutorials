## 2.2. The never trap — conflicting intersections and impossible states

### 1) **Conflicting property trap** (`{ kind: "a" } & { kind: "b" }` → `never` on `kind`)

**Definition** — when two intersected types disagree on the same property's type in an *unresolvable* way, that property collapses to `never` — no value can satisfy both at once. The canonical case is a discriminant conflict: `{ kind: "circle" } & { kind: "square" }` requires `kind` to be both `"circle"` *and* `"square"` — the intersection of `"circle"` and `"square"` is `never`, so the whole branch becomes un-constructable. The hover still lists the property, but its type is `never` — the signal that the composition is impossible.

**What problem it solves / history** — without `never`, conflicting intersections would have silently widened to `unknown` or to the last write wins, and code that tried to construct the impossible value would compile and then fail at the first runtime use. `never` makes the impossibility *visible* — the assignment to `never` errors, downstream narrowing sees the branch as dead, and the reviewer can distinguish "intentionally impossible" from "accidentally conflicting."

**Modern guidance** — as of TypeScript 5.9 era, treat a hovering `never` property as a red flag — search for `&` on discriminants or literal keys where members were meant to be alternative (`|`). Never silence the `never` with `as` — fix the operator: alternatives should be `|` (either), co-present fields should be `&` (both). When reviewing a new `&`, hover the resulting type and check every overlapping key — if any reads `never`, the composition is wrong.

**Runnable example** — discriminant conflict that hovers as `never` (good vs bad, `tsc --strict`):

```typescript
// good — discriminant conflict is visible as never
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Both = Circle & Square; // { kind: never; radius: number; side: number }
declare const both: Both;
// both.kind is never — no string satisfies both "circle" and "square"
// const k: "circle" = both.kind; // error TS2322: never not assignable to "circle"

// good — construction attempt errors at the assignment, not silently later
// const c: Both = { kind: "circle", radius: 1, side: 1 }; // error — kind "circle" not assignable to never
// const s: Both = { kind: "square", side: 1, radius: 1 }; // error — kind "square" not assignable to never
// correct — no value can occupy Both; the type is intentionally empty on kind

// good — overlapping compatible literal does narrow, not collapse
type A = { role: "admin" | "user"; level: number };
type B = { role: "admin"; team: string };
type Narrowed = A & B; // role is "admin" (intersection of "admin"|"user" & "admin" is "admin")
const ok: Narrowed = { role: "admin", level: 1, team: "platform" }; // ok — narrowed to "admin"

// bad — accidental & on alternatives builds an impossible state that blocks all use
type ClickEvent = { kind: "click"; x: number };
type KeyEvent = { kind: "keydown"; key: string };
type ImpossibleEvent = ClickEvent & KeyEvent; // kind is never
// const evt: ImpossibleEvent = { kind: "click", x: 1, key: "a" }; // error — kind never
// fix — pick | for alternatives
type EitherEvent = ClickEvent | KeyEvent;
const evtGood: EitherEvent = { kind: "click", x: 1 }; // ok — either, not both

// good — primitive literal conflict also collapses (same set algebra)
type Red = { color: "red"; hex: string };
type Blue = { color: "blue"; rgb: number };
type RedAndBlue = Red & Blue; // color is never
// hover shows { color: never; hex: string; rgb: number } — impossible color
```

**Common confusion** — "`never` on `kind` means the whole `&` is `never`" — sibling properties (`radius`, `side`, `hex`) still exist — the type is constructible only for those siblings, but `kind` can never be satisfied — the value as a whole is impossible to produce without `as`. "`A & B` collapsing to `never` is a type error" — the `&` itself does not error — only an attempt to satisfy it signals — `type Bad = A & B` compiles; `const x: Bad = …` fails — check with a construction attempt, not with the `type` line alone. "I can `as` the discriminant to pick one" — `as unknown as Both` silences the checker, but downstream `if (both.kind === "circle")` still sees `both.kind` as `never` — dead code follows, and the patching PR hides the semantic mistake.

**Performance note** — `never` collapses are checker-only — zero emit. Detector cost is one hover walk — negligible. The value is review cost: a hover with `never` spotted early saves a debugging trip where an impossible `kind` silently disables an event handler. Prefer early conflict reporting via `interface extends` (see [2.1. Intersection vs extends](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.1. Intersection vs extends composing object types.md>)) for public contracts so the `never` is caught at the `interface`, not in some downstream test's impossible fixture.

**Mentor note** — show the hover drill: declare the conflicting `Both` and hover `both.kind` — point out `never`. Ask "what runtime string could be both `"circle"` and `"square"`?" — answer is none — teach `| vs &` as "either vs both." Review exercise: hand a 2-member `Event` union that was accidentally typed as `&`, ask to predict whether constructing `{ kind: "click" }` compiles — answer is "error, `kind` is `never`."

### 2) **Impossible-state modeling** (using `never` to forbid illegal combinations — design, not bug)

**Definition** — an *impossible state* is a combination of props that the type *intentionally* makes inexpressible via `never` — `type HasKey = { kind: "preset"; key: string } | { kind: "custom"; value: string }` vs the bad flat `{ kind: "preset" | "custom"; key?: string; value?: string }` that allows `kind: "preset"` without `key`. By making the illegal shape's prop `never`, callers cannot construct the invalid mix.

**What problem it solves / history** — flat "bag of optionals" types (`{ mode: "a"|"b"; x?: number; y?: string }`) let any combination slip past the checker — `mode: "a"` without `x` compiled and failed inside the handler. Discriminated-union alternatives exist precisely to *exclude* impossible combos at the type layer; `never` is the same idea for intersections that would otherwise conflate unrelated fields. The pattern underpins form validation (`{ email?: never; phone: string } | { email: string; phone?: never }` — exactly one contact method).

**Modern guidance** — as of TypeScript 5.9 era, prefer discriminated unions over optionals for *mutually exclusive* fields — each branch lists exactly the props that belong together, and `never` appears only as the deliberate absence in a branch, not as a leaked collision: `type Contact = { kind: "email"; email: string } | { kind: "phone"; phone: string }`. When an intersection would enable an illegal cross, split into a union instead. Document impossibles with an explanatory `never` prop (`forbidden?: never` with a comment "exactly one contact method") rather than with `unknown`.

**Runnable example** — impossibles designed with unions, not with `never` collisions (good vs bad, `tsc --strict`):

```typescript
// good — discriminated union forbids mixed branches by construction
type EmailContact = { kind: "email"; email: string };
type PhoneContact = { kind: "phone"; phone: string };
type Contact = EmailContact | PhoneContact; // exactly one branch

function send(c: Contact): void {
  if (c.kind === "email") console.log(`email ${c.email}`); // narrowed to EmailContact
  else console.log(`phone ${c.phone}`); // narrowed to PhoneContact
}
send({ kind: "email", email: "ada@example.com" }); // ok
// send({ kind: "email", email: "ada@example.com", phone: "555-1234" }); // error TS2353: phone excess on EmailContact unless in var — but discriminated, not flat

// good — impossible flat shape rejected by encoding exactly-one at the union layer
type HaveEmail = { kind: "email"; email: string; phone?: never };
type HavePhone = { kind: "phone"; phone: string; email?: never };
type StrictContact = HaveEmail | HavePhone; // every branch, forbidden field is never
const contactOk: StrictContact = { kind: "phone", phone: "555-1234" }; // ok — no email
// const contactBad: StrictContact = { kind: "email", email: "a@b.c", phone: "555" }; // error TS2322: phone not assignable to never

// bad — flat bag of optionals lets impossible shape through
type LooseContact = { kind: "email" | "phone"; email?: string; phone?: string };
const loose: LooseContact = { kind: "email" }; // compiles, but email missing at runtime
// sendLoose(loose); // handler would need runtime if (!loose.email) throw — checker did not block
// fix — StrictContact above; impossible states are caught at construction

// good — intersection impossibility used deliberately: branding that never conflates
type Brand<Tag extends string> = { readonly __brand: Tag };
type UserId = string & Brand<"UserId">; // brand via intersection that never conflicts with string literal
type OrderId = string & Brand<"OrderId">;
function getUser(id: UserId): void { console.log(id); }
const uid = "u1" as UserId; // branded
// getUser("u1" as OrderId); // error TS2345: OrderId brand mismatch (via intersection tag)
```

**Common confusion** — "`never` means I cannot model optionality" — `never` is the *intentional* absence, not the `T | undefined` suggestion — `email?: never` says "this branch must not have `email`" — distinct from `email?: string` which says "maybe present." "Union vs `never` collision is style only" — behavior differs: collision (`never`) blocks construction but is reported late (at the `&` use); union encoding reports precisely which branch violated — pick the union encoding when the branches represent *alternatives*. "Exactly-one needs `XOR`" — the literal `StrictContact` above *is* XOR in disguise — two branches each with the other branch's field as `never` — readable without a generic helper.

**Performance note** — impossible-state modeling adds no runtime cost — `never` props erase — the runtime handler sees `c.kind === "email"` then `c.email` (already present). The cost is one extra literal prop per variant (`kind`) — trivial — versus the bug cost of an unguarded optional that every callee must re-check at runtime. Prefer the union model for hot paths that construct many typed payloads — each value is one object allocation, not one allocation plus a fallback map keyed by `mode`.

**Mentor note** — give students the flat `LooseContact` and the "buggy" construction `{ kind: "email" }` — ask why it compiles — answer is optionals do not enforce *presence* — then show `StrictContact` where the same literal errors on `phone: never` if present and the discriminant enforces the branch. Exercise: remodel `{ mode: "preset" | "custom"; preset?: string; custom?: string }` to a discriminated union where only the matching prop is allowed.

### 3) **Detecting the trap early** (hover, assignment to `never`, and the guard before it ships)

**Definition** — detection is three cheap signals: (1) *hover* — intersecting result hovers with `never` on the conflicting key; (2) *construction* — `const x: Bad = { kind: "a" }` errors as `Type '"a"' is not assignable to type 'never'`; (3) *early declaration* — `interface C extends A, B` reports `TS2430` at the `interface` line before any value is made (see [2.1](<./2.1. Intersection fundamentals merging object shapes.md>)). Any one of them before the PR ships prevents the silent downstream dead branch.

**What problem it solves / history** — conflicting intersections often ship because the `type T = A & B` line itself does not error — the bug is latent until someone writes `const x: T = …` or a caller narrows on `x.kind`. Without a habit of hovering the composite or probing construction, the `never` stays hidden and the dead handler sits until a new feature depends on the missing branch.

**Modern guidance** — as of TypeScript 5.9 era, add two hard habits: (1) after defining any `&`, immediately hover the new type and assert that no member reads `never` unexpectedly; (2) probe construction — write `declare const probe: T;` and let the editor underline `never` use sites. For public compositions use `interface extends` so the error is at the boundary — `TS2430` triggers at `interface Audited extends HasKind, WithKind` instead of deep in a consumer.

**Runnable example** — early detection via hover, probe, and interface report (good vs bad, `tsc --strict`):

```typescript
// good — hover reveals never immediately after defining the composite
type A = { kind: "a"; x: number };
type B = { kind: "b"; y: number };
type AB = A & B; // hover: { kind: never; x: number; y: number } — kind flagged instantly
// fix: use | for alternatives
type Either = A | B; // hover: A | B — kind splits, no never

// good — construction probe that triggers the diagnostic without building a full fixture
type Probe = A & B;
// const probeOk: Probe = { kind: "a", x: 1, y: 2 }; // error TS2322: "a" not assignable to never — probe surfaces bug

// good — early-report via interface (error at declaration, not at distant usage)
interface IHasA { kind: "a"; payload: string; }
interface IHasB { kind: "b"; payload: string; }
// interface IConflict extends IHasA, IHasB {} // error TS2430: kind incompatibility at interface line

// good — utility guard that maps any never-containing composite to a diagnostic
type HasNever<T> = T extends never ? true : false; // not for composite internals — for branch reach check
function assertPossible<T>(value: T): void {} // generic probe
// assertPossible<AB>({} as AB); // hovering AB already shows kind: never

// bad — hiding with as silences probe and ships dead branch downstream
const hidden = { kind: "a" } as unknown as AB; // compiles via launder, but hidden.kind is never
// if (hidden.kind === "a") { /* dead branch checker sees never — unreachable code warning */ }
// fix — choose |, not &, or remodel branch as union with proper discriminants
```

**Common confusion** — "the composite `type` should have errored" — `type X = A & B` never errors by itself — laziness is deliberate; laziness avoids cascading errors before a use site proves the conflict matters — so add the probe or the `interface extends` to force early mention. "`never` check needs a test file" — a single hover plus a `declare const probe: AB;` line in the defining file is enough; no test needed to catch discriminant collision. "The build would catch it" — only a construction or reachability site catches it — an unused `&` that is exported but never constructed passes build green.

**Performance note** — detection adds zero runtime code — probes are `declare const` or `type` aliases that erase — omit them from emit. The only runtime piece is `assertNever`/`assertPossible` helper that hovers as `(x: never): never` and throws when reached. Checker cost is hovering O(members) once per new composite — seconds in editor, saves hours of post-ship debugging for the missing branch.

**Mentor note** — make the hover check part of the PR checklist: "did you hover every new `A & B` and confirm no `never` member?" Add a probing line `declare const _probe: MyIntersection; void _probe;` in the defining file when reviewing intersection PRs — require deleting it before merge or guarding via `interface extends` instead. Pair with exhaustive `assertNever` (see [3.2. Exhaustiveness](<../3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>)) for the downstream caller side.
