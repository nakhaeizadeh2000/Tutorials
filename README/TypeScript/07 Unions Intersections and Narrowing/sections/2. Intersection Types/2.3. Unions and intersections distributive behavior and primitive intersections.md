## 2.3. Unions and intersections — distributive behavior and primitive intersections

### 1) **Distributivity** (`(A|B) & C` distributes — reading `(A & C) | (B & C)`)

**Definition** — set-theoretically, `(A | B) & C` equals `(A & C) | (B & C)` — the union distributes over the intersection, and intersection distributes over union. TypeScript checks this distribution — narrowing `Shape & { auditId: string }` over a `Shape = Circle | Square` preserves the split; intersecting a union with a common augmentation threads the augmentation into each member, not into a shared supertype.

**What problem it solves / history** — intersecting a union with a shared shape naively would have erased variant structure — `Circle | Square` is structurally distinct per member, but `Audited = (Circle | Square) & Timestamped` needs to stay *two* timestamped variants, not one flat object with optional discriminant. Distribution keeps the variants — `Audited` is `{ Circle & Timestamped } | { Square & Timestamped }` — so discriminant narrowing still works after augmentation. The distributive walk is part of everyday augmentation (`T & { id: string }`) over unions.

**Modern guidance** — as of TypeScript 5.9 era, rely on distribution when augmenting a union — `type AuditedShape = Shape & { auditId: string }` remains a discriminated union you can still `switch(kind)`. When reading hovers, expect the distributed form — the checker expands the composite into per-member intersections, then collapses compatible keys — so read `AuditedShape` as the per-member product, not as a supertype. For type-level filtering (forward to [09 Utility Types](<../../../09 Utility Types and Type Transformations/README.md>)), note that `T extends U ? T : never` also distributes over bare `T extends` — same distributive intuition, but filtering lives there, not here.

**Runnable example** — distribution preserves discriminant after intersection (good vs bad, `tsc --strict`):

```typescript
// good — augmentation distributes, discriminant narrows after intersection
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Shape = Circle | Square;
type Audited = Shape & { auditId: string }; // distributed: (Circle & {auditId}) | (Square & {auditId})
// hover shows two compatible shapes per variant, not one flat with never

function stamp(shape: Shape, id: string): Audited {
  return { ...shape, auditId: id };
}
function describe(a: Audited): string {
  if (a.kind === "circle") return `circle ${a.radius} audit:${a.auditId}`;
  return `square ${a.side} audit:${a.auditId}`;
}
console.log(describe(stamp({ kind: "circle", radius: 3 }, "a1"))); // circle 3 audit:a1

// good — (A|B) & { discriminator filter } keeps live variants, drops dead ones
type Card = { kind: "visa"; pan: string } | { kind: "amex"; code: string } | { kind: "unknown"; raw: string };
type KnownCard = Card & { kind: "visa" | "amex" }; // distributively drops | unknown member
// KnownCard hover is {kind:"visa"}|{kind:"amex"} shape — unknown filtered via kind intersection
const c: KnownCard = { kind: "visa", pan: "4111" }; // ok — unknown not allowed

// bad — intersecting with discriminant literal collapses non-matching variants silently
type FilteredBad = Card & { kind: "visa" }; // only visa survives, others become never then dropped
// const lost: FilteredBad = { kind: "amex", code: "37" }; // error — amex not assignable to visa brand
// fix — use union filtering intentionally (KnownCard above via kind union), or Exclude/Extract for explicit filter

// good — nested distribution: (A|B) & (C|D) expands to 4 intersections, live ones survive
type Prefix = "create" | "delete";
type Suffix = "User" | "Post";
type Action = `${Prefix}_${Suffix}`; // template expansion, also distributive (4 members)
type AuditedAction = Action & { readonly: false }; // not useful here — count is 4 members still
console.log(("create_User" as Action).length > 0); // true — runtime plain string
```

**Common confusion** — "intersection with a literal type keeps the literal set" — it *filters* — `(A|B) & { kind: "a" }` keeps only the `A` branch, the other becomes `never` on the discriminant and vanishes from the union — expected when explicitly filtering, surprising when accidental. "Distribution means the checker rewrites my type" — distribution is an equivalence, not a rewrite — hover just shows the per-member shape; the type remains `(A|B) & C` — the checker reasons per member internally, but documentation can display either side. "Distributive `T extends U ?` is the same mechanism" — `extends` distributes only on *naked* `T extends` — ` [T] extends [U] ?` does not — intersection `&` always distributes over `|` at the shape level.

**Performance note** — distributive intersections cost O(members × properties) — 5-member union intersected with an object with 5 keys walks 25 — still cheap. Combinatorial explosion (`(A|B|C) & (D|E|F)`) is 9 intersections — hover size multiplies; keep augmentations as one `Shape & Audit` product where the union sits on the left, not as `A & B & …` with unions on both sides.

**Mentor note** — demo by writing `type Audited = Shape & { auditId: string }`, hovering, and asking "how many `kind`s are still available?" — answer is still both `"circle"` and `"square"` — distribution preserved the literal set. Then write `type OnlyCircle = Shape & { kind: "circle" }` — hover shows only `Circle & …`, `Square` gone — teach filtering vs augmenting as the two reads.

### 2) **Primitive intersections and `never`** (`string & number` is `never` — no value is both)

**Definition** — primitive type `string` and `number` have no value in common — no runtime value is simultaneously a string *and* a number — so `string & number` is `never`. Similarly `string & {}` is `string` (`string` already has properties like `length`), `"a" & ("a"|"b")` is `"a"` (literal narrowing), and `"a" & "b"` is `never` (conflicting literals). The same set algebra that made object intersections accumulate properties makes primitive intersections collapse when the sets are disjoint.

**What problem it solves / history** — without primitive intersection rules, `string & number` would have widened to `unknown` and hidden impossible branches. `never` instead makes the impossible *assignable nowhere* — any attempt to satisfy it errors, and conditional-type filtering (`T & unknown` preserving `T`, `T & never` yielding `never`) behaves like set intersection and underpins `Extract<T,U> = T extends U ? T : never` as the `&`-shaped filter (see [2.2](<./2.2. The never trap conflicting intersections and impossible states.md>)).

**Modern guidance** — as of TypeScript 5.9 era, treat primitive `&` as intentional narrowing only when the primitives overlap on a literal — `type A = "login" | "logout"; type B = "login" | "signup"; type Both = A & B; // "login"` is the only sane primitive `&`; `string & number` signals a logic bug. For object-branded primitives (`type Id = string & Brand<Tag>`), the brand trick succeeds because `{ __brand: Tag }` is an *object* intersection with the primitive — not two primitives fighting the same slot — distinct from pure `string & number`.

**Runnable example** — primitive intersections that survive vs collapse (good vs bad, `tsc --strict`):

```typescript
// good — overlapping literal sets intersect to their overlap (narrowing, not collapsing)
type A = "login" | "logout" | "signup";
type B = "login" | "signup" | "delete";
type Overlap = A & B; // "login" | "signup" — common literals survive
const ok: Overlap = "login"; // ok
// const bad: Overlap = "logout"; // error TS2322: "logout" not in "login"|"signup"

// good — disjoint primitives are never — the checker blocks construction
type Collapsed = string & number; // never
// const x: Collapsed = "hi"; // error TS2322: string not assignable to never

// good — string & {} keeps string ({} accepts many, includes string's structural side)
type StrWithProps = string & { trimmed: true }; // string branded — used for tagged strings
function tagTrimmed(s: string): StrWithProps {
  (s as StrWithProps & { trimmed: true }).trimmed = true as unknown as true; // fake brand—see next line
  return s as StrWithProps;
}
type Trimmed = string & { __trimmed: "yes" };
function makeTrimmed(raw: string): Trimmed { return raw.trim() as Trimmed; }
console.log(makeTrimmed("  hello ").length); // 5 — runtime plain string with checker tag

// bad — literal conflict collapses to never, caller probe surfaces never before shipping
type Red = "red" & "blue"; // never — no runtime value is both
// const color: Red = "red"; // error TS2322 — red not assignable to never
// fix — use | for alternatives: type Color = "red" | "blue"; const color: Color = "red";
```

**Common confusion** — "`string & {}` should be `never` — strings are objects" — `string` structurally has properties (`length`, `slice`) so `& {}` (any non-null value) still admits strings — `string & {}` is `string`. "`never & T` is `never`" — intersection with empty set is empty — correct; `unknown & T` is `T` (intersection with top keeps `T`). "Branded `string & Brand` is also `never`" — `string & { __brand }` is an intersection of a primitive with an object slice — the object adds a branded key the primitive is widened to accommodate via the brand trick — distinct from `string & number`.

**Performance note** — primitive `&` is a one-member set-intersection check — O(members) — fastest path. No emit. Branded primitives (`string & Brand`) add zero runtime allocation — the brand is purely at the checker; the runtime value stays a plain string — the tradeoff is that the brand persists only while `string & Brand` flows through the checker; an incidental `as string` erases it.

**Mentor note** — present `"login" | "logout"` intersect `"login" | "signup"` and ask what survives — answer is only `"login"` — the common member — then present `string & number` and ask what value could pass — answer is none → `never`. Link both to the runtime thought: no string is also a number.

### 3) **Filtering with `Exclude`/`Extract` echo** (how `&` underpins conditional-type filtering — forward link without full teaching)

**Definition** — `Exclude<T, U>` and `Extract<T, U>` (stdlib, `lib.d.ts`) filter a union: `type E = Exclude<"a"|"b"|"c", "a">` → `"b"|"c"`; `type F = Extract<"a"|"b"|"c", "a"|"b">` → `"a"|"b"`. Internally they rely on *naked* conditional distribution over `T` (`T extends U ? never : T`) — the distributed walk mirrors `&` distributivity at the shape layer — `T` intersected-with-`U` *membership* decides which members survive. This leaf does not teach full conditional types (that lives in [08 Generics Deep Dive](<../../../08 Generics Deep Dive/README.md>) — it shows the echo so learners recognize `&`'s filtering role when they land there.

**What problem it solves / history** — filtering unions without a built-in operator needed a mechanism that iterates per member, drops mismatches, and preserves the surviving set — conditional distribution over `T extends U` provides that iteration — conceptually "is this member in the filter set?" — `&` provides the dual (`member & Filter` survives iff the literal overlaps). Both share the set-intersection intuition — union filtering is type-level grep.

**Modern guidance** — as of TypeScript 5.9 era, prefer `Exclude`/`Extract` for union filtering over hand-rolled `&` filters — `Exclude<Role, "admin">` is explicit, `Role & NotAdmin` via intersection literal is ad-hoc and hides intent. Recognize `&` filtering when reading code — `Role & "admin"` appears idiomatically as a literal-level filter in narrow scopes — broaden it to `Extract<Role, "admin" | "editor">` when the filter grows. Do not author conditional types in this domain; use stdlib filters and wait for [09 Utility Types](<../../../09 Utility Types and Type Transformations/README.md>) for `Mapped`/`Conditional` synthesis.

**Runnable example** — set-intersection filtering with stdlib filters (good vs bad, `tsc --strict`):

```typescript
// good — Exclude filters a union (the intended, readable tool for union filtering)
type Role = "admin" | "editor" | "viewer" | "guest";
type NonGuest = Exclude<Role, "guest">; // "admin" | "editor" | "viewer"
type ViewerOrGuest = Extract<Role, "viewer" | "guest">; // "viewer" | "guest"
console.log((("admin" as NonGuest) satisfies Role).length > 0); // true

// good — & as literal ad-hoc filter (ok for a two-literal scope, still distributes)
type ActionKind = "create" | "update" | "delete" | "read";
type Mutating = ActionKind & ("create" | "update" | "delete"); // "create"|"update"|"delete"
const act: Mutating = "create"; // ok — filtered via intersected literal
// const read: Mutating = "read"; // error — read not in mutating set

// good — distribution + filter discards whole branch (Card filter echo)
type Card =
  | { kind: "visa"; pan: string }
  | { kind: "amex"; code: string }
  | { kind: "unknown"; raw: string };
type KnownKind = Exclude<Card["kind"], "unknown">; // "visa"|"amex"
type KnownCard = Extract<Card, { kind: KnownKind }>; // two-member variant set, unknown dropped
const known: KnownCard = { kind: "visa", pan: "4111" }; // ok

// bad — intersecting with interface literal instead of filtering felt implicit
type FilteredBad = Card & { kind: "unknown" }; // only unknown survives — reader thinks you mutated Card
// use Extract<Card, { kind: "unknown" }> — intent is filter, not augmentation
```

**Common confusion** — "`&` is the same as `Extract`" — `&` on discriminants is literal filtering (narrow scope, may surprise with dead branches); `Extract` is a *conditional* filter that distributes cleanly and signals intent ("keep only matching members") — style differs even when results coincide. "`Exclude` changes the runtime set" — all filtering erases — the runtime values remain plain strings/objects; filtering only proves at the checker which values may pass a branch. "I need conditional types here" — prefer stdlib filters (`Exclude`/`Extract`/`NonNullable`/`ReturnType` …) until [08/09](<../../../08 Generics Deep Dive/README.md>) teach how to write your own — hand-rolled `T extends U ? …` for union filtering is the junior trap that produces accidental naked-distribution forks.

**Performance note** — `Exclude`/`Extract` expand to per-member conditionals at check time — O(members) per call, same as an `&` literal filter. No emit. For unions with 50 members both have identical cost; readability is the tiebreaker — named `type NonGuest = Exclude<Role,"guest">` leads hover better than `type NG = Role & "admin"` assembled slices.

**Mentor note** — ask "filter `"viewer"|"guest"` from `Role`" — first with `&` (`Role & ("viewer"|"guest")`), then with `Extract` — ask which one a stranger reads correctly — answer is `Extract` — introduce stdlib as the shared vocabulary for union filtering. Pair with [1.3](<./1.3. Literal unions enums vs unions and exhaustiveness preview.md>)'s `as const` derivation to model "owning the set in one place."
