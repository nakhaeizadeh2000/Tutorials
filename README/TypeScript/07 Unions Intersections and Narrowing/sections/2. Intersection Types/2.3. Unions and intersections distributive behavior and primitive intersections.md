## 2.3. Unions and intersections — distributive behavior and primitive intersections

Intersecting a union with an extra requirement applies that requirement to its alternatives. Sometimes all alternatives survive; sometimes a conflicting tag removes one. This is useful for reading composed contracts, but it does not make intersection interchangeable with the `Extract` utility.

These independent files were verified with TypeScript 7.0.2 and Node.js 20.20.2. Save each TypeScript fence under the stated filename. Compile with `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`; run `node dist/FILE.js`. To observe a commented negative, activate only that line and compile with the same flags plus `--noEmit`, replacing `--outDir dist`.

### 1) **Distributivity**

For the object contracts below, read `(Circle | Square) & Audit` as `(Circle & Audit) | (Square & Audit)`. Each value needs the audit field and one valid shape. The tag continues to connect the variant-specific fields; it has not become a flat bag of optional properties. Parentheses matter when reading mixed operators: `Circle | Square & Audit` requires auditing only the square alternative.

Save as `augment.ts`.

```typescript
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Shape = Circle | Square;
type Audit = { auditId: string };
type Together = Shape & Audit;
type Expanded = (Circle & Audit) | (Square & Audit);
function expand(value: Together): Expanded { return value; }
function combine(value: Expanded): Together { return value; }
function stamp(shape: Shape, auditId: string): Together {
  return { ...shape, auditId };
}
function describe(shape: Together): string {
  if (shape.kind === "circle") return `circle ${shape.radius} ${shape.auditId}`;
  return `square ${shape.side} ${shape.auditId}`;
}
console.log(describe(combine(expand(stamp({ kind: "circle", radius: 3 }, "a1")))));
console.log(describe(stamp({ kind: "square", side: 4 }, "a2")));
// const missing: Together = { kind: "circle", radius: 3 }; // TS2322
// function unguarded(shape: Together) { return shape.radius; } // TS2339

type OnlyCircle = Shape & { kind: "circle" };
const circle: OnlyCircle = { kind: "circle", radius: 5 };
console.log(circle.kind, circle.radius);
// const lost: OnlyCircle = { kind: "square", side: 4 }; // TS2322
```

The output is `circle 3 a1`, `square 4 a2`, then `circle 5`. Adding `Audit` preserves both variants; adding `kind: "circle"` leaves only the compatible alternative. The conflicting square intersection reduces to `never`, as explained in [the never trap](<./2.2. The never trap conflicting intersections and impossible states.md>). The two conversion functions check that the compact and expanded contracts accept each other's values. No particular editor hover rendering is needed for that check.

Two independent unions can also combine. Save as `product.ts`.

```typescript
type Mode = { mode: "read" } | { mode: "write" };
type Place = { place: "local" } | { place: "remote" };
type Request = Mode & Place;
const cases: Request[] = [
  { mode: "read", place: "local" },
  { mode: "read", place: "remote" },
  { mode: "write", place: "local" },
  { mode: "write", place: "remote" },
];
for (const value of cases) console.log(value.mode, value.place);
// const invalid: Request = { mode: "erase", place: "local" }; // TS2322
export {}; // Keep Request local rather than colliding with the DOM Request name.
```

The four lines are the four pairs in the array. This demonstrates a product of independent object requirements. A template literal such as `` `${Prefix}_${Suffix}` `` generates string combinations through a separate mechanism; see [template literal composition](<../../../09 Utility Types and Type Transformations/sections/3. Transformations in Practice/3.2. Template literal composition Capitalize handlers and routes.md>) for that operation.

### 2) **Primitive intersections and never**

A string cannot also be a number, so `string & number` is `never`. Overlapping literal unions retain their shared values. By contrast, `{}` means any non-nullish value under strict null checking; it includes strings, numbers, booleans, symbols, bigints, functions and objects. A string is admitted by `{}` because it is non-nullish, not because it is an object.

Save as `primitives.ts`. `Equal` plus `Expect` checks the stated results instead of printing an unconnected boolean.

```typescript
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Overlap = ("login" | "logout") & ("login" | "signup");
type SharedLiteral = Expect<Equal<Overlap, "login">>;
type Disjoint = Expect<Equal<string & number, never>>;
type StringToIntersection = Expect<string extends (string & {}) ? true : false>;
type IntersectionToString = Expect<(string & {}) extends string ? true : false>;
type NumberToIntersection = Expect<number extends (number & {}) ? true : false>;
type IntersectionToNumber = Expect<(number & {}) extends number ? true : false>;
type RemovedNullish = Expect<Equal<(string | null | undefined) & {}, string>>;
type TopIdentity = Expect<Equal<string & unknown, string>>;
const word: Overlap = "login";
console.log(word, typeof word);
// const alternative: Overlap = "logout"; // TS2322
// const impossible: string & number = "hello"; // TS2322
// const nullish: {} = null; // TS2322
// const objectOnly: object = "hello"; // TS2322

function fakeTag(text: string): string & { trimmed: true } {
  const tagged = text as string & { trimmed: true };
  tagged.trimmed = true; // Accepted after the cast; cannot add a field to this primitive.
  return tagged;
}
try {
  fakeTag(" hello ");
} catch (error) {
  console.log(error instanceof TypeError ? "primitive write: TypeError" : "unexpected error");
}
const trimmed = " hello ".trim(); // A real operation, returning a plain string.
console.log(trimmed, trimmed.length, typeof trimmed);
```

The output is `login string`, `primitive write: TypeError`, then `hello 5 string`. Strict JavaScript rejects the property write; an intersection assertion does not attach metadata. If a domain needs a checked branded string, its factory validates the invariant and confines the assertion, as taught by [branding and opaque types](<../../../02 The Type System Core/sections/1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>). This example needs only a trimmed string, so ordinary `.trim()` fulfills its contract.

The bidirectional checks show that `string & {}` accepts the same string assignments as `string` here, and likewise for numbers. The compiler can retain the intersection representation; do not use an exact-equality helper to assume every assignability-equivalent spelling has normalized identically.

The standard `NonNullable<T>` definition uses `T & {}` on this baseline. The change and its reduction behavior are documented in [TypeScript 4.8](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-8.html#improved-intersection-reduction-union-compatibility-and-narrowing). That removes nullish constituents from a static contract; it does not test a runtime input or trim a string.

### 3) **Filtering with Exclude and Extract**

`Extract<T, U>` keeps existing union members assignable to `U`. `Exclude<T, U>` drops those members. An intersection instead imposes both requirements and can refine a broad member into a narrower contract. The operations coincide for some finite literal sets, but differ on broad types and object composition. Their behavior is specified by the [utility-type reference](https://www.typescriptlang.org/docs/handbook/utility-types.html#extracttype-union); their conditional implementation belongs to [the utility owner](<../../../09 Utility Types and Type Transformations/sections/2. Conditional Types/2.2. Exclude Extract NonNullable Pick Omit under the hood.md>).

Save as `filters.ts`.

```typescript
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Role = "admin" | "editor" | "guest";
type LiteralIntersection = Expect<Equal<Role & "admin", "admin">>;
type LiteralExtraction = Expect<Equal<Extract<Role, "admin">, "admin">>;
type WithoutGuest = Expect<Equal<Exclude<Role, "guest">, "admin" | "editor">>;
type BroadIntersection = Expect<Equal<string & "admin", "admin">>;
type BroadExtraction = Expect<Equal<Extract<string, "admin">, never>>;

type Wide = { kind: "circle" | "square"; size: number };
type Refined = Wide & { kind: "circle" };
type Selected = Extract<Wide, { kind: "circle" }>;
type NoMatchingMember = Expect<Equal<Selected, never>>;
const refined: Refined = { kind: "circle", size: 3 };
console.log(refined.kind, refined.size);
// const selected: Selected = refined; // TS2322

type Variant = { kind: "circle"; radius: number } | { kind: "square"; side: number };
type SelectedCircle = Extract<Variant, { kind: "circle" }>;
const selectedCircle: SelectedCircle = { kind: "circle", radius: 4 };
console.log(selectedCircle.kind, selectedCircle.radius);
// const wrong: SelectedCircle = { kind: "square", side: 4 }; // TS2322
```

The output is `circle 3`, then `circle 4`. `string` is not assignable to the narrower literal `"admin"`, so extraction keeps nothing, while the intersection is that literal. Similarly, `Wide` is one object type whose tag permits two values; that whole member is not assignable to a circle-only contract. `Refined` imposes the narrower tag, whereas `Selected` is `never`. Once `Variant` represents the alternatives as separate members, extraction can select the circle member with its `radius` field.

Choose extraction when the question is “which existing variants match?” Choose an intersection when the question is “which values satisfy both requirements?” Neither choice adds or removes items in a runtime array. A real array filter needs an executed condition, such as the guards in [control-flow narrowing](<../3. Control Flow Narrowing/3.1. Built-in narrowers typeof instanceof in and equality.md>).

### 4) **Common confusion**

The broad-versus-literal distinction matters even when two types admit similar examples. `Extract<"a" | "b", "a">` selects a listed member, whereas `Extract<string, "a">` cannot carve a literal from the broad `string` member. Intersection can impose that literal requirement. Treating the difference as a naming preference leads to unexpected `never` results.

A union also has no promised source ordering for your algorithm. Reversing a finite literal union's spelling does not turn it into an ordered pipeline. Conditional distribution has its own syntax rule involving a bare type parameter; the full rule is taught in [conditional types](<../../../09 Utility Types and Type Transformations/sections/2. Conditional Types/2.1. Conditional fundamentals distributive law and never branches.md>), rather than inferred from a hover.

### 5) **Performance note**

These type operations erase. The runtime spread in `stamp` still copies properties, the loop still iterates, and `.trim()` still executes. A growing product of independent alternatives can make a type harder to inspect, but these examples establish no formula for checker work or equal-cost claim for intersection and extraction. If a real project becomes slow, measure through [extended diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) before changing its model.

### 6) **Mentor note**

Start with the finite-role examples, then replace `Role` with `string` and ask why only extraction becomes `never`. A strong explanation names assignability of the existing member, rather than saying both operations find an overlap. Next compare `Wide` with `Variant`; ask which representation retains a circle-specific field after extraction and have the learner construct its result without a cast.

As an augmentation exercise, add `{ actorId: string }` to `Variant`. Both variants should still construct and narrow, a missing `actorId` should fail, and an unguarded `radius` read should fail. These checks distinguish applying a common requirement from selecting one alternative.
