## 6.1. Common interview QA — unions, intersections and narrowing

### 1) **Why can I only access common members of `A | B` without narrowing?** (the set-safety argument)

**Definition** — `A | B` exposes only the *intersection of the members' properties* — those present on every branch — because the value might be either — reading an exclusive key `a.a` when the value is actually `B` returns `undefined` in that runtime — the checker proves `u.common` is safe by intersecting member N, blocks `u.exclusive` until you prove which member it is with `in`/`===`/`typeof`/`instanceof`.

**What problem it solves / history** — early type systems exposed every property and punished the forgotten guard later — JavaScript's runtime `undefined` leak made it concrete — TypeScript's common-property gate (since 1.6) flipped the default to "prove which branch."

**Modern guidance** — as of TypeScript 5.9 era, treat `u.exclusive` error as instruction, not ceremony — add `if ("exclusive" in u)` or `if (u.kind==="a")` — the exclusive member then auto-completes inside that block. Never silence past the gate with `as A` — it compiles but disables the proof for the next reviewer.

**Runnable example** — common exposes, exclusive gates (good vs bad, `tsc --strict`):

```typescript
type A = { kind: "a"; value: string; common: number };
type B = { kind: "b"; other: boolean; common: number };
type AB = A | B;
function use(x: AB): void {
  console.log(x.common); // ok — common
  // console.log(x.value); // error TS2339: not common — need narrowing
  if (x.kind === "a") console.log(x.value); // ok — narrowed to A
  else console.log(x.other); // narrowed to B
}
use({ kind: "a", value: "hi", common: 1 });

// bad — widen past gate with cast hides missing branch
function useBad(x: AB): string { return (x as A).value; } // compiles even when x is B — wrong value at runtime
// fix — narrow with kind/in before reading exclusive
```

**Common confusion** — "`x?.value` fixes the gate" — `?.` yields `number|undefined` but `B` does not have `value` at all — the optional read masks the member absence instead of proving it. "`in` always fixes" — `in` must check an exclusive key — `"common" in x` proves nothing because both have `common` — use `kind ===`.

**Performance note** — gate is O(members×properties) per call site — checker-only — zero emit — no runtime cost beyond the proving `===`/`in`.

**Mentor note** — have candidate read `type U = { a: number } | { b: number }`, ask "can you read `u.a`?" — answer is "only after you prove it." Then ask "how?" — answer is `in` or `kind` — one narrowing concept checked.

### 2) **When does `{ kind: "a" } & { kind: "b" }` become `never` — and how do you catch it?** (conflicting literal intersection)

**Definition** — intersected discriminants disagree — no value satisfies both — the overlapped key collapses to `never` — `type Bad = { kind: "a" } & { kind: "b" }` is `{ kind: never }` — construction with either literal errors (`"a"` not assignable to `never`). Detect via hover (key shows `never`), probing `const _p: Bad = { kind: "a" }` errors, or `interface extends` reporting `TS2430` at declaration (see [2.1](<../../2. Intersection Types/2.1. Intersection fundamentals merging object shapes.md>)).

**What problem it solves / history** — `&` intended as augmentation over a union alternative collapses to dead branch — handler typed over `Circle & Square` never executes on real payloads — early hover catches the bug before shipping — laziness of `type` definitions makes probe mandatory beyond just writing the alias.

**Modern guidance** — as of TypeScript 5.9 era, after defining any `&`, hover the result — `never` member signals operator bug — fix with `|` when alternatives — use `interface extends` for public composites so TS2430 surfaces at boundary.

**Runnable example** — conflicting & vs alternative | (good vs bad, `tsc --strict`):

```typescript
type A = { kind: "a"; x: number };
type B = { kind: "b"; y: number };
type Both = A & B; // { kind: never; x:number; y:number }
// const both: Both = { kind: "a", x: 1, y: 2 }; // error — "a" not assignable to never

// good — alternative is |, not &
type Either = A | B;
const a: Either = { kind: "a", x: 1 }; // ok

// compatible overlap — narrowing, not collapse
type C = { role: "admin" | "user"; level: number };
type D = { role: "admin"; team: string };
type Narrow = C & D; // role "admin" — compatible intersection narrows, not collapses
const admin: Narrow = { role: "admin", level: 3, team: "platform" }; // ok
```

**Common confusion** — "`never` means the whole `&` empty" — siblings remain (`x`, `y`) — only `kind` impossible — whole value cannot be constructed without `as`. "The type line should have errored" — `type` alias never errors alone — add probe or `interface extends`.

**Performance note** — collapse is checker-only — zero emit — cost is bug triage when handler typed over dead branch — early hover saves downstream runtime debugging.

**Mentor note** — hand two types with literal overlap that collides via `&`, ask to predict hover — then sketch fix with `|` and compatible narrowing — one-operator decision checked.

### 3) **How do you make a `switch` on a discriminated union exhaustive — and why `never`?** (proof every variant was handled)

**Definition** — each `case` narrows to one member — after covering every discriminant literal, the trailing value's narrowed type *is* `never` — assignment `const _e: never = value;` / call `return assertNever(value);` under `default:` proves no branch remains — missing variant leaves narrowed type as that variant, not `never` — assignment errors — PR blocked until case added.

**What problem it solves / history** — `default: break` swallowed new variants — reducer returned stale state — `never` sink makes omission a compile error via `never`'s property (assignable only from unreachable code — see [2.3 never](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.3. never and void bottom vs deliberate nothing.md>)).

**Modern guidance** — as of TypeScript 5.9 era, add `default: return assertNever(x);` to every `switch(kind)` over a public discriminated union or literal set that may grow — `Shape`, `Action`, `APIStatus`. Use `function assertNever(x: never): never { throw new Error("Unexpected " + JSON.stringify(x)); }` — shared util, imported everywhere; skip only closed local primitives (`string|number` in one function).

**Runnable example** — switch with never sink proves exhaustive vs missing-variant fallthrough (good vs bad, `tsc --strict`):

```typescript
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; side: number }
  | { kind: "triangle"; base: number; height: number };

function assertNever(x: never): never { throw new Error(`Unexpected ${JSON.stringify(x)}`); }

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2;
    case "square": return shape.side ** 2;
    case "triangle": return (shape.base * shape.height) / 2;
    default: return assertNever(shape); // exhaustive — add | { kind: "ellipse" } and this errors
  }
}
console.log(area({ kind: "circle", radius: 2 }).toFixed(2)); // 12.57

// bad — missing case fell through default returning stale value
function areaBad(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2;
    case "square": return shape.side ** 2;
    case "triangle": return (shape.base * shape.height) / 2;
    default: return 0; // stale 0 when Shape gains new kind — no error, PR merged silently
  }
}

// good — if/else trailing assert variant
function areaElse(shape: Shape): number {
  if (shape.kind === "circle") return Math.PI * shape.radius ** 2;
  if (shape.kind === "square") return shape.side ** 2;
  if (shape.kind === "triangle") return (shape.base * shape.height) / 2;
  // else { const _e: never = shape; return assertNever(_e); }
  return assertNever(shape);
}
```

**Common confusion** — "`default: break` exhaustive" — `break` leaves unhandled variant open after `switch` — missing variant inherits post-switch valid path — never sink required. "`never` is a value returned" — you never *return* `never` — you assign remaining narrowed type to `never`; `assertNever` helper returns `never` via `throw`.

**Performance note** — `never` assignments erase — `assertNever` is one `throw` helper — never taken on success — zero cost.

**Mentor note** — exercise: extend Shape with `{ kind: "ellipse"; rx: number; ry: number }` without updating `area` — demonstrate error on `assertNever(shape)` line — fix by adding `case "ellipse"` — each student experiences PR gate.

### 4) **When does `typeof` narrow and when do you need a custom predicate?** (runtime-checkable vs expression-level narrowing)

**Definition** — `typeof x === "string"` narrows primitive unions (`string | number | bigint | …`); custom predicate `isCircle(x): x is Circle` narrows object unions where built-ins do not prove the property — `isCircle` encapsulates arbitrary `"radius" in x` / shape checks into a reusable `x is T` call.

**What problem it solves / history** — built-ins suffice for primitive or disjoint-key splits — complex business rule that "looks like Circle because radius numeric and kind absent" needs a reusable narrow with one token site — predicates import that proof to every `if (isCircle(x))` call.

**Modern guidance** — as of TypeScript 5.9 era, prefer direct `typeof` for primitive unions — no predicate indirection — prefer single `in` / `kind===` at call sites for one-off object splits; lift to `is*` only when the same complex check repeats (3+ sites) or when validation is non-trivial — keep predicate body sound (return `true` iff the value really is that member) — unsound predicate narrows wrongly and ships property read mismatch.

**Runnable example** — typeof vs predicate for unions (good vs bad, `tsc --strict`):

```typescript
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Shape = Circle | Square;

function areaPrimitive(v: string | number): string {
  if (typeof v === "string") return v.toUpperCase(); // typeof narrows primitive union — predicate overhead unnecessary
  return v.toFixed(2);
}
console.log(areaPrimitive("hi")); // HI
console.log(areaPrimitive(3.14)); // 3.14

// good — complex check encapsulated as predicate, reused
function isCircle(shape: Shape): shape is Circle { return shape.kind === "circle"; }
function area(shape: Shape): number {
  if (isCircle(shape)) return Math.PI * shape.radius ** 2; // narrowed to Circle — predicate reuses test
  return shape.side ** 2;
}

// bad — predicate returning boolean never narrows callers
function isCircleBool(shape: Shape): boolean { return shape.kind === "circle"; }
function areaBad(shape: Shape): number {
  if (isCircleBool(shape)) return Math.PI * (shape as Circle).radius ** 2; // needs cast — boolean not narrowing
  return (shape as Square).side ** 2;
}
// fix — signature above (shape is Circle) — callers narrowed automatically
```

**Common confusion** — "any boolean wrapper narrows" — only `x is T` tag produces narrowing — `boolean` leaves caller unchanged. "Predicate body type-checked for soundness" — no, body still must return boolean — checker does not prove body matches `is T` — soundness is a reviewer contract.

**Performance note** — predicates add one call frame per call site vs inline `===` — trivial — reuse scales review cost, not emission — for extremely hot loops a direct equality may be measurably cheaper than the extra frame.

**Mentor note** — ask "when does `typeof` suffice?" — answer `string | number` etc. — then "when predicate?" — more than 2 steps or reused across files.

### 5) **`in` vs `x is T` vs `asserts x is T` — which narrows, when, and for whom?** (caller vs callee, throwing vs returning)

**Definition** — `if ("a" in x)` checks *key presence* at runtime and narrows both branches of the `if/else` — `if (isT(x))` via predicate `x is T` narrows the `true` branch to `T` and the `else` to the complement — `asserts x is T` returns `void` but narrows *after* the call — if `x` was not `T`, it throws instead of falling through — use `in` for one-off property proof, `is T` for reusable `if/else` split, `asserts` for invariant fail-fast.

**What problem it solves / history** — predicates require branching logic at every call site — assertions let fails within — choice determines whether the non-`T` branch is handled (predicate bifurcates), not thrown — library shape differs when the consumer must succeed vs must fail when precondition absent.

**Modern guidance** — as of TypeScript 5.9 era, use `in`/`kind===` for single-site split, `isT` when the same test repeats across files or hides multi-step validation, `asserts` when violation should throw and the post-call body expects `T` — write `function assertIsMember(x: T): asserts x is Valid` with body throwing when not valid — never silent guard at call site — the checker narrows only as well as your body throws.

**Runnable example** — three narrowers on one union (good vs bad, `tsc --strict`):

```typescript
type Text = { text: string };
type Image = { src: string; alt: string };
type Node = Text | Image;

// good — 'in' at single site, no helper
function renderIn(node: Node): string {
  if ("text" in node) return node.text; // narrowed via key presence — both branches handled
  return `[img ${node.src}]`;
}
console.log(renderIn({ text: "hi" })); // hi

// good — predicate for reuse (splits if/else)
function isText(node: Node): node is Text { return "text" in node; }
function renderIs(node: Node): string {
  if (isText(node)) return node.text; // narrowed via predicate
  return `[img ${node.src}]`; // complement
}

// good — assert for invariant (throws, no else)
function assertIsText(node: Node): asserts node is Text {
  if (!("text" in node)) throw new Error("Expected Text");
}
function textContent(node: Node): string {
  assertIsText(node); // after this call, node narrowed to Text
  return node.text;
}
console.log(textContent({ text: "hi" })); // hi

// bad — predicate typed as boolean never narrows else branch caller
function isTextBool(node: Node): boolean { return "text" in node; }
function renderBad(node: Node): string {
  if (isTextBool(node)) return (node as Text).text; // needs cast
  return (node as Image).src;
}
```

**Common confusion** — "`in` is weaker than `is`" — `in` narrows the lexical branch as strongly as the predicate's `true` branch; predicate ns widen to a reusable token and splits else automatically — `in` is broader for one-site — predicate scales reuse — asserts guarantee after-call `T` regardless of `if` placement — three operators serve distinct call-site ergonomics. "Assertion should return boolean" — `asserts` returns `void` and throws on non-`T` — caller learns `T` via fallthrough, not branch on boolean.

**Performance note** — `in` is one opcode key-presence test; predicate/assert are one function call plus that test — call overhead only when reuse justifies — assertion carries extra factory for throwing helper — still trivial.

**Mentor note** — exercise: give `type A = string | { items: string[] }` union — ask which narrower to use at single site — answer `typeof` vs `in`; then a shared validator across two files — answer predicate; then invariant before upload — answer asserts. Show diff of `boolean` vs `is T` captured when caller needs else.
