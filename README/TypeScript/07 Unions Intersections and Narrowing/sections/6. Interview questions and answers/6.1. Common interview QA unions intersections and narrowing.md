## 6.1. Common interview QA — unions intersections and narrowing

Use these questions to test reasoning from accepted inputs to safe operations. A strong answer predicts a compiler result, explains its cause and distinguishes it from runtime behavior. The short answers link to the full owners; the three programs provide concrete follow-up evidence.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each TypeScript fence under its filename and compile independently with `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`. Run `node dist/FILE.js`. Activate each commented negative individually and check with the same flags plus `--noEmit` instead of `--outDir dist`.

### 1) **Why can I only access common members of a union without narrowing**

An operation must be valid for each alternative still permitted at that point. If one alternative lacks a property, reading it requires further evidence. A common property may itself have a union of value types, and a common method name does not guarantee every argument list is callable. Explain the actual operation rather than mechanically counting keys.

Follow-up: does optional chaining establish the missing property? No. It handles a nullish receiver or optional segment; it does not add an exclusive property to another union member. Follow-up: can a union accept an object with both sets of fields? Yes, when it satisfies at least one structural alternative; union does not mean exact object shape. [Union fundamentals](<../1. Union Types/1.1. Union fundamentals member access and the common property rule.md>) owns both points.

### 2) **When does a conflicting intersection become never and how do you detect it**

In the conflicting literal-tag example below, the entire intersection reduces to `never`. Sibling access fails too. An ordinary string/number property conflict can instead leave a non-never object type with an impossible field. Check the particular whole type or property, and try constructing the fixture you intended without an assertion.

Follow-up: is accepting the type alias proof that a value exists? No. Follow-up: where can an interface report conflict earlier? Multiple incompatible parents report TS2320 in the composition example; an incompatible single-parent extension reports TS2430. Do not substitute a guessed diagnostic or hover for an observed check. [The never trap](<../2. Intersection Types/2.2. The never trap conflicting intersections and impossible states.md>) and [intersection fundamentals](<../2. Intersection Types/2.1. Intersection fundamentals merging object shapes.md>) own the distinction, supported by [the primary discriminant-reduction notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-9.html#intersections-reduced-by-discriminant-properties).

Save as `contracts.ts` to test the first two answers.

```typescript
type A = { kind: "a"; common: string; a: number };
type B = { kind: "b"; common: string; b: boolean };
type Input = A | B;
function describe(input: Input): string {
  const label = input.common;
  return input.kind === "a" ? `${label}:${input.a}` : `${label}:${input.b}`;
}
console.log(describe({ kind: "a", common: "left", a: 1 }));
console.log(describe({ kind: "b", common: "right", b: true }));
// function exclusive(input: Input) { return input.a; } // TS2339
// function optional(input: Input) { return input?.a; } // TS2339 too
const bothFields = { a: 1, b: true };
const inclusive: { a: number } | { b: boolean } = bothFields;
console.log("a" in inclusive, "b" in inclusive);

type Expect<T extends true> = T;
type IsNever<T> = [T] extends [never] ? true : false;
type Both = A & B;
type Ordinary = { value: string; id: string } & { value: number };
type Whole = Expect<IsNever<Both>>;
type Field = Expect<IsNever<Ordinary["value"]>>;
type ObjectRemains = Expect<IsNever<Ordinary> extends false ? true : false>;
// const impossible: Both = { kind: "a", common: "x", a: 1, b: true }; // TS2322
// function sibling(input: Both) { return input.common; } // TS2339
```

The output is `left:1`, `right:true`, then `true true`. The three live type assertions check whole-type and property reduction independently. The optional-chaining alternative still reports a missing property; it does not return a synthesized optional value.

### 3) **How do you make a discriminated-union switch exhaustive and why never**

Place an operation requiring `never` where all declared alternatives should have been eliminated. A remaining member cannot satisfy that requirement. Adding a variant then makes the handler fail until the new behavior is supplied. This is about the declared input and control-flow paths, not the visibility of the function or an arbitrary number of cases.

Follow-up: does a never annotation insert a runtime throw? No. A declaration such as `const complete: never = input` retains its variable and initializer after the annotation erases. A helper must actually throw if that is the desired runtime policy. A permissive default may return a valid value while concealing a missing variant. [Exhaustiveness](<../3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>) owns the complete comparison, following [the primary never-sink pattern](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#exhaustiveness-checking).

Save as `coverage.ts`.

```typescript
type Event = { kind: "start"; id: string } | { kind: "stop"; reason: string };
function assertNever(_value: never): never { throw new Error("Unhandled event"); }
function describe(event: Event): string {
  switch (event.kind) {
    case "start": return `start ${event.id}`;
    case "stop": return `stop ${event.reason}`;
    default: return assertNever(event);
  }
}
console.log(describe({ kind: "start", id: "j1" }), describe({ kind: "stop", reason: "done" }));
try { describe({ kind: "pause" } as unknown as Event); } // Deliberate invalid-input experiment.
catch (error) { console.log(error instanceof Error ? error.message : "unexpected error"); }
export {}; // Keep this Event separate from the DOM Event declaration.
```

The output is `start j1 stop done`, then `Unhandled event`. Add `| { kind: "pause"; seconds: number }` to Event and leave the handler unchanged: TS2345 reports the pause alternative at the helper. The compiler check does not parse external events or validate a handled variant's payload; those remain separate input-boundary obligations.

### 4) **When does typeof suffice and when is a custom predicate useful**

Use a built-in check when it directly establishes the distinction needed at this site. `typeof` works for a string versus object union; an object tag or property check can distinguish known object alternatives. A reusable predicate is useful when callers need a named, shared type distinction or a compatible filtering signature. Its benefit is expressing that contract, not meeting a repetition-count rule.

Follow-up: must every predicate explicitly write `is`? No. Eligible unannotated functions can infer predicates on the current baseline. An explicit boolean return omits that narrowing contract. Follow-up: is returning true only for some circles a valid Circle predicate? Not if false still permits a circle: callers also rely on exclusion in the false branch. [Custom narrowers](<../3. Control Flow Narrowing/3.3. Custom narrowers predicates asserts and type guards on unions.md>) demonstrates that failure; [the primary inference explanation](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-5.html#inferred-type-predicates) describes the two-sided meaning.

### 5) **How do in predicates and assertions differ for the caller**

An `in` expression checks property presence, including the prototype chain. Its narrowing depends on the current contract; optional members may remain on both paths. A predicate communicates a true/false type distinction through a function's signature. An assertion communicates facts after a normal return and should implement the required rejection behavior when those facts do not hold. An assertion signature alone does not verify its body's honesty.

Follow-up: does `asserts condition` merely remember a boolean? It can narrow the variable referenced by a condition such as `result.ok`. Follow-up: does Object.hasOwn automatically replace an in guard's inference? It returns a boolean without that object-union refinement on this baseline; own presence also asks a different question. See [built-in guards](<../3. Control Flow Narrowing/3.1. Built-in narrowers typeof instanceof in and equality.md>) and [object-shape checks](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.3. satisfies assertions and narrowing on object shapes.md>).

Save as `guards.ts` to test the last two answers.

```typescript
function size(value: string | { items: string[] }): number {
  return typeof value === "string" ? value.length : value.items.length;
}
console.log(size(""), size({ items: ["a", "b"] }));
type Success = { ok: true; value: string };
type Failure = { ok: false; error: string };
type Result = Success | Failure;
function byPresence(result: Result): string {
  return "error" in result ? result.error : result.value;
}
const isSuccess = (result: Result) => result.ok === true; // Inferred predicate.
function booleanSuccess(result: Result): boolean { return result.ok === true; }
function byPredicate(result: Result): string {
  return isSuccess(result) ? result.value : result.error;
}
function assert(condition: unknown): asserts condition {
  if (!condition) throw new Error("success required");
}
function byAssertion(result: Result): string {
  assert(result.ok);
  return result.value;
}
// function afterBoolean(result: Result) { if (booleanSuccess(result)) return result.value; } // TS2339
const success: Success = { ok: true, value: "saved" };
const failure: Failure = { ok: false, error: "offline" };
console.log(byPresence(success), byPresence(failure));
console.log(byPredicate(success), byPredicate(failure), byAssertion(success));
try { byAssertion(failure); }
catch (error) { console.log(error instanceof Error ? error.message : "unexpected error"); }
```

The output is `0 2`, `saved offline`, `saved offline saved`, then `success required`. The predicate handles both alternatives; the assertion stops the failure continuation. All three start from a trusted Result contract, so these tag/presence checks do not establish every field of arbitrary unknown data.

### 6) **Common confusion**

An accepted assertion is not runtime evidence. Neither casting a union member nor assigning a forced value to never establishes that the program can safely perform an operation. A sound answer separates accepted inputs, checker refinement, emitted operations and the observed result.

Intersection and Extract also answer different questions. Extract selects existing assignable members, while intersection imposes simultaneous requirements and can refine a broad member. They coincide in some finite literal examples; [distribution and filtering](<../2. Intersection Types/2.3. Unions and intersections distributive behavior and primitive intersections.md>) supplies counterexamples to universal equivalence.

### 7) **Performance note**

Type-level unions, intersections and guard signatures erase; branch conditions, calls and throws remain. No interview answer here establishes a universal speed ranking for guards, a variant-count dispatch threshold or a checker-work formula. A useful performance answer identifies the remaining runtime work and the measurement needed, instead of treating erased annotations as erased application logic.

### 8) **Mentor note**

Ask for a prediction before showing a diagnostic. Change one assumption at a time: add an alternative, make a key optional, publish boolean instead of an inferred predicate, or force an invalid runtime value. A strong candidate updates the reasoning and names which evidence changed. Memorizing a hover spelling or diagnostic number without the assignment direction is insufficient.

For the coverage exercise, implement pause as `pause Ns`, verify all three event outputs, and retain the sink. Then explain why casting a raw payload to Event would still leave payload validation unresolved. This joins the static extension check to the runtime behavior without turning the interview into a duplicate parsing lesson.
