## 1.3. Literal unions — enums vs unions and exhaustiveness preview

### 1) **A finite type and a runtime membership test serve different callers**

A literal union names a finite set of allowed values, such as "light" | "dark". It helps checked callers avoid invalid spellings. The type itself does not create an array of values or validate an unknown input. A retained runtime collection can provide the allowed values for both type derivation and an actual membership test.

Use TypeScript **7.0.2** and Node **20.20.2**, verified 2026-10-15. Save each named program in its own fresh directory without tsconfig.json. Build with `tsc --strict --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then run `node dist/FILE.js`. All three positive programs exit 0. Activate one marked negative in a separate copy and replace `--outDir dist` with `--noEmit` to observe its checker failure. The enum example deliberately requires transformation; its separate erasable gate failure is described in part 2.

Save `finite.ts`:

```typescript
export {};
const THEMES = ["light", "dark"] as const;
type Theme = typeof THEMES[number];
function paint(theme: Theme): string { return "paint " + theme; }
function isTheme(value: unknown): value is Theme {
  return THEMES.some(theme => theme === value);
}
function parseTheme(value: unknown): Theme {
  if (!isTheme(value)) throw new Error("Invalid theme");
  return value;
}
console.log(paint("light"), parseTheme("dark"));
console.log("membership:", isTheme("light"), isTheme("auto"), isTheme(42));
try { parseTheme("ligth"); }
catch (error: unknown) { console.log(error instanceof Error ? error.message : "unexpected"); }
type ThemeEvent = `theme:${Theme}`;
const event: ThemeEvent = "theme:dark";
console.log(event);
// paint("ligth"); // TS2345: invalid checked argument.
// const wrongEvent: ThemeEvent = "theme:night"; // TS2820: invalid spelling with a suggestion.
```

Output is `paint light dark`, `membership: true false false`, `Invalid theme`, then `theme:dark`. The literal type checks paint's typed caller; parseTheme actually checks the unknown input before returning a Theme. The predicate's behavior agrees with the finite source array in these cases. An annotation claiming a predicate is not itself proof that its body validates correctly; see [custom narrowers](<../3. Control Flow Narrowing/3.3. Custom narrowers predicates asserts and type guards on unions.md>).

Const capture preserves the literal members for the indexed type query. It gives a readonly checked view of the array, not runtime freezing. The array, some call and error branch remain in JavaScript while Theme and ThemeEvent erase. [Literal types](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>) owns capture/widening; [template literal types](<../../../09 Utility Types and Type Transformations/sections/3. Transformations in Practice/3.2. Template literal composition Capitalize handlers and routes.md>) owns general string composition. Here the template simply derives the two event spellings.

### 2) **Enums can participate in type operations while still requiring emit**

Literal unions, runtime const objects and enums make different contracts. A union alone creates no runtime object. A const object retains an ordinary object whose values can supply a union. A regular enum creates runtime output through TypeScript transformation and also supplies enum member types. The inability of a strip-only pipeline to transform enum syntax does not mean enum member types cannot be filtered or interpolated.

Save `enum-comparison.ts`:

```typescript
export {};
const Status = { Draft: "draft", Published: "published" } as const;
type StatusValue = typeof Status[keyof typeof Status];
const status: StatusValue = Status.Draft;
console.log("const object:", status, Object.keys(Status).join(","));
enum Theme { Light = "light", Dark = "dark" }
type LightOnly = Exclude<Theme, Theme.Dark>;
type ThemeEvent = `theme:${Theme}`;
const selected: LightOnly = Theme.Light;
const event: ThemeEvent = "theme:dark";
console.log("string enum:", selected, event, Theme.Dark);
// const excluded: LightOnly = Theme.Dark; // TS2322.
// const raw: Theme = "light"; // TS2322: plain string literal is not the enum member type.
enum NumericStatus { Draft, Published }
type PublishedOnly = Exclude<NumericStatus, NumericStatus.Draft>;
type StatusText = `${NumericStatus}`;
const published: PublishedOnly = NumericStatus.Published;
const text: StatusText = "1";
console.log("numeric enum:", published, text, NumericStatus[0]);
function consume(value: NumericStatus): number { return value; }
const external: number = 42;
console.log("number boundary:", consume(NumericStatus.Draft), consume(external), consume(NumericStatus.Draft + 10));
function isStatus(value: unknown): value is NumericStatus {
  return value === NumericStatus.Draft || value === NumericStatus.Published;
}
console.log("validated:", isStatus(0), isStatus(42));
// consume(42); // TS2345: an out-of-set numeric literal is rejected.
// const wrongMember: PublishedOnly = NumericStatus.Draft; // TS2322.
```

Output is `const object: draft Draft,Published`, `string enum: light theme:dark dark`, `numeric enum: 1 1 Draft`, `number boundary: 0 42 10`, then `validated: true false`. Exclude works over the enum member union when its excluded operand identifies the intended member. Template interpolation works for these string and numeric enums too. The [primary union-enum notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#all-enums-are-union-enums) describe enum member types, and the [template reference](https://www.typescriptlang.org/docs/handbook/2/template-literal-types.html) explains union interpolation. The local program verifies these exact accepted operations; literal unions are not the only types usable with them.

The numeric boundary is deliberately asymmetric: the broad number view and arithmetic result are accepted, while consume(42) is rejected. Do not describe NumericStatus as simply unrestricted number, and do not treat its static contract as input validation. isStatus supplies a runtime membership decision for this enum. Conversely, the raw string "light" is not accepted as Theme, while Theme.Light is accepted as its member. A literal union is a finite structural value set, not automatically a nominal identity.

Inspect dist/enum-comparison.js: Status remains an object; regular enum initializers construct runtime enum objects. The numeric enum has the shown reverse mapping; the string enum does not gain a numeric reverse map. Add `--erasableSyntaxOnly --noEmit` to this example's build command: both enum declarations are rejected with TS1294, exit 1. The finite.ts and exhaustive.ts examples pass the same gate. Erasable syntax does not mean their runtime arrays, objects or calls disappear.

Choose a literal union when plain finite values and an erasable source contract fit. Retain a const object when callers need named runtime constants without enum transformation. An existing enum API or desired enum-member contract can justify using enums in a pipeline that supports them. This is a pipeline/API choice, not a universal ban. Full regular/const enum and numeric-compatibility details belong in [Enums and Literal Types](<../../../11 Enums and Literal Types/README.md>); [execution paths](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>) owns runner capabilities. This example executed emitted JavaScript; no native source-stripping execution is claimed.

### 3) **A never sink checks remaining alternatives and retains ordinary runtime code**

After every Direction member is handled, the remaining dir type is never. Assigning it to a never-annotated local checks that no declared alternative remains. Adding a member without another case makes that assignment fail. The annotation erases; its const declaration and the explicit throw do not disappear merely because the checker considers the branch unreachable.

Save `exhaustive.ts`:

```typescript
export {};
type Direction = "up" | "down";
function move(dir: Direction): string {
  switch (dir) {
    case "up": return "y+1";
    case "down": return "y-1";
    default: {
      const exhaustive: never = dir;
      throw new Error("Unhandled " + exhaustive);
    }
  }
}
function fallback(dir: Direction): string {
  switch (dir) {
    case "up": return "y+1";
    case "down": return "y-1";
    default: return "unknown";
  }
}
console.log(move("up"), move("down"));
console.log("fallback:", fallback("sideways" as Direction));
try { move("sideways" as Direction); } // Deliberate assertion bypass to observe the retained runtime branch.
catch (error: unknown) { console.log(error instanceof Error ? error.message : "unexpected"); }
```

Output is `y+1 y-1`, `fallback: unknown`, then `Unhandled sideways`. The double-purpose lesson is visible: the declared exhaustive handler catches a missing case during checking, while its explicit runtime throw can still reject an asserted unexpected value. The fallback function accepts such a value at runtime by design. Neither static exhaustiveness nor an assertion validates an external string.

**Evolution exercise:** extend Direction with "sideways". Checking move now fails with TS2322 at the never assignment. Add `case "sideways": return "x+1,y+1";` and verify that move("sideways") returns that string. A blanket default would instead swallow the newly declared alternative without forcing a decision. Use an intentional fallback when unknown/future values really should be handled generically; use explicit completeness when a missing known variant is a defect. The [exhaustiveness owner](<../3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>) develops helper and control-flow patterns beyond this preview.

### 4) **Common confusion**

A literal union supplies a checker contract, not a runtime list or validator. A const object remains a runtime object even though its type query erases. Enums can support Exclude and template interpolation while still failing an erasable-syntax gate. An arithmetic value's acceptance does not prove every numeric literal is assignable to an enum. A never annotation does not delete the declaration or throw beside it.

### 5) **Performance note**

Aliases, predicates' type annotations and type transformations erase. The runtime array scan, const object, enum initialization, branch tests and throw remain. Which runtime constants an application needs depends on its consumers; replacing an enum with an object can still retain a runtime object. No bundle size, enum retention cost, per-assignment checker formula or universal literal-count threshold was measured here. Template union combinations can multiply the number of possible strings, but their actual checking impact needs measurement rather than a fixed review quota. Use the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) for checking evidence and a runtime profiler for executing work.

### 6) **Mentor note**

Ask the learner to identify the runtime producer for each value: the literal passed to paint, the array used by parseTheme, the const object property and the enum member. Then remove a type alias and inspect what still exists in JavaScript. A strong answer distinguishes checking from actual data and validation.

For the enum comparison, require all three numeric observations rather than accepting “enums are numbers” as a complete answer. For exhaustiveness, add the new member before adding the implementation, observe TS2322 and then demonstrate the repaired behavior. Finally, explain why the forced sideways call can reach a supposedly unreachable branch: the assertion discarded the checker evidence while the runtime value remained.
