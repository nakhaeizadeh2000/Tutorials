## 1.3. Literal unions — enums vs unions and exhaustiveness preview

### 1) **Literal union as a finite set** (a type that is exactly N strings/numbers/booleans)

**Definition** — a *literal union* is a `|` over literal types — `type Direction = "up" | "down" | "left" | "right"` — each member is one exact value. The type admits only those values, rejects everything else, and provides a finite set for `switch` and exhaustive narrowing. No `enum` emit or reverse map is needed — the literals *are* the values at runtime too.

**What problem it solves / history** — JavaScript modeled finite sets as ad-hoc strings — `"up"` vs `"north"` typos survived as runtime bugs, and `string` swallowed every misspelling. `enum` organized them but added emit and a non-erasable transform (see [3.3. Choosing erasable syntax](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>)). Literal unions give the same set *without* emit — every spelling is checked, every missing case can be proved with `never` (see [3.2. Exhaustiveness](<../3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>)), and template literal types can compose them (`${Prefix}_${Suffix}`).

**Modern guidance** — as of TypeScript 5.9 era, prefer literal unions for finite sets — `type Theme = "light" | "dark"`, `type Method = "get" | "post" | "put" | "delete"`, `type Role = "admin" | "editor" | "viewer"`. Use `as const` on the source object to derive the union (`const THEMES = ["light","dark"] as const; type Theme = typeof THEMES[number]`) so the runtime array and the type stay synchronized. Keep the set below ~20 members for hover readability; beyond that model with a `Set`/`Record` lookup keyed by the union instead of a 50-branch `switch`.

**Runnable example** — literal union as validated set (good vs bad, `tsc --strict`):

```typescript
// good — literal union is the set; typos are errors, missing cases are provable
type Theme = "light" | "dark";
type ThemeAction = { kind: "setTheme"; theme: Theme } | { kind: "reset" };

function apply(state: { theme: Theme }, action: ThemeAction): { theme: Theme } {
  switch (action.kind) {
    case "setTheme": return { theme: action.theme }; // 'theme' is Theme, narrowed
    case "reset": return { theme: "light" };
  }
}
console.log(apply({ theme: "light" }, { kind: "setTheme", theme: "dark" })); // { theme: 'dark' }

// good — derived from const array so runtime validation shares the set
const ROLES = ["admin", "editor", "viewer"] as const;
type Role = typeof ROLES[number]; // "admin" | "editor" | "viewer"
function isRole(v: string): v is Role { return (ROLES as readonly string[]).includes(v); }
console.log(isRole("admin")); // true
console.log(isRole("superadmin")); // false

// bad — wide string swallows the set; typos survive
function paintBad(theme: string): void { console.log(theme); }
paintBad("ligth"); // compiles — string accepts any spelling — bug ships
// fix — narrow the param so the checker blocks the typo
function paintGood(theme: Theme): void { console.log(theme); }
// paintGood("ligth"); // error TS2322: not assignable to Theme

// good — union composes with template literals without an enum
type Method = "get" | "post";
type EventName = `on${Capitalize<Method>}`; // "onGet" | "onPost"
const ev: EventName = "onGet"; // ok — derived name, still checked
```

**Common confusion** — "`type Direction = string` is the same as `"up" | "down"`" — `string` allows any spelling — a literal union rejects everything outside the enumerated set — pick the narrow set when the finite members are known. "Literal unions are just `enum` under the hood" — `enum` emits a runtime object and is *not* erasable under `--erasableSyntaxOnly` (TS 5.8+); literal unions erase — zero emit, native strip compatible. "50 literals need an `enum`" — a 50-element literal union is harder to hover but still erasable; an `enum` with 50 members still emits an object; prefer a derived `as const` array + `typeof` union for both readability and single-source truth.

**Performance note** — literal unions erase — identical emit to `string` at runtime (just a string value). Checker cost is O(members) per set check — each assignment walks the members — keep hot-path sets small. Template literal composition over unions (`${A}_${B}`) distributes and can explode combinatorially — `("a"|"b") + ("1"|"2"|"3")` is 6 members; adding a third factor multiplies — cap composition depth in reviews.

**Mentor note** — show the derivation trick as the teaching anchor: `const TAGS = ["user", "admin"] as const` → `type Tag = typeof TAGS[number]` — change the array and the type follows. Ask why `as const` is needed — answer is widening: without it `typeof TAGS[number]` collapses to `string` (see [3.3. Literal types](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>)).

### 2) **Literal union vs `enum`** (literal unions erase and compose — enums emit and constrain)

**Definition** — `enum Status { Draft, Published }` is *both* a type and a runtime value that emits an object with bidirectional mapping — `Status.Draft === 0` and `Status[0] === "Draft"` — and is rejected by `--erasableSyntaxOnly` (TS 5.8+). `type Status = "draft" | "published"` is *only* a type (erasable, zero emit) where the runtime values are plain strings. The choice is emit vs erasable, and composability vs object identity.

**What problem it solves / history** — `enum` predates literal types (added in TypeScript 1.0) to give JavaScript a missing language-level enum. Literal unions arrived later and solved the same finite-set problem without emit — template literals (`${M}_${P}`), `Exclude`/`Extract` filtering, and `as const` derivation all work over unions, not over numeric `enum` members. Node 22.12+'s native type stripping and TS 5.8's `--erasableSyntaxOnly` tilt new code toward literal unions because `enum` requires a transform that strip-only loaders cannot perform.

**Modern guidance** — as of TypeScript 5.9 era, default to literal unions for finite sets in new code — they erase, survive native stripping, compose with `Capitalize`/`Exclude`/template literals, and stay readable in hovers. Use `enum` only when you *need* a runtime value with identity beyond the string — numeric `enum` reverse maps for debugging, or an existing JavaScript `enum` boundary — and isolate the `enum` behind a lint rule that forbids new ones elsewhere. Replace `enum` with `const` object + `as const` for an erasable object that gives both the set and the runtime value (`const Status = { Draft: "draft", Published: "published" } as const`).

**Runnable example** — literal union and const object vs enum (good vs bad, `tsc --strict --erasableSyntaxOnly`):

```typescript
// good — literal union (erasable, composable)
type Theme = "light" | "dark" | "auto";
function setTheme(t: Theme): void { console.log(t); }
setTheme("light"); // ok
// setTheme("night"); // error TS2322

// good — const object gives both runtime value and erasable type
const Status = {
  Draft: "draft",
  Published: "published",
} as const;
type StatusType = typeof Status[keyof typeof Status]; // "draft" | "published"
function publish(s: StatusType): void { console.log(s); }
publish(Status.Draft); // "draft" — runtime + type, still erasable
console.log(Status.Draft); // "draft"

// good — union composes with Exclude and template literals (enum does not)
type ThemeWithoutAuto = Exclude<Theme, "auto">; // "light" | "dark"
type ThemeEvent = `theme:${Theme}`; // "theme:light" | "theme:dark" | "theme:auto"
const evt: ThemeEvent = "theme:dark"; // ok

// bad — enum is non-erasable; breaks --erasableSyntaxOnly and native stripping
enum LegacyTheme { Light, Dark, Auto } // emits object, reverse map for numeric enums
// LegacyTheme.Light === 0, LegacyTheme[0] === "Light" — extra identity beyond the string
// use --erasableSyntaxOnly: enum LegacyTheme { ... } // error TS1294: not erasable
// fix — literal union / const object above

// good — erasable proof: literal set leaves no emit
// input:  type T = "a" | "b"; const x: T = "a";
// output: const x = "a"; // only "a" remains, no trace of T
```

**Common confusion** — "`enum` is type-safe" — numeric `enum` is *unsound* — `LegacyTheme` widens to `number` (`LegacyTheme.Light + 10` compiles), and extra members leak through assignability — literal unions stay nominally strict. "`const enum` solves emit" — `const enum` inlines members at emit but is still non-erasable under `--erasableSyntaxOnly` and requires declaration knowledge across files — prefer literal unions for cross-file tooling speed. "I lose runtime validation without `enum`" — expose `const SET = ["light","dark"] as const` and validate with `SET.includes(value)` at runtime — same check as `enum` includes, still erasable and derived from one source.

**Performance note** — literal unions emit nothing — `enum` emits an IIFE that builds an object with forward *and* reverse mappings (numeric enums double the keys) — measurable bundle cost and extra GC retention for large enums. Numeric `const enum` avoids the emit object by inlining, but the inlining scan costs checker time per use site — literal unions avoid both the emit object and the inlining pass. For toolchain throughput, avoid `enum` in new files — `--erasableSyntaxOnly` is O(1) delete per erasable file; every `enum` forces a row in the non-erasable fallback path.

**Mentor note** — review rule: disallow `enum` in new PRs except when interoperating with generated JavaScript that already exports an `enum`. Exercise: give `enum Role { Admin, Editor }` and ask to rewrite to a `const ROLES` + literal union — students must show `typeof ROLES[keyof typeof ROLES]`, `Exclude<Role, "Admin">`, and `${Role}_role` — only the literal rewrite supports the latter two.

### 3) **Exhaustiveness hook** (`switch` with missing case should break — `never` proves it)

**Definition** — an *exhaustiveness check* is a `never` assignment at the end of a union's handling — `const _exhaustive: never = value` after narrowing all known cases — that *proves* every member was handled. If a new member is added to the union and no branch handles it, the `never` line errors — the compiler becomes the migration guard. The classic pairing is `switch (x.kind) { case "a": …; default: assertNever(x); }` where `assertNever(n: never): never` throws.

**What problem it solves / history** — without exhaustiveness, `switch` `default: break` silently swallows new variants — a new `Shape` kind or `Action` type ships, the reducer returns stale state, and no error fires. The `never` sink (leveraging [2.3. never as bottom](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.3. never and void bottom vs deliberate nothing.md>) — `never` is assignable *only* from unreachable code) turns the omission into a compile error — the next PR that extends the union cannot pass CI until the handler is extended too.

**Modern guidance** — as of TypeScript 5.9 era, add a `never` sink to every `switch`/`if/else` that handles a *public* discriminated union or literal set whose members may grow — API status machines, product-type reducers, permission `Role` switches. Use a tiny helper `function assertNever(x: never): never { throw new Error("Unexpected " + JSON.stringify(x)); }` — one import, every exhaustive site calls `default: return assertNever(x)`. Reserve the bare `const _: never = x` form for one-off exhaustive blocks. Full treatment of exhaustive control flow is in [3.2. Exhaustiveness](<../3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>); this promise is the *preview* that hooks the habit before that leaf.

**Runnable example** — exhaustive preview that breaks when a variant is added (good vs bad, `tsc --strict`):

```typescript
type Direction = "up" | "down" | "left" | "right";

function move(dir: Direction): string {
  switch (dir) {
    case "up": return "y+1";
    case "down": return "y-1";
    case "left": return "x-1";
    case "right": return "x+1";
    default: {
      // good — never sink proves exhaustiveness
      const _exhaustive: never = dir; // if a new Direction member appears, this line errors
      throw new Error(`Unhandled direction: ${_exhaustive}`);
    }
  }
}
console.log(move("up")); // y+1

// good — helper form (idiomatic at production call sites)
function assertNever(x: never): never { throw new Error(`Unexpected ${JSON.stringify(x)}`); }
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; side: number };
function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2;
    case "square": return shape.side ** 2;
    default: return assertNever(shape); // proves Shape is exhausted
  }
}
console.log(area({ kind: "circle", radius: 3 })); // 28.274...

// bad — default silently absorbs new variants (new kind ships, old code stale)
function moveBad(dir: Direction): string {
  switch (dir) {
    case "up": return "y+1";
    case "down": return "y-1";
    case "left": return "x-1";
    case "right": return "x+1";
    default: return "unknown"; // compiles even when Direction gains "diagonal"
  }
}
// fix — replace 'default: return "unknown"' with the never sink above so add-tail fails

// preview — add a new literal and watch the sink error:
// type Direction2 = Direction | "diagonal";
// function move2(dir: Direction2): string {
//   switch (dir) {
//     case "up": return "y+1";
//     case "down": return "y-1";
//     case "left": return "x-1";
//     case "right": return "x+1";
//     default: { const _e: never = dir; /* error TS2322: "diagonal" not assignable to never */ throw _e; }
//   }
// }
```

**Common confusion** — "`default: break` is enough" — `default: break` hides the missing variant — the `never` line is what turns the omission into an error. "`never` is a value you return" — you never *return* `never` — you assign the remaining narrowed type to `never`; reachability makes the assignment valid only when no cases remain. "Exhaustiveness is only for `switch`" — `if/else` chains and `Array.reduce` over discriminated unions get the same sink — `if (x.kind === "a") … else if (…) … else assertNever(x);` also proves coverage.

**Performance note** — `never` sinks erase — `const _exhaustive: never = dir` becomes nothing in emit, `assertNever` survives only as the throwing helper (one allocation per file). The runtime cost is the `default` branch taken *only* when the exhaustive invariant is violated — zero cost on the normal path. Checker cost is one assignment per sink — negligible.

**Mentor note** — seed the convention in the first union PR: ship `assertNever` as a shared util and require its import in every discriminated-union handler review. Exercise: extend `Direction` with `"diagonal"` without updating `move` — show TS2322 on the `never` line — then fix by adding `case "diagonal"` — teaches that the type, not the test suite, protects the next PR.
