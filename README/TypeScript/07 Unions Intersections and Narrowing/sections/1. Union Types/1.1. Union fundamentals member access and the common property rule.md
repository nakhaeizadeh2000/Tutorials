## 1.1. Union fundamentals — member access and the common property rule

### 1) **What `A | B` means** (set union — a value is either — why unions model alternatives)

**Definition** — `type U = A | B` is the set union of `A` and `B` — a value of `U` is *either* an `A` *or* a `B`, never both at the same time in the same check. Writing `string | number` says "this slot accepts a string or a number"; writing `Circle | Square` says "this drawing command is one of those two shapes." Every alternative is an independent member; the checker reasons about each member separately until you narrow.

**What problem it solves / history** — before unions, TypeScript and its predecessors leaned on inheritance or `any` for alternatives — `function print(x: any)` hid which types were actually allowed, and error messages never explained the missing branch. Unions (present since TypeScript 1.4) let the checker *list* the allowed alternatives and then prove that every consumer handles each one. The alternatives stay flat — no class hierarchy, no `instanceof` ceremony — so adding a new case is adding a member to `|`, not extending a tree.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), model alternatives with unions by default — `type Status = "idle" | "loading" | "done"` for UI states, `type Payload = User | Error` for results, `type Event = ClickEvent | KeyEvent` for inputs. Keep unions flat and explicit — `type Result = Ok | Err` reads better at every call site than `class Result extends Base`. Unions erase (see [2.1. Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)) — zero emit, purely checker-side set algebra.

**Runnable example** — union as alternative set (good vs bad, `tsc --strict`):

```typescript
// good — union lists the allowed alternatives explicitly
type Status = "idle" | "loading" | "done";
type Result<T> = { ok: true; value: T } | { ok: false; error: string };

function handle(r: Result<number>): string {
  if (r.ok) return `value ${r.value}`; // narrowed to { ok: true; value: number }
  return `error ${r.error}`; // narrowed to { ok: false; error: string }
}
console.log(handle({ ok: true, value: 42 })); // value 42
console.log(handle({ ok: false, error: "timeout" })); // error timeout

// good — primitives as a union (common at boundaries)
function format(v: string | number): string {
  if (typeof v === "string") return v.toUpperCase(); // narrowed to string
  return v.toFixed(2); // narrowed to number
}
console.log(format("hello")); // HELLO
console.log(format(3.1415)); // 3.14

// bad — widening to any hides the alternative set; callers lose exhaustiveness
function printBad(x: any): void {
  // x.toFixed(); // compiles (any), crashes when x is "hello"
  console.log(x);
}
// fix — list alternatives so the checker can enforce handling
function printGood(x: string | number): void {
  if (typeof x === "string") console.log(x.toUpperCase());
  else console.log(x.toFixed(2));
}
```

**Common confusion** — "`A | B` means the value is both `A` and `B`" — it means *either* — `&` is the both operator (see [2.1. Intersection fundamentals](<../2. Intersection Types/2.1. Intersection fundamentals merging object shapes.md>)). "`string | number` widens to `string`" — no widening; the checker keeps both members until you narrow — `typeof` narrows `string | number` branch by branch. "`any | string` is still `any`" — `any` absorbs the union (`any | T` is `any`), which is why `any` infection is dangerous (see [2.1. any the escape hatch](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.1. any the unchecked escape hatch.md>)).

**Performance note** — unions are checker-only — set algebra costs O(members) per check site, not per runtime value. A 3-member discriminated union and a 20-member union emit the same JavaScript (nothing). The measurable cost is on `tsc --extendedDiagnostics`: a union with 50 literal members is checked member-by-member at each narrowing site — keep hot-path unions under ~20 members or model with a lookup table derived from a `Record`.

**Mentor note** — teach "or" by asking "how many values could be here right now?" — one, but the checker does not know *which* one until you narrow. Exercise: give `type U = { a: string } | { b: number }`, ask what `u.a` alone means — answer is "error until you prove which branch you're on." Link the failure to the next promise (common-property rule).

### 2) **The common-property rule** (only shared members are safe without narrowing)

**Definition** — without narrowing, the checker only exposes properties present on *every* member of `A | B`. If `type U = { a: string; common: number } | { b: string; common: number }`, then `u.common` is safe (both have it) but `u.a` is an error — `u` might be the second member where `a` is absent. Narrow first (`if ("a" in u)`) and the member's exclusive properties become available in that branch.

**What problem it solves / history** — early type systems exposed all members optimistically and relied on runtime guards that the checker never verified — reading `u.a` on a `U` that was actually `{ b: string }` was an unchecked `undefined`. The common-property rule flipped the default to *soundness*: access is blocked until the value is proven to be the right member — the same discipline that makes `strictNullChecks` force `if (x !== null)` before `x.length` (see [1.3. null and undefined](<../../../03 Basic Types and Annotations/sections/1. The Primitive Family/1.3. null and undefined strictNullChecks and optionality.md>)).

**Modern guidance** — as of TypeScript 5.9 era, never widen a union access with `as` or `(u as any).a` — narrow with a real proof (`typeof`/`in`/`===` on discriminant/predicate). When a union grows beyond two members, add a discriminant literal `kind` (see [1.2. Discriminated unions](<./1.2. Discriminated unions the tagged pattern that scales.md>)) — the checker then narrows via `switch(kind)` and common-property guessing becomes unnecessary.

**Runnable example** — common vs exclusive members (good vs bad, `tsc --strict`):

```typescript
type Circle = { kind: "circle"; radius: number; common: string };
type Square = { kind: "square"; side: number; common: string };
type Shape = Circle | Square;

function describe(shape: Shape): string {
  // good — common property is always safe
  console.log(shape.common.toUpperCase()); // ok — both have 'common'

  // good — narrow before touching exclusive member
  if (shape.kind === "circle") {
    return `circle r=${shape.radius}`; // ok — narrowed to Circle
  }
  return `square s=${shape.side}`; // ok — narrowed to Square
}
console.log(describe({ kind: "circle", radius: 2, common: "geo" })); // circle r=2

// bad — reading exclusive member without narrowing; checker blocks it
function describeBad(shape: Shape): string {
  // return `r=${shape.radius}`; // error TS2339: 'radius' does not exist on Square
  // fix — narrow first as above, or use 'in' check for un-discriminated unions
  if ("radius" in shape) return `r=${shape.radius}`; // narrowed to Circle
  return `s=${shape.side}`;
}
console.log(describeBad({ kind: "square", side: 4, common: "geo" })); // s=4

// good — union with optional common pattern (two shapes sharing only 'id')
type A = { id: string; a: number };
type B = { id: string; b: number };
type AB = A | B;
function getId(x: AB): string { return x.id; } // ok — common
// function getA(x: AB): number { return x.a; } // error — not common; need narrowing

// bad — 'as' silences the rule and ships the undefined read
function getAUnsafe(x: AB): number {
  return (x as A).a; // compiles, but may be undefined when x is B
}
// fix — narrow, do not cast
function getASafe(x: AB): number | undefined {
  return "a" in x ? x.a : undefined;
}
```

**Common confusion** — "the property is on *one* member, so it should be `T | undefined`" — the property is *not* optional on the union — it is *absent* on that branch; reading it without narrowing is unsound — model with `in` check, not optional chaining alone. "`shape.radius` should be `number | undefined`" — the union does not synthesize an optional — the checker treats `radius` as absent on `Square`, not as `number | undefined` — use narrowing, not `?.`. "Adding `as` is narrowing" — `as` is an assertion, not a proof — `in`/`===` narrow; `as` widens and hides the branch.

**Performance note** — common-property computation is O(members × properties) at the call site — cheap for small unions, but a union of object types each with 20 distinct keys and one common key still walks every member to prove that only `common` survives. That cost is checker-only — zero emit, zero runtime branch. For a hot factory that constructs thousands of union values, the runtime branch is `if/else` or `switch`, not the type layer — keep the discriminant literal narrow (`kind` as string literal) so control-flow analysis stays O(variants).

**Mentor note** — demo the diagnostic: write `type U = { a: number } | { b: number }` and attempt `u.a` — show TS2339 and explain "the checker is protecting the `b`-shaped value that happens to not have `a`." Follow with fixing via `if ("a" in u)` — students see the stubbed narrowing block autocomplete. Review gate: disallow `(u as X).prop` in PRs for union access — require `in`/`kind ===` instead.

### 3) **Unions from optionality** (`T | null` vs optional `T?` — the nullability contract)

**Definition** — `T | null` (and `T | undefined`) is the *explicit* nullability union — the type says "a `T` or the absence marker." TypeScript 2.0's `strictNullChecks` makes this a real contract: `string` excludes `null`/`undefined`; only `string | null` allows `null`. Optional `prop?: T` is sugar for `prop?: T | undefined` — the property may be missing *and* is `T | undefined` when read — interact with `exactOptionalPropertyTypes` (TS 4.4) to distinguish missing vs `undefined` explicitly.

**What problem it solves / history** — without `strictNullChecks`, `string` silently accepted `null` — every dereference risked `TypeError: cannot read property of null` with no checker help. Unions reified nullability as a branch: `string | null` forced the consumer to narrow before calling `s.length`, and `T?` replaced the "sometimes present" convention with a checked property signature. The erasable rule stayed unchanged — `| null` still erases (see [3.3. Choosing erasable syntax](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>)).

**Modern guidance** — as of TypeScript 5.9 era, treat nullability as a union, not an afterthought: return `User | null` (not `User` that "might be null"), and accept `value: string | null` at boundaries — then narrow with `if (value !== null)` or `value ?? default`. Prefer `T | undefined` for "not yet set" / optional params and `T | null` for "intentionally absent" returned values — the two sentinels signal different intent. For optional object properties, pick one spelling and lint it: `?:` (missing) vs `prop: T | undefined` (present but maybe `undefined`) — `exactOptionalPropertyTypes` makes the distinction enforceable.

**Runnable example** — nullability unions vs optional (good vs bad, `tsc --strict`):

```typescript
// good — strict nullability as a union: caller must narrow
type User = { id: string; name: string };
function findUser(id: string): User | null {
  return id === "42" ? { id: "42", name: "Ada" } : null;
}
const u = findUser("1");
if (u !== null) console.log(u.name.toUpperCase()); // narrowed to User
else console.log("not found");

// good — nullish coalescing as narrowing sugar (still checks)
function displayName(user: User | null): string {
  return (user?.name ?? "anonymous").toUpperCase();
}
console.log(displayName(null)); // ANONYMOUS

// good — optional property vs T | undefined contract
type Config = { host: string; port?: number }; // port is number | undefined when read, but may be missing
function connect(cfg: Config): void {
  const port = cfg.port ?? 3000; // narrows undefined away
  console.log(`${cfg.host}:${port}`);
}
connect({ host: "localhost" }); // localhost:3000

// bad — non-strict habit: string pretends to absorb null, crashes at runtime
function upperBad(s: string): string {
  return s.toUpperCase(); // assumes non-null, crashes if caller passed null without union in type
}
// upperBad(null as unknown as string); // compiles only via laundering — real fix: upperGood
function upperGood(s: string | null): string {
  return s !== null ? s.toUpperCase() : "(none)";
}
console.log(upperGood(null)); // (none)

// bad — truthiness narrowing smuggles falsy-vs-nullish bug
function countStrBad(s: string | null): number {
  if (s) return s.length; // treats "" as absent (bug when "" is valid)
  return 0;
}
function countStrGood(s: string | null): number {
  if (s !== null) return s.length; // "" counts as 0-length string, not absent
  return 0;
}
console.log(countStrBad("")); // 0 — wrong intent ("" dropped)
console.log(countStrGood("")); // 0 — correct intent but via null check, not falsiness

// good — exactOptionalPropertyTypes-friendly spelling (TS 4.4+)
// host: string | undefined requires presence; port?: number allows absence
type ExactCfg = { host: string | undefined; port?: number };
const cfg1: ExactCfg = { host: undefined, port: 3000 }; // host present but undefined allowed
// const cfg2: ExactCfg = { port: 3000 }; // error TS2741: host missing (not optional)
```

**Common confusion** — "`T | null` and `T | undefined` are the same" — they signal different intent: `null` is *intentional* absence (returned value), `undefined` is *incidental* absence (missing property/param) — pick consistently and narrow accordingly. "`prop?: T` means `prop` is `T | null`" — it means `T | undefined` (and missing is allowed) — `null` requires explicit `T | null`. "`if (x)` is enough to narrow `T | null | undefined`" — `if (x)` narrows *truthiness* (drops `""`/`0`/`false` too) — use `x != null` (loose) or `x !== null && x !== undefined` (strict) / `x ??` to keep valid falsy values.

**Performance note** — `T | null` adds no runtime allocation — it is one extra control-flow branch (`if (x !== null)`) per use, not per value. The checker cost is one extra member per nullability site — negligible. The measurable win is fewer production `TypeError`s: a codebase that enforces `T | null` over bare `T` under `strictNullChecks` shifts null crashes from runtime to compile time; the flag is purely checker-time and has zero emit/bundle cost.

**Mentor note** — review gate: ban bare `string` returns that can actually be `null` — require `string | null` and a null-narrow at every call site. Exercise: give `function get(key: string): string` that internally returns `map.get(key) ?? null`, ask why callers cannot prove `get("x").length` is safe — answer is the return type lies; fix is `string | null`. Add a lint rule for `== null` vs truthiness to keep `""`/`0` safe (see [3.1. Built-in narrowers](<../3. Control Flow Narrowing/3.1. Built-in narrowers typeof instanceof in and equality.md>)).
