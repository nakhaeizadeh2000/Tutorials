## 1.1. Union fundamentals — member access and the common property rule

### 1) **A union accepts membership in at least one alternative**

`A | B` accepts values assignable to A or B, including values that satisfy both. It is an inclusive union, not an instruction to attach exactly one runtime identity. String and number values are disjoint alternatives, but object contracts can overlap because each describes required members rather than an exact list of all permitted properties.

Use TypeScript **7.0.2** and Node **20.20.2**, verified 2026-10-15. Save each named program in a fresh directory without tsconfig.json. Build with `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then run `node dist/FILE.js`. For a marked rejection, activate only that line in a separate copy and replace `--outDir dist` with `--noEmit`.

Save `membership.ts`:

```typescript
export {};
type A = { a: string };
type B = { b: number };
type Either = A | B;
const both = { a: "yes", b: 1 };
const assigned: Either = both;
const fresh: Either = { a: "fresh", b: 2 };
function memberships(value: Either): string {
  return String("a" in value) + "/" + String("b" in value);
}
console.log(memberships({ a: "only A" }), memberships({ b: 3 }));
console.log(memberships(assigned), memberships(fresh));
function format(value: string | number): string {
  return typeof value === "string" ? value.toUpperCase() : value.toFixed(2);
}
console.log(format("hello"), format(3.1415));
// format(true); // TS2345: boolean is outside this union.
```

The build and execution exit 0. Output is `true/false false/true`, `true/true true/true`, then `HELLO 3.14`. Both object assignments meet the union while also satisfying each member. The parameter to memberships still has the declared union view; testing one property does not mean the other property must be absent.

The [primary union guide](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#union-types) explains the union in terms of allowed values. The apparent restriction on available properties comes from what is known about *every* possible input, which is a separate question. Distinct conflicting tags such as kind:"circle" and kind:"square" can make a particular model's variants disjoint. The operator alone does not do that. [Discriminated unions](<./1.2. Discriminated unions the tagged pattern that scales.md>) owns that modeling pattern; [structural assignability](<../../../02 The Type System Core/sections/1. Structural typing/1.1. Structural assignability shape not name.md>) and [freshness](<../../../02 The Type System Core/sections/1. Structural typing/1.2. Excess property checks and freshness.md>) explain object assignment checks in full.

### 2) **Use common operations, then narrow for member-specific work**

A value accepted by Circle | Square may be either shape. Both provide label, so label can be read directly. Only Circle promises radius, so radius cannot be read through the unresolved union. The checker does not automatically invent an optional radius property on Square. Optional chaining protects against a nullish receiver; it does not establish that a missing member belongs to the receiver's type.

Save `members.ts`:

```typescript
export {};
type Circle = { kind: "circle"; label: string; radius: number };
type Square = { kind: "square"; label: string; side: number };
type Shape = Circle | Square;
function describe(shape: Shape): string {
  const label = shape.label.toUpperCase();
  if (shape.kind === "circle") return label + " r=" + shape.radius;
  return label + " s=" + shape.side;
}
console.log(describe({ kind: "circle", label: "geo", radius: 2 }));
console.log(describe({ kind: "square", label: "tile", side: 4 }));
// function wrong(shape: Shape): number { return shape.radius; } // TS2339.
// function optionalWrong(shape: Shape): number | undefined { return shape?.radius; } // TS2339.
type A = { id: string; a: number };
type B = { id: string; b: number };
type AB = A | B;
function unsafe(value: AB): number { return (value as A).a; }
function guarded(value: AB): number | undefined {
  return "a" in value ? value.a : undefined;
}
console.log("unproved read:", unsafe({ id: "b", b: 2 }));
console.log("guarded:", guarded({ id: "a", a: 3 }), guarded({ id: "b", b: 2 }));
```

The output is `GEO r=2`, `TILE s=4`, `unproved read: undefined`, then `guarded: 3 undefined`. Each marked member access is rejected with TS2339, exit 1. The assertion in unsafe is accepted, but its declared number result does not match the observed undefined for that input. The guarded contract honestly permits an absent result for the demonstrated alternatives.

The equality and in expressions remain real runtime operations. An annotation or assertion does not validate external data, and an in test establishes property presence rather than a complete domain schema. These examples assume values satisfying their declared member contracts; [runtime boundary checking](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.2. Static checking vs runtime reality trust but verify.md>) owns validation. Use [built-in narrowers](<../3. Control Flow Narrowing/3.1. Built-in narrowers typeof instanceof in and equality.md>) for the wider control-flow rules and [custom narrowers](<../3. Control Flow Narrowing/3.3. Custom narrowers predicates asserts and type guards on unions.md>) for predicate obligations.

Common access applies to operations, not just property spelling. Two members can both expose a method name whose parameter contracts still restrict which calls are valid. Conversely, an assignment or earlier guard can already narrow a variable whose annotation contains a union. Ask what type is known at the current use site instead of applying the common-property rule without considering control flow.

### 3) **Nullish alternatives and optional properties describe different states**

With strictNullChecks, a string excludes null and undefined. A result annotated User | null requires the caller to handle absence. Which sentinel an API uses is a contract choice: null and undefined do not intrinsically prove why the value is absent. Follow the actual producer's documented behavior and preserve meaningful falsy values when they are valid data.

Save `nullable.ts`:

```typescript
export {};
type User = { id: string; name: string };
function findUser(id: string): User | null {
  return id === "42" ? { id, name: "Ada" } : null;
}
function display(user: User | null): string {
  return (user?.name ?? "anonymous").toUpperCase();
}
console.log(display(findUser("42")), display(findUser("missing")));
function truthyLabel(value: string | null): string { return value ? value : "(missing)"; }
function nullishLabel(value: string | null): string { return value ?? "(missing)"; }
console.log("empty:", JSON.stringify(truthyLabel("")), JSON.stringify(nullishLabel("")));
console.log("null:", truthyLabel(null), nullishLabel(null));
type Config = { port?: number };
const absent: Config = {};
const present: Config = { port: 0 };
const read: number | undefined = absent.port;
console.log("optional:", Object.hasOwn(absent, "port"), Object.hasOwn(present, "port"), read, present.port);
type Required = { port: number | undefined };
const explicit: Required = { port: undefined };
console.log("required:", Object.hasOwn(explicit, "port"), explicit.port);
// const notExact: Config = { port: undefined }; // TS2375 with exactOptionalPropertyTypes.
// const missingRequired: Required = {}; // TS2741: key required even when undefined is allowed.
// function unguarded(user: User | null): string { return user.name; } // TS18047.
```

Output is `ADA ANONYMOUS`, `empty: "(missing)" ""`, `null: (missing) (missing)`, `optional: false true undefined 0`, then `required: true undefined`. The empty-string case now shows an actual behavioral difference: truthiness replaces a valid empty value with the fallback, while nullish coalescing retains it. Both functions choose the fallback for null.

An optional property permits omission and can read as undefined. A required property whose type includes undefined still requires its key. With exactOptionalPropertyTypes, Config's omitted port is valid but an explicitly undefined port is rejected unless undefined is included in the declared optional value type. Activate notExact and check once with the declared flags, then with `--exactOptionalPropertyTypes false`: it fails with TS2375 in the first mode and succeeds in the second. This affects permitted writes; the optional read still needs number | undefined. The [option reference](https://www.typescriptlang.org/tsconfig/exactOptionalPropertyTypes.html) explains why missing and present-undefined differ. Full sentinel/option semantics live in [null and undefined](<../../../03 Basic Types and Annotations/sections/1. The Primitive Family/1.3. null and undefined strictNullChecks and optionality.md>) and [object modifiers](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>).

### 4) **Common confusion**

Inclusive membership does not grant access to every member's properties. An object satisfying both alternatives is accepted, while a function accepting arbitrary values from the union must still account for values satisfying only one. A tagged model can deliberately make its alternatives disjoint without changing the meaning of |.

An assertion can expose a narrower checked view while leaving the runtime value unchanged. It is not inherently widening, validation or a branch test. Any in a union also removes useful checking rather than proving an alternative. Finally, optional absence, explicit undefined and null are distinct contracts; a truthiness test answers a broader question than a nullish test.

### 5) **Performance note**

Union aliases and annotations erase. The object literals, property tests, typeof/equality operations, string formatting and fallback expressions still execute. There is no automatic runtime tag or branch inserted simply because a type contains |. This lesson measured no universal checker complexity, per-member cost or union-size threshold. Use real checking measurements for a demonstrated slow type and runtime profiles for a demonstrated branch cost; the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) covers the former. Do not weaken a truthful contract to meet an invented member quota.

### 6) **Mentor note**

Start with the two membership results that both print true/true, then ask why an unresolved A | B still cannot promise a. A sound answer separates allowed inputs from facts guaranteed for all of them. Next, compare unsafe's number annotation with its actual output and require a repair that states the absent-result case honestly.

For optionality, ask the learner to distinguish {}, {port:undefined} and {port:0} before looking at diagnostics. Then have them predict the empty-string outputs and explain why both functions producing zero length would have been an inadequate demonstration of the difference. Require the guard and the resulting operation, not just a keyword name.
