## 1.2. Discriminated unions — the tagged pattern that scales

### 1) **A discriminant connects a branch test to the variant's payload**

A tagged union gives its alternatives a common property with distinguishing values. For example, kind:"circle" belongs with radius and kind:"square" belongs with side. Testing kind lets the checker recover the corresponding payload contract. A string tag is easy to read and can grow to several named states; distinct numeric or boolean literals can discriminate too. A broad string or boolean shared by every member does not identify which payload is present.

Use TypeScript **7.0.2** and Node **20.20.2**, verified 2026-10-15. Save each named program in a fresh directory without tsconfig.json. Build with `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then run `node dist/FILE.js`. For a commented rejection, activate just that line in a separate copy and replace `--outDir dist` with `--noEmit`.

Save `discriminants.ts`:

```typescript
export {};
type Shape = { kind: "circle"; radius: number } | { kind: "square"; side: number };
function area(shape: Shape): number {
  return shape.kind === "circle" ? Math.PI * shape.radius ** 2 : shape.side ** 2;
}
console.log("areas:", area({ kind: "circle", radius: 2 }).toFixed(2), area({ kind: "square", side: 3 }));
type Result = { ok: true; value: number } | { ok: false; error: string };
function message(result: Result): string {
  return result.ok ? "value=" + result.value : "error=" + result.error;
}
console.log(message({ ok: true, value: 42 }), message({ ok: false, error: "timeout" }));
type Outcome = { error: Error; data: null } | { error: null; data: string };
function unwrap(outcome: Outcome): string {
  if (outcome.error) {
    const absent: null = outcome.data;
    return outcome.error.message + ":" + absent;
  }
  const text: string = outcome.data;
  return text.toUpperCase();
}
console.log(unwrap({ error: null, data: "ok" }), unwrap({ error: new Error("failed"), data: null }));
type Wide = { kind: string; radius: number } | { kind: string; side: number };
// function wide(shape: Wide): number { return shape.kind === "circle" ? shape.radius : 0; } // TS2339.
type WideBoolean = { ok: boolean; value: number } | { ok: boolean; error: string };
// function wideBoolean(result: WideBoolean): number { return result.ok ? result.value : 0; } // TS2339.
type Nested = { meta: { kind: "circle" }; radius: number } | { meta: { kind: "square" }; side: number };
// function nested(shape: Nested): number { return shape.meta.kind === "circle" ? shape.radius : 0; } // TS2339.
// area({ kind: "circle", side: 3 }); // TS2353: this tag requires the circle contract.
```

Output is `areas: 12.57 9`, `value=42 error=timeout`, then `OK failed:null`. The boolean result works because its branches use different literal values, not because booleans are forbidden tags. A boolean tag is convenient for a two-way result; descriptive string tags may communicate several states more clearly.

The nullable-error example also narrows data, even though Error is not a literal type. The [primary 3.2 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-2.html#non-unit-types-as-union-discriminants) document this broader discriminant support. Keep simple tags as the introductory model without claiming every recognized discriminator must be a literal in every alternative. The exact Outcome contract and branch-local assignments above are verified; this is not a claim that any common property can discriminate.

The three marked functions fail with TS2339. Wide and WideBoolean have no payload-identifying tag. Testing Nested.meta.kind does not narrow the outer shape enough to expose its radius in this program. A flat tag on the union value makes that relationship explicit. An external object still needs validation: the type declaration and the equality expression do not together validate arbitrary payload fields. The [object-check owner](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.3. satisfies assertions and narrowing on object shapes.md>) and [custom-narrower owner](<../3. Control Flow Narrowing/3.3. Custom narrowers predicates asserts and type guards on unions.md>) explain evidence and assertion limits.

### 2) **Scale state transitions by making each valid state explicit**

A union is useful when behavior depends on data describing a particular state or event. Model the payload with the variant that needs it: loading has a request ID, success has items, and error has a message. This prevents consumers from assuming every state has every field. It does not itself reject stale events; the transition function must implement that policy.

Save `state.ts`:

```typescript
export {};
type State =
  | { status: "idle" }
  | { status: "loading"; requestId: string }
  | { status: "success"; items: string[] }
  | { status: "error"; message: string };
type Action =
  | { kind: "start"; requestId: string }
  | { kind: "succeed"; requestId: string; items: string[] }
  | { kind: "fail"; requestId: string; message: string }
  | { kind: "reset" };
function transition(state: State, action: Action): State {
  switch (action.kind) {
    case "start": return { status: "loading", requestId: action.requestId };
    case "succeed": return state.status === "loading" && state.requestId === action.requestId
      ? { status: "success", items: action.items } : state;
    case "fail": return state.status === "loading" && state.requestId === action.requestId
      ? { status: "error", message: action.message } : state;
    case "reset": return { status: "idle" };
  }
}
function render(state: State): string {
  switch (state.status) {
    case "idle": return "idle";
    case "loading": return "loading " + state.requestId;
    case "success": return "success " + state.items.length;
    case "error": return "error " + state.message;
  }
}
let state: State = { status: "idle" };
state = transition(state, { kind: "start", requestId: "r1" });
console.log(render(state));
const waiting = state;
state = transition(state, { kind: "succeed", requestId: "old", items: ["stale"] });
console.log("stale:", state === waiting, render(state));
state = transition(state, { kind: "succeed", requestId: "r1", items: ["a", "b"] });
console.log(render(state));
state = transition(state, { kind: "reset" });
console.log(render(state));
state = transition(state, { kind: "start", requestId: "r2" });
state = transition(state, { kind: "fail", requestId: "r2", message: "network" });
console.log(render(state));
// transition(state, { kind: "succeed", requestId: "r2" }); // TS2345: missing items.
```

Output is `loading r1`, `stale: true loading r1`, `success 2`, `idle`, then `error network`. Each branch exposes its own payload, and the request ID check preserves the waiting state for the stale response. These are local deterministic transitions, not a network or framework integration test. Class hierarchies remain useful when shared behavior or construction relationships are the central requirement; use [abstract classes](<../../../06 Classes and Object-Oriented Types/sections/2. Inheritance and Polymorphism/2.2. Abstract classes and members when abstract beats interface.md>) for that decision. There is no variant-count threshold at which one representation always wins.

**Evolution exercise:** append `| { kind: "retry" }` to Action while leaving transition unchanged. The explicit State return annotation and strict checking reject the missing-return path with TS2366. Adding `default: return state` would accept the new action while silently ignoring it. Decide whether that fallback is intentional. An explicit never sink can make the missing variant diagnostic direct; the full pattern belongs in [exhaustiveness](<../3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>). Merely adding a tag does not make every switch exhaustive.

A table of constant payload samples is not automatically a schema for arbitrary payload values. Save `fixtures.ts`:

```typescript
export {};
const samples = { click: { x: 0, y: 0 } } as const;
type SampleClick = typeof samples.click;
const fixture: SampleClick = { x: 0, y: 0 };
console.log("fixture:", fixture.x, fixture.y);
// const different: SampleClick = { x: 10, y: 20 }; // TS2322: fields are the literal zero.
```

This prints `fixture: 0 0`. The exact inferred payload preserves zero; it does not mean x and y accept all numbers. Give real event payloads explicit number contracts when coordinates vary, as Shape does for dimensions. Mapped-union derivation is useful once those contracts are chosen, but its machinery belongs in [mapped types](<../../../09 Utility Types and Type Transformations/sections/1. Mapped Types/1.1. Mapped type fundamentals homomorphic mapping over keys.md>), rather than treating sample data as the general contract.

### 3) **Use an untagged union when an existing distinction is enough**

String | number can be handled with typeof, and string | null can be handled with a nullish check. Wrapping every primitive in {kind,value} adds an API obligation without necessarily clarifying the consumer's work. An object union can also use an existing property distinction when that is the intended contract.

Save `untagged.ts`:

```typescript
export {};
function normalize(input: string | number): string {
  return typeof input === "string" ? input.trim() : String(input);
}
type Source = { path: string } | { inline: string };
function describe(source: Source): string {
  return "path" in source ? "file:" + source.path : "inline:" + source.inline;
}
console.log(normalize("  hello "), normalize(42));
console.log(describe({ path: "a.txt" }), describe({ inline: "text" }));
const both = { path: "a.txt", inline: "fallback" };
console.log("both:", describe(both));
function username(value: string | null): string { return value ?? "guest"; }
console.log("names:", JSON.stringify(username("")), JSON.stringify(username(null)));
```

Output is `hello 42`, `file:a.txt inline:text`, `both: file:a.txt`, then `names: "" "guest"` (the empty name is retained). The Source union is inclusive: both is valid, and this function intentionally prioritizes path. If both properties must be forbidden together, a plain untagged union has not expressed that rule. [Union fundamentals](<./1.1. Union fundamentals member access and the common property rule.md>) owns inclusive membership; [impossible-state modeling](<../2. Intersection Types/2.2. The never trap conflicting intersections and impossible states.md>) owns exclusions.

Add a tag when it names a meaningful variant and gives consumers a stable distinction, even with only two alternatives. Keep an existing primitive or property distinction when it already expresses the intended API. The decision follows meaning and evolution, not a universal two-versus-three-member rule. An in test checks presence, not the complete runtime schema; optional/shared properties and external input require their own reasoning.

### 4) **Common confusion**

A common property name is not enough: the contract must connect its tested value to a useful variant. Distinct true/false tags work, a shared broad boolean does not supply the same correlation, and the checked nullable-error case demonstrates a broader recognized discriminator. Nested tags do not automatically recover arbitrary outer payload relationships.

Tagged records also do not automatically provide exhaustive handling, serialization safety or correct state transitions. The reducer's missing-case check depends on its return contract; rejecting a stale response depends on its request-ID comparison. A const table can preserve exact fixture literals without describing a general payload schema.

### 5) **Performance note**

The union and mapped/query types erase. Tags, wrapper objects, property tests and switch branches exist only because the program creates or executes them. The state example allocates new objects for transitions and returns the existing reference for a stale event. A tag does not imply a particular string storage layout or switch dispatch algorithm. No speed comparison, allocation formula, branch-count threshold or checker complexity was measured. Profile the actual representation and workload before replacing clear branch logic with a handler map. The [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) treats compiler checking separately.

### 6) **Mentor note**

Ask the learner why Result narrows on ok while WideBoolean does not. Then have them predict the data type in each Outcome branch and explain why Nested's outer radius access is still rejected. A sound answer connects the tested property to the declared payload relationship instead of reciting “tags must be strings.”

For design practice, add retry and choose its intended transition. Require a missing-case diagnostic before implementing it, then demonstrate the repaired state behavior. Ask why the stale response retains the old reference, and whether Source should prioritize a path when both fields exist. Finally, vary a fixture coordinate and explain the literal-zero diagnostic before choosing a general number payload. These tasks test correlation, evolution and API judgment together.
