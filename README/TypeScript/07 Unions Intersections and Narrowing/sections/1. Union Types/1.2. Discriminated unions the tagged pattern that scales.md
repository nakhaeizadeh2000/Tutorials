## 1.2. Discriminated unions — the tagged pattern that scales

### 1) **The discriminant** (a shared literal property that the checker uses to split the union)

**Definition** — a *discriminated union* (tagged union) is a `|` where every member carries the same literal property — conventionally `kind`, `type`, or `status` — with a distinct literal value per member: `type Shape = { kind: "circle"; radius: number } | { kind: "square"; side: number }`. The checker treats `shape.kind === "circle"` as a narrowing proof that the whole value is the `Circle` member — no `in` check, no cast, no predicate needed.

**What problem it solves / history** — without a discriminant, narrowing a union required `in` checks or `typeof`/`instanceof` per branch — `if ("radius" in shape)` works for two members but degrades as variants grow, and the property being checked might accidentally appear on both members. Discriminated unions (documented since Handbook "Discriminated Unions" and formalized in control-flow analysis in TS 2.0) give the checker a single, stable literal to branch on — the literal is cheap to read at runtime and provably unique at compile time. The pattern scales from Redux actions to state machines to `Result<T, E>`.

**Modern guidance** — as of TypeScript 5.9 era, tag every union that has more than two non-primitive members with a narrow literal — `kind: "circle" | "square"`, `status: "idle" | "loading" | "success" | "error"`, `action: { type: "increment" }`. Keep the discriminant at the top level (flat `kind`, not `meta.kind`) — the checker only narrows directly on `x.kind`, not on nested paths without an additional guard. Derive the discriminant type from `as const` collections so the source of truth is one place (see [3.3. Literal types](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>)).

**Runnable example** — discriminant as splitter (good vs bad, `tsc --strict`):

```typescript
// good — discriminant-carrying union (scales to many variants)
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Triangle = { kind: "triangle"; base: number; height: number };
type Shape = Circle | Square | Triangle;

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2; // narrowed to Circle
    case "square": return shape.side ** 2; // narrowed to Square
    case "triangle": return (shape.base * shape.height) / 2; // narrowed to Triangle
  }
}
console.log(area({ kind: "circle", radius: 2 })); // 12.566...

// good — action union tagging (the Redux / event pattern)
type Action =
  | { type: "increment"; amount: number }
  | { type: "reset" }
  | { type: "set"; value: number };

function reduce(state: number, action: Action): number {
  switch (action.type) {
    case "increment": return state + action.amount;
    case "reset": return 0;
    case "set": return action.value;
  }
}
console.log(reduce(10, { type: "increment", amount: 5 })); // 15

// bad — un-tagged union forced to use 'in' per branch (fragile when members evolve)
type BadA = { radius: number; shared?: string };
type BadB = { side: number; shared?: string };
type BadShape = BadA | BadB;
function areaBad(shape: BadShape): number {
  if ("radius" in shape) return Math.PI * shape.radius ** 2; // works for 2 members, unreadable for 8
  return shape.side ** 2;
}
// fix — add kind: "circle" | "square" so the switch branches are explicit and exhaustive
```

**Common confusion** — "`kind` must be `string`" — `kind` must be a *literal* type (`"circle"`, `42`, `true`) — a narrow literal is the splitter; a wide `string` discriminant never narrows because both branches share `string`. "Any common property is a discriminant" — only a *literal* common property discriminates; `shared: string` present on both members is the common-property rule (see [1.1. Union fundamentals](<./1.1. Union fundamentals member access and the common property rule.md>)) and does not split. "`in` check is the same" — `in` is a runtime property-existence check; the discriminant is a value equality check — `kind === "circle"` is tighter, hovers cleaner, and pairs with exhaustiveness (see [3.2. Exhaustiveness](<../3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>)).

**Performance note** — one string-literal discriminant adds one property slot per value (tiny) and one equality comparison per branch (`===`) — identical cost to any property read. Checker cost is O(variants) per `switch`/`if` chain — the same as `in` checks. The win is refactor speed: adding a variant to a discriminated union triggers TS errors in every exhaustive `switch` — no runtime hunt. Keep the discriminant as a single flat literal, not a computed expression — the checker narrows `shape.kind === "circle"` but not `shape.meta.kind.tag === "circle"` without an intermediate guard.

**Mentor note** — teach by starting with `type Action = { type: "add"; payload: number } | { type: "clear" }` — a domain every junior has touched (state updates). Show `switch (action.type)` and ask what `action.payload` outside the `case "add"` branch means — answer is "error until you prove the case." Review exercise: hand a 4-variant untagged union and ask to add `kind` so every member is distinct — check that no two members share the same `kind` literal.

### 2) **Scaling to many variants** (adding actions/events/states without growing a class tree)

**Definition** — discriminated unions scale *horizontally* — adding a variant is appending a type to the `|` (`type Event = MouseEvent | KeyEvent | TouchEvent | PointerEvent`) — while class hierarchies scale *vertically* (inheritance chain, `override` cascade, `instanceof` chain). At 2 variants either works; at 8+ the union stays one import and one `switch`; the hierarchy carries virtual dispatch, `this` capture, and method-bivariance traps (see [2.3. Override](<../../../06 Classes and Object-Oriented Types/sections/2. Inheritance and Polymorphism/2.3. Override and polymorphic this typing.md>)).

**What problem it solves / history** — Redux, XState, and React's `useReducer` proved that UI state as a union of tagged records out-scales class hierarchies — every action is data (serializable, loggable, replayable, debuggable), not a method call. TypeScript's control-flow analysis was tuned for this shape: `switch (action.type)` narrows the union through the entire `case` block, and adding a member to the union automatically tightens every exhaustive check — the compiler becomes the migration tool.

**Modern guidance** — as of TypeScript 5.9 era, prefer discriminated unions over class hierarchies for *data-shaped* variation: API results (`{ status: "success"; data: T } | { status: "error"; error: E }`), form states, AST nodes, event streams. Keep class hierarchies for *behavior-shaped* variation where shared runtime logic and construction constraints matter (see [2.2. Abstract classes](<../../../06 Classes and Object-Oriented Types/sections/2. Inheritance and Polymorphism/2.2. Abstract classes and members when abstract beats interface.md>)). Derive the union from a `const` map when variants share structure — one source, many members — using template and mapped patterns (forward to [09 Utility Types](<../../../09 Utility Types and Type Transformations/README.md>) but already readable in this domain).

**Runnable example** — 8-variant event union that still switches cleanly (good vs bad, `tsc --strict`):

```typescript
// good — discriminated union scales flat; add a variant by adding a type to |
type AppEvent =
  | { kind: "click"; x: number; y: number }
  | { kind: "keydown"; key: string }
  | { kind: "scroll"; delta: number }
  | { kind: "resize"; w: number; h: number }
  | { kind: "focus"; id: string }
  | { kind: "blur"; id: string }
  | { kind: "submit"; values: Record<string, string> }
  | { kind: "cancel" };

function handle(evt: AppEvent): string {
  switch (evt.kind) {
    case "click": return `click ${evt.x},${evt.y}`;
    case "keydown": return `key ${evt.key}`;
    case "scroll": return `scroll ${evt.delta}`;
    case "resize": return `resize ${evt.w}x${evt.h}`;
    case "focus": return `focus ${evt.id}`;
    case "blur": return `blur ${evt.id}`;
    case "submit": return `submit ${Object.keys(evt.values).length} fields`;
    case "cancel": return "cancelled";
  }
}
console.log(handle({ kind: "keydown", key: "Enter" })); // key Enter

// good — deriving the union from a const event table (single source)
const EVENTS = {
  click: { x: 0, y: 0 },
  scroll: { delta: 0 },
} as const;
type DerivedEvent = {
  [K in keyof typeof EVENTS]: { kind: K } & typeof EVENTS[K];
}[keyof typeof EVENTS]; // flat union

// bad — class hierarchy for the same shape (heavy for data)
abstract class EventBase { abstract kind: string; }
class ClickEvent extends EventBase { kind = "click" as const; constructor(public x: number, public y: number) { super(); } }
class KeyEvent extends EventBase { kind = "keydown" as const; constructor(public key: string) { super(); } }
// ... 6 more classes → instanceof chain + shared file + emit per class
// fix — union above: same exhaustiveness, zero emit per member, data stays serializable
```

**Common confusion** — "unions always beat class hierarchies" — for *data* they do; for *shared behavior with construction gates* classes beat unions (see [2.2. Abstract classes](<../../../06 Classes and Object-Oriented Types/sections/2. Inheritance and Polymorphism/2.2. Abstract classes and members when abstract beats interface.md>)). "A large union is slow to check" — checker cost is O(variants) per `switch`, but that pass often dominates a single-file diagnostic; at 50+ variants consider splitting by domain (`UIEvent | NetworkEvent`) before merging — still O(variants) but faster hovers and narrower imports. "Template/mapped derivation needs generics domain" — simple mapped unions (`[K in keyof M]`) are idiomatic here; reserve conditional `infer` filtering for Domain 08.

**Performance note** — discriminated unions emit only the data the runtime writes — `kind` is one string per value. No prototype, no `instanceof`, no method table — O(variants) fewer allocations than an equivalent class hierarchy where each variant carries a prototype link and method closure. The `switch (kind)` dispatches as a hash of strings — identical to hand-rolled property checks. For ultra-hot dispatch (millions of events/sec), a `Record<Kind, Handler>` map keyed by `kind` can out-perform a long `switch` due to fewer branch-predictions, but any choice is about runtime shape, not type cost — the union still erases.

**Mentor note** — demonstrate the migration win: add `{ kind: "doubleclick"; x: number; y: number }` to `AppEvent` — show that `handle` now errors inside the `switch` until the new case is added (with `never` exhaustiveness from [3.2](<../3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>)). Contrast with a class hierarchy where adding a subclass silently missing a `handle` override compiles. Assign a kata: refactor a 3-class event hierarchy into a discriminated union — students must delete constructors and switch on `kind`.

### 3) **When a non-discriminated union is better** (two primitives, optional fields, or `in`-check narrowing)

**Definition** — a *non-discriminated* (untagged) union has no shared literal — the members are distinguished by shape or runtime type: `type Value = string | number | { items: string[] }`, `type Input = string | null`, `type Config = { path: string } | { inline: string }`. Narrowing uses `typeof`/`instanceof`/`in`/equality instead of `kind ===`. Two members, primitive-only unions, and "maybe" wrappers (`T | null`, `T | undefined`) rarely warrant a tag — the narrowers in [3.1](<../3. Control Flow Narrowing/3.1. Built-in narrowers typeof instanceof in and equality.md>) are sufficient and more concise.

**What problem it solves / history** — tagging *every* union — `type MaybeString = { kind: "string"; value: string } | { kind: "null" }` — duplicates what `string | null` already expresses with one assignment and one null check. Non-discriminated unions keep primitive-mixing and "absent vs present" ergonomics without allocating a wrapper object per value. The `in` narrow (`"items" in value`) and `typeof` narrow remain the lightest proof when the members genuinely have disjoint shapes.

**Modern guidance** — as of TypeScript 5.9 era, choose the shape by variant kind count and runtime reality: `T | null | undefined` for absent-vs-present; `string | number` for primitive alternatives (narrowed with `typeof`); `{ data: T } | { error: E }` for un-tagged two-member records (narrowed with `in`). Add a discriminant only when the union has 3+ members that overlap on all other keys (e.g., `Square` and `Rectangle` both have `width`/`height` — a `kind` disambiguates without fragile `in` chains). Never synthesize a wrapper tag solely to avoid writing an `in` check for a two-member shape — the check is one line and the wrapper adds allocation.

**Runnable example** — non-discriminated unions where `in`/`typeof` win (good vs bad, `tsc --strict`):

```typescript
// good — primitive union narrowed with typeof (no tag needed)
function normalize(input: string | number): string {
  if (typeof input === "string") return input.trim(); // narrowed to string
  return String(input); // narrowed to number
}
console.log(normalize("  hello ")); // hello
console.log(normalize(42)); // 42

// good — two-member object union narrowed with 'in' (tag would be boilerplate)
type Success<T> = { data: T };
type Failure = { error: string };
type Result<T> = Success<T> | Failure;

function get<T>(result: Result<T>): T {
  if ("error" in result) throw new Error(result.error); // narrowed to Failure branch
  return result.data; // narrowed to Success<T>
}
console.log(get({ data: 42 })); // 42

// good — T | null where tag would over-wrap
function username(name: string | null): string {
  return name ?? "guest"; // nullish coalescing narrows null, one assignment
}
console.log(username(null)); // guest

// bad — over-tagged Maybe that duplicates T | null idiomatically
type OverTaggedMaybe<T> = { kind: "value"; value: T } | { kind: "none" };
function usernameBad(input: OverTaggedMaybe<string>): string {
  return input.kind === "value" ? input.value : "guest";
  // equivalent to above but every caller must construct { kind, value } wrappers
}
// fix — use string | null (or string | undefined) and ??/!== null at the boundary

// good — three overlapping rectangles where tag finally earns its keep
type UntaggedRect = { w: number; h: number; kind?: undefined };
type UntaggedSquare = { w: number; h: number; kind?: undefined };
// both have w/h — 'in' does not split them → add kind
type TaggedRect = { kind: "rect"; w: number; h: number };
type TaggedSquare = { kind: "square"; side: number };
type TaggedShape = TaggedRect | TaggedSquare; // now split cleanly via kind ===
```

**Common confusion** — "every union needs a discriminant" — only unions with overlapping shapes need one; `string | number`, `T | null`, and `T | undefined` stay untagged precisely because `typeof`/`=== null` split them. "`in` is unsafe" — `in` is a sound narrower for un-tagged unions where the members genuinely have disjoint property sets — it is unsafe only when the queried property accidentally appears on both members (hence the tag for overlapping shapes). "Wrapping with `{ kind }` is always cheaper" — the wrapper allocates one extra object per value — for a hot boundary that returns `string | null` at high throughput, the bare union avoids the allocation while staying exhaustive.

**Performance note** — untagged unions and tagged unions emit identically except for the discriminant property value — the difference is one string per value. Runtime narrowers `typeof`/`in` compile to one operation each; discriminant `===` is also one string compare. For two-member primitive unions, `typeof` dispatch is marginally faster to read than a property load + compare; for large variant counts, `switch (kind)` may beat an `if ("a" in x) else if ("b" in x)` chain because engines can optimize string `switch` as a jump table. Checker cost is identical — no winner on type layer.

**Mentor note** — kata: give `type A = string | { items: string[] }`, ask "how do you tell them apart?" — answer is `typeof a === "string"` vs object branch — no tag fits. Then give `type B = { kind: "rect"; w: number; h: number } | { kind: "square"; side: number }`, ask the same — answer is `kind ===`. Teach the decision table: 2 members & distinct `typeof`/`in` → stay untagged; 3+ & overlapping keys → tag.
