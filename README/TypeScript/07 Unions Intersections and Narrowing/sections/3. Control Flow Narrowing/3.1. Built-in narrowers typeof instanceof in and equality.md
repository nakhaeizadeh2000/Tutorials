## 3.1. Built-in narrowers — `typeof` `instanceof` `in` and equality

### 1) **`typeof` and `instanceof`** (the runtime checks the checker trusts for primitive and class unions)

**Definition** — `typeof x === "string"` narrows `string | number` to `string`; `x instanceof Dog` narrows `Dog | Cat` (class instances) to `Dog`. The checker knows these runtime expressions *prove* which branch a value currently inhabits — control-flow analysis threads the narrowed type through the `if`/`else`, `while`, and `for` blocks without a cast.

**What problem it solves / history** — runtime JavaScript has always separated primitives by `typeof` and class instances by `instanceof` — TypeScript (since 1.6) simply taught the checker to *reuse* those same expressions as proofs instead of inventing new syntax. Unlike discriminant checks (which require a designed `kind`), `typeof`/`instanceof` work on existing runtime shape — no type redesign needed for primitive or class-heavy code that already had the checks.

**Modern guidance** — as of TypeScript 5.9 era, prefer `typeof` for primitive unions (`string | number | bigint | boolean | symbol`) — the checker narrows only the string literals from `typeof`'s result set (`"string" | "number" | "bigint" | "boolean" | "symbol" | "undefined" | "object" | "function"`). Prefer `instanceof` only for `class`-based branches — never for interfaces or object literals (they have no runtime constructor). For broader object unions, `in` or discriminant equality is usually cheaper than an `instanceof` chain.

**Runnable example** — `typeof`/`instanceof` narrow with control flow (good vs bad, `tsc --strict`):

```typescript
// good — typeof narrows primitive union branch by branch
function format(v: string | number): string {
  if (typeof v === "string") return v.toUpperCase(); // narrowed to string
  return v.toFixed(2); // narrowed to number
}
console.log(format("hello")); // HELLO
console.log(format(3.1415)); // 3.14

// good — instanceof narrows class union (instance check, not structural)
class Dog { bark(): string { return "woof"; } }
class Cat { meow(): string { return "meow"; } }
type Pet = Dog | Cat;
function speak(p: Pet): string {
  if (p instanceof Dog) return p.bark(); // narrowed to Dog
  return p.meow(); // narrowed to Cat
}
console.log(speak(new Dog())); // woof

// good — typeof filters null away from T | null where primitive
function len(v: string | null): number {
  if (typeof v === "string") return v.length; // narrowed away null
  return 0; // v is null
}
console.log(len("hi")); // 2

// bad — instanceof on plain objects never narrows (no runtime class)
type A = { kind: "a"; x: number };
type B = { kind: "b"; y: number };
type AB = A | B;
function describe(a: AB): string {
  // if (a instanceof A) // error — A is not a value — no runtime constructor
  // fix — use discriminant equality or 'in'
  if (a.kind === "a") return `a ${a.x}`;
  return `b ${a.y}`;
}
console.log(describe({ kind: "a", x: 1 })); // a 1

// bad — loose typeof equality without the literal is not a narrower
function handle(v: string | number): void {
  // if (typeof v == "String") // capitalization error — checker does not narrow "String"
  if (typeof v === "string") console.log(v.toUpperCase()); // must use lowercase literal
}
```

**Common confusion** — "`typeof null === "object"` narrows to object" — `typeof null` is `"object"` at runtime (JavaScript quirk) — the checker does not treat it as narrowing to object — pair `typeof x === "object"` with `x !== null` to eliminate `null`. "`instanceof` works on interfaces" — interfaces erase; there is no runtime `Interface` constructor — use `in` or discriminant instead. "`typeof` narrows `string | null`" — `typeof v === "string"` eliminates `null` only because `null`'s `typeof` result is not `"string"` — works, but idiomatically prefer `v !== null` for `T|null` unions.

**Performance note** — `typeof` and `instanceof` are single runtime operations — `typeof` is a type-tag read, `instanceof` walks the prototype chain — checker cost is O(members) per narrowing branch, negligible. No emit delta between narrowing styles — every branch emits its runtime guard. For hot loops over primitive unions (`string | number` per iteration) `typeof` is slightly cheaper than property access; for class unions per `instanceof` vs discriminant property read, discriminant property read is cheaper when many variants exist because `instanceof` chain length grows O(variants).

Contrast with `x instanceof String` (object wrapper) vs `typeof x === "string"` (primitive) — link to [1.1. string number boolean wrapper pitfall](<../../../03 Basic Types and Annotations/sections/1. ### 2) **`in` and property checks** (`"prop" in x` and `x.kind === "a"` — narrowing un-tagged and flat unions)

**Definition** — `"value" in x` checks whether property `value` exists on `x` at runtime — the checker narrows to members *with* that key vs without: `if ("value" in result) return result.value; else return result.error;` for `{ value: number } | { error: string }`. Discriminant equality (`x.kind === "a"`) is a *value* test on a shared literal property, not existence — both are cheaper than `instanceof` for plain objects.

**What problem it solves / history** — not every union can afford a `kind` tag — two-member result types, optional-field bags, and ad-hoc `string | { items: string[] }` unions are idiomatically narrowed via `typeof` or `in` without allocating a wrapper per value (see [1.2 pure "when non-discriminated is better"](<../../1. Union Types/1.2. Discriminated unions the tagged pattern that scales.md>)). `in` was added as a built-in narrower early (TS 2.7) for exactly the `in` vs `typeof` complement: `in` splits object shapes by *property presence*; `===` on `kind` splits tagged unions by *value*.

**Modern guidance** — as of TypeScript 5.9 era, use `in` for two-member un-tagged unions where members have disjoint keys — `{ data: T } | { error: E }` via `"error" in result`, `{ items: string[] }` vs `{}` via `"items" in value`. Use `x.kind === "literal"` for discriminated unions (more readable than `in` when the key exists on every member). Never `in`-check a key that appears on *both* members — that `in` never splits (both have it) — switch to value equality instead.

**Runnable example** — `in` and discriminant equality (good vs bad, `tsc --strict`):

```typescript
// good — 'in' narrows two-member un-tagged union (no kind, just shape)
type Success<T> = { data: T };
type Failure = { error: string };
type Result<T> = Success<T> | Failure;

function unwrap<T>(r: Result<T>): T {
  if ("error" in r) throw new Error(r.error); // narrowed to Failure
  return r.data; // narrowed to Success<T>
}
console.log(unwrap({ data: 42 })); // 42

// good — discriminant equality (the idiomatic tagged path)
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Shape = Circle | Square;
function area(s: Shape): number {
  if (s.kind === "circle") return Math.PI * s.radius ** 2; // narrowed to Circle
  return s.side ** 2; // narrowed to Square
}
console.log(area({ kind: "square", side: 4 })); // 16

// good — 'in' with inherited fallback guard
type Payload = { items: string[] } | { text: string };
function count(p: Payload): number {
  if ("items" in p) return p.items.length; // narrowed to { items: string[] }
  return p.text.length; // narrowed to { text: string }
}
console.log(count({ items: ["a", "b"] })); // 2

// bad — 'in' on key present on every member never narrows (guard is pointless)
type A = { shared: string; a: number };
type B = { shared: string; b: number };
type AB = A | B;
function get(union: AB): string {
  // 'shared' is on both — no narrowing needed, already common
  return union.shared; // ok without guard — 'shared' common
}
// fix — to split branches, check an exclusive key:
function getASafe(union: AB): number | undefined {
  return "a" in union ? union.a : undefined; // splits — only A has a
}

```

**Common confusion** — "`in` checks value, not key" — `in` checks *presence* — `"key" in obj` tests whether `obj` has the property key, not whether the value equals `"key"` — confusion makes people write `if ("circle" in shape)` instead of `shape.kind === "circle"`. "`typeof` can replace `in`" — `typeof` works on primitive type tags, `in` works on property existence — use `typeof` for `string|number`, `in` for object shape alternatives. "`in` works through optional property" — `if ("opt" in x)` distinguishes "present as `undefined`" from "absent" at runtime, but the checker does not treat `x.opt !== undefined` identically — `in` narrows to *member-contains-key*, truthiness narrowing drops more cases.

**Performance note** — `in` compiles to `in` operator (prototype chain walk, O(prototype depth)) — trivial. Discriminant read is property load + `===` — no prototype walk — slightly cheaper for deep prototype chains. No checker emit delta beyond the narrowing rule — both are control-flow analysis, zero emitted helper.

**Mentor note** — exercise: give `type A = { x: number } | { y: string } | { z: boolean }` and ask which `in` check splits correctly — answer is any member's exclusive key — `"x" in value` splits A away from the others. Show that `if ("a" in x)` compiles even when `x` is not a union — the student must see that the guard's power is *proving which member* the value is, not that the check itself is exotic.

### 3) **Equality and truthiness** (`x !== null` / `x != null` / `if (x)` — which nullish removal is sound)

**Definition** — equality narrowers use `===`/`!==`/`==`/`!=` to eliminate members: `if (x === null)` → `null` branch; `if (x !== null && x !== undefined)` → remainder without nullish; `if (x != null)` (loose) eliminates *both* `null` and `undefined` but retains literal type widening quirks. Truthiness `if (x)` eliminates *falsy* values (`false | 0 | "" | null | undefined | 0n`) — stronger than nullish removal and often wrong for strings/numbers where `""`/`0` are valid non-null values.

**What problem it solves / history** — nullish unions (`T | null | undefined`) appear at every boundary (`map.get`, `JSON.parse`, `optionalChaining?.`) — narrowing them to `T` without calling a predicate is the daily chore. Equality null-checks are the one-line proof; truthiness is the terse sibling that piggybacks on JavaScript falsiness but conflates "absent" with "empty string/zero." `== null` idiomatically pairs with `strictNullChecks` as a one-shot filter, while explicit `!= null` vs `if (x)` distinction appears in every production PR diff.

**Modern guidance** — as of TypeScript 5.9 era, prefer `x != null` (loose) or `x !== null && x !== undefined` (strict) to filter nullish unions without introducing extra widening — both are understood by the checker as nullish elimination. Reserve `if (x)` for *truthiness* intent (filtering empties alongside nullish) and never for `string | null` where `""` is a valid value — use `x !== null` there. Pair `===` on discriminant with truthiness only inside already-narrowed branches, not as the primary union split.

**Runnable example** — nullish vs truthiness narrowing (good vs bad, `tsc --strict`):

```typescript
// good — loose != null removes both null and undefined in one proof
type User = { name: string };
function greet(user: User | null | undefined): string {
  if (user != null) return `hi ${user.name}`; // narrowed to User
  return "guest";
}
console.log(greet({ name: "Ada" })); // hi Ada

// good — strict triple keeps intent explicit (and pairs with flag noImplicitCoercion)
function countStr(s: string | null): number {
  if (s !== null) return s.length; // keeps "" as length 0, not treated as absent
  return 0;
}
console.log(countStr("")); // 0 — "" counted, not dropped

// bad — truthiness smuggles empty-string/zero away with nullish
function countStrBad(s: string | null): number {
  if (s) return s.length; // "" is falsy → taken as absent (bug when "" valid)
  return 0;
}
console.log(countStrBad("")); // 0 via bug path — "" treated as absent, not as empty string
// fix — use s !== null (or s != null) instead of if (s)

// good — discriminant equality carving off a branch before truthiness
type Result<T> = { ok: true; value: T } | { ok: false; error: string };
function show<T>(r: Result<T>): string {
  if (r.ok === true) return `ok ${r.value}`; // narrowed via literal equality
  return `err ${r.error}`; // narrowed to failure
}
console.log(show({ ok: true, value: 42 })); // ok 42
// bad would be if (r.ok) on non-boolean discriminant — keep literal ===

// good — optional string where undefined removal preserves "" handling
function display(s?: string): string {
  if (s !== undefined) return `value ${s.length}`; // preserves "" as value
  return "missing";
}
console.log(display("")); // value 0 — "" preserved; if (s) would return missing incorrectly
```

**Common confusion** — "`if (x)` is the same as `x != null`" — `if (x)` drops six falsy values (`""`, `0`, `0n`, `false`, `null`, `undefined`) — `x != null` drops only the last two. "Loose `==` is always bad" — `x == null` as a narrowing guard is idiomatic (and linted-for null-only) precisely because it matches only nullish — use `== null` / `!= null` idiomatically for nullish filtering, and enable `noImplicitAny`/`strict` for genuine mistake-prone loose comparisons elsewhere. "Equality on `T | undefined` needs a discriminant" — no, `!== undefined` and `!= null` are the built-in proof for nullish unions; discriminants solve *unrelated discriminants* on object members.

**Performance note** — equality compares are one operation per branch — loose `!= null` is one comparison that the engine combines; strict `!== null && !== undefined` is two comparisons — micro-cost only in tight loops over nullish-heavy unions. The meaningful cost is correctness: filtering empties unintentionally causes re-fetches and shifted `0` counts — audit costs dwarf the branch cost.

**Mentor note** — show truthiness vs nullish by giving `type Input = string | null` and asking what `if (input)` filters *besides* `null` — answer is `""` (still a bug when `""` is a valid display). Exercise: hand code that uses `if (value)` on `number | null` where `0` is a valid metric — ask to rewrite with `value != null` — ensure the new branch keeps `0`.
