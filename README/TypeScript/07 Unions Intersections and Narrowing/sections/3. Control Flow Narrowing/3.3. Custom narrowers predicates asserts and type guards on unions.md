## 3.3. Custom narrowers — predicates, asserts and type guards on unions

### 1) **Predicate `x is T` on unions** (caller-side narrowing, not body validation)

**Definition** — `function isCircle(shape: Shape): shape is Circle` declares that when the function returns `true`, its argument *is* `Circle` — the checker narrows the caller, not the predicate body. Return type `x is Circle` is a subtype of `boolean`; the body must still prove that returning `true` implies the narrows (usually with discriminant/property checks). The narrowed branch survives the `if (isCircle(shape))` test like built-ins but is reusable across call sites.

**What problem it solves / history** — built-in narrowers cover `typeof`/`in`/`===` but not arbitrary "shape matches my complex business rule" — a predicate lifts a multi-step derivation (validate a field combination, check an external tag) into a reusable narrow with one `if (isValid(x))` site. Predicates appeared with control-flow narrowing (TS 1.6+) as the callable analog to discriminant equality.

**Modern guidance** — as of TypeScript 5.9 era, use `x is T` when the narrowing condition spans multiple checks or hides detrás an imported validator — e.g., `isSuccess(result): result is { data: T }` that checks `result.ok && "data" in result`. Keep the predicate's body *sound* — returning `true` on a value that is not actually `T` narrows callers to the wrong branch and manifests as a runtime property shift rather than a diagnostic. Never use `x is T` to narrow when a single `in`/`===` already splits (prefer the built-ins).

**Runnable example** — predicate over unions (good vs bad, `tsc --strict`):

```typescript
// good — discriminant predicate reusable for Shape
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Shape = Circle | Square;

function isCircle(shape: Shape): shape is Circle {
  return shape.kind === "circle"; // body proves Circle when true
}
function area(shape: Shape): number {
  if (isCircle(shape)) return Math.PI * shape.radius ** 2; // narrowed to Circle
  return shape.side ** 2; // narrowed to Square
}
console.log(area({ kind: "circle", radius: 2 })); // 12.566...

// good — predicate for untagged object union (no kind, shape-only check)
type TextNode = { text: string; bold?: boolean };
type ImageNode = { src: string; alt: string };
type Node = TextNode | ImageNode;

function isText(node: Node): node is TextNode {
  return "text" in node;
}
function render(node: Node): string {
  if (isText(node)) return node.text; // narrowed to TextNode
  return `[image ${node.src}]`; // narrowed to ImageNode
}
console.log(render({ text: "hello" })); // hello

// bad — predicate returning boolean (no 'is') never narrows callers
function isCircleBool(shape: Shape): boolean {
  return shape.kind === "circle";
}
function areaBad(shape: Shape): number {
  if (isCircleBool(shape)) return (shape as Circle).radius ** 2; // requires cast — boolean not narrowing
  return (shape as Square).side ** 2;
}
// fix — use 'shape is Circle' return type in predicate above

// good — predicate vs in/=== decision: prefer direct equality at single site
function areaDirect(shape: Shape): number {
  if (shape.kind === "circle") return Math.PI * shape.radius ** 2; // direct — no predicate needed
  return shape.side ** 2;
}
```

**Common confusion** — "`x is T` validates inside the function" — the *caller's* type is narrowed; the *predicate body* is not rechecked for soundness — returning `true` on a non-`T` is a bug that no diagnostic catches — review the body as a contract. "`is` narrows via `this` or catch variable" — `catch (e: unknown)` with predicate `isError(e): e is Error` is caller-narrowing too — `useUnknownInCatchVariables` makes this common (see [2.2. unknown](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>)). "Boolean wrapper is fine" — `function check(x: T): boolean` never narrows — only `x is T` imports the proof.

**Performance note** — predicates emit as plain functions — runtime cost is the body check (one or several conditions) — checker cost is one branch per predicate call — negligible. Reusing a predicate does not recompute per member beyond the predicate body — cheap. For extremely hot call sites doing 100M calls/sec, inlining `===`/`in` may beat the extra call frame but the difference is runtime arithmetic, not type — the predicate's local caching may pay for itself if it caches invariant parts of the shape.

**Mentor note** — show that predicate call is *also* callable-inspection: `isCircle` reused across 5 run sites narrows at each; direct `===` duplicates the literal per site — ask when to lift to a predicate — answer is 3+ repetitions or multi-step check (validate + brand). Emphasize that a predicate is a *promise* — shipping a buggy body produces a runtime property read bug; review should verify the body returns `false` precisely when the remaining branch is reachable.

### 2) **`asserts x is T` / `asserts condition`** (throwing narrows after the call)

**Definition** — `function assertIsCircle(shape: Shape): asserts shape is Circle` is a *void*-returning function that narrows `shape` *after* it returns — if `shape` is not `Circle`, the function *throws* instead of returning — callers write `assertIsCircle(shape); shape.radius;` with no `if` wrapper. `asserts condition` narrows the boolean condition to `true` — `assertNonEmpty<T>(x: T[]): asserts x is [T, ...T[]]` proves non-empty.

**What problem it solves / history** — predicates return `boolean` and require `if (predicate(x))` per site; assertions let directory-level "must be" guards live outside `if` blocks — `assertDefined(value)` at a function's top replaces repeated `if (!value) throw` per use site, and early exit after `assertNotNull` preserves the rest of the function's body at the narrowed type without wrapping it in an `if`.

**Modern guidance** — as of TypeScript 5.9 era, use `asserts` for *invariant guards* at function or block entry — demand that a value *is* a shape, that an array *is* non-empty, that a status *is* success — and throw when violated. Keep assertion bodies sound (throw when the type is not satisfied) and name `assertIs*` call sites clearly — an assertion that throws behaviorally but narrates the wrong brand is still a runtime lie. Prefer predicates for `if/else` splits (narrowing both branches) and assertions for "fail-fast" leaves (narrowing only the fallthrough path).

**Runnable example** — assertions that narrow post-call (good vs bad, `tsc --strict`):

```typescript
import { strict as assertNode } from "node:assert"; // for demo throw if needed

type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Shape = Circle | Square;

// good — assert narrows after returning (no if wrapper needed)
function assertIsCircle(shape: Shape): asserts shape is Circle {
  if (shape.kind !== "circle") throw new Error(`Expected circle, got ${shape.kind}`);
}
function radiusOf(shape: Shape): number {
  assertIsCircle(shape);
  return shape.radius; // narrowed to Circle — no if wrapper
}
console.log(radiusOf({ kind: "circle", radius: 4 })); // 4

// good — asserts condition narrows boolean / truthiness
function assertNonEmpty<T>(arr: T[]): asserts arr is [T, ...T[]] {
  if (arr.length === 0) throw new Error("empty");
}
function first<T>(arr: T[]): T {
  assertNonEmpty(arr);
  return arr[0]; // narrowed to [T, ...T[]], element exists
}
console.log(first([1, 2, 3])); // 1

// bad — predicate used where assertion pattern expected (if wrapper cargo)
function isCircle(shape: Shape): shape is Circle { return shape.kind === "circle"; }
function radiusBad(shape: Shape): number {
  if (!isCircle(shape)) throw new Error("must be circle"); // verbose
  return shape.radius; // could be replaced by assertIsCircle(shape); return shape.radius
}
// fix — single assert line above uses assertion idiom

// bad — assert that does not throw when the branch widens still "narrows" incorrectly
function assertBad(shape: Shape): asserts shape is Circle {
  // if (shape.kind === "square") throw new Error("square"); // forgot all branches
  // no guard — caller assertBad(square) does not throw but narrow to Circle applied — wrong narrower
  // fix — body must throw unless shape actually is Circle
}
// caller assertBad({ kind: "square", side: 4 }); // would run with wrong shape
```

**Common confusion** — "assert returns `boolean`" — assertion returns `void` (never returns when the assertion is false) — its narrowed typed value is available *after* the call, not via `if`. "Predicate and assert are interchangeable" — when both branches need handling, use predicate (`if (isX) … else …` narrows both); when the non-`X` branch should never be reached (fail-fast), use `assert` (one side throws, fallthrough is narrowed). "An assert with no throw still narrows" — the checker narrows *as if* the call proved the type — if the assertion's body does not throw on a non-`X` path, the narrowing is *unsound* — callers proceed with wrong member.

**Performance note** — assertions emit as guard functions — one call + one equality plus throw path only on violated invariant — zero cost on success (guard succeeds, returns narrowed type). No checker overhead beyond the narrowed-type thread — one assignment propagated.

**Mentor note** — present two call sites: `if (isShapeA(x)) handleA(x); else handleB(x);` vs `assertIsA(x); handleA(x);` — ask which narrows both branches — answers are predicate handles both, assertion handles only success (B path unreachable). Test soundness exercise: give an assert with missing `if (x.kind !== …) throw` — ask what callers see — answer is narrowed to A even when they pass B — silent bug — repair the body to throw precisely on non-A branches.

### 3) **`satisfies` + `as const` with unions** (preserving literal discriminants so narrowing stays precise)

**Definition** — `satisfies Record<string, Shape>` checks that a value *satisfies* the union-typed constraint while *preserving* its literal narrowness — unlike `as Shape`, `satisfies` does not widen. `as const` freezes literals (`"circle" as const` stays `"circle"`, not `string`) and makes arrays `readonly` tuples. Together they keep discriminants tight (`kind: "circle"`) instead of widening to `kind: string`, so downstream `switch(kind)` still threads per literal.

**What problem it solves / history** — before `satisfies` (TS 4.9) many codebases used `as Shape` — the checker widens literal `kind: "circle"` to `kind: string` inside the shape — the discriminant eroded and exhaustive `never` checks stopped catching new members because every value already widened past its literal. `satisfies` checks compatibility *without* widening — the preserved literal continues to narrow exactly whereas `as` hid the gap; `as const` preserves the source container's literal shape.

**Modern guidance** — as of TypeScript 5.9 era, aggregate literal unions via `as const` source and check them with `satisfies` — `const SHAPES = [{ kind: "circle", radius: 1 } as const, …] satisfies Shape[]` — hovers retain `"circle"`/`"square"` literals. When using unions as a map, write `const FEATURE_FLAGS = { darkMode: true, … } satisfies Record<Feature, boolean> as const` — the map's entries keep literal keys while ensuring every flag needed is present. Prefer `as const satisfies` over `as` at union-typed declarations where narrowing or exhaustiveness follows.

**Runnable example** — `satisfies` keeps discriminant literals while `as` widens (good vs bad, `tsc --strict`):

```typescript
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Shape = Circle | Square;

// good — as const + satisfies preserves discriminant literals for downstream narrowing
const shapes = [
  { kind: "circle" as const, radius: 3 },
  { kind: "square" as const, side: 4 },
] satisfies Shape[];
shapes.forEach((s) => {
  if (s.kind === "circle") console.log(s.radius); // kind narrowed to "circle", radius accessible (preserved)
  else console.log(s.side); // s.kind is "square"
});

// good — as vs satisfies under microscope: as widens, satisfies does not
const cBad = { kind: "circle", radius: 3 } as Shape; // widens: cBad.kind is string (Checker loses literal)
const cGood = { kind: "circle", radius: 3 } satisfies Shape; // checks: cGood.kind is "circle" literal
// inside switch the satisfies path narrows correctly; the as path would treat cBad.kind as string-wide — exhaustive check fails

// good — Record with satisfies + as const keeps keys literal-typed for union key
type Feature = "darkMode" | "newNav";
const flags = {
  darkMode: true,
  newNav: false,
} as const satisfies Record<Feature, boolean>; // every Feature key present, values boolean, keys stay "darkMode"|"newNav"
function isEnabled(k: Feature): boolean { return flags[k]; }
console.log(isEnabled("darkMode")); // true

// bad — as const without satisfies would check but would allow extra keys
const flagsBad = {
  darkMode: true,
  newNav: false,
  experimental: true, // excess key but satisfies would error
} as const; // without satisfies constraint — extra key not caught at union-key site
// fix — as const satisfies Record<Feature, boolean> lines above — experimental would error

// good — theme/record pattern where literal keys must be exhaustive union members
const THEMES = ["light", "dark", "auto"] as const;
type Theme = typeof THEMES[number]; // derived union
const themeColors = {
  light: "#fff",
  dark: "#000",
  auto: "auto",
} as const satisfies Record<Theme, string>; // every Theme key present — missing key would error
```

**Common confusion** — "`as const` and `satisfies` are redundant" — `as const` freezes the *value* side (literal + readonly); `satisfies` checks the shape *against* a union type without widening — they are orthogonal and idiomatically paired. "`satisfies` is the same as `as` with more checks" — `as` widens and weakens — `c as Shape` widens `kind: "circle"` to `string` — losing the exhaustiveness source — `satisfies Shape` verifies and keeps the wide type. "Literal inference already preserved `kind`" — inference widens `const cfg = { kind: "circle", radius: 3 }` to `kind: string` unless `as const` or `satisfies` pairs to keep `"circle"` — see [3.2. widening](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.2. Type inference widening and contextual typing.md>).

**Performance note** — `satisfies` and `as const` are checker-only — emit removes both — no helper — zero runtime cost. Checker cost is one compatibility walk per `satisfies` site — O(properties) — no per-member overhead for `as const` beyond the literal freeze — trivial. The win is exhaustiveness correctness — the `satisfies` preserved discriminant avoids a `never` sink that proves nothing because every discriminant had already widened to `string`.

**Mentor note** — demonstrate hovers: `const x = { kind: "circle", radius: 1 } as Shape` vs `const y = { kind: "circle", radius: 1 } satisfies Shape` — show `x.kind` hover is `string` vs `y.kind` hover is `"circle"`. Ask why exhaustive handling on `x` fails when it was declared via `as` — answer is widen, lost discriminant. Link to [3.3. Literal types](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>) for the widening story and [04 3.3 satisfies on objects](<../../../04 Objects Interfaces and Type Aliases/sections/3.
