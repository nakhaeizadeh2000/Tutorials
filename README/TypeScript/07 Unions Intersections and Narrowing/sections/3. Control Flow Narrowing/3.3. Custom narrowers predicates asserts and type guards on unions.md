## 3.3. Custom narrowers — predicates asserts and type guards on unions

Reusable guards connect runtime decisions to the alternatives a caller may use. A predicate communicates a type distinction through its boolean result; an assertion describes successful continuation after a call. Both depend on an honest implementation. A checked literal helps construct a valid input, but does not replace those runtime decisions.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent TypeScript fence under its filename and compile with `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`. Run `node dist/FILE.js`. Activate commented negative lines individually and check with the same flags plus `--noEmit` instead of `--outDir dist`.

### 1) **Predicates on unions**

The [callable guard owner](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.3. Type guards predicates asserts and satisfies on functions.md>) explains predicate signatures and their inference conditions. Here the application is selecting a variant from an array. Both an explicit predicate and an eligible inferred predicate communicate the circle distinction. Publishing an explicit `boolean` return type omits that caller contract.

Save as `selection.ts`.

```typescript
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Shape = Circle | Square;
function isCircle(shape: Shape): shape is Circle { return shape.kind === "circle"; }
const inferredCircle = (shape: Shape) => shape.kind === "circle";
function booleanOnly(shape: Shape): boolean { return shape.kind === "circle"; }
const shapes: Shape[] = [{ kind: "circle", radius: 2 }, { kind: "square", side: 4 }];
const explicit = shapes.filter(isCircle);
const inferred = shapes.filter(inferredCircle);
const booleanResult = shapes.filter(booleanOnly);
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type ExplicitResult = Expect<Equal<typeof explicit, Circle[]>>;
type InferredResult = Expect<Equal<typeof inferred, Circle[]>>;
type BooleanResult = Expect<Equal<typeof booleanResult, Shape[]>>;
console.log(explicit.map(shape => shape.radius).join(","));
console.log(inferred.map(shape => shape.radius).join(","), booleanResult.length);
// booleanResult.map(shape => shape.radius); // TS2339: no advertised narrowing
function bodyCheck(shape: Shape): boolean {
  // shape.radius; // TS2339: predicate-related code does not start with Circle
  if (shape.kind === "circle") return shape.radius > 0; // Actual check narrows locally.
  return false;
}
console.log(bodyCheck({ kind: "circle", radius: 2 }));
```

The output is `2`, `2 1`, then `true`. All three filters execute the same tag decision, but their exposed types differ. TypeScript 5.5 introduced the [inferred predicates](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-5.html#inferred-type-predicates) used here. This does not mean every function returning a boolean acquires a predicate. A declared predicate also does not make its input narrowed on entry; ordinary checks can still narrow inside its body.

A predicate's false result matters too. If `isCircle` returns false, the caller excludes Circle from Shape. A selection rule for only *some* circles must not claim that equivalence. Save as `partial.ts`.

```typescript
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Shape = Circle | Square;
function isSmallCircle(shape: Shape): shape is Circle {
  return shape.kind === "circle" && shape.radius < 10; // Deliberately dishonest false case.
}
function badDescription(shape: Shape): string {
  if (isSmallCircle(shape)) return `small ${shape.radius}`;
  return `square ${shape.side.toFixed(0)}`; // Checker trusts the predicate's exclusion.
}
console.log(badDescription({ kind: "circle", radius: 2 }));
console.log(badDescription({ kind: "square", side: 4 }));
try {
  badDescription({ kind: "circle", radius: 20 }); // False does not mean Square.
} catch (error) {
  console.log(error instanceof TypeError ? "false exclusion: TypeError" : "unexpected error");
}
function fixedDescription(shape: Shape): string {
  if (shape.kind === "circle") return shape.radius < 10 ? "small circle" : "large circle";
  return `square ${shape.side.toFixed(0)}`;
}
console.log(fixedDescription({ kind: "circle", radius: 20 }));
```

The output is `small 2`, `square 4`, `false exclusion: TypeError`, then `large circle`. The explicit signature compiles despite its incomplete test. Keep a business selection as a boolean-only function, or separate the true type distinction from that selection as the repaired implementation does. Testing only small circles would miss the false-branch failure. The [original analysis of predicate false cases](https://effectivetypescript.com/2024/02/27/type-guards/) motivates this review question; current primary inference guidance also states the two-sided predicate contract.

These examples start from a trusted Shape union. Checking a tag on arbitrary unknown input would not prove that its radius is a number. Use the [parsing owner](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>) for that boundary.

### 2) **Assertions describe successful continuation**

An assertion is useful when failing the requirement should stop the current operation. `asserts shape is Circle` relates the argument to a type. `asserts condition` can also refine the referenced shape when the caller supplies a discriminant comparison. The annotation supplies no automatic runtime guard; the body must implement the promised failure behavior. [Assertion signatures](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-7.html#assertion-functions) model that successful continuation.

Save as `assertions.ts`.

```typescript
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Shape = Circle | Square;
function assert(condition: unknown): asserts condition {
  if (!condition) throw new Error("circle required");
}
function assertCircle(shape: Shape): asserts shape is Circle {
  if (shape.kind !== "circle") throw new Error("circle required");
}
function byCondition(shape: Shape): string {
  assert(shape.kind === "circle");
  return shape.radius.toFixed(0);
}
function byType(shape: Shape): string {
  assertCircle(shape);
  return shape.radius.toFixed(0);
}
console.log(byCondition({ kind: "circle", radius: 3 }), byType({ kind: "circle", radius: 4 }));
for (const read of [byCondition, byType]) {
  try { read({ kind: "square", side: 2 }); }
  catch (error) { console.log(error instanceof Error ? error.message : "unexpected error"); }
}
function dishonest(_shape: Shape): asserts _shape is Circle {} // Accepted empty body.
function useDishonest(shape: Shape): string {
  dishonest(shape);
  return shape.radius.toFixed(0);
}
try { useDishonest({ kind: "square", side: 2 }); }
catch (error) { console.log(error instanceof TypeError ? "empty assertion: TypeError" : "unexpected error"); }
function ordinary(shape: Shape): void {
  if (shape.kind !== "circle") throw new Error("circle required");
}
// function afterVoid(shape: Shape) { ordinary(shape); return shape.radius; } // TS2339
```

The output is `3 4`, two `circle required` lines, then `empty assertion: TypeError`. Both honest assertions reject Square before the radius operation. The empty assertion still narrows its caller and then fails at that operation. An ordinary `void` signature does not advertise the same refinement even if its current body throws for Square.

A direct `if (shape.kind !== "circle") throw ...` is also valid when a local guard is clearer. Extract an assertion to express a shared invariant or failure policy, not because the local check is intrinsically bad. Use a predicate when both alternatives are recoverable. Detailed assertion-library and callable-context rules stay with [assertion functions](<../../../15 Strictness Errors and Validation/sections/1. Assertion Functions/1.1. Assertion signatures asserts condition and asserts x is T.md>) and the callable owner.

### 3) **Checked literals and const assertions with unions**

A discriminated union already carries its tag literals. Asserting `as Shape` exposes that union; it does not change `kind` to arbitrary `string`. `satisfies Shape` checks the source and can retain a specific tag through its contextual typing. A const assertion additionally preserves literal fields and readonly views. None of those operations freezes a runtime object.

Save as `literals.ts`.

```typescript
type Circle = { kind: "circle"; radius: number };
type Square = { kind: "square"; side: number };
type Shape = Circle | Square;
const asserted = { kind: "circle", radius: 3 } as Shape;
const checked = { kind: "circle", radius: 3 } satisfies Shape;
const precise = { kind: "circle", radius: 3 } as const satisfies Shape;
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type AssertedTag = Expect<Equal<typeof asserted.kind, "circle" | "square">>;
type CheckedTag = Expect<Equal<typeof checked.kind, "circle">>;
type CheckedRadius = Expect<Equal<typeof checked.radius, number>>;
type PreciseRadius = Expect<Equal<typeof precise.radius, 3>>;
function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2;
    case "square": return shape.side ** 2;
    default: { const complete: never = shape; return complete; }
  }
}
console.log(area(asserted).toFixed(1), area(checked).toFixed(1)); // Both narrow correctly.
console.log(Object.isFrozen(precise));
Reflect.set(precise, "radius", 8); // Deliberately bypass the readonly static view.
console.log(precise.radius); // Runtime 8, despite its retained static literal type 3.
// precise.radius = 8; // TS2540: readonly through this view
// const tag: "circle" = asserted.kind; // TS2322: exposes the union
// const invalid = { kind: "triangle", radius: 3 } satisfies Shape; // TS2322

type Feature = "darkMode" | "newNav";
const flags = { darkMode: true, newNav: false } as const satisfies Record<Feature, boolean>;
console.log(flags.darkMode, flags.newNav);
// const missing = { darkMode: true } as const satisfies Record<Feature, boolean>; // TS2741
// const extra = { darkMode: true, newNav: false, experiment: true } as const satisfies Record<Feature, boolean>; // TS2353
// const reversed = ({ darkMode: true, newNav: false } satisfies Record<Feature, boolean>) as const; // TS1355
```

The output is `28.3 28.3`, `false`, `8`, then `true false`. Both asserted and checked values are valid inputs to an exhaustive Shape handler. Their exposed source precision differs, as the live type assertions establish. The const assertion preserves a readonly literal view but leaves the runtime object mutable; the deliberate reflective write demonstrates the limitation without presenting it as an application update pattern.

`as const satisfies` applies a const assertion to the literal and then checks its contract. Applying `as const` to the already checked expression is rejected by TS1355 in the alternative shown. The feature table checks its keys because that is its declared `Record` contract. It is not a prerequisite for narrowing another declared union. See [object checks and inference](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.3. satisfies assertions and narrowing on object shapes.md>) for the full comparison; [the primary satisfies introduction](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html#the-satisfies-operator) explains the compatibility check.

### 4) **Common confusion**

A predicate must justify exclusion as well as acceptance. “Every accepted value is Circle” is too weak when a rejected value might still be Circle. Keep arbitrary selection rules separate from the type distinction or publish only a boolean result. Inference can supply an honest predicate for eligible checks; an explicit predicate can still make a dishonest claim.

An assertion communicates information after normal return, not a value to branch on. Its implementation determines whether an invalid input returns anyway. A checked literal and const assertion provide yet another kind of evidence: source compatibility and static precision, rather than a runtime validator or freeze operation.

### 5) **Performance note**

Predicate/assertion signatures, satisfies checks and const assertions erase. Array filtering, tag checks, function calls, throws and reflective writes remain. An assertion that succeeds still executes its guard; it is not a zero-work success path. No call-frequency threshold, inlining benefit or checker-cost formula was measured here. Choose soundness and failure policy first, then measure actual runtime work if it matters.

### 6) **Mentor note**

For each predicate ask for a true example, an ordinary false example and a value of the claimed type that fails an extra business rule. The large circle exposes the missing false-case reasoning immediately. Have the learner repair the contract without using a cast and explain the resulting branch types.

Then compare byCondition and byType on both variants. A sound answer explains the actual throw as well as the caller's refinement. Finally predict the four type assertions and the frozen check in literals.ts before execution. If the learner says `as Shape` makes kind string or `as const` freezes the object, use the observed results to separate the static view from runtime state.
