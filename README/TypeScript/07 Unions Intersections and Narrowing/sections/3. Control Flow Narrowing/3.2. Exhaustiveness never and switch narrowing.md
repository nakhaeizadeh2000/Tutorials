## 3.2. Exhaustiveness — `never` and `switch` narrowing

### 1) **Exhaustiveness via `never`** (the assignment that proves every branch was handled)

**Definition** — an *exhaustive* handler accounts for every member of a union — if one member is missing, the check must error. The idiomatic proof is a `never` assignment after narrowing: `const _exhaustive: never = remaining;` or a helper `function assertNever(x: never): never { throw new Error(…); }` called as `default: return assertNever(value);`. If any branch remains, the narrowed `remaining` is that member's type, not `never` — the assignment errors — the compiler becomes the proof.

**What problem it solves / history** — `switch` with `default: break` silently swallows new variants — a new `Shape` kind or `Action` type ships, the reducer returns stale state, and no error fires until a runtime path produces the wrong branch. Handling exhaustiveness via `never` dates to `never` as empty/bottom (TS 2.0) and control-flow analysis in 2.0+ that tracks narrowed types through blocks — the `never` sink exploits the fact that `never` is assignable only from unreachable code — reaching it means a case is missing.

**Modern guidance** — as of TypeScript 5.9 era, add a `never` sink to every `switch`/`if/else` that handles a *public* union whose members may grow — `Shape`, `Action`, `Status`, `EventKind`, `Result`. Use the helper `assertNever` at `default:` so the throwing branch also returns `never` — the caller knows the path never returns normally. For `if/else` chains, write `else { const _exhaustive: never = value; return assertNever(_exhaustive); }` rather than `else { /* assume no cases left */ }`.

**Runnable example** — `never` sink that blocks a missing variant (good vs bad, `tsc --strict`):

```typescript
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; side: number }
  | { kind: "triangle"; base: number; height: number };

function assertNever(x: never): never {
  throw new Error(`Unhandled ${JSON.stringify(x)}`);
}

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2;
    case "square": return shape.side ** 2;
    case "triangle": return (shape.base * shape.height) / 2;
    default: return assertNever(shape); // narrowed to never iff every kind handled
  }
}
console.log(area({ kind: "circle", radius: 3 })); // 28.274...

// good — bare never assignment also proves exhaustiveness in if/else
type Direction = "up" | "down" | "left" | "right";
function opposite(dir: Direction): Direction {
  if (dir === "up") return "down";
  if (dir === "down") return "up";
  if (dir === "left") return "right";
  if (dir === "right") return "left";
  // else { const _e: never = dir; return _e; } // if you comment out one case, this line errors
  const _exhaustive: never = dir; // dir is never — all four handled
  return _exhaustive;
}

// bad — default swallows missing variant silently (no error when Shape gains kind)
function areaBad(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2;
    case "square": return shape.side ** 2;
    case "triangle": return (shape.base * shape.height) / 2;
    default: return 0; // compiles even when Shape gains | { kind: "ellipse" }
  }
}
// fix — replace default: return 0 with default: return assertNever(shape)

// good — preview: add a variant without updating handler → compiler blocks PR
type ShapeExtended = Shape | { kind: "ellipse"; rx: number; ry: number };
function areaExtended(shape: ShapeExtended): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2;
    case "square": return shape.side ** 2;
    case "triangle": return (shape.base * shape.height) / 2;
    case "ellipse": return Math.PI * shape.rx * shape.ry;
    default: return assertNever(shape); // exhaustive — all four handled
  }
}
// if ellipse case were missing, the line above would error: TS2345 Ellipse not assignable to never
```

**Common confusion** — "`default: break` is enough" — `default: break` *hides* the missing variant — the `never` line is what turns omission into a compile error. "`never` is a value you return" — you never *return* `never` — you *assign* the remaining narrowed type to `never`; reachability makes the assignment valid only when no cases remain. "`assertNever` must be in every case" — only in `default` or the trailing else — cases prove they handle their literal, the trailing sink proves nothing is left.

**Performance note** — `never` sinks erase — `const _exhaustive: never = dir` becomes nothing in emit; `assertNever` is a one-line `throw` helper. Zero cost on the normal path (default not taken). Checker cost is one assignment per sink — O(members) walks once — negligible.

**Mentor note** — seed the convention with a shared `assertNever` util in the first union PR — require its import in every exhaustive handler review. Kata: provide `type Status = "idle"|"loading"|"success"|"error"` with a handler missing `"error"` — ask what line errors when the sink is added — answer is the `never` assignment — then fix by adding the case.

### 2) **`switch` and `if/else` narrowing** (how control-flow threads narrowed types through the branches)

**Definition** — control-flow analysis threads narrowed types through every `switch`/`if`/`else` branch: inside `case "circle":` for `shape.kind === "circle"` the type of `shape` *is* `Circle`; the checker knows the narrowed member for the entire block, not just the condition expression. Fallthrough vs `break` vs `return` determines whether the analysis merges branches afterward — `return`/`throw` inside a case ends that member's proof; `break` leaves the next case to prove the next member.

**What problem it solves / history** — prior to CFA (TypeScript 2.0's control-flow analysis), type information was flow-insensitive — the checker rechecked `shape.kind` per line. CFA made each branch's dependent properties narrowing-aware — `switch (shape.kind)` narrows `shape` per case so the entire `Circle` payload is available without an extra `if ("radius" in shape)` guard inside the case.

**Modern guidance** — as of TypeScript 5.9 era, handle discriminated unions with `switch(kind)` first — each `case` narrows the union without re-testing the discriminant. Use `if (shape.kind === "circle")` when only two branches — `else` covers the other — `switch` earns its keep at 3+ variants. Signal termination inside the case with `return`/`throw` so the `default` exhaustive sink immediately sees an unhandled minority — `break` then trailing logic merges types differently than `return`.

**Runnable example** — switch vs if/else narrowing threaded through cases (good vs bad, `tsc --strict`):

```typescript
type AppEvent =
  | { kind: "click"; x: number; y: number }
  | { kind: "keydown"; key: string }
  | { kind: "scroll"; delta: number };

function handleSwitch(evt: AppEvent): string {
  switch (evt.kind) {
    case "click": return `click ${evt.x},${evt.y}`; // evt is Click — x,y available
    case "keydown": return `key ${evt.key}`; // evt is KeyDown
    case "scroll": return `scroll ${evt.delta}`; // evt is Scroll
    default: {
      const _e: never = evt; // exhaustive — narrowing proved every kind handled
      throw new Error(`Unhandled ${JSON.stringify(_e)}`);
    }
  }
}
console.log(handleSwitch({ kind: "click", x: 1, y: 2 })); // click 1,2

// good — if/else narrows the complement branch (remaining members)
function handleIf(evt: AppEvent): string {
  if (evt.kind === "click") return `click ${evt.x},${evt.y}`; // narrowed to Click, else is 2 members
  if (evt.kind === "keydown") return `key ${evt.key}`; // narrowed to KeyDown, else is Scroll
  return `scroll ${evt.delta}`; // narrowed to Scroll
}
console.log(handleIf({ kind: "scroll", delta: 10 })); // scroll 10

// bad — switch fallthrough mixes narrowing without return/break semantics confusion
function handleFallthrough(evt: AppEvent): string {
  let out = "";
  switch (evt.kind) {
    case "click": out = `click ${evt.x},${evt.y}`; break; // assign then break
    case "keydown": out = `key ${evt.key}`; break;
    // no scroll — out remains "" — missed branch, exhaustive sink outside switch would catch
    default: out = `unknown ${evt.kind}`; // too permissive
  }
  return out;
}
// fix — use return per case or add assertNever inside default as above

// good — narrowing survives through a helper extracted from the branch (not just lexical block)
// caller narrowing propagates — if you extract a handler per kind, assert that exhaustive map exists
const handlers: Record<AppEvent["kind"], (e: AppEvent) => string> = {
  click: (e) => handleSwitch(e as AppEvent), // map enforces all kinds present at type level
  keydown: (e) => handleSwitch(e as AppEvent),
  scroll: (e) => handleSwitch(e as AppEvent),
};
console.log(handlers["click"]({ kind: "click", x: 0, y: 0 })); // click 0,0
```

**Common confusion** — "`switch` narrows `shape` and `if` does not" — both narrow — difference is that `switch` narrows *which literal* labels matched, not that one mechanism is stronger. "Narrowing inside a case persists after `break`" — `break` after `case "a":` with assignment does not mean the next statement is still `A` — once flow merges after the `switch`, the type is un-narrowed again (or the trailing sink handles exhaustiveness). "`return` is stylistic" — `return` inside the branch terminates that control path — the trailing `never` sink sees only remaining paths — `break` plus post-switch sink behaves differently — prefer `return`/`throw` per case when the function can return the result directly.

**Performance note** — `switch` vs `if/else` emits the same dispatch under the engine — `switch` on strings may compile to a jump table for many string literals (engine heuristic), `if/else` is linear — large variant counts (8+) favor `switch` for engine branching cost. Checker CFA cost is O(branches) per switch/if chain regardless — not a source of type-level perf regression.

**Mentor note** — demo narrowing by hovering member-specific properties inside each `case` — point out which properties are present exclusively in that branch. Ask students to predict what hovers inside `case "click":` for the original `A | B | C` union — answer is only the `Click` shape — then ask what hovers *after* the `switch` (un-narrowed unless exhausted).

### 3) **When exhaustiveness is worth the ceremony** (public `APIResult`, state machines, reducers — the cases where missing-case is production bug)

**Definition** — exhaustiveness ceremony (writing the `never` sink) is worth it whenever the union is *public* (across files, across team, serialized over the wire) and *growing* (new variant may be added by someone else) — API response shapes (`{ status: 200 | 201 | 400 | 404 }`), product reducers, permission roles, event kinds. For throwaway one-off unions inside a single function (`string | number` formatting), the case count is bounded and rarely extended — `switch` without a sink is proportionate.

**What problem it solves / history** — exhaustiveness-less reducers and mappers led to silent fallback bugs — a new `Action` type (`"duplicate"`) shipped, the reducer fell to `default: return state` (stale state), and tests missed it because fixtures never exercised the new variant. `never` turns the silent path into a compile error at the reducer — the next PR adding the variant must fix the reducer or CI fails — missing-case bugs become unshippable at PR gate, not post-ship triage.

**Modern guidance** — as of TypeScript 5.9 era, require a `never` sink in (a) any module-exported union handler whose members represent *domain* variants (API result, state branch, permission gate) — the union may be extended at the domain layer without expanding the handler file; (b) reducers and event handlers fed by external/serialized data; (c) any handler where `default` would return a *value* (stale `0`/`""`) rather than throw — returning a value means falling through to a valid output path with no signal that the new variant was ignored. Skip the sink only when the handler and the union live in the same function and the set is clearly closed (a local two-member primitive split).

**Runnable example** — exhaustive as production gate (good vs bad, `tsc --strict`):

```typescript
// good — public reducer with exhaustive sink — adding a Variant blocks PR until handler fixes
type CartAction =
  | { kind: "add"; id: string; qty: number }
  | { kind: "remove"; id: string }
  | { kind: "clear" };

function assertNever(x: never): never { throw new Error(`Unexpected ${JSON.stringify(x)}`); }
function reduce(cart: Map<string, number>, action: CartAction): Map<string, number> {
  switch (action.kind) {
    case "add": {
      const next = new Map(cart);
      next.set(action.id, (next.get(action.id) ?? 0) + action.qty);
      return next;
    }
    case "remove": { const next = new Map(cart); next.delete(action.id); return next; }
    case "clear": return new Map();
    default: return assertNever(action); // exhaustive — miss "add" duplication or miss new "discount" fails compile
  }
}
const cart = reduce(new Map(), { kind: "add", id: "sku-1", qty: 2 });
console.log(cart.get("sku-1")); // 2

// bad — non-exhaustive default returning stale state — new variant ships with silent no-op
function reduceBad(cart: Map<string, number>, action: CartAction): Map<string, number> {
  switch (action.kind) {
    case "add": { const n = new Map(cart); n.set(action.id, n.get(action.id)! + action.qty); return n; }
    case "remove": { const n = new Map(cart); n.delete(action.id); return n; }
    case "clear": return new Map();
    default: return cart; // compiles even when CartAction gains { kind: "discount" } — reducer returns stale cart for new action
  }
}
// fix — replace default: return cart with default: return assertNever(action)

// good — when set is closed and local, exhaustive is noise (not required)
function format(v: string | number): string {
  if (typeof v === "string") return `s:${v}`;
  return `n:${v}`; // remaining is only number — no public union growing nearby → optional sink
}
```

**Common confusion** — "every union needs a `never` sink" — only public/growing unions where `default` would be a *valid value path* — local one-off primitives rarely need it; the rule is "if adding a variant would be a production bug without a handler change, add the sink; otherwise skip." "`never` sink makes code fragile" — fragility *is* the intent — the next PR adding a variant should be fragile — `never` introduces the exactly-desired fragility. "`default: return assertNever` costs an extra import" — place `assertNever` in one shared util (`src/utils/assertNever.ts`) and import everywhere — the helper itself is one `throw` and is tree-shakeable as the normal path never executes.

**Performance note** — `assertNever` is never-executed under exhaustiveness (thin tail) — cold call, one allocation never taken. The win is de-bugging cost — measuring that a new variant shipped without a handler often means a new customer-facing bug plus triage, not a metric on the check layer. Document ceremony as a code-review rule with lint: `switch` over exported discriminants must end with `assertNever` — faster review, no runtime measure needed.

**Mentor note** — pair this leaf with the next PR drill: extend `CartAction` with `{ kind: "discount"; code: string }`, show `reduce` now errors inside `default: assertNever(action)` — fix by adding `case "discount"`. Ask why the non-exhaustive `reduceBad` would not error — answer is the stale-default return swallows the new member into a valid code path — have juniors experience the missing error as a lesson in why the sink matters.
