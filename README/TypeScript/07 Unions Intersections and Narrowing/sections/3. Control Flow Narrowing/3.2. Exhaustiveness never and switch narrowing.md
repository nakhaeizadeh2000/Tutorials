## 3.2. Exhaustiveness — never and switch narrowing

An exhaustive handler accounts for every alternative in its declared input union. A `never` sink asks the checker to verify that no alternative remains at a particular point. That is a static coverage check. Whether unexpected runtime data throws, falls back or passes through depends on the JavaScript you actually write.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each TypeScript fence under its stated filename and compile independently with `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`. Run `node dist/FILE.js`. For each negative exercise, change only the stated line and check with the same flags plus `--noEmit`, replacing `--outDir dist`.

### 1) **Exhaustiveness via never**

After handled paths return or throw, the remaining input can be assigned to `never` only if its narrowed type permits that assignment. A new union member makes the sink fail unless the handler accounts for it. This is the [Handbook exhaustiveness pattern](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#exhaustiveness-checking). A `never` parameter on a throwing helper checks coverage at its call; the helper's `throw` controls runtime behavior.

Save as `directions.ts`.

```typescript
type Direction = "up" | "down" | "left" | "right";
function assertNever(_value: never): never {
  throw new Error("Unhandled direction");
}
function opposite(direction: Direction): Direction {
  switch (direction) {
    case "up": return "down";
    case "down": return "up";
    case "left": return "right";
    case "right": return "left";
    default: return assertNever(direction);
  }
}
function assignmentOnly(direction: Direction): Direction {
  if (direction === "up") return "down";
  if (direction === "down") return "up";
  if (direction === "left") return "right";
  if (direction === "right") return "left";
  const complete: never = direction;
  return complete;
}
for (const direction of ["up", "down", "left", "right"] as const) {
  console.log(direction, opposite(direction), assignmentOnly(direction));
}
const unexpected = "forward" as Direction; // Deliberately bypass the input contract.
console.log("assignment fallback:", assignmentOnly(unexpected));
try {
  opposite(unexpected);
} catch (error) {
  console.log(error instanceof Error ? error.message : "unexpected error");
}
```

The four valid lines are `up down down`, `down up up`, `left right right`, and `right left left`. The final lines are `assignment fallback: forward` and `Unhandled direction`. Both functions check static coverage, but only one throws for the deliberately invalid runtime value. Inspect `dist/directions.js`: `const complete = direction; return complete;` remains. The annotation erases; the declaration does not.

For the first negative exercise, add `| "forward"` to `Direction` without editing either function. The helper call reports TS2345, and the bare assignment reports TS2322. A concrete remaining string cannot flow to `never`. The opposite assignment direction is different: `never` can flow to `Direction`, which is why returning `complete` is accepted. Do not cast the remaining input to `never` to silence these errors; handle the new alternative or revise the intended input contract.

### 2) **switch and if/else narrowing**

Both forms refine the input along their control-flow paths. `return` exits the function, `throw` ends normal execution, and `break` exits the switch. A `break` does not mean the handled input has disappeared from every path after the switch. Grouped labels also share a body, so the value there can still be a union of those cases.

Save as `flow.ts`.

```typescript
type AppEvent =
  | { kind: "click"; x: number }
  | { kind: "keydown"; key: string }
  | { kind: "scroll"; delta: number };
function assertNever(_value: never): never { throw new Error("Unhandled event"); }
function describe(event: AppEvent): string {
  switch (event.kind) {
    case "click": return `click ${event.x}`;
    case "keydown": return `key ${event.key}`;
    case "scroll": return `scroll ${event.delta}`;
    default: return assertNever(event);
  }
}
function describeIf(event: AppEvent): string {
  if (event.kind === "click") return `click ${event.x}`;
  if (event.kind === "keydown") return `key ${event.key}`;
  if (event.kind === "scroll") return `scroll ${event.delta}`;
  return assertNever(event);
}
function grouped(event: AppEvent): string {
  switch (event.kind) {
    case "click":
    case "keydown":
      // return event.key; // TS2339: click is also possible in this body
      return `direct input ${event.kind}`;
    case "scroll": return `scroll ${event.delta}`;
    default: return assertNever(event);
  }
}
function breakAndContinue(event: AppEvent): string {
  switch (event.kind) {
    case "click": break;
    case "keydown": break;
    case "scroll": break;
  }
  // const complete: never = event; // TS2322: all cases reach this point
  return `after switch ${event.kind}`;
}
const examples: AppEvent[] = [
  { kind: "click", x: 1 }, { kind: "keydown", key: "Enter" }, { kind: "scroll", delta: 2 },
];
for (const event of examples) {
  console.log(describe(event), describeIf(event), grouped(event), breakAndContinue(event));
}
```

The lines are `click 1 click 1 direct input click after switch click`, `key Enter key Enter direct input keydown after switch keydown`, and `scroll 2 scroll 2 scroll 2 after switch scroll`. Remove the scroll case from `describe`: TS2345 reports the scroll member at the helper call. Remove the scroll test from `describeIf`: its trailing helper reports the same missing alternative. These failures depend on the remaining input, not a required choice of switch over if.

A complete handler table has a different proof obligation from a narrowed payload. Save as `table.ts`.

```typescript
type AppEvent = { kind: "click"; x: number } | { kind: "scroll"; delta: number };
const handlers: Record<AppEvent["kind"], (event: AppEvent) => string> = {
  click: event => `click slot received ${event.kind}`,
  scroll: event => `scroll slot received ${event.kind}`,
};
console.log(handlers.click({ kind: "scroll", delta: 3 })); // Accepted: each parameter is AppEvent.
// const missing: Record<AppEvent["kind"], (event: AppEvent) => string> = { click: () => "click" }; // TS2741
function clickOnly(event: Extract<AppEvent, { kind: "click" }>): string {
  return `click ${event.x}`;
}
// clickOnly({ kind: "scroll", delta: 3 }); // TS2322
console.log(clickOnly({ kind: "click", x: 4 }));
```

The output is `click slot received scroll`, then `click 4`. `Record` requires both keys; it does not correlate a key with a narrower parameter when every value is declared `(event: AppEvent) => string`. A branch-specific parameter does reject the wrong variant. Full correlated table construction belongs to [mapped types](<../../../09 Utility Types and Type Transformations/sections/1. Mapped Types/1.1. Mapped type fundamentals homomorphic mapping over keys.md>); a switch that passes each narrowed payload to its corresponding helper is also a clear dispatch design. Do not insert casts merely to make an indexed call compile.

### 3) **When exhaustiveness is worth the ceremony**

Add the coverage check when adding an alternative should require reviewing this behavior. That applies to a small local state machine as well as a public API. A handler deliberately consuming a subset of a larger event stream can instead have a documented ignore policy. The decision follows the required behavior; public versus local visibility alone does not decide it.

Save as `reducer.ts`. The new action is already included in the input, so the stale fallback is an executed bug rather than an untested future comment.

```typescript
type CartAction =
  | { kind: "add"; id: string; quantity: number }
  | { kind: "clear" }
  | { kind: "remove"; id: string }; // A newly added alternative.
function assertNever(_value: never): never { throw new Error("Unhandled cart action"); }
function stale(cart: ReadonlyMap<string, number>, action: CartAction): ReadonlyMap<string, number> {
  switch (action.kind) {
    case "add": {
      const next = new Map(cart);
      next.set(action.id, (next.get(action.id) ?? 0) + action.quantity);
      return next;
    }
    case "clear": return new Map();
    default: return cart; // Accepts remove and silently preserves the old item.
  }
}
function reduce(cart: ReadonlyMap<string, number>, action: CartAction): ReadonlyMap<string, number> {
  switch (action.kind) {
    case "add": {
      const next = new Map(cart);
      next.set(action.id, (next.get(action.id) ?? 0) + action.quantity);
      return next;
    }
    case "clear": return new Map();
    case "remove": { const next = new Map(cart); next.delete(action.id); return next; }
    default: return assertNever(action);
  }
}
const initial = new Map([["sku-1", 2]]);
const remove: CartAction = { kind: "remove", id: "sku-1" };
const bad = stale(initial, remove);
const good = reduce(initial, remove);
console.log("fallback:", bad.has("sku-1"), bad === initial);
console.log("repaired:", good.has("sku-1"), good === initial, initial.get("sku-1"));
console.log("add:", reduce(new Map(), { kind: "add", id: "sku-2", quantity: 3 }).get("sku-2"));
console.log("clear:", reduce(initial, { kind: "clear" }).size);
```

The output is `fallback: true true`, `repaired: false false 2`, `add: 3`, then `clear: 0`. The repaired reducer handles every action and preserves the original map. Delete its remove case: TS2345 rejects the remaining member at `assertNever(action)`. Replace `stale`'s fallback with that same call and the checker exposes its missing case too.

A throwing default without a `never` parameter can provide runtime failure while still accepting future unhandled union members at compile time. Conversely, a bare `never` assignment can enforce static coverage without throwing at runtime. Make both policies explicit. Meticulous's [exhaustive-switch article](https://www.meticulous.ai/blog/safer-exhaustive-switch-statements-in-typescript) compares guard, lint and missing-return approaches; those checks have different scope. A missing-return check does not detect `default: return cart`, because every path already returns a valid value.

Exhaustiveness is relative to the declared type, not every value another process might send. Parse external data before dispatch; a cast from a parsed value is not that validation. A throwing default is useful for detecting an unexpected runtime path but does not validate a handled variant's payload, quantity range or application permissions. Use the [boundary parsing owner](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>) for that separate contract.

### 4) **Common confusion**

Writing a default is not itself an exhaustiveness proof. A permissive fallback and a plain throwing default can both accept a newly added member without a compiler error. The `never` sink makes that remaining member incompatible. A type assertion to `never` defeats precisely that check.

A function returning `never` promises no normal returned value; its implementation still has to throw or otherwise avoid returning. The annotation does not insert a throw. Similarly, no static proof justifies removing the unexpected-input policy from emitted JavaScript by assumption.

### 5) **Performance note**

The types erase, but switches, if statements, variable declarations, map copies and throwing helpers remain. A throwing default executes when an unexpected value reaches it; the static union does not make that impossible after arbitrary assertions or unchecked inputs. No benchmark here establishes dispatch thresholds, switch versus if speed, helper removal by a bundler or a checker-complexity formula. The cart example copies a map to preserve the input; that runtime work is independent of its exhaustiveness proof.

### 6) **Mentor note**

Have the learner add a union member and identify the exact operation that fails. Require them to explain why returning the remaining value through a `never`-annotated variable does not perform runtime validation. Then inspect the emitted assignment and compare the controlled invalid-input outcomes.

For a review exercise, add `{ kind: "replace"; id: string; quantity: number }` to `CartAction`. A sound repair adds a case that copies the map and sets the specified quantity, retains the sink, and checks replacement of an existing item plus preservation of the original map. Returning the old cart or casting `action` to `never` would suppress the desired review signal rather than implement the new behavior.
