## 2.1. Zod, Valibot and Runtime Validation (TS erasure bridge)

### 1) **Problem** (no runtime)

**Problem** — Types erase (see [01 2.2 Erasure](<../../../01%20TypeScript%20Fundamentals%20and%20Mental%20Model/sections/2.%20Mental%20Model%20—%20Structural%20Types%20and%20Erasure/2.2.%20Erasure%20and%20Emit%20no%20runtime%20types.md>)). Data from `fetch`/`JSON`/`env` is `unknown` even if you write `as User`. No runtime validator = silent corruption.

```typescript
type User = { id: string; email: string };
let raw: unknown = JSON.parse(`{"id":"1"}`); // missing email
// let u = raw as User; // bad — compiles, u.email undefined at runtime
// console.log(u.email.toLowerCase()); // TypeError
```

---

### 2) **Solution** (Zod schema)

**Solution — codec/validator:** define schema once → parse at runtime → infer type — no duplication.

```typescript
import { z } from "zod"; // Zod 3 (stable) — Valibot similar but ESM-first

const UserSchema = z.object({
  id: z.string(),
  email: z.string().email(),
  age: z.number().int().min(0).optional(),
});
type User = z.infer<typeof UserSchema>; // inferred — single source

// parse throws if invalid, returns User if ok
let raw2: unknown = JSON.parse(`{"id":"1","email":"a@b.com"}`);
let user: User = UserSchema.parse(raw2); // ok
// let bad: unknown = { id: 123 }; UserSchema.parse(bad) // ZodError

// safeParse for no-throw
let result = UserSchema.safeParse(raw2);
if (result.success) console.log(result.data.email); // User
else console.error(result.error.issues);

// Valibot (alternative — smaller bundle, fast)
import * as v from "valibot";
const UserSchemaV = v.object({ id: v.string(), email: v.pipe(v.string(), v.email()) });
type UserV = v.InferOutput<typeof UserSchemaV>;
// v.parse(UserSchemaV, raw2)

// choose one validator per repo — don't mix zod + valibot on same boundary
```

Also covers `superstruct`, `arktype`; Zod most common in 2025+ Next.js/NestJS stacks.

---

### 3) **Example** (z.infer)

```typescript
// end-to-end (fetch + zod)
import { z } from "zod";
const ProductSchema = z.object({
  id: z.string(),
  price: z.number().nonnegative(),
  status: z.enum(["draft", "published"]),
});
type Product = z.infer<typeof ProductSchema>; // "draft"|"published" already narrow

async function fetchProduct(id: string): Promise<Product> {
  const raw: unknown = await fetch(`/api/products/${id}`).then(r => r.json());
  return ProductSchema.parse(raw); // validated — typed
}

// discriminated union via schema
const ResultSchema = z.discriminatedUnion("status", [
  z.object({ status: z.literal("ok"), value: z.string() }),
  z.object({ status: z.literal("error"), error: z.string() }),
]);
type Result = z.infer<typeof ResultSchema>;

// helper for env (common pitfall)
const EnvSchema = z.object({ DATABASE_URL: z.string().url(), PORT: z.coerce.number().default(3000) });
type Env = z.infer<typeof EnvSchema>;
let env: Env = EnvSchema.parse(process.env); // fails fast if missing
```

**Common confusion** —

- "`z.infer` is extra" — no, it's the type reuse that prevents drift between runtime schema and type.

**Performance note** —

Validation cost ~microseconds per object (zod ~10–20% overhead vs raw). For hot hot path (streaming 10k rows), benchmark `valibot` (faster, tree-shakeable) vs `zod`.

**Example** —

Boundary parse once, trust inside — avoid per-function re-parse.

**Mentor note** —

Rule: "every `unknown` boundary needs a schema." PR template question: "which validator guards this `fetch`?"
