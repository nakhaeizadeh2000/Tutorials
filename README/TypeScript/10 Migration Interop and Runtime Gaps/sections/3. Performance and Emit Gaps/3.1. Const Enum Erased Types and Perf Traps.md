## 3.1. Const Enum, Erased Types and Perf Traps

### 1) **Trap** (const enum cross-module)

**Trap — `const enum` looks zero-cost (inlines) but breaks `isolatedModules`:**

```typescript
// shared.ts
export const enum Status { Ready = 0, Pending = 1 }

// app.ts (with isolatedModules: true)
import { Status } from "./shared.js";
console.log(Status.Ready); // with isolatedModules error — const enum cross-file inlining needs whole-program emit
// error: Cannot access ambient const enums when 'isolatedModules' is enabled.
```

Why: `const enum` inlines *values* at use site — requires whole program; per-file transpile (swc/esbuild/tsx) cannot see definition.

### 2) **Alternative** (union)

**Fix — use erasable union (zero emit, isolatedModules-safe):**

```typescript
// shared pattern (2025+)
export type Status = "ready" | "pending";
export const Status = { Ready: "ready" as const, Pending: "pending" as const } as const;
// or numeric if needed: Ready = 0

export type StatusNum = 0 | 1;
export const StatusNum = { Ready: 0 as const, Pending: 1 as const } as const;

import { Status } from "./shared.js";
console.log(Status.Ready); // "ready" — value object, not enum inlining
function handle(s: Status) {
  switch (s) {
    case "ready": return "R";
    case "pending": return "P";
    default: { const _ex: never = s; throw new Error("exhaust"); }
  }
}
handle("ready"); // ok
```

If you *must* keep `const enum`, use `preserveConstEnums: true` (then emits real object) — but you lose zero-cost benefit. Better to migrate.

### 3) **Expert** (isolatedModules perf)

**Expert traps beyond const enum:**

- **Erased helpers cost** — `useDefineForClassFields`, `__extends` legacy emit for `target: es5` bloats. Keep `target: es2022`.
- **`esModuleInterop` helpers** — `__importDefault` per default CJS import — negligible but measurable in micro-benchmark.
- **`verbatimModuleSyntax` + `import type`** — missing `type` triggers emit of empty import (runtime side-effect import not elidable) — ensure `import type` for types.
- **Large `skipLibCheck: false`** — typecheck drags in all `@types` — slows CI; keep `true` for apps.

```typescript
// bad emit (verbatim false): import { User } from "./user.js" where User is type-only
// emit still has: import { User } from "./user.js" → runtime require for side-effect (wasted)
// good: import type { User } from "./user.js" → erased even with bundler

// measure advice: `tsc --extendedDiagnostics` shows parse/bind/check/emit time per program
// `tsc --generateTrace trace/` → analyze hot checker paths (Chrome trace)
// prefer `swc`/`esbuild` for emit hot path; keep `tsc` only for check (--noEmit)
```

### Mentor note

Add lint `no-const-enum` (`typescript-eslint`) or Biome `noConstEnum`. One rule prevents the isolation break.

### Common confusion

- "`const enum` is faster" — only for whole-program; with modern tooling it's a bug vector with same runtime cost as object after inlining decisions removed.

### Performance note

Prefer union literal runtime object (`as const`) — bundle size same as enum, but tree-shake friendly when `isolatedModules`.

### Expert gap

Erased `type` vs `enum` emit mismatch is #1 TS build perf trap reported on issue tracker — codemod early.
