## 1.1. Promise states and the Promise type anatomy

A promise represents an eventual outcome: fulfillment with a value or rejection with a reason. Promise<T> describes the fulfillment value's type. It does not encode the current pending/fulfilled/rejected state or a separate rejection type. TypeScript's declarations describe permitted uses; the JavaScript implementation performs resolution and schedules reactions.

Examples use **TypeScript 7.0.2** and **Node.js 20.20.2**, verified 2026-10-17. Create each named file in a directory without a tsconfig. Compile a TypeScript file with `tsc --strict --target es2022 --module nodenext --outDir dist FILE.mts`, then run `node dist/FILE.mjs`. The standalone JavaScript failure demonstration has its own command.

### 1) **Separate fulfillment typing from state and resolution**

An ordinary Promise<T> reference does not narrow according to its current runtime state. Await or a fulfillment handler exposes the fulfilled value; neither converts a possibly rejecting operation into one that cannot fail. A user interface can still model loading/error/success in its own discriminated union. That is application state, not an inspection API on a native promise.

A promise can be pending, fulfilled or rejected. Fulfilled and rejected are settled states. Resolving with another pending promise commits to adopting its eventual outcome, so resolved does not always mean already fulfilled. The [ECMAScript constructor specification](https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-promise-executor) defines that mechanism. Save:

```typescript
// file: states.mts
const events: string[] = [];
let release!: (value: number) => void;
const inner = new Promise<number>((resolve) => { release = resolve; });
const adopted = new Promise<number>((resolve, reject) => {
  events.push("executor");
  resolve(inner);
  reject(new Error("ignored after resolve"));
});
let observed = false;
const observer = adopted.then((value) => { observed = true; events.push(`value:${value}`); return value; });
events.push("after construction");
if (events.join("|") !== "executor|after construction") throw new Error("executor timing");
await Promise.resolve();
if (observed) throw new Error("inner has not completed");
release(7);
if (await observer !== 7) throw new Error("adoption result");
console.log(events.join("|"));
```

It prints `executor|after construction|value:7`. The executor ran during construction, while the fulfillment handler ran later. Resolving with inner did not immediately produce a number; it adopted inner. The later reject call could not replace that decision. The same static type Promise<number> described the operation throughout.

Promise.resolve(42) can already be fulfilled when it returns; a newly obtained promise is not necessarily still pending. Even an already fulfilled promise's then handler runs later. [Jake Archibald's original introduction](https://web.dev/articles/promises) develops states, late observers and composition; its historical browser-support advice is separate from this current fixture.

### 2) **Read then, catch and finally as outcome propagation**

The standard declarations give then two result parameters, one for fulfillment and one for rejection handling, returning Promise<TResult1 | TResult2>. A handler may return a plain value or a PromiseLike result. Catch adds a recovery result to the possible fulfillment type: Promise<T | U>. That union says nothing about which rejection reasons remain possible.

Finally retains Promise<T> as its fulfillment type. At runtime it waits for returned cleanup work: successful cleanup preserves the original outcome, while a thrown error or rejected cleanup result replaces it with a rejection. The [finally algorithm](https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-promise.prototype.finally) makes both propagation and cleanup adoption explicit. Save:

```typescript
// file: chains.mts
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
const mapped = Promise.resolve(2).then((value) => Promise.resolve(value * 2));
const recovered = Promise.reject<number>(new Error("offline")).catch((_reason: unknown) => "fallback" as const);
const preserved = Promise.resolve(3).finally(() => 99);
const overridden = Promise.resolve(3).finally(() => { throw new Error("cleanup failed"); });
type Results = [
  Expect<Equal<typeof mapped, Promise<number>>>,
  Expect<Equal<typeof recovered, Promise<number | "fallback">>>,
  Expect<Equal<typeof preserved, Promise<number>>>,
  Expect<Equal<typeof overridden, Promise<number>>>
];
// Attach rejection handling before waiting on other work.
const overrideResult = overridden.catch((reason: unknown) => {
  if (!(reason instanceof Error)) throw new Error("unexpected reason");
  return reason.message;
});
if (await mapped !== 4) throw new Error("mapped result");
if (await recovered !== "fallback") throw new Error("recovery result");
if (await preserved !== 3) throw new Error("finally transformed the value");
if (await overrideResult !== "cleanup failed") throw new Error("cleanup rejection");
let finishCleanup!: () => void;
const cleanup = new Promise<void>((resolve) => { finishCleanup = resolve; });
let delivered = false;
const delayed = Promise.resolve(5).finally(() => cleanup).then((value) => { delivered = true; return value; });
await new Promise<void>((resolve) => setTimeout(resolve, 0));
if (delivered) throw new Error("cleanup was not awaited");
finishCleanup();
if (await delayed !== 5) throw new Error("delayed value");
console.log("mapped 4; recovered fallback; preserved 3; cleanup failed; delayed 5");
```

All assertions pass and the final line is printed. Returning 99 from finally does not replace 3. Throwing during cleanup does replace the outcome, although overridden still has fulfillment type Promise<number>. The delayed case supplies a controlled cleanup gate. A separate timer task lets already queued reactions run before checking that the unresolved cleanup still blocks delivery; its wall-clock duration is not asserted.

For a static failure, change the recovered expectation to Promise<number>. Compile with the same flags plus noEmit instead of outDir: TS2344 exposes the added recovery value. Restore it. Recovery can return T, a different type, any, or throw; it does not always make a visibly larger union. Returning never from a throwing handler does not add a fulfillment member.

### 3) **Construct promises at the right boundary**

The standard constructor accepts resolve with T | PromiseLike<T> and reject with an optional any reason. Catch callbacks likewise receive any in the current declarations. That is a library typing, not proof that every catch variable is unchecked: under strict checking a catch-clause variable defaults to unknown, and a callback can explicitly accept unknown as above. Narrow before reading arbitrary reason properties. Error objects are often useful for stacks and metadata, but the language permits other rejection values.

Use a constructor when bridging a completion protocol such as callbacks or when deliberately controlling a promise for a fixture. An explicit type argument can make that boundary clear; inference or contextual typing can also supply it. For example, `const value: Promise<number> = new Promise((resolve) => resolve(42));` checks without an explicit constructor type argument. An unconstrained construction without a useful inference source need not infer the fulfillment type from a later resolve call. Inspect the actual result instead of imposing one annotation rule everywhere.

Keep a Promise executor synchronous. It starts work and reports through resolve/reject; its returned value is ignored. Prefer an ordinary async function when composing existing promises. **Do not pass an async function as the executor.** Its thrown error rejects the async function's separate returned promise rather than automatically rejecting the outer promise. [ESLint's no-async-promise-executor explanation](https://eslint.org/docs/latest/rules/no-async-promise-executor) describes this pitfall.

Save this deliberate failure observation as a separate Node script and run `node bad-executor.mjs`:

```javascript
// file: bad-executor.mjs
import assert from "node:assert/strict";
// Test-only observation of the lost rejection in this standalone process.
const reported = new Promise((resolve) => { process.once("unhandledRejection", resolve); });
const outer = new Promise(async () => { throw new Error("lost executor failure"); });
let outerSettled = false;
outer.then(() => { outerSettled = true; }, () => { outerSettled = true; });
const reason = await reported;
assert(reason instanceof Error);
assert.equal(reason.message, "lost executor failure");
assert.equal(outerSettled, false);
console.log("lost executor failure; outer still pending");
```

It prints `lost executor failure; outer still pending`. The observer makes this failure inspectable in an isolated demonstration; adding a process listener is not the repair. Compose an ordinary async function's returned promise instead, or report completion from a synchronous constructor executor. The constructor can turn a synchronous executor throw into rejection; an async function's returned rejection is a different path.

### 4) **Common confusion**

Promise<T> is not a state union or Promise<T, Error>. A UI state model or Result value can express additional application information, but that does not change the native Promise type. A promise resolving to T may still reject or remain pending indefinitely; the generic is not a liveness guarantee.

Finally preserves the fulfillment type, not an unconditional guarantee of successful completion. A cleanup throw, rejection or indefinitely pending cleanup changes what the caller observes. Likewise, the catch fulfillment union is not an inventory of errors that have been handled.

### 5) **Performance note**

Promise construction executes its executor immediately. Chaining and awaiting involve runtime promise/reaction work and scheduling; type arguments and alias assertions erase. This lesson measures no allocation count, nanosecond overhead or claim that awaiting a settled/non-promise value is free. Prefer synchronous operations for purely synchronous work and measure actual hot paths before changing an otherwise clear async design.

### 6) **Mentor note**

Ask why adopted can be committed to inner while its observer has not run, and why overridden has Promise<number> despite rejecting with a cleanup error. Then trace the two promises in the async-executor failure. A sound explanation separates fulfillment typing, resolution, runtime state, reaction scheduling and the promise that owns a rejection.
