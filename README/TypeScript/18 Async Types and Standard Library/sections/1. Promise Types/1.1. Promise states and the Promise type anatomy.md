## 1.1. Promise states and the Promise type anatomy

### 1) **One generic, three states** (pending plus fulfilled plus rejected, state invisible in the type)

**Definition** — `Promise<T>` is a single generic over the *fulfillment value* `T`: at runtime the promise sits in exactly one of three states (pending → fulfilled(`T`) | rejected(`reason`)), but the type records only `T` (states unrepresented — a `Promise<T>` variable may be pending, fulfilled, or rejected; the checker cannot distinguish). Rejection reasons are untyped (`any` — the executor legacy, part 3).

**What problem it solves / history** — callback pyramids (`fs.readFile(a, (e1, d1) => ...)` — nesting per step, error branches duplicated, unhandled errors silent) replaced by a *value* representing eventual completion: states machine-checked by the runtime (settled-once enforcement), values typed by the generic (`.then` chains carrying `T` through transforms). Promises made asynchrony composable (combinators per 2.1) instead of nested.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), treat `Promise<T>` as "eventual `T` or throw" (the only mental model that survives composition); never branch on imagined "states" in types (states unrepresentable — narrow via `await`/`then`, not via state unions). Prefer `async`/`await` syntax over raw `.then` chains (readability — same mechanics, linear spelling).

**Runnable example** — eventual values, not state unions (good vs bad, `tsc --strict`):

```typescript
// good — Promise as eventual-T (states handled by await, values typed by the generic)
export {}; // module marker (top-level await below needs module scope)
function fetchName(id: string): Promise<string> {
  return Promise.resolve(`user:${id}`); // eventual string (pending now, string later — one type both times)
}
console.log(await fetchName("u1")); // user:u1 — await discharging eventuality (T out, Promise gone)
// bad — state-union modeling (type Pending | Fulfilled<T> | Rejected hand-rolled — states the runtime already enforces, re-typed badly)
// fix — Promise<T> natively (states runtime-owned, values checker-owned — each layer doing its job)
```

```typescript
// good — chains carrying types through transforms (each then mapping T forward)
export {}; // module marker (consistent module scope across fences)
async function userAge(id: string): Promise<number> {
  const row = await Promise.resolve({ id, age: 30 }); // T inferred (object — generic flowing)
  return row.age; // number (transform narrows the eventual value — chains typed end-to-end)
}
console.log(await userAge("u1")); // 30 — transforms typed (each step's T explicit in hovers, verified by noEmit)
// bad — any-threaded chains (.then((x: any) => ...) — each step unchecking the last, drift compounding per link)
// fix — inferred generics per link (hover each then — T visible, drift red immediately)
```

**Common confusion** — "`Promise<T>` tells you the state" — it tells you the *fulfillment* type (states invisible — `await` on settled values works identically; pending-ness unobservable statically). "pending promises need different handling" — `await`/combinators handle all states uniformly (branching on states is runtime introspection most code never needs). "rejection reasons are typed" — reasons are `any` by default (executor legacy — contained per part 3, tested per 17/2.3).

**Performance note** — promise allocation per async op is one object + microtask hops (nanoseconds-to-microseconds — the price of composability); `await` on non-promises costs nothing extra (wrapping optimized — no allocation in modern engines for settled values).

**Mentor note** — the one-sentence test: "a `Promise<T>` is an eventual `T` or a throw" (candidates adding states to the sentence overcomplicate; candidates dropping the throw forget rejections).

### 2) **`then`/`catch`/`finally` signatures** (continuation typing per method)

**Definition** — the three continuations, typed: `then<U>(onF: (v: T) => U | Promise<U>): Promise<U>` — wait, precisely: `then<TResult1 = T, TResult2 = never>(onfulfilled?: ((value: T) => TResult1 | PromiseLike<TResult1>) | null, onrejected?: ((reason: any) => TResult2 | PromiseLike<TResult2>) | null): Promise<TResult1 | TResult2>` (fulfilled/rejected branches merging into one union promise); `catch<U>(onR: (reason: any) => U | Promise<U>): Promise<T | U>` (recovery widening the union); `finally(onF: () => void): Promise<T>` (observation preserving the type exactly).

**What problem it solves / history** — untyped chaining (jQuery-era deferreds — each link `any`, errors vanishing between links) vs precisely-typed continuations (each branch's contribution visible in the resulting union — recovery paths widening honestly, observations preserving exactly). The signatures encode the whole error-handling algebra (throw vs recover vs observe — 15's discipline at async scale).

**Modern guidance** — prefer `try`/`catch`/`finally` syntax (linear, reviewable); reach for raw `.then/.catch/.finally` only for combinator-adjacent plumbing (conditional chaining, lazy attachment). Read the resulting union after each `catch` (recovery widening — the union tells you which failures remain possible).

**Runnable example** — continuations shaping unions (good vs bad, `tsc --strict`):

```typescript
// good — catch widening the union honestly (recovery visible in the type)
export {}; // module marker (consistent module scope across fences)
async function load(id: string): Promise<string> { throw new Error(`missing:${id}`); }
const recovered: Promise<string> = load("x").catch(() => "fallback"); // Promise<string> (rejection recovered — union honest)
console.log(await recovered); // fallback — recovery typed (catch contributing its branch to the union)
// bad — catch swallowing to any (onrejected returning any — union polluted, downstream checks vacuous)
// fix — typed recovery values (catch returns matching T — unions staying honest per branch)
```

```typescript
// good — finally preserving exactly (observation without type contribution)
export {}; // module marker (consistent module scope across fences)
let closed = false;
async function use(): Promise<number> { return 1; }
const v: Promise<number> = use().finally(() => { closed = true; }); // Promise<number> (finally contributes nothing — preservation by signature)
console.log(await v, closed); // 1 true — observation typed (cleanup runs, type untouched — the finally contract)
// bad — cleanup inside then (cleanup returning values — accidental union widening per observation)
// fix — finally for observation (side channels typed as side channels — values flowing only through then/catch)
```

**Common confusion** — "`catch` narrows" — `catch` *widens* (recovery adding its branch — `Promise<T|U>`; narrowing happens at `await` + control flow, see 07). "`finally` can transform" — `finally` preserves (returned values ignored by signature — transforms belong in `then`). "chaining order doesn't matter" — order decides unions (catch-then vs then-catch — recovery scope differing per position; read the chain as nested unions).

**Performance note** — each `.then` allocates one promise + schedules microtasks (linear in chain length — chains of dozens fine, chains of thousands chunked via async iteration per 3.2); `finally` adds one hop (negligible).

**Mentor note** — whiteboard the three signatures from the union perspective (then-maps, catch-widens, finally-preserves — one verb each; candidates reciting parameter lists miss the algebra).

### 3) **Executor typing** (resolve-typed, reject-any legacy and containment)

**Definition** — `new Promise<T>((resolve: (v: T | PromiseLike<T>) => void, reject: (reason?: any) => void) => void)` — `resolve` enforces `T` (wrong values error at construction); `reject` accepts `any` (historical — pre-`unknown` stdlib, frozen for compatibility). Containment: wrap executors so rejections are always `Error` instances (team rule — `reject(new XError(...))`, never `reject("string")` or `reject(42)`).

**What problem it solves / history** — string/number rejections (`reject("boom")` — catch blocks receiving untyped primitives, `instanceof` narrowing impossible, 15/2.2 hierarchies unusable): the `any`-typed `reject` parameter permits every misuse silently. Team-level containment (Error-only rejections + 17/2.3 class-pinned tests) restores narrowability without changing stdlib.

**Modern guidance** — resolve with exact `T` (construction-checked — the generic working for you); reject with `Error` subclasses only (lint via `only-throw-error`-adjacent review — 16/2.1 tiers; class-pinned rejection tests per 17/2.3). Prefer `async` executors over `new Promise` where possible (wrapping automatic — fewer executor bugs by construction).

**Runnable example** — typed construction, contained rejections (good vs bad, `tsc --strict`):

```typescript
// good — resolve checked at construction (wrong values red HERE, not at consumers)
export {}; // module marker (consistent module scope across fences)
const p: Promise<number> = new Promise<number>((resolve) => resolve(42)); // T enforced (resolve("x") errors — construction-time check)
// const bad = new Promise<number>((resolve) => resolve("x")); // ❌ errors when uncommented (string not assignable to number)
console.log(await p); // 42 — construction typing (producers checked where they produce)
// bad — resolve-any executors (new Promise((resolve) => ...) unannotated — T inferred never/unknown, consumers guessing)
// fix — explicit <T> on every new Promise (producers declaring — inference starts from the declaration)
```

```typescript
// good — Error-only rejections (narrowable catches — 15/2.2 hierarchies usable)
export {}; // module marker (consistent module scope across fences)
class LoadError extends Error { constructor(id: string) { super(`load:${id}`); this.name = "LoadError"; } }
const q: Promise<string> = new Promise<string>((_, reject) => reject(new LoadError("u9"))); // Error instance (narrowable downstream)
const outcome = await q.catch((e) => e instanceof LoadError ? `retry:${e.message}` : "unknown"); // class-narrowed (containment paying off)
console.log(outcome); // retry:load:u9 — rejections as values (typed by class — the 15 discipline at async scale)
// bad — reject("u9-missing") (string rejection — instanceof impossible, catch blocks string-matching like 2012)
// fix — Error subclasses only (team rule + class-pinned tests — rejections narrowable everywhere)
```

**Common confusion** — "`reject` typing will be fixed to `unknown`" — frozen as `any` (lib compatibility — changing breaks every `.catch` in existence; containment is team policy, not stdlib evolution). "executors run synchronously" — executors run *immediately* (synchronous until first await — throws inside executors auto-reject, a feature for construction errors). "avoid `new Promise` entirely" — wrapping callback APIs *requires* executors (the promisification seam — own it with `<T>` + Error-only rules).

**Performance note** — executor invocation is one synchronous call (construction cost trivial); promisification adds one promise per callback op (unavoidable, negligible — the seam's price).

**Mentor note** — review rule: every `new Promise` needs explicit `<T>` (unannotated executors rejected in review — inference-from-resolve is backwards); every `reject(` needs an `Error` (string-rejects rejected harder).
