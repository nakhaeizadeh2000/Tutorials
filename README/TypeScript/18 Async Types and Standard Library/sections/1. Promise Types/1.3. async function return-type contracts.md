## 1.3. async function return-type contracts

An async function returns a promise. Its body can return a value or another promise-like result, and resolution adopts the eventual outcome. A throw from the async body rejects its returned promise. The fulfillment type, completion ownership and runtime scheduling are related but separate questions.

Use **TypeScript 7.0.2** and **Node.js 20.20.2**, verified 2026-10-17. Save each TypeScript file in a directory without a tsconfig. Compile with `tsc --strict --target es2022 --module nodenext --outDir dist FILE.mts`, then run `node dist/FILE.mjs`. For a commented negative, activate it independently and use noEmit instead of outDir.

### 1) **Observe the returned promise and the error boundary**

The [primary return-annotation guide](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#return-type-annotations) uses Promise<T> for annotated async returns. Under this lesson's ES2022 target, a bare number or a PromiseLike<number> annotation on an async implementation is rejected with TS1064; an omitted annotation can be inferred. Save:

```typescript
// file: returns.mts
const source = Promise.resolve(7);
function direct(): Promise<number> { return source; }
async function adopting(): Promise<number> { return source; }
const adopted = adopting();
if (direct() !== source || adopted === source || await adopted !== 7) throw new Error("promise identity/adoption");
async function readName(id: string): Promise<string> {
  if (id === "") throw new Error("empty id");
  return `user:${id}`;
}
let pending: Promise<string> | undefined;
try { pending = readName(""); }
catch { throw new Error("async body escaped synchronously"); }
if (pending === undefined) throw new Error("missing promise");
const message = await pending.catch((reason: unknown) => {
  if (!(reason instanceof Error)) throw reason;
  return reason.message;
});
if (message !== "empty id" || await readName("u1") !== "user:u1") throw new Error("async outcome");
function argument(): string { throw new Error("argument failure"); }
let caughtArgument = false;
try { void readName(argument()); }
catch (reason: unknown) { caughtArgument = reason instanceof Error && reason.message === "argument failure"; }
if (!caughtArgument) throw new Error("argument boundary");
console.log("direct same; async different; adopted 7; rejected empty id; argument caught");
// async function bare(): number { return 1; } // TS1064.
// async function onlyLike(): PromiseLike<number> { return 1; } // TS1064 at this target.
// async function wrongBody(): Promise<number> { return "x"; } // TS2322.
```

The final output line is printed after all checks succeed. The direct function returns source itself. The async function returns a distinct promise that adopts source's value. That identity difference is a runtime property; both return contracts are Promise<number>.

The async body's error appears as a rejection and is observed through the returned promise. The separate argument expression throws before readName is called, so the surrounding synchronous catch sees it. Saying an async body rejects is not a guarantee that every expression used to obtain or call that function cannot throw synchronously.

### 2) **Choose explicit or inferred returns from the intended contract**

An annotation publishes a chosen boundary and can produce an error when the implementation violates it. Inference can also preserve useful precision. It does not always widen a public async function's literal results to string. Save:

```typescript
// file: inference.mts
export async function single() { return "ok"; }
export async function branch(id: string) { return id === "a" ? "active" : "suspended"; }
export async function annotated(id: string): Promise<"active" | "suspended"> {
  return id === "a" ? "active" : "suspended";
}
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Contracts = [
  Expect<Equal<ReturnType<typeof single>, Promise<string>>>,
  Expect<Equal<ReturnType<typeof branch>, Promise<"active" | "suspended">>>,
  Expect<Equal<Awaited<ReturnType<typeof annotated>>, "active" | "suspended">>
];
if (await single() !== "ok" || await branch("a") !== "active" || await annotated("x") !== "suspended") {
  throw new Error("inferred/annotated results");
}
console.log("ok active suspended");
```

The three type gates pass and runtime prints `ok active suspended`. To inspect the actual published declarations, run `tsc --strict --target es2022 --module nodenext --declaration --emitDeclarationOnly --outDir declarations inference.mts`. Single declares Promise<string>, while branch and annotated both declare Promise<"active" | "suspended">. The annotation was not required to obtain branch's shown union.

Change annotated's suspended branch to "unknown". The implementation fails with TS2322 against its chosen return contract. Restore it. Adding a new literal branch to an inferred function can instead change its published return type without that implementation error; a relevant consumer or type regression test can expose the change. Choose annotations for a stable intended boundary, clarity or inference requirements, and inference when its resulting API is intentional. No universal export annotation/probe quota follows from these examples.

The [callable return owner](<../../../05 Functions and Callable Types/sections/1. Function Type Fundamentals/1.3. Return types void never and contextual inference.md>) owns the underlying widening and contextual typing rules. [Awaited](<./1.2. Awaited recursive unwrapping and thenables.md>) distinguishes the declared wrapper from the consumed value and demonstrates a misleading nested annotation.

### 3) **Keep completion separate from void, undefined and never**

Promise<void> describes completion without a useful fulfillment value in that view. It does not mean fire-and-forget: a caller can still await completion and observe rejection. Promise<undefined> promises that particular fulfillment value. Promise<never> has no normal fulfillment value, but it can reject or remain pending; it does not promise which or how soon.

```typescript
// file: payloads.mts
const events: string[] = [];
async function notify(): Promise<void> { await Promise.resolve(); events.push("notified"); }
async function absent(): Promise<undefined> { return undefined; }
async function failOnly(): Promise<never> { throw new Error("stopped"); }
const completion: () => Promise<void> = notify;
await completion();
if (events.join(",") !== "notified") throw new Error("completion not owned");
const canIgnore: Promise<void> = absent();
await canIgnore;
if (await absent() !== undefined) throw new Error("undefined result");
const failure = await failOnly().catch((reason: unknown) => {
  if (!(reason instanceof Error)) throw reason;
  return reason.message;
});
if (failure !== "stopped") throw new Error("never rejection");
console.log("notified; undefined; stopped");
// const wrongCallback: () => Promise<void> = async () => 42; // TS2322.
// const exactAbsent: Promise<undefined> = notify(); // TS2322.
// async function badVoid(): Promise<void> { return 42; } // TS2322.
// async function badNever(): Promise<never> { return; } // TS2322.
```

It prints `notified; undefined; stopped`. Promise<undefined> fits the void completion view, but the reverse does not establish an exact undefined payload. Unlike the special permission to ignore an entire () => void callback return, a Promise<number> result does not satisfy Promise<void>. The canonical callable owner demonstrates the separate hazard that a void callback host can accept an async callback and ignore its returned promise.

A pending promise also does not by itself keep Node running. Save this separate JavaScript file and run `node pending.mjs`:

```javascript
// file: pending.mjs
const pending = new Promise(() => {});
pending.then(() => { throw new Error("unexpected fulfillment"); });
console.log("pending promise created; no active operation");
```

It prints the line and the process exits successfully. This script does not await an unsettled top-level promise; that is another execution condition. Node's [process documentation](https://nodejs.org/download/release/v20.20.2/docs/api/process.html#event-beforeexit) explains its no-work exit boundary. Use real resource ownership and shutdown handling, not a Promise<never> annotation, to describe process lifetime. A timeout race also needs cleanup of any losing timer or operation, as the [actual async cleanup tests](<../../../17 Testing Types/sections/2. Typed Test Doubles/2.3. Testing async and error paths with types.md>) demonstrate.

### 4) **Common confusion**

An async return annotation constrains the static contract; it does not add validation, prevent unchecked assertions or make the operation terminate. Inferred return types can be precise, and an explicitly broad annotation can deliberately expose a broader view than the current body. Inspect the actual declaration and consumer need.

Void and never describe different fulfillment contracts, not different levels of detachment. Both promise types can reject, and both require a completion/error policy when work is started. A pending promise with no active resource is not a process-lifetime mechanism.

### 5) **Performance note**

Async calls, adoption and awaiting perform runtime work. Return annotations and type gates erase. This fixture checks identity, outcomes, declarations and process exit; it measures no allocation count, fixed extra hop or microsecond overhead. Choose direct returns or async composition from semantics and readability, then measure a relevant hot path if its cost matters.

### 6) **Mentor note**

Ask why direct and adopting share a type but differ in identity, why branch infers a union and why Promise<never> can reject promptly. Then compare a void callback host with a promise-aware completion contract. A strong answer explains what the caller may use, who waits, who handles failure and which resource keeps an operation alive.
