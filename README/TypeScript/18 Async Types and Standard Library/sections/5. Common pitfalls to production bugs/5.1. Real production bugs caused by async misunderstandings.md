## 5.1. Real production bugs caused by async misunderstandings

The title names the kinds of failures this page teaches. The cases below are **synthetic reproductions**, not accounts of a named production outage. They show lost completion ownership, premature cancellation, mistaken timer diagnosis and assumptions about rejection values. The original page's incident durations, socket counts and billing claims were not supported by evidence.

Use **Node.js 20.20.2**, verified 2026-10-17, for the complete verify.mjs fixture below. It uses Node's assertion library and an actual local HTTP server; it needs no installed dependencies. The linked TypeScript owners declare their compiler and package versions. The local server is closed in finally, including open connections.

### 1) **Starting a batch without returning its completion**

Promise.all can aggregate work already started by map. Discarding its returned promise does not turn those operations into a sequential batch. It loses a completion or failure observation unless another owner retains it. Returning that promise, awaiting it, or explicitly handing it to a supervisor can all be valid ownership choices; launch and join need not be adjacent text.

In the fixture, detached schedules one reaction and returns accepted before its gate is released. This is observable with one operation: a large load test is not necessary to detect the missing completion contract. After release, the operation still finishes. The second function returns its aggregate promise, letting its caller observe completion.

Ordinary TypeScript checking permits many discarded promises. The [actual typed-lint fixture](<../../../16 Tooling Language Server and Ecosystem/sections/2. Lint Format and Checks/2.1. typescript-eslint rules and type-aware linting.md>) separately executes no-floating-promises and shows that default void handling can silence that rule without handling a rejection. The [bounded mapper](<../2. Combinators and Cancellation/2.3. Sequential vs parallel patterns and tuple typing.md>) owns validated limits, ordered results and failure draining; do not replace it with a pool that quietly accepts zero or fractional concurrency.

### 2) **Cancelling a winning response before its body is consumed**

Fetch can fulfill with a Response after headers arrive while its body is still being read. If a race returns that Response and immediately aborts the shared signal in finally, the winning request's unread body is also affected. The controller does not know which contender the application calls a winner. The [original abortable-fetch explanation](https://developer.chrome.com/blog/abortable-fetch) explicitly distinguishes aborting the request from aborting body consumption.

The first HTTP case sends only a partial body. The response wins a race against a never-settling promise; aborting its controller then makes response.text reject. It demonstrates the cleanup mistake without assuming a socket count or remote rollback.

In the repaired text-race contract, each contender consumes its body before fulfilling. Only after one complete string wins does finally abort the remaining fetch. The server deliberately waits until both requests arrive before completing the winner, so the test observes an actual in-flight loser. All race inputs have rejection reactions attached by the combinator. The application still needs a policy for cancellation cooperation, diagnostics, caller deadlines and any independent work.

Save and run `node verify.mjs`:

```javascript
// file: verify.mjs
import assert from "node:assert/strict";
import { createServer } from "node:http";
function deferred() {
  let resolve;
  const promise = new Promise(done => { resolve = done; });
  return { promise, resolve };
}
const workLog = [];
const gate = deferred();
function detached() {
  void Promise.all([gate.promise.then(() => workLog.push("done"))]);
  return "accepted";
}
assert.equal(detached(), "accepted");
assert.deepEqual(workLog, []);
gate.resolve();
await new Promise(resolve => setTimeout(resolve, 0));
assert.deepEqual(workLog, ["done"]);
const joinedGate = deferred();
function joined() { return Promise.all([joinedGate.promise.then(() => "finished")]); }
const completion = joined();
joinedGate.resolve();
assert.deepEqual(await completion, ["finished"]);

const seen = new Set();
let winnerResponse;
function finishWinner() {
  if (winnerResponse && seen.has("/slow")) winnerResponse.end("complete body");
}
const server = createServer((request, response) => {
  seen.add(request.url);
  if (request.url === "/headers") {
    response.writeHead(200, { "Content-Type": "text/plain" });
    response.write("partial"); // Headers and a partial body, deliberately no end.
  } else if (request.url === "/winner") {
    winnerResponse = response;
    finishWinner();
  } else if (request.url === "/slow") {
    response.writeHead(200, { "Content-Type": "text/plain" });
    response.write("pending");
    finishWinner();
  } else { response.writeHead(404); response.end(); }
});
await new Promise((resolve, reject) => {
  server.once("error", reject);
  server.listen(0, "127.0.0.1", resolve);
});
const address = server.address();
assert.ok(address && typeof address === "object");
const base = `http://127.0.0.1:${address.port}`;
try {
  const premature = new AbortController();
  async function responseRace() {
    try {
      return await Promise.race([
        fetch(base + "/headers", { signal: premature.signal }),
        new Promise(() => {}),
      ]);
    } finally { premature.abort(); }
  }
  const response = await responseRace();
  await assert.rejects(() => response.text(), { name: "AbortError" });
  const controller = new AbortController();
  async function readText(path) {
    const candidate = await fetch(base + path, { signal: controller.signal });
    if (!candidate.ok) throw new Error("HTTP " + candidate.status);
    return await candidate.text(); // Body completion belongs to this contender.
  }
  let text;
  try { text = await Promise.race([readText("/winner"), readText("/slow")]); }
  finally { controller.abort(); }
  assert.equal(text, "complete body");
  assert.equal(seen.has("/winner"), true);
  assert.equal(seen.has("/slow"), true);
  assert.equal(controller.signal.aborted, true);
} finally {
  await new Promise((resolve, reject) => {
    server.close(error => error ? reject(error) : resolve());
    server.closeAllConnections();
  });
}

class RetryableError extends Error {
  constructor() { super("temporary"); this.kind = "temporary"; this.code = 503; }
}
const local = new RetryableError();
const received = JSON.parse(JSON.stringify(local)); // Simulated serialization boundary.
assert.equal(local instanceof RetryableError, true);
assert.equal(received instanceof RetryableError, false);
function isTemporary(value) {
  return typeof value === "object" && value !== null &&
    value.kind === "temporary" && value.code === 503;
}
assert.equal(isTemporary(received), true);
assert.equal(isTemporary({ kind: "temporary", code: "503" }), false);
assert.equal(isTemporary(null), false);
let reason;
try { await Promise.reject(17); } catch (error) { reason = error; }
assert.equal(reason, 17);
console.log("completion ownership, response-body cancellation and reason boundaries passed");
```

The final message means the assertions passed. As a finite deliberate failure, change the expected AbortError name to a wrong name and observe the assertion fail. Restore it afterward. Removing cancellation instead would leave the partial-body read waiting on an endpoint that deliberately never finishes; the cleanup policy matters independently of the result type.

For the repaired path, replace return await candidate.text() with return candidate. It still runs as JavaScript, but the complete-string assertion fails. Finishing the body is part of this text API's contract. A streaming-response API needs a different ownership design: keep the winner's signal alive while the caller reads, and cancel losers through separate controllers or another policy that preserves the winner's remaining work.

### 3) **Mistaking a type annotation for a broken timer handle**

A DOM number annotation does not convert the value returned by Node setTimeout. Passing that original object to Node clearTimeout still works. A cast cannot explain a runtime cancellation failure by itself. The [timer fixture](<../3. Standard Library in Practice/3.3. Timers queues and the event-loop type view.md>) compiles the deliberate mismatch, observes the object, verifies cancellation, and detects a mutation that removes the clear call.

Diagnose the actual timer identity, the lifecycle path that calls clear, repeated scheduling and captured state. A stop callback can make ownership convenient, but a closure is real runtime code rather than an erased type. Unref permits Node to exit; it neither cancels an interval nor replaces cleanup while the process stays alive. The same owner executes child processes to make that distinction observable.

### 4) **Assuming a rejection is an instance of a local class**

Promise<T> does not type its rejection reason. Throwing an Error subclass within one process may support instanceof-based handling there. Serializing it across a service boundary does not preserve that local prototype. The fixture's simulated JSON boundary turns a local RetryableError into a plain object, then validates a deliberately small wire contract. This validation is classification, not authorization or evidence that retrying an effect is safe.

The fixture also observes an accepted primitive rejection. An application's own API can normalize reasons into Error objects for useful stack and cause information, or use a validated Result/wire schema. External input still requires validation. A string name or unvalidated code is not a reliable class or retry policy. Decide retry safety from the operation's effects, limits and contract; this example does not execute a retry or prove an outage would be bounded.

### 5) **Common confusion**

Losing a join loses an observation; it does not automatically serialize starts. A race winner can still own unfinished resource work. A fulfilled Response is the concrete example: headers have arrived, but the body may remain active.

A runtime class check and a wire-data check solve different problems. Neither a Promise annotation nor a passed class assertion proves every future failure has the same representation. The [actual rejection tests](<../../../17 Testing Types/sections/2. Typed Test Doubles/2.3. Testing async and error paths with types.md>) distinguish fulfilled types from observed rejection behavior.

### 6) **Performance note**

These cases expose ownership failures without assigning fabricated incident costs. Unbounded starts, unconsumed bodies and recurring timers can retain resources, but their cost depends on actual operation behavior and load. The fixture uses a small local server and no throughput measurement. Correct cleanup and capacity limits need their own evidence; the presence of an aggregate or controller does not supply it.

### 7) **Mentor note**

Ask what each function promises has finished when it returns. Then stop the explanation at Response and ask whether the body has finished too. A sound review traces remaining work after the selected outcome and chooses who owns it. For timer and error reports, request the actual emitted value and boundary representation before accepting a diagnosis based only on a type name.
