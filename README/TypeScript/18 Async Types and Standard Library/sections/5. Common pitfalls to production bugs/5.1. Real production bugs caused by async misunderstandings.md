## 5.1. Real production bugs caused by async misunderstandings

### 1) **Unawaited `Promise.all` in a loop serialized 10k requests** (float disguised as batching, p99 incident)

**Definition** — the incident: a sync job mapped 10k URLs to fetch promises inside a `for` loop with `await Promise.all(batch)` — except the `await` sat *inside* a callback that never returned the promise (float per 17/2.3 — batches launched, never joined). Latency summed anyway (loop outpacing joins — 10k floats racing, memory spiking), p99 breaching SLO for 4 hours before the missing `return` was spotted in review of the incident diff.

**What problem it solves / history** — launch-without-join (mapping without awaiting the `all` — parallel start, serial-or-never consumption per 2.3 part 2's for-await warning): the batch *looked* batched (Promise.all present) while behaving serially (join missing). `no-floating-promises` (17/2.3 part 2) would have errored at authoring (unjoined `all` is a float — lint catching what review missed).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), `await` every `Promise.all` at the mapping site (launch AND join adjacent — never separated); enable `no-floating-promises` on all async code (floats as compile errors — the rule that prevents this exact incident); load-test batch jobs at 10× expected N (join-missing degrading visibly under load, invisibly in unit tests).

**Runnable example** — joined vs floated batches (good vs bad, `tsc --strict`):

```typescript
// good — launch joined at the site (map-then-all adjacent — batching real)
export {}; // module marker (top-level await below needs module scope)
async function fetchOne(n: number): Promise<number> { return n * 2; }
const ids = [1, 2, 3];
const doubled: number[] = await Promise.all(ids.map(fetchOne)); // joined HERE (launch + join adjacent — latency maxed, never summed)
console.log(doubled.join(",")); // 2,4,6 — batches joined (the await present — floats unrepresentable beside the map)
// bad — mapped batches never joined (Promise.all(...) floating — launched parallel, consumed never: latency summed + memory spiking)
// fix — await at the mapping site (launch/join adjacency — reviewable in one glance, lint-enforced by no-floating-promises)
```

```typescript
// good — pool-bounded large fan-out (10k URLs at K=20 — throughput without collapse per 2.3 part 3)
export {}; // module marker (consistent module scope across fences)
async function fetchUrl(u: string): Promise<string> { return `body:${u}`; }
async function bounded(urls: string[], k: number): Promise<string[]> {
  const out: string[] = new Array(urls.length);
  let next = 0;
  async function lane(): Promise<void> {
    while (next < urls.length) { const i = next++; out[i] = await fetchUrl(urls[i]); } // K lanes (flight bounded — designed limit)
  }
  await Promise.all(Array.from({ length: Math.min(k, urls.length) }, lane)); // joined (lanes awaited — floats structurally absent)
  return out;
}
console.log((await bounded(["a", "b"], 2)).join(",")); // body:a,body:b — bounded joins (scale without collapse — the incident's fix in miniature)
// bad — unbounded unjoined fan-out (10k floats — descriptors exhausted, p99 breached for 4 hours)
// fix — pools + joined alls (bounds designed, joins adjacent — both halves of the incident addressed)
```

**Common confusion** — "`Promise.all` present means batched" — presence without `await`/`return` is decoration (floats launching, never joining — 2.3's launch-vs-join lesson restated as incident). "unit tests catch join-missing" — unit tests at N=3 pass either way (latency invisible — load tests at 10× catching what units cannot). "lint on async is noise" — this incident IS the lint's business case (one rule, four hours of SLO breach prevented).

**Performance note** — joined batches latency = max (200ms for the incident's shape); floated loops latency = sum + memory spikes (33 minutes + OOM pressure at 10k — the incident arithmetic).

**Mentor note** — incident-review exhibit for `no-floating-promises` adoption (the missing `return` in the incident diff — one red line that would have existed).

### 2) **`race` without cleanup leaked every losing socket** (losers un-aborted, connection exhaustion)

**Definition** — the incident: mirror-redundant fetches via `Promise.race([primary, secondary])` (2.1 redundancy pattern) — winners consumed, losers running (sockets held, 40k ESTABLISHED at peak, downstream throttling the account). No abort wiring existed (combinators don't cancel per 2.1 — the team assuming `race` cleans losers). Fix: `AbortController` per race, losers aborted on settle (2.2 mechanics applied — connections back to hundreds).

**What problem it solves / history** — first-wins without loser-cleanup (results consumed, work abandoned — resource accounting ignoring losers): every `race`/`any` needs its cleanup answer (2.1 mentor note restated as incident — "who aborts the losers?" unanswered in review, answered in the postmortem).

**Modern guidance** — abort losers on every `race`/`any` (controller per race — settle handler aborting; 2.2 linked patterns); monitor socket counts per service (ESTABLISHED gauges — leaks visible in metrics before throttling); review-check every combinator for cleanup (no answer, no merge — 2.1 rule enforced).

**Runnable example** — races with cleanup (good vs bad, `tsc --strict`):

```typescript
// good — loser aborted on settle (cleanup wired — resources accounted including losers)
export {}; // module marker (top-level await below needs module scope)
async function primary(signal: AbortSignal): Promise<string> {
  signal.throwIfAborted();
  return "primary-data"; // winner (loser aborted below — settle handler cleaning)
}
async function secondary(signal: AbortSignal): Promise<string> {
  signal.throwIfAborted();
  return "secondary-data";
}
async function raced(): Promise<string> {
  const ctrl = new AbortController(); // per-race controller (lifetimes scoped — settle aborting losers)
  try {
    return await Promise.race([primary(ctrl.signal), secondary(ctrl.signal)]); // first wins (losers still running HERE — cleanup next line)
  } finally {
    ctrl.abort(); // losers aborted (settle cleanup — connections released win-or-lose)
  }
}
console.log(await raced()); // primary-data — races cleaned (40k-sockets class structurally prevented)
// bad — bare races (losers running — sockets held per race, exhaustion at volume)
// fix — per-race controllers + finally-abort (cleanup wired — settle means abort-losers, always)
```

**Common confusion** — "winners imply cleanup" — combinators settle (results delivered); cleanup is *caller-owned* (abort wiring — the ownership split 2.1 states and this incident prices). "losers finish quickly anyway" — losers hang longest (slow mirrors losing races — the slow tail holding resources exactly when load peaks). "abort-on-settle races the winner" — aborting after settle affects only losers (winner already resolved — `finally` ordering safe by construction).

**Performance note** — per-race controllers one object + listeners (microseconds — trivial vs held sockets at 40k); uncleaned races cost descriptors + downstream throttling (exhaustion economics — cleanup always cheaper).

**Mentor note** — combinator review ritual: "who aborts the losers?" (every `race`/`any` answering — the question preventing this incident class outright).

**Cross-links** — race cleanup → [2.1. Combinators](<../2. Combinators and Cancellation/2.1. all race allSettled any typed precisely.md>); signal trees → [2.2. AbortSignal](<../2. Combinators and Cancellation/2.2. AbortSignal propagation and cancellation contracts.md>).

### 3) **DOM-typed timer handle shipped to Node cleared nothing** (number vs Timeout, interval leak)

**Definition** — the incident: a shared utils package typed `setTimeout` via `DOM` lib (`number` handles) consumed by a Node service (`Timeout` handles with `.unref()`/object identity): `clearTimeout(handle as unknown as number)` no-op-ing (handle mismatch — clear silently failing), a 30s polling interval surviving shutdown for 6 weeks (metrics double-emitting, bills doubling on the polled API). Fix: environment-scoped timer modules per 3.3 part 1 (handles opaque, `delay()` wrappers per runtime).

**What problem it solves / history** — cross-runtime handle leaks (duality per 3.3 part 1 un-contained — raw handles crossing module boundaries, clears no-op-ing silently): encapsulation containing the duality once (wrappers per environment — callers never touching handles, clears always matching).

**Modern guidance** — timer utilities per runtime (Node package: `@types/node`, `Timeout`; browser package: `DOM`, `number` — never shared raw); `delay()`-style wrappers (handles encapsulated — 3.3 part 1 pattern); shutdown tests asserting timer release (17/2.3 doubles driving SIGTERM — intervals verifiably cleared).

**Runnable example** — handles matching (good vs bad, `tsc --strict`):

```typescript
// good — encapsulated polling (handles hidden — clears matching by construction)
export {}; // module marker (top-level await below needs module scope)
function startPolling(tick: () => void, ms: number): () => void {
  const h = setInterval(tick, ms); // handle local (same-environment clear — match guaranteed structurally)
  return () => clearInterval(h); // matched clear (stop function closing over its own handle — mismatch unrepresentable)
}
let ticks = 0;
const stop = startPolling(() => { ticks++; }, 10); // polling started (handle encapsulated — callers stopping, never clearing)
stop(); // cleared (matched pair — 6-week-leak class structurally prevented)
console.log(ticks >= 0 ? "poll-managed" : "bad"); // poll-managed — clears matching (encapsulation guaranteeing what casts cannot)
// bad — cross-runtime handle casts (as unknown as number — clears no-op-ing, intervals leaking for 6 weeks)
// fix — per-runtime timer modules (handles opaque — clears matched by construction, never by casting)
```

**Common confusion** — "clear functions are universal" — clears match *same-environment* handles (cross handles no-op-ing — the incident's mechanism). "shared timer utils save code" — shared *wrappers* save code (delay/poll per runtime — shared *handles* leak it). "interval leaks are minor" — 6-week double-emit doubling polled-API bills (leaks compounding financially, not just technically).

**Performance note** — encapsulation zero-cost (closures, erased — 01/2.1); leaked intervals cost polls × weeks (billing + load — the most expensive timer bug class).

**Mentor note** — cross-runtime timer review: raw handles outside timer utilities are duality leaks (wrap-or-justify — 3.3 rule enforced as incident response).

### 4) **`any`-typed reject swallowed error classes across service boundaries** (wrong-class handling, outage extended)

**Definition** — the incident: a gateway `catch` narrowing `e instanceof RetryableError` — except the upstream rejected with a plain object (`reject({ code: 503 })` — non-Error rejection, `reject: any` permitting): `instanceof` false, error routed to fatal (no retry), a 20-minute partial outage becoming a 3-hour full one (retries structurally disabled by untyped rejections).

**What problem it solves / history** — `reject(anything)` (executor legacy per 1.1 — rejections unshaped, handlers guessing): Error-only rejection rules (1.1 part 3 — `reject(new XError(...))`, class-pinned tests per 17/2.3) restoring narrowability across boundaries (handlers routing by class — retries firing where designed).

**Modern guidance** — Error-only rejections (team rule — 1.1 containment; review-rejected string/object rejects); `instanceof` + name routing in catches (2.2 part 2 — aborts quiet, failures retried, unknown rethrown); class-pinned rejection tests per boundary (17/2.3 — wrong-class handling red at authoring).

**Runnable example** — rejections shaped (good vs bad, `tsc --strict`):

```typescript
// good — Error-class rejections routing retries (narrowable catches — outages bounded by design)
export {}; // module marker (top-level await below needs module scope)
class RetryableError extends Error { constructor(msg: string) { super(msg); this.name = "RetryableError"; } }
async function upstream(fail: boolean): Promise<string> {
  if (fail) throw new RetryableError("downstream:503"); // Error instance (narrowable — handlers routing by class)
  return "ok";
}
async function gateway(fail: boolean): Promise<string> {
  try { return await upstream(fail); }
  catch (e) {
    if (e instanceof RetryableError) return "retried-later"; // retry path (class-routed — 20-minute partial, not 3-hour full)
    throw e; // unknown rethrown (unshaped rejections never swallowed — routing honest)
  }
}
console.log(await gateway(true)); // retried-later — class routing (retries firing where designed — outage bounded)
// bad — object rejections (reject({code:503}) — instanceof false, retry path dead, partials becoming fulls)
// fix — Error-only rejects + class pins (boundaries shaped — handlers routing, retries firing)
```

**Common confusion** — "rejection shapes are internal" — rejections cross boundaries (services, layers — shapes contractual, tested per 17/2.3). "unknown-rethrow loses context" — rethrow preserves (stack + cause per 15/2.2 — swallowing loses, rethrowing carries). "retry-all is safer" — retry-all retries fatals + aborts (storms — routing precise: retryables retried, rest rethrown).

**Performance note** — Error allocation per rejection (rare path — exceptions exceptional; hot-path failures modeled as `Result` per 15/2.1, not throws).

**Mentor note** — boundary review: "reject shapes?" (Error subclasses listed — object/string rejects blocked like `any` — same severity).
