## 4.1. Async checklist — mental models mentors insist on

Review an async API by following its values, starts, failures and resource ownership. Types can describe the accepted inputs and fulfilled outputs, but many important promises concern execution. The worked owners linked below use TypeScript 7.0.2 and declared Node runtimes to test those boundaries. This page synthesizes their evidence; it introduces no new executable fixture or benchmark.

### 1) **Choose the contract and the evidence that tests it**

Promise<T> describes a fulfilled value, not a rejection class or settlement guarantee. Awaited<T> describes the type consumed by await, not a runtime operation that inspects every field in an object. Wrapped and consumed types can both be useful public contracts; select a test for the promise the API makes rather than demanding an Awaited assertion on every export.

| Review question | Evidence to inspect | What it does not establish |
|---|---|---|
| Which value does the caller await? | [Actual return inference and chosen annotations](<../1. Promise Types/1.3. async function return-type contracts.md>) | That the operation fulfills or rejects with a particular class |
| Is a foreign thenable adopted honestly? | [Thenable and normalization fixture](<../1. Promise Types/1.2. Awaited recursive unwrapping and thenables.md>) | That an inaccurate nested annotation changes runtime adoption |
| Are positions preserved? | [Inline tuple versus widened-array gates](<../2. Combinators and Cancellation/2.1. all race allSettled any typed precisely.md>) | That as const is required on every heterogeneous input |
| Who waits for cleanup? | [Controlled finally cleanup](<../1. Promise Types/1.1. Promise states and the Promise type anatomy.md>) | That cleanup cannot reject or start unrelated work |

The combinator fixture infers a tuple for its inline heterogeneous Promise.all input without as const. Passing a previously widened array has a different contract. Explain that difference before adding an annotation. Type-test helpers should be selected compile-only declarations or real tool APIs; declaring an ambient function and then calling it does not erase the call. The [type-assertion owner](<../../../17 Testing Types/sections/1. Type Assertions in Tests/1.1. Expect Equal and compile-time type assertions.md>) demonstrates the resulting runtime failure.

### 2) **Follow cancellation to the operation that must cooperate**

Adding a signal parameter only creates a place to receive a cancellation request. The operation must check the signal, subscribe where necessary, or forward it to an API that acts on it. A pre-entry check alone does not cancel I/O started later. The [actual fetch fixture](<../2. Combinators and Cancellation/2.2. AbortSignal propagation and cancellation contracts.md>) observes both pre-abort and in-flight abort through a loader to a local HTTP request.

Abort reasons may be arbitrary values. Bare abort is valid and supplies the default reason; it does not lose all causality. Classify cancellation and failures according to the operation's contract instead of making every abort quiet or retrying every rejection. A required signal can be appropriate when callers must participate in a lifecycle; an optional signal can be appropriate when uncancelled calls are supported. An options object may express that policy more clearly than an unqualified last-parameter rule.

Signals standardize state, events and reasons. A private flag may still be useful for local state or cooperative computation. Neither a flag nor a signal makes races impossible, and neither undoes already completed effects. Test the consequence that matters: the request stops, a timer is cleared, a listener is removed, or new work is no longer admitted. The [actual async tests](<../../../17 Testing Types/sections/2. Typed Test Doubles/2.3. Testing async and error paths with types.md>) verify a complete cancellable-wait lifecycle.

### 3) **Choose starts and failure ownership deliberately**

First establish dependencies, ordering constraints and the capacity of downstream systems. Sequential work can be necessary; overlapping independent operations can reduce idle waiting; bounded admission can protect a scarce resource. Independence should be established rather than assumed. Even independent operations can share a quota, connection limit or CPU bottleneck.

The [bounded scheduling owner](<../2. Combinators and Cancellation/2.3. Sequential vs parallel patterns and tuple typing.md>) separately tests sequential starts, input-ordered consumption of already-started promises, and capped active callbacks. Its failure policy stops new admissions after the first observed failure, drains callbacks already started, and then rejects. This choice has a real limitation: a callback that never settles can prevent the drain from finishing.

Promise.all does not itself start callbacks, cancel siblings or roll back effects. Race selects an outcome without releasing losing resources. AllSettled records member failures but still needs its input iteration and every member to settle. Choose those behaviors from the application's needs and assign an owner to any remaining work. A comment explaining sequential dependence helps reviewers; it does not itself suppress a lint rule or enforce a capacity limit.

### 4) **Check declarations, runtime APIs and cleanup separately**

The [library fixture](<../3. Standard Library in Practice/3.1. lib settings and built-in async types.md>) makes browser-only document compile and then fail in Node. It also transforms async iteration for an ES2015 target. These observations show why adding lib declarations, transforming syntax and providing an API implementation are separate decisions. Missing names call for diagnosis of the actual project and host, not automatically maximal libraries or a code rewrite.

The same fixture tests using on early return and throw, plus await using waiting for a cleanup gate. It also shows that registering no resource still type-checks. Cleanup can fail or be incomplete; emitted helpers do not install all native constructors. Review acquisition, ownership, disposal implementation and escaped references rather than treating two keywords as a leak-proof architecture.

The [timer fixture](<../3. Standard Library in Practice/3.3. Timers queues and the event-loop type view.md>) demonstrates Node handle identity despite a DOM-only number annotation, actual ref/unref child processes and context-specific scheduling order. A timer wrapper can express ownership, but exposing a raw host handle is also legitimate when callers need that lifecycle. Neither a wrapper nor a selected lib establishes portability without matching implementations and tests.

### 5) **Common confusion**

A green static check can coexist with a stuck operation, a wrong runtime API, or an incomplete disposer. A runtime assertion can confirm the tested behavior without proving every type relation. Match the evidence to the claim and state its boundary.

Do not substitute an input-size threshold such as dozens of operations for capacity reasoning. A small batch can overload an expensive dependency; a larger batch can be appropriate under a tested policy. Likewise, a loop's input order says nothing by itself about when operations already held in the input started.

### 6) **Performance note**

Types and annotations do not set actual latency, throughput, buffer sizes or scheduler fairness. Simple max-versus-sum latency formulas omit dependencies, contention, scheduling and failures. Measure the real workload under the chosen admission and cleanup policy. Compiler-library selection affects checking work, but this checklist makes no measured claim about a speedup from reducing declarations.

### 7) **Mentor note**

Use this review exercise: a loader adds signal?: AbortSignal, calls throwIfAborted once, then races an un-signalled fetch against a timeout. Its declared return is Promise<string>. Ask what has been proved and what still needs repair.

The signature describes accepted cancellation input and fulfilled output. It does not propagate later aborts to fetch, release the losing operation, type every rejection, or establish a deadline for remote effects. A sound repair passes the signal to the cooperating operation, defines timeout composition and cleanup, and tests success, pre-abort and in-flight failure. The actual fetch and timer owners provide that evidence separately from the static contract.
