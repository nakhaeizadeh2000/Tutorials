## 2.2. AbortSignal propagation and cancellation contracts

An AbortSignal communicates that a caller no longer wants an operation to continue. An operation must observe it and release the resources it owns. Passing a signal through a function signature is useful only when that function forwards or implements the relevant cancellation behavior. A promise itself has no cancel method.

This lesson uses **TypeScript 7.0.2** and **Node.js 20.20.2**, verified 2026-10-17. It performs real fetch calls against a local HTTP fixture, with no external service. TypeScript's DOM declarations describe the shared fetch/signal API used here; the actual implementation is Node's. [Node's globals reference](https://nodejs.org/download/release/v20.20.2/docs/api/globals.html#class-abortcontroller) documents support in this runtime, including AbortSignal.any added in Node 20.3.0.

### 1) **Forward the signal to the operation that owns the work**

Create these two files in an empty directory without a tsconfig. Compile with `tsc --strict --target es2022 --module nodenext --outDir dist loader.mts`, then run `node verify.mjs`.

```typescript
// file: loader.mts
export async function loadText(url: string, signal: AbortSignal): Promise<string> {
  signal.throwIfAborted();
  const response = await fetch(url, { signal });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const text = await response.text();
  signal.throwIfAborted();
  return text;
}
export async function loadWithDeadline(url: string, signal: AbortSignal, ms: number): Promise<string> {
  const combined = AbortSignal.any([signal, AbortSignal.timeout(ms)]);
  return loadText(url, combined);
}
export function checkPoint(signal: AbortSignal): void {
  signal.throwIfAborted();
  // const guaranteedFalse: false = signal.aborted; // TS2322: its declared type remains boolean.
}
```

The wrapper checks for an already-aborted caller before starting and passes the same signal to fetch. Fetch owns the request and body-consumption implementation. The final check is another observation point before returning; it does not make cancellation impossible immediately afterward or undo a completed effect. [Jake Archibald's original abortable-fetch explanation](https://developer.chrome.com/blog/abortable-fetch) develops forwarding one signal through request/body work and related requests. Its historical browser rollout and default-error-only examples are separate from the tested Node/custom-reason cases below.

```javascript
// file: verify.mjs
import assert from "node:assert/strict";
import { createServer } from "node:http";
import { loadText, loadWithDeadline } from "./dist/loader.mjs";
let requestCount = 0;
let markStarted;
const started = new Promise((resolve) => { markStarted = resolve; });
const server = createServer((request, response) => {
  requestCount++;
  if (request.url === "/slow") { markStarted(); return; }
  response.statusCode = request.url === "/error" ? 503 : 200;
  response.end(request.url === "/error" ? "unavailable" : "ready");
});
await new Promise((resolve, reject) => {
  server.once("error", reject);
  server.listen(0, "127.0.0.1", resolve);
});
const address = server.address();
assert(address && typeof address !== "string");
const base = `http://127.0.0.1:${address.port}`;
try {
  assert.equal(await loadText(`${base}/ok`, new AbortController().signal), "ready");
  await assert.rejects(loadText(`${base}/error`, new AbortController().signal), { message: "HTTP 503" });
  const pre = new AbortController();
  const preReason = new Error("stopped before start");
  pre.abort(preReason);
  const before = requestCount;
  await assert.rejects(loadText(`${base}/ok`, pre.signal), (error) => error === preReason);
  assert.equal(requestCount, before);

  const live = new AbortController();
  const liveReason = new Error("stopped in flight");
  const pending = loadText(`${base}/slow`, live.signal);
  const observed = assert.rejects(pending, (error) => error === liveReason);
  await started;
  live.abort(liveReason);
  await observed;

  const ordinary = new AbortController();
  ordinary.abort();
  assert.equal(ordinary.signal.reason.name, "AbortError");
  assert.throws(() => AbortSignal.abort(17).throwIfAborted(), (reason) => reason === 17);
  const parent = new AbortController();
  const child = new AbortController();
  const parentReason = new Error("parent stopped");
  parent.abort(parentReason);
  const composed = AbortSignal.any([parent.signal, child.signal]);
  assert.equal(composed.aborted, true);
  assert.equal(composed.reason, parentReason);
  assert.equal(child.signal.aborted, false);

  const zero = AbortSignal.timeout(0);
  assert.equal(zero.aborted, false);
  await new Promise((resolve) => zero.addEventListener("abort", resolve, { once: true }));
  assert.equal(zero.reason.name, "TimeoutError");
  assert.throws(() => AbortSignal.timeout(-1), RangeError);
  await assert.rejects(loadWithDeadline(`${base}/slow`, new AbortController().signal, 20),
    (error) => error instanceof DOMException && error.name === "TimeoutError");
  console.log("ready; HTTP 503; pre-abort; in-flight abort; composed reason; scheduled timeout");
} finally {
  await new Promise((resolve, reject) => {
    server.close((error) => error ? reject(error) : resolve());
    server.closeAllConnections();
  });
}
```

The final line is printed and the fixture closes its server and connections. The success case reads a real response. The pre-abort case starts no new request; the in-flight case waits until the local server has received a request, then aborts its pending client response with the exact Error reason. The server deliberately leaves slow responses open, so the last case requires the deadline signal to stop waiting.

This tests client cancellation against the local fixture, not a guarantee that a remote service rolls back its work. The fixture does not test streaming-body cancellation after headers or every fetch implementation. A custom timer/event operation needs its own abort listener, pre-abort handling and cleanup; the [actual timer tests](<../../../17 Testing Types/sections/2. Typed Test Doubles/2.3. Testing async and error paths with types.md>) demonstrate those responsibilities without copying their implementation here.

### 2) **Separate runtime observation from type narrowing**

In the current declarations, aborted is boolean, reason is any and throwIfAborted returns void. It is an ordinary runtime check, not an asserts signature proving a permanent non-aborted typestate. Activate guaranteedFalse in loader.mts and compile with noEmit instead of outDir to observe TS2322, then restore it.

The [DOM algorithm](https://dom.spec.whatwg.org/#dom-abortsignal-throwifaborted) throws the stored reason when aborted. The fixture demonstrates default AbortError, a custom Error and the primitive 17. Promise<string> still has no rejection-type parameter. In application code, treat a caught reason as unknown until narrowed. Do not assume every aborted operation rejects with an Error named AbortError, and do not assume an arbitrary failure during cancellation must have been caused by it.

Routing should reflect the actual operation's contract. The wrapper's HTTP 503 is an ordinary response failure; the pre-abort and in-flight Error identities are known cancellation cases in this runtime. Timeout uses a TimeoutError DOMException. Whether cancellation is quiet, logged or retried depends on its cause and the caller's policy. A default abort reason is useful; a custom reason is useful when it carries relevant context. Neither needs a blanket ban.

Choose controller lifetimes around related operations. Sharing a parent signal across one request's sub-operations can be intentional; sharing it across unrelated requests couples their cancellation. AbortSignal.any observes its inputs and can already be aborted when created. It does not abort those input controllers: the fixture's child remains active after composition with an already-aborted parent. A manual forwarding listener would need to handle both existing state and future events, plus listener cleanup.

### 3) **Compose a deadline without promising preemption or rollback**

LoadWithDeadline combines caller cancellation and a timeout signal, then passes that combined signal into the real operation. Its fulfillment type stays Promise<string>; that says nothing about the class of a rejection. The fixture tests that an unfinished fetch rejects for the timeout reason. It asserts no exact wall-clock duration: scheduler delay and other runtime work can affect when the timeout is observed.

In the tested Node version, timeout(0) initially has aborted false and aborts through a later timer event. It is not an already-aborted sentinel or a disabled timeout. Timeout(-1) throws RangeError. Use AbortSignal.abort(reason) for an already-aborted signal. The server remains an active resource while the zero-delay signal is observed; a pending promise alone is not a process keepalive.

A timeout signal only helps code that observes it. It does not preempt a synchronous CPU loop, make a signal-less SDK stop, or undo a completed request. Promise.race can bound which result a caller waits for, but the losing work continues unless a separately owned mechanism stops it. Choose cancellation, completion and cleanup policies for the specific operation instead of adding a race and calling the resource problem solved.

### 4) **Common confusion**

Accepting signal in a signature is not the same as forwarding it to fetch. A pre-check alone handles already-aborted input but cannot interrupt an in-flight operation that never observes the signal. Conversely, a post-check can reject a stale result without undoing any work already performed.

Abort is an operation protocol, not an extra Promise state or a static guarantee that a returned value was produced while cancellation remained impossible. Check the actual API, reason behavior and observation points under the supported runtime.

### 5) **Performance note**

Signals, composition, timeout scheduling, listeners and real requests perform runtime work. The declarations do not make that work free. This fixture measures outcomes and resource closure without per-check nanoseconds, per-link microseconds or a cancellation-tree size budget. Keep lifetimes and cleanup clear, and measure relevant throughput or resource pressure before optimizing the protocol.
