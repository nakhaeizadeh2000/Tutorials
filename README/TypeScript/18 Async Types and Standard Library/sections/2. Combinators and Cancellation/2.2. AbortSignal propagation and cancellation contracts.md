## 2.2. AbortSignal propagation and cancellation contracts

### 1) **Signals as parameters** (cancellation as data, threading not globals)

**Definition** — cancellation-as-data: every cancellable operation accepts `signal?: AbortSignal` (optional, last parameter by convention — `fetch(url, { signal })`, `withSignal(op, signal)`), checks `signal.aborted` at cheap points, and wires `signal.addEventListener("abort", cleanup, { once: true })` for in-flight work. Controllers stay test-owned (one `AbortController` per operation/suite — lifetimes explicit, see 17/2.3 doubles).

**What problem it solves / history** — boolean-flag cancellation (`cancelled = true` globals — races between flag-set and flag-read, untestable interleavings, flags forgotten across refactors): signals standardize the protocol (aborted state + events + reason — one vocabulary across fetch/streams/timers/workers), making cancellation composable (parent signals spawning linked children via `AbortSignal.any`, timeouts via `AbortSignal.timeout`).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS; `AbortSignal.any`/`timeout` stable since Node 18/20), thread `signal` through every cancellable signature (parameters, not globals — data, not ambient state); check `throwIfAborted()` at operation starts (fail-fast, zero-cost when unaborted); link child controllers to parent signals (trees, not chains — `addEventListener` forwarding or `AbortSignal.any`).

**Runnable example** — signals threaded (good vs bad, `tsc --strict`):

```typescript
// good — signal parameter with fail-fast (cancellation data, checked at entry)
export {}; // module marker (top-level await below needs module scope)
async function loadChunk(id: string, signal?: AbortSignal): Promise<string> {
  signal?.throwIfAborted(); // fail-fast (aborted-before-start rejecting immediately — no wasted work)
  return `chunk:${id}`; // (real I/O would re-check per chunk — cheap points, per iteration)
}
const ctrl = new AbortController();
console.log(await loadChunk("c1", ctrl.signal)); // chunk:c1 — signals threaded (test-owned controllers — 17/2.3 doubles pattern)
// bad — global cancel flags (ambient booleans — races, untestable interleavings, forgotten resets)
// fix — signal parameters (protocol standardized — state + events + reason in one object)
```

```typescript
// good — linked children (parent abort cascading — trees via any/listener)
export {}; // module marker (consistent module scope across fences)
async function childWork(signal: AbortSignal): Promise<string> {
  signal.throwIfAborted();
  return "child-done";
}
const parent = new AbortController();
const linked = new AbortController();
parent.signal.addEventListener("abort", () => linked.abort(parent.signal.reason), { once: true }); // cascade (parent → child — tree, not chain)
parent.abort(new Error("shutdown"));
try { await childWork(linked.signal); console.log("unexpected"); }
catch { console.log("cascaded"); } // cascaded — abort cascading (one shutdown aborting whole trees — structured cancellation)
// bad — per-op independent controllers (shutdown aborting one op — siblings running on, resources leaking)
// fix — linked trees (parents cascading — shutdown as one event, not N forgotten flags)
```

**Common confusion** — "signals cancel promises" — signals *notify* (operations must observe — unobserved signals change nothing; combinators don't auto-wire, see 2.1 loser cleanup). "`throwIfAborted` vs `aborted` checks" — `throwIfAborted()` throws the *reason* (fail-fast with causality); `aborted` branches custom handling (cleanup-then-throw — control where needed). "one controller per app" — controllers scope *lifetimes* (per-request/per-suite — shared controllers coupling unrelated cancellations).

**Performance note** — `throwIfAborted` is a flag read (nanoseconds — check freely per iteration); listeners add one registration per link (microseconds — trees of dozens trivial; thousands pooled per 2.3).

**Mentor note** — signature review: cancellable without `signal?` is uncancellable (missing parameter = missing feature — request changes, not comments).

### 2) **Abort semantics in types** (aborted checks narrowing control flow)

**Definition** — the type-level view: `signal.aborted: boolean` (narrowable flag — `if (signal.aborted) throw ...` refining downstream control flow, though not narrowing types per se); `signal.reason: any` (abort cause — `controller.abort(reason)` carrying values, defaulting to `AbortError` DOMException); `signal.throwIfAborted(): void` (asserts non-aborted — the 15 assertion-function shape applied to cancellation: callers proceed unconditionally after, narrowed by non-abortion).

**What problem it solves / history** — untyped abort handling (`catch { /* anything */ }` — aborts indistinguishable from failures, retries retrying cancellations forever): reason-carrying aborts + `instanceof`/name checks let handlers route (abort → stop quietly; failure → retry loudly — the 15 throw-vs-return discipline at cancellation scale).

**Modern guidance** — abort with reasons (`controller.abort(new Error("shutdown"))` — causality carried, not bare `abort()`); distinguish aborts in catches (`e instanceof Error && e.name === "AbortError"` or reason-identity — aborts stopping, failures retrying); type operation results to exclude post-abort states (results valid only when unaborted — control flow proving it).

**Runnable example** — aborts routed, failures retried (good vs bad, `tsc --strict`):

```typescript
// good — abort distinguished from failure (routing by cause — quiet stops vs loud retries)
export {}; // module marker (top-level await below needs module scope)
async function fetchWithSignal(url: string, signal: AbortSignal): Promise<string> {
  signal.throwIfAborted(); // reason thrown (causality carried — handlers routing on it)
  return `data:${url}`;
}
const c2 = new AbortController();
c2.abort(new Error("user-navigated"));
try { await fetchWithSignal("u", c2.signal); console.log("unexpected"); }
catch (e) { console.log(e instanceof Error ? `stopped:${e.message}` : "stopped:unknown"); } // stopped:user-navigated — aborts quiet (no retry — cancellation intended)
// bad — catch-retry-all (aborts retried forever — cancelled operations resurrecting per backoff tick)
// fix — cause routing (aborts stopping, failures retrying — different causes, different handlers)
```

```typescript
// good — reason-carrying abort (default AbortError vs custom reasons — causality explicit)
export {}; // module marker (consistent module scope across fences)
const c3 = new AbortController();
c3.abort(); // default reason (AbortError DOMException — standard, recognizable)
console.log(c3.signal.aborted, c3.signal.reason instanceof Error); // true true — default reasons (AbortError carrying standard semantics)
// bad — bare abort() everywhere (reasons unknown — handlers guessing intent from context)
// fix — reasons at abort sites (shutdown/timeout/navigate — causality recorded where decided)
```

**Common confusion** — "aborts are errors" — aborts are *control flow* (intended stops — quiet handling); failures are *errors* (retry/log loudly) — conflating them retries cancellations (the classic abort-retry storm). "`reason: any` is safe" — reasons untyped (executor-legacy echo per 1.1 — narrow before use, `instanceof` + name checks). "throwIfAborted narrows types" — it narrows *control flow* (post-call code runs only unaborted — assertion shape per 15/1.1, not type-narrowing per 07).

**Performance note** — reason allocation one object per abort (rare path — aborts exceptional, not hot); `aborted` reads nanoseconds (poll freely).

**Mentor note** — catch-block review: "abort or failure?" (every async catch routing explicitly — unrouted catches retrying cancellations is the #1 abort bug).

### 3) **Timeout composition** (signal timeouts plus race patterns end-to-end)

**Definition** — time-bounded operations, two spellings: `AbortSignal.timeout(ms)` (signal auto-aborting after ms — declarative, composable with signal-accepting APIs) and `Promise.race([op, timeout(ms)])` (2.1 pattern — works with non-signal APIs, needs loser cleanup). End-to-end typing: operation `Promise<T>` + timeout rejection → `Promise<T>` (timeout as rejection, typed by the timer's error).

**What problem it solves / history** — hung external calls (unbounded awaits on third-party APIs — request accumulation, outage amplification): timeouts bounding every external wait (architecture, not optimism — 2.1's "bounded waits" restated with signal mechanics). Signal-timeouts compose (one abort reason across fetch+parse+validate — causality unified); races adapt (legacy APIs without signal support).

**Modern guidance** — prefer `AbortSignal.timeout` for signal-native APIs (fetch, streams — one mechanism, unified reasons); use `race` for signal-less APIs (legacy SDKs — timeout rejection + manual cleanup per 2.1); always clean losers (aborting the operation on timeout — bounded waits without leaked work, see 5.1 incident 2).

**Runnable example** — bounded waits, both spellings (good vs bad, `tsc --strict`):

```typescript
// good — signal-timeout composition (declarative bound — reason unified)
export {}; // module marker (top-level await below needs module scope)
async function bounded(signal: AbortSignal): Promise<string> {
  signal.throwIfAborted();
  return "bounded-ok";
}
try {
  console.log(await bounded(AbortSignal.timeout(1000))); // bounded-ok — timeout signal (auto-abort after ms — declarative)
} catch { console.log("timed-out"); } // bound enforced (slow ops rejecting — waits bounded by construction)
// bad — unbounded external awaits (third-party hangs accumulating — outage amplification without bounds)
// fix — timeouts everywhere external (signal.timeout or race — every outside wait bounded, no exceptions)
```

```typescript
// good — race for signal-less APIs (adaptation with cleanup — legacy bounded safely)
export {}; // module marker (consistent module scope across fences)
function legacyOp(): Promise<string> { return Promise.resolve("legacy-ok"); } // no signal support (legacy SDK shape)
function rejectAfter(ms: number): Promise<never> {
  return new Promise<never>((_, reject) => setTimeout(() => reject(new Error(`timeout:${ms}`)), ms)); // never-racer (1.3 pattern)
}
console.log(await Promise.race([legacyOp(), rejectAfter(500)])); // legacy-ok — race adaptation (bounds without signal support — cleanup noted for real I/O losers)
// bad — "legacy can't time out" (unbounded legacy awaits — oldest code, least bounded, most hung)
// fix — race adaptation (every await bounded — signal-native or raced, no third state)
```

**Common confusion** — "timeout(0) disables" — `AbortSignal.timeout(50)`-style small bounds abort aggressively (zero/negative → already-aborted — bounds as floors, tested per 17/2.3 timer doubles). "race-timeout cleans losers" — races never clean (2.1 rule restated — signal-timeouts DO propagate (abort observed); race-timeouts need manual abort). "timeouts replace retries" — timeouts bound *attempts*; retries repeat them (policies composing — timeout per attempt, budget across attempts, see 20/production).

**Performance note** — `AbortSignal.timeout` allocates one timer + signal (microseconds — per-operation cost trivial vs bounded I/O); race adds one extra promise + timer (same order — prefer signal-native where supported to skip the extra promise).

**Mentor note** — architecture review: every external call without a timeout is a hang waiting for load (bound-or-explain — the review question per integration).
