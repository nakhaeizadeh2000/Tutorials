## 2.1. all race allSettled any typed precisely

### 1) **`Promise.all` tuple preservation** (readonly-tuple in, tuple out)

**Definition** — `Promise.all<T extends readonly unknown[] | []>(values: T): Promise<{ -readonly [P in keyof T]: Awaited<T[P]> }>` — the mapped-tuple signature: heterogeneous inputs (`[Promise<string>, Promise<number>]`) yield positional results (`[string, number]` — order preserved, types per position). Empty tuple in → `Promise<[]>` (never hangs — vacuous resolution).

**What problem it solves / history** — `await a; await b; await c` serialization (latency summed — three 200ms fetches costing 600ms) vs `Promise.all` batching (latency maxed — 200ms total): the combinator converts independent awaits into one typed tuple (results positional, failures fast — first rejection rejecting the whole).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), default to `Promise.all` for independent operations (parallelism as the norm — 2.3's sequential-by-reason rule); pass `as const` tuples for literal-positional results (destructuring typed per slot); handle the fail-fast semantics explicitly (one rejection kills all — `allSettled` where partial results matter, part 3).

**Runnable example** — positional batching (good vs bad, `tsc --strict`):

```typescript
// good — heterogeneous batch with positional results (tuple preserved, order guaranteed)
export {}; // module marker (top-level await below needs module scope)
async function fetchUser(id: string): Promise<{ name: string }> { return { name: id }; }
async function fetchCount(id: string): Promise<number> { return id.length; }
const [user, count] = await Promise.all([fetchUser("u1"), fetchCount("u1")] as const); // [{name}, number] (positional — destructuring typed per slot)
console.log(user.name, count); // u1 2 — batch typed (independence batched, results positional)
// bad — serialized awaits (latency summed — N independent ops costing N round trips)
// fix — Promise.all by default (parallelism norm — sequential only with ordering reasons, see 2.3)
```

```typescript
// good — empty-tuple vacuity (zero inputs resolving immediately — no hang)
export {}; // module marker (consistent module scope across fences)
const none: [] = await Promise.all([]); // [] (vacuous resolution — loops over dynamic lists safe at zero length)
console.log(none.length); // 0 — empty batches (dynamic-list batching without length guards — combinator handling zero)
// bad — length-guarded batching (if (xs.length) await Promise.all(...) — guards duplicating vacuous semantics)
// fix — trust vacuity (empty in, empty out — guards only where post-processing needs them)
```

**Common confusion** — "`Promise.all` returns in completion order" — results are *positional* (input order — completion order invisible; `race` per part 2 for first-wins). "`all` fails everything on one rejection" — `all` *rejects* on first rejection (siblings continuing unobserved — losers needing cleanup per 2.2; `allSettled` for partial results). "tuples need `as const`" — array literals infer `Promise<T>[]` unions (positional info lost); `as const` (or explicit tuple annotations) preserves positions.

**Performance note** — `all` launches all inputs eagerly (concurrency = input count — unbounded for dynamic lists; pools per 2.3 where hundreds+); allocation one result array + one promise (negligible vs the awaited I/O).

**Mentor note** — batching review: "are these independent?" (yes → `all`; ordered → loop-await per 2.3; bounded → pool per 2.3) — the three-way question per multi-await site.

### 2) **`race`/`any` union collapsing** (first-settled wins, losers discarded)

**Definition** — `Promise.race<T extends readonly unknown[] | []>(values: T): Promise<Awaited<T[number]>>` (first *settled* — fulfillment or rejection — wins, typed as the member union); `Promise.any<T...>(values: T): Promise<Awaited<T[number]>` minus rejections... precisely: fulfills with the first *fulfillment* (rejections ignored until all reject → `AggregateError`), typed as `Awaited<T[number]>` (non-never members). Losers keep running (no cancellation — cleanup per 2.2).

**What problem it solves / history** — timeout patterns (operation vs timer — whichever settles first deciding), redundant-source patterns (three mirrors — fastest wins): `race`/`any` encode first-wins directly (result union-typed, losers discarded by the combinator — cleanup owned by the caller, see 5.1 incident 2).

**Modern guidance** — use `race` for timeouts (operation vs `timeout(ms)` never-racer — 1.3 part 3 pattern); use `any` for redundant sources (first success wins — rejections collected, not thrown); always pair with loser cleanup (AbortControllers aborting losers — 2.2; uncleaned losers leak per 5.1).

**Runnable example** — first-wins patterns (good vs bad, `tsc --strict`):

```typescript
// good — timeout via race (operation vs never-racer — bounded waiting typed)
export {}; // module marker (top-level await below needs module scope)
function timeout(ms: number): Promise<never> {
  return new Promise<never>((_, reject) => setTimeout(() => reject(new Error(`timeout:${ms}`)), ms)); // never-fulfills (1.3 pattern — rejects or loses)
}
async function slow(source: string): Promise<string> { return `data:${source}`; }
console.log(await Promise.race([slow("s"), timeout(1000)])); // data:s — timeout pattern (bounded waits — losers cleaned per 2.2 in production code)
// bad — unbounded awaits (operations hanging forever — no timeout, no race, hung requests accumulating)
// fix — race-with-timeout (every external await bounded — timeouts as architecture, not optimism)
```

```typescript
// good — any for redundant sources (first success — rejections tolerated until all fail)
export {}; // module marker (consistent module scope across fences)
async function mirrorA(): Promise<string> { throw new Error("a-down"); }
async function mirrorB(): Promise<string> { return "b-data"; }
console.log(await Promise.any([mirrorA(), mirrorB()])); // b-data — redundancy winning (partial failure tolerated — allSettled where results matter)
// bad — all for redundant sources (one mirror down killing the read — redundancy defeated by fail-fast)
// fix — any (success-oriented — failures collected into AggregateError only when ALL fail)
```

**Common confusion** — "`race` cancels losers" — losers *run on* (combinators don't abort — cleanup via signals per 2.2; the 5.1 socket-leak class). "`any` never rejects" — `any` rejects when *all* reject (`AggregateError` with `errors[]` — total-failure typed, not silent). "race-vs-any interchangeable" — `race` settles first (win OR lose fast — timeouts); `any` fulfills first (wins only — redundancy).

**Performance note** — losers consume resources until settled (sockets, timers — cleanup cost real; abort losers promptly per 2.2); `race`/`any` allocation one promise + adoption (negligible vs loser I/O).

**Mentor note** — every `race`/`any` in review needs its loser-cleanup answer ("who aborts the losers?" — no answer, no merge; see 5.1 incident 2 as exhibit).

### 3) **`allSettled` never-rejecting unions** (partial-failure shapes typed)

**Definition** — `Promise.allSettled<T extends readonly unknown[] | []>(values: T): Promise<{ -readonly [P in keyof T]: PromiseSettledResult<Awaited<T[P]>> }>` where `PromiseSettledResult<T> = { status: "fulfilled"; value: T } | { status: "rejected"; reason: any }` — per-member settled unions (never rejects itself — total function over promise lists; partial failures typed as data, see 15/2.1's Result philosophy).

**What problem it solves / history** — bulk operations with tolerable partial failure (10 notifications — 9 delivered, 1 bounced: `all` throwing away 9 successes with 1 rejection): `allSettled` returns every outcome (successes usable, failures inspectable — the Result-as-value pattern at combinator scale).

**Modern guidance** — use `allSettled` for bulk/best-effort work (notifications, migrations, fan-out — partial success normal); narrow per member via `status` discriminant (exhaustive handling per 07 — fulfilled values flowing, rejected reasons logged/retried); reserve `all` for atomic batches (all-or-nothing — fail-fast semantics intended).

**Runnable example** — partial failure as data (good vs bad, `tsc --strict`):

```typescript
// good — settled unions narrowed per member (successes used, failures handled — exhaustively)
export {}; // module marker (top-level await below needs module scope)
async function ping(host: string): Promise<string> {
  if (host === "bad") throw new Error(`unreachable:${host}`);
  return `ok:${host}`;
}
const results = await Promise.allSettled([ping("a"), ping("bad")] as const); // settled tuple (never rejects — total function)
for (const r of results) {
  console.log(r.status === "fulfilled" ? r.value : `retry:${String(r.reason)}`); // discriminant narrowing (07 mechanics — per-member handling)
}
// ok:a + retry:Error: unreachable:bad — partial failure typed (9-successes-usable pattern at small scale)
// bad — all for bulk work (one bounce discarding all deliveries — atomicity where independence holds)
// fix — allSettled (partial results data — successes flowing, failures enumerated)
```

**Common confusion** — "`allSettled` never fails" — it never *rejects* (failures encoded as `rejected` members — handling still required; unhandled settled-rejections are logic bugs, not type errors). "`reason: any` is safe" — reasons untyped (executor legacy per 1.1 — narrow via `instanceof` before use, see 17/2.3 class-pinning). "settled equals Result" — shapes rhyme (`ok`/`status` discriminants) but differ (`reason: any` vs typed `E` — 15/2.1 `Result<T, E>` stricter where error types known).

**Performance note** — `allSettled` waits for *every* input (latency = slowest, not first-failure — bulk semantics priced accordingly); allocation one wrapper object per member (negligible vs bulk I/O).

**Mentor note** — batch-semantics question: "atomic or best-effort?" (`all` vs `allSettled` — the answer documented above the call, not discovered in incidents).
