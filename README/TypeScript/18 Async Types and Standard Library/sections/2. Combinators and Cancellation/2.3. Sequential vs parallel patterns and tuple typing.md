## 2.3. Sequential vs parallel patterns and tuple typing

Separate **starting work** from **waiting for results**. Awaiting an operation before starting the next creates sequential work. Mapping a starter over a list may start every operation before a later loop consumes any result. A bounded mapper controls when another operation may start; Promise.all alone does not provide that control.

Use **TypeScript 7.0.2** and **Node.js 20.20.2**, verified 2026-10-17. The complete fixture below uses manually released promises to observe starts and completion without guessing request durations. It performs no network requests or throughput benchmark.

### 1) **Choose sequential or already-started work from dependencies**

A loop that calls and awaits each operation before its next iteration enforces that start/completion order. It suits a cursor request that needs the previous response or a step that must observe the previous effect. That ordering does not eliminate unrelated races or make a batch transactional.

By contrast, `const pending = inputs.map(start)` invokes the starters during map. A subsequent for-await loop consumes those existing promises in input order. It does not restart them one by one or turn their already overlapping work into a sum of operation durations. It can delay observing a later completed result while waiting for an earlier one. Rejections also need a deliberate owner; input-ordered consumption is not a general substitute for aggregate error handling.

The [combinator owner](<./2.1. all race allSettled any typed precisely.md>) tests input-ordered results, fail-fast observation and fixed tuples versus a widened array. Dynamic lists may contain union-valued elements; they do not require every job to have one identical concrete result type. A fixed tuple can preserve a positional relationship that an ordinary R[] API does not promise.

The fixture's sequential and already-started cases below make this distinction observable. ESLint's [core no-await-in-loop rule](https://eslint.org/docs/latest/rules/no-await-in-loop) can flag intentional sequencing too. An ordinary reason comment explains a choice to a reviewer but does not suppress the rule. The [executed tooling-pitfall lesson](<../../../16 Tooling Language Server and Ecosystem/sections/5. Common pitfalls to production bugs/5.1. Real production bugs caused by tooling misunderstandings.md>) shows an actual diagnostic and a scoped exception.

### 2) **State a bounded mapper's complete contract**

This mapper accepts a dense array with own indexed entries and a positive safe-integer concurrency limit. It snapshots entries before starting work, returns results in input order and admits at most limit active callbacks. The snapshot is shallow: object payloads remain shared references.

Its failure policy is explicit: after the first observed callback failure, stop admitting jobs, wait for callbacks already started to settle, then reject with that first reason. A rejection reason may even be undefined. This is a draining policy, not fail-fast return or cancellation. A running callback that never settles prevents the drain from finishing. The limit bounds simultaneous callbacks, not requests per second or memory retained by results.

Save:

```typescript
// file: pool.mts
export async function mapBounded<T, R>(
  items: readonly T[], limit: number, work: (value: T, index: number) => R | PromiseLike<R>,
): Promise<R[]> {
  if (!Number.isSafeInteger(limit) || limit < 1) throw new RangeError("positive safe-integer limit required");
  for (let index = 0; index < items.length; index++) {
    if (!Object.hasOwn(items, index)) throw new TypeError("dense own entries required");
  }
  const jobs = Array.from(items, (value, index) => ({ value, index }));
  const output: R[] = new Array(jobs.length);
  let next = 0;
  let failed = false;
  let firstReason: unknown;
  async function lane(): Promise<void> {
    while (!failed && next < jobs.length) {
      const job = jobs[next++]!; // Index is bounded; the private snapshot is not mutated.
      try { output[job.index] = await work(job.value, job.index); }
      catch (reason: unknown) {
        if (!failed) { failed = true; firstReason = reason; }
      }
    }
  }
  await Promise.all(Array.from({ length: Math.min(limit, jobs.length) }, () => lane()));
  if (failed) throw firstReason;
  return output;
}
```

Each lane claims an index before it awaits. In this ordinary JavaScript execution, that synchronous claim is not interleaved with another lane. Awaiting gives other lanes a chance to progress. The result slot records the original index, so completion order cannot reorder the returned array. This is async concurrency in one JavaScript agent, not CPU parallelism across worker threads.

A separate failed flag distinguishes no failure from a failure whose reason is undefined. Catching each callback failure lets the outer Promise.all wait for every started lane. Stopping admission does not cancel callbacks already running or reverse their side effects. An application needing cooperative cancellation should pass its [signal protocol](<./2.2. AbortSignal propagation and cancellation contracts.md>) to the work and define how it combines with this drain policy.

### 3) **Verify starts, capacity, order and failure ownership**

Save the following consumer beside pool.mts. Compile with `tsc --strict --noUncheckedIndexedAccess --target es2022 --module nodenext --outDir dist pool.mts`, then run `node verify.mjs`.

```javascript
// file: verify.mjs
import assert from "node:assert/strict";
import { mapBounded } from "./dist/pool.mjs";
function controlled() {
  let resolve, reject;
  const promise = new Promise((yes, no) => { resolve = yes; reject = no; });
  return { promise, resolve, reject };
}
function fixture(size) {
  const gates = Array.from({ length: size }, controlled);
  const entered = Array.from({ length: size }, controlled);
  const started = [];
  let active = 0, maximum = 0;
  return {
    gates, entered, started,
    get maximum() { return maximum; },
    get active() { return active; },
    async work(value, index) {
      started.push(index); active++; maximum = Math.max(maximum, active);
      entered[index].resolve();
      try { await gates[index].promise; return value * 2; }
      finally { active--; }
    },
  };
}
const sequential = fixture(2);
const sequentialValues = [];
const sequence = (async () => {
  for (const index of [0, 1]) sequentialValues.push(await sequential.work(index, index));
})();
assert.deepEqual(sequential.started, [0]);
sequential.gates[0].resolve();
await sequential.entered[1].promise;
sequential.gates[1].resolve();
await sequence;
assert.equal(sequential.maximum, 1);
assert.deepEqual(sequentialValues, [0, 2]);

const overlapping = fixture(2);
const pending = [0, 1].map((value, index) => overlapping.work(value, index));
assert.deepEqual(overlapping.started, [0, 1]);
const observed = [];
const consumption = (async () => { for await (const value of pending) observed.push(value); })();
overlapping.gates[1].resolve();
await Promise.resolve();
assert.deepEqual(observed, []); // Waiting for input 0, although job 1 was already started.
overlapping.gates[0].resolve();
await consumption;
assert.deepEqual(observed, [0, 2]);
assert.equal(overlapping.maximum, 2);

const bounded = fixture(4);
const inputs = [0, 1, 2, 3];
const collected = mapBounded(inputs, 2, bounded.work);
assert.deepEqual(bounded.started, [0, 1]);
inputs[2] = 99; // The mapper already snapshotted the primitive entries.
bounded.gates[1].resolve();
await bounded.entered[2].promise;
assert.equal(bounded.active, 2);
bounded.gates[2].resolve();
await bounded.entered[3].promise;
bounded.gates[0].resolve(); bounded.gates[3].resolve();
assert.deepEqual(await collected, [0, 2, 4, 6]);
assert.equal(bounded.maximum, 2);
assert.equal(bounded.active, 0);

const failing = fixture(3);
let returned = false;
const drained = mapBounded([0, 1, 2], 2, failing.work).then(
  () => { returned = true; return { ok: true }; },
  (reason) => { returned = true; return { ok: false, reason }; },
);
failing.gates[1].reject(undefined);
await new Promise((resolve) => setTimeout(resolve, 0)); // Let the failure be observed by its lane.
assert.deepEqual(failing.started, [0, 1]);
assert.equal(returned, false); // The already-started job 0 still belongs to the drain.
failing.gates[0].resolve();
const failure = await drained;
assert.equal(failure.ok, false);
assert.equal(failure.reason, undefined);
assert.equal(failing.active, 0);

for (const limit of [0, -1, 0.5, NaN, Infinity, Number.MAX_SAFE_INTEGER + 1]) {
  await assert.rejects(mapBounded([1], limit, (value) => value), RangeError);
}
await assert.rejects(mapBounded(new Array(2), 2, (value) => value), TypeError);
assert.deepEqual(await mapBounded([], 3, () => { throw new Error("must not run"); }), []);
assert.deepEqual(await mapBounded([undefined], 3, (value) => value), [undefined]);
assert.deepEqual(await mapBounded([1, 2], 1, (value) => value * 2), [2, 4]);
assert.deepEqual(await mapBounded([1], 99, (value) => value + 1), [2]);
await assert.rejects(mapBounded([1], 2, () => { throw new Error("sync failure"); }), { message: "sync failure" });
console.log("sequential 1; overlapping 2; bounded 2; ordered results; drained failure; boundaries passed");
```

The final line is printed after all assertions. Separate started gates show that the pool admits job 2 as a slot becomes available instead of waiting for an entire fixed chunk. It keeps input-order results while completion overlaps. The failure scenario proves both no new admission after observation and waiting for already-started work, including an undefined reason. Invalid limits and sparse inputs reject instead of silently returning unfilled output slots.

This mapper intentionally returns an R[] rather than preserving an arbitrary heterogeneous tuple's per-position transform.

Maintained libraries can supply queue controls and tested integration beyond this bounded example. The [p-limit maintainer documentation](https://github.com/sindresorhus/p-limit) distinguishes active and pending work and explicitly states that clearing a queue does not cancel running promises. ### 4) **Common confusion**

A concurrency limit is not a rate limit. Even one quickly completing callback can start many operations per second. An upstream quota may require pacing or a separate rate policy. Likewise, preserving result order does not require starting jobs sequentially, and consuming already-started promises in order does not erase their overlapping execution.

Bounding active callbacks also does not bound every resource automatically. The mapper retains a snapshot and output array, while each callback may start additional work of its own. Its drain policy can wait indefinitely for an uncooperative callback. Define those limits instead of claiming a pool makes resource collapse or races impossible.

### 5) **Performance note**

The mapper bounds its own active callback count while retaining input snapshots and results proportional to the list size. A sequential loop can still accumulate a large output, and an individual operation can retain arbitrary memory. These fixtures measure capacity and order, not latency, throughput or an N/K formula. Choose the limit from dependencies, resource budgets and actual measurements; use an incremental/streaming design when retaining the full list is inappropriate.

### 6) **Mentor note**

Ask when each operation starts in the sequential loop, mapped list and bounded mapper. Then reject one controlled job and ask when the outer result should arrive under the stated drain contract. A useful answer identifies pending versus active jobs, result order, rejection ownership, cancellation limits and what a different failure policy would change.
