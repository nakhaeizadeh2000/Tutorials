## 2.3. Sequential vs parallel patterns and tuple typing

### 1) **Loop-await serialization** (for-of plus await, ordered slow simple)

**Definition** — *serialization*: `for (const x of xs) { await op(x); }` — each iteration completing before the next starts (latency summed, order guaranteed, memory flat — one in-flight op). Typing trivial (loop variable per iteration, results pushed into an array — no tuples, no unions, sequential control flow the checker follows line by line).

**What problem it solves / history** — rate-limited/ordered work (migrations in sequence, API quotas, dependent steps where `xs[i+1]` needs `xs[i]`'s result): serialization enforces order structurally (no race conditions possible — later iterations observing earlier effects). Misapplied to independent work it serializes what could batch (the 5.1 10k-requests incident — floats disguised as batches, or batches disguised as loops).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), choose loop-await when: order matters (dependent steps), the callee rate-limits (quota/connection caps), or side effects must serialize (migrations, deploys). Document the reason above the loop (serialization surprising reviewers — `// sequential: order-dependent (step N needs step N-1)`) to survive "parallelize this" cleanups.

**Runnable example** — ordered slowness, deliberately (good vs bad, `tsc --strict`):

```typescript
// good — sequential migration (order structural — later steps observing earlier effects)
export {}; // module marker (top-level await below needs module scope)
const applied: string[] = [];
async function migrate(step: string): Promise<void> {
  applied.push(step); // effect visible to subsequent steps (ordering load-bearing)
}
// sequential: each migration sees previous ones (order-dependent — parallelizing breaks semantics)
for (const s of ["001", "002", "003"]) { await migrate(s); }
console.log(applied.join(",")); // 001,002,003 — order guaranteed (serialization as correctness, not caution)
// bad — Promise.all over migrations (parallel application — later steps missing earlier effects, schema corrupted)
// fix — loop-await with a reason comment (order documented — parallelization attempts reviewed against the reason)
```

```typescript
// good — dependent chaining (step N+1 consuming step N — serialization forced by data)
export {}; // module marker (consistent module scope across fences)
async function nextPage(cursor: string | null): Promise<{ rows: number[]; next: string | null }> {
  return cursor === null ? { rows: [1, 2], next: "c2" } : { rows: [3], next: null }; // paged API (cursor threading — inherently sequential)
}
const all: number[] = [];
let cursor: string | null = null;
while (true) {
  const page = await nextPage(cursor); // each request needing the previous cursor (data-forced order)
  all.push(...page.rows);
  cursor = page.next;
  if (cursor === null) break;
}
console.log(all.join(",")); // 1,2,3 — pagination serialized (cursors chaining — parallelism unrepresentable)
// bad — batching cursor APIs (parallel page fetches without cursors — protocol violation, duplicate/missing rows)
// fix — while-await for cursors (data dependency visible — sequential by protocol, not by choice)
```

**Common confusion** — "loops are always slower" — loops are slower *per independent op* (latency summed); for dependent/ordered work loops are the *only* correct shape (speed comparisons meaningless across semantics). "`no-await-in-loop` forbids this" — the lint rule *flags* loop-awaits for review (16/2.1 tier — serialization needing justification, not prohibition; reason comments satisfying it). "serialization wastes connections" — one in-flight op uses minimal resources (memory flat — the tradeoff documented, chosen deliberately).

**Performance note** — loop latency = sum (N × single-op latency — 10k × 200ms = 33 minutes, the 5.1 incident arithmetic); memory O(1) in flight (vs O(N) for batches — serialization's resource virtue).

**Mentor note** — loop-await review: "order, quota, or dependence?" (one of the three justifying serialization — none present means `Promise.all` per 2.1).

### 2) **`Promise.all` parallelism** (concurrent launch, tuple results)

**Definition** — *batching*: `await Promise.all(xs.map(op))` — all operations launched before any completes (latency maxed, order of *results* positional per 2.1, memory O(N) in flight). Typing tuple-preserving for fixed lists (2.1 part 1), array-unioned for dynamic lists (`Promise<T>[]` in, `T[]` out — homogeneity required).

**What problem it solves / history** — independent I/O serialized by habit (config loads, parallel fetches, fan-out reads — latency summed for no semantic reason): batching recovers the parallelism the protocol allows (N round trips collapsing to the slowest one — the single highest-ROI async refactor in most codebases).

**Modern guidance** — default to `Promise.all` for independent operations (parallelism as the norm — 2.1 rule restated at pattern level); map-then-all in one expression (`xs.map(op)` launching eagerly — launch-before-await, the batching precondition); bound dynamic lists (pools per part 3 — hundreds+ in flight collapsing servers, see 5.1).

**Runnable example** — batching by default (good vs bad, `tsc --strict`):

```typescript
// good — fan-out batch (independence batched — latency maxed, results positional)
export {}; // module marker (top-level await below needs module scope)
async function readConfig(key: string): Promise<string> { return `${key}=1`; }
const [a, b] = await Promise.all([readConfig("x"), readConfig("y")] as const); // tuple (positional — per-slot types preserved)
console.log(a, b); // x=1 y=1 — parallel launch (both in flight before either completes — latency of one)
// bad — serialized config loads (latency summed — three files costing three round trips for no reason)
// fix — map-then-all (independence batched — the default shape, serialization justified per part 1)
```

```typescript
// good — dynamic-list batching (homogeneous arrays in, arrays out — union element types)
export {}; // module marker (consistent module scope across fences)
async function fetchRow(id: number): Promise<{ id: number }> { return { id }; }
const ids = [1, 2, 3];
const rows: { id: number }[] = await Promise.all(ids.map(fetchRow)); // T[] (dynamic — homogeneity required, positions untyped)
console.log(rows.length); // 3 — list batching (map launching eagerly — launch-before-await precondition met)
// bad — for-await over the mapped array (mapped-then-serially-awaited — launching parallel, consuming serial: latency summed anyway)
// fix — await the all (launch AND join batched — mapping without all is serial consumption in disguise)
```

**Common confusion** — "map-then-for-await batches" — mapping launches (parallel start) but for-await *consumes serially* (completion order forced sequential — latency summed despite parallel launch; `await Promise.all(mapped)` joins in parallel). "batching preserves completion order" — batching preserves *input* order (results positional — completion invisible; `race` for first-wins per 2.1). "all handles partial failure" — `all` fail-fasts (one rejection killing the batch — `allSettled` for partials per 2.1 part 3).

**Performance note** — batch latency = max (not sum — N×200ms → 200ms for independent ops); memory O(N) in flight (results buffered — hundreds fine, hundred-thousands streamed per 3.2).

**Mentor note** — the launch-vs-join distinction (map launches, all joins — for-await joins serially; the two-line diagram teaching batching permanently).

### 3) **Bounded concurrency** (pools limiting flight, typed worker contracts)

**Definition** — *pooling*: at most K operations in flight (semaphore/queue admitting K, parking the rest — latency between max and sum, memory O(K), servers un-collapsed). Typed worker contracts: `Worker<T, R> = (job: T) => Promise<R>` (jobs homogeneous, results positional-by-completion or collected in order — pool implementations varying, contracts stable).

**What problem it solves / history** — unbounded fan-out (10k URLs `Promise.all`ed — connection exhaustion, file-descriptor limits, downstream 429s, OOM from buffered results): pools bound flight structurally (K concurrent — throughput without collapse), replacing emergent limits (crashes) with designed ones (queues).

**Modern guidance** — pool dynamic lists over ~dozens (K = 5–20 typical — tuned per downstream capacity, not CPU); preserve input order in results where consumers index (collect by slot — positional honesty); expose pool metrics (in-flight gauges — observability per 20/production discipline). Hand-roll simple pools (20 lines — semaphore + loop) or adopt `p-limit` (dependency where pooling pervades).

**Runnable example** — designed bounds (good vs bad, `tsc --strict`):

```typescript
// good — minimal pool (K in flight — throughput without collapse)
export {}; // module marker (top-level await below needs module scope)
async function worker(job: number): Promise<number> { return job * 2; } // Worker<T, R> contract (homogeneous jobs, typed results)
async function pool<T, R>(jobs: T[], k: number, run: (job: T) => Promise<R>): Promise<R[]> {
  const out: R[] = new Array(jobs.length); // positional collection (input order preserved — slot-indexed)
  let next = 0;
  async function lane(): Promise<void> {
    while (next < jobs.length) { const i = next++; out[i] = await run(jobs[i]); } // lanes consuming (K lanes — flight bounded)
  }
  await Promise.all(Array.from({ length: Math.min(k, jobs.length) }, lane)); // K lanes (bounded flight — designed limit)
  return out;
}
console.log(await pool([1, 2, 3, 4], 2, worker)); // [2,4,6,8] — pooled results (positional, bounded — collapse impossible)
// bad — unbounded all over 10k (descriptors exhausted, 429s, OOM — emergent limits replacing designed ones)
// fix — pools past dozens (K tuned per downstream — throughput designed, not discovered)
```

**Common confusion** — "pools serialize" — pools *parallelize boundedly* (K concurrent — between serial (1) and unbounded (N); K=1 reduces to serialization honestly). "order lost in pools" — slot-indexed collection preserves order (completion order invisible — positional results per input index). "libraries required" — 20-line pools suffice (semaphore + lanes — adopt `p-limit` when pooling pervades, not before).

**Performance note** — pool latency ≈ ceil(N/K) × single-op (tunable — K trading latency for load); memory O(K) in flight + O(N) results (results buffered regardless — stream per 3.2 where N huge).

**Mentor note** — capacity question per fan-out: "what breaks at N=10k?" (descriptors/429s/memory — the answer setting K; unbounded fan-out merged only with a written N-cap).
