## 7.1. Boundaries — what is covered elsewhere

Use this domain to connect asynchronous operations with their TypeScript contracts. Keep the runtime operation, inferred result, completion owner, checking program and verification evidence visible as separate questions. This page routes those questions to the existing lessons; it does not introduce another promise implementation, type-test helper or compiler configuration.

### 1) **Type transformations versus asynchronous operations**

Start with [Awaited and infer pipelines](<../../../09 Utility Types and Type Transformations/sections/2. Conditional Types/2.3. infer pipelines ReturnType Parameters Awaited.md>) when the question is how a conditional type derives an eventual result. Use [infer mechanics](<../../../08 Generics Deep Dive/sections/2. Constraints Defaults and Inference Control/2.3. infer conditional inference and distributive preview.md>) for inference binding and [conditional evaluation](<../../../09 Utility Types and Type Transformations/sections/2. Conditional Types/2.1. Conditional fundamentals distributive law and never branches.md>) for distribution. Keep the async application here in [Awaited and thenables](<../1. Promise Types/1.2. Awaited recursive unwrapping and thenables.md>) and [promise combinator shapes](<../2. Combinators and Cancellation/2.1. all race allSettled any typed precisely.md>): the learner needs to connect an actual operation to the type of the value consumed afterward.

A type query cannot schedule work, await a value or validate a network response. If the expected result shape is wrong, inspect the producing signature and transformation. If an operation has not completed or produced the expected value, inspect the actual execution and completion path. An assertion about the first question does not settle the second.

Synchronous iterator helpers have a separate worked owner in [collections and synchronous iterator helpers](<../../../10 Arrays Tuples and Collections/sections/3. Collections and Selection/3.1. Map and Set typing generics over collections.md>). That lesson checks helper availability, finite input/output counts and iterator completion. Use the [AsyncIterable and generator owner](<../3. Standard Library in Practice/3.2. AsyncIterable generators and for-await.md>) for inferred versus defaulted channels, startup sends, synchronous fallback, controlled consumer pacing and awaited closing. Its custom iterator failure also shows that not every rejected next call triggers return. Shared words such as iterator or collection do not make their library requirements and execution examples interchangeable.

### 2) **Completion evidence versus test construction**

The test-design owners are [spies, stubs and fakes](<../../../17 Testing Types/sections/2. Typed Test Doubles/2.2. Spies stubs and fakes over generics.md>), [async test seams](<../../../17 Testing Types/sections/2. Typed Test Doubles/2.3. Testing async and error paths with types.md>) and [type-test CI gates](<../../../17 Testing Types/sections/3. Type Tests in Practice/3.3. CI gates running type tests with unit tests.md>). They explain the signatures and observations a test double or suite should preserve. This domain supplies the asynchronous contract being exercised: eventual results, cancellation requests, aggregation and scheduling.

Choose evidence for the actual failure. To check a rejected operation, the test needs to observe its completion and rejection. To check a public type result, use an actual configured type-test gate such as the worked tools in [real tsd/Vitest/expect-type fixtures](<../../../17 Testing Types/sections/1. Type Assertions in Tests/1.2. tsd expect-type and type-testing libraries.md>). To check a published declaration, use the [public declaration test owner](<../../../17 Testing Types/sections/3. Type Tests in Practice/3.2. Testing declaration files and public API surface.md>) and a consumer of the built artifact. These checks may exercise related code, but one passing result does not establish every other contract.

A declaration such as declare function assertType does not install a runtime implementation. If a documentation probe calls an absent helper, use the real tool's documented checking path or a type-only assertion that does not execute. The [type-assertion owner](<../../../17 Testing Types/sections/1. Type Assertions in Tests/1.1. Expect Equal and compile-time type assertions.md>) reproduces an emitted ambient call failing at runtime. Copying it into an async example would add a failure unrelated to the promise being taught.

### 3) **Callable contracts and callback hosts**

Use [return and completion contracts](<../../../05 Functions and Callable Types/sections/1. Function Type Fundamentals/1.3. Return types void never and contextual inference.md>) for void, never, inferred returns and the behavior of an ignoring versus awaiting callback host. Use [callback variance](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.2. Callback variance strictFunctionTypes and bivariance pitfalls.md>) for parameter/result assignment directions and the method exception, and [receiver contracts](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.1. this parameter explicit typing and arrow vs function capture.md>) for explicit receivers, capture and binding. This domain's [async return owner](<../1. Promise Types/1.3. async function return-type contracts.md>) adds the async function contract and its eventual result.

When a callback returns a Promise, ask two questions: is that function accepted by the target callback type, and what does the host do with the returned value? The verified return lesson accepts an async callback at a void callback boundary, then contrasts a host that ignores its result with one that awaits and propagates completion. Receiver requirements are another independent part of invocation. Do not explain a lost completion or detached receiver solely by quoting an accepted assignment.

For cancellation, keep the operation contract in [cancellation owner](<../2. Combinators and Cancellation/2.2. AbortSignal propagation and cancellation contracts.md>) and the test seam in the async-double owner. A parameter's presence in a signature and the runtime path that consumes it deserve separate review. The [actual HTTP body-race reproduction](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by async misunderstandings.md>) adds a lifecycle boundary: a fulfilled Response can still have unread body work affected by a shared abort. Detailed callback and test mechanics stay in their owners rather than being repeated under each async API.

### 4) **Declarations, programs and executed artifacts**

Use [async library-surface owner](<../3. Standard Library in Practice/3.1. lib settings and built-in async types.md>) to locate the relevant async declarations and [module pairing](<../../../13 Configuration and Compiler Options/sections/3. Modules Emit and Projects/3.1. module and moduleResolution pairing.md>) for the module/resolution program. Use [source/emit import graphs](<../../../12 Modules Namespaces and Declaration Files/sections/1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>) when checking source imports separately from emitted destinations, and the [current configuration migration](<../../../25 Update TypeScript 7.0/sections/1. Configuration Migration/1.1. Configuration defaults and removed options.md>) when migrating compiler defaults. A library declaration can make an API available to the checker without installing that API in the runtime. The local library owner actually compares isolated DOM and Node declarations, an ES2015 async-iteration transform, and scope cleanup with disposal symbols present but stack constructors absent.

The iterator-helper owner supplies a concrete comparison: its declared library and runtime versions are checked separately, with an older runtime failing the helper call. If the checker cannot find a built-in member, inspect the program's libraries and included declarations. If the emitted program fails when calling the member, inspect the actual runtime or installed implementation. If loading fails before that call, inspect the consumed file graph. Changing a type assertion cannot repair either runtime problem.

A successful check of one source program does not prove that a different entry point, output directory or consumer uses the same declarations and values. Keep the run command and artifact explicit; the source/emit owner provides that full project rather than a promise that a set of flags makes every graph executable.

### 5) **Runtime scheduling and compiler scaling**

Keep typed concurrency choices in [sequential, concurrent and bounded operation owner](<../2. Combinators and Cancellation/2.3. Sequential vs parallel patterns and tuple typing.md>) and timer-handle contracts in [timer and queue owner](<../3. Standard Library in Practice/3.3. Timers queues and the event-loop type view.md>). The timer owner executes ref/unref child processes and confirms that a number annotation does not change a Node handle's identity or cancellation. For the JavaScript execution model, use [Async Event Loop and Promises](<../../../../JavaScript/13 Async Event Loop and Promises/README.md>). For TypeScript checking/build concerns, use [checking measurements](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>), [type-instantiation diagnosis](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.2. Instantiation budgets and TS2589 carve-outs.md>) and [native build/watch measurements](<../../../25 Update TypeScript 7.0/sections/3. Native Build and Watch/3.1. Native builds watch and measurement.md>). Domain19 is published; it need not remain a future placeholder in this route.

A slow application operation and a slow compiler are different measurements. Record the elapsed operation, inputs and relevant environment before choosing a remedy. A change to a type representation may alter checking work while leaving the executed program unchanged. A change to scheduling or concurrency may alter runtime behavior without addressing a type-instantiation bottleneck. The native-build owner demonstrates process identity and comparable cache states for compiler measurements; do not apply those results as promise timing guarantees.

No synthetic delay benchmark is added here. Use the owning lesson's actual experiment and verify that its inputs, failure semantics and limits match the question being investigated.

### 6) **Common confusion**

A type test is not an awaited operation, and awaiting a local fake does not prove an external service integration. A void callback target may accept a Promise-producing implementation while its host ignores the return. A lib setting supplies declarations, not a runtime polyfill. Finally, async runtime profiling and compiler checking diagnostics are different investigations. Route the observed failing operation before selecting another type annotation or flag.

### 7) **Performance note**

Navigation itself changes no runtime behavior. Type-only probes can still require checker work; executable helper calls and test doubles can perform real work. There is no microsecond cost or guarantee that splitting explanations removes checking cost. Measure the checking program with the compiler owners and the executed workload with appropriate runtime tools. Keeping canonical owners helps readers avoid conflicting advice, but does not establish a numerical performance improvement.

### 8) **Mentor note**

Use three diagnostic cases and require both an owner and its evidence. First, an async callback is accepted but a host reports completion early: route to return contracts and compare the observed ignoring/awaiting hosts. Second, the checker accepts an iterator helper but the tested older runtime throws: route to the collection owner's library/runtime contrast and identify the implementation requirement. Third, a documentation assertion call throws ReferenceError before any useful async result: route to the real type-test tool fixture and establish whether that assertion should execute at all.

A sound answer names the failure layer, follows a precise existing route and states what additional observation is needed. It does not infer a runtime pass from a green type check, add a cast to install an API or reproduce a whole neighboring lesson inside the async domain.
