## 3.3. Timers queues and the event-loop type view

### 1) **Timer handle types** (dom-number vs node-Timeout duality and containment)

**Definition** — the duality: `DOM` declares `setTimeout(...): number` (numeric handle — `clearTimeout(handle: number)`); Node (`@types/node`) declares `setTimeout(...): NodeJS.Timeout` (object handle — `.unref()/.ref()/.refresh()` methods). Both declarations present → overloads colliding (return type `number | Timeout` — `clearTimeout` accepting both, `.unref()` available on neither without narrowing).

**What problem it solves / history** — cross-environment timer code (`clearTimeout` no-ops from mismatched handles — 5.1 incident 3: DOM-typed handle shipped to Node clearing nothing, interval leaking): environment-scoped timer modules (one wrapper per runtime — handles opaque outside) containing the duality structurally instead of casting per call.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), isolate timers per environment (Node services: `@types/node` only, no `DOM` — `Timeout` handles with `unref`; browser code: `DOM` only — numeric handles); wrap cross-platform timer use (`delay(ms, signal?)` helper — handles encapsulated, callers never touching them); never expose raw handles across module boundaries (opaque timer tokens — duality invisible to consumers).

**Runnable example** — duality contained (good vs bad, `tsc --strict`):

```typescript
// good — encapsulated delay (handles hidden — callers timing, never handling)
// (checker runs esnext+dom libs: setTimeout→number here; Node services see Timeout — wrapper hiding both)
export {}; // module marker (top-level await below needs module scope)
function delay(ms: number): Promise<void> {
  return new Promise<void>((resolve) => { setTimeout(resolve, ms); }); // handle encapsulated (never escaping — duality contained in one function)
}
await delay(1);
console.log("delayed"); // delayed — timers wrapped (handles opaque — environment duality invisible to callers)
// bad — raw handles across boundaries (Timeout-vs-number leaking per module — clearTimeout no-ops cross-runtime)
// fix — delay-style wrappers (handles encapsulated — one containment point per codebase, not per call)
```

```typescript
// good — cancellable delay (signal-composed — 2.2 mechanics on encapsulated timers)
export {}; // module marker (consistent module scope across fences)
function delaySignal(ms: number, signal?: AbortSignal): Promise<void> {
  return new Promise<void>((resolve, reject) => {
    const h = setTimeout(resolve, ms); // handle local (clearable on abort — containment enabling cleanup)
    signal?.addEventListener("abort", () => { clearTimeout(h); reject(signal.reason); }, { once: true }); // abort clearing (loser cleanup — 2.1 rule at timer scale)
  });
}
await delaySignal(1);
console.log("bounded-delay"); // bounded-delay — timers cancellable (encapsulation + signals composed)
// bad — unabortable sleeps (delay without signals — shutdowns waiting out full sleeps, deployments slow)
// fix — signal-accepting delays (every sleep abortable — shutdowns immediate, deployments fast)
```

**Common confusion** — "`ReturnType<typeof setTimeout>` is portable" — it resolves *per lib-set* (number under DOM, Timeout under Node — portable-looking, environment-pinned; wrappers genuinely portable). "`clearTimeout` always works" — works only with same-environment handles (cross handles no-op-ing silently — 5.1 incident 3's mechanism). "timers need no abstraction" — every raw handle is a duality leak (one wrapper per codebase — abstraction proportional to blast radius).

**Performance note** — timer allocation one handle + queue entry (microseconds — thousands concurrent fine; millions pooled/scheduled hierarchically); `unref`ed timers excluding process lifetime (servers exiting cleanly — lifecycle without leaks).

**Mentor note** — cross-runtime review: raw `setTimeout` handles outside timer utilities are duality leaks (wrap-or-justify — the review question per timer call).

### 2) **`queueMicrotask` vs `setImmediate` vs `setTimeout`** (scheduling tiers by intent)

**Definition** — three tiers: `queueMicrotask(cb)` (microtask queue — runs before next macrotask/render, DOM+Node universal); `setImmediate(cb)` (Node-only — check phase, after I/O callbacks, before timers); `setTimeout(cb, 0)` (macrotask — clamped ≥1ms, render may interleave in browsers). Ordering: microtasks drain fully between macrotasks (starvation risk — see below); immediates/macrotasks yield to the loop (starvation-free, slower).

**What problem it solves / history** — `setTimeout(0)` for everything (deferral granularity single-tier — microtask-suitable continuations paying macrotask latency + render interleaving; I/O-phase work missing its phase): tier selection matching intent (continuations → microtasks; I/O-phase → immediates; delayed/visible → timeouts) — latency and ordering correct by construction.

**Modern guidance** — continuations/deferred-cleanup → `queueMicrotask` (universal, fastest deferral); Node I/O-phase scheduling → `setImmediate` (streams/pipes turn-taking); human-perceptible delays/debounce → `setTimeout` (clamped, render-aware); never chain microtasks unboundedly (drain-starvation — I/O never running; chunk with macrotask yields per part 3 streaming).

**Runnable example** — tiers by intent (good vs bad, `tsc --strict`):

```typescript
// good — microtask continuations (fastest deferral — ordering before macrotasks)
export {}; // module marker (top-level await below needs module scope)
const order: string[] = [];
queueMicrotask(() => { order.push("micro"); }); // microtask tier (drains before timers — continuation intent)
await new Promise<void>((resolve) => setTimeout(resolve, 1)); // macrotask tier (yields to loop — test synchronization)
order.push("after");
console.log(order.join(",")); // micro,after — tier ordering (microtasks first — intent-typed scheduling)
// bad — setTimeout-0 continuations (macrotask latency + render interleaving for continuation work)
// fix — queueMicrotask (continuation tier — fastest correct deferral, universal)
```

```typescript
// good — starvation-bounded chains (macrotask yields inside long microtask sequences)
export {}; // module marker (consistent module scope across fences)
async function drainBounded(total: number): Promise<number> {
  let done = 0;
  while (done < total) {
    done++; // microtask-speed work (fast iterations — draining quickly)
    if (done % 100 === 0) { await new Promise<void>((r) => setTimeout(r, 0)); } // macrotask yield (loop breathing — I/O unstarved per 100)
  }
  return done;
}
console.log(await drainBounded(250)); // 250 — bounded draining (starvation prevented — yields scheduled by count, not by hope)
// bad — unbounded microtask chains (recursive queueMicrotask — I/O starved, servers unresponsive under load)
// fix — counted yields (macrotask breathing per N — starvation structurally impossible)
```

**Common confusion** — "`setImmediate` equals `setTimeout(0)`" — different phases (immediate: check-phase, pre-timer; timeout: timer-phase, clamped — ordering differing under I/O load; plus `setImmediate` Node-only). "microtasks always faster" — faster per deferral, starving at volume (throughput vs fairness — tiers trading off, not ranking). "queueMicrotask needs no lib" — needs `DOM` or `@types/node` (missing-lib TS2304 per 3.1 — configuration before code).

**Performance note** — microtask hop ~tens of nanoseconds (fastest deferral); macrotask hop ~microseconds-to-milliseconds (clamped, phase-queued); starvation cost unbounded (I/O never served — the tier-misuse catastrophe).

**Mentor note** — deferral review: "which tier, and why?" (continuation/phase/delay — intent stated per deferral; `setTimeout(0)` defaults justifying themselves).

### 3) **Unref/drain patterns** (process-lifetime management without leaks)

**Definition** — *lifetime management*: Node `Timeout.unref()` (timer not keeping the event loop alive — process exiting despite pending timers) / `.ref()` (re-arming lifetime); *draining*: awaiting in-flight work before exit (`process.on("SIGTERM")` → stop-accepting → `await drain()` → `process.exit` — graceful shutdown typed as phases). Types: `unref(): Timeout` (chainable — handle retained); drain contracts `() => Promise<void>` (shutdown phases awaited — 17/2.3 floats structurally prevented).

**What problem it solves / history** — servers hanging on deploy (intervals keeping loops alive — SIGTERM ignored until orchestrator SIGKILLs, in-flight requests severed): `unref`ed housekeeping timers (metrics flushes, cache sweeps — background work never blocking exit) + SIGTERM drain phases (requests completing, then exit — graceful shutdown as typed phases, see 20/production).

**Modern guidance** — `unref` all recurring housekeeping timers (intervals never blocking exit — foreground work alone holding lifetime); implement SIGTERM drains (stop → drain → exit — three phases, each awaited); test shutdown paths (17/2.3 doubles driving SIGTERM handlers — drains asserted, not hoped).

**Runnable example** — lifetime honesty (good vs bad, `tsc --strict`):

```typescript
// good — drain phases typed (stop, drain, exit — graceful shutdown as phases)
export {}; // module marker (top-level await below needs module scope)
let inFlight = 0;
async function trackedWork(): Promise<string> {
  inFlight++; // admission counted (drain observing — work inventoried)
  await new Promise<void>((r) => setTimeout(r, 1));
  inFlight--;
  return "done";
}
async function drain(): Promise<void> {
  while (inFlight > 0) { await new Promise<void>((r) => setTimeout(r, 1)); } // drain awaiting (in-flight completing — exit after, not during)
}
console.log(await trackedWork(), await drain().then(() => "drained")); // done drained — phased shutdown (requests completing before exit)
// bad — exit-during-flight (process.exit mid-request — severed responses, corrupted partial writes)
// fix — drain phases (stop-accepting → await-drain → exit — graceful as typed phases)
```

```typescript
// good — housekeeping unrefed (background timers never blocking exit — lifetime honest)
// (Node-only API illustrated as documented pattern — unref on Timeout handles where @types/node present:
// const sweep = setInterval(() => { /* cache sweep */ }, 60_000); (sweep as unknown as { unref?: () => void }).unref?.();
// — housekeeping unrefed (exit unblocked — foreground work alone holding lifetime))
export {}; // module marker (consistent module scope across fences)
console.log("lifetime-honest"); // lifetime-honest — background timers documented (unref pattern — exit never hostage to housekeeping)
// bad — refed intervals forever (hourly sweeps holding loops — deploys SIGKILLed after timeout, requests severed)
// fix — unref housekeeping (background work lifetime-free — exit immediate when foreground drains)
```

**Common confusion** — "`unref` cancels timers" — `unref` detaches *lifetime* (timer still fires while the loop lives — exit-blocking removed, scheduling unchanged). "drains need frameworks" — drains need *counting* (in-flight inventory + phase loop — 15 lines; frameworks packaging the pattern, not inventing it). "browser code needs unref" — browsers lack loop-lifetime (page lifecycle instead — `unref` Node-only; visibility/pagehide handlers the browser analogue).

**Performance note** — `unref` zero runtime cost (flag on the handle); drain latency = slowest in-flight op (bounded by timeouts per 2.2 — drains composed with bounds, never unbounded).

**Mentor note** — deploy-readiness: "SIGTERM path?" (stop/drain/exit demoed in review — undemoed shutdowns failing at 3am, not at 3pm).
