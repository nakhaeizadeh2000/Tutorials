## 3.3. Timers queues and the event-loop type view

A timer handle identifies a scheduled operation. Its TypeScript type depends on the declarations selected for the host; that type does not change the runtime handle or guarantee when its callback runs. Scheduling order, cancellation and process lifetime are separate concerns.

Use **TypeScript 7.0.2**, **Node.js 20.20.2** and **@types/node 20.19.43**, verified 2026-10-17. Work in a fresh directory with the package.json from [the library-selection fixture](<./3.1. lib settings and built-in async types.md>) and run npm install. The examples below execute Node timers and child processes; they do not simulate a browser or implement service shutdown.

### 1) **Inspect the selected handle type**

With only DOM declarations, the global setTimeout call returns number. With the pinned Node declarations it returns NodeJS.Timeout, an object with ref, unref and hasRef methods. Loading both does not automatically produce a number | Timeout union. In this fixture, the selected call and ReturnType both resolve to NodeJS.Timeout. Overload order matters; inspect actual declarations rather than deriving a union from the existence of two hosts.

Save:

```typescript
// file: node-handle.mts
import { setTimeout as nodeTimeout } from "node:timers";
const handle: NodeJS.Timeout = setTimeout(() => {}, 100);
const same: ReturnType<typeof setTimeout> = handle;
const imported: ReturnType<typeof nodeTimeout> = handle;
handle.unref();
handle.ref();
clearTimeout(same);
// const numeric: number = handle;
```

Run `tsc --strict --target es2022 --module nodenext --types node --lib es2022 --noEmit node-handle.mts`, then repeat with lib es2022,dom. Both pass. Uncomment numeric: both reject the assignment. Importing the Node timer explicitly identifies the intended host; ReturnType is also useful for a handle local to the environment being compiled. Neither technique promises identical declarations for downstream consumers using other hosts.

For contrast, isolate DOM declarations:

```json
// file: tsconfig.dom-only.json
{
  "compilerOptions": {
    "strict": true, "target": "ES2022", "module": "NodeNext",
    "lib": ["ES2022", "DOM"], "types": [], "outDir": "dom-out"
  },
  "files": ["dom-handle.mts"]
}
```

```typescript
// file: dom-handle.mts
export let fired = false;
export const handle: number = setTimeout(() => { fired = true; }, 10);
clearTimeout(handle);
```

Compile with `tsc -p tsconfig.dom-only.json`. This is a deliberate declaration/runtime mismatch when run in Node: the emitted handle is still an object. Crucially, clearTimeout receives that original object and cancels it. An annotation or `as unknown as number` assertion does not convert an object into a number or make cancellation silently fail. Node also supports its own same-thread numeric timer identifiers, as documented in its [versioned timer API](https://github.com/nodejs/node/blob/v20.20.2/doc/api/timers.md#timeoutsymboltoprimitive).

Expose raw handles when the caller legitimately owns a host-specific timer lifecycle. Use a stop callback or higher-level operation when that better expresses ownership across a shared API. A wrapper is a design choice, not automatic portability: its implementation, cancellation behavior and supported hosts still need tests.

The [executed cancellable-wait owner](<../../../17 Testing Types/sections/2. Typed Test Doubles/2.3. Testing async and error paths with types.md>) covers pre-aborted signals, mid-wait abort, timer clearing and listener removal on completion. Reuse that complete contract rather than copying a sleep helper that adds an abort listener but never removes it after normal completion. Some bounded waits need no external cancellation; others are part of a cancellable request or shutdown lifecycle.

### 2) **Test scheduling with an explicit context**

queueMicrotask schedules a microtask, while Node setImmediate schedules a check-phase callback and setTimeout schedules a timer. Their callback types do not encode ordering relative to another operation. A timer delay is a scheduling threshold, not an exact completion time. Node's delay normalization differs from browser timer rules.

There is no universal entry-point rule that setImmediate beats setTimeout(0). The [Node event-loop guide](https://nodejs.org/learn/asynchronous-work/event-loop-timers-and-nexttick) distinguishes main-module scheduling from scheduling both inside an I/O callback: in the latter case, the immediate runs first. Node 20 also changed timer processing with libuv 1.45; old phase diagrams need that qualification.

Recursive microtasks can delay timers and I/O. Yielding through a later event-loop phase can let other work run, but does not prove fairness, a response-time bound or absence of starvation throughout an application. Choose a scheduler for its required semantics and supported host. Avoid choosing one solely because it sounds fastest. setImmediate is a Node API, while callback availability for queueMicrotask still depends on the actual runtime.

Save the verification file below. Its first scheduling observation uses a microtask queued before a timer. Its second schedules both operations inside an actual file-read callback. It deliberately makes no assertion about immediate-versus-timeout order at module startup.

### 3) **Observe unref separately from cancellation and draining**

A referenced Node timer can keep the event loop alive. Unref removes that requirement; ref restores it. Unref does not clear the timer, and its callback may run while other work keeps the process alive. Required cleanup or writes must not depend on a timer that the process may abandon.

The child-process cases below observe a referenced timer, an unreferenced timer, an explicitly cleared timer and an unreferenced timer allowed to fire while another timer keeps the process alive. The [Node 20 timer documentation](https://github.com/nodejs/node/blob/v20.20.2/doc/api/timers.md#timeoutunref) defines this lifetime distinction.

```javascript
// file: verify.mjs
import assert from "node:assert/strict";
import { readFile } from "node:fs";
import { spawnSync } from "node:child_process";
import * as domTyped from "./dom-out/dom-handle.mjs";
assert.equal(typeof domTyped.handle, "object");
await new Promise(resolve => setTimeout(resolve, 30));
assert.equal(domTyped.fired, false);
const timer = setTimeout(() => { throw new Error("cleared timer fired"); }, 100);
assert.equal(timer.hasRef(), true);
assert.equal(timer.unref(), timer);
assert.equal(timer.hasRef(), false);
assert.equal(timer.ref(), timer);
assert.equal(timer.hasRef(), true);
clearTimeout(timer);
const order = [];
queueMicrotask(() => order.push("micro"));
await new Promise(resolve => setTimeout(() => { order.push("timer"); resolve(); }, 0));
assert.deepEqual(order, ["micro", "timer"]);
const ioOrder = [];
await new Promise((resolve, reject) => {
  readFile(new URL(import.meta.url), error => {
    if (error) { reject(error); return; }
    setTimeout(() => { ioOrder.push("timer"); resolve(); }, 0);
    setImmediate(() => ioOrder.push("immediate"));
  });
});
assert.deepEqual(ioOrder, ["immediate", "timer"]);
function child(body) {
  const result = spawnSync(process.execPath, ["--input-type=module", "-e", body], {
    encoding: "utf8", timeout: 2000,
  });
  assert.ifError(result.error);
  assert.equal(result.status, 0, result.stderr);
  return result.stdout.trim().split("\n");
}
const makeTimer = 'const timer = setTimeout(() => console.log("fired"), 100);';
assert.deepEqual(child(makeTimer + 'console.log("ready");'), ["ready", "fired"]);
assert.deepEqual(child(makeTimer + 'timer.unref(); console.log("ready");'), ["ready"]);
assert.deepEqual(child(makeTimer + 'clearTimeout(timer); console.log("ready");'), ["ready"]);
assert.deepEqual(child(makeTimer + 'timer.unref(); setTimeout(() => console.log("kept alive"), 150);'),
  ["fired", "kept alive"]);
console.log("handle cancellation, scheduling context and process lifetime passed");
```

Run `node verify.mjs` after the DOM-only build. Its final message means those assertions passed. No elapsed-time performance threshold is asserted; the child timeout only bounds a broken or hung test process. Removing clearTimeout from dom-handle.mts still compiles, but the fired assertion detects the missing cancellation after rebuilding. Replacing timer.unref() with timer.ref() in the child case causes an unexpected fired line.

Graceful service shutdown requires a separate admission policy, inventory of active operations, settlement/error handling and cleanup or deadline policy. Promise<void> alone cannot prove those steps, and unref does not perform them. The [bounded mapper](<../2. Combinators and Cancellation/2.3. Sequential vs parallel patterns and tuple typing.md>) tests an actual drain of already-started callbacks; that fixture explicitly says an operation that never settles can prevent completion. This page does not test SIGTERM, a server drain or forced process exit.

### 4) **Common confusion**

Changing a handle's annotation does not change its identity or cancelability at runtime. Selecting both DOM and Node declarations also does not mean every call returns a union. Inspect the selected call, and keep host-specific methods within code whose supported runtime supplies them.

Unref and clearTimeout solve different problems. Unref permits process exit; clearing cancels the scheduled callback. Awaiting a promise is another distinction: it describes how code observes completion, but a pending promise without active host work does not independently keep Node alive. A shutdown deadline can stop waiting without stopping an operation that ignores cancellation.

### 5) **Performance note**

Timers, callbacks, captured values and scheduling all consume resources. Unref changes process lifetime rather than making a timer free or releasing its captured data. Delayed callbacks can run later than requested because of other work and host scheduling. Measure actual timer volume, retained state, loop delay and shutdown completion; the fixture establishes behavior, not nanosecond costs or a universally safe timer count.
