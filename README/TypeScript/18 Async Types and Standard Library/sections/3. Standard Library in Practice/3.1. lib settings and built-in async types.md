## 3.1. lib settings and built-in async types

A declaration tells TypeScript what an API promises. It does not install that API. Keep three questions separate: which names the checker can see, which syntax the compiler transforms, and which operations the deployed runtime implements. An async program can pass the first two checks and still fail the third.

These examples use **TypeScript 7.0.2** and **Node.js 20.20.2**, verified 2026-10-17. Use a fresh directory. The resource example uses TypeScript's emitted helpers, rather than asking Node 20 to parse using syntax directly.

### 1) **Select declarations for the actual host**

The [lib option](https://www.typescriptlang.org/tsconfig/lib.html) selects bundled declaration files. ES2022 describes that edition's built-in APIs; DOM adds browser interfaces such as document. ESNext changes with compiler releases, so it is not a fixed runtime compatibility promise. Explicit lib settings can differ from the syntax target when the runtime or polyfills provide newer APIs.

@types/node is a separately installed declaration package, not a lib entry. The types option controls automatic inclusion of named type packages; it does not install them, and imports can still bring declarations into the program. Modern Node declarations include APIs such as fetch and AbortController without requiring the entire DOM surface. Match declaration versions to the supported host, then test that host.

Save these files:

```json
// file: package.json
{
  "private": true,
  "devDependencies": { "@types/node": "20.19.43" }
}
```

```json
// file: tsconfig.dom.json
{
  "compilerOptions": {
    "strict": true, "target": "ES2022", "module": "NodeNext",
    "lib": ["ES2022", "DOM"], "types": [], "outDir": "dom-out"
  },
  "files": ["api.mts", "browser.mts"]
}
```

```json
// file: tsconfig.node.json
{
  "compilerOptions": {
    "strict": true, "target": "ES2022", "module": "NodeNext",
    "lib": ["ES2022"], "types": ["node"], "outDir": "node-out"
  },
  "files": ["api.mts", "node-api.mts"]
}
```

```typescript
// file: api.mts
export const aborted = new AbortController().signal.aborted;
```

```typescript
// file: browser.mts
console.log(document.title);
```

```typescript
// file: node-api.mts
import { aborted } from "./api.mjs";
import { version } from "node:process";
console.log(aborted, typeof fetch, version);
```

Run npm install, then `tsc -p tsconfig.dom.json`. Both files compile, but `node dom-out/browser.mjs` fails with ReferenceError because document is absent. Adding DOM only supplied a declaration. Run `tsc -p tsconfig.node.json` and `node node-out/node-api.mjs`: output starts with `false function` and identifies Node v20.20.2.

For a controlled missing-declaration test, change the DOM configuration's lib to only ES2022 while keeping types empty. Compilation reports missing AbortController, document and console. Restore DOM afterward. This isolates the declaration choice from implicitly discovered packages. In an actual project, investigate effective configuration, selected packages, spelling, and runtime support before deciding whether the right repair is declarations, a runtime implementation, or different code.

Syntax emission is separate. Save:

```typescript
// file: downlevel.mts
async function* values(): AsyncGenerator<number, void, unknown> {
  yield 1;
  yield 2;
}
export async function collect(): Promise<number[]> {
  const output: number[] = [];
  for await (const value of values()) output.push(value);
  return output;
}
```

Run `tsc --strict --target es2015 --module nodenext --lib es2018 --outDir older-out downlevel.mts`, then `node --input-type=module -e 'import("./older-out/downlevel.mjs").then(async m => console.log(await m.collect()))'`. The result is [1, 2]. Async iteration does not universally require an ES2018 emit target; the compiler transforms this example for ES2015. There is no compiler option named downlevelAsyncIteration. Declarations and emitted helpers still depend on suitable runtime facilities, including Promise and the iterator symbols.

### 2) **Read result declarations without inventing guarantees**

In the installed compiler, PromiseSettledResult is declared in lib.es2020.promise.d.ts. It is a union distinguished by status: fulfillment carries value; rejection carries reason, declared any. AggregateError and its errors array are declared in lib.es2021.promise.d.ts, whose errors elements are also any. Moving such a value into an unknown variable forces validation before use; the declaration itself does not establish an error class.

The [combinator fixture](<../2. Combinators and Cancellation/2.1. all race allSettled any typed precisely.md>) actually checks both shapes. Promise.any rejects with AggregateError when every input rejects, with reasons in input order. Promise.all ordinarily rejects with the first observed reason; it does not collect all failures into AggregateError for you.

Consume the settled union directly when its status/value/reason contract fits. Mapping it into an application's [Result type](<../../../15 Strictness Errors and Validation/sections/2. Error Values and Hierarchies/2.1. Error as value Result Ok Err patterns.md>) can also be useful at a deliberate boundary. A cast to Result<T, MyError> cannot validate that an arbitrary rejection is MyError. Define that validation or normalization explicitly. Avoid unnecessary translations, but do not turn one representation into a universal rule.

### 3) **Make scope cleanup observable**

TypeScript added using and await using support in [5.2](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-2.html). A Disposable has a Symbol.dispose method returning void. AsyncDisposable has a Symbol.asyncDispose method returning **PromiseLike<void>**. Using registers a value for disposal on scope exit; await using awaits the disposal result. Await using can also accept a synchronous disposable.

For multiple successful acquisitions, cleanup runs in reverse registration order, including ordinary early return and thrown-error paths. Acquisition must have succeeded before there is a resource to dispose. This is a cleanup protocol: its guarantee depends on what the method actually does and whether execution reaches scope exit. It cannot force a blocked operation to settle, survive process termination, prevent escaped aliases, or make every resource acquisition use this syntax.

Save:

```typescript
// file: resources.mts
export function scoped(log: string[], fail: boolean): string {
  function acquire(name: string): Disposable {
    log.push("acquire:" + name);
    return { [Symbol.dispose]() { log.push("release:" + name); } };
  }
  using first = acquire("first");
  using second = acquire("second");
  log.push("body");
  if (fail) throw new Error("body failed");
  return "ok";
}

export async function flush(
  log: string[], gate: Promise<void>, started: () => void,
): Promise<void> {
  const resource: AsyncDisposable = {
    async [Symbol.asyncDispose]() {
      log.push("cleanup:start");
      started();
      await gate;
      log.push("cleanup:end");
    },
  };
  await using writer = resource;
  log.push("write");
}

export function cleanupFailure(): void {
  using resource = { [Symbol.dispose]() { throw new Error("close failed"); } };
}

export function nativeStacks(): string[] {
  return [typeof DisposableStack, typeof AsyncDisposableStack];
}
```

```javascript
// file: verify.mjs
import assert from "node:assert/strict";
import { scoped, flush, cleanupFailure, nativeStacks } from "./resource-out/resources.mjs";
const expected = ["acquire:first", "acquire:second", "body", "release:second", "release:first"];
const success = [];
assert.equal(scoped(success, false), "ok");
assert.deepEqual(success, expected);
const failure = [];
assert.throws(() => scoped(failure, true), /body failed/);
assert.deepEqual(failure, expected);
assert.throws(cleanupFailure, /close failed/);
let release;
const gate = new Promise(resolve => { release = resolve; });
let signalStarted;
const started = new Promise(resolve => { signalStarted = resolve; });
const log = [];
let finished = false;
const pending = flush(log, gate, signalStarted).then(() => { finished = true; });
await started;
// Let promise reactions run before checking that cleanup is still blocked.
await new Promise(resolve => setTimeout(resolve, 0));
assert.equal(finished, false);
assert.deepEqual(log, ["write", "cleanup:start"]);
release();
await pending;
assert.equal(finished, true);
assert.deepEqual(log, ["write", "cleanup:start", "cleanup:end"]);
assert.deepEqual(nativeStacks(), ["undefined", "undefined"]); // This exact Node 20 runtime.
assert.equal(typeof Symbol.dispose, "symbol");
assert.equal(typeof Symbol.asyncDispose, "symbol");
console.log("scope order, failure and awaited cleanup passed");
```

Compile with `tsc --strict --target es2022 --module nodenext --lib es2022,esnext.disposable --outDir resource-out resources.mts`, then run `node verify.mjs`. The final message means the assertions passed. These are instrumented resources, not actual file, lock or transaction implementations. The gate makes awaited cleanup observable without asserting a flush duration.

On this runtime the two disposal symbols exist but the stack constructors do not. Selecting ESNext.Disposable makes their names type-check; it does not create them. Emitted using helpers likewise do not install every resource-management API. Check the actual deployed runtime or explicitly supply an appropriate implementation before using stack constructors.

As a deliberate failure, remove await gate from the disposer, rebuild and rerun. The assertions detect that cleanup completed before the gate was released. Similarly, replacing using with const still type-checks but fails the release-order assertions. The checker does not require every disposable object to be registered for automatic cleanup.

Cleanup itself can fail, as cleanupFailure demonstrates. When both the body and cleanup fail, the protocol preserves both through SuppressedError; see the 5.2 explanation rather than assuming one catch receives only the body error. Await using waits for the promise returned by disposal. A disposer that starts unrelated work and fails to return or await it can still leave that work running.

### 4) **Common confusion**

A missing name can mean missing declarations, an incorrect project boundary, an unsupported runtime API, or a mistake in the code. Adding every lib can hide the mismatch. Conversely, a newer lib with an older syntax target can be appropriate when the runtime supplies the declared API.

Disposable describes a method contract, not an ownership or liveness proof. Reverse disposal order helps express dependencies but does not prove freedom from deadlocks. Synchronous acquisition, asynchronous acquisition and asynchronous cleanup are separate decisions: the await before using selects awaited cleanup; an await on the initializer waits for acquisition.

### 5) **Performance note**

Declaration selection affects the compiler's program and checking work; it does not add runtime implementations. Measure compiler time for the actual project before claiming a benefit from reducing libraries. Using can add emitted helper and cleanup work. Awaited cleanup can delay scope completion, and a disposer can block indefinitely. The fixture verifies order and waiting, not latency, throughput or a fixed allocation count.

### 6) **Mentor note**

Ask a learner why browser.mts compiles but fails in Node, then why the resource example works while the stack constructors are absent. A sound explanation separates declarations, syntax transformation and runtime APIs. Have them predict both release orders and identify which returned promise owns cleanup completion. Finally remove using: compilation still passing should prompt an ownership review rather than a claim that resource safety is automatic.
