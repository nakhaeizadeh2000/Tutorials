## 3.1. lib settings and built-in async types

### 1) **`lib` selecting async surface** (esnext-asynciterable plus dom timers, missing-lib diagnosis)

**Definition** — `lib` (tsconfig compiler option — 13/3.1 pairing) selects which `.d.ts` surface the checker sees: `ESNext` (language — `Promise`, `AsyncIterable`, `Disposable`), `DOM` (browser — `fetch`, `AbortSignal`, `setTimeout→number`), `DOM.AsyncIterable`, `WebWorker`, `@types/node` (Node — timers, streams, `setTimeout→Timeout`). Missing entries produce `TS2550` (property doesn't exist on target-lib) / `TS2304` (cannot find name) — configuration errors wearing type-error costumes.

**What problem it solves / history** — copy-pasted `fetch`/`AbortSignal` code failing in Node-targeted projects (`DOM` absent — `TS2304: Cannot find name 'fetch'`), or `for await` failing pre-ES2018 targets (`TS2569` — downlevel iteration): lib mismatches misread as code bugs (hours debugging signatures that simply aren't loaded). Reading missing-lib errors as *configuration* (add the lib, don't rewrite the code) resolves the class in minutes.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), set `lib` per runtime (Node services: `ESNext` + `@types/node`, no `DOM`; edge/browser: `ESNext` + `DOM` + `DOM.AsyncIterable`; workers: `WebWorker`): minimal libs surfacing environment mistakes as errors (browser APIs in Node services failing loudly — architecture enforced by configuration). Diagnose `TS2550`/`TS2304` on stdlib names as lib gaps first (config before code, always).

**Runnable example** — lib surfaces, shown as portable fences plus a labeled config doc (good vs bad, `tsc --strict`):

```typescript
// good — AbortSignal available (DOM-or-node surface loaded — configuration, not code)
// (checker here runs with esnext+dom libs per track harness — AbortSignal resolving as configured)
const c: AbortController = new AbortController(); // configured surface (name resolving — lib providing, code consuming)
console.log(c.signal.aborted); // false — lib-selected APIs (availability declared in tsconfig, used in code)
// bad — rewriting code around TS2304 (polyfilling what a lib line provides — code compensating configuration)
// fix — read TS2304-on-stdlib as config (add the lib — minutes, not refactors)
```

```jsonc
// good — per-runtime lib selection (minimal surfaces, environment mistakes loud)
// tsconfig.node.json (labeled config doc — services): { "compilerOptions": { "lib": ["ESNext"], "types": ["node"] } }
// tsconfig.edge.json (labeled config doc — browser/edge): { "compilerOptions": { "lib": ["ESNext", "DOM", "DOM.AsyncIterable"] } }
// (Node service importing DOM fetch-with-number-timeout failing loudly — architecture as configuration)
```

```typescript
// good — target-gated async syntax (for-await needing ES2018+ downlevel support)
export {}; // module marker (consistent module scope across fences)
async function drain<T>(source: AsyncIterable<T>): Promise<T[]> {
  const out: T[] = [];
  for await (const item of source) { out.push(item); } // downlevelAsyncIteration or ES2018+ target (syntax gated by target — 13/2.3 trio-adjacent)
  return out;
}
async function* gen(): AsyncGenerator<number> { yield 1; yield 2; }
console.log(await drain(gen())); // [1,2] — gated syntax (target permitting — configuration enabling syntax, not just names)
// bad — for-await under ES2015 target (TS2569 downlevel error — syntax mistaken for a type bug)
// fix — target/lib together (syntax + names configured per runtime — 13/3.1 pairing restated for async)
```

**Common confusion** — "`lib` and `@types` are interchangeable" — `lib` ships *with* TypeScript (language + DOM surfaces); `@types/*` are DefinitelyTyped packages (Node, Jest — installed separately, versioned independently). "maximal libs are safest" — maximal libs *hide* environment mistakes (DOM in Node services compiling browser-only calls — minimal libs failing loudly is the feature). "TS2550 means old TypeScript" — TS2550 means *target/lib too low* (often fixable by config — version upgrades the second suspect, not the first).

**Performance note** — lib selection costs check-time only (larger libs = larger program — milliseconds; minimal libs marginally faster AND stricter — both axes winning).

**Mentor note** — onboarding diagnostic drill: `Cannot find name 'fetch'` → "which lib?" (config-first reflex — the five-minute fix replacing hour-long signature hunts).

### 2) **`PromiseSettledResult`/`AggregateError` shapes** (settled unions, multi-error aggregation)

**Definition** — stdlib's failure containers, read as documentation: `type PromiseSettledResult<T> = { status: "fulfilled"; value: T } | { status: "rejected"; reason: any }` (2.1 part 3's per-member union — discriminant `status`); `interface AggregateError extends Error { errors: any[] }` (many-errors-one-object — `Promise.any`'s total-rejection, `Promise.all`-with-aggregation patterns). Both read directly from `lib.es5.d.ts`/`lib.es2021.promise.d.ts` (declarations as the primary source — hover-to-definition per 16/1.1).

**What problem it solves / history** — hand-rolled settled unions (each codebase inventing `{ok, value/error}` variants incompatible across libraries — 15/2.1's `Result` vs stdlib's settled shapes confused): using stdlib shapes where stdlib produces them (combinator outputs narrowed via `status`, never remapped into bespoke unions at the boundary).

**Modern guidance** — narrow stdlib shapes in place (`status` discriminant — 07 mechanics, no remapping); reserve `Result<T, E>` (15/2.1) for *own* APIs (typed errors `E` where error classes known); convert at boundaries explicitly (settled→Result mapping functions — `reason: any` narrowed to `E` once, centrally, tested per 17/2.3).

**Runnable example** — stdlib shapes narrowed, converted once (good vs bad, `tsc --strict`):

```typescript
// good — settled narrowed in place (no remapping — stdlib shape consumed natively)
export {}; // module marker (top-level await below needs module scope)
async function flaky(id: number): Promise<string> {
  if (id === 2) throw new Error("bad:2");
  return `ok:${id}`;
}
const settled = await Promise.allSettled([flaky(1), flaky(2)]); // PromiseSettledResult<string>[] (stdlib shape — consumed natively)
const values = settled.flatMap((r) => r.status === "fulfilled" ? [r.value] : []); // discriminant narrowing (07 mechanics — fulfilled values extracted)
console.log(values.join(",")); // ok:1 — native consumption (shapes read from lib, narrowed in place)
// bad — remapping settled into bespoke unions (translation layers per call site — shape churn, mapping bugs)
// fix — narrow in place (stdlib shapes first-class — Result reserved for own APIs)
```

```typescript
// good — AggregateError carrying many failures (total-rejection typed — errors enumerated)
export {}; // module marker (consistent module scope across fences)
async function down1(): Promise<string> { throw new Error("d1"); }
async function down2(): Promise<string> { throw new Error("d2"); }
try {
  await Promise.any([down1(), down2()]); // all reject (total failure — AggregateError thrown)
  console.log("unexpected");
} catch (e) {
  const errs = e instanceof AggregateError ? e.errors.length : -1; // errors[] enumerated (multi-failure carried — counted, logged, alerted)
  console.log(`all-failed:${errs}`); // all-failed:2 — aggregation typed (many errors, one object — total failures inspectable)
}
// bad — any-total-failure handling (catch counting one error — N-1 failures invisible, alerts understated)
// fix — AggregateError.errors (failures enumerated — total-failure diagnostics complete)
```

**Common confusion** — "settled `reason` is typed" — `reason: any` (executor legacy per 1.1 — narrow via `instanceof` before use). "`AggregateError` needs construction" — usually *received* (any/all rejections — constructed manually only for fan-in aggregation patterns). "Result replaces settled" — `Result<T,E>` types *errors* (`E` known); settled carries *any* (unknown failures — different strictness, different homes).

**Performance note** — settled wrappers allocate per member (one object — negligible vs bulk I/O); `AggregateError` one object per total-failure (rare path — cost irrelevant).

**Mentor note** — declaration-reading drill: hover `allSettled`, jump to `PromiseSettledResult` definition (16/1.1 navigation — stdlib declarations as the primary async reference, not blog posts).

### 3) **`Disposable`/`AsyncDisposable` with `using`** (explicit resource management typed)

**Definition** — explicit resource management (ES2024, TS 5.2+): `interface Disposable { [Symbol.dispose](): void }` / `AsyncDisposable { [Symbol.asyncDispose](): Promise<void> }` — `using x = acquire()` disposing at scope exit (sync), `await using x = acquire()` awaiting async disposal (async). Types enforcing cleanup contracts (acquire-typed resources disposable only via declared methods — unreleased resources checker-visible).

**What problem it solves / history** — `try/finally` cleanup repeated per site (release calls forgotten, disposal order inverted, async cleanup unawaited — resource leaks as the norm): `using` structuralizes disposal (scope-exit guaranteed, order LIFO, async awaited — cleanup as syntax, not discipline).

**Modern guidance** — adopt `using` for scoped resources (files, locks, connections — acquire/dispose pairs becoming declarations); `await using` for async teardown (flushed writers, committed transactions — disposal awaited, not floated — 17/2.3 float discipline satisfied by syntax); keep `try/finally` for conditional cleanup (non-scope-shaped lifetimes — syntax where it fits, explicit where it doesn't).

**Runnable example** — disposal as syntax (good vs bad, `tsc --strict`):

```typescript
// good — sync disposal at scope exit (cleanup guaranteed — LIFO, exception-safe)
export {}; // module marker (consistent module scope across fences)
class Lock implements Disposable {
  constructor(private name: string) { console.log(`acquire:${name}`); }
  [Symbol.dispose](): void { console.log(`release:${this.name}`); } // disposal declared (contract — scope exit invoking)
}
{
  using _guard = new Lock("db"); // disposed at block exit (guaranteed — early returns/throws included)
  console.log("critical-section"); // acquire → section → release (order structural — LIFO by declaration)
}
// bad — manual release calls (forgotten on early returns — locks held, deadlocks under error paths)
// fix — using declarations (cleanup as syntax — scope exit disposing, always)
```

```typescript
// good — async disposal awaited (flushed teardown — floats impossible by syntax)
export {}; // module marker (consistent module scope across fences)
class Writer implements AsyncDisposable {
  async [Symbol.asyncDispose](): Promise<void> { console.log("flushed"); } // async teardown (awaited at scope exit — 17/2.3 floats structurally prevented)
  write(s: string): void { console.log(`write:${s}`); }
}
async function run(): Promise<void> {
  await using w = new Writer(); // awaited disposal (scope exit awaiting — floats unrepresentable)
  w.write("row");
}
await run(); // write → flushed (teardown awaited — async cleanup as syntax, not discipline)
// bad — floating close() calls (unflushed writes lost — async cleanup raced, the 17/2.3 float class)
// fix — await using (disposal awaited structurally — two keywords deleting a bug class)
```

**Common confusion** — "`using` replaces try/finally" — `using` covers *scope-shaped* lifetimes (acquire-use-release blocks); conditional/complex lifetimes still need `try/finally` (syntax where it fits — explicit where it doesn't). "disposal order irrelevant" — order is LIFO (reverse declaration — lock ordering deadlocks avoided structurally). "AsyncDisposable needs esnext" — needs `lib: ESNext.Disposable` (or ESNext — 13/3.1 pairing; missing-lib TS2550 diagnosing per part 1).

**Performance note** — disposal adds one scope-exit call (sync) / one awaited call (async) — linear in scopes (negligible vs resource lifetimes); ordering LIFO costs nothing (declaration order reversed — compile-time).

**Mentor note** — resource-review: acquire/dispose pairs without `using` need justification (syntax-first — manual cleanup the exception, not the norm, from TS 5.2 onward).
