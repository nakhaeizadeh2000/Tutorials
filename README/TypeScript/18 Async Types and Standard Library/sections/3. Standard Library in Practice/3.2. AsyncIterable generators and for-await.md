## 3.2. AsyncIterable generators and for-await

### 1) **`AsyncGenerator<T, TReturn, TNext>` anatomy** (yield send return channels)

**Definition** — `interface AsyncGenerator<T = unknown, TReturn = any, TNext = any> extends AsyncIterator<T, TReturn, TNext>` — three channels: `T` (yielded values — `yield v` producing), `TReturn` (`return v` completing — the generator's eventual value), `TNext` (`next(v)` sending values *in* — bidirectional communication). Defaults `unknown`/`any`/`any` (annotate all three in public contracts — defaults loosening silently).

**What problem it solves / history** — callback-pulled streams (EventEmitter wiring per consumer — backpressure manual, cleanup ad-hoc, types any-threaded): generators structuralize pull-streams (consumer pacing via `next()`, cleanup via `return()`/`throw()`, all three channels typed — backpressure by protocol, not by discipline).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), annotate generator channels explicitly (`AsyncGenerator<Row, void, void>` — yields/returns/sends each stated); keep generators pure-ish (yield computed values — I/O at boundaries, testable cores); prefer `for await` consumption (protocol-driven — manual `.next()` loops only for bidirectional sends).

**Runnable example** — three channels typed (good vs bad, `tsc --strict`):

```typescript
// good — channels annotated (yields/return/sends each stated — no silent any)
export {}; // module marker (top-level await below needs module scope)
async function* pages(): AsyncGenerator<number[], void, void> {
  yield [1, 2]; // T (yielded — number[] per page)
  yield [3]; // T again (channel consistent — the generator's element contract)
} // TReturn void (no return value — completion bare); TNext void (no sends accepted)
const collected: number[] = [];
for await (const page of pages()) { collected.push(...page); } // consumption protocol (for-await driving — backpressure by awaiting)
console.log(collected.join(",")); // 1,2,3 — channels flowing (yields collected — return/send absent by annotation)
// bad — unannotated generators (AsyncGenerator<any, any, any> — channels any-threaded, sends unnoticed)
// fix — three-parameter annotations (channels declared — loosening visible, sends deliberate)
```

```typescript
// good — bidirectional sends typed (TNext carrying queries inward — protocol explicit)
export {}; // module marker (consistent module scope across fences)
async function* echo(): AsyncGenerator<string, void, string> {
  let incoming = "start";
  while (true) {
    const next: string = incoming; // TNext received (send channel typed — queries flowing inward)
    incoming = yield `echo:${next}`; // T yielded (responses flowing outward — channels distinct)
  }
}
const e = echo();
console.log((await e.next("hello")).value); // echo:start — first send starting (protocol: sends query, yields answer)
// bad — any-typed sends (next(anything) — protocol unenforced, queries unshaped)
// fix — TNext annotations (inward channel shaped — bidirectional protocols reviewed like APIs)
```

**Common confusion** — "generators are async functions" — generators are *pausable* (yields suspending — multiple values over time); async functions are *eventual* (one value, once — 1.3 contracts). "for-await needs arrays" — for-await needs `Symbol.asyncIterator` (protocol, not array — streams, queues, pagers all consumable). "return values unusable" — `TReturn` arrives via the final `{ done: true, value }` (for-await *discards* it — manual `.next()` loops reading returns where they matter).

**Performance note** — generator suspension allocates per yield (frame capture — microseconds; millions of yields chunked per part-3 streaming guidance); for-await backpressures naturally (consumer pacing — producers suspended, memory flat).

**Mentor note** — channel-annotation review: bare `AsyncGenerator` (defaults any — rejected; three params stated — merged).

### 2) **`for await...of` consumption** (async iteration protocol, backpressure by awaiting)

**Definition** — `for await (const x of source)` desugars to `source[Symbol.asyncIterator]()` acquisition + repeated `await iterator.next()` + `return()` on abrupt exit (break/throw triggering cleanup — disposal protocol per 3.1's `using` philosophy). Backpressure: the producer advances only when the consumer awaits (pull pacing — no buffering beyond one yielded value, memory flat regardless of stream length).

**What problem it solves / history** — push-stream overload (data events firing regardless of consumer readiness — buffering unbounded, OOM on fast producers/slow consumers): pull iteration paces production to consumption (backpressure structural — the protocol, not the programmer, throttling).

**Modern guidance** — consume streams with `for await` (protocol-driven — cleanup automatic on break); break early freely (`return()` invoked — resources released, see 3.1 disposal); never collect unbounded streams into arrays without bounds (streaming transforms per part 3 — arrays where N known-small, pipelines where N huge).

**Runnable example** — paced consumption (good vs bad, `tsc --strict`):

```typescript
// good — for-await pacing (producer advancing per consumer await — backpressure structural)
export {}; // module marker (top-level await below needs module scope)
async function* count(n: number): AsyncGenerator<number, void, void> {
  for (let i = 0; i < n; i++) { yield i; } // yields pacing (suspended until next() — production throttled by consumption)
}
let sum = 0;
for await (const v of count(3)) { sum += v; } // paced consumption (one value buffered — memory flat at any N)
console.log(sum); // 3 — pull pacing (protocol throttling — no buffering, no OOM)
// bad — push-event buffering (data events queueing unbounded — fast producers OOMing slow consumers)
// fix — for-await (pull protocol — production paced to consumption, structurally)
```

```typescript
// good — early break releasing (return() on abrupt exit — cleanup automatic)
export {}; // module marker (consistent module scope across fences)
let released = false;
async function* resource(): AsyncGenerator<number, void, void> {
  try { yield 1; yield 2; } finally { released = true; } // finally as return()-handler (cleanup on break — disposal protocol)
}
for await (const v of resource()) { if (v === 1) break; } // break triggering return() (producer finalized — resources released)
console.log(released); // true — abrupt-exit cleanup (breaks finalizing — leaks structurally prevented)
// bad — manual next() loops without return() (abandoned generators — resources held, producers suspended forever)
// fix — for-await (cleanup protocol automatic — manual loops only for bidirectional sends per part 1)
```

**Common confusion** — "for-await buffers everything" — for-await buffers *one* value (pull pacing — arrays buffering everything only when you collect into them). "break leaks" — break invokes `return()` (cleanup protocol — `finally` blocks running; leaks only in manual loops skipping `return()`). "for-await works on promises" — for-await needs async-iterables (arrays of promises need `Promise.all` per 2.3 — different shapes, different consumption).

**Performance note** — per-item overhead one `next()` promise + microtasks (microseconds per item — millions of items chunked/batched per part 3; small streams unbothered).

**Mentor note** — stream-consumption review: "for-await or manual?" (for-await default — manual only for TNext sends; abandoned manual iterators flagged like leaked handles).

### 3) **Sync/async generator choice** (push-vs-pull, chunked streams, Promise-array comparison)

**Definition** — the decision table: sync `Generator<T>` (CPU-bound sequences — ranges, traversals, parsers; zero async overhead); `AsyncGenerator<T>` (I/O-bound sequences — pages, sockets, queues; awaits per item); `Promise<T[]>` (bounded batches — N known-small, random access needed). Chunked streams (`AsyncGenerator<T[]>` — pages/batches yielded — per-chunk overhead amortized, backpressure preserved) bridging async iteration and batching at scale.

**What problem it solves / history** — `Promise<Row[]>` for million-row exports (full buffering — OOM; random access unused): chunked async generators stream bounded memory (pages yielded, consumed, released — throughput without buffering), chosen by the table instead of by habit.

**Modern guidance** — sync generators for computed sequences (no I/O — async machinery pure overhead); async generators for I/O sequences (awaits pacing — backpressure structural); `Promise<T[]>` for bounded results (small N, indexed access); chunked `AsyncGenerator<T[]>` for huge N (pages amortized — the scale bridge).

**Runnable example** — choice by shape (good vs bad, `tsc --strict`):

```typescript
// good — sync generator for computed sequences (zero async overhead — machinery matched to work)
export {}; // module marker (consistent module scope across fences)
function* range(n: number): Generator<number, void, void> {
  for (let i = 0; i < n; i++) { yield i; } // computed (no I/O — sync machinery, no promises allocated)
}
console.log([...range(3)].join(",")); // 0,1,2 — sync sequences (overhead zero — async unjustified)
// bad — async generators for computed data (promises per item — machinery mismatched, throughput halved for nothing)
// fix — decision table (CPU → sync; I/O → async; bounded → Promise-array; huge → chunked)
```

```typescript
// good — chunked streaming at scale (pages yielded — bounded memory at any N)
export {}; // module marker (consistent module scope across fences)
async function* exportPages(total: number, size: number): AsyncGenerator<number[], void, void> {
  for (let i = 0; i < total; i += size) {
    yield Array.from({ length: Math.min(size, total - i) }, (_, k) => i + k); // chunks (per-page overhead amortized — backpressure per page)
  }
}
let exported = 0;
for await (const page of exportPages(5, 2)) { exported += page.length; } // streaming consumption (memory O(size) — N unbounded-safe)
console.log(exported); // 5 — chunked scale (throughput without buffering — the huge-N bridge)
// bad — Promise<Row[]> for exports (full buffering — OOM at scale, random access unused anyway)
// fix — chunked generators (pages streamed — memory bounded, throughput kept)
```

**Common confusion** — "async generators slower than batches" — per-item overhead vs batch efficiency (chunks amortizing — pages of 100+ approaching batch throughput with streaming memory). "chunks complicate consumers" — consumers `for await` identically (chunk shape internal — `flatMap` at the edge where flat items needed). "sync/async mixing freely" — sync consumers can't drive async generators (await required — boundary explicit, layering honest).

**Performance note** — chunk sizing trades overhead for latency (pages of 10–1000 typical — measured per workload, not defaulted); per-item generators for small N (simplicity winning where scale irrelevant).

**Mentor note** — scale question per collection API: "N at p99?" (small → Promise-array; huge → chunked generator — the answer in the design doc, not the incident report).
