## 6.1. Common interview QA — async types and standard library

### 1) **`Promise<T>` vs `T` vs `Awaited<T>` — what does each mean at an await position?**

**Definition** — three views of one value: `Promise<T>` (eventual — the declared/produced shape, states invisible per 1.1); `T` (fulfilled value — the unwrapped result, what logic operates on); `Awaited<T>` (consumption assertion — what `await` *delivers*, recursion-flattened per 1.2 — the probe spelling for consumed contracts).

**What problem it solves / history** — candidates (and code) confusing declared vs consumed shapes (probing `Promise<T>` where callers receive `Awaited<T>` — wrapping asserted, consumption untested): the interview separates wrapping mechanics (async/Promise — 1.3) from consumption semantics (await/Awaited — 1.2).

**Modern guidance** — answer shape: define all three, demo `Awaited<ReturnType<...>>` probes (17/4.1 async restatement), note flattening (`Promise<Promise<T>>` consumed as `T`). As of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS).

**Runnable example** — the demo to whiteboard (good vs bad, `tsc --strict`):

```typescript
// good — three views distinguished (declared, valued, consumed — each named)
export {}; // module marker (top-level await below needs module scope)
async function getScore(id: string): Promise<number> { return id.length * 5; }
type Declared = ReturnType<typeof getScore>; // Promise<number> (declared — produced shape, states invisible)
type Consumed = Awaited<ReturnType<typeof getScore>>; // number (consumed — delivered shape, flattened)
type Equal<X, Y> = (<T>() => T extends X ? 1 : 2) extends (<T>() => T extends Y ? 1 : 2) ? true : false;
declare function assertType<T extends true>(): void;
assertType<Equal<Consumed, number>>(); // consumption pinned (probe spelling — what callers receive)
console.log(await getScore("abc")); // 15 — views composed (declared wrapped, consumed flat)
// bad — "Promise<number> means pending number" (states read into types — pending-ness unobservable statically)
// fix — eventual-or-throw model (1.1 sentence — states runtime-owned, values checker-owned)
```

**Common confusion** — "`Awaited` only unwraps promises" — `Awaited` passes non-thenables through (`Awaited<42>` is `42` — total function, not partial). "probing `Promise<T>` suffices" — probes assert *consumed* shapes (callers receive `Awaited` — probe the delivery, not the packaging).

**Performance note** — view distinctions cost nothing (type-level — probes microseconds, annotations erased).

**Mentor note** — hiring signal: candidates reaching for `Awaited<ReturnType<...>>` unprompted (consumption-first thinking — senior instinct).

**Cross-links** — Awaited mechanics → [1.2. Awaited](<../1. Promise Types/1.2. Awaited recursive unwrapping and thenables.md>); probe discipline → [1.1. Expect Equal](<../../../17 Testing Types/sections/1. Type Assertions in Tests/1.1. Expect Equal and compile-time type assertions.md>).

### 2) **`all` vs `allSettled` vs `race` vs `any` — what shapes come back, and which rejects?**

**Definition** — the combinator table: `all` → tuple (positional, fail-fast rejecting); `allSettled` → settled-union tuple (never rejecting); `race` → member union (first-settled winning, rejection possible); `any` → member union minus rejections (first-fulfillment winning, `AggregateError` on total failure). Shapes + rejection behavior, one table (2.1's content as interview recall).

**What problem it solves / history** — combinator confusion in production code (`all` for bulk tolerable-failure — successes discarded; `race` expecting cleanup — losers leaking): the interview probes selection judgment (atomic vs best-effort vs first-wins vs redundant — semantics matched to requirements).

**Modern guidance** — answer shape: draw the 2×2 (shape: tuple-vs-union; failure: fail-fast-vs-tolerant), give one use-case per cell (atomic batch → all; bulk notify → allSettled; timeout → race; mirrors → any), state loser cleanup for race/any (2.2 — no answer, no merge).

**Runnable example** — the table as code (good vs bad, `tsc --strict`):

```typescript
// good — shapes recalled precisely (tuples vs unions — selection by requirement)
export {}; // module marker (top-level await below needs module scope)
async function f1(): Promise<string> { return "a"; }
async function f2(): Promise<number> { return 1; }
const tuple = await Promise.all([f1(), f2()] as const); // [string, number] (tuple — atomic batch, positional)
const settled = await Promise.allSettled([f1(), f2()] as const); // settled tuple (tolerant — partials as data)
console.log(tuple.join(","), settled.length); // a,1 2 — shapes recalled (table as code — selection demonstrated)
// bad — "they all return arrays" (shapes conflated — positional vs union vs settled undistinguished)
// fix — 2×2 table (shape × failure — four cells, four use-cases, four typings)
```

**Common confusion** — "`race` and `any` differ only in errors" — `race` settles first (win-or-lose — timeouts); `any` fulfills first (wins only — redundancy); error paths differ structurally (rejection vs AggregateError). "`allSettled` never fails" — never *rejects* (failures encoded — handling still required).

**Performance note** — selection costs nothing (same allocation class — one promise + adoption); wrong selection costs incidents (discarded successes, leaked losers — 5.1 exhibits).

**Mentor note** — follow-up: "who aborts the losers?" (cleanup ownership — senior candidates answering unprompted; juniors learning the 2.2 rule on the spot).

**Cross-links** — combinator mechanics → [2.1. Combinators](<../2. Combinators and Cancellation/2.1. all race allSettled any typed precisely.md>); loser cleanup → [2.2. AbortSignal](<../2. Combinators and Cancellation/2.2. AbortSignal propagation and cancellation contracts.md>).

### 3) **How does cancellation propagate — and what types carry it?**

**Definition** — propagation: `AbortController` owned per operation tree (test/request scope) → `signal` threaded as optional-last parameters (data, 2.2 part 1) → `throwIfAborted()` fail-fasts + `addEventListener("abort")` in-flight cleanup → reasons (`any`, default `AbortError`) carrying causality → catches routing aborts (quiet) vs failures (retry) per 2.2 part 2. Types carrying: `AbortSignal` (notification), `AbortController` (source), reasons (causality).

**What problem it solves / history** — cancellation as folklore (flags, unobserved signals, retried aborts — 5.1-adjacent classes): the interview probes protocol completeness (threading → observing → reasoning → routing — all four, not just "pass a signal").

**Modern guidance** — answer shape: trace one cancellation end-to-end (controller → parameter → throwIfAborted/listener → reason → routed catch), name the types at each hop, state the two classic bugs (unobserved signals changing nothing; retried aborts storming).

**Runnable example** — propagation traced (good vs bad, `tsc --strict`):

```typescript
// good — end-to-end propagation (four hops — threading, observing, reasoning, routing)
export {}; // module marker (top-level await below needs module scope)
async function cancellable(signal?: AbortSignal): Promise<string> {
  signal?.throwIfAborted(); // observing (fail-fast — reason thrown with causality)
  return "completed";
}
const ctrl = new AbortController(); // source owned (per-operation tree — lifetimes explicit)
ctrl.abort(new Error("stale-request")); // reasoned abort (causality carried — not bare)
try { await cancellable(ctrl.signal); console.log("unexpected"); } // threaded (signal as data — parameter, not global)
catch (e) { console.log(e instanceof Error ? `stopped:${e.message}` : "stopped"); } // routed (quiet stop — no retry: cancellation intended)
// stopped:stale-request — propagation complete (four hops — protocol, not folklore)
// bad — "pass signals to fetch" (one hop named — threading without observing/reasoning/routing)
// fix — four-hop trace (thread → observe → reason → route — completeness as the senior signal)
```

**Common confusion** — "signals cancel work" — signals *notify* (work observing — unobserved signals inert; the single most-misunderstood cancellation fact). "abort reasons typed" — `reason: any` (narrow before use — executor-legacy echo).

**Performance note** — propagation hops nanoseconds-to-microseconds (flag reads + listener dispatch — cancellation cheaper than the work it stops).

**Mentor note** — completeness grading: threading-only (junior), +observing (mid), +reasons (senior), +routing (staff — quiet-vs-loud handling designed).

**Cross-links** — signal contracts → [2.2. AbortSignal](<../2. Combinators and Cancellation/2.2. AbortSignal propagation and cancellation contracts.md>); abort doubles → [2.3. ### 4) **Why does `setTimeout` return two different types — and how do you contain it?**

**Definition** — the duality (3.3 part 1): `DOM` lib → `number`; `@types/node` → `NodeJS.Timeout` (object with `unref`/`ref`/`refresh`); both present → `number | Timeout` collision (clears accepting both, methods on neither without narrowing). Containment: per-runtime timer modules + `delay()`-style wrappers (handles opaque — callers never touching duality).

**What problem it solves / history** — cross-runtime handle no-ops (5.1 incident 3 — clears silently failing, 6-week interval leak): the interview probes environment-awareness (lib selection per runtime — 3.1) and encapsulation judgment (wrappers, not casts).

**Modern guidance** — answer shape: name both declarations + their libs, explain the collision, present the wrapper fix (encapsulation — one containment point), cite the incident mechanism (mismatched clear no-op).

**Runnable example** — duality named and contained (good vs bad, `tsc --strict`):

```typescript
// good — wrapper hiding duality (handles opaque — clears matching by construction)
export {}; // module marker (consistent module scope across fences)
function delay(ms: number): Promise<void> {
  return new Promise<void>((resolve) => { setTimeout(resolve, ms); }); // encapsulated (environment invisible outside — 3.3 pattern)
}
await delay(1);
console.log("contained"); // contained — duality contained (one function — callers timing, never handling)
// bad — "cast to number" (as unknown as number — clears no-op-ing cross-runtime, 6-week leaks)
// fix — per-runtime modules + wrappers (handles opaque — mismatch unrepresentable)
```

**Common confusion** — "`ReturnType<typeof setTimeout>` fixes it" — resolves per lib-set (environment-pinned — portable-looking, not portable). "one lib set for monorepos" — per-runtime tsconfigs (services vs edge — minimal libs failing loudly per 3.1).

**Performance note** — wrappers zero-cost (closures erased); leaked intervals billing × weeks (most expensive timer class — containment always cheaper).

**Mentor note** — environment-awareness signal: candidates naming both libs + the collision outrank candidates proposing casts (architecture over casting, every time).

**Cross-links** — handle duality → [3.3. Timers](<../3. Standard Library in Practice/3.3. Timers queues and the event-loop type view.md>); lib selection → [3.1. lib settings](<../3. Standard Library in Practice/3.1. lib settings and built-in async types.md>).

### 5) **Sequential loop vs `Promise.all` vs pool — how do you choose, and how does typing differ?**

**Definition** — the three concurrency shapes (2.3): loop-await (serial — `T[]` accumulated, order structural, latency summed); `Promise.all` (unbounded parallel — tuples for fixed, `T[]` for dynamic, latency maxed); pools (K-bounded — slot-indexed order, latency ≈ ceil(N/K)×single). Choice inputs: dependence (data forcing order), scale (N sizing bounds), downstream capacity (K tuning).

**What problem it solves / history** — one-shape-fits-all concurrency (loops for independent work — throughput abandoned; unbounded `all` at 10k — collapse; pools for three items — machinery unjustified): the interview probes cost-model reasoning (three shapes, three cost models, chosen per site).

**Modern guidance** — answer shape: state the decision inputs (dependent? huge? downstream limits?), map to shapes (dependent → loop+reason; independent-small → all; independent-huge → pool), give typing per shape (accumulated arrays vs tuples vs slot-indexed).

**Runnable example** — shapes chosen (good vs bad, `tsc --strict`):

```typescript
// good — shape per requirement (dependence, scale, capacity — inputs mapped)
export {}; // module marker (consistent module scope across fences)
async function fetchN(n: number): Promise<number> { return n; }
// small-independent → all (latency maxed — default shape)
const small: number[] = await Promise.all([1, 2, 3].map(fetchN));
console.log(small.join(",")); // 1,2,3 — batched (independence assumed until dependence shown)
// bad — "always Promise.all" (10k fan-out collapsing — scale unexamined, downstream throttled)
// fix — three-shape decision (dependent → loop; small → all; huge → pool — inputs examined per site)
```

**Common confusion** — "pools always safer" — pools add machinery (lanes, slots — justified past dozens, noise below). "typing identical across shapes" — loops accumulate (`T[]` pushed), `all` positions (tuples), pools slot-index (order preserved differently — shapes typing differently).

**Performance note** — three cost models (sum vs max vs ceil(N/K) — chosen, not defaulted; measured at 10× N per 5.1 part 1).

**Mentor note** — staff signal: candidates asking "N at p99? downstream limits?" before choosing (capacity-first reasoning — 3.2's scale question restated for concurrency).
