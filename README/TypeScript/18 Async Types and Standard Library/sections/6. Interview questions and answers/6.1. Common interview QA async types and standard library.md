## 6.1. Common interview QA — async types and standard library

Use these questions to explain mechanisms and limits, then connect the answer to an observable check. The linked worked owners declare their verified TypeScript and Node versions. This page is a reasoning exercise, not a separate executable test suite or a hiring-rank checklist.

### 1) **What do Promise<T>, T and Awaited<T> tell a caller?**

Promise<T> describes a promise whose fulfilled value has type T. It does not promise fulfillment, settling within a deadline or a particular rejection class. T is a type parameter and can itself describe many kinds of value. Awaited<T> models await-style consumption, including recursive thenable adoption and passing non-thenable values through. It is a type operation rather than runtime code that walks object fields.

For a function declared to return Promise<number>, ReturnType describes that wrapped contract and Awaited<ReturnType<...>> describes number. Either can be an appropriate test depending on the public promise being checked. A supplied type annotation cannot change runtime adoption. The [thenable fixture](<../1. Promise Types/1.2. Awaited recursive unwrapping and thenables.md>) demonstrates a nested annotation whose callback type disagrees with the actual flattened value.

**Follow-up:** Does a pending promise keep Node running, and does async preserve the identity of a returned promise? The [return-contract fixture](<../1. Promise Types/1.3. async function return-type contracts.md>) observes different promise identity with adopted fulfillment and a standalone pending promise that does not keep the process alive. A sound answer separates the type, promise state, underlying active work and process lifecycle.

### 2) **How do the four combinators differ in results and failure?**

| Operation | Fulfillment result | Failure boundary |
|---|---|---|
| Promise.all | Input-ordered fulfilled values, preserving suitable tuple positions | Rejects on an observed input failure; does not roll back siblings |
| Promise.allSettled | Input-ordered status-tagged member outcomes | Member rejection becomes data; input iteration or related setup can still fail |
| Promise.race | The value of the first settled input, if that input fulfills | Rejects if the first settled input rejects |
| Promise.any | The first fulfilled input's value | AggregateError when all inputs reject, with reasons in input order |

TypeScript preserves positions for suitably inferred tuples and produces array/union relationships for widened collections. A heterogeneous inline Promise.all array can infer a tuple without as const. Rejected promises do not add a typed error alternative to the fulfilled value union. None of these operations is a transaction, a concurrency limiter or an automatic cancellation manager.

**Follow-up:** What happens for empty input and for a throwing iterator? The [actual combinator fixture](<../2. Combinators and Cancellation/2.1. all race allSettled any typed precisely.md>) checks fulfilled empty all/allSettled results, rejected empty any and a race that stays pending through the observation. It also reproduces allSettled rejecting when a well-typed input iterator throws. A sound answer qualifies member-failure handling rather than claiming allSettled can never reject.

### 3) **What makes a cancellation contract complete?**

A controller requests cancellation through its signal. The operation has to observe or forward that signal to cooperating work. A pre-entry throwIfAborted check handles an already-aborted caller but does not cancel later I/O by itself. In the current declaration, throwIfAborted returns void; it is not an assertion signature proving aborted is permanently false.

The [actual fetch fixture](<../2. Combinators and Cancellation/2.2. AbortSignal propagation and cancellation contracts.md>) tests success, pre-abort, in-flight abort, HTTP failure and a composed deadline. Default abort reasons, custom reasons and timeout reasons differ; catch policy should match the contract and validate unknown failures. A signal may be required, optional or part of an options object depending on the lifecycle the API promises.

**Follow-up:** Is aborting a shared controller after a fetch response wins a race safe for the winner? It can abort the winner's unread body. The [local HTTP reproduction](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by async misunderstandings.md>) demonstrates that failure, then races complete text reads before cancelling remaining requests. A streaming-response API needs to preserve the winner's ongoing ownership instead. A sound answer follows the actual work still pending after the selected outcome.

### 4) **Why do timer declarations differ, and what does a cast do?**

DOM declarations describe a numeric timeout handle. Node declarations describe a NodeJS.Timeout object. Loading both does not automatically form a union; the selected overload in the pinned fixture returns NodeJS.Timeout. ReturnType<typeof setTimeout> can describe a local handle under the selected environment, while an explicit Node timer import makes host intent clear. Neither guarantees one declaration for every possible consumer.

Annotations and assertions do not convert the handle. The [timer fixture](<../3. Standard Library in Practice/3.3. Timers queues and the event-loop type view.md>) compiles a deliberately DOM-typed program, runs it in Node, observes the actual object and confirms clearTimeout cancels it. Raw handles can be appropriate for host-specific lifecycle APIs; a stop function or wrapper can express other ownership needs. A wrapper has real runtime behavior to verify.

**Follow-up:** Does unref cancel the callback or drain the service? Neither. It permits Node to exit if no other active work requires the loop. The fixture's child processes show an unreferenced callback still firing while another timer keeps the process alive. A sound answer also distinguishes that lifecycle question from exact timer timing or universal setImmediate-versus-timeout order.

### 5) **How do you choose sequential work, an aggregate or a bounded mapper?**

Establish dependencies and ordering requirements first. Then inspect resource capacity, input size and failure policy. Sequential starts can express dependence; independent work may overlap; a bounded mapper can limit active callbacks even for a small batch if each operation is expensive. A Promise.all call aggregates its supplied inputs and does not itself decide when their underlying operations start.

The [scheduling fixture](<../2. Combinators and Cancellation/2.3. Sequential vs parallel patterns and tuple typing.md>) tests sequential starts, input-ordered consumption of already overlapping work, and a validated mapper with an active-work cap. The mapper returns R[] in input order. Fixed tuples can carry positional relationships that this dynamic array API does not claim. Concurrency limits also differ from rate limits: bounding active jobs does not set starts per second.

**Follow-up:** What happens after one callback rejects? The example stops new admissions after the first observed failure, drains callbacks already started, and then rejects with the first reason. It neither cancels those callbacks nor undoes their effects. A callback that never settles prevents its drain from finishing. A sound answer states this policy before claiming capacity or latency benefits, and asks whether the application needs a different failure contract.

### 6) **Common confusion**

A fulfilled type is not a timing, cancellation or rejection guarantee. A compiled declaration also does not install a runtime API; the [library fixture](<../3. Standard Library in Practice/3.1. lib settings and built-in async types.md>) makes document type-check and then fail in Node. Use the same distinction when reasoning about disposal or generator cleanup.

A good interview explanation need not recite every API. It should identify the mechanism, make a testable prediction and state what the evidence leaves open. Repeating a rule such as always use Promise.all or always wrap handles skips the design constraints that determine whether it is appropriate.

### 7) **Performance note**

The chosen starts, dependencies, buffers and cleanup affect runtime behavior. Types describe parts of those contracts but do not supply max/sum latency formulas, fixed allocation counts or a universally correct pool size. The linked fixtures verify behavior with controlled work; they do not establish throughput or production response-time bounds. State the measurement needed before giving a performance recommendation.

### 8) **Mentor note**

Give a learner a response race that aborts its shared signal in finally. Ask what return type the function exposes, what has finished at that point and which assertion would detect an unread-body failure. Then ask them to change the contract to a complete string or design separate loser cancellation. Assess the causal explanation and ownership choice using the worked reproduction, rather than rewarding an unqualified slogan about cancelling losers.
