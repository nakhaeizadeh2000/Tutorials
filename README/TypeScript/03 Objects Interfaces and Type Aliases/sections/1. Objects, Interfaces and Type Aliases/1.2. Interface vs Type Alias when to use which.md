## 1.2. Interface vs Type Alias (when to use which)

### 1) **Comparison** (declaration merging vs alias)

Both describe object shapes, but differ in openness and composition:

| Feature | `interface` | `type` |
|---------|-------------|--------|
| Declaration merging | yes — duplicate `interface Foo` merges | no — duplicate `type Foo` is error |
| Extends | `extends` (heritage) | intersection `&` |
| Union/conditional/mapped | cannot directly (`type` only) | full power |
| Performance | slightly faster for large object hierarchies | same |
| Error messages | named interface | alias or expanded |

```typescript
// interface — open
interface User { name: string; }
interface User { age: number; } // merges → { name: string; age: number }
const u: User = { name: "Ava", age: 30 };

// type — closed
type UserType = { name: string };
// type UserType = { age: number }; // error: duplicate identifier
type UserExtended = UserType & { age: number };

// interface heritage
interface Animal { species: string; }
interface Dog extends Animal { bark(): void; }

// type composition
type DogType = Animal & { bark(): void };

// type-only expressiveness
type Keys = "a" | "b";
type Mapped = { [K in Keys]: number }; // only type can do this
type Conditional<T> = T extends string ? true : false;
```

### 2) **Good** (interface for public API)

**Modern guidance:**

- **Public API / library surface → `interface`.** Consumers can *augment* via `declare module` / declaration merging (see [07 2.2 Augmentation](<../../../07%20Modules%20Namespaces%20and%20Declaration%20Files/sections/2.%20Declaration%20Files%20and%20Ambient/2.2.%20Ambient%20Modules%20and%20Augmentation.md>)). Also error messages read `User` not expanded intersection.
- **Internal composition / unions / utilities → `type`.** Anything needing `|`/`&`/mapped/conditional must be `type`.

```typescript
// good: library shape as interface — augmentable
export interface Config { timeout: number; retries: number; }
// consumer can:
// declare module "lib" { interface Config { debug?: boolean; } }

// good: internal derived types as type
type ConfigKeys = keyof Config; // "timeout" | "retries"
type PartialConfig = Partial<Config>;
type WithDefaults = Required<Config>;

// bad: using interface for union — impossible
// interface Status extends "idle" | "loading" {} // error — cannot extend string union
type Status = "idle" | "loading"; // correct
```

### 3) **Bad** (interface for unions)

**Bad patterns:**

- `interface` wrapping a union via awkward heritage trick.
- Using `interface` for tuple/primitive aliases where `type` is idiomatic.
- Creating deep `interface extends` chains where flat `type &` + utility is clearer.

```typescript
// bad: forced interface for union
interface BadStringUnion { value: string | number } // why not type directly?

// bad: interface for function type — verbose
interface BadFn { (x: number): string; }
// good: type alias
type GoodFn = (x: number) => string;

// bad: deep interface hierarchy — hard to flatten
interface A { a: string; }
interface B extends A { b: string; }
interface C extends B { c: string; }
// good: composition via type if hierarchy is flat data
type AClean = { a: string } & { b: string } & { c: string };
// or via utility: type C2 = A & BExtra & CExtra
```

### Mentor note

Default policy: `interface` for exported shapes, `type` for everything else. Document it; add `consistent-type-definitions` (typescript-eslint) with `["error","interface"]` for interfaces vs types if team wants enforcement, but keep exception for union cases.

### Performance note

Interfaces can be faster for checker on huge hierarchies (cached), but difference is noise vs bad project references or `skipLibCheck: false`. Don't choose based on perf unless profiling shows it.
