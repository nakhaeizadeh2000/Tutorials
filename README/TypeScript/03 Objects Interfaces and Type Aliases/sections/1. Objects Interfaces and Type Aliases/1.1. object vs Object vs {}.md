## 1.1. object vs Object vs {}

### 1) **Distinction** (object is useful)

Three similar names, very different meanings:

- `object` (lowercase) — any non-primitive: objects, arrays, functions. The only *useful* of the three for constraints.
- `Object` (uppercase) — legacy boxed type — includes primitives via boxing (`"hi"` has `toString`) plus all object members. Too wide.
- `{}` (empty object) — "non-nullish" — accepts any non-nullish value including primitives with boxing, plus `{}`, `[]`, etc. Also too wide.

```typescript
let a: object = { x: 1 }; // ok
a = [1, 2];                // ok — array is object
a = () => {};              // ok — function is object
// a = "hi"; // error — string is primitive, not object
// a = null; // error — null not object

let b: Object = "hi"; // ok — boxes to String object (too permissive)
let c: {} = "hi";     // ok — also permissive
let d: object = "hi"; // error — correctly rejects

// modern guidance table:
// need "any non-primitive" → object
// need "any value except null/undefined" → unknown or {} is legacy, prefer unknown
// need "exact shape" → { prop: string } or interface/type
```

---

### 2) **Bad** (Object/{} accept too much)

```typescript
// bad: Object accepts primitives — hides bug
function printBad(x: Object) {
  console.log(x.toString()); // works even for primitives due to boxing — misleading
}
printBad("hi"); // ok — but caller thinks object expected
printBad(123);  // also ok

// bad: {} accepts primitives too — eslint bans it
function printBad2(x: {}) {
  console.log(Object.keys(x)); // Object.keys("hi") => ["0","1"] — rarely intended
}
printBad2("hi");
printBad2(42);

// good: object or precise shape
function printGood(x: object) {
  console.log(Object.keys(x)); // only for non-primitives
}
printGood({ a: 1 }); // ok
// printGood("hi"); // error — caught

// even better: precise
function printBest(x: Record<string, unknown>) {
  for (const [k, v] of Object.entries(x)) console.log(k, v);
}
printBest({ a: 1, b: "hi" });
```

ESLint `no-wrapper-object-types` and Biome `noWrapperObjectTypes` flag `Object`/`String` etc; add `no-empty-object-type` (eslint) for `{}`.

---

### 3) **Fix** (use object or Record)

**Fix rules:**

- Never use `Object` or `{}` in new code. Replace with:
  - `object` — if you truly mean "non-primitive object."
  - `Record<string, unknown>` — if you mean "dictionary-like object."
  - `unknown` — if you mean "any value."
  - specific shape `{ x: number }` — if you know structure.
- For `Object` static methods, call via `Object` value (runtime object), not as type: `Object.keys(obj)` is fine; `let x: Object` is not.

```typescript
// fix mapping:
// {} → unknown (for any) or object (for non-primitive)
// Object → object
// Function → specific callable type: () => void or (x: string) => number

// Record vs object example
type Dict = Record<string, string>; // { [key: string]: string }
const d2: Dict = { a: "hi", b: "ho" };
// const d3: Dict = { a: 1 }; // error

// unknown vs {} for "any value"
function handleUnknown(x: unknown) {
  if (typeof x === "string") console.log(x.toUpperCase());
}
function handleBadObjectLike(x: {}) {
  // x could be string — still need typeof anyway, but type pretended otherwise
}
```

**Common confusion** —

- "`{}` means empty object" — at type level it means "non-nullish" (anything except `null`/`undefined`). Empty object at runtime is type `{}` but also accepts `string`. Use `Record<string, never>` for true empty-object.

**Performance note** — Types are erased (zero emit); checker cost dominates. For this feature, keep types shallow and measure `tsc --extendedDiagnostics` if checker slows.

**Mentor note** —

Add lint rule `ban-types` (or equivalent) to reject `Object`, `Function`, `{}` at PR time. One auto-fix prevents a class of "why did my string pass an object check?" bugs.
