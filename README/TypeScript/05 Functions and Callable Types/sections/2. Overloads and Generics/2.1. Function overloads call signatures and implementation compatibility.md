## 2.1. Function overloads — call signatures and implementation compatibility

### 1) **Overload shape** (multiple call signatures above one implementation — which signatures callers see)

**Definition** — an *overload* declares several call signatures for one function, with a single implementation that handles them all. Only the overload signatures are visible to callers — the implementation signature is hidden (not callable directly) and must satisfy every overload. Ordering matters: the checker tries overloads top-to-bottom and picks the first matching.

**What problem it solves / history** — some functions behave like different functions depending on arguments — `createElement(tag: "canvas"): HTMLCanvasElement` vs `createElement(tag: string): HTMLElement`. A union param `tag: "canvas" | string` would lose the correlated return; a generic alone cannot express per-argument return mapping without conditionals. Overloads (TS 1.0) let each call arity map to its precise return while sharing one runtime body.

**Modern guidance** — as of TypeScript 5.9 era, use overloads when *call-site* experience (hover, autocomplete, error message) matters and a single generic/union would widen or produce confusing conditional errors. Prefer inline call signatures in `interface` for API design — they document each variant. Keep overload count ≤3 where possible; beyond that a generic or discriminated param often reads better.

**Runnable example** — correlated param→return via overloads (good vs bad, `tsc --strict`):

```typescript
// good — two precise call sites, one implementation
function pick(value: string): string;
function pick(value: number): number;
function pick(value: string | number): string | number {
  return typeof value === "string" ? value.toUpperCase() : value * 2;
}
const s: string = pick("hello"); // string — first overload
const n: number = pick(42); // number — second overload
// const wrong: string = pick(42); // error — second overload returns number

// good — arity overload (different param counts map to different returns)
function makeArray(length: number): number[];
function makeArray(value: string, length: number): string[];
function makeArray(a: number | string, b?: number): number[] | string[] {
  if (typeof a === "number") return Array.from({ length: a }, () => 0);
  return Array.from({ length: b! }, () => a);
}
const nums = makeArray(3); // number[]
const strs = makeArray("hi", 2); // string[]

// bad — union param loses correlation (return widens, caller must narrow)
function pickBad(value: string | number): string | number {
  return typeof value === "string" ? value.toUpperCase() : value * 2;
}
const badResult = pickBad("hello"); // string | number — caller needs narrowing even for known input
// fix — overload above keeps string→string, number→number for callers

// bad — overloading to model what a generic does
function identityOverload(x: string): string;
function identityOverload(x: number): number;
function identityOverload(x: unknown): unknown { return x; }
// fix — generic covers infinite T without enumerating each: function identity<T>(x: T): T
```

**Common confusion** — "the implementation signature is callable" — it is not — `pick(value: string | number)` is invisible to callers; only `pick(string)` and `pick(number)` are. "Overload order doesn't matter" — it does — `pick(string | number)` first would match everything and shadow the precise `pick(string)` below. "Overloads emit" — signatures erase; only the implementation body emits.

**Performance note** — overload resolution is O(signatures) per call — 10+ overloads on a hot utility can slow hover and checker diagnostics (each call tries every signature). Prefer a generic or conditional return when overload count grows — fewer signatures → faster `tsc --extendedDiagnostics`.

**Mentor note** — teach with `pick` vs `pickBad` side-by-side — hover both calls and show `string` vs `string|number`. Exercise: give `function get(key: "users"): User[]; function get(key: "posts"): Post[];` and ask what `get(Math.random() > 0.5 ? "users" : "posts")` returns — answer is *no overload matches* (argument not a literal) — then show the single generic/union alternative for dynamic keys.

### 2) **Implementation compatibility** (the implementation signature must be *wider* than every overload — "implementation is not callable")

**Definition** — the *implementation signature* (the function with a body) must be assignable-compatible with every overload signature: its params must accept a *superset* of each overload's params, and its return must be assignable *to* each overload's return (the body returns something each overload can narrow to). The checker verifies the body against the implementation signature, not directly against overloads.

**What problem it solves / history** — without widening, the body could not handle all overloads in one place — each overload describes a *subset* of runtime behavior; the implementation must union those subsets. The "hidden implementation" rule prevents callers from seeing the broad `string|number` signature when the overloads promise `string` and `number` separately.

**Modern guidance** — as of TypeScript 5.9 era, write the implementation signature as the *union* of overload params and the *union* of their returns (or `unknown`/`any` when forced, but then narrow inside). Never use the implementation signature to expose a looser API — callers cannot call it, but the body must still handle every overload input — keep the body exhaustive with `typeof`/`in` guards.

**Runnable example** — compatible widening and hidden implementation (good vs bad, `tsc --strict`):

```typescript
// good — implementation is wider (string|number param, string|number return)
function format(value: string): string;
function format(value: number): string;
function format(value: string | number): string { // implementation: superset param, common return
  return typeof value === "string" ? value.toUpperCase() : value.toFixed(2);
}
format("hi"); // string
format(3.14); // string
// format(true); // error — no overload matches boolean; implementation signature not visible

// good — implementation with different arities must union arities
function concat(a: string, b: string): string;
function concat(a: string[], b: string[]): string[];
function concat(a: string | string[], b: string | string[]): string | string[] {
  return typeof a === "string" ? (a as string) + (b as string) : [...(a as string[]), ...(b as string[])];
}

// bad — implementation too narrow (doesn't accept second overload's input)
// function badOverload(x: string): string;
// function badOverload(x: number): string;
// function badOverload(x: string): string { // error TS2391 — second overload (number) not compatible with impl (string only)
//   return String(x);
// }
// fix — widen param to string | number: function badOverload(x: string | number): string

// bad — calling through implementation type by aliasing (loses overload precision)
// const aliased: (x: string | number) => string | number = format; // widens away overloads
// aliased("hi") → string | number, not string — overload benefit lost
```

**Common confusion** — "I can call the implementation signature" — you cannot — `format(true)` via `string|number` impl is rejected because no overload lists `boolean`. "The body is checked against overloads" — body checked against *implementation* signature; overload-to-implementation compatibility is a separate pass — so `return value` inside must match the implementation's return, not any single overload's.

**Performance note** — compatibility checking is O(overloads) — trivial. The bug cost of a too-narrow implementation is a runtime `typeof` miss where the body assumes only one overload's type — test every overload path.

**Mentor note** — have students intentionally make the implementation too narrow and read the `No overload matches this call` vs `Overload signature not compatible` error — the second is about impl-to-overload width. Exercise: give two overloads `f(x: string): string` / `f(x: number): number` and ask what impl signature serves both — answer is `f(x: string|number): string|number` or `f(x: unknown): unknown` with guards.

### 3) **When not to overload** (union + conditional vs overload — readability vs hover budget)

**Definition** — use *overload* when each call variant deserves its own hover and error message; use *union + conditional* (`function f<T>(x: T): T extends string ? string : number`) or *discriminated param* (`{ kind: "a"; x: string }`) when variants are many, correlated types are systematic, or dynamic keys must be handled.

**What problem it solves / history** — overloads excel for 2–3 hand-picked variants (DOM APIs), but `n` overloads for `n` keys don't scale — a generic `get<K extends Key>(key: K): Store[K]` covers `n` keys with one signature and works for dynamic `K`.

**Modern guidance** — as of TypeScript 5.9 era, choose by this table:

| Shape | Prefer |
|---|---|
| 2–3 fixed variants with distinct returns | Overload (best hover, crisp errors) |
| `n` correlated keys (store, factory) | Generic + indexed access `T[K]` |
| Boolean flag selecting return | Generic conditional or two named functions `getString`/`getNumber` |
| Dynamic arg not a literal | Union with narrowed return requiring caller guard |

All forms erase; `erasableSyntaxOnly` impact is none.

**Runnable example** — overload vs generic, boolean flag trap (good vs bad, `tsc --strict`):

```typescript
// good — 3 fixed overloads (best caller ergonomics)
function load(path: "users"): { id: string }[];
function load(path: "posts"): { title: string }[];
function load(path: string): unknown[];
function load(path: string): unknown[] { return []; }
load("users"); // { id: string }[]
load("posts"); // { title: string }[]

// good — generic covers n keys + dynamic keys (one signature)
type Store = { users: { id: string }[]; posts: { title: string }[] };
function get<K extends keyof Store>(key: K): Store[K] { return null as unknown as Store[K]; }
const which = (Math.random() > 0.5 ? "users" : "posts") as keyof Store;
get(which); // Store[keyof Store] — works for dynamic, overload would need catch-all

// bad — boolean flag overload that invites mistakes
function fetchData(asJson: true): Promise<object>;
function fetchData(asJson: false): Promise<string>;
function fetchData(asJson: boolean): Promise<object | string> { return fetch("/api").then((r) => asJson ? r.json() : r.text()); }
// fix — two named functions are clearer than a flag overload
function fetchJson(): Promise<object> { return fetch("/api").then((r) => r.json()); }
function fetchText(): Promise<string> { return fetch("/api").then((r) => r.text()); }

// bad — overload for dynamic key fails at call site
// load(Math.random() > 0.5 ? "users" : "posts"); // error — no overload for string (dynamic)
// fix — generic get(which) above handles string union
```

**Common confusion** — "more overloads is more precise" — beyond ~5, hover truncates and error messages say "no overload matches" with 8 signatures listed — precision lost to noise. "Generic replaces all overloads" — overloads still win for unrelated param shapes (e.g., `createElement("canvas")` vs `createElement("img")` with disjoint option bags).

**Performance note** — hover rendering and error formatting are O(signatures) — 20 overloads produce a 20-line hover. A generic with `Store[K]` produces one line regardless of `n` keys — measurably faster `tsc` hover in large codebases.

**Mentor note** — review a PR with 6 overloads and ask "would `get<K extends Key>(key: K): Store[K]` cover this with one line and handle `K` from a variable?" — forces the trade-off conversation. Exercise: given `function f(x: string): string` / `f(x: number): number` vs `function f<T>(x: T): T` ask which callers care — answer is *overload for 2 types is fine, generic for n*.
