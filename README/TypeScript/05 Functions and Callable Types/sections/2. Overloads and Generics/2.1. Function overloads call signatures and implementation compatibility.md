## 2.1. Function overloads — call signatures and implementation compatibility

An overload set gives callers several signatures for one runtime function. Each signature states an accepted argument list and its exposed result. The implementation has one body and a separate compatible signature; callers do not automatically get to call that implementation signature. Keep caller selection, implementation checking and actual runtime behavior distinct.

Examples use TypeScript 7.0.2 / Node 20.20.2, verified 2026-10-14. Save each named file in a new directory without a tsconfig.json. Run `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`, replacing FILE with implementation, views, keys or order. Activate one commented failure at a time and use the same flags with `--noEmit` instead of `--outDir dist`. The intentionally wrong broken body is caught during its demonstration so the other examples can finish.

### 1) **Overload shape and implementation compatibility**

The pick overloads expose string-to-string and number-to-number. Its body accepts both kinds and branches to produce the corresponding result. A union result annotation is compatible here even though string-or-number is not assignable to string or number separately by ordinary value assignment. An unknown implementation result can also be compatible with those specific overloads. Overload compatibility is a distinct check; do not describe it as ordinary assignment of the entire implementation to every public signature.

Save `implementation.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
function pick(value: string): string;
function pick(value: number): number;
function pick(value: string | number): string | number {
  return typeof value === "string" ? value.toUpperCase() : value * 2;
}
const text = pick("hello");
const number = pick(21);
type Text = Expect<Equal<typeof text, string>>;
type NumberResult = Expect<Equal<typeof number, number>>;
console.log(text, number); // HELLO 42
function broad(value: string): string;
function broad(value: number): number;
function broad(value: unknown): unknown { return value; }
console.log(broad("Ada"), broad(3)); // Ada 3
function zeros(length: number): number[];
function zeros(value: string, length: number): string[];
function zeros(value: string | number, length?: number): number[] | string[] {
  if (typeof value === "number") return Array.from({ length: value }, () => 0);
  if (length === undefined) throw new Error("string value requires a length");
  return Array.from({ length }, () => value);
}
console.log(zeros(3).join(","), zeros("hi", 2).join(",")); // 0,0,0 hi,hi
function broken(value: string): string;
function broken(value: number): number;
function broken(value: string | number): string | number { return 0; }
const promisedString = broken("hi");
console.log("broken runtime:", typeof promisedString); // number despite the string overload result
try { console.log(promisedString.toUpperCase()); }
catch (error: unknown) { console.log(error instanceof TypeError ? "TypeError" : "other"); }
// const wrong: string = pick(1); // uncomment: TS2322
// function acceptsUnion(value: string | number) { return pick(value); } // uncomment: TS2769
// zeros("hi"); // uncomment: TS2345
```

The output is `HELLO 42`, `Ada 3`, `0,0,0 hi,hi`, `broken runtime: number` and `TypeError`. The two live equality checks establish pick's exposed result types. Broad's unknown implementation annotation does not make its string call return unknown through the public overload. Zeros demonstrates separate one-argument and two-argument public contracts, with an actual length check in the string branch rather than a non-null assertion.

Activate wrong to see TS2322. A string-or-number argument is not covered merely because the hidden implementation accepts it: activating acceptsUnion yields TS2769 because neither of pick's individual public inputs accepts that union. Zeros("hi") yields TS2345 against the available one-argument numeric overload, rather than calling the optional-length implementation directly.

The [primary compatibility guide](https://www.typescriptlang.org/docs/handbook/2/functions.html#overload-signatures-and-the-implementation-signature) distinguishes public overloads, a hidden implementation and incompatible cases. To reproduce a too-narrow implementation separately, save `narrow.ts`:

```typescript
export {};
function narrow(value: string): string;
function narrow(value: number): string;
function narrow(value: string): string { return value; }
```

The check-only command reports TS2394 on the numeric overload. An implementation that cannot handle every exposed input is not compatible. The body itself is checked against its implementation annotation, not independently as a complete proof of each overload's input/output mapping.

Broken makes that limit observable. Its body always returns zero, which fits its union implementation return; its string overload nonetheless promises string to the caller. The program compiles, then the attempted string operation throws a caught TypeError. Review and test every exposed runtime path. Signature compatibility does not establish branch correlation by itself, and an assertion or any return annotation would not repair an incorrect body.

### 2) **Preserving overloads, choosing a view and exposing a union input**

An unannotated alias can keep the overload set. A compatible narrower view can select an input contract. Neither exposes a hidden implementation automatically. If a consumer needs a union-input function, implement an actual union-input wrapper or deliberately expose that input as a public overload.

Save `views.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
function format(value: string): string;
function format(value: number): string;
function format(value: string | number): string { return String(value); }
const preserved = format;
const stringOnly: (value: string) => string = format;
type Preserved = Expect<Equal<typeof preserved, typeof format>>;
function unionWrapper(value: string | number): string {
  return typeof value === "string" ? format(value) : format(value);
}
console.log(preserved("hi"), preserved(3), stringOnly("Ada"), unionWrapper(4)); // hi 3 Ada 4
function exposed(value: string): string;
function exposed(value: number): string;
function exposed(value: string | number): string;
function exposed(value: string | number): string { return String(value); }
const broadView: (value: string | number) => string = exposed;
function useBroad(value: string | number): string { return broadView(value); }
console.log(useBroad("hi"), useBroad(5)); // hi 5
// const rejected: (value: string | number) => string | number = format; // uncomment: TS2322
// stringOnly(3); // uncomment: TS2345
// function hidden(value: string | number) { return format(value); } // uncomment: TS2769
```

The output is `hi 3 Ada 4` then `hi 5`. Preserved retains format's type, verified by the live equality assertion. StringOnly deliberately permits only strings, and its numeric call fails with TS2345. The attempted broad rejected view fails with TS2322: format's exposed overload set lacks one callable signature that accepts a string-or-number argument.

UnionWrapper supplies that signature and narrows the argument before each format call. Exposed explicitly publishes a string-or-number overload, so its broad view and useBroad calls are accepted. Activate hidden to observe TS2769 for the original overload set. A variable annotation states a consumer contract; it cannot make an incompatible source satisfy it or make an implementation signature visible.

Choose a view from how the consumer will invoke the function, and keep its argument/result relationship useful. Do not use a cast just to hide a missing public input contract. The [generic function owner](<./2.2. Generic functions inference constraints defaults and scope.md>) supplies the alternative when one type-parameter relationship naturally describes all inputs.

### 3) **Dynamic keys, specialized signatures and choosing an API shape**

A public catch-all overload can accept a dynamic argument while returning a less precise contract. Without that overload, separate literal inputs may fail to cover a union input. A generic indexed lookup can describe a systematic key/result relationship directly, provided its implementation actually returns the selected value.

Save `keys.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Store = { users: { id: string }[]; posts: { title: string }[] };
const store: Store = { users: [{ id: "u1" }], posts: [{ title: "Hello" }] };
function load(path: "users"): Store["users"];
function load(path: "posts"): Store["posts"];
function load(path: string): unknown[];
function load(path: string): unknown[] {
  if (path === "users") return store.users;
  if (path === "posts") return store.posts;
  return [];
}
const dynamicKey = Math.random() > 0.5 ? "users" : "posts";
const broadResult = load(dynamicKey);
type BroadResult = Expect<Equal<typeof broadResult, unknown[]>>;
console.log(load("users")[0]?.id, broadResult.length, load("missing").length); // u1 1 0
function specific(path: "users"): Store["users"];
function specific(path: "posts"): Store["posts"];
function specific(path: "users" | "posts"): Store["users"] | Store["posts"] { return store[path]; }
console.log(specific("users")[0]?.id, specific("posts")[0]?.title); // u1 Hello
// const rejectedUnion = specific(dynamicKey); // uncomment: TS2769
function get<K extends keyof Store>(key: K): Store[K] { return store[key]; }
const precise = get("users");
const either = get(dynamicKey);
type Precise = Expect<Equal<typeof precise, Store["users"]>>;
type Either = Expect<Equal<typeof either, Store["users"] | Store["posts"]>>;
console.log(precise[0]?.id, either.length); // u1 1
// get("missing"); // uncomment: TS2345
```

The output is `u1 1 0`, `u1 Hello` and `u1 1`. Both stored collections contain one entry, so the dynamic-key length outputs remain deterministic. Load's string catch-all accepts the users-or-posts argument and exposes unknown[], as its active assertion verifies. Specific has only the individual literal overloads: its dynamic call yields TS2769. Get uses an actual store and returns the indexed result, with live assertions for the precise users call and the union-key call. Its unknown-key call is rejected with TS2345.

Use an overload for distinct argument shapes or caller contracts that need separate descriptions. Use a union input when the same result contract works for all alternatives. Use a generic indexed relationship when one key should determine one stored result type. The [primary good-overloads guide](https://www.typescriptlang.org/docs/handbook/2/functions.html#writing-good-overloads) illustrates why separate signatures can reject a union caller and why a union parameter can be clearer when the results agree. These choices depend on the required API, not a fixed maximum overload count.

Order can affect selection, but "the first textual match always wins" is not a complete rule. Observe the specialized string-literal case and a separate ordinary structural comparison.

Save `order.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
function select(value: string): "general";
function select(value: "special"): "special";
function select(value: string): "general" | "special" { return value === "special" ? "special" : "general"; }
const selected = select("special");
type Selected = Expect<Equal<typeof selected, "special">>;
console.log(selected); // special; the later string-literal overload is selected
function ordinary(value: { a: string }): { a: string };
function ordinary(value: { b: string }): { b: string };
function ordinary(value: { a: string } | { b: string }): { a: string } | { b: string } { return value; }
function reversed(value: { b: string }): { b: string };
function reversed(value: { a: string }): { a: string };
function reversed(value: { a: string } | { b: string }): { a: string } | { b: string } { return value; }
const both = { a: "left", b: "right" };
const first = ordinary(both);
const second = reversed(both);
type First = Expect<Equal<typeof first, { a: string }>>;
type Second = Expect<Equal<typeof second, { b: string }>>;
console.log(first.a, second.b); // left right; both signatures match the actual supplied object
// console.log(first.b); // uncomment: TS2339; narrower public view omits b
```

The output is `special` then `left right`. All three equality checks pass. Select's later single-string-literal signature is chosen over the earlier string signature in this call. Ordinary and reversed both accept the supplied object, but their ordering gives different exposed result views. The implementation returns that original object, which meets either requirement; the chosen view controls member access. Activating first.b yields TS2339 despite the runtime object retaining b.

The [primary merging guide](https://www.typescriptlang.org/docs/handbook/declaration-merging.html#merging-interfaces) also describes specialized string-literal signatures in merged overload lists. That is relevant context rather than a specification of the entire standalone resolution algorithm. These probes establish the shown calls on 7.0.2. Check the actual overload set and caller types instead of extending either example into a universal ordering rule.

### 4) **Common confusion**

A hidden broad implementation does not provide an extra public overload. A catch-all that is publicly declared does. An alias preserves or restricts a compatible view; it does not expose an implementation by annotation. A union/unknown implementation return can pass overload compatibility without proving that each branch returns the value promised by its selected signature. Finally, overload order matters, with specialized cases that a simple textual first-match slogan misses.

### 5) **Performance note**

Overload signatures and type probes are erased; the one implementation body, wrappers, branches and collection construction remain. No compiler complexity, hover threshold or runtime speed comparison was measured here. Fewer signatures do not by themselves prove faster checking or clearer errors. Prefer the contract a consumer can understand and use, then investigate a real slow workload with the [measurement workflow](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>).

### 6) **Mentor note**

Ask the learner why pick's implementation accepts a union but its public calls do not, and why load's dynamic call succeeds while specific's fails. A sound answer identifies the visible signatures. Next give the rejected broad alias and ask for a real wrapper or deliberate catch-all. Finish with broken: the checking pass accepts its implementation, so which runtime cases prove the advertised relationship? They should test both input kinds and explain the controlled string-operation failure.
