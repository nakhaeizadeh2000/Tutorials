## 2.3. Rest parameters — tuple types and variadic composition

A tuple rest parameter describes an argument list with positional requirements. A generic tuple can name that list so a wrapper forwards the same arguments and result relationship. Type-level tuple concatenation computes a new positional contract; it does not execute an array concatenation or automatically implement an arbitrary pipeline.

Examples use TypeScript 7.0.2 / Node 20.20.2, verified 2026-10-14. Save each named file in a new directory without a tsconfig.json. Run `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`, replacing FILE with rest, composition or capture. Activate one commented failure at a time and use `--noEmit` instead of `--outDir dist` for its diagnostic. Intentional runtime mistakes are caught so the valid cases continue.

### 1) **Rest contracts, spread sources and mutation permissions**

Set requires a tag followed by a numeric value and unit. A tuple supplies known positions; an open array type does not promise the same length and per-position types. Labels explain those positions to a reader. They do not turn runtime arguments into named properties.

Save `rest.ts`:

```typescript
export {};
function set(tag: string, ...rest: [value: number, unit: string]): string {
  return `${tag} ${rest[0].toFixed(0)}${rest[1]}`;
}
console.log(set("temp", 36, "C")); // temp 36C
const pair = [10, "px"] as const;
console.log(set("size", ...pair)); // size 10px
const source: readonly string[] = ["a", "b"];
function join(...parts: readonly string[]): string { return parts.join("/"); }
function mutableRest(...parts: string[]): string {
  console.log("same array:", parts === source); // false
  parts.push("c");
  return parts.join("/");
}
console.log(join(...source)); // a/b
console.log(mutableRest(...source), source.join("/")); // a/b/c a/b
try { set("temp", "hi" as unknown as number, "C"); }
catch (error: unknown) { console.log(error instanceof TypeError ? "TypeError" : "other"); }
const open: (number | string)[] = [10, "px"];
// set("temp", 36); // uncomment: TS2554
// set("temp", "hi", "C"); // uncomment: TS2345
// set("size", ...open); // uncomment: TS2556
// const mutable: string[] = source; // uncomment: TS4104
// function cannotPush(...parts: readonly string[]): void { parts.push("c"); } // uncomment: TS2339
```

The output is `temp 36C`, `size 10px`, `a/b`, `same array: false`, `a/b/c a/b` and `TypeError`. Set accepts the readonly pair's elements as two positional arguments. The missing unit is rejected with TS2554, a plain string value with TS2345, and the open array spread with TS2556. The [primary rest/spread explanation](https://www.typescriptlang.org/docs/handbook/2/functions.html#rest-arguments) distinguishes the source iterable from the argument-list contract.

Both join and mutableRest accept a readonly spread source. MutableRest gathers a new rest array for the call, so its push does not change source. Join's readonly rest type instead denies that operation in its body. Activate cannotPush for TS2339, or the direct mutable array assignment for TS4104. Spreading elements into a call is not assigning the original readonly array to a mutable variable.

The forced number assertion also passes checking, then fails at the numeric toFixed operation. It supplies no runtime conversion or validation. This controlled contrast corrects the misleading idea that the old asserted string call would be rejected automatically. Use a genuine bad string argument for the checking example and evidence for a real numeric value at a boundary. [Unknown boundary checks](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>) owns that evidence; [parameter basics](<../1. Function Type Fundamentals/1.2. Parameters optional default rest and destructuring.md>) owns optional/default/destructured argument contracts.

### 2) **Two-step composition and tuple concatenation**

Compose2 relates the first function's argument tuple to its intermediate result, then relates the second function's input to that result. Its implementation performs those two calls. There is no assertion needed for this particular relationship and no claim that the declaration implements an arbitrary-length pipeline.

Save `composition.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
function compose2<Args extends unknown[], Middle, Result>(
  first: (...args: Args) => Middle,
  second: (value: Middle) => Result,
): (...args: Args) => Result {
  return (...args: Args) => second(first(...args));
}
const add = (a: number, b: number): number => a + b;
const double = (value: number): number => value * 2;
const combined = compose2(add, double);
type CombinedArgs = Expect<Equal<Parameters<typeof combined>, [a: number, b: number]>>;
type CombinedResult = Expect<Equal<ReturnType<typeof combined>, number>>;
console.log(combined(3, 4)); // 14
type Prefix = [label: string];
type Suffix = [count: number, enabled: boolean];
type All = [...Prefix, ...Suffix];
type Positions = Expect<Equal<All, [label: string, count: number, enabled: boolean]>>;
function callAll(...args: All): string { return args.join("/"); }
const prefix = ["prefix"] as const;
const suffix = [7, false] as const;
console.log(callAll(...prefix, ...suffix)); // prefix/7/false
// combined(3); // uncomment: TS2554
// combined("3", 4); // uncomment: TS2345
// compose2(add, (value: string) => value.length); // uncomment: TS2345
// callAll("prefix", 7); // uncomment: TS2554
```

The output is `14` then `prefix/7/false`. The three active equality checks establish the combined callable's two numeric arguments, numeric result and concatenated three-position tuple. The runtime call forwards the arguments to add and sends its result to double. A missing argument yields TS2554; a string in the numeric position yields TS2345; a string-input second function is rejected with TS2345 because it cannot consume add's numeric result.

The All alias concatenates tuple types. CallAll still has an actual runtime implementation; its arguments come from the two spread sources. Omitting enabled yields TS2554. A type-level tuple computation neither executes a new call nor joins runtime arrays by itself. The [primary 4.0 variadic tuple notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-0.html#variadic-tuple-types) introduce composing tuple contracts; the broader [generic variadic owner](<../../../08 Generics Deep Dive/sections/3. Variance and Advanced Generic Patterns/3.3. Variadic tuple generics pipe concat and rest capture.md>) deepens those relationships.

Use this bounded two-step form when it matches the real operation. If a helper needs more stages, receivers, asynchronous results or other call variants, specify and verify those relationships instead of assuming the same declaration handles them. Distinct public argument shapes may still be clearer as [overloads](<./2.1. Function overloads call signatures and implementation compatibility.md>).

### 3) **Capture a parameter tuple and preserve the tested callable relationship**

An Args type parameter can name the entire argument list. In the capture call below, its inferred type is a string/number tuple; the empty call infers an empty tuple. A bare unknown[] parameter accepts an open bag without exposing that named positional result. Any[] suppresses element/arity checks in the unsafe helper, rather than recovering a meaningful forwarded contract.

Save `capture.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
function capture<Args extends readonly unknown[]>(...args: Args): Args { return args; }
const captured = capture("Ada", 30);
const empty = capture();
type Captured = Expect<Equal<typeof captured, [string, number]>>;
type Empty = Expect<Equal<typeof empty, []>>;
type First<T extends readonly unknown[]> = T extends readonly [infer Head, ...unknown[]] ? Head : never;
type Head = Expect<Equal<First<typeof captured>, string>>;
type EmptyHead = Expect<Equal<First<typeof empty>, never>>;
console.log("captured:", captured[0], captured[1], "empty:", empty.length); // captured: Ada 30 empty: 0
function invoke<Args extends readonly unknown[], Result>(fn: (...args: Args) => Result, ...args: Args): Result {
  return fn(...args);
}
function greet(name: string, age: number): string { return `${name} ${age.toFixed(0)}`; }
console.log(invoke(greet, "Ada", 30)); // Ada 30
function wrap<Args extends unknown[], Result>(fn: (...args: Args) => Result): (...args: Args) => Result {
  return (...args: Args) => fn(...args);
}
const wrapped = wrap(greet);
console.log(wrapped("Ada", 31)); // Ada 31
function invokeAny(fn: (...args: any[]) => unknown, ...args: any[]): unknown { return fn(...args); }
try { invokeAny(greet, "Ada", "oops", 999); } // accepted: wrong type/extra argument hidden by any[]
catch (error: unknown) { console.log("unsafe:", error instanceof TypeError ? "TypeError" : "other"); }
// invoke(greet, "Ada"); // uncomment: TS2554
// invoke(greet, "Ada", "oops"); // uncomment: TS2345
// wrapped("Ada", "oops"); // uncomment: TS2345
// captured[0].toFixed(0); // uncomment: TS2551
```

The output is `captured: Ada 30 empty: 0`, `Ada 30`, `Ada 31` and `unsafe: TypeError`. Four equality assertions verify the captured positions, empty tuple and static head extraction. First is a type-level conditional: for an empty tuple it produces never because no required head exists. It does not create a runtime value of never or replace the behavior of an array index read.

Invoke relates its provided function's argument tuple and result to the call. Wrap returns a callable with that same tested parameter/result relationship. The missing age yields TS2554, wrong age in invoke or wrapped yields TS2345, and treating captured's first string slot as a number yields TS2551. By contrast, invokeAny accepts the wrong age and an extra argument, then the numeric operation throws a caught TypeError.

These examples use ordinary receiver-independent functions. A parameter/result wrapper is not proof that every overloaded or generic callable's full set of relationships has been preserved, and it does not bind an object receiver. Inspect the actual callable type, implementation and supported inputs. The [generic scope owner](<./2.2. Generic functions inference constraints defaults and scope.md>) explains per-call and fixed choices; [receiver typing](<../3. Advanced Callable Patterns/3.1. this parameter explicit typing and arrow vs function capture.md>) owns receiver requirements and runtime remedies. Full Parameters/ReturnType extraction belongs in [infer pipelines](<../../../09 Utility Types and Type Transformations/sections/2. Conditional Types/2.3. infer pipelines ReturnType Parameters Awaited.md>).

### 4) **Common confusion**

Readonly on a source array controls operations through that array view; readonly on rest controls operations through the gathered rest view. Spreading does not assign one array to the other. A forced assertion can bypass a real element error without changing the value. Tuple concatenation computes a type, and generic rest names a list relationship; neither automatically implements arbitrary stages, binds a receiver or proves every hidden callable variant.

### 5) **Performance note**

Tuple/type-parameter annotations and equality checks are erased. Rest collection, spreads and the wrapper's function calls remain runtime operations. No checker complexity, tuple-size threshold, allocation benchmark or runtime ranking was measured here. An added type-depth cap can change a transform's resulting contract; use the [measured budget owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.2. Instantiation budgets and TS2589 carve-outs.md>) for that separate problem rather than claiming a fixed number of tuple elements causes TS2589.

### 6) **Mentor note**

Ask the learner why mutableRest may push after receiving source's spread while a direct mutable array assignment fails. A sound answer distinguishes gathered arguments from the original array view. Then replace double with a string-input function and predict the composition error, and compare invoke with invokeAny on the wrong age. Finish by asking what would have to be specified before the wrapper could safely handle a receiver-dependent or overloaded API.
