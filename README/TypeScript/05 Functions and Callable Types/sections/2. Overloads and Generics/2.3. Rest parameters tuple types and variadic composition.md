## 2.3. Rest parameters — tuple types and variadic composition

### 1) **Rest as tuple, spread as call** (`...args: [A, B]` defines arity; `fn(...tuple)` checks assignability — labeled tuples)

**Definition** — a rest param `...args: [A, B, C]` is syntactic sugar for "the final param is a tuple with fixed arity and per-element types"; call-site `fn(...tuple)` spreads a tuple into positional args and is checked element-by-element. Labeled tuples `...args: [path: string, count: number]` preserve names for hover.

**What problem it solves / history** — `function f(...args: any[])` modeled variadic JS but lost arity — `printf("%s %d", 1, "hi")` was accepted. Labeled tuples (TS 4.0) + spread checking let `...args: [format: string, ...values: unknown[]]` model `printf` arity precisely and make `fn(...tuple)` fail when `tuple` length mismatches.

**Modern guidance** — as of TypeScript 5.9 era, use `readonly` labeled tuples for public rest (`...args: readonly [tag: string, value: number]`) so both `readonly` and mutable spreads satisfy arity. Use homogeneou `...args: T[]` only for true bags. Keep tuple labels — they cost nothing at runtime but keep hover readable at call sites.

**Runnable example** — fixed tuple rest with labeled spread (good vs bad, `tsc --strict`):

```typescript
// good — labeled tuple rest enforces per-position types + names in hover
function set(tag: string, ...rest: [value: number, unit: string]): string {
  return `${tag} ${rest[0]}${rest[1]}`;
}
console.log(set("temp", 36, "C")); // temp 36C
const t: [value: number, unit: string] = [10, "px"];
console.log(set("size", ...t)); // ok — tuple satisfies rest

// bad — spread of wrong arity or type fails
// set("temp", 36); // error TS2554: Expected 3 arguments, but got 2 (unit missing)
// set("temp", "hi" as unknown as number, "C"); // error — first rest element must be number

// good — readonly rest accepts readonly spread (caller can hold const tuple)
function join(...parts: readonly string[]): string { return parts.join("/"); }
const ro: readonly string[] = ["a", "b", "c"];
join(...ro); // ok — readonly rest accepts readonly
join("a", "b"); // also ok

// bad — mutable rest rejects readonly without widening (exactOptional port)
// function joinMutable(...parts: string[]): string { return parts.join("/"); }
// joinMutable(...ro); // error under exact caller checks in some libs — widen to readonly
```

**Common confusion** — "rest is always `any[]`" — annotate it; bare `...args` without `noImplicitAny` is an error under `strict`. "Spread works for any array" — `fn(...string[])` does *not* satisfy `...args: [string, number]` because arity is unknown — the checker needs a tuple with known length.

**Performance note** — tuple spread checking is O(arity) — trivial. The readability cost dominates: long unlabeled tuples ` [string, string, number]` hide intent — label them `[tag: string, value: string, count: number]`.

**Mentor note** — have students hover `...t` in `set("size", ...t)` — tooltip shows the rest label `value`, `unit` — then remove labels and show the same type as `[number, string]` with no names — labels win.

### 2) **Variadic tuple composition** (`[...A, ...B]` — concatenating parameter lists for `pipe`/`compose` without overloads)

**Definition** — *variadic tuples* concatenate tuple types `[...A, ...B]` to compose parameter lists — `[a: string, b: number]` + `[c: boolean]` → `[string, number, boolean]`. Used to type `pipe`/`compose` where •each step consumes the previous return and rest composition merges arities without per-step overloads.

**What problem it solves / history** — piping `pipe(f, g, h)(x)` with per-step overloads needed `n` signatures for `n` steps. Variadic tuples (TS 4.0) let one signature describe `pipe(...fns)` by threading `[first arg, ...rest]` tuple concatenation — `Parameters`/`ReturnType` helpers compose steps structurally.

**Modern guidance** — as of TypeScript 5.9 era, use variadic tuples for composition utilities that must thread arity: `type PipeArgs<T extends unknown[]> = [...T]` plus constraints on each step. Keep the generic simple — `type Tail<T extends unknown[]> = T extends [unknown, ...infer R] ? R : never` — and assert the pipe body with casts rather than proving every inference in the type.

**Runnable example** — concat tuples for `compose2` without overloads (good vs bad, `tsc --strict`):

```typescript
// good — compose two functions generically via tuple inference (no overload per arity)
function compose2<A extends unknown[], B, C>(
  f: (...args: A) => B,
  g: (x: B) => C,
): (...args: A) => C {
  return (...args: A) => g(f(...args));
}
const add = (a: number, b: number) => a + b;
const double = (n: number) => n * 2;
const addThenDouble = compose2(add, double);
console.log(addThenDouble(3, 4)); // 14 — args [number, number] threaded through add

// good — concat tuple types for parameter list merging (hover shows concatenated arity)
type Args1 = [a: string];
type Args2 = [b: number, c: boolean];
type All = [...Args1, ...Args2]; // [string, number, boolean]
function callAll(...args: All): void { console.log(args); }
callAll("hi", 42, true);

// bad — overload-per-step scales poorly (3 steps = 3 overloads, 10 steps = 10)
// function pipeOverload(...fns: Function[]): unknown // too loose
// fix — one variadic tuple signature covers n steps

// good — spread a concatenated tuple at call site
const prefix: Args1 = ["prefix"];
const suffix: Args2 = [7, false];
callAll(...prefix, ...suffix); // ok — two spreads satisfy All
```

**Common confusion** — "`[...A, ...B]` is array concat at runtime" — at the type level it merges tuples structurally; at runtime you still spread `...prefix, ...suffix` positionally. "Variadic tuple keeps labels" — labels are preserved on concatenation but may collapse if spread across many merges.

**Performance note** — deeply nested `[...[...A, ...B], ...C]` recursions on >20-element tuples can cause `TS2589: Type instantiation is excessively deep` — keep tuple compositions flat and bounded (the same depth budget as recursive objects in [3.1. Recursive object types](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.1. Recursive object types and self-referential structures.md>)).

**Mentor note** — have students hover `All` to see the concatenated labels — discuss when to stop adding steps to `pipe` (3 steps readable, 12 steps opaque) even if the type could support more.

### 3) **Generic rest and `infer`** (how `function call<T extends unknown[]>(...args: T)` captures full arity and why `any[]` loses it)

**Definition** — a *generic rest* `function call<T extends unknown[]>(...args: T): void` captures the *entire* argument list as tuple `T` — per-call inference remembers `[string, number]` as `T`, not as `unknown[]`. `infer` on rest positions (`T extends [infer A, infer B]`) decomposes that captured tuple for mapping. `any[]` erases the capture — `T = any[]` satisfies every call and recovers nothing for callers.

**What problem it solves / history** — capturing arity generically lets utilities like `call(fn, ...args: Parameters<typeof fn>)` enforce that `args` matches `fn` without listing each arity. `infer` (TS 2.8) lets the utility peel the first/second element for conditional returns.

**Modern guidance** — as of TypeScript 5.9 era, use generic rest (`<T extends unknown[]>` or `<T extends readonly unknown[]>`) for any helper that forwards or wraps a callable — `apply`, `memoize`, `debounce`. Use `any[]` only at a narrow boundary where you immediately narrow with a predicate (see [2.2. unknown](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>) pattern) — otherwise it leaks.

**Runnable example** — generic rest capture vs `any[]` leak (good vs bad, `tsc --strict`):

```typescript
// good — generic rest captures full arity; spread is checked against fn
function invoke<T extends readonly unknown[], R>(fn: (...args: T) => R, ...args: T): R {
  return fn(...args);
}
function greet(name: string, age: number): string { return `${name} ${age}`; }
invoke(greet, "Ada", 30); // ok — T=[string, number]
 // invoke(greet, "Ada"); // error — missing second arg (T needs [string, number])
 // invoke(greet, "Ada", "oops"); // error — second arg must be number

// good — wrapping a callable while preserving its signature via Parameters/ReturnType
function wrap<F extends (...args: any[]) => any>(fn: F): (...args: Parameters<F>) => ReturnType<F> {
  return (...args: Parameters<F>) => fn(...args) as ReturnType<F>;
}
const wrappedGreet = wrap(greet);
wrappedGreet("Ada", 30); // ok — Parameters<Greet> = [string, number]

// bad — any[] generic rest (or any[] param) disables arity and leaks
function invokeAny(fn: (...args: any[]) => unknown, ...args: any[]): unknown {
  return fn(...args);
}
invokeAny(greet, "Ada", "oops", 999); // compiles — any[] swallows extra args and wrong types
// fix — generic rest above recovers checking

// good — infer on rest to map tuple elements
type First<T extends readonly unknown[]> = T extends readonly [infer A, ...unknown[]] ? A : never;
type F = First<[string, number, boolean]>; // string
```

**Common confusion** — " `...args: T` with `T=any[]` captures arity" — `any[]` erases per-element types so `Parameters<F>` collapses to `any[]` — no check. "`T extends unknown[]` is the same as `...args: unknown[]`" — no, `T` *names* the tuple so `Parameters<F>` can recall it; `unknown[]` alone is a bag with no recall.

**Performance note** — generic rest instantiates `T` per call — O(calls) — same cost as per-call generics in [2.2](<./2.2. Generic functions inference constraints defaults and scope.md>). Very large rest spreads (`...args: [...A, ...B, ...C, ...D]` with 30+ elements) can hit instantiation depth — keep wrappers shallow.

**Mentor note** — contrast `invoke` (captured `T`) vs `invokeAny` (leaked `any[]`) with the same wrong call — `invoke` shows a per-element error, `invokeAny` shows nothing — students see the stub `T` remember the arity.
