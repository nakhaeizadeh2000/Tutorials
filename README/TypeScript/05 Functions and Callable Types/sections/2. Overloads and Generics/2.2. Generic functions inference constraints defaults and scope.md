## 2.2. Generic functions — inference, constraints, defaults and scope

A generic signature describes a relationship that stays true for different input types. An identity function returns its input's type; a mapper relates the collection's element type to the callback's input and its result to a new collection. The implementation must work for every type allowed by the signature, rather than choosing a convenient type inside its body.

Examples use TypeScript 7.0.2 / Node 20.20.2, verified 2026-10-14. Save each named file in a new directory without a tsconfig.json. Run `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`, replacing FILE with inference, constraints, scope or decoder. Intentional failures are commented out. Activate one indicated example at a time and replace `--outDir dist` with `--noEmit` to observe the diagnostic without running rejected code.

### 1) **Call-site inference: relate the input to the result**

For identity<T>(value: T): T, each call supplies evidence for T. The literal calls below retain 42 and hi as literal types. Passing a let-bound string supplies the broader string type that the source already has. Writing identity<string> deliberately chooses that broader contract. The active equality checks distinguish these results without relying on an editor tooltip.

Save `inference.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
function identity<T>(value: T): T { return value; }
const numberLiteral = identity(42);
const stringLiteral = identity("hi");
const unionLiteral = identity(Math.random() > 0.5 ? 1 : "a");
let text = "hi";
const widened = identity(text);
const explicit = identity<string>("hi");
type N = Expect<Equal<typeof numberLiteral, 42>>;
type S = Expect<Equal<typeof stringLiteral, "hi">>;
type U = Expect<Equal<typeof unionLiteral, 1 | "a">>;
type W = Expect<Equal<typeof widened, string>>;
type E = Expect<Equal<typeof explicit, string>>;
function mapValues<T, U>(values: readonly T[], transform: (value: T) => U): U[] {
  return values.map(transform);
}
const labels = mapValues([1, 2, 3], value => value.toFixed(1));
type Labels = Expect<Equal<typeof labels, string[]>>;
function makeArray<T>(length: number, value: T): T[] {
  return Array.from({ length }, () => value);
}
const empty = makeArray(0, "placeholder");
const explicitEmpty = makeArray<string>(0, "placeholder");
type Empty = Expect<Equal<typeof empty, string[]>>;
console.log(numberLiteral, stringLiteral, widened, explicit); // 42 hi hi hi
console.log(labels.join(",")); // 1.0,2.0,3.0
console.log(empty.length, explicitEmpty.length); // 0 0
// const wrong: string = identity(42); // uncomment: TS2322
// mapValues([1, 2], (value: string) => value.length); // uncomment: TS2322
```

The three output lines are `42 hi hi hi`, `1.0,2.0,3.0` and `0 0`. The random branch is used only for its static union assertion, so the documented output is deterministic. All seven equality checks pass. The runtime strings remain the same even where their static types differ.

MapValues obtains number for T from the array and string for U from the callback's returned expression. Its callback therefore receives a number without a repeated parameter annotation. The empty makeArray call still has a value argument providing evidence: zero length does not erase the placeholder's element type. Both the inferred and explicit calls produce empty string arrays here. A factory with no argument evidence is a different case, covered in the [inference-control owner](<../../../08 Generics Deep Dive/sections/1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>).

Activate wrong to see TS2322: a numeric identity result does not become string because a consumer requests it. Activate the string-parameter mapper to see TS2322 on its numeric array elements. These errors preserve the relationship that an any-returning stand-in would conceal. Use inference when it describes the intended contract; select explicit arguments when the API needs a chosen element/result contract. There is no rule that inference always widens literals or selects a universal widest type. The [primary generic-functions explanation](https://www.typescriptlang.org/docs/handbook/2/functions.html#generic-functions) teaches the input/output relationship; the deeper owner explains competing candidates and NoInfer.

### 2) **Constraints give body guarantees; defaults fill missing choices**

The constraint T extends { id: string } gives the body permission to read id. Returning the original T preserves the caller's additional name field. It does not permit constructing an arbitrary replacement that merely meets the constraint: a caller's T can require members beyond id. This is the distinction explained in the [primary constrained-values example](https://www.typescriptlang.org/docs/handbook/2/functions.html#working-with-constrained-values).

Save `constraints.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
function withId<T extends { id: string }>(value: T): T {
  console.log(value.id.toUpperCase());
  return value;
}
const user = withId({ id: "u1", name: "Ada" }); // U1
type User = Expect<Equal<typeof user, { id: string; name: string }>>;
console.log(user.name); // Ada
// withId({ name: "Ada" }); // uncomment: TS2353
// function readId<T>(value: T): string { return value.id; } // uncomment: TS2339
// function replace<T extends { id: string }>(value: T): T {
//   return { id: value.id }; // uncomment all three lines: TS2322
// }
type Box<T = string> = { value: T };
function unwrap<T = string>(box: Box<T>): T { return box.value; }
const stringBox: Box = { value: "hello" };
const numberBox: Box<number> = { value: 42 };
const firstValue = unwrap(stringBox);
const secondValue = unwrap(numberBox);
type NumberValue = Expect<Equal<typeof secondValue, number>>;
console.log(firstValue, secondValue); // hello 42
function emptyValues<T = string>(): T[] { return []; }
const defaulted = emptyValues();
const selected = emptyValues<number>();
function first<T = string>(values: readonly T[]): T | undefined { return values[0]; }
const noFirst = first([]);
type Defaulted = Expect<Equal<typeof defaulted, string[]>>;
type Selected = Expect<Equal<typeof selected, number[]>>;
type NoFirst = Expect<Equal<typeof noFirst, undefined>>;
console.log(defaulted.length, selected.length, noFirst); // 0 0 undefined
// type Invalid<T extends { id: string } = number> = T; // uncomment: TS2344
```

The output is `U1`, `Ada`, `hello 42` and `0 0 undefined`. All five equality checks pass. Missing id is rejected with TS2353; reading id from an unconstrained T yields TS2339. Activate the complete replace fragment to observe TS2322: { id } may satisfy the constraint while failing a more specific T. Returning the supplied object avoids discarding its required members.

Box defaults its type argument to string when the alias is used without one. Box<number> remains legal, and unwrap infers number from that box despite its own default of string. EmptyValues has no argument inference site, so its bare call uses the default string; its explicit number call chooses number. First([]) supplies an empty literal from which this call infers never, so the result is undefined rather than using string. A default supplies a missing type choice; it does not populate an empty array or initialize a runtime value.

A default must satisfy an accompanying constraint. Activate Invalid to see TS2344. Keep a constraint as small as the body requires, and choose a default that represents the API's ordinary omitted-type contract. Avoid an asserted generic return whose only evidence is a caller's angle brackets. The [primary default rules](https://www.typescriptlang.org/docs/handbook/2/generics.html#generic-parameter-defaults) distinguish fallback selection from a bound.

### 3) **Generic scope: a fresh call choice or a fixed member contract**

A call signature containing <T, U> lets each invocation select new types. A type alias Transform<T, U> receives its choices when instantiated; Transform<number, string> then accepts numbers and produces strings for every call through that view. Both forms are useful. Choose the location from the relationship the consumer needs, rather than assuming every stored callable must be generic per call.

Save `scope.ts`:

```typescript
export {};
type Mapper = { <T, U>(values: readonly T[], transform: (value: T) => U): U[] };
const mapper: Mapper = (values, transform) => values.map(transform);
const numbers = mapper([1, 2], value => value * 2);
const strings = mapper(["a"], value => value.toUpperCase());
console.log(numbers.join(","), strings.join(",")); // 2,4 A
type Transform<T, U> = (value: T) => U;
const formatNumber: Transform<number, string> = value => value.toFixed(1);
console.log(formatNumber(3)); // 3.0
// formatNumber("hi"); // uncomment: TS2345
type Box<T> = { value: T; get(): T; map<U>(transform: (value: T) => U): Box<U> };
function box<T>(value: T): Box<T> {
  return {
    value,
    get() { return this.value; },
    map<U>(transform: (value: T) => U): Box<U> { return box(transform(this.value)); },
  };
}
const numberBox = box(42);
const textBox = numberBox.map(value => `n=${value}`);
const booleanBox = numberBox.map(value => value > 0);
console.log(numberBox.get(), textBox.get(), booleanBox.get()); // 42 n=42 true
// numberBox.value = "hi"; // uncomment: TS2322
```

The output is `2,4 A`, `3.0` and `42 n=42 true`. Mapper serves numeric and string collections through one generic value. FormatNumber has a fixed number-to-string contract, so the commented string argument is rejected with TS2345. NumberBox retains its number value contract; assigning a string yields TS2322.

The box combines both scopes: T belongs to the container, while each map invocation chooses a fresh U from its callback's result. The first call creates a string box and the next creates a boolean box. For an existing Array<number>, the element contract is similarly fixed while a map callback can choose a new result type. Generic scope describes the static contract; the runtime implementation still has to create and return the appropriate value. The full declaration-site comparison belongs in [generic scope](<../../../08 Generics Deep Dive/sections/1. Generic Fundamentals/1.3. Generic scope per-call vs per-value and declaration sites.md>).

### 4) **A generic result needs real runtime evidence at a boundary**

A caller-written T cannot check a parsed value. Make the result depend on an implementation that decodes unknown input, so inference and runtime evidence have a concrete connection. This small local example replaces the unsafe pattern of asserting fetched JSON as an arbitrary Promise<T>; it exercises the boundary without a network dependency.

Save `decoder.ts`:

```typescript
export {};
function parseText<T>(text: string, decode: (raw: unknown) => T): T {
  const raw: unknown = JSON.parse(text);
  return decode(raw);
}
type User = { id: string; name: string };
function decodeUser(raw: unknown): User {
  if (typeof raw !== "object" || raw === null ||
      !("id" in raw) || typeof raw.id !== "string" || raw.id.length === 0 ||
      !("name" in raw) || typeof raw.name !== "string") {
    throw new TypeError("expected nonempty id and string name");
  }
  return { id: raw.id, name: raw.name };
}
const user = parseText('{"id":"u1","name":"Ada"}', decodeUser);
console.log(user.id, user.name.toUpperCase()); // u1 ADA
for (const text of ['null', '{"id":"","name":"Ada"}', '{"id":"u1","name":3}', '{"name":"Ada"}']) {
  try { parseText<User>(text, decodeUser); }
  catch (error: unknown) { console.log(error instanceof TypeError ? "invalid User" : "other"); }
}
// Four invalid User lines; explicit User arguments do not bypass the decoder.
// parseText<number>('42', decodeUser); // uncomment: TS2345
```

The output is `u1 ADA`, followed by four `invalid User` lines. ParseText infers User from decodeUser's return. The same decoder rejects null, an empty id, a numeric name and a missing id even when the call explicitly selects User. Activating the number-result call yields TS2345 because a User decoder cannot establish number.

The decoder promises a nonempty string id and a string name, and reconstructs those two selected fields. It does not establish an email policy, a database identity or an immutable object. JSON syntax errors propagate separately from the chosen shape error. Keep the full parser design in [boundary validation](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>); the purpose here is to show why a generic result must relate to evidence rather than a free assertion.

### 5) **Common confusion**

T is tracked checking information, whereas any suppresses useful restrictions. Literal identity calls, an already widened source and an empty collection are distinct inference situations. A constraint describes what the body may assume; it does not discard extra caller members. A default gives a fallback type choice, and a fixed container can still have methods with their own fresh type parameters. Finally, neither a constraint nor an explicit type argument executes validation.

### 6) **Performance note**

Type parameters, constraints, defaults and equality checks are erased. Array construction, mapping, JSON parsing and decoding remain runtime work. This lesson measures no checker, editor or runtime performance; no O(1) inference guarantee or speed ranking follows from the number of type parameters. Use the [measurement workflow](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) for an actual slow workload, and preserve the tested input/output contract during any simplification.

### 7) **Mentor note**

Ask the learner to predict identity(42), identity(text), makeArray(0, "placeholder"), emptyValues() and first([]) before revealing the equality checks. A sound answer names the evidence site and distinguishes a type default from a runtime fallback. Then ask whether withId may replace its input with only { id }: it cannot promise the caller's richer T after discarding its fields. Finish by mapping T and U in the box example and explaining why parseText<User> still rejects a numeric name.
