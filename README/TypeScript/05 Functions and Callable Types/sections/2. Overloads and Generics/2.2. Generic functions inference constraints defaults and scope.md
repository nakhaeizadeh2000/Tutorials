## 2.2. Generic functions — inference, constraints, defaults and scope

### 1) **Call-site inference** (`function id<T>(x: T): T` — how `T` is inferred from arguments, why inference is per-call)

**Definition** — a *generic function* declares type parameters `<T>` on its call signature — `function id<T>(x: T): T` — and each call *infers* `T` from the actual arguments. Inference is per-call, not per-declaration: one call `id(42)` infers `T=number`, the next `id("hi")` infers `T=string`, and the implementation is checked once against the generic shape.

**What problem it solves / history** — without generics, `function id(x: any): any` loses the input→output correlation (`id(42)` returns `any`). Generics (TS 0.9) preserve that correlation with zero runtime cost — the call-specific `T` is a compile-time witness that input and output share a type. Inference lets callers omit `<T>` (`id(42)` not `id<number>(42)`) because the argument already witnesses `T`.

**Modern guidance** — as of TypeScript 5.9 era, prefer generic inference over explicit `<T>` at call sites — `map([1,2], n => String(n))` infers `T=number` — and only write `fn<string>(x)` when inference would widen incorrectly (empty array `[]` or literal `"a"` vs `string`). Keep inference site simple: one generic param inferred from one argument position is fastest and clearest.

**Runnable example** — per-call inference and explicit fallback (good vs bad, `tsc --strict`):

```typescript
// good — inference from argument preserves input→output correlation
function id<T>(x: T): T { return x; }
const n = id(42); // T=number, n: number
const s = id("hi"); // T=string, s: string
const inferred = id(Math.random() > 0.5 ? 1 : "a"); // T=number|string — widest common

// good — two params inferred jointly (array + mapper)
function map<T, U>(arr: T[], fn: (x: T) => U): U[] {
  return arr.map(fn);
}
const mapped = map([1, 2, 3], (x) => x * 2); // T=number from [1,2,3], U=number from (x)=>number

// good — explicit <T> when inference has no value to infer from
function makeArray<T>(length: number, value: T): T[] {
  return Array.from({ length }, () => value);
}
const empty = makeArray<string>(0, "placeholder"); // T=string explicit — otherwise never/unknown
// const badInference = makeArray(0, undefined); // T=undefined — probably not intended, annotation helps

// bad — using any to fake correlation that generic gives for free
function idAny(x: any): any { return x; }
const anyResult: string = idAny(42); // any leaks — assignment ok but runtime is number pretending to be string
// fix — generic id<T>(x: T): T keeps correlation without any
```

**Common confusion** — "generic means `any` with a name" — no, `T` is a *specific* unknown per call that the checker tracks; `any` is compatible everywhere, `T` is only equal to itself for that call. "Inference picks the best `T`" — inference picks the *widest* type that satisfies all sites (see `1 | "a"` → `number|string`), not the narrowest.

**Performance note** — one generic param inferred from one argument is O(1). Multi-site inference (`T` from `a: T` and `b: T` with `a=1, b="hi"`) forces the checker to compute a common supertype — still cheap, but `T` from `typeof cfg` + `keyof` chains can amplify on large codebases. No runtime cost — generics erase.

**Mentor note** — demo `id(42)` hover shows `number`, `id("hi")` shows `string` — same `id<T>` declaration, different witnesses. Ask "what is `T` in `id(42)`?" — correct answer is *per-call, inferred as number*.

### 2) **Constraints and defaults** (`<T extends { id: string }>` vs `<T = string>` — what `extends` guarantees inside the body)

**Definition** — a *constraint* `T extends U` says "whatever `T` is, it has *at least* `U`'s members" — inside the body you may read `U`'s members without narrowing. A *default* `T = Default` says "if inference or explicit arg provides no `T`, use `Default`" (defaults are fillers, not constraints).

**What problem it solves / history** — unconstrained `T` has no members — `function f<T>(x: T){ x.id }` errors because not every `T` has `id`. `T extends { id: string }` adds the proof the body needs while callers may pass richer `T` (`{ id, name }`). Defaults (TS 2.3) mirror function param defaults for types — `type FetchOpts<T = string>` lets most callers omit `T`.

**Modern guidance** — as of TypeScript 5.9 era, constrain only what the body *reads* — `T extends { id: string }` not `T extends User` if you only need `id`. Use defaults for public generic APIs where one `T` covers 90% of calls (e.g., `ApiResponse<T = unknown>`). Never use `T extends any` to "constrain" — it constrains nothing; leave unconstrained when no members are needed.

**Runnable example** — constrained read and default filler (good vs bad, `tsc --strict`):

```typescript
// good — constraint guarantees 'id' inside body; callers may pass richer T
function withId<T extends { id: string }>(obj: T): T {
  console.log(obj.id.toUpperCase()); // ok — constraint proves id exists and is string
  return obj;
}
const user = withId({ id: "u1", name: "Ada" }); // T={ id:string; name:string } — preserved
// withId({ name: "Ada" }); // error — missing id

// good — default fills when no inference site provides T
type Box<T = string> = { value: T };
function unwrap<T = string>(box: Box<T>): T { return box.value; }
const b1: Box = { value: "hello" }; // T default string
const b2: Box<number> = { value: 42 };
console.log(unwrap(b1)); // string via default
console.log(unwrap(b2)); // number via explicit Box<number>

// good — constraint + default together for fetch helper
function fetchJson<T extends object = Record<string, unknown>>(url: string): Promise<T> {
  return fetch(url).then((r) => r.json() as Promise<T>);
}
fetchJson("/api/user"); // T default Record — caller not forced to annotate

// bad — unconstrained T trying to read members
// function bad<T>(x: T): string { return x.id; } // error — 'id' not on unknown T
// fix — add extends { id: string }

// bad — default hides missing inference (empty array trap)
function first<T = never>(arr: T[]): T | undefined { return arr[0]; }
const empty = first([]); // T inferred never? Actually default never — empty call infers never → undefined
const explicit = first<number>([]); // explicit fixes empty literal having no element to infer from
```

**Common confusion** — "default constrains `T`" — no, `T = string` does not require `T` to extend `string`; callers may still pass `number` — default only applies when `T` is otherwise *unprovided*. " `extends` narrows callers" — callers are *accepted* if they satisfy the constraint, not narrowed to it — `withId({ id, name, extra })` keeps `name`/`extra`, not just `{ id }`.

**Performance note** — constrained generics with object constraints `{ id: string }` are checked per call via structural assignability O(members) — trivial. No emit — constraints erase.

**Mentor note** — show error on `x.id` without constraint, then fix with `T extends { id: string }` — students see the stub `T` acquire one member to read. Ask "does `T = string` prevent `T=number`?" — answer is *no* (default is filler, not bound).

### 3) **Generic scope and capture** (type params live on the *call signature*, not the implementation — when to put `<T>` on the function vs on the interface)

**Definition** — a generic type param belongs to a *call signature* — `interface Fn { <T>(x: T): T }` is generic *per call* (each call picks a new `T`); `interface Fn<T> { (x: T): T }` is generic *per value* (`Fn<number>` fixes `T` for every call). `function f<T>(x: T): T` is sugar for a per-call signature on a named function.

**What problem it solves / history** — per-call generics model `Array.map` where `T` (element) and `U` (mapped) are chosen fresh per invocation; per-value generics model `Array<T>` where `T` is fixed when the array is created. Mixing them scrambles whether a second call can change `T`.

**Modern guidance** — as of TypeScript 5.9 era, put `<T>` on the *function* (per-call) for utilities that are stateless across calls (`identity`, `map`, `pick`). Put `<T>` on the *interface/type* (per-value) for containers whose members share `T` (`Box<T>`, `Repository<T>`, `Map<K,V>`). When a callable is stored as a property, per-call is almost always correct — per-value bakes a single `T` into the stored binding.

**Runnable example** — per-call vs per-value, inference per invocation (good vs bad, `tsc --strict`):

```typescript
// good — per-call generic: each call picks fresh T
type Mapper = { <T, U>(arr: T[], fn: (x: T) => U): U[] };
const mapper: Mapper = (arr, fn) => arr.map(fn);
const n = mapper([1, 2], (x) => x * 2); // T=number,U=number
const s = mapper(["a"], (x) => x.toUpperCase()); // T=string,U=string — different T per call

// good — per-value generic: T fixed when the value is created
type Box<T> = { value: T; get(): T };
type NumberBox = Box<number>;
const nb: NumberBox = { value: 42, get() { return this.value; } };
// nb.value = "hi"; // error — T fixed as number

// bad — per-value when per-call was intended (bakes T across calls)
type BadMapper<T> = { (arr: T[], fn: (x: T) => T): T[] };
const badMapper: BadMapper<number> = (arr, fn) => arr.map(fn);
// badMapper(["a"], (x) => x.toUpperCase()); // error — BadMapper<number> cannot map strings (T baked)

// good — generic function (per-call) is sugar for per-call interface
function identity<T>(x: T): T { return x; }
const a1 = identity(42); // per-call T=number
const a2 = identity("hi"); // per-call T=string

// bad — trying to infer a per-value T from a call argument (T already fixed at binding site)
// const box: Box<number> = { value: 42, get() { return this.value; } };
// identity(box.value); // T already fixed as number in Box<number>, not per-call
```

**Common confusion** — "`<T>` on `type F<T> = ...` is per-call" — per-value — you pick `T` when you instantiate `F<string>`; "`<T>` on `function f<T>` is per-value" — per-call — you pick `T` when you *call* `f`. "I can put `<T>` on both" — `type F<T> { <U>(x: T): U }` gives one baked `T` and one fresh `U` per call — rare but legal (container plus mapper).

**Performance note** — per-call generics create a fresh instantiation per invocation — checker work O(calls); per-value creates one instantiation per binding. No runtime difference — both erase. Prefer per-call for helpers to avoid instantiating many distinct `Mapper<number>`/`Mapper<string>` bindings.

**Mentor note** — show `Mapper` vs `BadMapper<number>` side-by-side — students call each twice with different element types and see the second mapper reject the alternative type — reframes "where does `<T>` live?" as "when is `T` chosen?".
