## 4.1. Functions checklist — mental models mentors insist on

Review a callable by following one real call: identify its public view, the supplied arguments, the relationship inferred for that call, and the evidence available after its result. A signature makes promises to callers; the implementation and runtime invocation must fulfill them. Use this checklist to locate the right question before reaching for an assertion or compiler option.

The synthesis program below uses TypeScript 7.0.2 / Node 20.20.2, verified 2026-10-14. Its four equality assertions and runtime outputs provide evidence for these particular contracts. They do not certify every overload, callback host or external input.

### 1) **Read the caller's contract and verify the body**

Pick exposes separate string and number overloads. Its implementation accepts their union and returns values appropriate to the executed branch. The synthesis prints HI for a string call and 6 for a number call; the caller's inferred result types are string and number. A boolean call is rejected with TS2769. The broad body is not another public overload.

Compatibility alone does not prove every overload's input/output correlation. Review the branches and observe each promised behavior. Likewise, a void callback view permits a caller to ignore a result; it does not erase the result or handle a returned promise. The host's implementation determines whether an asynchronous callback is awaited. [Overload contracts](<../2. Overloads and Generics/2.1. Function overloads call signatures and implementation compatibility.md>) and [return views](<../1. Function Type Fundamentals/1.3. Return types void never and contextual inference.md>) supply the worked contrasts.

For callback substitution, name what the host supplies: an Animal-capable handler can serve a Dog supplier; a Dog-only handler cannot serve every Animal supplier. Method signatures retain a checking exception. For extracted methods, identify the actual receiver too. [Callback variance](<../3. Advanced Callable Patterns/3.2. Callback variance strictFunctionTypes and bivariance pitfalls.md>) and [receiver typing](<../3. Advanced Callable Patterns/3.1. this parameter explicit typing and arrow vs function capture.md>) own those independent checks.

### 2) **Trace required positions and spread evidence**

Set needs a tag, number and unit. The readonly pair supplies the two rest positions, producing size 10px. Missing unit gives TS2554; a string value gives TS2345. Tuple labels document positions. They do not create named runtime fields, and an open array does not necessarily promise the same positional list.

Check optional and default positions deliberately. An optional parameter accepts explicit undefined regardless of exactOptionalPropertyTypes; that flag concerns property contracts. A leading default still occupies its positional slot. A readonly spread source can supply elements to a mutable rest array because the function gathers new arguments. [Parameters](<../1. Function Type Fundamentals/1.2. Parameters optional default rest and destructuring.md>) and [tuple forwarding](<../2. Overloads and Generics/2.3. Rest parameters tuple types and variadic composition.md>) own the full source-versus-body distinction. Do not add a cast simply to suppress a missing positional contract.

### 3) **Locate each generic choice and its evidence**

Identity introduces a type parameter per call. The simple direct calls below preserve the literal types 42 and hi; a different signature or widened source may lead to a broader result. Box<number> fixes its element contract for this value, so assigning a string to box.value fails. “Generic” alone does not tell a reviewer whether a choice is fresh per call or already fixed on a container.

Use actual input/output relationships instead of assuming every call widens to a primitive or every empty array selects a default. A generic result derived from unknown JSON also needs a real decoder that checks the promised shape. [Generic functions](<../2. Overloads and Generics/2.2. Generic functions inference constraints defaults and scope.md>) owns those cases; [inference and NoInfer](<../../../08 Generics Deep Dive/sections/1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>) explains competing evidence sites. Constraints supply a body contract; they do not validate runtime input.

### 4) **Check the narrowing contract and its failure path**

The inferred isDog predicate permits bark in the Dog branch and meow in the Cat branch. Assert's condition animal.kind === dog also refines the union after a successful call. On Cat it throws before the second bark. An ordinary void helper would not communicate the same postcondition, and dishonest explicit predicates/assertions can mislead the checker.

Save `checklist.ts` in a fresh directory without tsconfig.json:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
function pick(value: string): string;
function pick(value: number): number;
function pick(value: string | number): string | number {
  return typeof value === "string" ? value.toUpperCase() : value * 2;
}
const text = pick("hi"); const count = pick(3);
type Text = Expect<Equal<typeof text, string>>;
type Count = Expect<Equal<typeof count, number>>;
console.log(text, count);
function set(tag: string, ...rest: [value: number, unit: string]): string {
  return `${tag} ${rest[0]}${rest[1]}`;
}
const pair = [10, "px"] as const;
console.log(set("size", ...pair));
function identity<T>(value: T): T { return value; }
const literal = identity(42);
const word = identity("hi");
type Literal = Expect<Equal<typeof literal, 42>>;
type Word = Expect<Equal<typeof word, "hi">>;
type Box<T> = { value: T; get(): T };
const box: Box<number> = { value: 1, get() { return this.value; } };
console.log(literal, word, box.get());
type Animal = { kind: "dog"; bark(): void } | { kind: "cat"; meow(): void };
const isDog = (animal: Animal) => animal.kind === "dog";
function assert(condition: unknown): asserts condition { if (!condition) throw new Error("not a dog"); }
function demo(animal: Animal): void {
  if (isDog(animal)) animal.bark(); else animal.meow();
  assert(animal.kind === "dog");
  animal.bark();
}
demo({ kind: "dog", bark() { console.log("bark"); } });
try { demo({ kind: "cat", meow() { console.log("meow"); } }); }
catch (error: unknown) { console.log(error instanceof Error ? error.message : "other"); }
// pick(true); // uncomment: TS2769
// set("temp", 36); // uncomment: TS2554
// set("temp", "hi", "C"); // uncomment: TS2345
// box.value = "wrong"; // uncomment: TS2322
// const widened: number = literal; const narrow: 42 = widened; // uncomment: TS2322
// function unchecked(animal: Animal): void { animal.bark(); } // uncomment: TS2339
```

Run `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist checklist.ts`, then `node dist/checklist.js`. Both succeed. Output is `HI 6`, `size 10px`, `42 hi 1`, two `bark` lines, `meow` and `not a dog`. Four live equality assertions verify the two overload result types and two literal types. The final Cat call exercises the other predicate branch and the rejected assertion condition; it does not silently continue through a false guarantee.

Activate one commented line at a time and check with `--noEmit` replacing `--outDir dist` for its stated diagnostic. The ordinary number view assigned from literal can still represent any number; assigning it back to 42 fails. Reading bark before narrowing also fails. [Guards and assertions](<../3. Advanced Callable Patterns/3.3. Type guards predicates asserts and satisfies on functions.md>) owns inferred/explicit/boolean signatures and their trust limits. Satisfies checks a callable against a target, but is not a predicate, exact-arity assertion or runtime adapter by itself.

### 5) **Common confusion**

The public signature and the implementation are related but distinct. A broad implementation signature is hidden from overload callers; a void view does not consume a promise. Generic scope and inference depend on the declaration and evidence, while a predicate's runtime boolean is not the whole static narrowing contract. Successful assertion continuation is conditional on returning normally. Keep the checking claim and observable runtime operation separate at each step.

### 6) **Performance note**

The signature, tuple labels, type parameters, predicate/assertion annotations and equality checks erase. The branches, function calls, rest collection, object access and throw remain runtime work. This checklist measures no runtime or compiler performance. Changing a type spelling does not justify a speed ranking, and hiding a mismatch with a cast does not remove its runtime consequence.

### 7) **Mentor note**

Ask the learner to review three proposed edits: replace pick's branches with return 0, replace Box<number> with a per-call generic getter that casts its stored number, and remove assert's throw. Each edit can misdescribe the behavior promised to callers; changing annotations is not the repair. A sound review requests branch outputs, an evidence-based generic relationship and a rejected-input test. Then ask why the readonly pair call is accepted and why the asserted Cat continuation stops. Assess explanations against the actual program and linked owners rather than memorized slogans.
