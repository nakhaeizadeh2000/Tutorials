## 4.1. Functions checklist — mental models mentors insist on

### 1) **Call signature is the contract** (params are contravariant, returns covariant — signature what callers see, not body)

**Definition** — the *signature* `(x: T) => R` is the only thing callers type-check against. Param positions are *contravariant* (caller supplies supertype → callback must handle it), returns are *covariant* (callback may return subtype). The body may be broader (implementation union) but callers see the narrow overload/generic promise.

**What problem it solves** — anchors the mental model: ask "what does the caller supply vs what does the callable return?" — not "what does the body do?" — to predict assignability, variance, and contextual typing.

**Modern guidance** — as of TypeScript 5.9 era, design signatures for callers (hover clarity) and make the body satisfy the broadest overload. Review signatures by reading them as caller contracts, not implementation sketches.

**Runnable example** — signature vs body (good vs bad):

```typescript
// good — callers see (x: string) => string, body handles string|number broadly
function pick(value: string): string;
function pick(value: number): number;
function pick(value: string | number): string | number {
  return typeof value === "string" ? value.toUpperCase() : value * 2;
}
const s: string = pick("hi"); // caller sees string

// bad — signature says void discard but body returns eagerly (caller's void hides 42 at runtime)
type VoidCb = () => void;
const returns42: () => number = () => 42;
const voidCb: VoidCb = returns42; // ok — void discards, but runtime still 42
// fix — caller typing void ignores return — don't rely on void to hide values
```

### 2) **Arity is type-checked** (optional/default/rest and tuple labels define "enough" arguments — spread checked structurally)

**Definition** — *arity* (how many args and which types) is carried by `?:`, defaults, and labeled tuples `...args: [a: string, b: number]`. `fn(...tuple)` is checked elementwise, not as a bag.

**What problem it solves** — makes `set("temp", 36, "C")` vs `set("temp", 36)` a type error, not a silent `undefined` at runtime.

**Modern guidance** — model required arity with `?:`/tuple, not `any[]`. Use `readonly` tuples so mutable/readonly spreads satisfy rest.

**Runnable example**:

```typescript
function set(tag: string, ...rest: [value: number, unit: string]): string {
  return `${tag} ${rest[0]}${rest[1]}`;
}
set("temp", 36, "C"); // ok
// set("temp", 36); // error — missing unit
const t: [number, string] = [10, "px"];
set("size", ...t); // ok — tuple satisfies rest
```

### 3) **Generic scope lives on the signature** (one inference per call — constraints guarantee properties, defaults fill gaps)

**Definition** — `<T>` on a function is *per-call* — each invocation infers a fresh `T`; `<T>` on a type alias/interface is *per-value* — baked when the container is created.

**What problem it solves** — explains why `map([1,2], n=>String(n))` picks `T=number` per call, while `Box<number>` fixes `T` for every `get()`.

**Modern guidance** — put `<T>` on the function for utilities (`identity`, `map`); on the interface for containers (`Repository<T>`); on both for hybrid `Pipe<T, U>`.

**Runnable example**:

```typescript
function id<T>(x: T): T { return x; }
const a = id(42); // per-call T=number
const b = id("hi"); // per-call T=string

type Box<T> = { value: T; get(): T }; // per-value T fixed
const box: Box<number> = { value: 1, get() { return this.value; } };
```

### 4) **Narrow via the return** (predicates and asserts turn a boolean-returning function into a narrowing tool for callers)

**Definition** — `x is T` and `asserts x is T` tag a boolean/void return as a *proof* for callers — `if (isDog(a))` or `assertIsDog(a)` narrows `a` without a cast.

**What problem it solves** — lifts `in`/`typeof` narrowing into reusable, testable predicates and flat control flow after `assert`.

**Modern guidance** — prefer `x is T` for `if`-branching reuse; `asserts x is T` for unconditional validation that throws; `satisfies` on function literals to keep proofs without widening.

**Runnable example**:

```typescript
type Dog = { kind: "dog"; bark(): void };
type Animal = Dog | { kind: "cat"; meow(): void };
function isDog(a: Animal): a is Dog { return a.kind === "dog"; }
function assertIsDog(a: Animal): asserts a is Dog {
  if (a.kind !== "dog") throw new Error();
}
function demo(a: Animal): void {
  if (isDog(a)) a.bark(); // narrowed
  assertIsDog(a); // also narrowed for rest of scope
  a.bark();
}
```
