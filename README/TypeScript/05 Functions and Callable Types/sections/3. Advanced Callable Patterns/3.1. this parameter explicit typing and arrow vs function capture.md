## 3.1. `this` parameter — explicit typing and arrow vs function capture

A receiver is the value a regular function observes as this during a call. TypeScript can describe a required receiver in the function signature, while JavaScript invocation supplies the actual value. An arrow instead reads this from its surrounding scope. Keeping those two mechanisms separate explains why a well-typed method can still fail after extraction, and why a this:void callback may still use an outer object.

Examples use TypeScript 7.0.2 / Node 20.20.2, verified 2026-10-14. Save each named file in a new directory without tsconfig.json. Run `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`, replacing FILE with receiver, void, hosts or methods. For a commented checking failure, activate that line alone and replace `--outDir dist` with `--noEmit`. Strict enables noImplicitThis and strictBindCallApply for these probes. Runtime mistakes are caught so later remedies execute.

### 1) **Explicit receiver contracts and actual invocation**

Greet needs an object with a string name as its receiver and a greeting as its ordinary argument. The special first this parameter tells the checker about that requirement; it is not a positional argument supplied by greet(context, greeting).

Save `receiver.ts`:

```typescript
export {};
function greet(this: { name: string }, greeting: string): string {
  return `${greeting}, ${this.name}`;
}
const context = { name: "Ada" };
console.log(greet.call(context, "hello"));
console.log(greet.apply(context, ["hey"]));
const bound = greet.bind(context);
console.log(bound("hi"), "arity:", greet.length);
// greet("hello"); // uncomment: TS2684
// greet.call({ wrong: true }, "hello"); // uncomment: TS2353
// greet.bind({ wrong: true }); // uncomment: TS2769
// const badArrow = (this: { name: string }) => "bad"; // uncomment: TS2730
// function untyped(): string { return this.name; } // uncomment: TS2683
```

The output is `hello, Ada`, `hey, Ada` and `hi, Ada arity: 1`. Call supplies the receiver and ordinary arguments immediately. Apply supplies the ordinary arguments in an array. Bind produces a new callable that can later run without a caller-supplied receiver. The emitted greet function has one parameter, greeting, and its length is one; the receiver annotation is erased. [Primary receiver documentation](https://www.typescriptlang.org/docs/handbook/2/classes.html#this-parameters) explains this static contract.

A receiverless greet call yields TS2684. The wrong call object yields TS2353, and the wrong bind object fails overload checking with TS2769. An arrow cannot declare this as a parameter (TS2730). A standalone regular function whose this remains implicit any yields TS2683 when it reads this.name. That last check diagnoses a missing body type; it does not automatically add a receiver requirement to every inferred class method.

Use an explicit receiver when borrowing or extraction makes its requirement important to callers. For a reusable receiverless callback, bind at the boundary or wrap an actual method call. Neither an annotation nor successful argument checking creates runtime binding for an unchecked caller. Full runtime invocation rules belong in [call/apply/bind](<../../../../JavaScript/05 Functions Deep Dive/sections/3. this binding/3.3. call apply bind and bound functions.md>).

### 2) **Void receivers, lexical capture and callback hosts**

This:void describes a callable that does not require a meaningful dynamic receiver. It does not ban reading the this value as a whole or prove that the function is pure. Logging it is legal; reading this.name is rejected because void has no such property. An arrow can satisfy a receiverless contract while capturing an outer Owner.

Save `void.ts`:

```typescript
export {};
function observe(this: void, value: number): void { console.log(this, value); }
observe(1);
observe.call(undefined, 2);
function run(callback: (this: void) => string): string { return callback(); }
class Owner {
  name = "outer";
  make(): (this: void) => string { return () => this.name; }
}
const owner = new Owner();
const captured = owner.make();
console.log(run(captured));
owner.name = "changed";
console.log(run(captured));
// observe.call({ id: 1 }, 1); // uncomment: TS2345
// function wrong(this: void): string { return this.name; } // uncomment: TS2339
```

The output is `undefined 1`, `undefined 2`, `outer` and `changed`. Run calls its callback directly. The arrow created in Owner.make continues to read that owner's name, including the later mutation. It captures access to the object, rather than taking an immutable snapshot of the string. An object supplied to observe.call is rejected with TS2345 under strictBindCallApply; this.name in a void-receiver function yields TS2339. The [primary callback explanation](https://www.typescriptlang.org/docs/handbook/functions.html#this-parameters-in-callbacks) distinguishes a receiver requirement from lexical access.

A callback annotation must also match its host's contract. For TypeScript 7.0.2, the installed Array.forEach declaration accepts a callback without a correlated this parameter and a thisArg of any. Adding this:Context to the callback does not make built-in forEach check that its second argument supplies Context. A custom wrapper can explicitly relate those positions and perform the corresponding call.

Save `hosts.ts`:

```typescript
export {};
type Context = { name: string };
function callback(this: Context, value: number): void {
  console.log(this.name.toUpperCase(), value);
}
[1].forEach(callback, { name: "Ada" });
for (const invoke of [
  () => [1].forEach(callback),
  () => [1].forEach(callback, { wrong: true }),
]) {
  try { invoke(); }
  catch (error: unknown) { console.log(error instanceof TypeError ? "TypeError" : "other"); }
}
function forEachWithThis<T, Receiver>(
  values: readonly T[], fn: (this: Receiver, value: T) => void, context: Receiver,
): void {
  for (const value of values) fn.call(context, value);
}
forEachWithThis([2], callback, { name: "Bo" });
class Labeler {
  name = "outer";
  show(): void {
    forEachWithThis([3], (value) => console.log(this.name, value), { name: "supplied" });
  }
}
new Labeler().show();
// forEachWithThis([2], callback, { wrong: true }); // uncomment: TS2353
```

The output is `ADA 1`, two `TypeError` lines, `BO 2` and `outer 3`. Standard forEach accepts both missing and wrong thisArg; each fails when the callback reads the receiver. ForEachWithThis requires a receiver and uses fn.call(context, value). Its wrong object is rejected with TS2353. The arrow in Labeler.show reads Labeler's name even though the wrapper supplies another object. A host's call mechanism does not rebind an arrow's lexical this.

Prefer an arrow when you intend to access surrounding state; prefer a regular function when the host intentionally supplies a receiver. For an existing library, inspect both its declaration and invocation behavior before relying on a receiver guarantee. A custom wrapper's stronger signature does not retroactively change standard forEach or validate external objects.

### 3) **Implicit methods, explicit requirements and detachment remedies**

A class method's body can infer this as the instance without exposing an explicit receiver requirement on an extracted function. The User comparison shows exactly where checking and runtime behavior diverge.

Save `methods.ts`:

```typescript
export {};
class User {
  name = "Ada";
  greet(greeting: string): string { return `${greeting}, ${this.name}`; }
  checked(this: User, greeting: string): string { return `${greeting}, ${this.name}`; }
  captured = (greeting: string): string => `${greeting}, ${this.name}`;
}
const user = new User();
console.log(user.greet("hi"));
const detached = user.greet;
try { console.log(detached("hi")); } // accepted under strict
catch (error: unknown) { console.log(error instanceof TypeError ? "TypeError" : "other"); }
const checked = user.checked; // extracting the reference is accepted
console.log(checked.call(user, "call"));
const bound = user.checked.bind(user);
const wrapped = (greeting: string) => user.checked(greeting);
const captured = user.captured;
console.log(bound("bound"), wrapped("wrapped"), captured("arrow"));
// checked("hi"); // uncomment: TS2684
// const wrongReceiver = { checked, name: 123 }; wrongReceiver.checked("hi"); // uncomment: TS2739
```

The output is `hi, Ada`, `TypeError`, `call, Ada` and `bound, Ada wrapped, Ada arrow, Ada`. The ordinary detached greet call is accepted under strict, then loses its receiver and throws. Extracting checked is also legal, but calling it directly fails with TS2684 because its signature explicitly requires User. An object holding checked but missing User's greet and captured members also fails the receiver contract with TS2739. Call and bind supply the actual User; wrapped performs a method call on user; the field arrow retains the construction receiver.

Choose the remedy from the intended API. An explicit requirement makes an accidental receiverless checked call visible to TypeScript consumers. Bind or a wrapper provides the runtime invocation needed at a callback boundary. A field arrow is useful when extraction should preserve its instance, with a separate function value per instance. An explicit method receiver is therefore purposeful rather than universally redundant. [Class receiver guidance](https://www.typescriptlang.org/docs/handbook/2/classes.html#this-parameters) and the [runtime lexical-this owner](<../../../../JavaScript/05 Functions Deep Dive/sections/3. this binding/3.2. Arrow lexical this and why callbacks break or heal.md>) cover their respective boundaries.

### 4) **Common confusion**

NoImplicitThis checks an implicit-any body view; it does not infer a detached-call restriction for every method. This:void prevents a meaningful dynamic receiver requirement, not lexical closures or logging. A declared receiver does not bind a function, and built-in forEach does not correlate its any thisArg with a separately annotated callback receiver. Ask who performs the call before treating a signature as an invocation guarantee.

### 5) **Performance note**

Receiver annotations erase and have no direct runtime performance effect. Call, bind, wrapper invocation and field-arrow construction remain real operations. Bind returns a new function value, and a class field arrow is created for each instance; reuse a chosen callback when stable identity is needed for registration/removal. No allocation benchmark or call-versus-arrow speed ranking was measured. Select the behavior first and profile an actual workload before optimizing it.
