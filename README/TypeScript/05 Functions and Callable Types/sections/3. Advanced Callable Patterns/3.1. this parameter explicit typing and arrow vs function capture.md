## 3.1. `this` parameter — explicit typing and arrow vs function capture

### 1) **Explicit `this` parameter** (`function f(this: Context, x: number)` — fake first param that types `this` without emitting)

**Definition** — TypeScript lets you declare a *fake* first parameter `this: T` on a function — `function f(this: { id: string }, x: number): void` — that types what `this` must be when the function is called via `call`/`apply`/`bind` or as a method. `this` is erased (no JS param emitted) and must be first, if present.

**What problem it solves / history** — JavaScript `this` is dynamic — `function handler(){ console.log(this.id) }` may be called as `handler.call(ctx)` or detached as `const h = handler; h()` where `this` becomes `undefined` (strict). Without `this: T`, the checker typed `this` as `any`. Explicit `this` (TS 2.0) plus `--noImplicitThis` lets the checker reject detached calls and enforce `bind`.

**Modern guidance** — as of TypeScript 5.9 era, annotate `this` on functions that *read* `this` and are meant to be borrowed — event handlers, mixin helpers, `Array.forEach` callbacks where `thisArg` matters. Never annotate `this` on arrow functions — arrows capture lexical `this` and cannot be rebound — the checker will error `Arrow function cannot have this parameter`.

**Runnable example** — explicit `this` with `call`/`bind` (good vs bad, `tsc --strict`):

```typescript
// good — explicit this typed, checked at call site
function greet(this: { name: string }, greeting: string): string {
  return `${greeting}, ${this.name}`;
}
const ctx = { name: "Ada" };
console.log(greet.call(ctx, "hello")); // hello, Ada
console.log(greet.bind(ctx)("hi")); // hi, Ada

// bad — calling without correct this is rejected
// greet("hello"); // error TS2684: The 'this' context of type 'void' is not assignable to '{ name: string }'
// const detached = greet;
// detached("hello"); // error — this is void (no context)

// good — interface method with this: void declares "must not use this"
type NoThisCb = (this: void, x: number) => number;
const pure: NoThisCb = (x) => x * 2; // arrow-like pure — cannot access this inside (would error)

// bad — arrow with this param is illegal
// const arrowBad = (this: { name: string }, x: number) => this.name; // error TS2730: Arrow function cannot have 'this' parameter
// fix — use function expression when you need typed this
const arrowFix = function (this: { name: string }, x: number): string {
  return this.name + x;
};
```

**Common confusion** — "`this` param emits as a real param" — no, `function f(this: T, x: number)` emits `function f(x){}` — `this` is erased. "`this: void` means the function has no this" — it means the function *must* be called with no meaningful `this` (detached safe); `this: void` plus passing a `thisArg` is an error.

**Performance note** — explicit `this` erases — zero runtime cost. The cost of *not* typing `this` is the implicit `any` in `noImplicitThis` files, which hides detached-call bugs that surface at runtime as `Cannot read properties of undefined`.

**Mentor note** — demo `detached("hello")` error — students see the checker treat a borrowed function without its context as `this: void` mismatch — reframes `this` as a caller-supplied argument, not intrinsic property.

### 2) **`this` in callbacks** (`--noImplicitThis` and `this: void` on callbacks — why library `forEach` types `this` and how arrow functions erase `this` capability)

**Definition** — library callbacks often accept an optional `thisArg` — `array.forEach(function(this: T, x: T){}, thisArg)`. Typing the callback as `(this: T, x: T) => void` lets the checker enforce that inside the callback `this` has type `T`, and `thisArg` supplies it. Arrow functions *capture* `this` lexically, so they never observe `thisArg` — libraries type `this: void` for arrow-friendly callbacks or `this: T | void` for both.

**What problem it solves / history** — `Array.prototype.forEach(callback, thisArg)` passes `thisArg` as `this` to `callback` — without typing, `function(x){ this.id }` was `any`. `this: T` on the callback (TS 2.0) lets `forEach` declare `forEach(callback: (this: T, value: T) => void, thisArg?: T)` so the checker's `noImplicitThis` bridges the two.

**Modern guidance** — as of TypeScript 5.9 era, type callbacks that use `this` with `this: T` *and* document the `thisArg` param; type pure callbacks with `this: void` to prove they don't rely on `this` (safe to store/detach). Prefer arrow callbacks for `this: void` cases — they capture outer `this` and are never confused by a stale `thisArg`.

**Runnable example** — `thisArg` typing and arrow capture (good vs bad, `tsc --strict`):

```typescript
// good — typed thisArg threads through forEach
function forEachWithThis<T, This>(arr: T[], cb: (this: This, value: T) => void, thisArg: This): void {
  for (const v of arr) cb.call(thisArg, v);
}
const ctxObj = { label: "item" };
forEachWithThis(["a", "b"], function (this: { label: string }, value: string) {
  console.log(this.label, value); // this: { label: string } from thisArg
}, ctxObj);

// good — pure callback typed this: void (no reliance on this)
function forEachPure<T>(arr: T[], cb: (this: void, value: T) => void): void {
  for (const v of arr) cb(v);
}
forEachPure([1, 2], (value) => console.log(value * 2)); // arrow — this is lexical, not used
forEachPure([1, 2], function (value) {
  // console.log(this); // error — this: void
  console.log(value);
});

// bad — callback using this without typing is any
function forEachUntyped(arr: string[], cb: (value: string) => void): void {
  for (const v of arr) cb(v);
}
forEachUntyped(["a"], function (value) {
  // console.log(this.id); // this is any (if noImplicitThis off, silently any)
  // fix — type cb: (this: { id: string }, value: string) => void
});

// bad — arrow observing thisArg (arrows ignore thisArg)
forEachWithThis(["a"], ((value) => {
  // console.log(this); // lexical this (module/undefined), not thisArg
  console.log(value);
}) as (this: { label: string }, value: string) => void, ctxObj);
// fix — use function expression when you need thisArg, arrow when you need this: void
```

**Common confusion** — "arrow callbacks receive `thisArg`" — no, arrows capture lexical `this` at definition, `thisArg` is ignored — use `function` for `this`-dependent callbacks. "`this: void` bans calling the callback with `.call`" — it bans *relying* on `this` inside, not the call form — `.call(ctx, value)` still compiles but `this` inside is `void`, not `ctx`.

**Performance note** — `this` threading adds one `Function.prototype.call` dispatch per iteration — same as any `this`-dependent loop. Arrow `this: void` avoids `call` — direct `cb(value)` is one indirect call — slightly faster in hot loops.

**Mentor note** — pair a `function` vs `arrow` callback on `forEachWithThis` side-by-side and log `this` — `function` logs `thisArg`, `arrow` logs `undefined`/outer — reframing "when does `this` vary?".

### 3) **When to annotate** (methods vs standalone functions vs `bind`/`call` — where `this` actually varies)

**Definition** — *methods* (`obj.method()`) have an implicit `this` bound to `obj`; *standalone* functions have `this` supplied by the caller (`call`/`bind`); *arrows* have no own `this` (lexical). Annotate `this` only where `this` *varies* at call sites — mixed-`this` helpers, detacheable methods, or library `thisArg` patterns.

**What problem it solves / history** — most methods never need an explicit `this` — `this` is typed from the class/interface automatically. Explicit `this` is for the outliers where the same function body runs against different contexts (`mixin` helpers, `Function.prototype.call` utilities).

**Modern guidance** — as of TypeScript 5.9 era, omit `this` on class methods and object methods — the instance type is implicit. Add `this: This` on borrowed helpers (`function logName(this: { name: string }){}`) that will be `call`-ed or assigned. Mark detached-safe callbacks `this: void`. Use `--noImplicitThis` so untyped `this` is an error, not `any`.

**Runnable example** — method (implicit) vs borrowed helper (explicit) (good vs bad, `tsc --strict`):

```typescript
// good — class method needs no explicit this (instance is implicit)
class User {
  constructor(public name: string) {}
  greet(greeting: string): string {
    return `${greeting}, ${this.name}`; // this: User (implicit)
  }
}
const u = new User("Ada");
console.log(u.greet("hi"));

// good — borrowed helper needs explicit this so call sites are checked
function formatName(this: { name: string }, prefix: string): string {
  return `${prefix} ${this.name}`;
}
const a = { name: "Ada" };
const b = { name: "Bo" };
console.log(formatName.call(a, "Ms.")); // Ms. Ada
console.log(formatName.call(b, "Mr.")); // Mr. Bo
// formatName("Mr."); // error — this missing

// good — detaching a method needs bind or arrow wrapper (this would be lost)
const greetFn = u.greet.bind(u);
console.log(greetFn("hello")); // hello, Ada — bind fixed this
// const detached = u.greet; detached("hi"); // error — this is void when detached (if noImplicitThis)

// bad — annotating this on a method is redundant and invites mismatch
// class BadUser {
//   greet(this: { name: string }, g: string): string { return g + this.name; } // works but redundant
// }
// fix — omit this on methods; annotate only standalone borrowed helpers

// bad — forgetting this: void on a detachable callback lets this leak
type LeakyCb = (x: number) => void; // no this: void — callback may read stray this
// fix — LeakyCb = (this: void, x: number) => void proves this not used
```

**Common confusion** — "every function should have `this: T`" — only where `this` is borrowed or where you want to forbid it (`this: void`). "`bind` fixes any `this` error" — `bind` returns a new function where `this` is bound — the checker sees `(): R` (no `this` param) — but `bind` with wrong `this` type still errors at the `bind` call.

**Performance note** — `bind` allocates a bound function per call — in hot loops prefer `arrow` wrapper `(x)=>u.greet(x)` (closure) or stable `bind` once outside the loop — measure allocation if profiling shows `bind` in the flame.

**Mentor note** — ask "does this function ever run with a different `this` than where it was defined?" — if *yes* (borrowed), annotate `this`; if *no* (method/arrow), omit. Show `bind` vs `call` cost distinction.
