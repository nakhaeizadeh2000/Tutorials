## 3.3. Type guards — predicates, asserts and `satisfies` on functions

A function can communicate more than its runtime result. A predicate signature relates a boolean to a variable's type in both branches. An assertion signature describes what holds after a normal return. Satisfies checks a callable expression against a target, while an assertion publishes the target view and may conceal a mismatch. Each is checker information whose usefulness depends on an honest runtime implementation.

Examples use TypeScript 7.0.2 / Node 20.20.2, verified 2026-10-14. Save each named file in a fresh directory without tsconfig.json. Run `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`, replacing FILE with predicates, assertions or context. Activate one commented checking failure at a time and replace `--outDir dist` with `--noEmit`. Dishonest implementations and forced callable mistakes are caught so later cases run.

### 1) **Explicit predicates, inferred predicates and boolean-only signatures**

Dog and Cat form a trusted discriminated union. The explicit function writes animal is Dog; the unannotated inferred arrow can obtain that predicate signature from its discriminant test. BooleanOnly deliberately publishes boolean, so callers receive no equivalent predicate guarantee. All three still return runtime booleans.

Save `predicates.ts`:

```typescript
export {};
type Dog = { kind: "dog"; bark(): void };
type Cat = { kind: "cat"; meow(): void };
type Animal = Dog | Cat;
const dog: Dog = { kind: "dog", bark() { console.log("bark"); } };
const cat: Cat = { kind: "cat", meow() { console.log("meow"); } };
function explicit(animal: Animal): animal is Dog { return animal.kind === "dog"; }
const inferred = (animal: Animal) => animal.kind === "dog";
const predicate: (animal: Animal) => animal is Dog = inferred;
function booleanOnly(animal: Animal): boolean { return animal.kind === "dog"; }
function handle(animal: Animal): void {
  if (predicate(animal)) animal.bark(); else animal.meow();
}
handle(dog); handle(cat);
console.log("explicit:", explicit(dog), explicit(cat), "boolean:", booleanOnly(dog));
function body(animal: Animal): boolean {
  if (animal.kind === "dog") { animal.bark(); return true; }
  return false;
}
body(dog); // runtime discriminant check also narrows inside the body
function lieTrue(animal: Animal): animal is Dog { return true; }
function lieFalse(animal: Animal): animal is Dog { return false; }
function useLieTrue(animal: Animal): void { if (lieTrue(animal)) animal.bark(); }
function useLieFalse(animal: Animal): void { if (!lieFalse(animal)) animal.meow(); }
for (const invoke of [() => useLieTrue(cat), () => useLieFalse(dog)]) {
  try { invoke(); } catch (error: unknown) { console.log(error instanceof TypeError ? "TypeError" : "other"); }
}
// function notNarrowed(animal: Animal): void { if (booleanOnly(animal)) animal.bark(); } // uncomment: TS2339
// function falseBranch(animal: Animal): void { if (!inferred(animal)) animal.bark(); } // uncomment: TS2339
// function beforeCheck(animal: Animal): animal is Dog { animal.bark(); return animal.kind === "dog"; } // uncomment: TS2339
```

The output is `bark`, `meow`, `explicit: true false boolean: true`, `bark` and two `TypeError` lines. Assigning inferred to the explicit predicate type succeeds. Its true branch accepts bark, while its false branch accepts meow. BooleanOnly's caller trying bark yields TS2339; calling bark in the inferred false branch also fails. A predicate declaration does not make its parameter Dog at entry: beforeCheck fails, while body narrows after its own actual discriminant test.

The [primary 5.5 inference explanation](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-5.html#inferred-type-predicates) describes an eligible function with no explicit return annotation, one return/no implicit returns, no parameter mutation and a boolean expression tied to parameter refinement. It also requires appropriate true/false meaning. This capability does not mean every boolean expression becomes a predicate. Check the actual resulting signature and both branches instead of assuming that only an explicitly written is can narrow.

Explicit predicates are trusted claims rather than automatically verified equivalences. LieTrue wrongly treats a Cat as Dog; lieFalse wrongly excludes a real Dog and the caller tries meow. Both compile and fail at runtime. Testing only accepted inputs misses the second failure. The [original predicate analysis](https://effectivetypescript.com/2024/02/27/type-guards/) motivates examining false cases too; these local fixtures reproduce both consequences without copying its examples.

Use a predicate for a type distinction, not merely an arbitrary selection rule that cannot justify the excluded branch. Keep a boolean-only signature when that is the honest contract. This Animal input is already trusted: checking kind alone does not validate unknown data's callable bark/meow members. [Unknown boundaries](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>) owns those runtime checks; [union narrowing](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.3. Custom narrowers predicates asserts and type guards on unions.md>) owns broader control-flow applications.

### 2) **Assertion signatures describe successful continuation**

Assert states that its supplied condition holds after it returns normally. AssertDog states that its argument is Dog. The condition animal.kind === "dog" carries enough information for the caller to refine Animal to Dog too. An ordinary void helper can perform the same runtime check without advertising either narrowing contract to its caller.

Save `assertions.ts`:

```typescript
export {};
type Dog = { kind: "dog"; bark(): void };
type Cat = { kind: "cat"; meow(): void };
type Animal = Dog | Cat;
const dog: Dog = { kind: "dog", bark() { console.log("bark"); } };
const cat: Cat = { kind: "cat", meow() {} };
function assert(condition: unknown): asserts condition {
  if (!condition) throw new Error("failed condition");
}
function assertDog(animal: Animal): asserts animal is Dog {
  if (animal.kind !== "dog") throw new Error("not a dog");
}
function ordinary(animal: Animal): void {
  if (animal.kind !== "dog") throw new Error("not a dog");
}
function byCondition(animal: Animal): void { assert(animal.kind === "dog"); animal.bark(); }
function byVariable(animal: Animal): void { assertDog(animal); animal.bark(); }
byCondition(dog); byVariable(dog);
for (const invoke of [() => byCondition(cat), () => byVariable(cat)]) {
  try { invoke(); } catch (error: unknown) { console.log(error instanceof Error ? error.message : "other"); }
}
function dishonest(animal: Animal): asserts animal is Dog {} // accepted, but false claim
function useDishonest(animal: Animal): void { dishonest(animal); animal.bark(); }
try { useDishonest(cat); }
catch (error: unknown) { console.log(error instanceof TypeError ? "TypeError" : "other"); }
// function afterVoid(animal: Animal): void { ordinary(animal); animal.bark(); } // uncomment: TS2339
```

The output is two `bark` lines, `failed condition`, `not a dog` and `TypeError`. Both assertion forms permit bark after their successful calls. On the Cat fixture, each throws before that operation. The ordinary helper's caller still cannot use bark without another check (TS2339). It lacks an assertion signature, even though its current body throws for a Cat.

The [primary assertion-signature explanation](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-7.html#assertion-functions) models the asserted condition as holding after normal return. That can refine a referenced variable through a discriminant or typeof expression; it is not limited to remembering an isolated truthy flag. Narrowing follows the specific condition and the control-flow facts available to the caller.

Dishonest is accepted despite never throwing. Its caller narrows to Dog and then fails on the Cat's missing bark. An assertion signature records a contract, not a checker-enforced guarantee that the body throws on every invalid case. Tests should exercise the successful continuation and the rejected input. Use a predicate when a caller should branch on a recoverable alternative; use an assertion when a failed invariant should stop this continuation. Full assertion-library design belongs in [assertion functions](<../../../15 Strictness Errors and Validation/sections/1. Assertion Functions/1.1. Assertion signatures asserts condition and asserts x is T.md>).

### 3) **Callable context, compatibility checks and published views**

Both as Handler and satisfies Handler provide context to the request parameter below. The assertion does not make that arrow parameter implicit any. What differs is the outer compatibility operation and the resulting view available through the variable. A target can also affect inference, so inspect the real source/context/result relationship rather than promising that satisfies leaves every inference unchanged.

Save `context.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Handler = (request: { id: string }) => string;
const asserted = ((request) => `hi ${request.id}`) as Handler;
const checked = ((request) => `hi ${request.id}`) satisfies Handler;
type AssertedArgs = Expect<Equal<Parameters<typeof asserted>, [request: { id: string }]>>;
type CheckedArgs = Expect<Equal<Parameters<typeof checked>, [request: { id: string }]>>;
console.log(asserted({ id: "u1" }), checked({ id: "u2" }));
const sourceResult = (() => "ok" as const) satisfies (() => string);
const targetResult = (() => "ok" as const) as (() => string);
type Source = Expect<Equal<ReturnType<typeof sourceResult>, "ok">>;
type Target = Expect<Equal<ReturnType<typeof targetResult>, string>>;
console.log(sourceResult(), targetResult());
const noArgs = (() => "constant") satisfies Handler; // ignoring an argument is compatible
const published: Handler = noArgs;
type OwnArgs = Expect<Equal<Parameters<typeof noArgs>, []>>;
console.log(noArgs(), published({ id: "u3" }));
const requiresSuffix = (request: { id: string }, suffix: string): string => request.id + suffix.toUpperCase();
const forced = requiresSuffix as Handler; // accepted assertion, not a valid implementation of Handler
try { forced({ id: "u4" }); }
catch (error: unknown) { console.log(error instanceof TypeError ? "TypeError" : "other"); }
const handlers = { double: (value: number) => String(value * 2), hex: (value: number) => value.toString(16) } satisfies Record<string, (value: number) => string>;
type Keys = Expect<Equal<keyof typeof handlers, "double" | "hex">>;
console.log(handlers.double(3), handlers.hex(15));
type AppHandler = { (request: { id: string }): string; displayName: string };
const app = Object.assign((request: { id: string }) => request.id, { displayName: "app" }) satisfies AppHandler;
console.log(app({ id: "u5" }), app.displayName);
// const missing = ((request) => request.missing) as Handler; // uncomment: TS2339
// const badArity = requiresSuffix satisfies Handler; // uncomment: TS1360
// const badResult = ((request) => 42) satisfies Handler; // uncomment: TS2322
// checked({ id: "u2" }, "extra"); // uncomment: TS2554
// const literal: "ok" = targetResult(); // uncomment: TS2322
```

The output is `hi u1 hi u2`, `ok ok`, `constant constant`, `TypeError`, `6 f` and `u5 app`. Six active equality checks verify both request tuples, the literal versus string result views, noArgs' empty parameter tuple and the concrete handler-table keys. The asserted arrow's request.missing yields TS2339, demonstrating contextual body checking. [Primary contextual-typing guidance](https://www.typescriptlang.org/docs/handbook/type-inference.html#contextual-typing) includes assertions among contextual positions.

SourceResult keeps its literal result, while targetResult exposes string through the asserted view. NoArgs is compatible with Handler because it can ignore the supplied argument. It retains its own zero-argument signature; the published Handler view accepts the request. Satisfies therefore checks assignability rather than exact arity equality. Checked's extra ordinary argument yields TS2554 because that particular expression has one parameter.

RequiresSuffix cannot fulfill Handler: a caller supplies only request, while its body needs suffix too. Satisfies rejects it with TS1360; the contextually typed numeric-returning body fails the string-result contract with TS2322. The accepted assertion forced exposes the one-argument target view, then throws when suffix is undefined. A checking bypass does not adapt the implementation. Use a real wrapper that defines the missing value or change the public contract instead of hiding the mismatch.

The table preserves its concrete keys, and app combines a real function with its runtime displayName property. These remain actual objects and operations after type annotations erase. [Object checks and contextual inference](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.3. satisfies assertions and narrowing on object shapes.md>) owns the full operator comparison; [return contracts](<../1. Function Type Fundamentals/1.3. Return types void never and contextual inference.md>) owns result views and ignored callback results.

### 4) **Common confusion**

Runtime boolean values can come from either a boolean-only or predicate signature. An inferred predicate can narrow callers, and a runtime condition can narrow inside the predicate body. Asserts condition can refine a discriminated union through the supplied discriminant expression. As supplies context to this arrow body while still concealing an outer callable mismatch. Successful checking of any of these declarations does not prove an explicit predicate or assertion body honest.

### 5) **Performance note**

Predicate/assertion signatures and satisfies/as operators erase. The predicate tests, function calls, assertion throws, table construction and Object.assign remain runtime operations. Replacing a signature does not remove those checks or bind a receiver. No checking complexity, code-size improvement or predicate-versus-boolean speed ranking was measured. Select failure behavior and evidence first, and measure a real workload separately.

### 6) **Mentor note**

Ask the learner to predict the inferred predicate's two branches before comparing its explicit boolean alternative. Then run lieFalse on Dog and explain the false branch's mistaken exclusion. Compare both successful assertions with ordinary's caller, and identify where a Cat stops. Finally ask why asserted's missing property is rejected while forced's missing suffix reaches runtime. A sound answer separates source context, target compatibility, published view and actual function body.
