## 3.3. Type guards — predicates, asserts and `satisfies` on functions

### 1) **Predicate returns** (`x is Dog` — how `is` narrows callers, not the function body; `in` vs predicate vs `instanceof`)

**Definition** — a *type predicate* `function isDog(x: Animal): x is Dog` declares that a truthy return proves `x` is `Dog` for callers — inside the predicate body `x` is still `Animal`; only call-site `if (isDog(a)) { a.bark() }` narrows `a` to `Dog`.

**What problem it solves / history** — `in` and `typeof` narrow via control flow but don't abstract — `if ("bark" in a)` works inline but `const isDog = (a)=>"bark" in a` returning `boolean` loses the narrowed proof for callers. `x is T` (TS 1.6) lifts the proof into a reusable predicate without runtime cost.

**Modern guidance** — as of TypeScript 5.9 era, use `x is T` for domain predicates that reuse narrowing (`isUser`, `isTruthy`) and for boundary validators where runtime `in`/`typeof` proves a type. Keep predicate logic exhaustive — a buggy predicate that returns `true` for a `Cat` narrows callers unsoundly with no checker error (see [3.3. Unsound by design spots](<../../../02 The Type System Core/sections/3. Soundness and variance/3.3. Unsound by design spots budgeted risks.md>)).

**Runnable example** — predicate vs boolean, `in` vs predicate (good vs bad, `tsc --strict`):

```typescript
type Animal = { kind: string } & ({ kind: "dog"; bark(): void } | { kind: "cat"; meow(): void });
type Dog = Extract<Animal, { kind: "dog" }>;
type Cat = Extract<Animal, { kind: "cat" }>;

// good — predicate narrows caller (boolean would not narrow)
function isDog(a: Animal): a is Dog {
  return a.kind === "dog";
}
function handle(a: Animal): void {
  if (isDog(a)) {
    a.bark(); // ok — narrowed to Dog
  } else {
    a.meow(); // ok — else branch narrowed to Cat (exhaustive where kind is discriminant)
  }
}

// good — in-check inline narrows without predicate (for one-off)
function handleIn(a: Animal): void {
  if ("bark" in a) a.bark(); // ok — "bark" in a narrows to Dog (field check)
}

// bad — boolean-returning helper loses narrowing (caller must cast)
function isDogBad(a: Animal): boolean {
  return a.kind === "dog";
}
function handleBad(a: Animal): void {
  if (isDogBad(a)) {
    // a.bark(); // error — boolean does not narrow Animal to Dog
    (a as Dog).bark(); // cast needed — unsound if predicate was wrong
  }
}

// bad — predicate that lies (no checker error, callers narrow unsoundly)
function isDogLying(a: Animal): a is Dog {
  return true; // always true — checker trusts predicate, callers think Cat is Dog
}
// fix — keep predicate body honest; test predicates with both Dog and Cat fixtures
```

**Common confusion** — "predicate narrows inside the function" — no, `a` inside `isDog` body is still `Animal` — only callers after `if (isDog(a))` see `Dog`. "`boolean` and `x is T` are interchangeable" — callers only narrow on `x is T`.

**Performance note** — predicates erase — one function call at runtime — same as `boolean` helper. The cost of a lying predicate is call-site unsoundness that spreads — one wrong predicate infects every `if`.

**Mentor note** — show `isDogBad` (boolean) vs `isDog` (predicate) side-by-side and hover `a` in the `if` — `boolean` keeps `Animal`, predicate shows `Dog` — reframes `is` as *proof* syntax.

### 2) **Assertion signatures** (`asserts x is Dog` — void-returning functions that narrow on success and throw on failure; `asserts condition` form)

**Definition** — an *assertion signature* `function assertIsDog(x: Animal): asserts x is Dog` narrows `x` *after* the call if it returns — on failure it must throw (return is `void`). The simpler `asserts condition` form `function assert(cond: unknown): asserts cond` narrows any truthy condition.

**What problem it solves / history** — predicates narrow inside `if`; assertions narrow *unconditionally* for the rest of the scope — `assertIsDog(a); a.bark();` after the call `a` is `Dog` without an `if` wrapper, matching JS-style invariant helpers (`assert`, `invariant`).

**Modern guidance** — as of TypeScript 5.9 era, use `asserts x is T` for validator throws at boundaries (`assertIsUser(payload)`), and `asserts condition` for generic invariants (`assert(x != null)`). Keep assertion bodies throwing on failure — a non-throwing assertion silently narrows callers to a false proof.

**Runnable example** — predicate vs assertion, unconditional narrowing (good vs bad, `tsc --strict`):

```typescript
type Animal = { kind: string } & ({ kind: "dog"; bark(): void } | { kind: "cat"; meow(): void });
type Dog = Extract<Animal, { kind: "dog" }>;

// good — predicate narrows inside if
function isDog(a: Animal): a is Dog { return a.kind === "dog"; }
function usePred(a: Animal): void {
  if (isDog(a)) a.bark(); // narrowed inside if
}

// good — assertion narrows after the call (unconditional)
function assertIsDog(a: Animal): asserts a is Dog {
  if (a.kind !== "dog") throw new Error("not a dog");
}
function useAssert(a: Animal): void {
  assertIsDog(a); // narrows for rest of scope
  a.bark(); // ok — Dog
}

// good — generic condition assert
function assert(condition: unknown, msg = "assertion failed"): asserts condition {
  if (!condition) throw new Error(msg);
}
function useCondition(a: Animal): void {
  assert(a.kind === "dog");
  // a is still Animal here? No narrowing beyond condition truthiness (see below)
  // for x is Dog need assertIsDog; assert for truthiness only
}

// bad — asserting condition without x is T cannot narrow to T for callers beyond truthiness
function assertTruth(a: Animal): void {
  if (a.kind !== "dog") throw new Error();
  // after this, caller doesn't know a is Dog — return is void, not asserts
}
function useTruth(a: Animal): void {
  assertTruth(a);
  // a.bark(); // error — not narrowed (void assert gives no proof)
  // fix — use asserts a is Dog signature
}

// bad — non-throwing assertion narrows callers unsoundly
function assertLying(a: Animal): asserts a is Dog {
  // forgot to throw — caller narrows to Dog even for Cat
}
function useLying(a: Animal): void {
  assertLying(a);
  // a.bark(); // compiles (assert says Dog) but runtime Cat has no bark
}
```

**Common confusion** — "`asserts x is T` narrows the param inside the assert body" — body still sees input type; narrowing applies *after* returns. "`asserts condition` narrows `x is T`" — `asserts condition` narrows only that `condition` truthiness (`x != null` → `x` non-null), not sibling variables — for `x is Dog` use `asserts x is Dog`.

**Performance note** — asserts erase to a throw-or-return function — one call at runtime. Cost of not using asserts is repeated `if`/`else` nesting at every call site — code size grows, not checker cost.

**Mentor note** — refactor a `if (isDog(a))` block into `assertIsDog(a)` and show flat control flow after. Quiz: give `function assert(x: unknown): asserts x is string` and ask what `assert(x); x.length` does — answer is *narrowed to string after*.

### 3) **`satisfies` on function values** (checking a value matches a callable type while preserving literal arity/narrowness — vs `as` widening)

**Definition** — `satisfies` on a function value checks that the value is assignable to a callable type while *keeping* the source's literal/narrowed type for downstream inference — `const fn = ((x: "a" | "b") => x) satisfies Handler` preserves `"a" | "b"` vs `as Handler` widens to `Handler`.

**What problem it solves / history** — `as Handler` silences the typo guard and widens literals (see [1.1. Function type syntax](<../1. Function Type Fundamentals/1.1. Function type syntax call signatures and callable objects.md>)). `satisfies` (TS 4.9) adds checking without loss — useful for route handler tables, config callables, and `as const` alternatives where literals drive discriminant narrowing.

**Modern guidance** — as of TypeScript 5.9 era, use `satisfies Handler` on function literals in tables and exported handlers — it catches excess params and arity mismatches at the literal site while keeping the literal for narrowing. Reserve `as` for unavoidable widens (e.g., `as unknown as T` airlock) and comment why the checker cannot see the proof.

**Runnable example** — `satisfies` vs `as` on callables (good vs bad, `tsc --strict`):

```typescript
// good — satisfies checks Handler while preserving literal narrowness for callers
type Handler = (req: { id: string }) => string;
const hOk = ((req: { id: string }) => `hi ${req.id}`) satisfies Handler; // checks → ok, param stays { id: string } not widened

// bad — as widens and silences
const hBad = ((req) => `hi ${req.id}`) as Handler; // no error, but req inferred any if noImplicitAny off
// satisfies would have enforced that the literal matches Handler at the literal site

// good — satisfies on a handler map preserves keys + handler arities
type Handlers = Record<string, (x: number) => string>;
const handlers = {
  double: (x: number) => String(x * 2),
  hex: (x: number) => x.toString(16),
} satisfies Handlers; // checks each handler is (number)=>string, keeps double/hex names
handlers.double(42); // ok — preserved

// good — callable object with method + satisfies
type AppHandler = { (req: { id: string }): string; displayName: string };
const app: AppHandler = Object.assign((req: { id: string }) => `id:${req.id}`, { displayName: "app" }) satisfies AppHandler;

// bad — as on arity-mismatched handler smuggles wrong param count
// type TakesOne = (x: string) => void;
// const takesOneBad = ((x: string, y: number) => {}) as TakesOne; // as silences extra param
// const takesOneGood = ((x: string, y: number) => {}) satisfies TakesOne; // error — literal has extra param
```

**Common confusion** — "`satisfies` changes the variable's type to Target" — no, `satisfies T` keeps source type and only checks assignability; `as T` forces `T`. "`satisfies` emits" — checker-only, erases.

**Performance note** — `satisfies` erases — zero runtime. Keeps the source literal so hover shows the precise param tuple rather than widened `Handler` — helps read call sites.

**Mentor note** — convert `as Handler` on a literal to `satisfies Handler` and hover both — `as` shows `Handler`, `satisfies` shows the literal signature with narrowed params — reframes which sight is preserved.
