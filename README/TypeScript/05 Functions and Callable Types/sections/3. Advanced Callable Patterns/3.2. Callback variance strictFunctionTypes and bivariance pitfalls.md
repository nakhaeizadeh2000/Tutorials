## 3.2. Callback variance — `strictFunctionTypes` and bivariance pitfalls

A callback consumer supplies arguments to someone else's function. Before substituting a callback, ask what values the consumer may supply and what the callback requires. A handler that accepts every Animal can handle a Dog. A Dog-only handler cannot handle every Animal. This direction is the basis of parameter contravariance; method syntax retains a checking exception that needs separate attention.

Examples use TypeScript 7.0.2 / Node 20.20.2, verified 2026-10-14. Save each named file in a fresh directory without tsconfig.json. Run `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`, replacing FILE with directions, members or wiring. For a commented checking failure, activate that line alone and replace `--outDir dist` with `--noEmit`. Strict enables strictFunctionTypes. The unsafe method call is caught so the remedy executes.

### 1) **Substitution follows supplied inputs and promised outputs**

HandleDog always supplies a Dog, so either handler can serve it: AnimalHandler only needs kind, while DogHandler can use bark. HandleAnimal may supply the cat value, so its callback must not require bark. For returned values, a Dog-producing function can satisfy a promise to return Animal; the reverse loses the required bark member.

Save `directions.ts`:

```typescript
export {};
type Animal = { kind: string };
type Dog = Animal & { bark(): void };
const dog: Dog = { kind: "dog", bark() { console.log("bark"); } };
const cat: Animal = { kind: "cat" };
function animalHandler(value: Animal): void { console.log(value.kind); }
function dogHandler(value: Dog): void { value.bark(); }
function handleDog(callback: (value: Dog) => void): void { callback(dog); }
function handleAnimal(callback: (value: Animal) => void): void { callback(cat); }
const forDog: (value: Dog) => void = animalHandler;
forDog(dog);
handleDog(animalHandler);
handleAnimal(animalHandler);
handleDog(dogHandler);
function makeDog(): Dog { return dog; }
function makeAnimal(): Animal { return cat; }
const producer: () => Animal = makeDog;
console.log("produced:", producer().kind);
// const forAnimal: (value: Animal) => void = dogHandler; // uncomment: TS2322
// handleAnimal(dogHandler); // uncomment: TS2345
// const dogProducer: () => Dog = makeAnimal; // uncomment: TS2322
```

The output is `dog`, `dog`, `cat`, `bark` and `produced: dog`. The forDog assignment and handleDog(animalHandler) both succeed. Reverse the substitution with forAnimal for TS2322, or pass dogHandler to handleAnimal for TS2345. The rejected dogProducer also yields TS2322 because makeAnimal can return a value without bark. Draw these flows from actual source values before naming their variance.

The [primary 2.6 strict-function-type explanation](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-6.html#strict-function-types) establishes the two parameter directions and method exception. Its feature introduction is historical; the examples here were executed with 7.0.2. The broader [variance owner](<../../../02 The Type System Core/sections/3. Soundness and variance/3.1. Covariance contravariance and invariance who varies which way.md>) covers producers, consumers and generic positions.

Repair a callback mismatch by making its body handle the values the consumer actually supplies, or by narrowing/validating inputs before a genuinely narrower consumer calls it. Merely widening an annotation while retaining an unconditional bark call would misdescribe the implementation. Disabling strictFunctionTypes allows the unsafe assignment in this example; it does not give a cat a bark method. To observe that specific consequence, activate only handleAnimal(dogHandler), compile with `--strictFunctionTypes false`, and run the emitted file: the unguarded call throws TypeError. Keep this intentional failure separate from the normal successful run.

### 2) **Method signatures and function properties receive different checks**

MethodBox declares handle as a method. PropertyBox declares a property whose type is a callable. This distinction affects assigning the two generic boxes, even though their intended runtime operation is the same. The exception is about the signature's origin; it is not a promise that every declaration containing a function is checked loosely.

Save `members.ts`:

```typescript
export {};
type Animal = { kind: string };
type Dog = Animal & { bark(): void };
interface MethodBox<T> { handle(value: T): void }
interface PropertyBox<T> { handle: (value: T) => void }
const dogBox: MethodBox<Dog> = { handle(value) { value.bark(); } };
const animalBox: MethodBox<Animal> = dogBox; // accepted by method exception
const backToDog: MethodBox<Dog> = animalBox; // also accepted
const dog: Dog = { kind: "dog", bark() { console.log("bark"); } };
backToDog.handle(dog);
try { animalBox.handle({ kind: "cat" }); }
catch (error: unknown) { console.log(error instanceof TypeError ? "TypeError" : "other"); }
const propertyAnimal: PropertyBox<Animal> = { handle(value) { console.log(value.kind); } };
const propertyDog: PropertyBox<Dog> = propertyAnimal; // wider-capable handler is safe
propertyDog.handle(dog);
const onlyDogs: PropertyBox<Dog> = { handle(value) { value.bark(); } };
// const unsafeProperty: PropertyBox<Animal> = onlyDogs; // uncomment: TS2322
// const unsafeBody: PropertyBox<Animal> = { handle(value: Dog) { value.bark(); } }; // uncomment: TS2322
```

The output is `bark`, `TypeError` and `dog`. Both method-box assignments are accepted. AnimalBox's public view allows the cat call, but its actual implementation still requires bark. The call therefore throws a caught TypeError. For the function-property boxes, an Animal-capable implementation can fill the Dog slot, while onlyDogs cannot fill the Animal slot (TS2322). A Dog-only body supplied directly to PropertyBox<Animal> is rejected too.

Use function-property contracts for stored or reassigned callbacks when strict parameter substitution is part of the API. Rewriting the interface syntax changes checking; it does not rewrite a function body or create runtime validation. A function-property declaration may still receive a method-shaped implementation whose body accepts the required Animal, as propertyAnimal demonstrates. Keep these distinctions separate from actual instance method versus arrow-field allocation.

The method exception was retained for compatibility with generic classes/interfaces such as Array. It is not caused by callbacks ignoring extra arguments; argument count and parameter type substitution are different questions. [Parameter contracts](<../1. Function Type Fundamentals/1.2. Parameters optional default rest and destructuring.md>) owns arity, and [verified variance reasoning](<../../../02 The Type System Core/sections/6. Interview questions and answers/6.1. Common interview QA the type system core.md>) supplies broader substitution contrasts.

### 3) **Receiver, domain and generic contracts check different relationships**

This:void describes a receiver requirement, a UserId brand distinguishes a domain contract, and a generic element parameter relates supplied values to a callback. None establishes every aspect of callback safety or validates arbitrary external input. The combined wiring example gives each check an actual producer and invocation.

Save `wiring.ts`:

```typescript
export {};
type Receiverless = (this: void, value: number) => void;
const stored: Receiverless[] = [];
function register(callback: Receiverless): void { stored.push(callback); }
register(function (value) { console.log(this, value); }); // logging void is legal
class Owner {
  factor = 2;
  install(): void { register((value) => console.log("captured:", value * this.factor)); }
  dependent(this: Owner, value: number): void { console.log(this.factor * value); }
}
const owner = new Owner(); owner.install();
for (const callback of stored) callback(3);
type UserId = string & { readonly __brand: "UserId" };
type OrderId = string & { readonly __brand: "OrderId" };
function userId(value: string): UserId {
  if (!value.startsWith("u_") || value.length <= 2) throw new Error("invalid user id");
  return value as UserId; // checked prefix/nonempty suffix; no runtime brand marker
}
function onUser(id: UserId, callback: (id: UserId) => void): void { callback(id); }
const id = userId("u_1");
onUser(id, (value) => console.log("user:", value));
try { userId("o_1"); } catch { console.log("rejected prefix"); }
function forEachStrict<T extends { id: string }>(
  values: readonly T[], callback: (value: NoInfer<T>) => void,
): void { for (const value of values) callback(value); }
const users = [{ id: "u_1", name: "Ada" }];
forEachStrict(users, (value) => console.log(value.name));
forEachStrict(users, (value: { id: string }) => console.log(value.id));
// register(owner.dependent); // uncomment: TS2345
// register(function (value) { console.log(this.factor, value); }); // uncomment: TS2339
// onUser(id, (value: OrderId) => console.log(value)); // uncomment: TS2345
// onUser("u_1", (value) => console.log(value)); // uncomment: TS2345
// forEachStrict(users, (value: { id: string; missing: string }) => {}); // uncomment: TS2345
```

The output is `undefined 3`, `captured: 6`, `user: u_1`, `rejected prefix`, `Ada` and `u_1`. Logging void is legal, and the stored arrow captures Owner.factor. Register rejects an explicitly Owner-dependent callback with TS2345 and reading this.factor through the void view with TS2339. Detailed dynamic-versus-lexical behavior belongs in the [receiver owner](<./3.1. this parameter explicit typing and arrow vs function capture.md>); this example adds storage and later invocation.

UserId's factory checks a prefix and nonempty suffix, then represents that chosen contract with a phantom brand. It does not prove database identity, authorization or every possible identifier format. An OrderId-only callback or a raw string at onUser yields TS2345. The marker erases; checking and constructing trusted domain values belongs in the [branded-object owner](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>).

ForEachStrict takes T from its input values; NoInfer prevents the callback position from contributing another candidate. The callback can read the supplied name or accept the less demanding id-only contract. It cannot require a missing field (TS2345). The constraint guarantees id to the body, while the actual inferred element shape supplies name to the callback. [Inference and NoInfer](<../../../08 Generics Deep Dive/sections/1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>) owns the full mechanism. Parse unknown data before entering these trusted contracts; neither a generic constraint nor a phantom brand checks it at runtime.

### 4) **Common confusion**

An Animal handler is usable by a Dog supplier because it asks for fewer capabilities. A Dog handler asks for more, so widening its consumer is unsafe. A bivariant method assignment can accept that unsafe direction; a function-property contract rejects it under strictFunctionTypes. This:void is unrelated to parameter variance and does not ban captured state. A checked domain factory supplies limited evidence, rather than removing the need to validate external inputs.

### 5) **Performance note**

Variance annotations, callable type declarations and phantom brand members erase. The receiverless host's calls, iteration and the ID factory's string checks remain runtime work. Changing only an interface method signature to a function-property signature has no direct runtime performance effect. No assignability complexity, compiler-time threshold, allocation benchmark or guard-cost reduction was measured. Preserve the actual contract first; use the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) for a demonstrated checking bottleneck.

### 6) **Mentor note**

Ask who can supply a cat before deciding whether dogHandler fits. A sound answer rejects the Animal consumer without rejecting the Dog consumer's wider-capable handler. Then predict the accepted method-box assignment and its TypeError, and show exactly which property assignment fails. Finally ask what the ID prefix check, NoInfer and this:void each prove. The learner should name three bounded relationships and keep runtime input validation separate.
