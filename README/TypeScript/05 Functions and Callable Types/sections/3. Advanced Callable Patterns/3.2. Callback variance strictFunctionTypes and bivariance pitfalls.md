## 3.2. Callback variance — `strictFunctionTypes` and bivariance pitfalls

### 1) **`strictFunctionTypes` in practice** (parameter contravariance for function values — why `(x: Animal) => void` is not assignable to `(x: Dog) => void`)

**Definition** — under `--strictFunctionTypes` (part of `--strict`, TS 2.6+), function *parameter* types are checked *contravariantly* (reverse direction): a function that handles a *supertype* cannot be substituted where a function handling a *subtype* is expected. Return types stay *covariant* (narrower return ok).

**What problem it solves / history** — without contravariance, `function feedDog(dog: Dog)` could be passed where `function feedAnimal(animal: Animal)` is expected — the caller would then pass `Cat` (an `Animal`) to `feedDog`, which assumes `Dog`-only members and crashes. Strict checks (borrowed from sound type theory) catch that callback inversion at assignment.

**Modern guidance** — as of TypeScript 5.9 era, keep `--strictFunctionTypes` on (on via `--strict`) and fix contravariance errors by widening the callback's param to the expected *supertype* (`(x: Animal) => void`) or by using a generic constraint — never disable `strictFunctionTypes` to silence a callback error.

**Runnable example** — contravariant parameter, covariant return (good vs bad, `tsc --strict`):

```typescript
type Animal = { kind: string };
type Dog = Animal & { bark(): void };
type Cat = Animal & { meow(): void };

// good — param contravariance: supertype handler cannot fill subtype slot
function handleDog(cb: (d: Dog) => void): void {
  const dog: Dog = { kind: "dog", bark() {} };
  cb(dog);
}
function handleAnimal(cb: (a: Animal) => void): void {
  const cat: Cat = { kind: "cat", meow() {} };
  cb(cat);
}
// handleDog((a: Animal) => console.log(a.kind)); // error TS2345 under strictFunctionTypes — (Animal)=>void not assignable to (Dog)=>void
// reason: handleDog supplies Dog, but Animal-handler expects to handle Cat too (broader)
handleAnimal((a: Animal) => console.log(a.kind)); // ok — Animal handler handles Cat
handleDog((d: Dog) => d.bark()); // ok — Dog handler handles Dog

// good — return covariance: narrower return ok (Dog ≤ Animal)
function makeAnimal(): Animal { return { kind: "animal" }; }
function makeDog(): Dog { return { kind: "dog", bark() {} }; }
const makeAnimalCb: () => Animal = makeDog; // ok — Dog return is subtype of Animal (covariant)

// bad — disabling strictFunctionTypes to silence error hides soundness bug
// tsconfig "strictFunctionTypes": false lets (Animal)=>void assign to (Dog)=>void — then Cat slips into Dog handler at runtime
```

**Common confusion** — "params should be covariant like returns" — returns *produce* values (narrower is safe); params *consume* values (narrower requires more, so must be contravariant). "My method worked without `strict`" — methods are still bivariant (see §2).

**Performance note** — variance checks are O(assignability) per callback assignment — trivial. The safety cost of disabling `strictFunctionTypes` is hidden runtime `TypeError` when a parent-type value flows into a child-expecting callback.

**Mentor note** — ask "who supplies the argument?" — caller supplies, callback consumes → callback param is input position → contravariant. Show `handleDog` vs `handleAnimal` side-by-side to anchor.

### 2) **Method bivariance trap** (`interface Obj { method(x: Animal): void }` stays bivariant for compatibility — when it leaks and how to close it)

**Definition** — *methods* (`interface Obj { method(x: Animal): void }`) are *bivariant* on params even under `strictFunctionTypes` — both `(Animal)=>void → (Dog)=>void` and `(Dog)=>void → (Animal)=>void` are allowed — for JS compatibility (many libraries assign methods with narrower params). *Property* syntax (`method: (x: Animal) => void`) is strictly contravariant.

**What problem it solves / history** — built-in `Array<T>` methods and DOM handlers historically relied on bivariant assignment; forcing contravariance would have broken half the ecosystem. TS keeps methods bivariant and offers property syntax to opt into strictness where you need it.

**Modern guidance** — as of TypeScript 5.9 era, use *property* syntax for callbacks you store and later call with a specific subtype — `handler: (x: Dog) => void` not `method(x: Dog)`. Keep method syntax for true OO methods where `this` and inheritance dictate bivariance. Lint with `@typescript-eslint/method-signature-style: property` for callback-bearing interfaces.

**Runnable example** — method vs property bivariance (good vs bad, `tsc --strict`):

```typescript
type Animal = { kind: string };
type Dog = Animal & { bark(): void };

// bivariant method — both directions allowed (unsafe but compat)
interface WithMethod {
  method(x: Animal): void;
}
const withMethod: WithMethod = {
  method(x: Dog) { x.bark(); }, // ok under bivariant method — x narrowed to Dog
};
withMethod.method({ kind: "cat" } as Animal); // runtime error — cat has no bark (bivariance leak)

// good — property syntax is strict (contravariant) and rejects the narrowing
interface WithProperty {
  handler: (x: Animal) => void;
}
// const withProp: WithProperty = {
//   handler(x: Dog) { x.bark(); }, // error TS2322 under strictFunctionTypes — (Dog)=>void not assignable to (Animal)=>void
// };
const withPropOk: WithProperty = {
  handler(x: Animal) { console.log(x.kind); }, // ok — Animal handles Cat and Dog
};

// good — using property syntax on an interface method to close the trap
interface SafeStore {
  save: (x: Dog) => void; // property — strict
}
function saveDog(store: SafeStore, dog: Dog): void { store.save(dog); }
// saveDog({ save(x: Animal) { console.log(x.kind); } }, { kind: "dog", bark() {} }); // error if Animal assigned where Dog expected

// bad — method-typed callback accepted parent and mutated missing child property at runtime (production bug shape)
// fix — switch to property syntax so the checker closes the hole
```

**Common confusion** — "methods and properties are the same" — under `strictFunctionTypes` they differ on variance; methods remain bivariant for compat. "Bivariance is a bug" — by design for migration; close it with property syntax where safety matters ([4.1 Objects checklist](<../../../04 Objects Interfaces and Type Aliases/sections/4. Important points to remember/4.1. Objects interfaces checklist mental models mentors insist on.md>) notes this).

**Performance note** — bivariance vs property has zero runtime difference — only checker behavior. The production cost is the runtime crash when a parent slips into a child-expecting method — parent→child flow plus mutation (`dog.bark()`) triggers `TypeError`.

**Mentor note** — have students convert `method(x: Dog)` to `handler: (x: Dog)=>void` and see the error appear — reframes "how do I close the hole?" as "change method to property."

### 3) **Callback safety patterns** (`this: void`, branded params, generic constraints — how production code keeps callbacks safe without disabling `strict`)

**Definition** — safe callbacks use three patterns: `this: void` to prove no stray `this`, branded params (`UserId` vs `OrderId` as branded strings) to prevent cross-type callback misuse, and generic constraints (`<T extends Animal>`) to tie callback param to the container's element type.

**What problem it solves / history** — callbacks cross boundaries — event emitters, `useEffect` cleanups, queue handlers — where a wrong param type at one site ships a runtime `undefined` three hops later. Patterns make the checker prove callback safety locally instead of relying on runtime tests.

**Modern guidance** — as of TypeScript 5.9 era, annotate detachable callbacks `this: void` so `strict` proves they don't read stray `this`. Brand ID strings that must not cross (`UserId` ≠ `OrderId`, see [3.2. Branded and opaque object patterns](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>)). Constrain generic callbacks `<T extends Animal>` so `T` threads from container `T[]` to callback `(x: T) => void`.

**Runnable example** — three patterns together (good vs bad, `tsc --strict`):

```typescript
// good — this: void proves callback doesn't capture stray this (safe to store)
type SafeCb = (this: void, x: number) => void;
const stored: SafeCb[] = [];
function register(cb: SafeCb): void { stored.push(cb); }
register((x) => console.log(x * 2)); // ok — arrow implicitly this: void
// register(function (x) { console.log(this); }); // error — this inside is not void

// good — branded ids prevent callback wiring wrong id type
type UserId = string & { __brand: "UserId" };
type OrderId = string & { __brand: "OrderId" };
function onUser(id: UserId, cb: (id: UserId) => void): void { cb(id); }
const uid = "u1" as UserId;
// onUser(uid, (oid: OrderId) => {}); // error — OrderId not assignable to UserId (brand mismatch)

// good — generic constraint threads element type to callback (array handler)
function forEachStrict<T extends { id: string }>(arr: T[], cb: (x: T) => void): void {
  for (const x of arr) cb(x);
}
forEachStrict([{ id: "u1", name: "Ada" }], (x) => console.log(x.name)); // T inferred preserves name
// forEachStrict([{ id: "u1" }], (x: { id: string; missing: string }) => {}); // error — callback expects more

// bad — unbranded string ids let callback wires cross silently
type RawId = string;
function onOrderRaw(id: RawId, cb: (id: RawId) => void): void { cb(id); }
onOrderRaw("u1", (id) => console.log(id)); // user id flows to order handler — no brand guard
// fix — brand ids per domain so callback param brands mismatch
```

**Common confusion** — "`this: void` changes runtime" — purely type-level; no emit. "Branding callbacks is overkill" — at boundaries where `UserId`/`OrderId` look alike, branding is the cheapest proof — one factory proves the brand once, callers carry it (see [3.2 Branded and opaque object patterns](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>)).

**Performance note** — `this: void` and branding erase — zero runtime. Generic constraint threading is O(assignability) per call — negligible. The win is fewer runtime guard checks — typed callbacks shift validation to compile time.

**Mentor note** — give a PR where `onUser` and `onOrder` both take `string` id — ask "what stops a user id wiring to order callback?" — answer is *nothing without a brand* — then add `__brand` and show the error at wiring.
