## 6.1. Common interview QA — functions and callable types

A useful interview answer predicts a call, assignment or failure and explains its cause. These five questions ask for that evidence rather than an arbitrary overload-count rule or a universal safety slogan. The shared program uses TypeScript 7.0.2 / Node 20.20.2, verified 2026-10-14. It contains real data and function bodies, six type-equality assertions and controlled failure handling.

### 1) **When does an overload beat a union parameter or generic lookup?**

**Question:** What does the caller gain from overloads, and what should support a dynamic key?

**Answer:** Overloads can express distinct input/result relationships, as pick's string and number calls do. Its implementation handles both branches, but the broad body signature is not a public overload. A union parameter is useful when callers only need one common result contract. An implemented generic keyed lookup can relate a key to Store[Key], including a union of supported keys. The program checks User[] for the users literal and Store[keyof Store] for read's dynamic key.

Choose from the actual call shapes, error messages and maintenance needs, rather than a fixed number of variants. Verify the implementation's branches; compatibility alone does not prove every advertised result. **Follow-up:** add a string-input public catch-all and explain what it permits and what precision its dynamic result loses. [Overload contracts](<../2. Overloads and Generics/2.1. Function overloads call signatures and implementation compatibility.md>) owns that worked comparison.

### 2) **Why does strictFunctionTypes reject a callback substitution?**

**Question:** Can an Animal-capable handler serve a Dog supplier? Can a Dog-only handler serve an Animal supplier?

**Answer:** The first is safe because the handler can process every Dog the caller supplies. The second is unsafe because the caller may supply an Animal without bark. ForDog below accepts animalHandler and prints dog; reversing it produces TS2322. Return direction differs: a Dog producer can satisfy an Animal result contract. Method signatures retain a checking exception, so an accepted method assignment can still conceal a narrow body.

**Follow-up:** show a Cat reaching that body, then change the stored callback contract to a function property and identify the rejected assignment. The [variance owner](<../3. Advanced Callable Patterns/3.2. Callback variance strictFunctionTypes and bivariance pitfalls.md>) and [controlled pitfalls](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by function type misunderstandings.md>) supply those observations. A receiver annotation or phantom brand does not by itself repair an input-domain mismatch.

### 3) **What does this:void buy a callback host?**

**Question:** Does it ban logging this, accessing surrounding state or every unsafe detachment?

**Answer:** It describes a callable without a required meaningful dynamic receiver. Observe can log this, and its receiverless call prints undefined. A function reading this.name through that void view fails checking, but Owner.make's arrow can capture the outer object and returns outer. An explicit Owner receiver requirement makes a detached receiverless call fail. An implicit method can still lose its receiver without that diagnostic; annotations do not install binding.

**Follow-up:** inspect the actual host declaration and invocation before relying on its receiver policy. Standard forEach's any thisArg is not a correlated receiver guarantee. Bind or a wrapper changes invocation; an arrow retains lexical access. [Receiver typing](<../3. Advanced Callable Patterns/3.1. this parameter explicit typing and arrow vs function capture.md>) owns those separate contrasts. This:void does not prove purity or immutability of captured state.

### 4) **How do predicates and assertion signatures communicate narrowing?**

**Question:** Can a helper narrow without an explicit is, and can asserting a discriminant condition refine the union?

**Answer:** A predicate signature relates a runtime boolean to both the selected and excluded types. IsDog's unannotated arrow infers that predicate for this discriminant test; an explicit boolean annotation would publish a weaker contract. An assertion signature describes what holds after normal return. Assert(pet.kind === dog) therefore permits bark afterward, while the Cat fixture stops with not a dog. An ordinary void helper would not communicate the same postcondition.

**Follow-up:** test a dishonest predicate's false case and an assertion that forgets to throw. Both explicit signatures are trusted, so successful checking is not implementation proof. Use branching for a recoverable alternative and assertion continuation for a failed invariant. [Guards and assertions](<../3. Advanced Callable Patterns/3.3. Type guards predicates asserts and satisfies on functions.md>) owns the inference conditions and controlled dishonest cases.

### 5) **How do satisfies and as differ on a function expression?**

**Question:** Which checks compatibility, supplies context and determines the published view?

**Answer:** Both expressions below supply the request's contextual type, so the asserted arrow's request.missing still fails. Satisfies checks assignability while leaving the resulting expression available through its source relationship; a target can also influence inference. As exposes the target view and can bypass an outer mismatch. Source's literal result remains ok, whereas target publishes string. For checked/asserted's deliberately identical request signatures, both parameter tuples are the same.

Satisfies does not require exact arity equality: a function that ignores a supplied argument can be compatible, while a function requiring an extra positional argument cannot fulfill that target. **Follow-up:** replace Handler's implementation with one requiring suffix and explain why an accepted assertion would not supply suffix at runtime. The guard/callable-check owner above verifies that failure, and [return views](<../1. Function Type Fundamentals/1.3. Return types void never and contextual inference.md>) owns result inference and ignored returns.

### 6) **Common confusion**

Public overloads are not the broad implementation signature. A wider-capable handler is usable by a narrower supplier. This:void allows logging and lexical access; it does not bind a method or prove every extracted callback safe. Predicates may be inferred, assertions may refine through a condition, and an asserted function body can still receive contextual checking. Each answer should state which relationship was actually established.

### 8) **Mentor note**

Give the learner the accepted Animal-to-Dog handler assignment, the inferred predicate and the asserted arrow before revealing their types. Ask for the valid call and one failing change in each case. A sound answer predicts the supplying domain, both predicate branches and the contextual member error. Then ask which examples would still need runtime data validation or an actual receiver remedy. Favor a justified diagnosis and repair over reciting contravariance, narrowing or erasure alone.
