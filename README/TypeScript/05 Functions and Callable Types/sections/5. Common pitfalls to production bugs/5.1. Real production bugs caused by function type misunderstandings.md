## 5.1. Real production bugs caused by function type misunderstandings

These controlled reproductions show failure patterns that can affect real applications; they are not claims about named production incidents. In each case, trace the public callable contract to its actual invocation. Then repair the behavior and the signature together. An accepted annotation can hide a returned promise, restrict a consumer view or miss an invocation requirement without changing any runtime value.

Examples use TypeScript 7.0.2 / Node 20.20.2, verified 2026-10-14. Save each named file in a fresh directory without tsconfig.json. Run `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`, replacing FILE with save, views, variance or queue. Activate one commented failure alone and replace `--outDir dist` with `--noEmit` to observe its diagnostic. All ordinary runtime mistakes are handled; the save fixture observes its returned promise so it does not create an unhandled rejection.

### 1) **A void callback view can hide completion ownership**

A host calls save and immediately reports success. The assignment of an async function to a void callback contract is legal; no any escape is needed. The problem is that this host neither waits for completion nor owns the asynchronous failure.

Save `save.ts`:

```typescript
export {};
async function main(): Promise<void> {
  let complete: () => void = () => { throw new Error("not initialized"); };
  const gate = new Promise<void>((resolve) => { complete = resolve; });
  async function save(): Promise<void> { await gate; console.log("save completed"); }
  const ignored: () => void = save; // accepted without any
  const pending: unknown = ignored(); // fixture observes the runtime return through unknown
  console.log("toast before save");
  complete();
  if (pending instanceof Promise) await pending;
  async function failedSave(): Promise<void> { throw new Error("offline"); }
  async function host(callback: () => Promise<void>): Promise<void> {
    await callback(); console.log("toast after save");
  }
  await host(save);
  try { await host(failedSave); }
  catch (error: unknown) { console.log("handled:", error instanceof Error ? error.message : "other"); }
}
void main().catch((error: unknown) => { console.error(error); });
```

The output is `toast before save`, `save completed`, `save completed`, `toast after save` and `handled: offline`. The first operation waits on a controllable gate, proving that the toast happened before completion. The fixture retrieves the runtime return through unknown and awaits it after releasing the gate. That observation prevents a floating task in the demonstration; it is not part of the bad host's void contract.

The repaired host awaits a Promise<void> callback before reporting success and routes a rejection to its caller. Writing void before a call merely discards its result; it does not await or catch it. Similarly, changing the callback type without changing the host's invocation leaves completion unowned. Choose an explicit asynchronous contract when the caller needs completion, or an intentional background-task policy with real error handling. [Return types and host behavior](<../1. Function Type Fundamentals/1.3. Return types void never and contextual inference.md>) owns the compatibility rules; [typed linting](<../../../16 Tooling Language Server and Ecosystem/sections/2. Lint Format and Checks/2.1. typescript-eslint rules and type-aware linting.md>) provides a separate tooling layer. No fresh lint run is claimed here.

### 2) **A broadened alias can lose a useful overload result**

Get exposes users/posts overloads. Keeping typeof get preserves their results. Its broad implementation is hidden; it cannot be treated as an automatically available public string-input overload. An assertion can force that broader view, but callers then lose the typed user members and the cast may invent accepted input shapes.

Save `views.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type User = { id: string };
type Post = { title: string };
const data = { users: [{ id: "u_1" }], posts: [{ title: "hello" }] };
function get(key: "users"): User[];
function get(key: "posts"): Post[];
function get(key: string): unknown[] { return key === "users" ? data.users : key === "posts" ? data.posts : []; }
const kept: typeof get = get;
const users = kept("users");
type Kept = Expect<Equal<typeof users, User[]>>;
console.log(users.map((user) => user.id).join(","));
const forced = get as unknown as (key: string) => unknown[];
const broad = forced("users");
type Broad = Expect<Equal<typeof broad, unknown[]>>;
console.log("same values:", broad === users);
function getOpen(key: "users"): User[];
function getOpen(key: string): unknown[]; // public broad overload permits a broad alias
function getOpen(key: string): unknown[] { return key === "users" ? get("users") : key === "posts" ? get("posts") : []; }
const publishedBroad: (key: string) => unknown[] = getOpen;
console.log("broad count:", publishedBroad("users").length);
// const rejectedBroad: (key: string) => unknown[] = get; // uncomment: TS2322
// get("anything"); // uncomment: TS2769
// const ids = broad.map((user) => user.id); // uncomment: TS18046
```

The output is `u_1`, `same values: true` and `broad count: 1`. Two equality checks verify User[] through kept and unknown[] through forced. The runtime array did not change when its consumer view changed. A direct broad alias of get is rejected with TS2322, and an unsupported string-key call is rejected with TS2769. Reading user.id through the forced unknown[] gives TS18046.

GetOpen deliberately publishes a broad overload, so its broad alias is accepted. That is a public contract choice, rather than an implementation signature leaking automatically. Preserve overloads when clients need their relationships; publish a broad view when it is intentional and callers can handle its weaker result. For real key/result lookup, an implemented generic Store[K] can be another suitable design. Do not replace the implementation with an asserted null or claim an arbitrary variant-count threshold determines the choice. [Overload contracts and views](<../2. Overloads and Generics/2.1. Function overloads call signatures and implementation compatibility.md>) owns the full comparison.

### 3) **A method exception can conceal a narrower implementation**

A handler publicly accepts Animal but its method body requires Dog. That is the unsafe direction: an Animal supplier may pass the cat shape. A handler capable of handling Animal remains usable by a Dog supplier; rejecting that safe direction would invert the reasoning.

Save `variance.ts`:

```typescript
export {};
type Animal = { kind: string };
type Dog = Animal & { bark(): void };
interface MethodHandler { handle(value: Animal): void }
interface PropertyHandler { handle: (value: Animal) => void }
const onlyDogs: MethodHandler = { handle(value: Dog) { value.bark(); } }; // accepted method exception
try { onlyDogs.handle({ kind: "cat" }); }
catch (error: unknown) { console.log(error instanceof TypeError ? "TypeError" : "other"); }
const handlesAnimals: PropertyHandler = { handle(value) { console.log(value.kind); } };
handlesAnimals.handle({ kind: "cat" });
const dogHost: { handle: (value: Dog) => void } = handlesAnimals; // accepted safe direction
const dog: Dog = { kind: "dog", bark() {} };
dogHost.handle(dog);
// const rejected: PropertyHandler = { handle(value: Dog) { value.bark(); } }; // uncomment: TS2322
```

The output is `TypeError`, `cat` and `dog`. The method contract accepts onlyDogs' narrower body under the method exception, then the cat call fails at bark. The function-property contract rejects that same narrow body with TS2322. The repaired implementation actually handles every supplied Animal, and a Dog host can use it too.

Change the required body capability or the consumer's promised input domain; changing interface syntax supplies an earlier diagnostic but does not repair an unsafe body by itself. Avoid casting Animal to Dog to disguise the missing capability. [Callback variance](<../3. Advanced Callable Patterns/3.2. Callback variance strictFunctionTypes and bivariance pitfalls.md>) owns the strict/property/method contrasts and a flag-off reproduction. Runtime boundary validation remains a separate responsibility.

### 4) **Stored methods need an actual receiver remedy**

This queue stores callbacks and invokes them later with a direct call. Its this:void contract rejects an explicitly Owner-dependent function. It does not automatically discover every implicit method's receiver requirement, and it does not prohibit an arrow from accessing captured state.

Save `queue.ts`:

```typescript
export {};
type Receiverless = (this: void) => void;
const pending: Receiverless[] = [];
function queue(callback: Receiverless): void { pending.push(callback); }
function drain(): void {
  for (const callback of pending.splice(0)) {
    try { callback(); }
    catch (error: unknown) { console.log(error instanceof TypeError ? "TypeError" : "other"); }
  }
}
class Owner {
  cache = new Map([ ["key", "value"] ]);
  implicit(): void { this.cache.clear(); console.log("implicit cleared"); }
  checked(this: Owner): void { this.cache.clear(); console.log("checked cleared"); }
}
const owner = new Owner();
queue(owner.implicit); // accepted even by this:void target: no explicit receiver requirement on implicit
queue(() => owner.checked());
drain();
console.log("cache size:", owner.cache.size);
queue(owner.checked.bind(owner));
drain();
// queue(owner.checked); // uncomment: TS2345
// queue(function () { this.cache.clear(); }); // uncomment: TS2339
```

The output is `TypeError`, `checked cleared`, `cache size: 0` and `checked cleared`. Queue accepts the implicit method even through the receiverless target, but its later direct invocation fails. The wrapper performs owner.checked() with the required receiver. The bound callback supplies the same receiver when invoked later. Queue rejects the explicitly checked method alone with TS2345, and the regular void-receiver callback's this.cache read with TS2339.

These are deterministic local storage/invocation mechanics, not a timer or framework integration test. A callback host determines how the callback is called; do not assume every host uses the same receiver. Strict/noImplicitThis checks body types, while explicit this requirements can expose a receiverless-call mismatch. The compiler option does not change JavaScript this into any or void at runtime. [Receiver typing](<../3. Advanced Callable Patterns/3.1. this parameter explicit typing and arrow vs function capture.md>) owns those distinctions and standard-versus-custom host behavior.

### 5) **Common confusion**

Async-to-void compatibility is accepted without any, and the host still must own the returned task. An overload's implementation signature is hidden unless a matching broad public overload is deliberately exposed. Method bivariance permits the unsafe narrow-body direction, while an Animal-capable handler remains safe for a Dog supplier. A this:void target does not prove every implicit method safe to detach. Follow the runtime function and call form instead of interpreting an annotation as an adapter.

### 6) **Performance note**

The aliases, interfaces, equality probes and receiver annotations erase. Saving, waiting on promises, allocating data arrays, queue storage and clearing a Map remain operations with real runtime consequences. No incident rate, memory benchmark or callback speed ranking was measured. The relevant issue in the save case is completion and failure ownership, not a claim that one type spelling makes asynchronous work faster.

### 7) **Mentor note**

Ask the learner to identify the first lost guarantee in each reproduction: completion ownership, precise overload result, required input capability or receiver invocation. Then have them explain why the remedy changes the necessary behavior. A good answer awaits and handles the task, preserves or intentionally broadens the public view, supplies a body that handles the host's domain, and binds or wraps a receiver-dependent call. Do not accept a cast or disabled flag as evidence that the missing runtime capability now exists.
