## 5.1. Real production bugs caused by function type misunderstandings

### 1) **`void` swallowed return** (a callback typed `() => void` ignoring a `Promise` or meaningful return that the caller awaited)

**Incident** — an `onSave` handler typed `() => void` returned `Promise<void>` from an `async` implementation; the caller did `onSave(); toast("saved")` without `await` — toast showed before save completed and errors were unhandled. `() => Promise<void>` not assignable to `() => void` was hidden because the handler was wrapped through `any` at a boundary (see [2.1. any](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.1. any the unchecked escape hatch.md>) leak).

**Fix** — type `onSave: () => Promise<void>` if async; keep `() => void` only for sync discard. Lint `no-misused-promises` (`@typescript-eslint`) flags `() => void` receiving a `Promise`.

```typescript
// bad — caller ignores Promise because signature says void (fire-and-forget bug)
type SaveVoid = () => void;
async function saveAsync(): Promise<void> { await fetch("/api/save"); }
const handlerBad: SaveVoid = saveAsync; // error under good lint — but via any it slipped
// handlerBad(); // Promise ignored, errors lost

// good — signature matches async reality
type SaveAsync = () => Promise<void>;
const handlerGood: SaveAsync = saveAsync;
void handlerGood(); // caller should await: await handlerGood() — errors propagate (wrapped to avoid top-level await in fence)

// bad — any at boundary hid the Promise<void> vs void mismatch
// function registerVoid(cb: any): void { cb(); } // any swallowed the return
// fix — use unknown then narrow, not any
```

Return types void never and contextual inference.md>); `any` budgeting → [2.1. any](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.1. any the unchecked escape hatch.md>).

### 2) **Overload implementation leaks** (calling the broad implementation signature instead of the narrow overload — caller sees `string | number` when they expected `string`)

**Incident** — `function get(key: "users"): User[]; function get(key: string): unknown[];` with implementation `function get(key: string): unknown[]`. A refactor aliased `const g: (k: string) => unknown[] = get; g("users")` — caller got `unknown[]` not `User[]` because the aliased type was the widened implementation signature, not the overloads.

**Fix** — never alias through the implementation type; keep the overloaded `typeof get` or a generic `get<K extends Key>(k: K): Store[K]`.

```typescript
// good — call through overloads preserves narrow return
function get(key: "users"): { id: string }[];
function get(key: "posts"): { title: string }[];
function get(key: string): unknown[] { return []; }
const users = get("users"); // { id: string }[] via overload

// bad — alias via implementation widens away overloads
type Impl = (key: string) => unknown[];
const aliased = get as unknown as Impl; // forced widen — overloads lost via impl type
const widened = aliased("users"); // unknown[] — narrow lost
// fix — type alias as typeof get (keeps overloads) or generic index
const viaTypeof: typeof get = get;
const kept = viaTypeof("users"); // { id: string }[] — overload kept
```

Generic functions](<../2. Overloads and Generics/2.2. Generic functions inference constraints defaults and scope.md>).

### 3) **Bivariant method accepts wrong subtype** (a method-typed callback accepted a parent type and mutated a missing child property at runtime)

**Incident** — `interface Handler { handle(x: Dog): void }` via method syntax accepted `handle(x: Animal)` due to bivariance — `handler.handle(cat)` inside mutated `cat.bark` (missing) → `TypeError`. Switched to property `handle: (x: Dog) => void` — checker then rejected `Animal` handler and forced `Dog` handler.

```typescript
type Animal = { kind: string };
type Dog = Animal & { bark(): void };
interface HandlerMethod { handle(x: Dog): void } // method — bivariant (unsafe)
interface HandlerProp { handle: (x: Dog) => void } // property — strict

const methodHandler: HandlerMethod = {
  handle(x: Animal) { console.log((x as Dog).bark()); }, // ok via bivariance but Cat slips in
};
// methodHandler.handle({ kind: "cat" } as Animal); // runtime error — no bark

// const propHandler: HandlerProp = { handle(x: Animal) {} }; // error TS2322 — strict rejects
const propOk: HandlerProp = { handle(x: Dog) { x.bark(); } }; // ok — Dog only
```

Unsound by design spots](<../../../02 The Type System Core/sections/3. Soundness and variance/3.3. Unsound by design spots budgeted risks.md>).

### 4) **`this: void` omission lets `this` leak into a detached callback** (later moved to a `strict` codebase and `this` became `any` at runtime)

**Incident** — a utility `queue(handler: () => void)` stored `handler` and later invoked `handler()` after the original `this` context was lost. Handler `function onTick(){ this.cache.clear() }` relied on implicit `this` typed `any` (`noImplicitThis` off); when the file moved to `strict`, `this` became `void` and the detached call crashed (`Cannot read properties of undefined`).

**Fix** — type detachable callbacks `this: void` and enforce `noImplicitThis`; store bound `() => void` or arrow wrappers, not raw methods.

```typescript
// bad — untyped this inside detached callback (any, hidden bug)
function queueBad(handler: () => void): void { setTimeout(handler, 0); }
// function onTick() { (this as unknown as { cache: Map<string, unknown> }).cache.clear(); } // this:any
// queueBad(onTick); // detached this is undefined at runtime

// good — this: void proves handler doesn't use this; caller binds or uses arrow
type SafeHandler = (this: void) => void;
function queue(handler: SafeHandler): void { setTimeout(handler, 0); }
const ctx = { cache: new Map<string, string>() };
queue(() => ctx.cache.clear()); // arrow captures ctx lexically — safe
// queue(function () { this.cache.clear(); }); // error — this: void, cannot read
```
