## 7.1. Boundaries — what is covered elsewhere

This domain owns callable contracts: signatures, parameter and return relationships, overloads, generic calls, receiver annotations, callback variance and narrowing signatures. When a call fails, identify whether the problem is the static contract, runtime execution or the surrounding object/data model before choosing another lesson.

### 1) **Runtime functions versus callable types**

A signature can describe the arguments and receiver a call expects. JavaScript determines how the function is invoked, which closure it retains and how this is supplied. Start with [Functions Deep Dive](<../../../../JavaScript/05 Functions Deep Dive/README.md>) for execution mechanics, particularly [call-site receiver rules](<../../../../JavaScript/05 Functions Deep Dive/sections/3. this binding/3.1. Call-site rules default implicit explicit new and strict mode.md>). Return here for [explicit receiver typing](<../3. Advanced Callable Patterns/3.1. this parameter explicit typing and arrow vs function capture.md>) and [call signatures](<../1. Function Type Fundamentals/1.1. Function type syntax call signatures and callable objects.md>).

The verified [object-boundary example](<../../../04 Objects Interfaces and Type Aliases/sections/7. Overlaps to avoid/7.1. Boundaries what is covered elsewhere.md>) shows why a function-property type does not bind an ordinary method's receiver. Moving a method into a variable changes its invocation context independently of how its type was spelled. Follow the runtime call as well as the checker message.

### 2) **Objects, classes and decorator boundaries**

Callable objects may carry properties as well as a call signature; this domain teaches that combination. General structural members, modifiers and composition belong in [Objects, Interfaces and Type Aliases](<../../../04 Objects Interfaces and Type Aliases/README.md>). Constructor/instance relationships, private members and inheritance belong in [Classes](<../../../06 Classes and Object-Oriented Types/README.md>).

A receiver requirement can matter on a method that will be detached, as well as on a free function. Choose the receiver contract from its intended calls rather than prohibiting annotations based on whether the function appears in a class. Decoration adds another boundary: value/context signatures and configured decorator programs belong in [Decorators and Metadata](<../../../14 Decorators and Metadata/README.md>), especially the [standard-versus-legacy comparison](<../../../14 Decorators and Metadata/sections/2. Legacy and Metadata/2.1. Legacy experimental decorators compared.md>). A method wrapper still needs the callable contract from this domain, but its application order and metadata channel are separate concepts.

### 3) **Narrowing signatures versus evidence and branch reasoning**

This domain explains [predicate and assertion signatures](<../3. Advanced Callable Patterns/3.3. Type guards predicates asserts and satisfies on functions.md>). ### 5) **Configuration and a debugging route**

[Configuration](<../../../13 Configuration and Compiler Options/README.md>) owns program options. This domain applies options such as strictFunctionTypes and noImplicitThis to callables; a configuration lesson explains enabling them, their boundaries and migration. Current compiler defaults/tool APIs have a separate [learning route](<../../../25 Update TypeScript 7.0/sections/6. Overlaps and Update Route/6.1. Overlaps and the current learning route.md>). Syntax acceptance alone is one part of a runnable program; use the [import/source-output owner](<../../../12 Modules Namespaces and Declaration Files/sections/1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>) when the consumed graph fails to load.

For practice, route three failures. A detached method reads an absent receiver; a parser's declared predicate accepts a malformed ID; a generic API admits an invalid initial choice by expanding its candidates. The first requires call-site reasoning and a deliberate bound/captured receiver. The second requires evidence in the runtime validator. The third requires inspecting the generic inference sites, with NoInfer appropriate when one input owns the allowed set. A compiler-option change cannot replace those contract decisions.

### 6) **Common confusion**

The same method can raise a runtime receiver problem, a static parameter-variance problem or a decorator-program mismatch. Similar syntax does not make these one topic. Likewise, an assertion signature promises narrowing but does not establish the validation algorithm. Choose the owner from the failing operation and the evidence needed to explain it.

### 7) **Performance note**

These ownership routes have no direct runtime performance effect. Function bodies, wrappers and scheduling still have execution costs; changing a type annotation does not establish a speed improvement. Diagnose checker costs with the [measurement workflow](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>), and runtime costs with a measurement suited to the actual work. No compiler/runtime benchmark is supplied by this navigation lesson.

### 8) **Mentor note**

Have the learner explain which of the three practice failures a type checker can reject and which needs runtime observation. A sound answer identifies the trusted declaration, actual call or inference candidates, then names the owning lesson and a small discriminating check. Challenge a proposed fix that merely changes syntax without explaining the failing relationship.
