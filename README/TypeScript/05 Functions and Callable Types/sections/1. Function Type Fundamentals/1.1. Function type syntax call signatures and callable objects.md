## 1.1. Function type syntax — call signatures and callable objects

### 1) **Syntax inventory** (arrow type `(x: T) => R` vs `interface` call signature vs `type` with construct — what each spells)

**Definition** — a function type describes a *callable* value — what arguments it accepts and what it returns. TypeScript offers three spellings for the same contract: the arrow form `type F = (x: number) => string` is the everyday alias; the `interface` call signature `{ (x: number): string }` names the callable member as if the object *itself* were callable; and the object-with-call form `{ (x: number): string; debug: string }` fuses a call signature with properties. All three erase — they leave no emit (see [2.1. Type erasure what survives compilation](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)).

**What problem it solves / history** — JavaScript functions *are* objects — `function f() {} ; f.debug = "trace"` is legal, and libraries routinely attach properties to callables (`fn.cache`, `fn.displayName`). A type system that only knew `Function` (the untyped JS supertype) could not say "this value is callable *and* has a `cache` map." Call signatures were added in TypeScript 1.0 to model that reality — the callable is an object type whose *call* member is the function, not a separate universe.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), default to `type F = (x: T) => R` for plain callables — it reads like the value it describes and composes with unions/intersections without ceremony. Use `interface Callable { (x: T): R; }` when you need declaration merging or an augmentable public contract (see [1.3. Interfaces vs type aliases](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.3. Interfaces vs type aliases when to use which.md>)). Use the object-with-call form only when the callable genuinely carries properties — otherwise a separate `{ fn: Fn; meta: Meta }` wrapper is clearer.

**Runnable example** — three spellings, one contract (good vs bad, `tsc --strict`):

```typescript
// good — arrow alias for a plain callable (most common, most readable)
type Mapper = (value: string) => number;
const len: Mapper = (s) => s.length;
console.log(len("hello")); // 5

// good — interface call signature (augmentable, mergeable)
interface Parser {
  (input: string): number;
  fallback: number;
}
const parseNum: Parser = Object.assign(
  (s: string) => Number.parseInt(s, 10),
  { fallback: -1 },
);
console.log(parseNum("42")); // 42
console.log(parseNum.fallback); // -1

// good — object-with-call via type (fused callable + properties, one type)
type TrackedFn = {
  (x: number): number;
  calls: number;
  reset(): void;
};
function makeTracked(): TrackedFn {
  const fn = ((x: number) => {
    (fn as TrackedFn).calls++;
    return x * 2;
  }) as TrackedFn;
  fn.calls = 0;
  fn.reset = () => { fn.calls = 0; };
  return fn;
}
const tracked = makeTracked();
console.log(tracked(3)); // 6
console.log(tracked.calls); // 1

// bad — 'Function' accepts anything callable and nothing is checked
const badFn: Function = (s: string) => s.length; // any args, any return — no arity check
// badFn(1, 2, 3); // compiles — arity not checked because 'Function' is untyped
// fix — avoid 'Function'/'CallableFunction'; use precise (x: string) => number

// bad — confusing construct vs call signature
type ConstructOnly = new (x: number) => { x: number }; // 'new' means constructable, not callable
// const c: ConstructOnly = (x: number) => ({ x }); // error — value is not constructable with 'new'
// fix — use (x: number) => { x: number } for callable, 'new (...)' only for classes/factories
```

```typescript
// bad — trying to add properties to an arrow-typed value without the object-with-call type
type Plain = (x: number) => number;
const plain: Plain = (x) => x + 1;
// plain.cache = new Map(); // error TS2339: 'cache' does not exist on type 'Plain'
// fix — declare the callable-object shape so the checker knows the property exists
type Cached = { (x: number): number; cache: Map<number, number> };
const cached: Cached = Object.assign((x: number) => x * 2, { cache: new Map<number, number>() });
cached.cache.set(3, 6); // ok — property is part of the type
```

**Common confusion** — "`Function` is the base for function types" — `Function` is the untyped escape that disables arity and return checks (like `any` for callables); never use it for typed code. "`interface Fn { (x: number): string }` is different from `type Fn = (x: number) => string`" — for a single call signature they are interchangeable structurally; difference is declaration merging and `extends` vs `&` composition. "`new (x:T)=>R` is the same as `(x:T)=>R`" — no, `new` marks a *construct* signature (call with `new`); omit `new` for callable, keep it for class-like factories.

**Performance note** — every function-type spelling erases identically — zero emit, zero allocation, zero dispatch difference. Checker cost is O(signatures) — a union of 20 overload signatures is checked per call site, but a single arrow type is O(1). Prefer one signature where a generic can cover the variants (see [2.1. Function overloads](<../2. Overloads and Generics/2.1. Function overloads call signatures and implementation compatibility.md>)) — fewer signatures → faster hover and quicker `tsc --extendedDiagnostics` on large codebases.

**Mentor note** — teach with the question "is the callable *also* an object?" — start with `typeof fn === "function"` and `typeof fn === "object"` nuance in JavaScript (functions are objects), then show why the type mirrors that (`{ (x:T):R; prop: P }`). Review exercise: give `type A = (x: number) => string` and `interface B { (x: number): string; debug: boolean }` and ask which can describe `function f(x:number){ return String(x); } f.debug = true` — answer is *B* (or the fused `type`), *A* cannot hold the property.

### 2) **Callable objects** (functions that carry properties — one type for call + state)

**Definition** — a *callable object* is a single value that is both invokable and property-bearing — the type has a call signature *and* named members: `type F = { (x: number): number; calls: number; cache: Map<number, number> }`. Assign a function and then attach the properties (usually via `Object.assign` or a factory that returns the fused value) — the result satisfies callability and the property contract simultaneously.

**What problem it solves / history** — before callable objects, typing `lodash`-style utilities (`_.curry`, memoize, `fn.cache`) required two separate types and a cast at every use. Callable-object types let the checker see `memoized(3)` *and* `memoized.cache.has(3)` through one binding, so caches, counters, and `displayName` stay type-safe without splitting the API into `{ fn, meta }`.

**Modern guidance** — as of TypeScript 5.9 era, use callable objects when the function *is* the API and the property is tightly coupled to the call (cache, call count, `displayName`). Prefer a wrapper object `{ fn: Fn; meta: Meta }` when the meta is used independently of calling — wrapper composes better with `Pick`/`Omit` and avoids `Object.assign` ceremony. Always construct callable objects through a factory that returns the fused type — direct `fn.prop = ...` after a plain arrow assignment widens `fn` away from the callable-object type.

**Runnable example** — cache-carrying callable vs wrapper (good vs bad, `tsc --strict`):

```typescript
// good — memoized callable with a typed cache (one value, two capabilities)
type MemoFn = {
  (x: number): number;
  cache: Map<number, number>;
  clear(): void;
};
function memoize(fn: (x: number) => number): MemoFn {
  const cache = new Map<number, number>();
  const m = ((x: number) => {
    if (cache.has(x)) return cache.get(x)!;
    const r = fn(x);
    cache.set(x, r);
    return r;
  }) as MemoFn;
  m.cache = cache;
  m.clear = () => cache.clear();
  return m;
}
const double = memoize((x) => x * 2);
console.log(double(5)); // 10
console.log(double.cache.has(5)); // true
double.clear();

// good — wrapper alternative when cache is used without calling
type Wrapper = { fn: (x: number) => number; cache: Map<number, number> };
function makeWrapper(fn: (x: number) => number): Wrapper {
  return { fn, cache: new Map() };
}

// bad — function-typed binding cannot accept properties after the fact
type PlainFn = (x: number) => number;
const fnPlain: PlainFn = (x) => x + 1;
// fnPlain.calls = 1; // error TS2339 — 'calls' not on PlainFn
// fix — give the binding the callable-object type before adding properties
const fnFused: MemoFn = Object.assign((x: number) => x + 1, { cache: new Map<number, number>(), clear() {} });
// fnFused.calls is typed if declared; plain assignment loses it
```

**Common confusion** — "callable object is two types" — it is one object type with a call signature plus members; assignability checks both the call and the members together (structural). "`Object.assign` is required" — `Object.assign` is the idiomatic runtime helper, but any factory that returns the fused type works — the checker only sees the resulting shape, not the construction method. "Properties on a function survive erasure" — types erase, *values* do not — `fn.cache = new Map()` emits; only the *type* `{ (x):R; cache: Map }` erases.

**Performance note** — callable objects add one runtime allocation (the function object plus its property slots) — same as any closure with captured state. No extra checker cost beyond the object-member walk (O(members)). Prefer a closure with private `Map` when the cache should not be public — exposing `cache` invites external mutation that defeats memo consistency.

**Mentor note** — demo by attaching `displayName` to a React component type (`type FCWithName = { (props: P): JSX.Element; displayName: string }`) — students see the JSX callable and the devtools name through one binding. Review check: give `type F = { (x:number):number; tag: string }` and ask what `const f: F = (x)=>x` lacks — answer is a `tag` assignment before it satisfies `F`.

### 3) **Erasable and literal-free** (every function-type form erases — no `enum` trap)

**Definition** — function-type syntax is *fully erasable* — `type`, `interface`, call signatures, `this` params, type params, and annotations all disappear in emit (see [2.1. Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)). Under `--erasableSyntaxOnly` (TS 5.8+, idiomatic as of 5.9 era) no function-type syntax is rejected — unlike `enum`, there is no non-erasable function-type form. The emitted JavaScript keeps only the runtime function, never its type.

**What problem it solves / history** — Node 22.12+ can execute TypeScript by *stripping* types without transforming them — only syntax that can be dropped without rewriting (`interface`, `type`, call signatures) qualifies as "erasable." Function types have always been erasable, so they sail through `--erasableSyntaxOnly` and through Node's native strip — no build step, no `tsc` emit needed for `type Fn = (x: number) => string`.

**Modern guidance** — as of TypeScript 5.9 era, write every function-type contract with erasable syntax so the file remains runnable under `node --experimental-strip-types` and `tsc --erasableSyntaxOnly`. Verify with `npx tsc --noEmit --erasableSyntaxOnly` — a function-typed file should pass with zero errors. Reserve non-erasable patterns (there are none for functions) for the documented exceptions (`enum` → `const` object, see [3.3. Choosing erasable syntax](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>)) — function types are never the blocker.

**Runnable example** — erasable proof and `satisfies` literal preservation (good vs bad, `tsc --strict --erasableSyntaxOnly`):

```typescript
// good — every line below is erasable and passes --erasableSyntaxOnly
type Op = (a: number, b: number) => number;
interface Binary {
  (a: number, b: number): number;
  label: string;
}
function apply(op: Op, a: number, b: number): number {
  return op(a, b);
}
const add: Op = (a, b) => a + b;
console.log(apply(add, 2, 3)); // 5

// good — satisfies preserves literal arity without adding a type that survives emit
const routes = {
  method: "get" as const,
  handler: (req: { id: string }) => `user:${req.id}`,
} satisfies { method: "get" | "post"; handler: (req: { id: string }) => string };
type Method = typeof routes.method; // "get" — literal preserved, no widening

// bad — 'as' widens and silences; satisfies would have caught the arity literal
// (contrast with 03 3.3 literal types and 04 3.3 satisfies on objects)
type Handler = (req: { id: string }) => string;
const handlerBad = ((req) => `hi ${req.id}`) as Handler; // widens, no check for extra props
const handlerGood = ((req: { id: string }) => `hi ${req.id}`) satisfies Handler; // checks, preserves

// emit check — function-type syntax leaves no trace
// input:  type Fn = (x: number) => number; const f: Fn = x => x;
// output: const f = x => x;  // only the value remains
```

**Common confusion** — "call signatures need a runtime transform" — no transform, just deletion — `interface Fn { (x:number): string }` becomes nothing in JS. "`satisfies` emits" — `satisfies` also erases — it is a checker-only assertion (`as` sibling that preserves literals). "I need `enum` for a dispatch table of handlers" — use `const` object with `satisfies` + `as const` for literals — erasable and tree-shakeable (see [3.3. Choosing erasable syntax](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>)).

**Performance note** — erasable syntax has zero runtime cost — no helper, no wrapper, no allocation. Checker cost is one type per call signature — negligible. The measurable win is toolchain speed: files using only erasable syntax skip the `tsc` emit/transform step under Node's strip or `tsx` — cold start improves because the loader only deletes, never rewrites.

**Mentor note** — run `npx tsc --noEmit --erasableSyntaxOnly` on the student's file as a review gate — if a function-type file fails, the failure is elsewhere (likely an `enum` import). Exercise: have them convert `as Handler` on a literal to `satisfies Handler` and hover both — `satisfies` keeps the parameter literal union, `as` widens to `Handler` and loses it — visible in the tooltip.
