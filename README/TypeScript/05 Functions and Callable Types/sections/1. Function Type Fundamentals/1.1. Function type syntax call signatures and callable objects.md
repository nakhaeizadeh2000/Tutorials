## 1.1. Function type syntax — call signatures and callable objects

A function contract describes an operation a caller may perform: arguments go in and a result comes out. A callable value can also carry properties. Its type can expose just the call, or the call together with named state and methods. A narrower view of the value does not delete properties from the actual function object.

Examples use TypeScript 7.0.2 and Node 20.20.2, verified 2026-10-15. Save each named file in a fresh directory without tsconfig.json. Build with `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then run `node dist/FILE.js`. For an intentional rejection, activate one marked line in a separate copy and replace --outDir dist with --noEmit. The deliberate broad-Function misuse is caught so the remaining program can run.

### 1) **Calls, object call signatures and construction**

An arrow type `(input: string) => number` describes a call. An object or interface call signature uses `(input: string): number`. Adding new describes construction instead. The [function guide](https://www.typescriptlang.org/docs/handbook/2/functions.html#call-signatures) shows call signatures with properties and the separate construct-signature form. Use a construct signature when your code actually invokes the value with new; a callable arrow is not automatically a constructor.

Save `syntax.ts`:

```typescript
export {};
type Mapper = (input: string) => number;
interface Measure { (input: string): number }
const length: Mapper = input => input.length;
const measure: Measure = length;
console.log(length("hello"), measure("Ada"), length === measure);
// length(42); // TS2345: the public call requires string.
// const wrong: Mapper = input => input; // TS2322: result must be number.

class Point {
  x: number;
  constructor(x: number) { this.x = x; }
}
type PointConstructor = new (x: number) => Point;
const Ctor: PointConstructor = Point;
console.log(new Ctor(3).x);
// Ctor(3); // TS2348: a construct-only type is not callable.
// const arrowCtor: PointConstructor = (x: number) => ({ x }); // TS2322: no new signature.

const broad: Function = (input: string) => input.toUpperCase();
try { console.log(broad(42)); } // Accepted through Function's broad call view.
catch (error: unknown) {
  console.log(error instanceof TypeError ? "unchecked call: TypeError" : "unexpected error");
}
```

The output is `5 3 true`, `3` and `unchecked call: TypeError`. Both plain-call spellings describe the same function here. Neither assignment wraps the function. The broad Function view permits the wrong call and loses the useful argument/result contract. Prefer a precise signature when the caller needs checked arguments and a known result.

Choose interface versus alias from the capabilities the contract needs, such as declaration merging, rather than a runtime cost ranking. The [interfaces/aliases owner](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.3. Interfaces vs type aliases when to use which.md>) covers that decision. Full constructor/instance contracts belong in [class queries](<../../../06 Classes and Object-Oriented Types/sections/3. Advanced Class Patterns/3.3. Class type queries InstanceType and constructor signatures.md>).

### 2) **Actual properties, inferred properties and published views**

A function that has a debug property can satisfy both a plain call type and a richer type requiring that property. The plain view simply does not expose debug for checked member access. Separately, same-scope assignments can contribute inferred properties to an unannotated const function. An explicit plain annotation intentionally limits the visible contract; it is not evidence that direct property assignment universally loses inference.

Save `views.ts`:

```typescript
export {};
type Plain = (x: number) => string;
interface Tagged { (x: number): string; debug: boolean }
const decorated = Object.assign((x: number) => String(x), { debug: true });
const plain: Plain = decorated;
const tagged: Tagged = decorated;
console.log(plain(2), tagged.debug, plain === tagged);
// plain.debug; // TS2339: Plain does not expose this property.
// const missingTag: Tagged = (x: number) => String(x); // TS2741: missing debug.

type Counted = { (x: number): number; calls: number; reset(): void };
const fn = (x: number) => { fn.calls++; return x + 1; };
fn.calls = 0;
fn.reset = () => { fn.calls = 0; };
const counted: Counted = fn;
console.log(counted(2), counted.calls);
counted.reset();
console.log(counted.calls);
// counted.calls = "many"; // TS2322: calls is number.
const numberOnly: (x: number) => number = counted;
console.log(numberOnly(4), counted.calls);
// numberOnly.calls; // TS2339: declared plain view omits calls.
```

The output is `2 true true`, `3 1`, `0` and `5 1`. The first two views refer to the same decorated function. The inferred fn satisfies Counted without an assertion or Object.assign; calls and reset are inferred from its assignments in this scope. Calling through numberOnly still runs that same function and increments its actual calls state.

The [3.1 property-declaration notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-1.html#properties-declarations-on-functions) document function declarations and const functions with same-scope property assignments. This lesson checks current behavior rather than requiring that historical compiler. Use an explicit callable-object return type when publishing a factory contract is helpful; Object.assign is one construction technique, not a universal inference requirement.

A cache-bearing callable also has real runtime state. Save `memo.ts`:

```typescript
export {};
type Memo = { (x: number): number; cache: Map<number, number>; clear(): void };
function memoize(fn: (x: number) => number): Memo {
  const cache = new Map<number, number>();
  return Object.assign((x: number) => {
    const found = cache.get(x);
    if (found !== undefined) return found;
    const value = fn(x);
    cache.set(x, value);
    return value;
  }, { cache, clear(): void { cache.clear(); } });
}
let computations = 0;
const double = memoize(x => { computations++; return x * 2; });
console.log(double(5), double(5), computations, double.cache.has(5));
double.cache.set(5, 999);
console.log("public mutation:", double(5), computations);
double.clear();
console.log("after clear:", double(5), computations);
// double.cache.set("5", 10); // TS2345: numeric key required.
// double.cache.set(5, "ten"); // TS2345: numeric value required.
```

The output is `10 10 1 true`, `public mutation: 999 1` and `after clear: 10 2`. The number-returning contract makes undefined an adequate missing-entry signal for this particular cache. The type checks key/value shapes, but a correctly typed public cache mutation can still change the result. Keep the cache private if callers should only invoke and clear the function. A wrapper with a run member and separate metadata is another API choice when those concerns should be accessed independently; it does not require pretending that a function cannot own properties.

### 3) **Context, result views and emitted values**

Call annotations and type declarations erase; implementations, attached properties and cache operations remain. Satisfies checks compatibility and can provide contextual parameter types while leaving the expression's resulting type available. An explicit annotation can deliberately publish a broader view. Inspect actual source/context/result relationships instead of promising that one operator always widens or preserves every literal.

Save `contracts.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Handler = (request: { id: string }) => string;
const handler = ((request) => "user:" + request.id) satisfies Handler;
const literal = (() => "ready" as const) satisfies (() => string);
const published: () => string = literal;
type SourceResult = Expect<Equal<ReturnType<typeof literal>, "ready">>;
type PublishedResult = Expect<Equal<ReturnType<typeof published>, string>>;
const route = { method: "get" as const, handler } satisfies {
  method: "get" | "post"; handler: Handler;
};
type RouteMethod = Expect<Equal<typeof route.method, "get">>;
console.log(route.method, route.handler({ id: "u1" }), literal(), published());
// const badContext = ((request) => request.missing) satisfies Handler; // TS2339.
// const badResult = ((request) => request.id.length) satisfies Handler; // TS2322.
// route.handler({ id: 1 }); // TS2322: id must be string.
```

This prints `get user:u1 ready ready`. Three equality assertions distinguish the source literal result, the annotated string result and the route's explicit literal method. The request parameter is contextually typed, so accessing missing is rejected. The [callable-check owner](<../3. Advanced Callable Patterns/3.3. Type guards predicates asserts and satisfies on functions.md>) develops the full operator/arity comparison; [return types](<./1.3. Return types void never and contextual inference.md>) develops callback result ownership.

Inspect the emitted files under the declared removeComments setup: aliases, interfaces, equality probes and satisfies are absent, while function calls, property assignments, Object.assign and Map remain. Passing the erasable-syntax gate verifies the restricted syntax; it does not establish runtime API availability, module resolution or every source runner. Use the [execution owner](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>) and [source/emit owner](<../../../12 Modules Namespaces and Declaration Files/sections/1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>) for those separately verified pipelines.

### 4) **Common confusion**

A value satisfying Tagged can also satisfy Plain; the narrower view restricts member access rather than changing the object. Same-scope inferred function properties differ from properties omitted by an explicit plain annotation. A call signature does not provide construction, and a type-only declaration does not create either capability at runtime. Finally, a typed cache is still mutable runtime state whose semantic policy needs its own design.

### 5) **Performance note**

Function types and operators erase. The actual functions, attached state, allocations, Map lookups and computations still execute. The memo example counts computations to establish its cache behavior; it is not a time or memory benchmark. No signature-count complexity, hover improvement or runner cold-start ranking was measured. Choose a contract that preserves the needed behavior, then investigate a real cost with the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) or an appropriate runtime profiler.

### 6) **Mentor note**

Give the learner Plain, Tagged and the decorated value. Require three predictions: both assignments pass, plain.debug fails checking, and both variables still refer to the same function. Then remove the plain annotation from an inferred property-bearing function and explain which properties become visible. For the memo, ask why a typed cache mutation changes the answer without a type error and what contract should be public. A good answer distinguishes assignment, visible members and behavior instead of adding a cast to every property assignment.
