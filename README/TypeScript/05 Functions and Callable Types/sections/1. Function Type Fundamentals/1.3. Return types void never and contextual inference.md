## 1.3. Return types — `void`, `never`, and contextual inference

### 1) **`void` vs `never` vs `undefined` on returns** (`void` means "ignored", `never` means "never returns", `undefined` means "value undefined" — different contracts)

**Definition** — `void` on a return type says "the caller *ignores* the return value" — the function may `return` nothing or `return undefined`; assigning `() => string` to `() => void` is allowed because `void` discards. `never` says "this function never returns normally" — it throws, loops forever, or `process.exit` — `never` is the empty set (see [2.3. never and void](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.3. never and void bottom vs deliberate nothing.md>)). `undefined` says "the function returns the value `undefined`" — and `exactOptionalPropertyTypes` distinguishes it from missing. The callback rule: `void` *allows* discarding; `undefined` *requires* `undefined`.

**What problem it solves / history** — JavaScript callbacks often ignore returns — `array.forEach(cb)` calls `cb` but discards its return. Typing `forEach(cb: (x: T) => void)` lets `cb` return a string internally without forcing callers to handle it. `never` solves exhaustiveness — `function fail(msg: string): never { throw new Error(msg); }` tells the checker that code after `fail()` is unreachable. The confusion has real cost: `async () => void` vs `() => Promise<void>` vs `() => Promise<never>` differ in whether callers `await` and whether errors propagate.

**Modern guidance** — as of TypeScript 5.9 era, use `void` for callbacks whose return is intentionally ignored (event handlers, `forEach`, disposal). Use `undefined` when the caller *must* see `undefined` (optional chaining result, `JSON.stringify` replacer). Use `never` for functions that never complete normally (throwers, exhaustive `default` with `never` assignment). Never annotate a function that returns a value as `void` to "hide" that value — annotate `void` only when discarding is contractual.

**Runnable example** — `void` discards, `never` exhausts, `undefined` is a value (good vs bad, `tsc --strict`):

```typescript
// good — void discards: () => string is assignable to () => void (return is ignored)
type VoidCb = () => void;
const returnsString: () => string = () => "hi";
const voidCb: VoidCb = returnsString; // ok — void discards the string
voidCb(); // caller's void says "I ignore what came back"

// bad — void does NOT mean "callback will not be called" or "undefined will be checked"
// function takeVoid(cb: () => void): void { cb(); }
// takeVoid(() => 42); // ok at assignment, but 42 is discarded — surprise if you expected 42

// good — never for throwers + exhaustiveness
function fail(msg: string): never {
  throw new Error(msg);
}
type Shape = { kind: "circle"; r: number } | { kind: "square"; size: number };
function area(s: Shape): number {
  switch (s.kind) {
    case "circle": return Math.PI * s.r * s.r;
    case "square": return s.size * s.size;
    default: {
      const _exhaust: never = s; // error if a variant is unhandled — exhaustive guard
      return _exhaust;
    }
  }
}

// good — undefined as value vs void as discard
function returnsUndefined(): undefined { return undefined; }
function returnsVoid(): void { /* no return */ }
// const v: void = returnsUndefined(); // ok — void accepts undefined (discard)
const u: undefined = returnsUndefined(); // ok — caller sees undefined

// bad — confusing void with Promise<void> in async callbacks
async function asyncVoid(): Promise<void> { }
type AsyncVoidCb = () => Promise<void>;
const av: AsyncVoidCb = asyncVoid; // ok — async returns Promise<void>, not void
// const wrong: VoidCb = asyncVoid; // error — () => Promise<void> not assignable to () => void (async vs sync)
```

**Common confusion** — "`void` means returns `undefined`" — `void` *accepts* `undefined` but also accepts any discarded value; `() => string` assignable to `() => void` proves `void` is about *ignoring*, not *being* `undefined`. "`never` is just `void` that throws" — `never` is bottom: `never` is assignable *to* every type (`never` → `string` ok for exhaustiveness), while `void` is not. " `Promise<void>` is `void`" — `Promise<void>` is a promise that resolves to ignored — `await` still works; bare `void` is synchronous discard.

**Performance note** — return-type contracts are checker-only — no emit difference — `void`/`never`/`undefined` all erase. The cost is misuse: marking a public API `void` when it actually returns a `Promise` hides an `await` from callers and ships fire-and-forget bugs — no engine cost, but large incident cost.

**Mentor note** — quiz: `const f: () => void = () => 42` — ask "does call site see 42?" — answer is *assigned ok but caller who types void ignores it; value still returned at runtime* — demo with `const x = f(); console.log(x)` where `x` is `void` (not `number`) so the checker hides the value. Exercise: given `function onClick(handler: () => void)` show why `onClick(async () => { await fetch(...) })` is a bug — `Promise<void>` is not `void` and the outer code does not `await` the handler.

### 2) **Annotation strategy** (when to annotate return types for public APIs vs when to let inference preserve literals)

**Definition** — TypeScript infers return types from `return` expressions — `function f(x: boolean){ return x ? "a" : "b"; }` infers `string`. Annotating `function f(x: boolean): "a" | "b"` narrows the inferred `string` to the literal union. Public APIs benefit from explicit returns because inference is *implementation* truth that callers then depend on; internal helpers benefit from inference because it stays in sync with the body.

**What problem it solves / history** — early TS inferred `any` for many returns (no `strict`). As `noImplicitAny` + `strict` landed, inference became precise, but public APIs whose return type was *inferred* broke on refactor — changing a return expression from `"a"` to `"a" as string` widened callers silently. Explicit return annotations make the contract independent of the body's literal choices.

**Modern guidance** — as of TypeScript 5.9 era, annotate return types on *exported* functions, library boundaries, and recursive functions (inference needs a seed for recursion). Let inference handle *private* helpers and inline callbacks where the body is visible and literals should flow. Use `satisfies` on returned literals when you want checking without annotating the whole return (see [3.3. satisfies on object shapes](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.3. satisfies assertions and narrowing on object shapes.md>)). Lint with `explicit-function-return-type` only for `src/public/**`, not for `src/internal/**`.

**Runnable example** — public annotation vs private inference, recursive need (good vs bad, `tsc --strict`):

```typescript
// good — public API: annotate return so callers don't depend on literal inference drift
export function parseStatus(raw: string): "ok" | "error" {
  return raw === "ok" ? "ok" : "error"; // inferred would be string without annotation
}
type Status = ReturnType<typeof parseStatus>; // "ok" | "error" — precise

// good — private helper: let inference preserve literals (body nearby, refactor-local)
function classify(n: number) {
  return n > 0 ? "positive" as const : "non-positive" as const;
}
const label = classify(3); // "positive" | "non-positive" via inference — ok locally

// bad — public function without return annotation widens unexpectedly on edit
export function makeTag(flag: boolean) {
  return flag ? "a" : "b"; // inferred string — callers get string, not "a" | "b"
}
 // const t: "a" | "b" = makeTag(true); // error — string not assignable to union (if strict)
 // fix — annotate: function makeTag(flag: boolean): "a" | "b"

// good — recursive: annotation required as inference seed
function fact(n: number): number {
  return n <= 1 ? 1 : n * fact(n - 1); // needs : number to seed recursion
}

// good — satisfies on returned object keeps literal while checking shape
type Route = { method: "get" | "post"; path: string };
function makeRoute(path: string): Route {
  return { method: "get", path } satisfies Route; // checks Route, keeps "get" literal narrow
}
```

**Common confusion** — "always annotate returns" — over-annotation freezes inference and duplicates the literal (hover shows both) — annotate boundaries, not every helper. "`satisfies` is an alternative to return annotation" — `satisfies` checks the *literal* before return, but the function's *return type* Still needs annotation for callers if you want it narrow — use both: `return { ... } satisfies T` inside a `(): T` function. "Inference is free" — inference that widens to `string` loses discriminant narrowing downstream — measurable bug cost, not performance cost.

**Performance note** — inference vs annotation both O(1) for the checker — no runtime difference. The performance win is *incremental* checking: annotated boundaries give `tsc --incremental` a stable signature to cache — changing a body without changing the annotated return avoids re-checking importers.

Exercise: have them decide per-file which functions need `: T` — public exports vs 3-line helpers — and enforce with ESLint overrides.

### 3) **Contextual typing for callbacks** (`arr.map(x => x * 2)` infers `x: number` from the target — when context helps and when it hides)

**Definition** — *contextual typing* infers a callback's parameter types from the *target* callable's signature, not from the callback's own annotation — `["a","b"].map(s => s.toUpperCase())` infers `s: string` because `Array<string>.map` expects `(value: string) => T`. It applies to inline arrows, function expressions, and `satisfies`-typed handlers where the target type is known.

**What problem it solves / history** — without contextual typing, every callback would need explicit params `arr.map((x: number) => ...)` — noisy, and the literal would drift from the container's element type. Contextual inference (TS 1.0+) lets the container's type flow into the callback, so `forEach`/`map`/`filter` callbacks are typed for free.

**Modern guidance** — as of TypeScript 5.9 era, rely on contextual typing for inline callbacks where the target is typed (array methods, `Promise.then`, event handlers). Annotate callback params when the callback is detached (`const cb = (x) => ...; arr.map(cb)`) — detached callbacks lose context and fall back to `any`/`unknown` without `noImplicitAny`. Avoid *double* context: don't annotate the callback *and* the target with conflicting types — the callback annotation wins and hides the contextual narrowing (especially for `void` vs `string` returns).

**Runnable example** — context helps vs context hides (good vs bad, `tsc --strict`):

```typescript
// good — context infers param from target (no annotation needed)
const nums: number[] = [1, 2, 3];
const doubled = nums.map((n) => n * 2); // n: number from Array<number>.map
const strings = nums.map((n) => String(n)); // (n: number) => string → string[]

// good — async context flows through Promise
async function fetchIds(): Promise<number[]> { return [1, 2]; }
fetchIds().then((ids) => ids.map((id) => id * 2)); // ids: number[], id: number — contextual

// bad — detached callback loses context and becomes any/unknown via noImplicitAny
// const cb = (x) => x * 2; // error TS7006 under strict: Parameter 'x' implicitly has an 'any' type
// nums.map(cb); // doesn't help — cb already typed as (x: any) => any if it compiled
// fix — annotate detached callback or type the binding
const cbFixed: (x: number) => number = (x) => x * 2; // ok — binding gives context
nums.map(cbFixed);

// bad — annotating with a wider type hides contextual narrowing (void trap)
function forEachVoid(items: string[], cb: (x: string) => void): void {
  for (const x of items) cb(x);
}
forEachVoid(["a", "b"], (x) => x.toUpperCase()); // ok but return string is discarded via void (see §1)
forEachVoid(["a", "b"], (x: string): string => x.toUpperCase()); // error — string not assignable to void contextually
// fix — don't force return annotation in void context; let context decide that return is ignored

// good — context + satisfies preserves literal while checking
type Handler = (req: { id: string }) => string;
const h: Handler = (req) => `hi ${req.id}`; // req: { id: string } from Handler — contextual
```

**Common confusion** — "contextual typing works for detached callbacks" — only when the target type is known at the assignment/callsite — `const cb = (x) => ...` has no target, so `x` is `any`/`unknown`. "Annotating a callback param overrides context" — yes — `(x: string | number) => ...` defeats the string-only context and widens to the annotation — prefer no annotation when context is precise. "`void` callback context ignores my return" — intentional — `(x: T) => void` context means the return is discarded regardless of what the arrow returns.

**Performance note** — contextual inference is per-call-site O(signature) — trivial. The cost of *not* using it is verbosity and `any` propagation from detached ` (x) => ...` — each `any` removes downstream rename/quick-fix precision (see [2.1. any](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.1. any the unchecked escape hatch.md>)).

**Mentor note** — demo detached vs inline side-by-side — students see hover on inline `n` says `number` while detached `x` says `any` — reframes "annotate detached, not inline." Review check: give `const f = (x) => x.length; [1,2].map(f)` and ask what `x` is — answer is `any` (no context on `f`), so `any` leaks.
