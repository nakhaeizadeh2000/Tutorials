## 1.3. Return types — void, never and contextual inference

A return contract tells a caller which result it may use. A void callback view permits ignoring a result; undefined describes a particular returned value; never describes a function that does not return normally. The implementation still executes, and a return annotation does not remove a runtime value or handle a returned promise.

Examples use TypeScript 7.0.2 / Node 20.20.2, verified 2026-10-14. Save each named file in a new directory without a tsconfig.json. Run `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`, replacing FILE with contracts, async, returns or context. Activate one commented failure at a time and replace `--outDir dist` with `--noEmit` to inspect it without executing rejected code.

### 1) **Void, never and undefined: separate the view from the implementation**

A callback typed () => void may refer to a function that returns a value. Calling through that view produces a void-typed expression for the consumer, while the runtime function still returns its actual result. An explicit void return annotation on an implementation body is a different restriction: that body cannot return an arbitrary number or string. The [primary void-assignability explanation](https://www.typescriptlang.org/docs/handbook/2/functions.html#return-type-void) shows both cases.

Save `contracts.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
function returnsString(): string { return "hi"; }
const ignored: () => void = returnsString;
const value = ignored();
type Ignored = Expect<Equal<typeof value, void>>;
console.log(value, typeof value); // hi string
function returnsUndefined(): undefined { return undefined; }
function returnsVoid(): void {}
console.log(returnsUndefined(), returnsVoid()); // undefined undefined
function fail(message: string): never { throw new Error(message); }
try { fail("stopped"); } catch (error: unknown) { console.log(error instanceof Error ? error.message : "other"); } // stopped
// function badVoid(): void { return 42; } // uncomment: TS2322
// const expectsUndefined: () => undefined = returnsString; // uncomment: TS2322
// const expectsNever: () => never = returnsVoid; // uncomment: TS2322
```

The output is `hi string`, `undefined undefined` and `stopped`. The active type assertion establishes that value is void in the caller's view, even though logging observes a string. Undefined requires the undefined result. ReturnsVoid completes normally without a value; fail throws, so its never annotation describes the absence of a normal result rather than an ignored result.

Activate badVoid to observe TS2322 on the numeric return. Activate expectsUndefined or expectsNever to see TS2322 for their incompatible result contracts. The callback discard rule does not mean void is assignable to every result type, and never is not just another spelling of normal completion without a value. Full bottom-type and exhaustiveness reasoning belongs in the [never/void owner](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.3. never and void bottom vs deliberate nothing.md>) and [exhaustiveness](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>).

A promise-returning function can also satisfy () => void. That accepted assignment is a reason to examine the callback host's behavior, not proof that the host awaits it. If the host intentionally ignores returns, asynchronous work needs an explicit owner for completion and failure.

Save `async.ts`:

```typescript
export {};
function invokeIgnoring(callback: () => void): void {
  callback();
  console.log("ignoring host returned");
}
async function invokeAwaiting(callback: () => Promise<void>): Promise<void> {
  await callback();
  console.log("awaiting host completed");
}
async function main(): Promise<void> {
  const tasks: Promise<void>[] = [];
  function failingTask(): Promise<void> {
    const task = Promise.reject(new Error("offline"));
    tasks.push(task); // the fixture retains a handle to observe the failure
    return task;
  }
  const accepted: () => void = failingTask; // accepted even though the function returns a promise
  invokeIgnoring(accepted);
  const pending = tasks[0];
  if (pending === undefined) throw new Error("task not started");
  try { await pending; } catch (error: unknown) { console.log("fixture observed:", error instanceof Error ? error.message : "other"); }
  await invokeAwaiting(async () => { await Promise.resolve(); console.log("task completed"); });
  try { await invokeAwaiting(() => Promise.reject(new Error("offline"))); }
  catch (error: unknown) { console.log("awaiting host rejected:", error instanceof Error ? error.message : "other"); }
}
void main().catch((error: unknown) => { console.log("unexpected:", String(error)); });
async function returnsNumber(): Promise<number> { return 42; }
// const wrongPromise: () => Promise<void> = returnsNumber; // uncomment: TS2322
```

The five output lines are `ignoring host returned`, `fixture observed: offline`, `task completed`, `awaiting host completed` and `awaiting host rejected: offline`. The ignoring host calls the callback and returns without consuming its result. This fixture deliberately retains the started promise and immediately awaits it in the same call sequence, so the controlled failure is observed without leaving an unhandled rejection. That observation is performed by the fixture, not by invokeIgnoring.

InvokeAwaiting explicitly awaits its callback. Its completion log follows the task log, and rejection propagates to the caller's catch. Use a promise-aware contract when the host must wait for completion. If a real host owns errors independently or deliberately detaches work, document and test that behavior rather than treating every async callback as automatically wrong.

Activate wrongPromise to observe TS2322: () => Promise<number> is not assignable to () => Promise<void>. The special permission to ignore a callback's entire return does not make those two promise payload contracts interchangeable. The [async return owner](<../../../18 Async Types and Standard Library/sections/1. Promise Types/1.3. async function return-type contracts.md>) develops promise-specific result behavior; actual lint integration belongs in the [typed-lint owner](<../../../16 Tooling Language Server and Ecosystem/sections/2. Lint Format and Checks/2.1. typescript-eslint rules and type-aware linting.md>).

### 2) **Return annotations and actual inferred results**

A function's return inference depends on its expressions and context. The literal branches shown below infer literal unions. Concatenating a runtime string supplies a broader string expression. An annotation can publish an intentional boundary and catch an implementation change, but it is not necessary to obtain the shown literal union in the first place.

Save `returns.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
function makeTag(flag: boolean) { return flag ? "a" : "b"; }
function parseStatus(raw: string) { return raw === "ok" ? "ok" : "error"; }
function widened(flag: boolean, suffix: string) { return flag ? "a" + suffix : "b"; }
function publicTag(flag: boolean): "a" | "b" { return flag ? "a" : "b"; }
type Tag = Expect<Equal<ReturnType<typeof makeTag>, "a" | "b">>;
type Status = Expect<Equal<ReturnType<typeof parseStatus>, "ok" | "error">>;
type Wide = Expect<Equal<ReturnType<typeof widened>, string>>;
console.log(makeTag(true), parseStatus("bad"), widened(true, "!"), publicTag(false)); // a error a! b
type Route = { method: "get" | "post"; path: string };
function inferredRoute(path: string) { return { method: "get", path } satisfies Route; }
function publishedRoute(path: string): Route { return { method: "get", path } satisfies Route; }
type NarrowMethod = Expect<Equal<ReturnType<typeof inferredRoute>["method"], "get">>;
type PublishedMethod = Expect<Equal<ReturnType<typeof publishedRoute>["method"], "get" | "post">>;
console.log(inferredRoute("/a").method, publishedRoute("/b").method); // get get
// const singleton: "a" = makeTag(false); // uncomment: TS2322
// function brokenPublic(): "a" | "b" { return "c"; } // uncomment: TS2322
```

All five equality checks pass. The output is `a error a! b` then `get get`. MakeTag infers a-or-b, parseStatus infers ok-or-error, and widened infers string. Activate singleton to observe TS2322: the union result is not a proof that one call returns only a. Activate brokenPublic to observe TS2322 at an implementation that violates its explicit public contract.

InferredRoute returns a checked object with the get method contract. PublishedRoute explicitly exposes Route, so consumers see get-or-post despite its current body returning get. The same runtime values can be exposed through different static views. Satisfies checks the expression; the surrounding function return annotation still determines the published result contract. The [object-check owner](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.3. satisfies assertions and narrowing on object shapes.md>) explains source context and target views more fully.

Choose annotations for a stable intended public contract, recursive cases that need an inference seed, or a clearer diagnostic boundary. Keep useful inferred precision for local expressions when that is the intended API. Do not mandate an annotation quota or promise that annotations alone prevent importer checks; verify the consumer declarations and the actual build if that behavior matters.

### 3) **Contextual typing for callbacks**

A known target signature can supply parameter types to a function expression. Array.map relates its collection's element type to the callback input, then derives its result element type from the callback's return. A typed variable can also provide context to an arrow. Merely passing a separately declared unannotated function later does not retroactively give its original parameter a contextual type.

Save `context.ts`:

```typescript
export {};
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
const numbers = [1, 2, 3];
const doubled = numbers.map(value => value * 2);
const strings = numbers.map(value => String(value));
type Doubled = Expect<Equal<typeof doubled, number[]>>;
type Strings = Expect<Equal<typeof strings, string[]>>;
console.log(doubled.join(","), strings.join(",")); // 2,4,6 1,2,3
const fixed: (value: number) => number = value => value * 2;
console.log(numbers.map(fixed).join(",")); // 2,4,6
// const detached = (value) => value * 2; // uncomment: TS7006
// const wrong = numbers.map(value => value.toUpperCase()); // uncomment: TS2339
let calls = 0;
function forEachVoid(values: readonly string[], callback: (value: string) => void): void {
  for (const value of values) callback(value);
}
forEachVoid(["a", "b"], (value: string): string => { calls++; return value.toUpperCase(); });
console.log("calls:", calls); // calls: 2; explicit string return is accepted by the void callback contract
type Handler = (request: { id: string }) => string;
const handler: Handler = request => `hi ${request.id}`;
console.log(handler({ id: "u1" })); // hi u1
// const missing: Handler = request => request.missing; // uncomment: TS2339
```

The output is `2,4,6 1,2,3`, `2,4,6`, `calls: 2` and `hi u1`. Both array-result equality checks pass. The callback parameters are numbers because the map target provides that context. The fixed variable similarly supplies a number-to-number signature; Handler supplies the request's id member.

Activate detached to see TS7006 on its context-free parameter. Activate wrong or missing to observe TS2339: a known number does not have toUpperCase, and the request has no missing field. Use a parameter or variable annotation when a callback has no useful context at its declaration; do not assume it becomes unknown by default.

The explicitly string-returning callback passed to forEachVoid is accepted. The host's void contract permits ignoring that result even though the source callback annotates it as string. This differs from annotating that callback's implementation as void and returning a string from its body. Context helps type the parameter; it does not cancel the void callback discard rule. Full source-level widening/contextual mechanics belong in [inference](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.2. Type inference widening and contextual typing.md>), while [generic functions](<../2. Overloads and Generics/2.2. Generic functions inference constraints defaults and scope.md>) explains the mapper relationship.

### 4) **Common confusion**

A void result view does not force undefined at runtime. An async function remains promise-returning even when accepted as a void callback; identify who observes that promise. A literal-return function need not widen to string, while a concatenated or already widened source may do so. Contextual parameter typing and a published return annotation are separate pieces of the callable's contract.

### 5) **Performance note**

Return annotations and equality assertions are erased, while function calls, promise work, logging and exception paths remain runtime behavior. This lesson measures no compiler complexity, incremental-cache benefit or runtime speed. An explicit return contract can help expose an unintended API change, but that is a checking/design benefit, not a measured optimization. Investigate actual build cost with the [measurement workflow](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>).

### 6) **Mentor note**

Have the learner predict the static type and runtime value of ignored(), then explain why a promise-returning callback is accepted by invokeIgnoring. A strong answer identifies the caller's view and the code that handles the task's rejection. Next ask why makeTag infers a union while widened infers string, and why publishedRoute exposes a broader method contract. Finish by moving an inline map callback into an unannotated variable and diagnosing TS7006 at its declaration.
