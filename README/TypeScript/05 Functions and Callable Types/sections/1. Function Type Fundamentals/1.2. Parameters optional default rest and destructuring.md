## 1.2. Parameters — optional, default, rest and destructuring

### 1) **Optionality matrix** (`param?: T` vs `param: T | undefined` vs `param = default` — assignability, `exactOptionalPropertyTypes`, call-site arity)

**Definition** — TypeScript spells "maybe you don't pass this" three ways. `param?: T` means the argument may be omitted — at call site `f()` is legal and inside the body `param` is `T | undefined`. `param: T | undefined` means the argument *must* be supplied (arity 1), but the value may be `undefined`. `param = defaultValue` is sugar for `param?: T` with a runtime fallback — if the caller omits or passes `undefined`, the default runs. Under `--exactOptionalPropertyTypes` (TS 4.4+, see [13 Configuration](<../../../13 Configuration and Compiler Options/README.md>) textual forward) `?:` and `| undefined` diverge: `?:` allows omission but not explicit `undefined` unless the type includes it.

**What problem it solves / history** — JavaScript functions are variadic by default — `function f(a,b){}` can be called as `f()`, `f(1)`, `f(1,2,3)` with `arguments` silently padding or discarding. TypeScript needed a way to mark which omissions are *intentional* and which are bugs. `?:` (added TS 1.0) models omission; `| undefined` (with `strictNullChecks` TS 2.0) models "supply an explicit absence"; default params (ES2015) model the common JS pattern `x = x || 10` with a precise type.

**Modern guidance** — as of TypeScript 5.9 era, use `param?: T` when the caller should be able to omit — it documents arity, not just value. Use `param: T | undefined` when the caller *must* acknowledge the param (arity contract) even if the value is absent — e.g., curried handlers where position matters. Use default `param = 42` when there is a single sensible fallback and you want `f()` and `f(undefined)` to behave identically. Never mark a required param as `?:` just to avoid passing `undefined` — it silently changes arity and weakens call-site checks.

**Runnable example** — arity and the three spellings (good vs bad, `tsc --strict`):

```typescript
// good — ?: caller may omit; inside body it's T | undefined so you must narrow
function greet(name?: string): string {
  return `hi ${name ?? "guest"}`;
}
console.log(greet()); // hi guest — omitted
console.log(greet("Ada")); // hi Ada
console.log(greet(undefined)); // hi guest — explicit undefined also allowed

// good — T | undefined: caller must supply one argument (arity 1), value may be undefined
function greetExplicit(name: string | undefined): string {
  return `hi ${name ?? "guest"}`;
}
// greetExplicit(); // error TS2554: Expected 1 arguments, but got 0 — arity enforced
console.log(greetExplicit(undefined)); // ok — arity 1, value is undefined

// good — default: omission and explicit undefined both trigger the default
function timeout(ms = 1000): number {
  return ms;
}
console.log(timeout()); // 1000
console.log(timeout(undefined)); // 1000 — undefined triggers default
console.log(timeout(500)); // 500

// bad — ?: on a callback that positionally requires the argument (curry case)
type Handler = (a: string, b?: string) => void;
const h: Handler = (a, b) => console.log(a, b?.toUpperCase());
// callers that rely on position may omit second arg accidentally and lose contextual typing
// fix — use | undefined when position matters: (a: string, b: string | undefined) => void
type StrictHandler = (a: string, b: string | undefined) => void;
const hs: StrictHandler = (a, b) => console.log(a, b?.toUpperCase());

// bad — default hides that the param is effectively optional but call-site loses the literal
// function fetch(url?: string = "/api") — syntax error: can't combine ?: and default
// fix — use one: function fetch(url = "/api") or function fetch(url?: string)
```

```typescript
// exactOptionalPropertyTypes divergence — enable with --exactOptionalPropertyTypes
type Opt = { timeout?: number };
type Explicit = { timeout: number | undefined };

function withOpt(o: Opt) { console.log(o.timeout); }
withOpt({}); // ok — omitted
withOpt({ timeout: 3000 }); // ok
// withOpt({ timeout: undefined }); // error under exactOptionalPropertyTypes — 'timeout' is optional, not undefined

function withExplicit(e: Explicit) { console.log(e.timeout); }
// withExplicit({}); // error — property missing (must be supplied)
withExplicit({ timeout: undefined }); // ok — value undefined is required to be present
```

**Common confusion** — "`?:` and `| undefined` are the same under `strictNullChecks`" — without `exactOptionalPropertyTypes` they overlap heavily, but `?:` changes *arity* (0 vs 1 argument) while `| undefined` does not — `f()` vs `f(undefined)` are different calls. "`undefined` triggers a default param" — only `undefined` (or omission) triggers the default; `null` does *not* — `timeout(null)` would be a type error for `ms = 1000` where `ms: number`. "Destructured optional is the same" — destructuring defaults interact (see §3).

**Performance note** — all three are checker-only for arity — zero emit difference beyond the default-value initialization code (`ms = 1000` emits `ms = 1000` in JS). `exactOptionalPropertyTypes` adds no runtime cost but can increase type-check diagnostics because `{ timeout: undefined }` is no longer assignable to `{ timeout?: number }` — measure `tsc --extendedDiagnostics` if you enable it on a large codebase with many optional props.

**Mentor note** — quiz with `function f(a?: string, b: string)` — ask why it errors — answer is `?:` cannot skip positionally: optional params must be last, or you must use `| undefined`. Teach the "arity is documentation" framing — `?:` says "you may not supply this position"; `| undefined` says "you must supply this position, even if the value is absent."

### 2) **Rest as tuple** (`...args: T[]` vs `...args: [A, B]` — why rest is syntax for a final tuple, and how spread arity is checked)

**Definition** — a *rest parameter* `...args: T[]` collects all remaining arguments into an array; `...args: [A, B, C]` (labeled tuple) collects them with fixed arity and per-position types. At call sites, spread `fn(...tuple)` is checked as if the tuple elements were passed positionally — `readonly` tuples and labeled tuples preserve names in hover.

**What problem it solves / history** — JavaScript `function f(...args){}` gathers variadic arguments at runtime; TypeScript needed to type that gathering — `...args: string[]` (TS 1.0) typed the bag, but it lost per-position information (`format("%s %d", "hi", 42)` could not know first is string, second number). Labeled tuples (TS 4.0) and variadic tuples (TS 4.0+) let rest carry *arity* — `...args: [format: string, ...values: unknown[]]` models `printf`.

**Modern guidance** — as of TypeScript 5.9 era, use `...args: readonly unknown[]` or a specific labeled tuple for public variadic APIs — `readonly` accepts both mutable and readonly spreads, and labels document each position. Use plain `...args: T[]` for homogeneous bags (e.g., `sum(...nums: number[])`). Never type rest as `any[]` — it disables per-element checks and infects callers (see [2.1. any the unchecked escape hatch](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.1. any the unchecked escape hatch.md>)).

**Runnable example** — homogeneous vs tuple rest with spread checks (good vs bad, `tsc --strict`):

```typescript
// good — homogeneous rest: any number of numbers
function sum(...nums: number[]): number {
  return nums.reduce((a, b) => a + b, 0);
}
console.log(sum()); // 0
console.log(sum(1, 2, 3)); // 6
// sum(1, "2"); // error — string not assignable to number

// good — labeled tuple rest: fixed leading param + variadic tail, spread-checked
function format(fmt: string, ...args: [label: string, count: number]): string {
  return `${fmt} ${args[0]} x${args[1]}`;
}
console.log(format("items:", "apple", 3)); // items: apple x3
const tuple: [string, number] = ["banana", 5];
console.log(format("items:", ...tuple)); // ok — tuple satisfies rest
// format("items:", "apple"); // error — missing second element
// format("items:", "apple", "oops"); // error — second must be number

// good — readonly rest accepts both mutable and readonly spreads
function join(...parts: readonly string[]): string {
  return parts.join("-");
}
const ro: readonly string[] = ["a", "b"];
join(...ro); // ok — readonly rest accepts readonly tuple
join("a", "b"); // also ok

// bad — any[] rest disables checks and leaks
function logAny(...args: any[]): void { console.log(args); }
logAny(1, "oops", { weird: true }); // compiles — any element, no check
// fix — use unknown[] or specific tuple so callers are checked
function logChecked(...args: readonly unknown[]): void { console.log(args.length); }

// bad — typing rest as optional param instead of tuple loses spread checking
// function bad(first?: string, second?: number) — callers can pass 0,1,2 args silently
// fix — model arity explicitly with tuple rest so spread is validated: ...args: [string, number] | []
```

**Common confusion** — "rest is `any[]` by default" — without `noImplicitAny` (in `strict`) a bare `...args` is an implicit `any[]` error — annotate it. "Spread always works" — `fn(...args)` where `args: string[]` does *not* satisfy `...args: [string, number]` because arity is unknown — the checker requires a tuple with known length for fixed rest. "Labels affect types" — labels are documentation only — `[a: string, b: number]` and `[string, number]` are identical structurally.

**Performance note** — rest/tuple scoring is O(arity) at call sites — negligible. The cost that matters is hover — a 20-element labeled tuple expands in the tooltip — prefer `type Args = [format: string, ...values: unknown[]]` and spread `...args: Args` to keep hover readable. No runtime cost — rest emits `...args` (ES2018+) or a helper in down-level targets; `...tuple` spread emits `...tuple`.

**Mentor note** — teach with `printf`-style `format` — students see why `...args: string[]` is too loose and a tuple is precise. Exercise: given `function f(...args: [string, number])` ask what `const t: string[] = ["a","b"]; f(...t)` does — answer is *error* (unknown length), while `const t2 = ["a",3] as const; f(...t2)` *ok* (tuple literal).

### 3) **Destructured params** (`function f({ x, y }: { x: number }): void` — naming the destructured shape without duplicating the type)

**Definition** — *destructured parameters* unpack an argument at the signature level: `function f({ host, port }: { host: string; port?: number })` — the first argument is an object, and `host`/`port` are bindings inside the body. The *type* is on the whole pattern, not on the individual identifiers — `({ x }: { x: number })` not `({ x: number })`.

**What problem it solves / history** — options-bag APIs `createUser({ name, email })` are ergonomic in JS, but typing each destructured binding separately duplicates the shape (`{ name: string; email: string; ... }` vs `{ name, email }` param list). Destructured params let one object type govern all bindings and let defaults live on the destructuring (`{ port = 5432 }`) rather than on a second line.

**Modern guidance** — as of TypeScript 5.9 era, type the *whole* destructured pattern once — `function connect({ host, port = 5432 }: { host: string; port?: number })`. Prefer a named type alias for reuse: `type ConnectOpts = { host: string; port?: number }` then `function connect({ host, port }: ConnectOpts)`. Use defaults on the destructuring (`port = 5432`) rather than on the whole param (`opts = {}`) unless the entire bag may be omitted — then default the bag: `function connect({ host, port = 5432 }: ConnectOpts = { host: "localhost" })` is rarely correct; prefer overload or wrapper object.

**Runnable example** — options-bag with defaults and reuse (good vs bad, `tsc --strict`):

```typescript
// good — type the whole pattern once, defaults on the bindings
type ConnectOpts = { host: string; port?: number; retries?: number };
function connect({ host, port = 5432, retries = 3 }: ConnectOpts): string {
  return `${host}:${port} retries=${retries}`;
}
console.log(connect({ host: "localhost" })); // localhost:5432 retries=3
console.log(connect({ host: "db", port: 3306, retries: 5 })); // db:3306 retries=5

// good — reuse the same type for callers so they get hover and excess checks
const opts: ConnectOpts = { host: "cache", retries: 1 };
console.log(connect(opts)); // ok — excess not allowed in literal, allowed via variable width

// bad — typing destructured bindings individually duplicates and drifts
// function badConnect({ host, port }: string, number): void {} // syntax error — can't type bindings separately
// function alsoBad({ host }: { host: string }, { port }: { port?: number }): void {} // two params, not one bag
// fix — one object type for the whole bag (ConnectOpts above)

// bad — forgetting the type on the pattern falls back to implicit any (if noImplicitAny is off, silently any)
function untypedBag({ host, port }: { host: string; port?: number }): string { // without annotation would be any
  return `${host}:${port}`;
}
// fix — always annotate the pattern; alias if repeated

// good — omitting the whole bag when every field is optional (rare, document it)
type FetchOpts = { url?: string; signal?: AbortSignal };
function fetchWithDefaults({ url = "/api", signal }: FetchOpts = {}): string {
  return url;
}
console.log(fetchWithDefaults()); // /api
console.log(fetchWithDefaults({ url: "/users" })); // /users
```

**Common confusion** — "`{ x, y }` destructuring is the type" — the destructured names are *values*; the type after `:` is the type of the *whole* argument — `({ x }: { x: number })` not `({ x: number })`. "Default on the pattern vs default on the param" — `{ port = 5432 }` defaults `port` when the *property* is missing; `= {}` defaults the *whole argument* when omitted — `function f({ x } = { x: 1 })` vs `function f({ x = 1 }: { x?: number })` are different contracts. "Excess checks don't apply" — they do — `connect({ host: "h", extra: 1 })` still freshness-checks the literal against `ConnectOpts`.

**Performance note** — destructured params emit identical code to manual `opts.host` access — the destructuring is syntax only. Checker cost is one object-type walk — negligible. The readability win dominates: one alias for the options bag keeps call-site hover small (the bag name, not 15 inline fields).

**Mentor note** — have students convert apositional `function createUser(name: string, email: string, age?: number)` into an options bag and back — discuss arity vs discoverability vs call-site naming. Review check: give `{ host, port }: HostOpts` and ask where `port`'s default should live — answer is on the *binding* (`port = 5432`) not on the bag.
