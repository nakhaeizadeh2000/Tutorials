## 2.1. tsd, expect-type and dtslint

### 1) **Definition** (expectType)

**Definition** — Type-level tests assert *types*, not runtime values, using helpers that fail to compile if expectation mismatches. Tools:

- **`expect-type`** (light, `vitest`/`tsc` paired) — `expectTypeOf<T>().toEqualTypeOf<U>()`.
- **`tsd`** (classic) — `expectType<string>(value)` + `expectError(...)` + separate test folder with `tsd`.
- **`dtslint` (DefinitelyTyped)** — stricter for `.d.ts` (uses `// $ExpectType string`).

Pick one; they all rely on `tsc` to typecheck test file — so failures appear as `tsc` errors before runtime.

```typescript
import { expectTypeOf } from "expect-type";

// expect-type usage
type User = { id: string; name: string };
expectTypeOf<User>().toEqualTypeOf<{ id: string; name: string }>();
expectTypeOf<keyof User>().toEqualTypeOf<"id" | "name">();

// utility assertion
type MyPick<T, K extends keyof T> = { [P in K]: T[P] };
expectTypeOf<MyPick<User, "id">>().toEqualTypeOf<{ id: string }>();

// dtslint style for .d.ts
// declare function greet(x: string): string;
// // $ExpectType string
// greet("hi");

// tsd style
// import { expectType, expectError } from "tsd";
// expectType<string>("hi");
// expectError(greet(123));
```

Add as `tsc` typecheck step, not runtime test runner.

### 2) **Example** (tsd test)

```typescript
// file: test-d/user.test-d.ts (tsd convention)
import type { User } from "../src/models.js";
import { expectType, expectError, expectNotAssignable } from "tsd";

expectType<string>({} as User["id"]);
expectError({} as User["missing"]); // should error
expectNotAssignable<User>({ name: "x" }); // missing id — not assignable

// shared helper: ensure mapped type keeps literal
type Foo = "a" | "b";
type Bar = Foo extends string ? true : false;
expectType<Bar>(true);

// vitest + expect-type combo (modern):
// vitest: runtime test file also does expectTypeOf at top — single file tests both
// src/utils.test.ts (runs with vitest, but type checked via tsc --noEmit)
import { describe, test, expect } from "vitest";
import { expectTypeOf } from "expect-type";
import { formatUser } from "./utils.js";
describe("formatUser", () => {
  test("runtime", () => { expect(formatUser("Ava")).toBe("AVA"); });
  test("types", () => { expectTypeOf<Parameters<typeof formatUser>[0]>().toEqualTypeOf<string>(); });
});
```

Run in CI (see 2.2).

### 3) **Bad** (only runtime tests)

**Bad — testing only runtime values:**

```typescript
// bad: asserts runtime but never types
test("format returns string", () => {
  expect(formatUser("Ava")).toBe("AVA"); // runtime pass, but type could still be any — inferred error unseen
});

// bad: any in test utils hides type error
function createUserBad(): any { return { id: "1", name: "Ava" }; }
let u = createUserBad(); // any — not testing User shape

// good: type test adjacent to runtime
expectTypeOf<User>().toHaveProperty("name"); // ensures shape change breaks test

// bad: dtslint // $ExpectType comment drifts — use expect-type helper that CI checks via tsc --noEmit
```

Without type-level tests, refactors to utility types (`Omit`, `Mapped`) break silently.

### Mentor note

Add `expect-type` as devDependency and gate `tsc --noEmit` on each PR. Type-level tests are 5 lines but catch regressions that unit tests cannot (e.g., "did `Pick` still produce correct shape?").

### Common confusion

- "Type tests run at runtime" — they run at `tsc` check time; `vitest` may ignore them unless configured to typecheck (use `vitest --typecheck` or separate `tsc`).

### Performance note

Type-level test files add checker load proportional to assertions; keep them co-located, and use `--isolatedModules` for non-test files to keep check fast.
