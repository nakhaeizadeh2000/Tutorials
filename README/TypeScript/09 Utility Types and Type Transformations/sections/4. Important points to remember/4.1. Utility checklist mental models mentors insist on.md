## 4.1. Utility checklist — mental models mentors insist on

### 1) **Map with mapped, filter with conditional, extract with `infer`** (one primitive per intent)

**Definition** — three tools, three intents: reshaping objects → mapped types (`{ [K in keyof T]… }`); selecting union members → conditionals (`T extends U ? … : never`); pulling nested types out → `infer` (`Array<infer U>`, `(...args: never[]) => infer R`). Choosing by intent (not by familiarity) keeps each transform one primitive deep instead of a conditional doing mapping's job or a mapper doing filtering's.

**What problem it solves / history** — intent-mismatched transforms (`Exclude` reimplemented as a mapped type over keys, `Pick` reimplemented as a conditional over members) worked on the author's example and broke on the next input kind — because the mechanic fit the example, not the intent. The three-tool rule routes each job to the primitive whose *failure modes* match the job (mapping preserves keys, filtering sinks members, extraction names pieces).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), start every transform by naming the intent in one word (reshape? select? extract?) and reach for the matching primitive — then compose (mapped *containing* a conditional guard, conditional *returning* an `infer` binding) for mixed jobs. See [1.1. Mapped fundamentals](<../1. Mapped Types/1.1. Mapped type fundamentals homomorphic mapping over keys.md>) + [2.1. Conditional fundamentals](<../2. Conditional Types/2.1. Conditional fundamentals distributive law and never branches.md>) + [2.3. infer pipelines](<../2. Conditional Types/2.3. infer pipelines ReturnType Parameters Awaited.md>).

**Runnable example** — intent picks the primitive (good vs bad, `tsc --strict`):

```typescript
// good — reshape (mapped), select (conditional), extract (infer): each intent its tool
interface U { id: string; age: number; }
type OptU = { [K in keyof U]?: U[K] }; // reshape → mapped
type Strs<T> = T extends string ? T : never; // select → conditional
type El<T> = T extends Array<infer E> ? E : never; // extract → infer
const o: OptU = {};
const s: Strs<"a" | 1> = "a";
const e: El<number[]> = 1;
console.log(Object.keys(o).length, s.toUpperCase(), e.toFixed(0)); // 0 A 1

// bad — conditional doing mapping's job: works once, breaks on next kind
type PickBad<T, K extends keyof T> = T extends object ? { [P in K]: T[P] } : never; // conditional wrapper adds nothing
// fix — { [P in K]: T[P] }: the mapper alone (intent was reshape all along)
type PickGood<T, K extends keyof T> = { [P in K]: T[P] };
const pg: PickGood<U, "id"> = { id: "u1" };
console.log(pg.id.toUpperCase()); // U1
```

**Common confusion** — "one primitive suffices for everything" — conditionals *can* rebuild objects and mappers *can* filter via `as never`, but each bends its failure modes (distribution accidents, lost modifier memory) — composition beats contortion. "composing means nesting deeply" — two layers (guard outside, mapper inside) cover nearly every production transform; depth beyond three wants a named intermediate, not cleverness.

**Performance note** — intent-matched primitives check minimally (mapper visits keys once; filter walks members once); mismatched ones double-walk (conditional wrapping a mapper evaluates the guard *plus* the mapping per member) — small per reference, real across generated-schema transforms.

**Mentor note** — the one-word-intent drill ("reshape? select? extract?") before any transform code — asked out loud in reviews — prevents more utility bugs than any catalog knowledge. Exercise: classify five stdlib utilities by intent before reading their sources, then verify — the predictions prove the rule transferred.

### 2) **Prefer stdlib names at call sites** (readability, hover, cache sharing)

**Definition** — `Partial`, `Pick`, `Omit`, `Exclude`, `Extract`, `NonNullable`, `ReturnType`, `Parameters`, `Awaited` at call sites; custom bodies only for genuinely new semantics (`ExtractByKind`, `OmitDeep`, `PublicKeys`). Names read instantly, hover compactly, and share instantiation caches repo-wide; copies fragment caches and risk naked/wrapped forks.

**What problem it solves / history** — private one-line copies (`MyExcl`, `DropNull`, `GetRet`) multiplied fork risk and cache fragments across files (see [2.2. Stdlib](<../2. Conditional Types/2.2. Exclude Extract NonNullable Pick Omit under the hood.md>) promise 3) — each copy a future accident with a private name nobody else recognizes. The naming rule deletes the copies and keeps the semantics.

**Modern guidance** — as of TypeScript 5.9 era, grep custom single-conditional aliases quarterly and replace stdlib-duplicates with names; compose stdlib pieces for near-misses (`Pick<T, Exclude<keyof T, K>>` before raw `extends`). Comment naked-or-wrapped intent on the raw conditionals that remain.

**Runnable example** — names share, copies fragment (good vs bad, `tsc --strict`):

```typescript
// good — canonical names: one cache entry, every reader fluent
type A = Exclude<"a" | 1, string>; // 1
type B = Pick<{ x: number; y: string }, "x">; // { x: number }
console.log("named");

// bad — private copies: same bodies, fragmented caches, fork risk
type MyEx<T, U> = T extends U ? never : T; // Exclude by another name (extra cache entry)
// fix — Exclude<T, U>: the name every file already shares
const a: A = 1;
console.log(a.toFixed(0)); // 1
```

**Common confusion** — "domain-specific names read better" — `Exclude<Status, "archived">` reads *more* precisely than `DropArchived<Status>` (mechanic visible, no lookup) — reserve custom names for composed semantics, not renamed primitives. "stdlib lacks my exact filter" — `ExtractByKind<T, K>` composing `Extract` is a new semantic (deserves a name); `T extends U ? never : T` inline is a copy (does not).

**Performance note** — canonical names share instantiation caches across files; copies check per alias — names are a measured check-time practice on large codebases, not merely style.

**Mentor note** — quarterly alias audit (grep `extends.*?.*never` one-liners, compare against stdlib) — each deletion removes a fork risk. Hiring signal: `Exclude`-first candidates know the catalog; `extends`-first candidates know only syntax.

### 3) **Naked distributes, wrapped tests whole** (the sentence predicting every conditional)

**Definition** — naked `T` in `T extends U ? X : Y` maps member-by-member; `[T] extends [U]` (or any wrapper) tests whole-to-whole. The single sentence predicts `Exclude` (naked filter), `IsNever` (wrapped emptiness), `Omit`-over-union surprises (naked `T` inside `Pick`), and the accidental-fork class of custom filters.

**What problem it solves / history** — conditional questions dominated generics Q&A precisely because each looked bespoke — `Exclude` behavior, `IsNever` trap, `Omit`-union surprise, `[T]` escapes seemed like four facts. One rule unifies them: find the naked parameter (or its absence) and the result follows — four memorizations collapse into one prediction.

**Modern guidance** — as of TypeScript 5.9 era, read every conditional naked-first: locate `T`, check for wrappers, predict distribution, then verify with a two-member probe (`"a" | 1` distinguishes every case in this domain). Write the naked-or-wrapped intent in a comment on every raw conditional that survives review.

**Runnable example** — one rule, four predictions (good vs bad, `tsc --strict`):

```typescript
// good — probe union distinguishes naked from wrapped in one hover
type Naked<T> = T extends string ? T : never; // distributes: "a"
type Wrapped<T> = [T] extends [string] ? T : never; // whole: never on ("a" | 1)
const n: Naked<"a" | 1> = "a";
// const w: Wrapped<"a" | 1> = "a"; // error TS2322 — never (whole union isn't string)
console.log(n.toUpperCase()); // A

// bad — guessing per-utility instead of applying the rule
// "does MyFilter distribute?" — find the naked T (or wrapper) and stop guessing
// fix — probe `"a" | 1` once per custom conditional; record naked/wrapped in a comment
```

**Common confusion** — "the rule has exceptions" — `keyof T`, `T[]`, `Box<T>`, function-wrapped `T` all test whole — consistently, because none is naked — apparent exceptions are wrapper confirmations. "probing wastes time" — one probe instantiation vs one production incident — cheapest test in the type system.

**Performance note** — naked conditionals cost O(members); wrapped cost O(1) — choosing wrapped for whole-union questions is both clearer *and* faster; choosing naked for member questions is the only correct option regardless of cost.

**Mentor note** — the `"a" | 1` probe belongs on the team checklist next to the one-word-intent drill — two habits covering nearly every conditional review. Exercise: classify six stdlib/custom conditionals naked-vs-wrapped before hovering results — perfect scores prove the rule internalized.

### 4) **Budget recursion before it budgets you** (caps, scope, largest-schema fixture)

**Definition** — every recursive utility ships a depth cap (tuple-counter, default 3–5, overflow → passthrough `T`), applies to scoped inputs (owned subtrees deep, generated schemas shallow), and pins the largest real schema as a compiling fixture. The rule from [08/3.2](<../../../08 Generics Deep Dive/sections/3. Variance and Advanced Generic Patterns/3.2. Recursive generic types and self-referential patterns.md>) and [08/5.1](<../../../08 Generics Deep Dive/sections/5. Common pitfalls to production bugs/5.1. Real production bugs caused by generic misunderstandings.md>), restated for the catalog: `DeepPartial`, `DeepReadonly`, `Awaited`-chains, and template products all share one budget discipline.

**What problem it solves / history** — each incident class in this domain's pitfalls (5.1 promise 3: CI-only TS2589 over generated schema) traces to unbounded recursion meeting unbounded input — locally green (small fixture), globally red (whole program). Cap + scope + fixture converts every such incident into a local error with a documented repair *before* main goes red.

**Modern guidance** — as of TypeScript 5.9 era, no recursive utility merges without: a counter parameter with default, a doc comment stating D and overflow behavior, and a fixture compiling the largest real input. Application code prefers scoped application (deep on owned, shallow on generated). See [3.1. Deep transforms](<../3. Transformations in Practice/3.1. Deep transforms DeepPartial DeepReadonly and the budget.md>) promise 3 for the full production pattern.

**Runnable example** — capped, scoped, fixtured (good vs bad, `tsc --strict`):

```typescript
// good — cap + scope: deep where bounded, shallow where generated
type Capped<T, D extends number = 3, Seen extends 0[] = []> = Seen["length"] extends D
  ? T
  : T extends object ? { [K in keyof T]?: Capped<T[K], D, [...Seen, 0]> } : T;
interface Owned { a: { b: string } }
const o: Capped<Owned> = { a: {} };
console.log(o.a?.b ?? "none"); // none — within budget, leaves omittable

// bad — unbounded utility applied to unbounded input (kept shallow here; CI knows the rest)
// type DeepAny<T> = T extends object ? { [K in keyof T]?: DeepAny<T[K]> } : T;
// fix — Capped (counter) + scope (owned deep, generated shallow) + fixture (largest schema compiles)
```

**Common confusion** — "caps weaken the transform" — overflow passthrough is sound (untransformed, not wrong) — strictly better than a timed-out build. "fixtures duplicate tests" — budget fixtures test *scale*, feature tests test *behavior* — different failures, different fixtures. "small utilities don't need caps" — caps cost one parameter; incidents cost queue-hours — cap everything recursive, no exceptions.

**Performance note** — caps bound memory linearly (D × keys); overflow is O(1); fixtures add one whole-schema check per utility-touching PR — the cheapest insurance in the build.

**Mentor note** — post-mortem template (cap + fixture + doc comment) from 08/5.1 applies verbatim — print it in the contributing guide. Review gate: recursive utilities without counters fail review unconditionally.
