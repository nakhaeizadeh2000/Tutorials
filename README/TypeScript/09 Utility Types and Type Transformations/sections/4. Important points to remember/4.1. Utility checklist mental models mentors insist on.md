## 4.1. Utility checklist — mental models mentors insist on

Review a transformation by naming the required result, checking its source relationship, then identifying the JavaScript that establishes the corresponding value. A familiar utility name can help communicate an operation, but it does not replace that reasoning. Use these four questions after the domain's worked lessons.

### 1) **Which relationship should change and which must remain?**

Property mapping, union selection and shape extraction solve different questions, and a useful transform can combine them. A conditional around a mapper can deliberately distribute across alternatives; it is not automatically redundant. A mapped key filter can intentionally remove properties. Start with accepted and rejected examples instead of enforcing a one-primitive rule.

Use [mapping foundations](<../1. Mapped Types/1.1. Mapped type fundamentals homomorphic mapping over keys.md>) for structure, [conditional fundamentals](<../2. Conditional Types/2.1. Conditional fundamentals distributive law and never branches.md>) for union-member questions and [callable/awaited pipelines](<../2. Conditional Types/2.3. infer pipelines ReturnType Parameters Awaited.md>) for extraction boundaries. Deriving an element type does not prove an element exists.

### 2) **Does the chosen utility have the exact needed contract?**

Read the actual input constraints and resulting shape. Omit permits absent removal keys, while Pick requires source keys. NonNullable uses a non-nullish intersection and preserves zero, false and empty string. Partial<typeof snapshot> can be too narrow or readonly for valid edits; Partial<Domain> may express the intended changes.

Prefer standard utility names for recognizable operations. A domain alias can also communicate meaning, and a custom composition can add genuinely different behavior. Do not use a claimed repository-wide cache advantage or hiring stereotype to decide a name. Consult [standard utilities](<../2. Conditional Types/2.2. Exclude Extract NonNullable Pick Omit under the hood.md>) and [snapshot versus editing contracts](<../3. Transformations in Practice/3.3. satisfies and as const preserving literals through transforms.md>) for those decisions.

### 3) **Are alternatives and edge cases preserved deliberately?**

Standard Omit over an object union derives common keys; an explicitly distributive Omit can preserve each branch's required payload. For a conditional, find the checked left operand. A bare T can distribute even when its right-hand pattern is an array or tuple; a left wrapper changes the question. Test mixed inputs, never, unknown and any when relevant instead of assuming one two-member probe proves every behavior.

Use [key remapping](<../1. Mapped Types/1.3. keyof constrained mapping and template literal keys.md>) and [legal string combinations](<../3. Transformations in Practice/3.2. Template literal composition Capitalize handlers and routes.md>) to inspect filtered keys and collisions. A full cross-product can admit illegal combinations if the domain has a relationship between its factors.

### 4) **Which operation establishes the value and what happens at a stopping boundary?**

Omitted static keys can remain on an assigned runtime object. Readonly views do not copy or freeze it. A complete type-derived handler table does not register callbacks automatically. Identify the actual construction, validation, dispatch or update operation and verify its observable result.

For deep transforms, choose array/tuple, container and leaf policies before recursion. A cap's unchanged remainder may require deeper fields or leave writes possible; reaching it is not automatically a diagnostic. Do not replace a required full transformation with a partial one merely to claim equivalent behavior or a speed improvement. [Deep policies](<../3. Transformations in Practice/3.1. Deep transforms DeepPartial DeepReadonly and the budget.md>) and [instantiation budgets](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.2. Instantiation budgets and TS2589 carve-outs.md>) own those experiments.

Run this integrated review drill with TypeScript 7.0.2 and Node.js 20.20.2. Save it as export-review.ts, compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist export-review.ts`, then run `node dist/export-review.js`. Activate negatives separately using the same flags with --noEmit instead of --outDir dist.

```typescript
type Entry =
  | { kind: "account"; id: string; email: string; secret: string }
  | { kind: "device"; id: string; serial: string; secret: string };
function loadEntries(): Promise<readonly Entry[]> {
  return Promise.resolve([
    { kind: "account", id: "a1", email: "a@example.test", secret: "private" },
    { kind: "device", id: "d1", serial: "s1", secret: "private" }
  ]);
}
type Loaded = Awaited<ReturnType<typeof loadEntries>>[number];
type PublicEach<T> = T extends unknown ? Omit<T, "secret"> : never;
type PublicEntry = PublicEach<Loaded>;
type Common = Omit<Loaded, "secret">;
const insufficient: Common = { kind: "account", id: "a1" }; // Accepted, but loses branch payload requirements.
// const missing: PublicEntry = insufficient; // TS2322
function unexpected(value: never): never { throw new Error(`unhandled entry: ${String(value)}`); }
function redact(entry: Loaded): PublicEntry {
  switch (entry.kind) {
    case "account": return { kind: entry.kind, id: entry.id, email: entry.email };
    case "device": return { kind: entry.kind, id: entry.id, serial: entry.serial };
    default: return unexpected(entry);
  }
}
async function main(): Promise<void> {
  const entries = await loadEntries();
  // console.log(entries[0].id); // TS2532
  const first = entries[0];
  if (first === undefined) throw new Error("fixture needs an entry");
  const view: PublicEntry = first;
  // console.log(view.secret); // TS2339
  console.log(JSON.stringify(view));
  const published = entries.map(redact);
  console.log(published.map(entry => entry.kind).join(","));
  console.log(published.map(entry => "secret" in entry).join(","));
}
void main().catch(error => { console.log("unexpected failure", error); });
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Source = Expect<Equal<Loaded, Entry>>;
type CommonShape = Expect<Equal<Common, { kind: "account" | "device"; id: string }>>;
type Payload = Expect<Equal<Extract<PublicEntry, { kind: "account" }>["email"], string>>;
```

The output is `{"kind":"account","id":"a1","email":"a@example.test","secret":"private"}`, then `account,device`, then `false,false`. Three live probes compile. The assigned public view still contains secret. The explicit redaction constructs the public values and preserves each branch's payload. LoadEntries returns local fixtures; no external data source or service has been validated by the utility pipeline.

This example deliberately uses Omit to focus on the mechanics. For an evolving public boundary, decide whether newly added internal fields should be admitted automatically or whether a fixed Pick is the intended contract. That decision affects both the return type and the actual projection; the [source-evolution exercise](<../2. Conditional Types/2.2. Exclude Extract NonNullable Pick Omit under the hood.md>) demonstrates it.

### 5) **Common confusion**

A transform can preserve modifiers while failing to preserve alternative-specific payloads. A snapshot can be precise yet wrong for an editing API. A static public view can omit a property while its runtime value still serializes that property. These observations concern different relationships, so one successful type probe cannot stand in for every required behavior.

A depth cap also has a semantic result, not just a performance setting. Check what remains required or mutable where it stops. Use the actual conditional/mapped definitions and a relevant fixture instead of assuming every recursive alias needs the same counter default.

### 6) **Performance note**

Utility types and probes erase. The drill retains promise resolution, array traversal, JSON serialization and object construction. No universal mapping/filtering complexity, alias-cache benefit or O(1) wrapped comparison was established. A transform's changed contract must be evaluated separately from its measured checking cost. Use [diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) for a real performance problem.

### 7) **Mentor note**

Ask the learner to explain the first serialized value before running the program, then identify the expression that actually removes secret. Next ask why Common is insufficient for a complete account result despite accepting its tag and id. A good review follows both type and value evidence.

For practice, add a session alternative with id, token and secret to Entry, and include a session fixture in loadEntries. Compilation must reject the remaining session at unexpected. Add a branch that constructs its public kind/id/token object without secret. Existing branches must retain their payloads, the published kind list must include session, and all three secret-presence checks must be false. An assertion that reclassifies the input without constructing the output does not meet the task.
