## 1.3. `keyof`-constrained mapping and template literal keys

### 1) **Constraining the key set** (narrowing which keys the mapper visits)

**Definition** — the `in` clause accepts any union, but constraining it (`K extends keyof T`, `K extends string`, `K extends keyof T & string`) decides the mapper's domain: full-object iteration, string-only keys (skipping `number`/`symbol`), or a caller-chosen subset. The broadest legal domain is `PropertyKey` (bare `in K` without a constraint errors — the checker forces the author to state the domain); precise when intentional, `never`-keyed when accidental.

**What problem it solves / history** — unfiltered mappers over entities with symbol-keyed internals or numeric indexes produced nonsense properties (`Symbol()` keys stringified, array indices remapped as `"length"`) — bugs that compiled because the mapper visited keys the author never considered. Key constraints make the domain explicit: `string`-keyed mappers skip symbols/numbers by construction instead of by luck.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), constrain every generative mapper (`K extends string` for handler tables, `K extends keyof T` for variants, `K extends PropertyKey` for caches) and leave variant mappers on bare `keyof T`. When callers supply the key set (`Pick<T, K extends keyof T>`), the constraint doubles as documentation of legal arguments.

**Runnable example** — domain decides the output (good vs bad, `tsc --strict`):

```typescript
// good — string-only domain skips symbols and numbers by construction
const sym = Symbol("id");
interface Entity { name: string; [sym]: number; }
type StringVals<T> = { [K in keyof T & string]: string };
const sv: StringVals<Entity> = { name: "a" }; // symbol key excluded from the domain
console.log(sv.name.toUpperCase()); // A

// good — caller-supplied subset stays checked against the source
function project<T, K extends keyof T>(obj: T, ...keys: K[]): Pick<T, K> {
  const out = {} as Pick<T, K>;
  for (const k of keys) out[k] = obj[k];
  return out;
}
console.log(project({ a: 1, b: "x" }, "b").b.toUpperCase()); // X
// project({ a: 1 }, "zzz"); // error TS2345 — K constrained to "a"

// bad — over-broad domain visits keys the author never considered
type Blind<K extends PropertyKey> = { [P in K]: number }; // domain is "whatever arrives"
const b: Blind<"a" | 1> = { a: 1, 1: 2 }; // numeric key mapped without intent
console.log(b.a.toFixed(0)); // 1
// fix — Blind<K extends string>: numeric keys rejected at the boundary
type StrictBlind<K extends string> = { [P in K]: number };
// const s2: StrictBlind<"a" | 1>; // error — 1 violates the string domain (correctly)
```

**Common confusion** — "`keyof T & string` loses homomorphism" — intersections on `keyof T` *preserve* it (still syntactically a `keyof T` iteration) — only fully-resolved unions lose memory (see [1.2. Modifier memory](<./1.2. readonly and optional modifiers with plus and minus.md>)). "constraints validate keys at runtime" — static only; `project(obj, key)` with a dynamic string still needs a runtime `in`-check before the call. "`PropertyKey` and `string` constraints are interchangeable" — `PropertyKey` admits `number`/`symbol` too — use `string` when the output must be JSON-shaped.

**Performance note** — constrained domains check faster (fewer keys visited, smaller unions cached) — `keyof T & string` over a 100-key entity with 5 symbols skips 5 instantiations per reference. Trivial singly, measurable across generated schema mappers referenced hundreds of times.

**Mentor note** — ask "which keys does this mapper visit?" before "what does it compute?" — domain-first reading catches the symbol/index bugs that value-first reading misses. Exercise: map over an interface with a symbol key unconstrained, then constrained — the disappearing property teaches domains in one hover.

### 2) **`as` key remapping** (renaming keys while mapping values)

**Definition** — `[K in keyof T as NewKey<K>]` remaps each key through a type-level function (TS 4.1+): `as Exclude<K, "secret">` filters, `as `get${Capitalize<K>}`` prefixes, `as never` drops. Value mapping (`T[K]`) and key mapping (`as …`) compose in one pass — the output has *different keys* with *computed values* from a single declaration.

**What problem it solves / history** — derived-key shapes (getters for every property, `onX` handlers for every event, `Args` for every method) previously needed code generation or parallel hand-written interfaces — both drifted from the source within a quarter. `as` remapping computes derived keys from the source at check time: renaming `name` to `getName` in the source interface renames the getter type automatically.

**Modern guidance** — as of TypeScript 5.9 era, derive mechanical key sets (`getters`, `handlers`, `args`) with `as` instead of declaring them — one source of key truth. Filter with `as Exclude<…>` / `as never` (homomorphic *and* filtered — see 1.2 promise 3); rename with template literals (next promise). Keep remapping functions total (every input key maps somewhere, even `never`) so no key vanishes silently.

**Runnable example** — getters derived, secrets dropped (good vs bad, `tsc --strict`):

```typescript
// good — one source, getters derived, secret filtered, memory kept
interface State { name: string; readonly id: string; secret: string; }
type Getters<T> = { [K in keyof T as K extends "secret" ? never : `get${Capitalize<K & string>}`]: () => T[K] };
const g: Getters<State> = { getName: () => "a", getId: () => "1" };
console.log(g.getName().toUpperCase()); // A
// g.getSecret; // error TS2339 — filtered by the `as never` branch

// bad — parallel getter interface drifts from the source
interface StateGetters { getName: () => string; getId: () => string; } // mirrors State today
// State gains `email` → Getters<State> gains `getEmail`; StateGetters silently lacks it
// fix — Getters<T>: derived keys track the source automatically
```

**Common confusion** — "`as` remapping breaks homomorphism" — filtering/renaming *within* `keyof T` keeps memory (the `getId` getter above returns `string`, and `readonly` semantics carry per 1.2 rules) — only pre-resolved unions break it. "`as never` and `Exclude` differ" — same result via different positions (`as` drops during mapping; `Exclude` drops before) — prefer `as` (one pass, memory kept). "remapped keys must stay strings" — keys may be `string | number | symbol`; template-literal remaps require `K & string` (numbers/symbols need explicit handling).

**Performance note** — remapping adds one conditional evaluation per key (O(keys), cached per instantiation) — negligible against the mapping itself. Deeply-nested template remaps (`` `a${B}${C}` `` over 500-key unions) multiply string instantiations — name intermediate key unions once.

**Mentor note** — live-derive `getEmail` by adding `email` to `State` — the getter appearing without touching `Getters` sells derivation better than any explanation. Exercise: convert one hand-mirrored `XxxGetters`/`XxxHandlers` interface to `as`-remapping and delete the mirror — count the deleted lines as the ROI.

### 3) **Template literal keys** (generating handler and event key sets)

**Definition** — template literal types in the `as` clause compute *new* key strings: `` [K in keyof T as `on${Capitalize<K & string>}`] `` turns `{ click, key }` into `{ onClick, onKey }` — keys the source object never declared, derived entirely at the type level. Intrinsics (`Capitalize`, `Uppercase`, …) transform the interpolated pieces (full catalog in [3.2. Template composition](<../3. Transformations in Practice/3.2. Template literal composition Capitalize handlers and routes.md>)).

**What problem it solves / history** — event/handler binding tables (`onClick`, `onKeyDown`, `GET /users`) were stringly-typed (`Record<string, Handler>` — ormai any typo compiled) or exhaustively hand-listed (correct but rotting). Template-literal keys derive the table from the event union: a new event in the union appears in the handler map automatically, and a misspelled handler errors against the computed set.

**Modern guidance** — as of TypeScript 5.9 era, derive binding tables from source unions (events → `onX` handlers, methods+paths → route keys) instead of listing them — the union is the single source of key truth. Constrain interpolated pieces (`K & string`) so numbers/symbols fail loudly instead of vanishing. Keep the *value* side precise (handler signatures per event, not a shared `Handler` alias that flattens arity).

**Runnable example** — handler table derived from events (good vs bad, `tsc --strict`):

```typescript
// good — events in, handler table out; typo errors, new events propagate
type Ev = "click" | "keydown";
type Handlers = { [K in Ev as `on${Capitalize<K>}`]: (at: number) => void };
const h: Handlers = { onClick: (at) => console.log(at), onKeydown: (at) => console.log(at) };
h.onClick(10); // 10 logged
// const bad: Handlers = { onClik: (at) => console.log(at), onKeydown: (at) => console.log(at) }; // error TS2741 + TS2322 — typo caught

// bad — stringly-typed table accepts every typo
const loose: Record<string, (at: number) => void> = { onClik: (at) => console.log(at) }; // compiles — dead handler ships
// fix — Handlers: the computed key set rejects what the event union never listed
```

**Common confusion** — "template keys validate at runtime" — static derivation only; dispatching `handlers[name]` with a dynamic string still needs a runtime lookup guard. "`Capitalize` runs at runtime" — intrinsic mappers are compile-time string surgery with zero emit (see 3.2). "derived tables replace the event union" — the union remains the source of truth; the table is a *view* — edit the union, never the table.

**Performance note** — key generation multiplies instantiations (events × template parts) — a 200-event union through two nested templates creates ~400 key instantiations (fine, cached once). Distributing intrinsics over 10k-member generated unions is the known cliff — derive tables from curated unions, not raw codegen output.

**Mentor note** — misspell `onClick` deliberately and read the error together — the "did you mean" moment converts skeptics faster than advocacy. Exercise: add `"scroll"` to `Ev` and watch `Handlers` demand `onScroll` — propagation made tangible. Review rule: `Record<string, Handler>` binding tables are defects where a source union exists.
