## 1.3. Keyof-constrained mapping and template literal keys

A mapped declaration has two separate choices: which source keys it visits and which output key each source key produces. A constraint limits admitted arguments; a filter can instead remove keys from an admitted type. Distinguish those operations before deriving getter or handler contracts.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence as named below. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts` and run `node dist/FILE.js`. Check commented negatives independently with those flags and --noEmit instead of --outDir dist.

### 1) **Choose admitted keys and distinguish a static view from projection**

A mapped key must be assignable to PropertyKey: string, number or symbol. A parameter constrained to keyof T selects keys supported by T. A string constraint admits only string choices, while intersecting keyof T with string selects the source's string keys and excludes numeric and symbol key types. An object can still have all three kinds of keys at runtime.

Save as keys.ts.

```typescript
const internal = Symbol("internal");
interface Entity { name: string; 1: boolean; [internal]: number; }
type Flags<Keys extends PropertyKey> = { [K in Keys]: boolean };
const flags: Flags<"name" | 1 | typeof internal> = { name: true, 1: false, [internal]: true };
// type Invalid<Keys> = { [K in Keys]: boolean }; // TS2322: unconstrained Keys is not guaranteed PropertyKey

type StringPart<T> = { [K in keyof T as K extends string ? K : never]: T[K] };
const entity: Entity = { name: "Ada", 1: true, [internal]: 9 };
const view: StringPart<Entity> = entity;
const projected: StringPart<Entity> = { name: entity.name };
console.log(flags[internal], view.name, Reflect.ownKeys(view).length, Reflect.ownKeys(projected).length);
// console.log(projected[1]); // TS7053: numeric key excluded from this contract

type OnlyStrings<Keys extends string> = { [K in Keys]: boolean };
// type Rejected = OnlyStrings<"name" | 1>; // TS2344: a constraint rejects the supplied numeric type
const callbacks: Record<string, () => void> = { run: () => {} };
console.log(JSON.stringify(callbacks));
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type SourceKeys = Expect<Equal<keyof Entity, "name" | 1 | typeof internal>>;
type KeptKeys = Expect<Equal<keyof StringPart<Entity>, "name">>;
```

The output is `true Ada 3 1`, then `{}`. Entity is accepted as input to StringPart; the mapping quietly excludes its non-string keys. OnlyStrings instead rejects a supplied numeric key type. The view still refers to entity with all three own keys, whereas the explicit object construction creates the one-key projection.

A numeric literal property 1 has a numeric key type in this interface even though ordinary object property storage coerces that key to a string. Do not confuse filtering its static key type with deleting a property. Likewise, string keys alone do not guarantee JSON preservation: the function-valued property is omitted by JSON.stringify. The [object query owner](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.3. Type queries on objects keyof indexed access and typeof capture.md>) explains static versus runtime keys in detail.

### 2) **Remap, filter and account for collisions**

An as clause computes each output key. Returning never from that key expression omits the property. A template literal can derive a new key from a string key, while T[K] still names the original property's value type. The [primary mapping guide](https://www.typescriptlang.org/docs/handbook/2/mapped-types.html#key-remapping-via-as) introduces filtering and remapping.

Save as getters.ts. These getters are actual functions supplied by the object literal; the mapped type only checks them.

```typescript
interface State { name: string; readonly id: string; secret: string; }
type Getters<T> = {
  [K in keyof T as K extends "secret" ? never : `get${Capitalize<K & string>}`]: () => T[K]
};
const state: State = { name: "Ada", id: "u1", secret: "private" };
const getters: Getters<State> = { getName: () => state.name, getId: () => state.id };
console.log(getters.getName().toUpperCase(), getters.getId());
// getters.getSecret; // TS2339
// getters.getId = () => "replacement"; // TS2540: source readonly modifier retained

type UpperKeys<T> = { [K in keyof T as Uppercase<K & string>]: T[K] };
type Collided = UpperKeys<{ id: number; ID: string }>;
const numeric: Collided = { ID: 7 };
const textual: Collided = { ID: "external" };
console.log(numeric.ID, textual.ID);
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Collision = Expect<Equal<Collided["ID"], number | string>>;
// const invalid: Collided = { ID: true }; // TS2322
```

The output is `ADA u1`, then `7 external`. The source's readonly id becomes a readonly getId property; the getter's return type remains string. The capitalization example also reveals an important limit: two source keys can become the same output key, and their value types combine. It does not report a duplicate-key error or create two runtime fields.

K & string inside the template quietly removes numeric and symbol key types in this form. If those inputs must be rejected, constrain the accepted key set instead. If numeric names should become text, design an explicit string-or-number interpolation policy. Do not assume every remap is reversible or keeps distinct source names distinct.

[Modifier operators](<./1.2. readonly and optional modifiers with plus and minus.md>) owns inheritance differences among mapping forms. In particular, the separate keyof T & string iteration example there does not preserve the same modifiers as the full keyof T mapper; encountering keyof is not a universal preservation rule.

### 3) **Generate handler names while preserving payload relationships**

A template literal derives the public handler key, and the value expression ties that handler to its original event payload. A shared any payload would lose this relationship even if every generated key were spelled correctly. The runtime object must implement every required handler in the chosen finite contract.

Save as handlers.ts.

```typescript
interface Events { click: { x: number }; keydown: { key: string }; }
type Handlers<T> = {
  [K in keyof T as `on${Capitalize<K & string>}`]: (event: T[K]) => void
};
const handlers: Handlers<Events> = {
  onClick: event => console.log(event.x.toFixed(0)),
  onKeydown: event => console.log(event.key.toUpperCase())
};
handlers.onClick({ x: 10 });
handlers.onKeydown({ key: "a" });
// handlers.onClick({ key: "a" }); // TS2353: wrong payload for this known handler
// const typo: Handlers<Events> = { onClik: handlers.onClick, onKeydown: handlers.onKeydown }; // TS2561
// const swapped: Handlers<Events> = { onClick: handlers.onKeydown, onKeydown: handlers.onClick }; // TS2322
const loose: Record<string, (event: any) => void> = { onClik: handlers.onClick };
const found = loose["onClick"];
console.log(found === undefined ? "handler missing" : "handler found");
```

The output is `10`, `A`, then `handler missing`. The loose table accepts the typo and its expected lookup is absent. The computed table checks names and payloads at the known calls. This example intentionally derives onKeydown from keydown; a different spelling convention such as onKeyDown needs a different source spelling or naming policy.

The type does not generate functions, validate an incoming event or correlate an arbitrary runtime string with an unknown payload. Dynamic dispatch needs real checks and a design that preserves that relationship. [Template composition](<../3. Transformations in Practice/3.2. Template literal composition Capitalize handlers and routes.md>) owns the broader intrinsic and route-key applications; [custom narrowing](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.3. Custom narrowers predicates asserts and type guards on unions.md>) owns runtime predicate guarantees.

### 4) **Common confusion**

A key constraint rejects an inadmissible type argument; a filter can accept a source and omit some of its keys. Intersections with string often serve that filter role, including inside a template literal. They do not produce runtime errors for removed keys. A remapped type also does not remove fields from an existing object assigned through its view.

Generated names are neither guaranteed unique nor an implementation of a naming convention beyond the written transformation. The collision probe permits number or string under one ID key, and Capitalize changes the first character without inventing word boundaries. Check those assumptions before adopting a mechanically derived public API.

### 5) **Performance note**

Key computations and intrinsic types erase. Explicit getter closures, object construction, JSON serialization and handler calls remain. No fixed key-count cliff, cache ratio, one-pass speed advantage or per-property compiler saving was measured. Combining literal unions can grow the set of possible keys, but actual checking cost needs [diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>), not a guessed instantiation formula.

### 6) **Mentor note**

Ask whether each operation rejects a caller, removes a static key, renames a contract or constructs a runtime object. Require the learner to predict entity's runtime key count through view, then explain why the explicit projection differs. For the collision, ask what information would be needed to reconstruct the original id versus ID source choice.

For practice, add scroll: { y: number } to Events before changing handlers. Observe the missing onScroll error, then supply a handler that formats y and call it with { y: 20 }. Existing calls must still print 10 and A, and the new call must print 20. A click payload passed to onScroll must be rejected. This tests both key propagation and payload preservation.
