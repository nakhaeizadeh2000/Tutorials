## 1.2. `readonly` and optional modifiers — with plus and minus

### 1) **Adding and removing `readonly`** (freezing output vs unfreezing input)

**Definition** — prefix operators inside a mapped type control `readonly` explicitly: `{ +readonly [K in keyof T]: T[K] }` adds it (the stdlib `Readonly`), `{ -readonly [K in keyof T]: T[K] }` strips it. Bare `readonly` (no sign) means `+readonly`. The operator overrides homomorphic memory: `-readonly` unfreezes even sources declared `readonly`.

**What problem it solves / history** — homomorphic memory alone could only *preserve* `readonly` — builders needed the opposite (mutable drafts from frozen configs) and had to rebuild interfaces by hand or cast away freezing (`as Mutable<T>` via `any`). Explicit `-readonly` (TS 2.8) made unfreezing a checked one-liner: the draft tracks the frozen source key-for-key instead of drifting from a copied interface.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), freeze at publication boundaries (`Readonly<State>` for store snapshots, `Readonly<Config>` for shared defaults) and unfreeze inside builders (`Mutable<Draft>` for staged construction, then freeze on `build()`). Never cast away `readonly` with `as` — `-readonly` documents the unfreezing where the cast hides it.

**Runnable example** — freeze out, unfreeze in (good vs bad, `tsc --strict`):

```typescript
// good — publish frozen, build mutable, freeze on exit
interface Config { host: string; port: number; }
type Mutable<T> = { -readonly [K in keyof T]: T[K] };
const published: Readonly<Config> = { host: "h", port: 80 };
console.log(published.host.toUpperCase()); // H
// published.port = 81; // error TS2542 — frozen at the boundary
const draft: Mutable<Readonly<Config>> = { host: "h", port: 81 }; // unfrozen for staging
draft.port = 82;
console.log(draft.port.toFixed(0)); // 82

// bad — casting away readonly hides the freeze from reviewers
function tweakBad(c: Readonly<Config>): void {
  (c as Mutable<Config>).port = 81; // compiles — the boundary lie lives in one cast
}
// fix — Mutable<T>: the unfreezing is a named type in the signature, not a hidden cast
function tweakGood(c: Mutable<Config>): void { c.port = 81; }
tweakGood({ host: "h", port: 80 });
console.log("tweaked");
```

**Common confusion** — "`-readonly` mutates the source" — mapped output is a *new* type; the source stays frozen — `-readonly` describes the output, never the input. "`Readonly` freezes deeply" — shallow only: nested objects stay mutable (deep freezing needs recursion, see [3.1. Deep transforms](<../3. Transformations in Practice/3.1. Deep transforms DeepPartial DeepReadonly and the budget.md>)). "`readonly` affects assignability structurally" — `Readonly<User>` still accepts a mutable `User` (fewer capabilities required); the reverse errors only on write attempts, not assignment.

**Performance note** — modifier operators add no check cost beyond the underlying O(keys) mapping — one flag per property, cached with the instantiation. No emit delta — `readonly` erases fully.

**Mentor note** — pair the operators visually (`+readonly` in, `-readonly` out) around a builder's `build(): Readonly<Draft>` signature — students see the freeze as a lifecycle (mutable inside, frozen outside) rather than a constraint. Review gate: `as Mutable` / `as { -readonly }`-shaped casts must become named `Mutable<T>` parameters.

### 2) **Adding and removing `?`** (`Partial` adds, `Required` removes)

**Definition** — `{ [K in keyof T]?: T[K] }` adds optionality (stdlib `Partial`), `{ [K in keyof T]-?: T[K] }` strips it (stdlib `Required`). Like `readonly`, bare `?` means `+?`, and `-?` overrides memory — an already-optional `port?` becomes required under `Required`. Value types are untouched; only presence changes.

**What problem it solves / history** — update/patch shapes (`PATCH /users` accepting any subset) previously needed parallel optional-mirrored interfaces that rotted on every source change (the `UserPatch` rot from 1.1). `Partial` computes the patch shape from the source; `Required` inverts it for validated output (post-schema-parse objects where every field is proven present).

**Modern guidance** — as of TypeScript 5.9 era, type PATCH bodies and draft states as `Partial<Entity>`, validated/complete values as `Required<Entity>` (or the narrower proven-present shape). Keep `null` out of the decision: `Partial` controls *presence* (`undefined`/missing), not *nullability* (`| null` is a separate union — see [1.3. null and undefined](<../../../03 Basic Types and Annotations/sections/1. The Primitive Family/1.3. null and undefined strictNullChecks and optionality.md>)).

**Runnable example** — patch in, complete out (good vs bad, `tsc --strict`):

```typescript
// good — PATCH accepts any subset, validated output requires everything
interface Account { id: string; email: string; }
function applyPatch(id: string, patch: Partial<Account>): Account {
  const base: Account = { id, email: "a@x.io" };
  return { ...base, ...patch };
}
console.log(applyPatch("u1", { email: "b@x.io" }).email); // b@x.io
type Complete = Required<Partial<Account>>; // back to all-required
const c: Complete = { id: "u1", email: "c@x.io" };
console.log(c.id.toUpperCase()); // U1

// bad — mirrored patch interface drifts from the source
interface AccountPatch { id?: string; email?: string; } // correct today, stale tomorrow
// fix — Partial<Account>: presence computed from the source, never mirrored
```

**Common confusion** — "`Partial` makes values nullable" — values keep their types (`email?: string`, not `email?: string | null`) — presence vs nullability differ (see [1.3. null and undefined](<../../../03 Basic Types and Annotations/sections/1. The Primitive Family/1.3. null and undefined strictNullChecks and optionality.md>)). "`Required` validates at runtime" — purely static: `Required<Partial<Account>>` *claims* completeness the code must still ensure (spread over defaults, schema parse). "`-?` on methods breaks `this`" — methods map as function-valued properties; stripping `?` from an optional method keeps its signature — `this` handling unchanged.

**Performance note** — same O(keys) profile as any homomorphic mapper; `Partial` of a 200-key entity referenced 50 times caches once — name the instantiation (`type Patch = Partial<Account>`) rather than inlining it per signature.

**Mentor note** — contrast `Partial` (any subset — PATCH) with `Pick` (chosen subset — projections) in one exercise: same source, different intent — subset-by-caller vs subset-by-design. Review rule: mirrored `XxxPatch`/`XxxUpdate` interfaces are defects; the mapped derivation is the fix.

### 3) **Homomorphic modifier memory** (only `keyof T` mappers inherit silently)

**Definition** — modifier inheritance fires *only* for the syntactic form `{ [K in keyof T] … }`: the output starts with the source's exact `?`/`readonly` set, then `+`/`-` operators adjust. Any other `in` clause (`K in string`, `K in Union`, `K in keyof T & string`) starts modifier-clean — operators still apply, but there is nothing to inherit.

**What problem it solves / history** — `Pick<T, K>` (TS 2.1) preserves modifiers because it maps `K in K` over a *subset*… yet stays homomorphic only when written against `keyof T` — the subtlety bit library authors who filtered keys (`Exclude<keyof T, "secret">`) and lost `readonly` silently. The rule is syntactic, not semantic: write the `in` clause as `keyof T` (possibly intersected) when memory matters, and verify with a hover when it must.

**Modern guidance** — as of TypeScript 5.9 era, default to `keyof T` iteration for variant mappers (memory almost always wanted); use explicit key sets for generative mappers (memory meaningless). When filtering keys, keep the `keyof T` form with an `as` exclusion (`[K in keyof T as Exclude<K, "secret">]` — homomorphic *and* filtered) instead of pre-resolving the union outside.

**Runnable example** — memory needs the `keyof T` spelling (good vs bad, `tsc --strict`):

```typescript
// good — homomorphic + filtered: memory kept, secret dropped
interface Record_ { name: string; readonly id: string; secret: string; }
type Public<T> = { [K in keyof T as Exclude<K, "secret">]: T[K] };
const p: Public<Record_> = { name: "a", id: "1" };
console.log(p.name.toUpperCase(), p.id); // A 1
// p.id = "2"; // error TS2542 — readonly remembered through the filter

// bad — pre-resolved union loses the readonly memory
type Keys = Exclude<keyof Record_, "secret">; // "name" | "id" — plain union now
type PublicBad = { [K in Keys]: Record_[K] }; // non-homomorphic: modifiers forgotten
const pb: PublicBad = { name: "a", id: "1" };
pb.id = "2"; // compiles — readonly silently lost (no error to catch it)
// fix — Public<T>: filter INSIDE with `as`, keep `keyof T` outside
```

**Common confusion** — "`as` filtering changes homomorphism" — `as` remaps keys *within* a `keyof T` mapper — memory stays (the `in` clause, not the `as` clause, decides). "`keyof T & string` breaks memory" — intersections on `keyof T` preserve homomorphism (still syntactically a `keyof T` iteration) — only fully-resolved unions lose it. "memory applies to value types" — modifiers only; value transforms (`T[K] | null`) apply identically in both forms.

**Performance note** — `as`-filtered homomorphic mappers cost the same O(keys) as plain ones (excluded keys still visit the filter — one conditional per key, cached). Pre-resolving unions outside saves nothing and loses memory — never "optimize" by hoisting the key computation out.

**Mentor note** — the `pb.id = "2"` silent write is the demo: two mappers, same keys, different freezability — ask which preserves the source contract before compiling. Rule of thumb: filter with `as` inside, never with `Exclude` outside, when the mapper must remember.
