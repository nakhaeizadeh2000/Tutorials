## 1.2. Readonly and optional modifiers — with plus and minus

Mapped modifiers control whether a property can be written through a type view and whether it may be omitted. A plus sign adds a modifier, and a minus sign removes it. Omitting the sign means plus. These operations change static contracts; they do not create values, validate fields, copy objects or change runtime property descriptors.

Use TypeScript 7.0.2 and Node.js 20.20.2. The first three programs use `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then `node dist/FILE.js`. The final program deliberately omits --exactOptionalPropertyTypes. Save fences as named below. Check commented negatives independently using the appropriate flags with --noEmit instead of --outDir dist.

### 1) **Add and remove readonly without pretending to freeze or thaw**

`{ +readonly [K in keyof T]: T[K] }` adds readonly, while `{ -readonly [K in keyof T]: T[K] }` removes it. The shorter readonly form adds it too. A readonly property prevents an assignment through that view. Ordinary object properties can still be shared with a mutable alias; merely publishing the view is not a snapshot.

Save as views.ts.

```typescript
interface Config { host: string; port: number; }
type Published<T> = { +readonly [K in keyof T]: T[K] };
type Mutable<T> = { -readonly [K in keyof T]: T[K] };
const source: Config = { host: "h", port: 80 };
const published: Published<Config> = source;
// published.port = 81; // TS2540
const alias: Mutable<Published<Config>> = published; // Accepted for these ordinary object properties.
alias.port = 82;
console.log(source.port, published.port, alias === published, Object.isFrozen(published));

function changePort(config: Mutable<Config>): void { config.port = 83; }
changePort(published); // Naming a mutable parameter does not require a copy.
console.log(published.port);
const copy: Mutable<Published<Config>> = { ...published };
copy.port = 84;
console.log(published.port, copy.port, copy === published);

const frozen: Readonly<Config> = Object.freeze({ host: "h", port: 80 });
const writableView: Mutable<typeof frozen> = frozen;
try { writableView.port = 81; }
catch (error) { console.log(error instanceof TypeError ? "frozen write: TypeError" : "unexpected error"); }
```

The output is `82 82 true false`, `83`, `83 84 false`, then `frozen write: TypeError`. Removing readonly from a view of a frozen object cannot make its property writable at runtime. Conversely, adding readonly to the mutable source did not freeze it. Here the actual spread creates an independent top-level copy; nested object references would still be shared.

This ordinary object-property compatibility does not imply that a readonly array is assignable to a mutable array. Array methods and capabilities have their own contract. [Readonly foundations](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) owns the shared-view distinction, and [array readonly](<../../../10 Arrays Tuples and Collections/README.md>) owns collection choices. A mutable parameter name alone is not an ownership guarantee.

### 2) **Add and remove optionality with explicit undefined semantics**

`{ [K in keyof T]+?: T[K] }` adds optionality, matching Partial's usual spelling with ?. The -? form makes the mapped properties required, as Required does. It does not prove they were supplied at runtime. Nor is it always correct to say that only presence changes: removing an optional marker can also remove undefined from the value type.

Save as presence.ts with exactOptionalPropertyTypes enabled.

```typescript
type Optional<T> = { [K in keyof T]+?: T[K] };
type Complete<T> = { [K in keyof T]-?: T[K] };
interface Options { port?: number; label?: string | undefined; note?: string | null; }
const optional: Optional<{ port: number }> = {};
// optional.port = undefined; // TS2412: exact optional write is not an absent property
const complete: Complete<Options> = { port: 5432, label: undefined, note: null };
// const missing: Complete<Options> = { port: 5432, note: null }; // TS2741
// const invalid: Complete<Options> = { port: undefined, label: "x", note: null }; // TS2322
console.log(optional.port, complete.port, complete.label === undefined, complete.note);
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Port = Expect<Equal<Complete<Options>["port"], number>>;
type Label = Expect<Equal<Complete<Options>["label"], string | undefined>>;
```

The output is `undefined 5432 true null`. An absent optional port reads as possibly undefined; making it required gives number here. With exact optional checking on, label's explicitly written undefined remains a legitimate required value. Null is independently allowed by note's union.

For a controlled flag comparison, turn exactOptionalPropertyTypes off and compile the same file: label: undefined and the Label equality probe fail. In this mode the homomorphic removal also strips undefined from that optional property's value. Replace label with a string and expect string in the probe to compile the variant. The [exact optional option](https://www.typescriptlang.org/tsconfig/exactOptionalPropertyTypes.html) distinguishes omitted properties from present undefined writes; the [historical modifier notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-8.html#improved-control-over-mapped-type-modifiers) explain why -? was already more than a textual deletion before that option existed.

### 3) **Verify modifier inheritance for the actual mapping form**

The familiar generic keyof T mapping preserves modifiers unless overridden. A Pick-style constrained subset can preserve them too, including when its key choice is computed with Exclude. A separately resolved key union or a different key intersection need not preserve them. These distinctions concern the whole declaration, not whether the words keyof appear somewhere in it.

Save as subsets.ts.

```typescript
interface Model { readonly id: string; port?: number; secret: string; }
type Public<T> = { [K in keyof T as Exclude<K, "secret">]: T[K] };
type Selected<T> = Pick<T, Exclude<keyof T, "secret">>;
const filtered: Public<Model> = { id: "a" };
const picked: Selected<Model> = { id: "b" };
// filtered.id = "x"; // TS2540
// picked.id = "x"; // TS2540

type Keys = Exclude<keyof Model, "secret">;
type Resolved = { [K in Keys]: Model[K] };
const resolved: Resolved = { id: "c", port: undefined };
resolved.id = "changed";
// const absent: Resolved = { id: "c" }; // TS2741: port is required, with undefined in its value type

type StringKeys<T> = { [K in keyof T & string]: T[K] };
const intersected: StringKeys<Model> = { id: "d", port: undefined, secret: "s" };
intersected.id = "also changed";
// const missing: StringKeys<Model> = { id: "d", secret: "s" }; // TS2741
console.log(filtered.id, picked.id, resolved.id, intersected.id);
```

The output is `a b changed also changed`. Both Public and Selected omit port and reject id writes. Resolved requires a port property but permits its value to be undefined; that is distinct from an optional port. The shown generic keyof T & string form also loses those modifiers. Do not generalize that an intersection preserves modifier behavior simply because it contains keyof T. [Mapping foundations](<./1.1. Mapped type fundamentals homomorphic mapping over keys.md>) separates modifier preservation from other homomorphic features; [key remapping](<./1.3. keyof constrained mapping and template literal keys.md>) covers filtering and renaming in depth.

### 4) **Do not confuse a patch contract with a complete result**

Under non-exact optional checking, a present undefined field can satisfy Partial<Account>. Spreading it after a complete base overwrites the base's value. The compiler can accept the resulting Account annotation while the runtime field is undefined. The fix must establish the intended update policy, rather than merely naming the result Required.

Save as loose-patch.ts and deliberately compile with `tsc --strict --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist loose-patch.ts` (exactOptionalPropertyTypes off).

```typescript
interface Account { id: string; email: string; }
const base: Account = { id: "u1", email: "a@example.test" };
const patch: Partial<Account> = { email: undefined }; // Rejected when exactOptionalPropertyTypes is on.
function mergeUnchecked(account: Account, update: Partial<Account>): Account {
  return { ...account, ...update };
}
const broken = mergeUnchecked(base, patch);
console.log(typeof broken.email);
try { console.log(broken.email.toLowerCase()); }
catch (error) { console.log(error instanceof TypeError ? "overwritten email: TypeError" : "unexpected error"); }
function applyEmail(account: Account, update: Partial<Pick<Account, "email">>): Account {
  // This policy treats absent or undefined email as no change and keeps the existing id.
  return typeof update.email === "string" ? { ...account, email: update.email } : { ...account };
}
console.log(applyEmail(base, patch).email, applyEmail(base, { email: "b@example.test" }).email);
```

The output is `undefined`, `overwritten email: TypeError`, then `a@example.test b@example.test`. Enabling exact optional checking rejects this particular present-undefined patch; runtime checks remain necessary for unverified input. This example's repair intentionally supports only email updates and treats undefined as no change. Other APIs may need explicit rejection, deletion or a nullable field with different semantics. Partial by itself defines none of those policies.

### 5) **Common confusion**

Readonly is a static view, and removing it is a static operation. Neither guarantees ownership or changes an actual frozen object. Optional permits omission; a required property whose value includes undefined must still exist. The exact optional mode affects which writes and required-value contracts are admitted, so show the flag when discussing undefined.

Modifier inheritance is also not reserved for a single spelling. The constrained Pick in this lesson preserves the source properties despite an externally computed subset. The resolved-key and intersection examples demonstrate different outcomes that need direct verification.

### 6) **Performance note**

Mapped modifiers erase, while copying, freezing and patch validation remain actual runtime operations. Copies have work proportional to the actual properties copied, with no deep copy implied. No universal per-key checking count, cache reuse benefit or equality of filtered/unfiltered mapping cost was measured. Use [compiler diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) for a concrete check-time problem.

### 7) **Mentor note**

Ask which operation made copy independent and which operation made frozen reject a write. Then ask why complete requires label even though its value can be undefined in exact mode. These questions distinguish runtime ownership, property presence and field values.

For practice, turn the copying step into draftOf(config: Readonly<Config>): Mutable<Config> that returns a fresh top-level object. Modifying its port must leave the original unchanged, even if the input was Object.freeze'd. Verify unequal identity and unchanged input, and explain why adding a nested object would require a separate copy policy. A function that simply returns config fails the exercise despite compiling.
