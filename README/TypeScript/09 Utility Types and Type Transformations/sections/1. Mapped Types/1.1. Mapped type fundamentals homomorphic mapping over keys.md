## 1.1. Mapped type fundamentals — homomorphic mapping over keys

### 1) **What `{ [K in keyof T]: V }` computes** (rebuilds `T` key by key)

**Definition** — a mapped type iterates the keys of `T` and rebuilds the object with transformed values: `type Nullable<T> = { [K in keyof T]: T[K] | null }` takes `{ a: string }` and produces `{ a: string | null }` — same keys, new value types. The `in` clause names the loop variable (`K`), `keyof T` supplies the key set, and the right side computes each property from `K`.

**What problem it solves / history** — before mapped types (TS 2.1, 2016), every shape variant needed a hand-written interface — `User`, `PartialUser`, `ReadonlyUser`, `NullableUser` multiplied per entity, and adding a field to `User` meant editing four declarations. Mapped types made variants *computed*: one source interface plus one-line transforms, so the field is added once and every variant follows.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), derive variants instead of declaring them — `Partial<Config>` for updates, `Readonly<State>` for published snapshots, `Record<Key, Handler>` for dispatch tables. Keep the source interface canonical and every variant a mapped computation over it. All mapped syntax erases (see [2.1. Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)).

**Runnable example** — variants computed, not declared (good vs bad, `tsc --strict`):

```typescript
// good — one source, every variant derived
interface User { id: string; age: number; }
type Nullable<T> = { [K in keyof T]: T[K] | null };
const n: Nullable<User> = { id: null, age: null };
console.log(n.id ?? "no-id", n.age ?? 0); // no-id 0

// good — stdlib Partial is the same shape: optionality mapped over keys
const patch: Partial<User> = { age: 36 }; // id omitted legally
console.log(patch.age?.toFixed(0) ?? "missing"); // 36

// bad — hand-written variant interfaces rot when the source gains a field
interface UserPatch { id?: string; age?: number; } // mirrors User today...
// interface User { id: string; age: number; email: string; } // source grows; patch silently lacks email
// fix — Partial<User>: the variant tracks the source automatically
const patch2: Partial<User> = { age: 36 };
console.log(Object.keys(patch2).length); // 1 — and stays correct when User grows
```

**Common confusion** — "mapped types run at runtime" — purely checker-side; `Nullable<User>` emits nothing (see [2.1. Type space vs value space](<../../../02 The Type System Core/sections/2. The type vs value separation/2.1. Type space vs value space two parallel universes.md>)). "`keyof T` includes methods" — yes: methods map too (their function types transform like any value — usually passed through unchanged). "mapped output preserves the source's identity" — output is a *new* type; assignability follows structure (see [1.1. Structural assignability](<../../../02 The Type System Core/sections/1. Structural typing/1.1. Structural assignability shape not name.md>)), not naming.

**Performance note** — homomorphic mapping costs O(keys) instantiations per reference — a 50-key interface mapped 10 times creates ~500 cached property checks (fast). Cost concentrates in *nested* mapping (mapped-over-mapped per property) — flatten to one mapper where possible; measure with `tsc --extendedDiagnostics`.

**Mentor note** — teach `in` as "for..of for keys" — draw the loop unrolled (`{ id: T["id"] | null; age: T["age"] | null }`) beside the one-liner so the computation is visible before it becomes idiomatic. Exercise: add `email` to `User` and watch `Nullable<User>` accept it while `UserPatch` silently ignores it — the rot made visible. Review gate: hand-mirrored variant interfaces must be replaced by mapped derivations.

### 2) **Homomorphic vs non-homomorphic** (modifier memory vs fresh shapes)

**Definition** — a *homomorphic* mapper iterates `keyof T` directly (`{ [K in keyof T]: … }`) and silently carries the source's `?`/`readonly` modifiers into the output; a *non-homomorphic* mapper iterates anything else (`keyof any`, a union, `string`) and starts with clean modifiers. `Partial<T> = { [K in keyof T]?: … }` is homomorphic (remembers, then adds `?`); `Record<string, V>` is not (fresh shape, no memory).

**What problem it solves / history** — early mapped-type users were surprised both ways: `Readonly<User>` kept `age?` optional (memory working as designed, but unexpected), while `Record<"a"|"b", number>` dropped modifiers callers assumed would transfer (no source to remember — there is no `T`). Naming the split turns both surprises into predictions: modifier behavior follows the `in` clause, not the mapper's name.

**Modern guidance** — as of TypeScript 5.9 era, map over `keyof T` when the output must track the source's shape evolution (variants: `Partial`, `Readonly`, `Nullable`); map over explicit key sets when building *new* shapes (dispatch tables, handler maps, form state). When memory surprises, say so explicitly with `+`/`-` operators (next leaf) instead of restructuring the `in` clause.

**Runnable example** — memory follows `keyof T` (good vs bad, `tsc --strict`):

```typescript
// good — homomorphic: optional stays optional through the mapper
interface Cfg { host: string; port?: number; }
type Frozen<T> = { readonly [K in keyof T]: T[K] };
const f: Frozen<Cfg> = { host: "h" }; // port still omittable — memory preserved
console.log(f.host.toUpperCase()); // H
// f.host = "x"; // error TS2542 — readonly added, optionality remembered

// good — non-homomorphic: fresh shape, no memory, explicit modifiers rule
type Scores = Record<"ada" | "lin", number>;
const s: Scores = { ada: 10, lin: 9 };
console.log(s.ada.toFixed(0)); // 10 — every key required, nothing remembered

// bad — expecting memory where no source exists
type MaybeScores = { [K in "ada" | "lin"]?: number }; // must ADD ? explicitly
const m: MaybeScores = {}; // ok — ? written, not remembered (no T to remember from)
// const m2: Scores = {}; // error TS2741 — Record has no memory; missing keys error
// fix — homomorphic for variants (memory wanted), explicit modifiers for fresh shapes
```

**Common confusion** — "`Partial` *adds* optionality" — `Partial` adds `?` *on top of* remembered modifiers; an already-optional `port?` stays optional for two reasons (memory + operator) — harmless duplication, not a conflict. "`Record<K, V>` remembers when `K = keyof T`" — `Record<keyof User, string>` is still non-homomorphic (iterates a *resolved union*, not `keyof T` syntactically) — memory requires the literal `keyof T` form. "homomorphic mappers are always preferable" — fresh shapes need clean modifiers; forcing `keyof T` iteration to gain memory couples the new shape to an unrelated source.

**Performance note** — homomorphic mappers check faster on repeated use: the checker caches per-`(mapper, T)` and reuses modifier computation; non-homomorphic `Record<Union, V>` re-resolves the union per reference — name large unions once (`type K = "a" | …`) instead of inlining them in 50 `Record`s.

**Mentor note** — demonstrate memory by hovering `Frozen<Cfg>` (`{ readonly host: string; readonly port?: number }`) — the `?` surviving next to `readonly` makes the concept visible in one tooltip. Exercise: predict `Partial` of `{ a: string; b?: number }` before hovering — then explain *both* reasons `b` is optional. Review question for every mapper: "which `in` clause, and is memory wanted here?"

### 3) **Reading mapped hover types** (the checker shows the result, not the loop)

**Definition** — hovering `Partial<User>` shows `{ id?: string; age?: number }` — the *computed result*, never the `{ [K in keyof T]?: T[K] }` recipe. Verification habit: hover the alias reference (not the declaration) and read the expanded properties; when the result surprises, unroll one level manually (`T["id"]`) to find which branch of the computation diverged.

**What problem it solves / history** — mapped-type bug reports were unactionable ("`DeepPartial` gives something weird") because authors read the *recipe* instead of the *result* — the error was always in one property's computation, visible only in the expanded hover. Result-first reading (hover the use, expand, compare per key) localizes every mapped bug to a single `T[K]` evaluation.

**Modern guidance** — as of TypeScript 5.9 era, verify transforms at the use site: hover `patch: Partial<User>`, confirm each key's optionality and value type, then write the confirming assignment (`const check: Partial<User> = { age: 1 }`). For large results, hover a *narrow* instantiation first (`Partial<Pick<User, "age">>`) — small output isolates the faulty key faster than scrolling 100 expanded properties.

**Runnable example** — result-first verification (good vs bad, `tsc --strict`):

```typescript
interface Product { sku: string; price: number; tag?: string; }
type PriceOnly<T> = { [K in keyof T as K extends "price" ? K : never]: T[K] };
// hover PriceOnly<Product> → { price: number } — the result, not the loop
const po: PriceOnly<Product> = { price: 9 };
console.log(po.price.toFixed(2)); // 9.00

// good — per-key unrolling finds the faulty branch
type Check = Product["tag"]; // string | undefined — explains why mapped tag stays optional-ish
console.log("tag-value-type-checked");

// bad — reading the recipe and guessing the result
// "PriceOnly keeps tag because tag was optional" — wrong: the `as` filter dropped it;
// fix — hover the REFERENCE (PriceOnly<Product>), not the declaration, before asserting
```

**Common confusion** — "hover shows the mapper, so the transform didn't apply" — the IDE sometimes *collapses* to the alias name; expand (`Ctrl+hover` / explicit annotation) to see the result — the transform applied, the display abbreviated. "`T[K]` in the recipe means indexed access happens once" — it evaluates *per key* during mapping — a conditional inside (`T[K] extends …`) branches independently per property. "expanded hovers are the stored type" — displays abbreviate deep results (`…`); the full structure still checks — abbreviate display, not understanding.

**Performance note** — hover expansion itself costs IDE time on huge mapped results (1000-key `DeepPartial<Schema>` tooltips stall) — verify with small instantiations during development; the check cost is identical, the *rendering* cost is what stalls.

**Mentor note** — make "hover the use, not the declaration" a team mantra — it generalizes beyond mapped types (generics, conditionals, `infer` all display results at uses). Exercise: show only the recipe, ask for the result shape, then hover to confirm — builds the unrolling reflex that debugs every transform.
