## 1.1. Mapped type fundamentals — homomorphic mapping over keys

A mapped type derives a property contract from a set of keys. In `{ [K in keyof T]: T[K] | null }`, K names each selected key and T[K] supplies that property's type. The result permits null at each mapped property. No JavaScript object is created or changed by that declaration.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence under its filename. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`; run `node dist/FILE.js`. Activate commented negatives separately and check with the same flags and --noEmit instead of --outDir dist.

### 1) **Derive property types and distinguish actual construction**

For a User containing id: string and age: number, Nullable<User> requires id: string | null and age: number | null. The keys stay the same while the value contracts change. Partial<User> is a different transformation that permits omission. Neither transform validates incoming data or implements an update operation.

Save as data.ts.

```typescript
interface User { id: string; age: number; }
type Nullable<T> = { [K in keyof T]: T[K] | null };
type Copy<T> = { [K in keyof T]: T[K] };
const nullable: Nullable<User> = { id: null, age: null };
const patch: Partial<User> = { age: 36 };
console.log(nullable.id ?? "no-id", nullable.age ?? 0, patch.age?.toFixed(0));
// const missing: Nullable<User> = { id: null }; // TS2741: nullable is not optional
// const wrong: Nullable<User> = { id: 42, age: null }; // TS2322

const original: User = { id: "u1", age: 36 };
const same: Copy<User> = original;
same.age = 37;
console.log(same === original, original.age);
const separate: Copy<User> = { ...original };
separate.age = 38;
console.log(original.age, separate.age, separate === original);
interface ManualPatch { id?: string; age?: number; }
```

The output is `no-id 0 36`, `true 37`, then `37 38 false`. Assigning a mapped view retains the original reference. The spread expression creates the separate object, just as it would without a type annotation. This is a shallow copy; nested references would still need their own policy.

Derivation is useful when a variant should follow source changes. An intentionally different public model need not mirror every new internal field; use a deliberate selection for that boundary. The [object query owner](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.3. Type queries on objects keyof indexed access and typeof capture.md>) explains keyof and indexed access, including why a static key set is not an enumeration of all runtime properties. The [primary mapped-type guide](https://www.typescriptlang.org/docs/handbook/2/mapped-types.html) introduces the mapping syntax.

### 2) **Modifier preservation differs from fresh key generation**

The generic shape `{ [K in keyof T]: ... }` is commonly called a homomorphic mapped type: it derives a variant of T while preserving important source structure. With no modifier override, its properties retain readonly and optional markers. A fresh Record<Keys, Value> has no source property modifiers to copy, even if Keys was obtained with keyof.

Do not turn this distinction into the rule that only the literal in keyof T spelling can preserve modifiers. A constrained Pick-style mapping over a separate key parameter also preserves them. The installed standard library uses that form for Pick. Modifier preservation is a behavior to verify; the homomorphic label describes more than that single behavior.

Save as modifiers.ts.

```typescript
interface Config { readonly id: string; port?: number; }
type Mirror<T> = { [K in keyof T]: T[K] };
type Select<T, Keys extends keyof T> = { [K in Keys]: T[K] };
const mirrored: Mirror<Config> = { id: "a" };
const selected: Select<Config, "id" | "port"> = { id: "b" };
// mirrored.id = "changed"; // TS2540
// selected.id = "changed"; // TS2540: constrained subset still preserves readonly
// type BadKey = Select<Config, "absent">; // TS2344

type Fresh = Record<keyof Config, string>;
const fresh: Fresh = { id: "c", port: "5432" };
fresh.id = "changed"; // Fresh properties are writable and required.
// const missing: Fresh = { id: "c" }; // TS2741
console.log(mirrored.id, selected.id, fresh.id, selected.port === undefined);
```

The output is `a b changed true`. Both mapped views can omit port and reject an id assignment. Fresh requires both keys but permits replacing id. This is about contracts, not runtime freezing; none of these declarations calls Object.freeze. [Modifier operators](<./1.2. readonly and optional modifiers with plus and minus.md>) owns explicit additions/removals and exact optional-property writes.

### 3) **Check structure and values rather than relying on a tooltip**

Homomorphic mapping can preserve array and tuple structure as well as object modifiers. A mapping over an array transforms element types rather than boxing its length and methods. For tuples it retains ordered positions, optional positions and readonly status. A generic mapping over a union can produce the union of mapped alternatives. These facts make a literal key-loop analogy useful for ordinary objects but incomplete for every input type.

Save as structure.ts. The [primary tuple/array notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-1.html#mapped-types-on-tuples-and-arrays) describe the specialized array and tuple behavior.

```typescript
type Box<T> = { [K in keyof T]: { value: T[K] } };
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Tuple = Expect<Equal<Box<readonly [string, number?]>, readonly [{ value: string }, { value: number | undefined }?]>>;
type ArrayResult = Expect<Equal<Box<number[]>, { value: number }[]>>;
type Choice = { a: string } | { b: number };
type Alternatives = Expect<Equal<Box<Choice>, { a: { value: string } } | { b: { value: number } }>>;
type Primitive = Expect<Equal<Box<"x">, "x">>;
const tuple: Box<readonly [string, number?]> = [{ value: "hi" }];
const boxes: Box<number[]> = [{ value: 1 }];
boxes.push({ value: 2 });
console.log(tuple[0].value.toUpperCase(), tuple[1]?.value ?? "absent", boxes.length);
// tuple.push({ value: "x" }); // TS2339
// const wrong: Box<[number]> = [{ value: "x" }]; // TS2322
// const boxedLength: Box<number[]>["length"] = { value: 2 }; // TS2322: length remains number
function describe(value: Box<Choice>): string {
  return "a" in value ? value.a.value.toUpperCase() : value.b.value.toFixed(0);
}
console.log(describe({ a: { value: "yes" } }), describe({ b: { value: 7 } }));
```

The output is `HI absent 2`, then `YES 7`. Four live probes check exact claimed results, including the unchanged primitive input for this homomorphic form. The actual arrays/objects are explicitly constructed. No implementation of a generic runtime boxing operation has been inferred from these declarations.

An editor may display an alias, an expanded type or an abbreviation. Display choices are useful for exploration, but are not the semantic result itself. Construct representative values, read a selected property, activate a rejected write and use a live probe for an exact relationship. Remapping/filtering can change these behaviors; [key remapping](<./1.3. keyof constrained mapping and template literal keys.md>) owns that next step.

### 4) **Common confusion**

Nullable values and optional properties are separate: the missing age example still fails. Readonly views and runtime immutability are separate too. A constrained subset can preserve modifiers even though its declaration differs from the familiar full keyof T mapper. Conversely, Record<keyof Config, string> uses Config's keys without inheriting Config's modifiers or value types.

A mapper's value expression also applies to function-valued properties. Adding null to every property would make a method's value nullable; it does not automatically pass methods through unchanged. Choose a different transform policy when callable members need special treatment. Do not infer that policy from the mapper's friendly name.

### 5) **Performance note**

Mapped types and probes erase. Object literals, spread copies, mutation and array operations remain. There is no runtime loop caused by the mapped declaration, and no automatic copying or freezing cost. No per-key instantiation count, universal homomorphic-versus-Record speed ranking or tooltip latency was measured. Investigate an actual checking problem through [diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) rather than estimating it from a key count alone.

### 6) **Mentor note**

Ask the learner to unroll Nullable<User> into its two explicit properties, then identify the JavaScript expression that creates separate. Next ask why selected can omit port while fresh cannot. An answer should account for source modifiers and the distinct key/value relationships, rather than treating every mapped type as a runtime loop.

For practice, add required email: string to User. First observe the missing-property diagnostics on values that must represent the expanded source. Then provide email on original and nullable, and construct a Partial<User> containing only email. Its derived contract accepts that field; ManualPatch does not until edited. Explain when that difference is desirable and when a deliberately limited external patch should keep its own selected fields.
