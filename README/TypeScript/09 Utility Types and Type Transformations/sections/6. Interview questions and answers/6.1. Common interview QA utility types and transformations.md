## 6.1. Common interview QA — utility types and transformations

### 1) **How does `{ [K in keyof T]?: T[K] }` implement `Partial` — and what makes it homomorphic?** (key iteration + modifier memory)

**Definition** — the mapper iterates `keyof T` (`K` visits each key), rebuilds each property with the same value type (`T[K]`), and adds `?` — homomorphic because the `in` clause is syntactically `keyof T`, so the source's existing `?`/`readonly` modifiers carry over silently before the operator applies. One line, three behaviors: iterate, remember, optionalize.

**What problem it solves / history** — interviewers ask this to separate utility-*users* (`Partial` as vocabulary) from utility-*readers* (mapped mechanics: iteration + memory + operators) — readers predict `Partial`'s behavior on `readonly`/optional sources without hovering, and generalize to `Readonly`, `Nullable`, and project-specific mappers on the spot.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), answer in three beats (iterate `keyof T` → remember modifiers → add `?`), then volunteer the memory rule's boundary (only literal `keyof T` inherits; resolved unions don't). Full treatment in [1.1. Mapped fundamentals](<../1. Mapped Types/1.1. Mapped type fundamentals homomorphic mapping over keys.md>) + [1.2. Modifiers](<../1. Mapped Types/1.2. readonly and optional modifiers with plus and minus.md>).

**Runnable example** — memory visible in one hover (`tsc --strict`):

```typescript
interface Cfg { host: string; readonly id: string; port?: number; }
type P = Partial<Cfg>; // { host?: string; readonly id?: string; port?: number }
const p: P = { host: "h" }; // port omittable (memory + operator), id assignable once
console.log(p.host?.toUpperCase() ?? "none"); // H
// p.id = "2"; // error TS2542 — readonly remembered through Partial
```

**Common confusion** — "`Partial` *adds* optionality to everything" — it adds `?` atop *remembered* modifiers; already-optional members stay optional for two reasons (harmless overlap). "homomorphism is about values" — about *modifiers*; value transforms apply identically in both forms.

**Performance note** — homomorphic `Partial` caches per `T` (one instantiation per entity) — referencing `Partial<Cfg>` 30 times computes once; name repeated instantiations.

**Mentor note** — strong answers predict the hover (`readonly id?: string`) before seeing it — probe with "what happens to `readonly id` and `port?`?" when candidates stop at "makes everything optional." Hiring signal: memory-rule volunteers generalize to `as`-filtered mappers unprompted.

**Cross-links** — mapped → [1.1. Mapped fundamentals](<../1. Mapped Types/1.1. Mapped type fundamentals homomorphic mapping over keys.md>); modifiers → [1.2. Modifiers](<../1. Mapped Types/1.2. readonly and optional modifiers with plus and minus.md>).

### 2) **Write `Exclude` from memory — and explain which word makes it distribute.** (naked `T` + `never` sink)

**Definition** — `type Exclude<T, U> = T extends U ? never : T` — the naked `T` (first word after `type Exclude<…>`, standing alone before `extends`) distributes over union members; matches sink to `never`; survivors reunite. Distribution lives in nakedness, filtering in the `never` branch — two facts, one line.

**What problem it solves / history** — the standard generics interview filter: candidates who write the line *and* name nakedness predict `Exclude<"a"|1, string>` (`1`) and diagnose `[T]`-wrapped copies (`"a"|1`, unfiltered) without compiling — syntax recall plus mechanism in one answer.

**Modern guidance** — as of TypeScript 5.9 era, answer with the line, the nakedness pointer ("`T` stands alone — that word distributes"), and the wrapped counterexample (`[T] extends [U]` tests whole). Full treatment in [2.1. Conditional fundamentals](<../2. Conditional Types/2.1. Conditional fundamentals distributive law and never branches.md>) + [2.2. Stdlib](<../2. Conditional Types/2.2. Exclude Extract NonNullable Pick Omit under the hood.md>).

**Runnable example** — line plus fork (`tsc --strict`):

```typescript
type Excl<T, U> = T extends U ? never : T; // naked T distributes
type E = Excl<"a" | 1 | "b", string>; // 1 — strings sunk per member
const e: E = 1;
console.log(e.toFixed(0)); // 1
type Wrapped<T, U> = [T] extends [U] ? never : T; // wrapped: whole-union test
type W = Wrapped<"a" | 1, string>; // "a" | 1 — whole union isn't string, nothing sunk
console.log("wrapped keeps:", "a");
```

**Common confusion** — "the `never` branch distributes" — nakedness distributes; `never` only *sinks* (drops matched members from reunion) — swapped branches (`Extract`) distribute identically. "`Exclude` widens survivors" — survivors keep exact member types — filtering never widens.

**Performance note** — `Exclude` over N-member unions costs N evaluations, cached per instantiation — filter large unions once into named aliases.

**Mentor note** — ask for the wrapped version *after* the correct line — candidates who predict `"a" | 1` (not `1`) understand distribution; candidates guessing need the naked-vs-wrapped lesson. Follow-up: "when is wrapped what you actually want?" (`IsNever`, whole-union predicates).

**Cross-links** — distributive law → [2.1. Conditional fundamentals](<../2. Conditional Types/2.1. Conditional fundamentals distributive law and never branches.md>); stdlib → [2.2. Stdlib](<../2. Conditional Types/2.2. Exclude Extract NonNullable Pick Omit under the hood.md>).

### 3) **How is `Awaited` implemented — and why must it recurse?** (`infer` payload + self-reference with base)

**Definition** — simplified: `type Awaited<T> = T extends null | undefined ? T : T extends { then(f: infer F, ...r: infer _): unknown } ? F extends (v: infer V, ...r: infer _) => unknown ? Awaited<V> : never : T` — match the thenable, extract the callback's value type, recurse on it, stop at non-thenables (pass through) and nullables (preserve). Recursion because nesting is unbounded (`Promise<Promise<…>>` any depth); the base (`: T` / null-preserving branch) because every level must terminate.

**What problem it solves / history** — single-level `Once<T>` unwraps depth 1 and rots at depth 2 (see [2.3. infer pipelines](<../2. Conditional Types/2.3. infer pipelines ReturnType Parameters Awaited.md>) promise 2) — interviewers probe whether candidates see *why* one level fails (input depth varies) and what recursion guarantees (any depth bottoms out at the same base).

**Modern guidance** — as of TypeScript 5.9 era, answer with the three-part shape (match → recurse → base) rather than the exact lib source (which adds native-promise fast paths) — interviewers test the pattern, not the transcription. Full treatment in [2.3. infer pipelines](<../2. Conditional Types/2.3. infer pipelines ReturnType Parameters Awaited.md>).

**Runnable example** — any depth bottoms out (`tsc --strict`):

```typescript
type Once<T> = T extends Promise<infer V> ? V : T; // one level — rots at depth 2
type O = Once<Promise<Promise<string>>>; // Promise<string> — still wrapped
type A = Awaited<Promise<Promise<string>>>; // string — recursed to base
const a: A = "hi";
console.log(a.toUpperCase()); // HI
```

**Common confusion** — "recursion loops on non-promises" — the base (`: T`) terminates: strings/numbers match no branch and pass through — recursion needs a shrinking input *or* a non-matching base; `Awaited` has the base. "`Awaited` executes" — purely static; timing untouched.

**Performance note** — depth equals nesting (1–2 in practice — trivially cached); pathological nesting hits TS2589 like any deep recursion — cap or flatten.

**Mentor note** — "match → recurse → base" as the answer template generalizes to `DeepPartial`, `DeepReadonly`, `DeepArray` — ask candidates to name all three parts before accepting the answer. Transfer test: "now sketch `DeepArray`" — same shape, new wrapper.

**Cross-links** — pipelines → [2.3. infer pipelines](<../2. Conditional Types/2.3. infer pipelines ReturnType Parameters Awaited.md>); recursion budget → [3.2. Recursive generics](<../../../08 Generics Deep Dive/sections/3. Variance and Advanced Generic Patterns/3.2. Recursive generic types and self-referential patterns.md>) (in 08).

### 4) **When does a mapped type *lose* `readonly`/`?` — and how do `-`/`+` control it?** (memory vs operators)

**Definition** — loss happens exactly when iteration is non-homomorphic (resolved union, `string`, `PropertyKey` — nothing to remember) — output starts modifier-clean. The operators then decide explicitly: `-readonly`/`-?` strip, `+readonly`/`+?` (or bare) add, absent operator on homomorphic keeps memory. Loss is a property of the `in` clause; control is a property of the operator.

**What problem it solves / history** — "my `Readonly` lost optionality" / "my `Record` kept nothing" reports both resolve to the same diagnosis (which `in` clause?) plus the same fix vocabulary (`as`-filter inside `keyof T` to keep memory while dropping keys; explicit `?` on fresh shapes). Interviewers use this to test whether candidates debug mappers structurally or by trial-and-error operator toggling.

**Modern guidance** — as of TypeScript 5.9 era, diagnose in order: read the `in` clause (homomorphic? → memory explains the modifiers; fresh? → clean slate explains their absence), then read the operators (added? stripped? untouched?). Full treatment in [1.2. Modifiers](<../1. Mapped Types/1.2. readonly and optional modifiers with plus and minus.md>).

**Runnable example** — clause decides, operator adjusts (`tsc --strict`):

```typescript
interface S { a: string; readonly b: string; c?: string; }
type KeepAll<T> = { [K in keyof T]: T[K] }; // homomorphic, no operators: memory verbatim
type Strip<T> = { -readonly [K in keyof T]-?: T[K] }; // homomorphic + strip all
const k: KeepAll<S> = { a: "a", b: "b" }; // c omittable (remembered)
const s: Strip<S> = { a: "a", b: "b", c: "c" }; // all required, writable (stripped)
s.b = "x"; // compiles — -readonly stripped writability back (compare p.id above, still frozen)
console.log(k.a.toUpperCase(), s.b.toUpperCase()); // A X
```

**Common confusion** — "bare `readonly` means something different from `+readonly`" — identical (`+` is the default when the keyword appears) — the *absence* of the keyword (on homomorphic) means "remember", which differs from both. "`-?` on required members errors" — no-op on already-required (stripping nothing is legal) — operators never fail, they just describe output.

**Performance note** — operators add zero check cost beyond the mapping (one flag per property, cached) — diagnosis is free, trial-and-error toggling is the actual cost (each guess recompiles the reviewer's mental model).

**Mentor note** — the clause-first diagnostic order ("read `in`, then operators") is the teachable habit — trial-and-error toggling is the anti-habit to name explicitly. Exercise: present a modifier surprise and require the clause diagnosis before any operator change.

### 5) **How do you generate `` `on${Capitalize<K>}` `` keys from a union — and why `as` remapping instead of a second object?** (derivation vs duplication)

**Definition** — `{ [K in Ev as `on${Capitalize<K & string>}`]: Handler<K> }` — iterate the event union, remap each key through the template, type each handler with the event's payload: one declaration producing the whole binding table. `as` remapping (not a second hand-written object) because derivation tracks the union — new events propagate, typos error, per-key values thread through the same mapper.

**What problem it solves / history** — parallel handler interfaces drifted (new event → forgotten handler key → silently unwired feature, see [3.2. Template composition](<../3. Transformations in Practice/3.2. Template literal composition Capitalize handlers and routes.md>) promise 2) — interviewers ask the *why-second-object* half to test whether candidates feel the rot cost or merely know the syntax.

**Modern guidance** — as of TypeScript 5.9 era, answer with derivation benefits (propagation, typo-rejection, per-key precision) plus the `K & string` constraint rationale (numbers/symbols need explicit handling, not silent vanishing). Full treatment in [1.3. Template keys](<../1. Mapped Types/1.3. keyof constrained mapping and template literal keys.md>) + [3.2. Template composition](<../3. Transformations in Practice/3.2. Template literal composition Capitalize handlers and routes.md>).

**Runnable example** — derivation propagates, duplication rots (`tsc --strict`):

```typescript
type EvQ = "click" | "keydown";
type TableQ = { [K in EvQ as `on${Capitalize<K>}`]: (at: number) => void };
const t: TableQ = { onClick: (at) => console.log(at), onKeydown: (at) => console.log(at) };
t.onClick(1); // 1 logged
// EvQ gains "scroll" → TableQ demands onScroll; a hand-written mirror would silently lack it
```

**Common confusion** — "`as` remapping breaks homomorphism" — filtering/renaming within `keyof T` keeps memory; over a bare union there is no memory to break — either way `as` is not the culprit. "templates validate runtime dispatch" — static key sets only; dynamic dispatch still needs lookup guards.

**Performance note** — generation caches per union (events × template = one entry); referencing the table 50 times reuses it — derivation is cache-friendly versus mirrored interfaces (two shapes to check).

**Mentor note** — ask "what happens when the union gains a member?" for both approaches — propagation vs rot is the decision criterion, syntax secondary. Hiring signal: rot-aware answers design maintainable tables; syntax-only answers write tomorrow's drift.
