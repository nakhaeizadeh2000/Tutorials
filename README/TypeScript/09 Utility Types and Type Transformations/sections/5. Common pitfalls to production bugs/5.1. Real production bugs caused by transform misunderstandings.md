## 5.1. Real production bugs caused by transform misunderstandings

### 1) **`Partial` at an API boundary hid a missing `price`** (optional-ized response skipped validation; checkout charged zero)

**Definition** — a `fetchProduct(): Promise<Partial<Product>>` helper (partiality meant for PATCH *requests*) was reused for GET *responses* — `price?: number` let `undefined` through, the cart summed `undefined ?? 0`, and a malformed upstream payload charged customers zero for six hours with every check green (`Partial` is honest — the *use* lied about completeness).

**What problem it solves / history** — `Partial` reads as "flexible" so it spread to positions requiring completeness (responses, validated configs, published state) — each a presence-hole the type system was told not to check. The incident rule now: `Partial` flows *inward* (requests, drafts, overrides); complete types flow *outward* (responses, snapshots, charges) — direction enforced by review, not by syntax.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), type response boundaries with complete types (`Product`, `Required<Draft>`) and validate-then-narrow at ingestion (guard/schema proving presence) — `Partial` never crosses an outward boundary. When PATCH and GET share a shape, name both (`ProductPatch = Partial<Product>` vs `Product`) so direction is visible in every signature.

**Runnable example** — direction enforced by type choice (good vs bad, `tsc --strict`):

```typescript
export {}; // module marker for top-level await in this runnable snippet
// bad — Partial response: missing price compiles, cart charges zero
interface Product { id: string; price: number; }
async function fetchBad(): Promise<Partial<Product>> {
  return JSON.parse('{"id":"p1"}') as Partial<Product>; // price missing — type permits
}
async function totalBad(): Promise<string> {
  const p = await fetchBad();
  return (p.price ?? 0).toFixed(2); // "0.00" — silent zero charge
}

// good — complete response: absence errors at ingestion, not at charging
async function fetchGood(): Promise<Product> {
  const raw = JSON.parse('{"id":"p1"}') as Partial<Product>;
  if (typeof raw.price !== "number" || typeof raw.id !== "string") throw new Error("bad payload");
  return { id: raw.id, price: raw.price }; // narrowed to complete before crossing
}
async function totalGood(): Promise<string> {
  return (await fetchGood()).price.toFixed(2); // no ?? 0 — presence proven
}
console.log(await totalBad(), "vs guarded-good (throws on malformed)");
```

**Common confusion** — "`Partial` is safe because consumers use `?.`" — `?.`/`??` convert absence into *defaults*, and defaults at charging boundaries are silent money bugs — safe handling means *rejecting*, not defaulting. "validating duplicates the type" — validation *discharges* the type's claim (proves `Partial` became complete); without it the claim is unverified. "responses are partial during loading" — loading states are *unions* (`{ status: "loading" } | Product`), not partials — model states, not optionality (see [1.2. Discriminated unions](<../../../07 Unions Intersections and Narrowing/sections/1. Union Types/1.2. Discriminated unions the tagged pattern that scales.md>)).

**Performance note** — one validation branch per boundary crossing (negligible vs the network call) replaces unbounded `?? 0` defaults scattered downstream — fewer branches total, each meaningful.

**Mentor note** — post-mortem drill: replay the `?? 0` line and ask "what did this default *cost*?" — defaults at money boundaries are the incident class; `throw` at ingestion is the fix. Gate: `Partial` in a response/outward position fails review unconditionally.

### 2) **Hand-rolled `Exclude` distributed accidentally and dropped a state** (non-naked intent written naked — reducer lost `"archived"`)

**Definition** — a `Visible<S> = S extends "archived" | "deleted" ? never : S` filter (intended: drop exactly those two) was later fed a *branded* status union whose members were objects (`{ kind: "archived"; … }`) — naked distribution tested each object against string literals, dropped *nothing* (objects never extend `"archived"`), and the "hidden" states rendered publicly for a release.

**What problem it solves / history** — hand-rolled filters bake in an input-kind assumption (strings today, objects tomorrow) that stdlib `Exclude` shares — but stdlib call sites get reviewed against known semantics while private filters get trusted blindly. The incident filter worked for a year on string unions, then silently passed through object members it was never tested against — distribution doing exactly what it always did, on input the author never imagined.

**Modern guidance** — as of TypeScript 5.9 era, constrain filter inputs (`S extends string` for string filters — objects then error instead of passing through) and prefer stdlib `Exclude` (reviewed semantics, recognized hover) over private copies. When the input kind genuinely varies, branch explicitly (`S extends object ? … : …` per-kind handling) instead of relying on distribution accidents.

**Runnable example** — constrained filter fails loudly on kind change (good vs bad, `tsc --strict`):

```typescript
// bad — unconstrained hand filter passes object members straight through
type VisibleBad<S> = S extends "archived" | "deleted" ? never : S;
type V1 = VisibleBad<"a" | "archived">; // "a" — correct on strings (masks the flaw)
type V2 = VisibleBad<{ kind: "archived" } | { kind: "live" }>; // BOTH survive — objects never extend strings
const v2: V2 = { kind: "archived" }; // compiles — "hidden" state renders publicly
console.log(v2.kind); // archived — leaked

// good — constrained input: kind change errors instead of leaking
type Visible<S extends string> = S extends "archived" | "deleted" ? never : S;
type G = Visible<"a" | "archived">; // "a"
// type G2 = Visible<{ kind: "x" }>; // error TS2344 — constraint rejects objects (loud, not leaky)
// fix — constrain the filter's domain; model object-states with discriminant checks (07), not string Exclude
console.log("visible:", "a");
```

**Common confusion** — "distribution is the bug" — distribution behaved correctly; the *domain* (strings assumed, objects received) was the bug — constrain domains, don't blame mechanics. "stdlib would have saved us" — `Exclude` on objects behaves identically (passes through) — the fix is the constraint + kind-appropriate check, not the name. "tests would catch it" — type-level pass-through compiles green in value tests (the object renders *something*) — only type assertions (`expectTypeOf<V2>`) or discriminant exhaustiveness catch kind drift.

**Performance note** — constrained filters check identically to unconstrained (one conditional per member) — the constraint adds one assignability test per reference and removes an entire incident class. Cheapest insurance in this domain.

**Mentor note** — feed the object union to the string filter live and ask for the result before hovering — the confident wrong answer ("archived dropped") teaches domain-blindness in one hover. Rule: every hand-rolled filter declares its input domain in the constraint; unconstrained filters fail review.

### 3) **Unbounded `DeepPartial` over generated schema timed out CI** (same TS2589 class as 08/5.1, catalog angle)

**Definition** — a form library applied its (uncapped) `DeepPartial<FormState>` to a generated 800-field schema type — unit fixtures (hand-written, depth 3) stayed green while CI's whole-program check hit TS2589 on main. Same incident class as [08/5.1](<../../../08 Generics Deep Dive/sections/5. Common pitfalls to production bugs/5.1. Real production bugs caused by generic misunderstandings.md>) promise 4, new angle: here the *utility author* (library) and the *input owner* (codegen) were different teams, so neither owned the budget.

**What problem it solves / history** — cross-team recursion (library ships unbounded transform, app feeds unbounded input) has no single owner until the incident assigns one retroactively. The fix assigns ownership upfront: libraries ship caps (counter + documented overflow), apps scope inputs (deep on owned, shallow on generated), and the fixture (largest schema compiling) is co-owned — added by whoever first combines the two.

**Modern guidance** — as of TypeScript 5.9 era: library authors cap every recursive export (see [3.1. Deep transforms](<../3. Transformations in Practice/3.1. Deep transforms DeepPartial DeepReadonly and the budget.md>) promise 3); application authors scope generated inputs shallow; the combining PR adds the largest-schema fixture. No uncapped recursive utility crosses a team boundary — contractual, not advisory.

**Runnable example** — capped library + scoped app + co-owned fixture (good vs bad, `tsc --strict`):

```typescript
// good — library ships the cap; app scopes the input; fixture pins the combination
type CappedPartial<T, D extends number = 3, Seen extends 0[] = []> = Seen["length"] extends D
  ? T
  : T extends object ? { [K in keyof T]?: CappedPartial<T[K], D, [...Seen, 0]> } : T;
interface OwnedForm { name: string; address: { city: string } }
const f: CappedPartial<OwnedForm> = { address: {} }; // deep on owned — within budget
console.log(f.address?.city ?? "empty"); // empty

// bad — uncapped export meets generated input (shape kept tiny so docs compile;
// at 800 fields × 12 deep this exact pattern timed out CI — see 08/5.1)
// type DeepAny<T> = T extends object ? { [K in keyof T]?: DeepAny<T[K]> } : T;
// fix — cap (library) + scope (app) + fixture (combining PR): ownership assigned upfront
```

**Common confusion** — "small fixtures prove safety" — fixtures prove *behavior*; only largest-input fixtures prove *budget* — different properties, different fixtures, both required. "capping is the library's job alone" — caps bound depth, scoping bounds breadth — an uncapped *application* of a capped utility to generated input still explodes breadth-first; both sides own half. "TS2589 means wrong code" — means over-budget instantiation on some input — correct code, ambitious scale; restructure, don't just deepen.

**Performance note** — capped + scoped keeps `instantiations` flat across schema growth (the metric to graph in CI); uncapped grows super-linearly with codegen size — the queue-time graph tells the story before any single PR does.

**Mentor note** — run the 08/5.1 post-mortem template verbatim (cap + fixture + doc comment) — same incident, same template, new catalog instance proves the rule generalizes. Ownership exercise: for each recursive utility, name the cap owner, scope owner, and fixture owner — blanks are future incidents.

### 4) **Template-literal route table widened through `Record<string, …>`** (generated keys collapsed; exhaustiveness died)

**Definition** — a `` `GET ${Path}` `` route-key union (200 exact members) passed through a `normalize<R extends string>(r: R): Record<string, Handler>` helper — the `Record<string, …>` return widened every key to `string`, the exhaustive `switch (route)` over the table went silent, and an unauthenticated handler shipped because no branch was required to exist.

**What problem it solves / history** — `Record<string, V>` as a *carrier* (helper returns, middleware params, context fields) is the template-literal analog of `string`-annotated returns [08/2.1](<../../../08 Generics Deep Dive/sections/2. Constraints Defaults and Inference Control/2.1. Constraints extends narrowing inside the body.md>) promise 2: one wide joint collapses the entire downstream key set. The rule transfers unchanged — carriers must thread the parameter (`Record<M, Handler<M>>`, return `M`), never the constraint.

**Modern guidance** — as of TypeScript 5.9 era, never route template-literal key sets through `Record<string, …>` carriers — thread the key parameter (`normalize<M extends string>(r: M): Route<M>`) and keep tables in derived form (mapped over the union) until the final lookup. Probe carriers with literal hovers (`normalize("/a")` → `"/a"`? or `string`?) before trusting the pipeline.

**Runnable example** — carrier threads the key, table stays exhaustive (good vs bad, `tsc --strict`):

```typescript
// good — carrier threads M: 200 keys stay 200 keys
type Path2 = "/a" | "/b";
type Table2 = { [K in Path2 as `GET ${K}`]: () => string };
function get2<M extends Path2>(m: M): `GET ${M}` { return `GET ${m}`; }
const k = get2("/a"); // "GET /a" — literal, hover it
const t2: Table2 = { "GET /a": () => "A", "GET /b": () => "B" };
console.log(t2[k]()); // A — exhaustive table, precise lookup

// bad — Record<string> carrier collapses the key set
function getBad(m: string): string { return `GET ${m}`; }
const kb = getBad("/a"); // string — 200 keys became one
// const check: "GET /a" = kb; // error — string is not the literal (precision already lost)
// fix — thread M (parameter), never string (constraint), through every carrier
```

**Common confusion** — "`Record<string, V>` preserves keys" — `Record`'s key type *is* the key set — `string` keys mean "any string", collapsing whatever literals flowed in; use mapped-over-union (`{ [K in U as …]: V }`) to preserve. "one collapsed table is harmless with runtime routing" — runtime routes correctly while the *exhaustiveness proof* dies — the next unauthenticated handler ships without a compile error, which is the incident. "re-narrowing downstream recovers" — recovery needs per-value runtime checks — precision lost statically returns only dynamically.

**Performance note** — literal-keyed tables check per member (200 keys — fine); collapsed `string` checks trivially but proves nothing — precision costs linear member checks, collapse costs incidents. Split tables per domain when call-site verification slows.

**Mentor note** — widen one carrier joint live and count table keys before/after (200 → `string`) — the blast radius of a single annotation, visible in one hover. Review probe: every carrier function in a template pipeline gets a literal hover-probe (`f("lit")` → `"lit"`?) — `string` answers fail review.
