## 5.1. Real production bugs caused by transform misunderstandings

These four minimal local reproductions show failure patterns; they are not verified external incident reports. Each makes the wrong assumption observable and checks the proposed repair. Type computation, runtime validation and application policy remain separate.

Use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence as named below. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`; run `node dist/FILE.js`. Activate negatives independently with those flags and --noEmit instead of --outDir dist.

### 1) **A permissive field default concealed incomplete input**

Partial<Product> legitimately permits a missing price. A consumer that needs a price must establish one; silently treating absence as zero changes the meaning of the input. Merely renaming the result Product or Required<Product> supplies no missing runtime check. Sparse responses can be legitimate API contracts, so the issue is the consumer's required information, not an unconditional ban on Partial in outputs.

Save as product.ts. The formatter is a local numeric example, not a payment integration.

```typescript
interface Product { id: string; price: number; }
function permissive(product: Partial<Product>): string { return (product.price ?? 0).toFixed(2); }
const sparse: Partial<Product> = { id: "p1" };
console.log(permissive(sparse));
// const complete: Product = sparse; // TS2322
function parseProduct(raw: unknown): Product {
  if (typeof raw !== "object" || raw === null || !("id" in raw) || !("price" in raw)
      || typeof raw.id !== "string" || typeof raw.price !== "number" || !Number.isFinite(raw.price)) {
    throw new Error("incomplete product");
  }
  return { id: raw.id, price: raw.price };
}
for (const raw of [sparse, null, { id: "p1", price: "12.5" }]) {
  try { parseProduct(raw); }
  catch (error) { console.log(error instanceof Error ? error.message : "unexpected error"); }
}
console.log(parseProduct({ id: "p1", price: 12.5 }).price.toFixed(2));
```

The output is `0.00`, incomplete product on three lines, then `12.50`. The first result is a consequence of the fallback, not proof that the input contained a price. The repair checks the whole unknown value before reading members and establishes the required field types and finiteness. More domain rules may be needed by a real application; this example's contract is explicit.

Use [modifier semantics](<../1. Mapped Types/1.2. readonly and optional modifiers with plus and minus.md>) for Partial/Required and [unknown boundaries](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>) for value checks. Neither optional chaining nor a complete return annotation chooses the correct missing-data policy for a consumer.

### 2) **A string filter was applied to object alternatives**

Exclude<State, "archived"> tests each object member's assignability to a string literal. It does not compare that member's kind property, so both alternatives survive. Distribution is working; the supplied matching pattern asks the wrong question. Standard utility names do not change that semantics.

Save as states.ts.

```typescript
type State = { kind: "live"; title: string } | { kind: "archived"; archivedAt: string };
type Wrong = Exclude<State, "archived">;
type Visible = Exclude<State, { kind: "archived" }>;
const states: State[] = [{ kind: "live", title: "welcome" }, { kind: "archived", archivedAt: "2026-01-01" }];
const wrongView: Wrong[] = states;
console.log(wrongView.map(value => value.kind).join(","));
const visible = states.filter(value => value.kind !== "archived");
console.log(visible.map(value => value.title.toUpperCase()).join(","));
// const rejected: Visible = { kind: "archived", archivedAt: "2026-01-01" }; // TS2322
// wrongView.map(value => value.title); // TS2339

type StringsOnly<S extends string> = Exclude<S, "archived">;
// type DomainMismatch = StringsOnly<State>; // TS2344
// A composite member is not automatically split into discrete object alternatives.
type Composite = { kind: "live" | "archived"; title: string };
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Unchanged = Expect<Equal<Wrong, State>>;
type Payload = Expect<Equal<Visible, { kind: "live"; title: string }>>;
type Filtered = Expect<Equal<typeof visible, Visible[]>>;
type CompositeResult = Expect<Equal<Exclude<Composite, { kind: "archived" }>, Composite>>;
```

The output is `live,archived`, then `WELCOME`. Four live probes compile. The corrected type filters a discrete tagged alternative, while the actual array filter checks values and removes the archived entry. A composite object's wider kind field is not rewritten into separate variants by Exclude.

A string-domain constraint can catch an unintended input-kind change when the API really supports only strings. For object alternatives, choose the actual shape relation and value check. [Conditional fundamentals](<../2. Conditional Types/2.1. Conditional fundamentals distributive law and never branches.md>) owns distribution and runtime filtering, while [utility selection](<../2. Conditional Types/2.2. Exclude Extract NonNullable Pick Omit under the hood.md>) separates member filters from object projections.

### 3) **A broad depth argument stopped a transform immediately**

A counter tested with Seen["length"] extends D does not mean "continue until the runtime number D is reached." D is a type. If D is number, zero already extends it, so this form returns the unchanged source immediately. A finite literal-depth domain makes supported choices explicit; its stopping remainder still needs a meaningful contract.

Save as depth.ts. The fixture concerns plain record data, not a complete container transform.

```typescript
type BroadCap<T, D extends number, Seen extends 0[] = []> = Seen["length"] extends D ? T
  : T extends object ? { [K in keyof T]?: BroadCap<T[K], D, [...Seen, 0]> } : T;
interface Config { db: { host: string; port: number }; tag: string; }
// const notPartial: BroadCap<Config, number> = {}; // TS2739: original required properties remain

type Depth = 0 | 1 | 2;
type Previous = [0, 0, 1];
type Cap<T, D extends Depth> = D extends 0 ? T
  : T extends object ? { [K in keyof T]?: Cap<T[K], Previous[D]> } : T;
const patch: Cap<Config, 2> = { db: { host: "h" } };
// const stopped: Cap<Config, 1> = { db: { host: "h" } }; // TS2741: unchanged db still requires port
// type Unsupported = Cap<Config, number>; // TS2344
console.log(patch.db?.host, patch.db?.port ?? "absent");
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Immediate = Expect<Equal<BroadCap<Config, number>, Config>>;
type Zero = Expect<Equal<Cap<Config, 0>, Config>>;
```

The output is `h absent`, and both probes compile. Depth one and two intentionally accept different nested inputs. Reaching a cap is not automatically a diagnostic, and returning an unchanged remainder is not proof of the same full deep-partial result. A cap also does not guarantee flat instantiation counts or a bound on every comparison.

For actual TS2589 reproductions and investigation, use [instantiation budgets](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.2. Instantiation budgets and TS2589 carve-outs.md>). [Deep-transform policies](<../3. Transformations in Practice/3.1. Deep transforms DeepPartial DeepReadonly and the budget.md>) owns arrays, containers, leaves and stopping choices. No particular field count, schema depth or CI incident was measured here.

### 4) **An open registry admitted a missing callback**

A finite Record<RouteKey, Handler> requires every chosen key, while Record<string, Handler> permits an object whose own keys omit one of those routes. Assigning a finite table through an open view also changes its exposed key contract without changing its actual runtime keys. Keep those two observations separate.

Save as registry.ts.

```typescript
type Path = "/a" | "/b";
type RouteKey = `GET ${Path}`;
type Handler = () => string;
const finite: Record<RouteKey, Handler> = { "GET /a": () => "A", "GET /b": () => "B" };
const openRegistry: Record<string, Handler> = { "GET /a": () => "A" }; // No missing-/b diagnostic.
console.log(openRegistry["GET /b"]?.() ?? "handler missing");
// openRegistry["GET /b"](); // TS2722: noUncheckedIndexedAccess keeps the possible absence visible
const wideView: Record<string, Handler> = finite;
console.log(wideView === finite, Object.keys(wideView).length);
function key<P extends Path>(path: P): `GET ${P}` { return `GET ${path}`; }
function broad(path: string): string { return `GET ${path}`; }
const exact = key("/a");
const widened = broad("/a");
console.log(finite[exact]());
// finite[widened](); // TS7053
// const silent: never = widened; // TS2322: a real never check still rejects the residual string

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type FiniteKeys = Expect<Equal<keyof typeof finite, RouteKey>>;
type OpenKeys = Expect<Equal<keyof typeof wideView, string>>;
```

The output is `handler missing`, `true 2`, then `A`. Both probes compile. The open object really omits a callback; the wide view of finite still has two runtime keys. A broad key is rejected when indexing the finite contract, and an actual never check does not become silent merely because the value's type widened to string.

For a controlled comparison, disable noUncheckedIndexedAccess and wrap the activated `openRegistry["GET /b"]()` call in try/catch: compilation accepts it and the actual call throws TypeError. The flag can expose absence; it does not create the handler. An open registry can be appropriate for dynamic plugins, provided lookup and validation implement its real policy. Neither representation proves authentication or server routing behavior. [Template composition](<../3. Transformations in Practice/3.2. Template literal composition Capitalize handlers and routes.md>) owns a complete local finite-dispatch example.

### 5) **Common confusion**

Partial admits absence without deciding its meaning. A complete type annotation is not validation. Exclude compares member types to the supplied pattern rather than automatically checking a discriminant field. The actual runtime filter must still examine values.

A broad number type is not a literal counter limit, and a cap changes the result where it stops. Likewise, an open key contract changes what the compiler promises without changing existing runtime properties. Check actual values and rejected operations before assigning the wrong cause to a failure.

### 7) **Mentor note**

Ask which assumption fails before accepting a repair: the consumer needed a missing field, the filter matched strings rather than objects, a broad depth type matched zero, or a registry omitted an actual function. Require an observation from the program and a reason the proposed change addresses that cause.

For practice, add /c to Path. The finite table must now fail for missing GET /c, while openRegistry still compiles. Add a callback returning C and invoke `finite[key("/c")]()`. Existing A behavior must remain, the new call must return C, and the open table's absent /b must still be handled explicitly. This checks propagation and runtime behavior without confusing a table with an HTTP implementation.
