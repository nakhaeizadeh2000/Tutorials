## 3.1. Deep transforms — DeepPartial, DeepReadonly and the budget

A deep transform applies a type policy recursively. The hard part is choosing that policy: should arrays contain partial elements, should tuples keep required positions, and should a Map key change type? DeepPartial and DeepReadonly are common project or library names, not one universal built-in contract. Define the supported shapes and stopping behavior before applying them to an API.

Use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence as named below. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`; run `node dist/FILE.js`. Check commented negatives independently with the same flags and --noEmit instead of --outDir dist.

### 1) **Read the recursion and verify what the runtime update does**

The simple recipe makes each object property optional, then applies itself to that property's type. Primitives pass through. Functions and Date are objects, so they enter this naive object branch too: mapping their properties does not preserve a callable signature. A real Date may still be assignable to the weakened shape, and an empty object may be admitted as well. The problem is a lost contract, not necessarily a rejected Date construction.

Save as patching.ts.

```typescript
type NaivePartial<T> = T extends object ? { [K in keyof T]?: NaivePartial<T[K]> } : T;
interface Org { name: string; billing: { street: string; city: string }; }
const base: Org = { name: "Acme", billing: { street: "street", city: "old" } };
const patch: NaivePartial<Org> = { billing: { city: "Berlin" } };
// const shallowPatch: Partial<Org> = { billing: { city: "Berlin" } }; // TS2741
const shallow = { ...base, ...patch };
// const claimed: Org = shallow; // TS2322: the replacement billing may be incomplete
console.log("street" in shallow.billing, shallow.billing.city);
function applyBillingPatch(org: Org, update: NaivePartial<Org>): Org {
  return {
    name: update.name ?? org.name,
    billing: {
      street: update.billing?.street ?? org.billing.street,
      city: update.billing?.city ?? org.billing.city
    }
  };
}
const repaired = applyBillingPatch(base, patch);
console.log(repaired.billing.street, repaired.billing.city.toUpperCase(), base.billing.city);

const date = new Date("2026-01-01T00:00:00Z");
const weakenedDate: NaivePartial<Date> = date; // Accepted.
const emptyDate: NaivePartial<Date> = {}; // Also accepted; no Date has been constructed.
const weakenedCall: NaivePartial<(n: number) => string> = (n: number) => String(n);
console.log(typeof weakenedDate.toISOString, typeof emptyDate.toISOString, typeof weakenedCall);
// weakenedDate.toISOString?.(); // TS2349: mapped member has no call signature
// weakenedCall(2); // TS2349
```

The output is `false Berlin`, `street BERLIN old`, then `function undefined function`. Shallow spread replaces the entire billing object, losing street. The concrete repair copies the known nested fields and preserves the original; it does not claim to implement a universal merge. Empty string is a valid supplied string under its nullish fallback policy. Validate untrusted data before relying on this typed input.

The runtime function in weakenedCall still exists, but its static view no longer describes a call. [Recursive generics](<../../../08 Generics Deep Dive/sections/3. Variance and Advanced Generic Patterns/3.2. Recursive generic types and self-referential patterns.md>) owns the shape/computation distinction; this leaf now chooses the fuller container and leaf policies.

### 2) **Choose partial-data rules for containers and leaves**

This lesson's PartialData is a limited policy for ordinary records, arrays/tuples, Map/Set views, Date, RegExp and ordinary function values. Custom classes and additional built-ins require their own decisions. Passing through a function preserves its whole callable type, including any attached state; it does not partially rebuild that state.

| Input category | PartialData policy |
|---|---|
| Date, RegExp, function | Keep the supplied type as an atomic leaf. |
| Map or ReadonlyMap | Publish a readonly map view; keep key types and partially transform values. |
| Set or ReadonlySet | Publish a readonly set view with complete member types. |
| Array or tuple | Transform elements, preserving array mutability and tuple position requirements. |
| Ordinary record | Make each property optional and transform its value. |

These are deliberate choices. Array-element patches still need an application policy to match or merge elements; the type implements no such operation. Set members remain complete because this example does not define partial membership updates. Map key types remain unchanged so the view does not suggest a different key contract. Library utilities can choose differently: the [TypeFest source](https://github.com/sindresorhus/type-fest/blob/main/source/partial-deep.d.ts) exposes separate array-recursion and undefined-element options. This lesson does not install or certify that library version.

Save as partial-data.ts.

```typescript
type PartialData<T> = T extends Date | RegExp ? T
  : T extends (...args: never[]) => unknown ? T
  : T extends ReadonlyMap<infer Key, infer Value> ? ReadonlyMap<Key, PartialData<Value>>
  : T extends ReadonlySet<infer Item> ? ReadonlySet<Item>
  : T extends readonly unknown[] ? { [K in keyof T]: PartialData<T[K]> }
  : T extends object ? { [K in keyof T]?: PartialData<T[K]> } : T;
interface Feature { id: string; enabled: boolean; }
interface Config {
  at: Date; match: RegExp; run: (n: number) => string;
  rows: readonly Feature[]; pair: readonly [string, { port: number }];
  byId: Map<object, Feature>; members: Set<Feature>;
}
const key = {};
const member: Feature = { id: "full", enabled: true };
const draft: PartialData<Config> = {
  at: new Date("2026-01-01T00:00:00Z"), match: /a/,
  run: n => n.toFixed(0), rows: [{ id: "row" }], pair: ["db", {}],
  byId: new Map([[key, { enabled: true }]]), members: new Set([member])
};
console.log(draft.at?.getUTCFullYear(), draft.run?.(3), draft.rows?.[0]?.id, draft.pair?.[0]);
console.log(draft.byId?.get(key)?.enabled, draft.byId?.get({}), draft.members?.has(member));
// draft.byId?.set(key, {}); // TS2339: readonly map view
// draft.members?.add(member); // TS2339
// const incompleteMember: PartialData<Config> = { members: new Set([{}]) }; // TS2322
// const incompleteTuple: PartialData<Config> = { pair: ["db"] }; // TS2322
// const sparse: PartialData<Config> = { rows: [undefined] }; // TS2322

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Tuple = Expect<Equal<PartialData<readonly [{ id: string }, number]>, readonly [{ id?: string }, number]>>;
type ArrayResult = Expect<Equal<PartialData<{ id: string }[]>, { id?: string }[]>>;
type Callable = Expect<Equal<PartialData<(n: number) => string>, (n: number) => string>>;
```

The output is `2026 3 row db`, then `true undefined true`. Three live probes compile. The original object key retrieves its entry while a newly created object does not. A map type transformation does not clone or normalize keys. Array elements in this policy may have partial fields, but the array does not gain an undefined element type just because record properties become optional. Present tuple positions also remain required.

The branch order matters where categories overlap: specific leaves and containers must be handled before the broad object mapping. A readonly map interface here changes available operations through the view, not the runtime Map instance or aliases to it. [Collection types](<../../../10 Arrays Tuples and Collections/README.md>) owns Map/Set identity and container selection; [mapped foundations](<../1. Mapped Types/1.1. Mapped type fundamentals homomorphic mapping over keys.md>) owns tuple/array structure preservation.

### 3) **Publish a readonly data view without promising immutable values**

The following policy removes writes through ordinary records and arrays, recursively views map values and set members, and preserves original map key types. Date, RegExp and functions remain leaves, so their mutating behavior can remain available. A different contract may wrap, replace or reject such leaves. This is a data view, not a deep-freezing function or complete immutability guarantee.

Save as readonly-data.ts.

```typescript
type ReadonlyData<T> = T extends Date | RegExp ? T
  : T extends (...args: never[]) => unknown ? T
  : T extends ReadonlyMap<infer Key, infer Value> ? ReadonlyMap<Key, ReadonlyData<Value>>
  : T extends ReadonlySet<infer Item> ? ReadonlySet<ReadonlyData<Item>>
  : T extends object ? { readonly [K in keyof T]: ReadonlyData<T[K]> } : T;
const key = { id: "key" };
const member = { enabled: true };
const source = {
  rows: [{ id: "initial" }], byId: new Map([[key, { label: "initial" }]]), members: new Set([member]),
  at: new Date("2026-01-01T00:00:00Z"), match: /a/g, run: (n: number) => n.toFixed(0)
};
const view: ReadonlyData<typeof source> = source;
// view.rows.push({ id: "x" }); // TS2339
// view.byId.set(key, { label: "x" }); // TS2339
const row = view.rows[0];
if (row) {
  // row.id = "x"; // TS2540
}
const mapped = view.byId.get(key);
if (mapped) {
  // mapped.label = "x"; // TS2540
}
for (const item of view.members) {
  // item.enabled = false; // TS2540
}
const originalRow = source.rows[0];
if (originalRow) originalRow.id = "changed";
source.byId.set(key, { label: "changed" });
member.enabled = false;
view.at.setUTCFullYear(2027);
view.match.exec("a");
key.id = "changed key";
console.log(view.rows[0]?.id, view.byId.get(key)?.label, [...view.members][0]?.enabled);
console.log(view.at.getUTCFullYear(), view.match.lastIndex, view.run(3), view === source, Object.isFrozen(source));
console.log(view.byId.get({ id: "changed key" }));
```

The output is `changed changed false`, `2027 1 3 true false`, then `undefined`. Writes rejected through the readonly view do not prevent the source aliases from changing shared values. Date and RegExp still mutate under the documented leaf policy. The map still uses the same original key identity, even after that key object's field changes.

No runtime collection was converted into a plain object by the mapped alias. The actual Map and Set remain and are exposed through readonly contracts. The [readonly modifier owner](<../1. Mapped Types/1.2. readonly and optional modifiers with plus and minus.md>) separates static views, actual copies and Object.freeze; deep ownership or immutable domain design needs stronger runtime decisions than another mapped keyword.

### 4) **Treat a cap as part of the result contract**

A cap can stop a utility's own descent, but the result at that point must be specified. This small cap demonstration concerns plain record data; integrating it into the fuller container policies requires counting and stopping in each chosen branch. It returns the original T at depth zero. For a partial transform, that can make fields below the stopping boundary required again.

Save as capped-data.ts.

```typescript
type Depth = 0 | 1 | 2 | 3;
type Previous = [0, 0, 1, 2];
type CappedPartial<T, D extends Depth = 2> = D extends 0 ? T
  : T extends object ? { [K in keyof T]?: CappedPartial<T[K], Previous[D]> } : T;
interface Config { db: { host: string; pool: { size: number } }; tag: string; }
const depthTwo: CappedPartial<Config, 2> = { db: { pool: { size: 4 } } };
const depthThree: CappedPartial<Config, 3> = { db: { pool: {} } };
// const stopped: CappedPartial<Config, 2> = { db: { pool: {} } }; // TS2741: size required at unchanged remainder
// const shallower: CappedPartial<Config, 1> = { db: { host: "h" } }; // TS2741: pool required at unchanged db
// type Unsupported = CappedPartial<Config, number>; // TS2344
console.log(depthTwo.db?.pool?.size, depthThree.db?.pool?.size ?? "absent");
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Zero = Expect<Equal<CappedPartial<Config, 0>, Config>>;
```

The output is `4 absent`, and the zero-depth probe compiles. Reaching the cap does not automatically emit a diagnostic; the identity remainder is the intended result. Invalid construction can then fail because that remainder still has requirements. Increasing the cap changes which deeper fields may be omitted, rather than repairing an equivalent implementation for free.

There is no universal correct default depth or largest-schema threshold. Choose a representative input that tests your semantics, reproduce actual checking failures, and profile when needed. The [instantiation-budget owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.2. Instantiation budgets and TS2589 carve-outs.md>) contains actual TS2589 fixtures and counterexamples; it does not promise that this cap bounds every computation or every program's memory use.

### 5) **Common confusion**

Functions enter a naive object branch, and a mapped view can lose its callable contract even while the original runtime function remains. Accepting a real Date does not prove the transformed type still guarantees Date behavior: the naive view also accepted an empty object. Handle those leaves intentionally.

Partial fields describe allowed data without defining how to merge it. Array element partiality, tuple slot presence, map key identity and set membership are separate policy choices. Readonly views do not make all reachable values immutable, especially when mutating leaves and source aliases remain.

### 6) **Performance note**

Deep types erase. The examples retain actual object copying, Map/Set operations, Date/RegExp mutations and calls. Recursive checking work depends on input shape, branch policies, unions and downstream operations; no properties-times-depth instantiation formula or fixed memory bound was measured. A cap limits this alias's descent but changes its result and does not bound all comparisons. Use [diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) for an actual problem.

### 7) **Mentor note**

Ask the learner to specify a policy before writing a recursive alias. Require an answer for array replacement versus element updates, tuple requirements, key/member identity and mutating leaves. Then ask which operation really merges billing and which alias merely admits the partial input. A sound explanation also names the unchanged cap remainder.

For practice, change PartialData's array/tuple branch to return T unchanged, modeling a policy that requires complete array replacements. The existing partial row and partial tuple object must now be rejected. Supplying { id: "row", enabled: true } and ["db", { port: 5432 }] makes them valid. Verify that the prior readonly tuple structure and required fields remain intact. This policy change deliberately alters accepted inputs; it does not implement the replacement operation itself.
