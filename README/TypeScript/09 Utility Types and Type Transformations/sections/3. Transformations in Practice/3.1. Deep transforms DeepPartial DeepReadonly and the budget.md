## 3.1. Deep transforms — `DeepPartial`, `DeepReadonly`, and the budget

### 1) **`DeepPartial` line by line** (mapped recursion with a stop condition)

**Definition** — `type DeepPartial<T> = T extends object ? { [K in keyof T]?: DeepPartial<T[K]> } : T` — three parts: the guard (`T extends object` decides descend-vs-stop), the mapper (`[K in keyof T]?` rebuilds each level partially), the recursion (`DeepPartial<T[K]>` descends per property). Primitives, functions-as-values, and already-`never` branches hit the false arm and terminate. [04/3.1](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.1. Recursive object types and self-referential structures.md>) budgeted a capped variant; [08/3.2](<../../../08 Generics Deep Dive/sections/3. Variance and Advanced Generic Patterns/3.2. Recursive generic types and self-referential patterns.md>) proved `DeepReadonly` — this leaf owns the *catalog* reading: guard, mapper, recursion, base.

**What problem it solves / history** — nested PATCH bodies (`PATCH /orgs` with a partial billing address inside a partial settings object) could not be expressed shallowly — `Partial<Org>` leaves `billing` all-or-nothing (present means complete). `DeepPartial` makes every level independently partial: clients send exactly the leaves they change, and the server merges — one type replacing per-level hand-written patch interfaces at every depth.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), use `DeepPartial` for nested update inputs (PATCH bodies, config overrides, test fixtures); keep *outputs* shallow (`Partial` or exact) so consumers never guess which leaves are present. Carve out leaf types the recursion must not enter (`Date`, `Map`, functions — see promise 2) instead of letting the mapper rebuild their internals.

**Runnable example** — nested partiality without per-level mirrors (good vs bad, `tsc --strict`):

```typescript
// good — every level independently partial: send exactly the leaves that change
interface Billing { street: string; city: string; }
interface Org { name: string; billing: Billing; }
type DeepPartial<T> = T extends object ? { [K in keyof T]?: DeepPartial<T[K]> } : T;
const patch: DeepPartial<Org> = { billing: { city: "Berlin" } }; // street omitted legally
console.log(patch.billing?.city?.toUpperCase() ?? "missing"); // BERLIN

// good — shallow Partial leaves nested objects all-or-nothing (know the difference)
const shallow: Partial<Org> = { billing: { street: "s", city: "c" } }; // billing complete or absent
console.log(shallow.billing?.city); // c

// bad — per-level patch mirrors rot when the source gains a field
interface BillingPatch { street?: string; city?: string; }
interface OrgPatch { name?: string; billing?: BillingPatch; } // mirrors two levels today...
// Org.billing gains `zip` → DeepPartial<Org> accepts { billing: { zip: "x" } }; OrgPatch rejects it
// fix — DeepPartial<Org>: the recursion (not the author) enumerates the levels
const future: DeepPartial<Org> = { name: "acme" };
console.log(future.name?.toUpperCase()); // ACME
```

**Common confusion** — "`DeepPartial` validates merges" — static shape only; merging (`{...base, ...patch}`) is runtime code with its own depth semantics (shallow spread vs deep merge) — the type describes the input, not the merge. "`Partial` nested once is enough" — `Partial<Org>` makes `billing` *optional* but, when present, still *complete* — depth-1 vs depth-N differ exactly at the nested leaf. "functions inside descend harmlessly" — function properties recurse per *property of the function object* (usually harmless, occasionally surprising) — carve them out (promise 2).

**Performance note** — `DeepPartial` costs O(properties × depth) instantiations (a 50-key config 4 deep ≈ 200 cached entries — fine). The cliff is wide *and* deep generated schemas — cap or scope (promise 3); never apply unbounded deep transforms to codegen output without a fixture proving the budget.

**Mentor note** — trace one level on the board (`Org` → `billing?: DeepPartial<Billing>` → `city?: string`) and stop — students extrapolate. Exercise: add `zip` to `Billing` and watch the `OrgPatch` mirror break while `DeepPartial<Org>` adapts — rot-vs-derivation in one field. Review rule: per-level patch mirrors are defects; the recursive derivation is the fix.

### 2) **Composing mapped with conditional** (the guard decides descend-vs-stop per branch)

**Definition** — every production deep transform is `T extends <Descendable> ? {mapped recursion} : T`: the conditional *guards*, the mapper *rebuilds*, the false branch *stops*. Refining the guard refines behavior — `T extends Date ? T : …` preserves dates, `T extends (...args: never[]) => unknown ? T : …` preserves functions, `T extends Map<infer K, infer V> ? Map<K, Deep<V>> : …` rebuilds containers structurally instead of property-wise.

**What problem it solves / history** — naive `DeepPartial` recursed into `Date` (mapping its 40 methods into partial method-shapes — assignability broke: a real `Date` no longer satisfied `DeepPartial<Date>`), into functions (methodish recursion), and into `Map`/`Set` (property-mapping a structural container into a plain-object shape). Guard clauses carve each category out: dates/functions pass through, containers rebuild structurally, plain objects recurse property-wise — one alias, four behaviors, zero surprises.

**Modern guidance** — as of TypeScript 5.9 era, ship deep transforms with an explicit carve-out chain ordered most-specific-first: `Date`/`RegExp` → functions → `Map`/`Set`/arrays → plain objects → primitives. Order matters (each branch must precede the general `object` test it would otherwise match). Document the carve-outs in the alias's doc comment — the next author extends the chain instead of rediscovering each casualty.

**Runnable example** — carve-outs preserve leaf categories (good vs bad, `tsc --strict`):

```typescript
// good — Date passes through; plain objects recurse; primitives stop
type Smart<T> = T extends Date ? T
  : T extends (...args: never[]) => unknown ? T
  : T extends object ? { [K in keyof T]?: Smart<T[K]> } : T;
interface Event { at: Date; meta: { tag: string }; run: () => void; }
const e: Smart<Event> = { at: new Date("2026-01-01"), meta: {} };
console.log(e.at?.toISOString().slice(0, 4), e.meta?.tag ?? "none"); // 2026 none
// e.at is Date (not a 40-method partial); e.run stays callable when provided

// bad — naive recursion rebuilds Date into an unusable method-partial
type Naive<T> = T extends object ? { [K in keyof T]?: Naive<T[K]> } : T;
type ND = Naive<Date>; // { toString?: ...; getTime?: ...; ... } — a real Date fails this shape
// const nd: ND = new Date(); // error TS2322 — methods optional-ized, nothing satisfies it
// fix — Smart<T>: carve Date (and functions) out before the object branch
const ok: Smart<Date> = new Date("2026-01-01");
console.log(ok.getFullYear()); // 2026 — passthrough, not rebuilt
```

**Common confusion** — "carve-out order is cosmetic" — `Date extends object` is true, so the `Date` branch must precede the `object` branch — order *is* semantics in conditional chains. "functions need deep treatment" — function *signatures* are atomic for transform purposes (parameters/returns map via `Parameters`/`ReturnType`, not via property recursion) — pass through, transform separately. "`Map` recursion equals object recursion" — `Map<K, V>` rebuilt as `{[K in keyof Map]…}` is a plain-object lie — rebuild structurally (`Map<Smart<K>, Smart<V>>`) or pass through.

**Performance note** — each carve-out adds one conditional test per instantiation (O(branches) per level — trivial). The saving is downstream: passthrough branches skip entire subtree mappings (a `Date` costs 1 test instead of 40 method mappings) — carve-outs *reduce* total instantiations while fixing correctness.

**Mentor note** — add a `Date` field to a naive-`DeepPartial` fixture and read the 40-method hover together — the casualty teaches stop-conditions better than any rule statement. Exercise: order a shuffled carve-out chain correctly and justify each position ("why must `Date` precede `object`?"). Review gate: new deep transforms without a carve-out comment fail review.

### 3) **Budgeting deep transforms in production** (caps, scope, largest-schema fixtures)

**Definition** — production rule for recursive utilities: ship a depth cap (tuple-counter, default 3–5), narrow the input scope (transform owned subtrees, reference pre-computed aliases for generated ones), and pin the largest real schema as a fixture that must compile. [08/3.2](<../../../08 Generics Deep Dive/sections/3. Variance and Advanced Generic Patterns/3.2. Recursive generic types and self-referential patterns.md>) proved the counter; [08/5.1](<../../../08 Generics Deep Dive/sections/5. Common pitfalls to production bugs/5.1. Real production bugs caused by generic misunderstandings.md>) showed the CI-only TS2589 incident — this promise applies both to the catalog: capped `DeepPartial`, scoped application, fixture discipline.

**What problem it solves / history** — uncapped `DeepPartial<GeneratedSchema>` (800 keys, 12 deep) compiled against unit fixtures (depth 4) and timed out CI's whole-program check — green PRs, red main, forty minutes of queue forensics. The cap turns timeout into a local error (overflow degrades to `T`), scoping turns global application into a local one (freeze the owned subtree), and the fixture turns CI-only into CI-pinned (largest schema compiles on every PR touching the utility).

**Modern guidance** — as of TypeScript 5.9 era, library-published deep transforms take `D extends number = 5` counters with documented overflow (`D = 0` → passthrough `T`); application code applies deep transforms to owned types and shallow ones (`Partial`, explicit projections) to generated types. Measure with `tsc --extendedDiagnostics` after any recursive-utility change; record `instantiations` deltas in the PR. Full scaling treatment lands in [19 Performance](<../19 Performance Project References and Scaling/README.md>) (textual forward).

**Runnable example** — cap degrades locally instead of timing out globally (good vs bad, `tsc --strict`):

```typescript
// good — capped: overflow falls back to T (sound, unfrozen) instead of TS2589
type CappedPartial<T, D extends number = 3, Seen extends 0[] = []> = Seen["length"] extends D
  ? T
  : T extends object ? { [K in keyof T]?: CappedPartial<T[K], D, [...Seen, 0]> } : T;
interface Cfg { db: { host: string; pool: { size: number } }; tag: string; }
const c: CappedPartial<Cfg> = { db: { pool: {} } };
console.log(c.db?.pool?.size ?? "default"); // default — deep leaves omittable within budget

// good — scope-narrowing: transform the owned subtree, reference the generated one
interface App { theme: { mode: string }; schemaId: string } // theme owned, schemaId opaque
type ThemePatch = CappedPartial<App["theme"]>; // deep only where depth is bounded
const t: ThemePatch = {};
console.log(Object.keys(t).length); // 0 — patch shape without touching generated input

// bad — unbounded deep transform over an unbounded input (shape kept shallow so docs compile;
// the same alias over the 800-key generated schema tripped TS2589 in CI — see 08/5.1 incident)
// type DeepAny<T> = T extends object ? { [K in keyof T]?: DeepAny<T[K]> } : T;
// fix — CappedPartial (counter) for libraries; scoped application for apps; fixture for CI
```

**Common confusion** — "capping loses type safety" — overflow falls back to the *untransformed* (still sound) type — strictly safer than a timed-out build shipping nothing. "fixtures test the feature" — the largest-schema fixture tests the *budget*, not the feature — it fails exactly when growth exceeds the cap, which is the intended signal. "shallow transforms are weaker" — shallow is *scoped*: `Partial` on generated input plus `DeepPartial` on owned subtrees beats unbounded depth everywhere.

**Performance note** — the cap bounds check memory linearly (D levels × keys); overflow passthrough is O(1). Measured rule: keep application deep transforms under depth ~5 over owned types; library transforms default 3–5 with documented overflow. `instantiations` in `--extendedDiagnostics` is the number to watch per PR.

**Mentor note** — pin the largest-schema fixture *for the utility* (not just feature PRs) — the fixture is the budget's test. Post-mortem template from 08/5.1 still applies: cap + fixture + doc comment stating D and overflow behavior — three lines preventing the next queue outage.
