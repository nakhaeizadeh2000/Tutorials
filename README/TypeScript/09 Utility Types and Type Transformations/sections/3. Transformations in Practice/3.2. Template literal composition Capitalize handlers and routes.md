## 3.2. Template literal composition — Capitalize, handlers and routes

Template literal types compute string contracts from other types. Intrinsic string types change case in those contracts, and interpolated unions describe combinations. A computed name does not create a runtime function, bind an event or validate an incoming path. Use the relationship to check actual implementations, then verify their value behavior separately.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence as named below. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then run `node dist/FILE.js`. Activate commented negatives separately using those flags with --noEmit instead of --outDir dist.

### 1) **Distinguish a cased contract from a runtime conversion**

Uppercase and Lowercase transform the whole string type, while Capitalize and Uncapitalize transform its first character. A literal union produces the corresponding union of transformed literals. Capitalize does not find word boundaries: keydown becomes Keydown, not KeyDown.

The broad form Uppercase<string> is not simply interchangeable with string on this baseline. It accepts suitable literals such as GET and rejects get. Capitalize<string> similarly rejects the lowercase-first hello fixture. A runtime string method returns a broad string type here; its execution does not automatically give a result the compiler proves to be every desired intrinsic type.

Save as casing.ts.

```typescript
type Method = "get" | "post";
type Verb = Uppercase<Method>;
const uppercase: Uppercase<string> = "GET";
const capitalized: Capitalize<string> = "Hello";
// const wrong: Uppercase<string> = "get"; // TS2322
// const wrongFirst: Capitalize<string> = "hello"; // TS2322
const verbs: Record<Method, Verb> = { get: "GET", post: "POST" };
function normalize(method: Method): Verb { return verbs[method]; }
console.log(uppercase, normalize("post"), capitalized);
const runtimeText = "get".toUpperCase();
// const claimed: Verb = runtimeText; // TS2322: this expression's static result is string
console.log(runtimeText, "ß".toUpperCase());

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type U = Expect<Equal<Uppercase<Method>, "GET" | "POST">>;
type L = Expect<Equal<Lowercase<"GET" | "POST">, Method>>;
type C = Expect<Equal<Capitalize<"keydown">, "Keydown">>;
type Un = Expect<Equal<Uncapitalize<"HELLO">, "hELLO">>;
type Expansion = Expect<Equal<Uppercase<"ß">, "SS">>;
type Broad = Expect<Equal<Equal<Uppercase<string>, string>, false>>;
```

The output is `GET POST Hello`, then `GET SS`. Six probes compile. The finite normalization table performs a real runtime selection with the declared Verb result; the intrinsic alone performs no conversion on a supplied value. This table promises an uppercase method result, not a type-level proof that any arbitrary generic string converter preserves an exact literal relationship.

The [primary intrinsic guidance](https://www.typescriptlang.org/docs/handbook/2/template-literal-types.html#intrinsic-string-manipulation-types) describes the operations and their non-locale-aware casing basis. Case conversion may change length, as ß to SS demonstrates. Do not treat these helpers as locale-aware identifier normalization or reversible encodings.

### 2) **Apply generated names to precise value contracts**

The key-remapping owner already derives handlers from event keys. Apply that same relationship to setting-change callbacks: derive the changed name from the property, while retaining that property's actual value type. Keeping the names precise but replacing their values with any would lose half the contract.

Save as changes.ts.

```typescript
interface Settings { theme: "dark" | "light"; pageSize: number; }
type Changes<T> = { [K in keyof T as `${K & string}Changed`]: (value: T[K]) => string };
const changes: Changes<Settings> = {
  themeChanged: value => `theme:${value}`,
  pageSizeChanged: value => value.toFixed(0)
};
console.log(changes.themeChanged("dark"), changes.pageSizeChanged(20));
// changes.themeChanged(20); // TS2345
// const missing: Changes<Settings> = { themeChanged: changes.themeChanged }; // TS2741
// const typo: Changes<Settings> = { themeChange: changes.themeChanged, pageSizeChanged: changes.pageSizeChanged }; // TS2561
```

The output is `theme:dark 20`. These callbacks are actual functions in an object and are called explicitly. No observer or framework subscription has been installed. The [key-remapping lesson](<../1. Mapped Types/1.3. keyof constrained mapping and template literal keys.md>) owns generated-key mechanics, collisions, string-key filtering and per-event payloads; use it for the complete explanation rather than duplicating another event-table tutorial here.

### 3) **Model legal combinations and implement the runtime boundary**

Interpolating Version and Resource independently produces their full cross-product. That is correct only when every pair is legal. If admin exists only in v2, the type must preserve that relationship. Map each version to its allowed resources, then unite the resulting paths. An explicit Exclude of the one illegal pair gives the same current set; a structural rule can make the intended evolution clearer.

Save as routes.ts. This is a local string dispatcher, not an HTTP server or authentication system.

```typescript
type Version = "v1" | "v2";
type Resource = "users" | "health" | "admin";
type Product = `/api/${Version}/${Resource}`;
type AllowedResource<V extends Version> = V extends "v1" ? "users" | "health" : Resource;
type Route = { [V in Version]: `/api/${V}/${AllowedResource<V>}` }[Version];
const illegalProduct: Product = "/api/v1/admin"; // Accepted by the unrestricted product.
// const illegalRoute: Route = "/api/v1/admin"; // TS2820
const routes: Readonly<Record<Route, () => string>> = Object.freeze({
  "/api/v1/users": () => "v1 users",
  "/api/v1/health": () => "v1 health",
  "/api/v2/users": () => "v2 users",
  "/api/v2/health": () => "v2 health",
  "/api/v2/admin": () => "v2 admin"
});
function isRoute(value: unknown): value is Route {
  return typeof value === "string" && Object.hasOwn(routes, value);
}
function dispatch(value: unknown): string { return isRoute(value) ? routes[value]() : "invalid route"; }
console.log(dispatch("/api/v2/admin"), dispatch(illegalProduct));
console.log(dispatch("/api/v3/users"), dispatch(42));
const dynamic: string = "/api/v2/users";
// routes[dynamic](); // TS7053: unchecked string is not a known route

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type ProductSet = Expect<Equal<Product,
  "/api/v1/users" | "/api/v1/health" | "/api/v1/admin" |
  "/api/v2/users" | "/api/v2/health" | "/api/v2/admin">>;
type LegalSet = Expect<Equal<Route, Exclude<Product, "/api/v1/admin">>>;
```

The output is `v2 admin invalid route`, then `invalid route invalid route`. Both probes compile. The product admits six paths, while the rule admits five. The complete Record requires implementations for the legal set, and the runtime membership check rejects the forbidden pair and unrelated inputs.

The isRoute predicate is justified by this particular frozen object: it is explicitly constructed with exactly the required own route keys and cannot later gain another own key. Object.hasOwn on an arbitrary mutable or externally supplied object would not establish the same finite-key guarantee. Nor does a type predicate's signature insert these checks automatically; [custom narrowing](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.3. Custom narrowers predicates asserts and type guards on unions.md>) owns that obligation.

Finite generated types can help check a table; open-ended plugins or dynamically loaded routes may require a different registry contract. Choose a representation for the actual supported relationships instead of declaring every handwritten or open table defective. The [primary template guide](https://www.typescriptlang.org/docs/handbook/2/template-literal-types.html) describes union interpolation; [conditional fundamentals](<../2. Conditional Types/2.1. Conditional fundamentals distributive law and never branches.md>) explains which generic conditionals distribute.

### 4) **Common confusion**

Broad intrinsic types can retain casing restrictions; they do not all collapse to plain string. Capitalize changes the first character and does not invent internal word boundaries. A type-level casing computation also does not execute a runtime converter or prove that an arbitrary string method's broad result satisfies a finite union.

Independent interpolation admits every pair, including illegal combinations unless a relationship removes them. A complete static table checks required keys and values, but actual callbacks, dispatch and input validation still require implementation. Here those behaviors are supplied explicitly and observed locally.

### 5) **Performance note**

Intrinsic and template types erase. Actual casing, table lookup, freezing, callbacks and guards remain. Independent factors can increase the number of possible strings, but no fixed key-count cliff, per-call union walk or instantiation/cache formula was measured. The product's size alone is not the entire checking cost. Investigate a real problem with [compiler diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>); choose explicit types, factored APIs or generated declarations according to the contract and evidence.

### 6) **Mentor note**

Ask which six pairs Product admits and which one the rule removes before showing the table. Require an explanation of why the runtime guard is trustworthy for the frozen local table, and what would change for a mutable external registry. For casing, ask why keydown and keyDown produce different names.

For practice, add metrics to Resource while keeping the current v1 restriction. Route gains /api/v2/metrics, so the table must supply that callback. After adding it, dispatching that path must return v2 metrics, while /api/v1/metrics remains invalid. Update the explicit product probe to include both new product members, and keep the legal-set check correct by excluding both v1-only forbidden pairs. This tests evolution of the relationship, not just appending a key blindly.
