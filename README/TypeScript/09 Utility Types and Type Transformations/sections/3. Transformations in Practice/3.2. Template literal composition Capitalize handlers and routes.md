## 3.2. Template literal composition — `Capitalize`, handlers, and routes

### 1) **Intrinsic string mappers** (compile-time string surgery, zero emit)

**Definition** — four intrinsic types transform string literals at check time: `Capitalize<S>` (`"click"` → `"Click"`), `Uncapitalize<S>`, `Uppercase<S>`, `Lowercase<S>`. They operate inside template literal types (`` `on${Capitalize<K>}` ``), distribute over unions member-wise, and emit nothing — the transformed strings exist only as types until values (already spelled that way in source) flow through them.

**What problem it solves / history** — derived string sets (handler names, HTTP verbs, CSS properties) previously lived as hand-listed unions (`"onClick" | "onKeyDown" | …`) that rotted whenever the source union changed — or as `string`, which accepted every typo. Intrinsics (TS 4.1, with template literal types) derive the set computationally: the event union is the single source, the cased table is a view, and drift is impossible by construction.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), derive cased string sets from source unions (`Capitalize<Event>` for handlers, `Uppercase<Method>` for verbs) instead of listing them. Apply intrinsics to *literal* inputs — over `string` they return `string` (no information to transform), which is correct but useless; the value comes from literal unions.

**Runnable example** — cased sets derived, typos rejected (good vs bad, `tsc --strict`):

```typescript
// good — handler names computed from the event union
type Ev = "click" | "keydown";
type Handler = `on${Capitalize<Ev>}`; // "onClick" | "onKeydown"
const h: Handler = "onClick";
console.log(h.toUpperCase()); // ONCLICK
// const bad: Handler = "onClik"; // error TS2322 — typo rejected against the computed set

// good — verbs normalized once, reused everywhere
type Verb = "get" | "post";
type Up = Uppercase<Verb>; // "GET" | "POST"
function serve(v: Up): string { return v === "GET" ? "read" : "write"; }
console.log(serve("GET")); // read

// bad — hand-listed cased union rots when the source grows
type HandlersListed = "onClick" | "onKeydown"; // mirrors Ev today...
// Ev gains "scroll" → Handler gains "onScroll"; HandlersListed silently lacks it
// fix — `on${Capitalize<Ev>}`: derivation tracks the union automatically
type H = `on${Capitalize<Ev | "scroll">}`; // "onClick" | "onKeydown" | "onScroll"
const h2: H = "onScroll";
console.log(h2); // onScroll
```

**Common confusion** — "intrinsics run at runtime" — zero emit; they constrain which *already-spelled* strings are assignable — the value `"onClick"` in source is an ordinary string literal. "`Capitalize<string>` gives `String`" — it gives `string` (passthrough on non-literals) — intrinsics need literal inputs to produce literal outputs. "`Uppercase` validates casing" — it *computes* the cased form; a lowercase value assigned to an `Uppercase` slot still errors — computation, not leniency.

**Performance note** — intrinsics distribute over union members (N literals → N computations, cached once per alias) — trivial for curated unions, expensive over 10k-member codegen unions — derive from curated sources, not raw generation output.

**Mentor note** — add `"scroll"` to `Ev` live and watch both `Handler` (adapts) and `HandlersListed` (rots) — derivation-vs-listing in one union member. Exercise: convert one hand-listed cased union in the codebase to its intrinsic derivation and delete the list — count deleted lines as ROI.

### 2) **Key generation at scale** (handler maps, route tables, prop families)

**Definition** — template literals scale key derivation from one-off renames to whole API surfaces: `` { [K in Ev as `on${Capitalize<K>}`]: Handler<K> } `` builds handler maps, `` `${Method} ${Path}` `` builds route tables, `` `${Prop}Changed` `` builds subscription keys — each a complete binding surface computed from small source unions, with per-key value types threaded through the same mapper.

**What problem it solves / history** — binding surfaces were the highest-rot interfaces in frontend codebases: every new event/route/prop needed a handler key, a route entry, and a subscription name in three places — one forgotten and the feature silently unwired (no error: `Record<string, …>` accepted the absence). Generated key sets make absence an error: the table *must* contain every derived key, so unwired features fail at compile time.

**Modern guidance** — as of TypeScript 5.9 era, generate binding tables from source unions with per-key value precision (handler per event with its payload, route per method+path with its params) — never `Record<string, SharedHandler>` where a derivation exists. Keep source unions curated (events, routes, props the team owns); derive tables freely from them.

**Runnable example** — unwired features become compile errors (good vs bad, `tsc --strict`):

```typescript
// good — every event gets a typed handler slot; missing slots error
type Ev2 = "click" | "keydown";
type Payload = { click: { x: number }; keydown: { key: string } };
type Table = { [K in Ev2 as `on${Capitalize<K>}`]: (p: Payload[K]) => void };
const t: Table = {
  onClick: (p) => console.log(p.x.toFixed(0)),
  onKeydown: (p) => console.log(p.key.toUpperCase()),
};
t.onClick({ x: 5 }); // 5
// const missing: Table = { onClick: (p) => console.log(p.x) }; // error TS2741 — onKeydown missing

// bad — stringly table accepts absence and mistypes payloads
const loose: Record<string, (p: unknown) => void> = {
  onClick: (p) => console.log(p), // payload unknown — per-event precision lost
}; // compiles — onKeydown absence invisible, payload untyped
// fix — Table: derived keys enforce presence AND per-key payload types
```

**Common confusion** — "generated tables need codegen tooling" — no build step: template literal types *are* the generator, running in `tsc`. "per-key values overcomplicate" — `(p: Payload[K])` threads each event's payload through the same mapper — one line buys per-key precision that `Record<string, Handler>` destroys. "exhaustive tables slow the IDE" — key generation caches per union (events × template = one entry); hover cost is linear in keys, fine under hundreds.

**Performance note** — table generation costs O(events) instantiations once — referencing `Table` 50 times reuses the cache. The cliff is cross-product tables (methods × paths × versions over codegen unions — 10k+ keys) — curate the source unions or split tables per domain.

**Mentor note** — delete `onKeydown` from `t` and read TS2741 together — "missing property" for a key nobody wrote is the magic moment for derivation skeptics. Exercise: add an event with a *new payload shape* and watch the handler's `p` parameter demand it — presence plus precision in one propagation.

### 3) **String unions as programs** (distributing transforms over literal sets)

**Definition** — a template literal over a union *is* a compile-time loop: `` `v${1|2}` `` evaluates per member (`"v1" | "v2"`), nested templates cross-product (`${A}-${B}` over two unions yields every pair), and conditionals inside filter (`A extends … ? … : never` sinks unwanted pairs). String-union algebra — concat, product, filter — replaces hand-enumerated string sets.

**What problem it solves / history** — versioned API paths (`/v1/users`, `/v2/users`), locale keys (`en.title`, `fr.title`), and permission strings (`read:docs`, `write:docs`) combinatorially exploded hand-listed unions (versions × resources × actions — hundreds of literals, each a typo risk and a maintenance line). Cross-product templates derive the full set from three small unions: add a version once, every path follows.

**Modern guidance** — as of TypeScript 5.9 era, derive combinatorial string sets from factor unions (versions, resources, actions) with one template per axis — never list the product. Filter illegal pairs with in-template conditionals (`IsValid<M, P> extends true ? … : never`) instead of post-hoc `Exclude` where the rule is structural. Keep factors small and curated — the product's size is the check cost.

**Runnable example** — product derived, illegal pairs sunk (good vs bad, `tsc --strict`):

```typescript
// good — versions × resources derived; admin-only pair filtered in-template
type V = "v1" | "v2";
type R = "users" | "health";
type Path = `/api/${V}/${R}`; // 4 paths from 2+2 factors
const p: Path = "/api/v2/users";
console.log(p.toUpperCase()); // /API/V2/USERS
function call(path: Path): string { return `called ${path}`; }
console.log(call("/api/v1/health")); // called /api/v1/health
// call("/api/v3/users"); // error TS2345 — v3 not in the factor union

// bad — hand-listed product rots per factor change
type PathsListed = "/api/v1/users" | "/api/v1/health" | "/api/v2/users" | "/api/v2/health";
// V gains "v3" → Path gains 2 members; PathsListed silently lacks them
// fix — `/api/${V}/${R}`: factors are the source of truth, the product is a view
```

**Common confusion** — "products validate runtime strings" — derivation constrains *literals*; dynamic strings (`/api/${v}/${r}` with `v: string`) still need runtime validation against the computed set (a guard or schema). "cross-products explode check time" — the product union's *size* is the cost (members = |A| × |B|) — keep factors small (versions × resources, not rows × columns of a dataset). "filter-in-template vs Exclude differ" — same result; in-template filtering documents the rule *at* the derivation, `Exclude` documents it *after* — prefer at-site for structural rules.

**Performance note** — product size multiplies downstream check cost (every function accepting `Path` checks against all members) — a 10k-path union as a parameter type slows every call site. Prefer factor-typed signatures (`call(v: V, r: R)`) with template assembly inside, over product-typed parameters, when the product exceeds hundreds.

**Mentor note** — grow one factor live (`"v3"`) and count the members before/after — multiplication made tangible. Exercise: express "admin paths only for v2" as an in-template conditional vs post-hoc `Exclude` — same set, different documentation site; discuss which survives the next factor change better.
