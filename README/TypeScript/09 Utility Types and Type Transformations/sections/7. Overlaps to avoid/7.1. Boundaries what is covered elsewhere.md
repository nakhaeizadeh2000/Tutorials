## 7.1. Boundaries — what is covered elsewhere

A type transformation computes a new contract from an existing type. It does not create a replacement object, remove a runtime property or validate a parsed value. This domain explains how mapped types, conditional types and extraction utilities produce a static result. Its neighbors establish the source shapes, generic relationships, live branch checks, collection design and tool configuration used by those transformations.

Choose an owner from the operation being questioned. An unexpected key set, a rejected tuple spread and a field required beyond a depth cap need different observations. The routes below point to published explanations; navigation does not certify every linked example or integration.

### 6) **Common confusion**

Pick does not delete object properties, Partial does not make an incomplete external payload valid, and Extract does not execute a discriminant check. A type's static keys can differ from observed own keys on a live value. If a mapped or conditional result is unexpected, inspect both its source type and its transform rule; if a runtime field access fails, follow the actual value and checks that produced it.

### 7) **Performance note**

These documentation boundaries have no direct runtime effect. Mapped/conditional annotations are erased; projection code, parsing, collection traversal and branch checks still execute if the implementation contains them. No additive checker-cost formula, transform-cache guarantee or universal tuple-size limit is established here. Use the [measurement workflow](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) for a real slow workload, and preserve the intended transformed contract when changing it.
