### 1) **Generic declaration mechanics** (sites, inference, constraints, `in`/`out`, recursion theory) — [08 Generics Deep Dive](<../../../08 Generics Deep Dive/README.md>)

**Definition** — where `<T>` may appear, how inference fills it, what `extends` unlocks, what `in`/`out` promise, and how recursion budgets work live in 08 — this domain *applied* those mechanics (mapped over `keyof T`, distributed naked `T`, recursed with caps) without re-teaching them.

**What problem it solves / history** — 08 owns "how do type parameters behave?"; 09 owns "what do I compute with them?" — the split keeps parameter theory (scope, variance, budgets) and transform selection (which utility when) each in one place, composed at use sites.

**Modern guidance** — for parameter questions (scope, constraint design, variance annotation, depth counters) start at the relevant 08 leaf; for transform questions (which utility, how implemented, where it breaks) stay here. The bridge leaves ([2.3. infer](<../../../08 Generics Deep Dive/sections/2. Conditional Types/2.3. infer pipelines ReturnType Parameters Awaited.md>), [3.2. Recursive generics](<../../../08 Generics Deep Dive/sections/3. Variance and Advanced Generic Patterns/3.2. Recursive generic types and self-referential patterns.md>) → [3.1. Deep transforms](<../3. Transformations in Practice/3.1. Deep transforms DeepPartial DeepReadonly and the budget.md>)) document the handoff.

**Runnable example** — 08 mechanic, 09 application (`tsc --strict`):

```typescript
// 08 owns the extraction mechanic (infer binding); 09 owns the catalog use
type El<T> = T extends Array<infer E> ? E : never; // 08 pattern, applied here
type Nums = El<number[]>; // number — mechanic (08) serving selection (09)
console.log("extracted");
function first<T>(xs: T[]): T | undefined { return xs[0]; } // 08 scope/inference owns this shape
console.log(first([1])?.toFixed(0) ?? "empty"); // 1
```

**Common confusion** — "09 replaces 08/2.3" — 09 *completes* it (preview → catalog); extraction theory (positions, distributivity interaction) stays in 08.

**Performance note** — no overlap means no duplicated budget guidance — 08 measures parameter mechanics, 09 measures transform applications; read both for recursive utilities.

**Mentor note** — route "why does `<T>` behave this way?" to 08 and "which transform computes this?" here — the question's verb (behave vs compute) picks the domain.

### 2) **Object-type composition primitives** (`&` vs `extends`, merging, `keyof`/`T[K]` queries) — [04 Objects, Interfaces and Type Aliases](<../../../04 Objects Interfaces and Type Aliases/README.md>)

**Definition** — object shape composition (`&` vs `extends` diagnostics, declaration merging, `keyof`/`T[K]`/`typeof` derivation groundwork) lives in 04 — this domain iterated those primitives at scale (mapped over `keyof T`, indexed with `T[K]`) without re-teaching them.

**What problem it solves / history** — transforms sit *atop* shape mechanics: `Partial<User>` needs 04's optionality semantics and `T[K]` lookup rules to be readable — linking (not copying) keeps each rule in its home domain, as 04/7.1's stop-list requires.

**Modern guidance** — design the shape in 04 first (freshness-safe, constructible, queried correctly), then transform it here (map, filter, derive) — shape before transform, always. For `keyof`/`T[K]` questions start at [2.3. Type queries](<../../../04 Objects Interfaces and Type Aliases/sections/2. Composition and Declaration Merging/2.3. Type queries on objects keyof indexed access and typeof capture.md>).

**Runnable example** — 04 shape, 09 transform (`tsc --strict`):

```typescript
// 04 owns the query primitive; 09 iterates it
interface Cfg { host: string; port: number; }
type K = keyof Cfg; // "host" | "port" — 04 groundwork
type V = { [P in K]?: Cfg[P] }; // 09 iteration over the 04 primitive
const v: V = { host: "h" };
console.log(v.host?.toUpperCase() ?? "none"); // H
```

**Common confusion** — "transforms need no shape rules" — freshness, `readonly`, and `T[K]` semantics all still apply *inside* every mapped instantiation — transforms add a layer, they do not replace the shape layer.

**Performance note** — shape checks (04) and transform checks (09) compose additively — keep shapes small *and* transforms cached.

**Mentor note** — review transforms in two passes (shape pass per 04, transform pass per 09) — mixed passes miss one layer's bugs.

### 3) **Union/intersection algebra and narrowing** (distributivity at shape level, discriminants, exhaustiveness) — [07 Unions, Intersections and Narrowing](<../../../07 Unions Intersections and Narrowing/README.md>)

**Definition** — `|`/`&` set algebra, discriminated-union design, and control-flow narrowing (`typeof`/`in`/`never`-sink exhaustiveness) live in 07 — this domain used them (`Exclude`/`Extract` over unions, `never` sinks, exhaustive switches over filtered sets) without re-teaching them.

**What problem it solves / history** — filters are *applications* of 07's algebra via 08's distribution mechanic, cataloged here — each domain owns its layer (algebra, mechanism, catalog) so the three compose instead of repeating. 07/2.3's `Exclude`/`Extract` echo explicitly forwards here for the real thing.

**Modern guidance** — model alternatives in 07 (discriminants, exhaustiveness), filter them here (`Exclude`/`Extract`), narrow the survivors with 07's guards — alternative → transform → narrow, in that order.

**Runnable example** — 07 algebra through the 09 catalog (`tsc --strict`):

```typescript
// 07: discriminated union + exhaustive sink; 09: filter feeding the switch
type Ev = { kind: "click"; x: number } | { kind: "key"; k: string } | { kind: "sys"; at: number };
type UserEv = Exclude<Ev, { kind: "sys" }>; // 09 filter over the 07 union
function assertNever(x: never): never { throw new Error("unhandled"); }
function handle(e: UserEv): string {
  if (e.kind === "click") return `x=${e.x}`;
  if (e.kind === "key") return `k=${e.k}`;
  return assertNever(e); // 07 exhaustiveness over the 09-filtered set
}
console.log(handle({ kind: "key", k: "Enter" })); // k=Enter
```

**Common confusion** — "filtering *is* narrowing" — filtering selects *types* at compile time; narrowing refines *values* along control flow — related, not identical; 07 owns the latter, this domain the former.

**Performance note** — filtered unions (09) feed narrower switches (07) — filter once upstream so every downstream `switch` checks fewer members.

**Mentor note** — teach the pipeline order explicitly (model → transform → narrow) — students who sequence the three domains stop building filters before modeling the union.

**Cross-links** — unions/narrowing → [07 Unions](<../../../07 Unions Intersections and Narrowing/README.md>); distributivity echo → [2.3. Distributivity](<../../../07 Unions Intersections and Narrowing/sections/2. Intersection Types/2.3. Unions and intersections distributive behavior and primitive intersections.md>).

**Modern guidance** — for tuple-shape questions (variadic generics, `as const` tuples, label preservation) await 10 when it lands — until then, 08/2.3 + 08/3.3 are the authoritative previews, and this domain's tuple examples link back to them.

**Runnable example** — 09 borrows tuple mechanics, 10 will own them (`tsc --strict`):

```typescript
// borrowed pattern (08 shape): head extraction; full tuple catalog lands in 10
type Head<T> = T extends [infer H, ...unknown[]] ? H : never;
const h: Head<["a", 1]> = "a";
console.log(h.toUpperCase()); // A
```

**Common confusion** — "tuple `infer` belongs to 09" — extraction *positions* were cataloged here as pipeline pieces; tuple *shapes* (variadic, readonly, labels) belong to 10 — position vs shape differ.

**Performance note** — tuple matching costs O(length) per use — fine for short heads/tails; 10 will budget long-tuple transforms.

**Mentor note** — tell students "you can *use* tuple extraction now; 10 teaches tuple *design*" — sets the expectation that 10 is construction, not re-teaching.

### 5) **Compiler strictness and emit flags** (`strict`, `--erasableSyntaxOnly`, `isolatedDeclarations`) — [13 Configuration and Compiler Options](<../../../13 Configuration and Compiler Options/README.md>)

**Definition** — `strict` (surfacing `unknown` fallbacks and `never` sinks), `--erasableSyntaxOnly` (mapped/conditional syntax passes — no `enum` trap in this domain), and `isolatedDeclarations` (explicit annotations on exported transforms) live in 13 — this domain verified every fence under `strict` without owning the flags.

**What problem it solves / history** — flag semantics belong with the compiler-options reference (13), not scattered across 20 domains — one home keeps `tsconfig` advice consistent as defaults evolve through TS 5.x into 6.0.

**Modern guidance** — develop transforms under `strict` (all examples verified so); take flag questions (which combination surfaces `unknown`? does `erasableSyntaxOnly` affect mapped syntax?) to 13 when it lands — until then, per-leaf verification notes are authoritative.

**Runnable example** — strict surfaces what lax hides (`tsc --strict`):

```typescript
// strictNullChecks ON: Partial leaves are undefined-checked (this domain assumes it throughout)
interface Cfg2 { host: string; port?: number; }
function portOf(c: Partial<Cfg2>): number {
  return c.port ?? 3000; // narrow required — strict surfaces the fallback
}
console.log(portOf({ host: "h" })); // 3000
```

**Common confusion** — "transforms need special flags" — they need `strict` (like everything) plus nothing else; `--erasableSyntaxOnly` already passes for all mapped/conditional syntax.

**Performance note** — `strict` adds check-time precision at zero emit cost — the catalog guidance here (cache, cap, name) assumes `strict` on.

**Mentor note** — standardize team `tsconfig` on `strict: true` before teaching transforms — unstrict utilities teach `any`-shaped habits that `strict` later punishes.
