## 2.1. Conditional fundamentals — distributive law and never branches

A conditional type chooses a result using a type relationship: A extends B ? X : Y selects X when A is assignable to B, otherwise Y. A generic conditional whose checked left operand is a bare type parameter has an additional behavior: it distributes over union inputs. This lets one declaration compute a result for each member, then combine those results as a union.

Use TypeScript 7.0.2 with strict, exact optional and unchecked-index checking enabled. The type-only files relations.ts and special.ts below are complete compile-time checks: run `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --target es2022 --module commonjs --lib es2022,dom --noEmit FILE.ts`. They have no runtime output; successful compilation checks their live assertions. Activate commented negatives separately to observe rejection. The runtime program has its own build/run command below.

### 1) **Find the checked parameter before predicting distribution**

For `type Classify<T> = T extends string ? "text" : "other"`, applying string | number is equivalent to Classify<string> | Classify<number>. Both branches occur, producing text | other. An ordinary concrete string | number comparison has no bare checked parameter and tests the union as a whole. The [primary conditional guide](https://www.typescriptlang.org/docs/handbook/2/conditional-types.html#distributive-conditional-types) demonstrates the rule and wrapped alternative.

Wrapping the checked T changes the operation. Wrapping only the pattern on the right does not: T extends [string] still distributes, now asking whether each member is a matching tuple. T extends readonly unknown[] also distributes; the array pattern is on the right. Inspect the left operand rather than searching the entire declaration for brackets.

Save as relations.ts.

```typescript
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Classify<T> = T extends string ? "text" : "other";
type Whole<T> = [T] extends [string] ? "text" : "other";
type Concrete = (string | number) extends string ? "text" : "other";
type ArrayKind<T> = T extends readonly unknown[] ? "array" : "other";
type RightWrapped<T> = T extends [string] ? "tuple" : "other";
type ArrayOnLeft<T> = T[] extends string[] ? "text" : "other";
type Filter<T> = T extends string ? never : T;
type Expand<T> = T extends unknown ? T[] : never;
type D = Expect<Equal<Classify<string | number>, "text" | "other">>;
type W = Expect<Equal<Whole<string | number>, "other">>;
type C = Expect<Equal<Concrete, "other">>;
type A = Expect<Equal<ArrayKind<readonly number[] | "x">, "array" | "other">>;
type R = Expect<Equal<RightWrapped<[string] | number>, "tuple" | "other">>;
type L = Expect<Equal<ArrayOnLeft<string | number>, "other">>;
type F = Expect<Equal<Filter<"a" | 1 | "b" | true>, 1 | true>>;
type E = Expect<Equal<Expand<string | number>, string[] | number[]>>;
// type WrongArrayRule = Expect<Equal<ArrayKind<number[] | string>, "other">>; // TS2344
// const widened: Filter<"a" | 1 | true> = 2; // TS2322: the survivor is literal 1, not all numbers
// const mixed: Expand<string | number> = ["a", 1]; // TS2322: union of arrays differs from array of a union
```

The eight probes compare exact claimed results. In particular, the filter retains literal 1 and true; it does not widen them to every number and boolean. Expand distributes into string[] | number[], whose members each describe a homogeneous array. A nondistributive form returning (string | number)[] would permit the mixed array instead.

There is no member ordering in the resulting union to use as a runtime iteration order. Nor does a right-side tuple pattern turn a bare checked T into a whole-union test. [Infer matching](<../../../08 Generics Deep Dive/sections/2. Constraints Defaults and Inference Control/2.3. infer conditional inference and distributive preview.md>) previews these mechanics; this owner applies them to complete filtering and boundary cases.

### 2) **Use never as a type-level filter without inventing runtime filtering**

A never result contributes no member to a union: A | never simplifies to A. Exclude keeps nonmatching members and Extract keeps matching ones by choosing T or never in opposite branches. Returning an inhabited sentinel instead deliberately produces another member; it is a different operation, not removal.

A filter whose entire result is never may correctly describe an empty set of admissible values. It is not automatically a broken declaration. A value of type never can also be assigned to other types; the rejected operation is constructing an ordinary value where never is required. The [never owner](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.3. never and void bottom vs deliberate nothing.md>) explains the assignment direction.

Save as filtering.ts. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist filtering.ts`, then run `node dist/filtering.js` with Node.js 20.20.2.

```typescript
type Status = "draft" | "published" | "archived";
type Active = Exclude<Status, "archived">;
type KeepString<T> = T extends string ? T : never;
type KeepWithSentinel<T> = T extends string ? T : "dropped";
const statuses: Status[] = ["draft", "archived", "published"];
// const rejected: Active[] = statuses; // TS2322
const asserted = statuses as Active[]; // Accepted assertion; the array has not changed.
console.log(asserted.join(","));
function unexpected(value: never): never { throw new Error(`unsupported: ${String(value)}`); }
function label(status: Active): string {
  switch (status) {
    case "draft": return "D";
    case "published": return "P";
    default: return unexpected(status);
  }
}
try { console.log(asserted.map(label).join(",")); }
catch (error) { console.log(error instanceof Error ? error.message : "unexpected error"); }
const filtered = statuses.filter(status => status !== "archived");
console.log(filtered.map(label).join(","));
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Filtered = Expect<Equal<typeof filtered, Active[]>>;
type Empty = Expect<Equal<KeepString<1 | true>, never>>;
type Sentinel = Expect<Equal<KeepWithSentinel<"draft" | 1>, "draft" | "dropped">>;
// const impossible: KeepString<1 | true> = 1; // TS2322
```

The output is `draft,archived,published`, `unsupported: archived`, then `D,P`. The assertion changes the static view while retaining the same runtime array. The filter callback actually removes archived, and this toolchain infers its narrowing predicate. The three probes check the filtered array and two purely static results; they perform no array mutation themselves.

Use a type-level filter to compute a contract, and actual value checks to establish which runtime inputs satisfy it. [Custom narrowing](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.3. Custom narrowers predicates asserts and type guards on unions.md>) owns inferred/explicit predicate guarantees. [Standard utilities](<./2.2. Exclude Extract NonNullable Pick Omit under the hood.md>) owns the full catalog, including why filtering a union is different from selecting object properties.

### 3) **Test empty, unknown and unchecked inputs deliberately**

A bare distributive conditional applied to never has no union members to evaluate and produces never. Wrapping the checked type permits a whole-type question: [never] extends [never] is true. The same wrapper can change behavior for any: a bare conditional can combine both branch results for any, while the wrapped comparison below chooses its true branch.

A whole-type assignability question is not a general equality test. Ordinary mutable and readonly object-property views can be mutually assignable, even though the probe used here distinguishes their declarations. Names such as Equal and IsAny are project helpers, not built-in standard-library utilities. State the relationship each helper actually checks and test its edge cases.

Save as special.ts.

```typescript
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type BadNever<T> = T extends never ? true : false;
type IsNever<T> = [T] extends [never] ? true : false;
type IsAny<T> = 0 extends (1 & T) ? true : false;
type Classify<T> = T extends string ? "text" : "other";
type Whole<T> = [T] extends [string] ? "text" : "other";
type Mutual<A, B> = [A] extends [B] ? [B] extends [A] ? true : false : false;
type N0 = Expect<Equal<BadNever<never>, never>>;
type N1 = Expect<Equal<IsNever<never>, true>>;
type N2 = Expect<Equal<IsNever<string | never>, false>>;
type A0 = Expect<Equal<IsAny<any>, true>>;
type A1 = Expect<Equal<IsAny<unknown>, false>>;
type A2 = Expect<Equal<IsAny<never>, false>>;
type B0 = Expect<Equal<Classify<any>, "text" | "other">>;
type B1 = Expect<Equal<Whole<any>, "text">>;
type B2 = Expect<Equal<Classify<unknown>, "other">>;
type B3 = Expect<Equal<Classify<never>, never>>;
type B4 = Expect<Equal<Whole<never>, "text">>;
type Writable = { id: number };
type ReadOnly = { readonly id: number };
type M = Expect<Equal<Mutual<Writable, ReadOnly>, true>>;
type Distinct = Expect<Equal<Equal<Writable, ReadOnly>, false>>;
// const answer: BadNever<never> = true; // TS2322
// type WrongEquality = Expect<Equal<Equal<Writable, ReadOnly>, true>>; // TS2344
```

Thirteen live assertions compile. IsAny uses the special intersection behavior of any: intersecting it with 1 still yields any, while an ordinary 1 type does not accept 0. Its checked operand is the concrete literal 0, so it is not a naked-T distributive test. This helper asks a specialized question; a tuple wrapper alone would not establish that answer.

Whole<never> is text because never is assignable to string in this wrapped test. That does not mean an actual string exists in an empty result. Choose an explicit emptiness policy before applying a whole-type property to a possibly empty input. For exact type-test requirements, use the [type-testing owner](<../../../17 Testing Types/sections/1. Type Assertions in Tests/1.1. Expect Equal and compile-time type assertions.md>) and verify the helper's supported relationships rather than treating mutual assignment as universal identity.

### 4) **Common confusion**

Distribution depends on the checked left parameter, not the presence of brackets or an array anywhere in the declaration. A union of arrays and an array of union elements describe different accepted values. Replacing T with [T] changes the question and can change any/never outcomes as well; it is not a universally transparent operation.

Never drops from a type union without deleting runtime values or code. An empty filtered type can be intentional. Conversely, an unchecked assertion can supply a static active view while leaving archived in the array, as the actual failure demonstrates.

### 5) **Performance note**

Conditional aliases and live probes erase. The runtime example retains its array, assertion-free emitted assignment, filter callback, map calls and throwing branch. Distribution and wrapping can produce different contracts; neither promises a universal checking speed advantage. A whole-type assignability comparison can still examine a large structure, so describing it as O(1) is unjustified. Use [diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) for actual cost evidence.

### 6) **Mentor note**

Ask the learner to mark the checked operand, expand a two-member input, then predict never and any separately. Require an explanation of why asserted still contains archived before executing it. That distinguishes type computation from a value transformation.

For practice, write AllArrayTypes<T> that returns false for never, true when every member of a nonempty type union is assignable to readonly unknown[], and false otherwise. First use IsNever to apply the explicit empty-input policy, then use a wrapped whole-type check. Verify readonly number[] | string[] gives true, number[] | string gives false, unknown gives false and never gives false. This exercise concerns a nonempty union of types, not whether any runtime array contains elements; an empty runtime array still satisfies an array type. Handling any would need its own chosen policy.
