## 2.3. `infer` pipelines — `ReturnType`, `Parameters`, `Awaited`

### 1) **Function utilities under the hood** (one `infer` pattern each)

**Definition** — three stdlib lines from [08's four `infer` sites](<../../../08 Generics Deep Dive/sections/2. Constraints Defaults and Inference Control/2.3. infer conditional inference and distributive preview.md>): `ReturnType<F> = F extends (...args: never[]) => infer R ? R : never`, `Parameters<F> = F extends (...args: infer P) => unknown ? P : never`, `ConstructorParameters<T> = T extends abstract new (...args: infer P) => unknown ? P : never`. Each matches the wrapper shape, names the hole, returns the name — the mechanic 08 taught, applied to the catalog.

**What problem it solves / history** — pre-utility code read function metadata through overloads or `any`-typed helpers (`fn(...args: any[])` wrappers that laundered arity, `result: any` for unwrapped returns) — every wrapper was a checking hole. The `infer` utilities made metadata *computed*: `Parameters<typeof handler>` types the forwarder, `ReturnType<typeof parse>` types the cache — both track the source function through refactors instead of mirroring it.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), type wrappers from the wrapped function (`Parameters<typeof fn>` for forwarders, `ReturnType<typeof fn>` for result storage, `ConstructorParameters<typeof C>` for factories) — never mirror signatures by hand. Constrain utility inputs (`F extends (...args: never[]) => unknown`) so non-functions error at the call site instead of sinking to `never` silently.

**Runnable example** — metadata computed, never mirrored (good vs bad, `tsc --strict`):

```typescript
// good — forwarder and cache track the source function through refactors
function fetchUser(id: string, verbose: boolean): Promise<{ id: string }> {
  void verbose;
  return Promise.resolve({ id });
}
function logged(...args: Parameters<typeof fetchUser>): ReturnType<typeof fetchUser> {
  console.log("fetch", args[0]);
  return fetchUser(...args);
}
console.log("logged-arity:", logged.length); // 2 — arity tracked, not mirrored
// logged("u1"); // error TS2554 — missing verbose caught through Parameters

// bad — mirrored signatures rot when the source gains a parameter
function loggedBad(id: string): Promise<{ id: string }> { // mirrors fetchUser v1...
  console.log("fetch", id);
  return fetchUser(id, false);
}
// fetchUser gains `verbose` → loggedBad silently drops it (stale mirror, no error)
// fix — Parameters<typeof fetchUser>: the wrapper tracks the source automatically
void loggedBad;
```

**Common confusion** — "`ReturnType` of an overload gives all overloads" — it returns the *last* (implementation) signature's return — overloads resolve at the call, `ReturnType` reads the declaration tail; for overload precision, reference the specific call shape instead. "`Parameters` on a generic function instantiates it" — `Parameters` of `<T>(x: T) => T` is `[x: unknown]` (erased to constraint) — genericity does not survive metadata extraction; forward generics with `<T extends unknown[]>` rest capture instead (see [3.3. Variadic tuples](<../../../08 Generics Deep Dive/sections/3. Variance and Advanced Generic Patterns/3.3. Variadic tuple generics pipe concat and rest capture.md>) in 08). "non-function input errors loudly" — it sinks to `never` (false branch) — constrain inputs to fail fast.

**Performance note** — metadata utilities cache per function type (one instantiation each) — `Parameters<typeof fn>` referenced 20 times computes once. Cost appears only when applied to *enormous* overload sets (DOM APIs with 50 signatures) — extract once into a named alias at module scope.

**Mentor note** — refactor-drill: add `verbose` to `fetchUser` and watch `logged` adapt while `loggedBad` rots — the mirror-tax made visible in one parameter. Review gate: hand-mirrored wrapper signatures (`(id: string) => …` copying a source) must become `Parameters`/`ReturnType` derivations.

### 2) **`Awaited` as recursive conditional** (the stdlib's canonical recursion)

**Definition** — `Awaited<T> = T extends null | undefined ? T : T extends object & { then(onfulfilled: infer F, ...args: infer _): unknown } ? F extends (value: infer V, ...args: infer _) => unknown ? Awaited<V> : never : T` (simplified: unwrap `then`-ables recursively, pass through everything else, preserve `null`/`undefined`). The real lib source adds native-`Promise` fast paths, but the shape is: match → extract `V` → recurse `Awaited<V>` → stop at non-thenables.

**What problem it solves / history** — nested async (`Promise<Promise<User>>` from chained `then`, `Promise<Promise<…>>` from generic middleware) previously needed manual per-level unwrapping (`p.then(u => u.then(…))` typed by hand) — each nesting level was a new type annotation. `Awaited` (TS 4.5) computes the terminal payload regardless of depth: `async`/`await` desugaring, `Promise.all` results, and middleware chains all bottom out through it.

**Modern guidance** — as of TypeScript 5.9 era, unwrap payloads with `Awaited` (never hand-recurse `Promise<infer V>` chains unless teaching); type middleware generically as `<T>(p: Promise<T>) => Promise<Awaited<T>>` so arbitrary nesting collapses. Recognize the recursion shape (match → recurse → base) — it is the template for every project-level deep unwrap (`DeepAwaited` over custom `Task<T>` wrappers).

**Runnable example** — depth-independent unwrapping (good vs bad, `tsc --strict`):

```typescript
export {}; // module marker for top-level await in this runnable snippet
// good — Awaited bottoms out regardless of nesting depth
type P1 = Awaited<Promise<string>>; // string
type P2 = Awaited<Promise<Promise<number>>>; // number — recursed twice
const a: P1 = "hi";
const b: P2 = 7;
console.log(a.toUpperCase(), b.toFixed(0)); // HI 7

// good — middleware collapses arbitrary nesting through Awaited
async function collapse<T>(p: Promise<T>): Promise<Awaited<T>> { return await p; }
console.log(await collapse(Promise.resolve(Promise.resolve(42))).then((v) => v.toFixed(0))); // 42

// bad — manual per-level unwrap rots at the next nesting
type Once<T> = T extends Promise<infer V> ? V : T; // one level only
type O = Once<Promise<Promise<string>>>; // Promise<string> — still wrapped, downstream .toUpperCase errors
// const o: O = "hi"; // error TS2322 — Promise<string> is not string
// fix — Awaited<T>: recurse to the base instead of unwrapping once
const fixed: Awaited<Promise<Promise<string>>> = "hi";
console.log(fixed.toUpperCase()); // HI
```

**Common confusion** — "`Awaited` executes the promise" — purely static; unwrapping the *type* never touches runtime timing. "`Awaited<null>` is `never`" — `null`/`undefined` pass through (first branch preserves them) — only non-thenables pass through *and* thenables recurse; nullables are deliberately transparent. "custom `Task<T>` wrappers work with `Awaited`" — only `then`-shaped (has callable `then`) types unwrap — structurally foreign wrappers need their own recursive alias modeled on this shape.

**Performance note** — recursion depth equals promise nesting (almost always 1–2 — trivially cached). Pathological `Promise<Promise<…>>` × 50 (generated middleware types) hits the same TS2589 budget as any deep recursion — cap or flatten (see [3.2. Recursive generics](<../../../08 Generics Deep Dive/sections/3. Variance and Advanced Generic Patterns/3.2. Recursive generic types and self-referential patterns.md>) in 08).

**Mentor note** — trace `Awaited<Promise<Promise<string>>>` two levels on the board (match → `V = Promise<string>` → recurse → match → `V = string` → base) — then ask for the *shape* of the rule (match/recurse/base) rather than the code. Exercise: write `DeepArray<T>` (unwrap nested arrays) by analogy — transfer proven in one alias.

### 3) **Composing pipelines** (stacking extraction without intermediate aliases)

**Definition** — `infer` utilities compose by nesting: `Awaited<ReturnType<typeof fetchUser>>` reads inside-out (call shape → return promise → payload type) with no temporary alias. Each layer preserves structure (tuple stays tuple, promise stays promise until unwrapped), so the pipeline's hover shows the terminal type while every intermediate remains navigable via go-to-definition.

**What problem it solves / history** — intermediate-alias style (`type R = ReturnType<F>; type P = Awaited<R>; type E = ElemOf<P>`) scattered one pipeline across three declarations that reviewers had to mentally re-zip — and each alias invited reuse-in-wrong-context (someone importing `R` for a different purpose). Single-expression pipelines keep the derivation local to its use: read inside-out once, no shared temporaries to misuse.

**Modern guidance** — as of TypeScript 5.9 era, nest two-to-three extraction layers inline at the use site (`Awaited<ReturnType<typeof f>>`, `ElemOf<Parameters<typeof f>[0]>`); extract a named alias only when the *same pipeline* repeats (3+ uses) or exceeds three layers (readability cliff). When pipelines fail, unroll one layer at a time (hover each nesting level) — the faulty layer is always exactly one `infer` match away.

**Runnable example** — nested extraction, debugged layer by layer (good vs bad, `tsc --strict`):

```typescript
// good — inside-out pipeline: function → promise → payload, no temporaries
declare function listUsers(): Promise<{ id: string }[]>;
type User = Awaited<ReturnType<typeof listUsers>>[number]; // { id: string }
const u: User = { id: "u1" };
console.log(u.id.toUpperCase()); // U1

// good — unrolling finds the faulty layer (each hover is one match)
type L0 = typeof listUsers; // () => Promise<{id}[]> — layer 0: the source
type L1 = ReturnType<L0>; // Promise<{id}[]> — layer 1: infer R matched
type L2 = Awaited<L1>; // {id}[] — layer 2: recursion bottomed out
const check: L2[number] = { id: "u2" };
console.log(check.id); // u2

// bad — shared temporaries leak across contexts
type TempR = ReturnType<typeof listUsers>; // "temporary" that three files now import...
// fix — inline the pipeline at its (single) use; name it only on third reuse
```

**Common confusion** — "nesting hurts performance" — each layer caches independently; the composed reference reuses all three caches — identical cost to the aliased form. "pipelines hide intent" — past three layers they do (name them); at two layers the inside-out reading *is* clearer than chasing aliases across files. "`[number]` after `Awaited` distributes" — indexing is not conditional — no distribution; element access on the resolved array, one step, no fork.

**Performance note** — composed pipelines share per-layer caches with every other use of those layers (`ReturnType<typeof listUsers>` computed once even inside five different pipelines) — nesting *improves* cache sharing versus bespoke single-purpose aliases.

**Mentor note** — the unrolling drill (L0 → L1 → L2 hovers) is the debugging skill for every "pipeline gives something weird" report — teach it before the pipelines get deep. Rule: name on third reuse, nest before that; review any 4+-layer inline pipeline as a naming candidate.
