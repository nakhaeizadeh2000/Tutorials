## 2.2. `Exclude`, `Extract`, `NonNullable`, `Pick`, `Omit` — under the hood

### 1) **One-line implementations** (stdlib sources as distributive applications)

**Definition** — four stdlib lines every TypeScript developer should read once: `Exclude<T, U> = T extends U ? never : T` (drop matches), `Extract<T, U> = T extends U ? T : never` (keep matches), `NonNullable<T> = T & {}` (drop `null`/`undefined` — built on intersection, not conditional), `Pick<T, K extends keyof T> = { [P in K]: T[P] }` (rebuild from a key subset). `Omit<T, K> = Pick<T, Exclude<keyof T, K>>` composes two of them.

**What problem it solves / history** — stdlib utilities felt like compiler magic ("how does `Exclude` *know*?") until developers read the one-line sources and recognized 2.1's mechanics — naked distribution plus `never` sink plus homomorphic mapping. Reading the sources converts the catalog from memorization (which utility for which job) into derivation (which one-liner composes from primitives).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), read each source once (hover the stdlib name — the IDE shows the body), then *use names, not bodies* at call sites. Reimplement locally only when the stdlib shape mismatches (custom `ExtractByKind`, `OmitDeep`) — and even then, compose stdlib pieces (`Pick` + `Exclude`) before writing raw conditionals.

**Runnable example** — sources recognized in action (good vs bad, `tsc --strict`):

```typescript
// good — Exclude drops, Extract keeps: same mechanic, swapped branches
type Status = "idle" | "loading" | "done" | "archived";
type Live = Exclude<Status, "archived">; // "idle" | "loading" | "done"
type Done1 = Extract<Status, "done" | "archived">; // "done" | "archived"
const l: Live = "idle";
console.log(l.toUpperCase()); // IDLE

// good — Omit composes Pick + Exclude: no new primitive involved
interface Doc { id: string; title: string; secret: string; }
type Safe = Omit<Doc, "secret">; // Pick<Doc, Exclude<"id"|"title"|"secret", "secret">>
const s: Safe = { id: "1", title: "t" };
console.log(s.title.toUpperCase()); // T

// bad — hand-rolled filter that accidentally distributes (or fails to)
type DropBad<T, U> = [T] extends [U] ? never : T; // wrapped: whole-union test, NOT a filter
type D = DropBad<"a" | 1, string>; // "a" | 1 — nothing dropped (whole union isn't string)
// fix — Exclude<T, U>: naked distributes per member; use the name, not the almost-right copy
type DGood = Exclude<"a" | 1, string>; // 1 — dropped per member
const dg: DGood = 1;
console.log(dg.toFixed(0)); // 1
```

**Common confusion** — "`Omit` distributes" — `Omit` maps keys (non-distributive over the *object*; distributes only if `T` itself is a union passed naked — `Omit<A|B>` maps the union member-wise because `Pick`'s parameter is naked — usually desired, occasionally surprising with divergent members). "`NonNullable` is conditional" — `T & {}` (intersection with the non-null object-ish set) — different primitive, same outcome; `null`/`undefined` are not assignable to `{}`. "`Extract` widens survivors" — survivors keep their exact member types (`Extract<"a"|"b", string>` is `"a"|"b"`, not `string`) — filtering never widens.

**Performance note** — stdlib utilities cache per instantiation like any generic — `Exclude<BigUnion, X>` referenced 30 times computes once. Hand-rolled copies (`DropBad`-shaped) create *separate* cache entries per alias — prefer the canonical name so instantiations share across files.

**Mentor note** — hover each stdlib name once as a team exercise (the bodies are one line — the "magic" evaporates in a minute). Then ask which of `Exclude`/`Omit` distributes *over what* — members vs keys — the answer predicts every surprise in this leaf. Review gate: hand-rolled one-line conditionals that duplicate stdlib names must be replaced by the names.

### 2) **Union filters vs object pickers** (different primitives, often confused)

**Definition** — *union filters* (`Exclude`, `Extract`, `NonNullable`) take a union and return a sub-union — members in, members out, keys untouched. *Object pickers* (`Pick`, `Omit`, `Record`) take an object (plus a key set) and return a reshaped object — keys in, keys out, members transformed. Confusing them (`Exclude` on object keys, `Omit` on union members) compiles into nonsense instead of erroring loudly.

**What problem it solves / history** — `Omit<StatusUnion, "archived">` (picker on a union) and `Exclude<User, "secret">` (filter on an object) were the two most common utility misuses in code review — `Omit` over a union distributes `Pick` per member into a reshaped-union surprise, while `Exclude` over an object tests whole-object assignability and usually returns the input unchanged. Naming the categories turns both into caught-at-authorship errors: unions filter, objects pick.

**Modern guidance** — as of TypeScript 5.9 era, filter unions (`Exclude<Status, "archived">`), pick objects (`Pick<User, "id">`, `Omit<Doc, "secret">`), and convert explicitly at the boundary (`Exclude<keyof T, K>` bridges object keys into a filterable union — exactly how `Omit` is built). When the input kind is itself generic, constrain it (`T extends object` → pick; naked `T` union → filter) so misuse errors at the call site.

**Runnable example** — right tool per input kind (good vs bad, `tsc --strict`):

```typescript
// good — filter the union, pick the object: each primitive on its own kind
type Ev = "click" | "key" | "scroll";
type NoScroll = Exclude<Ev, "scroll">; // "click" | "key" — union in, union out
interface Cfg { host: string; port: number; secret: string; }
type Pub = Pick<Cfg, "host" | "port">; // object in, reshaped object out
const p: Pub = { host: "h", port: 80 };
console.log(p.host.toUpperCase(), p.port.toFixed(0)); // H 80

// bad — picker on a union: constraint rejects it at the declaration
// type BadPick = Pick<Ev, "click">; // error TS2344 — "click" is not among keyof Ev (string methods); caught!
// const bp: BadPick = ... // declaration itself fails: constraint K extends keyof T rejects
// bad — filter on object keys without the keyof bridge:
type Keys = keyof Cfg; // "host" | "port" | "secret" — bridge FIRST, then filter
type PubKeys = Exclude<Keys, "secret">; // "host" | "port"
const pk: PubKeys = "host";
console.log(pk.toUpperCase()); // HOST
```

**Common confusion** — "`Omit` on a union filters members" — `Omit<A | B, K>` applies `Pick` to *each member* (distributes via naked `T` inside `Pick`) — result is a union of reshaped members, not a filtered union — use `Exclude` to drop members. "`Pick` requires a union of keys" — `K extends keyof T` accepts one key too (`Pick<Cfg, "host">`) — single-key picks are the norm for projections. "bridge-then-filter is ceremony" — `Exclude<keyof T, K>` *is* `Omit`'s documented implementation — the bridge is the pattern, not boilerplate.

**Performance note** — pickers cost O(keys) per instantiation; filters cost O(members) — both cached. `Omit` over a *union of objects* multiplies (members × keys) — pre-filter members with `Exclude` first when only some variants need reshaping.

**Mentor note** — the two-line mantra ("unions filter, objects pick") resolves 90% of utility-choice questions — print it on the review checklist. Exercise: hand each misfire (`Omit` on union, `Exclude` on object) and ask for the category error before compiling — builds kind-first thinking that outlasts any catalog.

### 3) **When the stdlib name beats a hand-rolled conditional** (readability, hover, accidents)

**Definition** — prefer `Exclude`/`Pick`/`Awaited`/`ReturnType` over equivalent hand-rolled conditionals at call sites — three reasons: readers recognize names instantly, hovers render names compactly (custom conditionals expand into unreadable branches), and hand-rolled filters risk the accidental-distribution fork (`[T]` vs naked) that stdlib names already got right.

**What problem it solves / history** — codebases with `FilterStrings<T>`, `DropNull<T>`, `GetReturn<F>` aliases (each one line from stdlib equivalents) paid three taxes: onboarding readers learned N private names instead of 4 public ones, hovers expanded custom branches instead of showing `Exclude<…>`, and one alias in six had a naked/wrapped fork the author never intended — caught only when a new union member behaved unexpectedly.

**Modern guidance** — as of TypeScript 5.9 era, the rule is: call sites use stdlib names; custom aliases exist only for *new* semantics (`ExtractByKind`, `OmitDeep`, `PublicKeys<T>`) — and those compose stdlib pieces (`Pick<T, Exclude<keyof T, K>>`) rather than raw `extends` where possible. When raw conditionals are genuinely needed (recursive transforms, template Brand checks), comment the naked-or-wrapped intent on the line.

**Runnable example** — name vs copy (good vs bad, `tsc --strict`):

```typescript
// good — stdlib names: recognized, compact hover, no fork risk
type S1 = Exclude<string | number, string>; // number — every reader knows this line
type R1 = ReturnType<() => boolean>; // boolean — one name, zero branches to audit
console.log("named");

// bad — private copies with identical bodies plus one accidental fork
type MyExcl<T, U> = T extends U ? never : T; // identical to Exclude — private name tax
type MyExclWrapped<T, U> = [T] extends [U] ? never : T; // forked: whole-union, NOT a filter
type W = MyExclWrapped<"a" | 1, string>; // "a" | 1 — silently unfiltered; Exclude gives 1
const w: Exclude<"a" | 1, string> = 1; // fix — the name that already got it right
console.log(w.toFixed(0)); // 1
```

**Common confusion** — "custom names document intent better" — `Exclude<Status, "archived">` *is* the documented intent; `DropArchived<Status>` hides the mechanic behind a name every new hire must look up. "stdlib can't express my filter" — compose first (`Pick` + `Exclude` + `Extract` cover most "custom" filters); write raw conditionals only for recursion, template inference, or arity shapes. "hover expansion doesn't matter" — expanded custom branches in a 50-file refactor review hide the one-line change that matters — names keep diffs readable.

**Performance note** — canonical names share instantiation caches across files (`Exclude<X, Y>` computed once repo-wide); private copies fragment the cache per alias — N copies of the same filter check N times. Names are a performance practice, not just style.

**Mentor note** — grep custom one-line conditionals quarterly and delete those matching stdlib bodies — each deletion removes a fork risk and a cache fragment. Exercise: present `MyExclWrapped` without comment and ask for the result on `"a" | 1` — the wrong guess ("`1`") teaches why names beat copies. Hiring signal: candidates reaching for `Exclude` before `extends` know the catalog; candidates hand-rolling first know the syntax.
