## 1.1. What TypeScript Is vs JavaScript (erasable types)

### 1) **Definition** (TS is JS plus static types erased at emit)

**Definition** — TypeScript is JavaScript with a static type system that is *erased* before runtime. Every valid JavaScript program is a valid TypeScript program (with `allowJs`/no type errors), but TypeScript adds syntax for describing shapes (`: string`, `interface`, `<T>`) that the compiler checks and then removes when emitting `.js`.

- Types exist only at compile time. There is no `typeof` reflection for interfaces at runtime.
- Emit is pure JavaScript — runnable anywhere JS runs. Source maps reconnect emitted JS to `.ts` for debugging.

```typescript
// erasable: this compiles to plain JS with all annotations removed
type User = { id: string; name: string };

function greet(u: User): string {
  return `Hi ${u.name}`;
}

const u: User = { id: "1", name: "Ava" };
console.log(greet(u)); // Hi Ava

// emitted JS (tsc):
// function greet(u) { return `Hi ${u.name}`; }
// const u = { id: "1", name: "Ava" };
```

### 2) **Problem** (why JS alone fails at scale)

Plain JS fails predictably as codebases grow:

- **No contract at boundaries** — a function that expects `{ id: string }` will accept `null` until it crashes at `user.id` in production. In JS the bug surfaces at runtime; in TS it surfaces at edit time.
- **Refactoring without tools is guesswork** — renaming `userName` → `displayName` in JS relies on find-and-replace; in TS the compiler lists every mismatch.
- **Docs drift** — JSDoc comments describe intent but are not checked; types *are* the checked docs.

```typescript
// bad: JS-style — error hides until runtime
function getDisplayName(user: any) {
  return user.displayName; // any hides missing prop; passes type-check, fails at runtime if wrong shape
}

// good: precise type — error at author time
type UserV2 = { displayName: string };
function getDisplayName2(user: UserV2): string {
  return user.displayName;
}
getDisplayName2({ displayName: "Ada" }); // ok
// getDisplayName2({ name: "Ada" }); // error: Property 'displayName' is missing
```

### 3) **Modern** (TS 5.6 era, handbook view)

**Modern guidance** (TypeScript 5.6 era, August 2026):

- Treat TS as a *type checker*, not a runtime. Use `tsc --noEmit` (or `tsc --build`) for checking; use `tsc` / `esbuild` / `swc` only for emit. The handbook's mental model is explicit: "types are erased."
- Prefer **erasable-only** features. Avoid emit-dependent features that behave differently under `isolatedModules` (e.g., `const enum` cross-file inlining, legacy `namespace` that emits IIFE). See [2.2. Erasure and Emit](<../2. Mental Model — Structural Types and Erasure/2.2. Erasure and Emit no runtime types.md>) and [3.1. tsc, tsx and ts-node](<../3. Toolchain First Look/3.1. tsc tsx and ts-node Overview when to use which.md>).
- As of 5.6: `moduleResolution: "bundler"` / `"node16"` ("nodenext") are the only modern choices for ESM-aware projects; `esModuleInterop` remains required for many CJS libs — see domain `07` for resolution. Declaration emit (`declaration: true`) is the contract for libraries.

### Common confusion

- "TS runs at runtime" — no. Only emitted JS runs. Any code that tries `if (x is User)` at runtime without a predicate or validation library will always be wrong.
- "TS is slower at runtime because of types" — erased types have zero runtime cost; observed slowdowns come from emitted helpers (`__extends`, `useDefineForClassFields`) or bad `target`, not from annotations.

### Performance note

Erasable types are zero-cost at runtime but checklist-time cost matters: project with `skipLibCheck: false` and thousands of `.d.ts` can add seconds to `tsc`. Keep `skipLibCheck: true` for apps, enable for libs publishing types.

### Mentor note

Teach erasure first, before any syntax. Show side-by-side `.ts` → `.js` emit in the playground. Once students *see* that `interface` disappears, they stop expecting runtime type guards and start reaching for discriminants/Zod (see domain `10`).

**Good vs bad:** bad — `const x: MyInterface = JSON.parse(s) as MyInterface` (lies to compiler); good — `const x = MySchema.parse(JSON.parse(s))` (validates at runtime, then types flow).
