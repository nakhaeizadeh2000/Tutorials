## 1.2. Why Types Matter (correctness, docs, refactoring)

### 1) **Tradeoff** (strictness vs velocity)

**Definition** — Types trade a small upfront cost (writing annotations, fixing checker errors) for a large downstream gain: fewer production bugs, checked documentation, and safe refactoring. At small scale or exploratory prototyping the tax can outweigh the benefit; past ~5k lines or >2 contributors the gain dominates — every datum the handbook leads with.

- **Velocity story**: untyped code writes faster for 30 minutes; typed code changes faster for 30 months. The compiler is a persistent reviewer that never sleeps.
- **When to be strict**: new apps, libraries, teams >1, any code with runtime boundaries (API payloads, DB rows). When to relax: throwaway scripts, one-off migrations — even there `// @ts-check` + JSDoc recovers most value without full TS.

```typescript
// without types — rename breaks silently
// function formatPrice(price) { return `$${price.value}`; }
// formatPrice({ val: 10 }) — no error until UI shows "$undefined"

// with types — rename is a compiler error you fix once
type Price = { value: number; currency: string };
function formatPrice(p: Price): string {
  return `${p.currency} ${p.value.toFixed(2)}`;
}
const p: Price = { value: 10, currency: "USD" };
console.log(formatPrice(p)); // USD 10.00
```

### 2) **Bad practice** (any everywhere hides bugs)

**Bad practices** and why they hurt:

- `any` everywhere — disables checking entirely; correctness regresses to JS while keeping the illusion of safety. Prefer `unknown` + narrowing.
- `as` assertions to silence errors — `JSON.parse(s) as User` tells the compiler "trust me" even when data is malformed; crashes downstream instead of at the boundary.
- `@ts-ignore` / `@ts-expect-error` without tracking — hides real regressions. If you must use `// @ts-expect-error`, add a reason comment and prefer narrow suppression over file-wide.

```typescript
// bad: any swallows the bug
function totalBad(items: any) {
  return items.reduce((s: any, x: any) => s + x.price, 0); // no error even if items is string
}
console.log(totalBad("oops")); // runtime TypeError: items.reduce is not a function

// good: unknown + guard — bug surfaces at check time, not in prod
type Item = { price: number };
function totalGood(items: unknown): number {
  if (!Array.isArray(items)) throw new Error("expected array");
  return (items as Item[]).reduce((s, x) => s + x.price, 0);
}

// bad vs good at boundaries: assert vs validate
type User = { id: string; email: string };
const raw = `{"id":"1"}`; // missing email
// const u1 = JSON.parse(raw) as User; // bad: compiles, u1.email is undefined at runtime
// good: validate (Zod pattern, see domain 10)
function isUser(v: unknown): v is User {
  return typeof v === "object" && v !== null && "id" in v && "email" in v;
}
const parsed: unknown = JSON.parse(raw);
if (!isUser(parsed)) throw new Error("invalid user");
console.log(parsed.email); // safe — narrowed to User
```

### 3) **Mentor** (how to sell types to teams)

**Mentor note — selling types without dogma:**

1. **Show the bug, not the theory.** Take a real production incident (e.g., `undefined is not a function` from a renamed prop) and replay it with and without types. One live diff convinces more than a slide deck.
2. **Measure what types fix.** Track categories: wrong prop names, null dereferences (`strictNullChecks` catches), mismatched API shapes. After enabling `strict`, teams routinely see 20–40% of open bugs become compiler errors.
3. **Adopt gradually.** Don't demand a rewrite. Path: enable `allowJs` + `checkJs` + JSDoc → rename `.js` → `.ts` file-by-file → enable `strict` per package (see [10 1.1 allowJs](<../../../10 Migration Interop and Runtime Gaps/sections/1. Migrating JS to TS/1.1. allowJs checkJs and JSDoc Migration.md>)). Celebrate reduced PR back-and-forth.
4. **Review checklist**: reject `any` without `// reason`, reject `as` across module boundaries, require validation at every `unknown` boundary (fetch, localStorage, env vars).

### Common confusion

- "More types = slower" — checked docs *reduce* review time. The slow path is large PRs with no types where reviewers manually simulate the checker.
- "Tests replace types" — they complement. Tests prove specific paths; types prove all paths respect contracts. `strictNullChecks` catches the `null` that your test didn't cover.

### Performance note

Types don't affect runtime, but *bad* type-driven code does: `as` + `any` often hides expensive runtime workarounds (e.g., defensive `JSON.parse(JSON.stringify(x))` deep clones). Correct types let you remove those guards.
