## 3.1. tsc, tsx and ts-node Overview (when to use which)

### 1) **Choice** (tsc for build, tsx for dev)

**Definition** — Three ways to run TypeScript, different roles:

- **`tsc` (TypeScript compiler)** — the reference checker + emitter. Use for *type checking* (`tsc --noEmit`) and for production emit when you want `tsc`-controlled output (`tsc --build` with project references). It is the only tool that actually checks types.
- **`tsx`** — esbuild-powered runner/loader for local dev and scripts. It *transpiles only* (no checking) and is fast. Ideal for `tsx watch src/index.ts`, one-off scripts, and Node `--import tsx` loaders. Default choice for dev in 5.6 era.
- **`ts-node`** — Node loader that transpiles on-the-fly with `tsc` under the hood. Works but historically needs `isolatedModules`/`transpileOnly` tuning; slower and more config surface than `tsx`.

Rule-of-thumb table:

| Need | Tool | Checks types? | Speed |
|------|------|---------------|-------|
| CI typecheck | `tsc --noEmit` (or `--build`) | yes | slow, correct |
| Production emit (controlled) | `tsc` | yes | slow |
| Local dev / scripts | `tsx` | no — pair with `tsc --noEmit --watch` | fast |
| Legacy config needing transformers | `ts-node --transpile-only` + `tsc --noEmit` separate | via separate `tsc` | medium |

```bash
# production-grade split (package.json scripts)
# check only:
tsc --noEmit
# dev run (fast, no check):
tsx watch src/index.ts
# build emit:
tsc --build
```

```typescript
// src/index.ts — any runner executes this after transpilation
console.log("hello from", process.version);

// check separately: tsc --noEmit will catch:
const msg: string = 123 as unknown as string; // ok at emit, error at check if misused
```

### 2) **Bad** (ts-node without isolatedModules)

**Bad practices:**

- `ts-node` without `isolatedModules: true` — single-file transpile assumption breaks; features like `const enum` cross-file inlining, `namespace` merging across files, and type-only imports produce different emit per file vs whole program. Symptom: code passes locally but fails in `tsx` or `tsc` emit.
- Relying on any runner to *check* types — `tsx` and `ts-node --transpile-only` intentionally skip checking for speed. Type errors slip to CI only if you also run `tsc --noEmit`.
- Using `ts-node` for production emit — slower startup, hidden `tsconfig` mismatch between dev and build.

```jsonc
// bad: tsconfig for ts-node without isolation
{
  "compilerOptions": { "isolatedModules": false }
}
// better: force single-file emit parity
{
  "compilerOptions": { "isolatedModules": true, "esModuleInterop": true, "module": "nodenext" }
}
```

```typescript
// bad: relies on non-isolatedModules behavior (const enum inlines only whole-program)
// file a.ts
export const enum Color { Red = 0, Blue = 1 }
// file b.ts
import { Color } from "./a.js";
console.log(Color.Red); // with isolatedModules, must be union literal instead — see perf traps domain 10

// good: erasable union — works in any runner
export type Color2 = "red" | "blue";
```

### Mentor note

Enforce two-process discipline from day one: `tsx` for running, `tsc --noEmit` for checking (run in parallel via `concurrently` or watch mode). Teams that conflate the two oscillate between "slow dev" and "missed type errors."

### Common confusion

- "tsx checks types, so I don't need tsc" — false. `tsx` is transpile-only by design (it wraps `esbuild`). Always pair with `tsc --noEmit` in CI and optionally in dev watch.
- "ts-node is deprecated" — not deprecated, but `tsx` is the simpler default for greenfield. Keep `ts-node` only when you need its transformer plugins or legacy setup.

### Performance note

`tsc --build` incremental can be 5–10× faster than `tsc` cold on large repos after first build (uses `.tsbuildinfo`). `tsx` startup is dominated by `esbuild` transpilation — near-native speed, negligible vs Node cold start.
