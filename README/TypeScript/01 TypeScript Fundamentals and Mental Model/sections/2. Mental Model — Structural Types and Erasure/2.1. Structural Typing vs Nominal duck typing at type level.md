## 2.1. Structural Typing vs Nominal (duck typing at type level)

### 1) **Definition** (shape compatibility)

**Definition** — TypeScript is *structurally typed*: two types are compatible if their shapes (members) are compatible, regardless of declaration name. If `x` has all members required by `T`, `x` is assignable to `T` — "duck typing" lifted to the type checker.

This is unlike nominal systems (Java, C#) where `class A` and `class B` with identical fields are incompatible because they have different *names*.

```typescript
type Point = { x: number; y: number };

const p1 = { x: 0, y: 0, z: 0 }; // extra prop ok — has x,y
const p2: Point = p1; // ok: structural

// function cares only about shape
function len(v: Point): number { return Math.hypot(v.x, v.y); }
len({ x: 3, y: 4 }); // 5
len(p1); // also ok — extra field ignored
```

Width subtyping at work: a subtype may have *more* members. Readonly / optional modifiers participate in the check (see domain `03`).

### 2) **Example** (branded types for nominal)

When you *need* nominal behavior (IDs that shouldn't mix), simulate it with a brand — an uninhabited property only seen by the checker:

```typescript
// branded nominal ids — erased at emit (no runtime field set)
type Brand<K, T> = K & { readonly __brand: T };

type UserId = Brand<string, "UserId">;
type OrderId = Brand<string, "OrderId">;

function getUser(id: UserId) { /* ... */ }

const u = "abc" as UserId;
const o = "abc" as OrderId;

getUser(u); // ok
// getUser(o); // error: OrderId not assignable to UserId even though both are strings at runtime

// factory keeps branding ergonomic
function UserId(raw: string): UserId { return raw as UserId; }
function OrderId(raw: string): OrderId { return raw as OrderId; }

getUser(UserId("u_1")); // ok
```

Alternative when you also need runtime check: use a `class` with `private` brand field — private fields are nominal even structurally (different declarations are incompatible). See [05 1.1 Class types](<../../../05%20Classes%20Generics%20and%20Mixins/sections/1.%20Classes%20and%20Modifiers/1.1.%20Class%20Types%20public%20private%20protected.md>).

### 3) **Mistake** (expecting nominal by default)

**Common mistakes:**

- Expecting `type A = { x: number }` and `type B = { x: number }` to be distinct — they are interchangeable. The bug: you pass a `Customer` where a `Product` is expected and the checker says nothing because they share shape.
- Relying on `instanceof` for type aliases — aliases erase, so `instanceof` only works for class values, not structural types.
- Over-using classes "for nominal safety" — adds runtime cost and hierarchy where a branded type suffices.

```typescript
// bad: two roles collapsed to same shape → mix-up undetected
type Customer = { id: string; name: string };
type Product  = { id: string; name: string };
function shipTo(c: Customer) {}
const product: Product = { id: "p1", name: "Widget" };
shipTo(product); // no error — structural! Bug at runtime.

// good: brand each role
type Customer2 = Brand<{ id: string; name: string }, "Customer">;
type Product2  = Brand<{ id: string; name: string }, "Product">;
function shipTo2(c: Customer2) {}
const customer2 = { id: "c1", name: "Ava" } as Customer2;
// shipTo2({ id: "p1", name: "Widget" } as Product2); // error
shipTo2(customer2); // ok
```

### Performance note

Branded types are zero-cost: the `__brand` property never exists at runtime — it's a phantom field in an intersection with `never`-occupied trick. No object growth, no allocation.

### Mentor note

Teach structural thinking with a physical demo: hold up two objects with same keys but different labels and ask "does the function care about the label?" Once students stop naming-driven reasoning, excess-property and union-discriminant lessons click instantly.

### Common confusion

- "Structural = unsafe" — no, it's strict about shape; unsafety comes from `any` or missing freshness checks, not from structurality itself.
- "Interfaces are nominal, types are structural" — false. Both are structural; only `class` with `private`/`protected` members introduces nominal-like separation.
