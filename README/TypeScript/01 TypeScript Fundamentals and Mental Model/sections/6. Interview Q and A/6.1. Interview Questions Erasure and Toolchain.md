## 6.1. Interview Questions Erasure and Toolchain

### 1) **Q: Why does `typeof null === "object"` still affect TS?** (quirk preserved)

**Answer** — `typeof null === "object"` is a 1995 artifact; TS preserves JS semantics, so `typeof` check for `object` includes `null`. `strictNullChecks` separates `null` type via control-flow analysis.

```typescript
let x: unknown = null;
if (typeof x === "object") {
  // x is object | null — must also check !== null
  if (x !== null) console.log(Object.keys(x)); // narrowed to object
}
```

**Follow-up:** `Object` vs `object` vs `{}` — see [03 1.1](<../../../03%20Objects%20Interfaces%20and%20Type%20Aliases/sections/1.%20Objects%20Interfaces%20and%20Type%20Aliases/1.1.%20object%20vs%20Object%20vs%20{}.md>).

### 2) **Q: Erasable types cost?** (zero runtime)

**Answer** — Erased types have zero runtime cost; observed slowdowns come from emitted helpers (`__extends`, `useDefineForClassFields`) controlled by `target`, not annotations. Measure `tsc --extendedDiagnostics`; keep `skipLibCheck: true` for apps.

```typescript
// target es2022 emit: class A { x = 1; } — native define
// target es5 emit: class A { constructor(){ this.x = 1; } } + helpers
```

### 3) **Q: When to use `any`?** (never in app)

**Answer** — Never in app code; `unknown` + narrow. `any` is for untyped legacy lib one-off with `// reason: integration with X #123` and ticket.

```typescript
function handle(v: unknown) { if (typeof v === "string") console.log(v.toUpperCase()); }
// vs
function handleAny(v: any) { console.log(v.toUpperCase()); } // no check
```

**Common confusion** —

- "`tsx` checks types" — no, transpiles only; `tsc --noEmit` checks.
- "`any` is faster" — not measured; `any` hides bugs that cost debug time.

**Performance note** — `tsc --build` incremental saves 50-80% cold time; keep `.tsbuildinfo` cached.

**Mentor note** — Require candidate to state definition before code: "erasure = TS is checker, JS is runtime" — tests model.
