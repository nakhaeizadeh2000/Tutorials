## 3.3. `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`

### 1) **`noUncheckedIndexedAccess` honesty** (open index reads gain `| undefined`)

**Definition** — `noUncheckedIndexedAccess: true` (NOT in `strict` — enable separately) adds `| undefined` to every *open* index read: `arr[i]` → `T | undefined`, `dict[k]` → `V | undefined`. Fixed tuple positions stay non-optional (arity proves presence). [10/5.1](<../../../10 Arrays Tuples and Collections/sections/5. Common pitfalls to production bugs/5.1. Real production bugs caused by collection misunderstandings.md>) promise 4 owns the incident; this promise owns *configuring* it (enabling, triaging the backlog, banning `!` fixes).

**What problem it solves / history** — default indexing lies (`users[0]: User` on empty pages — `TypeError` with confident types, green `strict` CI). The flag converts the entire class into narrow-or-error at every read — the single highest-yield flag flip in collection-heavy codebases, routinely surfacing dozens of latent crashes on first enable (each a crash that hadn't happened *yet*).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), enable alongside `strict` in every tsconfig; triage the resulting errors as a latent-incident backlog (each a crash pre-triaged — fix with `?.`/`??`/early-return, never `!`); keep tuples for fixed shapes (positions dodge the flag by construction — arity as documentation).

**Runnable example** — flag converts crashes to narrows (good vs bad, `tsc --strict`):

```typescript
// good — honest index reads: empty input handled, never thrown
interface U157 { name: string }
function first(users: U157[]): string {
  return users[0]?.name ?? "anonymous"; // narrows the honest undefined (flag or no flag — correct both ways)
}
console.log(first([]), first([{ name: "ada" }])); // anonymous ada — empty page handled, not crashed
```

```typescript
// good — record reads narrow per key (honest absence at every lookup)
const scores: Record<string, number> = { a: 1 };
function get(key: string): string {
  return scores[key]?.toFixed(0) ?? "missing"; // ?. narrows (flag makes it REQUIRED; habit makes it universal)
}
console.log(get("a"), get("zzz")); // 1 missing — missing keys handled, never thrown
// bad — scores[key].toFixed(0) (compiles without the flag — throws on missing keys at runtime)
// fix — enable the flag: the ?. above becomes REQUIRED (honesty enforced, not stylistic)
```

```typescript
// good — tuples dodge by construction (arity proves presence — no flag needed for positions)
type Pair157 = [first: string, second: number];
function head(p: Pair157): string { return p[0].toUpperCase(); } // p[0]: string (arity-proven — flag exempts positions)
console.log(head(["x", 1])); // X — fixed positions stay non-optional (design with tuples where shapes are fixed)
// bad — (string | number)[] with positional reads (open indexing + position assumptions — flag errors every read, correctly)
// fix — Pair157: fixed shapes as tuples (positions exempt), open lists with narrowing (honesty enforced)
```

**Common confusion** — "the flag breaks valid code" — reveals unhandled absence in valid-*looking* code (breakage is diagnosis; `?.` fixes are one line each). "`!` migrates faster" — redistributes the lie per site (every crash preserved, flag silenced) — slower *and* dishonest. "tuples need the same treatment" — fixed positions prove presence by arity (`pair[0]` on `[A, B]` stays `A`) — open indexing is the hole, not positions.

**Performance note** — zero emit delta (pure check-time `| undefined`); narrowing branches (`?.`) cost one check each vs unbounded `TypeError`s — highest-ROI flag by post-mortem count in collection-heavy code.

**Mentor note** — enable Friday, triage Monday (dozens of errors = latent-incident backlog, prioritized free). Rule: `!` on indexed reads fails review; narrowing is the only accepted fix. Exercise: count triaged errors per file (density predicts incident density — schedule accordingly).

### 2) **`exactOptionalPropertyTypes` precision** (`?:` vs `| undefined` distinguished)

**Definition** — `exactOptionalPropertyTypes: true` (NOT in `strict` — enable separately) distinguishes *missing* from *explicitly-undefined*: `prop?: T` means "absent, or `T`" (assigning explicit `undefined` errors); `prop: T | undefined` means "present, possibly `undefined`" (explicit `undefined` required-allowed). Without the flag, both spellings collapse (`?:` accepts explicit `undefined` — intent erased).

**What problem it solves / history** — collapsed optionality conflated "not provided" (default applies) with "explicitly cleared" (reset requested) — PATCH handlers couldn't distinguish absent fields (leave alone) from `undefined` fields (clear?) — every handler guessed, most guessed wrong per API. Exactness makes the distinction compiler-enforced: absent vs `undefined` are different inputs with different types, handled in different branches.

**Modern guidance** — as of TypeScript 5.9 era, enable alongside `strict` in API-heavy codebases (PATCH semantics, config merging, default application); spell intentionally (`?:` for omittable-with-defaults, `T | undefined` for explicitly-clearable, required `T` for must-provide); handle both branches where both are possible (`key in obj` distinguishes missing from present-undefined at runtime).

**Runnable example** — absence vs explicit-undefined distinguished (good vs bad, `tsc --strict`):

```typescript
// good — exact: absent (default) vs undefined (rejected) are different inputs
interface Patch { name?: string } // omittable (absent → keep current; explicit undefined → error)
function apply(p: Patch): string { return p.name ?? "keep"; }
console.log(apply({}), apply({ name: "x" })); // keep x — absence defaults, presence applies
// apply({ name: undefined }); // error TS2375 under exactOptionalPropertyTypes (explicit undefined rejected — intent enforced)
```

```typescript
// good — clearable spelled explicitly (present-possibly-undefined admits the reset)
interface Reset { name: string | undefined } // clearable (explicit undefined REQUIRED-allowed, absence banned)
function clear(r: Reset): string { return r.name ?? "cleared"; }
console.log(clear({ name: undefined })); // cleared — reset requested AND typed (distinct from absent)
// const bad: Reset = {}; // error TS2741 (property missing — absence banned for clearable fields)
// fix — Patch (absent→default) vs Reset (undefined→clear): two intents, two spellings, enforced
```

```typescript
// good — runtime distinguishes what types distinguish (in-operator for presence)
interface Patch { name?: string } // re-declared: fences compile standalone
function describe(p: Patch): string {
  return "name" in p ? `set:${p.name ?? "undef"}` : "absent"; // in-operator: presence vs absence at runtime
}
console.log(describe({}), describe({ name: "y" })); // absent set:y — runtime mirrors the type distinction
// bad — collapsed optionality (flag off: Patch accepts { name: undefined } — absent/clear conflated, handlers guess)
// fix — enable exactOptionalPropertyTypes: the compiler enforces what handlers previously guessed
```

**Common confusion** — "exactness breaks JSON/partial flows" — `JSON.parse` results need validation into exact shapes regardless (unvalidated JSON is `any`-adjacent — exactness *guides* the validation: absent vs undefined handled per branch). "optional-with-default covers clearing" — defaults apply on *absence*; clearing needs *explicit* `undefined` (different intent — `Reset` spelling, not `Patch`). "the flag is only for API code" — config merging, test fixtures, and builder patterns share absent-vs-undefined semantics (defaults vs overrides) — enable repo-wide, spell per field.

**Performance note** — zero emit delta (pure check-time distinction); per-field intent spelled once (declaration) vs per-use guessing (handlers) — declaration-side precision scales, handler-side guessing rots.

**Mentor note** — `apply({ name: undefined })` erroring live (TS2375) vs compiling silently unflagged — intent enforced vs erased in one object literal. Exercise: classify five optional fields (omittable? clearable? required?) and respell (`?:` vs `| undefined` vs `T`) — intent made explicit per field. Gate: new optional fields state their intent (comment or spelling choice reviewed).

### 3) **Enabling both on existing code** (backlog triage, narrowing-only fixes)

**Definition** — adoption sequence for the two non-strict precision flags: enable `noUncheckedIndexedAccess` first (error volume concentrates in collection reads — `?.`/`??` fixes, mechanical); then `exactOptionalPropertyTypes` (errors concentrate in PATCH/config/fixture shapes — respelling fixes, judgmental). Triage both as latent-incident backlogs (each error a crash-or-conflation that hadn't fired *yet*), fixing with narrowing/respelling only (mass-`!`/widening banned — laundering, not migration).

**What problem it solves / history** — simultaneous enablement (both flags + full strict in one PR) mixed mechanical fixes (index narrowing) with judgmental ones (intent respelling) in unreviewable volumes — reviewers rubber-stamped, `!`s and widenings slipped in as "migration", precision theater replacing precision. Sequenced adoption (index honesty first — mechanical; optionality intent second — judgmental) keeps each PR's fix discipline uniform and reviewable.

**Modern guidance** — as of TypeScript 5.9 era, sequence: `strict` → `noUncheckedIndexedAccess` (mechanical narrowing pass) → `exactOptionalPropertyTypes` (intent respelling pass) — each green before the next; ban `!`/widening fixes in migration PRs (narrowing/respelling only — the discipline *is* the migration); track error counts per flag weekly (falling = triage working).

**Runnable example** — sequenced triage, uniform fixes (good vs bad, `tsc --strict`):

```typescript
// pass 1 (mechanical): index reads narrowed (one pattern, every site)
const words: string[] = ["a"];
const first = words[0]?.toUpperCase() ?? "EMPTY"; // ?. + ?? (mechanical fix — no judgment needed)
console.log(first); // A — index honesty (flag enforced, habit universal after)
// bad — words[0]!.toUpperCase() (assertion migration: crash preserved, flag silenced — theater)
// fix — ?. + ?? (narrowing: honest undefined handling, uniform across the pass)
```

```typescript
// pass 2 (judgmental): optionality respelled per intent (omittable vs clearable decided per field)
interface Update { title?: string } // omittable (absent → keep; decided per field intentionally)
function upd(u: Update): string { return u.title ?? "keep"; }
console.log(upd({})); // keep — intent spelled (reviewed per field, not bulk-converted)
// bad — bulk { title?: string } → { title: string | undefined } (mechanical respell destroying intent distinctions)
// fix — per-field judgment (omittable/clearable/required — the slow, correct pass after the fast mechanical one)
```

```typescript
// green both flags: honest indexes + precise optionality composed (the migrated steady state)
interface Entry { tag?: string }
function show(entries: Entry[]): string {
  return entries[0]?.tag ?? "none"; // index honesty (?. on open read) + optionality precision (?? on ?:) composed
}
console.log(show([]), show([{ tag: "t" }])); // none t — both flags' disciplines in one expression
// bad — enabling both + fixing in one PR (mechanical + judgmental mixed: reviewers rubber-stamp, !s slip in)
// fix — sequence (index pass, then intent pass): uniform fix discipline per PR, reviewable throughout
```

**Common confusion** — "triage order doesn't matter" — mechanical-first builds narrowing habits + tooling (codemods for `?.`) that judgmental-second relies on (respelling needs honest reads first) — order compounds. "small repos enable together" — small repos *finish* sequential passes in days (overhead trivial); simultaneous PRs still mix disciplines (review quality, not size, is the argument). "backlog counts demoralize" — counts *prioritize* (density predicts incident density — schedule by file, celebrate per-file green).

**Performance note** — both flags zero-emit (pure check-time precision); triage costs authoring minutes per error (one-time); un-triaged imprecision costs incidents (unbounded, recurring) — audit economics favor completion heavily.

**Mentor note** — graph both error counts weekly during adoption (two falling lines = triage working; flat = stalled class needing pairing). Exercise: triage ten errors from each flag live (mechanical narrowing vs intent respelling) — two disciplines, one migration. Gate: `!`/widening fixes in migration PRs fail review unconditionally.
