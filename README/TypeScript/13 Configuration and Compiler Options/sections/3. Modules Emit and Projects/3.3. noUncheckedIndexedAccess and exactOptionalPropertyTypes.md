## 3.3. noUncheckedIndexedAccess and exactOptionalPropertyTypes

These separately enabled options address two different questions: whether an
indexed read might be missing, and which values may be assigned to an optional
property. Strict alone does not enable either. Use TypeScript 7.0.2 and Node
20.20.2 in a fresh directory without a tsconfig. All flag comparisons below keep
strict null checking active through strict.

### 1) **Observe indexed reads without inventing presence evidence**

Save this deliberately unsafe read:

```typescript
// file: indexed.mts
const scores: Record<string, number> = { a: 1 };
function show(key: string): string { return scores[key].toFixed(0); }
console.log(show("missing"));
```

```sh
# Accepted, followed by an intentional runtime TypeError:
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --outDir loose indexed.mts
node loose/indexed.mjs
# Expected TS2532:
tsc --strict --noUncheckedIndexedAccess --target es2022 --module nodenext --moduleResolution nodenext --noEmit indexed.mts
```

The extra flag adds undefined to this unchecked lookup. It does not insert a
runtime test or choose what missing means. One valid policy is to return a
missing label; another API may need to throw or expose an optional result.
Replace show's body with `return scores[key]?.toFixed(0) ?? "missing"` and build
with the flag: execution prints missing. That fallback is a behavior decision,
not a mechanical repair that is correct for every caller.

Declared properties, tracked assignments and fixed required tuple positions
can provide stronger evidence. The [option reference](https://www.typescriptlang.org/tsconfig/noUncheckedIndexedAccess.html)
contrasts declared properties with an open index signature. Save:

```typescript
// file: evidence.mts
interface Scores { known: number; [key: string]: number }
const scores: Scores = { known: 1 };
const declared: number = scores.known;
const dynamic: Record<string, number> = {};
dynamic.saved = 2;
const assigned: number = dynamic.saved;
const pair: [string, number?] = ["first"];
const required: string = pair[0];
const optional: number | undefined = pair[1];
function sum(values: readonly number[]): number {
  let result = 0;
  for (const value of values) result += value;
  return result;
}
console.log(declared, assigned, required, optional, sum([1, 2]));
// const absent: number = scores.other;
// const optionalRequired: number = pair[1];
function first(values: readonly number[]): number {
  for (let i = 0; i < values.length; i++) {
    const value = values[i];
    if (value !== undefined) return value;
  }
  return 0;
}
console.log(first([]), first([4]));
```

Build with `--strict --noUncheckedIndexedAccess --target es2022 --module nodenext
--moduleResolution nodenext --outDir dist evidence.mts`, then run
`node dist/evidence.mjs`. The output is `1 2 first undefined 3`, then `0 4`.
The negative lines produce TS2322. Remove the `value !== undefined` guard and
return value directly from that loop: TS2322 still occurs despite the loop's
length condition. The checker does not generally prove an arbitrary indexed read
present from that numeric bound. For-of supplies element types without the added
index-read undefined; that is not a runtime validation of a sparse or dishonestly
typed array. The [collection owner](<../../../10 Arrays Tuples and Collections/sections/2. Tuple Types/2.1. Fixed arity tuples labels and optional elements.md>)
develops required, optional and open tuple positions.

### 2) **Separate property presence from optional assignment values**

With exactOptionalPropertyTypes, `name?: string` permits omission or a string
value; explicit undefined needs to be included if intended. `name: string |
undefined` still requires the property to exist. Those shapes do not collapse
when the flag is off: the required-property rule remains.

```typescript
// file: presence.mts
interface OptionalName { name?: string }
interface RequiredName { name: string | undefined }
const omitted: OptionalName = {};
const present: RequiredName = { name: undefined };
console.log(Object.hasOwn(omitted, "name"), Object.hasOwn(present, "name"));
const current = { name: "Ada" };
function merge(patch: OptionalName): { name: string } {
  return { ...current, ...patch };
}
console.log(merge({ name: undefined }).name.toUpperCase());
// const missingRequired: RequiredName = {};
```

```sh
# Accepted with the option off; the second console call throws TypeError:
tsc --strict --exactOptionalPropertyTypes false --target es2022 --module nodenext --moduleResolution nodenext --outDir loose presence.mts
node loose/presence.mjs
# Expected TS2379 at the merge argument with the option on:
tsc --strict --exactOptionalPropertyTypes --target es2022 --module nodenext --moduleResolution nodenext --noEmit presence.mts
```

The first output is `false true`. Under weaker assignment rules, the spread
can overwrite a required string with undefined, and the next call fails. The
extra flag rejects this explicit optional-property undefined at the call site.
Change the call to `merge({})` and the flagged build runs successfully, printing
false true and ADA. Activating missingRequired reports TS2741 with either setting.
Diagnostics depend on the operation: an optional-property assignment can instead
report TS2412; do not memorize one code for every exactness error. The [option
reference](https://www.typescriptlang.org/tsconfig/exactOptionalPropertyTypes.html)
shows that assignment case.

Reading an optional name still normally yields string or undefined, even with
exact assignment rules. In this declared contract, an `"name" in patch` branch
can establish that OptionalName's present value is a string when exactness is
on; with the flag off, an explicitly undefined present value remains possible.
Object.hasOwn is useful for runtime own-presence policy, but it does not generally
supply the same narrowing to the checker. Never treat these flags as validation
of an arbitrary incoming object.

### 3) **Implement clearable and serialized updates deliberately**

An optional property need not mean keep-current, and undefined need not mean
clear. Those meanings belong to the application. Here we deliberately choose:
omission keeps the original name; an own property containing undefined clears it.

```typescript
// file: clearable.mts
interface Update { name?: string | undefined }
function apply(current: string, update: Update): string {
  if (!Object.hasOwn(update, "name")) return current;
  return update.name ?? "(cleared)";
}
const inherited: Update = Object.create({ name: "prototype" });
console.log(apply("Ada", {}), apply("Ada", { name: "Grace" }), apply("Ada", { name: undefined }));
console.log("name" in inherited, Object.hasOwn(inherited, "name"), apply("Ada", inherited));
console.log(JSON.stringify({ name: undefined }), JSON.stringify({ name: null }));
```

Build clearable with strict and both extra flags, then run dist/clearable.mjs.
The lines are `Ada Grace (cleared)`, `true false Ada`, and `{} {"name":null}`.
The in operator includes inherited properties; our own-property policy does not.
That distinction can matter to merging even when the input structurally satisfies
the interface.

JSON serialization drops this undefined object property. An explicit clear marker
for a JSON API may therefore use null or a tagged operation, with a corresponding
validated contract. Changing the TypeScript flag does not add undefined to JSON
or choose the wire protocol. A parser must also verify actual member values:
[boundary parsing](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>)
owns that runtime step. The [optional-modifier owner](<../../../09 Utility Types and Type Transformations/sections/1. Mapped Types/1.2. readonly and optional modifiers with plus and minus.md>)
owns transformed property contracts rather than this configuration decision.

### 4) **Migrate from intended behavior and the actual program**

For a small project, enabling both options together can be practical. A larger
migration can split collection-read changes from optional-write contract changes.
Neither order is prescribed by the language. Inspect the diagnostics and caller
semantics before deciding whether a missing value should default, throw, remain
optional or represent an invalid state.

An assertion can document a separately established invariant, but it cannot
create a missing element. Conversely, adding an undefined alternative can be the
correct contract when callers intentionally provide it. Blanket bans on every
assertion or widening can prevent an accurate repair. Require evidence for the
chosen contract and preserve that behavior with relevant checks; do not equate
every new diagnostic with a previously inevitable incident.

Both options are program settings. Exact optional property checking requires
strict null checking. Use effective configs and separate projects where needed;
a directory name alone does not create an exception. The [strict-family
configuration lesson](<../1. Strictness Family/1.1. strict and strictNullChecks the nullability contract.md>)
owns current defaults and staged overrides.

### 5) **Common confusion**

Exact optional types refine assignment and some presence-based narrowing; they
do not remove absence from an unguarded read. Indexed-access checking adds an
absence possibility where the checker lacks the relevant evidence; it does not
make every property or tuple position optional.

Finally, `??` supplies a fallback for both null and undefined, whether the property
was omitted or explicitly present. Object spread can overwrite with an own
undefined value, while JSON serialization can omit it. Choose the operation from
the required policy rather than claiming that the type spelling alone supplies
defaulting, clearing or transport behavior.

### 6) **Performance note**

These checks add no runtime presence validation. The branches, optional chains,
spreads and serialization in the examples execute as ordinary code. Inferred
output declarations can reflect changed optional read types, so inspect the
published API when inference matters. No checker-time, branch-cost or incident-rate
benchmark was run; a fixed per-error migration duration or error-density prediction
would not be supported by these probes.

### 7) **Mentor note**

Ask a learner to predict which evidence reads stay required and why the numeric
loop still needs its value guard. Then compare omitted, own undefined and inherited
properties before choosing an update policy. A sound answer distinguishes checker
admission, runtime presence and serialized representation.

For review, require one missing-input test and one explicit-clear test for the
chosen update contract. If a colleague proposes replacing every read with a
fallback, ask whether that fallback preserves the caller's meaning. This tests
reasoning about the migration rather than mechanical compliance with a flag.
