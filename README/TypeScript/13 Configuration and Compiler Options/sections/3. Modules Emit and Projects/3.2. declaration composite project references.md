## 3.2. declaration, composite and project references

A project reference connects compiler programs so build mode can order their
work and consumers can use built declarations. Runtime imports still need actual
JavaScript at their named destinations. This lesson builds two real projects,
inspects their artifacts and tests the limits of the reference graph.

Use TypeScript 7.0.2 and Node 20.20.2. The final alternative JavaScript emitter
uses esbuild 0.28.2. All commands run from a new fixture root. There is no external
runtime package and no claimed editor integration test.

### 1) **Configure and build two actual programs**

Create these four JSON files. Omit each `// file:` label when saving JSON.
The base centralizes checking and declaration options; each child owns its
source/output and build-information paths. The solution has no root source files
and names app, whose reference names core.

```json
// file: tsconfig.base.json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "types": [],
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "noEmitOnError": true
  }
}
```

```json
// file: core/tsconfig.json
{
  "extends": "../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": "src", "outDir": "dist",
    "tsBuildInfoFile": "../cache/core.tsbuildinfo"
  },
  "include": ["src/**/*.mts"]
}
// file: app/tsconfig.json
{
  "extends": "../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": "src", "outDir": "dist",
    "tsBuildInfoFile": "../cache/app.tsbuildinfo"
  },
  "include": ["src/**/*.mts"],
  "references": [{ "path": "../core" }]
}
// file: tsconfig.json
{ "files": [], "references": [{ "path": "./app" }] }
```

```typescript
// file: core/src/index.mts
export interface User { id: string }
export function label(user: User): string { return `user:${user.id}`; }
// file: core/src/internal.mts
export const internalValue = "internal";
// file: app/src/main.mts
import { label } from "../../core/dist/index.mjs";
console.log(label({ id: "u1" }));
```

The app explicitly consumes a built artifact. On a fresh fixture, checking app
alone does not build core and cannot resolve that absent artifact:

```sh
# Expected missing module diagnostic TS2307 before core has been built:
tsc -p app --noEmit
# Build dependencies, then consumers:
tsc --build --verbose
node app/dist/main.mjs
# Repeat without edits:
tsc --build --verbose
```

The solution build succeeds and the app prints `user:u1`. The verbose log shows
core before app and the unchanged invocation reports the projects up to date.
Inspect core/dist: index and internal each have .mjs, .d.mts and .d.mts.map outputs.
Cache contains separate .tsbuildinfo files. These observations establish this
fixture's work states; no elapsed-time or memory improvement is inferred.

Composite requires an explicit implementation-file set through files/include,
and declaration output cannot be disabled for a composite project. Build mode
finds referenced projects and orders needed work. A regular `tsc -p app` does not
perform that dependency build. The [project-reference handbook](https://www.typescriptlang.org/docs/handbook/project-references.html)
explains these roles. The runtime import path is a separate deliberate choice;
references do not rewrite imports to the correct JavaScript location.

### 2) **Inspect declarations and maps at the consumer boundary**

Run this after the successful build:

```sh
tsc -p app --noEmit --listFilesOnly
```

The file list includes core/dist/index.d.mts and excludes core/src/index.mts.
That is evidence that this consumer checks the built signature. A source-directory
import would be a different experiment. The declaration contains User and label's
signature; the JavaScript contains label's implementation. Declarations can also
include non-exported supporting names where the public signature needs them;
[declaration authoring](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.1. Authoring d.ts public API surface.md>)
inspects that case and an asserted runtime lie.

Open core/dist/index.d.mts.map as JSON. Its sources entry names
`../src/index.mts` relative to the map. A declaration map helps supported editor
features connect signatures with source, but a path reference does not embed or
ship the source file. Consumers need the corresponding files and editor support.
This lesson inspected the map; it did not run Go to Definition or a debugger.
JavaScript sourceMap and declarationMap also serve different artifact mappings.

Declaration generation therefore needs a packaging decision: which files are
included, which source paths remain available and which declaration entry points
a consumer resolves. Use the [packed-package project](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>)
for the tarball and installed-consumer boundary rather than treating a local map
file as publication proof.

### 3) **Observe build invalidation without calling references an allow-list**

Try a body-only edit: change core's returned prefix from user: to member: without
changing the function signature. Build the solution again and run app. It now
prints `member:u1`. Inspect verbose output to see what was rebuilt or reused.
The public declaration can remain unchanged while implementation behavior changes;
the running app loads the new JavaScript even if its own emitted text is unchanged.

Now change label to require a second string parameter and use it as the prefix.
The next build diagnoses app's missing argument with TS2554. noEmitOnError is
explicit in these projects; a failed check is not permission to execute an old
artifact as if it came from that successful build. Existing files from earlier
builds can remain. Restore the original function and rebuild before continuing.

References establish build/program relationships, not a general import
allow-list. With core's outputs already present, temporarily remove app's
references entry and run `tsc -p app --noEmit`: its direct declaration import can
still check. Adding a direct import of `internalValue` from
`../../core/dist/internal.mjs` also checks. These published physical files are
not hidden merely because app previously referenced core as one project.
Restore the reference to retain dependency build ordering.

Package export maps, dependency rules and architecture linting address different
boundaries. Not every package.json dependency is a TypeScript source project that
needs a reference twin: an external prebuilt package can already provide its
contract. [Nx's package-management comparison](https://nx.dev/blog/managing-ts-packages-in-monorepos)
usefully separates package-manager linking from the TypeScript reference graph.
This small relative-artifact fixture needs neither a package manager workspace
nor Nx; a real workspace must also configure how its runtime packages are linked.

Force means rebuild, not erase all old output. Observe that distinction locally:

```sh
node -e 'require("node:fs").writeFileSync("app/dist/obsolete.txt", "stale")'
tsc --build --force
node -e 'console.log(require("node:fs").existsSync("app/dist/obsolete.txt"))'
```

The final command prints true. `--force` treats projects as out of date; it does
not clean unrelated or stale files from output directories. Build mode's clean
operation removes known outputs, which is also not a promise to erase arbitrary
files. Define the intended generated-output cleanup when validating a fresh
artifact, and preserve source/user files. The [incremental-build owner](<../../../19 Performance Project References and Scaling/sections/2. Project References and Builds/2.2. Incremental builds and tsbuildinfo discipline.md>)
develops cache and rebuild workflows.

### 4) **Use declaration-only emit with an honest runtime plan**

EmitDeclarationOnly selects output; it does not restrict source to interfaces or
prove that no runtime implementation is needed. Using the restored core source,
run:

```sh
tsc -p core --emitDeclarationOnly --outDir core/type-dist --tsBuildInfoFile cache/core-types.tsbuildinfo
```

Core/type-dist now contains .d.mts and map files for both source modules, without
.mjs implementations from this command. Label and internalValue still appear as
value exports in the declarations. A consumer can check those descriptions while
runtime imports fail if no corresponding provider exists. The [authoring
project](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.1. Authoring d.ts public API surface.md>)
reproduces that missing-provider failure.

One legitimate workflow uses tsc for declarations and another emitter for
JavaScript. For this small core module:

```sh
npm exec --yes --package=esbuild@0.28.2 -- esbuild core/src/index.mts --platform=node --format=esm --outfile=core/type-dist/index.mjs
node --input-type=module -e 'import {label} from "./core/type-dist/index.mjs"; console.log(label({id:"u1"}))'
```

The output is `user:u1`. This adds an actual implementation beside the generated
declaration. It covers index only; internal would need its own runtime emit if
that export were part of the supported package. Verify the final artifact set
and consumers rather than assuming declaration success configures the other tool.

A genuinely type-only package can instead expose only checking contracts and be
consumed with import type. Such a statement also erases when its declarations
come from a package that happens to ship JavaScript; JavaScript's presence in the
package alone does not create a runtime import edge. Runtime predicates and guards
still require implementations. Packaging a brand type alone does not make its
values validated or nominally incompatible with every independently written type.

### 5) **Common confusion**

A reference edge, a package dependency and a runtime import describe related but
different graphs. The solution orders project builds; the relative import names
an artifact; package metadata and linking govern distributed package resolution.
A successful edge in one graph does not automatically construct the others.

Likewise, map inspection is not editor verification, and force is not clean.
No declaration switch validates what a function returns at runtime. Keep these
pieces of evidence distinct so a green source build cannot hide stale or missing
consumer artifacts.

### 6) **Performance note**

This lesson observes fresh, unchanged and edited build behavior without timing
those states. References can enable reuse of declaration/build information, but
which projects are rebuilt depends on source/signature changes, compiler behavior
and cache state. There is no guaranteed seconds-versus-minutes gain from adding
a second project. Declarations and maps also need emission, storage and checking;
measure the actual graph before predicting downstream memory or latency.

The runtime function still executes and allocates its returned string. A type-only
import statement adds no runtime edge from that statement. Neither fact makes a
particular package layout the cheapest distribution on every axis.

### 7) **Mentor note**

Ask the learner to explain why app-only checking fails before the first build,
then succeeds against core's declarations. Next change only core's body and ask
why runtime behavior changes even if the app output text does not. A sound answer
connects build ordering, type signatures and the runtime import target.

For a proposed architecture rule, test the unreferenced built-artifact import.
For a release claim, test the obsolete-output sentinel and inspect the packed
files. These counterexamples expose what the configuration actually enforces
before a team builds policy on a misleading allow-list or clean-build assumption.
