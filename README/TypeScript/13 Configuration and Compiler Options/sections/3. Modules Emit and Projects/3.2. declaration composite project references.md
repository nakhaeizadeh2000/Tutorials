## 3.2. `declaration`, `composite`, and project references

### 1) **`declaration` + `declarationMap`** (consumers check signatures; maps restore sources)

**Definition** — `declaration: true` emits `.d.ts` beside JS (consumers check *signatures*, skipping implementation bodies — faster downstream checks, enforced API surface); `declarationMap: true` adds `.d.ts.map` (consumer go-to-definition navigates *through* declarations to sources — debugging with bodies, not stubs). [12/3.1](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.1. Authoring d.ts public API surface.md>) owns authoring discipline; this promise owns *configuring* emission (flags, maps, verification).

**What problem it solves / history** — sourceless packages (declarations without maps) stranded consumer debugging at `.d.ts` stubs (signatures without bodies — "what does it *do*?" unanswerable in-IDE) while declaration-less packages forced source compilation downstream (slow checks, implementation coupling). The pair serves both speeds: fast checking via declarations, deep debugging via maps — configured once per library, benefiting every consumer build.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), enable both in every library tsconfig (`declaration` + `declarationMap` + `sourceMap` for the full navigation chain); verify maps resolve (go-to-definition from a consumer test project lands in sources, not stubs); keep `emitDeclarationOnly` for type-only packages (see promise 3). Never ship declarations without maps where sources ship (stub-debugging is a support cost shifted to consumers).

**Runnable example** — signatures fast, sources reachable (multi-file sets):

```typescript
// file: lib149.ts
export interface Cfg149 { host: string }
export function connect(c: Cfg149): string { return `conn:${c.host}`; } // declaration: signatures emitted (consumers skip the body)
// file: con149.ts
import { connect, type Cfg149 } from "./lib149.js";
const c: Cfg149 = { host: "h" };
console.log(connect(c).toUpperCase()); // CONN:H — checked against declarations (fast), debuggable via maps (deep)
// declarationMap: con149's go-to-definition on connect lands in lib149.ts (source), not lib149.d.ts (stub)
```

```typescript
// file: lib150.ts
export class Pool { constructor(public size: number) {} acquire(): string { return `slot:${this.size}`; } }
// file: con150.ts
import { Pool } from "./lib150.js";
const p = new Pool(4);
console.log(p.acquire(), p.size.toFixed(0)); // slot:4 4 — class shapes via declarations (constructors + methods, no bodies needed)
// bad — declaration: false libraries (consumers compile sources: slower checks + implementation coupling per dependency)
// fix — declaration: true (+ declarationMap): fast downstream, deep debugging, enforced surface (see 12/3.1)
```

```typescript
// file: pub151.ts
export function pub(): string { return "pub"; }
export function alsoPub(): string { return pub() + "!"; }
// file: con151.ts
import { pub, alsoPub } from "./pub151.js";
console.log(pub().toUpperCase(), alsoPub()); // PUB pub! — surface derived (only exported names appear in declarations — privacy by generation)
// bad — hand-maintained .d.ts beside evolving source (drift both directions — generation + CI-diff per 12/3.1 instead)
```

**Common confusion** — "declarations slow library builds" — one emit pass (incrementalized via `composite` — next promise; seconds, not minutes, for most packages). "maps leak sources" — maps *reference* sources (consumers navigate *if* sources ship/sourcemapped; otherwise degrade gracefully to stubs — no leak beyond what's published). "consumers prefer sources" — consumers prefer *speed* (declarations) with *depth on demand* (maps) — the pair serves both, sources-alone serve neither well.

**Performance note** — downstream checks against `.d.ts` skip bodies (measurably faster per dependency — the primary monorepo check-time lever with project references); declaration emit adds one pass to library builds (incrementalized — changed packages only).

**Mentor note** — go-to-definition from a consumer into sources vs stubs (maps on/off) — navigation depth demonstrated in two jumps. Exercise: enable `declarationMap` on one library and navigate three symbols from a consumer (bodies, not stubs — debugging depth restored). Gate: libraries without `declaration` fail review; without maps, warn loudly.

### 2) **`composite` + project references** (monorepo builds: programs per package, ordered emit)

**Definition** — `composite: true` marks a project buildable-incrementally (emits `.tsbuildinfo`, requires `declaration` — downstream projects consume its *declarations* without rebuilding its sources); `references: [{ path: "../lib" }]` declares program dependencies (build order topological, downstream checks against upstream declarations). Monorepos become *ordered program graphs* instead of one giant compilation (fast incremental rebuilds, enforced layering, per-package flags).

**What problem it solves / history** — single-program monorepos (one tsconfig, all sources) rebuilt everything per change (minutes per save), checked everything per error (unrelated packages in every diagnostic), and permitted every import direction (layering by convention — violated silently). References split the graph: changed packages rebuild (seconds), diagnostics scope per program (relevant errors only), imports violating layering error (references are *allow-lists* — unlisted cross-imports fail).

**Modern guidance** — as of TypeScript 5.9 era, structure monorepos as referenced projects (one tsconfig per package + solution file; `composite` on libraries; `references` mirroring dependency direction); build with `tsc --build` (ordered, incremental, `--force` for clean-room verification in CI); keep references *matching* package dependencies (each `dependencies` entry has a `references` twin — drift between them is the layering incident queued). Full scaling treatment lands in [19 Performance](<../19 Performance Project References and Scaling/README.md>).

**Runnable example** — ordered programs, layered imports (multi-file sets):

```typescript
// file: core152.ts
export interface Core152 { id: string } // upstream program (composite library: declarations consumed downstream)
// file: mid152.ts
import type { Core152 } from "./core152.js"; // downstream references upstream (layering: mid → core, never reverse)
export function wrap(c: Core152): string { return `[${c.id}]`; }
// file: app152.ts
import { wrap } from "./mid152.js";
console.log(wrap({ id: "x" })); // [x] — layered graph (core ← mid ← app: order enforced, rebuilds incremental)
// bad — app152 importing core152's internals directly (layering violation invisible without references — references make it an error)
// fix — references as allow-lists (unlisted cross-imports fail: layering compiler-enforced, not convention-hoped)
```

```typescript
// file: jsonc152.jsonc (solution tsconfig shape, documented as config — not compiled)
// {
//   "files": [],
//   "references": [{ "path": "./core" }, { "path": "./mid" }, { "path": "./app" }]
//   // tsc --build: topological order (core → mid → app), incremental (.tsbuildinfo per project)
// }
// file: app152b.ts
console.log("solution-ordered"); // build order follows references (changed packages rebuild, others reuse declarations)
// bad — single-program monorepo tsconfig (everything rebuilds per change, diagnostics span unrelated packages)
```

```typescript
// file: leaf153.ts
export function leaf(): string { return "leaf"; } // leaf program (no references out — depends on nothing)
// file: mid153.ts
import { leaf } from "./leaf153.js"; // references: [{ path: "./leaf-proj" }] (declared dependency, checked layering)
export function mid(): string { return leaf().toUpperCase(); }
// file: app153.ts
import { mid } from "./mid153.js";
console.log(mid()); // LEAF — three programs, ordered emit, per-program diagnostics (monorepo at scale, configured)
// bad — references missing a real dependency (import resolves via paths but build order wrong — stale declarations consumed silently)
// fix — references mirror dependencies (each package.json dep has a references twin — drift is the incident queued)
```

**Common confusion** — "references duplicate package.json" — *mirror* deliberately (two views of one graph: runtime deps + build order — drift tooling (`syncpack`-adjacent checks) keeps them aligned; unmirrored drift breaks ordering silently). "`composite` slows small repos" — single-package repos skip references (nothing to order); multi-package repos gain incremental rebuilds immediately (seconds vs minutes from the second package on). "declaration output pollutes repos" — declarations *are* the inter-program contract (downstream checks signatures, never sources — the performance architecture, not pollution).

**Performance note** — incremental rebuilds touch changed programs only (seconds vs full minutes); per-program diagnostics scope errors (relevant packages only); declaration-mediated checks skip upstream bodies (the primary monorepo check-time lever — compounds per package).

**Mentor note** — `tsc --build` twice in a row (second run: "up to date" in milliseconds — incrementality demonstrated) then touch one leaf (rebuilds only downstream — ordering visible). Exercise: draw the repo's program graph from `references` (cycles? orphans? missing twins?) — the graph *is* the layering audit. Gate: new cross-package imports without `references` twins fail review.

### 3) **`emitDeclarationOnly` for type packages** (types without JS emit)

**Definition** — `emitDeclarationOnly: true` (+ `declaration: true`) emits `.d.ts` *without* `.js`: type-only packages (shared interfaces,ambient shims curated as a package, generated contract types) publish checking contracts with zero runtime. Consumers check against real declarations (not ambient shims — first-class packages with versions, changelogs, and dependency graphs).

**What problem it solves / history** — shared types traveled three bad ways: copied interfaces per package (drift across copies), ambient global shims (unversioned, unscoped trust), or JS-emitting packages imported for types alone (runtime weight for checking contracts). Type-only packages (`@org/contracts`: `emitDeclarationOnly`, versioned, depended-upon) give shared types *packaging*: versioned truth, scoped imports, zero runtime — the distribution story types deserved.

**Modern guidance** — as of TypeScript 5.9 era, publish shared contracts as type-only packages (interfaces + literal unions + branded ids — no values, no runtime); version them like code (breaking type changes are breaking releases — semver applies to checking contracts); consume via `import type` (erased everywhere — zero-weight checking at scale). Never emit JS from contract packages (runtime in a types package is a layering violation with a version number).

**Runnable example** — contracts packaged, weight zero (multi-file sets):

```typescript
// file: contracts154.ts
export interface Order154 { id: string; total: number } // contract package source (emitDeclarationOnly: .d.ts out, no .js)
export type Status154 = "new" | "paid";
// file: shop154.ts
import type { Order154, Status154 } from "./contracts154.js"; // type-only consumption (erased — zero runtime edge)
export function label(o: Order154, s: Status154): string { return `${o.id}:${s}`; }
// file: app154.ts
import { label } from "./shop154.js";
console.log(label({ id: "o", total: 1 }, "new")); // o:new — contracts versioned, consumed weight-free
```

```typescript
// file: ids155.ts
export type UserId155 = string & { readonly __brand: "U" }; // branded ids as shippable contracts (zero-runtime nominality)
export function isUserId(s: string): s is UserId155 { return s.startsWith("u_"); } // predicate travels WITH the brand (guard included)
// file: app155.ts
import { isUserId, type UserId155 } from "./ids155.js";
const id: string = "u_1";
console.log(isUserId(id) ? id.toUpperCase() : "bad"); // U_1 — brand + guard versioned together (narrowing travels with the type)
// bad — copied brand definitions per package (drift: two UserIds that never interchange — nominal fragmentation)
// fix — @org/contracts (one brand definition, versioned, imported type-only everywhere)
```

```typescript
// file: shapes156.ts
export interface Circle156 { r: number } // contract shapes (consumers narrow over them without importing values)
// file: app156.ts
import type { Circle156 } from "./shapes156.js";
function area(c: Circle156): number { return Math.PI * c.r ** 2; }
console.log(area({ r: 2 }).toFixed(2)); // 12.57 — shape contracts (checking without runtime, versioned without weight)
// bad — JS-emitting package imported type-only (runtime weight for checking contracts — bundlers carry dead code paths)
// fix — emitDeclarationOnly packages (types publish, JS never ships — layering honored by construction)
```

**Common confusion** — "type packages need runtime tests" — contracts test via *consumers* (type assertions in consumer suites — `expectTypeOf` checks; the package itself has nothing executable to test). "versioning types is overkill" — breaking type changes break consumers' builds (semver-major by definition — unversioned shared types break silently across repos). "ambient shims suffice" — shims are unversioned + unscoped (global trust without packaging); type packages version + scope (imports explicit, versions pinned — trust with provenance).

**Performance note** — zero runtime (no JS ships — nothing to load, parse, or execute); checking against real declarations (not ambient globals) keeps resolution scoped (per-import candidates, no global scan). Type-only packages are the cheapest shared-types distribution on every axis.

**Mentor note** — `npm pack` a contracts package and inspect the tarball (`.d.ts` only — zero JS proving the layering) — packaging made visible in one archive. Exercise: convert one copied-interface cluster to a versioned contracts package and delete the copies — drift vectors deleted per copy. Rule: shared types cross package boundaries only as versioned type-only packages (never copies, never ambient globals).
