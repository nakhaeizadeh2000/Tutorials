## 3.1. module and moduleResolution pairing

`module` helps determine JavaScript output format and the import/require context
used during checking. `moduleResolution` determines how the checker finds source
and declarations for an import. Choose them from the artifact's consumer: native
Node, a bundler or another declared host. A compatible pair helps model that host;
it does not make the checker load JavaScript at runtime or prove that deployed
files, package conditions and providers agree.

Use TypeScript 7.0.2 and Node 20.20.2. Bundling below uses esbuild 0.28.2. These
are the actual compiler/runtime baselines; no separate historical language-era
label overrides their behavior.

### 1) **Start from supported combinations, not matching option names**

There is no `module: bundler` value. Bundler is a resolution mode. Common choices
include:

| Consumer/process | module | moduleResolution | Boundary to test |
|---|---|---|---|
| Native Node with format determined by extensions/package scope | nodenext | nodenext | The emitted import or require path and runtime graph |
| Bundler consumes preserved ESM syntax | preserve or esnext | bundler | Bundler conditions, extensions and final output |
| A supported CommonJS transformation with bundler-style resolution | commonjs | bundler | Actual CJS output and downstream host |
| A deliberately versioned Node model | node16, node18 or node20 as appropriate | The supported/default Node resolution for that module mode | That model's features versus the deployed runtime |

The CommonJS/bundler combination is supported from TypeScript 6; the [release
notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html#combining---moduleresolution-bundler-with---module-commonjs)
explain the migration motivation. Some contradictory explicit combinations are
compiler errors, rather than silently accepted mismatches. In TypeScript 7,
module commonjs with moduleResolution nodenext reports TS5110; module nodenext
with moduleResolution bundler reports TS5109. A setting omitted from a config
can also receive a valid inferred default: module nodenext selects NodeNext
resolution without requiring the second property to be written redundantly.

Use `--showConfig` to inspect selected settings and `--traceResolution` to inspect
actual resolution. A trace records the checker finding a type/source candidate;
it is not a native-loader trace. TypeScript deliberately substitutes source or
declaration extensions for runtime specifiers. The [resolution reference](https://www.typescriptlang.org/tsconfig/moduleResolution.html)
describes the supported models; execute the artifact as a separate check.

### 2) **Reproduce a bundler-accepted import that native Node rejects**

Create `relative/package.json`, `dep.ts` and `app.mts`. File labels identify
locations; omit the label from JSON. Run this section's commands from relative.

```json
// file: relative/package.json
{ "type": "module", "private": true }
```

```typescript
// file: relative/dep.ts
export const value = 3;
// file: relative/app.mts
import { value } from "./dep";
console.log(value);
```

```sh
tsc --strict --target es2022 --module preserve --moduleResolution bundler --noEmitOnError --outDir bundle-check app.mts
# Expected native ERR_MODULE_NOT_FOUND:
node bundle-check/app.mjs
npm exec --yes --package=esbuild@0.28.2 -- esbuild app.mts --bundle --platform=node --format=esm --outfile=bundle.mjs
node bundle.mjs
# Expected checker TS2835 for this ESM relative specifier:
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmit app.mts
```

Bundler resolution accepts the extensionless source import. That tsc output still
names `./dep`, so native Node cannot locate it using ESM's explicit-file rules.
Esbuild resolves and bundles the source, and that bundle prints 3. The bundler
check models a build step; it does not promise that every intermediate file is
suitable for direct native execution.

For an emitted Node entry, change the source import to `./dep.js`. Check and run:

```sh
tsc --strict --target es2022 --module nodenext --noEmitOnError --outDir node-dist app.mts
node node-dist/app.mjs
tsc --strict --target es2022 --module nodenext --noEmit --traceResolution app.mts
```

The build and run now succeed with output 3. Resolution was deliberately omitted
from the first command; the trace identifies NodeNext resolution and finds dep.ts
for the `.js` specifier. Emission supplies dep.js for the actual loader. This
is a useful correspondence, not “the checker and Node open the same file.”
For native TypeScript source execution, follow the separate [source/emit import
strategy](<../../../12 Modules Namespaces and Declaration Files/sections/1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>).

### 3) **Align package conditions explicitly**

Bundler resolution does not automatically mean browser conditions. To see the
selection, create a second directory called conditional. Manually install this
local fixture beneath its node_modules; no registry package is needed.

```json
// file: conditional/node_modules/target-kit/package.json
{
  "name": "target-kit", "version": "1.0.0", "type": "module",
  "exports": {
    ".": {
      "browser": { "types": "./browser.d.mts", "default": "./browser.mjs" },
      "node": { "types": "./node.d.mts", "default": "./node.mjs" },
      "default": { "types": "./fallback.d.mts", "default": "./fallback.mjs" }
    }
  }
}
```

```javascript
// file: conditional/node_modules/target-kit/browser.mjs
export const target = "browser";
// file: conditional/node_modules/target-kit/node.mjs
export const target = "node";
// file: conditional/node_modules/target-kit/fallback.mjs
export const target = "fallback";
```

```typescript
// file: conditional/node_modules/target-kit/browser.d.mts
export declare const target: "browser";
// file: conditional/node_modules/target-kit/node.d.mts
export declare const target: "node";
// file: conditional/node_modules/target-kit/fallback.d.mts
export declare const target: "fallback";
// file: conditional/app.mts
import { target } from "target-kit";
const expected: "browser" = target;
console.log(expected);
```

Run from conditional:

```sh
# Expected TS2322: default bundler conditions select fallback, not browser.
tsc --strict --target es2022 --module preserve --moduleResolution bundler --noEmit app.mts
# Browser condition selected explicitly:
tsc --strict --target es2022 --module preserve --moduleResolution bundler --customConditions browser --noEmit app.mts
npm exec --yes --package=esbuild@0.28.2 -- esbuild app.mts --bundle --platform=browser --format=esm --outfile=browser-bundle.mjs
node browser-bundle.mjs
```

The bundle prints browser. This Node run tests the bundled value; it does not
exercise browser APIs or rendering. Trace each compiler command if you want to
see fallback.d.mts versus browser.d.mts. The [customConditions reference](https://www.typescriptlang.org/tsconfig/customConditions.html)
explains adding a condition to the checker's normal condition set.

Even a legal NodeNext pair needs matching custom conditions at runtime:

```sh
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --customConditions browser --outDir node-dist app.mts
node node-dist/app.mjs
node --conditions=browser node-dist/app.mjs
```

The checker accepts the browser literal contract. The first runtime nevertheless
prints node, because Node's default conditions select node.mjs. The second prints
browser. The TypeScript annotation does not assert the runtime value. Setting
customConditions only affects checking; it does not configure Node or a bundler.
Metadata condition order also matters when multiple conditions match. Match the
actual host and build configuration, then inspect and run the selected artifacts.

### 4) **Migrate removed settings and test a library's real outputs**

In TypeScript 7, moduleResolution node10 and esModuleInterop false are removed.
For a small isolated configuration check, save probe.ts in a fresh directory:

```typescript
// file: probe.ts
export const probe = 1;
```

```sh
# Expected TS5108 for each removed setting:
tsc --strict --target es2022 --module commonjs --moduleResolution node10 --noEmit probe.ts
tsc --strict --target es2022 --module commonjs --esModuleInterop false --noEmit probe.ts
# A supported combination, not module: bundler:
tsc --strict --target es2022 --module commonjs --moduleResolution bundler --noEmit probe.ts
```

Choose a replacement from the intended consumer rather than deleting an option
and assuming semantics stayed identical. The [configuration update](<../../../25 Update TypeScript 7.0/sections/1. Configuration Migration/1.1. Configuration defaults and removed options.md>)
owns the broader migration list. The [CommonJS owner](<../../../12 Modules Namespaces and Declaration Files/sections/1. ES Modules/1.3. export equals and interop with CommonJS.md>)
tests shape and loader differences under the current baseline.

For a library, first decide which formats and consumers are supported. Writing
dual import/require conditions does not turn one ESM build into a second CommonJS
implementation. The [packed-package project](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>)
builds actual .mjs/.cjs implementations with matching .d.mts/.d.cts declarations
and tests installed consumers. An ESM-only or CommonJS-only package can also be
an intentional supported contract. No one library format is runtime-agnostic or
compatible with every downstream pairing by construction.

### 5) **Common confusion**

A resolution mode models selected host rules for the checker; it is not the host
itself. Successful resolution to a declaration neither verifies the JavaScript
provider nor guarantees that the file was deployed. Relative specifiers, export
conditions, package scope and available artifacts each need appropriate evidence.

Bundler tolerance is useful when a supported bundler completes the graph. It
can conceal a direct-Node failure if that build step is later skipped. Likewise,
a legal NodeNext pair can select the wrong runtime branch when custom conditions
are not aligned. Diagnose the actual failing boundary rather than demanding
that both option strings always be identical.

### 6) **Performance note**

This lesson measures selected paths and outputs, not resolution time or cache
behavior. No fixed one-lookup-per-import cost or zero-cost comparison follows
from choosing a supported pair. Compiler resolution, bundling and runtime loading
perform different work. Use traces for diagnosis and measured diagnostics for
performance questions; a trace is not itself a timing benchmark.

### 7) **Mentor note**

Ask the learner why the extensionless source checks and bundles but the tsc output
fails under native Node. They should identify the missing build step or change
the emitted-target specifier, then run the intended artifact.

Next give them the custom browser condition case. A sound answer predicts both
native outputs and explains why a browser literal annotation did not enforce a
browser runtime branch. Require the condition set and selected file path as
evidence before accepting a proposed configuration change.
