## 3.1. `module` and `moduleResolution` pairing

### 1) **Pairing rules** (matched pairs resolve identically at check and run time)

**Definition** — `module` (emit format: `nodenext`, `bundler`, `commonjs`, `esnext`) and `moduleResolution` (lookup algorithm) must *pair*: `nodenext`↔`nodenext` (Node ESM/CJS semantics), `bundler`↔`bundler` (package-exports-aware, extensionless-friendly), `node16`↔`node16` (versioned Node). Mismatched pairs (`module: nodenext` + `moduleResolution: node10`-legacy) resolve differently at check time (tsc) vs run time (Node/bundler) — imports verifying green then failing to load.

**What problem it solves / history** — legacy defaults (`moduleResolution: node10` carried forward into nodenext-`module` projects) resolved `exports`-mapped subpaths, extensionless ESM imports, and dual-package entry points *wrongly*: tsc found types where Node found nothing (or vice versa) — green CI, `ERR_MODULE_NOT_FOUND` in production. Paired settings make the checker's resolution *simulate* the runtime's (same algorithm, same `exports` handling, same extension rules).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), pair by runtime: Node ESM/CJS apps and libraries → `nodenext`/`nodenext`; bundler-built apps (Vite/Next/webpack) → `bundler`/`bundler`; legacy CJS-only → `node16` + CJS package scope (or modernize to nodenext). Never set one without the other (orphaned `module` with legacy resolution is the mismatch class); verify with `tsc --traceResolution` on one mapped + one relative import per project setup.

**Runnable example** — paired resolution, identical graphs (multi-file sets, nodenext):

```typescript
// file: lib140.ts
export function total140(xs: number[]): number { return xs.reduce((a, b) => a + b, 0); }
// file: app140.ts
import { total140 } from "./lib140.js"; // explicit .js extension (nodenext/Node-ESM requirement)
console.log(total140([1, 2]).toFixed(0)); // 3 — checker + Node resolve identically (paired settings)
// bad — import { total140 } from "./lib140" (extensionless: resolves under bundler/legacy, fails under Node ESM at runtime)
// fix — explicit .js extensions under nodenext (one spelling, both worlds agree)
```

```typescript
// file: lib141.ts
export const V141 = "v";
// file: app141.ts
import { V141 } from "./lib141.js"; // paired resolution (checker simulates Node: exports, extensions, conditions)
console.log(V141.toUpperCase()); // V — agreement by construction (matched pair, verified via traceResolution)
// bad — module: nodenext + moduleResolution: node10-legacy (checker guesses, Node decides — green CI, missing modules in prod)
// fix — pair the settings (nodenext/nodenext or bundler/bundler: matched algorithms, identical graphs)
```

```typescript
// file: entry142.jsonc (tsconfig pairing shapes, documented as config — not compiled)
// Node ESM/CJS: { "module": "nodenext", "moduleResolution": "nodenext" } (paired — default choice)
// Bundler apps: { "module": "esnext", "moduleResolution": "bundler" } (paired — exports-aware, extensionless-tolerant)
// Legacy CJS: { "module": "commonjs" } (resolution pairs automatically — modernize to nodenext when possible)
// file: app142.ts
console.log("pairing-documented"); // settings live in tsconfig (this fence documents the three pairings)
// bad — module without matching resolution (orphaned settings: check-time and run-time graphs diverge silently)
```

**Common confusion** — "resolution is a minor setting" — resolution *is* module loading (which file an import means) — mismatches break loading entirely (not subtly — `ERR_MODULE_NOT_FOUND` at startup). "bundler resolution works for Node" — `bundler` tolerates extensionless/exports-loose imports Node ESM rejects at runtime (dev-green, prod-red across the deploy boundary). "explicit `.js` extensions are ugly" — required by Node ESM (files are URLs — extensionless doesn't resolve) — style follows runtime reality, not preference.

**Performance note** — paired resolution costs one deterministic lookup per import (cached); mismatched resolution costs production outages (unbounded) plus `traceResolution` forensics per incident. Pairing is pure incident prevention at zero steady cost.

**Mentor note** — `tsc --traceResolution` one mapped + one relative import (paired output lines showing identical candidate lists) — resolution made visible in one command. Exercise: mismatch a project deliberately (nodenext + legacy) and run the same imports (divergent candidates = the incident class, demonstrated). Gate: unpaired `module`/`moduleResolution` fail config review.

### 2) **tsc-7 removals** (`node10` resolution gone, `esModuleInterop: false` gone)

**Definition** — tsc 7 removed two legacy options: `moduleResolution: node10` (deleted — use `nodenext`/`bundler`/`node16`; discovered empirically in unit 61) and `esModuleInterop: false` (deleted — interop always on; discovered empirically in unit 61). Removals *force* modernization: configs referencing them error TS5108 at startup (loud, immediate, one fix per option) instead of resolving legacy-semantics silently.

**What problem it solves / history** — legacy options persisted by inertia (configs copied across years carrying `node10` resolution and explicit `esModuleInterop: false`) — each a silent semantic anchor to older TypeScript (legacy lookup, no interop bridging) that newer docs no longer described. Removal converts inertia into errors: upgrade tsc → TS5108 names each dead option → fix by modernizing (pair nodenext, drop the interop toggle) — migration forced kindly, once.

**Modern guidance** — as of the tsc-7 toolchain era (verified `tsc --version` → 7.0.2 in this repo; track era labels TypeScript 5.9/6.0-beta — see version-labeling note below): remove `moduleResolution: node10` (pair `nodenext`/`nodenext` or `bundler`/`bundler`); remove `esModuleInterop: false` (behavior now default-on — delete the line, keep the semantics). Version-label rule: claims about *defaults* carry the toolchain version (`tsc --version`), claims about *language* carry the track era (5.9 labels) — never conflate the two.

**Runnable example** — removals fixed by modernizing (multi-file sets):

```typescript
// file: modern143.ts
export function sum143(xs: number[]): number { return xs.reduce((a, b) => a + b, 0); }
// file: app143.ts
import { sum143 } from "./modern143.js"; // nodenext-paired import (explicit extension, matched resolution)
console.log(sum143([1, 2, 3]).toFixed(0)); // 6 — modern pairing (no legacy options referenced anywhere)
// bad — "moduleResolution": "node10" (TS5108 on tsc 7: option removed — pair nodenext/nodenext instead)
// bad — "esModuleInterop": false (TS5108 on tsc 7: option removed — interop default-on, delete the line)
```

```typescript
// file: interop144.ts
function build144(n: number): number[] { return Array.from({ length: n }, (_, i) => i); }
export = build144; // whole-record shape (interop question applies — see 12/1.3 for the pairing answer)
// file: app144.ts
import build144 from "./interop144.js"; // bridges by default on tsc 7 (no flag needed, no flag available to disable)
// file: app144b.ts
import buildB = require("./interop144.js"); // pairing alternative (flag-independent, every toolchain/version)
console.log(buildB(2).length); // 2 — both consumption styles work (default bridging + require-pairing, no configuration)
// bad — depending on esModuleInterop: false semantics (removed: audit interop-sensitive imports on tsc-7 upgrade)
```

```typescript
// file: vers145.ts
export const toolchain = "tsc-7"; // version reality stated (labels follow reality, not habit)
// file: app145.ts
import { toolchain } from "./vers145.js";
console.log(`verified-on:${toolchain}`); // verified-on:tsc-7 — version claims carry verification (tsc --version per occurrence)
// bad — "works on TS 5.x" claims without verification (defaults differ across majors — interop, resolution, erasability all moved)
// fix — verify per toolchain (npx tsc --version + behavior probe per claim — the version-labeling discipline from unit 61)
```

**Common confusion** — "removals break configs" — removals *error loudly* (TS5108 at startup naming the dead option — kindest possible breakage) vs legacy options *mis-resolving silently* (wrong modules loading green — cruelest). "pinning tsc avoids migration" — pins compound (security, features, editor support all freeze with the compiler) — migrate options (minutes), not toolchains (quarters). "defaults never change" — interop, resolution, and erasability defaults all moved across 5.x→7.x (verified empirically in units 61/67) — version-label every defaults claim, verify per toolchain.

**Performance note** — modern resolution (nodenext/bundler) caches per import identically to legacy (no steady cost); removed-option errors cost one startup failure (seconds, once) vs legacy-misresolution incidents (unbounded). Migrate options eagerly, pin toolchains reluctantly.

**Mentor note** — upgrade tsc on a legacy config live and read each TS5108 (dead option named + fix implied) — removal-as-migration-guide in one command. Exercise: audit one tsconfig per legacy option removed in tsc 7 (node10, esModuleInterop:false, plus deprecated companions) — each a modernization with a compiler-written ticket.

### 3) **Choosing per runtime** (Node ESM, bundlers, libraries — three pairings)

**Definition** — three runtimes, three pairings: Node ESM/CJS execution → `module: nodenext` + `moduleResolution: nodenext` (exact Node semantics incl. `exports` conditions, extension rules, dual-package resolution); bundler-built apps → `module: esnext` + `moduleResolution: bundler` (exports-aware, extensionless-tolerant, `browser` conditions); libraries → clean ESM emit (`module: nodenext`, declarations on) with dual `exports` conditions (import/require) so *consumers'* pairings resolve correctly.

**What problem it solves / history** — one-pairing-everywhere configs (bundler resolution for Node CLIs — extensionless imports crashing at Node load; nodenext for Vite apps — `browser`-conditioned deps resolving server-side) broke across the deploy boundary (dev-green, prod-red per runtime). Runtime-matched pairing makes checker resolution *simulate the deploy target* (same conditions, same extensions, same entry selection) — agreement by construction per runtime.

**Modern guidance** — as of TypeScript 5.9 era, pair per deploy target (Node → nodenext; Vite/Next/webpack → bundler; libraries → nodenext-clean-ESM + dual exports); document the pairing beside the runtime in the README/CONTRIBUTING (one line: "Node 24 ESM: nodenext/nodenext"); re-pair on runtime migration (CJS→ESM, bundler→native — settings migrate with the runtime, same PR).

**Runnable example** — pairing follows the runtime (multi-file sets):

```typescript
// file: node146.ts
export function env(): string { return "node-esm"; } // Node ESM target (nodenext/nodenext in tsconfig)
// file: app146.ts
import { env } from "./node146.js"; // explicit extension (Node requires, checker simulates)
console.log(env().toUpperCase()); // NODE-ESM — paired for the deploy runtime (agreement by construction)
// bad — bundler pairing for a Node CLI (extensionless dev imports crashing at node load: deploy-boundary divergence)
```

```typescript
// file: app147.ts
export function ui(): string { return "bundled"; } // bundler target (esnext/bundler: exports-aware, tolerant)
// file: con147.ts
import { ui } from "./app147.js"; // bundler resolves (conditions per bundler: browser, development, module)
console.log(ui().toUpperCase()); // BUNDLED — paired for Vite/Next/webpack (tolerant where Node is strict)
// bad — nodenext pairing for a Vite app (browser-conditioned deps resolving server-side variants — subtle wrong-module bugs)
```

```typescript
// file: lib148.ts
export function lib(): string { return "lib"; } // library: clean ESM emit (nodenext) + declarations on
// file: con148.ts
import { lib } from "./lib148.js";
console.log(lib().toUpperCase()); // LIB — library emit serves BOTH consumer pairings (dual exports conditions per 12/3.3)
// bad — library emitting CJS-only (ESM consumers get interop wrappers + helper weight — emit for the ecosystem, not the author)
// fix — clean ESM + dual conditions (import/require): consumers' pairings resolve correctly regardless
```

**Common confusion** — "one pairing serves monorepos" — monorepos host *multiple runtimes* (Node services + Vite apps + libraries — per-package tsconfigs extending a base with pairing overrides; `references` propagate declarations across pairings safely). "bundler tolerance is harmless for Node" — tolerance *hides* Node-invalid imports (extensionless, condition-mismatched) until deploy — strictness belongs to the deploy target, not the dev loop. "libraries choose consumers' pairing" — libraries emit *runtime-agnostic* ESM + dual conditions (consumers pair independently — library emit serves all pairings by being standard).

**Performance note** — correct pairing costs nothing steady-state (deterministic lookups, cached); wrong pairing costs deploy-boundary incidents (unbounded) — pairing is pure incident prevention with zero runtime profile.

**Mentor note** — run the same import under both pairings (`traceResolution` diff: candidate lists diverge) — pairing made visible in one command. Exercise: assign each repo package its runtime + pairing in a table (mismatches are pre-filed incidents; fix by re-pairing, same PR as the runtime declaration).
