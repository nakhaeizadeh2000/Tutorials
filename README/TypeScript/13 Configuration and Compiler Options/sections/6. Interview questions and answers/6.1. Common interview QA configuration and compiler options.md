## 6.1. Common interview QA — configuration and compiler options

### 1) **What does `strict: true` enable — and in what order do you triage enabling it?** (family bundle + sequence)

**Definition** — `strict: true` enables `strictNullChecks`, `noImplicitAny`, `strictFunctionTypes`, `strictBindCallApply`, `strictPropertyInitialization`, `noImplicitThis`, `useUnknownInCatchVariables` (+ `alwaysStrict` emit) — one flag, one checking contract. Triage order on legacy code: nullability first (largest class, biggest incident yield), implicit-any second (per-site annotations), variance/init/this last (fewest errors, most architectural).

**What problem it solves / history** — interviewers ask this to test migration judgment beyond rule recall: candidates who sequence (frequency-ordered classes, one per PR) show production experience; candidates answering "enable it all and fix everything" show greenfield-only thinking. The order *is* the seniority signal.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), answer bundle-first (name 5+ members), sequence-second (nullability → any → variance with per-class fix discipline), theater-third (mass-`!` banned — narrowing/annotations only). Full treatment in [1.1. strict](<../1. Strictness Family/1.1. strict and strictNullChecks the nullability contract.md>).

**Runnable example** — bundle + sequence (multi-file sets):

```typescript
// file: fam180.ts
export function nullable(ok: boolean): string | null { return ok ? "y" : null; } // strictNullChecks shapes the signature
export function typed(x: string): string { return x.toUpperCase(); } // noImplicitAny shapes params
// file: app180.ts
import { nullable, typed } from "./fam180.js";
console.log(nullable(true) ?? "n", typed("a")); // y A — family members composing (nullability + annotations, one contract)
// bad — enabling strict + fixing with ! per site (assertion theater: errors silenced, crashes preserved)
// fix — sequence (nullability narrowing first, annotations second, variance last — one class per PR)
```

```typescript
// file: seq181.ts
export function step(ok: boolean): string | null { return ok ? "y" : null; }
// file: app181.ts
import { step } from "./seq181.js";
console.log(step(true) ?? "n", step(false) ?? "n"); // y n — nullability class triaged (biggest yield, mechanical narrowing)
// bad — flag-day strict (800 errors, unreviewable PR, pressured !-assertions — stalled quarterly)
// fix — per-class PRs (reviewable, revertible, compounding weekly — migration that merges)
```

```typescript
// file: variance182.ts
export type Handler182 = (x: { kind: string }) => string; // variance-relevant position (last triage class — architectural)
// file: app182.ts
import type { Handler182 } from "./variance182.js";
const h: Handler182 = (x: { kind: string }) => "got"; // matching direction (compiles — variance satisfied)
// const narrow: Handler182 = (x: { kind: string; at: number }) => "got"; // error TS2322 (narrower param — direction enforced, last class)
console.log("variance-triaged"); // variance errors rarify (fewest, deepest — fixed by design, not annotation)
// bad — disabling strictFunctionTypes to silence direction errors (hole reopened for one smuggled callback)
// fix — widen the callback (direction fixed where written — cheapest location in the pipeline)
```

**Common confusion** — "strict is all-or-nothing" — per-flag overrides exist mid-migration (dated TODOs); all-or-nothing is the *goal*, sequencing is the *path*. "triage order is preference" — frequency-ordered (nullability dominates error counts *and* incident yields); variance-last because rarest, not least important. "mass-`!` unblocks" — unblocks the flag while preserving every crash (theater scoring zero on every axis that matters).

**Performance note** — strict checking costs single-digit percent (measured, not folklore); triage costs authoring minutes per error (one-time); theater costs incidents (unbounded). Sequence for economics, not just aesthetics.

**Mentor note** — strong answers sequence unprompted (nullability → any → variance + per-class fixes); probe with "what do you do with 800 errors?" (sequence, never flag-day) when candidates stop at the bundle list. Hiring signal: migration sequencing predicts production judgment.

### 2) **`isolatedModules` vs `verbatimModuleSyntax` vs `erasableSyntaxOnly` — what does each guarantee?** (three axes)

**Definition** — `isolatedModules`: per-file *transpilability* (no cross-file value knowledge — const-enum imports and ambiguous re-exports fail); `verbatimModuleSyntax`: predictable *emit* (stated traffic only — TS1484 on guessing, statements preserved verbatim); `erasableSyntaxOnly`: deletion-only *syntax* (TS1294 bans enums/namespaces — strippers process every file mechanically). Transpilable × predictable × deletable = toolchain universality.

**What problem it solves / history** — conflated trio ("the strictness flags for modules" — one mental bucket) led to partial adoption (isolated without verbatim: transpilable but divergent; verbatim without erasable: predictable but crashing strippers) — each pair leaving one divergence axis exposed. Distinguished guarantees route each error class correctly (TS1205/TS2748 → isolation; TS1484 → verbatim; TS1294 → erasable).

**Modern guidance** — as of TypeScript 5.9 era, answer axis-first (transpilable/predictable/deletable — one word each), error-second (TS1205+TS2748 / TS1484 / TS1294 mapped per flag), standard-third (all three in base tsconfig — universality by construction). Full treatment in [2.1. isolatedModules](<../2. Erasable and Isolated Toolchain/2.1. isolatedModules single-file transpilation.md>) + [2.2. verbatimModuleSyntax](<../2. Erasable and Isolated Toolchain/2.2. verbatimModuleSyntax predictable emit.md>) + [2.3. erasableSyntaxOnly](<../2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>).

**Runnable example** — three axes, three guarantees (multi-file sets):

```typescript
// file: iso183.ts
export interface Iso183 { a: string } // isolated-safe (no cross-file values needed to transpile this file)
// file: app183.ts
import type { Iso183 } from "./iso183.js"; // verbatim-stated (predictable emit) + erasable (deletion-only)
const v: Iso183 = { a: "x" };
console.log(v.a.toUpperCase()); // X — all three axes satisfied (transpilable + predictable + deletable)
// bad — value-imported types + const-enum member + namespace grouping (one violation per axis — three toolchains disagreeing)
```

```typescript
// file: verb184.ts
export interface Verb184 { b: number }
export const W184 = 1;
// file: app184.ts
import { W184, type Verb184 } from "./verb184.js"; // split traffic (verbatim: values kept, types erased — per-axis honesty)
const w: Verb184 = { b: W184 };
console.log(w.b.toFixed(0)); // 1 — predictable emit (bundlers/strippers see exactly these statements)
// bad — import { W184, Verb184 } (guessing: elision heuristics decide per toolchain — divergence class)
// fix — split syntax (stating replaces guessing — verbatim's entire guarantee in one import line)
```

```typescript
// file: eras185.ts
export const K185 = { A: "A" } as const; // erasable finite set (union + const object — no enum to ban)
export type KU185 = keyof typeof K185;
// file: app185.ts
import { K185, type KU185 } from "./eras185.js";
const k: KU185 = "A";
console.log(K185[k]); // A — deletion-only syntax (strippers process mechanically — TS1294 impossible here)
// bad — enum + namespace equivalents (TS1294 under erasableSyntaxOnly — code generation where deletion was promised)
// fix — unions/const-objects/modules (11/2.2's map + 12/2.1's rule, configured here)
```

**Common confusion** — "one flag covers the trio" — transpilability ≠ predictability ≠ deletability (isolated code can guess imports; verbatim code can declare enums; erasable code can guess re-exports — each pair exposes one axis). "error codes are interchangeable" — TS1205/TS2748 (isolation), TS1484 (verbatim), TS1294 (erasable) — code-first triage routes per flag. "trio is new-project luxury" — per-directory compounding serves legacy equally (new clean, legacy triaged with counters falling).

**Performance note** — trio-clean code starts fastest under stripping runtimes, bundles smallest, transpiles identically everywhere — the performance story *is* the universality story (measured in startup ms + bundle bytes + zero divergence debugging).

**Mentor note** — ask "which guarantee?" per error code (TS1484 → verbatim, TS1294 → erasable, TS1205 → isolation) — axis-first diagnosis transfers to every future flag. Exercise: classify ten config errors by axis before fixing — perfect classification proves the trio internalized as architecture, not checklist.

**Cross-links** — trio standard → [2.3. erasableSyntaxOnly](<../2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>); import discipline → [1.2. import type](<../../../12 Modules Namespaces and Declaration Files/sections/1. ### 3) **Which `module`/`moduleResolution` pair for Node ESM vs bundlers — and what breaks when mismatched?** (pairing + divergence)

**Definition** — Node ESM/CJS → `nodenext`/`nodenext` (exact Node semantics: `exports` conditions, extension rules, dual entries); bundler apps → `bundler`/`bundler` (exports-aware, extensionless-tolerant, `browser` conditions); tsc-7 removed `node10` (TS5108 — modernize) and `esModuleInterop: false` (default-on — delete the line). Mismatched pairs resolve check-time vs run-time graphs differently (green CI, load crashes).

**What problem it solves / history** — unpaired settings (`module` modernized alone, resolution legacy) split graphs silently (tsc finds types one way, Node loads another — `ERR_MODULE_NOT_FOUND` or interop-wrapped `undefined` at startup). Interviewers probe pairing to test deploy-awareness: candidates who match settings to runtimes (and verify via `traceResolution`) reason about production loading, not just checking.

**Modern guidance** — as of TypeScript 5.9 era (plus tsc-7 removal awareness — version-label defaults per toolchain), answer runtime-first (Node → nodenext; Vite/Next → bundler; libraries → clean ESM + dual conditions), mismatch-second (divergent graphs: green check, load crash), verification-third (`traceResolution` per setup). Full treatment in [3.1. module pairing](<../3. Modules Emit and Projects/3.1. module and moduleResolution pairing.md>).

**Runnable example** — paired per runtime (multi-file sets):

```typescript
// file: node186.ts
export function env186(): string { return "node"; } // Node ESM target (nodenext/nodenext)
// file: app186.ts
import { env186 } from "./node186.js"; // explicit extension (Node requires — checker simulates identically)
console.log(env186().toUpperCase()); // NODE — paired agreement (graphs identical by construction)
// bad — bundler pairing for Node CLIs (extensionless dev imports crashing at node load — deploy-boundary divergence)
```

```typescript
// file: modern187.ts
export function sum187(xs: number[]): number { return xs.reduce((a, b) => a + b, 0); }
// file: app187.ts
import { sum187 } from "./modern187.js";
console.log(sum187([1, 2]).toFixed(0)); // 3 — modern pairing (no legacy options referenced — tsc-7 clean)
// bad — "moduleResolution": "node10" (TS5108 on tsc 7: removed — pair nodenext/nodenext or bundler/bundler instead)
// fix — remove dead options (modernize on upgrade — TS5108 names each removal kindly, once)
```

```typescript
// file: interop188.ts
function build188(n: number): number { return n * 2; }
export = build188; // whole-record shape (interop question applies — 12/1.3 owns the pairing answer)
// file: app188.ts
import build188 from "./interop188.js"; // bridged by default (tsc-7 interop-on; TS 5.x needed the flag)
console.log(build188(21).toFixed(0)); // 42 — default bridging (version-labeled: flag era vs default-on era)
// bad — depending on esModuleInterop: false semantics (removed on tsc 7 — audit interop-sensitive imports per upgrade)
```

**Common confusion** — "one pairing serves monorepos" — monorepos host multiple runtimes (per-package tsconfigs extending a base with pairing overrides; references propagate declarations safely across pairings). "bundler tolerance suits Node" — tolerance hides Node-invalid imports (extensionless, condition-mismatched) until deploy — strictness belongs to the target. "removals break configs" — removals error *loudly* (TS5108 naming dead options) vs legacy *mis-resolving silently* — kind breakage vs cruel drift.

**Performance note** — paired resolution costs one deterministic lookup per import (cached); mismatched resolution costs load crashes (unbounded) plus forensics. Pairing is pure incident prevention at zero steady cost.

**Mentor note** — strong answers pair unprompted (runtime → settings, no hesitation); probe with "bundler app, which pair?" (esnext/bundler + why tolerant) and "tsc-7 upgrade breaks what?" (node10 + interop-false removals) when candidates stop at nodenext. Hiring signal: deploy-aware pairing predicts production judgment.

### 4) **When does `noUncheckedIndexedAccess` pay — and what breaks on first enable?** (honesty + backlog)

**Definition** — the flag adds `| undefined` to open index reads (`arr[i]`, `dict[k]` — fixed tuple positions exempt by arity); enabling surfaces dozens of latent crashes as narrow-or-error sites (each a crash that hadn't happened *yet* — the latent-incident backlog, prioritized free). Pays wherever collections index dynamically (caches, pages, queues, registries); costs one narrowing per read (`?.`/`??`/early-return — never `!`).

**What problem it solves / history** — default indexing lies (`users[0]: User` on empty pages — `TypeError` with confident types, green `strict` CI). Interviewers probe this to test crash-class thinking: candidates who answer "dozens of latent crashes surfacing as narrow-sites" show incident economics; candidates answering "stricter types" show vocabulary without judgment.

**Modern guidance** — as of TypeScript 5.9 era, answer honesty-first (open reads gain `undefined` — tuples exempt by arity), backlog-second (enable Friday, triage Monday — density predicts incident density), fix-third (narrowing only — `!` migrations preserve every crash while silencing the flag). Full treatment in [3.3. index honesty](<../3. Modules Emit and Projects/3.3. noUncheckedIndexedAccess and exactOptionalPropertyTypes.md>) + [10/5.1](<../../../10 Arrays Tuples and Collections/sections/5. Common pitfalls to production bugs/5.1. Real production bugs caused by collection misunderstandings.md>) promise 4.

**Runnable example** — honesty enforced (multi-file sets):

```typescript
// file: users189.ts
export interface U189 { name: string }
// file: app189.ts
import type { U189 } from "./users189.js";
function first(users: U189[]): string {
  return users[0]?.name ?? "anonymous"; // honest read (flag or no flag — correct both ways, REQUIRED under it)
}
console.log(first([]), first([{ name: "a" }])); // anonymous a — empty page handled, not thrown
// bad — users[0].name (compiles unflagged — throws on [] — the lie this flag deletes)
```

```typescript
// file: cache190.ts
export const cache190: Record<string, number> = { a: 1 };
// file: app190.ts
import { cache190 } from "./cache190.js";
function get(key: string): string {
  return cache190[key]?.toFixed(0) ?? "missing"; // per-key honesty (missing keys handled, never thrown)
}
console.log(get("a"), get("zzz")); // 1 missing — absence in the type, handled at every read
// bad — cache190[key].toFixed(0) with !-migration (! preserves the crash, deletes the diagnostic — theater)
// fix — ?. + ?? (narrowing: honest undefined handling, uniform across the triage backlog)
```

```typescript
// file: tup191.ts
export type Pair191 = [first: string, second: number]; // fixed positions (arity proves presence — flag exempts)
// file: app191.ts
import type { Pair191 } from "./tup191.js";
function head(p: Pair191): string { return p[0].toUpperCase(); } // p[0]: string (exempt by construction — design with tuples where fixed)
console.log(head(["x", 1])); // X — positions over indexes where shapes are fixed (the flag rewarding tuple design)
// bad — (string | number)[] with positional reads (flag errors every read correctly — open indexing + position assumptions)
// fix — Pair191 (fixed shapes as tuples dodge honestly; open lists narrow honestly — both disciplines, no theater)
```

**Common confusion** — "the flag breaks valid code" — reveals unhandled absence in valid-*looking* code (breakage is diagnosis; `?.` fixes are one line each). "tuples need the same treatment" — fixed positions prove presence by arity (exempt by construction — another reason to prefer tuples for fixed shapes). "`!` migrates faster" — redistributes the lie per site (every crash preserved, flag silenced) — slower *and* dishonest.

**Performance note** — zero emit delta (pure check-time `| undefined`); narrowing branches cost one check each vs unbounded `TypeError`s — highest-ROI flag by post-mortem count in collection-heavy code.

**Mentor note** — ask "how many errors on first enable, and what does each represent?" (dozens; latent crashes pre-triaged) — backlog thinking over strictness theater. Exercise: triage ten flagged reads live (narrow each three ways — `?.`, `??`, early-return — readability compared). Gate: `!` on indexed reads fails review, always.

### 5) **How do you migrate a legacy tsconfig to strict — without a flag-day?** (sequencing + gating)

**Definition** — migration sequence: `strict` family first in class order (nullability → implicit-any → variance/init/this, one class per PR), trio second per directory (re-export kinds → import kinds → enum/namespace migrations), precision flags third (indexed honesty mechanical, optionality intent judgmental) — each green before the next, CI-gated per class, counts tracked weekly. Never flag-days, never theater (`!`/suppression/widening banned in migration PRs).

**What problem it solves / history** — flag-day migrations (all flags + all errors, one PR) stalled quarterly (unreviewable, conflicting, pressuring suppression — suppressed diagnostics preserving untranspilable designs, `!`s preserving crashes). Sequenced migration merges weekly (reviewable, revertible, compounding) — same total triage distributed across green PRs instead of one red quarter.

**Modern guidance** — as of TypeScript 5.9 era, answer sequence-first (class order per family, families ordered strict → trio → precision), discipline-second (narrow/annotate/state — never suppress/assert/widen), gating-third (per-class CI gates before next class). Full playbook in [4.1. Configuration checklist](<../4. Important points to remember/4.1. Configuration checklist mental models mentors insist on.md>) promise 4 + [1.1. strict](<../1. Strictness Family/1.1. strict and strictNullChecks the nullability contract.md>) promise 3.

**Runnable example** — sequenced green (multi-file sets):

```typescript
// file: seq192.ts
export interface Item192 { title: string }
// file: app192.ts
import type { Item192 } from "./seq192.js";
function titleOf(items: Item192[]): string {
  return items[0]?.title ?? "untitled"; // nullability class (first — biggest yield, mechanical narrowing)
}
console.log(titleOf([]), titleOf([{ title: "a" }])); // untitled a — class triaged (green PR, compounding)
// bad — strict + trio + honesty in one PR (mixed disciplines, unreviewable volume, rubber-stamped theater)
// fix — sequence (one class per PR: uniform fix discipline, reviewable throughout, green each)
```

```typescript
// file: seq193.ts
export const seen193: string[] = []; // implicit-any class (declared state — second after nullability)
// file: app193.ts
import { seen193 } from "./seq193.js";
console.log(seen193.length); // 0 — annotated evolution (per-site fixes, precision ratio as team metric)
// bad — const seen: any[] (keeps the hole: pushes unchecked, reads untrusted — class un-triaged, incidents queued)
// fix — declare element types (annotation fixes scale linearly, reviewably — class two of three)
```

```typescript
// file: gate194.ts
export const classes = ["nullability", "implicit-any", "variance"] as const; // gated sequence (CI green per class before next)
// file: app194.ts
import { classes } from "./gate194.js";
console.log(classes.join("→")); // nullability→implicit-any→variance — compounding green (never big-bang red)
// bad — single big-bang gate (all-or-nothing CI: red for a quarter, force-merged red — gates as decoration)
// fix — per-class gates (each green before next starts — compounding green, revertible steps)
```

**Common confusion** — "sequencing slows migration" — sequenced PRs merge weekly (reviewable); flag-days stall quarterly (unreviewable) — sequencing is *faster* wall-clock, not just safer. "small teams skip process" — one checklist per PR (class named, fixes uniform, gate green) — process scales down to a line; theater scales down to nothing (small teams feel incidents *more*). "theater unblocks" — unblocks flags while preserving crashes (suppression/`!`/widening keep incidents, delete diagnostics) — unblocking theater ships the incident queue faster.

**Performance note** — triage costs authoring minutes per error (one-time); theater costs incidents (unbounded, recurring); gates cost CI seconds per class (parallelizable) — audit economics favor completion heavily at every team size.

**Mentor note** — strong answers sequence unprompted (class order + per-class fixes + gating) — probe with "800 errors Monday, what ships Friday?" (one triaged class, green) when candidates answer flag-day. Hiring signal: sequencing predicts production judgment; flag-day answers predict stall quarters.
