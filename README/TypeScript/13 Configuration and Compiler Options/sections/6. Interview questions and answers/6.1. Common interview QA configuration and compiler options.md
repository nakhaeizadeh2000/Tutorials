## 6.1. Common interview QA — configuration and compiler options

Good configuration answers identify the compiler version, checked program and
artifact consumer, then propose a check that could disprove the claim. Use these
questions to connect the domain's worked projects. Memorizing an option list or
migration order is not enough to establish the resulting runtime behavior.

### 1) **Does strict mean every potentially unsafe operation is rejected?**

No. Strict enables a versioned checking family, with individual overrides and
some dependent behavior. It includes null checks, implicit-any checks, function
checking, initialization checks, catch-variable checking and built-in iterator
return checking. It does not enable every stricter option. Indexed-access,
exact-optional-property and implicit-override choices remain separate.

The [strict-family project](<../1. Strictness Family/1.1. strict and strictNullChecks the nullability contract.md>)
compares null-only, implicit-any-only and full checks, accepted assertions and
changed declarations. It also verifies that TypeScript 7 no longer permits
alwaysStrict false: JavaScript strict mode and checker strictness are different
concepts. The [any/catch project](<../1. Strictness Family/1.2. noImplicitAny and useUnknownInCatchVariables.md>)
shows declared/contextual any still entering strict code and Promise.catch needing
its own unknown callback annotation.

For a compact probe, use TypeScript 7.0.2 and Node 20.20.2 in a fresh directory
without a tsconfig. Save:

```typescript
// file: probe.mts
interface Item { value: string }
const items: Item[] = [];
const raw: any = { value: 7 };
const item: Item = raw;
const first = items[0];
console.log(typeof item.value, first?.value ?? "missing");
// const required: Item = first;
// const patch: { value?: string } = { value: undefined };
```

```sh
tsc --strict --isolatedModules --verbatimModuleSyntax --erasableSyntaxOnly --noUncheckedIndexedAccess --exactOptionalPropertyTypes --target es2022 --module nodenext --moduleResolution nodenext --outDir dist probe.mts
node dist/probe.mjs
```

It prints `number missing`. The selected checks pass; raw's any type still lets
a number masquerade as a string property. Activate the two negative lines
separately and replace outDir with noEmit: the required assignment reports TS2322
and the optional-property object reports TS2375. Ask why those particular added
options expose the negatives without validating raw. A useful answer separates
checker admission from runtime data validation.

### 2) **How do isolated, verbatim and erasable checks differ?**

IsolatedModules checks selected constructs that are problematic for single-file
JavaScript processing; tsc still checks imported source. Ordinary source-defined
const enums can cross files and are preserved under the flag. Ambient const-enum
member access is a different restricted case. IsolatedDeclarations instead asks
for sufficient exported annotations for declaration production. The
[isolation project](<../2. Erasable and Isolated Toolchain/2.1. isolatedModules single-file transpilation.md>)
executes those contrasts.

VerbatimModuleSyntax removes marked type traffic and retains unmarked runtime
imports according to its module rules. Valid class imports used only for type
annotations can remain. Inline-only imports can leave an empty evaluation edge,
and supported extension rewriting still changes paths. It rejects ESM value
syntax in a CommonJS file instead of silently transforming that syntax. The
[verbatim project](<../2. Erasable and Isolated Toolchain/2.2. verbatimModuleSyntax predictable emit.md>)
tests each configuration consequence.

ErasableSyntaxOnly restricts TypeScript forms needing nontrivial generation,
including runtime namespaces, enums, parameter properties, import/export assignments
and prefix assertions. Ambient or type-only namespace contexts differ from
value-bearing implementations. The [bounded trio owner](<../2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>)
keeps the inventory and source/emitted graph. A pass still does not certify a
runtime parser, API availability or every package import. Diagnose the particular
syntax or artifact boundary rather than multiplying three words into a universal
compatibility claim.

### 3) **Which module settings should a Node or bundler project use?**

Start from the consuming process. Native Node projects commonly use nodenext
with its NodeNext resolution model. A bundler can use preserve or esnext with
bundler resolution; TypeScript 6 also introduced support for commonjs with bundler
resolution. Bundler is not itself a module emit value. Some contradictory explicit
settings produce configuration errors, and omitted settings can receive supported
defaults. Both strings need not be written identically.

The [resolution project](<../3. Modules Emit and Projects/3.1. module and moduleResolution pairing.md>)
checks an extensionless import, bundles it successfully and then demonstrates
why direct execution of tsc's intermediate output fails. It also supplies a local
browser/node/fallback package: a browser custom condition accepted by the checker
does not configure Node, which can still execute its node branch. Bundler mode
does not automatically supply every browser condition either.

A strong answer names the selected file format, condition set and actual emitted
or bundled target, then runs it. TraceResolution identifies checker candidates;
it is not evidence that Node opened the same declaration file. For a compiler
upgrade, test removed-option diagnostics against the named version and follow
the [current migration list](<../../../25 Update TypeScript 7.0/sections/1. Configuration Migration/1.1. Configuration defaults and removed options.md>).

### 4) **What do indexed and exact optional checks prove?**

NoUncheckedIndexedAccess adds possible absence to unchecked indexed reads.
Declared properties, tracked writes and required fixed tuple positions can have
stronger evidence; optional tuple positions still permit undefined. A loop length
condition does not generally establish every array index read. Missing data may
need a fallback, an optional result or an error according to the API.

ExactOptionalPropertyTypes constrains optional-property assignment: omission and
an explicit undefined value can require different declared contracts. A required
string-or-undefined property remains required even with the flag off. Unguarded
optional reads still permit absence. Neither spelling supplies keep-current or
clear semantics automatically.

The [combined option project](<../3. Modules Emit and Projects/3.3. noUncheckedIndexedAccess and exactOptionalPropertyTypes.md>)
reproduces the index and spread failures, in-versus-own-property behavior and JSON's
omission of an undefined object property. Ask the learner to define a clearable
JSON update protocol, not simply add undefined to an interface. The type contract,
runtime presence policy and transport representation need to agree.

### 5) **Does a green declaration or project build certify a release?**

Identify what the command actually checked and emitted. Declaration generation
records the compiler's view, which can still include an asserted lie. A declaration
map references source paths and needs supported tooling and available files for
navigation. It is not evidence that an editor or debugger was tested.

The [two-project build](<../3. Modules Emit and Projects/3.2. declaration composite project references.md>)
orders core/app work and checks built declarations. It also shows a direct built
import accepted without a reference: references are not a universal import
allow-list. A body edit can change runtime behavior without changing the public
signature. Force rebuild is not full directory cleanup, and an earlier output
can survive a failed new build.

SkipLibCheck is another evidence boundary. The [local configuration failures](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by configuration misunderstandings.md>)
hide a missing declaration type, observe the resulting any leak and runtime
failure, and verify that a known argument signature still checks. Choose the
option with an explicit accuracy/performance trade-off, not a blanket claim that
generated declarations are always correct or consumer checking can never weaken.

For an actual library release, inspect and install its tarball and run supported
consumers. The [packed-package project](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>)
executes that boundary. Emitting ESM once and writing dual metadata does not create
a CommonJS implementation. Declaration-only emit can also support a separate
JavaScript emitter; value exports still need actual providers.

### 6) **How should a legacy configuration migration be planned?**

Inventory compiler versions, effective settings, included/imported files, build
commands and deployed entry points. Run candidate checks and group diagnostics
by the operation they expose. Review caller behavior and declaration changes,
then select a manageable scope. A small project can migrate together; a large one
may benefit from staged changes. No language rule requires nullability first,
variance last or one particular number of changes per pull request.

Use the [integrated checkpoint](<../4. Important points to remember/4.1. Configuration checklist mental models mentors insist on.md>):
its strict syntax-checked baseline still has two runtime failures, and the repairs
need stated missing-product/update policies. A falling diagnostic count helps
track work but does not prove unchanged behavior. Assertions or widening need
justification from a real invariant; they are not automatically either correct
repairs or forbidden operations.

Options apply to programs. A directory TODO does not create a compiler exemption,
exclude does not prevent every imported file from entering a program, and a lint
rule cannot guarantee loader compatibility. Keep current checks passing for the
intended scope and preserve precise evidence for the remaining work.

### 7) **Common confusion**

Compiler checks, emitted syntax, runtime imports and package contents answer
different questions even when their diagnostics point near the same source line.
A correct response names which boundary changed and proposes an observation that
could reveal a wrong assumption.

Likewise, a checklist or lint convention is not a language rule. Distinguish team
preferences from required compiler dependencies and actual supported combinations.
Avoid using fixed error counts, migration dates or tool names as substitutes for
explaining the consumer contract.

### 8) **Performance note**

The probe establishes acceptance, diagnostics and output, not compiler overhead
or bundle/startup rankings. Type-only code still contributes checker work; emitted
JavaScript and runtime validation have their own costs. Compare matching fresh,
unchanged and edited build states when evaluating speed. No fixed flag overhead,
per-import lookup count or per-error triage duration is justified here.

### 9) **Mentor note**

Begin with the probe and ask which annotations are trusted, which reads can be
missing and what happens if the extra flags are removed. Then vary one boundary:
change the module consumer, omit the runtime provider or inspect a stale declaration.
A strong answer predicts the relevant diagnostic or runtime observation and can
choose its worked owner.

Assess the reasoning, including limits and a falsifiable next check. Memorized
“strict, trio, precision” sequences or universal “all pipelines agree” claims
should prompt a concrete counterexample, not be treated as a seniority signal.
