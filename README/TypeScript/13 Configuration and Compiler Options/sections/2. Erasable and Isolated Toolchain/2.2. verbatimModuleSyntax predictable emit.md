## 2.2. verbatimModuleSyntax — predictable emit

Verbatim module checking makes type markers and module format more consequential.
It removes whole type-only statements and marked specifiers while retaining
unmarked runtime imports, rather than eliding them solely from type-position use.
It also rejects ESM value syntax when the file's selected output format is
CommonJS. These are bounded compiler rules, not a promise that all tools emit
byte-identical files or execute the same graph.

The [type-import lesson](<../../../12 Modules Namespaces and Declaration Files/sections/1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>)
owns statement/specifier mechanics and inline-only empty imports. Here we
configure an inherited project and test adoption consequences. Use TypeScript
7.0.2, Node 20.20.2 for emitted JavaScript and Node 22.18.0 for source execution.

### 1) **Make the effective project configuration observable**

Create these two JSON files at the project root and the sources below in `src`.
Remove the `// file:` labels when saving JSON. The derived config supplies root
files; its relative paths are interpreted from its own location.

```json
// file: tsconfig.base.json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "verbatimModuleSyntax": true,
    "rewriteRelativeImportExtensions": true,
    "noEmitOnError": true,
    "types": []
  }
}
```

```json
// file: tsconfig.json
{
  "extends": "./tsconfig.base.json",
  "compilerOptions": { "rootDir": "src", "outDir": "dist" },
  "files": ["src/annotation.mts", "src/mixed.mts", "src/types.mts"]
}
```

```typescript
// file: src/model.mts
console.log("model evaluated");
export interface Config { mode: "dev" | "prod" }
export class Model { value = "model"; }
export const port = 80;
// file: src/annotation.mts
import { Model } from "./model.mts";
const local: Model = { value: "local" };
console.log(local.value);
// file: src/mixed.mts
import { port, type Config } from "./model.mts";
const config: Config = { mode: "dev" };
console.log(port, config.mode);
// file: src/types.mts
import type { Model, Config } from "./model.mts";
const config: Config = { mode: "prod" };
const local: Model = { value: "local" };
console.log(config.mode, local.value);
```

```sh
tsc -p tsconfig.json --showConfig
tsc -p tsconfig.json
node dist/annotation.mjs
node dist/mixed.mjs
node dist/types.mjs
```

The showConfig result confirms inherited verbatim and rewrite settings and the
selected roots. Each runtime command starts a fresh process:

| Entry | Output |
|---|---|
| annotation | `model evaluated`, then `local` |
| mixed | `model evaluated`, then `80 dev` |
| types | `prod local` |

Model has both an instance type and a runtime constructor. Annotation uses only
its type, but the unmarked import is legal under verbatimModuleSyntax and remains
in output, so model evaluates. The flag does not force every type-position use
of a value-bearing declaration to become import type. Config is an interface;
removing its inline type marker from mixed instead reports TS1484.

A mixed value/type import is valid. Requiring two separate statements is a style
choice unless whole-statement erasure changes the desired evaluation behavior.
The [official option reference](https://www.typescriptlang.org/tsconfig/verbatimModuleSyntax.html)
shows marked-specifier removal and the retained empty-import case.

### 2) **Compare retention and rewriting without assuming byte identity**

Inspect the emitted entries. Annotation retains a Model import, types has no model
import, and mixed keeps port while dropping Config. The retained paths name
`./model.mjs`: the [relative extension-rewrite option](https://www.typescriptlang.org/tsconfig/rewriteRelativeImportExtensions.html)
changes the source `.mts` suffix in output. “Verbatim” does not override that
supported rewrite or preserve exact whitespace and bytes.

Now compare the same sources with the flag off and output in a fresh directory:

```sh
tsc -p tsconfig.json --verbatimModuleSyntax false --outDir elided
node elided/annotation.mjs
node elided/mixed.mjs
node elided/types.mjs
```

Annotation now prints only `local`: its type-position-only Model import was
elided. Mixed still evaluates model because port is a runtime binding. Types
still prints `prod local`. Enabling the flag can therefore add evaluation that
previous elision omitted, even when the source already passes the checker.
Decide whether evaluation is intended before performing a project-wide rewrite.

To omit that dependency deliberately, change annotation to `import type { Model }`
and rebuild with verbatim enabled. Its fresh-process output is then only local.
If initialization is required, retain an intentional value or side-effect edge;
the [registration failure project](<../../../12 Modules Namespaces and Declaration Files/sections/5. Common pitfalls to production bugs/5.1. Real production bugs caused by module misunderstandings.md>)
shows why changing a marker alone cannot install a plugin.

The source paths also support this declared Node source runner:

```sh
npm exec --yes --package=node@22.18.0 -- node src/annotation.mts
npm exec --yes --package=node@22.18.0 -- node src/types.mts
```

With the original unmarked Model import restored, the source outputs match their
original emitted entries. These runs verify this source graph, not TypeScript
checker execution inside Node. A retained `.mjs` source specifier would require
that output file to exist at the named source location; the rewrite flag does
not configure the Node loader.

### 3) **Resolve CommonJS classification errors as format decisions**

The .mts entries are explicitly ESM. A .cts entry is CommonJS under NodeNext, so
its ESM value import cannot be silently rewritten with verbatim enabled. Save:

```typescript
// file: src/cjs.cts
import { port } from "./model.mjs";
console.log(port);
```

```json
// file: tsconfig.cjs.json
{
  "extends": "./tsconfig.json",
  "files": ["src/cjs.cts"],
  "compilerOptions": { "outDir": "cjs-dist" }
}
```

```sh
# Expected TS1286:
tsc -p tsconfig.cjs.json --noEmit
# Deliberate CommonJS transformation:
tsc -p tsconfig.cjs.json --verbatimModuleSyntax false
node cjs-dist/cjs.cjs
```

The weaker setting permits transformation and the run prints `model evaluated`,
then 80 on Node 20.20.2. This is that version's synchronous require-of-ESM path;
a graph containing top-level await has different loading requirements. The
[CommonJS interop owner](<../../../12 Modules Namespaces and Declaration Files/sections/1. ES Modules/1.3. export equals and interop with CommonJS.md>)
executes that contrast rather than relying on historical blanket rules.

For an explicit CommonJS consumer with verbatim retained, replace cjs's import
with `import model = require("./model.mjs")` and print `model.port`. Building the
same CJS project with verbatim enabled now passes and the runtime prints the
same two lines. This older import-assignment form is intentionally transformed;
it is not compatible with an erasableSyntaxOnly source gate. Choosing ESM instead
would mean changing the file/package contract, not merely adding type markers.

### 4) **Adopt the option at real program boundaries**

Inspect the effective inherited configuration and classify diagnostics before
editing. TS1484 asks for an explicit type-only marker on the relevant interface
import. TS1286 asks whether the file is intended to be CommonJS and whether
transformation is allowed. A valid unmarked class import may instead require an
initialization decision even though it reports neither error.

Options apply to the checked program. A directory name alone does not select a
different verbatim mode for its imports. Separate configs can model real project
boundaries, but included dependencies still participate in each program. The
[extends reference](https://www.typescriptlang.org/tsconfig/extends.html) documents
inherited settings, root-list replacement and relative-path interpretation; the
CJS config above replaces the original root list rather than adding an independent
per-file exemption.

For small projects, one reviewed change may be sufficient; larger migrations can
use smaller verified steps. Keep runtime behavior checks and inspect the selected
output. A lint rule may establish additional style conventions but cannot prove
loader compatibility or make every future change safe. Compare meaningful
outputs and module evaluation rather than expecting a tsc file and a bundled
entry chunk to have identical text.

### 5) **Common confusion**

Verbatim is not “no emit transformation at all.” Type markers disappear, supported
relative suffixes can be rewritten, and import assignment has its own CommonJS
transformation. Nor does the flag reject every value binding used only in a type
position: Model's accepted retained import demonstrates that boundary.

Removing a type statement does not erase every dependency path. Mixed still
loads model through port. Conversely, keeping an unused value import can add
side effects relative to an older elision-based build. Decide the intended graph
and verify it; a falling diagnostic count alone does not establish unchanged
initialization behavior.

### 6) **Performance note**

This project measures evaluation outputs, not compiler speed or bundle size.
Verbatim can retain an import elision would remove, so startup work can change.
A type-only statement can avoid that edge if no other edge loads the dependency.
Downstream bundlers still analyze imports, side effects and exports. No universal
speedup, free CI run or pipeline-equality guarantee follows from this option.

### 7) **Mentor note**

Ask why annotation checks successfully yet evaluates model, and why Config needs
a marker while Model does not. Then compare flag-on and flag-off output in fresh
processes. A sound explanation follows declaration kind, import syntax and the
remaining runtime uses rather than calling every import conversion an optimization.

For CJS adoption, ask which file format the project selects and which loader runs
the output. Require the proposed syntax or format change to pass the actual
project check and runtime entry. This keeps a module-classification repair from
becoming an unrelated bulk type-import rewrite.
