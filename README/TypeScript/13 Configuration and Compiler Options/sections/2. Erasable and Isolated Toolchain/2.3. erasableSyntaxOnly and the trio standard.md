## 2.3. `erasableSyntaxOnly` and the trio standard

A source-running pipeline needs restrictions the checker can enforce, plus runtime tests for what flags cannot prove. This lesson configures three related checks and runs a small module graph from source and emitted JavaScript. It assumes the [execution paths](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>) and [type-only imports](<../../../12 Modules Namespaces and Declaration Files/sections/1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>).

Verified 2026-10-12 with TypeScript 7.0.2 and Node 22.18.0. The worked graph is ESM, using `.mts` source and `.mjs` output; it has no package dependencies. No Babel, SWC or bundler integration is implied by the Node checks.

### 1) **Deletion-only syntax gate**

`erasableSyntaxOnly`, introduced in TypeScript 5.8, rejects several TypeScript forms a stripping pipeline cannot handle. The inventory is broader than enums and namespaces: it includes parameter properties, non-ECMAScript import/export assignments and prefix-style assertions. A namespace containing only type declarations differs from a namespace containing runtime code. The [option reference](https://www.typescriptlang.org/tsconfig/erasableSyntaxOnly.html) is the precise inventory owner.

| Restricted source form | Possible migration, with a trade-off to check |
|---|---|
| `enum` | A const object and derived union; verify callers that relied on numeric values or reverse mapping |
| Namespace/module containing runtime code | File-scoped exports; verify module loading and grouping changes |
| Constructor parameter property | Declare a field and assign it in the constructor; preserve initialization behavior |
| `import =` / `export =` | ECMAScript module forms where consumers support them; review CommonJS interop |
| `<number>value` assertion | `value as number`; neither spelling validates the value |

To observe the gate, save `restricted.ts` in a separate directory without a `tsconfig.json` and run `tsc --strict --erasableSyntaxOnly --noEmit restricted.ts`. This is an intentional failing check, not a script to execute:

```typescript
// restricted.ts
export {};
enum OldKind { A, B }
namespace RuntimeGroup { export const value = 1; }
class Point { constructor(public x: number) {} }
const asserted = <number>1;
```

The tested compiler reports TS1294 at the four restricted forms. Removing a restriction is a design choice, not a text substitution: for example, replacing a numeric enum with strings may change a public serialization contract. [Enum migration](<../../../11 Enums and Literal Types/sections/2. Enums vs Erasable Alternatives/2.2. erasableSyntaxOnly the enum ban and migration.md>) owns that larger comparison.

### 2) **The trio as project standard**

The flags guard different risks. None installs packages, configures a runtime resolver or guarantees that every transpiler produces identical behavior.

| Check | Bounded responsibility | Still verify separately |
|---|---|---|
| `isolatedModules` | Detect certain constructs incompatible with single-file processing | Actual transformer/version support |
| `verbatimModuleSyntax` | Make type-only traffic explicit and preserve value module syntax | Module context and side-effect expectations |
| `erasableSyntaxOnly` | Reject the restricted TypeScript forms above | JavaScript parser support, imports and APIs |

For example, decorator source can pass these checks yet fail Node 22.18.0's parser. The [execution lesson](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>) demonstrates that failure. The detailed flag contracts belong in [isolatedModules](<./2.1. isolatedModules single-file transpilation.md>) and [verbatimModuleSyntax](<./2.2. verbatimModuleSyntax predictable emit.md>); their [primary](https://www.typescriptlang.org/tsconfig/isolatedModules.html) [references](https://www.typescriptlang.org/tsconfig/verbatimModuleSyntax.html) explain the checking/emit distinction.

Create this project in a new directory. Save `tsconfig.json` at its root and the two `.mts` files inside `src`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "lib": ["es2022", "dom"],
    "types": [],
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "erasableSyntaxOnly": true,
    "rewriteRelativeImportExtensions": true,
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": ["src/**/*.mts"]
}
```

```typescript
// src/kinds.mts
export const KIND = { A: "A", B: "B" } as const;
export type Kind = keyof typeof KIND;
export function label(kind: Kind): string { return `Kind:${KIND[kind]}`; }
```

```typescript
// src/app.mts
import { label } from "./kinds.mts";
import type { Kind } from "./kinds.mts";
const selected: Kind = "A";
console.log(label(selected));
```

With TypeScript 7.0.2 and Node 22.18.0, run:

```bash
tsc --project tsconfig.json --noEmit
node src/app.mts
tsc --project tsconfig.json
node dist/app.mjs
```

Both executions print `Kind:A`. The checker succeeds, the source importer names an actual `.mts` file, and emission rewrites that relative specifier to `./kinds.mjs`. Inspect `dist/app.mjs`: the separate type-only import is gone; the value import remains with the output extension. [rewriteRelativeImportExtensions](https://www.typescriptlang.org/tsconfig/rewriteRelativeImportExtensions.html) controls that rewrite. It is an additional setting, not a property of the trio.

An emitted-only project can instead use an output extension in its source import under a compatible resolution mode. Do not assume that source execution will then find a `.mjs` file which was never emitted beside it. Nor does the rewrite option turn an alias or arbitrary package specifier into a relative runtime path. Declare which graph you intend to run.

### 3) **Adopting per directory**

First identify the actual checking, building and execution commands. Enable the relevant checks on a small representative package or directory and group diagnostics by cause. Type traffic may need only an `import type` change; a runtime namespace or enum may need a compatibility decision and consumer tests. Separate those changes when doing so makes review and rollback clearer.

A directory is not necessarily its own compiler program. Use the project's include patterns, package boundaries or reference graph to define a manageable migration unit. Configuration inheritance can help keep packages aligned, but verify the effective configuration and actual file set rather than assuming all source is covered.

Practice with the worked graph: change the second import to `import { Kind } ...` and run the check. The compiler reports TS1484 because `Kind` is a type. Restore `import type`, then change only the value import's extension to `./kinds.mjs`. The compiler can resolve the source equivalent, but native source execution fails if that `.mjs` file does not exist in `src`. Restore `.mts` and observe both paths again. One change exercises a static flag; the other exposes a runtime resolution assumption.

When recording progress, name diagnostic categories, affected files and the tests actually run. A zero counter for a few error codes is not proof of runtime equivalence, and a lint rule does not make regressions impossible. Document any exception's reason, scope and revisit condition; avoid suppressing a diagnostic merely to make the metric fall.

### 4) **Common confusion**

“Erasable” describes supported syntax removal, not a promise about the whole program. The wrong import extension can fail before any application code runs, and an unavailable runtime API can fail afterward. Those failures need resolver or support checks, not a different interpretation of TS1294.

The flag also does not require deleting an ambient declaration that describes another library. Describing a runtime object in a `.d.ts` file and generating that object from an implementation file are different jobs. A declaration alone does not create the object.

### 5) **Performance note**

These flags constrain source/emit choices; they do not establish a startup speed or bundle-size ranking. Runtime transforms, emitted constructs, module evaluation and dependency loading each have costs that depend on the program. The experiments here verify behavior and resolution, not timing. Replacing an enum may also change its representation, so assess semantics before measuring cost.

Migration and CI have operational costs too. A focused unit with observable checks can be easier to review than a large mixed change, but no fixed duration or saving applies to every codebase.

### 6) **Mentor note**

Ask a learner to identify which promise each failing experiment disproves. The type import violates a compiler rule; the missing `.mjs` violates a runtime file assumption. A strong answer explains why three successful flags cannot fill that missing file.

Have them review a proposed enum replacement for a serialized public API, then define the tests needed before accepting it. Good advice preserves the contract or explicitly plans its migration, rather than calling every replacement equivalent.
