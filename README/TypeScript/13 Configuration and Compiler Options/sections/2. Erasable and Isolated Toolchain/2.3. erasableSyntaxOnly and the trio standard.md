## 2.3. `erasableSyntaxOnly` and the trio standard

### 1) **Deletion-only syntax gate** (TS1294 bans enums/namespaces project-wide)

**Definition** — `erasableSyntaxOnly: true` (TS 5.8) errors (TS1294) on syntax no syntax-only transpiler can process by deletion: `enum` declarations (emit objects) and `namespace` groupings (emit IIFEs) — the only two declaration forms with runtime output. Everything else (types, interfaces, `import type`, literals, generics) deletes cleanly. [11/2.2](<../../../11 Enums and Literal Types/sections/2. Enums vs Erasable Alternatives/2.2. erasableSyntaxOnly the enum ban and migration.md>) owns the enum migration map; this promise owns *configuring* the gate (enabling, triaging TS1294s, verifying across toolchains).

**What problem it solves / history** — syntax-only runtimes (Node 22.12+ stripping, esbuild/swc/Babel single-file) crashed or diverged on enums/namespaces (generated code no deleter can produce — transpilers either errored opaquely or emitted subtly different semantics). The gate converts toolchain incompatibility into authoring errors: untranspilable declarations fail at `tsc` (with migration pointers) instead of at customer load (with stack traces).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), enable the flag in new projects (with the trio partners below); migrate legacy enums/namespaces per 11/2.2's map + 12/2.1's avoidance rule (one declaration per PR — union/const-object/module replacements, tests green throughout). Verify with stripping execution (`node --experimental-strip-types` on entry files — runs prove deletability, not just checking).

**Runnable example** — gate enforced, replacements runnable (multi-file sets; TS1294 demos as commented errors):

```typescript
// file: kinds131.ts
export const KIND131 = { A: "A", B: "B" } as const; // erasable replacement (deletion-only emit)
export type Kind131 = keyof typeof KIND131; // "A" | "B" — union derived erasably
// file: app131.ts
import { KIND131, type Kind131 } from "./kinds131.js";
const k: Kind131 = "A";
console.log(KIND131[k]); // A — enum-free finite set (works under stripping, bundlers, tsc alike)
// enum Old131 { A, B } // error TS1294 under erasableSyntaxOnly (declaration form banned, not the concept)
```

```typescript
// file: mods132.ts
export function twice(n: number): number { return n * 2; } // module replaces namespace (file scope groups)
// file: app132.ts
import { twice } from "./mods132.js";
console.log(twice(21).toFixed(0)); // 42 — module grouping (erasable) vs namespace IIFE (banned)
// namespace Old132 { export const X = 1 } // error TS1294 (IIFE emit un-deletable — modules do the grouping)
// fix — file scope + named exports: same organization, deletion-only syntax
```

```typescript
// file: trio133.ts
export interface Trio133 { a: string }
export type { Trio133 as TrioAlias }; // export-type aliasing (stated, erasable — verbatim-safe too)
// file: app133.ts
import { type TrioAlias } from "./trio133.js";
const t: TrioAlias = { a: "x" };
console.log(t.a.toUpperCase()); // X — the erasable inventory composed (types + type-only traffic, zero bans triggered)
// bad — same shape with enum status + namespace grouping (two TS1294s: migration per 11/2.2 + 12/2.1, one PR each)
```

**Common confusion** — "the flag bans useful features" — bans two *forms* (enum/namespace declarations) with documented replacements (unions/const-objects/modules — strictly more composable); features (finite sets, grouping) migrate fully. "TS1294 errors are cryptic" — each names the banned form *and* the flag (grep-able, documented, one-fix-per-error — clearest diagnostics in the strict family). "stripping runtimes need the flag" — runtimes strip regardless (crashing on untranspilable syntax); the flag makes *tsc* agree with strippers at authorship (one contract, two enforcers).

**Performance note** — deletion-only files strip in microseconds (no transpile decisions — syntax deletes mechanically); enum/namespace emit costs table/IIFE bytes + evaluation (deleted with the forms). Startup wins concentrate in stripping runtimes (the flag's primary audience).

**Mentor note** — run one entry file under Node stripping with and without an enum (runs vs TS1294/crash) — deletability demonstrated, not asserted. Exercise: migrate one enum + one namespace per the maps and execute the entries under three runtimes (tsc-emit, esbuild-bundle, node-strip) — universality proven per migration.

### 2) **The trio as project standard** (isolated + verbatim + erasable — guaranteed processability)

**Definition** — the complete standard: `isolatedModules: true` (per-file transpilable) + `verbatimModuleSyntax: true` (predictable emit, stated traffic) + `erasableSyntaxOnly: true` (deletion-only syntax) — together guaranteeing *every file* processes identically under `tsc`, esbuild, swc, Babel, Vite, and Node stripping. Three flags, one property: toolchain universality by construction, verified by dual-pipeline CI.

**What problem it solves / history** — partial adoption (isolated without verbatim: transpilable but divergent emit; verbatim without erasable: predictable but crashing strippers on enums) left *some* files toolchain-locked — the ones nobody remembered, discovered mid-migration (Node-stripping pilot choking on a `const enum`, esbuild diverging on an elided import). The trio as a *project standard* (all three in base tsconfig, inherited everywhere) makes universality a repo property, not a per-file lottery.

**Modern guidance** — as of TypeScript 5.9 era, set all three in the base tsconfig new projects inherit (no per-package opt-outs without dated reasons); migrate legacy repos per-directory (new code trio-clean, legacy triaged error-class by error-class); verify with dual-pipeline CI (tsc typecheck + a per-file transpiler executing the same tests — divergence fails the build). Track trio violations as a single metric (TS1205 + TS1484 + TS1294 counts, falling to zero and locked by lint).

**Runnable example** — trio-clean module (multi-file sets):

```typescript
// file: trio134.ts
export interface Order134 { id: string; total: number } // erasable (deletes cleanly)
export function total134(o: Order134): number { return o.total; } // plain function (every pipeline executes)
// file: shop134.ts
import { total134 } from "./trio134.js";
import type { Order134 } from "./trio134.js"; // stated traffic (verbatim-honest, isolated-safe)
export function checkout(o: Order134): string { return `pay ${total134(o).toFixed(2)}`; }
// file: app134.ts
import { checkout } from "./shop134.js";
console.log(checkout({ id: "o", total: 9 })); // pay 9.00 — trio-clean (tsc + esbuild + stripping agree byte-for-byte on graphs)
// bad — same shape with enum status + value-imported types + const-enum discount (three violations, three toolchains disagreeing)
```

```typescript
// file: base135.jsonc (base tsconfig shape, documented as config — not compiled)
// {
//   "compilerOptions": {
//     "strict": true,
//     "isolatedModules": true, // per-file transpilable (unit 76)
//     "verbatimModuleSyntax": true, // predictable emit (unit 77)
//     "erasableSyntaxOnly": true, // deletion-only syntax (this promise)
//     "module": "nodenext",
//     "moduleResolution": "nodenext",
//     "declaration": true
//   }
// }
// file: app135.ts
console.log("trio-base-documented"); // the standard stated once (inherited everywhere, opted out nowhere without dates)
// bad — per-package flag drift (lib strict, app lax, tools unflagged: moved code changes meaning per directory)
```

```typescript
// file: legacy136.ts
export interface Old136 { a: string }
export const V136 = 1;
// file: triaged136.ts
import type { Old136 } from "./legacy136.js"; // trio-triaged (stated traffic; no enums/namespaces present to migrate)
import { V136 } from "./legacy136.js";
export function use(o: Old136): string { return `${o.a}:${V136}`; }
// file: app136.ts
import { use } from "./triaged136.js";
console.log(use({ a: "x" })); // x:1 — legacy file triaged to trio-clean (one PR, green throughout)
// bad — flag-day trio adoption (all files + all errors in one PR: unreviewable, conflicting, pressuring suppression)
```

**Common confusion** — "trio slows feature work" — per-declaration stating (seconds) vs toolchain migrations (quarters) — front-loaded triviality preventing back-loaded rewrites. "one flag suffices" — each flag guards a *different* divergence axis (transpilability / emit-predictability / deletability) — pairs leave one axis exposed (the exact partial-adoption failure above). "legacy code must convert immediately" — per-directory compounding (new clean, legacy triaged with error counts as progress) — flag-day conversion is the anti-pattern the trio exists to prevent.

**Performance note** — trio-clean repos start fastest under stripping runtimes (no transpile decisions — mechanical deletion), bundle smallest (type edges absent), and transpile identically everywhere (zero divergence debugging) — the performance story *is* the universality story.

**Mentor note** — graph the three error counts weekly during adoption (TS1205 + TS1484 + TS1294 falling to zero, lint-locked after) — one dashboard for the whole standard. Exercise: trio-convert one directory end-to-end (flags + imports + enum/namespace migration) and execute under three runtimes — universality proven per directory, compounding quarterly.

### 3) **Adopting per directory** (new clean, legacy triaged, metrics falling)

**Definition** — adoption sequence: base tsconfig carries the trio (new code compliant from day one — violations fail at authorship); legacy directories triage error-class by error-class (TS1205 re-export kinds first, TS1484 import kinds second, TS1294 enum/namespace migrations third — each class one PR per directory); progress tracked as three falling counters, locked by lint on completion (`consistent-type-imports`, `no-namespace` scoped, enum-stamp reviews).

**What problem it solves / history** — flag-day trio adoption (all flags + all errors in one PR) stalled like every flag-day (unreviewable, conflicting, pressuring suppression — suppressed diagnostics preserving untranspilable designs). Per-directory compounding keeps every step green and reviewable: new code never adds violations (locked from birth), legacy violations fall monotonically (counted weekly), suppressions never enter (review-banned).

**Modern guidance** — as of TypeScript 5.9 era, adopt in this order per directory: `isolatedModules` triage (re-export kinds — mechanical) → `verbatimModuleSyntax` triage (import kinds — mechanical) → `erasableSyntaxOnly` migration (enums/namespaces — judgmental, per 11/2.2 + 12/2.1 maps). One directory green before the next begins (compounding, revertible, reviewable); lint-lock each completed directory (regression impossible without review).

**Runnable example** — compounding adoption (multi-file sets):

```typescript
// file: new137.ts
export interface New137 { n: string } // new code (trio-clean from birth: no violations possible here)
export function greet137(x: New137): string { return x.n.toUpperCase(); }
// file: app137.ts
import { greet137, type New137 } from "./new137.js"; // stated traffic (locked by lint from day one)
const v: New137 = { n: "a" };
console.log(greet137(v)); // A — greenfield compliance (zero triage needed, ever)
// bad — new code with value-imported types (violation at birth: triage debt from day one — lint prevents)
```

```typescript
// file: leg138.ts
export interface Old138 { o: string }
export const W138 = 2;
// file: tri138.ts
import type { Old138 } from "./leg138.js"; // triaged (TS1484 fixed by stating — one class, one PR)
import { W138 } from "./leg138.js";
export function use(o: Old138): string { return `${o.o}:${W138}`; }
// file: app138.ts
import { use } from "./tri138.js";
console.log(use({ o: "x" })); // x:2 — legacy directory triaged (falling counter, green PR)
// bad — triaging all three error classes in one legacy PR (unreviewable mix: kinds + imports + migrations)
// fix — one class per PR (mechanical classes first, judgmental migrations last)
```

```typescript
// file: met139.ts
export const counts = { ts1205: 0, ts1484: 0, ts1294: 0 } as const; // metrics stated (falling to zero, then locked)
// file: app139.ts
import { counts } from "./met139.js";
console.log(Object.values(counts).join(",")); // 0,0,0 — dashboard green (trio adopted, lint-locked, compounding done)
// bad — adoption without metrics (progress invisible: stalled classes hide, completed ones regress silently)
// fix — three counters weekly (audit progress made countable; locks make it permanent)
```

**Common confusion** — "metrics are bureaucracy" — three counters (TS1205/TS1484/TS1294) replace status meetings about adoption (progress visible without asking) — instrumentation, not bureaucracy. "per-directory is slow" — per-directory merges weekly (reviewable); flag-day stalls quarterly (unreviewable) — compounding is *faster* wall-clock, not just safer. "locks prevent pragmatic exceptions" — locks require *reviewed* exceptions (dated, reasoned — the escape hatch with a paper trail, not a wall).

**Performance note** — adoption costs authoring minutes per file (one-time); locked discipline costs zero ongoing (lint enforces); un-adopted guessing costs phantom-edge + divergence incidents (unbounded, recurring) — audit economics favor completion heavily.

**Mentor note** — graph the three counters team-visible during adoption (falling lines = audit working; flat = stalled class needing pairing). Exercise: triage five files across all three classes live (kinds → imports → enum migration) — the full adoption arc in under an hour. Gate: TS-error suppressions fail review unconditionally; triage PRs stay per-directory green.
