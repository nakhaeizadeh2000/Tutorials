## 2.1. isolatedModules — single-file transpilation

Some JavaScript emitters process TypeScript syntax one file at a time without
performing TypeScript's cross-file type analysis. `isolatedModules` adds checks
for selected patterns that are problematic for that process. It does not make
tsc stop resolving or checking imported files, run a transpiler for you, or prove
identical behavior under every toolchain.

Use TypeScript 7.0.2 and Node 20.20.2 in a fresh directory without a tsconfig.
Native-source execution below explicitly uses Node 22.18.0; the independent
transform uses esbuild 0.28.2. Keep checking, transformation and execution as
separate observations.

### 1) **State type-only re-exports while retaining whole-program checks**

Save this graph. The interface is checker information; port is a runtime value.
The barrel states which kind each export supplies.

```typescript
// file: config.mts
export interface Config { host: string }
export const port = 80;
// file: barrel.mts
export type { Config } from "./config.mjs";
export { port } from "./config.mjs";
// file: app.mts
import { port } from "./barrel.mjs";
import type { Config } from "./barrel.mjs";
const config: Config = { host: "h" };
console.log(config.host.toUpperCase(), port);
```

```sh
tsc --strict --isolatedModules --verbatimModuleSyntax false --target es2022 --module nodenext --moduleResolution nodenext --noEmitOnError --outDir dist app.mts
node dist/app.mjs
```

The result is `H 80`. Change only `export type { Config }` to `export { Config }`:
the isolated check reports TS1205. With isolatedModules false and verbatim mode
false, tsc can use cross-file knowledge to remove that type-only re-export. The
explicit marker makes the intent available to a syntax-oriented processor without
having it determine whether Config has a value in another file.

Now change config's host value in app to 7. Checking the graph still reports
TS2322 with isolatedModules on. The ordinary assignability check remains active.
The [option reference](https://www.typescriptlang.org/tsconfig/isolatedModules.html)
explains the re-export and non-module restrictions. Verbatim checking supplies
related import/export requirements; disabling it here isolates this particular
option's effect, rather than recommending its removal from a project standard.

A type-only import used as a value is another diagnostic, not a special isolated
restriction. Replace port's import with `import type { port } ...` while retaining
its console use: TS1361 occurs both with isolatedModules true and false. A
checker query such as `typeof port` can legitimately use a type-only binding;
an actual runtime read cannot. The [type-import owner](<../../../12 Modules Namespaces and Declaration Files/sections/1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>)
owns that distinction.

### 2) **Separate source-defined const enums from ambient const enums**

Ordinary source-defined const enums can be imported across files under this flag.
Save these two sources:

```typescript
// file: code.mts
export const enum Code { Ready = 1 }
// file: use-code.mts
import { Code } from "./code.mjs";
const enum Local { Start = 2 }
console.log(Code.Ready, Local.Start);
```

```sh
tsc --strict --isolatedModules false --verbatimModuleSyntax false --target es2022 --module nodenext --moduleResolution nodenext --outDir ordinary use-code.mts
tsc --strict --isolatedModules --verbatimModuleSyntax false --target es2022 --module nodenext --moduleResolution nodenext --outDir isolated use-code.mts
node ordinary/use-code.mjs
node isolated/use-code.mjs
```

Both print `1 2`. Inspect their JavaScript. The ordinary build inlines the member
reads and removes the const-enum runtime objects and enum-only import. With
isolatedModules, this compiler retains the Code and Local runtime objects and
runtime references. The option implies const-enum preservation; explicitly setting
preserveConstEnums false with it reports TS5091. Therefore “same-file const enums
always inline” and “the option can never affect emit” are misleading summaries.
The ordinary cross-file import here is not TS2748.

TS2748 concerns ambient const-enum member access. Save the following separate
declaration and consumer solely for a compile-time contrast; no runtime provider
is supplied by this fixture:

```typescript
// file: foreign.d.mts
export declare const enum ForeignCode { Ready = 3 }
// file: ambient-use.mts
import { ForeignCode } from "./foreign.mjs";
console.log(ForeignCode.Ready);
```

```sh
# Expected TS2748:
tsc --strict --isolatedModules --verbatimModuleSyntax false --target es2022 --module nodenext --moduleResolution nodenext --noEmit ambient-use.mts
```

A declaration contributes no implementation. A transform that preserves a runtime
member access cannot invent the missing object. The [const-enum publication
owner](<../../../11 Enums and Literal Types/sections/2. Enums vs Erasable Alternatives/2.1. const enum inlining and isolatedModules danger.md>)
contains complete real providers, version changes and pinned transform comparisons.
Use it for choosing a publication repair; removing const or localizing constants
can change a public runtime contract and requires its consumer tests.

### 3) **Test module classification and runtime syntax support independently**

A value-bearing namespace in a global script is rejected under isolatedModules.
Save `script.ts`:

```typescript
// file: script.ts
namespace Legacy { export const value = 1; }
console.log(Legacy.value);
```

```sh
# Expected TS1280:
tsc --strict --isolatedModules --moduleDetection legacy --target es2022 --module commonjs --noEmit script.ts
# Intentional module classification change:
tsc --strict --isolatedModules --moduleDetection force --target es2022 --module commonjs --outDir script-dist script.ts
node script-dist/script.js
```

The second build prints 1. Adding an empty export marker is another way to make
this file a module, but that changes its scope contract; it is not a mechanical
repair for a deliberately shared global script. Ambient declaration files have
different treatment. The [namespace owner](<../../../12 Modules Namespaces and Declaration Files/sections/2. Namespaces and Ambient Contexts/2.1. Namespaces organization and when to avoid.md>)
compares module-local and shared-script identities and loading.

Module-scoped namespaces can still require JavaScript generation. Save:

```typescript
// file: native.mts
namespace Group { export const value = 1; }
console.log(Group.value);
```

```sh
tsc --strict --isolatedModules --target es2022 --module nodenext --moduleResolution nodenext --outDir dist native.mts
node dist/native.mjs
# Expected ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX:
npm exec --yes --package=node@22.18.0 -- node native.mts
```

The emitted JavaScript prints 1; native source execution rejects the namespace.
An isolatedModules pass does not establish deletion-only source compatibility.
That is a separate [erasable-syntax and execution contract](<./2.3. erasableSyntaxOnly and the trio standard.md>).

### 4) **Keep JavaScript isolation, declaration isolation and type checking separate**

`isolatedDeclarations` asks for sufficient exported annotations for declaration
production without full cross-file inference. It is not another spelling of
isolatedModules. This source passes ordinary isolatedModules checking:

```typescript
// file: api.mts
export function greet(name: string) { return name.toUpperCase(); }
```

```sh
tsc --strict --isolatedModules --target es2022 --module nodenext --moduleResolution nodenext --declaration --outDir api-dist api.mts
# Expected TS9013:
tsc --strict --isolatedModules --isolatedDeclarations --target es2022 --module nodenext --moduleResolution nodenext --declaration --noEmit api.mts
```

Adding the explicit return annotation `: string` satisfies this declaration
restriction. The [isolatedDeclarations reference](https://www.typescriptlang.org/tsconfig/isolatedDeclarations.html)
describes its exported-annotation purpose. This does not mean every export needs
every possible annotation; test the actual expression and diagnostic.

Conversely, a syntax transform can succeed on a program that fails checking. Save:

```typescript
// file: unchecked.mts
const count: number = "oops";
console.log(typeof count, count);
```

```sh
# Expected TS2322:
tsc --strict --isolatedModules --target es2022 --module nodenext --moduleResolution nodenext --noEmit unchecked.mts
npm exec --yes --package=esbuild@0.28.2 -- esbuild unchecked.mts --platform=node --format=esm --outfile=unchecked.mjs
node unchecked.mjs
```

The transform succeeds and execution prints `string oops`. Esbuild does not
perform this type check, as its [TypeScript documentation](https://esbuild.github.io/content-types/#typescript)
explains. Run the actual compiler gate as well as supported build/runtime tests.
Neither passing one transform nor enabling isolatedModules installs that gate.

### 5) **Common confusion**

Isolation describes restrictions for particular processing boundaries, not a
promise that imported source is ignored by the checker. The whole-program graph
still matters. Some restrictions overlap verbatim checking; others, such as the
ambient const-enum case, concern a value a declaration cannot supply at runtime.

A library consumer importing built JavaScript and declarations has a different
processing boundary from a consumer compiling raw TypeScript source. Decide which
you support before requiring or dropping a flag. The [packed-package project](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>)
tests those artifacts directly. One passing source check is not a certificate
for every downstream loader or compiler configuration.

### 6) **Performance note**

This lesson has no timing benchmark or universal transpiler-speed comparison.
The checker still resolves and checks the program; syntax transformation and
checking perform different work. Isolation also implies const-enum preservation
in the observed emit, so runtime objects remain where the ordinary build inlined
reads. Measure the actual build and output when cost matters rather than treating
flag compliance as zero checker work or guaranteed smaller JavaScript.

### 7) **Mentor note**

Give a learner three reports: TS1205 on a type re-export, TS2748 on an ambient
const-enum read, and TS1361 on a type-only value import. Ask which facts the
processor lacks and whether the diagnostic occurs without isolatedModules. A
sound answer distinguishes the declaration kind, absent provider and erased
runtime binding instead of applying one “cross-file enum” rule to all of them.

Then compare the source-defined enum output and the native namespace failure.
The learner should identify what was preserved or generated and which runtime
actually consumes it. Keep that evidence with the support decision rather than
claiming every pipeline agrees after one flag is enabled.
