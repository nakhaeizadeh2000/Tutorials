## 2.1. `isolatedModules` — single-file transpilation

### 1) **What isolation requires** (each file transpilable alone, no cross-file value knowledge)

**Definition** — `isolatedModules: true` requires every file to transpile *independently*: no cross-file value inference (re-exported types need `export type`), no `const enum` value imports (nothing to inline from unseen files), no ambient-const-enum access. The flag doesn't change checking (same types, same errors) — it restricts *emittable* patterns to the per-file-transpilable subset, erroring (TS2748/TS1205/TS1361) where whole-program knowledge was assumed.

**What problem it solves / history** — per-file transpilers (esbuild, swc, Babel, Vite dev, Node stripping) process files *without type information*: patterns needing cross-file values (`export { SomeType }` re-exported as value-or-type ambiguously, `const enum` member values) compiled under `tsc` and broke (or silently differed) under transpilers. The flag makes `tsc` *enforce* transpilability: code passing with the flag on transpiles identically on every per-file pipeline.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), enable `isolatedModules` in every tsconfig (libraries *and* apps — any code a per-file pipeline might touch, which is all code eventually); fix each error by stating (export type, non-const enums, explicit re-export kinds) rather than restructuring logic. [12/1.3](<../../../12 Modules Namespaces and Declaration Files/sections/1. ES Modules/1.3. export equals and interop with CommonJS.md>) documented tsc-7's interop defaults; this promise owns the *flag*.

**Runnable example** — isolation enforced at authorship (multi-file sets, nodenext):

```typescript
// file: types113.ts
export interface Cfg113 { host: string }
export const PORT113 = 80;
// file: re113.ts
export type { Cfg113 } from "./types113.js"; // stated type re-export (transpiler-safe: erased unambiguously)
export { PORT113 } from "./types113.js"; // value re-export (kept unambiguously)
// file: app113.ts
import { PORT113, type Cfg113 } from "./re113.js";
const c: Cfg113 = { host: "h" };
console.log(c.host.toUpperCase(), PORT113.toFixed(0)); // H 80 — stated kinds transpile identically everywhere
```

```typescript
// file: vals114.ts
export interface Opts114 { retries: number }
export const DEF114: Opts114 = { retries: 3 };
// file: re114.ts
// export { Opts114 } from "./vals114.js"; // error TS1205 under isolatedModules (re-exported TYPE without `type` keyword — ambiguous to transpilers)
// fix — export type { Opts114 } (stated; transpilers erase without cross-file knowledge)
export type { Opts114 } from "./vals114.js";
export { DEF114 } from "./vals114.js";
// file: app114.ts
import { DEF114, type Opts114 } from "./re114.js";
const o: Opts114 = DEF114;
console.log(o.retries.toFixed(0)); // 3 — stated re-exports (no guessing on any pipeline)
```

```typescript
// file: local115.ts
const enum Local115 { A, B } // same-file const enum (isolatedModules-safe: values visible in THIS file)
console.log(Local115.A.toFixed(0)); // 0 — inlined locally (no cross-file knowledge needed)
// bad — exported const enum consumed cross-file (TS2748 under isolatedModules: values live in an unseen file)
// fix — plain enum or union + const object for shared constants (see 11/2.1 — same rule, flag-enforced here)
// file: app115.ts
console.log("locally-inlined"); // same-file const enums stay legal (isolation satisfied trivially)
```

**Common confusion** — "the flag changes checking" — emit-restrictions only (same types, same assignability — new *errors* on untranspilable patterns, never new *types*). "TS1205/TS2748 are bureaucracy" — each names a pattern that *breaks or diverges* under per-file transpilers (re-export ambiguity → wrong emit; const-enum import → crash) — the errors are pipeline incidents pre-filed at authorship. "bundler projects don't need it" — bundlers *are* per-file transpilers (esbuild/swc under Vite/Next) — the flag's primary audience is exactly them.

**Performance note** — zero runtime/check delta (restrictions only); per-file transpilers run orders of magnitude faster than `tsc` (no type-checking — the speed isolation buys); flag-compliant code transpiles identically everywhere (no divergence debugging — the hidden cost deleted).

**Mentor note** — enable the flag on a legacy project and triage each error class (re-export kinds, const enums, ambient consts) — the transpilability audit the codebase needed, automated. Exercise: convert three value-syntax type re-exports to `export type` and explain *which* pipeline each would have broken — authorship errors mapped to production incidents.

### 2) **Errors as architecture documentation** (TS2748/TS1205 name untranspilable designs)

**Definition** — each isolation error documents an architecture fact: TS1205 (re-exported type without `type` — *transpilers can't tell type from value*; state the kind), TS2748 (const-enum access across files — *values live unseen*; inline locally or publish plainly), TS1361 (`import type` of values — *erased reference to runtime data*; import values as values). Reading errors as design feedback (not bureaucracy) routes each to its structural fix.

**What problem it solves / history** — error-suppression reflex (`// @ts-ignore` per isolation error, or disabling the flag "until later") preserved untranspilable designs while silencing their diagnostics — codebases accumulated transpiler-incompatible patterns behind suppressions, then paid per-pipeline incidents at migration time. Error-as-documentation inverts the reflex: each diagnostic *teaches* the transpilable alternative (state kinds, inline locally, import values as values).

**Modern guidance** — as of TypeScript 5.9 era, fix every isolation error structurally (never suppress — suppression preserves the untranspilable design *and* deletes its only diagnostic); document the mapping (TS1205 → state re-export kinds; TS2748 → localize or de-const the enum; TS1361 → match import syntax to universe). Keep a running log of fixed classes during adoption (the team's transpiler literacy, written once).

**Runnable example** — errors routed to structural fixes (multi-file sets; error demos as commented errors):

```typescript
// file: t116.ts
export interface T116 { x: number }
export const V116 = 1;
// file: re116.ts
export type { T116 } from "./t116.js"; // TS1205 fix: stated kind (transpiler erases without cross-file knowledge)
export { V116 } from "./t116.js"; // values stated as values (kept unambiguously)
// file: app116.ts
import { V116, type T116 } from "./re116.js";
const t: T116 = { x: V116 };
console.log(t.x.toFixed(0)); // 1 — stated re-exports (every pipeline agrees on emit)
// bad — export { T116 } (TS1205: ambiguous re-export — transpilers guess, tsc refuses to let them)
```

```typescript
// file: ce117.ts
export const enum CE117 { A, B } // same-file use legal (values visible here); export for cross-file use illegal-ish
// file: app117.ts
// import { CE117 } from "./ce117.js"; console.log(CE117.A); // TS2748 under isolatedModules (values unseen cross-file)
// fix — plain enum or union + const object for shared constants (localize inlining or publish plainly — see 11/2.1)
// (demo kept import-free so the fence compiles: the error above is the documented diagnostic, verified in 11/2.1)
export const local = 1;
console.log(local.toFixed(0)); // 1 — placeholder runnable (error demos stay commented per convention)
```

```typescript
// file: u118.ts
export const VAL118 = "v";
export interface Typ118 { t: string }
// file: app118.ts
import { VAL118 } from "./u118.js";
import type { Typ118 } from "./u118.js"; // universe-matched traffic (values kept, types erased — TS1361 impossible by construction)
const t: Typ118 = { t: VAL118 };
console.log(t.t.toUpperCase()); // V — matched syntax per universe (the TS1361 class deleted structurally)
// bad — import type { VAL118 } (TS1361: erased reference to runtime data — universe mismatch, refused at authorship)
```

**Common confusion** — "suppression unblocks faster" — suppression unblocks the *error* while preserving the *design flaw* (transpiler breakage deferred to migration — with interest). "one suppression is harmless" — suppressions normalize (each teaches the next author that diagnostics are negotiable — culture rots per instance). "fixing changes behavior" — stating kinds / localizing enums / matching universes preserve behavior *exactly* (same types, same values — only emit-determinism changes, from divergent to identical).

**Performance note** — stated patterns emit identically-or-smaller (type re-exports vanish; localized enums inline trivially); suppressed patterns risk per-pipeline divergence debugging (hours per incident — the cost suppression pretends to save).

**Mentor note** — keep an "isolation error log" during adoption (error code → design fix → file) — the log *is* the team's transpiler literacy, reviewable and onboarding-friendly. Exercise: fix five suppressed isolation errors structurally and delete the suppressions — each deletion removes a deferred incident. Gate: `@ts-ignore`/`@ts-expect-error` on isolation errors fail review unconditionally.

### 3) **Who needs it on** (libraries, apps with per-file pipelines — everyone, eventually)

**Definition** — enable `isolatedModules` in: libraries (consumers transpile with unknown pipelines — universality required), apps on Vite/Next/esbuild/swc/Babel (per-file transpilation *is* the dev loop — flag matches reality), and Node-stripping runtimes (type-stripping *is* single-file transpilation). Exempt essentially nothing durable — even tsc-only monorepos gain the discipline (stated kinds, local enums) for free.

**What problem it solves / history** — flag-off libraries shipped patterns their consumers' pipelines choked on (const-enum exports, ambiguous re-exports — library CI green on tsc, consumer builds red on esbuild — the pipeline-dependent breakage class from 11/5.1 promise 2 and 12/5.1). Flag-on libraries can't express those patterns (errors at authorship) — consumer-pipeline compatibility proven before publish, not after incident.

**Modern guidance** — as of TypeScript 5.9 era, `isolatedModules: true` in every tsconfig without a dated, reasoned exemption (the very few: tsc-only single-program embedded builds with zero external consumers — revisit yearly); pair with `verbatimModuleSyntax` (predictable emit) and `--erasableSyntaxOnly` where adopted (deletion-only syntax) — the trio from 12/1.2 promise 3, configured here. Verify with dual-pipeline CI (tsc + a per-file transpiler on the same tests).

**Runnable example** — flag matches reality (multi-file sets):

```typescript
// file: lib119.ts
export interface Cfg119 { host: string }
export function connect(c: Cfg119): string { return c.host; } // library code (unknown consumer pipelines → flag on)
// file: con119.ts
import { connect, type Cfg119 } from "./lib119.js"; // stated traffic (transpiles identically on tsc/esbuild/swc/Babel)
console.log(connect({ host: "h" }).toUpperCase()); // H — universality proven at authorship (not after incident)
```

```typescript
// file: lib119.ts
export interface Cfg119 { host: string }
export function connect(c: Cfg119): string { return c.host; } // re-declared: fences compile standalone
// file: comp120.ts
export type { Cfg119 } from "./lib119.js"; // stated re-export (library surface transpiler-safe by construction)
// file: con120.ts
import type { Cfg119 } from "./comp120.js";
const c: Cfg119 = { host: "x" };
console.log(c.host); // x — barrels state kinds (per 12/1.1 explicit lists + per this flag's demands, composed)
// bad — export { Cfg119 } (TS1205: ambiguous barrel hop — the highest-traffic isolation error in library code)
```

```typescript
// file: dual121.ts
export const VERSION121 = "1.0"; // value (kept on every pipeline identically)
export interface Meta121 { v: string } // type (erased on every pipeline identically)
// file: con121.ts
import { VERSION121, type Meta121 } from "./dual121.js";
const m: Meta121 = { v: VERSION121 };
console.log(m.v); // 1.0 — dual-pipeline CI (tsc + esbuild) passes identically (flag matching reality, verified)
// bad — tsc-only CI for library code (pipeline-specific patterns ship to per-file consumers undetected)
```

**Common confusion** — "tsc-only projects skip the flag" — tsc-only *today* (pipelines change — Vite adoption, stripping runtimes, consumer bundlers — flag-on code survives all of them; flag-off code breaks per migration). "the flag is library-only" — apps on per-file dev loops need it equally (Vite dev *is* esbuild per-file — reality, not preference). "dual-pipeline CI doubles costs" — stripping/transpile runners execute in milliseconds (no typecheck — checking runs once under tsc); second pipeline verifies emit-divergence for near-zero CI time.

**Performance note** — per-file transpilers run orders of magnitude faster than `tsc` (no checking — the speed isolation buys); flag compliance costs authoring precision only (stated kinds, local enums — seconds per declaration, once).

**Mentor note** — dual-pipeline CI this quarter (same tests, tsc + esbuild) — divergence failures are the flag audit automated. Exercise: list every consumer pipeline for one shared package (tsc? esbuild? swc? stripping?) — unknown entries are incidents queued; the flag answers them preemptively.
