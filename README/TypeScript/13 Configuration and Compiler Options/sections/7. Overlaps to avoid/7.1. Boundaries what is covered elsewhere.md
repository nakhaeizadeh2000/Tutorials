## 7.1. Boundaries — what is covered elsewhere

A compiler option selects part of the checking or output contract. Understanding the reported error still requires the relevant language behavior, and accepting a deployment requires evidence about the produced artifact. Use this map to identify which layer a configuration change is meant to affect. Its practice refers to completed worked examples in the linked owners.

### 1) **Nullability, absence and unknown inputs**

[null and undefined](<../../../03 Basic Types and Annotations/sections/1. The Primitive Family/1.3. null and undefined strictNullChecks and optionality.md>) owns the values null and undefined and the types that admit them. [the checked unknown boundary](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>) shows why unknown data must be checked before a declared member is used. Here, [strict and nullability configuration](<../1. Strictness Family/1.1. strict and strictNullChecks the nullability contract.md>) and [implicit-any and catch configuration](<../1. Strictness Family/1.2. noImplicitAny and useUnknownInCatchVariables.md>) own the relevant option selection and adoption. Learn the failing read as well as the setting: a nullable access and an unknown member access are different reasons to require evidence.

A guard is useful because its runtime condition establishes the fact needed by the following operation. Changing a return annotation or asserting a narrower type does not supply that evidence. The checked unknown lesson contrasts a safe boundary with an unchecked array-element assumption; the same strict compilation can accept a dishonest explicit predicate. Use its malformed-input tests when the question is whether the guard proves its claim.

For object properties, distinguish reading an optional member from assigning explicit undefined or omitting a required member. [the verified object-modifier lesson](<../../../04 Objects Interfaces and Type Aliases/sections/1. Object Type Fundamentals/1.2. Optional readonly and index signatures.md>) has the actual presence/JSON contrasts; [index and optional-property precision](<../3. Modules Emit and Projects/3.3. noUncheckedIndexedAccess and exactOptionalPropertyTypes.md>) owns the associated precision options. Explain what the application means by absence before choosing a default value. A broad suppression or assertion may erase the diagnostic while retaining the mistaken runtime assumption.

When a supplied handler expects only a narrower input than the host may send, identify that relationship before changing a flag. ### 4) **Configured checking and runtime validation**

[the verified predicate/assertion lesson](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.3. Type guards predicates asserts and satisfies on functions.md>) explains what predicate and assertion signatures promise to callers, while [runtime boundary parsing](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>) owns the runtime boundary practice. [union exhaustiveness](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>) covers proving that a finite union's branches are handled. These are published owners, so use them directly when the diagnostic or review question crosses from configuration into a function's behavior.

Keep the evidence distinct. A never sink checks remaining static alternatives; it does not validate arbitrary input from a network or file. A declared predicate can tell the checker to narrow, but its body and both branch outcomes still need review. The verified assertion lesson executes dishonest signatures that compile and later produce a controlled TypeError. Strict settings do not replace those checks.

Likewise, a `typeof` observation can describe a coarse runtime category without checking the required object fields. Use a parser when the caller needs a complete returned contract, and choose a predicate or assertion according to how failure should be handled. Configure the checked program consistently, then execute valid and malformed boundary cases. Avoid treating the presence of flags or guards as sufficient proof without examining what each one establishes.

A configuration change can alter included files, declarations or emitted artifacts, but a setting name is not a measured speedup. Compare representative results before splitting a project, loosening checking or changing cache policy. The [local skipped-declaration reproduction](<../5. Common pitfalls to production bugs/5.1. A project that checks successfully can still need a compatibility compiler for an API consumer. Identify the tool's interface and supported arrangement before assuming that a changed compiler dependency configures every editor and linter. Record actual command, output and artifact results for the chosen path.

### 6) **Common confusion**

A strict checked program can still contain explicit any, assertions or trusted predicate signatures that bypass useful evidence. Configuration and the body of a function both matter. For a bad boundary, inspect the value checks; for an unsafe callback, inspect the substitution direction and whether the signature is a method or property.

Check-only success does not establish emitting success or the output path used by deployment. The configuration migration's rootDir probe exposes that difference. Syntax gates likewise do not prove runtime import resolution. Use each command as evidence for its own contract instead of allowing one green gate to stand in for the whole pipeline.

A compiler version, a language-server setting and a tool's imported compiler API are related choices with different consumers. State which one changed and which checks ran. Follow the current update route for version-sensitive differences while keeping unchanged language mechanics in their existing owners.

### 7) **Performance note**

This navigation lesson has no direct performance effect. Some configuration changes alter checker inputs or output generation; runtime parser bodies and retained module dependencies perform actual work. Their cost depends on the program, values and environment. No new compiler, runtime or editor benchmark was run for this lesson.

Use the measurement owners to compare the relevant build or interaction with matching conditions. A smaller declaration environment may change checking work without changing an algorithm's runtime speed. A type assertion erases without performing validation, while adding a parser changes runtime work. Neither observation supplies a universal optimization rule or a reason to weaken a correctness contract without evidence.

### 8) **Mentor note**

Give the learner a failure and require an owner, an explanation and a next check. These three cases use evidence from the linked worked examples:

1. **Check-only passes after an upgrade, but the emitting command reports TS5011.** Inspect rootDir and the actual emitted paths. The configuration migration isolates this change and restores the package's intended entry point with explicit settings and a clean consumer run.
2. **Strict checking accepts a method-box callback that throws when the host sends another valid variant.** Explain the method exception and the handler's narrower assumption. The callback lesson demonstrates this failure and contrasts a function-valued property and wider handler; disabling strictness is not a repair of the input contract.
3. **The checker accepts a changed import, but native source execution cannot find its destination.** Inspect the source/output graph and retained specifier. The import lesson shows the missing output-extension file beside the source; the syntax gates alone cannot supply it.

A sound answer names what the check establishes and what remains to execute. For a tool failure, add its compiler interface; for malformed input, add the missing field proof. Ask the learner to reject a proposed blanket assertion or flag removal by explaining the unchanged failure mechanism, then choose a bounded remedy and its verification.
