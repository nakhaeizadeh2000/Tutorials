## 1.2. noImplicitAny and useUnknownInCatchVariables

These flags protect different boundaries. `noImplicitAny` diagnoses particular
fallback inference sites; it does not ban every value whose type is any.
`useUnknownInCatchVariables` changes the default type of a catch-clause binding;
it does not change what JavaScript can throw or automatically type every
asynchronous rejection callback as unknown.

Use TypeScript 7.0.2 and Node 20.20.2 in a fresh directory without a tsconfig.
All examples explicitly use strict checking. The underlying [any](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.1. any the unchecked escape hatch.md>)
and [unknown](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>)
contracts remain in their owners; this lesson tests where the options apply.

### 1) **Observe reported inference sites and permitted inference separately**

A bare function parameter without a useful context receives TS7006 under
noImplicitAny. A callback parameter can instead receive a precise contextual
type without an annotation. Evolving locals also have useful supported behavior;
a local empty array is not automatically rejected at its declaration.

```typescript
// file: inference.mts
const names = ["Ada"].map(name => name.toUpperCase());
const queue = [];
queue.push("a");
queue.push(1);
const snapshot = [...queue];
let current;
current = "first";
current = 7;
console.log(names.join(","), snapshot.join(","), current.toFixed(0));
const closed = {};
console.log(Object.keys(closed).length);
// Activate one negative line at a time:
// function uncovered(value) { return value; }
// const onlyStrings: string[] = snapshot;
// closed.added = 1;
```

```sh
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmitOnError --outDir dist inference.mts
node dist/inference.mjs
```

The output is `ADA a,1 7`, then `0`. The negative lines respectively produce
TS7006, TS2322 and TS2339. The empty object is not an evolving arbitrary-key any:
its undeclared property write is rejected. The local queue evolves through
observed writes; its snapshot is a mixed array, so the string-only assignment
fails. If string-only writes are the intended invariant, `queue: string[]`
moves rejection to the bad push. Do not annotate contextual callback parameters
merely to satisfy a rule that noImplicitAny does not impose.

A local read whose element type remains unresolved can still fail. Add
`const unresolved = []; console.log(unresolved);` and check: TS7034 and TS7005
identify the unresolved implicit array type and read. The [original inference
notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-1.html#improved-any-inference)
explain this distinction. The [inference owner](<../../../03 Basic Types and Annotations/sections/3. Annotations Inference and Literals/3.2. Type inference widening and contextual typing.md>)
develops evolving locals versus fixed empty-array contexts.

### 2) **Find any that the flag legitimately leaves in the program**

A declared library return type of any can propagate into an unannotated local
without TS7006. A context explicitly containing any can likewise supply that type
to a callback. These are not uncovered parameter inference sites.

```typescript
// file: permitted-any.mts
const parsed = JSON.parse('{"count":"oops"}');
const count: number = parsed.count;
function receive(handler: (value: any) => void): void { handler("text"); }
receive(value => {
  const claimed: number = value;
  console.log(typeof claimed, claimed);
});
console.log(typeof count, count);
```

```sh
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmitOnError --outDir dist permitted-any.mts
node dist/permitted-any.mjs
```

The output is `string text`, then `string oops`. Strict checking accepts both
assignments because their sources are any. Adding a number annotation to the
receiving variable is not validation or containment. Explicit any also remains
legal; a separate lint policy may restrict it, but that policy is not this flag.

At an untyped boundary, prefer an unknown holding type when downstream code must
check the value. For example, change the parsed binding to `const parsed: unknown
= JSON.parse(...)`: `parsed.count` is then rejected with TS18046. The [unknown
boundary project](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>)
shows a complete parser. A check that a value is a non-null object does not prove
that all its properties are strings; arrays and numeric-valued objects also
satisfy that broad object check. A dictionary parser must establish its member
contract, not assert it from the container category.

### 3) **Configure catch bindings, then handle the thrown values**

Save this deliberate unsafe handler:

```typescript
// file: unsafe-catch.mts
try {
  throw undefined;
} catch (error) {
  console.log(error.message);
}
```

```sh
# Expected compiler failure TS18046:
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmit unsafe-catch.mts
# Deliberately weaker checking; expected runtime TypeError:
tsc --strict --useUnknownInCatchVariables false --target es2022 --module nodenext --moduleResolution nodenext --outDir unsafe-dist unsafe-catch.mts
node unsafe-dist/unsafe-catch.mjs
```

The flag defaults the binding to unknown under strict. Disabling it restores any
and permits the unsafe read. Writing `catch (error: any)` also opts out, even
when the flag is enabled. Writing `catch (error: unknown)` requests checked use
explicitly. The [option reference](https://www.typescriptlang.org/tsconfig/useUnknownInCatchVariables.html)
explains this binding rule.

If you replace `throw undefined` with `throw "oops"` in the weaker example, the
property read prints `undefined`; it does not itself throw. A later method call
on that missing message could fail. Distinguish those observations rather than
claiming that every non-Error property read crashes immediately.

Here is a handler for several controlled thrown values. Its fallback deliberately
avoids invoking arbitrary conversion methods on an unknown object.

```typescript
// file: handled-catch.mts
function describeThrown(value: unknown): string {
  if (value instanceof Error) return value.message;
  if (typeof value === "string") return value;
  if (value === null) return "null";
  return "unrecognized throw";
}
const values: unknown[] = [new Error("broken"), "oops", 42, undefined, null];
for (const value of values) {
  try { throw value; }
  catch (error) { console.log(describeThrown(error)); }
}
const hostile = { toString(): string { throw new Error("conversion failed"); } };
console.log(describeThrown(hostile));
try { console.log(String(hostile)); }
catch (error) { console.log(describeThrown(error)); }
```

```sh
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmitOnError --outDir dist handled-catch.mts
node dist/handled-catch.mjs
```

The lines are `broken`, `oops`, `unrecognized throw`, `unrecognized throw`, `null`,
`unrecognized throw`, then `conversion failed`. `new Error(String(value))` is
therefore not an infallible normalizer for every possible thrown object: conversion
itself can execute code. Choose logging, preservation, wrapping or rethrowing from
the application's failure policy. This handler demonstrates these fixtures; it
is not a universal defense against hostile proxies or every possible Error object.

### 4) **Treat Promise rejection callbacks as a separate typed API**

The catch-clause option does not change the standard Promise.catch callback's
contextual parameter type. Contrast these callbacks in one module:

```typescript
// file: rejection.mts
function describeThrown(value: unknown): string {
  return typeof value === "string" ? value : "other rejection";
}
await Promise.reject("oops").catch(error => {
  const claimed: number = error;
  console.log(typeof claimed, claimed);
});
await Promise.reject("oops").catch((error: unknown) => {
  console.log(describeThrown(error));
  // console.log(error.message);
});
```

```sh
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmitOnError --outDir dist rejection.mts
node dist/rejection.mjs
```

This prints `string oops`, then `oops`. The first contextual any is permitted
by noImplicitAny. The second parameter explicitly requests unknown and rejects
the commented property read with TS18046. A team may use a lint rule to enforce
unknown rejection callbacks; verify that rule and its scope rather than attributing
it to useUnknownInCatchVariables.

### 5) **Common confusion**

NoImplicitAny does not mean no annotations may be omitted, no evolving local is
allowed or no any can enter from a declaration. Contextual typing, unresolved
inference and a deliberately permissive API signature are different mechanisms.
The diagnostic and source signature tell you which boundary needs repair.

Unknown is useful for both holding and consuming unverified data. Any is not
required merely to transport a value. When an unavoidable interop or migration
API uses any, limit how far it flows and test its actual boundary behavior.
Test doubles also benefit from useful contracts; no compiler option automatically
makes all test-file any safe. Choose lint severity and exceptions for the actual
project rather than presenting one warning-only policy as a language rule.

### 6) **Performance note**

These flags add checking requirements, not runtime validation. The narrowed
handler executes its branches; JSON parsing, error construction and conversion
have their ordinary runtime costs. A thrown value need not be an Error and need
not have incurred stack construction, so there is no universal cost comparison
between a catch check and a throw. No timing or compiler-cost benchmark was run.
Do not claim annotation placement costs zero checker work or that errors only
occur off hot paths.

### 7) **Mentor note**

Ask a learner why both permitted-any assignments compile under strict, then make
the parsed value unknown and find the newly rejected operation. Follow with the
empty object and evolving queue: a sound answer identifies different inferred
contracts instead of calling both “unchecked evolution.”

Next compare a catch clause and Promise.catch callback. Require the actual type
of each parameter and one observed runtime consequence. The hostile conversion
case tests whether a proposed normalizer implements a bounded failure policy or
simply relocates an unchecked operation.
