## 1.1. `strict` and `strictNullChecks` — the nullability contract

### 1) **What `strict: true` enables** (the family bundle, one flag one contract)

**Definition** — `strict: true` enables the full checking family at once: `strictNullChecks`, `noImplicitAny`, `strictFunctionTypes`, `strictBindCallApply`, `strictPropertyInitialization`, `noImplicitThis`, `useUnknownInCatchVariables` (plus `alwaysStrict` emit). One flag, one contract: "the checker proves what unstrict code assumes." Individual flags remain overridable (`strict: true, strictNullChecks: false` compiles — discouraged, occasionally needed mid-migration).

**What problem it solves / history** — per-flag adoption (`strictNullChecks` on, `noImplicitAny` off — every combination a different dialect) fragmented codebases into local checking cultures where moved code changed meaning across directory boundaries. `strict: true` (TS 2.3) made strictness *one* decision with one name: new projects enable it on day one, migrations converge toward it, and `strict` in a tsconfig states the contract without enumerating seven flags.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), `"strict": true` in every new tsconfig (no exceptions — libraries, apps, configs, scripts); migrate legacy projects per §6.4's sequence (nullability → implicit-any → variance/init, one class per PR); never disable individual strict flags permanently (temporary `strictNullChecks: false` carries a dated TODO + tracking issue, or it becomes forever).

**Runnable example** — one flag, family behavior (good vs bad, `tsc`):

```typescript
// good — strict: nullability + implicit-any + this-checking all active
function greet(name: string | null): string {
  if (name === null) return "(anon)";
  return name.toUpperCase(); // narrowed (strictNullChecks proving, not assuming)
}
console.log(greet(null), greet("ada")); // (anon) ADA
// function bad(x) { return x; } // error TS7006 (noImplicitAny: unannotated param has a fix site)
```

```typescript
// good — strict this-checking on callbacks (noImplicitThis via strict)
interface Store { items: string[]; count(): number }
const store: Store = {
  items: ["a"],
  count(this: Store): number { return this.items.length; }, // explicit this (checked, not assumed)
};
console.log(store.count().toFixed(0)); // 1 — this-typed methods verify receivers
// bad — untyped this in callbacks (this: any silently — method extracted, receiver lost, crash at call)
// fix — this: Store annotations (explicit receivers checked at every detached call)
```

```jsonc
// tsconfig base (documented as config — not compiled): the one-flag contract
// {
//   "compilerOptions": {
//     "strict": true, // family bundle on (individual flags overridable mid-migration only)
//     "target": "es2022",
//     "module": "nodenext",
//     "moduleResolution": "nodenext"
//   }
// }
```

**Common confusion** — "`strict` slows compilation meaningfully" — strict adds check branches (nullability per dereference, variance per comparison — single-digit percent on most codebases, measured via `--extendedDiagnostics` before/after, never assumed). "`strict` is all-or-nothing" — per-flag overrides exist (`strictNullChecks: false` mid-migration) — all-or-nothing is the *goal*, graduated adoption is the *path*. "libraries shouldn't impose strict" — libraries *check* strict (their code verified) without imposing (consumers choose their own flags — checking strictness never leaks into emitted declarations' requirements).

**Performance note** — strict checking costs single-digit percent check-time on typical code (null-flow branches per dereference — measure with `--extendedDiagnostics`, not folklore); emit identical (flags change proofs, never bytes). The performance story is incident-negative (null-crash class deleted) at negligible check cost.

**Mentor note** — enable `strict` on a legacy project live and read the error count by class (nullability N, implicit-any M, variance K) — the triage backlog made countable in one command. Rule: new tsconfigs ship `strict: true` (no discussion); legacy migrations sequence per promise 3 with one class per PR.

### 2) **`strictNullChecks` mechanics** (exclusion + union + narrowing)

**Definition** — with the flag on: `string` excludes `null`/`undefined` (assigning either errors TS2322); `string | null` admits `null` and *forces* narrowing before use (property access on the union errors until `!== null`/`?.`/`??` proves); `strictNullChecks: false` restores the absorbing `string` (every string possibly null at runtime, never in types — the lie). [03/1.3](<../../../03 Basic Types and Annotations/sections/1. The Primitive Family/1.3. null and undefined strictNullChecks and optionality.md>) owns the behavior; this promise owns *configuring* it (enabling, migrating, verifying).

**What problem it solves / history** — pre-flag TypeScript (and every unstrict codebase today) typed `findUser(id): User` while returning `null` for missing users — `user.name` compiled and threw `TypeError` in production (the billion-dollar mistake, compiler-blessed). The flag (TS 2.0) made nullability *a branch in the type*: `User | null` returns force handling (`if (u)`) at every call site — null crashes converted from runtime incidents to compile-time branches.

**Modern guidance** — as of TypeScript 5.9 era, model absence explicitly (`T | null` for intentional absence in returns, `T | undefined` for incidental/optional, `T?` for missing properties — see 03/1.3's intent split); narrow with `!== null`/`?.`/`??` (strict equality preserving falsy values — never truthiness for nullable strings/numbers); enable the flag before any other strict child (nullability errors dominate migration triage — first class, biggest incident yield).

**Runnable example** — exclusion enforced, unions narrowed (good vs bad, `tsc --strict`):

```typescript
// good — explicit nullability union: absence handled, never assumed
interface User { name: string }
function find(id: string): User | null {
  return id === "u1" ? { name: "Ada" } : null; // nullability in the signature (honest contract)
}
const u = find("u2");
console.log(u === null ? "missing" : u.name.toUpperCase()); // missing — branch forced by the union
// const n: string = u === null ? "x" : u.name; // narrows cleanly (no cast, no assertion)
```

```typescript
// good — strict equality preserves falsy values ("" and 0 survive null checks)
function label(s: string | null): string {
  return s !== null ? s : "(none)"; // "" stays "" (valid value, not absence)
}
console.log(`[${label("")}]`, `[${label(null)}]`); // [] [(none)] — falsy-safe narrowing
// bad — truthiness conflates "" with null (if (s) drops valid empty strings — falsy-vs-nullish bug class)
// fix — !== null / ?? (nullish-only checks keep ""/0/false intact — see 07/3.1)
```

```typescript
// good — optional chaining + nullish coalescing as narrowing sugar (still checked)
interface Cfg { host?: string }
function addr(c: Cfg): string {
  return `${c.host ?? "localhost"}:80`; // ?? narrows undefined away (checked sugar, not escape)
}
console.log(addr({}), addr({ host: "h" })); // localhost:80 h:80 — defaults with proven types
// bad — non-null assertion at every read (u!.name — presence re-asserted per site, never proven)
// fix — narrow once (if/??/?.) and let the narrowed type flow (proof beats assertion everywhere)
```

**Common confusion** — "`| null` and `| undefined` interchange" — `null` signals *intentional* absence (returned values), `undefined` *incidental* (missing props/params) — pick consistently; narrow identically. "`?.` hides bugs like `!`" — `?.` *propagates* absence honestly (`string | undefined` result forces downstream handling); `!` *deletes* absence dishonestly (claims presence without proof) — opposite semantics, opposite review outcomes. "flag migration means adding `| null` everywhere" — means *discovering* where null flows (each error a latent crash with a fix site — add unions where honest, narrow where already-unioned, assert never).

**Performance note** — zero emit delta (null checks compile to the same branches hand-written code has); check cost one flow-branch per nullable use (trivial); incident deletion (null-`TypeError` class) unbounded upside — highest-ROI single flag in typed practice by post-mortem count.

**Mentor note** — `grep "\.name" | wc -l` before/after enabling (each new error a null-crash that hadn't happened *yet*) — the latent-incident backlog, prioritized free. Exercise: fix ten nullability errors three ways (`if`/`?.`/`??`) and compare readability — narrowing vocabulary, not just compliance. Gate: `!` on nullable reads fails review (narrowing is the only accepted fix).

### 3) **Enabling `strict` on existing code** (triage order: nullability → any → variance)

**Definition** — migration sequence for legacy tsconfigs: (1) `strictNullChecks` first (largest error class, largest incident yield — nullability branches per dereference); (2) `noImplicitAny` second (`any`-shaped holes with per-site fixes — annotate or narrow); (3) variance/init/this flags last (fewest errors, most architectural — contravariance breaks, definite-assignment redesigns). One class per PR, each green before the next begins — compounding, reviewable, revertible.

**What problem it solves / history** — flag-day `strict: true` (enable all, fix 800 errors in one PR) stalled every migration it touched (unreviewable diffs, conflicts with feature branches, pressure to `!`-assert through the backlog — converting strictness into assertion theater). Sequenced migration keeps every step green and reviewable: nullability PRs (narrowing fixes), implicit-any PRs (annotation fixes), variance PRs (design fixes) — each class teaching its own discipline.

**Modern guidance** — as of TypeScript 5.9 era, sequence strictly in the 1→2→3 order (frequency-ordered: nullability errors dominate, variance errors rarify); fix with narrowing/annotations (never mass-`!` — assertion migrations preserve every crash while silencing the flag); gate each class in CI before starting the next (regression-proof per class, not one big-bang gate). Track error counts per class weekly (falling = migration working).

**Runnable example** — sequenced fixes, one class per PR (good vs bad, `tsc`):

```typescript
// PR 1 (nullability): branch newly-nullable reads (largest class, biggest yield)
interface Item { title: string }
function titleOf(items: Item[]): string {
  return items[0]?.title ?? "untitled"; // ?. + ?? (narrowing fix — crash class deleted per site)
}
console.log(titleOf([]), titleOf([{ title: "a" }])); // untitled a — empty input handled, not thrown
// bad — items[0]!.title (assertion migration: errors silenced, crashes preserved — theater, not strictness)
```

```typescript
// PR 2 (implicit-any): annotate evolution sites (second class, per-site fixes)
const seen: string[] = []; // was: const seen = [] (never[]/any[] evolution — now declared)
function track(id: string): number {
  seen.push(id);
  return seen.length;
}
console.log(track("a").toFixed(0)); // 1 — declared element type (pushes checked from first write)
// bad — const seen: any[] = [] (keeps the hole: every push unchecked, every read untrusted)
```

```typescript
// PR 3 (variance/init): design fixes (fewest errors, deepest changes)
class Box {
  private content!: string; // definite assignment (init proven in constructor below — ! with justification)
  constructor() { this.content = "x"; }
  get(): string { return this.content.toUpperCase(); }
}
console.log(new Box().get()); // X — ! justified (assigned in constructor, documented at declaration)
// bad — strictPropertyInitialization: false (whole-class blindness for one unproven field — scope the !, not the flag)
```

**Common confusion** — "sequencing slows migration" — sequenced PRs merge weekly (reviewable); flag-day PRs stall quarterly (unreviewable) — sequencing is *faster* wall-clock, not just safer. "mass-`!` unblocks migration" — unblocks the flag while preserving every crash (theater) — `!` density post-migration predicts incident density; narrow/annotate instead, count `!`s as debt. "some code can't go strict" — generated/vendor code exempts per-path (`exclude`, `skipLibCheck` scoped — see promise 5.1-adjacent reasoning in unit 75); owned code goes strict unconditionally (no owned-code exemptions — ever).

**Performance note** — migration check-cost grows per class enabled (nullability branches dominate — single-digit percent total, measured); incident deletion compounds per class (null crashes → any-holes → variance escapes — each class's incidents vanish permanently). Track `tsc --extendedDiagnostics` per PR to keep folklore out of estimates.

**Mentor note** — graph error counts per class weekly (three falling lines = migration working; flat lines = stalled class needing pairing sessions). Exercise: fix ten errors from each class live (narrowing vs annotating vs redesigning) — three disciplines, one migration. Gate: mass-`!` PRs fail review unconditionally; per-class CI gates before next class begins.
