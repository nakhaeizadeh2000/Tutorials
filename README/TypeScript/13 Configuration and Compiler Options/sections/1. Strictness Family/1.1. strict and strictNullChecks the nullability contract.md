## 1.1. strict and strictNullChecks — the nullability contract

`strict` enables a family of compiler checks. It helps expose assumptions about
values; it does not validate runtime inputs or prove that every execution is
safe. This lesson owns selecting and verifying the configuration. The
[nullability lesson](<../../../03 Basic Types and Annotations/sections/1. The Primitive Family/1.3. null and undefined strictNullChecks and optionality.md>)
owns the underlying null/undefined operations.

Use TypeScript 7.0.2 and Node 20.20.2, verified 2026-10-16. TypeScript 6 changed
strictness defaults, so the legacy experiments explicitly set `strict: false`.
For new projects, state the intended setting rather than relying on a remembered
default from an older compiler. The [configuration migration update](<../../../25 Update TypeScript 7.0/sections/1. Configuration Migration/1.1. Configuration defaults and removed options.md>)
explains the baseline changes.

### 1) **Treat strict as a versioned family with individual overrides**

The family includes `strictNullChecks`, `noImplicitAny`, `noImplicitThis`,
`strictFunctionTypes`, `strictBindCallApply`, `strictPropertyInitialization`,
`useUnknownInCatchVariables` and `strictBuiltinIteratorReturn`. Older descriptions
also list alwaysStrict as an optional family child; TypeScript 7 no longer
permits disabling that runtime strict-mode behavior, as section 4 demonstrates.
The [strict reference](https://www.typescriptlang.org/tsconfig/strict.html) explains
that individual checks can be overridden and future versions can add stricter
behavior. A compiler upgrade can therefore reveal new errors without a source edit.

Not every useful checking option belongs to this family. In particular,
`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` and `noImplicitOverride`
need separate choices. An override is a real configuration change; record why it
is needed and verify its effect instead of assuming `strict: true` makes it inert.
`strictPropertyInitialization` requires strict null checking. In this compiler,
`strict: true` with `strictNullChecks: false` implicitly disables the dependent
property-initialization check. Explicitly forcing `strictPropertyInitialization:
true` alongside disabled null checking reports TS5052. Inspect both the override
and its dependent behavior when evaluating a migration configuration.

Create a fresh directory and save the source and configuration below. JSON file
labels identify destinations; omit the `// file:` line from saved JSON.

```typescript
// file: legacy.ts
interface User { name: string }
function findUser(id: string): User | undefined {
  return id === "u1" ? { name: "Ada" } : undefined;
}
function greet(id) {
  const user = findUser(id);
  return user.name.toUpperCase();
}
console.log(greet("missing"));
```

```json
// file: tsconfig.json
{
  "compilerOptions": {
    "strict": false,
    "target": "es2022",
    "module": "commonjs",
    "types": [],
    "noEmitOnError": true,
    "outDir": "dist"
  },
  "files": ["legacy.ts"]
}
```

Use the project option when checking this configuration. Passing source filenames
directly does not load this tsconfig. TypeScript 7 reports TS5112 when a config
is present unless `--ignoreConfig` explicitly requests that separate invocation.

```sh
tsc -p tsconfig.json --showConfig
tsc -p tsconfig.json
# Expected runtime failure TypeError:
node dist/legacy.js
# Expected compiler failures:
tsc -p tsconfig.json --noEmit --strictNullChecks
tsc -p tsconfig.json --noEmit --noImplicitAny
tsc -p tsconfig.json --noEmit --strict
```

The baseline compiles, then crashes because no user exists. The partial and full
checks expose different assumptions:

| Configuration over this baseline | Observed diagnostics |
|---|---|
| strict false, strictNullChecks true | TS18048: user may be undefined. |
| strict false, noImplicitAny true | TS7006: id implicitly has type any. |
| strict true | Both diagnostics. |

`--showConfig` is useful for verifying selected settings, file inputs and overrides;
it is not a proof that runtime inputs obey their declarations. In this compiler
it need not expand every strict-family child into a printed property. Test the
relevant behavior as well as inspecting configuration.

### 2) **Repair the missing-data behavior, then keep checking its boundary**

For the remaining standalone probes, create another fresh directory without a
tsconfig. Save this repaired entry there. The parameter annotation states the accepted
input and the nullish fallback implements the chosen missing-user behavior.

```typescript
// file: repaired.ts
interface User { name: string }
function findUser(id: string): User | undefined {
  return id === "u1" ? { name: "Ada" } : undefined;
}
function greet(id: string): string {
  const user = findUser(id);
  return user?.name.toUpperCase() ?? "missing";
}
console.log(greet("missing"), greet("u1"));
```

```sh
tsc --strict --target es2022 --module commonjs --noEmitOnError --outDir repaired-dist repaired.ts
node repaired-dist/repaired.js
```

The result is `missing ADA`. The optional chain returns undefined for an absent
user; the fallback handles it. It does not validate arbitrary JSON or establish
that a dishonest declaration is true. Keep data parsing at its [runtime boundary](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>).

For a deliberate counterexample, replace `user?.name.toUpperCase() ?? "missing"`
with `user!.name.toUpperCase()`. The same strict build succeeds, then the missing
case throws TypeError. The non-null assertion removes a possibility from the
checker view and supplies no runtime check. Assertions can be appropriate when
an invariant is established elsewhere; explain that evidence. Adding them in bulk
does not implement the missing-data policy.

Strict null checking also does not make every indexed read optional. Save:

```typescript
// file: indexed.ts
function firstName(users: readonly { name: string }[]): string {
  return users[0].name;
}
console.log(firstName([]));
```

```sh
tsc --strict --target es2022 --module commonjs --outDir indexed-dist indexed.ts
# Expected runtime failure TypeError:
node indexed-dist/indexed.js
# Expected compiler failure TS2532:
tsc --strict --target es2022 --module commonjs --noUncheckedIndexedAccess --noEmit indexed.ts
```

The array operation needs the separate indexed-access policy. The [indexed-access
and optional-property owner](<../3. Modules Emit and Projects/3.3. noUncheckedIndexedAccess and exactOptionalPropertyTypes.md>)
develops that configuration; do not describe every diagnostic as a strictNullChecks
migration error.

### 3) **Inspect newer strict-family behavior instead of memorizing an old list**

`strictBuiltinIteratorReturn` changes the built-in iterator return type to
undefined rather than any. With strict null checks active, that makes an empty
Set's `.next().value` potentially undefined. This is a declaration/checking effect,
not a runtime iterator polyfill. The [option reference](https://www.typescriptlang.org/tsconfig/strictBuiltinIteratorReturn.html)
states the type change; [Dan Vanderkam's TypeScript 5.6 analysis](https://effectivetypescript.com/2024/09/30/ts-56/)
explains why this previously surprising source of any matters during upgrades.
The following probe verifies the current compiler instead of relying on that
article's historical baseline.

```typescript
// file: iterator.ts
const first = new Set<string>().values().next().value;
const required: string = first;
console.log(required);
```

```sh
# Expected compiler failure TS2322:
tsc --strict --target es2022 --module commonjs --noEmit iterator.ts
# Deliberately weaker check; runtime still produces undefined:
tsc --strict --strictBuiltinIteratorReturn false --target es2022 --module commonjs --outDir iterator-dist iterator.ts
node iterator-dist/iterator.js
```

The weaker build prints `undefined` even though `required` is annotated string.
The flag changes what this declaration permits the checker to infer, not what
an empty iterator returns. Prefer handling the optional value or iterator result
rather than weakening the flag to satisfy the annotation.

### 4) **Distinguish checking from mandatory runtime strict mode and declarations**

Most type checks add no runtime validation. JavaScript strict mode is a separate
execution rule. In TypeScript 7, alwaysStrict cannot be disabled even when the
checking-family switch is false. In a fresh directory without a tsconfig, save:

```typescript
// file: script.ts
function twice(value: number): number { return value * 2; }
console.log(twice(2));
// file: public-api.cts
export function maybeReady(ready: boolean) {
  return ready ? "ready" : undefined;
}
```

```sh
tsc --strict false --target es2022 --module commonjs --moduleDetection legacy --outDir loose-script script.ts
tsc --strict --target es2022 --module commonjs --moduleDetection legacy --outDir strict-script script.ts
node loose-script/script.js
node strict-script/script.js
tsc --strict false --target es2022 --module nodenext --declaration --outDir loose-api public-api.cts
tsc --strict --target es2022 --module nodenext --declaration --outDir strict-api public-api.cts
```

Both scripts print 4 and both builds contain the `"use strict"` directive.
Trying `tsc --strict false --alwaysStrict false --target es2022 --module commonjs
--noEmit script.ts` fails with TS5108 in TypeScript 7. The [TypeScript 6 migration
notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html#deprecated---alwaysstrict-false)
explain the move to mandatory JavaScript strict-mode semantics. The older
[alwaysStrict option description](https://www.typescriptlang.org/tsconfig/alwaysStrict.html)
explains the directive but does not establish that its false value is still
supported. ES modules already execute in JavaScript strict mode; that runtime
mode is distinct from the compiler's checking-family switch.

Inspect the two `public-api.d.cts` files. Without strict null checking, the
inferred return is string; with it, the return is `"ready" | undefined` in this
compiler. Both JavaScript implementations can return undefined. A publisher's
inferred declaration can therefore change with configuration even if the function
body does not. Test the actual declaration and consumer contract; do not promise
that publisher strictness can never affect consumers.

### 5) **Plan migration from observed dependencies and errors**

For a small codebase, enabling the full family and fixing the resulting errors
may be manageable. For a large one, check the same source under candidate flags,
classify the errors and select reviewable steps. In this fixture either nullable
reads or implicit parameters can be addressed first; full strictness still needs
both repairs. The [official migration guide](https://www.typescriptlang.org/docs/handbook/migrating-from-javascript.html#moving-to-typescript-files)
even discusses enabling noImplicitAny early. No universal incident-frequency or
nullability-first ordering follows from the language.

Keep the intended runtime behavior under test as each step lands. Use checked
configuration inheritance or separate projects where a real program boundary
supports it. Compiler options apply to a program, not arbitrary directories
inside that program. `exclude` affects root-file discovery; imported dependencies
can still enter the program. `skipLibCheck` concerns declaration checking and is
not a per-source-file strictness exemption. The project-options lessons own those
boundaries; do not treat a configuration comment as enforcement.

A nonzero checker exit must fail its configured gate. `noEmitOnError` prevents
new output on errors; it does not delete output from previous successful builds.
Use clean artifacts when validating a release. Document deliberate overrides and
support baselines so upgrades and handoffs can reproduce the actual checking mode.

### 6) **Common confusion**

Null checking exposes possible absence; it does not force one universal handling
policy. A fallback, explicit error or caller-visible optional return may each be
appropriate. Choose from the API's meaning. Likewise, null and undefined can
express different conventions, but the compiler does not require “intentional”
versus “incidental” absence based on their names.

Strict does not include every stricter flag, eliminate any, validate inputs or
make assertions true. An error is evidence of a mismatch needing investigation;
it is not automatically proof of a production crash. The indexed and iterator
examples show why identifying the specific active option matters.

### 7) **Performance note**

No compiler-speed, startup or incident-rate benchmark was run here. Checking cost
depends on the program and options; a fixed single-digit overhead is unsupported.
Use extended diagnostics on the actual project when build performance matters.
Most checking changes add no runtime tests. This compiler always assumes
JavaScript strict mode, while declaration inference can change the published
checking contract.
Runtime fallback or validation code has its ordinary execution cost.

### 8) **Mentor note**

Ask a learner to predict the diagnostics for null-only, any-only and full strict
checks before running the matrix. Then ask why the asserted repair compiles but
still throws. A sound answer separates the parameter contract, optional result,
selected handling policy and erased assertion.

For migration review, ask which configuration and inputs the command actually
loads, which override is active and which regression demonstrates the intended
behavior. For a library, add the emitted declaration diff. This yields reviewable
evidence without equating error counts or assertion counts with incident rates.
