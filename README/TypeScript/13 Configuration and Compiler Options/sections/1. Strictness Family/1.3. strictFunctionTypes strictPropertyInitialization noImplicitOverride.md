## 1.3. `strictFunctionTypes`, `strictPropertyInitialization`, `noImplicitOverride`

### 1) **`strictFunctionTypes` contravariance** (strict function positions, bivariant methods)

**Definition** — `strictFunctionTypes: true` (in `strict`) checks *function-type* positions contravariantly (a `(x: Animal) => void` is NOT assignable to `(x: Cat) => void` — narrower parameter required); *method* shorthand positions stay bivariant (unsound escape for OOP ergonomics — `m(x: Cat)` accepts `m(x: Animal)` implementations). [02/3.2](<../../../02 The Type System Core/sections/3. Soundness and variance/3.2. Function variance and strictFunctionTypes.md>) owns variance theory; [05/3.2](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.2. Callback variance strictFunctionTypes and bivariance pitfalls.md>) owns callable practice — this promise owns *configuring* it (enabling, reading its errors, migrating call sites).

**What problem it solves / history** — bivariant-by-default callbacks let `(x: Cat) => void` handlers receive arbitrary `Animal`s (property reads on missing members — `c.meows` on a `Dog` — compiling cleanly). Strict function types convert each such assignment into an authoring error *at the assignment* (not at the property read three calls later): contravariance enforced where callbacks flow, bivariance kept where methods need ergonomic override freedom.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), keep the flag on (in `strict` — never disable to silence a variance error; fix the direction instead); write callbacks as property-style function types (`cb: (x: Cat) => void` — strict) when contravariance protects, method shorthand (`m(x: Cat): void` — bivariant) when override ergonomics matter; read TS2345 variance errors as direction diagnostics (which side is narrower? which position?).

**Runnable example** — direction enforced at assignment (good vs bad, `tsc --strict`):

```typescript
// good — contravariant acceptance: Animal-handler serves Cat positions (wider param, safe)
interface Animal { name: string }
interface Cat extends Animal { meows: boolean }
type CatHandler = (c: Cat) => string;
const wide: CatHandler = (a: Animal) => a.name.toUpperCase(); // ok (accepts any Animal, Cat included)
console.log(wide({ name: "m", meows: true })); // M — direction correct, use safe
// const narrow: (a: Animal) => string = (c: Cat) => "x"; // error TS2322 (Cat-handler can't serve Animal positions)
```

```typescript
// good — property-style callbacks stay strict (the protection working as configured)
interface Evt { kind: string; at: number }
interface Registry { onEvent: (e: Evt) => void }
const reg: Registry = {
  onEvent: (e: { kind: string }) => console.log(e.kind.toUpperCase()), // ok: wider param (fewer requirements) accepted — contravariance
};
console.log("registered");
// bad — narrowing callback smuggled through method shorthand (bivariant escape, unsound by design)
// interface MReg { onEvent(e: Evt): void } // method syntax: bivariant (accepts narrower — the escape)
// fix — property-style for callbacks (strict); method shorthand for overridable class members (ergonomic)
```

```typescript
// good — generic handlers thread variance through parameters (per 08/2.1 constraint discipline)
interface Animal { name: string }
function handle<T extends Animal>(h: (x: T) => string, x: T): string { return h(x).toUpperCase(); }
const nm = (a: Animal): string => a.name;
console.log(handle(nm, { name: "r" })); // R — constraint bounds, contravariance protects calls
// bad — (x: any) => string handlers (variance unchecked entirely — any absorbs both directions)
// fix — precise params + strict flag: direction errors surface at assignment (cheapest location in the pipeline)
```

**Common confusion** — "the flag broke my working handler" — the handler was *unsound* (narrower param than the position allows — worked until a wider value arrived); the flag surfaced latent incorrectness, it didn't create it. "methods should be strict too" — method bivariance is *deliberate* (OOP override ergonomics — see 02/3.3's budgeted-risk framing); property-style callbacks are the strict spelling — choose per position, don't wish the flag broader. "variance errors need casts" — casts launder direction violations (the exact hole the flag closes); fix by widening the callback param or narrowing the position type.

**Performance note** — variance checking is O(positions) per assignment (trivial); the dividend is deleted contravariance incidents (property-reads on absent members — unbounded debugging per occurrence). No emit delta — direction is purely a checking relation.

**Mentor note** — flip one callback from method shorthand to property style and watch the bivariant hole close (same code, new error surfacing latent unsoundness) — position syntax as a safety control in one edit. Exercise: audit callbacks for method-shorthand smuggling (bivariant where strict was intended) — each a contravariance incident waiting. Gate: narrowing callbacks through method syntax fail review where strictness was intended.

Covariance contravariance and invariance who varies which way.md>) + [3.2. strictFunctionTypes](<../../../02 The Type System Core/sections/3. Soundness and variance/3.2. ### 2) **`strictPropertyInitialization`** (definite assignment for class fields)

**Definition** — `strictPropertyInitialization: true` (in `strict`) requires every non-optional class property to be *definitely assigned*: via declaration initializer (`x = 1`), constructor assignment (`this.x = …` on all paths), or definite-assignment assertion (`x!: T` — justified, documented). Unproven fields error TS2564/TS2565 at declaration — construction contracts checked, not assumed.

**What problem it solves / history** — uninitialized fields (`class U { name: string }` with no assignment — `undefined` at runtime, `string` in types) crashed on first method call (`this.name.toUpperCase()` — `TypeError` with a confident type). The flag converts each unproven field into a declaration error *listing the field*: initialize, make optional, or assert-with-justification — three honest options replacing one silent lie.

**Modern guidance** — as of TypeScript 5.9 era, initialize at declaration where possible (`x = default` — simplest, always definite); assign in constructors covering all paths (early-return branches must assign before returning); use `!` only for framework-assigned fields (ORM hydration, DI injection, test setup — with a comment naming the external assigner). Never disable the flag per class-file (scope `!` per field, not blindness per file).

**Runnable example** — assignment proven three ways (good vs bad, `tsc --strict`):

```typescript
// good — initializer (simplest definite assignment, preferred where possible)
class Cfg {
  host = "localhost"; // assigned at declaration (definite on every construction path)
  port = 80;
  addr(): string { return `${this.host}:${this.port}`; }
}
console.log(new Cfg().addr()); // localhost:80 — no constructor needed, fields proven
```

```typescript
// good — constructor assignment on all paths (early returns assign first)
class Session {
  token: string; // assigned below on EVERY path (checker verifies each branch)
  constructor(ok: boolean) {
    if (!ok) {
      this.token = "guest";
      return; // assigned before return (each exit path proven separately)
    }
    this.token = "user";
  }
}
console.log(new Session(false).token.toUpperCase()); // GUEST — branch-checked assignment
// bad — class Bad { t: string; constructor(ok: boolean) { if (ok) this.t = "x"; } } (error TS2564: else-path unassigned)
// fix — assign on all paths, make optional (t?: string), or assert-with-reason (!)
```

```typescript
// good — definite-assignment assertion for externally-assigned fields (justified, documented)
class Entity {
  id!: string; // assigned by ORM hydration (external assigner documented HERE, not hidden)
  label(): string { return this.id.toUpperCase(); }
}
const e = new Entity();
e.id = "e1"; // hydration (the documented external assignment, now reviewable)
console.log(e.label()); // E1 — ! scoped to one field with a named assigner
// bad — strictPropertyInitialization: false (whole-file blindness for one hydratd field — scope !, not the flag)
```

**Common confusion** — "`!` is cheating" — `!` *documents* external assignment (reviewable claim with a named assigner); cheating is *undocumented* `!` (claim without evidence) — justification distinguishes. "optional (`?`) equals `!`" — `?` admits `undefined` *forever* (every read narrows); `!` claims assignment *once* (reads trusted after) — different contracts for different knowledge (maybe-absent vs externally-assigned). "constructors always satisfy" — only *all-paths* assignment satisfies (early returns, conditional branches, try/catch exits each need proof — the checker verifies paths, not intentions).

**Performance note** — zero emit delta (assignment checks erase); field initializers emit per construction (same as constructor assignments — identical runtime). The dividend is deleted undefined-field incidents (first-method-call crashes — unbounded debugging per occurrence).

**Mentor note** — remove one constructor assignment and read TS2564 naming the field (declaration-error precision vs runtime-crash vagueness). Exercise: convert three `!` fields to initializers/optionals where possible (each conversion deletes a trust claim); justify the remainder with assigner comments. Gate: undocumented `!` fails review; flag-disabling fails review absolutely.

### 3) **`noImplicitOverride`** (explicit overrides — renames break loudly)

**Definition** — `noImplicitOverride: true` (NOT in `strict` — enable separately) requires `override` on every member that overrides a base member: missing keyword errors TS4114 (looks like an override, isn't declared one); `override` on non-overriding members errors TS4113 (declared override, nothing overridden). Renaming a base member breaks every derived `override` loudly (error per site) instead of silently orphaning derived methods (dead code shadowing nothing).

**What problem it solves / history** — base renames (`render()` → `paint()`) silently orphaned derived `render()` methods (still compiling, never called — dead overrides shipping while the new base method ran unextended). The flag converts renames into compiler-enumerated migration lists: every `override` site errors until updated-or-deleted — the rename's blast radius computed, not discovered.

**Modern guidance** — as of TypeScript 5.9 era, enable `noImplicitOverride` alongside `strict` in every tsconfig (the strict-adjacent eighth flag — same contract spirit); mark every override explicitly (methods *and* properties — `override name = …` for field overrides); treat base renames as migration events (fix each TS4114 loudly — update to the new name or delete the orphan, never remove `override` to silence).

**Runnable example** — renames enumerated, orphans impossible (good vs bad, `tsc --strict --noImplicitOverride`):

```typescript
// good — explicit overrides: base rename breaks every site loudly
class View {
  render(): string { return "base"; }
}
class Page extends View {
  override render(): string { return "page:" + super.render(); } // declared (rename-tracked)
}
console.log(new Page().render()); // page:base — override chain explicit end to end
// base renames render→paint: Page.render errors TS4113 (no base member — update to paint or delete: enumerated!)
```

```typescript
// good — property overrides declared (fields shadow too — silently without the flag)
class Cfg2 {
  timeout = 100;
}
class Fast extends Cfg2 {
  override timeout = 10; // declared field override (base rename breaks this loudly)
}
console.log(new Fast().timeout.toFixed(0)); // 10 — field override tracked like methods
// bad — timeout = 10 without override (compiles today; base renames timeout→limit → orphan field shipping silently)
// fix — override keyword: shadowing declared (rename-tracked) instead of accidental
```

```typescript
// good — super calls pair with override declarations (chain explicit both directions)
class Base2 {
  render(): string { return "base"; }
}
class Log2 extends Base2 {
  override render(): string { return `[${super.render()}]`; } // super + override (chain readable both ways)
}
console.log(new Log2().render()); // [base] — explicit chain (each link declared, each rename tracked)
// bad — noImplicitOverride off (default): orphan overrides accumulate silently across refactors (dead methods, live confusion)
// fix — flag on + override everywhere: renames enumerate, orphans error, chains read explicitly
```

**Common confusion** — "the flag is only for methods" — properties/fields override too (`override timeout = 10` — field shadowing tracked identically). "`override` on non-overrides is harmless" — errors TS4113 (declared override with no base member — usually a *deleted* base member whose derived references need cleanup, not silence). "base renames are rare" — library major versions rename regularly; internal refactors rename constantly — rarity is no defense (one silent orphan per rename, compounding).

**Performance note** — zero emit/runtime delta (keyword erases; dispatch identical) — pure checking discipline with incident-deletion upside (orphan-override class) at one keyword per member.

**Mentor note** — rename one base method live and watch derived `override`s error per site (migration list computed) vs unmarked derived methods staying green (orphans shipping) — tracked-vs-silent in one rename. Exercise: enable the flag on a legacy hierarchy and mark each TS4114 (each a previously-silent override relationship, now explicit). Gate: overriding members without `override` fail review unconditionally.
