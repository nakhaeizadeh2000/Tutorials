## 1.3. strictFunctionTypes, strictPropertyInitialization and noImplicitOverride

These options check different relationships: which functions may substitute for
others, whether an instance field has initialization evidence, and whether a
member deliberately overrides an inherited implementation. Strict enables the
first two. `noImplicitOverride` is a separate option. Use TypeScript 7.0.2 and
Node 20.20.2 in a fresh directory without a tsconfig for the experiments below.

### 1) **Verify function assignment in the correct direction**

A function that accepts every Animal can serve a position that supplies only Cats.
A Cat-only function cannot safely serve a position that may supply an Animal
without meow. The [callback owner](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.2. Callback variance strictFunctionTypes and bivariance pitfalls.md>)
explains the substitution relationship; here we observe the switch.

```typescript
// file: variance.mts
interface Animal { name: string }
interface Cat extends Animal { meow(): string }
const catOnly = (cat: Cat): string => cat.meow();
const forAnimals: (animal: Animal) => string = catOnly;
console.log(forAnimals({ name: "dog" }));
```

```sh
# Expected TS2322:
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmit variance.mts
# Deliberately weaker check, followed by runtime TypeError:
tsc --strict --strictFunctionTypes false --target es2022 --module nodenext --moduleResolution nodenext --outDir unsafe-dist variance.mts
node unsafe-dist/variance.mjs
```

The flag-off build accepts the assignment but cannot supply a missing meow
function. Repair the callback's body to handle the values this consumer supplies,
or restrict the consumer after establishing the narrower input contract.
Changing only an annotation while keeping an unconditional meow call is not a
behavioral repair. This safe direction needs no flag override:

```typescript
// file: wide.mts
interface Animal { name: string }
interface Cat extends Animal { meow(): string }
const animalHandler = (animal: Animal): string => animal.name.toUpperCase();
const forCats: (cat: Cat) => string = animalHandler;
console.log(forCats({ name: "m", meow: () => "mew" }));
```

Build with the same strict options and `--outDir dist wide.mts`; run
`node dist/wide.mjs` for `M`. The [option reference](https://www.typescriptlang.org/tsconfig/strictFunctionTypes.html)
also documents the method-syntax exception. It remains possible to accept an
unsafe method assignment under strict:

```typescript
// file: methods.mts
interface Animal { name: string }
interface Cat extends Animal { meow(): string }
interface MethodReceiver { handle(animal: Animal): string }
const receiver: MethodReceiver = {
  handle(cat: Cat): string { return cat.meow(); }
};
console.log(receiver.handle({ name: "dog" }));
```

Build methods with the same strict options, then run `node dist/methods.mjs`:
the build passes and the runtime throws TypeError. Change the target declaration
to `interface MethodReceiver { handle: (animal: Animal) => string }` and check
again: TS2322 rejects the narrow handler. Choose callback property contracts
when this strict substitution check is required. Method syntax is a checking
exception, not proof that a subclass-only callback handles all base values.

### 2) **Distinguish initialization evidence from an initialization promise**

Save this deliberately incomplete class:

```typescript
// file: unset.mts
class Client {
  endpoint: string;
  upper(): string { return this.endpoint.toUpperCase(); }
}
console.log(new Client().upper());
```

```sh
# Expected TS2564:
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmit unset.mts
# Deliberately weaker check, followed by runtime TypeError:
tsc --strict --strictPropertyInitialization false --target es2022 --module nodenext --moduleResolution nodenext --outDir unsafe-dist unset.mts
node unsafe-dist/unset.mjs
```

Replacing `endpoint: string` with `endpoint!: string` makes the strict build pass
but leaves the same runtime failure. The assertion records a trusted promise;
a comment naming an external initializer does not execute it. If endpoint must
exist before first use, a constructor can establish that lifecycle directly:

```typescript
// file: initialized.mts
class Client {
  endpoint: string;
  constructor(endpoint: string) { this.endpoint = endpoint; }
  upper(): string { return this.endpoint.toUpperCase(); }
}
class OptionalClient {
  endpoint: string | undefined;
  upper(): string { return this.endpoint?.toUpperCase() ?? "missing"; }
}
console.log(new Client("api").upper(), new OptionalClient().upper());
```

Build initialized with the same strict options and run `node dist/initialized.mjs`:
the result is `API missing`. A field whose type admits undefined does not require
a string initializer. A field initializer is another option when a real default
exists. Constructor branches must provide the appropriate assignment evidence;
calling a helper method does not automatically make its effects part of definite
assignment analysis. An ambient `declare` field is also a description, not an
ordinary initialization obligation or runtime provider.

The [property-initialization reference](https://www.typescriptlang.org/tsconfig/strictPropertyInitialization.html)
shows the undefined-admitting case. This check depends on strict null checking;
the [strict-family lesson](<./1.1. strict and strictNullChecks the nullability contract.md>)
tests the implicit dependency and explicit invalid combination. The [constructor
owner](<../../../06 Classes and Object-Oriented Types/sections/1. Class Type Fundamentals/1.2. Constructors parameter properties and instance creation.md>)
owns complete construction and external-initialization patterns. Runtime class
field order and definition versus assignment semantics are separate concerns;
do not infer equivalence from both forms satisfying this checker.

### 3) **Enable override checks without overstating what they require**

NoImplicitOverride requires markers for overriding concrete inherited members.
The marker itself also checks that a corresponding base member exists, even
when the option is off. Save:

```typescript
// file: overrides.mts
class View {
  timeout = 100;
  render(): string { return "base"; }
}
class Page extends View {
  override timeout = 10;
  override render(): string { return "page:" + super.render(); }
}
abstract class AbstractView { abstract render(): string; }
class ConcreteView extends AbstractView {
  render(): string { return "concrete"; }
}
console.log(new Page().render(), new Page().timeout, new ConcreteView().render());
```

```sh
tsc --strict --noImplicitOverride --target es2022 --module nodenext --moduleResolution nodenext --noEmitOnError --outDir dist overrides.mts
node dist/overrides.mjs
```

The output is `page:base 10 concrete`. Remove the marker from Page.render or
Page.timeout: with the option on, TS4114 rejects the corresponding concrete
override. With the option off, those unmarked overrides are permitted. Strict
alone does not enable noImplicitOverride. The [option reference](https://www.typescriptlang.org/tsconfig/noImplicitOverride.html)
explains the refactoring motivation.

ConcreteView deliberately omits override when implementing the abstract method:
this is accepted even with noImplicitOverride. Adding the marker there is also
legal. A team's convention may require it, but “every implementation must carry
override under this option” is too broad.

For a refactor experiment, rename only View.render to paint. Page's marked render
now reports TS4113; its super.render call also reports that the base member is
missing. Turning noImplicitOverride off does not disable the meaning of an
existing override marker. Decide whether Page should follow the renamed API or
become a separate member. Removing the marker solely to silence the diagnostic
can conceal an unintended relationship change. The check does not guarantee
behavioral substitutability or that all old callers use the intended entry point.

### 4) **Common confusion**

These three checks cannot replace each other. Override markers do not close the
method variance exception. Definite-assignment assertions do not assign a field.
A callback annotation cannot manufacture members on an argument. Identify the
relationship that failed before disabling a flag or changing a type.

A type that permits absence and a promise that initialization happens elsewhere
also differ. The former makes consumers handle undefined; the latter asks them
to trust a lifecycle invariant. Keep that invariant with an actual provider and
a first-use check. A constructor's accepted assignment evidence is not a general
proof of every runtime initialization path.

### 5) **Performance note**

The checking options and override/type assertions do not add runtime guards.
Actual field initializers, constructor assignments and callbacks still execute.
This lesson measured no checking complexity, startup speed or allocation cost.
Field definition and assignment can have different effects under inheritance
and emit settings; do not claim identical runtime work merely because both
satisfy property initialization. The override keyword erases while dispatch
continues to follow the actual runtime object.

### 6) **Mentor note**

Ask the learner to draw the callback assignment from supplied inputs to required
members, then predict the flag-off failure. A correct answer explains why the
Animal handler serves Cat calls and why the reverse is unsafe. Next change only
the method receiver's target syntax and explain the new diagnostic.

For a class review, require the initialization producer and first-use evidence.
For an override review, compare the concrete and abstract cases before applying
a blanket rule. The goal is to connect each option with a particular observable
contract, not to memorize three flag names as a complete safety certificate.
