## 5.1. Real production bugs caused by configuration misunderstandings

### 1) **`strict: false` shipped `undefined` is not an object across checkout** (unstrict nullability)

**Definition** — a checkout service compiled with `strict: false` (legacy tsconfig, "too many errors to enable") typed `currentCoupon(): Coupon` while returning `undefined` for coupon-less carts — `coupon.code.toUpperCase()` threw `TypeError` on every guest checkout (100% of non-logged-in purchases) with green CI, typed signatures, and zero diagnostics pointing at the boundary.

**What problem it solves / history** — unstrict nullability is the *absence* of a contract where one is most needed (money paths with optional entities — coupons, discounts, gift state): every `Coupon`-typed value possibly `undefined` at runtime, never in types. `strictNullChecks` converts the class: `Coupon | undefined` returns force handling (`?.`/`??`/early-return) at every call site — guest-checkout crashes become compile branches.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), enable `strict` (nullability included) before any other reliability work — unstrict codebases debug *despite* their types (every fix re-verified at runtime); strict codebases debug *with* them (each error a fix site). Money paths go strict first (highest incident density per line), never last.

**Runnable example** — strict boundary vs unstrict crash (good vs bad, `tsc --strict`):

```typescript
// good — nullable return forces handling (strict contract, guest-safe)
interface Coupon { code: string }
function currentCoupon(has: boolean): Coupon | null {
  return has ? { code: "SAVE10" } : null; // nullability in the signature (honest boundary)
}
function price(has: boolean): string {
  const c = currentCoupon(has);
  return c === null ? "full" : `discount:${c.code}`; // branch forced (crash class deleted)
}
console.log(price(false), price(true)); // full discount:SAVE10 — guest path handled, not thrown
```

```typescript
// bad — unstrict signature lies about absence (the pre-strict shape that shipped the incident)
// function currentCouponBad(has: boolean): Coupon { return has ? { code: "S" } : null as unknown as Coupon; }
// currentCouponBad(false).code.toUpperCase(); // TypeError at runtime (green CI, confident types, guest crash)
// fix — Coupon | null + branch (strictNullChecks converts the incident into a compile error at the boundary)
interface Coupon { code: string }
function currentCoupon2(has: boolean): Coupon | null {
  return has ? { code: "S" } : null;
}
const c2 = currentCoupon2(false);
console.log(c2?.code ?? "none"); // none — honest absence (narrowed, never thrown)
```

```typescript
// good — triage order starts here (nullability class first — biggest incident yield per error fixed)
interface Coupon { code: string }
function currentCoupon2(has: boolean): Coupon | null { // re-declared: fences compile standalone
  return has ? { code: "S" } : null;
}
function checkoutTotal(items: string[], hasCoupon: boolean): string {
  const c = currentCoupon2(hasCoupon);
  return `${items.length} items ${c === null ? "full-price" : c.code}`; // branch per nullable (habit, not heroics)
}
console.log(checkoutTotal([], false)); // 0 items full-price — empty + couponless composed safely
// bad — shipping strict:false to "move fast" (null crashes move fastest of all — into production, at scale)
// fix — strict first (1.1 promise 3's sequence: nullability errors dominate AND prevent the most incidents)
```

**Common confusion** — "strict slows checkout development" — strict *surfaces* the guest-path branch every checkout needs regardless (unstrict defers it to production — same work, worse timing, customer impact). "one `?.` fixes unstrict code" — spot-narrowing without the flag leaves a thousand un-narrowed reads (the flag *enumerates* them — piecemeal `?.` without enumeration is theater). "legacy checkout can't go strict" — per-file triage (checkout first — incident density justifies priority; rest sequenced after).

**Performance note** — zero emit delta (branches compile identically); check cost one flow-branch per nullable use (trivial); incident deletion (null-`TypeError` across money paths — unbounded revenue + trust impact) — highest-ROI flag flip in typed practice, period.

**Mentor note** — replay one guest checkout under unstrict types (confident `Coupon`, runtime `undefined`, thrown `code` read) — nullability theater in one request. Exercise: enable `strictNullChecks` on the money paths first and fix each error with narrowing (error count = incident backlog, prioritized free). Gate: money paths without `strict` fail review unconditionally.

### 2) **Mismatched module/resolution pair bundled CJS as ESM and crashed** (interop divergence at load)

**Definition** — a service configured `module: nodenext` + legacy `moduleResolution` resolved a dual-package dependency's *types* via one condition set and its *runtime* via another (checker green on ESM types, Node loading CJS entry — or the reverse): `import` bindings arrived as interop-wrapped-or-bare mismatches (`undefined` default, missing named) — crashing at first use in production with green typecheck.

**What problem it solves / history** — unpaired settings (`module` modernized alone during an ESM migration, resolution left legacy "temporarily") split check-time and run-time graphs silently: tsc resolved per legacy rules (finding *a* declaration), Node resolved per `exports` conditions (loading *another* entry) — agreement assumed, divergence shipped. Pairing (3.1 promise 1) makes the checker *simulate* the runtime (same algorithm — divergence structurally impossible).

**Modern guidance** — as of TypeScript 5.9 era, pair per runtime (nodenext/nodenext for Node, bundler/bundler for Vite/Next — documented beside the deploy target); verify with `traceResolution` on mapped + relative imports per project setup (paired output = agreement proof); migrate settings *with* runtimes (CJS→ESM moves module, resolution, extensions, and conditions in one PR — never piecemeal).

**Runnable example** — paired agreement vs unpaired divergence (multi-file sets):

```typescript
// file: paired171.ts
export function start(): string { return "started"; } // paired resolution (explicit .js imports below verify)
// file: app171.ts
import { start } from "./paired171.js"; // explicit extension (nodenext agreement — checker + Node identical)
console.log(start().toUpperCase()); // STARTED — paired settings (graphs agree by construction)
// bad — module: nodenext + legacy resolution (checker finds types one way, Node loads another — green CI, load crash)
// fix — pair the settings (3.1 promise 1: matched algorithms, identical graphs, verified via traceResolution)
```

```typescript
// file: dual172.ts
export default { go: () => "go" }; // dual-shape default (interop-sensitive under mismatched pairs)
// file: app172.ts
import bundle from "./dual172.js"; // default import (bridged identically when paired; divergent when not)
console.log(bundle.go().toUpperCase()); // GO — paired interop (checker + runtime agree on the default slot)
// bad — unpaired interop (checker synthesizes default per its rules, runtime per its own — slot mismatch at load)
// fix — pair + verify (traceResolution shows which entry/condition each side selects — agreement visible per import)
```

```typescript
// file: cond173.ts
export const ENV173 = "prod"; // conditions-sensitive entry (exports map selects per importer kind)
// file: app173.ts
import { ENV173 } from "./cond173.js";
console.log(ENV173.toUpperCase()); // PROD — conditions agreed (paired resolution simulates the runtime's condition set)
// bad — resolution ignoring exports conditions (legacy lookup finds filesystem neighbors the runtime never serves — phantom modules)
// fix — nodenext/bundler resolution (exports-aware — conditions simulated, phantom modules unresolvable loudly)
```

**Common confusion** — "resolution mismatches are rare" — *every* unpaired project mismatches on *some* import (exports-mapped subpaths, extensionless ESM, dual entries — modern packages trigger all three routinely). "bundlers forgive mismatches" — bundlers resolve *per their own* rules (third graph — neither tsc-legacy nor Node) — forgiveness is divergence with better error messages. "traceResolution is arcane" — one command per setup (two imports traced — agreement proof in seconds, rerun per settings change).

**Performance note** — paired resolution costs one deterministic lookup per import (cached); mismatched resolution costs load crashes (unbounded) plus traceResolution forensics per incident. Pairing is pure incident prevention at zero steady cost.

**Mentor note** — mismatch one project deliberately and run the same import under tsc + Node (green check, load crash — divergence demonstrated in 60 seconds). Exercise: table every package's runtime + pairing (mismatches are pre-filed incidents; fix by re-pairing same-PR as runtime declarations). Gate: unpaired `module`/`moduleResolution` fail config review.

### 3) **Elided side-effect import skipped plugin registration in prod only** (heuristics vs bundlers)

**Definition** — `import { Plugin } from "./setup"` (used type-only) elided under tsc heuristics (import deleted — setup never evaluated) while esbuild preserved it (registration ran): tests (esbuild) green with plugins registered; production (tsc-emit) missing every plugin (routes unhandled, 404s across the board). Same source, two module graphs — behavior diverging by toolchain, diagnosed nowhere.

**What problem it solves / history** — elision heuristics decide emit from usage analysis (type-only use → delete) while side effects live in evaluation (deleted import = skipped body) — colliding exactly when value imports serve *both* typing and loading. `verbatimModuleSyntax` + split imports (bare `import "./setup"` for loading, `import type` for typing) separate the jobs: each statement has one emit semantic, identical on every toolchain.

**Modern guidance** — as of TypeScript 5.9 era, split dual-purpose imports (bare for loading, `import type` for typing — never one statement serving both); enable `verbatimModuleSyntax` (heuristics off — stated traffic only); verify with dual-pipeline CI (tsc-emit + bundler executing the same registration test — divergence fails the build). See [2.2. verbatimModuleSyntax](<../2. Erasable and Isolated Toolchain/2.2. verbatimModuleSyntax predictable emit.md>) + 12/5.1 promise 2's fuller treatment.

**Runnable example** — loading stated, typing stated (multi-file sets):

```typescript
// file: setup174.ts
console.log("setup evaluated");
export interface Plugin174 { name: string }
// file: app174.ts
import "./setup174.js"; // BARE import (loading stated — kept verbatim on every toolchain, registration runs)
import type { Plugin174 } from "./setup174.js"; // type traffic (erased — zero weight, zero guessing)
const p: Plugin174 = { name: "x" };
console.log(p.name.toUpperCase()); // X (+ "setup evaluated" exactly once, everywhere — split imports, identical graphs)
// bad — import { Plugin174 } (type-only use → elided by tsc heuristics → setup never evaluates in prod; kept by esbuild in tests)
// fix — bare + import type (each job its own statement: loading guaranteed, typing erased, divergence impossible)
```

```typescript
// file: setup175.ts
export const registry175: string[] = [];
console.log("registry loaded");
// file: app175.ts
import "./setup175.js"; // kept (verbatim — evaluation guaranteed regardless of usage analysis)
import { registry175 } from "./setup175.js"; // value use (also keeps — belt and suspenders, both honest)
registry175.push("a");
console.log(registry175.length); // 1 (+ "registry loaded" — module evaluated because STATEMENTS say so, not heuristics)
// bad — type-only consumption of a side-effect module (elision deletes the load the app needed — toolchain roulette)
// fix — verbatimModuleSyntax: stated imports never reinterpret when module bodies evolve (stability by construction)
```

```typescript
// file: setup176.ts
export interface Cfg176 { v: number } // side-effect-free module (erasure total and safe — no bare import needed)
// file: app176.ts
import type { Cfg176 } from "./setup176.js"; // pure types (no loading job exists — single honest statement)
const c: Cfg176 = { v: 1 };
console.log(c.v.toFixed(0)); // 1 — side-effect-free modules erase cleanly (bare imports reserved for loaders)
// bad — bare-importing side-effect-free modules (harmless but noisy — review asks "what load does this guarantee?" with no answer)
// fix — bare imports ONLY for loaders/registrars (each bare import names a load the app needs — auditability preserved)
```

**Common confusion** — "side-effect imports are smell" — registration/plugin/polyfill modules *are* side effects by design (evaluation *is* the API) — bare imports state the design honestly. "bundlers handle this" — bundlers preserve what tsc *emits* (elided imports never arrive — the toolchain split *is* the incident; verbatim emit unifies it). "one import serving both jobs is fine" — dual-use imports are exactly what heuristics misjudge (usage evolves type-only silently — elision flips on unrelated edits).

**Performance note** — bare imports cost the module's evaluation (intended — registration runs); `import type` costs zero (erased) — stating both pays each exactly once, visibly. Heuristic elision "saved" evaluation by *breaking* the app — the most expensive optimization in this domain's ledger.

**Mentor note** — delete a bare side-effect import and watch registration vanish (then restore) — load-vs-type separation in one deletion. Exercise: grep value imports used type-only in side-effect modules (elision-risk set) and split each — the at-risk list is the incident backlog, pre-triaged.

### 4) **`skipLibCheck: false` on generated declarations timed out CI** (50k-line codegen `.d.ts`)

**Definition** — `skipLibCheck: false` (explicit — default *true*) type-checks *all* `.d.ts` (including generated 50k-line codegen declarations with deep conditional instantiations): CI typecheck ballooned past timeouts on the codegen package while application code waited. Generated declarations (correct-by-construction from checked sources) cost more to *re-verify* than any defect they've ever contained.

**What problem it solves / history** — full-lib checking treated generated declarations as hand-written (worth verifying line-by-line) — but generated `.d.ts` derives from already-checked sources (re-verification with near-zero defect yield at full instantiation cost). `skipLibCheck: true` (the default — keep it) skips *declaration-file internals* (still checks assignability *against* them at use sites — consumer contracts verified, library innards trusted).

**Modern guidance** — as of TypeScript 5.9 era, keep `skipLibCheck: true` (default — don't touch it); scope exceptions per path where needed (never global `false` — the flag is all-or-nothing per program, so scope via project references: generated packages checked separately on their own schedule, apps skipping). Distinguish *checking declarations* (skipped internals) from *checking against declarations* (always on — consumer assignability verified regardless).

**Runnable example** — trust boundaries, not blanket checking (multi-file sets):

```typescript
// file: gen177.ts
export interface Big177 { a: string } // stands in for generated sources (checked at generation; declarations trusted downstream)
// file: app177.ts
import type { Big177 } from "./gen177.js";
const b: Big177 = { a: "x" }; // assignability AGAINST declarations (always checked — skipLibCheck never skips USES)
console.log(b.a.toUpperCase()); // X — consumer contracts verified (declaration internals trusted, not re-verified)
// bad — skipLibCheck: false globally (50k-line codegen .d.ts re-verified per CI run — timeouts for near-zero defect yield)
// fix — default true (trust generated innards); verify generation (regenerate-diff per 12/3.1) instead of re-checking output
```

```typescript
// file: hand178.ts
export function precise(a: string, b: number): string { return `${a}:${b}`; } // hand-written sources (checked fully — sources are never skipped)
// file: app178.ts
import { precise } from "./hand178.js";
console.log(precise("x", 1).toUpperCase()); // X:1 — source checking unaffected by skipLibCheck (flag scopes .d.ts internals only)
// bad — "skipLibCheck hides type errors" (hides LIBRARY-INTERNAL errors; consumer-facing assignability always checked)
// fix — understand the boundary (skip innards, check uses — trust with verification at the generation step, per 12/3.1)
```

```typescript
// file: scoped179.ts
export const S179 = 1; // scoped checking demo (per-path scoping via references, not global flags)
// file: app179.ts
import { S179 } from "./scoped179.js";
console.log(S179.toFixed(0)); // 1 — app program skips lib innards (default) while lib program checks its own sources (separately scheduled)
// bad — one program checking everything including codegen output (monolith checking: slow, noisy, unscoped)
// fix — project references (generated packages on their own schedule — see 3.2 promise 2; apps default-skipping)
```

**Common confusion** — "`skipLibCheck` hides real errors" — hides *library-internal* errors (generated innards — near-zero yield); consumer *uses* always check (assignability against declarations — full yield). "disabling speeds CI safely" — speeds CI by skipping verification *with* yield (own sources unexamined — different boundary entirely). "generated code needs no checks" — generated *sources* check on their own schedule (codegen package CI); generated *output* (`.d.ts`) trusts with regenerate-diff verification (per 12/3.1 — verification at generation, not consumption).

**Performance note** — skipping lib internals saves the dominant CI check-time term on codegen-heavy repos (50k-line declarations with deep conditionals — minutes → seconds); per-path scoping via references keeps owned-code verification complete. Measure with `--extendedDiagnostics` (trace the `checkTime` leader before scoping).

**Mentor note** — time CI with the flag both ways on a codegen-heavy repo (minutes vs seconds — the measurement that ends "but thoroughness" debates with data). Exercise: scope one generated package to its own program (references + schedule) and watch app CI drop — scoping demonstrated, not asserted. Gate: global `skipLibCheck: false` fails review (scope per path or keep the default).
