## 5.1. Configuration failure modes reproduced locally

A compiler diagnostic, a failed module load and an incorrect runtime value ask
different questions. These are reproducible local cases, not reports of particular
production incidents. Use TypeScript 7.0.2 and Node 20.20.2. Select the failing
operation before changing a flag or inventing a dependency's type.

### 1) **Use the observed boundary to choose a reproduction**

The preceding owners already supply complete projects for several failures. Use
the specific case rather than a source fragment described as equivalent to a
package or deployment:

| Observation | Actual worked reproduction | What the evidence establishes |
|---|---|---|
| A missing entity compiles under weaker null checks, then a property read fails | [Strict-family matrix](<../1. Strictness Family/1.1. strict and strictNullChecks the nullability contract.md>) | Null-only and implicit-any-only settings report different diagnostics. A non-null assertion still permits a failing run under strict. |
| An import checks and bundles, but direct Node execution fails | [Resolution project](<../3. Modules Emit and Projects/3.1. module and moduleResolution pairing.md>) | Extensionless bundler resolution does not supply an emitted Node file target. Its custom-condition case also passes checking while native Node selects a different branch. |
| Plugin registration is absent | [Module failure project](<../../../12 Modules Namespaces and Declaration Files/sections/5. Common pitfalls to production bugs/5.1. Real production bugs caused by module misunderstandings.md>) | The tested tsc and esbuild paths both elide the type-only import. An explicit setup edge restores registration. |
| An accepted class-type import starts evaluating a module after a flag change | [Verbatim configuration project](<../2. Erasable and Isolated Toolchain/2.2. verbatimModuleSyntax predictable emit.md>) | A valid value-bearing import can remain under verbatim even when used only for an annotation. |

Strict does not validate assertions or foreign implementations. Compatible module
settings do not prove that conditions and deployed files agree. A trace reports
checker resolution, not the native loader's execution. These distinctions make
the reproductions useful; a blanket “enable flags and incidents disappear” would
misdescribe what they test.

### 2) **Expose a declaration error hidden by skipLibCheck**

SkipLibCheck skips checking declaration-file internals. It can reduce checking
work or permit a temporary dependency migration, but its [official reference](https://www.typescriptlang.org/tsconfig/skipLibCheck.html)
explicitly describes an accuracy trade-off. It is not proof that generated or
third-party declarations are correct, and it does not mean every consumer use
remains equally informative when a declaration contains an error.

Create these files in a fresh directory without a tsconfig. The JavaScript is a
real local provider. Its companion declaration deliberately imports a type from
a nonexistent module.

```typescript
// file: bad-types.d.mts
import type { Missing } from "./absent.mjs";
export declare function load(): Missing;
export declare function echo(value: string): string;
// file: consumer.mts
import { load, echo } from "./bad-types.mjs";
console.log(echo("ok"));
const value = load();
console.log(value.notAMethod());
```

```javascript
// file: bad-types.mjs
export function load() { return 7; }
export function echo(value) { return value; }
```

```sh
# Expected TS2307 in the declaration, including under this compiler's default:
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --noEmit consumer.mts
tsc --strict --skipLibCheck false --target es2022 --module nodenext --moduleResolution nodenext --noEmit consumer.mts
# Accepted check, followed by intentional runtime TypeError:
tsc --strict --skipLibCheck --target es2022 --module nodenext --moduleResolution nodenext --outDir dist consumer.mts
cp bad-types.mjs dist/bad-types.mjs
node dist/consumer.mjs
```

The default and explicit false checks report the missing type module. With
skipLibCheck true, this checker accepts the consumer's notAMethod call because
the unresolved imported type supplies no usable constraint here. Execution prints
ok and then throws TypeError: load returned a number. The copy command supplies
the actual runtime file; declaration emit or checking would not install it.

This is a declaration-accuracy failure with a concrete downstream consequence.
It is not a claim that every skipped declaration becomes any or that the option
skips all source checking. To expose this particular flow directly, add
`type IsAny<T> = 0 extends (1 & T) ? true : false; const leaked: IsAny<typeof value>
= true;`: the skipped-declaration consumer accepts that probe.

### 3) **Verify what still checks, then repair the actual declaration**

With skipLibCheck still enabled, change echo's argument to 7. The consumer reports
TS2345 because that signature is known. Adding a source assignment such as
`const invalid: string = 7` still reports TS2322. A missing module imported by
consumer source also remains an error. Skipping library checks therefore does
not disable the compiler gate, but neither does it make every unresolved library
contract safe for downstream use.

Repair the declaration to match the actual provider:

```typescript
// file: repaired.d.mts
export declare function load(): number;
export declare function echo(value: string): string;
```

With the original consumer unchanged, either skipLibCheck setting now reports
TS2339 on notAMethod. Replace that call with `value.toFixed(0)`, build and run:

```sh
cp repaired.d.mts bad-types.d.mts
# Before the consumer fix, expected TS2339:
tsc --strict --skipLibCheck --target es2022 --module nodenext --moduleResolution nodenext --noEmit consumer.mts
# After replacing value.notAMethod() with value.toFixed(0):
tsc --strict --skipLibCheck false --target es2022 --module nodenext --moduleResolution nodenext --noEmitOnError --outDir repaired-dist consumer.mts
cp bad-types.mjs repaired-dist/bad-types.mjs
node repaired-dist/consumer.mjs
```

The final output is ok and 7. This fixes the declaration and consumer agreement;
changing the flag alone did not change the implementation. A dependency with
conflicting or missing declarations may instead need a version or dependency-tree
repair. If an override is temporary, record the actual failing contract and the
check required to remove it. Choose its scope at a compiler-program boundary;
skipLibCheck is not a per-directory source-check exemption.

Generated declarations can also reflect an incorrect assertion in source. The
[authoring project](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.1. Authoring d.ts public API surface.md>)
generates a number signature from a function that actually returns a string,
then checks and runs a consumer. Generation is valuable evidence of the compiler's
view; it is not independent runtime validation. Declaration-file checking and
provider tests answer different questions.

### 4) **Common confusion**

Skipped declaration errors can reduce information available to a consumer even
though known signatures and source checks remain active. Inspect the effective
API and the diagnostic being hidden, not merely the directory containing it.
The unresolved return and checked echo argument demonstrate both sides.

A faster or green invocation also does not prove that new artifacts were emitted.
The [composite build project](<../3. Modules Emit and Projects/3.2. declaration composite project references.md>)
shows old output surviving a failed consumer build and an obsolete file surviving
force. Start the intended artifact and verify its source/configuration state
before treating an old successful run as evidence for the latest change.

### 5) **Performance note**

The option skips declaration checking work, which can help some projects.
This fixture measures no duration, memory reduction or incident rate. Declaration
size alone does not establish a dominant compiler cost or justify a universal
true/false policy. Compare the actual program with matching cache/build states
and record both diagnostics and runtime/consumer checks. Use [compiler measurement](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>)
when performance is the reason for changing the setting.

### 6) **Mentor note**

Ask why the original consumer accepts notAMethod with skipped checks but rejects
echo(7). Then repair the declaration before changing the consumer and explain
the new TS2339. A sound answer follows which type information was absent and
which remained available.

For the routing table, require the actual failing entry point and one observation
that distinguishes its category. A type assertion cannot supply a runtime file,
a module pairing cannot validate a provider, and a declaration checker cannot
prove an asserted implementation is honest. Use the evidence that addresses the
specific failed operation.
