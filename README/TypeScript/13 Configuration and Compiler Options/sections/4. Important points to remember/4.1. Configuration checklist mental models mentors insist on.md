## 4.1. Configuration checklist — mental models mentors insist on

A configuration review should connect selected options with the source program,
emitted artifacts and executed behavior. Use this checkpoint to evaluate a small
change, rather than memorize a universal adoption order or a fixed number of
release gates. The detailed flag mechanics remain in the preceding owners.

Use TypeScript 7.0.2 and Node 20.20.2. Create this project in a fresh directory.
It intentionally begins with two runtime failures accepted by its baseline
checking configuration.

### 1) **State the checked program and the deployment path**

Save these JSON files and sources. Remove `// file:` labels when saving JSON.
The baseline uses strict and the three bounded syntax/import checks. The second
config adds indexed-access and optional-property checks to the same source roots.
Both run emitted ESM; extension rewriting supplies the retained .mjs paths.

```json
// file: tsconfig.json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "types": [],
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "erasableSyntaxOnly": true,
    "rewriteRelativeImportExtensions": true,
    "declaration": true,
    "noEmitOnError": true,
    "rootDir": "src",
    "outDir": "baseline"
  },
  "include": ["src/**/*.mts"]
}
// file: tsconfig.precise.json
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "outDir": "precise"
  }
}
```

```typescript
// file: src/catalog.mts
export interface Product { title: string }
const catalog: Record<string, Product> = { p1: { title: "Book" } };
export function lookup(id: string) { return catalog[id]; }
export interface Patch { title?: string }
export function apply(product: Product, patch: Patch): Product {
  return { ...product, ...patch };
}
// file: src/read.mts
import { lookup } from "./catalog.mts";
console.log(lookup("missing").title);
// file: src/update.mts
import { apply } from "./catalog.mts";
console.log(apply({ title: "Book" }, { title: undefined }).title.toUpperCase());
```

```sh
tsc -p tsconfig.precise.json --showConfig
tsc -p tsconfig.json
# Each intentional runtime failure is a separate process:
node baseline/read.mjs
node baseline/update.mjs
# Expected TS2532 and TS2379:
tsc -p tsconfig.precise.json --noEmit
```

The baseline build succeeds and both runtime entries throw TypeError. The more
precise check reports the possibly missing lookup result and explicitly undefined
optional argument. Strict plus the syntax checks did not cover either obligation.
The [strict-family](<../1. Strictness Family/1.1. strict and strictNullChecks the nullability contract.md>)
and [indexed/optional-property](<../3. Modules Emit and Projects/3.3. noUncheckedIndexedAccess and exactOptionalPropertyTypes.md>)
lessons explain why these are separate choices. ShowConfig confirms the inherited
settings; runtime execution supplies the separate behavioral evidence.

### 2) **Choose behavior before changing annotations or assertions**

For this application, a missing product should display missing. An omitted patch
should keep the product's title; undefined is not an accepted clear instruction.
Change the two entries accordingly:

```typescript
// file: repaired/read.mts
import { lookup } from "./catalog.mts";
console.log(lookup("missing")?.title ?? "missing");
// file: repaired/update.mts
import { apply } from "./catalog.mts";
console.log(apply({ title: "Book" }, {}).title.toUpperCase());
```

```sh
cp repaired/read.mts src/read.mts
cp repaired/update.mts src/update.mts
tsc -p tsconfig.precise.json
node precise/read.mjs
node precise/update.mjs
```

The results are missing and BOOK. Replacing the guarded read with a non-null
assertion would also satisfy the checker but would not implement the chosen
missing-product policy. Adding undefined to Patch could instead be correct if
clearing were intentional, but then apply must implement that different contract.
Do not select a fallback or widening merely to reduce the error count.

Inspect baseline/catalog.d.mts and precise/catalog.d.mts. Lookup's inferred
return changes from Product to Product or undefined. Its source body stayed the
same; the configuration changed what the checker inferred about the open read.
A migration can therefore affect consumers through declarations. An explicit
return annotation can state an intended API, but it still needs an implementation
that satisfies the checks and real boundary behavior.

Try a separate restriction experiment: add a runtime enum to an included .mts
file. The erasable gate reports TS1294 even after the precision repairs pass.
That diagnosis asks about processing syntax, not product absence. Removing the
gate may be an intentional transformation-based support choice, but neither an
enum replacement nor a directory TODO proves compatibility automatically. The
[bounded syntax lesson](<../2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>)
owns the complete inventory and actual source/emitted graph tests.

### 3) **Review the boundaries this checkpoint does not certify**

For this application, the runtime starts emitted files. [Module/resolution
selection](<../3. Modules Emit and Projects/3.1. module and moduleResolution pairing.md>)
shows why a supported pair can still need aligned conditions and deployed paths.
For a source runner, test the real source entry and parser instead of assuming
the same three flags certify it.

For a library, test its built declarations and actual package exports. This
checkpoint emits declarations but does not pack a library or test an installed
package. The [declaration/project project](<../3. Modules Emit and Projects/3.2. declaration composite project references.md>)
builds two programs and inspects declaration inputs, map paths and rebuild states.
The [packed-consumer project](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>)
then covers a real tarball, dual formats and compiler-version selection.

For untrusted JSON or a foreign implementation, these flags do not validate the
values. Use a runtime parser or checked provider contract where the application
needs one. Likewise, references order builds rather than establish a universal
import allow-list. Config settings, code comments, package metadata and runtime
providers are different pieces of a review.

A small project can enable related checks in one reviewed change; a larger one
may need staged units. Choose the sequence from actual errors, flag dependencies,
consumer changes and manageable review scope. Options apply to compiler programs,
so verify included/imported files and overrides. There is no mandatory alphabetical
or pedagogical ordering of keys in a JSON configuration, and no fixed migration
calendar follows from the language.

### 4) **Common confusion**

A green syntax/import gate is not proof of correct application behavior. The
baseline above is already syntax-compatible with its selected transformation,
yet both entries fail. Additional flags expose particular assumptions; they do
not select the business rule that fixes them.

A declaration diff is also meaningful evidence even when runtime source is
unchanged. Check which consumer artifact changed and why. Keep a failed checker
exit separate from output left by an earlier build; noEmitOnError prevents new
emit on error but does not remove all old files.

### 5) **Performance note**

This checkpoint contains no timing or bundle benchmark. Syntax-restricted code
is not automatically fastest to start or smallest to bundle. Optional chains,
spreads, imports and provider code have costs determined by the actual program
and toolchain. Compiler options and declaration generation perform different
work, so compare matching build states when investigating speed.

Error counts can track reviewed work, but they do not establish incident rates,
review duration or runtime safety. Measure the relevant workload rather than
assigning fixed costs or savings to the number of flags enabled.

### 6) **Mentor note**

Ask the learner to predict why the strict baseline accepts both failures and what
each added diagnostic reveals. Then require a stated missing/clearing policy
before accepting the repair. A sound answer identifies the changed source,
configuration, emitted declaration and runtime observation.

Finally ask which check would be needed for an installed library or a native
source runner. The learner should name the actual missing boundary and route to
its worked owner, rather than add another flag and claim universal compatibility.
