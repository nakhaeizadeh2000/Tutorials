## 4.1. Configuration checklist — mental models mentors insist on

### 1) **Strict trio first, everything else after** (foundation all other flags assume)

**Definition** — enable `strict` + `isolatedModules` + `verbatimModuleSyntax` first (the foundation trio: proving, transpilable, predictable) — every other flag in this domain assumes them (erasable syntax needs stating discipline; indexed honesty needs nullability; declaration emit needs module pairing). Foundation first, specializations after, migrations sequenced per flag — the order that compounds instead of conflicts.

**What problem it solves / history** — flag adoption in random order (erasable syntax before verbatim imports — TS1294 migrations fighting guessing imports; indexed honesty before strict — `| undefined` without nullability narrowing vocabulary) multiplied confusion (each flag's errors blamed on the wrong cause). Foundation-first sequencing means each flag's errors arrive with their prerequisites already installed (narrowing known before honesty demanded, stating known before verbatim enforced).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), order every adoption: `strict` (proving) → `isolatedModules` (transpilable) → `verbatimModuleSyntax` (predictable) → specializations (`erasableSyntaxOnly`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, declaration/composite). See promises 2–4 for the erasable, emission, and migration thirds of the checklist.

**Runnable example** — foundation ordered (multi-file sets):

```typescript
// file: found158.ts
export interface Found158 { host: string } // strict-first code (nullability + no-implicit-any assumed throughout)
// file: app158.ts
import { type Found158 } from "./found158.js"; // verbatim-second (stated traffic — isolatedModules-honest too)
const f: Found158 = { host: "h" };
console.log(f.host.toUpperCase()); // H — foundation ordered (proving → transpilable → predictable, each assumed by the next)
// bad — erasableSyntaxOnly before verbatimModuleSyntax (TS1294 migrations fighting guessing imports — sequence violated)
// fix — strict → isolated → verbatim → specializations (each flag's prerequisites installed before its errors arrive)
```

```typescript
// file: seq159.ts
export function step(ok: boolean): string | null { return ok ? "yes" : null; } // strict-shaped (nullable honest)
// file: app159.ts
import { step } from "./seq159.js";
console.log(step(true) ?? "no", step(false) ?? "no"); // yes no — narrowing vocabulary (strict) ready BEFORE indexed honesty arrives
// bad — noUncheckedIndexedAccess before strictNullChecks (honest-undefined without narrowing vocabulary — errors unfixable by an unready team)
// fix — sequence: proving first (strict), precision after (specializations assume the vocabulary)
```

```typescript
// file: base160.jsonc (adoption order, documented as config — not compiled)
// 1. "strict": true (proving — nullability/any/variance/init vocabulary)
// 2. "isolatedModules": true (transpilable — per-file reality matched)
// 3. "verbatimModuleSyntax": true (predictable — stating enforced)
// 4. specializations: erasableSyntaxOnly, noUncheckedIndexedAccess, exactOptionalPropertyTypes, noImplicitOverride, declaration/composite
// file: app160.ts
console.log("sequence-documented"); // order stated once (base tsconfig comments carry the sequence rationale)
// bad — alphabetical flag ordering (no sequence signal — adopters guess, prerequisites arrive late, errors confuse)
```

**Common confusion** — "order is cosmetic" — each flag's *errors* assume prior flags' *vocabulary* (honesty errors need narrowing; stating errors need universe-matching; migration errors need both) — sequence determines whether errors teach or confuse. "new projects skip sequencing" — new projects enable *all* at once (sequence satisfied trivially — nothing to migrate). "foundation flags suffice alone" — foundation enables specializations (doesn't replace them — indexed honesty, erasability, and override tracking need their own flags regardless).

**Performance note** — sequenced adoption costs the same total triage (error counts sum identically) distributed reviewably (per-flag PRs green each); random order costs the same triage *plus* confusion overhead (misattributed errors, reverted PRs). Sequence is free correctness.

**Mentor note** — order one legacy adoption live (strict → isolated → verbatim → picks) narrating *why* each precedes the next (vocabulary before honesty before predictability) — sequencing rationale transfers in one migration. Rule: flag PRs state their sequence position ("step 2 of 4: verbatim after isolated") or fail review as unordered.

### 2) **Erasable by default, recorded where not** (trio-clean code, dated exemptions)

**Definition** — new code ships trio-clean (`isolatedModules` + `verbatimModuleSyntax` + `erasableSyntaxOnly` compliant — no enums/namespaces, stated traffic, transpilable patterns); legacy exemptions carry dates + reasons (per-directory TODOs with revisit quarters); survivors (ambient-foreign, generated, deliberate non-erasable) document like 11's enum stamp (reason + date, re-audited on condition change).

**What problem it solves / history** — unenforced erasability decayed (trio-clean directories re-accumulated guessing imports and enum additions — each unreviewed addition a toolchain lock reintroduced silently). Recorded exemptions + lint locks hold the line: new violations fail at authorship (lint), legacy exemptions expire by date (revisit), survivors justify continuously (re-audit).

**Modern guidance** — as of TypeScript 5.9 era, trio-clean by default (base tsconfig carries all three — inheritance does the enforcing); exempt per directory with TODO + date (never globally, never undated); stamp survivors (reason + date, same playbook as 11/2.3). Track the three error counters weekly (TS1205 + TS1484 + TS1294 → zero, locked).

**Runnable example** — default clean, exemptions recorded (multi-file sets):

```typescript
// file: clean161.ts
export interface Clean161 { a: string } // trio-clean (no enums, no namespaces, nothing to state beyond honest imports)
export function use(c: Clean161): string { return c.a.toUpperCase(); }
// file: app161.ts
import { use, type Clean161 } from "./clean161.js";
console.log(use({ a: "x" })); // X — default state (clean without trying, locked without watching)
// bad — new enum in trio-clean directory (TS1294 fails at authorship — the default defending itself)
// fix — union + const object (default serves; enum needs a recorded survivor reason per the stamp)
```

```typescript
// file: legacy162.ts
export interface Old162 { o: string } // TODO(trio, 2026-Q4): verbatim triage pending (dated exemption, one directory)
// file: app162.ts
import { type Old162 } from "./legacy162.js";
const o: Old162 = { o: "y" };
console.log(o.o); // y — exempted directory (progress tracked, not hidden — TODO dated, revisit scheduled)
// bad — undated exemptions ("legacy, skip" — permanent by neglect; no revisit, no progress, no accountability)
// fix — TODO(trio, <quarter>): exemptions expire (revisit scheduled or don't exempt at all)
```

```typescript
// file: surv163.ts
export function svc(): string { return "s"; } // survivor-adjacent code (trio-clean itself; exemption lives elsewhere)
// file: app163.ts
import { svc } from "./surv163.js";
console.log(svc().toUpperCase()); // S — clean code needs no stamp (stamps mark EXEMPTIONS, not compliance)
// bad — stamping compliant code (noise burying real exemptions — stamp the exceptions, trust the default)
// fix — record where not-clean (dated TODOs + survivor reasons); leave clean code uncommented
```

**Common confusion** — "recorded exemptions are bureaucracy" — one TODO line per directory (seconds) vs toolchain migration quarters (months) — exemptions with dates compound; without dates they rot. "lint locks slow development" — locks fail *violations* in seconds (fast feedback); unlocked decay fails *migrations* in quarters (slow catastrophe). "survivors need re-justification constantly" — re-audit on *condition change* (pipeline switches, erasability adoption — events, not calendars).

**Performance note** — trio-clean code starts fastest under stripping runtimes and bundles smallest (per 2.3 promise 2's economics); exemption tracking costs one TODO per directory (negligible); unrecorded decay costs toolchain migrations (unbounded).

**Mentor note** — `grep -r TODO.trio | wc -l` quarterly (falling = adoption compounding; rising = new exemptions needing scrutiny). Exercise: convert one dated exemption before its quarter (early wins compound team confidence). Culture pattern: same as 11's enum stamp (measured behavior, celebrated deletions).

### 3) **Pair module settings, generate declarations, map exports** (resolution, signatures, surfaces)

**Definition** — emission third of the checklist: `module`/`moduleResolution` paired per runtime (checker simulates deploy target — see 3.1); declarations generated + mapped (consumers check signatures via `exports.types` — see 12/3.1 + 12/3.3); project references ordered for monorepos (incremental builds, layered imports — see 3.2). Three wirings, each verified (traceResolution diff, regenerate-diff, subpath smoke).

**What problem it solves / history** — emission misconfiguration (unpaired resolution, stale declarations, unmapped subpaths) broke *consumers* while producers stayed green (check-passing libraries shipping unresolvable/untyped/wrong-runtime packages — the boundary incidents of 5.1 promise 2/4 and 12/5.1 promise 4). Checklist wiring makes producer CI prove consumer outcomes (resolution traces, declaration diffs, subpath smokes — consumer-equivalent verification pre-publish).

**Modern guidance** — as of TypeScript 5.9 era, pair per runtime (documented beside the deploy target); generate + verify declarations (regenerate-diff in CI); map every public subpath (smoke per subpath per release); reference-order monorepos (references mirroring dependencies). See [3.1. module pairing](<../3. Modules Emit and Projects/3.1. module and moduleResolution pairing.md>) + [3.2. declaration composite](<../3. Modules Emit and Projects/3.2. declaration composite project references.md>) + [3.3. Publishing types](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>) (in 12).

**Runnable example** — wired emission end to end (multi-file sets):

```typescript
// file: paired164.ts
export function calc164(n: number): number { return n * 2; } // paired resolution (explicit .js imports below verify)
// file: app164.ts
import { calc164 } from "./paired164.js"; // explicit extension (nodenext agreement — checker + Node identical)
console.log(calc164(21).toFixed(0)); // 42 — paired settings (resolution traces match runtime behavior)
// bad — extensionless imports under nodenext (checker guesses, Node refuses — deploy-boundary divergence)
// fix — explicit .js (one spelling, both worlds agree — verified via traceResolution per project setup)
```

```typescript
// file: gen165.ts
export interface Gen165 { g: string } // generated declarations (consumers check signatures, skip bodies)
export function use(g: Gen165): string { return g.g.toUpperCase(); }
// file: app165.ts
import { use, type Gen165 } from "./gen165.js";
const v: Gen165 = { g: "z" };
console.log(use(v)); // Z — declaration-mediated checking (fast downstream, enforced surface per 12/3.1)
// bad — hand-synced .d.ts beside evolving source (drift both directions — generation + CI-diff instead)
```

```typescript
// file: surf166.ts
export function alpha166(): string { return "a"; }
export function beta166(): string { return "b"; }
// file: app166.ts
import { alpha166 } from "./surf166.js"; // mapped-subpath equivalent (types travel with the path — no untyped publics)
console.log(alpha166().toUpperCase()); // A — every public path typed (checklist gate: no public path without types)
// bad — unmapped public subpaths (consumer any-infection per untyped path — P0 packaging bugs, see 5.1 promise 4)
// fix — exports map with types per subpath + smoke per release (wiring verified, not hoped)
```

**Common confusion** — "wiring is release-engineering, not config" — wiring *lives in* tsconfig/package.json (configuration by definition) — release gates *verify* it (CI), but the settings are the product. "small packages skip wiring" — small packages grow (wiring scales with zero human steps; hope scales with forgetting) — install at birth. "traceResolution is arcane" — one command per project setup (mapped + relative import traces) —ARCANE once, routine after (document the traces beside the settings).

**Performance note** — paired resolution (deterministic, cached); declaration-mediated checks (bodies skipped — primary monorepo lever); mapped subpaths (one lookup each) — wiring performs optimally by construction; miswiring costs incidents, never speed.

**Mentor note** — traceResolution one mapped + one relative import per project setup (paired output = wiring proof). Exercise: audit one package's wiring end-to-end (pairing + declarations + maps + references) — misses found are consumer incidents pre-triaged. Gate: unwired public paths fail release review.

### 4) **Migrate flags with triage, never flag-days** (sequenced, error-classed, CI-gated)

**Definition** — migration discipline for every flag in this domain: enable per directory (new code compliant from birth), triage error-class by error-class (nullability → implicit-any → variance; kinds → imports → enums; mechanical → judgmental), gate each class in CI before starting the next, track counts weekly (falling = working). Flag-days (all flags + all errors in one PR) stall; triage compounds.

**What problem it solves / history** — flag-day migrations (strict-all-at-once, trio-all-at-once, 800-error PRs) stalled quarterly (unreviewable, conflicting, pressuring suppression/theater) while sequenced migrations merged weekly (reviewable, revertible, compounding). The discipline is uniform across flags (strict per 1.1 promise 3, trio per 2.3 promise 3, honesty/optionality per 3.3 promise 3) — one migration playbook, every flag.

**Modern guidance** — as of TypeScript 5.9 era, migrate in class order per flag family (mechanical classes first, judgmental last); fix with narrowing/annotations/stating (never suppression/`!`/widening — theater, not migration); gate per class in CI (regression-proof steps, not one big-bang gate). Track per-class counts weekly; pair on stalled classes (flat lines need pairing sessions, not pressure).

**Runnable example** — triage ordered, theater banned (multi-file sets):

```typescript
// file: tri167.ts
export interface Tri167 { a?: string } // triaged (narrowed + spelled — one class, green PR)
// file: app167.ts
import type { Tri167 } from "./tri167.js";
function use(t: Tri167): string { return t.a ?? "dflt"; } // narrowing fix (honest undefined handling)
console.log(use({}), use({ a: "x" })); // dflt x — one error class fixed (reviewable, revertible, compounding)
// bad — use(t: Tri167): string { return t.a!; } (assertion migration: errors silenced, crashes preserved — theater)
// fix — narrow/annotate/state (discipline IS the migration — shortcuts are the incident queued)
```

```typescript
// file: seq168.ts
export function step168(ok: boolean): string | null { return ok ? "y" : null; } // strict-shaped (sequenced adoption assumed)
// file: app168.ts
import { step168 } from "./seq168.js";
console.log(step168(true) ?? "n", step168(false) ?? "n"); // y n — nullability class first (biggest yield, mechanical narrowing)
// bad — enabling strict + trio + honesty + optionality in one PR (mixed disciplines, unreviewable volume, rubber-stamped theater)
// fix — sequence (strict → trio → honesty → intent): uniform fix discipline per PR, reviewable throughout
```

```typescript
// file: gate169.ts
export const migrated = ["strict", "trio"] as const; // classes gated (CI green per class before next begins)
console.log(migrated.join("+")); // strict+trio — gated sequence (regression-proof steps, compounding quarterly)
// bad — single big-bang gate (all-or-nothing CI: red for a quarter, then force-merged red — gates as decoration)
// fix — per-class gates (each green before next starts — compounding green, never big-bang red)
```

**Common confusion** — "sequencing slows migration" — sequenced PRs merge weekly (reviewable); flag-days stall quarterly (unreviewable) — sequencing is *faster* wall-clock, not just safer. "theater unblocks migration" — unblocks the *flag* while preserving every *crash* (`!`/suppression/widening keep incidents, delete diagnostics) — unblocking theater ships the incident queue faster. "small teams skip process" — process scales down to one checklist per PR (class named, fixes uniform, gate green) — theater scales down to nothing (small teams feel incidents *more*, not less).

**Performance note** — triage costs authoring minutes per error (one-time); theater costs incidents (unbounded, recurring); gates cost CI seconds per class (parallelizable) — audit economics favor completion heavily at every team size.

**Mentor note** — graph per-class counts weekly (falling lines = migration working; flat = stalled class needing pairing, not pressure). Exercise: fix ten errors from three classes live (narrowing vs stating vs respelling) — three disciplines, one migration playbook. Gate: suppression/`!`/widening fixes in migration PRs fail review unconditionally.
