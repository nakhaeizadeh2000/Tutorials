## 1.1. From JavaScript to TypeScript — history, superset claim, and why it exists

### 1) **JavaScript behavior with a checked contract**

TypeScript builds on JavaScript and adds a static type system and related syntax. A type describes which values and operations a checked program intends to allow. The checker can report a mismatch before execution; it does not execute every possible input or install runtime validation.

The word superset expresses that JavaScript is the foundation. Treat it as a relationship between languages, not a promise that every file parses, checks and runs under every compiler version, file mode or configuration. JavaScript-specific inference rules, module formats and JSX file handling can matter. Renaming a file is not proof of a correct contract. The [actual mixed-source migration](<../../../20 Production Checklist Migration and Interoperability/sections/2. Migration Playbooks/2.1. JavaScript to TypeScript file by file.md>) later tests those boundaries in detail; no migration tooling is needed for the small example here.

Use TypeScript **7.0.2** and Node **20.20.2**, verified 2026-10-17. Create a fresh directory without tsconfig.json, package.json or local dependencies. Save this ordinary JavaScript as `plain.cjs`:

```javascript
function shout(name) { return name.toUpperCase(); }
console.log(shout("Ada"));
```

Run `node plain.cjs`: it prints ADA. The function body assumes that name has a suitable toUpperCase method. JavaScript has not declared or enforced a string-only call contract here.

Now save `example.ts`:

```typescript
function shout(name: string): string { return name.toUpperCase(); }
console.log(shout("Ada"));
```

The parameter annotation promises a string input; the return annotation describes the result. The function body and console call still perform ordinary JavaScript operations. Run checking/emission and execution separately:

```bash
tsc --version
tsc --strict --target es2022 --module commonjs --rootDir . --outDir dist --noEmitOnError example.ts
node dist/example.js
```

All commands exit 0; the last prints ADA. Inspect dist/example.js: the string annotations are absent, while the function and call remain. This example needs no runtime library supplied by TypeScript. The declared target and module format describe this emitted path; they do not establish every deployment runtime's APIs or loader behavior.

Change the TypeScript call to `shout(17)` and run the same compiler command. It fails with TS2345: number is not assignable to string. Restore the string before rebuilding and running again. With noEmitOnError, do not run an old dist file as proof that the erroneous source built successfully. For the runtime contrast, change only the JavaScript call in plain.cjs to `shout(17)` and run Node: it exits 1 with TypeError because the number lacks that method. Restore it afterward. The checker identified this selected mismatch earlier; that result is not a promise that every checked function is correct.

### 2) **Why the project appeared and how to read its history**

Microsoft introduced TypeScript 0.8 in October 2012 and released 1.0 on April 2, 2014. The [original 1.0 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-1-0/) describes support for large JavaScript applications, declaration files, editor tooling and community development. That is a more useful causal history than imagining that JavaScript had no structure or that all earlier refactoring was text replacement.

The [design-goals document](https://github.com/microsoft/TypeScript/wiki/TypeScript-Design-Goals) describes error detection, code structure and recognizable JavaScript output, while explicitly balancing correctness with productivity. These are design intentions, not proof that every program is sound or every transformation is free. The next lesson explains the goals and limitations more fully.

This track's verified compiler baseline is 7.0.2. Historical examples name older versions when reproducing an actual change; those laboratory inputs are not the recommended default. Use the [current learning route](<../../../25 Update TypeScript 7.0/sections/6. Overlaps and Update Route/6.1. Overlaps and the current learning route.md>) for the native compiler update and affected topical owners, rather than memorizing a broad chronology before understanding the language.

An upgrade can change accepted source, library declarations, configuration defaults, output and tool interfaces. It is too broad to say that only checker errors ever change. The [worked version comparison](<../../../20 Production Checklist Migration and Interoperability/sections/2. Migration Playbooks/2.2. TypeScript version upgrades without flag-days.md>) later separates those observations. In this introductory example, we observed only annotation removal and the selected string call.

### 3) **Evaluate adoption by useful contracts and tooling**

Types can make input/output assumptions visible, detect selected mistakes and support navigation or refactoring in tools that understand the actual program. Those benefits depend on meaningful checked contracts, project scope and tool support. A rename result is reviewable evidence about that operation; it is not a guarantee that every runtime string, external consumer or generated use changed correctly.

| Need | Useful contribution | Work still required |
|---|---|---|
| Catch a wrong argument earlier | A checked parameter contract rejects the number above. | Decide the right contract and test relevant behavior. |
| Explain an API | A signature makes expected inputs/results visible. | Keep descriptions honest and handle runtime boundaries. |
| Navigate or refactor code | A language service can relate declarations and selected uses. | Use the actual provider/project and review the edit. |
| Maintain a larger project | Explicit boundaries can support ownership and tooling. | Manage configuration, dependencies, builds and consumer evidence. |

JavaScript with checked JSDoc is also a supported way to gain static information; every useful project need not immediately rename every file. Larger adoption can use staged or project-wide strategies depending on constraints. The later migration playbook discusses the original maintainer experience and follow-up type quality; no universal percentage benefit or conversion throughput is established here.

### 4) **Common confusion**

A type annotation does not turn a number into a string or add toUpperCase to it. The TypeScript version rejects the selected bad call statically; the JavaScript runtime still needs values that support the operations actually executed.

Erasing types does not mean all TypeScript syntax is handled by every stripping runtime or that every compiler emits identical JavaScript. Some constructs require transformation. Keep the full explanation in [type erasure](<../2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>) and [execution paths](<../3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>). A successful check is useful evidence, not runtime validation or complete correctness.

### 5) **Performance note**

The annotations in this example add no runtime validation operation. The remaining function and string method still execute normally. Adoption adds checking, tooling and configuration work, but this lesson measures no bottleneck, file-count threshold or speed benefit. Language-service work, checking and emission can have different costs; investigate the actual workload through the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) instead of assuming checking always dominates or declaration flags automatically parallelize a build.

### 6) **Mentor note**

Ask the learner to point to the assumption in plain.cjs, then show where the TypeScript version states it. Have them predict the bad argument's compiler result and the JavaScript runtime result before running both. A sound answer distinguishes a static contract from the method call that the engine performs.

When explaining adoption, ask for one useful checked boundary and one remaining runtime uncertainty. Avoid beginning with a release-number quiz or a guarantee that types fix all refactoring. The important first skill is explaining what was checked, what executed and what evidence is still missing.
