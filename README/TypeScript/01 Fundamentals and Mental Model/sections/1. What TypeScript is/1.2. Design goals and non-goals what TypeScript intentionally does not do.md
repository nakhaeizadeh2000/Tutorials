## 1.2. Design goals and non-goals — what TypeScript intentionally does not do

### 1) **Read the goals as design intentions**

TypeScript aims to identify likely mistakes statically, help structure programs and support tools while producing recognizable JavaScript. Its [design-goals document](https://github.com/microsoft/TypeScript/wiki/TypeScript-Design-Goals) also explains a deliberate balance between correctness and productivity. These principles explain choices; they are not a proof that every accepted program is safe or that every compiler transformation is identical to deleting text.

Separate three operations. The checker analyzes selected source and declared contracts. An emitter or source runner prepares executable code according to its supported syntax/options. The runtime executes that code and supplies its host APIs. A successful result from one operation does not perform the others. The [introduction](<./1.1. From JavaScript to TypeScript history superset claim and why it exists.md>) demonstrated one removed string annotation and a selected wrong argument; the detailed owners later examine broader syntax, configuration and loading.

Tooling can use static information for navigation, diagnostics and edits, but a type graph does not include every dynamic string or external caller automatically. Inspect actual tool results and project scope. Static contracts are useful precisely when they state meaningful assumptions; they do not replace the implementation or observations needed to establish those assumptions.

### 2) **Understand the non-goals at a concrete boundary**

TypeScript does not promise complete soundness, install a runtime type system, supply arbitrary platform libraries or aggressively optimize an application into faster code. A type describing a value is different from a runtime test of that value. Also distinguish ordinary erased types from constructs that require generated JavaScript; “the output is character-for-character source minus annotations” is too broad.

Use TypeScript **7.0.2** and Node **20.20.2**, verified 2026-10-17. Start in a fresh directory without a config, package metadata or dependencies. Save `claim.ts`:

```typescript
export {};
const value = JSON.parse('{"text":17}') as { text: string };
console.log(value.text.toUpperCase());
```

The object type describes a text property that should be a string. The `as` expression tells the checker to use that description; it does not test or convert the parsed value. Run independently:

```bash
tsc --strict --target es2022 --module commonjs --rootDir . --outDir dist --noEmitOnError claim.ts
node dist/claim.js
```

Checking/emission exits 0, then execution intentionally exits 1 with TypeError: the actual parsed text is a number. JSON.parse checks JSON syntax while producing a value; its standard TypeScript return declaration is any, not automatically unknown. The assertion supplied the string claim, and no validation operation appeared in JavaScript. This is a deliberately false boundary contract, not evidence that all compiler diagnostics are useless.

Save `checked.ts`:

```typescript
export {};
function upperFromJson(raw: string): string {
  const value: unknown = JSON.parse(raw);
  if (typeof value === "object" && value !== null &&
      "text" in value && typeof value.text === "string") {
    return value.text.toUpperCase();
  }
  throw new TypeError("string text required");
}
console.log(upperFromJson('{"text":"hello"}'));
try {
  upperFromJson('{"text":17}');
  throw new Error("invalid text accepted");
} catch (error) {
  if (!(error instanceof TypeError)) throw error;
  console.log("numeric text rejected");
}
```

Here unknown is a deliberate annotation that prevents assuming a shape before checking it. The runtime branch establishes this example's used text field before the method call. Build and run:

```bash
tsc --strict --target es2022 --module commonjs --rootDir . --outDir dist --noEmitOnError checked.ts
node dist/checked.js
```

Both exit 0; output is HELLO followed by `numeric text rejected`. The checks are ordinary JavaScript operations supplied by the author. Their presence, rather than the unknown annotation, implements the runtime decision. This small example accepts the needed field from parsed JSON; it is not a full schema for arbitrary hostile objects, business rules or every property. The [static/runtime owner](<../2. How TypeScript doesnt execute/2.2. Static checking vs runtime reality trust but verify.md>) develops complete malformed-input examples and their limits.

### 3) **Choose implementation and toolchain policy deliberately**

Prefer syntax supported by the execution path you intend to use. A stripping path can require erasable constructs; a compiler transform can support constructs that stripping alone cannot execute. A supported enum or runtime namespace is not automatically a misuse merely because another pipeline disallows it. The [erasable-syntax owner](<../3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>) and [bounded syntax gates](<../../../13 Configuration and Compiler Options/sections/2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>) own the inventories and actual restrictions.

A compiler can check without emission, and another tool can emit or bundle. That separation can fit an application, but the other tool still needs its supported configuration, module graph and meaningful execution checks. noEmit is not a bundler, and a faster emitter does not replace a checker. Declaration generation likewise has its own inputs and output contract; erasable syntax does not automatically implement parallel declaration emission.

Strict checking is a useful starting policy for new checked code. Existing code may need a deliberate migration plan with explicit exceptions, and strict does not include every independent check or eliminate all escapes. Keep the effective command and selected inputs visible. The [configuration domain](<../../../13 Configuration and Compiler Options/README.md>) owns those choices, while the [migration playbook](<../../../20 Production Checklist Migration and Interoperability/sections/2. Migration Playbooks/2.1. JavaScript to TypeScript file by file.md>) compares actual JavaScript/JSDoc/TypeScript stages. Do not treat one workflow as a language-level guarantee.

### 4) **Common confusion**

“No runtime type information” does not mean that JavaScript values lack runtime behavior. typeof, instanceof and property operations examine actual values or prototypes. An erased object type cannot be supplied as a runtime constructor, but a real class can have both a type meaning and an executable constructor.

A checked program can still fail through false assertions, any, external values, mutation or ordinary logic errors. It is also possible to encounter a compiler defect. Diagnose a reproducible case before deciding which explanation applies; intentional limitations are not a reason to dismiss every reported bug. Conversely, the selected false assertion above does not show that the checker promised validation it never performed.

### 5) **Performance note**

The annotations/assertion in claim.ts add no runtime validation; checked.ts deliberately adds field tests and a branch. Their cost depends on the actual operation and data. TypeScript does not promise to speed up the remaining JavaScript. This lesson measures no runtime or build performance, fixed validation overhead or percentage improvement from a flag. Compare actual supported pipelines and preserved contracts before attributing a speed change to syntax restrictions.

### 6) **Mentor note**

Ask the learner to identify the source of the string claim in claim.ts and the actual value parsed. Then have them point to the executable branch in checked.ts that changes the outcome. A sound explanation separates annotation, assertion, parsing syntax and runtime field validation.

For a toolchain decision, ask which component checks, which emits and which executes. Require a concrete supported path before accepting “erasable means everything works.” For a reported accepted-but-failing program, ask what assumption failed and what evidence would distinguish an intentional limitation from a compiler bug.
