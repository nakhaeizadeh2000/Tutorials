## 1.2. Design goals and non-goals — what TypeScript intentionally does not do

### 1) **Goals** (add static types to JavaScript, preserve JS runtime behavior, remain erasable, support tooling)

**Definition** — The TypeScript design goals (stated in the handbook's "Design Goals" page) are deliberately conservative. TypeScript aims to *add a static type system on top of JavaScript*, not to reinvent the runtime.

- **Statically type JavaScript** — catch errors at compile time that would otherwise surface in production.
- **Align with JavaScript evolution** — track ECMAScript proposals and emit idiomatic JavaScript, not a custom VM.
- **Preserve runtime behavior** — emitted JavaScript should behave identically to handwritten JavaScript for the same input (no hidden runtime).
- **Support large-scale tooling** — provide the type graph that powers rename, navigation, and refactoring.

Junior-friendly frame: TypeScript is a *checker*, not a *compiler that optimizes*. It tells you when your program is inconsistent; it doesn't make your program faster.

### 2) **Non-goals** (no runtime type system, no performance optimization, no breaking JS, no new runtime primitives)

| Non-goal | What it means | Why it matters |
|---|---|---|
| **No runtime types** | Types are erased; there is no `instanceof TypeScriptType` at runtime | You must still validate external data (see [2.2. Static vs runtime](<../2. How TypeScript doesnt execute/2.2. Static checking vs runtime reality trust but verify.md>)) |
| **No emit-time optimization** | `tsc` does not minify or optimize emitted JS beyond downleveling | Use `esbuild`/`swc` or `tsc` + minifier for production bundles |
| **No breaking JS semantics** | `===`, coercion, prototype chain all behave exactly as in JavaScript | A `.ts` bug is a `.js` bug — TypeScript won't "fix" JS quirks (see [JavaScript 03 Values](<../../../JavaScript/03%20Values%20Types%20and%20Coercion/README.md>)) |
| **No new runtime features** | TypeScript doesn't add new primitives like `int` that exist at runtime | `enum` is the historic exception; modern guidance avoids it precisely because it violates this goal |

Modern guidance — if you expect TypeScript to *change* what the JavaScript does, you are modeling it incorrectly. It changes what the *editor and checker* say before the JavaScript runs.

### 3) **Modern guidance** — design consequences for daily code

- **Prefer erasable syntax** — `interface`, `type`, `as`, `satisfies`, annotations are goals-aligned; `enum` and `namespace` IIFE emit are legacy that violates the erasable ideal (see [3.3. Choosing erasable syntax](<../3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>)).
- **Let `tsc` be the checker, not the bundler** — many teams run `tsc --noEmit` for checking and delegate emit to Vite/esbuild (faster, single-pass).
- **Strictness is opt-in but should be default** — `strict: true` (which enables `strictNullChecks`, `noImplicitAny`, etc.) aligns with the goal of catching real bugs; non-strict is migration mode.

### 4) **Runnable example** — goal-aligned vs goal-violating code (good + bad)

```typescript
// good — goals-aligned: types describe values, runtime is plain JS
// file: good.ts
type UserId = string & { readonly __brand: unique symbol }; // nominal branding via intersection — erasable
function createUserId(raw: string): UserId { return raw as UserId; }

function getUser(id: UserId): { id: UserId; name: string } {
  // implementation uses plain JS values — type disappears after emit
  return { id, name: "Ada" };
}
// emit (npx tsc good.ts --target es2022): function createUserId(raw) { return raw; } — no overhead

// bad — expecting types to affect runtime
// file: bad.ts
function isUserId(value: string): boolean {
  // ❌ there is no runtime check that value is a UserId — the type is gone
  // This always returns true for any string, because the type system isn't there at runtime
  return true; // placeholder — must add runtime validation
}
// fix: validate at the boundary
function isUserIdChecked(value: unknown): value is UserId {
  return typeof value === "string" && value.length > 0; // runtime guard — the type predicate links it to the static side
}
```

### 5) **Common confusion**

- "TypeScript will make my code faster" — no. After erasure, the JS is character-for-character your source minus annotations. Performance wins come from *fewer bugs causing fewer hotfixes*, not from faster bytecode.
- "`tsc` should bundle/minify/tree-shake" — not its job. It emits per-file JS; bundling is delegated to tools that understand the module graph at runtime granularity.
- "If the checker says it's safe, the runtime will be safe" — only for inputs that *honor* their declared types. External data (`fetch` response, `JSON.parse`, `process.env`) is `unknown` until you prove otherwise.

### 6) **Performance note**

Choosing goals-aligned (erasable) syntax is not just aesthetic — it enables `isolatedDeclarations` and native Node stripping to run *without* a transform. Non-erasable constructs force a per-file parse-then-emit step that breaks parallelism. Measure build times before/after enabling `erasableSyntaxOnly`; the delta is often 10–20% on large monorepos.

### 7) **Mentor note**

Ask candidates: "Give an example where TypeScript's checker says the code is safe but it still throws at runtime." Good answers cite `any`, type assertions, array covariance, or missing boundary validation — all consequences of intentional non-goals. If they say "that's a bug in TypeScript", they haven't internalized the goals.
