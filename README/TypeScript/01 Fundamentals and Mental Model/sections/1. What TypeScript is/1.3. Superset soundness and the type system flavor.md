## 1.3. Superset, soundness, and the type system flavor

### 1) **Structural vs nominal** (compatibility by shape, not by name)

**Definition** — A *structural* type system considers two types compatible if their *members* match, regardless of explicit declarations. A *nominal* system requires the same *name* or explicit inheritance. TypeScript is overwhelmingly structural — with a small set of nominal exceptions (e.g., `class` with `private`/`protected` members, branded primitives).

```typescript
// structural: shape is identity
type Point = { x: number; y: number };
const p: Point = { x: 10, y: 20 }; // ok
const q = { x: 10, y: 20, color: "red" }; // extra members are fine (freshness is the caveat — see below)
const r: Point = q; // ok — structural compatibility, not nominal

// nominal-like via class privacy (the rare exception)
class A { private secret = 1; }
class B { private secret = 1; }
declare let a: A; declare let b: B;
// a = b; // error TS2322: Type 'B' is not assignable to type 'A' — different private declarations
```

Freshness/excess-property check — when you write a *fresh* object literal directly against a target type, TypeScript applies an extra check for unknown members. This is not part of the structural core; it's a pragmatic lint for typos.

### 2) **Sound vs useful** (TypeScript is intentionally unsound for ergonomics)

**Soundness** means the checker *never* claims a program is safe when it can fail at runtime. TypeScript *chooses* to be unsound where strict soundness would make everyday JavaScript untypable.

| Intentionally unsound spot | Example | Why tolerated |
|---|---|---|
| **Bivariant function params** (`strictFunctionTypes` only checks *function* values, not method shorthand) | `(x: Animal) => void` accepted where `(x: Dog) => void` expected in method position | Mirrors JS's flexible `Array.prototype.forEach` usage |
| **Array covariance** | `Dog[]` assignable to `Animal[]` (then `animals.push(cat)` unsafely) | Array is the workhorse; invariant arrays would require massive generics |
| **`any` escape hatch** | `any` compatible with everything | Migration and library boundaries need an opt-out |
| **Type assertions `as`** | `x as T` trusts the caller | Boundary validation after `unknown` sometimes requires a final assertion |

Modern guidance — leave `strict: true` enabled (which includes `strictFunctionTypes` for function *values*), and treat method bivariance and `any` as budgeted exceptions, not patterns.

### 3) **Gradual typing** (file-by-file adoption with `any` as pressure relief)

TypeScript is *gradually typed*: you can add types incrementally. A newly renamed `.ts` file with `noImplicitAny: false` will still check with many `any` types; tightening `noImplicitAny` and `strictNullChecks` incrementally ratchets safety without a big-bang rewrite.

The ladder: `allowJs` + `checkJs: false` (JS with JSDoc) → rename to `.ts` → `strict: false` → `strict: true` → `noUncheckedIndexedAccess` / `exactOptionalPropertyTypes`. Each rung catches a new class of bugs.

### 4) **Runnable example** — structural assignment and a soundness surprise (good + bad)

```typescript
// good — leverage structural typing; add branding only where nominal identity is truly required
type HasName = { name: string };
function greet(x: HasName): string { return `hi ${x.name}`; }

// Both satisfy HasName structurally — no inheritance needed
class Dog { constructor(public name: string, public breed: string) {} }
greet(new Dog("Rex", "Shepherd")); // ok — Dog has name: string
greet({ name: "Ada" });            // ok — plain object with name

// bad — tripping over the intentional unsoundness
let animals: HasName[] = [];
let dogs: Dog[] = [new Dog("Rex", "Shepherd")];
animals = dogs; // ok in the type system (Dog[] is covariant to HasName[])
animals.push({ name: "Cat" }); // runtime: dogs array now contains a plain object, not a Dog instance
// At runtime, dogs[1] is { name: "Cat" } — missing .breed. Soundness hole manifests here.
// fix: prefer readonly arrays for covariant positions, or keep collections invariant via generics
const readonlyDogs: readonly Dog[] = dogs; // readonly is safe for covariance
```

### 5) **Common confusion**

- "If two types have the same shape, they're the same type" — almost, but declaration-site identity matters for branded types and for `private` members.
- "Soundness means no runtime errors" — even a fully sound checker couldn't prevent boundary errors (`JSON.parse`, `fetch`) — those inputs are `unknown` until validated. Soundness is about *internal* consistency.
- "`any` means `unknown`" — distinct. `any` disables checking for that value; `unknown` forces checking. Use `unknown` for "I don't know yet", `any` only for "I intentionally escape" (see [03 Basic Types domain — textual forward](../03%20Basic%20Types%20and%20Annotations/README.md)).

### 6) **Performance note**

Structural checking is *proportional to shape depth*. Deeply recursive mapped types (e.g., `DeepPartial<LargeConfig>`) can dominate checker time. Prefer `type` aliases that name intermediate shapes — the language server memoizes named types more effectively than anonymous intersections.

### 7) **Mentor note**

Teach with "assignability is a question, not a declaration": ask "is X assignable to Y?" rather than "is X an instance of Y?". Students who internalize structural assignability stop writing `implements` ceremonially and start designing shapes that compose. Grading probe: can they explain why `class A { private x }` breaks structural compatibility?
