## 1.3. Superset, soundness, and the type system flavor

### 1) **Ask a directional compatibility question**

TypeScript usually compares the structure needed by an operation. If a function requires a name string, a larger object can supply it without inheriting from a named base class. Assignability asks whether a source is acceptable at a particular target. It does not say both types are identical, that assignment works in reverse or that the object has a particular runtime prototype.

Use TypeScript **7.0.2** and Node **20.20.2**, verified 2026-10-17. Save `flavor.ts` in a fresh directory without configuration, package metadata or dependencies:

```typescript
export {};
type Named = { name: string };
type Dog = { name: string; bark(): string };
function greet(value: Named): string { return `hi ${value.name}`; }
const dog: Dog = { name: "Rex", bark() { return "woof"; } };
const named: Named = dog;
console.log(greet(dog), greet({ name: "Ada" }), dog.bark());
const dogs: Dog[] = [dog];
const names: Named[] = dogs;
names.push({ name: "Milo" });
let rejected = false;
try {
  dogs[1].bark();
} catch (error) {
  if (!(error instanceof TypeError)) throw error;
  rejected = true;
}
if (!rejected) throw new Error("expected missing bark operation");
const view: readonly Dog[] = dogs;
if (view.length !== 2 || typeof view[1].bark !== "undefined") throw new Error("unexpected alias state");
console.log("shared mutation broke the Dog contract", rejected);
```

Build and run separately:

```bash
tsc --strict --target es2022 --module commonjs --rootDir . --outDir dist --noEmitOnError flavor.ts
node dist/flavor.js
```

Both exit 0. The first line is `hi Rex hi Ada woof`. The second is `shared mutation broke the Dog contract true`; the program deliberately catches the observed TypeError. The following section explains that failure rather than treating a green checker as complete safety.

For an independent static contrast, append `const notADog: Dog = { name: "Milo" };`. Checking fails TS2741 because bark is required. Restore the source. Then try `greet({ name: "Ada", color: "red" });`: the fresh argument is rejected with TS2353 for an excess property. A separately held larger object can be structurally acceptable. This additional check helps catch unintended properties in particular contexts; it is still a compiler check, not a runtime property filter. The [core assignability and freshness owners](<../../../02 The Type System Core/README.md>) develop these rules fully.

Some compatibility rules also depend on declaration origin, such as private/protected class members. Branding patterns can add distinctions too, with their own structural and escape limits. Those mechanisms come later; “same public shape means identical type” and “a brand is unforgeable” are both too broad.

### 2) **Distinguish type consistency from all runtime correctness**

Soundness concerns the relationship between accepted static claims and execution under a language's assumptions; it is not a promise to prevent every logic error, explicit throw, unavailable API or operational failure. TypeScript deliberately trades some guarantees for compatibility and usability, as its [design non-goals](https://github.com/microsoft/TypeScript/wiki/TypeScript-Design-Goals) explain. A reproducible failure still needs diagnosis: an intentional escape, false declaration, mutable alias and compiler bug are different possibilities.

In the fixture, dogs and names reference the **same array**. The broader Named view can append an object with no bark, while dogs still has the static element type Dog. The later method call exposes that inconsistency. Strict checking alone did not prevent it. Creating a readonly view afterward did not copy, freeze or repair the already corrupted array; the final observation still sees its second item without bark.

An API accepting readonly Named[] can avoid requesting write access through that parameter. That is useful when the operation only reads. It does not prevent all other aliases from mutating the underlying array or make existing bad state safe. The [actual variance owner](<../../../02 The Type System Core/sections/3. Soundness and variance/3.1. Covariance contravariance and invariance who varies which way.md>) explains mutable-alias and readonly boundaries; merely adding a generic parameter is not an automatic invariance repair.

Function parameters have another directional constraint: a callback requiring Dog cannot generally handle every Animal/Named value promised to a broader consumer. A function that only needs the broader shape can handle a Dog. Strict function checking rejects particular unsafe substitutions, while method syntax has an important exception. The [callback owner](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.2. Callback variance strictFunctionTypes and bivariance pitfalls.md>) supplies actual checked/runtime contrasts. Keep that rule distinct from the array example rather than treating every accepted callback direction as unsound.

### 3) **Adopt checking without confusing escapes with validation**

Types can be introduced through checked JavaScript/JSDoc, TypeScript source and deliberate stricter configurations. There is no required ladder that first disables strictness in every renamed file. Choose a coherent unit and verify the full intended target. The [real mixed-source migration](<../../../20 Production Checklist Migration and Interoperability/sections/2. Migration Playbooks/2.1. JavaScript to TypeScript file by file.md>) demonstrates alternative stages and their limits.

An any boundary gives up selected checking; unknown asks the consumer to establish what it uses. Neither keyword validates a value. Also avoid saying every external API automatically returns unknown: JSON.parse has an any return declaration, and other providers have their own declarations. Deliberately receive uncertain data as unknown where appropriate, then implement the required runtime checks. The [previous goal/boundary example](<./1.2. Design goals and non-goals what TypeScript intentionally does not do.md>) contrasts a false assertion with an actual field check.

A green migration command can omit a source file or probe, and a total can stay constant while one accepted diagnostic is replaced by another. Record selected contracts and remaining exceptions, then test their actual consequences. Counts and suppression comments can support review but do not establish safety or make all remaining risk impossible.

### 4) **Common confusion**

Assignability is directional and context-sensitive. It is different from prototype identity and from equality of two type expressions. Extra properties on a held object can coexist with structural acceptance, while a fresh literal at a target can receive an excess-property diagnostic.

Readonly limits particular checked operations, not every alias or runtime mutation. A successful compiler result also does not prove that declared external values are true. These boundaries explain selected failures without implying that every runtime exception is a soundness failure or that every reported compiler problem should be dismissed.

### 5) **Performance note**

This lesson observes compatibility and a mutable-alias failure. It measures no checker complexity, cache advantage, runtime performance or structural-depth cost formula. Naming a type can improve clarity, but does not guarantee a faster checker or language service. Use the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) when performance is an actual question, preserving the contract while comparing candidates.

### 6) **Mentor note**

Ask why dog is acceptable to greet, why the plain Named object is not a Dog and why the fresh color property is rejected. Then have the learner identify the two aliases to the same array and predict the failing bark operation. A sound answer separates shape requirements from storage identity.

Show the readonly view created after mutation and ask whether it repairs the array. Require the learner to explain the remaining aliases and actual runtime state. For gradual adoption, ask which checks and boundaries improve rather than grading progress solely by file extensions or any counts.
