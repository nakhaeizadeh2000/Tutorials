## 3.3. Choosing erasable syntax — the zero-cost interop rule

### 1) **Erasable** (type annotations, interfaces, `type` aliases, generics, `as`, `satisfies` — all vanish cleanly)

**Definition** — A construct is *erasable* if its removal is sufficient to produce valid JavaScript — no synthetic code needs to be generated. Erasable constructs are zero-cost at runtime: they cannot fail, cannot slow startup, and work with every executor (`tsc`, `esbuild`, `swc`, Node native stripping).

Complete erasable inventory (as of TypeScript 5.9 era):

| Erasable construct | Example | Emit |
|---|---|---|
| Type annotation | `const x: string = "hi"` | `const x = "hi"` |
| `interface` | `interface User { name: string }` | *(removed)* |
| `type` alias | `type Id = string` | *(removed)* |
| Generic parameter | `function f<T>(x: T)` | `function f(x)` |
| `as` / `satisfies` / `!` | `value as string`, `value!` | `value` |
| `declare` | `declare const x: number` | *(removed)* |
| Type-only `import` | `import type { User } from "./user"` | *(removed, never emitted as value import)* |

Modern default: `verbatimModuleSyntax: true` in `tsconfig.json` enforces that `import type` and `import` are never conflated (a bare `import { User }` that is only used as a type would otherwise be elided incorrectly).

### 2) **Non-erasable legacy** (`enum`, `namespace` IIFE emit, `parameter properties` — require a transform)

These constructs *require* the compiler to generate synthetic JavaScript. They work under `tsc`/`tsx`/esbuild transforms, but *fail* under type stripping (Node `--experimental-strip-types`) and violate `--erasableSyntaxOnly` (introduced in TypeScript 5.8).

| Non-erasable | Generated code | Modern replacement |
|---|---|---|
| `enum E { A, B }` | IIFE object `{ A: 0, B: 1, "0": "A", … }` | `type E = "A" \| "B"` + `const E = { A: "A", B: "B" } as const` |
| `namespace N { export const x = 1 }` | IIFE `var N; (function (N) { N.x = 1; })(N \|\| (N = {}))` | ES modules: `export const x = 1` in file `n.ts`, `import { x } from "./n"` |
| `class C { constructor(public x: number) {} }` | `this.x = x` synthetic assignment | `class C { x: number; constructor(x: number) { this.x = x; } }` |
| `module`-augmentation legacy patterns | varies | Use ESM module augmentation (see forward to [12 Modules](../12 Modules Namespaces and Declaration Files/README.md)) |

### 3) **Modern default** (`--erasableSyntaxOnly` + `--isolatedDeclarations`)

- **`--erasableSyntaxOnly: true`** — rejects any non-erasable construct at check time. Enable in new apps and libraries that target native stripping.
- **`--isolatedDeclarations: true`** — requires that every exported declaration has an explicit return/type annotation so its `.d.ts` can be generated *without* reading other files. Enables parallel declaration emit and scales project references (see [2.3. Language server](<../2. How TypeScript doesnt execute/2.3. The language server editor superpowers that justify TypeScript.md>)).
- **`verbatimModuleSyntax: true`** + **`isolatedModules: true`** — together ensure `import type` elision is correct and every file can be transpiled in isolation (required for Vite/esbuild interop).

Recommended `tsconfig.json` for a 2026 application (as of TypeScript 5.9 era, `tsc --init` now generates a similar shape):

```jsonc
{
  "compilerOptions": {
    "strict": true,
    "target": "ES2022",
    "module": "ESNext",
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "erasableSyntaxOnly": true,
    "isolatedDeclarations": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true
  }
}
```

### 4) **Runnable example** — enforcing erasable syntax (good + bad)

```typescript
// good — erasable-only file: works with tsc, tsx, native stripping, esbuild
// file: good-erasable.ts — npx tsc good-erasable.ts --erasableSyntaxOnly --strict → ok
type Status = "pending" | "done" | "failed";
interface Task { id: string; status: Status; }
export function isDone(t: Task): boolean { return t.status === "done"; }
// emit: function isDone(t) { return t.status === "done"; } — just erasure

// bad — non-erasable: fails erasableSyntaxOnly, fails native stripping
// file: bad.ts — npx tsc bad.ts --erasableSyntaxOnly → error
// enum Status { Pending, Done, Failed } // error TS1294: This syntax is not erasable under --erasableSyntaxOnly.
// export enum Status { Pending, Done, Failed } // same error
// fix: use union + const object (erasable)
const Status = { Pending: "pending", Done: "done", Failed: "failed" } as const;
type Status = typeof Status[keyof typeof Status]; // "pending" | "done" | "failed"
interface Task { id: string; status: Status; } // Task remains erasable

// bad — parameter property shortcut
// class Cache { constructor(private store: Map<string, string>) {} } // error under erasableSyntaxOnly
// fix: explicit field
class Cache {
  private store: Map<string, string>;
  constructor(store: Map<string, string>) { this.store = store; }
}
```

### 5) **Common confusion**

- "`--erasableSyntaxOnly` is required for type stripping" — not strictly; stripping will fail at *execution* time for non-erasable files, but `erasableSyntaxOnly` moves the failure to *check* time with a clear error. That's the point: fail fast.
- "`isolatedDeclarations` forbids inferred return types" — only on *exported* declarations. Internal functions can still infer; exported APIs must be explicit.
- "I use `enum` heavily, migration is impossible" — codemod is mechanical: `enum E { A, B }` → `const E = { A: "A", B: "B" } as const; type E = typeof E[keyof typeof E]` preserves runtime members and narrows type; exhaustive switch helpers keep discriminants working.

### 6) **Performance note**

Non-erasable emits add hidden IIFEs that block tree-shaking and prevent scope hoisting. An `enum` with 10 members emits an object literal + bidirectional mapping + IIFE closure; the equivalent union + const object emits a single `const` binding that bundlers can inline. On libraries with many enums, migrating to unions has shaved 3–8% bundle size in measured cases (measure before/after with `source-map-explorer`).

### 7) **Mentor note**

Make the rule crisp: *if `node --experimental-strip-types src/*.ts` exits 0 for every source file, your codebase is erasable and stripping-compatible*. Add it as a CI check (`tsc --erasableSyntaxOnly --noEmit` in one job, `node --experimental-strip-types --check` probe in another).
