## 3.3. Choosing erasable syntax — the zero-cost interop rule

### 1) **Choose syntax for a declared execution path**

An erasable type construct can be removed while leaving the intended JavaScript operation. That is useful when a runner strips types instead of transforming TypeScript value constructs. “Zero cost” here means the type description does not install a runtime type-checking operation; the remaining JavaScript, module loading and source processing still have costs and can fail.

The [erasure experiment](<../2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>) already compares executable/declaration artifacts, a successful transformed enum/namespace/parameter-property program and native stripping rejection. Keep that inventory there. Choose the actual loader, module graph and supported APIs as well as source syntax. An erasable file is not guaranteed to work under every runtime, transformer, version or configuration.

Use [type-import behavior](<../../../12 Modules Namespaces and Declaration Files/sections/1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>) when deciding which statements should remain at runtime. Whole-statement type imports disappear; inline-only type specifiers under verbatim syntax can leave an empty runtime import. Required initialization may need an explicit value/side-effect edge. A flag or automatic import rewrite does not by itself preserve that behavior.

### 2) **Treat non-erasable replacements as contract changes**

A supported emitter can transform TypeScript value constructs. A stripping path cannot necessarily do so. Choose a representation based on the path and public behavior needed, rather than labeling every transformed construct a mistake.

Replacing a numeric enum with strings changes values and can remove reverse lookup behavior. A const object can be a useful alternative, but its keys, serialized values, exports and consumer assumptions need review. The [enum migration owner](<../../../11 Enums and Literal Types/sections/2. Enums vs Erasable Alternatives/2.2. erasableSyntaxOnly the enum ban and migration.md>) supplies the full actual comparison. No universally equivalent codemod follows from “use a union.” Similarly a module reorganization can change loading and names even when it removes a runtime namespace.

Distinguish an ambient declaration or augmentation describing a provider from runtime code implementing that provider. Type-only namespace content differs from a namespace that creates values. The [syntax configuration owner](<../../../13 Configuration and Compiler Options/sections/2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>) owns the exact restrictions and actual graph. Avoid copying a partial legacy list and calling it complete.

### 3) **Keep declaration isolation separate from stripping**

`isolatedDeclarations` asks whether exported declarations contain sufficient information for supported declaration generation without a full checker. It is not a prerequisite for executing erasable source or obtaining editor features, and it does not require explicit annotations on every export. Some simple expressions have supported inference. The [5.5 design explanation](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-5.html#isolated-declarations) documents these exceptions and explains that enabling the flag does not itself change emission into a parallel pipeline. Current tool behavior still needs verification.

For an actual extension, use the **complete two-file graph and tsconfig in section 2 of the syntax configuration owner linked above**. It creates src/kinds.mts and src/app.mts, checks explicit type imports and rewrites relative .mts imports to emitted .mjs. Use TypeScript **7.0.2**, Node **20.20.2** for emitted output and Node **22.18.0** for source execution, verified 2026-10-17. Add these exports to src/kinds.mts, retaining its original contents:

```typescript
export const release = 10;
export function literal() { return 20; }
```

Run from that fixture root:

```bash
tsc -p tsconfig.json --noEmit --declaration --isolatedDeclarations
tsc -p tsconfig.json --declaration --isolatedDeclarations --emitDeclarationOnly --noEmitOnError --outDir type-dist
tsc -p tsconfig.json --noEmitOnError
node dist/app.mjs
npm exec --yes --package=node@22.18.0 -- node src/app.mts
```

All commands exit 0; both executions print `Kind:A`. Inspect type-dist/kinds.d.mts: release and literal have generated declarations despite lacking explicit annotations. The former is a const literal declaration; the function's simple returned literal supplies sufficient information. This is a concrete counterexample to an “all exports must be annotated” rule. It does not establish every expression is supported or that the compiler scheduled independent workers.

Now add another export:

```typescript
export function fromCall() { return label("A"); }
```

Ordinary `tsc -p tsconfig.json --noEmit` still succeeds, and native Node 22.18.0 still runs the source entry with `Kind:A`. That source path does not require declaration isolation. The check with declaration and isolatedDeclarations fails TS9013 because this exported function needs an explicit return annotation for that restriction. Repair only its signature:

```typescript
export function fromCall(): string { return label("A"); }
```

Repeat the isolated check and declaration-only command; both pass, and the generated signature returns string. Rebuild and run emitted/source entries again. This verifies a declaration restriction and its repair independently of the already working source execution path. It is not evidence of a faster build, complete external consumer compatibility or identical editor behavior.

### 4) **Common confusion**

The syntax gate, explicit import handling, single-file restrictions and declaration restrictions have different purposes. JSON configuration uses a property such as `"erasableSyntaxOnly": true`; CLI invocation uses `--erasableSyntaxOnly`. Adding every flag to a starter config does not explain whether the project needs the restriction or meets the remaining host requirements.

A successful Node command checks the actual entry and modules loaded by that run. Passing multiple filenames after one entry does not execute each as an independent program, and a syntax-only check does not establish module behavior. Test supported entries and graph contracts deliberately; no single glob command proves every possible package or deployment path.

### 5) **Performance note**

This extension measures no startup, bundle size or parallel declaration speed. Restricting syntax can enable a chosen tool path, but the flag itself is not a measured optimization. Runtime representation, side effects, bundler configuration and consumer support affect results. Do not assume every emitted enum blocks tree shaking or that changing representation saves a fixed percentage; preserve the intended behavior before measuring the actual pipeline.

### 6) **Mentor note**

Ask the learner why unannotated release/literal pass while fromCall needs an annotation under the additional declaration restriction. Then ask why native source execution was unaffected by that diagnostic. A sound answer distinguishes sufficient declaration information from executable source syntax.

For an enum replacement, request one consumer behavior that could change and the evidence needed to preserve or deliberately migrate it. For a proposed “works everywhere” config, ask for the actual entry, loader and API assumptions. Require bounded observations instead of equating a green syntax flag with complete compatibility.
