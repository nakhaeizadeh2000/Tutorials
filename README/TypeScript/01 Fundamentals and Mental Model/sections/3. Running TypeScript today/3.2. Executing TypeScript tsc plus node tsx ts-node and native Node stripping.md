## 3.2. Executing TypeScript — tsc plus node, tsx, ts-node, and native Node stripping

A `.ts` file needs a path from typed source to JavaScript execution. You can emit JavaScript first, use a runner that transforms source during loading, or use a compatible Node version to strip erasable types. All three can run the same small program; they differ in supported syntax, configuration and checking.

The examples below were verified 2026-10-12. Classic checking/emission uses TypeScript 7.0.2 and Node 20.20.2. Native examples use Node **22.18.0**. Runner examples use Node 20.20.2 with the exact package versions given below. Those are tested combinations, not a claim that all tool versions are interchangeable.

### 1) **The classic path**

With compiler emission, inspect the files you deploy and run those files with the intended runtime. This is useful when a package needs JavaScript artifacts or the deployment runtime cannot process the source syntax. A compiler setting such as `target` controls its emission; the runtime must still implement APIs the emitted code calls.

In a new directory with no `tsconfig.json`, save this file:

```typescript
// hello.ts
const greeting: string = "Hello";
console.log(`${greeting}, TypeScript!`);
```

Run these as two commands:

```bash
tsc --strict --target es2022 --module commonjs --outDir dist hello.ts
node dist/hello.js
```

The output is `Hello, TypeScript!`. `dist/hello.js` contains the variable and console call, with the annotation removed. Use a project configuration for a larger application; this explicit file example keeps the first experiment small. [The compilation pipeline](<./3.1. The compilation pipeline tsc emit declarations and source maps.md>) covers project emission, declarations and source maps.

### 2) **Just-in-time execution**

A source runner transforms files while loading them. That avoids managing an output directory for a script, but the transform, module resolution and compiler integration become part of your execution environment. Test that environment rather than assuming a tool name establishes compatibility.

For the verified runner setup, run `npm init -y`, then install these development dependencies in this scratch directory:

```bash
npm install --save-dev --save-exact tsx@4.20.5 ts-node@10.9.2 typescript@5.9.3 @types/node@22.18.0
npx tsx hello.ts
npx ts-node --compiler-options '{"module":"CommonJS"}' hello.ts
```

Both print `Hello, TypeScript!`. The local TypeScript 5.9.3 package is deliberately pinned for this `ts-node` compiler-API integration; it is separate from the TypeScript 7.0.2 checker used in the classic example. Keep tool/compiler compatibility explicit during upgrades.

| Tested path | Checking responsibility | Files executed |
|---|---|---|
| `tsc`, then Node | The compiler checks the selected program; runtime tests still needed | Emitted JavaScript |
| `tsx` | Run a separate project check; successful execution is not a type check | Source transformed by the runner |
| `ts-node` setup above | Checking enabled by default; `--transpile-only` changes that | Source handled by its compiler integration |
| Native Node stripping | Run a separate project check | Supported source after stripping |

The [tsx maintainer project](https://github.com/privatenumber/tsx) and [ts-node option reference](https://typestrong.org/ts-node/docs/options/) are the owners of these tool contracts. Test runners also have their own transform and checking configuration; running tests is not evidence that all project files were type-checked.

### 3) **Native type stripping**

In the Node 22 line, stripping was introduced in **22.6.0** behind a flag and became enabled by default in **22.18.0**. On the tested 22.18.0 runtime, `node hello.ts` prints the same greeting. Earlier versions must be checked against their own documented flags; “22.12+” is not a precise statement about unflagged execution. See the [Node 22 API history](https://nodejs.org/docs/latest-v22.x/api/typescript.html).

Stripping removes supported type syntax. It neither checks assignments nor applies `tsconfig.json`. Relative imports must name files the runtime can find, and module syntax must match the actual module context. The compiler's `paths` aliases and `target` do not configure native Node execution. A multi-file program needs a source-import strategy as well as erasable syntax; [erasable toolchain guarantees](<../../../13 Configuration and Compiler Options/sections/2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>) compares source and emitted graphs.

You may deploy supported source when that matches your runtime, dependencies and checking pipeline. Emitted JavaScript is useful for artifact inspection and consumers that need it. Choose deliberately; neither source deployment nor building a `dist` directory is a universal production rule.

### 4) **Observe checking and syntax failures separately**

Save the next files individually. The first deliberately violates an annotation:

```typescript
// unchecked.ts — intentional type error
const count: string = 42;
console.log(count);
```

`tsc --strict --noEmit unchecked.ts` reports TS2322. Native Node 22.18.0 and `npx tsx unchecked.ts` instead print `42`: that number still exists after the annotation is removed. The pinned `ts-node` command from section 2 rejects it with a type diagnostic. Adding `--transpile-only` makes that command execute and print `42` too. Checking behavior depends on the configured path, not the filename alone.

The next file requires a TypeScript transform:

```typescript
// enum.ts
enum Color { Red, Green }
console.log(Color.Red);
```

On Node 22.18.0, `node enum.ts` fails with `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`. `node --experimental-transform-types enum.ts` prints `0` with an experimental warning. This flag can transform supported TypeScript-specific forms such as an enum; it is not a general JavaScript downlevel compiler.

Finally, decorator syntax is a separate unsupported case for that native path:

```typescript
// decorator.ts
function observe(_target: Function, _context: ClassDecoratorContext): void {}
@observe
class Example {}
console.log(typeof Example);
```

`node --experimental-transform-types decorator.ts` on Node 22.18.0 throws a `SyntaxError` at the decorator. It does not transform decorators. Compiling with `tsc --strict --target es2022 --module commonjs --outDir dist decorator.ts` and running `node dist/decorator.js` prints `function`. This contrast locates the failure in the source parser rather than in type checking. Node's [native execution tutorial](https://nodejs.org/learn/typescript/run-natively) explains the restricted syntax path.

### 5) **Common confusion**

“I executed the file, so its types are correct” confuses a runtime result with a static check. The deliberately incorrect annotation demonstrates the difference. A runner that checks loaded files can also miss files that were never loaded; retain a project-wide check when that is your release requirement.

“The transform flag handles anything TypeScript accepts” also fails. Supported TypeScript transforms, supported JavaScript syntax and available runtime APIs are different questions. Classify the failing construct before switching tools or compiler options.

### 6) **Performance note**

Startup includes loading tools, parsing source, transforming supported syntax and running imports. Watch/rebuild behavior also depends on caching and which files change. This lesson ran correctness comparisons, not a timing benchmark, so it promises no ranking or speed ratio. Measure cold and warm runs separately with the actual project, pinned tools and consistent inputs before choosing based on latency.

Source stripping avoids a separately managed emission step, but still performs work at execution. Compiler annotations themselves do not make the application faster.

### 7) **Mentor note**

Have a learner predict which command rejects each of `unchecked.ts`, `enum.ts` and `decorator.ts`. Ask them to name the responsible stage: checking, transform or parsing. A good explanation connects the observed output/error to that stage and states the tested versions.

Then ask how they would deploy the program and verify the chosen files. The answer should include a project check, actual runtime exercises and a reason for the source/artifact choice. Avoid judging the choice from a generic tool speed claim.
