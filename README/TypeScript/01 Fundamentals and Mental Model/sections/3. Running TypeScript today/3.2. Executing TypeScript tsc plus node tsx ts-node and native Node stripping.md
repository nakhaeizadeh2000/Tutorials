## 3.2. Executing TypeScript — tsc plus node, tsx, ts-node, and native Node stripping

### 1) **The classic path** (`tsc` → `node dist/app.js` — two steps, most faithful to production)

**Definition** — The most predictable execution path compiles first, then runs the emitted JavaScript with Node.js. This mirrors production: what runs in the deployed container is the `dist/` JavaScript, not the source `.ts`.

```bash
npx tsc                        # emit per tsconfig.json: src/app.ts → dist/app.js
node dist/app.js               # run the emitted JS
node --enable-source-maps dist/app.js # map stack traces back to .ts via .js.map
```

Trade-off: two steps and a `dist/` directory, but zero magic — stack traces and behavior are exactly what production sees.

### 2) **Just-in-time execution** (`tsx` / `ts-node` — transpile on import)

These tools hook Node's module loader and transpile `.ts` on the fly:

| Tool | Scope | Speed | Emit model |
|---|---|---|---|
| `tsx` (preferred as of 2025) | ESM + CJS, built on `esbuild` | Fast (esbuild's Go parser) | Transpile only (no type checking) |
| `ts-node` | CJS-first, ESM with loader flags | Slower (TypeScript compiler) | Optionally type-checks (`--transpile-only` to skip) |
| `vite` `ts` plugin | Dev server / HMR | Fastest (Vite+esbuild) | Transform for browser, check separately with `tsc --noEmit` |

Modern guidance — for local scripts and tooling, `tsx` is the default (e.g., `tsx src/app.ts`). For test suites, let the test runner's transform handle it (Vitest uses Vite's pipeline). Avoid `ts-node` transpile + separate `tsc` check duplication unless you need `ts-node`'s custom compiler hooks.

### 3) **Native type stripping** (Node.js 22.12+ can run `.ts` directly by erasing types — zero transform)

As of Node.js 22.12+ (stable as of September 2026, labeled TypeScript 5.9 era), Node can execute TypeScript by *stripping* type syntax without transforming other syntax. This is the zero-cost path — but it only works for *erasable* syntax (see [3.3. Choosing erasable syntax](<./3.3. Choosing erasable syntax the zero-cost interop rule.md>)).

```bash
node --experimental-strip-types src/app.ts            # strip types, run JS remainder (no emit to disk)
node --experimental-transform-types src/app.ts        # strip + transform syntax newer than target (e.g., decorator legacy)
```

What this enables: `node src/app.ts` during development without a watcher, and `node --experimental-strip-types --watch src/app.ts` for fast feedback loops. Production should still build an explicit `dist/` (don't deploy `.ts` for stripping in containers — emit once and run `node dist`).

---

### 4) **Runnable example** — three paths, same program (good + bad)

```typescript
// file: hello.ts — erasable, so all three paths work
const greeting: string = "Hello";
console.log(`${greeting}, TypeScript!`);

// Path A — classic (always works):
// npx tsc hello.ts --outDir dist && node dist/hello.js

// Path B — tsx (always works, strips + transpiles):
// npx tsx hello.ts

// Path C — native stripping (requires erasable syntax, Node 22.12+):
// node --experimental-strip-types hello.ts

// bad — using non-erasable API under native stripping
// file: bad-enum.ts
// enum Color { Red, Green, Blue }
// console.log(Color.Red); // ❌ fails with --experimental-strip-types: "Unexpected token 'enum'"
// fix: replace enum with union + const object (see [2.1. Type erasure](<../2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>))
// const Color = { Red: "Red", Green: "Green", Blue: "Blue" } as const;
// type Color = typeof Color[keyof typeof Color];
```

### 5) **Common confusion**

- "Native stripping type-checks my code" — it doesn't. Stripping removes annotations and runs the remainder; type errors are silently ignored. Always run `tsc --noEmit` in parallel (CI and editor).
- "`tsx` and native stripping are interchangeable" — not for non-erasable syntax. `tsx` transpiles `enum`/`namespace` via esbuild; stripping refuses them.
- "`ts-node` type-checks by default, so I don't need `tsc`" — `ts-node` without `transpileOnly` type-checks synchronously on import, which is slow and breaks ESM parallelism. Prefer `tsx` for execution + `tsc --noEmit` for checking as separate concerns.

### 6) **Performance note**

Native stripping cold-start is ~2–3× faster than `tsx` for a single-file script (no esbuild invocation, no cache). For a 300-file warm dev server, `tsx` (esbuild-backed) wins because it caches transforms across imports while stripping re-parses per file. Measure your workload: `time node --experimental-strip-types src/app.ts` vs `time npx tsx src/app.ts` before standardizing the dev script.

### 7) **Mentor note**

Teach execution as three distinct concerns: *checking* (is it well-typed?), *emitting* (produce distributable JS), *executing* (run it). Students who conflate them debug the wrong tool when a stack trace points to `dist/` or when a stripping error complains about `enum`. Exercise: have them run the same file via all three paths and compare the presence of `dist/`, the error messages, and the startup latency.
