## 3.1. The compilation pipeline — tsc, emit, declarations, and source maps

### 1) **Observe checking and the requested artifacts**

The compiler analyzes the selected program and can emit artifacts according to its options. A check is not complete runtime validation. JavaScript, declarations and maps are different outputs, and not every invocation creates all of them. noEmit disables output; noEmitOnError prevents new output when the compiler reports errors. The latter is not a promise that an existing old output directory disappears.

Use native TypeScript **7.0.2**, Node **20.20.2**, npm **10.8.2** and esbuild **0.28.2**, verified 2026-10-17. Create src in a disposable directory. Save `package.json`:

```json
{
  "name": "pipeline-contract",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "check": "tsc -p tsconfig.check.json",
    "build": "esbuild src/math.mts --platform=node --format=esm --target=es2022 --outfile=bundle/math.mjs --sourcemap",
    "smoke": "node smoke.mjs",
    "verify": "npm run check && npm run build && npm run smoke"
  },
  "devDependencies": { "esbuild": "0.28.2" }
}
```

The compiler is the stated native tsc on PATH; this package does not install a different TypeScript dependency. Save `tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "lib": ["es2022"],
    "types": [],
    "rootDir": "src",
    "outDir": "dist",
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true,
    "noEmitOnError": true
  },
  "include": ["src/**/*.mts"]
}
```

Save `tsconfig.check.json`:

```json
{"extends":"./tsconfig.json","compilerOptions":{"noEmit":true}}
```

Save `src/math.mts`:

```typescript
export function twice(value: number): number { return value * 2; }
export function fail(): never { throw new Error("demonstration"); }
```

Save `smoke.mjs`:

```javascript
import { twice } from "./bundle/math.mjs";
if (twice(21) !== 42) throw new Error("twice contract failed");
console.log("twice verified");
```

Run these independently:

```bash
npm install --ignore-scripts --no-audit --no-fund
npm run check
tsc -p tsconfig.json
tsc -p tsconfig.json --emitDeclarationOnly --outDir type-dist
npm run verify
```

All exit 0; verify finishes with `twice verified`. The initial check emits nothing into an initially absent dist directory. The regular compiler build produces the following four artifacts, while the declaration-only invocation creates just the last two kinds in type-dist:

| Artifact | Purpose |
|---|---|
| math.mjs | JavaScript implementation for this emitted ESM path. |
| math.mjs.map | Relates generated JavaScript locations to source locations. |
| math.d.mts | Describes exported functions to a type checker. |
| math.d.mts.map | Relates declaration locations to original source locations. |

The esbuild step instead creates bundle/math.mjs and its JavaScript map. It does not generate the TypeScript declaration artifacts. Its output filename does not imply bundling: this command transforms one entry and does not pass the bundle option. A library pipeline may combine a chosen implementation build with appropriate declaration generation and installed-consumer checks. Name which artifacts are actually released.

### 2) **Use maps through a real consumer**

Inspect dist/math.mjs and dist/math.d.mts for their sourceMappingURL comments, then parse their adjacent map JSON files. Both maps refer to ../src/math.mts in this layout. The [sourceMap reference](https://www.typescriptlang.org/tsconfig/sourceMap.html) explains the JavaScript map relationship; the [declarationMap reference](https://www.typescriptlang.org/tsconfig/declarationMap.html) describes source navigation through declarations.

A map file alone does not prove a debugger or editor can find the original source. The actual consumer needs the map and usable source paths. For a concrete Node stack contrast, run each deliberate failure from the project root:

```bash
node --input-type=module -e 'import {fail} from "./dist/math.mjs"; fail();'
node --enable-source-maps --input-type=module -e 'import {fail} from "./dist/math.mjs"; fail();'
```

Both exit 1 with the intentional demonstration Error. The ordinary stack names emitted math.mjs; the mapped stack identifies src/math.mts at the source throw. This verifies Node's stack mapping for these available artifacts. It does not automate breakpoint behavior, editor declaration-map navigation or source availability after packaging. Keep relevant maps/sources with the environment in which they are meant to be consumed.

### 3) **Preserve failures across separate tools and configurations**

The [esbuild TypeScript documentation](https://esbuild.github.io/content-types/#typescript) distinguishes transformation from type checking, identifies unsupported declaration generation and describes which configuration fields it reads. Matching a target/module label does not prove two emitters are behaviorally identical. Their supported features and configuration interpretations differ; esbuild's target is explicit in the command above rather than assumed from tsconfig. Check the actual consumers and features your pipeline supports.

In a disposable copy, change twice's return expression to `"wrong"`, keeping its number return annotation. The native check fails TS2322. With the fixture's noEmitOnError, a compiler build fails without replacing the previous dist implementation. Now run a controlled comparison with:

```bash
tsc -p tsconfig.json --noEmitOnError false --outDir permitted-error
```

It exits nonzero but creates erroneous output in that separate directory. This observes why process status and artifact presence are different. Do not execute it as a successful release candidate.

To test orchestration, remove only the scratch project's generated bundle directory and run npm run verify while the source error remains. Check fails and the build/smoke scripts do not run; no new bundle appears. Running npm run build **independently** still succeeds because esbuild does not type-check that return annotation. npm run smoke then exits 1 with `twice contract failed`. Separate tools need a workflow that preserves the required failures; a compiler emission option does not control an independent emitter.

Restore multiplication and run verify again: it passes. For a behavior-only contrast, change multiplication to addition. The source still checks, but verify reaches smoke and fails because twice(21) is 23. Restore multiplication, regenerate the compiler artifacts and run verify again. The selected number signature and successful transformation were insufficient to establish the algorithm.

The child check config intentionally inherits the selected files and changes emission. Use showConfig and listFilesOnly when reviewing such composition. Child include/files lists and individual options can override a base; [effective audits](<../../../20 Production Checklist Migration and Interoperability/sections/1. Production Checklist/1.2. Strictness and configuration audits.md>) demonstrate real scope failures. Project references add a different configured dependency/build contract, taught in the [complete reference project](<../../../13 Configuration and Compiler Options/sections/3. Modules Emit and Projects/3.2. declaration composite project references.md>). They do not guarantee a particular language-service recheck strategy or parallel speedup.

### 4) **Common confusion**

A combined check/emit command can be valid; inspect its diagnostic and output policy rather than assuming two jobs in one command make the cause unknowable. A separate command can also be misconfigured or ignored. The names check/build are conventions; their actual inputs, statuses and outputs establish their role.

A declaration is a checker description, while a map relates locations. Neither validates returned runtime values. noEmit does not delete an old dist directory, and noEmitOnError does not stop an independently invoked emitter. A successful smoke only checks its stated behavior; broader package or host promises need additional consumer evidence.

### 5) **Performance note**

No checking/emission/map overhead, bundler ranking or percentage improvement was measured here. Requested artifacts and tool setup add work, but costs depend on the program and pipeline. Disabling declaration output in a no-emit check is not automatically a speed optimization. Use [comparable successful measurements](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) when cost is the question, preserving selected coverage and actual consumer contracts.

### 6) **Mentor note**

Have the learner list the actual artifacts from each command and identify which one Node executes. Then compare the two deliberate stacks and explain what the map consumer did. Ask what would remain unverified if only map JSON existed.

For the wrong return, require the compiler status, old output state, independent emitter result and smoke result. For addition, ask why type checking stays green. A sound explanation distinguishes syntax/transformation, static contracts, output freshness and tested behavior without declaring one script layout universally correct.
