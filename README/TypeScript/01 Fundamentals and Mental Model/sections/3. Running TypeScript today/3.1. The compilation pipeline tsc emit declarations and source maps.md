## 3.1. The compilation pipeline — tsc, emit, declarations, and source maps

### 1) **`tsc` is a type checker and an emitter** (two jobs: validate the program, then rewrite `.ts` → `.js` + `.d.ts` + `.js.map`)

**Definition** — `tsc` performs two distinct jobs in one invocation. First it *type-checks* the program (validates that every expression matches its type). Then, if checking passes (or with `--noEmitOnError false`), it *emits* JavaScript, declaration files, and source maps. These jobs can be separated: `tsc --noEmit` checks only; `tsc --emitDeclarationOnly` generates only `.d.ts`.

Outputs per file `src/utils.ts`:

| Output | Flag | Purpose |
|---|---|---|
| `dist/utils.js` | default | Runtime JavaScript after erasure + downleveling |
| `dist/utils.d.ts` | `declaration: true` | Public type contract for consumers (what `import` sees) |
| `dist/utils.js.map` | `sourceMap: true` | Maps emitted line back to source for debuggers |
| `dist/utils.d.ts.map` | `declarationMap: true` | Maps `.d.ts` hover back to source definition |

### 2) **`noEmit` separates checking from building** (CI often checks, bundler emits)

In modern repos, `tsc` as emitter is slow for development. The faster split is:

- `tsc --noEmit` in CI and in the editor (type correctness).
- `esbuild`/`swc`/`Vite`/`Next.js` does the actual transpile for dev and production (faster, parallel, stripped types).

This separation works because emitted JavaScript from `tsc` and from esbuild is *behaviorally identical* when both target the same `target`/`module` (see [3.2. Executing TypeScript](<./3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>)).

### 3) **Configurations are composable** (base `tsconfig.json` + `extends` + project references)

A typical repo has a base config and per-project overrides:

```jsonc
// tsconfig.base.json
{ "compilerOptions": { "strict": true, "target": "ES2022", "module": "ESNext", "verbatimModuleSyntax": true } }
// packages/app/tsconfig.json
{ "extends": "../../tsconfig.base.json", "compilerOptions": { "outDir": "dist", "composite": true }, "references": [{ "path": "../shared" }] }
```

`composite: true` enables project references and incremental `.tsbuildinfo` caching — the language server (see [2.3. The language server](<../2. How TypeScript doesnt execute/2.3. The language server editor superpowers that justify TypeScript.md>)) uses these to recheck only changed projects.

### 4) **Runnable example** — checking vs emitting, separate modes (good + bad)

```typescript
// file: pipeline.ts — tsc can be invoked in three modes
export function add(a: number, b: number): number { return a + b; }
// Mode 1: check only — npx tsc --noEmit  (exit 0 if add is well-typed, no files written)
// Mode 2: emit — npx tsc (writes dist/pipeline.js + .d.ts if declaration: true)
// Mode 3: watch — npx tsc --watch (incremental recheck + emit on save)

// bad — mixing check and emit in CI and expecting them to coincide
// Running `tsc` in CI that both checks and emits conflates two failures:
// a type error blocks emit, so you don't know if the bug was a type bug or a syntax bug.
// fix: run check and build as separate steps:
// "scripts": { "check": "tsc --noEmit", "build": "tsc -b" } — CI runs check first, build second
```

```bash
# Try it (requires npx tsc 5.9+ / 7.0):
# npx tsc --noEmit --strict pipeline.ts && echo "types ok"
# npx tsc pipeline.ts --target es2022 --module esnext --declaration --sourceMap --outDir dist && ls dist
# cat dist/pipeline.d.ts  # should contain: export declare function add(a: number, b: number): number;
```

### 5) **Common confusion**

- "`tsc` bundles my project" — it emits per-file; bundling/graph splitting is a bundler's job (`Vite`, `esbuild`, `webpack`).
- "`--noEmitOnError` means I won't get broken `.js`" — only if you also emit via `tsc`. If esbuild emits separately, it will still emit JS even when `tsc --noEmit` fails — fix the type error regardless of who emits.
- "Declaration files are for publishing only" — project references *require* `declaration: true` even for private packages, because dependents read `.d.ts` to avoid rechecking source.

### 6) **Performance note**

`declaration: true` + `declarationMap: true` adds ~5–10% to emit time but enables project-reference parallelism (see [13 Configuration](../../13%20Configuration%20and%20Compiler%20Options/README.md) forward). For `tsc --noEmit` only, disable `declaration` in a dedicated `tsconfig.check.json` to cut CI time by ~15% on large repos. Measure `time npx tsc --noEmit` with/without declarations before standardizing.

### 7) **Mentor note**

Teach the pipeline as two tools in one binary: ask "which job failed — checking or emitting?" when `tsc` reports an error. Students who separate the jobs stop blaming the bundler for type errors and stop blaming the checker for bundle size. Review checklist: does `package.json` have distinct `check` and `build` scripts?
