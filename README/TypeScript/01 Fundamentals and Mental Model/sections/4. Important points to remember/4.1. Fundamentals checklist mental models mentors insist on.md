## 4.1. Fundamentals checklist — mental models mentors insist on

Use this checklist to explain the path from source code to a running program. It brings together four earlier ideas: erasure, JavaScript behavior, boundary validation and separate checking/execution. It is also a review aid: identify the actual assumption behind a piece of code, then show how that assumption is checked.

### 1) **Types don't exist at runtime**

An annotation describes a value to the checker; it does not create a runtime value. Inspect emitted JavaScript to see which declarations disappear and which function bodies remain. The detailed examples live in [Type erasure](<../2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>).

For example, a generic type parameter cannot be printed as though it were an object:

```typescript
// Compile-only probe: generic-probe.ts
export {};
function inspect<T>(): void {
  // @ts-expect-error T is a type parameter, not a value
  console.log(T);
}
```

Checking this file with `tsc --strict --noEmit generic-probe.ts` verifies the expected diagnostic. Without the suppression comment, the checker rejects the use of `T` as a value. If you deliberately emit despite that error and invoke `inspect`, the emitted body still refers to an undeclared `T` and throws a `ReferenceError`. The compiler error and that forced-emission runtime failure are different observations. A type parameter alone never creates an object to inspect.

### 2) **Superset means syntax-compatible, not semantics-identical**

Adding types preserves ordinary JavaScript runtime operations. `typeof null` still produces `"object"`, and calling a missing method still throws. A successful check reduces mistakes; assertions, `any` and trusted declarations can still hide a mismatch. Ask what values a function can actually receive, rather than treating a successful build as evidence about an external server's response.

Review question: can you point to a well-typed operation whose assumption could be false at runtime? An assertion on a network response is one example. The [soundness lesson](<../1. What TypeScript is/1.3. Superset soundness and the type system flavor.md>) explains the broader trade-offs.

### 3) **Validation at the boundary**

Treat untrusted data as `unknown` until runtime checks establish the properties the application needs. Checking that a property exists does not establish its value type: `{ id: 1, name: 123 }` has both properties, but its `name` cannot be uppercased. A predicate signature is a claim made by its author; TypeScript does not prove that every successful return validates that claim. This is why a review needs malformed inputs as well as the happy path. See the [Handbook's narrowing guidance](https://www.typescriptlang.org/docs/handbook/2/narrowing.html).

The example below checks both values before using the shape. It requires no library. Save it as `checklist.ts`, check and emit with `tsc --strict --target es2022 --module commonjs --outDir out checklist.ts`, then run `node out/checklist.js`. Verified with TypeScript 7.0.2 and Node 20.20.2.

```typescript
// checklist.ts
export {};
type ApiResult = { id: number; name: string };

function isApiResult(value: unknown): value is ApiResult {
  return typeof value === "object" && value !== null
    && "id" in value && typeof value.id === "number"
    && "name" in value && typeof value.name === "string";
}

function handle(raw: unknown): string {
  if (!isApiResult(raw)) throw new Error("invalid boundary");
  return raw.name.toUpperCase();
}

console.log(handle({ id: 1, name: "Ada" })); // ADA
for (const input of [null, {}, { id: "1", name: "Ada" }, { id: 1, name: 123 }]) {
  console.log(isApiResult(input)); // false, once per input
}
try {
  handle({ id: 1, name: 123 });
} catch (error: unknown) {
  if (!(error instanceof Error)) throw error;
  console.log(error.message); // invalid boundary
}
```

The valid object reaches the string operation. Each malformed input is rejected, and `handle` reports a boundary error before attempting the invalid method call. These checks establish the declared shape, not every business rule: a finite positive identifier or a nonempty name would need additional checks and an appropriate contract. Extra properties are accepted because the consumer only requires `id` and `name`.

Review assertions according to the evidence behind them. Counting occurrences of `as` cannot distinguish a justified assertion from an unchecked trust boundary. The full predicate mechanics belong in [Custom narrowers](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.3. Custom narrowers predicates asserts and type guards on unions.md>); richer parsing belongs in the validation domain.

### 4) **Tooling is the payoff**

Checking, building and executing answer different questions. A check asks whether the program satisfies the configured static rules. A build produces deployment artifacts. Execution demonstrates behavior for the actual inputs tested. Keep a checking command even when a development runner strips types without checking them.

Choose compiler options for the actual pipeline. `strict` enables a group of checking rules; import preservation and erasable-syntax restrictions address different concerns. Their suitability depends on how the source is executed or transformed. Use the [execution lesson](<../3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>) and [configuration domain](<../../../13 Configuration and Compiler Options/README.md>) to make that choice rather than copying a universal flag set.

### 5) **Common confusion**

A function returning `value is ApiResult` does not validate data merely by having that return annotation. Its body must check the promised shape. Test the false branch too: a guard that accepts malformed data permits unsafe operations, while one that rejects valid data can send callers down an incorrect alternative path.

Erasure also does not mean that all source code disappears. Runtime conditions and function bodies remain. The type alias vanishes from the example, but `typeof`, `in` and the string operation execute as JavaScript.

### 6) **Performance note**

The type alias and predicate return annotation add no runtime checking work. The predicate's ordinary JavaScript conditions do run on every call. This example inspects two properties; larger schemas, getters or additional validation rules can have different costs. Validate where trust changes, and keep ownership clear so a later mutation cannot invalidate the checked assumptions. A validation performed earlier is not a lifetime guarantee.

### 7) **Mentor note**

Give a learner the original existence-only guard and `{ id: 1, name: 123 }`. Ask them to predict its return value, the next operation and the eventual error. A sound repair checks property values, rejects the malformed input and retains a happy-path case. Ask them to explain why the static predicate declaration did not catch the faulty body.

Then ask which command proves a type error, which produces JavaScript, and which exercises behavior. Review the answers separately; one successful command cannot establish all three. [The hidden side of predicates](https://effectivetypescript.com/2024/02/27/type-guards/) provides further reasoning about the obligations of both predicate branches.
