## 4.1. Fundamentals checklist — mental models mentors insist on

### 1) **Types don't exist at runtime** (erasure is the single most important fact)

**Check** — Before writing any code, confirm you can answer:

- What does emitted JavaScript contain after stripping types? (Function bodies + values only; see [2.1. Type erasure](<../2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>).)
- Where does runtime validation happen if types are gone? (At boundaries via `unknown` → predicate; see [2.2. Static vs runtime](<../2. How TypeScript doesnt execute/2.2. Static checking vs runtime reality trust but verify.md>).)

Senior probe: "If I `console.log` the type of a generic parameter, what happens?" — correct answer: `ReferenceError`, because the parameter was erased.

### 2) **Superset means syntax-compatible, not semantics-identical** (well-typed ≠ bug-free)

**Check** —

- Can you name two places where well-typed code still throws at runtime? (Any `any`-backed value and a type assertion `as` that was wrong; also array covariance push.)
- Do you know why `typeof null === "object"` is unchanged by TypeScript? (Runtime semantics are JavaScript's; see [JavaScript 03 Values](<../../../../JavaScript/03 Values Types and Coercion/README.md>).)

### 3) **Validation at the boundary** (parse, don't assert: `unknown` → validated → typed)

**Check** —

- Is every `fetch`/`JSON.parse`/`process.env` entry typed as `unknown` until a predicate/schema proves it?
- Is every `as` justified by a proof you can point to, not by "I know the server returns this"?

Grep audit: `grep -R " as " src/ | wc -l` should decrease over time, not increase. Each `as` in a PR needs a comment linking to the predicate that justifies it.

### 4) **Tooling is the payoff** (rename, navigation, refactoring confidence justify the cost)

**Check** —

- Can you run `tsc --noEmit` and separately `node dist/app.js`? (See [3.1. The compilation pipeline](<../3. Running TypeScript today/3.1. The compilation pipeline tsc emit declarations and source maps.md>).)
- Is `strict: true` + `verbatimModuleSyntax` + `erasableSyntaxOnly` enabled? (See [3.3. Choosing erasable syntax](<../3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>).)
- Does hover on an exported function show a concise, named return type, not an expanded 80-line conditional? (See [2.3. Language server](<../2. How TypeScript doesnt execute/2.3. The language server editor superpowers that justify TypeScript.md>).)

---

### 5) **Runnable example** — the checklist as executable guardrails

```typescript
// checklist item 1: prove erasure — emitted file should contain no trace of types
// npx tsc checklist.ts --target es2022 --module esnext --outDir /tmp/chk && cat /tmp/chk/checklist.js
// If cat shows only JS values, erasure is working

// checklist item 3: boundary pattern (parse, don't assert)
type ApiResult = { id: number; name: string };
function isApiResult(v: unknown): v is ApiResult {
  return typeof v === "object" && v !== null && "id" in v && "name" in v;
}
function handle(raw: unknown): string {
  if (!isApiResult(raw)) throw new Error("invalid boundary"); // validated once
  return raw.name.toUpperCase(); // downstream code is zero-cost typed
}

// checklist item 4: check vs emit are separate
// package.json scripts should read:
// { "check": "tsc --noEmit", "build": "tsc -b", "start": "node --experimental-strip-types src/app.ts" }
// CI runs check even though start strips without checking
```

### 6) **Mentor note**

Use this checklist as a PR template: every PR description ticks these four boxes or notes why not. Students who practice the boundary pattern (`unknown` → predicate → typed) once will apply it correctly forever; those who always `as` will need retraining after each production incident. Review exercise: random file audit — hover every exported symbol and flag any `any`.
