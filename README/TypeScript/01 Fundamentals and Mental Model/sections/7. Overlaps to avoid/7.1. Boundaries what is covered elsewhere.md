## 7.1. Boundaries — what is covered elsewhere

### 1) **JavaScript language mechanics** (values, scope, closures, prototypes, async) — JavaScript track

TypeScript assumes you already understand JavaScript's runtime semantics. For:

- Values, types, coercion, and equality → [JavaScript 03 Values, Types and Coercion](<../../../JavaScript/03%20Values%20Types%20and%20Coercion/README.md>), [04 Variables, Scope and Closures](<../../../JavaScript/04%20Variables%20Scope%20and%20Closures/README.md>), [05 Functions Deep Dive](<../../../JavaScript/05%20Functions%20Deep%20Dive/README.md>)
- Objects, prototypes, classes, collections, iterables → [JavaScript 06 Objects in Depth](<../../../JavaScript/06%20Objects%20in%20Depth/README.md>), [07 Prototypes and Classes](<../../../JavaScript/07%20Prototypes%20and%20Classes/README.md>), [09 Collections](<../../../JavaScript/09%20Collections%20Map%20Set%20and%20Weak%20References/README.md>), [10 Iterables](<../../../JavaScript/10%20Iterables%20Generators%20and%20Async%20Iteration/README.md>)
- Async, event loop, modules, error handling → [JavaScript 13 Async](<../../../JavaScript/13%20Async%20Event%20Loop%20and%20Promises/README.md>), [14 Modules](<../../../JavaScript/14%20Modules%20and%20Code%20Organization/README.md>), [15 Error Handling](<../../../JavaScript/15%20Error%20Handling%20and%20Debugging/README.md>)

This domain reuses those mechanics; it does not re-teach them. Where JavaScript quirks surface (e.g., `typeof null === "object"`), cross-links explain the TypeScript interaction without duplicating the JavaScript explanation.

### 2) **Deep type system mechanics** (structural details, variance, conditional types) — [02 The Type System Core](<../../02%20The%20Type%20System%20Core/README.md>)

Structural typing was introduced here at the flavor level (see [1.3.](<../1. What TypeScript is/1.3. Superset soundness and the type system flavor.md>)) and erasure/validation at the boundary level (see [2.1.](<../2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)). The formal treatment — assignability rules, freshness checks, variance annotations `in`/`out`, soundness lattice, and the type/value separation — lives in **02 The Type System Core**. Do not extend that formalism here.

### 3) **Configuration deep dive** (`tsconfig` flags, project references, strict family) — [13 Configuration and Compiler Options](../../13%20Configuration%20and%20Compiler%20Options/README.md) (textual forward reference until that domain lands)

`strict`, `target`, `module`, `verbatimModuleSyntax`, `isolatedModules`, `erasableSyntaxOnly`, `isolatedDeclarations` were mentioned as modern defaults (see [3.1.](<../3. Running TypeScript today/3.1. The compilation pipeline tsc emit declarations and source maps.md>)/[3.3.](<../3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>)). The per-flag trade-offs, `extends` composition, and monorepo `references` graph belong in 13, not here. Until it lands, this domain's guidance stands: `strict: true` + erasable defaults are the baseline.

### 4) **Decorators and metadata** — [14 Decorators and Metadata](../../14%20Decorators%20and%20Metadata/README.md) (textual forward reference)

Decorators (legacy `experimentalDecorators` vs TC39 stage 3 `Symbol.metadata` stabilized in TS 5.9) and their interaction with `erasableSyntaxOnly` are not covered here; they deserve dedicated treatment in 14. This domain only notes that legacy `enum`/`namespace`/`parameter properties` are the *other* non-erasable class (see [3.3.](<../3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>)).

### 5) **Where this domain stops** (stop-list)

- **Stop:** Do not duplicate JavaScript mechanics, structural typing formalism, `tsconfig` flag catalogue, or decorator semantics.
- **Start here:** mental models for erasure, the checking-vs-runtime contract, execution paths, and the erasable-syntax default that every later domain assumes.
