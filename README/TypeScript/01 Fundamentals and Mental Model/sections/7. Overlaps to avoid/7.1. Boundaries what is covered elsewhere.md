## 7.1. Boundaries — what is covered elsewhere

Fundamentals establishes the first mental model: the checker describes a program, type syntax erases, execution depends on the selected pipeline, and incoming values need runtime evidence. Later owners explain the details. Use this page to choose the next lesson from the question you need to answer.

### 1) **JavaScript language mechanics**

For a value that changes through coercion or equality, start with [Values, Types and Coercion](<../../../../JavaScript/03 Values Types and Coercion/README.md>). For a captured variable or lost receiver, use [Scope and Closures](<../../../../JavaScript/04 Variables Scope and Closures/README.md>) and [Functions Deep Dive](<../../../../JavaScript/05 Functions Deep Dive/README.md>). Object identity, properties and inheritance belong in [Objects](<../../../../JavaScript/06 Objects in Depth/README.md>) and [Prototypes and Classes](<../../../../JavaScript/07 Prototypes and Classes/README.md>).

Scheduling, promise propagation and module evaluation belong in [Async](<../../../../JavaScript/13 Async Event Loop and Promises/README.md>) and [Modules](<../../../../JavaScript/14 Modules and Code Organization/README.md>). TypeScript reuses those runtime operations. A correct annotation does not change their receiver, scheduling or conversion rules.

### 2) **The type system and later transformations**

The introduction here distinguishes shape-based compatibility from names. The full assignability, declaration-space and variance model belongs in [The Type System Core](<../../../02 The Type System Core/README.md>). Its [type/value separation](<../../../02 The Type System Core/sections/2. The type vs value separation/2.1. Type space vs value space two parallel universes.md>) explains which use of a name refers to a runtime value.

Reusable inference belongs in [Generics](<../../../08 Generics Deep Dive/README.md>); mapped/conditional transformations belong in [Utility Types](<../../../09 Utility Types and Type Transformations/README.md>). Fundamentals can motivate these contracts without attempting their complete formal treatment. The local [flavor experiment](<../1. What TypeScript is/1.3. Superset soundness and the type system flavor.md>) observes a mutable-array alias breaking a Dog contract and a later readonly view retaining that bad state. It introduces the consequence; the core variance owner explains the fuller rules. Follow the generic/utility owners when you need to explain how a result was inferred or an object type was transformed.

### 3) **Configuration and execution pipelines**

Use the [verified execution comparison](<../3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>) for the first distinction between checking, transforming and running. Use [Configuration and Compiler Options](<../../../13 Configuration and Compiler Options/README.md>) for program flags, inheritance and project references. That domain is published; its options are not merely future defaults promised by this introduction.

Flags have different jobs. The [bounded erasable-toolchain lesson](<../../../13 Configuration and Compiler Options/sections/2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>) explains syntax/checking contracts alongside a real source/emitted graph. A successful syntax gate does not prove every runner or import path works. The local [pipeline project](<../3. Running TypeScript today/3.1. The compilation pipeline tsc emit declarations and source maps.md>) now generates actual JavaScript/declaration maps, observes Node stack mapping and contrasts static versus behavior failures through a separate emitter. The [syntax-choice extension](<../3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>) reuses the complete configuration graph to show optional declaration restrictions: simple unannotated exports pass while a call expression needs an annotation. Choose settings for the actual pipeline rather than assuming every listed option should be enabled together.

The checked current compiler baseline is 7.0.2. Returning readers can use the [configuration migration](<../../../25 Update TypeScript 7.0/sections/1. Configuration Migration/1.1. Configuration defaults and removed options.md>); both new and returning readers can follow the [current learning route](<../../../25 Update TypeScript 7.0/sections/6. Overlaps and Update Route/6.1. Overlaps and the current learning route.md>) at the relevant prerequisites.

### 4) **Decorators and metadata**

Decorators execute functions and may change a class or member. Their signature and compiler model belong in [Decorators and Metadata](<../../../14 Decorators and Metadata/README.md>). Start with the [two-program comparison](<../../../14 Decorators and Metadata/sections/2. Legacy and Metadata/2.1. Legacy experimental decorators compared.md>) when a legacy/standard signature fails.

Metadata requires both a producer and a consumer. The [verified metadata-channel lesson](<../../../14 Decorators and Metadata/sections/2. Legacy and Metadata/2.3. Symbol.metadata and the metadata proposal.md>) explains runtime symbol initialization, storage and transition reading. A compiler declaration of Symbol.metadata is not proof that a runtime supplies the symbol. Keep that evidence in its owner rather than describing metadata as automatically stabilized by an unrelated compiler version.

### 5) **Practice choosing the owner**

An asserted response crashes while reading name. Start with [static versus runtime checking](<../2. How TypeScript doesnt execute/2.2. Static checking vs runtime reality trust but verify.md>), because the annotation supplied trust without proving the required field. For the complete parser design, continue to [boundary parsing](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>).

A displayed type or rename result needs the actual provider and project too. The [language-service introduction](<../2. How TypeScript doesnt execute/2.3. The language server editor superpowers that justify TypeScript.md>) sends native hover/definition/rename requests and checks the applied edit. It distinguishes native LSP from historical tsserver, and preserves an unrelated local binding/string during rename; this is not a guarantee about every dynamic or external use.

A source file passes checking but cannot resolve an import when run. Start with the execution owner, then the [source/emit import strategy](<../../../12 Modules Namespaces and Declaration Files/sections/1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>), because checking and runtime resolution consume different artifacts. Neither case requires a new explanation of all JavaScript mechanics inside Fundamentals.

### 6) **Common confusion**

An ownership boundary is a learning route, not a guarantee that a bug involves only one layer. A missing runtime value can combine a declaration-space assumption, an emitted artifact and a failing property read. Name those steps, use the local reminder for the immediate diagnosis and follow the precise owner for the complete mechanism. Do not treat an annotation or syntax gate as runtime validation.

### 7) **Performance note**

These routes introduce no executable code. Erased type syntax itself supplies no runtime work, but a chosen decoder, runner, transformation or decorator can. The costs of those operations require their own evidence; a topic's placement in Fundamentals or an advanced domain does not establish a speed claim. Use the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) for a checking/build investigation.

### 8) **Mentor note**

Have the learner route the two practice failures and explain the first missing piece of evidence. A sound response identifies a required-field check in the first case and the actual source/output import graph in the second. A link without that reason is insufficient guidance; a complete re-lecture hides the useful next step. In review, retain a short causal reminder and one precise route.
