## 6.1. Common interview Q&A — fundamentals of TypeScript

### 1) **Is TypeScript a different language?** (superset vs separate language — why it matters)

**Question** — "Is TypeScript a completely separate language from JavaScript, or just tooling?"

**Answer** — Syntax-superset. Every JavaScript program is syntactically valid TypeScript; TypeScript adds checked syntax (annotations, interfaces, generics) that is erased before execution. After compilation, what runs is JavaScript with identical semantics — no runtime type system, no new primitives (except legacy `enum` which modern guidance avoids). Practical consequence: a TypeScript bug is always a JavaScript bug — the checker may have missed it because of `any`/`as`/soundness holes.

**Red flag:** "TypeScript compiles like Java compiles to bytecode" — wrong mental model; it's stripping, not translation.

---

### 2) **Where do types live?** (compile time only — erasure consequences)

**Question** — "Can I use `typeof MyInterface` or branch on a generic parameter at runtime?"

**Answer** — No. Types are erased (see [2.1. Type erasure](<../2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)). `console.log(typeof MyInterface)` is `ReferenceError` because `MyInterface` doesn't exist after emit. `Array<string>` and `Array<number>` are the same at runtime (`instanceof Array`). If you need runtime branching, add a value-level discriminant (e.g., `kind: "a" | "b"`).

**Follow-up:** "How do you validate external data then?" — `unknown` → predicate/schema → typed (see [2.2.](<../2. How TypeScript doesnt execute/2.2. Static checking vs runtime reality trust but verify.md>)).

---

### 3) **Structural vs nominal** (why class Dog is assignable to `{ name: string }`)

**Question** — "Why does `new Dog('Rex')` satisfy `{ name: string }` without `implements`?"

**Answer** — TypeScript is structural: compatibility is by *shape*, not by declaration. `Dog` has a `name: string` member, so it satisfies `{ name: string }` (see [1.3. Superset, soundness](<../1. What TypeScript is/1.3. Superset soundness and the type system flavor.md>)). Nominal-like exceptions are rare: `class` with `private`/`protected` members, or branded types (`string & { __brand }`). `implements` *checks* that a class satisfies an interface; it doesn't *make* it satisfy — removing `implements` doesn't break structural assignability.

---

### 4) **Soundness trade-offs** (examples interviewers probe for: `any`, `as`, bivariance, array covariance)

**Question** — "Is TypeScript sound? Give examples where it says safe but fails at runtime."

**Answer** — Intentionally unsound where strictness would make idiomatic JavaScript untypable (see [1.3.](<../1. What TypeScript is/1.3. Superset soundness and the type system flavor.md>)):

- `any` is compatible with everything and erases downstream errors.
- `value as T` trusts the caller; if `T` is wrong, runtime fails.
- `Dog[]` → `Animal[]` is covariant; `animals.push(new Cat())` then violates `Dog[]` at runtime.
- Method shorthand `m(x: Animal)` is checked bivariantly under `strictFunctionTypes` for methods (function values are stricter).

**Strong answer includes:** "Each unsoundness is a pragmatic trade-off — `any`/`as` exists for migration and boundaries; bivariance/array covariance exist because invariant arrays would require massive generics."

---

### 5) **Type erasure and execution paths** (classic vs tsx vs native stripping)

**Question** — "How do you run TypeScript, and what's the difference between `tsx` and Node's native stripping?"

**Answer** — Three paths: (a) `tsc` → `node dist` (emit, faithful), (b) `tsx`/`ts-node` (hook loader, transpile on import, fast for dev), (c) native stripping (`node --experimental-strip-types`, Node 22.12+ — zero transform, only erasable syntax). Stripping doesn't check; `tsx` transpiles non-erasable `enum` but stripping rejects it. Always pair any JIT path with `tsc --noEmit` in CI (see [3.2.](<../3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>)). Enable `erasableSyntaxOnly` to fail fast on non-erasable files.

---

### 6) **Boundary validation** (the parsing question)

**Question** — "How do you handle API responses in a typed codebase?"

**Answer** — Treat every external source as `unknown`, validate with a predicate or schema (`zod`, `valibot`), and only then treat it as the target type. `as` at the `fetch` boundary is the anti-pattern; `unknown` → `isUser` → `User` is the pattern (see [2.2.](<../2. How TypeScript doesnt execute/2.2. Static checking vs runtime reality trust but verify.md>) and pitfalls [5.1.](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by misunderstanding fundamentals.md>)).
