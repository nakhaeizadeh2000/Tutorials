## 6.1. Common interview QA fundamentals of TypeScript

### 1) **Is TypeScript a different language or tooling for JavaScript?**

TypeScript adds static type syntax and tooling to JavaScript. Type annotations describe contracts to the checker; they do not create a runtime type system. Emission can also rewrite syntax according to compiler options, so “everything is only stripped” is too broad. Identify the actual compiler/runtime path and inspect its output when that distinction matters.

A strong answer connects this to an observable consequence: asserting an API response as User does not validate the response. The runtime executes JavaScript and the application's explicit checks. The [execution lesson](<../3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>) distinguishes checking, transpilation and stripping with actual probes.

### 2) **Can you inspect an interface or generic parameter at runtime?**

An interface or type parameter supplies no runtime value. TypeScript rejects using an interface in a value expression with TS2693. However, the JavaScript operator selected for an unbound name matters: typeof returns the string `undefined`, while a direct read throws ReferenceError. Neither result means that the erased interface became a runtime validator.

To observe the distinction, use TypeScript 7.0.2 and Node 20.20.2 in a directory without a tsconfig. Save `typeof.ts`:

```typescript
interface MyInterface { name: string }
console.log(typeof MyInterface);
```

Save a separate `direct.ts`:

```typescript
interface MyInterface { name: string }
console.log(MyInterface);
```

Run each compiler command separately. Both are intentional failures:

```bash
tsc --strict --target es2022 --module commonjs --lib es2022,dom --outDir typeof typeof.ts
tsc --strict --target es2022 --module commonjs --lib es2022,dom --outDir direct direct.ts
```

Both report TS2693 and exit 2. Under the observed default emission policy they also produce JavaScript. Run that output only to inspect the failure behavior:

```bash
node typeof/typeof.js
node direct/direct.js
```

The first prints `undefined`, exit 0. The second throws ReferenceError, exit 1. The [ECMAScript typeof rule](https://tc39.es/ecma262/multipage/ecmascript-language-expressions.html#sec-typeof-operator) has a special case for an unresolvable reference. It does not suppress every reference failure, such as accessing a lexical binding before initialization. For an actual runtime branch, use a value discriminant or an explicit parser; the type-only name cannot choose it.

### 3) **Why can a class instance satisfy an interface without implements?**

For ordinary public members, compatibility depends on the required shape. A Dog instance with `name: string` can satisfy `{ name: string }` because the member is present with a compatible type. An implements clause asks the checker to verify that contract at the class declaration; it does not create runtime membership in an interface.

A stronger answer identifies relevant boundaries: private/protected member provenance can restrict class compatibility, and branded types add a static distinction between otherwise similar values. Those cases belong in the [structural model](<../../../02 The Type System Core/sections/1. Structural typing/1.1. Structural assignability shape not name.md>) and [branding owner](<../../../02 The Type System Core/sections/1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>), rather than a second complete treatment here.

### 4) **Can accepted TypeScript still fail at runtime?**

Yes. Explicit any bypasses checks, assertions trust the author, and an incorrect predicate can mislead subsequent narrowing. Mutable array covariance can also let a broader alias insert a value incompatible with the original narrower array. Explain the particular trusted claim or mutation path rather than saying every accepted program is safe.

For callback parameters, strictFunctionTypes treats function properties more strictly than method declarations. The [primary strict-function notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-6.html) explain the method exception. A strong answer connects the rule to a consequence and a suitable boundary, such as a readonly parameter for a reader that does not need mutation. That view does not freeze all aliases of the array.

### 5) **How do tsc runners and native stripping differ?**

The important questions are who checks, who emits/transforms and who executes. A classic build checks/emits with tsc and runs the generated JavaScript with Node. The tested tsx setup transpiles without a whole-project check; the tested ts-node setup checks unless configured for transpile-only. Node 22.18.0 runs supported erasable TypeScript with default stripping and does not type-check it. Its strip-only path rejects enum syntax.

Use the pinned projects and meaningful type-error/enum/decorator cases in [running TypeScript](<../3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>). Avoid promising that a syntax gate makes every loader, dependency or runtime graph compatible. A sound answer names the tested versions and a separate checking gate when execution alone does not provide it.

### 6) **How should a typed application handle an API response?**

Treat the response as unknown until runtime checks establish the required contract. For a User with id and name, checking only name is insufficient. A predicate's return annotation does not prove its own implementation; exercise valid and malformed cases, including missing fields and error envelopes. If parsing an array, element checks must account for the chosen presence/iteration contract.

The [pitfalls exercise](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by misunderstanding fundamentals.md>) demonstrates these exact failures with local fake responses and sparse arrays. A strong interview answer explains the checks and their limits instead of replacing one assertion with an unverified predicate.

### 7) **Common confusion**

Type erasure and the behavior of a JavaScript expression are separate questions. The checker rejects an interface used as a value, but the emitted typeof expression has the operator's unbound-name behavior. Similarly, implements does not add runtime validation, and a successful runner invocation does not necessarily mean type checking occurred. State which observation belongs to which layer.

### 8) **Performance note**

Interfaces and type parameters erase; they do not add a runtime registry to inspect. Actual validators, discriminant checks and selected execution tools perform runtime or build work. No runner-speed or validation-latency measurement was made in this interview lesson, so a good answer should avoid rankings based on those erased annotations. Use the measured build lesson when making a timing claim.

### 9) **Mentor note**

Ask the candidate to predict the diagnostic and runtime outcome separately for each interface probe. Then ask which malformed response would expose an incomplete predicate. A strong answer distinguishes static rejection, default emission and the selected JavaScript operation, and supplies a test that could disprove the proposed validation claim. Reward that reasoning over terminology alone.
