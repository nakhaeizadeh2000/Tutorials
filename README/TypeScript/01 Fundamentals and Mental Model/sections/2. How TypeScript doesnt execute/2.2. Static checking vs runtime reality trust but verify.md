## 2.2. Static checking vs runtime reality — trust but verify

### 1) **The checker is a proof assistant, not a runtime guard** (it proves consistency assuming inputs honor their types)

**Definition** — The TypeScript checker verifies that *if* every value matches its declared type, then the program doesn't misuse those values. It does not insert runtime checks to ensure the premise is true. Any data entering the type system without proof (network response, `JSON.parse`, `process.env`, `any`, `as` assertion) is trusted blindly.

Mental model: the checker is a proof of the form "assuming `user` is `User`, then `user.name.toUpperCase()` is safe". If `user` is actually `{ name: undefined }` coming from a mis-typed API response, the proof's premise was false and no runtime error is prevented.

### 2) **Boundary validation is mandatory** (any data from outside the type system must be validated at runtime)

Three untrusted boundaries dominate production bugs:

| Boundary | Inferred type without validation | What to do |
|---|---|---|
| `fetch` / `axios` response | `any` or `unknown` → developer writes `as ApiUser` | Parse with a validator: `zod`, `valibot`, or manual `isApiUser` predicate |
| `JSON.parse` | `any` | Same — never `as` the result of `JSON.parse` |
| `localStorage`, `process.env`, `URLSearchParams` | `string \| null \| undefined` | Validate presence and shape before narrowing |

Modern guidance — parse, don't assert: `unknown` → *validated* → typed. A type predicate `value is T` bridges the runtime proof and the static type.

### 3) **Soundness holes are documented, not accidental** (trade-offs for usability)

As seen in [1.3. Superset, soundness](<../1. What TypeScript is/1.3. Superset soundness and the type system flavor.md>), TypeScript is intentionally unsound where strictness would make common JavaScript untypable. Each hole is a place where the checker says "safe" but runtime can still fail — treat them as budgeted risks, not surprises.

### 4) **Runnable example** — trusted `as` vs validated predicate (good + bad)

```typescript
// bad — trusting an external boundary with 'as'
type ApiUser = { id: number; name: string };
async function fetchUserBad(id: number): Promise<ApiUser> {
  const res = await fetch(`https://api.example.com/users/${id}`);
  const data = (await res.json()) as ApiUser; // ❌ trusts the server — checker is silent, runtime may be { error: "not found" }
  return data; // caller does data.name.toUpperCase() — may throw "Cannot read property 'toUpperCase' of undefined"
}

// good — validating at the boundary with a type predicate (erasable, but bridges to runtime)
type ApiUser = { id: number; name: string };

function isApiUser(value: unknown): value is ApiUser {
  return (
    typeof value === "object" &&
    value !== null &&
    "id" in value &&
    "name" in value &&
    typeof (value as Record<string, unknown>).id === "number" &&
    typeof (value as Record<string, unknown>).name === "string"
  );
}

async function fetchUserGood(id: number): Promise<ApiUser> {
  const res = await fetch(`https://api.example.com/users/${id}`);
  const data: unknown = await res.json(); // unknown forces validation
  if (!isApiUser(data)) throw new Error("Invalid API response shape");
  return data; // now proven ApiUser — checker and runtime agree
}

// good with zod (idiomatic in 2026):
// import { z } from "zod";
// const ApiUserSchema = z.object({ id: z.number(), name: z.string() });
// const data = ApiUserSchema.parse(await res.json()); // throws if shape mismatches, returns typed ApiUser
```

### 5) **Common confusion**

- "If the checker says it's safe, I can skip runtime validation" — only safe *for values that actually honor their types*. External data never honors its type until you validate it.
- "Adding `!` (non-null assertion) fixes the maybe-null" — it silences the checker; it doesn't prove non-null at runtime. Prefer narrowing (`if (x != null)`) or validation.
- "Type assertions `as` allocate or convert" — they disappear after erasure (see [2.1. Type erasure](<./2.1. Type erasure what survives compilation.md>)); they never guard.

### 6) **Performance note**

Validation has a cost (O(n) over the shape), so apply it once at the boundary, not per-field on every function call. The pattern `unknown → validate → typed` pays that cost exactly once, then downstream code runs at zero type-check overhead. Don't sprinkle `zod.parse` inside hot loops — validate at the edge and pass typed values inward.

### 7) **Mentor note**

Teach "every `as` is a TODO": ask students to justify each assertion by pointing to a *proof* elsewhere (a predicate, a schema, a prior narrow). If they can't point to a proof, the assertion is a bug waiting to happen. Code review checklist: count `as` per PR; high counts correlate with boundary-validation gaps. Prefer `satisfies` and predicates; reserve `as` for tested boundaries.
