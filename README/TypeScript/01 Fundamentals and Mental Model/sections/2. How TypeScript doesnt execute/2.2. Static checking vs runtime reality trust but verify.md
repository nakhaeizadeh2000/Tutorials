## 2.2. Static checking vs runtime reality — trust but verify

### 1) **Checking a contract does not install a runtime guard**

A TypeScript type describes what code may assume about a value. The checker uses that description to diagnose incompatible operations before execution. An annotation or assertion does not inspect a network response, convert a field or insert a runtime guard. If a response is an error envelope rather than the declared User, accessing its name can still fail.

It is useful to ask what evidence supports each assumption. A checked object literal supplies different evidence from an unchecked JSON result. TypeScript is also deliberately unsound in some compatibility rules, so successful checking is not a mathematical proof that every execution is safe. The [soundness introduction](<../1. What TypeScript is/1.3. Superset soundness and the type system flavor.md>) explains that design choice.

An `as ApiUser` assertion tells the checker to use a type; it neither validates nor constructs ApiUser at runtime. Keep uncertain boundary values as unknown while inspecting them. The [narrowing reference](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#using-type-predicates) explains how conditions affect the checked type. The implementation of a declared predicate is still your responsibility.

### 2) **Verify the boundary with actual inputs**

Use TypeScript **7.0.2 / Node 20.20.2**, verified 2026-10-13. This small contract requires a finite numeric id and a string name. It does not require a positive integer or a nonempty name; those would be additional domain rules. Save `boundary.ts` in a directory without a tsconfig:

```typescript
type ApiUser = { id: number; name: string };
type RequestLike = (id: number) => Promise<{ json(): Promise<unknown> }>;

function isApiUser(value: unknown): value is ApiUser {
  return typeof value === "object" && value !== null
    && "id" in value && typeof value.id === "number" && Number.isFinite(value.id)
    && "name" in value && typeof value.name === "string";
}
async function fetchUserBad(id: number, request: RequestLike): Promise<ApiUser> {
  const response = await request(id);
  return await response.json() as ApiUser;
}
async function fetchUserGood(id: number, request: RequestLike): Promise<ApiUser> {
  const response = await request(id);
  const raw: unknown = await response.json();
  if (!isApiUser(raw)) throw new Error("Invalid API response shape");
  return raw;
}
async function main(): Promise<void> {
  const payloads: unknown[] = [
    { id: 1, name: "Ada" }, { name: "Ada" }, { id: "1", name: "Ada" },
    { id: 1, name: 42 }, null, { error: "not found" }, { id: NaN, name: "Ada" },
  ];
  for (const payload of payloads) {
    const fake: RequestLike = async () => ({ json: async () => payload });
    try {
      const user = await fetchUserGood(1, fake);
      console.log("checked:", user.id, user.name.toUpperCase());
    } catch (error: unknown) {
      if (!(error instanceof Error)) throw error;
      console.log(error.message);
    }
  }
  const invalid: RequestLike = async () => ({ json: async () => ({ error: "not found" }) });
  try { console.log((await fetchUserBad(1, invalid)).name.toUpperCase()); }
  catch (error: unknown) {
    if (!(error instanceof TypeError)) throw error;
    console.log("asserted: TypeError");
  }
}
void main().catch((error: unknown) => { throw error; });
```

One ApiUser alias serves both paths. The request function is an injected local fake, so the example needs no HTTP service. The bad path asserts the response; the good path reads unknown and checks both required fields. Run:

```bash
tsc --strict --target es2022 --module commonjs --lib es2022,dom --outDir dist boundary.ts
node dist/boundary.js
```

Both commands exit 0. Output:

```text
checked: 1 ADA
Invalid API response shape
Invalid API response shape
Invalid API response shape
Invalid API response shape
Invalid API response shape
Invalid API response shape
asserted: TypeError
```

The valid input reaches the caller; missing id, string id, numeric name, null, an error envelope and NaN are rejected before the caller uses the record. The asserted error envelope reaches the unsafe field access, which throws the caught TypeError. A successful checker run did not distinguish those runtime results by itself.

The same boundary principle applies to parsed JSON, files and user input. Validate the values the application actually depends on, and choose how rejection is reported. Presence/shape checking is not authentication or an HTTP-status check; those need their own contracts. A parser may also normalize or copy a record when downstream ownership requires it. The [parse-boundary owner](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>) develops that architecture; the [fundamentals pitfalls](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by misunderstanding fundamentals.md>) adds array and artifact failure cases.

### 3) **Treat soundness holes as explicit assumptions**

Assertions, any, mutable aliases and permissive compatibility rules can undermine an assumption after checking. A predicate declaration can also promise more than its body verifies. [Dan Vanderkam's predicate analysis](https://effectivetypescript.com/2024/02/27/type-guards/) motivates testing the rejected path as well as the accepted path; do not judge a guard solely by its annotated return type.

A controlled exercise exposes that distinction. Remove only the id-check line from isApiUser and rebuild. The checker still accepts its `value is ApiUser` declaration. The altered runtime accepts `{ name: "Ada" }` and prints `checked: undefined ADA`; it also admits other id values the original contract rejected. Restore the complete check. The consequence is missing evidence in the predicate body, not a need for a stronger assertion at the caller.

A record checked now can also be changed later through another reference. Define ownership and mutation rules rather than treating a passed guard as a permanent runtime lock. Use the [type-system risk owner](<../../../02 The Type System Core/sections/3. Soundness and variance/3.3. Unsound by design spots budgeted risks.md>) for the detailed array and callback mechanisms.

### 4) **Common confusion**

Unknown forces a checked use, but it does not automatically make the checks correct. A declaration such as `value is ApiUser` is a promise which the checker uses for narrowing. The incomplete-guard experiment shows why its runtime behavior must be verified.

Neither a non-null assertion nor a type assertion fixes a malformed value. Their type syntax is erased. A condition can supply runtime evidence; a schema/parser can supply an agreed conversion and rejection policy. Choose the smallest mechanism that establishes the actual contract, and keep any assumptions it leaves visible.

### 5) **Performance note**

The type annotations and assertions add no runtime validation code. The predicate's ordinary JavaScript operations do execute: this fixture checks a fixed pair of fields, while a parser for a large collection may traverse its elements. No timing measurement or universal cost formula is claimed. Validate where data first enters the relevant contract, then pass that result through an ownership model that preserves the assumptions; rechecking can still be necessary after mutation or another external boundary.

### 6) **Mentor note**

Ask the learner to predict what happens to the error envelope through each function, then trace where rejection occurs. Ask which input exposes the missing id check even though name.toUpperCase succeeds. A sound answer notices that checking only the next expression's field is weaker than validating the returned ApiUser contract.

During review, ask for the contract, the evidence and the failure policy for each boundary. An assertion count is not proof of safety or a defect quota. Require meaningful valid/malformed cases and name integrations the local fixture did not exercise, such as real HTTP status and transport failures.
