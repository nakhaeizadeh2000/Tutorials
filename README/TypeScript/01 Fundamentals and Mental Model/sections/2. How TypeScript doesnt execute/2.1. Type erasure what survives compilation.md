## 2.1. Type erasure — what survives compilation

### 1) **All type syntax disappears** (annotations, interfaces, type aliases, generics leave no trace)

**Definition** — *Type erasure* means the TypeScript compiler removes every type-level construct before emitting JavaScript. The emitted `.js` contains zero runtime artifacts of the type system. This is the single most important fact for reasoning about TypeScript: types exist to be checked, then vanish.

What is erased: `: Type` annotations, `interface` declarations, `type` aliases, generic parameters `<T>`, `as` assertions, `satisfies`, `!` non-null assertions, `declare` modifiers.

What is *not* erased: JavaScript values, class bodies (minus type annotations), function bodies, and — historically — constructs that required emit (`enum`, legacy `namespace`, parameter properties). Those are the *non-erasable* exceptions modern guidance avoids (see [3.3. Choosing erasable syntax](<../3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>)).

### 2) **Only value-level constructs survive** (values, function bodies, `enum` caveat)

Consider what the checker sees vs what Node.js runs:

```typescript
// Input (what you write):
interface User { id: number; name: string; }
type Result<T> = { ok: true; value: T } | { ok: false; error: string };
function getName(user: User): string { return user.name; }
const x: Result<number> = { ok: true, value: 42 };
```

After `npx tsc --target es2022`, the emitted JavaScript is:

```javascript
function getName(user) { return user.name; }
const x = { ok: true, value: 42 };
```

No `interface User` remains, no `Result<number>` remains, no `: string` remains. The function body is identical.

### 3) **Erasable syntax rule** (modern guidance as of TypeScript 5.9 era)

TypeScript 5.8 introduced `--erasableSyntaxOnly` (enabled via `--erasableSyntaxOnly: true` in `tsconfig.json`). When on, any construct that requires non-trivial emit fails the check:

- `enum E { A, B }` → error: `enum` requires emit (use union `type E = "A" | "B"` instead)
- `namespace N { export const x = 1; }` → error: legacy namespace requires IIFE emit
- `class C { constructor(public x: number) {} }` → error: parameter property requires emit (write explicit `this.x = x`)

**Modern guidance** — enable `erasableSyntaxOnly` in new projects so your `.ts` files can be executed by *stripping* types alone (Node.js 22.12+ native stripping, or `tsx`/`ts-node --transpile-only`). This guarantees zero runtime cost and zero emit-time surprises.

### 4) **Runnable example** — erased vs emitted (good + bad)

```typescript
// good — erasable: stripping types is sufficient, no transform needed
// file: good.ts
interface Config { host: string; port: number; }
type Port = number & { __brand: "Port" };
function connect(cfg: Config): void {
  console.log(`connecting to ${cfg.host}:${cfg.port}`);
}
const cfg: Config = { host: "localhost", port: 5432 };
connect(cfg);
// emit: function connect(cfg) { console.log(`connecting to ${cfg.host}:${cfg.port}`); } — identical logic

// bad — non-erasable: requires a transform, breaks stripping
// file: bad.ts
// enum Direction { Up, Down, Left, Right } // error under erasableSyntaxOnly
// console.log(Direction.Up); // would have emitted an IIFE object at runtime
// fix: use union + const object (erasable)
const Direction = { Up: "Up", Down: "Down", Left: "Left", Right: "Right" } as const;
type Direction = typeof Direction[keyof typeof Direction]; // "Up" | "Down" | "Left" | "Right"
console.log(Direction.Up); // "Up" — value exists at runtime, type is erasable
```

### 5) **Common confusion**

- "Generics exist at runtime like Java's reified generics" — no. `Array<string>` and `Array<number>` are indistinguishable after erasure; `instanceof Array` is the same check for both. Runtime branching on generic parameters requires explicit value-level tags.
- "Type assertions `as` do a cast at runtime" — no. `value as string` disappears; it doesn't validate or convert. If `value` is actually a number, you will get a runtime type error later *outside* the assertion.
- "`interface` generates a validator" — no. `interface` is a compile-time shape description; use a runtime validator (`zod`, `valibot`, manual guard) for boundary checks (see next leaf [2.2. Static vs runtime](<./2.2. Static checking vs runtime reality trust but verify.md>)).

### 6) **Performance note**

Erasable files avoid the *transform* phase entirely under native stripping. In a 500-file project, stripping-only execution (Node `--experimental-strip-types` as of Node 22.12) can cold-start ~40% faster than `ts-node` transpile, because no AST rewrite is needed beyond removing annotations. Measure `node --experimental-strip-types app.ts` vs `tsx app.ts` startup for your repo.

### 7) **Mentor note**

Repetition that matters: say it on day one and again before every advanced topic — *types don't exist at runtime*. Students who internalize this stop expecting `typeof` to reveal a type alias and start designing explicit runtime validators. Quiz probe: "What does `console.log(typeof MyInterface)` do?" — correct answer: "ReferenceError, because `MyInterface` was erased."
