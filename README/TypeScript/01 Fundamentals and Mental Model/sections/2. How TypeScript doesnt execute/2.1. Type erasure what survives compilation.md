## 2.1. Type erasure — what survives compilation

### 1) **Inspect executable output separately from declarations**

Type erasure removes static descriptions from executable JavaScript. Parameter annotations, interfaces, type aliases and generic type parameters do not become validators or runtime type arguments. Actual values and function bodies still need to execute, and the selected emitter can also transform syntax according to its target/module settings. Erasure therefore does not imply output identical to source with a few characters deleted.

Use TypeScript **7.0.2** and Node **20.20.2** for emitted JavaScript, verified 2026-10-17. Create a fresh directory without a config or dependencies. Save `erased.mts`:

```typescript
export interface User { name: string }
export type Box<T> = { value: T };
export function identity<T>(value: T): T { return value; }
const box: Box<User> = { value: { name: "Ada" } };
console.log(identity(box).value.name);
```

The interface describes name, Box describes a value property, and identity preserves its input's checked type. None of those descriptions constructs a User or Box runtime object; the object literal supplies the actual value. Run:

```bash
tsc --strict --target es2022 --module nodenext --rootDir . --outDir dist --noEmitOnError --declaration --erasableSyntaxOnly erased.mts
node dist/erased.mjs
```

Both exit 0 and runtime prints Ada. Inspect the two generated files. dist/erased.mjs contains identity's ordinary function, the object literal and console call, with no interface, type alias or generic parameter. dist/erased.d.mts still describes User, Box<T> and identity<T> for a checker consumer. A declaration artifact can retain types without creating an executable provider for those names. The [declaration owner](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.1. Authoring d.ts public API surface.md>) develops that boundary.

Calling identity does not supply a hidden runtime T. If an operation needs a runtime tag, constructor or validation rule, pass or implement an actual value. Likewise an `as` assertion does not convert the value. The [goal/boundary experiment](<../1. What TypeScript is/1.2. Design goals and non-goals what TypeScript intentionally does not do.md>) compiles a false assertion and observes the resulting runtime failure.

### 2) **Observe constructs that need runtime transformation**

Some TypeScript syntax has value-level consequences that cannot be implemented by merely deleting type text. Save `values.mts`:

```typescript
enum Status { Ready, Done }
namespace Group { export const label = "group"; }
class Holder { constructor(public value: number) {} }
console.log(Status.Ready, Group.label, new Holder(7).value);
```

Here the enum supplies a runtime object, the namespace groups a runtime label, and the constructor parameter property creates an instance property as well as accepting a parameter. These are different from the erased interface and alias. Run:

```bash
tsc --strict --target es2022 --module nodenext --rootDir . --outDir dist-values --noEmitOnError values.mts
node dist-values/values.mjs
tsc --strict --target es2022 --module nodenext --noEmit --erasableSyntaxOnly values.mts
```

The first two commands exit 0; runtime prints `0 group 7`. Inspect the emitted enum/group initialization and Holder property. The last command deliberately fails with TS1294 at the three restricted forms. They work in the declared emitting path, while this syntax gate rejects them for a different pipeline contract. Replacing an enum with a const object/string union can change numeric values or reverse mapping, so it is a design change to verify rather than an automatically equivalent edit.

Native source stripping is another path. The following pinned **Node 22.18.0** command intentionally fails on the enum with ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX:

```bash
npm exec --yes --package=node@22.18.0 -- node values.mts
```

This observes unsupported transformation syntax, not a type-checking diagnostic. It does not establish support for every other TypeScript or JavaScript form. The [execution owner](<../3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>) supplies fuller pinned runner comparisons.

### 3) **Keep the erasure gate's promise bounded**

The [erasableSyntaxOnly reference](https://www.typescriptlang.org/tsconfig/erasableSyntaxOnly.html) restricts particular TypeScript forms, including runtime namespaces, parameter properties, non-ECMAScript import/export assignments and prefix-style assertions. A namespace containing only types differs from runtime Group above. It is not a rule that every construct needing any rewrite for any target must fail.

For a direct contrast, save `fields.mts`:

```typescript
class Counter { value = 1; }
console.log(new Counter().value);
```

Run with an older JavaScript emission target:

```bash
tsc --strict --target es2015 --module nodenext --rootDir . --outDir dist-fields --noEmitOnError --erasableSyntaxOnly fields.mts
node dist-fields/fields.mjs
```

Both exit 0; runtime prints 1. Inspect the constructor-based property initialization in the output. The ordinary JavaScript class field passed the erasure gate while the target still required downlevel emission. Syntax restrictions do not eliminate every transformation or prove a loader/API works. The [configuration owner](<../../../13 Configuration and Compiler Options/sections/2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>) contains the full flag inventory and actual source/output graph; keep its broader configuration there.

### 4) **Common confusion**

An erased type name is not a runtime binding. There is also a difference between directly reading an absent JavaScript identifier and applying typeof to it. In fresh Node processes, these plain JavaScript commands demonstrate the distinction:

```bash
node --input-type=module -e 'console.log(typeof AbsentTypeName)'
node --input-type=module -e 'console.log(AbsentTypeName)'
```

The first prints undefined and exits 0; the second exits 1 with ReferenceError. Using an interface as a value in TypeScript also has a compiler diagnostic. The [fundamentals interview experiment](<../6. Interview questions and answers/6.1. Common interview QA fundamentals of TypeScript.md>) observes the checked and emitted cases separately. Do not answer a question about typeof with a direct-read result.

Generic arguments describe static relationships rather than runtime element validation. A runtime array test does not verify that every element satisfies a string type. Use explicit data checks where that is the intended contract; erasure alone neither validates nor makes incorrect data safe.

### 5) **Performance note**

The erased descriptions above add no runtime validation. The object creation, function call, enum/group initialization and property operations remain actual work. Stripping still needs source processing, and a syntax flag does not establish startup speed, bundle size or a percentage improvement over another runner. No benchmark was run here. Preserve semantics and compare the actual runtime/tool versions, graph and workload before making a performance claim.

### 6) **Mentor note**

Ask the learner to identify which names exist in executable JavaScript and which appear only in the declaration artifact. Then compare values.mts's successful emitter path with its rejected stripping path. A sound answer explains what runtime behavior the transform supplied.

Use fields.mts to challenge “the gate bans every rewrite.” Finish with the two absent-name commands and require separate answers for typeof, direct access and TypeScript checking. The goal is to attribute each observed result to the checker, emitter or JavaScript runtime rather than repeating “types disappear” as an explanation for every failure.
