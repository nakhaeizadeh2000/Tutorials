## 2.3. The language server — editor superpowers that justify TypeScript

### 1) **tsserver powers the IDE** (autocompletion, go-to-definition, rename, hover types — all from the same type graph)

**Definition** — `tsserver` is the TypeScript language server: a long-running process that parses your project, builds the type graph via the same checker that `tsc` uses, and answers editor queries. Every hover type, completion list, rename, and quick fix you see in VS Code (and other LSP clients) is a *query* against that graph — not a text search.

Capabilities that justify the adoption cost:

- **Hover shows the computed type** — not just the annotation. If `const x = [1, 2, 3] as const` is hovered, the server shows `readonly [1, 2, 3]`, not `number[]`.
- **Go-to-definition crosses files and re-exports** — follows the module graph, not file names.
- **Rename symbol is semantics-aware** — renames only bindings that resolve to the same symbol, ignoring same-named shadowing.
- **Refactor and quick fix** — `Extract function`, `Add missing import`, `Implement interface` are type-driven transforms.

### 2) **Project references and incremental builds** (the language server understands your monorepo graph)

Large repositories split into projects (`projectReferences` in `tsconfig.json`). The server checks each project independently and rechecks only dependents when a dependency changes. `isolatedDeclarations` (see [3.3. Choosing erasable syntax](<../3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>)) requires explicit return types on exports so each file's `.d.ts` can be generated in parallel without reading other files — a prerequisite for scalable language-server performance.

### 3) **Types as documentation** (hover is the primary reading surface)

In a TypeScript codebase, the *authoritative* documentation for a function is its hover type, not its JSDoc. Good API design shows up as a concise, readable hover; complex conditional types that expand to 80-line tooltips signal an API that needs simplification (see [09 Utility Types textual forward](../../09%20Utility%20Types%20and%20Type%20Transformations/README.md) for shaping hovers).

### 4) **Runnable example** — hovering reveals computed, not annotated, types

```typescript
// file: hover-demo.ts
// Hover each variable in your editor to see the computed type — the annotation is not the story

const nums = [1, 2, 3];                // hover: number[]          (inferred, mutable)
const tuple = [1, 2, 3] as const;       // hover: readonly [1,2,3]  (literal, readonly)
type User = { id: number; name: string };
declare const users: User[];
const names = users.map(u => u.name);   // hover: string[]          (generic inference from participants)

function pluck<T, K extends keyof T>(obj: T, key: K): T[K] { return obj[key]; }
const n = pluck({ name: "Ada", age: 36 }, "name"); // hover: string (T[K] computed from call site)

// Refactoring demo: rename 'name' on User — every pluck(users[i], "name") and { name: ... } is updated
// via the type graph, not text search.
```

### 5) **Common confusion**

- "The editor uses a simpler checker than `tsc`" — it uses the *same* checker (or a project-references subset). A file that passes in the editor should pass `tsc --noEmit`; a mismatch usually means `tsconfig.json` `include`/`exclude` globs differ from the editor's file set.
- "Hover types are always accurate" — they can show `any` when declaration files are missing (`@types/node` not installed, `skipLibCheck: false` surfacing upstream errors). Fix the declaration graph, not the hover.
- "Language server performance doesn't matter if `tsc` is fast" — `tsc` is a batch job; the server is interactive. A project that checks in 5s but has a 2s hover latency feels broken — `projectReferences` + `isolatedModules` matter more for server responsiveness than raw check time.

### 6) **Performance note**

Hover for large unions (e.g., `type Props = A & B & C & DiscriminatedUnion<200>`) can expand to thousands of characters and slow completions by 40%. Prefer named intermediate types and `Omit`/`Pick` composition over giant inline intersections — the server memoizes named aliases, not anonymous intersections (see also [09 Utility Types](../../09%20Utility%20Types%20and%20Type%20Transformations/README.md)).

### 7) **Mentor note**

Teach students to *read the hover*, not the annotation. Ask "what does the editor show when you hover this variable?" — that habit surfaces `any` leaks and widened literals immediately. Review exercise: open a file, hover every exported function, and flag any return type that expands beyond one line.
