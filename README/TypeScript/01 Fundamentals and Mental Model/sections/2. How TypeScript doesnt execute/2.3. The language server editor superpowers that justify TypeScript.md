## 2.3. The language server — editor superpowers that justify TypeScript

### 1) **Identify the provider and the requested operation**

A language service answers questions about a program: the type at a position, the declaration an identifier refers to, its selected references or edits for a rename. The editor sends requests and presents results. Static information can make those operations more useful than raw text replacement, but the actual provider, document state and project determine their scope.

Historical TypeScript tsserver is a Node-based service with its own protocol. Native TypeScript **7.0.2** supplies an LSP service; the verified launcher is `tsc --lsp --stdio`. LSP means Language Server Protocol. Launching it alone does not perform a hover or configure your editor. Choose a compatible client/provider and inspect its actual version. A separate compiler command can use a different version, configuration or saved document from the editor's open buffer. The [native compatibility owner](<../../../25 Update TypeScript 7.0/sections/2. Editor and Tool Compatibility/2.1. Editor and tool API compatibility.md>) explains those interfaces.

For this introductory workspace use native TypeScript 7.0.2 and Node **20.20.2**, verified 2026-10-17. Create a fresh directory and save `tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "lib": ["es2022", "dom"],
    "types": [],
    "rootDir": ".",
    "outDir": "dist",
    "noEmitOnError": true
  },
  "files": ["core.mts", "app.mts"]
}
```

Save `core.mts`:

```typescript
export interface User { name: string }
/** Format a greeting; this function performs no network request. */
export function greet(user: User): string { return `hi ${user.name}`; }
```

Save `app.mts`:

```typescript
import { greet } from "./core.mjs";
import type { User } from "./core.mjs";
const user: User = { name: "Ada" };
const names = [user].map(value => value.name);
const marker = "greet";
function local(): string {
  const greet = "local";
  return greet;
}
console.log(greet(user), names.join(","), marker, local());
```

Run:

```bash
tsc -p tsconfig.json
node dist/app.mjs
```

Both exit 0; runtime prints `hi Ada Ada greet local`. Every value used at runtime has an implementation; no ambient users array is assumed. The output-extension imports describe this emitted Node path.

### 2) **Compare service results, checked types and an applied edit**

Open the workspace with the intended TypeScript provider. Use hover on names and marker, follow the greet call to its definition, and preview renaming the exported greet to welcome. Review the edit before applying it, then rebuild and run. The verification here sent actual native LSP requests and applied their returned edit in a disposable copy; editor UI rendering was not automated.

| Native operation in this workspace | Observed result and limit |
|---|---|
| Hover on names | Displays string[]. This is presentation of a checked inferred type, not an element validator. |
| Hover on marker | Displays the const literal type "greet". A scalar const does not mean every nested object would become readonly. |
| Definition from the greet call | Targets its implementation in core.mts. Available declaration files can instead supply descriptive targets in other projects. |
| Rename exported greet to welcome | Updates its declaration, import and call; the unrelated local greet and string marker remain. |
| Build/run after applying returned rename | Still prints `hi Ada Ada greet local`. This exercises the edited graph, not every external consumer. |

For a separate static probe, append `const wrong: number[] = names;`. Checking fails TS2322, consistent with the displayed string array. Restore the line before rebuilding. A hover string, type probe and executed result are complementary observations, not interchangeable tests.

Renaming a symbol does not mean replacing every same-named property or string. Reflection, serialized names, dynamic access and external users need review appropriate to the API. The [rename/code-action owner](<../../../16 Tooling Language Server and Ecosystem/sections/1. Language Server in Practice/1.2. Rename refactorings and code actions.md>) applies real edits and also demonstrates an organize-imports change losing required initialization. A suggested edit still needs semantic judgment and relevant verification.

### 3) **Read types alongside meaning and project scope**

Hover can show an inferred or declared type, documentation and provider-specific formatting. It is useful for understanding a value's checked contract, but does not make a declaration truthful or replace documentation about side effects, units, errors and completion. The greeting comment above distinguishes formatting from a network request; the return type alone cannot express that distinction. A multiline type is not automatically bad API design, and a one-line type can hide any or an incorrect assumption.

A service uses configured and inferred projects, imports and open documents according to its implementation/client. Project references use the references field in a configuration; they do not promise one server per project, exactly which source is rechecked after every edit or independent process restarts. isolatedDeclarations concerns declaration-generation restrictions and is not a prerequisite for basic hover, rename or language-service scalability. Its exact behavior belongs to [configuration](<../../../13 Configuration and Compiler Options/README.md>).

When CLI and editor disagree, first compare the executable/provider, project, options and actual document contents. The [debugging owner](<../../../16 Tooling Language Server and Ecosystem/sections/3. Debugging and Ecosystem/3.1. Debugging tsserver logs and responsiveness.md>) requests an actual diagnostic from an unsaved changed buffer while the original disk file compiles. Those results are consistent. A batch check also does not measure interactive hover latency.

### 4) **Common confusion**

A successful language-service request can return a source diagnostic; that is different from a protocol error. Likewise a declaration target is different from a runtime implementation. Identify the requested operation and the result before deciding that a tool or compiler is broken.

Any in a displayed type can have several causes: an explicit escape, provider declarations, inference or a selected program boundary. It does not automatically mean a missing @types package or a particular skipLibCheck setting. Inspect the real declaration/program and a meaningful use. The detailed navigation and hover owners supply additional actual contrasts.

### 5) **Performance note**

This workspace verifies native query results, checked types and an applied rename. It measures no response latency, cache behavior or fixed slowdown from a large tooltip. Batch checking and interactive requests perform different work; neither a file-count threshold nor a named alias guarantees faster service responses. Reproduce the actual operation and preserve its provider/document/project conditions when measuring.

### 6) **Mentor note**

Have the learner predict names and marker, then compare the actual display with the static rejection probe. Ask why a successful rename leaves the string and unrelated local binding unchanged. A sound answer identifies a symbol relationship and the edit's scope rather than promising every textual name changes.

For a discrepancy, ask for the exact provider and document before accepting “the editor uses a simpler checker.” Then ask what the greeting's type leaves undocumented. Encourage types, meaningful prose and actual behavior checks to support one explanation rather than declaring hover the sole authority.
