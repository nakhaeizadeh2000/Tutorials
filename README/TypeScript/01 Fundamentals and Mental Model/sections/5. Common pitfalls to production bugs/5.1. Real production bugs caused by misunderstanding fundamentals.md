## 5.1. Real production bugs caused by misunderstanding fundamentals

### 1) **Assuming types guard at runtime**

A response asserted as `User` can actually be an error envelope or an incomplete record. The checker trusts the assertion, so the first field access can fail in production. The failure pattern is missing runtime evidence, not a missing interface definition. These examples reproduce such patterns locally; they do not claim measured incident rates from an unidentified team.

For this exercise, a User requires a finite numeric `id` and string `name`. That contract does not require a positive integer or a nonempty name; add those checks if your domain requires them. The complete file also parses a string-array field, so we can compare a declared type with actual element checks. Save `boundaries.ts` in a fresh directory without a tsconfig:

```typescript
type User = { id: number; name: string };
function isUser(value: unknown): value is User {
  return typeof value === "object" && value !== null
    && "id" in value && typeof value.id === "number" && Number.isFinite(value.id)
    && "name" in value && typeof value.name === "string";
}
type FetchLike = (url: string) => Promise<{ json(): Promise<unknown> }>;
async function fetchUser(id: number, request: FetchLike): Promise<User> {
  const response = await request(`/users/${id}`);
  const raw: unknown = await response.json();
  if (!isUser(raw)) throw new Error("invalid user");
  return raw;
}
function parseItems(data: unknown): string[] {
  if (typeof data !== "object" || data === null || !("items" in data)) {
    throw new Error("invalid items");
  }
  const raw = data.items;
  if (!Array.isArray(raw)) throw new Error("invalid items");
  const values: readonly unknown[] = raw;
  const result: string[] = [];
  for (const value of values) {
    if (typeof value !== "string") throw new Error("invalid items");
    result.push(value);
  }
  return result;
}
function readAny(data: any): any { return data.items; }
async function main(): Promise<void> {
  for (const payload of [{ id: 1, name: "Ada" }, { name: "Ada" },
                         { id: "1", name: "Ada" }, null, { error: "rate_limited" }]) {
    const fake: FetchLike = async () => ({ json: async () => payload });
    try { console.log("user:", (await fetchUser(1, fake)).name); }
    catch (error) { console.log(error instanceof Error ? error.message : "unexpected"); }
  }
  for (const payload of [{ items: ["Ada"] }, { items: [] }, { items: ["Ada", 2] },
                         { items: new Array(1) }, { items: null }, null]) {
    try { console.log("items:", parseItems(payload).length); }
    catch (error) { console.log(error instanceof Error ? error.message : "unexpected"); }
  }
  try { readAny({ items: null }).map((item: string) => item.toUpperCase()); }
  catch (error) { console.log(error instanceof TypeError ? "any: TypeError" : "unexpected"); }
  const input = { items: ["Ada"] };
  const parsed = parseItems(input);
  input.items[0] = "Grace";
  console.log("copy:", parsed[0]);
}
void main();
```

Use TypeScript 7.0.2 / Node 20.20.2:

```bash
tsc --strict --target es2022 --module commonjs --lib es2022,dom --outDir boundaries boundaries.ts
node boundaries/boundaries.js
```

The observed output was:

```text
user: Ada
invalid user
invalid user
invalid user
invalid user
items: 1
items: 0
invalid items
invalid items
invalid items
invalid items
any: TypeError
copy: Ada
```

The request function is an injected local fake: no HTTP service was called. It exercises the response-to-validator path with a valid record, missing/wrong id, null and an error envelope. The two required fields are checked before the result becomes User. Real HTTP status handling, authentication and network failures need separate integration tests.

### 2) **Using enum on a strip-only execution path**

A transpiling runner can process an enum while a strip-only runtime rejects it. That makes local success insufficient evidence for the deployed execution path. Save `enum.ts`:

```typescript
enum Status { Pending, Done }
console.log(Status.Done);
```

Run the checker gate and the explicitly selected native runtime:

```bash
tsc --strict --target es2022 --module commonjs --lib es2022,dom --erasableSyntaxOnly --noEmit enum.ts
npm exec --yes --package=node@22.18.0 -- node enum.ts
```

The first command intentionally reports TS1294 and exits 1. Node 22.18.0's default stripping reports `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` and exits 1. This is a tested strip-only path; the [execution owner](<../3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>) explains other runner and transform conditions. [Node's TypeScript documentation](https://nodejs.org/docs/latest-v22.x/api/typescript.html) establishes the runtime restrictions.

For a string status contract, save the erasable alternative as `status.ts`:

```typescript
const Status = { Pending: "pending", Done: "done" } as const;
type Status = typeof Status[keyof typeof Status];
const currentStatus: Status = Status.Done;
console.log(currentStatus);
```

```bash
tsc --strict --target es2022 --module commonjs --lib es2022,dom --erasableSyntaxOnly --outDir status status.ts
node status/status.js
npm exec --yes --package=node@22.18.0 -- node status.ts
```

All commands exited zero and both runtimes printed `done`. This alternative intentionally uses string values; a library that persisted numeric enum values must preserve its wire contract when migrating. Use the [erasable-syntax owner](<../3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>) for the broader inventory instead of treating enums as the only transform requirement.

### 3) **Treating any as proof that an array is usable**

The deliberately unsafe `readAny` bypasses checking inside the boundary and returns any to its caller. A `.map` call on null therefore compiles but throws TypeError. `noImplicitAny` helps find implicit holes; it does not prohibit this explicit any. Replacing the input with unknown requires checks, but the correctness of those checks still matters.

In the same exercise, `Array.isArray` establishes array membership and exposes an any[] view. The explicit `readonly unknown[]` view makes each visited value require narrowing. `parseItems` builds a new dense array from checked string values, so changing the input afterward does not replace a returned element. The empty array is accepted; the return type does not promise a first element exists.

The sparse case is especially important. `every` invokes its callback only for existing properties, as specified by [ECMA-262](https://tc39.es/ecma262/multipage/indexed-collections.html#sec-array.prototype.every). An all-string check using `every` can therefore accept holes. The exercised for-of traversal reads an ordinary missing slot as undefined and rejects it; the output array contains only values actually checked. See the [JavaScript holes owner](<../../../../JavaScript/08 Arrays/sections/2. Holes sparsity and length/2.1. Holes vs undefined sparse arrays and empty slots.md>) and [unknown owner](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>) for the full distinctions.

### 4) **Confusing a compiler exit with artifact freshness**

Plain tsc can emit JavaScript despite a type error. `noEmitOnError` suppresses new emission, but it does not remove an older output file. If a pipeline ignores the failed command and deploys whatever is present, either case can violate the release contract. The [option documentation](https://www.typescriptlang.org/tsconfig/noEmitOnError.html) states its default is false.

Save `pipeline.py` beside the other examples. It creates and cleans only its own `emit-demo/dist` directory. The intentional observation steps run bad/stale output to expose the difference; the final safe sequence skips the consumer after failure.

```python
from pathlib import Path
import shutil, subprocess

project = Path("emit-demo")
project.mkdir(exist_ok=True)
source = project / "main.ts"
output = project / "dist"
artifact = output / "main.js"
base = ["tsc", "--strict", "--target", "es2022", "--module", "commonjs",
        "--lib", "es2022,dom", "--outDir", "dist", "main.ts"]
def compile_source(block_errors=False):
    result = subprocess.run(base + (["--noEmitOnError"] if block_errors else []),
                            cwd=project, capture_output=True, text=True)
    if result.returncode and "TS2322" not in result.stdout:
        raise RuntimeError(result.stdout + result.stderr)
    return result.returncode
def run_artifact():
    return subprocess.check_output(["node", "dist/main.js"], cwd=project, text=True).strip()
good_old = 'const version: string = "old";\nconsole.log(version);\n'
bad = 'const version: string = 123;\nconsole.log(version);\n'
source.write_text(good_old)
shutil.rmtree(output, ignore_errors=True)
assert compile_source() == 0
print("baseline:", run_artifact())
source.write_text(bad)
status = compile_source()
assert status != 0 and artifact.exists()
print("default:", status, run_artifact())
source.write_text(good_old)
assert compile_source() == 0
source.write_text(bad)
status = compile_source(block_errors=True)
assert status != 0 and artifact.exists()
print("blocked emit:", status, run_artifact())
shutil.rmtree(output, ignore_errors=True)
status = compile_source(block_errors=True)
assert status != 0 and not artifact.exists()
print("safe failed: deploy skipped; artifact absent")
source.write_text('const version: string = "new";\nconsole.log(version);\n')
shutil.rmtree(output, ignore_errors=True)
status = compile_source(block_errors=True)
assert status == 0 and artifact.exists()
print("safe fixed:", run_artifact())
```

Run `python3 pipeline.py` with Python 3, the tested compiler and Node available on PATH. The observed output was:

```text
baseline: old
default: 2 123
blocked emit: 1 old
safe failed: deploy skipped; artifact absent
safe fixed: new
```

The default diagnostic has a nonzero exit but fresh erroneous output. The blocked-emission diagnostic leaves the old artifact visible. The safe failure has neither a successful gate nor an output to consume. After correcting the source, the safe build creates and runs `new`. In an application pipeline, deployment must depend on successful gate results and the intended fresh build artifact. Separate check/build script names alone do not enforce that dependency.

### 5) **Common confusion**

A predicate signature is a claim the checker trusts, not a verifier of the predicate's implementation. An assertion can make the same unsupported claim without any check. Likewise, explicit any still bypasses strict checking, array membership does not establish element types, and a compiler error does not always imply absent JavaScript. Diagnose the actual boundary or artifact transition rather than counting assertions or assuming a command name proves its behavior.

### 6) **Performance note**

The user validator executes field checks and the array parser traverses values while allocating a checked copy. Those are real runtime operations; the erased User and string[] annotations add no validation work themselves. A copy isolates the returned array from element replacement through the input alias, at the cost of storage for its elements. No latency benchmark was run. Cleaning build output and checking consumers also perform work, but their purpose here is a verifiable artifact contract, not a promised speed improvement.

### 7) **Mentor note**

Ask the learner to predict the missing-id and sparse-array cases before running them, then explain which value each check established. For emission, ask whether a nonzero exit, an existing file and a fresh artifact are the same fact; the three demonstrated states show they are different. Review the actual malformed cases and pipeline dependencies instead of a zero-assertion slogan. A sound explanation names the unproved contract and the observation that would expose it.
