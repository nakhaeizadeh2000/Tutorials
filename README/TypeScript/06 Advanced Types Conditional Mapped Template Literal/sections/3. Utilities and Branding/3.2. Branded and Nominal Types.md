## 3.2. Branded and Nominal Types

### 1) **Pattern** (brand property)

**Pattern** — Structural typing makes `{ id: string }` interchangeable regardless of domain. Brand adds a phantom property visible only to checker to simulate nominal typing.

Common shapes:

```typescript
type Brand<K, T> = K & { readonly __brand: T };

// primitive brand
type UserId = Brand<string, "UserId">;
type OrderId = Brand<string, "OrderId">;
function getUser(id: UserId): void {}
const u = "u-1" as UserId; // factory
const o = "o-1" as OrderId;
// getUser(o); // error — OrderId not UserId (brand differs)
getUser(u); // ok

// object brand
type HasId = { id: string };
type User = Brand<HasId, "User"> & { name: string };
type Product = Brand<HasId, "Product"> & { title: string };
// User vs Product not assignable — brand separates despite same shape

// alternative: class with private field (nominal leak)
class UserIdClass {
  private readonly __brand!: "UserId";
  constructor(public readonly value: string) {}
}
// UserIdClass nominal — different class with same field not assignable
```

Brand is erased — no runtime field need be set (though you may store companion object).

### 2) **Example** (UserId)

```typescript
// helper factory keeps call site ergonomic and grep-able
declare const __brand: unique symbol; // alternative symbol brand
type UserId2 = string & { readonly [__brand]: "UserId" };
function UserId2(raw: string): UserId2 { return raw as UserId2; }

function findUser(id: UserId2): { id: UserId2; name: string } | undefined {
  // simulate
  return { id, name: "Ava" };
}
let id = UserId2("user_42");
let user = findUser(id);
console.log(user?.name);

// branding with validation (zod-like without library)
function parseUserId(raw: unknown): UserId2 {
  if (typeof raw !== "string" || !raw.startsWith("user_")) throw new Error("bad UserId");
  return raw as UserId2;
}

// object + brand + discriminant combo
type EntityId<T> = Brand<string, T>;
type ArticleId = EntityId<"Article">;
type Article = { id: ArticleId; title: string };
type UserEntity = { id: UserId2; name: string };
// ids cannot mix
function loadArticle(id: ArticleId): Article { return { id, title: "Hi" }; }
// loadArticle(id) // error — UserId2 vs ArticleId
loadArticle("article_1" as ArticleId); // ok
```

### 3) **Link** (to DesignPatterns)

Branding is a design decision (DDD Value Object, Refined Types):

- DDD: value object `UserId` as class with private ctor + `equals` → see [DesignPatterns track](<../../../DesignPatterns/README.md>) — patterns `Value Object`, `Factory`, `Identity Map`.
- Compare to runtime validation → [10 2.1 Zod bridge](<../../../10%20Migration%20Interop%20and%20Runtime%20Gaps/sections/2.%20Interop%20and%20Boundaries/2.1.%20Zod%20Valibot%20and%20Runtime%20Validation%20TS%20erasure%20bridge.md>) — brand for compile-time + codec for runtime.
- Structural base → [01 2.1 Structural](<../../../01%20TypeScript%20Fundamentals%20and%20Mental%20Model/sections/2.%20Mental%20Model%20—%20Structural%20Types%20and%20Erasure/2.1.%20Structural%20Typing%20vs%20Nominal%20duck%20typing%20at%20type%20level.md>) why brands necessary.

**Common confusion** —

- "Brand changes runtime object" — no, phantom field not set; it's `never`-occupied trick. If you *need* runtime tag, add real field `kind: "UserId"`.

**Performance note** —

Zero-cost — brand intersection adds no object size. Checker cost minimal; excessive branded intersections in huge mapped types can bloat hover, but not runtime.

**Mentor note** —

Enforce brand for any domain string that appears in two contexts (UserId vs OrderId). The one-time cost of `as Brand` factory pays back at first mix-up caught.
