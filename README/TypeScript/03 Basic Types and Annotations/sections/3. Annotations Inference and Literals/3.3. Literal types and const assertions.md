## 3.3. Literal types and const assertions

### 1) **Literal as subtype**

A literal type names a particular value, such as `"success"`, `42`, `true` or `1n`. That value can satisfy its broader primitive type. A general string does not, by itself, prove that it is the one string `"success"`. Unions of literals can describe a finite vocabulary, such as `"idle" | "done"`.

The union is a static contract, not an emitted collection or a runtime input validator. Use it when the finite alternatives are the intended API. A value table can additionally supply runtime data. Choosing between that design and an enum requires the actual representation and compatibility requirements, developed in the [enum owner](<../../../11 Enums and Literal Types/README.md>).

### 2) **Const assertions and satisfies**

A const assertion on a supported literal expression prevents its literal types from widening, gives object-literal properties readonly views and makes array literals readonly tuples. It does not recursively change every object reached through an existing reference, nor freeze runtime data. The [3.4 introduction and caveats](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-4.html#const-assertions) explain those limits.

Satisfies checks an expression against a target while preserving the expression's resulting type rather than replacing it with the target. However, the target can supply inference context. Therefore, do not predict that every string property remains a literal or that adding satisfies can never influence the inferred result. The [4.9 introduction](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html#the-satisfies-operator) motivates checked expression precision; verify the actual input and target.

Use TypeScript 7.0.2 and Node.js 20.20.2. Save this complete module as `literals.mts` in an empty directory. The equality helpers are active compiler assertions, separate from the runtime observations.

```typescript
// literals.mts
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Route = { path: string; method: "get" | "post"; retries: number; enabled: boolean };
const checked = { path: "/", method: "get", retries: 3, enabled: true } satisfies Route;
const annotated: Route = { path: "/", method: "get", retries: 3, enabled: true };
const exact = { path: "/", method: "get", retries: 3, enabled: true } as const satisfies Route;
type CheckedMethod = Expect<Equal<typeof checked.method, "get">>;
type CheckedPath = Expect<Equal<typeof checked.path, string>>;
type CheckedRetries = Expect<Equal<typeof checked.retries, number>>;
type CheckedEnabled = Expect<Equal<typeof checked.enabled, true>>;
type AnnotatedMethod = Expect<Equal<typeof annotated.method, "get" | "post">>;
type ExactPath = Expect<Equal<typeof exact.path, "/">>;
type ExactRetries = Expect<Equal<typeof exact.retries, 3>>;
console.log(checked.method, annotated.method, exact.method);
checked.retries = 4;
console.log("mutable", checked.retries, Object.isFrozen(exact));

const shared = { count: 0 };
const view = { nested: { mode: "get" }, shared } as const;
view.shared.count = 1;
console.log("shared", shared.count, Object.isFrozen(view.nested));
const severities = ["low", "high"] as const;
type Severity = typeof severities[number];
type Tuple = Expect<Equal<typeof severities, readonly ["low", "high"]>>;
function severity(value: Severity): string { return value.toUpperCase(); }
console.log(severity("high"));

const asserted = { method: "get" } as Route;
console.log("asserted path", asserted.path);
```

```sh
tsc --strict --erasableSyntaxOnly --target ES2022 --module NodeNext --noEmitOnError --outDir dist literals.mts
node dist/literals.mjs
```

Output:

```text
get get get
mutable 4 false
shared 1 false
HIGH
asserted path undefined
```

All three route views initially hold the same method string. Checked retains a get-only method and a true-only enabled field, while its path and retries are broader primitive properties. Its retries property remains writable. Annotated deliberately exposes the wider Route method contract. Exact retains literal path/retries and readonly properties, yet is not frozen at runtime.

The nested literal under view receives readonly property types, but shared is an existing mutable object. Mutating its count through view is accepted and changes the original. Const assertion is not a general deep-immutability operation. If runtime integrity matters, choose an explicit strategy; Object.freeze itself is shallow.

The asserted object lacks a path but its assertion is accepted through the overlapping shape. Reading it produces undefined. An assertion is not equivalent to a checked construction that establishes every required field. The [object-check owner](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.3. satisfies assertions and narrowing on object shapes.md>) develops these source/context/target distinctions.

Append one independent negative probe at a time, compile and restore:

```typescript
checked.method = "post";
```

```typescript
checked.enabled = false;
```

These report TS2322: the properties are not readonly, but their inferred types admit only get and true respectively. The following two probes each report TS2540 for readonly literal properties:

```typescript
exact.retries = 4;
```

```typescript
view.nested.mode = "get";
```

This independent severity call reports TS2345:

```typescript
severity("critical");
```

To require a configuration that can change its method later, use an appropriate wider annotation such as Route. To require fixed literal information for deriving types, preserve that information deliberately. Neither choice is universally “more correct.”

### 3) **Template literal types preview**

Template literal types compose string patterns. The type ``type Greeting = `hello ${"Ada" | "Lin"}` `` describes two string alternatives. The type ``type UserPath = `/user/${string}` `` instead accepts any string suffix, rather than a finite set of valid user identifiers. These are type contracts, not runtime string-generation calls or validation of a real account.

Full composition, inference and key-remapping work belongs to [type transformations](<../../../09 Utility Types and Type Transformations/README.md>). Here, the tuple-derived Severity shows the smaller building block: `typeof severities[number]` obtains a union of the declared tuple elements without constructing a second runtime collection.

Const assertions also have expression restrictions. For a separate negative probe, append `const copy = checked as const;`: TS1355. Apply const context when constructing the supported literal, rather than expecting an assertion to recover literals already widened in an arbitrary variable.

### 4) **Common confusion**

Const binding, literal inference, readonly property types and runtime freezing are different mechanisms. Referenced objects can remain mutable inside a const-asserted literal. Satisfies can check a contract while the expression retains different precision in different members; an asserted target view can also hide a missing field.

A finite union does not mean all runtime inputs are known. A type-only vocabulary must still be validated at an untrusted boundary. Likewise, a template pattern with a string hole does not enumerate or authorize every matching value.

### 5) **Performance note**

Literal types, const assertions, satisfies and equality probes erase. The objects, shared mutation and formatting remain executable operations. No fixed literal-count threshold or assignment-complexity formula was measured. Type-level expansions can make a real checking workload larger, but investigate it with the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) before changing a meaningful contract for performance.

### 6) **Mentor note**

Ask which checked properties can change to a different value and require a reason for each. Then predict the shared count mutation and both isFrozen observations. A sound answer separates contextual literal inference, readonly views and runtime operations. For a repair exercise, replace the missing-field assertion with satisfies and supply the required Route members; explain why the diagnostic reveals a missing construction step instead of merely asking for another cast.
