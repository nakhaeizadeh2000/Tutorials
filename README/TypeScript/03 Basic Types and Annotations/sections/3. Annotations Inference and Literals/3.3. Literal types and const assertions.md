## 3.3. Literal types and const assertions

### 1) **Literal as subtype** (`"success"` is assignable to `string`, not vice-versa — string literal unions as enums without emit)

**Definition** — a *literal type* is the type of a single literal value: `"success"` (string literal), `42` (numeric literal), `true`/`false` (boolean literal, via `true`/`false` subtypes of `boolean`), `1n` (bigint literal), and `unique symbol`. Literal types are *subtypes* of their base primitive: `"success" ≤ string`, `42 ≤ number`, `true ≤ boolean`. They are the building block for unions that model finite vocabularies without `enum` emit.

- **Why literal unions win** — `type Status = "idle" | "loading" | "done"` is a union of three literal types. It erases (no emit), is `erasableSyntaxOnly` compatible, supports exhaustiveness via `never` (see [2.3. never and void](<../2. The Special Types/2.3. never and void bottom vs deliberate nothing.md>)), and composes with template literals (`type Route = `/user/${stringId}``). `enum Status { Idle, Loading, Done }` emits a runtime object, is not erasable, and requires `erasableSyntaxOnly` escape — prefer literal unions for new code (see [enum cost](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>)).
- **Hierarchy** — `literal ≤ primitive ≤ {} (object) ≤ unknown` (narrowest to widest). Narrowing (`if (x === "success")`) moves from `string` toward a literal; widening ([3.2. Type inference](<./3.2. Type inference widening and contextual typing.md>)) moves the opposite.

```typescript
let wide: string = "success"; // string
let lit: "success" = "success"; // "success" — subtype
let litFromConst = "success" as const; // "success" — inferred literal via const

wide = lit; // ok — subtype to supertype
// lit = wide; // error — supertype not assignable to literal
```

### 2) **const assertions and as const** (`{ x: 1 } as const` → `readonly` + literal narrowing; `satisfies` preserves literal while checking shape)

- **`as const`** (TS 3.4+) freezes *all* literal positions recursively, and marks members `readonly`: `const cfg = { retry: 3, mode: "fast" } as const` → `{ readonly retry: 3; readonly mode: "fast" }` (both fields literal types and readonly). Without `as const`, `cfg.retry` is `number` and mutable. Use `as const` for config objects, test fixtures, and route tables where you need literal identity for type-level programming.
- **`satisfies` vs `as const` vs `as Type`** — `satisfies T` checks assignability while *preserving* literal identity (added TS 4.9); `as T` narrows/widens to exactly `T` (may hide errors); `as const` narrows to literals and deep readonly. Idiomatic as of TS 5.9 era:

| You write | Checks `T`? | Preserves literal? | Readonly? |
|---|---|---|---|
| `const x = { method: "get" } as Route` | yes, but widens to `Route` (`method: "get" | "post"`) | no | no |
| `const x = { method: "get" } satisfies Route` | yes | yes (`method: "get"`) | no |
| `const x = { method: "get" } as const satisfies Route` | yes | yes + literals | yes (deep) |

- **`as const` on arrays** — `const ids = ["a", "b"] as const` → `readonly ["a", "b"]` (readonly tuple of literals, not `string[]`). Array literals without `as const` widen to `string[]`; `as const` keeps tuple positions and literals, enabling `typeof ids[number]` → `"a" | "b"` (see [10 Arrays, Tuples and Collections](<../10 Arrays Tuples and Collections/README.md>) textual forward).

### 3) **Template literal types preview** (forward link to mapped/utility domains — where literal types compose into type-level programs)

- **Composition** — literal types compose: `` type Greeting = `hello ${"Ada" | "Bob"}` `` → `"hello Ada" | "hello Bob"`; `` type Action = `on${Capitalize<"click" | "hover">}` `` → `"onClick" | "onHover"`. These are *string literal types* built from other literals — zero runtime cost, full type-level exhaustiveness.
- **Preview link** — template literal types, `infer` on strings, and mapped types that generate literal unions are owned by [09 Utility Types and Type Transformations](<../09 Utility Types and Type Transformations/README.md>) and [08 Generics Deep Dive](<../08 Generics Deep Dive/README.md>) textual forwards — this leaf only establishes the primitive literal model. Enabling `noErrorTruncation: false` in large literal unions shows the checker enumerating them in hover.

### 4) **Runnable example** — literal unions, const assertions, and satisfies (good vs bad)

```typescript
// good — literal union as erasable enum replacement (no emit, exhaustive)
type Status = "idle" | "loading" | "done";
function handleStatus(s: Status): string {
  switch (s) {
    case "idle": return "waiting";
    case "loading": return "spinner";
    case "done": return "finished";
    default: {
      const _ex: never = s; // exhaustiveness via never (see 2.3)
      return _ex;
    }
  }
}
console.log(handleStatus("loading")); // spinner
// handleStatus("offline"); // error TS2322: "offline" not in Status — literal checks

// bad — enum that requires emit (not erasable, fails erasableSyntaxOnly)
 // enum StatusEnum { Idle, Loading, Done } // TS1294 when erasableSyntaxOnly:true
 // fix — use literal union above

// good — as const preserves literals + readonly for type-level programming
const ROUTES = {
  home: { path: "/", method: "get" },
  users: { path: "/users", method: "get" },
} as const; // deep literal + readonly
type RouteKey = keyof typeof ROUTES; // "home" | "users" — derived from literals
type MethodOf<R extends RouteKey> = typeof ROUTES[R]["method"]; // "get" (literal, not string)

// bad — without as const, literal identity lost (widened to string)
const routesWidened = {
  home: { path: "/", method: "get" },
  users: { path: "/users", method: "get" },
}; // method: string — widened, keyof still works but method is not "get" literal
// fix — as const or satisfies

// good — satisfies checks shape without widening (TS 4.9+, idiomatic 5.9)
type Route = { path: string; method: "get" | "post" };
const routeOk = { path: "/users", method: "get" } satisfies Route; // method stays "get"
const methodOk: "get" = routeOk.method; // preserved literal — can assign to narrow variable

const routeCast = { path: "/users", method: "get" } as Route; // method widened to "get"|"post"
 // const methodLost: "get" = routeCast.method; // error? Actually "get"|"post" not assignable to "get" — asymmetry reveals the loss

// good — as const on arrays → readonly tuple of literals
const severities = ["low", "med", "high"] as const;
type Severity = typeof severities[number]; // "low" | "med" | "high" — literal union derived from values
function alertLevel(s: Severity): void { console.log(s); }
alertLevel("high"); // ok
// alertLevel("critical"); // error — not in tuple-derived union

// bad — mutable widened array loses literal connection
const severitiesWidened: string[] = ["low", "med", "high"];
type SeverityWidened = typeof severitiesWidened[number]; // string — not a useful union

// good — template literal types compose literals (preview)
type ApiRoute = `/user/${string}` | `/post/${string}`;
const route: ApiRoute = "/user/123"; // ok — template literal matches
// const badRoute: ApiRoute = "/other/123"; // error — prefix fails

// bad — numeric literal widened when literal intended
let retryCount = 3; // inferred number — loses "3"
const retryLit = 3 as const; // 3 (literal)
function setRetry(n: 1 | 2 | 3): void {}
 // setRetry(retryCount); // error — number not assignable to 1|2|3
setRetry(retryLit); // ok
setRetry(3 as const); // ok
```

### 5) **Common confusion**

- "`as const` makes the object immutable at runtime" — it makes *types* readonly, but runtime mutation still works (`(obj as any).x = 2` would succeed). For runtime immutability use `Object.freeze` in addition — `as const` is a type-level promise, not a runtime freeze.
- "Literal type is just a string with a value" — at runtime yes, but statically `string` accepts any string while `"success"` accepts only that literal — assignability direction matters (literal ⊆ primitive).
- "`satisfies` changes the variable's type to `T`" — no, `satisfies T` keeps the *source* literal type and only checks that it satisfies `T`. `as T` forces the variable to `T` and loses source literals.

### 6) **Performance note**

Literal unions have no emit cost and near-linear checker cost for small unions (`<20` members). Huge unions (`>100` literals) can dominate checker time (each call site branches over every member — measured as O(N) for assignment checks, and template literal expansions can multiply). Keep literal vocabularies bounded; when a string set comes from a database or config, model it as `string` (or branded string) instead of enumerating every literal. `as const` adds no runtime allocation — it only refines the type graph.

### 7) **Mentor note**

Teach literal unions as "the erasable enum". Exercise: refactor an `enum` domain to a literal union, add a branch that handles every member with `never` exhaustiveness, then add a new literal — watch the checker force the branch update. Review checklist: config objects use `as const` when their literals are derived via `typeof ...[number]`; exported factory functions use `satisfies` when callers should benefit from literal preservation; runtime immutability promise uses `Object.freeze` alongside `as const`.
