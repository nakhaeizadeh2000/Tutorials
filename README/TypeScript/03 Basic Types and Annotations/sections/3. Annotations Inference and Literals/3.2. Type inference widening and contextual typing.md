## 3.2. Type inference widening and contextual typing

Inference supplies a type when you do not write one. The result depends on the value, its context and the operations visible to the compiler. A literal may widen to a primitive type, an expected callback type may supply a parameter type, and some initially empty locals can evolve through later assignments. Use annotations when the intended invariant should be fixed independently of those operations.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence under its filename. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`; run `node dist/FILE.js`. Activate negatives separately and use those flags with --noEmit instead of --outDir dist.

### 1) **Widening values and choosing a stable contract**

For the primitive string declarations below, the mutable binding widens idle to string, while the const binding retains idle. Const prevents rebinding; it does not make object properties immutable. A const object literal can still have a writable string property, while a const assertion on its literal expression preserves a readonly literal property.

Save as literals.ts.

```typescript
let mutableStatus = "idle";
const fixedStatus = "idle";
const mutableObject = { status: "idle" };
const literalObject = { status: "idle" } as const;
let selected: "idle" | "done" = "idle";
selected = "done";
function label(status: "idle" | "done"): string { return status.toUpperCase(); }
console.log(label(fixedStatus), label(selected), mutableStatus);
mutableObject.status = "something else";
console.log(mutableObject.status, literalObject.status, Object.isFrozen(literalObject));
// label(mutableStatus); // TS2345: string is broader than the admitted literal union
// selected = "other"; // TS2322
// literalObject.status = "idle"; // TS2540
// fixedStatus = "done"; // TS2588

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Mutable = Expect<Equal<typeof mutableStatus, string>>;
type Fixed = Expect<Equal<typeof fixedStatus, "idle">>;
type Property = Expect<Equal<typeof mutableObject.status, string>>;
type LiteralProperty = Expect<Equal<typeof literalObject.status, "idle">>;
```

The output is `IDLE DONE idle`, then `something else idle false`. Four live probes compile. The admitted statuses are meaningful values in this example; preserving the unrelated literal hello would not make it a valid status. The explicit selected annotation permits two intended assignments while rejecting other strings.

The runtime object remains unfrozen. The [literal/const owner](<./3.3. Literal types and const assertions.md>) owns that syntax in detail, and [checked object shapes](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.3. satisfies assertions and narrowing on object shapes.md>) explains how a satisfies target can supply context and influence literal inference too. No single slogan about const determines every object or generic result.

### 2) **Best common type and context flow in both directions**

When several values contribute to inference, the checker considers candidate types and compatible alternatives. In this primitive mixed-array example the result is an array of string | number. It does not always invent an arbitrary common superclass or simply choose the first element's type. An explicit expected type can supply a different useful contract.

Contextual typing means the expected location supplies information to an expression. Array methods know the element type and can supply it to a callback parameter; an annotated function variable can do the same. An isolated unannotated parameter lacks that evidence and can trigger noImplicitAny. The [primary inference guide](https://www.typescriptlang.org/docs/handbook/type-inference.html#contextual-typing) explains the candidate and context mechanisms.

Save as context.ts.

```typescript
const mixed = [1, "a"];
mixed.push(2);
mixed.push("b");
// mixed.push(true); // TS2345
console.log(mixed.join(","));
const lengths = ["Ada", "Bob"].map(word => word.length);
console.log(lengths.join(","));
function measure(text: string, callback: (value: string) => number): number { return callback(text); }
console.log(measure(" hi ", value => value.trim().length));
const format: (value: number) => string = value => value.toFixed(1);
console.log(format(2));
// format("2"); // TS2345
// const isolated = value => value.toUpperCase(); // TS7006: no contextual parameter type

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type ElementResult = Expect<Equal<typeof mixed[number], string | number>>;
type Mapped = Expect<Equal<typeof lengths, number[]>>;
```

The output is `1,a,2,b`, `3,3`, `2`, then `2.0`; both probes compile. No explicit word or value parameter annotation is needed where the signature supplies it. Conversely, writing any on the isolated parameter would disable the useful check rather than prove that an unknown value supports a string method.

Generic parameters have additional inference sites and body obligations. Use the [generic inference owner](<../../../08 Generics Deep Dive/sections/1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>) to inspect them instead of assuming every literal argument must widen or every explicit type argument validates a value.

### 3) **Distinguish evolving locals from fixed empty-array contexts**

Under these strict flags, a local initialized to [] can evolve through visible writes. The shown const binding can still receive pushed elements, and snapshots taken at two points have different inferred element contracts. An object property's empty array does not use that same evolving-local mechanism and can infer never[]. A typed position can instead establish the intended element type directly.

A null-initialized unannotated local can also acquire useful flow types after assignments in this pattern. It is not universally locked to null under strictNullChecks. Annotate string | null when that is the intended invariant; the annotation rejects a later number even when unannotated local inference would follow it. The [primary evolving-inference notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-1.html#improved-any-inference) explain the mechanism and real implicit-type failures.

Save as evolution.ts.

```typescript
const values = [];
values.push("a");
const textValues = [...values];
values.push(1);
const mixedValues = [...values];
console.log(textValues.join(","), mixedValues.join(","));
const objectState = { items: [] };
// objectState.items.push("a"); // TS2345: this property is never[]
const numericState: { items: number[] } = { items: [] };
numericState.items.push(1);
// numericState.items.push("a"); // TS2345

let current = null;
const initial = current;
current = "hi";
const textValue = current;
current = 7;
const numericValue = current;
console.log(initial, textValue, numericValue);
let intended: string | null = null;
intended = "hi";
// intended = 7; // TS2322
console.log(intended.toUpperCase());

function collect<T>(items: T[]): T[] { return items; }
const emptyArgument = collect([]);
const explicit = collect<string>([]);
explicit.push("x");
// emptyArgument.push("x"); // TS2345
console.log(explicit.join(","), emptyArgument.length);
// function premature(): void { const items = []; console.log(items[0]); } // TS7034 and TS7005

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type TextValues = Expect<Equal<typeof textValues, string[]>>;
type MixedValues = Expect<Equal<typeof mixedValues, (string | number)[]>>;
type PropertyItems = Expect<Equal<typeof objectState.items, never[]>>;
type Initial = Expect<Equal<typeof initial, null>>;
type AfterText = Expect<Equal<typeof textValue, string>>;
type AfterNumber = Expect<Equal<typeof numericValue, number>>;
type ArgumentItems = Expect<Equal<typeof emptyArgument, never[]>>;
type ExplicitItems = Expect<Equal<typeof explicit, string[]>>;
```

The output is `a a,1`, `null hi 7`, `HI`, then `x 0`; eight probes compile. The spread expressions create the snapshots; inference alone does not copy an array. The generic argument position, object property and evolving local are different contexts even though each contains [] somewhere in its source.

Activating premature produces real implicit-array diagnostics at the declaration and unresolved read. NoImplicitAny does not reject every empty declaration or every accepted mixed evolution. If a collection must remain numeric, state that invariant before the writes. Never is the bottom type, assignable to other types; a never[] cannot accept an ordinary string element, but it can be a valid inferred empty input in another context. [Array types](<../../../10 Arrays Tuples and Collections/sections/1. Array Types/1.1. Array type syntax and element checking.md>) applies these distinctions to collection operations.

### 4) **Common confusion**

A const binding is not a readonly object or array. Literal widening and contextual typing concern inferred contracts, while control flow can refine a value at a particular point. A successful local assignment is not evidence that every annotated variable admits the same change.

Empty arrays have context-dependent results: an evolving local, an object property and a generic argument can differ. An annotation is useful when the desired invariant should not grow with observed writes. An error discovered at an unresolved read also differs from a universal declaration-time rejection.

### 5) **Performance note**

Inference and annotations erase. Array pushes, spreads, callbacks and assignments remain, with the same runtime behavior whether their intended types were inferred or written. No general union-branching formula, performance benefit from annotation or bug-density measurement was established. Choose types from the intended contract; investigate actual checking costs through [diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) when needed.

### 6) **Mentor note**

Ask the learner to name the source of each type: literal initializer, expected callback signature, visible assignment or explicit invariant. Have them predict the two snapshots and the null-initialized local before compiling. A sound answer explains why the numericState write rejects a string while values can evolve to a mixed array.

For practice, write buildQueue(): number[] with an unannotated empty local queue, then push 1 and oops. The inferred mixed array must fail at the declared return. Annotating queue: number[] moves the rejection to the bad push. Remove that write and verify the function returns [1]. This shows how annotation placement establishes intent and changes the location of the useful diagnostic; it is not a claim that every evolving array is wrong.
