## 3.2. Type inference widening and contextual typing

### 1) **Widening defaults** (`let` widens `"hello"` → `string`; `const` keeps `"hello"` — control via annotation or `const` assertion)

**Definition** — *widening* is the checker's rule for inferring a *broader* type than the literal you wrote, on the assumption the variable will be reassigned. *Narrowing* is the opposite (control-flow refines a broad type to a precise one — covered in [07 Unions, Intersections and Narrowing](<../07 Unions Intersections and Narrowing/README.md>) textual forward). Widening is the reason `let x = "hello"` displays as `string` but `const x = "hello"` displays as `"hello"`.

- **The rule table** (as of TypeScript 5.9 era, `--strict`):

| Declaration | Inferred type | Why | To keep literal |
|---|---|---|---|
| `let x = "hello"` | `string` | `let` is reassignable → widen literal to base | `let x: "hello" = "hello"` or `let x = "hello" as const` |
| `const x = "hello"` | `"hello"` | `const` not reassignable → keep literal | default |
| `let x = 42` | `number` | same — numeric literal widens | `let x = 42 as const` or annotation |
| `const x = 42` | `42` | kept | — |
| `let x = null` | `any` (with `strictNullChecks: false`) else `null` then widen to `any`? Actually under strict, `let x = null` infers `any`? No — `null` widens? See note | Under strict, `null`/`undefined` widen? Practically `null` stays `null` until reassigned: `let x = null;` inferred as `any` under legacy? Deliberately avoid broad claim — check hover |

- **Wider families** — `let x = { name: "Ada" }` widens `name` to `string` (`{ name: string }`); `const x = { name: "Ada" }` keeps `{ readonly name: "Ada" }`? No — `const` object is still writable property-wise: `const obj = { name: "Ada" }` infers `{ name: string }`, not literal — object literals widen their properties regardless of `const` (to keep the object mutable). To freeze literality, use `as const` (next leaf [3.3. Literal types and const assertions](<./3.3. Literal types and const assertions.md>)).

| Object form | Inferred `name` | Fix |
|---|---|---|
| `let obj = { name: "Ada" }` | `string` | — (widened, mutable) |
| `const obj = { name: "Ada" }` | `string` | still `string` (property is `let`-like) |
| `const obj = { name: "Ada" } as const` | `"Ada"` (plus `readonly`) | frozen |

- **control flag** — `--noImplicitAny` does not affect widening; `--strictNullChecks` affects how `null`/`undefined` participate — `let x = null` with `strictNullChecks` stays `null` (not widened to `any`), but a later `x = 1` would error unless `x: number | null`.

### 2) **Best common type and contextual typing** (how `let x = [1, "a"]` becomes `(string | number)[]` and how arrow parameters infer without annotation)

- **Best common type (BCT)** — when the checker must *infer* a type from multiple values without an annotation, it computes the *least upper bound* that satisfies all of them. The canonical case is array literals and the generic `Array<T>` inference: `let xs = [1, 2, "hi"]` → `(string | number)[]` (BCT of `number` and `string`). Empty array `let xs = []` → inferred as `any[]` or `never[]` depending on `noImplicitAny` and context — which is why you should annotate empty collections (see bad example below).
- **Contextual typing** — when a value is *passed* to a typed position, that position's type flows *backwards* to infer the value. Example: `["a", "b"].map(s => s.length)` — `s` is never annotated but inferred as `string` because `Array<string>.map`'s callback is typed `(value: string) => ...`. The context supplies the type — no annotation needed. Contextual typing also applies to `const` assertions inside function calls, object literals assigned to typed variables, and `return` inference.

```typescript
// BCT
let mixed = [1, "hi"]; // (string | number)[]
mixed.push(2); // ok
mixed.push("ok"); // ok
// mixed.push(true); // error — boolean not in BCT

// Contextual typing
const names = ["Ada", "Bob"];
names.forEach(n => console.log(n.toUpperCase())); // n inferred as string — not annotated

// Without context, inference needs help
// let empty = []; // any[] or never[] — hover shows the guess
let empty: string[] = []; // annotated — intentional
```

- **Generic inference** — `function identity<T>(x: T): T { return x; } identity("hi")` → `T` inferred as `string` (or `"hi"` depending on call site widening). The checker infers `T` from the argument's *widened* type — another reason `let` vs `const` matters for generics.

### 3) **When inference surprises** (`noImplicitAny`, generic inference from empty arrays, `null`/`undefined` widening under `strictNullChecks`)

- **Empty array / uninitialized `let`** — `let xs = []; xs.push(1);` — with `noImplicitAny: false`, `xs` is `any[]` and `xs.push("str")` silently succeeds (any leak). With `noImplicitAny: true`, `let xs = [];` → error `Variable 'xs' implicitly has an 'any[]' type` — the checker forces `let xs: number[] = [];`. This is one of the highest-value `strict` checks for codebase hygiene.
- **`null` initialization** — `let current: string | null = null;` is correct — annotate when initialization is `null`/`undefined` and later assigned a real value. `let current = null;` alone is useless (stays `null` type, can't assign `string` later) — the annotation *widens the intention*.
- **Contextual fallback to `any`** — when neither side supplies context, the checker falls back to `any` or `unknown` depending on flags: `let f = x => x.foo;` with `noImplicitAny: true` → error `Parameter 'x' implicitly has an 'any' type`; without the flag, `x` is `any` and `x.foo` silently compiles. Always keep `noImplicitAny: true`.

### 4) **Runnable example** — widening, BCT, and context (good vs bad)

```typescript
// good — control widening with const / as const / annotation where intent matters
let widened = "hello"; // string
const kept = "hello";   // "hello"
let pinned: "hello" | "goodbye" = "hello"; // annotation pins the union
const literalObj = { status: "idle" } as const; // { readonly status: "idle" } — literal preserved

function setStatus(s: "idle" | "loading" | "done"): void {}
// setStatus(widened); // error — string not assignable to union (widening bites)
setStatus(kept); // ok — "hello" not in union? actually "hello" isn't in union — keep example literal relevant
setStatus(pinned); // ok

let statusWidened = "idle"; // string — not assignable to union
let statusGood: "idle" | "loading" | "done" = "idle"; // ok via annotation
setStatus(statusGood); // ok
setStatus("idle"); // ok — literal argument stays literal (call site context)

// good — best common type and contextual typing
let mixedGood: (string | number)[] = [1, "hi"]; // explicit when BCT not obvious
// let mixedInferred = [1, "hi"]; // also (string | number)[] via BCT — inferred, fine
const words = ["hello", "world"];
const lengths = words.map(w => w.length); // w inferred string via context — no annotation needed
console.log(lengths); // [5,5]

// bad — empty array without annotation becomes any[] (silent later)
function fillBad(): void {
  // let xs = []; // with noImplicitAny:false → any[]
  let xs: number[] = []; // fix — annotate intent
  xs.push(1);
  // xs.push("oops"); // now correctly errors: string not assignable to number
  console.log(xs);
}
fillBad();

// bad — unannotated callback parameter without contextual type
// const bad = (x) => x.toUpperCase(); // error under noImplicitAny: Parameter 'x' implicitly has an any type
// fix — let context supply it, or annotate when no context exists
const words2 = ["a", "b"];
words2.forEach((x) => console.log(x.toUpperCase())); // contextual → string, ok
function parsePair(p: string, cb: (value: string) => void): void { cb(p.trim()); }
parsePair(" hi ", value => console.log(value.length)); // value inferred string via cb type

// bad — null-initialized let without annotation locks to null
// let current = null; // null type — can't later assign string
// current = "hi"; // error TS2322
let currentGood: string | null = null; // widens intent to admit string later
currentGood = "hi"; // ok
console.log(currentGood?.toUpperCase()); // HI

// good — generic inference respects widening
function wrap<T>(value: T): { value: T } { return { value }; }
const viaConst = wrap("hi" as const); // T inferred as "hi" (literal) because as const prevented widening
const viaLet = wrap("hi"); // T inferred as string (widened from literal) — depends on call literal context
// Uncomment to see: hover viaConst.value → "hi"; viaLet.value → string
console.log(viaConst.value, viaLet.value);
```

### 5) **Common confusion**

- "`const` objects are immutable and keep literals" — `const` only prevents *reassigning the variable*; it does not freeze property literals. `const obj = { x: 1 }` still infers `{ x: number }` (mutable, widened). Use `as const` to freeze (`{ readonly x: 1 }` with `x: 1` literal).
- "`Array<T>` inference is just union of elements" — that's the *BCT* shorthand. For `let xs = [1, 2]` BCT is `number[]` (all elements `number`); for `[1, "a"]` BCT is `(string | number)[]`. For empty `[]`, there is no BCT — the checker falls back to `never[]`/`any[]` and requires annotation.
- "`noImplicitAny` affects widening" — it doesn't disable widening; it *flags* places where inference would otherwise fall back to `any` (untyped callbacks, empty collections). Widening (`let x = "hi"` → `string`) happens regardless.

### 6) **Performance note**

Inference granularity has checker cost. Widely inferred BCTs (`(string | number | Date)[]`) increase the type-checker's union branching factor — each downstream operation checks against every member. Prefer precise annotations for public signatures (`function f(xs: string[]): void` not `function f(xs: (string | number)[]): void` when only one is intended) to keep the control-flow graph shallow. The emit cost is zero (erased). The engineering cost of surprising widening is *bug density*: widened `let` that should have been a literal union silently admits wrong values — cheaper to annotate the union at declaration than to debug at the call site.

### 7) **Mentor note**

Have students hover `let x = "hi"` vs `const x = "hi"` vs `let x = "hi" as const` and explain all three. Then give them `let empty = []; empty.push(1); empty.push("a");` and ask what hover shows — watch them realize `any[]` leaked. Review checklist: function callbacks rely on contextual typing (no extra param annotations); exported `let` bindings initialized to `null`/`[]` have explicit type annotations; empty collections never use inference — they declare intent.
