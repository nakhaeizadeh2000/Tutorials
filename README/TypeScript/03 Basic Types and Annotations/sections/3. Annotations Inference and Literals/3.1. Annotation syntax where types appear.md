## 3.1. Annotation syntax where types appear

### 1) **Where you may annotate** (variable `let x: string`, parameter `(x: string)`, return `(): string`, property `prop: string`, `as` vs `satisfies` at the value site)

**Definition** — an *annotation* is the `: Type` syntax that places a type in type space alongside a value declaration. Annotations never change runtime behavior — they erase (see [Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)) and exist only for the checker and the language server. As of TypeScript 5.9 era, every annotation you write should be removable by stripping types alone (see [choosing erasable syntax](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>) and `--erasableSyntaxOnly`).

**The six annotation sites** (the only places `: Type` is valid):

```typescript
let x: string = "hi";                       // 1) variable
function f(p: string): string { return p; } // 2) parameter, 3) return
type T = { prop: string };                  // 4) property (inside type/interface)
const obj = { value: "hi" as string };      // 5) assertion at value site (as)
const s = "hi" satisfies string;            // 6) satisfies — checks without widening to the target
class C { prop: string = "hi"; }            // property (class field — same as type property but with emit)
```

- **`as` vs `satisfies`** — `as string` casts and widens (or narrows) without checking shape compatibility beyond assignability; `satisfies string` checks that the *value's* type satisfies `string` but preserves the literal type (added TS 4.9, idiomatic as of 5.9 era). Prefer `satisfies` when you want checking without losing literal information (preview in [3.3. Literal types and const assertions](<./3.3. Literal types and const assertions.md>)).

### 2) **Where you must not** (no runtime annotation semantics — annotations erase; `erasableSyntaxOnly` catches non-erasable attempts)

- **Annotations do not validate at runtime** — `function f(x: string) {}` still accepts a `number` if a caller bypasses the checker (via `any`, `as`, or plain JS call). Trust the annotation only if the call site is checked; otherwise validate with `unknown` + predicate (see [2.2. unknown](<../2. The Special Types/2.2. unknown the type-safe top type.md>)).
- **Non-erasable syntax is forbidden under modern flags** — `enum E { A, B }`, `namespace N { export const x = 1; }`, and legacy `parameter properties` (`constructor(private x: string)`) require a transform, not just stripping. With `--erasableSyntaxOnly: true` (TS 5.8+), these correctly error (`TS1294`). The modern alternatives are erasable: string literal unions for enums, modules for namespaces, explicit class fields (see [1.2. bigint](<../1. The Primitive Family/1.2. bigint and symbol the ES-era primitives.md>) for erasable inventory).
- **No annotation on destructuring default alone** — `function f({ x = 1 }) {}` infers `x: number` from the default; writing `function f({ x: string = 1 })` is syntax-invalid — annotate the whole pattern: `function f({ x }: { x: string })` or with defaults `function f({ x = "hi" }: { x?: string })`.

### 3) **Annotation style in code review** (annotate public contracts and exported signatures; let locals infer — signal vs noise trade-off)

**Modern guidance** — annotate where the checker *cannot* infer the contract, and where readers need a promise without hovering:

| Annotate | Infer (let the checker work) |
|---|---|
| Exported functions (`export function f(x: string): string`) — callers can't hover your locals | Local variables inside a function body (`let sum = 0;`) — hover shows `number` |
| Public class/interface members (`prop: string`) | Internal `const` derived from annotated inputs (`const doubled = x * 2`) |
| Generic call sites where inference would be `unknown`/`any` (`JSON.parse as (s: string) => User`) | Arrow callbacks where contextual typing infers params (`arr.map(v => v.length)`) |

- **Why this division** — exported types are *documentation that checks* (refactoring proof); locals are *noise* if annotated (they duplicate what the checker already knows and drift when the implementation changes). The review signal: if removing an annotation changes no call-site error, the annotation was noise.
- **`--isolatedDeclarations` and explicit returns** — TS 5.5+ `isolatedDeclarations` (used for parallel `.d.ts` generation) requires exported functions to have explicit return types so sub-processes can emit declarations without re-analyzing call graphs. Even without the flag, explicit return annotations on exports future-proof the repo for `isolatedDeclarations` adoption.

### 4) **Runnable example** — annotation sites and style (good vs bad)

```typescript
// good — annotate contracts, infer locals; erasable, --erasableSyntaxOnly ok
export type User = { id: string; name: string };
export function getUser(id: string): User | null {
  // locals inferred — no need to annotate
  const raw = localStorage.getItem(`user:${id}`); // inferred string | null (lib DOM types)
  if (raw === null) return null;
  const parsed: unknown = JSON.parse(raw); // boundary: unknown
  // narrow via predicate (see 2.2) — not via as
  if (isUser(parsed)) return parsed;
  return null;
}
function isUser(v: unknown): v is User {
  return typeof v === "object" && v !== null && "id" in v && "name" in v;
}

// bad — over-annotated locals (noise, drifts)
function countBad(items: string[]): number {
  const len: number = items.length; // noise — inferred as number already
  const first: string | undefined = items[0]; // ok at boundary but noisy if inferred via non-null guard below
  if (first === undefined) return 0;
  const upper: string = first.toUpperCase(); // noise — already string after guard
  return upper.length; // number — inference handles it
}

// good — satisfies preserves literal while checking shape (TS 4.9+, idiomatic 5.9 era)
type Route = { path: string; method: "get" | "post" };
const routeGood = { path: "/users", method: "get" } satisfies Route; // checks Route, keeps "get" literal
// routeGood.method is "get" — not widened to "get" | "post"
const routeBadAs = { path: "/users", method: "get" } as Route; // checks too, but widens method to "get" | "post"
// const usesAs = routeBadAs.method === "post"; // broader than needed

// bad — non-erasable enum under erasableSyntaxOnly (should error)
// enum Direction { Up, Down } // TS1294 under --erasableSyntaxOnly — use literal union instead
type Direction = "up" | "down"; // erasable — no emit

// bad — annotation on destructured default (syntax error)
// function drawBad({ radius: number = 10 }) {} // parse error
// fix — annotate the pattern
function drawGood({ radius = 10 }: { radius?: number }): void {
  console.log(radius);
}
drawGood({ radius: 5 }); // 5
drawGood({}); // 10 — default works with optional annotation

// bad — assertion skips validation (trusts without proof)
function getBad(id: string): User {
  return JSON.parse(localStorage.getItem(`user:${id}`)!) as User; // might be null/invalid — no check
}
// fix — use unknown + predicate as in getUser above
```

### 5) **Common confusion**

- "More annotations = safer" — beyond exported contracts, extra annotations *hide* inference bugs (you pin the wrong type and the checker trusts you). Prefer fewer, correctly placed annotations.
- "`as` is the same as annotation `:`" — `let x: string = 1 as string` hides an error via cast; `let x: string = 1` correctly errors. Use `: T` to *check*; use `as T` only when you have a runtime proof the checker can't see.
- "`satisfies` changes runtime" — it doesn't; it only checks and preserves literal type. At emit it's gone, like every other annotation (see erasable inventory — still covered by `--erasableSyntaxOnly`).

### 6) **Performance note**

Annotations have no runtime cost (erased) and negligible checker cost — the checker already builds the type graph from them. The cost of *too many* annotations is *human* review latency: PRs with noisy locals require more diff reading and more opportunities for annotation/implementation drift. The cost of *too few* on exports is slower fix suggestions: the language server must hover locals to infer contracts, so auto-complete for external callers improves measurably when exported signatures are explicit (no benchmark, but observable in large monorepos with `isolatedDeclarations` parallel builds — each file can emit `.d.ts` without re-analyzing callees).

### 7) **Mentor note**

Teach "annotate the contract, not the computation". Review exercise: give students a function with every local annotated, ask them to delete annotations until removing one would change a call-site error — whatever remains is the contract. Checklist: exported functions have explicit param + return types (future-proof for `isolatedDeclarations`); internal `let`/`const` rarely need them; `as` appears only beside a comment explaining the proof; `satisfies` appears where literal identity matters (route configs, test fixtures).
