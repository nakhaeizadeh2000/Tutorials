## 3.1. Annotation syntax where types appear

### 1) **Where you may annotate**

A type annotation places a contract beside a declaration, such as `let name: string`, a parameter `value: number`, a return `(): string`, or a class member `label: string`. Types also describe object members and whole callable signatures. These are common sites, not an exhaustive grammar of every TypeScript construct.

An annotation is checked against its initializer or implementation. It does not convert, initialize or validate a runtime value. The `as` assertion and `satisfies` expression are separate syntax: an assertion asks for a particular static view under assertion compatibility rules, while satisfies checks an expression against a contract without replacing its result with the target type. Context can still affect inference; neither syntax has a universal “preserve every literal” rule.

Use TypeScript 7.0.2 and Node.js 20.20.2. Save this complete module as `annotations.mts` in an empty directory.

```typescript
// annotations.mts
export type User = { id: string; name: string };
export function summarize(user: User): string {
  const upper = user.name.toUpperCase();
  return `${user.id}:${upper}`;
}
const user: User = { id: "u1", name: "Ada" };
const format: (value: number) => string = value => value.toFixed(1);
class Label {
  text: string;
  constructor(text: string) { this.text = text; }
}
function radius({ radius = 10 }: { radius?: number }): number { return radius; }
function renamed({ radius: number = 10 }: { radius?: number }): number { return number; }
console.log(summarize(user), format(2), new Label("local").text);
console.log(radius({}), renamed({ radius: 5 }));

type Route = { path: string; method: "get" | "post" };
const checked = { path: "/users", method: "get" } satisfies Route;
const asserted = { path: "/users", method: "get" } as Route;
console.log(checked.method, asserted.method);
export const version = 1;
export function literal() { return 2; }
```

```sh
tsc --strict --erasableSyntaxOnly --target ES2022 --module NodeNext --noEmitOnError --outDir dist annotations.mts
node dist/annotations.mjs
```

Output:

```text
u1:ADA 2.0 local
10 5
get get
```

The declared User supplies a checked argument shape, while the local `upper` is inferred from its string member. The callable variable supplies context for its arrow parameter. A typed class field still needs runtime initialization; its assignment is ordinary JavaScript. These choices give the reader a contract without annotating every intermediate expression.

The two radius functions expose a subtle syntax distinction. In a binding pattern, `radius: number` renames the radius property into a local variable named `number`; it is valid JavaScript syntax, not a type annotation. Its default remains 10. The annotation **after the whole pattern** specifies the expected object type. If you intend a local variable named radius with a number type, use the first form.

### 2) **Where a type cannot supply runtime behavior**

Append each independent probe and compile, restoring the original between checks:

```typescript
const wrong: User = { id: "u1", name: 42 };
```

```typescript
const wrongAssertion = 1 as string;
```

```typescript
const wrongRoute = { path: "/users", method: "delete" } satisfies Route;
```

The diagnostics are TS2322, TS2352 and TS2322. Assertions are not accepted for every incompatible pair. A deliberate intermediate unknown assertion could bypass that relation, but would still create no valid string operation or user field.

An external caller can also violate an erased annotation. Parse unknown input before entering trusted domain code when the producer is outside the checked contract. This lesson uses constructed values so that no undeclared storage service or browser API is needed. The [unknown owner](<../2. The Special Types/2.2. unknown the type-safe top type.md>) supplies complete malformed-input checks.

Some TypeScript syntax requires transformation beyond erasing types. That is a separate toolchain decision, owned by [syntax choices](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>). A permitted annotation does not prove that every file or imported dependency can run through a particular stripping host.

### 3) **Annotation style in code review**

Annotate where the contract expresses intent, constrains an implementation or supplies missing context. A public return annotation can publish a stable supported type instead of an accidentally narrow inferred implementation. A local annotation can also be valuable: `const numbers: number[] = []` states an element invariant that evolving inference alone might not express. Conversely, repeating an obvious local primitive type can add noise without a useful constraint.

Ask what would become less clear or less constrained if an annotation disappeared. The answer may involve API meaning, diagnostic placement or future changes, not just today's error count. Inspect inferred declarations when reviewing a published API. There is no universal public/local annotation quota.

`isolatedDeclarations` adds separate declaration-generation restrictions, but it does not require every export to have an explicit annotation and does not launch parallel workers itself. Check this module's supported inferred exports:

```sh
tsc --strict --erasableSyntaxOnly --target ES2022 --module NodeNext --declaration --isolatedDeclarations --emitDeclarationOnly --noEmitOnError --outDir types annotations.mts
```

The command passes, producing `types/annotations.d.mts` with `version = 1` and `literal(): number`. Trivial inference is permitted. More complex exported expressions can require explicit contracts; the complete [isolated-declaration project](<../../../13 Configuration and Compiler Options/sections/2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>) and [syntax-choice extension](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>) demonstrate the actual failure and repair. These compiler restrictions are not a general editor-completion requirement.

### 4) **Common confusion**

A colon inside a destructuring binding does not mean the same thing as a colon after a parameter pattern. An assertion is also not interchangeable with a checked annotation. Read the surrounding syntax before deciding whether a word names a type, a property or a local variable.

Satisfies checks compatibility, while an explicit annotation can deliberately expose the target contract. The example prints the same methods for both views. Actual inferred property precision, mutability and const assertions belong in the next two lessons; no runtime freezing follows from any of these annotations.

### 5) **Performance note**

Annotations, assertions and satisfies expressions erase. Constructing Label, formatting strings and calling functions remain executable work. Declaration isolation can support particular build architectures, but the flag alone is not a measured speed improvement. No checker latency or editor completion benchmark was run. Prefer a clear, accurate contract, then measure a demonstrated tooling bottleneck.

### 6) **Mentor note**

Ask the learner to explain both uses of the colon in renamed. Then remove the callable variable's signature: which input information is no longer provided to its arrow? Finally compare a stable public return contract with the inferred version/literal exports and explain why the declaration command accepts them. Assess the reason for each annotation instead of requiring a fixed style count.
