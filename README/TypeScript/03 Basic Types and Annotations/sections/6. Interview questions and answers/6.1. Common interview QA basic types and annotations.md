## 6.1. Common interview Q&A — basic types and annotations

### 1) **string vs String** (why the lowercase is correct and when the wrapper type appears in `.d.ts`)

**Q: "Should I use `string` or `String` in a signature?"**

- **Senior answer** — lowercase `string` describes the primitive (`"hi"`, `typeof "hi" === "string"`). Uppercase `String` describes the boxed object (`new String("hi")`, `typeof new String("hi") === "object"`). You almost never want the object: it allocates, breaks `Map`/`Set` key equality (`new String("a") !== "a"`), and is only needed when describing legacy APIs that intentionally construct wrappers. Use `string` plus lint `no-wrapper-object-types`; the only place `String` legitimately appears is in `.d.ts` for old libraries that return wrappers (see [1.1. string number boolean](<../1. The Primitive Family/1.1. string number boolean and the wrapper pitfall.md>)).

| Signature | Caller experience | Review verdict |
|---|---|---|
| `function f(x: string)` | primitives — no allocation | correct |
| `function f(x: String)` | primitives silently accepted via compat, but hover misleads; `new String("a")` object allowed | flagged — use `string` |

- **Follow-up:** "Why does `const x: String = "hi"` compile if it's wrong?" — structural leniency: primitives are compatible with `String` for JS compat, so the error is *style* not *type error* — that's why linting catches it.

### 2) **any vs unknown vs never** (three "not sure" flavors — assignability table interviewers probe)

**Q: "When would you use `any`, `unknown`, and `never`?"**

- **Expert answer** — they differ in proof obligations:

| Type | Assigns *to* it? | You can assign it *to* ...? | Property access | Interview cue |
|---|---|---|---|---|
| `any` | any → `any` ok | `any` → `string` ok (leaks) | `x.foo` ok | "I want to disable checking here" — budget it, comment ticket # |
| `unknown` | any → `unknown` ok | `unknown` → `string` error until narrowed | `x.foo` error | "I want to force a check at the boundary" — `JSON.parse` → `unknown` + predicate/schema |
| `never` | nothing → `never` (no value) | `never` → `string` ok (bottom) | — | "This branch never returns" — exhaustiveness (`switch` → `const _ex: never = s`) |

- **Modern guidance** (as of TS 5.9 era, `--strict` with `useUnknownInCatchVariables`) — default to `unknown` at boundaries; treat `any` as explicit debt (`any` count in CI trends down); use `never` for unreachable branches and filter conditionals. Interview signal: `unknown` requires `typeof`/`instanceof`/`in` or schema validation (`zod`) before use — `as T` after `unknown` is the anti-pattern ("parse, don't assert").

```typescript
let anyVal: any = 123; let s1: string = anyVal; // ok — leak
let unk: unknown = 123; // let s2: string = unk; // error — need guard
if (typeof unk === "string") { let s2: string = unk; } // only `typeof` branch would narrow — here error shows guard matters

function fail(msg: string): never { throw new Error(msg); }
type Status = "a" | "b";
function handle(s: Status): number {
  if (s === "a") return 1;
  if (s === "b") return 2;
  const _ex: never = s; // exhaustiveness
  return _ex;
}
```

### 3) **null vs undefined with strictNullChecks** (what changes when the flag flips)

**Q: "What does `strictNullChecks` do? Explain `null` vs `undefined`, and `prop?: string` vs `prop: string | undefined`."**

- **Senior answer** — without `strictNullChecks` (pre-TS 2.0 behavior), `null`/`undefined` are assignable to every type (`let s: string = null` compiles) — every string might be missing at runtime. With `strictNullChecks: true` (part of `--strict`, default since `tsc --init` as of TS 5.9 era), `null`/`undefined` are distinct types: `let s: string = null` → error; you must write `string | null` or `string | undefined` to admit absence, and call sites must narrow (`if (s != null)`, `s?.length`, `s ?? "default"`).

|Declaration|Key may be missing?|Value may be `undefined` when present?|JSON after `{"k": undefined}`?|
|---|---|---|---|
|`prop?: string`|yes (`{}` ok)|yes with default `exactOptionalPropertyTypes:false`|key stripped|
|`prop: string \| undefined`|no (`{}` error)|yes (`prop: undefined` required)|key stripped|
|`prop: string \| null`|no|no|key preserved as `null`|

- **`exactOptionalPropertyTypes:true` nuance** (TS 4.4+, opt-in stricter) — `prop?: string` means *missing or string* only; `{ prop: undefined }` becomes an error unless you write `prop?: string | undefined`. This catches the wire bug where `JSON.stringify` distinguishes missing vs `undefined`-valued — enable on new codebases once the team can articulate the difference (see [1.3. null and undefined](<../1. The Primitive Family/1.3. null and undefined strictNullChecks and optionality.md>)).

- **Follow-up:** "When do you use `null` vs `undefined`?" — `undefined` is implicit absence (missing property, default param, `void` return); `null` is explicit domain empty (database nullable column, JSON `null` wire). Pick one per API and keep it consistent; `??` and `== null` handle both.

### 4) **When to annotate** (public API vs local inference — the code-review answer that signals seniority)

**Q: "Should every variable be typed? When do you skip annotations?"**

- **Senior answer** — annotate *contracts* (exported functions `export function f(x: string): string`, public properties, boundary types); infer *locals* (`let sum = 0`, `const mapped = xs.map(v => v.length)` where `v` is contextually `string`). The rule: if removing an annotation changes no call-site error, the annotation was noise that duplicates inference and risks drift. If callers can't hover your locals (exported signature), the annotation is documentation that checks.

| Annotate | Infer |
|---|---|
| `export function fetchUser(id: string): Promise<User \| null>` | `let raw = await fetch(...)` → type from signature |
| `type Route = { path: string; method: "get" \| "post" }` + `satisfies Route` | `const route = { path: "/users", method: "get" } satisfies Route` — literal `"get"` preserved via check |
| Generic boundary where inference falls back to `any` (`let xs: number[] = []`) | `arr.forEach(v => v.length)` — `v` inferred via context, no annotation |

- **Advanced cue** — `isolatedDeclarations` (TS 5.5+) requires explicit return types on exports to allow parallel `.d.ts` generation — annotate exports even more aggressively when that flag is planned. `satisfies` checks shape without widening literals (prefer over `as T`); `as T` hides the proof — use only with a comment explaining why the checker can't see it.

### 5) **Literal types and widening** (why `let x = "hello"` is `string` but `const x = "hello"` is `"hello"`)

**Q: "Why does `let x = 'hello'` give `string`? How do you keep the literal?"**

- **Expert answer** — *widening*: `let` is reassignable, so the checker widens the literal `"hello"` to its base primitive `string` (anticipating reassignment to another string). `const` is not reassignable, so it keeps the literal type `"hello"` (literal is subtype of `string`). Within objects, properties widen even for `const` bindings: `const obj = { mode: "fast" }` → `mode: string` — because properties are mutable (`obj.mode = "slow"` allowed). To freeze literals, use `as const` (deep `readonly` + literal) or an explicit literal annotation / union.

| Form | Type of `value` | To keep literal |
|---|---|---|
| `let v = "hello"` | `string` | `let v: "hello" = "hello"` or `as const` |
| `const v = "hello"` | `"hello"` | default |
| `const obj = { mode: "fast" }` | `string` | `as const` → `"fast"` + `readonly` |
| `const arr = ["a","b"]` | `string[]` | `as const` → `readonly ["a","b"]`, `typeof arr[number]` → `"a" \| "b"` |

```typescript
type Mode = "fast" | "slow";
let modeW: Mode = "fast"; // widened via annotation → ok (pinned union)
const modeL = "fast"; // "fast" — literal, assignable to Mode
const obj = { mode: "fast" } as const; // { readonly mode: "fast" } — property literal kept
let widened = "fast"; // string — setStatus(widened) would error for Mode union — fix via annotation or const

// literal union as erasable enum
type Status = "idle" | "loading" | "done";
// handleStatus("offline") // error — literal not in union — versus `string` which would accept any string
```

- **Interview signal** — widening vs `as const` vs `satisfies`: `as const` narrows and deep-readonly; `satisfies T` checks assignability while preserving literals; `as T` widens to exactly `T`. Review answer mentions all three and `exactOptionalPropertyTypes` interaction for wire types.
