## 6.1. Common interview Q&A — basic types and annotations

### 1) **String versus String**

**Question:** What contract does each spelling provide?

Lowercase string describes primitive strings. Uppercase String is broader: a primitive can be assigned to it, and it can describe a constructed wrapper. An annotation does not perform boxing. Passing a constructed String to a string parameter is rejected with TS2345 in the [verified checklist](<../4. Important points to remember/4.1. Basic types checklist mental models mentors insist on.md>).

Prefer primitive contracts for ordinary text. If an API deliberately exchanges wrapper objects, describe and test that actual behavior; it is not limited by a rule that wrappers may appear only in old declaration files. The [Everyday Types reference](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#the-primitives-string-number-and-boolean) establishes the primitive recommendation. Follow up by asking why two separately constructed wrappers are different object keys even if their text matches.

### 2) **Any, unknown and never**

**Question:** Which type describes uncertainty, unchecked use or an impossible case?

Any opts out of useful restrictions and can pass unchecked assumptions onward. Unknown accepts an uncertain value but requires evidence before a string-only use. Never represents an impossible value or branch; it is not another “not sure” state. A value typed never can flow into a string target, while an ordinary string cannot satisfy never. An exhaustive branch checks that no declared possibility remains.

Use this compile-only probe as `compile-only.ts`. Its ambient declarations model type relationships; do not emit/run it as a runtime program:

```typescript
export {};
declare const impossible: never;
const text: string = impossible;
declare const uncertain: unknown;
// @ts-expect-error unknown needs evidence before assignment to string.
const unchecked: string = uncertain;
// @ts-expect-error a string cannot satisfy a never target.
const cannotExist: never = "Ada";
```

With TypeScript **7.0.2**, `tsc --strict --noEmit compile-only.ts` exits 0: both expected-error directives were used and the never-to-string assignment was accepted. Removing the directives reports TS2322 for unknown-to-string and string-to-never, exit 1. The [never reference](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#the-never-type) supports the assignment direction. Full top/bottom and ignored-return distinctions belong to [never and void](<../2. The Special Types/2.3. never and void bottom vs deliberate nothing.md>).

### 3) **Nullability, optionality and JSON presence**

**Question:** Does requiring `search: string | undefined` preserve search on the JSON wire?

No. Required means the TypeScript object must supply that property; undefined still lacks an ordinary JSON property representation. Missing and present undefined-valued properties can differ under in or Object.keys but both serialize with the key omitted. A null-valued property is serialized as null. [ECMA-262 JSON.stringify](https://tc39.es/ecma262/multipage/structured-data.html#sec-json.stringify) establishes that distinction.

Strict null checking and exactOptionalPropertyTypes affect permitted assignments. The exact-optional flag is a separate choice: `{ search?: string }` rejects an explicitly undefined value under that flag unless undefined is included in its value union. It does not change serialization. Use the [pitfalls fixture](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by basic type misunderstandings.md>) to test a serialized receiving contract. Follow up by asking whether the protocol chooses omission or an explicit-null placeholder and how its consumer checks the choice.

### 4) **When to annotate**

**Question:** How do you choose between an explicit contract and local inference?

Write an annotation when it states public intent, restricts future changes or satisfies a relevant declaration-tool contract. Let straightforward locals infer when their type already communicates the intended use. An annotation can remain useful even when today's inference matches it; removing it and seeing no immediate error is not sufficient evidence that it was noise.

Inspect actual inference before claiming a fallback to any. The [evolving-array exercise](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by basic type misunderstandings.md>) demonstrates accepted mixed inference, a real unresolved implicit-type error and an explicit numeric invariant. Declaration-option requirements belong to [configuration](<../../../13 Configuration and Compiler Options/README.md>); they should be checked under that option rather than treated as a promise of universal parallel emission.

### 5) **Literal types and widening**

**Question:** Why can a const object's property widen even though the binding cannot be reassigned?

The binding and its properties have different mutation permissions. A bare const string can preserve its literal, while an ordinary object's mutable string property can be inferred as string. A const assertion preserves literal and readonly information for the covered expression; it does not freeze the runtime object. An assertion to another type uses the asserted target and may lose or change precision; it is not always a widening to string. Satisfies checks assignability and can contribute contextual typing, so verify the exact expression's inferred result.

Save `interview.ts` in a directory without a tsconfig:

```typescript
export {};
const primitive: string = "Ada";
const broad: String = primitive;
console.log("representations:", typeof broad, typeof new String(primitive));
const missing = {};
const present: { search: string | undefined } = { search: undefined };
const explicitNull: { search: string | null } = { search: null };
console.log("presence:", "search" in missing, "search" in present);
console.log("JSON:", JSON.stringify(missing), JSON.stringify(present), JSON.stringify(explicitNull));
const unknownValue: unknown = "Ada";
if (typeof unknownValue === "string") console.log("narrowed:", unknownValue.toUpperCase());
type Status = "idle" | "done";
function handle(status: Status): string {
  switch (status) {
    case "idle": return "wait";
    case "done": return "done";
    default: { const impossible: never = status; return impossible; }
  }
}
console.log("status:", handle("idle"));
let widened = "fast";
const literal = "fast";
const settings = { mode: "fast" };
const fixed = { mode: "fast" } as const;
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type Widened = Expect<Equal<typeof widened, string>>;
type Literal = Expect<Equal<typeof literal, "fast">>;
type Property = Expect<Equal<typeof settings.mode, string>>;
type FixedProperty = Expect<Equal<typeof fixed.mode, "fast">>;
console.log("same initial value:", widened, literal, settings.mode, fixed.mode);
```

Run with **TypeScript 7.0.2 / Node 20.20.2**, verified 2026-10-13:

```bash
tsc --strict --exactOptionalPropertyTypes --target es2022 --module commonjs --lib es2022,dom --outDir dist interview.ts
node dist/interview.js
```

Both commands exit 0. Output:

```text
representations: string object
presence: false true
JSON: {} {} {"search":null}
narrowed: ADA
status: wait
same initial value: fast fast fast fast
```

The four live equality probes verify different static types even though all four initial runtime strings are fast. The presence and JSON observations separately establish the in-memory/wire distinction. Follow up by asking what mutation is permitted through each checked view and what runtime guarantee, if any, the assertion adds.

### 6) **Common confusion**

A checked type is neither a constructor nor a serializer. The uppercase annotation contains a primitive, the const assertion changes static information without freezing, and the required undefined property disappears from JSON. A strong interview answer names the layer it is discussing and supplies the corresponding diagnostic or runtime observation.

Never describes impossibility; unknown describes incomplete evidence. Keep that distinction when explaining the exhaustiveness assignment. The compile-only probe checks assignment directions without pretending to construct a real never value.

### 7) **Performance note**

Type annotations, literal unions and equality probes are erased. Wrapper construction, JSON parsing/serialization and ordinary branching still execute. No compiler, runtime or editor benchmark was measured here. Choose types for the contract they express and measure actual runtime/build work separately rather than inferring a speed improvement from a narrower hover.

### 8) **Mentor note**

Require an answer, a counterexample and a verification layer for each question. Ask the learner to explain why the JSON strings match despite different in-memory presence, and why identical runtime strings have different checked types. These explanations expose stronger understanding than reciting a type table.

Have the learner turn one answer into a small failing-then-passing probe without executing ambient compile-only declarations. In review, ask which invariants the annotation documents and which guarantees still need a runtime operation or boundary check.
