## 4.1. Basic types checklist — mental models mentors insist on

### 1) **Primitives are unboxed**

Choose lowercase string, number and boolean for primitive contracts. A primitive string can be assigned to the broad String type, but a String wrapper is rejected by a string parameter. These are different assignment directions, not a compiler rule that both calls compile and a linter catches the distinction later. A type annotation also does not box a primitive; `new String` constructs an object.

The [Everyday Types reference](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#the-primitives-string-number-and-boolean) recommends primitive spellings. The [no-wrapper-object-types rule](https://typescript-eslint.io/rules/no-wrapper-object-types/) supplies a separate style/contract check; no lint command is executed in this fixture. Diagnose compiler compatibility and lint policy separately.

### 2) **Nullability and property presence are explicit**

Under strict checking, a required string excludes null and undefined. An optional property may be absent; a required string-or-undefined property must be present in the TypeScript object but can contain undefined. With exactOptionalPropertyTypes, an optional string property does not admit an explicitly undefined value unless its value union includes undefined.

That is an in-memory assignment contract. JSON serialization omits ordinary undefined-valued object properties whether the type declared them required or optional; null has a JSON representation. Decide the wire rule deliberately instead of assuming a type annotation preserves a key. The demo compares all three outcomes; the [nullability owner](<../1. The Primitive Family/1.3. null and undefined strictNullChecks and optionality.md>) explains the detailed contract.

### 3) **Any bypasses checks; unknown requires a checked use**

Read uncertain external values as unknown and check the required fields before using them. A predicate's declaration is trusted by the checker, so validate its body with meaningful malformed inputs as well as a passing example. Any removes useful restrictions and can propagate to callers; count-based policies can identify review candidates, but a count does not prove the boundary is correct.

Never represents an impossible case. In a complete switch, assigning the remaining value to never checks that every declared variant has been handled. This is different from void, which describes an ignored return contract. Full mechanics remain in the [never/void owner](<../2. The Special Types/2.3. never and void bottom vs deliberate nothing.md>).

### 4) **Annotate contracts and inspect local inference**

An explicit public return type can state a reviewed API boundary; a local value often needs no repeated annotation. Keep an annotation when it documents intent or rejects an unintended future value, not only when today's inferred type differs. Declaration emission requirements belong to the [configuration owner](<../../../13 Configuration and Compiler Options/README.md>); a flag is not a promise that every tool emits declarations in parallel.

Use satisfies to check a literal against a contract while retaining useful inferred information. As const preserves literal/readonly information for the covered expression, without runtime freezing. The demo's route method stays get and its tuple elements form a finite Id union; use the [literal owner](<../3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>) for the fuller comparison.

### 5) **Run the checklist and change one condition**

Save `checklist.ts` in a directory without a tsconfig. Tested with TypeScript **7.0.2 / Node 20.20.2**, verified 2026-10-13:

```typescript
export {};
// Primitive and wrapper contracts are directional.
function greet(name: string): void { console.log(`hi ${name}`); }
greet("Ada"); // string primitive — ok
// greet(new String("Ada")); // TS2345: wrapper is not assignable to string.
const broad: String = "Ada"; // Accepted, though the primitive contract is usually clearer.
console.log(typeof broad, typeof new String("Ada"));

// nullability explicit — three spellings
type InputA = { title?: string };                 // may be missing
type InputB = { title: string | undefined };     // always key, may be undefined
type InputC = { title: string | null };          // always key, may be null
const a: InputA = {}; // ok — missing allowed
const b: InputB = { title: undefined }; // ok — explicit undefined required
const c: InputC = { title: null }; // ok — null required
console.log(JSON.stringify(a)); // {}
console.log(JSON.stringify(b)); // {} — undefined-valued property omitted
console.log(JSON.stringify(c)); // {"title":null}

// any leaks vs unknown contains
function parseUnknown(json: string): unknown { return JSON.parse(json); }
const raw: unknown = parseUnknown('{"name":"Ada"}');
function isNamed(v: unknown): v is { name: string } {
  return typeof v === "object" && v !== null && "name" in v && typeof v.name === "string";
}
if (isNamed(raw)) console.log(raw.name.toUpperCase()); // ADA

// never exhaustiveness + annotate contracts / infer locals
type Status = "idle" | "loading" | "done";
export function handleStatus(s: Status): string { // exported — annotate param + return
  switch (s) {
    case "idle": return "wait";
    case "loading": return "...";
    case "done": return "done";
    default: { const _ex: never = s; return _ex; }
  }
}

// literal preservation via satisfies + as const
type Route = { path: string; method: "get" | "post" };
const route = { path: "/users", method: "get" } satisfies Route; // method stays "get"
const ids = ["low", "med", "high"] as const;
type Id = typeof ids[number]; // "low"|"med"|"high"
const idGood: Id = "high"; // ok
console.log(route.method, idGood); // get high
console.log(handleStatus("idle"));
```

Run:

```bash
tsc --strict --exactOptionalPropertyTypes --target es2022 --module commonjs --lib es2022,dom --outDir dist checklist.ts
node dist/checklist.js
```

Both commands exit 0. Output:

```text
hi Ada
string object
{}
{}
{"title":null}
ADA
get high
wait
```

The primitive assigned to String is still a runtime string; the explicit wrapper is an object. The two undefined/missing object forms serialize identically here. The name guard enables a checked field use, and the remaining never branch is unreachable for the declared Status variants.

For a separate compiler exercise, activate the commented `greet(new String("Ada"))` call and run `tsc --strict --noEmit checklist.ts`: TS2345, exit 1. Restore that line. Add retrying to the Status union without adding a case: TS2322 at the never assignment, exit 1. Restore the union. Finally, `type Config = { title?: string }; const value: Config = { title: undefined };` checked with `--strict --exactOptionalPropertyTypes --noEmit` produces TS2375, exit 1. These failures establish the actual contract each check enforces; they are not lint or runtime test results.

### 6) **Common confusion**

A capitalized wrapper type does not force its value to be a constructed wrapper. The demo's broad annotation contains a primitive. Conversely, a constructed wrapper cannot be passed to the narrower primitive parameter. Keep both directions in the explanation.

Property presence, value nullability and serialized presence are separate questions. A required undefined-valued property can exist before serialization and disappear afterward. Likewise, readonly and as const are static restrictions, not a runtime freeze.

### 7) **Performance note**

Annotations, literal types and the never check add no runtime type representation. Wrapper construction and property guards are ordinary JavaScript work. This fixture does not measure allocation throughput, checker cost or lint latency; use primitive contracts for the intended semantics, then measure a real performance concern in its owning runtime/build environment.

### 8) **Mentor note**

Ask the learner to predict the wrapper diagnostic, both JSON omissions and the unhandled-status error before running the exercises. A sound answer separates source checking, runtime representation and serialization instead of treating all three as a consequence of the annotation.

In review, ask why a public type was chosen and what malformed input disproves the guard's promise. Retain useful intent annotations even when inference happens to match today. An annotation quota or a blanket cast ban cannot replace that explanation.
