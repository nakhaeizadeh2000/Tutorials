## 2.2. unknown the type-safe top type

### 1) **Top type that forces a check**

`unknown` lets a function receive any value while withholding permission to assume its shape. A string, number, object or `null` can enter an `unknown` parameter. The function must establish what it received before reading properties or using it as a more specific type. This is useful at a boundary where the producer is outside the checked program.

| Operation | With `unknown` | What supplies the missing information? |
|---|---|---|
| Store a value as `unknown` | Allowed | No shape is promised |
| Assign it to `string` | Rejected | A string check or another valid narrowing |
| Read an arbitrary property | Rejected | Establish an object and the relevant property |
| Call it | Rejected | Establish a callable type |
| Assign it to `any` | Allowed | Checking is deliberately abandoned |

The last row is why “assignable to nothing” is too absolute. `unknown` can flow to `unknown` and `any`; a type assertion can also bypass the restriction. None of those operations validates data. The [3.0 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-0.html) introduce the type; these examples use TypeScript 7.0.2.

Save this as `assignability.ts` in a fresh directory without a `tsconfig.json`:

```typescript
export {};
function inspect(value: unknown): void {
  const held: unknown = value;
  // @ts-expect-error: unknown is not established as string
  const unchecked: string = held;
  if (typeof held === "string") {
    const checked: string = held;
    console.log(checked.toUpperCase());
  }
}
inspect("Ada");
inspect(42);
```

Run `tsc --strict --target es2022 --module commonjs --outDir dist assignability.ts`, then `node dist/assignability.js`. It prints `ADA`. The expected-error directive verifies a rejected assignment; removing it produces TS2322. The directive does not validate the assigned value at runtime. The actual branch uses a runtime string check.

### 2) **Narrowing unknown**

Control-flow checks such as `typeof`, `instanceof`, equality, and an object/non-null check followed by `in` establish particular facts. A check must prove what the next operation needs. Finding a `name` key does not prove that its value is a string. An assertion such as `raw as User` simply asks the checker to trust that claim.

An important library exception is `Array.isArray`: with the checked compiler declarations, it narrows an unknown value to `any[]`, not `unknown[]`. The [TypeScript issue about this behavior](https://github.com/microsoft/TypeScript/issues/43865) explains the historical compatibility concern. Array identity proves neither element types nor index presence. Explicitly receive the result as `readonly unknown[]` when examining untrusted elements; each element then needs its own check.

Save this complete example as `boundaries.ts`:

```typescript
export {};
type User = { id: string; name: string; email: string };

function isUser(value: unknown): value is User {
  return typeof value === "object" && value !== null
    && "id" in value && typeof value.id === "string"
    && "name" in value && typeof value.name === "string"
    && "email" in value && typeof value.email === "string";
}
function parseUser(value: unknown): User {
  if (!isUser(value)) throw new Error("invalid user payload");
  return value;
}
function sumUnknownValues(value: unknown): number {
  if (!Array.isArray(value)) throw new Error("expected array");
  const elements: readonly unknown[] = value;
  let sum = 0;
  for (const element of elements) {
    if (typeof element !== "number") throw new Error("expected number element");
    sum += element;
  }
  return sum;
}
function uncheckedFirst(value: unknown): number {
  if (!Array.isArray(value)) throw new Error("expected array");
  const claimedNumber: number = value[0]; // Accepted through any, without a proof.
  return claimedNumber;
}
function observe(label: string, operation: () => unknown): void {
  try { console.log(label, operation()); }
  catch (error) {
    console.log(label, error instanceof Error ? error.message : "non-Error thrown");
  }
}

const raw: unknown = JSON.parse('{"id":"u1","name":"Ada","email":"ada@example.com"}');
observe("user", () => parseUser(raw).email);
observe("bad user", () => parseUser({ id: 123, name: "Ada", email: "x" }));
observe("sum", () => sumUnknownValues([1, 2, 3]));
observe("mixed", () => sumUnknownValues([1, "2"]));
observe("sparse", () => sumUnknownValues([1, , 3]));
observe("object", () => sumUnknownValues({ 0: 1, length: 1 }));
observe("unchecked", () => typeof uncheckedFirst(["text"]));
observe("thrown string", () => { throw "oops"; });
```

Run the same compile/Node commands, replacing `assignability.ts` with `boundaries.ts`. The output is:

```text
user ada@example.com
bad user invalid user payload
sum 6
mixed expected number element
sparse expected number element
object expected array
unchecked string
thrown string non-Error thrown
```

The mixed array is rejected before adding its string. Iteration visits the sparse slot as `undefined`, which is also rejected. The array-like object fails the outer array check. The final `unchecked string` proves that the annotation in `uncheckedFirst` did not convert or validate its element.

This sum accepts JavaScript numbers, including `NaN` and infinities; a finite-number business contract needs an additional check. Likewise, `isUser` checks the shown property types, not an email format or authorization. Named predicates are trusted contracts. Their implementation needs valid and invalid tests; [predicate reasoning](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.3. Custom narrowers predicates asserts and type guards on unions.md>) owns their broader behavior.

### 3) **Where unknown belongs**

Assigning a `JSON.parse` result to `unknown` prevents its historical `any` return from spreading through callers. A parser then returns a domain value or reports failure. Schema libraries can automate those runtime checks, with failure behavior determined by the API you choose. The [schema owner](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.2. Schema objects and inferred types.md>) develops that approach; a handwritten parser is sufficient for the small contract here.

A catch variable also needs care because JavaScript permits throwing strings, numbers and `null`. In the example, `--strict` enables [`useUnknownInCatchVariables`](https://www.typescriptlang.org/tsconfig/useUnknownInCatchVariables.html), so the variable is unknown until checked. Writing `catch (error: any)` opts out of that protection. Do not assume an `Error` merely because an operation failed.

Once a boundary produces a checked value, use its domain type downstream. Repeatedly reparsing the same owned value adds work without establishing a new boundary. If another party can mutate it or introduce new data, reconsider where the next check belongs.

### 4) **Common confusion**

`unknown` is not a validator that runs when a value is assigned. It changes what the checker permits. Runtime validation comes from the checks you write or call. The unchecked array branch shows how a library's `any` can remove that protection even inside a function whose parameter began as unknown.

A successful predicate declaration also does not prove its implementation. Review every promised property, and test malformed values. [Dan Vanderkam's predicate analysis](https://effectivetypescript.com/2024/02/27/type-guards/) also explains why the false branch matters when a predicate narrows a union.

### 5) **Performance note**

`unknown` annotations erase, so changing an annotation from `any` to `unknown` adds no runtime validation by itself. The shown sum inspects each visited element once, making its traversal linear in array length for these checks. It keeps one running total rather than copying the array. A schema parser's cost depends on payloads, refinements and implementation; this lesson establishes no universal microsecond cost or schema-size formula. Measure a relevant workload if validation is significant.

### 6) **Mentor note**

Ask a learner to predict whether `const n: number = value[0]` is rejected immediately after `Array.isArray`. Run `uncheckedFirst(["text"])` to resolve the surprise. Then ask them to annotate the local element view as unknown and explain which runtime check makes addition valid. A sound answer identifies both the outer array fact and the separate element fact. For the user parser, offer a numeric `id` and a missing `email`; neither should reach domain code.
