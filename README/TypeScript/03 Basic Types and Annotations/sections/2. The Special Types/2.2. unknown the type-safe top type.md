## 2.2. unknown the type-safe top type

### 1) **Top type that forces a check** (assignable *from* everything, assignable *to* nothing without narrowing — the safe counterpart to `any`)

**Definition** — `unknown` is the type-safe top type. Every type is assignable *to* `unknown` (`let u: unknown = 123; let v: unknown = "hi";` both ok), but `unknown` is assignable *to* almost nothing without a narrowing proof — `let s: string = u;` is an error until you prove `u` is a `string`. Unlike `any`, `unknown` preserves directionality: it contains every value but promises nothing about shape until you check.

- As of TypeScript 5.9 era (Aug 2026), `unknown` is the disciplined default for boundaries: `JSON.parse` returns `any` historically for compat, but new code wraps it as `(): unknown`, `catch (e)` is `unknown` when `useUnknownInCatchVariables: true` (part of `--strict` since TS 4.4), and `fetch` payloads should be `unknown` until validated.
- **Assignability table** (contrast with [2.1. any](<./2.1. any the unchecked escape hatch.md>)):

| Statement | Result | Why |
|---|---|---|
| `let u: unknown = "hi"` | ok | any string is unknown |
| `let s: string = u` | error | unknown might not be string — need check |
| `if (typeof u === "string") { let s: string = u; }` | ok | narrowed inside branch |
| `u.foo` | error | unknown has no known members |
| `u()` | error | unknown not known to be callable |

### 2) **Narrowing unknown** (`typeof`, `instanceof`, `in`, predicates, `zod`/`valibot` — the only ways to leave `unknown` legally)

- **Built-in guards** — `typeof u === "string"`, `typeof u === "number"`, `u instanceof Date`, `"prop" in (u as object)`, `Array.isArray(u)`. Each guard is a *type guard* that control-flow analysis understands — after `if (typeof u === "string")`, `u` is `string` in that branch.
- **User-defined predicates** — `function isUser(v: unknown): v is { name: string }` is a *type predicate* (`v is T`). The checker trusts your runtime implementation, so a lying predicate breaks soundness globally (see [02/3.3. Unsound spots](<../../../02 The Type System Core/sections/3. Soundness and variance/3.3. Unsound by design spots budgeted risks.md>)).
- **Schema libraries** — `zod`, `valibot`, `arktype` parse `unknown` and return a typed value or throw — they compose narrowing as a value-level program: `const user = UserSchema.parse(raw)` where `raw: unknown`. Modern guidance: at *every* external boundary, `unknown` enters, a schema proves it, the domain sees the proven type.

```typescript
// three narrowing styles, same guarantee
function isString(v: unknown): v is string { return typeof v === "string"; }
const raw: unknown = JSON.parse('"hello"');
if (isString(raw)) raw.toUpperCase(); // ok — inside, raw is string
```

### 3) **Where unknown belongs** (boundaries: network, file, `JSON.parse`, `catch` variables since TS 4.4 `useUnknownInCatchVariables`)

- **The boundary rule** — parse, don't assert: any data from *outside* the type system (network, file, user input, `JSON.parse`, `localStorage`, `URLSearchParams`, `catch` error) enters as `unknown` and exits as a proven domain type. `as` assertions skip validation; `unknown` + predicate/schema validates.
- **Catch variables** — with `useUnknownInCatchVariables: true` (enabled by `--strict`), `catch (e)` is `unknown`, not `any`/`Error`. You must narrow: `if (e instanceof Error) e.message` or stringify with a safe formatter. Without the flag, `catch (e: any)` silently allows `e.foo`.
- **History** — `unknown` added in TS 3.0 (2018); `useUnknownInCatchVariables` added in TS 4.4 (2021). As of TS 5.9 with `--strict`, both are the defaults for greenfield code — disable only for legacy migration.

### 4) **Runnable example** — unknown at boundaries with guards and schemas (good vs bad)

```typescript
// good — unknown boundary with type guard and schema-style validation
type User = { id: string; name: string; email: string };

function isUser(v: unknown): v is User {
  return (
    typeof v === "object" &&
    v !== null &&
    "id" in v &&
    "name" in v &&
    "email" in v &&
    typeof (v as Record<string, unknown>).id === "string" &&
    typeof (v as Record<string, unknown>).name === "string" &&
    typeof (v as Record<string, unknown>).email === "string"
  );
}

function fetchUser(payload: unknown): User {
  if (!isUser(payload)) throw new Error("invalid user payload");
  return payload; // narrowed to User
}

// Simulate network boundary: raw JSON enters as unknown
const raw: unknown = JSON.parse('{"id":"u1","name":"Ada","email":"ada@example.com"}');
console.log(fetchUser(raw).email); // ada@example.com

// bad — as assertion skips validation (compiles, fails at runtime)
function fetchUserBad(payload: unknown): User {
  return payload as User; // no runtime check — lying if payload is wrong
}
// fetchUserBad({ id: 123 }); // compiles, downstream code assumes id is string — breaks

// good — catch unknown requires narrowing
try {
  JSON.parse("not json");
} catch (e: unknown) { // with useUnknownInCatchVariables:true, e is unknown
  if (e instanceof SyntaxError) console.log("JSON syntax error:", e.message);
  else if (e instanceof Error) console.log("other error:", e.message);
  else console.log("thrown non-Error:", String(e));
}

// bad — catch any hides the need to narrow
try {
  JSON.parse("not json");
} catch (e: any) {
  console.log(e.message); // compiles even if e is a string — runtime error if throw "oops"
}

// good — Array.isArray and typeof narrowing for unknown arrays
function sumUnknownValues(values: unknown): number {
  if (!Array.isArray(values)) throw new Error("expected array");
  // values is unknown[] here — need element checks
  let sum = 0;
  for (const v of values) {
    if (typeof v !== "number") throw new Error("expected number element");
    sum += v;
  }
  return sum;
}
console.log(sumUnknownValues([1, 2, 3])); // 6
// sumUnknownValues([1, "2"]); // runtime throw via check, not silent coercion
```

### 5) **Common confusion**

- "`unknown` is just strict `any`" — not strict — it's a different proof obligation. `any` says "trust me everywhere downstream"; `unknown` says "prove it before you proceed". Use `any` to silence; use `unknown` to force a proof.
- "I can assign `unknown` to `string` with a cast" — `as string` bypasses the check you just bought with `unknown`. If you cast, you paid the price of `unknown` without the benefit — prefer narrowing.
- "`catch (e)` is `Error`" — with `useUnknownInCatchVariables`, it's `unknown` because JavaScript can `throw "oops"` (string), `throw 42` (number), or `throw null`. The checker now models the runtime truth — narrow before accessing `.message`.

### 6) **Performance note**

`unknown` has identical emit to `any` (erased) and identical runtime branches (`typeof` checks compile to the same JavaScript). The perf win is *fewer production failures*: validating `unknown` at the boundary prevents `TypeError: payload.name is undefined` downstream — fewer error-path allocations and telemetry spikes. `zod`/`valibot` parsing adds microseconds per payload (validate in O(m) where m is schema size) — cheaper than debugging corrupt domain state.

### 7) **Mentor note**

Teach "parse, don't assert" as the boundary mantra. Review checklist: every function that touches external data has `unknown` in its inbound signature until a guard/schema proves otherwise — if you see `as User` on the same line as `JSON.parse`, ask "where's the proof?". Exercise: give students a `fetch` payload typed as `any` and ask them to refactor to `unknown` + `isUser` + schema, then attempt `throw "oops"` in a `catch` block — watch the checker force handling of non-`Error` throws.
