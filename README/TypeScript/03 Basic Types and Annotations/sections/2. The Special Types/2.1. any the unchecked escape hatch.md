## 2.1. any the unchecked escape hatch

### 1) **What any disables**

`any` permits unchecked operations on a value: arbitrary property access, calls and assignment into many ordinary typed positions. Those operations may compile even when the value cannot support them at runtime. The permission is local to the checking relationship, not a switch that disables every check in the file.

For example, an any value can be assigned to string without a string check. An unrelated `const count: number = "wrong"` still fails, and assigning any to never also fails. Calling any “both top and bottom” hides that distinction. The [primary introduction](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#any) explains its permissive use; the explicit never probe below checks the boundary on this compiler.

`noImplicitAny`, enabled by strict mode, reports certain inference failures such as an untyped function parameter. It does not ban explicit any or every occurrence of any in a library result. Inspect where unchecked information enters and which useful fact is missing before choosing a repair.

### 2) **How it leaks**

A function returning any gives its callers unchecked results. An `any[]` similarly exposes unchecked elements. Assigning either result to a narrower annotated variable does not validate the value. Even annotating the function's return can conceal the unchecked implementation if it returns an any expression.

Use TypeScript 7.0.2 and Node.js 20.20.2. Save this complete fixture as `any.mts` in an empty directory. Its legacy provider is local and deliberately misbehaves; no external library is required.

```typescript
// any.mts
function legacy(): any { return { name: 42 }; }
function expectedFailure(label: string, action: () => void): void {
  try { action(); }
  catch (error) {
    if (error instanceof TypeError) { console.log(label, "TypeError"); return; }
    throw error;
  }
  throw new Error(`${label}: expected failure`);
}
const unchecked = legacy();
const claimedName: string = unchecked.name;
expectedFailure("name", () => { claimedName.toUpperCase(); });
function apparentlyTyped(): string { return legacy().name; }
console.log("annotated result", typeof apparentlyTyped());

const elements: any[] = [1, "oops"];
const first: number = elements[0];
const second: number = elements[1];
console.log("elements", typeof first, typeof second);
expectedFailure("element", () => { second.toFixed(1); });

function adaptLegacy(): { name: string } | undefined {
  const raw: unknown = legacy();
  if (typeof raw !== "object" || raw === null || !("name" in raw)) return undefined;
  const name: unknown = raw.name;
  if (typeof name !== "string") return undefined;
  return { name };
}
console.log("adapter", adaptLegacy() === undefined ? "rejected" : "accepted");
```

```sh
tsc --strict --target ES2022 --module NodeNext --noEmitOnError --outDir dist any.mts
node dist/any.mjs
```

Output:

```text
name TypeError
annotated result number
elements number string
element TypeError
adapter rejected
```

The first array element is genuinely a number; the second is a string despite its variable annotation. `apparentlyTyped` also returns a number despite its promised string. The adapter contains the legacy result as unknown, checks the property and returns a newly projected valid shape only when the check succeeds. The [unknown owner](<./2.2. unknown the type-safe top type.md>) develops complete parser and element-validation workflows.

Append one independent negative probe at a time, compile and restore:

```typescript
const impossible: never = unchecked;
```

```typescript
const stillChecked: number = "wrong";
```

Both report TS2322. A separate file, `implicit.mts`, exposes a missing parameter contract:

```typescript
// implicit.mts
function read(value) { return value.name; }
```

`tsc --strict --noEmit implicit.mts` reports TS7006. Writing `value: any` makes that particular error disappear while retaining unchecked access. Writing `value: unknown` instead exposes the need for evidence before the property use. Supply the actual input contract if callers are already trusted to provide it.

### 3) **Budgeting, not banning**

A temporary any can be useful while migrating an actual untyped integration. Give it a narrow owner and explain the assumption, accepted inputs and follow-up work. A count can locate remaining escapes; it cannot prove that the remaining program is safe. An accurate adapter, declaration or generic relation is preferable when the required contract is known. Do not replace missing knowledge with a precise annotation unsupported by the implementation.

Suppression comments are a different mechanism. Save this **compile-only** file as `suppression.mts`:

```typescript
// suppression.mts
// @ts-expect-error: intentional incompatible assignment for this checking exercise
const text: string = 42;
```

`tsc --strict --noEmit suppression.mts` exits zero because a diagnostic is present on the suppressed line. Change `42` to `"fixed"` and the same command reports TS2578 for an unused directive. Change the directive to `@ts-ignore` and the valid assignment passes without that unused-directive check.

The [3.9 introduction](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-9.html#ts-expect-error-comments) explains this distinction. An expect-error directive does not pin the exact diagnostic: another error on the line can keep it satisfied. Comments provide no runtime guard and do not automatically detect a particular upstream fix. Use the [type-test owner](<../../../17 Testing Types/README.md>) for deliberate negative assertions and diagnostic verification. Lint rules are separately configured tools, not compiler options.

### 4) **Common confusion**

A more precise variable or return annotation cannot repair unchecked data flowing through any. It may merely move the false promise into a place callers trust. Unknown makes the missing evidence visible before ordinary typed use; the actual checks still need implementation and tests.

Replacing any with an assertion or a suppression can preserve the same risk in a different spelling. Choose the input contract and validate what is actually unknown instead of optimizing a count of keywords.

### 5) **Performance note**

Any annotations and suppression comments erase. The example's provider calls, validation, projection and failing operations still execute. No rename-completeness, language-server latency or runtime-speed measurement was made. The practical consequence demonstrated here is loss of a useful checking guarantee, not a measured performance ranking.

### 6) **Mentor note**

Ask why `apparentlyTyped` can return a number without a compiler diagnostic, then require a repair that checks the actual field rather than asserting it. For the array, predict both runtime types before trying `toFixed`. Finally make the suppression example valid and explain why expect-error notices while ignore does not, including the limitation that it does not identify a specific error code.
