## 2.3. never and void bottom vs deliberate nothing

### 1) **Never is the empty set**

`never` represents no possible value. An expression already typed never can be assigned to other types; an ordinary number, undefined or any value cannot be assigned to never. In a return contract, never means the function does not return normally. It may throw, terminate or keep running; it does not mean a normal return whose value should be ignored.

After all alternatives of a finite union have been handled, the remaining variable can narrow to never. Assigning that remaining value to never creates an exhaustiveness check. Adding an unhandled alternative then produces a diagnostic. This proves coverage of the **declared** alternatives, not validation of arbitrary external data. The [primary function reference](https://www.typescriptlang.org/docs/handbook/2/functions.html#never) explains the role of impossible results.

Use TypeScript 7.0.2 and Node.js 20.20.2. Save this complete program as `results.mts` in an empty directory.

```typescript
// results.mts
type AppEvent = { kind: "click"; x: number } | { kind: "key"; key: string };
function unreachable(value: never): never { throw new Error(`unhandled: ${String(value)}`); }
function handle(event: AppEvent): string {
  switch (event.kind) {
    case "click": return `click ${event.x}`;
    case "key": return `key ${event.key}`;
    default: {
      const remaining: never = event;
      return unreachable(remaining);
    }
  }
}
console.log(handle({ kind: "click", x: 42 }), handle({ kind: "key", key: "A" }));
function fail(message: string): never { throw new Error(message); }
function upper(value: string | null): string {
  if (value === null) fail("missing");
  return value.toUpperCase();
}
console.log(upper("Ada"));
try { upper(null); }
catch (error) { console.log(error instanceof Error ? error.message : "other"); }

function produce(): number { return 42; }
const ignored: () => void = produce;
const result = ignored();
console.log(result, typeof result);
function explicitVoid(): void {}
function onlyUndefined(): undefined {}
console.log(explicitVoid(), onlyUndefined());
```

```sh
tsc --strict --noImplicitReturns --target ES2022 --module NodeNext --noEmitOnError --outDir dist results.mts
node dist/results.mjs
```

Output:

```text
click 42 key A
ADA
missing
42 number
undefined undefined
```

The null path throws and is caught by the demonstration. It cannot continue to `toUpperCase`, which justifies the string use after the guard. The switch's default has no remaining declared alternative. A default that merely returns `"unknown"` would not ask the checker to identify newly added cases.

For a checking exercise, extend AppEvent with `| { kind: "resize"; width: number }` without adding a switch branch. Compilation fails with TS2322 at `remaining`. Add a resize case that formats width before the default to repair the program. The [exhaustiveness owner](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>) develops full union design and runtime boundaries.

### 2) **Void describes a result contract**

A function typed `() => void` permits its caller to ignore the implementation's result. A number-returning function can fill that slot. The called expression is typed void, while runtime execution in the example still returns 42. Logging the value is legal; using number-specific operations through the void view is not.

This special callback result rule is separate from parameter bivariance and ordinary result subtyping. The [primary void-assignability explanation](https://www.typescriptlang.org/docs/handbook/2/functions.html#return-type-void) contrasts the callback view with an explicit void annotation on an implementation body. The latter rejects an arbitrary number return.

| Contract | Meaning for a checked caller | Normal completion |
|---|---|---|
| `() => void` | No useful returned value promised through this view | Can return normally; actual implementation may return a value |
| `() => undefined` | Result is the undefined value | Can fall through or return undefined |
| `() => never` | No normal result is possible | Does not return normally |

Since TypeScript 5.1, an undefined-returning function can have no explicit return statement. The [5.1 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-1.html#easier-implicit-returns-for-undefined-returning-functions) document the change; `onlyUndefined` above passes even with noImplicitReturns enabled. An undefined contract is useful when a result's particular value matters, whereas void is useful when the host deliberately ignores results.

### 3) **Never versus void in signatures**

Append each independent probe to the working program, compile, then restore:

```typescript
function badVoid(): void { return 42; }
```

```typescript
const requiresUndefined: () => undefined = produce;
```

```typescript
const requiresNever: () => never = explicitVoid;
```

Each reports TS2322. An empty void body can complete; it cannot promise never. A number result cannot promise undefined. This fourth probe reports TS2339 because the caller's result view does not expose number operations:

```typescript
result.toFixed(1);
```

A promise-returning function may also fill a void callback slot, but that does not make its host await or handle it. `Promise<void>` describes a promise's result contract, not automatic completion/error ownership or a runtime guarantee obtained from its annotation. `Promise<never>` admits no successful fulfillment value in the typed model; it can reject rather than remain pending forever. The [function-return owner](<../../../05 Functions and Callable Types/sections/1. Function Type Fundamentals/1.3. Return types void never and contextual inference.md>) executes the ignored-promise contrast, and the async owner supplies the broader promise model.

### 4) **Common confusion**

Never is not another absence value alongside null and undefined. A void view is also not evidence that the implementation returned undefined. Track whether a function completes, which runtime value it produces and what its published type allows the caller to use.

An explicit never annotation is checked against the body; do not assume every throwing declaration is inferred as never in every context. Inference and published function contracts have their linked owner. Conditional types can use never to filter alternatives, but that type-level operation does not execute a throw or loop.

### 5) **Performance note**

Never and void annotations erase. The actual switch, calls, throw and catch remain. Assigning a function to a void slot does not insert a closure adapter or remove its returned value. No incident-recovery, allocation or checking-speed comparison was measured. Choose the contract from completion and result semantics.

### 6) **Mentor note**

Ask the learner to predict the static type and runtime value of `result`, then explain why the explicit badVoid body fails. Next add the resize alternative and locate the first diagnostic before implementing its branch. A sound explanation distinguishes an ignored result, a specific undefined result and an impossible normal result without confusing the callback rule with parameter variance.
