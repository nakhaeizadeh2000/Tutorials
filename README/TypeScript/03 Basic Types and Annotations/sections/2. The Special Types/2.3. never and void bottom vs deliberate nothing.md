## 2.3. never and void bottom vs deliberate nothing

### 1) **never is the empty set** (no value inhabits `never` — exhaustiveness, unreachable branches, conditional filtering)

**Definition** — `never` is the *bottom type*: the type with zero inhabitants. No value can be assigned to `never` (`const x: never = 123;` is an error), but `never` is assignable *to* every type — it represents a branch that never returns (throws, infinite loop, or an impossible condition). The checker uses `never` for unreachable code and exhaustiveness checking.

- **How it appears** — a function that always throws has return type `never`; a `while (true) {}` loop has type `never`; a discriminated union narrowed to nothing becomes `never`: `type Status = "a" | "b"; const exhaustive: never = status;` after handling `"a"` and `"b"` guarantees `"c"` would error (see unions in [07 Unions, Intersections and Narrowing](<../07 Unions Intersections and Narrowing/README.md>) — textual forward).
- **As of TypeScript 5.9 era**, `never` is also the result of `T extends U ? never : T` filtering in conditional types — the canonical way to exclude members (see [09 Utility Types and Type Transformations](<../09 Utility Types and Type Transformations/README.md>) textual forward). It never emits code — it erases (see [Type erasure](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)).

```typescript
function fail(msg: string): never { throw new Error(msg); }
const x: never = fail("oops"); // ok — fail never returns
// const y: never = undefined; // error — undefined not in never

// exhaustiveness — checker enforces every case handled
type Shape = { kind: "circle"; r: number } | { kind: "square"; size: number };
function area(s: Shape): number {
  if (s.kind === "circle") return Math.PI * s.r ** 2;
  if (s.kind === "square") return s.size ** 2;
  const _exhaustive: never = s; // error if a new Shape variant is added without a branch
  return _exhaustive;
}
```

### 2) **void is deliberate nothing** (a function returning `void` may return `undefined` implicitly — `void` is not `undefined`, and callers must not depend on the value)

- **What `void` means** — `() => void` says "the return value is *not used* by the caller". The implementation is allowed to return `undefined` (all JS functions return `undefined` when they fall through), but the caller must not depend on it: `const v = voidFn();` has type `void`, not `undefined` — you can ignore it but you shouldn't compare it as a value.
- **How `void` differs from `undefined` and `never`**:

| Signature | Caller may use return? | Implementation may return `undefined`? | Assignability |
|---|---|---|---|
| `() => void` | no — `void` value ignored | yes (implicit `undefined`) | `() => string` not assignable to `() => void`? Actually under bivariant callback rules, `void` return allows ignoring — see variance leaf |
| `() => undefined` | yes — caller gets `undefined` | must be `undefined` explicitly | must return `undefined` value |
| `() => never` | no — never returns | never returns (throw/loop) | assignable to `() => void` (never is bottom) |

- **The classic pitfall** — `array.forEach(cb: (v: string) => void)` lets `cb` *return* anything (`return "oops"` inside `forEach` callback is allowed because return is ignored). But `type Mapper = (v: string) => string;` requires a return value to be used. Confusing the two lets callbacks return values that callers discard, hiding bugs.

### 3) **never vs void in signatures** (`() => void` vs `() => never` vs `() => undefined` — assignability, callback variance, and `strict` interactions)

- **Callback variance** — with `strictFunctionTypes`, a function returning `void` is *covariant* in a callback position that discards the result: `let f: () => void = () => "hi"` is allowed (the string is discarded). `() => never` is assignable to `() => void` (never is subtype of everything), but not vice-versa.
- **Modern guidance** — use `void` for callbacks whose return is ignored and for `async` functions that don't produce a value (`async (): Promise<void>`). Use `never` for exhaustiveness variables and functions that always throw. Use `undefined` only when the domain requires an *explicit* `undefined` value (e.g., `Map.get` returns `T | undefined` — caller must handle the value).
- **`async` nuance** — `async (): Promise<void>` resolves to `undefined` at runtime, but callers awaiting it should not depend on the resolved value — `void` signals that. `async (): Promise<never>` would promise the `await` never resolves (throw/loop).

### 4) **Runnable example** — never exhaustiveness and void callback nuance (good vs bad)

```typescript
// good — never for exhaustiveness (checker enforces future variants)
type Event =
  | { type: "click"; x: number }
  | { type: "keypress"; key: string }
  | { type: "resize"; w: number; h: number };

function handle(event: Event): string {
  switch (event.type) {
    case "click": return `click at ${event.x}`;
    case "keypress": return `key ${event.key}`;
    case "resize": return `resize ${event.w}x${event.h}`;
    default: {
      const _exhaustive: never = event; // ok — all variants handled
      return _exhaustive; // if Event gains a variant, this line errors — forces you to add a case
    }
  }
}
console.log(handle({ type: "click", x: 42 })); // click at 42

// bad — default returns string instead of never (hides missing cases)
function handleBad(event: Event): string {
  switch (event.type) {
    case "click": return `click`;
    case "keypress": return `key`;
    default: return "unknown"; // silently handles resize too — bug masked
  }
}

// good — void for ignored callback return, undefined when value matters
function forEachLog(values: string[], cb: (v: string) => void): void {
  for (const v of values) cb(v); // return value discarded — void Promise allows any return in cb
}
forEachLog(["a", "b"], (v) => { console.log(v); return "ignored"; }); // string return discarded — allowed with void

// bad — using void where undefined is needed (caller depends on value)
type Lookup<T> = (key: string) => T | undefined; // Map.get style — caller must handle missing
// type LookupVoid<T> = (key: string) => T | void; // bad — void signals "ignore", not "missing value"
const lookup: Lookup<number> = (key) => (key === "a" ? 42 : undefined);
const result: number | undefined = lookup("missing"); // caller checks undefined — correct model

// good — never-returning function narrows after call
function unreachable(msg: string): never { throw new Error(msg); }
function process(value: string | null): string {
  if (value === null) unreachable("value is null — should not happen here");
  return value.toUpperCase(); // value is string — checker knows unreachable never returns
}

// bad — void-returning fail that doesn't throw (caller continues with wrong type)
// function failVoid(msg: string): void { console.error(msg); /* no throw */ }
// function processBad(value: string | null): string {
//   if (value === null) failVoid("null"); // void returns undefined — execution continues, value still null → runtime error
//   return value.toUpperCase(); // error under strictNullChecks, but void version compiles without throw
// }
```

### 5) **Common confusion**

- "`void` means the function returns `undefined`" — at runtime yes (JS always returns `undefined` when falling through), but statically `void` says "caller must ignore the return" while `undefined` says "caller receives the value `undefined`". Using `void` where you mean `undefined` hides that callers can branch on the value.
- "`never` is the same as `void`" — `never` never returns at all; `void` returns `undefined` that you ignore. `never` is subtype of `void` (assignable to `void`), but not vice-versa.
- "Assigning `never` proves exhaustiveness" — only if you assign the *remaining* variable after narrowing (`const _ex: never = remaining`). If you write `const _ex: never = event` inside a branch without exhausting, the checker will error at the wrong place — ensure `default` is the unhandled case.

### 6) **Performance note**

Both `never` and `void` erase — no emit cost. The perf win of `never` is *correctness performance*: exhaustiveness checks prevent "unhandled variant leaked to production" incidents where the fallback branch silently did the wrong thing — those incident investigations dominate MTTR. `void`'s permissiveness in callbacks (`() => string` assignable to `() => void`) avoids speculative generic wrapper complexity that would otherwise allocate closure adapters.

### 7) **Mentor note**

Teach `never` as "the proof that a branch is impossible". Review checklist: can the student write an exhaustive `switch` with `never` in `default`, explain why adding a new union member makes the checker error exactly there, and articulate when to use `void` vs `undefined` in a return type? Exercise: give them a `type Result<T> = { ok: true; value: T } | { ok: false; error: string }` and ask for a `handle` function that returns `never` in the unhandled branch — then add a third variant and watch the checker demand an update.
