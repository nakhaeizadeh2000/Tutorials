## 5.1. Real production bugs caused by basic type misunderstandings

These are local reproductions of four failure patterns, without invented hit rates, revenue losses or recovery timelines. Tested with **TypeScript 7.0.2 / Node 20.20.2**, verified 2026-10-13. Save `pitfalls.ts` in a directory without a tsconfig:

```typescript
export {};
async function main(): Promise<void> {
  const wrapped = new String("a");
  const cache = new Map<String, number>([[wrapped, 42]]);
  console.log("keys:", cache.get("a"), cache.get(wrapped));
  const primitiveCache = new Map<string, number>([["a", 42]]);
  console.log("primitive:", primitiveCache.get(String(wrapped)));

  let rows = [];
  rows.push(1);
  rows.push("oops");
  console.log("evolving:", rows.join(","));
  const numericRows: number[] = [];
  numericRows.push(1, 2);
  console.log("numeric:", numericRows.reduce((sum, value) => sum + value, 0));

  const pending = Promise.reject(new Error("offline"));
  const ignored: () => void = () => pending;
  const returned = ignored();
  console.log("void return at runtime:", typeof returned);
  try { await pending; }
  catch (error: unknown) {
    if (!(error instanceof Error)) throw error;
    console.log("observed rejection:", error.message);
  }
  const loader: () => Promise<void> = async () => { throw new Error("retry failed"); };
  try { await loader(); }
  catch (error: unknown) {
    if (!(error instanceof Error)) throw error;
    console.log("awaited loader:", error.message);
  }

  const missing = {};
  const present: { search: string | undefined } = { search: undefined };
  console.log("memory:", "search" in missing, "search" in present);
  console.log("JSON:", JSON.stringify(missing), JSON.stringify(present));
  type Client = { search?: string };
  type Wire = { search: string | null };
  function toWire(client: Client): Wire { return { search: client.search ?? null }; }
  const encoded = JSON.stringify(toWire({}));
  const decoded: unknown = JSON.parse(encoded);
  if (typeof decoded !== "object" || decoded === null || !("search" in decoded)
      || !(decoded.search === null || typeof decoded.search === "string")) {
    throw new Error("Invalid wire body");
  }
  console.log("wire:", encoded, decoded.search);
}
void main().catch((error: unknown) => { throw error; });
```

Run:

```bash
tsc --strict --exactOptionalPropertyTypes --target es2022 --module commonjs --lib es2022,dom --outDir dist pitfalls.ts
node dist/pitfalls.js
```

Both commands exit 0. Output:

```text
keys: undefined 42
primitive: 42
evolving: 1,oops
numeric: 3
void return at runtime: object
observed rejection: offline
awaited loader: retry failed
memory: false true
JSON: {} {}
wire: {"search":null} null
```

### 1) **String wrapper comparison**

A constructed String is an object key, while a primitive string is a different key. The broad Map<String, number> accepts the wrapped key and a primitive lookup; the latter misses. Querying with the same wrapper object returns 42. The primitive-keyed map deliberately normalizes the wrapper using String without new and finds its string key.

For a string-only contract, Map<string, number> rejects a String object statically. Do not conclude that the checker can never distinguish primitive and wrapper contracts; the [verified checklist](<../4. Important points to remember/4.1. Basic types checklist mental models mentors insist on.md>) shows both assignment directions. Full key identity belongs to the JavaScript collection owner, while [primitive/wrapper types](<../1. The Primitive Family/1.1. string number boolean and the wrapper pitfall.md>) owns this type distinction.

### 2) **Inference can permit a mixed array without matching the intended contract**

Under the declared strict configuration, the unannotated rows array evolves as values are pushed. The number then string sequence is accepted and produces `1,oops`. This is a permitted mixed collection, not proof that the application's intended numeric-only invariant holds.

The [2.1 inference notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-1.html#improved-any-inference) introduce evolving inference; the [maintainer discussion](https://github.com/microsoft/TypeScript/issues/54414) records recurring confusion when an evolving array is displayed as any[]. That proposed tooltip change is not assumed to have shipped. The result here comes from actual 7.0.2 checking.

Compare three separate strict noEmit probes:

| Change | Actual diagnostic | Reason |
|---|---|---|
| `const rows: number[] = []; rows.push("oops");` | TS2345, exit 1 | The explicit numeric contract rejects a string. |
| Empty rows captured by read before any writes | TS7034 and TS7005, exit 1 | This use leaves an unresolved implicit array type. |
| Push number and string, then pass rows to sum(number[]) | TS2345, exit 1 | The inferred mixed array does not satisfy the numeric consumer. |

For the unresolved case, the complete input is:

```typescript
let rows = [];
function read() { return rows; }
console.log(read());
```

`tsc --strict --noEmit unresolved.ts` produces the two reported diagnostics. Do not generalize this rejection to every empty-array declaration. Annotate an array when a known element invariant must be enforced even if current local inference is acceptable. The [inference owner](<../3. Annotations Inference and Literals/3.2. Type inference widening and contextual typing.md>) develops the other contexts.

### 3) **Void can hide a return the caller needs**

A function assigned to `() => void` may return a value which its checked contract tells the caller to ignore. The fixture returns a promise through that contract; typeof observes an object at runtime. The type does not convert the promise to undefined or consume its rejection. The [function-return reference](https://www.typescriptlang.org/docs/handbook/2/functions.html#return-type-void) explains this contextual return rule.

The test deliberately retains the pending promise through a separate observation seam and awaits its rejection. It does not leave an unhandled rejection running. A Promise<void> loader exposes the awaited operation in its contract, and the example catches its failure. A promise annotation alone still does not force callers to await; a caller's control flow and appropriate lint/runtime tests establish handling. Use void when the result is intentionally ignored and a result-bearing or promise contract when callers need the operation. Full asynchronous error handling belongs to [async types](<../../../18 Async Types and Standard Library/README.md>).

### 4) **In-memory presence is not serialized presence**

The missing object and present undefined-valued object differ under the in operator: false and true. Both stringify to `{}`. Requiring the key in a TypeScript type did not preserve it on the JSON wire. exactOptionalPropertyTypes controls permitted assignments, not serialization; [ECMA-262 JSON.stringify](https://tc39.es/ecma262/multipage/structured-data.html#sec-json.stringify) establishes ordinary undefined-valued property omission.

This fixture chooses an explicit-null wire contract. toWire creates a required search key with null when the local value is absent. After serialization and parsing, the receiving check verifies that the key exists and contains null or a string. The output demonstrates that consumer contract, without claiming an HTTP or server integration. An omission-based protocol can also be correct if both ends agree; choose its semantics explicitly. The [nullability owner](<../1. The Primitive Family/1.3. null and undefined strictNullChecks and optionality.md>) explains the assignment spellings.

### 5) **Common confusion**

Strict checking does not force an annotation on every empty array. It can infer a mixed element type and reject that type later at a numeric-only consumer. Decide what the array is supposed to contain before using a diagnostic or hover as the application's specification.

A required property can disappear during JSON serialization when its value is undefined. Similarly, void describes the caller's use of a return; it does not remove a runtime promise or automatically handle errors. Keep static permission and actual runtime behavior separate.

### 6) **Performance note**

Wrapper construction, collection lookups, parsing and promise operations are real runtime work. Type annotations and exact-optional checking do not emit a serializer or a rejection handler. No cache-hit, latency, allocation or checker benchmark was measured here. Normalize keys and boundary data for the intended semantics, then measure their cost on representative workloads rather than using hypothetical incident percentages.

### 7) **Mentor note**

Ask the learner to predict each output before executing the fixture, then identify which one a stronger type contract can reject. A sound answer distinguishes wrapper key identity, local evolving inference, ignored returns and JSON representation. Have them design a numeric-only collection or an omission-based wire protocol and state what the consumer must verify.

During review, replace blanket grep/annotation rules with a specific invariant and a reproduction. For async callbacks, ask where the promise is observed; for JSON, inspect the serialized payload and receiving check. A type spelling does not supply either observation by itself.
