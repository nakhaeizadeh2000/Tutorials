## 5.1. Real production bugs caused by basic type misunderstandings

### 1) **String wrapper comparison** (`new String("a") !== "a"` — boxed strings break `Map`/`Set` keys)

**Incident** — a cache layer keyed by `new String(userId)` (constructed from legacy Java codegen) missed 100% of lookups when consumers queried with `userId` primitive. `Map` uses `SameValueZero`: `new String("a")` is an *object* distinct from `"a"` primitive — never equal. Telemetry showed 0% hit rate; P99 latency collapsed only after switching to primitive `string`.

**Why it hurt** — the type `String` accepted both primitives and boxed objects (structural compat), so the bug compiled. The checker cannot distinguish "primitive string" from "String object you happened to construct" without linting — `String` as a type is the enabler.

- **Bad** — `const key: String = new String(id); map.set(key, value); map.get(id) // undefined — different key`
- **Good** — `const key: string = String(id);` (`String(id)` without `new` returns a primitive) or simply `id: string`. Enable `@typescript-eslint/no-wrapper-object-types` to ban `String`/`Number`/`Boolean` types — treat `new String` in code review as `allocate useless object + break Map`.

---

### 2) **Implicit any from empty array** (`let xs = []; xs.push(1); xs.push("oops")` — becomes `any[]` under `noImplicitAny: false`)

**Incident** — an import pipeline built `let rows = [];` without an annotation, pushed `number` IDs into it, then a later refactor pushed a `string` error message into the same array. No type error surfaced because `rows` was inferred as `any[]` (legacy `noImplicitAny: false`). A downstream `sum(rows)` computed `"1oops"` via string concatenation on a `number[]` assumption — revenue report off by orders of magnitude before a manual QA caught it.

**Why it hurt** — `any[]` disables element checking: every `push` and every indexing is `any`. The checker proved nothing; the bug was invisible until the domain invariant ("all elements are numbers") was violated at runtime.

- **Bad** — `let rows = []; rows.push(1); rows.push("oops");` compiles with `any[]`.
- **Good** — `let rows: number[] = [];` (annotate intent) + `noImplicitAny: true` (part of `--strict`) — `let xs = [];` now errors `Variable 'xs' implicitly has an 'any[]' type` and forces annotation. CI also lints `any[]` via `no-explicit-any`.

---

### 3) **Void vs undefined callback misuse** (`forEach` callback returning a value that caller ignores vs depends upon)

**Incident** — a team wrote `type Loader = (id: string) => void; const loaders: Loader[] = [(id) => fetch(`/user/${id}`)];` — `fetch` returns `Promise<Response>`, but `Loader`'s `void` meant callers discarded the promise. No `await`, no error handling — every network error swallowed silently. Incident took days to surface because rejected promises were unhandled but invisible under `void`.

**Why it hurt** — `void` signals "return ignored" — the checker *allows* a callback returning `string`/`Promise` to be assigned to `() => void` (intentional leniency for callbacks like `forEach`). That leniency hides bugs when the caller *should* use the value (promise for error handling, mapper result). The fix is to model intent precisely:

- **When return is ignored** — `() => void` is correct (`forEach`, `addEventListener`).
- **When return matters** — `() => Promise<void>` (awaited side effect) / `(v: string) => string` (mapper) / `(k: string) => T | undefined` (lookup where `undefined` is a value — see [2.3. never and void](<../2. The Special Types/2.3. never and void bottom vs deliberate nothing.md>)).

| Signature | What checker allows in callback return | When to use |
|---|---|---|
| `(v: string) => void` | `return "anything"` allowed — discarded | `forEach`, `onClick` — return intentionally unused |
| `(v: string) => string` | must return `string` — checked | `map`, `filter`, `reduce` — return is the result |
| `() => Promise<void>` | async callers must `await` to catch errors | side-effect loaders |

- **Good** — `type Loader = (id: string) => Promise<void>; await loader(id);` — promise is now part of the contract and must be handled.

---

### 4) **Optional vs undefined mismatch** (`{ prop?: string }` passed where `prop: string | undefined` expected — `--exactOptionalPropertyTypes` reveals the gap)

**Incident** — an API client type declared `type Request = { search?: string }` (optional) and the server required `type ServerBody = { search: string | undefined }` (key always present, may be `undefined`). Client sent `{}` via `JSON.stringify({ search: undefined })` → `{}` (key missing) while server deserialization distinguished missing vs `undefined`-valued and threw validation `search is required`. Debug was hard because both sides looked "undefined-tolerant" but `{} !== { search: undefined }` after JSON — `JSON.stringify` strips `undefined` properties.

**Why it hurt** — `prop?: string` vs `prop: string | undefined` differ on whether the *key* must be present, which becomes observable after serialization, `Object.keys`, or `in` checks. Default `exactOptionalPropertyTypes: false` hides the distinction (`{ prop: undefined }` allowed for optional props); enabling `exactOptionalPropertyTypes: true` surfaces it (`{ prop: undefined }` for `prop?: string` becomes an error unless you write `prop?: string | undefined`).

- **Bad** — `type Client = { search?: string }; const c: Client = { search: undefined };` — passes default strict but not exact, and serializes to `{}`.
- **Good** — enable `exactOptionalPropertyTypes: true` (as of TS 5.9 era, opt-in stricter), model wire types exactly as sent: `type Wire = { search: string | null }` or `type Wire = { search: string | undefined }` with key always present if the server expects the key. Convert at the boundary: `function toWire(c: Client): Wire { return { search: c.search ?? null }; }` (see [1.3. null and undefined](<../1. The Primitive Family/1.3. null and undefined strictNullChecks and optionality.md>)).

---

### 5) **Checklist to avoid these four**

1. `grep -R "new String|new Number|new Boolean" --include="*.ts"` → 0 hits (primitives, never wrappers; Map/Set keys are primitives).
2. `npx tsc --noEmit --strict` passes and `grep -R "let .*\[\]"` — every empty-array declaration has an explicit type annotation (`let xs: number[] = [];`).
3. Callbacks that do async work have `Promise<void>` in their signature, not `void` — grep `=> void` on async callbacks is an audit flag.
4. Wire types with `JSON.stringify` distinguish `?` vs `| undefined` — enable `exactOptionalPropertyTypes` on CI or at least model optional `?` vs required `| undefined` consistently across client/server.
