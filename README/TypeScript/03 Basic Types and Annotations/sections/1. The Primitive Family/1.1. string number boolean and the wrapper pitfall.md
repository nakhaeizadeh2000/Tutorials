## 1.1. string number boolean and the wrapper pitfall

### 1) **The three workhorses**

Use `string`, `number` and `boolean` to describe the corresponding JavaScript primitive values. A string contract accepts text; a number contract includes integers, fractions, `NaN` and infinities; a boolean contract accepts `true` or `false`. An annotation does not validate a value's application-specific meaning. For example, an amount requiring a finite non-negative integer needs an actual boundary check.

These type annotations erase. The values and operations remain ordinary JavaScript. The [primary Everyday Types guidance](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#the-primitives-string-number-and-boolean) recommends the lowercase primitive spellings.

### 2) **Primitives versus wrappers**

`String`, `Number` and `Boolean` are broader built-in structural types describing wrapper capabilities. The corresponding primitives can also be assigned to them. Consequently, `const broad: String = "Ada"` still contains a primitive at runtime. An annotation is not a constructor call.

`new String("Ada")` instead creates an object. That object cannot be assigned to a primitive `string` contract. A wrapper can also behave differently in equality, collection keys and truthiness. Prefer primitive contracts for ordinary application data; an interoperability API that deliberately supplies wrappers needs its real representation described and handled explicitly.

Use TypeScript 7.0.2 and Node.js 20.20.2. Save this complete example as `primitives.mts` in an empty directory.

```typescript
// primitives.mts
const title: string = "TypeScript";
const values: number[] = [42, 1.5, NaN, Infinity];
const ready: boolean = true;
console.log(title.toUpperCase(), values.every(value => typeof value === "number"), ready);

const broadString: String = "Ada";
const broadNumber: Number = 42;
const broadBoolean: Boolean = false;
console.log(typeof broadString, typeof broadNumber, typeof broadBoolean);
const boxed: String = new String("Ada");
console.log(typeof boxed, boxed.valueOf());
const map = new Map<String, number>([[boxed, 1]]);
console.log(map.get("Ada"), map.get(boxed), map.get(new String("Ada")));
console.log(Boolean(new Boolean(false)), Boolean(false));
function greet(name: string): string { return `hi ${name}`; }
console.log(greet("Ada"), greet(boxed.valueOf()));

let mode = "light";
const fixedMode = "light";
function setMode(value: "light" | "dark"): string { return value; }
console.log(setMode(fixedMode));
```

```sh
tsc --strict --target ES2022 --module NodeNext --noEmitOnError --outDir dist primitives.mts
node dist/primitives.mjs
```

Output:

```text
TYPESCRIPT true true
string number boolean
object Ada
undefined 1 undefined
true false
hi Ada hi Ada
light
```

The broad annotations leave all three primitives unchanged. The explicit string wrapper is an object, and only that same instance finds the Map entry. A newly constructed wrapper with equal text is another key. The boxed false value is truthy because it is an object; converting the primitive false retains false. `valueOf()` deliberately extracts the wrapper's primitive for the narrow greeting contract.

Append this independent negative probe and compile, then restore the original:

```typescript
greet(boxed);
```

It reports TS2345. TypeScript rejects this direction even without a linter. A separate optional [no-wrapper-object-types rule](https://typescript-eslint.io/rules/no-wrapper-object-types/) can flag broad wrapper annotations as policy. That rule is supplied by typescript-eslint, not by `tsc`; no lint command is run in this lesson. Full lint setup belongs to the tooling domain.

### 3) **When widening matters**

For the scalar initializers shown, `let mode = "light"` infers `string`, allowing later reassignment to a different string. `const fixedMode = "light"` retains the literal type `"light"`. This separate negative probe reports TS2345 because the general string type is broader than the accepted mode union:

```typescript
setMode(mode);
```

If the variable should change only between the two modes, declare `let selected: "light" | "dark" = "light"`. An explicit union records that intent. Const bindings of objects still allow their ordinary mutable properties to widen; the [inference owner](<../3. Annotations Inference and Literals/3.2. Type inference widening and contextual typing.md>) explains that distinction. Use a broader type when broader values are intended rather than treating literal precision as universally preferable.

### 4) **Common confusion**

An uppercase type does not guarantee that a value is boxed; the example's broad variables contain primitives. Conversely, a constructed wrapper does not satisfy a narrower primitive contract merely because it exposes similar methods. Separate the permitted assignment direction from the actual constructor or value expression.

`number` also does not exclude `NaN` or impose integer bounds. Changing an alias's name cannot add such validation. Check the required numeric rule at the input boundary and preserve it through subsequent operations.

### 5) **Performance note**

Annotations erase without creating wrappers. Explicit wrapper construction creates an object with identity, while `Map` operations and string formatting execute independently of the annotations. No heap-layout, garbage-collection or throughput measurement was made. Choose primitive contracts to express the intended data; investigate an actual allocation bottleneck with runtime measurements rather than inferring storage from a TypeScript spelling.

### 6) **Mentor note**

Ask why the broad string variable prints `string` but the constructed wrapper prints `object`. Then predict all three Map lookups before running them. A sound answer identifies the constructor and object identity. Finally compare the accepted const mode with the rejected let mode, explaining the static contract without attributing a runtime conversion to inference.
