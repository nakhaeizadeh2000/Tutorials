## 1.1. string number boolean and the wrapper pitfall

### 1) **The three workhorses** (what `string`, `number`, `boolean` mean statically and how they erase — no runtime wrapper)

**Definition** — `string`, `number`, `boolean` are the primitive type literals for the three most common JavaScript values. A value typed `string` is any string primitive (`"hi"`, `` `hi ${x}` ``); `number` is any `number` primitive (integers, floats, `NaN`, `Infinity` — TypeScript does not distinguish them at the type level); `boolean` is `true` or `false`. All three erase completely — after `tsc` emits JavaScript, no trace remains (see [Type erasure — what survives compilation](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.1. Type erasure what survives compilation.md>)).

- Historically JavaScript has both primitives (`"hi"`) and boxed objects (`new String("hi")`). TypeScript's primitive types describe the *primitive* form — the one you use in 99.9% of code.
- Under `as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS)`, these three are the defaults the checker infers for unannotated `let` literals (before widening — see §3 below and [3.2. Type inference widening and contextual typing](<../3. Annotations Inference and Literals/3.2. Type inference widening and contextual typing.md>)).

### 2) **Primitives vs wrappers** (`string` vs `String`, `number` vs `Number` — the boxed object types exist but are almost never what you want)

**What problem it solves** — JavaScript's `String`, `Number`, `Boolean` global objects are constructors that produce *objects* (`typeof new String("a") === "object"`), not primitives (`typeof "a" === "string"`). The type system distinguishes them: lowercase `string` allows primitives; uppercase `String` allows the boxed object. Confusing the two is a correctness and performance trap.

| You write | Type allows | Runtime value | Equality |
|---|---|---|---|
| `string` | `"a"`, `` `a` `` | primitive | `"a" === "a"` → `true` |
| `String` | `new String("a")` (+ primitives via assignability quirks) | object | `new String("a") !== "a"` → `true` |
| `number` | `42`, `NaN`, `Infinity` | primitive | `42 === 42` |
| `Number` | `new Number(42)` | object | `new Number(42) !== 42` |

Modern guidance — always use lowercase. Enable `@typescript-eslint/no-wrapper-object-types` (or `ban-types` in `tsc`'s own lint) to flag uppercase wrappers. The only place uppercase appears legitimately is legacy `.d.ts` describing older libraries that intentionally constructed wrappers (e.g., `Object.prototype.valueOf` returning `String`).

- **Why boxed objects hurt** — they allocate, they break `Map`/`Set` key identity (`new String("a")` as key ≠ `"a"`), and they force `.valueOf()` call sites to have an extra type. TypeScript will *accept* a primitive where `String` is expected (structural leniency for compat), so the mistake compiles but misleads readers.

### 3) **When widening bites** (`let` widens a literal to its primitive; `const` keeps the literal — the first taste of inference)

- **Widening default** — `let x = "hello"` is inferred as `string`, not `"hello"`. The checker assumes a `let` variable will be reassigned, so it widens the literal to its base primitive. `const x = "hello"` is inferred as `"hello"` (the literal type) because `const` cannot be reassigned — the value is known forever (full widening model in [3.2. Type inference widening and contextual typing](<../3. Annotations Inference and Literals/3.2. Type inference widening and contextual typing.md>)).
- **Why this matters now** — even before you learn literal types formally ([3.3. Literal types and const assertions](<../3. Annotations Inference and Literals/3.3. Literal types and const assertions.md>)), you will see hover types flip between `"hello"` and `string` depending on `let`/`const`. That difference determines whether `x` is assignable to a `"hello" | "goodbye"` union or widened away from it.

### 4) **Runnable example** — workhorses, wrappers, and widening (good vs bad)

```typescript
// good — primitives as intended (as of TS 5.9 era, --strict)
let title: string = "TypeScript"; // explicit — reviewable contract
const titleConst = "TypeScript";   // inferred as "TypeScript" (literal), not string — hover shows it
let count = 42;                    // inferred as number (widened from 42 literal)
const ready = true;                // inferred as true (literal, because const)

// Widening control — when you need a literal union, use const or explicit literal
type Status = "idle" | "loading" | "done";
const statusConst = "idle"; // type "idle" — assignable to Status
let statusLet = "idle";     // type string — NOT assignable to Status without assertion
// fix: annotate at declaration
let status: Status = "idle"; // ok

// bad — wrapper types compile but mislead and allocate
function greetBad(name: String): void { // flagged: use string
  // name is typed as boxed object — caller may pass primitive, but hover lies
  console.log(name.toString());
}
greetBad("Ada");           // accepts primitive — structural compat hides the mistake
greetBad(new String("Ada")); // creates object: typeof === "object", breaks Map keys
const key1: String = new String("a");
const key2: string = "a";
const map = new Map<string | String, number>();
map.set(key1, 1); // key is object
console.log(map.get("a")); // undefined — different key! (object !== primitive)
console.log(map.get(key1)); // 1 — only the exact boxed instance works

// good — lowercase only, no allocation
function greetGood(name: string): void {
  console.log(`hi ${name}`);
}
greetGood("Ada"); // primitive, no object
```

```typescript
// bad — assuming let literal stays literal (widening bug)
function setMode(mode: "light" | "dark"): void {}
let mode = "light"; // inferred string — widens
// setMode(mode); // error TS2345: string not assignable to "light" | "dark"

// fix — const, annotation, or as const (see 3.3)
const modeConst = "light"; // "light"
let modeFixed: "light" | "dark" = "light"; // annotation pins the union
setMode(modeFixed); // ok
setMode(modeConst); // ok
```

### 5) **Common confusion**

- "`Number` is just more explicit than `number`" — opposite: `Number` describes the *object* form (`new Number()`). Linters that ban wrapper types exist for this reason; never accept PRs that introduce uppercase primitives.
- "`number` excludes `NaN`" — no, `NaN` is a `number` (`typeof NaN === "number"`). If you need to exclude it, use a branded type or runtime check (`Number.isNaN`), not a different type.
- "`let x = 'a'` should give me type `'a'`" — it widens to `string` by design (reassignability). Use `const` or an explicit annotation when you need the literal.

### 6) **Performance note**

Wrapper objects allocate: `new String("a")` creates an object with a prototype chain (`String.prototype`), properties, and GC pressure — versus a primitive string which is stored inline (or as a rope/flat string internally — engine-dependent, but no object header). Never construct wrappers in hot paths; the type distinction exists partly to make this allocation visible in code review. Primitives themselves have zero type-system cost after erasure — they become plain JavaScript literals.

### 7) **Mentor note**

Teach this as "lowercase is the contract". Review checklist: can the student explain why `const x: String = "hi"` compiles but is wrong (compat leniency, not correctness)? Exercise: have them hover `let x = "hi"` vs `const x = "hi"` and explain the displayed type difference — that single interaction reframes widening before the formal leaf. Warn about copy-pasting Java/C# habits (`String` is a class there, not here).
