## 1.2. bigint and symbol the ES-era primitives

### 1) **bigint is its own lane** (`123n` is not `number` — arithmetic, `target`/`lib`, and JSON serialization consequences)

**Definition** — `bigint` is the primitive type for arbitrary-precision integers (`123n`, `0n`, `-1n`). It is *not* a subtype of `number` and does not mix with `number` without explicit conversion. `bigint` literals require a trailing `n`; `typeof 123n === "bigint"` at runtime (see [JavaScript numbers vs bigint](<../../../../JavaScript/12 Numbers Dates Math and Temporal/README.md>)).

- **History** — ES2020 added `BigInt`; TypeScript has modeled it since TS 3.2 with `target >= es2020` (or `lib: ["es2020.bigint"]`). As of TypeScript 5.9 era (Aug 2026: TS 5.9 stable), `target: es2022` is conventional, so `bigint` is universally available without extra `lib` — older configs still need the lib entry.
- **Static separation** — `number` and `bigint` are disjoint: `let x: number = 1n;` is an error (`bigint` not assignable to `number`). Arithmetic between them is also an error (`1n + 1` → `Operator '+' cannot be applied to types 'bigint' and 'number'`).
- **Modern guidance** — use `bigint` only when you need integer precision beyond `Number.MAX_SAFE_INTEGER` (2^53 − 1) — e.g., ledger balances, snowflake IDs, cryptographic scalars. For counts, indexes, and ordinary math, `number` remains the default.

### 2) **symbol and unique symbol** (`symbol` vs `unique symbol` — the only literal-like primitive that needs `typeof` bridging)

- **Two forms** — `symbol` is the general primitive type (`typeof s === "symbol"`); `unique symbol` is a literal-like subtype produced by `const x = Symbol("id")` or `const X: unique symbol = Symbol()`. Only `const` declarations with a `unique symbol` annotation or a direct `typeof x` query can produce the literal form (bridges type and value spaces — see [2.1. Type space vs value space](<../../../02 The Type System Core/sections/2. The type vs value separation/2.1. Type space vs value space two parallel universes.md>)).
- **What problem it solves** — symbols are the only safe way to add non-colliding property keys (`obj[Symbol("private")]` cannot clash with string keys). `unique symbol` lets you type a *specific* symbol identity, not "any symbol" — essential for branding and protocol markers (e.g., `Symbol.hasInstance`).

| You write | Type | Assignability |
|---|---|---|
| `let s: symbol = Symbol("a")` | `symbol` | any symbol |
| `const S: unique symbol = Symbol("a")` | `typeof S` (unique) | only that symbol |
| `const obj = { [S]: 42 }` | `{ [S]: number }` with key `typeof S` | key is that unique symbol only |

### 3) **Why they stay rare** (API cost vs benefit — most domains reach for `string`/`number` first)

- **bigint cost** — no implicit coercion, `JSON.stringify(1n)` throws (`TypeError: Do not know how to serialize a BigInt`), `Math.*` does not accept `bigint`, and some ORMs/DB drivers need string conversion. Library ergonomics suffer if every numeric type is `bigint`.
- **symbol cost** — `unique symbol` parameters cannot be created dynamically (you need the same symbol value), and `JSON.stringify` ignores symbol keys. Useful for internal protocol markers and nominal branding, but overused symbols make serialization and debugging harder.
- **Mentor framing** — ask "does this value exceed safe integer range or need identity guarantee?" If no, `string`/`number` are cheaper.

### 4) **Runnable example** — bigint lane and unique symbol identity (good vs bad)

```typescript
// good — bigint as its own type, explicit conversions at the boundary
function addBalances(a: bigint, b: bigint): bigint {
  return a + b; // ok — same lane
}
const balA: bigint = 9007199254740993n; // beyond MAX_SAFE_INTEGER — needs bigint
const balB: bigint = 1n;
console.log(addBalances(balA, balB).toString()); // "9007199254740994" — preserves precision

// conversion at the interop boundary (number ↔ bigint)
function toBigint(n: number): bigint {
  if (!Number.isSafeInteger(n)) throw new Error("unsafe integer");
  return BigInt(n);
}
const mixed: bigint = toBigint(42) + 1n; // explicit — no silent coercion

// bad — mixing lanes or assuming JSON handles bigint
// const badMix = 1n + 1; // error TS2365: Operator '+' cannot be applied to types 'bigint' and 'number'.
// fix: convert before mixing
const fixedMix = Number(1n) + 1; // number lane, after explicit conversion (loses bigint precision — intentional)

// bad — JSON with bigint throws at runtime (type system doesn't catch the runtime throw)
const payloadGood = { id: 1n };
// JSON.stringify(payloadGood); // runtime TypeError — checker won't flag it (structural, not runtime)
// fix: serialize as string at the boundary
const payloadFixed = { id: 1n.toString() };
console.log(JSON.stringify(payloadFixed)); // {"id":"1"}

// good — unique symbol as protocol marker (literal identity)
const PrivateKey: unique symbol = Symbol("PrivateKey");
type Container = { [PrivateKey]: string; name: string };
function makeContainer(name: string, secret: string): Container {
  return { [PrivateKey]: secret, name };
}
const c = makeContainer("Ada", "s3cr3t");
console.log(c.name); // "Ada"
console.log(c[PrivateKey]); // "s3cr3t" — accessed only via the exact symbol value

// bad — plain symbol loses identity narrowing
let genericSym: symbol = Symbol("a");
const another = Symbol("a");
// c[genericSym]; // error: not the unique symbol key — checker preserves identity

// bad — using bigint where number suffices (API tax)
function countItemsBad(ids: bigint[]): number {
  return Number(ids.length); // ids.length is number — bigint indexing is unnecessary
}
// fix: use number for counts
function countItemsGood(ids: string[]): number { return ids.length; }
```

### 5) **Common confusion**

- "`bigint` is just a big `number`" — wrong lane: no mixing, different `typeof`, different `lib` history, different JSON behavior. Treat `bigint` like a distinct currency that requires exchange at the boundary.
- "`symbol` is like a string ID" — strings collide; symbols don't. But `Symbol("a") !== Symbol("a")` — each call creates a new identity. Only `Symbol.for("a")` shares a registry (and types as plain `symbol`, not `unique symbol`).
- "`unique symbol` can be widened to `symbol`" — yes (unique is subtype of `symbol`), but widening loses identity: a function taking `symbol` will accept any symbol, not the specific one. Annotate `unique symbol` at declarations where identity matters.

### 6) **Performance note**

`bigint` arithmetic is arbitrary-precision (big-integer library in the engine, not a single CPU register). It allocates for values beyond 64 bits and is ~10–100× slower than `number` for tight loops (measured as of V8/Node 24 era — microbenchmark, not dogma). Use it where precision justifies cost; in hot numeric loops, `number` + range checks is cheaper. `symbol` creation allocates a GC-tracked symbol value; `unique symbol` has no extra runtime cost over plain `symbol` — the uniqueness is a type-level fact.

### 7) **Mentor note**

Students should articulate when *not* to reach for `bigint`/`symbol`. Exercise: give them a ledger task where balances exceed `MAX_SAFE_INTEGER` and a cache-key task where string IDs currently collide across modules — in the first `bigint` wins, in the second `symbol` (or branded string — see [branding](<../../../02 The Type System Core/sections/1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>)) wins. Review checklist: does the PR include a `BigInt→string` conversion before `JSON.stringify` and before any `Math.*` call?
