## 1.3. null and undefined strictNullChecks and optionality

### 1) **Two absences, different intent** (`undefined` means "not yet assigned / not present"; `null` means "intentionally empty" — TypeScript makes both explicit under `--strict`)

**Definition** — `null` and `undefined` are distinct primitive values and, under `--strict` (which enables `strictNullChecks`), distinct types. `undefined` is the implicit absence JavaScript produces (`let x;` → `undefined`, missing property → `undefined`, `void` function → `undefined`); `null` is the *explicit* absence you assign (`let x = null`). TypeScript under `--strict` forces you to declare which absences a type admits.

- As of TypeScript 5.9 era (Aug 2026), `--strict` is the default in `npx tsc --init`; greenfield projects should never disable `strictNullChecks` — disabling it re-introduces billion-dollar-mistake bugs where every type silently includes `null`/`undefined`.
- **History** — before TS 2.0, `string` included `null`/`undefined` (all types nullable). `strictNullChecks` (TS 2.0, 2016) changed the type system to make nullability opt-in — the single most impactful correctness feature (see [01/1.3. Superset, soundness flavor](<../../../01 Fundamentals and Mental Model/sections/1. What TypeScript is/1.3. Superset soundness and the type system flavor.md>)).

| Value | How JavaScript produces it | Type under `--strict` | Assignable to `string`? |
|---|---|---|---|
| `undefined` | `let x;`, `({}).missing`, `void` return | `undefined` | no — need `string \| undefined` |
| `null` | `JSON.parse("null")`, explicit `= null` | `null` | no — need `string \| null` |

### 2) **strictNullChecks is the divider** (without it `null`/`undefined` are assignable to everything; with it they are separate members — the single most impactful flag)

- **Without the flag** (legacy, not recommended) — `let s: string = null;` compiles. Every `string` variable might be `null` at runtime — the checker proves nothing.
- **With `strictNullChecks: true`** — `let s: string = null;` → error `Type 'null' is not assignable to type 'string'`. You must write `string | null` or `string | undefined` to admit absence — call sites must handle it (`if (s !== null)`, `s ?? "default"`, optional chaining `s?.length`).

```typescript
// strictNullChecks ON
// let bad: string = undefined; // error TS2322
let ok: string | undefined = undefined; // must be explicit
function len(s: string): number { return s.length; }
// len(ok); // error — ok might be undefined
if (ok !== undefined) len(ok); // ok — narrowed
console.log(ok?.length ?? 0); // safe access + fallback
```

- The flag also controls control-flow analysis: after `if (x == null) return;`, the checker knows `x` is non-nullable below — the pattern `if (value == null)` (double-equals) narrows both `null` and `undefined` at once (idiomatic).

### 3) **Optionality vs union** (`prop?: string` vs `prop: string | undefined` vs `prop: string | null` — assignability and `--exactOptionalPropertyTypes`)

Three spellings look similar but mean different things:

| Declaration | Key may be missing? | Value may be `undefined` when present? | Value may be `null`? |
|---|---|---|---|
| `prop?: string` | yes (`{}` is ok) | yes, if `--exactOptionalPropertyTypes: false` (default) | no |
| `prop: string \| undefined` | no (`{}` is error) | yes (must write `prop: undefined` explicitly) | no |
| `prop: string \| null` | no | no | yes (`prop: null` only) |
| `prop?: string \| null` | yes | via `?` | yes |

- **Key nuance** — `prop?: string` with the default `exactOptionalPropertyTypes: false` allows *both* missing and `undefined`-valued. With `exactOptionalPropertyTypes: true` (TS 4.4+, stricter, recommended for new codebases), `prop?: string` means *missing or string* — `undefined` as an explicit value is *not* allowed unless you write `prop?: string | undefined`. This catches the bug where `JSON.stringify` strips `undefined` properties but preserves `null`.

**Modern guidance** — default to `prop?: string` for optional input (allow missing), `string | null` when the domain requires an explicit empty placeholder (e.g., database nullable columns). Enable `exactOptionalPropertyTypes` in strict configs once the codebase is clean — it surfaces missing-vs-undefined confusion at call sites.

### 4) **Runnable example** — nullish handling and optionality (good vs bad)

```typescript
// good — strictNullChecks ON (tsconfig: { strict: true })
type User = {
  id: string;
  displayName?: string;          // may be missing (optional)
  nickname: string | null;       // always present, may be intentionally empty
  bio: string | undefined;       // always present as key, may be undefined
};

function greeting(user: User): string {
  // optional + nullish handling — checker forces branches
  const name = user.displayName ?? user.nickname ?? "there";
  // user.displayName: string | undefined — optional
  // user.nickname: string | null — must handle null
  const bio = user.bio ?? "(no bio)"; // string | undefined → narrowed
  return `hi ${name} — ${bio}`;
}
console.log(greeting({ id: "1", nickname: null, bio: undefined })); // hi there — (no bio)

// exactOptionalPropertyTypes:true difference (commented — enable to see the error)
// type Exact = { title?: string };          // default false: { title: undefined } is allowed
// type ExactStrict = { title?: string }; // with exactOptionalPropertyTypes:true: { title: undefined } errors — need title?: string | undefined

// bad — disabling or ignoring strictNullChecks (legacy escape)
function lenUnsafe(s: string): number { return s.length; }
// In strict mode this is an error: lenUnsafe(undefined) not allowed.
// In non-strict mode it compiles and throws at runtime: Cannot read properties of undefined.

// good — narrowing both null and undefined with == null
function lenSafe(s: string | null | undefined): number {
  if (s == null) return 0; // narrows null + undefined in one check
  return s.length; // s is string here
}
console.log(lenSafe(null)); // 0
console.log(lenSafe("hi")); // 2

// bad — conflating null and undefined over a JSON boundary
const apiResponse: { note: string | null } = { note: null }; // API sends null for missing
const local: { note?: string } = {}; // local model optional
// When you POST local, JSON.stringify strips undefined but preserves null:
// console.log(JSON.stringify(local));           // {} — note missing entirely
// console.log(JSON.stringify(apiResponse)); // {"note":null} — explicit null
// fix: model the wire type as sent (null) and convert at the boundary
function toWire(local: { note?: string }): { note: string | null } {
  return { note: local.note ?? null };
}

// bad — optional property assigned undefined then spread (exactOptionalPropertyTypes)
function makeConfigBad(exact: { title?: string }): object {
  // With exactOptionalPropertyTypes:true, this would error if title is explicitly undefined
  return { ...exact };
}
// fix: be explicit about the three states (missing | string | null) and set exactOptionalPropertyTypes accordingly
```

### 5) **Common confusion**

- "`undefined` and `null` are interchangeable" — not under `--strict`: they are distinct members with different assignability. Functions that accept `string | null` do not accept `undefined` — the caller must convert (`value ?? null`). Pick one absence for your API and stay consistent.
- "`prop?: string` means `prop: string | undefined`" — almost, but not with `exactOptionalPropertyTypes:true`, and `{ prop: undefined }` is observably different from `{}` after `JSON.stringify` or `Object.keys`. Review APIs for which one the consumer actually expects.
- "`void` means `undefined`" — they overlap (a `void` function returns `undefined` when run) but differ in signatures: `() => void` allows a caller to ignore the return; `() => undefined` promises the value is `undefined` (see [2.3. never and void](<../2. The Special Types/2.3. never and void bottom vs deliberate nothing.md>)).

### 6) **Performance note**

Nullish checks have no emit cost beyond the branch you would write in plain JavaScript (`if (x == null)` → same JS). The perf win of `strictNullChecks` is *indirect*: it prevents `TypeError: Cannot read properties of null/undefined` in production — the most common JS exception in telemetry. The flag adds type-checker work (control-flow analysis per branch), but incremental builds keep it tractable; disabling it to "speed up `tsc`" trades hours of debugging for milliseconds of check time — bad trade (see [18 Memory management](<../../../../JavaScript/18 Memory Management and GC/README.md>) for why unchecked nulls cause downstream allocation/GC surprises when error paths allocate).

### 7) **Mentor note**

Teach optionality as "three questions at the API boundary": can the key be missing? can it be `undefined` when present? can it be `null`? Require students to answer all three before choosing a spelling. Review checklist: every function that touches external data (`fetch`, `JSON.parse`, `localStorage`) has a `| null | undefined` in its signature until validated — if not, ask "where did null go?". Enable `exactOptionalPropertyTypes` on new projects once the team can articulate why `{ prop: undefined }` differs from `{}`.
