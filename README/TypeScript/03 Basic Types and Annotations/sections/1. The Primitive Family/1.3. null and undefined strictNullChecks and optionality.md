## 1.3. null and undefined strictNullChecks and optionality

### 1) **Two absences, different intent**

`null` and `undefined` are distinct JavaScript primitive values. APIs often use `null` for an explicitly empty field and `undefined` for an absent result or omitted optional input. That is a convention an API must define, not a meaning enforced by JavaScript. A present property can hold undefined; a function can explicitly return it.

Under `strictNullChecks`, the two values have distinct types and cannot be used as an ordinary string without evidence. A union such as `string | null` deliberately admits null. The compiler's model remains separate from runtime input validation: unchecked data or assertions can still violate it.

### 2) **StrictNullChecks is the divider**

Use strict null checking for new typed contracts. The [primary flag reference](https://www.typescriptlang.org/tsconfig/strictNullChecks.html) explains why an absent result must be handled. Disabling the flag permits many nullish assignments and uses that would otherwise be rejected. It does not change JavaScript or remove every other type check.

Use TypeScript 7.0.2 and Node.js 20.20.2. Save `absence.mts` in an empty directory. The command below explicitly selects strict and exact optional checking; do not depend on an older generated starter configuration.

```typescript
// absence.mts
function lengthOrZero(value: string | null | undefined): number {
  if (value == null) return 0;
  return value.length;
}
function shown(value: string | null | undefined): string {
  return value?.toUpperCase() ?? "missing";
}
console.log(lengthOrZero(null), lengthOrZero(undefined), lengthOrZero("hi"));
console.log(shown(null), shown(""), shown("Ada"));

interface Optional { note?: string }
interface RequiredUndefined { note: string | undefined }
interface RequiredNull { note: string | null }
const missing: Optional = {};
const present: RequiredUndefined = { note: undefined };
const empty: RequiredNull = { note: null };
console.log(Object.hasOwn(missing, "note"), Object.hasOwn(present, "note"));
console.log(JSON.stringify(missing), JSON.stringify(present), JSON.stringify(empty));
function toWire(value: Optional): RequiredNull {
  return { note: value.note ?? null };
}
console.log(JSON.stringify(toWire(missing)), JSON.stringify(toWire({ note: "" })));
function read(value: Optional): string | undefined { return value.note; }
console.log(read(missing));
```

```sh
tsc --strict --exactOptionalPropertyTypes --target ES2022 --module NodeNext --noEmitOnError --outDir dist absence.mts
node dist/absence.mjs
```

Output:

```text
0 0 2
missing  ADA
false true
{} {} {"note":null}
{"note":null} {"note":""}
undefined
```

The `== null` condition intentionally matches both null and undefined; returning from that branch leaves a string for the subsequent property access. Optional chaining avoids accessing a nullish receiver. `??` uses a fallback only for null or undefined, so the empty string remains empty. It does not behave like a truthiness fallback.

`Object.hasOwn` observes missing versus present-with-undefined. JSON omits that undefined-valued object property, so both objects serialize as `{}`. Explicit null survives. The wire conversion chooses an explicit-null convention while retaining empty text. This is an application decision, not an effect of a type annotation.

### 3) **Optionality versus union**

With strict null checking and `exactOptionalPropertyTypes: true`, use these contracts:

| Property declaration | Can omit the key? | Can supply undefined explicitly? | Can supply null? |
|---|---|---|---|
| `note?: string` | Yes | No | No |
| `note?: string \| undefined` | Yes | Yes | No |
| `note: string \| undefined` | No | Yes | No |
| `note: string \| null` | No | No | Yes |
| `note?: string \| null` | Yes | No | Yes |

Reading an optional member can still produce undefined because the key may be absent. Exact checking restricts certain **writes**; it does not eliminate absence from reads. If exact checking is disabled, `note?: string` also accepts a present undefined. The [primary exact-option reference](https://www.typescriptlang.org/tsconfig/exactOptionalPropertyTypes.html) explains the existence distinction.

Append each independent negative probe, compile, and restore before the next:

```typescript
const explicitUndefined: Optional = { note: undefined };
```

```typescript
const omittedRequired: RequiredUndefined = {};
```

```typescript
const wrongAbsence: RequiredNull = { note: undefined };
```

These report TS2375, TS2741 and TS2322 respectively. The first passes with `--exactOptionalPropertyTypes false`; the missing required key remains rejected. These rules describe compatible inputs, not exact runtime key inventories for all structurally typed values.

A required parameter whose type includes undefined similarly differs from an optional parameter: the required one still requires an argument position. [TkDodo's original refactoring account](https://tkdodo.eu/blog/optional-vs-undefined) explains why that distinction can expose missed callers; it also motivates deliberate optional-property rules. The full parameter and object-update mechanics belong to their linked owners.

For a separate runtime contrast, save `loose.mts`:

```typescript
// loose.mts
function length(value: string): number { return value.length; }
console.log(length(undefined));
```

Check it with the build command above, replacing `absence.mts` with `loose.mts`: TS2345, exit 1. For this separate probe, disable **both** exact optional checking and strict null checking by adding `--exactOptionalPropertyTypes false --strictNullChecks false`. Compilation then succeeds; running `node dist/loose.mjs` throws TypeError. Keep the intentional failure separate from the successful example and restore strict checking afterward.

### 4) **Common confusion**

Optional and required-with-undefined are not identical even when exact checking is off: a required property must still be supplied in the checked shape. Conversely, JSON is unable to preserve this example's missing-versus-undefined distinction merely because both static types exist.

Void is a separate result contract. A void callback can cause its caller to ignore a real returned value; do not infer that every function viewed as returning void actually produces undefined. The [void owner](<../2. The Special Types/2.3. never and void bottom vs deliberate nothing.md>) explains that distinction.

### 5) **Performance note**

Nullability annotations and compiler flags add no runtime validator. The written guards, optional chaining, fallback and serialization still execute; emitted syntax depends on target. No checker-timing, exception-frequency or garbage-collection claim was measured. Decide the valid absence states first and measure actual processing costs if necessary.

### 6) **Mentor note**

Ask three questions before choosing a property spelling: may the key be omitted, may a present value be undefined, and may it be null? Then predict both own-property observations and JSON output. A sound answer explains why two different objects can serialize identically. For a migration review, identify which newly rejected call or assignment represents an intended contract rather than automatically suppressing the error.
