## 5.1. Assess a complete native compiler migration

### 1) **Turn an upgrade decision into distinct evidence**

Your team proposes using TypeScript 7 for a small library while retaining a 6.0 compiler API for typed linting. The release must preserve a working ESM entry point, declarations and string-count behavior. The assessment is to decide which gates establish those promises and prove that a green source check cannot hide a broken consumer package.

The [VS Code team's first-hand migration account](https://code.visualstudio.com/blogs/2026/06/26/iterating-faster-with-ts-7) describes introducing checking, emission and editor use in separate stages with an escape hatch. That historical preview rollout motivates separate evidence; it is not a current compatibility table or a schedule every team must copy. For this stable example, the [7.0 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) and [tool compatibility lesson](<../2. Editor and Tool Compatibility/2.1. Editor and tool API compatibility.md>) establish the native/compatibility package arrangement.

Complete the fixture below and keep a short decision record: command, actual version, artifact or diagnostic observed, and the promise it verifies. Add your application's own framework, editor and deployment checks before using this decision outside the fixture.

### 2) **Build a library with explicit ownership of each compiler**

Use Node 20.20.2 and npm 10.8.2, the tested environment. Create sibling `library` and `consumer` directories. In `library`, save `package.json`:

```json
{
  "name": "migration-counts",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "files": [
    "dist"
  ],
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    }
  },
  "scripts": {
    "check": "tsc -p tsconfig.json --noEmit",
    "check:compat": "tsc6 -p tsconfig.json --noEmit",
    "build": "tsc -p tsconfig.json",
    "build:compat": "tsc6 -p tsconfig.json --outDir dist-6",
    "lint": "eslint src"
  },
  "devDependencies": {
    "@typescript/native": "npm:typescript@7.0.2",
    "typescript": "npm:@typescript/typescript6@6.0.2",
    "eslint": "10.12.0",
    "typescript-eslint": "8.71.1"
  },
  "overrides": {
    "@typescript/old": "npm:typescript@6.0.3"
  }
}
```

Native `tsc` checks and builds. The compatibility package supplies `tsc6` and the older imported API for ESLint; the override pins its actual compiler to 6.0.3. Save `library/tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "lib": [
      "es2022"
    ],
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "rootDir": "src",
    "outDir": "dist",
    "types": [],
    "declaration": true
  },
  "include": [
    "src/**/*.ts"
  ]
}
```

Explicit roots, target, module mode and global types keep the artifact contract reviewable. Save `library/src/index.ts`:

```typescript
export interface Counts { units: number; points: number }
export function counts(input: string): Counts {
  return { units: input.length, points: [...input].length };
}
export function snapshot(input: string): Promise<Counts> {
  return Promise.resolve(counts(input));
}
```

`counts` exposes two explicitly named units, and `snapshot` returns the same contract through a promise. Neither claims to count graphemes. The output directories for native and compatibility builds are separate, so one build cannot silently overwrite the other's evidence.

Save `library/eslint.config.mjs`:

```javascript
import tseslint from "typescript-eslint";

export default [{
  files: ["src/**/*.ts"],
  languageOptions: {
    parser: tseslint.parser,
    parserOptions: {
      projectService: true,
      tsconfigRootDir: import.meta.dirname,
    },
  },
  plugins: { "@typescript-eslint": tseslint.plugin },
  rules: { "@typescript-eslint/no-floating-promises": "error" },
}];
```

From `library`, run:

```bash
npm install
node node_modules/@typescript/native/lib/tsc.js --version
node node_modules/typescript/bin/tsc6 --version
node --input-type=module -e 'import ts from "typescript"; if (typeof ts.createProgram !== "function") throw Error("missing API"); console.log(ts.version);'
npm run check
npm run check:compat
npm run lint
npm run build
npm run build:compat
```

The native command printed 7.0.2; the compatibility command and imported API printed 6.0.3. All five scripts exited zero. Observe the API function as well as the version: a package name alone cannot establish that a tool receives its expected interface. Keep the generated lockfile with the assessment inputs.

### 3) **Assess a deliberate semantic difference**

Create `library/probes/native.ts`:

```typescript
type HeadTail<S extends string> =
  S extends `${infer Head}${infer Tail}` ? [Head, Tail] : never;
const parts: HeadTail<"😀abc"> = ["😀", "abc"];
```

Create `library/probes/compat.ts`:

```typescript
type HeadTail<S extends string> =
  S extends `${infer Head}${infer Tail}` ? [Head, Tail] : never;
const parts: HeadTail<"😀abc"> = ["\ud83d", "\ude00abc"];
```

Run these from `library`:

```bash
node node_modules/@typescript/native/lib/tsc.js --ignoreConfig --strict --target es2022 --lib es2022 --noEmit probes/native.ts
node node_modules/typescript/bin/tsc6 --ignoreConfig --strict --target es2022 --lib es2022 --noEmit probes/compat.ts
```

Both checks exited zero. `ignoreConfig` makes these file-specific probes independent of the library configuration present in the working directory; otherwise the tested compatibility command reports TS5112. The expectations differ deliberately because [Unicode inference](<../4. Unicode Inference/4.1. Unicode code points in template literal inference.md>) changed. A migration review should classify this documented difference rather than demand that every internal type probe remain textually identical across versions. The public `Counts` interface and runtime counting policy remain explicit and independently tested.

### 4) **Consume the packed artifact instead of the source directory**

From `library`, run `npm pack --json`. [npm pack](https://docs.npmjs.com/cli/v11/commands/npm-pack/) creates a tarball; it does not publish it. Inspect the returned file list: both `dist/index.js` and `dist/index.d.ts` must be present. This run created `migration-counts-1.0.0.tgz`.

Save `consumer/package.json`:

```json
{
  "private": true,
  "type": "module",
  "dependencies": {
    "migration-counts": "file:../library/migration-counts-1.0.0.tgz"
  },
  "devDependencies": {
    "typescript": "7.0.2"
  }
}
```

Save `consumer/tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "lib": [
      "es2022"
    ],
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "rootDir": ".",
    "outDir": "dist",
    "types": []
  },
  "include": [
    "smoke.ts"
  ]
}
```

Save `consumer/smoke.ts`:

```typescript
import { counts, snapshot } from "migration-counts";
import type { Counts } from "migration-counts";
const result: Counts = counts("😀abc");
if (result.units !== 5 || result.points !== 4) throw new Error("wrong counts");
const asyncResult = await snapshot("👩‍🚀");
if (asyncResult.units !== 5 || asyncResult.points !== 3) throw new Error("wrong snapshot");
```

From `consumer`, run:

```bash
npm install
npm ci
node node_modules/typescript/lib/tsc.js -p tsconfig.json
node dist/smoke.js
node ../library/node_modules/typescript/bin/tsc6 -p tsconfig.json --outDir dist-6
node dist-6/smoke.js
```

All commands exited zero; the two runtime checks intentionally print nothing on success. They check the library installed from the tarball, including its declared ESM entry point and exported types. [npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/) replays the existing lockfile without updating it; this is a local clean installation check, not proof of every platform's reproducibility.

Save `library/parity.mjs` and run `node parity.mjs` from `library`:

```javascript
import { counts as native } from "./dist/index.js";
import { counts as compat } from "./dist-6/index.js";
for (const input of ["😀abc", "👩‍🚀"]) {
  if (JSON.stringify(native(input)) !== JSON.stringify(compat(input))) {
    throw new Error("changed output");
  }
}
```

The compatibility compiler emits the unchanged library into `dist-6`. This comparison of the two built entry points exited zero for the smile and astronaut. That is useful evidence for an emission fallback. It does not prove that a one-line compiler downgrade would reverse changed dependencies, configuration or public type semantics in an application. A real rollback record retains the previous manifest, lockfile, source/configuration revision and generated artifact route.

### 5) **Prove that the gates catch different failures**

First append `snapshot("😀abc");` to the library source without awaiting or handling it. Both source compiler checks still exit zero, while `npm run lint` exits 1 with `no-floating-promises`. Restore the source and run lint again; it passes. The linter's independently meaningful failure proves that it is active rather than a decorative script.

Next simulate an artifact mistake in this scratch fixture. Change the library version to `1.0.1` and its `files` list to `["dist/*.js"]`, then run `npm run check` and `npm pack --json`. Checking still passes, but the new tarball omits `index.d.ts`. Make a fresh sibling `bad-consumer`, copy the consumer's config/source and save its package manifest with the dependency changed to `file:../library/migration-counts-1.0.1.tgz`. Install there and run its native compiler with `-p tsconfig.json --noEmit`.

The observed consumer check exits 1 with TS7016 because declarations are missing. A direct JavaScript import of `counts` from that installed package still runs successfully. This is the reason source checking, consumer type checking and runtime import checks are separate gates. Restore the original library manifest after the experiment; do not let the intentionally bad packaging become the release input.

### 6) **Write a decision that the evidence supports**

An adequate decision for this fixture records:

| Promise | Observed evidence | Limit |
|---|---|---|
| Native checking/building works | 7.0.2 source check and emit pass | No framework compiler integration tested |
| Typed lint receives an older API | 6.0.3 API probe passes; floating-promise mutation fails lint | Only the configured rule/tool versions tested |
| Known inference difference is understood | Each compiler's explicit Unicode probe passes | No general string-parser compatibility claim |
| Packed consumers receive JS and types | Tarball manifest and two compiler/runtime consumers pass | Only this ESM export and Node environment tested |
| Packaging gate is meaningful | Missing-declaration tarball causes TS7016 | Other export conditions need their own consumers |
| An emission fallback exists locally | Separate 6.0.3 build gives matching counts | Full application rollback not rehearsed |

The fixture supports adoption for its declared interfaces and environment. Editor support, watch behavior and performance require their own evidence; the earlier [build/watch comparison](<../3. Native Build and Watch/3.1. Native builds watch and measurement.md>) supplies a method, not performance numbers to transplant into this package. For your application, record unresolved checks as unresolved and make the promotion criterion explicit.

### 7) **Common confusion**

The package installed under `typescript` here intentionally provides the 6.0 API, while native `tsc` comes from the other alias. “We upgraded TypeScript” therefore needs an interface and version attached. Likewise, green compilation of source cannot prove that a tarball contains declarations: the missing-file experiment demonstrates a consumer failure even when the source and JavaScript import remain valid.

### 8) **Performance note**

Running both compilers and multiple consumers adds verification work during a migration window. This assessment did not measure its elapsed cost or savings, and the cost is not necessarily exactly twice a single check. Keep the temporary comparison gates only as long as their migration purpose requires; retain the release consumer checks that protect the artifact contract. The small fixture is correctness evidence, not a benchmark.

### 9) **Mentor note**

Ask the learner which result would stay green if `index.d.ts` disappeared from the tarball. A sound answer names the source check and runtime import, then points to the consumer's type check as the failing gate. Ask for the same reasoning for an unhandled promise and for a compiler API import. The assessment is passed when the learner can explain each gate's jurisdiction and limitations, not merely collect green command outputs.
