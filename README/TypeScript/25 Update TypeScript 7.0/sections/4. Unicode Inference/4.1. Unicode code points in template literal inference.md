## 4.1. Unicode code points in template literal inference

### 1) **Know which string unit your contract means**

A type utility that extracts the first part of a string can change its result even when its source code stays the same. TypeScript 7 preserves a supplementary Unicode code point when inferring adjacent template-literal parts. In the verified 6.0.3 comparison, the same pattern splits its UTF-16 surrogate pair. The [7.0 release announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) identifies this as a breaking change for utilities that modeled code units.

A UTF-16 code unit is one 16-bit part of JavaScript's string representation. The smile in `"😀"` needs two units, which together encode one Unicode code point. A grapheme cluster is a user-perceived character and can contain several code points: `"👩‍🚀"` combines a woman, a zero-width joiner and a rocket. Keeping a surrogate pair together does not keep that whole grapheme together.

The compiler change applies to inferred types. JavaScript still indexes strings by code unit and iterates strings by code point, as specified by [String iteration](https://tc39.es/ecma262/multipage/text-processing.html#sec-string.prototype-@@iterator). The full runtime explanation belongs in [JavaScript's string-unit lesson](<../../../../JavaScript/11 Strings and Regular Expressions/sections/1. String model/1.2. Indexing length and iteration code units vs code points vs graphemes.md>); here we test the upgrade's effect on type contracts.

### 2) **Lock the old and new results with executable type tests**

Use a fresh directory with Node 20.20.2 and npm 10.8.2. Save `package.json`, then run `npm install`:

```json
{
  "private": true,
  "devDependencies": {
    "typescript": "7.0.2",
    "ts6": "npm:typescript@6.0.3"
  }
}
```

Save `old.ts`:

```typescript
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type HeadTail<S extends string> =
  S extends `${infer Head}${infer Tail}` ? [Head, Tail] : never;
type SplitCount<S extends string, Steps extends unknown[] = []> =
  S extends `${infer _Head}${infer Tail}`
    ? SplitCount<Tail, [...Steps, unknown]> : Steps["length"];
type Ascii = Expect<Equal<HeadTail<"abc">, ["a", "bc"]>>;
type Empty = Expect<Equal<HeadTail<"">, never>>;
type Combining = Expect<Equal<SplitCount<"e\u0301">, 2>>;
type EmojiHead = Expect<Equal<HeadTail<"😀abc">, ["\ud83d", "\ude00abc"]>>;
type EmojiCount = Expect<Equal<SplitCount<"😀abc">, 5>>;
type AstronautCount = Expect<Equal<SplitCount<"👩‍🚀">, 5>>;
```

`Equal` compares the tested types and `Expect` requires the result to be `true`. A changed result therefore becomes TS2344 rather than a stale comment. `HeadTail` infers one leading part and the remaining string. `SplitCount` removes that leading part repeatedly, recording one tuple element per step. It is a demonstration for the short, concrete literals shown; it is not a general counter for arbitrary dynamic strings or huge generated literals.

Save `new.ts` as a separate compiler input:

```typescript
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type HeadTail<S extends string> =
  S extends `${infer Head}${infer Tail}` ? [Head, Tail] : never;
type SplitCount<S extends string, Steps extends unknown[] = []> =
  S extends `${infer _Head}${infer Tail}`
    ? SplitCount<Tail, [...Steps, unknown]> : Steps["length"];
type Ascii = Expect<Equal<HeadTail<"abc">, ["a", "bc"]>>;
type Empty = Expect<Equal<HeadTail<"">, never>>;
type Combining = Expect<Equal<SplitCount<"e\u0301">, 2>>;
type EmojiHead = Expect<Equal<HeadTail<"😀abc">, ["😀", "abc"]>>;
type EmojiCount = Expect<Equal<SplitCount<"😀abc">, 4>>;
type AstronautCount = Expect<Equal<SplitCount<"👩‍🚀">, 3>>;
```

Run the two matched checks:

```bash
node node_modules/ts6/lib/tsc.js --strict --target es2022 --module commonjs --lib es2022,dom --noEmit old.ts
node node_modules/typescript/lib/tsc.js --strict --target es2022 --module commonjs --lib es2022,dom --noEmit new.ts
```

Both exited zero with the pinned compilers. The emoji-leading tuple changes from surrogate halves to `["😀", "abc"]`; the count changes from 5 to 4. The astronaut changes from five code-unit steps to three code-point steps. ASCII, empty-string handling and the decomposed `e` plus combining accent assertions retain their tested results.

Now exchange the input filenames in those commands. The 6.0.3 compiler rejects `new.ts` with three TS2344 diagnostics and exit 2. The 7.0.2 compiler rejects `old.ts` with the same three assertion diagnostics and exit 1. These intentional failures establish the changed contract; do not run both files in one program, because their demonstration aliases deliberately use the same names.

### 3) **Observe the unchanged runtime contract**

Save `runtime.ts`:

```typescript
const segmenter = new Intl.Segmenter("en", { granularity: "grapheme" });
for (const input of ["😀abc", "e\u0301", "👩‍🚀"]) {
  console.log(input.length, [...input].length, [...segmenter.segment(input)].length);
}
const input = "😀abc";
console.log(JSON.stringify(input[0]), JSON.stringify([...input][0]));
console.log("\u00e9".normalize("NFC") === "e\u0301".normalize("NFC"));
```

Compile and run it:

```bash
node node_modules/typescript/lib/tsc.js --strict --target es2022 --module commonjs --lib es2022,dom --outDir dist runtime.ts
node dist/runtime.js
```

The observed output was:

```text
5 4 4
2 2 1
5 3 1
"\ud83d" "😀"
true
```

Each of the first three rows shows code-unit length, code-point count and grapheme count. The decomposed accent has two code points but one grapheme; the astronaut has three code points but one grapheme. `Intl.Segmenter` uses the requested grapheme granularity, as described in the [internationalization specification](https://tc39.es/ecma402/#sec-intl.segmenter.prototype.segment). These outputs were also observed after compiling the same file with 6.0.3. The compiler upgrade did not turn `input[0]` into code-point indexing.

The last line compares explicitly normalized runtime strings. Template-literal inference is not a normalization step. A composed accent and its decomposed representation need a separate policy when equality, storage or display rules require normalization.

### 4) **Migrate according to the intended invariant**

Search for recursive string splitting, type-level length counters and generic return types derived from a first-character utility. If an API promised a UTF-16 offset, simply accepting the new inferred count would change its meaning. If it promised code points, update the versioned type tests and verify that the runtime implementation also iterates code points. If it promised visible characters, neither old nor new `SplitCount` establishes that promise; use a runtime grapheme policy and test representative sequences.

[PersistDev's worked explanation](https://www.persistdev.blog/post/typescript-7-template-literal-unicode-code-points) uses the indexing-versus-iteration contrast to introduce this migration question. Our additional combining-accent and joined-emoji cases keep “character” from concealing three different contracts. Avoid a cast that merely labels `input[0]` as the inferred full emoji: the assertion cannot change the returned surrogate half.

Exercise: change the astronaut count assertion in `new.ts` to expect 1. Predict the result and explain the repair. The actual check produces TS2344, because inference consumes three code points rather than one grapheme. Restore 3 for this utility; a display-character requirement belongs in a segmentation function and its runtime tests. A sound answer changes the contract or the implementation deliberately, rather than silencing the assertion.

### 5) **Common confusion**

“Unicode-aware” does not mean “one visible character per step.” The paired-surrogate change makes the emoji head a complete code point, while combining marks and joiners remain separate code points. It also does not validate arbitrary input strings, fix lone surrogates or normalize text. Name a counter's unit explicitly and keep its literal type probes separate from its dynamic-input runtime validation.

### 6) **Performance note**

These type aliases erase during emission, so the inference change adds no runtime counting operation. Recursive splitting still asks the checker to evaluate successive tails; long literals can meet compiler limits, and a shorter inferred tuple alone is not a measured build-speed improvement. This lesson measured correctness, not compile-time or segmentation throughput. Use the measured diagnostic workflow before making a performance claim.

### 7) **Mentor note**

Ask a learner to explain the runtime `5 3 1` row before discussing the compiler version. Then ask why the type counter expects 3 in 7.0.2 while an input field might enforce a one-grapheme display limit. A sound answer identifies the invariant, the runtime operation and the type test independently. Include a combining mark in review probes so a lone smiling emoji cannot create false confidence.
