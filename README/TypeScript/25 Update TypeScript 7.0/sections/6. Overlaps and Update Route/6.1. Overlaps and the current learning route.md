## 6.1. Overlaps and the current learning route

### 1) **Keep concepts with their owners and study the version delta here**

An incremental update answers “what changed, and what must I verify when moving versions?” The topical lessons answer “how does this concept work?” You need both routes, but repeating the full type system or release process here would make the same explanation drift in several places.

This domain's verified compiler is 7.0.2. Each worked lesson names its comparison compiler, runtime and tested interface. The [stable release announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) establishes the release; the local examples establish their narrower behavior. A compiler version does not establish runtime availability or compatibility of an editor, linter or framework.

### 2) **Choose a route from what you already understand**

A returning reader who understands TypeScript's basic checking and project configuration can study this domain in its published order: configuration, interfaces, build/watch evidence, Unicode contracts, then the assessment. Start with a small project whose current command outputs and entry points you can reproduce. Record a mismatch before deciding whether it is a configuration migration, intentional type change, tool-interface problem or runtime failure.

A new reader should begin with [Fundamentals](<../../../01 Fundamentals and Mental Model/README.md>) and the type-system path in the [track index](<../../../README.md>). When reaching [running TypeScript](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>), use the verified execution environments there. At the configuration and tooling stages, follow this domain's defaults and interface comparisons before copying an older version-specific setup. Return to Unicode inference after conditional types and template-literal transformations make the pattern understandable.

The assessment is an integration task after those prerequisites. It combines known mechanics into evidence for a release decision. Starting there before understanding imports, declarations and compiler-versus-runtime behavior would turn the exercise into command copying. Conversely, a returning reader does not need to reread ordinary narrowing to understand a changed compiler option.

### 3) **Practice routing an actual failure**

Exercise: select a first diagnostic route for each case and explain what the selected evidence can establish.

| Case | Reasoned first route |
|---|---|
| `tsc --noEmit` passes, but the emitted entry point moved under `dist/src` | Use the configuration migration's check/emit contrast, then inspect `rootDir` and actual output. The green check alone does not establish the deployment path. |
| Native checking passes, but a tool cannot call `createProgram` | Identify which package/interface the tool imports, then use the compatibility lesson's API probe. A successful CLI invocation does not supply the older in-process API. |
| A recursive string counter changes its result for an emoji | Use the Unicode versioned assertions and distinguish code units, code points and graphemes. Avoid changing runtime indexing through a cast. |
| A packed consumer loses types while its JavaScript import still works | Use the assessment's missing-declaration experiment, then the package declaration/export owner. Source checks cannot inspect an omitted tarball file. |
| An API payload passes a trusted predicate and then crashes on a missing field | Use the [unknown boundary lesson](<../../../03 Basic Types and Annotations/sections/2. The Special Types/2.2. unknown the type-safe top type.md>) and validate every required field. This is an ordinary boundary contract, not evidence of a native compiler regression. |

For the first four cases, the update lesson supplies a concrete comparison or integration test. The fifth uses an unchanged concept in its topical owner. These routes lead to existing lessons; a version label does not justify creating a second full explanation of each mechanism.

### 4) **Common confusion**

The update domain is not a replacement prerequisite chain or proof that every old example works under 7.0.2. Historical examples can remain useful when their environment is identified, while current setup requires current evidence. Likewise, “both compilers passed” can mean only source checking; ask whether declarations, emitted consumers, tool APIs and runtime behavior were checked separately.

### 5) **Performance note**

Following a navigation route has no direct effect on the compiler's execution cost. It can help you choose the correct measurement or avoid investigating the wrong layer, but that is not a measured speedup. Use the build comparison for matching cache states and actual timings; use the API compatibility route for a tool failure. Repeating an explanation across files would create documentation maintenance work, not additional runtime checking by itself.

### 6) **Mentor note**

Give the learner a failing command and ask them to name its interface, version, input and observed output before opening a link. Then ask which additional check would distinguish the two most plausible explanations. A sound answer might choose an emitting build after a passing check, or a packed-consumer type test after a successful source build. Routing is successful when the learner can explain why the next observation separates the hypotheses.
