## 3.1. Native builds watch and measurement

### 1) **Compare the same work before interpreting speed**

A compiler upgrade can shorten the wait for feedback, but a timing is meaningful only when you know what work ran. A fresh build, an unchanged incremental invocation and a build after editing one file answer different questions. Comparing a fresh 6.0 build with an unchanged 7.0 invocation mostly compares cache states.

TypeScript 7 uses native code and parallel work. Its [release announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) describes parsing, checking and emission in parallel, plus experimental `checkers` and `builders` controls. Start with defaults; increasing workers can increase memory use, and project dependencies constrain parallel builds. This lesson measures the default single-project CLI and checks watch behavior. It does not measure editor latency or recommend a worker count.

The distinction between full and incremental work also structures [Pashalis Laoutaris's original benchmark](https://laoutaris.org/blog/typescript-benchmark/) and its [published harness](https://github.com/powergr/typescript-native-compiler-benchmark). We reuse that methodological question, then run our own complete fixture. Its Windows results and multipliers are not predictions for this Linux example.

### 2) **Create one reproducible source graph**

Use a fresh scratch directory on Linux x86_64 with GNU `/usr/bin/time`, Python 3 and Node installed. The observed environment was Node 20.20.2, npm 10.8.2, Python 3.14.4 and an Intel Core i5-8400 with six available logical CPUs. Both compiler versions are pinned. Save this `package.json`:

```json
{
  "private": true,
  "type": "module",
  "devDependencies": {
    "typescript": "7.0.2",
    "ts6": "npm:typescript@6.0.3"
  }
}
```

Save `tsconfig.json`. Explicit roots and global types keep the [configuration migration](<../1. Configuration Migration/1.1. Configuration defaults and removed options.md>) separate from this comparison. The scripts choose separate output and build-information paths for each compiler.

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "lib": [
      "es2022"
    ],
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "rootDir": "src",
    "types": [],
    "declaration": true,
    "incremental": true
  },
  "include": [
    "src/**/*.ts"
  ]
}
```

Save `generate.py`:

```python
from pathlib import Path

src = Path("src")
src.mkdir(exist_ok=True)
imports, terms = [], []
for i in range(200):
    (src / f"m{i}.ts").write_text(f"export const value{i}: number = {i};\n")
    imports.append(f'import {{ value{i} }} from "./m{i}.js";')
    terms.append(f"value{i}")
(src / "index.ts").write_text("\n".join(imports) + "\nexport const total = " + " + ".join(terms) + ";\n")
```

The generator produces 200 small modules and one importing entry point: 201 source files. The unchanged sum is 19,900. Replacing `value0` with 1 changes the expected sum to 19,901, so the test can detect stale output after an edit. Standard-library files also belong to the compiler program; its reported file count is therefore larger than 201.

Install and generate the fixture:

```bash
npm install
python3 generate.py
node node_modules/ts6/lib/tsc.js --version
node_modules/@typescript/typescript-linux-x64/lib/tsc --version
```

The version commands printed 6.0.3 and 7.0.2. The native executable path is specific to this npm package and platform; inspect the installed platform package if your machine differs. This harness intentionally runs the native executable directly. On the tested Node 20 installation the npm launcher starts a child process; measuring only the launcher's resident memory would identify the wrong process. Ordinary project commands can still use the normal `tsc` launcher.

### 3) **Measure fresh unchanged and edited builds separately**

Save `measure.py`:

```python
from pathlib import Path
import json, statistics, subprocess, time, shutil

compilers = {"6": ["node", "node_modules/ts6/lib/tsc.js"],
             "7": ["node_modules/@typescript/typescript-linux-x64/lib/tsc"]}
Path(".cache").mkdir(exist_ok=True)
Path(".results").mkdir(exist_ok=True)
source = Path("src/m0.ts")
original = source.read_text()
rows = []
try:
    for trial in range(1, 4):
        for version in (["6", "7"] if trial % 2 else ["7", "6"]):
            source.write_text(original)
            shutil.rmtree(f"dist-{version}", ignore_errors=True)
            Path(f".cache/{version}.tsbuildinfo").unlink(missing_ok=True)
            for phase in ["clean", "unchanged", "edit"]:
                if phase == "edit":
                    source.write_text("export const value0: number = 1;\n")
                key = f"{version}-{trial}-{phase}"
                rss = Path(f".results/{key}.rss")
                command = ["/usr/bin/time", "-o", str(rss), "-f", "%M", *compilers[version],
                           "-p", "tsconfig.json", "--outDir", f"dist-{version}",
                           "--tsBuildInfoFile", f".cache/{version}.tsbuildinfo", "--extendedDiagnostics"]
                start = time.perf_counter()
                result = subprocess.run(command, capture_output=True, text=True, timeout=30)
                elapsed = time.perf_counter() - start
                Path(f".results/{key}.log").write_text(result.stdout + result.stderr)
                if result.returncode != 0:
                    raise RuntimeError(f"{key} failed: inspect its log")
                expected = 19901 if phase == "edit" else 19900
                smoke = subprocess.run(["node", "--input-type=module", "-e",
                    f'import {{ total }} from "./dist-{version}/index.js"; if (total !== {expected}) throw Error("wrong total");'],
                    capture_output=True, text=True, timeout=10)
                if smoke.returncode != 0:
                    raise RuntimeError(smoke.stderr)
                rows.append({"version": version, "trial": trial, "phase": phase,
                             "wall_seconds": elapsed, "peak_rss_kib": int(rss.read_text())})
                Path("measurements.json").write_text(json.dumps(rows, indent=2))
finally:
    source.write_text(original)
for version in compilers:
    for phase in ["clean", "unchanged", "edit"]:
        samples = [r for r in rows if r["version"] == version and r["phase"] == phase]
        print(version, phase, round(statistics.median(r["wall_seconds"] for r in samples), 3),
              round(statistics.median(r["peak_rss_kib"] for r in samples)))
```

Run it with `python3 measure.py`. Each trial deletes that compiler's output and project cache, then performs three consecutive invocations. The clean phase has neither artifact; the unchanged phase reuses the successful build state; the edit phase changes one source value. Compiler order alternates between trials to reduce a fixed first-run bias. The script restores the source even after failure.

The wall clock includes the GNU time command and compiler invocation. The consumer check runs afterward, outside that interval. GNU time records peak resident set size (RSS), in KiB, for the selected process; it is a memory high-water mark, not idle watch memory. The JSON retains all samples and each log retains diagnostics. A failing compiler or incorrect emitted sum stops the experiment instead of becoming a misleading fast result.

The executed experiment completed 18 successful compiler invocations and 18 successful emitted-consumer checks. These are medians of three samples per cell, recorded 2026-10-12:

| Compiler | Build state | Wall seconds | Peak RSS KiB |
|---|---|---:|---:|
| 6.0.3 | clean | 0.727 | 138172 |
| 6.0.3 | unchanged | 0.371 | 100092 |
| 6.0.3 | one-file edit | 0.394 | 102624 |
| 7.0.2 | clean | 0.061 | 43992 |
| 7.0.2 | unchanged | 0.033 | 30884 |
| 7.0.2 | one-file edit | 0.030 | 31952 |

Here “clean” means fresh project outputs and `.tsbuildinfo`; operating-system and filesystem caches were not flushed. Three samples on a small synthetic graph are an exploratory observation, not a production estimate. Process startup contributes to these short times. Repeat the method on the application's actual dependency graph and CI resources before making a rollout decision.

The two implementations' `extendedDiagnostics` counters and internal memory figures should not be treated as interchangeable measurements. In the first clean logs both reported 258 files, but 6.0.3 reported 1,178 instantiations and 7.0.2 reported 1,998. That difference alone does not establish more expensive semantic work. Use the same external wall/RSS instrument for the cross-version comparison; use diagnostics to investigate a fixed version and fixture. The [primary performance guide](https://github.com/microsoft/TypeScript/wiki/Performance) describes the broader diagnostic process.

### 4) **Check watch transitions with a finite test**

Watch keeps a process running and reacts to file changes. A successful startup cannot prove that later edits are detected. Save `watch.py` after running the measurement script, which creates `.cache` and `.results`:

```python
from pathlib import Path
import json, os, queue, signal, subprocess, threading, time

compilers = {"6": ["node", "node_modules/ts6/lib/tsc.js"],
             "7": ["node_modules/@typescript/typescript-linux-x64/lib/tsc"]}
source = Path("src/m0.ts")
original = source.read_text()
records = []
for version, compiler in compilers.items():
    lines = queue.Queue()
    process = subprocess.Popen([*compiler, "-p", "tsconfig.json", "--watch", "--noEmit",
                                "--preserveWatchOutput", "--tsBuildInfoFile", f".cache/watch-{version}.tsbuildinfo"],
                               stdout=subprocess.PIPE, stderr=subprocess.STDOUT, text=True,
                               start_new_session=True)
    def read_output(stream=process.stdout, target=lines):
        for line in stream:
            target.put(line)
    threading.Thread(target=read_output, daemon=True).start()
    transcript = []
    def wait_for(phrase):
        deadline = time.monotonic() + 30
        while time.monotonic() < deadline:
            try:
                line = lines.get(timeout=min(1, max(0.01, deadline - time.monotonic())))
            except queue.Empty:
                continue
            transcript.append(line)
            if phrase in line:
                return
        raise RuntimeError(f"watch {version} never reported {phrase}")
    try:
        wait_for("Found 0 errors")
        source.write_text('export const value0: number = "bad";\n')
        wait_for("TS2322")
        wait_for("Found 1 error")
        source.write_text(original)
        wait_for("Found 0 errors")
        records.append({"version": version, "observed": "0 -> TS2322 / 1 -> 0"})
        print(version, records[-1]["observed"], flush=True)
    finally:
        source.write_text(original)
        os.killpg(process.pid, signal.SIGTERM)
        try:
            process.wait(timeout=5)
        except subprocess.TimeoutExpired:
            os.killpg(process.pid, signal.SIGKILL)
            process.wait()
        Path(f".results/watch-{version}.log").write_text("".join(transcript))
Path("watch-results.json").write_text(json.dumps(records, indent=2))
```

Run `python3 watch.py`. Each compiler first reports zero errors. The harness writes a string into a number declaration and waits for TS2322 plus a one-error summary. It then restores the number and waits for zero errors again. The observed output was:

```text
6 0 -> TS2322 / 1 -> 0
7 0 -> TS2322 / 1 -> 0
```

The timeout converts a missed event into a failure. The `finally` block restores the source, terminates only the process group created for this test and waits for it to exit. This Linux harness tests diagnostics with `--noEmit`; it does not prove watch emission or hot reload. Watch latency, idle CPU use, long-session memory and behavior on network filesystems were not measured. Test those separately when they matter to your deployment environment.

### 5) **Review an upgrade claim**

Exercise: a teammate compares a 6.0 clean build with a 7.0 unchanged build and reports the ratio as “our upgrade speedup.” They also omit the emitted-consumer test because both commands exit zero. Explain the missing evidence.

An adequate answer compares matching states across versions, records source/configuration/tool versions and preserves the individual samples. It verifies fresh outputs and the changed sum, because correct checking does not by itself prove that the expected artifact was emitted and consumed. For an application, add its real tests and packaging entry points. A fast synthetic build does not justify skipping those gates.

### 6) **Common confusion**

An incremental invocation starts a new process while reusing disk build information. Watch reuses a running process as it observes edits. Neither is the same as an unchanged fresh compilation, and one timing cannot describe all three workflows. Likewise, the compiler's internal “Memory used” field is not the external process peak RSS recorded here; mixing them would change the quantity being compared.

### 7) **Performance note**

Native compilation reduced elapsed time and peak RSS in this measured fixture. The table establishes only these versions, commands and graph on this machine. Larger graphs, constrained CI CPUs, declaration-heavy dependencies and different edit patterns can change both time and memory. Experimental parallelism controls deserve a separate controlled comparison; this lesson did not execute tuning experiments. Keep compiler correctness and consumer checks beside the timing so a skipped or broken build cannot win the benchmark.

### 8) **Mentor note**

Ask the learner to explain why the edited consumer must produce 19,901 and why an unchanged result of 19,900 is useful in a different phase. A sound answer connects the source edit, emitted dependency and entry-point sum rather than quoting the timing table. Then ask which process was measured and whether the cache state was comparable. These questions expose stale-artifact and launcher-memory mistakes before a persuasive headline reaches a review.
