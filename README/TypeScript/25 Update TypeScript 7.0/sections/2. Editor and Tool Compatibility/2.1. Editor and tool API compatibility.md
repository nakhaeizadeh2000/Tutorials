## 2.1. Editor and tool API compatibility

A project can pass native TypeScript 7 checking while a linter still needs the TypeScript 6 compiler API. The two tools communicate with TypeScript differently. Understanding that boundary lets you migrate checking deliberately while retaining a working toolchain. This lesson uses a complete typed ESLint fixture rather than a placeholder that merely prints “compatible”.

### 1) **Identify which interface each tool uses**

A command-line compiler receives files/options and returns diagnostics or artifacts. An editor sends interactive requests to a language service. A tool using the JavaScript compiler API imports functions and objects into its own process. Availability through one interface does not establish compatibility through another.

The [7.0 release guidance](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) describes the native Language Server Protocol (LSP) editor service and a TypeScript 6 compatibility package for API consumers. Its side-by-side installation keeps the package name `typescript` available to tools expecting the older API, while the native compiler supplies `tsc`.

Our installed 7.0.2 package root exposes version information but has no old `createProgram` function. Its package also lists experimental `unstable/*` exports; their presence does not make them compatible replacements for a tool written against the older API. This fixture uses the supported compatibility route and does not exercise those experimental interfaces.

### 2) **Run native checking and typed ESLint together**

Use a new scratch directory with Node 20.20.2 and npm 10.8.2. Save `package.json`:

```json
{
  "private": true,
  "type": "module",
  "scripts": {
    "check": "tsc -p tsconfig.json --noEmit",
    "check:compat": "tsc6 -p tsconfig.json --noEmit",
    "lint": "eslint src"
  },
  "devDependencies": {
    "@typescript/native": "npm:typescript@7.0.2",
    "typescript": "npm:@typescript/typescript6@6.0.2",
    "eslint": "10.12.0",
    "typescript-eslint": "8.71.1"
  },
  "overrides": {
    "@typescript/old": "npm:typescript@6.0.3"
  }
}
```

The `typescript` alias names the compatibility wrapper, version 6.0.2. That wrapper depends on the older compiler; the override fixes its actual compiler/API implementation at 6.0.3. Those are distinct versions. The native alias supplies 7.0.2 and the executable `tsc`, while the compatibility wrapper supplies `tsc6`. Keep the generated lockfile for reproducible subsequent installs.

```bash
npm install
npm exec -- tsc --version
npm exec -- tsc6 --version
node --input-type=module -e 'import ts from "typescript"; console.log(ts.version, typeof ts.createProgram);'
mkdir -p src
```

Expected outputs are `Version 7.0.2`, `Version 6.0.3` and `6.0.3 function`. Always inspect actual executable/API versions; a dependency label alone cannot establish which checker a command used.

Save `tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "rootDir": "src",
    "types": []
  },
  "include": [
    "src/**/*.ts"
  ]
}
```

Save `src/index.ts`:

```typescript
export function pendingJob(): Promise<number> {
  return Promise.resolve(42);
}

export async function run(): Promise<number> {
  return await pendingJob();
}
```

Save `eslint.config.mjs`:

```javascript
import tseslint from "typescript-eslint";

export default [{
  files: ["src/**/*.ts"],
  languageOptions: {
    parser: tseslint.parser,
    parserOptions: {
      projectService: true,
      tsconfigRootDir: import.meta.dirname,
    },
  },
  plugins: { "@typescript-eslint": tseslint.plugin },
  rules: { "@typescript-eslint/no-floating-promises": "error" },
}];
```

This narrowly configured rule asks the compatibility project service for type information so it can recognize promise-returning calls. It does not enable an entire recommended lint policy; ordinary rule selection belongs in [the tooling owner](<../../../16 Tooling Language Server and Ecosystem/README.md>). The maintainer's [typed-linting guide](https://typescript-eslint.io/getting-started/typed-linting/) explains the project service. At verification time, its [dependency support page](https://typescript-eslint.io/users/dependency-versions/) covers TypeScript `>=4.8.4 <6.1.0`, which includes the selected 6.0.3 API.

```bash
npm run check
npm run check:compat
npm run lint
npm exec -- tsc -p tsconfig.json --outDir dist
node --input-type=module -e 'import { run } from "./dist/index.js"; console.log(await run());'
```

Both checking commands and typed ESLint exit 0. The native emitting build exits 0; its actual Node consumer prints `42`. This proves the declared fixture's commands work together. It does not establish compatibility for a different linter, custom transformer or framework.

### 3) **Diagnose different kinds of failure**

Append `pendingJob();` to the source as an intentional mistake. Both compilers still exit 0. Typed ESLint exits 1 and reports `@typescript-eslint/no-floating-promises`. The compiler accepts a valid expression statement; the lint rule enforces handling or explicitly acknowledging the returned promise. Do not disable the rule merely to declare the upgrade green. Remove the appended call and rerun all three checks; each returns to exit 0.

A different failure occurs when a tool assumes the native package has the old API:

```bash
node --input-type=module -e 'import ts from "@typescript/native"; console.log(typeof ts.createProgram);'
node --input-type=module -e 'import ts from "@typescript/native"; ts.createProgram([], {});'
```

The first prints `undefined` and exits 0; the second intentionally throws `TypeError: ts.createProgram is not a function` and exits 1. Successful import proves only that a package entry point loaded. Inspecting and using the required interface tests the actual compatibility question.

Exercise: a teammate removes the compatibility alias because native checking already passes. Explain which dependency and command you would inspect before accepting the change. The solution is to identify the tool's API import and supported versions, then rerun its actual typed command. Retain the alias until that tool offers and verifies a supported native route. A peer-dependency installation result alone is insufficient.

### 4) **Configure the editor as its own migration step**

LSP is the request/response protocol between an editor and a language server. Selecting a CLI executable does not automatically tell every editor which server to start. Use your editor's current TypeScript 7 integration instructions and test navigation, diagnostics and refactoring on the real project.

For VS Code, the [TypeScript 7 extension instructions](https://marketplace.visualstudio.com/items?itemName=TypeScriptTeam.native-preview) provide the command `TypeScript: Enable TypeScript 7` and the setting below. With this fixture's alias layout, the optional local-package path points to the native package:

```jsonc
{
  "js/ts.experimental.useTsgo": true,
  "js/ts.tsdk.path": "./node_modules/@typescript/native"
}
```

These are documented editor settings, not an executed editor demonstration. Open the source, hover `run`, navigate to `pendingJob`, and temporarily change its result to a string while retaining its `Promise<number>` annotation. Confirm that the chosen service reports the incompatibility and that restoring the source clears it. Record the editor/extension/server versions and the features actually tested. CLI and typed-lint results above were executed; no VS Code UI session is claimed here.

Embedded-language integrations may use their own compiler APIs or language-service plugins. Check that integration's maintained support guidance before switching its server. A `.ts` smoke test cannot prove template checking works. Keep a reversible editor setting and preserve the working API dependency when the required integration still needs it.

### 5) **Common confusion**

`tsc`, `tsc6` and `import "typescript"` are three lookups, not three spellings for one selected compiler. In this setup the first is native 7, while the latter two use the 6 compatibility implementation. Their versions differ deliberately.

A tool can need type information without using the editor's language server. Typed ESLint's project service operates in its own tool process. Editor selection, batch checking and API-dependent analysis therefore deserve separate observed results.

### 6) **Performance note**

Native checking does not automatically accelerate typed linting that still uses the older API. The typed rule needs a type-aware project, which adds analysis work beyond parsing one source file. This lesson verifies behavior, not timings or memory use. Measure each command on representative inputs before changing budgets or claiming that a compiler upgrade sped up the entire pipeline.

### 7) **Mentor note**

Ask the learner to draw the three connections: CLI to native compiler, typed ESLint to compatibility API, editor to selected service. Then introduce the unhandled call and predict which checks fail. A useful answer names the interface and the rule's purpose, not just the latest package version. For a migration review, require the actual command, reported version and observed result beside each tool.
