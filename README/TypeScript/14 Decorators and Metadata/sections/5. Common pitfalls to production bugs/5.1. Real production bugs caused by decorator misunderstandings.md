## 5.1. Real production bugs caused by decorator misunderstandings

The following are **local reproductions of failure mechanisms**, not claims about particular production incidents or measured failure rates. Each case identifies a trigger, observes the result, and applies a bounded repair. The baseline is **TypeScript 7.0.2** and emitted modules on **Node.js 20.20.2**.

Use a new directory without a `tsconfig.json`. Save the five named files below. The metadata case additionally needs `npm init -y` and `npm install --save-exact reflect-metadata@0.2.2`. Its legacy configuration is separate from the standard-form files.

### 1) **The imported decorator has the wrong call contract**

A decorator import supplies a function; it does not independently select the compiler's decorator model. A legacy descriptor decorator used under the standard-form model is rejected for its incompatible call contract. Changing the file path or stacking another decorator does not make the two signatures coexist automatically.

```typescript
// file: wrong-model.mts
function legacy(
  _target: object, _key: string | symbol, descriptor: PropertyDescriptor,
): void {
  descriptor.enumerable = false;
}
class Wrong { @legacy run(): string { return "ok"; } }
```

Check with `tsc --strict --target es2022 --module nodenext --noEmit wrong-model.mts`. It exits 1 with TS1241: the standard method decorator call supplies two arguments, while this function expects the legacy three-argument contract. Enabling `--experimentalDecorators` makes this particular legacy signature check successfully. Neither observation proves a framework migration.

For a standard-form call-counting concern, implement and check that actual contract:

```typescript
// file: standard.mts
let calls = 0;
function counted<This, Args extends unknown[], Result>(
  value: (this: This, ...args: Args) => Result,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Result>,
): (this: This, ...args: Args) => Result {
  void context;
  return function (this: This, ...args: Args): Result {
    calls++;
    return value.apply(this, args);
  };
}
class Service { @counted run(): string { return "ok"; } }
console.log(new Service().run(), calls); // ok 1
```

Compile `standard.mts`, `fields.mts` and `receivers.mts` with `tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --outDir dist standard.mts fields.mts receivers.mts`. Run each emitted `.mjs` with Node. The count proves the behavior of this wrapper, not the origin of its import or a hypothetical cache hit rate. The [configured comparison](<../2. Legacy and Metadata/2.1. Legacy experimental decorators compared.md>) owns migration and independently built artifact boundaries.

### 2) **A broad metadata constructor is trusted as a dependency contract**

A declaration's emitted design metadata can be too broad to identify a provider. In this legacy fixture, the union parameter records `Object`. The deliberately unsafe assertion below turns that metadata into a supposedly useful repository constructor. It makes compilation green while bypassing the repository contract.

```typescript
// file: dependency.mts
import "reflect-metadata";
function marked(_value: Function): void {}
class SqlRepo { find(): string { return "sql"; } }
class MemoryRepo { find(): string { return "memory"; } }
@marked
class Service {
  constructor(readonly repo: SqlRepo | MemoryRepo) {}
  run(): string { return this.repo.find(); }
}
const metadata: unknown = Reflect.getOwnMetadata("design:paramtypes", Service);
if (!Array.isArray(metadata) || metadata.length !== 1 || metadata[0] !== Object) {
  throw new Error("unexpected fixture metadata");
}
console.log(metadata[0] === Object); // true
// Deliberately wrong: this assertion claims that metadata proves the provider's shape.
const AssumedRepo = metadata[0] as new () => SqlRepo | MemoryRepo;
try { new Service(new AssumedRepo()).run(); }
catch (error) { console.log(error instanceof TypeError); } // true: Object has no find method
const createService = (): Service => new Service(new MemoryRepo());
console.log(createService().run()); // memory
// new Service({}); // TS2345: missing find, without the unsafe assertion
```

Compile with `tsc --strict --experimentalDecorators --emitDecoratorMetadata --target es2022 --module nodenext --outDir legacy-dist dependency.mts`, then run `node legacy-dist/dependency.mjs`. The script exits 0 because the intentional TypeError is caught. The explicit construction recipe supplies the actual required behavior. A supported typed token/factory binding can serve the same purpose; a caller-selected `get<T>()` or a string token alone would not establish it.

This failure comes from trusting a lossy representation and using an assertion to bridge the gap. It is not a claim that every union becomes `Object`, that every metadata consumer blindly constructs it, or that structural substitutes must pass `instanceof`. [Design metadata](<../2. Legacy and Metadata/2.2. emitDecoratorMetadata and design types.md>) owns the actual serialization cases, and [dependency injection](<../3. Patterns in Practice/3.3. Dependency injection with decorators.md>) owns typed bindings and lifetime.

### 3) **A field hook writes the wrong property or runs before later fields**

A field extra initializer runs after its own field initializes. It can still run before a later field. A property-name mismatch can also make a successful write invisible to the reader. Both problems require observing the actual storage and initialization sequence.

```typescript
// file: fields.mts
function wrongProperty<This extends { seen: string[]; log?: string[] }>(
  _value: undefined, context: ClassFieldDecoratorContext<This, number>,
): void {
  context.addInitializer(function (this: This) {
    (this.log ??= []).push(String(context.name));
  });
}
class WrongProperty {
  seen: string[] = [];
  log?: string[];
  @wrongProperty score = 1;
}
const wrong = new WrongProperty();
console.log(wrong.seen.length, wrong.log?.join(",")); // 0 score: the reader uses a different property
function record<This extends { seen?: string[] }>(
  _value: undefined, context: ClassFieldDecoratorContext<This, number>,
): void {
  context.addInitializer(function (this: This) {
    (this.seen ??= []).push(String(context.name));
  });
}
class TooLate {
  @record score = 1;
  seen: string[] = []; // This later initializer overwrites the hook-created array.
}
console.log(new TooLate().seen.length); // 0
class Fixed {
  seen: string[] = [];
  @record score = 1;
  @record level = 2;
}
const fixed = new Fixed();
console.log(fixed.seen.join(","), fixed.score, fixed.level); // score,level 1 2
```

The first hook does execute, but writes `log` while the consumer reads `seen`. The second creates `seen` early and then loses it to a later declared initializer. The repaired class initializes the intended collection before the decorated fields and uses the same property in the writer and reader.

These hooks record construction events; they are not a complete validator. [Field ordering](<../1. Standard Decorators/1.2. Decorator evaluation and application order.md>) owns the wider trace, while [validation](<../3. Patterns in Practice/3.1. Validation decorators field rules.md>) records rules and checks actual current values with an explicit missing-schema policy. Validation verdict caching needs an immutability/version/freshness contract; calling every possible cache incorrect would conceal the real issue of reusing a verdict after its inputs change.

### 4) **A forwarding wrapper does not bind a detached method**

A normal wrapper forwards the `this` supplied by its call. Extracting an instance method and calling it without a receiver does not automatically retain the original instance. The same failure can occur without a decorator.

```typescript
// file: receivers.mts
function forward<This, Args extends unknown[], Result>(
  value: (this: This, ...args: Args) => Result,
): (this: This, ...args: Args) => Result {
  return function (this: This, ...args: Args): Result { return value.apply(this, args); };
}
class Wrapped {
  prefix = "wrapped:";
  @forward run(): string { return this.prefix + "ok"; }
}
const wrapped = new Wrapped();
const detached = wrapped.run;
try { detached(); }
catch (error) { console.log(error instanceof TypeError); } // true
console.log(wrapped.run.bind(wrapped)()); // wrapped:ok
function bound<This extends object, Args extends unknown[], Result>(
  value: (this: This, ...args: Args) => Result,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Result>,
): void {
  if (context.private || context.static) throw new Error("public instance method required");
  context.addInitializer(function (this: This) {
    Object.defineProperty(this, context.name, {
      configurable: true, writable: true, value: value.bind(this)
    });
  });
}
class Auto {
  prefix: string;
  constructor(prefix: string) { this.prefix = prefix; }
  @bound run(): string { return this.prefix + "ok"; }
}
const one = new Auto("one:");
const two = new Auto("two:");
const callback = one.run;
console.log(callback(), two.run()); // one:ok two:ok
console.log(Object.hasOwn(one, "run"), one.run === two.run); // true false
```

Unlike a passthrough named `bound`, this decorator installs an own bound function for each instance using a method extra initializer. The method is bound before fields initialize, but does not read `prefix` until the later call. Its allocation is per instance, not per property access. The [TypeScript 5.0 example](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#decorators) uses this initializer mechanism for binding as well.

This bounded implementation supports public instance methods and the single-decorator use shown. Other stacked policies must establish which replacement gets bound. The source declaration's static type also does not automatically lose an explicitly declared `this` parameter. Choose explicit binding, an arrow field, a callback closure or a supported binding decorator from the actual callback and class contracts; [the receiver owner](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.1. this parameter explicit typing and arrow vs function capture.md>) explains those contracts.

### 5) **Common confusion**

An import path does not choose decorator semantics independently of program options. Compatible class shapes can work in both models, while an incompatible descriptor method signature is rejected. Likewise, a green build produced through a constructor assertion does not prove that a metadata-selected object implements the required behavior.

A field hook is not an after-all-fields callback. A function named `bound` is not evidence of binding, and a forwarding wrapper preserves the receiver it is given rather than inventing one. Inspect the actual write, initialization point and call site before choosing a repair.

### 6) **Performance note**

These reproductions measure outcomes and identities, not performance. Definition-time metadata, wrapper invocation, field hooks and bound-function allocation are different work. The binding decorator creates one function per instance; the forwarding decorator creates its wrapper during decoration. No incident rate, cache hit-rate percentage, dispatch bound, timer overhead or universal cost relative to application I/O was measured. Verify correctness first, then measure the relevant startup or callback workload if required.

### 7) **Mentor note**

Have the learner predict each failure before running it, then identify the smallest responsible boundary: configured signature, metadata trust, field storage/order or receiver invocation. Ask what changes if the field collection moves below the decorated field, or if a correct binding helper is replaced by a passthrough. A sound repair explains the observed mechanism and its limits rather than prescribing a global decorator ban, a migration certificate or an invented production metric.
