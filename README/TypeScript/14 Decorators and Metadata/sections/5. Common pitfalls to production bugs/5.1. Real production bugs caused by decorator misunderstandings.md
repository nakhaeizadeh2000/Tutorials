## 5.1. Real production bugs caused by decorator misunderstandings

### 1) **Legacy/standard mix double-wrapped methods** (migrated file kept one legacy import)

**Definition** — a half-migrated service file kept one legacy `@timed` import (legacy positions) beside standard `@logged` (value+context): the method wrapped twice under different semantics (legacy descriptor-surgery outer, standard replacement inner) — timing logged entry/exit while logging measured inner-only durations, and the memo layer (keyed on standard-wrapped identity) cached per wrapper-instance instead of per method (hit rate ~0%, invisible without metrics).

**What problem it solves / history** — per-file migration done *mostly* (all decorators converted except one import nobody noticed — same name `timed` from a legacy utils path) compiled cleanly (both forms check independently) while composing incorrectly (mixed semantics per layer — order, `this` handling, and return contracts differing per form). One-form-per-file (see 2.1 promise 2) plus import-path auditing (legacy utils vs standard utils) prevents the class structurally.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), migrate per file completely (all decorators one form — grep legacy import paths per migrated file before merging); audit decorator import *sources* in review (legacy-utils vs standard-utils paths — same name, different semantics); monitor wrapper metrics post-migration (hit rates, timing distributions — behavioral divergence surfaces in metrics before incidents).

**Runnable example** — one form per file (good vs bad, `tsc --strict`):

```typescript
// good — standard stack (one form, composable semantics, measurable behavior)
function timedA<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); };
}
function loggedA<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); };
}
class Svc7 {
  @timedA
  @loggedA
  calc(n: number): number { return n * 2; } // one form (standard pair — order per 1.2, semantics uniform)
}
console.log(new Svc7().calc(21).toFixed(0)); // 42 — uniform stack (metrics coherent: timing wraps logging identically)
// bad — @timedLegacy (legacy import path) beside @loggedA (standard): compiled clean, composed double-wrapped with mismatched semantics
// fix — per-file migration (all decorators one form — import paths audited per migrated file before merge)
```

```typescript
// good — import-path audit (legacy vs standard utils distinguished by path, enforced by review)
function auditedB<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); };
}
class Svc8b {
  @auditedB
  run(): string { return "ok"; } // standard-utils path (audited: same-name legacy import absent — verified by grep)
}
console.log(new Svc8b().run()); // ok — single-form file (import audit passing: no legacy paths present)
// bad — import { timed } from "./legacy-utils" beside standard imports (same name, legacy semantics — audit missed it for months)
// fix — grep legacy-utils paths per migrated file (mechanical audit — import source is the form's fingerprint)
```

```typescript
// good — metrics proving composition (hit rates + timing distributions per stack — behavioral verification)
let wrapped = 0; // composition counter (test seam: wrappers increment — counts prove layering)
function countedB<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret {
    wrapped += 1; // counted per layer (two stacked counted-wrappers increment twice — composition verified)
    return fn.apply(this, args);
  };
}
class Svc9 {
  @countedB
  @countedB
  go(): string { return "g"; } // stacked pair (same form — counts compose predictably: 2 per call)
}
console.log(new Svc9().go(), wrapped.toFixed(0)); // g 2 — composition counted (metrics prove layering — mixed forms would diverge here)
// bad — unmonitored stacks (behavioral divergence invisible until incidents — metrics are the migration's proof layer)
// fix — composition counters + hit-rate dashboards per stack (behavioral verification beyond green tests)
```

**Common confusion** — "same name means same semantics" — `timed` from legacy-utils vs standard-utils differs (descriptor surgery vs value+context replacement — order, `this`, and return contracts all differ per form). "green tests prove migration" — tests prove *outcomes* (same results both forms often); metrics prove *composition* (wrapping counts, hit rates, timing distributions diverge invisibly to outcome tests). "one missed import is harmless" — one missed import *reintroduces* the legacy form (flag, emit, and semantics follow the import — per-file purity is all-or-nothing).

**Performance note** — double-wrapping costs one extra closure per call (trivial); memo-keyed-on-wrapper-identity costs ~0% hit rates (unbounded recomputation — the incident's actual bill); composition counters cost one increment per call in tests only (production-gated or sampled).

**Mentor note** — grep legacy decorator import paths across migrated files (missed imports = mixed-form files — audit mechanical, findings immediate). Exercise: complete one half-migration (convert the missed import, re-verify metrics) — migration *completion* as a distinct task from migration *start*. Review gate: legacy import paths in migrated files fail review; unmonitored decorator stacks fail review.

### 2) **`emitDecoratorMetadata` `Object` fallback injected the wrong service** (union param recorded as garbage)

**Definition** — a constructor param typed `Repo | MockRepo` (union for test flexibility) recorded `design:paramtypes: [Object]` (erased unions collapse — see 2.2 promise 3); the container resolved `Object` as a garbage dependency (empty object instance — boot succeeded, every repository call failed with `repo.find is not a function` in production, green types throughout).

**What problem it solves / history** — metadata-trusting containers resolve *whatever* the emit recorded (`Object` for unions/interfaces/primitives — structurally valid metadata, semantically garbage). Explicit tokens (`@Inject(REPO_TOKEN)` — precision where emit degrades) bypass the degradation entirely: the container never reads design-types for tokenized params (tokens *are* the wiring — emit-independent, degradation-proof).

**Modern guidance** — as of TypeScript 5.9 era, tokenize every non-class DI param (unions, interfaces, primitives, literals — `@Inject(TOKEN)` explicit); reserve bare metadata reliance for concrete-class params (exact constructor recorded — the one shape emit preserves faithfully); validate resolved instances at container boundaries (`instanceof` checks on resolution — never blind trust of emitted facts).

**Runnable example** — tokens where emit degrades (good vs bad, `tsc --strict`):

```typescript
// good — tokenized union param (precision explicit — no emit to degrade)
const REPO_TOKEN = "repo"; // token constant (typo-proof wiring key)
interface RepoI { find(): string }
class SqlRepo implements RepoI {
  find(): string { return "sql"; }
}
class MemRepo implements RepoI {
  find(): string { return "mem"; }
}
const bindings = new Map<string, new () => RepoI>([[REPO_TOKEN, SqlRepo]]);
function resolve<T>(token: string): T {
  const C = bindings.get(token);
  if (!C) throw new Error(`unbound:${token}`);
  return new C() as T; // token-resolved (explicit map — precision where design:paramtypes records Object)
}
console.log(resolve<RepoI>(REPO_TOKEN).find()); // sql — token wiring (unions/interfaces served precisely)
// bad — bare-injected union param under metadata emit (design:paramtypes [Object] — container resolves garbage at boot)
// fix — @Inject(REPO_TOKEN) explicit tokens (precision where emit degrades — portable, testable via rebind)
```

```typescript
// good — container validates resolved instances (never blind-trusts emitted facts)
class RealRepo {
  find(): string { return "real"; }
}
function resolveChecked<T>(token: string, guard: (x: unknown) => x is T, make: () => T): T {
  void token; // token selects (explicit wiring — emit-independent)
  const inst: unknown = make(); // constructed (factory-provided — no metadata read at all)
  if (!guard(inst)) throw new Error("resolution mismatch"); // validated (resolved instances checked — trust verified)
  return inst;
}
const rr = resolveChecked("r", (x): x is RealRepo => x instanceof RealRepo, () => new RealRepo());
console.log(rr.find()); // real — validated resolution (metadata treated as hint, instances as truth)
// bad — container returning design:paramtypes resolutions unchecked (garbage Object instances flowing into typed positions)
// fix — instanceof guards at resolution boundaries (emitted facts verified — trust, but verify, per boundary)
```

```typescript
// good — interface params always tokenized (interfaces erase completely — no emit could ever record them)
const IFACE_TOKEN = "iface";
interface Store { load(): string }
class DiskStore implements Store {
  load(): string { return "disk"; }
}
const b2 = new Map<string, new () => Store>([[IFACE_TOKEN, DiskStore]]);
console.log(b2.get(IFACE_TOKEN)!.name, new (b2.get(IFACE_TOKEN)!)().load()); // DiskStore disk — interface served via token (only honest path)
// bad — constructor (store: Store) bare-injected (design:paramtypes [Object] — interface erased, garbage resolved, boot "succeeds")
// fix — tokens for ALL non-class params (unions, interfaces, primitives, literals — the token rule without exceptions)
```

**Common confusion** — "metadata works for most params" — works for *concrete-class* params (exact constructors recorded); degrades for *everything else* (unions/interfaces/primitives/literals → `Object`/base — the common DI shapes!). "validating resolutions is paranoid" — garbage-`Object` injection boots successfully (no crash at wiring — failures surface per-method-call later, far from cause). "tokens are boilerplate" — tokens are *wiring documentation* (greppable, rename-safe, typo-proof) — boilerplate that reads vs magic that mis-resolves.

**Performance note** — token maps resolve O(1) per binding (same as metadata maps); validation guards cost one `instanceof` per resolution (startup-shaped — resolve once, inject everywhere); garbage-`Object` incidents cost boot-misbehavior debugging (unbounded — validation is free insurance).

**Mentor note** — log `design:paramtypes` for a union param live (`[Object]` — degradation demonstrated, not described) — tokens-from-here-on-out in one log line. Exercise: tokenize three bare-injected non-class params and delete the metadata reliance (precision restored per conversion). Rule: non-class DI params carry `@Inject(TOKEN)` or fail review.

### 3) **Field decorator ordering ran validation before initialization** (definition vs instance confusion)

**Definition** — a `@Validate` field decorator executing rule *checks* in the decorator body (definition time — no instance exists) instead of *registering* rules for per-instance runs: every decorated class threw at import (`cannot read property of undefined` — validating phantom values) or, worse, validated once against `undefined` and cached the verdict (all instances "valid" regardless of values — checking theater with decorator syntax).

**What problem it solves / history** — definition/instance phase confusion (see 1.2 promise 3) is the most common field-decorator bug class *and* the hardest to spot (decorator bodies run at import — failures look like module-load issues, not validation bugs; cached verdicts pass tests with default-valued fixtures while failing on real data). The two-phase pattern (register at definition via schema/metadata; check per instance via `validate()`) assigns each job its phase structurally.

**Modern guidance** — as of TypeScript 5.9 era, decorator bodies *register* (schemas, metadata, rule tables — definition-time, instance-free); `validate()` *checks* (reads instances against schemas — instance-time, value-full); never branch decorator bodies on values (nothing exists to branch on — the `undefined` read is always a bug, never data). See 3.1's full two-phase pattern; this promise is its incident ledger.

**Runnable example** — phases separated correctly (good vs bad, `tsc --strict`):

```typescript
// good — register at definition (schema), check per instance (validate) — phases separated per 1.2 promise 3
type R10 = { min?: number };
const SCH10 = new Map<string, R10>();
function min10(n: number) {
  return function (value: undefined, context: ClassFieldDecoratorContext<object, number>): void {
    void value;
    SCH10.set(String(context.name), { min: n }); // REGISTER (definition — schema entry, no values read)
  };
}
class Form10 {
  @min10(0) age = 5;
}
function check10(inst: Form10): string[] {
  const out: string[] = [];
  for (const [k, r] of SCH10) {
    const v = (inst as unknown as Record<string, number>)[k] ?? 0;
    if (r.min !== undefined && v < r.min) out.push(`${k}<min`); // CHECK (instance — values exist here)
  }
  return out;
}
console.log(check10(new Form10()).length); // 0 — valid instance, empty errors (phases correct: register-then-check)
// bad — checking in the decorator body (definition-time: values undefined — throws at import or caches vacuous verdicts)
// fix — two-phase pattern (3.1 full treatment: bodies register, validate() checks — never the reverse)
```

```typescript
// good — addInitializer for per-instance setup needing construction timing (hooks, not bodies)
function observed10(value: undefined, context: ClassFieldDecoratorContext<object, number>): void {
  void value;
  context.addInitializer(function (this: { log?: string[] }) {
    (this.log ??= []).push(String(context.name)); // HOOK (instance time — this exists, fields set)
  });
}
class Rec10 {
  seen: string[] = [];
  @observed10 score = 1;
}
const r10 = new Rec10();
console.log(r10.seen?.join(","), r10.score.toFixed(0)); // score,level 1 — hooks observed construction in field order
```

```typescript
// good — cached verdicts banned (validate per instance, every time — no memoization of correctness)
function min10b(n: number) { // re-declared minimally: fences compile standalone
  return function (value: undefined, context: ClassFieldDecoratorContext<object, number>): void {
    void value; void context; void n;
  };
}
class Form10 { // re-declared minimally: fences compile standalone
  @min10b(0) age = 5;
}
function check10(inst: Form10): string[] {
  return inst.age < 0 ? ["age<min"] : [];
}
function freshCheck(inst: Form10): string[] { return check10(inst); } // fresh run per call (values current — never cached)
const f10 = new Form10();
f10.age = -3;
console.log(freshCheck(f10).join(",")); // age<min — current values checked (cached verdicts would still say valid)
// bad — validate-once-cache-forever (first instance's verdict reused — subsequent violations invisible, tests green on defaults)
// fix — check per instance per call (validation is O(rules) — caching correctness saves microseconds, risks incidents)
```

**Common confusion** — "definition-time checks work for defaults" — defaults aren't instances (checking `5` at definition proves nothing about runtime values — the one case that "works" teaches the wrong lesson for all others). "hooks replace validate()" — hooks *observe* construction (logging, setup); `validate()` *judges* values (rules against instances) — observation vs judgment differ. "caching validations is an optimization" — caching *correctness verdicts* (vs memoizing pure *computations* per 3.2) — verdicts depend on mutable values (stale by design); computations depend on arguments (stable by contract).

**Performance note** — registration once per class (negligible); validation O(rules) per instance per call (trivial vs I/O); hooks once per instance-field (initializer chain — trivial). Uncached correctness costs microseconds; cached-correctness incidents cost post-mortems.

**Mentor note** — log inside a decorator body vs inside a hook vs inside `validate()` (import-once vs per-instance vs per-check — three phases in three log lines). Exercise: classify three field-decorator bugs by phase (body-reading-instance? shared-hook-state? cached-verdict?) — phase vocabulary debugging directly. Review gate: value reads in decorator bodies fail review; correctness caching fails review.

### 4) **Unbound method passed as callback lost `this` through decoration** (wrapped detachment)

**Definition** — a decorated method extracted as a callback (`onClick(svc.handler)` — decorated `handler` detached from `svc`) lost `this` at call time (`undefined` receiver — `this.state` throwing inside the wrapper): decoration preserved the *signature* but not the *binding* (wrappers forward `this` they receive — detached calls receive `undefined`, correctly forwarded into the crash).

**What problem it solves / history** — method decorators compose with *extraction* badly (every `@timed`/`@logged` method is a future detached callback — event handlers, timers, promise chains all detach). Fixes live at three levels (bind at extraction `svc.handler.bind(svc)`, arrow-field methods `handler = () => …` (bound per instance), decorator-provided auto-binding (returning bound functions — allocation per access)): unexamined, teams blamed the decorator (removing observability instead of fixing binding).

**Modern guidance** — as of TypeScript 5.9 era, bind at extraction (`.bind(svc)` at the callback site — explicit, local, greppable); or arrow-field methods for handler-heavy classes (bound per instance — allocation per instance, zero per-use thought); or auto-binding decorators where the pattern repeats (returning `this`-bound replacements — documented allocation, centralized). Never undecorate to fix binding (observability sacrificed for a binding bug — wrong layer sacrificed).

**Runnable example** — binding fixed at three levels (good vs bad, `tsc --strict`):

```typescript
// good — bind at extraction (explicit, local, greppable — the default fix)
class Btn {
  constructor(public id = "b") {}
  click(): string { return `clicked:${this.id}`; }
}
const btn = new Btn();
const bound = btn.click.bind(btn); // bound at extraction (receiver fixed where detached)
console.log(bound()); // clicked:b — explicit binding (works decorated or not — extraction discipline)
// bad — onClick(btn.click) (detached: this undefined at call — TypeError inside, decorator blamed wrongly)
// fix — bind at extraction (not undecoration — binding layer, not observation layer)
```

```typescript
// good — arrow-field methods for handler-heavy classes (bound per instance — zero per-use thought)
class Panel {
  id = "p";
  onClick = (): string => `panel:${this.id}`; // arrow field (lexical this — detachment-proof by construction)
}
const panel = new Panel();
const cb: () => string = panel.onClick; // detached safely (bound at construction — extraction discipline unnecessary)
console.log(cb()); // panel:p — handler-heavy classes prefer fields (binding solved once per class, not per extraction)
// bad — method-form handlers in event-heavy classes (every extraction a bind-or-crash decision — decision fatigue as bug source)
// fix — arrow fields for handlers (bound by construction); methods for logic (bound at extraction where detached)
```

```typescript
// good — auto-binding decorator where the pattern repeats (centralized binding, documented allocation)
function bound<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
  _context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Ret>,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); }; // transparent (binding fixed by CALLERS via .bind — decorator preserves, doesn't solve)
}
class Svc11 {
  @bound
  run(): string { return "ran"; } // decorated (transparent — extraction still needs .bind (honest layering))
}
const svc = new Svc11();
console.log(svc.run.bind(svc)()); // ran — layers honest (decorator observes, .bind binds — each job its layer)
// bad — removing @timed to "fix" this-loss (observability sacrificed for a binding bug — wrong layer sacrificed, telemetry lost)
// fix — bind at extraction (extraction discipline — decorator layer untouched, telemetry kept)
```

**Common confusion** — "decorators break `this`" — *extraction* breaks `this` (detached calls receive `undefined` — decorated or not; undecorated methods detach identically). "arrow functions in decorators fix it" — arrow *wrappers* capture definition-site `this` (wrong receiver permanently — always `function` in wrappers + `apply`); arrow *fields* bind per instance (correct — different mechanism, different layer). "auto-binding decorators solve extraction" — bound-*returning* decorators allocate per access (getter-based) or bind once wrongly (first receiver wins) — explicit `.bind` at extraction stays the default for good reasons.

**Performance note** — `.bind` allocates one bound function per extraction (trivial); arrow fields allocate per instance per handler (bounded by handler count — fine outside thousands-of-instances paths); transparent decorators add zero binding cost (preserve, don't solve — honest layering).

**Mentor note** — detach one decorated method live (`const f = svc.handler; f()`) and read the `this`-undefined TypeError *with* telemetry intact (proving the decorator innocent — binding guilty). Exercise: fix three detached calls three ways (bind-at-extraction, arrow-field, auto-bind decorator) — layer-appropriate fixes per context. Review gate: undecorating to fix `this`-loss fails review (wrong layer sacrificed).
