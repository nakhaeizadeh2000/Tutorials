## 6.1. Common interview QA — decorators and metadata

### 1) **What does a standard method decorator receive and return?**

It receives the method function and a context with `kind: "method"`, its name and member information, plus APIs such as `addInitializer`. It may return a compatible replacement function or leave the method value unchanged by returning nothing. The return contract alone does not describe every side effect: a void-returning decorator can still schedule initialization that installs instance behavior.

Contrast other kinds before generalizing. A class decorator receives a constructor. A field decorator receives `undefined` and may return an initial-value transformer; that transformer still receives the result of the original field expression. An auto-accessor decorator receives getter/setter functions and can return an object with replacements or an `init` transformer. The context type depends on the kind. [Standard signatures](<../1. Standard Decorators/1.1. TC39 standard decorators classes methods fields.md>) owns the complete examples.

A useful follow-up is: “Does `void` prove zero work per call?” The answer is no. This complete probe deliberately installs a counting callback on each instance without returning a method replacement from the decorator. Its arrow captures the receiver of the per-instance initializer; it does not capture a nonexistent instance from the decorator's definition-time invocation.

Use **TypeScript 7.0.2** with `experimentalDecorators` omitted and **Node.js 20.20.2**. Save `probe.mts` in an empty directory without a `tsconfig.json`, run `tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --outDir dist probe.mts`, then `node dist/probe.mjs`.

```typescript
// file: probe.mts
let declarations = 0;
let initializations = 0;
let calls = 0;
function instrument<This extends object, Args extends unknown[], Result>(
  value: (this: This, ...args: Args) => Result,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Result>,
): void {
  if (context.private || context.static) throw new Error("public instance method required");
  declarations++;
  context.addInitializer(function (this: This) {
    initializations++;
    const receiver = this;
    Object.defineProperty(receiver, context.name, {
      configurable: true, writable: true,
      value: (...args: Args): Result => { calls++; return value.apply(receiver, args); }
    });
  });
}
class Service {
  base = 10;
  @instrument run(value: number): number { return this.base + value; }
}
const one = new Service();
const two = new Service();
const callback = two.run;
console.log(one.run(1), callback(2)); // 11 12
console.log(declarations, initializations, calls, Object.hasOwn(one, "run"), one.run === two.run);
// 1 2 2 true false
// one.run("1"); // TS2345: the declared method still requires a number.
```

The decorator executes once, its initializer twice, and the installed callbacks twice. This is intentional per-instance behavior with its own identity/allocation policy. It is not a universal replacement for all binding or instrumentation designs. The [binding reproduction](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by decorator misunderstandings.md>) and [timing/cache owner](<../3. Patterns in Practice/3.2. Logging timing and memoization decorators.md>) explore those policies in depth.

### 2) **How do legacy and standard models differ, and what proves a migration?**

A legacy method decorator receives target, key and descriptor. A standard method decorator receives value and context and can return a method value. Legacy property and parameter decorators have different contracts again. `experimentalDecorators` selects the legacy model for a configured program; it is not a separate setting for each file or imported function.

A migration first identifies the actual consumer's supported model, signatures, metadata and declaration kinds. Parameter decorators and `emitDecoratorMetadata` constrain consumers that require the legacy path. Then test the replacement behavior and emitted artifacts at the real boundary. Independent compilation can isolate settings; merely moving files cannot.

Both tested models apply a stack on one method bottom-to-top. Do not claim the migration reverses that direction. Other class-processing or field semantics still need their own checks. A successful build after removing a flag is insufficient proof: some constructor-only decorators deliberately accept both shapes. [The configured comparison](<../2. Legacy and Metadata/2.1. Legacy experimental decorators compared.md>) demonstrates compatible and incompatible examples, separate builds, receiver/result/error checks and artifact consumption.

For a changed-assumption follow-up, ask whether emitted JavaScript from an independently compiled legacy package can be consumed by another program. The local comparison shows that possibility. It does not prove that importing both raw source trees shares those independent settings, or certify the package's declaration/framework integration.

### 3) **What does design metadata tell a runtime consumer?**

With the legacy options enabled, TypeScript can emit `design:type`, `design:paramtypes` and `design:returntype` representations for eligible decorated declarations. They are approximations, not a complete type system or runtime schema. In the executed [design-metadata project](<../2. Legacy and Metadata/2.2. emitDecoratorMetadata and design types.md>), a concrete class has a constructor representation, an interface and heterogeneous union become `Object`, a string-literal union becomes `String`, and a tuple becomes `Array`. “Every union becomes Object” is therefore too broad.

A reader must distinguish the producer, runtime store and interpretation policy. TypeScript's helper guards absent `Reflect.metadata`; it can skip recording while a class still evaluates. Calling an absent reader API can then throw, and installing the library late does not retroactively record prior decoration. The actual missing/late entry-point examples demonstrate those different outcomes.

Standard `context.metadata`/`Symbol.metadata` is a different channel. A library declaration in `lib` does not install its runtime symbol; [2.3](<../2. Legacy and Metadata/2.3. Symbol.metadata and the metadata proposal.md>) supplies and tests that setup and an explicit transition reader. Neither channel reconstructs all erased types. If a provider cannot be identified from the recorded representation, supply a consumer-supported binding/token/factory policy. A string token or unchecked generic resolver is not proof that the selected value implements the required contract.

Follow-up: “Does a successful metadata read prove the input is valid?” No. It proves a value was found under a key. The [validation consumer](<../3. Patterns in Practice/3.1. Validation decorators field rules.md>) separately checks actual values and missing schema configuration.

### 4) **Which order are you describing?**

For a stack on one member, expressions evaluate top-to-bottom and decorator functions apply bottom-to-top. If those decorators return conventional wrappers that enter before delegation and exit in `finally`, invocation enters outer-to-inner and exits inner-to-outer. A short-circuiting wrapper can skip inner work. Name the phase and kind before predicting a trace.

Returned field transformers are another sequence: both transformations in [1.2](<../1. Standard Decorators/1.2. Decorator evaluation and application order.md>) run in source order, while the extra hooks run in registration order. The noncommutative example stores `40`; swapping the lines stores `31`. Neither transformer is discarded, and the original field expression still executes.

An instance method extra initializer runs before that class's instance fields; a field extra initializer runs after its own field, before later fields may exist. Static hooks and class hooks have their own boundaries. This is why “addInitializer means after construction” cannot explain the observed field-overwrite failure.

A useful follow-up is to remove `finally` from the wrapper stack or move a collection initializer below the decorated field. Explain the missing exit events or erased collection using the appropriate phase. An identical method result need not expose an ordering defect; an explicit event trace may be the required observation.

### 5) **When would you choose annotation, a wrapper, a mixin or explicit assembly?**

Choose from the consumer's contract and where the policy should be visible. A decorator can keep a supported framework or member policy near its declaration. An explicit wrapper can make local or conditional assembly visible where the value is used. A mixin factory can expose added instance capabilities through inference, while returning a subclass from a decorator does not automatically expand the declared class type. [Class patterns](<../1. Standard Decorators/1.3. Practical class decorators registration and mixins.md>) demonstrates that distinction and a legal conditional decorator factory.

State can also live in a wrapper closure or a receiver-keyed store; it is not exclusive to mixins. Decide whether the state belongs to a class definition, each receiver, a particular cache entry or a request. The [memoization example](<../3. Patterns in Practice/3.2. Logging timing and memoization decorators.md>) needs separate receiver identity, capacity and invalidation policies. Syntax alone determines none of them.

For dependency injection, the factory and cache implement the lifetime. The [container example](<../3. Patterns in Practice/3.3. Dependency injection with decorators.md>) compares actual singleton/transient identities, undefined cache presence, rebinding and manual constructor substitution. Rebinding future resolutions does not rewrite existing references. For application-oriented backend work, retain the NestJS/Fastify route and verify its actual provider pipeline; these language fixtures run no framework integration.

A good design answer names a concrete need, an alternative and a consequence. It does not impose a decorator-count threshold, assume annotation is always clearer, or claim equal performance from two syntactically different arrangements.

### 6) **Common confusion**

`void` means no replacement is returned through that result channel. It does not prohibit initialization or side effects. A context declaration does not create a runtime metadata API. A configured model is not selected independently by each import. Matching result types do not prove binding, identity, settlement or provider validity.

Interview vocabulary is useful only when it predicts behavior. Change one condition and ask for the consequence: omit the bootstrap, detach the method, swap field transformations, add a subclass field after freezing or change cached receiver state. The explanation should identify the relevant contract and evidence, not predict someone's competence from a memorized phrase.

### 7) **Performance note**

The probe creates one per-instance callback in each method initializer and executes each callback once. It demonstrates work and identity, not speed or memory quantity. Standard/legacy helpers, metadata queries, validation and cache retention have distinct costs that need a real workload. The fake-clock timing examples elsewhere are semantic checks, not latency results, and no syntax choice implies a universal performance ranking.

### 8) **Mentor note**

Start with a prediction, then ask the learner to justify it with the value/context contract and the actual callback that runs. For migration, require a named program and consumer boundary. For metadata, require a producer, store and reader. For caching or DI, require an invalidation or lifetime owner. Follow with one changed assumption and inspect which earlier conclusion remains valid.
