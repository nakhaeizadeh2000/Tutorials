## 6.1. Common interview QA — decorators and metadata

### 1) **What does a standard method decorator receive — and what may it return?** (value + context, same-kind or void)

**Definition** — method decorators receive `(value, context)`: `value` is the method function (with `this`/args/return types), `context` is `{ kind: "method", name, static, private, metadata, addInitializer }`. Returns: a same-kind replacement function (interception — must accept/return identically) or `void` (observation — no interception). Field decorators receive `undefined` + field context (no value exists yet); class decorators receive the constructor + class context (optionally returning an extended subclass).

**What problem it solves / history** — interviewers ask this to test proposal literacy (not legacy memory): candidates answering value+context per kind (with same-kind-or-void returns) show standard fluency; candidates answering `(target, key, descriptor)` show legacy-only experience (hireable for framework-bound teams, mismatch otherwise).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), answer per kind (class/method/field/accessor receive different values, uniform context shape), returns second (replace-same-kind vs observe-void), then volunteer the `this`-generic threading (`<This, Args, Ret>` preserving receivers — the precision marker). Full treatment in [1.1. TC39 standard decorators](<../1. Standard Decorators/1.1. TC39 standard decorators classes methods fields.md>).

**Runnable example** — three kinds, three signatures (good vs bad, `tsc --strict`):

```typescript
// good — method decorator: function + context in, same-kind function (or void) out
function wrap<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Ret>,
): (this: This, ...args: Args) => Ret {
  void context;
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); }; // same-kind replacement
}
class C12 {
  @wrap
  m(n: number): number { return n; }
}
console.log(new C12().m(7).toFixed(0)); // 7 — signature preserved exactly (contract identical)
// bad — (target: object, key: string) legacy answer (different proposal — correct for legacy, wrong for standard)
// fix — value + context per kind (standard vocabulary — legacy positions live in 2.1, not here)
```

```typescript
// good — void return observes without intercepting (zero per-call cost — see 1.1 promise 3)
function seen<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Ret>,
): void {
  void fn; void context; // observed (counted/registered at decoration — no wrapper installed)
}
class C13 {
  @seen
  n(): string { return "s"; }
}
console.log(new C13().n()); // s — observation without interception (cheapest decoration)
// bad — wrapping where observing suffices (closure per method for zero behavior delta — indirection without purpose)
// fix — void for telemetry (observe); function for interception (transform) — intent decides the return
```

```typescript
// good — field decorator receives undefined + context (no instance exists at definition)
function note(value: undefined, context: ClassFieldDecoratorContext<object, number>): void {
  void value; // always undefined (values don't exist at definition — context carries name/metadata)
  void context; // name/kind/metadata read here (per-instance behavior via initializers, never here)
}
class C14 {
  @note score = 1;
}
console.log(new C14().score.toFixed(0)); // 1 — field observed (registration shape — values flow per instance)
// bad — (target, key) legacy field answer (no descriptor exists for fields in EITHER proposal — properties don't exist yet)
// fix — undefined + context (standard field truth — initializer functions carry per-instance behavior)
```

**Common confusion** — "decorators receive the instance" — receive *definitions* (constructor functions, method functions, undefined-for-fields) — instances don't exist at decoration (per-instance behavior via initializers/hooks). "return type is free choice" — same-kind-or-void per position (returning a *different kind* errors — the checker enforces replacement discipline). "context shapes are uniform" — `kind`-discriminated per target (class/method/field/accessor contexts differ — read `kind` first, then the kind-specific fields).

**Performance note** — decoration runs once per definition (negligible); wrappers add one closure per call (observation cost identical to manual composition); void-observed methods cost zero per call (no wrapper installed).

**Mentor note** — strong answers give all three kinds unprompted (class/method/field + returns per kind); probe with "what does a field decorator receive?" (`undefined` — the definition-vs-instance split) when candidates stop at methods. Hiring signal: value+context vocabulary predicts standard fluency.

### 2) **Legacy vs standard decorators — how do signatures differ, and how do you migrate?** (positions vs value+context)

**Definition** — legacy: `(target, key, descriptor?)` positions (class → target function; method → target+key+descriptor (mutate-and-return); property → target+key (no descriptor); parameter → target+key+index) behind `experimentalDecorators`. Standard: `(value, context)` per kind (class → constructor+class-context; method → function+method-context; field → undefined+field-context), no flag. Migration: rewrite signatures per decorator, re-verify order (top-down member application → bottom-up), run behavior tests, delete the flag at zero legacy uses.

**What problem it solves / history** — framework-bound codebases (Angular/NestJS/TypeORM) standardized on legacy while greenfield code writes standard — interviews probe migration judgment (mechanical signature mapping + careful order re-verification) for teams straddling both eras. Candidates who name *both* deltas (signatures *and* order) migrate safely; signature-only migrators ship order bugs.

**Modern guidance** — as of TypeScript 5.9 era, answer signatures-first (positions vs value+context per kind), order-second (legacy member top-down vs standard bottom-up — stacks re-verified, not just retyped), migration-third (per file: all decorators one form, tests green, flag deleted at completion). Full treatment in [2.1. Legacy compared](<../2. Legacy and Metadata/2.1. Legacy experimental decorators compared.md>).

**Runnable example** — same behavior, both signatures (good vs bad, `tsc --strict`; legacy as commented code):

```typescript
// good — standard passthrough (no flag; value + context; same-kind return)
function pass<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); };
}
class Std {
  @pass
  go(): string { return "g"; }
}
console.log(new Std().go()); // g — standard form (flag-free, portable)
// legacy equivalent (commented: needs --experimentalDecorators; verified both ways in unit 91):
// function passLeg(target: object, key: string, desc: PropertyDescriptor): PropertyDescriptor { return desc; }
// class Leg { @passLeg go(): string { return "g"; } }
// console.log(new Leg().go()); // g — same behavior, legacy positions (flag-gated, framework-required only)
```

```typescript
// good — migration per file (all decorators one form — never mixed per file)
function a1<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); };
}
function a2<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); };
}
class Mig {
  @a1
  @a2
  m(): string { return "m"; } // one form throughout (migrated file — import paths audited, metrics coherent)
}
console.log(new Mig().m()); // m — per-file migration (all decorators, one form, tests green)
// bad — @a1Legacy beside @a2 standard (mixed forms: checkers cope awkwardly, readers never adapt, metrics diverge)
// fix — per-file migration PRs (all decorators in the file, one form at the end — mechanical + careful)
```

```typescript
// good — flag deletion as completion proof (no legacy uses remain — verified mechanically)
// tsconfig after migration: experimentalDecorators REMOVED (flag-off + green CI = zero legacy, proven)
export const form15 = "standard-only";
console.log(form15); // standard-only — completion verified (not asserted — green without the flag)
// bad — flag retained "just in case" post-migration (dead configuration inviting legacy regressions silently)
// fix — delete on completion (flag-off + green = proof; flag-on-forever = migration theater)
```

**Common confusion** — "legacy is deprecated" — maintained (flag + emit stable; framework ecosystems depend on it) but not recommended (new code writes standard) — deprecated-never vs recommended-never differ. "migration is renaming" — signatures *and* order differ (member application top-down → bottom-up — order-sensitive stacks re-verified, not just retyped). "mixed files work carefully" — mixed files check awkwardly and read impossibly (two mental models per file) — careful mixing is still mixing.

**Performance note** — identical runtime profile either form (closures per wrapper — migration is semantics-preserving with zero performance delta; verify via behavior tests, not benchmarks).

**Mentor note** — implement one decorator in both forms side by side (same behavior, different parameters) — signatures compared directly teach more than migration guides describe. Follow-up: "what else changes besides signatures?" (order — the careful half of migration). Hiring signal: order-aware migrators vs signature-only retypers.

### 3) **What does `emitDecoratorMetadata` emit — and why does a union param record `Object`?** (design facts + erasure)

**Definition** — the flag (with legacy `experimentalDecorators`) emits `Reflect.metadata("design:type"|"design:paramtypes"|"design:returntype", …)` per decorated declaration: the *declared* types as runtime values. Unions/interfaces/generics/literals erase to `Object`/`Array`/`String` (only *expressible* runtime types survive — specifics collapse to base constructors; see 2.2 promise 3). Requires the `reflect-metadata` polyfill (no import → `Reflect.metadata` undefined → definition-time crash).

**What problem it solves / history** — DI containers need constructor types at runtime (erasure blinds them — see 01/2.1); design metadata bridges selectively (compiler records, container reads). Interviewers probe the `Object`-fallback to test erasure understanding: candidates who derive it (unions don't exist at runtime → nothing recordable → `Object`) understand types-as-erasures, not just DI configuration.

**Modern guidance** — as of TypeScript 5.9 era, answer emit-first (three design keys, per decorated declaration), degrade-second (unions/interfaces → `Object` by erasure necessity), token-third (`@Inject(TOKEN)` where emit degrades — precision explicit). Full treatment in [2.2. emitDecoratorMetadata](<../2. Legacy and Metadata/2.2. emitDecoratorMetadata and design types.md>).

**Runnable example** — emit facts and degradation (good vs bad, `tsc --strict`; legacy emit described):

```typescript
// good — explicit tokens where emit degrades (unions/interfaces never bare-injected)
const TOK16 = "repo";
interface Repo16 { find(): string }
class Sql16 implements Repo16 {
  find(): string { return "sql"; }
}
const bindings16 = new Map<string, new () => Repo16>([[TOK16, Sql16]]);
console.log(new (bindings16.get(TOK16)!)().find()); // sql — token wiring (precision where design:paramtypes records Object)
// legacy emit reality (commented): constructor (repo: Repo | Mock) records [Object] (erased union — garbage if trusted)
// fix — @Inject(TOK16) explicit tokens (precision where emit degrades — portable across proposals)
```

```typescript
// good — concrete-class params record faithfully (exact constructors survive erasure — the shape emit serves)
class RealRepo17 {
  find(): string { return "real"; }
}
function resolve17<T>(make: () => T, guard: (x: unknown) => x is T): T {
  const inst: unknown = make(); // constructed (factory-provided — no metadata read at all)
  if (!guard(inst)) throw new Error("mismatch"); // validated (resolved instances checked — trust verified)
  return inst;
}
console.log(resolve17(() => new RealRepo17(), (x): x is RealRepo17 => x instanceof RealRepo17).find()); // real — validated resolution (metadata as hint, instances as truth)
// bad — trusting emitted union metadata (Object resolved as garbage dependency at boot — 5.1 promise 2's incident)
// fix — instanceof guards at resolution boundaries (emitted facts verified — trust, but verify, per boundary)
```

```typescript
// good — polyfill prerequisite stated (entry imports reflect-metadata before decorated modules evaluate)
// (entry shape documented; standard code below needs no polyfill — Symbol.metadata is runtime-native)
function needsNoPolyfill(): string { return "standard-channel"; } // standard metadata (no polyfill — native symbol)
console.log(needsNoPolyfill()); // standard-channel — legacy reflect-metadata serves legacy emit only (channels never cross)
// bad — legacy emit without reflect-metadata import (Reflect.metadata undefined → definition-time crash at first decorated class)
// fix — entry-template enforcement (polyfill line 1 of main.ts for legacy stacks — prerequisite verified, not assumed)
```

**Common confusion** — "metadata reflects runtime values" — reflects *declared types* (design-time facts — `design:paramtypes` of `(repo: Repo)` is `[Repo]` even when called with subclass instances). "standard decorators emit metadata" — no `emitDecoratorMetadata` equivalent exists for standard (flag pairs with legacy emit only) — standard metadata travels via `Symbol.metadata` (see 2.3). "unions will improve" — erasure is structural (union members don't exist at runtime — no future emit records them; tokens are permanent, not workaround).

**Performance note** — metadata emit adds per-decorated-declaration calls (startup cost — bounded by decorated surface); token maps O(1) per binding (same profile, zero polyfill); garbage-`Object` incidents cost boot-misbehavior debugging (unbounded — validation is free insurance).

**Mentor note** — log `design:paramtypes` for a union param live (`[Object]` — degradation demonstrated, not described) — tokens-from-here-on-out in one log line. Follow-up: "which params can skip tokens?" (concrete classes only — everything else tokenized, no exceptions). Hiring signal: degradation-aware DI answers predict production judgment.

### 4) **In what order do stacked decorators evaluate and apply — and why two phases?** (top-down eval, bottom-up apply)

**Definition** — evaluation (decorator *expressions* — `@a`, `@b(x)` — including factory *calls*) runs top-down as the class body processes; application (decorator *functions* invoked with target+context) runs bottom-up (closest-to-member first). Entry-hook wrappers therefore execute top-down (outer pre-hook first), exit-hooks bottom-up — the full sandwich predicted from two rules.

**What problem it solves / history** — stacked-decorator order questions are the most-asked decorator interview topic because *both* wrong answers sound right ("listed-first runs first" — true for evaluation, false for application; "last runs first" — true for application, false for evaluation). Candidates who name *both phases* (eval top-down, apply bottom-up) predict entry *and* exit order; single-phase answers fail half the stacks.

**Modern guidance** — as of TypeScript 5.9 era, answer phases-first (evaluation top-down incl. factory calls; application bottom-up), sandwich-second (entry top-down, body, exit bottom-up), legacy-contrast third (legacy member application top-down — reversed! — migration re-verifies order, never assumes). Full treatment in [1.2. Evaluation order](<../1. Standard Decorators/1.2. Decorator evaluation and application order.md>).

**Runnable example** — two phases, full sandwich (good vs bad, `tsc --strict`):

```typescript
// good — phase log proves both directions in one run
const order17: string[] = [];
function tag17(name: string) {
  order17.push(`eval:${name}`); // evaluation (top-down — factory calls run as encountered)
  return function (_v: unknown, _c: object): void {
    order17.push(`apply:${name}`); // application (bottom-up — last-listed applies first)
  };
}
class Demo17 {
  @tag17("outer")
  @tag17("inner")
  method(): void {}
}
void Demo17;
console.log(order17.join(",")); // eval:outer,eval:inner,apply:inner,apply:outer — two phases, opposite directions
// bad — "listed-first applies first" (evaluation truth misapplied to application — exit-hook order predicted backwards)
// fix — two-phase vocabulary (eval top-down, apply bottom-up — entry/exit derived per wrapper kind, tested per stack)
```

```typescript
// good — entry top-down, exit bottom-up (sandwich derived from wrapping, asserted in tests)
const flow17: string[] = [];
function step17(name: string) {
  return function <This, Args extends unknown[], Ret>(
    fn: (this: This, ...args: Args) => Ret,
  ): (this: This, ...args: Args) => Ret {
    return function (this: This, ...args: Args): Ret {
      flow17.push(`in:${name}`); // entry (outer pre-hook first — top-down execution for entries)
      try {
        return fn.apply(this, args);
      } finally {
        flow17.push(`out:${name}`); // exit (inner post-hook first — bottom-up execution for exits)
      }
    };
  };
}
class Pipe17 {
  @step17("a")
  @step17("b")
  run(): string { return "done"; }
}
console.log(new Pipe17().run(), flow17.join(",")); // done in:a,in:b,out:b,out:a — full sandwich (entry top-down, exit bottom-up)
// bad — testing outcomes only (results identical regardless of order — order bugs invisible without phase assertions)
// fix — spanning order tests (entry + exit sequences asserted — the order contract proven, not hoped)
```

```typescript
// good — legacy contrast stated (member application top-down — reversed from standard bottom-up)
function plain17<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); }; // passthrough (order-neutral — safe under both proposals)
}
class Safe17 {
  @plain17
  m(): string { return "m"; }
}
console.log(new Safe17().m()); // m — order-neutral decorators (passthrough/registration) migrate without order risk
// bad — assuming standard order for legacy stacks (reversed application — exit/entry predictions flip silently)
// fix — re-verify order per migrated stack (never assume across proposals — test entry + exit sequences post-migration)
```

**Common confusion** — "evaluation order doesn't matter" — factory *calls* can side-effect (argument evaluation, registry touches during evaluation phase run top-down — order-dependent side effects exist). "one example proves a stack" — outcomes prove nothing about order (identical results under both orders); phase *assertions* (entry/exit logs) prove order. "legacy order matches" — legacy member application runs *top-down* (reversed from standard bottom-up) — the migration detail most often missed (re-verify, never assume).

**Performance note** — order costs nothing at runtime beyond the wrappers installed (same closures any order — sequence differs, count identical); order *tests* cost one test per critical stack (cheapest ordering insurance available).

**Mentor note** — run the phase log live (eval-outer/inner, apply-inner/outer in one line) — two phases, opposite directions, unforgettable in 30 seconds. Follow-up: "which runs first on entry — outer or inner wrapper's pre-hook?" (outer — applied last = outermost = entry-first) then "on exit?" (inner — sandwich completed). Hiring signal: sandwich predictors vs single-phase guessers.

### 5) **When would you choose a decorator over a higher-order function or mixin?** (declaration distance rule)

**Definition** — decorators for *declarative member concerns* (telemetry/validation/caching visible at declarations, removable per line, recurring stacks named); higher-order calls for *local/conditional/dynamic* wrapping (explicit at use sites, tested as values, branched programmatically); mixins (call or decorator form) for *stateful composition* (fields + methods added — behavior with state, not just wrapping). Distance decides: declaration → decorator; use site → call; stateful → mixin.

**What problem it solves / history** — decorator-maximalism (indirection without co-location benefit — single-use locals decorated, control flow hidden) and composition-purism (manual nesting for framework telemetry — paren pyramids hiding intent) both misplace by ideology. Distance-based judgment (where does the reader need this information?) places each concern optimally — the senior answer interviewers probe for beyond syntax recall.

**Modern guidance** — as of TypeScript 5.9 era, answer distance-first (declaration/member → decorator; local/conditional → call; stateful → mixin), then depth (stacks past 3–4 named composed), then testability (named units tested as values, applied as annotations). Full treatment in [3.2. Logging timing](<../3. Patterns in Practice/3.2. Logging timing and memoization decorators.md>) promise 3 + [1.3. Practical decorators](<../1. Standard Decorators/1.3. Practical class decorators registration and mixins.md>).

**Runnable example** — distance decides (good vs bad, `tsc --strict`):

```typescript
// good — decorator for member concern (visible at declaration, removable per line)
function audited4<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); }; // hook point (named, tested passthrough)
}
class Orders5 {
  @audited4
  place(total: number): string { return `order:${total}`; } // concern declared (coverage visible per member)
}
console.log(new Orders5().place(9)); // order:9 — decoration where declarations live (right distance)
// bad — audit(order5.place) post-hoc per method (wrapping assignments scattered post-class — declaration/observation split)
// fix — @audited4 at declaration (co-located) for member concerns; calls at use sites for local needs
```

```typescript
// good — calls for local/conditional flow (explicit where readers need it)
function maybeWrap2<F extends (...args: never[]) => unknown>(fn: F, on: boolean): F {
  return (on ? ((...args: Parameters<F>): ReturnType<F> => {
    console.log("wrapped");
    return fn(...args) as ReturnType<F>;
  }) : fn) as F; // conditional (annotation can't branch — call form can, explicitly)
}
function base2(n: number): number { return n; }
const w2 = maybeWrap2(base2, true);
console.log(w2(1).toFixed(0)); // wrapped \n 1 — conditional flow as values (tested, branched, explicit)
// bad — @conditional decorators (branching hidden in decorator factories — control flow as annotation surprise)
// fix — calls for control flow (conditions/loops/pipelines as values — explicit where readers need it)
```

```typescript
// good — mixin for stateful composition (fields + methods added — behavior with state)
// (mixin mechanics in 06/3.2; decorator form in 1.3 promise 2 — referenced, not re-taught: stateful needs neither plain wrapper)
function withTag(tag: string) {
  return function <T extends new (...args: any[]) => object>(target: T): T {
    return class extends target {
      constructor(...args: any[]) {
        super(...args);
        (this as unknown as Record<string, unknown>)["tag"] = tag; // state ADDED (mixin territory — wrappers can't add fields)
      }
    };
  };
}
@withTag("v1")
class Doc7 {
  constructor(public n = 0) {}
}
const d7 = new Doc7();
console.log((d7 as unknown as Record<string, unknown>)["tag"]); // v1 — stateful composition (mixin form — wrappers observe, mixins extend)
// bad — decorator pretending to add state via closure (per-wrapper state, not per-instance — shared across instances silently)
// fix — mixin form for state (fields via subclassing — per-instance state with construction timing)
```

**Common confusion** — "decorators replace helpers" — decorators *apply* helpers declaratively (helper exists as a function — testable, composable independently); replacing helpers strands untested closures. "composition is always clearer" — six-deep manual nesting reads inside-out where vertical decorators read top-down — clarity depends on depth (shallow: calls; cross-cutting stacks: decorators). "mixins are just complex decorators" — mixins add *state* (fields via subclassing — per-instance data with construction timing); wrappers observe/transform behavior (stateless interception) — different capabilities, different tools.

**Performance note** — identical mechanics per form (closures per wrap — zero delta); mixins add subclass levels (prototype +1 per application — negligible shallow); named units test once, apply everywhere (test-time efficiency). Form choice is readability/testability economics, never runtime.

**Mentor note** — ask "where does the reader need this info?" per wrapping decision (declaration → decorator; use site → call; stateful → mixin) — distance judgment transfers to every future wrapping decision. Hiring signal: distance-based answers predict design judgment; ideology-based (always/never decorate) predict thrash.
