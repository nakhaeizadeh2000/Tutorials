## 7.1. Boundaries — what is covered elsewhere

Decorators combine several layers: a class or member, a function applied to it, compiler processing and any runtime consumer of stored metadata. Begin with the operation that failed. A decorator signature error, a detached method and an absent service binding need different evidence even when they occur in the same class. This lesson routes those questions to existing owners and uses their completed examples for practice.

### 1) **Class behavior before decorator behavior**

[the class-mechanics lesson](<../../../06 Classes and Object-Oriented Types/README.md>) owns constructor and instance views, inheritance and class-specific contracts. [construction and initialization](<../../../06 Classes and Object-Oriented Types/sections/1. Class Type Fundamentals/1.2. Constructors parameter properties and instance creation.md>) and [access and property mutation](<../../../06 Classes and Object-Oriented Types/sections/1. Class Type Fundamentals/1.3. Access modifiers and encapsulation public private protected readonly.md>) provide verified initialization, visibility and mutation contrasts. This domain owns [class and member decorator forms](<../1. Standard Decorators/1.1. TC39 standard decorators classes methods fields.md>) and [decorator registration and composition](<../1. Standard Decorators/1.3. Practical class decorators registration and mixins.md>): what the decorator receives, what it may return and how its runtime work is applied.

A parameter property or getter still has its ordinary class meaning when its class is decorated. Diagnose an uninitialized field at its producer and first read; diagnose a getter-only write at its actual property contract. Adding decoration does not supply omitted constructor state or make a readonly view freeze a shared object.

For composition, distinguish [function-form mixins](<../../../06 Classes and Object-Oriented Types/sections/3. Advanced Class Patterns/3.2. Mixins and class composition without inheritance.md>) from the decorator that returns or registers a constructor. A mixin is runtime implementation, not merely an erased intersection. Decide whether explicit composition or declaration-site decoration makes the dependency easier to see. Keep full class mechanics in their owner and verify the resulting constructor/member behavior in the chosen decorator project.

### 2) **Callable contracts and actual invocation**

[generic callable contracts](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.2. Generic functions inference constraints defaults and scope.md>), [tuple forwarding and bounded composition](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.3. Rest parameters tuple types and variadic composition.md>) and [overload contracts](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.1. Function overloads call signatures and implementation compatibility.md>) own relationships between arguments and results. [the verified receiver lesson](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.1. this parameter explicit typing and arrow vs function capture.md>) owns call-time this requirements and lexical capture; [callback variance](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.2. Callback variance strictFunctionTypes and bivariance pitfalls.md>) owns callback substitution. Use those contracts when designing a decorator wrapper, then use [logging and memoization decorators](<../3. Patterns in Practice/3.2. Logging timing and memoization decorators.md>) for the decorator-specific placement and cache policy.

A wrapper's assertion that it returns the original function type does not establish every property, overload, generic relationship or runtime effect of that function. The tuple owner explicitly bounds its ordinary callable forwarding and two-step composition. Name the supported contract, preserve the required receiver in the body, and check representative results and failures. Review any broader asserted promise rather than assuming that generic utility types prove it.

Preserving a receiver during an attached call also does not bind a detached method to an instance. The receiver lesson accepts extraction of an implicit method and executes its failed detached call, then contrasts explicit requirements, bind, wrappers and arrow fields. A function using apply(this, args) can preserve its caller's receiver without manufacturing the instance receiver a later bare call lacks. Choose the remedy from the intended invocation, not from the decorator's name.

### 3) **Compiler programs, emitted code and metadata stores**

[the configured decorator comparison](<../2. Legacy and Metadata/2.1. Legacy experimental decorators compared.md>) builds standard and legacy forms in separate configured programs, executes their wrappers and rejects mismatched settings. Use that owner before changing experimentalDecorators or transplanting a decorator between models. Project configuration selects the model for the checked program; a filename comment does not configure another model for that file.

[the bounded syntax gates](<../../../13 Configuration and Compiler Options/sections/2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>) and [execution paths](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>) supply the broader processing boundaries. A syntax gate or accepted decorated class is not proof that a native source loader supports its decorators. Consume the tested emitted artifact when that is the example's declared path. Verify a different processor independently before promising another deployment route.

Metadata introduces another producer/store/consumer relationship. [the verified metadata-channel lesson](<../2. Legacy and Metadata/2.3. Symbol.metadata and the metadata proposal.md>) initializes the required Symbol.metadata runtime channel, checks inherited and own metadata, and implements an actual standard-first reader with a separate legacy store. Selecting a lib declaration does not install a runtime symbol. Conversely, initializing a symbol does not attach or interpret the application's metadata automatically.

Keep [legacy design-type metadata](<../2. Legacy and Metadata/2.2. emitDecoratorMetadata and design types.md>) as the owner of compiler-emitted legacy design-type information. Do not infer that the standard metadata object and reflect-metadata contain identical entries or that generic/union types survive as complete runtime schemas. For an absent route or wrong dependency, trace the decorator's write, the selected store and the consumer's lookup under the actual program configuration. [the current learning route](<../../../25 Update TypeScript 7.0/sections/6. Overlaps and Update Route/6.1. Overlaps and the current learning route.md>) provides the version-specific learning route.

### 4) **Value validation and lifecycle tests**

[runtime boundary parsing](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.3. Parse do not validate at boundaries.md>) owns the evidence required at an external boundary, while [verified predicate and assertion behavior](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.3. Type guards predicates asserts and satisfies on functions.md>) demonstrates what predicates and assertions promise to the checker. Here, [the field-rule validation lesson](<../3. Patterns in Practice/3.1. Validation decorators field rules.md>) applies decorator registration to field rules. A decorator that merely records a rule is not itself a successful validation of an incoming value. Identify which function runs the checks and what malformed inputs it rejects.

Likewise, [the verified dependency-injection example](<../3. Patterns in Practice/3.3. Dependency injection with decorators.md>) implements a bounded synchronous token/factory mechanism with actual singleton and transient observations. It separates decorator registration from explicit dependency assembly, handles missing bindings and preserves existing-reference behavior after rebinding. Calling a binding singleton is not evidence that repeated resolutions reuse its result; the owner executes a cache-bypass mutation that exposes the difference.

Use [typed spies, stubs and fakes](<../../../17 Testing Types/sections/2. Typed Test Doubles/2.2. Spies stubs and fakes over generics.md>) for substitution and behavior-focused tests, and [the executed type-testing projects](<../../../17 Testing Types/sections/1. Type Assertions in Tests/1.2. tsd expect-type and type-testing libraries.md>) for real configured type-test runners. [the negative type-check lesson](<../../../17 Testing Types/sections/1. Type Assertions in Tests/1.3. Negative type tests with ts-expect-error.md>) owns negative type-test discipline. A passing signature check and a correct runtime lifecycle answer different questions. For decorated code, observe the critical initialization/application/call sequence as well as ordinary return values and errors. Scope tests to the behavior the example or application actually promises.

### 5) **Framework ownership and application context**

The language examples establish mechanisms for registration, metadata and dependency assembly. Their limits remain explicit: the local container does not implement a production framework's module discovery, request scopes, circular-dependency strategy or disposal. Use it to explain the token/factory/cache behavior before attributing a framework failure to that mechanism.

The [root curriculum](<../../../../../README.md>) lists NestJS as planned. The planned application-oriented backend curriculum uses NestJS with the Fastify adapter after the relevant foundations; its framework mechanics belong in that dedicated track when authored. Express-adapter differences should be discussed there when they change the application behavior being taught.

Before adopting a decorator example into an application, identify the framework's actual decorator/metadata contract, dependency lifecycle and processing pipeline. A standard-form class registration example demonstrates its own configured behavior; it does not certify every framework or adapter. Use the existing language owners to formulate the question, then validate the application's declared environment and consumer.

### 6) **Common confusion**

A callable wrapper and an instance-bound function are different results. Receiver forwarding preserves the receiver supplied to the wrapper; it does not invent an absent receiver. A type assertion that claims full signature preservation likewise cannot prove every runtime property or effect of the wrapped function.

Compiler libraries describe available names for checking. They do not initialize a metadata symbol or cause an application to consume its entries. The verified metadata lesson distinguishes bootstrap, inheritance, writes and reading from a separate store. Diagnose each missing link instead of treating another lib option as a runtime repair.

Registration, validation and service reuse are observable operations. A marker decorator returning its input is not evidence of routing, input validation or dependency injection. The worked validation and container owners supply the bodies and outcomes to inspect; a framework integration needs its own corresponding evidence.

### 7) **Performance note**

Following a navigation route has no direct performance effect. Decorator expressions/application, generated initializers, wrapper calls, metadata reads and container resolution can perform runtime work at different phases. Their cost depends on the implementation and invocation pattern; no timing, memory, cache-hit or framework benchmark was run for this routing lesson.

Do not estimate savings from the number of decorators or assume that call syntax and decorator syntax always generate identical work. Inspect the emitted code and measure the operation that matters. Type signatures erase without enforcing validation; actual validator and factory bodies still execute. Use [compiler measurement](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) for a compiler problem and an application measurement for runtime behavior.

### 8) **Mentor note**

Ask the learner to identify the failed operation, its owner and the next check. These cases reuse actual observations from the linked owners:

1. **A compiled route reader sees no metadata.** Check symbol initialization, the decorator's write and the reader's selected store. The metadata lesson's bootstrap-removed run fails its prerequisite; the bridge reads the actual standard or legacy entry according to declared precedence.
2. **A decorated method works attached to an object but fails as a stored callback.** Inspect invocation and receiver requirements. The receiver and configured-decorator lessons distinguish preserving the supplied receiver from binding a particular instance. Choose bind, an instance wrapper or a suitable arrow field and execute that invocation.
3. **A binding marked singleton returns different objects on consecutive resolutions.** Inspect the cache-presence path and factory calls. The container lesson mutates that branch and observes shared identity becoming false. A compiler pass does not establish the reuse contract.

A strong answer traces producer→operation→consumer and identifies the actual configured artifact. For a framework question, add the missing application contract rather than claiming parity with a teaching container. For a wrapper, state the supported signature and invocation before presenting its implementation as transparent.
