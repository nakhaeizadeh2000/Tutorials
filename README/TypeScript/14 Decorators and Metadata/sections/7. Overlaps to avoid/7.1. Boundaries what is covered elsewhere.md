### 1) **Class mechanics and mixin composition** (duality, constructors, `extends`, function mixins) — [06 Classes and Object-Oriented Types](<../../../06 Classes and Object-Oriented Types/README.md>)

**Definition** — class duality (instance type + constructor value), constructors/parameter properties, `extends`/`implements`/`abstract`/`override`, statics, and function-form mixins live in 06 — this domain *decorated* those mechanics (wrapping constructors, extending via decorator mixins, overriding decorated members) without re-teaching them.

**What problem it solves / history** — 06 owns "how do classes work?"; 14 owns "how do decorators annotate them?" — mechanics vs annotation, composed at every decorated class (06's rules governing what decorators receive and return).

**Modern guidance** — for class questions (duality, construction, inheritance, override discipline, mixin mechanics) start at the relevant 06 leaf; for decorator questions stay here ([1.1. TC39 standard decorators](<../1. Standard Decorators/1.1. TC39 standard decorators classes methods fields.md>), [1.3. Practical decorators](<../1. Standard Decorators/1.3. Practical class decorators registration and mixins.md>)).

**Runnable example** — 06 mechanics, 14 annotation (good vs bad, `tsc --strict`):

```typescript
// good — 06 duality + 14 decoration composed (constructor value decorated, instance type checked)
function tagged3(tag: string) {
  return function <T extends new (...args: any[]) => object>(target: T): T {
    return target; // marker (mechanics: 06 duality untouched — annotation purely additive)
  };
}
@tagged3("v1")
class Widget2 {
  constructor(public w = 0) {}
}
const wd: Widget2 = new Widget2(3); // instance type (06) of decorated constructor (14) — layers composed
console.log(wd.w.toFixed(0)); // 3 — mechanics (06) serving annotation (14), neither re-taught
// bad — learning class mechanics from decorator examples (decorated classes demonstrate annotation, not duality)
// fix — 06 first (mechanics), 14 second (annotation) — reference before application, always
```

```typescript
// good — mixin mechanics (06) in decorator form (14) — same subclassing, different syntax
function stamped3<T extends new (...args: any[]) => object>(target: T): T { // 06/3.2 mechanics, 14 syntax
  return class extends target {};
}
@stamped3

  constructor(public n = 0) {}
}
console.log(new Doc8() instanceof Doc8); // true — instanceof preserved (06 rule, 14 application)
// bad — decorator mixins without 06 mixin knowledge (constraint violations, instanceof surprises — mechanics missing)
// fix — 06/3.2 first (mixin mechanics: constraints, chains, instanceof), 14/1.3 second (annotation form)
```

```typescript
// good — override discipline on decorated members (06 rules govern, 14 observes)
class Base3 {
  render(): string { return "b"; }
}
class Page3 extends Base3 {
  override render(): string { return "p"; } // 06: override declared (rename-tracked); 14 would wrap (not replace) this

console.log(new Page3().render()); // p — override mechanics (06) orthogonal to decoration (14) — composed, never confused
// bad — decorating instead of overriding (behavioral extension via annotation where inheritance belongs — layer violation)
// fix — override for extension (06), decorate for cross-cutting (14): extension vs annotation differ
```

**Common confusion** — "14 replaces 06/3.2" — 14 *applies* mixin mechanics declaratively; 06 *defines* them (constraints, chains, `instanceof`, conditional composition) — application vs reference differ. "decorated classes need no class knowledge" — decorators receive constructors/instances/members (06's subjects) — annotation without mechanics produces constraint violations and `this` bugs.

**Performance note** — no overlap means no duplicated measurement — mechanics (06) and annotation (14) each cost trivially (subclass levels + closures, identical either form).

**Mentor note** — route "how do classes work?" to 06 and "how do I annotate them?" here — the question's verb (work vs annotate) picks the domain, every time.

### 2) **Higher-order functions and callable patterns** (wrappers, overloads, `this`, variance) — [05 Functions and Callable Types](<../../../05 Functions and Callable Types/README.md>)

**Definition** — higher-order wrappers, overloads vs generics, `this` parameters, rest/tuple composition, callback variance, and predicates/asserts live in 05 — this domain *chose between* decorator syntax and call composition per case (see 3.2 promise 3's distance rule) without re-teaching callables.

**What problem it solves / history** — 05 owns "how do functions compose?"; 14 owns "when does annotation beat calls?" — mechanics vs placement, composed at every wrapping decision (05's wrappers available in both forms; 14's distance rule placing each).

**Modern guidance** — for callable mechanics (signatures, overloads, `this`, variance, predicates) start at the relevant 05 leaf; for decorator-vs-call placement stay here ([3.2. Logging timing](<../3. Patterns in Practice/3.2. Logging timing and memoization decorators.md>) promise 3 + [4.1. Checklist](<../4. Important points to remember/4.1. Decorators checklist mental models mentors insist on.md>) promise 4).

**Runnable example** — 05 mechanics, 14 placement (good vs bad, `tsc --strict`):

```typescript
// good — higher-order call where readers need it (local, explicit — 05 mechanics, 14 placement)
function withLog<F extends (...args: never[]) => unknown>(fn: F): F {
  return ((...args: Parameters<F>): ReturnType<F> => {
    return fn(...args) as ReturnType<F>; // 05: generic wrapper mechanics (Parameters/ReturnType threading)
  }) as F;
}
function base3(n: number): number { return n; }
const logged3 = withLog(base3); // 14: call form (local one-off — placement rule applied)
console.log(logged3(1).toFixed(0)); // 1 — mechanics (05) placed by distance (14): composed, not duplicated
// bad — @withLog on single-use locals (decorator machinery for one call site — placement violated)
// fix — distance rule (declaration → decorator; use site → call — 3.2 promise 3 decides per case)
```

```typescript
// good — this-threading via 05 mechanics inside 14 wrappers (explicit receivers, applied receivers)
function bound3<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); }; // 05: this-parameter mechanics
}
class Svc12 {
  @bound3
  run(): string { return "r"; } // 14: annotation placement (member concern, declaration-visible)
}
const s12 = new Svc12();
console.log(s12.run.bind(s12)()); // r — mechanics (05) placed decoratively (14): layers composed
// bad — arrow-function wrappers capturing definition-site this (05 violation inside 14 syntax — layer confusion)
// fix — function + apply (05 mechanics) in decorators (14 placement): each layer correct independently
```

```typescript
// good — overloads vs generics untouched by decoration (05 judgment preserved under @)
function flex<This>(fn: (this: This) => string): (this: This) => string {
  return function (this: This): string { return fn.apply(this); }; // transparent (overload shapes pass through unwidened)
}
class Multi {
  @flex
  m(): string { return "m"; }
}
console.log(new Multi().m()); // m — overload/generic shapes (05) survive decoration transparently (14 adds, never rewrites)
// bad — decorators widening overloaded signatures (contract rewritten under annotation — 4.1 promise 2's additive rule violated)
// fix — generic threading (signatures preserved — additive-only discipline per 4.1 promise 2)
```

**Common confusion** — "14 replaces 05 wrappers" — 14 *places* wrappers declaratively; 05 *defines* them (signatures, generics, `this`, variance) — placement vs mechanics differ. "decorated callables skip 05 rules" — variance/`this`/overload rules apply *inside* every decorator wrapper (05 governs decorator bodies as strictly as plain functions).

**Performance note** — no overlap means no duplicated measurement — callables (05) and annotation (14) each cost trivially (closures per wrap, identical either form).

**Mentor note** — route "how do I wrap this?" to 05 and "decorator or call?" here — mechanics vs placement, every time. Exercise: implement one wrapper both ways and place each per the distance rule — mechanics learned once (05), placed twice (14).

**Cross-links** — generic wrappers → [2.2. Generic functions](<../../../05 Functions and Callable Types/sections/2. Overloads and Generics/2.2. ### 4) **Validation at boundaries and testing decorated code** (schemas, guards, doubles) — [15 Strictness, Errors and Validation](<../15 Strictness Errors and Validation/README.md>) + [17 Testing Types](<../17 Testing Types/README.md>) (textual forwards)

**Definition** — boundary validation practice (schemas, assertion functions, error-as-value patterns) lives in domain 15; testing decorated code (doubles for decorated classes, DI rebinding in suites, order-asserting decorator tests) lives in 17 — this domain *produced* validatable/testable shapes (schemas via decorators, injectable constructors, order-assertable stacks) without owning validation or testing practice.

**What problem it solves / history** — 14 owns "how do decorators declare?"; 15/17 own "how do teams prove?" (schemas proving inputs, suites proving behavior) — declaration vs proof, composed at every validated boundary and tested decorator (14's shapes consumed by 15/17's practices).

**Modern guidance** — as of TypeScript 5.9 era, declare with decorators here (rules, tokens, order hooks); prove with 15 (schemas/guards at boundaries) and 17 (doubles/rebinding/order-assertions in suites) when those domains land — until then, 07's guards + hand-rolled `validate()` (see 3.1) and container rebinding (see 3.3) are the authoritative previews.
