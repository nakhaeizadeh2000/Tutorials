## 1.2. Decorator evaluation and application order

### 1) **Evaluation vs application** (expressions top-down, application bottom-up)

**Definition** — two phases: *evaluation* (decorator *expressions* — `@a`, `@b(x)` — evaluated top-down as the class body is processed) then *application* (decorator *functions* invoked with target+context bottom-up — last decorator applies first). Factories add a third beat: factory *calls* evaluate during evaluation phase (top-down), their *returned* decorators apply bottom-up with the rest.

**What problem it solves / history** — stacked decorators (`@auth @validate @log`) behaved "inside-out" versus reading order — `log` (listed last) wrapped first (innermost), so logs showed validation-inside-auth instead of the expected auth-then-validate-then-log pipeline. The two-phase rule predicts every stacking: read application bottom-up (closest to the member applies first, becomes innermost wrapper).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), order stacked decorators outermost-first in source (framework outermost — `@Controller` above `@Get`; cross-cutting outermost — `@auth` above `@validate` above `@log` for auth→validate→log execution); verify order assumptions with one spanning test per critical stack (execution-order assertion, not just outcome). Factories capture per-use arguments during evaluation (top-down — argument side effects order top-down too).

**Runnable example** — two phases demonstrated (good vs bad, `tsc --strict`):

```typescript
// good — application runs bottom-up: closest decorator wraps first (innermost)
const order: string[] = [];
function tag2(name: string) {
  order.push(`eval:${name}`); // factory CALL runs at evaluation (top-down)
  return function (_v: unknown, _c: object): void {
    order.push(`apply:${name}`); // APPLICATION runs bottom-up (last-listed first)
  };
}
class Demo {
  @tag2("outer")
  @tag2("inner")
  method(): void {}
}
void Demo;
console.log(order.join(",")); // eval:outer,eval:inner,apply:inner,apply:outer — two phases, opposite directions
```

```typescript
// good — execution pipeline reads bottom-up: auth(outer) → validate → log(inner applies first = innermost)
const flow: string[] = [];
function step(name: string) {
  return function <This, Args extends unknown[], Ret>(
    fn: (this: This, ...args: Args) => Ret,
  ): (this: This, ...args: Args) => Ret {
    return function (this: This, ...args: Args): Ret {
      flow.push(name);
      return fn.apply(this, args);
    };
  };
}
class Pipe {
  @step("auth")
  @step("validate")
  @step("log")
  run(): string { return "done"; }
}
console.log(new Pipe().run(), flow.join(">")); // done ... auth>validate>log?? (see confusion: application bottom-up means log wraps FIRST = runs LAST around... read on)
```

```typescript
// good — corrected mental model: innermost wrapper runs FIRST (log inner = logs entry before validate/auth bodies)
// flow above: auth(outer, applied last = outermost wrapper = runs FIRST on entry), then validate, then log, then body
// execution order on entry: auth → validate → log → body (source order top-down == execution order top-down HERE)
// rule of thumb: application bottom-up + wrapping = execution top-down for entry-hooks (each wrapper runs pre-hook, then delegates inward)
// bad — assuming listed-first runs first WITHOUT the wrapping model (wrong for exit-hooks: log(inner) exit-logs LAST)
// fix — trace one stack fully (entry hooks top-down, body, exit hooks bottom-up — the full sandwich, asserted in tests)
const flow: string[] = ["auth", "validate", "log"]; // re-declared (mirrors fence 1's runtime result; fences compile standalone)
function sandwich(): string[] { return [...flow]; }
console.log(sandwich().join(">")); // auth>validate>log — entry order (exit order reverses: log>validate>auth)
```

**Common confusion** — "listed-first applies first" — listed-first *evaluates* first; *applies* last (bottom-up) — for entry-hook wrappers the net execution still reads top-down (outer pre-hook runs before delegating inward), which is why the confusion persists harmlessly until exit-hooks (post-body order reverses — bottom-up) expose it. "factories complicate ordering" — factories evaluate (top-down, capturing args) *then* join application (bottom-up with the rest) — two beats, same rule, no exception. "order doesn't matter for pure registration" — registration decorators are order-independent *only if* they don't interact (route + auth metadata merging *does* interact — order documents precedence; test it).

**Performance note** — decoration order costs nothing at runtime beyond the wrappers it installs (same closures in any order — only *execution sequence* differs, never count). Order *tests* (spanning assertions per critical stack) cost one test each — cheapest ordering insurance available.

**Mentor note** — run the `order` array demo live (eval-outer/inner, apply-inner/outer in one log line) — two phases, opposite directions, unforgettable in 30 seconds. Exercise: predict one 3-stack's entry *and* exit order before running (entry top-down, exit bottom-up — full sandwich predicted, then verified). Review gate: critical decorator stacks carry order-asserting tests.

### 2) **Multiple decorators per member** (composition order and factories)

**Definition** — stacking composes wrappers inside-out (bottom-up application = innermost-first wrapping); factories (`@rule(min, max)`) parameterize per use (factory call per decoration site, captured args closing over the returned decorator). Composition reads as nested function application (`auth(validate(log(fn)))` for top-down `@auth @validate @log`) — decorators as syntax for manual wrapping.

**What problem it solves / history** — cross-cutting member concerns (auth + validation + logging + timing + caching on one endpoint) composed manually as nested calls (`timed(logged(auth(handler)))` — inside-out reading, paren-counting, reorder-by-rewriting) — decorators linearize the stack vertically (one concern per line, reorder by moving lines, remove by deleting lines) with identical runtime semantics.

**Modern guidance** — as of TypeScript 5.9 era, stack vertically (one decorator per line, outermost concern first in source); parameterize with factories (arguments captured per site — `@Min(0)`, `@Route("/x")`, `@Retry(3)`); keep stacks shallow (3–4 decorators readable; past that extract a composed decorator (`@endpoint = compose(auth, validate, log)`) naming the stack). Test composed behavior per stack (unit per decorator + spanning test per critical stack).

**Runnable example** — vertical stack equals nested calls (good vs bad, `tsc --strict`):

```typescript
// good — three concerns, three lines, reorder by moving lines
function min2(n: number) {
  return function (value: undefined, context: ClassFieldDecoratorContext<object, number>): void {
    void value; void context; void n; // rule registered (see 3.1 full pattern — registration sketch here)
  };
}
function required<T>(value: undefined, context: ClassFieldDecoratorContext<object, T>): void {
  void value; void context; // presence rule, generic over field type (applies to any field — sketch; 3.1 implements fully)
}
class Form2 {
  @min2(0)
  @required
  age: number = 5; // stacked field rules (bottom-up application: required registers first — order irrelevant here, both pure registration)
}
console.log(new Form2().age.toFixed(0)); // 5 — stacked registration (order-independent for pure collectors)
// bad — manual nested rule assembly (rule objects composed by hand per field — drift per field, unreviewable at scale)
// fix — stacked decorators (one concern per line — add/remove/reorder by editing lines, never expressions)
```

```typescript
// good — factory capturing per-site arguments (parameterized decoration)
function prefix(p: string) {
  return function <T extends new (...args: any[]) => object>(target: T): T { // factory closes over p per use
    return class extends target {
      constructor(...args: any[]) {
        super(...args);
        (this as Record<string, unknown>)["tag"] = p; // per-site argument materialized per class
      }
    };
  };
}
@prefix("A")
class BoxA {}
@prefix("B")
class BoxB {}
console.log((new BoxA() as Record<string, unknown>)["tag"], (new BoxB() as Record<string, unknown>)["tag"]); // A B — same factory, different captures
// bad — one decorator per argument value (@prefixA, @prefixB — combinatorial decorator explosion)
// fix — factories (arguments captured per site — one decorator definition, unbounded uses)
```

```typescript
// good — composed decorator naming a recurring stack (shallow source, deep behavior)
function logged2<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); }; // transparent (behavior identical, hook point named)
}
class Svc2 {
  @logged2
  calc(n: number): number { return n * 2; } // single named decorator (stack of one — grows by composing, not appending)
}
console.log(new Svc2().calc(21).toFixed(0)); // 42 — composed stacks start as named singles (extract on third concern, not fifth)
// bad — 6-deep anonymous stacks (unreadable, untestable per layer, reorder-by-prayer)
// fix — named composition (@endpoint bundling auth+validate+log — one name per recurring stack, tested once)
```

**Common confusion** — "stacking order is cosmetic" — order decides wrapping (innermost-first execution for entry hooks, reversed exits) AND registration precedence (metadata merges in application order — later-applied (lower-listed) wins ties by default). "factories run per instance" — factories run per *decoration site* (class-definition time — once per class, never per instance; per-instance behavior needs initializers/hooks). "composed decorators hide behavior" — *named* composition documents (the name states the stack's purpose); *anonymous* deep stacks hide (six concerns, no name — extract on sight).

**Performance note** — stacked wrappers nest closures per call (3-deep stack = 3 frames per invocation — same as manual nesting, identical cost); registration-only stacks cost zero per call (definition-time only). Depth cost is readability (extract past 3–4), never speed (closures are cheap; clarity isn't).

**Mentor note** — rewrite one 3-stack as nested calls beside the decorated version (`auth(validate(log(fn)))` vs three lines) — identical runtime, vertical readability winning visibly. Exercise: extract one recurring 3-stack into a named composed decorator with one spanning test — naming + testing in one refactor. Review gate: 5+-deep anonymous stacks fail review (extract + name + test).

### 3) **Field initialization timing** (definition-time vs instance-time split)

**Definition** — field decorators execute at *class-definition* time (module load — registration, schema building, metadata attachment); field *initializers* (declared `= value`, returned replacements, `addInitializer` hooks) execute per *instance* (construction — values, validation runs, observation). Confusing the two (validating at definition against nonexistent instances, or registering per instance) is the most common field-decorator bug class.

**What problem it solves / history** — definition-time validation (`if (initialValue < min) throw` inside the decorator body — evaluating against `undefined`, since no instance exists) threw at import for every decorated class (module load crash from a check that needed an instance). The timing split assigns each job its phase: *rules* register at definition (schema built once), *checks* run per instance (values exist) — see 3.1's two-phase validation pattern in full.

**Modern guidance** — as of TypeScript 5.9 era, register at definition (schemas, metadata, rule tables — once per class); act per instance (initializers, `addInitializer` hooks, validation runs — once per construction); never read instance state in decorator bodies (nothing exists yet — the `undefined` you read is always a bug, never data).

**Runnable example** — phases separated (good vs bad, `tsc --strict`):

```typescript
// good — definition registers, instance initializes (phases separated by construction)
const DEFAULTS = new Map<string, unknown>();
function def(v: unknown) {
  return function (value: undefined, context: ClassFieldDecoratorContext<object, unknown>): void {
    void value;
    DEFAULTS.set(String(context.name), v); // DEFINITION time (schema/defaults table built once per class)
  };
}
class Cfg3 {
  @def("localhost") host = "x"; // instance value "x" (per construction); default "localhost" registered (per definition)
}
console.log(new Cfg3().host, DEFAULTS.get("host")); // x localhost — instance value + definition default, separate phases
// bad — reading instance state in the decorator body (undefined always — no instance exists at definition)
// fix — bodies register (tables/schemas/metadata); initializers/hooks act (per-instance behavior lives there)
```

```typescript
// good — addInitializer hooks run per instance (post-field-initialization timing, this-bound)
function observed(value: undefined, context: ClassFieldDecoratorContext<object, number>): void {
  void value;
  context.addInitializer(function (this: { seen?: string[] }) {
    (this.seen ??= []).push(String(context.name)); // INSTANCE time (this exists — fields set, hooks observe)
  });
}
class Rec3 {
  seen?: string[];
  @observed score = 1;
  @observed level = 2; // hooks run in field order (score then level — deterministic per declaration order)
}
const r = new Rec3();
console.log(r.seen?.join(","), r.score.toFixed(0)); // score,level 1 — hooks observed construction in order
// bad — pushing to shared (module-level) arrays in hooks expecting per-instance isolation (shared state, cross-instance leaks)
// fix — this-bound state (hooks receive the instance — isolate per this, never module globals)
```

```typescript
// good — replacement initializer runs INSTEAD of declared (documented interception, per instance)
function fixed(v: number) {
  return function (_value: undefined, _context: ClassFieldDecoratorContext<object, number>): (this: object) => number {
    return function (this: object): number { return v; }; // replacement (declared initializer ignored — interception explicit)
  };
}
class Consts {
  @fixed(42) answer = 0; // declared 0 ignored (replacement documented at the decorator — interception visible)
}
console.log(new Consts().answer.toFixed(0)); // 42 — replacement initializer (per instance, documented interception)
// bad — replacement initializers as silent defaults (declared values dead code — readers trust `= 0`, runtime serves 42)
// fix — document interception (decorator name + comment stating replacement — declared values must visibly lose)
```

**Common confusion** — "decorator bodies see field values" — bodies see `undefined` + context (definition phase — values don't exist); *only* returned initializers and hooks see values (instance phase). "hook order is unspecified" — field hooks run in *declaration order* per instance (deterministic — score then level above, always). "replacement initializers compose" — last-applied (bottom-most) replacement *wins* (earlier replacements discarded — stacking replacements is usually a bug; stack *hooks*, replace sparingly).

**Performance note** — definition work runs once per class (registration tables — negligible); hooks/initializers run per instance-field (one function call each — trivial vs construction); shared-state leaks in hooks cost unbounded debugging (isolate per `this`, always).

**Mentor note** — `console.log` inside a decorator body vs inside a hook (body logs once at import; hook logs per `new`) — phases demonstrated in two lines of output. Exercise: classify three field-decorator bugs by phase (definition-reading-instance? shared-state-in-hook? silent-replacement?) — phase vocabulary debugging directly. Review gate: instance reads in decorator bodies fail review; module-global writes in hooks fail review.
