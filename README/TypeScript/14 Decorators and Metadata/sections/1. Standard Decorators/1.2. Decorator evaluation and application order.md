## 1.2. Decorator evaluation and application order

### 1) **Separate expression evaluation, application and invocation**

For a stack on one declaration, decorator expressions evaluate in source order, from top to bottom. Their resulting decorator functions are then called from bottom to top. A returned wrapper runs later, when the method is invoked. These are different events. Calling the bottom decorator first does not imply that its wrapper's entry code runs first.

This lesson uses **TypeScript 7.0.2** with the standard-form model (`experimentalDecorators` omitted) and emitted modules on **Node.js 20.20.2**. The [TypeScript 5.0 explanation](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#decorators) illustrates reverse application for a member stack. The [legacy comparison](<../2. Legacy and Metadata/2.1. Legacy experimental decorators compared.md>) tests the same bottom-to-top application direction in both models; their signatures and broader class-processing rules differ.

Save the three independent files below in an empty directory without a `tsconfig.json` and run:

```bash
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --outDir dist wrappers.mts transforms.mts lifecycle.mts
node dist/wrappers.mjs
node dist/transforms.mjs
node dist/lifecycle.mjs
```

In the first example, `layer("outer")` and `layer("inner")` are factory calls. Their results are decorator functions, and those functions return method wrappers. The factory, decorator and wrapper each record their own event.

```typescript
// file: wrappers.mts
const events: string[] = [];
function layer(label: string) {
  events.push(`evaluate:${label}`);
  return function <This, Args extends unknown[], Result>(
    value: (this: This, ...args: Args) => Result,
    context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Result>,
  ): (this: This, ...args: Args) => Result {
    void context;
    events.push(`apply:${label}`);
    return function (this: This, ...args: Args): Result {
      events.push(`enter:${label}`);
      try { return value.apply(this, args); }
      finally { events.push(`exit:${label}`); }
    };
  };
}
class Service {
  @layer("outer")
  @layer("inner")
  run(fail: boolean): number {
    events.push("body");
    if (fail) throw new RangeError("failed");
    return 7;
  }
}
console.log(events.join("|"));
events.length = 0;
const service = new Service();
console.log(service.run(false));
console.log(events.join("|"));
events.length = 0;
try { service.run(true); }
catch (error) { console.log(error instanceof RangeError); }
console.log(events.join("|"));
// evaluate:outer|evaluate:inner|apply:inner|apply:outer
// 7
// enter:outer|enter:inner|body|exit:inner|exit:outer
// true
// enter:outer|enter:inner|body|exit:inner|exit:outer
```

Application produces `outer(inner(originalMethod))`. The outer wrapper enters first, delegates to the inner wrapper, and exits last. The `finally` blocks make exit events run on either return or throw. Without `finally`, a statement after the delegated call would be skipped on a throw. The wrappers' generic signatures belong to [1.1](<./1.1. TC39 standard decorators classes methods fields.md>); the important observation here is which function executes at each phase.

This member-stack rule is not a complete timeline for an entire class. Decorator expression evaluation also interacts with computed names, and application is grouped by decorated element kinds and static/instance roles. The [proposal's detailed design](https://github.com/tc39/proposal-decorators#detailed-design) distinguishes these operations. Do not extrapolate one stack into a claim that every decorator body in a class runs in textual order.

### 2) **Returned field transformers compose**

A field decorator can return a function from an initial value to a stored value. With stacked decorators, the field transformers in this example run top-to-bottom, while extra callbacks registered during application run in the order they were registered. Those two sequences differ. Neither transformer is discarded.

```typescript
// file: transforms.mts
const events: string[] = [];
function change(label: string, transform: (value: number) => number) {
  events.push(`evaluate:${label}`);
  return function <This>(
    _value: undefined, context: ClassFieldDecoratorContext<This, number>,
  ): (this: This, initial: number) => number {
    events.push(`apply:${label}`);
    context.addInitializer(function (this: This) {
      events.push(`hook:${label}:${context.access.get(this)}`);
    });
    return function (this: This, initial: number): number {
      events.push(`init:${label}:${initial}`);
      return transform(initial);
    };
  };
}
function source(): number { events.push("source"); return 3; }
class Box {
  @change("plus", n => n + 1)
  @change("times", n => n * 10)
  value = source();
  constructor() { events.push(`body:${this.value}`); }
}
console.log(events.join("|"));
events.length = 0;
const box = new Box();
console.log(box.value);
console.log(events.join("|"));
// evaluate:plus|evaluate:times|apply:times|apply:plus
// 40
// source|init:plus:3|init:times:4|hook:times:40|hook:plus:40|body:40
```

The declared `source()` expression still runs. Its `3` becomes `4`, then `40`, and both extra hooks read the final stored value. “Bottom-to-top application” alone cannot predict the transformer direction. The decorator call contributes a transformer to the initialization sequence; it is not itself that transformation.

Exercise: swap the two decorator lines. The definition trace becomes `evaluate:times|evaluate:plus|apply:plus|apply:times`. Construction becomes `source|init:times:3|init:plus:30|hook:plus:31|hook:times:31|body:31`, and the stored value is `31`. This noncommutative pair exposes ordering more clearly than two log-only decorators. Prefer transformations whose order is intentional and explain that order at the declaration.

A returned method wrapper can also stop delegation entirely. For example, an authorization wrapper may throw before calling its input. In that case inner wrappers and the body do not run. Consequently, order can change correctness and the amount of work performed. There is no language-wide rule that metadata merging or registration “last wins”; the actual storage operations decide that policy. [Validation](<../3. Patterns in Practice/3.1. Validation decorators field rules.md>) owns rule collection, and [logging and memoization](<../3. Patterns in Practice/3.2. Logging timing and memoization decorators.md>) owns those call-time policies.

### 3) **Locate each initialization callback**

The timing of `context.addInitializer` depends on the decorated declaration. These are the [proposal's initialization boundaries](https://github.com/tc39/proposal-decorators#adding-initialization-logic-with-addinitializer):

| Decorated declaration | Extra callback runs |
|---|---|
| Instance method/getter/setter | Before the class's instance fields initialize |
| Instance field/auto-accessor | Immediately after that field/accessor initializes |
| Static method/getter/setter | Before static fields initialize |
| Static field/auto-accessor | Immediately after that static field/accessor initializes |
| Class | After static initialization of the class |

For an inherited class, reason about the base and derived initialization steps separately. An instance method hook is not permission to read every derived field. Likewise, an instance field hook can observe its own value before the next field exists. The basic field trace in [1.1](<./1.1. TC39 standard decorators classes methods fields.md>) demonstrates that read boundary. This complete example compares static, class and instance hooks:

```typescript
// file: lifecycle.mts
const events: string[] = [];
function mark(label: string, value: number): number { events.push(label); return value; }
function method(_value: () => void, context: ClassMethodDecoratorContext<object>): void {
  context.addInitializer(function () { events.push(`method-hook:${context.static}`); });
}
function field(_value: undefined, context: ClassFieldDecoratorContext<object, number>): void {
  context.addInitializer(function () {
    events.push(`field-hook:${String(context.name)}:${context.access.get(this)}`);
  });
}
function complete(_value: new () => object, context: ClassDecoratorContext): void {
  context.addInitializer(function () { events.push("class-hook"); });
}
@complete
class Lifecycle {
  @method static boot(): void {}
  @field static count = mark("static-field", 1);
  static { events.push("static-block"); }
  @method run(): void {}
  @field first = mark("first-field", 2);
  after = mark("after-field", 3);
  constructor() { events.push("body"); }
}
events.push("defined");
new Lifecycle();
new Lifecycle();
console.log(events.join("|"));
// method-hook:true|static-field|field-hook:count:1|static-block|class-hook|defined|method-hook:false|first-field|field-hook:first:2|after-field|body|method-hook:false|first-field|field-hook:first:2|after-field|body
```

Static and class events happen during this one class definition. Instance events repeat for each `new`. Defining a class inside a repeatedly invoked factory would repeat the definition work too. A class hook is a useful point for registering the final decorated constructor; an instance field hook is not a universal “all construction is complete” callback.

### 4) **Common confusion**

A factory call, a decorator call, a returned transformer and an extra initializer are four different functions. Label the function whose order you are describing. “Top-to-bottom” can correctly describe expression evaluation, wrapper entry, or field transformation in the examples, while “bottom-to-top” describes decorator application and wrapper exit. Those statements require their phase and declaration kind.

The legacy and standard method stacks do not reverse each other's application direction. Migrating requires checking signatures, metadata and supported declaration kinds, not swapping decorator lines by habit. Also, a standard field's initial expression is evaluated even when a transformer returns a constant; its side effects have not disappeared.

### 5) **Performance note**

A definition creates the replacement wrappers; calls execute the installed chain. The stack does not allocate a fresh wrapper chain on every invocation. Reordering a short-circuiting cache or guard can skip inner work, so equal decorator counts do not imply equal runtime cost. Extra initializers run at the points shown above and can themselves allocate or perform expensive work. Assess the actual policies and workload rather than assigning a universal cheapness or maximum readable stack depth.

### 6) **Mentor note**

Have the learner predict all three traces before execution. Then swap `plus` and `times`, and explain why the result changes from `40` to `31` while both hooks still observe the final value. For methods, remove `finally` and predict the throwing path. A sound review describes evaluation, application, invocation and initialization separately, and tests the order that the application's policy actually requires.
