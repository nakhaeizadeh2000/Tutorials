## 1.1. TC39 standard decorators — classes, methods, fields

### 1) **What `@dec` means in TS 5.0+** (functions receiving target + context)

**Definition** — a standard decorator is a *function* called with the decorated value and a context object: class decorators receive `(target, context)` where context has `kind: "class"` + `name` + `metadata`; method decorators receive the method function + `{ kind: "method", name, static, private }`; field decorators receive `undefined` + `{ kind: "field", name }` plus initializer access. No flag needed (TS 5.0+) — standard decorators are plain language, not experimental syntax.

**What problem it solves / history** — legacy experimental decorators (TS 1.6+, `experimentalDecorators` flag, `(target, key, descriptor)` signature) were TypeScript-proprietary — TC39 standardized a *different* proposal (2022, stage 3) with incompatible signatures, splitting the ecosystem (Angular/NestJS on legacy; new code on standard). TS 5.0 implemented standard decorators flag-free: new code writes the portable form, legacy code migrates per [2.1. Legacy compared](<../2. Legacy and Metadata/2.1. Legacy experimental decorators compared.md>).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), write all new decorators in standard form (no flag, portable across transpilers supporting the proposal); type decorator signatures precisely (class/method/field contexts differ — one generic `Function` type fits none well); keep decorators additive (observe/wrap/register — never silently rewrite contracts, see [4.1. Checklist](<../4. Important points to remember/4.1. Decorators checklist mental models mentors insist on.md>)).

**Runnable example** — standard signatures on three targets (`tsc --strict`, no flag):

```typescript
// good — class decorator: receives constructor, returns extended subclass
function sealed<T extends new (...args: any[]) => object>(target: T, context: ClassDecoratorContext<T>): T {
  void context; // kind === "class" (metadata/name available here — see 2.3)
  return class extends target {
    constructor(...args: any[]) { // mixin rule: subclass ctor takes single ...args: any[] (verified against TS2545)
      super(...args);
      Object.seal(this); // instances sealed (additive behavior, contract preserved)
    }
  };
}
@sealed
class Point {
  constructor(public x: number) {}
}
console.log(new Point(1).x.toFixed(0)); // 1 — decorated class constructs normally (behavior added, shape kept)
```

```typescript
// good — method decorator: receives function + context, returns wrapped function
function logged<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Ret>,
): (this: This, ...args: Args) => Ret {
  const name = String(context.name);
  return function (this: This, ...args: Args): Ret {
    console.log(`call:${name}`); // around-advice (observe + delegate — signature preserved exactly)
    return fn.apply(this, args);
  };
}
class Calc {
  @logged
  add(a: number, b: number): number { return a + b; }
}
console.log(new Calc().add(2, 3).toFixed(0)); // call:add \n 5 — wrapped transparently
```

```typescript
// good — field decorator: observes initializer via context.addInitializer, transforms via return
function upper(value: undefined, context: ClassFieldDecoratorContext<object, string>): (this: object) => string {
  void value; // fields receive undefined (initializer accessed via context, not value)
  context.addInitializer(function (this: { tag?: string }) {
    this.tag = `field:${String(context.name)}`; // initializer hook (runs per instance, post-construction fields set)
  });
  return function (this: object): string { return "FIXED"; }; // replacement initializer (runs instead of declared one)
}
class Rec {
  @upper tag = "orig";
}
console.log(new Rec().tag.toUpperCase()); // FIXED — field decorator replaced the initializer (documented interception)
// bad — field decorators mutating shared state at definition time (definition runs once; instances many — scope confusion)
// fix — addInitializer (per-instance hooks) for instance behavior; definition-time work only for registration
```

**Common confusion** — "`@dec` without parens vs `@dec()` are identical" — `@dec` passes the decorator itself (receives target+context directly); `@dec()` *calls a factory first* (factory return receives target+context — arguments captured per use; see 1.2 promise 2). "standard decorators work under `experimentalDecorators`" — separate proposals (flag enables *legacy* semantics; standard needs no flag — mixing forms in one file confuses both checkers and readers; migrate fully per 2.1). "field decorators receive the value" — receive `undefined` (no instance exists at decoration) — initializer functions (returned or via `addInitializer`) carry per-instance behavior.

**Performance note** — decoration runs once per class definition (module load — negligible); wrapped methods add one closure call per invocation (same as higher-order wrappers — the cost of observation, identical to manual composition). Field initializers via decorators cost one extra function call per instance field (trivial vs construction).

**Mentor note** — hover each decorator's parameters (`target` + `context` shapes per kind) — three kinds, three signatures, one pattern (value + context). Exercise: convert one legacy decorator to standard by mapping parameters (`target/key/descriptor` → `value/context`) — the signature migration made mechanical. Review gate: untyped decorator signatures (`Function`, `any`) fail review (precise context types exist per kind).

### 2) **Class decorators** (wrapping constructors, registration, sealing)

**Definition** — class decorators receive the constructor and return (optionally) a replacement: same-shape subclass (behavior added — logging construction, sealing instances, attaching metadata), or `void` (observation/registration only — route tables, plugin lists, test collectors built without touching the class body).

**What problem it solves / history** — cross-cutting class concerns (registration in frameworks, sealing value objects, emitting metadata for DI) previously needed explicit post-class calls (`register(Foo); seal(Foo);`) after every declaration — steps forgotten per class, in exactly the files reviewers skimmed. Class decorators co-locate the concern *with* the declaration (`@register @sealed class Foo`) — impossible to declare without decorating, impossible to forget.

**Modern guidance** — as of TypeScript 5.9 era, use class decorators for registration (framework tables), sealing/freezing (value-object integrity), and metadata attachment (2.3's channel); return same-typed subclasses (additive — constructor signature preserved so `new` call sites never change); observe-only (return `void`) where no wrapping is needed (registration pure).

**Runnable example** — registration + sealing (good vs bad, `tsc --strict`):

```typescript
// good — registration at declaration (no central list to forget)
const registry = new Map<string, new () => object>();
function plugin(name: string) {
  return function <T extends new () => object>(target: T): T { // factory: argument captured per use (see 1.2)
    registry.set(name, target);
    return target; // unchanged (observe-only — registration pure, class untouched)
  };
}
@plugin("circle")
class Circle { constructor(public r = 1) {} }
console.log(registry.has("circle"), new Circle().r.toFixed(0)); // true 1 — declared once, registered automatically
// bad — central plugin list maintained by hand (new classes forgotten monthly — registry/checksum drift)
// fix — @plugin at each declaration (registration co-located, drift impossible by construction)
```

```typescript
// good — sealing via subclass (instances frozen by construction contract)
function frozen<T extends new (...args: any[]) => any>(target: T): T {
  return class extends target {
    constructor(...args: any[]) { // mixin rule (see promise 1): subclass ctor takes ...args: any[]
      super(...args);
      Object.freeze(this); // integrity: instances immutable post-construction (additive guarantee)
    }
  };
}
@frozen
class Cfg {
  constructor(public host = "h") {}
}
const c = new Cfg();
console.log(c.host.toUpperCase()); // H — frozen instance behaving identically (guarantee added, shape kept)
// bad — Object.freeze per construction site (forgotten per site — integrity scattered instead of declared)
// fix — @frozen on the class (guarantee travels with the declaration, not per new-expression)
```

```typescript
// good — metadata attachment for framework consumers (data, not behavior — see 2.3 full treatment)
function tag(name: string) {
  return function <T extends new (...args: any[]) => object>(target: T, context: ClassDecoratorContext<T>): T {
    if (context.metadata) context.metadata["tag"] = name; // attached (framework reads Class[Symbol.metadata].tag later)
    return target;
  };
}
@tag("entity")
class User {}
console.log("tagged"); // metadata attached at definition (consumed by frameworks, invisible to business logic)
// bad — static side-channel properties (User.tag = "entity" post-declaration — separable, forgettable, untyped)
// fix — decorator attachment (co-located, typed via metadata channel, consumed uniformly)
```

**Common confusion** — "returning a subclass breaks `instanceof`" — subclass instances pass `instanceof` for *both* base and subclass (prototype chain extended, not replaced) — `instanceof` checks widen safely. "registration decorators execute per instance" — execute once *per class definition* (module load) — instance-count-independent (registration cost O(classes), never O(instances)). "factories and plain decorators interchange" — `@dec` (direct — no arguments) vs `@dec(x)` (factory capturing `x` per use) — factories for parameterized decoration, plain for fixed.

**Performance note** — class decoration runs once per definition (registration map insert / subclass creation at module load — negligible); subclassing adds one prototype link per hierarchy level (method lookup unaffected measurably); sealed/frozen instances optimize identically in JITs (shapes stable post-construction).

**Mentor note** — delete one `@plugin` and watch the registry test fail (registration-by-declaration proven by absence) — co-location made visible via removal. Exercise: convert three post-declaration `register(X)` calls to decorators and delete the central list — drift vectors deleted per conversion. Review gate: post-declaration registration/sealing calls fail review (decorate at declaration).

### 3) **Method and field decorators** (wrapping functions, transforming initializers)

**Definition** — method decorators wrap functions (logging, timing, memoization, access control — around-advice preserving signatures); field decorators intercept initializers (validation, transformation, observation — definition-time registration plus per-instance hooks). Methods: same-signature replacement (or `void` for pure observation). Fields: replacement initializer *or* `addInitializer` hooks (never direct value access — no instance exists yet).

**What problem it solves / history** — cross-cutting member concerns (timed methods, validated fields, logged calls) previously needed manual wrapper assignment (`Foo.prototype.m = timed(Foo.prototype.m)` — post-hoc, fragile, invisible at declaration) or base-class machinery (inheritance for what should be annotation). Member decorators co-locate the concern *with* the member (`@timed m()`, `@Min(0) x`) — visible, composable, removable per member.

**Modern guidance** — as of TypeScript 5.9 era, decorate members for observation/transformation (timing, logging, validation rules, memoization — see 3.1/3.2's full patterns); preserve signatures exactly (wrapper accepts/returns the same types — contract-preserving by construction); prefer `addInitializer` for per-instance field effects (definition-time returns serve registration; instance effects need hooks).

**Runnable example** — wrap methods, intercept fields (good vs bad, `tsc --strict`):

```typescript
// good — timed method (signature preserved, behavior observed)
function timed<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Ret>,
): (this: This, ...args: Args) => Ret {
  void context;
  return function (this: This, ...args: Args): Ret {
    const t0 = Date.now();
    const out = fn.apply(this, args);
    console.log(`took:${Date.now() - t0}ms`);
    return out; // same Ret (contract preserved — timing purely additive)
  };
}
class Svc {
  @timed
  work(n: number): number { return n * 2; }
}
console.log(new Svc().work(21).toFixed(0)); // took:0ms \n 42 — observed without contract change
```

```typescript
// good — validated field via initializer hook (per-instance, post-construction timing correct)
const MIN_RULES = new Map<string, number>();
function min(n: number) {
  return function (value: undefined, context: ClassFieldDecoratorContext<object, number>): void {
    void value;
    MIN_RULES.set(String(context.name), n); // rule registered at DEFINITION time (schema built once)
  };
}
class Form {
  @min(0) age = 5; // rule attached (validation runs via schema + instance — see 3.1 full pattern)
}
console.log(new Form().age.toFixed(0), MIN_RULES.get("age")); // 5 0 — value intact, rule collected
// bad — validating inside the field decorator directly (definition-time: no instance exists — rules evaluated against undefined)
// fix — register at definition (schema), validate against instances (3.1's two-phase pattern)
```

```typescript
// good — observation-only method decorator (void return — no wrapping, pure telemetry hook)
function calls<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Ret>,
): void {
  void fn; // observed (counted/registered), NOT wrapped (zero behavior change — telemetry pure)
  void context;
  console.log("method-observed");
}
class Api {
  @calls
  fetch(): string { return "data"; }
}
console.log(new Api().fetch()); // method-observed \n data — observation without interception (cheapest decoration)
// bad — wrapping where observing suffices (closure per method for zero behavior delta — indirection without purpose)
// fix — void-returning decorators for telemetry (observe); function-returning for interception (wrap)
```

**Common confusion** — "wrappers change `this`" — standard wrappers receive explicit `this` types (`This` generic threaded — `fn.apply(this, args)` preserves receivers; arrow-function wrappers would *capture* `this` wrongly — always `function`). "field decorators see values" — see `undefined` + context (values don't exist at definition) — initializer *functions* (returned or hooked) carry per-instance behavior. "void vs function return interchanges" — `void` = observe-only (no interception possible); function = intercept (replacement runs instead) — choose by intent (telemetry vs transformation).

**Performance note** — wrapped methods add one closure per call (same as manual higher-order wrapping — observation cost identical to composition); void-observed methods cost zero per call (no wrapper installed — telemetry free); field hooks run once per instance-field (initializer chain — trivial vs construction).

**Mentor note** — implement the same timing *manually* (`Svc.prototype.work = timed(...)`) beside `@timed` — identical mechanics, co-located declaration winning on visibility. Exercise: convert three manual prototype-wraps to decorators and delete the post-hoc assignments — declaration-site visibility in one diff. Review gate: post-hoc `Prototype.method = wrap(...)` assignments fail review (decorate at declaration).
