## 1.1. TC39 standard decorators — classes, methods, fields

### 1) **The decorated value and its context**

A decorator is a function that runs while a class is defined. It receives the value being decorated and a context describing that declaration. It can return a permitted replacement, register initialization work, or leave the value unchanged. This lets a declaration name a reusable policy such as logging. A normal function call or an explicit class factory is often easier to follow when declaration-site annotation adds little.

This lesson uses **TypeScript 7.0.2**, with `experimentalDecorators` omitted, and runs emitted JavaScript on **Node.js 20.20.2**. TypeScript introduced this decorator model in 5.0. “Standard decorators” names the model based on the TC39 proposal; it does not promise finalized ECMAScript syntax or native support in every runtime. The [current proposal](https://github.com/tc39/proposal-decorators) remains work in progress. Choose a framework's required model before writing its decorators. The [TypeScript 5.0 notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html) distinguish this model from the legacy flag, including the absence of standard parameter decorators and incompatibility with `emitDecoratorMetadata`.

| Declaration | First argument | Context `kind` | Permitted return |
|---|---|---|---|
| Class | Constructor | `class` | Compatible constructor or `void` |
| Method | Method function | `method` | Compatible function or `void` |
| Getter or setter | That individual function | `getter` or `setter` | Compatible function or `void` |
| Field | `undefined` | `field` | Initial-value transformer or `void` |
| Auto-accessor | Object with `get` and `set` | `accessor` | Object with optional `get`, `set`, `init`, or `void` |

The context types, such as `ClassMethodDecoratorContext`, expose the contract for that kind. Member contexts distinguish static and private members. Context access functions let later code read or write an appropriate receiver; they do not manufacture an instance during decoration. Metadata has a separate runtime setup and consumer, explained in [2.3](<../2. Legacy and Metadata/2.3. Symbol.metadata and the metadata proposal.md>).

`@logged` supplies the decorator function directly. `@logged("service")` first calls a factory whose result must be a decorator. The factory argument configures that use; the context still comes from the class definition. Stacking and factory evaluation order belong to [1.2](<./1.2. Decorator evaluation and application order.md>).

Save the following independent files in an empty directory. No packages are required beyond the stated compiler and runtime. Compile all five with:

```bash

node dist/identity.mjs
node dist/methods.mjs
node dist/fields.mjs

```

The `.mts` files produce `.mjs` modules. Run these commands from a directory without another `tsconfig.json`. The examples test this compiler's emitted artifacts; using a different transpiler requires checking its decorator version and behavior.

### 2) **Class replacement changes identity**

A class decorator can observe the original constructor or return a replacement. Returning a subclass retains its inherited instance methods, but changes the constructor value bound to the class name. Here the input contract intentionally covers only a zero-argument service with `run`; it is not a general mixin helper.

```typescript
// file: identity.mts
type ServiceClass = new () => { run(): string };
let original: ServiceClass | undefined;
function replace(value: ServiceClass, context: ClassDecoratorContext<ServiceClass>): ServiceClass {
  if (context.kind !== "class") throw new Error("class required");
  original = value;
  return class extends value {};
}
@replace
class Service {
  run(): string { return "ok"; }
}
if (!original) throw new Error("decorator did not run");
console.log(Service === original, new Service() instanceof original, new Service().run());
// false true ok
```

The decorator runs before any instance is constructed. A subclass instance passes the original constructor's `instanceof` test because its prototype chain includes the original prototype. This observation does not prove every replacement preserves private static access, identity-based registries, or external contracts. New members supplied by a decorator also do not automatically become members of the declared class type.

Returning `void` leaves the constructor value in place, but a decorator can still perform side effects. Registering a constructor changes a registry. Co-location makes registration visible; it cannot make omitted annotations or unimported modules impossible. [1.3](<./1.3. Practical class decorators registration and mixins.md>) owns registration and class composition.

### 3) **Method wrappers forward a call**

A method replacement receives each invocation. Thread the receiver, argument tuple and result through its signature, and use a normal function so that its `this` comes from the call. This wrapper counts its own creation separately from its invocations.

```typescript
// file: methods.mts
let wrappers = 0;
let calls = 0;
function logged<This, Args extends unknown[], Result>(
  value: (this: This, ...args: Args) => Result,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Result>,
): (this: This, ...args: Args) => Result {
  wrappers++;
  const name = String(context.name);
  return function (this: This, ...args: Args): Result {
    calls++;
    console.log(`call:${name}`);
    return value.apply(this, args);
  };
}
class Calc {
  base = 10;
  @logged
  add(this: Calc, a: number, b: number): number { return this.base + a + b; }
}
const one = new Calc();
const two = new Calc();
console.log(one.add(2, 3));
const detached = two.add;
console.log(detached.call(two, 1, 1));
console.log(wrappers, calls, one.add === two.add);
// call:add
// 15
// call:add
// 12
// 1 2 true
// detached(1, 1); // TS2684: the explicit Calc receiver is missing
// one.add("2", 3); // TS2345: the argument must be a number
```

The two instances share the prototype method replacement. Calling `.call(two, ...)` supplies the receiver; the decorator does not bind it automatically. Its `.apply` preserves the receiver it was given. This synchronous wrapper returns the original result and lets thrown errors propagate. Its type signature alone does not prove that arbitrary logging, caching or asynchronous wrappers preserve behavior. Use [3.2](<../3. Patterns in Practice/3.2. Logging timing and memoization decorators.md>) for those policies, and the [receiver lesson](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.1. this parameter explicit typing and arrow vs function capture.md>) for callback contracts.

A decorator that only logs inside its definition-time body observes a method declaration. It cannot count later calls without installing call-time behavior. Returning `void` is therefore suitable for declaration registration, not a substitute for per-call telemetry.

### 4) **Field transformation precedes its extra hook**

For a field, the decorator receives `undefined`, not its initial value. A returned initializer receives the result of the declared field expression and returns the value to store. The declared expression still executes. A field's `addInitializer` callback runs after that field is initialized; later fields and the constructor body can still be pending. The [proposal's initialization rules](https://github.com/tc39/proposal-decorators#adding-initialization-logic-with-addinitializer) distinguish this from method and class hooks.

```typescript
// file: fields.mts
const events: string[] = [];
let sourceCalls = 0;
function source(): string {
  sourceCalls++;
  events.push("source");
  return "orig";
}
function upper<This extends object>(
  value: undefined, context: ClassFieldDecoratorContext<This, string>,
): (this: This, initial: string) => string {
  events.push(`decorate:${value === undefined}`);
  context.addInitializer(function (this: This) {
    events.push(`hook:${context.access.get(this)}:${Object.hasOwn(this, "after")}`);
  });
  return function (this: This, initial: string): string {
    events.push(`transform:${initial}`);
    return initial.toUpperCase();
  };
}
class RecordValue {
  @upper label = source();
  after = "later";
  constructor() { events.push(`body:${this.label}:${this.after}`); }
}
const first = new RecordValue();
const second = new RecordValue();
console.log(first.label, second.label, sourceCalls);
console.log(events.join("|"));
// ORIG ORIG 2
// decorate:true|source|transform:orig|hook:ORIG:false|body:ORIG:later|source|transform:orig|hook:ORIG:false|body:ORIG:later
```

Decoration occurs once, but the declared expression, returned transformer and extra hook run for each construction. `hook:ORIG:false` proves that the hook sees the transformed field while `after` is not yet an own property. A hook that writes `label` again would overwrite `ORIG`; it would not run before the returned transform. Full-object validation should run at an explicit point when the needed object state exists. [3.1](<../3. Patterns in Practice/3.1. Validation decorators field rules.md>) owns rule storage and validation.

### 5) **Auto-accessors and freezing have different boundaries**

An auto-accessor has a prototype getter/setter backed by storage. Its decorator receives those functions, and can return an `init` function to transform the first stored value. Omitting a replacement setter keeps normal subsequent assignment behavior.

```typescript
// file: accessors.mts
function doubleInitial<This>(
  value: ClassAccessorDecoratorTarget<This, number>,
  context: ClassAccessorDecoratorContext<This, number>,
): ClassAccessorDecoratorResult<This, number> {
  void value;
  void context;
  return { init(initial: number): number { return initial * 2; } };
}
class Counter {
  @doubleInitial accessor amount = 3;
}
const counter = new Counter();
console.log(counter.amount, Object.hasOwn(counter, "amount")); // 6 false
counter.amount = 4;
console.log(counter.amount); // 4
```

An ordinary public field is an own data property. An auto-accessor's public name here is on the prototype. Transforming an initial value does not validate all later writes. A setter policy would be a separate decision.

Likewise, freezing an instance inside a replacement constructor is an observable restriction. It can break a further subclass whose field is initialized after `super()`:

```typescript
// file: freeze.mts
function freezeInstance(value: new () => object): new () => object {
  return class extends value {
    constructor() { super(); Object.freeze(this); }
  };
}
@freezeInstance
class Base {}
class Derived extends Base { extra = 1; }
console.log(Object.isFrozen(new Base())); // true
try { new Derived(); }
catch (error) { console.log(error instanceof TypeError); } // true
```

The derived field cannot be defined on the frozen object. Freezing also remains shallow. Neither a compatible constructor type nor the decorator syntax makes this policy universally additive or deeply immutable. Choose it only with an explicit construction and subclassing contract; the fuller class pattern belongs to [1.3](<./1.3. Practical class decorators registration and mixins.md>).

### 6) **Common confusion**

Omitting `experimentalDecorators` selects this compiler model; enabling it selects legacy behavior. It does not mean a runtime parses `@` directly. In a separate check, TypeScript 7.0.2 accepted `methods.mts` with `isolatedModules`, `verbatimModuleSyntax` and `erasableSyntaxOnly`, while native Node.js 22.18.0 rejected that source with a syntax error. These compiler options do not certify decorator support in the runtime parser. Run the emitted `.mjs` files with the declared commands.

A field decorator's `undefined` argument is an API contract. It does not show that the later field expression evaluates to `undefined`. Also, `addInitializer` is not a general “after construction” hook: its timing depends on the decorated kind. Predict the exact read point before accessing another field.

### 7) **Performance note**

The method example creates one replacement function when its class is defined and invokes it twice. It does not create a new wrapper closure for each call. The rest parameter and logging are additional runtime work, and each construction runs the decorated field's transformation and hook. A class expression evaluated repeatedly would also repeat decoration. These observations identify where work happens; they do not establish negligible overhead, JIT equivalence, or a universal cost relative to manual composition. Measure the chosen wrapper and workload if that cost matters.

### 8) **Mentor note**

Ask the learner to predict whether `source()` still runs, and whether `after` exists during the field hook. Then remove the returned transformer while retaining the hook and explain the changed trace. A correct answer separates definition-time invocation, original expression evaluation, transformation, storage and the extra callback. For method review, ask who supplies `this` and whether the policy changes return values, error propagation or asynchronous completion.
