## 1.3. Practical class decorators — registration and mixins

### 1) **Register the constructor the consumer will use**

A registration decorator associates a class with a lookup key when its definition is evaluated. It can keep the registration policy near the class. It still requires the defining module to execute, a collision policy for duplicate keys, and a checked lookup for missing keys. An explicit registration list is also a valid design when visible startup assembly or test isolation matters more than annotation locality.

The examples use **TypeScript 7.0.2** standard-form decorators (`experimentalDecorators` omitted) and emitted modules on **Node.js 20.20.2**. Create an empty directory without a `tsconfig.json` and save all seven named files below. No external libraries are needed. Compile and run:

```bash
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --outDir dist registry.mts handler.mts absent.mts present.mts mixin.mts sealed.mts frozen.mts
node dist/absent.mjs
node dist/present.mjs
node dist/mixin.mjs
node dist/sealed.mjs
node dist/frozen.mjs
```

The registry intentionally supports zero-argument handlers. It is an in-process demonstration, not an HTTP router or a dependency-injection container. A class extra initializer uses `this` to register the final constructor after class decoration and static initialization, following the [proposal's class initializer rule](https://github.com/tc39/proposal-decorators#adding-initialization-logic-with-addinitializer).

```typescript
// file: registry.mts
export type Handler = new () => { handle(): string };
export const routes = new Map<string, Handler>();
export const inputs = new Map<string, Handler>();
export function route(path: string) {
  return function <Value extends Handler>(value: Value, context: ClassDecoratorContext<Value>): void {
    inputs.set(path, value); // Observe the input before a later decorator replaces it.
    context.addInitializer(function (this: Value) {
      if (routes.has(path)) throw new Error(`duplicate:${path}`);
      routes.set(path, this);
    });
  };
}
export function resolve(path: string): Handler {
  const found = routes.get(path);
  if (!found) throw new Error(`missing:${path}`);
  return found;
}
```

The route decorator applies before `wrap`, because it is lower in the stack. Its input is therefore the original class. Its deferred class initializer runs with the final replacement constructor as `this`.

```typescript
// file: handler.mts
import { route, type Handler } from "./registry.mjs";
function wrap(value: Handler): Handler {
  return class extends value {
    override handle(): string { return "wrapped:" + super.handle(); }
  };
}
@wrap
@route("/a")
export class A {
  handle(): string { return "A"; }
}
```

```typescript
// file: absent.mts
import { routes, resolve } from "./registry.mjs";
console.log(routes.size); // 0: handler.mjs has not been imported in this process.
try { resolve("/a"); }
catch (error) { console.log(error instanceof Error ? error.message : "unexpected"); }
// missing:/a
```

```typescript
// file: present.mts
import { A } from "./handler.mjs";
import { routes, inputs, resolve, route } from "./registry.mjs";
const Handler = resolve("/a");
console.log(routes.size, Handler === A, Handler === inputs.get("/a"), new Handler().handle());
// 1 true false wrapped:A
try {
  @route("/a")
  class Duplicate { handle(): string { return "duplicate"; } }
  void Duplicate;
} catch (error) {
  console.log(error instanceof Error ? error.message : "unexpected");
}
console.log(new (resolve("/a"))().handle());
// duplicate:/a
// wrapped:A
```

Each `node` command starts a fresh process. The absent entry has an empty registry; the present entry evaluates the handler module and registers its final class. The duplicate definition throws without replacing the original route. A plain `Map<string, Handler>` gives typed values but cannot prove that an arbitrary string is present. The explicit `resolve` check establishes that before construction.

Exercise: register `value` immediately inside the decorator instead of scheduling `routes.set(path, this)`. The input and registry identity then match, while the registry no longer holds `A`'s replacement and dispatch returns `A` instead of `wrapped:A`. This is why a registry must specify which constructor identity it stores. [Module cycles and registration](<../../../12 Modules Namespaces and Declaration Files/sections/5. Common pitfalls to production bugs/5.1. Real production bugs caused by module misunderstandings.md>) owns entry-point and import-graph failures. Bundler retention additionally depends on its side-effect analysis and configuration; annotation alone does not promise removal or retention.

### 2) **Choose the statically exposed composition contract**

A decorator may return a subclass with additional runtime state, but the class declaration's exposed type does not automatically gain those members. An explicitly called mixin factory can expose its inferred result. The following small comparison uses the same transformation both ways; the general mixin implementation and constructor constraints belong to [06/3.2](<../../../06 Classes and Object-Oriented Types/sections/3. Advanced Class Patterns/3.2. Mixins and class composition without inheritance.md>).

```typescript
// file: mixin.mts
type Constructor = new (...args: any[]) => object;
function Stamped<Base extends Constructor>(value: Base) {
  return class extends value { born = "ready"; };
}
@Stamped
class Decorated {
  title: string;
  constructor(title: string) { this.title = title; }
}
const decorated = new Decorated("doc");
console.log(decorated.title, Reflect.get(decorated, "born")); // doc ready
// decorated.born; // TS2339: decorating does not add born to the declared instance type.
class Plain {
  title: string;
  constructor(title: string) { this.title = title; }
}
const Explicit = Stamped(Plain);
const explicit = new Explicit("note");
console.log(explicit.title, explicit.born); // note ready
console.log(explicit instanceof Plain, new Plain("base") instanceof Explicit); // true false
// new Explicit(); // TS2554: the base constructor still requires title.
function optionalStamp(enabled: boolean) {
  return function <Base extends Constructor>(value: Base): Base {
    return enabled ? Stamped(value) : value;
  };
}
@optionalStamp(false)
class Off {}
@optionalStamp(true)
class On {}
console.log(Reflect.has(new Off(), "born"), Reflect.has(new On(), "born")); // false true
```

Reflection here deliberately observes a runtime property without asserting that it is in the declared type. Calling `Stamped(Plain)` exposes `born` through inference and preserves the required constructor argument. A derived instance matches the base's `instanceof` check; an original base instance does not thereby become an instance of the subclass. The actual chain has a direction.

Conditional behavior is possible in a decorator factory: `optionalStamp(false)` returns a decorator that leaves its input unchanged. An explicit factory call can still be clearer when conditional composition is central to the design or callers need the added member's type. Choose from the public contract and startup behavior, rather than treating annotation as an interchangeable spelling of `extends`.

### 3) **Specify which object is sealed or frozen**

A class has a constructor object, a prototype object and instances created later. Integrity operations act on the object passed to them. Sealing the first two does not seal the third, and it does not forbid extending the class. [Object.seal](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/seal) makes existing properties non-configurable and prevents adding properties; writable properties can still change. The [TypeScript class-decorator example](https://www.typescriptlang.org/docs/handbook/decorators.html#class-decorators) also explicitly warns that sealing does not prevent subclassing. That older page teaches legacy signatures; only the stated object/type distinction is reused here, with this lesson's standard-model code verified separately.

```typescript
// file: sealed.mts
function sealSurface<Value extends new () => object>(value: Value): void {
  Object.seal(value);
  Object.seal(value.prototype);
}
@sealSurface
class Api {
  count = 1;
  version(): string { return "v1"; }
}
class Child extends Api { extra = 2; }
const child = new Child();
console.log(Object.isSealed(Api), Object.isSealed(Api.prototype), Object.isSealed(child));
console.log(child.extra, Reflect.set(Api, "newStatic", 1));
console.log(Reflect.set(Api.prototype, "version", function (): string { return "patched"; }));
Object.defineProperty(child, "added", { value: 3 });
console.log(child.version(), Reflect.get(child, "added"));
// true true false
// 2 false
// true
// patched 3
```

The child is constructed normally, the new static property is rejected, and an existing writable prototype method is replaced. A new instance property is also permitted. Calling this policy “no subclassing” or “immutable instances” would describe behavior it does not enforce.

Freezing an instance changes a different boundary. It does not recursively freeze referenced objects or freeze private state. This wrapper intentionally supports a concrete zero-argument constructor and uses the usual generic mixin constructor forwarding.

```typescript
// file: frozen.mts
function freezeInstances<Value extends new (...args: any[]) => object>(value: Value): Value {
  return class extends value {
    constructor(...args: any[]) { super(...args); Object.freeze(this); }
  };
}
@freezeInstances
class Config {
  count = 1;
  nested = { value: 2 };
  #secret = 3;
  setSecret(value: number): void { this.#secret = value; }
  getSecret(): number { return this.#secret; }
}
const config = new Config();
try { config.count = 9; } // The type permits this write; the runtime freeze rejects it.
catch (error) { console.log(error instanceof TypeError); }
config.nested.value = 4;
config.setSecret(5);
console.log(Object.isFrozen(config), Object.isFrozen(config.nested));
console.log(config.count, config.nested.value, config.getSecret());
// true
// true false
// 1 4 5
```

These are shallow property restrictions, as described by [Object.freeze](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/freeze). `DeepReadonly` is a static transformation and performs no freezing. Also, freezing inside a base replacement constructor can make later derived fields throw, as the executed [1.1 example](<./1.1. TC39 standard decorators classes methods fields.md>) shows. Apply integrity at a construction boundary that matches the intended extension policy. An explicit freeze after assembling a final value may be easier to reason about than inherited constructor behavior.

### 4) **Common confusion**

A decorated class is registered only if its definition executes; decorating it does not import its module. Registration and dependency resolution are different jobs. The example maps a string to a zero-argument constructor, while a container must assemble dependencies and define lifetimes.

Returning a subclass changes the runtime constructor without automatically expanding the source class's public type. Sealing constructor/prototype objects permits subclasses and new instance properties. Freezing an instance prevents certain property writes, while nested objects and private state can still change. Review the particular target and operation rather than relying on names such as `sealed` or `immutable`.

### 5) **Performance note**

The registration callback and generated subclass are created during class definition; handler construction happens on lookup. The registry retains constructor references for as long as its map retains entries. Repeated definitions, reloads or independently assembled registries require deliberate ownership and cleanup. Freeze operations run per construction in this wrapper. No lookup bound, construction timing, JIT improvement or bundler retention was measured here. Prefer clear ownership, then measure the actual startup or dispatch workload if it matters.

### 6) **Mentor note**

Ask why `Handler === A` is true while `Handler === inputs.get("/a")` is false. Move registration into the decorator body and predict the changed dispatch result. Then ask which three objects `sealSurface` affects: a correct answer names the constructor and prototype, and identifies the untouched instance. Finish by choosing a decorator, explicit registration list, inferred mixin call or explicit final-object freeze for a concrete caller contract, with a reason tied to imports, types or construction timing.
