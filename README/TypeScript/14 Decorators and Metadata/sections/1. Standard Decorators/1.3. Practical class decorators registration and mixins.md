## 1.3. Practical class decorators — registration and mixins

### 1) **Registration pattern** (framework tables without central lists)

**Definition** — decorators adding classes to keyed registries at definition time (`Map` of route→handler class, name→plugin, test-name→suite): `@Route("/x") class H` inserts `H` under `"/x"` when the module loads — no central registry file enumerating classes, no forgotten registrations, no import-order coupling (registration follows module evaluation, which imports determine).

**What problem it solves / history** — central registries (`routes = [H1, H2, H3]`, plugin arrays, test-suite lists) drifted on every addition (new class working but unregistered — 404s for wired handlers, silent test skips) — the file everyone forgot ranked exactly with the feature's importance (critical features, unlisted). Decorator registration co-locates membership *with* the member: declaring the class registers it, deleting the class unregisters it — drift structurally impossible.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), register framework participants via decorators (routes, plugins, entities, tests, CLI commands); keep the registry typed (`Map<Key, Constructor>` — lookups checked, iterations typed); test registration (registry size/keys asserted per module — co-location verified, not assumed).

**Runnable example** — membership by declaration (good vs bad, `tsc --strict`):

```typescript
// good — route table built by declarations (no central list to forget)
type Ctor = new () => { handle(): string };
const routes = new Map<string, Ctor>();
function route(path: string) {
  return function <T extends Ctor>(target: T): T { // factory captures path per class (see 1.2 promise 2)
    routes.set(path, target);
    return target; // unchanged (observe-only registration — class untouched)
  };
}
@route("/a")
class A {
  handle(): string { return "A"; }
}
@route("/b")
class B {
  handle(): string { return "B"; }
}
console.log(routes.size, new (routes.get("/a")!)().handle()); // 2 A — declared twice, registered twice, listed nowhere
// bad — central routes array (new classes forgotten monthly — 404s for wired handlers, silent skips for tests)
// fix — @route per class (membership co-located — drift impossible by construction)
```

```typescript
// good — plugin registry with typed lookup (iteration + construction both checked)
interface Plug { label(): string } // named Plug: `Plugin` would merge with DOM lib's global Plugin interface
const plugins = new Map<string, new () => Plug>();
function plugin2(name: string) {
  return function <T extends new () => Plug>(target: T): T {
    plugins.set(name, target);
    return target;
  };
}
@plugin2("auth")
class Auth implements Plug {
  label(): string { return "auth"; }
}
console.log(plugins.has("auth"), new (plugins.get("auth")!)().label()); // true auth — typed registry (lookups construct checked instances)
// bad — stringly plugin names resolved via any-record (typos compile, missing plugins undefined-crash at dispatch)
// fix — Map<string, new () => Plugin> (lookups typed; get-checked before construct — see 10/3.1 Map discipline)
```

```typescript
// good — test collector without a suite list (suites self-register per file)
type Test = () => void;
const suite = new Map<string, Test>();
function test(name: string) {
  return function (fn: Test): Test { // function decorator (registers the test itself — no class needed)
    suite.set(name, fn);
    return fn; // unchanged (registration pure — test body untouched)
  };
}
const t1 = test("adds")(() => console.log(1 + 1)); // registered at definition (suite built by declaring)
console.log(suite.size, t1()); // 1 2 — declared once, collected automatically (central lists deleted permanently)
// bad — test(name, fn) central-suite calls per file (registration call + definition — two sites per test, one forgotten monthly)
// fix — @test / test() at definition (membership co-located — suites assemble themselves)
```

**Common confusion** — "registration order is controllable" — registration follows *module evaluation order* (import graph — deterministic per entry, varying per entry point; multi-entry apps register different subsets — test with the production entry, not the test entry). "decorated classes must be imported to register" — yes (unimported modules never evaluate — tree-shaking *removes* unreferenced decorated classes *and their registrations*; side-effect imports (`import "./plugins/auth"`) preserve intentional registration). "registries replace DI containers" — registries *map* (lookup by key); containers *resolve* (construct graphs with dependencies — see 3.3's DI treatment).

**Performance note** — registration costs one map insert per class at module load (negligible); lookups O(1) per dispatch (same as central lists); tree-shaking removes unreferenced registrations (registration follows reachability — dead code stays dead, including its table entries).

**Mentor note** — delete one `@route` and watch the route test 404 (registration-by-declaration proven by absence) — co-location made visible via removal. Exercise: convert one central registry (routes/plugins/tests) to decorator registration and delete the list file — drift vectors deleted per conversion. Review gate: post-declaration registration calls fail review (decorate at declaration).

### 2) **Decorator-driven mixins** (extended subclasses via annotation)

**Definition** — class decorators returning extended subclasses (`timestamped(Base)` as `@timestamped class X`) compose behavior via annotation — the 06/3.2 mixin pattern in declarative form: `class X` declares *what* (its own members), `@timestamped` adds *when-created tracking* (or logging, validation hooks, serialization). Same subclassing mechanics as function mixins; annotation syntax instead of call syntax.

**What problem it solves / history** — mixin call syntax (`class X extends Timestamped(Base)`) composed well but read inside-out (innermost mixin listed first in nesting, last in comprehension) and reordered by rewriting expressions. Decorator mixins linearize vertically (`@logged @timestamped class X` — top-down reading, move-to-reorder, delete-to-remove) with identical subclass mechanics underneath.

**Modern guidance** — as of TypeScript 5.9 era, prefer decorator mixins for *annotative* composition (cross-cutting: timestamped, logged, validated — declared intent per class); prefer function mixins for *programmatic* composition (conditional application, parameterized bases, mixin factories — logic over annotation). Both obey the mixin constraint (`...args: any[]` constructors — see 1.1's TS2545 rule); both preserve `instanceof` both directions.

**Runnable example** — annotation vs call composition (good vs bad, `tsc --strict`):

```typescript
// good — decorator mixin: vertical composition, move-to-reorder readability
function stamped<T extends new (...args: any[]) => object>(target: T): T { // re-declared: fences compile standalone (mixin constraint TS2545-safe)
  return class extends target {
    constructor(...args: any[]) {
      super(...args);
      (this as unknown as Record<string, unknown>)["born"] = Date.now(); // added behavior (timestamp tracking)
    }
  };
}
@stamped
class Doc {
  constructor(public title = "d") {}
}
const d = new Doc();
const dRec = d as unknown as Record<string, unknown>;
console.log(d.title.toUpperCase(), typeof dRec["born"]); // D number — composed via annotation
// bad — class Doc extends stamped(Object) (call composition: inside-out reading, reorder-by-rewriting)
// fix — @stamped (vertical: top-down reading, move-to-reorder, delete-to-remove — identical mechanics underneath)
```

```typescript
// good — stacked decorator mixins compose like stacked calls (bottom-up application per 1.2)
function stampedB<T extends new (...args: any[]) => object>(target: T): T { // local copy (fences compile standalone)
  return class extends target {
    constructor(...args: any[]) {
      super(...args);
      (this as unknown as Record<string, unknown>)["born"] = Date.now();
    }
  };
}
function tagged(tag: string) {
  return function <T extends new (...args: any[]) => object>(target: T): T {
    return class extends target {
      constructor(...args: any[]) {
        super(...args);
        (this as Record<string, unknown>)["tag"] = tag; // per-site capture (factory form — see 1.2 promise 2)
      }
    };
  };
}
@tagged("v2")
@stampedB
class Rec4 {
  constructor(public n = 0) {}
}
const r4 = new Rec4();
const r4rec = r4 as unknown as Record<string, unknown>;
console.log(r4rec["tag"], typeof r4rec["born"]); // v2 number — stacked mixins (application bottom-up: stamped inner, tagged outer)
// bad — mixin factories without constraints (TS2545 on first generic base — constraint is load-bearing, not ceremonial)
// fix — <T extends new (...args: any[]) => object> on every mixin (constraint + any[] ctor, verified in 1.1)
```

```typescript
// good — programmatic mixins where annotation doesn't fit (conditional application)
function stamped2<T extends new (...args: any[]) => object>(target: T): T { // local copy (fences compile standalone)
  return class extends target {};
}
function maybeStamp<T extends new (...args: any[]) => object>(target: T, on: boolean): T {
  return on ? stamped2(target) : target; // conditional (annotation can't branch — call form can)
}
class Plain {}
const StampedPlain = maybeStamp(Plain, true); // programmatic choice (runtime flag deciding composition)
console.log(new StampedPlain() instanceof Plain); // true — instanceof preserved both directions (subclass mechanics)
// bad — @stamped with runtime conditionals (decorators apply unconditionally — conditional needs call form)
// fix — call form for programmatic composition (conditions, loops, factories); annotation for declarative composition
```

**Common confusion** — "decorator mixins differ mechanically from function mixins" — identical subclass mechanics (same constraints, same `instanceof`, same prototype chains) — syntax differs (annotation vs call), machinery doesn't. "stacked decorator mixins apply top-down" — bottom-up per 1.2 (closest applies first = innermost subclass — order matters for conflicting member definitions). "mixins replace inheritance" — mixins *are* inheritance (single-chain subclassing per application — diamond problems unsolved; composition depth still linear).

**Performance note** — one subclass level per decorator mixin (prototype chain +1 per application — method lookup unaffected measurably under shallow stacks); construction runs the chain (super-calls per level — trivial vs body work). Depth cost is readability (extract past 3–4 stacked mixins), never speed.

**Mentor note** — write one mixin both ways (call vs decorator) and diff (identical mechanics, vertical vs nested reading) — syntax choice made visible as readability, not magic. Exercise: convert one `extends Mixin(Base)` to `@mixin` and one conditional composition the other way (annotation ↔ call per fit) — direction judgment transfers. Review gate: conditional decorator application attempts fail review (call form for programmatic composition).

### 3) **Sealing and freezing via decorators** (integrity declared, not scattered)

**Definition** — `@sealed` (prevent subclassing — `Object.seal` on the constructor: no new statics, no prototype extension) and `@frozen`-instances (per 1.1 promise 2: freeze per construction) declare integrity *at the class*: value objects immutable by contract, API surfaces closed by contract — instead of `Object.seal/freeze` calls scattered per use site (forgotten per site, unenforced globally).

**What problem it solves / history** — integrity-by-convention (`// do not extend`, `// treat as immutable` comments) relied on every author reading every comment — subclasses appeared quarterly, mutations slipped through un-frozen paths. Declarative integrity converts convention to construction: sealed constructors *throw* (strict mode) or refuse extension structurally; frozen instances throw on write — violations fail loudly at the violating line, not silently in state.

**Modern guidance** — as of TypeScript 5.9 era, seal API-surface classes (plugin contracts, public base classes — extension points explicit via documented subclassing, closed by default); freeze value objects (money, coordinates, config snapshots — mutation is a bug class, not a feature); document the integrity choice on the class (`// sealed: extension via composition, not inheritance` — the reasoning travels with the declaration).

**Runnable example** — integrity by declaration (good vs bad, `tsc --strict`):

```typescript
// good — sealed constructor (extension refused structurally)
function sealed2<T extends new (...args: any[]) => object>(target: T): T {
  Object.seal(target); // constructor sealed (no new statics; prototype closed to extension)
  Object.seal(target.prototype); // instances' shape closed (no new methods post-definition)
  return target;
}
@sealed2
class Api {
  version(): string { return "v1"; }
}
console.log(new Api().version()); // v1 — sealed surface behaving identically (integrity added, shape kept)
// (Api as Record<string, unknown>)["extra"] = 1; // throws TypeError in strict mode (seal enforced, not suggested)
```

```typescript
// good — frozen value objects (mutation refused per instance)
function frozen2<T extends new (...args: any[]) => object>(target: T): T {
  return class extends target {
    constructor(...args: any[]) {
      super(...args);
      Object.freeze(this); // per-instance freeze (value-object integrity by construction contract)
    }
  };
}
@frozen2
class Money {
  constructor(public cents = 0) {}
}
const m = new Money(100);
console.log(m.cents.toFixed(0)); // 100 — frozen value behaving identically (reads unaffected, writes refused)
// (m as Record<string, unknown>)["cents"] = 0; // throws TypeError (frozen — mutation is the bug class deleted)
// bad — freeze-per-use-site (forgotten per site — integrity scattered instead of declared)
// fix — @frozen on the class (guarantee travels with the declaration, not per new-expression)
```

```typescript
// good — integrity documented where declared (reasoning travels with the class)
/// Sealed: extend via composition (wrap Api, don't subclass — surface closed deliberately).
// (doc comment on @sealed2 classes states the extension story — reviewers audit the story, not just the decorator)
class Documented {
  describe(): string { return "doc"; }
}
console.log(new Documented().describe()); // doc — documented integrity (convention + construction, composed)
// bad — unexplained seals (future authors unseal "to unblock" without understanding the contract — documentation prevents)
// fix — reason comments on every integrity decorator (why sealed/frozen + what to do instead — the story preserved)
```

**Common confusion** — "sealing prevents all extension" — `Object.seal` prevents *structural* extension (new properties) — subclassing a sealed *constructor* still type-checks (seal the prototype chain deliberately where subclassing itself is banned — or document composition-over-inheritance). "frozen objects are deeply immutable" — shallow (nested objects mutable — deep-freeze or `DeepReadonly` types per 09/3.1 for nested integrity). "integrity decorators slow construction" — seal/freeze run once per class/instance (microseconds — the mutation bugs they delete cost post-mortems).

**Performance note** — sealed/frozen shapes optimize identically-or-better in JITs (stable hidden classes — integrity *helps* optimization); per-instance freeze costs one call per construction (trivial vs body work). Integrity is performance-neutral-to-positive, incident-negative always.

**Mentor note** — attempt the forbidden write live (strict-mode throw on sealed/frozen targets) — enforcement demonstrated beats convention described. Exercise: convert three freeze-per-site call clusters to `@frozen` classes and delete the scattered calls — integrity centralized per conversion. Review gate: unexplained integrity decorators fail review (reason + alternative required).
