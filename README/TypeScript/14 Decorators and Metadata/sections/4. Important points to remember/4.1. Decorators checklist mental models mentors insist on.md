## 4.1. Decorators checklist — mental models mentors insist on

### 1) **Standard by default, legacy by framework requirement** (no flag vs pinned flag)

**Definition** — new decorators use the TC39 standard form (no flag, portable, proposal-stable — value+context signatures per kind); legacy experimental form survives only where frameworks require its emit (Angular/NestJS/TypeORM-era stacks — `experimentalDecorators` on, version-pinned, recorded per file). One form per file, migration per file, flag deletion as completion proof.

**What problem it solves / history** — unrecorded form choices (standard-looking decorators in legacy-configured files failing as proposal mismatches; legacy decorators in standard pipelines crashing consumers) confused checkers and readers alike (units 88–91 each hit a form-boundary issue during authoring). The default-plus-pinned rule makes form choice explicit per file: standard unless a framework record says otherwise.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), write standard (no flag); pin legacy per framework major (comment + package.json version + migration-guide link); migrate per file (signatures + order + green tests); delete the flag at zero legacy uses (flag-off + green = mechanical completion proof). See [2.1. Legacy compared](<../2. Legacy and Metadata/2.1. Legacy experimental decorators compared.md>).

**Runnable example** — standard default, legacy pinned (good vs bad, `tsc --strict`):

```typescript
// good — standard decorator (no flag; portable across transpilers supporting the proposal)
function tagged2(tag: string) {
  return function <T extends new (...args: any[]) => object>(target: T): T {
    return target; // marker shape (application services need no legacy — standard throughout)
  };
}
@tagged2("v1")
class Svc6 {
  run(): string { return "ran"; }
}
console.log(new Svc6().run()); // ran — standard default (flag state irrelevant — plain language)
// bad — legacy form without a framework record (flag + positions + emit costs, no consumer requiring them)
// fix — standard by default (migrate per file); legacy by pinned framework requirement (recorded, revisited per major)
```

```typescript
// good — pinned legacy boundary (framework-owned positions, recorded, isolated per file)
// (legacy: framework controllers use legacy positions + metadata emit — pinned per package.json major + migration link)
// Standard-decorated application code beside pinned boundaries (coexistence per FILE, never mixed per file):
function audited2<T extends new (...args: any[]) => object>(target: T): T {
  return target; // application-side marker (standard form — file contains zero legacy decorators)
}
@audited2
class Log6 {
  constructor(public m = "") {}
}
console.log(new Log6().m.toUpperCase()); // (empty) — mixed forms per BOUNDARY (file granularity, never mixed per file)
// bad — migrating framework-boundary files early (DI/routing breaks silently — framework reads legacy shapes only)
// fix — upgrade-window migration (framework major lands standard support → migrate in that upgrade PR)
```

```typescript
// good — flag deletion as completion proof (no legacy uses remain — verified mechanically, not declared)
// tsconfig after migration: experimentalDecorators REMOVED (flag-off + green CI = zero legacy, proven)
// (documented as config evolution: the flag's deletion is the migration's completion certificate)
export const form = "standard-only";
console.log(form); // standard-only — completion verified (not asserted — green without the flag)
// bad — flag retained "just in case" post-migration (dead configuration inviting legacy regressions silently)
// fix — delete on completion (flag-off + green = proof; flag-on-forever = migration theater)
```

**Common confusion** — "standard works everywhere legacy did" — parameter decorators + `emitDecoratorMetadata` have no standard equivalents yet (gaps keeping legacy alive — see 2.2–2.3); migrate what maps, pin what doesn't. "flag-off prevents legacy" — flag-off *breaks parsing* of legacy syntax (errors, not prevention — prevention is migration + deletion). "one file can mix carefully" — mixed files check awkwardly and read impossibly (two mental models per file) — careful mixing is still mixing.

**Performance note** — standard emit is leaner (direct calls vs `__decorate` helpers per legacy file); flag state has zero runtime profile (parse-time only). Migration dividends: smaller emit + portable syntax, one file at a time.

**Mentor note** — grep legacy-form files quarterly with framework pins beside each (pins current? migration windows open?) — interop backlog made countable. Exercise: migrate one file fully (signatures + order + tests) and delete nothing else — mechanical plus careful in one task. Review gate: mixed-form files fail review; unpinned legacy fails review.

### 2) **Decorators observe and wrap — never silently change contracts** (additive behavior only)

**Definition** — decorator discipline: observe (register, count, log — void returns, zero behavior delta), wrap transparently (same signature in/out — timing, memoization with documented bounds, auth gating that *adds* rejection without changing success shapes), or transform *documentedly* (field initializer replacement with interception comments). Never: silent contract changes (widened returns, swallowed errors, altered arities) hidden behind annotation syntax.

**What problem it solves / history** — contract-changing decorators (wrappers widening returns to `any`, swallowing throws with defaults, reordering tuple positions "helpfully") broke callers at a distance (call sites trusting signatures the decorator secretly rewrote — green types, wrong runtime). Additive-only discipline keeps the signature as the contract: decorators add behavior *around* it (observation, caching, gating) or document transformation explicitly (interception comments + tests).

**Modern guidance** — as of TypeScript 5.9 era, preserve signatures exactly (generic `<This, Args, Ret>` threading — see 1.1's shapes); rethrow always (telemetry observes outcomes; handling belongs to callers); document interceptions (replacement initializers, gating rejections — visible at the decorator, tested per stack). Review wrappers against the wrapped signature (identical in/out — any delta is a documented transformation or a defect).

**Runnable example** — additive only (good vs bad, `tsc --strict`):

```typescript
// good — transparent wrapper (identical signature, additive timing only)
function timed2<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); }; // same in/out (contract preserved)
}
class Calc3 {
  @timed2
  add(a: number, b: number): number { return a + b; }
}
console.log(new Calc3().add(2, 3).toFixed(0)); // 5 — wrapped transparently (additive behavior, identical contract)
// bad — widening wrapper (fn: (...) => Ret) => (...args: any[]) => any (signature destroyed — callers untrusted post-decoration)
// fix — generic threading (This/Args/Ret preserved — contract identical with and without the decorator)
```

```typescript
// good — rethrowing observer (outcomes observed, handling untouched)
function traced2<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret {
    try {
      return fn.apply(this, args);
    } catch (e) {
      console.log("threw"); // observed (telemetry dimension added — behavior unchanged)
      throw e; // rethrown (handling belongs to callers — observers never interfere)
    }
  };
}
class Api4 {
  @traced2
  get(): string { throw new Error("x"); }
}
try {
  new Api4().get();
} catch {
  console.log("caught-outside"); // caught-outside — error propagated (observer transparent to control flow)
}
// bad — swallowing wrapper (catch + default return inside telemetry — behavior changed under observation flags)
// fix — rethrow always (telemetry observes outcomes; handling belongs to callers, never to observers)
```

```typescript
// good — documented interception (replacement stated where it happens, tested per stack)
function fixed2(v: number) {
  return function (_value: undefined, _context: ClassFieldDecoratorContext<object, number>): (this: object) => number {
    return function (this: object): number { return v; }; // INTERCEPTION (declared initializer ignored — stated in decorator name + comment)
  };
}
class Consts2 {
  @fixed2(7) answer = 0; // declared 0 dead (interception documented at the decorator — readers see it lose)
}
console.log(new Consts2().answer.toFixed(0)); // 7 — documented interception (visible, tested, reviewed as transformation)
// bad — silent interception (declared values dead without a trace — readers trust `= 0`, runtime serves 7)
// fix — interception comments + tests (transformation visible at the decorator, proven per stack)
```

**Common confusion** — "wrappers must add value visibly" — transparent wrappers (hook points for future observation) add *structure* (named interception points, tested passthrough) — value today (testability) plus value tomorrow (telemetry without refactoring). "rethrow loses context" — rethrow preserves stack + type (transparent propagation); *wrapping* errors (`new Error(cause)`) adds context deliberately where needed — observe-then-rethrow vs enrich-and-wrap are different promises, both honest. "documented interception is still surprising" — surprising *once* (first read of the decorator), then explicit everywhere (name + comment + test) — versus silent interception surprising *every* reader forever.

**Performance note** — transparent wrappers add one closure per call (identical to manual higher-order wrapping — observation cost, not decorator cost); void-observed methods cost zero per call (no wrapper installed); interceptions cost one function per instance-field (initializer chain — trivial).

**Mentor note** — disable one decorator and diff behavior (identical results for transparent wrappers — additivity proven by removal). Exercise: audit three wrappers for signature deltas (identical? documented transformation? silent change?) — each category has its disposition (keep / document+test / delete). Review gate: signature-changing wrappers without interception comments + tests fail review.

### 3) **Metadata serves frameworks, not application logic** (attach for tooling; code reads values)

**Definition** — metadata (`context.metadata`, `Symbol.metadata` reads, `design:*` facts) serves *frameworks* (routers dispatching, validators scheming, ORMs mapping, test runners selecting) — application logic reads *values* (fields, params, returns) and branches on them. Business rules branching on `Reflect.getMetadata`/`Symbol.metadata` lookups are untestable without emit setup, invisible in reviews, and untyped without assertion scaffolding.

**What problem it solves / history** — metadata-read business logic (`if (Cls[Symbol.metadata].tier === "gold")` pricing branches) coupled pricing to emit setup (tests needing decorator evaluation + metadata polyfills to exercise a discount rule), hid rules from reviews (logic in data lookups, not branches), and broke under channel migration (standard-vs-legacy store mismatch — rules silently defaulting). Values in code, metadata in tooling — layers separated by consumer, not by syntax.

**Modern guidance** — as of TypeScript 5.9 era, attach metadata for framework consumers (routes, schemas, tables, suite ids — tooling reads); branch business logic on values (fields, params, discriminants — code reads); test business rules without decorator machinery (pure functions over values — no emit setup in unit tests, ever).

**Runnable example** — tooling reads metadata, logic reads values (good vs bad, `tsc --strict`):

```typescript
// good — metadata for the dispatcher, values for the logic (layers separated by consumer)
function route2(path: string) {
  return function <T extends new (...args: any[]) => object>(target: T, context: ClassDecoratorContext<T>): T {
    if (context.metadata) context.metadata["path"] = path; // tooling data (dispatcher reads post-definition)
    return target;
  };
}
@route2("/orders")
class Orders3 {
  total(items: number[]): number { return items.reduce((a, b) => a + b, 0); } // LOGIC reads values (no metadata in sight)
}
type WMM2 = { [Symbol.metadata]?: Record<string, unknown> };
const path = (Orders3 as unknown as WMM2)[Symbol.metadata]?.["path"]; // dispatcher read (tooling layer)
console.log(path, new Orders3().total([1, 2]).toFixed(0)); // /orders 3 — metadata (tooling) + values (logic), separated
// bad — if ((Cls[Symbol.metadata].tier) === "gold") price *= 0.9 (business rule in metadata lookup — untestable without emit setup)
// fix — tier as a field (values branch business logic; metadata serves dispatchers/validators/runners only)
```

```typescript
// good — validation metadata consumed by validator (framework), errors consumed by forms (application values)
function min3(n: number) {
  return function (value: undefined, context: ClassFieldDecoratorContext<object, number>): void {
    void value; void context; void n; // rule sketch (full pattern in 3.1 — metadata accumulation there)
  };
}
class Form6 {
  @min3(0) age = 5;
}
function isAdult(age: number): boolean { return age >= 18; } // LOGIC on values (no metadata read — plain branch, unit-testable)
console.log(isAdult(new Form6().age)); // false — business rule (values) beside validation metadata (tooling), never mixed
// bad — isAdult reading min-rules from metadata to decide (logic coupled to emit setup — unit tests need decorator evaluation)
// fix — logic on values (testable without machinery); metadata for validators/runners/dispatchers (tooling consumers)
```

```typescript
// good — suite metadata for runners, assertions in tests (each layer's data where it belongs)
function suite2(id: string) {
  return function <T extends new (...args: any[]) => object>(target: T, context: ClassDecoratorContext<T>): T {
    if (context.metadata) context.metadata["suite"] = id; // runner data (selection, filtering, reporting)
    return target;
  };
}
@suite2("billing")
class Billing6 {
  run(): boolean { return 1 + 1 === 2; } // test body (values + assertions — no metadata reads inside)
}
console.log(new Billing6().run()); // true — tests assert values (runners select via metadata — layers never cross)
// bad — tests branching on their own suite metadata (self-inspection replacing parameters — indirection without purpose)
// fix — metadata outward (for runners/selectors/dispatchers); values inward (logic/tests branch on data, always)
```

**Common confusion** — "metadata avoids plumbing" — metadata avoids *explicit* plumbing by adding *implicit* coupling (emit setup, channel matching, assertion scaffolding) — plumbing made invisible, not removed. "framework code is application code" — framework *configuration* (routes/schemas/tables via metadata) differs from business *rules* (pricing/eligibility/totals via values) — same file, different layers, different consumers. "unit tests can set up emit" — unit tests *shouldn't need to* (pure functions over values test without machinery — emit-dependent tests are integration tests wearing unit names).

**Performance note** — metadata reads cost property lookups (tooling paths — boot/discovery, never hot); value branches cost comparisons (hot paths welcome) — layering aligns cost with frequency naturally (tooling slow-path, logic fast-path).

**Mentor note** — grep business logic for `Symbol.metadata`/`getMetadata` reads (each a layer violation to refactor into value reads) — layering audited by search. Exercise: convert one metadata-branching rule to a value branch (testability before/after: emit-setup-required vs pure) — layers separated per conversion. Review gate: application logic reading metadata channels fails review.

### 4) **Prefer explicit composition where annotation hides control flow** (HOF calls and mixins where `@` obscures)

**Definition** — decorator syntax hides *control flow* (wrapping order, conditional application, dynamic pipelines read cleanly as calls, opaquely as stacked annotations past depth 3–4); explicit composition (higher-order calls, `pipe()` chains, mixin call expressions) shows flow where readers need it (locals, conditionals, dynamic assembly). Annotate cross-cutting *declarations* (telemetry/validation/caching on members); compose *control flow* explicitly (locals, branches, pipelines as values).

**What problem it solves / history** — annotation-maximalism (`@` for conditional/dynamic/local wrapping — behavior defined far from use, stacked invisibly, ordered opaquely) obscured the exact flows composition states plainly (conditionals as `if`, pipelines as `pipe()`, locals as call results). Distance-based judgment (declaration → decorator; use site → call — see 3.2 promise 3) keeps each form where readers need its information.

**Modern guidance** — as of TypeScript 5.9 era, decorate member concerns (cross-cutting, declaration-visible, line-removable); call-compose locals/conditionals/pipelines (explicit at use sites, tested as values); name recurring stacks (`@endpoint` bundling auth+validate+log — composed-then-declared, best of both). Review 5+-deep anonymous stacks as extract-and-name candidates unconditionally.

**Runnable example** — each form where readers need it (good vs bad, `tsc --strict`):

```typescript
// good — decorator for member concern (visible at declaration, removable per line)
function audited3<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); }; // hook point (named, tested passthrough)
}
class Orders4 {
  @audited3
  place(total: number): string { return `order:${total}`; } // concern declared (coverage visible per member)
}
console.log(new Orders4().place(9)); // order:9 — decoration where declarations live (right distance)
// bad — audit(order4.place) post-hoc per method (wrapping assignments scattered post-class — declaration/observation split)
// fix — @audited3 at declaration (co-located) for member concerns; calls at use sites for local needs
```

```typescript
// good — calls for conditional/local flow (explicit where readers need it)
function maybeWrap<F extends (...args: never[]) => unknown>(fn: F, on: boolean): F {
  return (on ? ((...args: Parameters<F>): ReturnType<F> => {
    console.log("wrapped");
    return fn(...args) as ReturnType<F>;
  }) : fn) as F; // conditional (annotation can't branch — call form can, explicitly)
}
function base(n: number): number { return n; }
const wrapped = maybeWrap(base, true);
console.log(wrapped(1).toFixed(0)); // wrapped \n 1 — conditional flow as values (tested, branched, explicit)
// bad — @conditional decorators (branching hidden in decorator factories — control flow as annotation surprise)
// fix — calls for control flow (conditions/loops/pipelines as values — explicit where readers need it)
```

```typescript
// good — named stacks bridging both (composed + tested as values, applied as annotations)
function stackLogger<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); }; // named unit (tested once as value)
}
class Api5 {
  @stackLogger
  handle(): string { return "ok"; } // named stack applied (composed-then-declared — best of both worlds)
}
console.log(new Api5().handle()); // ok — composition tested as value, applied as annotation (each form where it shines)
// bad — anonymous 5-stacks (undeclared composition spilling across members — untestable per layer, unreadable as units)
// fix — name recurring stacks (composed + tested as values, applied as decorators — readability AND testability)
```

**Common confusion** — "one form per codebase" — mixed forms per *fit* (members declarative, locals explicit, stacks named) — uniformity across fits is the actual consistency (same rule as 3.2 promise 3's distance judgment). "explicit composition is verbose" — verbose *where readers need it* (control flow at use sites deserves lines); terse *where declarations live* (cross-cutting concerns deserve annotations) — verbosity placed, not minimized globally. "named stacks add indirection" — named stacks *remove* anonymous-stack indirection (one name per recurring composition vs N anonymous layers per member).

**Performance note** — identical mechanics either form (closures per wrap — zero delta); named stacks test once, apply everywhere (test-time efficiency); anonymous stacks re-verify per use (wasted verification). Form choice is readability/testability economics, never runtime.

**Mentor note** — write one concern both ways (decorated member + composed call) and ask "where does the reader need this?" (declaration → decorator; use site → call) — distance judgment transfers to every future wrapping decision. Review gate: single-use decorators fail review (calls for locals); manual member-wrap assignments fail review (decorators for members).
