## 4.1. Decorators checklist — mental models mentors insist on

### 1) **Identify the configured model and the executed artifact**

A decorator review starts with the consuming program. On the verified **TypeScript 7.0.2** baseline, `experimentalDecorators` selects the legacy model; omitting it selects the standard-form model. The option belongs to a configured program, not an individual source file. Moving a declaration to another folder does not give it an independent flag value. [2.1](<../2. Legacy and Metadata/2.1. Legacy experimental decorators compared.md>) demonstrates separate programs and consumption of their emitted artifacts.

Ask what the framework or tool actually consumes, which decorator signatures it expects, and whether it requires parameter decorators or legacy design metadata. Keep the supported configuration until that consumer path is verified. Some class decorators intentionally work in both models, so a passing build after deleting a flag does not prove a complete migration. The incompatible method signatures in the comparison give a stronger diagnostic than counting files that contain `@`.

Compiler support also differs from runtime parsing. The [standard-signature lesson](<../1. Standard Decorators/1.1. TC39 standard decorators classes methods fields.md>) compiles and executes emitted modules on Node.js 20.20.2, and separately shows native Node.js 22.18.0 rejecting decorator source. `isolatedModules`, `verbatimModuleSyntax` and `erasableSyntaxOnly` acceptance does not certify that runtime parser. Name the source, emitter, output and runtime at the actual deployment boundary.

For application-oriented backend work, retain the NestJS/Fastify path and the framework's supported model. This domain's local language fixtures do not establish NestJS, Angular, ORM, browser or bundler integration.

### 2) **Review observable behavior beyond a compatible type**

A compatible replacement signature helps preserve caller-facing parameter and result types. It does not prove that the replacement preserves identity, binding, errors, side effects or timing. Trace the actual returned function or constructor.

| Review question | Concrete evidence to inspect |
|---|---|
| Who supplies the method receiver? | [1.1](<../1. Standard Decorators/1.1. TC39 standard decorators classes methods fields.md>) uses `.apply` and an explicitly supplied receiver; it does not bind automatically. |
| Which stack layer enters or exits first? | [1.2](<../1. Standard Decorators/1.2. Decorator evaluation and application order.md>) separates factory evaluation, application, invocation and extra initialization. |
| Does the original field expression still execute? | The field traces show the expression, every returned transformer and the extra hooks. Returning a constant does not remove the original expression's effects. |
| Which constructor does the consumer store? | [1.3](<../1. Standard Decorators/1.3. Practical class decorators registration and mixins.md>) registers the final replacement through a class initializer and contrasts immediate input registration. |
| Does telemetry observe return or settlement? | [3.2](<../3. Patterns in Practice/3.2. Logging timing and memoization decorators.md>) demonstrates a pending return event versus later settlement, new promise identity and a changed synchronous-throw channel. |
| Which object receives an integrity operation? | [1.3](<../1. Standard Decorators/1.3. Practical class decorators registration and mixins.md>) seals constructor/prototype objects without banning subclassing or sealing instances. |

For a worked review, consider the settlement decorator in 3.2. Its value and error checks pass, but its returned promise differs from the input promise. It also turns a synchronous throw into rejection. Accept it only if the intended observation contract permits those differences; documenting it as a transparent synchronous observer would be inaccurate.

Similarly, freezing in a base replacement can break a later derived field even when the constructor types remain compatible. A comment saying “additive” or “same shape” cannot substitute for the construction contract. Choose a narrower policy or an explicit final-object operation when that matches the caller's needs better.

### 3) **Find the metadata producer, store and consumer**

A metadata claim needs all three parts: code that records the data, an initialized runtime channel that retains it, and a reader that interprets it. A marker decorator with an empty body is not evidence of an attached rule, and a string printed after decoration is not evidence that a reader found metadata.

The [standard channel](<../2. Legacy and Metadata/2.3. Symbol.metadata and the metadata proposal.md>) initializes `Symbol.metadata`, writes through `context.metadata`, then reads and checks values through the constructor. The [legacy project](<../2. Legacy and Metadata/2.2. emitDecoratorMetadata and design types.md>) uses compiler-emitted design keys and reflect-metadata. They are distinct stores and APIs. An import of the legacy library does not make a standard decorator populate its store.

Check bootstrap order and the consumer's missing-data policy. TypeScript's guarded legacy helper may skip recording when its API is absent; installing the library later does not recover those missed calls. By contrast, this domain's validation registration deliberately throws if its standard metadata bootstrap is missing. The correct review asks which implementation is running and what it does, rather than treating “missing metadata” as one universal failure mode.

Design metadata is also lossy. The executed legacy fixture records some declarations as `Object`, a string-literal union as `String`, and a tuple as `Array`. None is a full runtime schema. The [validation consumer](<../3. Patterns in Practice/3.1. Validation decorators field rules.md>) therefore checks actual values and rejects a missing schema; a successful type check or an empty fallback dictionary would not establish valid input.

Metadata readers are ordinary application code with dependencies that can be tested. Prefer an explicit value parameter when it communicates a business rule more clearly, but do not declare every application metadata read untestable or forbid it by syntax. Review its producer/reader contract, missing and malformed cases, inheritance policy, and coupling to runtime setup.

### 4) **Assign ownership for composition, caching and lifetime**

A decorator can make a declaration's policy visible. An explicit function wrapper, registration list, class factory or construction recipe can make assembly visible at a caller or startup boundary. Neither syntax is automatically clearer. The same `withTiming` helper in [3.2](<../3. Patterns in Practice/3.2. Logging timing and memoization decorators.md>) is used both through annotation and an ordinary call. Conditional decorator factories are also possible, as [1.3](<../1. Standard Decorators/1.3. Practical class decorators registration and mixins.md>) demonstrates.

For a recurring stack, identify its component policies and observe the order they require. Naming the stack can help, but a name does not prove that it contains the claimed behavior. A no-op passthrough called `audit` has not implemented auditing. Review the actual callbacks, results and failures rather than setting an arbitrary decorator-count cutoff.

For caching, name the receiver/key equivalence, capacity, eviction, freshness and invalidation owner. The bounded memo in 3.2 isolates instances and caches `undefined`, yet still returns an old result after receiver state changes until cleared. A TTL, a WeakMap or an available clear method alone does not guarantee a retained-entry bound. Test the selected policy with distinct instances, changed state, eviction and failure paths.

For dependency injection, identify the factory and cache that make the lifetime real. [3.3](<../3. Patterns in Practice/3.3. Dependency injection with decorators.md>) proves singleton/transient identity and factory counts, including an undefined singleton result. Rebinding affects future resolutions; it does not rewrite existing objects or every cached dependent graph. Manual construction remains a valid substitution mechanism when its ownership is clear.

### 5) **Common confusion**

A build pass is one piece of evidence, not a migration certificate. One member stack's bottom-to-top application is not an entire class's execution timeline. A decorator return type does not bind `this`, create a validation schema, make metadata APIs exist, expose added class members statically, or establish cache freshness.

Tests should target the promised behavior. A local compiler rejection, an emitted runtime trace and a framework integration check answer different questions. Keep those results distinct, and retain explicit unverified boundaries when the actual consumer has not been run.

### 6) **Performance note**

A review checklist itself has no runtime cost. The chosen emitter helpers, wrappers, metadata storage, validators and caches execute real work. Standard and legacy output may use different helpers; no smaller-output or equal-speed result follows from the flag name. A wrapper is created at decoration and then invoked on calls, while field hooks run during the appropriate initialization step. Use the owners' observations to locate work, then measure the actual workload before claiming a cost or benefit.

### 7) **Mentor note**

Ask a learner to review a decorator without using the words “magic” or “transparent.” They should name its configured model, arguments, permitted return, initialization point, runtime consumer and observable policy. Then change one assumption: remove the bootstrap, alter receiver state, skip an import or replace the class. A sound answer predicts the affected behavior and chooses the appropriate compiler, runtime or integration evidence to check it.
