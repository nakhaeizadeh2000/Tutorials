## 3.2. Logging, timing, and memoization decorators

### 1) **Method wrapping** (logging entry/exit, timing spans — signature-preserving advice)

**Definition** — method decorators replacing functions with observed equivalents: log entry/exit (arguments in, result out), time spans (`Date.now()` deltas per call), trace correlation (span ids threaded through nested decorated calls). Replacement preserves the signature exactly (`(this, ...args) => Ret` in and out) — observability purely additive, behavior identical with and without the decorator.

**What problem it solves / history** — cross-cutting telemetry (`console.log` per method, `performance.now()` spans, span-id threading) handwritten per method bloated bodies (telemetry dominating logic 3:1 in hot services) and drifted per author (formats, units, correlation keys all local dialects). Decorator wrapping centralizes telemetry shape (one `timed` implementation, one log format) while distributing application (one line per method — coverage visible at declarations).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), wrap with signature-preserving generics (`<This, Args extends unknown[], Ret>` threaded — see 1.1's `timed` shape); log structured records (method, args-count, duration-ms, outcome — greppable JSON, not interpolated strings); correlate with explicit context (span ids via parameters/AsyncLocalStorage — never decorator-closure state shared across concurrent calls).

**Runnable example** — observed without contract change (good vs bad, `tsc --strict`):

```typescript
// good — timed span with structured record (signature preserved, telemetry centralized)
function timed<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Ret>,
): (this: This, ...args: Args) => Ret {
  const name = String(context.name);
  return function (this: This, ...args: Args): Ret {
    const t0 = Date.now();
    try {
      return fn.apply(this, args); // delegate (behavior identical — observation purely additive)
    } finally {
      console.log(JSON.stringify({ op: name, ms: Date.now() - t0 })); // structured (greppable, dashboard-ready)
    }
  };
}
class Orders {
  @timed
  total(items: number[]): number { return items.reduce((a, b) => a + b, 0); }
}
console.log(new Orders().total([1, 2]).toFixed(0)); // {"op":"total","ms":0} \n 3 — observed, contract intact
```

```typescript
// good — entry/exit logging with outcome tagging (success vs throw distinguished in telemetry)
function traced<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret {
    console.log(`enter(args=${args.length})`); // entry (arity logged, values redacted by policy — see confusion)
    try {
      const out = fn.apply(this, args);
      console.log("exit:ok"); // success tagged (outcome dimension for dashboards)
      return out;
    } catch (e) {
      console.log("exit:throw"); // failure tagged (throw rates visible per method — the alerting dimension)
      throw e; // rethrown (telemetry never swallows — observe, don't interfere)
    }
  };
}
class Api2 {
  @traced
  get(id: string): string { return `got:${id}`; }
}
console.log(new Api2().get("a")); // enter(args=1) \n exit:ok \n got:a — outcome-tagged telemetry
// bad — swallowing wrapper (catch + default return inside telemetry — behavior changed under observation flags)
// fix — rethrow always (telemetry observes outcomes; handling belongs to callers, never to observers)
```

```typescript
// good — void-observation where interception is unnecessary (zero per-call cost — see 1.1 promise 3)
let calls = 0; // module-level counter (telemetry state OUTSIDE instances — shared intentionally here)
function counted<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret {
    calls += 1; // counted (central metric — call volume per decorated method family)
    return fn.apply(this, args);
  };
}
class Svc4 {
  @counted
  ping(): string { return "pong"; }
}
console.log(new Svc4().ping(), calls.toFixed(0)); // pong 1 — counted interception (metric centralized, behavior intact)
// bad — per-method hand-rolled counters (counter variables scattered, formats drifting, removal touching logic)
// fix — @counted (one decorator, central metric, zero logic intrusion — remove the line to uninstrument)
```

**Common confusion** — "logging arguments is always safe" — arguments carry PII/secrets (log *arity* + *outcome* by default; log *values* only with explicit redaction policy + review — the example above logs `args.length`, never contents). "telemetry wrappers change `this`" — standard wrappers thread `This` explicitly (`fn.apply(this, args)` — receiver preserved; arrow-function wrappers would capture definition-site `this` — always `function`). "timing needs `performance.now`" — `Date.now()` suffices for ms-granularity service telemetry (sub-ms needs `performance.now` — choose per required resolution, not habit).

**Performance note** — wrapped calls add one closure + timer reads per invocation (nanoseconds-to-microseconds — invisible outside ultra-hot loops; uninstrument hot paths or sample there). Structured `JSON.stringify` per call costs serialization (batch/buffer high-volume telemetry — never stringify per call past thousands/sec).

**Mentor note** — disable one `@timed` and diff behavior (identical results, absent telemetry) — additivity proven by removal. Exercise: convert three hand-instrumented methods to decorators and delete the inline telemetry (bodies shrink to logic — coverage visible at declarations). Review gate: inline timing/logging in method bodies fails review (decorate — telemetry centralized, removable per line).

### 2) **Memoization decorators** (per-argument caching with invalidation notes)

**Definition** — method decorators caching return values by argument key (`Map` from serialized args → result; cache hits skip recomputation): `@memo` on pure deterministic methods (same args → same result, no side effects). Invalidation explicit (`cache.clear()` API, TTL, or key-scoped eviction) — unbounded caches leak by design without it.

**What problem it solves / history** — repeated expensive pure calls (parsed configs per request, computed permissions per session, formatted reports per render) recomputed identically per call-site (CPU burned re-deriving stable values) or cached ad hoc (per-call-site `Map`s with inconsistent keys, missing invalidation, unbounded growth). Decorator memoization centralizes the cache (one key strategy, one invalidation API) while distributing application (one line per expensive pure method).

**Modern guidance** — as of TypeScript 5.9 era, memoize pure deterministic methods only (purity verified by review — impure methods memoized serve stale side effects); key by stable serialization (`JSON.stringify` of JSON-safe args — non-serializable args need custom keyers); bound every cache (TTL, LRU cap, or explicit `clear` — unbounded memoization is a memory leak with a decorator). Expose invalidation (`memo.clear()` per method or per instance — documented alongside the decorator).

**Runnable example** — cached purity, bounded growth (good vs bad, `tsc --strict`):

```typescript
// good — memoize pure computation (keyed cache, bounded by design note)
function memo<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  const cache = new Map<string, Ret>(); // per-method cache (closure-scoped — one cache per decorated method)
  const wrapped = function (this: This, ...args: Args): Ret {
    const key = JSON.stringify(args); // stable key (JSON-safe args required — documented constraint)
    if (cache.has(key)) return cache.get(key) as Ret; // hit (recomputation skipped — purity assumed, reviewed)
    const out = fn.apply(this, args);
    cache.set(key, out); // miss stored (bounded: see eviction note below)
    return out;
  };
  (wrapped as unknown as Record<string, unknown>)["clear"] = () => cache.clear(); // invalidation API (documented alongside)
  return wrapped;
}
class Fib {
  @memo
  fib(n: number): number { return n < 2 ? n : this.fib(n - 1) + this.fib(n - 2); } // exponential made linear-ish per instance chain
}
const f = new Fib();
console.log(f.fib(10).toFixed(0)); // 55 — memoized (repeated subcalls hit cache — same result, fraction of calls)
// bad — memoizing impure methods (Date.now()/random/IO inside — stale side effects served as fresh results)
// fix — purity review per @memo (deterministic + side-effect-free verified — impure stays unmemoized, always)
```

```typescript
// good — TTL-bounded memo (time-boxed freshness for slowly-changing data)
function memoTtl<This, Args extends unknown[], Ret>(ms: number) {
  return function (
    fn: (this: This, ...args: Args) => Ret,
  ): (this: This, ...args: Args) => Ret {
    let at = 0;
    let val: Ret | undefined;
    let key = "";
    return function (this: This, ...args: Args): Ret {
      const k = JSON.stringify(args);
      const now = Date.now();
      if (k === key && now - at < ms && val !== undefined) return val; // fresh hit (TTL + key both required)
      key = k; at = now; val = fn.apply(this, args); // refresh (single-entry TTL cache — bounded by construction)
      return val;
    };
  };
}
class Rates {
  @memoTtl(1000)
  rate(cur: string): number { return cur.length * 1.5; } // slowly-changing data (TTL freshness documented at decoration)
}
console.log(new Rates().rate("usd").toFixed(1)); // 4.5 — TTL memo (freshness bounded, growth impossible — single entry)
// bad — unbounded memo on high-cardinality args (user-id-keyed cache growing per request — leak with a decorator)
// fix — TTL/LRU/explicit-clear (every memo documents its bound — unbounded memoization fails review unconditionally)
```

```typescript
// good — per-instance caches via WeakMap (instances collectable — no cross-instance leaks)
function memoInst<This extends object, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  const caches = new WeakMap<object, Map<string, Ret>>(); // per-instance (collectable with the instance — no leak class)
  return function (this: This, ...args: Args): Ret {
    let c = caches.get(this);
    if (!c) { c = new Map(); caches.set(this, c); } // lazy per-instance cache (created on first call per instance)
    const key = JSON.stringify(args);
    if (c.has(key)) return c.get(key) as Ret;
    const out = fn.apply(this, args);
    c.set(key, out);
    return out;
  };
}
class Calc2 {
  @memoInst
  sq(n: number): number { return n * n; }
}
console.log(new Calc2().sq(7).toFixed(0)); // 49 — instance-scoped memo (collectable — cross-instance leaks structurally impossible)
// bad — shared-closure caches keyed without instance (instance A's results served to instance B — correctness bug wearing memo clothes)
// fix — WeakMap per instance (isolation + collectability — the two properties shared caches lack)
```

**Common confusion** — "memoization suits all expensive methods" — suits *pure deterministic* methods (same args → same result, no side effects, no time-dependence) — impure/temporal methods serve stale lies when memoized. "JSON keys work universally" — JSON-safe args only (functions/symbols/`undefined`-in-arrays serialize lossily — custom keyers for exotic args, documented per decorator). "caches need no bounds in tests" — unbounded caches leak in *long-lived* processes (tests pass, production OOMs months later — bound every cache regardless of current scale).

**Performance note** — memo hits skip recomputation entirely (the win — exponential→linear for fib-style recursion); misses pay key serialization + map ops (overhead per *first* call per key — profitable past trivial recomputation costs); TTL checks add one timestamp read per call (negligible). Profile hit rates (hits/total logged per method — unmeasured memoization is hope with a cache).

**Mentor note** — log hit/miss per memoized method for a day (hit-rate dashboard per method — unprofitable memos (0% hits) deleted, profitable ones kept with data). Exercise: memoize one pure hotspot, measure before/after (wall-clock + hit rate — both numbers required, either alone insufficient). Review gate: unbounded `@memo` (no TTL/LRU/clear) fails review; impure `@memo` fails review absolutely.

### 3) **Wrapping vs composing functions** (when `@` earns its indirection)

**Definition** — the choice: decorator syntax (`@timed m()`) vs higher-order calls (`m = timed(m)` / `pipe(m, timed, logged)`) — identical runtime mechanics (closures wrapping functions), different readability profiles. Decorators win for *declarative* cross-cutting (telemetry/validation/caching visible at declarations, removable per line); composition wins for *programmatic* assembly (conditional wrapping, dynamic pipelines, tested compositions as values).

**What problem it solves / history** — decorator-maximalism (`@` for everything including one-off local wrappers — indirection without co-location benefit) obscured control flow (behavior defined far from use, stacked invisibly), while composition-purism (manual nesting for framework Telemetry — six-deep paren pyramids) obscured intent equally. The criterion is *distance*: decoration co-locates with declarations (near), composition assembles at use sites (explicit) — choose by where the reader needs the information.

**Modern guidance** — as of TypeScript 5.9 era, decorate cross-cutting member concerns (timing/logging/validation/memo — declaration-visible, line-removable); compose local/one-off/conditional wrappers as function calls (explicit at the use site — no decorator machinery for single uses); extract named compositions for recurring stacks (`@endpoint` bundling auth+validate+log — decorator form *of* composed functions, best of both).

**Runnable example** — each form where it fits (good vs bad, `tsc --strict`):

```typescript
// good — decorator for declarative member concern (visible at declaration, removable per line)
function audit<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); }; // hook point (behavior identical today, observable tomorrow)
}
class Orders2 {
  @audit
  place(total: number): string { return `order:${total}`; } // concern declared (auditable coverage visible per member)
}
console.log(new Orders2().place(9)); // order:9 — decoration where declarations live (right distance)
// bad — audit(order2.place) post-hoc per method (wrapping assignments scattered post-class — declaration/observation split)
// fix — @audit at declaration (co-located) for member concerns; calls at use sites for local needs
```

```typescript
// good — composition for local one-off needs (explicit at the use site, no decorator machinery)
function twiceFn(n: number): number { return n * 2; }
function withLog<F extends (...args: never[]) => unknown>(fn: F): F {
  return ((...args: Parameters<F>): ReturnType<F> => {
    console.log("called");
    return fn(...args) as ReturnType<F>; // local wrapper (one use — decorator would add indirection without co-location benefit)
  }) as F;
}
const loggedTwice = withLog(twiceFn); // composed at use (explicit — reader sees wrapping where it happens)
console.log(loggedTwice(21).toFixed(0)); // called \n 42 — composition where use lives (no decorator file touched)
// bad — @withLog on a single-use local function (decorator machinery for one call site — indirection without distribution)
// fix — calls for locals (explicit), decorators for members (declarative): distance decides, always
```

```typescript
// good — named composition bridging both (composed functions exposed AS a decorator)
function namedEndpoint<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); }; // composed once (tested as a value)
}
class Api3 {
  @namedEndpoint
  handle(): string { return "ok"; } // named stack applied decoratively (composed-then-declared — best of both worlds)
}
console.log(new Api3().handle()); // ok — composition tested as value, applied as annotation (each form where it shines)
// bad — anonymous 5-stacks (undeclared composition spiller across members — untestable per layer, unreadable as units)
// fix — name recurring stacks (composed + tested as values, applied as decorators — readability AND testability)
```

**Common confusion** — "decorators replace helpers" — decorators *apply* helpers declaratively (the helper still exists as a function — testable, composable independently); replacing helpers with decorator-only logic strands untested closures. "composition is always clearer" — six-deep manual nesting (`a(b(c(d(e(f))))))`) reads inside-out where vertical decorators read top-down — clarity depends on depth (shallow: calls; cross-cutting stacks: decorators). "one form per codebase" — mixed forms per *fit* (members declarative, locals explicit, stacks named) — uniformity across fits is the actual consistency.

**Performance note** — identical mechanics (closures per wrap either form — zero delta); named compositions test once, apply everywhere (test-time efficiency); anonymous stacks re-verify per use (wasted verification). Form choice is readability/testability economics, never runtime.

**Mentor note** — write one concern both ways (decorated member + composed call) and ask "where does the reader need this info?" (declaration → decorator; use site → call) — distance-based judgment transfers to every future wrapping decision. Exercise: convert three misplaced forms (decorated locals → calls; manual member wraps → decorators) — placement corrected per fit. Review gate: single-use decorators fail review (calls for locals); manual member-wrap assignments fail review (decorators for members).
