## 3.2. Logging, timing, and memoization decorators

### 1) **Define what a timing wrapper observes**

A method wrapper can record an invocation without changing its declared arguments and result type. That type compatibility does not prove behavioral equivalence. A logger can throw, a clock can fail, and a promise-returning call can finish synchronously long before its asynchronous work settles. Specify the observed boundary and instrumentation failure policy.

These four files use **TypeScript 7.0.2**, standard-form decorators and emitted modules on **Node.js 20.20.2**, with no package dependencies. Save them in an empty directory without a `tsconfig.json`, then run:

```bash
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --outDir dist observe.mts sync.mts async.mts memo.mts
node dist/sync.mjs
node dist/async.mjs
node dist/memo.mjs
```

The helper below measures synchronous return or throw. It forwards the call's receiver and arguments and returns its result. Its chosen policy suppresses sink exceptions so they do not replace the business result or error. The clock is assumed to be non-throwing. A real application may require a different, explicitly tested reporting policy.

```typescript
// file: observe.mts
export type Event = { op: string; outcome: "return" | "throw"; ms: number };
export function withTiming<This, Args extends unknown[], Result>(
  value: (this: This, ...args: Args) => Result,
  op: string,
  emit: (event: Event) => void,
  clock: () => number = () => performance.now(),
): (this: This, ...args: Args) => Result {
  return function (this: This, ...args: Args): Result {
    const start = clock();
    let outcome: Event["outcome"] = "return";
    try { return value.apply(this, args); }
    catch (error) { outcome = "throw"; throw error; }
    finally {
      const event = { op, outcome, ms: clock() - start };
      try { emit(event); }
      catch { /* This policy suppresses telemetry sink failures. */ }
    }
  };
}
```

[Node's performance API](https://nodejs.org/download/release/v20.20.2/docs/api/perf_hooks.html#performancenow) provides a high-resolution process-relative timestamp. The next tests inject a fake clock that advances by five units per read. Their exact `ms:5` output proves deterministic control flow; it is not a measurement of the method's elapsed runtime.

```typescript
// file: sync.mts
import { withTiming, type Event } from "./observe.mjs";
const events: Event[] = [];
let tick = 0;
const clock = (): number => tick += 5;
const failure = new Error("business failure");
function timed<This, Args extends unknown[], Result>(
  value: (this: This, ...args: Args) => Result,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Result>,
): (this: This, ...args: Args) => Result {
  return withTiming(value, String(context.name), event => events.push(event), clock);
}
class Service {
  base = 3;
  @timed
  calc(value: number): number {
    if (value < 0) throw failure;
    return this.base + value;
  }
}
console.log(new Service().calc(2)); // 5
try { new Service().calc(-1); }
catch (error) { console.log(error === failure); } // true
console.log(events.map(event => `${event.op}:${event.outcome}:${event.ms}`).join("|"));
// calc:return:5|calc:throw:5
let sinkCalls = 0;
const brokenSink = (): void => { sinkCalls++; throw new Error("sink failed"); };
const observedSuccess = withTiming(() => 9, "ok", brokenSink, clock);
const observedFailure = withTiming(() => { throw failure; }, "bad", brokenSink, clock);
console.log(observedSuccess()); // 9
try { observedFailure(); }
catch (error) { console.log(error === failure); } // true
console.log(sinkCalls); // 2
const plusOne = withTiming((value: number) => value + 1, "plain", event => events.push(event), clock);
console.log(plusOne(3), events.at(-1)?.op); // 4 plain
// plusOne("3"); // TS2345: this wrapper still requires a number.
```

The same helper is applied through a decorator and an explicit function call. Both are legitimate ways to install this particular policy. The generic signature covers these ordinary functions; it does not promise to preserve arbitrary function-object properties, every overload set, binding, or identity. [1.1](<../1. Standard Decorators/1.1. TC39 standard decorators classes methods fields.md>) owns the basic receiver/signature contract and [1.2](<../1. Standard Decorators/1.2. Decorator evaluation and application order.md>) owns stacked entry/exit order.

### 2) **Observe settlement deliberately for promises**

A synchronous wrapper's `finally` runs when a method returns its promise. Awaiting that promise requires a different wrapper. An `async` replacement below reports settlement and returns a new promise; it also converts a synchronous throw from a promise-typed method into rejection. These are observable contract choices, supported by the [async function semantics](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/async_function#description).

```typescript
// file: async.mts
import { withTiming, type Event } from "./observe.mjs";
const syncEvents: Event[] = [];
let resolvePending: (value: number) => void = () => { throw new Error("not initialized"); };
const pending = new Promise<number>(resolve => { resolvePending = resolve; });
let tick = 0;
const clock = (): number => ++tick;
const observedReturn = withTiming(() => pending, "returning", event => syncEvents.push(event), clock);
console.log(observedReturn() === pending, syncEvents[0]?.outcome); // true return: still pending
const events: { op: string; outcome: "resolve" | "reject"; ms: number }[] = [];
function settled<This, Args extends unknown[], Result>(
  value: (this: This, ...args: Args) => Promise<Result>,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Promise<Result>>,
): (this: This, ...args: Args) => Promise<Result> {
  return async function (this: This, ...args: Args): Promise<Result> {
    const start = clock();
    let outcome: "resolve" | "reject" = "resolve";
    try { return await value.apply(this, args); }
    catch (error) { outcome = "reject"; throw error; }
    finally { events.push({ op: String(context.name), outcome, ms: clock() - start }); }
  };
}
const failure = new Error("failed");
class AsyncService {
  @settled load(): Promise<number> { return pending; }
  @settled reject(): Promise<number> { return Promise.reject(failure); }
  @settled explode(): Promise<number> { throw failure; }
}
const service = new AsyncService();
const result = service.load();
console.log(result === pending, events.length); // false 0
resolvePending(7);
console.log(await result, events[0]?.outcome); // 7 resolve
try { await service.reject(); }
catch (error) { console.log(error === failure); } // true
let synchronousThrow = false;
let rejected: Promise<number> | undefined;
try { rejected = service.explode(); }
catch { synchronousThrow = true; }
console.log(synchronousThrow); // false
try { await rejected; }
catch (error) { console.log(error === failure); } // true
console.log(events.map(event => `${event.op}:${event.outcome}`).join("|"));
// load:resolve|reject:reject|explode:reject
```

The pending promise is controlled explicitly; no sleep or guessed duration determines the trace. A pending return produced a synchronous `return` event, while settlement instrumentation had no event until resolution. Even when the settled value and error identities are preserved, the promise identity and synchronous-throw channel differ. Do not label the two policies interchangeable.

The local array sink in this second fixture has no injected failure. If it is replaced with an external logger, define and test its failure policy as well. Node's [timerify](https://nodejs.org/download/release/v20.20.2/docs/api/perf_hooks.html#performancetimerifyfn-options) is an existing explicit instrumentation facility with a documented promise-settlement policy; the fixture does not benchmark or reproduce its implementation.

### 3) **Make cache identity, capacity and invalidation real**

Memoization reuses a stored result when its key identifies an equivalent computation. A method may also depend on receiver state, so a cache keyed only by arguments can serve one instance's result to another. This deliberately narrow example caches a single string argument and a string-or-undefined result, with a separate cache for each receiver. It supports no promise results or arbitrary argument tuples.

It bounds each receiver's cache to two entries using first-in, first-out eviction. Hits do not refresh insertion order. `clear(instance)` removes that receiver's cache. The implementation checks `has` separately so a cached `undefined` is still a hit.

```typescript
// file: memo.mts
function boundedMemo<This extends object, Result extends string | undefined>(capacity: number) {
  if (!Number.isInteger(capacity) || capacity < 1) throw new Error("positive integer capacity required");
  const caches = new WeakMap<This, Map<string, Result>>();
  return {
    decorate(
      value: (this: This, key: string) => Result,
      context: ClassMethodDecoratorContext<This, (this: This, key: string) => Result>,
    ): (this: This, key: string) => Result {
      void context;
      return function (this: This, key: string): Result {
        let cache = caches.get(this);
        if (!cache) { cache = new Map(); caches.set(this, cache); }
        if (cache.has(key)) return cache.get(key) as Result;
        const result = value.call(this, key); // A throw reaches the caller without storing a result.
        cache.set(key, result);
        if (cache.size > capacity) {
          const first = cache.keys().next();
          if (!first.done) cache.delete(first.value);
        }
        return result;
      };
    },
    clear(instance: This): void { caches.delete(instance); }
  };
}
let calls = 0;
const failure = new Error("lookup failed");
const memo = boundedMemo<{ prefix: string }, string | undefined>(2);
class Reader {
  prefix: string;
  constructor(prefix: string) { this.prefix = prefix; }
  @memo.decorate
  find(key: string): string | undefined {
    calls++;
    if (key === "throw") throw failure;
    return key === "missing" ? undefined : this.prefix + key;
  }
}
const a = new Reader("A:");
const b = new Reader("B:");
console.log(a.find("x"), a.find("x"), b.find("x"), calls); // A:x A:x B:x 2
console.log(a.find("missing"), a.find("missing"), calls); // undefined undefined 3
console.log(a.find("y"), a.find("x"), calls); // A:y A:x 5: x was evicted before its second computation
 a.prefix = "A2:";
console.log(a.find("x"), calls); // A:x 5: receiver isolation does not invalidate changed receiver state
memo.clear(a);
console.log(a.find("x"), calls); // A2:x 6
let failures = 0;
for (let i = 0; i < 2; i++) {
  try { a.find("throw"); }
  catch (error) { if (error === failure) failures++; }
}
console.log(failures, calls); // 2 8: thrown failures were not cached
console.log("JSON collisions",
  JSON.stringify([undefined]) === JSON.stringify([null]),
  JSON.stringify([NaN]) === JSON.stringify([null]),
  JSON.stringify([{ x: undefined }]) === JSON.stringify([{}]));
// JSON collisions true true true
try { JSON.stringify([1n]); }
catch (error) { console.log(error instanceof TypeError); } // true
```

The `as Result` bridges the library typing of `get` after an immediately preceding `has` check on the same local map; it is not a claim that arbitrary external data has type Result. No external callback runs between that check and read. The typed `clear` operation belongs to the factory object, rather than a hidden property added to the decorated method's runtime function.

Receiver isolation and state invalidation are separate. After `prefix` changes, the stored `A:x` remains until the explicit clear. If changing state should invalidate automatically, put that policy in the state-owning API or include a version in the key. Exceptions are retried here because the failed computation never reaches `set`.

The collision examples show why [JSON serialization](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/JSON/stringify#description) is not a universal cache key. Different values can produce the same string, and some inputs throw. This cache instead has an explicit string-key contract. Other argument domains require an equality/key policy of their own, including object identity or a carefully defined canonical representation.

A time-to-live policy controls freshness checks; it does not by itself cap all retained entries in a multi-key map. A `WeakMap` allows an unreachable receiver and its cache to become collectible, but does not bound the entries for a receiver that remains reachable. An available `clear` method also bounds nothing until some owner invokes it. Choose capacity, eviction, freshness and ownership separately. Asynchronous caches additionally need policies for in-flight reuse, rejection retention and cancellation; this example intentionally excludes them.

### 4) **Common confusion**

A `finally` around a promise-returning call observes the return unless it awaits settlement. Adding `async` can change identity and the throw channel even when the result type still reads `Promise<number>`. Likewise, a type-compatible telemetry sink can fail; this synchronous helper deliberately suppresses such errors, while another consumer might require a reported instrumentation failure.

A receiver-keyed cache prevents the demonstrated cross-instance mix-up but does not make changing state fresh. A capacity cap and a TTL answer different questions. Caching is appropriate when the declared equivalence and freshness policy allows reuse; do not infer that policy from a method being expensive or from a generic signature.

### 5) **Performance note**

The wrapper function is created during decoration; calls execute it and its clock/sink work. The fake-clock durations are semantic tests, not performance measurements. The memo example's call counter proves skipped computations, including an undefined result, and additional calls after eviction or clearing. It does not measure a speedup. Cache lookup, retention, rule work, serialization and logging can cost more than the computation saved. Measure representative hit rates, key distributions and workloads before retaining a cache or adding instrumentation to a hot path.

### 6) **Mentor note**

Ask the learner to predict promise identity, event availability before resolution and whether `explode()` throws synchronously. Then predict the memo call counter after two instances, an undefined result, eviction and a changed prefix. A sound explanation names the observation boundary, receiver/key equivalence, capacity and invalidation owner. Finish by choosing a decorator or explicit wrapper from where the caller needs the policy to be visible, rather than imposing one syntax everywhere.
