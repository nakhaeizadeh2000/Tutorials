## 3.3. Dependency injection with decorators

### 1) **Token-based registration** (`@Inject(TOKEN)` / `@Singleton` — explicit container maps)

**Definition** — token DI: string/symbol tokens key a container map (`Map<Token, Constructor>`); `@Inject(TOKEN)` marks constructor params (or properties) with their token (explicit, metadata-free, portable across standard/legacy); `@Singleton` marks lifecycle (one instance per container — vs transient per-resolution). Explicit tokens work everywhere `design:paramtypes` degrades (unions, interfaces, primitives — see 2.2 promise 3).

**What problem it solves / history** — manual wiring (`new Svc(new Repo(new Db(conn)))` — construction order hand-threaded, test doubles requiring call-site surgery, graph depth re-threaded per new dependency) scaled with depth (each dependency re-plumbed through every construction site). Token containers invert control: classes declare needs (tokens), containers satisfy them (recursive resolution, singleton caching) — dependencies added per constructor, tests substituted per binding.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), tokenize all DI boundaries (string/symbol tokens, typo-proof constants — never bare strings repeated); mark singletons explicitly (`@Singleton` vs default-transient documented per registration); test via container rebinding (provider substitution — construction logic lives in one place: the container). Prefer framework DI (NestJS) where the framework owns modules; hand-rolled token containers where the graph is small and explicit.

**Runnable example** — tokens explicit, lifecycle marked (good vs bad, `tsc --strict`):

```typescript
// good — token container: explicit maps, singleton lifecycle, testable rebinding
type Ctor2<T = object> = new (...args: never[]) => T;
class Container2 {
  private bound = new Map<string, Ctor2>();
  private singletons = new Map<string, object>();
  bind<T>(token: string, ctor: new (...args: never[]) => T, singleton: boolean): void {
    const maker = singleton
      ? (() => { let inst: T | undefined; return () => (inst ??= new ctor()); })()
      : (() => new ctor());
    void maker; // (simplified: singleton caching sketched — full memo per 3.2 patterns in production containers)
    this.bound.set(token, ctor as unknown as Ctor2);
  }
  get<T>(token: string): T {
    const C = this.bound.get(token);
    if (!C) throw new Error(`unbound:${token}`);
    return new (C as new () => T)();
  }
}
const cc = new Container2();
cc.bind("svc", class Svc5 { run(): string { return "ran"; } }, true);
console.log(cc.get<{ run(): string }>("svc").run()); // ran — token-explicit registration (portable, testable)
// bad — new Svc(new Repo(new Db())) chains (construction order hand-threaded — depth re-plumbed per dependency)
// fix — container bindings (dependencies declared per constructor, satisfied centrally, substituted per test)
```

**Common confusion** — "DI removes constructors" — DI *calls* constructors (with resolved arguments — classes declare needs via params; containers satisfy them). "tokens are boilerplate" — tokens *are* the wiring documentation (which abstraction binds where — greppable, rename-safe, typo-proof vs bare strings). "singletons are default" — lifecycle *marked* per registration (singleton vs transient decided explicitly — unmarked lifecycles assume differently per consumer).

**Performance note** — token maps resolve O(1) per binding (same as metadata maps); singleton caching skips reconstruction (startup-shaped cost — resolve once, inject everywhere); transient construction costs per resolution (bounded by graph size — factory-cached after first where stable).

**Mentor note** — rebind one token live (Real → Fake) and rerun the consumer (behavior flips without touching consumer code — inversion of control in two lines). Exercise: convert one manual-wiring chain to token bindings and count deleted construction sites — wiring centralized per conversion. Review gate: `new Svc(new Repo(...))` past depth 2 fails review (container or factory).

### 2) **Constructor injection without metadata emit** (explicit tokens over magic)

**Definition** — constructor injection *without* `design:paramtypes`: constructor params declared normally (`constructor(private repo: Repo)`), *wired* explicitly (tokens passed at container configuration — `container.bind(Svc).deps(TOKENS.repo)` or `@Inject` markers read by the container's own (non-emit) metadata channel). No flag, no polyfill, no degradation class — portability across standard/legacy, testability via rebinding, readability via explicit wiring.

**What problem it solves / history** — metadata-emit injection (`design:paramtypes` auto-wiring) broke on unions/interfaces/primitives (`Object` recorded — garbage resolved) and locked projects to legacy emit + polyfill (toolchain + runtime prerequisites for the wiring mechanism itself). Explicit-token injection works identically everywhere (standard decorators, no flags, no polyfill) — wiring stated in code reviewers read, not emit reviewers trust.

**Modern guidance** — as of TypeScript 5.9 era, wire constructors explicitly (token per param, declared at registration — readable, greppable, version-stable); reserve metadata-emit auto-wiring for framework-owned code (NestJS modules — idiomatic there, tested there); never mix (explicit tokens *and* metadata inference on one constructor — two wirings disagreeing silently on drift).

**Runnable example** — explicit wiring, no magic (good vs bad, `tsc --strict`):

```typescript
// good — constructor declares, container wires explicitly (no emit magic anywhere)
class Db8 {
  query(): string { return "rows"; }
}
class Svc8 {
  constructor(public db: Db8) {} // declares need (constructor param — explicit dependency surface)
  run(): string { return this.db.query().toUpperCase(); }
}
const db = new Db8();
console.log(new Svc8(db).run()); // ROWS — manual wiring (explicit: construction order visible, test doubles trivial)
// bad — metadata-auto-wired union param (design:paramtypes records Object — container resolves garbage at boot)
// fix — explicit tokens/wiring (precision where emit degrades — portable, testable, readable)
```

```typescript
// good — test doubles via constructor params (no container needed at small scale)
class Db8 { // re-declared: fences compile standalone (minimal dependency pair)
  query(): string { return "rows"; }
}
class Svc8 {
  constructor(public db: Db8) {}
  run(): string { return this.db.query().toUpperCase(); }
}
class FakeDb extends Db8 {
  override query(): string { return "fake-rows"; } // subclass double (behavior overridden, surface identical)
}
console.log(new Svc8(new FakeDb()).run()); // FAKE-ROWS — substitution via constructor (no container, no tokens, no magic)
// bad — container for a 2-class graph (indirection without scale benefit — containers earn their keep past manual-wiring pain)
// fix — constructor injection manually at small scale (explicit, zero machinery); containers past depth/complexity thresholds
```

```typescript
// good — factory wiring for parameterized construction (tokens for values, factories for configured instances)
class Db8 { // re-declared: fences compile standalone (minimal dependency pair)
  query(): string { return "rows"; }
}
class Svc8 {
  constructor(public db: Db8) {}
  run(): string { return this.db.query().toUpperCase(); }
}
function makeSvc(env: string): Svc8 {
  return new Svc8(new Db8()); // factory centralizes configured construction (env-threaded once, not per call site)
}
console.log(makeSvc("prod").run(), makeSvc("dev").run()); // ROWS ROWS — factories compose explicit wiring with configuration
// bad — container resolving configured values via metadata (values aren't types — emit records nothing usable; tokens required)
// fix — factories for values (explicit configuration), containers/tokens for service graphs (explicit wiring)
```

**Common confusion** — "explicit wiring is verbose" — verbose *once* per construction site (visible, greppable, testable) vs magic *opaque* per framework (invisible, debugging-hostile on mismatch) — verbosity that reads beats magic that surprises. "subclass doubles are heavyweight" — one subclass per double (overrides only differing behavior — shared surface via base type); heavier alternatives (container reconfiguration, module mocking) cost more machinery, not less. "factories replace containers" — factories *configure* (values + assembly per call); containers *resolve graphs* (recursive dependencies + lifecycles) — complementary layers (factory per configured root, container per graph).

**Performance note** — manual wiring costs zero indirection (direct construction — fastest possible); container resolution costs map lookups per binding (startup-shaped); factories cost one call per root (trivial). Wire manually until graph pain justifies containers (threshold, not ideology).

**Mentor note** — wire one 3-deep graph manually, then convert to tokens (construction sites deleted per level) — the pain threshold made tangible (convert *at* pain, not before or long after). Exercise: identify the repo's wiring-threshold violations (containers for 2-class graphs; manual chains past depth 4) — both directions misapplied, each fixable per this promise. Review gate: untestable constructors (concrete `new` inside business logic) fail review (inject or factory).

### 3) **When DI frameworks pay** (graphs, doubles, lifecycles — thresholds, not ideology)

**Definition** — framework DI (NestJS-style modules/providers/scopes) pays past three thresholds: graph depth (manual chains past 3–4 levels — construction order unmanageable by hand); test-double surface (dozens of injection points needing substitution — container rebinding beats surgery); lifecycle mix (singletons + request-scoped + transient coexisting — lifecycles marked centrally, not tracked per call site). Below thresholds: manual wiring/factories (explicit, zero machinery).

**What problem it solves / history** — framework-DI-by-default (NestJS for a 3-class CRUD — module boilerplate, decorator ceremony, container indirection for graphs manual wiring serves trivially) and manual-wiring-forever (200-provider monoliths wired by hand — construction order tribal knowledge, test doubles requiring archaeology) both misapply by ideology. Thresholds decide empirically: pain present → framework; absent → manual — reviewed per growth stage, not per preference.

**Modern guidance** — as of TypeScript 5.9 era, stay manual while graphs stay shallow (factories + constructor params — explicit, testable, zero framework); adopt framework DI past any threshold (depth/doubles/lifecycles — NestJS where the ecosystem fits, hand-rolled token containers where it doesn't); re-evaluate per growth stage (thresholds crossed gradually — framework adoption is a migration with its own triage, not a founding decision).

**Runnable example** — thresholds decide (good vs bad, `tsc --strict`):

```typescript
// good — manual wiring below thresholds (explicit, zero machinery, fully testable)
class Db9 { q(): string { return "q"; } }
class Repo9 { constructor(public db: Db9) {} all(): string { return this.db.q(); } }
class Svc9 { constructor(public repo: Repo9) {} run(): string { return this.repo.all().toUpperCase(); } }
console.log(new Svc9(new Repo9(new Db9())).run()); // Q — depth 3, manual (readable end to end — no framework earned yet)
// bad — NestJS module for 3 classes (boilerplate + ceremony + indirection for graphs manual wiring serves trivially)
// fix — thresholds (depth/doubles/lifecycles): framework past any, manual below all — decided empirically per stage
```

```typescript
// good — container past depth threshold (manual chains unmanageable — container centralizes)
class C0 { constructor(public v = 0) {} }
class C1 { constructor(public c0: C0) {} }
class C2 { constructor(public c1: C1) {} }
class C3 { constructor(public c2: C2) {} }
class C4 { constructor(public c3: C3) {} } // depth 5 (manual: new C4(new C3(new C2(new C1(new C0())))) — order tribal knowledge)
function build(depth: number): string { return `depth:${depth}`; } // factory sketch (centralized assembly point)
console.log(build(5)); // depth:5 — past threshold: container/factory centralizes (manual chain retired here)
// bad — manual 8-deep chains (construction order tribal knowledge — onboarding reads archaeology, tests perform surgery)
// fix — framework/container past thresholds (wiring centralized, doubles rebindable, lifecycles marked)
```

```typescript
// good — lifecycle mix marked centrally (singleton + transient coexisting — marked, not assumed)
class Stateless { f(): string { return "s"; } } // transient-safe (stateless — fresh per use, no lifecycle question)
class Stateful { n = 0; bump(): number { return ++this.n; } } // singleton-candidate (stateful — shared lifecycle marked)
console.log(new Stateless().f().toUpperCase(), new Stateful().bump().toFixed(0)); // S 1 — lifecycles differ by design (marked per registration in containers)
// bad — unmarked lifecycles (singleton assumed for stateful, transient assumed for stateless — assumptions splitting per consumer)
// fix — mark per registration (@Singleton vs transient — documented, auditable, testable both ways per 3.3 promise 1)
```

**Common confusion** — "frameworks are always worth it" — worth it past thresholds (depth/doubles/lifecycles); below thresholds they're ceremony without pain (boilerplate + indirection + learning curve for graphs manual wiring serves). "manual wiring doesn't scale" — scales to its thresholds (factories extend manual further than assumed — threshold honest assessment beats both ideologies). "migration is all-or-nothing" — strangler adoption (new modules framework-managed, legacy manual — boundary adapters bridging) migrates incrementally like every other migration in this track.

**Performance note** — manual wiring zero-overhead (direct construction); containers startup-shaped (resolve once, inject everywhere); frameworks add module-scan + metadata costs at boot (bounded by decorated surface — measured per app, not assumed). Thresholds are performance-informed (deep manual chains also cost *developer* time super-linearly — the dominant term).

**Mentor note** — count manual construction sites per graph (depth × breadth = wiring pain score) and compare against framework boilerplate lines (crossover visible numerically — decide with numbers, not preference). Exercise: hold a "framework or manual?" review per growth stage (thresholds checked quarterly — adopt/keep/defer decided empirically). Review gate: framework adoption without threshold evidence fails review (ceremony needs pain); manual chains past thresholds fail review (pain needs tooling).
