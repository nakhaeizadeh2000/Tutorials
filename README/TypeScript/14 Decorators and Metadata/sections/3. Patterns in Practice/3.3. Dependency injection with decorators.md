## 3.3. Dependency injection with decorators

Dependency injection means a consumer receives its dependencies rather than constructing a particular implementation inside its business method. A factory or container can own assembly, while a decorator can register a class. Registration and lifecycle are runtime behavior: writing “singleton” beside a token is insufficient if each resolution still constructs another instance.

This bounded example uses TypeScript 7.0.2 and Node 20.20.2, verified 2026-10-13. It supports synchronous factories, singleton/transient resolution and future-resolution replacement. It is a teaching mechanism, not an implementation of NestJS module discovery, request scopes, circular-dependency handling or disposal.

### 1) **Tokens, factories and lifecycle**

A token identifies a binding. Here each token contains a fresh symbol key, so its description is for diagnostics rather than identity. The phantom type member relates that token to the returned service type. A binding associates the key with a factory and an explicit lifecycle.

Singleton means the same cached result is returned for that token within this container. Transient means the factory runs for every resolution. The implementation checks cache presence with has instead of testing the value, so even an undefined result can be cached. A missing binding throws before constructing a consumer.

The container's heterogeneous maps store unknown; two localized assertions restore T on retrieval. That trust rests on using the declared token values and the typed bind API, which checks the factory result against the token's T. NoInfer prevents that return position from expanding the selected contract; its full explanation belongs in the [inference owner](<../../../08 Generics Deep Dive/sections/1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>). A forged token or assertion escape can violate this invariant; the token is not a runtime schema.

### 2) **A decorator that performs real registration**

The register factory returns a standard-form class decorator. When the class is decorated, it calls container.bind with a factory that invokes the zero-argument constructor. It neither reads constructor parameter metadata nor injects fields. The Counter class has no required constructor dependencies, making that bounded operation sufficient.

A service with dependencies instead gets an explicit assembly factory. Its normal constructor still declares the dependency interface. The factory resolves the repository token and passes that value to new UserService. No emitDecoratorMetadata, reflect-metadata or parameter decorator is used by this fixture. Those separate mechanisms belong in the [metadata channel owner](<../2. Legacy and Metadata/2.3. Symbol.metadata and the metadata proposal.md>) and the [legacy/standard comparison](<../2. Legacy and Metadata/2.1. Legacy experimental decorators compared.md>).

Save `container.ts` in a new directory without a `tsconfig.json`:

```typescript
export {};
interface Token<T> { readonly key: symbol; readonly _type?: T }
function token<T>(description: string): Token<T> { return { key: Symbol(description) }; }
type Lifecycle = "singleton" | "transient";
type Binding = { factory: (container: Container) => unknown; lifecycle: Lifecycle };
class Container {
  private readonly bindings = new Map<symbol, Binding>();
  private readonly instances = new Map<symbol, unknown>();
  bind<T>(key: Token<T>, factory: (container: Container) => NoInfer<T>, lifecycle: Lifecycle): void {
    this.bindings.set(key.key, { factory, lifecycle });
    this.instances.delete(key.key); // future resolutions must use the new binding
  }
  get<T>(key: Token<T>): T {
    const binding = this.bindings.get(key.key);
    if (!binding) throw new Error(`unbound:${key.key.description}`);
    if (binding.lifecycle === "singleton" && this.instances.has(key.key)) {
      return this.instances.get(key.key) as T;
    }
    const value = binding.factory(this);
    if (binding.lifecycle === "singleton") this.instances.set(key.key, value);
    return value as T; // localized trust: bind checked this token's factory result
  }
}
function register<T>(container: Container, key: Token<T>, lifecycle: Lifecycle) {
  return function <C extends new () => T>(ctor: C, _context: ClassDecoratorContext<C>): void {
    container.bind(key, () => new ctor(), lifecycle);
  };
}
interface CounterContract { count: number; next(): number }
interface Repository { all(): string[] }
const keys = {
  shared: token<CounterContract>("shared"),
  fresh: token<CounterContract>("fresh"),
  repo: token<Repository>("repo"),
  service: token<UserService>("service"),
  absent: token<Repository>("absent"),
  empty: token<undefined>("empty")
};
const container = new Container();
@register(container, keys.shared, "singleton")
class Counter implements CounterContract {
  count = 0;
  next(): number { return ++this.count; }
}
container.bind(keys.fresh, () => new Counter(), "transient");
const shared1 = container.get(keys.shared);
const shared2 = container.get(keys.shared);
console.log("shared:", shared1 === shared2, shared1.next(), shared2.next()); // true 1 2
const fresh1 = container.get(keys.fresh);
const fresh2 = container.get(keys.fresh);
console.log("fresh:", fresh1 === fresh2, fresh1.next(), fresh2.next()); // false 1 1

let emptyCalls = 0;
container.bind(keys.empty, () => { emptyCalls++; return undefined; }, "singleton");
container.get(keys.empty);
container.get(keys.empty);
console.log("empty calls:", emptyCalls); // 1: presence check caches undefined too
try { container.get(keys.absent); }
catch (error: unknown) { console.log("missing:", error instanceof Error ? error.message : "other"); }

class RealRepository implements Repository { all(): string[] { return ["Ada"]; } }
class UserService {
  constructor(readonly repo: Repository) {}
  names(): string { return this.repo.all().join(",").toUpperCase(); }
}
container.bind(keys.repo, () => new RealRepository(), "singleton");
container.bind(keys.service, c => new UserService(c.get(keys.repo)), "transient");
const before = container.get(keys.service);
console.log("real:", before.names()); // ADA
container.bind(keys.repo, () => ({ all: () => ["test-user"] }), "singleton");
const after = container.get(keys.service);
console.log("replacement:", after.names(), before.names(), after.repo === before.repo); // TEST-USER ADA false

const manual = new UserService({ all: () => ["manual"] });
console.log("manual:", manual.names()); // MANUAL
const otherContainer = new Container();
otherContainer.bind(keys.shared, () => new Counter(), "singleton");
console.log("container scope:", otherContainer.get(keys.shared) === shared1); // false
// container.bind(keys.shared, () => ({ count: 0, next: () => "wrong" }), "singleton"); // TS2322
```

Run `tsc --strict --target es2022 --module commonjs --lib es2022,dom --outDir out container.ts`, then `node out/container.js`. Both exit 0 and print:

```text
shared: true 1 2
fresh: false 1 1
empty calls: 1
missing: unbound:absent
real: ADA
replacement: TEST-USER ADA false
manual: MANUAL
container scope: false
```

The identity checks explain the counts: shared1 and shared2 are the same Counter, while fresh1 and fresh2 are different Counters. The undefined factory runs once because the cache distinguishes a present result from an absent entry. The last line establishes that another container has its own singleton cache; singleton is not automatically a process-wide global.

Uncomment the final incorrect factory and check with `tsc --strict --target es2022 --module commonjs --lib es2022,dom --noEmit container.ts`. It reports TS2322 because next must return a number. The registered factory is checked instead of accepting an unchecked get<T> chosen independently by the caller.

### 3) **Constructor substitution and replacement limits**

UserService depends on the Repository contract rather than constructing RealRepository. The first assembly returns ADA. Rebinding repo to a fake clears that token's cached result, and a future transient service receives the replacement. The old service still owns its original repository reference, so the replacement line prints TEST-USER, ADA and false. Rebinding does not rewrite existing objects or invalidate every cached dependent graph.

The manual service shows the same constructor substitution without container machinery. Keep assembly in a place where lifetime, configuration and test substitutions can be understood. A deeper graph can still be assembled explicitly; a small graph can still belong to an application's framework. Choose by the application's actual ownership/lifecycle requirements rather than imposing a universal graph-depth cutoff.

For application-oriented backend tracks, preserve the user's NestJS-first decision with the Fastify adapter. NestJS's [custom-provider guide](https://docs.nestjs.com/fundamentals/custom-providers) teaches class/value/factory bindings and constructor injection; its [scope guide](https://docs.nestjs.com/fundamentals/injection-scopes) owns framework lifecycle behavior. The tiny container here is not a drop-in replacement, and no NestJS/Fastify integration was run. The full framework track remains planned in the [root curriculum](<../../../../../README.md>).

### 4) **Practice: expose the lifecycle bug**

Predict what happens if the cached-result branch in get is bypassed while registration still says singleton. The observed regression is shared:false 1 1 and empty calls:2. Compilation still succeeds. Repairing the lifecycle therefore needs an identity/state/factory-count observation, rather than a label or a successful type check.

Next predict whether changing the repo binding changes before.names(). It remains ADA because before already holds the real repository. A correct explanation distinguishes a future resolution from an existing reference. A production framework may define additional replacement/testing operations; verify those actual semantics in its own owner.

### 5) **Common confusion**

A registration decorator performs whatever its function implements; a marker named Inject does not inherently resolve a parameter. A singleton annotation does not cache an object by itself. Tokens identify bindings, while the factory controls construction and the scope controls reuse. Runtime lifetime must match the intended sharing: a stateful object is not automatically suitable for sharing between unrelated requests.

### 6) **Performance note**

The maps, factories, constructors and cache checks execute at runtime. Singleton reuse can avoid repeated factory construction, but it also retains the cached result and whatever that result references. Transient resolution reconstructs according to the chosen factory. No constant-time lookup guarantee, startup/latency benchmark or framework-versus-manual ranking was measured here. Verify the required lifetime first, then measure construction and retention on the actual application graph.

### 7) **Mentor note**

Ask the learner to find the line that makes singleton behavior real, then explain why has is used for an undefined result. Have them replace Repository through the constructor and through bind and compare the consumer outputs. A sound answer identifies the construction owner, lifetime boundary and existing references. In review, check observable identity/state and the selected application's provider semantics rather than enforcing an arbitrary number of classes before allowing a framework.
