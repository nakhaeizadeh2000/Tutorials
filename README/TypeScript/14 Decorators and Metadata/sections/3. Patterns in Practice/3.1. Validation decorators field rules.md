## 3.1. Validation decorators — field rules

### 1) **Register rules and invoke a real consumer**

A validation decorator can associate a field with a rule. Recording the rule does not check an instance or an incoming payload. A separate consumer chooses the schema, reads actual values and reports failures. This separation makes it possible to test whether a declaration was registered and whether its rule rejects malformed input.

The complete example uses **TypeScript 7.0.2**, standard-form decorators and emitted modules on **Node.js 20.20.2**. It has no package dependency. Save the following fence as `validation.mts` in an empty directory without a `tsconfig.json`. Compile and run:

```bash
tsc --strict --target es2022 --module nodenext --moduleResolution nodenext --lib es2022,esnext.decorators,dom --outDir dist validation.mts
node dist/validation.mjs
```

This implementation intentionally validates flat own data properties. All registered fields are required. It does not parse nested schemas, normalize values, run asynchronous checks, reject every extra property or prove a complete TypeScript object type. Those are additional consumer policies. The [metadata owner](<../2. Legacy and Metadata/2.3. Symbol.metadata and the metadata proposal.md>) explains the runtime symbol and inheritance channel; this example uses it to connect real rules to real checks.

```typescript
// file: validation.mts
if (!Symbol.metadata) {
  Object.defineProperty(Symbol, "metadata", { value: Symbol("Symbol.metadata") });
}
type Check = (value: unknown) => string | undefined;
type FieldRule = { key: string | symbol; check: Check };
type Issue = { key: string | symbol; message: string };
const ownRules = new WeakMap<object, readonly FieldRule[]>();
function between(min: number, max: number): Check {
  if (!Number.isFinite(min) || !Number.isFinite(max) || min > max) {
    throw new Error("invalid range configuration");
  }
  return value => {
    if (typeof value !== "number" || !Number.isFinite(value)) return "finite number";
    return value < min || value > max ? `range:${min}..${max}` : undefined;
  };
}
const nonempty: Check = value => typeof value === "string" && value.length > 0
  ? undefined : "nonempty string";
function append<This, Value>(context: ClassFieldDecoratorContext<This, Value>, check: Check): void {
  if (context.static || context.private) throw new Error("public instance fields only");
  const metadata = context.metadata;
  if (!metadata) throw new Error("metadata bootstrap missing");
  const own = ownRules.get(metadata) ?? [];
  ownRules.set(metadata, [...own, { key: context.name, check }]);
}
function Ranged(min: number, max: number) {
  const check = between(min, max);
  return function <This>(_value: undefined, context: ClassFieldDecoratorContext<This, number>): void {
    append(context, check);
  };
}
function Nonempty<This>(_value: undefined, context: ClassFieldDecoratorContext<This, string>): void {
  append(context, nonempty);
}
function schemaFor(target: Function): readonly FieldRule[] {
  let metadata: unknown = Reflect.get(target, Symbol.metadata);
  const chain: object[] = [];
  while (typeof metadata === "object" && metadata !== null) {
    chain.unshift(metadata);
    metadata = Object.getPrototypeOf(metadata);
  }
  const rules = chain.flatMap(item => ownRules.get(item) ?? []);
  if (rules.length === 0) throw new Error("validation schema missing");
  return rules;
}
function checkFields(rules: readonly FieldRule[], input: unknown): Issue[] {
  if (typeof input !== "object" || input === null || Array.isArray(input)) {
    return [{ key: "$", message: "object required" }];
  }
  const issues: Issue[] = [];
  for (const rule of rules) {
    const descriptor = Object.getOwnPropertyDescriptor(input, rule.key);
    if (!descriptor) { issues.push({ key: rule.key, message: "missing" }); continue; }
    if (!("value" in descriptor)) {
      issues.push({ key: rule.key, message: "data property required" }); continue;
    }
    const message = rule.check(descriptor.value);
    if (message !== undefined) issues.push({ key: rule.key, message });
  }
  return issues;
}
function validateWith(target: Function, input: unknown): Issue[] {
  return checkFields(schemaFor(target), input);
}
function show(issues: readonly Issue[]): string {
  return issues.map(issue => `${String(issue.key)}:${issue.message}`).join("|") || "valid";
}
class Product {
  @Ranged(0, 100) price = 0;
  @Ranged(0, 1000) stock = 0;
}
class Special extends Product { @Nonempty sku = ""; }
class Other { @Ranged(10, 20) price = 10; }
const product = new Product();
product.price = 50;
console.log("instance", show(validateWith(Product, product)));
console.log("malformed", show(validateWith(Product, { price: -1, stock: "many" })));
console.log("nan", show(validateWith(Product, { price: NaN, stock: 0 })));
console.log("missing", show(validateWith(Product, { stock: 0 })));
console.log("undefined", show(validateWith(Product, { price: undefined, stock: 0 })));
console.log("child", show(validateWith(Special, new Special())));
console.log("schema counts", schemaFor(Product).length, schemaFor(Special).length, schemaFor(Other).length);
console.log("other", show(validateWith(Other, { price: 5 })));
console.log("inherited", show(validateWith(Product, Object.create({ price: 1, stock: 1 }))));
let getterReads = 0;
const getterInput = Object.defineProperty({ stock: 1 }, "price", {
  get() { getterReads++; return 1; }
});
console.log("accessor", show(validateWith(Product, getterInput)), getterReads);
console.log("null", show(validateWith(Product, null)));
class Unregistered {}
try { validateWith(Unregistered, {}); }
catch (error) { console.log(error instanceof Error ? error.message : "unexpected"); }
const explicitSchema: readonly FieldRule[] = [{ key: "label", check: nonempty }];
console.log("explicit", show(checkFields(explicitSchema, { label: "" })));
// @Ranged(0, 10) on a string field is a compiler error; check the isolated exercise below.
```

Expected output:

```text
instance valid
malformed price:range:0..100|stock:finite number
nan price:finite number
missing price:missing
undefined price:finite number
child sku:nonempty string
schema counts 2 3 1
other price:range:10..20
inherited price:missing|stock:missing
accessor price:data property required 0
null $:object required
validation schema missing
explicit label:nonempty string
```

The range factory validates its own bounds, then captures a predicate for later values. The field decorator records that predicate. Nothing in `@Ranged` automatically intercepts subsequent assignment. `validateWith` is the actual invocation that checks values. A returned field initializer could validate initialization, as [1.1](<../1. Standard Decorators/1.1. TC39 standard decorators classes methods fields.md>) explains, but that would be a different policy and still would not check all later mutations.

The explicit schema at the end uses the same runner and `nonempty` rule without decorators. It is a working alternative, not a second independent copy of Product's constraints. Both approaches need defined rule semantics and a real consumer.

### 2) **Make absence, malformed values and inheritance explicit**

A numeric comparison alone does not establish that an input is a number. For example, `NaN < 0` and `NaN > 100` are both false. Defaulting a missing property to `0` can also turn missing data into apparent success. Here each range rule first requires a finite number. Missing own properties receive a separate issue; an explicitly present `undefined` reaches the rule and fails its type check.

The consumer takes its schema class explicitly rather than trusting `input.constructor`. That lets it check a plain payload against a deliberately chosen contract. It reads own property descriptors, rejects accessors and avoids calling the getter in the demonstration. Inherited values do not satisfy this particular input policy. This is not a sandbox for hostile proxies: descriptor operations can invoke proxy traps or throw. Use a boundary/parser appropriate to the actual incoming values.

The private `WeakMap` stores each metadata object's own rules. During schema lookup, ancestor entries are gathered before descendant entries. A child adds its rule without mutating its parent's array, and unrelated classes with the same field name remain separate. If a descendant adds a rule for an already constrained key, this implementation applies both; it does not silently override the base constraint. Symbols remain distinct rule keys, although the `show` helper converts keys to diagnostic text.

No schema is a configuration failure here, not an empty list proving valid input. Missing bootstrap also throws during registration instead of silently dropping every rule. To check that failure, remove only the initial symbol bootstrap in a copy and run it in a fresh Node.js 20.20.2 process: the first decorated class throws `metadata bootstrap missing`. This differs from the guarded legacy metadata helper in [2.2](<../2. Legacy and Metadata/2.2. emitDecoratorMetadata and design types.md>), whose missing-store behavior has its own explicit checks.

Exercise: append `class Wrong { @Ranged(0, 10) price = "free"; }` to an isolated copy and compile with `--noEmit`. The compiler rejects a numeric field decorator on a string field. This type check helps authors of the class; it does not remove the runtime checks needed for incoming unknown values. Also try a static or private decorated numeric field: this demonstration explicitly rejects those kinds at definition time instead of pretending its own-data-property consumer supports them.

### 3) **Choose a validation model for the actual boundary**

Decorator locality can help when the supported framework already consumes rules beside class fields. Explicit schemas can help when a caller needs a standalone value describing its input, transformations or inferred output. Either can serve a boundary or an internal model. There is no language rule that data-transfer objects must avoid decorators, or that domain objects must use them.

Library contracts matter. For example, the [class-validator maintainer documentation](https://github.com/typestack/class-validator) describes its instance/plain-input prerequisites, inheritance behavior and validation options. This lesson's explicit `validateWith(Product, payload)` API is a different implementation; it is not evidence that a framework's validator accepts the same plain payload. No class-validator, Zod, NestJS or HTTP integration was executed here. Application-oriented backend work retains the NestJS/Fastify route and must verify the actual framework pipeline.

This runner collects all its flat-field issues to support useful diagnostics. A different consumer may intentionally stop early or throw. Decide from the caller's needs, information exposure and workload. Likewise, normalization and validation may be separate steps or an explicitly documented parsing pipeline. Avoid maintaining two independent copies of the same rule without a clear relationship; distinct transport and domain contracts can legitimately apply different constraints.

The returned `Issue[]` is not a type predicate and creates no validated copy. An empty result means only that these registered checks passed on these own properties at this moment. It does not reject extra keys, guarantee methods, or protect an object from later mutation. The [schema parsing owner](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.1. Hand-rolled schemas parse validate narrow.md>) owns constructing and narrowing a fully checked boundary value; [schema objects](<../../../15 Strictness Errors and Validation/sections/3. Schema Validation in Practice/3.2. Schema objects and inferred types.md>) owns schema-first typing.

### 4) **Common confusion**

Recording a range is not enforcing it. A green type check is not evidence that a plain payload has the declared runtime values, and an absent schema must not accidentally look like success. Constructor/metadata discovery and value validation are separate contracts; this consumer chooses the schema explicitly and handles missing configuration distinctly.

Inheritance also does not mean every class should share one mutable dictionary. The child owns its additions while the reader intentionally combines ancestor rules. Finally, a finite-number check is stricter than `typeof value === "number"`, while this nonempty-string rule deliberately accepts whitespace. Choose and document the intended rule rather than relying on a name such as `required` or `email` to imply an unimplemented format policy.

### 5) **Performance note**

For this implementation, a validation call gathers ancestor metadata entries, creates a combined rule array, inspects one descriptor per rule and allocates the reported issues. Cost depends on rule count, ancestry and predicate work; there is no generic “rules × nesting” formula because this runner does not recurse through nested input. Caching a resolved schema may help repeated checks, but needs an invalidation policy if rules can change. No speed, memory quantity, I/O comparison or library-equivalence benchmark was measured.

### 6) **Mentor note**

Ask the learner to predict the difference between missing `price`, present `undefined`, `NaN` and a getter returning `1`. Then ask why creating Special leaves Product with two rules. A sound explanation identifies the selected schema, the private own-rule store, the inheritance policy and the actual runtime predicate. Finish by asking what “valid” does not guarantee: extra keys, nested structures, instance methods and future mutation are outside these checks.
