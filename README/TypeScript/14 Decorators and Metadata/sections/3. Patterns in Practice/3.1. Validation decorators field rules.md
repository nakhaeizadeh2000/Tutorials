## 3.1. Validation decorators — field rules

### 1) **Rule registration per field** (`@Min(0)`, `@IsEmail` — constraints collected at definition)

**Definition** — validation decorators record per-field rules into a class-level schema at definition time (`MIN_RULES.set("age", 0)`); a separate `validate(instance)` function runs rules against values per instance. Registration (definition) and checking (instance) split across phases (see 1.2 promise 3) — decorators *declare* constraints, validators *enforce* them.

**What problem it solves / history** — validation logic scattered through setters, constructors, and submit handlers (each field checked wherever someone remembered — coverage gaps where nobody did) made rule coverage unauditable (which fields validate? grep `if` statements and hope). Decorator-collected schemas centralize rules *with* fields (visible per declaration) while executing centrally (one `validate` walking the schema — coverage provable by inspecting one table).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), declare rules via decorators (`@Min(0)`, `@Max(120)`, `@Matches(/…/)`, `@Required`), collect into a per-class schema (metadata channel per 2.3 or module-level registry keyed by constructor), and validate through one function (`validate(instance): string[]` — error list, empty when valid). Never validate inside decorators (no instance exists at definition — rules without values are declarations, not checks).

**Runnable example** — declare per field, enforce centrally (good vs bad, `tsc --strict`):

```typescript
// good — rules registered at definition (schema built once per class)
type Rule = { min?: number; max?: number };
function Ranged(min: number, max: number) { // named Ranged: Range collides with DOM lib's Range interface
  return function (value: undefined, context: ClassFieldDecoratorContext<object, number>): void {
    void value;
    const md = context.metadata; // guarded slot (metadata exists per decorated class — see 1.1/2.3 pattern)
    if (md) {
      const rules = (md["rules"] ?? {}) as Record<string, Rule>;
      rules[String(context.name)] = { min, max };
      md["rules"] = rules; // mutate the object (never reassign the readonly slot itself)
    }
  };
}
class Product {
  @Ranged(0, 100) price = 0;
  @Ranged(0, 1000) stock = 0;
}
function validate<T extends object>(inst: T): string[] {
  const rules = ((inst.constructor as unknown as { [Symbol.metadata]?: Record<string, unknown> })[Symbol.metadata]?.["rules"] ?? {}) as Record<string, Rule>;
  const out: string[] = [];
  for (const [k, r] of Object.entries(rules)) {
    const v = (inst as unknown as Record<string, unknown>)[k] as number;
    if (r.min !== undefined && v < r.min) out.push(`${k}<min`);
    if (r.max !== undefined && v > r.max) out.push(`${k}>max`);
  }
  return out; // error list (empty = valid — centralized enforcement over declared rules)
}
const goodP = new Product();
goodP.price = 50;
console.log(validate(goodP).length); // 0 — valid (rules declared per field, checked centrally)
```

```typescript

```

```typescript
// good — required-field rules via the same channel (presence + range composed per field)
function required2(value: undefined, context: ClassFieldDecoratorContext<object, unknown>): void {
  void value; void context; // marker sketch (presence enforced by validate() reading undefined-ness — full presence checks below)
}
class Signup {
  @required2 name = ""; // presence-marked (validate() flags empty/absent per rule kind)
}
function present(inst: object, key: string): boolean {
  const v = (inst as unknown as Record<string, unknown>)[key];
  return v !== undefined && v !== null && v !== "";
}
console.log(present(new Signup(), "name")); // false — "" fails presence (rule kind distinguished from range rules)
// bad — one mega-decorator validating everything inline (definition-time instance confusion + untestable rule units)
// fix — small rule decorators (registration) + one validate() (enforcement): units testable separately
```

**Common confusion** — "decorators validate" — decorators *register* (schema entries); `validate()` *checks* (reads instances against the schema) — conflating them produces definition-time checks against `undefined` (always failing or always passing, never meaningful). "central validate() is boilerplate" — one function per project (shared across all decorated classes) vs validation logic scattered per field (N sites, N styles, gaps everywhere). "rules must live with validators" — rules live with *fields* (declaration site — visible where the data is shaped); enforcement lives centrally (one function — auditable coverage).

**Performance note** — registration runs once per class (schema built at module load — negligible); validation walks schema entries per instance (O(rules) per check — trivial vs I/O-bound request handling; cache compiled schemas (not re-derived) where validation runs hot).

**Mentor note** — run `validate()` on valid vs invalid instances (empty list vs complete violation list) — centralized enforcement demonstrated in two calls. Exercise: add one rule kind (pattern-match) end to end (decorator → schema entry → validate branch → test) — the full loop in under an hour. Review gate: validation logic inside decorator bodies fails review (register, don't check).

### 2) **Running validation** (schema + instance → error list)

**Definition** — the `validate(instance)` contract: read the class schema (metadata channel or registry), walk entries, run each rule against the instance value, collect *all* violations (not first-failure — forms need complete error lists), return `string[]` (empty = valid). Nested objects recurse (child schemas per nested class); arrays map per element (index-tagged errors: `items[2].price<min`).

**What problem it solves / history** — first-failure validation (`throw` on first violation — users fixing forms one error per submit round-trip) frustrated users and hid error interactions (fixing price revealed stock — sequential discovery). Error-list validation (all violations per run) powers complete form rendering, API 422 bodies with full details, and config-load diagnostics listing every problem before exit.

**Modern guidance** — as of TypeScript 5.9 era, return error lists (never throw on first violation — collect-then-decide); tag errors with paths (`address.city<min`, `items[0].price<min` — locators, not just messages); recurse into nested decorated classes (schemas compose — child `validate()` results prefixed by parent path); keep validators pure (instance in, errors out — no mutation, no I/O, trivially testable).

**Runnable example** — complete error lists with paths (good vs bad, `tsc --strict`):

```typescript
// good — all violations listed with paths (forms render completely, APIs return 422 bodies fully)
type Rule2 = { min?: number };
const SCH2 = new Map<string, Rule2>([["age", { min: 0 }], ["score", { min: 10 }]]);
function validate2(inst: Record<string, unknown>): string[] {
  const out: string[] = [];
  for (const [k, r] of SCH2) {
    const v = inst[k] as number;
    if (r.min !== undefined && v < r.min) out.push(`${k}<min`);
  }
  return out; // complete list (every violation per run — no sequential discovery)
}
console.log(validate2({ age: -1, score: 5 }).join(",")); // age<min,score<min — both (forms fixed in one round-trip)
// bad — throw on first violation (users fix one error per submit — sequential discovery frustration)
// fix — collect-then-return (error lists power complete rendering + full 422 bodies + config diagnostics)
```

```typescript
// good — nested schemas recurse with path prefixes (composition across classes)
function validateNested(user: { name: string; addr: { city: string } }): string[] {
  const out: string[] = [];
  if (user.name === "") out.push("name:required");
  if (user.addr.city === "") out.push("addr.city:required"); // path-tagged (locator, not just message)
  return out;
}
console.log(validateNested({ name: "", addr: { city: "" } }).join(",")); // name:required,addr.city:required — nested paths composed
// bad — flat error strings ("invalid input" — unlocatable; forms can't highlight, APIs can't detail)
// fix — path-tagged errors (every violation locatable — rendering + diagnostics precise per path)
```

```typescript
// good — pure validators (instance in, errors out — no mutation, no I/O, testable in isolation)
function isValidEmail(s: string): boolean { return s.includes("@"); } // pure rule unit (testable alone)
function validateForm(email: string): string[] {
  return isValidEmail(email) ? [] : ["email:format"]; // pure composition (rules + runner, both side-effect-free)
}
console.log(validateForm("a"), validateForm("a@b").length); // ["email:format"] 0 — invalid listed completely, valid empty
// bad — validators mutating instances (normalizing + validating in one pass — side effects hide in checks)
// fix — validate pure (errors out); normalize separately (explicit transform step — phases separated, each testable)
```

**Common confusion** — "collecting all errors is slower" — validation walks rules once either way (throw-first *aborts* early — marginally faster per invalid input, catastrophically slower per *user* (round-trips); collect-all optimizes the human loop, not the CPU loop). "paths overcomplicate" — paths *are* the API (forms highlight by path, 422 bodies detail by path, config errors locate by path) — unlocated errors are unactionable regardless of message quality. "pure validators can't access context" — pass context explicitly (`validate(inst, ctx)` — request locale, tenant rules as arguments, not globals; purity preserved, context available).

**Performance note** — validation is O(rules × nesting) per instance (trivial vs I/O — forms/APIs/config-loads all wait on slower things); compiled schemas (pre-resolved rule functions, not re-derived per call) keep hot paths flat; error-list allocation per run negligible.

**Mentor note** — submit one invalid form against throw-first vs collect-all validators (one error per round-trip vs all errors at once) — user experience made visceral in two submits. Exercise: convert one throw-first validator to error-list with path tags and update its consumers (forms/APIs) to render completely — UX dividend in one refactor. Review gate: throw-on-first-violation validators fail review (collect, tag, return).

### 3) **Decorators vs schema objects** (annotation locality vs central explicitness)

**Definition** — two homes for validation rules: *decorators* (`@Min(0) age` — rules co-located with fields; schema derived) vs *schema objects* (Zod/Yup-style: `z.object({ age: z.number().min(0) })` — rules centralized in one expression, types *inferred from* the schema). Decorators optimize field-locality (rule visible where data shaped); schemas optimize explicitness (whole contract in one readable expression, no decorator machinery).

**What problem it solves / history** — decorator-only validation hid the *whole contract* (rules scattered per field across files — "what does a valid User look like?" unanswerable without reading the class end to end); schema-only validation hid *field intent* (central file growing to thousands of lines, distant from the classes it constrained — drift between schema and class). The choice is locality-vs-explicitness per project (small co-located teams favor decorators; API-boundary teams favor schemas) — made deliberately, not by habit.

**Modern guidance** — as of TypeScript 5.9 era, choose decorators when rules evolve *with* fields (domain classes owned alongside their constraints — co-location wins); choose schema objects at *boundaries* (API inputs, config files, form payloads — whole-contract readability + inference wins); never both for the same fields (dual sources drift — one home per validated shape, enforced by review). Zod-style `z.infer` gives schema-first typing without decorators where boundaries dominate.

**Runnable example** — locality vs explicitness, chosen per home (good vs bad, `tsc --strict`):

```typescript
// good — schema object at the boundary (whole contract in one expression, types inferred)
interface UserIn { name: string; age: number }
function parseUser(raw: unknown): UserIn | undefined {
  if (typeof raw !== "object" || raw === null) return undefined; // boundary guard (explicit, central, testable)
  const r = raw as Record<string, unknown>;
  if (typeof r["name"] !== "string" || typeof r["age"] !== "number") return undefined;
  return { name: r["name"], age: r["age"] }; // parsed contract (schema-first typing, hand-rolled here; Zod infers this shape)
}
console.log(parseUser({ name: "a", age: 1 })?.name.toUpperCase() ?? "bad"); // A — boundary parsing (explicit contract, inferred types)
// bad — decorator rules on boundary DTOs (framework-coupled validation at the system's edge — boundaries deserve explicit schemas)
// fix — decorators inside (domain co-location), schemas at edges (boundary explicitness): one home per shape
```

```typescript
// good — decorator rules inside the domain (co-located with fields they constrain)
// (Product + @Range from promise 1: rules travel with the class — domain locality preserved)
class Item {
  price = 0; // rule lives HERE via decorator (see promise 1's @Range — co-location demonstrated there)
}
console.log(new Item().price.toFixed(0)); // 0 — domain rules co-located (evolve with fields, visible at declaration)
// bad — central schema file for 200 domain fields (thousand-line validator distant from every class it constrains — drift by distance)
// fix — per-home choice (domain: decorators; boundaries: schemas — locality vs explicitness decided per shape, not globally)
```

```typescript
// good — never both homes for one shape (single source of validation truth per validated type)
function singleHome(): string { return "decorators-inside XOR schemas-at-edges (never both — dual sources drift)"; }
console.log(singleHome()); // rule stated (one home per shape — enforced by review, not hoped)
// bad — @Min(0) on the field AND z.number().min(0) in the boundary schema (dual sources: disagree silently on change — which wins?)
// fix — pick per shape (domain-owned → decorators; boundary-owned → schema; migrated shapes move homes explicitly with tests)
```

**Common confusion** — "schemas replace decorators" — schemas replace decorators *at boundaries* (explicit contracts win); decorators win *inside domains* (co-location wins) — different homes, different winners. "decorators can't infer types" — decorator-collected schemas *can* drive inference (validate() + `as` narrowing per rule kinds — weaker than Zod's `z.infer`, stronger than nothing; choose per precision need). "one home globally" — per-*shape* homes (domain shapes decorate, boundary shapes schematize — global uniformity in either direction mismatches half the shapes).

**Performance note** — decorator schemas build once per class (definition time); schema objects build once per module (import time); validation runs equivalently per instance (rule walks — same complexity either home). Choice is organizational (locality vs explicitness), never performance.

**Mentor note** — show one shape validated both ways side by side (decorated class + boundary schema duplicating rules) and ask "which updates when the field changes?" (both must — drift demonstrated) — then delete one home (single source restored). Exercise: classify five validated shapes by home (domain → decorators; boundary → schema) and migrate the mis-homed two — placement corrected per shape. Review gate: dual-homed validation fails review (one home per shape).
