## 2.1. Legacy experimental decorators — compared

### 1) **Legacy vs standard signatures** (different parameters, different returns)

**Definition** — legacy decorators (`experimentalDecorators: true`, TS 1.6+): class → `(target: Function)`; method → `(target: object, key: string, descriptor: PropertyDescriptor)` returning descriptor-or-void; property → `(target: object, key: string)` (no descriptor — properties don't exist yet); parameter → `(target: object, key, index: number)`. Standard (TS 5.0+): `(value, context)` per kind with same-kind returns. Different proposals, incompatible shapes — one file must pick one form (mixed forms confuse checkers and readers alike).

**What problem it solves / history** — TypeScript shipped legacy decorators in 2015 against a TC39 proposal that later changed *incompatibly* (the 2022 standard: different parameters, different evaluation order — legacy applies top-down per member in declaration order vs standard bottom-up; see 1.2). TS 5.0 implemented the standard *alongside* (flag-free), keeping legacy behind its flag for Angular/NestJS/TypeORM-era ecosystems that standardized on it. Two forms coexist by necessity (migration takes years), never by preference.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), write new decorators standard (no flag, portable, proposal-stable); maintain legacy where frameworks require (Angular DI, NestJS routing, TypeORM entities — version-pinned interop, recorded per file); migrate one decorator at a time (same behavior, new signature — tests green throughout). Never mix forms in one file (checker accepts per-decorator flags awkwardly; readers accept never).

**Runnable example** — same behavior, both signatures (`tsc --strict`; legacy fences verified with `--experimentalDecorators`):

```typescript
// good — standard method wrapper (no flag; value + context; same-kind return)
function timedStd<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); };
}
class SvcStd {
  @timedStd
  work(n: number): number { return n * 2; }
}
console.log(new SvcStd().work(21).toFixed(0)); // 42 — standard form (flag-free, portable)
```

```typescript
// legacy form (requires --experimentalDecorators; verified with the flag — see LOG unit 91):
// function timedLegacy(target: object, key: string, descriptor: PropertyDescriptor): PropertyDescriptor {
//   const fn = descriptor.value as (...args: unknown[]) => unknown; // descriptor surgery (legacy mechanic)
//   descriptor.value = function (...args: unknown[]): unknown { return (fn as (...a: unknown[]) => unknown).apply(this, args); };
//   return descriptor; // mutated descriptor returned (vs standard same-kind replacement)
// }
// class SvcLeg {
//   @timedLegacy
//   work(n: number): number { return n * 2; }
// }
// console.log(new SvcLeg().work(21)); // 42 — same behavior, legacy signature (flag-gated, framework-required only)
// (kept commented: legacy needs --experimentalDecorators, incompatible with standard-form checking in one program)
```

```typescript
// good — migration side by side (same behavior, new signature, tests green throughout)
function loggedStd<This, Args extends unknown[], Ret>(
  fn: (this: This, ...args: Args) => Ret,
): (this: This, ...args: Args) => Ret {
  return function (this: This, ...args: Args): Ret { return fn.apply(this, args); };
}
class SvcMig {
  @loggedStd
  calc(n: number): number { return n + 1; }
}
console.log(new SvcMig().calc(41).toFixed(0)); // 42 — migrated decorator (behavior identical, signature standard)
// bad — mixed forms in one file (legacy @Inject beside standard @logged: checkers flag awkwardly, readers never adapt)
// fix — one form per file (migrate fully per file: same behavior, new signatures, tests green throughout)
```

**Common confusion** — "legacy is deprecated" — *maintained* (flag + emit stable; Angular/NestJS depend on it) but not *recommended* (new code writes standard) — deprecated-never vs recommended-never differ. "standard covers all legacy uses" — parameter decorators and `emitDecoratorMetadata` have no standard equivalents yet (see 2.2–2.3 for the gaps keeping legacy alive) — migrate what maps, keep what doesn't (recorded). "migration is mechanical renaming" — signatures *and* evaluation order differ (legacy member application top-down vs standard bottom-up — order-sensitive stacks need re-verification, not just retyping).

**Performance note** — identical runtime profile (closures per wrapper either form); legacy descriptor mutation vs standard replacement compile equivalently — migration is semantics-preserving with zero performance delta (verify via behavior tests, not benchmarks).

**Mentor note** — implement one decorator in both forms side by side (same behavior, different parameters) — signatures compared directly teach more than migration guides describe. Exercise: migrate one legacy decorator (signature map + order re-verification + green tests) — mechanical plus careful in one task. Review gate: mixed-form files fail review (one form per file, migrated fully).

### 2) **`experimentalDecorators` flag and migration** (legacy needs flag; standard needs none)

**Definition** — `experimentalDecorators: true` enables legacy decorator *syntax* (`@dec` parsed as legacy when the flag is on and the signature matches legacy positions); standard decorators compile *regardless* (no flag — plain TS 5.0+ language). Migration path per decorator: rewrite signature (legacy positions → standard value+context), re-verify order (top-down member application → bottom-up), run behavior tests (green throughout), delete the flag when no legacy uses remain (flag removal as migration-complete signal).

**What problem it solves / history** — flag-off codebases couldn't parse `@` at all (legacy syntax error without the flag — adoption cliff); flag-on codebases parsed *both* ambiguously (standard-looking decorators checked against legacy positions when signatures overlapped — silent misinterpretation). Explicit per-form knowledge (which files use which form, tracked during migration) plus flag hygiene (on while legacy remains, off when gone) keeps both forms compiling correctly through multi-quarter migrations.

**Modern guidance** — as of TypeScript 5.9 era, keep the flag on while any legacy decorator remains (removing early breaks parsing, not just checking); migrate per file (all decorators in one file per PR — never mixed forms); delete the flag when the last legacy use migrates (flag-off + green CI = migration complete, verified mechanically). Track legacy count (grep `@` in legacy-form files quarterly — falling to zero, then flag deletion).

**Runnable example** — flag hygiene through migration (standard fences runnable flag-free):

```typescript
// good — standard decorator (no flag needed; compiles with or without experimentalDecorators)
function sealedStd<T extends new (...args: any[]) => object>(target: T): T {
  return target; // observe-only (registration shape — flag-independent standard form)
}
@sealedStd
class BoxStd {
  constructor(public n = 0) {}
}
console.log(new BoxStd().n.toFixed(0)); // 0 — standard (flag state irrelevant — plain language)
// bad — relying on flag-off to "prevent" legacy (new legacy-looking code errors opaquely instead of migrating deliberately)
// fix — flag on during migration (legacy parses), per-file migration (forms separate), flag off at completion (proof)
```

```typescript
// legacy shape (commented: needs --experimentalDecorators; behavior identical to standard above):
// function sealedLeg<T extends new (...args: any[]) => object>(target: T): T { return target; }
// class BoxLeg { constructor(public n = 0) {} }
// (@sealedLeg applied as @sealedLeg above class BoxLeg under the flag — same registration, legacy positions)
// (kept commented: single-program checking can't mix standard-form fences with legacy-form fences under one flag set)
export const migrated = true;
console.log(migrated ? "migrated-per-file" : "no"); // migrated-per-file — one form per file (migration granularity)
// bad — half-migrated files (standard @logged beside legacy @Inject: checkers cope awkwardly, readers never do)
// fix — per-file migration PRs (all decorators in the file, one form at the end, tests green throughout)
```

```typescript
// good — migration-complete signal (flag deleted, CI green, zero legacy uses remaining)
// tsconfig after migration: { "experimentalDecorators": <removed>, "strict": true, ... } (flag absence = proof)
// (documented as config evolution, not code: the flag's deletion is the migration's completion certificate)
export const done = true;
console.log(done ? "flag-deleted" : "no"); // flag-deleted — completion verified mechanically (not declared socially)
// bad — flag retained "just in case" post-migration (dead configuration inviting legacy regressions — new legacy code compiles silently)
// fix — delete on completion (flag-off + green = proof; flag-on-forever = migration theater)
```

**Common confusion** — "flag-off prevents legacy" — flag-off *breaks parsing* of legacy syntax (errors, not prevention — prevention is migration + deletion). "one file can mix carefully" — mixed files check awkwardly (per-decorator form resolution) and read impossibly (two mental models per file) — careful mixing is still mixing. "flag deletion is cosmetic" — deletion *proves* zero legacy uses remain (green CI without the flag = mechanical completion proof; social declarations prove nothing).

**Performance note** — flag state has zero runtime profile (parse-time only); migration costs authoring minutes per decorator (signature map + order check + green tests); flag-on-forever costs legacy lock-in (new syntax unavailable in mixed files, toolchain assumptions frozen).

**Mentor note** — delete the flag on a migrated branch and watch CI stay green (completion proof) vs fail on missed legacy uses (incomplete migration itemized) — deletion as verification in one command. Exercise: migrate one file fully (signatures + order + tests) and count the behavioral diffs (zero expected — migration preserves behavior by contract).

### 3) **When legacy stays** (frameworks requiring legacy emit)

**Definition** — legacy stays where frameworks *require* its emit: Angular (DI + templates on legacy parameter decorators + metadata), NestJS (routing/controllers/providers on legacy + `emitDecoratorMetadata`), TypeORM-era stacks (entity decorators with legacy positions). Staying is version-pinned interop (framework major versions dictate the form — upgrade when *they* migrate, not before), recorded per file (`// legacy: NestJS 10 requires experimental emit`), never preference.

**What problem it solves / history** — premature standard migration in framework codebases (rewriting NestJS controllers to standard decorators NestJS couldn't read) broke DI/routing silently (frameworks reflect on legacy metadata shapes — standard-emitted classes register as unknown). Framework-major upgrades (NestJS standard-decorator support landing per version) define migration windows — staying until the window opens is discipline; migrating early is breakage with modern syntax.

**Modern guidance** — as of TypeScript 5.9 era, pin legacy to framework majors (Angular/NestJS/TypeORM versions in package.json + comment links to their migration guides); isolate legacy to framework-boundary files (controllers/entities/modules — application logic stays standard-decorated or undecorated); re-evaluate per framework major (upgrade notes first line: decorator-form support — migrate in the upgrade PR, not after).

**Runnable example** — pinned interop, isolated boundaries (standard fences runnable; legacy documented):

```typescript
// good — application logic standard-or-bare (framework boundary isolated to controllers/entities)
// (legacy: NestJS 10 controllers use @Controller/@Get (legacy positions + metadata) — pinned per package.json)
// Standard-decorated service (application side — migratable independently of framework majors):
function singleton<T extends new (...args: any[]) => object>(target: T): T {
  return target; // marker (application services need no legacy — standard or bare throughout)
}
@singleton
class UserService {
  find(id: string): string { return `user:${id}`; }
}
console.log(new UserService().find("u").toUpperCase()); // USER:U — application side migratable now (boundary isolated)
// bad — standard decorators on framework-read positions (framework reflects legacy shapes — standard-emitted classes register as unknown)
// fix — legacy at framework boundaries (pinned, recorded), standard everywhere else (migrated independently)
```

```typescript
// good — version pin documents the stay (package.json + comment + migration-guide link, reviewed per major)
// (legacy: TypeORM 0.3 entities use @Entity/@Column (legacy positions) — recorded per entity file)
// Standard-decorated helper beside legacy entities (coexistence per FILE, never mixed per file):
function audited<T extends new (...args: any[]) => object>(target: T): T {
  return target; // application-side marker (standard form — file contains zero legacy decorators)
}
@audited
class AuditLog {
  constructor(public msg = "m") {}
}
console.log(new AuditLog().msg.toUpperCase()); // M — mixed forms per BOUNDARY (file granularity, never mixed per file)
// bad — migrating framework-boundary files early (DI/routing breaks silently — framework reads legacy shapes only)
// fix — upgrade-window migration (framework major lands standard support → migrate in that upgrade PR)
```

```typescript
// good — re-evaluation trigger documented (upgrade notes first line: decorator support)
// (legacy: revisit on NestJS major per UPGRADE.md checklist item — scheduled, not hoped)
export const frameworkForm = "legacy-pinned"; // stated (audit finds it; upgrades revisit it)
console.log(frameworkForm); // legacy-pinned — pin visible (grep-able, reviewable, expirable)
// bad — unrecorded legacy (no pin, no link, no revisit — permanent by neglect, discovered at framework EOL)
// fix — pin + link + revisit trigger per legacy file (staying is a decision with an expiry, not a default)
```

**Common confusion** — "staying means legacy is fine" — staying means *pinned interop* (version-bound, recorded, revisited) — fine *conditionally*, never by default. "frameworks will support both forever" — majors migrate (Angular/NestJS roadmaps move toward standard — pins expire per major; unrecorded stays become surprise migrations). "isolation doubles work" — boundary files are few (controllers/entities/modules — the framework surface); application code (services/logic — the majority) migrates freely regardless.

**Performance note** — legacy emit costs decorator-helper code per file (`__decorate` helpers — bytes × decorated files); standard emit is leaner (direct calls) — staying pays helper bytes per boundary file until migration windows open (documented cost of pinned interop).

**Mentor note** — `grep -r experimentalDecorators` + framework versions quarterly (pins current? migration windows open?) — interop backlog made countable. Exercise: identify one framework-boundary file migrated early (broken DI/routing) vs one pinned correctly — staying-vs-early contrast in production behavior. Rule: legacy without pin+link+revisit fails review.
