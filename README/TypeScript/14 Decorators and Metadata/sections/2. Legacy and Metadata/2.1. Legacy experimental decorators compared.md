## 2.1. Legacy experimental decorators — compared

TypeScript supports two decorator models. With experimentalDecorators true, the configured program checks and emits the legacy model. With it false or omitted, TypeScript 5.0+ uses the newer standard-form model. Moving a decorator to a different source file inside the same program does not give that file another flag value. A migration must respect the consumer's signature, emit and metadata contracts.

This lesson was checked with TypeScript 7.0.2 and run with Node 20.20.2, 2026-10-13. Both programs use emitted JavaScript; native execution of decorator source is a separate [runner constraint](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>).

### 1) **Different signatures and return contracts**

A legacy method decorator receives a target object, a string/symbol member key and a property descriptor. It may change/return that descriptor. A standard-form method decorator receives the method value and a context object; it may return a replacement method of the compatible signature. The same @ syntax therefore has different call/checking contracts. [TypeScript 5.0's comparison](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#differences-with-experimental-legacy-decorators) establishes the two models.

Create `standard/src/index.ts`:

```typescript
export {};
function trace(label: string) {
  console.log(`evaluate:${label}`);
  return function <This, Args extends unknown[], Result>(
    method: (this: This, ...args: Args) => Result,
    context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Result>
  ): (this: This, ...args: Args) => Result {
    console.log(`apply:${label}:${String(context.name)}`);
    return function (this: This, ...args: Args): Result {
      console.log(`enter:${label}`);
      try { return method.apply(this, args); }
      finally { console.log(`exit:${label}`); }
    };
  };
}
class Service {
  offset = 1;
  @trace("outer")
  @trace("inner")
  work(value: number): number {
    if (value < 0) throw new RangeError("negative input");
    return value + this.offset;
  }
}
const service = new Service();
console.log("result:", service.work(41));
try { service.work(-1); }
catch (error: unknown) {
  console.log("failure:", error instanceof RangeError ? "RangeError" : "other");
}
```

The generic wrapper preserves the receiver, argument tuple and result type. It calls the original method using that receiver and logs exit in finally, including when the method throws. The context supplies the decorated member name.

Create `legacy/src/index.ts` separately:

```typescript
export {};
type Work = (this: { offset: number }, value: number) => number;
function trace(label: string) {
  console.log(`evaluate:${label}`);
  return function (
    _target: object,
    key: string | symbol,
    descriptor: TypedPropertyDescriptor<Work>
  ): TypedPropertyDescriptor<Work> {
    console.log(`apply:${label}:${String(key)}`);
    const method = descriptor.value;
    if (!method) throw new TypeError("expected a method descriptor");
    descriptor.value = function (this: { offset: number }, value: number): number {
      console.log(`enter:${label}`);
      try { return method.call(this, value); }
      finally { console.log(`exit:${label}`); }
    };
    return descriptor;
  };
}
class Service {
  offset = 1;
  @trace("outer")
  @trace("inner")
  work(value: number): number {
    if (value < 0) throw new RangeError("negative input");
    return value + this.offset;
  }
}
const service = new Service();
console.log("result:", service.work(41));
try { service.work(-1); }
catch (error: unknown) {
  console.log("failure:", error instanceof RangeError ? "RangeError" : "other");
}
```

This legacy wrapper deliberately targets the narrower Work contract, rather than pretending every descriptor holds the same method shape. It checks for a method value, replaces descriptor.value and returns the descriptor. The receiver still supplies offset. Neither form is just a renamed version of the other's parameters.

### 2) **Two configured programs and a real migration boundary**

Create `standard/tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "commonjs",
    "lib": ["es2022", "dom"],
    "types": [],
    "rootDir": "src",
    "outDir": "dist",
    "noEmitOnError": true,
    "experimentalDecorators": false
  },
  "include": ["src/**/*.ts"]
}
```

Create `legacy/tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "commonjs",
    "lib": ["es2022", "dom"],
    "types": [],
    "rootDir": "src",
    "outDir": "dist",
    "noEmitOnError": true,
    "experimentalDecorators": true
  },
  "include": ["src/**/*.ts"]
}
```

From their common parent directory, run `tsc -p standard/tsconfig.json` and `tsc -p legacy/tsconfig.json`, then `node standard/dist/index.js` and `node legacy/dist/index.js`. Both builds and runs exit 0. Each program includes only its own source directory and selects one decorator model; types and rootDir are explicit for this current compiler baseline.

Check the incompatible settings with `tsc -p standard/tsconfig.json --experimentalDecorators --noEmit` and `tsc -p legacy/tsconfig.json --experimentalDecorators false --noEmit`. Both exit 1 with TS1241 and TS1270. The compiler parses the decorator syntax but rejects the supplied method signatures/return contracts. This is not repaired by splitting those declarations into different files under one configuration.

An independently compiled boundary can consume the resulting JavaScript. Save `consumer.cjs` in the common parent directory, after building both programs:

```javascript
require("./legacy/dist/index.js");
require("./standard/dist/index.js");
```

`node consumer.cjs` succeeds and prints the legacy trace followed by the standard trace. This verifies consumption of emitted artifacts with different compiler settings. Importing both raw source trees into one configured program would not reproduce that isolation. A real package boundary additionally needs tested declarations, module resolution and framework consumers; this small local fixture does not establish those integrations.

### 3) **Evaluation, application and observed behavior**

Both runs begin with evaluate:outer, evaluate:inner, apply:inner:work and apply:outer:work. Factory expressions evaluate top-down, then decorators on this method apply bottom-up in both models. The [legacy composition reference](https://www.typescriptlang.org/docs/handbook/decorators.html#decorator-composition) describes that order. Do not invent a legacy top-down application rule to explain migration.

On the successful call, the log order is enter:outer, enter:inner, exit:inner, exit:outer, then result:42. The outer replacement calls the inner replacement. On the failing call, both enter/exit pairs still appear and the caller prints failure:RangeError. Both traces are identical for this fixture: it preserves this method's result, receiver dependence and thrown failure.

That bounded evidence does not prove every decorator migration preserves behavior. Field initialization, parameter decorators, descriptor-specific features and metadata consumers need their own checks. The full [evaluation-order owner](<../1. Standard Decorators/1.2. Decorator evaluation and application order.md>) explains other decorator kinds; keep this comparison focused on the method stack actually executed.

### 4) **Compatible class shapes and legacy dependencies**

Some decorator functions can intentionally work under both models. This class decorator reads only the constructor value and returns nothing; it needs neither a legacy descriptor nor the newer context. Save `dual-class.ts` outside either source directory:

```typescript
export {};
function inspect(target: Function): void { console.log("class:", target.name); }
@inspect
class Dual {}
```

Run `tsc --strict --target es2022 --module commonjs --experimentalDecorators false --outDir dual-false dual-class.ts`, then `node dual-false/dual-class.js`. Repeat with true and dual-true. All four commands succeed and both runs print class:Dual. This compatible shape does not make the incompatible method wrappers portable across the flag settings. It also means a successful build after removing the flag is insufficient proof that every dependency has been migrated correctly.

If a consumer needs legacy parameter decorators or emitDecoratorMetadata, that requirement constrains the program using it. The standard-form model does not support those two legacy facilities, as the 5.0 comparison explains. The [metadata channel comparison](<./2.3. Symbol.metadata and the metadata proposal.md>) owns the separate stores and verified transition reader. Keep required legacy configuration until the actual supported consumer path is tested; do not predict a framework's migration schedule from the language release.

For application-oriented backend work, retain the user's NestJS-first route with the Fastify adapter. That framework track is planned in the [root curriculum](<../../../../../README.md>); this lesson teaches the language/compiler comparison and runs no NestJS, Angular or ORM integration. Plain application logic may remain undecorated while the framework boundary uses its required configuration.

### 5) **Common confusion**

The flag chooses the configured program's model, rather than resolving a different model per decorator or file. Both models accept @ syntax on the tested compiler but supply different arguments. Some class decorators overlap deliberately; method-specific acceptance must be tested. A matching result of 42 proves the tested method's behavior, rather than proving metadata compatibility or every order-sensitive migration.

### 6) **Performance note**

The emitted files contain different helper machinery (`__esDecorate` versus `__decorate`) and both wrappers execute real logging/calls. No size, allocation, checking-time or runtime benchmark was measured. Equal traces do not establish equal performance, and the standard-form model is not simply direct calls without helpers. Compare relevant artifacts and representative workloads before making a cost claim.

### 7) **Mentor note**

Ask the learner to predict the four definition-time log lines, then identify which configuration supplies each decorator's arguments. Swap the program flag and explain the diagnostics. A sound migration review lists the actual consumer requirements and verifies receiver, returns, failure behavior and metadata where used. Separate programs only when the resulting source/artifact boundary really supports independent settings; a folder name alone is not evidence.
