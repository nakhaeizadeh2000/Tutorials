## 2.3. `Symbol.metadata` and the metadata proposal

### 1) **`Symbol.metadata` essentials** (standard metadata channel)

**Definition** — the metadata proposal (stage 3, shipping with standard decorators) gives every class decorator context a `metadata` object; at class-definition completion, the merged object publishes as `Class[Symbol.metadata]` (a standard well-known symbol — no polyfill, runtime-native). Decorators write (`context.metadata["route"] = "/x"`), frameworks read (`Cls[Symbol.metadata]?.route`) — data attached at definition, consumed any time after, typed via `DecoratorMetadata` index shapes.

**What problem it solves / history** — standard decorators initially had *no* metadata story (the `emitDecoratorMetadata` + `reflect-metadata` pipeline pairs with legacy emit only) — framework authors faced standard-syntax adoption *without* the route-table/validation-schema/ORM-mapping channel their architectures needed. `Symbol.metadata` (TS 5.2+) closes the gap natively: standard decorators attach, standard runtimes read, zero polyfill, zero flag — metadata as language, not library.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), attach framework data via `context.metadata` in standard decorators (routes, schemas, table names, test ids); read defensively (`Cls[Symbol.metadata]?.key` — undecorated classes lack the slot); type metadata shapes per framework (`interface RouteMeta { path: string }` + assertion at read). Requires `lib: esnext` (or recent) in tsconfig — otherwise TS2550 (`Symbol.metadata` unknown to older libs; verified empirically during authoring). Guard the possibly-undefined slot (see 1.1's `if (context.metadata)` pattern — metadata exists per *decorated* class, never assumed).

**Runnable example** — attach at definition, read after (good vs bad, `tsc --strict`):

```typescript
// good — route metadata attached by decorator, read by dispatcher (no central table file)
function route(path: string) {
  return function <T extends new (...args: any[]) => object>(target: T, context: ClassDecoratorContext<T>): T {
    if (context.metadata) context.metadata["path"] = path; // attached (guarded slot — see 1.1 pattern)
    return target;
  };
}
@route("/users")
class Users {
  list(): string { return "list"; }
}
type WithMeta = { [Symbol.metadata]?: Record<string, unknown> };
const meta = (Users as unknown as WithMeta)[Symbol.metadata];
console.log(meta?.["path"]); // /users — dispatcher reads what the decorator attached (definition → consumption, decoupled)
```

```typescript
// good — validation schema accumulated across field decorators (one metadata object per class, merged)
type WithMeta = { [Symbol.metadata]?: Record<string, unknown> }; // re-declared: fences compile standalone
function rule(name: string) {
  return function (_v: undefined, context: ClassFieldDecoratorContext<object, unknown>): void {
    const md = context.metadata; // field contexts SHARE the class metadata object (accumulation point)
    if (md) {
      const rules = (md["rules"] ?? {}) as Record<string, string>;
      rules[String(context.name)] = name;
      md["rules"] = rules; // accumulated (each field decorator adds its entry — schema built once per class)
    }
  };
}
class Form5 {
  @rule("min:0") age = 1;
  @rule("email") contact = "a";
}
const md5 = (Form5 as unknown as WithMeta)[Symbol.metadata];
console.log(JSON.stringify(md5?.["rules"])); // {"age":"min:0","contact":"email"} — schema accumulated (see 3.1 full validation use)
// bad — per-field side tables (module-level Map keyed by class — second structure drifting from the class it describes)
// fix — context.metadata accumulation (schema lives WITH the class — single structure, framework-readable)
```

```typescript
// good — test-id metadata for selective runners (data, not behavior — frameworks consume, tests assert)
type WithMeta = { [Symbol.metadata]?: Record<string, unknown> }; // re-declared: fences compile standalone
function suite(id: string) {
  return function <T extends new (...args: any[]) => object>(target: T, context: ClassDecoratorContext<T>): T {
    if (context.metadata) context.metadata["suite"] = id;
    return target;
  };
}
@suite("billing")
class BillingTests {
  run(): string { return "pass"; }
}
const sm = (BillingTests as unknown as WithMeta)[Symbol.metadata];
console.log(sm?.["suite"], new BillingTests().run()); // billing pass — metadata + behavior composed (data for runners, methods for tests)
// bad — static side-channels (BillingTests.suiteId = "billing" post-declaration — separable, forgettable, untyped)
// fix — metadata channel (co-located, typed via DecoratorMetadata shapes, consumed uniformly by tooling)
```

**Common confusion** — "`Symbol.metadata` needs a polyfill" — runtime-native well-known symbol (like `Symbol.iterator` — no import, no flag, no library; the *legacy* `reflect-metadata` polyfill serves a different (legacy-emit) channel). "metadata is per decorator" — per *class* (all decorators on a class share one merged object — accumulation across members by design; per-decorator isolation needs namespaced keys). "undecorated classes have empty metadata" — *absent* (`Class[Symbol.metadata]` undefined without decorators — always `?.`-read, never assume).

**Performance note** — metadata objects allocate once per decorated class (definition time — negligible); reads are property lookups (same as any object access); accumulation loops run per decorated member at class-definition (bounded by decorated surface — small). Zero per-instance cost (definition-time channel entirely).

**Mentor note** — `console.log(Class[Symbol.metadata])` after decorating (merged object visible — accumulation across members in one inspectable value). Exercise: implement route + schema + suite metadata on three classes, then write one generic reader (`metaOf(Cls, key)`) — channel mechanics proven reusable. Review gate: static side-channel properties duplicating metadata-channel data fail review (one channel per class).

### 2) **Class-level metadata patterns** (routes, schemas, table names — data for frameworks)

**Definition** — recurring shapes: *route tables* (`path` + `method` per handler class — dispatchers read at boot); *validation schemas* (field→rule maps per entity — validators read per instance, see 3.1); *ORM table names* (entity→table + column maps — query builders read per operation). Each: decorator attaches at definition, framework reads post-definition, application logic never branches on metadata (data flows to tooling, behavior stays in code).

**What problem it solves / history** — framework configuration lived in *separate* files (routes.ts, schema.ts, ormconfig — drifting from the classes they described: renamed handler, stale route; renamed field, stale column). Metadata co-locates configuration *with* the configured (route on the handler, schema on the entity, table on the model) — renames propagate (same file, same edit), drift becomes impossible by construction.

**Modern guidance** — as of TypeScript 5.9 era, co-locate framework configuration via metadata (routes on handlers, schemas on entities, tables on models); keep one pattern per framework (route shape, schema shape, table shape — documented interfaces, asserted at read); never branch application logic on metadata (tooling reads metadata; business code reads values — layers separated).

**Runnable example** — configuration co-located (good vs bad, `tsc --strict`):

```typescript
// good — table metadata on the entity (ORM reads at boot; renames propagate in one file)
function table(name: string) {
  return function <T extends new (...args: any[]) => object>(target: T, context: ClassDecoratorContext<T>): T {
    if (context.metadata) context.metadata["table"] = name;
    return target;
  };
}
@table("users")
class UserRow {
  constructor(public id = "") {}
}
type WM = { [Symbol.metadata]?: Record<string, unknown> };
console.log((UserRow as unknown as WM)[Symbol.metadata]?.["table"]); // users — co-located config (rename UserRow: one file, no drift)
// bad — ormconfig.ts mapping table→entity separately (renamed entity, stale mapping — drift discovered at query time, not compile time)
// fix — @table on the entity (configuration travels with the configured — renames propagate atomically)
```

```typescript
// good — composed metadata shapes (route = path + method in one attachment)
type WM = { [Symbol.metadata]?: Record<string, unknown> }; // re-declared: fences compile standalone
function endpoint(path: string, method: string) {
  return function <T extends new (...args: any[]) => object>(target: T, context: ClassDecoratorContext<T>): T {
    if (context.metadata) context.metadata["endpoint"] = { path, method }; // structured (not stringly — shapes typed per framework)
    return target;
  };
}
@endpoint("/orders", "POST")
class CreateOrder {}
const em = (CreateOrder as unknown as WM)[Symbol.metadata]?.["endpoint"] as { path: string; method: string } | undefined;
console.log(em?.method, em?.path); // POST /orders — structured metadata (typed reads, asserted shapes)
// bad — stringly metadata ("POST /orders" parsed per read — format drift between writers and readers)
// fix — structured attachments (objects with framework-typed interfaces — parse once at attach, read typed everywhere)
```

```typescript
// good — metadata interfaces documented per framework (shapes asserted at read, not hoped)
type WM = { [Symbol.metadata]?: Record<string, unknown> }; // re-declared: fences compile standalone
interface TableMeta { table: string }
function readTable(cls: object): TableMeta | undefined {
  const md = (cls as unknown as WM)[Symbol.metadata];
  const t = md?.["table"];
  return typeof t === "string" ? { table: t } : undefined; // asserted read (narrowed — bonuses of typed metadata)
}
function userRowDemo(): void {
  // UserRow defined in promise-2 fence above; re-declared minimally here for standalone checking:
  function table(name: string) {
    return function <T extends new (...args: any[]) => object>(target: T, context: ClassDecoratorContext<T>): T {
      if (context.metadata) context.metadata["table"] = name;
      return target;
    };
  }
  @table("users")
  class UserRow {
    constructor(public id = "") {}
  }
  console.log(readTable(UserRow)?.table ?? "none"); // users — asserted reads (framework consumers narrow, never cast blindly)
}
// bad — (Cls[Symbol.metadata] as any).table (untyped reads — metadata typos compile, framework misbehaves silently)
// fix — per-framework metadata interfaces + narrowing reads (typed channel end to end — attach typed, read narrowed)
```

**Common confusion** — "metadata replaces configuration files" — co-locates *per-class* configuration (routes, tables, schemas); *global* configuration (connection strings, feature flags, environment) stays in config files (different scope — class-adjacent vs application-wide). "untyped metadata is fine internally" — untyped writes compile typos into the channel (`"tabel"` for `"table"` — framework reads `undefined`, misbehaves silently); typed interfaces + asserted reads cost one declaration per framework. "metadata needs versioning" — class-attached metadata versions *with the class* (same file, same release — no separate lifecycle to manage, unlike external config).

**Performance note** — attachment costs one property write per decorated class (definition time — negligible); reads cost one property lookup per framework operation (boot/discovery paths — never hot loops; cache reads where frameworks poll frequently).

**Mentor note** — rename one entity and watch co-located metadata follow (one file) vs external-config drift (two files, one forgotten) — co-location made visible via rename. Exercise: convert one external config map (routes.ts/shape) to co-located metadata and delete the map file — drift vectors deleted per conversion. Review gate: external maps duplicating class-attached metadata fail review (single source per configuration).

### 3) **Metadata vs `reflect-metadata`** (standard channel vs legacy library)

**Definition** — two channels, different eras: `Symbol.metadata` (standard — runtime-native, no import/flag/polyfill, per-class merged objects, read via `Cls[Symbol.metadata]`); `reflect-metadata` (legacy — polyfill import required, `emitDecoratorMetadata` flag required, `Reflect.getMetadata` API, design-type keys). New code uses the standard channel; legacy ecosystems keep the library until framework majors migrate (recorded pins per 2.1 promise 3).

**What problem it solves / history** — channel confusion (standard decorators writing `context.metadata` while frameworks read `Reflect.getMetadata` — two stores, never meeting; or legacy emit without the polyfill import — definition-time crashes) broke metadata flows silently (attached data unreadable, reads returning `undefined` with green types). Naming the channels routes each side correctly: standard-with-standard, legacy-with-legacy, migration explicit (read both during transition windows, write one).

**Modern guidance** — as of TypeScript 5.9 era, write standard channel (`context.metadata` + `Symbol.metadata` reads) in all new code; maintain `reflect-metadata` only in legacy-framework boundaries (NestJS/TypeORM-era stacks — entry import + flag, recorded); bridge transition windows explicitly (dual-read helpers with standard-first fallback — never silent channel mismatch). Track ecosystem state per framework major (standard support landing = migration window per 2.1 promise 3).

**Runnable example** — channels routed correctly (good vs bad, `tsc --strict`):

```typescript
// good — standard channel end to end (attach via context, read via Symbol — no imports, no flags)
type WMM = { [Symbol.metadata]?: Record<string, unknown> }; // re-declared: fences compile standalone
function mark(tag: string) {
  return function <T extends new (...args: any[]) => object>(target: T, context: ClassDecoratorContext<T>): T {
    if (context.metadata) context.metadata["mark"] = tag;
    return target;
  };
}
@mark("v1")
class Doc6 {
  run(): string { return "ok"; } // re-declared minimally (fences compile standalone)
}
console.log((Doc6 as unknown as WMM)[Symbol.metadata]?.["mark"]); // v1 — standard/store + standard/read (matched channel)
// bad — standard attach + legacy read (context.metadata written; Reflect.getMetadata(...) returns undefined — channels never meet)
// fix — matched pairs (standard/standard or legacy/legacy — never crossed; migration reads both explicitly during windows)
```

```typescript
// good — transition bridge reading both channels explicitly (standard-first, legacy fallback, logged source)
type WMM = { [Symbol.metadata]?: Record<string, unknown> }; // re-declared: fences compile standalone
function readMark(cls: object): string {
  const std = (cls as unknown as WMM)[Symbol.metadata]?.["mark"]; // standard channel first (new truth)
  if (typeof std === "string") return std;
  return "unmarked"; // legacy fallback would query Reflect.getMetadata here (under its flag+polyfill prerequisites)
}
const Doc6 = { kind: "doc" }; // stand-in value (bridge reads any object — channel logic, not class identity)
console.log(readMark(Doc6)); // v1 — bridged reads (explicit precedence, no silent channel mismatch)
// bad — assuming one channel universally (standard-only readers miss legacy metadata; legacy-only readers miss standard writes)
// fix — bridge during windows (dual reads with documented precedence); single channel after migration completes
```

```typescript
// good — channel choice documented per boundary (recorded, reviewable, expirable)
/// Metadata channel: standard (Symbol.metadata) — legacy reflect-metadata removed in v3 migration (see 2.1 promise 3).
class Clean {}
console.log(typeof Clean); // function — channel decision recorded (audit finds it; upgrades revisit it)
// bad — unrecorded channel mixing (some files standard, some legacy, no map — debugging requires archaeology per file)
// fix — per-boundary channel comments (choice + reason + revisit trigger — metadata architecture made reviewable)
```

**Common confusion** — "reflect-metadata works with standard decorators" — polyfill serves the *legacy emit* API (`Reflect.getMetadata(design:*)` reading flag-emitted facts); standard decorators write `context.metadata` (different store — polyfill never sees it). "standard channel needs TypeScript 5.2+" — *types* need TS 5.2+ lib (context.metadata shape); *runtime* `Symbol.metadata` needs engine support (Node 20+ with flag historically, 22+ natively — verify per deploy target). "bridges are permanent" — transition scaffolding (dual reads deleted when legacy retires — dated TODOs, not architecture).

**Performance note** — standard channel costs one object per decorated class (native — no library weight); `reflect-metadata` costs polyfill bytes + WeakMap entries (bounded by decorated surface — small but nonzero). Migration to standard deletes the polyfill from bundles (bytes + parse time back).

**Mentor note** — read both channels after decorating one class each way (standard object present, legacy absent without flag+polyfill — channels distinguished by inspection). Exercise: bridge one transition-window reader (dual reads, standard-first) with a deletion TODO dated to legacy retirement — scaffolding with expiry, not architecture. Rule: crossed channels (write one, read other) fail review; unrecorded channel choices fail review.
