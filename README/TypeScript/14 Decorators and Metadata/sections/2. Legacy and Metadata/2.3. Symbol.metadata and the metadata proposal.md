## 2.3. `Symbol.metadata` and the metadata proposal

A decorator can attach configuration that a later consumer reads from a class. The standard-decorator metadata channel uses `context.metadata` when writing and `Class[Symbol.metadata]` when reading. It does not reconstruct erased TypeScript types. You need the [standard decorator signatures](<../1. Standard Decorators/1.1. TC39 standard decorators classes methods fields.md>) before this lesson.

Verified 2026-10-18 with TypeScript 7.0.2 and emitted JavaScript on Node 20.20.2 and 22.18.0. These runtimes needed symbol initialization in the examples. The metadata proposal is a proposal implemented by the compiler; a declaration in `lib` is not evidence of native runtime support. The [TypeScript introduction](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-2.html) describes the compiler setup and initialization requirement; the [proposal](https://github.com/tc39/proposal-decorator-metadata) defines the channel.

### 1) **`Symbol.metadata` essentials**

The decorators on a class share a metadata object. Once decoration finishes, the object is available on the constructor. Writing to that object during decoration and reading from an instance are different operations: use the constructor to discover configuration, then apply it to values separately.

The compiler's declarations describe `Symbol.metadata`, but the JavaScript runtime must supply that symbol before decorated classes evaluate. The bootstrap below supplies it only when missing. It does not implement native decorator syntax or add automatic design-type reflection. TypeScript emits the decorator machinery used here, so run the emitted `.js` rather than sending decorator source directly to Node's type stripper.

Save the complete next fence as `metadata.ts` in a directory without a project configuration. Compile with `tsc --strict --target es2022 --module commonjs --lib es2022,esnext.decorators,dom --outDir out metadata.ts`, then run `node out/metadata.js`. No package dependency is needed.

```typescript
// metadata.ts
export {};
if (!Symbol.metadata) {
  Object.defineProperty(Symbol, "metadata", { value: Symbol("Symbol.metadata") });
}

function metadataOf(target: object): DecoratorMetadataObject | undefined {
  const value: unknown = Reflect.get(target, Symbol.metadata);
  // This provides an unknown-valued dictionary view, not a validated schema.
  return typeof value === "object" && value !== null
    ? value as DecoratorMetadataObject : undefined;
}

const routeKey = Symbol("route");
const fieldsKey = Symbol("fields");
function route(path: string) {
  return function (_target: Function, context: ClassDecoratorContext): void {
    if (!context.metadata) throw new Error("metadata symbol missing at decoration");
    context.metadata[routeKey] = path;
  };
}
function routeOf(target: object): string | undefined {
  const value = metadataOf(target)?.[routeKey];
  return typeof value === "string" ? value : undefined;
}

@route("/users")
class Users {}
class Plain {}
console.log(routeOf(Users)); // /users
console.log(metadataOf(Plain) === undefined); // true

function fieldsOf(metadata: DecoratorMetadataObject | undefined): readonly string[] {
  const value = metadata?.[fieldsKey];
  if (value === undefined) return [];
  if (!Array.isArray(value)) throw new Error("invalid field metadata");
  const input: readonly unknown[] = value;
  const checked: string[] = [];
  for (const item of input) {
    if (typeof item !== "string") throw new Error("invalid field metadata");
    checked.push(item);
  }
  return checked; // a checked copy; sparse slots are visited as undefined
}
function field(_value: undefined, context: ClassFieldDecoratorContext): void {
  if (!context.metadata) throw new Error("metadata symbol missing at decoration");
  // Copy inherited data before adding this class's field.
  context.metadata[fieldsKey] = [...fieldsOf(context.metadata), String(context.name)];
}
class BaseForm {
  @field name = "Ada";
}
class ExtendedForm extends BaseForm {
  @field email = "ada@example.test";
}
class InheritedForm extends BaseForm {}
console.log(fieldsOf(metadataOf(BaseForm)).join(",")); // name
console.log(fieldsOf(metadataOf(ExtendedForm)).join(",")); // name,email
console.log(fieldsOf(metadataOf(BaseForm)).join(",")); // name — not mutated
console.log(metadataOf(InheritedForm) === metadataOf(BaseForm)); // true
console.log(Object.hasOwn(InheritedForm, Symbol.metadata)); // false
const usersMetadata = metadataOf(Users);
if (!usersMetadata) throw new Error("route metadata missing");
usersMetadata[routeKey] = 123;
console.log(routeOf(Users)); // undefined — malformed route value rejected
let rejectedFields = 0;
for (const invalid of [["name", 1], ["name", , "email"], "name"]) {
  try { fieldsOf({ [fieldsKey]: invalid }); }
  catch (error) {
    if (!(error instanceof Error) || error.message !== "invalid field metadata") throw error;
    rejectedFields++;
  }
}
if (rejectedFields !== 3) throw new Error("field validation failed");
console.log("invalid field lists", rejectedFields); // invalid field lists 3
const sourceFields = ["name"];
const checkedFields = fieldsOf({ [fieldsKey]: sourceFields });
sourceFields[0] = "changed";
console.log("checked copy", checkedFields.join(",")); // checked copy name
```

The first read observes the route after class evaluation. `Plain` has neither its own metadata nor an ancestor providing it. The decorated subclass gets a metadata object that can read inherited entries; copying the inherited field list prevents a child from appending to the parent's array. An undecorated subclass can inherit the parent's constructor property, so an ordinary lookup and an own-property check answer different questions. That distinction matters when a framework discovers subclasses. The field-list reader iterates an unknown-valued array and constructs a checked string copy. Array iteration visits a sparse slot as undefined, so the malformed sparse list is rejected rather than silently skipped. Unlike an every-based element guard, this checks the absence represented by that slot too. The copied primitive strings also remain unchanged when the original array is edited afterward. Changing the route to a number rejects that value as a route. The final lines print `invalid field lists 3` and `checked copy name`, covering mixed elements, sparse slots, a non-array value and source-array mutation. These are local metadata policies, not a general validator for arbitrary objects or authorization.

To observe the missing prerequisite safely, remove only the bootstrap from a copy and run it in a fresh process without native `Symbol.metadata`. Compilation still succeeds, but the first decorator throws `metadata symbol missing at decoration`. Initializing the symbol after that class definition is too late: it cannot recreate the lost decoration context.

### 2) **Class-level metadata patterns**

A route, table name or field list is configuration for a consumer. Attaching it beside a declaration can make related edits easier to find, but strings can still be misspelled and different consumers can disagree about the shape. A decorator does not make configuration valid merely by co-locating it. Give each independent feature its own key, define its accepted values, and check values when reading an extensible metadata channel.

The example uses symbols to avoid accidental collisions between unrelated keys. The symbols are not secrets; reflection can discover them. A private `WeakMap` keyed by the metadata object is an alternative when data should remain inside one library. Keep the reference available to the consumer and decide whether inherited configuration is appropriate.

A field list registers which members matter; it does not validate an instance's field values. That later operation belongs in [Validation decorators](<../3. Patterns in Practice/3.1. Validation decorators field rules.md>). If a plain schema or an explicit registration call communicates the same configuration more clearly, use it. Metadata is an option with consumer and initialization costs, not a requirement to delete every external configuration map.

### 3) **Metadata vs `reflect-metadata`**

The legacy library uses `Reflect.defineMetadata` and `Reflect.getMetadata`. It stores data separately from `context.metadata`; importing it does not make a standard decorator write into its store. Compiler-emitted `design:*` metadata requires the legacy decorator pipeline, covered in [emitDecoratorMetadata](<./2.2. emitDecoratorMetadata and design types.md>). The [library's maintainer documentation](https://github.com/microsoft/reflect-metadata) explains its API and legacy support role.

Here is an actual reader for a transition where standard data takes precedence. In a new scratch directory, run `npm init -y` and `npm install --save-exact reflect-metadata@0.2.2`. Save `bridge.ts` below, compile with the same options as the first example, replacing its filename, and run `node out/bridge.js`. This example writes the legacy store explicitly so the two stores can be compared without another decorator syntax. It demonstrates class-level tags, not automatic parameter-type injection.

```typescript
// bridge.ts
import "reflect-metadata";
if (!Symbol.metadata) {
  Object.defineProperty(Symbol, "metadata", { value: Symbol("Symbol.metadata") });
}
const markKey = Symbol("mark");
function mark(tag: string) {
  return function (_target: Function, context: ClassDecoratorContext): void {
    if (!context.metadata) throw new Error("metadata symbol missing at decoration");
    context.metadata[markKey] = tag;
  };
}
function standardMark(target: object): string | undefined {
  const metadata: unknown = Reflect.get(target, Symbol.metadata);
  if (metadata === null || typeof metadata !== "object") return undefined;
  const value: unknown = Reflect.get(metadata, markKey);
  return typeof value === "string" ? value : undefined;
}
function readMark(target: object): string {
  const standard = standardMark(target);
  if (standard !== undefined) return standard;
  const legacy: unknown = Reflect.getMetadata("mark", target);
  return typeof legacy === "string" ? legacy : "unmarked";
}
@mark("v1")
class Modern {}
class Legacy {}
class Neither {}
Reflect.defineMetadata("mark", "v0", Modern);
Reflect.defineMetadata("mark", "legacy-v1", Legacy);
console.log(readMark(Modern)); // v1 — standard wins when both exist
console.log(readMark(Legacy)); // legacy-v1 — actual library fallback
console.log(readMark(Neither)); // unmarked
console.log(Reflect.getMetadata("mark", Modern)); // v0 — a different store
```

Document the precedence and the intended inheritance behavior: this bridge uses inherited lookup in both channels. Use the library's own-metadata API and an own-property check when the consumer requires only directly attached data. A malformed value is rejected as a string and the reader then tries the alternative store. Decide whether that fallback is acceptable for your migration; some applications should report corrupt metadata instead.

Choose a channel supported by the specific framework and toolchain you use. Do not infer framework support from compiler acceptance. A bridge should have a defined removal condition once consumers and producers agree on one store.

### 4) **Common confusion**

Declaring a library in `lib` describes an API to TypeScript; it does not create that API in Node. Emitted decorator helpers, the runtime metadata symbol and the legacy reflection library are three separate prerequisites. The bootstrap addresses the symbol; the compiler handles the decorated source; the bridge import supplies legacy APIs.

A string-array predicate using every would skip sparse slots. Checking only visited present elements is insufficient when later iteration expects a string at each position. The reader above rejects the missing value and copies accepted strings; readonly by itself would not create that snapshot.

Metadata also describes what a decorator wrote, not the complete TypeScript type of a class. A route string can be wrong, a metadata key can collide, and inherited objects can be shared. Typed readers and tests make those assumptions visible.

### 5) **Performance note**

Class decoration and metadata attachment occur when the class definition evaluates. Consumers add their own lookup, validation and dispatch work; instance field decorators may separately add initialization work. Copying the inherited field list allocates a new array for each registration and does work proportional to that list's length. The field-list reader also allocates a checked copy on each array read; registration then constructs its new list. A large schema may benefit from a different representation, which should be measured with its actual discovery and validation workload.

The symbol bootstrap and legacy library have distinct startup/dependency costs. Neither the compiler's type declarations nor a successful check measures those costs. No speed or memory advantage is promised here.

### 6) **Mentor note**

Ask a learner to predict four cases before execution: attached route, plain class, decorated child and undecorated child. A sound answer distinguishes absent data, inherited lookup and own metadata. Then change the copied field list to an in-place push and inspect whether the parent's list changes; explain why inheritance affects mutation.

For the bridge, remove the legacy write, then supply tags in both stores. The learner should explain each observed result and the precedence policy. Review the actual producer/consumer pair and bootstrap order before accepting a migration claim.
