## 5.1. Real production bugs caused by tooling misunderstandings

### 1) **Rename-symbol missed stringly references and broke runtime routing** (type-level rename complete; dispatch stale)

**Definition** — a `handler` → `processor` rename-symbol covered all *typed* occurrences (declaration, imports, type positions — green build, green tests) while a string-keyed dispatch table (`{ "handler": fn }` + `routes[name]()`) kept the old string (untyped reference invisible to rename) — runtime routing 404'd on every renamed path with fully-green CI (type-complete rename, runtime-incomplete).

**What problem it solves / history** — rename-symbol rewrites *bindings* (checker-resolved occurrences); stringly references (dispatch keys, event names, serialization tags, URL paths) live *outside* bindings (plain strings the checker never links to declarations). Renames spanning both worlds need two passes (server rename for bindings + text search for strings) — either alone leaves half the rename undone, silently.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), follow every rename-symbol with a string search for the old name (dispatch tables, event strings, serialized tags, URL paths — stringly references enumerated deliberately); prefer derived string keys (`keyof typeof` tables, template-derived routes per 09/3.2 — strings computed from bindings, renamed automatically); test renamed paths end to end (dispatch smoke per renamed route — runtime proof beyond type-green).

**Runnable example** — bindings renamed, strings hunted (good vs bad, `tsc --strict`):

```typescript
// good — derived dispatch keys (renamed automatically — strings computed from bindings, never listed)
const handlers = { processor: () => "P" } as const; // renamed WITH the binding (single edit — key follows declaration)
type HandlerKey = keyof typeof handlers; // "processor" — derived (stringly reference eliminated structurally)
function dispatch(k: HandlerKey): string { return handlers[k](); } // typed dispatch (keys checked — rename-safe by construction)
console.log(dispatch("processor")); // P — derived keys (renames propagate — no string hunt needed)
// bad — hand-listed string table beside renamed binding (old string lingering — runtime 404 with green CI)
// fix — derived keys (keyof/template tables — strings computed from bindings; renames propagate automatically)
```

```typescript
// good — post-rename string hunt (text search for old name per rename — stringly references enumerated deliberately)
function processor2(): string { return "p2"; } // renamed symbol (server rewrote bindings — strings hunted next)
const legacyNames = ["processor"]; // string mention (found by text hunt — evaluated: historical reference, kept deliberately)
console.log(processor2(), legacyNames.join(",")); // p2 processor — hunt completed (string references dispositioned per hit)
// bad — rename-symbol then done (stringly references unhunted — dispatch tables/event strings/tags stale silently)
// fix — rename + hunt (server pass for bindings, text pass for strings — both passes, every rename, no exceptions)
```

```typescript
// good — dispatch smoke per renamed route (runtime proof beyond type-green — renamed paths executed, not just compiled)
function routeP(path: string): string { return `route:${path}`; } // renamed path constant (smoke-tested below)
console.log(routeP("processor")); // route:processor — smoke executes (runtime proof — type-green PLUS dispatch-green)
// bad — type-green renames shipping without dispatch smoke (compile proving bindings, runtime unproven — 404s with green CI)
// fix — smoke renamed paths end to end (dispatch executed per rename — runtime proof beyond type-green, always)
```

**Common confusion** — "rename-symbol renames everything" — renames *bindings* (checker-resolved occurrences); strings/comments/configs need deliberate text passes (different tool, different review). "stringly references are tech debt" — *derived* string keys (keyof/template tables) eliminate the class structurally (see 09/3.2); *hand-listed* strings need hunt discipline per rename. "smoke tests duplicate unit tests" — unit tests cover *logic* (renamed functions behave); smoke covers *wiring* (renamed paths dispatch) — different layers, both needed post-rename.

**Performance note** — rename + hunt costs minutes per rename (server pass instant, text pass greppable); stringly-routing incidents cost 404-windows per missed reference (unbounded user impact per stale string). Derived keys cost zero ongoing (renames propagate automatically — hunt discipline needed only for hand-listed strings).

**Mentor note** — rename one dispatched handler live without the string hunt (green CI, 404 runtime — type-complete/incomplete in one rename). Exercise: convert one hand-listed dispatch table to derived keys and re-rename (propagation automatic — hunt discipline needed once, structurally thereafter). Review gate: renames without string-hunt evidence + dispatch smoke fail review.

### 2) **Disabled lint rule hid an `await` in a loop that serialized 10k requests** (velocity vs latency incident)

**Definition** — `no-await-in-loop` disabled "for velocity" (bulk-fetch loop `await`ing per iteration — 10k sequential requests, p99 latency incident) — the rule exists precisely because sequential-await *looks* correct (each iteration handled) while performing serially (latency × N instead of parallel batches). Disabled without a recorded reason, the incident class returned on the next bulk loop.

**What problem it solves / history** — per-iteration `await` reads naturally (`for (const id of ids) results.push(await fetch(id))` — correct results, sequential timing) — correctness masking performance (10k × 50ms = 8 minutes vs `Promise.all` batches in seconds). The lint rule flags the *pattern* (await-in-loop) forcing the decision explicit (sequential-deliberate with reason, or parallel batches); disabled rules skip the decision entirely (performance decided by accident).

**Modern guidance** — as of TypeScript 5.9 era, keep `no-await-in-loop` enabled (error, not warning — sequential awaits justify per site with reason comments); batch independent iterations (`Promise.all`/`map` with concurrency limits — parallel by construction); document deliberate sequential loops (ordered side effects, rate limits — reason recorded where the rule is suppressed per line, never globally).

**Runnable example** — batched vs serial (good vs bad, `tsc --strict`):

```typescript
// good — batched awaits (parallel by construction — latency bounded by slowest, not sum)
async function fetchAll(ids: string[]): Promise<string[]> {
  return Promise.all(ids.map(async (id) => `d:${id}`)); // batched (concurrent — latency ≈ max, never Σ)
}
console.log((await fetchAll(["a", "b"])).join(",")); // d:a,d:b — batched (rule satisfied structurally — no per-iteration await exists)
// bad — await-in-loop (sequential: 10k iterations × latency each — p99 incident with green tests)
// fix — Promise.all batches (parallel — or documented sequential where ordering/rate-limits demand it)
export {}; // module marker for top-level await in this runnable snippet
```

```typescript
// good — documented sequential loop (ordered side effects justify serial awaits — reason recorded per suppression)
export {}; // module marker (each fence compiles standalone — markers repeated per fence needing top-level await)
async function runSeries(steps: string[]): Promise<string[]> {
  const out: string[] = [];
  for (const s of steps) {
    // eslint-disable-next-line no-await-in-loop -- ordered side effects (sequence required — documented, reviewed)
    out.push(await Promise.resolve(s.toUpperCase())); // deliberate serial (reason recorded — rule satisfied via justification)
  }
  return out;
}
console.log((await runSeries(["a"])).join(",")); // A — documented sequential (suppression reasoned — velocity with latency awareness)
// bad — rule disabled globally "for velocity" (incident class returning on the next bulk loop — unrecorded, unreviewed)
// fix — per-line suppressions with reasons (ordered-side-effects documented — global disable never justified by one case)
```

```typescript
// good — concurrency-limited batches (parallel with backpressure — neither serial nor unbounded)
export {}; // module marker (each fence compiles standalone — markers repeated per fence needing top-level await)
async function fetchLimited(ids: string[], limit: number): Promise<string[]> {
  const out: string[] = [];
  for (let i = 0; i < ids.length; i += limit) {
    const batch = ids.slice(i, i + limit);
    out.push(...(await Promise.all(batch.map(async (id) => `d:${id}`)))); // await OUTSIDE inner loop (per-batch — rule satisfied structurally)
  }
  return out; // bounded parallelism (backpressure by construction — neither serial drift nor stampede)
}
console.log((await fetchLimited(["a", "b", "c"], 2)).join(",")); // d:a,d:b,d:c — limited batches (throughput + backpressure composed)
// bad — unbounded Promise.all over 100k ids (stampede — connection exhaustion, rate-limit bans, OOM on results)
// fix — chunked batches (limit documented per call site — parallelism bounded, backpressure explicit)
```

**Common confusion** — "await-in-loop is always wrong" — *ordered-side-effect* loops require serial awaits (migrations, sequenced writes — documented per suppression); *independent* iterations parallelize (batches by default). "disabling speeds delivery" — disabling speeds *typing* (rule silent) while slowing *production* (serial latency incidents) — velocity theater. "Promise.all everywhere" — unbounded concurrency stampedes (connection pools, rate limits, memory — chunk with limits, see above).

**Performance note** — serial awaits cost Σ(latencies) per loop (10k × 50ms = 8 minutes); batched cost max(latency) + overhead (seconds); chunked cost batches × max (bounded throughput + backpressure). Rule enforcement is latency insurance with zero steady cost.

**Mentor note** — run one 100-iteration loop serial vs batched live (seconds vs milliseconds wall-clock — latency made visceral, not theoretical). Exercise: find one await-in-loop and classify (ordered-side-effects → document; independent → batch; unbounded-all → chunk) — three dispositions, no global disable. Review gate: disabled `no-await-in-loop` without per-line reasons fails review.

### 3) **Unpublished `types` condition shipped `any` to every consumer** (untyped subpath, downstream infection)

**Definition** — a new package subpath (`lib/retry`) shipped with JS emit + `exports` JS conditions but *no* `types` condition (and no top-level `types` covering it): consumer imports resolved *implicit `any`* (untyped module — `noImplicitAny` errors at strict imports, silent `any` where suppressed) — every downstream use unchecked, every consumer codebase infected through one missing map entry (see 12/5.1 promise 4's fuller treatment).

**What problem it solves / history** — producer-green releases (tsc passing on sources, tests passing on behavior, publint *not gated*) shipped untyped subpaths repeatedly (each new subpath a fresh chance to forget `types`). The 12/3.3 + 16/2.3 gate trio (publint + attw + smoke per subpath) converts each chance into a blocking check — packaging bugs failing like type errors pre-publish instead of infecting consumers post-release.

**Modern guidance** — as of TypeScript 5.9 era, map `types` per exported subpath (no untyped public paths — checklist gate); smoke-consume every subpath in release CI (strict imports per path — untyped paths fail the gate, not the customer); treat consumer `any`-reports on subpaths as P0 packaging bugs (checking lost at the boundary infects unbounded downstream code).

**Runnable example** — mapped subpaths check (good vs bad, `tsc --strict`):

```typescript
// good — mapped subpath equivalent (types travel with the path — no untyped publics)
// (package.json shape per 12/3.3: exports RETRY entry with types condition — mapped, attw-verified, smoke-consumed)
export function retry<T>(fn: () => T, times: number): T { // mapped export (types condition present — attw checks per path)
  let last: unknown = null;
  for (let i = 0; i < times; i++) {
    try {
      return fn(); // success returns (typed — consumer checks against real declarations)
    } catch (e) {
      last = e; // recorded (retryable failures collected — last thrown if exhausted below)
    }
  }
  throw last instanceof Error ? last : new Error("exhausted"); // exhausted throws (documented throw contract — see 15/2.1 discipline)
}
console.log(retry(() => 7, 3).toFixed(0)); // 7 — mapped subpath (types present — consumers check, never any-fall)
// bad — exports RETRY entry with JS-only conditions (consumer import resolves implicit any — downstream any-infection at scale)
// fix — types per subpath (checklist gate 2 from 12/3.3 + attw matrix + smoke imports — trio blocking, always)
```

```typescript
// good — smoke per subpath per release (strict imports per public path — untyped paths fail the gate)
// (CI shape: for each exports subpath: strict tsc import (types resolve — attw matrix green per cell, smoke green per path)
// fix — subpath smoke matrix (one strict import per public path per release — minutes per release, zero consumer infections)
export function smoked(): string { return "smoked"; }
console.log(smoked()); // smoked — smoked surface (every public path imported under strict per release — coverage complete)
// bad — root-only resolution testing (subpaths resolving any/fallback — untyped publics shipping behind green root checks)
// fix — matrix per subpath (attw enumerates — coverage complete across paths AND kinds simultaneously)
```

```typescript
// good — consumer any-reports as P0 packaging bugs (checking lost at the boundary infects unbounded downstream code)
export function reported(): string { return "p0"; } // any-report triaged as packaging P0 (boundary fix, not consumer workaround)
// (process shape: consumer reports any on subpath → P0 packaging bug → types condition added → patch release → attw gate added)
// fix — P0 triage (any-reports on subpaths never closed as consumer-error — packaging owns consumer type outcomes absolutely)
// bad — "add // @ts-ignore" responses to consumer any-reports (workarounds pushed downstream — N shims for one missing entry)
// fix — boundary ownership (packaging owns consumer type outcomes — reports fixed at source, never worked around downstream)
console.log(reported()); // p0 — P0 triage (any-report → packaging fix → patch + gate — loop closed per report)
```

**Common confusion** — "`skipLibCheck` covers this" — `skipLibCheck` skips *checking declarations*, not *missing* ones (untyped subpath still resolves `any` — the flag is irrelevant to absent types). "consumers can declare the subpath" — pushing packaging work onto every consumer (N shims for one missing entry — commons tragedy with extra steps). "deep filesystem imports work around it" — unmapped deep paths bypass encapsulation (support contracts on internals — 12/3.3 promise-1 violation compounding per workaround).

**Performance note** — typed subpaths check per import (cached once per consumer program); `any`-resolved subpaths skip checks (faster compile, unbounded incident surface) — speed-vs-safety inverted destructively; always choose checking.

**Mentor note** — import one unmapped subpath under strict tsc and read the implicit-`any` error (or worse, the silence where suppressed) — packaging bugs made visible in one import. Gate: release CI imports every public subpath under strict (subpath smoke matrix — minutes per release, zero consumer infections).

### 4) **Stale `.tsbuildinfo` served week-old declarations to downstream builds** (incremental cache poisoning)

**Definition** — corrupted/stale `.tsbuildinfo` (killed mid-write builds, clock-skewed filesystems, cache restored across branches) made incremental builds *skip* changed files (fingerprints mismatching reality — downstream programs checking against week-old declarations while sources moved on): green incremental CI alongside red clean builds — divergence invisible until someone rebuilt from scratch.

**What problem it solves / history** — incremental-build trust (`.tsbuildinfo` as ground truth for what-changed) breaks exactly when the cache lies (crashes mid-write, cross-branch cache restores, timestamp games on network filesystems) — downstream checking stale declarations while sources evolved (fulfillment gaps *between* programs, invisible *within* each). Clean-build verification (periodic `--force`, cache-keyed restores, staleness quarantines) distinguishes cache poisoning from real green.

**Modern guidance** — as of TypeScript 5.9 era, build incrementally by default (speed — `.tsbuildinfo` per program, references ordered); verify clean periodically (nightly `--force` builds + clean release builds — staleness surfaced on schedule, not incidentally); key caches precisely (lockfiles + tsc version + tsconfig hash in cache keys — cross-branch restores invalidated structurally); quarantine on divergence (incremental-green + clean-red = cache poisoning until proven otherwise — rebuild, don't debug code).

**Runnable example** — incremental speed with clean verification (good vs bad, `tsc --strict`):

```typescript
// good — program shape supporting incrementality (composite-ready sources — declarations mediate downstream)
// (tsconfig shape per 13/3.2: composite + declaration + references — incremental programs with declaration contracts)
export function fresh(n: number): number { return n; } // composite-ready source (downstream checks declarations, never sources)
// (build shape: tsc --build (incremental — changed programs rebuild, others reuse declarations — seconds, not minutes)
// fix — composite programs (incremental by construction — downstream decoupled via declarations, rebuilds ordered)
console.log(fresh(1).toFixed(0)); // 1 — incremental speed (changed-only rebuilds — cache trusted when verified clean periodically)
// bad — single-program monorepos (everything rebuilds per change — minutes per save, diagnostics spanning unrelated packages)
// fix — references-ordered composite programs (incremental speed + scoped diagnostics — 13/3.2 + 19's architecture)
```

```typescript
// good — clean verification cadence (nightly force + release clean — staleness surfaced on schedule)
// (CI shape: per-PR incremental (fast feedback) + nightly --force (staleness sweep) + release clean-room (final proof))
// fix — verification cadence (incremental-green + periodic-clean — trust verified, never assumed across cache restores)
export function nightly(): string { return "verified-clean"; }
console.log(nightly()); // verified-clean — cadence stated (incremental per PR, clean nightly + per release — staleness window bounded)
// bad — incremental-only CI (cache poisoning invisible indefinitely — green builds on stale declarations for weeks)
// fix — clean cadence (nightly force + release clean-room — staleness surfaced on schedule, not incidentally)
```

```typescript
// good — cache keys invalidating precisely (lockfiles + tsc version + tsconfig hash — cross-branch restores miss by construction)
// (cache-key shape: key = lockfile-hash + tsc-version + tsconfig-hash + branch — restores valid only when all match)
// fix — precise cache keys (poisoning structurally impossible across branches/versions/configs — invalidation by construction)
export function keyed(): string { return "invalidated-precisely"; }
console.log(keyed()); // invalidated-precisely — cache hygiene (keys precise — stale restores miss, never poison)
// bad — branch-agnostic caches (main-branch .tsbuildinfo restored onto feature branches — downstream checking week-old declarations)
// fix — branch-aware keys (restores valid per branch/version/config — poisoning impossible by key construction)
```

**Common confusion** — "clean builds replace incrementality" — clean builds *verify* (periodic proof); incremental builds *accelerate* (per-change speed) — verification cadence plus incremental default (both, composed — speed daily, proof nightly/per-release). "cache poisoning is rare" — crash-killed builds, cross-branch restores, and clock skew make it routine at scale (weekly occurrences in busy monorepos — cadence catches routinely). "deleting caches fixes everything" — deletion *treats symptoms* (fresh state, same keying flaws — poisoning recurs); precise keys + cadence *cure* (structural prevention + scheduled verification).

**Performance note** — incremental rebuilds touch changed programs only (seconds vs full minutes); clean verification costs full builds periodically (nightly + release — scheduled off critical path); precise cache keys cost key-computation seconds (hashing lockfiles/configs — trivial vs poisoning incidents).

**Mentor note** — compare incremental vs clean build outputs once per quarter (divergence = poisoning caught — cadence proven valuable per catch). Exercise: poison one cache deliberately (restore foreign `.tsbuildinfo`) and watch incremental-green/clean-red diverge (poisoning demonstrated, quarantine practiced). Review gate: incremental-only CI without clean cadence fails review (trust verified, never assumed).
