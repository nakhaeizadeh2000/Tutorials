## 5.1. Real production bugs caused by tooling misunderstandings

### 1) **An internal rename is not a protocol migration**

The following are synthetic reproductions of failure mechanisms. They are not reports of a measured production incident, outage count or response-time percentile. The aim is to identify which evidence would detect the mistake and which repair addresses its cause.

A function's internal identifier and an external command string need not be the same contract. Renaming a function can leave a stable wire name intentionally unchanged. Conversely, changing a table key can break callers still sending the old name. Deriving a union with keyof checks that table's current keys; it does not update deployed clients, serialized messages or arbitrary configuration.

Reuse the complete pinned project from [typed linting](<../2. Lint Format and Checks/2.1. typescript-eslint rules and type-aware linting.md>), with its Node 20.20.2/native TypeScript 7.0.2 and compatible lint API setup. Add this file:

```typescript
// file: src/pitfalls.mts
function processor(): string { return "P"; }
const registry = { handler: processor };
type WireName = keyof typeof registry;
const stableName: WireName = "handler";
function dispatch(name: string): string {
  return name === "handler" ? registry[name]() : "missing";
}
console.log(dispatch(stableName), dispatch("processor"));
// const wrongName: WireName = "processor"; // TS2322: the internal function name is not a table key.
function load(id: string): Promise<string> { return Promise.resolve(id.toUpperCase()); }
async function batches(ids: readonly string[], limit: number): Promise<string[]> {
  if (!Number.isInteger(limit) || limit <= 0) throw new RangeError("positive integer limit required");
  const result: string[] = [];
  for (let start = 0; start < ids.length; start += limit) {
    const batch = ids.slice(start, start + limit);
    result.push(...await Promise.all(batch.map(load)));
  }
  return result;
}
console.log((await batches(["a", "b", "c"], 2)).join(","));
try { await batches(["a"], 0); }
catch (error: unknown) { console.log(error instanceof RangeError ? error.message : "unexpected"); }
```

Run `npm run check`, `npm run build` and `node dist/pitfalls.mjs`. Output is:

```text
P missing
A,B,C
positive integer limit required
```

Processor implements the existing handler wire command. Sending its internal name produces missing; it is not an automatically created alias. Activate wrongName independently to observe the compiler reject that local key claim. For a genuine wire rename, choose a compatibility or migration policy and test actual callers. The [actual server-rename owner](<../1. Language Server in Practice/1.2. Rename refactorings and code actions.md>) shows binding-specific edits; it does not promise every string or consumer is rewritten.

### 2) **Chunking still contains an await in a loop**

The same file processes one chunk at a time and starts each chunk's load calls before awaiting that chunk's results. It retains input order and waits before beginning the next chunk. This helper uses immediately resolved local Promises; it demonstrates control structure and output, not network throughput. A production worker pool may need different scheduling and failure policies, owned by the [async pattern lesson](<../../../18 Async Types and Standard Library/sections/2. Combinators and Cancellation/2.3. Sequential vs parallel patterns and tuple typing.md>).

No-await-in-loop is an ESLint core rule, not a typed typescript-eslint rule. Add this separate config beside the existing eslint.config.mjs:

```javascript
// file: eslint.loop.config.mjs
import base from "./eslint.config.mjs";
export default [...base, {
  files: ["src/pitfalls.mts"],
  rules: { "no-await-in-loop": "error" }
}];
```

Run `npx eslint --config eslint.loop.config.mjs src/pitfalls.mts`. It fails with no-await-in-loop at the batch await. The await is still inside the outer loop, even though Promise.all handles a group. The [rule reference](https://eslint.org/docs/latest/rules/no-await-in-loop) explains both the pattern it reports and valid serial dependencies. For this deliberate batch boundary, place this comment immediately before the result.push line, then rerun the same command:

```text
// eslint-disable-next-line no-await-in-loop -- Wait for this batch before starting the next one.
```

The scoped suppression makes that lint run pass. It does not make the implementation correct by itself. Validate the limit: zero would prevent progress in this loop, negative values would move backward, and fractional or nonfinite limits do not satisfy its intended contract. The baseline rejects invalid limits before scheduling work. An empty input and a limit larger than the array are also useful cases to check.

Sequential work can be required by dependencies, ordering or a rate policy. Promise.all does not itself impose a concurrency limit or cancel already started work on rejection. Choose a policy from the actual task; do not replace every reported loop with an unbounded map solely to silence lint.

### 3) **A source check can miss a packed-file defect**

A missing types condition is not automatically an untyped import: an appropriate adjacent declaration can still resolve. A blocked package subpath is another distinct failure. The [publishing fixture](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>) makes these differences observable.

For an actual missing-declaration failure, follow the [package-health reproduction](<../2. Lint Format and Checks/2.3. publint attw and package health checks.md>) that packs JavaScript but excludes declarations. Source checking remains green, publint fails and a fresh strict consumer reports TS7016. The tested attw version reports an untyped package but exits 0. Inspect the tarball and resolved declaration before proposing a consumer shim. A temporary workaround can be a deliberate decision; it should not obscure the producer's missing artifact or become proof that every consumer lost checking identically.

### 4) **Force rebuilding is not output cleanup**

A stale file in an output directory is not proof that build information is corrupt. In the [project-reference fixture](<../../../13 Configuration and Compiler Options/sections/3. Modules Emit and Projects/3.2. declaration composite project references.md>), an obsolete.txt sentinel survives `tsc --build --force`. Force treats projects as out of date; it does not erase every old output. Even clean removes known outputs rather than arbitrary files.

That owner also changes an implementation body without changing its declaration, then changes a signature to provoke a consumer error. These are different invalidation questions. When clean and incremental results differ, retain the inputs and inspect build logs, actual output paths and reused artifacts. A restart or cache deletion changing the result is a clue, not a definitive diagnosis of cache poisoning.

Choose cache keys and artifact cleanup from the real build inputs, tool versions and restore policy. A hash of a few metadata files is not a universal guarantee against stale files, source drift, tool bugs or a mismatched restored artifact set. The [incremental-build owner](<../../../19 Performance Project References and Scaling/sections/2. Project References and Builds/2.2. Incremental builds and tsbuildinfo discipline.md>) owns that workflow in depth.

### 5) **Common confusion**

A passing type relationship applies to the modeled values, not unvalidated external command strings. A lint suppression acknowledges a rule decision, not runtime success. A forced build performs work, not blanket cleanup. Diagnose those boundaries before adding more flags or deleting state.

These reproductions do not establish an incident severity for every project. Severity follows actual reach and consequences. Keep the missing contract and observed failure explicit so a repair can be reviewed and tested.

### 6) **Performance note**

Serial and concurrent scheduling can have different latency, resource and rate-limit consequences. This local helper has no network delays and supports no sum-versus-max timing claim. Tooling checks and cache restores also have environment-dependent costs. Measure the workload and relevant resource use before selecting a batch size or claiming that a lint rule or cache policy guarantees performance.

### 7) **Mentor note**

Ask the learner to predict both dispatch results and explain why keyof does not migrate callers. Then run the loop lint failure, justify the batch boundary and test the invalid limit. For the artifact cases, require the packed file list or obsolete-output observation before accepting an explanation. A good answer names the mechanism and test instead of inventing a production story around a green build.
