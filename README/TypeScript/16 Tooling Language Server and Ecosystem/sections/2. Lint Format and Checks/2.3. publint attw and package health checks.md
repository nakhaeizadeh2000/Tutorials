## 2.3. publint, attw, and package health checks

### 1) **Check the artifact consumers will install**

A package can pass its own source check while shipping a missing file or routing a consumer to the wrong declaration. Package-health tools add checks around that boundary. publint reports packaging problems according to its rules. Are The Types Wrong, whose CLI is attw, analyzes package contents for type-resolution and module-format problems in supported resolution modes. These checks overlap in some areas and leave other behavior to consumer tests.

Use the complete [publishing fixture](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>) through its first two sections. It creates producer, artifacts and consumer directories, emits a dual-format calc-kit package and installs its tarball into a separate consumer. Follow its actual file labels and commands, including the secret file and both public entry points. That owner explains exports, extension substitution and declaration routing; this lesson adds actual tool gates to the same artifact.

For these commands, use **TypeScript 7.0.2**, **Node.js 20.20.2**, **npm 10.8.2**, **publint 0.3.25** and **@arethetypeswrong/cli 0.18.5**. From producer, install the additional tools into a sibling tools directory:

```bash
npm install --prefix ../tools --save-dev --save-exact publint@0.3.25 @arethetypeswrong/cli@0.18.5
../tools/node_modules/.bin/publint ../artifacts/calc-kit-1.0.0.tgz --strict
../tools/node_modules/.bin/attw ../artifacts/calc-kit-1.0.0.tgz --profile node16
```

Both commands succeed for this fixture. publint may also print nonblocking suggestions. Strict elevates warnings to errors; it is not a promise that every possible issue becomes an error. The [publint CLI reference](https://publint.dev/docs/cli) documents directory and tarball inputs and packing choices. Passing this explicit tarball makes the checked artifact unambiguous. Rebuilding source later does not change an already packed tarball; pack again and inspect the file list.

### 2) **Read the resolution matrix and its scope**

attw's table names root and stats entry points and shows outcomes for its resolver modes. In this fixture, the node16 profile requires the relevant modern modes while ignoring legacy node10 failures. It does not turn the package into a legacy-compatible package. Use a stricter profile when that is actually your support contract, or a deliberately narrower one for a genuinely narrower contract.

The [attw CLI reference](https://github.com/arethetypeswrong/arethetypeswrong.github.io/blob/main/packages/cli/README.md) documents entry-point discovery, explicit entry-point options, profiles and ignored problems. Keep those choices visible in the release configuration. A green result after excluding a path says nothing about that excluded path. Missing types conditions also do not automatically imply any: the canonical fixture shows adjacent declaration files being found through extension substitution. Conversely, absent declarations can cause strict consumer errors.

The tool performs static analysis using its own dependencies and modeled resolutions. It does not execute every Node loader, bundle your application or establish TypeScript 7 compatibility merely because the application's tsc is version 7. Keep the fresh consumer checks: the canonical fixture compiles the installed package with the actual compiler and runs ESM and CommonJS consumers on the stated Node version. A supported bundler needs its own relevant integration check.

An [original ESM-only support question](https://github.com/arethetypeswrong/arethetypeswrong.github.io/issues/198) illustrates why a reported CJS incompatibility must be interpreted against an intended support policy. Do not silence arbitrary failures to obtain green, and do not add a dual build solely because an unrelated profile tests it. Name the supported consumers and choose checks that test that promise.

### 3) **Prove a failure, then state what a pass cannot prove**

In a disposable copy of producer, retain the built files on disk but change files to the following packing selection, then pack again into a separate bad-artifacts directory:

```json
{ "files": ["dist/*.mjs", "dist/*.cjs"] }
```

This fragment replaces only the files field, not the entire package.json. Run the two tool commands against the newly created bad tarball. publint reports missing type targets and fails. In the tested version, attw instead prints that the package does not contain types and exits 0 without the normal typed resolution matrix. That successful process exit is not proof of a typed package; retain an explicit requirement that declarations exist and strict consumers check. The source build can remain green because the source program still exists; it is the packed file selection that changed. Installing that tarball into a fresh strict consumer also fails its declaration check. Restoring files to `["dist"]`, rebuilding and repacking repairs the missing-artifact cause.

Now consider a different disposable variant. Keep all paths and declarations correct, but change add's implementation from left + right to left - right in both producer sources. Build, pack, run the health checks and install that new tarball into a fresh consumer. The compiler accepts number → number, and both package checks still pass. The observed add(2, 3) result becomes -1 instead of the expected 5. A behavioral assertion catches an error outside these gates' purpose.

For a compact assertion, save this additional consumer file and run it from the consumer directory after installation:

```javascript
// file: consumer/assert-add.mjs
import { add } from "calc-kit";
if (add(2, 3) !== 5) throw new Error("add contract failed");
console.log("addition verified");
```

It prints addition verified for the original package and exits with an error for the subtraction variant. Nothing here publishes a package. A release workflow should run the relevant build, artifact checks, supported type-consumer tests and behavioral tests, then publish the artifact whose evidence was reviewed. Choose ordering so an expensive operation does not conceal an earlier failure; a fixed trio of tools is not exhaustive proof.

### 4) **Common confusion**

An export map describes permitted package subpaths, not every path an author intended to expose. A checker cannot infer an unlisted intended API from a private source filename. Enumerate and test the actual public contract. Likewise, a blocked export, missing declaration and permissive ambient shim are different diagnoses, not interchangeable forms of an any leak.

Health checks do not certify that declarations tell the truth about arbitrary runtime behavior. They can catch supported structural problems, but valid numeric signatures say nothing about addition versus subtraction. Some failures trigger several checks, so their coverage is neither disjoint nor a guarantee that a defect must defeat every tool to escape.

### 5) **Performance note**

Packing, extracting files, discovering entry points and analyzing resolutions have costs that depend on the package and tool versions. Reusing one reviewed tarball can avoid inconsistent inputs across checks, but this fixture establishes no timing bound, cache guarantee or universal cost saving. Expanding the supported consumer matrix also expands maintenance work; retain the combinations your contract requires.

### 6) **Mentor note**

Give a learner the missing-declaration tarball and the subtraction tarball. Ask which checks should fail, then inspect their actual output. A sound explanation separates source checking, packed-file presence, declaration resolution and runtime meaning. Finish by asking which consumers a narrowed profile excludes and what additional test would support a new runtime or bundler promise.
