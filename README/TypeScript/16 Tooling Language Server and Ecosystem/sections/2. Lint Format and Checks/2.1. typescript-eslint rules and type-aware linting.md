## 2.1. typescript-eslint rules and type-aware linting

### 1) **Choose rules and their information requirements**

TypeScript checks a program against its type contracts. ESLint runs configured rules against selected source files. Some rules inspect syntax; others ask a TypeScript service about types. A program can compile successfully while violating a lint policy, so run both checks and name the command that produced a diagnostic.

The [shared-config reference](https://typescript-eslint.io/users/configs/) distinguishes these choices:

| Preset | Relationship and purpose |
|---|---|
| recommended | Recommended rules without typed-lint setup. |
| recommendedTypeChecked | Recommended plus recommended rules requiring types. |
| strict | Recommended plus more opinionated bug-catching rules; it does not include all typed rules. |
| strictTypeChecked | Includes recommended, recommendedTypeChecked and strict, plus further typed rules. |
| stylistic / stylisticTypeChecked | Additional conventions, with a typed variant; these are separate from strictness. |

Strict presets can change rules or options outside major releases. Review the effective configuration when upgrading. These presets do not enable whitespace-formatting rules. Neither recommended nor strict is a universal guarantee of safe code, and choosing all available rules can introduce conflicting policies.

### 2) **Run an actual typed-lint project**

This fixture uses **Node.js 20.20.2**, **ESLint 10.12.0**, **typescript-eslint 8.71.1**, the compatible **TypeScript 6.0.2 API package**, and a separate **native TypeScript 7.0.2 compiler**. The two TypeScript installations are deliberate: passing a native compiler check does not establish compatibility with tools consuming older JavaScript APIs. The [dependency support page](https://typescript-eslint.io/users/dependency-versions/) currently lists a TypeScript range below 6.1. Check the actual tool's support window before changing its API dependency.

Save these files in an empty directory, run `npm install`, then run the commands below. Commit the resulting lockfile in a real project so CI can use `npm ci`. The minimal rule configuration isolates three behaviors; it is not a complete application lint policy.

```json
// file: package.json
{
  "private": true,
  "type": "module",
  "scripts": {
    "check": "tsc -p tsconfig.json --noEmit",
    "build": "tsc -p tsconfig.json",
    "lint": "eslint src --max-warnings 0"
  },
  "devDependencies": {
    "@typescript/native": "npm:typescript@7.0.2",
    "typescript": "npm:@typescript/typescript6@6.0.2",
    "eslint": "10.12.0",
    "typescript-eslint": "8.71.1"
  },
  "overrides": { "@typescript/old": "npm:typescript@6.0.3" }
}
```

```json
// file: tsconfig.json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "nodenext",
    "rootDir": "src",
    "outDir": "dist",
    "types": []
  },
  "include": ["src/**/*.mts"]
}
```

```javascript
// file: eslint.config.mjs
import tseslint from "typescript-eslint";
export default [{
  files: ["src/**/*.mts"],
  languageOptions: {
    parser: tseslint.parser,
    parserOptions: { projectService: true, tsconfigRootDir: import.meta.dirname }
  },
  plugins: { "@typescript-eslint": tseslint.plugin },
  rules: {
    "@typescript-eslint/no-floating-promises": ["error", { ignoreVoid: false }],
    "@typescript-eslint/no-misused-promises": "error",
    "@typescript-eslint/no-unnecessary-condition": "error"
  }
}];
```

```typescript
// file: src/main.mts
function load(): Promise<string> { return Promise.resolve("ready"); }
function fail(): Promise<never> { return Promise.reject(new Error("offline")); }
function label(value: string | null): string { return value === null ? "none" : value.toUpperCase(); }
console.log(await load(), label(null), label("ok"));
try { await fail(); }
catch (error: unknown) { console.log(error instanceof Error ? error.message : "unknown"); }
// load(); // no-floating-promises: a fulfilled result here does not justify ignoring arbitrary promise failures.
// void fail(); // also rejected with this configuration's ignoreVoid: false.
// const callback: () => void = () => load(); // no-misused-promises: the consumer discards the return.
// if (load()) console.log("not the result"); // no-misused-promises; the native compiler also reports an always-defined Promise condition.
// if (label("x") !== null) console.log("always"); // no-unnecessary-condition: the declared return is string.
```

Run `npm run check`, `npm run lint`, `npm run build` and `node dist/main.mjs`. Both checks pass and output is:

```text
ready none OK
offline
```

Activate one commented negative line at a time and rerun the relevant checks. The floating call, voided rejection and void callback pass the native compiler but fail the named lint rules. The Promise condition is an example of overlapping diagnostics, not evidence that compiler and lint checks have disjoint jurisdictions. Do not run the voided-rejection variant: the rule failure is enough to inspect it without creating an unhandled rejection.

Project Service associates a linted file with a TypeScript project. [Josh Goldberg's maintainer explanation](https://typescript-eslint.io/blog/project-service/) motivates aligning this configuration with the editor and supporting project references. If a file is outside its configured project, fix the intended file membership or use a carefully scoped supported alternative; disabling the rule does not repair a parser/project error.

### 3) **Make handling and enforcement policies explicit**

Await suspends the current async operation until settlement; a rejection then throws at that await. Returning a Promise transfers its result and rejection to the caller. Neither statement proves that some caller ultimately handles the failure. The try/catch in this fixture makes the failure policy visible. A rejection handler can itself fail, so inspect the resulting chain as well.

The [floating-promises rule](https://typescript-eslint.io/rules/no-floating-promises/) defaults to ignoring void expressions. Writing void does not install a rejection handler. This fixture sets ignoreVoid to false so an intentional discard requires another explicit decision. Changing that option can silence a diagnostic while leaving runtime behavior unchanged. A detached task needs an appropriate error/reporting policy and lifecycle ownership, not just an operator that quiets lint.

Warnings normally do not fail ESLint; `--max-warnings 0` makes any warning exceed the allowed count. A positive ceiling controls the total count, not which findings are old: removing one old warning could make room for a new one. It does not grandfather specific legacy lines. For gradual adoption, scope rules/files deliberately or use an explicit suppression mechanism supported by the pinned ESLint version and review its entries. If using an inline disable, name the rule and explain why that site is acceptable. An unused disable is a maintenance finding, not proof of a justified exception.

### 4) **Common confusion**

A tsc run does not execute ESLint, and ESLint does not normally report every compiler diagnostic. Typed rules use type information to apply their own policies. Some findings overlap; others, such as this floating call, add a check beyond compiler acceptance.

A rule named no-unnecessary-condition reasons from available static types. If untrusted data violates a declared type, deleting a defensive check can be the wrong repair; correct the boundary model or validate the input. Type-aware does not mean omniscient about runtime values.

### 5) **Performance note**

Typed linting can load projects, analyze types and evaluate rules. Project Service can reuse information within its process, but that does not imply that each fresh CI invocation checks only changed files. ESLint file caching is another mechanism with its own invalidation limits. Measure the actual selected files, dependency graph and cold/warm command before choosing a policy. This example establishes findings and output; it makes no latency or incident-reduction claim.

### 6) **Mentor note**

Ask a learner to classify the four negative cases by producing command, rule and runtime consequence. Then change ignoreVoid to true and explain why a green result still would not handle fail's rejection. A sound review distinguishes a parser setup failure, compiler diagnostic, rule violation and an intentional documented exception.
