## 2.2. Prettier, dprint, and formatting discipline

### 1) **Formatter choice** (Prettier ubiquity vs dprint speed)

**Definition** — Prettier (opinionated, near-universal, plugin ecosystem — format-on-save default across editors) vs dprint (Rust-compiled, 10–30× faster on large repos, plugin-based TypeScript support). Both enforce *deterministic* formatting (same input → same output, always) — the choice trades ecosystem ubiquity (Prettier: every editor, every CI template documents it) against speed (dprint: monorepo-scale format/check in milliseconds).

**What problem it solves / history** — unformatted codebases debated style per PR (quotes, semicolons, trailing commas — review threads on whitespace, contributor friction per style) while formatted-by-habit codebases drifted per author (four indent styles, two quote styles — diffs noisy with reformatting). Opinionated formatters delete the debate structurally: style decided once in config, enforced mechanically everywhere — reviews read logic exclusively.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), default to Prettier (ubiquity — contributors already have it; config shared via repo + editor defaults); choose dprint past scale thresholds (monorepos where Prettier check exceeds seconds — speed measured, not assumed); configure once (`printWidth`, `semi`, `singleQuote`, `trailingComma` — decided deliberately, changed almost never).

**Runnable example** — deterministic output, configured once (good vs bad, `tsc --strict`):

```typescript
// good — formatted code (deterministic output — style decided in config, enforced mechanically)
export function total(xs: number[]): number {
  return xs.reduce((a, b) => a + b, 0); // printWidth/trailingComma/semi applied uniformly (no author decisions per line)
}
console.log(total([1, 2]).toFixed(0)); // 3 — formatted (reviews read logic — style identical everywhere)
// bad — hand-formatted inconsistency (indent drift, quote mixing, comma chaos — diffs noisy with reformatting)
// fix — formatter + format-on-save (style decided once in config — enforced mechanically everywhere, debated never)
```

```typescript
// good — config stated once (shared via repo — contributors inherit, CI verifies)
// prettier.jsonc (documented as config — not compiled):
// { "semi": true, "singleQuote": true, "trailingComma": "all", "printWidth": 100 }
// (above: jsonc shape documented (config-as-documentation, labeled honestly — formatter reads it, humans review it once)
export function greet2(name: string): string {
  return `hi ${name}`; // formatted per shared config (single quotes, semicolons, trailing commas — uniform)
}
console.log(greet2("ada").toUpperCase()); // HI ADA — configured once (style decided deliberately, changed almost never)
// bad — per-author editor settings (four indent styles, two quote styles — diffs noisy, onboarding friction per contributor)
// fix — repo-shared config (contributors inherit — editor defaults + CI check, zero per-author decisions)
```

```typescript
// good — dprint shape (same discipline, faster engine — scale threshold documented per repo)
// dprint.jsonc (documented as config — not compiled):
// { "lineWidth": 120, "indentWidth": 2, "semiColons": "prefer", "quoteStyle": "preferSingle" }
// (above: dprint config shape (Rust engine, plugin-based TS — 10-30x faster past monorepo scale thresholds)
export function fast(n: number): number {
  return n * 2; // formatted identically in spirit (deterministic output — engine differs, discipline identical)
}
console.log(fast(21).toFixed(0)); // 42 — formatter choice (Prettier ubiquity vs dprint speed — decided per repo scale, measured)
// bad — no formatter ("we format by convention" — conventions unenforced decay per author per quarter)
// fix — opinionated formatter (discipline automated — reviews read logic exclusively, forever)
```

**Common confusion** — "formatters replace lint" — formatters handle *whitespace/punctuation* (deterministic layout); lint handles *correctness/hygiene* (unused vars, type-aware rules, import discipline) — complementary automation (both on save + CI, neither substituted). "Prettier vs dprint is bikeshedding" — engine/speed/ecosystem differ measurably (choose per repo scale, measured); *whether* to format is never debated (always — the settled question). "formatting slows CI" — format-*check* runs in seconds (Prettier) to milliseconds (dprint); unformatted diffs slow *reviews* unboundedly (human re-reads per style noise).

**Performance note** — Prettier check seconds per repo (Node-based, per-file parse); dprint milliseconds (Rust, parallel, incremental-aware); hand-formatting costs reviewer minutes per PR (unbounded, recurring). Formatter choice optimizes CI seconds; formatting itself optimizes review hours.

**Mentor note** — show one PR diff before/after formatting (style noise vs logic-only — review burden made visible in one diff). Exercise: time `prettier --check` vs `dprint check` on the repo (numbers decide the engine; discipline is non-negotiable either way). Review gate: unformatted files fail CI (check blocking — style decided once, enforced mechanically).

### 2) **Format-on-save + CI check** (local instant, remote blocking)

**Definition** — format-on-save (editor formats per save — zero author effort, instant feedback) plus CI `check` (pipeline fails unformatted files — enforcement independent of editor setup). Local comfort (authors never think about style) composed with remote guarantee (unformatted code never merges regardless of local config).

**What problem it solves / history** — save-only formatting (authors without the extension shipping unformatted code — "works on my machine" style) and CI-only checking without local automation (every PR a formatting-fix commit round-trip — velocity tax per change) each covered half the problem. The pair covers both: locals format instantly (comfort), CI blocks drift (guarantee) — authors who configure nothing still pass (their code was already formatted by... nothing — CI catches it; one round-trip teaches the extension).

**Modern guidance** — as of TypeScript 5.9 era, enable format-on-save team-wide (documented in contributing + editor recommendations — zero author effort); enforce `check` in CI (blocking — unformatted never merges); pre-commit hooks as middle ground (format-staged-changes automatically — comfort + guarantee without CI round-trips).

**Runnable example** — comfort plus guarantee (good vs bad, `tsc --strict`):

```typescript
// good — save-formatted code (author effort zero — style correct by construction at every save)
export function clean(s: string): string {
  return s.trim().toLowerCase(); // formatted on save (indentation/quotes/semicolons automatic — thinking about logic only)
}
console.log(clean("  Hi  ")); // hi — comfort layer (authors never think about style — tooling thinks constantly)
// bad — manually formatted "carefully" (effort per line, drift per author, review noise per PR — human formatting doesn't scale)
// fix — format-on-save (comfort automated — author effort zero, style correct by construction at every save)
```

```typescript
// good — CI check shape (blocking guarantee independent of editor setup — documented as process)
// (CI step: format --check (Prettier) or check (dprint) — failing PRs show exact diffs to apply)
// fix — check blocking (unformatted never merges — guarantee independent of who configured what locally)
export function stable(n: number): number { return n; } // check-clean (CI green on style — logic reviewed, order automated)
console.log(stable(1).toFixed(0)); // 1 — guarantee layer (remote enforcement — comfort's complement, never substitute)
// bad — save-only without CI (unconfigured authors shipping unformatted code — comfort without guarantee covers configurers only)
// fix — pair both (comfort + guarantee — authors who configure nothing still pass after one round-trip teaches the extension)
```

```typescript
// good — pre-commit middle ground (staged changes formatted automatically — comfort + guarantee without CI round-trips)
export function mid(s: string): string { return s; } // pre-commit formatted (staged diff clean before CI ever sees it)
console.log(mid("m")); // m — middle layer (local guarantee pre-push — CI round-trips reserved for real failures)
// bad — CI-only without local automation (every PR a formatting-fix commit — velocity tax per change, morale tax per round-trip)
// fix — all three layers (save comfort + pre-commit guarantee + CI block — defense in depth for style, cheap at every layer)
```

**Common confusion** — "format-on-save suffices" — suffices for *configurers* (extension installed, settings right); CI check covers *everyone* (unconfigured authors, web-edit PRs, bot commits). "CI check suffices" — suffices for *guarantee* (nothing merges unformatted); save/pre-commit add *comfort* (no round-trips for style — velocity preserved). "pre-commit hooks annoy" — format-*staged* hooks (fast, scoped, silent on clean diffs) vs format-*all* hooks (slow, noisy, touching unrelated lines) — scope decides annoyance, not hooks per se.

**Performance note** — save-format milliseconds per file (editor-local); pre-commit seconds per staged set; CI check seconds per repo (Prettier) to milliseconds (dprint). Layered costs all trivial vs review-noise savings (human minutes per PR).

**Mentor note** — count formatting-fix commits last quarter (round-trips × velocity tax — automation ROI in one query). Exercise: install all three layers in one afternoon (save + pre-commit + CI) and watch formatting discussion vanish from reviews permanently. Review gate: unformatted merges fail CI (blocking — style decided once, enforced mechanically).

### 3) **What formatters don't do** (import order, naming, architecture — boundaries)

**Definition** — formatter boundaries: *layout* (whitespace, punctuation, wrapping — deterministic, automated) vs *everything else* (import organization needs binding resolution — organize-imports, not Prettier; naming needs judgment — conventions + review; architecture needs design — no tool formats structure). Knowing the boundary routes each concern to its automation (formatter/linter/reviewer) instead of expecting one tool to do all three.

**What problem it solves / history** — formatter-maximalism (Prettier plugins for import sorting, comment reflowing, "smart" wrapping — slow, contentious, frequently wrong) bloated formatting into lint/review territory (automation fighting human judgment per diff). Boundary clarity keeps formatters fast and uncontroversial (layout only — seconds, agreement universal) while lint/review own the rest (correctness + judgment — slower, thoughtful).

**Modern guidance** — as of TypeScript 5.9 era, formatters for layout (whitespace/punctuation/wrapping — deterministic); organize-imports for import order (binding-aware — server action, not text sort); lint for correctness/hygiene (unused, kinds, cycles, type-aware rules); review for naming/architecture (judgment — no automation substitutes). Four layers, each owning its concern, none substituting another.

**Runnable example** — boundaries respected (good vs bad, `tsc --strict`):

```typescript
// good — formatter owns layout (whitespace/punctuation deterministic — humans never discuss)
// (this file's layout IS formatter output shape: 2-space indent, single quotes, semicolons, trailing commas where multiline)
export function laid(n: number): string {
  return `n:${n}`; // layout automated (formatter decided — authors think about logic only)
}
console.log(laid(7)); // n:7 — layout layer (deterministic — same input, same output, always)
// bad — hand-layout debates in review ("indent here?", "line break there?" — whitespace threads on logic PRs)
// fix — formatter (layout automated — reviews read logic exclusively, forever)
```

```typescript
// good — organize-imports owns import order (binding-aware — server action, not text sort)
function invariant(cond: unknown, msg: string): asserts cond { // local assert helper (stdlib-only — no @types/node needed)
  if (!cond) throw new Error(msg);
}
export function guarded(n: number): string {
  invariant(n > 0, "positive");
  return "ok";
}
console.log(guarded(1)); // ok — organize-imports would sort/merge these imports (formatter handles layout only)
```

```typescript
// good — review owns naming/architecture (judgment — no automation substitutes, ever)
export function calculateTotalPrice(items: number[]): number { // naming reviewed (descriptive — conventions + judgment)
  return items.reduce((a, b) => a + b, 0); // architecture reviewed (reduce here — design decision, human-approved)
}
console.log(calculateTotalPrice([1, 2]).toFixed(0)); // 3 — judgment layers (naming + architecture — reviewers own, tools assist)
// bad — formatter-maximalism (import sorting + comment reflowing + smart wrapping in Prettier — slow, contentious, frequently wrong)
// fix — boundaries (formatter/layout, organize/imports, lint/correctness, review/judgment — four layers, each owning its concern)
```

**Common confusion** — "one tool should do everything" — layout/lint/judgment need different engines (deterministic formatter, binding-aware server, human reviewer) — unified tools do each worse (slow formatters, contentious sorts, suppressed judgment). "boundaries excuse gaps" — boundaries *route* (each concern to its automation — coverage complete across layers, none substituted). "reviewing formatting wastes time" — reviews never *discuss* formatting (automated); reviews *verify* automation ran (CI check green — seconds of attention, not threads).

**Performance note** — layered automation costs milliseconds-to-seconds per layer (formatter + organize + lint, parallelizable); unified maximalist tools cost minutes (slow + contentious); human review of automated layers costs seconds (CI green verified — attention freed for logic).

**Mentor note** — list one concern per layer for a real PR (layout→formatter, imports→organize, correctness→lint, naming/architecture→reviewers) — routing drill transferring in 15 minutes. Exercise: remove one maximalist formatter plugin and replace with layered automation (faster + less contentious + better coverage per concern). Review gate: formatting debates in logic PRs fail process review (automate, don't discuss).
