## 2.2. Prettier, dprint, and formatting discipline

### 1) **Choose reproducible formatting behavior**

A formatter parses supported source and prints it according to its rules and configuration. Its purpose is to reduce recurring layout decisions. A formatted file can still contain a type error, incorrect algorithm or misleading name. Review those concerns separately.

Prettier provides language support and plugins in a JavaScript ecosystem. dprint runs configured formatting plugins, including a TypeScript/JavaScript plugin. Choose based on the languages and syntax you need, output you can accept, integration support and measurements on your repository. Neither tool has a universal speed ratio, and different engines need not produce identical text.

Pin the tool, plugins and configuration. Reproducing the same input and relevant environment is more precise than saying formatting is always the same. Some rules deliberately retain source layout: [Prettier's rationale](https://prettier.io/docs/rationale) explains preserved multiline objects and how automatic semicolon insertion can make an existing bug visible without repairing it.

### 2) **Observe check, write and repeat**

Use **Node.js 20.20.2**, **Prettier 3.9.10**, **dprint 0.63.0**, **@dprint/typescript 0.96.1** and **TypeScript 7.0.2**. In an empty directory without a tsconfig, save the following files, then run `npm install --save-dev --save-exact prettier@3.9.10 dprint@0.63.0 @dprint/typescript@0.96.1`. This creates package and lock files. A real repository commits those files and uses `npm ci` for repeatable dependency installation.

```json
// file: .prettierrc.json
{ "singleQuote": true, "semi": true, "printWidth": 80 }
```

```json
// file: dprint.json
{
  "lineWidth": 80,
  "indentWidth": 2,
  "typescript": { "quoteStyle": "preferSingle", "semiColons": "prefer" },
  "includes": ["src/**/*.mts"],
  "excludes": ["dist", "node_modules"],
  "plugins": ["./node_modules/@dprint/typescript/plugin.wasm"]
}
```

```typescript
// file: src/calc.mts
export function total(xs:number[]):number{return xs.reduce((a,b)=>a+b,0)}
console.log("total",total([1,2]))
```

The JSON file labels above are instructions, not JSON comments to save. The dprint TypeScript options are nested under typescript and a real plugin is selected. The [dprint setup](https://dprint.dev/plugins/typescript/) and [configuration guide](https://dprint.dev/config/) explain this separation. A file named prettier.jsonc is not one of Prettier's automatically discovered configuration filenames; use a [supported configuration name](https://prettier.io/docs/configuration) such as the one above.

First compile and run the unformatted source:

```bash
tsc --strict --target es2022 --module nodenext --outDir dist src/calc.mts
node dist/calc.mjs
```

It prints `total 3`. Formatting is not required for that result. Now run:

```bash
npx prettier src --check
npx prettier src --write
npx prettier src --check
```

The first check reports the dirty file and exits 1. Write changes the source; the next check exits 0. [Prettier's CLI](https://prettier.io/docs/cli) distinguishes style differences from tool errors and documents file selection. Read the exit code as well as the message. Running write again should leave this fixture unchanged. Compile and run again to verify the same `total 3` result.

To compare dprint independently, restore the original unformatted calc.mts from the fence before running:

```bash
npx dprint check
npx dprint fmt
npx dprint check
```

The first check reports a formatting difference and fails. Format writes the change; the final check passes. Repeating fmt leaves this fixture unchanged. Compile and run again to compare behavior. In a real project, select one formatter for each file set; alternating engines can produce repeated layout changes. Matching this tiny example's output is not proof that their formatting agrees across a codebase.

### 3) **Connect local convenience to a checked file set**

Format-on-save is useful when an editor selects the intended provider, repository config and local version. A CI check verifies the selected files even when a contributor has no editor extension. This fixture executed CLI operations; it did not automate editor save, hooks or a hosted CI job. A local hook can help, but it can be bypassed and needs care around partially staged files.

Choose the CI file set deliberately. An ignored, unmatched or excluded file is outside the claim established by a passing run. Keep generated output and vendored code under appropriate owners, and avoid a broad write command that touches unrelated changes. Review a formatter upgrade's diff separately when possible so logic changes remain visible.

Formatters and plugins have different transformation boundaries. Do not assume that every formatter sorts imports or that none can. Inspect the chosen plugin and options. Import sorting, removal or merging can interact with module effects; the [code-action lesson](<../1. Language Server in Practice/1.2. Rename refactorings and code actions.md>) demonstrates an actual lost registration effect after unused-import removal. Formatting success does not verify package exports, types or runtime behavior.

### 4) **Common confusion**

A green format check means the selected files match the selected formatter's output. It does not mean TypeScript accepted them. Append `const wrong: number = "oops";` to a scratch copy, format it and observe a passing style check followed by TS2322 from the compiler. Keep that negative example out of the runnable baseline.

Comments can affect other tools. [Josh Goldberg's DefinitelyTyped migration account](https://www.joshuakgoldberg.com/blog/definitelyformatted/) reports comment directives shifting relative to their intended error locations after formatting. That historical case motivates rerunning compiler/lint checks after a large reformat; it is not evidence that every current formatting pass has that defect. Likewise, a project's contributor needs may justify a different enforcement process from this check-first workflow.

### 5) **Performance note**

Parsing, printing, file discovery, plugin loading, downloads and caching can all affect elapsed time. A cold install and a warm format-on-save request measure different work. Compare equivalent file sets, pinned versions, cache states and hardware before selecting a tool for speed. This fixture measures correctness outcomes and repeat stability, not a current throughput ratio or a guaranteed response time.

### 6) **Mentor note**

Have the learner explain the sequence dirty check → write → clean check, then show why compilation succeeds before formatting. Ask what an excluded file and a formatted type error prove about a green check. For an upgrade, inspect one nontrivial diff involving a directive or import and choose the additional verification its behavior needs.
