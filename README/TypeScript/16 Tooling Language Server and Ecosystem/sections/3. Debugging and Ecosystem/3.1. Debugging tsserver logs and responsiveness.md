## 3.1. Debugging tsserver logs and responsiveness

### 1) **Identify the process and the failing operation**

An editor symptom can originate in the language server, client integration, project configuration or document state. Start by naming the operation: a stale diagnostic, slow completion, wrong definition target or failed project load. Record the executable/provider and version as well as the editor and extension versions. A command-line compiler version alone does not identify the service your editor launched.

The historical name tsserver refers to TypeScript's Node-based server and its protocol. Native **TypeScript 7.0.2** supplies an LSP service; the tested launcher is `tsc --lsp --stdio`. LSP is the Language Server Protocol. The server consumes framed protocol messages on standard input, so this command alone is not an interactive diagnostics console. Native-provider selection and logging depend on the client integration. Do not assume that a setting pointing at an older TypeScript lib directory configures the native service.

The [legacy TS Server logging guide](https://github.com/microsoft/TypeScript/wiki/Getting-logs-from-TS-Server-in-VS-Code) describes opening its log in VS Code. Its sample is explicitly an older Node tsserver session. Use it for that provider rather than treating its commands, TSS_LOG environment variable or record shape as a native LSP guarantee. A transport/request error, compiler diagnostic and client-rendering failure are different evidence. For example, the native probe's unsupported method received a protocol error; an invalid number assignment instead appeared in a successful diagnostic response with code 2322.

### 2) **Separate disk configuration from an open document**

Use TypeScript 7.0.2 and **Node.js 20.20.2**. Save these files in an empty directory:

```json
// file: tsconfig.base.json
{ "compilerOptions": { "strict": true, "target": "es2022", "module": "nodenext", "types": [] } }
```

```json
// file: tsconfig.json
{ "extends": "./tsconfig.base.json", "compilerOptions": { "outDir": "dist" }, "files": ["app.mts"] }
```

```typescript
// file: app.mts
export const port: number = 7;
console.log(port);
```

Remove the file labels when saving JSON. Run these commands from the fixture directory:

```bash
tsc -p tsconfig.json --showConfig
tsc -p tsconfig.json --listFilesOnly
tsc -p tsconfig.json --noEmit --extendedDiagnostics
tsc -p tsconfig.json
node dist/app.mjs
```

The effective configuration includes strict checking and app.mts. The file list includes library declarations as well as the application source. The build succeeds and runtime prints 7. The diagnostics report aggregate compiler work for this invocation. They do not rank source files by check time or measure editor response latency.

The native headless check separately initialized the service, opened app.mts and requested `textDocument/diagnostic`. It then sent a full-document `textDocument/didChange` replacing the initializer with `"wrong"`, without changing the saved file, and requested diagnostics again. Restoring the original document through another change cleared the diagnostic:

| State | Actual native diagnostic result | Saved file |
|---|---|---|
| Opened original document | No diagnostic items | port initialized to 7 |
| Open buffer changed to a string | TS2322, string not assignable to number | Still initialized to 7 |
| Open buffer restored | No diagnostic items | Still initialized to 7 |

The protocol request succeeded even when it returned a code diagnostic. In this fixture, disk compilation can be green while an unsaved document correctly has an error. That difference is not evidence of a stale server. Compare file URI, document version/content, project, options and compiler implementation before claiming that editor and CLI disagree on the same input. [Navigation scope](<../1. Language Server in Practice/1.1. Navigation go to definition find references.md>) shows another case where opening a file changes what the service can inspect.

An editor exercise is to reproduce the same unsaved edit with the intended provider and compare its displayed diagnostic. The verification here used actual native requests and separate CLI/runtime commands; editor UI rendering and the legacy log UI were not automated.

### 3) **Test one loading or performance hypothesis at a time**

In a disposable fixture copy, rename tsconfig.base.json so the extends target is absent, then run `tsc -p tsconfig.json --noEmit`. The compiler fails with TS5083 because it cannot read the base. It does not silently accept the intended base options. Restore the file and confirm the check passes. An invalid config load should be repaired before treating its resulting program as the intended baseline.

For a slow feature, reproduce a specific action, determine its actual project membership and compare the service's request evidence with a batch check. The [compiler performance guide](https://github.com/microsoft/TypeScript/wiki/Performance) explains effective configuration, file-list and aggregate-diagnostic inspection. Some examples describe older compiler implementations, so check that a profiling command and format are supported by the actual executable. Native 7.0.2's LSP help offers pprofDir for profiles; that is distinct from an older Node CPU-profile invocation. This lesson did not collect or analyze a performance profile.

Change one condition and repeat the same operation. Examples include disabling a relevant extension, narrowing accidental root files or testing a reduced type expression. Do not assume that maxNodeModuleJsDepth, watcher settings or project-reference redirects address every slow completion. Those options affect particular inputs and behavior; [configuration](<../../../13 Configuration and Compiler Options/README.md>) and [performance scaling](<../../../19 Performance Project References and Scaling/README.md>) own their detailed trade-offs.

A restart can be a useful comparison, but a vanished symptom does not prove a corrupted cache. Restarting changes process state, timing and often project loading at once. Preserve useful evidence before removing generated state, and distinguish build information from a running server's memory. A clean rebuild cannot by itself exonerate every service or configuration cause.

### 4) **Common confusion**

A diagnostic code such as 2322 is part of a source-check result. It is not an LSP transport failure or a machine-readable fix pointer for every server error. Read the enclosing message and the operation that produced it.

The nearest config is a discovery clue rather than a universal ownership rule. Files, imports, references, inferred projects, workspace roots and client requests can affect membership. A green batch run also does not establish healthy completion or hover behavior. An [original 2023 editor-performance report](https://github.com/microsoft/TypeScript/issues/53609) separates batch output, plugin experiments and request tracing; its timings are evidence about that historical project, not a benchmark for this fixture.

### 5) **Performance note**

Logging and profiling add work and can change the observed timing. Capture the smallest relevant interval and record cold/warm state, loaded project and operation. Logs can include paths or source text; inspect them before sharing an excerpt. This fixture establishes state-dependent diagnostics and configuration failures, not response-time guarantees, universal file-count thresholds or the cost benefit of splitting a project.

### 6) **Mentor note**

Show a learner the green CLI result and TS2322 from the changed buffer. Ask for the evidence needed before calling it a server bug. A strong answer compares the actual content and configuration first. Then provide a missing-base diagnostic and an unsupported-method response and ask which layer each identifies. Encourage one controlled hypothesis per experiment instead of an arbitrary checklist of tuning knobs.
