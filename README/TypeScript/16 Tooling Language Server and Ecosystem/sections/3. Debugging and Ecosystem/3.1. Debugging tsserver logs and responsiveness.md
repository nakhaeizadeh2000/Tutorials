## 3.1. Debugging `tsserver` — logs and responsiveness

### 1) **tsserver log anatomy** (request/response shapes, error codes, project traces)

**Definition** — the `TSServer log` channel (VS Code: Output → TypeScript; `tsserver.log` via `TSS_LOG` env) records JSON-RPC-ish request/response pairs (command, arguments, execution time per request), project-loading traces (config discovery, file enumeration, program construction per tsconfig), and error codes (server-side failures with `err` payloads). Reading logs turns "editor is broken" into named, locatable failure classes.

**What problem it solves / history** — editor misbehavior reports ("hover wrong", "errors stale", "completions missing" — symptoms without causes) debugged by restarting/reinstalling hopefully (ritual without diagnosis — issues recurring per project shape). Log reading names causes (stale program vs version mismatch vs corrupted cache vs project misconfiguration — each with distinct log signatures and distinct fixes).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), reproduce first (minimal steps in the log channel — request shapes visible per action), read project-loading traces second (config discovery order, file counts, program boundaries — loading failures live here), match error codes third (server errors carry `err` payloads with fix pointers, not just messages).

**Runnable example** — log-shaped thinking via checkable analogues (good vs bad, `tsc --strict`):

```typescript
// good — version-pinned tooling (log-first question "which tsc serves this editor?" answered in code, not settings-hunting)
// (editor reality: VS Code uses workspace tsc version when configured (typescript.tsdk) — version mismatch (bundled 5.x vs repo 5.9) explains whole symptom classes)
export function toolchain(): string { return "workspace-tsdk-pinned"; } // stated (settings.json documents — no per-machine drift)
console.log(toolchain()); // workspace-tsdk-pinned — version question answered structurally (settings, not folklore)
// bad — "restart the editor" as first resort (ritual without diagnosis — issues recurring per project shape, unlearned)
// fix — logs first (request/response/error shapes per symptom — named failure classes, located fixes)
```

```typescript
// good — project-boundary awareness (which tsconfig owns this file? — loading traces answer, assumptions don't)
export function owner(): string { return "nearest-tsconfig"; } // (tsserver assigns files to nearest program — multi-root awareness built in)
// (loading-trace reading: config discovery order, file counts, program boundaries per project — failures live here, not in code)
// fix — project-loading traces second (config discovery + file enumeration + program construction per tsconfig)
console.log(owner()); // nearest-tsconfig — ownership questions answered via traces (assumptions replaced by evidence)
// bad — editing tsconfig at random (config changes without loading-trace evidence — fixes by coincidence, regressions by surprise)
```

```typescript
// good — error-code reading (server errors carry err payloads with fix pointers — messages plus machine-readable causes)
export function diagnose(code: number): string {
  return code === 0 ? "ok" : `err:${code}`; // coded diagnostics (programs branch on codes — humans read messages, tooling reads codes)
}
console.log(diagnose(0), diagnose(13)); // ok err:13 — error codes (fix pointers, not just messages — log-shaped thinking in code)
// bad — "editor is broken" reports (symptoms without causes — unactionable tickets, ritual responses, recurring issues)
// fix — logs with request/response/error shapes (named failure classes — locatable fixes per class, documented per incident)
```

**Common confusion** — "logs are for extension authors" — logs are for *anyone* debugging editor behavior (request shapes per action, project traces per load, error payloads per failure — user-readable with thirty minutes of orientation). "restarting fixes it" — restarting *masks* state issues (stale programs, corrupted caches — recurring per project shape); logs *diagnose* (named classes with located fixes). "tsserver matches tsc exactly" — tsserver *wraps* tsc programs with editor features (inlay state, pending diagnostics, auto-import caches — server-specific failure modes need server logs, not tsc output).

**Performance note** — log verbosity costs disk per session (megabytes on large programs — scope via `TSS_LOG` levels, rotate aggressively); log *reading* costs minutes per incident (vs hours of ritual restarts across teams). Enable verbose logging per incident, not permanently.

**Mentor note** — reproduce one editor bug with the log channel open (request/response/error shapes per action — diagnosis in one session). Exercise: classify three editor symptoms via logs (stale program vs version mismatch vs corrupted cache — named classes with located fixes each). Review gate: "editor is broken" tickets without log excerpts fail process review (evidence first, always).

### 2) **Responsiveness triage** (large-program slowdowns and tuning knobs)

**Definition** — slow-editor triage order: project size (file counts per program — split via project references past thresholds), watch programs (file-watching overhead on huge trees — `watchOptions` tuning), plugin load (editor extensions contributing completions/diagnostics — bisect by disabling), `maxNodeModuleJsDepth`/`disableSourceOfProjectReferenceRedirect` (dependency-depth and navigation-target tuning). Measure first (`--extendedDiagnostics` + editor timing APIs), tune second, split last.

**What problem it solves / history** — slow editors blamed vaguely ("TypeScript is slow" — unactionable, version-pinned folklore) while causes sat in configuration (single 50k-file programs, deep `node_modules` traversal, plugin storms — each measurable, each tunable). Triage order converts folklore into metrics (file counts, watch load, plugin cost per feature) with a knob per cause (references, watchOptions, disable-lists).

**Modern guidance** — as of TypeScript 5.9 era, triage in order (program size → watch load → plugins → depth/navigation knobs); measure with `--extendedDiagnostics` (check-time leaders) + editor performance tooling (per-feature timing); split programs via project references past file-count thresholds (incremental checking + scoped language service per program — see domain 19 for full scaling treatment).

**Runnable example** — triage order encoded (good vs bad, `tsc --strict`):

```typescript
// good — program-size awareness (file counts per program — split past thresholds, measured not hoped)
export function program(): string { return "sized-and-split"; } // (programs counted via extendedDiagnostics — leaders named per run)
// (triage step 1: file counts per program (split via project references past thresholds — incremental checking per program)
// fix — measure first (extendedDiagnostics per perf question — check-time leaders named, tuning targeted)
console.log(program()); // sized-and-split — size triaged (thresholds measured, splits justified by data)
// bad — "TypeScript is slow" folklore (unactionable complaints — version-pinned myths, no metrics, no knobs)
// fix — triage order (size → watch → plugins → knobs — metrics per step, knobs per cause)
```

```typescript
// good — watch-program awareness (file-watching overhead tuned per tree shape — watchOptions as needed)
// (triage step 2: watch load on huge trees (watchOptions tuning — polling vs native events per platform/filesystem)
// fix — watchOptions per repo shape (measured overhead, tuned watching — editors stay interactive on huge trees)
export function watched(): string { return "watched-tuned"; }
console.log(watched()); // watched-tuned — watch load triaged (second step — size first, always in that order)
// bad — disabling editor features blindly (inlay off, semantic highlighting off — responsiveness via amputation, root cause untouched)
// fix — triage order (features last — size/watch/plugins/knobs first, features never sacrificed for config debt)
```

```typescript
// good — plugin bisection (extensions disabled per half — cost attributed per feature, kept or removed with evidence)
export function plugins(): string { return "bisected"; } // (triage step 3: plugin load per extension — bisect to attribute)
// (knobs step 4: maxNodeModuleJsDepth + disableSourceOfProjectReferenceRedirect — depth/navigation tuning per measurement)
// fix — bisect plugins (evidence per extension — kept with data, removed with data, never on folklore)
console.log(plugins()); // bisected — plugin costs attributed (triage complete: size → watch → plugins → knobs, in order)
// bad — reinstalling editors/editors-extensions wholesale (ritual without diagnosis — issues recurring per project shape)
// fix — ordered triage (metrics per step, knobs per cause — folklore replaced by instrumentation, permanently)
```

**Common confusion** — "bigger machine fixes editor slowness" — hardware masks *some* slowness linearly while configuration issues scale super-linearly (50k-file single programs stay slow on any machine — structure beats hardware). "disabling features is tuning" — disabling *sacrifices* (inlay/semantic features off — capability lost); tuning *configures* (programs split, watches tuned, plugins bisected — capability kept, speed restored). "triage order is pedantic" — order prevents misattribution (tuning watches for a program-size problem wastes the quarter — sequence matters because causes mask each other).

**Performance note** — triage costs minutes per step (diagnostics + editor timing per question); program splits pay permanently (incremental checking + scoped services); misattributed tuning costs quarters (wrong knobs, unchanged symptoms). Measure-first economics dominate.

**Mentor note** — triage one slow editor live in order (size → watch → plugins → knobs — cause located in under 30 minutes typical). Exercise: run `--extendedDiagnostics` and name the top three check-time leaders (optimization backlog self-triaged per run). Review gate: "editor is slow" reports without triage data fail process review (metrics first, always).

### 3) **Project-loading failures** (version mismatches, extends chains, corrupted caches)

**Definition** — loading-failure triage: TypeScript version serving the editor (workspace `typescript.tsdk` vs bundled — mismatch explains whole symptom classes); `extends` chains resolving (missing base configs, circular extends, path-mapping drift); corrupted caches (`.tsbuildinfo` staleness, `node_modules/.cache` poisoning — clean-rebuild verification). Each with distinct log signatures and one-command verifications.

**What problem it solves / history** — loading failures presented as *checking* failures (phantom errors, missing symbols, stale diagnostics — symptoms in code, causes in setup) sending developers to fix code that wasn't broken (edits atop misloaded programs — churn without cause). Loading-first triage (version → extends → caches → program boundaries) separates setup failures from code failures before any code changes.

**Modern guidance** — as of TypeScript 5.9 era, verify version first (`TypeScript: Select Version` → workspace — mismatch explains most phantom-error classes); trace `extends` chains second (base configs resolvable? circular? path-mapped correctly?); clean-rebuild third (delete `.tsbuildinfo`/caches, reload — corruption eliminated or exonerated in one command); inspect program boundaries last (file-to-tsconfig assignment per multi-root setups).

**Runnable example** — loading verified before code touched (good vs bad, `tsc --strict`):

```typescript
// good — version-pinned tooling (workspace tsc version — editor and CI serving identical programs)
// (settings.json: typescript.tsdk → ./node_modules/typescript/lib — version mismatch class deleted structurally)
export function pinned(): string { return "workspace-tsdk"; } // stated (settings documented — no per-machine drift)
console.log(pinned()); // workspace-tsdk-pinned — version question answered structurally (settings, not folklore)
// bad — bundled-vs-workspace drift (editor serving 5.x, repo building 5.9 — phantom-error classes per version delta)
// fix — typescript.tsdk pinned (editor + CI identical programs — mismatch class deleted, not debugged per symptom)
```

```typescript
// good — extends chains traceable (base configs resolvable — missing/circular bases error loudly at load)
// tsconfig.json shape (documented as config — extends chains verified, not hoped):
// { "extends": "./tsconfig.base.json", "compilerOptions": { "strict": true } }
// (above: extends verified (base resolvable — circular extends error at load with chain trace, not silent misconfiguration)
export function chained(): string { return "extends-verified"; }
console.log(chained()); // extends-verified — chain traced (bases resolvable — misconfiguration loud, not silent)
// bad — extends-dead configs (missing base silently defaulting — programs checking under wrong flags, symptoms in code)
// fix — trace extends per setup (bases resolvable — circularity erroring with traces, drift visible immediately)
```

```typescript
// good — clean-rebuild verification (caches exonerated or eliminated in one command)
// (ritual: delete .tsbuildinfo + caches, reload window, re-check symptom — persists? real bug. vanishes? cache poisoning (fixed by deletion + CI hygiene))
// fix — clean-rebuild before code changes (setup failures separated from code failures — triage order enforced)
export function rebuilt(): string { return "clean-verified"; }
console.log(rebuilt()); // clean-verified — caches exonerated (symptom persists post-clean → real bug, code changes justified)
// bad — editing code atop misloaded programs (churn without cause — fixes for phantom errors, regressions for real ones)
// fix — loading-first triage (version → extends → caches → boundaries — setup verified before code touched, always)
```

**Common confusion** — "clean rebuilds fix everything" — clean rebuilds *exonerate-or-eliminate* caches (vanishing symptoms = cache poisoning, fixed; persisting symptoms = real bugs elsewhere) — diagnostic step, not cure-all. "version pinning is bureaucratic" — unpinned versions drift per machine (bundled auto-updates changing editor behavior silently — phantom-error classes per delta). "extends chains are self-evident" — multi-root + extends + paths combinations surprise (nearest-tsconfig assignment, base-relative path resolution — trace, don't assume).

**Performance note** — clean rebuilds cost full check time once (seconds-to-minutes — diagnostic price, paid per incident triage); version pinning costs zero steady-state (settings committed once); extends tracing costs seconds per setup (one-time verification).

**Mentor note** — triage one phantom-error report live (version → extends → clean-rebuild → boundaries — cause located before code touched). Exercise: break each loading layer deliberately (wrong version, missing base, poisoned cache) and match symptoms to layers (loading-failure vocabulary in three drills). Review gate: code changes for phantom errors without loading triage fail review (setup first, always).
