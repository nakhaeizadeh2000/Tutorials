## 3.3. Version management and upgrade playbooks

### 1) **Separate the build compiler from the consumer contract**

A project's compiler dependency selects a tool for its own development commands. A library can pin that development compiler without forcing every consumer to use that version. Consumers normally type-check the published declarations with their own compiler. The minimum supported compiler therefore depends on declaration syntax and the behavior the library promises, not simply the version used to build it.

The [npm package reference](https://docs.npmjs.com/cli/v10/configuring-npm/package-json/) distinguishes development dependencies from peer compatibility with a host. A tool that consumes TypeScript's compiler API may need TypeScript as a peer or dependency. A library that merely ships JavaScript and declarations does not automatically need a TypeScript peer. Do not impose a universal apps-pin/libraries-range rule; identify which interface each package actually consumes.

An exact version reduces one source of drift. The lockfile records the resolved dependency graph, while package-manager version/options, platform, environment and scripts can also affect installation or output. A packageManager field states intended tooling but does not by itself prove that every invocation enforces it. Check the actual executable/version and use the repository's enforced installation route. A range with a committed lockfile can also have a stable resolved compiler until the graph is deliberately updated.

### 2) **Observe an upgrade and a complete local rollback**

Use **Node.js 20.20.2** and **npm 10.8.2** for this disposable fixture. It starts with the compatible JavaScript compiler **6.0.3** and then installs native **7.0.2**. Save these two files in an empty directory without a tsconfig. Remove the file label when saving JSON.

```json
// file: package.json
{
  "private": true,
  "type": "module",
  "scripts": {
    "version:compiler": "tsc --version",
    "check": "tsc --strict --target es2022 --module nodenext --noEmit demo.mts",
    "build": "tsc --strict --target es2022 --module nodenext --outDir dist demo.mts"
  },
  "devDependencies": { "typescript": "6.0.3" }
}
```

```typescript
// file: demo.mts
export function twice(value: number): number { return value * 2; }
console.log(twice(21));
```

Install, snapshot the inputs and run the baseline:

```bash
npm install
cp package.json package.before.json
cp package-lock.json package-lock.before.json
npm ci
npm run version:compiler
npm run check
npm run build
node dist/demo.mjs
```

The compiler reports 6.0.3, both scripts pass and the runtime prints 42. npm scripts select the installed local compiler here rather than an unrelated global tsc.

Now edit only the TypeScript version in package.json to 7.0.2 and run `npm ci`. It fails because the manifest and lockfile disagree. It does not silently rewrite the lockfile to upgrade. The [npm ci contract](https://docs.npmjs.com/cli/v10/commands/npm-ci/) documents that distinction. Update the installation intentionally and repeat the checks:

```bash
npm install
npm ci
npm run version:compiler
npm run check
npm run build
node dist/demo.mjs
```

These checks pass with compiler 7.0.2 and output 42. That is evidence for this small program, not compatibility for an application's linters, editor, framework or deployment build. Inspect the changed manifest and lockfile together before retaining an upgrade.

To rehearse the fixture's rollback, restore both saved inputs:

```bash
cp package.before.json package.json
cp package-lock.before.json package-lock.json
npm ci
npm run version:compiler
npm run check
npm run build
node dist/demo.mjs
```

The version returns to 6.0.3 and the same checks/output pass. Real migrations may also change source, configuration, plugins and generated artifacts. Preserve the prior revision and artifact route for those inputs; restoring a version string alone is not a complete rollback. This local exercise does not merge, publish or deploy anything.

### 3) **Promote interfaces with evidence, not one global readiness label**

Read the target release's changes and relevant tool support notes, then inventory the program's actual use: batch checking, JavaScript/declaration emit, build/watch mode, editor features, API-dependent tools and supported consumers. Classify new diagnostics and behavioral differences. Group fixes into reviewable changes, but choose ordering from prerequisites and failure causes rather than a mandatory error-class sequence. A multi-version jump may be practical for a small project; a staged transition may make a complex one easier to investigate.

[The VS Code team's first-hand migration account](https://code.visualstudio.com/blogs/2026/06/26/iterating-faster-with-ts-7) describes introducing checking, emission and editor usage in stages while retaining a fallback. That preview-era rollout supports the method of separate evidence, not a current support matrix or a schedule every team must follow. Its historical benchmarks are not measurements of this fixture.

Native checking can coexist with a compatible older API for a tool that still requires it. The [7.0 update's tool lesson](<../../../25 Update TypeScript 7.0/sections/2. Editor and Tool Compatibility/2.1. Editor and tool API compatibility.md>) supplies that arrangement; the [complete migration assessment](<../../../25 Update TypeScript 7.0/sections/5. Migration Assessment/5.1. Assess a complete native compiler migration.md>) checks source, lint, emit and fresh consumers independently. Do not replace the API package merely because native checking is green, or assume switching an editor provider also changes the release compiler.

For a library, test the claimed minimum and relevant newer compiler versions against the packed public declarations. Include the type relationships that callers depend on, not just parse acceptance. The [publishing owner](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>) demonstrates a legacy declaration that parses but infers a broader result. Add real runtime/bundler consumers where the support contract requires them. Record a blocked integration by its failing command, supported alternative and condition for revisiting it, rather than predicting when an ecosystem category will catch up.

### 4) **Common confusion**

A devDependency pin is not a library's consumer support range, and a broad peer range is not a compatibility test. Installation success does not prove declarations parse or a compiler API works. Keep package installation, source checking, API probes, editor operations and runtime tests distinct.

Identical runtime output for twice does not mean two compilers have identical inference or emitted code for every feature. The update domain owns documented differences such as Unicode inference and removed options. Investigate a known difference before suppressing it or demanding textual equality from outputs that have different contracts.

### 5) **Performance note**

Version policy is metadata, but changing compiler or dependency versions can change check time, emit and runtime behavior. Temporary comparison builds add work; their cost is not necessarily exactly twice one check. This fixture establishes versions, lockfile enforcement and behavior for one program. It does not benchmark performance or guarantee a particular upgrade duration or savings.

### 6) **Mentor note**

Ask a learner why npm ci rejected the edited manifest and which files the rollback needed. Then ask whether pinning a library's development compiler forces a consumer compiler version. A sound answer names the installed tool, resolved graph, published declaration contract and any actual API host relationship before proposing a version range.
