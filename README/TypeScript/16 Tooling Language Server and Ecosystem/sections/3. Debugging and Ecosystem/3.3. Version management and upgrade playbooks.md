## 3.3. Version management and upgrade playbooks

### 1) **Pinning vs ranging TypeScript** (exact pins for apps, ranges for libraries)

**Definition** — apps pin exact TypeScript versions (`"typescript": "5.9.3"` — reproducible builds, identical diagnostics per checkout); libraries range (`"^5.0.0"` — consumer choice preserved, minimum declared). Pins trade upgrade friction (manual bumps) for determinism; ranges trade determinism (consumer variance) for flexibility. `packageManager` + lockfiles enforce pins; `peerDependencies` ranges declare library support windows.

**What problem it solves / history** — ranged app compilers (`^5.x` auto-upgrading 5.8→5.9 — new errors/errors-removed mid-sprint, CI red without code changes) versus pinned library compilers (consumers locked to the library's exact tsc — ecosystem fragmentation per dependency). Each side pins what it *ships* (apps: behavior determinism) and ranges what it *supports* (libraries: consumer choice) — mismatches in either direction break the other side's assumptions.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), pin apps exact (lockfile + `"typescript": "x.y.z"` — deterministic diagnostics per checkout); range libraries (`peerDependencies` with tested minimum — consumer choice, declared floor); document the minimum supported TS per library (README badge + CI matrix job on the floor version — support claimed *and* proven).

**Runnable example** — pins and ranges stated (good vs bad, `tsc --strict`):

```typescript
// good — version-aware code (minimum-version features used deliberately — floor declared, usage consistent)
// (package.json shape, documented as config: apps {"devDependencies": {"typescript": "5.9.3"}} (pinned); libraries {"peerDependencies": {"typescript": "^5.0.0"}} (ranged))
export function pinned(): string { return "deterministic"; } // behavior identical across versions (no version-conditional code paths here)
console.log(pinned()); // deterministic — version policy (pins for apps, ranges for libraries — each side's assumptions honored)
// bad — ranged app compilers (auto-upgrades mid-sprint — new errors/errors-removed without code changes, CI red mysteriously)
// fix — exact pins for apps (deterministic diagnostics per checkout — upgrades deliberate PRs, never ambient drift)
```

```typescript
// good — minimum-version CI job (support floor proven, not claimed — matrix job on the minimum)
// (CI shape, documented as process: jobs: [ts-minimum, ts-latest] — floor green + ceiling green per PR)
// fix — minimum-version matrix (consumer floor verified — support claimed AND proven per release)
export function floor(): string { return "supported"; }
console.log(floor()); // supported — floor-tested (library claims verified where consumers live — oldest supported, not newest)
// bad — minimum declared, never tested (floor claim without CI job — consumers on old tsc hitting untested syntax paths)
// fix — matrix job on the floor version (support proven per release — claims without jobs are hopes)
```

```typescript
// good — upgrade PRs sized per version (one major/minor per PR — changelog triaged, errors classified, tests green)
// (upgrade shape: bump → tsc → triage error classes → fix per class → dual-pipeline verify — 13/4.1 sequencing applied to the compiler itself)
export function upgraded(): string { return "current"; }
console.log(upgraded()); // current — upgrades deliberate (PRs sized per version — changelog-driven, error-class-ordered)
// bad — multi-major jumps (4.x → 6.x in one PR — breaking changes compounded, error classes mixed, reverts impossible)
// fix — one version per PR (upgrade sequence: changelog triage → branch build → class-ordered fixes → dual verify)
```

**Common confusion** — "pinning prevents upgrades" — pinning *schedules* upgrades (deliberate PRs vs ambient drift — control, not prevention). "ranges serve apps" — ranges serve *libraries* (consumer choice); apps need determinism (pins) — each side's mechanism mismatched breaks the other's assumptions. "minimum-version testing is overkill" — minimum-testing *proves* support claims (consumers on old tsc are real users — untested floors are unhonest claims).

**Performance note** — version policy costs zero runtime (resolution-time/install-time only); upgrade PRs cost triage per error class (one-time per version); ambient drift costs mystery-red CI (unbounded debugging per incident). Determinism is free correctness.

**Mentor note** — show one ambient-drift incident (CI red without code changes — ranged compiler auto-upgrading) beside pinned determinism (identical diagnostics per checkout) — policy value in one comparison. Exercise: pin one ranged app + range-test one pinned library (each side corrected per rule). Review gate: ranged app compilers fail review (pins for apps); untested minimums fail review (matrix jobs for floors).

### 2) **Upgrade playbook** (changelog triage, branch builds, class-ordered fixes)

**Definition** — upgrade sequence: changelog triage (breaking + deprecation + behavior-change sections read first — scope sized before starting), branch builds (`tsc` on the bumped branch — error inventory per class), class-ordered fixes (nullability/variance/import-kinds/enum-syntax per class per PR — same sequencing as 13/4.1 promise 4), dual-pipeline verification (tsc + bundler/stripping agreeing post-upgrade). One major/minor per PR — green throughout, revertible always.

**What problem it solves / history** — upgrade-by-bumping (version changed, errors fixed ad hoc until green — classes mixed, suppressions slipped in as "temporary", behavior changes unnoticed until production) produced green-but-wrong upgrades (suppressed diagnostics masking real breakage, behavior deltas discovered post-deploy). Playbook upgrades produce green-*and*-right (class-ordered fixes reviewed per class, behavior deltas tested per changelog entry).

**Modern guidance** — as of TypeScript 5.9 era, upgrade in playbook order (changelog → branch → triage → class-ordered fixes → dual verify → merge); fix per error class (one class per commit within the PR — reviewable chunks, revertible steps); verify behavior beyond types (emit diffs, runtime smoke, dual-pipeline agreement — upgrades change *behavior* (emit/helpers), not just diagnostics).

**Runnable example** — playbook executed (good vs bad, `tsc --strict`):

```typescript
// good — changelog-triaged upgrade (scope sized before starting — breaking/deprecation/behavior sections read first)
// (playbook step 1: changelog triage (entries classified: breaking (fix now) / deprecated (plan) / behavior (test) — scope known pre-build)
export function triaged(): string { return "scoped"; } // scope known (upgrade sized — no surprise classes mid-PR)
// bad — bump-and-fix-ad-hoc (version changed, errors fixed until green — classes mixed, suppressions slipped, behavior unnoticed)
// fix — playbook order (changelog → branch → triage → class-ordered fixes → dual verify → merge — green AND right)
console.log(triaged()); // scoped — triaged upgrade (scope-first sequencing — surprises eliminated before starting)
```

```typescript
// good — class-ordered fixes (one error class per commit — reviewable chunks, revertible steps)
// (playbook steps 2-4: branch build (error inventory per class) → class-ordered fixes (nullability → imports → syntax) → per-class green)
// fix — per-class commits (reviewable chunks — each class independently revertible, uniformly fixed)
export function ordered(): string { return "sequenced"; }
console.log(ordered()); // sequenced — class-ordered fixes (same sequencing as 13/4.1 promise 4 — migration discipline reused)
// bad — mixed-class fix commits (nullability + imports + syntax per commit — unreviewable, unrevertible, suppression-prone)
// fix — one class per commit (uniform fix discipline per PR — reviewers verify patterns, not archaeology)
```

```typescript
// good — dual-pipeline verification post-upgrade (tsc + bundler/stripping agreeing — behavior verified, not just diagnostics)
// (playbook step 5: dual verify (emit diffs reviewed, runtime smoke green, pipelines agreeing — upgrades change behavior too)
// fix — behavior verification (emit diffs + smoke tests + pipeline agreement — diagnostics green AND runtime correct)
export function verified(): string { return "dual-green"; }
console.log(verified()); // dual-green — verified upgrade (types + emit + runtime agreeing — green AND right)
// bad — diagnostics-only verification (tsc green, emit/behavior unverified — behavior deltas discovered post-deploy)
// fix — dual verify (emit diffs reviewed, smoke green, pipelines agreeing — behavior verified per upgrade, always)
```

**Common confusion** — "playbooks slow upgrades" — playbooks *sequence* upgrades (same total triage distributed across green PRs vs one red quarter) — faster wall-clock *and* safer (compounding green beats stalled red on both axes). "changelog reading is optional" — changelog triage *sizes* the upgrade (breaking count known pre-build — scope surprises eliminated); unread changelogs produce mid-PR discoveries (re-scoping under pressure). "dual verification duplicates CI" — dual verification *extends* CI (emit + runtime agreement beyond diagnostics — behavior deltas caught pre-merge, not post-deploy).

**Performance note** — playbook upgrades cost triage per error class (one-time per version); big-bang upgrades cost stalled quarters + suppression debt (unbounded); dual verification costs seconds per pipeline (parallelizable). Sequenced economics dominate at every upgrade size.

**Mentor note** — run one playbook upgrade live (changelog → branch → triage → class-ordered fixes → dual verify → merge — green throughout) beside one big-bang attempt (red quarter, suppressions, behavior surprise) — sequencing demonstrated, not asserted. Exercise: upgrade one minor version per playbook solo (triage + class-order + dual verify — full loop in under a day typical). Review gate: un-triaged upgrades fail review (changelog-first, always); suppression fixes fail review (class-ordered, never theater).

### 3) **Ecosystem lag management** (framework/editor/linter support windows)

**Definition** — ecosystem lag: frameworks/editors/linters supporting TypeScript versions behind latest (Next.js bundling TS X-1, ESLint rules parsing X-1 syntax, editor bundles lagging releases) — upgrading past ecosystem support breaks tooling while code stays green (parse failures in linters, missing syntax in editors, bundler transpile gaps). Management: support windows tracked per dependency (framework × editor × linter matrices), upgrades gated on ecosystem readiness (all green before bumping), lag documented where blocking.

**What problem it solves / history** — day-one major upgrades (TS 6.0 Monday, broken ESLint parsing Tuesday, editor red squiggles everywhere Wednesday — tooling lagging language releases by weeks-to-months) forced reverts (downgrade PRs erasing triage work) or limping (new syntax banned informally — undocumented, unenforced, drifted). Lag management sequences upgrades *behind* ecosystem readiness (track windows → upgrade when green → adopt new syntax after tooling supports parsing it).

**Modern guidance** — as of TypeScript 5.9 era, track support windows per dependency (framework major × TS version matrix; editor bundled-TS vs workspace-TS; typescript-eslint version support notes); gate upgrades on ecosystem green (all three ready before bumping — readiness verified, not hoped); document lag blocks (pinning with reason + revisit date — blocked upgrades scheduled, not forgotten).

**Runnable example** — lag-gated upgrades (good vs bad, `tsc --strict`):

```typescript
// good — support-window tracking (upgrades gated on ecosystem readiness — verified, not hoped)
// (matrix shape: { framework: "ready", editor: "ready", linter: "ready" } → bump approved (all green — upgrade proceeds)
// fix — readiness gates (track windows per dependency — bump when green across the matrix, never before)
export function ready(): string { return "ecosystem-green"; }
console.log(ready()); // ecosystem-green — gated upgrade (readiness verified — tooling lag respected, not discovered)
// bad — day-one major upgrades (tooling lagging language releases — parse failures, missing syntax, transpile gaps post-bump)
// fix — lag management (support windows tracked — upgrades sequenced behind ecosystem readiness, always)
```

```typescript
// good — documented lag blocks (pinning with reason + revisit — blocked upgrades scheduled, never forgotten)
// (pin shape: typescript pinned + TODO(ecosystem): unblock on framework-vX (revisit date) — block visible, expiry scheduled)
export function blocked(): string { return "pinned-with-reason"; }
console.log(blocked()); // pinned-with-reason — documented block (reason + revisit — upgrades queued, not abandoned)
// bad — silent lag (upgrade failing mysteriously — tooling errors misattributed to code, weeks lost per cycle)
// fix — lag documentation (pins + reasons + revisit dates — blocked upgrades visible, scheduled, expirable)
```

```typescript
// good — syntax adoption gated on tooling parse support (new syntax used after linters/editors parse it — never before)
// (adoption shape: tsc supports → linter parses → editor highlights → codebase adopts (staged per tool, in that order)
// fix — staged adoption (language → tooling → codebase — each stage verified before the next begins)
export function staged(): string { return "parsed-everywhere"; }
console.log(staged()); // parsed-everywhere — staged adoption (tooling parsing verified pre-adoption — no gaps)
// bad — new-syntax adoption day-one (linter parse failures, editor red squiggles — tooling lag discovered per file)
// fix — adoption sequencing (tsc → tooling → codebase — staged, verified per stage, never rushed)
```

**Common confusion** — "lag management delays upgrades" — lag management *sequences* upgrades (ecosystem-ready bumps merging cleanly vs day-one bumps reverting messily — faster wall-clock *and* safer). "pinning is the same as lagging" — pins *await* readiness (documented, dated, expiring); lag *ignores* readiness (silent, indefinite, discovered per incident). "ecosystem always catches up fast" — majors lag weeks-to-months per dependency (frameworks slowest, editors medium, linters variable) — track per dependency, never assume aggregate speed.

**Performance note** — lag tracking costs minutes per quarter (matrix review); day-one upgrades cost revert PRs + triage rework (weeks per incident); staged adoption costs nothing beyond sequencing (same total triage, ordered sanely). Lag economics favor patience heavily.

**Mentor note** — table one upgrade's ecosystem matrix live (framework × editor × linter readiness per TS version — green/red cells deciding the bump date). Exercise: document one lag block fully (pin + reason + revisit + matrix evidence) — blocked-upgrade hygiene in under an hour. Review gate: major bumps without ecosystem matrix fail review (readiness verified, not hoped).
