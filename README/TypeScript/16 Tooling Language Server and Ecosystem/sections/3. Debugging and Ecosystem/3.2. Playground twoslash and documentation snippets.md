## 3.2. Playground, twoslash, and documentation snippets

### 1) **Playground as a verification tool** (isolated reproductions, version switching, share links)

**Definition** — the TypeScript Playground (typescriptlang.org/play) runs full programs in-browser: version switching (5.x–6.x–nightly per URL param), shareable links (reproduction + config encoded), multi-file tabs, and emit/AST viewers. Verification uses: minimal reproductions for bug reports (isolated from repo complexity), version bisection (works-on-5.8-breaks-on-5.9 narrows regressions), and behavior probes (hover/emit inspection without local setup).

**What problem it solves / history** — unreproducible bug reports ("fails on my machine" — 50k-line repo context, local config, unshared state — maintainers unable to start) stalled issues for weeks (reproduction-request ping-pong). Playground links collapse reproduction to one URL (minimal code + pinned version + visible config — maintainers debugging in one click). This track's own fence-verification discipline (isolated `/tmp` snippets per example) is the local equivalent of the same practice.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), reproduce every bug report as a playground link before filing/triaging (minimal code, pinned version, expected-vs-actual stated); bisect versions via URL switching (regression windows in minutes, not bisect-builds); probe emit/hover questions in playgrounds before asking teammates (self-service verification, links as evidence).

**Runnable example** — reproduction discipline (good vs bad, `tsc --strict`):

```typescript
// good — minimal reproduction shape (isolated snippet: imports trimmed, config pinned, behavior asserted)
// (playground equivalent: 10-line link with version param — maintainers debugging in one click)
export function minimal(input: string): string { return input.toUpperCase(); } // trimmed (no repo context — reproduction isolated)
console.log(minimal("x")); // X — expected-vs-actual stated (behavior asserted inline — report complete without prose)
// bad — "fails on my machine" reports (50k-line context, local config, unshared state — maintainers unable to start)
// fix — playground link per report (minimal code + pinned version + expected-vs-actual — reproduction complete in one URL)
```

```typescript
// good — version-bisection shape (same code, version param varied — regression windows in minutes)
// (playground: ?ts=5.8 vs ?ts=5.9 on identical code — behavior delta locates the breaking change precisely)
export function stable(s: string): string { return s; } // version-agnostic construct (bisectable — no version-specific syntax)
console.log(stable("v")); // v — bisection-ready (identical snippet across versions — delta attributable to compiler, never code)
// bad — "broke after upgrade" without bisection (version range unknown — maintainers bisecting blind across majors)
// fix — URL-switched bisection (same link, version param varied — regression window in minutes, not bisect-builds)
```

```typescript
// good — emit/hover probing shape (behavior questions answered without local setup)
// (playground emit viewer: .js output inspected per construct — erasability/emit questions self-served)
export function probe(n: number): number { return n * 2; } // probe target (minimal — one construct per question)
// (hover viewer: inferred types inspected per expression — widening/inference questions self-served identically)
console.log(probe(21).toFixed(0)); // 42 — probed behavior (evidence linked, not described — links as verification)
// bad — "does X emit Y?" questions without probes (teammates answering from memory — folklore per recall)
// fix — playground probes (emit/hover inspected — evidence linked, folklore retired)
```

**Common confusion** — "playgrounds replace local reproduction" — playgrounds *isolate* (minimal cases, version control, shareability); local reproduction *contextualizes* (repo config, dependencies, scale interactions) — isolate first (playground), contextualize second (local), always in that order. "share links rot" — pinned versions + minimal code stay reproducible indefinitely (unlike "latest + repo snapshot" links — pin versions, trim context). "playground config matches repos" — playground defaults differ (strict off historically — set flags explicitly per reproduction, or reproduce the wrong configuration's behavior).

**Performance note** — playground verification costs seconds per question (browser execution, no setup); local reproduction costs environment setup per question (clones, installs, config matching). Isolate-first economics dominate for behavior questions; contextualize for integration questions.

**Mentor note** — require playground links on every bug report for a quarter (reproduction quality transforming issue triage permanently). Exercise: reduce three "fails here" reports to playground minimums (trim config, pin versions, state expected-vs-actual — reproduction discipline in under an hour). Review gate: bug reports without reproductions fail process review (evidence first, always).

### 2) **Twoslash documentation** (hover-annotated snippets keeping docs honest)

**Definition** — twoslash (`// @filename`, `// ---cut---`, `// ^?` hover queries in markdown code blocks) type-checks documentation snippets *as part of docs builds* (Shiki-twoslash/VitePress integration): hover annotations render checked types inline (`const x: string` with `^?` showing the hover), cut markers hide boilerplate while checking it, multi-file blocks verify cross-file examples. Docs that compile — drift structurally impossible.

**What problem it solves / history** — documentation snippets rotted (API examples from v2 shown against v5 — untested markdown, wrong signatures, fictional outputs — every reader a beta tester). Twoslash converts docs into test surface: snippet errors fail docs builds (drift caught like code), hover queries prove claims inline (types shown, not described). This track's fence-verification (every example compiled per session) practices manually what twoslash automates.

**Modern guidance** — as of TypeScript 5.9 era, annotate teaching snippets with twoslash where docs tooling supports it (hover queries per claim — types proven inline, not asserted); cut boilerplate (`// ---cut---` hiding imports/setup while checking them — readers see essence, checkers see everything); fail docs builds on snippet errors (drift caught like code — documentation with tests, not hopes).

**Runnable example** — honest snippets (good vs bad, `tsc --strict`):

```typescript
// good — claimed types proven inline (hover-query style: assertion per claim — twoslash automates this shape)
// const greeting = "hi"; // ^? const greeting: string (twoslash hover query — checked type rendered inline)
const greeting = "hi";
console.log(greeting.toUpperCase()); // HI — claim proven (hover shows string — widening visible, not described)
// bad — undescribed claimed outputs (docs asserting behavior prose-only — drift invisible until readers trip)
// fix — hover queries per claim (types proven inline — documentation with tests, not hopes)
```

```typescript
// good — cut boilerplate pattern (hidden setup checked, visible essence taught)
// (twoslash // ---cut--- shape: imports/setup above the cut (checked), lesson below (focused) — readers see essence)
// (this fence: zero boilerplate needed — essence only, checked fully — cut markers unnecessary where setup is trivial)
export function essence(s: string): string { return s.trim(); }
console.log(essence("  x  ")); // x — essence taught (setup trivial here — cut markers serve complex setups, not this one)
// bad — 40-line setup dumps per 3-line lesson (readers wading through imports for one insight — signal buried)
// fix — cut markers (boilerplate checked-but-hidden — readers see essence, checkers see everything)
```

```typescript
// good — multi-file documentation (cross-file examples verified as sets — 12/3.x patterns documented honestly)
// (twoslash // @filename blocks: each file checked, imports resolved — documentation sets compiling like real programs)
// (this track practices manually what twoslash automates: isolated sets per example, verified per session — see promise 3)
export function documented(a: number, b: number): number { return a + b; } // documented shape (checked fully — drift impossible)
console.log(documented(20, 22).toFixed(0)); // 42 — docs compiling (twoslash-automated or fence-verified — honesty either way)
// bad — single-file-extracted multi-file examples (imports removed for brevity — examples that never compiled as shown)
// fix — filename blocks (cross-file examples verified as sets — brevity via cut markers, never via deletion)
```

**Common confusion** — "twoslash is documentation theater" — twoslash *checks* (snippet errors fail builds — drift caught mechanically); untested snippets *hope* (drift caught by readers — theater). "hover queries clutter docs" — queries annotate *claims* (one per non-obvious type — evidence inline); prose-only claims clutter *understanding* (readers verifying mentally what tooling could prove). "this track doesn't need twoslash" — this track *practices* twoslash's discipline manually (fence verification per session — automation pending, honesty present either way).

**Performance note** — twoslash checking costs docs-build seconds (typecheck per snippet — incrementalizable); untested-snippet drift costs reader trust (unbounded — every wrong example taxes all future readers). Docs-build checking is the cheapest trust available.

**Mentor note** — annotate three doc snippets with hover queries live (claims proven inline — documentation honesty in under an hour). Exercise: break one documented snippet deliberately and watch docs CI fail (drift caught like code — automation proven, not hoped). Review gate: documentation code samples without checking (twoslash or fence-verified) fail review.

### 3) **This track's verification pattern** (isolated snippets per fence, verified per session)

**Definition** — this repository's own discipline (practiced across Sessions 1–7, units 01–125): every leaf example extracted per fence and compiled (`tsc --strict` + module-appropriate flags — nodenext/node16/esnext-lib variants per need), multi-file sets split and program-checked (`check_mod.py` — imports resolved, cross-file contracts verified), failures fixed or documented as commented-error demos (intended errors labeled with codes, never left failing). Docs that compile — enforced by harness, not hoped by authors.

**What problem it solves / history** — tutorial examples rot fastest (readers copy-pasting into newer compilers — stale syntax failing on arrival; unverified claims eroding trust per page). Per-session fence verification (this track's LOG-verified practice — 138 checks in domain 15 alone) makes examples *assets* (runnable as-shown, version-labeled, regression-checked per continuation) instead of liabilities.

**Modern guidance** — as of TypeScript 5.9 era, verify every documentation example mechanically (fence extraction + `tsc` per session — this track's harness pattern, adoptable per docs repo); label intended errors (commented demos with codes — TS2322/TS1294/TS1484 documented, never failing); record verification in logs (counts + fixes per session — honesty auditable, not asserted).

**Runnable example** — verification practiced (good vs bad, `tsc --strict`):

```typescript
// good — fence-extracted example (isolated, compiled, green — this track's unit of honesty)
export function honest(n: number): number { return n; } // extracted per fence (compiled standalone — no cross-fence references)
// (checker: tsc --strict (+ module/lib flags per need) — green means runnable-as-shown, period)
console.log(honest(7).toFixed(0)); // 7 — verified example (readers copy-paste with confidence — assets, not liabilities)
// bad — unextracted documentation examples (cross-fence references, missing imports, version drift — liabilities per page)
// fix — fence verification per session (isolated compilation — examples runnable as-shown, always)
```

```typescript
// good — intended errors labeled (commented demos with codes — documented, never failing)
// const bad: string = 42; // error TS2322 (intended-error demo shape — labeled with code, educational, green)
// fix — commented-error convention (demonstrate failures without failing — diagnostics taught, builds green)
export function fine(s: string): string { return s; } // green fence (intended errors commented — builds passing, lessons intact)
console.log(fine("ok")); // ok — labeled errors (diagnostics taught via comments — builds green via commenting discipline)
// bad — live error demos (failing fences — builds red, readers confused about intent vs accident)
// fix — comment intended errors (codes labeled — failures demonstrated, never committed as failures)
```

```typescript
// good — verification logged (counts + fixes per session — honesty auditable, not asserted)
// (LOG pattern: fences-verified counts, DOM-collision renames, flag discoveries, depth fixes — per session, in place)
// fix — continuous logging (verification recorded per unit — crash-recovery + honesty-audit in one mechanism)
export function logged(): string { return "verified"; }
console.log(logged()); // verified — logged verification (counts auditable — trust earned per session, not claimed)
// bad — unverified example dumps (hundreds of fences, zero checking — liabilities compounding per page per release)
// fix — harness verification (extraction + tsc + logging per session — examples as tested assets, permanently)
```

**Common confusion** — "verification slows authoring" — verification *catches* (DOM collisions, flag changes, cross-fence references — each caught in seconds vs reader-reported issues over quarters). "commented errors teach less" — commented errors teach *diagnostics* (codes + messages + fixes — labeled intentionally); live errors teach *confusion* (red builds, unclear intent). "logging verification is bureaucratic" — logged counts *prove* honesty (auditable per session); unlogged verification is indistinguishable from skipped verification.

**Performance note** — fence verification costs seconds per leaf (extraction + tsc per fence — parallelizable); reader-reported issue triage costs hours each (reproduction + diagnosis + fix + release). Verification economics favor automation overwhelmingly at tutorial scale.

**Mentor note** — adopt fence verification for one docs repo (extraction + tsc + logging per change — examples as tested assets within a week). Exercise: verify ten existing examples (failures found = liabilities retired; passes = assets confirmed). Review gate: unverified documentation examples fail review (twoslash or fence-checked — honesty enforced, not hoped).
