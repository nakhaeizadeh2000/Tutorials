## 3.2. Playground, twoslash, and documentation snippets

### 1) **Match the reproduction to the question**

The TypeScript Playground is useful for sharing a small compiler question with its selected version and relevant options. A reproduction should state expected and observed behavior, preserve the condition that triggers the problem and identify the environment. Start locally when package contents, filesystem layout, build tools or runtime integration are central; reducing those away can remove the actual failure.

The [Playground URL guide](https://www.typescriptlang.org/_playground-handbook/url-structure.html) describes encoded code, compiler options and version selection. Check the selected version rather than treating latest or nightly as a pinned result. A URL is convenient evidence to share, but external type acquisition, service availability and changing defaults can limit long-term reproduction. Keep important source and configuration in a reproducible local fixture too.

The [Run documentation](https://www.typescriptlang.org/_playground-handbook/running-code.html) describes executing generated JavaScript in the browser session. That is a different host from Node. Compiler diagnostics, displayed type information, emitted JavaScript and runtime output are separate observations. Do not assume that a browser Run result exercises a package's Node loader or native TypeScript 7 server.

### 2) **Actually check a Twoslash sample**

Twoslash processes annotated source to obtain diagnostics and type information for documentation tooling. A renderer can display that data in highlighted code. Merely writing a `// ^?` comment in Markdown does not invoke it, and ordinary tsc treats the notation as a comment.

This local example uses **Node.js 20.20.2**, **twoslash 0.3.9** and a compatible **TypeScript 6.0.3 JavaScript API**. Native **TypeScript 7.0.2** separately compiles the runtime sample. Those are intentionally distinct tool results. Save the files in an empty directory without a tsconfig and run `npm install`. Commit the generated lockfile in a documentation project that adopts this setup.

```json
// file: package.json
{ "private": true, "type": "module", "devDependencies": { "twoslash": "0.3.9", "typescript": "6.0.3" } }
```

```typescript
// file: sample.ts
const hidden: number = 1;
// ---cut---
const greeting = "hi";
//    ^?
console.log(greeting.toUpperCase(), hidden);
```

The query marker points at greeting on the line above. The cut marker removes preceding setup from the displayed result after the full source has been checked. The complete saved source still matters: copying only the visible code would leave hidden undefined. Supply a complete example or make hidden setup available to the reader.

```javascript
// file: verify.mjs
import assert from "node:assert/strict";
import { readFileSync } from "node:fs";
import ts from "typescript";
import { createTwoslasher } from "twoslash";
const check = createTwoslasher({ compilerOptions: {
  strict: true, target: ts.ScriptTarget.ES2022,
  module: ts.ModuleKind.ESNext, moduleResolution: ts.ModuleResolutionKind.Bundler, types: []
} });
const source = readFileSync(new URL("./sample.ts", import.meta.url), "utf8");
const result = check(source, "ts");
assert.equal(result.errors.length, 0);
assert.equal(result.queries[0].text, 'const greeting: "hi"');
assert.equal(result.code.includes("const hidden"), false);
console.log(result.queries[0].text);
const bad = 'const wrong: number = "x";';
assert.throws(() => check(bad, "ts"), /2322/);
const expected = check("// @errors: 2322\n" + bad, "ts");
assert.equal(expected.errors[0].code, 2322);
console.log("unexpected error rejected; expected error recorded");
const multi = check(`// @filename: a.ts
export const port = 7;
// ---cut---
// @filename: b.ts
import { port } from "./a";
const value = port;
//    ^?`, "ts");
assert.equal(multi.queries[0].text, "const value: 7");
console.log(multi.queries[0].text);
```

Run `node verify.mjs`. It prints:

```text
const greeting: "hi"
unexpected error rejected; expected error recorded
const value: 7
```

The first query reports a literal, not string. That corrects a common widening misconception. The expected-error sample deliberately contains an invalid assignment; it is checked and recorded, not executed. The multi-file sample checks a virtual import and preserves the literal from another file. [Twoslash's notation reference](https://twoslash.netlify.app/refs/notations) explains queries, cuts and virtual filenames; its [API reference](https://twoslash.netlify.app/refs/api) documents the instance used here.

Now separately compile the complete saved sample with the native compiler and run it:

```bash
tsc --strict --target es2022 --module nodenext --outDir dist sample.ts
node dist/sample.js
```

It prints `HI 1`. That runtime result was observed independently of the Twoslash queries. This fixture obtains data through the API; it does not render HTML, run a documentation framework or automate the Playground UI. To try the browser manually, copy the complete sample, select a supported compiler version and relevant options, compare the inferred literal and run its generated JavaScript. Record that browser result separately.

### 3) **Make the documentation check an honest gate**

A docs integration must select the intended snippets, load their dependencies and fail when its validation policy fails. Expected errors intentionally permit specified diagnostics. The [options reference](https://twoslash.netlify.app/refs/options) also documents noErrors, noErrorsCutted and noErrorValidation; these can suppress or bypass error validation. A successful documentation build therefore does not automatically mean every code sample is valid. Review those settings and verify a deliberately unexpected error fails the actual integration.

[Fatih Kalifa's original 2020 integration account](https://fatihkalifa.com/blog/typescript-twoslash) explains the practical sequence of build-time annotations, expected diagnostics and hidden setup. Its older package, result fields and rendering APIs differ from this pinned fixture. Reuse the reasoning rather than copying historical integration code unchanged.

For this tutorial, attach evidence to the exact file set, options and commands that ran. Compiling a commented negative example does not execute its failure. A generated hover string does not assert a runtime result. Splitting each fence into unrelated programs can also destroy an intentional multi-file example. Group source by the named files and run the appropriate type, runtime, package or editor checks. A log count helps locate evidence; the count alone cannot prove the prose or all other lessons correct.

### 4) **Common confusion**

A Twoslash query shows the chosen compiler's presentation of a type at a position. An assertion in verify.mjs makes this specific display an expected result; a query comment alone does not assert the author's prose. A changed display can require investigation without proving an API became incompatible. Use type relationships when that is the contract being tested.

Cuts hide code from presentation, not necessarily from checking, while error-suppression options can change validation. Neither a clean visible snippet nor a green build proves hidden setup or external behavior correct. An intentional error is useful teaching when its purpose and observed diagnostic are explicit.

### 5) **Performance note**

Loading libraries and creating compiler environments can add documentation-build cost. The factory can reuse environments across calls with compatible options, but that is not a fixed speedup or a promise about the whole documentation build. This fixture checked outputs and validation behavior; it did not measure throughput, browser startup or renderer cost.

### 6) **Mentor note**

Ask the learner to predict greeting's type, explain why hidden must remain in the complete source and identify what the expected-error tag permits. Then remove that tag and observe verification fail. A strong answer distinguishes compiler data, an explicit assertion, presentation and separately executed runtime behavior.
