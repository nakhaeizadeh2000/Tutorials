## 7.1. Boundaries — what is covered elsewhere

Tools observe different parts of a TypeScript project. An editor query, compiler check, lint rule, package consumer and runtime test can disagree because they inspect different inputs or establish different claims. Identify the tool and operation before changing a setting. This lesson routes those questions to their owners and uses completed worked examples for practice.

### 1) **Compiler interfaces and daily editor work**

[language-server motivation](<../../../01 Fundamentals and Mental Model/sections/2. How TypeScript doesnt execute/2.3. The language server editor superpowers that justify TypeScript.md>) and [compilation stages](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.1. The compilation pipeline tsc emit declarations and source maps.md>) explain the purpose of interactive queries and compilation. [the verified execution-path lesson](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>) separates checking from source/output execution. Here, [definition and reference navigation](<../1. Language Server in Practice/1.1. Navigation go to definition find references.md>), [renames and code actions](<../1. Language Server in Practice/1.2. Rename refactorings and code actions.md>) and [hover and signature help](<../1. Language Server in Practice/1.3. Inlay hints hover and signature help.md>) own daily editor operations. Use them to inspect the resolved declaration, related references and the signature available at the current call site.

Record which project and compiler the editor uses when its result differs from the command-line check. A small compiler reproduction can establish a type relationship; it does not demonstrate that a particular editor action ran correctly. Likewise, printing a function's return value does not verify go-to-definition or rename behavior.

[the verified editor/tool-interface lesson](<../../../25 Update TypeScript 7.0/sections/2. Editor and Tool Compatibility/2.1. Editor and tool API compatibility.md>) tests another interface boundary: a native compiler command and a tool importing the older JavaScript compiler API. Its configured fixture checks both compilers, runs typed ESLint and exposes the missing old API function in the native package. Use that owner for a tool-interface failure, and retain the distinction between its executed commands and its documented but unexecuted editor settings.

### 2) **Configuration, lint and formatting**

[configuration ownership](<../../../13 Configuration and Compiler Options/sections/7. Overlaps to avoid/7.1. Boundaries what is covered elsewhere.md>) owns the checked program and option selection. [the bounded syntax-gate lesson](<../../../13 Configuration and Compiler Options/sections/2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>) establishes separate syntax/import restrictions. This domain owns [type-aware linting](<../2. Lint Format and Checks/2.1. typescript-eslint rules and type-aware linting.md>) and [formatting discipline](<../2. Lint Format and Checks/2.2. Prettier dprint and formatting discipline.md>) for their rules, configuration and enforcement. Determine which diagnostic came from which command before changing an annotation or suppressing it.

A compiler can accept a call whose returned Promise is ignored while a configured lint rule rejects that use. The verified editor/tool fixture demonstrates exactly that: both compilers pass its added pending job call, and no-floating-promises reports it. A green compiler check is therefore useful evidence about the checked program, while the selected lint rule establishes an additional handling policy.

Formatting and code actions need their own boundaries too. Review the actual diff when an action changes imports or identifiers, then check the affected graph and behavior. A formatting check does not validate a package entry point, and a semantic rename cannot be assumed to update every runtime string or external reference. Choose the relevant operation owner instead of attributing correctness to the presence of automation.

A producer's successful source check does not establish that its tarball includes the declarations its consumer needs. [the complete native migration assessment](<../../../25 Update TypeScript 7.0/sections/5. Migration Assessment/5.1. Its missing-declaration mutation keeps runtime import working while consumer checking fails. Inspect that artifact before replacing the consumer's contract with an any shim.

Import automation can also affect runtime edges. The import owner compares whole-statement erasure with a retained inline-only import and executes source/output extension failures. Preserve required initialization deliberately and run the intended entry points. An organized import block is not proof that the loader can locate its retained destinations.

[the executed type-testing lesson](<../../../17 Testing Types/sections/1. For async work, [the verified completion/return lesson](<../../../05 Functions and Callable Types/sections/1. Function Type Fundamentals/1.3. Return types void never and contextual inference.md>) supplies a controlled task gate contrasting an ignored void callback result with an awaiting host. [the async-return lesson](<../../../18 Async Types and Standard Library/sections/1. Promise Types/1.3. async function return-type contracts.md>) owns async return types. A lint pass, Promise annotation and successful synchronous host return do not establish that the underlying task completed or that its rejection was handled. Test the consumer that owns completion and failure.

Use [Playground and documentation reproductions](<../3. Debugging and Ecosystem/3.2. Playground twoslash and documentation snippets.md>) for a small explanation or bug report with explicit compiler version and options. Match the original program's relevant context and state what actually ran. A Playground result can explain a compiler relationship; it does not replace a project's package-consumer, runtime, editor or tool-interface check. Keep an execution outcome attached to its actual command and environment.

Compare representative conditions before proposing graph partitioning, caches or weaker checks; neither a monorepo nor a reference setting alone proves a speedup.

Replaying the relevant checks is more informative than copying a fixed migration cadence or assuming that every ecosystem consumer upgrades through the same interface.

### 6) **Common confusion**

Tools do not all use the same program or expose the same compiler interface. Establish the resolved files, options, version and entry point before interpreting a disagreement. A native CLI pass does not imply that an older compiler-API consumer can import the required function.

Passing one gate cannot establish every layer. The lint-only failure and missing-declaration tarball are concrete examples: source checks stay green while another relevant consumer rejects the result. Use each tool's output for the claim it actually checks.

A reproduction, an editor setting and a runtime test are also different evidence. State which operation ran. Avoid describing a hover or rename as verified merely because the underlying source compiled, or describing a package as healthy because a local function printed the expected value.

### 7) **Performance note**

This navigation lesson has no direct performance effect. Type-aware lint, compiler checks, package analysis, test suites and editor requests can perform different work and may construct different programs. Their cost depends on inputs, caches, processes and configuration. No fresh tool, editor, timing or memory benchmark was run here.

Use the measurement owners to compare the operation that matters with matching conditions. Keep checking, emission, linting, tests and editor latency distinguishable. A shared diagnostic label does not make their timings interchangeable, and automation does not guarantee negligible cost or prevent every maintenance error.

### 8) **Mentor note**

Require the tool, failing operation, relevant owner and next observable check. These cases use prior executed evidence:

1. **Both compiler checks pass, but typed lint reports an ignored Promise.** Inspect the configured rule and completion owner. The editor/tool fixture demonstrates the lint-only failure; the return lesson shows why an ignored callback result does not establish completion.
2. **Native checking works, but a tool calls an absent createProgram function.** Identify its imported compiler API. The verified interface lesson observes the native package's missing old function and tests a compatible tool arrangement separately from the native command.
3. **A library builds, but a fresh consumer cannot find its declaration files.** Inspect the packed files and entry points. The complete migration assessment reproduces this consumer failure while runtime import still succeeds.

Ask the learner to reject a proposed blanket shim, suppression or dependency upgrade by naming the unchanged failure mechanism. Require the restored gate and relevant consumer run. For a responsiveness problem, choose a build or editor measurement before changing a tuning option, and state which claim remains untested.
