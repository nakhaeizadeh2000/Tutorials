## 1.2. Rename refactorings and code actions

### 1) **Rename-symbol mechanics** (occurrence rewriting across files)

**Definition** — rename-symbol (`F2`) rewrites *every occurrence* of a binding (declaration, reads, writes, type positions, import/export aliases, JSDoc name references where configured) across the program in one atomic edit — previewable per occurrence, undoable as one operation. Unlike text find-replace (which rewrites comments/strings/unrelated identifiers), rename touches exactly the binding's occurrences — shadowing distinguished, aliases followed.

**What problem it solves / history** — text-based renames (`sed s/old/new/` — comments rewritten, strings corrupted, shadowed locals renamed wrongly, aliased imports missed) broke code that *looked* renamed (all text changed) while semantics shifted (wrong bindings rewritten, right ones missed). Semantic rename rewrites bindings (checker-resolved occurrences — complete and exact), with text search reserved for the non-binding remainder (comments/strings updated deliberately, separately).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), rename via the server (F2 — preview occurrences, apply atomically); follow with text search for comments/strings mentioning the old name (deliberate second pass — prose updated consciously, never by rewrite); prefer rename-friendly declarations (named exports over defaults — one name everywhere renames once; see 12/1.1).

**Runnable example** — binding rename vs text rename (good vs bad, `tsc --strict`):

```typescript
// good — rename-friendly declarations (one name per binding — server rename rewrites completely)
export interface Customer { id: string }
export function customerName(c: Customer): string { return c.id.toUpperCase(); }
const cust: Customer = { id: "c" };
console.log(customerName(cust)); // C — F2 on Customer rewrites all three occurrences atomically (declaration + param + annotation)
// bad — default-anonymous exports (rename untargetable — no stable name to rewrite; text search per alias dialect)
// fix — named exports (rename-symbol operates — one name everywhere, previewable, atomic)
```

```typescript
// good — shadowed locals distinguished (rename touches the binding, never the shadow)
function outer(): string {
  const token = "outer";
  function inner(): string {
    const token = "inner"; // shadows (distinct binding — server rename of outer.token skips this occurrence)
    return token.toUpperCase();
  }
  return `${token}:${inner()}`;
}
console.log(outer()); // outer:INNER — shadowing respected (rename outer.token → inner.token untouched — text replace would corrupt both)
// bad — sed s/token/key/ (both bindings rewritten — shadowing destroyed, semantics shifted silently)
// fix — F2 rename (binding-resolved occurrences — shadows distinguished structurally, never textually)
```

```typescript
// good — aliased imports followed (rename tracks through import/export aliases to the declaration)
export function computeTotal(n: number): number { return n * 2; } // rename target (aliased below — server follows)
function local(): number { return 1; }
const ctLocal = local; // alias (rename of local rewrites declaration + this alias — binding followed)
console.log(computeTotal(21).toFixed(0), ctLocal().toFixed(0)); // 42 1 — aliases tracked (rename follows bindings across aliasing)
// bad — text-renaming aliased imports (alias missed — old name lingering at one use site, breaking silently)
// fix — server rename (aliases followed to declarations — complete rewrite, previewable per occurrence)
```

**Common confusion** — "rename updates comments/strings" — renames *bindings* (code occurrences); comments/strings need deliberate text passes (prose updated consciously — automatic prose rewriting would corrupt documentation examples). "preview is optional" — preview *is* the audit (occurrence list reviewed before applying — unexpected hits investigated, not blindly rewritten). "rename works without project context" — rename needs the *program* (cross-file occurrences require project-loaded tsserver — single-file mode renames locally only).

**Performance note** — rename queries cost indexed occurrence lookups (milliseconds — symbol tables maintained); application edits per occurrence (one atomic workspace edit — undoable as one operation). Text renames cost human verification per hit (unbounded — comments/strings/false-positives each judged manually).

**Mentor note** — rename one widely-used symbol live (preview occurrences, apply, tests green — impact analysis plus edit in under two minutes). Exercise: text-rename vs server-rename one shadowed binding (corruption vs precision — the demonstration that ends sed-renames permanently). Review gate: text-based renames of bindings fail review (F2 + preview, always).

### 2) **Quick fixes and refactors** (intention actions encoding conventions)

**Definition** — quick fixes (lightbulb actions on diagnostics: add-missing-import, fix-override-modifier, remove-unused) and refactors (extract-to-function/constant, convert-to-`import type`, move-to-file) encode team conventions as one-keystroke transformations — reviewed transformations (the action's output diffed like hand-written code) applied mechanically. Actions compose with review (apply → diff → adjust), never bypass it.

**What problem it solves / history** — repetitive mechanical edits (adding `override` to 40 members, converting 200 value-imports to `import type`, extracting 30 duplicated blocks) consumed review-trivial authoring time while inviting inconsistency (each hand-edit slightly different — 40 `override`s with 3 forgotten). Intention actions apply team conventions mechanically (one keystroke per site, identical output) — authors review diffs, actions do typing.

**Modern guidance** — as of TypeScript 5.9 era, apply quick fixes per diagnostic (lightbulb first — the checker's own suggestion encodes the convention); refactor via actions (extract/convert/move — diffed like hand-written code, never blind-applied); fix-all with preview (fix-all-*kind* across files — occurrence list reviewed before applying, like rename preview).

**Runnable example** — actions encoding conventions (good vs bad, `tsc --strict`):

```typescript
// good — convert-to-import-type action output (stated traffic — action applied the team convention mechanically)
export interface CfgA { host: string }
export function addrA(c: CfgA): string { return c.host.toUpperCase(); } // (imported via import type where consumed — action output shape)
// fix-all illustration (200 value-imported types → import type each — one action per file, diffed per application)
const ca: CfgA = { host: "h" };
console.log(addrA(ca)); // H — action output (convention applied mechanically — reviewed as diff, not authored)
// bad — hand-converting 200 imports (inconsistency per edit — 3 missed, 2 mis-edited, weeks of follow-ups)
// fix — fix-all with preview (occurrence list reviewed — mechanical application, human audit)
```

```typescript
// good — extract-to-function action output (duplicated block → named helper, call sites updated)
function areaC(r: number): number { return Math.PI * r ** 2; } // extracted (action created + replaced 3 call sites identically)
console.log(areaC(2).toFixed(2), areaC(3).toFixed(2)); // 12.57 28.27 — extraction uniform (parameters inferred, returns threaded)
// bad — hand-extracting per site (parameter lists drifting per copy — 3 extractions, 3 signatures, 1 bug)
// fix — extract action (uniform extraction — inferred identically, applied identically, diffed once)
```

```typescript
// good — add-missing-import action output (import inserted with correct path + kind — no manual path arithmetic)
export function helperD(s: string): string { return s.trim(); } // (imported elsewhere via action — path + type-kind correct)
// fix-all illustration (missing imports resolved per file — action computes paths, authors review diffs)
console.log(helperD("  x  ")); // x — action output (path arithmetic automated — reviewed, never hand-typed)
// bad — hand-typed imports (wrong paths, wrong kinds (value vs type), missing extensions — per-import defect surface)
// fix — quick-fix imports (checker-computed paths + kinds — authors review, actions type)
```

**Common confusion** — "actions replace review" — actions *produce diffs* (reviewed like hand-written code — output inspected, adjusted, committed); blind-applying actions (especially fix-all across files) ships mechanical errors at machine speed. "fix-all is always safe" — fix-all applies *one* transformation everywhere (safe for uniform conventions — `import type` conversion; unsafe for judgment calls — preview lists exist precisely for triage). "custom refactors aren't worth building" — team-specific code actions (framework idioms, migration patterns) pay off past dozens of applications — build at repetition thresholds, not before.

**Performance note** — actions execute in milliseconds (server-side transformations on indexed programs); hand-edits cost minutes per site (authoring + inconsistency risk); fix-all scales sub-linearly (one review pass for N applications — the economics that justify automation).

**Mentor note** — apply one fix-all live with preview open (occurrence list reviewed, applied, diff skimmed — mechanical application with human audit in under two minutes). Exercise: convert one repetitive-edit class to actions (fix-all + preview) and count consistency defects vs hand-editing baseline (zero vs several — automation dividend measured). Review gate: blind fix-all application (unpreviewed) fails review; hand-repetition of action-covered edits fails review.

### 3) **Organize-imports and sort discipline** (auto-ordered blocks, review-noise reduction)

**Definition** — organize-imports (server action sorting + merging + removing-unused imports per file) plus sort discipline (member ordering conventions — sorted object keys, sorted union members, sorted exports where teams adopt) eliminate *ordering* diffs from reviews (imports sorted identically everywhere — diffs show logic, never order). Formatting-adjacent automation with semantic awareness (unused removal needs binding resolution — text sorting can't).

**What problem it solves / history** — import-block churn (added imports appended wherever, unused imports lingering, duplicate paths accumulating — every PR touching imports produced ordering noise reviewers waded through) and key-order drift (object literals/union members ordered by accretion — diffs unreadable across refactors). Organize-on-save + sorted-conventions delete the entire class: files arrive ordered, reviews read logic.

**Modern guidance** — as of TypeScript 5.9 era, enable organize-imports on save (sorted + merged + unused-removed per file — zero manual import hygiene); sort where teams adopt (perfectionist/sort-* rules for keys/unions/exports — consistency over preference, configured once); never hand-order imports (automation owns order — human edits target logic, diffs prove it).

**Runnable example** — ordered blocks, clean diffs (good vs bad, `tsc --strict`):

```typescript
// good — organized import block (sorted, merged, unused-removed — automation output, review-clean)
function assertStrict(cond: unknown, msg: string): asserts cond { // local assert helper (stdlib-free — no @types/node needed here)
  if (!cond) throw new Error(msg);
}
export function check(n: number): string {
  assertStrict(n > 0, "positive");
  return "ok";
}
// (organize-imports output shape: sorted paths, merged duplicates, no unused — files arrive clean, diffs show logic)
console.log(check(1)); // ok — organized block (order automated — human edits target logic only)
// bad — hand-ordered imports (appended wherever, duplicates accumulating, unused lingering — ordering noise per PR)
// fix — organize-on-save (sorted + merged + cleaned per file — zero manual import hygiene, review-noise deleted)
```

```typescript
// good — sorted union members (canonical order — diffs readable across refactors)
// (sort-union-members convention: literals alphabetical — additions slot deterministically, never append-chaos)
type Sorted = "a" | "b" | "c"; // alphabetical (new member "aa" slots second — deterministic position, clean diff)
function isS(s: string): boolean { return (["a", "b", "c"] as const).includes(s as "a" | "b" | "c"); }
console.log(isS("b")); // true — sorted members (order conventional — refactors slot, never append)
// bad — accretion-ordered unions ("c" | "a" | "b" — history-ordered, diffs noisy per addition)
// fix — sort conventions (configured once — consistency over preference, diffs readable forever)
```

```typescript
// good — no unused imports (removed on save — dead references never accumulate)
// (organize-imports removes unused automatically — the import block always reflects actual usage)
export function used(x: number): number { return x; } // used below (survives organization — referenced imports kept)
console.log(used(1).toFixed(0)); // 1 — used imports kept (organization removes unused only — referenced imports untouched)
// bad — unused imports lingering (dead references accumulating — each a false lead for readers, a false hit for grep)
// fix — organize-on-save (unused removed per file — import blocks reflect usage exactly, always)
```

**Common confusion** — "organize-imports rewrites semantics" — reorders *statements* with side-effect awareness (bare side-effect imports keep position — order preserved where evaluation matters); pure reordering is semantics-preserving by construction. "sorted everything is obsessive" — sorted *imports/keys/unions* (lookup-heavy structures — consistency aids scanning); sorted *logic* (statements in execution order — never alphabetical) — sort lookup structures, never procedures. "organization replaces lint" — organization handles *order*; lint handles *correctness* (unused, kinds, cycles) — complementary automation (both on save + CI, neither substituted).

**Performance note** — organize-on-save costs milliseconds per file (server-side transform on indexed programs); sorted structures aid *human* lookup (binary-searchable visually — reviewer performance, not machine); CI check (`--check` mode) fails unordered files in seconds.

**Mentor note** — show one PR diff before/after organize-on-save (ordering noise vs logic-only — review burden made visible in one diff). Exercise: enable organize-on-save + sorted-keys team-wide for a week and count ordering comments in review (→ zero — automation dividend measured). Review gate: hand-ordered import blocks fail review (automation owns order).
