## 1.2. Rename refactorings and code actions

### 1) **Preview a semantic rename at the intended binding**

A symbol rename asks the language provider for edits associated with a selected binding. That is more targeted than replacing matching text, but its scope still depends on loaded projects and the provider. Review the proposed edits before applying them, especially at public APIs and protocol boundaries. An editor may group them into one undo operation; that is not a guarantee of an atomic change to every file or external consumer.

Use **TypeScript 7.0.2** and **Node.js 20.20.2**, reusing the complete project from [1.1](<./1.1. Navigation go to definition find references.md>). On the exported `compute` declaration, request a rename to `scale`. The native server returned these changes in the configured project:

- Change the function declaration in `core.mts` from compute to scale.
- Change the imported name in `app.mts` to `import { scale as double } from "./core.mjs"`.

The local alias `double` and its call remain unchanged. The unrelated local compute function and the string `"compute"` remain unchanged too. In a separate run starting from the original project, renaming the alias double to twice changed only its import alias and call; it did not rename the exported compute declaration. These are distinct operations despite their related references.

After either alternative rename, compile with `tsc -p tsconfig.json` and run `node dist/app.mjs`. The output remains `42 11 compute local`. The unopened outside file is outside this configured edit set, so inspect additional consumers separately. A string that names a route, serialized field or reflection key may also need a deliberate migration; the symbol rename does not establish that protocol's compatibility.

A text replacement is not inherently behavior-changing: changing two independent local names consistently can preserve their behavior. Its risk is that matching spelling does not identify which binding or protocol you intended to change. Likewise, named exports can be convenient without making default exports unrenameable. [VS Code's refactoring guide](https://code.visualstudio.com/docs/typescript/typescript-refactoring) documents the editor commands; their presentation and support depend on the selected integration.

### 2) **Distinguish a diagnostic, an offered action and an applied repair**

Quick fixes address particular diagnostics. Refactors restructure a selected expression or declaration. Source actions such as Organize Imports operate at a broader file scope. Availability depends on the provider, version, selection and configuration; a diagnostic does not guarantee an offered fix, and a fix-all request is not proof that every proposed edit matches the application's intent.

Add this intentionally incorrect file to the project's `files` list:

```typescript
// file: fix.mts
const item = { label: "ok" };
console.log(item.lable);
export {};
```

`tsc -p tsconfig.json --noEmit` rejects it with TS2551 and suggests the spelling `label`. The headless native 7.0.2 diagnostic request also reported TS2551. The code-action requests used in this verification returned no spelling fix for that selection. That is an observed limit of these requests, not proof that every editor integration lacks the action.

Repair the second line to `console.log(item.label);`, then compile and run `node dist/fix.mjs`; the output is `ok`. This repair was made explicitly, so it is not described as generated action output. When an editor offers an extraction, missing-import fix or type-import conversion, inspect its actual diff and test the affected contract. Import kind and module evaluation deserve particular attention; [the import-type owner](<../../../12 Modules Namespaces and Declaration Files/sections/1. ES Modules/1.2. import type and verbatimModuleSyntax erasable imports.md>) explains that behavior in full.

### 3) **Test import organization against module effects**

Add these three files to the same project and its `files` list. Start this exercise after repairing fix.mts, with the original navigation files restored if you want to repeat the rename alternatives independently.

```typescript
// file: register.mts
console.log("registered");
export const unused = 1;
```

```typescript
// file: values.mts
export const answer = 42;
```

```typescript
// file: imports.mts
import { unused } from "./register.mjs";
import { answer } from "./values.mjs";
console.log(answer);
```

Compile with `tsc -p tsconfig.json`, then run `node dist/imports.mjs`. The output is `registered` followed by `42`. Under this configuration, the unused value import remains in emitted code and evaluates the imported module. Lack of a local binding use is not proof that importing the module has no effect.

The native server's Organize Imports action removed that unused named import. After applying the returned edit and rebuilding, the output was only `42`: the registration module no longer ran. If that effect is required, express it explicitly:

```typescript
// replacement file: imports.mts
import "./register.mjs";
import { answer } from "./values.mjs";
console.log(answer);
```

The bare import states that module evaluation is intentional. In this fixture, organizing the repaired file retained that dependency and the rebuilt program again printed `registered` followed by `42`. Check ordering too when several modules have initialization dependencies; neither a formatter nor an “organize” label establishes arbitrary reordering safety.

Sorting unrelated structures needs its own reasoning. Object-property evaluation order can be observable, and overload declaration order can affect selection. Do not extend an import-order convention into a universal rule to sort object keys, union presentations, exports and executable statements. Keep formatting conventions in [2.2](<../2. Lint Format and Checks/2.2. Prettier dprint and formatting discipline.md>) and verify semantic transformations against the affected operation.

The verification applied actual native-server edits to fresh local files, then compiled and executed the results. Editor preview widgets, save triggers, extraction UI and grouped undo were not automated. Use editor-supported action settings only after testing their effects on representative files; a smaller or manually reviewed edit can be appropriate when an action is unavailable or too broad.

### 4) **Common confusion**

References can be related through an alias without every related spelling being renamed together. Selecting the exported declaration and selecting its local alias can produce different edit sets. An unchanged protocol string or external consumer still needs its own review.

An unused import binding can still cause module initialization. A source action that removes it can therefore change behavior even though the resulting program type-checks. An offered action is a proposed edit, not a correctness or compatibility certificate.

### 5) **Performance note**

Rename and code actions may load projects, resolve symbols and construct edits proportional to affected files and occurrences. Applying an edit and rerunning checks adds separate work. This example establishes edit contents and runtime effects, not fixed response times, sublinear scaling or a guaranteed productivity improvement. Measure the relevant operation if responsiveness is poor, and avoid using speed as a reason to skip reviewing semantic changes.

### 6) **Mentor note**

Ask the learner to predict the exported rename and alias rename separately, then compare the actual edits. Next, explain why deleting an unused import changed output and repair the dependency explicitly. Finish by distinguishing the spelling diagnostic from an unavailable action and from the manual repair. A strong answer identifies binding scope, protocol compatibility, module evaluation and the verification needed after a proposed edit.
