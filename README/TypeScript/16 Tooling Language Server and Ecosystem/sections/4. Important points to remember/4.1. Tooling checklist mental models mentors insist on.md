## 4.1. Tooling checklist — mental models mentors insist on

### 1) **Attach each conclusion to an operation and its inputs**

Before accepting “the tooling is green,” identify what ran. Name the executable/provider and version, selected files or artifact, configuration, document state and result. A compiler check, editor request, formatter operation and runtime test answer different questions. This checklist connects those questions to the worked owners; it does not repeat their fixtures or turn a printed success label into evidence.

| Review question | Useful evidence | Boundary to preserve |
|---|---|---|
| Where is this binding declared and used? | Actual definition/reference requests for the loaded project | Strings, unopened external consumers and unrelated same-name bindings need separate investigation. |
| What did a refactoring change? | Proposed edits, applied diff and subsequent relevant checks | A valid edit can still change public protocols or module initialization. |
| Is an inferred type or signature what the author claims? | Hover/query plus a targeted compiler relationship | Display can be abbreviated; a hint does not add a source contract. |
| Does a rule policy pass? | The actual configured lint command and named rule | Typed lint is separate from compiler acceptance and can overlap some diagnostics. |
| Is layout accepted? | Pinned formatter check over a known file set | A formatted program can still have type or behavior errors. |
| What reaches a package consumer? | Packed files, health-tool results, strict consumer checks and runtime tests | Profiles, entry points and supported versions bound the claim. |
| Why does the editor differ from a batch check? | Provider, project and buffer-content comparison | Unsaved text can correctly differ from the saved file. |
| Can the upgrade be restored? | Previous manifest/lock/source/configuration and a rehearsed artifact route | A version-string change alone may not restore all inputs. |

Use navigation to reach relevant code, then read the declaration and its surrounding behavior. Text search and directory browsing remain useful for protocols, configuration and discovering unfamiliar structure. There is no mandatory sequence that makes reading unnecessary or guarantees constant-time navigation.

### 2) **Inspect the behavior an automated edit can hide**

The [code-action fixture](<../1. Language Server in Practice/1.2. Rename refactorings and code actions.md>) compares exported and local-alias renames. It also applies actual import organization: removing an unused value import removes a registration effect, while an explicit side-effect import preserves it. The review question is therefore not only whether a tool offered the edit. Inspect the binding scope and the runtime dependency it changed.

The [typed-lint fixture](<../2. Lint Format and Checks/2.1. typescript-eslint rules and type-aware linting.md>) shows a floating call that compiles but fails lint. It also shows a Promise condition where both checks report a problem. Their jurisdictions are not disjoint. Awaiting or returning a Promise transfers failure through the surrounding operation; it does not prove an ultimate rejection policy. Inspect the relevant caller and handling path.

The [formatter fixture](<../2. Lint Format and Checks/2.2. Prettier dprint and formatting discipline.md>) runs dirty check → write → clean check and then proves that a formatted type error is still rejected by the compiler. When adding format-on-save or a hook, check the selected provider, config and staged-file behavior. The CLI evidence in that owner does not certify an unexecuted editor or hosted CI integration.

### 3) **Use failures to test whether gates protect their promises**

A gate is useful when the failure it is meant to catch actually fails. In the [package-health owner](<../2. Lint Format and Checks/2.3. publint attw and package health checks.md>), excluding declarations leaves the source build green while publint and strict consumers fail. The tested attw version prints that the package lacks types but exits 0. Check the result's meaning, not just its process status. Conversely, a wrong arithmetic implementation passes the compiler and both health tools but fails a runtime assertion.

For documentation, the [Twoslash fixture](<../3. Debugging and Ecosystem/3.2. Playground twoslash and documentation snippets.md>) asserts returned query text, checks a virtual import and proves an unexpected error fails. Expected-error and suppression options change that validation contract. A documentation build is not a runtime test, and an unprocessed query comment establishes no assertion.

For upgrades, the [version fixture](<../3. Debugging and Ecosystem/3.3. Version management and upgrade playbooks.md>) demonstrates a manifest/lock mismatch, a deliberate update and restoration of both inputs. Add the actual framework, editor, API-tool and consumer checks your application needs. The [native migration assessment](<../../../25 Update TypeScript 7.0/sections/5. Migration Assessment/5.1. Assess a complete native compiler migration.md>) develops those separate interfaces with an executable package exercise.

A short review exercise: a colleague says “references found no callers, lint passed after adding void, and attw exited 0, so the release is safe.” Identify the missing evidence. An adequate response asks about external/string consumers, the floating rule's ignoreVoid option and the task's actual rejection policy, then inspects packed declarations and supported consumers. It does not conclude that these tools are useless; it limits each result to the question it answered.

### 4) **Common confusion**

A tool's name is not evidence it ran. A source snippet that prints “lint passed” has only printed a string. Likewise, actual reference results do not prove every external consumer was loaded, and successful packaging checks do not prove API semantics. Prefer the smallest observation that directly tests the claimed behavior.

An apparent disagreement is not automatically a stale cache. The [server fixture](<../3. Debugging and Ecosystem/3.1. Debugging tsserver logs and responsiveness.md>) reports TS2322 for changed unsaved text while the saved program remains valid. Match inputs before changing configuration or deleting generated state.

### 5) **Performance note**

Navigation, linting, formatting, packing and server queries perform different work. Project loading and caches can change their cost; a batch compiler total is not an editor-response measurement. This checklist adds no executable hot path and establishes no speed ranking. When performance matters, measure the specific command or request with its file set, version and cold/warm state recorded.

### 6) **Mentor note**

Give the learner one claimed success from the table and ask for the command or request, selected inputs, observed result and one remaining limit. Then offer an intentional failure that should invalidate the claim. A strong answer chooses a relevant check and explains the causal result, rather than accumulating unrelated green commands or memorizing a fixed tool trio.
