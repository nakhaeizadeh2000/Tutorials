## 4.1. Tooling checklist — mental models mentors insist on

### 1) **Navigate before reading** (jumps, references, peek flows — comprehension per keystroke)

**Definition** — comprehension order: go-to-definition first (declaration located in one keystroke), references second (impact enumerated), peek third (context preserved), file-tree scanning never (unfamiliar-codebase tax eliminated). Navigation-first comprehension answers per question in seconds (current answers, indexed tables) versus minutes per file-scan (stale maps, hopeful grep).

**What problem it solves / history** — scan-first comprehension (directories top-down per question — O(files) with stale mental maps) taxed onboarding, incident response, and cross-team reviews heaviest (unfamiliar code × time pressure × wrong guesses compounding). Navigation-first inverts the economics: jumps (O(1), current), references (impact enumerated), peek (context preserved) — questions answered in seconds with evidence.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), navigate before reading (jump → references → peek → scan, in that order, always); audit before editing (references per rename/delete/change — blast radius enumerated first); search-approximate for vague names (fuzzy symbol search — partial memory locating exactly). See [1.1. Navigation](<../1. Language Server in Practice/1.1. Navigation go to definition find references.md>).

**Runnable example** — navigation vocabulary (good vs bad, `tsc --strict`):

```typescript
// good — jump-targetable declarations (named exports — navigation O(1), always current)
export interface Invoice { id: string }
export function total(i: Invoice): string { return i.id.toUpperCase(); } // jump lands HERE (owned source — logic readable)
const inv: Invoice = { id: "x" };
console.log(total(inv)); // X — navigate-first (definition in one keystroke — comprehension per jump, not per scan)
// bad — scan-first comprehension (directories top-down per question — O(files) with stale mental maps)
// fix — jump → references → peek → scan (ordered navigation — questions answered in seconds with evidence)
```

```typescript
// good — reference-audited edits (impact enumerated before editing — renames/deletions/changes proven safe)
export function audited(n: number): number { return n; } // audited (references: declaration + call below — complete)
console.log(audited(1).toFixed(0)); // 1 — edit-audited (blast radius enumerated — renames/deletions/changes safe)
// bad — editing without reference audits (blast radius guessed — renames missing sites, deletions breaking hidden consumers)
// fix — references per edit (count + skim — impact enumerated first, edits applied second, tests green third)
```

```typescript
// good — search-approximated location (fuzzy names locating exactly — partial memory sufficient)
export function fetchCustomerById(id: string): string { return `c:${id}`; } // token-rich name (fuzzy-findable per token)
console.log(fetchCustomerById("u").toUpperCase()); // C:U — searchable naming (conventions serving tooling — findable vaguely)
// bad — file-tree spelunking for guessed filenames (O(directories) per question, wrong guesses compounding)
// fix — symbol search (approximate names locating exactly — unfamiliar code navigable in seconds, not quarters)
```

**Common confusion** — "navigation replaces reading" — navigation *locates* (declarations/uses in seconds); reading *comprehends* (logic understood per jump target) — locate-then-read, never scan-instead. "references replace tests" — references enumerate *impact* (what changes); tests verify *behavior* (what breaks) — audit then test, in that order. "search replaces structure" — search *locates known-approximately*; structure *discovers unknown-unknowns* — both needed (search what you can name, browse what you can't).

**Performance note** — navigation queries cost indexed lookups (milliseconds); file scans cost human minutes per question (unbounded, compounding per unfamiliar file). Navigation-first comprehension is the highest-ROI editor habit by time saved.

**Mentor note** — time one "find the definition" by scan vs jump (minutes vs seconds — tooling dividend measured once, believed forever). Exercise: answer five codebase questions by navigation only (no file-tree, no grep — vocabulary under test). Review gate: "I couldn't find X" reports fail process review (jump → references → peek → scan, in that order).

### 2) **Lint what compilers can't** (type-aware rules, import discipline, boundary conventions)

**Definition** — lint jurisdiction: checker-*backed* rules compilers don't run (floating promises, unnecessary conditions, theater casts — legal-but-dangerous flagged), import/style discipline (kinds, order, barrel hygiene — conventions enforced), boundary conventions (validation, parsing, error budgets — team rules automated). Compilers check *types*; linters check *everything types miss* (suspicion, convention, boundary).

**What problem it solves / history** — unlinted legal-but-dangerous code (floating promises compiling, dead conditions maintained, theater casts laundering — each legal, each incident-adjacent) passed tsc green into production incidents. Type-aware lint converts checker facts into findings (legal-but-dangerous flagged with fix sites) — coverage compilers structurally cannot provide.

**Modern guidance** — as of TypeScript 5.9 era, lint type-aware rules (five high-yield rules per 2.1 promise 2 — enforced as errors, triaged quarterly); lint import/style discipline (kinds, order, barrels — conventions automated, reviews logic-only); lint boundary conventions (validation/parsing/budgets per team rules — automation where reviewers look). See [2.1. typescript-eslint](<../2. Lint Format and Checks/2.1. typescript-eslint rules and type-aware linting.md>).

**Runnable example** — lint jurisdiction (good vs bad, `tsc --strict`):

```typescript
// good — awaited promises (no-floating-promises satisfied — rejections handled, never floating)
async function load2(id: string): Promise<string> { return `d:${id}`; }
async function use2(): Promise<string> {
  return load2("a"); // returned (handled by caller — lint satisfied via return-chain, crash class deleted)
}
console.log("handled"); // rule satisfied (rejections flow to callers — local handling, never floating)
// bad — load2("a"); floating (legal TypeScript — tsc green, process crash in production — lint jurisdiction exactly)
// fix — no-floating-promises as error (legal-but-dangerous flagged — checker-backed findings compilers never run)
```

```typescript
// good — necessary conditions only (no-unnecessary-condition satisfied — branches provably live)
function label2(s: string | null): string {
  return s === null ? "none" : s.toUpperCase(); // necessary (union distinguished — condition proves per branch)
}
console.log(label2(null), label2("a")); // none A — live conditions (each branch reachable — rule silent correctly)
// bad — if (typeof "x" === "string") branches (provably-true conditions — dead logic maintained, readers confused)
// fix — no-unnecessary-condition (dead branches flagged — provable code deleted, live code kept)
```

```typescript
// good — kind-stated imports (consistent-type-imports satisfied — traffic honest per line)
export interface K2 { k: string } // (imported via import type where consumed — lint enforced, bundlers unburdened)
const k2: K2 = { k: "v" };
console.log(k2.k.toUpperCase()); // V — kind-stated (lint jurisdiction: conventions compilers never check)
// bad — value-imported types (bundler weight + elision roulette — legal TypeScript, toolchain-divergent emit)
// fix — consistent-type-imports (traffic stated — lint covering what compilers structurally cannot)
```

**Common confusion** — "lint duplicates tsc" — lint covers *legal-but-dangerous* (floating, dead, theater, undisciplined — compiling cleanly, incident-adjacent); tsc covers *violations* (assignability, arity, exhaustiveness) — jurisdictions disjoint by construction. "type-aware lint is slow" — projectService incrementalizes (seconds post-warmup — measured per repo, not assumed). "warnings suffice" — warnings *accumulate* (unread backlogs); errors *block* (fixed or reason-disabled per line).

**Performance note** — lint costs seconds per run (incrementalized); findings prevent incidents (floating crashes, dead maintenance, theater laundering — unbounded upside per rule). Type-aware lint is the highest-ROI automation past the compiler itself.

**Mentor note** — enable the five high-yield rules on one package and triage every finding (incident-preventing vs noise — per-rule evidence in one afternoon). Exercise: write one floating promise and watch the rule flag it (checker-backed finding demonstrated, not described). Review gate: disabled type-aware rules require recorded reason + metric.

### 3) **Verify packages like consumers** (publint + attw + smoke — release proof)

**Definition** — release verification from consumer perspectives: `publint` (packaging coherence — maps/conditions/files), `attw` (resolution matrix — per subpath per importer kind), per-subpath strict smoke imports (consumer-equivalent typecheck). Green across all three proves consumer outcomes (typed, resolvable, checkable); any red blocks publish (packaging bugs fail like type errors).

**What problem it solves / history** — producer-green releases (tsc passing on sources, tests passing on behavior) breaking consumers (untyped subpaths → `any`-infection; kind-specific resolution → load crashes; stale declarations → fulfillment gaps) — verification from the wrong perspective (producer, not consumer). Consumer-equivalent gates verify *as dependents resolve* (tarball matrix, strict smokes) — producer green *plus* consumer green before publish.

**Modern guidance** — as of TypeScript 5.9 era, gate publint + attw + smoke in release CI (blocking, ordered coherence→resolution→consumption); fix per failing gate (maps → 12/3.3 wiring; conditions → per kind; smoke → declarations per subpath); version gates with incident history (new failure modes append gates — 11's stamp playbook applied to releases). See [2.3. publint attw](<../2. Lint Format and Checks/2.3. publint attw and package health checks.md>).

**Runnable example** — consumer-equivalent proof (good vs bad, `tsc --strict`):

```typescript
// good — mapped + resolved + smoked surface (consumer outcomes proven — release ships on proof)
export function shipped2(): string { return "s"; } // gated surface (publint coherent + attw green + smoke strict)
console.log(shipped2()); // s — proof composed (packaging × resolution × consumption — no single gap remaining)
// bad — tsc-only releases (programs green, packaging/resolution unchecked — consumer incidents per un-gated class)
// fix — trio gates (independent failure modes covered jointly — escaping requires defeating all three simultaneously)
```

```typescript
// good — per-subpath smoke (every public path imported under strict — untyped publics impossible)
export function sub2(): string { return "sub"; } // subpath export (types condition present — attw checks per path, not just root)
console.log(sub2()); // sub — subpath matrix (coverage complete — root-green/subpath-red classes eliminated)
// bad — root-only resolution testing (subpaths resolving any/fallback — untyped publics shipping behind green root checks)
// fix — smoke matrix (strict imports per public path per release — minutes per release, zero consumer infections)
```

```typescript
// good — gates versioned with incident history (new failure modes append gates — coverage compounding per incident)
export const gates2 = ["publint", "attw", "smoke"] as const; // gate list (versioned — new classes append, never replace)
console.log(gates2.join("+")); // publint+attw+smoke — composed proof (coverage compounding per incident class learned)
// bad — frozen gate sets (checklists never growing — novel failure modes shipping through gates designed for old ones)
// fix — incident-driven gate growth (each packaging incident appends a gate/check — 11's stamp playbook applied to releases)
```

**Common confusion** — "gates slow releases" — seconds combined (pack + matrix + smoke, parallelizable) vs patch cycles (days + trust each). "gates duplicate each other" — coherence (maps), resolution (per-kind outcomes), consumption (strict typecheck) — independent failure modes (each gate catches classes others miss by construction). "small packages skip gates" — gates scale with zero human steps (automation per release); hope scales with forgetting (incidents per un-gated class, regardless of size).

**Performance note** — trio runtime seconds-to-minute (parallelizable); incident cost days + consumer trust per escaped class. Composed gates are the cheapest release insurance in typed-package practice.

**Mentor note** — break one gate deliberately (unmap a subpath) and watch the trio locate it (publint flags coherence, attw flags cells, smoke fails imports — layered location vs single-point vagueness). Exercise: audit the last three releases against all three gates retroactively (misses found = gates' ROI, receipt included). Culture pattern: same as 11's enum stamp (measured behavior, celebrated prevention).

### 4) **Debug tooling with tooling** (logs, traces, playgrounds — evidence per symptom)

**Definition** — tooling failures diagnosed with tooling: tsserver logs per editor symptom (request/response/error shapes — named failure classes), `traceResolution`/`extendedDiagnostics` per build question (candidates/check-leaders listed), playground links per behavior question (isolated reproductions with pinned versions). Evidence per symptom class — folklore retired permanently.

**What problem it solves / history** — tooling folklore ("restart the editor", "delete node_modules", "TypeScript is slow" — rituals without diagnosis, issues recurring per project shape) wasted hours per incident across teams (unlearned lessons, repeated rituals). Evidence-based debugging (logs per symptom, traces per question, reproductions per report) resolves per class with located fixes — folklore replaced by instrumentation, permanently.

**Modern guidance** — as of TypeScript 5.9 era, log editor symptoms (TSServer channel per misbehavior — request/response/error shapes read first); trace build questions (`traceResolution` per resolution, `extendedDiagnostics` per performance); reproduce behavior questions (playground links with pinned versions — evidence linked, not described). See [3.1. Debugging tsserver](<../3. Debugging and Ecosystem/3.1. Debugging tsserver logs and responsiveness.md>) + [3.2. Playground twoslash](<../3. Debugging and Ecosystem/3.2. Playground twoslash and documentation snippets.md>).

**Runnable example** — evidence per symptom (good vs bad, `tsc --strict`):

```typescript
// good — version-pinned tooling (log-first question answered structurally — settings, not folklore)
export function pinned2(): string { return "workspace-tsdk"; } // stated (settings.json documents — no per-machine drift)
console.log(pinned2()); // workspace-tsdk-pinned — version question answered (mismatch class deleted structurally)
// bad — "restart the editor" as first resort (ritual without diagnosis — issues recurring per project shape, unlearned)
// fix — logs first (request/response/error shapes per symptom — named failure classes, located fixes)
```

```typescript
// good — traced resolution (candidates listed per import — agreement proof, not hope)
export function traced(): string { return "paired"; } // (traceResolution output shape: paired candidates per import — verified per setup)
console.log(traced()); // paired — resolution traced (candidates visible — mismatches located, not guessed)
// bad — "works on my machine" resolution reports (unpaired settings diverging per environment — evidence absent, folklore present)
// fix — trace per question (candidates listed — resolution proved, not hoped, per setup)
```

```typescript
// good — playground-linked behavior questions (isolated reproductions with pinned versions — evidence linked)
// (playground shape: minimal code + version param + expected-vs-actual — reproduction complete in one URL)
export function linked(): string { return "reproduced"; }
console.log(linked()); // reproduced — evidence linked (behavior questions answered with URLs, never prose-only)
// bad — prose-only behavior reports ("X emits Y, I think" — folklore per recall, unverifiable per report)
// fix — playground links (evidence linked — folklore retired permanently, verification in seconds)
```

**Common confusion** — "debugging tooling wastes feature time" — undiagnosed tooling issues tax *every* subsequent hour (slow editors, phantom errors, broken builds — recurring drag vs one-time diagnosis). "logs are for extension authors" — logs are for *anyone* debugging editor behavior (thirty minutes of orientation pays permanent dividends). "reproductions are overhead" — reproductions *are* the diagnosis (minimal cases isolating causes — without them, fixes address symptoms).

**Performance note** — log/trace/reproduction costs minutes per incident (bounded, one-time); folklore costs hours per incident across teams (unbounded, recurring). Evidence-based debugging is pure economics favoring instrumentation heavily.

**Mentor note** — resolve one tooling issue three ways (restart-ritual vs log-diagnosis vs playground-reproduction) and compare time-to-cause (hours vs minutes vs seconds — economics demonstrated, not asserted). Exercise: document one debugging run per class (logs/traces/reproductions — team runbooks growing per incident). Review gate: "tooling is broken" tickets without evidence fail process review (logs/traces/links first, always).
