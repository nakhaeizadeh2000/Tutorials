## 6.1. Common interview QA — tooling, language server and ecosystem

### 1) **How do compiler commands and editor queries differ?**

A compiler command checks the configured program and may emit artifacts. A language server responds to operations such as diagnostics, hover, references or rename while maintaining document/project state. The distinction is the interface and work requested, not a guarantee that every batch run discards all prior information or every query is a cheap table lookup.

For native TypeScript 7.0.2, the same launcher can start CLI compilation or the LSP service with different arguments. Historical Node tsserver uses a different protocol. A tool importing the older JavaScript compiler API is another interface. Name the actual provider and version before asserting that the editor, command line and lint process use the same implementation or program.

Follow-up: can an editor correctly report an error when tsc passes? Yes: the [server fixture](<../3. Debugging and Ecosystem/3.1. Debugging tsserver logs and responsiveness.md>) changes an unsaved number initializer to a string, obtains native TS2322 and leaves disk compilation green. Compare content, project/options and document state first. Compilation also does not demonstrate a rename or hover operation; [navigation](<../1. Language Server in Practice/1.1. Navigation go to definition find references.md>) supplies actual requests.

### 2) **What does typed lint add, and what does a pass mean?**

Typed rules use available type information to apply configured policies. Examples include no-floating-promises, no-misused-promises and no-unnecessary-condition. A core syntax rule such as no-await-in-loop has a different information requirement. Do not classify a rule as type-aware merely because it reports a TypeScript file.

The [typed-lint project](<../2. Lint Format and Checks/2.1. typescript-eslint rules and type-aware linting.md>) contains a floating call that compiles but fails lint, and a Promise condition where diagnostics overlap. Compiler and lint coverage are not disjoint. The rule configuration, selected files and parser/project setup bound a lint result.

Follow-up: does void handle a rejected Promise? No. It can satisfy the default floating-rule option while installing no rejection handler. Await can throw a rejection into its surrounding operation, and returning a Promise transfers responsibility to the caller. Explain who owns completion and failure before calling the task handled. The [pitfalls fixture](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by tooling misunderstandings.md>) also shows a deliberate batch await that still triggers the core loop rule.

### 3) **Why check a tarball when the source already compiles?**

A source check does not establish which files are packed or which entry point a consumer resolves. publint reports supported packaging problems; attw statically analyzes supported type-resolution/module-format cases. Inspect their selected inputs, profiles and results alongside actual consumer compiler/runtime checks. Their coverage can overlap and is not exhaustive.

The [health-check fixture](<../2. Lint Format and Checks/2.3. publint attw and package health checks.md>) provides two useful contrasts. Omitting declarations leaves source checking green but breaks strict installed consumers; the tested attw version prints an untyped result and exits 0. A subtraction implementation with a valid numeric signature instead passes both health tools and the compiler, but fails the addition behavior assertion.

Follow-up: does every missing types condition produce any? No. Adjacent declarations may resolve through extension substitution. A blocked subpath, absent declaration and declaration that lies about runtime behavior are separate mechanisms. Use the [publishing owner](<../../../12 Modules Namespaces and Declaration Files/sections/3. Declaration Files in Practice/3.3. Publishing types exports map and typesVersions.md>) to inspect the resolved path and packed contract.

### 4) **How would you investigate slow or inconsistent editor behavior?**

Name a reproducible operation and record provider/version, relevant source state and project membership. Compare a batch check when it tests a useful hypothesis, but retain request-specific evidence for an editor problem. Native LSP, legacy tsserver and client rendering have different diagnostic paths. A restart can test whether process state matters; it does not identify corrupted caches by itself.

Extended diagnostics report aggregate compiler work, not a ranked list of slow files. If a project appears unexpectedly large, inspect its effective config and file list. If a feature is slow, use appropriate request timing or profiling for that provider, then change one relevant condition and repeat. The [diagnosis owner](<../3. Debugging and Ecosystem/3.1. Debugging tsserver logs and responsiveness.md>) gives the concrete config and document-state checks.

Follow-up: is disabling a feature or splitting a project always wrong or always right? Neither. Explain the observed cost, required capability and trade-off. An immediate workaround and a longer investigation can both be justified. There is no universal file threshold or fixed sequence of watcher knobs that guarantees a repair.

### 5) **How would you upgrade a compiler without losing compatibility evidence?**

Inventory batch checking, emit/build/watch, editor features, API tools and supported consumers. Read the release changes, run the relevant old/new checks and classify differences before weakening a contract. Choose reviewable stages from the dependency graph and deployment constraints; leaf-first order is useful in some graphs, not a universal migration law.

The [version exercise](<../3. Debugging and Ecosystem/3.3. Version management and upgrade playbooks.md>) upgrades 6.0.3 to 7.0.2, observes manifest/lock mismatch and restores both inputs. An application's rollback may also require source, configuration and artifacts. A library can pin its own development compiler while testing published declarations against consumer versions. A TypeScript peer is appropriate for an actual host/API relationship, not every typed library.

Follow-up: must every tool switch to native TypeScript at once? No. A compatible API package can remain for tools that need it while native checking and emission are verified separately. The [complete native migration assessment](<../../../25 Update TypeScript 7.0/sections/5. Migration Assessment/5.1. Assess a complete native compiler migration.md>) provides executable evidence for those interfaces. Its small package does not certify a framework or every editor integration.

### 6) **Common confusion**

A good interview answer explains a mechanism and an observation that could disprove it. Memorizing a preferred sequence, promising a speedup or listing tool names is weaker evidence. A successful process status is also not the same as the desired contract: the untyped attw result is a concrete counterexample.

Checking, emission and execution remain distinct. Running TypeScript source depends on the selected runtime and supported syntax; do not infer Node source-execution support from a compiler or server version. Use the [execution-path owner](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.2. Executing TypeScript tsc plus node tsx ts-node and native Node stripping.md>) for that environment.

### 7) **Performance note**

These questions have no direct runtime performance effect. Their referenced operations can load programs, analyze types, pack artifacts or execute consumers. Compare the specific operation and environment before making a latency or cost claim. No new benchmark or tool execution is implied by this question set; the linked owners retain the actual fixtures and their limits.

### 8) **Mentor note**

Choose one follow-up and let the learner predict a result before inspecting the worked owner. Evaluate whether they identify the inputs, mechanism, appropriate check and remaining limit. For deeper practice, ask them to design a failure that stays green at one layer and fails at another, then explain why. The missing-declaration tarball and unsaved-buffer case supply two explained solutions without requiring every candidate to recite a fixed workflow.
