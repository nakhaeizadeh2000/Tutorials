## 6.1. Common interview QA — tooling, language server and ecosystem

### 1) **What does the language server do that `tsc` doesn't — and when do you run each?** (interactive queries vs batch verification)

**Definition** — `tsc` batch-verifies programs (full check, emit, exit code — CI correctness); tsserver *interactively* queries them (go-to-definition, references, hovers, renames, quick fixes, inlay hints — editor-time comprehension with incremental programs). Same compiler core, different interfaces: batch (stateless runs) vs interactive (stateful sessions with navigation/refactor/code-action APIs).

**What problem it solves / history** — interviewers ask this to test tooling literacy beyond "both check types": candidates who distinguish *interfaces* (batch verification vs interactive queries) route work correctly (CI runs tsc; editors host tsserver; scripts choose per need); candidates equating them misroute (tsc-as-language-server latency, tsserver-as-CI fragility).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), answer interface-first (batch vs interactive), use-second (CI → tsc; editing → tsserver; one-off scripts → tsc --noEmit or transpiler), debug-third (build failures → tsc output; editor weirdness → tsserver logs). Full treatment in [1.1. Navigation](<../1. Language Server in Practice/1.1. Navigation go to definition find references.md>) + [3.1. Debugging tsserver](<../3. Debugging and Ecosystem/3.1. Debugging tsserver logs and responsiveness.md>).

**Runnable example** — interfaces distinguished (good vs bad, `tsc --strict`):

```typescript
// good — batch verification shape (tsc territory: full check, exit code, CI correctness)
export function checked(n: number): number { return n; } // tsc verifies (assignability, arity, exhaustiveness — batch)
// (CI shape: npx tsc --noEmit (exit 0/1 — correctness gate, stateless run, no interaction)
// fix — CI runs tsc (batch verification — stateless, reproducible, gate-blocking)
console.log(checked(1).toFixed(0)); // 1 — batch-verified (correctness proven per run, no editor involved)
// bad — tsserver as CI (editor sessions in pipelines — stateful, interactive APIs misused as batch, fragility without benefit)
// fix — interfaces matched to needs (CI → tsc batch; editing → tsserver sessions; scripts → per need)
```

```typescript
// good — interactive queries (tsserver territory: navigation/refactors/actions — editor-time comprehension)
export function queried(s: string): string { return s.trim(); } // (go-to-definition lands HERE from call sites — interactive query)
// (editor shape: hover queried (signature inline), references listed (impact enumerated), rename applied (occurrences rewritten))
// fix — editors host tsserver (interactive sessions — comprehension per keystroke, never batch runs)
console.log(queried("  x  ")); // x — interactively navigable (queries answered in milliseconds, sessions stateful)
// bad — tsc executions per navigation question (full-program runs per jump — seconds per question, stateless waste)
// fix — tsserver sessions (incremental programs — queries answered from maintained state, not recomputed)
```

```typescript
// good — one-off scripts (tsc --noEmit for checking, transpilers for running — per-need tool choice)
export function script(n: number): string { return `#${n}`; } // (script shape: node --experimental-strip-types runs directly (no build step for scripts)
// fix — scripts per need (check via tsc --noEmit; run via stripping/transpiler — interfaces matched, never conflated)
console.log(script(7)); // #7 — script tooling (check + run composed per need — batch and interactive both wrong here)
// bad — full tsc builds for script checks (emit + programs for one-off verification — heavyweight habit, slow feedback)
// fix — tsc --noEmit (checking without emit — script-speed verification, batch-correct)
```

**Common confusion** — "tsserver is a different checker" — same core (tsserver *wraps* tsc programs with interactive APIs — checking identical, interfaces differing). "editors need tsc installed separately" — editors bundle *or* inherit workspace tsc (typescript.tsdk pinning decides — mismatch classes per 3.1 promise 3). "one tool suffices" — batch (CI correctness), interactive (editor comprehension), transpile (script speed) — three needs, three interfaces, one core.

**Performance note** — tsc batch costs full checks per run (seconds-to-minutes — CI-scheduled); tsserver amortizes (incremental programs — queries in milliseconds post-warmup); transpilers cost milliseconds per file (no checking — speed for scripts). Interfaces matched to needs optimize each axis independently.

**Mentor note** — strong answers lead with interfaces (batch vs interactive) unprompted — probe with "CI uses which?" (tsc) and "editor weirdness debugged where?" (tsserver logs) when candidates stop at "both check types." Hiring signal: interface-matched tooling predicts operational judgment.

### 2) **Which typescript-eslint rules actually need type information — and why are they worth the cost?** (checker-backed findings)

**Definition** — type-aware rules (needing checker facts): `no-floating-promises` (un-awaited rejections), `no-misused-promises` (async in boolean/void positions), `no-unnecessary-condition` (provably dead/alive branches), `no-unnecessary-type-assertion` (theater casts), `await-thenable`/`require-await` (async shape discipline). Worth the cost (program load + type queries per linted file, incrementalized via projectService) because each maps to a production incident class plain ESLint structurally cannot express.

**What problem it solves / history** — syntax-only linting (plain ESLint — un-awaited calls parsing identically awaited-or-not) passed floating promises, dead conditions, and theater casts green into production incidents. Type-aware rules convert checker facts into findings (legal-but-dangerous flagged with fix sites) — coverage compilers structurally cannot provide (tsc errors on violations, never on legal-but-dangerous patterns).

**Modern guidance** — as of TypeScript 5.9 era, answer rules-first (five high-yield rules named with incident classes each), cost-second (projectService incrementalizes — seconds post-warmup, measured per repo), triage-third (per-rule evidence quarterly — disabling zero-yield rules, keeping incident-preventing ones). Full treatment in [2.1. typescript-eslint](<../2. Lint Format and Checks/2.1. typescript-eslint rules and type-aware linting.md>).

**Runnable example** — checker-backed findings (good vs bad, `tsc --strict`):

```typescript
// good — awaited promises (no-floating-promises satisfied — rejections handled, never floating)
async function load3(id: string): Promise<string> { return `d:${id}`; }
async function use3(): Promise<string> {
  return load3("a"); // returned (handled by caller — lint satisfied via return-chain, crash class deleted)
}
console.log("handled"); // rule satisfied (rejections flow to callers — local handling, never floating)
// bad — load3("a"); floating (legal TypeScript — tsc green, process crash in production — lint jurisdiction exactly)
// fix — no-floating-promises as error (legal-but-dangerous flagged — checker-backed findings compilers never run)
```

```typescript
// good — necessary conditions only (no-unnecessary-condition satisfied — branches provably live)
function label3(s: string | null): string {
  return s === null ? "none" : s.toUpperCase(); // necessary (union distinguished — condition proves per branch)
}
console.log(label3(null), label3("a")); // none A — live conditions (each branch reachable — rule silent correctly)
// bad — if (typeof "x" === "string") branches (provably-true conditions — dead logic maintained, readers confused)
// fix — no-unnecessary-condition (dead branches flagged — provable code deleted, live code kept)
```

```typescript
// good — narrowing without theater (no-unnecessary-type-assertion satisfied — casts only where narrowing can't reach)
function narrow3(x: unknown): string {
  if (typeof x !== "string") throw new Error("want-string"); // narrowed (assertion-free — predicate proves)
  return x.toUpperCase(); // narrowed string (no cast needed — rule would flag `x as string` here as theater)
}
console.log(narrow3("hi")); // HI — theater-free assertions (casts only where narrowing can't reach — evidenced per cast)
// bad — (x as string).toUpperCase() post-narrowing (theater cast — rule flags: assertion narrowing nothing, laundering risk)
// fix — no-unnecessary-type-assertion as error (theater casts deleted — remaining casts evidenced per site)
```

**Common confusion** — "type-aware lint duplicates tsc" — tsc errors on *violations* (assignability, arity); lint flags *legal-but-dangerous* patterns (floating, dead, theater) — disjoint jurisdictions by construction. "projectService setup isn't worth it" — setup once (minutes), findings per lint run forever (incident prevention per rule) — cost/benefit overwhelmingly positive past small repos. "warnings suffice for lint" — warnings *accumulate* (unread backlogs); errors *block* (fixed or reason-disabled per line).

**Performance note** — type-aware rules cost program load + type queries per linted file (incremental via projectService — seconds, not minutes); findings prevent incidents (floating crashes, dead maintenance, theater laundering — unbounded upside per rule).

**Mentor note** — ask "which rules need the checker?" before "which rules do you enable?" (jurisdiction first — syntax vs checker-backed rules distinguished structurally). Follow-up: "why pay the cost?" (incident class per rule — floating/dead/theater mapped to production). Hiring signal: jurisdiction-aware lint answers predict operational judgment.

### 3) **What do publint and attw check that `tsc` can't — and when do they run?** (packaging + resolution)

**Definition** — `publint`: packaging coherence (exports/types/files agreement — maps present, conditions aligned, outputs included); `attw`: consumer-equivalent resolution (per subpath per importer kind — Node-ESM/CJS/bundler resolving typed); `tsc`: program correctness (types/assignability within the package). Three disjoint jurisdictions (packaging vs resolution vs programs) run as composed release gates (blocking, ordered coherence→resolution→consumption).

**What problem it solves / history** — producer-green releases (tsc passing on sources) breaking consumers (untyped subpaths → `any`-infection; kind-specific resolution → load crashes) — verification from the wrong perspective (producer, not consumer). `publint` + `attw` verify *as dependents resolve* (tarball matrix, strict smokes) — consumer-equivalent proof pre-publish, not post-ticket.

**Modern guidance** — as of TypeScript 5.9 era, answer jurisdiction-first (packaging vs resolution vs programs — disjoint by construction), run-second (release CI, blocking, ordered), fix-third (maps → 12/3.3 wiring; conditions → per kind; smoke → declarations per subpath). Full treatment in [2.3. publint attw](<../2. Lint Format and Checks/2.3. publint attw and package health checks.md>).

**Runnable example** — three jurisdictions (good vs bad, `tsc --strict`):

```typescript
// good — mapped surface (publint-coherent — exports + types + files agreeing per subpath)
export function mapped(): string { return "m"; } // gated surface (maps coherent — consumer outcomes proven pre-publish)
console.log(mapped()); // m — coherence proven (packaging verified like code, not hoped)
// bad — tsc-only releases (programs green, packaging/resolution unchecked — consumer incidents per un-gated class)
// fix — trio gates (independent failure modes covered jointly — escaping requires defeating all three simultaneously)
```

```typescript
// good — kind-resolved surface (attw-green — per subpath per importer kind resolving typed)
export function kinded(): string { return "k"; } // resolved surface (matrix green — Node-ESM/CJS/bundler agreeing)
console.log(kinded()); // k — resolution proven (consumer-equivalent verification — behavioral, not structural)
// bad — root-only resolution testing (subpaths resolving any/fallback — untyped publics shipping behind green root checks)
// fix — attw matrix (per subpath × per kind — kind-specific failures surface pre-publish, not per-consumer post-release)
```

```typescript
// good — smoked surface (strict imports per public path — consumer-equivalent typecheck per subpath)
export function smoked(): string { return "s"; } // smoked surface (strict smoke per path — untyped publics impossible)
console.log(smoked()); // s — consumption proven (subpath matrix — minutes per release, zero consumer infections)
// bad — untested subpaths (root green, subpaths any — coverage theater with a root-shaped hole)
// fix — smoke matrix (strict imports per public path per release — coverage complete across paths AND kinds)
```

**Common confusion** — "publint duplicates tsc" — publint checks *packaging* (maps/conditions/files coherence); tsc checks *programs* (types/assignability) — disjoint jurisdictions (both blocking, neither substituted). "attw duplicates publint" — attw checks *resolution outcomes* (per subpath per kind, actually importing); publint checks *map coherence* (structurally present) — behavioral vs structural verification differ. "gates slow releases" — seconds combined (parallelizable) vs patch cycles (days + trust each) — cheapest release insurance available.

**Performance note** — trio runtime seconds-to-minute (parallelizable); incident cost days + consumer trust per escaped class. Composed gates are the cheapest release insurance in typed-package practice.

**Mentor note** — ask "what does each gate catch the others miss?" (coherence vs resolution vs consumption — disjoint jurisdictions stated per gate). Follow-up: "when do gates run?" (release CI, blocking, ordered — proof before publish, every release). Hiring signal: jurisdiction-aware gate answers predict stewardship.

### 4) **How do you debug a slow or broken tsserver — in what order?** (logs → loading → tuning)

**Definition** — triage order: symptom logs first (TSServer channel — request/response/error shapes naming failure classes), project loading second (version → extends → caches → boundaries — setup failures separated from code failures), responsiveness tuning third (program size → watch load → plugins → depth/navigation knobs — metrics per step, knobs per cause). Evidence per step, folklore never.

**What problem it solves / history** — ritual debugging (restarts, reinstalls, setting-toggles without evidence — issues recurring per project shape, unlearned lessons) wasted hours per incident across teams. Ordered triage (logs → loading → tuning) locates causes in under 30 minutes typical — named failure classes with located fixes per step, documented per incident.

**Modern guidance** — as of TypeScript 5.9 era, answer order-first (logs → loading → tuning — sequence matters because causes mask each other), evidence-second (log excerpts, trace outputs, metric readings per step), folklore-never (no restarts/reinstalls/toggles without diagnosis). Full treatment in [3.1. Debugging tsserver](<../3. Debugging and Ecosystem/3.1. Debugging tsserver logs and responsiveness.md>).

**Runnable example** — ordered triage (good vs bad, `tsc --strict`):

```typescript
// good — version-pinned tooling (log-first question answered structurally — settings, not folklore)
export function pinned3(): string { return "workspace-tsdk"; } // stated (settings.json documents — no per-machine drift)
console.log(pinned3()); // workspace-tsdk-pinned — version question answered (mismatch class deleted structurally)
// bad — "restart the editor" as first resort (ritual without diagnosis — issues recurring per project shape, unlearned)
// fix — logs first (request/response/error shapes per symptom — named failure classes, located fixes)
```

```typescript
// good — program-size awareness (file counts per program — split past thresholds, measured not hoped)
export function sized(): string { return "measured"; } // (extendedDiagnostics per perf question — check-time leaders named)
// fix — measure first (extendedDiagnostics per perf question, editor timing per feature — metrics before knobs, always)
console.log(sized()); // measured — size triaged (thresholds measured, splits justified by data)
// bad — disabling features blindly (inlay off, semantic highlighting off — responsiveness via amputation, root cause untouched)
// fix — triage order (size → watch → plugins → knobs — metrics per step, knobs per cause)
```

```typescript
// good — clean-rebuild verification (caches exonerated or eliminated in one command — diagnostic step, not cure-all)
export function rebuilt3(): string { return "clean-verified"; }
console.log(rebuilt3()); // clean-verified — caches exonerated (symptom persists post-clean → real bug, code changes justified)
// bad — editing code atop misloaded programs (churn without cause — fixes for phantom errors, regressions for real ones)
// fix — loading-first triage (version → extends → caches → boundaries — setup verified before code touched, always)
```

**Common confusion** — "triage order is pedantic" — order prevents misattribution (tuning watches for a program-size problem wastes the quarter — sequence matters because causes mask each other). "logs are for extension authors" — logs are for *anyone* debugging editor behavior (thirty minutes of orientation pays permanent dividends). "clean rebuilds fix everything" — clean rebuilds *exonerate-or-eliminate* caches (vanishing symptoms = cache poisoning, fixed; persisting = real bugs elsewhere).

**Performance note** — triage costs minutes per step (diagnostics + timing per question); misattributed tuning costs quarters (wrong knobs, unchanged symptoms); ritual restarts cost hours per incident across teams. Ordered triage is pure economics favoring instrumentation heavily.

**Mentor note** — ask "in what order?" before "what's wrong?" (sequence first — logs → loading → tuning, always). Follow-up: "when do you touch code?" (after setup verified — code changes justified only post-triage). Hiring signal: ordered-triage answers predict debugging skill, not just tool knowledge.

### 5) **How do you upgrade TypeScript across a monorepo — without a flag-day?** (pinning, playbook, lag)

**Definition** — upgrade sequence: pin versions per package (apps exact, libraries ranged + minimum-tested); playbook per version bump (changelog triage → branch build → class-ordered fixes → dual-pipeline verification); ecosystem-lag gating (framework/editor/linter readiness matrices green before bumping); strangler sequencing across the monorepo (leaf packages first, roots last — dependency-ordered migration).

**What problem it solves / history** — flag-day major upgrades (all packages + all errors in one PR — unreviewable, conflicting, pressuring suppression) stalled quarters while ecosystem lag (framework/editor/linter support windows) broke tooling post-bump. Sequenced upgrades (per-package, class-ordered, lag-gated) merge weekly green — compounding, revertible, verified per step.

**Modern guidance** — as of TypeScript 5.9 era, answer pinning-first (exact/ranged per package kind + minimum-tested floors), playbook-second (changelog → branch → class-ordered → dual-verify per version), lag-third (ecosystem matrices green before bumping), sequence-fourth (leaf-to-root dependency order). Full treatment in [3.3. Version management](<../3. Debugging and Ecosystem/3.3. Version management and upgrade playbooks.md>).

**Runnable example** — sequenced upgrades (good vs bad, `tsc --strict`):

```typescript
// good — pinned versions (deterministic diagnostics per checkout — upgrades deliberate PRs, never ambient drift)
export function pinned4(): string { return "deterministic"; } // (package.json: typescript exact for apps, ranged + floor-tested for libraries)
// fix — exact pins for apps (deterministic diagnostics per checkout — upgrades deliberate PRs, never ambient drift)
console.log(pinned4()); // deterministic — version policy (pins for apps, ranges + floors for libraries — each side's assumptions honored)
// bad — ranged app compilers (auto-upgrades mid-sprint — new errors/errors-removed without code changes, CI red mysteriously)
// fix — pins (deterministic per checkout — upgrades deliberate, triaged, class-ordered)
```

```typescript
// good — playbook per version (changelog → branch → class-ordered → dual-verify — green AND right)
// (playbook shape: triage scope first, fix per error class second, verify behavior third — upgrades sequenced, never big-banged)
export function played(): string { return "sequenced"; }
console.log(played()); // sequenced — playbook executed (same total triage distributed across green PRs vs one red quarter)
// bad — bump-and-fix-ad-hoc (version changed, errors fixed until green — classes mixed, suppressions slipped, behavior unnoticed)
// fix — playbook order (changelog → branch → triage → class-ordered fixes → dual verify → merge — green AND right)
```

```typescript
// good — lag-gated bumps (ecosystem matrices green before bumping — tooling lag respected, not discovered)
// (matrix shape: framework × editor × linter readiness per TS version — green across before bump approved)
// fix — lag management (support windows tracked — upgrades sequenced behind ecosystem readiness, always)
export function lagged(): string { return "gated"; }
console.log(lagged()); // gated — lag-gated bumps (readiness verified — tooling lag respected, reverts avoided)
// bad — day-one major upgrades (tooling lagging language releases — parse failures, missing syntax, transpile gaps post-bump)
// fix — readiness gates (track windows per dependency — bump when green across the matrix, never before)
```

**Common confusion** — "upgrades are just version bumps" — upgrades are *triaged migrations* (changelog scope, class-ordered fixes, behavior verification, ecosystem gating — bumps initiate, playbooks complete). "monorepos upgrade atomically" — monorepos upgrade *leaf-to-root* (dependency-ordered sequencing — roots last, after dependencies prove green). "lag gating delays" — lag gating *sequences* (ecosystem-ready bumps merging cleanly vs day-one bumps reverting messily — faster wall-clock *and* safer).

**Performance note** — playbook upgrades cost triage per error class (one-time per version); big-bang upgrades cost stalled quarters + suppression debt (unbounded); lag tracking costs minutes per quarter (matrix review). Sequenced economics dominate at every upgrade size.

**Mentor note** — ask "what's the sequence?" before "what's the target version?" (pinning → playbook → lag → dependency-order — order first, version second). Follow-up: "how do you verify beyond green CI?" (emit diffs + dual-pipeline + behavior smoke — green AND right). Hiring signal: sequenced-upgrade answers predict production judgment.
