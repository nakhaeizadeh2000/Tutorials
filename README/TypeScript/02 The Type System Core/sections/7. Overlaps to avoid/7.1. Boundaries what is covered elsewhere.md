## 7.1. Boundaries — what is covered elsewhere

### 1) **JavaScript mechanics** — [JavaScript track](<../../../../JavaScript/README.md>)

Value semantics, coercion, closure, prototype, iterables — the runtime behaviors that TypeScript types describe. For those mechanics themselves, use the JavaScript track: [03 Values Types and Coercion](<../../../../JavaScript/03 Values Types and Coercion/README.md>), [04 Variables Scope and Closures](<../../../../JavaScript/04 Variables Scope and Closures/README.md>), [06 Objects in Depth](<../../../../JavaScript/06 Objects in Depth/README.md>), [07 Prototypes and Classes](<../../../../JavaScript/07 Prototypes and Classes/README.md>). This domain describes their *type shapes*; it does not re-teach their execution.

### 2) **Basic type inventory** (`string`, `number`, `any`/`unknown`/`never`/`void`, literal types) — [03 Basic Types and Annotations](<../../../03 Basic Types and Annotations/README.md>)

Primitive and special types (`any`, `unknown`, `never`, `void`, `object`) and annotation forms (`:`, inference, `as`, `satisfies`, `!`) have their detailed inventory in 03. This domain already introduced their *role* in the system (see [01/1.2](<../../../01 Fundamentals and Mental Model/sections/1. What TypeScript is/1.2. Design goals and non-goals what TypeScript intentionally does not do.md>) non-goals, [3.3. Unsound spots](<../3. Soundness and variance/3.3. Unsound by design spots budgeted risks.md>)), but leaves the per-type catalogue to 03 — no duplication.

### 3) **Utility types and type transformations** (mapped, conditional, `infer`, template literals) — [09 Utility Types and Type Transformations](<../../../09 Utility Types and Type Transformations/README.md>)

Mapped types (`{ [K in keyof T]: ... }`), conditional types (`T extends U ? X : Y`), `infer`, and template literal types enable type-level computation on the shapes described here. Full transformation composition lives in 09, while [generic inference and infer binding](<../../../08 Generics Deep Dive/README.md>) belong in 08. This domain owns the *primitive* operators (`typeof`, `keyof`, `T[K]` — see [2.3.](<../2. The type vs value separation/2.3. Type queries typeof keyof and indexed access.md>)) and the variance model that constrains them.

### 4) **Configuration and variance flags** (`strictFunctionTypes`, `strictPropertyInitialization`, `noImplicitAny`, `exactOptionalPropertyTypes`) — [13 Configuration and Compiler Options](<../../../13 Configuration and Compiler Options/README.md>)

Configuration is already published in 13. This domain explains the relation affected by strictFunctionTypes; the [flag owner](<../../../13 Configuration and Compiler Options/sections/1. Strictness Family/1.3. strictFunctionTypes strictPropertyInitialization noImplicitOverride.md>) explains configuration and related checks. A strict setting does not add a runtime validator or turn all method parameters into strictly checked function properties. Current compiler/tool migration belongs in the [7.0 learning route](<../../../25 Update TypeScript 7.0/sections/6. Overlaps and Update Route/6.1. Overlaps and the current learning route.md>); this track's checked baseline is 7.0.2.

### 5) **Where this domain stops** (stop-list)

- **Stop:** Do not duplicate JavaScript mechanics, per-type inventories, utility-type transformations, or `tsconfig` flag catalogue.
- **Start here:** explain the source/target assignability relation, creation-site freshness, brands, declaration meanings, primitive queries and variance decisions.

Practice routing a question before answering it fully. “Can a never value be assigned to string?” is the [verified core interview's assignment-direction question](<../6. Interview questions and answers/6.1. Common interview QA the type system core.md>). “Which runtime string operation does a wrapper expose?” needs the [primitive/wrapper owner](<../../../03 Basic Types and Annotations/sections/1. The Primitive Family/1.1. string number boolean and the wrapper pitfall.md>). “Why did blue expand my generic's allowed set?” needs the [NoInfer/inference owner](<../../../08 Generics Deep Dive/sections/1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>). State the specific question so the link supplies the missing depth rather than a vague direction.

### 6) **Common confusion**

The assignability model and a particular primitive's operations are related but have different owners. A namespace can qualify an interface without giving it nominal identity; a utility can transform that interface without creating a runtime value. Use the core model to identify what is compared, then follow the feature owner for its full contract. A static acceptance still leaves the actual runtime operation to explain.

### 7) **Performance note**

This navigation page has no executable example or measured speed result. Core type relations and queries supply checking information, while runtime object/function/collection work follows the actual implementation. If a complex transformation checks slowly, follow the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) instead of inferring cost from a utility's name or its position in the curriculum.

### 8) **Mentor note**

Ask the learner to route the never, wrapper and competing-inference questions above and give a reason for each. A sound answer identifies assignment direction, runtime representation and candidate inference respectively. In review, keep that immediate distinction plus a precise link; avoid reteaching the entire primitive inventory or mapped-type catalog in a core-system explanation.
