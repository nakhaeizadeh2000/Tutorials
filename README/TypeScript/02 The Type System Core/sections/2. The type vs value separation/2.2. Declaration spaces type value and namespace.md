## 2.2. Declaration spaces — type, value, and namespace

### 1) **Three declaration spaces**

A declaration can introduce a runtime value, a type name, or a namespace whose exported names are reached through qualification. These meanings explain why two declarations sometimes share a spelling. They do not, by themselves, decide whether a pair may merge.

| Declaration | Type meaning | Value meaning | Namespace meaning |
|---|---|---|---|
| `type`, `interface` | Yes | No | No |
| Variable, function | No | Yes | No |
| Class | Instance type | Constructor | No |
| Enum | Enum/member types | Enum object in ordinary emit | No |
| Namespace | No standalone type for the namespace itself | When it contains runtime members | Exported qualified names |

A class's static properties do not make the original declaration a namespace. An enum object is also distinct from a namespace declaration. A subsequent `namespace Point` or `namespace Direction` can add the namespace meaning. The [Handbook's declaration table](https://www.typescriptlang.org/docs/handbook/declaration-merging.html) and [declaration-file deep dive](https://www.typescriptlang.org/docs/handbook/declaration-files/deep-dive.html) describe this distinction.

A namespace can contain types without creating JavaScript. A namespace with exported runtime values needs emitted code. Consequently, the presence of a namespace declaration does not prove that a runtime object exists.

### 2) **Merging rules**

The useful diagnostic sequence is: identify the scope, identify each declaration's meanings, then check whether TypeScript permits that particular pair. Two interfaces in the same scope can merge even though both introduce a type. A type alias and an interface in the same scope collide. Different declaration kinds do not make that pair valid. A `type Mode` and `const Mode` can coexist because they supply separate meanings; this is not interface merging.

Create `declarations.ts` in a fresh directory without a `tsconfig.json`. This example was checked with TypeScript 7.0.2 and run as emitted JavaScript on Node 20.20.2:

```typescript
export {};

type Mode = "read" | "write";
const Mode = { Read: "read", Write: "write" } as const;
const mode: Mode = Mode.Read;
console.log(mode);

interface Config { host: string; }
interface Config { port: number; }
const config: Config = { host: "localhost", port: 5432 };
console.log(config.host, config.port);

class Point {
  x = 0;
  y = 0;
}
namespace Point {
  export type Label = "origin" | "other";
  export const origin = new Point();
}
const label: Point.Label = "origin";
console.log(label, Point.origin.x);

namespace Protocol {
  export interface Packet { id: string; }
}
const packet: Protocol.Packet = { id: "p1" };
console.log(packet.id);
```

```sh
tsc --strict --target es2022 --module commonjs --outDir dist declarations.ts
node dist/declarations.js
```

The output is `read`, `localhost 5432`, `origin 0`, then `p1`, on separate lines. Both `Config` blocks contribute to the same required shape. The `Point` namespace follows the class and supplies a qualified type and a constructor property. `Protocol.Packet` is a type; inspection of `dist/declarations.js` shows no `Protocol` object because that namespace contains only an interface.

For a rejection exercise, create a separate `duplicate.ts`:

```typescript
export {};
type Entry = { id: string };
interface Entry { name: string; }
```

Run `tsc --strict --noEmit duplicate.ts`. It exits unsuccessfully with TS2300 on both declarations. Replacing the alias with an interface allows their members to merge. Alternatively, keep separate names and compose a new type. Choose composition for a local application model when accidental reopenings would make its definition harder to find. Choose merging when extending an existing open declaration is the actual requirement.

### 3) **Module scope vs script scope**

Top-level imports or exports establish module scope. Configuration can classify files as modules too; therefore, “no imports means script” needs a stated configuration. The following project deliberately sets `moduleDetection` to `legacy` so that the import/export distinction is visible. See the [module-detection reference](https://www.typescriptlang.org/tsconfig/moduleDetection.html) for other modes.

Create these files in a separate `scope-example` directory:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2022",
    "module": "commonjs",
    "moduleDetection": "legacy",
    "types": [],
    "lib": ["es2022", "dom"],
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": ["src"]
}
```

Save that configuration as `tsconfig.json`. Save this declaration as `src/globals.d.ts`:

```typescript
export {};
declare global {
  interface AppStamp { version: string; }
  interface AppStamp { source: string; }
  var __appStamp: AppStamp;
}
```

Save `src/main.ts`:

```typescript
export {};
globalThis.__appStamp = { version: "1", source: "cli" };
console.log(globalThis.__appStamp.version, globalThis.__appStamp.source);
```

From `scope-example`, run `tsc --project tsconfig.json`, then `node dist/main.js`. The output is `1 cli`. The declaration file contributes a merged global type and describes a global variable. The assignment in `main.ts` supplies the runtime value; declarations alone would not initialize it.

Remove only `export {};` from `globals.d.ts` and rerun the build. With this configuration, the file becomes a script, and `declare global` produces TS2669. Inside a script declaration file, a top-level interface already participates in the global scope. Inside a module declaration file, `declare global` deliberately escapes module scope. Restoring the export restores the passing build. The [global-augmentation owner](<../../../12 Modules Namespaces and Declaration Files/sections/2. Namespaces and Ambient Contexts/2.2. declare global and global augmentation.md>) develops the provider and deployment responsibilities further.

### 4) **Common confusion**

“Same space means collision” fails for two interfaces: merging is a supported same-space operation. “Different kinds mean no collision” fails for a type alias plus an interface: both occupy the type meaning and that pair cannot merge. Explain the permitted pair rather than inventing a universal complementary-space rule.

Merging declarations also does not install implementations. Adding a method to an interface describes a capability; it does not put that method on an object. The complete global example uses an explicit assignment so that the declared value actually exists when read.

### 5) **Performance note**

Interface merging and type aliases leave no runtime instructions. The runtime-bearing `Point` namespace adds initialization code; the type-only `Protocol` namespace does not. Inspect emit when this distinction matters to a source runner or bundle. Global declarations can affect a program's checking context, but this example provides no timing evidence and no guarantee that converting scripts to modules speeds up every incremental build. Use the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) to investigate an actual slow project.

### 6) **Mentor note**

Ask learners to predict the three cases before running them: alias plus variable, interface plus interface, alias plus interface. A sound answer identifies the scope and explains the accepted or rejected pair. Then remove the global example's runtime assignment and ask what supplies `__appStamp`. The answer must distinguish a checker-visible declaration from initialization. For the namespace example, ask them to locate the emitted `Point` initialization and explain why `Protocol` has none.
