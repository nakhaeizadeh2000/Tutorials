## 2.2. Declaration spaces — type, value, and namespace

### 1) **Three declaration spaces** (value: `const x`; type: `type T`, `interface I`; namespace: `namespace N` / `enum E` legacy)

**Definition** — Every declaration belongs to one or more of three spaces:

| Space | Declarations | Can coexist with same name? |
|---|---|---|
| Value | `const`/`let`/`var`, `function`, `class` (constructor value), `enum` (object), `namespace` (object) | Same identifier in value + type is ok; value + value collides |
| Type | `type`, `interface`, `class` (instance type), `enum` (member type), type parameters `<T>` | Same name in value + type is ok; type + type for `type` collides |
| Namespace | `namespace`, `enum`, `class` | Legacy value-space containers; `namespace` merging is nominal |

The key rule: *value vs type can share a name; type vs type usually cannot* — except `interface` which has a special merging exception (see below).

### 2) **Merging rules** (`class` + `namespace` can merge; `type` cannot merge with `class` value; `interface` merging is special)

Merging allows two declarations with the *same name in complementary spaces* to combine:

```typescript
// class + namespace merge — canonical dual augmentation
class Point { constructor(public x: number, public y: number) {} }
namespace Point { export const origin = new Point(0, 0); }
// Value: Point is both the constructor and a namespace holding origin
// Type: Point is still the instance type { x, y }
// Usage: Point.origin is a Point

// interface merging — allowed for same-named interfaces (declaration merging)
interface Config { host: string; }
interface Config { port: number; } // merges → { host: string; port: number }
declare const cfg: Config; // has both host and port

// type merging — forbidden
// type A = { x: number }; type A = { y: number }; // error TS2300: Duplicate identifier 'A'
// fix: use interface merging or a union
```

Modern guidance — use `interface` merging only for *ambient* declarations (augmenting globals or library types). In application code, prefer a single `interface`/`type` declaration or `type Combined = A & B` over merging via repetition.

### 3) **Module scope vs script scope** (files are modules when they contain `import`/`export` — otherwise ambient global merging applies)

A file with *any* top-level `import` or `export` is a *module*; its declarations are scoped to that file. A file without either is a *script*; its declarations are global and can merge across files in the global namespace. This is why adding `export {}` to a file can silence ambient merging surprises.

```typescript
// file: a.ts (no import/export → script, global)
// declare global { interface Window { myProp: string } } // augments global Window in script mode

// file: b.ts (has export → module, isolated)
export type UserId = string; // scoped to module; not global
// To augment global from a module, use explicit declare global { }
```

### 4) **Runnable example** — merging rules in practice (good + bad)

```typescript
// good — interface merging for ambient augmentation (the legitimate use case)
// file: globals.d.ts — declare global augmentation for Window
// declare global {
//   interface Window { __appVersion: string; }
// }
// export {}; // makes file a module so declare global is required and scoped

// bad — type alias duplicate (error) and unintended global leakage
// file: types.ts (no import/export → script, global leakage)
type User = { name: string };
// type User = { age: number }; // error TS2300: Duplicate identifier — type space collision

// fix: single declaration or intersection
type UserFixed = { name: string } & { age: number }; // { name: string; age: number }

// good — class + namespace merge for companion static (value + value namespace augmentation)
class Vec { constructor(public x: number, public y: number) {} }
namespace Vec {
  export function zero(): Vec { return new Vec(0, 0); }
  export const unitX = new Vec(1, 0);
}
const v: Vec = Vec.zero(); // type Vec = instance; value Vec.zero() = constructor's namespace

// bad — expecting type and value with same name to collide (they don't)
// type Status = "a" | "b";
// const Status = { a: "a", b: "b" }; // no collision — type vs value is allowed
// The confusion is expecting an error that never arrives
```

### 5) **Common confusion**

- "`interface` merging is an anti-pattern" — in application code, it's usually unnecessary; in ambient `.d.ts` and library augmentation, it's the idiomatic way to extend global interfaces.
- "Adding `export {}` does nothing" — it converts a script to a module, isolating declarations from the global scope. That's a real semantic change.
- "`enum` merges like `interface`" — `enum` merges with its namespace in a non-erasable IIFE; that's legacy behavior. Use union + const object instead (see [01/3.3](../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>)).

### 6) **Performance note**

Declaration merging itself is negligible, but globally scoped script files participating in many `interface Window` augmentations force the checker to re-evaluate the global namespace on every change — a reason large apps prefer modules over scripts. Prefer per-module `import type` over global script merging for faster incremental checks.

### 7) **Mentor note**

Merging is best taught as "complementary spaces compose; same-space repeats collide — except `interface`". Exercise: give students `type A = ...; interface A { }` and ask if it collides (no — `type` vs `interface` are both type space, but different kinds, still error for duplicate `A`). Then show `interface A { x }; interface A { y }` merging and ask why two `type A` declarations cannot do the same (answer: `type` forbids merging by design; `interface` permits it by declaration-merging special case).
