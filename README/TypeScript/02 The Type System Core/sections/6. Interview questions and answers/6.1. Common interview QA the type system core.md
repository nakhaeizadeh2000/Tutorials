## 6.1. Common interview Q&A — the type system core

### 1) **Structural vs nominal** (when does TypeScript behave nominally?)

**Question** — "When does TypeScript treat two identically shaped types as different?"

**Answer** — Almost never — structural is default. Nominal-like behavior occurs for: (a) `class` with `private`/`protected` members (different private declarations break assignability), (b) branded types (`string & { __brand }`) which add a phantom member, and sometimes `enum`/`namespace` uniqueness. Otherwise, `{ x: number }` compatibility depends solely on members, not name (see [1.1.](<../1. Structural typing/1.1. Structural assignability shape not name.md>) and [1.3.](<../1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>)).

---

### 2) **Freshness** (why does `const x: Point = { x: 1, y: 2, z: 3 }` error but `const y = { x: 1, y: 2, z: 3 }; const x: Point = y` not?)

**Question** — same code fragment, different path — why divergent result?

**Answer** — Fresh object literals get an *excess property check* at assignment/call/return sites; variables bypass it. First form is a fresh literal directly against `Point` → error "Object literal may only specify known properties" (heuristic lint, not structural failure). Second goes via intermediate variable `y` → freshness evaporates → width subtyping silently allows extra `z` (see [1.2.](<../1. Structural typing/1.2. Excess property checks and freshness.md>)).

**Follow-up:** "Is the second form still assignable?" — yes. Freshness never changes the underlying assignability relation.

---

### 3) **`in`/`out` variance** (how to annotate and what it catches)

**Question** — "What do `in`/`out` mean on a type parameter and what error does mis-annotating produce?"

**Answer** — `out T` = covariant (only produces `T`), `in T` = contravariant (only consumes), `in out T` = invariant (produces+consumes). Declaring `type Box<out T> = { write(v: T): void }` fails at declaration time: `TS2717: 'T' is declared 'out' but used as 'write' parameter (invariant position)` — catches the mismatch before any use (see [3.1.](<../3. Soundness and variance/3.1. Covariance contravariance and invariance who varies which way.md>)). Omitting `in`/`out` infers variance per member — annotate for library contracts.

---

### 4) **`any` vs `unknown` vs `never`** (three "I don't know" flavors — when each fits)

**Question** — "Compare `any`, `unknown`, `never`."

**Answer** — `any` disables checking (compatible transitively, leak). `unknown` forces checking (must narrow before use — the disciplined "don't know"). `never` has no values (bottom type, returned by `throw`/`while(true)` and rejected by every assignment). Use `unknown` at boundaries, `never` for unreachable/exhaustive checks. See also forward to [03 Basic Types](../../03%20Basic%20Types%20and%20Annotations/README.md) for the full inventory.

**Red flag:** "use `any` for I don't know" — should be `unknown`.

---

### 5) **Type/value separation** (why `class C` can be both a type and a value)

**Question** — "Why can `class Point` be used both as `const p = new Point()` and `type T = Point`?"

**Answer** — Two declaration spaces: `class` declares a value (constructor function) and a type (instance shape) simultaneously. `Point` in value position is the constructor; `Point` in type position is the instance type `{ x: number; y: number }`; `typeof Point` in type position is the *constructor* type (see [2.1.](<../2. The type vs value separation/2.1. Type space vs value space two parallel universes.md>) and [2.2.](<../2. The type vs value separation/2.2. Declaration spaces type value and namespace.md>)). `type` and `const` sharing a name don't collide — different spaces.

---

### 6) **`typeof` in two spaces** (runtime check vs type query — same keyword, different meaning)

**Question** — "`typeof` appears twice — explain the two."

**Answer** — Value `typeof x === "string"` is the JS runtime operator (emitted). Type `type T = typeof x` is a type query that captures the static type of `x` (erased). Position decides: after `:`/`extends`/`type` it's a query; before `===` it's runtime (see [2.3.](<../2. The type vs value separation/2.3. Type queries typeof keyof and indexed access.md>)). `as const` + `typeof`/`keyof`/`T[K]` together round-trip values to types with zero runtime cost.
