## 6.1. Common interview Q&A — the type system core

A strong answer predicts a particular assignment or runtime result and explains why. These questions use TypeScript 7.0.2 with `strict`; the runtime example uses Node 20.20.2. Save each named file in a new directory without a `tsconfig.json`. The files containing `declare` are compile-only probes: use `--noEmit` and do not execute them.

### 1) **Structural vs nominal**

**Question:** Does putting two identically shaped interfaces in different namespaces make them incompatible?

**Answer:** Namespace qualification changes how you name an interface; compatibility still follows its members. `First.Point` and `Second.Point` below both require `x: number`, so assignment succeeds. A class with a private member adds a different condition: the corresponding private member must originate from the same declaration. `FirstKey` and `SecondKey` fail that condition despite spelling their private field alike. Brands similarly distinguish types by adding a member to the contract; a type alias's name alone adds no protection. [Type compatibility](https://www.typescriptlang.org/docs/handbook/type-compatibility.html) describes the private/protected rule.

Save `directions.ts`. This shared probe also supplies the assignment directions for question 4.

```typescript
export {};
namespace First { export interface Point { x: number } }
namespace Second { export interface Point { x: number } }
const first: First.Point = { x: 1 };
const second: Second.Point = first; // qualification adds no brand

class FirstKey { private token = "key"; }
class SecondKey { private token = "key"; }
const firstKey = new FirstKey();
// @ts-expect-error: different private declarations
const secondKey: SecondKey = firstKey;

declare const impossible: never;
const text: string = impossible;
const count: number = impossible;
const flag: boolean = impossible;
// @ts-expect-error: an ordinary string cannot inhabit never
const rejected: never = "hello";
declare const incoming: unknown;
// @ts-expect-error: narrow unknown before treating it as string
const unchecked: string = incoming;
```

Run `tsc --strict --noEmit directions.ts`: exit 0. Each `@ts-expect-error` is an active rejection check. Remove those three directives to observe TS2322 for the separate private declarations, string-to-never and unknown-to-string assignments. The namespace and never-to-string/number/boolean assignments remain accepted. An ambient `declare` supplies a checker assumption, not a runtime object.

### 2) **Freshness and excess properties**

**Question:** Why does a directly assigned extra `z` fail while a richer object assigned through a variable succeeds?

**Answer:** A fresh literal checked against `PointShape` receives an excess-property check. The variable `richPoint` still has `z`, but assigning it to a contract requiring `x` and `y` succeeds structurally. The assignment neither deletes `z` nor creates a new object. The runtime program in question 6 prints `true` for `"z" in point`. Uncomment its fresh-literal line and check with `tsc --strict --noEmit interview.ts` to observe TS2353.

For a configuration typo, validate the literal at its construction site with an annotation or `satisfies`; do not introduce an intermediate variable simply to hide the diagnostic. Full rules and qualifications belong in [freshness](<../1. Structural typing/1.2. Excess property checks and freshness.md>).

### 3) **Variance annotations and the method exception**

**Question:** Which direction is safe for a producer or consumer? Does `out T` forbid every parameter mentioning T?

**Answer:** A Dog producer can satisfy an Animal producer contract because every returned Dog is an Animal. An Animal consumer can satisfy a Dog consumer contract because it handles every input that caller may provide. The two substitutions go in opposite directions. `out` expresses covariance and `in` expresses contravariance; `in out` expresses invariance when comparing instantiations of that generic. These optional annotations arrived in [TypeScript 4.7](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-7.html#optional-variance-annotations-for-type-parameters).

Save `variance.ts` and run `tsc --strict --noEmit variance.ts`: exit 0. Remove the two expected-error directives to observe TS2322 in both unsafe directions. This is another compile-only file.

```typescript
export {};
interface Animal { name: string }
interface Dog extends Animal { bark(): void }
type Producer<out T> = () => T;
type Consumer<in T> = (value: T) => void;
declare const dogProducer: Producer<Dog>;
const animalProducer: Producer<Animal> = dogProducer;
declare const animalConsumer: Consumer<Animal>;
const dogConsumer: Consumer<Dog> = animalConsumer;
// @ts-expect-error: an Animal producer might not produce a Dog
const rejectedProducer: Producer<Dog> = animalProducer;
// @ts-expect-error: a Dog-only consumer cannot handle every Animal
const rejectedConsumer: Consumer<Animal> = dogConsumer;

// Accepted by 7.0.2: method parameters retain the bivariance exception.
type MethodBox<out T> = { write(value: T): void };
```

The final method alias is accepted. Under strict function checking, method parameter positions have a [bivariance exception](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-6.html#strict-function-types). Annotation acceptance therefore does not establish that a writer can safely consume every widened input. Compare a **separate** file, `variance-property.ts`, using a function property:

```typescript
export {};
type PropertyBox<out T> = { write: (value: T) => void };
```

`tsc --strict --noEmit variance-property.ts` fails with TS2636 on 7.0.2: the write property contradicts the declared covariant relation. The method/property distinction changes the check. Derive the needed input/output relation and test actual substitutions; do not memorize an invented diagnostic or annotate every generic. The [generics reference](https://www.typescriptlang.org/docs/handbook/2/generics.html#variance-annotations) also explains that annotations apply to instantiation-based comparisons, rather than changing all structural comparisons.

### 4) **any, unknown and never**

**Question:** Which type represents untrusted input, and which represents an impossible case?

**Answer:** `unknown` represents a value whose operations require evidence, such as the string check in the runtime example. `any` permits unchecked operations and can spread that lack of checking into callers; use it deliberately at a documented escape boundary. `never` has no possible values. It can flow into other types, while an ordinary string cannot flow into a never target, as `directions.ts` checks. This direction makes a remaining union member fail an exhaustiveness check. It does not turn `never` into another spelling of “unknown.” See the primary [never and exhaustiveness explanation](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#exhaustiveness-checking) and the [basic type inventory](<../../../03 Basic Types and Annotations/README.md>).

### 5) **A class as a type and a value**

**Question:** What do `Point`, `new Point()` and `typeof Point` mean?

**Answer:** In a value expression, `Point` is the constructor. In an instance annotation, `Point` describes the instance. In a type query, `typeof Point` describes the constructor value's static type. The runtime program assigns that constructor to `ConstructorValue`, constructs an instance and prints `function object`. An interface supplies no equivalent runtime constructor. The [type/value owner](<../2. The type vs value separation/2.1. Type space vs value space two parallel universes.md>) explains the declaration meanings and legal same-name combinations.

### 6) **Runtime typeof and type-query typeof**

**Question:** Which typeof executes, and does deriving a type validate a runtime value?

**Answer:** `typeof incoming === "string"` executes a JavaScript check that supports narrowing. `type Constructor = typeof Point` and the query over `modes` are checker expressions whose annotations erase. The derived `Mode` constrains the declared program; it does not parse an external request or change the strings stored in `modes`.

Save `interview.ts`:

```typescript
export {};
type PointShape = { x: number; y: number };
const richPoint = { x: 1, y: 2, z: 3 };
const point: PointShape = richPoint;
console.log("point:", point.x, point.y, "z" in point); // 1 2 true
// const fresh: PointShape = { x: 1, y: 2, z: 3 }; // uncomment: TS2353

class Point {
  x = 1;
  y = 2;
}
type Constructor = typeof Point;
const ConstructorValue: Constructor = Point;
const instance: Point = new ConstructorValue();
console.log("class:", typeof Point, typeof instance); // function object

const incoming: unknown = "Ada";
if (typeof incoming === "string") {
  console.log("narrowed:", incoming.toUpperCase()); // ADA
}
const modes = { read: "get", write: "post" } as const;
type Mode = (typeof modes)[keyof typeof modes];
const method: Mode = "get";
console.log("query:", typeof method, method); // string get
```

Run `tsc --strict --target es2022 --module commonjs --lib es2022,dom --outDir out interview.ts`, then `node out/interview.js`. Both exit 0; the four output lines are `point: 1 2 true`, `class: function object`, `narrowed: ADA` and `query: string get`. Relate each line to the specific object, constructor or guard involved.

### 7) **Common confusion**

A qualified name is not a brand, a method parameter is not checked identically to a function property, and an accepted never-to-string assignment does not construct a string value. Each confusion comes from predicting behavior from a name or spelling instead of the contract being compared. State the source and target types before answering. For runtime questions, separately identify which values actually exist after emission.

### 8) **Performance note**

Namespaces containing only interfaces, variance annotations and type queries add no runtime validation. The runtime program still constructs an instance, checks a string and logs values. This lesson measures no execution or checking speed. Variance-related optimization requires a measured checker bottleneck and a justified annotation; it is not a reason to decorate every type parameter. Keep such investigation in the [measurement owner](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>).

### 9) **Mentor note**

Ask the learner to predict three changes before checking them: rename a namespace, reverse the never assignment, and replace method syntax with a function property. A sound answer predicts unchanged structural compatibility, a rejected ordinary value, and TS2636 for this covariant writer. Then ask why the ambient probe must not run. Assess the explanation and evidence, rather than rewarding jargon or a memorized error number.
