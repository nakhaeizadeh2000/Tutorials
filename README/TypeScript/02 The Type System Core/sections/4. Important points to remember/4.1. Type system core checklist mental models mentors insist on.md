## 4.1. Type system core checklist — mental models mentors insist on

### 1) **Shape, not name, governs assignability** (freshness is the exception — know when it triggers)

**Check** —

- Extra members through a variable are silent (width subtyping) — freshness only fires on *fresh* literals at assignment/call/return (see [1.1. Structural assignability](<../1. Structural typing/1.1. Structural assignability shape not name.md>) and [1.2. Excess property checks](<../1. Structural typing/1.2. Excess property checks and freshness.md>)).
- Can you state why `const x = { x: 1, y: 2, z: 3 }; const p: Point = x` succeeds but `const p: Point = { x: 1, y: 2, z: 3 }` fails? (Freshness.)

### 2) **Type and value are parallel spaces** (same name, different meaning; `typeof` is context-dependent)

**Check** —

- `type User = ...` and `const User = ...` coexist (value vs type space) — see [2.1. Type space vs value space](<../2. The type vs value separation/2.1. Type space vs value space two parallel universes.md>).
- `typeof x` is a *value* runtime check inside `if`, but a *type query* inside `type T = typeof x` — see [2.3. Type queries](<../2. The type vs value separation/2.3. Type queries typeof keyof and indexed access.md>).
- `class C` creates both a constructor value and an instance type — `C` vs `typeof C` distinction is instance vs constructor.

### 3) **Variance is directional** (`return` covariant, `parameter` contravariant — method bivariance is the legacy exception)

**Check** —

- Returns vary same direction (`Dog ≤ Animal` → `() => Dog ≤ () => Animal`) — see [3.1. Covariance, contravariance](<../3. Soundness and variance/3.1. Covariance contravariance and invariance who varies which way.md>).
- Parameters vary opposite (`(Dog) => void` not assignable where `(Animal) => void` expected under `strictFunctionTypes`) — but method shorthand stays bivariant (see [3.2. Function variance](<../3. Soundness and variance/3.2. Function variance and strictFunctionTypes.md>)).
- Arrays are covariantly treated (unsound) — use `readonly` to recover safe covariance (see [3.3. Unsound spots](<../3. Soundness and variance/3.3. Unsound by design spots budgeted risks.md>)).

### 4) **Branding adds nominal identity without runtime cost** (but requires a proving assertion at creation)

**Check** —

- Branded `UserId` requires `as UserId` at creation, zero emit cost, but demands a predicate or validator before `as` (see [1.3. Nominal branding](<../1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>)).
- Every `as Brand` should be justified by a runtime proof — countable and reviewable.

---

### 5) **Runnable example** — the checklist as executable guardrails

```typescript
// 1: freshness — this should error if literal is fresh, silent if through var
type Point = { x: number; y: number };
// const a: Point = { x: 1, y: 2, z: 3 }; // error TS2353 (freshness)
const via = { x: 1, y: 2, z: 3 };
const b: Point = via; // ok — width subtyping, no freshness

// 2: type vs value
const config = { host: "localhost" } as const;
type ConfigType = typeof config; // type query — captures { readonly host: "localhost" }
const configValue = config; // value reference

// 3: variance — property vs method (property is stricter under strictFunctionTypes)
type HandlerValue = { handle: (s: string) => void };
interface HandlerMethod { handle(s: string): void; }
type Dog = string & { __brand: "Dog" };
// property assignment strictly checked; method may still pass bivariantly

// 4: branding
type UserId = string & { __brand: "UserId" };
function makeUserId(s: string): UserId { return s as UserId; }
const uid: UserId = makeUserId("u-1"); // one trusted site
```

### 6) **Mentor note**

Use this checklist as the opening quiz for every type-level review: ask "which rule explains why this assignment succeeds/fails?" If students can't name the rule, they haven't internalized the model. Exercise: given `dogs: Dog[]` passed to `fn(animals: Animal[])` where `fn` does `animals.push(cat)`, ask which rule is violated — answer: array covariance hole requiring `readonly` (see [3.3.](<../3. Soundness and variance/3.3. Unsound by design spots budgeted risks.md>)).
