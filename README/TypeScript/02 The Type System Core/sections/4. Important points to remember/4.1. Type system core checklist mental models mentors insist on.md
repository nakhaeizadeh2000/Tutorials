## 4.1. Type system core checklist — mental models mentors insist on

### 1) **Shape, not name, governs assignability** (freshness is the exception — know when it triggers)

**Check** —

- An ordinary richer variable can satisfy a narrower required-member contract; this does not waive missing-member, incompatible-member or weak-type checks. A directly checked literal receives an additional excess-property check (see [1.1. Structural assignability](<../1. Structural typing/1.1. Structural assignability shape not name.md>) and [1.2. Excess property checks](<../1. Structural typing/1.2. Excess property checks and freshness.md>)).
- Can you state why `const x = { x: 1, y: 2, z: 3 }; const p: Point = x` succeeds but `const p: Point = { x: 1, y: 2, z: 3 }` fails? (Freshness.)

### 2) **Type and value are parallel spaces** (same name, different meaning; `typeof` is context-dependent)

**Check** —

- `type User = ...` and `const User = ...` coexist (value vs type space) — see [2.1. Type space vs value space](<../2. The type vs value separation/2.1. Type space vs value space two parallel universes.md>).
- `typeof x` is a *value* runtime check inside `if`, but a *type query* inside `type T = typeof x` — see [2.3. Type queries](<../2. The type vs value separation/2.3. Type queries typeof keyof and indexed access.md>).
- `class C` creates both a constructor value and an instance type — `C` vs `typeof C` distinction is instance vs constructor.

### 3) **Variance is directional** (`return` covariant, `parameter` contravariant — method bivariance is the legacy exception)

**Check** —

- Returns vary same direction (`Dog ≤ Animal` → `() => Dog ≤ () => Animal`) — see [3.1. Covariance, contravariance](<../3. Soundness and variance/3.1. Covariance contravariance and invariance who varies which way.md>).
- Parameters vary opposite (`(Dog) => void` not assignable where `(Animal) => void` expected under `strictFunctionTypes`) — but method shorthand stays bivariant (see [3.2. Function variance](<../3. Soundness and variance/3.2. Function variance and strictFunctionTypes.md>)).
- Mutable arrays can be widened and then corrupted through an alias. A readonly parameter prevents writes through that view; it neither freezes the array nor repairs other mutable aliases (see [3.3. Unsound spots](<../3. Soundness and variance/3.3. Unsound by design spots budgeted risks.md>)).

### 4) **Branding records a reviewed construction decision**

**Check** —

- A branded `UserId` separates otherwise similar values during checking. Review the construction boundary and the evidence needed for its domain invariant (see [1.3. Nominal branding](<../1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>)).
- For untrusted input, validation must establish the claimed invariant before the assertion. An assertion alone does not check it. The existing [branding owner](<../1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>) develops the pattern; this checklist asks whether the chosen construction policy is justified.

### 5) **Runnable example** — inspect the checklist's static distinctions

Use TypeScript 7.0.2 and Node 20.20.2 in a directory without a tsconfig. Save the fence as `checklist.ts`. The example intentionally demonstrates an assertion site, not a validator for a particular ID format; decide and implement any domain validation before applying that construction to external data.

```typescript
export {};
// 1: Compare this particular literal with a compatible richer variable.
type Point = { x: number; y: number };
// const a: Point = { x: 1, y: 2, z: 3 }; // error TS2353 (freshness)
const via = { x: 1, y: 2, z: 3 };
const b: Point = via; // ok — width subtyping, no freshness

// 2: type vs value
const config = { host: "localhost" } as const;
type ConfigType = typeof config; // type query — captures { readonly host: "localhost" }
const configValue = config; // value reference

// Variance is reviewed with the complete linked function/method example.

// 4: branding
type UserId = string & { __brand: "UserId" };
function makeUserId(s: string): UserId { return s as UserId; }
const uid: UserId = makeUserId("u-1"); // an assertion site; no format validation occurs here
console.log(b === via, "z" in b, typeof configValue);
console.log(uid, typeof uid);
```

Run the saved file:

```bash
tsc --strict --target es2022 --module commonjs --lib es2022,dom --outDir dist checklist.ts
node dist/checklist.js
```

Both commands exit zero. The output is `true true object`, then `u-1 string`. Assignment retains the richer object, the runtime config remains an object, and the asserted identifier remains a string. The complete function/method substitution check is in the linked variance owner; declaring unused handler types here would not test that relation. Uncomment the fresh-literal assignment and the same compiler command reports TS2353. Restore it, then append `const unbranded: UserId = "u-1";`: this produces TS2322 even though the value is a string. Those diagnostics distinguish an extra-property check from an incompatible branded target. They do not establish runtime validation.

### 6) **Common confusion**

Assignability checks the required shape; it does not delete the source's extra properties or make an object exact. A type query such as `typeof config` describes a value to the checker, while runtime `typeof config` evaluates to `"object"`. The branded `uid` in the example is still a string at runtime. Finally, `readonly` removes mutation operations from a particular typed view; it does not freeze the underlying array or eliminate a mutable alias. These distinctions prevent static guarantees from being mistaken for runtime transformations.

### 7) **Performance note**

The type aliases, interfaces and assertions in this checklist erase. They add no runtime branding object or type-query operation. The factory call and any validation you implement are ordinary executable code with their own cost; calling that whole boundary zero-cost would hide those operations. Structural comparisons and branded intersections also require checker work, whose cost depends on the actual program. No timing benchmark was run for this checklist; use measurements before making build-performance claims.

### 8) **Mentor note**

Ask which rule explains each successful or rejected assignment before accepting “TypeScript allows it.” Use the fresh-literal and unbranded-string probes to demand different explanations. For variance, ask whether a callback required to accept every Animal can safely be replaced by one that only accepts Dog, then compare a function property with a method declaration in the existing variance owner. For branding, ask what the factory actually verifies. A sound answer notices that this example's assertion does not validate an ID format and identifies where an application's domain proof must occur.
