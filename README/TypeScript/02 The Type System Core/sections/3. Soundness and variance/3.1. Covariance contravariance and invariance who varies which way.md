## 3.1. Covariance contravariance and invariance — who varies which way

Variance describes how a parameterized contract's assignment direction relates to the direction of its type argument. Start with actual producers and consumers: a Cat has the Animal members plus meow, so a cat producer can serve an animal reader. A consumer accepting any Animal can also accept a Cat; a Cat-only consumer cannot handle every Animal.

Here `Reader<T>` means a reader producing the chosen T, while `Writer<T>` consumes it. The full declaration mechanics come later in [Generics](<../../../08 Generics Deep Dive/README.md>); this lesson uses those small contracts to explain substitution. Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each TypeScript fence under its filename and compile independently with `tsc --strict --exactOptionalPropertyTypes --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`. Run `node dist/FILE.js`. Activate each commented negative individually and check with the same flags plus `--noEmit` instead of `--outDir dist`.

### 1) **Definitions from substitution**

For the related Animal and Cat types below, use these directions. The names describe an assignment relationship; they do not insert runtime checks.

| Relationship | Direction | Reason |
|---|---|---|
| Covariant | Reader<Cat> can serve Reader<Animal> | Each Cat supplies the promised Animal members. |
| Contravariant | Writer<Animal> can serve Writer<Cat> | A consumer accepting every Animal can handle the caller's Cat. |
| Invariant | StrictCell<Cat> and StrictCell<Animal> cannot substitute either way here | Its function-property input and output impose opposing requirements under strict checking. |
| Bivariant checking | A method parameter can permit both related directions | This is a compatibility exception that can accept an unsafe substitution. |

Save as `directions.ts`.

```typescript
interface Animal { name: string }
interface Cat extends Animal { meow(): string }
const cat: Cat = { name: "Mira", meow: () => "meow" };
const animal: Animal = { name: "Other" };
interface Reader<T> { read: () => T }
interface Writer<T> { write: (value: T) => void }
const cats: Reader<Cat> = { read: () => cat };
const animals: Reader<Animal> = cats;
console.log(animals.read().name);
const acceptAnimals: Writer<Animal> = { write: value => console.log("accepted", value.name) };
const acceptCats: Writer<Cat> = acceptAnimals;
acceptCats.write(cat);
const onlyCats: Writer<Cat> = { write: value => console.log(value.meow()) };
const onlyAnimals: Reader<Animal> = { read: () => animal };
// const unsafeInput: Writer<Animal> = onlyCats; // TS2322
// const unsafeOutput: Reader<Cat> = onlyAnimals; // TS2322
```

The output is `Mira`, then `accepted Mira`. Reverse either successful direction and the required operation is no longer justified: an Animal may lack meow, while an Animal caller may supply that less demanding object to its consumer. The [primary strict-function-type explanation](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-6.html#strict-function-types) establishes parameter checking and its method exception. Reason from the caller's possible values before attaching the variance name.

### 2) **Check the actual member syntax and mutation policy**

A contract reading and writing T through strict function properties has an invariant relationship in this example. Do not infer that every writable property or method-based read/write contract receives that same checking. TypeScript permits some mutable widening that is unsound through aliases.

Save as `members.ts`.

```typescript
interface Animal { name: string }
interface Cat extends Animal { meow(): string }
const cat: Cat = { name: "Mira", meow: () => "meow" };
const other: Animal = { name: "Other" };
interface StrictCell<T> { read: () => T; write: (value: T) => void }
function cell<T>(value: T): StrictCell<T> {
  return { read: () => value, write: next => { value = next; } };
}
const catCell = cell<Cat>(cat);
const animalCell = cell<Animal>(other);
console.log(catCell.read().meow(), animalCell.read().name);
// const widenedCell: StrictCell<Animal> = catCell; // TS2322: write input is too narrow
// const narrowedCell: StrictCell<Cat> = animalCell; // TS2322: read result is too broad

interface Box<T> { value: T }
const catBox: Box<Cat> = { value: cat };
const animalBox: Box<Animal> = catBox; // Accepted despite the writable field.
animalBox.value = other; // Changes the same box seen through catBox.
try { catBox.value.meow(); }
catch (error) { console.log(error instanceof TypeError ? "mutable field: TypeError" : "unexpected error"); }

interface MethodCell<T> { read(): T; write(value: T): void }
let stored: Cat = cat;
const methodCats: MethodCell<Cat> = { read: () => stored, write(value) { stored = value; } };
const methodAnimals: MethodCell<Animal> = methodCats; // Accepted by the method parameter exception.
methodAnimals.write(other);
try { methodCats.read().meow(); }
catch (error) { console.log(error instanceof TypeError ? "method input: TypeError" : "unexpected error"); }

interface ReadonlyBox<T> { readonly value: T }
const reader: ReadonlyBox<Animal> = { value: cat };
console.log(reader.value.name, Object.isFrozen(reader));
// reader.value = other; // TS2540: this view does not permit replacing the field
```

The output is `meow Other`, `mutable field: TypeError`, `method input: TypeError`, then `Mira false`. Both unsafe examples compile without casts. The plain writable box is not automatically invariant, and replacing the function-property writer with method syntax changes checking. Function properties provide the strict input/output contract demonstrated by StrictCell.

ReadonlyBox safely permits reading its value as Animal and rejects replacement through that view. It does not freeze the object or prevent mutation through every other alias. [Unsound spots](<./3.3. Unsound by design spots budgeted risks.md>) and [mutable-alias pitfalls](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by type system misunderstandings.md>) own broader examples. The [original unsoundness analysis](https://effectivetypescript.com/2021/05/06/unsoundness/) uses array mutation to expose the same substitution risk; the local field/method fixtures above verify their specific current behavior. Full method-versus-function-property reasoning belongs to [callback variance](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.2. Callback variance strictFunctionTypes and bivariance pitfalls.md>).

### 3) **Optional annotations describe a limited checking relationship**

TypeScript 4.7 introduced `out`, `in` and `in out` annotations on supported generic declarations. Out describes covariance, in describes contravariance, and in out describes invariance. Their role and historical examples are documented in [the primary 4.7 notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-7.html#optional-variance-annotations-for-type-parameters). TypeScript normally infers variance; adding keywords is not required for ordinary producer/consumer checking.

Save as `annotations.ts`.

```typescript
interface Animal { name: string }
interface Cat extends Animal { meow(): string }
type Producer<out T> = () => T;
type Consumer<in T> = (value: T) => void;
interface State<in out T> { get: () => T; set: (value: T) => void }
const cat: Cat = { name: "Mira", meow: () => "meow" };
const makeCat: Producer<Cat> = () => cat;
const makeAnimal: Producer<Animal> = makeCat;
const takeAnimal: Consumer<Animal> = value => console.log(value.name);
const takeCat: Consumer<Cat> = takeAnimal;
console.log(makeAnimal().name);
takeCat(cat);
let stored = 1;
const state: State<number> = { get: () => stored, set: value => { stored = value; } };
state.set(2);
console.log(state.get());
// interface WrongOutput<out T> { write: (value: T) => void } // TS2636
// interface WrongInput<in T> { read: () => T } // TS2636
interface MethodOutput<out T> { write(value: T): void } // Accepted: the method exception still matters.
```

The output is `Mira`, `Mira`, then `2`. The wrong function-property annotations produce TS2636. The method form is accepted, so “a consuming use under out always errors” would be false. An annotation is not a general runtime safety mechanism or a way to make arbitrary object shapes behave nominally.

Annotations are consulted in comparisons between instantiations in specific circumstances; they do not rewrite structural comparisons. The [current primary guidance](https://www.typescriptlang.org/docs/handbook/2/generics.html#variance-annotations) recommends using them only for a specific need, matching structural behavior. [Generic variance annotations](<../../../08 Generics Deep Dive/sections/3. Variance and Advanced Generic Patterns/3.1. Variance in out annotations and generic positions.md>) owns that comparison boundary and the detailed diagnostic workflow. Keep a correct structural definition first, rather than treating an annotation as a replacement for it.

### 4) **Common confusion**

The assignment direction is about substituting a whole contract, not whether Cat is “more capable” in isolation. More specific output can fulfill a broader promise, while a narrower input demand cannot fulfill a caller allowed to supply broader values.

Mutability does not imply that TypeScript enforces invariance everywhere. A writable field or bivariant method can permit an unsafe widened alias. Readonly means a restriction through that view, not a snapshot or runtime freeze. Distinguish the sound relationship you want from the checking behavior the actual syntax provides.

### 5) **Performance note**

These interfaces and variance annotations erase. The getter/setter callbacks, writes, shared references and method calls remain. The examples measure checking acceptance and runtime failures, not checker timing. Inference is already part of TypeScript's variance machinery; no claim that every unannotated assignment re-walks all members follows from these tests. Use [diagnostics and traces](<../../../19 Performance Project References and Scaling/sections/1. Check-Time Performance/1.1. Measuring with extendedDiagnostics and traces.md>) before investigating a real checking bottleneck.

### 6) **Mentor note**

Ask who can supply the other Animal and who requires meow before choosing an assignment direction. Then compare the two rejected StrictCell assignments with the accepted Box and MethodCell widenings. A sound explanation identifies the exact input/output operation or method exception, not merely a label such as “mutable means invariant.”

For a repair exercise, replace MethodCell's write method signature with a function-property signature and recheck its widening. It should fail at assignment, before the other Animal can enter the Cat cell through that view. Explain why the same change has no automatic runtime transformation: it changes checking of the existing operations.
