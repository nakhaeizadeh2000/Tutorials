## 3.1. Covariance, contravariance, and invariance — who varies which way

### 1) **Definitions** (covariant: same direction; contravariant: opposite; invariant: neither)

**Variance** describes how a generic's subtyping direction relates to its type argument's subtyping. Given `Dog ≤ Animal` (Dog is subtype of Animal):

| Variance | Generic direction | Example |
|---|---|---|
| **Covariant** (`out`) | Same: `Dog ≤ Animal` → `F<Dog> ≤ F<Animal>` | `ReadonlyArray<Dog> ≤ ReadonlyArray<Animal>`; return types |
| **Contravariant** (`in`) | Opposite: `Dog ≤ Animal` → `F<Animal> ≤ F<Dog>` | `(x: Animal) => void ≤ (x: Dog) => void` (parameter position) |
| **Invariant** (`in out`) | Neither: `F<Dog>` incomparable with `F<Animal>` | `MutableBox<T> = { value: T }` (reads + writes) |
| **Bivariant** | Both (unsound, legacy) | Method shorthand `m(x: Animal)` still bivariant |

### 2) **Where each appears** (returns are covariant; function parameters are contravariant — but methods remain bivariant for compat)

| Position | Variance | Why |
|---|---|---|
| `() => T` return | Covariant | If you expected `Animal` and get `Dog`, safe — `Dog` has Animal's members |
| `(x: T) => void` param | Contravariant | If caller will pass `Dog`, a handler accepting `Animal` is safe (wider), not narrower |
| `{ value: T }` with read+write | Invariant | Must be exact — reads covariantly, writes contravariantly; only exact match is safe |
| `class Box<out T> { readonly value: T }` | Covariant via `out` | Read-only use → same direction |

Explicit annotations (TypeScript 5.8+) let you *declare* intent and the checker validates variance:

```typescript
// Covariant (out): only produces T (e.g., readonly container)
type ReadonlyBox<out T> = { readonly value: T };
// Contravariant (in): only consumes T (e.g., writer)
type Writer<in T> = { write(value: T): void };
// Invariant: both produces and consumes
type MutableBox<in out T> = { value: T };
```

### 3) **How to reason without memorization** (substitution test)

Ask: "Can I substitute `F<Dog>` where `F<Animal>` is expected without breaking safety?"

- Producer `() => Dog` where `() => Animal` expected → safe (produces more specific) → covariant.
- Consumer `(Animal) => void` where `(Dog) => void` expected → safe (consumer accepts wider) → contravariant.

If both directions fail, invariant.

---

### 4) **Runnable example** — variance in practice (good + bad)

```typescript
// good — covariant readonly, safe to widen
type ReadonlyBox<out T> = { readonly value: T };
declare let dogBox: ReadonlyBox<string & { __brand: "Dog" }>;
type Animal = string; // simplified
// ReadonlyBox<Dog> ≤ ReadonlyBox<Animal> is safe: you only read Dogs as Animals
declare let animalBox: ReadonlyBox<Animal>;
animalBox = dogBox as unknown as ReadonlyBox<Animal>; // widening via readonly — safe

// bad — invariant mutable box collapses covariance
type MutableBox<T> = { value: T };
declare let dogs: MutableBox<string & { __brand: "Dog" }>;
declare let animals: MutableBox<Animal>;
// dogs = animals; // error if invariant (correct) — writing Animal into Dog box breaks Dogs
// animals = dogs; // also error — reading Dog from Animal box may lack Dog members
// But plain Array<T> is treated covariantly (unsound) — see [3.3. Unsound spots](<./3.3. Unsound by design spots budgeted risks.md>)

// good — explicit variance catches mistakes at declaration time, not at use
// type WrongBox<out T> = { write(value: T): void }; // error TS2717: 'T' is declared 'out' but used in invariant position
// fix: invariant
type CorrectBox<T> = { write(value: T): void; read(): T }; // implicit invariant via read+write
```

### 5) **Common confusion**

- "`Array<T>` is invariant" — wishful thinking, but TypeScript treats it as *covariant* for historical usability (see [3.3. Unsound spots](<./3.3. Unsound by design spots budgeted risks.md>)). `readonly T[]` is the covariant-safe variant.
- "`in`/`out` affect runtime" — they are type-only annotations; erased after checking. Runtime still sees `Box` as a plain object.
- "Variance annotations are required" — optional; TypeScript infers variance per member when you omit them. Annotate only when inference would be wrong or when documenting intent for a library.

### 6) **Performance note**

Explicit variance allows the checker to short-circuit subtyping comparison: if a generic is declared `out T`, checking `Box<Dog> ≤ Box<Animal>` requires no deep member walk — just check `Dog ≤ Animal` once. Inferred variance requires re-walking the generic's structure per use.

### 7) **Mentor note**

Don't start with formalism; start with "which direction is safe to substitute?" and derive `in`/`out`. Once students see return = covariant, parameter = contravariant, the method-bivariance exception (see next leaf [3.2. Function variance](<./3.2. Function variance and strictFunctionTypes.md>)) feels like a named exception, not a mystery. Exercise: given `type Handler<in T> = (value: T) => void`, ask which handler can be passed to which caller.
