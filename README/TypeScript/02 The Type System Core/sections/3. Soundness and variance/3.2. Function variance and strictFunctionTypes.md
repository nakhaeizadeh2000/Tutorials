## 3.2. Function variance and strictFunctionTypes

### 1) **Strict function types**

A callback slot that may receive any `Animal` cannot safely hold a function requiring a `Dog`: the caller might supply an animal without `bark`. The reverse works. A function accepting every animal can handle a caller's dog.

`strictFunctionTypes` checks this parameter substitution contravariantly for function signatures covered by the flag. It defaults to enabled under `strict`; an explicit `--strictFunctionTypes false` overrides that part of strict checking. The feature was introduced in TypeScript 2.6. Its [primary explanation](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-6.html#strict-function-types) also documents exceptions for signatures originating in method or constructor declarations.

### 2) **Why methods stay bivariant**

The method exception preserves compatibility of generic classes and interfaces such as `Array<T>`. In the related method contracts below, both assignment directions are accepted, including an unsafe one. This is a checking compromise, rather than proof that a dog-only implementation can handle every animal.

Ignoring later callback arguments is a different question. JavaScript supplies arguments that a function may ignore. A one-parameter callback can serve `forEach`, which supplies more arguments. Strict parameter-type substitution does not require the callback to declare every supplied parameter. Keep arity and the type of each consumed argument separate.

### 3) **How to use a stricter contract**

For stored or reassigned callbacks whose input relationship must be checked strictly, declare a function property such as `handle: (value: Animal) => void`. A method signature is written `handle(value: Animal): void`. Changing the contract changes checking; it does not generate an adapter or rewrite the implementation.

Use TypeScript 7.0.2 and Node.js 20.20.2. Save this complete program as `functions.mts` in an empty directory.

```typescript
// functions.mts
interface Animal { name: string }
interface Dog extends Animal { bark(): string }
const dog: Dog = { name: "Rex", bark: () => "woof" };
const other: Animal = { name: "Other" };
const takeAnimal = (value: Animal): string => value.name;
const takeDog = (value: Dog): string => value.bark();
const dogSlot: (value: Dog) => string = takeAnimal;
console.log(dogSlot(dog));
[other, dog].forEach(value => console.log(value.name));

interface AnimalMethod { handle(value: Animal): string }
interface DogMethod { handle(value: Dog): string }
const methodDog: DogMethod = { handle: takeDog };
const methodAnimal: AnimalMethod = methodDog;
const backToDog: DogMethod = methodAnimal;
console.log(backToDog.handle(dog));
let observed = false;
try { methodAnimal.handle(other); }
catch (error) { observed = error instanceof TypeError; }
if (!observed) throw new Error("expected unsafe method failure");
console.log("method failure", observed);

interface AnimalProperty { handle: (value: Animal) => string }
interface DogProperty { handle: (value: Dog) => string }
const propertyAnimal: AnimalProperty = { handle: takeAnimal };
const propertyDog: DogProperty = propertyAnimal;
console.log(propertyDog.handle(dog));
```

```sh
tsc --strict --target ES2022 --module NodeNext --noEmitOnError --outDir dist functions.mts
node dist/functions.mjs
```

Output:

```text
Rex
Other
Rex
woof
method failure true
Rex
```

The ordinary safe assignment accepts a dog and only reads its name. `forEach` similarly accepts a callback that ignores index and array arguments. The method assignment, however, gives callers an `AnimalMethod` view of the dog-only implementation. Its call with `other` produces the caught TypeError. Both method assignment directions pass; the actual implementation did not gain `bark` on its input.

Append each independent probe to the working program, compile, and restore before the next:

```typescript
const animalSlot: (value: Animal) => string = takeDog;
```

```typescript
const unsafeProperty: AnimalProperty = { handle: takeDog };
```

Each reports TS2322. This separate call reports TS2345:

```typescript
[other, dog].forEach((value: Dog) => console.log(value.bark()));
```

The problem is its narrow element type, not an omitted index parameter. To observe what disabling the flag permits, instead append the following two lines and compile with the same command plus `--strictFunctionTypes false`:

```typescript
const unsafeSlot: (value: Animal) => string = takeDog;
console.log(unsafeSlot(other));
```

Compilation succeeds, but emitted execution exits nonzero with an uncaught TypeError. Run this failure separately from the working example. Restore the original afterward. A useful repair must accept and handle the caller's actual inputs, or restrict the consumer so it only supplies dogs. An assertion does neither.

### 4) **Common confusion**

A function capable of accepting more kinds of input is suitable for a narrower caller. A function requiring more capabilities is not suitable for a broader caller. Explain who supplies `other` and who attempts `bark` before naming the direction.

Method syntax in an object implementation does not by itself mean every surrounding function-property contract becomes loose. The relevant signature origin and receiving contract matter. The [callback application](<../../../05 Functions and Callable Types/sections/3. Advanced Callable Patterns/3.2. Callback variance strictFunctionTypes and bivariance pitfalls.md>) checks method/property assignments and contextual implementations in detail. Neither syntax nor this flag proves all program behavior safe.

### 5) **Performance note**

This flag changes static checking, not the emitted callback body. Interface and callable types erase; actual calls, array iteration and object creation remain. No compiler-speed benefit was measured for replacing callbacks with loops. Choose an iteration form for its semantics and clarity; investigate a demonstrated checker bottleneck separately.

### 6) **Mentor note**

Ask the learner to draw the flow from `other` to `methodAnimal.handle` to `takeDog`. Then predict the equivalent function-property rejection and the shorter `forEach` callback's acceptance. A sound explanation distinguishes signature origin, parameter-type substitution and ignored arguments instead of treating all three as the same exception.
