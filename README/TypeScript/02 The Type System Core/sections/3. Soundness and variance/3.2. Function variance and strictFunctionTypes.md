## 3.2. Function variance and strictFunctionTypes

### 1) **`strictFunctionTypes`** (enabled via `strict`: function *values* are checked contravariantly; method shorthand remains bivariant)

**Historical joint** — Before TypeScript 2.6, *all* function parameters were compared bivariantly (both directions accepted). This modeled common JavaScript patterns (`array.forEach` accepting both narrower and wider callbacks) but allowed unsound calls. `strictFunctionTypes` (included in `strict: true`) tightened the check for *function values* assigned to variables/properties, while leaving *method syntax* bivariant for compat.

| Syntax | Variance for parameters | Under `strictFunctionTypes` |
|---|---|---|
| Function value: `prop: (x: T) => void` | Contravariant | Contravariant (strict) |
| Method shorthand: `m(x: T): void` | Bivariant | Bivariant (still lenient) |

```typescript
type Handler = (animal: string) => void;
type DogHandler = (dog: string & { __brand: "Dog" }) => void;

declare let handler: Handler;
declare let dogHandler: DogHandler;

// Method remains bivariant — both directions may pass
interface Methods { m(x: string): void; }
interface DogMethods { m(x: string & { __brand: "Dog" }): void; }
// const mh: Methods = dogMethods; // may succeed even though widening is unsound — method shorthand is the escape hatch
```

### 2) **Why methods stay bivariant** (historical compatibility with JS's `Array.prototype` patterns)

Real JavaScript APIs routinely pass callbacks that are *more* specific than strictly allowed. `Array<string>.forEach((value, index, array) => ...)` style callers often pass functions that ignore later parameters — strict contravariance would reject thousands of existing call sites. To avoid a massive breaking change, method-position signatures retained bivariance. Function-value syntax (`prop: (...) =>`) was the new syntax where strictness could be introduced cleanly.

### 3) **How to be safe** (prefer function-value syntax `prop: (x: T) => void` over method `prop(x: T): void` when variance matters)

Modern guidance — when writing an interface/type for a callback or handler that will be *assigned* rather than called internally:

- Use *property* syntax: `onEvent: (value: T) => void` → checked strictly.
- Avoid *method* shorthand when the parameter type is meant to be contravariantly enforced.

This is especially relevant for event emitters, middleware handlers, and repository callbacks (see forward to [07 Unions and Narrowing](../../07 Unions Intersections and Narrowing/README.md) for narrowing handlers).

### 4) **Runnable example** — strict function-value vs lenient method (good + bad)

```typescript
// good — property syntax is strictly checked (error correctly raised under strictFunctionTypes)
type Animal = string;
type Dog = string & { __brand: "Dog" };
type HandlerValue = { handle: (animal: Animal) => void }; // property: contravariant
declare let handleAnimal: HandlerValue;
const handleDogValue: HandlerValue = { handle: (d: Dog) => {} };
// handleAnimal = handleDogValue; // actually, the reverse: verify direction
// Correct direction test: Handler<Dog> should NOT be assignable to Handler<Animal> under strict
type HandleDog = { handle: (d: Dog) => void };
// handleAnimal = handleDog as HandleDog; // error under strictFunctionTypes: (Dog → void) not assignable to (Animal → void)
// Reason: if caller passes generic Animal to handleAnimal.handle, but implementation expects Dog, it will access Dog-only members

// bad — method shorthand silently passes (unsound) even under strict
interface HandlerMethod { handle(animal: Animal): void; }
interface HandleDogMethod { handle(d: Dog): void; }
declare let methodAnimal: HandlerMethod;
declare let methodDog: HandleDogMethod;
// methodAnimal = methodDog; // may pass without error (method bivariance) — unsound: caller passes Animal, implementation reads Dog-only brand
// At runtime, methodDog.handle expects a branded Dog string but receives plain Animal — mis-typed access

// fix: use property syntax for handlers that will be reassigned
type SafeHandler = { handle: (animal: Animal) => void }; // property → error correctly surfaces
// SafeHandler prevents the unsound assignment from compiling — fail fast
```

### 5) **Common confusion**

- "Enabling `strictFunctionTypes` fixes all unsound parameter variance" — it fixes *function values*; method shorthand remains bivariant by design. Don't assume a method parameter is strictly checked.
- "`as` fixes the variance error" — `as` silences the check without fixing the underlying unsoundness; the runtime still receives the wrong shape.
- "`strict` already covers this" — `strict` enables `strictFunctionTypes`, but only the next leaf's array covariance remains regardless of `strict` (see [3.3.](<./3.3. Unsound by design spots budgeted risks.md>)).

### 6) **Performance note**

`strictFunctionTypes` checks parameters contravariantly, which can add up when a high-order function is called with many callback sites (e.g., `array.map((x: Specific) => ...)` where `Specific ≤ Expected`). Each call's parameter compatibility is rechecked. Prefer `for (const x of array)` with `const x` narrow over chained `map` with per-element callback type assertions to reduce redundant variance checks.

### 7) **Mentor note**

Live-demo the two syntaxes sharing the same type signature but behaving differently under `tsc --strict`: property vs method. Students who see the same `(x: T) => void` type pass in the method case but fail in the property case finally understand that *syntax* selects variance checking, not just the types. Exercise: given `interface A { m(x: string) }` vs `type B = { m: (x: string) => void }`, ask "which assignment is stricter?".
