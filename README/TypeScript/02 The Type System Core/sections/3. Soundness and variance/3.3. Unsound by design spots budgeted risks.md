## 3.3. Unsound by design spots — budgeted risks

### 1) **Array covariance**

A sound static model would ensure that accepted operations preserve the types it promises. TypeScript makes some compatibility compromises for JavaScript usage, so even strict checking does not prove that every value will match its static type. The [primary compatibility reference](https://www.typescriptlang.org/docs/handbook/type-compatibility.html#a-note-on-soundness) states this design boundary.

One example is assigning `Dog[]` to `Animal[]`. Reading each dog as an animal is safe, but a mutable animal view also permits inserting an animal without `bark`. Both variables then observe the same changed array. A readonly parameter can prevent that callee from inserting through its view. It cannot repair prior corruption, freeze the array or stop another mutable alias.

### 2) **Any and assertions are unchecked assumptions**

`any` allows unchecked operations and can propagate through subsequent expressions. It is not literally assignable to every type: an ordinary `any` value cannot be assigned to `never`. A type assertion instead tells the checker to treat a particular expression as the stated type, subject to the assertion rules. It neither converts nor validates the value. A double assertion can bypass a compatibility check without involving `any` at all.

`unknown` prevents operations that require information not yet established. It does not force a program to execute validation: the program may ignore the value, return it as unknown or assert past the restriction. Its benefit is making the need for evidence visible before ordinary typed use. Keep unchecked assumptions near a boundary whose contract can be reviewed.

### 3) **Predicates require implementation evidence**

A declared type predicate lets callers narrow a value based on its boolean result. TypeScript does not prove that its implementation establishes every member of the promised type. Checking only “non-null object” is insufficient to promise a string `text` field. That incomplete check can lead to an accepted call that throws.

[Dan Vanderkam's original analysis](https://effectivetypescript.com/2021/05/06/unsoundness/) groups assertion, lookup, declaration and alias risks. Its useful teaching method is to connect an accepted static claim with a concrete runtime counterexample. The following local fixture checks three such boundaries on the current compiler; it is not a complete inventory of all unsound behavior.

Use TypeScript 7.0.2 and Node.js 20.20.2. Save `risks.mts` in an empty directory. `expectTypeError` verifies the intentional failures so they do not terminate the rest of the demonstration.

```typescript
// risks.mts
function expectTypeError(label: string, action: () => void): void {
  try { action(); }
  catch (error) {
    if (error instanceof TypeError) { console.log(label, "TypeError"); return; }
    throw error;
  }
  throw new Error(`${label}: expected TypeError`);
}
interface Animal { name: string }
interface Dog extends Animal { bark(): string }
const dogs: Dog[] = [{ name: "Rex", bark: () => "woof" }];
const reader: readonly Dog[] = dogs;
const animals: Animal[] = dogs;
animals.push({ name: "Other" });
expectTypeError("mutable alias", () => {
  for (const dog of dogs) console.log(dog.bark());
});
console.log("reader length", reader.length);

const unchecked: any = "wrong";
const numberValue: number = unchecked;
expectTypeError("any", () => { numberValue.toFixed(1); });
const asserted = "wrong" as unknown as number;
expectTypeError("assertion", () => { asserted.toFixed(1); });

interface Text { text: string }
function isTextIncomplete(value: unknown): value is Text {
  return typeof value === "object" && value !== null;
}
function isText(value: unknown): value is Text {
  return typeof value === "object" && value !== null &&
    "text" in value && typeof value.text === "string";
}
const malformed: unknown = {};
if (isTextIncomplete(malformed)) {
  expectTypeError("predicate", () => { malformed.text.toUpperCase(); });
}
console.log("checked", isText(malformed), isText({ text: "hello" }));
```

```sh
tsc --strict --target ES2022 --module NodeNext --noEmitOnError --outDir dist risks.mts
node dist/risks.mjs
```

Output:

```text
woof
mutable alias TypeError
reader length 2
any TypeError
assertion TypeError
predicate TypeError
checked false true
```

The readonly reader was created before mutation and still sees the inserted element. It is a view of the same array, not a validated snapshot. The unchecked number cases preserve the original string at runtime. The incomplete predicate admits `{}`, whose absent `text` then causes the fourth observed TypeError. The complete predicate rejects that input and accepts the required string field. This small predicate is a field-shape example, not a general schema validator for hostile objects or account permissions.

Append each independent negative probe, compile and restore the original before the next:

```typescript
reader.push({ name: "Other" });
```

```typescript
const raw: unknown = "wrong";
raw.toFixed(1);
```

```typescript
const impossible: never = unchecked;
```

The diagnostics are TS2339, TS18046 and TS2322 respectively. They establish three distinct checking restrictions; none modifies the runtime values.

### 4) **Common confusion**

Strict mode leaves deliberate assumptions and compatibility exceptions. In addition to the examples here, an unchecked indexed lookup can return an absent value, a declaration can misdescribe its provider, and a callback can mutate a property that was previously narrowed. These have their own [index-access](<../../../15 Strictness Errors and Validation/README.md>), [declaration](<../../../12 Modules Namespaces and Declaration Files/README.md>) and [callback](<../../../05 Functions and Callable Types/README.md>) owners. Do not interpret this lesson's three themes as an exhaustive safety checklist.

A brand's meaning also needs a construction policy; a prefix check proves only the chosen prefix contract, not a phantom runtime member or authorization. Readonly restrictions and variance annotations likewise have bounded roles. Follow the [variance owner](<./3.1. Covariance contravariance and invariance who varies which way.md>) rather than assuming every mutable shape can be made safe by a keyword.

### 5) **Performance note**

Readonly types, assertions and interfaces erase. The example's iteration, string operations and predicate checks remain. Copying accepted values or validating external data can add runtime work; skipping that work changes the guarantee. No checker-speed benefit or general performance ranking was measured for these type forms.

### 6) **Mentor note**

Ask which existing assumption each operation can invalidate: a wider mutable array alias, an unchecked input, or an incomplete predicate. Require a failing input and a repair matched to the risk. Replacing a write-capable parameter with a readonly view limits that callee; validating and copying input establishes a different boundary. Counting assertions alone does not establish either guarantee.

For practice, replace the incomplete predicate's body with the checked body's logic. Explain why its conditional no longer reaches the expected-failure call for `{}`. Then design malformed field cases that would catch a future regression, rather than testing only successful input.
