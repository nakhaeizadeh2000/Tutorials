## 1.2. Excess property checks and freshness

### 1) **Freshness is the exception**

An object type usually describes required operations rather than an exact inventory of properties. At a directly checked object literal, TypeScript also checks for unexpected properties. This excess-property check catches a likely mistake where it is introduced: `portt` probably meant `port`.

“Freshness” is a useful name for that additional literal-site check. It is a compiler check, with a nonzero exit when it reports an error. It is not runtime validation and does not make all future values exact. The [object-types reference](https://www.typescriptlang.org/docs/handbook/2/objects.html#excess-property-checks) contrasts literal and variable flow.

### 2) **When freshness does not apply**

Use TypeScript 7.0.2 and Node.js 20.20.2. Save this complete program as `freshness.mts` in an empty directory.

```typescript
// freshness.mts
interface Options { host: string; port?: number }
function endpoint(options: Options): string {
  return `${options.host}:${options.port ?? 3000}`;
}
const uncheckedAtCreation = { host: "localhost", portt: 5432 };
console.log(endpoint(uncheckedAtCreation));
console.log(endpoint({ ...uncheckedAtCreation }));

const reviewed = { host: "localhost", port: 5432 } satisfies Options;
console.log(endpoint(reviewed));
function keep<T extends Options>(value: T): T { return value; }
const extended = keep({ host: "localhost", port: 8080, label: "local" });
console.log(endpoint(extended), extended.label);
```

```sh
tsc --strict --target ES2022 --module NodeNext --noEmitOnError --outDir dist freshness.mts
node dist/freshness.mjs
```

Output:

```text
localhost:3000
localhost:3000
localhost:5432
localhost:8080 local
```

The first variable supplies the required `host`, and `port` is optional. Its extra `portt` property remains in the object but is never read by `endpoint`. The spread also carries that property without reporting it as an explicitly written excess member. Both calls therefore use the implemented default, 3000.

The `satisfies` expression checks the correct literal against `Options` while retaining its inferred expression type. The generic call permits a richer value and returns that richer type. This can be a useful API contract; it also means a generic constraint alone is not a universal typo detector.

### 3) **How to diagnose**

Append each independent probe below to the original program and run the same compiler command. Restore the original between probes. The first three each report TS2561, suggesting `port`:

```typescript
endpoint({ host: "localhost", portt: 5432 });
```

```typescript
endpoint({ ...uncheckedAtCreation, portt: 5432 });
```

```typescript
const rejected = { host: "localhost", portt: 5432 } satisfies Options;
```

The second probe matters: using spread does not disable checks for properties written directly beside it. Diagnose which properties were introduced by spread and which were explicitly written. A return literal checked against an annotated return type also receives the check.

A variable is not guaranteed to pass either. This separate probe reports TS2559 because the target has only optional properties and the source shares none:

```typescript
interface OptionalOptions { port?: number }
const typoOnly = { portt: 5432 };
const weak: OptionalOptions = typoOnly;
```

Removing the excess-property check also does not remove required-member checking. This separate variable probe reports TS2741:

```typescript
const missingHost = { port: 5432 };
endpoint(missingHost);
```

Fix a typo at construction, using an annotation or `satisfies` when a configuration should be reviewed there. If extra properties are intentional, document the richer input or provide an appropriate open-property contract. Avoid adding an index signature merely to hide a spelling mistake. `exactOptionalPropertyTypes` governs optional-property assignments; `noPropertyAccessFromIndexSignature` governs access syntax. Neither makes arbitrary objects exact.

### 4) **Common confusion**

An assertion such as `value as Options` is not a validation step. It can bypass the useful creation-site check, but it does not disable every type check or delete extra fields. Prefer fixing the value or its intended contract. Checking an existing variable with `satisfies` is also different from checking a new literal: it does not retroactively restore the literal's creation-site excess-property check.

For external data, decide separately whether extra keys should be accepted, ignored or rejected by an actual validator. A compiler diagnostic about a source literal cannot inspect JSON arriving after the program starts.

### 5) **Performance note**

Excess-property checks run in the checker; they add no runtime property-filtering code. The spread in the example does create a shallow copy because it is JavaScript syntax. An annotation or `satisfies` does not create that copy. No fixed complexity or editor-latency guarantee follows from the name “freshness.”

### 6) **Mentor note**

Ask the learner to predict the difference between `{ ...uncheckedAtCreation }` and `{ ...uncheckedAtCreation, portt: 5432 }` before compiling. Then ask why the accepted first call uses 3000. A strong explanation identifies literal-site checking, the optional target member and the actual property read; it does not treat an accepted object as validated input.
