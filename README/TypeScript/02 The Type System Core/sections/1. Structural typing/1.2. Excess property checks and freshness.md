## 1.2. Excess property checks and freshness

### 1) **Freshness is the exception** (a fresh object literal checked directly against a target gets an extra "unknown property" check)

**Definition** — TypeScript applies an extra *excess property check* (also called "freshness" or "strict object literal check") only when a *fresh* object literal is directly assigned to a target type, passed as an argument, or returned. It reports known properties that the target doesn't declare — a heuristic for typos.

```typescript
type Point = { x: number; y: number };

// Fresh literal directly → extra check triggers
// const p: Point = { x: 1, y: 2, z: 3 }; // error TS2353: Object literal may only specify known properties, and 'z' does not exist in type 'Point'

// But freshness does not change the core assignability relation — see next section
```

This error is *not* a failure of structural subtyping (`{ x, y, z }` is still structurally assignable to `{ x, y }`). It's an additional lint that fires only on fresh literals.

### 2) **When freshness doesn't apply** (assigning through an intermediate variable, spread, or non-literal — excess members are silent)

Freshness evaporates the moment the literal travels through an intermediate binding, a spread, or a type assertion:

```typescript
type Point = { x: number; y: number };

// Through variable — no freshness → silent
const withExtra = { x: 1, y: 2, z: 3 };
const p1: Point = withExtra; // ok — width subtyping (extra members ignored)

// Spread — no freshness → silent
const p2: Point = { ...withExtra, x: 1 }; // ok

// Assertion — freshness disabled
const p3: Point = { x: 1, y: 2, z: 3 } as Point; // ok (but now you've disabled the typo guard for that line)
```

Senior note: prefer the *variable* path only when you *intend* to carry extra members. If you wanted the guard, keep the literal fresh.

### 3) **How to diagnose** ("Object literal may only specify known properties" means freshness triggered — not a structural failure)

When you see `Object literal may only specify known properties and 'X' does not exist in type 'Y'`, ask:

- Is the source a fresh `{ ... }` directly at the assignment/pass/return site? → That's the freshness lint — fix a typo or switch to a non-fresh path if extra members are intentional.
- Is the source a variable/spread/assertion? → The error won't appear; excess members silently pass (which may hide a typo downstream).

Modern guidance — treat the freshness error as a *warning*, not a proof that types are nominal. Don't rely on it for safety; use `exactOptionalPropertyTypes` and `noPropertyAccessFromIndexSignature` where precision matters (see forward to [13 Configuration](../../13 Configuration and Compiler Options/README.md)).

---

### 4) **Runnable example** — freshness triggers vs escapes (good + bad)

```typescript
type Options = { host: string; port?: number };
function connect(opts: Options): void {}

 // good — fresh literal with typo caught by freshness
// connect({ host: "localhost", portt: 5432 }); // error TS2353: 'portt' does not exist — caught!

// bad — freshness accidentally bypassed, typo leaks silently
const opts = { host: "localhost", portt: 5432 }; // no freshness — object is not a literal at the call site
connect(opts as Options); // ❌ no error here — typo survives because `as` disables freshness and opts wasn't checked fresh
// At runtime, opts.port is undefined, portt is ignored — connection falls back to undefined port.

// fix — keep literals fresh for validation, or type the intermediate variable
const goodOpts: Options = { host: "localhost", port: 5432 }; // typed binding catches typo immediately
connect(goodOpts); // ok

// alternative fix — spread freshness re-applies: fresh literal at return/call re-triggers check
function makeOpts(): Options { return { host: "localhost", portt: 5432 } as Options; } // loses freshness — avoid
// Prefer: function makeOpts(): Options { return { host: "localhost", port: 5432 }; } // fresh return triggers check
```

### 5) **Common confusion**

- "Excess property error means my object is not assignable" — no, it's assignable. The error is a heuristic for *literals*, not a type-system failure. The same members through a variable are assignable.
- "Freshness applies everywhere" — only literals at assignment/call/return sites. Variables, spreads, `as` assertions, and type-parameter-constrained generics bypass it.
- "I should always `as` to silence the excess error" — that silences the typo guard globally. Instead, type the variable or fix the literal.

### 6) **Performance note**

Freshness checking is cheap (O(k) where k is literal member count). It doesn't affect emit or language-server performance. The cost comes from *working around* it with extra intermediate variables that then materialize extra types in the hover graph — negligible for most repos.

### 7) **Mentor note**

Demonstrate the three-way comparison in one code block: fresh literal → error, variable → silent, `as` → silent. Students who see all three side-by-side stop treating "excess property" as a nominal-vs-structural claim and recognize it as a literal-site lint. Exercise: given `const x = { a: 1, b: 2, typoC: 3 }; f(x)`, ask whether `f` sees the typo — answer: no, freshness doesn't apply.
