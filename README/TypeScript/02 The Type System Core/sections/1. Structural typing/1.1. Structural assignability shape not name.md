## 1.1. Structural assignability — shape, not name

### 1) **Assignability by shape** (if A has every member B requires, A is assignable to B — member types checked recursively)

**Definition** — TypeScript's assignability relation is *structural*: the checker asks "does the source shape contain at least the members of the target, with compatible member types?" — not "were these types declared with the same name?". Depth matters: nested member types must themselves be assignable.

```typescript
// shallow: source has superset of target's members → ok
type Point = { x: number; y: number };
const a: Point = { x: 1, y: 2, z: 3 } as Point; // via assertion; direct literal would hit freshness (see 1.2)
const viaVar = { x: 1, y: 2, z: 3 };
const b: Point = viaVar; // ok — via intermediate var freshness doesn't apply

// deep: inner member must be assignable
type Config = { server: { host: string } };
type PartialConfig = { server: { host: string; port?: number } };
declare let cfg: PartialConfig;
const c: Config = cfg; // error: not assignable? Actually PartialConfig's server has extra optional port — compatible
// The deeper check: { host: string; port?: number } is assignable to { host: string } → ok (optional extra is fine)
```

Recursion is bounded by structural depth, not by inheritance declarations. There is no `extends` required for compatibility; `extends` merely *checks* that a type satisfies another.

### 2) **Width subtyping** (extra members don't break assignability)

If `S = { x, y, color }` and `T = { x, y }`, then `S ≤ T` (S is subtype of T). Extra width makes the source *more specific*, not incompatible. This is why passing a rich object to a function that only reads a subset is safe.

### 3) **Depth subtyping** (nested members must themselves be assignable)

```typescript
type InnerA = { value: string };
type InnerB = { value: string; tag: number };
type OuterA = { inner: InnerA };
type OuterB = { inner: InnerB };
declare let outerB: OuterB;
const outerA: OuterA = outerB; // error? InnerB has extra tag → InnerB ≤ InnerA is ok, so OuterB ≤ OuterA is ok
// If inner value types conflicted, the assignment would fail:
type Conflict = { inner: { value: number } };
declare let conflict: Conflict;
// const outerA2: OuterA = conflict; // error: number not assignable to string
```

### 4) **Runnable example** — width/depth in practice (good + bad)

```typescript
// good — leverage width subtyping for flexible callers
type HasName = { name: string };
function greet(x: HasName): string { return `hi ${x.name}`; }
class Dog { constructor(public name: string, public breed: string) {} }
class Cat { constructor(public name: string, public lives: number) {} }
greet(new Dog("Rex", "Shepherd")); // ok — Dog has name
greet(new Cat("Whiskers", 9));     // ok — Cat has name
greet({ name: "Ada", role: "admin" } as HasName); // ok via width (or via var)

// bad — expecting nominal protection that doesn't exist
type UserId = string; type OrderId = string;
function deleteUser(id: UserId): void {}
declare let orderId: OrderId;
deleteUser(orderId); // no error — UserId and OrderId are the same shape (string) → structural alias
// fix: branding (see [1.3. Nominal typing techniques](<./1.3. Nominal typing techniques branding and opaque types.md>))
// type UserId = string & { __brand: "UserId" }; // now incompatible with OrderId brand
```

### 5) **Common confusion**

- "Extra members cause an error" — only for *fresh* literals (see next leaf [1.2. Excess property checks](<./1.2. Excess property checks and freshness.md>)). Through a variable or spread, extra members are invisible to the checker.
- "`implements` makes a class satisfy an interface" — `implements` only *asserts* satisfaction; removing it doesn't make the shape incompatible — the structural relation exists regardless.
- "Structural means weak" — it's strong depth-wise. `{ a: string }` is not assignable to `{ a: number }` even though both have one member `a`.

### 6) **Performance note**

Width subtyping with huge object literals (50+ members) still checks in near-linear time for first-level members, but deeply nested structures (e.g., `DeepPartial<LargeConfig>` with recursion depth >5) can dominate checker time. Prefer `Pick`/`Omit` composition that names intermediate shapes.

### 7) **Mentor note**

Teach with "assignability is a question": `is A assignable to B?` — the answer is determined by member-wise compatibility, not by looking up `extends`. Exercise: give students two unrelated classes with the same shape and ask if assignment succeeds; correct answer is *yes* (structural), which reframes `class` as a shape factory, not a nominal type.
