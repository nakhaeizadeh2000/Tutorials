## 1.3. Nominal typing techniques — branding and opaque types

### 1) **Why nominal sometimes matters** (two `string`-based IDs that shouldn't mix)

**Definition** — In a structural system, two types with the same shape are compatible. For *identity-sensitive* domains, that's unsafe:

```typescript
type UserId = string;
type OrderId = string;
declare function getUser(id: UserId): void;
declare let orderId: OrderId;
getUser(orderId); // no error — both are string → structural alias collapses nominal intent
```

At runtime, mixing a user ID into an order lookup fails silently — wrong record or 404. The type system should distinguish them, but width-agnostic structural assignment says they're the same.

### 2) **Branding pattern** (`string & { __brand }` — intersection adds a phantom member)

Add a discriminant member that exists only in the type space (not at runtime) via intersection. Because the extra member participates in structural checks, two differently branded strings become incompatible:

```typescript
// brand as phantom member (never exists at runtime, but checker sees it)
type UserId = string & { readonly __brand: unique symbol; readonly kind: "UserId" };
type OrderId = string & { readonly __brand: unique symbol; readonly kind: "OrderId" };

// Construction requires a proving assertion (one trusted site per brand)
function makeUserId(raw: string): UserId { return raw as UserId; }
function makeOrderId(raw: string): OrderId { return raw as OrderId; }

declare function getUser(id: UserId): void;
const uid: UserId = makeUserId("u-42");
const oid: OrderId = makeOrderId("o-7");
getUser(uid);  // ok
// getUser(oid); // error TS2322: Type 'OrderId' is not assignable to type 'UserId'
```

Variants: `string & { __brand: "UserId" }` (string literal brand), `number & { __brand: "Cents" }` for numeric units. The `unique symbol` form guarantees no two brands accidentally share the same literal value.

### 3) **Trade-offs** (branding requires assertions at creation; true opaque types remain a proposal)

| Aspect | Cost |
|---|---|
| Construction needs `as Brand` per value | One trusted site per brand; audit those sites |
| Erasure means branding has zero runtime cost | Also zero runtime validation — `UserId` still accepts any string after `as` |
| Library boundary: branded types must cross `unknown` validation before branding | Validate string shape first, then `as UserId` |

Modern guidance — use branding for domain IDs, monetary units, and security tokens — roughly 5–15 brands per codebase is the common range. Don't brand every `string`; reserve it for "mixing these would be a production incident". Full opaque types (`opaque type UserId = string`) remain a TC39/TypeScript proposal, not yet stable as of September 2026 — branding is the pragmatic approximation.

### 4) **Runnable example** — nominal safety via branding (good + bad)

```typescript
// bad — unbranded alias collapses
type UserIdBad = string; type OrderIdBad = string;
function deleteUserBad(id: UserIdBad): void { /* ... */ }
declare let orderBad: OrderIdBad;
deleteUserBad(orderBad); // no error — bug ships

// good — branded: mixing fails at check time, zero runtime overhead
type UserId = string & { readonly __brand: unique symbol };
type OrderId = string & { readonly __brand: unique symbol };
function makeUserId(s: string): UserId { if (!s.startsWith("u-")) throw new Error("bad user id"); return s as UserId; }
function makeOrderId(s: string): OrderId { if (!s.startsWith("o-")) throw new Error("bad order id"); return s as OrderId; }

function deleteUser(id: UserId): void { console.log(`deleting ${id}`); }
const goodUid = makeUserId("u-123");
const badOid = makeOrderId("o-456");
deleteUser(goodUid);  // ok
// deleteUser(badOid); // error TS2322: Type 'OrderId' is not assignable to parameter of type 'UserId'
// emit (npx tsc file.ts --target es2022): function deleteUser(id) { console.log(`deleting ${id}`); } — no branding remains
```

### 5) **Common confusion**

- "Branding has runtime cost" — none. After erasure, `UserId` and `string` are both `string` at runtime; the phantom member never materializes. Cost is a single `as` at construction (see [01/2.1 Type erasure](../../01%20Fundamentals%20and%20Mental%20Model/sections/2.%20How%20TypeScript%20doesnt%20execute/2.1.%20Type%20erasure%20what%20survives%20compilation.md>)).
- "`enum` is nominal, so use it for IDs" — `enum` is non-erasable (see [01/3.3 Choosing erasable syntax](../../01%20Fundamentals%20and%20Mental%20Model/sections/3.%20Running%20TypeScript%20today/3.3.%20Choosing%20erasable%20syntax%20the%20zero-cost%20interop%20rule.md>)) and fail under native stripping; `type + brand` is erasable and strippable.
- "Branding prevents all mixing" — only within `strict` type space. `any`, `as`, and lying predicates still break it — branding is a *proof discipline*, not a vault.

### 6) **Performance note**

Branding adds no emit and negligible check time (intersection of primitive + object with one brand member = single property check). Unlike `unique symbol` runtime values, the brand member is type-only; there is no symbol allocation at runtime. Prefer `string & { __brand }` over `newtype` class wrappers that allocate objects.

### 7) **Mentor note**

Branding is best introduced after students feel the pain of a real incident (see ask: "tell me a time a wrong ID was passed"). Introduce the pattern as "one trusted constructor per domain concept" — every other file must *receive* the brand, never *forge* it. Review gate: count `as UserId` sites — should be ≤ `makeUserId` call count.
