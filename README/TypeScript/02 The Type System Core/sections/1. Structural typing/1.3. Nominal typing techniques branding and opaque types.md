## 1.3. Nominal typing techniques — branding and opaque types

### 1) **Why nominal sometimes matters**

Two aliases for `string` document intent but remain compatible. If an operation accepts only a user identifier, accidentally passing an order identifier can request the wrong domain. A brand adds a required static marker so that these otherwise compatible representations cannot flow into each other accidentally.

This does not change TypeScript into a wholly nominal language. The pattern uses structural comparison to encode a distinction. Start by identifying the mix-up that matters; different required data members may already distinguish two object types without a brand.

### 2) **Branding pattern**

A phantom brand participates in the type contract but is absent from the primitive runtime value. This example uses distinct symbol keys, whose identities are tied to their declarations, as described in the [primary symbol reference](https://www.typescriptlang.org/docs/handbook/symbols.html#unique-symbol). The declarations are used only in type positions; they need no runtime provider.

Use TypeScript 7.0.2 and Node.js 20.20.2. Save this complete program as `brands.mts` in an empty directory. Its lookups only format strings; they perform no network request or deletion.

```typescript
// brands.mts
type PlainUserId = string;
type PlainOrderId = string;
function plainLookup(id: PlainUserId): string { return `user:${id}`; }
const plainOrder: PlainOrderId = "o-7";
console.log(plainLookup(plainOrder));

declare const userKey: unique symbol;
declare const orderKey: unique symbol;
type UserId = string & { readonly [userKey]: true };
type OrderId = string & { readonly [orderKey]: true };
function parseUserId(raw: unknown): UserId {
  if (typeof raw !== "string" || !/^u-[0-9]+$/.test(raw)) {
    throw new Error("bad user id");
  }
  return raw as UserId;
}
function parseOrderId(raw: unknown): OrderId {
  if (typeof raw !== "string" || !/^o-[0-9]+$/.test(raw)) {
    throw new Error("bad order id");
  }
  return raw as OrderId;
}
function lookupUser(id: UserId): string { return `user:${id}`; }
const user = parseUserId("u-42");
const order = parseOrderId("o-7");
console.log(lookupUser(user), typeof user, order);
let rejected = 0;
for (const raw of [null, 42, "o-7", "u-", "u-1x"]) {
  try { parseUserId(raw); } catch { rejected++; }
}
if (rejected !== 5) throw new Error("parser contract failed");
console.log("rejected", rejected);

const forged = "o-7" as UserId;
console.log(lookupUser(forged));
```

```sh
tsc --strict --erasableSyntaxOnly --target ES2022 --module NodeNext --noEmitOnError --outDir dist brands.mts
node dist/brands.mjs
```

Output:

```text
user:o-7
user:u-42 string o-7
rejected 5
user:o-7
```

The first line shows the plain-alias collision. The parser then grants `UserId` after checking this lesson's exact syntax rule. It does not establish account existence, ownership or permission. The last line deliberately bypasses the parser: an assertion supplies no runtime evidence, and `lookupUser` does not repeat validation.

Append each independent probe below to the original program and compile, restoring the original between probes:

```typescript
lookupUser(order);
```

This reports TS2345 for the wrong argument. The following assignment separately reports TS2322:

```typescript
const unproved: UserId = "u-42";
```

A brand therefore prevents accidental unchecked flow while leaving explicit assertions, `any` and dishonest predicates as escape routes. The marker's compatibility distinction is not conditional on enabling `strict`, although strict checking remains the recommended baseline.

### 3) **Trade-offs**

A string-key alternative such as `string & { readonly __brand: "UserId" }` can be sufficient within a controlled codebase. Reusing the same key and tag recreates compatibility. Separate `unique symbol` declarations avoid that accidental marker collision; reusing one declaration intentionally shares its identity. Export the type and construction API consistently when several modules need the same brand.

Keep the assertion near the code that establishes the domain's invariant. A parser can accept `unknown` at an untrusted boundary, while an internal factory may accept already checked inputs. Predicates and assertion functions can also grant brands; their signatures do not prove their implementations correct. [Learning TypeScript's branding discussion](https://www.learningtypescript.com/articles/branded-types) explains that trade-off. Review the actual checks and test malformed inputs.

A phantom scalar brand preserves the primitive representation, so JSON or another untyped boundary does not carry proof of the static marker. Re-establish the contract when accepting new untrusted data. Transformations can also invalidate a semantic invariant: concatenating two valid identifiers does not automatically produce another valid identifier.

Use a brand when preventing confusion justifies the extra construction and API work. Use a runtime wrapper when behavior or runtime identity is part of the model. “Opaque type” is sometimes used for this branding pattern, but it is not a separate `opaque type` declaration syntax in this example. Do not assume a phantom brand provides secrecy or authentication.

### 4) **Common confusion**

The runtime cannot inspect `userKey` on the string to verify the brand: no such member was attached. Do not turn its type-only declaration into an executable property check. If a runtime tag is required, model and create a real value with that tag.

Counting assertions is also not proof of correct construction. A single parser can contain an incomplete check, while a reviewed factory and a reviewed deserializer may both legitimately grant the same brand. Review what each site establishes and who can bypass it.

### 5) **Performance note**

The phantom marker, type-only symbol declaration and assertion erase. The parser's string test and regular expression still execute. A runtime `Symbol()` call or wrapper construction would also execute if the program used one; this example does neither. No checker-cost formula or validation-speed comparison was measured. Choose representation from the required guarantees before measuring a real bottleneck.

### 6) **Mentor note**

Ask why `parseUserId("o-7")` throws while `lookupUser("o-7" as UserId)` runs. A sound answer identifies the parser's executed check and the assertion's lack of one. Then ask whether a valid `u-42` proves permission to access an account. The answer should separate syntax, domain identity and authorization.

For practice, require exactly three digits after `u-` and add accepted and rejected cases. Explain why changing only the type alias cannot enforce that new runtime rule.
