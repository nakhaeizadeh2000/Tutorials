## 1.1. ESM vs CommonJS and Module Resolution (node16, bundler)

### 1) **Definition** (ESM emit)

**Definition** — Module format controls emit + resolution:

- **ESM (`import`/`export`)** — static, tree-shakable, `await` at top level (`target` allows). Emit preserves `import` (with `verbatimModuleSyntax`) or transpiles per `module`.
- **CJS (`require`/`module.exports`)** — dynamic `require` callable inside function, synchronous.
- **Module resolution** — how checker finds `.ts`/`.d.ts` for an import specifier: `node16`/`nodenext` (Node's ESM-aware resolution, respects `package.json#exports` + `.js` extension), `bundler` (for Vite/webpack — lenient), legacy `node` (CJS-only) deprecated.

```jsonc
// tsconfig for modern ESM (Node 18+ / bundler)
{
  "compilerOptions": {
    "target": "es2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "esModuleInterop": true,
    "verbatimModuleSyntax": true
  }
}
// import must include .js extension even though source is .ts (nodenext rule)
import { greet } from "./greet.js";
```

```typescript
// ESM (static)
import { readFile } from "node:fs/promises";
export function hello(): string { return "hello"; }

// Dynamic import (ESM or CJS caller — lazy)
async function load(): Promise<string> {
  const { hello } = await import("./hello.js");
  return hello();
}

// CJS interop (only with esModuleInterop)
import express from "express"; // CJS lib default import requires esModuleInterop
```

### 2) **Config** (moduleResolution)

**Config choices (5.6 era):**

| `moduleResolution` | When | Behavior |
|--------------------|------|----------|
| `nodenext`/`node16` | Node apps with ESM | Respects `exports`, requires `.js` in import, checks CJS/ESM boundary |
| `bundler` | Vite, Next.js, webpack | Lenient (no `.js` required), respects `exports` |
| `node` | legacy CJS only | Deprecated — misses ESM checks |

`module` vs `moduleResolution` pairing: `module: "nodenext"` ↔ `moduleResolution: "nodenext"`; `module: "esnext"` often pairs with `bundler`. Mismatch yields false positives.

```typescript
// nodenext requires .js
import { User } from "./user.js"; // correct — even if file is user.ts
// import { User } from "./user"; // error under nodenext — use .js

// bundler allows without
import { User } from "./user"; // ok under bundler
```

### 3) **Mistake** (mixed import)

**Common mistakes:**

- Omitting `.js` extension under `nodenext` — checker error, runtime would also fail (Node requires extension).
- Mixing `require` in ESM without `createRequire` — use `import` or `await import()`.
- `allowSyntheticDefaultImports` vs `esModuleInterop` confusion — former only checks; latter emits `__importDefault` helper. Need both for CJS default import.
- Using `module: "commonjs"` while authoring `import` — emit will transpile to `require`, but resolution must match.

```typescript
// bad: mixing
import fs = require("fs"); // old TS import=require — prefer import

// bad: default import from CJS without interop flag
// import express from "express"; // error without esModuleInterop
import * as express from "express"; // alternative but clumsy

// good: enable esModuleInterop and use default
import express2 from "express";

// bad: mixed esm/cjs emit
// tsconfig: module commonjs + import("./foo.js") — .js emitted but require expected
// fix: pick one world and align module + resolution
```

### Mentor note

Standardize one pair per repo (Node app → `nodenext`+`.js`; web app → `bundler`). Re-tag PRs that import without extension as style error — mechanical, not taste.

### Performance note

`verbatimModuleSyntax` (5.0+) eliminates `import` elision surprises and keeps bundler tree-shake clean; no runtime cost, fewer emitted helpers.
