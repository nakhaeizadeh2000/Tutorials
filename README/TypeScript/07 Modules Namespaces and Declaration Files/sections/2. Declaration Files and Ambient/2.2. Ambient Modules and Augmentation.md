## 2.2. Ambient Modules and Augmentation

### 1) **Definition** (declare global)

**Definition** — *Ambient* means "type-only, no JS emit": `declare` tells checker a value exists at runtime without emitting it. *Augmentation* adds members to existing modules/globals:

- `declare global { interface Window { myApp: { version: string } } }` — extend global `Window`.
- `declare module "express" { interface Request { user?: User } }` — module augmentation.

```typescript
// ambient global augmentation (must be in a module — so ensure file has import/export)
export {}; // make file a module
declare global {
  interface Window {
    myApp: { version: string };
  }
  var CONFIG: { apiUrl: string };
}
window.myApp.version; // ok now

// ambient module: add property to Express request
import "express"; // pull in original types
declare module "express-serve-static-core" { // or "express" depending on version
  interface Request {
    user?: { id: string; name: string };
  }
}
// then middleware can set req.user, downstream reads with type

// ambient module for untyped JS
declare module "legacy-lib" {
  export function legacy(x: string): string;
}
```

`declare` forms are erased — they only add to checker's view.

### 2) **Example** (window patch)

```typescript
// patching DOM — augment lib via declare global
declare global {
  interface Document {
    startViewTransition(update: () => void): { finished: Promise<void> };
  }
}
// document.startViewTransition now typed without lib upgrade

// per-file augment: add to existing module locals
// my-augment.d.ts
declare module "./config.js" {
  export interface Config {
    debug?: boolean; // merge into Config from config.ts if interface (not type)
  }
}
// only interfaces merge — type aliases not augmentable (see 03 1.2)

// bare ambient module (without augmentation) — for .js without types
declare module "*.png" {
  const src: string;
  export default src;
}
// now: import logo from "./logo.png" works
```

Add `esModuleInterop` + `allowSyntheticDefaultImports` caveat when augmenting CJS default.

### 3) **Pitfall** (pollution)

**Pitfall — global pollution:**

- Every `declare global` affects whole program; two libraries both augmenting `Window` with same field but different types conflict.
- Augmenting `Object.prototype` globally breaks ESM isolation.
- Over-using `declare var` instead of proper `import` brings `any` into global scope.

```typescript
// bad: global var instead of env module
declare var CONFIG: any; // pollutes, any leaks
// good: typed config module
// config.ts
export const config: { apiUrl: string } = { apiUrl: process.env.API_URL! };
// import wherever needed — no global

// bad: two augmentations conflict
// app1: declare global { interface Window { app: { a: string } } }
// app2: declare global { interface Window { app: { b: number } } } // conflict if both loaded

// good: namespace your global
declare global { interface Window { myApp: { version: string; config: Config } } }

// bad: augmenting via any d.ts shim
declare module "express" { export interface Request { user: any } } // any leaks downstream
// good: precise
declare module "express-serve-static-core" { interface Request { user?: { id: string } } }
```

Keep augmentations in a single `src/types/augmentations.d.ts` file — discoverable, reviewable.

### Mentor note

Rule: augment `interface` only, never `type`. Keep one file per augmented module; PR template: "which module are you augmenting and why?"

### Performance note

Augmentation adds to checker global scope — minimal cost, but many `declare module "*.png"`-like wildcard ambients are cheap vs scanning.

### Common confusion

- "declare global works in script file" — ambient augmentation only in a *module* (file with `import`/`export`). Add `export {}` to make .d.ts a module.
