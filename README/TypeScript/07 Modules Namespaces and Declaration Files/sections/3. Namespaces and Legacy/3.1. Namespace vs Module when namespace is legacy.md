## 3.1. Namespace vs Module (when namespace is legacy)

### 1) **History** (namespace = IIFE)

**History** — `namespace` (originally `module`) predates ES6 modules (2015). It emitted an IIFE that nested objects under a global:

```typescript
// legacy namespace
namespace Utils {
  export function format(name: string): string { return name.toUpperCase(); }
  export const VERSION = "1.0";
}
// emit (before ES modules): var Utils; (function(Utils){ Utils.format = ... })(Utils||(Utils={}))
Utils.format("hi"); // "HI" — globally available if no module system used
```

Before `import`/`export`, namespaces provided file concatenation isolation (e.g., `outFile: "app.js"` concatenates). With ESM/composition, they are superseded.

---

### 2) **Modern** (prefer module)

**Modern — prefer ESM `import`/`export`:**

```typescript
// modern module — utils.ts
export function format(name: string): string { return name.toUpperCase(); }
export const VERSION = "1.0";

// consumer — tree-shakable, works with bundler/esbuild/swc correctly
import { format, VERSION } from "./utils.js";

// namespaces still allowed for d.ts shaping old global libs (jquery)
// but for app code, module is default
```

Version-feature table:

| Need | Use | Why |
|------|-----|-----|
| App code | ESM module | Tree-shake, isolatedModules |
| New lib | ESM + `.d.ts` | Consumer-friendly |
| Global script without bundler | `namespace` + `outFile` | legacy IIFE (rare) |
| Ambient d.ts for global lib | `declare namespace X` | Describes global without emit |

As of 5.6, `namespace` triggers `isolatedModules` errors when re-export confused with `verbatimModuleSyntax`; prefer modules.

---

### 3) **Bad** (namespace in new code)

**Bad patterns:**

- Using `namespace` in new ESM app — breaks `isolatedModules` single-file transpile parity, forces `outFile`, disables tree-shake.
- Mixing `namespace` and `export` in same file — confuses CJS interop.
- `namespace` augmentation for app state instead of `declare module` / `declare global`.

```typescript
// bad: namespace in modern ESM
namespace App {
  export interface Config { debug: boolean; }
}
// good: export type Config
export type Config = { debug: boolean };

// bad: namespace for grouping when export {} suffices
namespace Models {
  export type User = { id: string };
  export type Post = { id: string };
}
// good:
export type User = { id: string };
export type Post = { id: string };

// exception: keep namespace only for legacy ambient global lib
declare namespace LegacyGlobal { // d.ts only — describes window.LegacyGlobal
  function help(): void;
}
```

**Common confusion** —

- "`namespace` is an ES module" — no. It's legacy TS IIFE wrapper. ES module is `import`/`export`.

**Performance note** —

Namespace emit (`var X; (function(X){...})(X||...)`) not tree-shakable — whole namespace kept. ESM `export` allows dead-code elimination.

**Mentor note** —

Add eslint rule `no-namespace` (`@typescript-eslint`) for app code; allow in `*.d.ts` via override.
