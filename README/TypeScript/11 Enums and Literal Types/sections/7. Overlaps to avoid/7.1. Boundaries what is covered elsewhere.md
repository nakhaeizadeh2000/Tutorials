### 2) **Union algebra, narrowing, and exhaustiveness mechanics** (distributivity, discriminants, sinks) — [07 Unions, Intersections and Narrowing](<../../../07 Unions Intersections and Narrowing/README.md>)

**Definition** — set algebra (`|`/`&`), discriminated-union design, control-flow narrowing, predicate guards, and the `never`-sink mechanic live in 07 — this domain *applied* them to finite sets (union switches, discriminant-style member cases, parity proofs) without re-teaching any mechanic.

**What problem it solves / history** — 07 owns "how do unions narrow and prove?"; 11 owns "how do finite sets (enum or union) stay exhaustive?" — mechanism vs application, composed at every switch (narrow with 07's guards, sink with 07's `never`, choose the form with 11's rule).

**Modern guidance** — for narrowing/sink mechanics start at [3.2. Exhaustiveness](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>); for enum-vs-union exhaustiveness parity stay here ([3.2. Exhaustive switches](<../3. Literals and Nominal Patterns/3.2. Exhaustive switches over enums and unions.md>)).

**Runnable example** — 07 mechanic, 11 application (`tsc --strict`):

```typescript
// 07: never-sink mechanic; 11: applied to a union-as-enum switch
function assertNever(x: never): never { throw new Error(`unreachable ${String(x)}`); }
type Sig = "go" | "stop";
function act(s: Sig): number {
  switch (s) {
    case "go": return 1;
    case "stop": return 0;
    default: return assertNever(s); // 07 mechanic proving 11's finite set
  }
}
console.log(act("go")); // 1 — mechanism (07) serving application (11)
```

**Common confusion** — "parity means 11 owns sinks" — sinks *mechanically* belong to 07; 11 proves they apply *equally* to enums and unions — ownership vs parity differ.

**Performance note** — zero runtime either layer (sinks unreachable when covered); compile errors when not — shared economics, separate homes.

**Mentor note** — teach the mechanic in 07 first (unions generally), then the parity in 11 (enums specifically) — mechanism before application, always in that order.

**Cross-links** — exhaustiveness → [3.2. Exhaustiveness](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>); discriminants → [1.2. Discriminated unions](<../../../07 Unions Intersections and Narrowing/sections/1. Union Types/1.2. **Modern guidance** — for transform mechanics (mapped/conditional/infer/template) start at 09; for enum-replacement selection stay here ([2.3. Decision rule](<../2. **Runnable example** — 09 computes, 11 selects (`tsc --strict`):

```typescript
// 09: template derivation mechanic; 11: applied as the enum-replacement table
type EvB = "click" | "key";

```

**Common confusion** — "template tables belong to 11" — templates *mechanically* belong to 09; finite-domain *application* belongs here — mechanism vs application, same split as 03/07 above.

**Performance note** — derivation caches per union (09 guidance); selection costs nothing beyond it (11 guidance) — layers compose without double-counting.

**Definition** — flag *configuration* (`strict`, `isolatedModules`, `--erasableSyntaxOnly`, `verbatimModuleSyntax` — what to enable, where, and how they interact) lives in 13 — this domain cited flag *effects* (TS1294 ban, TS2748 const-enum errors, strict exhaustiveness) without owning configuration guidance.

**What problem it solves / history** — flag semantics belong with the compiler-options reference (13), not scattered across 20 domains — one home keeps `tsconfig` advice consistent as defaults evolve through TS 5.x into 6.0 (the standing reason every flag-forward exists).

**Modern guidance** — develop enums under `strict` + `isolatedModules` (all examples verified so); take configuration questions (which combination for erasable codebases? how to migrate flags incrementally?) to 13 when it lands — until then, per-leaf verification notes are authoritative.

**Runnable example** — flags change what the same enum reports (`tsc --strict`):

```typescript
// isolatedModules ON: cross-file const-enum value use errors at authorship (not customer load)
const enum Local2 { P, Q } // same-file: inlines fine on every pipeline
console.log(Local2.P.toFixed(0)); // 0 — local const enums stay safe; exported ones don't
```

**Common confusion** — "enums need special flags" — they need `strict` + `isolatedModules` (like shared code generally) plus `--erasableSyntaxOnly` where adopted — no enum-specific flag exists beyond the ban itself.

**Performance note** — flags add check-time precision at zero emit cost — the enum guidance here (anchor, sink, stamp) assumes `strict` on.

**Mentor note** — standardize team `tsconfig` on the erasable trio (`isolatedModules` + `verbatimModuleSyntax` + `--erasableSyntaxOnly` where adopted) before teaching enums — unstrict pipelines teach habits the flags later punish.
