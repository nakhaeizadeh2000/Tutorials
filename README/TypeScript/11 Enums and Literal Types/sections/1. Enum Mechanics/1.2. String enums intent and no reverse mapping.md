## 1.2. String enums — intent and no reverse mapping

### 1) **Explicit string values** (self-describing at runtime)

**Definition** — `enum Method { Get = "GET", Post = "POST" }` binds each member to an explicit string: values readable in logs, payloads, and debuggers without any lookup table. Unlike numeric enums, nothing is positional — reordering members changes zero values, and every member's runtime form is visible at its declaration.

**What problem it solves / history** — numeric codes in wire formats (`method: 1` in JSON — meaningless without the enum source) forced every log reader and API consumer to decode integers through documentation that drifted. String enums (TS 2.4) made values self-describing (`"GET"` reads everywhere) — payloads debuggable without sources, logs greppable without tables, at the cost of the reverse map numeric enums provided (next promise).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), prefer string enums over numeric wherever values cross boundaries (wire, storage, logs) — readability beats integer compactness outside hot loops. Initialize *every* member (no auto-increment exists for strings — the checker enforces explicitness). For new code without emit needs, prefer literal unions (see [2.3. Decision rule](<../2. Enums vs Erasable Alternatives/2.3. Literal unions as enums the decision rule.md>)) — string enums serve interop and readability, not greenfield modeling.

**Runnable example** — values readable without sources (good vs bad, `tsc --strict`):

```typescript
// good — wire-readable values: logs and payloads self-describe
enum Method { Get = "GET", Post = "POST" }
function call(m: Method, path: string): string { return `${m} ${path}`; }
console.log(call(Method.Get, "/a")); // GET /a — readable in every log line
console.log(JSON.stringify({ m: Method.Post })); // {"m":"POST"} — payload self-describes

// bad — numeric wire codes need the source to decode
enum NMethod { Get, Post } // 0, 1 — compact, opaque
console.log(JSON.stringify({ m: NMethod.Post })); // {"m":1} — "1" means what? (find the enum)
// fix — string values where humans or foreign systems read the bytes
```

**Common confusion** — "string enums auto-increment" — no auto-increment exists for strings (every member must initialize — the checker errors otherwise) — explicitness is enforced, not optional. "string values cost more than numbers" — bytes differ (negligible outside hot loops); debuggability differs enormously — optimize for readers unless profiling says otherwise. "string enums are just unions with emit" — unions lack *values* (`Method.Get` as a runtime reference); when call sites need the value (defaults, maps, iteration), the enum earns its emit.

**Performance note** — string comparison per use (same as literal-union comparison — no enum overhead); emit is a one-direction object (half the size of numeric reverse tables). No per-use cost beyond ordinary property reads.

**Mentor note** — show the two `JSON.stringify` outputs side by side (`{"m":"POST"}` vs `{"m":1}`) and ask which log you'd rather grep at 2am — readability wins the debate before theory begins. Rule: values crossing human or foreign boundaries are strings; transient internal codes may stay numeric.

### 2) **No reverse mapping** (string enums emit one direction only)

**Definition** — string enums emit `{ Get: "GET", Post: "POST" }` — forward only. `Method["GET"]` is *not* a reverse lookup (it errors — `"GET"` is a value, not a key); debugging a wire `"POST"` back to `Method.Post` needs an explicit inverse (hand-written map, or `Object.entries` search). The asymmetry is structural: numeric members generate both table directions, string members generate one.

**What problem it solves / history** — developers ported the numeric reverse-map idiom (`E[code] ?? "unknown"`) to string enums and got `undefined` for every input (values aren't keys) — display code that worked for numeric codes silently broke on string migration. Naming the asymmetry redirects string-enum debugging to explicit inverses (written once, typed exactly) instead of the missing reverse table.

**Modern guidance** — as of TypeScript 5.9 era, build explicit inverse maps for string enums that need value→member debugging (`Object.fromEntries(Object.entries(Method).map(([k, v]) => [v, k]))` — typed via `as const`-style derivation or a handwritten `Record<string, Method>`); better, avoid needing inverses — log the *value* (`"POST"` already reads) instead of resolving it back to the member name.

**Runnable example** — forward works, reverse needs help (good vs bad, `tsc --strict`):

```typescript
enum Method { Get = "GET", Post = "POST" }; // re-declared: each fence compiles standalone
// good — values already read: log them directly, no inverse needed
function logCall(m: Method): void { console.log(`called ${m}`); } // "called POST" — self-describing
logCall(Method.Post);

// good — explicit inverse when member names (not values) are required
const byValue = Object.fromEntries(
  (Object.entries(Method) as [keyof typeof Method, string][]).map(([k, v]) => [v, k]),
) as Record<string, keyof typeof Method>;
console.log(byValue["POST"]); // Post — one explicit inverse, typed at the boundary

// bad — numeric reverse idiom applied to string enums: undefined for every input
// const name = (Method as unknown as Record<string, string>)["POST"]; // undefined — values aren't keys
// fix — log values directly (they read); build byValue once when names are truly needed
console.log(byValue["GET"]); // Get
```

**Common confusion** — "`Method["GET"]` should reverse-lookup" — bracket access reads *keys* (`Get`/`Post`); `"GET"` is a *value* — key/value confusion, not a missing feature. "explicit inverses duplicate the enum" — derived via `Object.entries` (tracks the enum automatically) — hand-listed inverses rot; derived ones don't. "numeric-style debugging ports directly" — the whole point of string values is *not needing* the inverse — reaching for one usually means logging the wrong thing (log values, resolve names never).

**Performance note** — derived inverse costs O(members) once at module scope; per-lookup O(1) property read — identical profile to numeric reverse maps, with one explicit construction line instead of compiler magic.

**Mentor note** — run the numeric idiom against a string enum live (`undefined` for every code) — the asymmetry sticks better as a failed lookup than as a rule statement. Exercise: derive `byValue` generically (`inverseOf<T extends Record<string, string>>`) — one helper serving every string enum's debugging.

### 3) **String enums vs string unions at runtime** (when the value matters)

**Definition** — `Method.Get` is a *value* (passable as a default, usable as a computed key, iterable via `Object.values`); `"GET"` the union member is a *type only* (no runtime footprint). Code needing the value — defaults (`m = Method.Get`), maps keyed by member (`Record<Method, Handler>`), runtime enumeration (`Object.values(Method)`) — needs the enum (or an `as const` object); code needing only checking needs the union.

**What problem it solves / history** — union-only codebases re-created value needs by hand (default constants `const DEFAULT_METHOD = "GET" as Method` drifting from the union; `Object.values` over hand-mirrored arrays) — each a value/table the enum (or const object) would have supplied canonically. Naming *value needs* (defaults, keys, enumeration) as the enum's legitimate territory ends both the over-migration (enums deleted where values were needed) and the under-migration (enums kept where only checking was needed).

**Modern guidance** — as of TypeScript 5.9 era, keep string enums (or `as const` objects — see below) exactly where values are consumed: defaults, computed keys, runtime iteration, foreign interop. Everywhere else (parameters, returns, narrowing, exhaustiveness), accept the *union* (`"GET" | "POST"` — members flow into it, literals flow into it; verified above that only the reverse, literal-into-enum, errors). Prefer `as const` objects over string enums when methods/iteration plus erasability are all wanted (see [2.2. Migration map](<../2. Enums vs Erasable Alternatives/2.2. erasableSyntaxOnly the enum ban and migration.md>)).

**Runnable example** — values where needed, unions where checked (good vs bad, `tsc --strict`):

```typescript
enum Method { Get = "GET", Post = "POST" }; // re-declared: each fence compiles standalone
// good — enum supplies values (default, keys, iteration); union types the checking
function serve(m: Method = Method.Get): string { return `serving ${m}`; } // default needs the VALUE
const counts: Record<Method, number> = { [Method.Get]: 1, [Method.Post]: 2 }; // computed keys
console.log(serve(), Object.values(Method).join(","), counts[Method.Get].toFixed(0)); // serving GET GET,POST 1

// bad — union-only defaults drift from the union
type M = "GET" | "POST";
const DEFAULT_M = "GET"; // untyped string — drifts silently when M gains "DELETE"
// function serveBad(m: M = DEFAULT_M): string { return m; } // DEFAULT_M: string (widened — default unchecked)
// fix — enum (or as const object) as the value source; union as the checking type
const m2: M = "POST";
console.log(m2.toLowerCase()); // post — checking needs no value
```

**Common confusion** — "enum members and literals interchange freely" — one direction only, verified with `tsc --strict`: `Method.Get` flows *out* to `"GET"` and `string` (members are subtypes of their literals), but `"GET"` does *not* flow *in* to `Method` (error TS2322 — enums guard their boundary nominally). Consequence: APIs typed over the *union* accept both literals and members; APIs typed `Method` accept members only — design over unions by default, `Method` where enum identity matters. "`as const` objects replace enums everywhere" — replace where erasability + iteration matter; enums keep nominal member types (`Method.Get` distinct from `"GET"`) that const objects flatten — identity needs differ (see [3.3. Nominal patterns](<../3. Literals and Nominal Patterns/3.3. Nominal enum patterns branding vs enums.md>)).

**Performance note** — enum value access is a property read (same as const-object access); union checking is compile-time only — value-vs-type is a design axis with zero runtime delta between equivalent choices.

**Mentor note** — ask "where is the *value* consumed?" (defaults? keys? iteration? interop?) — any yes keeps the enum (or const object); all no migrates to union. Exercise: convert one union-only default constant to an enum-sourced default and watch the drift vector close. Review stamp: value needs are the enum's visa — no value need, no enum.
