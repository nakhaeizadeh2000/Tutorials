## 1.3. Heterogeneous, ambient, and computed members

### 1) **Heterogeneous members** (mixed string/number — legal, discouraged)

**Definition** — an enum may mix member kinds (`enum Mixed { No = 0, Yes = "YES" }`) — the checker permits it, narrowing treats each member by its own literal type, and emit stores both forms side by side. Legal since enums began; discouraged because every consumer must handle two value domains (numeric *and* string) where one would do.

**What problem it solves / history** — legacy protocols mixed codes (`0` for legacy states, `"N/A"` for the new absence marker) and a single enum *could* model both without a wrapper union — the pragmatic bridge during migrations from numeric to string codes. Outside migrations, heterogeneity doubles every consumer's reasoning (reverse-map works for the numeric half only; exhaustiveness needs both literal kinds) for zero modeling gain.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), allow heterogeneous members only as a documented migration bridge (numeric legacy + string newcomers, with a removal date); model everything else with one kind per enum — or better, a union (`0 | 1 | "N/A"` states intent more honestly than a mixed enum). Lint new heterogeneous enums (`no-heterogeneous-enums` custom rule or review convention).

**Runnable example** — bridge, not home (good vs bad, `tsc --strict`):

```typescript
// good — migration bridge: legacy numerics plus new string marker, removal dated
enum Legacy { Ok = 0, Err = 1, Unknown = "UNKNOWN" } // TODO(v2): drop numerics, use Status union
function isOk(s: Legacy): boolean { return s === Legacy.Ok; }
console.log(isOk(Legacy.Ok), Legacy.Unknown); // true UNKNOWN

// bad — permanent heterogeneity: every consumer reasons over two domains
enum Mixed { A = 0, B = "BEE" }
function describe(m: Mixed): string {
  return typeof m === "number" ? `num ${m.toFixed(0)}` : `str ${m.toLowerCase()}`;
  // each branch re-derives the kind split the enum refused to make
}
console.log(describe(Mixed.A), describe(Mixed.B)); // num 0 str bee
// fix — one kind per enum (or a union): homogeneous members, homogeneous reasoning
type Clean = 0 | 1 | "UNKNOWN"; // migration target: intent visible, no enum needed
const c: Clean = "UNKNOWN";
console.log(c.toLowerCase()); // unknown
```

**Common confusion** — "heterogeneous enums narrow like unions" — members narrow individually (each keeps its literal), but the *enum type* spans two domains — `switch` needs cases for both kinds plus the reverse-map asymmetry (numeric half reverses, string half doesn't). "mixing saves an enum" — saves one declaration, costs every consumer a kind-check — negative ROI past the first reader. "computed heterogeneity is inferred" — mixed *computed* members still need explicit values per position (next promise's const-ness rules apply per member).

**Performance note** — emit stores both forms (numeric members double-slotted with reverse entries; string members single) — heterogeneous emit is the sum of both costs. No per-use overhead beyond the kind-checks consumers write (which homogeneous enums avoid entirely).

**Mentor note** — ask "which half reverse-maps?" for any mixed enum — the asymmetric answer (numeric only) usually ends the heterogeneity debate on the spot. Exercise: convert one permanent mixed enum to a union and delete the kind-check branches it forced — branch count is the heterogeneity tax, receipt included.

### 2) **Computed members** (evaluable expressions as values)

**Definition** — members may initialize from compile-time-evaluable expressions: `Len = "hello".length` (5), `Mask = 1 << 3` (8), `Sum = A + B` (earlier members as inputs). Constant expressions keep the member *literal-typed* (usable in template/conditional positions); non-constant expressions (function calls, `Math.random()`) widen the member to its base type (`number`/`string`) and forbid followers from auto-incrementing after them.

**What problem it solves / history** — derived codes (`MAX = 1 << 16`, `PREFIX_LEN = "v1:".length`, `NEXT = PREV + 1`) previously lived as separate `const`s beside the enum — drifting when the base changed (`"v1:"` → `"v10:"` without updating `PREFIX_LEN`). Computed members co-locate derivation with declaration: the expression *is* the value's documentation, re-evaluated by the compiler on every build.

**Modern guidance** — as of TypeScript 5.9 era, compute powers/shifts (`1 << N`), lengths of stable literals, and sums of earlier members inline; keep impure computations (`Date.now()`, function calls) out of enums (they widen members and block auto-increment — assign at runtime instead). Prefer `const`-evaluable expressions so members stay literal-typed for template/conditional use.

**Runnable example** — derivation co-located (good vs bad, `tsc --strict`):

```typescript
// good — bit layout and derived lengths computed where declared
enum Flags { Read = 1 << 0, Write = 1 << 1, All = Read | Write } // 1, 2, 3 — layout visible
enum Frame { Tag = "v1:", TagLen = 3 } // literal length beside the literal (kept in sync by review)
function has(f: Flags, flag: Flags): boolean { return (f & flag) === flag; }
console.log(has(Flags.All, Flags.Read), Frame.TagLen.toFixed(0)); // true 3

// bad — impure member widens itself and blocks followers
enum Risky { At = 5, Now = Date.now() } // Now: number (widened — not the literal timestamp type)
// enum Risky2 { At = Date.now(), Next } // error TS1061 — auto-increment blocked after computed member
// fix — impure values belong at runtime (const now = Date.now()), not in the enum
console.log(Risky.At.toFixed(0)); // 5 — constant members stay precise
```

**Common confusion** — "computed members are runtime-evaluated per use" — evaluated once at emit (the *value* is inlined into the table) — `1 << 16` costs nothing per access. "any expression works" — only *constant* expressions keep literal types and permit following auto-increment; anything else widens and freezes the counter — the two-tier rule surprises once, then guides. "`All = Read | Write` is heterogeneous" — same-kind combination (numbers) — heterogeneity means mixed *kinds*, not combined members.

**Performance note** — constant expressions fold at compile time (zero runtime cost — the table holds final values); impure members evaluate once at module load (table construction) — same as hand-written consts, no enum penalty.

**Mentor note** — change `"v1:"` to `"v10:"` and ask what else must change (`TagLen` — co-located, visible, one diff) vs the separate-const design (two files, forgotten half the time). Exercise: express one magic-number pair (`MAX = 65536`) as its derivation (`1 << 16`) — intent replaces archaeology.

### 3) **Ambient enums** (describing foreign enums without emitting)

**Definition** — `declare enum Foreign { A, B }` (typically in `.d.ts`) types an enum that *someone else* emits (a JS library, a native module, generated code): all member access checks, zero bytes emitted locally. The declaration is a promise ("this shape exists at runtime") — the checker trusts it unconditionally, like all ambient declarations.

**What problem it solves / history** — untyped foreign constants (`window.STATUS_OK` as `any`, or magic numbers copied from C headers) infected call sites with `any` or wrong-typed literals that drifted from the foreign source. Ambient enums give foreign value-sets a typed local name without claiming ownership of the emit — updates mean editing the `.d.ts` mirror, and mismatches surface as type errors instead of runtime surprises.

**Modern guidance** — as of TypeScript 5.9 era, declare ambient enums only for genuinely foreign value sets (native bindings, vendored JS with enum-shaped exports, codegen-owned tables); mirror the foreign numbering *exactly* (explicit initializers — never auto-increment against someone else's table); prefer ambient *const objects* (`declare const X: { readonly A: 0 }`) when the foreign side may migrate to erasable syntax — same trust, no enum lock-in.

**Runnable example** — foreign shape, local checking (good vs bad, `tsc --strict`):

```typescript
// good — ambient mirror of a foreign table: checked locally, emitted elsewhere
declare enum Native { Ok = 0, Fail = 1 }
declare function runNative(): Native;
function ok(r: Native): boolean { return r === Native.Ok; }
// runNative() connects at runtime to foreign code; types verify the contract here
console.log(ok(Native.Ok)); // true — (foreign implementation linked at runtime)

// bad — magic numbers copied from the foreign header (drift on next vendor update)
const NATIVE_OK = 0; // mirrors Native.Ok today...
function okBad(r: number): boolean { return r === NATIVE_OK; }
// vendor renumbers Fail above Ok → NATIVE_OK still 0, meaning changed silently
// fix — declare enum: the mirror is typed (renumbering breaks assignments loudly)
console.log(okBad(0)); // true — correct result, unverified contract
```

**Common confusion** — "ambient enums emit guards" — emit nothing (the foreign side owns bytes); a missing runtime is a linker error, not a type error — ambient trust cuts both ways. "ambient and regular enums interchange" — regular enums *define* (emit + check); ambient ones *describe* (check only) — swapping them either double-emits (regular where ambient belonged) or crashes (ambient where definition belonged). "`declare const enum` is always better" — ambient `const enum` inlines *foreign* values at compile time (stale on vendor update without rebuild) — prefer plain ambient enums for versioned foreign tables.

**Performance note** — zero emit (nothing to measure); member access compiles to the same property reads as regular enums — ambient is purely a trust boundary with no runtime profile.

**Mentor note** — ask "who emits these bytes?" for every enum in interop code — foreign answer means `declare`, local answer means definition. Exercise: vendor-update drill (renumber one foreign member) — ambient mirror errors at assignments (loud), magic constants stay green (silent) — trust boundaries made tangible.
