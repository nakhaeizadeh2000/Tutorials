## 1.3. Heterogeneous ambient and computed members

Three separate choices affect an enum: which kinds of values it contains, how its member initializers are evaluated, and whether the declaration supplies a runtime definition. Keep these questions separate. A heterogeneous union still contains both value kinds, a computed member still has an enum member type on this baseline, and an ambient declaration still needs a real runtime provider.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. For mixed.ts, computed.ts and missing.ts, compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`, then run `node dist/FILE.js`. Activate their negatives individually with --noEmit instead of --outDir dist. Regular enum definitions require transformation; the ambient module project has its own commands below.

### 1) **Heterogeneous values retain their actual domains**

An enum can contain numeric and string members. Numeric members get reverse entries; string members do not. Choose this representation when the value contract actually contains both kinds and the enum API is useful, rather than inventing a migration deadline or rejecting every mixed definition. A literal union is an alternative type contract, but it does not remove the underlying distinction between a number and a string. The [primary heterogeneous-enum section](https://www.typescriptlang.org/docs/handbook/enums.html#heterogeneous-enums) presents the syntax and cautions about unnecessary mixing.

Save as mixed.ts.

```typescript
export {};
enum Mixed { No = 0, Yes = "YES" }
function describe(value: Mixed): string {
  return typeof value === "number" ? `num ${value.toFixed(0)}` : `str ${value.toLowerCase()}`;
}
console.log(describe(Mixed.No), describe(Mixed.Yes));
console.log(Mixed[0], Reflect.get(Mixed, "YES"), Object.keys(Mixed).join(","));
// describe("YES"); // TS2345: raw string is not the enum member
type Raw = 0 | "YES";
function describeRaw(value: Raw): string {
  return typeof value === "number" ? `num ${value.toFixed(0)}` : `str ${value.toLowerCase()}`;
}
console.log(describeRaw(0), describeRaw("YES"));
```

The output is `num 0 str yes`, `No undefined 0,No,Yes`, then `num 0 str yes`. Both representations need the same value-kind reasoning for these operations. The union admits the raw string while the enum API requires its member contract. If the actual domain can be simplified to one representation, simplify the data intentionally; merely changing enum syntax to a union does not do that conversion.

### 2) **Separate constant folding, runtime evaluation and member types**

A constant enum expression is a defined subset, not every expression whose result a person can predict. Bit shifts of constant operands can fold into the emitted table. A string's length property and a function call can remain runtime expressions. An uninitialized member after a runtime-computed initializer is rejected; a later explicit numeric anchor can start another automatic sequence.

Save as computed.ts.

```typescript
export {};
let calls = 0;
function nextCode(): number { calls++; return 10; }
enum Codes {
  Constant = 1 << 3,
  Length = "abc".length,
  Runtime = nextCode(),
  Anchor = 20,
  After,
}
console.log(calls, Codes.Constant, Codes.Length, Codes.Runtime, Codes.Runtime, calls, Codes.After);
// enum BadNext { Value = nextCode(), Next } // TS1061
// enum BadString { Value = String("x") } // TS18033: arbitrary string-returning computation is not a numeric computed member
// const wrongMember: Codes.Runtime = Codes.Constant; // TS2322

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type RuntimeNotPlainNumber = Expect<Equal<Equal<Codes.Runtime, number>, false>>;
type RuntimeIsNumeric = Expect<Codes.Runtime extends number ? true : false>;
```

The output is `1 8 3 10 10 1 21`; both probes compile. NextCode ran while this enum object initialized, not on either later member read and not during TypeScript compilation. Inspect dist/computed.js: Constant is assigned 8, Length still uses "abc".length and Runtime still calls nextCode(). The [primary constant-expression rules](https://www.typescriptlang.org/docs/handbook/enums.html#computed-and-constant-members) define that boundary.

The computed member does not simply become plain number. [TypeScript 5.0 made computed members participate in union enums](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#all-enums-are-union-enums), supplying their own member types. That static distinction neither makes the runtime expression pure nor proves an arbitrary incoming numeric value is a valid domain code. Keep nondeterministic or side-effecting initializers only when their initialization behavior is intended and understood; separate ordinary runtime state when enum initialization is the wrong lifecycle.

### 3) **Ambient declarations describe a provider instead of installing it**

A regular enum defines runtime output. A declare enum supplies a checker-visible description; it does not construct the object or verify that a foreign implementation matches. For a runnable local interop example, create a fresh directory with exactly the next three files and no package.json or tsconfig.json. This is a CommonJS fixture, not a native binding or an installed vendor SDK.

Save native.d.cts. This is a declaration file, not an executable program.

```typescript
export declare enum Status { Ok = 0, Fail = 1 }
export declare function run(fail: boolean): Status;
```

Save native.cjs. This JavaScript file supplies the actual runtime object and function, including the numeric reverse entries described by the enum API.

```javascript
exports.Status = Object.freeze({ 0: "Ok", 1: "Fail", Ok: 0, Fail: 1 });
exports.run = function (fail) { return fail ? exports.Status.Fail : exports.Status.Ok; };
```

Save consumer.ts.

```typescript
import { Status, run } from "./native.cjs";
const assumedZero: 0 = Status.Ok;
console.log(assumedZero, run(true) === Status.Fail, Status[Status.Fail]);
// run("yes"); // TS2345
```

Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --removeComments --target es2022 --module node16 --moduleResolution node16 --lib es2022,dom --outDir dist consumer.ts`. Then run `cp native.cjs dist/native.cjs` and `node dist/consumer.js`. The output is `0 true Fail`. No JavaScript implementation is emitted from native.d.cts. The explicit copy places the actual provider at the emitted import's relative path. The [file-extension reference](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-7.html#new-file-extensions) explains CommonJS .cjs/.d.cts pairing; the [declaration-space owner](<../../../02 The Type System Core/sections/2. The type vs value separation/2.2. Declaration spaces type value and namespace.md>) owns the general type/value distinction.

If the provider copy is omitted, this compiled consumer fails at runtime with MODULE_NOT_FOUND. A declaration does not satisfy that runtime import. A similarly missing global enum produces an ordinary JavaScript ReferenceError. Save missing.ts separately and use the first commands in this lesson:

```typescript
export {};
declare enum Missing { Ok = 0 }
try { console.log(Missing.Ok); }
catch (error) { console.log(error instanceof ReferenceError); }
```

The output is `true`. Inspection of its emitted JavaScript shows a read of Missing.Ok without an enum initializer. The failure is caught deliberately; no foreign implementation was linked.

Ambient numeric members also have a specific inference rule: an uninitialized member in a non-const ambient enum is considered computed, even after an explicit constant. The [ambient-enum reference](https://www.typescriptlang.org/docs/handbook/enums.html#ambient-enums) distinguishes it from a regular automatic sequence. Save ambient-types.ts and run `tsc --strict --noEmit ambient-types.ts`; this is a type-only fixture and is not run as JavaScript.

```typescript
export {};
declare enum Described { A = 1, B, C = 2 }
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type UninitializedNotProvenTwo = Expect<Equal<Described.B extends 2 ? true : false, false>>;
type ExplicitTwo = Expect<Described.C extends 2 ? true : false>;
```

Both probes compile. No runtime table is created from this fixture, and B is not an instruction telling a provider to initialize its next value to 2.

### 4) **Common confusion**

Heterogeneity concerns the values, so an equivalent union does not remove its numeric/string branches. Computation concerns initialization, while enum member types concern static relationships. A property access that looks constant to a reader can still remain in emitted code.

Ambient declarations are promises about a runtime provider. They do not load it, create it, synchronize its version or compare its behavior with the declared values. A changed JavaScript provider can leave type checking green while falsifying a literal-valued assumption. Explicit declarations make the expected contract visible; they do not enforce it at runtime.

### 5) **Performance note**

Regular enum initialization and retained initializer expressions execute. Subsequent member reads are property operations; the example observes one function call during initialization and two reads afterward. The ambient declaration adds no enum initializer, but its consumer and provider still execute real code. No per-member byte formula, universal kind-check overhead, module-load timing or foreign-call benchmark was measured. Use actual emitted code and initialization requirements when evaluating cost.

### 6) **Mentor note**

Ask which expression produces each runtime value and when it executes. Then remove the copied native.cjs and ask what the declaration file provides to Node: it provides no runtime module. A sound answer separates compile acceptance, module resolution and actual execution.

For practice, change only native.cjs to use Ok = 2 and Fail = 3, with reverse keys 2 and 3. Recompile the unchanged consumer against the old declaration: it still passes, but prints 2 true Fail despite assumedZero having type 0. Update native.d.cts to the actual 2/3 contract and confirm the old assumedZero annotation now fails TS2322. Repair that expectation to the new literal 2, rebuild and verify the output. This local mismatch drill demonstrates why maintaining and testing a declaration/provider pair matters; it does not certify compatibility with an external native library.
