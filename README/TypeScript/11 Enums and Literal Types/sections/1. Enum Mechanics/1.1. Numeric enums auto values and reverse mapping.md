## 1.1. Numeric enums auto values and reverse mapping

A numeric enum names numbers and creates a runtime object with forward and reverse entries. Its initializers affect the numbers a program stores or transmits, while its type controls some accepted operations. Neither the named type nor the reverse object validates an arbitrary incoming number. Bit masks add another contract whose arithmetic follows JavaScript's number bitwise rules.

Examples use TypeScript 7.0.2 and Node.js 20.20.2. Save each independent fence under its filename. Compile with `tsc --strict --exactOptionalPropertyTypes --noUncheckedIndexedAccess --removeComments --target es2022 --module commonjs --lib es2022,dom --outDir dist FILE.ts`; run `node dist/FILE.js`. These enum programs deliberately require transformation and omit erasableSyntaxOnly. Add `--erasableSyntaxOnly --noEmit` instead of --outDir dist to see TS1294 on their enum declarations. Activate other negatives individually using the original flags with --noEmit.

### 1) **Automatic values follow the preceding constant until another anchor**

An uninitialized first numeric member starts at zero; later uninitialized members follow the preceding numeric constant by one. An explicit initializer anchors the following sequence. Inserting a member can shift later automatic values, but a later explicit anchor stops that shift. The [primary numeric-enum guide](https://www.typescriptlang.org/docs/handbook/enums.html#numeric-enums) describes these rules. A member after a runtime-computed initializer needs its own initializer; the [computed-member owner](<./1.3. Heterogeneous ambient and computed members.md>) owns that separate case.

Save as codes.ts.

```typescript
export {};
enum Phase { Load, Parse, Done }
console.log(Phase.Load, Phase.Parse, Phase.Done);
enum Before { New = 10, Paid, Shipped, Archived = 90, Closed }
enum After { New = 10, Paid, Refunded, Shipped, Archived = 90, Closed }
console.log(Before.Shipped, After.Shipped, Before.Closed, After.Closed);
const storedCode = 12;
console.log(Before[storedCode], After[storedCode]);
enum Protocol { Accepted = 200, Rejected = 400 }
function receive(code: Protocol): number { return code; }
const incoming: number = 999;
console.log(receive(Protocol.Accepted), receive(incoming));
// receive(999); // TS2345: an out-of-set numeric literal is rejected
```

The output is `0 1 2`, `12 13 91 91`, `Shipped Refunded`, then `200 999`. No database was used: the two declarations simulate decoding the same stored number under two code versions. Explicitly assigning stable persisted/protocol values avoids dependence on declaration position, but changing an explicit value can still break that contract. A source edit is not a migration of historical data.

The accepted broad number and rejected literal also matter. Numeric enum typing is not simply unrestricted number, yet it is not an incoming-value validator. The [union-versus-enum owner](<../../../07 Unions Intersections and Narrowing/sections/1. Union Types/1.3. Literal unions enums vs unions and exhaustiveness preview.md>) verifies this numeric boundary and current enum-member type operations. Historical advice that every numeric literal is accepted does not describe this baseline.

### 2) **Reverse entries are runtime properties with collisions and absence**

A regular numeric member creates a forward property from its name to its number and a reverse property from that number to its name. This is useful for display, but it is not a one-to-one validation table: duplicate numeric values share one reverse key. With noUncheckedIndexedAccess, an ordinary reverse index here has type string | undefined. A runtime number outside the entries has no name.

Save as reverse.ts.

```typescript
export {};
enum Level { Low, High }
const code: number = 99;
const missing = Level[code];
console.log(Level.High, Level[1], missing ?? "unknown");
console.log(Object.keys(Level).join(","));
// missing.toUpperCase(); // TS18048
// const requiredName: string = Level[code]; // TS2322 with noUncheckedIndexedAccess
type LevelKey = keyof typeof Level;
const key: LevelKey = "High";
console.log(key, Level[key]);
// const numericKey: LevelKey = 1; // TS2322: reverse runtime keys are not the named key union
enum Alias { First = 1, Second = 1 }
console.log(Alias.First, Alias.Second, Alias[1]);

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type ReverseRead = Expect<Equal<typeof missing, string | undefined>>;
type NamedKeys = Expect<Equal<LevelKey, "Low" | "High">>;
```

The output is `1 High unknown`, `0,1,Low,High`, `High 1`, then `1 1 Second`; both probes compile. The last declaration writes the same numeric reverse property twice, so Second is the displayed name for both numeric aliases. Keyof typeof Level gives the named member keys even though Object.keys observes numeric reverse properties too.

Inspect dist/reverse.js: TypeScript emits assignments of the form `Level[Level["High"] = 1] = "High"`. The [primary reverse-mapping section](https://www.typescriptlang.org/docs/handbook/enums.html#reverse-mappings) shows this pattern. Do not infer a unique inverse or an exact emitted byte count from it. String members do not receive these numeric reverse entries. Const-enum emission depends on compiler options and tooling; [const enum inlining](<../2. Enums vs Erasable Alternatives/2.1. const enum inlining and isolatedModules danger.md>) owns that distinction.

Removing noUncheckedIndexedAccess makes the reverse expression appear as string in this example, while the runtime missing lookup still produces undefined. A display fallback handles that absence; validating a numeric input for application logic requires the intended member/value policy rather than trusting the reverse name.

### 3) **Bit flags need explicit mask semantics and bounded arithmetic**

Powers of two give independent bits. Combining them with | creates a mask; testing all requested bits differs from testing any requested bit. A named combined member is an alias for its numeric combination. It does not confer a separate runtime privilege or change how & works. Equality remains useful for an exact-mask or None test, so banning every enum equality comparison would be misleading.

Save as flags.ts.

```typescript
export {};
enum Permission {
  None = 0,
  Read = 1 << 0,
  Write = 1 << 1,
  Execute = 1 << 2,
  Admin = Read | Write,
}
const combined = Permission.Read | Permission.Write;
const admitted: Permission = combined;
function hasAll(mask: number, required: number): boolean { return (mask & required) === required; }
function hasAny(mask: number, requested: number): boolean { return (mask & requested) !== 0; }
console.log(combined, admitted, hasAll(combined, Permission.Read), hasAll(combined, Permission.Admin));
console.log(hasAll(combined, Permission.Read | Permission.Execute), hasAny(combined, Permission.Read | Permission.Execute));
console.log(hasAll(combined, Permission.None), hasAny(combined, Permission.None), combined === Permission.Read);
console.log(1 << 31, 1 << 32);
// const invalidLiteral: Permission = 99; // TS2322
// hasAll(combined, "Read"); // TS2345
const ALL = Permission.Read | Permission.Write | Permission.Execute;
function parseMask(value: unknown): number {
  if (typeof value !== "number" || !Number.isInteger(value) || value < 0 || value > 0x7fffffff || (value & ~ALL) !== 0) {
    throw new Error("invalid mask");
  }
  return value;
}
console.log(parseMask(0), parseMask(3), parseMask(7));
for (const input of [8, -1, 1.5, 2 ** 32, "3"]) {
  try { parseMask(input); } catch (error) { console.log(error instanceof Error ? error.message : "unexpected"); }
}
const Flag = { None: 0, Read: 1 << 0, Write: 1 << 1 } as const;
console.log(hasAll(Flag.Read | Flag.Write, Flag.Read));

type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;
type BitwiseResult = Expect<Equal<typeof combined, number>>;
```

The output is `3 3 true true`, `false true`, `true false false`, `-2147483648 1`, `0 3 7`, five `invalid mask` lines, then `true`; the live probe compiles. The combined Read|Write mask satisfies Admin because Admin is exactly that same combination. An empty requested mask makes hasAll true and hasAny false; those are the chosen bit-test semantics, not a claim that an application should grant access when nothing is requested.

Number bitwise operations use 32-bit integer conversion. The [AND reference](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Bitwise_AND#description) explains truncation, and the [shift reference](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Left_shift#description) explains the shift count modulo 32. Bit 31 becomes signed-negative and shifting by 32 repeats bit zero. This parser deliberately accepts only nonnegative signed-range integers containing the three allowed low bits; its range check prevents large numbers from being silently accepted after bitwise truncation. Other encodings need a separately chosen policy.

The bitwise expression has type number and can flow into the numeric enum contract here. ParseMask therefore validates the allowed mask independently and returns a number that can include combinations rather than pretending the enum annotation performed the check. The final const object uses the same runtime bit operations without enum syntax. Bit masks are not exclusive to enums; [erasable alternatives](<../2. Enums vs Erasable Alternatives/2.2. erasableSyntaxOnly the enum ban and migration.md>) owns the migration choices.

### 4) **Common confusion**

Automatic numbering is affected by preceding values, not a promise that every later member always shifts. A later explicit anchor and a duplicate numeric value have observable effects. Reverse mapping supplies names for display, can overwrite aliases and can miss; it is not a validator or a precise enumeration of the enum's named type keys.

A numeric enum can reject an out-of-set literal while accepting a broad number expression. Bit masks also represent combinations and have explicit all/any/empty semantics. Naming a mask Admin does not change the number or implement an authorization policy.

### 5) **Performance note**

Regular enums add initialization code and runtime objects; type queries and annotations erase. Reverse and forward accesses are ordinary property operations, and bitwise tests execute JavaScript's numeric conversions. No fixed bundle-size multiplier, CPU-instruction mapping, “fastest membership” ranking or enum-versus-object timing was measured. Choose a representation from its value/API/toolchain contract and measure the relevant workload if cost matters.

### 6) **Mentor note**

Ask the learner to predict the persisted-code decode, the duplicate reverse name, the type of a missing reverse read and the two Admin results before running the programs. Then ask why 1 << 32 is not a new independent flag. A sound answer separates source numbering, static acceptance, emitted properties and runtime arithmetic.

For practice, add Delete = 1 << 3 to Permission but leave ALL unchanged first. Calling parseMask(8) must still reject: a new declaration has not updated the parser's policy. Add Delete to ALL and verify parseMask(8) succeeds, hasAll(8, Delete) is true, hasAll(8, Read) is false and parseMask(16) still rejects. Keep the original invalid-input tests with the old 8 case replaced by 16. Explain why neither changing the enum alone nor asserting an unknown input to Permission would implement this behavior.
