## 1.1. Numeric enums — auto values and reverse mapping

### 1) **Auto-incremented values** (declaration order becomes data)

**Definition** — `enum Direction { Up, Down }` assigns `Up = 0`, `Down = 1` automatically (first member 0, each next +1 unless explicitly initialized). Explicit starts (`enum Code { Ok = 200, Err = 500 }`) anchor the sequence; followers continue from the anchor (`Err2 = 501`). Declaration order *is* persisted data — reordering or inserting members renumbers every follower.

**What problem it solves / history** — magic numbers (`if (status === 2)`) scattered unexplained integers that readers decoded from memory and refactors renumbered silently. Numeric enums (since TS 1.x, the original enum form) named the numbers — `Status.Active` reads where `2` puzzles — at the price of coupling names to positions (the renumbering hazard in 5.1 promise 1).

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), initialize *every* persisted numeric member explicitly (`OrderStatus.Shipped = 3` — never rely on position for stored values); auto-increment only for transient in-memory codes. Never insert mid-enum without auditing stored data — append new members at the end or assign stable codes deliberately.

**Runnable example** — names over magic numbers (good vs bad, `tsc --strict`):

```typescript
// good — named codes with explicit anchors for anything persisted
enum Http { Ok = 200, BadRequest = 400, Unauthorized = 401 }
function isOk(code: Http): boolean { return code === Http.Ok; }
console.log(isOk(Http.Ok), Http.BadRequest); // true 400

// good — transient in-memory codes may auto-increment (never stored)
enum Phase { Load, Parse, Done } // 0, 1, 2 — process-lifetime only
console.log(Phase.Parse); // 1

// bad — auto-values persisted: inserting a member renumbers followers in storage
enum Order { New, Paid, Shipped } // stored as 0,1,2 in the database...
// enum Order { New, Paid, Refunded, Shipped } // Shipped silently becomes 3 — historical rows reinterpreted
// fix — explicit codes: enum Order { New = 1, Paid = 2, Shipped = 3 } (append-only, never renumber)
console.log(Order.Paid); // 1 — position-coupled today, incident tomorrow
```

**Common confusion** — "enum members are just names" — numeric members *are* numbers (comparable, arithmetic-able, storable) — the name is a compile-time label over a runtime value. "explicit init anywhere is equivalent" — followers continue from the *nearest* anchor (mixed explicit/auto sequences confuse readers — anchor all or anchor none per enum). "renumbering only affects new code" — stored/serialized values reinterpret under new numbering — the blast radius is historical data, not source.

**Performance note** — numeric enums emit a bidirectional lookup object (O(members) object, one-time) — member access is a property read (fast); reverse lookup `E[0]` is a second property read (fast). No per-use cost beyond ordinary property access.

**Mentor note** — insert a member mid-enum live and ask "what changed in the database?" (nothing in schema, everything in meaning) — position-coupled persistence in one edit. Rule: persisted enums get explicit codes + a comment forbidding reordering; transient enums may auto-increment with a comment saying so.

### 2) **Reverse mapping** (the emitted table maps both directions)

**Definition** — numeric enums emit `{ Up: 0, 0: "Up", … }` — a two-way table: `Direction.Up` → `0` (forward) and `Direction[0]` → `"Up"` (reverse). Only *numeric* members reverse-map (string members emit forward-only); `const enum` emits nothing (inlined — no table, no reverse). Reverse lookup types as `string` (widened — the 3.2 trap), never the member literal.

**What problem it solves / history** — logging/debugging numeric codes (`received 2` — which state?) needed a handwritten inverse table per enum that drifted from the source on every member change. Reverse mapping derives the inverse from the declaration: `Direction[code] ?? "unknown"` debugs any code without a parallel table — at the cost of the widened `string` type on every lookup (precision surrendered for convenience).

**Modern guidance** — as of TypeScript 5.9 era, use reverse mapping for *display only* (logs, debug strings, admin labels) — never for control flow (switch on the enum member, not on `E[code]`'s `string`). Guard lookups (`E[code] ?? "unknown"`) — out-of-range codes return `undefined` at runtime while typing `string`. Prefer exhaustive switches over reverse-mapped displays for logic (see [3.2. Exhaustive switches](<../3. Literals and Nominal Patterns/3.2. Exhaustive switches over enums and unions.md>)).

**Runnable example** — display via reverse map, logic via members (good vs bad, `tsc --strict`):

```typescript
// good — reverse lookup for display; member switch for logic
enum Level { Low, High }
function label(code: number): string { return Level[code] ?? "unknown"; } // display only
function urgent(l: Level): boolean { return l === Level.High; } // logic on members
console.log(label(1), label(99), urgent(Level.High)); // High unknown true

// bad — control flow on the widened reverse lookup
function urgentBad(code: number): boolean {
  const name = Level[code] ?? "unknown"; // string — literal precision lost here
  return name === "High"; // string comparison: typos compile, exhaustiveness dead
}
// fix — urgent(l: Level): switch/compare on members (literals preserved, cases exhaustive)
console.log(urgentBad(1)); // true — correct result, unverifiable reasoning
```

**Common confusion** — "`E[code]` returns the member type" — returns `string` (widened — reverse maps erase member identity by design). "reverse mapping works for string enums" — string members emit forward-only (no `E["UP"]` table) — asymmetry is intentional (string values are already readable). "reverse maps are free" — doubles emit size per numeric member (forward + reverse entries) — trivial for small enums, measurable in generated mega-enums (another reason to prefer unions there).

**Performance note** — reverse lookup is one property read (same as forward) — no algorithmic cost; emit size doubles for numeric members (forward + reverse slots) — prefer string unions for large generated sets (zero emit).

**Mentor note** — hover `Level[code]` (`string`) vs `Level.High` (the member literal) — widening visible in one tooltip pair. Rule: reverse maps format strings; members drive logic — grep `E[variable]` in logic positions during review.

### 3) **Numeric enums as bit flags** (combinable members, the surviving pattern)

**Definition** — powers-of-two members (`Read = 1 << 0, Write = 1 << 1`) combine with `|` and test with `&`: `const rw = Perm.Read | Perm.Write` (type `Perm`, value `3`); `if (rw & Perm.Read)` tests membership. The one numeric-enum pattern unions replicate poorly (numeric bit math has no literal-union equivalent) — its survival case in the migration debate (see 2.3 promise 2).

**What problem it solves / history** — permission/flag sets as booleans-per-field (`{ canRead, canWrite, … }` — N fields, N checks, verbose serialization) or magic ints (`3` meaning read+write — opaque). Bit-flag enums pack N booleans into one number with named members: combinable at runtime (`|`), testable per flag (`&`), serializable as one integer — the C-style pattern TypeScript inherited deliberately.

**Modern guidance** — as of TypeScript 5.9 era, use flag enums for combinable permission/capability sets persisted as integers; test with `&` (never `===` — combined values equal no single member); document the bit layout (`1 << N` per member, never hand-numbered). For string-side flag sets (feature toggles, roles), prefer `Set<Union>` or union arrays — bit math serves integers, not strings.

**Runnable example** — combine and test (good vs bad, `tsc --strict`):

```typescript
// good — flags combine with |, test with &: one number, N named booleans
enum Perm { None = 0, Read = 1 << 0, Write = 1 << 1, Admin = (1 << 0) | (1 << 1) }
const me: Perm = Perm.Read | Perm.Write;
function can(p: Perm, flag: Perm): boolean { return (p & flag) === flag; }
console.log(can(me, Perm.Read), can(me, Perm.Admin), me.toFixed(0)); // true false 3

// bad — equality testing a combined value (never equals a single member)
function canBad(p: Perm): boolean { return p === Perm.Read; } // false for Read|Write holders
console.log(canBad(me)); // false — combined holder denied their own Read right
// fix — (p & flag) === flag: membership test, not equality test
```

**Common confusion** — "`Admin` as a combined member is redundant" — documents the *meaning* of the combination (all-rights) at the declaration — readers test `can(p, Perm.Admin)` instead of reconstructing the combination per call. "flags work for strings" — bit math needs integers; string flag sets want `Set<"read"|"write">` + `has` (same membership semantics, string domain). "heterogeneous flags mix freely" — mixing string and numeric members breaks `|`/`&` typing — keep flag enums purely numeric.

**Performance note** — bit ops are single CPU instructions (fastest membership test available); enum access is a property read — flags are the performance-optimal permission representation *and* the readable one (rare alignment — document it when choosing).

**Mentor note** — contrast `p === Perm.Read` vs `(p & Perm.Read)` on a combined holder — equality-denying-its-own-right in one boolean. Exercise: add a fourth flag and watch combinations compose without touching `can` — extensibility the boolean-fields design lacks. Review gate: `===` against flag-enum members fails review (membership uses `&`).
