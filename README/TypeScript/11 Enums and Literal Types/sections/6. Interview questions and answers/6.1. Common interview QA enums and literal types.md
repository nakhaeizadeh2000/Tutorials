## 6.1. Common interview QA — enums and literal types

### 1) **What does a numeric enum emit — and why does `Direction[0]` work while `StringEnum["UP"]` doesn't?** (reverse-mapping tables)

**Definition** — numeric enums emit bidirectional tables (`{ Up: 0, 0: "Up", … }` — forward member→value plus reverse value→name); string enums emit forward-only (`{ Get: "GET" }` — no reverse entries). `Direction[0]` reads the reverse slot (exists); `StringEnum["UP"]` reads a value as a key (absent — values aren't keys). `const enum` emits nothing (inlined — neither direction exists at runtime).

**What problem it solves / history** — interviewers ask this to test emit literacy (not just type literacy): candidates who describe the emitted object predict reverse-map behavior, `Object.values` doubling (numeric tables enumerate *both* directions — 4 entries for 2 members), and `const enum` enumeration errors without compiling anything.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), answer with the emit shape first (`{ Up: 0, 0: "Up" }` vs `{ Get: "GET" }` vs nothing), then derive each behavior (reverse works/doesn't/enumeration errors) from the shape. Full treatment in [1.1. Numeric enums](<../1. Enum Mechanics/1.1. Numeric enums auto values and reverse mapping.md>) + [1.2. String enums](<../1. Enum Mechanics/1.2. String enums intent and no reverse mapping.md>).

**Runnable example** — emit shapes compared (`tsc --strict`):

```typescript
enum Nums { A, B } // emits { A: 0, 0: "A", B: 1, 1: "B" } — bidirectional
enum Strs { A = "A", B = "B" } // emits { A: "A", B: "B" } — forward only
console.log(Nums[0], Strs.A); // A A — reverse works numerically, forward works for strings
console.log(Object.keys(Nums).length, Object.keys(Strs).length); // 4 2 — reverse slots double numeric keys
// Strs["A"]; // undefined at runtime (value read as key) — the asymmetry, demonstrated
```

**Common confusion** — "reverse mapping is type-level" — purely emit (runtime table slots); the *type* of `Nums[0]` is `string` (widened — the 3.2 trap lives one layer up). "`Object.values` counts members" — counts *slots* (numeric: 2× members; string: 1×) — enumerate members via `Object.keys` filtered to non-numeric, or avoid enumerating enums entirely.

**Performance note** — numeric tables double emit slots (forward + reverse) — trivial for small enums, measurable for generated mega-enums (prefer unions there — zero emit).

**Mentor note** — `tsc` one numeric and one string enum and diff the `.js` — emit shapes teach more than any definition. Follow-up probe: "what does `Object.values` return for each?" (slots, not members — the doubling surprise).

**Cross-links** — numeric emit → [1.1. Numeric enums](<../1. Enum Mechanics/1.1. Numeric enums auto values and reverse mapping.md>); string asymmetry → [1.2. String enums](<../1. Enum Mechanics/1.2. String enums intent and no reverse mapping.md>).

### 2) **Why does `--erasableSyntaxOnly` ban enums — and what replaces each kind?** (emit-is-the-feature + migration map)

**Definition** — the flag permits deletion-only syntax (types as comments); enums emit runtime objects (lookup tables, reverse maps) no deletion can produce — the declaration *is* code generation, banned as TS1294 alongside namespaces. Replacements: numeric → union + forward table; string → union + `as const` object; `const` → union + hand-inlined literals; ambient → ambient const-object declarations.

**What problem it solves / history** — erasable syntax lets type-stripping runtimes (Node 22.12+, esbuild/swc/Babel) run TypeScript without type-checking — enums broke the model (comments don't emit objects). Interviewers probe this to test toolchain literacy: candidates who name the flag *and* the per-kind map show migration judgment, not just rule recall.

**Modern guidance** — as of TypeScript 5.9 era, answer ban-first (deletion-only vs code-generation), map-second (four kinds, four replacements), incremental-third (alias → move → delete per enum — never flag-day). Full treatment in [2.2. erasableSyntaxOnly](<../2. Enums vs Erasable Alternatives/2.2. erasableSyntaxOnly the enum ban and migration.md>).

**Runnable example** — ban verified, map applied (`tsc --strict`):

```typescript
// replacement pattern (erasable under every toolchain): union + const object
const K = { A: "A", B: "B" } as const;
type KU = keyof typeof K; // "A" | "B" — checking set derived, zero enum
console.log(K.A); // A
// enum E { A, B } // TS1294 under --erasableSyntaxOnly (verified empirically in unit 49)
```

**Common confusion** — "only some enums fail" — *all* enum declarations fail (numeric, string, `const`, ambient-in-`.ts`) — the *form* is banned, not kinds. "`as const` objects are just verbose enums" — erasable, iterable, template-compatible — verbose where enums were terse, universal where enums were locked. "the flag is Node-only" — every syntax-only consumer benefits (esbuild/swc/Babel/Vite); type-checking still runs separately in CI.

**Performance note** — migrated tables match or shrink emit (forward-only vs reverse-doubled); unions zero-emit; startup wins under stripping runtimes (no transpile pass for deleted syntax).

**Mentor note** — strong answers give the map unprompted (four kinds → four replacements); probe with "string enum specifically?" when candidates stop at the ban. Follow-up: "how do you migrate incrementally?" (alias → move → delete — green throughout).

**Cross-links** — ban + map → [2.2. erasableSyntaxOnly](<../2. Enums vs Erasable Alternatives/2.2. erasableSyntaxOnly the enum ban and migration.md>); erasable inventory → [3.3. Choosing erasable syntax](<../../../01 Fundamentals and Mental Model/sections/3. Running TypeScript today/3.3. Choosing erasable syntax the zero-cost interop rule.md>) (in 01).

### 3) **When is `const enum` unsafe — and what breaks under `isolatedModules`/esbuild?** (cross-file inlining impossibility)

**Definition** — `const enum` inlines members as literals at compile time (zero object) — safe same-unit (definer + users under one `tsc` program), unsafe across files under per-file transpilers (esbuild/swc/Babel compile file-by-file; the defining file's values are invisible at use sites → `ReferenceError` at runtime, TS2748 at authorship when `isolatedModules` is on). Exporting `const enum` from shared packages is the incident pattern (see 5.1 promise 2).

**What problem it solves / history** — "faster, smaller — always" adoption inlined shared-library enums that crashed esbuild consumers 100% of loads (import-time, unconditional) while library CI stayed green (tsc pipeline). Interviewers use this to test pipeline thinking: candidates who ask "who consumes this, and with what transpiler?" reason about build architecture, not just language features.

**Modern guidance** — as of TypeScript 5.9 era, answer with the architecture (per-file transpilation cannot inline cross-file by design — not an esbuild bug), the rule (same-unit numeric non-enumerated → inline; shared/transpiled/enumerated → plain enum or union), and the authoring error (`isolatedModules` converts consumer crashes into library errors). Full treatment in [2.1. const enum](<../2. Enums vs Erasable Alternatives/2.1. const enum inlining and isolatedModules danger.md>).

**Runnable example** — same-unit safe, cross-file fatal (`tsc --strict`):

```typescript
// safe — same-unit constants: inlined literals, zero table, tsc owns the program
const enum Local { X, Y }
console.log(Local.X.toFixed(0)); // 0 — inlined (verify with tsc --emit)
// unsafe — exported const enum consumed via esbuild: ReferenceError (no table anywhere)
// fix — union + const object (universal) or plain enum (emitted table): shared values need runtime identity
export enum SharedOk { X, Y }
console.log(SharedOk.X.toFixed(0)); // 0 — works on every pipeline
```

**Common confusion** — "isolatedModules bans const enums" — bans *cross-file value use* (inlining needs the defining file); same-file compiles everywhere. "type-only imports fix value uses" — `import type` erases (no crash *and* no value) — useless for `Shared.X` value positions. "esbuild should support it" — architecturally impossible for per-file transpilers (no whole-program knowledge) — the constraint is shared by swc/Babel/Vite/Node-stripping alike.

**Performance note** — same-unit inlining saves table bytes (tens of bytes × enums) — real for opcode-dense internals; shared-table universality costs the same tens of bytes — correctness across pipelines dominates, bytes tiebreak.

**Mentor note** — ask "which transpiler consumes this package?" before "is const enum faster?" — pipeline-first reasoning is the hiring signal. Exercise: trace one shared `const enum`'s consumers by pipeline (tsc? esbuild?) — incompatible ones are pre-filed incidents.

**Cross-links** — const enum → [2.1. const enum](<../2. Enums vs Erasable Alternatives/2.1. const enum inlining and isolatedModules danger.md>); incident → [5.1. Production bugs](<../5. Common pitfalls to production bugs/5.1. Real production bugs caused by enum misunderstandings.md>).

### 4) **Union vs enum for a new status field — which by default, and what recorded reason overrides?** (decision rule + survivors)

**Definition** — default: literal union (`type Status = "idle" | "done"` — erasable, composable, exhaustible, zero emit). Override with a *recorded* reason only: numeric bit flags (combinability), ambient foreign tables (trust without emit), deliberately non-erasable codebases (reverse-lookup debugging + whole-program tsc). No comment, no enum — the review stamp from 2.3 promise 3.

**What problem it solves / history** — enum-by-default accumulated toolchain lock-in, composition preambles, and widening traps per use; union absolutism broke flags/foreign/debugging workflows. The default-plus-recorded-survivors rule routes the 90% automatically and protects the 10% explicitly — judgment concentrated where it matters instead of spread across every declaration.

**Modern guidance** — as of TypeScript 5.9 era, answer union-first with the composition proof (`Exclude`/templates apply directly), then volunteer the three survivors with one example each (flags: `Read | Write`; foreign: `declare enum`; non-erasable: reverse-debug tables). Full treatment in [2.3. Decision rule](<../2. Enums vs Erasable Alternatives/2.3. Literal unions as enums the decision rule.md>).

**Runnable example** — default composes, survivor records (`tsc --strict`):

```typescript
// default — union: filtered and templated with zero preamble
type Stt2 = "idle" | "done";
type LiveSt = Exclude<Stt2, "done">; // "idle"
const ls: LiveSt = "idle";
console.log(ls.toUpperCase()); // IDLE
// survivor — flags need combinability (recorded on the declaration per the stamp)
// Why enum: members combine with | (no union equivalent)
enum Fl { None = 0, Go = 1 << 0 }
console.log((Fl.Go).toFixed(0)); // 1 — combinability documented
```

**Common confusion** — "unions lack discoverability" — unions hover-expand fully at call sites (more discoverable than enum names hiding members until navigated). "one survivor justifies neighbors" — reasons don't propagate (flags in one enum don't bless string enums elsewhere) — each declaration earns its comment. "safety favors enums" — parity (same `never` sinks — see [3.2. Exhaustive switches](<../3. Literals and Nominal Patterns/3.2. Exhaustive switches over enums and unions.md>)) — safety never distinguishes the forms.

**Performance note** — unions zero-emit; survivors pay documented table costs knowingly — costs auditable per declaration instead of ambient.

**Mentor note** — strong answers name survivors unprompted (flags/foreign/non-erasable + one example each); probe with "string enums for readability?" (values read identically in unions — readability alone never survives) when candidates stop at the default. Metric: enum declarations per quarter, falling or holding.

**Cross-links** — decision rule → [2.3. Decision rule](<../2. Enums vs Erasable Alternatives/2.3. Literal unions as enums the decision rule.md>); parity → [3.2. Exhaustive switches](<../3. Literals and Nominal Patterns/3.2. Exhaustive switches over enums and unions.md>).

### 5) **What does `<const T>` change about `f("get")` — and when does it over-narrow?** (declaration-side preservation)

**Definition** — `<const T>` (TS 5.0) infers *as if* `as const`: `f("get")` gives `T = "get"` (not `string`), arrays infer `readonly` tuples, objects infer readonly properties — owned by the *declaration* (all calls inherit, no call-site ceremony). Over-narrows when callers wanted `string` (formatters, loggers) — fix at the *return* (`: string`), never by removing `const` (which re-widens every caller).

**What problem it solves / history** — literal-dependent helpers needed `as const` at every call (50 calls → 50 assertions, each independently forgettable — one widened call poisoned downstream exhaustiveness). `<const T>` moved ownership to the declaration: precision promised once, inherited everywhere — the scaling fix for literal pipelines (see [3.1. const type parameters](<../3. Literals and Nominal Patterns/3.1. const type parameters and literal preservation.md>)).

**Modern guidance** — as of TypeScript 5.9 era, declare `<const T>` on literal-dependent helpers (builders, registrars, factories); keep plain `<T>` where widening serves (accumulators, math, formatters); widen over-narrowed *returns* (`: string`) rather than de-consting sources. Full treatment in [3.1. const type parameters](<../3. Literals and Nominal Patterns/3.1. const type parameters and literal preservation.md>).

**Runnable example** — declaration owns precision (`tsc --strict`):

```typescript
function regC<const M extends string>(m: M): `r:${M}` { return `r:${m}`; }
const rc = regC("get"); // "r:get" — literal by declaration, no assertion
function useR(x: "r:get" | "r:post"): string { return x; }
console.log(useR(rc)); // r:get — exhaustiveness-ready
function shoutC<const T extends string>(x: T): string { return x.toUpperCase(); } // wide return: generality published
console.log(shoutC("get")); // GET — string, downstream unions unaffected
```

**Common confusion** — "`const T` makes params readonly" — affects *inference* (literals kept, readonly inferred) — the variable stays ordinary (mutable operations follow normal rules). "redundant `as const` under `<const T>` harms" — harmless but noisy (assertion agrees with inference) — remove for cleanliness. "over-narrowing means inference failed" — inference succeeding *too well* for the contract — fix contractually (return annotation), not mechanically.

**Performance note** — literal instantiations cache per argument (trivial for curated sets); wide returns *reduce* downstream check cost (one `string` vs N literal branches) — joints are performance decisions too.

**Mentor note** — ask "who owns precision here — declaration or call sites?" — `<const T>` vs `as const` is an ownership question, and ownership scales differently (1 declaration vs N calls). Exercise: convert one `as const`-heavy helper to `<const T>` and delete the call-site assertions — deleted lines are the ownership dividend.
