## 2.3. Literal unions as enums the decision rule

Choose the contract your consumers need. A literal union describes accepted values without creating data. A const object supplies named runtime constants and can supply a derived value union. An enum supplies its member-type API and, in ordinary enum transforms, a runtime object. None of these choices is an input validator.

For new finite string fields, a union is often a useful starting point because plain string literals fit the API and no enum transform is needed. Add a const object if callers need names, defaults or iteration. Retain or introduce an enum when its member API, existing consumers or generated numeric mappings justify that choice in a supported pipeline. Existing compatibility is a reason to investigate before changing a representation, even if no historical reason comment exists.

Examples use TypeScript 7.0.2 and Node.js 20.20.2, verified 2026-10-16. Save each named file in a fresh directory without tsconfig.json. Build with `tsc --strict --noUncheckedIndexedAccess --removeComments --target es2022 --module commonjs --outDir out FILE.ts`, then run `node out/FILE.js`. For an intentional rejection, activate one marked comment in a separate copy and replace --outDir out with --noEmit.

### 1) **Choose data and argument contracts separately**

| Need | Candidate | Check before choosing |
|---|---|---|
| Accept a finite set of plain values | Literal union | Unknown inputs still require validation |
| Named runtime values, a default or iteration | Const object with a derived union | As const does not freeze it; reflection and duplicate-value policy remain ordinary JavaScript |
| Existing enum-member API or generated numeric reverse entries | Enum in a supporting transform | Native stripping rejects implementation enums; preserve serialized values and public member contracts |
| Bit masks | Named numeric constants in an enum or object | Define allowed combinations, bit-width limits and actual validation independently |
| Description of a foreign provider | Declaration matching its actual exports | Neither declare enum nor declare const creates the implementation |

Save values.ts:

```typescript
export {};
const State = { Idle: "idle", Loading: "loading", Done: "done" } as const;
type State = (typeof State)[keyof typeof State];
type LiveState = Exclude<State, "done">;
type Label = `state:${State}`;
const defaultState: State = State.Idle;
const handlers: Record<State, () => string> = {
  idle: () => "waiting",
  loading: () => "working",
  done: () => "finished"
};
function render(state: State = defaultState): string { return handlers[state](); }
const live: LiveState = "loading";
const label: Label = "state:done";
console.log(render(), render("done"), render(live), label);
console.log(Object.values(State).join(","), Object.isFrozen(State));
// render("unknown"); // TS2345
// const finished: LiveState = "done"; // TS2322
// State.Idle = "idle"; // TS2540
```

The output is `waiting finished working state:done`, then `idle,loading,done false`. Defaults and iteration work without enum syntax. State is both a value binding and a type alias in their respective spaces. Only the alias and type operations erase; the object, functions and property lookups remain. This file also passes --erasableSyntaxOnly. The [Handbook's object alternative](https://www.typescriptlang.org/docs/handbook/enums.html#objects-vs-enums) makes the same distinction between an object and its derived value type.

This registry statically covers State, but its callbacks can still implement the wrong behavior. It also does not turn an arbitrary string into State. Runtime parsing and finite-table checks have their own owners linked below.

### 2) **Compare actual enum identity and composition**

Save members.ts:

```typescript
export {};
enum State { Idle = "idle", Loading = "loading", Done = "done" }
enum OtherState { Idle = "idle", Loading = "loading", Done = "done" }
type LiveState = Exclude<State, State.Done>;
type Label = `state:${State}`;
type RawState = `${State}`;
function render(state: State): string { return `render:${state}`; }
const live: LiveState = State.Loading;
const raw: RawState = State.Idle;
const label: Label = "state:done";
const labels: Record<State, string> = {
  [State.Idle]: "waiting",
  [State.Loading]: "working",
  [State.Done]: "finished"
};
console.log(render(live), raw, label, labels[State.Done]);
console.log(State.Idle === "idle", Object.values(State).join(","));
// render("idle"); // TS2345
// render(OtherState.Idle); // TS2345: matching string value does not make this the same enum API
// const finished: LiveState = State.Done; // TS2322
```

It prints `render:loading idle state:done finished`, then `true idle,loading,done`. Exclude filters the enum member union directly: no template extraction is required first. The template type interpolates its values, and Record accepts its members as keys. The [enum-member reference](https://www.typescriptlang.org/docs/handbook/enums.html#union-enums-and-enum-member-types) and [Exclude contract](https://www.typescriptlang.org/docs/handbook/utility-types.html#excludeuniontype-excludedmembers) explain why this composition is valid.

RawState deliberately exposes plain string values. A State member can flow into that representation; a raw string or member from the separately named OtherState is rejected by this render API. That checker distinction does not wrap the string at runtime: the equality test is true. It also does not validate untyped input. Use this evidence to decide whether member-based admission is useful for the public API, rather than treating the enum as either completely structural or a universal nominal safety boundary.

The regular enum example fails --erasableSyntaxOnly with TS1294. Keep its supported transform if preserving the API matters, or plan an explicit compatibility change using the [migration lesson](<./2.2. erasableSyntaxOnly the enum ban and migration.md>). String enums have no generated reverse mapping; numeric reverse behavior belongs in the numeric owner, rather than being a property of every enum.

### 3) **Test a proposed enum-specific requirement**

Bitwise combination is a JavaScript numeric operation. It does not require an enum. Save flags.ts:

```typescript
export {};
const Access = { None: 0, Read: 1, Write: 2 } as const;
type NamedAccess = (typeof Access)[keyof typeof Access];
const mine = Access.Read | Access.Write;
function hasAll(mask: number, required: number): boolean {
  return (mask & required) === required;
}
console.log(mine, hasAll(mine, Access.Write), hasAll(mine, Access.None));
const wide: number = mine;
console.log(wide, hasAll(Access.Read, Access.Write));
// const single: NamedAccess = mine; // TS2322: a combination is not necessarily one named constant
```

It prints `3 true true`, then `3 false`, and passes --erasableSyntaxOnly. NamedAccess is 0 | 1 | 2, while the bitwise expression has type number. An application can model the permitted mask domain explicitly; an ordinary named-constant union does not automatically enumerate its combinations. Numeric enums also accept broad number values, so choosing an enum does not supply a mask validator. The [numeric-enum lesson](<../1. Enum Mechanics/1.1. Numeric enums auto values and reverse mapping.md>) owns the checked parser, all-versus-any tests and 32-bit limits.

When reviewing a choice, name the actual requirement and demonstrate it. A numeric reverse table may be convenient generated behavior; a foreign declaration may need to match an existing provider; a public enum may have consumers depending on member types. None implies that const objects cannot support defaults, keys, iteration or arithmetic. A brief design comment can help when a trade-off is surprising, but a comment date or a falling enum count is not evidence that the design is correct. Avoid imposing a declaration-count target or migrating unrelated existing APIs simply because a file was touched.

Practice: extend State in values.ts with `Cancelled: "cancelled"`, then compile. Supply the newly required cancelled handler and run `console.log(render("cancelled"));`. Its expected output is `stopped` when the handler returns that string. An implementation returning finished still builds, but fails this stated behavior. Explain which test proves finite coverage and which proves semantics. In members.ts the analogous enum-member extension also makes its finite Record require an entry; this protection is available in both representations.

### 4) **Common confusion**

Zero enum transformation does not mean zero runtime work. The object-backed union example creates a table and calls callbacks. Conversely, an enum can be filtered and templated directly; a different syntax gate can reject its declaration independently of those type operations.

Matching runtime strings do not guarantee matching checker admission. Changing from State to its raw value union deliberately accepts more callers. Editor completion and hover presentation depend on tooling and context; neither representation has a universal discoverability advantage established by this lesson.

### 5) **Performance note**

Literal aliases, Exclude and template types erase. Regular enum transforms construct data; a const object also retains data. Their final size and runtime access cost depend on the actual emitted code and build pipeline. These examples establish behavior, not timing, byte ratios, checker cache formulas or a universal performance ranking. Measure the artifact and workload that matter before making a performance-based choice.

### 6) **Mentor note**

Give the learner an API that accepts raw wire strings and another that intentionally accepts enum members. Ask them to choose a representation and identify the migration tests needed to change it. A strong answer mentions accepted callers, actual runtime producers, finite behavior coverage and the deployment pipeline, and can disprove a claimed enum-only requirement with the flags example.
