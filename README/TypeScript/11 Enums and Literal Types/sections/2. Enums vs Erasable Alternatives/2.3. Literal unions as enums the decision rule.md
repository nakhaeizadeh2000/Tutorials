## 2.3. Literal unions as enums — the decision rule

### 1) **The default rule** (new code: unions — erasable, composable, zero emit)

**Definition** — default to literal unions for new finite sets: `type Status = "idle" | "loading" | "done"` — erasable (deletion-only emit), composable (`Exclude<Status, …>`, `` `on${Capitalize<Status>}` ``, `Record<Status, …>`), exhaustible (`never`-sink switches), zero bytes. Enums require a recorded reason (see promise 2) — the burden of proof sits on the heavier tool, as it should.

**What problem it solves / history** — enum-by-default codebases paid three recurring taxes: toolchain lock-in (every `const enum` a pipeline question, every enum an erasability question), composition friction (`Exclude` over enums needs member-literal extraction first; template tables need mapped derivation), and reverse-map widening (numeric lookups escaping literal precision). Union-by-default inverts the taxes: composition and erasure free, with enums available (documented) where their specific powers apply.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), write unions first; reach for enums only when a survivor reason (promise 2) applies *and* is recorded in a comment on the declaration. When an enum exists without a reason comment, the review default is migration (per 2.2's map), not grandfathering.

**Runnable example** — union default composes freely (good vs bad, `tsc --strict`):

```typescript
// good — union: filtered, templated, exhausted with zero emit
type Status = "idle" | "loading" | "done";
type Live = Exclude<Status, "done">; // "idle" | "loading" — one line, no extraction step
type Label = `status:${Status}`; // "status:idle" | ... — template-ready directly
function isLive(s: Status): boolean { return s !== "done"; }
console.log(isLive("idle"), "status:done" as Label); // true status:done

// bad — enum default: each composition needs an extraction preamble
enum StatusE { Idle = "idle", Loading = "loading", Done = "done" }
// type LiveE = Exclude<`${StatusE}`, "done">; // template-extract members first, then filter...
// fix — Status union: composition primitives apply directly, no preamble
type FromEnum = `${StatusE}`; // "idle" | "loading" | "done" — extraction when inheriting enums
const fe: FromEnum = "idle";
console.log(fe.toUpperCase()); // IDLE — escape hatch for legacy enums, not new ones
```

**Common confusion** — "unions lack discoverability" — unions hover-expand fully (`"idle" | "loading" | "done"` at every use) while enums hide members behind the enum name until navigated — unions are *more* discoverable at call sites. "unions can't carry methods" — attach behavior via functions/maps keyed by the union (`Record<Status, Handler>`) — methods on enums conflate data with behavior the same way. "default rules stifle judgment" — defaults route the 90% case; recorded reasons protect the 10% — judgment moves from every declaration to the exceptional ones.

**Performance note** — unions emit nothing (zero bytes, zero lookup cost — literals inline at use); enums emit tables (forward, doubled for numeric reverse). Composition over unions caches per derivation (one entry each) — check-time equivalent or cheaper than enum-member extraction chains.

**Mentor note** — the `${StatusE}` extraction line is the bridge lesson: inheriting enums *becomes* unions in one template — new code starts there directly. Exercise: convert one enum-default declaration to a union and delete the extraction preambles its consumers needed — preamble count is the composition tax, receipt included.

### 2) **Legitimate enum survivors** (bit flags, ambient foreign, non-erasable codebases)

**Definition** — three recorded reasons override the union default: (1) numeric bit flags (`Read | Write` combinability has no union equivalent — see 1.1 promise 3); (2) ambient foreign enums (`.d.ts` mirrors of vendor tables — trust without emit); (3) deliberately non-erasable codebases (whole-program `tsc` pipelines with reverse-lookup debugging needs and no toolchain pressure). Each recorded in a comment (`// enum: bit flags need combinability`) — unrecorded enums migrate.

**What problem it solves / history** — union absolutism ("never enums") broke flag composition (bit math over string unions is nonsense), foreign interop (ambient const objects approximate but don't mirror enum tables exactly), and debugging workflows (reverse maps operators rely on) — each a legitimate enum territory rediscovered through failed migrations. Recorded survivors protect the 10% while the default serves the 90%.

**Modern guidance** — as of TypeScript 5.9 era, record the reason *on the declaration* (`// Why enum: numeric bit flags combined with |`) with a review date for revisited conditions (pipeline changes, erasability adoption). Re-audit survivors when conditions change (adopting `--erasableSyntaxOnly` reopens every survivor except ambient-foreign). Never extend survivor reasoning by analogy ("this enum feels flaggish") — reasons are specific or they don't count.

**Runnable example** — survivors recorded, each irreplaceable by unions (good vs bad, `tsc --strict`):

```typescript
// good — bit flags: combinability no union can express (recorded reason inline)
// Why enum: members combine with | and test with & (numeric bit math)
enum Access { None = 0, Read = 1 << 0, Write = 1 << 1 }
const mine: Access = Access.Read | Access.Write;
console.log((mine & Access.Write) === Access.Write); // true — union equivalent: none sane

// bad — unrecorded enum surviving on vibes (migrates without loss)
enum Color { Red = "RED", Blue = "BLUE" } // no comment, no flags, no foreign table...
type ColorU = "RED" | "BLUE"; // ...migrates losslessly (values identical, composition gained)
// fix — record or migrate: ColorU + as const object covers values + iteration erasably
const COLOR_MAP = { Red: "RED", Blue: "BLUE" } as const;
console.log(COLOR_MAP.Red); // RED — value needs served without the enum
```

**Common confusion** — "survivors are permanent" — conditional on unchanged conditions (pipelines, erasability adoption, foreign-vendor stability) — re-audit on change, with dates. "string enums survive for readability" — readability comes from *values* (`"RED"` reads identically in unions) — string enums survive for *value needs* (defaults, keys, iteration — see 1.2 promise 3), not readability alone. "one survivor justifies neighboring enums" — reasons don't propagate (flags in one enum don't bless string enums elsewhere) — each declaration earns its own comment.

**Performance note** — survivors pay their documented costs (tables, reverse slots, pipeline constraints) *knowingly* — recorded reasons make costs auditable per declaration instead of ambient across the codebase.

**Mentor note** — audit one enum-heavy file with the class: default-migrate each, defend survivors with recorded reasons — the survivors standing at the end (flags, foreign, non-erasable) teach the rule's boundaries better than any list. Exercise: write the reason comment *before* the enum in new code — reason-first authoring prevents vibe-survivors.

### 3) **Review stamp** (new `enum` declarations require recorded reasons)

**Definition** — the stamp: every new `enum` keyword in a PR must carry a comment naming its survivor reason (flags/foreign/non-erasable + date) — missing comment means migrate-to-union before merge. Existing unrecorded enums migrate opportunistically (touch the file → record-or-migrate). The stamp makes the default rule enforceable in review instead of aspirational in docs.

**What problem it solves / history** — unenforced defaults decayed (union-by-default documented, enum-by-habit shipped — each new enum "just one more" until the codebase was enum-majority again with mixed idioms). Stamps work because they attach to the *mechanism that adds code* (PR review) rather than the *document nobody re-reads* — one checklist line per enum, permanent behavior change.

**Modern guidance** — as of TypeScript 5.9 era, add the stamp to the contributing guide (`New enums: record flags/foreign/non-erasable reason + date, or use a union`); lint what linters can (`no-restricted-syntax` on `TSEnumDeclaration` with a require-comment escape is impractical — human review owns this one); track migration progress (enum count per quarter — the metric should fall or hold, never rise unexplained).

**Runnable example** — stamped vs unstamped declarations (good vs bad, `tsc --strict`):

```typescript
// good — stamped: reason + date, reviewable in one line
// Why enum (2026-09): bit flags combined with | across auth checks; revisit on erasable adoption
enum Scope { None = 0, Read = 1 << 0, Write = 1 << 1 }
console.log((Scope.Read | Scope.Write).toFixed(0)); // 3 — combinability documented

// bad — unstamped: no reason, no date, no defense (migrates on sight)
enum Flavor { Vanilla = "VANILLA", Mint = "MINT" } // why not a union? (silence = migrate)
type FlavorU = "VANILLA" | "MINT"; // the review outcome, pre-computed
const f: FlavorU = "MINT";
console.log(f.toLowerCase()); // mint
// fix — record (Scope pattern) or migrate (FlavorU pattern): silence is not an option
```

**Common confusion** — "stamps bureaucratize trivial code" — one comment line per enum (seconds) vs migration debates per enum (hours) — stamps *remove* bureaucracy by pre-answering the review question. "grandfathered enums are exempt" — exempt from *immediate* migration, not from recording (touch-the-file rule migrates opportunistically; untouched legacy stays until conditions change). "linters should enforce this" — no reliable AST rule distinguishes reasoned from unreasoned enums (comments aren't reliably machine-checkable for *content*) — human review owns judgment calls by design.

**Performance note** — review-time only (zero code impact) — the stamp's ROI is measured in prevented incidents and migrations, per 5.1's ledger.

**Mentor note** — stamp the first five enum PRs together with the author watching — calibration beats documentation for judgment rules. Metric to graph: enum declarations per quarter (falling = default working; rising = stamp ignored). Celebrate migrations (deleted enums) in team notes — culture follows measured behavior.
