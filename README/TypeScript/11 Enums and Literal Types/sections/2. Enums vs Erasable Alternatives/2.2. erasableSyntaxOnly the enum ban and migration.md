## 2.2. erasableSyntaxOnly the enum ban and migration

ErasableSyntaxOnly checks whether source uses restricted TypeScript syntax that needs transformation. An enum replacement also needs a separate compatibility decision: keeping its strings or numbers does not automatically preserve accepted arguments, object keys, reverse lookups or external consumers. This lesson migrates one contract at a time and tests the distinctions.

Examples use TypeScript 7.0.2, Node.js 20.20.2 for emitted JavaScript and Node.js 22.18.0 for native type stripping, verified 2026-10-16. Save each named file in a fresh directory without tsconfig.json. Build with `tsc --strict --noUncheckedIndexedAccess --removeComments --target es2022 --module nodenext --outDir out FILE.mts`, then run `node out/FILE.mjs`. Each file is an independent program. For a marked rejection, activate only that comment in a separate copy and replace --outDir out with --noEmit.

### 1) **Distinguish runtime enum syntax from ambient descriptions**

An ordinary enum or const enum in an implementation file fails --erasableSyntaxOnly with TS1294. Its implementation requires generated code or substituted values. A declare enum describes a value supplied elsewhere; erasing that description does not require generating its implementation. Type-only namespaces also differ from namespaces that contain runtime code.

Save gate.mts:

```typescript
export {};
declare enum Foreign { Ready = 1 }
namespace Shapes { export type Packet = { text: string }; }
const packet: Shapes.Packet = { text: "ready" };
console.log(packet.text, typeof Foreign === "undefined");
// enum Local { Ready = 1 } // TS1294 with --erasableSyntaxOnly
// const enum Fast { Ready = 1 } // TS1294 with --erasableSyntaxOnly
// namespace Values { export const ready = 1; } // TS1294 with --erasableSyntaxOnly
// class Point { constructor(public x: number) {} } // TS1294 with --erasableSyntaxOnly
// const asserted = <number>1; // TS1294 with --erasableSyntaxOnly
// console.log(Foreign.Ready); // checks successfully, but execution fails: no provider exists
```

Add --erasableSyntaxOnly to its build command and run it: the output is `ready true`. Inspect out/gate.mjs: neither Foreign nor Shapes is initialized. The runtime typeof check observes the absence of Foreign safely; it does not read Foreign.Ready. That commented member read passes checking but throws ReferenceError when executed. An ambient declaration never installs a provider. [The complete ambient fixture](<../1. Enum Mechanics/1.3. Heterogeneous ambient and computed members.md>) demonstrates supplying one.

The [option reference](https://www.typescriptlang.org/tsconfig/erasableSyntaxOnly.html) also restricts non-ECMAScript import/export assignments. The [bounded configuration lesson](<../../../13 Configuration and Compiler Options/sections/2. Erasable and Isolated Toolchain/2.3. erasableSyntaxOnly and the trio standard.md>) owns the larger syntax/import/resolution contract. Do not classify every namespace as runtime code, or esbuild and Babel as deletion-only tools: their actual enum transforms are demonstrated in [const-enum tooling](<./2.1. const enum inlining and isolatedModules danger.md>).

### 2) **Migrate a string contract through independent working stages**

Suppose callers use two stable serialized directions. First save before.mts. Its parameter requires the enum type, even though its values are strings:

```typescript
export {};
enum Dir { Up = "UP", Down = "DOWN" }
function move(direction: Dir): string { return `go ${direction}`; }
console.log(move(Dir.Up), move(Dir.Down));
console.log(Object.isFrozen(Dir));
// move("UP"); // TS2345: raw literal is not the enum type
```

It builds without the erasable gate and prints `go UP go DOWN`, then `false`. Now save bridge.mts as a separate transitional version:

```typescript
export {};
enum Dir { Up = "UP", Down = "DOWN" }
type DirValue = "UP" | "DOWN";
function move(direction: DirValue): string { return `go ${direction}`; }
console.log(move(Dir.Up), move(Dir.Down));
console.log(Object.isFrozen(Dir));
const raw: DirValue = "UP";
move(raw);
// move("LEFT"); // TS2345
```

It prints the same two lines. Enum members flow into this value union, and raw UP is now accepted too. Writing Dir | DirValue would be redundant for these member values. The expanded admission is an API change, even though existing calls still produce the same strings. Whether to accept that change depends on the boundary; keep validation of unknown input in its actual parser.

Finally save after.mts. This version contains no enum declaration:

```typescript
export {};
const Dir = { Up: "UP", Down: "DOWN" } as const;
type DirValue = (typeof Dir)[keyof typeof Dir];
function move(direction: DirValue): string { return `go ${direction}`; }
console.log(move(Dir.Up), move(Dir.Down));
console.log(Object.isFrozen(Dir));
move("UP");
// move("LEFT"); // TS2345
// Dir.Up = "UP"; // TS2540: readonly to the checker
```

It again prints the same two lines and passes --erasableSyntaxOnly. The const object is real retained JavaScript data; as const disappears and does not freeze the object. Named Dir.Up callers can remain unchanged in this particular migration. Import paths, published declarations, enum-specific type uses and external consumers still need separate checks. Deleting an enum with no remaining checked references proves only that the checked program no longer requires those references; it does not certify every external consumer or runtime contract.

### 3) **Preserve the numeric behavior that callers actually consume**

Save numeric-before.mts. The duplicate alias is deliberate: the last member with value 20 supplies its reverse name.

```typescript
export {};
enum Severity { Low = 10, High = 20, Critical = 20 }
function display(code: number): string | undefined { return Severity[code]; }
console.log(Severity.High, display(20), display(99));
console.log(Object.keys(Severity).join(","));
```

The output is `20 Critical undefined`, then `10,20,Low,High,Critical`. Save numeric-after.mts:

```typescript
export {};
const Severity = { Low: 10, High: 20, Critical: 20 } as const;
type Severity = (typeof Severity)[keyof typeof Severity];
const names: Record<Severity, string> = { 10: "Low", 20: "Critical" };
function display(code: number): string | undefined {
  return code === Severity.Low || code === Severity.High ? names[code] : undefined;
}
console.log(Severity.High, display(20), display(99));
console.log(Object.keys(Severity).join(","));
```

The first line is preserved, but the second is `Low,High,Critical`. The explicit display table retains the consumed reverse-label policy, including the duplicate alias and missing-code result. Reflection over Severity has changed. If callers depend on its combined numeric/name keys, preserve that contract deliberately or migrate those callers too. Dropping reverse entries is not automatically a correctness improvement. The [numeric-enum owner](<../1. Enum Mechanics/1.1. Numeric enums auto values and reverse mapping.md>) explains duplicate assignment, bit masks and broad-number acceptance in depth.

Practice: change Critical to 30 in numeric-after. The Record table now requires a 30 entry, but that alone cannot fix display: its guard still admits only Low and High. Add `30: "Critical"`, change the 20 label to High and include Critical in the guard. Add `console.log(display(30), display(20), display(99));`; the expected extra line is `Critical High undefined`. A build failure detects a missing finite table entry; runtime tests detect a stale guard or wrong label. Both are needed.

### 4) **Run the actual deployment path before enabling the gate**

Check after.mts, numeric-after.mts and gate.mts with the same compiler command plus --erasableSyntaxOnly. Before.mts, bridge.mts and numeric-before.mts intentionally fail that gate with TS1294. They remain valid inputs for the ordinary tsc transform used above.

On Node 22.18.0, run `node after.mts`, `node numeric-after.mts` and `node gate.mts` directly. Their outputs match their emitted counterparts. Running `node before.mts` without a transform flag fails with ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX. With the system Node 20.20.2, invoke the pinned native runtime as `npm exec --yes --package=node@22.18.0 -- node after.mts`, and substitute the other filenames. The [Node 22.18 documentation](https://nodejs.org/download/release/v22.18.0/docs/api/typescript.html#type-stripping) states that stripping is enabled by default in this version, performs no type checking and ignores tsconfig.json. Passing a syntax gate does not create imports, satisfy missing dependencies or supply unavailable JavaScript APIs.

For a large codebase, choose a migration boundary from actual packages and compiler programs. There is no per-directory erasableSyntaxOnly override within a single program. Separate project configurations can define narrower checking programs, but imports can pull legacy files into those programs; include/exclude patterns alone are not an isolation wall. Keep legacy code behind a supported build/package boundary where necessary, and verify the effective file set. Choose the order from fan-out and compatibility risk instead of imposing one mandatory enum-kind sequence.

Const enums need no universal hand-inlining rule: a named const object may preserve member access, while internal inlining or publication needs the separate [toolchain analysis](<./2.1. const enum inlining and isolatedModules danger.md>). Ambient enums can already pass the syntax gate; changing their declaration alone does not repair a missing or mismatched implementation.

### 5) **Common confusion**

Same serialized value does not mean identical public type or runtime object. The bridge deliberately admits raw literals, and the numeric replacement deliberately separates reverse labels from the member object. State which behavior is preserved, changed or unsupported instead of calling every conversion mechanical.

ErasableSyntaxOnly checks source syntax; it is not a runtime switch and does not remove const objects. Native stripping and enum-transforming build tools therefore have different capabilities. Keep checking and execution as separate evidence.

### 6) **Performance note**

This migration changes emitted representation, but the checks here measure no startup time, bundle size or checker cost. A literal union erases; an object and display table remain. Their final cost depends on actual imports, bundling, minification and execution. Do not infer half the bytes, identical checking time or faster startup from the number of source declarations.

### 7) **Mentor note**

Ask a learner to name one test beyond a successful build. A strong answer points to the newly admitted raw literal, the duplicate numeric reverse label, the changed Object.keys result or the actual source runner. Then use the Critical=30 exercise to show why an exhaustive table cannot repair an independently maintained guard.
