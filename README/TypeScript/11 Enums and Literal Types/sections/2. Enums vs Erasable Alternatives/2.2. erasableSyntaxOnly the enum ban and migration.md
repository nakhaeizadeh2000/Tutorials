## 2.2. `erasableSyntaxOnly` — the enum ban and migration

### 1) **Why enums fail the erasable rule** (emit-is-the-feature, only namespaces share the ban)

**Definition** — `--erasableSyntaxOnly` (TS 5.8) permits only syntax erasable by *deleting types*: enums (and namespaces) fail because their emit *is* runtime code (lookup objects, reverse tables) that no type-deletion can produce. Under the flag, every `enum` declaration errors TS1294 — including `const enum` (inlining is still code *generation*, not deletion) and ambient enums in implementation files.

**What problem it solves / history** — erasable syntax enables syntax-only tooling (Node 22.12+ native type-stripping, esbuild/swc/Babel, `tsc` single-file transpile) to run TypeScript *without type-checking* — fast startup, no build step, one mental model ("types are comments"). Enums broke the model (comments don't emit objects), so the flag bans them: codebases opting in trade two features (enums, namespaces) for toolchain simplicity across every file.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), enable `--erasableSyntaxOnly` in new projects (with `verbatimModuleSyntax` + `isolatedModules` — the erasable trio) and migrate enums per the map below. Existing enum-heavy codebases: enable per-directory first (new code erasable, legacy exempted), then migrate legacy enums incrementally (next promise) — never flag-day the ban.

**Runnable example** — the ban and what passes (good vs bad, `tsc --strict`):

```typescript
// good — erasable finite sets: union + const object (deletion-only emit)
const KIND = { circle: "C", square: "S" } as const;
type Kind = keyof typeof KIND; // "circle" | "square" — erasable derivation
console.log(KIND.circle); // C — works under every syntax-only toolchain

// bad — enum under the flag: declaration itself errors (kept as commented error demo)
// enum Direction { Up, Down } // error TS1294 under --erasableSyntaxOnly: enums are not erasable
// fix — KIND pattern above, or literal union for checking-only positions (see decision rule 2.3)
// (verified: this file passes tsc --strict --erasableSyntaxOnly with the enum commented out)
```

**Common confusion** — "only *some* enums fail erasability" — *all* enum declarations fail (numeric, string, `const`, ambient-in-`.ts`) — the ban targets the *declaration form*, not the kind. "`as const` objects are just verbose enums" — erasable (deletion-only), iterable, template-compatible — verbose where enums were terse, universal where enums were toolchain-locked. "the flag is only for Node stripping" — also esbuild/swc/Babel/Vite single-file paths (any syntax-only consumer benefits; type-checking still runs separately in CI).

**Performance note** — erasable code starts faster under type-stripping runtimes (no transpile pass for enums/namespaces — deleted, not generated); const-object tables cost one object literal (same as plain-enum tables, half of numeric reverse tables). Startup wins dominate; check-time identical.

**Mentor note** — compile one enum file with and without the flag and read TS1294 together — the ban as a *diagnostic* (not documentation) makes erasability concrete. Exercise: migrate one enum to the KIND pattern and run the file under three toolchains (tsc-emit, esbuild, node-stripping) — universality demonstrated, not asserted.

### 2) **The migration map** (numeric → union + table; string → union + const object; const → literals)

**Definition** — per-kind replacement: numeric enums → literal *union* (checking) + plain lookup object (runtime table where needed); string enums → string-literal union + `as const` object (values + iteration, erasable); `const enum` → union + inlined literals at use sites (hand-inlining replaces compiler inlining); ambient enums → ambient const-object declarations (same trust, erasable form).

**What problem it solves / history** — flag-day enum deletion (remove all enums, fix 400 errors at once) stalled every migration it touched — too big to review, too risky to land. The per-kind map makes migration *mechanical and incremental*: each enum converts independently (union first, table second, delete last), each PR stays reviewable, and the codebase compiles at every step.

**Modern guidance** — as of TypeScript 5.9 era, migrate in this order: string enums first (mechanical: union + const object, behavior identical), numeric display enums second (union + forward table; drop reverse maps unless logic needs them — it shouldn't), `const`/ambient/flag enums last (require per-case judgment: inlining sites, foreign trust, bit math). Keep a `// migrated: <date>` comment on each converted declaration until the enum is deleted.

**Runnable example** — each kind converted independently (good vs bad, `tsc --strict`):

```typescript
// good — string enum → union + const object (behavior-identical, erasable)
const MethodMap = { Get: "GET", Post: "POST" } as const;
type MethodU = (typeof MethodMap)[keyof typeof MethodMap]; // "GET" | "POST"
function callU(m: MethodU): string { return `call ${m}`; }
console.log(callU("GET"), MethodMap.Post); // call GET POST

// good — numeric enum → union + forward table (reverse map dropped deliberately)
type LevelU = 0 | 1;
const LevelName: Record<LevelU, string> = { 0: "Low", 1: "High" }; // forward table only
console.log(LevelName[1]?.toUpperCase()); // HIGH — display without reverse-map widening

// bad — flag-day deletion (all enums out, 400 errors in one PR — unreviewable, reverted)
// fix — one enum per PR: union first (checking preserved), table second (runtime preserved), delete last
```

**Common confusion** — "migration changes runtime behavior" — string/numeric values preserved exactly (same strings, same numbers) — only the *declaration form* and reverse maps change; tests should pass unmodified (that's the migration's own verification). "reverse maps must be preserved" — reverse maps widened lookups to `string` (the 3.2 trap) — dropping them *fixes* precision; logic belongs on members/unions, display on forward tables. "ambient enums can't migrate" — ambient const-object declarations (`declare const X: { readonly A: 0 }`) carry identical trust in erasable form — same promise, no enum.

**Performance note** — migrated tables cost the same or fewer bytes (forward-only tables halve numeric reverse emit); unions cost zero — migrations typically *shrink* bundles while unblocking toolchains. Measure per-enum with emit diffs during migration PRs.

**Mentor note** — migrate one enum of each kind live (string → numeric → const) and run the unchanged test suite after each — green-green-green sells incremental over flag-day permanently. Rule: migration PRs convert one enum (union + table + delete) with tests green — never batch.

### 3) **Migrating incrementally** (alias first, move consumers, delete last)

**Definition** — the three-step per-enum migration: (1) introduce the union *alongside* (`type DirectionU = "Up" | "Down"` next to `enum Direction`), alias-accepting at boundaries (`d: Direction | DirectionU` during transition); (2) move consumers one call site at a time (union-typed signatures accept both — enum members flow into literals per 1.2's verified direction); (3) delete the enum when no reference remains (compiler-verified completion — deleting early errors loudly).

**What problem it solves / history** — big-bang migrations (delete enum, fix all consumers in one PR) conflicted with feature work (every in-flight branch broke) and hid behavioral changes inside mechanical diffs (reviewers rubber-stamped 400-line PRs). Incremental migration keeps every step green, reviewable, and revertible: alias (no behavior change), move (one consumer per commit), delete (compiler proves completion).

**Modern guidance** — as of TypeScript 5.9 era, migrate enums in this exact order per enum: alias → consumers (widest fan-out first, so later moves get easier) → delete. Lean on the one-way assignability (members flow *into* unions — step 2 needs no casts); never widen consumers to `string` mid-migration (precision must survive the transition, or the migration *caused* a widening incident).

**Runnable example** — three steps, green throughout (good vs bad, `tsc --strict`):

```typescript
// step 1 — alias alongside: boundary accepts both during transition
enum Dir { Up = "UP", Down = "DOWN" }
type DirU = "UP" | "DOWN";
function move(d: Dir | DirU): string { return `go ${d}`; } // accepts enum AND literals
console.log(move(Dir.Up), move("DOWN")); // go UP go DOWN — mixed consumers compile

// step 2 — consumers move one by one (members flow into unions, no casts)
// move("UP"); move(Dir.Down); // both compile against Dir | DirU — migrate call sites freely

// step 3 — delete when references vanish (compiler proves it: delete early → loud errors)
// (Dir deleted) → function move(d: DirU): string — final union-only signature
function moveFinal(d: DirU): string { return `go ${d}`; }
console.log(moveFinal("UP")); // go UP — migration complete, behavior identical

// bad — big-bang: delete Dir first, fix 40 call sites in one PR (conflicts, rubber-stamps, risk)
// fix — alias → move → delete: green at every commit, reviewable at every step
```

**Common confusion** — "aliasing duplicates the type" — temporarily (one PR lifespan per enum) — duplication with a deletion date is migration, without one is rot; the Next-steps-style tracking (`// TODO: delete Dir after call sites move`) distinguishes them. "members flowing into unions needs casts" — verified in 1.2 (`Method.Get` → `"GET"` compiles) — the language *designed* this direction for migrations; no casts at any step. "deleting early is fine with fixes" — early deletion breaks in-flight branches (merge conflicts across the team) — delete last costs nothing and respects parallel work.

**Performance note** — transitional unions cost zero (types only); the alias step adds one named type per enum (cached once) — migration overhead is review-time, never runtime or check-time meaningful.

**Mentor note** — run one full alias→move→delete cycle on a real enum in the session — three green commits in twenty minutes teaches more than any migration RFC. Rule: migration PRs carry the enum's deletion date; dateless aliases fail review as duplication.
