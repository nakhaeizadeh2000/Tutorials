## 2.1. const enum inlining and isolatedModules danger

A const enum's output depends on the tool and options. TypeScript's ordinary whole-program emit can substitute member values and remove the declaration. Other supported modes retain runtime values instead. The important library boundary is an ambient const enum: a declaration can promise constants while providing no runtime object for a different transform to read, or can inline values that no longer match the runtime dependency.

The following fixtures use TypeScript 7.0.2 and Node.js 20.20.2. The Babel commands additionally use Node.js 22.18.0, as required by the pinned Babel 8 packages. Create a fresh project directory with a src subdirectory, no tsconfig.json and no preexisting Babel configuration. Save the next three files there. Run all commands from this project directory unless another directory is named.

### 1) **Observe default, preserved and isolated TypeScript output**

Save src/local.ts.

```typescript
export {};
const enum Local { A = 1, B = 2 }
const enum TextCode { Ready = "ready" }
console.log(Local.A, Local.B, TextCode.Ready);
// console.log(Object.values(Local)); // TS2475: const enum cannot be used as an ordinary object value
// const enum Computed { Value = Date.now() } // TS2474: const enum initializer must be a constant expression
```

Save src/op.ts.

```typescript
export const enum Op { Add = 1, Sub = 2 }
```

Save src/main.ts.

```typescript
import { Op } from "./op.js";
console.log(Op.Add, Op.Sub);
```

Build with `tsc --strict --removeComments --target es2022 --module commonjs --outDir tsc-default src/local.ts src/main.ts`. Run `node tsc-default/local.js` and `node tsc-default/main.js`: the outputs are `1 2 ready` and `1 2`. Inspect the files: local enum declarations are absent, the member reads are constants, and the const-enum-only import does not require a runtime table. String members can be inlined too; this behavior is not restricted to numeric opcodes.

Repeat with `--preserveConstEnums` added and --outDir tsc-preserve. Both programs print the same results. This mode retains enum objects while still substituting the referenced constants in this fixture. The [preserveConstEnums reference](https://www.typescriptlang.org/tsconfig/preserveConstEnums.html) shows that distinction. Preservation does not make Object.values(Local) legal TypeScript source: the marked TS2475 negative still fails. Use an ordinary enum or a real const object when TypeScript consumers need object enumeration.

Repeat instead with `--isolatedModules` added to the original command and --outDir tsc-isolated. Both programs still build and print the same results, including the cross-file import. Here TypeScript retains enum objects and runtime member references. Trying to disable preserveConstEnums explicitly while isolatedModules is enabled is rejected. IsolatedModules is a compatibility check for operations needing cross-file type knowledge; it does not mean that tsc stops checking imported source files or that every source-defined const enum import is banned.

### 2) **Compare actual esbuild and Babel transforms**

Install these pinned tools in the fresh project directory with `npm install --ignore-scripts --save-exact esbuild@0.28.2 @babel/core@8.0.7 @babel/cli@8.0.6 @babel/plugin-transform-typescript@8.0.6 @babel/plugin-transform-modules-commonjs@8.0.1`. Babel executes under Node 22.18.0 in the commands below; installing the packages does not run Babel or change the project's tutorial source.

For esbuild, run `./node_modules/.bin/esbuild src/main.ts --bundle --platform=node --format=cjs --target=node20 --outfile=esbuild-bundle.cjs`, then `node esbuild-bundle.cjs`. The output is `1 2`; inspection shows the two constants in this bundled fixture. Cross-file const-enum use is not inherently a crash or an impossible bundling operation.

Also run `./node_modules/.bin/esbuild src/local.ts src/op.ts src/main.ts --platform=node --format=cjs --target=node20 --outdir=esbuild-files`, then run `node esbuild-files/local.js` and `node esbuild-files/main.js`. They print `1 2 ready` and `1 2`. The separately transformed exported op module supplies a runtime value for its consumer. The [esbuild syntax support and caveats](https://esbuild.github.io/content-types/#typescript) explicitly include const enums and advise isolatedModules checking; esbuild does not type-check these inputs.

For Babel's default enum transform, run `npm exec --yes --package=node@22.18.0 -- node node_modules/@babel/cli/bin/babel.js src --out-dir babel-default --extensions .ts --plugins @babel/plugin-transform-typescript,@babel/plugin-transform-modules-commonjs --no-babelrc`. Run the emitted local.js and main.js with Node: again they print `1 2 ready` and `1 2`. The default transform retains enum tables.

Save babel-opt.json in the same project directory:

```json
{
  "plugins": [
    ["@babel/plugin-transform-typescript", { "optimizeConstEnums": true }],
    "@babel/plugin-transform-modules-commonjs"
  ]
}
```

Run `npm exec --yes --package=node@22.18.0 -- node node_modules/@babel/cli/bin/babel.js src --out-dir babel-opt --extensions .ts --config-file ./babel-opt.json --no-babelrc`, then run its local.js and main.js. Their outputs remain the same. In this mode the local constants are substituted, while exported Op becomes a plain object that its separately transformed consumer can read. The [Babel option documentation](https://babeljs.io/docs/babel-plugin-transform-typescript#optimizeconstenums) distinguishes local inlining from the exported-object behavior.

These are tested tool/version/mode combinations, not certification of every Babel plugin, bundler, framework or build configuration. Keep type checking alongside transformation and inspect the output that the actual pipeline will publish. Successful execution does not prove every tool emits identical tables or preserves the same numeric reverse entries.

### 3) **Reproduce the ambient publication and version boundary**

Now create a separate published subdirectory for a declaration/provider fixture. Save published/foreign.d.cts. This declaration is a type-checking input, not a JavaScript provider.

```typescript
export declare const enum Code { Ready = 1 }
export declare function current(): number;
```

Save published/foreign.cjs. It represents a changed runtime implementation whose current value is now 2. It does not export a Code object.

```javascript
exports.current = () => 2;
```

Save published/consumer.cts.

```typescript
import { Code, current } from "./foreign.cjs";
console.log(Code.Ready, current(), current() === Code.Ready);
```

From published, build with `tsc --strict --removeComments --target es2022 --module node16 --moduleResolution node16 --outDir out consumer.cts`. Copy the runtime provider with `cp foreign.cjs out/foreign.cjs`, then run `node out/consumer.cjs`. The output is `1 2 false`. The type checker used the declared constant 1, while the actual provider returned 2. This local fixture simulates version disagreement; no external package version was deployed.

Inspect out/consumer.cjs: the two Code.Ready references became 1, while the call to current still loads and calls the runtime module. Adding --isolatedModules with --noEmit to the consumer's build rejects the ambient const-enum value references with TS2748. The [isolatedModules reference](https://www.typescriptlang.org/tsconfig/isolatedModules.html#references-to-const-enum-members) identifies that ambient restriction. It is different from the passing ordinary source-defined cross-file enum in part 1.

To observe the separate runtime-object problem, remain in published and run `../node_modules/.bin/esbuild consumer.cts --platform=node --format=cjs --target=node20 --outfile=esbuild/consumer.cjs`. Copy foreign.cjs into esbuild/foreign.cjs and run `node esbuild/consumer.cjs`. This transform succeeds but execution fails with TypeError because its Code member read has no runtime object to read. It did not obtain declaration-file constants from the type checker. Import type would not supply a runtime Code value either.

The [Handbook's ambient const-enum pitfalls](https://www.typescriptlang.org/docs/handbook/enums.html#const-enum-pitfalls) describes this publication/version problem and a deconstification workflow. An application can use internal const enums when its actual transforms and consumers support them. A library must decide which runtime values and declarations it promises, including consumers that do not inline declaration constants. Avoid describing every exported source const enum as broken, every ordinary enum as universally compatible, or every const object as zero emitted data.

### 4) **Common confusion**

Const enum does not mean a table is absent under every option. PreserveConstEnums can retain a table while reads are inlined; isolated source compilation can retain runtime references. Even then, const-enum object-value operations remain restricted by the checker.

A source-defined exported const enum differs from an ambient const enum in a declaration file. Current esbuild and Babel can transform ordinary source definitions into working values. An ambient declaration does not supply those values, and whole-program substitution can become stale relative to runtime behavior. These are specific contracts to test, not a ban on cross-file imports.

### 5) **Performance note**

The inspected output shows which tables, property reads and constants remain in each tested mode. It does not establish a fastest representation, a fixed byte saving, a per-enum memory amount or a workload speedup. Repeated inlining can also repeat values while object representations retain real data. Choose the required publication/toolchain contract first; use actual bundle and runtime measurements if size or latency motivates the choice.

### 6) **Mentor note**

Ask which observation distinguishes the three TypeScript outputs even though their console results match. Then ask why the declaration-only constant consumer can print 1 while current returns 2, and why the separately transformed consumer needs a real Code object. A sound answer identifies the value producer rather than blaming all single-file tools.

For practice, repair the published fixture with a real constant-object contract. Replace its ambient const enum with export declare const Code: { readonly Ready: 2 }, keep current's declaration and add exports.Code = Object.freeze({ Ready: 2 }) to foreign.cjs. Rebuild with isolatedModules and erasableSyntaxOnly, copy the provider and verify TypeScript and esbuild consumers both print 2 2 true. Remove exports.Code again to demonstrate that the declaration alone still cannot supply a runtime object. This exercise changes the public value contract deliberately; a production migration also needs its actual consumer/API checks.
