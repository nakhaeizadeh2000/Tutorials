## 3.3. Nominal enum patterns — branding vs enums

### 1) **Branded string unions for domain ids** (nominal-flavored identity without emit)

**Definition** — `type UserId = string & { readonly __brand: "UserId" }` (or template-flavored `` `user_${string}` `` intersections) creates *incompatible* string types: `UserId` and `OrderId` never interchange, while both remain strings at runtime (zero emit — the brand erases). [02/1.3](<../../../02 The Type System Core/sections/1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>) owns the mechanic; [04/3.2](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>) owns object application — this promise owns the *choice*: branded unions vs enums for domain identity.

**What problem it solves / history** — stringly-typed ids (`userId: string`, `orderId: string` — interchangeable, so `charge(orderId)` with a user id compiled) caused cross-entity bugs that tests rarely caught (values look valid — wrong entity, right shape). Brands make confusion a type error (`UserId` ≠ `OrderId` structurally) while keeping strings everywhere (JSON, logs, URLs unchanged) — nominal safety with zero runtime or serialization cost.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), brand domain ids and external handles (user/order/session/payment ids — anything crossing trust or entity boundaries); construct through validated factories (`UserId.parse(raw)` returning `UserId | undefined`) — never cast at call sites. Prefer template-flavored brands (`` `user_${string}` ``) when the prefix aids debugging; plain intersection brands when it doesn't.

**Runnable example** — confusion becomes a type error (good vs bad, `tsc --strict`):

```typescript
// good — branded ids: cross-entity confusion errors, runtime stays strings
type UserId = string & { readonly __brand: "UserId" };
type OrderId = string & { readonly __brand: "OrderId" };
function makeUserId(raw: string): UserId | undefined {
  return raw.startsWith("u_") ? raw as UserId : undefined; // validated once, at the factory
}
function charge(order: OrderId, amount: number): string { return `${order}:${amount}`; }
const uid = makeUserId("u_42");
console.log(uid?.toUpperCase() ?? "invalid"); // U_42 — narrowed after validation
// charge(uid as OrderId, 9); // only via cast (review-visible); direct passing errors:
// const bad: OrderId = uid as unknown as OrderId; // laundering (the review flag, not the pattern)

// bad — stringly ids interchange silently
function chargeBad(orderId: string, amount: number): string { return `${orderId}:${amount}`; }
console.log(chargeBad("u_42", 9)); // u_42:9 — user id charged as order (compiles, wrong entity)
// fix — branded params: charge(uid, 9) errors without the cast (confusion caught at the call)
```

**Common confusion** — "brands validate" — brands *distinguish* (UserId vs OrderId); factories *validate* (parse narrows `string` → `UserId`) — two halves, both required (brand without factory is cast-everywhere; factory without brand returns plain `string`). "brands cost runtime" — erase fully (intersection with object-literal brand emits nothing — values stay plain strings in JSON/logs). "template brands (`user_${string}`) replace intersection brands" — prefix aids debugging *and* constrains shape loosely — combine (`type UserId = `user_${string}` & {brand}`) when both help, either alone when one suffices.

**Performance note** — zero emit/runtime delta (brands vanish); factory validation costs one check per boundary crossing (same as any parse — budgeted, explicit). The dividend is deleted cross-entity incidents, not speed.

**Mentor note** — pass a user id to an order-id parameter live and read the brand-mismatch error — nominal safety in one diagnostic. Exercise: brand one stringly id pair end-to-end (type + factory + call sites) and count the casts required (zero, when factories own construction). Review gate: `as UserId` outside factories fails review.

### 2) **When enum identity wins** (foreign codes, reverse debugging, ambient tables)

**Definition** — three identity needs favor enums over brands: foreign-protocol numeric codes (vendor tables mirrored as numeric members — reverse lookup debugs wire values); reverse-debugging workflows (operators resolving codes to names at 2am — `E[code]` tables, display-only); ambient declarations (`.d.ts` mirrors where const-object ambient forms add no value). In each, the enum's *value identity* (a runtime table with a canonical name) serves needs brands (type-only distinctions) cannot.

**What problem it solves / history** — brand absolutism ("never enums") forced foreign numeric codes into branded-number unions (`type Code = number & {brand}`) that *couldn't* reverse-debug (no table — `187` stayed opaque) and ambient tables into const-object declarations that foreign tooling didn't recognize. Identity needs split by *runtime presence*: brands distinguish (compile-time), tables resolve (runtime) — confusing the two deletes whichever half the use case needed.

**Modern guidance** — as of TypeScript 5.9 era, choose enums when the workflow needs the *table* (reverse debugging, foreign mirroring, `Object.values` enumeration with nominal members); choose brands when the workflow needs *distinction* (same-shaped ids that must not interchange). Document the choice on the declaration (`// enum: reverse-debugging needs the table` vs `// brand: distinction without emit`).

**Runnable example** — table needs vs distinction needs (good vs bad, `tsc --strict`):

```typescript
// good — enum where the table serves (foreign codes + reverse debugging)
enum Vendor { Ok = 0, Busy = 1 }
function labelV(code: number): string { return Vendor[code] ?? `code:${code}`; } // table resolves
console.log(labelV(1), labelV(9)); // Busy code:9 — debugging served by the table

// good — brand where distinction serves (same-shaped ids, no table needed)
type SessId = string & { readonly __brand: "Sess" };
function resume(s: SessId): string { return `resumed ${s}`; }
const s: SessId = "s_1" as SessId; // factory-simplified for the demo (factories own this in prod)
console.log(resume(s)); // resumed s_1 — distinction without any table

// bad — brand where a table was needed (opaque codes, no resolution)
type VCode = number & { readonly __brand: "V" }; // distinguishes, but labelV-equivalent impossible (no table)
// fix — Vendor enum: table needs are enum territory (record the reason per 2.3's stamp)
```

**Common confusion** — "one identity tool suffices" — tables *resolve* (value→name at runtime), brands *distinguish* (type-level incompatibility) — orthogonal needs, occasionally coexisting (branded enum *members*? overkill — pick per need). "reverse debugging justifies all enums" — only *operator-facing* numeric codes (logs, dashboards, dumps humans read) — application-internal codes debug via member switches better. "ambient tables prefer brands" — ambient *const objects* and ambient *enums* both describe foreign shapes — match the foreign form (enum table → ambient enum; plain constants → ambient const object).

**Performance note** — tables cost emit bytes (numeric reverse doubles); brands cost zero — identity-choice has bundle implications favoring brands where tables serve nothing. Debug-path lookups (O(1) property reads) never gate performance either way.

**Mentor note** — ask "table or distinction?" per identity need — one question routing enums vs brands correctly. Exercise: classify five identity needs in the codebase (ids → brands; vendor codes → enums; statuses → unions) — the taxonomy exercise that ends "which nominal tool?" debates permanently.

### 3) **Choosing nominal flavor** (brand vs enum vs opaque class — the identity table)

**Definition** — three flavors, one table: *brands* (type-only distinction, zero emit, JSON-transparent — domain ids, handles); *enums* (runtime tables + nominal members — foreign codes, reverse debugging, ambient mirrors); *opaque classes* (private-field identity + methods — rich domain objects with behavior, `instanceof` narrowing). Flavor follows need: distinguish → brand; resolve/enumerate → enum; behave → class.

**What problem it solves / history** — nominal needs picked tools by familiarity (classes for ids — allocation + serialization friction; enums for ids — emit + erasability friction; brands for behavior — no methods to attach) — each mismatch taxed its use case until rewritten. The table routes upfront: ids (brand), codes-with-tables (enum), entities-with-behavior (class) — three needs, three tools, no rewrites.

**Modern guidance** — as of TypeScript 5.9 era, default ids to brands, codes-with-tables to enums (recorded), behavior-rich entities to classes — and re-test when needs change (an id gaining methods graduates brand → class; a table losing its debugging need migrates enum → union). Document the flavor choice where the next author will question it (the declaration's doc comment).

**Runnable example** — three flavors, three needs (good vs bad, `tsc --strict`):

```typescript
// good — brand distinguishes, enum resolves, class behaves: each need its tool
type KitId = string & { readonly __brand: "Kit" };
enum KCode { Ok = 0, Low = 1 }
class Battery {
  readonly #charge: number; // private-field identity (hard nominality + behavior)
  constructor(charge: number) { this.#charge = charge; }
  usable(): boolean { return this.#charge > 20; }
}
const kit = "k_7" as KitId; // factory-owned in prod (simplified here)
console.log(kit.toUpperCase(), KCode[KCode.Low] ?? "?", new Battery(50).usable()); // K_7 Low true

// bad — class for a plain id (allocation + serialization friction for zero behavior)
class IdBox { constructor(public raw: string) {} } // behaves like a string with extra steps
// fix — KitId brand: distinction without allocation, JSON-transparent, zero emit
console.log(new IdBox("k_7").raw.toUpperCase()); // K_7 — correct result, wasteful vehicle
```

**Common confusion** — "private-field classes and brands interchange" — `#field` classes are *hard* nominal (unforgeable without construction — strongest) with allocation + methods; brands are *soft* nominal (forgeable via `as`, factories guard) with zero cost — strength vs cost differ. "one flavor per codebase" — mixed flavors per need is the design (ids brand, codes enum, entities class) — uniformity across *needs* is the actual consistency. "enums with methods close the gap" — enums can't carry methods (no behavior attachment — use classes where behavior lives with identity).

**Performance note** — brands/unions zero-cost; enums table-cost; classes allocation-cost per instance — flavor choice has the clearest performance gradient in nominal design (distinguish free, resolve table-cheap, behave allocation-priced).

**Mentor note** — the three-column table (distinguish/resolve/behave → brand/enum/class) belongs on the domain-modeling guide — one table ending every "how do I model identity?" discussion. Exercise: classify the codebase's nominal types into the three columns — miscolumned entries (class-ids, enum-behaviors) are the refactoring backlog, self-prioritized.
