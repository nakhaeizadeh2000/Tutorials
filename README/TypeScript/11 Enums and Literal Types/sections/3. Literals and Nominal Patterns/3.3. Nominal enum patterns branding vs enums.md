## 3.3. Nominal enum patterns branding vs enums

Separate three questions: which values belong to a domain, which typed callers may interchange them, and which runtime operations need data or state. A brand addresses checker distinction; an enum can supply member types and a generated table; an object or Map can also supply a table. A class can keep per-instance state and behavior. These choices can coexist rather than partitioning every domain into one mandatory category.

The [branding owner](<../../../02 The Type System Core/sections/1. Structural typing/1.3. Nominal typing techniques branding and opaque types.md>) introduces phantom members, and [object branding](<../../../04 Objects Interfaces and Type Aliases/sections/3. Advanced Object Types/3.2. Branded and opaque object patterns for domain safety.md>) applies them to aggregate contracts. Here we compare their enum-related design consequences using complete local programs.

Examples use TypeScript 7.0.2 and Node.js 20.20.2, verified 2026-10-16. Save each named file in a fresh directory without tsconfig.json. Build with `tsc --strict --noUncheckedIndexedAccess --removeComments --target es2022 --module commonjs --outDir out FILE.ts`, then run `node out/FILE.js`. Activate one marked negative in a separate copy and replace --outDir out with --noEmit for its diagnostic. Ids and handles also pass --erasableSyntaxOnly; tables contains a regular enum and intentionally fails that gate.

### 1) **Distinguish checked callers without changing string representation**

Save ids.ts:

```typescript
export {};
declare const domainId: unique symbol;
type UserId = string & { readonly [domainId]: "UserId" };
type OrderId = string & { readonly [domainId]: "OrderId" };
function parseUserId(value: unknown): UserId | undefined {
  return typeof value === "string" && /^u_[0-9]+$/.test(value) ? value as UserId : undefined;
}
function parseOrderId(value: unknown): OrderId | undefined {
  return typeof value === "string" && /^o_[0-9]+$/.test(value) ? value as OrderId : undefined;
}
function charge(order: OrderId, amount: number): string { return `${order}:${amount}`; }
const user = parseUserId("u_42");
const order = parseOrderId("o_7");
if (user === undefined || order === undefined) throw new Error("invalid fixture");
console.log(user.toUpperCase(), charge(order, 9));
console.log(typeof user, JSON.stringify(user), parseUserId("u_") === undefined);
console.log(parseOrderId("u_42") === undefined, parseUserId(42) === undefined);
// charge(user, 9); // TS2345
// charge("o_7", 9); // TS2345: matching text is not yet the branded checker contract
const forged = "u_42" as unknown as OrderId; // Deliberately discard the proof to expose its limit.
console.log(charge(forged, 9));
```

The output is `U_42 o_7:9`, `string "u_42" true`, `true true` and `u_42:9`. Typed code rejects the user/order mix, while the deliberate assertion bypass still runs. DomainId is declared only as a type-level marker and emits no symbol allocation. The checked construction helpers perform the actual regex tests; the brand annotation performs none. The chosen grammar is a local example, not a claim that a syntactically valid id exists in a database or is authorized for a charge. Charge only formats a string; no payment is performed.

An enum represents a finite declared set, so it is a poor fit for an unbounded family of user ids. A finite status and an entity id can still appear together in one model. Use a brand when accidental interchange is worth a distinct typed contract, not as an automatic rule for every string. Serialization preserves the string but does not transmit the phantom proof; parse externally received data again according to the boundary's actual contract.

### 2) **Combine a brand with a real lookup table**

Save tables.ts:

```typescript
export {};
declare const vendorCode: unique symbol;
type VendorCode = (0 | 1) & { readonly [vendorCode]: true };
function parseCode(value: unknown): VendorCode | undefined {
  return value === 0 || value === 1 ? value as VendorCode : undefined;
}
const labels = new Map<number, string>([[0, "Ok"], [1, "Busy"]]);
function label(code: VendorCode): string { return labels.get(code) ?? `code:${code}`; }
const code = parseCode(1);
if (code === undefined) throw new Error("invalid fixture");
console.log(label(code), parseCode(9) === undefined, JSON.stringify(code));
labels.delete(1);
console.log(label(code));
enum Vendor { Ok = 0, Busy = 1 }
console.log(Vendor[Vendor.Busy], Vendor[9]);
// label(1); // TS2345: raw literal is not VendorCode
```

The output is `Busy true 1`, `code:1` and `Busy undefined`. The brand and lookup coexist: table data, not the brand syntax, resolves a name. Map's missing entry is handled explicitly; even an accepted code can lack a label after the separate table changes. A finite Record could require known entries statically, but would still need correct labels and a runtime integrity policy. The [collection owner](<../../../10 Arrays Tuples and Collections/sections/3. Collections and Selection/3.2. Record vs Map indexed access vs hashed keys.md>) explains that choice.

Vendor offers convenient generated numeric reverse entries in a pipeline that transforms enums. Its convenience is different from being the only possible lookup representation or proving provider correctness. A foreign declaration must match actual exports, as the [ambient provider fixture](<../1. Enum Mechanics/1.3. Heterogeneous ambient and computed members.md>) demonstrates. Do not replace or invent a provider merely by changing an ambient declaration's spelling.

Functions can operate on branded primitives, unions or enum members. TypeScript also supports attaching static helpers to an enum object through [namespace merging](https://www.typescriptlang.org/docs/handbook/declaration-merging.html#merging-namespaces-with-classes-functions-and-enums). That is different from giving each primitive member value an instance method, and the runtime namespace needs transformation. Behavior alone therefore does not impose a class; choose a class when its state and lifecycle model serve the API.

### 3) **Compare class representation with actual private-field possession**

Save handles.ts. This standalone fixture uses a small validated string grammar and a class that stores the resulting id. It is an alternative representation, not a stronger parser of the external domain.

```typescript
export {};
declare const userId: unique symbol;
type UserId = string & { readonly [userId]: true };
function parseUserId(value: unknown): UserId | undefined {
  return typeof value === "string" && /^u_[0-9]+$/.test(value) ? value as UserId : undefined;
}
class UserHandle {
  #id: UserId;
  constructor(id: UserId) { this.#id = id; }
  value(): string { return this.#id; }
  static owns(value: unknown): value is UserHandle {
    return typeof value === "object" && value !== null && #id in value;
  }
}
const id = parseUserId("u_42");
if (id === undefined) throw new Error("invalid fixture");
const handle = new UserHandle(id);
console.log(handle.value(), UserHandle.owns(handle), JSON.stringify(handle));
const fake: unknown = Object.create(UserHandle.prototype);
console.log(fake instanceof UserHandle, UserHandle.owns(fake));
if (fake instanceof UserHandle) {
  try { fake.value(); }
  catch (error) { console.log(error instanceof TypeError); }
}
const plain = { value: () => "u_42" };
console.log(UserHandle.owns(plain), UserHandle.owns(null));
// const wrong: UserHandle = plain; // TS2741: missing private element
// new UserHandle("u_42"); // TS2345
```

The output is `u_42 true {}`, `true false`, `true` and `false false`. A plain structural lookalike is rejected by the checker because of the class's private element. At runtime Object.create produces an object with the class prototype but without its private field. It passes instanceof, fails the #id possession check and throws when the method actually reads that field. An assertion could lie to the checker about a class value too; it would not install the private field.

The ordinary JSON serialization is {} because the id is private; this differs from the branded string's JSON. If the API needs a serialized id, call value explicitly or design an intentional serialization method. The [private-elements reference](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Classes/Private_elements) explains actual field access and possession tests. The [access-modifier owner](<../../../06 Classes and Object-Oriented Types/sections/1. Class Type Fundamentals/1.3. Access modifiers and encapsulation public private protected readonly.md>) owns their full semantics and limitations. Private fields enforce access on objects that possess those fields; they are not an application authorization mechanism or proof of a user's identity.

Practice: add `toJSON(): string { return this.value(); }` to UserHandle. Now JSON.stringify(handle) must produce `"u_42"`; the prototype fake must still fail owns and still throw on value. A representation change can alter serialization without altering the checker distinction or the private possession test. Verify those concerns independently.

### 4) **Common confusion**

Checker distinction, a runtime table and private state solve separate problems. A brand does not generate a table, but it can index or accompany one. An enum has member-type rules and convenient numeric output, but arbitrary external numbers still need validation. A class can enforce private field access while accepting any constructor input the implementation allows.

Neither a type assertion nor instanceof creates a private field. Conversely, omitting a class does not prevent behavior: ordinary functions can process branded primitives or enum values. Choose from the required contract rather than a universal brand/enum/class hierarchy.

### 5) **Performance note**

The phantom markers and type intersections erase. The regex tests, Map entries, enum initialization, object allocation and private state remain. This lesson measures no lookup complexity guarantee, byte ratio, validation budget or class-versus-brand speed ranking. A class wrapper changes representation and serialization; whether that cost is justified depends on its actual state, behavior and workload.

### 6) **Mentor note**

Ask the learner which part supplies evidence in each example: regex checks admit the local id grammar, a phantom member distinguishes typed callers, Map stores labels, and #id in value checks private-field possession. Then have them change serialization using the exercise while keeping the fake-object test. A strong explanation avoids treating any one of these mechanisms as proof of all the others.
