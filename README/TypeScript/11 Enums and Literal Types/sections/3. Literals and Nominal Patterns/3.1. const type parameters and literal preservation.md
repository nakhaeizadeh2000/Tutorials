## 3.1. const type parameters and literal preservation

A const type parameter requests const-like inference for fresh argument expressions. Its most useful contrast is an inline object or array whose literals would otherwise widen. It does not recover information already lost in a variable's type, freeze a value, or force a function's published return type to retain precision.

This feature was introduced in TypeScript 5.0. Examples here use TypeScript 7.0.2 and Node.js 20.20.2, verified 2026-10-16. Save each named file in a fresh directory without tsconfig.json. Build with `tsc --strict --noUncheckedIndexedAccess --erasableSyntaxOnly --removeComments --target es2022 --module commonjs --outDir out FILE.ts`, then run `node out/FILE.js`. Activate one marked negative in a separate copy and replace --outDir out with --noEmit for its diagnostic. These checks concern inference; no runtime const-type-parameter mechanism remains in the JavaScript.

### 1) **Compare actual inference at the call**

Save fresh.ts:

```typescript
export {};
function ordinary<T>(value: T): T { return value; }
function precise<const T>(value: T): T { return value; }
const word = ordinary("get");
const exactWord: "get" = word;
const wide = ordinary({ method: "get", paths: ["/a", "/b"] });
const exact = precise({ method: "get", paths: ["/a", "/b"] });
const callerExact = ordinary({ method: "get", paths: ["/a", "/b"] } as const);
wide.method = "post";
wide.paths.push("/c");
console.log(exactWord, wide.method, wide.paths.join(","));
console.log(exact.method, exact.paths.join(","), callerExact.method);
console.log(Object.isFrozen(exact), Object.isFrozen(exact.paths));
// const lost: "get" = wide.method; // TS2322
// exact.method = "get"; // TS2540
// exact.paths.push("/c"); // TS2339
```

The three output lines are `get post /a,/b,/c`, `get /a,/b get` and `false false`. Ordinary identity already preserves the top-level primitive get literal. Its inline object's method is string and its paths are string[], allowing the changes shown. Precise instead infers a readonly get property and a readonly two-element literal tuple for this fresh argument. A caller-side const assertion gives the ordinary helper the corresponding precise input too.

The important benefit is moving an aggregate inference preference into an API you control. It is not a blanket distinction that ordinary generics return string and const generics return literals. Constraints, inference positions and result annotations matter. The [inference owner](<../../../08 Generics Deep Dive/sections/1. Generic Fundamentals/1.2. Inference from arguments and explicit type arguments.md>) explains those relationships; the [TS 5.0 examples](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#const-type-parameters) establish fresh arguments, readonly constraints and the original TS 5.0 behavior. The current constraint comparison below uses the tested TS 7 baseline.

### 2) **Respect preexisting types and the constraint**

Save boundaries.ts:

```typescript
export {};
function mutable<const T extends string[]>(items: T): T { return items; }
function precise<const T extends readonly string[]>(items: T): T { return items; }
const mutableTuple = mutable(["get", "post"]);
mutableTuple.push("get");
const methods = precise(["get", "post"]);
const existing = ["get", "post"];
const fromExisting = precise(existing);
fromExisting.push("patch");
const explicit = precise<string[]>(["get", "post"]);
explicit.push("head");
console.log(mutableTuple.join(","), methods.join(","));
console.log(existing.join(","), Object.is(existing, fromExisting));
console.log(explicit.join(","), Object.isFrozen(methods));
const shared = [1];
function identity<const T>(value: T): T { return value; }
const box = identity({ shared });
box.shared.push(2);
console.log(shared.join(","));
// methods.push("delete"); // TS2339
// mutableTuple.push("delete"); // TS2345
// mutable(methods); // TS4104: readonly tuple is not mutable input
// const pair: readonly ["get", "post"] = fromExisting; // TS2322
// box.shared = [3]; // TS2540
```

The output is `get,post,get get,post`, `get,post,patch true`, `get,post,head false` and `1,2`. On this baseline, the mutable constraint infers a mutable ["get", "post"] tuple. It permits pushing another named element but rejects delete; its static tuple length still says two, despite the actual push. The readonly string[] constraint instead infers a readonly ["get", "post"] tuple and rejects push entirely. A preexisting readonly tuple cannot be passed to mutable. It still accepts existing mutable arrays: readonly in the constraint does not demand a frozen argument or copy the array.

The TS 5.0 release notes describe a string[] fallback for the mutable constraint; an actual run with TypeScript 5.0.4 produces that broader declaration. Running the same fixture with 5.3.3 and 7.0.2 produces the mutable literal tuple. Treat the historical fallback as version-specific, not the current rule for this example.

Existing was already inferred as string[]. The const modifier cannot reconstruct its original two literal elements, and the returned value aliases it. An explicit string[] type argument deliberately selects a mutable broad array too. In box, the fresh object's shared property is readonly to the checker, but it refers to the preexisting mutable number[]; pushing through that reference changes the original array. This is neither a deep freeze nor a snapshot.

Use a readonly constraint when the helper reads array input and should accept readonly tuples. If it genuinely mutates the input, design for that operation instead of adding readonly only to obtain a preferred hover type. [Readonly collections](<../../../10 Arrays Tuples and Collections/sections/1. Array Types/1.2. Readonly arrays and mutable vs frozen arrays.md>) owns the alias and snapshot consequences.

### 3) **Preserve the result only when the return contract expresses it**

Save returns.ts:

```typescript
export {};
function route<T extends string>(method: T): `route:${T}` {
  return `route:${method}`;
}
function wideRoute<const T extends string>(method: T): string {
  return `route:${method}`;
}
const narrow = route("get");
const broad = wideRoute("get" as const);
const explicit = route<string>("get");
function handle(value: "route:get" | "route:post"): string { return value; }
const exact: "route:get" = narrow;
const stillPrefixed: `route:${string}` = explicit;
function shout(value: string): string { return value.toUpperCase(); }
console.log(handle(exact), broad, stillPrefixed, shout(narrow));
// handle(broad); // TS2345
// handle(explicit); // TS2345
// function wrong<const T extends string>(value: T): T { return value.toUpperCase(); } // TS2322
```

The output is `route:get route:get route:get ROUTE:GET`. Ordinary string-constrained generic inference retains get here; the template return exposes route:get. WideRoute intentionally publishes string, so the caller's as const does not rescue its result. Explicit route<string> publishes the patterned type route:${string}, which is broader than the two cases accepted by handle but still narrower than arbitrary string.

Choose a precise return when callers rely on its relationship to the argument. Choose string for a formatter that promises general text. A get literal is already assignable to string, so preserving it does not inherently break a general-string consumer. Nor must every formatter have a const parameter: shout needs no generic relationship at all. The marked wrong helper attempts to promise the original T while returning an uppercase string; the checker rejects that false promise. An assertion would conceal the mismatch rather than implement the relationship.

Practice: add a finite callback table derived from methods in boundaries.ts: `const handlers: Record<(typeof methods)[number], () => string> = { get: () => "read", post: () => "write" };`, then print `handlers.get(), handlers.post()`. Extend only the inline methods argument with delete. The table must fail coverage checking until you add `delete: () => "remove"`. Print `handlers.delete()` to observe remove. Deriving from a prebound string[] instead would produce an open string-key contract and lose this finite coverage check; const inference cannot undo that earlier widening.

### 4) **Common confusion**

Const modifies an inference preference, not the generic body's capabilities or the runtime object's integrity. The constraint helps determine whether an inferred tuple is mutable; variables retain their existing types; explicit type arguments and result annotations can choose broader contracts. Predict each boundary separately instead of treating const as a precision switch for the entire program.

A precise caller-side argument cannot override a function's string return annotation. Conversely, a plain generic may already preserve the literal needed by a template return. Check the actual type relationship before adding assertions or changing an API.

### 5) **Performance note**

Const parameters, readonly modifiers and the literal/template types shown here erase. Their presence does not add freezing, copying or runtime validation; the actual array pushes and template construction remain. These examples measure no checker instantiation cost or runtime speed. Large inferred structures may deserve measurement in a real project, but no cache formula, call-count threshold or universal cheaper-return claim follows from these small examples.

### 6) **Mentor note**

Ask the learner to predict four calls: ordinary identity of a string, const identity of an inline object, const identity of a prebound array and a const helper with a mutable array constraint. Require checker probes and runtime alias observations separately. A strong explanation identifies where the information was retained or already lost, then chooses the return contract from the consumer's needs.
