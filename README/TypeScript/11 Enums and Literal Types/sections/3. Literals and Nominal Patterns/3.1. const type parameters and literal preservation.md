## 3.1. `const` type parameters and literal preservation

### 1) **What `<const T>` changes** (declaration-side literal preservation, TS 5.0)

**Definition** — `function f<const T>(x: T): T` infers *as if* the argument were `as const`: `f("get")` gives `T = "get"` (not `string`), `f(["a", 1])` gives `readonly ["a", 1]` (tuple + literals + readonly), `f({ x: 1 })` gives `{ readonly x: 1 }`. Widening suppressed and readonly added at inference — driven by the *declaration*, so no call site changes.

**What problem it solves / history** — literal-preserving helpers previously needed `as const` at *every call* (`f("get" as const)`, `useState("idle" as Status)`) — precision owned by callers, who forgot it inconsistently (one widened call poisoned downstream exhaustiveness while siblings stayed narrow). `const` type parameters (TS 5.0) moved ownership to the declaration: the helper *promises* literal inference, and every call — present and future — inherits it without ceremony.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), declare `<const T>` on helpers whose contract depends on literals (route builders, event registrars, config factories — anywhere downstream exhaustiveness or template composition consumes the result). Keep plain `<T>` where widening serves callers (accumulators, formatters returning `string`, numeric math).

**Runnable example** — precision by declaration (good vs bad, `tsc --strict`):

```typescript
// good — const param: every call infers literally, no call-site ceremony
function route<const T extends string>(method: T): `route:${T}` { return `route:${method}`; }
const r = route("get"); // "route:get" — literal preserved by declaration
function handle(m: "route:get" | "route:post"): string { return m; }
console.log(handle(r)); // route:get — exhaustiveness-ready without as const anywhere

// bad — plain param: widening at every call unless each caller remembers as const
function routeBad<T extends string>(method: T): string { return `route:${method}`; }
const rb = routeBad("get"); // string — literal lost (widened at inference)
// handle(rb); // error TS2345 — string not assignable to literals (correctly!)
// fix — <const T> + literal return: precision owned once, inherited everywhere
const rb2 = routeBad("get" as const); // per-call rescue (works, doesn't scale)
console.log(rb2.toUpperCase()); // ROUTE:GET — rescued once, forgotten next call
```

**Common confusion** — "`const T` makes the parameter readonly" — `const` affects *inference* (literals kept, tuples/objects inferred readonly) — the parameter is still a normal type variable (mutable operations on `T` inside the body follow ordinary rules). "`const` params replace `as const` everywhere" — call-site `as const` still serves one-off narrowing under plain `<T>` (library code you don't own); `<const T>` serves helpers you control. "const params prevent widening entirely" — explicit type arguments still widen on demand (`route<string>("get")` → `string`) — callers override deliberately, never accidentally.

**Performance note** — literal instantiations cache per distinct argument (one entry per literal — trivial for curated sets); readonly-tuple inference adds tuple instantiations per array argument (fine for small literals; prefer explicit `string` params for dataset-scale array inputs — see 09/3.3 size guidance).

**Mentor note** — delete `as const` from five call sites after adding `<const T>` to the helper — the diff *removes* ceremony while *adding* precision, which sells declaration-side ownership instantly. Exercise: find one helper whose JSDoc says "pass literals with as const" and move the promise into `<const T>` — documentation becomes compiler behavior.

### 2) **`const` params vs `as const` arguments** (who owns the precision decision)

**Definition** — two ownership models for the same precision: `as const` at the call (`f("get" as const)` — caller decides per call, works with any helper including library code) vs `<const T>` on the declaration (author decides once, inherited by all calls). Same inferred result (`"get"`); different owner, different scaling: per-call ceremony vs per-declaration promise.

**What problem it solves / history** — `as const`-at-calls scaled with call count (50 calls → 50 assertions to audit, each independently forgettable) while `<const T>` scales with helper count (one declaration covers all present and future calls). Teams that standardized call-site assertions paid perpetual audit tax; teams that moved ownership to declarations paid once. Neither replaces the other: library boundaries (helpers you don't own) still need call-site assertions.

**Modern guidance** — as of TypeScript 5.9 era, own precision at the declaration for project helpers (`<const T>` on builders/registrars/factories); assert at the call for foreign helpers (`as const` into library generics). When both appear (`constHelper("x" as const)` — harmless redundancy), prefer removing the call-site assertion (the declaration already promises) to keep calls clean.

**Runnable example** — ownership decides scaling (good vs bad, `tsc --strict`):

```typescript
// good — declaration owns precision: N calls, zero assertions, all narrow
function on<const E extends string>(event: E, cb: (p: string) => void): E {
  void cb; return event;
}
const e1 = on("click", () => undefined); // "click" — no assertion needed
const e2 = on("keydown", () => undefined); // "keydown" — second call equally narrow
console.log(e1.toUpperCase(), e2.toUpperCase()); // CLICK KEYDOWN

// bad — caller owns precision: N calls, N assertions, each forgettable
function onBad<E extends string>(event: E, cb: (p: string) => void): E {
  void cb; return event;
}
const b1 = onBad("click" as const, () => undefined); // "click" — asserted (works)
const b2 = onBad("keydown", () => undefined); // string — forgotten (widened silently)
// fix — <const E>: move ownership to the declaration; b2-style widening becomes impossible
console.log(b1.toUpperCase(), b2.toUpperCase()); // CLICK KEYDOWN — same output, weaker guarantee
```

**Common confusion** — "both forms always agree" — `on("click")` vs `onBad("click")` differ (`"click"` vs `string`) — ownership changes the *default*, not just the ceremony. "redundant `as const` under `<const T>` harms" — harmless (assertion agrees with inference) but noisy — remove for cleanliness, not correctness. "library helpers should all be const-paramed" — library authors choose widening deliberately (accumulators, math, formatters) — respect their default; assert at your calls when you need literals.

**Performance note** — identical check cost (same literal instantiations either way) — ownership is a scaling-of-correctness question (audit N calls vs 1 declaration), not a performance one.

**Mentor note** — count `as const` arguments per helper across the codebase — helpers with 5+ call-site assertions are `<const T>` candidates; convert the top three and delete the assertions. Rule: project helpers with literal-dependent contracts declare `<const T>`; foreign-helper calls assert locally.

### 3) **When `const` params over-narrow** (widen the return, not the source)

**Definition** — `<const T>` keeps `"get"` where callers wanted `string` (formatters, loggers, accumulators returning human text or merged collections) — downstream unions widen unexpectedly (`"get"`-specific branches appearing in general-string pipelines). The fix mirrors 09/3.3's joint rule: widen at the *return* (`: string`), never by removing `<const>` (which re-widens every caller's inference).

**What problem it solves / history** — const-paramed formatters (`label<const T>(x: T): T` returning `"get"` where `string` was promised) poisoned downstream unions with unexpected literals (exhaustive switches demanding `"get"` branches in generic pipelines). Return-side widening (`: string`) restores the promise while keeping call-site inference intact for helpers that *do* need literals — precision where consumed, generality where published.

**Modern guidance** — as of TypeScript 5.9 era, pair `<const T>` inputs with deliberate return choices: literal returns (`` `route:${T}` ``, `T` itself) where downstream exhaustiveness/composition consumes precision; `string`/wide returns where the helper publishes general text. Probe joints (`helper("lit")` hover — `"lit"` or `string`?) against the downstream contract before choosing.

**Runnable example** — narrow in, wide out where promised (good vs bad, `tsc --strict`):

```typescript
// good — const input, string output: precision consumed internally, generality published
function shout<const T extends string>(x: T): string { return x.toUpperCase(); }
const s: string = shout("get"); // string — downstream unions unaffected
console.log(s); // GET

// bad — const input leaking literals into general pipelines
function shoutBad<const T extends string>(x: T): T { return x; } // promises literal identity...
const sb = shoutBad("get"); // "get" — ...which downstream treats as a case to handle
function useStr(x: string): string { return x; }
console.log(useStr(sb)); // GET-consumable, but sb's type over-promises precision here
// fix — shout (return string): the helper's contract decides, not its inference
```

**Common confusion** — "over-narrowing is inference failing" — inference succeeding *too well* for the contract — the fix is contractual (return annotation), never mechanical (removing `const`). "wide returns waste the const param" — the param still *accepts* literally (constraints/exhaustiveness at input preserved); only the *output* widens — input precision and output generality compose freely. "callers can widen with as string" — per-call rescue that rots (next caller forgets) — return-side widening fixes all callers permanently.

**Performance note** — return-side widening *reduces* downstream check cost (one `string` vs N literal branches in switches) — widen where generality serves, narrow where exhaustiveness serves; the joint is also a performance decision.

**Mentor note** — hover-probe every `<const T>` helper's return against its downstream contract (`"lit"` where `string` promised = over-narrowing) — one probe per helper finds the leak in seconds. Exercise: convert one leaking helper to a wide return and count the downstream literal-branches that vanish (each was precision nobody consumed).
