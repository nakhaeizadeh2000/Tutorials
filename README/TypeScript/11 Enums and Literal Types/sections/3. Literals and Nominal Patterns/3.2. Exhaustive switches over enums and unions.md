## 3.2. Exhaustive switches over enums and unions

### 1) **Enum-member exhaustiveness** (never-sink over enum inputs)

**Definition** — `switch (dir) { case Direction.Up: …; default: assertNever(dir) }` with `const assertNever = (x: never): never => { throw … }` proves every member handled: adding `Down` breaks the build at the `default` (argument of type `Direction.Down` not assignable to `never`). The 07/3.2 mechanic applied to enum inputs — same sink, same proof, member-typed branches.

**What problem it solves / history** — `default: break` / `default: return fallback` on enum switches silently absorbed new members (the feature shipped; the switch ignored it — stale-state bugs with no compile signal). The `never` sink converts member-addition from a silent runtime gap into a compile error listing every unhandled site — the compiler enumerates the migration work.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), sink every `switch` over a finite set (enum or union) that drives behavior (reducers, routers, renderers, serializers); allow bare `default` only for genuinely open inputs (user strings, `number` codes from foreign systems — where exhaustiveness is impossible by definition).

**Runnable example** — new member breaks the build (good vs bad, `tsc --strict`):

```typescript
// good — never sink: adding a member errors at every unhandled switch
enum Dir2 { Up = "UP", Down = "DOWN" }
function assertNever(x: never): never { throw new Error(`unhandled ${String(x)}`); }
function arrow(d: Dir2): string {
  switch (d) {
    case Dir2.Up: return "^";
    case Dir2.Down: return "v";
    default: return assertNever(d); // d: never here IFF all members handled
  }
}
console.log(arrow(Dir2.Up)); // ^

// bad — default-break absorbs new members silently
function arrowBad(d: Dir2): string {
  switch (d) {
    case Dir2.Up: return "^";
    default: break; // Dir2.Down falls through silently (no error when Down was added)
  }
  return "?"; // stale fallback ships for Down
}
// fix — assertNever default: member-addition becomes a compile error listing this site
console.log(arrowBad(Dir2.Down)); // ? — wrong answer, zero diagnostics
```

**Common confusion** — "exhaustiveness requires unions" — works identically over enums (members narrow per `case` like discriminants) — the sink cares about *finiteness*, not the declaration form. "`default: assertNever` handles the default" — it *rejects* the default (throws) while *proving* unreachability — reachable defaults indicate missing cases, not handled ones. "small switches don't need sinks" — two-member enums grow a third member eventually — sink cost is one line, paid once, protecting every future addition.

**Performance note** — zero runtime cost in the common path (sink unreachable — one function definition, never called); new-member builds fail at compile time (error, not slower code). The economics are pure: one line prevents one incident class permanently.

**Mentor note** — add a third member live and watch the good switch error while the bad one stays green — coverage-proof vs coverage-theater in one enum edit. Rule: behavior-driving switches over finite sets sink `never`; `default: break` on such switches fails review.

### 2) **Reverse-mapping widening trap** (numeric lookups escape literal precision)

**Definition** — `Direction[code]` types `string` (widened — reverse tables erase member identity), so switching on it (or returning it into a literal-typed position) silently drops exhaustiveness: the `never` sink sees `string` (infinite, unexhaustible) instead of members, and every branch becomes best-effort string matching. Numeric reverse lookup is a display tool (see 1.1 promise 2) — never a control-flow input.

**What problem it solves / history** — `switch (Direction[code])` with string cases *looked* exhaustive (cases for every member name) while proving nothing (input typed `string` — any typo'd case compiled, missing cases never errored). The trap bit hardest during enum-to-display refactors: logic moved onto display strings "temporarily" and stayed, with exhaustiveness silently surrendered at the move.

**Modern guidance** — as of TypeScript 5.9 era, never branch on reverse-mapped strings — branch on members (or validated unions) and *render* via reverse maps at the leaves. When a numeric code enters the system, validate it into the enum first (`code in Direction ? …` with a predicate, or a lookup returning `Direction | undefined` narrowed before switching) — boundary validation restoring member precision before logic.

**Runnable example** — widened input defeats the sink (good vs bad, `tsc --strict`):

```typescript
// good — validate code into the enum, then switch on members (sink intact)
enum Lvl { Low, High }
function fromCode(code: number): Lvl | undefined {
  return code === 0 ? Lvl.Low : code === 1 ? Lvl.High : undefined; // boundary validation
}
function urgent2(l: Lvl): string {
  switch (l) {
    case Lvl.Low: return "no";
    case Lvl.High: return "YES";
    default: return assertNever(l); // never — adding a member breaks here (good)
  }
}
console.log(urgent2(fromCode(1) ?? Lvl.Low)); // YES

// bad — switch on the widened reverse lookup: sink sees string, proves nothing
function urgentBad(code: number): string {
  const name = Lvl[code] ?? "unknown"; // string — member identity lost at lookup
  switch (name) {
    case "Low": return "no";
    // case "High" missing — no error (input is string, cases are best-effort)
    default: return "???"; // silent gap ships
  }
}
// fix — fromCode boundary + member switch: precision restored before logic runs
function assertNever(x: never): never { throw new Error("unreachable"); }
console.log(urgentBad(1)); // ??? — correct input, unhandled branch, zero diagnostics
```

**Common confusion** — "string cases over reverse lookups are exhaustive" — cases over `string` input are *filters*, not proofs (missing cases never error — the sink needs a finite input type to bite). "validation duplicates the switch" — validation *restores* the finite type the switch proves over — two layers (validate-then-prove) vs zero layers (widened hope). "`in` checks validate enums" — `code in Lvl` checks *keys and reverse keys* (`"0"`, `"Low"` both present — true for garbage like `"toString"`? no — but reverse entries pollute the check: `0 in Lvl` true, `"Low" in Lvl` true, `2 in Lvl` false —usable with care, explicit validators preferred).

**Performance note** — boundary validation costs one comparison per entry (negligible vs the switch it protects); widened switches cost missing-branch incidents (unbounded). Validate once at ingestion, switch narrowly everywhere downstream.

**Mentor note** — hover `Lvl[code]` (`string`) next to `fromCode(1)` (`Lvl | undefined`) — widened vs restorable precision in one tooltip pair. Exercise: convert one reverse-lookup switch to validate-then-member-switch and count the new `never`-sink protections (each a future member-addition caught).

### 3) **Union exhaustiveness parity** (same sink, zero emit, erasable proof)

**Definition** — `"up" | "down"` switches sink identically: `default: assertNever(u)` with `u: never` iff all members cased — same proof, same member-addition breakage, zero emit (no table), erasable under every toolchain. Parity means the safety argument for enums *evaporates*: unions match enums on exhaustiveness while winning on erasure, composition, and template-readiness.

**What problem it solves / history** — "but enums are safer for switches" was the last safety-flavored objection to union migration (all other objections being values/emit/interop — legitimate, narrow). Parity demonstrations (same sink, same breakage-on-addition, side by side) retire the objection: safety never distinguished the forms — only values, emit, and interop do (the recorded survivor reasons, nothing more).

**Modern guidance** — as of TypeScript 5.9 era, sink union switches exactly like enum switches (same `assertNever`, same `default` position, same review rule); cite parity in migration PRs to preempt safety objections; keep the sink helper shared (`assertNever` in one utils module — not per file, not per domain).

**Runnable example** — parity side by side (good vs bad, `tsc --strict`):

```typescript
// good — union sink: identical proof, zero emit
function assertNever(x: never): never { throw new Error(`unhandled ${String(x)}`); }
type DirU2 = "up" | "down";
function arrowU(d: DirU2): string {
  switch (d) {
    case "up": return "^";
    case "down": return "v";
    default: return assertNever(d); // never — add "left" and this errors (parity with enums)
  }
}
console.log(arrowU("down")); // v — same guarantee as the Dir2 switch in promise 1

// bad — unsunk union switch (the objection's actual target — unsunk code, not unions)
function arrowUBad(d: DirU2): string {
  if (d === "up") return "^";
  return "v"; // "down" assumed by else — new member "left" silently maps to "v"
}
// fix — sinked switch: the discipline (sink), not the form (enum/union), provides safety
console.log(arrowUBad("down" as DirU2)); // v — correct today, silent tomorrow
```

**Common confusion** — "parity means forms are interchangeable" — safety parity only (values/emit/interop still differ — survivors stay survivors). "sinks require the helper" — inline `(x: never): never => { throw … }` works, but shared `assertNever` standardizes messages and stack traces — convention over repetition. "union switches need `const` assertions" — literal-typed parameters (`d: DirU2`) narrow per `case` without any assertion — narrowing needs finite *types*, not const values.

**Performance note** — identical profile to enum sinks (zero runtime cost when covered; compile error when not) minus table emit — parity at lower bundle cost.

**Mentor note** — add `"left"` to both `Dir2` and `DirU2` and watch both switches error identically — parity demonstrated, objection retired, in two edits. Migration-PR template: "safety: parity (sinks on both forms); values: none needed; emit: deleted" — three lines preempting three objections.
