## 3.2. Exhaustive switches over enums and unions

A never sink checks that a handler has no remaining alternative in its declared input type. Enum members and literal-union members can both supply that finite input. A numeric enum's reverse lookup supplies a name string instead, and an unchecked external number does not become validated merely because it is assignable to an enum.

This lesson applies the [control-flow and runtime fallback owner](<../../../07 Unions Intersections and Narrowing/sections/3. Control Flow Narrowing/3.2. Exhaustiveness never and switch narrowing.md>) to enum-specific boundaries. Examples use TypeScript 7.0.2 and Node.js 20.20.2, verified 2026-10-16. Save each named file in a fresh directory without tsconfig.json. Build with `tsc --strict --noUncheckedIndexedAccess --removeComments --target es2022 --module commonjs --outDir out FILE.ts`, then run `node out/FILE.js`. Activate one marked negative in a separate copy and replace --outDir out with --noEmit for its diagnostic. These enum programs require transformation and fail --erasableSyntaxOnly with TS1294.

### 1) **Compare the same coverage check on both representations**

Save coverage.ts:

```typescript
export {};
enum Direction { Up = "UP", Down = "DOWN" }
type DirectionValue = "UP" | "DOWN";
function unexpected(value: never): never {
  throw new Error(`unhandled ${String(value)}`);
}
function arrow(direction: Direction): string {
  switch (direction) {
    case Direction.Up: return "^";
    case Direction.Down: return "v";
    default: return unexpected(direction);
  }
}
function arrowValue(direction: DirectionValue): string {
  switch (direction) {
    case "UP": return "^";
    case "DOWN": return "v";
    default: return unexpected(direction);
  }
}
function assumedDown(direction: DirectionValue): string {
  return direction === "UP" ? "^" : "v";
}
console.log(arrow(Direction.Up), arrowValue("DOWN"), assumedDown("DOWN"));
const external: unknown = "LEFT";
try { arrow(external as Direction); } // Deliberately bypass checking to observe the runtime policy.
catch (error) { console.log(error instanceof Error ? error.message : "unexpected error"); }
// arrowValue("LEFT"); // TS2345
```

The output is `^ v v`, then `unhandled LEFT`. The casts and never annotation erase; the helper, throw and switch remain. The deliberate invalid call reaches the throwing branch even though the declared enum input was statically covered. Without that throw, the type annotation would not insert a runtime failure.

Add Left = "LEFT" to Direction and add | "LEFT" to DirectionValue, leaving the functions unchanged. Both helper calls fail with TS2345 because Left remains after the handled cases. AssumedDown still compiles and would return v for LEFT. Repair arrow and arrowValue with their respective left cases returning `<`; then `console.log(arrow(Direction.Left), arrowValue("LEFT"), assumedDown("LEFT"));` prints `< < v`. Coverage catches an omitted alternative; it does not prove that a branch returns the correct arrow. The [Handbook exhaustiveness example](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#exhaustiveness-checking) establishes the static remaining-type check.

Use this signal when adding an alternative should require revisiting behavior. A handler deliberately ignoring part of an event stream can have an explicit ignore policy instead. The choice is about intended behavior; neither every finite switch nor only public switches require one universal default policy.

### 2) **Parse values before dispatching, and keep reverse names separate**

Save codes.ts:

```typescript
export {};
enum Level { Low = 0, High = 1 }
function unexpected(value: never): never { throw new Error(`unhandled ${String(value)}`); }
function parseLevel(value: unknown): Level | undefined {
  return value === Level.Low ? Level.Low : value === Level.High ? Level.High : undefined;
}
function urgent(level: Level): string {
  switch (level) {
    case Level.Low: return "no";
    case Level.High: return "YES";
    default: return unexpected(level);
  }
}
function reverseName(code: number): string | undefined { return Level[code]; }
function staleDisplayLogic(code: number): string {
  switch (reverseName(code)) {
    case "Low": return "no";
    default: return "???";
  }
}
for (const input of [1, 0, 2, "1", "High", "toString", null]) {
  const level = parseLevel(input);
  console.log(String(input), level === undefined ? "invalid" : urgent(level));
}
console.log(reverseName(1), reverseName(99), staleDisplayLogic(1));
console.log("toString" in Level, Object.hasOwn(Level, "toString"), "High" in Level, 1 in Level);
const unvalidated: number = 99;
try { urgent(unvalidated); } // Broad number is accepted by this enum type; it is not a parser.
catch (error) { console.log(error instanceof Error ? error.message : "unexpected error"); }
// const definite: string = reverseName(99); // TS2322
// function falseProof(code: number): never { return unexpected(reverseName(code)); } // TS2345
```

The seven loop lines are `1 YES`, `0 no`, then `2 invalid`, `1 invalid`, `High invalid`, `toString invalid` and `null invalid`. The two displayed 1 inputs differ: one is a number and one a string. The final lines are `High undefined ???`, `true false true true` and `unhandled 99`.

The parser returns only recognized values. The explicit undefined test preserves valid Low = 0, which a truthiness test would accidentally discard. An enum parameter's acceptance of a broad number is a checker compatibility rule, not evidence that 99 names a member. The throwing default supplies a useful failure policy for that invalid call but does not replace parsing.

Under noUncheckedIndexedAccess, an arbitrary numeric reverse read is string | undefined. Without that option it is statically string, although the missing entry still produces undefined at runtime. It is not the literal union Low | High. StaleDisplayLogic therefore has no finite coverage relationship to Level: removing its High case leaves a valid fallback that returns ???. Trying to pass the open lookup into a never sink is rejected, as the marked falseProof shows; it does not silently become an exhaustiveness proof.

The in operator checks property names, including inherited ones. The actual toString result is true, while hasOwn is false; High and the reverse numeric key are both present. Neither general key-membership test is the value parser above. [MDN's in contract](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/in) distinguishes presence and the prototype chain. The [numeric-enum owner](<../1. Enum Mechanics/1.1. Numeric enums auto values and reverse mapping.md>) owns the generated table, duplicate alias policy and index-option contrast.

A validated finite union of names could drive a switch, if names are the actual domain. The error is assuming that an unvalidated reverse read already supplies that union, not using strings in control flow at all.

### 3) **Check additions at the parser and the handler separately**

For practice, add Critical = 2 to Level in codes.ts. Urgent's sink now fails, so add its case returning NOW. The program builds again, but its existing input 2 still prints invalid: parseLevel never admitted the new code. Extend the parser with the explicit Critical comparison; now the input 2 prints NOW and 99 still reaches the deliberate throwing-default test. The compiler did not prove the parser complete simply because its return type was Level | undefined.

Also verify the reverse-name fallback: it still prints ??? for High after the repair because no member-switch change fixes staleDisplayLogic. If that display logic should classify valid levels, delegate to the validated member handler rather than maintaining a parallel name-based classification. If unknown names intentionally need a fallback, document that policy instead of casting the name to a finite type.

### 4) **Common confusion**

Exhaustiveness is relative to the declared and narrowed input at one point. An assertion, untyped caller or broad numeric value can still reach a supposedly impossible runtime branch. A never annotation does not validate input or insert a throw; this helper's actual body throws.

A new enum member can expose incomplete switches while leaving a restrictive parser unchanged and compiling. Test accepted inputs and behavior after resolving the diagnostic, not just the disappearance of TS2345. A fallback may also be intentional; coverage does not decide product semantics.

### 5) **Performance note**

Enum initialization, property lookup, comparisons, switches and the throwing helper remain in emitted JavaScript. The type operations erase, but no check here measures dispatch speed, validation cost, bundle removal or incident prevention. A handled branch does not call the default helper in these programs; invalid input does. Keep that bounded observation separate from claims of zero runtime cost or permanent prevention of a bug category.

### 6) **Mentor note**

Ask the learner to add the new enum member, fix the handler and predict the parser's output before running it. A strong answer catches the independently stale parser. Then ask why toString in Level succeeds and why a missing reverse lookup can still be undefined when the unchecked-index option is off. These questions distinguish actual runtime membership, declared types and static coverage.
