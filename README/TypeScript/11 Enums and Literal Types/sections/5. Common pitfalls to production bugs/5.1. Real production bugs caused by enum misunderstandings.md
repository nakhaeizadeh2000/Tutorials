## 5.1. Enum failure modes reproduced locally

The following programs simulate mistakes that matter when values cross versions, build pipelines or registries. They use local data and tools; the database and outage stories formerly associated with this page are not evidence of actual production incidents. Diagnose the observable failure, preserve the relevant contract and verify the repair in the consuming environment.

Examples use TypeScript 7.0.2 and Node.js 20.20.2, verified 2026-10-16. Save each named file in a fresh directory without tsconfig.json. Build with `tsc --strict --noUncheckedIndexedAccess --removeComments --target es2022 --module commonjs --outDir out FILE.ts`, then run `node out/FILE.js`. For a marked negative, activate one comment in a separate copy and replace --outDir out with --noEmit. Both programs contain regular enums and intentionally fail --erasableSyntaxOnly with TS1294.

### 1) **A declaration edit can reinterpret an unchanged stored number**

Save history.ts:

```typescript
export {};
enum Before { New, Paid, Shipped }
enum Inserted { New, Paid, Refunded, Shipped }
enum Stable { New = 0, Paid = 1, Refunded = 3, Shipped = 2 }
const stored: number = 2;
console.log(stored, Before[stored], Inserted[stored], Stable[stored]);
console.log(Before.Shipped, Inserted.Shipped, Stable.Shipped);
function expectCode(actual: number, expected: number): void {
  if (actual !== expected) throw new Error("wire code changed");
}
expectCode(Stable.New, 0);
expectCode(Stable.Paid, 1);
expectCode(Stable.Shipped, 2);
expectCode(Stable.Refunded, 3);
console.log("stable contract checked");
```

The output is `2 Shipped Refunded Shipped`, `2 3 2` and `stable contract checked`. No stored row changed; the new unanchored declaration assigns another meaning to 2. The stable replacement retains all old meanings and assigns the new member an unused code. These explicit values can be reordered without positional renumbering, but editing an initializer still changes the contract.

Change only Stable.Shipped to 4. The program still type-checks, then expectCode throws wire code changed. A successful type check does not encode historical storage agreements; the runtime expectations supply that separate test. String values avoid positional numbering but can also be renamed or reused incorrectly. Numeric-to-string migration needs compatibility work for existing data and consumers, not an automatic substitution. The [numeric owner](<../1. Enum Mechanics/1.1. Numeric enums auto values and reverse mapping.md>) explains numbering, anchors and duplicate reverse entries; this exercise tests cross-version meaning.

### 2) **Distinguish source transforms from ambient publication failures**

A report that mentions const enum is not enough to infer its failure mode. First establish what files the consumer actually receives, which tool/version transforms them and whether a runtime value exists. The [pinned const-enum fixture](<../2. Enums vs Erasable Alternatives/2.1. const enum inlining and isolatedModules danger.md>) owns the complete runnable projects and commands. Its local and exported source enums run under tsc, esbuild 0.28.2 and the tested Babel 8 modes. Cross-file source use is not inherently impossible.

| Observation in that fixture | Actual boundary | Repair to verify |
|---|---|---|
| A whole-program build prints declared 1 beside provider 2 | An ambient const enum supplied stale inlined constants | Align declarations with runtime behavior and test the consumer artifact |
| A separately transformed consumer reads a missing Code object | The ambient description supplied no runtime table | Supply a matching runtime export or use a supported publication strategy |
| Isolated checking reports TS2748 for Code member reads | Ambient const-enum references need declaration constants | Change the publication contract rather than assuming all source const enums are forbidden |
| Native strip-only execution rejects a local enum declaration | The source uses syntax needing transformation | Use a supported transform or an explicitly tested erasable replacement |

The missing ambient-object experiment produces TypeError when reading Code.Ready; it is not an invented import-time ReferenceError for every esbuild build. Some missing-module situations instead fail in resolution. Name the actual observed error and its cause. Type-only imports cannot supply runtime constants, and a plain enum or const object still needs a compatible runtime artifact and import path. The [Handbook publication discussion](https://www.typescriptlang.org/docs/handbook/enums.html#const-enum-pitfalls) addresses ambient const-enum version and provider risks; the tested modes in the tooling owner establish their current bounds.

### 3) **A finite registry can be complete while a parallel open registry misses an event**

Save registry.ts. Scroll is already in the enum, so the missing handler is observed now rather than left as a future comment.

```typescript
export {};
enum EventKind { Click = "CLICK", Key = "KEY", Scroll = "SCROLL" }
type Handler = (at: number) => string;
const loose: Record<string, Handler> = {
  CLICK: at => `click:${at}`,
  KEY: at => `key:${at}`
};
const complete: Record<EventKind, Handler> = {
  [EventKind.Click]: at => `click:${at}`,
  [EventKind.Key]: at => `key:${at}`,
  [EventKind.Scroll]: at => `scroll:${at}`
};
console.log(loose[EventKind.Scroll]?.(2) ?? "missed", complete[EventKind.Scroll](2));
const wrong: Record<EventKind, Handler> = {
  ...complete,
  [EventKind.Scroll]: at => `key:${at}`
};
console.log(wrong[EventKind.Scroll](2));
console.log(typeof loose[EventKind.Scroll]);
// const missing: Record<EventKind, Handler> = { [EventKind.Click]: () => "click", [EventKind.Key]: () => "key" }; // TS2741
// loose[EventKind.Scroll](2); // TS2722 with noUncheckedIndexedAccess
```

The output is `missed scroll:2`, `key:2` and `undefined`. Optional calling prevents a crash but silently follows the missing-handler policy chosen by the code. The finite Record requires Scroll's key; its wrong variant still compiles because returning key:2 has the declared string type. Coverage and callback meaning are different checks.

Practice: add Resize = "RESIZE" to EventKind. Complete now fails with TS2741. Add its callback returning resize followed by the numeric timestamp, then print `complete[EventKind.Resize](3), loose[EventKind.Resize]?.(3) ?? "missed"`. The expected line is `resize:3 missed`. The open registry remains open, while the finite one tracks required membership. Its purpose is to serve the declared enum's events, so deriving its contract is useful. A genuinely open plugin registry can instead be represented with an object or Map and an explicit presence/registration policy; no single representation is mandatory for every registry.

### 4) **A reverse lookup and a type predicate are not automatic parser coverage**

Numeric reverse reads translate property keys to names. Under the index option they can be string | undefined; without it, a missing entry can still be undefined at runtime despite a declared string result. An in check also sees inherited keys. Neither is the same contract as admitting a recognized numeric value. The [actual member/parser experiment](<../3. Literals and Nominal Patterns/3.2. Exhaustive switches over enums and unions.md>) demonstrates both distinctions and preserves zero through an explicit undefined test.

That experiment also adds Critical to an enum: the handler's never sink fails, but fixing the handler does not update its independent parser. The [integrated review](<../4. Important points to remember/4.1. Enums checklist mental models mentors insist on.md>) exercises the same separation across action registration and wire-status parsing. An asserted predicate return type can lie too; check its actual admission behavior instead of treating the annotation as a validated implementation. If external strings or names are the intended domain, parse them into the chosen finite contract before relying on finite dispatch.

### 5) **Common confusion**

An unchanged database schema does not guarantee unchanged code meanings. A passing library build does not establish a different consumer's transform behavior. A complete finite Record does not prove callback semantics, and an updated switch does not prove parser completeness. Each failure needs a test at its own boundary.

Conversely, a fallback or open registry is not automatically a defect. Its behavior must match the intended contract. In the registry program, missed is explicitly observable; whether that policy is acceptable depends on whether Scroll must be processed. Do not replace that decision with a claim that all open keys, reverse names or enum declarations are forbidden.

### 6) **Performance note**

The failure mechanisms here concern compatibility and correctness. Enum initialization, callback lookup and calls, property checks and runtime expectations remain after type erasure. No benchmark establishes fixed table bytes, checker complexity, validation overhead or financial incident cost. Measure the actual consumer artifact if representation cost matters; preserve its meaning before optimizing it.

### 7) **Mentor note**

Have the learner demonstrate a change that builds but fails the intended contract: edit a stable code, retain the wrong Scroll callback or repair a member handler without its parser. Require the observed output or exception and the smallest repair. For a tooling report, require the actual supplied declaration, runtime module and transform command before accepting a guessed cause.
