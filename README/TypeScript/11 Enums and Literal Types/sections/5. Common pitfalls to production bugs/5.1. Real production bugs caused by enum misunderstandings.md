## 5.1. Real production bugs caused by enum misunderstandings

### 1) **Inserted enum member renumbered persisted order statuses** (auto-values shifted in storage)

**Definition** — an `OrderStatus { New, Paid, Shipped }` enum (auto 0/1/2) persisted raw numbers to Postgres; a `Refunded` member inserted between `Paid` and `Shipped` renumbered `Shipped` 2→3 — historical shipped rows (stored `2`) reinterpreted as refunded overnight, finance reports restated revenue as refunds, and no code changed behavior (every comparison still "worked" — against shifted meanings).

**What problem it solves / history** — position-coupled persistence treats declaration order as schema — an invariant no migration, test, or review checks (schema unchanged, types green, data reinterpreted). Explicit stable codes (`New = 1, Paid = 2, …`, append-only) decouple meaning from position: insertion becomes additive, reordering becomes cosmetic, and history stays interpretable under any future edit.

**Modern guidance** — as of TypeScript 5.9 era (Aug 2026: TS 5.9 stable, 6.0 beta; Node 24 Active LTS), anchor every persisted enum member explicitly with a comment forbidding reorder/removal (`// stable wire codes — append only`); prefer string codes for new persisted sets (self-describing in dumps, immune to position entirely). Add a test asserting each member's value (the test *is* the stability contract — renumbering breaks it loudly).

**Runnable example** — anchored codes survive insertion (good vs bad, `tsc --strict`):

```typescript
// good — explicit stable codes: insertion is additive, history immune
enum OrderS { New = 1, Paid = 2, Shipped = 3 } // append Refunded = 4 — 1..3 untouched
function labelS(s: OrderS): string {
  switch (s) {
    case OrderS.New: return "new";
    case OrderS.Paid: return "paid";
    case OrderS.Shipped: return "shipped";
    default: { const n: never = s; throw new Error(`unhandled ${String(n)}`); }
  }
}
console.log(labelS(OrderS.Paid), OrderS.Shipped); // paid 3 — codes stable across edits

// bad — auto-values persisted: insertion renumbers followers silently
enum OrderB { New, Paid, Shipped } // stored 0,1,2...
// database rows hold 2 meaning Shipped; inserting Refunded before Shipped shifts it to 3
// fix — explicit anchors + append-only + value-asserting tests (stability as tested contract)
console.log(OrderB.Paid); // 1 — position-coupled today, reinterpreted tomorrow
```

**Common confusion** — "migrations catch renumbering" — schema migrations track *columns*, not *value meanings* (no migration runs on enum insertion — that's precisely why it's silent). "string codes avoid this entirely" — true for new sets (prefer them); legacy numeric sets still need anchors + tests (migration to strings is itself a data migration — plan it, don't assume it). "tests can't cover declaration order" — value-assertion tests (`expect(OrderS.Shipped).toBe(3)`) cover exactly that — cheap, permanent, loud on insertion.

**Performance note** — anchors cost zero (same emit, explicit values); the incident cost data reinterpretation + restatement + backfill — orders of magnitude beyond any declaration verbosity.

**Mentor note** — insert a member into an unanchored persisted enum live and ask "which historical rows changed meaning?" (all followers — without touching storage) — position-coupled persistence in one edit. Gate: persisted enums without explicit codes + value tests fail review unconditionally.

String enums intent and no reverse mapping.md>); exhaustiveness → [3.2. Exhaustive switches](<../3. Literals and Nominal Patterns/3.2. Exhaustive switches over enums and unions.md>).

### 2) **`const enum` vanished under esbuild and crashed at import** (cross-file inlining impossible)

**Definition** — a shared package exported `const enum Status` consumed by an esbuild-bundled app: library CI (tsc) green, app production crashing `ReferenceError: Status is not defined` — esbuild emitted a value reference to a table that was never emitted (inlining needs the defining file; per-file transpilation never sees it). The crash hit 100% of loads: import-time, unconditional, invisible to library tests.

**What problem it solves / history** — `export const enum` from transpiled packages is pipeline-dependent breakage (works under tsc-programs, crashes under esbuild/swc/Babel/Vite) — invisible to the side that ships it (library CI green), total for the side that consumes it (app down). The `isolatedModules` error exists to convert this into an authoring-time failure; where it was disabled or ignored, the incident is the teacher.

**Modern guidance** — as of TypeScript 5.9 era, never export `const enum` from shared packages (union + `as const` object, or plain enum — see [2.1. const enum](<../2. Enums vs Erasable Alternatives/2.1. const enum inlining and isolatedModules danger.md>)); enable `isolatedModules` in every tsconfig touching shared code (the error fires at authorship, not at customer load); smoke-test shared packages under the *consumer's* pipeline (esbuild bundle import, not just tsc typecheck) before release.

**Runnable example** — pipeline-universal exports (good vs bad, `tsc --strict`):

```typescript
// good — union + const object: importable values on every pipeline, zero inlining needed
export const STATUS_MAP = { Idle: 0, Done: 1 } as const;
export type StatusU = keyof typeof STATUS_MAP; // "Idle" | "Done"
console.log(STATUS_MAP.Idle); // 0 — value reference, emitted table, universal access

// bad — exported const enum: tsc-green library, esbuild-red consumers (kept non-exported here so docs compile)
// const enum Shared { Idle, Done } // same-file use only (inlines fine under tsc)...
// ...consumed cross-file via esbuild: ReferenceError (no table emitted anywhere to reference)
// fix — STATUS_MAP pattern (or plain enum): shared values need runtime identity somewhere
export enum SharedPlain2 { Idle, Done }
console.log(SharedPlain2.Idle.toFixed(0)); // 0 — emitted table, every pipeline resolves it
```

**Common confusion** — "library CI passing proves safety" — CI runs the *library's* pipeline (tsc), not each consumer's (esbuild/swc/Babel) — pipeline-dependent breakage needs consumer-pipeline smoke tests, which library CI rarely runs. "type-only imports fix value uses" — `import type` erases (no runtime reference — no crash *and* no value); value uses need emitted values, period. "one bundler's behavior" — architectural (per-file transpilation cannot inline cross-file by design) — shared by esbuild, swc, Babel, Vite, and Node stripping alike.

**Performance note** — union + const-object costs one small table (same as plain enum, half of numeric reverse) — the library tax for universality, tens of bytes. The incident cost total outage per deploy until rollback — incomparable scales.

**Mentor note** — consume one shared `const enum` via esbuild live and watch the `ReferenceError` — pipeline-dependent breakage demonstrated beats documented. Rule: `export const enum` fails review unconditionally; same-file `const enum` needs its compilation-unit comment.

### 3) **Reverse-mapped lookup widened to `string` and skipped validation** (unguarded codes into exhaustive switches)

**Definition** — an API layer converted numeric status codes via `Status[code] ?? "unknown"` (typed `string`) and fed the result into business logic typed for members — invalid codes (`99`) flowed as `"unknown"`-or-worse through stringly paths that *looked* handled (a `default` returning stale data) while the exhaustive member switch downstream never saw the input (it received `string`, which no member-switch can exhaust).

**What problem it solves / history** — reverse-mapped strings *feel* validated ("we looked it up in the enum!") while typing `string` (the lookup proves nothing — out-of-range codes yield `undefined`→fallback, all typed `string`). Validation-into-members (`fromCode(code): Status | undefined` + narrowing) restores the finite type *before* logic; reverse strings stay in display positions where widening is harmless.

**Modern guidance** — as of TypeScript 5.9 era, validate numeric codes into enum/union members at ingestion (explicit validator returning `T | undefined`, narrowed before use); render via reverse maps only at display leaves; never branch business logic on reverse-mapped strings. See [3.2. Exhaustive switches](<../3. Literals and Nominal Patterns/3.2. Exhaustive switches over enums and unions.md>) promise 2 for the full validate-then-prove pattern.

**Runnable example** — validate into members, render from tables (good vs bad, `tsc --strict`):

```typescript
// good — validator restores finiteness; logic switches on members with a sink
enum Stt { Idle = 0, Done = 1 }
function fromCode(code: number): Stt | undefined {
  return code === 0 ? Stt.Idle : code === 1 ? Stt.Done : undefined;
}
function next(s: Stt): string {
  switch (s) {
    case Stt.Idle: return "start";
    case Stt.Done: return "again";
    default: { const n: never = s; throw new Error(`unhandled ${String(n)}`); }
  }
}
const s = fromCode(99);
console.log(s === undefined ? "rejected" : next(s)); // rejected — invalid code handled, not widened

// bad — reverse string into logic: widened input, unprovable branches
function nextBad(code: number): string {
  const name = Stt[code] ?? "unknown"; // string — member identity lost at lookup
  return name === "Idle" ? "start" : "???"; // best-effort matching, no sink possible
}
// fix — fromCode + member switch: precision restored before logic runs
console.log(nextBad(99)); // ??? — invalid code, silent gap, zero diagnostics
```

**Common confusion** — "the lookup validated the code" — lookups *translate* (valid or not, something stringly comes out); validators *decide* (`T | undefined` with narrowing) — translation without decision is the incident. "`?? "unknown"` handles invalidity" — handles *display* (renders something) while logic downstream still receives `string` (proves nothing) — handle invalidity by *rejection* (undefined + early return), not by fallback strings. "explicit validators duplicate the enum" — validators enumerate members once (like switches) — duplication that the `never` sink keeps in sync automatically.

**Performance note** — one comparison per ingestion (negligible vs the switch it protects); widened logic costs missing-branch incidents (unbounded). Validate once at the boundary, switch narrowly everywhere inside.

**Mentor note** — hover `Stt[code]` (`string`) vs `fromCode(99)` (`Stt | undefined`) — widened vs restorable precision in one tooltip pair. Exercise: convert one reverse-lookup logic path to validate-then-switch and count the new sink protections (each a future member-addition caught).

### 4) **Stringly `Record<string, Handler>` duplicated the enum table and drifted** (parallel map missed a member)

**Definition** — an event-handler registry typed `Record<string, Handler>` duplicated an existing event enum member-by-member (hand-listed keys mirroring `Event.Click`, …) — the enum gained `Scroll`, the registry didn't (nothing linked them), scroll events dispatched to `undefined` handlers (`?.` fallback rendering nothing) for a release. Parallel structures drift; derived structures track.

**What problem it solves / history** — mirrored registries (hand-listed keys beside the enum they serve) double every addition's edit sites and halve each site's visibility (the registry file looks complete — it lists *several* handlers — while missing one). Derived registries (`Record<Event, Handler>` or template-mapped tables from the member union) make absence a type error (TS2741) instead of a dispatch-time `undefined`.

**Modern guidance** — as of TypeScript 5.9 era, derive registries from their key source (`Record<Event, Handler>`, `` { [K in Ev as `on${K}`]: …} `` — see [09/3.2](<../../../09 Utility Types and Type Transformations/sections/3. Transformations in Practice/3.2. Template literal composition Capitalize handlers and routes.md>)); never hand-mirror finite key sets in a second structure. When the key source is an enum, `Record<Enum, …>` enforces per-member handlers with the same exhaustiveness spirit as switches.

**Runnable example** — derived registry proves coverage (good vs bad, `tsc --strict`):

```typescript
// good — registry derived from the key source: absence errors at registration
enum Evt { Click = "CLICK", Key = "KEY" }
type H = (at: number) => void;
const reg3: Record<Evt, H> = { [Evt.Click]: (at) => console.log(at), [Evt.Key]: (at) => console.log(at) };
reg3[Evt.Click](1); // 1 logged
// Evt gains Scroll → Record<Evt, H> demands a Scroll handler HERE (TS2741 until added)

// bad — hand-mirrored stringly registry: drifts without diagnostics
const looseReg: Record<string, H> = { CLICK: (at) => console.log(at), KEY: (at) => console.log(at) };
// Evt gains Scroll → looseReg still compiles (string keys accept anything, require nothing)
// looseReg["SCROLL"]?.(2); // undefined at runtime — event dispatched to nothing
// fix — Record<Evt, H>: the registry tracks the source instead of mirroring it
console.log(Object.keys(looseReg).length); // 2 — complete-looking, one member behind
```

**Common confusion** — "stringly registries are more flexible" — flexibility to *omit* (absence) and *mistype* (typos) is the incident, not a feature — open registries (plugins) want `Map` + validation, not `Record<string>`. "derivation couples modules" — derivation *links* what reality already couples (registry serves the enum — the coupling exists; derivation makes it compiler-visible instead of convention-hoped). "computed keys hurt readability" — `[Evt.Click]: …` reads identically to `CLICK: …` while tracking renames — readability preserved, drift deleted.

**Performance note** — derived registries cost the same object literal (identical emit); check-time adds per-key verification (O(members), cached once) — the coverage proof for free.

**Mentor note** — add a member to the enum and watch the derived registry error while the stringly one stays green — coverage-proof vs coverage-theater in one member. Gate: hand-mirrored finite registries fail review; derived registries (or validated open ones) are the only accepted shapes.
