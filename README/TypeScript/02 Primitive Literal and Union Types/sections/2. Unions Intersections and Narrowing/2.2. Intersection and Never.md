## 2.2. Intersection and Never

### 1) **Definition** (A & B)

**Definition** — `A & B` means "both A and B at once" — the value must satisfy *all* members. For object types, that merges properties; for primitives, it often collapses to `never` if no value can satisfy both.

```typescript
type A = { name: string };
type B = { age: number };
type C = A & B; // { name: string; age: number }

const c: C = { name: "Ava", age: 30 }; // must have both

// primitive intersection usually never:
type StringAndNumber = string & number; // never — no value is both
// string literal intersection can narrow:
type Greeting = "hello" & string; // "hello" (literal satisfies string)
type Impossible = "hello" & "world"; // never — distinct literals share no value

// practical: extend with intersection (preferred over interface extends for types)
type Timestamps = { createdAt: Date; updatedAt: Date };
type SoftDelete = { deletedAt: Date | null };
type Entity = A & Timestamps & SoftDelete;
```

### 2) **Use** (mixins)

Intersections compose behavior without inheritance hierarchies:

```typescript
// mixin-like composition
type HasId = { id: string };
type HasTimestamps = { createdAt: Date };
type HasSoftDelete = { deleted: boolean };

type User = HasId & HasTimestamps & { name: string };
type Article = HasId & HasTimestamps & HasSoftDelete & { title: string };

// function that requires both capabilities
function touch<T extends HasId & HasTimestamps>(entity: T): T {
  return { ...entity, createdAt: new Date() };
}

// intersection also powers utility types (05/06 domains)
type Overwrite<T, U> = Omit<T, keyof U> & U;
type UserPatch = Overwrite<User, { name?: string }>;
```

### 3) **Pitfall** (never from impossible)

**Pitfall — impossible intersection silently becomes `never`:**

```typescript
type A1 = { kind: "a"; x: string };
type B1 = { kind: "b"; x: string };
type Both = A1 & B1; // { kind: never; x: string } — kind "a" & "b" = never, so no value satisfies Both

declare const both: Both;
// both.kind is never — you can never construct Both, often a bug

// symptom: function accepting never is uncallable
function takesBoth(b: Both) {}
// takesBoth({ kind: "a", x: "hi" }); // error — kind "a" not assignable to never
// takesBoth({ kind: "b", x: "hi" }); // likewise

// fix: you meant union, not intersection
type Either = A1 | B1; // ok — either shape

// detecting never
type IsNever<T> = [T] extends [never] ? true : false;
type Test = IsNever<Both extends never ? never : unknown>; // distribution nuance — see 06

// deliberate never for exhaustiveness
function assertNever(x: never): never { throw new Error(`Unhandled: ${String(x)}`); }
```

### Mentor note

Teach "union is OR, intersection is AND" with Venn diagrams. Then show the `A1 & B1` never-trap: students who can predict when `&` yields `never` stop mis-modeling composition.

### Common confusion

- "`A & B` overwrites `A`'s props" — no, it requires *both*; conflicting prop types intersect (`string & number = never`). Overwriting is `Omit<A, keyof B> & B`.
- "`never` is an error" — it's a valid type (empty set). A function returning `never` never returns; a value of type `never` cannot exist.
